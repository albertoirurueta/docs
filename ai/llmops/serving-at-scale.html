Serving at Scale

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Written on 2026-10-01 against vLLM 0.30.0, SGLang 0.5.21, KServe 0.21.0 and Python 3.12 with httpx and numpy; the full list is the version baseline on the landing page. vLLM, SGLang and KServe could not be started in the environment where this page was written, so every command, manifest and flag below was written from the official documentation linked after it and was not run, and the load-test harness was not executed against a live server. Metric names and command-line flags in these engines change between releases, so each name is a starting point to confirm against /metrics and --help on the version you deploy. For the same reason the page quotes no throughput, latency or price figures: it gives the definitions and a harness, and the numbers have to come from your hardware, your model and your traffic.

The DocsAssistant in the running scenario calls an OpenAI-compatible endpoint behind a gateway (Deployment and Release Patterns). This page is about what sits behind that endpoint when you host the model yourself: how to run it, how to size it, how to scale it, and how to measure it. Installing and using the engines is covered in vLLM and SGLang, the single-host operational checklist is on Running Local LLMs in Production, and the kernel and quantisation techniques are in Inference Optimization. Huyen’s AI Engineering and Aryan’s LLMOps both treat inference optimisation and latency/throughput trade-offs as an operations concern; the engine flags and metric names here are taken from the current documentation, because the books pre-date these releases.

Why LLM serving is not ordinary web serving

A conventional request handler does a bounded amount of work and returns. An LLM request has two phases with different bottlenecks, and an unbounded second phase:

  1. Prefill processes the whole prompt in one pass. It is mostly compute-bound, and its cost grows with prompt length.

  2. Decode generates one token per step, each step reading the model weights and the request’s cached keys and values from GPU memory. It is mostly memory-bandwidth-bound, and it lasts as long as the answer.

The consequences shape everything below: a request occupies GPU memory for as long as it streams, request length is not known in advance, and a single long prompt can stall the short ones queued behind it. Capacity therefore depends on memory and on scheduling at least as much as on raw compute.

Run the engine as a service

Both engines expose an OpenAI-compatible HTTP server, so the gateway and the application do not change when you swap one for the other.

vLLM: a production-shaped launch for the DocsAssistant chat model
export VLLM_API_KEY="${DOCSASSISTANT_VLLM_KEY}"   # injected by the orchestrator, never committed

vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --served-model-name docsassistant-chat \
  --max-model-len 16384 \
  --gpu-memory-utilization 0.90 \
  --max-num-seqs 128 \
  --enable-prefix-caching \
  --host 0.0.0.0 --port 8000

Source: vLLM — OpenAI-compatible server and vLLM — Engine arguments. Recent vLLM releases enable prefix caching by default; the explicit flag is harmless and documents the intent. The four flags that matter most for capacity are:

Flag What it controls

--max-model-len

The longest prompt-plus-output a request may have. It bounds the worst-case KV memory per request, so lowering it from the model’s maximum is the cheapest way to fit more concurrent requests.

--gpu-memory-utilization

The fraction of GPU memory the engine may claim for weights, activations and KV cache. What remains after the weights is the KV-cache pool.

--max-num-seqs

The cap on sequences scheduled in one step. It is the upper bound on concurrency inside one replica.

--max-num-batched-tokens

The token budget per scheduler step. It trades prefill throughput against how long a decode step can be delayed by a prefill.

SGLang is launched with its own server module and takes equivalent options.

SGLang: the same model behind an OpenAI-compatible endpoint
python -m sglang.launch_server \
  --model-path meta-llama/Llama-3.1-8B-Instruct \
  --served-model-name docsassistant-chat \
  --context-length 16384 \
  --host 0.0.0.0 --port 30000 \
  --enable-metrics

Source: SGLang documentation (server arguments and the OpenAI-compatible APIs pages). The flag names were read from that documentation and not run; confirm them with python -m sglang.launch_server --help for the installed version. SGLang’s distinguishing feature is RadixAttention, a radix-tree cache of prefixes across requests, described in vLLM and SGLang and in the Zheng et al. paper listed in the references.

Continuous batching

Static batching waits for a group of requests, runs them together and returns when the longest one finishes, so short answers wait for long ones and the GPU idles in the gaps. Continuous batching (also called iteration-level scheduling) re-forms the batch at every decode step: a finished sequence leaves immediately and a waiting request joins, with its prefill interleaved. Both vLLM and SGLang do this by default; there is no flag to turn on. What you control is the budget it works within:

  • More allowed sequences (--max-num-seqs) raises throughput until KV memory or compute saturates, and raises per-request latency as each step does more work.

  • A larger per-step token budget lets prefill finish sooner and so improves time to first token, at the cost of longer pauses in the streams that are already decoding. Chunked prefill, which both engines support, splits a long prompt across steps to soften that pause.

The practical rule is to treat the batch limits as the knob that moves you along the latency/throughput curve, and to pick the point from your load-test results and your latency objectives, not from a default.

Prefix caching and the DocsAssistant prompt

Every DocsAssistant request starts with the same system prompt and, for many requests, the same retrieved passages for popular documentation pages. Automatic prefix caching stores the KV blocks of previously seen prompt prefixes and reuses them when a new request starts with the same tokens, so prefill for the shared part is skipped. Two operational consequences follow:

  1. Put stable content first. The system prompt and tool definitions go at the start; the retrieved passages and the user’s question go last. A timestamp or a request id near the top of the prompt makes every prefix unique and defeats the cache.

  2. Measure the hit rate, do not assume it. The engines export prefix-cache queries and hits as metrics; compare them before and after a prompt change. The prompt-ordering advice is the same one the hosted providers give for their own prompt caching, covered on Caching, Latency and Cost.

When several replicas run behind a load balancer, a plain round-robin scatters the same prefix across replicas and lowers each one’s hit rate. Prefix-aware or session-affinity routing recovers it; whether to build that is a decision to take with the measured hit rate in hand.

Source: vLLM — Automatic prefix caching.

size_kv.py: per-token KV bytes and a concurrency estimate from a model’s config.json
import json
import sys
from pathlib import Path


def kv_bytes_per_token(config: dict, bytes_per_element: int = 2) -> int:
    layers = config["num_hidden_layers"]
    kv_heads = config.get("num_key_value_heads", config["num_attention_heads"])
    head_dim = config.get("head_dim") or config["hidden_size"] // config["num_attention_heads"]
    return 2 * layers * kv_heads * head_dim * bytes_per_element


def max_sequences(pool_bytes: float, tokens_per_sequence: int, per_token: int) -> int:
    return int(pool_bytes // (tokens_per_sequence * per_token))


if __name__ == "__main__":
    config = json.loads(Path(sys.argv[1]).read_text())
    per_token = kv_bytes_per_token(config)
    print(f"KV cache per token: {per_token} bytes")
    # The pool size comes from the engine's startup log, not from this script.
    pool_gib = float(sys.argv[2])
    tokens = int(sys.argv[3])
    print(f"Sequences of {tokens} tokens in a {pool_gib} GiB pool:",
          max_sequences(pool_gib * 2**30, tokens, per_token))

Source: the field names (num_hidden_layers, num_key_value_heads, head_dim) follow the Hugging Face Transformers model configuration, Transformers — Configuration; the cache layout is described in vLLM — Paged Attention. The engine reports the actual KV pool size and the number of tokens it can hold in its startup log, which is the authoritative value; use the script to reason about what changes if you alter the context length, the cache dtype or the model, and to check the engine’s number for plausibility. Models with sliding-window or hybrid attention layers need fewer cache entries than this formula gives, so treat it as an upper bound for those architectures.

Parallelism: tensor, pipeline, data

A single replica fits on one GPU until the weights plus a useful KV pool do not. The three ways of using more devices answer different problems:

Strategy What it splits When to reach for it

Tensor parallelism

Each layer’s matrices across the GPUs of one node (--tensor-parallel-size).

The model does not fit on one GPU, or you need more KV pool. It communicates on every layer, so it wants a fast interconnect and is normally kept within a node.

Pipeline parallelism

Consecutive groups of layers across GPUs or nodes (--pipeline-parallel-size).

The model does not fit on one node, or the interconnect between GPUs is slow. It communicates less often but can leave devices idle between stages.

Data parallelism

Whole copies of the model, each serving different requests.

The model fits, and you need more throughput or availability. It is the simplest and the one to prefer first.
vLLM: a larger model split across the GPUs of one node (each replica runs this same command)
vllm serve meta-llama/Llama-3.3-70B-Instruct \
  --served-model-name docsassistant-chat-large \
  --tensor-parallel-size 4 \
  --max-model-len 16384

Source: vLLM — Parallelism and scaling. That page also documents pipeline, data and expert parallelism and multi-node launches; the exact flags for the data-parallel mode in a single server are version dependent, so the DocsAssistant uses the more conventional alternative: several independent replicas behind the gateway or a Kubernetes Service, each started with the same command. The rule of thumb is to use the smallest tensor-parallel degree that fits the model with a useful KV pool, then add throughput with replicas.

Disaggregated prefill and decode

Because prefill is compute-heavy and decode is bandwidth-heavy, running both on the same GPUs makes each interfere with the other: a long prefill delays the decode steps of streaming users, which shows up as jitter in the time between tokens. Disaggregated serving dedicates one pool of workers to prefill and another to decode and transfers the KV cache between them, so each pool can be sized and tuned independently and the two latency measures are decoupled.

vLLM documents a disaggregated-prefill feature and SGLang documents a prefill/decode disaggregation mode; both rely on a KV-transfer connector and, in their documentation, are presented as evolving features. The extra moving parts are real: a transfer fabric between the pools, a router that sends each request to a prefill worker and then a decode worker, and two sets of capacity to monitor. For the DocsAssistant, whose prompts are moderate and whose answers are short, a single pool with chunked prefill is the sensible default; disaggregation is worth evaluating when long prompts (large retrieved contexts) and strict inter-token latency coexist and your load test shows the interference. It is a reason to test, not a recommendation.

The request path through a disaggregated deployment is:

flowchart LR C[Client] --> R[Router] R --> P[Prefill worker pool] P -->|KV cache transfer| D[Decode worker pool] D -->|streamed tokens| C P -.-> MP["Prefill metrics: TTFT"] D -.-> MD["Decode metrics: TPOT"]

Source: vLLM — Disaggregated prefilling and the SGLang documentation for prefill/decode disaggregation at docs.sglang.io; the DistServe paper in the references explains the motivation.

Metrics the engines export

Both engines serve Prometheus text at /metrics. The signals that matter for scaling and alerting are:

Signal Why it matters

Requests waiting

The queue depth. Rising means demand exceeds capacity at the current scale; this is the earliest saturation sign.

Requests running

The batch size. Together with the waiting count it says whether you are at --max-num-seqs.

KV-cache utilisation

The fraction of the KV pool in use. Near 1, the scheduler preempts or stops admitting requests and TTFT climbs.

Time to first token, per-token latency and end-to-end latency histograms

The user-visible objectives, as histograms so that percentiles can be computed.

Prefix-cache queries and hits

The hit rate, which tells you whether prompt ordering is working.

Token counters (prompt and generation)

Throughput, and the input for cost attribution in Cost Management.

The metric names in vLLM carry a vllm: prefix (for example vllm:num_requests_waiting and the KV-cache usage gauge) and have been renamed across releases, notably for the KV-cache usage and per-token latency histograms; check the names in the /metrics output of your version before writing rules. Dashboards and alert rules built on these signals, together with the golden signals for the whole application, are the subject of Metrics, Dashboards and Alerting; the basics of scraping and recording rules are in Instrumenting Applications.

Source: vLLM — Metrics and the SGLang production-metrics page in its documentation.

Autoscaling on queue depth and KV-cache utilisation

CPU utilisation is a poor scaling signal for a GPU-bound engine: the process looks busy long before it is saturated, and GPU utilisation as reported by the driver stays high even when the batch is small. Two engine-level signals are better:

  1. Queue depth (requests waiting). A sustained non-zero queue means requests are waiting for capacity. It reacts quickly and is easy to reason about: add a replica when the waiting count per replica stays above a threshold for a minute or two.

  2. KV-cache utilisation. A pool above a high fraction means new requests will soon be preempted or queued. It is a leading indicator for long-context traffic, where the queue stays empty until memory is suddenly exhausted.

Scale-up must be fast and scale-down slow. A new replica has to start a container, schedule onto a GPU node, download or mount the weights and load them, which takes minutes, so scale on a leading signal, keep a floor of warm replicas, and use a long stabilisation window before scaling down so a pause in traffic does not discard capacity you will need again. The following KEDA object scales a vLLM Deployment on both signals; it assumes Prometheus already scrapes the engine.

docsassistant-vllm-scaledobject.yaml: scale on queue depth and KV-cache utilisation
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: docsassistant-vllm
  namespace: docsassistant
spec:
  scaleTargetRef:
    name: docsassistant-vllm
  minReplicaCount: 2
  maxReplicaCount: 8
  cooldownPeriod: 600
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring.svc:9090
        query: avg(vllm:num_requests_waiting{namespace="docsassistant"})
        threshold: "4"
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.monitoring.svc:9090
        # Confirm the KV-cache usage metric name on /metrics for your vLLM version.
        query: max(vllm:kv_cache_usage_perc{namespace="docsassistant"})
        threshold: "0.8"

Source: KEDA — Prometheus scaler and KEDA — Scaling Deployments. The thresholds are placeholders to be set from the knee of your own load-test curve. The Kubernetes HorizontalPodAutoscaler with an external-metrics adapter can express the same rule if you do not run KEDA; see Kubernetes — Horizontal Pod Autoscaling.

Kubernetes and KServe

On plain Kubernetes the engine is a Deployment with a GPU resource request, a persistent volume for the model cache and a readiness probe on /health; the manifest is in the Docker and Kubernetes section of vLLM and SGLang. Three additions matter once you scale beyond one replica:

  • Warm start. Model loading dominates start-up time. Put the weights on a shared read-only volume or a pre-pulled image instead of downloading from a hub on every start, and give the readiness probe a generous initial delay.

  • Disruption and rollout. A PodDisruptionBudget and a rollout strategy that never removes the last ready replica keep the tier available during node drains and image updates.

  • Scheduling. Use node selectors or taints for GPU nodes so that unrelated workloads do not take them.

KServe adds a standard Kubernetes API for model serving: an InferenceService that bundles the runtime, the model location, scaling and revision handling. Its Hugging Face serving runtime can use vLLM as its backend and exposes an OpenAI-compatible interface.

KServe InferenceService using the Hugging Face runtime with the vLLM backend

KServe also documents newer resources aimed specifically at LLM serving, including autoscaling on engine metrics, so check the current pages for your version before choosing between the generic InferenceService and a dedicated LLM resource. Its value is the uniform API, canary traffic splitting between revisions (which pairs with Deployment and Release Patterns) and integration with the cluster’s autoscaling; if you already run one Deployment per model and a gateway in front, KServe is optional.

A load-test harness that measures TTFT and TPOT

An HTTP load tester that reports only requests per second is blind to the thing users feel, because a streaming response spends most of its life after the first byte. The harness below drives an OpenAI-compatible endpoint with streaming requests, records TTFT and TPOT per request, and computes percentiles and goodput. It supports two load models: closed loop (a fixed number of concurrent users, each sending the next request when the previous finishes) and open loop (requests arrive at a given rate regardless of how fast the server answers, which is how real traffic behaves and the only way to see a queue form).

loadtest.py: async streaming load test for an OpenAI-compatible endpoint
import argparse
import asyncio
import json
import os
import random
import time
from dataclasses import dataclass

import httpx
import numpy as np

BASE_URL = os.environ.get("LLM_BASE_URL", "http://localhost:8000/v1")
API_KEY = os.environ["LLM_API_KEY"]  # injected by the environment, never hard-coded
MODEL = os.environ.get("LLM_MODEL", "docsassistant-chat")


@dataclass
class Sample:
    ok: bool
    ttft: float = float("nan")
    tpot: float = float("nan")
    e2e: float = float("nan")
    output_tokens: int = 0


async def one_request(client: httpx.AsyncClient, prompt: str, max_tokens: int) -> Sample:
    body = {
        "model": MODEL,
        "messages": [{"role": "user", "content": prompt}],
        "max_tokens": max_tokens,
        "stream": True,
        "stream_options": {"include_usage": True},
    }
    headers = {"Authorization": f"Bearer {API_KEY}"}
    start = time.perf_counter()
    first = last = None
    chunks = 0
    completion_tokens = None
    try:
        async with client.stream("POST", f"{BASE_URL}/chat/completions", json=body, headers=headers) as resp:
            resp.raise_for_status()
            async for line in resp.aiter_lines():
                if not line.startswith("data: "):
                    continue
                payload = line[len("data: "):]
                if payload == "[DONE]":
                    break
                event = json.loads(payload)
                if event.get("usage"):
                    completion_tokens = event["usage"]["completion_tokens"]
                choices = event.get("choices") or []
                if choices and choices[0].get("delta", {}).get("content"):
                    now = time.perf_counter()
                    first = first or now
                    last = now
                    chunks += 1
    except (httpx.HTTPError, json.JSONDecodeError):
        return Sample(ok=False)
    if first is None:
        return Sample(ok=False)
    n = completion_tokens if completion_tokens is not None else chunks
    tpot = (last - first) / (n - 1) if n > 1 else float("nan")
    return Sample(ok=True, ttft=first - start, tpot=tpot, e2e=last - start, output_tokens=n)


async def closed_loop(prompts, users, duration, max_tokens):
    deadline = time.perf_counter() + duration
    samples: list[Sample] = []
    limits = httpx.Limits(max_connections=users + 8)
    async with httpx.AsyncClient(timeout=None, limits=limits) as client:
        async def user():
            while time.perf_counter() < deadline:
                samples.append(await one_request(client, random.choice(prompts), max_tokens))
        await asyncio.gather(*(user() for _ in range(users)))
    return samples


async def open_loop(prompts, rate, duration, max_tokens):
    samples: list[Sample] = []
    tasks = []
    limits = httpx.Limits(max_connections=None)
    async with httpx.AsyncClient(timeout=None, limits=limits) as client:
        end = time.perf_counter() + duration
        while time.perf_counter() < end:
            tasks.append(asyncio.create_task(one_request(client, random.choice(prompts), max_tokens)))
            await asyncio.sleep(random.expovariate(rate))  # Poisson arrivals
        samples = await asyncio.gather(*tasks)
    return list(samples)


def report(samples, duration, slo_ttft, slo_tpot):
    good = [s for s in samples if s.ok]
    print(f"requests: {len(samples)}  failed: {len(samples) - len(good)}")
    if not good:
        return
    for name, values in (("TTFT", [s.ttft for s in good]),
                         ("TPOT", [s.tpot for s in good if s.tpot == s.tpot]),
                         ("E2E", [s.e2e for s in good])):
        p50, p95, p99 = np.percentile(values, [50, 95, 99])
        print(f"{name:5s} p50={p50:.3f}s p95={p95:.3f}s p99={p99:.3f}s")
    meeting = sum(1 for s in good if s.ttft <= slo_ttft and (s.tpot != s.tpot or s.tpot <= slo_tpot))
    print(f"output tokens/s: {sum(s.output_tokens for s in good) / duration:.1f}")
    print(f"goodput (req/s meeting SLO): {meeting / duration:.2f}")


if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("--prompts", required=True, help="JSONL file with one {\"prompt\": ...} per line")
    ap.add_argument("--mode", choices=["closed", "open"], default="open")
    ap.add_argument("--users", type=int, default=16)
    ap.add_argument("--rate", type=float, default=2.0, help="requests per second (open loop)")
    ap.add_argument("--duration", type=float, default=120.0)
    ap.add_argument("--max-tokens", type=int, default=256)
    ap.add_argument("--slo-ttft", type=float, default=1.0)
    ap.add_argument("--slo-tpot", type=float, default=0.05)
    args = ap.parse_args()
    with open(args.prompts) as f:
        prompts = [json.loads(line)["prompt"] for line in f if line.strip()]
    run = (closed_loop(prompts, args.users, args.duration, args.max_tokens) if args.mode == "closed"
           else open_loop(prompts, args.rate, args.duration, args.max_tokens))
    report(asyncio.run(run), args.duration, args.slo_ttft, args.slo_tpot)

Source: OpenAI — Chat Completions for the stream and stream_options.include_usage fields, which vLLM and SGLang implement in their compatible servers (vLLM — OpenAI-compatible server); HTTPX — Async support for streaming. The harness is the DocsAssistant’s own and was not run. The default objectives in the arguments are placeholders, not recommendations.

How to use it so that the result means something:

  1. Use representative prompts. Build the JSONL file from sampled, anonymised DocsAssistant traffic, including the retrieved context, so that prompt length and prefix sharing match production. Synthetic short prompts overstate throughput and hide the effect of long contexts.

  2. Warm up, then measure. Discard the first minute; the first requests pay for cache fills and kernel compilation.

  3. Sweep the load. Run open-loop at increasing rates and plot goodput, TTFT percentiles and the engine’s queue depth against the rate. The knee, where TTFT percentiles turn upward and the queue stops draining, is the capacity of one replica at your objectives. Closed-loop runs find the concurrency at which a fixed user population saturates the engine.

  4. Isolate the variable. Change one thing between sweeps (context length, batch limits, quantisation, parallelism, prefix caching) and keep the hardware and prompts fixed.

  5. Watch the server while you test. Scrape the engine’s /metrics during the run and read KV-cache utilisation and preemption counts; a client-side latency rise that coincides with a full KV pool has a different fix from one that coincides with an empty queue.

  6. Keep it off production. Run against a dedicated environment, and cap the spend if the target is a paid endpoint.

Ready-made tools cover the same ground with more options: the benchmark command shipped with vLLM, and GuideLLM, which sweeps load levels automatically. The harness above is useful because you can read it, extend it to send the DocsAssistant’s tool-call or multi-turn patterns, and run it in CI against a staging endpoint. For load-testing the Spring Boot application that sits in front of the model, with thread pools and connection limits as the subject, see Performance Testing with JMeter; its tools do not measure TTFT or TPOT natively, which is why this page uses a streaming-aware client.

Source: vLLM — Benchmark CLI and GuideLLM.

Operating the tier

A short list of practices that follow from the above:

  • Set a latency objective per user-facing path in terms of TTFT and TPOT, and size by goodput at that objective, with headroom for a replica loss.

  • Cap request size at the edge. Enforce maximum prompt tokens and maximum output tokens in the gateway so that one request cannot occupy a disproportionate share of the KV pool.

  • Re-run the sweep on every change of engine version, model, quantisation or prompt shape. A faster engine release and a longer system prompt can cancel out, and only a measurement tells you which.

  • Alert on the leading signals, queue depth and KV-cache utilisation, before the lagging ones, latency and error rate, as described in Metrics, Dashboards and Alerting.

  • Track cost per token from utilisation. An idle GPU costs the same as a busy one, so the cost of a self-hosted token depends on how full you keep the replicas; the accounting is in Cost Management.

  • Plan the fallback. When the tier is saturated or down, the gateway routes to a hosted model or returns a graceful degradation, as set out in Deployment and Release Patterns.

  • Secure the endpoint. Keep the engine on a private network, require the API key, and keep keys in the orchestrator’s secret store; the security guidance of each engine is linked in the references. Threat modelling for model endpoints belongs to AI Security & Responsible AI, a separate sub-section.
