The 2026 Agent Frameworks Landscape

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Every version below was read from the framework’s own package registry (PyPI, Maven Central, npm, crates.io, NuGet) on 2026-09-28, and every capability cell was checked against the installed package’s public API or its official repository documentation on that date. Frameworks in this space release weekly; treat the table as a dated snapshot and re-check a framework’s own documentation before choosing it. The deeper, framework-specific material lives elsewhere in this AI section: the LangChain sub-section and the Spring AI sub-section cover those two frameworks in full.

2026 deprecations and migrations

Several frameworks that older books and tutorials build on were retired or superseded in 2025-2026. This matters when following a book’s code: an example can be conceptually sound and still not run.

The OpenAI Assistants API was sunset on 2026-08-26; its replacement is the Responses API with the Conversations API for state, plus the OpenAI Agents SDK for agent orchestration, and OpenAI’s migration guide maps threads, runs and assistants onto the new primitives (Assistants API migration guide). Code written against Assistants — including examples in books published before the sunset — no longer runs.

AutoGen and the agent features of Semantic Kernel have been superseded by the Microsoft Agent Framework, which reached general availability with version 1.0 on 2026-04-03; AutoGen is in maintenance mode, and Microsoft publishes migration guides from both (Microsoft Agent Framework blog).

Prompt flow is scheduled for retirement on 2027-04-20; new flows should be built elsewhere, and existing ones migrated before that date.

Two API changes inside living frameworks are worth knowing as well: LangChain 1.x replaced the 0.x create_react_agent with langchain.agents.create_agent plus middleware (see LangGraph v1 release notes), and CrewAI’s current model is Crews plus Flows.

Choosing a framework

There is no single best framework; there is a best fit for a team and a problem. Weigh:

  • Language and platform. Use what the team and the rest of the system already run: LangChain4j or Spring AI in a Java estate, Microsoft Agent Framework in .NET, Mastra in TypeScript, Rig in Rust, and any of the Python frameworks otherwise.

  • Control vs. convenience. Low-level graphs (LangGraph, Microsoft Agent Framework workflows) give full control of the loop and state; prebuilt agents (create_agent, OpenAI Agents SDK, CrewAI crews, Claude Agent SDK) are faster to start with and harder to bend.

  • Model coupling. Vendor SDKs (OpenAI Agents SDK, Claude Agent SDK) are tuned for their own models and platform; the others are model-agnostic. Check whether the provider-neutral ones support the features you need (prompt caching, reasoning controls) on your model.

  • State and durability. Long-running or human-in-the-loop agents need durable checkpoints and resumable runs (see Human-in-the-Loop).

  • Interoperability. MCP support is now table stakes; A2A support matters if your agents must work with other teams' agents (see Agent-to-Agent Protocol (A2A)).

  • Observability and evaluation. Prefer frameworks that emit OpenTelemetry GenAI spans or integrate with your tracing backend (see Observability for Agents).

  • Maturity and stability. A 0.x version number means breaking changes are expected; beta modules (LangChain4j’s agentic module) likewise. Budget for upgrades.

  • Lock-in. Keep business logic in plain functions and tools, and let the framework own only orchestration, so a later switch is a rewrite of the thin layer, not of everything.

One plain function, three frameworks' tool wrappers
# docsassistant/core.py -- business logic with no framework imports
from docsassistant.search import search_docs


def search_docs_core(query: str, k: int = 5) -> list[dict]:
    """Search this site's documentation; returns page paths, sections and snippets."""
    return search_docs(query, k=k)


# LangChain / LangGraph
from langchain_core.tools import StructuredTool

lc_tool = StructuredTool.from_function(search_docs_core, name="docs_search")

# OpenAI Agents SDK
from agents import function_tool

oa_tool = function_tool(search_docs_core, name_override="docs_search")

# Claude Agent SDK: in-process MCP server
from claude_agent_sdk import create_sdk_mcp_server, tool


@tool("docs_search", "Search this site's documentation.", {"query": str, "k": int})
async def claude_docs_search(args: dict) -> dict:
    hits = search_docs_core(args["query"], args.get("k", 5))
    return {"content": [{"type": "text", "text": str(hits)}]}


docs_server = create_sdk_mcp_server(name="docs", tools=[claude_docs_search])

The function is the asset; each wrapper is a few lines. StructuredTool.from_function and the OpenAI Agents SDK’s function_tool infer the schema from the signature and docstring; the Claude Agent SDK’s @tool takes an explicit input schema and exposes the tool through an in-process MCP server (create_sdk_mcp_server), which is then passed to ClaudeAgentOptions(mcp_servers=…​). See LangChain — Tools, OpenAI Agents SDK and Claude Agent SDK — Overview.
