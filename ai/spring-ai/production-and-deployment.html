Production & Deployment

This content was generated with the assistance of AI and should be verified against the official documentation of each tool and framework before being relied on in production.

This section’s bibliography lists the reference material consulted while preparing these pages.

Written against Spring AI 2.0.1, Spring Boot 4.1.x and Java 21 (verified 2026-09-29). A model call is a slow, rate-limited, metered and sometimes failing remote request whose output changes with every run. In development that is a curiosity; under load it decides whether the service stays up and what it costs. This page takes DocsAssistant from a working sample to a service you can operate: what to retry and for how long, how to keep one busy client from starving the others, when a cached answer is safe, how the timeouts nest, how to package and run it on Kubernetes without baking in a secret, and how to estimate and govern the spend. The classes were compiled against 2.0.1 and the behaviours described as tested were run with scripted models, so they prove the mechanics of Spring AI and Spring, not the behaviour of any model provider under real load.

Retries

Two different retry mechanisms exist in 2.0.1 and the provider decides which one applies.

  • Providers built on Spring’s RestClient, such as Ollama, use the RetryTemplate that spring.ai.retry.* configures. It retries TransientAiException and ResourceAccessException (connection problems) and gives up immediately on anything else.

  • Providers built on an official vendor SDK, OpenAI and Anthropic among them since 2.0, use the SDK’s own retries, set per provider: spring.ai.openai.max-retries (default 3) and spring.ai.openai.timeout (default 60 seconds), and spring.ai.anthropic.max-retries and spring.ai.anthropic.timeout. The spring.ai.retry.* properties do not govern those calls.

Check which applies to your provider before tuning: setting spring.ai.retry.max-attempts while running on the OpenAI starter changes nothing.

What spring.ai.retry does

An HTTP error becomes a TransientAiException (retried) or a NonTransientAiException (not retried) according to these rules, applied in this order:

  1. A status listed in spring.ai.retry.on-http-codes is always transient.

  2. A 4xx status is non-transient unless spring.ai.retry.on-client-errors is true. So a 400 or a 401 fails at once, and a 429 fails at once too, unless you list it.

  3. A status in spring.ai.retry.exclude-on-http-codes is non-transient.

  4. Everything else, meaning 5xx, is transient.

A ceiling on total retry time

The properties cannot express a total deadline. Spring Framework 7’s RetryPolicy can (timeout(Duration)), and Spring AI’s template is @ConditionalOnMissingBean, so defining your own replaces it:

RetryConfig.java: retry at most three times, but never for more than 45 seconds
package com.example.docsassistant;

import java.time.Duration;

import org.springframework.ai.retry.TransientAiException;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.retry.RetryPolicy;
import org.springframework.core.retry.RetryTemplate;
import org.springframework.web.client.ResourceAccessException;

/**
 * Replaces the auto-configured template (which is @ConditionalOnMissingBean) to add what the properties cannot
 * express: a ceiling on the total time spent retrying one request.
 */
@Configuration(proxyBeanMethods = false)
class RetryConfig {

    @Bean
    RetryTemplate retryTemplate() {
        RetryPolicy policy = RetryPolicy.builder()
                .maxRetries(3)
                .includes(TransientAiException.class, ResourceAccessException.class)
                .delay(Duration.ofSeconds(1))
                .multiplier(2)
                .maxDelay(Duration.ofSeconds(8))
                .timeout(Duration.ofSeconds(45))   // give up after 45 s in total, whatever is left of maxRetries
                .build();
        return new RetryTemplate(policy);
    }
}

Source: Spring Framework: Resilience features.

A test with a 450 ms timeout, a 100 ms delay and up to 50 retries made 5 calls and then aborted with a message saying the pending sleep would exceed the timeout. The timeout limits the retry loop, not a single call that hangs, which is what the HTTP timeouts below are for. This bean applies to RestClient-based providers only.

Retrying the same request is safe for a chat call and not for a tool that changes something. A model call that fails midway may already have consumed tokens, and a tool such as openIssue that the model calls twice will create two issues unless it is idempotent. Give write tools a request key that makes a repeat harmless, or the approval queue described on Security & Guardrails will show the duplicate.

Retries can also be added around your own methods with Spring Framework 7’s @Retryable and @EnableResilientMethods, which is how the self-correcting evaluation loop on Evaluation works. That is a retry of a whole service call after a bad answer, a different thing from re-sending a request after a transport failure.

Rate limiting and concurrency

Providers limit requests and tokens per minute, and they answer 429 when you exceed the limit. A service should apply its own limit first, for three reasons: to stay under the provider’s quota, to stop one client using all of it, and to protect a local model server that answers only a few requests at a time. Spring AI has no rate limiter; use one from the Spring ecosystem. The example uses Resilience4j’s RateLimiter for a per-instance limit and Spring Framework 7’s @ConcurrencyLimit for the number of calls in flight.

ProductionConfig.java: a limiter bean and the switches for caching and resilience annotations
package com.example.docsassistant;

import java.time.Duration;

import io.github.resilience4j.ratelimiter.RateLimiter;
import io.github.resilience4j.ratelimiter.RateLimiterConfig;
import org.springframework.cache.annotation.EnableCaching;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.resilience.annotation.EnableResilientMethods;

@Configuration(proxyBeanMethods = false)
@EnableCaching
@EnableResilientMethods
class ProductionConfig {

    /** At most 5 model calls per second for this instance; a caller waits up to 2 s for a permit. */
    @Bean
    RateLimiter modelRateLimiter() {
        return RateLimiter.of("model", RateLimiterConfig.custom()
                .limitForPeriod(5)
                .limitRefreshPeriod(Duration.ofSeconds(1))
                .timeoutDuration(Duration.ofSeconds(2))
                .build());
    }
}

CachedDocsAnswers.java: the anonymous answer path with a limit, a concurrency cap and a cache
package com.example.docsassistant;

import io.github.resilience4j.ratelimiter.RateLimiter;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.prompt.ChatOptions;
import org.springframework.cache.annotation.Cacheable;
import org.springframework.resilience.annotation.ConcurrencyLimit;
import org.springframework.stereotype.Service;

/**
 * Anonymous, stateless documentation answers: no memory, no per-user tools, temperature 0, so an identical
 * question is a safe cache hit. Per-user conversations never go through this class.
 */
@Service
public class CachedDocsAnswers {

    private final ChatClient chatClient;
    private final RateLimiter rateLimiter;

    public CachedDocsAnswers(ChatClient.Builder builder, DocsTools docsTools, RateLimiter modelRateLimiter) {
        this.chatClient = builder
                .defaultSystem("Answer only from the documentation tool results. Be brief.")
                .defaultOptions(ChatOptions.builder().temperature(0.0).maxTokens(400))
                .defaultTools(docsTools)
                .build();
        this.rateLimiter = modelRateLimiter;
    }

    @Cacheable(cacheNames = "docs-answers", key = "#question.strip().toLowerCase()")
    @ConcurrencyLimit(8)   // at most 8 model calls in flight in this instance
    public String answer(String question) {
        // throws RequestNotPermitted when no permit arrives within the timeout
        return RateLimiter.decorateSupplier(this.rateLimiter, () -> this.chatClient.prompt()
                .user(question)
                .call()
                .content()).get();
    }
}

Source: Spring Boot: Caching and Spring Framework: Resilience features for @ConcurrencyLimit.

When the limiter cannot grant a permit within its timeout it throws RequestNotPermitted. Turn that into an honest HTTP answer with a Retry-After header, not a 500:

RateLimitAdvice.java: 429 instead of 500
package com.example.docsassistant;

import io.github.resilience4j.ratelimiter.RequestNotPermitted;
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@RestControllerAdvice
class RateLimitAdvice {

    @ExceptionHandler(RequestNotPermitted.class)
    ResponseEntity<ProblemDetail> tooManyRequests(RequestNotPermitted ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.TOO_MANY_REQUESTS,
                "The assistant is busy; retry shortly.");
        return ResponseEntity.status(HttpStatus.TOO_MANY_REQUESTS)
                .header("Retry-After", "2")
                .body(problem);
    }
}

Source: Resilience4j: RateLimiter.

Per-instance limits multiply with the number of replicas: five per second on each of three pods is fifteen per second against the provider. If the provider’s quota is global, divide it by the replica count or enforce the limit in a shared gateway, such as the ones on LLM Gateways. Limit by user or tenant too, not only per instance, when one client must not consume the budget of the rest.

The limiter grants a fixed number of permits per refresh period (limitForPeriod per limitRefreshPeriod), and a caller that cannot get one within timeoutDuration is refused. A short timeout is deliberate: a queue with no bound only turns overload into slow failures.

Caching

A cache is safe where the same input must give an acceptable answer for anyone who asks. For DocsAssistant that is the anonymous question "what does keep-alive do?", and it is not "summarise my open issues". The rules for @Cacheable on a model call:

  • Deterministic setup. Use a temperature of 0 and no per-user context. A cached answer is one sampled reply, and with a higher temperature it would freeze one arbitrary reply for everyone.

  • No memory, no per-user tools. Anything derived from the caller’s identity or history makes the same question produce different right answers. The CachedDocsAnswers class above has neither and is a separate path from the chat endpoint; conversations never go through it.

  • A normalised key. The key strips and lower-cases the question. Without it, What is keep-alive? and `what is KEEP-ALIVE ` would be two cache entries; matching questions that differ by more than case and spacing is semantic caching, below.

  • An expiry and an eviction. Cache for as long as the documentation stays the same, and clear the cache when the corpus is re-ingested, or answers describe pages that no longer say that.

  • Tools with side effects never run from a cache hit, because the cache skips the call entirely. Only cache paths whose tools read.

A test with a counting model showed the mechanics: two spellings of one question made one model call, and a limiter with two permits refused the third distinct question with RequestNotPermitted while the model had been called twice. Spring’s cache abstraction, providers and pitfalls are on Spring Boot Caching.

A semantic cache treats near-identical questions as the same by comparing embeddings. It hits more often and it can return a wrong answer to a question that only looks similar, so it needs a similarity threshold you have measured. The design, the threshold trade-off and the invalidation problem are on Semantic caching. Separately, some providers cache the prompt prefix on their side and bill cached tokens at a lower rate; in 2.0 Usage exposes getCacheReadInputTokens() and getCacheWriteInputTokens() (populated by Anthropic, Bedrock Converse, OpenAI and Google GenAI, as far as each reports them), so you can see whether a long stable system prompt is being reused.

Virtual threads

A blocking model call spends nearly all its time waiting, which is what virtual threads are for. With Java 21 set spring.threads.virtual.enabled=true and Boot runs request handling and @Async work on virtual threads, so a few hundred slow model calls in flight do not need a few hundred platform threads. It removes the thread pool as the limit; it does not remove the provider’s limit, so the rate limiter and concurrency cap above are still needed. Two details from the streaming work apply:

  • Reactor’s boundedElastic scheduler runs on platform threads unless you start the JVM with -Dreactor.schedulers.defaultBoundedElasticOnVirtualThreads=true, which in a test produced loomBoundedElastic virtual threads.

  • Tools run on Reactor threads while streaming, and the SecurityContext does not follow them unless spring.reactor.context-propagation=auto is set; without it a @PreAuthorize check failed with "An Authentication object was not found". The prod profile above sets it.

Spring Boot’s general treatment of threading is on Concurrency Alternatives.

The YAML parses and follows the Kubernetes API shapes; it was not applied to a cluster. The image name is a placeholder. Points that matter for AI workloads:

  • Readiness must not depend on the model. If readiness calls the provider, a provider outage takes every pod out of service at once and turns a partial failure into a full one. Keep the model out of the probes, serve a clear error when it fails, and alert on the error rate instead.

  • Graceful shutdown. server.shutdown=graceful and spring.lifecycle.timeout-per-shutdown-phase=45s let in-flight answers finish. The grace period (60 s) is longer than that, and an answer that takes longer is cut off, so keep the two aligned with your model timeouts.

  • Scale on load, not only CPU. The service spends its time waiting for the model, so CPU stays low while requests queue. Scale on concurrent requests or request rate from the metrics on Observability, within the provider’s quota.

  • A self-hosted model is a separate workload, with GPUs, warm-up and its own scaling; see Running local LLMs in production. The application reaches it by service name, as OLLAMA_BASE_URL does above.

  • Egress. If pods may reach only the model provider and the MCP servers they use, a prompt-injected instruction to send data elsewhere fails at the network.

Secrets

The rule is that no secret is written in a file that is committed, baked into an image, printed in a log or sent to the model. In practice:

  • Provider keys and tokens (OPENAI_API_KEY, GITHUB_TOKEN for the MCP client) reach the process as environment variables, injected from a secret store by the platform: Kubernetes Secrets synced from a vault, or a CSI driver. On Azure that is Key Vault. Properties refer to them as ${OPENAI_API_KEY}.

  • Use a separate key per environment and per service, with the smallest scope the provider offers and a spending limit, so a leaked key has a ceiling.

  • Rotate keys on a schedule and on suspicion; a rotation should need a restart at most, not a rebuild.

  • Keep keys out of prompts and out of tool results. A system prompt that contains a credential can be read back by the model.

  • Turn prompt and completion logging off (the prod profile does), since prompts hold user text and tool results hold whatever the tools returned.

  • Never pass the caller’s token through to a tool server, see MCP Client.
