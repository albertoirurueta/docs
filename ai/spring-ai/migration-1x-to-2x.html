Migrating from 1.x to 2.x

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Written against Spring AI 2.0.1, Spring Boot 4.1.x and Java 21 (verified 2026-09-29), from the official Upgrade Notes as they stood on that date, checked against the 2.0.1 jars and, where marked, by running code. Spring AI version 2.0.0 became generally available on 2026-06-12 and 2.0.1 is the current stable release. The 2.0 line requires Java 17 or later, Spring Boot 4.0 or 4.1 with Spring Framework 7, Jackson 3 and JSpecify nullability, so a Spring AI upgrade is also a Spring Boot upgrade, and the Boot 4 migration is the larger part of the work for most projects. This page is the reference to keep beside the compiler while you upgrade: the rows are the changes DocsAssistant-style code runs into, each with a link to the note it comes from. The rest of the sub-section describes 2.0.1 as if it were the only version; this page is the one place that looks back. A 2.1 milestone exists on Maven Central, but nothing here is based on it. The most common renames also fit in one box of the printable Spring AI Cheat Sheet, and the version baseline on the landing page lists every version this sub-section targets.

How to upgrade

flowchart TD A["1.x application on Boot 3.x"] --> B["Get the tests green on 1.x first"] B --> C["Move to Spring Boot 4.x and Java 17+ (Framework 7, Jackson 3)"] C --> D["Set spring-ai-bom to 2.0.x"] D --> E["Run OpenRewrite recipes for the mechanical part"] E --> F["Fix what the compiler reports: tables below"] F --> G["Update properties: drop .options, renamed keys"] G --> H["Review the silent changes: same code, different behaviour"] H --> I["Run the evaluation suite and compare answers, cost, latency"]

  1. Green tests first. An upgrade of this size needs a baseline. Tests with a scripted ChatModel (see Testing) are ideal, since they do not change when the provider does.

  2. Boot 4 and Java. Move the platform first or together with the BOM; Spring AI 2.0.x supports Spring Boot 4.0.x and 4.1.x. Jackson 3 changes the ObjectMapper package to tools.jackson.databind and the builder to JsonMapper.

  3. BOM. Import spring-ai-bom 2.0.1 (or the latest 2.0.x). All org.springframework.ai artifacts take their version from it.

  4. Recipes. Run the OpenRewrite recipes in the next section, then read the diff.

  5. Compile. Work through the tables below.

  6. Properties. Start the application with a configuration check; unknown keys under spring.ai are silently ignored by Boot, so compare your files with the tables, or run the recipe that renames them.

  7. Behaviour. Read the "compiles but behaves differently" table. These are the changes no compiler will report.

OpenRewrite recipes

Three sets of recipes exist. Two are from Spring AI and cover the MCP changes of 2.0.0-M3; one is a community recipe that covers most of the mechanical 2.0 changes.

The recipe names were read from the community documentation and from the YAML file in the Spring AI repository on 2026-09-29; the recipes themselves were not run for this page. The Spring AI ones are invoked like this, with the plugin version the notes use:

mvn org.openrewrite.maven:rewrite-maven-plugin:6.32.0:run \
  -Drewrite.configLocation=https://raw.githubusercontent.com/spring-projects/spring-ai/refs/heads/main/src/rewrite/migrate-to-2-0-0-M3.yaml \
  -Drewrite.activeRecipes=org.springframework.ai.migration.M3MigrateMcpAnnotations \
  -Dmaven.compiler.failOnError=false

Source: Spring AI: Upgrade Notes (the M3 recipes and the plugin version).

The community recipe is run like this:

./mvnw -U org.openrewrite.maven:rewrite-maven-plugin:run \
  -Drewrite.recipeArtifactCoordinates=io.arconia.migrations:rewrite-spring:LATEST \
  -Drewrite.activeRecipes=io.arconia.rewrite.spring.ai2.UpgradeSpringAi_2_0

Source: Arconia Migrations: Spring AI 2.0.

Two cautions. A recipe changes source files, so run it on a clean branch and read every hunk; LATEST in the second command floats, so pin a version for a repeatable run. And the M3 note warns that a pom.xml that declares mcp-spring-webflux without a version, relying on a BOM, may fail to parse before the recipe can run, which is why that note tells you to patch those files first. The same community project has io.arconia.rewrite.spring.ai1.UpgradeSpringAi_1_0 for the older 0.8 to 1.0 jump (Arconia: Spring AI 1.0); the Spring AI notes link to it for the 1.0.0-RC1 upgrade.

Migrating code from the books

Two books in this guide’s bibliography were written against versions before 2.0. Their concepts are sound; their code needs the changes below. The snippets are shapes of the API those versions used, written for this page (not taken from the books), and are not compiled.

Spring AI in Action (Spring AI 1.0.3, Spring Boot 3.5)

Spring AI in Action is close to 2.0 in style: fluent ChatClient, advisors, tools with @Tool, MCP. Most of the migration is the tables above. Its examples typically look like this:

Spring AI 1.0.x style: does not compile on 2.0.1
ChatClient client = ChatClient.builder(chatModel)
    .defaultAdvisors(PromptChatMemoryAdvisor.builder(memory).conversationId("session-1").build())
    .defaultOptions(OpenAiChatOptions.builder().temperature(0.2).build())
    .defaultToolNames("currentWeather")
    .build();

Source: Spring AI: Upgrade Notes.

and the 2.0.1 form is:

MigratedDocsAssistant.java: the 2.0.1 forms of the changes above
package com.example.docsassistant;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.client.advisor.MessageChatMemoryAdvisor;
import org.springframework.ai.chat.client.advisor.ToolCallingAdvisor;
import org.springframework.ai.chat.memory.ChatMemory;
import org.springframework.ai.chat.model.ChatModel;
import org.springframework.ai.chat.prompt.ChatOptions;
import org.springframework.ai.model.tool.ToolExecutionEligibilityChecker;
import org.springframework.ai.openai.OpenAiChatOptions;
import org.springframework.ai.tool.ToolCallback;
import org.springframework.ai.tool.function.FunctionToolCallback;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

/** The 2.0.1 form of the code the older books and 1.x tutorials show. */
@Configuration(proxyBeanMethods = false)
class MigratedDocsAssistant {

    record WeatherRequest(String city) { }

    record WeatherResponse(String summary) { }

    /** Was: a raw java.util.function.Function bean found by name. Now: an explicit ToolCallback. */
    @Bean
    ToolCallback currentWeather() {
        return FunctionToolCallback.builder("currentWeather",
                        (WeatherRequest request) -> new WeatherResponse("sunny in " + request.city()))
                .description("Get the weather in a city")
                .inputType(WeatherRequest.class)
                .build();
    }

    /** Was: an advisor created with .conversationId("...") or PromptChatMemoryAdvisor. */
    @Bean
    ChatClient memoryClient(ChatModel chatModel, ChatMemory chatMemory, ToolCallback currentWeather) {
        return ChatClient.builder(chatModel)
                .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory).build())
                .defaultTools(currentWeather)   // defaultToolCallbacks(...) is deprecated for removal in 2.0
                .build();
    }

    String ask(ChatClient client, String conversationId, String question) {
        return client.prompt()
                .user(question)
                // options() takes the builder, not a built object; the fields you set override the model's start-up options,
                // and a request's options replace (not merge with) any defaultOptions(...) on the client
                .options(OpenAiChatOptions.builder().temperature(0.2))
                // the conversation id is required and supplied per call; derive it from the authenticated user, never from client input alone
                .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))
                .call()
                .content();
    }

    /** Was: options.copy() / fromOptions(). Options are immutable; mutate() starts a builder from one. */
    ChatOptions lowerTemperature(ChatOptions options) {
        return options.mutate().temperature(0.0).build();
    }

    /** Was: internalToolExecutionEnabled(false). Now: decide in the advisor when the loop continues. */
    @Bean
    ToolExecutionEligibilityChecker stopOnFinishReasonStop() {
        return response -> response != null && response.hasToolCalls()
                && !"stop".equals(response.getResult().getMetadata().getFinishReason());
    }

    ToolCallingAdvisor insideTheLoopHistory() {
        return ToolCallingAdvisor.builder().disableInternalConversationHistory().build();
    }
}

Source: Spring AI: Upgrade Notes.

The class compiled against 2.0.1. It is not a program to run; each method shows one change:

  • the Function bean found by name becomes an explicit ToolCallback and is attached to the client;

  • the memory advisor is MessageChatMemoryAdvisor, with the conversation ID passed on each call;

  • options(…​) takes the builder;

  • mutate() replaces copy();

  • a ToolExecutionEligibilityChecker and ToolCallingAdvisor.builder() replace internalToolExecutionEnabled.

Mastering Spring AI (Spring AI 0.8.x)

Mastering Spring AI predates the fluent ChatClient, advisors, chat memory and MCP; it is a good source for concepts, prompt types and governance, and almost none of its code compiles today. Migrating from it is a rewrite in the direction of the 1.0 API followed by the 2.0 tables. Verify the upgrade

Compiling is not enough. After the mechanical changes:

  • Run the scripted-model tests: they catch wiring, advisor order and tool-loop changes without a provider.

  • Run the evaluation set against the same model before and after, and compare answers, latency, token use and cost; see Evaluation. Answers change with the default temperature and with structured-output schema changes even when the model is the same.

  • Check the metrics and dashboards listed in Observability for the renamed tool span and the accumulated usage.

  • Read the startup log for deprecation warnings on .options property paths and fix them now; the deprecated forms exist to ease the transition.

  • Re-test the security paths from Security & Guardrails: per-request tool registration, @PreAuthorize on tools and the conversation ID derived from the token.
