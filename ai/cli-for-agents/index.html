Building CLIs for AI Agents

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The native and terminal side of command-line programs — terminals, POSIX and Windows consoles, TUI libraries and shipping binaries — is covered in the CLI reference.

A command-line tool that an AI agent can drive is the same kind of tool a careful engineer would want anyway: predictable streams, honest exit codes, structured output, no surprise prompts and safe defaults. This sub-section collects those practices, shows them on one running example, and then shows how to wrap the finished tool as an MCP server or an agent tool. The versions used are listed in Version baseline, all checked on 2026-09-30, and every page repeats the subset it needs in its own lead paragraph.

Why CLIs work well with agents

An agent that can run a shell command can already use a very large tool ecosystem, and a CLI has properties that suit that style of work:

  • Nothing to load up front. A command costs context only when it is run, and only its output is paid for. Claude Code’s own guidance treats command-line tools as a context-efficient way to reach external services (see Claude Code — Best practices). Tool schemas, by contrast, are usually loaded before the first call.

  • Models already know the common ones. git, gh, curl and jq appear throughout training data, so little description is needed; an unfamiliar tool costs one --help call, which is why Self-Describing Help matters.

  • Composition is built in. Pipes, redirection and exit codes let an agent chain steps without a bespoke integration, which only works when the tool respects Streams & Exit Codes.

  • Humans and CI use the same interface. One implementation serves a terminal, a script and an agent, and the same contract can later be exposed as an MCP tool (see CLI vs. MCP for the honest trade-offs, including where MCP is the better fit).

  • Guardrails already exist. Hosts gate shell access with permission rules and sandboxes, described for Claude Code on Permissions & Settings; a well-designed CLI adds dry-runs, confirmations and least-privilege credentials on top.

The price is that a CLI written only for people is hostile to agents: colour codes and spinners in captured output, prompts that hang, human-only error text, unbounded output and unparseable tables. The pages below remove each of those problems in turn. The tool-design ideas behind them are the ones in Tool Design and Designing Good MCP Servers, applied to a process instead of a protocol.

Three audiences, one tool

A command-line tool has three kinds of caller, and a good design serves all of them from one implementation.

Audience Needs Where it is covered

Readable text, colour and progress on a terminal, helpful errors, examples in --help, prompts before risky actions, completion and man pages.

The reading map

The pages can be read in any order, but this route works for most readers:

  1. Start with CLI Design Fundamentals and Streams & Exit Codes; they are the foundation of everything else.

  2. Read the agent-specific pages: Machine-Readable Output, Agent Ergonomics and Safety & Idempotency.

  3. Pick your language on the framework pages, from Python to Swift & .NET.

  4. Decide how the tool reaches the agent: CLI vs. MCP, wrapping as an MCP server or as an agent tool, and the Security rules that apply either way.

  5. Ship it with Packaging & Distribution, Testing CLIs and Documenting CLIs, and review it against the Agent-Readiness Checklist.

Readers who only need a reminder can use the Cheat Sheet, which has a printable one-page PDF.

The docsctl running example

Every page uses the same small, fictional tool, docsctl, a command-line client for the documentation of this site. It exists only on these pages, its behaviour is illustrative, and its contract is repeated identically wherever it is used so that snippets in different languages stay comparable.

Table 2. The docsctl commands
Command What it does Safety

docsctl search QUERY

Full-text search over the documentation; supports --component, --limit and --cursor.

Read-only, idempotent

docsctl show PAGE

Returns one page such as irurueta-algebra::index.adoc, optionally one section, with --max-chars.

Read-only, idempotent

docsctl list-components

Lists the documented components and their versions.

Read-only, idempotent

docsctl validate [PATH]

Checks a documentation tree for broken references and reports problems with a code, a line and a hint.

Read-only, idempotent

docsctl publish --component NAME

Publishes a component; --dry-run prints a JSON plan and a confirmation token is required to apply it.

Destructive, needs confirmation, idempotent with the same key

docsctl login, logout, schema, completion

Credentials, the machine-readable command tree, and shell completion.

Credentials only, or read-only

Every command accepts --json (or --format json|jsonl|text), --no-input, --yes, --timeout and --no-color, writes data to stdout and messages to stderr, and ends with one of a small set of documented exit codes. A search looks like this from a script or an agent:

Searching from a script: data on stdout, nothing else
docsctl search kalman --component irurueta-statistics --limit 3 --json --fields id,title,score

Output (illustrative):

{"nextCursor":null,"query":"kalman","results":[{"id":"irurueta-statistics::kalman.adoc","score":0.91,"title":"Kalman filter"}],"schemaVersion":1,"total":1,"truncated":false}

The primary implementations are in Python with Typer (Python CLI Frameworks) and in Java with picocli, compiled to a native binary with GraalVM Native Image (Java CLI Frameworks). Shorter equivalents cover Node.js (commander), Go and Rust (Cobra; clap, with a Ratatui interface and a Rig agent) and Swift and .NET (swift-argument-parser with SwiftTUI; System.CommandLine). The finished tool is then wrapped three ways: as an MCP server (Python FastMCP, the TypeScript SDK and Spring AI @McpTool) on Wrapping a CLI as an MCP Server, and as a LangChain @tool, a Spring AI @Tool and a LangChain4j @Tool on Wrapping a CLI as an Agent Tool, which also shows using the CLI directly from Claude Code and from Copilot agent mode.

What’s covered

The pages are grouped the same way as the navigation.

Fundamentals

  • CLI Design Fundamentals — the clig.dev principles, POSIX and GNU conventions, the 12 Factor CLI Apps checklist, subcommand design and naming, flags versus positional arguments and why ambiguous prefix matching is a trap.

  • Streams & Exit Codes — stdout for data and stderr for messages, piping, crash-only design and the exit-code taxonomy, including 126, 127 and 128+N.

  • TTY, Colour & Interactivity — isatty, NO_COLOR, prompting only on a TTY, --no-input and --yes, and progress output only on a terminal.

  • Configuration & Auth — flag, environment, project, user and system precedence, XDG directories, and the token file, keychain and environment-variable trade-off.

Designing for agents

  • Machine-Readable Output — --json, JSON Lines, field projection, deterministic ordering, schemaVersion and published JSON Schemas.

  • Agent Ergonomics — token budgets, pagination with small defaults, truncation markers, errors that carry remediation, timeouts and fast startup.

  • Safety & Idempotency — read-only defaults, --dry-run plans, the confirmation envelope, --force and idempotency keys.

  • Self-Describing Help — --help written for LLMs, a machine-readable command tree, completion, man pages and a bundled agent skill.

  • CLI vs. MCP — an even-handed comparison, the gh plus GitHub MCP server case study and when to ship both.

Frameworks by language

  • Python CLI Frameworks — argparse, Click, Typer, Rich and Textual.

  • Java CLI Frameworks — picocli, GraalVM Native Image, Spring Shell and JLine.

  • Node.js CLI Frameworks — commander, yargs, oclif and Ink.

  • Go & Rust CLI Frameworks — Cobra and Bubble Tea; clap, Ratatui and Rig.

  • Swift & .NET CLI Frameworks — swift-argument-parser and SwiftTUI; System.CommandLine and Spectre.Console.

  • TUIs vs. CLIs — when a full-screen interface helps and why agents still need a non-interactive mode.

Integration

  • Wrapping a CLI as an MCP Server — subcommands to tools, exit codes to isError, JSON stdout to structuredContent, in Python, TypeScript and Spring AI.

  • Wrapping a CLI as an Agent Tool — narrow LangChain, Spring AI and LangChain4j tools versus a generic shell tool, and direct use from Claude Code and Copilot.

  • Security — argument injection, argv discipline, allowlists, least privilege, sandboxing and output sanitisation.

Shipping

  • Packaging & Distribution — pipx, Homebrew, npm, JBang, native binaries, cargo install, winget, .NET tools, GoReleaser, containers, signing and checksums.

  • Testing CLIs — golden tests of JSON output, no-TTY and exit-code tests, bats-core, framework test runners and agent evals.

  • Documenting CLIs — man pages and reference docs generated from the command tree, kept in sync from one source.

  • Agent-Readiness Checklist — a one-page review list linking every concept page.

  • Cheat Sheet — a grouped index of quick back-links and the printable one-page PDF.
