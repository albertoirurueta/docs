Model Context Protocol (MCP)

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This sub-section was written against the 2026-07-28 revision of the Model Context Protocol specification and the SDK, framework and host versions listed in Version baseline, all read from PyPI, npm, Maven Central and the official documentation on 2026-09-29. Where an individual page and that baseline ever disagree after a later update, the baseline is the one to trust.

Why MCP exists: the N x M problem

Before a standard existed, connecting an AI application to a tool or a data source meant writing an integration for that one pair: a Claude Code plugin for the issue tracker, a different VS Code extension for the same tracker, a hand-rolled function for a home-grown agent. With N hosts (AI applications) and M tools that is up to N x M integrations, each with its own authentication, schema mapping and failure modes. The Model Context Protocol (MCP) replaces that grid with one protocol: a host embeds an MCP client once, a tool or data source exposes an MCP server once, and any client can talk to any server — N + M implementations instead of N x M.

Figure 1. The N x M integration problem, and N + M with MCP

An MCP server exposes three kinds of capability to the model: tools (functions the model can call), resources (data the application can read, addressed by URI) and prompts (reusable message templates the user can pick), and can ask the user for missing information through elicitation. Messages are JSON-RPC 2.0 and travel over stdio for local servers or Streamable HTTP for remote ones. The details are on MCP Architecture, Tools, Resources, Prompts & Elicitation and Transports; this page only orients you and lists the sources.

Governance

MCP was introduced by Anthropic and is now an open standard governed under the Linux Foundation, which formed the Agentic AI Foundation (AAIF) as a neutral home for open agent standards, starting with MCP; its sibling protocol, Agent2Agent (A2A), is a separate Linux Foundation project, and Agent-to-Agent Protocol (A2A) explains how the two fit together. The specification is versioned by date, changes are proposed and decided in the open as Specification Enhancement Proposals (SEPs, the numbers quoted in the release blog), and SDKs are ranked in tiers by how completely and promptly they follow it (see the SDK table under Other SDK languages). Sources are in the Bibliography: the Linux Foundation announcement and the versioning page.

Three revisions in thirteen months

Protocol revisions are named by date. The three most recent ones changed different layers of the protocol, and the last one changed the shape of it:

Revision What changed

2025-06-18

JSON-RPC batching removed; structured tool output (outputSchema) added; servers classified as OAuth resource servers, with Protected Resource Metadata (RFC 9728) to find the authorization server; clients required to use resource indicators (RFC 8707); elicitation and resource links in tool results added; the negotiated protocol version had to be sent in an MCP-Protocol-Version header over HTTP.

2025-11-25

OpenID Connect Discovery accepted for authorization-server discovery; icons for tools, resources and prompts; incremental scope consent through WWW-Authenticate; URL-mode elicitation; tool calling inside sampling; Client ID Metadata Documents (CIMD) recommended for client registration; experimental Tasks for durable, pollable requests; JSON Schema 2020-12 made the default dialect; SSE streams that servers may close and clients poll.

2026-07-28

A stateless core: the initialize handshake and the Mcp-Session-Id header are gone, every request carries its protocol version, client information and capabilities in _meta, and an optional server/discover call replaces the handshake for clients that want capabilities up front. Server-to-client requests are redesigned as Multi Round-Trip Requests (resultType input_required). Streamable HTTP requests must carry Mcp-Method and Mcp-Name headers so gateways can route without parsing bodies. List results carry ttlMs and cacheScope and a deterministic order. A single subscriptions/listen stream replaces the GET endpoint. A formal extensions framework takes Tasks out of the core (io.modelcontextprotocol/tasks). Authorization is hardened: RFC 9207 iss validation, credentials bound to their issuer, and CIMD replaces Dynamic Client Registration (DCR), which is deprecated. Roots, sampling, logging and the HTTP+SSE transport are deprecated under a formal policy with a twelve-month minimum window, and ping and logging/setLevel are removed.

Two consequences follow for anyone reading older material, including the books in the bibliography, which all predate the 2026-07-28 revision: the initialize handshake, sessions and Mcp-Session-Id, the old FastMCP class name in the official Python SDK (now MCPServer), and the v1 TypeScript package @modelcontextprotocol/sdk describe the previous protocol era. Each page flags that behaviour where it matters and shows the current API, and the architecture page covers the history in one place.

The Java protocol-version skew

The Java stack lags the specification, and this sub-section says so rather than hiding it. The MCP Java SDK 2.0.x defines protocol versions only up to 2025-11-25, and Spring AI 2.0.1 builds on it, so a Spring AI MCP server has no server/discover and no multi-round-trip elicitation: it answers a 2026-07-28 client’s initialize with 2025-11-25, and calling server/discover fails (a "method not found" error on the Streamable mode, an internal error on the stateless mode). The Spring AI reference still describes its Streamable-HTTP servers as introduced with spec version 2025-03-26 and does not mention 2026-07-28. Consequently the Java build of docs-assistant is tested with the Inspector in its legacy protocol era and has no elicitation step, and its component argument is required. The Java SDK is a Tier 2 SDK on the official SDK list, not one of the SDKs updated in the release blog. The details and the practical consequences are on Spring Boot MCP Servers.

What’s covered

The sub-section builds one running example, the docs-assistant MCP server — the MCP-facing side of the DocsAssistant scenario used in LLM Foundations & Prompting, AI Agents and Vector Databases & RAG. It exposes this site’s documentation through the same four things on every stack:

  • a tool search_docs(query, component?, top_k) that returns structuredContent (hits with title, URL, snippet and score) together with an outputSchema;

  • a resource template docs://{component}/{page} that returns a page’s AsciiDoc;

  • a prompt answer_with_citations;

  • an elicitation through a Multi Round-Trip Request that asks which component to search when the query is ambiguous.

It is built three times — Python, Java and TypeScript — and each build passes the same Inspector CLI contract script, shown once on Testing & Debugging. The pages are grouped the same way as the navigation:
