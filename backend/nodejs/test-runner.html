The test runner is the part of Node.js that finds test files, runs them, and reports the results, with no dependency to install: you write functions with node:test, check values with node:assert, and start everything with node --test. node:test has been Stability 2 (Stable) since v20.0.0 (it was added in v18.0.0 and v16.17.0), and node:assert is Stable too. Several of the features around the edges are not: watch mode and code coverage are Stability 1 (Experimental), while test tags, global setup and teardown, randomized order and module mocks are Stability 1.0 (Early development) and are labelled where they appear. Mocks, snapshots and coverage have their own page, Mocking, Snapshots & Coverage; this page is the foundation it builds on. How node --test works

Running node --test does not simply load your files. The process you start is the runner: it finds the test files, decides which of them this process should run, starts each file in its own child Node.js process (the default, called process isolation), listens to what the children report, and feeds one stream of events to the reporters. A file does not have to use node:test at all; the runner treats it as a script and counts exit code 0 as a pass. Inside a file that does use node:test, every test runs on the same single application thread, whatever the concurrency option says, because concurrency there means interleaving asynchronous work on the event loop, not parallel threads (see Event Loop for why).

Because every file is a separate process by default, a crash, a global variable, or an open handle in one file cannot affect another, and the files can run in parallel on several cores. The cost is the start-up time of one Node.js process per file. The Node.js 26 documentation also says that child processes inherit Node.js options from the parent, including options from environment variables such as NODE_OPTIONS and from configuration files, except for the options the runner manages itself (--test, the coverage and reporter flags, --watch, the randomization flags and the tag filter). That is how a --import setup file reaches every test file.

Your first tests: test, describe and it

A test is one function. It passes when it returns normally (or its returned promise fulfills) and fails when it throws (or the promise rejects). A third style gives the function a callback as the second argument: calling it with a truthy first argument fails the test, and a test that takes a callback and also returns a promise fails. describe() groups tests into a suite and it() is the test function with the name you would expect there; describe is an alias of suite and it is an alias of test. The three styles are equivalent, so choose by taste and stay consistent in a codebase. The first example tests the ISBN check that the Bookshelf uses to reject malformed books.

The function under test: an ISBN-13 validator
// Validates an ISBN-13: 13 digits (hyphens/spaces allowed) whose weighted sum is divisible by 10.
export function isValidIsbn13(input) {
  if (typeof input !== 'string') throw new TypeError('ISBN must be a string');
  const digits = input.replace(/[-\s]/g, '');
  if (!/^\d{13}$/.test(digits)) return false;
  const sum = [...digits].reduce((acc, d, i) => acc + Number(d) * (i % 2 === 0 ? 1 : 3), 0);
  return sum % 10 === 0;
}

Hooks: before, after, beforeEach and afterEach

Hooks are functions the runner calls around your tests. before() runs once before the first test of its suite and after() runs once after the last one; the Node.js documentation guarantees that after() runs even when tests in the suite fail, which makes it the right place to close servers and delete temporary files. beforeEach() and afterEach() run around every test of the suite, including the tests of nested suites. Hooks take the same options as tests (timeout, signal) and may be written with a callback. Declared at the top level of a file, outside any describe(), they apply to every test in that file.

test/hooks.test.js: the order in which hooks and tests run
import { describe, it, before, after, beforeEach, afterEach } from 'node:test';
import assert from 'node:assert/strict';

describe('hook order', () => {
  const log = [];

  before(() => log.push('before'));
  after(() => {
    log.push('after');
    assert.deepStrictEqual(log, [
      'before',
      'beforeEach', 'test A', 'afterEach',
      'beforeEach', 'test B', 'afterEach',
      'after',
    ]);
  });
  beforeEach(() => log.push('beforeEach'));
  afterEach(() => log.push('afterEach'));

  it('A', () => log.push('test A'));
  it('B', () => log.push('test B'));
});

Subtests

The context object t that the runner passes to every test function has a t.test() method that creates a subtest. This builds hierarchies inside a test, shares setup between the subtests (the parent’s code runs once), and lets you generate cases in a loop. The context also has its own hooks, t.before(), t.beforeEach(), t.after() and t.afterEach(), which apply to the subtests of that one test.

test/nesting.test.js: a parent test, its hooks and two subtests
import { test } from 'node:test';
import assert from 'node:assert/strict';

test('parent', async (t) => {
  const seen = [];
  t.before(() => seen.push('parent before'));
  t.beforeEach((sub) => seen.push(`beforeEach for ${sub.name}`));
  t.after(() => assert.deepStrictEqual(seen, [
    'parent before',
    'beforeEach for first',
    'beforeEach for second',
  ]));

  await t.test('first', () => {});
  await t.test('second', () => {});
});

Source: Node.js API: Subtests

The documentation says to await every subtest, because a parent does not wait for its subtests (unlike tests declared inside a suite) and cancels the ones still pending when it finishes; a failing subtest also fails its parent. That is what happens on Node.js 22: in my run of a test that called t.test() without await, Node.js 22.23.3 reported the subtest as cancelled with the message test did not finish before its parent and was cancelled. On Node.js 24.21 and 26.10 the same file passed, because newer lines wait for outstanding subtests (the Learn guide dates this change to v23.8.0). Do not depend on that: write await t.test(…​) and the code works on every line.

Counting assertions: t.plan() and t.assert

t.plan(count) declares how many assertions and subtests the test must run; the test fails if the number differs. It exists for code where an assertion sits in a callback or event handler that might never fire, which would otherwise leave the test green. Plans count only assertions made through t.assert, the object that exposes the functions of node:assert bound to the current test; the plain imported assert is invisible to the plan. The wait option controls whether the check happens at once (the default, false), waits as long as needed (true), or waits up to a number of milliseconds.

A plan that counts t.assert calls
import test from 'node:test';
import { Readable } from 'node:stream';

test('every chunk is checked', (t, done) => {
  const chunks = ['a', 'b', 'c'];
  const expected = [...chunks];
  t.plan(chunks.length); // the test fails unless exactly three t.assert calls happen

  Readable.from(chunks)
    .on('data', (chunk) => t.assert.strictEqual(chunk, expected.shift()))
    .on('end', done);
});

test('a plan can wait for late assertions', (t) => {
  t.plan(1, { wait: 1_000 }); // wait up to one second for the assertion
  setTimeout(() => t.assert.ok(true), 50);
});

Asynchronous tests, timeouts and polling

An async function, a function that returns a promise, and a function that takes a callback are all valid. Each test can also be bounded: the timeout option fails the test after a number of milliseconds (the default is Infinity), --test-timeout sets a default for all tests, and t.signal is an AbortSignal that aborts when the test is cancelled or times out, so pass it to anything cancellable. The documentation is explicit that a timeout is not a reliable cancellation mechanism: a test that blocks the thread in a synchronous loop prevents the scheduled cancellation from running. For eventual conditions, t.waitFor() polls an assertion function until it stops throwing (default interval 50 ms, default timeout 1000 ms) and returns its value; prefer it to a hand-written sleep() followed by an assertion.

import assert from 'node:assert/strict';
import { setTimeout as sleep } from 'node:timers/promises';

test('hangs past its timeout', { timeout: 100 }, async (t) => {
  // t.signal aborts when the test times out, so the timer is cancelled too
  await sleep(5_000, undefined, { signal: t.signal });
});

test('polls until an eventual condition holds', async (t) => {
  let ready = false;
  setTimeout(() => { ready = true; }, 120);
  await t.waitFor(() => assert.equal(ready, true), { interval: 20, timeout: 1_000 });
});

Assertions with node:assert/strict

The test runner has no expect(). Assertions come from node:assert, and the module should be imported in its strict form, node:assert/strict: in strict assertion mode the loosely named methods behave like their strict counterparts (assert.equal() is assert.strictEqual(), assert.deepEqual() is assert.deepStrictEqual()), failure messages for objects include a colored diff, and the coercion surprises of legacy mode disappear. The legacy mode (import assert from 'node:assert') compares with == in equal(), deepEqual(), notEqual() and notDeepEqual(), and the Node.js documentation marks those four Stability 3 (Legacy) and points to the strict names.

Table 3. The assertions you will use every day
Assertion What it checks

assert.strictEqual(actual, expected)

Primitives or identity, compared with Object.is().

assert.deepStrictEqual(actual, expected)

Recursive equality of enumerable own properties, including the prototypes' identity, Map and Set contents, Error names, messages and causes. Property order does not matter; array order does.

assert.partialDeepStrictEqual(actual, expected)

Only the properties present in expected are compared (a superset of `deepStrictEqual’s rules). Handy for API responses with generated ids and timestamps.

assert.ok(value), assert.match(string, regexp), assert.doesNotMatch(string, regexp)

Truthiness; a regular expression must match; a regular expression must not match.

assert.throws(fn, expected), assert.doesNotThrow(fn)

expected may be an error class, a RegExp, an object of properties to compare, or a validation function.

assert.rejects(promiseOrFn, expected), assert.doesNotReject(promiseOrFn)

The asynchronous twins: always await them, otherwise a failure becomes an unhandled rejection after the test is over.

  assert.notDeepStrictEqual([1, 2], [2, 1]);             // order matters in arrays

Skipping, todo, only, expected failures and name patterns

While a feature is unfinished, or a test is known to be broken, you need to keep the suite green without deleting the test. The runner has four markers, all available as options on test() and describe() and as shorthand methods (it.skip(), it.todo(), it.only(), it.expectFailure()), and as methods on the context (t.skip(), t.todo()).

Table 4. The markers and what each one does to the run
Marker Behaviour Effect on the exit code

skip (option, it.skip(), t.skip())

The test is not run. A string is shown as the reason. t.skip() does not stop the function, so return after calling it.

None.

todo (option, it.todo(), t.todo())

The test runs, but a failure is not counted as a failure. If a test is both TODO and skipped, the TODO is ignored.

None: a failing TODO test leaves the exit code at 0, though its error text is still printed.

expectFailure (option, it.expectFailure())

The test must throw to pass and fails if it does not. A RegExp, function, object or error restricts which failure is accepted, and { label, match } supplies both a reason and a matcher. Added in v25.5.0 and v24.14.0.

A test that unexpectedly succeeds fails the run. skip beats it, and todo beats it too.

only (option, it.only(), describe.only())

With --test-only (or with isolation off), only tests marked only run. Everything below a marked suite runs unless a descendant is marked too.

Name patterns

--test-name-pattern runs only tests whose name matches a JavaScript regular expression, and --test-skip-pattern skips matching tests. Both can be repeated, "/…​/flags" syntax gives you flags such as i, and when both are given a test has to satisfy both. A pattern is tested against the test’s own name; to select one test among several with the same name, prefix it with its ancestors' names, separated by spaces. Tags (Early development)

Rerunning only what failed

A custom reporter

A custom reporter is a module whose default export is something stream.compose() accepts: a Transform in object mode or, simplest, an async generator function that receives the event stream and yields text. Pass its path to --test-reporter, the way you would pass a specifier to import() (a relative path needs ./).

reporters/one-line.js
// A custom reporter: an async generator that turns TestsStream events into lines.
export default async function* oneLine(source) {
  for await (const event of source) {
    const { type, data } = event;
    if (type === 'test:pass' && data.details.type !== 'suite') {
      yield `${data.skip === undefined ? 'PASS' : 'SKIP'} ${data.name}\n`;
    } else if (type === 'test:fail') {
      const error = data.details.error.cause ?? data.details.error;
      yield `FAIL ${data.name}: ${error.message.split('\n')[0]}\n`;
    } else if (type === 'test:summary' && data.file === undefined) {
      const { passed, failed, skipped } = data.counts;
      yield `${passed} passed, ${failed} failed, ${skipped} skipped\n`;
    }
  }
}

Testing an HTTP server

An HTTP service is tested by starting the real server on a random port, calling it with the global fetch(), and shutting it down. The pieces: listen on port 0 so the operating system picks a free port (no clash between the test files that run in parallel, and no dependency on port 3000 being free), read the actual port from server.address(), create and close the server in before() and after(), and do not leave keep-alive sockets behind, or the process will not exit. The Bookshelf server is the one used elsewhere in this section; createApp() returns a node:http server and an in-memory SQLite database, so each test file has its own clean data.

test/server.test.js
import { describe, it, before, after } from 'node:test';
import assert from 'node:assert/strict';
import { once } from 'node:events';
import { createApp } from '../src/server.js';

describe('books API', () => {
  let server;
  let base;

  before(async () => {
    ({ server } = createApp()); // in-memory SQLite database
    server.listen(0, '127.0.0.1'); // port 0: the OS picks a free port
    await once(server, 'listening');
    base = `http://127.0.0.1:${server.address().port}`;
  });

  after(async () => {
    server.close();
    server.closeAllConnections(); // do not wait for keep-alive sockets
    await once(server, 'close');
  });

  it('starts with an empty list', async () => {
    const res = await fetch(`${base}/books`);
    assert.equal(res.status, 200);
    assert.match(res.headers.get('content-type'), /^application\/json/);
    assert.deepStrictEqual(await res.json(), []);
  });

  it('creates a book and lists it', async () => {
    const created = await fetch(`${base}/books`, {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({ title: 'Dune', author: 'Herbert' }),
    });
    assert.equal(created.status, 201);
    assert.partialDeepStrictEqual(await created.json(), { title: 'Dune', author: 'Herbert' });

    const list = await (await fetch(`${base}/books`)).json();
    assert.equal(list.length, 1);
  });

  it('answers 400 to a malformed body', async () => {
    const res = await fetch(`${base}/books`, { method: 'POST', body: '{not json' });
    assert.equal(res.status, 400);
    assert.ok((await res.json()).error);
  });

  it('answers 404 to an unknown path', async () => {
    const res = await fetch(`${base}/nope`);
    assert.equal(res.status, 404);
    await res.body?.cancel();
  });
});

Four details in that file matter. partialDeepStrictEqual ignores the generated id, so the test does not depend on database order. The 404 test cancels the unread response body (res.body?.cancel()), because an unread body keeps the connection busy. server.closeAllConnections() closes idle keep-alive connections that fetch() leaves open, which otherwise makes close() wait. And binding to 127.0.0.1 explicitly avoids the IPv4 versus IPv6 resolution mismatch that a localhost base URL can produce on machines where the name resolves to ::1 first. A test that needs a database, a queue or another service is an integration test and should say so in its name and its folder; the sibling pages on databases and queues show how to start those dependencies in containers. Frameworks bring their own shortcuts (Fastify’s inject() injects a request without opening a socket, described on Web Frameworks: Express & Fastify), and the NestJS and Next.js sections have their own testing pages, which use Jest or Vitest (see Testing in NestJS and Testing in Next.js). The same test shape applies to a server you build in Building a REST API and to the lower-level API of HTTP Server Fundamentals.

Migrating from Mocha

Mocha and node:test have almost the same describe/it/hook shape, so migration is mostly mechanical. The Node.js project publishes a codemod, @nodejs/mocha-to-node-test-runner, that targets Mocha 8.x suites and node:test on Node.js 22 and 24. It adds the node:test imports for the globals a file uses, turns done callbacks into the (t, done) signature, rewrites this.skip() to t.skip() and this.timeout(n) to a { timeout: n } option, keeps your function style, supports both CommonJS and ESM files, and removes mocha and @types/mocha from package.json. Its documented limitation is that node:test has no equivalent of Mocha’s retry option.

Where the books are outdated

Testing is one of the clearest places where print falls behind, because the runner went from experimental to stable in v20.0.0 and has gained features in nearly every release since. Samer Buna’s Efficient Node.js (O’Reilly, 2025) has a chapter on testing Node that does cover node:test and node:assert, test doubles, TDD, --watch and coverage gates, and a later chapter that surveys Mocha, Chai and Jest as the tools of the trade. What it cannot cover are the later additions: partialDeepStrictEqual() as a stable assertion, awaited-by-default subtests, t.waitFor(), expectFailure, tags, randomized order and replayable seeds, --test-rerun-failures, JUnit and custom reporters as first-class output, the Experimental-to-Stable changes for snapshots and t.plan(), and the removal of assert.CallTracker in Node.js 25. Where a flag or option differs from this page, trust this page and the Node.js documentation. Jonathan Wexler’s Node.js Projects (O’Reilly, 2025) is organised around applications rather than around testing; its appendix on tools reaches for nodemon to restart a server, which node --watch (Stable since v22.0.0) now does, and node --test --watch does for tests. If you follow either book, use node:assert/strict rather than the legacy assert, import describe, it and the hooks explicitly (the runner has no globals), and prefer t.mock over mock so that doubles restore themselves.

A last reading note on one assertion helper, because it is easy to invert in your head: assert.doesNotMatch(string, regexp) passes when the string does not match the pattern (it is the negation of assert.match()), as the run of test/assertions.test.js above confirms.

Pitfalls

Table 13. Common mistakes with the Node.js test runner
Mistake Fix

Forgetting await on t.test()

Await every subtest; Node.js 22 cancels the ones still running when the parent finishes.

Using the imported assert with t.plan()

Use t.assert.*; the plan counts only assertions made through the context.

Importing node:assert instead of node:assert/strict

Legacy equal() and deepEqual() coerce with ==; use the strict import.

Passing a directory to node --test

Pass a glob ("test/*/.js") or rely on the default patterns; a directory name ran zero tests on Node.js 26 and failed on 24 and 22.

Putting helpers in test/

Every file under test/ is run as a test; keep helpers elsewhere or name them so no pattern matches.

Committing .only

Run with --test-only locally and let CI run without it, so a stray only fails loudly instead of silently narrowing the run.

Expecting todo to fail the build

A failing TODO test never changes the exit code; use expectFailure (Node.js 24.14 or later) to make a known failure self-checking.

A hard-coded port in server tests

Listen on port 0 and read server.address().port.

Not closing servers and handles

Close in after() or t.after(); --test-force-exit hides the leak rather than fixing it.

Tests that share state under --test-isolation=none

Keep the default process isolation unless you have measured a start-up problem.

Using retries as a flakiness cure

node:test has none; fix the race, or use --test-rerun-failures knowingly.

A test that cannot fail

Make sure the assertion would fail if the code were wrong: write the failing test first (TDD) and watch it fail for the reason you expect.

Relying on the exact text of a reporter

The output of built-in reporters is not stable; consume events through run() or a custom reporter.

Treating Early development features as stable

Tags, global setup, randomization and module mocks may change in minor releases; pin your Node.js version and re-test when upgrading.
