The File System

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Node.js 26 (26.10.0, released 2026-09-21, the Current line that becomes LTS on 2026-10-28), with the differences of Node.js 24 "Krypton" (24.21.0, Active LTS) and Node.js 22 "Jod" (22.23.3, Maintenance) called out; versions and stability levels were checked against the official documentation on 2026-10-03, and every example below was run on all three lines unless the text says otherwise. The node:fs module is Stability 2 (Stable) as a whole, and that covers the three API styles, FileHandle, fs.Stats, fs.openAsBlob() and filehandle.readableWebStream(). Three corners are not stable: fs.Utf8Stream and the filehandle.pull(), filehandle.pullSync() and filehandle.writer() methods are Stability 1 (Experimental), and fs.exists() is Stability 0 (Deprecated). Everything here is written for the Bookshelf application that grows across this section (see Introduction & Architecture): a catalog of books kept in JSON, an export in CSV, cover images, and a log. The page covers files; directories, glob patterns and file watching have their own page, Directories, Glob & Watch, and chunked reading and writing is the subject of Streams. The path helpers (join, resolve, dirname) are covered in OS, Path & URL.

Observations about operating systems come from the documentation unless the text says observed; the observed results were taken on macOS (an APFS volume, plus two small disk images created for the experiments: a case-sensitive APFS volume and a FAT32 volume). Linux and Windows behaviour is quoted from the documentation, never assumed.

How the file system API works underneath

The node:fs module is, in the words of its documentation, modeled on standard POSIX functions: open, read, stat, rename and friends, with the same names and, for system errors, the same error codes. Three layers are involved. The JavaScript functions you call validate the arguments, translate paths and options, and build the result (a Buffer, a string, an fs.Stats object). They call C++ bindings inside Node.js, which turn each call into a request for libuv. libuv then talks to the operating system.

The important design fact comes from libuv: unlike network sockets, files have no portable, platform-neutral way to be waited on, so libuv runs blocking file system calls on its thread pool. The Node.js documentation states the consequence: all callback and promise-based file system APIs, with the exception of fs.FSWatcher, use libuv’s thread pool, which can have surprising performance effects when the pool (four threads by default, UV_THREADPOOL_SIZE) is busy. The synchronous functions skip the hand-off and block the calling thread until the system call returns. The Event Loop shows the full journey of an fs.readFile() call through these layers, and its measurement of a stat() call queued behind CPU-bound pool tasks applies to every call on this page.

Three API styles

Every operation exists in three forms, reachable from both ES modules and CommonJS. The promise API lives in its own module, node:fs/promises (also available as the promises property of node:fs; the two are the same object, observed). The callback and synchronous forms live in node:fs, and the synchronous ones carry a Sync suffix. The promise API additionally has FileHandle objects; the callback and synchronous APIs use numeric file descriptors instead (see File descriptors and FileHandle).

The same read in each style
// One operation, three styles
import { readFile as readFileCb, readFileSync } from 'node:fs';
import { readFile } from 'node:fs/promises';

const catalog = new URL('./catalog.json', import.meta.url);

// 1. Promises: the default choice in application code
const viaPromise = JSON.parse(await readFile(catalog, 'utf8'));

// 2. Callback: error first, runs later
readFileCb(catalog, 'utf8', (err, text) => {
  if (err) throw err;
  console.log('callback  :', JSON.parse(text).length, 'books');
});

// 3. Sync: blocks the thread until the data is there
const viaSync = JSON.parse(readFileSync(catalog, 'utf8'));

console.log('promise   :', viaPromise.length, 'books');
console.log('sync      :', viaSync.length, 'books');
Output on Node.js 26, 24 and 22
promise   : 3 books
sync      : 3 books
callback  : 3 books

The order of the lines is the lesson. The promise and the synchronous read are finished by the time the first two lines print; the callback runs later, after the main code has returned to the event loop, which is why it prints last even though it was started second. A callback is never called synchronously by the file system API, so code after the call always runs first.

Source: Node.js Learn: Reading files with Node.js

When synchronous calls are acceptable

A synchronous call blocks the one JavaScript thread, so nothing else (timers, other requests, signal handlers) runs until it returns. The Learn article on blocking versus non-blocking names the synchronous standard-library methods that use libuv as the most common blocking operations: further JavaScript must wait until they finish. The measurement below reads a 200 MiB file twice, once in each style, while a timer asks to fire every millisecond.

A synchronous read freezes the timer; the promise read does not
// A synchronous read freezes the event loop; the promise version lets timers keep running
import { readFileSync, writeFileSync, rmSync } from 'node:fs';
import { readFile } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

const big = join(tmpdir(), 'bookshelf-big.bin');
writeFileSync(big, Buffer.alloc(200 * 1024 * 1024, 1));      // 200 MiB of test data

let ticks = 0;
const timer = setInterval(() => ticks++, 1);                  // wants to run every millisecond

try {
  let started = performance.now();
  readFileSync(big);
  console.log(`readFileSync: ${(performance.now() - started).toFixed(0)} ms, timer ticks: ${ticks}`);

  ticks = 0;
  started = performance.now();
  await readFile(big);
  console.log(`readFile    : ${(performance.now() - started).toFixed(0)} ms, timer ticks: ${ticks}`);
} finally {
  clearInterval(timer);
  rmSync(big);
}
Typical output on Node.js 26 (24 and 22 are within a few milliseconds of it)
readFileSync: 16 ms, timer ticks: 0
readFile    : 16 ms, timer ticks: 17

The synchronous read took about as long as the asynchronous one but delivered no timer ticks at all while it ran: for that whole time the process could not have answered a request. Reading a small file is far cheaper, but the principle scales with traffic, as Don’t Block the Event Loop explains.

The usual shape of a service is therefore synchronous at start-up, asynchronous afterwards:

Synchronous at start-up, promises inside the request handler
// Sync at start-up (once, before serving), promises inside request handlers
import { readFileSync } from 'node:fs';
import { readFile } from 'node:fs/promises';
import { createServer } from 'node:http';

// Acceptable: runs once, nothing else is waiting yet
const catalog = JSON.parse(readFileSync(new URL('./catalog.json', import.meta.url), 'utf8'));

const server = createServer(async (req, res) => {
  try {
    if (req.url === '/books') {
      res.setHeader('content-type', 'application/json');
      res.end(JSON.stringify(catalog));                       // in memory: no I/O at all
    } else if (req.url === '/about') {
      // Per-request file access: asynchronous, so other requests keep being served
      res.end(await readFile(new URL('./about.txt', import.meta.url)));
    } else {
      res.statusCode = 404;
      res.end('not found');
    }
  } catch (err) {
    res.statusCode = err.code === 'ENOENT' ? 404 : 500;
    res.end(err.code === 'ENOENT' ? 'not found' : 'internal error');
  }
});

server.listen({ port: 0, host: '127.0.0.1' }, async () => {
  const { port } = server.address();
  for (const path of ['/books', '/about', '/other']) {
    const response = await fetch(`http://127.0.0.1:${port}${path}`);
    console.log(path.padEnd(7), response.status, (await response.text()).slice(0, 30).replace(/\s+/g, ' '));
  }
  server.close();
});
Output on Node.js 26, 24 and 22
/books  200 [{"isbn":"978-0-00-000001-1","
/about  200 About the Bookshelf demo.
/other  404 not found

There is no ordering between independent calls

Because each callback or promise call is handed to a different pool thread, two calls started back to back may finish in any order. The documentation gives a rename followed by a stat of the new name as the canonical mistake. The experiment starts the stat at the same time as the rename, 200 times:

Starting two dependent calls together is a race
// No ordering between independent fs calls: they run on different thread pool threads
import { rename, stat, writeFile, mkdtemp, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

const dir = await mkdtemp(join(tmpdir(), 'bookshelf-'));
let failed = 0;
const runs = 200;
try {
  for (let i = 0; i < runs; i++) {
    const from = join(dir, `a${i}`);
    const to = join(dir, `b${i}`);
    await writeFile(from, 'x');
    // Both calls are started immediately: stat may reach the disk before rename does
    const [, statted] = await Promise.allSettled([rename(from, to), stat(to)]);
    if (statted.status === 'rejected') failed++;
  }
  console.log(`stat() failed with ENOENT in ${failed} of ${runs} runs`);

  // Correct: await the first operation, then start the second
  const from = join(dir, 'c');
  await writeFile(from, 'x');
  await rename(from, join(dir, 'd'));
  console.log('ordered:', (await stat(join(dir, 'd'))).size, 'byte');
} finally {
  await rm(dir, { recursive: true, force: true });
}
Output on Node.js 26 (198 to 200 of 200 on 24 and 22; observed, it varies from run to run)
stat() failed with ENOENT in 198 of 200 runs
ordered: 1 byte

The fix is the one the documentation states: await the first operation before starting the second (or, with callbacks, start the second inside the first’s callback). The same rule applies to mixed styles: an asynchronous readFile() followed by a synchronous unlinkSync() of the same file will usually delete the file before the read starts.

Source: Node.js API: File system (ordering of callback and promise-based operations)

Naming a file: strings, URLs and Buffers

Most fs functions accept a path in one of three forms, as the Learn article and the API reference describe.

Table 6. The three path forms
Form How it is interpreted Watch out for

String

UTF-8 text naming an absolute or relative file. A relative path is resolved against process.cwd(), the directory where the process was started, not against the file that contains the call.

Backslashes on Windows; the working directory changing between runs.

file: URL (a URL object)

Always absolute. new URL('./catalog.json', import.meta.url) names a file next to the current module, wherever Node.js was started.

Encoded separators (%2F) are rejected on every platform; on Windows a host name becomes a UNC path and a URL with no host needs a drive letter; on other platforms a host name is an error.

Buffer

Raw bytes; useful on POSIX systems where a path is an opaque byte sequence that may mix encodings.

Rarely needed; every string path is converted from UTF-8.

On Windows the documentation adds three details: each drive has its own working directory (fs.readdirSync('C:') and fs.readdirSync('C:\\') can differ), the characters < > : " / \ | ? * are reserved, and under NTFS a colon in a name makes Node.js open an alternate data stream rather than a file named with a colon.

Relative paths depend on where node starts; module-anchored paths do not
// Three ways to name the same file
import { readFile } from 'node:fs/promises';
import { basename, join } from 'node:path';
import { fileURLToPath } from 'node:url';

// Relative paths are resolved against the working directory (where node was started)...
console.log('relative  :', await readFile('catalog.json').then(() => 'found', (err) => err.code));

// ...so anchor files to the module instead
const viaJoin = join(import.meta.dirname, 'catalog.json');       // a string path
const viaUrl = new URL('./catalog.json', import.meta.url);       // a file: URL
console.log('url       :', viaUrl.protocol, basename(fileURLToPath(viaUrl)));

const [fromPath, fromUrl, fromBuffer] = await Promise.all([
  readFile(viaJoin),
  readFile(viaUrl),
  readFile(Buffer.from(viaJoin)),                                 // a Buffer path: raw bytes on POSIX
]);
console.log('same bytes:', fromPath.equals(fromUrl) && fromPath.equals(fromBuffer), fromPath.length, 'bytes');
Output on Node.js 26, 24 and 22, started from another directory (first three lines) and from the project directory (last three)
relative  : ENOENT
url       : file: catalog.json
same bytes: true 247 bytes
relative  : found
url       : file: catalog.json
same bytes: true 247 bytes

import.meta.dirname and import.meta.filename are the ES-module replacement for __dirname and __filename; their CommonJS equivalents are covered in ECMAScript Modules and CommonJS Modules. The node:path functions the Learn article lists (dirname, basename, extname, join, resolve, normalize) only compute strings: as the article says, neither resolve() nor normalize() checks that the path exists. That has a security consequence developed in Links: symbolic, hard, and why paths are not trustworthy.

Source: Node.js Learn: Node.js File Paths, Node.js API: File system (file paths)

Reading whole files

readFile() (and readFileSync()) is the simplest way to get a file’s content: it opens the file, reads all of it into memory and closes it. Without an encoding it returns a Buffer (see Buffers & Binary Data); with one, a string. A string as the options argument is shorthand for the encoding.

Table 7. Options of readFile()
Option Meaning Default and notes

encoding

Decode the bytes into a string ('utf8', 'latin1', 'base64', and the other Buffer encodings).

null: return a Buffer.

flag

How to open the file; see Flags.

'r'

signal

An AbortSignal that cancels the read. The promise rejects (or the callback receives) an AbortError.

Aborting stops Node.js’s internal buffering, not an individual operating-system request already in flight.

buffer

A Buffer, typed array or DataView to read into, or a function that receives the file size and returns one. The result is a Buffer view over it holding only the bytes read; a buffer that is too small is an error.

Added in v26.4.0 and v24.19.0; absent on Node.js 22.
readFile() options in action
// readFile options: encoding, signal, a caller-supplied buffer (Node.js 26.4+), and a directory
import { readFile } from 'node:fs/promises';
import { Buffer } from 'node:buffer';

const file = new URL('./catalog.json', import.meta.url);

const bytes = await readFile(file);               // no encoding: a Buffer
const text = await readFile(file, 'utf8');        // a string (same as { encoding: 'utf8' })
console.log(Buffer.isBuffer(bytes), typeof text);

Four practical points follow from the reference documentation and from what was observed:

  • Reading a directory fails with EISDIR on macOS, Linux and Windows; the documentation notes that FreeBSD returns a representation of the directory instead.

  • Descriptors are accepted in place of paths by the callback and synchronous forms. A descriptor is not closed for you, and reading begins at its current position, so a descriptor that has already been read from returns only the remainder.

  • A UTF-8 byte order mark is not stripped. Decoding a file that begins with one gives a string whose first character is U+FEFF, and JSON.parse() rejects it (observed); strip it with text.replace(/^﻿/, '') when the files come from editors that add it.

  • readFile() has no timeout and no size cap other than the one in the next section, so never point it at a path taken from a request without validating the path (see Links: symbolic, hard, and why paths are not trustworthy).

How readFile reads: chunks, not one gulp

The documentation’s performance notes explain what happens inside: readFile() reads the file into memory one chunk at a time, letting the event loop turn between chunks. For regular files each read handles 512 KiB; when Node.js cannot determine a size (a pipe, for instance) each read handles 64 KiB. That is kind to other pool users but slower than one big read, and the documentation says that code needing the fastest possible read should call fs.read() itself and manage the buffer. Memory is the other cost: the whole content is resident, plus any string decoded from it.

The 2 GiB limit

readFile() refuses files larger than 2 GiB with ERR_FS_FILE_TOO_LARGE. The error catalogue is explicit that this is not a limit of Buffer but an internal I/O constraint, and recommends fs.createReadStream() for larger files. The experiment creates a sparse file of 2 GiB plus one byte (it occupies almost no disk space on common file systems, which is why the test is cheap) and tries both approaches.

Concurrent writes and durable, atomic updates

Three rules from the reference documentation shape every write path:

  • writeFile() is not safe to call several times on the same file without waiting for the previous call to finish, in any of the three styles. The documentation recommends createWriteStream() for that situation. It could not be provoked deterministically in the test (two simultaneous 4 MB writes came out intact), which is exactly why it is dangerous: the failure depends on timing.

  • The promise API "is not synchronized or threadsafe", and care must be taken with concurrent modifications of the same data.

  • A successful write means the operating system accepted the data, not that it reached the disk. flush: true (or filehandle.sync() and fs.fsync()) asks for it to be pushed to the device.

The first rule is solved by serialising the writers. The second and third are solved together by the classic recipe for replacing a file so that readers see either the old or the new version, never half of a new one: write a temporary file in the same directory, flush it, and rename it over the target.

Serialising appends from many callers
// Serialise appends to one file: the next write starts only after the previous one finished
import { appendFile, readFile, mkdtemp, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

function createLogger(path) {
  let tail = Promise.resolve();
  return (line) => {
    tail = tail.then(() => appendFile(path, `${line}\n`));
    return tail;
  };
}

const dir = await mkdtemp(join(tmpdir(), 'bookshelf-'));
const file = join(dir, 'access.log');
try {
  const log = createLogger(file);
  await Promise.all(Array.from({ length: 5 }, (_, i) => log(`request ${i}`)));
  console.log((await readFile(file, 'utf8')).trim().split('\n'));
} finally {
  await rm(dir, { recursive: true, force: true });
}

    await rm(temp, { force: true });
    throw err;
  }
}

  console.log(await readFile(target, 'utf8'));
  console.log(await readdir(dir));                  // no temporary file left behind

}

File descriptors and FileHandle

Before Node.js can read or write a file it must open it, and opening returns a handle by which the operating system tracks that open file. On POSIX systems this is a small integer, the file descriptor, taken from a table the kernel keeps for each process; Windows uses a different but similar mechanism, and Node.js hides the difference by giving every open file a numeric descriptor. The Learn article’s point is that the whole fs API is built on this: every operation after open() identifies the file by descriptor.

The callback and synchronous APIs expose the number itself. Two consequences follow. First, the operating system limits how many descriptors a process may hold open, so a descriptor must always be closed, in a finally block when it is synchronous, because a leak grows until opens fail with EMFILE. Second, a number is easy to misuse: once closed, it may be handed out again for another file.

Descriptor-based calls: open, read at a position, always close
// Descriptor-based API: numbers instead of FileHandle objects. Every open needs a close.
import { openSync, readSync, closeSync, fstatSync, open, read, close } from 'node:fs';
import { promisify } from 'node:util';

const path = new URL('./catalog.json', import.meta.url);

// Synchronous: try/finally guarantees the close
const fd = openSync(path, 'r');
try {
  const { size } = fstatSync(fd);
  const head = Buffer.alloc(12);
  const n = readSync(fd, head, 0, head.length, 0);         // position 0
  console.log('sync    :', fd > 2, size, n, JSON.stringify(head.toString()));
} finally {
  closeSync(fd);
}

// Callback style, promisified with util.promisify when you need await
const openP = promisify(open);
const readP = promisify(read);
const closeP = promisify(close);
const fd2 = await openP(path, 'r');
try {
  const { bytesRead, buffer } = await readP(fd2, Buffer.alloc(12), 0, 12, 2);
  console.log('promisified:', bytesRead, JSON.stringify(buffer.toString()));
} finally {
  await closeP(fd2);
}

// The descriptor is gone after close: using it again fails
try { readSync(fd, Buffer.alloc(1), 0, 1, 0); } catch (err) { console.log('after close:', err.code); }

Too many open files

Descriptors are a finite resource. The limit is a per-process setting of the operating system (on Linux and macOS, ulimit -n). Reaching it produces EMFILE. In the experiment below, a low soft limit alone was not enough to provoke it: Node.js raised it by itself as far as the hard limit allowed (observed), so the hard limit had to be lowered too. Note the cause: not too many calls in flight (the thread pool runs only a few at a time) but too many open handles.

Opening files without closing them hits EMFILE; bounded concurrency does not
// Too many open files at once: EMFILE, and a bounded alternative
import { open, readFile, writeFile, mkdtemp, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

const dir = await mkdtemp(join(tmpdir(), 'bookshelf-'));

  const names = Array.from({ length: 3000 }, (_, i) => join(dir, `book-${i}.txt`));

Durability: when is the data really on disk?

A completed write() hands the bytes to the operating system’s cache; a power failure can still lose them. sync() and fs.fsync() (flush data and metadata) and datasync() and fs.fdatasync() (flush data, not all metadata) ask for the data to be pushed to the device, and the exact guarantee is "operating system and device specific", as the documentation puts it. The flush: true option of writeFile() and of write streams performs the same flush for you. Use it for data you cannot regenerate (an order, a payment record), not for logs where throughput matters more.

stat(path) returns an fs.Stats object describing the file, following symbolic links; lstat() describes a link itself; fstat(fd) and filehandle.stat() describe an open file. Permissions, modes and the umask

POSIX permissions are three groups (owner, group, others) of three bits (read 4, write 2, execute 1), written as three octal digits: 0o640 is read and write for the owner, read for the group, nothing for others. In JavaScript, use the 0o prefix; 640 is a different number. When a file is created, the mode option (default 0o666 for files) is reduced by the process umask, a mask of bits to remove, so a umask of 0o022 turns 0o666 into 0o644. The mode argument is only applied to newly created files.

A symbolic link is a small file whose content is a path; the operating system substitutes it when the path is used. A hard link is a second directory entry for the same data. The API follows the POSIX names: symlink(target, path), link(existing, new), readlink(), realpath(), unlink().

Describes the link itself; isSymbolicLink() is true.

Untrusted paths: traversal and symlink escape

When part of a path comes from outside (a request, an upload name, an archive entry), join(base, name) is not enough: name can be ../../etc/passwd, and the result is simply a string; path.resolve() and path.normalize() do not touch the file system, so they cannot see symbolic links. A containment check has to resolve links too and then compare the real locations:

Reading a file only if it really lives inside the base directory
// Resolve an untrusted name inside a base directory, following symbolic links, and refuse anything that escapes
import { readFile, realpath, writeFile, symlink, mkdir, mkdtemp, rm } from 'node:fs/promises';
import { isAbsolute, join, relative, sep } from 'node:path';
import { tmpdir } from 'node:os';

async function readInside(baseDir, untrustedName) {
  if (untrustedName.includes('\0')) throw new Error('invalid name');
  const base = await realpath(baseDir);
  const target = await realpath(join(base, untrustedName));   // resolves ".." and symbolic links; throws ENOENT if missing
  const rel = relative(base, target);
  if (rel === '' || rel === '..' || rel.startsWith(`..${sep}`) || isAbsolute(rel)) {
    throw Object.assign(new Error('outside the base directory'), { code: 'E_OUTSIDE_BASE' });
  }
  return readFile(target, 'utf8');
}

const root = await mkdtemp(join(tmpdir(), 'bookshelf-'));
try {
  await mkdir(join(root, 'covers'));
  await writeFile(join(root, 'covers', 'a.txt'), 'cover a\n');
  await writeFile(join(root, 'secret.txt'), 'not for clients\n');
  await symlink('../secret.txt', join(root, 'covers', 'sneaky.txt'));

  for (const name of ['a.txt', '../secret.txt', 'sneaky.txt', 'missing.txt']) {
    const result = await readInside(join(root, 'covers'), name).catch((err) => err.code);
    console.log(name.padEnd(15), JSON.stringify(result));
  }
} finally {
  await rm(root, { recursive: true, force: true });
}

A move that works across volumes
// rename() is atomic but cannot cross a file system boundary (EXDEV); fall back to copy + delete
import { rename, copyFile, unlink, writeFile, readFile, mkdtemp, rm, constants } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

async function move(from, to) {
  try {
    await rename(from, to);
    return 'rename';
  } catch (err) {
    if (err.code !== 'EXDEV') throw err;
    await copyFile(from, to, constants.COPYFILE_EXCL);   // refuse to overwrite an existing target
    await unlink(from);                                   // only after the copy succeeded
    return 'copy + unlink';
  }
}

// Pass another volume as the first argument to take the fallback path

const targetDir = await mkdtemp(join(tmpdir(), 'move-dst-'));
try {
  const from = join(sourceDir, 'cover.png');
  const to = join(targetDir, 'cover.png');
  await writeFile(from, 'png bytes');
  console.log('strategy :', await move(from, to));
  console.log('content  :', await readFile(to, 'utf8'));

  await writeFile(from, 'second copy');
  await copyFile(from, to, constants.COPYFILE_EXCL).catch((err) => console.log('no clobber:', err.code));
} finally {
  await rm(sourceDir, { recursive: true, force: true });
  await rm(targetDir, { recursive: true, force: true });
}

Different file systems behave differently

Node.js exposes what the operating system offers, and file systems differ in what they offer. The Learn article on different file systems lists the dimensions: case sensitivity and case preservation, Unicode form (NFC, NFD) preservation, timestamp resolution, extended attributes, inodes, Unix permissions, alternate data streams. Its advice is a small set of rules that this page’s experiments confirm.

  1. Do not infer behaviour from process.platform. A program on macOS may use a case-sensitive volume; a program on Linux may be writing to a USB drive or network share that has no Unix permissions.

  2. Probe instead of guessing. A few cheap experiments (create a file, look for it under another spelling) reveal the behaviour, and the answer can differ per directory because volumes are mounted at different places in one tree.

  3. Do not make your program a lowest common denominator by normalising every name to upper case, every string to NFC and every timestamp to one-second resolution. You could then only coexist with file systems with exactly those limits, and you would collide names that differ only in case or form and corrupt user data.

  4. Adopt a superset approach instead: preserve case, preserve the exact Unicode bytes, keep nanosecond timestamps, keep permissions. When a weaker file system loses information, compensate when you compare, not when you store.

  5. Use normalisation only as a comparison function. Compare a.normalize('NFC') === b.normalize('NFC') (either form works as long as both sides use the same), never overwrite the name you were given; and do not use a case-insensitive comparison on a case-sensitive file system.

The article also states that names and timestamps are user data: a file system may return ABC for a directory created as abc, a Unicode name in a form other than the one you wrote, or a modification time rounded to 2 seconds, and none of that is a Node.js bug, because Node.js returns what the file system stores.

The experiment below runs the probes the article suggests, on three different volumes, and prints what each one does.

Probing a file system for case, Unicode form and timestamp behaviour
// Probe the file system you are on instead of guessing from process.platform
import { writeFile, readdir, stat, utimes, mkdtemp, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

const dir = await mkdtemp(join(process.argv[2] ?? tmpdir(), 'bookshelf-probe-'));
try {
  // Case sensitivity: create "probe.txt", then ask for "PROBE.TXT"
  await writeFile(join(dir, 'probe.txt'), 'x');
  const caseInsensitive = await stat(join(dir, 'PROBE.TXT')).then(() => true, () => false);

  // Case preservation: what name does the directory listing return?
  await writeFile(join(dir, 'MixedCase.txt'), 'x');
  const listed = (await readdir(dir)).includes('MixedCase.txt');

  // Unicode form: create the NFC name, look for the NFD spelling
  const nfc = 'café.txt';
  const nfd = nfc.normalize('NFD');
  await writeFile(join(dir, nfc), 'x');
  const normalizationInsensitive = await stat(join(dir, nfd)).then(() => true, () => false);
  const names = (await readdir(dir)).filter((n) => n.startsWith('caf'));
  const stored = names[0] === nfc ? 'NFC' : 'NFD';

  // Timestamp resolution: set a mtime with millisecond detail and read it back
  const wanted = new Date(1_444_291_759_414);          // ...414 ms
  await utimes(join(dir, 'probe.txt'), wanted, wanted);
  const mtimeMs = (await stat(join(dir, 'probe.txt'), { bigint: true })).mtimeMs;

  console.log({ caseInsensitive, casePreserved: listed, normalizationInsensitive, storedAs: stored, mtimeMs });
  console.log('NFC length', nfc.length, 'NFD length', nfd.length, 'equal when normalised:', nfc.normalize('NFC') === nfd.normalize('NFC'));
} finally {
  await rm(dir, { recursive: true, force: true });
}

Two more file-backed APIs

fs.openAsBlob(path) returns a Blob whose data is backed by the file and read lazily, so blob.slice(0, 8).text() reads only those bytes. It is a cheap way to hand a file to any API that accepts a Blob without reading it into memory first. The file must not be modified after the blob is created: changes make reads fail with a DOMException, because Node.js checks the file before each read. It is stable since v24.0.0 and v22.17.0, and fs.openAsBlobSync() joined it in v26.10.0.

fs.Utf8Stream (Stability 1, Experimental, v24.6.0) is an optimised writer for UTF-8 text whose internal buffer can be flushed on demand, which handles EAGAIN correctly and can drop data when the disk is busy, the kind of control a logger wants. Treat the API as unstable and wrap it behind your own function.

A Blob backed by a file, and an experimental buffered log writer
// Two file-backed helpers: a Blob that reads lazily from disk, and an experimental fast log writer
import { openAsBlob, Utf8Stream } from 'node:fs';
import { readFile, mkdtemp, rm } from 'node:fs/promises';
import { once } from 'node:events';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

const catalog = new URL('./catalog.json', import.meta.url);
const blob = await openAsBlob(catalog, { type: 'application/json' });   // stable since v24.0.0 / v22.17.0
console.log('blob       :', blob.type, blob.size, 'bytes');
console.log('slice      :', JSON.stringify(await blob.slice(0, 8).text()));   // reads only that range

const dir = await mkdtemp(join(tmpdir(), 'bookshelf-'));
try {
  const log = new Utf8Stream({ dest: join(dir, 'app.log'), sync: false, minLength: 4096 });   // Stability 1 - Experimental
  await once(log, 'ready');
  for (let i = 0; i < 3; i++) log.write(`line ${i}\n`);     // buffered, not yet on disk
  log.end();                                                 // flush, then close
  await once(log, 'finish');
  console.log('log file   :', JSON.stringify(await readFile(join(dir, 'app.log'), 'utf8')));
} finally {
  await rm(dir, { recursive: true, force: true });
}

Where streams fit

createReadStream() and createWriteStream() belong to this module but are the subject of Streams. The facts to carry from here: both accept start (and end, inclusive, for reads) to address a byte range; autoClose and emitClose control closing; a read stream’s default highWaterMark is 64 KiB; the default for write streams was raised in v22.0.0; flush: true flushes a write stream before it closes; and since v26.8.0 a Windows-only windowsHandle option lets either wrap a raw Win32 handle. Use a stream whenever the data is big, unbounded, or produced over time.

Where the books are outdated

Efficient Node.js (Samer Buna, O’Reilly 2025) shows file reading in all three styles and uses a readFile against createReadStream comparison to motivate streams, which is a good introduction and still valid in spirit. Three things need updating. It says that a file above 2 GB cannot be served with readFile by default and hints that the limits can be changed; the documented limit is an internal I/O constraint of readFile() (ERR_FS_FILE_TOO_LARGE), independent of Buffer's maximum size, so there is no setting to raise and the answer is a stream or ranged reads (The 2 GiB limit). Its coverage of the promise API stops at readFile(): FileHandle, explicit positions, await using (Node.js 24 and later), durability (flush), flags, modes and the umask, symbolic links and file system differences are not part of its scope. And, written before Node.js 25, it cannot mention the end-of-life changes in What changed recently.

Node.js Projects (Jonathan Wexler, O’Reilly 2025) exports contacts to a CSV file with writeFileSync() and appendFileSync() and suggests guarding the append with existsSync(). Synchronous calls are acceptable in a one-person command-line tool (When synchronous calls are acceptable), but the guard is unnecessary (appending creates the file) and racy (Do not check, then act), the writes would block a server, and the CSV is built by joining strings, which breaks as soon as a title contains a comma. It imports from "fs" rather than "node:fs", which still works; the node: prefix is the convention throughout this section because it states plainly that the module is built in. The permission model for restricting file access gets at most a passing mention.
