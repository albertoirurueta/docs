Worker Threads

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Node.js 26 (26.10.0, released 2026-09-21, the Current line that becomes LTS on 2026-10-28), with the differences of Node.js 24 "Krypton" (24.21.0, Active LTS) and Node.js 22 "Jod" (22.23.3, Maintenance) called out; versions and stability levels were checked against the official documentation on 2026-10-04, and every example was run on all three lines unless the text says otherwise. The node:worker_threads module runs additional JavaScript threads inside one Node.js process. Each worker has its own V8 isolate, its own event loop and its own heap, so a loop that takes two seconds in a worker does not delay a single timer or HTTP response on the main thread. The module is Stability 2 (Stable); a few of its newer corners are not: postMessageToThread() is 1.1 (Active development), worker_threads.locks is 1 (Experimental), the --allow-worker permission flag is 1.1, and the browser-style Worker global added in Node.js 26.9 is 1 (Experimental) behind a flag. Workers are for CPU-bound JavaScript; for I/O, the built-in asynchronous APIs are more efficient than any worker. The page builds a worker pool for the Bookshelf application that grows across this section (see Introduction & Architecture), hashes cover images with it, and ends with a proof-of-work miner. The same ideas in the browser are in Web Workers.

Why threads, and when not

The main thread of a Node.js process runs your JavaScript, one callback at a time. Asynchronous I/O is cheap because libuv and the operating system do the waiting; but a long synchronous computation (hashing, parsing a large file, image work, compression in userland JavaScript) occupies the only thread and nothing else runs until it returns. The program below measures that. It runs the same one-million-step hash chain on the main thread and then in a worker, while a 10 ms interval records the longest gap between ticks.

Event-loop gap with the work on the main thread versus in a worker
import { Worker, isMainThread, parentPort } from 'node:worker_threads';
import { createHash } from 'node:crypto';

const work = () => {
  let h = Buffer.from('seed');
  for (let i = 0; i < 1_000_000; i++) h = createHash('sha256').update(h).digest();
  return h.toString('hex').slice(0, 8);
};

if (!isMainThread) {
  parentPort.postMessage(work());
} else {
  async function measure(label, fn) {
    let maxGap = 0, last = performance.now();
    const ticker = setInterval(() => {
      const now = performance.now();
      maxGap = Math.max(maxGap, now - last);
      last = now;
    }, 10);
    const start = performance.now();
    const result = await fn();
    const ms = Math.round(performance.now() - start);
    await new Promise((r) => setTimeout(r, 30));          // let a late tick report the gap
    clearInterval(ticker);
    console.log(label, { result, ms, maxTickGapMs: Math.round(maxGap) });
  }
  await measure('on the main thread', async () => { await new Promise((r) => setImmediate(r)); return work(); });
  await measure('in a worker       ', () => new Promise((resolve, reject) => {
    const w = new Worker(new URL(import.meta.url));
    w.once('message', resolve);
    w.once('error', reject);
  }));
}

Source: Node.js API: Worker threads, Node.js Learn: Don’t block the event loop

Observed output (Node.js 26.10.0, macOS arm64; timings vary run to run)
on the main thread { result: '6871b211', ms: 474, maxTickGapMs: 474 }
in a worker        { result: '6871b211', ms: 402, maxTickGapMs: 11 }

The result is identical; what changed is the longest tick gap, 474 ms (the whole computation) against 11 ms (the 10 ms timer plus scheduling noise). Creating a worker: Worker, isMainThread, parentPort, workerData

A Worker runs one script. The same file can be both the parent and the worker: isMainThread is true in the main thread and false inside a worker, workerData is a clone of whatever the constructor was given, and parentPort is the channel back to the parent (it is null on the main thread). Worker scripts are ECMAScript modules or CommonJS according to the same rules as any other file, so new URL(import.meta.url) is the ESM way to point at yourself and __filename the CommonJS one.

One file that is both the parent and the worker
import { Worker, isMainThread, parentPort, workerData, threadId } from 'node:worker_threads';

if (isMainThread) {
  const worker = new Worker(new URL(import.meta.url), { workerData: { title: 'Dune', n: 35 } });
  worker.once('online', () => console.log('main: worker', worker.threadId, 'is online'));
  worker.on('message', (msg) => console.log('main: got', msg));
  worker.once('error', (err) => console.error('main: worker threw', err.message));
  worker.once('exit', (code) => console.log('main: worker exited with', code));
} else {
  const fib = (n) => (n < 2 ? n : fib(n - 1) + fib(n - 2));
  parentPort.postMessage({ from: threadId, title: workerData.title, fib: fib(workerData.n) });
}

A worker is an EventEmitter and reports its life cycle through events. Wrapping them in a promise is the usual way to consume a one-shot worker. Three events must all be handled, because a failure shows up differently depending on how the worker dies:

'message'

Wrapping a worker in a promise
import { Worker } from 'node:worker_threads';

  return new Promise((resolve, reject) => {
    const worker = new Worker(file, { workerData });
    worker.once('message', resolve);                     // first result wins
    worker.once('error', reject);                        // uncaught exception in the worker
    worker.once('exit', (code) => {
      if (code !== 0) reject(new Error(`worker stopped with exit code ${code}`));
    });
  });
}

What a worker is, and how it differs from the main thread

Most of the Node.js API works inside a worker; the notable differences are that process.exit() stops only the current thread, process.abort() and process.chdir() and the user-id setters are not available, process.title cannot be changed, signals are not delivered to process.on(…​) handlers of a worker, there is no IPC channel from a parent process, and the trace_events module is not supported. process.env is a copy by default. Native add-ons can be loaded from several threads only if they are written for it. Workers can create workers.

The following example creates three workers with the three environment modes and passes the same data in each of the ways Node.js offers: workerData (one clone per worker), setEnvironmentData() (a value set once and visible to every worker created afterwards) and argv.

Environment, environment data, argv and thread names

  setEnvironmentData('locale', 'es-ES');                    // cloned into every Worker created afterwards

  for (const options of [
    { name: 'copy-env' },                                  // default: process.env is copied

    { name: 'custom-env', env: { ONLY_THIS: '1' } },

      const w = new Worker(new URL(import.meta.url), { ...options, argv: ['--verbose'], workerData: options.name });

      w.once('exit', resolve);

}

Execution arguments and preload scripts

Unless execArgv is set, a worker inherits the command-line options of the process, including --require and --import preloads. Messaging: MessageChannel, MessagePort and structured clone

Every worker has a built-in pair of connected MessagePort objects: worker.postMessage() and the worker’s parentPort.postMessage(). Messages are copied using the HTML structured clone algorithm, not JSON. That brings circular references, Date, Map, Set, RegExp, BigInt, typed arrays and WebAssembly.Module instances across the thread boundary, and it excludes functions and most native-backed objects. Instead of mutable sharing, you get copies: changing a message after posting it has no effect on what the other side received.

What survives structured clone, and what does not
import { MessageChannel } from 'node:worker_threads';

const { port1, port2 } = new MessageChannel();
port1.on('message', (m) => { console.log('received', m); });
port1.on('messageerror', (e) => console.log('messageerror', e.message));

const circular = { name: 'loop' }; circular.self = circular;
port2.postMessage({ when: new Date(0), tags: new Set(['a']), map: new Map([[1, 'x']]), big: 10n, circular, re: /x/g });

try { port2.postMessage({ fn() {} }); } catch (e) { console.log(e.name, '-', e.message); }
class Book { constructor(t) { this.title = t; } get upper() { return this.title.toUpperCase(); } }
port2.postMessage(new Book('Dune'));               // arrives as a plain object

const bytes = new Uint8Array([1, 2, 3, 4]);
port2.postMessage(bytes);                           // copy
console.log('after copy    :', bytes.byteLength);
port2.postMessage(bytes, [bytes.buffer]);           // transfer
console.log('after transfer:', bytes.byteLength, bytes.buffer.detached);
setTimeout(() => port1.close(), 50);

And bytes.byteLength becomes 0 after the transfer: ownership of the memory moved, so the sender’s view is detached.

The same Error class does cross the boundary in an 'error' event (as the promise example showed with RangeError), but errors posted as ordinary messages follow the structured-clone rules, which is why the pool below sends an error as a plain description.

Posting a function, a class instance with behaviour, or a framework object (a request, a socket wrapper, a database client)

Dedicated channels: MessageChannel

The built-in port is a single global channel per worker. The Node.js docs encourage creating a MessageChannel (a pair port1, port2) for each concern and handing one port to the other thread through the existing channel, listing it in the transfer list. A port can also be handed between workers, so two workers can talk directly without going through the parent.

Handing one end of a MessageChannel to a worker
import { Worker, MessageChannel, isMainThread, parentPort, threadId } from 'node:worker_threads';

if (isMainThread) {
  const worker = new Worker(new URL(import.meta.url));
  const { port1, port2 } = new MessageChannel();
  worker.postMessage({ hello: port2 }, [port2]);          // hand one end to the worker
  port1.on('message', (m) => {
    console.log('main via port1:', m);
    port1.close();                                         // closing one end closes both
  });
  port1.postMessage('ping');
  worker.once('exit', () => console.log('worker exited'));
} else {
  parentPort.once('message', ({ hello }) => {
    hello.on('message', (m) => hello.postMessage(`${m} -> pong from thread ${threadId}`));
    hello.on('close', () => parentPort.close());           // nothing left to listen to: let the worker end
  });
}

One-to-many: BroadcastChannel

A BroadcastChannel connects every BroadcastChannel created with the same name, in any thread of the process. A message goes to all other subscribers, never back to the sender. It is a good fit for invalidation messages (a cache entry changed) and a poor one for work distribution, because every subscriber receives every message.

  bc.close();
} else {
  const bc = new BroadcastChannel('catalog-events');
  bc.onmessage = ({ data }) => { console.log(`worker ${workerData.id} received`, data); bc.close(); };
  (await import('node:worker_threads')).parentPort.postMessage('ready');
}

Transferables

Cloning copies bytes; transferring moves them. A transferList accepts ArrayBuffer, MessagePort, FileHandle, and in the Node.js 24 and 26 docs also a TCP net.Server or net.Socket (26 adds net.BoundSocket). After the transfer the object is unusable on the sending side. Passing an ArrayBuffer in the list is how you avoid copying an image or a chunk of a file: the receiver gets the same memory, the sender gets a detached, zero-length buffer, as the clone example showed.

Two rules avoid surprises. All typed arrays and Buffer objects are views of an ArrayBuffer, and transferring that buffer detaches every view over it. And Buffer.from() and Buffer.allocUnsafe() for small sizes draw from a shared pool, so their .buffer is a large ArrayBuffer shared with unrelated buffers; Node.js marks the pool with markAsUntransferable(), and trying to transfer it throws. Copy into a fresh buffer first (new Uint8Array(source)), as the pool below does. markAsUntransferable() and markAsUncloneable() let you apply the same protection to your own objects.

Untransferable and uncloneable objects
import { MessageChannel, markAsUntransferable, markAsUncloneable } from 'node:worker_threads';
const { port1, port2 } = new MessageChannel();
const pooled = new ArrayBuffer(16);
markAsUntransferable(pooled);
try { port1.postMessage(pooled, [pooled]); } catch (e) { console.log(e.name, e.code); }
const secret = { token: 'placeholder' };
markAsUncloneable(secret);
try { port1.postMessage(secret); } catch (e) { console.log(e.name, e.code ?? ''); }
const b = Buffer.from('abc'); // small Buffers share a pooled ArrayBuffer
console.log('Buffer.from("abc").buffer.byteLength =', b.buffer.byteLength);
try { port1.postMessage(b, [b.buffer]); } catch (e) { console.log('pooled Buffer:', e.name); }
port1.close();

  client.setEncoding('utf8');
  client.on('data', (text) => console.log('client received:', text.trim()));
  client.on('close', () => worker.terminate());
} else {
  parentPort.once('message', ({ server }) => {
    server.on('connection', (socket) => socket.end(`served by thread ${threadId}\n`));
    parentPort.postMessage('listening');
  });
}

Shared memory: SharedArrayBuffer and Atomics

Where the pool above moves buffers, a SharedArrayBuffer is visible to every thread that receives it: it cannot be in a transfer list, it is simply posted (cloned as a handle to the same memory) in a message or in workerData. This is the only way worker threads share mutable memory, and it brings the usual shared-memory problem: unsynchronised read-modify-write sequences race. Atomics provides indivisible operations (add, load, store, compareExchange, exchange) and a wait/notify mechanism on an Int32Array (or BigInt64Array) over the shared buffer. In Node.js you do not need the cross-origin isolation headers that browsers require to expose SharedArrayBuffer.

The first example makes four workers increment one counter 200,000 times each, once with a plain counter[0]++ and once with Atomics.add().

A data race, and the fix with Atomics
import { Worker, isMainThread, workerData } from 'node:worker_threads';

const N = 200_000, THREADS = 4;
if (isMainThread) {
  for (const mode of ['plain', 'atomic']) {
    const sab = new SharedArrayBuffer(4);
    const counter = new Int32Array(sab);
    await Promise.all(Array.from({ length: THREADS }, () => new Promise((res, rej) => {
      const w = new Worker(new URL(import.meta.url), { workerData: { sab, mode } });
      w.once('exit', res); w.once('error', rej);
    })));
    console.log(mode.padEnd(6), 'expected', N * THREADS, 'got', counter[0]);
  }
} else {
  const counter = new Int32Array(workerData.sab);
  for (let i = 0; i < N; i++) {
    if (workerData.mode === 'plain') counter[0]++;      // read-modify-write: a data race
    else Atomics.add(counter, 0, 1);                    // one indivisible step
  }
}

Waiting for another thread is the other half. Atomics.wait() blocks the calling thread until another thread calls Atomics.notify() on the same index (or a timeout), which is acceptable inside a worker and wrong on the main thread, where it would freeze the event loop. Atomics.waitAsync() returns a promise instead and is safe on the main thread.

Guidelines that keep shared memory manageable:

  • Prefer messages and transfers; reach for SharedArrayBuffer only for large data that several threads must read, or for a tiny control block such as a stop flag or a counter, as in the proof-of-work example.

  • Share typed arrays of fixed layout. Objects, strings and Map cannot live in shared memory.

  • Use Atomics for every access to a location that another thread may write. Plain reads can be reordered or cached.

  • Never use Atomics.wait() on the main thread.

  • Without a lock, compound updates over several locations are still unsafe. worker_threads.locks (Stability 1, Experimental, added in v24.5.0) mirrors the browser Web Locks API for coordinating access to a named resource across threads; it works on Node.js 26 and 24 and does not exist on 22.

Resource limits, stopping workers, and failure

A worker shares the process with the main thread, so it needs fences. The resourceLimits option constrains the worker’s JavaScript engine: maxOldGenerationSizeMb, maxYoungGenerationSizeMb, codeRangeSizeMb and stackSizeMb (default 4). Reaching a limit terminates only the worker. The limits apply to the JS heap only: ArrayBuffer memory and other external memory are not counted, and a process-wide out-of-memory can still abort the whole process. The command-line options --max-old-space-size and --max-semi-space-size override the matching options.

A worker pool

The API documentation says it plainly: spawning a worker per task can cost more than the work saved, so use a pool. A pool owns a fixed number of workers, a queue of jobs and the bookkeeping that matches an answer to the caller that asked. The Bookshelf application needs one for cover images: for every uploaded cover it computes a content hash used as a cache key and for duplicate detection, a CPU-bound job that must not stall the catalogue API. The worker below stands in for real image work with a long hash chain.

The cover-hash worker (hash-worker.js)
import { parentPort } from 'node:worker_threads';
import { createHash } from 'node:crypto';

// One job = one cover image (an ArrayBuffer that was transferred to us).
parentPort.on('message', ({ id, bytes }) => {
  try {
    const data = new Uint8Array(bytes);
    let digest = createHash('sha256').update(data).digest();
    for (let i = 0; i < 150_000; i++) {                      // stand-in for real CPU work: perceptual hash, resize...
      digest = createHash('sha256').update(digest).update(data.subarray(0, 64)).digest();
    }
    parentPort.postMessage({ id, hash: digest.toString('hex') });
  } catch (error) {
    parentPort.postMessage({ id, error: { name: error.name, message: error.message } });
  }
});

The pool class has four responsibilities: spawn workers on demand up to a limit (the default availableParallelism() - 1 leaves a core for the event loop), queue jobs when everyone is busy, replace a worker that died, and wrap each job in an AsyncResource so that async context and stack traces survive the thread hop (the Node.js documentation shows this pattern for pools).

A small worker pool (pool.js)
import { Worker } from 'node:worker_threads';
import { availableParallelism } from 'node:os';
import { AsyncResource } from 'node:async_hooks';

export class WorkerPool {
  #file; #size; #idle = []; #all = new Set(); #queue = []; #jobs = new Map(); #nextId = 0; #closed = false;

  constructor(file, size = Math.max(1, availableParallelism() - 1)) {
    this.#file = file;
    this.#size = size;
  }

  /** Queue a job; resolves with the worker's answer. `transfer` lists buffers to move, not copy. */
  run(payload, transfer = []) {
    if (this.#closed) return Promise.reject(new Error('pool is closed'));
    return new Promise((resolve, reject) => {
      const id = this.#nextId++;
      const resource = new AsyncResource('WorkerPoolTask');  // keeps async stack traces / ALS context
      this.#queue.push({ id, payload, transfer, resolve: (v) => resource.runInAsyncScope(resolve, null, v), reject: (e) => resource.runInAsyncScope(reject, null, e) });
      this.#drain();
    });
  }

  #spawn() {
    const worker = new Worker(this.#file);
    worker.on('message', (msg) => this.#settle(worker, msg));
    worker.on('error', (err) => this.#crash(worker, err));         // uncaught error: the worker is already dead
    worker.on('exit', (code) => { if (this.#all.delete(worker)) this.#crash(worker, new Error(`worker exited with ${code}`), false); });
    this.#all.add(worker);
    return worker;
  }

  #drain() {
    while (this.#queue.length) {
      let worker = this.#idle.pop();
      if (!worker && this.#all.size < this.#size) worker = this.#spawn();
      if (!worker) return;                                          // everyone is busy; wait for a free worker
      const job = this.#queue.shift();
      this.#jobs.set(worker, job);
      worker.postMessage({ id: job.id, ...job.payload }, job.transfer);
    }
  }

  #settle(worker, msg) {
    const job = this.#jobs.get(worker);
    this.#jobs.delete(worker);
    this.#idle.push(worker);
    if (msg.error) job.reject(Object.assign(new Error(msg.error.message), { name: msg.error.name }));
    else job.resolve(msg);
    this.#drain();
  }

  #crash(worker, err, remove = true) {
    if (remove) this.#all.delete(worker);
    const job = this.#jobs.get(worker);
    this.#jobs.delete(worker);
    this.#idle = this.#idle.filter((w) => w !== worker);
    job?.reject(err);
    if (!this.#closed) this.#drain();                               // replacement is spawned on demand
  }

  async close() {
    this.#closed = true;
    await Promise.all([...this.#all].map((w) => w.terminate()));
  }
}

Proof of work in parallel

A proof-of-work puzzle asks for a number (a nonce) that, appended to a block of data and hashed with SHA-256, produces a digest that starts with a given number of zero characters. Nothing makes it faster except trying more values at once, so it is the textbook CPU-bound loop: on the main thread it would freeze every other request in a blockchain-style server. The program below splits the nonce space across four workers (worker i tries i, i plus 4, i plus 8, and so on), shares a two-slot Int32Array over a SharedArrayBuffer for coordination, and stops the others as soon as one finds an answer.

The shared state is the whole synchronisation design: slot 0 is a stop flag read with Atomics.load() every 16,384 attempts (cheap), and Atomics.compareExchange() guarantees that exactly one worker publishes a result even if two find valid nonces at the same moment.

A parallel miner with a shared stop flag (pow.js)
import { Worker, isMainThread, workerData, parentPort } from 'node:worker_threads';
import { createHash } from 'node:crypto';
import { availableParallelism } from 'node:os';

// Shared state: [0] = stop flag, [1] = winning nonce (low 31 bits are enough here)
const STOP = 0, NONCE = 1;

if (!isMainThread) {
  const { shared, block, difficulty, start, step } = workerData;
  const state = new Int32Array(shared);
  const prefix = '0'.repeat(difficulty);
  let tried = 0;
  for (let nonce = start; ; nonce += step) {
    if ((tried++ & 0x3fff) === 0 && Atomics.load(state, STOP) === 1) break;   // cheap periodic check
    const hash = createHash('sha256').update(`${block}:${nonce}`).digest('hex');
    if (hash.startsWith(prefix)) {
      if (Atomics.compareExchange(state, STOP, 0, 1) === 0) {                  // first finder wins
        Atomics.store(state, NONCE, nonce);
        parentPort.postMessage({ nonce, hash });
      }
      break;
    }
  }
  parentPort.postMessage({ tried });
} else {
  const block = 'bookshelf-block-1|prev=0000|data=alice->bob:5';
  const difficulty = 5;
  const threads = Math.min(4, availableParallelism());
  const shared = new SharedArrayBuffer(8);
  const state = new Int32Array(shared);
  const started = performance.now();
  const workers = Array.from({ length: threads }, (_, i) =>
    new Worker(new URL(import.meta.url), { workerData: { shared, block, difficulty, start: i, step: threads } }));
  let answer, total = 0;
  await Promise.all(workers.map((w) => new Promise((resolve, reject) => {
    w.on('message', (m) => { if (m.hash) answer = m; if (m.tried) total += m.tried; });
    w.once('error', reject);
    w.once('exit', resolve);
  })));
  const check = createHash('sha256').update(`${block}:${answer.nonce}`).digest('hex');
  console.log({ threads, nonce: answer.nonce, hash: answer.hash, verified: check === answer.hash, attempts: total, ms: Math.round(performance.now() - started) });
}

The browser side, including SharedWorker, Service Workers and MessageChannel between pages and workers, is covered in Web Workers. The messaging model is deliberately the same (structured clone, transfer lists), so knowledge of one carries over: postMessage(value, [buffer]) means the same in both.

Node.js 26.9 added an experimental global Worker that is "mostly browser-compatible", implemented on top of node:worker_threads: its threads get a DedicatedWorkerGlobalScope with self, name, location, navigator, postMessage(), close() and importScripts(), alongside the usual Node.js globals such as process. It exists to let code written for browsers (or a polyfill-free library) run in Node.js. Differences from the HTML Standard that the docs list include: no origin model (location.origin is 'null'), close() terminates immediately, and no SharedWorker.

The web-style Worker global (needs --experimental-web-worker, Node.js 26.9+)
const worker = new Worker(new URL('./web-worker-script.js', import.meta.url), { name: 'greeter' });
worker.addEventListener('message', (event) => {
  console.log(event.data);
  worker.terminate();
});
worker.postMessage('Hello');

Where the books are outdated

Neither book treats node:worker_threads as a first-class subject, and that is the main gap this page fills. Efficient Node.js (Samer Buna, O’Reilly, 2025) scales a server across cores with node:cluster and child processes, which are different tools with different costs (full processes, no shared memory); thread-based parallelism with transferables, SharedArrayBuffer and Atomics is the missing piece. Node.js Projects (Jonathan Wexler, O’Reilly, 2025) builds a hash-chain with a proof-of-work step, which is exactly a CPU-bound loop; read it with this page beside it to move that loop off the event loop with a worker pool. Where either book calls an API "experimental" or sends only plain data and JSON to another process, the current documentation is more capable: node:worker_threads is Stable and has been since v12.11.0, structured clone replaces JSON for messages between threads, and a pool of workers needs no process-per-request design. Also note that the permission model (where a worker needs --allow-worker) did not exist for most older tutorials.

Pitfalls

Table 10. Common mistakes and the safe alternative
Mistake Alternative

Using workers for I/O-bound work (database calls, HTTP)

Use the asynchronous APIs, which are more efficient than a worker can be.

Starting a worker for every request

Reuse a small pool; start-up costs milliseconds and several MiB.

Posting a function, a class instance or a request object

Post plain data; rebuild objects inside the worker.

Using counter[0]++ on shared memory

Atomics.add() or another atomic operation.

Calling Atomics.wait() on the main thread

Atomics.waitAsync(), or a message.

Transferring a Buffer from the pool

Copy into a fresh ArrayBuffer first, or use the pool’s own memory only inside one thread.

Forgetting 'error' and non-zero 'exit' handlers

Always handle both; a promise wrapper must reject on non-zero exit.

Starting workers from a preload script without a guard

Check isMainThread or set execArgv.

Assuming process.env writes are shared

They are a copy unless SHARE_ENV is passed.

Assuming a resource limit protects the whole process

It limits the worker’s JS heap only; keep process-level memory limits too.

Treating the Worker global as production API

It is Experimental (26.9) and flag-gated; use node:worker_threads.
