Debugging

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Node.js 26 (26.10.0, released 2026-09-21, the Current line that becomes LTS on 2026-10-28), with the differences of Node.js 24 "Krypton" (24.21.0, Active LTS) and Node.js 22 "Jod" (22.23.3, Maintenance) called out; versions and stability levels were checked against the official documentation on 2026-10-04, and every example below was run on all three lines unless the text says otherwise. Debugging in Node.js is built on one mechanism: the V8 inspector, a small server inside the process that speaks the Chrome DevTools Protocol (CDP) over a WebSocket. Chrome DevTools, VS Code, JetBrains IDEs and the command-line node inspect client are all just different front ends for that one protocol, so once you understand how to switch the inspector on, where it listens and who may talk to it, every tool works the same way. The node:inspector module and the node inspect command-line debugger are Stability 2 (Stable); the new non-interactive probe mode of node inspect is Stability 1 (Experimental); network inspection is Stability 1 (Experimental) and the node:inspector helpers that feed it are Stability 1.1 (Active development); --enable-source-maps is stable while the helper functions in node:module are still Stability 1 (Experimental). The --trace-* flags and NODE_DEBUG are long-standing command-line and environment features that carry no stability index. The running scenario is the Bookshelf application that grows across this section, described in Introduction & Architecture; this page is about stopping a program and looking inside it. Measuring where the time goes is the subject of Profiling & Performance, finding leaked memory is in Memory & Leaks, and post-mortem evidence from production is in Diagnostic Reports, Logging & Observability.

How the inspector works

When you start Node.js with --inspect, the process opens a TCP server (by default on 127.0.0.1:9229) and registers itself as a debug target. A client first makes a plain HTTP request to learn the target’s address, then upgrades to a WebSocket whose URL ends with a random UUID, and from then on exchanges JSON messages: commands such as Debugger.setBreakpointByUrl or Runtime.evaluate, and events such as Debugger.paused. Everything a debugger can do, from stepping to evaluating an expression in a paused frame, is one of those messages, which is why the protocol is also the foundation for the profilers described in Profiling & Performance. The UUID is not a password in the cryptographic sense, but a client must know host, port and UUID to connect, and by default Node.js prints the full URL on stderr and lists it at the /json/list endpoint of the same port.

node --inspect=127.0.0.1:0 hang.js &

What DevTools actually sends

It is worth seeing the protocol once, because it demystifies every front end and gives you a way to script a debugger. }

import { spawn } from 'node:child_process';

  stdio: ['ignore', 'inherit', 'pipe'],
});

// Read the WebSocket URL that the inspector prints on stderr.
const url = await new Promise((resolve) => {
  child.stderr.setEncoding('utf8');
  child.stderr.on('data', (text) => {
    const match = /ws:\/\/\S+/.exec(text);
    if (match) resolve(match[0]);
  });
});

const ws = new WebSocket(url);
let nextId = 0;
const pending = new Map();
const pauses = [];
ws.onmessage = ({ data }) => {
  const message = JSON.parse(data);
  if (message.id) pending.get(message.id)?.(message.result);
  else if (message.method === 'Debugger.paused') pauses.shift()?.(message.params);
};

  new Promise((resolve) => {
    const id = ++nextId;
    pending.set(id, resolve);
    ws.send(JSON.stringify({ id, method, params }));
  });
const nextPause = () => new Promise((resolve) => pauses.push(resolve));

await send('Runtime.runIfWaitingForDebugger');

console.log('paused at start:', paused.reason);

// Resume; the debugger statement pauses us again inside price().

Conditional breakpoints and logpoints are just expressions

The conditional breakpoint and the logpoint of the Sources panel are not special features of Node.js: the front end sets an ordinary breakpoint with a condition expression. The condition is evaluated in the paused frame; if it is falsy, execution continues. A logpoint is the same thing with a condition that logs and then evaluates to false, so the program never actually stops. The client below sets both on a small loop and prints what the conditional breakpoint saw.

  total += price;
}

The debugger statement

debugger; is a standard JavaScript statement, not a Node.js feature: it is a breakpoint written into the source. With a debugger attached (DevTools, VS Code or node inspect) execution pauses there; with none attached it does nothing, which is why the app.js target above printed 10 when run plainly and paused when run under the inspector. That is convenient for a bug that appears only after a long run: put the statement where you want to look, start the process with --inspect, attach when the process reaches it. The cost is that you must not forget to delete it; a linter rule such as no-debugger (see ESLint & Prettier) catches it before commit.

For a program that starts without any flag but should wait on a debugger; statement only when asked, combine it with inspector.open() and inspector.waitForDebugger() (shown earlier) behind an environment variable of your own.

Debug a single test file the way you debug any script: a file that uses node:test is an ordinary program, so node --inspect-brk test/app.test.js waits for a debugger and pauses before the first line; this was checked on Node.js 26. Source maps

Debuggers and stack traces show positions in the JavaScript that actually runs. When that JavaScript is generated (bundled, minified or transpiled from TypeScript), the positions mean nothing to you. A source map is a JSON file, referenced by a //# sourceMappingURL= comment at the end of the generated file, that maps positions in the output back to the original sources. Node.js supports the ECMA-426 source map format, and there are two separate consumers of it: the debugger front ends (DevTools and VS Code read the map themselves, so breakpoints and stepping work in your .ts files with no Node.js flag), and the runtime, which needs --enable-source-maps before it rewrites the stack traces of errors. The example bundles two tiny TypeScript files with esbuild (installed in a scratch project; the same idea applies to tsc --sourceMap) and throws from the first one.

  const digits = isbn.replaceAll('-', '');
  if (digits.length !== 13) {
    throw new RangeError(`ISBN must have 13 digits, got ${digits.length}`);
  }
  return Number(digits[12]);
}

The --trace-* flags

The --trace-* flags change what Node.js prints when something happens that normally leaves no trail: a warning with no origin, a hidden exit, a synchronous call on a hot path. They are for investigation, not for production defaults, and each is a one-line change you can try without touching the code.

--trace-warnings and --trace-deprecation

By default a process warning is one line and says nothing about where it was raised. --trace-warnings adds the stack trace for every warning (deprecations included) and --trace-deprecation only for deprecations. The program below triggers a real deprecation, DEP0005 (the Buffer() constructor, an application-level runtime deprecation since v10.0.0), and a custom warning.

Stack depth and other trace flags

--stack-trace-limit=<n> (or Error.stackTraceLimit in code) sets how many frames V8 keeps per error; the default is 10 and 0 disables collection. NODE_DEBUG and util.debuglog

Network inspection

Chrome DevTools has a Network panel, and Node.js can feed it. With --experimental-network-inspection (Stability 1, Experimental; added in v22.6.0 and v20.18.0) the outgoing HTTP requests of the process are announced to the inspector as CDP Network.* events, so a connected DevTools window lists requests, headers, timing and responses of your server’s calls to other services. The next example avoids the browser: it starts a target with --inspect-wait and the flag, subscribes to Network.enable over the WebSocket, and prints the events that a Network panel would draw. The target makes one fetch() to a local server.

The target
// net-target.js
import { createServer } from 'node:http';

const server = createServer((req, res) => {
  res.setHeader('content-type', 'application/json');
  res.end(JSON.stringify({ title: 'Dune' }));
}).listen(0, '127.0.0.1', async () => {
  const { port } = server.address();
  const res = await fetch(`http://127.0.0.1:${port}/books/1`);
  console.log(await res.json());
  server.close();
});

Source: Node.js API: --experimental-network-inspection, Node.js API: fetch()

A client that prints the Network events
// net-client.mjs
import { spawn } from 'node:child_process';

const child = spawn(
  process.execPath,
  ['--inspect-wait=127.0.0.1:0', '--experimental-network-inspection', 'net-target.js'],
  { stdio: ['ignore', 'inherit', 'pipe'] },
);
const url = await new Promise((resolve) => {
  child.stderr.setEncoding('utf8');
  child.stderr.on('data', (t) => {
    const m = /ws:\/\/\S+/.exec(t);
    if (m) resolve(m[0]);
  });
});

const ws = new WebSocket(url);
ws.onmessage = ({ data }) => {
  const m = JSON.parse(data);
  if (!m.method?.startsWith('Network.')) return;
  const p = m.params;
  const detail = p.request ? `${p.request.method} ${p.request.url.replace(/:\d+/, ':<port>')}`
    : p.response ? `HTTP ${p.response.status} ${p.response.mimeType}`
    : '';
  console.log(m.method, detail);
};
await new Promise((resolve) => (ws.onopen = resolve));
ws.send(JSON.stringify({ id: 1, method: 'Network.enable' }));
ws.send(JSON.stringify({ id: 2, method: 'Runtime.runIfWaitingForDebugger' }));
child.on('exit', () => ws.close());

Network.loadingFinished
{ title: 'Dune' }

Two observations from running it. Without --experimental-network-inspection the same client received no Network.* events at all, so the flag is required, and a request made with http.get() instead of fetch() produced the same three events, so both client APIs are covered. Workers, child processes and other targets

A worker thread has its own V8 isolate, so it needs its own inspector. Node.js 24.1.0 and 22.17.0 added --experimental-worker-inspection (Stability 1.1, Active development) so that DevTools can list and debug workers of a process started with --inspect; this is taken from the CLI reference and was not run. A Session created in a worker can reach the main thread with connectToMainThread(). Child processes are separate processes and so are separate targets: a flag put in NODE_OPTIONS reaches all of them, and a fixed port collides. With NODE_OPTIONS='--inspect=127.0.0.1:9333' a parent that spawned one child printed "Debugger listening" for the parent and, for the child, "Starting inspector on 127.0.0.1:9333 failed: address already in use" (observed on Node.js 26), so use --inspect-port=0 or give each process its own port. The patterns are described in Worker Threads and Child Processes.

Source: Node.js API: --experimental-worker-inspection, Node.js API: session.connectToMainThread()

Debugging remotely and safely

The inspector is a remote-code-execution endpoint by design: a client that can reach it can evaluate arbitrary JavaScript with the privileges of the process. The Node.js documentation is blunt about this, and the rules that follow are the ones in the Learn guide and the CLI reference.

Table 9. The threat model of an open inspector
Exposure What to know

Bound to a public address (--inspect=0.0.0.0)

Any client that can reach the port can connect and run code. The CLI reference calls --inspect=0.0.0.0 insecure unless the port is protected by a firewall. The default binding is 127.0.0.1.

Bound to 127.0.0.1 (the default)

Still open to every local process and every local user that can open the port; the guide says this is by design, so that local debuggers can attach conveniently.

A web page in a browser

The same-origin policy blocks the initial HTTP request that obtains the session id, and Node.js checks that the Host header is an IP address or exactly localhost to resist DNS rebinding. In a check on Node.js 26, a request with Host: debug.example.com to the IP address was answered with HTTP 400, while Host: localhost:<port> returned 200 (observed).

Switched on later by a signal

SIGUSR1 starts the inspector in a running process. Anyone who can signal the process can enable it, so use --disable-sigusr1 where that is not wanted.

Under the permission model

With --permission, using the inspector is denied unless --allow-inspector is passed. Observed: on Node.js 26 and 24, inspector.open() under --permission failed with "Access to this API has been restricted. Use --allow-inspector to manage permissions." and worked with the flag; on Node.js 22 the same failure occurred but the flag is rejected as a "bad option", so there is no way to allow it.

Source: Node.js Learn: Debugging Node.js (security implications), Node.js API: binding the inspector to a public IP and port is insecure, Node.js API: --allow-inspector

The guidance that follows from this is short. Never bind the inspector to a public interface, and never leave --inspect in a production start-up command, the NODE_OPTIONS of an image or a Kubernetes manifest. When you must debug something that is not on your machine, tunnel to the loopback address of the remote host instead of opening the port; the Learn guide recommends an SSH tunnel and gives an example for illustrative purposes. The command from the guide has this shape and was not run for this page, because the machine used here has no SSH server: ssh -L 9221:localhost:9229 user@remote.example.com, after which a local DevTools or VS Code attaches to localhost:9221, and the tunnel’s encryption and authentication stand in front of the inspector. Attach by IP address or by localhost, since hostnames are rejected by the Host check.

Containers are the common case where the process must listen on 0.0.0.0 inside the container, because the container’s loopback is not reachable from the host. Production is a different problem

The Learn page on live debugging says that using a live debugger in production is usually not an option: you have limited access to the machine and you cannot interrupt a process that handles business-critical work. Breakpoints stop the whole event loop, so a paused production server stops serving every request. In production, collect evidence without stopping anything: structured logs with correlation ids, a diagnostic report on failure, a CPU profile or heap snapshot taken on demand, and NODE_DEBUG or --trace-* flags on a single canary instance. Those techniques are the subject of Diagnostic Reports, Logging & Observability, Profiling & Performance and Production Deployment. Probe mode, as noted, only launches a new process, so it is for reproducing a problem, not for inspecting the live one.

Source: Node.js Learn: Live Debugging, Node.js Learn: Using Inspector

Common problems

Table 10. Symptoms and fixes
Symptom Likely cause and fix

"Starting inspector on 127.0.0.1:9229 failed: address already in use"

Another process (or a child that inherited --inspect through NODE_OPTIONS) owns the port. Use --inspect=127.0.0.1:0 or --inspect-port=0 and read the printed URL.

The debugger attaches but breakpoints never hit

The code ran before you attached (use --inspect-wait or --inspect-brk), or the breakpoint is in a generated file whose source map is missing (see Source maps; in VS Code check outFiles and resolveSourceMapLocations).

Breakpoints in a TypeScript file turn grey in VS Code

The map does not match the output. Rebuild with --sourcemap, and check that the sourceMappingURL comment points at a file that exists.

DevTools lists the process, but the connection fails when using a hostname

The Host header check allows only IP addresses and localhost. Use the IP address, or an SSH tunnel to localhost.

Stack traces point into a bundle

Run with --enable-source-maps (and set it in NODE_OPTIONS for services), or run the TypeScript sources directly so that no map is needed.

A server pauses and stops answering when you attach

Expected: a breakpoint stops the event loop. Use a logpoint or probe mode to observe without stopping, and do not attach to production.

node inspect hangs at "connecting to 127.0.0.1:9229 …​ failed to connect"

Nothing is listening on the port the client assumes. node inspect -p <pid> and node inspect host:port use the default port unless you pass --port; a target started with --inspect-port=0 has a random port, so use the address that it printed.

--test with --inspect is slow

The runner forces a concurrency of 1 when the inspector is on; debug a single test file instead, or set inspectPort when you use run().

Debugging starts with --inspect or --inspect-brk only

--inspect-wait (v22.2.0 and later) waits for the debugger without stopping on the first line, which is the better choice for short scripts, and --inspect-port plus SIGUSR1 attaches to a process that was not started in debug mode. Probe mode (v24.16.0 and v26.1.0) adds printf-style debugging with no source edits.

The chrome://inspect page is the way in, with the profiler and memory tools beside it

Still correct, but start the inspector on port 0 for automation, never on a public address, and know that the Host header check rejects hostnames. The security model (a debugger is remote code execution, tunnel instead of exposing) is in the official guide; the debugging passages of the books that were consulted do not discuss it.

The node --help listing of --trace-* flags

The set is stable, but the listing includes --trace-promises, which is absent from the CLI reference (observed), and omits flags that came later, such as --trace-env (v22.13.0 and v23.4.0) and --trace-require-module (v22.13.0 and v23.5.0). Node.js 22 also still lists a deprecated --trace-atomics-wait.

--enable-source-maps appears only as one line of the node --help listing

Transpiled and bundled code is the norm: use --enable-source-maps, or module.setSourceMapsSupport(); with native type stripping (stable since v24.12.0 and v25.2.0) a .ts file needs no map at all.

NODE_DEBUG is shown with core modules such as http

It still works the same way, but NODE_DEBUG=http now prints a warning that the log can contain secrets (observed), and fetch() is traced under fetch and undici, not http.

VS Code debugging is a single launch button

The debugger has auto attach, a JavaScript debug terminal, skipFiles, localRoot and remoteRoot for containers, and envFile; keep secrets out of launch.json.

Process restarts use external watchers such as nodemon

node --watch is stable; combine it with the VS Code attach configuration and "restart": true.

An external HTTP client (Postman) is used to exercise your own API

That covers requests into your server. For requests that your process makes, --experimental-network-inspection (v22.6.0 and later) shows fetch() and http client requests in the DevTools Network panel, with the caveat that it is Stability 1 (Experimental).
