Errors & Error Handling

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Node.js 26 (26.10.0, released 2026-09-21, the Current line that becomes LTS on 2026-10-28), with the differences of Node.js 24 "Krypton" (24.21.0, Active LTS) and Node.js 22 "Jod" (22.23.3, Maintenance) called out; versions and stability levels were checked against the official documentation on 2026-10-03, and every example below was run on all three lines unless the text says otherwise. It is the most detailed page of the section because error handling decides whether a Node.js service survives its first real incident: the runtime has several different error channels (exceptions, callbacks, rejected promises, 'error' events), a family of system errors that come from the operating system, a catalogue of several hundred stable ERR_* codes, and two process-wide safety nets whose correct use is widely misunderstood. The language-level mechanics of throw, try/catch and Error subclasses are covered in Exception Handling; this page owns what is specific to Node.js. The running scenario is the Bookshelf application that grows across this section, described in Introduction & Architecture.

The Node.js documentation lists five categories of error that an application meets: standard JavaScript errors, DOMException`s, system errors, assertion errors and user-specified errors. All errors raised by Node.js are instances of, or inherit from, the standard `Error class, so they are guaranteed to have at least the properties of that class. One rule from the same page drives most of the advice below: the error.message text may change in any release, while error.code only changes between major versions, so program against the code and never against the message.

Standard JavaScript errors

The language raises six native error classes. V8 throws them for faults inside the program, and Node.js reuses TypeError and RangeError as the class of its own argument-validation errors, which then also carry an ERR_* code. The Node.js documentation states that ReferenceError instances almost always indicate a bug in the code or its dependencies, that SyntaxError is only produced by code evaluation (eval, Function, require and the node:vm module; JSON.parse() throws one as well), and that a SyntaxError is unrecoverable in the context that created it.

Provoking each standard error and printing its name and message
// Standard JavaScript errors and what raises them
const attempts = {
  ReferenceError: () => missingVariable,
  TypeError: () => null.title,
  RangeError: () => new Array(-1),
  SyntaxError: () => JSON.parse('{ "title": '),
  URIError: () => decodeURIComponent('%'),
};

for (const [expected, run] of Object.entries(attempts)) {
  try {
    run();
  } catch (err) {
    console.log(`${expected.padEnd(14)} -> ${err.name}: ${err.message}`);
  }
}

EvalError is still a class, but modern engines no longer throw it themselves, so you will essentially never see one outside old tutorials. A DOMException is a different thing: it is the Web IDL class thrown by fetch(), AbortController and Web Streams. Its name identifies it (for example 'AbortError'), and unlike every other Node.js error its code is a legacy number (20 for ABORT_ERR). The Node.js documentation points out that Node.js-specific APIs that accept an AbortSignal, such as events.once(), throw a native Error named AbortError with the code 'ABORT_ERR' instead; checking err?.name === 'AbortError' recognises both. Cancellation is covered in Async Context & Cancellation.

Two facts from the "Exceptions vs. errors" part of the documentation are worth remembering. JavaScript can throw any value, but everything thrown by Node.js or the runtime is an Error instance. And some exceptions are unrecoverable at the JavaScript layer and always crash the process, for example a failed assert() in the C++ layer or an abort() call.

System errors and error.code

Custom errors

Application rules deserve their own error types. A good custom error is a small Error subclass with a stable name, a machine-readable code, optional structured fields, and a safe-to-expose flag so that the HTTP layer knows whether the message may be shown to a client. Pass cause through to the parent constructor instead of inventing your own field.

A custom error hierarchy for the Bookshelf API
// A custom error hierarchy for the Bookshelf API
export class AppError extends Error {
  constructor(message, { code = 'APP_ERROR', status = 500, expose = false, cause } = {}) {
    super(message, { cause });
    this.name = new.target.name;
    this.code = code;
    this.status = status;
    this.expose = expose;
    Error.captureStackTrace?.(this, new.target);
  }

  toJSON() {
    return { name: this.name, code: this.code, message: this.expose ? this.message : 'Internal error' };
  }
}

export class NotFoundError extends AppError {
  constructor(resource, id, options) {
    super(`${resource} ${id} was not found`, { code: 'NOT_FOUND', status: 404, expose: true, ...options });
    this.resource = resource;
    this.id = id;
  }
}

export class ValidationError extends AppError {
  constructor(problems) {
    super('The request is invalid', { code: 'VALIDATION', status: 400, expose: true });
    this.problems = problems;
  }
}

Stack traces, captureStackTrace and stackTraceLimit

A stack trace is captured when the error is created (new Error()), and V8 formats the text lazily: the first line, Name: message, is built the first time error.stack is read. The consequence, which the documentation hints at ("changing this property after the Error object is created may not change the first line of the stack trace"), is that renaming an error after something already read its stack leaves the old header in err.stack while String(err) shows the new name. Error.captureStackTrace(target[, constructorOpt]) creates a fresh .stack on any object and rebuilds the header from the current name and message. Its optional second argument hides every frame above and including that function, which is how a validation helper can make the trace start at its caller. Error.stackTraceLimit (default 10) caps the number of frames; it affects only traces captured after the change, and setting it to a non-number or a negative number captures no frames.

Custom errors in TypeScript

Node.js runs .ts files directly through type stripping (Stable since v24.12.0 and v25.2.0, enabled by default since v23.6 and v22.18), which is enough for error classes as long as the syntax is erasable: no enums, no parameter properties, no namespaces. A TypeScript error class with a narrowing catch (run with node file.ts)

    super(`Invalid book: ${problems.map((p) => p.field).join(', ')}`, options);

  return err instanceof Error && 'code' in err;

}

}

Operational errors versus programmer errors

The most useful classification for deciding what to do with an error splits them in two. Operational errors are failures of the environment that a correct program must expect: a missing file, a refused connection, a timeout, invalid user input. Programmer errors are bugs: reading a property of undefined, passing the wrong type to an API, a failed assertion. The reaction differs completely. Operational errors are handled where the program knows what to do (retry, fall back, return a 4xx, tell the user). A programmer error cannot be handled meaningfully, because the program is already in a state its author did not anticipate; the right response is to log it, fail the current unit of work if the damage is contained, and in the last resort crash and restart.

Classifying errors by code, name and an explicit marker
// Operational errors are handled; programmer errors are bugs
import { readFile } from 'node:fs/promises';

class ValidationError extends Error {
  name = 'ValidationError';
  operational = true;                 // our own marker for expected, recoverable failures
}

const OPERATIONAL_CODES = new Set([
  'ENOENT', 'EACCES', 'ECONNREFUSED', 'ECONNRESET', 'ETIMEDOUT', 'ENOTFOUND', 'EADDRINUSE', 'EPIPE',
]);

function isOperational(err) {
  if (err?.operational === true) return true;
  if (err?.name === 'AbortError') return true;
  return OPERATIONAL_CODES.has(err?.code);
}

for (const run of [
  () => readFile('/no/such/file'),                 // the world is not as expected
  () => { throw new ValidationError('title is required'); },
  () => { const book = null; return book.title; }, // a bug
]) {
  try {
    await run();
  } catch (err) {
    console.log(err.name.padEnd(16), isOperational(err) ? 'operational -> handle' : 'programmer  -> crash');
  }
}

The classifier is deliberately a whitelist: only codes you decided are expected count as operational, and everything else is presumed to be a bug. Rethrowing and forwarding

Handle only the errors you can do something about, and make sure everything else keeps travelling. In try/catch that means a narrow condition and a throw err at the end; when you add context, create a new error with the original as cause so no information is lost; and in callback code you forward the error to your own callback with return callback(err) instead of throwing from an asynchronous context where nobody can catch it. In a promise chain a .catch() that does not rethrow converts a failure into a success value, so it must be intentional.

Handle one case, add context to another, rethrow the rest
// Rethrowing: catch what you can handle, let everything else propagate
import { readFile } from 'node:fs/promises';

class ConfigError extends Error {
  name = 'ConfigError';
}

  let text;
  try {
    text = await readFile(path, 'utf8');

    if (err.code === 'ENOENT') return { port: 3000 };   // expected: use defaults
    throw err;                                          // unexpected: do not swallow
  }
  try {
    return JSON.parse(text);
  } catch (err) {
    // Add context, keep the original as cause, and keep the stack of the original
    throw new ConfigError(`Settings file ${path} is not valid JSON`, { cause: err });
  }
}

Every error path in a function should end in one of three outcomes: handled (a value or a response is produced), translated (a new error with cause is thrown) or propagated unchanged. An empty catch block is a fourth outcome that is always a mistake, because it makes a failure invisible. A finally block runs on every path, so it is the right place for cleanup, but a return or throw inside finally replaces the outcome of the whole statement.

Mapping errors at the HTTP boundary

The edge of the application is where internal errors become public answers. A single handler maps the typed errors to status codes and messages, and treats everything else as an internal error: log the detail on the server, return a generic message to the client, and never include stack traces, file paths or SQL in the response.

A node:http handler that maps error types to responses
// A node:http server that maps errors to responses and never leaks internals
import http from 'node:http';
import { once } from 'node:events';

class HttpError extends Error {
  constructor(status, message, options) {
    super(message, options);
    this.status = status;
    this.name = 'HttpError';
  }
}

const books = new Map([[1, { id: 1, title: 'Dune' }]]);

async function route(req) {
  const url = new URL(req.url, 'http://localhost');
  const match = /^\/books\/(\d+)$/.exec(url.pathname);
  if (!match) throw new HttpError(404, 'No such route');
  const book = books.get(Number(match[1]));
  if (!book) throw new HttpError(404, `Book ${match[1]} not found`);
  if (url.searchParams.has('boom')) null.title;           // a programmer error
  return book;
}

const server = http.createServer(async (req, res) => {
  try {
    const body = await route(req);
    res.writeHead(200, { 'content-type': 'application/json' }).end(JSON.stringify(body));
  } catch (err) {
    if (err instanceof HttpError) {
      res.writeHead(err.status, { 'content-type': 'application/json' }).end(JSON.stringify({ error: err.message }));
      return;
    }
    console.error('unexpected:', err.name);                 // log the details server-side
    res.writeHead(500, { 'content-type': 'application/json' }).end(JSON.stringify({ error: 'Internal error' }));
  }
});

  const res = await fetch(base + path);
  console.log(res.status, await res.text());
}

The last line of defence: uncaughtException and unhandledRejection

If an exception is thrown and nothing catches it, or a promise rejects and nothing handles it, the error reaches the process. What happens next is a policy decision with a well-documented answer: the process is in an undefined state, so it should report the failure and exit, and a supervisor should start a new one.

Registering an 'uncaughtException' listener replaces that default. The listener receives the error and an origin string, 'uncaughtException' or 'unhandledRejection'. The documentation is blunt about what the event is for: it is a crude last-resort mechanism, not an equivalent of "On Error Resume Next"; resuming normal operation after it is not safe, and the correct use is to perform synchronous cleanup of resources and then shut down. To restart reliably, use an external monitor in another process (a container orchestrator, systemd, a process manager), which also covers the failures that never reach the event, such as running out of memory or being killed. Exceptions thrown from inside the listener itself are not caught; the process exits with a non-zero code to prevent infinite recursion.

  writeSync(process.stderr.fd, `fatal (${origin}): ${err.message}\n`);
  // Only synchronous cleanup is safe here. Then leave with a failure code.
  process.exit(1);

A crash-only policy for services

Putting the rules together gives a small, boring policy that works for HTTP services and workers alike. On 'uncaughtException' or 'unhandledRejection': set a non-zero exit code, write one structured log line with synchronous I/O, stop accepting new work (server.close()), give in-flight requests a bounded grace period, and exit. A supervisor restarts the process. Exceptions that were caught and handled at a boundary, such as the HTTP mapping above, do not trigger it.

Crash-only handlers for the Bookshelf server
// A crash-only policy for the Bookshelf server: log synchronously, stop accepting work, exit non-zero
import http from 'node:http';
import { writeSync } from 'node:fs';

const server = http.createServer((req, res) => res.end('ok'));
server.listen(0, '127.0.0.1');

let shuttingDown = false;
function fatal(kind, err) {
  if (shuttingDown) return;
  shuttingDown = true;
  process.exitCode = 1;
  // 1. Report with synchronous I/O: async loggers may never flush
  writeSync(process.stderr.fd, JSON.stringify({ level: 'fatal', kind, name: err?.name, message: err?.message }) + '\n');
  // 2. Stop taking new connections and let in-flight requests finish
  server.close(() => process.exit());
  server.closeIdleConnections();
  // 3. Never hang: force the exit after a grace period (unref so it cannot keep the process alive)
  setTimeout(() => process.exit(), 5000).unref();
}

process.on('uncaughtException', (err) => fatal('uncaughtException', err));
process.on('unhandledRejection', (reason) => fatal('unhandledRejection', reason));

// Demonstration: a bug fires 100 ms after start-up
setTimeout(() => Promise.reject(new TypeError('cannot read properties of undefined')), 100);

assert.throws() and assert.rejects() check that the right error is thrown, optionally validating it against a class, a regular expression, a validation object whose properties are compared, or a function that returns true. assert.ifError(value) is the legacy adapter for error-first callbacks: it passes for null and undefined and throws for anything else.

Asserting on errors with throws, rejects and ifError
// assert.throws and assert.rejects validate the error, not only that something was thrown
import assert from 'node:assert/strict';
import { readFile } from 'node:fs/promises';

assert.throws(() => JSON.parse('{'), SyntaxError);
assert.throws(() => Buffer.alloc(-1), { code: 'ERR_OUT_OF_RANGE', name: 'RangeError' });
assert.throws(() => new URL('/x'), /Invalid URL/);

await assert.rejects(readFile('/no/such/file'), { code: 'ENOENT', syscall: 'open' });
await assert.rejects(Promise.reject(new TypeError('x')), (err) => {
  assert.equal(err.name, 'TypeError');
  return true;
});

// assert.throws fails if nothing is thrown
try {
  assert.throws(() => {}, Error);
} catch (err) {
  console.log(err.code, '|', err.message.split('\n')[0]);
}

// assert.ifError passes null/undefined and rethrows anything else
assert.ifError(null);
try {
  assert.ifError(new Error('callback failed'));
} catch (err) {
  console.log(err.code, '|', err.message.split('\n')[0]);
}
console.log('all assertions passed');

ERR_ASSERTION | Missing expected exception (Error).
ERR_ASSERTION | ifError got unwanted exception: callback failed
all assertions passed

The optional last argument is the failure message. It can be a string, an Error instance (which is then thrown instead of an AssertionError) or, since v26.0.0, a function (actual, expected) ⇒ string that is evaluated only on failure; extra arguments after a string message are treated as printf-style substitutions, and combining extra arguments with an Error or a function is rejected with ERR_AMBIGUOUS_ARGUMENT. assert.partialDeepStrictEqual() (Stable since v24.0.0 and v22.17.0) compares only the properties named in the expected value, which is convenient for large API responses. Since v25.0.0 the deep-equality family no longer considers two different promises equal and treats invalid dates as equal. assert.Assert (v24.6.0, v22.19.0) creates independent assertion instances with their own options such as a full diff.

Custom messages, partial matching and strict versus legacy comparison
// Custom messages: string, Error instance, or a function evaluated only on failure
import assert from 'node:assert/strict';
import legacy from 'node:assert';

const first = (err) => err.message.split('\n')[0];

try { assert.equal(1, 2, 'pages must match'); } catch (err) { console.log(first(err), err.generatedMessage); }
try { assert.equal(1, 2, new RangeError('thrown as is')); } catch (err) { console.log(err.name, err.message); }
try { assert.equal(1, 2, (actual, expected) => `wanted ${expected}, got ${actual}`); } catch (err) { console.log(first(err)); }

// Subset comparison
assert.partialDeepStrictEqual({ id: 1, title: 'Dune', tags: ['sf', 'classic'] }, { title: 'Dune', tags: ['sf'] });
console.log('partial match ok');

// Legacy mode compares with ==, strict mode with Object.is
legacy.equal('1', 1);
try { assert.equal('1', 1); } catch (err) { console.log('strict mode:', err.code); }
Output on Node.js 26
pages must match false
RangeError thrown as is
wanted 2, got 1
partial match ok
strict mode: ERR_ASSERTION

The message form that takes a function is new in Node.js 26: on 24 and 22 the same call does not fail, but the function is not called either, and the message is the function’s source text, which is observed behaviour and not an error. Code that has to run on all three lines should pass strings.

An assertion error is a programmer error by definition, so it is a way to state conditions that must hold inside the program, not a way to validate input from users. A client sending an out-of-range percentage must get a 400, not an AssertionError that ends up as a 500.

Assertions state invariants; validation reports operational errors
// Assertions are not input validation, and assertion errors are programmer errors
import assert from 'node:assert/strict';

function applyDiscount(price, percent) {
  assert(Number.isFinite(price) && price >= 0, 'price must be a non-negative number');
  assert(percent >= 0 && percent <= 100, `percent out of range: ${percent}`);
  return price * (1 - percent / 100);
}

console.log(applyDiscount(20, 25));
try {
  applyDiscount(20, 125);
} catch (err) {
  console.log(err instanceof assert.AssertionError, err.code, '|', err.message);
}
Output on Node.js 26 (identical on 24 and 22)
15
true ERR_ASSERTION | percent out of range: 125

Where the books are outdated

Two O’Reilly books were consulted as references for coverage: Efficient Node.js by Samer Buna (2025) and Node.js Projects by Jonathan Wexler (2025). Both are good introductions, but they were written against Node.js 22 and earlier baselines ("Node 20 or higher" in the first, Node 22.16 or later in the second), so several things on this page cannot appear in them.

  • Anything newer than Node.js 22 is missing: Error.isError() (Node.js 24 and later), the printf-style and function forms of assertion messages (v26.0.0), assert.Assert (v24.6.0), url.parse() warning at runtime (v24.0.0), and the newer ERR_* codes listed in the recent-changes table.

  • The chapter on errors in Efficient Node.js describes ENOTFOUND as an entity that was not found; it is a DNS lookup failure (getaddrinfo), and the missing file or directory case is ENOENT.

  • In Node.js Projects an error object returned by an LLM call is treated as if it were an answer; failures must be converted into typed errors at the boundary and propagated, never passed along as values.

The authoritative sources are the Node.js documentation pages cited on this page; the publisher pages are listed under References.

Matching on err.message
