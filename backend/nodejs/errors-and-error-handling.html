Errors & Error Handling

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Node.js 26 (26.10.0, released 2026-09-21, the Current line that becomes LTS on 2026-10-28), with the differences of Node.js 24 "Krypton" (24.21.0, Active LTS) and Node.js 22 "Jod" (22.23.3, Maintenance) called out; versions and stability levels were checked against the official documentation on 2026-10-03, and every example below was run on all three lines unless the text says otherwise. It is the most detailed page of the section because error handling decides whether a Node.js service survives its first real incident: the runtime has several different error channels (exceptions, callbacks, rejected promises, 'error' events), a family of system errors that come from the operating system, a catalogue of several hundred stable ERR_* codes, and two process-wide safety nets whose correct use is widely misunderstood. The language-level mechanics of throw, try/catch and Error subclasses are covered in Exception Handling; this page owns what is specific to Node.js. The running scenario is the Bookshelf application that grows across this section, described in Introduction & Architecture.

The Node.js documentation lists five categories of error that an application meets: standard JavaScript errors, DOMExceptions, system errors, assertion errors and user-specified errors. All errors raised by Node.js are instances of, or inherit from, the standard Error class, so they are guaranteed to have at least the properties of that class. One rule from the same page drives most of the advice below: the error.message text may change in any release, while error.code only changes between major versions, so program against the code and never against the message.

Standard JavaScript errors

The language raises six native error classes. V8 throws them for faults inside the program, and Node.js reuses TypeError and RangeError as the class of its own argument-validation errors, which then also carry an ERR_* code. The Node.js documentation states that ReferenceError instances almost always indicate a bug in the code or its dependencies, that SyntaxError is only produced by code evaluation (eval, Function, require and the node:vm module; JSON.parse() throws one as well), and that a SyntaxError is unrecoverable in the context that created it.

Provoking each standard error and printing its name and message
// Standard JavaScript errors and what raises them
const attempts = {
  ReferenceError: () => missingVariable,
  TypeError: () => null.title,
  RangeError: () => new Array(-1),
  SyntaxError: () => JSON.parse('{ "title": '),
  URIError: () => decodeURIComponent('%'),
};

for (const [expected, run] of Object.entries(attempts)) {
  try {
    run();
  } catch (err) {
    console.log(`${expected.padEnd(14)} -> ${err.name}: ${err.message}`);
  }
}
Output on Node.js 26 (identical on 24 and 22; the V8 message wording can differ between versions)
ReferenceError -> ReferenceError: missingVariable is not defined
TypeError      -> TypeError: Cannot read properties of null (reading 'title')
RangeError     -> RangeError: Invalid array length
SyntaxError    -> SyntaxError: Unexpected end of JSON input
URIError       -> URIError: URI malformed

Source: Node.js API: Errors

EvalError is still a class, but modern engines no longer throw it themselves, so you will essentially never see one outside old tutorials. A DOMException is a different thing: it is the Web IDL class thrown by fetch(), AbortController and Web Streams. Its name identifies it (for example 'AbortError'), and unlike every other Node.js error its code is a legacy number (20 for ABORT_ERR). The Node.js documentation points out that Node.js-specific APIs that accept an AbortSignal, such as events.once(), throw a native Error named AbortError with the code 'ABORT_ERR' instead; checking err?.name === 'AbortError' recognises both. Cancellation is covered in Async Context & Cancellation.

Two facts from the "Exceptions vs. errors" part of the documentation are worth remembering. JavaScript can throw any value, but everything thrown by Node.js or the runtime is an Error instance. And some exceptions are unrecoverable at the JavaScript layer and always crash the process, for example a failed assert() in the C++ layer or an abort() call.

How an error reaches you: four channels

The same failure is reported in a different way depending on the style of the API. This is the first thing to learn, because each channel needs a different handler, and a handler for one channel does not see errors from another.

Table 3. The four error channels
API style How the error arrives What you write

Synchronous (fs.readFileSync(), JSON.parse())

Thrown with throw

try/catch

Promise-returning (fs/promises, fetch())

await inside try/catch, or .catch()

Callback-taking (fs.readFile(path, cb))

Event-based (streams, sockets, servers, EventEmitter)

A handful of typically asynchronous methods still throw synchronously; the documentation says there is no comprehensive list and each method’s page has to be consulted. The examples below show all four channels and what happens when an 'error' event has no listener.

The four channels, plus an unhandled 'error' event
// The four ways Node.js reports an error
import { readFile as readFileCb } from 'node:fs';
import { readFile } from 'node:fs/promises';
import { readFileSync } from 'node:fs';
import { EventEmitter } from 'node:events';

const missing = new URL('./no-such-file.json', import.meta.url);

// 1. Synchronous API: throw
try {
  readFileSync(missing);
} catch (err) {
  console.log('throw     ', err.code);
}

// 2. Callback API: error first
readFileCb(missing, (err) => {
  console.log('callback  ', err?.code);
});

// 3. Promise API: rejection
try {
  await readFile(missing);
} catch (err) {
  console.log('promise   ', err.code);
}

// 4. EventEmitter: 'error' event
const emitter = new EventEmitter();
emitter.on('error', (err) => console.log('event     ', err.message));
emitter.emit('error', new Error('connection lost'));

// Without a listener the same emit throws
try {
  new EventEmitter().emit('error', new Error('nobody is listening'));
} catch (err) {
  console.log('no listener', err.message);
}
try {
  new EventEmitter().emit('error', 'a plain string');
} catch (err) {
  console.log('non-Error ', err.code, '|', err.context);
}
Output on Node.js 26
throw      ENOENT
callback   ENOENT
promise    ENOENT
event      connection lost
no listener nobody is listening
non-Error  ERR_UNHANDLED_ERROR | a plain string

Source: Node.js API: Errors (error propagation and interception), Node.js API: Events

The last two lines show the rule for 'error' events: if an emitter emits 'error' with no listener, the error is thrown (and, if nothing catches it, becomes an uncaught exception that crashes the process). If the emitted value is not an Error, Node.js wraps it in an error with the code ERR_UNHANDLED_ERROR and keeps the original value in the context property. Such errors cannot be caught with try/catch around the code that started the operation, because they are thrown after the calling code has already returned. This is why every socket, server, stream and child process you create needs an 'error' listener, and why the promise-based stream/promises helpers are preferred: they turn the event into a rejection. See Events & EventEmitter and Callbacks, Promises & async/await for the details of each style.

A stream pipeline: errors are forwarded to the awaiting caller
// Streams and pipelines: errors travel through the 'error' event or the promise
import { pipeline } from 'node:stream/promises';
import { Readable, Transform } from 'node:stream';

const failing = new Transform({
  transform(chunk, encoding, callback) {
    callback(new Error('bad row'));
  },
});

try {
  await pipeline(Readable.from(['a,b\n', 'c,d\n']), failing, async function (source) {
    for await (const chunk of source) console.log(String(chunk));
  });
} catch (err) {
  console.log('pipeline rejected:', err.message);
}

// A stream that ends without an error but too early
const early = new Readable({ read() {} });
setImmediate(() => early.destroy());
try {
  await pipeline(early, async function (source) { for await (const _ of source); });
} catch (err) {
  console.log(err.code);
}
Output on Node.js 26 (identical on 24 and 22)
pipeline rejected: bad row
ERR_STREAM_PREMATURE_CLOSE

Source: Node.js API: Stream, Node.js API: Errors

pipeline() destroys every stream in the chain when one fails and rejects with the first error. When a stream ends without an explicit error but before it should have, the rejection has the code ERR_STREAM_PREMATURE_CLOSE, which the second part of the example provokes.

System errors and error.code

System errors are generated when the runtime meets an operating-system constraint: opening a file that does not exist, binding to a port that is taken, writing to a closed socket. The documentation describes a SystemError class with code, errno, syscall, path, dest, address, port and info properties, and says that errno is a negative number that corresponds to a libuv error code. In practice, what you receive from fs, net, dns and the other modules is an ordinary Error instance carrying those properties (the example prints err.constructor.name, which is observed to be Error on all three lines), so instanceof Error is true and the properties are what you test.

Reading the anatomy of a file-system error
// System errors carry code, errno, syscall and path
import { readFile, mkdir, rmdir } from 'node:fs/promises';
import { getSystemErrorName, getSystemErrorMessage } from 'node:util';

try {
  await readFile('/definitely/not/here.txt', 'utf8');
} catch (err) {
  console.log(err instanceof Error, err.constructor.name);
  console.log({
    code: err.code,
    errno: err.errno,
    syscall: err.syscall,
    path: err.path,
    name: getSystemErrorName(err.errno),
    text: getSystemErrorMessage(err.errno),
  });
  console.log(err.message);
}

try {
  await readFile(new URL('.', import.meta.url));
} catch (err) {
  console.log(err.code, err.syscall); // EISDIR
}

try {
  await mkdir(new URL('.', import.meta.url));
} catch (err) {
  console.log(err.code, err.syscall); // EEXIST
}
try {
  await rmdir(new URL('.', import.meta.url));
} catch (err) {
  console.log(err.code, err.syscall); // ENOTEMPTY
}

The message of a system error always has the shape CODE: description, syscall 'path', which is convenient to read in a log but never something to parse. util.getSystemErrorName() turns a numeric errno into its name, util.getSystemErrorMessage() (Node.js 23.1 and 22.12 or later) returns the platform’s text for it, and util.getSystemErrorMap() returns every code the platform knows; the mapping is platform dependent.

The next example provokes the three network errors you see most often in a Bookshelf deployment: a second server on a taken port, a connection to a port nobody listens on, and a lookup of a host name that cannot resolve.

EADDRINUSE, ECONNREFUSED and ENOTFOUND
// Network system errors: EADDRINUSE, ECONNREFUSED, ENOTFOUND
import net from 'node:net';
import dns from 'node:dns/promises';

const first = net.createServer().listen(0, '127.0.0.1');
await new Promise((resolve) => first.once('listening', resolve));
const { port } = first.address();

// EADDRINUSE: a second server on the same address
const second = net.createServer();
second.on('error', (err) => {
  console.log(err.code, err.syscall, err.address, err.port === port);
  first.close();
});
second.listen(port, '127.0.0.1');
await new Promise((resolve) => first.once('close', resolve));

// ECONNREFUSED: nothing listens on the port any more
const socket = net.connect({ port, host: '127.0.0.1' });
await new Promise((resolve) => socket.once('error', (err) => {
  console.log(err.code, err.syscall, err.address, err.port === port);
  resolve();
}));

// ENOTFOUND: DNS failure (the .invalid TLD never resolves)
try {
  await dns.lookup('bookshelf.invalid');
} catch (err) {
  console.log(err.code, err.syscall, err.hostname);
}
Output on Node.js 26 (identical on 24 and 22)
EADDRINUSE listen 127.0.0.1 true
ECONNREFUSED connect 127.0.0.1 true
ENOTFOUND getaddrinfo bookshelf.invalid

Source: Node.js API: Errors (common system errors), Node.js API: Net, Node.js API: DNS

ENOTFOUND deserves a remark because it is easy to misread. It is not "entity not found" (the missing-file case is ENOENT); it means the DNS lookup failed, and its syscall is getaddrinfo. In the example the reserved .invalid top-level domain never resolves, so the result does not depend on the network, although a machine that is offline can report a different DNS code such as EAI_AGAIN for other names.

fetch() follows the web platform instead: a network failure rejects with a TypeError whose message is fetch failed and whose cause is the underlying error, so the system code is one level down. An HTTP error status such as 404 or 500 is not an error at all; the promise resolves and you check response.ok.

Network failures in fetch() are TypeErrors with the system error as cause
// fetch wraps network failures in a TypeError; the system error is the cause
import net from 'node:net';

// Find a port that is free right now
const probe = net.createServer().listen(0, '127.0.0.1');
await new Promise((resolve) => probe.once('listening', resolve));
const { port } = probe.address();
await new Promise((resolve) => probe.close(resolve));

try {
  await fetch(`http://127.0.0.1:${port}/books`, { signal: AbortSignal.timeout(2000) });
} catch (err) {
  console.log(err.name, '-', err.message);
  console.log(err.cause?.code, err.cause?.syscall);
}

// An aborted request rejects with a DOMException named AbortError
try {
  await fetch(`http://127.0.0.1:${port}/`, { signal: AbortSignal.abort() });
} catch (err) {
  console.log(err.name, err.constructor.name, err.code);
}
Output on Node.js 26 (identical on 24 and 22)
TypeError - fetch failed
ECONNREFUSED connect
AbortError DOMException 20

Source: Node.js API: Globals (fetch), Node.js API: Errors (DOMException)

The port is obtained by briefly opening and closing a server, because fetch() refuses a few well-known "bad ports" (port 9 for example) with a different error. Fetching, timeouts and retries are covered in depth on the Fetch & HTTP Clients page.

The ERR_* catalogue

Errors that Node.js itself raises (as opposed to the operating system) carry a stable string code that begins with ERR_. The catalogue in the Node.js 26 documentation has roughly 430 entries (counted on 2026-10-03), grouped by area: arguments (ERR_INVALID_ARG_TYPE), modules (ERR_MODULE_NOT_FOUND), streams (ERR_STREAM_PREMATURE_CLOSE), HTTP, crypto, the test runner, the permission model and so on. The single exception to the naming rule is ABORT_ERR, which is kept without the prefix for compatibility with the web platform’s AbortError. Custom errors

Application rules deserve their own error types. A good custom error is a small Error subclass with a stable name, a machine-readable code, optional structured fields, and a safe-to-expose flag so that the HTTP layer knows whether the message may be shown to a client. Pass cause through to the parent constructor instead of inventing your own field.

A custom error hierarchy for the Bookshelf API
// A custom error hierarchy for the Bookshelf API
export class AppError extends Error {
  constructor(message, { code = 'APP_ERROR', status = 500, expose = false, cause } = {}) {
    super(message, { cause });
    this.name = new.target.name;
    this.code = code;
    this.status = status;
    this.expose = expose;
    Error.captureStackTrace?.(this, new.target);
  }

  toJSON() {
    return { name: this.name, code: this.code, message: this.expose ? this.message : 'Internal error' };

}

    super(`${resource} ${id} was not found`, { code: 'NOT_FOUND', status: 404, expose: true, ...options });

    this.id = id;
  }
}

export class ValidationError extends AppError {
  constructor(problems) {
    super('The request is invalid', { code: 'VALIDATION', status: 400, expose: true });
    this.problems = problems;
  }
}

Stack traces, captureStackTrace and stackTraceLimit

A stack trace is captured when the error is created (new Error()), and V8 formats the text lazily: the first line, Name: message, is built the first time error.stack is read. The consequence, which the documentation hints at ("changing this property after the Error object is created may not change the first line of the stack trace"), is that renaming an error after something already read its stack leaves the old header in err.stack while String(err) shows the new name. Error.captureStackTrace(target[, constructorOpt]) creates a fresh .stack on any object and rebuilds the header from the current name and message. Its optional second argument hides every frame above and including that function, which is how a validation helper can make the trace start at its caller. Error.stackTraceLimit (default 10) caps the number of frames; it affects only traces captured after the change, and setting it to a non-number or a negative number captures no frames.

Custom errors in TypeScript

Node.js runs .ts files directly through type stripping (Stable since v24.12.0 and v25.2.0, enabled by default since v23.6 and v22.18), which is enough for error classes as long as the syntax is erasable: no enums, no parameter properties, no namespaces. A TypeScript error class with a narrowing catch (run with node file.ts)

  readonly problems: Problem[];
  constructor(problems: Problem[], options?: ErrorOptions) {
    super(`Invalid book: ${problems.map((p) => p.field).join(', ')}`, options);
    this.name = 'ValidationError';
    this.problems = problems;
  }
}

  return err instanceof Error && 'code' in err;
}

  if (!book.title) problems.push({ field: 'title', message: 'required' });
  if (!Number.isInteger(book.pages)) problems.push({ field: 'pages', message: 'must be an integer' });

Operational errors versus programmer errors

The most useful classification for deciding what to do with an error splits them in two. Operational errors are failures of the environment that a correct program must expect: a missing file, a refused connection, a timeout, invalid user input. Programmer errors are bugs: reading a property of undefined, passing the wrong type to an API, a failed assertion. The reaction differs completely. Operational errors are handled where the program knows what to do (retry, fall back, return a 4xx, tell the user). A programmer error cannot be handled meaningfully, because the program is already in a state its author did not anticipate; the right response is to log it, fail the current unit of work if the damage is contained, and in the last resort crash and restart.

Classifying errors by code, name and an explicit marker
// Operational errors are handled; programmer errors are bugs
import { readFile } from 'node:fs/promises';

class ValidationError extends Error {
  name = 'ValidationError';
  operational = true;                 // our own marker for expected, recoverable failures
}

const OPERATIONAL_CODES = new Set([
  'ENOENT', 'EACCES', 'ECONNREFUSED', 'ECONNRESET', 'ETIMEDOUT', 'ENOTFOUND', 'EADDRINUSE', 'EPIPE',
]);

function isOperational(err) {
  if (err?.operational === true) return true;
  if (err?.name === 'AbortError') return true;
  return OPERATIONAL_CODES.has(err?.code);
}

for (const run of [
  () => readFile('/no/such/file'),                 // the world is not as expected
  () => { throw new ValidationError('title is required'); },
  () => { const book = null; return book.title; }, // a bug
]) {
  try {
    await run();
  } catch (err) {
    console.log(err.name.padEnd(16), isOperational(err) ? 'operational -> handle' : 'programmer  -> crash');
  }
}

Rethrowing and forwarding

Handle only the errors you can do something about, and make sure everything else keeps travelling. In try/catch that means a narrow condition and a throw err at the end; when you add context, create a new error with the original as cause so no information is lost; and in callback code you forward the error to your own callback with return callback(err) instead of throwing from an asynchronous context where nobody can catch it. In a promise chain a .catch() that does not rethrow converts a failure into a success value, so it must be intentional.

Handle one case, add context to another, rethrow the rest
// Rethrowing: catch what you can handle, let everything else propagate
import { readFile } from 'node:fs/promises';

  name = 'ConfigError';

    return JSON.parse(text);
  } catch (err) {
    // Add context, keep the original as cause, and keep the stack of the original

Every error path in a function should end in one of three outcomes: handled (a value or a response is produced), translated (a new error with cause is thrown) or propagated unchanged. An empty catch block is a fourth outcome that is always a mistake, because it makes a failure invisible. A finally block runs on every path, so it is the right place for cleanup, but a return or throw inside finally replaces the outcome of the whole statement.

Mapping errors at the HTTP boundary

The edge of the application is where internal errors become public answers. A single handler maps the typed errors to status codes and messages, and treats everything else as an internal error: log the detail on the server, return a generic message to the client, and never include stack traces, file paths or SQL in the response.

A node:http handler that maps error types to responses
// A node:http server that maps errors to responses and never leaks internals
import http from 'node:http';
import { once } from 'node:events';

class HttpError extends Error {
  constructor(status, message, options) {
    super(message, options);
    this.status = status;
    this.name = 'HttpError';
  }
}

const books = new Map([[1, { id: 1, title: 'Dune' }]]);

async function route(req) {
  const url = new URL(req.url, 'http://localhost');
  const match = /^\/books\/(\d+)$/.exec(url.pathname);
  if (!match) throw new HttpError(404, 'No such route');
  const book = books.get(Number(match[1]));
  if (!book) throw new HttpError(404, `Book ${match[1]} not found`);
  if (url.searchParams.has('boom')) null.title;           // a programmer error
  return book;
}

const server = http.createServer(async (req, res) => {
  try {
    const body = await route(req);
    res.writeHead(200, { 'content-type': 'application/json' }).end(JSON.stringify(body));
  } catch (err) {
    if (err instanceof HttpError) {
      res.writeHead(err.status, { 'content-type': 'application/json' }).end(JSON.stringify({ error: err.message }));
      return;
    }
    console.error('unexpected:', err.name);                 // log the details server-side
    res.writeHead(500, { 'content-type': 'application/json' }).end(JSON.stringify({ error: 'Internal error' }));
  }
});

await once(server, 'listening');

for (const path of ['/books/1', '/books/9', '/nope', '/books/1?boom=1']) {
  const res = await fetch(base + path);
  console.log(res.status, await res.text());
}

Registering an 'uncaughtException' listener replaces that default. The listener receives the error and an origin string, 'uncaughtException' or 'unhandledRejection'. The documentation is blunt about what the event is for: it is a crude last-resort mechanism, not an equivalent of "On Error Resume Next"; resuming normal operation after it is not safe, and the correct use is to perform synchronous cleanup of resources and then shut down. To restart reliably, use an external monitor in another process (a container orchestrator, systemd, a process manager), which also covers the failures that never reach the event, such as running out of memory or being killed. Exceptions thrown from inside the listener itself are not caught; the process exits with a non-zero code to prevent infinite recursion.

A handler that reports synchronously and exits non-zero
// A handler turns the crash into your own policy, but the process state is still unsafe
import { writeSync } from 'node:fs';

process.on('uncaughtException', (err, origin) => {
  writeSync(process.stderr.fd, `fatal (${origin}): ${err.message}\n`);
  // Only synchronous cleanup is safe here. Then leave with a failure code.
  process.exit(1);
});

setTimeout(() => { throw new Error('boom in a timer'); }, 10);

unhandledRejection

A promise is unhandled when it rejects and no handler is attached within a turn of the event loop. Since v15.0.0 the default --unhandled-rejections mode is throw: Node.js first emits 'unhandledRejection'; if there is no listener for it, the rejection is raised as an uncaught exception, which means the process crashes with exit code 1 like any other uncaught exception. Before v15 it was only a warning.

The same rejection, with and without an unhandledRejection hook
// The same rejection under each --unhandled-rejections mode
const hooked = process.argv.includes('--hook');
if (hooked) {
  process.on('unhandledRejection', (reason, promise) => {
    console.log('hook:', reason.message, promise instanceof Promise);
  });
}
Promise.reject(new Error('lost'));
setTimeout(() => console.log('timer ran'), 50);

Whatever the mode, a rejection that happens during the static loading phase of the entry point of an ES module is always raised as an uncaught exception. Prefer the default throw mode in services: a rejected promise nobody awaited is a bug, and failing fast makes it visible.

Rejections can also be handled late. When a handler is attached after the 'unhandledRejection' event, Node.js emits 'rejectionHandled'. The set of unhandled rejections therefore grows and shrinks over time, and the documentation suggests tracking it in a Map and logging it periodically or at exit.

process.on('rejectionHandled', (promise) => pending.delete(promise));

await new Promise((resolve) => setTimeout(resolve, 20));
console.log('unhandled after late catch:', pending.size);

A crash-only policy for services

Putting the rules together gives a small, boring policy that works for HTTP services and workers alike. On 'uncaughtException' or 'unhandledRejection': set a non-zero exit code, write one structured log line with synchronous I/O, stop accepting new work (server.close()), give in-flight requests a bounded grace period, and exit. A supervisor restarts the process. Exceptions that were caught and handled at a boundary, such as the HTTP mapping above, do not trigger it.

Crash-only handlers for the Bookshelf server
// A crash-only policy for the Bookshelf server: log synchronously, stop accepting work, exit non-zero
import http from 'node:http';
import { writeSync } from 'node:fs';

const server = http.createServer((req, res) => res.end('ok'));
server.listen(0, '127.0.0.1');

let shuttingDown = false;
function fatal(kind, err) {
  if (shuttingDown) return;
  shuttingDown = true;
  process.exitCode = 1;
  // 1. Report with synchronous I/O: async loggers may never flush
  writeSync(process.stderr.fd, JSON.stringify({ level: 'fatal', kind, name: err?.name, message: err?.message }) + '\n');
  // 2. Stop taking new connections and let in-flight requests finish
  server.close(() => process.exit());
  server.closeIdleConnections();
  // 3. Never hang: force the exit after a grace period (unref so it cannot keep the process alive)
  setTimeout(() => process.exit(), 5000).unref();
}

process.on('uncaughtException', (err) => fatal('uncaughtException', err));
process.on('unhandledRejection', (reason) => fatal('unhandledRejection', reason));

// Demonstration: a bug fires 100 ms after start-up
setTimeout(() => Promise.reject(new TypeError('cannot read properties of undefined')), 100);
Output on Node.js 26 (the process exits with code 1)
{"level":"fatal","kind":"unhandledRejection","name":"TypeError","message":"cannot read properties of undefined"}

Source: Node.js API: Process (events uncaughtException and unhandledRejection), Node.js API: HTTP (server.close())

The unref() on the force-exit timer matters: without it the timer itself would keep a process alive that could otherwise end. The same shutdown sequence on SIGTERM is the subject of Process, Signals & Exit Codes, container restart policies are in Production Deployment, and the NestJS equivalent is in Lifecycle Events & Shutdown.

The node:domain module was an older attempt at this problem; its page carries Stability 0 (Deprecated) and describes the module as pending deprecation, the errors documentation mentions it only as an escape hatch for unhandled 'error' events, and it should not be used in new code. AsyncLocalStorage is the supported way to carry a request identifier into a fatal log line, see Async Context & Cancellation.

Warnings and deprecations

Not every problem is an error. Node.js emits process warnings (deprecations, experimental features, suspicious usage) through the 'warning' event and prints them to standard error. --trace-warnings adds the stack of the code that produced the warning, --trace-deprecation does so for deprecations only, --no-deprecation silences them, and --throw-deprecation turns a deprecation into a thrown error, which is a good setting for a CI job that should fail on use of deprecated APIs.

Assertion errors

The node:assert module (2 Stable) verifies invariants. A failing assertion throws an AssertionError, a subclass of Error whose code is always 'ERR_ASSERTION' and whose actual, expected, operator and generatedMessage properties describe the failure. Import node:assert/strict (the strict assertion mode): its equal, deepEqual and notEqual behave like the strict variants, and failure messages for objects show a diff. The legacy mode (plain node:assert) compares with loose equality, which hides bugs.

Anatomy of an AssertionError with a strict diff

} catch (err) {
  console.log(err.name, err.code, err.operator, err.generatedMessage);
  console.log(err.actual, err.expected);
  console.log(err.message);
}

// Assertions are not input validation, and assertion errors are programmer errors

  assert(percent >= 0 && percent <= 100, `percent out of range: ${percent}`);
  return price * (1 - percent / 100);
}

console.log(applyDiscount(20, 25));

} catch (err) {

Where the books are outdated

Two O’Reilly books were consulted as references for coverage: Efficient Node.js by Samer Buna (2025) and Node.js Projects by Jonathan Wexler (2025). Both are good introductions, but they were written against Node.js 22 and earlier baselines ("Node 20 or higher" in the first, Node 22.16 or later in the second), so several things on this page cannot appear in them.

  • Anything newer than Node.js 22 is missing: Error.isError() (Node.js 24 and later), the printf-style and function forms of assertion messages (v26.0.0), assert.Assert (v24.6.0), url.parse() warning at runtime (v24.0.0), and the newer ERR_* codes listed in the recent-changes table.

  • The chapter on errors in Efficient Node.js describes ENOTFOUND as an entity that was not found; it is a DNS lookup failure (getaddrinfo), and the missing file or directory case is ENOENT.

  • In Node.js Projects an error object returned by an LLM call is treated as if it were an answer; failures must be converted into typed errors at the boundary and propagated, never passed along as values.
