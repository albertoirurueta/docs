Upgrading & What’s Changed

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Node.js 26 (26.10.0, released 2026-09-21, the Current line that becomes LTS on 2026-10-28), with the differences of Node.js 24 "Krypton" (24.21.0, Active LTS until 2026-10-20, then Maintenance) and Node.js 22 "Jod" (22.23.3, Maintenance) called out; versions, dates and stability levels were checked against the official documentation on 2026-10-04, and every example below was run on Node.js 26, 24 and 22 (the outputs say which line printed what; the codemod commands were run once, on 26, because they only rewrite source files). It is the page to open when a project written for an older tutorial, or for the two books named in the bibliography, has to run on a current line: it explains how to plan an upgrade, how to make Node.js tell you what will break, which deprecations are documentation-only and which already print warnings or throw, what each major from 22 to 26 changed, and where the reference books (Samer Buna, Efficient Node.js, and Jonathan Wexler, Node.js Projects, both O’Reilly, 2025) no longer match the platform. Two facts shape every upgrade plan. First, from Node.js 27 the project moves to one major release per year, every line becomes LTS, and an alpha channel opens in October for early testing (the announcement is Evolving the Node.js Release Schedule); the "even numbers are production" rule ends with Node.js 26. Second, npm 12 exists (npm latest was 12.2.0 on 2026-10-03) but no Node.js line bundles it: Node.js 26.10.0 ships npm 11.19.1, so the npm version is an upgrade you control separately, covered in npm & Package Management.

Upgrading across majors

A Node.js major is the only release type that is allowed to break documented behaviour; minor and patch releases of a line keep the stability index promises (see the stability index in Globals & Web Platform APIs). Breaking changes are announced in three places, and the upgrade workflow below uses all of them.

The workflow that keeps surprises small is the same for a service and for a library:

  1. Move one LTS to the next LTS at a time (22 to 24, then 24 to 26) while the service still has tests, and read the release post of every major in between, including the odd one that was skipped: Node.js 23 and 25 ended their lives as Current lines, but their SEMVER-MAJOR changes are part of the jump from 22 to 24 and from 24 to 26.

  2. Declare the supported range in package.json engines and run the test suite on every line you promise to support, locally with a version manager and in CI with a matrix; add the next Current line (or, from 27, the alpha channel) as an allowed-to-fail job so a breaking change shows up months before it reaches LTS.

  3. Make deprecations visible and fatal in the test run (the next section), upgrade dependencies that print them, and run codemods for the rest.

  4. Rebuild native add-ons: an add-on compiled against V8 or OpenSSL internals needs a rebuild for each major, while Node-API add-ons keep the same ABI across majors (see Native Add-ons, WebAssembly & FFI).

  5. Update the base image, the .nvmrc or .node-version file, and the engines field last, once the suite is green, and check the new line’s bundled npm (npm 10.9.9 on 22, 11.19.x on 24 and 26) against the lockfile version your team expects.

The matrix part of that workflow is a plain loop when a version manager is installed. This script runs a project’s strict test script on each line and reports the exit code; the project is a tiny Bookshelf check with one test that calls the legacy url.parse().

A local line-by-line test matrix with nvm
#!/usr/bin/env bash
source ~/.nvm/nvm.sh
for v in 22 24 26; do
  nvm use "$v" >/dev/null
  npm run --silent test:strict >/dev/null 2>&1
  status=$?
  echo "$(node -v): npm run test:strict exits with $status"
done

Making Node.js show what will break

Node.js has four kinds of deprecation, and they differ in what you see:

Table 3. The four deprecation types

Documentation-only

Appears only in the API docs and generates nothing at run time.

Application (non-node_modules code only)

Userland Migrations and codemods

Node.js maintains official codemods for "userland" code, the code outside the node executable. They are published under the @nodejs scope of the Codemod registry, are reviewed or written by Node.js members, and cover the end-of-life deprecations and breaking changes that have a mechanical fix. The Learn page recommends running them on a separate branch, reviewing the diff, running the tests, and formatting or linting afterwards. Migration guides list per-major codemods; for example, the guides name @nodejs/import-assertions-to-attributes for v20 to v22, and @nodejs/crypto-rsa-pss-update, @nodejs/dirent-path-to-parent-path, @nodejs/fs-access-mode-constants, @nodejs/fs-truncate-fd-deprecation, @nodejs/http2-priority-signaling, @nodejs/process-assert-to-node-assert and @nodejs/tls-create-secure-pair-to-tls-socket for v22 to v24. Worked replacements

Four changes cause most upgrade failures in real projects: customization hooks, import syntax, TypeScript syntax and shell-based child processes.

module.register() becomes module.registerHooks()

module.register() registered asynchronous hooks that ran in a separate thread; it is Deprecated (Stability 0), became documentation-only deprecated in v25.9.0 and warns at run time since v26.0.0. module.registerHooks() is synchronous, runs in the same thread, works for every module type, and is Stability 1.2 (Release candidate) since v25.4.0 and v24.13.1; it was added in v23.5.0 and v22.15.0.

The old and the new registration
// hooks-old.mjs
import { register } from 'node:module';
register('./loader-hooks.mjs', import.meta.url);
console.log('registered with module.register()');

// hooks-new.mjs
import { registerHooks } from 'node:module';

registerHooks({
  resolve(specifier, context, nextResolve) {
    return nextResolve(specifier, context);
  },
});
console.log('registered with module.registerHooks()');
Result: only Node.js 26.10.0 warns about the old form
registered with module.register()
(node:97226) [DEP0205] DeprecationWarning: `module.register()` is deprecated. Use `module.registerHooks()` instead.
registered with module.registerHooks()

Source: Node.js API: DEP0205; Node.js API: module.registerHooks()

The warning appeared only on 26; both forms ran silently on 24.21.0 and 22.23.3. The details of writing hooks are in ESM & CommonJS Interoperability.

Import assertions become import attributes

The assert { type: 'json' } form was standardised as with { type: 'json' }; Node.js dropped support for assertions in 22.0.0 (it had accepted attributes since v21.0.0, v20.10.0 and v18.20.0). Every line from 22 to 26 reports a SyntaxError for the old keyword, and the codemod shown above does the rewrite.

// with.mjs: prints "bookshelf" on 22, 24 and 26

Enums and other non-erasable TypeScript syntax

Type stripping runs .ts files directly by erasing types; it was added in v22.6.0, is on by default since v23.6.0 and v22.18.0, prints no experimental warning since v24.3.0 and v22.18.0, and is Stable since v25.2.0 and v24.12.0. The flag that used to transform enums, namespaces and parameter properties, --experimental-transform-types, was removed in v26.0.0. On 26 there is no flag to fall back on, so the code must use erasable syntax. Run on each line with the default settings, an enum file fails with ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX ("TypeScript enum is not supported in strip-only mode"), and with --experimental-transform-types it ran on 22.23.3 and 24.21.0 (with an ExperimentalWarning) but is "bad option" on 26.10.0.

An enum and its erasable equivalent
// ts.ts: fails in strip-only mode on 22, 24 and 26
enum Color { Red, Green }
console.log(Color.Green);

// ts-erasable.ts: prints 1 on 22.23.3, 24.21.0 and 26.10.0
const Color = { Red: 0, Green: 1 } as const;
type Color = (typeof Color)[keyof typeof Color];
const c: Color = Color.Green;
console.log(c);

Source: Node.js API: Type stripping

More on what strip-only mode accepts, and the tsconfig options that enforce it, is in TypeScript in Node.js.

An args array with a shell

Passing an arguments array together with shell: true does not escape the arguments; they are only joined with spaces, which is a shell-injection hazard (DEP0190). It prints a runtime warning from v24.0.0. The safe form is to keep the array and drop the shell.

The deprecated and the safe call
import { execFileSync } from 'node:child_process';

// Deprecated since 24.0.0 (DEP0190): an args array together with shell: true
console.log(execFileSync('echo', ['hello', 'world'], { shell: true, encoding: 'utf8' }).trim());

// Replacement: no shell, arguments stay separate array items
console.log(execFileSync('echo', ['hello', 'world'], { encoding: 'utf8' }).trim());

Both lines printed hello world on all three lines, and [DEP0190] DeprecationWarning: Passing args to a child process with shell option true can lead to security vulnerabilities, as the arguments are not escaped, only concatenated. appeared only on 24.21.0 and 26.10.0. Source: Node.js API: DEP0190

On Windows, .bat and .cmd files cannot be launched with execFile() because they need a terminal; the child-process documentation lists exec(), or spawning cmd.exe explicitly, as the ways to run them, and marks spawn() with the shell option as not recommended because of DEP0190. See Child Processes for the argument-array rules.

Insecure practices that the projects should not copy

Some sample projects in Node.js Projects (Jonathan Wexler) are teaching code, not production code, and a reader who copies them inherits their weaknesses. The safe form for each:

Table 19. Insecure practices and the safe form
Area Weakness in the sample projects Safe form

Stored secrets

A password manager that keeps the managed passwords readable.

Derive a key with scrypt or Argon2id and encrypt each secret with AES-256-GCM, storing the IV and auth tag with the ciphertext (see Crypto, Passwords & Secrets).

Password hashing

A low-iteration, synchronous PBKDF2 whose hashes are compared with ===.

Use at least 210,000 iterations for PBKDF2-HMAC-SHA512 (OWASP), or better Argon2id or scrypt, the asynchronous API and crypto.timingSafeEqual().

Configuration

Hard-coded secrets and JWT secrets that fall back to a fixed string.

Fail fast at start-up when a secret is missing, and read it from process.env through --env-file.

Tokens

JWTs issued without an expiry and verified without pinned algorithms; session cookies without secure, httpOnly and sameSite.

Set expiresIn, pass algorithms when verifying, and set all three cookie attributes (see Authentication & Sessions).

Request protection

No CSRF protection, no rate limiting, and an email address placed in a verification URL.

Add CSRF defences and rate limits, and verify email with a random single-use token.

Scraping and templates

A scraper that spoofs its user agent and ignores robots.txt; a vulnerable version of the ejs template engine (CVE-2022-29078).

Respect robots.txt and site terms, identify your client, and keep template engines up to date (see Email, Feeds & Web Scraping).

Cloud database access

A MongoDB Atlas network access list open to every address.

Restrict access to the addresses that need it, and use credentials from the environment.

LLM prompts

User input concatenated into a single prompt string, and the model’s reply used as if it were trusted data.

Prompts are injectable: keep instructions in the system role and user text in the user role, treat model output as untrusted input, and request structured output that you validate before use (see Integrating LLM APIs).

Errors in the books worth knowing

Typos and slips are normal in technical books, and the page that covers each concept already shows the right form; the ones below are collected so that a reader following either book can check them in one place. The correct form is given, not the passage.

Table 20. Corrections for Efficient Node.js (Samer Buna)
Topic Correct form

Promise helper module

The module is node:stream/promises (singular stream).

Awaiting several promises

await [p1, p2] does not wait for both; use Promise.all(), Promise.allSettled() or another combinator.

Per-request child processes

A child forked per request must exit, or each request leaks a process; a request or response object cannot be sent to a worker (it is not serialisable).

Client IP hashing

An address-hashing sketch for sticky balancing must handle IPv6 as well as IPv4.

ES modules

Use export and export default in ES modules; exports and module.exports are CommonJS.

NODE_PATH

The separator is : on Unix and ; on Windows, not a comma, and the variable applies to CommonJS only.

assert.doesNotMatch()

It passes when the string does not match the pattern and throws when it does.

ENOTFOUND

A DNS lookup failure, not "entity not found".

Pausing a stream

Removing 'data' listeners does not pause a stream; call pause() or use pipeline().

Backpressure

Large generators must respect backpressure by honouring the result of write() and waiting for 'drain'.

Encryption

aes-256-ctr has no integrity protection; use aes-256-gcm and check the authentication tag.

Promise chains

A ; ends the statement, so a .finally() on the next line after then(…​); is a SyntaxError; chain .finally() without the semicolon.

fs.readFile() size limit

readFile() rejects files over 2 GiB with ERR_FS_FILE_TOO_LARGE; this is a fixed internal I/O limit that no option or heap flag raises, so stream large files with fs.createReadStream().

Orders test fixtures

The orders in the testing example have no ids, so the tests pass by accident; give every fixture a unique id so a lookup, update or delete can match only the intended record.
