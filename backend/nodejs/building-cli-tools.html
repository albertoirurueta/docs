Building CLI Tools

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Node.js 26 (26.10.0, released 2026-09-21, the Current line that becomes LTS on 2026-10-28), with the differences of Node.js 24 "Krypton" (24.21.0, Active LTS) and Node.js 22 "Jod" (22.23.3, Maintenance) called out; versions and stability levels were checked against the official documentation on 2026-10-04, and every example below was run on Node.js 26, 24 and 22 unless the text says otherwise. A command-line tool is the smallest useful Node.js program that still has to behave like a citizen of the shell: it takes its instructions from arguments, standard input and the environment, writes results to standard output and complaints to standard error, tells its caller how it went through an exit status, and stops cleanly when it is interrupted. Node.js ships the pieces for all of that, so a tool such as the Bookshelf catalogue manager built here needs no runtime dependency: util.parseArgs() parses flags, util.styleText() colours text, node:readline/promises asks questions and reads lines, and the process object carries the exit code and the signals. This page assembles those pieces into one complete bookshelf command and then ships it, first through npm and then as a single executable file. The individual APIs are documented in depth elsewhere in this section: see The util Module, Console, readline & Terminal I/O and Process, Signals & Exit Codes; the flags of the node binary itself are the subject of Running Scripts, the CLI & the REPL. What a CLI should look like to an automated caller, such as an AI agent, is covered in CLI for Agents, and its Node.js page Node.js CLI Frameworks compares commander, yargs, oclif and Ink.

A command is a package with a bin entry

An executable command in the npm world is a file that a package names in its bin field. When someone installs the package, npm links that file into a bin directory that is on the PATH (globally) or into node_modules/.bin (locally, where npx and npm run find it). The file must start with a shebang, the line #!/usr/bin/env node: the operating system reads it, looks node up on the PATH (so a version manager that swaps the active Node.js keeps working) and runs the file with it. Node.js itself skips a leading shebang line, so the same file also runs as node bin/bookshelf.js. The thin-entry layout below is the one used by most real tools: the file under bin/ only wires the process to the program (arguments, signals, exit code) and everything testable lives in modules under src/.

package.json of the Bookshelf CLI
{
  "name": "bookshelf-cli",
  "version": "0.1.0",
  "description": "Manage the Bookshelf catalogue from a terminal",
  "type": "module",
  "bin": {
    "bookshelf": "./bin/bookshelf.js"
  },
  "files": [
    "bin",
    "src"
  ],
  "engines": {
    "node": ">=22"
  },
  "license": "MIT"
}

"type": "module" makes the .js files ES modules (see ECMAScript Modules); bin maps the command name to the file (a plain string is shorthand for a command named after the package); files is an allow-list for what the published tarball contains; and engines documents the supported Node.js range, which npm only enforces as a warning unless engine-strict is set.

Source: npm docs: package.json (bin, files, engines)

The entry file: wiring only, with a shebang
#!/usr/bin/env node
import { constants } from 'node:os';
import { stdout } from 'node:process';
import { main } from '../src/main.js';

const controller = new AbortController();
let caught;
for (const name of ['SIGINT', 'SIGTERM']) {
  process.once(name, () => {
    caught = name;
    controller.abort();
  });
}

// A closed pipe (`bookshelf list | head -n 1`) is not a failure.
stdout.on('error', (err) => {
  if (err.code === 'EPIPE') process.exit(0);
  throw err;
});

const code = await main(process.argv.slice(2), { signal: controller.signal });
// Shell convention: a process ended by signal N reports 128 + N.
process.exitCode = caught ? 128 + constants.signals[caught] : code;

Source: Node.js API: process.exitCode, Node.js API: Signal events, Node.js API: OS signal constants

Parsing arguments with util.parseArgs

util.parseArgs() turns an argument array into { values, positionals } and covers what a small tool needs: long and short flags, booleans and strings, --name=value, grouped short flags, -- handling and negation. In strict mode (the default) an unknown flag or a missing value throws an error whose code starts with ERR_PARSE_ARGS_; the tool catches it, prints a one-line message and a hint on stderr, and exits with status 2, the conventional "usage error" code. The API reference of parseArgs() is in The util Module; what matters when building a tool is the decisions around it.

Excerpt of src/main.js: parse, then dispatch on the first positional
import { parseArgs, styleText } from 'node:util';
// ...
export async function main(argv, { signal } = {}) {
  try {
    const { values, positionals } = parseArgs({
      args: argv,
      allowPositionals: true,
      allowNegative: true,
      options: {
        help: { type: 'boolean', short: 'h' },
        version: { type: 'boolean', short: 'v' },
        json: { type: 'boolean' },
        color: { type: 'boolean' },
        file: { type: 'string', short: 'f' },
        year: { type: 'string', short: 'y' },
      },
    });
    const [command, ...rest] = positionals;
    if (values.help) { console.log(HELP); return EXIT.OK; }
    if (values.version) { console.log(pkg.version); return EXIT.OK; }
    if (!command) throw new UsageError('missing command');
    // ...
  } catch (err) {
    if (err instanceof UsageError || String(err.code).startsWith('ERR_PARSE_ARGS_')) {
      stderr.write(`bookshelf: ${err.message}\nTry 'bookshelf --help'.\n`);
      return EXIT.USAGE;
    }
    // ...
  }
}

Source: Node.js API: util.parseArgs()

Four design choices in that excerpt are worth stating, because each one avoids a bug that is easy to ship.

  • main() takes the arguments and returns an exit code. It never calls process.exit() and never reads process.argv itself, so a test can call it directly (or spawn the real binary, see Testing a CLI) and the entry file stays in charge of the process.

  • Options that take part in configuration layering have no default. parseArgs() applies a default whenever the flag is absent, which would make the flag win over the config file and the environment. Leaving it out keeps values.file undefined unless the user typed it, which is what the precedence code in Configuration relies on.

  • allowNegative: true gives --no-color for free. It sets the boolean color to false; with no flag, color stays undefined.

  • Subcommands are your job. parseArgs() has no command tree: the first positional is the command and the rest are its arguments. For a handful of commands a switch is enough. When each subcommand needs its own flags, the tokens option (an ordered list of options and positionals) lets you split the arguments yourself, and at that point a framework starts to pay off (see When a framework pays off).

It also does not generate --help, convert numbers or validate ranges; the tool above keeps its help text in one template string and validates the year with a regular expression. Running the parsing paths gives:

Output: stdout for results, stderr for talk, colour only for people

Two conventions carry most of the weight of a well-behaved tool. Results go to standard output, where they can be redirected or piped; everything else (prompts, progress, confirmations, errors) goes to standard error, so that bookshelf list > books.txt captures data and nothing else. And colour is for people: it is emitted only when the stream is a terminal and the user has not opted out. util.styleText() already makes that decision for you. It checks whether the target stream (process.stdout by default, { stream: process.stderr } for messages on stderr) supports colours and honours NO_COLOR, NODE_DISABLE_COLORS and FORCE_COLOR; with { validateStream: false } it always emits the escape codes. A --no-color flag is still worth offering, because not every user can set environment variables, and the tool below combines the three signals.

Prompts with readline/promises

A tool should ask a question only when a person can answer it. The check is stdin.isTTY: when standard input is a file or a pipe, the missing value is a usage error and the tool exits with 2 instead of waiting for input that will never arrive. When it is a terminal, readline/promises prints the query on stderr (so stdout stays clean) and question() resolves with the typed line.

src/prompt.js: asking only the missing questions, cancelable
import { createInterface } from 'node:readline/promises';
import { stdin, stderr } from 'node:process';

// Interactive only: the caller checks stdin.isTTY first. Prompts go to stderr so stdout stays clean.
export async function ask(questions, { signal } = {}) {
  const rl = createInterface({ input: stdin, output: stderr });
  // On a terminal Ctrl+C is a keystroke (raw mode), not a signal: readline reports it as 'SIGINT'.
  const cancelled = new AbortController();
  rl.once('SIGINT', () => cancelled.abort());
  const abort = AbortSignal.any([cancelled.signal, ...(signal ? [signal] : [])]);
  try {
    const answers = {};
    for (const [key, query] of Object.entries(questions)) {
      answers[key] = (await rl.question(`${query}: `, { signal: abort })).trim();
    }
    return answers;
  } catch (err) {
    // Ctrl+D also rejects with an AbortError, but nobody aborted our signal: report it as plain failure.
    if (err.name === 'AbortError' && !abort.aborted) throw new Error('input ended before every question was answered');
    throw err;
  } finally {
    rl.close();
  }
}

Exit codes and signals

The exit status is the tool’s return value for every caller: a shell if, a Makefile, a CI job, an npm script, an agent. The convention the tool follows is small and stable. It uses process.exitCode rather than process.exit(), so that pending writes to stdout and stderr are flushed; the full reasoning and the codes Node.js uses itself are in Process, Signals & Exit Codes.

1

Signals are delivered to the process, not to a function: the entry file registers a listener with process.once() for SIGINT and SIGTERM that records which signal arrived and aborts an AbortController. Configuration: flags, environment, config file

Tools usually accept the same setting in several places, and users expect a fixed precedence: built-in defaults, then a configuration file, then environment variables, then command-line flags, the most specific source winning. loadConfig() implements exactly that with object spread, where later spreads overwrite earlier ones. A missing config file is normal (ENOENT is swallowed); a file that exists but does not parse is an error the user must see, with its path in the message.

src/config.js: defaults, config file, environment, flags
import { readFile } from 'node:fs/promises';
import { homedir } from 'node:os';
import { join } from 'node:path';

const defaults = {
  file: join(process.env.XDG_DATA_HOME ?? join(homedir(), '.local', 'share'), 'bookshelf', 'books.json'),
  color: true,
};

async function readConfigFile() {
  const dir = process.env.XDG_CONFIG_HOME ?? join(homedir(), '.config');
  const path = join(dir, 'bookshelf', 'config.json');
  try {
    return JSON.parse(await readFile(path, 'utf8'));
  } catch (err) {
    if (err.code === 'ENOENT') return {};            // no config file is fine
    throw new Error(`cannot use ${path}: ${err.message}`);
  }
}

// Precedence, lowest to highest: defaults < config file < environment < command-line flags.
export async function loadConfig(flags) {
  const fromEnv = {};
  if (process.env.BOOKSHELF_FILE) fromEnv.file = process.env.BOOKSHELF_FILE;
  if (process.env.NO_COLOR) fromEnv.color = false;
  const fromFlags = Object.fromEntries(Object.entries(flags).filter(([, v]) => v !== undefined));
  return { ...defaults, ...(await readConfigFile()), ...fromEnv, ...fromFlags };
}

Where the files live is a convention, not an API: on Linux and macOS $XDG_CONFIG_HOME (default ~/.config) holds configuration and $XDG_DATA_HOME (default ~/.local/share) holds data; Windows tools typically use %APPDATA%. Node.js has no helper for this, and the Windows paths were not tried here.

Three related points:

  • .env files. A tool that wants a project-local .env can call process.loadEnvFile() itself. A run under all three lines gave the same results: the file’s value is used when the variable is not already set, a value from the shell wins, and a missing file throws an error with code ENOENT that the tool must tolerate. The --env-file flag exists for running scripts, but the flag belongs to the node binary and a user of your installed command cannot pass it, so the tool loads the file itself.

  • node.config.json is not your tool’s config file. It configures the node process (see CLI Options, Environment & Config File); a tool defines and reads its own file as above.

  • Secrets stay out of the config file and out of the arguments. Read tokens from the environment or a prompt, and if the tool stores credentials, restrict the file permissions; see Configuration & Auth for the agent-facing side.

The entry file and the real binary are part of the product, so test them as a user would: spawn the program, pass an argument array (never a shell command string), and assert on the exit status, standard output and standard error. node:test (see Test Runner) and child_process.spawnSync() are enough; process.execPath is the running node binary, so the test uses the same Node.js version that runs the suite.

Two details of the bundling step: the entry file uses top-level await, which esbuild cannot emit as CommonJS (the first attempt with --format=cjs failed with an error pointing at the await), so the build uses ESM output and "mainFormat": "module"; and --format=esm keeps the node: imports and the JSON import attribute working, because esbuild inlines the package.json version.

Things the run showed, labelled as observed on one platform and not as a promise:

  • The binary is a copy of node: about 145 MB in this build. Distribution size is the price of not requiring a runtime.

  • Arguments pass through unchanged. process.argv.slice(2) held the user’s arguments, and --help reached the tool’s own parser instead of being interpreted as a Node.js option. The documentation describes execArgvExtension ("env" by default, "cli" to accept --node-options=…​, "none") for controlling which extra Node.js flags the executable accepts, and execArgv for fixed ones.

  • On macOS the binary must be re-signed. Run straight after the build, without codesign, the unsigned file was killed (exit status 137); after codesign --sign - (an ad-hoc signature) it ran. The documentation lists the same step for macOS and an optional signtool step for Windows.

  • Assets (templates, data files) can be added with the assets map and read through node:sea; the useVfs option that exposes them as a read-only virtual file system was added in v26.9.0 as Stability 1.0 and was not run here.

  • Cross-building needs useCodeCache and useSnapshot set to false, because those caches only load on the platform that produced them.

On the older lines the workflow differs, because --build-sea is new in v25.5.0. Node.js 24.21.0 and 22.23.3 reject the flag (node: bad option: --build-sea). On 24 the older path worked as far as it was tried: node --experimental-sea-config wrote a preparation blob, and the third-party postject tool injected it into a copy of the node binary (after codesign --remove-signature, with --macho-segment-name NODE_SEA on macOS and the documented sentinel fuse), but the resulting program failed to start with Cannot use import statement outside a module for the ESM bundle, so on 24 and 22 the main script has to be CommonJS (the documentation of those lines has no mainFormat field). A SEA is therefore a Node.js 26 option for an ESM tool, and a bundle to a single CommonJS file for older lines, which this page did not complete.

Other ways to ship a self-contained tool are a container image with Node.js and the tool (see Docker) and the standalone binaries of other tool-chains; a SEA is attractive when the target machines have no container runtime and no Node.js.

When a framework pays off

util.parseArgs() stops where tools start to grow: it does not generate help from option descriptions, does not build subcommand trees with their own flags, does not coerce or validate values, and has no shell completion. When a tool reaches ten commands, nested subcommands, plugin loading or interactive terminal interfaces, a framework removes code you would otherwise write. Node.js CLI Frameworks works through commander, yargs, oclif (a plugin-based framework) and Ink (React for terminals) using a different running example, including package.json bin, shebang, ESM and CommonJS notes and exit codes that match a machine-readable contract. A reasonable rule: start with the built-ins, as here; adopt a framework when you find yourself writing a help generator, a validator or a command tree. The design rules for output that other programs consume are in CLI Design Fundamentals, and a finished CLI can be exposed to language-model clients as a tool; see Wrapping as an Agent Tool.

The complete src/main.js

The pieces above come from one file. This is its complete text, as it was run for every claim on this page.

src/main.js
import { parseArgs, styleText } from 'node:util';
import { createInterface } from 'node:readline/promises';
import { stdin, stdout, stderr } from 'node:process';
import { loadConfig } from './config.js';
import { readBooks, writeBooks } from './store.js';
import { ask } from './prompt.js';
import pkg from '../package.json' with { type: 'json' };

export const EXIT = { OK: 0, FAILURE: 1, USAGE: 2, SIGINT: 130 };

const HELP = `usage: bookshelf <command> [options]

commands:
  list                     print the catalogue (NDJSON when piped)
  add [title] [-y year]    add a book, prompting for what is missing
  import                   read NDJSON books from standard input

options:
  -f, --file <path>        catalogue file
  -h, --help               show this help
  -v, --version            print the version
      --json               force NDJSON output
      --no-color           disable colours`;

class UsageError extends Error {}

export async function main(argv, { signal } = {}) {
  try {
    const { values, positionals } = parseArgs({
      args: argv,
      allowPositionals: true,
      allowNegative: true,
      options: {
        help: { type: 'boolean', short: 'h' },
        version: { type: 'boolean', short: 'v' },
        json: { type: 'boolean' },
        color: { type: 'boolean' },
        file: { type: 'string', short: 'f' },
        year: { type: 'string', short: 'y' },
      },
    });
    const [command, ...rest] = positionals;
    if (values.help) { console.log(HELP); return EXIT.OK; }
    if (values.version) { console.log(pkg.version); return EXIT.OK; }
    if (!command) throw new UsageError('missing command');

    const config = await loadConfig({ file: values.file, color: values.color });
    const paint = (format, text) => (config.color ? styleText(format, text, { stream: stdout }) : text);
    const books = await readBooks(config.file);

    switch (command) {
      case 'list': {
        const lines = values.json || !stdout.isTTY;
        for (const b of books) {
          console.log(lines ? JSON.stringify(b) : `${paint('bold', b.title)} ${paint('dim', `(${b.year})`)}`);
        }
        return EXIT.OK;
      }
      case 'add': {
        let title = rest.join(' ');
        let year = values.year;
        if (!title || !year) {
          if (!stdin.isTTY) throw new UsageError('title and --year are required when stdin is not a terminal');
          const answers = await ask({ ...(title ? {} : { title: 'Title' }), ...(year ? {} : { year: 'Year' }) }, { signal });
          title ||= answers.title;
          year ||= answers.year;
        }
        if (!title || !/^\d{4}$/.test(year)) throw new UsageError('a title and a four-digit year are required');
        books.push({ title, year: Number(year) });
        await writeBooks(config.file, books);
        console.error(`added ${title}`);
        return EXIT.OK;
      }
      case 'import': {
        let count = 0;
        // The signal option closes the interface (ending the loop) when the caller aborts.
        for await (const line of createInterface({ input: stdin, crlfDelay: Infinity, signal })) {
          if (line.trim() === '') continue;
          books.push(JSON.parse(line));
          count++;
        }
        signal?.throwIfAborted();                          // interrupted: save nothing
        await writeBooks(config.file, books);
        console.error(`imported ${count} books`);
        return EXIT.OK;
      }
      default:
        throw new UsageError(`unknown command '${command}'`);
    }
  } catch (err) {
    if (err instanceof UsageError || String(err.code).startsWith('ERR_PARSE_ARGS_')) {
      stderr.write(`bookshelf: ${err.message}\nTry 'bookshelf --help'.\n`);
      return EXIT.USAGE;
    }
    if (err.name === 'AbortError') {
      stderr.write('\n');
      return EXIT.SIGINT;                                 // cancelled: 128 + SIGINT
    }
    stderr.write(`bookshelf: ${err.message}\n`);
    return EXIT.FAILURE;
  }
}

src/store.js is the other missing piece. It writes the catalogue through a temporary file and a rename, so a reader (or a crash) never sees a half-written JSON file:

src/store.js
import { mkdir, readFile, rename, writeFile } from 'node:fs/promises';
import { dirname } from 'node:path';

export async function readBooks(file) {
  try {
    return JSON.parse(await readFile(file, 'utf8'));
  } catch (err) {
    if (err.code === 'ENOENT') return [];
    throw err;
  }
}

// Write to a temporary file and rename it: readers never see a half-written catalogue.
export async function writeBooks(file, books) {
  await mkdir(dirname(file), { recursive: true });
  const tmp = `${file}.${process.pid}.tmp`;
  await writeFile(tmp, JSON.stringify(books, null, 2) + '\n');
  await rename(tmp, file);
}

One note on the design: main() catches errors and maps them to codes, but the String(err.code) in the parse-error check is deliberate. A DOMException such as the AbortError raised by signal.throwIfAborted() has a numeric code (20), and calling .startsWith() on it threw a TypeError in the first version of the tool.

Where the books are outdated

Both books that this section consults build command-line tools with the packages of their time. Node.js Projects by Jonathan Wexler (O’Reilly, 2025) starts its projects with readline plus process.stdin and util.promisify, and later builds a menu-driven password manager around synchronous terminal prompts. Today node:readline/promises returns promises directly, so the promisify step is unnecessary; the incomplete promisify example in that chapter, where the readline interface is not defined, is repaired by the ask() function above. Synchronous prompt packages block the event loop while they wait, which is acceptable in a one-shot script but not in a tool that also handles signals or timers. Efficient Node.js by Samer Buna (O’Reilly, 2025) teaches the REPL and the node command line well and is a good place to read about process.argv; it predates the habit, now possible with built-ins, of replacing argument parsers and colour libraries by util.parseArgs() and util.styleText(). Neither book covers the parts of a CLI that are about being a good citizen of the shell: the stderr/stdout split, exit code conventions beyond 0 and 1, handling EPIPE and signals, and shipping a single executable file, so use the sections above for those. Both books also install npm packages for environment-file loading and terminal prompts that process.loadEnvFile() and readline/promises now cover.

Pitfalls

  • A shebang with CRLF line endings fails with env: node\r: No such file or directory. Normalise line endings for files under bin/.

  • Forgetting "type": "module" (or the .mjs extension) can make import in the entry file fail to load. Recent releases detect ES module syntax in an untyped .js file (see Running Scripts, the CLI & the REPL), but a published package should be explicit.

  • Calling process.exit() after writing a lot to stdout can cut the output when stdout is a pipe: the documentation says pipes are asynchronous on POSIX and synchronous on Windows, and that process.exit() does not wait for pending I/O. Set process.exitCode and return, as the entry file does.

  • A prompt with a piped stdin that never answers leaves an unsettled promise; Node.js ends such a program with exit status 13 and a warning on all three lines. Check stdin.isTTY first.

  • Treating Ctrl+C at a prompt as a signal. In a terminal it arrives as a keystroke that readline reports as 'SIGINT'; with no listener the process can end with status 0.

  • Ignoring EPIPE. Writing with process.stdout.write() into a closed pipe throws an unhandled 'error' event; console.log() hides it.

  • Colour codes in piped output. Use styleText() with the right stream option, or the tool pollutes files and breaks grep.

  • Defaults in parseArgs() that outrank the config file. Keep layered settings out of default.

  • Putting a secret in an argument or in the config file exposes it in ps output, shell history and backups.

  • Shipping tests, fixtures or .env files in the tarball. Use files and check npm pack --dry-run before every publish.

  • Treating an SEA as portable. It is built for one operating system and CPU architecture, a macOS build must be signed, and it is a copy of the exact Node.js version that built it.
