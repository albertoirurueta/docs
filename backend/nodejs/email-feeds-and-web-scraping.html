Sending email with Nodemailer

Email delivery is a chain of independent systems: your application hands a message to a mail server over SMTP, that server relays it, and the recipient’s provider decides whether to deliver, junk or reject it. Nodemailer is the de facto library for the first hop. It builds the MIME message (headers, text and HTML alternatives, attachments, encodings) and speaks SMTP, so your code deals with objects instead of RFC 5322 text.

Transports

nodemailer.createTransport(options) returns a transporter, and the options select the transport, the mechanism that actually takes the message away.

Table 2. Transports bundled with Nodemailer
Transport Selected by Use it for

SMTP (the default)

host, port, secure, auth; or service for a well-known provider

Talking to any SMTP server or relay. The default port is 587, or 465 when secure is true.

Sendmail

sendmail: true

Piping the message to a local sendmail-compatible binary. Rare on containers, which usually ship none.

Stream and JSON

streamTransport: true, jsonTransport: true

Not delivering at all: unit tests and previews that receive the generated message as a buffer, stream or JSON object.

Amazon SES and community transports

A transport object passed to createTransport()

Posting to an HTTPS API instead of SMTP; the Nodemailer documentation lists the bundled and community options.

Two TLS options on the SMTP transport matter more than the rest. With secure: false (the default) the connection starts in plain text and is upgraded with STARTTLS if the server offers it; with secure: true it is TLS from the first byte, which is what port 465 expects. requireTLS: true makes sending fail instead of silently continuing in plain text when the server does not offer STARTTLS, and ignoreTLS: true disables STARTTLS altogether. Production code should use secure: true on 465 or requireTLS: true on 587 and never ignoreTLS; the examples below set ignoreTLS only because the local test server has no certificate. Credentials and the DKIM key belong in process.env, loaded with --env-file (see CLI Options, Environment & Config File).

For many messages, set pool: true. A pooled transporter keeps maxConnections connections open (default 5) and reuses them for maxMessages messages each, instead of paying a TCP and TLS handshake per mail, and rateDelta with rateLimit caps how many messages may leave per time window, which is how you stay under a provider’s sending limit. Call transporter.close() when you are done, or the pooled connections keep the process alive.

Testing against a local SMTP server

Never develop against a real mailbox. A catch-all SMTP server that accepts every message and delivers nothing is a few lines with the smtp-server package (a stand-alone tool such as Mailpit does the same job with a web inbox, and Nodemailer’s own guide also describes the hosted Ethereal service). Listening on port 0 lets the operating system pick a free port, and the addresses use the reserved .test top-level domain, so nothing can reach a real person.

Install the packages used on this page (scratch project, never in a repository you commit)
npm i nodemailer smtp-server mailparser cheerio puppeteer

HTML and text parts, templating and the unsubscribe headers

A message should carry both a text and an html body: Nodemailer sends them as a multipart/alternative pair, and clients that cannot or will not render HTML (and spam filters that distrust HTML-only mail) use the text part. Nodemailer has no template engine of its own; it offers a compile plugin stage (registered with transporter.use()) for template plugins, and for a handful of mails a function that returns { text, html } is enough. The one rule that is not optional is escaping: every value interpolated into HTML is data from somebody, and an unescaped name or URL is an injection into a message that arrives under your domain.

The example sends one confirmation mail with both parts, a List-Unsubscribe header created from the list option, the RFC 8058 List-Unsubscribe-Post header, and a DKIM signature, then reads the message back from the local server.

Generate a throwaway DKIM key pair in the scratch directory and pass the private key through the environment

SPF, DKIM, DMARC and List-Unsubscribe basics

The receiving provider cannot trust the From: header, so it checks three DNS-published policies. Each answers a different question, and mail sent from your own domain should pass all three.

Table 3. The authentication records and what each proves
Mechanism What it checks What you publish

SPF (RFC 7208)

Whether the connecting server’s IP address is allowed to send for the envelope sender’s domain.

A TXT record on the sending domain listing the IP ranges or providers (for example an include: for your mail provider).

DKIM (RFC 6376)

Whether the message was signed by a key that belongs to the signing domain, and whether the signed headers and body are unchanged in transit.

A TXT record at <selector>._domainkey.<domain> holding the public key. The private key signs; Nodemailer’s dkim option does it with domainName, keySelector and privateKey.

DMARC (RFC 7489)

Whether SPF or DKIM passed and the passing domain aligns with the visible From: domain, and what to do when it does not.

A TXT record at _dmarc.<domain>, starting with p=none to collect reports and tightening to quarantine or reject once legitimate senders are aligned.

If you send through a provider’s SMTP relay, the provider usually signs for you once you add its DNS records, and the DKIM option in Nodemailer is for the case where you sign yourself. Keep the private key out of the repository and the image: read it from an environment variable or a secret store, rotate it by publishing a new selector, and remember that the public key in DNS is the only part that is public. The DNS side can be checked without sending anything, for example with dig TXT <selector>._domainkey.<domain>; DNS lookups from Node.js itself are covered in TCP, UDP & DNS.

The unsubscribe headers are the part that is easy to forget. List-Unsubscribe (RFC 2369) tells a mail client where an unsubscribe request goes, so it can show its own "Unsubscribe" button. RFC 8058 adds List-Unsubscribe-Post: List-Unsubscribe=One-Click: the client then sends an HTTPS POST to the URL by itself, without the person visiting a page, and the endpoint must unsubscribe immediately with no login or confirmation. Mailbox providers have tied these to delivery. Google’s sender guidelines require senders of more than 5,000 messages a day to Gmail accounts to authenticate with SPF, DKIM and DMARC, support one-click unsubscribe and keep user-reported spam rates low (under 0.3%), and the Yahoo sender guidance likewise asks for DMARC and an easy, one-click unsubscribe; read the current pages, because thresholds change.

Consent: double opt-in, unsubscribe and pacing

Sending mail to people is regulated and policed, and the technical design should make the right behaviour the easy one. Email only people who asked, record when and how they did, and make leaving as easy as joining. The usual pattern is double opt-in: the sign-up form only stores a pending subscription and sends a confirmation message, and the address becomes active when the person follows the link in it. That proves the address belongs to the person (so nobody can subscribe a stranger) and gives you a record of consent. Two details are easy to get wrong. The token in the link must be unguessable and single use, so generate it from crypto.randomBytes(), store only its hash with an expiry time, and look the pending subscription up by that hash; an email address in a GET link is not a token, and the address does not belong in the link at all. And the confirmation and unsubscribe endpoints change state, so they need the protections described in Security Best Practices; the one-click unsubscribe endpoint in particular must accept the unauthenticated POST that mail providers send. Legal requirements depend on where you and your recipients are, so ask someone qualified rather than inferring them from a library’s documentation; tracking pixels, which the books' mailer examples use, add a consent question of their own and are better avoided.

The example below combines the token handling with a pooled transporter that is rate limited to two messages per second, and runs against its own local server.

consent.mjs: double opt-in tokens and a rate-limited pool
import { once } from 'node:events';
import { createHash, randomBytes } from 'node:crypto';
import { SMTPServer } from 'smtp-server';
import nodemailer from 'nodemailer';

// Double opt-in: the link carries only a random token; the store is keyed by the token's hash.
const TOKEN_TTL_MS = 48 * 60 * 60 * 1000;
const sha256 = (s) => createHash('sha256').update(s).digest('hex');
const pending = new Map(); // sha256(token) -> { email, expiresAt } (a table with a unique index in a real service)
function startSubscription(email, now = Date.now()) {
  const token = randomBytes(32).toString('base64url');
  pending.set(sha256(token), { email, expiresAt: now + TOKEN_TTL_MS });
  return { email, url: `https://bookshelf.example.test/confirm?token=${token}` }; // no address in the URL
}
function confirm(token, now = Date.now()) {
  const key = sha256(String(token)); // a lookup by digest of a 256-bit random token: nothing useful leaks
  const record = pending.get(key);
  if (!record) return null;
  pending.delete(key); // single use, and an expired token is removed too
  return record.expiresAt > now ? record.email : null;
}

// Pooled transport with a rate limit, against a local catch-all SMTP server that records recipients.
const recipients = [];
const server = new SMTPServer({ authOptional: true, disabledCommands: ['STARTTLS'],
  onData(stream, session, cb) {
    stream.resume();
    stream.on('end', () => { recipients.push(...session.envelope.rcptTo.map((r) => r.address)); cb(); });
  } });
server.listen(0, '127.0.0.1');
await once(server.server, 'listening');
const transporter = nodemailer.createTransport({
  host: '127.0.0.1', port: server.server.address().port, ignoreTLS: true,
  pool: true, maxConnections: 2, rateDelta: 1000, rateLimit: 2, // at most 2 messages per second
});

const subscriptions = ['a@example.test', 'b@example.test', 'c@example.test'].map((e) => startSubscription(e));
const started = performance.now();
await Promise.all(subscriptions.map(({ email, url }) => transporter.sendMail({
  from: 'news@bookshelf.example.test', to: email, subject: 'Confirm your subscription', text: url, // to the address being confirmed
})));
console.log('sent', recipients.length, 'in', Math.round((performance.now() - started) / 100) / 10, 's to', recipients.sort());
console.log(subscriptions[0].url.replace(/token=.{6}.*/, 'token=…'));

const tokenOf = (i) => new URL(subscriptions[i].url).searchParams.get('token');
console.log('wrong token:', confirm('wrong-token'), '| right token:', confirm(tokenOf(0)), '| reused:', confirm(tokenOf(0)));
console.log('after 49 hours:', confirm(tokenOf(1), Date.now() + 49 * 60 * 60 * 1000));

Consuming RSS and Atom feeds with fetch

A feed is an XML document that a site publishes so programs can follow it: RSS 2.0 (<rss><channel><item>) and Atom (RFC 4287, <feed><entry>) are the two formats you meet. They differ in the details a parser must absorb: RSS puts the link in the text of <link> and the date in <pubDate> (an RFC 822 date), while Atom puts the link in an href attribute and the date in <updated> (an RFC 3339 timestamp). Node.js ships no XML parser, so the choice is a dedicated feed-parsing package or an XML-aware library you already have; the example uses Cheerio in xml: true mode, which is enough for well-formed feeds and shows both shapes in one function. For anything that must survive malformed real-world feeds, prefer a maintained feed parser.

A feed reader is a polling client, so the manners matter more than the parsing. Send an identifying User-Agent, set a deadline with AbortSignal.timeout(), treat non-2xx answers as errors (fetch only rejects on network failure), and use conditional requests: remember the ETag (or Last-Modified) from the last answer and send it back as If-None-Match (or If-Modified-Since), so an unchanged feed costs the server a 304 with no body. Poll every few minutes at the fastest, honour any Retry-After, and spread many feeds out instead of firing them together at the top of the hour.

    headers: { 'user-agent': UA, accept: 'application/rss+xml, application/atom+xml, application/xml;q=0.9',

      title: $el.children('title').text(),

    };
  }).get();
  if (res.headers.get('etag')) cache.set(url, { etag: res.headers.get('etag'), items });

Scraping responsibly

Scraping means fetching pages meant for people and extracting data from them. It is sometimes the only way to get data, and it is also how well-meaning programs get blocked, sued or blamed for an outage. Before writing a selector, work through this list, in order.

Table 4. Checklist before scraping a site
Question What to do

Is there an API, a feed or a data export?

Use it. It is more stable than markup and it is what the site expects automated clients to use.

What do the terms of service say?

Read them. Many sites forbid automated access or reuse of their content, and no technical measure overrides that. If they forbid it, ask for permission or stop.

What does robots.txt say?

Fetch /robots.txt before anything else and obey it. RFC 9309 defines the format and states that its rules are not a form of access authorization, so a path that is not disallowed is not thereby permitted by the terms of service. Per the RFC, a 4xx answer means no published rules, while an unreachable file (5xx) means you should assume the whole site is off limits; cache the file for at most a day.

How fast may you go?

Slowly. Crawl-delay is a widespread but non-standard directive (RFC 9309 does not define it), and a polite default of one request per second per host, sequential, is a better start than concurrency. Back off on 429 and 503, and honour Retry-After.

Who are you?

Send a truthful User-Agent with a name, a version and a contact URL or address, so the operator can reach you instead of banning an IP range. Do not spoof a browser’s user agent to slip past a block; a block is an answer.

What are you collecting?

Personal data has its own legal regime. Collect only what the feature needs and do not republish whole sites.

The example below applies the checklist to the local test site: it reads robots.txt (only the group for *, which is enough here; use a maintained parser in production), skips a disallowed path, sends an identifying user agent, and waits between requests. Cheerio parses markup into a tree and offers a jQuery-like API ($('li.book'), .find(), .attr(), .text(), .map()) to query it. It never runs scripts, loads sub-resources or builds a layout, which makes it fast and safe, and means it sees exactly what the server sent. cheerio.load(html) returns the query function, and { xml: true } switches to an XML parser, as the feed example does. Because the site’s own markup is the only contract, prefer stable hooks such as data-* attributes, ids and semantic classes over positional selectors, resolve relative links with new URL(href, base), and treat every extracted string as untrusted input.

async function loadRules(origin) {
  const res = await fetch(`${origin}/robots.txt`, { headers });
  if (res.status >= 500) throw new Error('robots.txt unreachable: treat the site as disallowed');
  if (!res.ok) return { disallow: [], delayMs: 1000 }; // 4xx: no rules published
  const disallow = [];
  let delayMs = 1000;
  let applies = false;
  for (const raw of (await res.text()).split('\n')) {
    const [field, ...rest] = raw.split('#')[0].split(':');
    const value = rest.join(':').trim();
    switch (field.trim().toLowerCase()) {
      case 'user-agent': applies = value === '*'; break;
      case 'disallow': if (applies && value) disallow.push(value); break;
      case 'crawl-delay': if (applies) delayMs = Number(value) * 1000; break;
    }
  }
  return { disallow, delayMs };
}

Puppeteer and Playwright for rendered pages

Many sites today ship an almost empty HTML shell and build the page in the browser with JavaScript, so fetch plus Cheerio sees the shell and nothing else. The test site’s /spa page demonstrates it: its <div id="app"> says loading… until a script replaces it. For such pages (and for anything behind a login flow you are entitled to automate, or a real user-interaction test) you need a real browser engine. Puppeteer drives Chrome or Firefox and Playwright drives Chromium, Firefox and WebKit, both through a high-level API: launch a browser, open a page, navigate, wait for something to appear, read it.

The cost is large compared with Cheerio: a whole browser process per run, a few hundred megabytes on disk (the Chrome for Testing build Puppeteer downloaded here is about 370 MB), seconds of start-up, and far more memory per page. So decide in this order: an API or feed; then fetch plus Cheerio, possibly against the JSON endpoint the page itself calls (visible in the browser’s network tab, and still subject to the checklist above); and a headless browser only when the data truly exists only after rendering. Whatever the tool, the checklist applies unchanged: browsers are automated clients too, so set an honest user agent and keep the delay.

render.mjs: the same page seen by fetch plus Cheerio and by Puppeteer
import * as cheerio from 'cheerio';
import puppeteer from 'puppeteer';
import { startSite } from './site.mjs';

const site = await startSite();
const staticHtml = await (await fetch(`${site.origin}/spa`)).text();
console.log('fetch + Cheerio sees:', cheerio.load(staticHtml)('#app').text());

const browser = await puppeteer.launch(); // headless by default
try {
  const page = await browser.newPage();
  await page.setUserAgent('BookshelfBot/1.0 (+https://bookshelf.example.test/bot; bot@example.test)');
  await page.goto(`${site.origin}/spa`, { waitUntil: 'domcontentloaded' });
  const title = await page.waitForSelector('#app .title');
  console.log('Puppeteer sees:', await title.evaluate((el) => el.textContent));
  const html = await page.content();
  console.log('Cheerio on rendered HTML:', cheerio.load(html)('h1').text());
} finally {
  await browser.close();
  site.close();
}

Three points about the example. puppeteer.launch() is headless by default and npm i puppeteer downloaded a Chrome for Testing build for it (observed here; the cached browser is outside node_modules); puppeteer-core skips the download and needs an executablePath or channel. waitForSelector() waits for the element to exist instead of sleeping for a guessed time, which is the habit that separates a reliable scraper from a flaky one. And the finally block closes the browser even when navigation throws, because an orphaned browser process is the commonest way these scripts leak memory. page.content() returns the rendered HTML, so you can hand it to Cheerio and keep the extraction code you already have.

Playwright’s equivalent differs mainly in naming: browser.newContext() isolates a session and takes the userAgent option, and page.locator(selector) returns a lazily resolved, auto-waiting handle.

What changed recently

Table 6. Changes since the older material, with versions
Change Detail

Global fetch everywhere

Unflagged in Node.js 18 and no longer experimental since 21, so node-fetch and axios are no longer needed for feed polling or simple scraping; the Node.js project documents a codemod from axios to fetch.

Nodemailer 10

Requires Node.js 20 or later and ships ES module and CommonJS builds. The createTransport() and sendMail() calls used here are unchanged from earlier majors, but read the release notes when upgrading across majors, since options are occasionally removed.

Puppeteer 25

The current line is 25.x. In its TypeScript declarations headless is boolean | 'shell' (default true, the new headless mode) and Page has no waitForTimeout(), so older listings that pass headless: 'new' or sleep with page.waitForTimeout() do not match the current API; use the default and waitForSelector() or the other wait methods.

Mailbox-provider requirements

Large senders to Gmail must authenticate with SPF, DKIM and DMARC and support one-click unsubscribe, which makes RFC 8058 headers a delivery requirement and no longer a courtesy.

Install scripts in npm

npm 11.19 printed a warning that the puppeteer package has a postinstall script that is not covered by an allowlist, yet the download still happened in this run (observed). Read the warning for your npm version, because script policies are tightening across npm.

Where the books are outdated

This section compares the page with the two O’Reilly books consulted while preparing this guide: Node.js Projects by Jonathan Wexler (2025), whose mailer, feed-reader and scraper chapters overlap this page, and Efficient Node.js by Samer Buna (2025). Both are recent; the points below concern habits worth updating and safer forms.

  • The feed-reader project polls on a fixed setInterval() timer. Production polling should await each round before scheduling the next, send conditional requests with the ETag or Last-Modified validators, set a deadline with AbortSignal.timeout() and check the response status, so that a slow response cannot stack overlapping requests and an unchanged feed costs a 304.

  • The mailer project installs the 7.x line of Nodemailer; the current major is 10 and requires Node.js 20 or later. Its unsubscribe feature is a GET route keyed by the email address; the safe form is an unguessable per-subscriber token, the List-Unsubscribe header and the RFC 8058 one-click POST, because a GET can be triggered by link prefetchers and a guessable address lets anyone unsubscribe someone else. Mail authentication (SPF, DKIM, DMARC) and consent get little room in a tutorial but decide whether the mail is delivered. Open-tracking pixels deserve a deliberate consent decision.

  • The scraper project sets a user-agent string chosen to get the same response a browser receives and does not discuss robots.txt or terms of service. The checklist above is the safe form: an identifying user agent, robots rules, a delay and a permission check come before any selector. The chapter’s use of a headless browser for pages that return only a shell is still the right idea; current Puppeteer defaults and waiting methods differ from older listings.

  • Neither book covers AbortSignal.timeout() for deadlines on every outbound request, nor the built-in proxy support in recent Node.js lines that scraping behind a corporate proxy now depends on (see Fetch & HTTP Clients).
