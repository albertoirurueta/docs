Security Best Practices

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Node.js 26 (26.10.0, released 2026-09-21, the Current line that becomes LTS on 2026-10-28), with the differences of Node.js 24 "Krypton" (24.21.0, Active LTS) and Node.js 22 "Jod" (22.23.3, Maintenance) called out; versions and stability levels were checked against the official documentation on 2026-10-04, and every code example was run on all three lines unless the text says otherwise. It follows the structure of the official Node.js security guide, which lists the threats a Node.js application has to account for, each tagged with a Common Weakness Enumeration (CWE) number, and it adds what the guide only points at: the npm supply chain after npm 12, the hardening flags, and how security releases work. The APIs used are mostly Stability 2 (Stable): node:http, node:crypto, node:child_process, node:vm and node:inspector are Stable, and the Permission Model is Stable too, although its --allow-net flag is Stability 1.1 (Active development). --frozen-intrinsics is Stability 1 (Experimental), and node:sqlite, used for the parameterised-query example, is Stability 1.2 (Release candidate). Security is a property of the whole application: this page is the map, and the deeper dives live in Server Timeouts, Limits & Hardening, The Permission Model, Crypto, Passwords & Secrets and npm & Package Management. The running scenario is the Bookshelf application that grows across this section, described in Introduction & Architecture.

The threat model: what is, and is not, a Node.js vulnerability

The official guide opens by saying that it extends the Node.js threat model, which is the project’s definition of what counts as a vulnerability in Node.js itself. The idea is that Node.js treats some things as trusted: the code it is asked to run (your application and its dependencies), the file system the process can reach, and the inputs your own code hands to its APIs. A problem that needs one of those to be hostile is, by that definition, not a bug in Node.js core: it is your deployment’s problem. The practical consequence is the most important sentence on this page: the runtime will not save an application from a malicious dependency, a poisoned directory or unvalidated input, so those defences belong to you. The project’s own policy, including the threat model section, is in the SECURITY.md of the Node.js repository, listed in the references.

Denial of service of the HTTP server (CWE-400)

A denial of service (DoS) makes the application unavailable for the purpose it was built for. It does not need a malicious actor: a buggy client that retries in a tight loop has the same effect. The official guide draws a precise line. The Node.js HTTP server does not parse the request body and hands it to your handler, so a DoS that is triggered by the contents of a body (a pathological JSON document, a regular expression that backtracks) is the application’s responsibility. What the runtime does expect you to configure is everything about the timing and pattern of requests, because that is where an attack such as Slowloris lives: the client sends a request one fragment at a time, the server keeps resources reserved for every unfinished request, and enough of those exhaust the connection limit.

The guide gives three mitigations: put a reverse proxy in front of Node.js, configure the server timeouts, and limit open sockets (agent.maxSockets, agent.maxTotalSockets, agent.maxFreeSockets and server.maxRequestsPerSocket). It also warns about a smaller trap that is easy to miss: a server created without an 'error' listener on its sockets can crash the whole process on a bad request. The example sets the timeouts, answers malformed requests with a 400 through the 'clientError' event, and shows the equivalent listener for a raw node:net server.

A server that survives slow, idle and malformed clients (dos.mjs)
import http from 'node:http';
import net from 'node:net';

const server = http.createServer((req, res) => {
  res.end('ok\n');
});

// Close slow or idle connections instead of keeping resources dedicated to them.
server.headersTimeout = 10_000;      // time allowed to receive the complete headers
server.requestTimeout = 30_000;      // time allowed to receive the whole request
server.keepAliveTimeout = 5_000;     // idle keep-alive connections
server.maxRequestsPerSocket = 100;   // recycle long-lived connections

// Handle socket-level errors so a bad client cannot crash the process.
server.on('clientError', (err, socket) => {
  if (socket.writable) socket.end('HTTP/1.1 400 Bad Request\r\nConnection: close\r\n\r\n');
  else socket.destroy();
});

// A raw net server needs the same care: always attach an 'error' listener.
const echo = net.createServer((socket) => {
  socket.on('error', (err) => console.error('socket error:', err.code));
  socket.pipe(socket);
});

server.listen(0, '127.0.0.1', () => {
  const { port } = server.address();
  // Send a malformed request line and check that the server answers and survives.
  const c = net.connect(port, '127.0.0.1', () => c.write('NOT HTTP AT ALL\r\n\r\n'));
  c.on('data', (d) => console.log(d.toString().split('\r\n')[0]));
  c.on('close', async () => {
    const res = await fetch(`http://127.0.0.1:${port}/`);
    console.log('still serving:', res.status, (await res.text()).trim());
    server.close(); echo.close();
  });
});
echo.listen(0, '127.0.0.1');
Output (identical on Node.js 26, 24 and 22)
HTTP/1.1 400 Bad Request
still serving: 200 ok

Source: Node.js Learn: Security Best Practices, Denial of Service of HTTP server

The values above are illustrative. Choosing them, the size and connection limits, and the interaction with a reverse proxy are the subject of Server Timeouts, Limits & Hardening. The other DoS family, a handler that burns the CPU or blocks the loop for everyone, is in Don’t Block the Event Loop. A third family arrives with data you did not size: unbounded request bodies, unbounded uploads and decompression bombs (see Compression with zlib); always cap what you read.

DNS rebinding (CWE-346)

This attack targets applications that run with the debugging inspector enabled (--inspect). Browsers allow any web page to send HTTP and WebSocket requests, and the same-origin policy normally stops a page from reading answers from a local address. DNS rebinding defeats that: the attacker controls both a website and the DNS server that resolves its name, so for a moment the name resolves to the victim’s local address and the browser believes the request is same-origin. If an inspector is listening on 127.0.0.1:9229, such a page can talk to it, and the inspector protocol can run arbitrary code in your process.

The mitigations in the guide are to keep the inspector out of production and to stop it from being started on demand by a signal. By default, a Node.js process that receives SIGUSR1 starts the inspector, so a signal is enough to open the door; the guide suggests attaching a process.on('SIGUSR1', ...) listener to prevent that, and the --disable-sigusr1 flag does the same without code (it was experimental when added, and is no longer experimental since v24.8.0 and v22.20.0). The CLI reference also warns that binding the inspector to a public address is insecure; the default is 127.0.0.1:9229, and --inspect=0 picks a random port.

The same trick works against any service that listens on localhost and trusts the network location of its caller: development servers, admin ports, sidecars. A general, application-level defence is to validate the Host header and refuse names you do not serve, so a rebinding page that arrives under the attacker’s host name gets a 421.

Refusing requests addressed to an unexpected host (rebind.mjs)
import http from 'node:http';

// Only answer for host names we expect. A DNS-rebinding page reaches this server
// with the attacker's host name in the Host header, not "localhost".
const allowedHosts = new Set(['localhost', '127.0.0.1', '[::1]']);

const server = http.createServer((req, res) => {
  const host = (req.headers.host ?? '').replace(/:\d+$/, '');
  if (!allowedHosts.has(host)) {
    res.writeHead(421, { 'content-type': 'text/plain' }).end('Misdirected Request\n');
    return;
  }
  res.end('hello\n');
});

server.listen(0, '127.0.0.1', async () => {
  const { port } = server.address();
  const ask = (host) => new Promise((resolve) => {
    http.get({ host: '127.0.0.1', port, headers: { host } }, (res) => {
      res.resume(); res.on('end', () => resolve(`${host} -> ${res.statusCode}`));
    });
  });
  console.log(await ask(`localhost:${port}`));
  console.log(await ask(`evil.example:${port}`));
  server.close();
});
Output (the port varies; identical on Node.js 26, 24 and 22)
localhost:50307 -> 200
evil.example:50307 -> 421

Source: Node.js Learn: Security Best Practices, DNS Rebinding

The second half of the defence is to make the signal harmless. The script below installs a SIGUSR1 listener and sends the signal to itself. I observed on all three lines that, without a listener (and without --disable-sigusr1), the same signal makes the process print "Debugger listening on ws://127.0.0.1:9229/…​"; with the listener, or with the flag, it does not.

Keeping SIGUSR1 from opening the inspector (sigusr1.mjs)
// Keep a SIGUSR1 listener so the default "start the inspector" behaviour is not used.
process.on('SIGUSR1', () => console.log('SIGUSR1 ignored, inspector not started'));
setTimeout(() => process.kill(process.pid, 'SIGUSR1'), 50);
setTimeout(() => process.exit(0), 300);
Output
SIGUSR1 ignored, inspector not started

Source: Node.js API: CLI, --disable-sigusr1

Exposure of sensitive information (CWE-552)

The guide’s example of this CWE is a publishing accident: when you publish a package, everything in the current directory is pushed to the npm registry unless a mechanism excludes it. A .env file, a notes.txt, a private key or a local database ends up in a public tarball, and once somebody has downloaded it you cannot take it back. There are two mechanisms: a blocklist (the ignore files .npmignore and .gitignore) and an allowlist, the files field in package.json. The allowlist is the safer default because a new file is excluded until somebody opts it in. The guide’s checklist is to review what will be published with a dry run, maintain the ignore files, and unpublish in case of an exposure.

The check is one command, and it is worth running in CI: it prints exactly what would be in the tarball without publishing anything. The package here has a .env and a notes.txt next to dist/ and a files allowlist; only the allowlisted file (and package.json, which npm always includes) is listed.

An allowlist in package.json and a dry run
{
  "name": "@example/bookshelf-lib",
  "version": "1.0.0",
  "type": "module",
  "exports": "./dist/index.js",
  "files": ["dist"]
}

The same principle applies to every channel a secret can leak through: keep secrets in the environment (loaded with --env-file, see CLI Options, Environment & Config File), keep the .env file out of version control and Docker build contexts, never put them in URLs (they end up in logs and proxies), and never log them. The CLI reference lists report options such as --report-exclude-env for diagnostic reports, and --no-extra-info-on-fatal-exception hides extra detail on fatal exceptions; the handling of secrets in code is the subject of Crypto, Passwords & Secrets.

HTTP request smuggling (CWE-444)

Smuggling needs two HTTP servers, typically a proxy in front and Node.js behind it. If the front end and the back end read the same bytes as different requests (for example because a message carries both Content-Length and Transfer-Encoding), an attacker can hide a second request inside the first one: the proxy never sees it, the application does, and the proxy’s checks are bypassed. Whether a given case is a Node.js vulnerability depends on the specification: if Node.js interprets the message consistently with RFC 7230, then it is not considered a bug in Node.js, and the fix belongs in the front end (or in both).

The guide’s mitigations are: never enable insecureHTTPParser when creating an HTTP server, configure the front-end server to normalise ambiguous requests, monitor for new smuggling vulnerabilities in both Node.js and the front end, and use HTTP/2 end to end where possible (and disable HTTP downgrading). The leniency flag exists for interoperability with non-conformant clients; the CLI reference lists what it accepts, including a message that has both Transfer-Encoding and Content-Length. The experiment sends exactly that ambiguous message to a strict server (the default) and to one with the flag on.

The strict parser rejects an ambiguous message (smuggle.mjs)
import http from 'node:http';
import net from 'node:net';

// insecureHTTPParser defaults to false: leave it that way.
const strict = http.createServer({ insecureHTTPParser: false }, (req, res) => res.end('handled\n'));
const lenient = http.createServer({ insecureHTTPParser: true }, (req, res) => res.end('handled\n'));

// An ambiguous message: both Content-Length and Transfer-Encoding.
const ambiguous =
  'POST / HTTP/1.1\r\nHost: localhost\r\nContent-Length: 4\r\nTransfer-Encoding: chunked\r\nConnection: close\r\n\r\n0\r\n\r\n';

function send(server) {
  return new Promise((resolve) => {
    server.listen(0, '127.0.0.1', () => {
      const c = net.connect(server.address().port, '127.0.0.1', () => c.write(ambiguous));
      let data = '';
      c.on('data', (d) => (data += d));
      c.on('close', () => { server.close(); resolve(data.split('\r\n')[0]); });
    });
  });
}
console.log('strict parser :', await send(strict));
console.log('lenient parser:', await send(lenient));
Output (identical on Node.js 26, 24 and 22)
strict parser : HTTP/1.1 400 Bad Request
lenient parser: HTTP/1.1 200 OK

Source: Node.js Learn: Security Best Practices, HTTP Request Smuggling, Node.js API: CLI, --insecure-http-parser

The second row is the point: the lenient parser accepted the ambiguous request, and a proxy that treats it differently is the opening smuggling needs. Run the strict parser, and see Server Timeouts, Limits & Hardening for the proxy side (keep-alive alignment and who the client is).

Information exposure through timing attacks (CWE-208)

A timing attack learns a secret from how long the application takes to respond. It is not specific to Node.js; it is possible whenever a secret is used in a timing-sensitive operation. The guide’s example is a login: comparing the submitted password with the stored one using the built-in string comparison returns at the first differing character, so each additional correct prefix makes the response a little slower, and an attacker who can send many requests can recover the value.

The guide’s mitigations are crypto.timingSafeEqual(), which compares two values with a constant-time algorithm, and scrypt for passwords; more generally, avoid branching on secrets, and avoid using a secret as an index into memory when an attacker could share the machine. It adds that writing constant-time code in JavaScript is hard (partly because of the JIT), so use the built-in crypto APIs or WebAssembly rather than rolling your own. Three details trip people up. timingSafeEqual() throws ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH when the two inputs have different byte lengths, so hash both sides to a fixed size (or compare fixed-length digests) before comparing. The function does not turn a weak secret into a strong one. And a recently discovered case shows the lesson at the runtime level: the March 2026 security release fixed a non-constant-time comparison in the native HMAC verification code (CVE-2026-21713), which is a reminder to keep Node.js patched and to use the current APIs rather than hand-built ones.

Constant-time comparison for API keys, webhook signatures and passwords (timing.mjs)
import { createHash, createHmac, randomBytes, scrypt, timingSafeEqual } from 'node:crypto';
import { promisify } from 'node:util';

const scryptAsync = promisify(scrypt);

// 1. Compare secrets of unknown length: hash both sides to a fixed size first,
//    because timingSafeEqual() throws when the lengths differ.
function safeEqual(a, b) {
  const da = createHash('sha256').update(a).digest();
  const db = createHash('sha256').update(b).digest();
  return timingSafeEqual(da, db);
}

// 2. Verify an HMAC webhook signature in constant time.
const secret = randomBytes(32);                 // in real code: read from process.env
const body = '{"event":"book.created"}';
const signature = createHmac('sha256', secret).update(body).digest();
const received = Buffer.from(signature.toString('hex'), 'hex');   // what the client sent, decoded from its header
console.log('hmac ok:', timingSafeEqual(createHmac('sha256', secret).update(body).digest(), received));

// 3. Passwords: store a salted scrypt hash with its cost parameters, never the password, and compare in constant time.
//    N = 2^17, r = 8, p = 1 is the OWASP minimum; it needs about 128 MiB, so maxmem is raised above its 32 MiB default.
const SCRYPT = { N: 2 ** 17, r: 8, p: 1 };
const MAXMEM = 256 * 1024 * 1024;
async function hashPassword(password) {
  const salt = randomBytes(16);
  const key = await scryptAsync(password.normalize('NFKC'), salt, 64, { ...SCRYPT, maxmem: MAXMEM });
  return `scrypt$${SCRYPT.N}$${SCRYPT.r}$${SCRYPT.p}$${salt.toString('hex')}$${key.toString('hex')}`;
}
async function verifyPassword(password, stored) {
  const [, N, r, p, saltHex, keyHex] = stored.split('$');  // the stored parameters, so they can be raised later
  const expected = Buffer.from(keyHex, 'hex');
  const key = await scryptAsync(password.normalize('NFKC'), Buffer.from(saltHex, 'hex'), expected.length,
    { N: Number(N), r: Number(r), p: Number(p), maxmem: MAXMEM });
  return timingSafeEqual(key, expected);
}

Malicious third-party modules and the supply chain (CWE-1357)

Node.js treats the code it is asked to run, dependencies included, as trusted, so a malicious dependency is not a Node.js vulnerability. It is nevertheless, in the words of the guide, one of the most critical application-level risks. The reason is structural: any package in node_modules runs with the full privileges of your process. It can read the file system, open sockets, read process.env (where your database password lives), call eval(), and write files that will be loaded later. The guide gives two typical stories: a maintainer account of a popular logging library is compromised and a new minor version sends environment variables to a remote server when the logger initialises, and a typosquatted package with a name close to a well-known framework runs a postinstall script that uploads SSH keys.

A supply chain attack is the general form: one of your direct or transitive dependencies is compromised, and your application picks the bad version up because the specification was too lax (a range that admits new versions) or contained a typo. The guide lists the attack vectors: typosquatting, lockfile poisoning, compromised maintainers, malicious packages and dependency confusion. It also makes a point that is easy to miss: pinning a dependency to an exact version does not pin its transitive dependencies, so exact versions in package.json are not enough; only a lockfile pins the whole tree.

The baseline: lockfile, npm ci, audit and signatures

The guide’s mitigations map onto a handful of commands. A cool-down with min-release-age

Memory access violation (CWE-284)

Memory-based attacks depend on a combination of memory-management errors and an exploitable allocator. Like every runtime, Node.js is exposed to them if the application shares a machine with code you do not control, and the guide offers two mitigations: do not run production applications on shared machines, and consider the secure heap. --secure-heap=n initialises an OpenSSL secure heap of n bytes, which OpenSSL uses for selected allocations during key generation and other operations, so that sensitive material is not exposed by pointer overruns and underruns. The heap is fixed in size and cannot be resized at run time, n must be a power of two (anything below 2 disables it), and --secure-heap-min=n sets the minimum allocation. It is disabled by default, and not available on Windows. Size it generously: when it is full, allocations fall back to ordinary memory.

crypto.secureHeapUsed() reports the state, so you can check that the flag took effect and watch utilisation.

Monkey patching (CWE-349)

Monkey patching modifies properties at run time to change existing behaviour. In an application it is a legitimate (if risky) technique; in a hostile dependency it is a way to change what Array.prototype.push, JSON.parse or a built-in module method does for the whole process, without touching your code. The guide’s mitigation is --frozen-intrinsics, which recursively freezes the built-in JavaScript objects and functions. The CLI reference marks it Stability 1 (Experimental): only the root context is supported, there is no guarantee that globalThis.Array is the default intrinsic, and code (including libraries) may break under it. To let polyfills work, --require and --import modules run before the intrinsics are frozen.

The guide points out the limit as well: freezing the intrinsics does not prevent defining new globals or replacing existing ones through globalThis; for that, freeze globalThis too with Object.freeze(globalThis). The experiment runs both: after --frozen-intrinsics, replacing Array.prototype.push throws a TypeError; without the flag the replacement succeeds. After Object.freeze(globalThis), replacing globalThis.Array throws as well.

Prototype pollution (CWE-1321)

Prototype pollution abuses __proto__, constructor, prototype and the other properties inherited from built-in prototypes to inject properties into every object of a type. The attacker needs a path where untrusted input is merged into an object: a deep merge, a "set by path" helper, or a configuration loader. The guide gives the canonical snippet (a JSON.parse result containing a __proto__ key, merged with Object.assign) and two effects: logic bugs, such as an isAdmin-style check that now passes for every object, and denial of service, such as hasOwnProperty stopping to exist after a null prototype is assigned. The guide notes that Node.js core does not count prototype pollution caused by attacker-controlled input as its own vulnerability, because the input comes from application code; it is a language characteristic that libraries and applications must defend against, as real examples show (CVE-2018-3721 in a popular utility library, CVE-2018-16487 for insecure recursive merges, CVE-2022-21824 in Node.js itself).

The mitigations in the guide are: avoid insecure recursive merges, validate untrusted input against a JSON schema, create dictionaries without a prototype (Object.create(null)), freeze prototypes (Object.freeze(MyObject.prototype)), run with --disable-proto, check own properties with Object.hasOwn(), and avoid methods inherited from Object.prototype. The experiment first shows the vulnerable merge, then a safer one that skips the dangerous keys and writes into prototype-less objects.

A vulnerable merge, a safer merge, and prototype-less dictionaries (polluted.mjs)
const payload = '{"__proto__": {"isAdmin": true}, "title": "Dune"}';

// Vulnerable: a recursive merge that walks into "__proto__".
function unsafeMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (typeof source[key] === 'object' && source[key] !== null) {
      target[key] ??= {};
      unsafeMerge(target[key], source[key]);
    } else {
      target[key] = source[key];
    }
  }
  return target;
}
unsafeMerge({}, JSON.parse(payload));
console.log('after unsafe merge, {}.isAdmin =', ({}).isAdmin);   // true: every object is polluted
delete Object.prototype.isAdmin;

// Safer: skip dangerous keys, or build data objects without a prototype.
const FORBIDDEN = new Set(['__proto__', 'constructor', 'prototype']);
function safeMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (FORBIDDEN.has(key)) continue;
    const value = source[key];
    if (typeof value === 'object' && value !== null && !Array.isArray(value)) {
      target[key] = safeMerge(Object.hasOwn(target, key) ? target[key] : Object.create(null), value);
    } else {
      target[key] = value;
    }
  }
  return target;
}

Uncontrolled search path element (CWE-427)

Node.js resolves modules by the Module Resolution Algorithm and assumes that the directory in which a module is requested is trusted. Injection: commands, SQL and paths

The official guide’s threat list does not have a section for injection, but it is the most common way real Node.js applications get compromised, and the guide’s own theme (untrusted input must not become code) applies. Three cases cover most of it, and each has one rule.

For commands, never build a shell string from input. child_process.execFile() and spawn() take an argument array, and with no shell involved there is nothing to interpret ;, $() or backticks. The trap is to add shell: true "to make it work": the arguments are then only concatenated, not escaped, which is why passing an args array together with the shell option is DEP0190 (documentation-only since v23.11.0 and v22.15.0, a runtime deprecation since v24.0.0). Pick the program from an allowlist, never from input.

For SQL, bind values with placeholders and never splice them into the statement; table and column names cannot be bound, so choose them from an allowlist too. The example uses the built-in node:sqlite (Stability 1.2, Release candidate; it still prints an ExperimentalWarning on Node.js 22.23.3), but every driver offers the same thing: ? or $1 placeholders.

For paths, resolve the input against a base directory and check that the result is still inside it before opening anything. A string startsWith() check on the unresolved input is not enough, and a bare rel.startsWith('..') rejects a legitimate file called ..notes, so the check below compares against the separator.

Argument arrays, parameterised queries and an allowlist (inject.mjs)
import { execFile } from 'node:child_process';
import { promisify } from 'node:util';
import { DatabaseSync } from 'node:sqlite';

const run = promisify(execFile);
const userInput = 'Dune; echo INJECTED';

// Command injection: pass arguments as an array. There is no shell to interpret ";".
const { stdout } = await run(process.execPath, ['-p', 'process.argv[1]', userInput]);
console.log('argv value:', stdout.trim());

// The shell form concatenates a string, so the same input would run a second command (shown here
// only as text; never build commands like this):
console.log('unsafe form would run: echo ' + userInput);

// An allowlist for the program itself, never taken from user input:
const ALLOWED = new Set(['git', 'node']);

The vm module is not a sandbox

node:vm lets you compile and run code in a separate V8 context with its own global object, and that sounds like isolation. The documentation is blunt: the module is not a security mechanism, and you must not use it to run untrusted code. The context object you pass in is made from the host realm, so any code inside can walk up its constructor chain to the host’s Function constructor and from there to process. The timeout option only limits how long synchronous code runs; it does not prevent anything else.

The escape in two lines, and why timeouts are not isolation (vm.mjs)
import vm from 'node:vm';

// The context object looks empty, but code inside it can reach the host realm through
// any object that was created outside the sandbox, including the context object itself.
const sandbox = vm.createContext({});
const leaked = vm.runInContext(`this.constructor.constructor('return typeof process')()`, sandbox);
console.log('process visible inside the "sandbox":', leaked);

const hostRealm = vm.runInContext(`this.constructor.constructor('return typeof process.pid')()`, sandbox);
console.log('host process.pid reachable:', hostRealm);

// vm timeouts only bound synchronous CPU time; they do not isolate anything.
try { vm.runInNewContext('while (true) {}', {}, { timeout: 50 }); } catch (e) { console.log(e.code); }
Output (identical on Node.js 26, 24 and 22)
process visible inside the "sandbox": object
host process.pid reachable: number
ERR_SCRIPT_EXECUTION_TIMEOUT

Source: Node.js API: VM

The practical rule: use node:vm for what it was built for (evaluating your own trusted code in a controlled global scope, for example a templating or REPL feature) and never as a boundary. If you must run untrusted code, give it a separate process (or container, or virtual machine) with no secrets, a read-only file system, no network and resource limits; a worker_threads worker is not a security boundary either, because it shares the process. The Permission Model can restrict what a whole process may do, and is covered next. --disallow-code-generation-from-strings is complementary and independent of vm:

The Permission Model: a seat belt, not a sandbox

The official guide ends the threat list by pointing at the Permission Model, which limits what a given process may do at run time: file-system reads and writes, child processes, worker threads, native addons, WASI, and (since Node.js 25, as an Active-development feature) network access. Its value for this page is containment: even trusted code is stopped from doing things you did not grant, so a compromised dependency that tries to read ~/.ssh or spawn a shell fails with ERR_ACCESS_DENIED instead of succeeding. It is a seat belt for mistakes and for supply-chain surprises, and not a sandbox for hostile code: the project’s own security releases in 2026 fixed several bypasses (see Security releases and reporting), and the guide’s threat model still treats the process as a trust boundary you must otherwise defend.

Starting with nothing and granting one file (perm.mjs)
import { readFileSync } from 'node:fs';
console.log('read own file:', readFileSync(new URL(import.meta.url)).length > 0);
console.log('has fs.read for /etc:', process.permission.has('fs.read', '/etc/hosts'));
try { readFileSync('/etc/hosts'); } catch (e) { console.log(e.code); }
Run with --permission and one --allow-fs-read grant (identical on Node.js 26, 24 and 22)
node --permission --allow-fs-read="$PWD/perm.mjs" perm.mjs
Output
read own file: true
has fs.read for /etc: false
ERR_ACCESS_DENIED

Source: Node.js API: Permissions, Node.js API: CLI, --permission

Every flag, the audit mode, the config-file block and the limits are in The Permission Model. Two operational points belong here: grant the narrowest paths that work (a directory per concern, not *), and combine it with the other layers on this page rather than relying on it alone.

Security releases and reporting

Everything above reduces the risk, but the runtime itself has vulnerabilities, and the control that matters most is applying fixes. The Node.js project publishes security releases through a documented process, and the release lines you can run are listed in Release Lines & LTS. Only the Current, Active LTS and Maintenance lines receive them: on the dates checked for this page that was Node.js 26, 24 and 22. Anything older (Node.js 20 reached end of life on 2026-04-30, Node.js 25 on 2026-06-01) gets no fixes, whatever your application does.

Table 6. How a Node.js security report is handled (from the security reporting policy)
Stage What happens

Report

Report security bugs in Node.js through HackerOne. The page notes that submitting there requires a minimum Signal score of 1.0, and otherwise to contact the security release stewards through the OpenJS Foundation Slack. Reports are normally acknowledged within 5 days and receive a more detailed answer within 10 days.

Embargo

An embargo date is chosen and a CVE is requested. Typically the embargo is 72 hours from when the CVE is issued, but it can vary with the severity or the difficulty of the fix.

On the embargo date the announcement goes to the security mailing list, the changes are pushed to the public repository, and builds are deployed to nodejs.org. The advisory appears on the Node.js blog within 6 hours of the mailing list being notified.

Pitfalls

Table 9. Common mistakes
Mistake Better

Treating node:vm or a worker as a sandbox

Use a separate process or container with no secrets and no network; see The vm module is not a sandbox.

Comparing secrets with ===, or calling timingSafeEqual() on values of different lengths

Hash both sides to the same length and compare digests with crypto.timingSafeEqual().

Adding shell: true to execFile() or spawn() with an argument array

Remove the shell; pass the array; allowlist the program (DEP0190).

Pinning one dependency to an exact version and calling it safe

Exact versions do not pin transitive dependencies; commit the lockfile and install with npm ci.

Running npm install in CI and Docker

Run npm ci so that a changed package.json or lockfile fails the build instead of resolving new versions.

Allowing every install script because one package needs it

On npm 12 approve the single package with a pinned version; on older npm run --ignore-scripts and the one script by hand.

Setting min-release-age and then blocking a security fix

Add the package to min-release-age-exclude or override for that command, and review the fix.

Starting the service with --inspect=0.0.0.0 "just for a minute"

Keep the inspector on localhost and tunnel to it; add --disable-sigusr1 or a SIGUSR1 listener.

Enabling insecureHTTPParser to make a client work

Fix the client or the proxy; leave the parser strict.

Merging request bodies into configuration with a recursive helper

Validate with a schema, skip __proto__, constructor and prototype, or use prototype-less objects.

Publishing from a directory that contains .env and no files allowlist

Add files, run npm pack --dry-run in CI.

Using --frozen-intrinsics in production without testing

It is Experimental and breaks some libraries; try it in staging with the full test suite.

Relying on the Permission Model alone

Treat it as one layer; keep patching, since 2026 brought several bypass fixes.

Where the books are outdated

Two books were consulted for this section: Efficient Node.js by Samer Buna (O’Reilly, 2025) and Node.js Projects by Jonathan Wexler (O’Reilly, 2025). Neither covers the application security landscape described here, and the points below should be checked against the official documentation instead of the books.

Table 11. Where the books fall short on security
Topic Current state

Supply chain

Neither book covers npm ci, lockfile review, npm audit and npm audit signatures, min-release-age, or the npm 12 install-script policy. Treat these as required, not optional, today.

Permission Model

Efficient Node.js describes it as something being introduced; it is stable (--permission, --allow-fs-read, --allow-fs-write, --allow-child-process, --allow-worker), with --allow-net since Node.js 25 as an active-development feature.

Child processes

Passing an argument array together with shell: true is deprecated (DEP0190) and a runtime deprecation since Node.js 24.0.0; use argument arrays without a shell.

Password handling and secrets (Node.js Projects)

The password-manager project and several examples store or compare secrets in ways that are unsafe by today’s guidance: no plain-text storage, no hard-coded or fallback secrets, constant-time comparison, a high, tuned cost for key derivation (scrypt or argon2), authenticated encryption, and --env-file rather than committed .env files.

Web application protections (Node.js Projects)

The web examples lack CSRF protection, rate limiting and safe cookie flags, and one example used a view-engine release with a known vulnerability (CVE-2022-29078); verification links should carry a random token, not an email address, and database access lists should not allow all addresses.
