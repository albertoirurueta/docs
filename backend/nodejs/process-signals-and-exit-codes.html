Process, Signals & Exit Codes

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Node.js 26 (26.10.0, released 2026-09-21, the Current line that becomes LTS on 2026-10-28), with the differences of Node.js 24 "Krypton" (24.21.0, Active LTS) and Node.js 22 "Jod" (22.23.3, Maintenance) called out; versions and stability levels were checked against the official documentation on 2026-10-03, and every example below was run on all three lines unless the text says otherwise. The examples were run on macOS (arm64), so a few observations are labelled as such: signal numbers, pipe buffer sizes and the way a shell reports a killed process differ between operating systems.

Every Node.js program is a process, and the global process object is the program’s handle on it: what it was started with, what it is allowed to see, how much it uses, and how it ends. This page covers three connected topics. First the identity of the process: arguments, environment variables, the working directory, the process id, the platform, memory and high-resolution time. Second the ending of the process: exit codes, process.exitCode versus process.exit(), and the 'beforeExit' and 'exit' events. Third the conversation with the outside world while the process runs: signals, graceful shutdown, and the last-resort error handlers. It closes with the two newest corners of the object: process.getBuiltinModule() and process.features. How the loop decides that a process is finished is explained in The Event Loop; the error classes and the error.code values that end up in these handlers are in Errors & Error Handling; the language-level view of exceptions is JavaScript Exception Handling. The running scenario is the Bookshelf application that grows across this section, whose architecture is described in Introduction & Architecture.

What the process object is

process is a global, an instance of EventEmitter (see Events & EventEmitter), and the module node:process exports the same object. Prefer the import in modules that you want to read like a dependency list; the global is identical. Underneath, lib/process.js and its siblings are the JavaScript layer, and the C++ bindings call into the operating system through libuv for the parts that must be portable: the signal watchers, the high-resolution clock, the memory queries (process.availableMemory() and process.constrainedMemory() are documented in terms of libuv’s uv_get_available_memory and uv_get_constrained_memory) and the exit path. Two consequences are worth keeping in mind. The object describes one operating system process, so in a worker thread (see Worker Threads) several members change meaning: process.exit() stops the worker thread, not the process; signal events are not available; process.env is a copy; and a few POSIX identity functions such as process.initgroups() are not available. And it is the one object that mixes read-only facts (pid, platform), live measurements (memoryUsage()), settings (exitCode, title) and actions (kill(), exit()), so the sections below group it by purpose.

The working directory

Environment variables

process.env is an object that exposes the environment the process was started with. It looks like an ordinary object and behaves like a thin wrapper over the C-level environment, with rules that surprise people coming from objects:

  • Values are always strings. Assigning a number, a boolean, null or undefined stores its string form, so env.DEBUG_SQL = false stores the truthy string "false" and env.X = undefined stores the text "undefined". The documentation calls the implicit conversion deprecated (DEP0104, documentation-only since v10.0.0) and says a future version may throw for anything that is not a string, number or boolean.

  • A missing variable is undefined, and the only way to remove one is delete env.NAME.

  • Changes stay in the process and its children. They are inherited by child processes started afterwards (unless you pass your own env option) but never reach the parent shell: node -e 'process.env.foo = "bar"' && echo $foo prints an empty line.

  • Names are case-insensitive on Windows only; on every other platform Path and PATH are different variables.

  • Worker threads get a copy of the parent’s process.env by default (since v11.14.0), configurable with the env option of Worker; only the main thread can change the real environment.

The rules of process.env, one by one
import { env, loadEnvFile } from 'node:process';
import { spawnSync } from 'node:child_process';

// 1. Values are always strings
env.RETRIES = 3;
env.DEBUG_SQL = false;
console.log(typeof env.RETRIES, JSON.stringify(env.RETRIES), JSON.stringify(env.DEBUG_SQL));
console.log('"false" is truthy:', Boolean(env.DEBUG_SQL));

// 2. Missing keys are undefined; use delete, never assign undefined
env.TOKEN_HINT = undefined;
console.log('assigned undefined ->', JSON.stringify(env.TOKEN_HINT));
delete env.TOKEN_HINT;
console.log('after delete       ->', env.TOKEN_HINT, '| in:', 'TOKEN_HINT' in env);

// 3. Parse deliberately, with a default
const port = Number.parseInt(env.PORT ?? '3000', 10);
const verbose = env.VERBOSE === '1' || env.VERBOSE === 'true';
console.log({ port, verbose });

// 4. Changes are visible to children, never to the parent shell
env.BOOKSHELF_MODE = 'child-sees-this';
const child = spawnSync(process.execPath, ['-p', 'process.env.BOOKSHELF_MODE'], { encoding: 'utf8' });
console.log('child printed:', child.stdout.trim());

// 5. Pass an explicit environment to a child instead of mutating your own
const clean = spawnSync(process.execPath, ['-p', '[process.env.ONLY_THIS, process.env.HOME].join()'], {
  encoding: 'utf8',
  env: { PATH: env.PATH, ONLY_THIS: '1' },
});
console.log('clean child sees ONLY_THIS,HOME ->', clean.stdout.trim());

Resident set size: the memory of the whole process held in RAM, including the V8 heap, the code, native objects and buffers. In a worker thread it is still the value for the entire process.

heapTotal, heapUsed

V8’s allocated and used heap (JavaScript objects). In a worker thread they refer to that thread only.

High-resolution time

process.hrtime.bigint() returns the current high-resolution real time in nanoseconds as a bigint. It is relative to an arbitrary point in the past, unrelated to the time of day, and therefore monotonic: it is not affected by clock drift or by someone changing the system clock. Use it, or performance.now() (milliseconds with a fraction, monotonic, relative to the process start), to measure durations; use Date.now() only when you need a calendar time. The old process.hrtime() that returns a [seconds, nanoseconds] pair is 3 Legacy: it still works and its time argument allows a diff, but with bigint the difference is plain subtraction. Convert to milliseconds with Number(elapsedNs) / 1e6 once the subtraction is done, never before, because a bigint cannot be mixed with a number in arithmetic.

Measuring an interval with a monotonic clock
import { hrtime } from 'node:process';
import { setTimeout as sleep } from 'node:timers/promises';
import { performance } from 'node:perf_hooks';

const t0 = hrtime.bigint();           // monotonic, nanoseconds, bigint
const wall0 = Date.now();             // wall clock, can jump when NTP or the user changes the clock
const p0 = performance.now();         // monotonic, milliseconds since process start, fractional

await sleep(50);

const elapsedNs = hrtime.bigint() - t0;
console.log('type            :', typeof elapsedNs);
console.log('>= 49 ms        :', elapsedNs >= 49_000_000n);
console.log('as milliseconds :', Number(elapsedNs) / 1e6 >= 49);
console.log('Date.now delta  :', Date.now() - wall0 >= 49);
console.log('performance.now :', performance.now() - p0 >= 49);

// Legacy tuple form: [seconds, nanoseconds]
const [s, ns] = hrtime();
console.log('legacy tuple    :', Number.isInteger(s), Number.isInteger(ns));

How a process ends: exit codes

A process ends in one of four ways: the event loop runs out of work (a natural exit), your code calls process.exit(), an error nobody handles, or a signal. The result that other programs see is an exit status, a small integer: 0 means success, anything else means failure, and shells, CI systems, npm run, docker run and orchestrators all key off that number. Node.js uses the following codes itself.

process.exitCode versus process.exit()

Both set the status, and they differ in one important way: process.exitCode = n records the status and lets the process finish its work, while process.exit(n) ends the process right now, synchronously, after the 'exit' listeners run. Anything still queued is abandoned: pending timers, in-flight network requests, a database connection waiting to be closed, and output that has been handed to a stream but not yet flushed. The Node.js documentation warns specifically about the last one, because writes to process.stdout and process.stderr are asynchronous for pipes on POSIX.

Same 4 MiB of output, two ways of ending (observed on macOS with stdout connected to a pipe)
import { spawnSync } from 'node:child_process';
import { execPath } from 'node:process';

const writer = (ending) => `
  process.stdout.write('x'.repeat(4 * 1024 * 1024));   // 4 MiB of output
  ${ending}
`;

for (const [label, ending] of [
  ['process.exit(1)      ', 'process.exit(1);'],
  ['process.exitCode = 1 ', 'process.exitCode = 1;'],
]) {
  const { stdout, status } = spawnSync(execPath, ['-e', writer(ending)], { maxBuffer: 16 * 1024 * 1024 });
  console.log(label, 'status', status, '| bytes received:', stdout.length);
}
Output on Node.js 26, 24 and 22
process.exit(1)       status 1 | bytes received: 65536
process.exitCode = 1  status 1 | bytes received: 4194304

With process.exit(1) the reader got only the first 65536 bytes, the size of the operating system’s pipe buffer here; the rest was lost. Setting process.exitCode delivered all of it. The exact byte count is platform and load dependent and is an observation, not a guarantee; the loss is the documented behaviour. On Windows pipes are synchronous, so the same program would not lose data there in this way; that is how such bugs reach production: the code was tested on one platform and run on another.

The rules that follow from this:

  • In ordinary code set process.exitCode and return. Make the program finish by running out of work, which also guarantees that streams are flushed and 'exit' and 'beforeExit' fire.

  • If you must stop on an error, throw it. The documentation calls an uncaught error that terminates the process safer than process.exit().

  • Call process.exit() only at the very edge: in a CLI after the final output has been written and flushed, after you have closed what needs closing, or in a watchdog that fires when graceful shutdown has taken too long (see graceful shutdown).

  • Never call process.exit() in a library. It takes a decision that belongs to the application. Throw, reject or emit an error instead.

  • Do not pass anything but an integer or an integer string. Since v20.0.0 other values throw ERR_INVALID_ARG_TYPE (strings like 'abc', objects) or ERR_OUT_OF_RANGE (1.5), both of which were observed.

process.finalization: cleanup tied to an object’s lifetime

process.finalization.register(ref, callback) (Stability 1.1, Active development, added in v22.5.0) arranges for callback(ref, event) to run when the process emits 'exit', but only if ref has not been garbage collected by then; registerBeforeExit() does the same for 'beforeExit', and unregister(ref) cancels it. It exists so that a resource owner can promise "my temporary files are removed when the process ends" without being kept alive forever by the registration. The documentation lists the rules: pass a plain function, not an arrow function that closes over this (the closure would keep the object reachable), do the work synchronously, and do not rely on it for critical resources because the callback is not guaranteed to run in every circumstance. The first call prints an ExperimentalWarning even on Node.js 26.

Releasing a resource at exit unless the owner was collected first
import { finalization } from 'node:process';

class TempWorkspace {
  constructor(name) {
    this.name = name;
    // Pass a plain function and the object as `ref`; do not close over `this`.
    finalization.register(this, (ws, event) => ws.dispose(event));
  }
  dispose(event) {
    console.log(`cleaning up ${this.name} on ${event}`);   // synchronous work only
  }
}

Signals

A signal is a small message the operating system delivers to a process asynchronously: a user pressing Ctrl+C, a supervisor stopping a service, another process calling kill. Each signal has a default action (usually "terminate"), and a program may replace the default with its own handler. In Node.js a handler is simply an event listener on process whose name is the signal: process.on('SIGTERM', fn). The handler receives the signal name as its first argument, so one function can serve several signals.

The facts that matter in practice, from the official documentation and from running the examples:

SIGUSR1: the inspector’s signal

SIGUSR1 is reserved by Node.js: on a POSIX system, sending it to a running process starts the inspector and prints the address a debugger can connect to, without having restarted the process with --inspect. That is a lifesaver for a service already misbehaving in production, and a security concern in the wrong environment, because anyone who can signal the process (the same user, or root) can open a debugging port that allows arbitrary code execution. Control it deliberately:

  • --disable-sigusr1 (stable since v24.8.0 and v22.20.0) turns the feature off.

  • The permission model (--permission) does not create the listener at all.

  • Bind the inspector to localhost (the default is 127.0.0.1:9229) and tunnel to it; never expose it.

  • Do not install your own SIGUSR1 handler: you may break the debugger. Use SIGUSR2 for your own purposes.

Containers and PID 1

A container’s main process is PID 1, and Linux gives that process special treatment: the only signals that can be sent to PID 1 are those for which it has explicitly installed a handler (see kill(2)). Graceful shutdown

A graceful shutdown answers a signal by finishing what it started and refusing new work: stop accepting connections, let requests in flight complete, close the database pool and the queue consumers, flush logs, then end with a meaningful status. Every supervisor sends a signal first and a hard kill later, so the program has a budget measured in seconds. The pattern has four parts, and the example below implements them in about forty lines for the Bookshelf server:

  • Register one handler per signal (SIGINT for the developer’s Ctrl+C, SIGTERM for the platform) and make it idempotent: a second signal while shutting down must not start the work again.

  • Run the cleanup asynchronously and set process.exitCode, then let the loop drain. Do not call process.exit() from the happy path.

  • Add a watchdog timer that calls process.exit(1) if cleanup takes longer than the grace period. unref() it so that it never keeps a finished process alive.

  • Close the HTTP server in two steps: server.close() stops accepting connections and, since v19.0.0, also closes idle keep-alive connections; server.closeAllConnections() after a short deadline cuts those that are still busy (an upload, a stream, a stalled client).

A reusable shutdown helper (shutdown.js) for the Bookshelf server
import process from 'node:process';
import { once } from 'node:events';

/**
 * Run `cleanup` once, on the first of the given signals, then let the process
 * exit by itself with the conventional 128 + signal number status.
 */
export function onShutdown(cleanup, { signals = ['SIGINT', 'SIGTERM'], graceMs = 10_000 } = {}) {
  let started = false;

  const handler = async (signal) => {
    if (started) return;                         // ignore repeated signals
    started = true;
    console.log(`${signal} received, shutting down`);

    const watchdog = setTimeout(() => {          // last resort if cleanup hangs
      console.error('graceful shutdown timed out');
      process.exit(1);
    }, graceMs);
    watchdog.unref();                            // never keeps the process alive by itself

    try {
      await cleanup(signal);
      process.exitCode = 128 + signalNumber(signal);
    } catch (err) {
      console.error('cleanup failed:', err.message);
      process.exitCode = 1;
    }
  };

  for (const signal of signals) process.on(signal, handler);
  return () => { for (const signal of signals) process.off(signal, handler); };
}

function signalNumber(name) {
  return { SIGHUP: 1, SIGINT: 2, SIGTERM: 15 }[name] ?? 0;
}

/** Stop accepting connections, close idle ones, force-close the rest after a deadline. */
export async function closeServer(server, forceAfterMs = 2_000) {
  const closed = once(server, 'close');
  server.close();                                // stop accepting; closes idle keep-alive sockets
  const timer = setTimeout(() => server.closeAllConnections(), forceAfterMs);
  timer.unref();
  await closed;
  clearTimeout(timer);
}

Last-resort handlers: uncaughtException and unhandledRejection

The details of error handling belong to Errors & Error Handling; the process-level hooks matter here because they decide the exit status.

  • 'uncaughtException' fires when a JavaScript exception reaches the event loop uncaught. Without a listener Node.js prints the stack and exits with code 1, overriding any exitCode. With a listener the default is replaced, and the process continues and exits with 0 unless you set process.exitCode. The documentation calls the event "a crude mechanism …​ intended to be used only as a last resort"; the application is in an undefined state, so the correct use is synchronous cleanup followed by a controlled exit, and an external supervisor restarts the service.

  • 'uncaughtExceptionMonitor' is called first, with the same arguments, and does not change the outcome: use it for logging and metrics. The origin argument says whether the error came from a synchronous throw ('uncaughtException') or from a rejection ('unhandledRejection').

  • 'unhandledRejection' fires when a promise is rejected and no handler is attached within a turn of the loop. Since v15.0.0 the default mode is throw: if no listener handles the event, the rejection is raised as an uncaught exception. --unhandled-rejections=<mode> changes it.

  • process.setUncaughtExceptionCaptureCallback() is the lower-level hook that tools use (and process.addUncaughtExceptionCaptureCallback(), Experimental since v25.9.0, allows several).

process.getBuiltinModule()

process.getBuiltinModule(id) returns a built-in module synchronously and without an import statement, or undefined when id is not a built-in. It was added in v22.3.0 and v20.16.0 for code that must run in several environments: an ES module that does import fs from 'node:fs' fails to load in a browser or another runtime, a dynamic import() makes the module asynchronous, and require does not exist in ES modules. With getBuiltinModule the same file can ask "am I in Node.js?" and load what it needs in one synchronous step. It accepts the ids that module.isBuiltin(id) recognises, with or without the node: prefix, but modules that exist only under the prefix (node:test, node:sqlite, node:sea) must be requested with it. And it always returns the real built-in even if code has tampered with require.cache for the bare id, which makes it a small defence against monkey-patching.

Portable feature detection, and the difference from require
import { createRequire } from 'node:module';

// 1. Synchronous access to built-ins from an ES module, no import needed
const fs = process.getBuiltinModule('node:fs');
console.log('node:fs readFileSync  :', typeof fs.readFileSync);
console.log('bare id also works    :', process.getBuiltinModule('fs') === fs);
console.log('unknown id            :', process.getBuiltinModule('left-pad'));
console.log('"test" needs a prefix :', process.getBuiltinModule('test'), typeof process.getBuiltinModule('node:test'));

// 2. Portable code: works in Node.js and in runtimes without a `process` global
const isNode = typeof globalThis.process?.getBuiltinModule === 'function';
const { hostname } = isNode ? globalThis.process.getBuiltinModule('node:os') : { hostname: () => 'unknown' };
console.log('portable hostname call:', typeof hostname());

// 3. It returns the real built-in even if code tampers with require.cache
const require = createRequire(import.meta.url);
require.cache[require.resolve('path')] = { exports: { sep: 'patched' } };
console.log('require("path").sep   :', require('path').sep);
console.log('getBuiltinModule sep  :', process.getBuiltinModule('path').sep);

process.features

process.features is an object of booleans (and one string) that describe how this Node.js binary was built, so that tools can adapt to the runtime they find instead of parsing version numbers. The useful entries are inspector (the inspector is compiled in), require_module (require() of ES modules is supported), typescript (type stripping: 'strip' by default, false with --no-strip-types), tls (TLS support), cached_builtins (built-in modules are cached in the binary) and debug (a debug build). Do not check ipv6, uv, tls_alpn, tls_ocsp or tls_sni: they were deprecated in v23.4.0 and v22.13.0 because they are always true (ipv6, uv) or equal to tls in every current build. In a build with a minimal feature set a property can be false, which is the point of the object: embedders and single-executable builds differ.

Reading the build features
import { features } from 'node:process';

// Only the useful, non-deprecated entries
console.log({
  inspector: features.inspector,
  require_module: features.require_module,   // require(esm) support
  typescript: features.typescript,           // 'strip' unless --no-strip-types
  tls: features.tls,
  cached_builtins: features.cached_builtins,
  debug: features.debug,
});
Output on Node.js 26, 24 and 22
{
  inspector: true,
  require_module: true,
  typescript: 'strip',
  tls: true,
  cached_builtins: true,
  debug: false
}

Started with --no-strip-types (Node.js 26 and 24; on 22 the flag is --no-experimental-strip-types) the typescript entry is false; started with --no-experimental-require-module the require_module entry is false. Prefer testing a feature over testing a version: if (process.features.require_module) documents why the code branches.

Warnings: process.emitWarning() and the 'warning' event

Node.js reports process warnings (deprecations, experimental features, listener leaks) on stderr and as 'warning' events. process.emitWarning() lets libraries use the same channel, with an optional type and code; --no-warnings silences the output but the event is still emitted; --no-deprecation suppresses DeprecationWarning entirely.

import process from 'node:process';

process.on('warning', (w) => console.log(`event: ${w.name} [${w.code}] ${w.message}`));

process.emitWarning('Using the legacy shelf API', { type: 'DeprecationWarning', code: 'BOOKSHELF_DEP001', detail: 'Use /books instead.' });

Replacing the process image: process.execve()

process.execve(file, args, env) (Stability 1 Experimental, POSIX only) replaces the current process with a new program through the execve(2) system call: same pid, same standard streams, nothing else. On success it never returns and no JavaScript cleanup runs, not even 'exit' listeners. If the call fails it throws an error whose code is the errno string (for example 'ENOENT') and the process continues. Do your cleanup first. It is a niche tool for launchers and wrappers; for a normal child process use child_process instead.

import { execve, env, pid, execPath, platform } from 'node:process';

if (platform === 'win32') throw new Error('process.execve() is not available on Windows');

process.on('exit', () => console.log('exit handlers do NOT run on a successful execve'));

if (env.STAGE !== 'second') {
  console.log('first image, pid', pid);
  // Replaces this process image in place: same pid, no cleanup, no return on success.
  execve(execPath, [execPath, import.meta.filename], { ...env, STAGE: 'second' });
}
console.log('second image, STAGE =', env.STAGE, '| same pid as before:', pid > 0);
Output on Node.js 26, 24 and 22 (the ExperimentalWarning was silenced with --no-warnings)
first image, pid 52545
second image, STAGE = second | same pid as before: true
exit handlers do NOT run on a successful execve

(The last line is printed by the second image’s own 'exit' listener when it ends; the first image’s listener never ran.)

Asking what the permission model allows: process.permission

Only when the process was started with --permission (or --permission-audit) does process.permission exist; otherwise it is undefined. Because it is undefined, a named import such as import { permission } from 'node:process' fails with a SyntaxError ("does not provide an export named"); read it from the default export or the global instead.

import process from 'node:process';

// process.permission only exists when the permission model is on (--permission)
if (!process.permission) {
  console.log('permission model is off: process.permission is', process.permission);
} else {
  console.log('fs.read  :', process.permission.has('fs.read'));
  console.log('fs.write :', process.permission.has('fs.write'));
  console.log('child    :', process.permission.has('child'));
}
Output on Node.js 26, 24 and 22, without and with node --permission --allow-fs-read='*'
permission model is off: process.permission is undefined
fs.read  : true
fs.write : false
child    : false

The model itself, and --allow-net (Stability 1.1), are in The Permission Model.

Pitfalls

Table 9. The mistakes this page prevents
Mistake What to do instead

process.exit(1) right after writing output

Set process.exitCode = 1 and let the process drain; output to a pipe can be truncated otherwise.

An 'uncaughtException' listener that logs and carries on

Log synchronously, set a non-zero exitCode and let the process end; restart it from outside. Without the code the crash is reported as success.

A SIGINT or SIGTERM listener that never ends the process

Installing a listener removes the default. Always finish by letting the loop empty (with exitCode) or, in a watchdog, calling process.exit().

Relying on a signal listener to keep the program alive

Keep a server, timer or open handle referenced; signals do not keep the loop alive.

Handling SIGKILL, or expecting cleanup after it

Impossible. Design for crash safety (idempotent work, transactions) and use SIGTERM for graceful stops.

Starting Node.js as PID 1 in a container without handlers, or through npm start

Use exec-form CMD ["node", "server.js"], install a SIGTERM handler, or use docker run --init.

Treating process.env.FLAG as a boolean or number

Values are strings; "false" is truthy. Compare explicitly and parse numbers.

Writing env.X = undefined to "unset" a variable

Use delete env.X.

`process.env.SECRET

"fallback"` for a key or token

Fail fast when a secret is missing; a hard-coded fallback ships to production unnoticed.

Calling process.chdir() in a library

Anchor paths with import.meta.dirname instead.

Measuring durations with Date.now()

Use process.hrtime.bigint() or performance.now(); the wall clock can jump.

Reading memoryUsage().heapUsed to find a Buffer leak

Watch rss, external and arrayBuffers as well.

Relying on 'beforeExit' for cleanup

It does not fire for process.exit(), crashes or signals; use 'exit' for synchronous cleanup and the signal handler for asynchronous cleanup.

Calling process.exit() from a library

Throw or reject; the application decides when to end.

Installing a SIGUSR1 handler

The inspector uses it. Use SIGUSR2, and consider --disable-sigusr1 in hardened deployments.

Where the books are outdated or incomplete

Efficient Node.js (Samer Buna, O’Reilly 2025) introduces process.argv and process.env early and explains correctly that process.env is a copy of the environment that cannot change the operating-system variables of the parent. Where it has aged is in the tools around it: it shows loading a .env file through the third-party dotenv package, with -r dotenv/config, while the runtime now has --env-file, --env-file-if-exists, process.loadEnvFile() and util.parseEnv(), all stable since v24.10.0 and v22.21.0. Its coverage of unhandled errors recommends an 'uncaughtException' listener that exits with code 1 after cleanup, which is the right spirit, but it does not mention 'uncaughtExceptionMonitor', the origin argument, the --unhandled-rejections modes, the ES-module quirk shown above, or the trap that a listener without an exit code turns a crash into success. It does not cover exit codes in depth, signals, graceful shutdown, PID 1 in containers, process.getBuiltinModule() or process.features, which are the subject of this page.

Node.js Projects (Jonathan Wexler, O’Reilly 2025) scatters process.exit(1) through error branches of its servers and scripts. That is easy to read and wrong for programs whose output is consumed by a pipe, as the truncation example shows; process.exitCode plus a natural exit is the safe form. It reads ports and keys with the process.env.X || default idiom, which is risky for numbers and dangerous for secrets: || replaces valid falsy values, and a hard-coded fallback for a JWT secret means a missing variable silently deploys a known key. The safe form fails at startup when a required secret is absent and uses ?? only for harmless defaults. It also parses command-line arguments by slicing process.argv, where the built-in util.parseArgs() validates options and types, and it uses dotenv where --env-file is now enough. Neither book teaches signal handling, so the "Ctrl+C does nothing" and "the container will not stop" failures of this page are not covered.
