Authentication & Sessions

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Node.js 26 (26.10.0, released 2026-09-21, the Current line that becomes LTS on 2026-10-28), with the differences of Node.js 24 "Krypton" (24.21.0, Active LTS) and Node.js 22 "Jod" (22.23.3, Maintenance) called out; versions were checked against the official documentation and the npm registry on 2026-10-04, and every example below was run on Node.js 26, 24 and 22 with identical results. Authentication in Node.js is almost entirely a library and protocol question rather than a runtime one: the core gives you the building blocks (node:crypto for random identifiers, hashing and constant-time comparison, node:http for headers and cookies), and the ecosystem (express-session, Passport, jsonwebtoken, the @fastify/* plugins) assembles them into sessions and tokens. This page shows the two mainstream designs side by side, server-side sessions held in a store and stateless signed tokens, then adds the protections that sit around either of them: CSRF defences, rate limiting and lockout, and single-use email verification tokens. Password hashing itself is covered in Crypto, Passwords & Secrets and is not repeated here; the examples reuse its scrypt recipe. The running scenario is the Bookshelf application from Introduction & Architecture; Express and Fastify themselves are introduced in Web Frameworks: Express & Fastify, and the protocol theory (OAuth 2.0, OpenID Connect, token formats) lives in the OAuth section, which this page links to rather than re-explaining.

Sessions or tokens: choosing a design

Authentication answers "who is this?" once, at login; the rest of the design is how the server recognises the same client on the next request. There are two answers. A session keeps the state on the server: the client holds an opaque, random identifier in a cookie and the server looks it up in a store (memory, Redis, a database) on every request. A stateless token keeps the state in the client: the server signs a small set of claims (a JSON Web Token) and verifies the signature on every request without any lookup.

Table 1. Server-side sessions compared with stateless JWTs
Concern Server-side session (opaque id in a cookie) Stateless JWT (signed claims)

Revocation and logout

Immediate: delete the record in the store.

Hard. A token is valid until exp; revocation needs a deny-list or very short lifetimes, which brings state back.

Request cost

One store lookup per request (Redis: sub-millisecond on a local network).

One signature verification; no I/O.

Changing a user’s role or disabling an account

Takes effect on the next request.

Takes effect when the token expires or is refreshed.

Horizontal scaling

Needs a shared store, or sticky routing; see Cluster & Scaling.

Any instance that has the verification key can authenticate the request.

Browser story

Cookie with HttpOnly, Secure, SameSite; needs CSRF protection.

Usually sent in an Authorization header (immune to CSRF, but the token must then live in JavaScript-readable memory) or in a cookie (back to CSRF).

Best fit

A server-rendered site or a first-party single-page app on the same site as its API.

Service-to-service calls, short-lived API access tokens, and third-party clients (see Access & Refresh Tokens).

For a first-party web application with a single backend, a server-side session is the simpler and safer default, because logout and revocation work. Reach for tokens when several services must validate callers independently, and keep them short-lived and paired with a rotating refresh token. A JWT is a format, not a security feature: every property in the table comes from how it is issued and verified, which is why this page spends more time on the verification options than on the signing call. The OAuth section covers the format in JWT & JOSE and the opaque alternative in Opaque Tokens, Introspection & Revocation.

A user table with scrypt hashes

The examples share one small module: an in-memory user table, scrypt hashing with a per-password salt, the asynchronous crypto.scrypt() so the event loop is not blocked, a constant-time comparison, and a dummy hash so that a login attempt for an unknown address takes about as long as one for a real address (otherwise response time reveals which accounts exist). The parameters and the reasons for them are in Crypto, Passwords & Secrets; production code would store the table in a database and prefer Argon2id on Node.js 24.7 and later.

src/users.js: shared by every example on this page
import { scrypt, randomBytes, timingSafeEqual } from 'node:crypto';
import { promisify } from 'node:util';

const scryptAsync = promisify(scrypt);

export async function hashPassword(password) {
  const salt = randomBytes(16);
  const key = await scryptAsync(password.normalize('NFKC'), salt, 64);
  return `scrypt$${salt.toString('base64url')}$${key.toString('base64url')}`;
}

export async function verifyPassword(password, stored) {
  const [, salt, hash] = stored.split('$');
  const expected = Buffer.from(hash, 'base64url');
  const actual = await scryptAsync(password.normalize('NFKC'), Buffer.from(salt, 'base64url'), expected.length);
  return timingSafeEqual(actual, expected);
}

// A tiny in-memory user table for the examples; Bookshelf uses SQLite or PostgreSQL.
export const users = new Map();

// Returns the new user, or null when the address is already registered: an existing account is never overwritten.
// The password is hashed first in both cases, so a duplicate signup costs the same time as a new one.
export async function addUser(email, password) {
  const passwordHash = await hashPassword(password);
  if (users.has(email)) return null;
  const user = { id: randomBytes(8).toString('hex'), email, role: 'reader', passwordHash, verified: false };
  users.set(email, user);
  return user;
}

// Used to keep timing similar when the account does not exist.
export const dummyHash = await hashPassword('not-a-real-password');

Cookies: the attributes that matter

A session identifier travels in a cookie, so the cookie’s attributes are the first line of defence. They are set by the server in the Set-Cookie response header; the browser enforces them, so a missing attribute is a hole no server-side check can close.

Table 4. Cookie attributes for a session or refresh cookie
Attribute What it does Recommended value

HttpOnly

Hides the cookie from document.cookie, so a cross-site scripting (XSS) bug cannot read and exfiltrate the identifier.

Always for session and refresh cookies.

Secure

Sends the cookie only over HTTPS (browsers also accept it on localhost). Prevents sniffing on plain-HTTP links.

Always in production.

SameSite

Controls whether the cookie accompanies cross-site requests. Strict never does; Lax does on top-level GET navigations; None always (and requires Secure).

Lax for the session cookie, Strict for a refresh cookie that is only used by your own page. Do not rely on the browser default.

Path and Domain

Path limits which request paths carry the cookie; a Domain attribute widens it to every subdomain, which makes any sibling host a possible attacker.

Omit Domain. Use a narrow Path for a cookie only one endpoint needs (the refresh endpoint below).

Max-Age / Expires

Lifetime of the cookie in the browser. Without either it is a session cookie that disappears when the browser closes (browsers may restore it).

Short, and enforced again on the server; the browser is not a trustworthy clock.

__Host- name prefix

The browser refuses the cookie unless it is Secure, has Path=/ and no Domain. This blocks a sibling subdomain from overwriting it.

Use it for the session cookie where the deployment allows (HTTPS everywhere).

SameSite is a defence in depth against CSRF, not a replacement for a CSRF token, because it works on the site (registrable domain) and not the origin, and because Lax still allows cross-site top-level GET. The next sections apply these attributes; the CSRF section builds on them.

Four details in that output deserve a closer look.

  • The cookie is only issued when the connection looks secure. With secure: true, express-session sets the cookie only if Express considers the request HTTPS. Behind a TLS-terminating proxy that is true only when trust proxy is set and the proxy sends X-Forwarded-Proto: https; the last line of the output shows that over plain HTTP no cookie is issued at all, and the user appears to be unable to log in. The fix is the proxy configuration, never secure: false. Set trust proxy to the exact number of hops (1 for one reverse proxy), not to true, which trusts a client-supplied X-Forwarded-For and also defeats IP-based rate limiting (see Server Timeouts, Limits & Hardening for the proxy side).

  • Rotation at privilege change. req.session.regenerate() creates a new session id (and a new store record) after the credentials are checked. If an attacker had planted a known id in the victim’s browser before login (session fixation), that id is worthless afterwards. Do the same after any other privilege change, such as a step-up with a second factor or a role change.

  • Two lifetimes. The cookie maxAge (and the store’s ttl) is an idle timeout that touch extends on each request when rolling is on; add an absolute limit yourself by storing createdAt in the session (the example does) and rejecting sessions older than, say, eight hours. OWASP recommends both.

  • Logout is deletion. req.session.destroy() removes the record from Redis (the output shows the key count dropping to zero) and clearCookie() removes the cookie. This is the capability tokens lack: the server can end a session at any time, for example "sign out everywhere" by deleting every record that carries a user id.

Two operational notes. Rotating the signing secret without logging everyone out works by passing an array: the first element signs new cookies, the later ones are still accepted for verification. And the plain-HTTP request at the end of the example still created a (now unreachable) record in Redis before the cookie was refused; with an idle ttl that record expires on its own, which is one more reason to set one.

Stateless tokens with jsonwebtoken

A JWT is three base64url-encoded parts (header, payload, signature) joined with dots. Anyone can read the payload; the signature only proves it was produced by a holder of the key. Two rules follow, and breaking either is the source of most JWT vulnerabilities: never put anything in a token that the client must not see, and never trust a token until verify() has checked the signature and the claims with the options you chose.

The example issues a short-lived token with the registered claims (iss, aud, sub, exp, jti) and then tries five attacks on the verifier. jwt.decode() is shown last to make a point: it parses a token without checking anything, so using it for authorization is the same as having no authentication.

  • Do not store tokens in localStorage. Any script on the page can read them. Prefer an HttpOnly cookie, or keep the access token in memory and the refresh token in an HttpOnly cookie; see Browser-Based Apps for the standards position.

  • Revocation is a design decision. With a five-minute access token, "revoke" means "wait five minutes", plus revoking the refresh token. If that is not acceptable, you want sessions (or opaque tokens with introspection).

Refresh tokens, rotation and passport-jwt

A five-minute access token needs a way to be renewed without asking for the password again. The standard answer is a refresh token: a long-lived, opaque credential that can only be exchanged at one endpoint. It is deliberately not a JWT here: a random 32-byte value carries no claims to leak, and because it is looked up on the server, it can be revoked. Three practices make it safe:

  • store only a digest (SHA-256 is enough for a value with 256 bits of entropy; the slow password hashes are for low-entropy passwords);

  • rotate it on every use, so a stolen token works at most once;

  • remember which tokens have been used, and when one is presented a second time, revoke the whole family, since either the thief or the legitimate client now holds a dead token and the server cannot tell which.

The example puts the access token in the Authorization header (verified by passport-jwt with pinned algorithms, issuer and audience) and the refresh token in an HttpOnly, Secure, SameSite=Strict cookie whose Path is limited to the refresh endpoint, so the browser sends it nowhere else.

CSRF protection

Cross-site request forgery exploits the fact that browsers attach cookies automatically: a malicious page makes the victim’s browser send POST /books to your site, and the session cookie goes along. Only requests that change state matter, and only when the credential is a cookie. Consequences for the designs above:

  • A session cookie or a refresh cookie authenticating a state-changing request needs CSRF protection.

  • A bearer token in the Authorization header is not sent automatically, so a request authenticated only that way is not forgeable cross-site. (Cross-origin requests can still need a CORS policy; that is a different control.)

  • GET must never change state, so that the safe-method exemption in every library is actually safe.

Defend in layers, cheapest first:

Table 7. CSRF defence layers
Layer How it works Limits

SameSite=Lax or Strict on the cookie

The browser does not send the cookie on cross-site POST requests.

Same-site, not same-origin: a vulnerable sibling subdomain is not blocked. Older browsers ignore it.

Fetch Metadata (Sec-Fetch-Site)

Browsers label every request as same-origin, same-site, cross-site or none; the server refuses state-changing requests from cross-site.

The header is absent in non-browser clients and old browsers, so treat "absent" as "not a browser request" and keep the token layer.

Synchronizer token

A random token is stored in the session and must be echoed in a custom header (or a hidden form field) of every state-changing request. An attacker’s page cannot read it.

Needs a session.

Double-submit cookie (signed)

Stateless: the server sets a token in a cookie and requires the same token in a header; the signature binds it to the session or user.

Weaker if the token is not bound to the session, or if a sibling subdomain can set cookies; use the __Host- prefix.

The first example implements the synchronizer token by hand, because it is only a few lines, together with the Fetch Metadata check. Note the constant-time comparison, the header (never a query string, which ends up in logs and Referer), and the __Host- cookie name.

src/csrf-sync.js: Fetch Metadata plus a session-bound synchronizer token
import express from 'express';
import session from 'express-session';
import { randomBytes, timingSafeEqual } from 'node:crypto';

const { SESSION_SECRET } = process.env;
if (!SESSION_SECRET) throw new Error('SESSION_SECRET is required');

const SAFE_METHODS = new Set(['GET', 'HEAD', 'OPTIONS']);

// Layer 1: Fetch Metadata. Browsers send Sec-Fetch-Site; refuse state changes that start on another site.
function fetchMetadata(req, res, next) {
  const site = req.get('sec-fetch-site');
  if (SAFE_METHODS.has(req.method) || site === undefined || site === 'same-origin' || site === 'none') return next();
  return res.status(403).json({ error: 'cross-site request refused' });
}

// Layer 2: synchronizer token bound to the session, sent in a header (never in the URL).
function csrfToken(req) {
  req.session.csrf ??= randomBytes(32).toString('base64url');
  return req.session.csrf;
}
function verifyCsrf(req, res, next) {
  if (SAFE_METHODS.has(req.method)) return next();
  const sent = Buffer.from(req.get('x-csrf-token') ?? '');
  const expected = Buffer.from(req.session.csrf ?? '');
  if (sent.length === 0 || sent.length !== expected.length || !timingSafeEqual(sent, expected)) {
    return res.status(403).json({ error: 'invalid csrf token' });
  }
  return next();
}

Rate limiting and lockout

Passwords are the weakest credential, and the attacks on them are volume attacks: brute force against one account, and credential stuffing (leaked password lists replayed across many accounts). Two complementary controls address them. A rate limiter bounds how many requests one client (usually one IP address) may make in a window and protects every route, including expensive ones such as password hashing. An account lockout bounds failed attempts per account regardless of source address, which is what stops a distributed attack against one victim.

Table 8. Rate limiting and lockout compared
Control Protects against Trade-off

Per-IP rate limit

One client hammering any endpoint; cheap to apply everywhere.

Many clients behind one NAT share a quota; attackers rotate addresses. Needs a correct trust proxy to see the real address.

Per-account lockout with back-off

Distributed guessing against one account.

A denial-of-service lever: anyone can lock a known address. Use a short, growing delay rather than permanent lock, and notify the owner.

Generic failure message and equal timing

Account enumeration.

None worth avoiding; see the dummy hash in the shared module.

The example combines both. The limiter uses the standard RateLimit headers (draft 8) rather than the legacy X-RateLimit-* set, derives the key with ipKeyGenerator() so that an IPv6 client cannot dodge the limit by rotating addresses inside its own /64 block, and the lockout counts failures for unknown addresses too so the lockout behaviour does not reveal which accounts exist.

src/ratelimit.js: per-IP limiter plus per-account lockout with exponential back-off
import express from 'express';
import rateLimit, { ipKeyGenerator } from 'express-rate-limit';
import { addUser, users, verifyPassword, dummyHash } from './users.js';

const app = express();
app.set('trust proxy', 1); // required to see the real client address behind one proxy; never `true`
app.use(express.json());

// Layer 1: per-IP limiter on the login route (in-memory store here; use a shared store with several instances).
const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 20,
  standardHeaders: 'draft-8',
  legacyHeaders: false,
  keyGenerator: (req) => ipKeyGenerator(req.ip),
  message: { error: 'too many attempts, try again later' },
});

// Layer 2: per-account lockout with exponential back-off, independent of the source address.
const failures = new Map(); // email -> { count, lockedUntil }
const MAX_FAILURES = 5;
const lockSeconds = (count) => Math.min(2 ** (count - MAX_FAILURES) * 30, 15 * 60);

app.post('/login', loginLimiter, async (req, res) => {
  const email = String(req.body.email ?? '').toLowerCase();
  const state = failures.get(email) ?? { count: 0, lockedUntil: 0 };
  if (state.lockedUntil > Date.now()) {
    res.set('Retry-After', String(Math.ceil((state.lockedUntil - Date.now()) / 1000)));
    return res.status(429).json({ error: 'account temporarily locked' });
  }
  const user = users.get(email);
  const ok = await verifyPassword(String(req.body.password ?? ''), user ? user.passwordHash : dummyHash);
  if (!user || !ok) {
    state.count += 1;
    if (state.count >= MAX_FAILURES) state.lockedUntil = Date.now() + lockSeconds(state.count) * 1000;
    failures.set(email, state); // also tracked for unknown emails, so lockouts do not reveal which accounts exist
    return res.status(401).json({ error: 'invalid credentials' });
  }
  failures.delete(email);
  res.json({ ok: true });
});

Email verification tokens

Before an account is trusted, the owner of the address should prove control of it. The proof is a secret that only the mailbox receives. The same mechanism serves password reset and email-change confirmation. The rules:

  • Random, not derived. Use crypto.randomBytes(32), never the address, a user id, a counter, a timestamp or a hash of them. A link of the form /verify?email=someone@example.com lets anyone "verify" any address by typing it.

  • Store only a digest. A database leak then does not hand out working links. SHA-256 is appropriate for 256-bit random tokens.

  • Expire and consume. A fixed lifetime (the example uses 24 hours; use minutes for password reset) and single use; delete or mark the row on success.

  • Bind it to a purpose and a user, so a verification token cannot be replayed as a reset token.

  • Do not change state on GET. Mail scanners and link previews fetch URLs automatically and would confirm accounts, or consume reset tokens, before the person clicks. The link opens a page; the button on it sends a POST.

  • Uniform responses. Signup answers "check your inbox" whether or not the address already exists, otherwise registration leaks membership.

  • Keep the token out of logs and referrers. Put it in the query string only on that one confirmation page, serve it with Referrer-Policy: no-referrer, and exchange it immediately.

Sending the message itself (SMTP transports, HTML and text bodies, SPF, DKIM and DMARC, consent) is covered in Email, Feeds & Web Scraping; the example uses an array in place of sendMail().

import fastifyRateLimit from '@fastify/rate-limit';
import { addUser, users, verifyPassword, dummyHash } from './users.js';

const { JWT_SECRET, SESSION_SECRET } = process.env;
if (!JWT_SECRET || !SESSION_SECRET) throw new Error('JWT_SECRET and SESSION_SECRET are required');

const app = Fastify({ trustProxy: 1, logger: false });

await app.register(fastifyCookie, { secret: SESSION_SECRET }); // enables signed cookies
await app.register(fastifyJwt, {
  secret: JWT_SECRET,
  sign: { algorithm: 'HS256', expiresIn: '10m', iss: 'bookshelf' },
  verify: { algorithms: ['HS256'], allowedIss: 'bookshelf' }, // the default accepts every algorithm: pin it
});
await app.register(fastifyRateLimit, { global: false }); // opt in per route

app.decorate('authenticate', async (request, reply) => {
  try {
    await request.jwtVerify();
  } catch {
    return reply.code(401).send({ error: 'unauthorized' });
  }
});

app.post('/login', {
  config: { rateLimit: { max: 5, timeWindow: '1 minute' } },
  schema: { body: { type: 'object', required: ['email', 'password'], properties: { email: { type: 'string' }, password: { type: 'string' } } } },
}, async (request, reply) => {
  const user = users.get(request.body.email);
  const ok = await verifyPassword(request.body.password, user ? user.passwordHash : dummyHash);
  if (!user || !ok) return reply.code(401).send({ error: 'invalid credentials' });
  reply.setCookie('bookshelf.seen', '1', { signed: true, httpOnly: true, secure: true, sameSite: 'lax', path: '/' });
  return { accessToken: await reply.jwtSign({ role: user.role }, { sub: user.id }) };
});

app.get('/books', { preHandler: app.authenticate }, async (request) => ({ user: request.user.sub, role: request.user.role }));

await addUser('ada@example.com', 'correct horse battery staple');
const login = (password) => app.inject({ method: 'POST', url: '/login', payload: { email: 'ada@example.com', password } });

let res = await login('correct horse battery staple');
console.log('login:', res.statusCode, '| cookie:', res.cookies[0].name, res.cookies[0].httpOnly, res.cookies[0].secure, res.cookies[0].sameSite);
const { accessToken } = res.json();
res = await app.inject({ method: 'GET', url: '/books', headers: { authorization: `Bearer ${accessToken}` } });
console.log('with token:', res.statusCode, res.json().role);
res = await app.inject({ method: 'GET', url: '/books' });
console.log('without token:', res.statusCode);

for (let i = 1; i <= 6; i += 1) {
  res = await login('wrong');
  if (res.statusCode === 429) { console.log(`login failure ${i}: ${res.statusCode}`, res.headers['retry-after'] ? `retry-after ${res.headers['retry-after']}` : ''); break; }
}
await app.close();

Where the books are outdated

The authentication chapters of Node.js Projects (Jonathan Wexler, O’Reilly, 2025) are a useful tour of the moving parts (sessions, Passport’s local strategy, JWTs, hooks as authentication middleware), but several habits they show should not be copied into real code, and the corrected form is on this page:

Table 10. Habits to replace
Habit shown Replace with

Secrets written in source files, or a JWT secret with a fixed fallback string

Read secrets from the environment (--env-file), generate them with crypto.randomBytes(), and stop the process at start-up when one is missing.

Tokens issued without expiresIn and verified without algorithms

Short expiry, pinned algorithms, issuer and audience, plus a rotating refresh token (see the JWT and refresh sections).

Session cookies without secure, httpOnly or sameSite

The attribute table above; add __Host- where possible and regenerate the session at login.

No CSRF protection and no rate limiting on login

A CSRF layer for every cookie-authenticated state change, and rate limit plus lockout on authentication routes.

Email verification by a GET link that contains the email address

A random, hashed, expiring, single-use token confirmed with POST.

Low-cost password hashing (PBKDF2 with a low iteration count) and === comparison of hashes

Argon2id or scrypt, asynchronous APIs and crypto.timingSafeEqual(); OWASP’s PBKDF2-HMAC-SHA512 floor is 210,000 iterations. Details: Crypto, Passwords & Secrets.

req.logout() called without a callback, and session setup assumed to reuse the id (Passport before 0.6)

Pass a callback to logout(); Passport 0.7 rotates the id on login by itself.

Pitfalls and good practice

Table 11. Pitfalls
Pitfall Better practice

MemoryStore in production

Use Redis or a database store; the default store leaks memory and does not span processes.

trust proxy set to true

Set the exact hop count; otherwise X-Forwarded-For is attacker-controlled and rate limits are bypassed.

secure: true behind TLS termination without trust proxy

The cookie is silently never sent; configure the proxy headers.

Using jwt.decode() to authorise

Always verify() with pinned algorithms, issuer and audience.

Putting tokens in localStorage

HttpOnly cookie or in-memory access token.

Long-lived JWTs as session replacements

Minutes for access tokens; refresh tokens that rotate and are revocable; or use real sessions.

Verification or reset links that change state on GET

Link to a page; confirm with POST.

Different error messages or timings for unknown users

One message, a dummy hash comparison.

CSRF token in the URL

Custom header, constant-time comparison, bound to the session.

Per-process counters behind a load balancer

Shared store for limits, lockouts and sessions.

Rolling your own cryptography for tokens

Use the libraries here, or Web Crypto and node:crypto primitives as shown in Crypto, Passwords & Secrets.
