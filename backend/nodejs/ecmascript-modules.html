ECMAScript Modules

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Node.js 26 (26.10.0, released 2026-09-21, the Current line that becomes LTS on 2026-10-28), with the differences of Node.js 24 "Krypton" (24.21.0, Active LTS) and Node.js 22 "Jod" (22.23.3, Maintenance) called out; all versions and stability levels were checked against the official documentation on 2026-10-03, and every example below was run on all three lines unless the text says otherwise. ECMAScript modules (ESM) are the language’s own module format and the one to use for new code; Node.js still ships its older CommonJS format next to it, and the two can load each other (see ESM & CommonJS Interop). The stability level of what this page covers is not uniform: the module system as a whole is Stability 2 (Stable), as are import.meta.url, import.meta.dirname, import.meta.filename, dynamic import(), top-level await, import attributes and JSON modules. Syntax detection and import.meta.resolve() are Stability 1.2 (Release candidate). import.meta.main is Stability 1.0 (Early development). Text modules are Stability 1.0 (Early development) behind a flag, WebAssembly source phase imports and the JavaScript string builtins are Stability 1.2, and importing a WebAssembly module instance is Stability 1.1 (Active development).

For the language-level syntax (how export, export default, namespace imports and re-exports are spelled and what they mean in the browser too) read Modules in the JavaScript reference first; this page concentrates on what Node.js adds: how a file becomes a module, how specifiers are resolved, and what is different from CommonJS. The TypeScript flavour of the same syntax is in TypeScript Modules. The running scenario is the Bookshelf application that grows across this section.

import and export

An ES module is a file whose top-level code uses import and export declarations. Three facts distinguish a module from a classic script and are worth stating before the example: the module code is always in strict mode, its top-level variables are private to the file (nothing leaks to the global object), and the value of this at the top level is undefined. Exports are live bindings: an importer sees the current value of the exporting module’s variable, not a copy taken at import time, and it cannot assign to the binding. The module namespace object that import * as ns produces is a sealed object whose Symbol.toStringTag is Module.

A module with named and default exports, and a module that consumes them (lib/book.js and main.js)
// lib/book.js
export const GENRES = ['fiction', 'science', 'history'];

export function describe(book) {
  return `${book.title} (${book.year})`;
}

export default class Book {
  constructor(title, year) {
    this.title = title;
    this.year = year;
  }
}

export let counter = 0;
export function increment() {
  counter += 1;
}

// main.js
import Book, { describe, GENRES as genres, counter, increment } from './lib/book.js';
import * as bookModule from './lib/book.js';
export { describe as format } from './lib/book.js';

const b = new Book('Dune', 1965);
console.log(describe(b), genres.length);
console.log(Object.keys(bookModule), bookModule[Symbol.toStringTag]);
console.log('before', counter);
increment();
console.log('after', counter);
try {
  counter = 5;
} catch (e) {
  console.log(e.constructor.name + ':', e.message);
}

Source: Node.js API: Modules: ECMAScript modules (Introduction)

The two files live in a package whose package.json declares "type": "module" (explained in .mjs, .cjs and the "type" field). The output was identical on Node.js 26, 24 and 22:

Dune (1965) 3
[ 'GENRES', 'counter', 'default', 'describe', 'increment' ] Module
before 0
after 1
TypeError: Assignment to constant variable.

The counter import reflects the change made by increment() (the live binding), the namespace keys are listed in alphabetical order with default among them, and assigning to an imported binding throws a TypeError even though the exporting module declared it with let. Imports are hoisted: all import declarations are resolved and loaded before any code of the importing module runs, which is why they must be static strings. When the specifier is only known at run time, use dynamic import().

Specifiers and mandatory file extensions

The string after from is called the specifier, and Node.js distinguishes three kinds. How each one is resolved is summarised below and specified precisely in The resolution and loading algorithm.

Table 2. The three kinds of import specifier
Kind Examples Rule

Relative

./startup.js, ../config.mjs

Resolved against the URL of the importing file with standard URL resolution. The file extension is always required.

Bare

some-package, some-package/shuffle, path

Resolved by the package algorithm: built-in module names first, then node_modules lookup. An extension is only needed for packages without an "exports" field.

Absolute

file:///opt/nodejs/config.js, node:path, data:text/javascript,...

A full URL. file:, node: and data: are supported; https: is not supported natively.

Unlike CommonJS, ESM resolution performs no extension search and does not treat directories as modules: ./lib/book and ./lib/shelf (a folder with an index.js) both fail. This matches how a typically configured server behaves for browser imports. The error messages suggest the fix.

Omitting the extension, and importing a directory
// noext.js
import { describe } from './lib/book';

// dirimp.js
import { name } from './lib/shelf';

// dirimp-ok.js
import { name } from './lib/shelf/index.js';
console.log(name);

Source: Node.js API: ECMAScript modules (Mandatory file extensions)

Running each file reported (paths shortened, identical on Node.js 26, 24 and 22):

Error [ERR_MODULE_NOT_FOUND]: Cannot find module '.../ex1/lib/book' imported from .../ex1/noext.js
Did you mean to import "./lib/book.js"?

Error [ERR_UNSUPPORTED_DIR_IMPORT]: Directory import '.../ex1/lib/shelf' is not supported resolving ES modules imported from .../ex1/dirimp.js
Did you mean to import "./lib/shelf/index.js"?

shelf

TypeScript files follow the same rule when Node.js strips their types: the specifier must name the real file, including the .ts extension, and type-only imports must be marked with type. A relative import './book' from a .ts file also fails with ERR_MODULE_NOT_FOUND on all three lines (checked), and import { label, type Book } from './book.ts' runs. The details are in TypeScript in Node.js; the API reference is the TypeScript page of the Node.js documentation (https://nodejs.org/docs/latest/api/typescript.html).

Specifiers are URLs

Internally, ES modules are resolved and cached by URL. Two consequences matter in practice. Special characters in a path must be percent-encoded in a specifier (# as %23, ? as %3F), and a different query string or fragment is a different module, which is evaluated again. When you have a file system path rather than a specifier, convert it with url.pathToFileURL() instead of concatenating strings.

A query string makes a separate module instance; the same URL is cached
const a = await import('./src/util.js?v=1');
const b = await import('./src/util.js?v=2');
const c = await import('./src/util.js?v=1');
console.log('different query => different instance:', a !== b, '| same URL => cached:', a === c);

Source: Node.js API: ECMAScript modules (file: URLs)

The output was different query => different instance: true | same URL => cached: true on Node.js 26, 24 and 22. The query-string trick is occasionally used to bust the module cache in tests and file watchers, at the price of leaking the old instance, because ES modules cannot be evicted (see Evaluation order, caching and cycles).

Other URL schemes are handled by the default loader as follows.

Table 3. URL schemes accepted by import
Scheme Behaviour

file:

The normal case. Relative and absolute specifiers become file: URLs. import.meta.url is a file: URL.

node:

Built-in modules, for example node:fs/promises. Available since v14.13.1 and v12.20.0 for import, and in require() since v16.0.0 and v14.18.0.

data:

Inline modules, added in v12.10.0. MIME types text/javascript (ES modules), application/json and application/wasm. Only builtin and absolute specifiers resolve inside, because data: has no relative resolution.

https: and others

Fail with ERR_UNSUPPORTED_ESM_URL_SCHEME; a custom loader is needed to import over HTTP.

.mjs, .cjs and the "type" field

Node.js has to decide, for every file, whether to parse it as an ES module or as CommonJS. Explicit markers always win, and they are checked in this order of strength: the file extension, then the "type" field of the nearest parent package.json, then (for strings from --eval or standard input) the --input-type flag. Only if no marker exists does Node.js fall back to syntax detection.

Table 4. How a file is classified (rows are the explicit markers)
Marker Interpreted as Notes

.mjs

ES module

Always, whatever the nearest package.json says.

.cjs

CommonJS

Always, whatever the nearest package.json says.

.js and "type": "module"

ES module

The field applies to entry points and to files reached by import and import().

.js and "type": "commonjs"

CommonJS

Explicit, so no detection and no performance cost.

.js and no "type", or no package.json

Ambiguous

CommonJS first; see Syntax detection.

--input-type=module or commonjs

Same as the value

Only for --eval, --print or standard input; combining it with a file raises ERR_INPUT_TYPE_NOT_ALLOWED. Also accepts module-typescript and commonjs-typescript since v23.6.0 and v22.18.0.

.ts, .mts, .cts

TypeScript text

With type stripping; .mts is always ES module and .cts always CommonJS, like .mjs and .cjs.

The .mjs and .cjs extensions can mix both formats within a single package, for instance a .cjs configuration file inside a "type": "module" project. The official recommendation is that every package states its "type", even when all sources are CommonJS, which avoids the detection overhead, protects against a future change of the default, and helps build tools.

A probe file in three packages, saved with three extensions
// probe.js, probe.mjs and probe.cjs contain the same line
console.log(typeof require === 'undefined' ? 'ESM' : 'CommonJS', typeof module);

Source: Node.js API: Modules: Packages (Determining module system)

With a package.json that has no type, "type": "module" and "type": "commonjs" respectively, the result was the same on Node.js 26, 24 and 22:

notype   probe.js   CommonJS object
notype   probe.mjs  ESM undefined
notype   probe.cjs  CommonJS object
typemod  probe.js   ESM undefined
typemod  probe.mjs  ESM undefined
typemod  probe.cjs  CommonJS object
typecjs  probe.js   CommonJS object
typecjs  probe.mjs  ESM undefined
typecjs  probe.cjs  CommonJS object

To turn the whole project into ES modules, set the field once, for example with npm pkg set type=module.

Syntax detection

A file is ambiguous when it has a .js extension (or no extension) and no controlling package.json, or one without a "type" field; string input from --eval or standard input is ambiguous too unless --input-type is given. For ambiguous input Node.js runs the code as CommonJS first and, if the parser reports syntax that is only valid in an ES module, evaluates it again as an ES module. The syntax that counts as ES module syntax is exactly the syntax that would throw in CommonJS:

  • import statements (but not import() expressions, which are valid in CommonJS),

  • export statements,

  • import.meta references,

  • await at the top level of a module, and

  • top-level lexical declarations (const, let, class) of a CommonJS wrapper variable: require, module, exports, __filename or __dirname.

Four ambiguous files, each running as an ES module thanks to detection
// esm-import.js
import { sep } from 'node:path';
console.log('import statement ->', typeof require === 'undefined' ? 'ESM' : 'CommonJS', sep);

// esm-tla.js
const v = await Promise.resolve(42);
console.log('top-level await ->', v);

// esm-meta.js
console.log('import.meta ->', import.meta.url.startsWith('file:'));

// esm-redecl.js
const require = (name) => `fake ${name}`;
console.log('redeclared require ->', require('x'), typeof module);

// cjs-dyn.js stays CommonJS: import() alone is not ES module syntax
import('node:os').then((o) => console.log('dynamic import() only ->', typeof o.platform, typeof require));

Source: Node.js API: Modules: Packages (Syntax detection)

All four ES module files ran on Node.js 26, 24 and 22 (output import statement -> ESM /, top-level await -> 42, import.meta -> true, redeclared require -> fake x undefined), while the dynamic-import file stayed CommonJS (dynamic import() only -> function function). Detection is not free. When the nearest package.json exists but has no "type", all three lines also printed a process warning on standard error, whose code is MODULE_TYPELESS_PACKAGE_JSON (observed on all three lines; the code is not listed in the API reference):

(node:89704) [MODULE_TYPELESS_PACKAGE_JSON] Warning: Module type of file:///.../notype/esm-import.js is not specified and it doesn't parse as CommonJS.
Reparsing as ES module because module syntax was detected. This incurs a performance overhead.
To eliminate this warning, add "type": "module" to /.../notype/package.json.

The warning is the practical argument for always writing the "type" field: the file is parsed twice. With no package.json at all the file ran silently. Detection can be switched off with --no-experimental-detect-module, after which the same import statement fails with SyntaxError: Cannot use import statement outside a module; and the string inputs are detected as well:

Detection for --eval and standard input, and the explicit flag
node --eval "import { sep } from 'node:path'; console.log('eval detect', sep)"
echo "import { sep } from 'node:path'; console.log('stdin detect', sep);" | node
node --input-type=module -e "console.log(typeof require, import.meta.url.slice(0,5))"
node --no-experimental-detect-module -e "import 'node:path'"

Source: Node.js API: Command-line options (--input-type, --no-experimental-detect-module)

The four commands printed eval detect /, stdin detect /, undefined file: and the SyntaxError on Node.js 26, 24 and 22. The flags are explained with the others in CLI Options, Environment & Config File. The earlier --experimental-default-type flag, which let a project change what an ambiguous file means, still existed in the Node.js 22 documentation (Stability 1.0) and is rejected as a bad option by Node.js 24.21.0 and 26.10.0.

import.meta

import.meta is an object that exists only inside ES modules. On Node.js 26.10.0 it has exactly five keys:

Table 5. The import.meta properties
Property Stability Meaning

import.meta.url

Stable

The absolute file: URL of the module, defined as in browsers.

import.meta.filename

Stable

The absolute path of the file with symlinks resolved; equals url.fileURLToPath(import.meta.url). Only present for file: modules.

import.meta.dirname

Stable

The directory of the module; equals path.dirname(import.meta.filename). Only present for file: modules.

import.meta.main

1.0 Early development

true when the module is the entry point of the process, false otherwise; the equivalent of require.main === module.

import.meta.resolve(specifier)

1.2 Release candidate

Returns the URL string a specifier would resolve to from this module, without loading it.
Everything import.meta offers in one module (meta.js)
import { readFileSync } from 'node:fs';
import { basename } from 'node:path';

console.log('url      :', basename(import.meta.url));
console.log('filename :', basename(import.meta.filename));
console.log('dirname  :', basename(import.meta.dirname));
console.log('main     :', import.meta.main);
console.log('keys     :', Object.keys(import.meta).sort().join(', '));

// read a sibling file relative to this module, whatever the working directory is
const books = JSON.parse(readFileSync(new URL('./data/books.json', import.meta.url), 'utf8'));
console.log('books    :', books.length);

// import.meta.resolve() returns a URL string and never loads the module
console.log(import.meta.resolve('./config.js').endsWith('/ex4/config.js'));
console.log(import.meta.resolve('shelf-ui').endsWith('/shelf-ui/index.js'));
console.log(import.meta.resolve('shelf-ui/asset.css').endsWith('/css/asset.css'));
console.log(import.meta.resolve('#config').endsWith('/config.js'));
console.log(import.meta.resolve('node:fs'));
try {
  import.meta.resolve('shelf-ui/private.js');
} catch (error) {
  console.log(error.code);
}
console.log(import.meta.resolve('./does-not-exist.js').endsWith('does-not-exist.js'));

Source: Node.js API: ECMAScript modules (import.meta)

The scratch project has a node_modules/shelf-ui package whose "exports" lists only . and ./asset.css, and a "#config" entry in "imports". Started from the file system root (cd / and an absolute path), the output was the same on all three lines:

url      : meta.js
filename : meta.js
dirname  : ex4
main     : true
keys     : dirname, filename, main, resolve, url
books    : 2
true
true
true
true
node:fs
ERR_PACKAGE_PATH_NOT_EXPORTED
true

Several details are worth remembering:

  • Starting the program from another working directory does not matter: new URL('./data/books.json', import.meta.url) is anchored to the module, unlike a relative path handed to fs, which is anchored to process.cwd().

  • When the same module is imported by another file instead of being the entry point, import.meta.main is false (checked with an importer.js that only imports meta.js). Inside an inline data: module import.meta.dirname and import.meta.filename are undefined, import.meta.url starts with data: and import.meta.main is false.

  • import.meta.filename follows symlinks: for a symlink linkmeta.js pointing at meta.js, url and filename both report meta.js; with --preserve-symlinks-main they report linkmeta.js.

  • import.meta.resolve() applies the whole resolution algorithm, including "exports" encapsulation and "imports" aliases, and so it throws for a subpath that a package does not export. It does not touch the target file: a relative specifier to a file that does not exist still returns a URL (it stopped throwing in v20.6.0 and v18.19.0), and the load fails later when you import it.

  • It can perform synchronous file system operations like require.resolve(), and it is not available inside custom loaders (it would deadlock). The non-standard second parent argument needs --experimental-import-meta-resolve.

The usual CommonJS idioms translate directly: __filename becomes import.meta.filename, __dirname becomes import.meta.dirname, require.main === module becomes import.meta.main, and require.resolve(x) becomes import.meta.resolve(x) (a URL string rather than a path). The Bookshelf server in the scratch project uses the guard shown next, so that its handlers can be imported by tests without opening a port.

Dynamic import() and top-level await

import(specifier) is an expression, not a statement. It returns a promise for the module’s namespace object, accepts any string computed at run time, and works in both ES modules and CommonJS files; it can load both module formats. In a CommonJS file it is the way to reach an ES module that must stay asynchronous (for example one with top-level await), and in an ES module it is the way to load code lazily, conditionally or by name.

An ES module may also use await at its top level, without an enclosing async function. A module that awaits becomes asynchronous: modules that import it wait until it finishes evaluating, while unrelated modules keep going. The exports become available after the awaited work completes. That makes initialisation code (reading configuration, opening a connection) a normal part of the module graph.

Top-level await in a catalogue module, and dynamic import() of a plugin chosen at run time
// catalogue.js
import { readFile } from 'node:fs/promises';

);

WebAssembly modules

WebAssembly files (.wasm) can be imported like any other module, following the ES Module Integration proposal for WebAssembly. Since Node.js v24.5.0 and v22.19.0 no --experimental-wasm-modules flag is needed. There are two forms:

  • Instance imports: import { add } from './add.wasm' instantiates the module and exposes its exports as module exports. If the module imports other things, those imports are resolved as ordinary ES module specifiers (the Wasm module name is the specifier). Stability 1.1 (Active development).

  • Source phase imports: import source mod from './add.wasm' gives a WebAssembly.Module that is not yet instantiated, so you can instantiate it several times with different import objects. The dynamic variant is import.source('./add.wasm'). Stability 1.2 (Release candidate), added in v24.0.0.

Wasm modules must also avoid import and export names that begin with the reserved prefixes wasm-js: or wasm: (importing such a module instance throws a WebAssembly.LinkError). When WebAssembly modules are imported, the JavaScript String Builtins proposal is enabled automatically (Stability 1.2, v24.5.0 and v22.19.0), which lets a module call compile-time string builtins from the wasm:js-string namespace and import string constants from wasm:js/string-constants; this page does not exercise those.

The examples avoid external tooling by assembling two tiny modules byte by byte: add.wasm exports add(a, b), and add-offset.wasm imports offset() from ./offset.js and exports addOffset(n), which returns n + offset().

Importing CommonJS from ES modules

An import can reference a CommonJS file. The CommonJS module.exports value is always the default export; in addition Node.js runs a heuristic static analysis over the CommonJS source (it is performed before the file is evaluated, using the merve lexer) to expose property assignments such as exports.title = ... as named exports. Built-in modules

Built-in modules (node:fs, node:path…​) provide a named export for every public property of their API and a default export that is the CommonJS exports object. The node: prefix is the recommended spelling: it is unambiguous and it is mandatory for a few modules that exist only with the prefix. All named exports are populated eagerly when you import a built-in module, which makes the first import marginally slower than require() or process.getBuiltinModule(), where some properties of the exports object can be initialised lazily. Named exports are snapshots of the default export: patching fs.readFileSync changes the default object, and the named export updates only after module.syncBuiltinESMExports() is called.

Evaluation order, caching and cycles

Each module URL is loaded and evaluated at most once per process; later imports receive the same module namespace. The ES module loader keeps its own cache, which is not require.cache, and there is no public way to remove an entry (a different query string creates a new entry, see Specifiers are URLs). Evaluation follows a depth-first, post-order walk of the import graph, which defines what happens in a cycle: a module that is already being evaluated is not entered again, and its bindings may still be in the temporal dead zone for the importer.

Single evaluation, and a two-module cycle (counter.js, once.js, a.js and b.js)
// once.js -- three imports of the same file, one evaluation
import './counter.js';
import './counter.js';
await import('./counter.js');
// counter.js:
// globalThis.runs = (globalThis.runs ?? 0) + 1;
// console.log('counter.js evaluated, runs =', globalThis.runs);

// a.js
import { b, readA } from './b.js';
console.log('a runs; b =', b);
export const a = 'A';
console.log('a sees its own export through b:', readA());

// b.js
import { a } from './a.js';
console.log('b runs; a is in the TDZ:', (() => { try { return a; } catch (e) { return e.name; } })());
export const b = 'B';
export const readA = () => a;

Source: Node.js API: ECMAScript modules (Introduction, import specifiers)

b runs; a is in the TDZ: ReferenceError
a runs; b = B
a sees its own export through b: A

The cycle works because b.js only reads a lazily inside a function; reading a while b.js was evaluating, before a.js had declared it, throws a ReferenceError. The standard rule applies: keep top-level code in cyclic modules free of reads of the other module’s bindings, or break the cycle.

The resolution and loading algorithm

Loading a module specifier happens in two phases. Resolution turns a specifier plus the URL of the importing module (the parent URL) into a resolved URL and a suggested format. Loading then fetches the source for that URL and checks whether the protocol and the extension are acceptable. Resolution does not decide whether a protocol can be loaded; for example it will happily resolve to an https: URL, and the load phase refuses it. The default resolver is URL-based, has no default extensions and no folder mains, looks bare specifiers up through node_modules, and does not fail on unknown extensions or protocols. The default loader supports node: built-ins, inline data: modules and file: modules, and fails on any other protocol and on unknown file extensions (it supports only .cjs, .js and .mjs as JavaScript, plus JSON, Wasm and, when enabled, add-ons).

The documentation specifies the algorithm as pseudo-code (ESM_RESOLVE). In prose it is the following sequence, applied in order.

Table 7. ESM_RESOLVE(specifier, parentURL)
Step Condition Result

First

The specifier is a valid URL

Used as parsed and reserialised (file:, node:, data:…​).

Second

It starts with /, ./ or ../

URL resolution relative to the parent URL.

Third

It starts with #

PACKAGE_IMPORTS_RESOLVE: the nearest package.json "imports" map, with the default conditions. # alone is an invalid specifier, and an unmatched key throws a "Package Import Not Defined" error (ERR_PACKAGE_IMPORT_NOT_DEFINED).

Fourth

Anything else (a bare specifier)

PACKAGE_RESOLVE, described below.

Then, for file: results

Always

Percent-encoded / or \ (%2F, %5C) is an error; a directory is ERR_UNSUPPORTED_DIR_IMPORT; a missing file is ERR_MODULE_NOT_FOUND; otherwise the real path is taken (symlinks resolved) and the format is computed by ESM_FILE_FORMAT.

PACKAGE_RESOLVE handles bare specifiers: an empty specifier is invalid; a built-in module name returns node: plus the name; the package name is the part before the first / (two segments for a scope such as @scope/pkg); a package may then self-reference through its own "name" and "exports"; otherwise the lookup walks up from the parent URL through node_modules/<name> folders until the file system root. In the first folder that exists, if the package’s package.json has "exports" it alone decides (PACKAGE_EXPORTS_RESOLVE); without "exports" the "main" field (or the bare path) is used for the package root and the subpath is taken literally. If nothing is found the result is ERR_MODULE_NOT_FOUND. The "exports" and "imports" matching is explained in package.json, exports & imports; the points that matter here are these:

  • An exact key wins over a pattern; among keys with one *, the longest prefix (and then the longest key) wins.

  • Targets in "exports" must start with ./, and may not contain .., . or node_modules segments; "imports" targets may also be bare specifiers, which are resolved as packages.

  • Conditions are matched in the object’s key order, and "default" matches always; the default condition list in the documented algorithm is ["node", "import"]. The packages page also lists module-sync and node-addons as conditions implemented in core, and more can be enabled with --conditions/-C.

  • A target that is null, or a path that is not exported, produces ERR_PACKAGE_PATH_NOT_EXPORTED: exported packages are encapsulated, so internals cannot be imported with a deep path, except by absolute URL.

ESM_FILE_FORMAT decides how the file is parsed from its URL: .mjs is module, .cjs is commonjs, .json is json, .wasm is wasm, .node is addon when add-on imports are enabled; for .js the nearest "type" wins, otherwise syntax detection runs (module if the source has ES module syntax, otherwise commonjs); an extensionless file follows the package type or detection too; any other extension gives an undefined format, and the load phase throws ERR_UNKNOWN_FILE_EXTENSION.

Where the books are outdated

Efficient Node.js (Samer Buna, O’Reilly 2025) gives a sound introduction to the two loaders, .mjs and the "type" field, but several points have moved on. It treats mixing the formats as something to be careful about because one is synchronous and the other asynchronous; require() can now load synchronous ES modules (flag-free since v22.12.0, stable since v25.4.0), leaving only top-level await as an obstacle. Its description of how files become modules mentions only the extension and the "type" field, whereas syntax detection (default since v22.7.0 and v20.19.0) now runs ambiguous files containing import or export as ES modules, at the cost of a warning when a package.json without "type" exists. For the "am I the entry point" check it points to a third-party package; since v24.2.0 and v22.18.0 there is import.meta.main (still Stability 1.0). It says that import.meta.resolve() throws when the module does not exist, which stopped being true for file URLs in v20.6.0 and v18.19.0 (a missing bare package or a non-exported subpath still throws). Its NODE_PATH explanation applies to CommonJS only, which is also what the ESM differences table above says.

Node.js Projects (Jonathan Wexler, O’Reilly 2025) tells readers to add "type": "module" for import syntax and to use .mjs for individual files, and says the ES module support was stabilised in v13.2.0 (that version only removed the flag; the stabilisation is documented in v15.3.0, v14.17.0 and v12.22.0), and that import syntax is not enabled by default (syntax detection has changed this for files without markers). Its remarks that top-level await arrives with Node 18 understate history: it was unflagged in v14.8.0. Neither book covers import attributes and JSON modules, text modules or Wasm integration, nor the removal of the assert keyword that older articles still show; code copied from such sources fails with a syntax error on every supported line.
