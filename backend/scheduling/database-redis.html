Quartz with Redis

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Quartz has no official Redis job store. The only one that exists is a community project, net.joelinn:quartz-redis-jobstore, and this page documents it as it really behaves today: what it keeps in Redis, how it locks, how it is configured, which versions of Quartz and Jedis it can run with (almost none of the current ones), what survives when Redis dies and what happens to a running job when a node dies. It then spends the rest of its length on the options that do work with the current baseline: keep Quartz on a SQL database and use Redis for the application data, or drop Quartz for a distributed @Scheduled with ShedLock’s Redis lock provider. The generic job store concepts are on Job Stores & Persistence, the same decision for MongoDB is on Quartz with MongoDB, and the reference JDBC page is Quartz with PostgreSQL.

It was written against Quartz 2.5.2, Spring Boot 4.1.1, Spring Framework 7.0.9 and Java 21 (compiled for 21, run on JDK 26.0.1 with Maven 3.9.16) and verified on 5 October 2026. Redis was redis:8 (Redis 8.10.2) and, for the SQL alternative, postgres:17 (PostgreSQL 17.11), both started with Testcontainers 2.0.5 on Docker Desktop for Apple Silicon. The store was tested with Jedis 3.3.0, the version its own POM declares, and with Boot’s managed Jedis 7.4.1. Every statement of the form "works" or "fails" below was produced by a test run on those versions and the failures are quoted verbatim. Spring Boot 3.5.16 manages the same Quartz 2.5.2 (and Jedis 6.0.0), so the store fails there for the same reasons; the Boot 3.5 differences (package names of @QuartzDataSource and friends, no Flyway or Liquibase starter) are called out where they appear and collected in What changed.

Three independent breakages explain the table, and each is visible in the store’s source:

  • Jedis. The store is compiled against redis.clients.jedis.commands.JedisCommands of Jedis 3.3.0 and calls del(String) on it. In every later Jedis major that was tried (4.4.8 up to Boot’s 7.4.1) the method no longer exists with that return type on that interface, hence the NoSuchMethodError. Boot’s dependency management pins Jedis, and the store’s POM 3.3.0 loses against it.

  • Jackson mixin. JobDetailMixin ignores isConcurrentExectionDisallowed() (the misspelling was in Quartz up to 2.4). Quartz 2.5 removed that method and added isConcurrentExecutionDisallowed(), so the property is now serialized as concurrentExecutionDisallowed and cannot be read back into JobDetailImpl.

  • The JobStore SPI. Quartz 2.5.2 added long getAcquireRetryDelay(int failureCount) to org.quartz.spi.JobStore as an abstract method. A store compiled earlier does not implement it, which is the AbstractMethodError. Anyone writing a custom store (see the option on the MongoDB page) has to implement it.

So the practical answer on the Spring Boot 4.1 and 3.5 baseline is: the community Redis store cannot be used. The only working combination, Quartz 2.4.1 with Jedis 3.3.0, means overriding two managed versions of Boot (and of anything else on the classpath that uses Jedis), losing every Quartz 2.5 feature and bug fix, and depending on a library that has not been released since 2021. The next section shows that combination because it is the only way to see the store working, to test the claims of this page and to make an informed decision, not because it is recommended.

Four details of this file were measured and matter. spring.quartz.job-store-type stays memory: Boot then does not create a DataSource-backed store, hands the properties to Spring’s SchedulerFactoryBean, and the org.quartz.jobStore.class property replaces the store (the same behaviour is described on Job Stores & Persistence; with jdbc instead the scheduler fails with DataSource name not set). Property values are strings, so the numbers are accepted by the store’s String overloads of setPort, setDatabase, setLockTimeout and setSsl. The scheduler instance id must be AUTO (see How it locks for why). And, because Quartz asks the store whether it is clustered, the log line and the SchedulerMetaData report clustered=true even for a single node, since RedisJobStore.isClustered() returns true unconditionally.

The jobs and their schedule are ordinary Spring beans, identical to the ones used on every other page of the section.

OverdueLoanRemindersJob: non-concurrent, persists its JobDataMap, counts its runs
package bookshelf;

import org.quartz.DisallowConcurrentExecution;
import org.quartz.JobExecutionContext;
import org.quartz.PersistJobDataAfterExecution;
import org.springframework.scheduling.quartz.QuartzJobBean;
import org.springframework.stereotype.Component;

@DisallowConcurrentExecution
@PersistJobDataAfterExecution
public class OverdueLoanRemindersJob extends QuartzJobBean {

    private final ReminderLog log;

    public OverdueLoanRemindersJob(ReminderLog log) {
        this.log = log;
    }

    @Override
    protected void executeInternal(JobExecutionContext context) {
        int runs = context.getJobDetail().getJobDataMap().getInt("runs") + 1;
        context.getJobDetail().getJobDataMap().put("runs", runs);
        log.record(context.getFireInstanceId(), runs);
    }
}

BookshelfSchedule: the JobDetail and its CronTrigger as beans
package bookshelf;

import org.quartz.CronScheduleBuilder;
import org.quartz.JobBuilder;
import org.quartz.JobDetail;
import org.quartz.Trigger;
import org.quartz.TriggerBuilder;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
public class BookshelfSchedule {

    @Bean
    JobDetail overdueLoanRemindersJob() {
        return JobBuilder.newJob(OverdueLoanRemindersJob.class)
                .withIdentity("overdueLoanReminders", "bookshelf")
                .usingJobData("runs", 0)
                .storeDurably()
                .build();
    }

    @Bean
    Trigger overdueLoanRemindersTrigger(JobDetail overdueLoanRemindersJob,
                                        @Value("${bookshelf.reminders.cron:0 0 2 * * ?}") String cron) {
        return TriggerBuilder.newTrigger()
                .forJob(overdueLoanRemindersJob)
                .withIdentity("overdueLoanRemindersTrigger", "bookshelf")
                .withSchedule(CronScheduleBuilder.cronSchedule(cron)
                        .withMisfireHandlingInstructionFireAndProceed())
                .build();
    }
}

RedisJobStoreTest: Testcontainers redis:8, the Bookshelf job runs and its state lives in Redis
package bookshelf;

import static org.assertj.core.api.Assertions.assertThat;

import java.time.Duration;
import java.util.List;

import org.junit.jupiter.api.Test;
import org.quartz.JobKey;
import org.quartz.Scheduler;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.containers.GenericContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

@Testcontainers
@SpringBootTest(properties = "bookshelf.reminders.cron=0/2 * * * * ?")
class RedisJobStoreTest {

    @Container
    static final GenericContainer<?> REDIS = new GenericContainer<>("redis:8").withExposedPorts(6379);

    @DynamicPropertySource
    static void redis(DynamicPropertyRegistry registry) {
        registry.add("REDIS_HOST", REDIS::getHost);
        registry.add("REDIS_PORT", () -> REDIS.getMappedPort(6379));
    }

    @Autowired Scheduler scheduler;
    @Autowired ReminderLog log;

    @Test
    void remindersFireAndStateLivesInRedis() throws Exception {
        JobKey reminders = JobKey.jobKey("overdueLoanReminders", "bookshelf");
        long deadline = System.nanoTime() + Duration.ofSeconds(20).toNanos();
        while (runs(reminders) < 3 && System.nanoTime() < deadline) {
            Thread.sleep(100);
        }

        // the scheduler really runs on the community store
        assertThat(scheduler.getMetaData().getJobStoreClass().getName())
                .isEqualTo("net.joelinn.quartz.jobstore.RedisJobStore");
        assertThat(log.entries()).hasSizeGreaterThanOrEqualTo(3);

        // @PersistJobDataAfterExecution: the counter is written back to Redis
        assertThat(runs(reminders)).isGreaterThanOrEqualTo(3);

        // what Quartz stored, as seen by redis-cli inside the container
        String keys = REDIS.execInContainer("redis-cli", "--scan", "--pattern", "bookshelf:*").getStdout();
        List<String> sorted = keys.lines().sorted().toList();
        assertThat(sorted).contains(
                "bookshelf:job:bookshelf:overdueLoanReminders",
                "bookshelf:trigger:bookshelf:overdueLoanRemindersTrigger",
                "bookshelf:triggers",
                "bookshelf:jobs");
    }

    private int runs(JobKey key) throws Exception {
        return scheduler.getJobDetail(key).getJobDataMap().getInt("runs");
    }
}

Configuration

Every org.quartz.jobStore.<name> property is set by Quartz by calling the setter set<Name> on the store, so the list of properties is the list of public setters of RedisJobStore in 1.2.0, which was read from the source. Names that look plausible but have no setter fail at startup: org.quartz.jobStore.isClustered gives NoSuchMethodException: No setter for property 'isClustered' (measured), because the store is always clustered and enabling it is done only through the scheduler’s instanceId.

The state sorted sets use the next fire time in epoch milliseconds as the score (acquired_triggers held the trigger with score 1791193856000, equal to its nextFireTime), and a trigger is in exactly one of them. This is the Redis counterpart of the TRIGGER_STATE column of QRTZ_TRIGGERS in the JDBC schema, and finding the next triggers to fire is a ZRANGEBYSCORE on waiting_triggers.

JobDataMap values are stored as strings

JobDataMap is not serialized as a BLOB as it is in the JDBC store with useProperties=false. Each value is written with toString() and read back as a String. This was measured by scheduling a job with a Long, a Boolean and a record, then reading the stored JobDetail back:

What comes back from the store (measured, JobDataTypesTest)
dryRun -> String true
book -> String Book[isbn=978-0, tags=[a, b]]
memberId -> String 42

Source: Quartz Tutorial, Lesson 3: More About Jobs and JobDetails

The typed getters of JobDataMap (getLong, getInt, getBoolean) parse a string value, so ids, counters and flags keep working (the persisted runs counter of the job above is read with getInt), and Spring’s QuartzJobBean setter binding converts strings as well. What does not survive is the type of anything else: get("memberId") returns a String, and a record, a list or any other object comes back as its toString() and cannot be turned into the object again. Put only simple values in the map (ids, flags, short strings) and read the object from the database in the job, which is the advice of Jobs & Job Data anyway.

How it locks: one global key, not row locks

Every operation of the store, reading a job, storing a trigger, acquiring the next triggers, marking a trigger fired, completing a job, runs inside the same wrapper (RedisJobStore.doWithLock). The wrapper takes one Redis key, <keyPrefix>lock, with the single-instance lock pattern, runs the operation and releases the key. The mechanics, read from AbstractRedisStorage:

  • Acquire. SET <prefix>lock <random UUID> NX PX <lockTimeout>. If it answers OK the scheduler holds the lock; otherwise it sleeps a random 75 to 125 ms and tries again, forever.

  • Release. GET the key, and if the value equals the UUID this store instance generated, DEL it. Those are two commands, not an atomic compare-and-delete (the Lua script or DELEX pattern described in Redis use cases and patterns), and the UUID is a single field of the store shared by all threads of one scheduler.

  • Expiry. If an operation takes longer than lockTimeout (30 s), the key expires and another scheduler enters while the first is still working: there is no fencing token and no lock extension.

  • Scope. One key for the whole cluster, regardless of how many jobs, triggers or schedulers exist. All operations of all nodes are serialised on it.

  • Per-trigger lock. On top of that, for triggers of jobs annotated @DisallowConcurrentExecution only (the job of this page is one), trigger_lock:<group>:<name> is set with NX PX 600000 and the scheduler instance id as the value, to mark which scheduler is running the job. The ten minutes are a constant in the source (TRIGGER_LOCK_TIMEOUT), not a property. Triggers of ordinary jobs get no such key.

Redlock, the algorithm on the Redis documentation page about distributed locks, repeats this SET NX PX on several independent Redis masters and requires a majority. This store uses only the single-instance building block on one Redis, so it has none of Redlock’s resilience against the loss of a master, and with a replica that is promoted after a master failure the lock is exactly as safe as the replication is synchronous (it is not, see Durability). Redis use cases and patterns explains the pattern and its limits.

Durability

Redis is memory first, so what survives a restart is decided by the server’s persistence settings, not by Quartz. redis:8 ships with RDB snapshots enabled (save 3600 1 300 100 60 10000), appendonly no and appendfsync everysec, all read with CONFIG GET from the container used for this page. Quartz does not choose any of them.

What to configure when Redis holds scheduling state:

  • Turn AOF on (appendonly yes), with appendfsync everysec as the usual compromise or always when losing a trigger is unacceptable and the latency is acceptable. Keep RDB as well for backups.

  • Never let Redis evict Quartz keys. redis:8 defaults to maxmemory-policy noeviction, but managed services often ship another one. Only the two lock key families carry a TTL, so volatile- policies would evict exactly the lock keys, and allkeys- policies would evict job and trigger hashes silently (see Redis architecture, keyspace and eviction).

  • Replication is asynchronous. After a Sentinel or Cluster fail-over, the promoted replica may lack the last writes of the failed master: a trigger created or rescheduled in the last moments can vanish, and a completed job can fire again. min-replicas-to-write narrows the window; WAIT and WAITAOF cannot be requested by the store. See Redis replication, Sentinel and Cluster.

  • Secure it. Anything that can write to the keyspace can create, delete or reschedule jobs, and a job is a class name that Quartz instantiates. Use requirepass and ssl as far as the store allows, bind it to private networks and see Redis security.

  • Reconcile after any loss. Jobs defined as Spring beans are re-registered at startup (the overwrite-existing-jobs behaviour of Job Stores & Persistence decides what happens to existing ones), but jobs created at runtime, such as the per-member reminders of Bookshelf, are gone: a scheduled reconciliation job that recreates them from the application database is the safety net.

Fail-over of a node

With JDBC a dead node is detected after the next check-in cycle, about eleven seconds measured on PostgreSQL with a two second check-in, and the jobs with requestsRecovery that it was running are fired again by another node. The Redis store behaves differently, and the difference was measured: the test below runs a non-concurrent job that takes 25 seconds on one scheduler, "crashes" the scheduler with shutdown(false) while the job is running (nothing is cleaned up in Redis), starts a second scheduler against the same Redis and measures how long it takes until the second scheduler runs the job.

import static org.assertj.core.api.Assertions.assertThat;

import java.util.List;

import org.junit.jupiter.api.Test;

import org.quartz.impl.StdSchedulerFactory;
import org.testcontainers.containers.GenericContainer;

/** What happens to a running non-concurrent job when its scheduler dies, and a new one takes over? */
class RedisFailoverTest {

    static final List<String> RUNNERS = new CopyOnWriteArrayList<>();
    static volatile CountDownLatch firstRun = new CountDownLatch(1);

    @DisallowConcurrentExecution
    public static class WeeklyStatistics implements Job {
        @Override
        public void execute(JobExecutionContext context) throws org.quartz.JobExecutionException {
            try {
                RUNNERS.add(context.getScheduler().getSchedulerInstanceId());
                firstRun.countDown();
                Thread.sleep(25_000);                       // long running, never finishes before the "crash"
            } catch (Exception e) {
                throw new org.quartz.JobExecutionException(e);
            }
        }
    }

    private static Scheduler scheduler(GenericContainer<?> redis, long checkinMillis) throws Exception {
        Properties p = new Properties();
        p.setProperty("org.quartz.scheduler.instanceName", "failover");
        p.setProperty("org.quartz.scheduler.instanceId", "AUTO");
        p.setProperty("org.quartz.threadPool.threadCount", "2");
        p.setProperty("org.quartz.jobStore.class", "net.joelinn.quartz.jobstore.RedisJobStore");
        p.setProperty("org.quartz.jobStore.host", redis.getHost());
        p.setProperty("org.quartz.jobStore.port", String.valueOf(redis.getMappedPort(6379)));
        p.setProperty("org.quartz.jobStore.keyPrefix", "bookshelf:");
        if (checkinMillis > 0) {
            p.setProperty("org.quartz.jobStore.clusterCheckinInterval", String.valueOf(checkinMillis));
        }
        return new StdSchedulerFactory(p).getScheduler();
    }

    private long secondsUntilTakeover(long checkinMillis, long pauseBeforeSecondNodeMillis) throws Exception {
        try (GenericContainer<?> redis = new GenericContainer<>("redis:8").withExposedPorts(6379)) {
            redis.start();
            RUNNERS.clear();
            firstRun = new CountDownLatch(1);

            Scheduler first = scheduler(redis, checkinMillis);
            first.scheduleJob(JobBuilder.newJob(WeeklyStatistics.class).withIdentity("weeklyStatistics", "bookshelf").build(),
                    TriggerBuilder.newTrigger().withIdentity("weeklyStatistics", "bookshelf").startAt(new Date())
                            .withSchedule(SimpleScheduleBuilder.repeatSecondlyForever(2)).build());
            first.start();
            assertThat(firstRun.await(20, TimeUnit.SECONDS)).isTrue();
            first.shutdown(false);                          // "crash": the job is still running, nothing is cleaned up
            Thread.sleep(pauseBeforeSecondNodeMillis);

            Scheduler second = scheduler(redis, checkinMillis);
            second.start();
            long started = System.nanoTime();

                while (System.nanoTime() - started < TimeUnit.SECONDS.toNanos(60)) {
                    if (RUNNERS.size() > 1) {
                        return TimeUnit.NANOSECONDS.toSeconds(System.nanoTime() - started);
                    }
                    Thread.sleep(200);
                }
                return -1;                                  // had not taken over after 60 s
            } finally {
                second.shutdown(false);
            }
        }
    }

        long fastButImmediate = secondsUntilTakeover(2_000, 0);

        System.out.println("RESULT clusterCheckinInterval=2000, second node at once: " + fastButImmediate + " s");
        System.out.println("RESULT default clusterCheckinInterval (240000), second node 3 s later: " + defaults + " s");
    }
}

These numbers match what the source of AbstractRedisStorage does. A scheduler writes its heartbeat (last_instance_active_time) only when it acquires triggers. Orphaned ACQUIRED and BLOCKED triggers are released by a sweep that runs when the scheduler’s own heartbeat is missing (a freshly started node, hence "immediately at its first scan") or when ten minutes have passed since the last sweep of any node. A trigger that carries a trigger_lock, which means a trigger of a @DisallowConcurrentExecution job such as this one, is only released when the instance named in the lock has not checked in for clusterCheckinInterval; a trigger without one is released by the next sweep. With the default of four minutes, a restarted application therefore waits minutes, not seconds, for its non-concurrent jobs, and a cluster whose nodes are not restarted can wait for the next ten-minute sweep (that last part was read from the source, not run, because it needs minutes of waiting). The same mechanism is a plausible reason why the restart check of the compatibility matrix failed in one run, in which the application was restarted immediately after it had been stopped; that explanation was not verified.

There is no equivalent of requestsRecovery: the job running on the dead node is never re-fired, it simply stays blocked until the sweep releases its trigger, and the next scheduled fire time is the one that runs. For the weekly statistics report of Bookshelf, which must be recovered after a crash, that is the wrong behaviour, and the JDBC clustering of Clustering is the right tool.

package bookshelf;

import java.time.Duration;

import org.quartz.JobExecutionContext;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.scheduling.quartz.QuartzJobBean;

/** Reads the loan from Redis and sends the reminder at most once, however often Quartz runs it. */
public class MemberReminderJob extends QuartzJobBean {

    private final StringRedisTemplate redis;
    private final ReminderSender sender;

    public MemberReminderJob(StringRedisTemplate redis, ReminderSender sender) {
        this.redis = redis;
        this.sender = sender;
    }

    @Override
    protected void executeInternal(JobExecutionContext context) {
        String loanId = context.getMergedJobDataMap().getString("loanId");
        String status = (String) redis.opsForHash().get("loan:" + loanId, "status");
        if (!"OPEN".equals(status)) {
            return;                                   // returned (or deleted) in the meantime
        }
        Boolean first = redis.opsForValue()
                .setIfAbsent("reminder-sent:" + loanId, "1", Duration.ofDays(30));
        if (Boolean.TRUE.equals(first)) {             // idempotency guard: SET key value NX EX ...
            sender.send(loanId, context.getMergedJobDataMap().getString("memberId"));
        }
    }
}

                JobBuilder.newJob(MemberReminderJob.class).withIdentity(key)
                        .usingJobData(new JobDataMap(Map.of("loanId", loanId, "memberId", memberId)))
                        .build(),
                TriggerBuilder.newTrigger().withIdentity("loan-" + loanId, "reminders")
                        .startAt(Date.from(remindAt)).build());
    }

    public void giveBack(String loanId) throws SchedulerException {
        redis.opsForHash().put("loan:" + loanId, "status", "RETURNED");
        scheduler.deleteJob(JobKey.jobKey("loan-" + loanId, "reminders"));
    }
}

A dedicated database for Quartz

The configuration above uses the application’s only DataSource. As soon as the application has a second one (a primary business database next to the Quartz one), Boot’s JDBC store needs the business one marked @Primary and the Quartz one @QuartzDataSource; with no @Primary (even if one is @QuartzDataSource) it silently falls back to the RAM store (measured on the PostgreSQL work of this section: jobs lost on restart and no error). Flyway then needs @FlywayDataSource on the same bean to migrate the right database. This was run with two PostgreSQL containers.

Option: no Quartz, ShedLock with Redis

If the job does not need persistence across restarts, misfire policies or runtime scheduling (the cache refresh of Bookshelf is the textbook example), @Scheduled with ShedLock is enough, and Redis is a good lock store because the application already has a Redis. The lock provider is net.javacrumbs.shedlock:shedlock-provider-redis-spring:7.10.1 (the latest release on Maven Central on 5 October 2026, compiled against Spring Data Redis 4.1.1), together with net.javacrumbs.shedlock:shedlock-spring:7.10.1 for @EnableSchedulerLock and @SchedulerLock. The class is net.javacrumbs.shedlock.provider.redis.spring.RedisLockProvider. Its constructors take a RedisConnectionFactory (or a StringRedisTemplate), an optional environment name (default default) and an optional key prefix (default job-lock), and a RedisLockProvider.Builder adds a safeUpdate flag.

Its mechanics, from the 7.10.1 sources: the key is <keyPrefix>:<environment>:<lockName>, for example job-lock:bookshelf:catalogueRefresh; locking is SET key value NX PX <lockAtMostFor>, the value is ADDED:<timestamp>@<host>:<uuid>; unlocking deletes the key, or, when lockAtLeastFor has not elapsed yet, shortens its TTL to the remainder. With safeUpdate(true) the delete and the TTL update run as Lua scripts that act only if the value is still the caller’s, which stops a node whose lock had expired from releasing someone else’s. This is the single-instance lock of the previous sections, with a better release, used to skip a duplicate run rather than to guard data.

ShedLockRedisTest: two instances of the same application, one execution per tick
package lockdemo;

import static org.assertj.core.api.Assertions.assertThat;

import java.time.Duration;
import java.time.Instant;
import java.util.List;
import java.util.Optional;
import java.util.concurrent.CopyOnWriteArrayList;

import net.javacrumbs.shedlock.core.LockConfiguration;
import net.javacrumbs.shedlock.core.LockProvider;
import net.javacrumbs.shedlock.core.SimpleLock;
import net.javacrumbs.shedlock.provider.redis.spring.RedisLockProvider;
import net.javacrumbs.shedlock.spring.annotation.EnableSchedulerLock;
import net.javacrumbs.shedlock.spring.annotation.SchedulerLock;

import org.junit.jupiter.api.Test;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.connection.RedisConnectionFactory;
import org.springframework.data.redis.connection.RedisStandaloneConfiguration;
import org.springframework.data.redis.connection.lettuce.LettuceConnectionFactory;
import org.springframework.scheduling.annotation.EnableScheduling;
import org.springframework.scheduling.annotation.Scheduled;
import org.testcontainers.containers.GenericContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

@Testcontainers
class ShedLockRedisTest {

    /** Every execution of the scheduled method, from both "instances". */
    static final List<Long> EXECUTIONS = new CopyOnWriteArrayList<>();

    @Container
    static final GenericContainer<?> REDIS = new GenericContainer<>("redis:8").withExposedPorts(6379);

    @Configuration
    @EnableScheduling
    @EnableSchedulerLock(defaultLockAtMostFor = "PT30S")
    static class InstanceConfig {

        @Bean(destroyMethod = "destroy")
        LettuceConnectionFactory connectionFactory() {
            return new LettuceConnectionFactory(
                    new RedisStandaloneConfiguration(REDIS.getHost(), REDIS.getMappedPort(6379)));
        }

        @Bean
        LockProvider lockProvider(RedisConnectionFactory connectionFactory) {
            return new RedisLockProvider(connectionFactory, "bookshelf");
        }

        @Bean
        CatalogueRefresh catalogueRefresh() {
            return new CatalogueRefresh();
        }
    }

    static class CatalogueRefresh {

        @Scheduled(fixedRate = 1000)
        @SchedulerLock(name = "catalogueRefresh", lockAtMostFor = "PT10S", lockAtLeastFor = "PT0.9S")
        public void refresh() {
            EXECUTIONS.add(System.currentTimeMillis());
        }
    }

    private static AnnotationConfigApplicationContext startInstance() {
        AnnotationConfigApplicationContext context = new AnnotationConfigApplicationContext();
        context.register(InstanceConfig.class);
        context.refresh();
        return context;
    }

    @Test
    void twoInstancesRunTheJobOncePerTick() throws Exception {
        try (AnnotationConfigApplicationContext first = startInstance();
             AnnotationConfigApplicationContext second = startInstance()) {
            Thread.sleep(6500);

            List<Long> times = EXECUTIONS.stream().sorted().toList();
            long spanSeconds = (times.get(times.size() - 1) - times.get(0)) / 1000;
            System.out.println("RESULT executions=" + times.size() + " spanSeconds=" + spanSeconds);
            // two instances tick every second, yet the job ran about once per second in total, not twice
            assertThat(times.size()).isBetween(3, (int) spanSeconds + 2);

            // the lock lives in one Redis key, present between ticks because of lockAtLeastFor
            String key = "";
            for (int attempt = 0; attempt < 40 && key.isEmpty(); attempt++) {
                key = REDIS.execInContainer("redis-cli", "--scan", "--pattern", "job-lock:*").getStdout().trim();
                Thread.sleep(50);
            }
            assertThat(key).isEqualTo("job-lock:bookshelf:catalogueRefresh");
        }
    }

    @Test
    void lockProviderHandsOutTheLockOnce() throws Exception {
        LettuceConnectionFactory factory = new LettuceConnectionFactory(
                new RedisStandaloneConfiguration(REDIS.getHost(), REDIS.getMappedPort(6379)));
        factory.afterPropertiesSet();
        try {
            LockProvider provider = new RedisLockProvider.Builder(factory)
                    .environment("bookshelf").keyPrefix("job-lock").safeUpdate(true).build();
            LockConfiguration configuration = new LockConfiguration(
                    Instant.now(), "weeklyStatistics", Duration.ofSeconds(30), Duration.ZERO);

            Optional<SimpleLock> first = provider.lock(configuration);
            Optional<SimpleLock> second = provider.lock(configuration);
            assertThat(first).isPresent();
            assertThat(second).isEmpty();                    // SET key value NX PX 30000 returned nil

            first.get().unlock();                            // Lua script: delete only if the value is still ours
            assertThat(provider.lock(configuration)).isPresent();
        } finally {
            factory.destroy();
        }
    }
}

Other NoSQL stores

The same conclusion applies to the other NoSQL databases documented on this site. Quartz 2.5.2 ships a RAM store and the JDBC stores, and none of the databases below was tested with a third-party Quartz store for this section, so the dependable pattern is the same as for MongoDB and Redis: Quartz on a small SQL database, the application data wherever it belongs, idempotent jobs and a reconciliation job to cover the missing shared transaction. That is the first option of Quartz with MongoDB. The data side is documented in Couchbase (Spring Data in Spring Data Couchbase), Neo4j (Spring Data Neo4j) and Elasticsearch. A job that only needs to run once across several instances, with no persistence of its own, can use a ShedLock provider for the store it already has, as in the previous section.

Pitfalls

Table 7. Pitfalls of Quartz with Redis
Pitfall What happens What to do

Using quartz-redis-jobstore with Boot’s managed versions

Startup fails with NoSuchMethodError on JedisCommands.del(String) (Jedis 7.4.1) or, with Jedis 3.3.0 on Quartz 2.5.2, a Jackson UnrecognizedPropertyException and an AbstractMethodError in the scheduler thread

Do not use it on Quartz 2.5. If you must, pin quartz.version 2.4.1 and jedis.version 3.3.0 and test every upgrade

Setting org.quartz.jobStore.isClustered

NoSuchMethodException: No setter for property 'isClustered'

The store is always clustered; set org.quartz.scheduler.instanceId to AUTO

Leaving the instance id at its default

The default id is NON_CLUSTERED and it is the value written into the trigger_lock keys and the heartbeat hash, so two nodes cannot tell their triggers apart

org.quartz.scheduler.instanceId=AUTO on every node

job-store-type: jdbc together with jobStore.class

DataSource name not set

Keep job-store-type at memory when the store comes from spring.quartz.properties

Values in the JobDataMap that are not strings

They come back as strings (42 as "42", a record as its toString())

Only store ids and flags, read the data from the database in the job

: in job, trigger or group names

Keys are parsed by splitting on the delimiter, so loan:1001 becomes loan

Use - or _ in names (the section’s loan-<id> convention) or change keyDelimiter

Empty keyPrefix, shared database

Quartz keys mix with application keys in database 0

Always set a prefix such as bookshelf: and a dedicated database or instance

Default Redis persistence

After a crash of Redis the keys are gone (11 keys before, 0 after a SIGKILL)

appendonly yes, replicas, min-replicas-to-write, backups

Eviction policy other than noeviction

Job or trigger hashes can be evicted silently, or only the lock keys with volatile-*

maxmemory-policy noeviction on the Redis that holds Quartz

Expecting requestsRecovery

The store never re-fires a job interrupted by a crash

Use JDBC clustering for jobs that must recover, or make the job restartable by design

Waiting for fail-over with the default clusterCheckinInterval

A restarted node did not take over a blocked trigger within 60 s; the sweep is gated by 4 minutes and 10 minutes

Lower clusterCheckinInterval, restart nodes only after it has elapsed, and measure it in your environment

lockTimeout shorter than the slowest store operation

The global lock expires in the middle of an operation and another node enters

Keep the default 30 s and keep Redis latency low

A Redis ACL user or TLS client certificates

Only a password and a TLS boolean exist

Protect the default user with requirepass, or do not use the store

@Primary on the business DataSourceProperties bean

The Quartz DataSource is built from the business properties and both point at the same database

Mark only the DataSource as @Primary, give each properties bean its own name

Running the Quartz script as a migration unchanged

DROP TABLE IF EXISTS lines in tables_postgres.sql are harmless on a new schema and a hazard in a migration that is ever replayed

Remove them from the Flyway migration or use the bundled Liquibase changelog

ShedLock with a short lockAtMostFor

If the job runs longer, the key expires and a second instance runs it concurrently

Choose lockAtMostFor above the longest run, see Scheduling & ShedLock

What changed

  • Quartz 2.4 to 2.5. JobDetail.isConcurrentExectionDisallowed() (the misspelled method) was removed and isConcurrentExecutionDisallowed() is the only one, and JobStore gained the abstract method getAcquireRetryDelay(int). Both break stores compiled for earlier versions, including this one and quartz-mongodb. Terracotta was removed in 2.4.0, so JDBC remains the only officially supported store for clusters, as collected on Migration & What’s Changed.

  • Jedis. The store’s 3.3.0 is the last version it works with. Spring Boot 3.5.16 manages Jedis 6.0.0 and Spring Boot 4.1.1 manages 7.4.1, and every major in between that was tried fails identically.

  • Spring Boot 3.5 to 4.1. QuartzDataSource, QuartzTransactionManager and SchedulerFactoryBeanCustomizer moved to org.springframework.boot.quartz.autoconfigure, the Flyway and Liquibase starters were added, and DataSourceProperties moved to org.springframework.boot.jdbc.autoconfigure. The spring.quartz.* property names did not change. Both lines manage Quartz 2.5.2, so the community Redis store fails on both; it was only run on 4.1.1.

  • ShedLock. 7.10.1 is the current release of the Redis provider on Maven Central; it has the Builder with the safeUpdate option used above and is built against Spring Data Redis 4.1.1.
