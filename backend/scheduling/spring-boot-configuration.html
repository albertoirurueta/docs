Spring Boot Configuration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Spring Boot turns Quartz into a handful of spring.quartz.* properties, a hook for code (SchedulerFactoryBeanCustomizer) and a pass-through for every raw Quartz key. This page is the reference for all three: which property does what and what it defaults to, which layer wins when two of them say different things, and what Boot does not do for you (read quartz.properties, register listener beans, use your Executor bean, run two schedulers). The first steps with the starter are on Getting Started with Spring Boot, the store-specific properties are treated in depth on Job Stores & Persistence, and the general Spring Boot mechanics (property sources, profiles, relaxed binding) are on Configuration and Profiles.

It was written against Quartz 2.5.2, Spring Boot 4.1.1, Spring Framework 7.0.9 and Java 21, and verified on 5 October 2026: every default below was read from the 4.1.1 sources and every behaviour was run in a test project on exactly those versions (macOS, JDK 25 running Java 21 bytecode, Maven 3.9, PostgreSQL 17 in Docker), and the outputs are quoted, not assumed. Spring Boot 3.5.16 manages the same Quartz 2.5.2 and uses the same property names, with these differences: the auto-configuration classes live in org.springframework.boot.autoconfigure.quartz instead of org.springframework.boot.quartz.autoconfigure, the jdbc.* settings are a nested class of QuartzProperties that has no continue-on-error property, and Spring Framework is 6.2.19. They are collected in What changed.

Where a setting comes from

A Quartz scheduler under Boot is configured in layers, and knowing the order explains most surprises. Boot reads spring.quartz.* into QuartzProperties and QuartzJdbcProperties, creates one SchedulerFactoryBean from them, lets every SchedulerFactoryBeanCustomizer bean change it, and Spring’s SchedulerFactoryBean finally merges all Quartz keys into one java.util.Properties object that it hands to Quartz’s StdSchedulerFactory.

flowchart TD A["application.yml, profile files, environment: spring.quartz.*"] --> B["QuartzProperties and QuartzJdbcProperties"] B --> C["QuartzAutoConfiguration builds ONE SchedulerFactoryBean: name, auto-startup, startup-delay, shutdown wait, overwrite flag, SpringBeanJobFactory, JobDetail, Trigger and Calendar beans"] A2["spring.quartz.properties.org.quartz.*, raw keys"] --> C C --> D["SchedulerFactoryBeanCustomizer beans in Order: Boot's own JDBC customizer at order 0, yours after it"] D --> E["SchedulerFactoryBean merges the keys: Spring defaults first, then the configLocation file if one was set, then quartzProperties on top"] E --> F["StdSchedulerFactory initialize with the merged Properties"] F --> G["Scheduler: job store, thread pool, plugins, global listeners"]
Figure 1. How the configuration reaches Quartz (QuartzAutoConfiguration and SchedulerFactoryBean, read from the 4.1.1 and 7.0.9 sources)

The layers, from the weakest to the strongest, are these. Each row was checked in SchedulerFactoryBean.initSchedulerFactory.

Table 1. Who wins when two layers set the same key
Rank Layer What it contributes

1

Quartz’s code defaults

Used only for keys nobody set: a RAMJobStore, instance id NON_CLUSTERED, idleWaitTime 30000 ms and so on. The quartz.properties file inside the Quartz jar is not a layer: it is read only by new StdSchedulerFactory() without arguments, and Spring always passes properties.

2

Spring’s defaults

org.quartz.threadPool.class=org.quartz.simpl.SimpleThreadPool and org.quartz.threadPool.threadCount=10, set by SchedulerFactoryBean itself (or LocalTaskExecutorThreadPool when a task executor is set). ResourceLoaderClassLoadHelper is added as class loading helper.

3

A properties file given to setConfigLocation

Only when a customizer sets it. Boot never does, so a quartz.properties on the classpath is ignored (see below).

4

spring.quartz.properties.*

Every entry overrides the same key from layers 1 to 3. Passed through only when the map is not empty.

5

Typed spring.quartz.* properties and setSchedulerName

scheduler-name replaces org.quartz.scheduler.instanceName even when both are set (measured: both set gives the Boot name).

6

Customizers

Run last, in @Order, on the SchedulerFactoryBean itself, so they can overwrite anything above (setQuartzProperties, setConfigLocation, setTaskExecutor, setJobFactory, …​).

One special case follows from putIfAbsent: with a DataSource set, org.quartz.jobStore.class defaults to LocalDataSourceJobStore unless a raw property already names a class, so a raw jobStore.class replaces the Spring-aware store (measured in Overriding org.quartz.jobStore.class). Note also that a customizer’s setQuartzProperties replaces Boot’s whole map; it does not add to it.

Source: SchedulerFactoryBean.java (v7.0.9) and QuartzAutoConfiguration.java (v4.1.1).

Every spring.quartz property

Reading the defaults from the source is one thing; asking the running Boot is better, because it is the code that decides. This test binds both property classes from an empty Environment, which is exactly what Boot does when nothing is configured.

import org.springframework.boot.context.properties.source.ConfigurationPropertySources;
import org.springframework.boot.quartz.autoconfigure.QuartzJdbcProperties;
import org.springframework.boot.quartz.autoconfigure.QuartzProperties;
import org.springframework.core.env.StandardEnvironment;

class QuartzDefaultsTest {

    static String dump() {
        Binder binder = new Binder(ConfigurationPropertySources.get(new StandardEnvironment()));
        QuartzProperties q = binder.bindOrCreate("spring.quartz", QuartzProperties.class);
        QuartzJdbcProperties j = binder.bindOrCreate("spring.quartz.jdbc", QuartzJdbcProperties.class);

                + "\nauto-startup=" + q.isAutoStartup() + "\nstartup-delay=" + q.getStartupDelay()
                + "\nwait-for-jobs-to-complete-on-shutdown=" + q.isWaitForJobsToCompleteOnShutdown()
                + "\noverwrite-existing-jobs=" + q.isOverwriteExistingJobs() + "\nproperties=" + q.getProperties()
                + "\njdbc.initialize-schema=" + j.getInitializeSchema() + "\njdbc.schema=" + j.getSchema()
                + "\njdbc.platform=" + j.getPlatform() + "\njdbc.continue-on-error=" + j.isContinueOnError()
                + "\njdbc.comment-prefix=" + j.getCommentPrefix();
    }
}

What each property does, with the measurements that are not obvious from its name:

job-store-type

memory (the default) leaves Quartz on its RAMJobStore; jdbc makes Boot pass the DataSource to Spring’s LocalDataSourceJobStore and create the schema if asked to. The enum is JobStoreType with exactly these two values. The conditions under which jdbc silently turns back into memory are the second diagram of this page, in Which job store Boot selects. A store from a library (a MongoDB or Redis store) is not a third value: it is plugged in with job-store-type left at memory and spring.quartz.properties.org.quartz.jobStore.class (measured with a RAMJobStore subclass, which Boot honoured).

scheduler-name

No default. When it is not set the scheduler is named after the SchedulerFactoryBean bean, quartzScheduler (measured). The name is part of every key in a JDBC job store (SCHED_NAME is the first column of every primary key), so all nodes of one cluster must share it and two applications that share tables must not. When both spring.quartz.scheduler-name and spring.quartz.properties.org.quartz.scheduler.instanceName are set, the first wins (measured: the scheduler was named FromBoot). Setting only the raw instanceName is the third route in SchedulerFactoryBean (read from the source; the cluster and Actuator pages use scheduler-name).

auto-startup, startup-delay and the lifecycle

auto-startup is a SchedulerFactoryBean SmartLifecycle flag. With false the scheduler is created, jobs and triggers are stored, and nothing fires until somebody calls scheduler.start(): this is how tests and "migrate then start" deployments hold the scheduler back. startup-delay is a Duration, but Boot passes it as (int) getSeconds(), so the sub-second part is cut off. All of this was measured by reading isStarted() and isInStandbyMode() right after the context was ready:

overwrite-existing-jobs, properties and jdbc

overwrite-existing-jobs decides who wins when a JobDetail or Trigger bean meets the same key in a persistent store; the decision tree and its measurement are in the "job-registration decision" section of Getting Started with Spring Boot. properties is the raw pass-through, the next section. The five jdbc.* properties (initialize-schema, schema, platform, continue-on-error, comment-prefix) are explained with their failure modes on Job Stores & Persistence; only their defaults are repeated in the reference table at the end of this page.

Raw Quartz properties: spring.quartz.properties

Everything under spring.quartz.properties is copied unchanged into the Quartz configuration, so any key from the Quartz configuration reference is available. The map has string values, so numbers and booleans are quoted in YAML.

Environment variables lose the key’s case

Quartz keys are case sensitive and mixed case (org.quartz.threadPool.threadCount). Spring Boot maps an environment variable such as SPRING_QUARTZ_PROPERTIES_ORG_QUARTZ_THREADPOOL_THREADCOUNT to the lower-case key org.quartz.threadpool.threadcount, which Quartz does not know. It is not an error; the setting just does nothing. Measured:

Loading the file explicitly takes one bean:

A customizer that loads quartz.properties
import org.springframework.boot.quartz.autoconfigure.SchedulerFactoryBeanCustomizer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.io.ClassPathResource;

@Configuration(proxyBeanMethods = false)
class QuartzFileConfiguration {

    @Bean
    SchedulerFactoryBeanCustomizer quartzPropertiesFile() {
        return factory -> factory.setConfigLocation(new ClassPathResource("quartz.properties"));
    }
}

Source: SchedulerFactoryBean Javadoc (setConfigLocation(Resource)); run in the verification test project.

Prefer spring.quartz.properties: it works with profiles, environment layers and @ConfigurationProperties tooling, and a second file next to application.yml is a second place for the same settings to disagree.

SchedulerFactoryBeanCustomizer

SchedulerFactoryBeanCustomizer is a one-method functional interface (void customize(SchedulerFactoryBean)). Boot collects every bean of that type, orders them with @Order (an unordered bean sorts last) and applies them to the factory bean just before it is returned. Boot’s own JDBC customizer, which sets the DataSource and the transaction manager, is registered at order 0, so yours run after it and can override it. It is the one supported extension point; the properties cover about half of what SchedulerFactoryBean can do, and the customizer covers the rest:

Table 9. SchedulerFactoryBean settings that only a customizer can change (verified setters, Spring Framework 7.0.9)
Setter What it is for

setGlobalJobListeners, setGlobalTriggerListeners, setSchedulerListeners

Register listeners. Boot does not pick up listener beans (measured below).

setTaskExecutor

Use a Spring Executor as the thread pool instead of SimpleThreadPool.

setJobFactory

Replace the SpringBeanJobFactory that Boot installed, for example to add MDC context or counters.

setSchedulerContextAsMap, setApplicationContextSchedulerContextKey

Global data every job can read from the SchedulerContext, and the ApplicationContext itself.

setConfigLocation, setQuartzProperties

Load a file or add keys in code.

setDataSource, setNonTransactionalDataSource, setTransactionManager

What Boot’s own JDBC customizer does; change it only when @QuartzDataSource and @QuartzTransactionManager are not enough.

setPhase, setAutoStartup, setStartupDelay, setExposeSchedulerInRepository, setWaitForJobsToCompleteOnShutdown

Lifecycle: the SmartLifecycle phase, and the properties that have a typed spring.quartz twin.

Source: SchedulerFactoryBean Javadoc and SchedulerFactoryBeanCustomizer API (Boot 4.1).

Listeners are not registered for you

A JobListener or TriggerListener that is a Spring bean is not attached to the scheduler by Boot (QuartzAutoConfiguration collects JobDetail, Trigger, Calendar and customizer beans, nothing else). Measured: a context with one JobListener bean and no customizer had the bean and 0 listeners on the scheduler. One customizer closes the gap and adds global data:

BookshelfQuartzConfiguration.java: register every JobListener bean and set global data
package bookshelf;

import java.util.Map;

import org.quartz.JobListener;
import org.springframework.beans.factory.ObjectProvider;
import org.springframework.boot.quartz.autoconfigure.SchedulerFactoryBeanCustomizer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.annotation.Order;

@Configuration(proxyBeanMethods = false)
class BookshelfQuartzConfiguration {

    @Bean
    @Order(10)
    SchedulerFactoryBeanCustomizer bookshelfCustomizer(ObjectProvider<JobListener> jobListeners,
            ScheduleProperties schedule) {
        return factory -> {

Replacing the job factory

setJobFactory swaps the factory that creates job instances. Extend SpringBeanJobFactory (which is what Boot installs, with the ApplicationContext set) and call super, so that constructor injection keeps working:

A JobFactory that counts the jobs it creates
import org.quartz.spi.TriggerFiredBundle;
import org.springframework.boot.quartz.autoconfigure.SchedulerFactoryBeanCustomizer;
import org.springframework.context.ApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.quartz.SpringBeanJobFactory;

import java.util.concurrent.atomic.AtomicInteger;

@Configuration(proxyBeanMethods = false)
class JobFactoryConfiguration {

    static final AtomicInteger CREATED = new AtomicInteger();

    static class CountingJobFactory extends SpringBeanJobFactory {
        @Override
        protected Object createJobInstance(TriggerFiredBundle bundle) throws Exception {
            CREATED.incrementAndGet();
            return super.createJobInstance(bundle);
        }
    }

    @Bean
    SchedulerFactoryBeanCustomizer countingJobFactory(ApplicationContext context) {
        CountingJobFactory jobFactory = new CountingJobFactory();
        jobFactory.setApplicationContext(context);
        return factory -> factory.setJobFactory(jobFactory);
    }
}

Source: SpringBeanJobFactory Javadoc. Run with the Bookshelf jobs firing every second: the factory created 3 job instances and the overdue-loan job fired 2 times, so autowiring still worked.

The thread pool and why an Executor bean is not used

Boot’s Quartz auto-configuration never looks for an Executor, TaskExecutor or TaskScheduler bean. The only way a Spring executor reaches Quartz is SchedulerFactoryBean.setTaskExecutor, and Boot does not call it. The scheduler’s threads are the SimpleThreadPool that Quartz creates itself (<scheduler name>_Worker-N), ten of them unless configured. A common mistake is to declare a tuned ThreadPoolTaskExecutor and expect Quartz jobs to run on it.

ExecutorBeanConfiguration.java: an Executor bean that Quartz ignores
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;

@Configuration(proxyBeanMethods = false)
class ExecutorBeanConfiguration {

    @Bean(name = "myExecutor")
    ThreadPoolTaskExecutor myExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setThreadNamePrefix("my-exec-");
        executor.setCorePoolSize(2);
        executor.setMaxPoolSize(2);
        return executor;
    }
}

Source: Spring Boot: Task Execution and Scheduling and Spring Boot: Quartz Scheduler.

Measured with that bean and spring.threads.virtual.enabled=true, three jobs fired: the thread pool was SimpleThreadPool with 10 threads and the jobs ran on platform threads named BookshelfScheduler_Worker-N, none on my-exec-N. A side effect worth knowing: declaring any Executor bean made Boot’s own applicationTaskExecutor back off (applicationTaskExecutor present=false), because Boot creates it only @ConditionalOnMissingBean(Executor.class). That affects @Async and the web layer, not just Quartz.

A Spring TaskExecutor instead of the thread pool

To run jobs on a Spring executor, hand it over explicitly. The class that makes it work is org.springframework.scheduling.quartz.LocalTaskExecutorThreadPool (it exists in Spring Framework 7.0.9; SchedulerFactoryBean selects it by itself when a task executor is set). It adapts the executor to Quartz’s ThreadPool interface, and the adaptation is thin: getPoolSize() returns -1, blockForAvailableThreads() always returns 1, shutdown does nothing and runInThread calls executor.execute, returning false if the executor rejects the task. Three more consequences, two measured and one read from the source:

  • threadCount is not valid any more. With a task executor set and spring.quartz.properties.org.quartz.threadPool.threadCount still present, startup fails with ThreadPool class 'org.springframework.scheduling.quartz.LocalTaskExecutorThreadPool' props could not be configured, caused by NoSuchMethodException: No setter for property 'threadCount'. Remove every org.quartz.threadPool.* key (Spring’s default of 10 is a SimpleThreadPool setting).

  • Quartz no longer waits for running jobs. shutdown(true) waits through getThreadPool().shutdown(true), which is a no-op for this pool. With a virtual SimpleAsyncTaskExecutor and wait-for-jobs-to-complete-on-shutdown=true, close() took 1 ms and the 4-second job was still running afterwards. The executor can keep the JVM alive until the job ends (next section), but Quartz has already shut its job store down by then and does not record the job’s completion.

  • A rejection is a one-way street. When runInThread returns false, QuartzSchedulerThread logs "ThreadPool.runInThread() return false!" and calls triggeredJobComplete(…​, SET_ALL_JOB_TRIGGERS_ERROR): every trigger of that job goes to ERROR (the four rows above), and the application keeps running without that job (Quartz 2.5.2 source and the measured states).

Virtual threads

Quartz does not use virtual threads on its own: spring.threads.virtual.enabled=true changes Boot’s applicationTaskExecutor, @Async, the web server and @Scheduled, but the Quartz SimpleThreadPool keeps its platform threads (measured above). To run jobs on virtual threads, give Quartz Boot’s executor. The configuration below is switched on by a property and added by the virtual profile in the complete configuration.

A customizer that runs jobs on Boot’s applicationTaskExecutor
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.boot.quartz.autoconfigure.SchedulerFactoryBeanCustomizer;

import org.springframework.core.annotation.Order;
import org.springframework.core.task.AsyncTaskExecutor;

// inside BookshelfQuartzConfiguration
@Bean
@Order(20)
@ConditionalOnProperty(name = "bookshelf.quartz.use-application-task-executor", havingValue = "true")
SchedulerFactoryBeanCustomizer applicationTaskExecutorForJobs(
        @Qualifier("applicationTaskExecutor") AsyncTaskExecutor executor) {
    return factory -> factory.setTaskExecutor(executor);
}

When to bother: Quartz jobs that mostly wait (HTTP calls, a database) gain from virtual threads, and the concurrency limit gives the same protection as threadCount. CPU-bound jobs gain nothing. Three rules keep the split honest. First, profile-specific keys must be valid for the store they sit with (the isClustered failure above). TwoSchedulers.java: the first shape, Boot’s scheduler plus a hidden RAM scheduler
import java.util.Properties;

import org.quartz.Scheduler;
import org.quartz.SchedulerException;
import org.quartz.impl.StdSchedulerFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
class ReportsSchedulerConfiguration {

    /** Not an autowire candidate: injecting Scheduler keeps getting Boot's scheduler. Look this one up by name. */
    @Bean(destroyMethod = "shutdown", autowireCandidate = false)
    Scheduler reportsScheduler() throws SchedulerException {
        Properties properties = new Properties();
        properties.setProperty("org.quartz.scheduler.instanceName", "ReportsScheduler");
        properties.setProperty("org.quartz.threadPool.threadCount", "2");
        Scheduler scheduler = new StdSchedulerFactory(properties).getScheduler();
        scheduler.start();
        return scheduler;
    }
}

BookshelfSchedule.java: the five jobs and their triggers, driven by ScheduleProperties
package bookshelf;

import org.quartz.CronScheduleBuilder;
import org.quartz.JobBuilder;
import org.quartz.JobDetail;
import org.quartz.SimpleScheduleBuilder;
import org.quartz.Trigger;
import org.quartz.TriggerBuilder;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
@EnableConfigurationProperties(ScheduleProperties.class)
class BookshelfSchedule {

    @Bean JobDetail cacheRefreshJob() {
        return JobBuilder.newJob(CacheRefreshJob.class).withIdentity("cacheRefresh", "bookshelf").storeDurably().build();
    }

    @Bean Trigger cacheRefreshTrigger(JobDetail cacheRefreshJob, ScheduleProperties p) {
        return TriggerBuilder.newTrigger().forJob(cacheRefreshJob).withIdentity("cacheRefreshTrigger", "bookshelf")
                .withSchedule(SimpleScheduleBuilder.simpleSchedule()
                        .withIntervalInMilliseconds(p.cacheRefreshInterval().toMillis()).repeatForever()
                        .withMisfireHandlingInstructionNextWithRemainingCount()).build();
    }

    @Bean JobDetail overdueLoanRemindersJob() {
        return JobBuilder.newJob(OverdueLoanRemindersJob.class).withIdentity("overdueLoanReminders", "bookshelf")
                .usingJobData("runs", 0).storeDurably().build();
    }

    @Bean Trigger overdueLoanRemindersTrigger(JobDetail overdueLoanRemindersJob, ScheduleProperties p) {
        return cron(overdueLoanRemindersJob, "overdueLoanRemindersTrigger", p.overdueCron(), p);
    }

    @Bean JobDetail weeklyStatisticsJob() {
        return JobBuilder.newJob(WeeklyStatisticsJob.class).withIdentity("weeklyStatistics", "bookshelf").storeDurably().build();
    }

    @Bean Trigger weeklyStatisticsTrigger(JobDetail weeklyStatisticsJob, ScheduleProperties p) {
        return cron(weeklyStatisticsJob, "weeklyStatisticsTrigger", p.weeklyCron(), p);
    }

    @Bean JobDetail retentionCleanupJob() {
        return JobBuilder.newJob(RetentionCleanupJob.class).withIdentity("retentionCleanup", "bookshelf").storeDurably().build();
    }

    @Bean Trigger retentionCleanupTrigger(JobDetail retentionCleanupJob, ScheduleProperties p) {
        return cron(retentionCleanupJob, "retentionCleanupTrigger", p.retentionCron(), p);
    }

    private static Trigger cron(JobDetail job, String name, String expression, ScheduleProperties p) {
        return TriggerBuilder.newTrigger().forJob(job).withIdentity(name, "bookshelf")
                .withSchedule(CronScheduleBuilder.cronSchedule(expression).inTimeZone(p.zone())).build();
    }
}

    }

Worked example: asking the running scheduler what is configured

With this many layers, the useful habit is to ask the running scheduler, not the files. The Actuator endpoint shows jobs and triggers, SchedulerMetaData shows the engine. This is the check used throughout this page:

EffectiveConfiguration.java: what the scheduler is really running
import org.quartz.Scheduler;
import org.quartz.SchedulerMetaData;

static String describe(Scheduler scheduler) throws Exception {
    SchedulerMetaData md = scheduler.getMetaData();
    return "schedulerName=" + md.getSchedulerName()
            + "\ninstanceId=" + md.getSchedulerInstanceId()
            + "\njobStoreClass=" + md.getJobStoreClass().getName()
            + "\nthreadPoolClass=" + md.getThreadPoolClass().getName()
            + "\nthreadPoolSize=" + md.getThreadPoolSize()
            + "\nsupportsPersistence=" + md.isJobStoreSupportsPersistence()
            + "\nclustered=" + md.isJobStoreClustered();
}

Source: SchedulerMetaData Javadoc.

Output under the three configurations that matter (measured with the same getters)
default (memory)            schedulerName=BookshelfScheduler, instanceId=NON_CLUSTERED, jobStoreClass=org.quartz.simpl.RAMJobStore,
                            threadPoolClass=org.quartz.simpl.SimpleThreadPool, threadPoolSize=10, supportsPersistence=false, clustered=false
task executor set           ... threadPoolClass=org.springframework.scheduling.quartz.LocalTaskExecutorThreadPool, threadPoolSize=-1
prod (JDBC, clustered)      ... jobStoreClass=org.springframework.scheduling.quartz.LocalDataSourceJobStore, supportsPersistence=true, clustered=true

Source: output of the runs above (getMetaData() of the running scheduler).

When a setting "does nothing", compare this output with the file: a thread pool size of 10 after you set 4 is the environment-variable case, a RAMJobStore after you set jdbc is the DataSource case, a class name that is not the one you set is a customizer or a back-off.

Pitfalls

Table 17. Spring Boot configuration of Quartz: what goes wrong, why, and the fix
Symptom Cause Fix

A quartz.properties on the classpath has no effect

SchedulerFactoryBean reads a file only through setConfigLocation; Boot never sets it

Use spring.quartz.properties.*, or a customizer with setConfigLocation

org.quartz.threadPool.threadCount set through an environment variable stays at 10

The environment variable binds to the lower-case key, which Quartz ignores

Put raw keys in application.yml or in SPRING_APPLICATION_JSON

NoSuchMethodException: No setter for property 'isClustered' at startup

A JDBC-store key reached RAMJobStore: job-store-type: memory, or profiles prod,dev in the wrong order

Keep store keys in the profile that selects the store; order profiles so the store’s profile is last

job-store-type: jdbc and the jobs vanish at every restart, no error

Zero DataSource beans, or several without @Primary: Boot falls back to RAMJobStore

One DataSource, or @Primary on the application’s and @QuartzDataSource on Quartz’s; check getMetaData().getJobStoreClass()

@QuartzDataSource is ignored and the store is RAM

The jdbc configuration needs a single DataSource candidate; two beans without @Primary are not one

Add @Primary to the application’s data source

ThreadPool class …​ LocalTaskExecutorThreadPool props could not be configured

org.quartz.threadPool.threadCount (or another pool key) with a task executor set

Remove every org.quartz.threadPool.* key

Jobs do not run on the Executor bean

Boot never passes an Executor to Quartz

setTaskExecutor in a customizer; remember it also removes applicationTaskExecutor when you declare any Executor bean

Four of six triggers in state ERROR after a burst

A bounded executor rejected the tasks; LocalTaskExecutorThreadPool returns false and Quartz errors the trigger

Unbounded queue with care, or a blocking concurrency-limit; never queueCapacity=0 or reject-tasks-when-limit-reached

A running job is abandoned at shutdown, or finishes but stays EXECUTING in QRTZ_FIRED_TRIGGERS, although wait-for-jobs-to-complete-on-shutdown is true

With a Spring executor LocalTaskExecutorThreadPool.shutdown is a no-op, so Quartz shuts its job store down without waiting

spring.task.execution.shutdown.await-termination=true only keeps the JVM alive; the completion is still not recorded. Use Quartz’s own SimpleThreadPool with the wait flag, interruptJobsOnShutdownWithWait=true and a chunked InterruptableJob (Production & Best Practices: Graceful shutdown), or make requestsRecovery jobs idempotent

A second SchedulerFactoryBean makes Boot’s scheduler disappear

Boot’s is @ConditionalOnMissingBean(SchedulerFactoryBean)

Define both yourself with one @Primary, or add a plain Scheduler with autowireCandidate = false

NoUniqueBeanDefinitionException for Scheduler, also from the Actuator

Two Scheduler beans, none primary

@Primary, or hide the second one

Listener beans never run

Boot does not register listener beans

Customizer with setGlobalJobListeners / setGlobalTriggerListeners

A cron change in application.yml does nothing after the redeploy

JDBC store plus overwrite-existing-jobs: false

Set it to true, or change the trigger through the Scheduler API

A sub-second startup-delay starts the scheduler at once

(int) getSeconds() cuts the fraction off

Use whole seconds

Source: output of the runs on this page; the failure messages are quoted.
