Spring Boot Configuration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

Spring Boot turns Quartz into a handful of spring.quartz.* properties, a hook for code (SchedulerFactoryBeanCustomizer) and a pass-through for every raw Quartz key. This page is the reference for all three: which property does what and what it defaults to, which layer wins when two of them say different things, and what Boot does not do for you (read quartz.properties, register listener beans, use your Executor bean, run two schedulers). The first steps with the starter are on Getting Started with Spring Boot, the store-specific properties are treated in depth on Job Stores & Persistence, and the general Spring Boot mechanics (property sources, profiles, relaxed binding) are on Configuration and Profiles.

It was written against Quartz 2.5.2, Spring Boot 4.1.1, Spring Framework 7.0.9 and Java 21, and verified on 5 October 2026: every default below was read from the 4.1.1 sources and every behaviour was run in a test project on exactly those versions (macOS, JDK 25 running Java 21 bytecode, Maven 3.9, PostgreSQL 17 in Docker), and the outputs are quoted, not assumed. Spring Boot 3.5.16 manages the same Quartz 2.5.2 and uses the same property names, with these differences: the auto-configuration classes live in org.springframework.boot.autoconfigure.quartz instead of org.springframework.boot.quartz.autoconfigure, the jdbc.* settings are a nested class of QuartzProperties that has no continue-on-error property, and Spring Framework is 6.2.19. They are collected in What changed.

Where a setting comes from

A Quartz scheduler under Boot is configured in layers, and knowing the order explains most surprises. Boot reads spring.quartz.* into QuartzProperties and QuartzJdbcProperties, creates one SchedulerFactoryBean from them, lets every SchedulerFactoryBeanCustomizer bean change it, and Spring’s SchedulerFactoryBean finally merges all Quartz keys into one java.util.Properties object that it hands to Quartz’s StdSchedulerFactory.

flowchart TD A["application.yml, profile files, environment: spring.quartz.*"] --> B["QuartzProperties and QuartzJdbcProperties"] B --> C["QuartzAutoConfiguration builds ONE SchedulerFactoryBean: name, auto-startup, startup-delay, shutdown wait, overwrite flag, SpringBeanJobFactory, JobDetail, Trigger and Calendar beans"] A2["spring.quartz.properties.org.quartz.*, raw keys"] --> C C --> D["SchedulerFactoryBeanCustomizer beans in Order: Boot's own JDBC customizer at order 0, yours after it"] D --> E["SchedulerFactoryBean merges the keys: Spring defaults first, then the configLocation file if one was set, then quartzProperties on top"] E --> F["StdSchedulerFactory initialize with the merged Properties"] F --> G["Scheduler: job store, thread pool, plugins, global listeners"]
Figure 1. How the configuration reaches Quartz (QuartzAutoConfiguration and SchedulerFactoryBean, read from the 4.1.1 and 7.0.9 sources)

The layers, from the weakest to the strongest, are these. Each row was checked in SchedulerFactoryBean.initSchedulerFactory.

Table 1. Who wins when two layers set the same key
Rank Layer What it contributes

1

Quartz’s code defaults

Used only for keys nobody set: a RAMJobStore, instance id NON_CLUSTERED, idleWaitTime 30000 ms and so on. The quartz.properties file inside the Quartz jar is not a layer: it is read only by new StdSchedulerFactory() without arguments, and Spring always passes properties.

2

Spring’s defaults

org.quartz.threadPool.class=org.quartz.simpl.SimpleThreadPool and org.quartz.threadPool.threadCount=10, set by SchedulerFactoryBean itself (or LocalTaskExecutorThreadPool when a task executor is set). ResourceLoaderClassLoadHelper is added as class loading helper.

3

A properties file given to setConfigLocation

Only when a customizer sets it. Boot never does, so a quartz.properties on the classpath is ignored (see below).

4

spring.quartz.properties.*

Every entry overrides the same key from layers 1 to 3. Passed through only when the map is not empty.

5

Typed spring.quartz.* properties and setSchedulerName

scheduler-name replaces org.quartz.scheduler.instanceName even when both are set (measured: both set gives the Boot name).

6

Customizers

Run last, in @Order, on the SchedulerFactoryBean itself, so they can overwrite anything above (setQuartzProperties, setConfigLocation, setTaskExecutor, setJobFactory, …​).

One special case follows from putIfAbsent: with a DataSource set, org.quartz.jobStore.class defaults to LocalDataSourceJobStore unless a raw property already names a class, so a raw jobStore.class replaces the Spring-aware store (measured in Overriding org.quartz.jobStore.class). Note also that a customizer’s setQuartzProperties replaces Boot’s whole map; it does not add to it.

Source: SchedulerFactoryBean.java (v7.0.9) and QuartzAutoConfiguration.java (v4.1.1).

Every spring.quartz property

Reading the defaults from the source is one thing; asking the running Boot is better, because it is the code that decides. This test binds both property classes from an empty Environment, which is exactly what Boot does when nothing is configured.

QuartzDefaultsTest.java: the defaults, bound from nothing (Boot 4.1.1)
import org.springframework.boot.context.properties.bind.Binder;
import org.springframework.boot.context.properties.source.ConfigurationPropertySources;
import org.springframework.boot.quartz.autoconfigure.QuartzJdbcProperties;
import org.springframework.boot.quartz.autoconfigure.QuartzProperties;
import org.springframework.core.env.StandardEnvironment;

class QuartzDefaultsTest {

    static String dump() {
        Binder binder = new Binder(ConfigurationPropertySources.get(new StandardEnvironment()));
        QuartzProperties q = binder.bindOrCreate("spring.quartz", QuartzProperties.class);
        QuartzJdbcProperties j = binder.bindOrCreate("spring.quartz.jdbc", QuartzJdbcProperties.class);
        return "job-store-type=" + q.getJobStoreType() + "\nscheduler-name=" + q.getSchedulerName()
                + "\nauto-startup=" + q.isAutoStartup() + "\nstartup-delay=" + q.getStartupDelay()
                + "\nwait-for-jobs-to-complete-on-shutdown=" + q.isWaitForJobsToCompleteOnShutdown()
                + "\noverwrite-existing-jobs=" + q.isOverwriteExistingJobs() + "\nproperties=" + q.getProperties()
                + "\njdbc.initialize-schema=" + j.getInitializeSchema() + "\njdbc.schema=" + j.getSchema()
                + "\njdbc.platform=" + j.getPlatform() + "\njdbc.continue-on-error=" + j.isContinueOnError()
                + "\njdbc.comment-prefix=" + j.getCommentPrefix();
    }
}

Source: QuartzProperties API (Boot 4.1) and QuartzJdbcProperties.java (v4.1.1).

What each property does, with the measurements that are not obvious from its name:

job-store-type

memory (the default) leaves Quartz on its RAMJobStore; jdbc makes Boot pass the DataSource to Spring’s LocalDataSourceJobStore and create the schema if asked to. The enum is JobStoreType with exactly these two values. The conditions under which jdbc silently turns back into memory are the second diagram of this page, in Which job store Boot selects. A store from a library (a MongoDB or Redis store) is not a third value: it is plugged in with job-store-type left at memory and spring.quartz.properties.org.quartz.jobStore.class (measured with a RAMJobStore subclass, which Boot honoured).

scheduler-name

No default. When it is not set the scheduler is named after the SchedulerFactoryBean bean, quartzScheduler (measured). The name is part of every key in a JDBC job store (SCHED_NAME is the first column of every primary key), so all nodes of one cluster must share it and two applications that share tables must not. When both spring.quartz.scheduler-name and spring.quartz.properties.org.quartz.scheduler.instanceName are set, the first wins (measured: the scheduler was named FromBoot). Replacing the job factory

setJobFactory swaps the factory that creates job instances. Extend SpringBeanJobFactory (which is what Boot installs, with the ApplicationContext set) and call super, so that constructor injection keeps working:

A JobFactory that counts the jobs it creates
import org.quartz.spi.TriggerFiredBundle;
import org.springframework.boot.quartz.autoconfigure.SchedulerFactoryBeanCustomizer;
import org.springframework.context.ApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.quartz.SpringBeanJobFactory;

import java.util.concurrent.atomic.AtomicInteger;

@Configuration(proxyBeanMethods = false)
class JobFactoryConfiguration {

    static final AtomicInteger CREATED = new AtomicInteger();

    static class CountingJobFactory extends SpringBeanJobFactory {
        @Override
        protected Object createJobInstance(TriggerFiredBundle bundle) throws Exception {
            CREATED.incrementAndGet();
            return super.createJobInstance(bundle);
        }
    }

    @Bean
    SchedulerFactoryBeanCustomizer countingJobFactory(ApplicationContext context) {
        CountingJobFactory jobFactory = new CountingJobFactory();
        jobFactory.setApplicationContext(context);
        return factory -> factory.setJobFactory(jobFactory);
    }
}

Source: SpringBeanJobFactory Javadoc. Run with the Bookshelf jobs firing every second: the factory created 3 job instances and the overdue-loan job fired 2 times, so autowiring still worked.

The thread pool and why an Executor bean is not used

Boot’s Quartz auto-configuration never looks for an Executor, TaskExecutor or TaskScheduler bean. The only way a Spring executor reaches Quartz is SchedulerFactoryBean.setTaskExecutor, and Boot does not call it. The scheduler’s threads are the SimpleThreadPool that Quartz creates itself (<scheduler name>_Worker-N), ten of them unless configured. A common mistake is to declare a tuned ThreadPoolTaskExecutor and expect Quartz jobs to run on it.

ExecutorBeanConfiguration.java: an Executor bean that Quartz ignores
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.concurrent.ThreadPoolTaskExecutor;

@Configuration(proxyBeanMethods = false)
class ExecutorBeanConfiguration {

    @Bean(name = "myExecutor")
    ThreadPoolTaskExecutor myExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setThreadNamePrefix("my-exec-");
        executor.setCorePoolSize(2);
        executor.setMaxPoolSize(2);
        return executor;
    }
}

Source: Spring Boot: Task Execution and Scheduling and Spring Boot: Quartz Scheduler.

Measured with that bean and spring.threads.virtual.enabled=true, three jobs fired: the thread pool was SimpleThreadPool with 10 threads and the jobs ran on platform threads named BookshelfScheduler_Worker-N, none on my-exec-N. A side effect worth knowing: declaring any Executor bean made Boot’s own applicationTaskExecutor back off (applicationTaskExecutor present=false), because Boot creates it only @ConditionalOnMissingBean(Executor.class). That affects @Async and the web layer, not just Quartz.

Three more consequences, two measured and one read from the source:

  • threadCount is not valid any more.   • Quartz no longer waits for running jobs. shutdown(true) waits through getThreadPool().shutdown(true), which is a no-op for this pool. With a virtual SimpleAsyncTaskExecutor and wait-for-jobs-to-complete-on-shutdown=true, close() took 1 ms and the 4-second job was still running afterwards. The executor can keep the JVM alive until the job ends (next section), but Quartz has already shut its job store down by then and does not record the job’s completion.

  • A rejection is a one-way street. When runInThread returns false, QuartzSchedulerThread logs "ThreadPool.runInThread() return false!" and calls triggeredJobComplete(…​, SET_ALL_JOB_TRIGGERS_ERROR): every trigger of that job goes to ERROR (the four rows above), and the application keeps running without that job (Quartz 2.5.2 source and the measured states).

Virtual threads

Quartz does not use virtual threads on its own: spring.threads.virtual.enabled=true changes Boot’s applicationTaskExecutor, @Async, the web server and @Scheduled, but the Quartz SimpleThreadPool keeps its platform threads (measured above). When to bother: Quartz jobs that mostly wait (HTTP calls, a database) gain from virtual threads, and the concurrency limit gives the same protection as threadCount. CPU-bound jobs gain nothing. The simple SimpleThreadPool remains the right default for a service whose jobs are few and short, and it is the only configuration where Quartz itself does the waiting and records completion; with an executor, await-termination only keeps the JVM alive, the fired row stays EXECUTING and a surviving node re-runs a requestsRecovery job. The measured shutdown matrix and the recommended pattern (wait-for-jobs-to-complete-on-shutdown=true, org.quartz.scheduler.interruptJobsOnShutdownWithWait=true and a chunked InterruptableJob) are on Production & Best Practices: Graceful shutdown; the virtual-thread and executor questions of the whole service are on the same page.

TwoSchedulers.java: the first shape, Boot’s scheduler plus a hidden RAM scheduler
import java.util.Properties;

import org.quartz.Scheduler;
import org.quartz.SchedulerException;
import org.quartz.impl.StdSchedulerFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
class ReportsSchedulerConfiguration {

    /** Not an autowire candidate: injecting Scheduler keeps getting Boot's scheduler. Look this one up by name. */
    @Bean(destroyMethod = "shutdown", autowireCandidate = false)
    Scheduler reportsScheduler() throws SchedulerException {
        Properties properties = new Properties();
        properties.setProperty("org.quartz.scheduler.instanceName", "ReportsScheduler");
        properties.setProperty("org.quartz.threadPool.threadCount", "2");
        Scheduler scheduler = new StdSchedulerFactory(properties).getScheduler();
        scheduler.start();
        return scheduler;
    }
}

BookshelfSchedule.java: the five jobs and their triggers, driven by ScheduleProperties
package bookshelf;

import org.quartz.CronScheduleBuilder;
import org.quartz.JobBuilder;
import org.quartz.JobDetail;
import org.quartz.SimpleScheduleBuilder;
import org.quartz.Trigger;
import org.quartz.TriggerBuilder;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration(proxyBeanMethods = false)
@EnableConfigurationProperties(ScheduleProperties.class)
class BookshelfSchedule {

    @Bean JobDetail cacheRefreshJob() {
        return JobBuilder.newJob(CacheRefreshJob.class).withIdentity("cacheRefresh", "bookshelf").storeDurably().build();
    }

    @Bean Trigger cacheRefreshTrigger(JobDetail cacheRefreshJob, ScheduleProperties p) {
        return TriggerBuilder.newTrigger().forJob(cacheRefreshJob).withIdentity("cacheRefreshTrigger", "bookshelf")
                .withSchedule(SimpleScheduleBuilder.simpleSchedule()
                        .withIntervalInMilliseconds(p.cacheRefreshInterval().toMillis()).repeatForever()
                        .withMisfireHandlingInstructionNextWithRemainingCount()).build();
    }

    @Bean JobDetail overdueLoanRemindersJob() {
        return JobBuilder.newJob(OverdueLoanRemindersJob.class).withIdentity("overdueLoanReminders", "bookshelf")
                .usingJobData("runs", 0).storeDurably().build();
    }

    @Bean Trigger overdueLoanRemindersTrigger(JobDetail overdueLoanRemindersJob, ScheduleProperties p) {
        return cron(overdueLoanRemindersJob, "overdueLoanRemindersTrigger", p.overdueCron(), p);
    }

    @Bean JobDetail weeklyStatisticsJob() {
        return JobBuilder.newJob(WeeklyStatisticsJob.class).withIdentity("weeklyStatistics", "bookshelf").storeDurably().build();
    }

    @Bean Trigger weeklyStatisticsTrigger(JobDetail weeklyStatisticsJob, ScheduleProperties p) {
        return cron(weeklyStatisticsJob, "weeklyStatisticsTrigger", p.weeklyCron(), p);
    }

    @Bean JobDetail retentionCleanupJob() {
        return JobBuilder.newJob(RetentionCleanupJob.class).withIdentity("retentionCleanup", "bookshelf").storeDurably().build();
    }

    @Bean Trigger retentionCleanupTrigger(JobDetail retentionCleanupJob, ScheduleProperties p) {
        return cron(retentionCleanupJob, "retentionCleanupTrigger", p.retentionCron(), p);
    }

    private static Trigger cron(JobDetail job, String name, String expression, ScheduleProperties p) {
        return TriggerBuilder.newTrigger().forJob(job).withIdentity(name, "bookshelf")
                .withSchedule(CronScheduleBuilder.cronSchedule(expression).inTimeZone(p.zone())).build();
    }
}
