MongoDB and Quartz

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Quartz was designed around relational databases, and MongoDB is not one. Teams that keep their domain data in MongoDB therefore ask the same question when the first persistent, clustered job appears: can Quartz store its triggers in the database we already run? This page answers it with measurements. In short, there is no official MongoDB job store, the community one does not work on the Quartz version that Spring Boot manages, and the practical answer is to keep the business data in MongoDB and give Quartz a small SQL database of its own, which is option 1 below and the only option shown with a complete, tested Bookshelf example. The other three options (the community store, a custom JobStore, and no Quartz) are documented with what was measured, so that you can judge them without repeating the experiments.

The generic job-store concepts (what a store has to provide, the QRTZ_ tables, schema management, @QuartzDataSource) are on Job Stores & Persistence, the reference SQL database is PostgreSQL, and the other community store that is tested the same way is on Redis. The MongoDB side of the story (replica sets, transactions, write concern) is covered on MongoDB, especially Transactions and Replication, and the Spring Data usage on Spring Data MongoDB.

It was written against Quartz 2.5.2, Spring Boot 4.1.1, Spring Framework 7.0.9 and Java 21 and verified on 5 October 2026. Every behaviour below was run in a test project with Testcontainers 2.0.5 on the images mongo:8 (MongoDB 8.3.11, started by MongoDBContainer as a single-node replica set) and postgres:17 (PostgreSQL 17.11), with the MongoDB Java driver 5.8.1, Spring Data MongoDB 5.1.1, the PostgreSQL JDBC driver 42.7.13, Flyway 12.4.0, ShedLock 7.10.1 and the community store io.fluidsonic.mirror:quartz-mongodb:2.2.0-rc2; the results are quoted, not assumed. Spring Boot 3.5.16 manages the same Quartz 2.5.2, so the findings about Quartz and the community store are identical there; only the package of @QuartzDataSource (org.springframework.boot.autoconfigure.quartz instead of org.springframework.boot.quartz.autoconfigure), the package of DataSourceProperties (org.springframework.boot.autoconfigure.jdbc), the MongoDB connection property (spring.data.mongodb.uri instead of spring.mongodb.uri), Spring Framework 6.2.19 and the Testcontainers 1.x package of MongoDBContainer differ.

The status of Quartz on MongoDB

Quartz has no official MongoDB job store. Its own job stores are the in-memory RAMJobStore and the JDBC stores (JobStoreTX and JobStoreCMT), and clustering is JDBC only since the Terracotta store was removed in 2.4.0. The only MongoDB store in circulation is a community project, quartz-mongodb (class com.novemberain.quartz.mongodb.MongoDBJobStore). Its repository is archived on GitHub and read-only, with the last push in November 2022. Its README still tells you to fetch it from Bintray and JCenter, and JCenter has been shut down. The only copy on Maven Central is an unofficial mirror, io.fluidsonic.mirror:quartz-mongodb, whose latest version is 2.2.0-rc2 (a release candidate published in 2021 and compiled against Quartz 2.3.2 and the MongoDB driver 4.0.5). That version predates Quartz 2.4 and 2.5 by years.

The consequence was measured, not guessed: on Quartz 2.5.2, the version that both Spring Boot 4.1 and Spring Boot 3.5 manage, the store loads, the scheduler reports that it has started, and then no job ever fires, because the scheduler thread dies silently. The details and the matrix are in Option 2: the community quartz-mongodb store, tested and broken on Quartz 2.5.x. This is why the four options are not equal:

Option 1: Quartz on SQL, business data in MongoDB

The idea is to stop asking Quartz to store its state in MongoDB at all. Quartz keeps its eleven QRTZ_ tables in a small relational database that exists only for it (PostgreSQL here, any database from the support matrix works), and the application keeps loans and members in MongoDB exactly as before. Nothing about MongoDB is special for Quartz: the job class loads whatever it needs from MongoDB through a Spring Data repository when it fires, and the code that creates and cancels reminders runs next to the code that writes loans.

This costs one more database to operate, but it is a database that holds a few hundred small rows and that every operations team knows how to back up and monitor. In return you get everything the JDBC store offers: row-lock clustering (see Clustering), misfire handling (see Misfires), persistence across restarts and runtime scheduling with Scheduler.scheduleJob. The price, and it is the main point of this section, is that there is no transaction spanning MongoDB and the Quartz tables. MongoDB transactions cannot include a PostgreSQL connection, and this page does not use a distributed (XA) transaction manager, so the two systems can disagree after a crash. The design below accepts that and makes every disagreement harmless or self-healing.

The Bookshelf reminders

The running scenario for this option is the per-member "return your book" reminder: when a loan is made, a reminder is scheduled one day before the due date (the bookshelf.reminders.lead property); when the book is returned first, the reminder is cancelled. The conventions are the ones used on the other pages: job key and trigger key loan-<loanId> in the group reminders, job data memberId and loanId, job class MemberReminderJob. A second job, ReminderReconciliationJob, compares MongoDB with Quartz every ten minutes and repairs whichever side is wrong.

A dedicated data source for Quartz

Because the application has no JDBC data source of its own (its data is in MongoDB), Boot would happily use a single auto-configured one. This page declares the Quartz data source explicitly anyway, for two reasons: the pool belongs to Quartz and should be sized for it (worker threads plus three connections, see Production & Best Practices), and the day somebody adds a JDBC data source for something else (an outbox, a reporting database), Quartz must not silently switch to it. A data source marked @QuartzDataSource is the one Quartz uses among the candidates, but it does not rescue a context with several data sources and no @Primary: Boot does not fail, it silently falls back to the in-memory RAMJobStore and every job is lost at restart (this was measured, see the pitfalls table). So if an application data source is added later, mark that one @Primary.

QuartzDatabaseConfig.java: a pool that only Quartz uses
package bookshelf;

import com.zaxxer.hikari.HikariDataSource;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.jdbc.autoconfigure.DataSourceProperties;
import org.springframework.boot.quartz.autoconfigure.QuartzDataSource;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import javax.sql.DataSource;

/**
 * Quartz keeps its state in a small PostgreSQL database; the business data lives in MongoDB.
 * The pool is dedicated to Quartz and sized independently of everything else.
 */
@Configuration(proxyBeanMethods = false)
class QuartzDatabaseConfig {

    @Bean
    @ConfigurationProperties("bookshelf.quartz.datasource")
    DataSourceProperties quartzDataSourceProperties() {
        return new DataSourceProperties();
    }

    @Bean
    @QuartzDataSource
    @ConfigurationProperties("bookshelf.quartz.datasource.hikari")
    HikariDataSource quartzDataSource(DataSourceProperties quartzDataSourceProperties) {
        return quartzDataSourceProperties.initializeDataSourceBuilder().type(HikariDataSource.class).build();
    }
}

The Quartz schema with Flyway

Quartz ships a DDL script per database inside its jar: org/quartz/impl/jdbcjobstore/tables_postgres.sql for PostgreSQL. The script starts with eleven DROP TABLE IF EXISTS statements (and the Spring Boot initializer runs it as is, which is why initialize-schema: always destroys data). For a migration tool the DROP lines must go, so the Flyway version of the script is the original with exactly those lines removed. It has the standard Flyway name and location, so Boot picks it up without any spring.flyway.* property; spring.flyway.locations is only needed when the scripts live elsewhere.

The Quartz schema with Liquibase

Liquibase users do not need to copy the SQL: the Quartz jar bundles a changelog, org/quartz/impl/jdbcjobstore/liquibase.quartz.init.xml, with a single changeset (quartz-init, author quartz). It defines the tables with a table_prefix property (QRTZ_) and a blob_type property that resolves to BYTEA on PostgreSQL and BLOB elsewhere. A master changelog only has to include it from the classpath. Replace the Flyway starter with spring-boot-starter-liquibase (or disable Flyway with spring.flyway.enabled=false) and set spring.liquibase.change-log.

The domain side: documents and repositories

The domain is ordinary Spring Data MongoDB, nothing in it knows about Quartz. A Loan is an immutable record; reminderSentAt is what makes the reminder job idempotent, and returned is how cancellation is expressed in the source of truth.

Loan.java and LoanRepository.java: the source of truth
package bookshelf.loans;

import org.springframework.data.annotation.Id;
import org.springframework.data.mongodb.core.index.Indexed;
import org.springframework.data.mongodb.core.mapping.Document;

import java.time.Instant;

@Document("loans")
public record Loan(
        @Id String id,
        @Indexed String memberId,
        String isbn,
        Instant dueAt,
        boolean returned,
        Instant reminderSentAt) {

    public Loan(String memberId, String isbn, Instant dueAt) {
        this(null, memberId, isbn, dueAt, false, null);
    }

    public Loan markReturned() {
        return new Loan(id, memberId, isbn, dueAt, true, reminderSentAt);
    }
}

import org.springframework.data.mongodb.repository.MongoRepository;

import java.util.List;

public interface LoanRepository extends MongoRepository<Loan, String> {

    /** Loans whose reminder still has to be sent. */
    List<Loan> findByReturnedFalseAndReminderSentAtIsNull();
}

Creating and cancelling reminders at runtime

All Quartz calls for reminders live in one class, so that the key convention exists in one place. schedule builds a job and a trigger and stores them with scheduleJob(job, Set.of(trigger), true): the true means replace existing, so calling it twice for the same loan leaves exactly one job and one trigger (tested). cancel uses deleteJob, which returns false instead of throwing when the job is already gone, so cancelling is also safe to repeat.

The catch in schedule comes from a real race that the test run produced: the reconciliation job and the request that makes the loan can create the same reminder at the same moment, and with a persistent store the loser of that race gets a JobPersistenceException whose cause is a duplicate key on the primary key of QRTZ_JOB_DETAILS. The reminder exists in that case, so the method checks checkExists and swallows the exception only when it does.

The misfire instruction withMisfireHandlingInstructionFireNow makes a reminder that was due while the service was down fire as soon as it is back (see Misfires); the job still checks the loan, so a late reminder for a returned book is skipped.

ReminderScheduler.java: the only class that talks to Quartz about reminders
package bookshelf.loans;

import bookshelf.ReminderProperties;
import org.quartz.JobBuilder;
import org.quartz.JobDetail;
import org.quartz.JobKey;
import org.quartz.Scheduler;
import org.quartz.SimpleScheduleBuilder;
import org.quartz.SchedulerException;
import org.quartz.Trigger;
import org.quartz.TriggerBuilder;
import org.quartz.impl.matchers.GroupMatcher;
import org.springframework.stereotype.Component;

import java.util.Date;
import java.util.List;
import java.util.Set;

/** The only class that talks to Quartz about member reminders. Key convention: job and trigger "loan-<loanId>" in group "reminders". */
@Component
public class ReminderScheduler {

    public static final String GROUP = "reminders";
    private static final String KEY_PREFIX = "loan-";

    private final Scheduler scheduler;
    private final ReminderProperties properties;

    ReminderScheduler(Scheduler scheduler, ReminderProperties properties) {
        this.scheduler = scheduler;
        this.properties = properties;
    }

    public static JobKey keyFor(String loanId) {
        return JobKey.jobKey(KEY_PREFIX + loanId, GROUP);
    }

    /** Creates or replaces the reminder for a loan. Calling it twice leaves exactly one job and one trigger. */
    public void schedule(Loan loan) throws SchedulerException {
        JobDetail job = JobBuilder.newJob(MemberReminderJob.class)
                .withIdentity(keyFor(loan.id()))
                .usingJobData("loanId", loan.id())
                .usingJobData("memberId", loan.memberId())
                .build();
        Trigger trigger = TriggerBuilder.newTrigger()
                .withIdentity(KEY_PREFIX + loan.id(), GROUP)
                .forJob(job)
                .startAt(Date.from(loan.dueAt().minus(properties.lead())))
                .withSchedule(SimpleScheduleBuilder.simpleSchedule()
                        .withMisfireHandlingInstructionFireNow())
                .build();
        try {
            scheduler.scheduleJob(job, Set.of(trigger), true);
        } catch (SchedulerException e) {
            // LoanService and the reconciliation job can create the same reminder at the same moment; the
            // loser gets a duplicate key error from the primary key of QRTZ_JOB_DETAILS. The reminder exists, so that is fine.
            if (!exists(loan.id())) {
                throw e;
            }
        }
    }

    /** Deleting a job that is already gone is fine: the result is false, not an exception. */
    public boolean cancel(String loanId) throws SchedulerException {
        return scheduler.deleteJob(keyFor(loanId));
    }

    public boolean exists(String loanId) throws SchedulerException {
        return scheduler.checkExists(keyFor(loanId));
    }

    public List<String> scheduledLoanIds() throws SchedulerException {
        return scheduler.getJobKeys(GroupMatcher.jobGroupEquals(GROUP)).stream()
                .filter(k -> k.getName().startsWith(KEY_PREFIX))
                .map(k -> k.getName().substring(KEY_PREFIX.length()))
                .toList();
    }
}

Source: Quartz Tutorial: Lesson 2, the API

The service writes MongoDB first and Quartz second. MongoDB is the source of truth, so a loan is never lost; if the Quartz call fails the loan exists without a reminder, which the reconciliation job repairs. The opposite order would risk a reminder for a loan that was never saved, which the job would at best skip.

LoanService.java: MongoDB first, Quartz second
package bookshelf.loans;

import org.quartz.SchedulerException;
import org.springframework.stereotype.Service;

import java.time.Instant;

/**
 * There is no transaction spanning MongoDB and the Quartz tables. MongoDB is written first (it is the source of truth),
 * Quartz second; if the second step fails the reconciliation job repairs it.
 */
@Service
public class LoanService {

    private final LoanRepository loans;
    private final ReminderScheduler reminders;

    LoanService(LoanRepository loans, ReminderScheduler reminders) {
        this.loans = loans;
        this.reminders = reminders;
    }

    public Loan lend(String memberId, String isbn, Instant dueAt) throws SchedulerException {
        Loan loan = loans.save(new Loan(memberId, isbn, dueAt));
        reminders.schedule(loan);
        return loan;
    }

    public void giveBack(String loanId) throws SchedulerException {
        loans.findById(loanId).ifPresent(loan -> loans.save(loan.markReturned()));
        reminders.cancel(loanId);
    }
}

An idempotent job

A Quartz job that touches another system must assume it can run more than once for the same logical event: a node crashes while the job runs and a job that has requestsRecovery is executed again, an operator triggers it by hand, or the reconciliation job creates a duplicate. MemberReminderJob protects itself in two ways. It first reads the loan and does nothing if the loan is missing, returned or already reminded. After sending (with the loan id as the idempotency key for the mail provider) it marks the loan with a conditional update that only matches while reminderSentAt is still null, so a concurrent duplicate changes nothing. The delivery is therefore at-least-once with a de-duplicating key, which is the honest guarantee when a mail provider call and a MongoDB write cannot be made atomic. The job gets its collaborators through constructor injection (Boot’s SpringBeanJobFactory autowires job classes) and its data through setters bound from the JobDataMap, which holds plain strings so that it stays serializable and survives a change of the job class; see Jobs & Job Data.

MemberReminderJob.java: safe to run twice
package bookshelf.loans;

import org.quartz.JobExecutionContext;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.data.mongodb.core.MongoTemplate;
import org.springframework.data.mongodb.core.query.Criteria;
import org.springframework.data.mongodb.core.query.Query;
import org.springframework.data.mongodb.core.query.Update;
import org.springframework.scheduling.quartz.QuartzJobBean;

import java.time.Instant;

/**
 * Idempotent: it can run twice for the same loan (a retry after a crash, a recovered execution, a duplicate created
 * by reconciliation) and the member still receives one reminder.
 */
public class MemberReminderJob extends QuartzJobBean {

    private static final Logger log = LoggerFactory.getLogger(MemberReminderJob.class);

    private final MongoTemplate mongo;
    private final ReminderSender sender;
    private String loanId;
    private String memberId;

    MemberReminderJob(MongoTemplate mongo, ReminderSender sender) {
        this.mongo = mongo;
        this.sender = sender;
    }

    public void setLoanId(String loanId) {
        this.loanId = loanId;
    }

    public void setMemberId(String memberId) {
        this.memberId = memberId;
    }

    @Override
    protected void executeInternal(JobExecutionContext context) {
        Loan loan = mongo.findById(loanId, Loan.class);
        if (loan == null || loan.returned() || loan.reminderSentAt() != null) {
            log.info("Reminder for loan {} skipped (missing, returned or already sent)", loanId);
            return;
        }
        sender.send(memberId, loanId);
        // Only the first writer marks the loan; a concurrent duplicate would update nothing.
        mongo.updateFirst(
                Query.query(Criteria.where("_id").is(loanId).and("reminderSentAt").is(null)),
                Update.update("reminderSentAt", Instant.now()),
                Loan.class);
    }
}

Reconciliation

The reconciliation job turns the loose coupling into an eventually consistent one. MongoDB wins every disagreement: an active loan without a Quartz job gets one, and a Quartz job in the reminders group whose loan is returned, already reminded or gone is deleted. It is @DisallowConcurrentExecution so that a slow run is never overlapped (also across cluster nodes, because the flag is stored with the job), and it reports failures with JobExecutionException(e, false) so that the next tick simply tries again. This is a polling variant of the transactional outbox pattern: the pending state (returned and reminderSentAt) is part of the loan document, so it is always written atomically with the business change, and the job derives the scheduling from it.

ReminderReconciliationJob.java: MongoDB wins
package bookshelf.loans;

import org.quartz.DisallowConcurrentExecution;
import org.quartz.JobExecutionContext;
import org.quartz.JobExecutionException;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.scheduling.quartz.QuartzJobBean;

import java.util.HashSet;
import java.util.Set;

/**
 * Makes Quartz agree with MongoDB. MongoDB wins: active loans without a Quartz job get one, Quartz jobs whose loan is
 * returned, already reminded or gone are deleted.
 */
@DisallowConcurrentExecution
public class ReminderReconciliationJob extends QuartzJobBean {

    private static final Logger log = LoggerFactory.getLogger(ReminderReconciliationJob.class);

    private final LoanRepository loans;
    private final ReminderScheduler reminders;

    ReminderReconciliationJob(LoanRepository loans, ReminderScheduler reminders) {
        this.loans = loans;
        this.reminders = reminders;
    }

    @Override
    protected void executeInternal(JobExecutionContext context) throws JobExecutionException {
        try {
            Set<String> pending = new HashSet<>();
            for (Loan loan : loans.findByReturnedFalseAndReminderSentAtIsNull()) {
                pending.add(loan.id());
                if (!reminders.exists(loan.id())) {
                    log.warn("Loan {} had no reminder, scheduling it", loan.id());
                    reminders.schedule(loan);
                }
            }
            for (String scheduledId : reminders.scheduledLoanIds()) {
                if (!pending.contains(scheduledId)) {
                    log.warn("Reminder for loan {} has no pending loan, deleting it", scheduledId);
                    reminders.cancel(scheduledId);
                }
            }
        } catch (Exception e) {
            // refireImmediately=false: try again on the next tick
            throw new JobExecutionException(e, false);
        }
    }
}

Write concern and replica sets

The store builds its MongoDB connection with WriteConcern.MAJORITY, journaled, with a five-second write timeout, unless mongoOptionWriteConcernW names another value; every lock insert, trigger update and check-in therefore waits until a majority of a replica set has acknowledged it. The comment in the source gives the reason: after a failover of the primary, the new primary must still know about the locks and trigger states that were acknowledged. A majority write concern requires a replica set to be meaningful (a standalone server acknowledges immediately); a production deployment should be a replica set with three data-bearing members, as described on Replication. The store does not set a read concern or read preference, so reads go to the primary with the driver defaults, which is what you want for lock state; see Insert and Write Concern. Everything else in the connection (pool size, timeouts, TLS) is configured through the mongoOption* properties, or by a subclass whose constructor hands a MongoClient to the store.

How its locking differs from JDBC

The JDBC store serializes the critical sections with a row lock on QRTZ_LOCKS: SELECT * FROM QRTZ_LOCKS WHERE SCHED_NAME = ? AND LOCK_NAME = ? FOR UPDATE (class StdRowLockSemaphore), held until the transaction commits; whoever fails to get it waits, and the database releases the lock by itself when a connection dies. MongoDB has no equivalent of a blocking row lock, so the community store replaces it by lock documents. The comparison follows from the sources of both stores:

What is locked

Two global lock names (TRIGGER_ACCESS, STATE_ACCESS) around state changes, and around trigger acquisition when acquireTriggersWithinLock is set or the batch is larger than one trigger.

One lock document per acquired trigger (type t) and, for @DisallowConcurrentExecution jobs, per running job (type j). There is no global lock.

Claiming a trigger

The store selects the next due trigger and moves it to ACQUIRED with an UPDATE that succeeds only while the state is still WAITING (JobStoreSupport.acquireNextTrigger).

The store reads the eligible triggers with a find sorted by nextFireTime and then tries to insert the trigger lock; the first node to insert wins, the others skip that trigger.

Releasing

Commit or rollback of the transaction; a crashed node’s connection is closed by the database.

The owner deletes its lock documents after firing; a crashed owner leaves them behind.

Detecting a dead node

QRTZ_SCHEDULER_STATE check-ins; another node recovers the dead node’s fired triggers.

qrtz_schedulers check-ins; a lock is expired when its time is older than triggerTimeoutMillis (or jobTimeoutMillis) or when its owner is defunct, and another node then re-locks the trigger with a conditional update and recovers it.

Misfire detection

A background misfire handler scans QRTZ_TRIGGERS.

Applied while triggers are acquired, plus on recovery; there is no separate misfire thread.

Consequence of a failed check-in

The failure is logged and the check-in is retried at the next interval.

The default KamikazeErrorHandler calls System.exit(1), so that a node other nodes may have declared defunct cannot go on executing jobs.

The design is lock-free from the application’s point of view but has two weak spots that the JDBC store does not: a trigger is claimed by a find followed by an insert (not one atomic operation), and expiry is a comparison of timestamps taken from different machines' clocks, so clock skew between nodes shifts the moment at which a lock counts as expired. After a hard crash the locks of the dead node are taken over as soon as the node is declared defunct, which is quicker than the ten-minute lock timeouts; a node that is stuck but still checks in keeps its locks for the full timeout.

The same Bookshelf jobs (cache refresh, nightly reminders and a dynamic reminder with job data) were run on the store against mongo:8 with Quartz 2.5.2, 2.4.1 and 2.3.2 and two MongoDB driver generations. A job counted as working when it fired, a dynamic job with data fired, the persisted job data survived a restart of the application, and a two-node cluster run produced no duplicate execution.

The cause is a spelling fix in Quartz. Up to 2.4.1 the interface org.quartz.JobDetail declared a method with a typo, isConcurrentExectionDisallowed(); in 2.5.2 the method is spelled isConcurrentExecutionDisallowed() and the old name is gone. This was checked on the jars: javap on quartz-2.3.2.jar and quartz-2.4.1.jar lists only the misspelled method, and javap on quartz-2.5.2.jar lists only the correct one. The store was compiled against the old name (LockManager.lockJob calls it), so the call throws a NoSuchMethodError, which is an Error and not an Exception, and the scheduler thread has no handler for it: the thread ends, the scheduler object stays alive, and scheduler.isStarted() still returns true (also measured). No job runs again until the JVM restarts, and the trigger lock document of the claimed trigger stays in qrtz_locks (visible in a probe on 2.5.2: one lock of type t and no lock of type j, no execution). Because nothing is logged except that line on standard error, the failure is easy to miss in a log aggregator; any use of this store with a Quartz upgrade needs a monitor that alerts when no job has fired for longer than its schedule allows, see Listeners & Plugins and Observability.

Making it work therefore means pinning Quartz at 2.4.1 or lower. Boot exposes the managed version as a property, so <quartz.version>2.4.1</quartz.version> in the POM (or -Dquartz.version=2.4.1) is enough for Quartz; that is how the passing runs above were produced. The MongoDB driver version is a different matter: the MongoDB BOM is imported rather than inherited, so a mongodb.version property has no effect and the driver must be pinned in dependencyManagement. Pinning below Boot’s managed version gives up everything added in Quartz 2.4 and 2.5 and keeps you on a store nobody maintains while Spring Boot moves on, which is why this page keeps it out of the recommendations.

Option 3: a custom JobStore backed by MongoDB

Atomic trigger claim with findOneAndUpdate

MongoDB’s replacement for SELECT …​ FOR UPDATE on the trigger table is a single-document atomic read-modify-write. findOneAndUpdate changes the state of the earliest due trigger from waiting to acquired and returns it in one operation, so two schedulers can never get the same document. The sketch also takes over claims that expired (a node died after claiming). It was run with four concurrent threads on 200 due triggers: 200 distinct triggers were claimed and no trigger twice, and a trigger with an expired claim of a dead node was taken over by another node.

MongoTriggerAcquisition.java: the heart of acquireNextTriggers (sketch, compiled and run)
package jobstoresketch;

import com.mongodb.client.MongoCollection;
import com.mongodb.client.model.FindOneAndUpdateOptions;
import com.mongodb.client.model.Indexes;
import com.mongodb.client.model.ReturnDocument;
import com.mongodb.client.model.Updates;
import org.bson.Document;

import java.time.Duration;
import java.time.Instant;
import java.util.ArrayList;
import java.util.Date;
import java.util.List;

import static com.mongodb.client.model.Filters.and;
import static com.mongodb.client.model.Filters.eq;
import static com.mongodb.client.model.Filters.lte;
import static com.mongodb.client.model.Filters.or;
import static com.mongodb.client.model.Sorts.ascending;

/**
 * The heart of a MongoDB JobStore, as a sketch: JobStore.acquireNextTriggers without the rest of the SPI.
 * One findOneAndUpdate is atomic per document, so two schedulers can never claim the same trigger.
 */
public class MongoTriggerAcquisition {

    private final MongoCollection<Document> triggers;
    private final String instanceId;

    public MongoTriggerAcquisition(MongoCollection<Document> triggers, String instanceId) {
        this.triggers = triggers;
        this.instanceId = instanceId;
    }

    public void createIndexes() {
        triggers.createIndex(Indexes.compoundIndex(Indexes.ascending("state"), Indexes.ascending("nextFireTime")));
    }

    /** Claims up to maxCount triggers due before noLaterThan; every claimed trigger is returned exactly once. */
    public List<Document> acquireNextTriggers(Instant noLaterThan, int maxCount, Duration claimTimeout) {
        List<Document> acquired = new ArrayList<>();
        Instant now = Instant.now();
        for (int i = 0; i < maxCount; i++) {
            Document claimed = triggers.findOneAndUpdate(
                    and(lte("nextFireTime", Date.from(noLaterThan)),
                            or(eq("state", "waiting"),
                                    // a node that died after claiming: its claim expired, take the trigger over
                                    and(eq("state", "acquired"), lte("claimExpiresAt", Date.from(now))))),
                    Updates.combine(
                            Updates.set("state", "acquired"),
                            Updates.set("claimedBy", instanceId),
                            Updates.set("claimExpiresAt", Date.from(now.plus(claimTimeout)))),
                    new FindOneAndUpdateOptions().sort(ascending("nextFireTime")).returnDocument(ReturnDocument.AFTER));
            if (claimed == null) {
                break;
            }
            acquired.add(claimed);
        }
        return acquired;
    }
}

Lock documents with a TTL index

For the global critical sections of a cluster (and for the per-job lock of non-concurrent jobs) the sketch uses lock documents: the unique _id decides who owns the lock, so insertOne is the lock operation and a duplicate key error means someone else holds it. A TTL index on expiresAt cleans up the locks of crashed owners, but a TTL index is not a timer: MongoDB’s TTL monitor runs about once a minute (an expired document was deleted 58 seconds after its expiry time in this run). Correctness therefore cannot depend on it. The sketch also deletes an expired lock explicitly before inserting (tested: a lock that had expired a fraction of a second ago was taken over immediately by another node, long before the TTL monitor would have removed it).

MongoLocks.java: lock documents with an expiry (sketch, compiled and run)
package jobstoresketch;

import com.mongodb.ErrorCategory;
import com.mongodb.MongoWriteException;
import com.mongodb.client.MongoCollection;
import com.mongodb.client.model.IndexOptions;
import com.mongodb.client.model.Indexes;
import org.bson.Document;

import java.time.Duration;
import java.time.Instant;
import java.util.Date;
import java.util.concurrent.TimeUnit;

import static com.mongodb.client.model.Filters.and;
import static com.mongodb.client.model.Filters.eq;
import static com.mongodb.client.model.Filters.lte;

/**
 * Lock documents with an expiry, the Mongo answer to QRTZ_LOCKS. The unique _id decides who owns a lock,
 * the TTL index only cleans up after crashed owners.
 */
public class MongoLocks {

    private final MongoCollection<Document> locks;

    public MongoLocks(MongoCollection<Document> locks) {
        this.locks = locks;
    }

    public void createIndexes() {
        locks.createIndex(Indexes.ascending("expiresAt"), new IndexOptions().expireAfter(0L, TimeUnit.SECONDS));
    }

    public boolean tryLock(String name, String owner, Duration timeout) {
        Instant now = Instant.now();
        // the TTL monitor only runs about once a minute, so an expired lock is also removed here
        locks.deleteOne(and(eq("_id", name), lte("expiresAt", Date.from(now))));
        try {
            locks.insertOne(new Document("_id", name).append("owner", owner)
                    .append("expiresAt", Date.from(now.plus(timeout))));
            return true;
        } catch (MongoWriteException e) {
            if (e.getError().getCategory() == ErrorCategory.DUPLICATE_KEY) {
                return false;
            }
            throw e;
        }
    }

    public void unlock(String name, String owner) {
        locks.deleteOne(and(eq("_id", name), eq("owner", owner)));
    }
}

Source: MongoDB manual: TTL indexes

The remaining pieces follow the same pattern. The misfire scan is a query on state=waiting and nextFireTime older than the threshold followed by updateAfterMisfire and a conditional update (compare-and-set on nextFireTime). The cluster check-in is an upserted document per instance updated by a scheduled thread (a one-thread executor and an upsert update, as the community store does), with failed-node detection by comparing lastCheckinTime plus the interval with the clock, then recovery of the claimed triggers of the dead node. Multi-document operations (store job and trigger, remove job with its triggers) need a replica set and a transaction, with the limits on transaction size and duration from Transactions.

Why this is rarely worth it: the community store is about 4,700 lines of Java for roughly this scope; every Quartz upgrade can change the contract (option 2 died on a method rename); the JDBC store relies on the locking of mature relational databases; and a store you write must be tested under failure (killed nodes, clock skew, primary failover) which is more work than all the rest of the Quartz integration together. Choose it only when a team will own it for the life of the system.

Option 4: no Quartz, @Scheduled plus ShedLock with MongoDB

When the requirement is only "run this every night on exactly one instance", Quartz is more machinery than needed. Spring’s @Scheduled decides when, and ShedLock decides who by inserting a lock document into MongoDB. This is the right choice for the nightly overdue-loan reminder when persistence of schedules, misfire policies and runtime scheduling are not needed; it is the wrong one for the per-member reminders, which are created and cancelled while the service runs. What changed

  • Quartz 2.5. The typo in JobDetail.isConcurrentExectionDisallowed() was fixed (isConcurrentExecutionDisallowed()), which is what broke every store compiled against 2.4 or earlier that calls it, the community MongoDB store among them. Quartz 2.3.2 and 2.4.1 have only the old name, 2.5.2 only the new one (checked on the jars). Custom stores and delegates must be recompiled.

  • Quartz 2.4. The Terracotta job store was removed; JDBC is the only clustered store, so a MongoDB-based cluster means a community or custom store.

  • The community store. The upstream repository was archived after its last push in November 2022; the 2021 release candidate 2.2.0-rc2 on the Maven Central mirror is the last version, built for Quartz 2.3.2.

  • Spring Boot 3.5 to 4.x. @QuartzDataSource moved to org.springframework.boot.quartz.autoconfigure, DataSourceProperties to org.springframework.boot.jdbc.autoconfigure, the MongoDB URI property from spring.data.mongodb.uri to spring.mongodb.uri, and Flyway and Liquibase have their own starters. Both Boot lines manage Quartz 2.5.2, so the conclusions about the store do not depend on the Boot line.

  • Testcontainers 2. The MongoDB module is org.testcontainers:testcontainers-mongodb with org.testcontainers.mongodb.MongoDBContainer; the 1.x class in org.testcontainers.containers is its predecessor. The full list of version changes is on Migration & What Changed.
