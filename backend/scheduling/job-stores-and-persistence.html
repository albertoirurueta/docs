Job Stores & Persistence

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A scheduler that forgets everything when the process stops is fine for a cache refresh and useless for a reminder that must fire next Friday. What decides the difference is the job store: the Quartz component that keeps every JobDetail, Trigger and Calendar, answers the scheduler thread’s question "what is due next?", and, when it is backed by a database, lets several application instances share one schedule. This page is the generic part of that story, the one every database page of the section builds on: what a job store has to provide, the built-in stores and how Spring Boot picks one, what the eleven QRTZ_ tables contain, how the schema gets into the database (and why one of the three Boot modes deletes your schedule), how to give Quartz its own database, how a code-defined JobDetail bean is reconciled with what is already stored, how a non-JDBC store plugs in, and a matrix of which database works with which delegate and script. The database-specific details are on PostgreSQL, MySQL and MariaDB, Oracle, SQL Server, embedded and other SQL databases, MongoDB and Redis; running several nodes is on Clustering.

It was written against Quartz 2.5.2, Spring Boot 4.1.1, Spring Framework 7.0.9 and Java 21 and verified on 5 October 2026: every behaviour below was run in a test project and every default, property and class was read from the 2.5.2 and 4.1.1 sources (the results are quoted, not assumed). The new runs for this page used postgres:17 (PostgreSQL 17.11, pgJDBC 42.7.13), H2 2.4.240, Flyway 12.4.0, Liquibase 5.0.3 and Testcontainers 2.0.5 through Testcontainers modules, on a Mac with Docker 29.8. The support matrix reuses the runs of the other database images made for this section (mysql:9 = 9.7.2, mariadb:11 = 11.8.9, gvenzl/oracle-free:slim-faststart, mcr.microsoft.com/mssql/server:2022-latest under Rosetta emulation, mongo:8 = 8.3.11 and redis:8 = 8.10.2); each row of the matrix says which. Spring Boot 3.5.16 manages the same Quartz 2.5.2, so everything about Quartz is identical there; only the package of the Boot types differs (org.springframework.boot.autoconfigure.quartz instead of org.springframework.boot.quartz.autoconfigure) and Spring Framework is 6.2.19.

The running scenario is Bookshelf: the cache refresh, the nightly overdue-loan reminders, the weekly statistics report, the monthly retention cleanup and the per-member reminders created at runtime. All of them have to survive a restart, which is the reason this page exists.

What a job store is

Quartz separates running a job from remembering it. The scheduler thread, the worker pool and the listeners are the same whatever you choose; everything that has to be remembered goes through one interface, org.quartz.spi.JobStore, and the scheduler is created with exactly one implementation of it. Reading the 2.5.2 interface, its methods fall into five groups.

The three obligations

Whatever the technology behind it, a store that is correct for Quartz does three things.

Atomic trigger acquisition. The scheduler thread asks acquireNextTriggers for the triggers whose next fire time is within the next moments, in order of fire time and priority. The store must hand each trigger to exactly one caller and mark it as reserved. The RAMJobStore does this under a synchronized block around an in-memory sorted set of triggers (TreeSet<TriggerWrapper> in the source). The JDBC store has no shared memory to lock, so it uses the database: it selects the due trigger keys (SELECT_NEXT_TRIGGER_TO_ACQUIRE), then flips the trigger row from WAITING to ACQUIRED with an UPDATE …​ WHERE TRIGGER_STATE = 'WAITING' (updateTriggerStateFromOtherState) and inserts a row in QRTZ_FIRED_TRIGGERS. If the update touches no row, another node got there first and the store moves on to the next candidate. By default this runs without any lock (the code takes the TRIGGER_ACCESS lock only when org.quartz.jobStore.acquireTriggersWithinLock is true or the scheduler acquires more than one trigger per call, org.quartz.scheduler.batchTriggerAcquisitionMaxCount greater than 1), and a validator re-reads QRTZ_FIRED_TRIGGERS to confirm that the acquisition really was committed.

Misfire scan. A trigger whose fire time is far enough in the past must be handled according to its misfire instruction rather than fired blindly. The RAM store applies this while it hands out triggers. The JDBC store runs a dedicated MisfireHandler thread that wakes up every misfireThreshold milliseconds, selects waiting triggers older than the threshold (hasMisfiredTriggersInState), handles at most maxMisfiresToHandleAtATime (20 by default) per pass, and signals the scheduler thread. The policies themselves are on Misfires.

Cluster locking. A store that several scheduler instances share needs a mutual exclusion primitive and a way to notice that an instance died. The JDBC store provides both with ordinary rows: the locks are rows of QRTZ_LOCKS taken with SELECT …​ FOR UPDATE (TRIGGER_ACCESS and STATE_ACCESS), and each instance writes a heartbeat row into QRTZ_SCHEDULER_STATE; an instance whose heartbeat is older than its check-in interval plus a grace period is declared dead and its QRTZ_FIRED_TRIGGERS rows are recovered by a surviving node. The detail of that protocol, with the measured fail-over time, is on Clustering. The RAM store is never clustered (RAMJobStore.isClustered() returns false).

Two details of LocalDataSourceJobStore explain behaviour you will otherwise find puzzling. First, it registers two connection providers with Quartz’s DBConnectionManager, named springTxDataSource.<scheduler instance name> and springNonTxDataSource.<scheduler instance name>: the transactional one hands out the connection bound to the current Spring transaction (so scheduler.scheduleJob(…​) inside a @Transactional method commits or rolls back with your business data), the non-transactional one always opens a fresh connection (used by the scheduler thread, the misfire handler and the cluster manager, which manage their own commits). With an XA DataSource you pass a second, non-XA one through SchedulerFactoryBean.setNonTransactionalDataSource. Second, it calls setDontSetAutoCommitFalse(true), so Quartz does not touch the auto-commit flag of the connections it borrows from your pool.

useProperties

By default the JobDataMap of a job and of a trigger is stored as a serialized Java object. org.quartz.jobStore.useProperties=true switches the format: the map is stored as the text of a java.util.Properties file, which makes the column readable and survives class changes, at the price that every key and value must be a String. Quartz enforces it: with useProperties=true and the code-defined Integer value runs, the startup of the Bookshelf service failed with

Use it when the map holds only strings and you want to evolve job classes freely; keep the default when jobs carry records or numbers (the Bookshelf MemberReminderJob stores memberId and loanId as Long). The trade-offs of putting data in a JobDataMap at all are on Jobs & Job Data.

The driver delegates

Every statement the JDBC stores issue goes through a driver delegate, an implementation of org.quartz.impl.jdbcjobstore.DriverDelegate. The base class StdJDBCDelegate uses plain JDBC and works wherever JDBC does what it is told; the subclasses exist to handle database-specific BLOB, boolean or locking behaviour. The delegate is chosen by org.quartz.jobStore.driverDelegateClass, which Spring Boot leaves unset (so StdJDBCDelegate).

Why always destroys triggers. The scripts are installers, not migrations: most of them (PostgreSQL, MySQL, HSQLDB, Oracle) start by dropping every QRTZ_ table so that they can create it afresh. Spring Boot does not know that, it simply runs the script again at each startup. (H2’s script has no drops: with always its CREATE statements fail on "already exists" errors, which the default continue-on-error=true swallows, so the data is kept.) The result is a service that works perfectly in development (where an empty schedule at every start is what you want) and silently loses every runtime-created reminder, every paused trigger and every @PersistJobDataAfterExecution counter in production. The code-defined jobs reappear because the beans re-register them, which hides the problem until someone notices that the per-member reminders are gone. Use always for throwaway tests and demos, embedded (the default) for an in-memory H2, and never with Flyway or Liquibase for anything that has data worth keeping. Note the opposite trap of the default: embedded on a real database is not "create if missing", it is "do nothing", and the failure message is the missing table.

A dedicated Quartz database

Quartz does not have to share the application’s database. Two reasons are common: the business data lives in a database Quartz cannot use (MongoDB, Redis, Elasticsearch: none of them has a Quartz job store that works on the Quartz 2.5.2 that Boot manages, see Plugging in a store that is not JDBC), or the team wants the high-churn trigger tables, their locking and their vacuuming out of the business database. Spring Boot supports this with two qualifier annotations in org.springframework.boot.quartz.autoconfigure.

  • @QuartzDataSource marks the DataSource bean Quartz must use. It is honoured in two places in QuartzAutoConfiguration: the data source passed to SchedulerFactoryBean.setDataSource, and the data source the schema initializer runs the script against. Without it Boot uses the single (or @Primary) DataSource.

  • @QuartzTransactionManager marks the PlatformTransactionManager bean that Boot sets on the SchedulerFactoryBean with setTransactionManager. It exists in Spring Boot 4.1.1 (the source carries @since 4.0.0 for the new package; the 3.5.16 jar also contains it, in the old package: measured by listing the jar). Its Javadoc says it is meant for a secondary transaction manager when another one is marked @Primary. Without it Boot takes the one transaction manager it can find (ObjectProvider.getIfUnique(), so the @Primary one if there are several), and none at all if there is no unique candidate.

What the transaction manager is used for: SchedulerFactoryBean registers the JobDetail, Calendar and Trigger beans in a single transaction when it starts. The transaction is only meaningful if the transaction manager manages the Quartz data source. This was measured: the registration was made to fail halfway (two durable JobDetail`s and a `Trigger that names a calendar that does not exist, which makes scheduleJob throw SchedulerException: Calendar not found: doesNotExist after both jobs were stored), with the business DataSource (H2) @Primary and Quartz on PostgreSQL 17.

Sizing the connection pool

Quartz needs more connections than people expect. The scheduler thread, the misfire handler and the cluster manager each use the database, and every worker thread uses a connection when its job completes (triggeredJobComplete updates the trigger and deletes the fired row). The Quartz documentation states the rule on both the data sources page and the best-practices page: configure the data source’s maximum connections to at least the number of worker threads in the pool plus three, more if the application calls the scheduler API often, and at least four for the non-managed data source of a JobStoreCMT. The extra three match the three housekeeping threads; the page you are reading verified the rule against the documentation, not by exhausting a pool. (Some write-ups say threads plus two; the official text says plus three, which is what to use.)

The default makes it matter. Quartz’s thread pool defaults to 10 threads (measured 10 under Boot) and Hikari’s default pool is 10 connections, shared with the application, so a busy 10-thread scheduler on the application’s default pool is already under the recommendation. Raise the pool, or give Quartz its own, as in the previous section:

Spring’s SchedulerFactoryBean reconciles them when it starts, in SchedulerAccessor.registerJobsAndTriggers, controlled by one switch, spring.quartz.overwrite-existing-jobs (default false). The practical rules that follow from the table:

  • With the default (false) the code is only the initial definition: a changed cron expression, misfire instruction or job data in the code does not reach an already deployed environment. This is what you want when operators edit schedules at runtime (pause, reschedule) and a restart must not undo it; it is a trap when you change a cron in a pull request and nothing changes in production. The Boot reference says the same: a restart does not re-create or change jobs that already exist.

  • With true every start resets every code-defined job and trigger to the code’s version, including state: paused triggers resume, and @PersistJobDataAfterExecution counters go back to the bean’s value. It is the right setting for schedules that are code-only and where the code is the truth; it is wrong for any job whose data the job itself maintains.

  • Neither setting removes a job. Remove obsolete jobs explicitly, through a one-off migration or an administrative call (Scheduler.deleteJob), or accept that they keep firing.

  • The calendar is always replaced, even with false, and updateTriggers=true makes the stored triggers that use it recompute their next fire time.

  • A middle road that keeps both properties is to leave overwrite-existing-jobs false and update specific jobs from code at startup (a SchedulerFactoryBeanCustomizer or an ApplicationRunner that calls rescheduleJob for the triggers whose definition you changed, compare first, replace only on difference). The dynamic management of schedules is the subject of Dynamic Scheduling & Management.

Never write to the QRTZ tables yourself

The tables look like an ordinary schema, and a UPDATE QRTZ_TRIGGERS SET TRIGGER_STATE = 'PAUSED' is tempting during an incident. The Quartz best-practices page has a section titled "Never Write Directly To Quartz’s Tables", and warns that doing so can corrupt data, make jobs vanish without running or appear stuck, and cause deadlocks. The reason is visible in the structure above: a trigger’s state, its next fire time, the fired-trigger row of its current execution, the row locks and the in-memory view of the scheduler thread all have to agree, and Quartz maintains that agreement in code under locks, in several tables at once, with the serialized JobDataMap and calendar blobs in binary form. Read the tables freely (the queries above are safe, a read-only reporting user is a good idea), and change them only through the Scheduler API, the Actuator quartz endpoint (trigger-now only) or your own management endpoints. Everything you do through the API is also correct for every other node of a cluster at once, because it goes through the store. Source: Quartz documentation: Best Practices

Pitfalls

Table 17. Job store and persistence pitfalls (all measured unless marked source)
Pitfall What happens What to do

initialize-schema=always against a database you care about

The script drops every QRTZ_ table first, so every runtime job, pause and persisted counter is deleted at each restart

never plus Flyway or Liquibase; keep always for tests

The default embedded on a real database

Nothing is created; startup fails with relation "qrtz_job_details" does not exist

Let a migration tool create the schema, or use always once in development

continue-on-error=true (the default) hides script errors

A wrong platform or an unrunnable script (SQL Server, a mismatched platform) creates nothing and the failure shows later as a missing table

Set it to false while developing the script

No driverDelegateClass on PostgreSQL or SQL Server

Bad value for type long : \xaced…​ (PostgreSQL) or FOR UPDATE clause allowed only for DECLARE CURSOR (SQL Server) at the first trigger store

Set PostgreSQLDelegate or MSSQLDelegate

Two DataSource beans, none @Primary (with or without a @QuartzDataSource)

No error: Boot silently uses RAMJobStore; the schedule is lost at restart

Mark the application’s data source @Primary and the Quartz one @QuartzDataSource; assert isJobStoreSupportsPersistence() in a test

@QuartzDataSource without @QuartzTransactionManager while a @Primary manager exists for another database

Registration runs in the wrong transaction (two job rows left after a failed start); API calls from @Transactional code do not commit with the business data

Add @QuartzTransactionManager, or keep Quartz and business data in one database

Overriding org.quartz.jobStore.class with jdbc

DataSource name not set.

Leave the class to Boot; custom stores need job-store-type: memory

overwrite-existing-jobs=false and a changed cron in the code

The deployed environment keeps the old cron and job data

Redeploy with true once, update the trigger with rescheduleJob, or change it through the management endpoint

overwrite-existing-jobs=true with a counter kept in the JobDataMap

Every restart resets the counter, resumes paused triggers and resets the description

Keep it false for jobs that maintain their own data

Removing a job bean

The stored job and trigger remain and keep firing

Delete it explicitly with Scheduler.deleteJob

Writing to QRTZ_ tables by hand

Corrupt state, vanished or stuck jobs, deadlocks (Quartz best practices)

Use the Scheduler API

Pool smaller than threads plus three

Worker threads and the housekeeping threads wait for connections (the Quartz guidance; not exhausted in a test here)

Size the pool for the thread count, or give Quartz its own pool

useProperties=true with non-String job data

Startup or addJob fails with JobDataMap values must be Strings…​

Keep strings only, or leave the default

A tablePrefix the script does not use

relation "bks_qrtz_job_details" does not exist

Edit the script and set spring.quartz.jdbc.schema with the same prefix

A community NoSQL store on Quartz 2.5

MongoDB: scheduler "started", no job ever fires. Redis: startup failure

Quartz on SQL plus MongoDB or Redis for data, or ShedLock

What changed

Table 18. Changes that touch job stores and persistence
Release Change

Quartz 2.4.0

TerracottaJobStore removed (the 2.3.2 jar contains eight Terracotta classes, the 2.4.1 and 2.5.2 jars none); clustering is JDBC-only. HikariCP and c3p0 become provided dependencies, so a Quartz-managed pool needs them added.

Quartz 2.5.0

Jakarta namespace (jakarta.transaction in JobStoreCMT) and Java 11; the misspelled JobDetail.isConcurrentExectionDisallowed() is gone, which breaks community stores compiled against 2.4 and earlier.

Quartz 2.5.x scripts

The jar grows from 22 DDL scripts (2.3.2 and 2.4.1) to 25 in 2.5.2: tables_oracle23.sql (Oracle 23ai, BOOLEAN columns) and two GaussDB scripts. The SQL Server script uses NVARCHAR columns (commit of 29 November 2025, in the released 2.5.2).

After Quartz 2.5.2 (unreleased on main)

Pull request 1515 binds the scheduler-state instance name as NVARCHAR in MSSQLDelegate (the fix for clustered check-in deadlocks on SQL Server); not part of 2.5.2 or of any released version.

Spring Boot 3.5 to 4.x

The Quartz auto-configuration moved to org.springframework.boot.quartz.autoconfigure in the new spring-boot-quartz module: @QuartzDataSource, @QuartzTransactionManager, SchedulerFactoryBeanCustomizer and QuartzProperties change package, the property names (spring.quartz.job-store-type, spring.quartz.jdbc.*, spring.quartz.overwrite-existing-jobs) do not. The Flyway and Liquibase starters appear in 4.0.

Spring Framework 6.2 to 7.0

LocalDataSourceJobStore and SchedulerAccessor keep their behaviour; the 7.0 sources add JSpecify nullness annotations.
