Quartz on Embedded Databases (H2, HSQLDB, Derby) and Other SQL Engines

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

The first database a Quartz user meets is usually not PostgreSQL but whatever starts without any setup: an in-memory database on a laptop or inside a unit test. Spring Boot supports that case explicitly. If H2, HSQLDB or Derby is on the classpath and spring.quartz.job-store-type=jdbc is set, Boot creates the QRTZ_ tables by itself and the whole Quartz stack runs without Docker, without credentials and without a server. This page explains exactly when that automatic setup happens (and when it silently does not), which script and which delegate each of the three engines needs, how the engines behave under Quartz’s row locking, how to manage the same schema with Flyway or Liquibase, and how to split one application.yml into a development profile on an embedded database and a production profile on PostgreSQL. A short table at the end covers the other engines that Quartz ships scripts for (DB2, Sybase, CUBRID, GaussDB, InterSystems Cache and several historical ones).

It belongs to the database pages of the job stores and persistence chapter, which holds the generic material (the QRTZ_ tables, tablePrefix, delegates, the schema-management properties) and the database support matrix. The reference database of the section is PostgreSQL; the other production databases are on MySQL and MariaDB, Oracle and SQL Server. How to test jobs is on Testing, and the cluster semantics are on Clustering.

It was written against Quartz 2.5.2, Spring Boot 4.1.1, Spring Framework 7.0.9 and Java 21 and verified on 5 October 2026: every behaviour below was run in a test project (the results are quoted, not assumed), and every default and class name was read from the Quartz 2.5.2 and Spring Boot 4.1.1 sources. The code was compiled for Java 21 and run on JDK 25.0.2 with Maven 3.9.16. The embedded engines are the versions that Spring Boot 4.1.1 manages: H2 2.4.240, HSQLDB 2.7.3 and Apache Derby 10.16.1.1. The migration tools are the Boot-managed Flyway 12.4.0 and Liquibase 5.0.3, and the production half of the profile example ran against the postgres:17 image with PostgreSQL JDBC 42.7.13. Spring Boot 3.5.16 manages the same Quartz 2.5.2, so the Quartz side is identical there; the Boot package of the Quartz classes is org.springframework.boot.autoconfigure.quartz instead of org.springframework.boot.quartz.autoconfigure, Spring Framework is 6.2.19, and the managed engine versions (from the Boot 3.5.16 build file, not re-run) are H2 2.3.232, HSQLDB 2.7.3, Derby 10.16.1.1, Flyway 11.7.2 and Liquibase 4.31.1.

When an embedded database is the right choice

An embedded database runs inside the application’s JVM, so it needs no installation and starts quickly. For Quartz that is attractive for three jobs and unsuitable for a fourth.

Table 1. What embedded engines are good for with Quartz
Use Verdict Why

Developer laptop, run the service without a database container

Good

The jobs, the triggers and the JobDataMap serialization are the real JDBC code path, only the engine is lighter. The dev profile below does exactly this.

Unit and integration tests that need the persistent code path

Good

A named in-memory database per test class is faster than a container and, unlike the RAM store, still serializes job data (see the pitfalls table: a non-serializable value works with the RAM store and fails with every JDBC database).

Demos, workshops, CI smoke tests

Good

No credentials and no network.

Staging and production

No

A file or in-memory database inside one JVM cannot be shared by the second node of a cluster, so there is no failover and no single-execution guarantee across nodes. Use PostgreSQL or another server database, and keep the embedded one for the profiles that are not deployed.

The honest limit is the last row. H2 can be started in a mode that other JVMs can attach to (AUTO_SERVER=TRUE, tested below) but HSQLDB and Derby, as configured in this page, are in-process only. The test results for clustering on the embedded engines are therefore a statement about the lock code, not a recommendation.

How Spring Boot decides to create the tables

Spring Boot’s Quartz auto-configuration registers a script initializer for the Quartz DataSource. The property that controls it is spring.quartz.jdbc.initialize-schema, with the values embedded (the default), always and never. The behaviour of embedded is narrower than its name suggests, and that is the source of most surprises on this page.

The rules come from EmbeddedDatabaseConnection in the 4.1.1 source and were each confirmed by a run:

  • The embedded types Boot knows are H2, Derby and HSQLDB. For H2 the URL must contain :h2:mem, for HSQLDB it must contain :hsqldb:mem:, and for Derby any URL counts as embedded.

  • Measured: with the default embedded mode, jdbc:h2:mem:…​, jdbc:hsqldb:mem:…​, jdbc:derby:memory:…​ and jdbc:derby:<directory> all got the 11 tables, while jdbc:h2:file:…​ and jdbc:hsqldb:file:…​ got nothing and the application failed during start with Table "QRTZ_JOB_DETAILS" not found (this database is empty) (H2) and user lacks privilege or object not found: QRTZ_JOB_DETAILS (HSQLDB).

  • Derby is marked deprecated in the 4.1.1 source (@Deprecated(since = "4.1.0", forRemoval = true), "for removal in 4.3.0 as Derby is EOL"). It still works in 4.1.1 (it ran here) but it is the engine to avoid for new code.

  • When no spring.datasource.url is set at all, Boot creates the embedded DataSource itself, with a generated unique name, and takes the first engine it finds on the classpath in the order H2, then Derby, then HSQLDB. Measured with the three on the classpath: H2 (jdbc:h2:mem:<uuid>); with H2 removed: Derby (jdbc:derby:memory:<uuid>); with only HSQLDB: HSQLDB (jdbc:hsqldb:mem:<uuid>). In every case 11 tables were created.

The script that is run is chosen by the @@platform@@ placeholder in spring.quartz.jdbc.schema, whose default is classpath:org/quartz/impl/jdbcjobstore/tables_@@platform@@.sql. The platform is the id of Boot’s DatabaseDriver, lower case, except for a few explicit mappings (DB2 to db2_v95, MySQL and MariaDB to mysql_innodb, PostgreSQL to postgres, SQL Server to sqlServer). For the three embedded engines nothing is remapped, so the names are the plain ids. The platform can be overridden with spring.quartz.jdbc.platform, or the whole script with spring.quartz.jdbc.schema. Two properties change how failures are reported, and both matter for embedded databases. spring.quartz.jdbc.continue-on-error defaults to true, so a failing statement in the script is skipped silently; and spring.quartz.jdbc.comment-prefix defaults to # and --, which is why the comment lines of every script, in either style, are accepted. Set continue-on-error: false in any test that depends on the script, so a broken schema fails loudly. This needs Spring Boot 4.x: on 3.5.16 the property does not exist (the initializer hard-codes true), so the line has no effect there.

A file database and always: no DROP in the H2 script

The header of the H2 script and the documentation of the other engines suggest that always recreates the tables. For H2 that is not what the 2.5.2 script does: tables_h2.sql contains only CREATE TABLE and CREATE INDEX statements and no DROP. Measured on a file database:

  • With continue-on-error left at its default true, starting twice with always kept the data: a marker row inserted into QRTZ_CALENDARS after the first start was still there after the second, and the four jobs were still stored. Every CREATE TABLE of the second start failed with "already exists" and Boot ignored the errors.

  • With continue-on-error: false, the second start failed during bean creation with Table "QRTZ_CALENDARS" already exists, naming the statement of tables_h2.sql that failed.

So on H2 the combination "file database plus `always`" is harmless but only because the failures are swallowed. It is a sign that the schema should be owned by a migration tool; the Flyway and Liquibase sections below show both. The same is not true for HSQLDB (next section), where the script drops the tables first.

Locking, isolation and clustering on H2

Quartz serializes its critical sections with a row lock: it runs SELECT * FROM QRTZ_LOCKS WHERE SCHED_NAME = ? AND LOCK_NAME = ? FOR UPDATE (the SELECT_FOR_LOCK constant of StdRowLockSemaphore) inside the scheduler’s transaction. Three facts were measured on H2:

  • Under Spring Boot the lock handler is StdRowLockSemaphore with useDBLocks=true, in clustered and in non-clustered mode.

  • The default isolation level of a pooled H2 connection is READ_COMMITTED (JDBC value 2).

  • The lock is real. With connection A holding the TRIGGER_ACCESS lock row, connection B asking for the same row waited and gave up inside the three-second window with Timeout trying to lock table "QRTZ_LOCKS", while B asking for the STATE_ACCESS row was served at once (row-level locking). B was also refused the same row when the connection of A was set to READ_COMMITTED, REPEATABLE_READ or SERIALIZABLE.

Clustering was tested in two ways. First, three Quartz schedulers with instanceId=AUTO and isClustered=true in one JVM on one in-memory database ran for 30 seconds: 32 executions of the cache refresh and 17 of the overdue-loan reminders, none executed twice, and the work was split between the nodes in the usual first-come way (one node ran every cache refresh, the overdue reminders went mostly to another). Second, a real two-process cluster: the H2 file database was opened with AUTO_SERVER=TRUE, the first JVM started the scheduler (initialize-schema: always), a second JVM attached to the same database 10 seconds later (never), and a third process read the state table:

HSQLDB

HSQLDB needs the same Maven setup as H2 with org.hsqldb:hsqldb instead (Boot manages 2.7.3), and the same in-memory URL rule: jdbc:hsqldb:mem:<name> is initialized by embedded, jdbc:hsqldb:file:<path> is not.

Configuration for HSQLDB in memory with the delegate that the script header names
spring:
  datasource:
    url: jdbc:hsqldb:mem:bookshelf
  quartz:
    job-store-type: jdbc
    jdbc:
      continue-on-error: false
    properties:
      org.quartz.jobStore.driverDelegateClass: org.quartz.impl.jdbcjobstore.HSQLDBDelegate

HSQLDB differs from H2 in three ways that were measured or read from the sources:

  • The script drops first. tables_hsqldb.sql starts with eleven DROP TABLE …​ IF EXISTS statements. On a file database started twice with always, a marker row in QRTZ_CALENDARS was present after the first start and gone after the second: always on a persistent HSQLDB file destroys every trigger on every restart. On an in-memory database it is irrelevant.

  • No row locks under Spring. Spring’s LocalDataSourceJobStore (the store Boot uses when a DataSource is present) contains a special case for HSQLDB: if the product name contains hsql it calls setUseDBLocks(false) and installs a SimpleSemaphore. Measured: with HSQLDB the lock handler is SimpleSemaphore with useDBLocks=false, also when isClustered=true. Quartz therefore does not use FOR UPDATE on HSQLDB at all.

  • Table-level blocking when the lock is used. A manual probe of SELECT …​ FOR UPDATE on QRTZ_LOCKS made the second connection wait for the first one’s transaction even when it asked for a different lock row. HSQLDB 2.7.3 serializes writers per table here. Together with the previous point: nothing in HSQLDB under Spring Boot gives you the cross-node mutual exclusion that a cluster relies on, and the tests with two schedulers in one JVM on HSQLDB (10 executions of the cache refresh, 5 of the overdue reminders, none executed twice, 8 seconds) only show that single-process coordination works.

The default isolation level of a pooled HSQLDB connection is READ_COMMITTED.

What was measured on Derby 10.16.1.1:

  • Delegate. tables_derby.sql needs no special delegate: with the default StdJDBCDelegate the whole scenario passed (counter 4 to 5, both with memory: and with a directory database). The HSQLDBDelegate also passed, which is not a recommendation. The script stores the boolean flags in varchar(5) columns, which is long enough for the text true or false (the default delegate passed).

  • The script is re-run on every start. Boot treats every Derby URL as embedded, so embedded runs tables_derby.sql against a directory database each time. The script has its drop table statements commented out. With the default continue-on-error: true the second start silently ignored the "already exists" errors and the data survived (marker row and four jobs still present); with continue-on-error: false the second start failed with ERROR X0Y32: Table/View 'QRTZ_JOB_DETAILS' already exists in Schema 'SA'. As with H2, the quiet success hides a script that should be owned by a migration tool.

  • Cloudscape. tables_derby_previous.sql and tables_cloudscape.sql name a CloudscapeDelegate in their headers. That class does not exist in 2.5.2; do not copy that line.

  • Deprecation. Derby support is deprecated in Spring Boot 4.1 and planned for removal in 4.3 (see above). New code should use H2 or HSQLDB.

The locking result for Derby is the most important finding of this page.

Derby row locking at the default isolation level
A: SELECT ... FOR UPDATE on QRTZ_LOCKS (TRIGGER_ACCESS), rs.next(), close, keep the transaction open
default isolation of a pooled Derby connection: READ_COMMITTED (2)
READ_COMMITTED:   B asking for the same row is served at once (0 ms)
REPEATABLE_READ:  B is still blocked after 3 s
SERIALIZABLE:     B is still blocked after 3 s

Source: Quartz source: StdRowLockSemaphore (v2.5.2)

The probe copies what StdRowLockSemaphore.executeSQL does: it runs the query, reads one row and closes the result set and statement, then leaves the transaction open. On Derby at READ_COMMITTED the update lock of FOR UPDATE is released as soon as the cursor is closed, so the "lock" does not exclude another connection; at REPEATABLE_READ and SERIALIZABLE it is held until the transaction ends, like on H2. Quartz has a switch for this (org.quartz.jobStore.txIsolationLevelSerializable, which JobStoreSupport applies to the connections it creates; whether that changes the lock behaviour under Boot’s LocalDataSourceJobStore was not measured). Three Derby schedulers in one JVM ran for 30 seconds with and without it and executed nothing twice (34 and 33 cache refreshes), which shows that the scenario does not trigger the race, not that the race cannot happen. Treat Derby as single-node only.

Schema management with Flyway and Liquibase

The embedded mode is convenient for a throw-away database and wrong for a database that has a lifetime. A file database, a shared development database and every production database should have the Quartz tables created by the same migration tool as the rest of the schema, with spring.quartz.jdbc.initialize-schema set to never. The generic page describes the idea; this section shows both tools on an embedded engine, because that is the cheapest place to try them. The wider tooling is on Schema Evolution; Choosing a Migration Tool compares Flyway, Liquibase and Mongock, and Liquibase Getting Started covers the tool itself.

Flyway

Flyway needs the script as a versioned migration. The 2.5.2 jar contains the H2 script, so the migration is a copy of it, with a name Flyway understands:

Creating the migration from the Quartz jar (extracting the script gives exactly the file that Boot would run)
mkdir -p src/main/resources/db/migration
unzip -p ~/.m2/repository/org/quartz-scheduler/quartz/2.5.2/quartz-2.5.2.jar \
  org/quartz/impl/jdbcjobstore/tables_h2.sql \
  > src/main/resources/db/migration/V1__quartz_tables.sql

Source: Flyway documentation

application-flyway.yml: Flyway creates the tables, Quartz only uses them
spring:
  datasource:
    url: jdbc:h2:file:./target/bookshelf-flyway
  quartz:
    job-store-type: jdbc
    jdbc:
      initialize-schema: never      # Flyway owns the schema
  flyway:
    enabled: true
    locations: classpath:db/migration

Source: Spring Boot: Execute Flyway Database Migrations on Startup

Measured with spring-boot-starter-flyway: Flyway ran V1__quartz_tables.sql before the scheduler started, flyway_schema_history held the baseline row and version=1, description=quartz tables, success=true, the 11 tables existed, the Bookshelf jobs were stored, and a second application start was a no-op for Flyway and a restart for Quartz. The same migration also passed the complete Bookshelf scenario including the restart on an in-memory H2 database. Boot orders the scheduler after the database initializers, which is why no explicit dependency is needed.

Flyway 12 loads each database family as a separate module. Measured with only flyway-core on the classpath: HSQLDB failed with FlywayException: Unsupported Database: HSQL Database Engine 2.7 and Derby with Unsupported Database: Apache Derby 10.16. Adding org.flywaydb:flyway-database-hsqldb and org.flywaydb:flyway-database-derby (versions managed by Boot) fixed both; the migration for HSQLDB was tables_hsqldb.sql and for Derby tables_derby.sql, copied the same way. H2 needs no extra module.

Liquibase

The Quartz 2.5.2 jar ships a Liquibase changelog, org/quartz/impl/jdbcjobstore/liquibase.quartz.init.xml, with one change set (id="quartz-init", author="quartz") that creates all 11 tables with database-independent types (it only special-cases the BLOB type for PostgreSQL, where it uses BYTEA). Because it is on the classpath, a changelog of your own can simply include it:

src/main/resources/db/changelog/db.changelog-master.yaml
databaseChangeLog:
  - include:
      file: org/quartz/impl/jdbcjobstore/liquibase.quartz.init.xml

Source: Liquibase documentation: Changelogs

application-liquibase.yml: Liquibase creates the tables, Quartz only uses them
spring:
  datasource:
    url: jdbc:h2:file:./target/bookshelf-liquibase
  quartz:
    job-store-type: jdbc
    jdbc:
      initialize-schema: never      # Liquibase owns the schema
  liquibase:
    enabled: true
    change-log: classpath:db/changelog/db.changelog-master.yaml

Source: Quartz source: liquibase.quartz.init.xml (v2.5.2)

Measured with spring-boot-starter-liquibase: the changelog table recorded quartz-init from org/quartz/impl/jdbcjobstore/liquibase.quartz.init.xml, the 11 tables existed, the Bookshelf jobs were stored and, on an in-memory H2 database, the complete scenario (jobs fire, BLOB job data, restart) passed. If you prefer to own the DDL, use a sqlFile change that points at your copy of the engine’s script instead; the bundled changelog is the shorter route when the types it chooses suit you. Run only one migration tool per schema. With both starters on the classpath, switch off the one that has nothing to do with spring.flyway.enabled: false or spring.liquibase.enabled: false; the two runs above used only the starter of the tool being tested.

Do not combine a migration tool with the embedded initializer

With Flyway enabled and initialize-schema left at embedded on an in-memory H2 database, the application started normally, because Flyway ran first and the Quartz script’s "already exists" errors were ignored by the default continue-on-error: true. With continue-on-error: false the same configuration failed with Table "QRTZ_CALENDARS" already exists. Liquibase behaved like Flyway in the default configuration. The remedy is the one line initialize-schema: never in the profile that has a migration tool.

The dev and prod profile split

The most useful application of an embedded database is not a test, it is a profile: one application.yml with a YAML document per Spring profile, an embedded Quartz store (or no store) while developing, and PostgreSQL in the deployed environments. The Java code does not change; only the properties do. Spring’s profile-specific documents use spring.config.activate.on-profile, one --- separator per document.

The Bookshelf schedule that all three profiles share is the same set of beans, taken unchanged from the test project (the bookshelf.fast flag only shortens the intervals in tests):

The cache refresh and the overdue-loan reminders as Quartz beans (excerpt of BookshelfSchedule)
@Configuration(proxyBeanMethods = false)
public class BookshelfSchedule {

    @Bean JobDetail cacheRefreshJob() {
        return JobBuilder.newJob(CacheRefreshJob.class).withIdentity("cacheRefresh", "bookshelf")
                .withDescription("Refresh the catalogue cache").storeDurably().build();
    }
    @Bean Trigger cacheRefreshTrigger(JobDetail cacheRefreshJob, @Value("${bookshelf.fast:false}") boolean fast) {
        return TriggerBuilder.newTrigger().forJob(cacheRefreshJob).withIdentity("cacheRefreshTrigger", "bookshelf")
                .withSchedule(SimpleScheduleBuilder.simpleSchedule()
                        .withIntervalInSeconds(fast ? 1 : 300).repeatForever()
                        .withMisfireHandlingInstructionNextWithRemainingCount()).build();
    }

    @Bean JobDetail overdueLoanRemindersJob() {
        return JobBuilder.newJob(OverdueLoanRemindersJob.class).withIdentity("overdueLoanReminders", "bookshelf")
                .usingJobData("runs", 0).storeDurably().build();
    }
    @Bean Trigger overdueLoanRemindersTrigger(JobDetail overdueLoanRemindersJob, @Value("${bookshelf.fast:false}") boolean fast) {
        return TriggerBuilder.newTrigger().forJob(overdueLoanRemindersJob).withIdentity("overdueLoanRemindersTrigger", "bookshelf")
                .withSchedule(CronScheduleBuilder.cronSchedule(fast ? "0/2 * * * * ?" : "0 0 2 * * ?")
                        .withMisfireHandlingInstructionFireAndProceed()).build();
    }
}

class EmbeddedQuartzTest {

}

Pitfalls

Table 10. Embedded and other-SQL pitfalls, most of them measured
Pitfall What happens What to do

initialize-schema left at embedded with a file or server URL

Nothing is created; the application fails during start with Table "QRTZ_JOB_DETAILS" not found (this database is empty) (H2) or user lacks privilege or object not found: QRTZ_JOB_DETAILS (HSQLDB).

Use a jdbc:h2:mem or jdbc:hsqldb:mem: URL in the profile that relies on embedded, or create the schema with a migration tool and set never.

H2 in-memory URL without DB_CLOSE_DELAY=-1

The first context’s tables disappear when its pool closes; a second context finds an empty database.

Add DB_CLOSE_DELAY=-1 to a named in-memory URL; remember the database then lives until the JVM ends.

Copying MVCC=TRUE from the header of tables_h2.sql

H2 2.4.240 rejects it: Unsupported connection setting "MVCC" [90113-240].

Delete the setting. Multi-version concurrency is how H2 2.x works.

always on a persistent HSQLDB file database

tables_hsqldb.sql drops every table first, so each restart wipes all jobs and triggers (a marker row was gone after the second start).

Use always only for in-memory databases, or create the schema once with a migration tool and use never.

Silent script errors (continue-on-error defaults to true)

Repeated runs on H2 or Derby fail with "already exists" and nobody notices; with false the second start fails.

Set continue-on-error: false in tests, and move persistent schemas to Flyway or Liquibase.

Derby without derbytools

java.lang.ClassNotFoundException: org.apache.derby.jdbc.EmbeddedDriver while the pool is created.

Add both derby and derbytools, and plan to leave Derby: it is deprecated in Boot 4.1 for removal in 4.3.

Relying on Quartz’s row lock on Derby at the default isolation

The FOR UPDATE lock is released when the cursor closes at READ_COMMITTED, so a second connection is not blocked.

Do not cluster on Derby. If you must, use txIsolationLevelSerializable and test the exclusion yourself.

Expecting FOR UPDATE row locks on HSQLDB under Spring Boot

Spring’s LocalDataSourceJobStore installs a SimpleSemaphore for HSQLDB, even when isClustered=true; there is no cross-process lock.

Use HSQLDB for single-process tests only.

Flyway starter with HSQLDB or Derby but only flyway-core

FlywayException: Unsupported Database: HSQL Database Engine 2.7 (or Apache Derby 10.16).

Add flyway-database-hsqldb or flyway-database-derby.

A migration tool and embedded together

Works while continue-on-error is true (errors ignored); fails with Table "QRTZ_CALENDARS" already exists when it is false.

Set initialize-schema: never wherever Flyway or Liquibase is enabled.

A dev-memory profile as the only local run

RAMJobStore accepts a non-serializable JobDataMap value; the same call on a JDBC store throws JobPersistenceException caused by NotSerializableException: Unable to serialize JobDataMap for insertion into database because the value of property 'mailbox' is not serializable.

Run the dev (JDBC) profile or a test with an embedded database before merging, and put only Serializable values (or primitives) into job data.

Removing H2 from the classpath of a Boot-generated database

Boot silently switches to the next embedded engine (H2, then Derby, then HSQLDB), with a different script and different locking.

Set spring.datasource.url explicitly in every profile that uses an embedded database.

Treating an embedded database as a cluster store

Two schedulers in one JVM coordinate, a second JVM cannot attach to an in-memory database, and two of the three engines do not give Quartz an exclusive lock.

Use PostgreSQL or another server database; see Production and Best Practices.

Change Effect
