Dynamic Scheduling & Management

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Most schedules are known when the application starts: the nightly overdue-loan reminders, the weekly report, the monthly cleanup are declared as beans, see Getting Started with Spring Boot. Some are not. The Bookshelf promises each member a "return your book" reminder two days before a loan is due, which means one new schedule per loan, created while the application runs and cancelled when the book comes back. That is dynamic scheduling: creating, changing, pausing and removing jobs and triggers through the Scheduler that Spring Boot injects, and it is the main reason to choose Quartz over @Scheduled. This page tours the whole runtime API with the value each call returns, rewrites the cookbook’s list, update and unschedule recipes, wraps the reminders in a secured REST API, shows how to keep the loan and its reminder consistent in one transaction, and ends by showing what the same reminder looks like with a plain TaskScheduler.

The trigger and job definitions themselves are on Triggers & Schedules and Jobs & Job Data; the store that makes dynamic schedules survive a restart is on Job Stores & Persistence; what a resume does to a trigger that missed its time is on Misfires.

It was written against Quartz 2.5.2, Spring Boot 4.1.1, Spring Framework 7.0.9, Spring Security 7.1.1 and Java 21 and verified on 5 October 2026: every behaviour below was run in a test project (ten tests, PostgreSQL 17.11 in Testcontainers 2.0.5, the JDBC store with PostgreSQLDelegate), and the results are quoted, not assumed. Spring Boot 3.5.16 manages the same Quartz 2.5.2, so the whole Scheduler API behaves identically there; what differs is spelling around it: the starter is spring-boot-starter-web instead of spring-boot-starter-webmvc, @QuartzDataSource lives in org.springframework.boot.autoconfigure.quartz, Spring Framework is 6.2.19 and Spring Security is 6.5.11 (the SecurityFilterChain code below uses the same lambda DSL there). Boot 3.5 was not run.

The Bookshelf reminder lifecycle

The convention used here and on the other pages: the reminder of loan 1001 has job key and trigger key loan-1001 in the group reminders, the job class is MemberReminderJob, and the job data holds memberId and loanId. Using the loan identifier in the key makes every operation idempotent and lets any node, or an operator, find a reminder without a lookup table.

sequenceDiagram autonumber participant C as Librarian client participant L as LoanService transaction participant S as Scheduler injected bean participant DB as PostgreSQL loan and QRTZ tables participant J as MemberReminderJob C->>L: lend book 7 to member 42, due in 10 days L->>DB: INSERT INTO loan L->>S: scheduleJob loan-1001 in group reminders, startAt due minus 2 days S->>DB: INSERT job, trigger, simple trigger rows, same connection L->>DB: COMMIT, loan row and reminder become visible together alt book returned before the reminder time C->>L: give back loan 1001 L->>DB: DELETE FROM loan L->>S: deleteJob loan-1001 S->>DB: DELETE trigger and job rows L->>DB: COMMIT Note over S,J: nothing is left to fire else reminder time arrives first S->>J: fire loan-1001 with memberId 42 and loanId 1001 J->>J: load the loan, send the mail only if it is still open end
Figure 1. A loan creates a reminder, returning the book deletes it

The figure is what the rest of the page implements: the first half in the services, the transaction boundary in Transactional consistency, and the alt branch is why the job must re-check the loan (a reminder can fire for a loan that was returned a moment earlier).

The injected Scheduler

Spring Boot’s spring-boot-starter-quartz registers one Scheduler bean (bean name quartzScheduler, scheduler name from spring.quartz.scheduler-name, here BookshelfScheduler). With the JDBC store its job store is LocalDataSourceJobStore and getMetaData().isJobStoreSupportsPersistence() is true, which the first line of the run confirmed. Inject it like any bean; every method below throws SchedulerException (a checked exception) unless the table says otherwise, and every call goes through the store, so on a clustered JDBC store a change made on one node is seen by all of them, see Clustering.

The examples on this page ran with this configuration: the JDBC store on PostgreSQL, the schema created beforehand by a migration (the tests let Boot create it), and the credentials from the environment.

application.yml of the test project
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USER}
    password: ${DB_PASSWORD}
  quartz:
    job-store-type: jdbc
    scheduler-name: BookshelfScheduler
    jdbc:
      initialize-schema: never
    properties:
      org.quartz.jobStore.driverDelegateClass: org.quartz.impl.jdbcjobstore.PostgreSQLDelegate

Source: Spring Boot: Quartz Scheduler. Used by every test of this page on Boot 4.1.1; the tests override the three datasource properties with the Testcontainers values and set initialize-schema=always (which drops and recreates the tables, test use only, see Job Stores & Persistence).

Stored with zero triggers and checkExists true.

true, then false when called again: an unknown key is not an error.

The calls that create the Bookshelf reminders look like this:

Creating, replacing, moving and deleting a reminder with the Scheduler API
// scheduleJob(job, trigger): fails if loan-1001 already exists
Date first = scheduler.scheduleJob(job, trigger);

// create or replace in one call (void): the idempotent choice for an API
scheduler.scheduleJob(job, Set.of(trigger), true);

// a durable job first, a trigger later
scheduler.addJob(durableJob, false);
scheduler.scheduleJob(TriggerBuilder.newTrigger()
        .withIdentity("loan-3001", "reminders")
        .forJob(durableJob)
        .startAt(Date.from(Instant.now().plusSeconds(3600)))
        .build());

// move a reminder: null means there was nothing to move
Date moved = scheduler.rescheduleJob(TriggerKey.triggerKey("loan-1001", "reminders"), newTrigger);

// cancel: false means there was nothing to cancel
boolean cancelled = scheduler.deleteJob(JobKey.jobKey("loan-1001", "reminders"));

// run it now, with extra data for this run only
JobDataMap extra = new JobDataMap();
extra.put("memberId", 99L);
scheduler.triggerJob(JobKey.jobKey("loan-1001", "reminders"), extra);

Source: Quartz Cookbook — Scheduling a job and Scheduler Javadoc. Run on Quartz 2.5.2 with Spring Boot 4.1.1 and PostgreSQL 17.11: scheduleJob returned the first fire time, the second scheduleJob(…​, true) left one trigger, rescheduleJob returned the new first fire time (30 minutes ahead), deleteJob returned true and then false, and triggerJob produced Sent[memberId=99, loanId=1001].

Pausing and resuming

Pausing keeps the schedule and stops the firing: the trigger goes to state PAUSED in the store and nothing runs until it is resumed. Quartz also remembers paused groups, which matters for triggers created afterwards.

Table 2. Pause and resume methods (all return void)
Method What it pauses or resumes Measured behaviour

pauseJob(JobKey), resumeJob(JobKey)

All current triggers of one job.

getTriggerState went NORMAL → PAUSED → NORMAL.

pauseTrigger(TriggerKey), resumeTrigger(TriggerKey)

One trigger.

Same transitions.

pauseJobs(GroupMatcher<JobKey>), resumeJobs(GroupMatcher<JobKey>)

The jobs of every group the matcher selects.

Not run separately; same mechanism as the trigger variants.

pauseTriggers(GroupMatcher<TriggerKey>), resumeTriggers(GroupMatcher<TriggerKey>)

Every trigger group the matcher selects, and remembers the group.

getPausedTriggerGroups() returned [reminders]; a trigger added to the group afterwards was created PAUSED; after resumeTriggers the set was empty and the trigger NORMAL.

pauseAll(), resumeAll()

Every trigger, and remembers that everything is paused, until resumeAll.

getPausedTriggerGroups() returned [reminders, $_ALL_GROUPS_PAUSED$_]; a trigger added after pauseAll was PAUSED; resumeAll emptied the set and the trigger was NORMAL.

Source: Quartz 2.5.x Javadoc: Scheduler. Measured on the JDBC store; the group names come from getPausedTriggerGroups().

Three details from the Javadoc matter in practice. The group matchers are applied to the groups that exist now: pausing the groups that start with a remembers aaa but not a later axx, while pausing the exact group axx is remembered even before it has any member. Resuming applies each trigger’s misfire instruction, so a trigger that was paused across its fire time does what its policy says (see Misfires). And pauseAll is not standby: the first marks triggers paused in the store for the whole cluster, the second only stops this one scheduler thread from firing.

Pausing the reminders for maintenance and resuming them
scheduler.pauseTriggers(GroupMatcher.triggerGroupEquals("reminders"));   // new reminders are paused too
// ... migrate, deploy, investigate ...
scheduler.resumeTriggers(GroupMatcher.triggerGroupEquals("reminders"));  // misfire instructions apply now

scheduler.pauseJob(JobKey.jobKey("loan-1001", "reminders"));             // one loan
scheduler.resumeJob(JobKey.jobKey("loan-1001", "reminders"));

Source: Quartz Tutorial — Lesson 2: The Quartz API, Jobs and Triggers. Run on Quartz 2.5.2: the states and the remembered group behaved as in the table above.

getCurrentlyExecutingJobs and interrupt are not cluster aware: both look only at the scheduler instance they are called on, so on a cluster the answer to "is the weekly report running?" has to come from the database (the QRTZ_FIRED_TRIGGERS table, read-only) or from your own bookkeeping. A Bookshelf reminders REST API

The service layer is a thin wrapper that owns the key convention. It uses the create-or-replace form, so posting the same loan twice is harmless, and deleteJob for cancellation, so cancelling twice is a 404 the second time rather than an error.

ReminderService: create, move, cancel, list
@Service
public class ReminderService {

    static final String GROUP = "reminders";

    public record ReminderView(long loanId, long memberId, Instant remindAt, String state) { }

    private final Scheduler scheduler;

    public ReminderService(Scheduler scheduler) {
        this.scheduler = scheduler;
    }

    static JobKey jobKey(long loanId) { return JobKey.jobKey("loan-" + loanId, GROUP); }

    static TriggerKey triggerKey(long loanId) { return TriggerKey.triggerKey("loan-" + loanId, GROUP); }

    public Instant schedule(long memberId, long loanId, Instant remindAt) throws SchedulerException {
        JobDetail job = JobBuilder.newJob(MemberReminderJob.class)
                .withIdentity(jobKey(loanId))
                .usingJobData("memberId", memberId)
                .usingJobData("loanId", loanId)
                .build();
        Trigger trigger = TriggerBuilder.newTrigger()
                .withIdentity(triggerKey(loanId))
                .startAt(Date.from(remindAt))
                .build();
        scheduler.scheduleJob(job, Set.of(trigger), true);   // create-or-replace
        return remindAt;
    }

    public boolean reschedule(long loanId, Instant remindAt) throws SchedulerException {
        Trigger moved = TriggerBuilder.newTrigger()
                .withIdentity(triggerKey(loanId))
                .forJob(jobKey(loanId))
                .startAt(Date.from(remindAt))
                .build();
        return scheduler.rescheduleJob(triggerKey(loanId), moved) != null;
    }

    public boolean cancel(long loanId) throws SchedulerException {
        return scheduler.deleteJob(jobKey(loanId));
    }

    public List<ReminderView> list(Long memberId) throws SchedulerException {
        List<ReminderView> out = new ArrayList<>();
        for (JobKey key : scheduler.getJobKeys(GroupMatcher.jobGroupEquals(GROUP))) {
            JobDetail detail = scheduler.getJobDetail(key);
            if (detail == null) continue;                         // fired and removed meanwhile
            long member = detail.getJobDataMap().getLong("memberId");
            if (memberId != null && memberId != member) continue;
            for (Trigger t : scheduler.getTriggersOfJob(key)) {
                if (t.getNextFireTime() == null) continue;        // finished while we were looking
                out.add(new ReminderView(detail.getJobDataMap().getLong("loanId"), member,
                        t.getNextFireTime().toInstant(),
                        scheduler.getTriggerState(t.getKey()).name()));
            }
        }
        out.sort(Comparator.comparing(ReminderView::remindAt));
        return out;
    }
}

Source: Scheduler Javadoc and Quartz Cookbook — Listing Jobs in the Scheduler. Compiled and run on Spring Boot 4.1.1 with the JDBC store; the two continue lines exist because a one-shot reminder can fire and disappear between getJobKeys and the lookups, so getJobDetail returns null and a finished trigger has no next fire time.

The job class is the QuartzJobBean of the triggers page, with the mail gateway injected through the constructor (Spring creates jobs, so constructor injection works) and memberId and loanId set from the job data:

MemberReminderJob with a constructor-injected collaborator
public class MemberReminderJob extends QuartzJobBean {

    private final ReminderSender sender;
    private long memberId;
    private long loanId;

    public MemberReminderJob(ReminderSender sender) {
        this.sender = sender;
    }

    public void setMemberId(long memberId) { this.memberId = memberId; }

    public void setLoanId(long loanId) { this.loanId = loanId; }

    @Override
    protected void executeInternal(JobExecutionContext context) {
        sender.send(memberId, loanId, "quartz");   // in the real service: check the loan is still open first
    }
}

Source: Spring Framework: Task Execution and Scheduling. Run on Spring Boot 4.1.1: the job received its ReminderSender and the values 42 and 1001.

The controller is ordinary Spring MVC. It maps the four operations to HTTP verbs and the "nothing there" results of the Scheduler API to 404:

ReminderController: POST creates, PUT moves, DELETE cancels, GET lists
@RestController
@RequestMapping("/api/reminders")
class ReminderController {

    record CreateReminder(long memberId, long loanId, Instant remindAt) { }

    record MoveReminder(Instant remindAt) { }

    private final ReminderService reminders;

    ReminderController(ReminderService reminders) {
        this.reminders = reminders;
    }

    @PostMapping
    @PreAuthorize("hasRole('LIBRARIAN')")
    ResponseEntity<Void> create(@RequestBody CreateReminder request) throws SchedulerException {
        reminders.schedule(request.memberId(), request.loanId(), request.remindAt());
        return ResponseEntity.status(HttpStatus.CREATED)
                .header("Location", "/api/reminders/" + request.loanId()).build();
    }

    @PutMapping("/{loanId}")
    @PreAuthorize("hasRole('LIBRARIAN')")
    ResponseEntity<Void> move(@PathVariable long loanId, @RequestBody MoveReminder request)
            throws SchedulerException {
        return reminders.reschedule(loanId, request.remindAt())
                ? ResponseEntity.noContent().build()
                : ResponseEntity.notFound().build();
    }

    @DeleteMapping("/{loanId}")
    @PreAuthorize("hasRole('LIBRARIAN')")
    ResponseEntity<Void> cancel(@PathVariable long loanId) throws SchedulerException {
        return reminders.cancel(loanId)
                ? ResponseEntity.noContent().build()
                : ResponseEntity.notFound().build();
    }

    @GetMapping
    @PreAuthorize("hasRole('LIBRARIAN') or (#memberId != null and #memberId.toString() == authentication.name)")
    List<ReminderService.ReminderView> list(@RequestParam(required = false) Long memberId)
            throws SchedulerException {
        return reminders.list(memberId);
    }
}

Securing the API

An endpoint that can create and delete schedules is an administrative interface: anyone who can post to it decides what runs and when, and a job class name must never come from the request (the controller above fixes MemberReminderJob and takes only identifiers and an instant, so nothing the client sends is turned into a class name or a cron expression). The security model, filters and method security are explained on Spring Security; the part that matters here is small.

A stateless chain with method security: SecurityFilterChain and @EnableMethodSecurity
@Configuration(proxyBeanMethods = false)
@EnableMethodSecurity
class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/**").authenticated()   // roles are checked by @PreAuthorize
                .anyRequest().denyAll())
            .httpBasic(withDefaults())
            .csrf(AbstractHttpConfigurer::disable)            // stateless API, no browser session
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS));
        return http.build();
    }
}

Source: Spring Security: Authorize HttpServletRequests and Spring Security: Method Security. Compiled and run on Spring Security 7.1.1 (Boot 4.1.1); withDefaults is the static import of org.springframework.security.config.Customizer.withDefaults. HTTP Basic stands in for your real authentication (JWT, OAuth 2.0, see Spring Security); users come from a UserDetailsService, no password appears in the code.

Two rules are worth stating. Put the coarse rule in the filter chain (/api/** needs authentication, everything else is denied) and the fine rule next to the method (hasRole('LIBRARIAN'), or the own-reminders expression for members), so that a new endpoint added to the controller without an annotation is still at least authenticated. And switch method security on: the same controller was run with @EnableMethodSecurity commented out, and the @PreAuthorize annotations were silently ignored, so the MEMBER user got 201 on POST, 204 on DELETE, and could read member 7’s reminders with 200. CSRF protection is disabled here only because the API is stateless and authenticated by a header on every request; a browser session needs it. Do not expose the Actuator quartz endpoint without the same care, see Observability.

Transactional consistency

The loan row and its reminder are two writes, and they should succeed or fail together: a reminder for a loan that was rolled back mails a member about a loan that does not exist, and a loan whose reminder was lost never reminds anyone. With the JDBC store they can share one transaction, because of how Spring Boot wires Quartz: LocalDataSourceJobStore asks DataSourceUtils for its connection, and DataSourceUtils returns the connection that the current Spring transaction has bound to that DataSource. If the DataSource Quartz uses is the same one the business code uses, every QRTZ_* insert made by scheduleJob happens on the same connection as the INSERT INTO loan, and commits or rolls back with it. (The JobStoreCMT that LocalDataSourceJobStore extends is Quartz’s "container managed" store: it never commits itself.)

LoanService: the business row and the reminder in one transaction
@Service
public class LoanService {

    private static final ZoneId MADRID = ZoneId.of("Europe/Madrid");

    private final JdbcClient jdbc;
    private final ReminderService reminders;

    public LoanService(JdbcClient jdbc, ReminderService reminders) {
        this.jdbc = jdbc;
        this.reminders = reminders;
    }

    @Transactional(rollbackFor = Exception.class)
    public void lend(long loanId, long memberId, long bookId, Instant due) throws SchedulerException {
        jdbc.sql("INSERT INTO loan (id, member_id, book_id, due_date) VALUES (?, ?, ?, ?)")
                .params(loanId, memberId, bookId, java.sql.Timestamp.from(due)).update();
        reminders.schedule(memberId, loanId, due.atZone(MADRID).minusDays(2).toInstant());
    }

    @Transactional(rollbackFor = Exception.class)
    public void giveBack(long loanId) throws SchedulerException {
        jdbc.sql("DELETE FROM loan WHERE id = ?").param(loanId).update();
        reminders.cancel(loanId);
    }
}

Source: Spring Framework: Transaction Management and SchedulerFactoryBean Javadoc; behaviour read from LocalDataSourceJobStore in Spring Framework 7.0.9. rollbackFor = Exception.class matters because SchedulerException is checked and a Spring transaction does not roll back on checked exceptions by default. The test version of lend had an extra flag that throws IllegalStateException after scheduling, to force a rollback.

Sharing the transaction has a price that the first measurement hides, which is the locking in the store. Scheduling takes the TRIGGER_ACCESS row lock of QRTZ_LOCKS (lockOnInsert is true by default), and a lock taken inside a transaction is held until that transaction ends. Two threads were run: the first scheduled a reminder and then held its transaction open for 2000 ms; a second thread scheduling another reminder 500 ms later waited 1519 ms, whether it did so inside its own transaction or without any (1513 ms). The rule that follows: keep the transaction around scheduleJob short, never call a slow service (a mail gateway, a remote API) between the scheduleJob and the commit, and expect the scheduler’s firing (triggersFired) to queue behind a long business transaction. The locks and what each call takes are on Job Stores & Persistence and PostgreSQL; the general transaction and locking background is on Transaction Isolation & Locking.

When the stores cannot share a transaction

With a separate @QuartzDataSource, with a Quartz store in another database engine, or with business data in MongoDB, there is no transaction around both writes (a MongoDB multi-document transaction cannot enlist a PostgreSQL connection). Pick the failure you can live with and design for it:

  • Schedule after the commit. Publish an event inside the transaction and schedule in an AFTER_COMMIT listener, so a rollback never creates a reminder. The price is a window between the commit and the scheduleJob in which a crash loses the reminder, so the reconciliation below is still needed. Measured on the separate-data-source setup: the commit created the reminder, the rollback created none.

  • Make the job re-check. The reminder job loads the loan and returns without mailing if it is closed, which also neutralises any orphan. It should be idempotent anyway, see Jobs & Job Data.

  • Reconcile. A periodic job compares open loans with the reminders group and creates the missing reminders (create-or-replace makes this harmless) and deletes the orphans. The MongoDB page does exactly that, see MongoDB and Quartz and Spring Data MongoDB for the MongoDB side.

Scheduling only if the loan transaction commits
public record LoanLent(long loanId, long memberId, Instant due) { }

// inside LoanService.lend(...): the INSERT, then
events.publishEvent(new LoanLent(loanId, memberId, due));

@Component
class ReminderScheduling {

    private static final ZoneId MADRID = ZoneId.of("Europe/Madrid");

    private final ReminderService reminders;

    ReminderScheduling(ReminderService reminders) {
        this.reminders = reminders;
    }

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    void onLoanLent(LoanLent event) throws SchedulerException {
        Instant remindAt = event.due().atZone(MADRID).minusDays(2).toInstant();
        reminders.schedule(event.memberId(), event.loanId(), remindAt);
    }
}

Source: Spring Framework: Transaction-bound Events. Run with a separate @QuartzDataSource on Boot 4.1.1: after a committed lendThenSchedule the reminder existed; after a rolled-back one (IllegalStateException) it did not, and loans stayed at 1. The events field is an ApplicationEventPublisher.

Dynamic scheduling versus TaskScheduler

Spring’s own TaskScheduler can also schedule a one-shot task at runtime: taskScheduler.schedule(runnable, instant) returns a ScheduledFuture that you can cancel. For a task that only matters while the application is up that is enough, and the whole mechanism is explained on Scheduling and ShedLock. For the Bookshelf reminders it is not, because the schedule exists only as a ScheduledFuture in the heap of one JVM. The next test scheduled the same reminder both ways for five seconds ahead, stopped the application after one second, waited two seconds, and started it again against the same database.

The practical guidance: use TaskScheduler for in-process, loss-tolerant work (a debounce, a short timeout, a retry in a few seconds), and the Quartz Scheduler when the schedule belongs to the business data and must survive a restart, a deployment and the loss of a node. Pitfalls

Table 10. Runtime scheduling pitfalls and what to do instead
Pitfall What happens and the fix

scheduleJob for a key that exists

ObjectAlreadyExistsException. Use scheduleJob(job, Set.of(trigger), true), or test checkExists first (and accept the race on a cluster).

addJob with a non-durable job

SchedulerException: Jobs added with no trigger must be durable. The UpdateJob cookbook snippet fails for this reason. Add storeDurably() or use the three-argument addJob.

rescheduleJob for an unknown trigger key

Returns null and stores nothing: the new trigger is not created. Check the result, as the controller does.

deleteJob or unscheduleJob for an unknown key

Return false, no exception. Map that to 404 or ignore it deliberately; deleteJobs is true only if every job existed.

addJob(replace=true) as a "partial update"

The whole JobDataMap is replaced, not merged ({memberId=42, loanId=1} became {memberId=99}). Read the stored map first, change it, then store it.

pauseAll() as a maintenance switch, then new triggers

Triggers created after it are PAUSED until resumeAll(); forgetting resumeAll leaves the pseudo group $_ALL_GROUPS_PAUSED$_ in the store for the whole cluster. Prefer standby() for one node.

Group matchers and groups that do not exist yet

pauseTriggers with a prefix matcher does not pause groups created later; an exact-group matcher does remember a group that has no members yet.

Resume after a long pause

Misfire instructions are applied at once, so a daily trigger may fire immediately. Choose the policy with the pause in mind, see Misfires.

getCurrentlyExecutingJobs and interrupt on a cluster

Local to the node you call; they say nothing about the others. Use your own bookkeeping or the read-only QRTZ_FIRED_TRIGGERS table.

Modifying a JobDetail or Trigger you got from the scheduler

They are snapshots; nothing changes until you store them again (addJob, rescheduleJob).

getJobDetail(key) assumed non-null

null when a reminder fired and was deleted between listing and lookup. Skip it, as ReminderService.list does.

@PreAuthorize without @EnableMethodSecurity

Silently ignored: measured, a MEMBER could create and delete reminders and read another member’s. Enable method security and test the 403.

A job class or cron expression taken from the request

The caller chooses what runs. Fix the job class in code and accept only identifiers, instants and validated values.

Scheduling in the loan transaction and then calling a slow service

The QRTZ_LOCKS lock is held until commit; measured 1.5 s of waiting for other schedulers, and the scheduler thread’s firing (triggersFired) waits behind it too. Schedule last, commit quickly.

scheduleJob and a transaction that rolls back, with a separate @QuartzDataSource

The reminder stays (measured): an orphan. Schedule AFTER_COMMIT, make the job re-check the loan, and reconcile periodically.

@Transactional without rollbackFor = Exception.class around scheduleJob

SchedulerException is checked, so the business row commits while the reminder failed. Declare rollbackFor.

A reminder time in the past

Fires at once (smart misfire policy for a one-shot trigger, see Triggers & Schedules); check remindAt before scheduling if that is wrong.

TaskScheduler.schedule for work that must outlive the process

The ScheduledFuture is lost on restart (measured). Use the Quartz Scheduler.

Source: Quartz 2.5.x Javadoc: Scheduler and the measurements of this page.
