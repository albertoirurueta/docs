Scheduling

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This Backend Development section is a practical guide, focused on Spring Boot services, to running work on a clock: refresh a cache every few minutes, send reminders every night, create a reminder for one member when a loan is made and cancel it when the book comes back, produce a report that must not run twice and must survive a crash. It complements the SpringBoot Reference, whose Scheduling & ShedLock page documents standard scheduling, and it compares that standard scheduling with the advanced features of Quartz Scheduler: persistent and clustered schedules, misfire policies, calendars, runtime job management and recovery after a crash.

The section documents Quartz 2.5.2 (released 2025-12-01; Java 11 or later, Jakarta namespace; there is no 3.x) on Spring Boot 4.1.1, which manages that version, and Spring Framework 7.0.9, whose spring-context-support provides SchedulerFactoryBean, QuartzJobBean and LocalDataSourceJobStore, with Java 21. Standard scheduling is compared with ShedLock 7.10.1 (Java 17 or later). Where Spring Boot 3.5 differs, the pages show a short "Spring Boot 3.5" delta: Boot 3.5.16 manages the same Quartz 2.5.2, so only the package of the Boot Quartz types (org.springframework.boot.autoconfigure.quartz instead of org.springframework.boot.quartz.autoconfigure) and Spring Framework 6.2.19 differ. The versions were verified on 5 October 2026, and each page states what it measured: behaviours were verified in a test project, against real databases in Docker where a database page says so.

What scheduling means for a backend service

A web request starts when a client sends it; scheduled work starts when the clock says so. That difference creates the problems this section is about:

  • Nobody is waiting. A failed nightly job is noticed late, so jobs must log, expose their state and be safe to run again.

  • The service has more than one copy. Three replicas behind a load balancer would send every reminder three times unless something makes exactly one of them run each job.

  • The clock does not stop for deployments. A restart over a fire time either loses the run or runs it late; the right behaviour is a decision (a misfire policy), not an accident.

  • Some schedules are data. "Remind this member in 14 days" is created at run time, must survive a restart and may be deleted before it fires.

  • Crashes happen halfway. A report that took five minutes and died at minute four has to be finished by somebody.

Spring’s @Scheduled solves the first problem class for the simple case and is the right default. Quartz solves the rest and costs a job store. The section helps you tell which jobs are which.

This section is for developers who:

  • use @Scheduled today, possibly with ShedLock, and need to know when to move to Quartz and how

  • are adding Quartz to a Spring Boot 4 (or 3.5) service and need the starter, the configuration and the database set-up that actually work

  • have to run Quartz on a particular database (PostgreSQL, MySQL, MariaDB, Oracle, SQL Server, H2 or another SQL engine) or want it with MongoDB or Redis

  • want to test scheduled jobs, observe them in production and run them in a cluster

Running example

Every example builds on Bookshelf, the domain used by the Resilience, FastAPI, NestJS, Django, Next.js and Kubernetes sections of this site, so readers can compare stacks. Here it is a Spring Boot 4.1 bookshelf-service (Java 21) with five kinds of scheduled work, each of which motivates a feature:

Figure 2. The five jobs of bookshelf-service and the mechanism each one uses

  • Cache refresh of the catalogue every 5 minutes. Standard @Scheduled(fixedDelay) is enough.

  • Nightly overdue-loan reminders at 02:00 Europe/Madrid on business days. @Scheduled(cron) with ShedLock first, then a Quartz CronTrigger with a holiday Calendar and a misfire policy.

  • Per-member "return your book" reminders, created at run time when a loan is made and cancelled when the book is returned. This needs Quartz: dynamic one-shot SimpleTrigger`s, a `JobDataMap and persistence across restarts.

  • Weekly statistics report, long running, which must not overlap itself and must recover after a crash: @DisallowConcurrentExecution and requestsRecovery, in a three-node cluster.

  • Monthly retention cleanup on the last business day: L and LW in cron and a Calendar; it launches a Spring Batch job (linked).

The reference database is PostgreSQL; every database page re-runs the same jobs on its own database so the pages can be compared. The comparison page, Standard Scheduling vs Quartz, migrates the weekly report from @Scheduled to Quartz.

The final layout

The classes the pages build up to, in one Maven module. Each piece is shown on the page named beside it:

bookshelf-service
├── pom.xml                                   spring-boot-starter-quartz, -jdbc, -actuator, the JDBC driver
└── src
    ├── main
    │   ├── java/bookshelf
    │   │   ├── BookshelfApplication.java
    │   │   ├── ScheduleProperties.java       record for bookshelf.schedule.*      (Spring Boot Configuration)
    │   │   ├── BookshelfSchedule.java        JobDetail and Trigger beans          (Getting Started, Spring Boot Configuration)
    │   │   ├── CacheRefreshJob.java          job 1, or @Scheduled in the standard version
    │   │   ├── OverdueLoanRemindersJob.java  job 2, a QuartzJobBean                (Getting Started)
    │   │   ├── MemberReminderJob.java        job 3, created through the Scheduler  (Dynamic Scheduling)
    │   │   ├── ReminderController.java       REST API that creates and cancels reminders
    │   │   ├── WeeklyStatisticsJob.java      job 4, DisallowConcurrentExecution and requestsRecovery  (Clustering)
    │   │   ├── RetentionCleanupJob.java      job 5, launches a Spring Batch job    (Jobs and Job Data)
    │   │   └── JobAuditListener.java         a global JobListener                  (Listeners and Plugins)
    │   └── resources
    │       ├── application.yml               shared settings, below
    │       ├── application-dev.yml           memory store, fast schedules
    │       ├── application-prod.yml          PostgreSQL, clustered, schema owned by Flyway
    │       └── db/migration
    │           └── V1__quartz_tables.sql     tables_postgres.sql from the Quartz jar
    └── test
        └── java/bookshelf                    unit tests, memory-store test, Testcontainers cluster test (Testing)

Source: Spring Boot: Quartz Scheduler. The layout is a map of the pages, not one downloadable project: the five jobs and the schedule beans were compiled and run together for Spring Boot Configuration. Individual pages use local property names in their own examples (for example bookshelf.reminders.), while the consolidated configuration below uses bookshelf.schedule..

The application.yml that every environment shares, with the schedule as configuration so that each environment can speed it up:

application.yml: the settings every environment shares
spring:
  application:
    name: bookshelf-service
  quartz:
    scheduler-name: BookshelfScheduler
    wait-for-jobs-to-complete-on-shutdown: true   # honoured with Quartz's own SimpleThreadPool, not with a Spring TaskExecutor
    overwrite-existing-jobs: false

bookshelf:
  schedule:
    zone: Europe/Madrid
    cache-refresh-interval: 5m
    overdue-cron: "0 0 2 ? * MON-FRI"
    weekly-cron: "0 0 6 ? * MON"
    retention-cron: "0 30 3 LW * ?"         # last weekday of the month

management:
  endpoints:
    web:
      exposure:
        include: health,quartz

Source: Spring Boot: Quartz Scheduler and Spring Boot: Actuator Endpoints. The same file, with the dev, test and prod profiles around it, is on Spring Boot Configuration. The shutdown flag makes Quartz wait for running jobs and record their completion only with its own SimpleThreadPool; with a Spring TaskExecutor it is not honoured, and await-termination keeps the JVM alive without the completion being recorded (see Production & Best Practices).

The production profile turns on the JDBC store and clustering:

application-prod.yml: PostgreSQL, clustered, tables created by a migration tool
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USER}
    password: ${DB_PASSWORD}
  quartz:
    job-store-type: jdbc
    jdbc:
      initialize-schema: never
    properties:
      org.quartz.scheduler.instanceId: AUTO
      org.quartz.jobStore.driverDelegateClass: org.quartz.impl.jdbcjobstore.PostgreSQLDelegate
      org.quartz.jobStore.isClustered: "true"

Source: Quartz documentation: Configure Clustering with JDBC-JobStore. The credentials are placeholders resolved from the environment, never literal values. The Testcontainers cluster test that exercises this configuration with two schedulers is on Testing Scheduled Jobs.
