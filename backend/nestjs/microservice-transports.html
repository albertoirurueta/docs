Microservice Transports

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against NestJS 12.1 (npm @nestjs/microservices 12.1.2), Node.js 20.19+ or 22.12+, TypeScript 6 (6.0.3) and RxJS 7.8, all checked on 2026-10-02. A transporter is the pluggable layer that carries Nest’s two message styles (request-response with @MessagePattern() and send(), event-based with @EventPattern() and emit()) over a concrete protocol. The programming model is covered in Microservices Fundamentals; this page is the reference for what differs per transporter: the package to install, the options object, how patterns map to the wire, the context object, record builders, wildcards, connection status, on() and unwrap(), and the failure modes. The six built-in network transporters are covered (Redis, MQTT, NATS, RabbitMQ, Kafka, gRPC), followed by custom transporters and a comparison table. The broker theory itself (Kafka partitions and consumer groups, RabbitMQ exchanges and queue types, delivery guarantees) lives in the Messaging section and is linked rather than repeated; the architecture of a split system is in Microservices Architecture and Patterns.

What the examples are tested against

The examples are exercised in-process, without a Redis, MQTT, NATS, RabbitMQ or Kafka broker. Every snippet below type-checks with tsc --noEmit under strict in a NestJS 12.1.2 project (ESM, Vitest), and its tests drive the real @nestjs/microservices server and client classes. What stands in for the broker is stated per transporter:

Transporter What is exercised Against what

gRPC

The real @grpc/grpc-js server and client over TCP: unary, server streaming, client streaming, bidirectional streaming, metadata, GrpcExceptionFilter, health and reflection.

Nothing is substituted. TLS credentials are compile-checked only.

The real mqtt client library: wildcards, request-response, per-pattern QoS, record builder QoS, status, unwrap().

The real ioredis client library: request-response, wildcard events, status, on(), unwrap(), and the overlapping-pattern pitfall.

A small RESP stub (about 120 lines) that understands only SUBSCRIBE, PSUBSCRIBE and PUBLISH. It is test scaffolding, not Redis.

The real @nats-io/transport-node client: queue groups, fan-out without a queue, wildcards, headers, status, unwrap().

The real ServerRMQ and ClientRMQ classes: manual acknowledgement, record builder options, durable queue assertion, topic exchange wildcards, request-response through the reply queue.

Nothing is substituted.

Treat the RabbitMQ and Kafka sections as checked against Nest’s own code paths and the official documentation, but confirm broker-side behaviour (redelivery, offsets, rebalancing) on a real broker before relying on it.

What every transporter has in common

Running a transporter

A microservice is created with NestFactory.createMicroservice() and one options object: transport selects the transporter (the Transport enum from @nestjs/microservices) and options is specific to it. The same object is accepted by ClientsModule on the client side, with a name that becomes the injection token.

bootstrap.ts
import { NestFactory } from '@nestjs/core';
import type { MicroserviceOptions } from '@nestjs/microservices';
import { ReviewsModule } from '../nats/reviews.module.js';
import { natsOptions } from './options.js';

export async function bootstrap() {
  // A standalone microservice: no HTTP server, just the transporter.
  const app = await NestFactory.createMicroservice<MicroserviceOptions>(
    ReviewsModule,
    natsOptions,
  );
  app.enableShutdownHooks();
  await app.listen();
}

Source: NestJS: Microservices - Getting started

The options object used here is built in the NATS section. When the options need injected providers such as ConfigService, pass AsyncMicroserviceOptions (inject plus useFactory) instead, so the broker address comes from configuration:

bootstrap-from-config.ts
import { NestFactory } from '@nestjs/core';
import { ConfigService } from '@nestjs/config';
import { Transport } from '@nestjs/microservices';
import type { AsyncMicroserviceOptions } from '@nestjs/microservices';
import { ReviewsModule } from '../nats/reviews.module.js';

export async function bootstrapFromConfig() {
  // Transport options that need injected providers: AsyncMicroserviceOptions.
  const app = await NestFactory.createMicroservice<AsyncMicroserviceOptions>(
    ReviewsModule,
    {
      inject: [ConfigService],
      useFactory: (config: ConfigService) => ({
        transport: Transport.NATS,
        options: {
          servers: [config.getOrThrow<string>('NATS_URL')],
          queue: 'notifications',
        },
      }),
    },
  );
  await app.listen();
}

Nothing in this page depends on the HTTP adapter: a standalone microservice has no HTTP server at all, and in a hybrid application (an HTTP app that also calls connectMicroservice(), covered in Microservices Fundamentals) the Express 5.2 or Fastify 5.12 adapter and the transporter run side by side without interacting.

Registering clients from configuration

Every transporter is consumed through a ClientProxy (gRPC uses ClientGrpc, Kafka the ClientKafkaProxy type). ClientsModule.registerAsync() builds them from ConfigService, so no address is hardcoded. Each entry’s useFactory runs in ClientsModule’s own scope: either make `ConfigModule global, as below, or give each entry imports: [ConfigModule]. Without that, Nest fails at start-up with Nest can’t resolve dependencies of the REDIS_CLIENT (?).

clients.module.ts
import { join } from 'node:path';
import { Module } from '@nestjs/common';
import { ConfigModule, ConfigService } from '@nestjs/config';
import { ClientsModule, Transport } from '@nestjs/microservices';

@Module({
  imports: [
    // registerAsync() factories live in ClientsModule's own scope: either make
    // ConfigModule global (as here) or add `imports: [ConfigModule]` to each entry.
    ConfigModule.forRoot({ isGlobal: true }),
    ClientsModule.registerAsync([
      {
        name: 'REDIS_CLIENT',
        inject: [ConfigService],
        useFactory: (config: ConfigService) => ({
          transport: Transport.REDIS,
          options: {
            host: config.getOrThrow<string>('REDIS_HOST'),
            port: config.getOrThrow<number>('REDIS_PORT'),
          },
        }),
      },
      {
        name: 'MQTT_CLIENT',
        inject: [ConfigService],
        useFactory: (config: ConfigService) => ({
          transport: Transport.MQTT,
          options: { url: config.getOrThrow<string>('MQTT_URL') },
        }),
      },
      {
        name: 'NATS_CLIENT',
        inject: [ConfigService],
        useFactory: (config: ConfigService) => ({
          transport: Transport.NATS,

Using a client is the same everywhere: send() returns a cold Observable that you bound with timeout() and turn into a promise with firstValueFrom(); emit() is also cold, so subscribe to it or await it, otherwise nothing is sent.

review-notifier.ts
import { Inject, Injectable } from '@nestjs/common';
import { ClientProxy } from '@nestjs/microservices';
import { firstValueFrom, timeout } from 'rxjs';

@Injectable()
export class ReviewNotifier {
  constructor(@Inject('NATS_CLIENT') private readonly client: ClientProxy) {}

  // Request-response: always bound the wait with timeout().
  countUnread(userId: number): Promise<number> {
    return firstValueFrom(
      this.client.send<number, number>('notifications.count', userId).pipe(timeout(5000)),
    );
  }

  // Event: fire-and-forget. emit() is cold until subscribed, so await it
  // (or subscribe) to make sure the event is actually dispatched.
  notifyReviewCreated(bookId: number): Promise<void> {
    return firstValueFrom(this.client.emit('reviews.created', { bookId }));
  }
}

The common surface: context, status, on() and unwrap()

Each transporter provides the same four extension points, with transporter-specific types:

Feature What it gives you

Context object

@Ctx() injects RedisContext (getChannel()), MqttContext (getTopic(), getPacket()), NatsContext (getSubject(), getHeaders()), RmqContext (getPattern(), getMessage(), getChannelRef()), KafkaContext (getTopic(), getPartition(), getMessage(), getConsumer(), getHeartbeat()). gRPC handlers instead receive the Metadata and call objects as plain arguments.

status

An Observable of connection states on both the client and the server: connected, disconnected and reconnecting for Redis, NATS and MQTT (MQTT adds closed); connected, disconnected, blocked and unblocked for RabbitMQ; rebalancing, crashed and stopped for Kafka.

on()

Subscribes to the driver’s own events (for example error). Supported on the Redis, MQTT, NATS and RabbitMQ clients and servers. On Kafka it throws Method is not supported for Kafka server (and the equivalent for the client), which is why Kafka exposes its KafkaJS producer and consumer instead.

unwrap()

Returns the underlying driver: two ioredis instances (publisher, subscriber) for Redis, an MqttClient, a NatsConnection, an AmqpConnectionManager. Prefer not to need it.

Under strict the documented snippets for status, on() and unwrap() need three small adjustments, each needed for the code to type-check with tsc. Type the injected client with the transporter’s events and status maps so that status and on() are typed; do not annotate the status callback of a server (INestMicroservice.status is an Observable<string>); and give on() on the server both type arguments so the callback parameters are inferred.

redis-connection-watcher.ts
import { Inject, Injectable } from '@nestjs/common';
import { ClientProxy, RedisEvents, RedisStatus } from '@nestjs/microservices';

@Injectable()
export class RedisConnectionWatcher {
  // Typing the client with the transport's events and status maps makes
  // status and on() type-check under `strict`.
  constructor(
    @Inject('REDIS_CLIENT')
    private readonly client: ClientProxy<RedisEvents, RedisStatus>,
  ) {}

  watch() {
    this.client.status.subscribe((status) => console.log('redis', status));
    // Redis uses two connections, so the callback also receives which one failed.
    this.client.on('error', (connection, err) =>
      console.error(connection, err),
    );
    const [pub, sub] =
      this.client.unwrap<[import('ioredis').Redis, import('ioredis').Redis]>();
    return { pub, sub };
  }
}

A strict-mode pitfall with @EventPattern()

@MessagePattern() accepts handlers with any parameter list, but the first overload of @EventPattern() in 12.1.2 types the decorated method as (data, …​args: unknown[]) ⇒ any. A handler whose second parameter is typed, as @Ctx() context: RedisContext is, therefore fails with TS1241: Unable to resolve signature of method decorator when called as an expression. Handlers with a single parameter compile. Passing an explicit type argument selects the plain MethodDecorator overload, so every event handler on this page is written @EventPattern<string>('…​'). With a RegExp pattern (Kafka) the problem does not arise. The behaviour was reproduced with TypeScript 6.0.3.

The Bookshelf scenario

The running scenario is the Bookshelf application. Its notifications service reacts to review and follow events and renders messages; the catalogue is reachable over gRPC; the examples below give each transporter the job it is usually chosen for. They are not a recommendation to run six brokers: pick one transporter per boundary, as the comparison table at the end explains.

Redis

The Redis transporter is built on Redis Pub/Sub (it needs the ioredis package). Messages are published to channels without the publisher knowing who subscribes. They are fire-and-forget: a message published while nobody listens is gone, and there is no guarantee that any service handles a given message. Every subscriber to a channel receives every message, so Pub/Sub has no consumer groups: if you run three instances of a service, all three handle each event and each answers each request. For durable or load-balanced delivery use RabbitMQ or Kafka instead, or Redis Streams outside the Nest transporter (see Redis Streams and Pub/Sub).

npm install ioredis

Patterns, context and wildcards

A message pattern becomes a channel: a request published to notifications.count is answered on notifications.count.reply (the client subscribes to that reply channel for the duration of the request). Event patterns are used as the channel name directly. RedisContext.getChannel() returns the channel the message arrived on.

notifications.controller.ts
import { Controller } from '@nestjs/common';
import {
  Ctx,
  EventPattern,
  MessagePattern,
  Payload,
  RedisContext,
} from '@nestjs/microservices';

@Controller()
export class NotificationsController {
  readonly received: { channel: string; data: unknown }[] = [];

  // Request-response: the reply travels on "notifications.count.reply".
  @MessagePattern('notifications.count')
  count(@Payload() userId: number, @Ctx() ctx: RedisContext) {
    return { userId, unread: 3, channel: ctx.getChannel() };
  }

  // With wildcards: true the pattern is subscribed with PSUBSCRIBE.
  @EventPattern<string>('notify.*')
  onNotification(@Payload() data: unknown, @Ctx() ctx: RedisContext) {
    this.received.push({ channel: ctx.getChannel(), data });
  }
}

Source: NestJS: Redis - Context

With the server and a ClientProxy both using wildcards: true, sending notifications.count with the payload 7 receives { userId: 7, unread: 3, channel: 'notifications.count' }, and emitting notify.review and notify.follow gets both handled with the matching getChannel() values. status emits connected on both sides, and unwrap() returns two ioredis instances whose status is ready.

Redis globs are broader than they look: matches any run of characters, dots included. An event pattern notifications. therefore also matches the request channel notifications.count and the reply channel notifications.count.reply. With the controller below, the notifications. event handler runs for both of those channels in addition to the real events, so the reply is handled as if it were an event. Keep event channels and request channels in disjoint namespaces (notify. against notifications.count above).

overlap pitfall
@Controller()
class Overlap {
  seen: string[] = [];

  @MessagePattern('notifications.count')
  count() {
    return 1;
  }

  @EventPattern<string>('notifications.*')
  any(@Ctx() ctx: RedisContext) {
    this.seen.push(ctx.getChannel());
  }
}
// seen contains 'notifications.count' and 'notifications.count.reply'

Connections, retries and listeners

The transporter keeps two connections, one to publish and one to subscribe (a subscribed Redis connection cannot issue other commands), so the on() callback receives 'pub' or 'sub' first, and unwrap() returns the pair. In 12.1, listeners registered on a client with on() stay registered until close(), so they are also attached to the new connections the client creates after a failed connect; do not register the same listener again from a callback, because registrations are not deduplicated. 12.1.0 also fixed the Redis client so that it retries after a failed connect (PR 17828).

MQTT

MQTT is a lightweight publish/subscribe protocol for constrained devices and unreliable networks, with a broker in the middle. The transporter uses the mqtt (MQTT.js) package. Unlike Redis, it offers three delivery levels (QoS 0, 1 and 2) negotiated per subscription and per publish.

npm install mqtt

Options

The options are the MQTT.js client options plus url, subscribeOptions (global subscription QoS) and userProperties (headers sent on every request, MQTT 5). On the server maxConnectionAttempts limits the initial connection attempts (default -1, unlimited; reconnections are not limited).

Topics, wildcards and QoS

MQTT topics use / as the separator. + matches exactly one level and # matches the rest of the topic. The default subscription QoS is 0 for every @MessagePattern() and @EventPattern(); set subscribeOptions: { qos } for a global value, or pass { qos } as the extras argument of one decorator to override it for that pattern. The effective QoS of a delivery is the lower of the QoS the publisher used and the QoS granted to the subscription, which is MQTT’s rule and is why both sides matter.

sensors.controller.ts
import { Controller } from '@nestjs/common';
import {
  Ctx,
  EventPattern,
  MessagePattern,
  MqttContext,
  Payload,
} from '@nestjs/microservices';

@Controller()
export class ReadingsController {
  readonly seen: { topic: string; qos: number; data: unknown }[] = [];

  // '+' matches exactly one topic level, '#' matches the rest of the topic.
  @MessagePattern('shelves/+/temperature/+')
  temperature(@Payload() data: { celsius: number }, @Ctx() ctx: MqttContext) {
    return { topic: ctx.getTopic(), celsius: data.celsius };
  }

  // Per-pattern QoS overrides the global subscribeOptions.qos.
  @EventPattern<string>('books/+/reviews', { qos: 1 })
  review(@Payload() data: { text: string }, @Ctx() ctx: MqttContext) {
    this.seen.push({
      topic: ctx.getTopic(),
      qos: ctx.getPacket().qos ?? 0,
      data,
    });
  }

  @EventPattern<string>('audit/#')
  audit(@Payload() data: unknown, @Ctx() ctx: MqttContext) {
    this.seen.push({ topic: ctx.getTopic(), qos: ctx.getPacket().qos ?? 0, data });
  }
}

Source: NestJS: MQTT - Per-pattern QoS

Against an MQTT broker (Aedes, in-process), a request to shelves/a1/temperature/top is matched by the shelves//temperature/ pattern and answered with { topic: 'shelves/a1/temperature/top', celsius: 21 }; events on books/42/reviews and audit/login/ok are delivered with getTopic() returning the concrete topic, and getPacket().qos is 0 by default.

Record builders and user properties

MqttRecordBuilder sets per-message options: setQoS(), the retain and DUP flags and, with MQTT 5, setProperties() for user properties. A record built with .setQoS(1) arrives with getPacket().qos === 1. User properties require protocol version 5 on the connection; Aedes speaks only MQTT 3.1.1, so the following is compile-checked only:

mqtt-record.ts
import { ClientProxyFactory, MqttRecordBuilder, Transport } from '@nestjs/microservices';

// MQTT 5 user properties (the in-process broker used for the runnable tests is MQTT 3.1.1 only).
export const mqttRecord = new MqttRecordBuilder('payload')
  .setProperties({ userProperties: { 'x-version': '1.0.0' } })
  .setQoS(1)
  .build();

export const mqttV5Client = ClientProxyFactory.create({
  transport: Transport.MQTT,

Patterns, request-response and event semantics

The transporter does not use the NATS built-in request-reply API. The client publishes the request on the subject with a unique reply subject, and the responder publishes to that reply subject, which is routed back dynamically wherever each party is. Events use plain NATS publish-subscribe: every active subscriber on the subject receives the event (fan-out). Subject wildcards work in patterns: * for one token, > for one or more.

Manual acknowledgement and durable queues

With the default noAck: true RabbitMQ considers a message done the moment it is delivered, so a crash loses it. Set noAck: false and the handler must acknowledge, on the channel taken from RmqContext.getChannelRef(), with the original message from getMessage(). If the consumer dies before acknowledging, the broker re-queues the message. Pair this with a durable queue (queueOptions: { durable: true }) and persistent messages (persistent: true) for messages that must survive a broker restart; as the official page puts it, persistent messages survive a restart only in a queue that survives one too.

notifications.controller.ts
import { Controller } from '@nestjs/common';
import {
  Ctx,
  EventPattern,
  MessagePattern,
  Payload,
  RmqContext,
} from '@nestjs/microservices';

@Controller()
export class RmqNotificationsController {
  readonly handled: { pattern: string; priority?: number; version?: string }[] = [];

  // noAck: false -> the handler MUST acknowledge, otherwise RabbitMQ keeps the
  // message unacknowledged (and redelivers it when the channel closes).
  @MessagePattern('notifications.render')
  render(@Payload() data: { user: string }, @Ctx() context: RmqContext) {
    const channel = context.getChannelRef();
    const original = context.getMessage();
    const { headers, priority } = original.properties;
    this.handled.push({
      pattern: context.getPattern(),
      priority,
      version: headers?.['x-version'],
    });
    channel.ack(original);
    return `Hello ${data.user}`;
  }

  // Events are acknowledged the same way.
  @EventPattern<string>('notifications.sent')
  sent(@Payload() data: unknown, @Ctx() context: RmqContext) {
    this.handled.push({ pattern: context.getPattern() });
    context.getChannelRef().ack(context.getMessage());
  }
}

Naming conventions

The transporter appends -server to the server’s clientId and groupId and -client to the client’s, so a client and a server using the same configuration never collide: a consumer groupId of bookshelf-consumer becomes bookshelf-consumer-server for the microservice and bookshelf-consumer-client for the client (both asserted in the test). For request-response the reply topic is the request topic plus .reply (books.get is answered on books.get.reply); override getResponsePatternName() in a subclass of ClientKafka to change it.

Request-response over reply topics

Kafka has no built-in request-reply, so send() builds one: the client sends the request with a correlation id, a reply topic and a reply partition in the message headers, and the server replies to that topic and partition with the same correlation id. The client must therefore be subscribed to the reply topic, and assigned a partition of it, before it sends. Three consequences follow. Call subscribeToResponseOf('<request topic>') for every request topic, before connect() if you connect yourself. Provision at least one reply-topic partition for every running instance of the client application: with four instances and a three-partition reply topic, one instance fails to send. And a rebalance can strand replies, which Nest avoids with a built-in partition assigner that lets existing clients keep the reply partition they had.

Incoming messages reach the handler as key, value and headers buffers that Nest turns into strings, parsing anything that starts with { or [ as JSON. @MessagePattern() and @EventPattern() accept a RegExp on Kafka since Nest 12: the pattern is passed to KafkaJS’s subscribe() and, when Nest resolves a handler for an incoming topic, it falls back to regular-expression matching (resetting lastIndex, so /g and /y expressions behave). In books.controller.ts above, @EventPattern(/^reviews\..+$/) handled reviews.created and reviews.deleted but not other.topic, and context.getTopic() returned the concrete topic. Other transporters still match patterns by exact value.

KafkaContext, heartbeats and offsets

KafkaContext gives getTopic(), getPartition(), getMessage() (the original IncomingMessage with offset, headers, timestamp, …​), getConsumer() (the KafkaJS consumer) and getHeartbeat(). Call the heartbeat from a slow handler between steps so the session timeout does not expire and trigger a rebalance.

By default KafkaJS commits offsets automatically. To commit only after the work is done, set run: { autoCommit: false } and commit the next offset to consume (the current offset plus one) from the handler:

import { Controller } from '@nestjs/common';
import {
  Ctx,
  EventPattern,
  KafkaContext,
  Payload,
} from '@nestjs/microservices';

    ]);

Retriable exceptions and retry filters

An unhandled exception in a message handler is normally turned into an error reply. To make KafkaJS retry instead, throw KafkaRetriableException: it bypasses the reply, bubbles up to KafkaJS’s eachMessage callback (even with interceptors or an Observable response) and the offset is not committed, so the message is redelivered. A books.flaky handler that throws it twice and then succeeds answers { id: 1, attempts: 3 }: the request is redelivered twice. Events are different: all unhandled exceptions in event handlers are already treated as retriable.

An unbounded retry loop blocks the partition on a poison message. A bounded alternative is an exception filter that republishes the event with a retry-count header and, when the limit is reached, skips it by committing its offset. This filter is adapted from the official one:

kafka-max-retry.filter.ts
import { ArgumentsHost, Catch, ExceptionFilter, Logger } from '@nestjs/common';
import { KafkaContext } from '@nestjs/microservices';
import type { Producer } from 'kafkajs';

const toWire = (v: unknown) =>
  v === null || typeof v === 'string' || Buffer.isBuffer(v)
    ? v
    : JSON.stringify(v);

/**
 * Retries a failing event a bounded number of times by republishing it with a
 * retry-count header, then skips it (committing its offset) so the partition
 * is not blocked by a poison message.
 */
@Catch()
export class KafkaMaxRetryExceptionFilter implements ExceptionFilter {
  private readonly logger = new Logger(KafkaMaxRetryExceptionFilter.name);

  constructor(
    private readonly producer: Producer,
    private readonly maxRetries: number,
    private readonly skipHandler?: (message: unknown) => Promise<void>,
  ) {}

  async catch(exception: unknown, host: ArgumentsHost) {
    const context = host.switchToRpc().getContext<KafkaContext>();
    const message = context.getMessage();
    const retries = this.retryCount(context);

    if (retries >= this.maxRetries) {
      this.logger.warn(`Max retries (${this.maxRetries}) exceeded, skipping`);
      await this.skipHandler?.(message);
      await this.commit(context);
      return; // stop propagating: KafkaJS sees a successful handler
    }

    try {
      await this.producer.send({
        topic: context.getTopic(),
        messages: [
          {
            key: message.key,
            // Nest has already JSON-parsed the value; KafkaJS only accepts
            // strings and Buffers, so serialize it again.
            value: toWire(message.value),
            headers: { ...message.headers, 'retry-count': String(retries + 1) },
          },
        ],
      });
      await this.commit(context);
    } catch (republishError) {
      this.logger.error('Failed to republish for retry', republishError);
      throw exception; // let KafkaJS redeliver the original message
    }
  }

  private retryCount(context: KafkaContext): number {
    const header = context.getMessage().headers?.['retry-count'];
    return header ? parseInt(String(header), 10) || 0 : 0;
  }

  private async commit(context: KafkaContext) {
    await context.getConsumer().commitOffsets([
      {
        topic: context.getTopic(),
        partition: context.getPartition(),
        // commit the NEXT offset: current offset + 1
        offset: (Number(context.getMessage().offset) + 1).toString(),
      },
    ]);
  }
}

Source: NestJS: Kafka - Custom exception handling

Nest hands the filter a message whose value it has already parsed from JSON into an object, and KafkaJS only accepts strings and buffers as values. Republishing message.value as is therefore fails (KafkaJS requires a string or Buffer, and an object is rejected with The first argument must be of type string or an instance of Buffer), the filter rethrows, and the message is redelivered unchanged instead of being retried by the filter, which is why toWire() serializes the value again. Handlers: unary, server streaming, client streaming and bidirectional

@GrpcMethod(service, rpc) handles unary and server-streaming RPCs. Both arguments are optional: without the RPC name the method name with its first letter capitalised is used (create handles Create), and without the service name the controller’s class name is used. A handler receives the request data, the request Metadata and the call object (for example sendMetadata()).

A server-streaming handler returns an Observable: each emitted value is a stream message. Returning an array is wrong: it fails with 13 INTERNAL: Error serializing response: …​ expected object with Review structure, got array instead; wrap it with from([…​]).

Request streams use @GrpcStreamMethod() (the handler receives an Observable of requests; for a client-streaming RPC the last value of the returned Observable is the response, and for a bidirectional RPC every value is a response message and the handler must return an Observable) or @GrpcStreamCall() (the handler gets the raw duplex stream, writes with write(), ends with end(), and for a client-streaming RPC responds through a callback). The controller below uses both strategies:

books.controller.ts
import { Controller } from '@nestjs/common';
import {
  GrpcAlreadyExistsException,
  GrpcMethod,
  GrpcNotFoundException,
  GrpcStreamCall,
  GrpcStreamMethod,
} from '@nestjs/microservices';
import { Metadata } from '@grpc/grpc-js';
import type { ServerDuplexStream, ServerUnaryCall } from '@grpc/grpc-js';
import { Observable, Subject, from, map, reduce } from 'rxjs';

export interface Book {
  id: number;
  title: string;
}
export interface BookById {
  id: number;
}
export interface Review {
  book_id: number;
  text: string;
}
export interface Rating {
  book_id: number;
  stars: number;
}
export interface RatingSummary {
  count: number;
  average: number;
}
export interface ChatMessage {
  text: string;
}

@Controller()
export class BooksController {
  private readonly books = new Map<number, Book>([
    [1, { id: 1, title: 'Dune' }],
    [2, { id: 2, title: 'Emma' }],
  ]);

  // Both arguments given: service name and rpc name.
  @GrpcMethod('BooksService', 'FindOne')
  findOne(
    data: BookById,
    metadata: Metadata,
    call: ServerUnaryCall<BookById, Book>,
  ): Book {
    // Echo the request id back as initial (header) metadata.
    const out = new Metadata();
    out.add('x-request-id', String(metadata.get('x-request-id')[0] ?? 'none'));
    call.sendMetadata(out);

    const book = this.books.get(data.id);
    if (!book) throw new GrpcNotFoundException(`Book ${data.id} not found`);
    return book;
  }

  // Only the service name given: the rpc is derived from the method name
  // (create -> Create).
  @GrpcMethod('BooksService')
  create(data: Book): Book {
    if (this.books.has(data.id)) {
      throw new GrpcAlreadyExistsException('Book already exists');
    }
    this.books.set(data.id, data);
    return data;
  }

  // Server streaming: return an Observable, every value is a stream message.
  @GrpcMethod('BooksService', 'ListReviews')
  listReviews(data: BookById): Observable<Review> {
    return from([
      { book_id: data.id, text: 'Great' },
      { book_id: data.id, text: 'Long' },
      { book_id: data.id, text: 'Classic' },
    ]);
  }

  // Client streaming with the RxJS strategy: the last value emitted is the
  // single response.
  @GrpcStreamMethod('BooksService', 'RateMany')
  rateMany(ratings: Observable<Rating>): Observable<RatingSummary> {
    return ratings.pipe(
      reduce(
        (acc, r) => ({ count: acc.count + 1, sum: acc.sum + r.stars }),
        { count: 0, sum: 0 },
      ),
      map(({ count, sum }) => ({
        count,
        average: count === 0 ? 0 : sum / count,
      })),
    );
  }

  // Bidirectional streaming with the Subject strategy.
  @GrpcStreamMethod('BooksService', 'Chat')
  chat(messages: Observable<ChatMessage>): Observable<ChatMessage> {
    const subject = new Subject<ChatMessage>();
    messages.subscribe({
      next: (m) => subject.next({ text: `echo: ${m.text}` }),
      complete: () => subject.complete(),
    });
    return subject.asObservable();
  }

  // Client streaming with the call-stream handler: respond through the callback.
  @GrpcStreamCall('BooksService', 'CountRatings')
  countRatings(
    requestStream: ServerDuplexStream<Rating, RatingSummary>,
    callback: (err: unknown, value: RatingSummary) => void,
  ) {
    let count = 0;
    let sum = 0;
    requestStream.on('data', (r: Rating) => {
      count += 1;
      sum += r.stars;
    });
    requestStream.on('end', () =>
      callback(null, { count, average: count === 0 ? 0 : sum / count }),
    );
  }

  // Bidirectional streaming with the call-stream handler: a plain Duplex.
  @GrpcStreamCall('BooksService', 'Echo')
  echo(call: ServerDuplexStream<ChatMessage, ChatMessage>) {
    call.on('data', (m: ChatMessage) => call.write({ text: `echo: ${m.text}` }));
    call.on('end', () => call.end());
  }
}

The client

Register the package with ClientsModule, inject the ClientGrpc with the registration name and call getService() once the module is initialised. The returned object is typed by an interface you write; methods are lower camel case (FindOne becomes findOne), unary calls return an Observable, and a client-streaming or bidirectional call takes an Observable of requests (a ReplaySubject is convenient). Under the Nest template (isolatedModules together with emitDecoratorMetadata) the ClientGrpc interface must be imported with import type in a decorated constructor, otherwise TS1272.

books.client.ts
import { Inject, Injectable, Module, OnModuleInit } from '@nestjs/common';
import { ClientsModule, Transport } from '@nestjs/microservices';
import type { ClientGrpc } from '@nestjs/microservices';
import { join } from 'node:path';
import { Metadata } from '@grpc/grpc-js';
import { Observable, ReplaySubject, lastValueFrom, toArray } from 'rxjs';
import type {
  Book,
  BookById,
  ChatMessage,
  Rating,
  RatingSummary,
  Review,
} from './books.controller.js';

interface BooksService {
  findOne(data: BookById, metadata?: Metadata): Observable<Book>;
  create(data: Book): Observable<Book>;
  listReviews(data: BookById): Observable<Review>;
  rateMany(upstream: Observable<Rating>): Observable<RatingSummary>;
  chat(upstream: Observable<ChatMessage>): Observable<ChatMessage>;
}

@Injectable()
export class BooksClient implements OnModuleInit {
  private books!: BooksService;

  constructor(@Inject('BOOKS_PACKAGE') private readonly client: ClientGrpc) {}

  onModuleInit() {
    this.books = this.client.getService<BooksService>('BooksService');
  }

  findOne(id: number) {
    const metadata = new Metadata();
    metadata.add('x-request-id', 'req-42');
    return lastValueFrom(this.books.findOne({ id }, metadata));
  }

  create(book: Book) {
    return lastValueFrom(this.books.create(book));
  }

  reviews(id: number) {
    return lastValueFrom(this.books.listReviews({ id }).pipe(toArray()));
  }

  rate(stars: number[]) {
    const upstream = new ReplaySubject<Rating>();
    stars.forEach((s) => upstream.next({ book_id: 1, stars: s }));
    upstream.complete();
    return lastValueFrom(this.books.rateMany(upstream));
  }

  chat(texts: string[]) {
    const upstream = new ReplaySubject<ChatMessage>();
    texts.forEach((text) => upstream.next({ text }));
    upstream.complete();
    return lastValueFrom(this.books.chat(upstream).pipe(toArray()));
  }
}

Metadata

gRPC metadata is a list of key-value pairs attached to a call, typically authentication tokens, request ids and trace context. A handler reads the request metadata from its second parameter and sends header metadata back with call.sendMetadata(); findOne() above echoes the x-request-id request header. The raw @grpc/grpc-js client in the test received the metadata event with the echoed value. Custom transporters

When no built-in transporter fits (a cloud queue, a proprietary bus, an in-process test double) you write a strategy and, if you want Nest clients, a client class. The server side extends Server and implements CustomTransportStrategy (listen() and close() are required; on() and unwrap() may throw if you do not support them). Server provides addHandler()/getHandlerByPattern(), handleEvent(), handleRequest() and the messageHandlers map, so the transporter only has to receive packets from the wire and call into them. The client extends ClientProxy and implements connect(), close(), unwrap(), publish() (request-response) and dispatchEvent() (events). publish() returns a teardown function that runs when the caller unsubscribes, and the response callback’s isDisposed flag marks the last value.

This minimal in-process transporter is complete and works end to end; a real one replaces the direct call with its network I/O:

memory-transport.ts
import {
  BaseRpcContext,
  ClientProxy,
  CustomTransportStrategy,
  ReadPacket,
  Server,
  WritePacket,
} from '@nestjs/microservices';

/** A process-local "broker": the client hands packets straight to the server. */
export class MemoryBus {
  server?: MemoryServer;
}

export class MemoryServer extends Server implements CustomTransportStrategy {
  constructor(private readonly bus: MemoryBus) {
    super();
  }

  /** Triggered by app.listen(). */
  listen(callback: () => void) {
    this.bus.server = this;
    callback();
  }

  /** Triggered on application shutdown. */
  close() {
    this.bus.server = undefined;
  }

  on(): never {
    throw new Error('Method not implemented.');
  }

  unwrap<T = never>(): T {
    return this.bus as T;
  }

  /** What a real transporter calls when a message arrives from the wire. */
  receive(pattern: string, data: unknown, respond?: (p: WritePacket) => void) {
    const context = new BaseRpcContext([pattern]);
    if (!respond) {
      return this.handleEvent(pattern, { pattern, data }, context);
    }
    const handler = this.getHandlerByPattern(pattern);
    if (!handler) {
      return respond({ err: `No handler for ${pattern}` });
    }
    return this.handleRequest(
      context,
      async () => this.transformToObservable(await handler(data, context)),
      respond,
    );
  }
}

export class MemoryClient extends ClientProxy {
  constructor(private readonly options: { bus: MemoryBus }) {
    super();
  }

  async connect() {}
  async close() {}

  unwrap<T = never>(): T {
    return this.options.bus as T;
  }

  protected publish(
    packet: ReadPacket,
    callback: (packet: WritePacket) => void,
  ): () => void {
    this.options.bus.server?.receive(packet.pattern, packet.data, callback);
    return () => undefined; // teardown when the caller unsubscribes
  }

  protected async dispatchEvent(packet: ReadPacket): Promise<any> {
    await this.options.bus.server?.receive(packet.pattern, packet.data);
  }
}

How to choose, in short: use gRPC for synchronous calls between services you own (a typed contract, streaming, deadlines), and a broker for asynchronous work and events. Among brokers, Kafka when events must be retained and replayed, RabbitMQ when you need queues with acknowledgements and flexible routing, NATS when you want a small, fast bus, MQTT when the producers are devices, and Redis only when losing a message is acceptable. What changed recently, and where older material is outdated

  • NATS v3 (12.0). The transporter uses @nats-io/transport-node; the nats package, StringCodec and JSONCodec are gone, packets are JSON strings and custom deserializers receive the whole message (msg.json()). Older tutorials that import nats or JSONCodec no longer work.

  • GrpcExceptionFilter and the gRPC status exceptions (12.0). Older material shows hand-built { code, message } objects thrown through RpcException, or says every error is UNKNOWN.

  • RegExp patterns on Kafka (12.0). Before 12 every topic had to be registered explicitly.

  • Microservices pre-request hook (12.0). A hook runs before a message handler (see Microservices Fundamentals).

  • 12.1. The Redis client retries after a failed connect (PR 17828), a throwing callback no longer leaves other pending requests hanging (PR 17810), and on() listeners on a client survive until close(). Release notes: v12.1.0 and v12.0.0.

  • Strict TypeScript. The official snippets for status, on() and @EventPattern() with a context parameter were written without strict in mind; the adjusted forms on this page compile under it.

  • Books and tutorials written for Nest 9 and 10 predate all of the above, show the ClientProxy type for Kafka rather than ClientKafkaProxy, and treat nats v2 as the NATS driver.

Pitfalls

  • Calling emit() and never subscribing: the observable is cold, nothing is dispatched.

  • Calling send() without timeout(): with a broker transport a missing responder leaves the request pending forever.

  • Redis (and any pattern-based wildcard): overlapping event and request patterns turn replies into events.

  • Running several instances on Redis Pub/Sub or on NATS without a queue group: every instance handles every message.

  • RabbitMQ with noAck: false and a handler path that forgets to acknowledge: the queue fills with unacknowledged messages and prefetch stalls the consumer.

  • Kafka request-response without subscribeToResponseOf() for every request topic, or with fewer reply-topic partitions than client instances.

  • Kafka retries without a limit: a poison message blocks its partition; bound it, as the retry filter does.

  • Republishing a Nest-parsed Kafka value without serializing it again.

  • gRPC .proto files missing from dist/ because the Nest CLI assets entry is absent.

  • gRPC loader options that differ between client and server (keepCase, defaults, enums): fields vanish or change type.

  • gRPC server-streaming handler that returns an array or a promise of one instead of an Observable.

  • ClientsModule.registerAsync() factories that cannot resolve ConfigService because ConfigModule is not global.

  • Treating the tests on this page as broker tests: the RabbitMQ and Kafka fakes do not model redelivery, rebalancing or persistence.
