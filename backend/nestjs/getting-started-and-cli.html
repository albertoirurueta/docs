Getting Started & CLI

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against NestJS 12.1 (npm @nestjs/core 12.1.2, published 2026-09-30), @nestjs/cli 12.0.8, @nestjs/schematics 12.0.6, Node.js 20.19+ or 22.12+ to run an application (a newer Node.js to use the generators), TypeScript 6 (6.0.x, what the Nest 12 templates install), Express 5.2 and Fastify 5.12, all as of 2026-10-02. It takes you from an empty directory to a running, watched, debuggable application, and documents every command of the CLI together with the nest-cli.json options and builders behind it. The commands and snippets apply to @nestjs/cli 12.0.8 on Node.js 24.16 (ESM and CommonJS projects); the app grows into the Bookshelf over the following pages. For what NestJS is and how it is layered, see Introduction & Architecture.

For installing Node.js and choosing a release line, see Installing Node.js and Release Lines & LTS in the Node.js section.

Requirements

There are two different Node.js floors in Nest 12, and mixing them up is the most common first-day surprise:

What you do Minimum Node.js Why

Run a Nest 12 application

20.19+, or 22.12+ on the 22.x line

The v12 packages are ESM-only. A CommonJS application loads them through require(esm), which is unflagged from 20.19 and 22.12. The 21.x line never received it.

nest new, nest generate, nest upgrade

22.22.3+, 24.15+ or 26+

The schematics (@nestjs/schematics) inherit the floor of the Angular devkit they are built on. The 23.x and 25.x lines and earlier 22.x/24.x releases are excluded.

Run the CLI binary itself (nest build, nest start, nest --help)

20.11+

The @nestjs/cli package declares this engine range.

Source: NestJS: Migration guide - Node.js requirements, NestJS: CLI overview - Requirements

In practice: install the latest active LTS release of Node.js and both floors are met. Pick the bare minimum only for a specific reason, and remember that Node.js 20.19 can run your application but cannot scaffold or generate code. Two more requirements are worth knowing:

  • ICU. The CLI needs a Node.js binary built with internationalization support (ICU), such as the official binaries from nodejs.org. Check yours with the command below; it prints a version, and undefined means the binary has no ICU.

  • AWS Lambda. Lambda disables require(esm) on its Node.js 20, 22 and 24 runtimes. A CommonJS Nest 12 function needs NODE_OPTIONS=--experimental-require-module in its environment (append it to existing flags).

node --version
node -p process.versions.icu

Source: NestJS: CLI overview - Requirements

NestJS is written in TypeScript and also supports plain JavaScript (JavaScript needs Babel because Nest relies on recent language features). TypeScript 6 (~6.0.2) is a dependency of the v12 CLI and is pinned by the generated project. TypeScript 7, the native compiler, is the latest tag on npm at the time of writing but is not what nest new installs, so do not upgrade it by hand and expect the CLI to follow.

A global install means every project on the machine runs the same CLI version, and nothing in a project’s package.json pins it. There are three ways to deal with that:

Approach When to use it

npm i -g @nestjs/cli

Day-to-day development, and what the rest of the documentation assumes. You are responsible for keeping it current.

npx @nestjs/cli@latest new bookshelf

One-off scaffolding without a global install; always the latest published CLI.

npm i -D @nestjs/cli (local dev dependency)

Every generated project already has it. The package.json scripts (npm run build, npm run start:dev) use this local copy, so every team member and the CI runner build with the same version.

Source: NestJS: CLI overview - Installation, NestJS: CLI scripts - Package scripts

The split matters: nest new and nest generate are not part of the build pipeline and have no package script, so they use the global (or npx) binary, while nest build and nest start should be run through the package.json scripts so the project controls their version. Command syntax is uniform: nest <commandOrAlias> <requiredArg> [optionalArg] [options]. Commands and many options have aliases, and omitted required arguments are prompted for:

nest new bookshelf --dry-run     # long form
nest n bookshelf -d              # identical, with aliases
nest generate --help             # help for one command

Source: NestJS: CLI overview - CLI command syntax

Creating a Project with nest new

nest new bookshelf
cd bookshelf
npm run start:dev

Source: NestJS: CLI overview - Basic workflow

The command prompts for what you did not pass as an option: the project name, the package manager, the module system and whether to set up NestJS Observe. It then creates the directory, writes the configuration files and a src/ and test/ skeleton, installs the dependencies and initializes a git repository.

The prompts

  • Package manager — npm, yarn, pnpm or bun (bun is supported since v12). The chosen manager must already be installed globally; Nest uses it for the install step and records nothing else about it.

  • Module system — ESM (the default; Vitest for testing) or CommonJS (Jest for testing). Both use oxlint for linting. The generated code differs in a few visible ways, summarised below.

  • NestJS Observe — whether to wire the @nestjs/observe SDK (the official observability platform; pre-1.0) into AppModule and NestFactory.create(). In an interactive terminal the prompt defaults to yes; without a terminal (CI) it is skipped and Observe is not added. Use --observe / --no-observe to decide without being asked.

In a non-interactive environment such as CI, pass the name and --package-manager; the module system then defaults to ESM, and Observe is only set up if you pass --observe:

nest new bookshelf --package-manager npm --skip-git --no-observe

Strict mode

New projects are generated with TypeScript’s strict flag on, and with strictPropertyInitialization switched off. That second exception exists because decorated class properties (DTOs, entities, injected fields) are assigned by a framework, not by a constructor; with the flag on, every name: string; would need a ! or an initializer. To opt out of strict mode, set "strict": false in the generated tsconfig.json — the --strict option cannot do it. Keep it on: it catches the undefined and null mistakes that otherwise surface at runtime in a request handler. See TypeScript for NestJS for the ! convention on DTO properties.

Both variants compile with "module": "nodenext" and "moduleResolution": "nodenext", which is what makes the .js extensions mandatory in the ESM variant. Two practical consequences: existing CommonJS projects can upgrade to v12 and stay CommonJS (nest upgrade deliberately leaves the module format alone), and Jest can load the ESM-only v12 packages only on Node.js 24.9 or newer. The .js extension rule, emitDecoratorMetadata and the other tsconfig.json settings are explained in TypeScript for NestJS and, for the compiler options themselves, in TSConfig & Compiler Options.

main.ts and NestFactory.create

The file src/main.ts bootstraps the application:

import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module.js';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  await app.listen(process.env.PORT ?? 3000);
}
await bootstrap();

Source: NestJS: First steps - Setup

(The CommonJS variant imports './app.module' and ends with void bootstrap();.) Starting it with npm run start and calling it:

curl http://localhost:3000/
Hello World!

Source: NestJS: First steps - Running the application

NestFactory (from @nestjs/core) is the static entry point of the framework. Its create() method takes the root module (and optional options or an adapter) and returns an application object implementing INestApplication. Everything else — global pipes and filters, shutdown hooks, app.listen(), app.close() — is a method of that object and is covered in the pages that follow. The listen() port comes from the PORT environment variable, falling back to 3000 (do not hardcode it; containers and platforms inject it).

Where bootstrap sits in the lifecycle

flowchart LR A["node dist/main.js"] --> B["NestFactory.create(AppModule)
scan modules, build the DI graph,
instantiate providers"] B --> C["app.listen(port)
init: onModuleInit,
onApplicationBootstrap"] C --> D["HTTP server accepts requests
middleware, guards, pipes,
handler"] D --> E["app.close()
onModuleDestroy,

create() resolves the module graph and instantiates providers; onModuleInit() and onApplicationBootstrap() hooks run when the application is initialized, which happens when you call app.init() or app.listen() (or, in tests, createNestApplication().init()), and the HTTP port is bound only afterwards. The per-request path (middleware, guards, interceptors, pipes, filters) begins after listen(); see Request Lifecycle, and Lifecycle Events & Shutdown for the hooks. Source: NestJS: Lifecycle events

Failing at startup: abortOnError

If anything throws while the application is being created (for example a provider factory that cannot reach its database), Nest logs the error and the process exits with code 1. To receive the error instead — to close resources, report it, or set your own exit code — disable abortOnError:

import { NestFactory } from '@nestjs/core';
import { FailingModule } from './failing.module.js';

async function bootstrap() {
  try {
    const app = await NestFactory.create(FailingModule, {
      abortOnError: false,
    });
    await app.listen(process.env.PORT ?? 3000);
  } catch (error) {
    console.error('Bootstrap failed, cleaning up before exit', error);
    process.exitCode = 1;
  }
}
await bootstrap();

Source: NestJS: First steps - Setup

An end-to-end check of this behaviour (await expect(NestFactory.create(FailingModule, { abortOnError: false })) .rejects.toThrow(…​)) passes; without the option the same call terminates the Node.js process, which is also why a test that needs to assert on the failure must set it.

Express and Fastify

Nest is platform-agnostic. Two HTTP platforms are supported out of the box: @nestjs/platform-express (Express 5, the default and already installed) and @nestjs/platform-fastify. Each has its own application interface: NestExpressApplication and NestFastifyApplication. Pass the type to create() only when you need the underlying platform API; otherwise the plain INestApplication is enough.

import { NestFactory } from '@nestjs/core';
import type { NestExpressApplication } from '@nestjs/platform-express';
import { AppModule } from './app.module.js';

async function bootstrap() {
  const app = await NestFactory.create<NestExpressApplication>(AppModule);
  app.set('trust proxy', 'loopback'); // Express-only API, available through the typed app
  await app.listen(process.env.PORT ?? 3000);
}
await bootstrap();

Source: NestJS: First steps - Platform, NestJS: Rate limiting

To use Fastify, install the adapter (npm i @nestjs/platform-fastify) and pass a FastifyAdapter:

import { NestFactory } from '@nestjs/core';
import {
  FastifyAdapter,
  NestFastifyApplication,
} from '@nestjs/platform-fastify';
import { AppModule } from './app.module.js';

async function bootstrap() {
  const app = await NestFactory.create<NestFastifyApplication>(
    AppModule,
    new FastifyAdapter(),
  );
  // Fastify listens on localhost only unless a host is given.
  await app.listen(process.env.PORT ?? 3000, '0.0.0.0');
}
await bootstrap();

Source: NestJS: Performance (Fastify)

Running the Application: the start Scripts

A Nest application is a standard TypeScript application that must be compiled before Node.js runs it. The CLI is a thin, replaceable layer: nest build wraps the compiler (tsc or swc for standard projects, Rspack for monorepos) and adds only path mapping and CLI plugins, and nest start ensures the project is built and then launches node portably. The scripts nest new writes into package.json are:

{
  "scripts": {
    "build": "nest build",
    "deploy": "nest deploy",
    "format": "prettier --write \"src/**/*.ts\" \"test/**/*.ts\"",
    "start": "nest start",
    "start:dev": "nest start --watch",
    "start:debug": "nest start --debug --watch",
    "start:prod": "node dist/main",
    "lint": "oxlint --type-aware src/ test/",
    "test": "vitest run",
    "test:watch": "vitest",
    "test:cov": "vitest run --coverage",
    "test:debug": "vitest --inspect-brk --no-file-parallelism",
    "test:e2e": "vitest run --config ./vitest.config.e2e.ts"
  }
}

Source: NestJS: CLI scripts, NestJS: SWC - Vitest

Extra options are passed to the CLI after --. For example npm run start — -b swc starts with the SWC builder without touching nest-cli.json. Because nest start forwards process-level flags, you can also load environment files and pass application arguments:

echo "PORT=3111" > .env.dev
nest start --env-file .env.dev -- mode=demo

Source: NestJS: CLI usage - nest start

With a main.ts that logs process.env.PORT and process.argv.slice(2), this prints PORT=3111 ARGV=["mode=demo"] and serves on port 3111. --env-file is relative to the current directory, may be repeated, and is for development: in production set real environment variables or use the configuration module (see Configuration). A typical production build-and-run sequence is:

npm ci
npm run build
npm run start:prod

Source: NestJS: CLI scripts

That sequence is the minimum; containerizing it properly (multi-stage builds, pruning dev dependencies, a non-root user) is covered in Deployment.

@Controller('books')
export class BooksController {
  constructor(private readonly booksService: BooksService) {}

  @Post()
  create(@Body() createBookDto: CreateBookDto) {
    return this.booksService.create(createBookDto);
  }

  @Get()
  findAll() {
    return this.booksService.findAll();
  }

  @Get(':id')
  findOne(@Param('id') id: string) {
    return this.booksService.findOne(+id);
  }

  @Patch(':id')
  update(@Param('id') id: string, @Body() updateBookDto: UpdateBookDto) {
    return this.booksService.update(+id, updateBookDto);
  }

  @Delete(':id')
  remove(@Param('id') id: string) {
    return this.booksService.remove(+id);
  }
}
@Injectable()
export class BooksService {
  create(createBookDto: CreateBookDto) {
    return 'This action adds a new book';
  }

  findAll() {
    return `This action returns all books`;
  }

  findOne(id: number) {
    return `This action returns a #${id} book`;
  }
  // update() and remove() follow the same pattern
}

With --dry-run nothing was written (package.json was unchanged). What the command does, in full:

  • Refuses to run on Node.js lacking require(esm) (older than 20.19, or 22.x older than 22.12).

  • Moves every recognized @nestjs/* package to its v12-compatible major (GraphQL, Apollo and Mercurius packages go to v14) and lists the unrecognized ones for you to review.

  • Bumps TypeScript to v6 and raises engines.node to >=20.19.0 if lower.

  • Moves nest-cli.json off the deprecated webpack options to --builder rspack, updating matching scripts.

  • Renames the GraphQL playground option to graphiql and switches subscriptions from subscriptions-transport-ws to graphql-ws; replaces the legacy nats package with @nats-io/transport-node; moves @nestjs/config library-specific settings under validationOptions.libraryOptions and bumps Joi to v18.

  • Bumps Jest to v30 where present (Jest loads the ESM-only v12 packages only on Node.js 24.9+).

  • Optionally installs and wires up @nestjs/observe (prompt defaults to no).

  • Checks tsconfig.json and tsconfig.build.json for settings TypeScript 6 or the ESM packages no longer support.

  • Scans sources and prints notes about behaviour changes it cannot migrate (lifecycle hook ordering, refined pipe signatures, structured logging params), then installs dependencies unless --skip-install is given and prints a report.

It deliberately does not migrate your project to ESM, Vitest or oxlint. SWC

SWC is a Rust-based compiler and the quickest way to speed up the development loop. Install the packages and select the builder on the command line or in nest-cli.json:

npm i --save-dev @swc/cli @swc/core
nest start -b swc
nest start -b swc --watch

Source: NestJS: SWC - Getting started

{
  "compilerOptions": {
    "builder": "swc"
  }
}

To customize it, pass an object. Here the SWC settings are read from a custom .swcrc path:

{
  "compilerOptions": {
    "builder": {
      "type": "swc",
      "options": { "swcrcPath": "infrastructure/.swcrc" }
    },
    "typeCheck": true
  }
}

Source: NestJS: SWC - Getting started

The builder is preconfigured for Nest. To change SWC options, put a .swcrc in the project root; for example this file (with legacyDecorator and decoratorMetadata, which Jest-with-SWC setups also need):

{
  "$schema": "https://swc.rs/schema.json",
  "sourceMaps": true,
  "jsc": {
    "parser": { "syntax": "typescript", "decorators": true, "dynamicImport": true },
    "transform": { "legacyDecorator": true, "decoratorMetadata": true },
    "baseUrl": "./"
  },
  "minify": false
}

Source: NestJS: SWC - SWC configuration

Both configurations build and run. The SWC builder emits ES modules when package.json has "type": "module" (the default for new projects) and CommonJS otherwise; a module setting in .swcrc overrides this.

SWC and type checking

SWC only strips types; it never reports a type error. With a deliberate type error in the source (a number constant assigned the string 'forty-two') the three variants behaved differently:

nest build                       # tsc
nest build -b swc                # SWC without checking
nest build -b swc --type-check   # SWC plus tsc in noEmit mode
src/bad.ts:1:14 - error TS2322: Type 'string' is not assignable to type 'number'.
Found 1 error(s).

SWC  Running...
Successfully compiled: 17 files with swc (36.11ms)

1 export const answer: number = 'forty-two';
   ~~~~~~
Error  Found 1 type error(s) during compilation.

Source: NestJS: SWC - Type checking

Plain SWC built the broken file without complaint. With --type-check (or "typeCheck": true) the CLI runs tsc in noEmit mode alongside SWC and fails the build on errors. In watch mode the check runs asynchronously, so the application restarts quickly and reports type problems next to it; in CI always enable it, or run tsc --noEmit as a separate step. The --type-check flag also executes CLI plugins and writes the serialized metadata file the application loads at runtime.

Known SWC limits, from the official page: it handles circular imports poorly, so wrap entity property types (profile: Relation<Profile> with TypeORM’s Relation, or a WrapperType<T> alias of your own, also used with forwardRef injections); and in a monorepo CLI plugins need the PluginMetadataGenerator. The docs claim SWC is about 10x (overview page) or 20x (SWC page) faster than tsc; the two pages disagree and the factor depends on the project, so measure your own. On a fresh 17-file project, SWC compiled the files in 36 ms. Source: NestJS: SWC - Common pitfalls

Rspack

Rspack bundles the application into a single file and is the default builder for monorepo projects in v12 (it replaces webpack, which is deprecated together with --webpack, --webpackPath and the webpack and webpackConfigPath options; nest upgrade migrates them). It requires extra packages that the CLI checks for. Selecting it without them fails with:

The "webpack-node-externals" package is required when using the rspack compiler but could not be found. Please install it:

  npm install --save-dev @rspack/core webpack-node-externals tsconfig-paths-webpack-plugin

After installing them, "builder": "rspack" (or nest build -b rspack) produces dist/main.js and dist/main.js.map only, and node dist/main.js serves Hello World!. Use --rspackPath [path] for a custom Rspack configuration. Standard projects default to tsc, monorepos to Rspack, which the docs say can significantly reduce build times on larger codebases and emits one file with all components. Rspack did not report a type error that tsc reports (the same broken file built successfully), so run tsc --noEmit in CI when you use it. Details of monorepo builds are in Project Structure & Workspaces. Source: NestJS: CLI workspaces - Specified compiler, NestJS: CLI usage - nest build

Hot Reload and Watch Mode

nest start --watch (npm run start:dev) recompiles on change and restarts the process. It is live reload, not hot-module replacement: application state is lost on every change. With the SWC builder, editing app.service.ts while nest start --watch is running produces Successfully compiled src/app.service.ts with swc, a type-checker pass, a second Starting Nest application…​ and a changed curl response a few seconds later. SWC recompiles only the changed file, which is why it feels faster than tsc on a large project.

npm run start:dev
# or, faster compile with type checking in the background:
nest start --watch -b swc --type-check

Source: NestJS: First steps - Running the application

Related switches:

  • --watchAssets or compilerOptions.watchAssets also watches non-TypeScript files (for example .graphql schemas).

  • --preserveWatchOutput keeps earlier output instead of clearing the screen in tsc watch mode.

  • Manual restart. With "manualRestart": true in compilerOptions, typing rs in the terminal restarts the server (the process restarts after rs is sent to a running nest start --watch).

  • HMR. The official Hot reload recipe uses webpack’s Hot-Module Replacement for CommonJS projects. Webpack is deprecated in v12 and the recipe’s own warning points new projects to --builder rspack; for daily work the SWC watch loop above is the supported fast path. Source: NestJS: Hot reload

Debugging in an IDE

nest start --debug starts the compiled application with the Node.js inspector (--inspect); start:debug adds --watch. The optional value is a host and port:

nest start --debug
nest start --debug 0.0.0.0:9230
Debugger listening on ws://127.0.0.1:9229/...
Debugger listening on ws://0.0.0.0:9230/...

Source: NestJS: CLI usage - nest start

The default is port 9229 on the loopback address. Do not bind the inspector to 0.0.0.0 on a shared network: the protocol offers remote code execution to anyone who can reach it (the second example is for a container where the port is published only to your machine). Any client that speaks the inspector protocol can attach. In VS Code, run npm run start:debug in a terminal and attach with a .vscode/launch.json like this:

{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "node",
      "request": "attach",
      "name": "Attach to Nest",
      "port": 9229,
      "restart": true
    }
  ]
}

Source: Visual Studio Code: Debugging Node.js

restart: true re-attaches after each watch-mode restart. Breakpoints in .ts files work because the generated tsconfig.json sets sourceMap: true, so the debugger maps dist/*.js back to the sources (the SWC builder also emits source maps with the preconfigured settings, and the .swcrc shown above sets sourceMaps). The attach configuration itself is an IDE feature; the CLI’s part is opening the inspector on the expected port. The inspector also works with Chrome DevTools via the chrome://inspect page and with other IDEs. For tests, the ESM template’s test:debug script (vitest --inspect-brk --no-file-parallelism) pauses before the first line so you can attach and step through a test; the CommonJS one runs Jest with --inspect-brk and --runInBand. Beyond a step debugger, the Nest Devtools integration visualises the module graph; it is the subject of Debugging & Devtools.

Pitfalls

  • Wrong Node.js for the job. Running works on 20.19+/22.12+, but nest new and nest g need 22.22.3+, 24.15+ or 26+. An older Node.js fails in the generator, not in your code.

  • Missing .js extension (ESM). import { AppModule } from './app.module' compiles under nodenext only with the extension in an ESM project. Do not "fix" it by switching moduleResolution.

  • Forgetting to build before start:prod. node dist/main runs whatever is in dist/; a stale or missing build means stale or no application. deleteOutDir empties dist/ on every build.

  • Global CLI drift. Two developers with different global nest versions generate different code. Use the package.json scripts for build and start, and nest info in bug reports.

  • nest upgrade with an old global CLI. The command ships with the CLI; upgrade the global binary first.

  • SWC without type checking. Builds pass with type errors unless --type-check or typeCheck: true is set.

  • SWC and circular imports. Use Relation<> or a wrapper type for entity relations.

  • Rspack without its packages. The build fails until @rspack/core, webpack-node-externals and tsconfig-paths-webpack-plugin are installed.

  • Assets outside src or on incremental builds. Only files under src are copied, and not on incremental --watch compiles unless watchAssets is on.

  • generateOptions.spec keys. The key must match the schematic spelling you type (service versus s).

  • Fastify in a container. Without '0.0.0.0' the server is unreachable from outside the container.

  • Placeholder generated code. Generated guards return true and generated resource services return strings; replace them before exposing the endpoint.

  • Port in use. A stale start:dev holds port 3000; set PORT or stop the old process.

  • Reading outdated tutorials. See the next section.

  • Docs (Sep 2026). The documentation was restructured; this section only links the new URLs (/cli/, /recipes/, /http/*, …​).

  • TypeScript. The v12 templates pin TypeScript 6; TypeScript 7 is not what nest new generates.

  • Pre-1.0 packages. @nestjs/observe (offered by nest new) and @nestjs/mau (used by nest deploy) are pre-1.0; expect their APIs and the prompts that reference them to move.

The book Scalable Application Development with NestJS (published January 2025) predates all of this: it cannot show the ESM/Vitest default, oxlint, Rspack, nest upgrade or nest deploy, and it contains commands that are not valid, such as nest new app hr (nest new takes one name; generate an extra monorepo app with nest g app <name>) and nest start:dev order (a script name is not a CLI subcommand; use nest start order --watch, or npm run start:dev). Use the commands on this page instead; the bibliography is on the section index.
