What’s Changed & Migration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against NestJS 12.1 (npm @nestjs/core 12.1.2, published 2026-09-30; the newest GitHub release page is v12.1.1, 2026-09-28), TypeScript 6 (6.0.x, what the Nest 12 templates install), Node.js 22 and 24 LTS, Express 5 and Fastify 5, and was checked on 2026-10-02. The code examples target the Nest 12 ESM template with Vitest and supertest, and the output blocks are what they produce. The nest upgrade --dry-run report comes from @nestjs/cli 12.0.8 run against a small NestJS 11 project.

NestJS moved quickly between the book’s era (NestJS 10, Node.js 16, TypeScript 4, published January 2025) and today. This page is the one place that collects what is different, with the version and date of each change, the old way next to the new way, the page of this section that teaches it, the official migration guide and the GitHub release notes. Read it once if you are following the book or an older tutorial, then use the tables as a lookup. Where a row says "pre-1.0", the package is still at a 0.x version and its API may change; the pages that teach it show the established alternative.

Release timeline

Dates are those of the GitHub release page, except 12.1.2, which has an npm publication but no GitHub release page yet. The migration guide column links the guide that was current for that major: the archived versions of the documentation keep their own migration-guide page.

Express 5 routing and HTTP

Version Date Old way New way Covered on Guide Notes

11.0.0

2025-01-16

forRoutes(''), @Get('files/'), optional parameters with ? (:id?), regular-expression characters in paths, nested query strings (?filter[a]=1 parsed into objects).

Express 5 and path-to-regexp 8: wildcards are named (splat, or {*splat} to also match the bare path), optional parts use braces ({.:ext}), regexp characters are no longer allowed, and the query parser is simple (restore the old one with app.set('query parser', 'extended')). Nest still converts an unnamed and logs a warning, so old code runs, but the docs call bare * deprecated. The Fastify adapter does not support mid-route wildcards.

Standard Schema in the route decorators

@Body({ schema }) and @Param('id', { schema }) only attach the schema; StandardSchemaValidationPipe validates it. Zod is used here, but any Standard Schema library works.

standard-schema.ts
import { Body, Controller, Get, Param, Post } from '@nestjs/common';
import { z } from 'zod';

// Any Standard Schema library works (Zod 4, Valibot, ArkType); Zod is used here.
export const createBookSchema = z.object({
  title: z.string().min(1),
  isbn: z.string().regex(/^\d{13}$/),
});
export type CreateBook = z.infer<typeof createBookSchema>;

@Controller('books')
export class BooksController {
  private readonly books: Array<CreateBook & { id: number }> = [];

  @Post()
  // The decorator only attaches the schema; StandardSchemaValidationPipe validates it.
  create(@Body({ schema: createBookSchema }) body: CreateBook) {
    const book = { id: this.books.length + 1, ...body };
    this.books.push(book);
    return book;
  }

  @Get(':id')
  findOne(@Param('id', { schema: z.coerce.number().int().positive() }) id: number) {
    return { id, typeofId: typeof id };
  }
}

Register the pipe once, for example in main.ts (app.useGlobalPipes(new StandardSchemaValidationPipe())). A valid body and an invalid one produced:

Output
{"id":1,"title":"Dune","isbn":"9780441013593"}
{"message":["title: Too small: expected string to have >=1 characters","isbn: Invalid string: must match pattern /^\\d{13}$/"],"error":"Bad Request","statusCode":400}

GET /books/42 returned {"id":42,"typeofId":"number"} (the schema coerces the string) and GET /books/-1 returned 400. Source: Migration guide, "Route decorator schemas".

Route conflicts

The controller below declares the parametric route first, as in the documentation’s example:

route-conflicts.ts
import { Controller, Get, Param } from '@nestjs/common';

@Controller('members')
export class MembersController {
  // Declared first: on Express it is registered first and shadows 'me'.
  @Get(':id')
  byId(@Param('id') id: string) {
    return { handler: 'byId', id };
  }

  @Get('me')
  me() {
    return { handler: 'me' };
  }
}

With the defaults, GET /members/me returned {"handler":"byId","id":"me"}. With the two opt-in options:

const app = await NestFactory.create(MembersModule, {
  routeConflictPolicy: { duplicate: 'error', shadow: 'warn' },
  routeResolutionStrategy: 'specificity',
});

routeResolutionStrategy: 'specificity' alone made GET /members/me return {"handler":"me"}. routeConflictPolicy: { shadow: 'warn' } logged the following warning at bootstrap, and { shadow: 'error' } aborted the bootstrap with the same text under a "Conflicting HTTP routes detected" heading:

Warning (logger.warn)
Route GET /members/me (MembersController#me) is shadowed by GET /members/:id (MembersController#byId). The first-registered route will match all matching requests on order-sensitive adapters.

Combining shadow: 'error' with routeResolutionStrategy: 'specificity' started without error, because the specificity ordering removes the shadowing. Source: Controllers, "Route conflicts and resolution order".

Express 5 wildcards, optional parts and the query parser

express5-routes.ts
import { Controller, Get, MiddlewareConsumer, Module, NestModule, Param, Query } from '@nestjs/common';
import type { Request, Response, NextFunction } from 'express';

@Controller()
export class FilesController {
  // Express 4: 'files/*'. Express 5 needs a named wildcard; the value is an array of segments.
  @Get('files/*path')
  file(@Param('path') path: string[]) {
    return { path };
  }

  // '{*path}' also matches the bare 'docs' (the wildcard is optional).
  @Get('docs{/*path}')
  docs(@Param('path') path?: string[]) {
    return { path: path ?? null };
  }

  // Express 5 uses the 'simple' query parser: 'a[b]=1' stays a flat key, it is no longer nested.
  @Get('search')
  search(@Query() query: Record<string, unknown>) {
    return query;
  }

  // Express 4: 'report/:id?'. Express 5 has no '?'; optional parts use braces.
  @Get('report/:id{.:ext}')
  report(@Param('id') id: string, @Param('ext') ext?: string) {
    return { id, ext: ext ?? null };
  }
}

export function tag(req: Request, res: Response, next: NextFunction) {
  res.setHeader('x-seen', 'yes');
  next();
}

@Module({ controllers: [FilesController] })
export class FilesModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    // Express 4 / Nest 10: forRoutes('*'). Nest 11+: a named wildcard.
    consumer.apply(tag).forRoutes('{*splat}');
  }
}

export function restoreExtendedQueryParser(app: import('@nestjs/platform-express').NestExpressApplication) {
  // Express 5 defaults to the 'simple' parser; opt back in to nested objects.
  app.set('query parser', 'extended');
}
Responses
GET /files/a/b/c.txt                    {"path":["a","b","c.txt"]}
GET /docs                               {"path":null}
GET /docs/x/y                           {"path":["x","y"]}
GET /report/7                           {"id":"7","ext":null}
GET /report/7.pdf                       {"id":"7","ext":"pdf"}
GET /search?filter[genre]=sf&tag=a&tag=b  {"filter[genre]":"sf","tag":["a","b"]}
GET /search?filter[genre]=sf  (after app.set('query parser', 'extended'))  {"filter":{"genre":"sf"}}

The old spellings still run: a controller with @Get('old/') and a module that calls forRoutes('') start, answer 200 and apply the middleware, but Nest logs a warning (Unsupported route path: "/old/*" …​ Attempting to auto-convert to "/old/{*path}"…​). Treat that warning as a to-do item: the converter is a compatibility layer, not a supported spelling. Source: Controllers, "Route wildcards" and Express: Migrating to Express 5.

The global prefix: string, with an array of exclusions

prefix.ts
import type { INestApplication } from '@nestjs/common';

export function configurePrefix(app: INestApplication) {
  // exclude has always been an array; the prefix itself is a string in 12.1.2.
  app.setGlobalPrefix('api', { exclude: ['health', 'status'] });
}

export function arrayPrefixTypeCheck(app: INestApplication) {
  // The v12.1.0 notes list "array of global prefixes"; the published 12.1.2 typings
  // still take a string, so this line is a compile-time error.
  // @ts-expect-error prefix must be a string in the published packages
  app.setGlobalPrefix(['api', 'v1']);
}

The first function behaved as documented (/health unprefixed, /api/members/5 served, /members/5 404). The @ts-expect-error line proves the 12.1.2 signature is setGlobalPrefix(prefix: string, options?: GlobalPrefixOptions): if the array overload had shipped, the directive would itself be reported as unused. Forcing the array through a cast did not fail at bootstrap, but /api/members/5, /v1/members/5 and /api,v1/members/5 all returned 404. The v12.1.0 release notes (PR 17713) and the published 12.1.2 packages therefore disagree; use a single string prefix and exclude (which was always an array), and re-check the typings after upgrading. Source: Global prefix.

@Optional() and inheritance

The migration guide says Nest 12 reads optional markers with Reflect.getOwnMetadata, so a subclass without its own constructor keeps the parent’s parameter types but loses their optional status, and Nest throws UnknownDependenciesException. The 12.1.0 release notes list "inherit optional ctor params when the constructor is not redeclared" (PR 17838). Both were tested with a parent that has an optional parameter, a subclass that does not redeclare the constructor and a subclass that does:

optional-inheritance.ts
@Injectable()
export class BaseClient {
  constructor(@Optional() @Inject('HTTP_OPTIONS') readonly options?: HttpOptions) {}
}

// Does not redeclare the constructor: what happens to the parent's @Optional()?
@Injectable()
export class ImplicitChild extends BaseClient {}

// Recommended: redeclare the constructor and repeat the marker.
@Injectable()
export class ExplicitChild extends BaseClient {
  constructor(@Optional() @Inject('HTTP_OPTIONS') options?: HttpOptions) {
    super(options);
  }
}
Output with @nestjs/core 12.1.2 (the HTTP_OPTIONS provider missing, then present)
BaseClient, dep missing:     resolved options=undefined
ExplicitChild, dep missing:  resolved options=undefined
ImplicitChild, dep missing:  resolved options=undefined
BaseClient, dep present:     resolved options={"timeout":5}
ExplicitChild, dep present:  resolved options={"timeout":5}
ImplicitChild, dep present:  resolved options={"timeout":5}

A typed parameter without @Inject() (constructor(@Optional() readonly mailer?: Mailer)), compiled with SWC so that decorator metadata is emitted as in a real project, gives the same result: the implicit subclass resolves with mailer undefined. With 12.1.2, then, the behaviour matches the 12.1.0 fix, not the migration guide’s text. The 12.0.x behaviour is the one the guide describes. The portable rule is the one the guide gives: when a subclass takes optional dependencies, declare the constructor and repeat @Optional(). That is correct on every v12 release and does not depend on the fix. Source: Migration guide, "@Optional() is no longer inherited" and release v12.1.0.

nest upgrade

nest upgrade (alias nest update) ships with the CLI, so upgrade the CLI first, and do it globally if you use a global binary, because the command only bumps the project’s local @nestjs/cli dependency:

npm i -g @nestjs/cli@latest @nestjs/schematics@latest
npm i -D @nestjs/cli@latest @nestjs/schematics@latest   # if the CLI is a local dev dependency
nest upgrade --dry-run      # print the report, change nothing
nest upgrade                # apply the changes and run the install

It refuses to run on Node.js releases without require(esm) (older than 20.19, or 22.x older than 22.12). It moves every recognised @nestjs/* package to its v12-compatible major (and reports unrecognised ones), bumps TypeScript to v6, raises engines.node when it declares a lower floor, migrates the webpack options of nest-cli.json and package.json scripts to Rspack, renames the GraphQL playground option to graphiql and swaps the subscription packages, replaces nats with @nats-io/transport-node, moves @nestjs/config library settings under libraryOptions and bumps Joi to v18, bumps Jest to v30 where present, can install and wire @nestjs/observe, checks the tsconfig files for options TypeScript 6 or the ESM packages no longer support, and prints notes about behaviour it cannot migrate (lifecycle hook ordering, pipe signatures, structured logging params). It deliberately does not move your project to ESM, Vitest or oxlint.

Where the book is outdated

The reference book (see the section bibliography) targets NestJS 10, Node.js 16 and TypeScript 4, and was published in January 2025, a few days before NestJS 11. Use it for the concepts and this section for the current API; the tables above give every difference. In short:

  • Runtime and tooling: its Node.js, Docker and CI versions are past their end of life, and it predates nest upgrade, ESM packages, Vitest, oxlint, Rspack, bun and Mau.

  • Express 5 (11.0.0): its forRoutes('*'), unnamed wildcards and optional ? parameters need the named forms, and nested query strings are no longer parsed by default.

  • Packages that moved: caching comes from @nestjs/cache-manager (cache-manager 6, Keyv, TTL in milliseconds), HTTP calls from @nestjs/axios or @nestjs/http-client, queues from @nestjs/bullmq, health checks from the HealthIndicatorService API, GraphQL from @nestjs/apollo with a driver, GraphiQL and graphql-ws.

  • Validation, serialization and configuration: Standard Schema is a second option beside class-validator; @nestjs/config is a first-class dependency, not an afterthought, and credentials come from it, never from source code or synchronize: true in production.

  • Security: Helmet, CSRF and cookies have built-in equivalents since 12.1, rate limiting is @nestjs/throttler 6, and encryption uses an authenticated mode.

  • Reliability: the book’s hand-rolled outbox, idempotency, locks and sagas have first-party, pre-1.0 counterparts, and @nestjs/cqrs sagas are in-process, not distributed.

  • Code errors: the book contains code that does not run (decorators that do not exist, removed TypeORM APIs, errors returned as HTTP 200, a response interceptor registered twice, GraphQL types without @ObjectType, one new PubSub() per resolver, invalid CLI commands). The pages of this section show the correct form where they touch those topics instead of repeating them.

What changed recently

  • NestJS 11.2.0 (2026-08-14): the HTTP QUERY method and the SSE signal, plus fixes for lazy-loaded modules and Fastify middleware on excluded routes.

  • NestJS 12.0.0 (2026-08-27): ESM packages, Standard Schema, the rebuilt CLI, native observability, route conflict diagnostics, errorCode, structured logging, and the breaking changes listed in the migration guide (Node.js floor, lifecycle hook order, NATS v3, graphql-ws only, GraphiQL, @nestjs/config validation, pipe signatures, removed Terminus legacy API, deprecated webpack workflows, removed angular schematic).

  • NestJS 12.1.0 (2026-09-23): built-in cookies, CSRF protection and security headers, Fastify upload interceptors, the ParseDatePipe default fix, middleware fixes, the optional constructor parameter fix and the array-prefix entry that the published packages do not contain.

  • NestJS 12.1.1 (2026-09-28) and 12.1.2 (2026-09-30): logger fixes for JSON output, level changes, fatal and buffered logs, reconnect fixes for the Redis, MQTT, TCP, NATS, Kafka and RabbitMQ clients, ParseArrayPipe item checking and circular dependency detection across more than two providers.

  • Documentation (September 2026): the restructure described below, a new Observability group, a new Reliability group, and the migration guide rewritten for 11 to 12.

  • Ecosystem: TypeORM is on 1.x (1.1.1), Prisma’s latest tag points at the 8.0.0 release candidate (8.0.0-rc.19), so the pages of this section pin prisma@7 (check npm view prisma dist-tags before choosing a version), @nestjs/graphql 14 resolves GraphQL 16, and TypeScript 7.0 is on npm while Nest 12 templates stay on TypeScript 6.

Checklist for moving a book-era project to NestJS 12

  1. Upgrade Node.js to a supported release (20.19+ or 22.12+ to run, 22.22.3+ or 24.15+ to use the generators) and the CLI, then run nest upgrade --dry-run and read the report.

  2. Run nest upgrade, fix the tsconfig.json and Rspack items it lists, and run the test suite on Node.js 24.9+ if you stay on Jest.

  3. Replace unnamed wildcards and ? parameters, check any code that relied on nested query strings, and consider routeConflictPolicy in a test environment.

  4. Move cache, HTTP client, queue and health-check code to the packages and APIs in the tables above.

  5. Give every subclass with optional dependencies an explicit constructor with @Optional().

  6. Review lifecycle hook ordering, GraphQL subscriptions clients, NATS imports and custom pipe signatures, then adopt Standard Schema, the built-in security features and the new first-party packages on your own schedule.
