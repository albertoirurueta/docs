Flask 3.2 has not been released yet; nothing in the Flask 3.2 changelog checked on that date changes the command line, and the context changes announced for it are described in the Application & Request Lifecycle page. Installing Flask installs a console script called flask. It is a Click program that Flask ships and that looks your application up on demand, so one command gives you the development server, a route listing, an interactive shell, the commands of your extensions (flask db upgrade, for instance) and the maintenance commands you write yourself. The page uses the Bookshelf application of the previous pages and answers four questions: how flask finds the app, what the built-in commands do, how to add your own commands and how to test them.

What the flask Command Is

pip install Flask puts a flask script in the virtual environment. Its entry point is flask.cli:main, and python -m flask runs the same function, which is handy when the script is not on the PATH or when an IDE or a process manager wants a module to run. The object behind the command is a FlaskGroup, a subclass of AppGroup, which is itself a subclass of Click’s Group. Click parses the command line, shows --help, converts option types and reads environment variables; Flask adds the part Click cannot know about: finding and loading your application.

  • FlaskGroup registers the built-in commands run, shell and routes, three eager options that act before anything else (--env-file, --app and --debug), and --version.

  • Commands from installed packages are added from the flask.commands entry point group (see Plugins).

  • Commands from your application are added from app.cli, a Click AppGroup that every Flask object has. Looking at app.cli means the app has to be imported first, so flask --help imports your application to list its commands.

  • A ScriptInfo object travels in the Click context. It stores the --app string and loads the application once, so every command of one invocation sees the same app instance.

flowchart TD A["flask --env-file F --app X --debug COMMAND"] --> B["eager options: load dotenv files, remember X, set FLASK_DEBUG"] B --> C{"COMMAND is built-in or from a plugin?"} C -->|yes| D["run it (run, shell and routes load the app themselves)"] C -->|no| E["ScriptInfo.load_app() imports the app"] E --> F["look COMMAND up in app.cli"] F --> G["push an application context and run it"]

Two consequences of this design matter in practice. First, built-in and plugin commands are looked up before the app is loaded, so flask --version and flask run --help work even when the application is broken, while flask routes or any command of app.cli shows the load error instead. Second, because the flask script belongs to Flask and not to your project, it works with any layout; the alternative of shipping your own script built on FlaskGroup is covered in Custom Scripts.

Application Discovery: How --app Resolves

The --app option (short -A) is the first thing every flask invocation needs. The value has three optional parts: a path, a module (a file or a dotted import) and a name that can carry factory arguments in parentheses. The table of examples is in Application Factory & Project Layout; this page shows the full algorithm that sits behind it, which the official page only summarises:

  1. With no --app (and no FLASK_APP environment variable) Flask tries to import wsgi.py first and then app.py from the current directory. The first one that imports and contains an application wins.

  2. The module is searched for an object called app, then one called application, and then for any single Flask instance among the module’s globals. Two or more candidates are an error that asks for module:name.

  3. If there is no instance, Flask looks for a function called create_app and then one called make_app and calls it without arguments. A factory with a required parameter fails with a message that tells you to write module:create_app(args).

  4. With module:name the name is a plain attribute (an instance or a function). If it is a function it is called; what it returns must be a Flask object.

  5. With module:name(args) the text in parentheses is parsed with ast.literal_eval, so arguments are Python literals such as "dev" or debug=True, and a name like len is rejected.

  6. A path is accepted as well as a dotted name: Flask works out the import name and puts the directory that contains the top-level module on sys.path, which is why --app src/hello works without installing anything.

The FLASK_APP environment variable takes the same value; the command-line option wins when both are present. The following block builds throwaway projects and runs the real command against them. The helper flask() runs python -m flask in a directory and returns the exit code and the combined output.

import os
import pathlib
import subprocess
import sys
import tempfile

root = pathlib.Path(tempfile.mkdtemp())
CLEAN_ENV = {k: v for k, v in os.environ.items() if not k.startswith("FLASK_")}


def project(name, files):
    """Create a throwaway project directory and return it."""
    directory = root / name
    directory.mkdir(parents=True, exist_ok=True)
    for filename, body in files.items():
        path = directory / filename
        path.parent.mkdir(parents=True, exist_ok=True)
        path.write_text(body)
    return directory


def flask(*args, cwd, env=None, input=None):
    result = subprocess.run(
        [sys.executable, "-m", "flask", *args],
        cwd=cwd,
        env={**CLEAN_ENV, **(env or {})},
        input=input,
        capture_output=True,
        text=True,
        timeout=60,
    )
    return result.returncode, (result.stdout + result.stderr).strip()


APP = "from flask import Flask\napp = Flask(__name__)\n\n@app.get('/{path}')\ndef view():\n    return 'ok'\n"

both = project("both", {"wsgi.py": APP.format(path="from-wsgi"), "app.py": APP.format(path="from-app")})
code, out = flask("routes", cwd=both)  # no --app: wsgi.py is tried before app.py
assert code == 0 and "/from-wsgi" in out and "/from-app" not in out
print(out)

two = project("two", {"pair.py": "from flask import Flask\nfirst = Flask('a')\nsecond = Flask('b')\n"})
code, out = flask("--app", "pair", "routes", cwd=two)  # two instances: ambiguous
assert code != 0
print(out.splitlines()[-1])

Pitfalls of discovery:

  • The factory runs once per process that loads the app. flask run --debug starts a parent process that watches files and a child process that serves requests, and both load the app, so the factory body (and any print or connection opened in it) runs twice. Keep factories free of side effects that cannot be repeated.

  • A name such as app that points at a Flask object created inside if __name__ == "__main__": is not found, because the module is imported, not run as a script.

  • Setting FLASK_APP in the shell for the whole session is convenient and still supported, but the documented form is flask --app <module> run --debug (Flask 2.2). The older books and tutorials that tell you to export FLASK_APP=... and export FLASK_ENV=development are covered in What Changed.

  • --app has to come before the command: flask run --app bookshelf is rejected with "No such option" because run has no such option. Only --debug is accepted in both places.

dotenv files. When python-dotenv is installed, flask reads .flaskenv and .env before it looks at --app, so neither --app nor FLASK_APP has to be typed. The rules, as implemented in flask.cli.load_dotenv:

  1. Variables already set in the process environment always win; a dotenv file never overwrites them.

  2. Among the files, --env-file beats .env, which beats .flaskenv.

  3. .flaskenv is meant to be committed and holds public settings such as FLASK_APP; .env is not committed and holds secrets.

  4. The files are searched in the current directory and then upwards, so running flask from a sub-directory still finds the project’s files. Since Flask 2.0 the working directory is no longer changed to the file’s location, and the files are read as UTF-8.

  5. Only the flask command and app.run() load them. A production process started by Gunicorn or Waitress never reads them, so call flask.cli.load_dotenv() yourself or, better, inject real environment variables (the Configuration page shows the options).

  6. Without python-dotenv the command prints a yellow tip on stderr when it sees the files and loads nothing. With FLASK_SKIP_DOTENV set to a true value Flask skips the default files even when python-dotenv is installed, for instance when a process manager already loaded them. The value 0, false or no means "do not skip".

flask routes: Listing the URL Map

flask routes prints every rule of the application’s url_map with its endpoint and methods. It is the quickest way to check that a blueprint was registered, that url_prefix did what you meant and which of two overlapping rules Flask tries first. HEAD and OPTIONS are hidden unless you pass --all-methods. When any rule has a subdomain (or a host, if the app uses host matching) an extra column appears. --sort (short -s) accepts endpoint (the default), methods, domain, rule and match; match keeps the order in which the URL map holds the rules, which is registration order (the static rule of the application is registered first). Since Werkzeug 2.2 a request is matched by a state machine that prefers static parts to converters, so in the listing below /books/new still wins over /books/<int:book_id> although it is listed second; the block checks it.

flask shell: An Interactive Shell With the App Loaded

flask shell starts an interactive Python session with an application context already pushed. Without it, you would import the app, push a context by hand, and import every model each time. The command is built on the standard library’s code.interact; it is not IPython and has no special display or editing features beyond what the interpreter offers. The banner shows the Python version, the application’s import name and the instance folder path, which tells you at a glance which app and which instance (and therefore which config.py and SQLite file) you are about to modify:

What is in the namespace:

  1. The names defined by the file named in the PYTHONSTARTUP environment variable, if it is set (the regular interpreter startup script is honoured).

  2. Whatever app.make_shell_context() returns: by default app and g, plus every dictionary returned by a function registered with @app.shell_context_processor.

  3. Tab completion and history when readline is available; completion uses the shell’s own namespace.

The processors are called every time the shell starts, inside the application context, so they can touch current_app, configuration and extensions. Extensions use them too: Flask-SQLAlchemy registers one that adds db and the model classes (see Flask-SQLAlchemy).

Pitfalls and security of the shell:

  • The shell uses the real configuration. flask shell against a production DATABASE_URL edits production data without review, so read the Instance: line and the config before you type, and prefer a custom command with a confirmation prompt for anything destructive.

  • The shell does not reload code. After editing a model, exit and start it again, or importlib.reload the module.

  • Anyone who can open a shell in a production container has the application’s secrets (its configuration is in memory). Restrict who can run kubectl exec or docker exec, and do not offer a shell through the web application.

  • Creating tables by typing db.create_all() in the shell, as Full-Stack Flask and React does in its SQL chapter, is fine for a first local run, but it neither alters existing tables nor leaves a history; use Database Migrations for anything that outlives a laptop.

Custom Commands With Click

A custom command is a Python function decorated with Click decorators and registered on a group. Flask’s app.cli is an AppGroup; its command() decorator wraps the function so that an application context is pushed before it runs, which means current_app, g, the database extension and app.config work inside it. Click does everything else: the name, the help text (from the docstring), arguments, options, type conversion, prompts, confirmation and exit codes. The name defaults to the function name with underscores turned into dashes (import_books becomes import-books); pass a string to choose it.

import json
import sqlite3

import click
from flask import Flask, current_app, g


def get_db():
    if "db" not in g:
        g.db = sqlite3.connect(current_app.config["DATABASE"])
        g.db.execute("CREATE TABLE IF NOT EXISTS book (title TEXT PRIMARY KEY, author TEXT, year INTEGER)")
    return g.db


def create_app(database):
    app = Flask("bookshelf")
    app.config["DATABASE"] = database

    @app.teardown_appcontext
    def close_db(exception):
        db = g.pop("db", None)
        if db is not None:
            db.close()

    @app.cli.command("add-book")
    @click.argument("title")
    @click.option("--author", required=True, help="Name of the author.")
    @click.option("--year", type=click.IntRange(min=1000, max=2100), default=2000, show_default=True)
    def add_book(title, author, year):
        """Add one book to the catalogue."""
        db = get_db()
        try:
            db.execute("INSERT INTO book VALUES (?, ?, ?)", (title, author, year))
        except sqlite3.IntegrityError:
            raise click.ClickException(f"{title!r} is already in the catalogue") from None
        db.commit()
        click.echo(f"Added {title!r} ({year})")

    @app.cli.command("count-books")
    @click.option("--as-json", is_flag=True, help="Print JSON instead of text.")
    def count_books(as_json):
        """Print the number of books."""
        total = get_db().execute("SELECT COUNT(*) FROM book").fetchone()[0]
        click.echo(json.dumps({"books": total}) if as_json else f"{total} books")

    return app

Notes on writing commands:

  • Arguments and options. @click.argument is positional and required unless given a default; @click.option is named. The types (click.IntRange, click.Path, click.Choice, click.DateTime, click.File) validate before your function runs and print a usage error with exit code 2. Options can read an environment variable (see the next section), prompt (prompt=True), ask for confirmation (confirmation_option) or hide what is typed (hide_input).

  • Output and exit codes. Use click.echo instead of print (it handles encodings and redirected output) and click.echo(..., err=True) for diagnostics. Raise click.ClickException for an expected failure (exit code 1, message prefixed by Error:), click.UsageError for bad usage (exit code 2), or call sys.exit(code) or ctx.exit(code). An uncaught exception prints a traceback and exits with 1. Schedulers and CI jobs rely on that non-zero code.

  • Application context. Commands on app.cli, on a group created with AppGroup, and on bp.cli get the context for free since Flask 2.2, and so do their parameter callbacks. A command built with plain @click.command() needs flask.cli.with_appcontext (shown below). Pass with_appcontext=False to an AppGroup command() for a command that must not load the application, for instance one that creates it.

  • Idempotence and transactions. Commands are re-run after failures. Make them safe to repeat (INSERT OR IGNORE, a check before creating) and commit or roll back explicitly, because teardown_appcontext closes the connection but does not commit for you unless your extension does.

  • Everything is on the app. app.cli.add_command(group) and @app.cli.command() run when the factory builds the app, so a command defined in a module that the factory never imports does not exist. In a factory-based project the cli.py module with an init_app(app) function, shown in Application Factory & Project Layout, is the usual fix.

Blueprint commands

A blueprint carries its own cli group, so a module that owns a feature can also own the commands that maintain it. The commands become available when the blueprint is registered and live in a group named after the blueprint, unless cli_group says otherwise: a string renames the group (in Blueprint(...) or in register_blueprint(..., cli_group=...)) and None merges the commands into the top level, where a name clash with a built-in command or another blueprint means the one registered last silently replaces the other.

from flask import Blueprint

stock = Blueprint("stock", __name__)  # group "stock"
reports = Blueprint("reports", __name__, cli_group=None)  # merged into the top level


@stock.cli.command("count")
def stock_count():
    click.echo("42 books in stock")


@reports.cli.command("weekly")
def weekly():
    click.echo("weekly report")


bp_app = Flask("bp-demo")
bp_app.register_blueprint(stock)
bp_app.register_blueprint(reports)
renamed = Flask("bp-demo-2")
renamed.register_blueprint(stock, cli_group="inventory")  # per registration

assert bp_app.test_cli_runner().invoke(args=["stock", "count"]).output == "42 books in stock\n"
assert bp_app.test_cli_runner().invoke(args=["weekly"]).output == "weekly report\n"
assert renamed.test_cli_runner().invoke(args=["inventory", "count"]).output == "42 books in stock\n"

Options From Environment Variables

The flask group sets Click’s auto_envvar_prefix to FLASK. Every option of every command that does not name its own variable then reads one automatically, built from the prefix, the command path and the option name, upper-cased with dashes as underscores: FLASK_RUN_PORT for flask run --port, FLASK_ROUTES_SORT and FLASK_BOOKS_PURGE_OLDER_THAN for the nested command above. Boolean flags take values such as 1 or true. A value on the command line beats the variable, and the variable beats the option’s default. The rule makes .flaskenv a handy place for per-project defaults (FLASK_RUN_PORT=8000), and it works for your own commands too, provided they are run through flask.

The prefix is a property of the FlaskGroup, not of app.cli. app.test_cli_runner() invokes app.cli directly, so tests do not see the automatic variables unless you pass auto_envvar_prefix="FLASK" to invoke(). An option can also name its variable explicitly with envvar="BOOKSHELF_PAGE_SIZE", which then works in both situations.

env_project = project(
    "envopts",
    {
        "shelf.py": (
            "import click\n"
            "from flask import Flask\n"
            "from flask.cli import AppGroup\n"
            "\n"
            "app = Flask(__name__)\n"
            "books = AppGroup('books')\n"
            "\n"
            "@books.command('purge')\n"
            "@click.option('--older-than', type=int, default=30)\n"
            "def purge(older_than):\n"
            "    click.echo(f'older-than={older_than}')\n"
            "\n"
            "@app.cli.command('page')\n"
            "@click.option('--size', type=int, default=10, envvar='BOOKSHELF_PAGE_SIZE')\n"
            "def page(size):\n"
            "    click.echo(f'size={size}')\n"
            "\n"
            "app.cli.add_command(books)\n"
        )
    },
)
assert flask("--app", "shelf", "books", "purge", cwd=env_project)[1] == "older-than=30"
assert flask("--app", "shelf", "books", "purge", cwd=env_project, env={"FLASK_BOOKS_PURGE_OLDER_THAN": "90"})[1] == "older-than=90"
assert flask("--app", "shelf", "books", "purge", "--older-than", "7", cwd=env_project, env={"FLASK_BOOKS_PURGE_OLDER_THAN": "90"})[1] == "older-than=7"
assert flask("--app", "shelf", "page", cwd=env_project, env={"BOOKSHELF_PAGE_SIZE": "25"})[1] == "size=25"

Plugins: Commands From Installed Packages

Any installed distribution can add commands to the flask script, with no code in your application, by declaring an entry point in the group flask.commands. The name of the entry point becomes the command name and its value must be a Click command or group. The entry point is read with importlib.metadata (since Flask 2.1; earlier versions used pkg_resources), and the commands are loaded when the group is asked for a command or a listing. Because they are loaded before the application, a plugin command works even when the app itself cannot be imported, which is what you want from a command such as a health check or a setup helper.

[project.entry-points."flask.commands"]
bookshelf-doctor = "bookshelf_tools.commands:doctor"
# bookshelf_tools/commands.py
import click


@click.command()
def doctor():
    """Check the Bookshelf environment."""
    click.echo("all good")

Once the package is installed in the same virtual environment as Flask, flask bookshelf-doctor runs the command. The next block proves it without installing anything: it writes the metadata an installed package would have (a .dist-info directory with entry_points.txt) into a temporary directory and puts that directory on PYTHONPATH of a real flask process.

(plugin_dir / "bookshelf_tools" / "commands.py").write_text(

)

dist_info.mkdir()

Extensions use the two mechanisms. Flask-Migrate registers its db group on app.cli when you call Migrate(app, db) or init_app, so flask db exists only for apps that configured it; packages such as Flask-Limiter and APIFlask publish entry points, which is why limiter and spec appear in the flask --help of an environment that has them installed. Plugin commands are added after the built-in ones and share one namespace with them, so a plugin command named like a built-in (run, shell, routes) replaces it; choose distinctive names.

Custom Scripts With FlaskGroup

The flask script is generic. A project that has a single way to build its app can ship its own console script that is a FlaskGroup bound to a factory, so users never type --app and the project can add commands that belong to the script rather than to the app. The group is declared with @click.group(cls=FlaskGroup, create_app=...). The factory is called without arguments (Flask has not passed a script_info argument since 2.1).

FlaskGroup parameter Meaning

create_app

Callable that returns the application, used instead of --app.

add_default_commands

When False, run, shell and routes are not added. Default True.

add_version_option

Adds --version. Default True.

load_dotenv

Load .env and .flaskenv. Default True.

set_debug_flag

Set app.debug from FLASK_DEBUG after loading. Default True.

Source: Flask API: flask.cli.FlaskGroup

Commands defined on the group itself (@cli.command()) are plain Click commands without an application context; the commands of app.cli are still merged in, so the script exposes both. A FlaskGroup can also be nested as a sub-command of a larger Click program (Flask 2.2).

from click.testing import CliRunner
from flask.cli import FlaskGroup


def make_bookshelf():
    app = Flask("bookshelf")

    @app.cli.command("seed")
    def seed():
        """Seed the catalogue."""
        click.echo(f"seeding {current_app.name}")

    return app


@click.group(cls=FlaskGroup, create_app=make_bookshelf, add_version_option=False, load_dotenv=False)
def bookshelf():
    """Management script for the Bookshelf."""


@bookshelf.command()
def about():
    """Prints a line; has no application context."""
    click.echo("Bookshelf management script")


runner = CliRunner()
result = runner.invoke(bookshelf, ["about"])
assert result.output == "Bookshelf management script\n"
result = runner.invoke(bookshelf, ["seed"])
assert result.output == "seeding bookshelf\n"
result = runner.invoke(bookshelf, ["--help"])
print("\n".join(line for line in result.output.splitlines() if line.startswith("  ") and line.split()[0] in {"about", "seed", "routes", "run", "shell"}))


@click.group()
def ops():
    """Umbrella script."""


ops.add_command(bookshelf, "shelf")  # FlaskGroup as a sub-command of another group
assert runner.invoke(ops, ["shelf", "seed"]).output == "seeding bookshelf\n"

  about    Prints a line; has no application context.
  routes   Show the routes for the app.
  run      Run a development server.

Two warnings. The group still accepts --app, so a user can point the script at another app by accident; pass add_default_commands=False and handle run yourself if that is a problem. And, as the official documentation says, an error in module-level code of a custom script breaks the reloader, because the reloader can no longer load the entry point; the plain flask command, which lives outside your code, does not have that problem, so it is recommended for most projects.

Testing Commands

app.test_cli_runner() returns a FlaskCliRunner, which extends Click’s CliRunner. Its invoke() runs a command in the same process, with captured output and no real terminal, and returns a Result. Without a cli argument it invokes app.cli, with a ScriptInfo that returns the app under test, so there is no --app and no import by name. Attributes of the result that tests use:

Attribute Content

exit_code

0 on success, 1 for ClickException, Abort or an exception, 2 for a usage error.

output

Standard output and standard error as the user would see them, interleaved.

stdout, stderr

The two streams separately (Click 8.2 and newer keep both).

exception

The exception raised by the command, or SystemExit; invoke(..., catch_exceptions=False) lets exceptions propagate instead, which gives better tracebacks in a failing test.

Source: Click: Testing Click Applications

Parameters worth knowing: args (a list or a string), input (text for prompts and confirmations), env (variables set during the call) and auto_envvar_prefix (see above). The built-in commands are reachable by passing a FlaskGroup as the first argument, as the routes example did. A pytest fixture keeps tests short:

Running Commands in Jobs and Containers

Custom commands are the supported way to run maintenance work (purging expired rows, importing a feed, sending a digest) because they use the exact configuration and extensions of the web application. A scheduler only has to run the command and look at its exit code:

flask --app bookshelf books purge --yes

Source: Flask: Command Line Interface

In a container, run the same command as a one-off process of the image, not by opening a shell in the running web container: docker run --rm bookshelf-image flask --app bookshelf books purge --yes, or a Kubernetes Job or CronJob whose container command is that line. The Docker and Kubernetes sections of this site explain images, jobs and cron schedules (Docker, Kubernetes). Use --yes (or an option that defaults to the safe answer) for any confirmation prompt, since a job has no terminal, and make sure the command exits non-zero on failure so that the scheduler can retry or alert. Database migrations are run the same way (flask --app bookshelf db upgrade) as a separate job before the new web pods start. Work that must run on request, retry and scale on its own belongs in a task queue rather than in the CLI; the Celery page of this section covers it.

IDE Run Configurations

An IDE has to start the flask command the same way a terminal does, so every configuration comes down to "run the module flask with these parameters, in this directory, with these environment variables".

PyCharm. PyCharm Professional has a Flask run configuration. Community Edition (and any command other than run) uses a generic Python configuration: choose Run, Edit Configurations, click + and pick Python, switch the Script path drop-down to Module name and enter flask, and put the command in Parameters, for example --app bookshelf run --debug. Copy the configuration and change the parameters to run shell, routes or your own commands. If the project is installed as a package in the virtual environment, uncheck the PYTHONPATH options so the run matches deployment.

Visual Studio Code. The Python debugger extension generates a "Flask" launch configuration that runs the module and sets the app in env. The --no-debugger and --no-reload flags matter: the IDE debugger and Werkzeug’s own debugger and reloader (which restarts the process and would detach the IDE’s debugger) are two separate mechanisms, and only one of them should be active.

Pitfalls and Security

  • The server and the debugger are for development. flask run --debug, app.run(debug=True) and --host 0.0.0.0 together put an interactive Python console on the network. Do not ship them in a Dockerfile, a systemd unit or a tutorial’s "deploy" step; run the production servers described in the deployment page of this section.

  • Secrets stay out of arguments and out of .flaskenv. Command-line arguments are visible to other users in the process list and are kept in the shell history; .flaskenv is committed. Use prompts, environment variables injected by the platform, or an uncommitted .env.

  • Destructive commands ask first. Use click.confirmation_option or click.confirm(abort=True), show the target (database name, environment) in the question, and provide --yes for jobs. Never hardcode a production URL in a command; read it from the configuration.

  • A shell or a command can reach everything the app can. Treat kubectl exec, docker exec and SSH access to the host as production access, and log who ran what.

  • --env-file and .env are code-adjacent. A .env file in a parent directory is picked up when you run flask from a sub-directory, which can load settings from an unrelated project. FLASK_SKIP_DOTENV=1 turns the lookup off.

  • Factories run at import time of the command. Anything the factory connects to (a database, a broker) is contacted by flask --help and flask routes too; keep slow or failing connections out of the factory (lazy connections are the norm for extensions).

Where the books and older tutorials are out of date:

  • Flask-Script and manage.py. Old books and tutorials add a manage.py with Manager(app) and @manager.command. Flask-Script was last released in 2017 and the book recipes that use it no longer apply; Click commands on app.cli replace it, and flask db (Flask-Migrate) replaced its db sub-commands.

  • export FLASK_APP=... is still honoured but the documented form is flask --app bookshelf run --debug, and a .flaskenv file removes the need for both.

  • FLASK_ENV=development in shells, .flaskenv files and Dockerfiles was removed in 2.3 and does nothing in 3.x. Use --debug or FLASK_DEBUG=1, and never leave debug on in a Dockerfile.

  • @with_appcontext on every command is no longer needed on app.cli and bp.cli commands (2.2); it is only for plain Click commands.

  • flask run --eager-loading / --lazy-loading were removed in 2.2.

  • create_app(script_info) factories, which were passed the ScriptInfo, stopped receiving it in 2.1.

  • CliRunner(mix_stderr=False) was removed in Click 8.2, see Testing Commands.

  • Typing db.create_all() in flask shell, as the SQL chapter of Full-Stack Flask and React does, still works but is a first-run shortcut; the same book’s flask db init, migrate and upgrade flow is current and is described in Database Migrations.

  • Starting the app with python app.py and app.run(debug=True) is still possible, but it skips the CLI, ignores FLASK_RUN_* variables and, in the Docker and deployment chapters of some books, ships the debugger to production.
