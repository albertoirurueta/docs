What’s Changed & Migration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Flask 3.1.3 (released 2026-02-18), Werkzeug 3.1.9 (2026-09-27), Jinja 3.1.6, Click 8.5.0, ItsDangerous 2.2.0, MarkupSafe 3.0.4 and Blinker 1.9.0, checked on 2026-10-07. Flask 3.2 has not been released: the official documentation still lists "Version 3.2.0 - Unreleased", so everything described below as "Flask 3.2" is upcoming and may change before the release. Every current-style Python example was executed on Python 3.13 with app.test_client(); deprecated or removed forms appear as the old way and are only run to show the error they raise. A large part of the material on the web, including the Flask books listed in the section bibliography, was written for Flask 1.x, 2.2 or 2.3. This page is the map between that material and today’s documentation: which release changed what, on which date, what the old code looked like, what to write now, and which page of this section covers it.

How to Read the Tables

Each release table lists the kind of change (added, changed, deprecated or removed), what changed, and the page of this section that covers it. Dates are the official release dates from the changelog. "Removed" means the name raises an error, or silently does nothing, in the versions you install today. Flask follows a deprecation policy: a name is deprecated in one feature release, keeps working with a DeprecationWarning, and is removed in a later major or minor release, which is why a lot of old code still works on 2.x and then stops on 2.3 or 3.0.

Two habits make upgrades safe. Pin Flask, Werkzeug and every extension to exact versions (or a lock file) and upgrade one major step at a time. Run the whole test suite with deprecation warnings turned into errors before each step, as the upgrade checklist below explains.

Which Release Changed What

Flask makes its breaking changes in two moments: 2.2 and 2.3 (2022 and 2023) removed or deprecated most of the idioms found in books, and 3.0 (2023-09-30) removed what had been deprecated since 2.3. The diagram shows an upgrade order that follows those moments.

flowchart LR A["Flask 1.x or 2.0 code"] --> B["2.1 to 2.2: fix warnings, adopt --app and --debug"] B --> C["2.3: remove FLASK_ENV, before_first_request, JSON_* keys, flask.Markup"] C --> D["3.0 and 3.1: drop the version attribute, add key rotation and limits"] D --> E["3.2 when released: contexts merged, redirect 303, Python 3.11"]

Werkzeug Highlights

Werkzeug does the HTTP work under Flask, so its changes show up in your application even when the Flask changelog is silent. These are the ones that matter for application code.

Version Date Change

2.1

2022-03-28

Request and response mixins merged into Request and Response; the test client returns TestResponse; the user agent parser was removed.

2.2

2022-07-23

A new, faster state-machine URL router. A custom converter that must match a / has to set part_isolating = False. MarkupSafe became a dependency.

2.3

2023-04-25

Request.get_json() raises 415 Unsupported Media Type instead of a generic 400 when Content-Type is not JSON. PBKDF2 work factor raised to 600,000 iterations. werkzeug.urls deprecated except uri_to_iri and iri_to_uri. A converter’s part_isolating defaults to False if its regex contains a /.

3.0

2023-09-30

generate_password_hash uses scrypt by default. Removal of everything deprecated in 2.3.

3.1

2024-10-31

Python 3.8 dropped. Request.max_form_memory_size defaults to 500 kB, so oversized non-file form fields raise RequestEntityTooLarge. OrderedMultiDict and ImmutableOrderedMultiDict deprecated. PBKDF2 work factor raised to 1,000,000 iterations. Partitioned (CHIPS) cookies supported. Behaviour of the cache_control properties adjusted. 421 MisdirectedRequest added.

3.1.8 and 3.1.9

2026-04-02 and 2026-09-27

Request.host returns an empty string for a missing or invalid Host; get_host validates the port range; x-www-form-urlencoded data is limited by max_content_length rather than max_form_memory_size; the int converter returns 404 instead of 500 for absurdly long values; a safe_join fix on Windows.

3.2

unreleased

Python 3.9 and 3.10 dropped; OrderedMultiDict removed; many data-structure helpers deprecated in favour of type annotations (ImmutableList, ImmutableDict, TypeConversionDict, and others); request properties are cached.

Source: Werkzeug: Changes

Code You Will Meet, and What to Write Now

The tables of this section map idioms you will find in books, tutorials and Stack Overflow answers to the current code. Each group is followed by examples that were executed. Where an old form is shown, the example runs it only to print the error it produces on Flask 3.1.

Running the App, the CLI and Packaging

Old idiom What happened Current

export FLASK_APP=app.py and flask run

Still works, but the documented form since 2.2 is the --app option. Without it, app.py or wsgi.py is discovered.

flask --app bookshelf run --debug

FLASK_ENV=development, ENV, app.env, .flaskenv with FLASK_ENV, Dockerfiles that set it

Deprecated in 2.2, removed in 2.3. There is no development/production switch any more.

--debug or FLASK_DEBUG; production never enables it

--eager-loading, --lazy-loading

Removed in 2.2. The app is eager loaded first, then lazily reloaded.

Nothing to pass

@with_appcontext on every app.cli command

Not needed since 2.2: an app context is already active.

@app.cli.command("seed") alone

python app.py with app.run(debug=True) inside Docker or production

The development server and the debugger are never for production: the interactive debugger can execute code.

Gunicorn or Waitress, see the Introduction & Architecture and the Docker and Kubernetes sections

python setup.py install, setup.py develop

Packaging moved to pyproject.toml (the official tutorial uses flit_core).

pip install -e .

virtualenvwrapper

Superseded by the standard library.

python -m venv .venv or uv venv

-e/--env-file, .env, .flaskenv

--env-file arrived in 2.2; in 3.1 -e overrides the default .env files.

flask --env-file .env.local --app bookshelf run

Local development uses the development server with debug mode, which is acceptable only on your own machine:

# Development only: the reloader and the interactive debugger must never face a network
flask --app bookshelf run --debug

# List the registered routes, including subdomain or host rules
flask --app bookshelf routes

# Load a specific dotenv file (it wins over the default .env and .flaskenv)
flask --env-file .env.local --app bookshelf run

Source: Flask: Command Line Interface

In production, a WSGI server imports the application factory. The command below runs it with Gunicorn behind a reverse proxy; debug mode is never enabled:

gunicorn --workers 4 --bind 127.0.0.1:8000 "bookshelf:create_app()"

Source: Flask: Deploying with Gunicorn

Names That No Longer Exist

The following example checks the removed names in one place. flask.__version__ still works on 3.1 (with a DeprecationWarning) but is removed in 3.2, so read the version from the package metadata.

import importlib.metadata as metadata
import warnings

import flask
from markupsafe import Markup, escape

print(metadata.version("flask"), metadata.version("werkzeug"))

with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always")
    legacy_version = flask.__version__
print([w.category.__name__ for w in caught])  # a DeprecationWarning on 3.1

for name in ("Markup", "escape", "_app_ctx_stack", "_request_ctx_stack"):
    print(name, hasattr(flask, name))  # all False since 3.0

print(escape("<script>"), Markup("<b>trusted</b>"))

app = flask.Flask(__name__)
for name in ("env", "before_first_request", "json_encoder", "json_decoder"):
    print(name, hasattr(app, name))  # all False since 2.3

Source: Flask: Changes, Version 3.0.0

Application Lifecycle

Old idiom What happened Current

@app.before_first_request

Deprecated 2.2, removed 2.3.

Do one-time setup in the application factory; see the Application Factory & Project Layout

_app_ctx_stack.top, _request_ctx_stack.top

Contexts use contextvars since 2.2; the stacks were removed in 3.0.

current_app, g, has_app_context(), and g attributes with a unique prefix for extension data

Registering routes, blueprints or error handlers after the first request

An error since 2.3.

Finish all setup in the factory before the app serves a request

flask.__version__

Deprecated in 3.0, removed in 3.2.

importlib.metadata.version("flask")

The application factory is where the old before_first_request code belongs. The example also shows the error that late setup raises:

from flask import Flask


def create_app() -> Flask:
    app = Flask(__name__)
    # One-time setup that older code placed in @app.before_first_request
    app.extensions["shelves"] = ["fiction", "science"]

    @app.get("/shelves")
    def shelves():
        return {"shelves": app.extensions["shelves"]}

    return app


app = create_app()
client = app.test_client()
print(client.get("/shelves").json)

try:
    app.add_url_rule("/late", "late", lambda: "too late")
except AssertionError as exc:
    print("AssertionError:", str(exc).splitlines()[0])

Source: Flask: Application Factories

Templates and Escaping

Old idiom What happened Current

from jinja2 import Markup, escape

Removed in Jinja 3.1.

from markupsafe import Markup, escape

from flask import Markup, escape

Deprecated in 2.3, removed in 3.0.

from markupsafe import Markup, escape

A Jinja date helper that builds <script>document.write(...)</script> with % formatting inside Markup

An XSS-prone pattern: the formatted string is marked safe without escaping its parts.

Format dates on the server with Babel, or emit <time datetime="..."> and let Intl.DateTimeFormat in the browser localize it; see the Jinja Templates and Internationalization with Flask-Babel pages

.svg templates rendered unescaped

Autoescape is on for .svg since 2.2.3.

Nothing to change; mark markup safe only when you fully trust it

Hand-written streaming responses for templates

stream_template and stream_template_string since 2.2.

stream_template("report.html", rows=rows)

The safe replacement for the date helper never builds HTML out of unescaped strings. Jinja escapes the value, and Markup.format escapes its arguments:

from flask import Flask, render_template_string
from markupsafe import Markup

app = Flask(__name__)


@app.template_filter()
def publication_date(value):
    # Markup.format escapes every argument, so the attribute and the text are safe
    return Markup('<time datetime="{iso}">{iso}</time>').format(iso=value.isoformat())


import datetime

with app.test_request_context():
    html = render_template_string(
        "{{ published | publication_date }} {{ title }}",
        published=datetime.date(2026, 10, 7),
        title='<script>alert("x")</script>',
    )
print(html)

Source: MarkupSafe documentation

Requests, Responses and JSON

Old idiom What happened Current

request.is_xhr

Removed in Werkzeug 1.0.

Check an explicit header, or better, use separate API routes returning JSON

request.get_json() on a non-JSON body

Werkzeug 2.3 returns 415 instead of a generic 400.

Send Content-Type: application/json; test with request.is_json

send_file(..., attachment_filename=, cache_timeout=, add_etags=), send_from_directory(filename=)

Sessions, Hashing and Secrets

Old claim or idiom What is true now Current

"The session cookie is encrypted"

The default session is signed with ItsDangerous, not encrypted: anyone holding the cookie can read it.

Keep secrets out of session; use server-side sessions (Flask-Session) when the data must stay private

One SECRET_KEY forever

SECRET_KEY_FALLBACKS (3.1) lets old keys unsign cookies during rotation.

Rotate keys: new key in SECRET_KEY, old keys in SECRET_KEY_FALLBACKS

SESSION_COOKIE_DOMAIN falls back to SERVER_NAME

It does not since 2.3: the cookie has no domain, so browsers use an exact host match.

Set the domain explicitly only when subdomains must share the cookie

Cookies without Vary

Vary: Cookie is set whenever the session is accessed (2.3.2, completed in 3.1.3).

Nothing to do; keep proxies and caches honouring Vary

SESSION_COOKIE_PARTITIONED, TRUSTED_HOSTS, MAX_FORM_MEMORY_SIZE, MAX_FORM_PARTS

New in 3.1.

Set them in config; see the Security Considerations page

generate_password_hash with PBKDF2 or an explicit method

Werkzeug 3.0 defaults to scrypt; PBKDF2 uses 1,000,000 iterations since 3.1.

Accept the default and verify with check_password_hash

A hard-coded placeholder string as the secret_key and cloud keys in source

Publishing them hands the keys to everyone.

Generate with secrets.token_hex() and read from config or the environment

The example below decodes a session cookie to show that it is only signed, then rotates the key with SECRET_KEY_FALLBACKS. Keys are generated at run time, never written in source:

import base64
import secrets

from flask import Flask, jsonify, session

old_key = secrets.token_hex()
new_key = secrets.token_hex()

app = Flask(__name__)
app.config["SECRET_KEY"] = old_key


@app.get("/login")
def login():
    session["user_id"] = 42
    return "ok"


@app.get("/me")
def me():
    return jsonify(user=session.get("user_id"))


client = app.test_client()
response = client.get("/login")
cookie = response.headers["Set-Cookie"].split(";")[0].split("=", 1)[1]
payload = cookie.split(".")[0]
payload += "=" * (-len(payload) % 4)
print(base64.urlsafe_b64decode(payload))  # readable: signed, not encrypted
print(response.headers.get("Vary"))

returning = app.test_client()
returning.set_cookie("session", cookie)
app.config["SECRET_KEY"] = new_key  # rotated: the old cookie no longer verifies
print(returning.get("/me").json)
app.config["SECRET_KEY_FALLBACKS"] = [old_key]  # the old key may still unsign
print(returning.get("/me").json)

Chapter 6 of the Manning book on microservice APIs applies flask-smorest and marshmallow to a Flask API. Several of its statements are wrong or out of date. The table lists them; the example after it proves the corrections.

Book statement or idiom Correct behaviour Current

Meta.unknown = EXCLUDE rejects unknown fields

The opposite: EXCLUDE silently drops them, and RAISE (the default) rejects them with a validation error.

Choose RAISE for strict contracts

@blp.response(...) stacked above @blp.route(...)

route must be the outermost decorator.

@blp.route(...) first, then @blp.arguments, then @blp.response

@blp.response(Schema) with the schema as the first positional argument

Since flask-smorest 0.25 the first positional argument is the status code.

@blp.response(201, Schema)

Raising marshmallow’s ValidationError inside a view

It produces a 500, not a formatted 422: validation errors are converted only by @blp.arguments.

Let @blp.arguments validate, or call abort(422, ...)

Possible, but only a workaround.

import threading

from celery import Celery, Task
from flask import Flask, current_app


def celery_init_app(app: Flask) -> Celery:
    class FlaskTask(Task):
        def __call__(self, *args, **kwargs):
            with app.app_context():
                return self.run(*args, **kwargs)

    celery_app = Celery(app.name, task_cls=FlaskTask)
    celery_app.config_from_object(app.config["CELERY"])
    celery_app.set_default()
    app.extensions["celery"] = celery_app
    return celery_app


app = Flask("digest")
app.config.from_mapping(
    CELERY=dict(broker_url="memory://", result_backend="cache+memory://", task_always_eager=True)
)
celery_app = celery_init_app(app)


@celery_app.task
def app_name():
    return current_app.name


print(app_name.delay().get())

results = []


def send_digest(flask_app: Flask, address: str) -> None:
    with flask_app.app_context():  # without this, current_app is unavailable in the thread
        results.append((current_app.name, address))


worker = threading.Thread(target=send_digest, args=(app, "reader@example.com"))
worker.start()
worker.join()
print(results)

Upgrading from 1.x or 2.x to 3.x

Follow the steps in order. Each step is small enough to keep the test suite green.

  • Read the changelog entries between your version and the target and list the removals that apply to your code.

  • Pin every dependency, then upgrade Flask and Werkzeug together with the extensions that support the target.

  • Raise the Python version first: Flask 2.3 needs 3.8, 3.1 needs 3.9, and 3.2 will need 3.11.

  • Run the tests with DeprecationWarning turned into an error and fix each warning before moving on.

  • Replace FLASK_ENV, ENV and app.env with --debug (development) or nothing (production).

  • Move before_first_request code into the application factory and finish all setup before the first request.

  • Replace flask.Markup and flask.escape with markupsafe, and json_encoder settings with a JSON provider.

  • Replace Model.query with db.session.get, db.get_or_404, db.select and db.paginate (keyword arguments).

  • Replace flask.__version__ with importlib.metadata.version("flask").

  • Set SECRET_KEY from the environment and plan key rotation with SECRET_KEY_FALLBACKS.

  • Review TRUSTED_HOSTS, MAX_CONTENT_LENGTH, MAX_FORM_MEMORY_SIZE and MAX_FORM_PARTS for the limits you need.

  • Update extension calls (@jwt_required(), locale_selector=, StringField, SimpleCache).

  • Build and deploy the container with a production WSGI server and re-run the smoke tests.

Turning warnings into errors uses the pytest configuration, so the next step is a test run that fails on any deprecated call:

[tool.pytest.ini_options]
filterwarnings = [
    "error::DeprecationWarning",
]

Coming in Flask 3.2

Flask 3.2.0 is unreleased: its changelog is a work in progress. The list below is what the development docs say today. You can already write code that works on both 3.1 and 3.2.

  • Contexts merge. RequestContext becomes a deprecated alias of AppContext, and an app context that was already pushed is no longer reused when a request is dispatched. Code that pushes an app context and then expects a request to join it must be re-checked; code that subclasses Flask and overrides dispatch methods gets a deprecation warning for the old signatures. See the Application & Request Lifecycle page.

  • redirect() defaults to 303. The client always switches to GET, which keeps the behaviour of both GET and POST redirects and is correct for HTMX. Pass code=303 today to get the future behaviour.

  • All teardown callbacks run. A teardown that raises no longer prevents the others from running. Make each teardown handle its own errors. should_ignore_error is deprecated.

  • Decorators without parentheses. template_filter, template_test and template_global can be used bare. The form with parentheses keeps working.

  • provide_automatic_options=True. A view can re-enable OPTIONS handling when the config turned it off; today only disabling works.

  • app.query. A decorator for the HTTP QUERY method.

  • Smaller items. __version__ is removed, Python 3.9 and 3.10 are dropped, select_jinja_autoescape is case-insensitive, and IPv6 addresses with a port are parsed correctly.

The example runs on 3.1 and behaves the same on 3.2. It uses an explicit 303, the parenthesised template decorator, a QUERY route declared through methods, and teardown handlers that handle their own errors:

from flask import Flask, redirect, render_template_string

app = Flask(__name__)
app.config["PROVIDE_AUTOMATIC_OPTIONS"] = False


@app.route("/search", methods=["QUERY"])  # on 3.2 you can use @app.query("/search")
def search():
    return "results"


@app.get("/old")
def old():
    return "x"


@app.route("/enabled", provide_automatic_options=True)  # re-enables OPTIONS only on 3.2
def enabled():
    return "y"


@app.template_filter()  # parentheses work on 3.1 and 3.2
def shout(value):
    return value.upper()


calls = []


@app.teardown_appcontext
def close_one(error):
    calls.append("one")
    try:
        raise RuntimeError("handled inside the teardown")
    except RuntimeError:
        calls.append("one handled")


@app.teardown_appcontext
def close_two(error):
    calls.append("two")


@app.get("/go")
def go():
    return redirect("/old", code=303)  # explicit: the default on 3.2


client = app.test_client()
print(client.open("/search", method="QUERY").status_code)
print(client.options("/old").status_code, client.options("/enabled").status_code)  # 405 405 on 3.1; 405 200 on 3.2
with app.app_context():
    print(render_template_string("{{ 'ok' | shout }}"))
response = client.get("/go")
print(response.status_code, calls[-3:])
print(hasattr(app, "query"))  # False on 3.1.3, True once 3.2 is released

Source: Flask: Changes (development version)

Moving Away from Flask

Two migrations are common: to Quart when a Flask code base should become asynchronous with the fewest edits, and to FastAPI when typed models and generated OpenAPI documents matter more than Flask’s flexibility.

Flask to Quart

Quart implements the Flask API on ASGI, and Flask 3.0 split Flask and Blueprint into Sans-IO bases so the two share code. Most migrations change imports, make views async def and add await where the Quart API is asynchronous. Quart 0.23.1 needs Python 3.13 or newer. Flask extensions are not automatically compatible, because many call blocking code; check each one. The Quart section of the Async, gevent & Quart page compares the options, including when to switch.

import asyncio

from flask import Flask, jsonify, request
from quart import Quart
from quart import jsonify as quart_jsonify
from quart import request as quart_request

flask_app = Flask(__name__)


@flask_app.post("/books")
def create_book():
    data = request.get_json()
    return jsonify(title=data["title"]), 201


quart_app = Quart(__name__)


@quart_app.post("/books")
async def create_book_async():
    data = await quart_request.get_json()  # request data is awaited in Quart
    return quart_jsonify(title=data["title"]), 201


async def main():
    response = await quart_app.test_client().post("/books", json={"title": "Dune"})
    print(response.status_code, await response.get_json())


print(flask_app.test_client().post("/books", json={"title": "Dune"}).status_code)
asyncio.run(main())

Source: Quart: Migrating from Flask

Flask to FastAPI

A gradual migration mounts the existing Flask application inside a FastAPI application with a WSGI adapter, then moves routes to FastAPI one at a time. The FastAPI section explains the mount, the path prefix and the pitfalls in Embedding Flask or Django with WSGIMiddleware (on the Sub-applications, WSGI & GraphQL page); the FastAPI introduction compares both frameworks, and the FastAPI changes and migration page covers FastAPI’s own moving parts. The example mounts a Flask app under /legacy with a2wsgi and serves a new typed route next to it. It needs fastapi, a2wsgi and httpx, which are not installed with Flask:

from a2wsgi import WSGIMiddleware
from fastapi import FastAPI
from fastapi.testclient import TestClient
from flask import Flask, jsonify, request
from pydantic import BaseModel

flask_app = Flask(__name__)


@flask_app.post("/books")
def create_book():
    return jsonify(title=request.get_json()["title"]), 201


class BookIn(BaseModel):
    title: str


api = FastAPI()


@api.post("/v2/books", status_code=201)
async def create_book_typed(book: BookIn):
    return {"title": book.title}


api.mount("/legacy", WSGIMiddleware(flask_app))  # the Flask app keeps working under /legacy

client = TestClient(api)
print(client.post("/v2/books", json={"title": "Dune"}).json())
print(client.post("/legacy/books", json={"title": "Dune"}).status_code)
