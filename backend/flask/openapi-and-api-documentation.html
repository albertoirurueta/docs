OpenAPI & API Documentation

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Flask 3.1.3 (released 2026-02-19), Werkzeug 3.1.9, flask-smorest 0.47.0 (2026-03-22), apispec 6.10.0, marshmallow 4.3.1, APIFlask 3.1.2 (2026-09-12) and Python 3.13, checked on 2026-10-07; every Python example was executed with those versions through Flask’s test client. Flask 3.2 is not released yet and does not change anything described here. An API that nobody can discover is an API nobody can use, and an API whose documentation is written by hand drifts away from the code within weeks. The cure is a machine-readable description, an OpenAPI document, that is the single source of truth: documentation pages, interactive consoles, client libraries, mocks, gateways and contract tests are all generated from it. The page covers what an OpenAPI document contains, the two ways of keeping it truthful (code-first, where the code produces the document, and design-first, where the document produces or constrains the code), how Flask does each, and how to publish, test and consume the result. It extends the Bookshelf API of the previous pages. Flask itself has no OpenAPI support: everything here comes from extensions, and the page says which library does which job.

Why Document an API with OpenAPI

Flask validates nothing and documents nothing by itself: a view receives a request and returns whatever it likes (see Request Data and Responses & JSON). That freedom is exactly why an API needs a contract. The OpenAPI Specification (OAS) is a language-neutral way of writing that contract as a JSON or YAML document: the paths, the operations on each path, the parameters, the request bodies, the responses, the data types and the security requirements. Because it is machine-readable, the same document feeds many tools.

Consumer of the document What it does with it

Documentation renderers (Swagger UI, ReDoc, RapiDoc)

Render interactive reference pages, with a "try it out" console in the case of Swagger UI and RapiDoc

Client generators

Produce typed client libraries and SDKs for Python, TypeScript and many other languages

Gateways, proxies and mock servers

Route, authenticate, rate-limit or simulate the API from the same description

Contract and property-based tests

Generate requests from the schemas and check every response against them; see the page on API contract and property-based testing in this section

Linters and governance tools

Enforce naming, error-format and versioning rules across many services

People

Review the API shape in a pull request before any code exists (documentation-driven or API-first development)

The API-first idea, argued at length in Microservice APIs (Manning), is that the interface between services is the part that is expensive to change, so it deserves a document that is reviewed, versioned and agreed before the implementation. Whether the document is written first or generated, the rule stays the same: the running service and the published document must never disagree.

Both are only as good as the checks around them, which is why the page ends with contract validation.

Anatomy of an OpenAPI Document

An OpenAPI document is a single JSON or YAML object. The OpenAPI Specification 3.1 is aligned with JSON Schema draft 2020-12, so the objects that describe data (schema) are ordinary JSON Schema, with a few OpenAPI keywords added.

Top-level field Meaning

openapi

the version of the specification the document follows, for example 3.1.0 (required)

info

title, version of the API itself (not of the specification), description, contact, license (required)

servers

the base URLs where the API is available

paths

every URL template, each with its operations (get, post, put, patch, delete and so on)

components

reusable objects referenced with $ref: schemas, parameters, requestBodies, responses, headers, examples, securitySchemes, links, callbacks

security

the security requirements that apply to every operation unless an operation overrides them

tags, externalDocs

grouping and extra documentation

webhooks

incoming calls the API may receive (new in 3.1)

A document needs openapi and info, and at least one of paths, components or webhooks. Inside paths, each operation lists its parameters (each with a name, a location in in, either path, query, header or cookie, and a schema), an optional requestBody keyed by media type, and responses keyed by status code (or default). Every response has a mandatory description and optionally content and headers. The reusable parts live in components and are referenced with $ref, so that the same Book schema is written once and used by the request of POST /books and the response of GET /books/{bookId}. Security is declared once under components.securitySchemes (types apiKey, http, oauth2, openIdConnect and mutualTLS) and applied with security, which is how Swagger UI knows to show an "Authorize" button.

Which OpenAPI Version

OpenAPI 3.0 and 3.1 differ in ways that show up in generated documents.

Topic OpenAPI 3.0.x OpenAPI 3.1.x

Schema dialect

a modified subset of JSON Schema draft 4/5 (nullable, exclusiveMinimum as a boolean)

JSON Schema draft 2020-12 in full (type: [string, "null"], numeric exclusiveMinimum, $ref with sibling keywords)

Webhooks

not available

top-level webhooks

Root requirements

paths required

one of paths, components or webhooks

The OpenAPI Initiative has published later versions as well (the specification site lists 3.2.1, dated 2026-09-10, as the latest). The Flask libraries on this page generate documents that follow the 3.0 and 3.1 shapes: APIFlask defaults to 3.1.0 and flask-openapi3 uses 3.1.0, while flask-smorest has no default and requires you to set OPENAPI_VERSION (its quickstart uses 3.0.2). apispec, the library underneath flask-smorest, accepts any version string without checking it, so the value you choose is a promise you must keep: set 3.1.0 and let tools validate the result. The book Microservice APIs configures 3.0.3; 3.1 is the better target for new work because its schemas are plain JSON Schema, which every modern validator, test generator and code generator understands.

Code-First with flask-smorest

flask-smorest (installed with pip install flask-smorest) combines three libraries: marshmallow describes the data, webargs parses requests into those schemas, and apispec builds the OpenAPI document from everything it sees. The Flask part is deliberately small: an Api object attached to the application, a Blueprint subclass whose decorators carry the documentation, and the standard Flask MethodView from Class-Based Views to group the methods of a resource.

The Minimal API

Three settings are required, and Api raises MissingAPIParameterError when one is absent: API_TITLE, API_VERSION and OPENAPI_VERSION. Everything else is optional.

from flask import Flask
from flask.views import MethodView
import marshmallow as ma
from flask_smorest import Api, Blueprint, abort


class BookSchema(ma.Schema):
    id = ma.fields.Int(dump_only=True)
    title = ma.fields.Str(required=True, validate=ma.validate.Length(min=1, max=200))
    year = ma.fields.Int(validate=ma.validate.Range(min=1450))


blp = Blueprint("books", __name__, url_prefix="/books", description="Operations on books")
BOOKS: dict[int, dict] = {}


@blp.route("/")
class Books(MethodView):
    @blp.response(200, BookSchema(many=True))
    def get(self):
        """List the books"""
        return list(BOOKS.values())

    @blp.arguments(BookSchema)
    @blp.response(201, BookSchema)
    def post(self, data):
        """Create a book"""
        data["id"] = len(BOOKS) + 1
        BOOKS[data["id"]] = data
        return data


@blp.route("/<int:book_id>")
class Book(MethodView):
    @blp.response(200, BookSchema)
    def get(self, book_id):
        """Fetch one book"""
        try:
            return BOOKS[book_id]
        except KeyError:
            abort(404, message="No such book")


def create_app() -> Flask:
    app = Flask(__name__)
    app.config.update(
        API_TITLE="Bookshelf API",
        API_VERSION="v1",
        OPENAPI_VERSION="3.1.0",
    )
    api = Api(app)
    api.register_blueprint(blp)
    return app


app = create_app()
client = app.test_client()
print(client.post("/books/", json={"title": "Dune", "year": 1965}).status_code)
print(client.get("/books/1").json)
print(client.get("/books/9").json)
print(client.post("/books/", json={"year": 1965}).json)

What happened underneath:

  • Api(app) read the three settings, built an apispec.APISpec, registered a default error handler for HTTPException and added the flask openapi command group to app.cli.

  • Blueprint is a subclass of flask.Blueprint; blp.route registers the view like Flask does and also stores the view in the documentation. Because it is a real Flask blueprint, everything in Blueprints (prefixes, error handlers, hooks) still applies.

  • api.register_blueprint(blp) registers it in the application and generates the documentation of its views from the decorators and docstrings. It must be called after Api is attached to the app; use Api().init_app(app) in an application factory, as in Application Factory & Project Layout.

  • A blueprint registered with plain app.register_blueprint(blp) works as a Flask blueprint but never appears in the document.

The Decorators and Their Order

The decorators belong to the Blueprint; each one both changes the runtime behaviour of the view and contributes to the document.

Decorator Runtime effect Documentation effect

@blp.route(rule, parameters=None, tags=None, **options)

registers the view (a function or a MethodView class) under rule

creates the path item; parameters documents path parameters declared in rule or in url_prefix

@blp.arguments(schema, location="json", required=True, description=None, example=None, examples=None, content_type=None)

parses and validates the request with the schema (through webargs) and passes the result as an extra positional argument; on failure answers 422 with the errors

requestBody for json, form and files; for any other location one entry per schema field in parameters

@blp.response(status_code, schema=None, content_type=None, description=None, example=None, examples=None, headers=None)

serializes the returned object with the schema; the status code is used unless the view returns a tuple with another

the success response, with the schema referenced from components.schemas

@blp.alt_response(status_code, response=None, schema=None, description=None, example=None, examples=None, headers=None, success=False)

nothing by default: it only documents a response the view may produce

an additional response (typically an error) for the operation; the parameter success=True marks it as part of the normal flow so pagination and ETag also apply to it

@blp.paginate(pager=None, page=None, page_size=None, max_page_size=None)

adds page and page_size query parameters and the X-Pagination header

documents the two parameters and the header

@blp.doc(**kwargs)

nothing

merges any keyword (summary, description, security, deprecated, operationId, tags, responses…​) into the operation

Three rules about the order, all of which the book Microservice APIs gets wrong or leaves out, decide whether the document and the behaviour are correct.

  1. @blp.route must be the outermost decorator when decorating a function. It registers whatever function it receives, so a @blp.response written above it is applied to a function that is no longer the one Flask calls. With a MethodView class the problem does not exist, because @blp.route decorates the class and the other decorators sit on the methods.

  2. Under @blp.route, put @blp.arguments first (outermost) and @blp.response below it; @blp.paginate goes below @blp.response. The view’s own signature mirrors that order: the parsed arguments come first, then pagination_parameters when pagination is handled in the view.

  3. The first positional argument of @blp.response is the status code and the schema is the second. Writing @blp.response(BookSchema) fails at import time with a TypeError, because a schema class is not a status code. The status_code-first signature has existed since flask-smorest 0.29.0 (2021-02-13); older tutorials and the book use the previous form, with the schema first.

The wrong order is not just a documentation bug, it is a data leak. The view below returns an attribute that is not in the schema; with the right order the response schema filters it out, with the wrong order the decorator is bypassed and the attribute is sent (and the success response is missing from the document).

import marshmallow as ma
from flask import Flask
from flask_smorest import Api, Blueprint


class PublicBook(ma.Schema):
    title = ma.fields.Str()


app = Flask(__name__)
app.config.update(API_TITLE="Order demo", API_VERSION="v1", OPENAPI_VERSION="3.1.0")
api = Api(app)
blp = Blueprint("order", __name__, url_prefix="/order")


@blp.response(200, PublicBook)
@blp.route("/wrong")
def wrong():
    return {"title": "Dune", "internal_note": "do not publish"}


@blp.route("/right")
@blp.response(200, PublicBook)
def right():
    return {"title": "Dune", "internal_note": "do not publish"}


api.register_blueprint(blp)
c = app.test_client()
print(c.get("/order/wrong").json)
print(c.get("/order/right").json)
spec = api.spec.to_dict()
print("200 documented for wrong:", "200" in spec["paths"]["/order/wrong"]["get"]["responses"])
print("200 documented for right:", "200" in spec["paths"]["/order/right"]["get"]["responses"])

Describing Data with marshmallow Schemas

A marshmallow Schema does three jobs at once: it validates and deserializes input (load), it serializes output (dump), and, through apispec, it becomes an entry under components.schemas of the document. The vocabulary that matters for an API is small.

Feature Effect on behaviour and on the document

fields.Str(), Int(), Float(), Bool(), Date(), DateTime(), UUID(), List(), Dict()

types of the properties; DateTime becomes format: date-time, UUID becomes format: uuid

required=True

input without the field is rejected; the field is listed under required

dump_only=True / load_only=True

read-only fields (id, timestamps) are ignored on input and marked readOnly; write-only fields (passwords) never appear in output and are marked writeOnly

load_default= / dump_default=

value used when the field is missing on input / output; in marshmallow 3.13 and later these replace the old missing= and default= keywords, and load_default=list is the way to default to a fresh list

validate= (Length, Range, OneOf, Regexp, custom callables)

rejects the input with a 422; most standard validators become minLength, maxLength, minimum, maximum, enum and pattern

@validates("field"), @validates_schema

custom field-level and cross-field validation; custom validators are not visible in the document, so describe them in prose

fields.Nested(OtherSchema)

a nested object, rendered as a $ref to the other schema; many=True makes an array

Meta.unknown

what to do with fields the input contains but the schema does not declare; see below

Meta.exclude, only=, partial=

subset or partial variants, which become separate component names, so use them sparingly

schema inheritance

a subclass inherits the parent’s fields; a subclass is a distinct component, so put the common fields in a base class and keep Meta options in it

The Unknown-Field Policy

Meta.unknown takes one of three values, and the two that matter are the opposite of what Microservice APIs states.

Value Behaviour on load Effect on the document

RAISE (the default)

unknown fields are rejected: the request fails with a 422 and Unknown field. for each one

additionalProperties: false

EXCLUDE

unknown fields are silently dropped: the request succeeds and the view never sees them

no additionalProperties keyword

INCLUDE

unknown fields are kept in the result

no additionalProperties keyword

EXCLUDE therefore means tolerant (drop what you do not know), and RAISE strict. The choice is a design decision: strict input catches misspelt optional fields (a client that sends titel hears about it), tolerant input lets old servers accept newer clients. Note that the default for output schemas is irrelevant at runtime, because dumping ignores attributes the schema does not declare, as the leak demonstration above showed.

import json
import marshmallow as ma


class Base(ma.Schema):
    """Common configuration for every schema of the API."""

    class Meta:
        unknown = ma.RAISE


class AuthorSchema(Base):
    name = ma.fields.Str(required=True)


class LenientAuthor(AuthorSchema):
    class Meta:
        unknown = ma.EXCLUDE


class BookInSchema(Base):
    title = ma.fields.Str(required=True)
    authors = ma.fields.List(ma.fields.Nested(LenientAuthor), load_default=list)

    @ma.validates("title")
    def no_padding(self, value, **kwargs):
        if value != value.strip():
            raise ma.ValidationError("must not start or end with spaces")


try:
    BookInSchema().load({"title": "Dune", "isbn": "x"})
except ma.ValidationError as err:
    print("RAISE:", err.messages)
print("EXCLUDE:", BookInSchema().load({"title": "Dune", "authors": [{"name": "Herbert", "born": 1920}]}))
try:
    BookInSchema().load({"title": " Dune"})
except ma.ValidationError as err:
    print("validator:", err.messages)

Parsing Query Strings, Forms and Headers

@blp.arguments(schema, location="json") is not limited to bodies. The location argument chooses where webargs looks for the data: json (the default), query, form, files, headers, cookies, among others webargs supports. For json, form and files the schema becomes the requestBody and required and description apply to it; for the other locations each field of the schema becomes one entry of parameters with its own required flag, and the required argument of the decorator has no effect. That is the part worth remembering when a query parameter looks optional in the document although you passed required=True.

Query schemas usually want unknown = EXCLUDE, because browsers, proxies and trackers add parameters (utm_source, _ cache busters) that you do not want to turn into a 422.

Responses, Errors and Status Codes

@blp.response(status_code, schema) describes the success response. A few points about it are easy to miss.

  • If a view returns a list, the schema must be instantiated with many=True (BookSchema(many=True)), otherwise the list is serialized as if it were a single object.

  • The decorator serializes with the schema (dump) but does not validate the data: a view that returns {"title": 5} for a Str field sends {"title": "5"} with status 200. Contract problems in outgoing data are caught by tests that compare responses to the document (see Design-First with a Hand-Written Document), not by the decorator.

  • A view may return a tuple, such as (body, 201, headers). A status code in the tuple overrides the one in the decorator, and the document keeps showing the decorator’s value, which is why the documentation of flask-smorest advises against it.

  • A single @blp.response is allowed per view. Everything else the view may answer is documented with stacked @blp.alt_response decorators. With only a status code, alt_response documents that status with its standard HTTP phrase as description; with response="NOT_FOUND" (the name of an http.HTTPStatus member) it references the shared component #/components/responses/NOT_FOUND, created on demand with the error schema, so every operation that uses it shares one definition.

Errors have a default format. abort(status, message=..., errors=..., headers=...) is a republication of webargs' abort that stores its keyword arguments so the registered handler can render them as {"code": ..., "status": ..., "message": ..., "errors": ...}. Validation failures raised by @blp.arguments are the same kind of HTTPException, with the field errors under errors keyed by location. The default answer is documented once as components.schemas.Error and used for every operation as the default response, plus a 422 response for operations with @blp.arguments.

Problem Details Instead of the Default Format

RFC 9457 (Problem Details for HTTP APIs, which obsoletes RFC 7807) defines the application/problem+json format that many clients and gateways understand; the books on this page predate it or ignore it. The default flask-smorest format is a custom shape, but the error handler and the error schema are both attributes of Api and can be replaced by subclassing: ERROR_SCHEMA is the schema documented in the spec and handle_http_exception builds the response.

import marshmallow as ma
from flask import Flask, make_response
from flask.views import MethodView
from flask_smorest import Api, Blueprint, abort


class Problem(ma.Schema):
    type = ma.fields.Str(dump_default="about:blank")
    title = ma.fields.Str()
    status = ma.fields.Int()
    detail = ma.fields.Str()
    errors = ma.fields.Dict()


class ProblemApi(Api):
    ERROR_SCHEMA = Problem

    def handle_http_exception(self, error):
        payload, status, headers = super().handle_http_exception(error)
        body = {"title": payload["status"], "status": status}
        if "message" in payload:
            body["detail"] = payload["message"]
        if "errors" in payload:
            body["errors"] = payload["errors"]
        response = make_response(Problem().dumps(body), status)
        response.headers["Content-Type"] = "application/problem+json"
        response.headers.update(headers)
        return response


class Note(ma.Schema):
    n = ma.fields.Int(required=True)


app = Flask(__name__)
app.config.update(API_TITLE="Problem demo", API_VERSION="v1", OPENAPI_VERSION="3.1.0")
api = ProblemApi(app)

Pagination

@blp.paginate() adds page and page_size to the query parameters and the metadata to the response in an X-Pagination header (total, total_pages, page, first_page, last_page, and previous_page and next_page when they exist). It has two modes. In the first the view receives a pagination_parameters object, slices its own data and sets item_count. In the second paginate receives a pager class (a subclass of flask_smorest.Page, such as one wrapping a SQLAlchemy query) and the view just returns the whole collection or a lazy cursor.

A request for a larger page_size than allowed is rejected by the generated parameter schema (maximum: 100), which protects the database from page_size=1000000.

import marshmallow as ma
from flask import Flask
from flask.views import MethodView
from flask_smorest import Api, Blueprint, Page

    n = ma.fields.Int()

class ListPage(Page):
    @property
    def item_count(self):
        return len(self.collection)


@blp.route("/in-view")
class InView(MethodView):
    @blp.response(200, ItemSchema(many=True))
    @blp.paginate()
    def get(self, pagination_parameters):
        pagination_parameters.item_count = len(ITEMS)
        return ITEMS[pagination_parameters.first_item : pagination_parameters.last_item + 1]


@blp.route("/with-pager")
class WithPager(MethodView):
    @blp.response(200, ItemSchema(many=True))
    @blp.paginate(ListPage, page_size=5, max_page_size=20)
    def get(self):
        return ITEMS

Enriching the Generated Document

The decorators produce structure; people read the prose. Four sources add it.

  • Docstrings. The first line of a view’s docstring becomes the operation summary and the rest, until a line containing only ---, the description. Anything after the --- is not published, which makes the delimiter a place for internal notes.

  • @blp.doc(...) merges arbitrary keywords into the operation: summary, description, tags, deprecated=True, operationId, security=[...], externalDocs, servers.

  • Field metadata: ma.fields.Str(metadata={"description": "...", "example": "..."}) documents a property.

  • API_SPEC_OPTIONS and api.spec.components: root attributes (servers, info.description, info.contact…​) and reusable components registered with apispec’s Components API (security_scheme, parameter, response…​).

Security deserves its own mention. The document is where an operation says "this requires a bearer token", but flask-smorest only describes security, it does not enforce it: the view or a decorator from Hooks & View Decorators still has to authenticate the request, as shown in Authorization & Roles. A securitySchemes entry plus a security requirement makes Swagger UI and generated clients send the credential. The page on JWT and API authentication in this section builds the matching implementation.

Publishing documentation raises operational questions that a decorator cannot answer.

  • Third-party scripts. The pages above execute JavaScript from cdn.jsdelivr.net or unpkg.com, unpinned in the example (swagger-ui-dist with no version resolves to the latest release). That is convenient in development. In production pin an exact version in the URL, or download the distribution into the application’s static folder (see Static Files & Assets) and point the URL setting at it; this also keeps a strict Content-Security-Policy workable, as in Security Considerations.

  • Exposure. The document and the UI list every endpoint, including ones meant for internal clients. Decide whether they are public. A common pattern is to set OPENAPI_URL_PREFIX only when DEBUG is on or from an environment variable, so production serves nothing (None disables the whole blueprint), or to put the prefix behind the same authentication as the API.

  • Try it out. Swagger UI sends real requests with real credentials from the visitor’s browser. Point its servers entry at the right environment, and keep the CORS policy of the API consistent with where the UI is hosted; the page on single-page apps and CORS in this section and the site’s own web/cors page explain preflight requests.

  • Hosting the files elsewhere. The document is just a file: publishing the output of flask openapi write to a documentation site or an API portal avoids exposing the live service at all.

The OpenAPI Command-Line Group

Api registers a Click group named openapi (see the page on the Flask CLI). flask --app bookshelf openapi print writes the document to standard output and flask --app bookshelf openapi write openapi.json writes it to a file; both accept --format json|yaml (YAML needs PyYAML installed) and --config-prefix for applications with several Api objects; openapi list-config-prefixes shows the prefixes.

flask --app bookshelf openapi print --format yaml
flask --app bookshelf openapi write openapi.json
git diff --exit-code openapi.json   # fail the CI job when the committed spec is stale

Committing the generated file and failing the build when git diff is not empty turns every API change into a visible diff in the pull request, which is how code-first projects get the review step that design-first projects get from writing the document by hand. The same generated file is the input to linters, generators and contract tests, so no server has to be running.

Design-First with a Hand-Written Document

In design-first the document is the product of a design conversation. The team writes the YAML (an editor with an OpenAPI plug-in, or a design tool), reviews it, publishes it to front-end and partner teams, and only then implements. The risk is drift, so the workflow needs automation at three points: the document must be valid, the application must serve or reference it, and the implementation must be checked against it.

Validate the document. openapi-spec-validator (pip install openapi-spec-validator) checks a document against the specification schema for the version it declares, including $ref resolution, and raises on the first problem.

Serve it. Nothing in Flask requires a framework: a view that returns the parsed document is enough, and any of the UIs from the previous section can be pointed at it. With flask-smorest, set OPENAPI_URL_PREFIX to None (so the generated document is not published) and serve your file from your own route. The book Microservice APIs replaces the served document by monkeypatching APISpec.to_dict; that works only as a workaround, because it ties the application to a private detail of the library and defeats the point of the generator. If you want the spec to drive the application rather than sit beside it, Connexion maps each operationId to a Python function and validates requests and responses against the document at run time.

Check the implementation. The simplest contract test needs only jsonschema: for every operation, call the endpoint with the Flask test client and validate the response body against the schema the document declares for that status code. Components are referenced as #/components/schemas/..., so the validator is given a root object that carries both the schema and components. Dedicated tools do the same at scale: Schemathesis generates the requests from the document and fuzzes the API, and openapi-core validates requests and responses with Flask integration (both discussed in the page on API contract and property-based testing in this section; Dredd, used in the book, is archived).

import yaml

def assert_conforms(path, method, status, body):
    """Validate a response body against the schema the document declares."""
    response_doc = SPEC["paths"][path][method]["responses"][str(status)]
    schema = response_doc["content"]["application/json"]["schema"]
    root = {**schema, "components": SPEC["components"]}
    problems = [e.message for e in Draft202012Validator(root).iter_errors(body)]
    assert not problems, problems

Generating Clients from the Document

Because the document is the contract, consumers can generate their side of it. Quality in equals quality out: give every operation a stable operationId (flask-smorest does not invent one, so set it with @blp.doc(operationId=...); APIFlask has the AUTO_OPERATION_ID setting) because generators use it as the method name, and give every schema a meaningful name because they use it as the class name.

# Python client, typed, from a file or a URL (OpenAPI 3.0 and 3.1)
pipx install openapi-python-client --include-deps
openapi-python-client generate --path openapi.json

# Many languages through the Java-based OpenAPI Generator
npm install @openapitools/openapi-generator-cli -g
openapi-generator-cli generate -i openapi.json -g typescript-fetch -o ./client

Review generated clients like any dependency: regenerate them in CI from the committed document so that a breaking API change fails somewhere visible, and treat the generated code as build output, not as hand-edited source.

Source: openapi-python-client

Pitfalls and Security Notes

Pitfall What to do

@blp.response above @blp.route

the response schema is bypassed (unfiltered data) and the operation has no documented success response; keep @blp.route outermost, or use MethodView

@blp.response(BookSchema) with the schema first

the status code comes first; fix the call (TypeError at import time)

Expecting @blp.response to validate output

it serializes only; test the output against the document

Raising ValidationError inside a view

it becomes a 500; use @blp.arguments or abort(422/409, ...)

Unknown fields silently dropped

Meta.unknown = EXCLUDE is tolerant, RAISE is strict; choose per schema and remember RAISE becomes additionalProperties: false

required=True on a query field has no visible effect

for non-body locations the requirement is per field in the schema; a schema with load_default is optional

Wrong or missing OPENAPI_VERSION

the three required settings must be present; pick 3.1.0 and validate the result

Blueprint registered with app.register_blueprint

it works but is missing from the document; use api.register_blueprint

Documentation endpoints exposed in production

set OPENAPI_URL_PREFIX conditionally, or authenticate the prefix

Unpinned CDN scripts

pin versions or self-host; they run with your origin’s privileges

securitySchemes without enforcement

the document does not authenticate anything; protect the views

Documented examples with real credentials

use obvious placeholders; generated documents and Swagger "Authorize" fields are often copied around

Generated document not reviewed

commit it and diff it in CI so API changes are visible and deliberate

Where the Books Are Outdated

The Manning book Microservice APIs (José Haro Peralta, 2022/2023) is a good guide to API design, and chapter 5 gives the anatomy of an OpenAPI document; for flask-smorest, its chapter 6 contains errors and outdated choices that this page corrects. The Packt Flask Framework Cookbook editions and Full-Stack Flask and React document APIs with Flask-RESTful or Postman collections instead of OpenAPI. In summary:

In the book Current behaviour

Meta.unknown = EXCLUDE described as rejecting unknown fields, and RAISE as ignoring them

it is the other way round: RAISE rejects (and is the default), EXCLUDE silently drops; see The Unknown-Field Policy

@blp.response(...) decorating above @blp.route(...)

@blp.route must be outermost; see The Decorators and Their Order

@blp.response(Schema) with the schema first

the status code is the first positional argument (since flask-smorest 0.29.0)

marshmallow ValidationError raised in a view treated as a 422

it is a 500; only @blp.arguments and abort produce formatted errors; see Responses, Errors and Status Codes

the served document replaced by monkeypatching APISpec.to_dict

a workaround only; serve your own file, or use a design-first framework; see Design-First with a Hand-Written Document

OpenAPI 3.0.3

3.1 is aligned with JSON Schema 2020-12 and is the better target for new documents; see Which OpenAPI Version

RFC 7231 and a custom error payload

RFC 7231 is superseded by RFC 9110; use RFC 9457 Problem Details; see Problem Details Instead of the Default Format

Flask-RESTful with reqparse (Cookbook, chapter 7)

reqparse is deprecated and the extension barely maintained; use flask-smorest, APIFlask or flask-openapi3

Dredd for contract testing

archived; use Schemathesis or a validator-based test; see Design-First with a Hand-Written Document

Postman collections as the API documentation (Full-Stack Flask and React)

a Postman collection documents requests, not the contract; generate or write an OpenAPI document and import it

Summary

  • An OpenAPI document is the contract of the API; renderers, clients, mocks and tests are generated from it. Flask has no built-in support, so the document comes from an extension.

  • Code-first with flask-smorest: Api, Blueprint, MethodView, marshmallow schemas, and the decorators @blp.arguments, @blp.response, @blp.alt_response, @blp.paginate and @blp.doc, with @blp.route outermost.

  • The unknown-field policy decides strict or tolerant input; RAISE is the default and shows up as additionalProperties: false.

  • @blp.response serializes but does not validate; errors raised inside views are not formatted unless they are HTTPException instances; Problem Details is a subclass of Api away.

  • Set OPENAPI_VERSION to 3.1.0, serve the UIs from pinned or self-hosted scripts, and disable or protect them in production.

  • Commit the generated document (flask openapi write, or flask spec in APIFlask) and fail CI when it changes unexpectedly.

  • Design-first means a validated hand-written document plus contract tests; Connexion routes from the document, and Schemathesis and openapi-core automate the checks.
