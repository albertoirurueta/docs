Python Flask

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This section is written against Flask 3.1.3 (released 2026-02-18), Werkzeug 3.1.9 and Python 3.13, checked on 2026-10-07. Flask 3.1 supports Python 3.9 and newer, while the examples use Python 3.10+ syntax. Flask 3.2 had not been released on that date, so the changes planned for it (the merge of the application and request contexts, the removal of __version__, a 303 status for redirect, and the end of Python 3.9 and 3.10 support) are described as upcoming wherever they matter, and are collected on What’s Changed & Migration.

What Flask is

Flask is a Python web framework for the WSGI protocol. It is deliberately small: it gives you routing, request and response objects, a template engine, signed cookie sessions, a command-line interface and a test client, and it leaves the choice of database layer, form library, authentication and every other building block to you or to extensions. "Micro" means that the core does not decide those things for you, not that the framework is only for small applications.

Flask is not written from scratch. It is a thin layer over the Pallets libraries, and most of what you use daily is implemented one level down:

  • Werkzeug provides the WSGI toolkit: the Request and Response classes, the URL routing system, the development server and the interactive debugger.

  • Jinja renders the templates.

  • Click implements the flask command and your own CLI commands.

  • ItsDangerous signs the session cookie and other tokens.

  • MarkupSafe provides the escaping behind Jinja’s autoescape.

  • Blinker provides the signals.

This section is for developers who:

  • know Python and want to build server-rendered sites, JSON APIs or both with Flask, from a first route to a deployed, tested and monitored application

  • are coming from Django, FastAPI, Spring Boot, Express or ASP.NET Core and want a precise map of what Flask does itself, what an extension does and what is left to you

  • maintain a Flask application written for Flask 1.x or 2.x, or learned from older tutorials and books, and need the current idioms (DeclarativeBase models, db.session.execute(db.select(...)), flask --app, from_prefixed_env, SECRET_KEY_FALLBACKS) together with a table of what to change

Specifications used

The pages rely on these specifications and standards, each linked in the bibliography.

  • PEP 3333 (WSGI) and the ASGI specification, for the two server interfaces

  • RFC 9110 (HTTP semantics) and RFC 9111 (HTTP caching), and RFC 6265 (cookies), for status codes, headers, conditional requests and the session cookie

  • RFC 9457 (Problem Details for HTTP APIs), for error payloads

  • RFC 7519 (JSON Web Token), RFC 8725 and RFC 6750, for token authentication

  • OpenAPI 3.1 and JSON Schema 2020-12, for API descriptions

  • the WHATWG HTML Standard (Server-Sent Events) and the WHATWG Fetch Standard (CORS), for streaming and cross-origin requests

  • the OWASP Cheat Sheet Series, for the security guidance the official security page leaves open

  5. Authentication, authorization and security: Flask-Login, social login, roles and the security checklist.

Running example

Every example builds one small original application, the Bookshelf, so the pages fit together instead of being isolated snippets:

  • books, authors, reviews and users tables, modelled with SQLAlchemy 2.0 and versioned with Flask-Migrate

  • a catalog blueprint (Jinja pages, WTForms forms, message flashing and uploads of cover images), an auth blueprint (Flask-Login), an admin blueprint (Flask-Admin) and an api blueprint (flask-smorest and JWT)

  • English and Spanish pages with Flask-Babel, caching with Flask-Caching, a Celery job that sends a review digest and a live "new reviews" stream over Server-Sent Events

  • tests with pytest, and deployment with Gunicorn behind nginx and in Docker

Figure 2. The Bookshelf application: clients, nginx, Gunicorn, the Flask application with its blueprints and extensions, and its data services

The final project layout (pyproject.toml, src/bookshelf/__init__.py with create_app, config.py, extensions.py, models/, catalog/, auth/, admin/, api/, templates/, static/, migrations/, tests/ and instance/) is assembled on Application Factory & Project Layout.

The four books

Four published books were consulted for the concepts a Flask developer meets in practice, and to find the idioms that are out of date today. They are cited, never copied: no text, code listing, figure or data set from any of them appears in this section, every example is written against the current official documentation, and where a book and the documentation disagree the documentation wins.

How each book is used:

  • The two editions of the Flask Framework Cookbook are recipe books that cover the whole ecosystem: configuration, Jinja, SQLAlchemy, WTForms, authentication, REST, administration, internationalization, testing, deployment, containers and miscellaneous tips. The 3rd edition targets Flask 2.2, Werkzeug 2.2, SQLAlchemy 2.0 and Flask-SQLAlchemy 3.0 on Python 3.11, and the 2nd edition targets Flask 1.0, Werkzeug 0.15, SQLAlchemy 1.3 and Flask-SQLAlchemy 2.4 on Python 3.7, so the 2nd edition matters mostly for the Flask 1.x idioms you will meet in old code.

  • Microservice APIs is a framework-agnostic API design book. Only its chapter on Flask uses flask-smorest and marshmallow, and its other chapters on API design, documentation, security and testing are applied to Flask on the API and testing pages of this section.

  • Full-Stack Flask and React is half a React book. Only its Flask chapters are relevant here, on Flask 2.3 with Flask-SQLAlchemy and Flask-JWT-Extended, and the React side is covered by the site’s React section.
