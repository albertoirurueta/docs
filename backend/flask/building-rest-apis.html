REST in One Page

REST (Representational State Transfer) is an architectural style that Roy Fielding described in his doctoral dissertation; it is not a protocol and no library can make an API "RESTful" on its own. Applied to HTTP it comes down to six constraints, and Flask’s building blocks map onto them directly.

Constraint Meaning for an HTTP API Where it shows up in Flask

Client-server

The client owns presentation, the server owns data and rules; they evolve independently.

The API is a separate blueprint or application; see Application Factory & Project Layout.

Stateless

Every request carries everything the server needs; no server-side session between calls.

No flask.session for API clients; credentials travel in a header on each request (JWT & API Authentication).

Cacheable

Responses say whether and how long they may be reused.

Cache-Control, ETag, Last-Modified, make_conditional(); see Responses & JSON.

Uniform interface

Resources identified by URLs, manipulated through representations, with standard methods and self-describing messages.

@app.route, MethodView, jsonify, the Content-Type header, url_for().

Layered system

Proxies, gateways and caches may sit between client and server without the client knowing.

WSGI servers behind reverse proxies; ProxyFix (Deployment pages).

Code on demand (optional)

The server may ship executable code to the client.

Almost never used by JSON APIs.

The uniform interface includes hypermedia as the engine of application state (HATEOAS): representations contain links that tell the client what it can do next, so clients follow links instead of constructing URLs. Leonard Richardson’s maturity model, popularised by Martin Fowler, grades how far an API goes:

Level Name What it adds

0

The swamp of POX

One URL, one method (usually POST); the body says what to do. JSON-RPC and SOAP live here.

1

Resources

Many URLs, one per resource, but still mostly POST.

2

HTTP verbs

Methods carry the semantics (GET reads, PUT replaces, DELETE removes) and status codes carry the outcome.

3

Hypermedia controls

Responses include links to related resources and to the next possible actions.

Most production "REST" APIs stop at level 2, and that is a legitimate choice. Adding a small links object to each resource, as the Bookshelf API below does, is a cheap step towards level 3 that helps clients with pagination and discoverability without a full hypermedia format.

The same discipline is what makes API-first (or documentation-driven) development work in a microservice architecture: the API is the integration point between services, so its contract (the OpenAPI document, the status codes, the error format) is written down and agreed before the implementation. Flask supports both directions, code-first with the extensions compared later on this page and design-first by serving a hand-written specification, which is described in OpenAPI & API Documentation. The architectural trade-offs of splitting a system into services are covered by Architectural Patterns.

Types of Web APIs Compared

REST is one of several API styles. The choice is about the clients and the data, not fashion.

Style What it exposes Strengths Typical use

RPC and JSON-RPC

Named procedures (createBook(...)) over one endpoint

Simple, action-oriented, easy to map to functions

Internal commands, tooling, editors (Language Server Protocol)

SOAP

XML envelopes described by WSDL

Mature contracts, WS-* security and transaction extensions

Legacy enterprise and banking integrations

gRPC

Protobuf services over HTTP/2, streaming

Compact binary payloads, generated clients, bidirectional streaming

Service-to-service calls inside a platform; not directly callable from a browser without a proxy

REST

Resources identified by URLs, standard HTTP methods

Cache-friendly, uses every HTTP tool (proxies, CDNs, browsers), easy to debug with curl

GraphQL

One endpoint, a typed schema, queries chosen by the client

Many different clients with different data needs

Flask is a good fit for REST and RPC style APIs and can serve GraphQL through Ariadne or Strawberry; the GraphQL section of this site has the decision guide in Tips: When to Use GraphQL or a Typical REST API and the Python implementations in Python with FastAPI and Strawberry and Python with Ariadne. FastAPI-based REST APIs are described in FastAPI: Introduction & Architecture.

Designing Resources and URLs

A resource is a noun the API talks about: a book, a shelf, a loan. The URL identifies it, the method says what to do, the body is a representation of it. The conventions that keep an API predictable:

  • Use plural nouns for collections (/books) and the identifier for a single item (/books/42). The collection and the item are the two kinds of endpoint most resources need; a singleton resource that exists once per parent has no identifier of its own (/books/42/cover, /me).

  • Never put verbs in the path for ordinary CRUD (/getBook, /books/delete). When an operation really is not a CRUD verb, model it as a resource (POST /books/42/loans creates a loan) or as a sub-resource action (POST /books/42/archive) and say so in the documentation.

  • Nest only one level for ownership (/shelves/3/books) and give every resource a top-level URL as well; deep trees make URLs long and clients fragile.

  • Use lower-case, hyphen-separated path segments and identifiers that do not change. Remember Flask’s trailing-slash rule: a route declared with a trailing slash redirects the slash-less form, a route without one answers 404 for the slashed form (see Routing & URL Building). Pick the slash-less form for APIs; clients such as fetch and requests follow redirects but may turn a POST into a GET on a 301 or 302.

  • Put the what in the path and the how in the query string: filtering, sorting, searching and paging are query parameters, never separate endpoints.

The method decides the semantics. Two properties matter to clients and proxies: a method is safe if it does not change state, and idempotent if sending it twice has the same effect as sending it once. Retrying is only automatic for idempotent methods.

Two distinctions cause most of the arguments. First, 4xx means the client must change the request and 5xx means the server failed; clients and monitoring treat them differently, so an exception caused by bad input must never become a 500. Second, 400 versus 422: use 400 when the request cannot be understood at all and 422 (named Unprocessable Content in RFC 9110) when it is understood but invalid. Many APIs use 400 for both; what matters is being consistent. flask-smorest and APIFlask answer 422 for validation errors, and so does this page.

Error bodies should have one shape across the whole API. The standard shape is Problem Details, defined by RFC 9457 (which obsoleted RFC 7807) and sent as application/problem+json; the fields type, title, status, detail and instance are standard and extension members such as errors are allowed. How Flask finds an error handler, and the HTTPException hierarchy, are explained in Error Handling; here is the small toolkit the rest of this page uses: an exception that carries a status and extra members, and a function that turns it into a response.

import itertools
from threading import Lock

from flask import Flask, Blueprint, jsonify, request, url_for

class ApiError(Exception):
    """An error that becomes an RFC 9457 Problem Details response."""

    def __init__(self, status, title, detail=None, **extra):
        super().__init__(title)
        self.status, self.title, self.detail, self.extra = status, title, detail, extra


def problem(status, title, detail=None, **extra):
    body = {"type": "about:blank", "title": title, "status": status}
    if detail:
        body["detail"] = detail
    body.update(extra)
    response = jsonify(body)
    response.status_code = status
    response.mimetype = "application/problem+json"
    return response


def register_error_handlers(app):
    @app.errorhandler(ApiError)
    def handle_api_error(exc):
        return problem(exc.status, exc.title, exc.detail, **exc.extra)

    @app.errorhandler(HTTPException)
    def handle_http_exception(exc):
        response = problem(exc.code, exc.name, exc.description)
        if getattr(exc, "valid_methods", None):
            response.headers["Allow"] = ", ".join(exc.valid_methods)
        return response

Source: RFC 9457: Problem Details for HTTP APIs

Registering a handler for HTTPException makes every framework-generated error (a 404 for an unknown URL, a 405, a 413 for an oversized body, the 400 and 415 raised by get_json()) come back in the same shape. The HTTPException handler builds a new response, so it must copy headers that matter, such as Allow on a 405. The type about:blank means "no more information than the status code"; a real API can replace it with a URL that documents each kind of problem.

Filtering, Sorting and Pagination

A collection endpoint must never return "everything": the response grows without bound and one client can exhaust the server. The conventions are query parameters on the collection URL, parsed and validated like any other input:

  • Filtering: one parameter per field (?author=Ursula K. Le Guin) or a general search parameter (?q=dune).

  • Sorting: ?sort=-year,title, a comma-separated list where a leading minus means descending. Accept only an allow-list of field names; passing a client string to order_by is an injection risk.

  • Pagination: either offset pagination (?page=2&per_page=20), easy to implement and to jump around in, or keyset (cursor) pagination (?after=<cursor>&limit=20), which stays fast and stable for large or changing tables.

The helpers below work on a list of dictionaries so that they run without a database; the SQLAlchemy equivalents (db.paginate() and order_by) are in Flask-SQLAlchemy. They validate every parameter explicitly: Werkzeug’s request.args.get("page", 1, type=int) silently falls back to the default when the value is not a number, which hides client bugs.

import math

SORTABLE = {"id", "title", "author", "year"}
MAX_PER_PAGE = 100


def int_arg(args, name, default, minimum, maximum=None):
    raw = args.get(name)
    if raw is None:
        return default
    try:
        value = int(raw)
    except ValueError:
        raise ApiError(400, "Invalid query parameter", f"{name} must be an integer", parameter=name)
    if value < minimum or (maximum is not None and value > maximum):
        raise ApiError(400, "Invalid query parameter", f"{name} is out of range", parameter=name)
    return value


def query_books(books, args):
    """Filter, sort and paginate a list of book dictionaries; returns (items, meta)."""
    page = int_arg(args, "page", 1, 1)
    per_page = int_arg(args, "per_page", 20, 1, MAX_PER_PAGE)
    if author := args.get("author"):
        books = [b for b in books if b["author"].casefold() == author.casefold()]
    if q := args.get("q"):
        books = [b for b in books if q.casefold() in b["title"].casefold()]
    for key in reversed(args.get("sort", "id").split(",")):  # stable sort: last key first
        field = key.lstrip("-")
        if field not in SORTABLE:
            raise ApiError(400, "Invalid query parameter", f"cannot sort by {field}", parameter="sort")
        books = sorted(books, key=lambda b: (b.get(field) is None, b.get(field) or 0),
                       reverse=key.startswith("-"))
    total = len(books)
    pages = max(1, math.ceil(total / per_page))
    start = (page - 1) * per_page
    meta = {"page": page, "per_page": per_page, "total": total, "pages": pages}
    return books[start:start + per_page], meta


def link_header(endpoint, meta, args):
    """RFC 8288 Link header with first, last, prev and next relations."""
    def link(page, rel):
        return f'<{url_for(endpoint, **{**args.to_dict(), "page": page})}>; rel="{rel}"'

    links = [link(1, "first"), link(meta["pages"], "last")]
    if meta["page"] > 1:
        links.append(link(meta["page"] - 1, "prev"))
    if meta["page"] < meta["pages"]:
        links.append(link(meta["page"] + 1, "next"))
    return ", ".join(links)

Source: Werkzeug: MultiDict

The response carries the page data in the body (an items array and a meta object) and the navigation in a Link header, which is the standard way (RFC 8288) to point to the neighbouring pages; clients that only read the body can use meta. Offset pagination has two known weaknesses: OFFSET n makes the database walk past n rows, and a row inserted or deleted between two requests shifts every later page, so a client can see an item twice or miss one. Keyset pagination avoids both by asking for "the rows after this one"; the cursor is an opaque token that clients must not interpret (so the server can change it later).

import base64
import json


def encode_cursor(book_id):
    return base64.urlsafe_b64encode(json.dumps({"after": book_id}).encode()).decode()


def decode_cursor(token):
    try:
        return int(json.loads(base64.urlsafe_b64decode(token.encode()))["after"])
    except (ValueError, KeyError, TypeError):
        raise ApiError(400, "Invalid cursor", "the cursor is malformed", parameter="after")


def keyset_page(books, after=None, limit=20):
    last_seen = decode_cursor(after) if after else 0
    window = [b for b in sorted(books, key=lambda b: b["id"]) if b["id"] > last_seen][:limit + 1]
    items = window[:limit]
    next_cursor = encode_cursor(items[-1]["id"]) if len(window) > limit else None
    return items, next_cursor

Choose offset pagination for admin screens and small tables where "page 7 of 12" matters, and keyset pagination for feeds, exports and anything that grows quickly. With a real database, keyset pagination needs a unique, indexed sort key (WHERE id > :last ORDER BY id LIMIT :n). flask-smorest ships its own @blp.paginate() decorator that fills an X-Pagination response header; it is shown with that library below.

The layering matters more than the framework: the view translates between HTTP and the application (parse, validate, choose the status code), while the rules live in a service or repository that knows nothing about requests. Here the repository is an in-memory dictionary behind a lock, so the example runs anywhere; replace it with the SQLAlchemy models from the earlier pages without touching the views. Validation is passed to the view as a function, first a small hand-written one, later marshmallow and Pydantic, to show that the layers are independent.

class BookRepository:
    """In-memory stand-in for the database layer of the earlier pages."""

    def __init__(self):
        self._books, self._ids, self._lock = {}, itertools.count(1), Lock()

    def all(self):
        return list(self._books.values())

    def get(self, book_id):
        return self._books.get(book_id)

    def find_isbn(self, isbn):
        return next((b for b in self._books.values() if b["isbn"] == isbn), None)

    def add(self, data):
        with self._lock:
            book = {"id": next(self._ids), **data}
            self._books[book["id"]] = book
            return book

    def replace(self, book_id, data):
        self._books[book_id] = {"id": book_id, **data}
        return self._books[book_id]

    def delete(self, book_id):
        return self._books.pop(book_id, None)


FIELDS = {"title": str, "author": str, "isbn": str, "year": int}
REQUIRED = {"title", "author", "isbn"}


def parse_book(payload, partial=False):
    """Hand-written validation; the real projects below use a library."""
    if not isinstance(payload, dict):
        raise ApiError(422, "Validation failed", errors={"_body": ["Expected a JSON object."]})
    errors = {name: ["Unknown field."] for name in payload.keys() - FIELDS.keys()}
    if not partial:
        for name in REQUIRED - payload.keys():
            errors[name] = ["Missing data for required field."]
    for name, kind in FIELDS.items():
        if name in payload:
            value = payload[name]
            if kind is int:
                valid = isinstance(value, int) and not isinstance(value, bool)
            else:
                valid = isinstance(value, str) and value.strip() != ""
            if not valid:
                errors[name] = ["Must be an integer." if kind is int else "Must be a non-empty string."]
    if errors:
        raise ApiError(422, "Validation failed", "The request body is not valid.", errors=errors)
    return {name: payload[name] for name in FIELDS if name in payload}

from werkzeug.http import generate_etag


def book_resource(book):
    """Representation with hypermedia links (a step towards Richardson level 3)."""
    return {**book, "links": {"self": url_for("api_v1.book_item", book_id=book["id"]),
                              "collection": url_for("api_v1.book_collection")}}


def etag_for(book):
    return generate_etag(json.dumps(book, sort_keys=True).encode())


class BookCollection(MethodView):
    def __init__(self, repo, parse):
        self.repo, self.parse = repo, parse

    def get(self):
        items, meta = query_books(self.repo.all(), request.args)
        response = jsonify({"items": [book_resource(b) for b in items], "meta": meta})
        response.headers["Link"] = link_header("api_v1.book_collection", meta, request.args)
        response.headers["X-Total-Count"] = str(meta["total"])
        return response

    def post(self):
        data = self.parse(request.get_json())          # 400 or 415 here, 422 in parse
        if self.repo.find_isbn(data["isbn"]):
            raise ApiError(409, "Duplicate ISBN", f"A book with ISBN {data['isbn']} already exists.")
        book = self.repo.add(data)
        location = url_for("api_v1.book_item", book_id=book["id"])
        return jsonify(book_resource(book)), 201, {"Location": location}


class BookItem(MethodView):
    def __init__(self, repo, parse):
        self.repo, self.parse = repo, parse

    def _book_or_404(self, book_id):
        book = self.repo.get(book_id)
        if book is None:
            raise ApiError(404, "Book not found", f"There is no book with id {book_id}.")
        return book

    def _check_isbn(self, isbn, own_id):
        other = self.repo.find_isbn(isbn)
        if other and other["id"] != own_id:
            raise ApiError(409, "Duplicate ISBN", f"A book with ISBN {isbn} already exists.")

    def _check_if_match(self, book):
        if request.if_match and not request.if_match.contains(etag_for(book)):
            raise ApiError(412, "Precondition failed", "The book changed since you read it.")

    def get(self, book_id):
        book = self._book_or_404(book_id)
        response = jsonify(book_resource(book))
        response.set_etag(etag_for(book))
        return response.make_conditional(request)       # 304 when If-None-Match matches

    def put(self, book_id):                              # replace: all required fields again
        book = self._book_or_404(book_id)
        self._check_if_match(book)
        data = self.parse(request.get_json())
        self._check_isbn(data["isbn"], book_id)
        return jsonify(book_resource(self.repo.replace(book_id, data)))

    def patch(self, book_id):                            # JSON Merge Patch (RFC 7396)
        book = self._book_or_404(book_id)
        self._check_if_match(book)
        changes = self.parse(request.get_json(), partial=True)
        if "isbn" in changes:
            self._check_isbn(changes["isbn"], book_id)
        merged = {**{k: v for k, v in book.items() if k != "id"}, **changes}
        return jsonify(book_resource(self.repo.replace(book_id, merged)))

    def delete(self, book_id):
        self._book_or_404(book_id)
        self.repo.delete(book_id)
        return "", 204


def create_app(repo=None, parse=parse_book):
    app = Flask(__name__)
    repo = repo if repo is not None else BookRepository()
    api = Blueprint("api_v1", __name__, url_prefix="/api/v1")
    api.add_url_rule("/books", view_func=BookCollection.as_view("book_collection", repo, parse))
    api.add_url_rule("/books/<int:book_id>", view_func=BookItem.as_view("book_item", repo, parse))
    app.register_blueprint(api)
    register_error_handlers(app)
    return app

The decisions in that code are worth spelling out.

  • POST returns 201 and a Location header with the URL of the new item, so the client never has to build it. The header is relative here; Werkzeug 2.1 and later no longer rewrite Location to an absolute URL, and RFC 9110 allows a relative reference. Use url_for(..., _external=True) if a client demands an absolute one.

  • PUT replaces, PATCH merges. A PUT body must be a complete representation, so the required fields are required again and anything omitted is gone; it is idempotent. A PATCH body lists only the fields to change. The format used here is JSON Merge Patch (RFC 7396, media type application/merge-patch+json): the body is a partial object and a null value removes a field. Its alternative, JSON Patch (RFC 6902), is a list of explicit operations ({"op": "replace", "path": "/year", "value": 1969}) and suits arrays and atomic multi-field edits. Whichever format you choose, document it, because PATCH has no default body format. Flask’s request.get_json() accepts any application/*+json media type, so the merge-patch type needs no special handling.

  • DELETE returns 204 with an empty body. Returning 202 Accepted with a body, as some tutorials do, promises asynchronous processing that did not happen; use 200 with a body only if the client needs the deleted representation.

  • 409 for state conflicts and 404 for missing items are raised as ApiError, never returned as 200 with {"error": ...}.

  • ETag and If-Match implement optimistic concurrency: the client reads a book, sends the ETag back in If-Match with its update, and gets 412 if someone else changed the book in between; without that, two editors silently overwrite each other (the "lost update"). make_conditional() turns a matching If-None-Match into a 304 with no body.

  • Unknown fields are rejected (422), so a typo such as titel is reported instead of being ignored.

Validation and Serialization

Hand-written validation does not scale: every field needs type checks, ranges, formats, nested objects and clear error messages, and the same rules must be repeated for the documentation. Two libraries dominate Python APIs, and Flask works with both because validation happens in your view (or in a decorator), not in the framework.

marshmallow describes data with Schema classes of fields; the same schema loads (validates and deserializes input) and dumps (serializes output). Pydantic describes data with annotated classes (BaseModel) and validates on construction; it is the library behind FastAPI. The two are interchangeable for the API-building purpose of this page; the usual rule is to follow the extension: flask-smorest and APIFlask’s default are marshmallow, flask-openapi3 and APIFlask’s Pydantic mode use Pydantic.

RAISE (the default) rejects the request, EXCLUDE silently discards the field and INCLUDE passes it through unvalidated. A published book on microservice APIs states the opposite for EXCLUDE; trust the documentation. RAISE is the right default for request bodies (typos are reported, and clients cannot smuggle extra attributes into a mass-assignment). EXCLUDE is acceptable for query strings, where proxies and analytics tools append unrelated parameters, and when you must stay tolerant of newer clients.

    except PydanticValidationError as exc:

extra="forbid" is Pydantic’s RAISE: without it Pydantic ignores unknown keys. model_dump(exclude_unset=True) returns only the fields the client actually sent, which is what a PATCH handler needs; it is easy to forget and to overwrite fields with defaults. For output, serialization is a separate concern from validation: marshmallow’s dump() and the output decorators of the extensions below serialize and do not validate what your code returns. If you want guarantees about outgoing data, validate it explicitly with a Pydantic output model or check it in tests against the OpenAPI document (API Contract & Property-Based Testing).

Versioning and Deprecation

An API is a contract: once clients depend on a field, removing or renaming it breaks them. Versioning lets you ship an incompatible change next to the old behaviour and retire the old one on a schedule. Not every change needs a new version:

Compatible (no new major version) Breaking (new major version)

Adding an endpoint

Removing or renaming an endpoint

Adding an optional request field or query parameter

Making an optional field required

Adding a field to a response

Removing, renaming or retyping a response field

Adding a new value to an extensible enumeration (if documented as extensible)

Changing the meaning of a status code or of a field

Making validation more lenient

Making validation stricter

Clients must therefore ignore response fields they do not know. The three places to put the version:

Where Example Notes

URL path

/api/v1/books

The most common: visible, easy to route, cache and test with curl; the version is part of the resource identity.

Header (media type)

Accept: application/vnd.bookshelf.v2+json

Keeps URLs stable and follows HTTP content negotiation; harder to try in a browser and to document.

Query parameter

/api/books?version=2

Easy but easy to forget and awkward for caching; generally discouraged.

In Flask, a URL version is a blueprint per major version with its own url_prefix (see Blueprints), which also lets the two versions have different error handlers and different schemas while sharing the service layer. Header-based versioning is a before_request function or a view that inspects request.accept_mimetypes. Semantic versioning applies to the API as MAJOR.MINOR.PATCH, but only the major number appears in URLs; the full number belongs in the OpenAPI info.version field and in release notes.

A version is retired in stages: announce, mark deprecated, set a retirement date, then remove (answering 410 Gone for a while is kinder than a 404). Two response headers let machines read the status: Deprecation (RFC 9745, published in March 2025) holds the date the endpoint became deprecated as an @-prefixed Unix timestamp, and Sunset (RFC 8594) holds the HTTP date after which it may stop working. A Link header with the relation successor-version points to the replacement, and deprecation points to the migration guide.

import datetime

from werkzeug.http import http_date

DEPRECATED_SINCE = datetime.datetime(2026, 10, 1, tzinfo=datetime.timezone.utc)
SUNSET = datetime.datetime(2027, 6, 30, tzinfo=datetime.timezone.utc)
BOOKS = {1: {"id": 1, "title": "Dune", "authors": ["Frank Herbert"]}}


def v1_book(book):                      # the old shape: one author string
    return {"id": book["id"], "title": book["title"], "author": book["authors"][0]}


def v2_book(book):                      # the new shape: a list of authors
    return {"id": book["id"], "title": book["title"], "authors": book["authors"]}


v1 = Blueprint("v1", __name__, url_prefix="/api/v1")
v2 = Blueprint("v2", __name__, url_prefix="/api/v2")


@v1.get("/books/<int:book_id>")
def v1_get(book_id):
    return jsonify(v1_book(BOOKS[book_id]))


@v2.get("/books/<int:book_id>")
def v2_get(book_id):
    return jsonify(v2_book(BOOKS[book_id]))


@v1.after_request
def mark_v1_deprecated(response):
    response.headers["Deprecation"] = f"@{int(DEPRECATED_SINCE.timestamp())}"
    response.headers["Sunset"] = http_date(SUNSET)
    response.headers.add("Link", f'<{request.path.replace("/v1/", "/v2/", 1)}>; rel="successor-version"')
    return response


negotiated = Flask(__name__)
negotiated.register_blueprint(v1)
negotiated.register_blueprint(v2)


@negotiated.get("/api/books/<int:book_id>")           # version chosen by the Accept header
def negotiated_get(book_id):
    media = request.accept_mimetypes.best_match(
        ["application/vnd.bookshelf.v2+json", "application/vnd.bookshelf.v1+json"])
    if media is None:
        raise ApiError(406, "Not acceptable", "Supported: application/vnd.bookshelf.v1+json and v2+json")
    shape = v1_book if media.endswith("v1+json") else v2_book
    response = jsonify(shape(BOOKS[book_id]))
    response.mimetype = media
    response.headers["Vary"] = "Accept"
    return response

flask-smorest

flask-smorest builds on marshmallow, webargs and apispec. Its Api object wraps the Flask application, its Blueprint subclass collects the routes, and the decorators arguments and response validate input and serialize output. The configuration keys API_TITLE and API_VERSION are required to generate the OpenAPI document and OPENAPI_VERSION selects the specification version (the keys that publish the document and the documentation UIs are explained in OpenAPI & API Documentation). The example reuses the BookSchema defined above.

import flask_smorest

smorest_app = Flask(__name__)
smorest_app.config.update(API_TITLE="Bookshelf API", API_VERSION="v1", OPENAPI_VERSION="3.1.0")
smorest_api = flask_smorest.Api(smorest_app)
blp = flask_smorest.Blueprint("books", __name__, url_prefix="/books", description="Bookshelf books")
shelf = {1: {"id": 1, "title": "Dune", "author": "Frank Herbert", "isbn": "9780000000001"}}


class BookQuery(Schema):
    q = fields.Str()


@blp.route("/")                                   # route is always the outermost decorator
class Books(MethodView):
    @blp.arguments(BookQuery, location="query")   # query string -> first extra argument
    @blp.response(200, BookSchema(many=True))     # the status code is the FIRST positional argument
    @blp.paginate()                               # adds page and page_size, X-Pagination header
    def get(self, args, pagination_parameters):
        books = [b for b in shelf.values() if args.get("q", "").casefold() in b["title"].casefold()]
        pagination_parameters.item_count = len(books)
        return books[pagination_parameters.first_item:pagination_parameters.last_item + 1]

    @blp.arguments(BookSchema)                    # JSON body, validated; 422 on error
    @blp.response(201, BookSchema)
    def post(self, new_book):
        new_book["id"] = max(shelf) + 1
        shelf[new_book["id"]] = new_book
        return new_book, 201, {"Location": f"/books/{new_book['id']}"}


@blp.route("/<int:book_id>")
class BookById(MethodView):
    @blp.response(200, BookSchema)
    def get(self, book_id):
        if book_id not in shelf:
            flask_smorest.abort(404, message="Book not found")   # formatted JSON error
        return shelf[book_id]

    @blp.arguments(BookSchema(partial=True))
    @blp.response(200, BookSchema)
    def patch(self, changes, book_id):
        if book_id not in shelf:
            flask_smorest.abort(404, message="Book not found")
        shelf[book_id].update(changes)
        return shelf[book_id]

Points that older material gets wrong or that surprise people:

  • @blp.route() must be the outermost decorator, above arguments and response; put it below and the route registers the undecorated function.

  • Since flask-smorest 0.25 the first positional argument of @blp.response() is the status code. Passing the schema first (@blp.response(BookSchema)) is the pre-0.25 signature and fails.

  • The validated arguments are passed to the view as extra positional arguments, in the order of the decorators, before the URL variables.

  • Validation errors are raised by the arguments decorator and formatted as a 422 with an errors member keyed by location (json, query, headers). Raising marshmallow.ValidationError yourself inside the view is not translated and gives a 500; use flask_smorest.abort(422, ...) or validate through the decorator.

  • Query-string schemas usually want unknown = EXCLUDE; request bodies keep the default RAISE.

  • The error shape of flask-smorest (code, status, message, errors) is its own; to answer with Problem Details, override its error handler.

APIFlask

APIFlask is a thin layer over Flask that keeps ordinary function routes and adds the decorators app.input(), app.output() and app.doc(). It documents itself with OpenAPI 3.1 by default and validates with marshmallow or, when the schema is a BaseModel, with Pydantic.

import apiflask
from apiflask import fields as af_fields
from apiflask import validators as af_validators

apiflask_app = apiflask.APIFlask(__name__, title="Bookshelf API", version="1.0")
af_shelf = {1: {"id": 1, "title": "Dune", "year": 1965}}


class AfBookIn(apiflask.Schema):
    title = af_fields.String(required=True, validate=af_validators.Length(1, 200))
    year = af_fields.Integer(validate=af_validators.Range(min=1450))


class AfBookOut(apiflask.Schema):
    id = af_fields.Integer()
    title = af_fields.String()
    year = af_fields.Integer()


@apiflask_app.get("/books/<int:book_id>")
@apiflask_app.output(AfBookOut)
def af_get(book_id):
    if book_id not in af_shelf:
        apiflask.abort(404, "Book not found")
    return af_shelf[book_id]


@apiflask_app.post("/books")
@apiflask_app.input(AfBookIn)                      # the validated body arrives as json_data
@apiflask_app.output(AfBookOut, status_code=201)
@apiflask_app.doc(summary="Create a book")
def af_create(json_data):
    book = {"id": max(af_shelf) + 1, **json_data}
    af_shelf[book["id"]] = book

Flask-RESTX organizes an API into Namespace objects of Resource classes and describes payloads with its own fields models; it generates a Swagger 2.0 document, not OpenAPI 3. Choosing

Start with plain Flask, MethodView and the validation library you already know when the API has a handful of endpoints. Choose flask-smorest when you want marshmallow schemas, class-based views and mature OpenAPI generation, APIFlask when you want function routes and the option of Pydantic, and flask-openapi3 when you want FastAPI-style annotations on Flask. Treat Flask-RESTX as a maintenance-mode choice and Flask-RESTful as legacy. If the main reason for choosing Flask is nothing but the API itself, compare it with FastAPI, which builds validation, documentation and dependency injection into the framework (FastAPI: Introduction & Architecture).

Pitfalls and Security

  • Mass assignment. Never pass the whole request body to a model constructor (Book(**request.json)). A schema with an allow-list of fields, dump_only for identifiers and flags such as is_admin, and RAISE for unknown fields closes that hole.

  • Authentication and authorization on every endpoint. A missing check is the most common API vulnerability (OWASP calls it broken object level authorization): after loading a book by identifier, check that the caller may see it. Credentials belong in headers, not in URLs; see JWT & API Authentication and the authorization page of this section.

  • Limit sizes. Set MAX_CONTENT_LENGTH so oversized bodies are answered with 413, cap per_page, limit nesting and list lengths in schemas, and add rate limiting (429 with Retry-After) at the proxy or with Flask-Limiter.

  • Do not leak. Error handlers must not return tracebacks, SQL, file paths or the submitted input; return a generic 500 Problem Details body with an identifier that you can find in the logs. Run with debug mode off.

  • Safe methods stay safe. A GET that changes state is triggered by link prefetchers, crawlers and CSRF. Cookie-based sessions combined with a JSON API need CSRF protection (see the security page); token-based APIs sent in the Authorization header do not.

  • Retries. POST is not idempotent, so a client that retries after a timeout can create two books. Provide an idempotency key (an Idempotency-Key request header, currently an IETF draft rather than an RFC) or a natural unique constraint such as the ISBN, and answer duplicates with 409.

  • CORS applies as soon as a browser on another origin calls the API; see Single-Page Apps & CORS and the CORS page.

  • Content negotiation. Check the Content-Type of request bodies (Flask’s get_json() already answers 415) and declare the response type. jsonify sets application/json; the Problem Details responses set application/problem+json.

Summary

  • Model resources as plural nouns with a collection and an item endpoint; let the method carry the verb and the status code carry the outcome: 201 plus Location on creation, 204 on deletion, 404 for missing items, 409 for conflicts, 422 for invalid bodies.

  • PUT replaces and is idempotent; PATCH merges and needs a documented body format; ETag with If-Match prevents lost updates.

  • Return every error as RFC 9457 Problem Details through error handlers for ApiError and HTTPException.

  • Always filter, sort and page collections, validate each query parameter, and allow-list sort fields; use keyset pagination for large, changing data.

  • Validate with marshmallow or Pydantic, reject unknown fields in request bodies, and remember that output decorators serialize but do not validate.

  • Version by major number in the URL or the media type, add Deprecation, Sunset and Link headers when retiring a version.

  • Pick flask-smorest, APIFlask or flask-openapi3 for new documented APIs; treat Flask-RESTX as maintenance mode and Flask-RESTful as legacy.
