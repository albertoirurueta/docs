app/settings.py: configuration from the environment
from functools import lru_cache
from pathlib import Path

from pydantic_settings import BaseSettings, SettingsConfigDict
from sqlalchemy.engine import URL


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="BOOKSHELF_")

    db_drivername: str = "sqlite"
    db_host: str | None = None
    db_port: int | None = None
    db_name: str = "bookshelf.db"
    db_user: str | None = None
    db_password_file: Path | None = None  # path of a secret file, never the password itself

    def database_url(self) -> URL:
        password = None
        if self.db_password_file is not None:
            password = self.db_password_file.read_text().strip()
        return URL.create(
            self.db_drivername,
            username=self.db_user,
            password=password,
            host=self.db_host,
            port=self.db_port,
            database=self.db_name,
        )


@lru_cache
def get_settings() -> Settings:
    return Settings()

Source: FastAPI: Settings and Environment Variables

With no variables set the service uses a local SQLite file, which keeps fastapi dev and the tests simple. In a container the same code is pointed at PostgreSQL purely through BOOKSHELF_DB_* variables, and the password never appears in an environment variable, a layer or a manifest: only the path of the secret file does.

app/main.py: lifespan, session dependency and health endpoints
import logging
from collections.abc import AsyncIterator, Iterator
from contextlib import asynccontextmanager
from typing import Annotated

from fastapi import Depends, FastAPI, HTTPException
from sqlalchemy import text
from sqlmodel import Field, Session, SQLModel, create_engine, select

from .settings import get_settings

logger = logging.getLogger("uvicorn.error")


class Book(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    title: str = Field(index=True)
    author: str


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    app.state.engine = create_engine(get_settings().database_url(), pool_pre_ping=True)
    logger.info("startup: engine created")
    yield
    app.state.engine.dispose()
    logger.info("shutdown: engine disposed")


app = FastAPI(title="Bookshelf API", lifespan=lifespan)


def get_session() -> Iterator[Session]:
    with Session(app.state.engine) as session:
        yield session


SessionDep = Annotated[Session, Depends(get_session)]


@app.get("/healthz")
def liveness() -> dict[str, str]:
    """Liveness: the process is up. No dependency is checked on purpose."""
    return {"status": "alive"}


@app.get("/readyz")
def readiness(session: SessionDep) -> dict[str, str]:
    """Readiness: the database answers."""
    try:
        session.exec(text("SELECT 1"))
    except Exception:
        raise HTTPException(status_code=503, detail="database unavailable")
    return {"status": "ready"}


@app.post("/books", status_code=201)
def create_book(book: Book, session: SessionDep) -> Book:
    session.add(book)
    session.commit()
    session.refresh(book)
    return book


@app.get("/books")
def list_books(session: SessionDep) -> list[Book]:
    return list(session.exec(select(Book)))

Exec Form CMD and Graceful Shutdown

CMD can be written as a JSON array (exec form) or as plain text (shell form). The official guide is explicit: always use the exec form so that FastAPI can shut down gracefully and its lifespan shutdown code runs.

Exec form versus shell form
# Do this: the container's main process (PID 1) is fastapi itself
CMD ["fastapi", "run", "app/main.py", "--port", "80"]

# Don't do this: Docker wraps the text in /bin/sh -c, so the shell is PID 1
CMD fastapi run app/main.py --port 80

Source: FastAPI: FastAPI in Containers - Docker

The reason is signals. docker stop, Docker Compose and Kubernetes all stop a container by sending SIGTERM to the main process and, after a grace period, SIGKILL. With the exec form the main process is the server, which handles SIGTERM by finishing the requests in flight and running the lifespan shutdown code (here: disposing the engine). With the shell form the main process is a shell, which in many setups does not forward the signal, so the server never learns that it should stop, the grace period runs out, and the container is killed without cleanup. That is also the cause of the "services take 10 seconds to stop or recreate" symptom with Docker Compose that the official page points to (the default stop timeout in Docker is 10 seconds). The same applies to a wrapper script: end it with exec so the server replaces the shell (see Running Alembic as a Pre-Start Step).

Layer Caching: Dependencies Before Code

An image is a stack of layers, one per instruction. When Docker rebuilds, it reuses every layer from the top until the first one whose inputs changed, and rebuilds everything after it. The Dockerfile therefore orders instructions from least to most frequently changing: base image, then the dependency file and its install, then the code. A code edit invalidates only the last COPY; installing the dependencies, which can take minutes, is served from the cache. If you wrote COPY . /code before pip install, every code change would reinstall every package. The generic mechanics, BuildKit cache mounts and multi-stage builds are covered in Build Cache and Multi-Stage Builds and BuildKit and Buildx; the basics of each instruction are in Dockerfile Fundamentals.

A .dockerignore file keeps local junk out of the build context (and out of cache invalidation): a changing .git directory or a developer’s pycache would otherwise invalidate the COPY layers or end up in the image.

.git
.venv
__pycache__/
*.pyc
*.db
.env
secrets/
k8s/
compose.yaml

    PYTHONUNBUFFERED=1

Behind a Load Balancer: --proxy-headers

In production the container almost never faces clients directly: an ingress controller, cloud load balancer or Traefik terminates TLS and forwards plain HTTP. Without help the application then sees http and the proxy’s IP, so generated redirects point to http://, request.url is wrong and rate limits see one client. --proxy-headers makes Uvicorn (through the FastAPI CLI) honour the X-Forwarded- headers, but only from trusted peers. Uvicorn’s default trusted list is the loopback address (127.0.0.1 and ::1) only, so in a cluster, where the proxy has a pod or node IP, add --forwarded-allow-ips with the proxy’s address or range. Trusting everything with is acceptable only when the container is reachable exclusively through the proxy, because otherwise any client can forge its own address or scheme. The full explanation, with a run showing the spoofing difference, is in Forwarded headers and --forwarded-allow-ips and the TLS side in HTTPS and TLS Termination.

    UV_COMPILE_BYTECODE=1 \

    --mount=type=bind,source=uv.lock,target=uv.lock \
    --mount=type=bind,source=pyproject.toml,target=pyproject.toml \
    uv sync --locked --no-install-project

# Layer 2: the project itself.
COPY . /app
RUN --mount=type=cache,target=/root/.cache/uv \

How it works and why:

  • Where uv comes from. Copying the binaries out of the official uv image (COPY --from=ghcr.io/astral-sh/uv:<version> /uv /uvx /bin/) is the approach the uv guide describes, together with pinning the version; the guide also publishes derived images with uv and Python together (for example Debian slim or Alpine based). The version shown (0.12.22) is the guide’s own example: replace it with the uv release you have tested.

  • uv sync --locked installs exactly what uv.lock records and errors if the lock does not match pyproject.toml, which is what a CI image build wants. --no-install-project in the first layer installs only the dependencies, so the layer is reused while only your code changes.

  • PATH="/app/.venv/bin:$PATH" puts the project’s virtual environment first, so fastapi is found directly and CMD can stay in exec form. The alternative the guide shows is uv run; as a CMD it adds a wrapper process, so prefer the environment on the PATH for signal handling.

  • .venv in .dockerignore. The guide recommends it: the virtual environment of your machine must not be copied into the image, because it is platform specific. The .dockerignore above already lists it.

  • Cache mounts (--mount=type=cache) require BuildKit, the default builder in current Docker.

  • The uv guide also documents development setups for Compose (docker compose watch syncing the project but ignoring .venv).

A single Uvicorn process runs one event loop on one CPU core. To use several cores you need several processes, and the question is where they are managed. The FastAPI documentation gives a clear default by environment:

In a Dockerfile this is CMD ["fastapi", "run", "app/main.py", "--port", "8000", "--workers", "4"], as in the official page. Things to weigh when you choose workers:

  • Memory multiplies. Each worker imports the application and holds its own copies of models, caches and pools. One process per container gives a stable, per-container memory figure that you can express as a Kubernetes or Compose limit; with --workers the limit must cover all of them.

  • Connection pools multiply. Four workers with a pool of ten connections each is forty connections to PostgreSQL, per container, per replica.

  • Do not hard-code a core count. Inside a container the machine’s core count may not match the CPU limit that the container actually gets (a Kubernetes CPU limit throttles rather than hides cores), so size --workers from a measurement or a platform setting, not from detection. Uvicorn itself defaults --workers to the WEB_CONCURRENCY environment variable when set, and to 1 otherwise.

  • CPU-bound code is a separate problem. Workers help throughput when requests are independent; they do not turn a CPU-heavy endpoint into a fast one, and blocking calls in async def handlers still stall their own worker’s loop (see Async & Concurrency).

  • The orchestrator still sees one thing. A container with four workers looks like one unit to Kubernetes. If one worker is stuck, the liveness probe may hit a healthy sibling and the container is not restarted.

  • Startup order is a chain of conditions. depends_on with condition: service_healthy waits for the database healthcheck, and service_completed_successfully waits for the migration container to exit with status 0. Running Alembic as a Pre-Start Step

Schema changes must be applied before the new code serves traffic, and the application must not apply them itself on every worker start: with two replicas or four workers, several processes would race to alter the same tables. The FastAPI deployment concepts call this "previous steps before starting", and the container page describes two options: a separate container that runs the step once before the replicas (an init container or Job in Kubernetes), or the step in the same container right before the main process when running it several times is harmless. Alembic itself, the env.py that reads the URL from the same settings as the application, and the import sqlmodel line that script.py.mako needs for SQLModel’s string type are covered in Alembic Migrations.

A Wrapper Script (single container)

For a single container (a small VM, Compose without a separate migration service, or a Container Apps revision with one replica), a tiny entrypoint script runs the migration and then replaces itself with the server. exec is what keeps fastapi as PID 1, so the signal handling of Exec Form CMD and Graceful Shutdown still works:

entrypoint.sh
#!/bin/sh
set -eu

# Optional pre-start step: apply migrations, then replace the shell with the server.
if [ "${RUN_MIGRATIONS:-0}" = "1" ]; then
    alembic upgrade head
fi

exec "$@"

A Kubernetes Job

On Kubernetes the one-shot step is a Job that uses the same image and runs to completion once per release (a Helm hook, an Argo CD sync wave or a pipeline step decides when). Because the Job is separate from the Deployment, it runs exactly once however many replicas follow:

An init container (Kubernetes: Init Containers) is the other native option, and the FastAPI documentation names it, but it runs in every pod, so with several replicas the migration runs several times, at the same time on a first rollout. Use it only for steps that are safe to repeat in parallel, such as "wait until the database accepts connections", and put real migrations in a Job.

Rolling out a schema change safely is mostly about compatibility: during a rolling update old and new pods run side by side against the new schema, so the migration must keep working for the old code (add the nullable column in one release, start using it in the next, drop the old one later). The pattern (expand and contract) is described in the schema evolution material on this site, starting from Schema Evolution.

Health Endpoints and Probes

Kubernetes asks three different questions of a container, and each needs a different answer from the application:

Table 5. The three probes
Probe Question What happens on failure

startupProbe

Has the application finished starting?

Other probes are held back until it succeeds; if it never does within failureThreshold x periodSeconds, the container is restarted. It lets slow starts (loading a model) be tolerated without a long liveness delay.

livenessProbe

Is the process alive, or stuck beyond recovery?

The container is restarted.

readinessProbe

Can this pod serve traffic right now?

The pod is removed from the Service’s endpoints (no restart) and added back when it passes again.

The crucial design rule is in the example endpoints above: liveness must not depend on external systems. If /healthz checked the database and the database had an outage, every pod would fail liveness, Kubernetes would restart all of them, and the restarts would add load to a database that is already struggling. Liveness answers only "is this process responsive?", which is why /healthz does nothing. Readiness may check dependencies that this pod needs to serve requests, so a pod that cannot reach the database is taken out of rotation instead of returning errors; /readyz runs a SELECT 1 through the same session dependency as the real endpoints. Keep the check cheap, with a short timeout, because it runs every few seconds on every pod.

This is the observed behaviour of the two endpoints with the database unreachable (the SQLite path pointed at a missing directory):

GET /readyz   -> HTTP/1.1 503 Service Unavailable
{"detail":"database unavailable"}

Graceful Shutdown

When a pod is deleted (a rollout, a scale-down, a node drain), two things happen at the same time and Kubernetes does not order them: the pod is removed from Service endpoints, and the kubelet starts shutting the containers down. Proxies learn about the removal with a small delay, so for a moment a pod that has begun stopping can still receive new requests. The sequence is:

sequenceDiagram autonumber participant K as Kubernetes participant E as Service endpoints / proxies participant C as Container (fastapi run) K->>E: pod marked terminating, remove from endpoints K->>C: preStop hook (sleep 5) Note over E,C: proxies stop sending new requests during the sleep K->>C: SIGTERM C->>C: Uvicorn stops accepting, finishes in-flight requests C->>C: lifespan shutdown runs (dispose engine, close clients) C-->>K: process exits 0 Note over K,C: if still running when terminationGracePeriodSeconds ends: SIGKILL

The pieces the application and the manifest must get right:

  • SIGTERM reaches the server. That requires the exec-form CMD (or exec in a wrapper): see Exec Form CMD and Graceful Shutdown. The log shown earlier (Shutting down, Waiting for application shutdown, the lifespan message) is the proof you want to see in your own pods.

  • terminationGracePeriodSeconds (default 30 seconds) is the total budget; after it the container receives SIGKILL. Its countdown starts before the preStop hook, and the hook must finish before SIGTERM is sent (see the Kubernetes container lifecycle documentation), so budget preStop plus the slowest request plus the lifespan shutdown.

  • The preStop sleep. A short sleep (five seconds in the manifest) delays SIGTERM until the endpoint removal has propagated, so the load balancer stops sending new requests before the server stops accepting them. The sleep action is built into the lifecycle hooks, so the slim image needs no sleep binary.

  • In-flight requests. On SIGTERM Uvicorn stops accepting new connections and waits for requests in progress to complete; requests that can take a long time (large uploads, slow reports) must fit inside the grace period, or be moved to a background worker.

  • Long-lived connections. WebSockets, Server-Sent Events and streaming responses keep a connection open indefinitely, and Uvicorn’s graceful shutdown waits for them. Without a limit the pod waits until SIGKILL. Uvicorn has --timeout-graceful-shutdown <seconds>: the maximum wait for a graceful shutdown, after which the server starts terminating the remaining requests. It is an option of the uvicorn command (it is not in the fastapi run options), so use CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--proxy-headers", "--timeout-graceful-shutdown", "20"] when you need it, and pick a value below the grace period. Clients of those endpoints should reconnect (see WebSockets and Streaming, JSON Lines & SSE).

  • Lifespan work stays short. Cleanup in the lifespan (closing pools and clients, flushing metrics) runs after the requests have ended; a hung await there would consume the rest of the grace period. Background tasks started with BackgroundTasks run after the response in the same process and can be cut off by SIGKILL; work that must not be lost belongs in a queue (see BackgroundTasks and shutdown).

Source: Kubernetes: Pod Lifecycle: termination of Pods

Autoscaling and Disruption Budgets

k8s/hpa-pdb.yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: bookshelf-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: bookshelf-api
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: bookshelf-api
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: bookshelf-api

Source: Kubernetes: Horizontal Pod Autoscaling

  • The HorizontalPodAutoscaler adds or removes pods based on CPU utilization relative to the request, so a CPU request is required for it (the Deployment sets one). An async API is I/O bound, and CPU can stay low while requests queue behind a slow database; scale on request rate or latency with a metrics adapter when CPU is a poor signal.

  • Scaling out multiplies database connections: maxReplicas times the pool size must stay below the database’s connection limit (see Connection pooling).

  • The PodDisruptionBudget keeps at least two pods up during voluntary disruptions such as node drains (Kubernetes: Specifying a Disruption Budget).

  • Cluster-wide topics are covered by the Kubernetes Reference: Ingress, Helm, GitOps and CI/CD and Network Policies. The managed cloud options are in the next section.

The Deprecated tiangolo/uvicorn-gunicorn-fastapi Image

Many tutorials still start with FROM tiangolo/uvicorn-gunicorn-fastapi, a ready-made image that ran Gunicorn managing Uvicorn workers and chose the number of workers by itself. The FastAPI documentation, re-checked on 2026-10-02, now states that this image is deprecated and that you should probably not use it or any similar base image. Its history explains why: the image was created when Uvicorn could not manage and restart dead workers itself, so Gunicorn was needed for that. Today Uvicorn and the fastapi command support --workers, so there is no reason to prefer a special base image over your own image from the official Python image, which is "pretty much the same amount of code". Kubernetes and similar platforms handle replication at the cluster level, so a one-process image is the better fit anyway.

Migrating from the old base image
# Old: FROM tiangolo/uvicorn-gunicorn-fastapi:python3.9 (workers chosen by the image, app in /app)
FROM python:3.13-slim
WORKDIR /code
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY ./app /code/app
CMD ["fastapi", "run", "app/main.py", "--port", "8000", "--proxy-headers"]
# Several workers on one machine: add "--workers", "4" to the CMD list.

Source: FastAPI: FastAPI in Containers - Docker

The migration list: replace the image’s worker-count environment variables with an explicit --workers; replace its configuration files with settings read from the environment; move its /app/app/main.py convention to your own layout; and add the health endpoints, signals and non-root user from this page, which the old image did not give you.

Where Older Guides Are Outdated, and What Changed Recently

  • The base image. tiangolo/uvicorn-gunicorn-fastapi is deprecated in the official documentation; older guides still recommend it. See The Deprecated tiangolo/uvicorn-gunicorn-fastapi Image.

  • Gunicorn as the process manager. Guides that put Gunicorn in front of every container predate Uvicorn’s own worker supervision. --workers on fastapi run or uvicorn now covers it; if you still want Gunicorn, Uvicorn’s documentation deprecates its bundled uvicorn.workers module in favour of the uvicorn-worker package.

  • CMD and the CLI. Before the fastapi command (0.111.0, 2024-05-03) containers ran uvicorn main:app --host 0.0.0.0 --port 80. The current documentation uses fastapi run, which listens on 0.0.0.0 by default and detects the app. Plain uvicorn remains valid and is needed for options such as --timeout-graceful-shutdown.

  • pip install fastapi is not enough. Since 0.112.0 (2024-08-02) the CLI, Uvicorn and the other defaults come with fastapi[standard]; the older fastapi-slim package was deprecated and then dropped (0.129.2, 0.128.8, February 2026), so use fastapi or one of the extras (standard, standard-no-fastapi-cloud-cli, opentelemetry, all).

  • Python versions in Dockerfiles. The documentation’s Dockerfile now uses Python 3.14, while many guides still show 3.8 or 3.9. FastAPI dropped 3.8 (0.125.0) and 3.9 (0.129.0), so a base image older than 3.10 can no longer install current FastAPI. Python 3.14 is supported since 0.118.3, and free-threaded 3.14t since 0.136.0.

  • Pydantic v1 images. An image pinned to Pydantic v1 cannot run current FastAPI: Pydantic v1 support was dropped in 0.126.0 (2025-12-20) and pydantic.v1 in 0.128.0 (2025-12-27).

  • Dependency management in the docs. The documentation now uses uv projects by default (0.140.0, 2026-07-24) and shows uv export for the pip-based Dockerfile; guides that only show pip install -r requirements.txt are not wrong, but miss the locked workflow.

  • PostgreSQL 18 volume path. Compose examples that mount /var/lib/postgresql/data predate PostgreSQL 18, whose image declares /var/lib/postgresql as the volume.

  • on_event and shutdown. Guides that rely on @app.on_event("shutdown") for cleanup should use the lifespan, which is what the log in this page shows running (see Deprecated on_event).

  • Healthchecks in images. Old guides used the Docker HEALTHCHECK instruction as the only health signal; Kubernetes ignores it and uses its own probes, so the application endpoints, not the Dockerfile, are the portable part.

  • Native OpenTelemetry (0.142.0, 2026-09-29). FastAPI can emit traces itself, and its opentelemetry extra is part of standard; tracing configuration is passed to containers through environment variables (see What’s Changed & Migration).

Pitfalls

  • Shell-form CMD. The container takes ten seconds to stop (Docker’s default timeout) and the lifespan shutdown never runs. Use the exec form; end wrapper scripts with exec.

  • localhost inside a container. A server bound to 127.0.0.1 is unreachable from outside; fastapi run binds 0.0.0.0 already, fastapi dev does not. Likewise localhost in a database URL means the API’s own container, not the db service: use the service name.

  • Copying code before installing dependencies. Every edit reinstalls every package. Copy requirements.txt (or pyproject.toml and uv.lock) first.

  • No .dockerignore. The build context contains .git, a local .venv (platform specific, and it breaks the image) and .env files with secrets.

  • Secrets in the image or in Compose YAML. Anything in a layer or a manifest in version control is a leak. Use secret files or the platform’s secret store, and read them through pydantic-settings.

  • depends_on without a condition. It waits for the container to start, not for PostgreSQL to accept connections.

  • Migrations in every replica. Several pods or workers running alembic upgrade head at once can collide. Run a Job or a one-shot Compose service.

  • A database check in the liveness probe. A database outage then restarts every pod. Put dependency checks in readiness only.

  • Probe timing. A readiness timeoutSeconds shorter than a slow endpoint’s response while the loop is busy makes a healthy pod flap in and out of the Service; use a startup probe for slow starts instead of a long liveness delay.

  • --workers plus replicas. Four workers in each of five pods is twenty processes, twenty pools of connections, and memory limits that must cover four copies of the app.

  • A CPU limit that throttles. A hard CPU limit can add latency to an async server; start with requests and measure before adding limits.

  • Trusting every proxy. --forwarded-allow-ips "*" on a container that is also reachable without the proxy lets clients forge their address and scheme.

  • latest tags. image: …​:latest makes a rollout irreproducible and a rollback impossible; tag by version or digest, and pin FastAPI itself (fastapi==0.142.2) because it is still 0.x.

  • Running as root. The official example does; production images should not. A non-root user needs a port above 1023 and readable secret files.

  • Slim images without a compiler. A dependency that needs building fails on python:*-slim; use a binary wheel, or build in a multi-stage build.

  • No curl in the image for the Docker healthcheck. Slim images do not include it; use Python’s standard library, as shown, or rely on the orchestrator’s probes.

  • Docker build verification. The Dockerfiles and manifests of this page were not built or applied in this environment; build the image and run docker compose up once, and kubectl apply --dry-run=server against your cluster, before relying on them.
