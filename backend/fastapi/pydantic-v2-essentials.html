Pydantic v2 Essentials

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against FastAPI 0.142.2 (released 2026-09-30), Pydantic 2.13 (2.13.5, released 2026-08-28) and Starlette 1.7, checked on 2026-10-02. Every example was executed on Python 3.13 with those versions through FastAPI’s TestClient (or with plain Pydantic where FastAPI is not involved); the printed output shown after an example is what that run produced. FastAPI does not validate anything itself: every request parameter, every body and every response goes through Pydantic, so the quality of your API is largely the quality of your Pydantic models. This page explains the Pydantic features you meet in FastAPI work, shows the effect each has on the 422 response and on the OpenAPI document, and ends with the table that maps Pydantic v1 code (the style of most books and tutorials written before mid-2023) to v2.

What Pydantic Does in FastAPI

FastAPI inspects the signature of a path operation function and, for every parameter, decides where the value comes from (path, query, header, cookie, body, form) and what type it must have. The second half is delegated entirely to Pydantic, whose validation engine (pydantic-core) is written in Rust. The division of work is:

Table 1. Who does what in a request
Layer Responsibility

Starlette

Receives the ASGI request, exposes headers, cookies, query string and the raw body, and builds the response.

FastAPI

Reads the function signature, extracts each value from the right place of the request, checks the Content-Type, decodes JSON, calls Pydantic, collects all errors into one RequestValidationError (422), calls your function, validates the return value against the response model and generates the OpenAPI document.

Pydantic

Coerces and validates values against the declared types and constraints, runs your validators, builds the model instance, serializes models back to JSON-compatible data and produces the JSON Schema that FastAPI embeds in OpenAPI.

Everything on this page therefore applies to all parameter kinds, not only to JSON bodies: Query(), Path(), Header(), Cookie(), Form() and Body() accept the same constraint arguments as Field(), and a Pydantic model can describe a group of query parameters, headers, cookies or form fields (see Query Parameters, Headers & Cookies and Forms & File Uploads). The way request bodies are declared, nested and documented is the subject of Request Body & Models; this page covers the Pydantic machinery underneath. Pydantic is a separate project with its own version number; FastAPI 0.142 requires pydantic>=2.9.0 and does not support Pydantic v1 any more (see Migrating from Pydantic v1 to v2).

Models and Fields

A Pydantic model is a class that inherits from BaseModel; each annotated attribute is a field. The annotation is the validation rule, a default value makes the field optional, and a field without a default is required:

from datetime import date

from fastapi import FastAPI
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field


class Author(BaseModel):
    name: str                                   # required
    born: date | None = None                    # optional, may be None
    tags: list[str] = Field(default_factory=list)   # fresh list per instance


app = FastAPI()


@app.post("/authors")
def create_author(author: Author) -> Author:
    return author


c = TestClient(app)
print(c.post("/authors", json={"name": "Ursula", "born": "1929-10-21"}).json())
print(c.post("/authors", json={"born": "1929-10-21"}).json()["detail"][0])

# Models are keyword-only; positional arguments raise TypeError
try:
    Author("Ursula")
except TypeError as exc:
    print("TypeError:", exc)

a = Author(name="Ursula")
print(a.model_fields_set, a.tags is Author(name="X").tags)
print(Author.model_fields["name"].is_required(), Author.model_fields["born"].is_required())

TypeError: BaseModel.__init__() takes 1 positional argument but 2 were given
{'name'} False

The points worth noticing:

  • Required versus nullable are independent. born: date | None = None is optional and nullable. name: str | None without a default is required (the client must send the key, possibly as null) — this is a behaviour change from v1, see Migrating from Pydantic v1 to v2.

  • Mutable defaults are safe. Pydantic copies defaults, so tags: list[str] = [] would not be shared between instances either, but Field(default_factory=list) states the intent explicitly and is required for defaults that must be computed per instance (for example default_factory=datetime.now).

  • Models are keyword-only. Author("Ursula") is a TypeError; write Author(name="Ursula"). In FastAPI you rarely construct models by hand, but the rule matters in tests and in code that maps database rows to models.

  • model_fields_set remembers what was provided. This is how exclude_unset=True and PATCH-style updates work (see Serialization).

  • Models validate on construction only. Assigning a.name = 5 later does not validate unless you enable validate_assignment (see Model Configuration: model_config).

The type annotations accepted are everything Python’s typing module offers plus Pydantic’s own types: str, int, float, bool, bytes, Decimal, UUID, date, datetime, time, timedelta, Enum, Literal, list, set, frozenset, tuple, dict, unions with |, nested models, TypedDict, dataclasses and the specialised types in pydantic.types (HttpUrl, EmailStr, SecretStr, PositiveInt, AwareDatetime, Json and so on). The meaning of X | None and Annotated is explained in Python Types & Annotated.

Field Types and Constraints

Field() attaches constraints and metadata to a field. It works as a default (x: int = Field(ge=1)) or, preferably in FastAPI code, inside Annotated (x: Annotated[int, Field(ge=1)] = 1), which keeps the real default value in the usual place and lets you reuse the annotated type (see Constraints with Annotated). The arguments of Field() in Pydantic 2.13, grouped:

Table 2. Arguments of Field()

Defaults

default, default_factory, validate_default

The value used when the key is missing. A default is not validated unless validate_default=True.

Numbers

gt, ge, lt, le, multiple_of, allow_inf_nan, max_digits, decimal_places

Bounds and shape of int, float and Decimal values. max_digits and decimal_places apply to Decimal.

Sizes

min_length, max_length

Length of str, bytes, list, set, tuple, dict and other sized values. (v1’s min_items and max_items are gone.)

Strings

A regular expression the string must match (v1’s regex).

Strictness

strict, coerce_numbers_to_str

Per-field switch between strict and lax coercion, and permission to accept numbers for str fields (see Strict vs Lax Validation).

Unions

union_mode, discriminator

smart (default) or left_to_right matching, and discriminated unions on a tag field.

Names

The external name of the field (see Computed Fields and Aliases).

Documentation

The next example combines the numeric, string and size constraints in one model and shows both the 422 details and the fragment of the OpenAPI schema that results:

from decimal import Decimal
from typing import Annotated

from fastapi import FastAPI
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field, StringConstraints

Isbn = Annotated[str, StringConstraints(pattern=r"^\d{13}$")]
Rating = Annotated[int, Field(ge=1, le=5, description="Stars, 1 to 5")]
Slug = Annotated[str, StringConstraints(strip_whitespace=True, to_lower=True, min_length=3, max_length=40)]


class Book(BaseModel):
    isbn: Isbn
    slug: Slug
    price: Annotated[Decimal, Field(gt=0, max_digits=6, decimal_places=2)]
    pages: Annotated[int, Field(gt=0, multiple_of=1)] = 100
    keywords: Annotated[list[str], Field(min_length=1, max_length=5)] = ["new"]
    rating: Rating | None = None


app = FastAPI()


@app.post("/books")
def create_book(book: Book) -> Book:
    return book


c = TestClient(app)
ok = {"isbn": "9780441172719", "slug": "  DUNE ", "price": "9.99"}
print(c.post("/books", json=ok).json())
bad = {"isbn": "12", "slug": "x", "price": "1.234", "keywords": [], "rating": 9}
for e in c.post("/books", json=bad).json()["detail"]:
    print(e["loc"], e["type"], e["msg"])
schemas = c.get("/openapi.json").json()["components"]["schemas"]
print(list(schemas))
schema = schemas["Book-Input"]["properties"]
for k in ("isbn", "slug", "price", "rating"):
    print(k, schema[k])

  • StringConstraints(strip_whitespace=True, to_lower=True) transformed the value (" DUNE " became "dune") before the length check ran, so constraints are not only checks but can normalise input.

  • Every violation is reported at once, each with a type that identifies the rule (string_pattern_mismatch, string_too_short, decimal_max_places, too_short, less_than_equal) and a human-readable msg.

Constraints with Annotated

Annotated[T, metadata…​] attaches Pydantic metadata to a type without changing the type seen by static checkers. Four kinds of metadata are common:

  • Field(…​), for any of the arguments above;

  • StringConstraints(…​), a bundle of string rules (strip_whitespace, to_lower, to_upper, min_length, max_length, pattern) that also transforms the value;

  • annotated-types constraints (Gt, Ge, Lt, Le, MinLen, MaxLen), used by libraries and by Pydantic internally;

  • validator markers (AfterValidator, BeforeValidator, WrapValidator, PlainValidator), see Validators.

Because metadata travels with the type, define an alias once and reuse it everywhere. The Isbn, Rating and Slug aliases in the previous example are exactly that, and the same pattern works for query parameters, which is how a team keeps limit, offset or slug rules identical across routes. Two consequences matter when you migrate from v1:

  • The v1 constrained types (conint, constr, conlist, confloat) still exist but are discouraged; their arguments were renamed (conlist(int, min_length=1), not min_items=1). The Annotated spelling replaces them.

  • Constraints do not reach inside containers. isbns: list[str] = Field(pattern=…​) is an error in v2, because pattern applies to the list, not to its items. Put the constraint on the item type: list[Annotated[str, Field(pattern=…​)]] (verified in Migrating from Pydantic v1 to v2).

Validators

Constraints cover common rules; validators are Python functions for the rest. There are two decorators and four Annotated markers:

Table 3. Validator mode: when it runs and what it receives
Mode Runs Receives

after (default)

After Pydantic’s own validation of the field

The validated value, of the declared type. Use this unless you have a reason not to.

before

Before Pydantic’s validation

The raw input, of any type (a str, a dict, None…​). Use it to normalise input, so check isinstance.

wrap

Around Pydantic’s validation

The raw input and a handler that runs the inner validation; you can catch its error or post-process its result.

plain

Instead of Pydantic’s validation

The raw input; no coercion or constraint is applied afterwards. Also changes the field’s JSON Schema, which becomes empty unless you add one.

@field_validator("a", "b", mode=…​) validates one or more fields ("" means all). It must sit *above @classmethod, return the (possibly changed) value and may take a ValidationInfo second argument, whose data holds the previously validated fields (fields are validated in declaration order, so a validator can only compare with fields declared before it) and whose field_name names the field. @model_validator(mode="before" | "after" | "wrap") validates the whole model: before receives the raw input (a classmethod), after receives the finished instance and must return it, and is the place for rules that span several fields.

from typing import Annotated, Any

from fastapi import FastAPI
from fastapi.testclient import TestClient
from pydantic import (AfterValidator, BaseModel, BeforeValidator, ValidationInfo,
                      field_validator, model_validator)


def strip_title(v: str) -> str:
    return v.strip()


Title = Annotated[str, BeforeValidator(lambda v: v.strip() if isinstance(v, str) else v),
                  AfterValidator(str.title)]


class Review(BaseModel):
    book_id: int
    title: Title
    stars: int
    min_stars_for_blurb: int = 4
    blurb: str | None = None

    @field_validator("stars")
    @classmethod
    def stars_in_range(cls, v: int) -> int:
        if not 1 <= v <= 5:
            raise ValueError("stars must be between 1 and 5")
        return v

    @field_validator("blurb", mode="before")
    @classmethod
    def empty_blurb_is_none(cls, v: Any) -> Any:
        return None if v == "" else v

    @field_validator("title")
    @classmethod
    def title_not_shouting(cls, v: str, info: ValidationInfo) -> str:
        if "spoiler" in v.lower():
            raise ValueError(f"{info.field_name} must not contain spoilers")
        return v

    @model_validator(mode="after")
    def blurb_needs_stars(self) -> "Review":
        if self.blurb and self.stars < self.min_stars_for_blurb:
            raise ValueError("a blurb is only accepted with 4 or 5 stars")
        return self


app = FastAPI()


@app.post("/reviews")
def create_review(review: Review) -> Review:
    return review


c = TestClient(app)
print(c.post("/reviews", json={"book_id": 1, "title": "  a good read ", "stars": 5, "blurb": ""}).json())
r = c.post("/reviews", json={"book_id": 1, "title": "x", "stars": 9})
print(r.status_code, r.json())
r = c.post("/reviews", json={"book_id": 1, "title": "x", "stars": 2, "blurb": "meh"})
print(r.status_code, r.json())
r = c.post("/reviews", json={"book_id": 1, "title": "Spoiler alert", "stars": 3})
print(r.json()["detail"][0])

Three details in that output deserve attention. First, the Title alias combined a BeforeValidator and an AfterValidator in Annotated, so the normalisation is reusable and visible in the type. Second, the model-level error has loc ["body"] (the whole model), whereas field errors have ["body", "stars"]. Third, ctx is {"error": {}}: Pydantic puts the exception object in the context, and FastAPI’s JSON encoder renders an exception as an empty object. The useful information is in msg; do not rely on ctx.error.

The modes that change what validation does are best seen side by side:

from typing import Any

from pydantic import BaseModel, ValidationError, ValidatorFunctionWrapHandler, field_validator


class Shelf(BaseModel):
    name: str
    capacity: int
    tags: list[str] = []

    # one validator for several fields
    @field_validator("name", "capacity", mode="before")
    @classmethod
    def no_blank(cls, v: Any) -> Any:
        if isinstance(v, str) and not v.strip():
            raise ValueError("must not be blank")
        return v

    # wrap: runs around the inner validation, can recover from failure
    @field_validator("capacity", mode="wrap")
    @classmethod
    def clamp(cls, v: Any, handler: ValidatorFunctionWrapHandler) -> int:
        try:
            return handler(v)
        except ValidationError:
            return 0

    # plain: replaces the built-in validation completely
    @field_validator("tags", mode="plain")
    @classmethod
    def split_tags(cls, v: Any) -> list[str]:
        return [t.strip() for t in v.split(",")] if isinstance(v, str) else list(v)


print(Shelf(name="Sci-fi", capacity="12", tags="a, b ,c"))
print(Shelf(name="Sci-fi", capacity="many"))
try:
    Shelf(name=" ", capacity=1)
except ValidationError as e:
    print(e.errors(include_url=False)[0]["msg"])

Rules for the exceptions a validator may raise:

  • Raise ValueError (the error type is value_error and msg starts with Value error, `) or `AssertionError (assertion_error). Asserts are removed when Python runs with -O, so prefer ValueError for real rules.

  • Do not raise HTTPException from a validator: a validator also runs when your own code builds the model, and validators of a request model run before your function does, so the framework must be able to collect the problem into the 422 response.

  • To control the error type, msg and ctx yourself, raise pydantic_core.PydanticCustomError(type, message_template, context).

from typing import Annotated

from fastapi import FastAPI
from fastapi.testclient import TestClient
from pydantic import AfterValidator, BaseModel, ValidationInfo, field_validator
from pydantic_core import PydanticCustomError


def isbn_checksum(v: str) -> str:
    digits = [int(c) for c in v]
    if sum(d * (1 if i % 2 == 0 else 3) for i, d in enumerate(digits)) % 10 != 0:
        raise PydanticCustomError("isbn_checksum", "ISBN-13 check digit is wrong: {isbn}", {"isbn": v})
    return v


Isbn13 = Annotated[str, AfterValidator(isbn_checksum)]


class Password(BaseModel):
    password: str
    confirm: str

    @field_validator("confirm")
    @classmethod
    def same(cls, v: str, info: ValidationInfo) -> str:
        assert v == info.data.get("password"), "passwords differ"     # AssertionError works too
        return v


class Book(BaseModel):
    isbn: Isbn13


app = FastAPI()


@app.post("/books")
def book(b: Book) -> Book:
    return b


@app.post("/passwords")
def pw(p: Password) -> dict:
    return {"ok": True}


c = TestClient(app)
print(c.post("/books", json={"isbn": "9780441172710"}).json()["detail"])
print(c.post("/passwords", json={"password": "a", "confirm": "b"}).json()["detail"])

Model Configuration: model_config

Behaviour that applies to a whole model is configured with model_config = ConfigDict(…​). (The v1 inner class Config: still works in v2 but emits a deprecation warning; see Migrating from Pydantic v1 to v2.) The options you will actually use in a FastAPI project:

Several of these are worth a closer look in FastAPI context:

  • extra="forbid" and the OpenAPI document. It adds additionalProperties: false to the schema, so generated clients and Swagger UI treat unknown keys as errors too. The default (ignore) silently drops unknown keys, which hides client typos such as titel.

Computed Fields and Aliases

@computed_field on a @property adds a derived value to the serialized output (and to the output JSON Schema) without storing it as an input field. Strict vs Lax Validation

By default Pydantic validates in lax mode: it converts input to the target type when that is sensible and unambiguous ("412" to 412, "yes" to True, an ISO string to a date). In strict mode a value must already have the right type. This matters in FastAPI because the two ends of the pipe differ:

  • Query, path, header, cookie and form values are always text, so strict mode on such a parameter rejects everything that is not a str. It is rarely what you want there.

  • JSON bodies have a few native types (string, number, boolean, null, array, object). FastAPI validates the decoded JSON in lax mode, so {"pages": "412"} is accepted for an int field unless you opt into strictness.

The Structure of a 422

When validation of any parameter or body fails, FastAPI does not call your function. It raises RequestValidationError and its default handler answers 422 Unprocessable Content with a JSON object whose detail is the list of Pydantic errors, all of them (not only the first), each from every source (path, query, header, cookie, body):

curl -s -X POST localhost:8000/reviews \
  -H 'Content-Type: application/json' \
  -d '{"stars": 9, "text": "ok"}'
{"detail":[{"type":"less_than_equal","loc":["body","stars"],"msg":"Input should be less than or equal to 5","input":9,"ctx":{"le":5}},{"type":"string_too_short","loc":["body","text"],"msg":"String should have at least 3 characters","input":"ok","ctx":{"min_length":3}}]}

Migrating from Pydantic v1 to v2

Pydantic 2.0 was released on 2023-06-30; code written for v1 (including the code in books and tutorials from 2021 and 2022) does not run unchanged. FastAPI supported both major versions side by side for a long period and has now dropped v1 entirely (timeline below), so any project still on v1 must migrate to move past FastAPI 0.125. The official migration guide is the authoritative reference; this section is a field guide verified against the installed versions.

Behaviour Changes That Do Not Raise

The renames above fail loudly. These changes keep running and give different results, so check each in your own code and tests:

  • Optional[X] without a default is required. A v1 model in which clients could omit the key now answers 422 missing for that key (the required_nullable line of the output). Add = None.

  • No more number-to-string coercion. Num(s=5) is string_type in v2, where v1 produced "5". Opt back in with coerce_numbers_to_str=True (model or field), or fix the client.

  • Smart unions. str | int and int | str both keep "1" as a string in v2 because the input already matches a member; v1 tried members from left to right and converted. Use Field(union_mode="left_to_right") for the old behaviour and discriminated unions (discriminator=) for tagged data.

  • Defaults. A v1 @validator(always=True) ran only your function on a default. In v2 the same effect needs Field(validate_default=True), and it validates the default against the type too, so a default of the wrong type (x: str = 1) now fails.

  • Dicts from pairs. Iterables of pairs no longer validate as dict.

  • Subclass serialization writes only the declared type’s fields (see Serialization).

  • Models are not equal to dicts, parse_obj copies input and construct/model_construct do not validate.

  • Dataclasses. Tuples are no longer accepted as input for dataclass fields, post_init runs after validation, extra="allow" is unsupported and pydantic_model is gone (wrap the dataclass in a TypeAdapter for validation and schemas).

  • JSON Schema of Optional fields now says null is allowed (anyOf with {"type": "null"}), which changes generated OpenAPI clients.

  • Error output differs, as discussed in The Structure of a 422.

  • Models are keyword-only: positional construction is a TypeError.

Automating It with bump-pydantic

The Pydantic team maintains a code-transformation tool, bump-pydantic, that rewrites most v1 idioms in a package. It is a command-line tool installed with pip install bump-pydantic (latest release on PyPI: 0.8.0, 2023-12-28; the official migration guide still calls it beta). Run it on a clean git work tree, from the repository root, pointing at the package directory:

pip install bump-pydantic
cd /path/to/repository
bump-pydantic --diff my_package   # preview the changes
bump-pydantic my_package          # apply them

Source: GitHub: pydantic/bump-pydantic

The tool applies a fixed list of rules (BP001 to BP009): add the default None to Optional[T] fields, replace Config classes by model_config, rename old Field parameters, replace moved imports, replace GenericModel and root, replace validator decorators, replace the con* functions by Annotated, and mark Pydantic "protocol" methods of custom types with TODO comments. Individual rules can be disabled from the command line. FastAPI’s own guide recommends tests, then bump-pydantic, then the tests again. A practical order for an existing application:

  1. Make sure the application has tests and runs them in CI.

  2. Run bump-pydantic and review the diff.

  3. Run the tests, fix what remains by hand, using the tables above.

  4. Upgrade FastAPI to the current release; remember that the response bodies of validation errors changed shape.

Do not skip the review: the tool transforms syntax, not meaning, so the behaviour changes listed in the previous section still need human attention, in particular smart unions, number coercion and Optional fields that must stay optional.

Where Older Guides Are Outdated, and What Changed Recently

  • Pydantic v1 code (.dict(), class Config, orm_mode, @validator, regex=, min_items, Field(…​) for required fields, value_error.missing error types) is the style used by most FastAPI material written before mid-2023, including popular books. Map it with the tables in Migrating from Pydantic v1 to v2; the models in this section never use it.

  • Optional[X] is still sometimes presented as "optional parameter". It only says the value may be None.

  • pydantic.v1 is not a way to keep old code running any more: FastAPI stopped supporting it in 0.128.0 (2025-12-27), and Python 3.14 is unsupported by it.

  • 0.115.0 (2024-09-17) added Pydantic models for Query, Header and Cookie parameters and 0.113.0 (2024-09-05) for Form; both accept extra="forbid".

  • 0.100.0 (2023-07-07) introduced Pydantic v2 support; 0.102.0 (2023-08-25) added separate input and output schemas; 0.99.0 (2023-06-30) switched OpenAPI to 3.1 and JSON Schema 2020-12 (examples instead of example).

  • 0.130.0 (2026-02-22) serializes responses with Pydantic’s Rust JSON serializer when a return type or response model is declared, which is faster than building Python dictionaries first; see Response Models & Return Types.

  • 0.128.2 (2026-02-05) added support for TypeAliasType (PEP 695 type aliases) in annotations, so reusable constraint aliases can use the type statement on Python 3.12 and later.

  • Pydantic 2.11 (2025-03-27) introduced validate_by_name, validate_by_alias and serialize_by_alias.

  • The migration of the book’s era is summarised for the whole framework in What’s Changed & Migration.

Pitfalls

  • Optional is not "optional". str | None without = None is required. The OpenAPI required list and the 422 missing error show it.

  • Validators raise ValueError, not HTTPException. Validators run outside the HTTP layer; map errors to HTTP at the boundary.

  • ctx.error is empty. Exceptions raised in validators appear as {} in ctx; put the information in the message.

  • Echoed input. 422 bodies repeat input, including passwords and tokens. hide_input_in_errors=True in model_config does not hide it in FastAPI’s response (verified above); strip input (and ctx) in a RequestValidationError handler.

  • Strict query parameters. Query(strict=True) rejects everything, because query values are strings.

  • Constraints on containers. Field(pattern=…​) on a list[str] does not constrain the items; use list[Annotated[str, Field(…​)]].

  • Default values are not validated. x: int = "7" stays the string "7" unless validate_default=True.

  • Mutable models. A model is mutable and not validated on assignment by default; frozen=True prevents assignment but does not freeze nested lists.

  • model_construct and model_copy(update=) skip validation, so never use them on untrusted data.

  • Handlers registered late. An exception handler added after the app served its first request (as the TestClient does) is ignored; register handlers at start-up.

  • Validators that depend on field order. info.data only contains fields declared earlier and fields that passed validation, so a failed password leaves no info.data["password"].

  • Side effects in validators. They can run again when a response is validated (see The Validation Flow).

  • Responses leak by default. Without a response model, everything you return is serialized. Declare → BookOut or response_model= for any model that holds secrets.

  • PlainValidator hides the type from OpenAPI. Provide a schema or description.

  • Serialization of subclasses. Only fields of the declared type are written; use polymorphic_serialization or serialize_as_any deliberately.
