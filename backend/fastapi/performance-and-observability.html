Most slow services are slow for one reason: a blocked event loop, an N+1 query, a missing index, or a payload that is simply too large. Guessing is expensive, so the order of work on this page is the order of work in a real project:

Async Correctness

The first rule is in Async & Concurrency: an async def path operation runs on the event loop, and anything that blocks it blocks every request in the process. A path operation declared with plain def is run in a threadpool instead, so a blocking call there only occupies a thread. The example below sends ten concurrent requests to four versions of the same 100 ms operation through `httpx’s ASGI transport:

import asyncio
import time

import httpx
from fastapi import FastAPI

app = FastAPI(title="Bookshelf API")


@app.get("/slow-blocking")
async def slow_blocking() -> dict[str, str]:
    time.sleep(0.1)  # blocks the event loop: nothing else runs
    return {"how": "time.sleep inside async def"}


@app.get("/slow-await")
async def slow_await() -> dict[str, str]:
    await asyncio.sleep(0.1)  # yields to the loop
    return {"how": "await asyncio.sleep"}


@app.get("/slow-offloaded")
async def slow_offloaded() -> dict[str, str]:
    await asyncio.to_thread(time.sleep, 0.1)  # blocking call moved to a thread
    return {"how": "asyncio.to_thread"}


@app.get("/slow-def")
def slow_def() -> dict[str, str]:
    time.sleep(0.1)  # plain def: FastAPI runs it in the threadpool
    return {"how": "def runs in the threadpool"}


async def burst(path: str, n: int = 10) -> float:
    transport = httpx.ASGITransport(app=app)
    async with httpx.AsyncClient(transport=transport, base_url="http://test") as c:
        start = time.perf_counter()
        responses = await asyncio.gather(*(c.get(path) for _ in range(n)))
        assert all(r.status_code == 200 for r in responses)
        return time.perf_counter() - start


async def main() -> None:
    for path in ("/slow-blocking", "/slow-await", "/slow-offloaded", "/slow-def"):
        print(f"{path:16} 10 concurrent requests: {await burst(path):.2f}s")


asyncio.run(main())

Source: FastAPI: Concurrency and async / await

/slow-blocking   10 concurrent requests: 1.08s
/slow-await      10 concurrent requests: 0.10s
/slow-offloaded  10 concurrent requests: 0.11s
/slow-def        10 concurrent requests: 0.13s

The blocking async def took ten times as long, because the ten requests ran one after the other; the other three overlapped. The checklist that follows from this:

  • Inside async def, use an async library (httpx.AsyncClient, an async database driver, redis.asyncio) and await it. This is the fastest option.

  • If a library only has a blocking API, either declare the path operation with def or move the single call into a thread with asyncio.to_thread() (as /slow-offloaded does).

  • CPU-bound work (image processing, large data transformations, password hashing) is not helped by threads under the global interpreter lock; move it to a process pool or a job queue, as the async page explains.

  • Do not put time.sleep(), a synchronous HTTP client, or a synchronous database session in an async def path operation or in an async def dependency. A synchronous call in a dependency declared with def is fine.

  • A forgotten await does not block, it silently skips the work and returns a coroutine object; the async page shows the symptom.

  • The threadpool is finite (40 threads by default), so a def endpoint that is slow because of a slow remote service can still exhaust it under load; that page shows how to tune the limit.

Pydantic Serialization

FastAPI validates what you return and turns it into JSON using the return type annotation or response_model, and since 0.130.0 (2026-02-22) that JSON is produced directly by Pydantic’s Rust core, without going through Python objects first. The FastAPI documentation says so itself: Pydantic is written in Rust, "so it will be much faster". The example serves 5000 books three ways and measures each:

import timeit
from typing import Annotated

from fastapi import FastAPI, Response
from fastapi.encoders import jsonable_encoder
from fastapi.responses import JSONResponse
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field, TypeAdapter

app = FastAPI(title="Bookshelf API")


class BookPublic(BaseModel):
    id: int
    title: str
    isbn: str
    pages: Annotated[int, Field(ge=1)]
    authors: list[str]


ROWS = [
    {"id": i, "title": f"Book {i}", "isbn": f"978-{i:010d}", "pages": 300, "authors": ["A. Writer", "B. Author"]}

The Pydantic documentation has a list of performance tips for your own models. Four of them matter most in an API, and the example below measures each one:

import json

from pydantic import BaseModel, Field, TypeAdapter
from typing_extensions import TypedDict

    book_id: int

    text: str

print(f"model_validate_json is {two_step / one_step:.1f}x the speed of json.loads + model_validate")


# 2. Build a TypeAdapter once, not inside the function that uses it.
def bad(raw: list[int]) -> list[int]:
    return TypeAdapter(list[int]).validate_python(raw)  # builds a validator on every call


ADAPTER = TypeAdapter(list[int])


def good(raw: list[int]) -> list[int]:
    return ADAPTER.validate_python(raw)


rebuilt = timeit.timeit(lambda: bad([1, 2, 3]), number=2000)
reused = timeit.timeit(lambda: good([1, 2, 3]), number=2000)
print(f"reusing the TypeAdapter is {rebuilt / reused:.0f}x faster")

Caching

The fastest request is the one that does not repeat work. There are three places to cache, with different rules about who may see the result and how it is invalidated.

functools.cache and lru_cache

functools.cache memoizes a synchronous function; lru_cache(maxsize=…​) does the same with a bound on the number of entries (and plain @lru_cache as used in the FastAPI settings recipe). The Bookshelf API below caches the genre list per language, injects a cached settings object, and sets a Cache-Control header for client-side caching. The last block shows the one mistake that cannot be made with async def:

import asyncio

    calls["settings"] += 1
    return Settings()

Redis

When several processes or machines must share a cache, or entries must expire, use Redis. The full cache-aside walk-through, with a lifespan-managed client, hit and miss headers and invalidation on write, is on NoSQL & Other Data Stores; the data-structure side is on this site under Redis Use Cases and Patterns and Architecture, Keyspace and Eviction (what happens when the memory limit is reached). The example below adds the one piece that page leaves out, protection against a burst of identical misses: a per-key lock inside the process makes eight simultaneous requests run the expensive loader once (it was executed with fakeredis, which implements the same async client API):

import asyncio
from concurrent.futures import ThreadPoolExecutor
from collections.abc import AsyncIterator, Awaitable, Callable
from contextlib import asynccontextmanager
from typing import Annotated, TypedDict

    redis: redis.Redis

    # Real deployment: redis.Redis.from_url(settings.redis_url, decode_responses=True)
    client = FakeAsyncRedis(decode_responses=True)
    yield {"redis": client}
    await client.aclose()

def get_redis(request: Request) -> redis.Redis:
    return request.state.redis


Redis = Annotated[redis.Redis, Depends(get_redis)]
_locks: dict[str, asyncio.Lock] = {}
loads = 0


class TopBooks(BaseModel):
    titles: list[str]


async def get_or_load(
    r: redis.Redis, key: str, ttl: int, loader: Callable[[], Awaitable[TopBooks]]
) -> TopBooks:
    cached = await r.get(key)
    if cached is not None:
        return TopBooks.model_validate_json(cached)
    # One in-process lock per key: a burst of identical misses runs the loader once.
    async with _locks.setdefault(key, asyncio.Lock()):
        cached = await r.get(key)  # somebody may have filled it while we waited
        if cached is not None:
            return TopBooks.model_validate_json(cached)
        value = await loader()
        await r.set(key, value.model_dump_json(), ex=ttl)
        return value


async def expensive_ranking() -> TopBooks:
    global loads
    loads += 1
    await asyncio.sleep(0.05)  # a slow aggregation query
    return TopBooks(titles=["Dune", "Emma"])


@app.get("/books/top")
async def top_books(r: Redis) -> TopBooks:
    return await get_or_load(r, "top-books:v1", 60, expensive_ranking)


with TestClient(app) as client:

        bodies = list(pool.map(lambda _: client.get("/books/top").json(), range(8)))

The lock only coordinates requests inside one process; with several workers each may load once, which is usually acceptable. The ex=ttl argument gives every entry an expiry so stale data cannot live forever, and the key carries a version (:v1) so a change of the cached shape can be deployed by bumping it. Cache only data that is the same for every caller.

Database: Indexes and N+1

In most APIs the database is the slowest span of a trace. Two mistakes cause most of that.

N+1 Queries

Reading a list of books and then touching a relationship for each one runs one query for the list plus one query per book. The code looks innocent, because the extra queries hide behind attribute access. The example counts the SQL statements for the same endpoint written both ways, using a SQLAlchemy event, and finishes with the query plan SQLite chooses for a lookup of reviews by book:

selectinload(Book.reviews) loads all reviews of all returned books with one extra query, which is why fifty books cost two statements instead of fifty-one. Indexes

An index lets the database find rows without reading the whole table. Index the columns you filter, join and sort by: foreign keys (Field(foreign_key=…​, index=True) above), lookup fields such as an ISBN (unique=True creates a unique index), and the columns of a frequent WHERE …​ ORDER BY. EXPLAIN (spelled EXPLAIN QUERY PLAN in SQLite) shows the difference: SCAN reads the whole table, SEARCH …​ USING INDEX does not. Indexes are not free: every write updates them and they take space, so add them for measured queries, not for every column. Two further habits belong to the same family: never return an unbounded list (use limit and offset or keyset pagination, see the SQLModel page) and select only the columns the endpoint returns. For the database side, see SQL DDL for creating indexes.

Streaming Large Responses

Building a large export in memory costs memory proportional to the response and delays the first byte until the last row is ready. A StreamingResponse over a generator sends it piece by piece. The example below exports 100000 rows as CSV both ways and measures the peak memory of the server side by calling the ASGI app directly and discarding each message as it is sent (the test client would otherwise collect the body itself and hide the difference):

import asyncio
import csv
import io
import tracemalloc
from collections.abc import Iterator

from fastapi import FastAPI, Response
from fastapi.responses import StreamingResponse
from fastapi.testclient import TestClient

app = FastAPI(title="Bookshelf API")
ROWS = 100_000


def book_rows() -> Iterator[tuple[int, str, int]]:
    # Stands in for a database cursor that yields rows in batches.
    for i in range(ROWS):
        yield i, f"Book {i}", 300


@app.get("/export/buffered")
def export_buffered() -> Response:
    buffer = io.StringIO()
    csv.writer(buffer).writerows(book_rows())  # the whole file exists in memory
    return Response(buffer.getvalue(), media_type="text/csv")


@app.get("/export/streamed")
def export_streamed() -> StreamingResponse:
    def generate() -> Iterator[str]:
        buffer = io.StringIO()
        writer = csv.writer(buffer)
        for number, row in enumerate(book_rows(), start=1):
            writer.writerow(row)
            if number % 1000 == 0:  # one chunk per 1000 rows, not one per row
                yield buffer.getvalue()
                buffer.seek(0)
                buffer.truncate(0)
        yield buffer.getvalue()  # the remainder

    return StreamingResponse(
        generate(),
        media_type="text/csv",
        headers={"Content-Disposition": 'attachment; filename="books.csv"'},
    )


async def drive(path: str) -> tuple[int, int]:
    """Call the ASGI app directly and discard each chunk as it is sent."""
    scope = {
        "type": "http", "asgi": {"version": "3.0"}, "http_version": "1.1", "method": "GET",
        "path": path, "raw_path": path.encode(), "query_string": b"", "headers": [],
        "scheme": "http", "server": ("test", 80), "client": ("test", 1), "root_path": "",
    }
    sent = chunks = 0

    first = True

    async def receive():
        nonlocal first
        if first:
            first = False
            return {"type": "http.request", "body": b"", "more_body": False}
        await asyncio.Event().wait()  # no disconnect ever arrives

    async def send(message):
        nonlocal sent, chunks
        if message["type"] == "http.response.body":
            sent += len(message.get("body", b""))
            chunks += 1

    await app(scope, receive, send)
    return sent, chunks


async def main() -> None:
    for path in ("/export/buffered", "/export/streamed"):
        tracemalloc.start()
        sent, chunks = await drive(path)
        peak = tracemalloc.get_traced_memory()[1]
        tracemalloc.stop()
        print(f"{path:18} {sent / 1e6:.1f} MB in {chunks:6} body messages, peak memory {peak / 1e6:.2f} MB")


asyncio.run(main())

with TestClient(app) as client:  # and the download still works end to end
    r = client.get("/export/streamed")
    print(r.status_code, r.headers["content-disposition"], r.text.splitlines()[:2])

Three details matter: the generator is a plain function, so FastAPI iterates it in the threadpool and a blocking database cursor does not block the loop; the chunks are batches of 1000 rows rather than one row each (a message per row wastes time on overhead); and there is no Content-Length, so progress bars cannot show a percentage. Profiling answers "where does the time go in this code". Use the standard library’s cProfile for a deterministic count of calls and a sampling profiler such as pyinstrument for a readable call tree. PyPy, Cython and Rust Extensions

When a profile shows one pure-Python function dominating a CPU-bound endpoint and no algorithmic improvement is left, there are three ways to run Python code faster, in increasing order of effort. This is a brief orientation, not a guide:

  • PyPy is an alternative interpreter with a just-in-time compiler that speeds up long-running pure-Python code without code changes. It cannot load every compiled extension, so check that each of your dependencies (Pydantic’s Rust core, the database driver, the JSON and cryptography libraries) supports it before choosing it; it was not run for this page.

  • Cython compiles Python-like code, with optional C type declarations, to a C extension module you import as usual.

  • Rust extensions are written with PyO3 (Rust bindings for Python) and built and published with maturin; the result is imported like any other module. Pydantic’s validation and serialization core is itself written in Rust, as the FastAPI documentation notes, which is why the earlier sections can stay in Python. Writing such an extension is covered in the Rust Reference’s Python Interop with PyO3.

The Cython example below compiles an ISBN-13 check-digit function and calls it from an endpoint. The build command is python setup.py build_ext --inplace:

Observability: Logs, Metrics and Traces

Observability is being able to ask a running service what it is doing without redeploying it. It rests on three kinds of signal: logs (what happened, as events), metrics (how much and how fast, as numbers aggregated over time) and traces (the path of one request through the code and across services). The following sections add each one to the Bookshelf API.

Logs leave through standard output, metrics are pulled by Prometheus from an HTTP endpoint, and traces are pushed by the application over OTLP, the OpenTelemetry protocol. A request ID ties the three together.

A plain-text log line cannot be filtered or aggregated reliably, so production services log one JSON object per line and attach a request ID to every line. The Uvicorn access line has no place for that ID, so the application writes its own access line from a middleware and the Uvicorn access logger is quietened. The request ID middleware must be pure ASGI and use a ContextVar, for the reasons explained on Middleware, CORS & Proxies. The first file holds the pieces:

observability.py
import json
import logging
import time
import uuid
from contextvars import ContextVar
from datetime import datetime, timezone

from starlette.datastructures import Headers, MutableHeaders
from starlette.types import ASGIApp, Message, Receive, Scope, Send

request_id_var: ContextVar[str] = ContextVar("request_id", default="-")


class RequestIdFilter(logging.Filter):
    """Copies the current request ID onto every record, whichever logger emitted it."""

    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id_var.get()
        return True


class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        payload = {
            "time": datetime.fromtimestamp(record.created, timezone.utc).isoformat(timespec="milliseconds"),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
            "request_id": getattr(record, "request_id", "-"),
        }
        for key in ("method", "path", "status", "duration_ms"):
            if hasattr(record, key):
                payload[key] = getattr(record, key)
        if record.exc_info:
            payload["exception"] = self.formatException(record.exc_info)
        return json.dumps(payload)


access_logger = logging.getLogger("bookshelf.access")


class RequestLogMiddleware:
    """Pure ASGI: assigns the request ID and writes one structured access line per request."""

    def __init__(self, app: ASGIApp) -> None:
        self.app = app

    async def __call__(self, scope: Scope, receive: Receive, send: Send) -> None:
        if scope["type"] != "http":
            await self.app(scope, receive, send)
            return
        request_id = Headers(scope=scope).get("x-request-id") or uuid.uuid4().hex
        token = request_id_var.set(request_id)
        status = 500
        start = time.perf_counter()

        async def send_wrapper(message: Message) -> None:
            nonlocal status
            if message["type"] == "http.response.start":
                status = message["status"]
                MutableHeaders(scope=message)["X-Request-ID"] = request_id
            await send(message)

        try:
            await self.app(scope, receive, send_wrapper)
        finally:
            access_logger.info(
                "request finished",
                extra={
                    "method": scope["method"],
                    "path": scope["path"],  # the path, not the query string: it may hold secrets
                    "status": status,
                    "duration_ms": round((time.perf_counter() - start) * 1000, 2),
                },
            )
            request_id_var.reset(token)

Every line produced while handling a request carries its ID, so one request_id search in a log platform returns the whole story, and the same ID is returned to the client in X-Request-ID for support tickets. Logging rules worth keeping:

  • Log the path, not the query string, and never log request bodies, tokens or passwords; a log is read by many more people than the database.

  • Log in the application’s own logger hierarchy (bookshelf.*) so levels can be set per area.

  • Log exceptions with logger.exception() or exc_info=True; the formatter above turns the traceback into one JSON field.

  • A logging call that formats a large object costs time even when the level is off; pass arguments instead of f-strings for expensive values.

  • Trust a client-supplied request ID only for correlation; a proxy that generates the ID itself is a better source.

Notice what the example configured:

  • handler is the route template (/books/{book_id}), not the concrete URL. Labels with unbounded values (user IDs, concrete paths, ISBNs) create one time series each and exhaust Prometheus' memory; this is called a cardinality explosion. should_ignore_untemplated=True drops requests that match no route, so a scanner probing random URLs adds no series. The default groups them under the handler none.

  • should_group_status_codes=True (the default) records 2xx instead of every code.

  • excluded_handlers takes regular expressions for paths to skip, such as /metrics and health checks.

  • Other options of the constructor include should_instrument_requests_inprogress, should_respect_env_var (only instrument when an environment variable, ENABLE_METRICS by default, is true), should_exclude_streaming_duration, round_latency_decimals and a custom registry.

  • The custom metric bookshelf_reviews_created_total comes straight from prometheus_client. Name counters with a _total suffix and keep labels to a handful of known values (the rating, not the review text).

OpenTelemetry

OpenTelemetry is a vendor-neutral set of standards and libraries for emitting traces, metrics and logs and sending them over OTLP to a collector or a monitoring service. Traces answer the question metrics cannot: which step of this one slow request was slow. A trace is a tree of timed operations called spans, and the root span is the HTTP request.

Native Support (FastAPI 0.142.0)

Release 0.142.0 (2026-09-29) added native OpenTelemetry support, and the FastAPI documentation now has an OpenTelemetry page. Per that page, FastAPI emits traces, metrics and logs for HTTP requests by default, and traces and logs for WebSocket connections; no custom code is needed, you only configure where the data goes. The fastapi[standard] extra contains the packages for sending telemetry (the opentelemetry extra is the smaller alternative), and FastAPI Cloud shows the metrics automatically. Compared with the native support, the contrib package has no spans for dependencies, the endpoint or serialization. If both are active, the two do not duplicate each other: in a run with a native tracer_provider configured and the contrib instrumentation applied, only the contrib spans appeared, and 0.142.2’s source checks for that middleware and then disables its own tracing, metrics and logs. This is an implementation detail that the documentation does not state, so do not rely on it; choose one.

Where Older Guides Are Outdated, and What Changed Recently

  • JSON serialization in Rust (0.130.0, 2026-02-22). Guides that recommend ORJSONResponse, UJSONResponse or a hand-written jsonable_encoder step for speed are out of date. Return annotations are serialized by Pydantic’s core, and ORJSONResponse and UJSONResponse were deprecated in 0.131.0 (2026-02-22).

  • @app.on_event("startup") for metrics and clients. The instrumentator’s README still shows on_event as an alternative; lifespan handlers superseded startup and shutdown events in 0.93.0 (2023-03-07), and the module-level instrument(app).expose(app) call used above needs neither.

  • Pydantic v1 performance advice. v1-era tips (orjson config on models, parse_raw) do not apply; use model_validate_json() and a shared TypeAdapter. Pydantic v1 support ended in FastAPI 0.126.0 (2025-12-20).

  • Native OpenTelemetry (0.142.0, 2026-09-29). Tutorials that hand-wire FastAPIInstrumentor and a tracer provider predate it; for a new service FastAPI emits traces, metrics and logs by itself, and 0.142.2 (2026-09-30) made start-up tolerant of a failing automatic configuration. Check the What’s Changed & Migration page for the full list.

  • Dependency exit code runs after the response (0.118.0). Spans and timing measured around a dependency with yield now include its exit code only after the response has been sent; see Dependencies with yield.

  • Free-threaded Python (0.136.0). FastAPI supports Python 3.14t, which changes the advice on CPU-bound threads; the async page covers it and this page’s examples were not run on it.

  • Process managers. Older deployment advice used Gunicorn with Uvicorn workers by default; the FastAPI documentation now shows --workers on fastapi run and uvicorn, and says that on Kubernetes you will probably want one process per container instead. Prometheus multiprocess mode only matters when several workers share one container.

  • Python 3.10 or later. Python 3.8 and 3.9 were dropped (0.125.0 and 0.129.0), so the examples use current syntax (list[str], X | None).

Pitfalls

  • Benchmarking the test client. TestClient runs the app in another thread and measures client overhead too; use it for correctness and use a load tool against a real server (Locust is covered in the testing material of this section) for throughput. Timings here show relative effects only.

  • Optimizing the wrong thing. Rewriting JSON handling while an N+1 dominates is wasted effort; profile or read the trace first.

  • Blocking calls hidden in async def. A synchronous database session, requests, time.sleep or a heavy loop looks fine in development and collapses under concurrent load.

  • Caching coroutines and per-user data. @cache on async def fails on the second call; a cache key that omits the user turns a performance feature into a data leak.

  • Unbounded caches. functools.cache never evicts; a Redis key without ex= never expires.

  • Indexes added blindly. Each index slows writes; confirm with EXPLAIN that the planner uses it.

  • High-cardinality labels. A Prometheus label from a URL, ID or exception message multiplies the series count; use route templates and bounded values.

  • Exposing /metrics and profiling endpoints publicly. Both reveal internals; restrict them at the proxy.

  • Logging secrets and personal data. Logs outlive requests and are shared widely; log identifiers, not bodies.

  • Per-process metrics with several workers. Without multiprocess mode, each scrape sees one worker; the numbers jump around.

  • Instrumenting twice. Configuring the same OTLP destination in two libraries sends every span twice; configure each destination once.

  • Assuming telemetry works because the service starts. Since 0.142.2 a failing automatic OpenTelemetry setup does not stop start-up; verify that data arrives.

  • Trusting a client-supplied X-Request-ID as an identity. It is user input; use it for correlation only and keep it to a sane length if you echo it into logs.
