WebSockets

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against FastAPI 0.142.2 (released 2026-09-30), Pydantic 2.13, Starlette 1.7 and Uvicorn 0.54, checked on 2026-10-02. All examples use Annotated where a parameter needs one, run on Python 3.10 or newer and were executed on Python 3.13: with TestClient where the behaviour can be observed in-process, and against a real Uvicorn server (with the websockets client library and Node.js) where the point is the live connection, such as handshake rejections, unhandled disconnects and shutdown. HTTP is one request, one response. A WebSocket starts as an ordinary HTTP request that asks the server to switch protocols; once the server agrees, the same TCP connection stays open and either side can send messages whenever it likes. That is what a chat room, a live dashboard, collaborative editing or a game needs, and what plain request/response cannot do. FastAPI does not implement the protocol: Uvicorn (or another ASGI server) does, Starlette provides the WebSocket object, and FastAPI adds what it adds everywhere else, parameter extraction, dependencies and validation, to the handshake. For one-way pushes read Streaming, JSON Lines & SSE first; the decision table is repeated in WebSockets, SSE or Polling?. The running scenario is the Bookshelf API from Introduction & Architecture: one chat room per book.

How a WebSocket Session Works

The protocol is RFC 6455. The client sends a GET with Upgrade: websocket and Sec-WebSocket-Key headers; the server answers 101 Switching Protocols; from then on both sides exchange frames (text, binary, ping, pong, close). In ASGI terms the server sends the application a websocket.connect event, the application replies with websocket.accept (or rejects), and after that websocket.receive, websocket.send, websocket.disconnect and websocket.close messages flow. Starlette’s WebSocket hides those messages behind methods such as accept(), receive_text(), send_json() and close().

Install a WebSocket Library

Uvicorn speaks the protocol through the websockets package or the wsproto package, and does not install either by default. pip install "fastapi[standard]" pulls in uvicorn[standard], whose extra includes websockets, so a project created by following Getting Started is already covered. With plain uvicorn or the bare fastapi package, add one explicitly:

pip install "uvicorn[standard]"   # or: pip install websockets

The failure is quiet, which is why it is worth knowing. Started with --ws none (the same situation as having no library), Uvicorn logs No supported WebSocket library detected and treats the upgrade request as an ordinary GET: the client sees a plain 404 instead of a connection (run: websockets.InvalidStatus: server rejected WebSocket connection: HTTP 404). --ws accepts auto (the default), none, websockets, websockets-sansio and wsproto. The websockets-sansio implementation was added in Uvicorn 0.35.0 (June 2025).

The First Endpoint: @app.websocket

A WebSocket route is declared with @app.websocket(path) (or @router.websocket(path) on an APIRouter, prefixes included). The function receives a WebSocket, which FastAPI re-exports from starlette.websockets (from fastapi import WebSocket). Two rules define every handler:

  • Call await websocket.accept() before sending or receiving. Until then the connection is a pending HTTP upgrade; calling close() instead rejects it.

  • Keep the function running. When it returns, FastAPI closes the connection; an async for or while True loop over the incoming messages is the normal shape.

from fastapi import FastAPI, WebSocket
from fastapi.testclient import TestClient

app = FastAPI()


@app.websocket("/ws/echo")
async def echo(websocket: WebSocket) -> None:
    await websocket.accept()
    async for text in websocket.iter_text():  # ends cleanly when the client disconnects
        await websocket.send_text(f"You said: {text}")
    print("client left")


client = TestClient(app)
with client.websocket_connect("/ws/echo") as ws:
    ws.send_text("hello")
    print(ws.receive_text())
    ws.send_text("again")
    print(ws.receive_text())

websocket.application_state (what the server has done) and websocket.client_state (what the client has done) are WebSocketState values, importable from fastapi.websockets: CONNECTING, CONNECTED, DISCONNECTED and, for a rejection that carries an HTTP response, RESPONSE. They are handy for guarding a late send in cleanup code. The next handler also shows the other handshake data Starlette exposes: websocket.url, websocket.headers, websocket.query_params, websocket.path_params, websocket.cookies, websocket.client and websocket.scope (including the subprotocols the client offered). Text, Bytes and JSON Messages

A WebSocket message is a text frame (UTF-8) or a binary frame. Starlette offers three pairs of methods over those two frame types:

Table 2. The send and receive methods
Receive Send Notes

receive_text() / iter_text()

send_text(str)

Text frames. A binary frame raises an error here.

receive_bytes() / iter_bytes()

send_bytes(bytes)

Binary frames, such as a cover image or a protobuf message.

receive_json(mode="text") / iter_json()

Every receive method raises WebSocketDisconnect when the client has gone; the iter_* variants end the loop instead.

from fastapi import FastAPI, WebSocket
from fastapi.testclient import TestClient

app = FastAPI()


@app.websocket("/ws/types")
async def types(websocket: WebSocket) -> None:
    await websocket.accept()
    text = await websocket.receive_text()
    await websocket.send_text(text.upper())
    blob = await websocket.receive_bytes()
    await websocket.send_bytes(blob[::-1])
    payload = await websocket.receive_json()
    await websocket.send_json({"title": payload["title"], "length": len(payload["title"])})
    # JSON over binary frames
    payload = await websocket.receive_json(mode="binary")
    await websocket.send_json({"binary": True, **payload}, mode="binary")
    # the raw ASGI message, whichever kind it is
    message = await websocket.receive()
    await websocket.send_json({"keys": sorted(k for k, v in message.items() if v is not None)})
    await websocket.close()

Validate Incoming JSON with Pydantic

FastAPI validates the handshake, never the messages: receive_json() returns whatever the client sent, and a text frame that is not JSON raises json.JSONDecodeError, an ordinary exception that is not a disconnect and ends your handler with a server error (run: json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)). Validate every message yourself with a Pydantic model, answer errors in-band, and keep the connection:

from fastapi import FastAPI, WebSocket, WebSocketDisconnect, status
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field, ValidationError, TypeAdapter
from typing import Annotated, Literal


class ChatIn(BaseModel):
    kind: Literal["message"] = "message"
    text: Annotated[str, Field(min_length=1, max_length=500)]


class ChatOut(BaseModel):
    kind: Literal["message", "error"]
    text: str


app = FastAPI()


@app.websocket("/ws/validated")
async def validated(websocket: WebSocket) -> None:
    await websocket.accept()
    async for raw in websocket.iter_json():
        try:
            incoming = ChatIn.model_validate(raw)
        except ValidationError as exc:
            await websocket.send_json(
                ChatOut(kind="error", text=f"{exc.error_count()} validation error(s)").model_dump()
            )
            continue
        await websocket.send_json(ChatOut(kind="message", text=incoming.text).model_dump())


client = TestClient(app)
with client.websocket_connect("/ws/validated") as ws:
    ws.send_json({"text": "hi"})
    print(ws.receive_json())
    ws.send_json({"text": ""})
    print(ws.receive_json())
    ws.send_json({"nope": 1})
    print(ws.receive_json())

Two cautions: a Field(max_length=…​) check runs only after the whole frame has been received, so cap frame size at the server too (Limits: Idle Timeouts, Rate Limits and Message Size); and use the same message shape in both directions so clients need one parser.

Path, Query, Cookie, Header and Dependency Parameters

In a WebSocket handler FastAPI resolves parameters from the handshake request, with the same machinery as for HTTP operations: Path (and {name} path parameters), Query, Cookie, Header, Depends and Security. Body, Form and File make no sense (there is no request body) and are not available. Remember how a connection is made: browsers cannot attach custom headers, so the practical carriers are the path, the query string and cookies.

from typing import Annotated

  • Closing before accept() rejects the handshake with plain HTTP 403. The client never gets a close code, only HTTP 403, whatever code you passed (the TestClient shows the code and reason instead, one reason to also test against a real server). The same goes for a WebSocketException or a validation failure raised before accept(), which covers every dependency in the examples above. Starlette can send a different HTTP status with send_denial_response() when the server supports the denial-response extension.

  • WebSocketException after accept() becomes a proper close frame with that code and reason (1008 'nope').

  • An unhandled exception in your handler drops the connection without a close frame (the client reports 1006, an abnormal closure, which is never sent on the wire but assigned by the client library) and Uvicorn logs Exception in ASGI application.

  • A loop that does not handle WebSocketDisconnect (while True: await websocket.receive_text()) also logs an error every time a client leaves normally. Use iter_text() or iter_json(), or catch the exception.

  • Uvicorn’s own shutdown closes open sockets with 1012 (service restart) and logs the unhandled WebSocketDisconnect of loops that do not catch it (run: closed 1012 on the client after sending SIGINT to the server). Clients should treat 1012 as "reconnect".

Always put cleanup in finally: it is the only place that runs on every path, including cancellation at server shutdown.

A Connection Manager for the Per-Book Chat

To send something to several clients you need to remember their sockets: the official docs call this a ConnectionManager and show a list of connections. The version for the Bookshelf API keeps one room per book, validates messages, broadcasts typed events and, an addition the official sketch lacks, drops a client that is dead or too slow instead of letting it block everyone:

import asyncio
from collections import defaultdict
from datetime import datetime, timezone
from typing import Annotated, Literal

from fastapi import FastAPI, Query, WebSocket
from pydantic import BaseModel, Field, ValidationError


class ChatIn(BaseModel):
    text: Annotated[str, Field(min_length=1, max_length=500)]


class ChatEvent(BaseModel):
    kind: Literal["join", "message", "leave", "error"]
    user: str
    text: str = ""
    at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))


class ConnectionManager:
    """Tracks the open sockets of each book's chat room, inside one process."""

    def __init__(self) -> None:
        self._rooms: dict[int, set[WebSocket]] = defaultdict(set)

    async def connect(self, book_id: int, websocket: WebSocket) -> None:
        await websocket.accept()
        self._rooms[book_id].add(websocket)

    def disconnect(self, book_id: int, websocket: WebSocket) -> None:
        room = self._rooms.get(book_id)
        if room is not None:
            room.discard(websocket)
            if not room:
                del self._rooms[book_id]

    def size(self, book_id: int) -> int:
        return len(self._rooms.get(book_id, ()))

    async def _send(self, book_id: int, websocket: WebSocket, data: str) -> None:
        try:
            await asyncio.wait_for(websocket.send_text(data), timeout=2.0)
        except Exception:  # dead or too slow: drop it, keep the room alive
            self.disconnect(book_id, websocket)

    async def broadcast(self, book_id: int, event: ChatEvent) -> None:
        await self.broadcast_raw(book_id, event.model_dump_json())

    async def broadcast_raw(self, book_id: int, data: str) -> None:
        sockets = list(self._rooms.get(book_id, ()))  # snapshot: the set changes while we await
        await asyncio.gather(*(self._send(book_id, ws, data) for ws in sockets))


manager = ConnectionManager()
app = FastAPI()


@app.websocket("/ws/books/{book_id}/chat")
async def book_chat(
    websocket: WebSocket, book_id: int, user: Annotated[str, Query(min_length=1, max_length=30)]
) -> None:
    await manager.connect(book_id, websocket)
    await manager.broadcast(book_id, ChatEvent(kind="join", user=user))
    try:
        async for raw in websocket.iter_json():
            try:
                incoming = ChatIn.model_validate(raw)
            except ValidationError:
                await websocket.send_text(
                    ChatEvent(kind="error", user="server", text="text must be 1-500 characters").model_dump_json()
                )
                continue
            await manager.broadcast(book_id, ChatEvent(kind="message", user=user, text=incoming.text))
    finally:
        manager.disconnect(book_id, websocket)
        await manager.broadcast(book_id, ChatEvent(kind="leave", user=user))

Source: FastAPI: WebSockets — Handling disconnections and multiple clients

Points worth reading in the code:

  • broadcast_raw copies the room into a list before sending (list(self._rooms.get(…​))): a send awaits, and while it waits other clients may join or leave, changing the set during iteration.

  • asyncio.gather sends to all sockets concurrently, and asyncio.wait_for(…​, timeout=2.0) bounds each send, so one stalled client cannot stop the others from receiving. A client that raises or times out is removed.

  • The manager is created at module level because it holds per-process state; it is not shared between workers (see Scaling Across Workers: Redis Pub/Sub). Rooms are plain sets guarded by the event loop: every method that mutates them runs between await points, so no lock is needed.

  • The endpoint broadcasts join after the connection is registered and leave in finally. The user name is a query parameter here only to keep the demo short; Authentication for WebSockets replaces it with an authenticated identity.

  • Messages go out as JSON text produced by model_dump_json(), so datetimes are ISO strings and every event has the same shape for the client.

A Browser Client with Reconnect

Browsers use the standard WebSocket object (also global in Node.js 22 and later). Networks drop connections, and Uvicorn closes them with 1012 on every deploy, so a client must reconnect, with exponential backoff and jitter so that a restart does not turn into a stampede:

// Reconnecting chat client: exponential backoff with jitter, reset after a successful open.
function connectChat(bookId, user, onEvent, base = "ws://localhost:8000") {
  let attempt = 0;
  let socket;
  let stopped = false;

  function open() {
    socket = new WebSocket(`${base}/ws/books/${bookId}/chat?user=${encodeURIComponent(user)}`);
    socket.onopen = () => { attempt = 0; };
    socket.onmessage = (e) => onEvent(JSON.parse(e.data));
    socket.onclose = () => {
      if (stopped) return;
      const delay = Math.min(30000, 500 * 2 ** attempt++) * (0.5 + Math.random() / 2);
      setTimeout(open, delay);
    };
  }
  open();
  return {
    send: (text) => socket.send(JSON.stringify({ text })),
    close: () => { stopped = true; socket.close(); },
  };
}

Authentication for WebSockets

HTTPBearer, OAuth2PasswordBearer and the other security classes of Security Fundamentals read the Authorization header from a Request. Two things make WebSockets different:

  1. The browser WebSocket API cannot set request headers. Only the URL, the subprotocol list and the cookies go on the handshake.

  2. The security classes cannot be used as dependencies in a WebSocket handler. They declare a request: Request parameter that a WebSocket does not have. Used as they are, the run fails inside FastAPI:

    TypeError: OAuth2PasswordBearer.__call__() missing 1 required positional argument: 'request'

    (run, with OAuth2PasswordBearer as a dependency of @app.websocket). Read the header with Header() or websocket.headers and decode the token yourself, as in the examples below.

Authentication happens once, at connection time; afterwards a socket may live for hours, so the design question is how to get a credential onto the handshake and what to do when it expires. The options:

A Ticket Flow with Origin Checking

The best fit for a single-page app that already holds a JWT from OAuth2 Password Flow & JWT is the ticket: a JWT that lives 30 seconds, is signed with its own key, names one user and one book, and is accepted only by the chat endpoint. The signing key comes from settings, as everywhere else in the section. The get_current_user below is a stand-in for the dependency of that page, so the example runs on its own. Run openssl rand -hex 32 to generate a real key; the script only creates a throwaway one so that it runs as is.

import os
import secrets
import time
from typing import Annotated

import jwt  # PyJWT
from fastapi import (Depends, FastAPI, Header, HTTPException, Query, WebSocket,
                     WebSocketException, status)
from pydantic import BaseModel
from pydantic_settings import BaseSettings, SettingsConfigDict

# Local demo only: a throwaway key generated for this run. In a real deployment it
# comes from the environment (for example: openssl rand -hex 32).
os.environ.setdefault("CHAT_TICKET_SECRET", secrets.token_hex(32))


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")
    chat_ticket_secret: str
    chat_ticket_ttl_seconds: int = 30
    allowed_origins: list[str] = ["https://bookshelf.example.com"]


def get_settings() -> Settings:
    return Settings()


SettingsDep = Annotated[Settings, Depends(get_settings)]


# --- HTTP side: stand-in for the get_current_user dependency of the OAuth2 + JWT page -----
def get_current_user(authorization: Annotated[str | None, Header()] = None) -> str:
    if not authorization or not authorization.startswith("Bearer user:"):
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "Not authenticated",
                            headers={"WWW-Authenticate": "Bearer"})
    return authorization.removeprefix("Bearer user:")


class Ticket(BaseModel):
    ticket: str
    expires_in: int


app = FastAPI()


@app.post("/books/{book_id}/chat-ticket")
def issue_ticket(book_id: int, user: Annotated[str, Depends(get_current_user)],
                 settings: SettingsDep) -> Ticket:
    now = int(time.time())
    claims = {"sub": user, "book": book_id, "aud": "bookshelf-chat",
              "iat": now, "exp": now + settings.chat_ticket_ttl_seconds}
    token = jwt.encode(claims, settings.chat_ticket_secret, algorithm="HS256")
    return Ticket(ticket=token, expires_in=settings.chat_ticket_ttl_seconds)


# --- WebSocket side ------------------------------------------------------------------------
async def check_origin(websocket: WebSocket, settings: SettingsDep) -> None:
    origin = websocket.headers.get("origin")
    if origin is not None and origin not in settings.allowed_origins:  # browsers always send it
        raise WebSocketException(status.WS_1008_POLICY_VIOLATION, reason="origin not allowed")


async def chat_user(book_id: int, settings: SettingsDep,
                    ticket: Annotated[str | None, Query()] = None) -> str:
    if ticket is None:
        raise WebSocketException(status.WS_1008_POLICY_VIOLATION, reason="ticket required")
    try:
        claims = jwt.decode(ticket, settings.chat_ticket_secret, algorithms=["HS256"],
                            audience="bookshelf-chat", options={"require": ["exp", "sub", "book"]})
    except jwt.InvalidTokenError:
        raise WebSocketException(status.WS_1008_POLICY_VIOLATION, reason="invalid ticket")
    if claims["book"] != book_id:
        raise WebSocketException(status.WS_1008_POLICY_VIOLATION, reason="ticket is for another book")
    return claims["sub"]


@app.websocket("/ws/books/{book_id}/chat", dependencies=[Depends(check_origin)])
async def chat(websocket: WebSocket, book_id: int, user: Annotated[str, Depends(chat_user)]) -> None:
    await websocket.accept()
    await websocket.send_json({"welcome": user, "book": book_id})
    async for message in websocket.iter_json():
        await websocket.send_json({"user": user, "echo": message})

Source: FastAPI: WebSockets — Using Depends and others and FastAPI: OAuth2 with Password (and hashing), Bearer with JWT tokens

How it works:

  • POST /books/{book_id}/chat-ticket is an ordinary authenticated path operation. It returns a JWT whose claims carry sub (the user), book, aud (the audience that stops the ticket from being accepted elsewhere), iat and exp.

  • chat_user is a dependency of the WebSocket route. It decodes with an explicit algorithm list (algorithms=["HS256"]), requires the audience and the exp, sub and book claims, and checks that the book matches the room in the path. Any failure is a WebSocketException with 1008.

  • check_origin compares the Origin header with an allow-list from settings. Browsers always send Origin on a WebSocket handshake and page scripts cannot forge it; non-browser clients usually send none, so a missing header is allowed here (decide for your clients). Neither CORS nor CORSMiddleware protects a WebSocket: Starlette’s CORSMiddleware and GZipMiddleware pass WebSocket connections through untouched, so the origin check is your job. It is the defence against cross-site WebSocket hijacking, which matters most for the cookie option, and it is wired as dependencies=[Depends(check_origin)] on the route.

Limits: Idle Timeouts, Rate Limits and Message Size

An open socket costs memory, a file descriptor and a task for as long as it lives, and a client can send as fast as the network allows. Four protections belong in every public WebSocket service:

  • a maximum message size;

  • an idle timeout for sockets that go quiet without closing;

  • a per-connection rate limit;

  • ping/pong so that dead peers are detected.

Uvicorn handles the last and part of the first at the protocol level:

A browser answers pings automatically, and a quiet but connected client is not dead, so an idle timeout is about application activity. An idle timeout and a sliding-window rate limit, with a size check on top, fit in the handler:

import time
from collections import deque

import anyio
from fastapi import FastAPI, WebSocket, WebSocketDisconnect, status
from fastapi.testclient import TestClient

IDLE_SECONDS = 0.3        # 60 or more in production
MAX_MESSAGES = 3          # per window
WINDOW_SECONDS = 1.0
MAX_TEXT_BYTES = 1024


class SlidingWindow:
    """At most `limit` events per `window` seconds, for one connection."""

    def __init__(self, limit: int, window: float) -> None:
        self.limit, self.window = limit, window
        self.events: deque[float] = deque()

    def allow(self) -> bool:
        now = time.monotonic()
        while self.events and now - self.events[0] > self.window:
            self.events.popleft()
        if len(self.events) >= self.limit:
            return False
        self.events.append(now)
        return True


app = FastAPI()


@app.websocket("/ws/guarded")
async def guarded(websocket: WebSocket) -> None:
    await websocket.accept()
    limiter = SlidingWindow(MAX_MESSAGES, WINDOW_SECONDS)
    while True:
        try:
            with anyio.fail_after(IDLE_SECONDS):
                text = await websocket.receive_text()
        except TimeoutError:
            await websocket.close(code=status.WS_1001_GOING_AWAY, reason="idle timeout")
            return
        except WebSocketDisconnect:
            return
        if len(text.encode()) > MAX_TEXT_BYTES:
            await websocket.close(code=status.WS_1009_MESSAGE_TOO_BIG, reason="message too big")
            return
        if not limiter.allow():
            await websocket.close(code=status.WS_1008_POLICY_VIOLATION, reason="rate limit exceeded")
            return
        await websocket.send_text(f"ok: {text}")

Flooding is cut off at the fourth message in a second with 1008; a 2000-byte frame against a 1024-byte limit closes with 1009; a connection that sends nothing for 0.3 seconds (60 seconds or more in production) is closed with 1001. On the sending side, await websocket.send_text() returns when the data is handed to the transport, so a slow client that never reads makes buffers grow instead of failing quickly. That is why the manager bounds every send with a timeout and drops stragglers; if a client genuinely needs every message, give each connection its own bounded queue and writer task, and close the connection when the queue is full.

Scaling Across Workers: Redis Pub/Sub

ConnectionManager lives in the memory of one process. Run uvicorn --workers 4 (or several containers) and each worker has its own manager; Ana, connected to worker A, never sees a message from Ben, connected to worker B, because broadcast only reaches sockets in the same process. The official docs say it plainly: an in-memory list works only while the process is running and only with a single process, and they point to encode/broadcaster, backed by Redis, PostgreSQL or others, for something more robust.

The cure is a shared message bus. Every worker publishes each event to the bus and subscribes to the same bus; each worker forwards what it hears to its own sockets. Redis pub/sub is the simplest bus.

import asyncio
import contextlib
from collections.abc import AsyncIterator
from typing import Annotated

import redis.asyncio as redis
from fastapi import FastAPI, Query, WebSocket

from chat import ChatEvent, ChatIn, ConnectionManager  # the per-process manager from the previous section


class ChatHub:
    """Publishes every chat event to Redis; each process relays what it hears to its own sockets."""

    def __init__(self, client: redis.Redis, local: ConnectionManager) -> None:
        self.client = client
        self.local = local
        self._pubsub = client.pubsub()
        self._task: asyncio.Task[None] | None = None

    async def start(self) -> None:
        await self._pubsub.psubscribe("book:*")
        self._task = asyncio.create_task(self._relay())

    async def stop(self) -> None:
        if self._task is not None:
            self._task.cancel()
            with contextlib.suppress(asyncio.CancelledError):
                await self._task
        await self._pubsub.aclose()

    async def publish(self, book_id: int, event: ChatEvent) -> None:
        await self.client.publish(f"book:{book_id}", event.model_dump_json())

    async def _relay(self) -> None:
        async for message in self._pubsub.listen():
            if message["type"] != "pmessage":
                continue
            book_id = int(message["channel"].removeprefix("book:"))
            await self.local.broadcast_raw(book_id, message["data"])


def create_app(client: redis.Redis) -> FastAPI:
    @contextlib.asynccontextmanager
    async def lifespan(app: FastAPI) -> AsyncIterator[dict]:
        hub = ChatHub(client, ConnectionManager())
        await hub.start()
        yield {"hub": hub}
        await hub.stop()

    app = FastAPI(lifespan=lifespan)

    @app.websocket("/ws/books/{book_id}/chat")
    async def chat(websocket: WebSocket, book_id: int,
                   user: Annotated[str, Query(min_length=1, max_length=30)]) -> None:
        hub: ChatHub = websocket.state.hub
        await hub.local.connect(book_id, websocket)
        await hub.publish(book_id, ChatEvent(kind="join", user=user))
        try:
            async for raw in websocket.iter_json():
                incoming = ChatIn.model_validate(raw)
                await hub.publish(book_id, ChatEvent(kind="message", user=user, text=incoming.text))
        finally:
            hub.local.disconnect(book_id, websocket)
            await hub.publish(book_id, ChatEvent(kind="leave", user=user))

    return app

Source: redis-py: Asyncio examples and Redis: Pub/Sub

Notes on the design:

  • The handler never broadcasts directly. It calls hub.publish, and the event comes back through the subscription, to this worker and every other. That keeps a single code path and a single ordering of events per channel.

  • One channel per book (book:7) and one pattern subscription (psubscribe("book:*")) per worker, not one subscription per socket: the number of Redis subscriptions grows with workers, not with users.

  • The subscriber task starts in the lifespan (see Settings, Lifespan & Background Tasks) and is cancelled and awaited on shutdown. yield {"hub": hub} stores the hub in lifespan state, readable as websocket.state.hub. await self._pubsub.psubscribe(…​) completes before the app serves, so no event published after startup is missed.

  • The client is passed to the application factory, so tests substitute it. Creating the real client (URL from settings, closing it in the lifespan) is shown on NoSQL & Other Data Stores.

Redis pub/sub is fire and forget: a message goes only to the subscribers connected at that moment, with no storage, no acknowledgements and no replay. A worker that restarts misses what happened meanwhile, and a client that reconnects needs its history from the database. When delivery must be reliable, use Redis Streams or a message broker; see Redis Streams and Pub/Sub and Messaging. Other points that decide whether a design scales:

  • Sticky sessions are not needed once events travel through the bus, and a reconnect may land on any worker.

  • Presence ("who is in this room") must be shared too, for example in a Redis set with expiry, or each worker publishes join and leave events as above and clients maintain the list.

  • Backpressure: a very busy channel can produce more events than one worker can fan out; the bounded-send logic of the manager applies here as well.

  • Deployment: workers, containers, and how many connections one process can hold (file descriptor limits, memory per connection) are on Deployment.

Behind a Reverse Proxy: wss://

In production, TLS usually terminates at a proxy and the browser connects to wss:// (WebSocket over TLS, the counterpart of https); a page served over HTTPS cannot open plain ws:// connections. The proxy must pass the upgrade through. In nginx, Upgrade and Connection are hop-by-hop headers and are not forwarded unless you set them:

location /ws/ {
    proxy_pass http://backend;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 120s;
}

Source: nginx: WebSocket proxying

By default nginx closes the connection if the proxied server sends no data for 60 seconds (proxy_read_timeout); either raise it or let the server send pings (Uvicorn does, every 20 seconds by default). Before nginx 1.29.7 the nginx page also asks for proxy_http_version 1.1;. This snippet comes from the nginx documentation and was not run here. Other proxies and load balancers have their own idle timeouts (often 60 seconds), so test the ping interval through the real chain. For forwarded headers, root_path and TLS termination see Running Behind a Proxy and HTTPS and TLS Termination. HTTPSRedirectMiddleware does apply to WebSocket connections (it redirects ws to wss), while CORS and GZip do not.

OpenAPI and the Interactive Docs

WebSocket routes are not part of the OpenAPI document (the paths printed by the first-endpoint run above is empty, although the route works) and /docs cannot open them; OpenAPI describes request/response operations. Where Older Guides Are Outdated, and What Changed Recently

  • Dependencies and parameters. FastAPI has supported parameters and dependencies in WebSocket routes since 0.24.0 (2019-05-24), yet older tutorials read the token by hand from websocket.query_params. Use Depends, Query, Cookie and Header, and put checks in dependencies so they are reusable and testable.

  • HTTPException in WebSocket code. Several guides raise HTTPException from WebSocket dependencies; there is no HTTP status to produce there. WebSocketException has been available since 0.87.0 (2022-11-13), and since 0.97.0 (2023-06-11) WebSocketRequestValidationError can have its own handler.

  • Unauthenticated, origin-blind endpoints. The official example is deliberately minimal. Production endpoints need authentication, an Origin check, size and rate limits, and a wss:// front.

  • Rooms in a global list. The documentation’s single-list manager works in a single process only; with several workers use a shared bus (Scaling Across Workers: Redis Pub/Sub).

  • A while True receive loop. It logs an error on every normal disconnect; use iter_* or catch WebSocketDisconnect.

  • websockets taken for granted. Plain uvicorn has no WebSocket library, and guides that assume uvicorn[standard] omit the step. fastapi[standard] includes it.

  • Annotated. Since 0.95.0 (2023-03-18) the recommended spelling of Query(), Cookie() and Depends() is Annotated[…​], also in WebSocket handlers.

  • Testing with several clients. Many examples open a single test socket; manager-style code needs the context-manager form of TestClient (Testing WebSockets).

Pitfalls

  • Sending or receiving before accept() raises an error; closing before accept() is a handshake rejection (HTTP 403), not a close frame.

  • A while True: await websocket.receive_text() loop logs Exception in ASGI application on every normal disconnect.

  • HTTPException is not an error channel here; use WebSocketException and a close code.

  • Browsers cannot send an Authorization header on a WebSocket, and OAuth2PasswordBearer and its siblings raise TypeError in a WebSocket route.

  • A token in the query string is written to access logs; use a ticket that lives seconds and is bound to one room.

  • CORS does not apply to WebSockets: check Origin yourself, especially when using cookies.

  • Not validating messages: receive_json() returns anything the client sent, or raises JSONDecodeError.

  • Broadcasting by iterating the live set of connections, or awaiting each send in turn: one dead or slow client then blocks or breaks everyone. Snapshot the set, send concurrently and bound each send.

  • Forgetting that a manager is per process: with several workers, events stop at the process boundary.

  • Redis pub/sub is fire and forget: a reconnecting client needs history from storage.

  • Holding a database session in a yield dependency for the life of the connection pins a pool connection per socket.

  • An unbounded per-client queue or an unlimited message size is a memory problem waiting for one misbehaving client.

  • Proxies close idle connections (nginx after 60 seconds by default); keep pings on or raise the timeout.

  • Putting secrets, stack traces or long text in the close reason, which is limited to 123 bytes.

  • Testing a multi-connection manager with a TestClient that is not used as a context manager hangs.

  • Relying on /docs to exercise WebSockets; it cannot.
