OpenAPI & Interactive Docs

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against FastAPI 0.142.2 (released 2026-09-30), Pydantic 2.13 and Starlette 1.7, checked on 2026-10-02. All examples use Annotated where a parameter needs one, run on Python 3.10 or newer and were executed on Python 3.13 with TestClient (see Testing for the deprecation warning that Starlette 1.7 prints when TestClient is used with httpx). The conditional and protected documentation examples were also run against a Uvicorn server with curl, and the whole API of the first example was fuzzed with Schemathesis. Every FastAPI application is also an OpenAPI document. FastAPI reads the path operations you declare — paths, parameters, request bodies, response models, security dependencies, status codes, docstrings — and assembles an OpenAPI 3.1.0 description from them. That one document then feeds everything else: the interactive documentation (Swagger UI at /docs, ReDoc at /redoc), client and server code generators, API gateways, contract tests and property-based fuzzers. This page covers how the document is built, every knob that shapes it, how to hide, protect, extend and self-host the documentation, and how to turn the document into client libraries and tests.

How the Schema Is Generated

The application object has an openapi() method. The first time it is called, it runs fastapi.openapi.utils.get_openapi() over the application’s routes, stores the result in app.openapi_schema and returns it; later calls return the stored dictionary. At startup FastAPI also registers a route at /openapi.json that returns app.openapi(), and two HTML routes (/docs, /redoc) whose pages fetch that URL in the browser.

Here is the smallest useful API of the running example, the Bookshelf API, and the document FastAPI derives from it.

A minimal Bookshelf API
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class Book(BaseModel):
    id: int
    title: str
    author: str
    year: int | None = None


BOOKS = [Book(id=1, title="Dune", author="Frank Herbert", year=1965)]


@app.get("/books")
def list_books(limit: int = 10) -> list[Book]:
    return BOOKS[:limit]


@app.get("/books/{book_id}")
def get_book(book_id: int) -> Book:
    return BOOKS[0]

Things to notice, all produced without any configuration:

  • The info block falls back to the title FastAPI and the version 0.1.0; the next section replaces them.

  • The summary List Books is the function name with underscores turned into spaces and each word capitalized.

  • The operationId is <function name>_<path with non-word characters replaced by underscores>_<method>. It is unique, ugly and the origin of the unwieldy method names in generated clients (Generating Clients and Operation IDs).

  • A 422 response with the HTTPValidationError schema is added to every operation that has parameters or a body, because FastAPI validates them. Operations with no input (such as /health in the next sections) get no 422.

  • Book is not inlined: it lives once under components.schemas and is referenced with $ref.

  • The version is 3.1.0. OpenAPI 3.1 aligns with JSON Schema 2020-12, which is why optional fields appear as anyOf with "type": "null" rather than the 3.0-era nullable: true.

Custom Request Schemas with openapi_extra

FastAPI documents a request body when a parameter is a Pydantic model or a Body. When the body is something else — raw bytes, a CSV upload, YAML, a vendor media type — you read it yourself from Request and describe it through openapi_extra. The dictionary is deep-merged into the generated operation, so it can add to the document or supply the whole requestBody.

Declaring a CSV body and a YAML body by hand
import csv
import io

import yaml
from fastapi import FastAPI, HTTPException, Request
from pydantic import BaseModel, ValidationError

app = FastAPI()


class BookIn(BaseModel):
    title: str
    author: str


@app.post(
    "/books/import",
    openapi_extra={
        "requestBody": {
            "required": True,
            "content": {
                "text/csv": {
                    "schema": {"type": "string"},
                    "example": "title,author\nDune,Frank Herbert\n",
                }
            },
        }
    },
)
async def import_books(request: Request) -> dict[str, int]:
    raw = (await request.body()).decode()
    rows = list(csv.DictReader(io.StringIO(raw)))
    return {"imported": len(rows)}


@app.post(
    "/books/yaml",
    openapi_extra={
        "requestBody": {
            "required": True,
            "content": {"application/x-yaml": {"schema": BookIn.model_json_schema()}},
        }
    },
)
async def add_book_yaml(request: Request) -> BookIn:
    try:
        data = yaml.safe_load(await request.body())
        return BookIn.model_validate(data)
    except (yaml.YAMLError, ValidationError) as exc:
        raise HTTPException(status_code=422, detail="Invalid book document") from exc

The first operation documents text/csv with a plain string schema and an example; the second reuses BookIn.model_json_schema() so that the same Pydantic model produces the JSON Schema and validates the parsed YAML, even though FastAPI never parses the body.   • model_json_schema() returns a self-contained schema. For a model with nested models it places them under $defs inside that schema, which is valid JSON Schema but is not hoisted into components.schemas, so generators see a separate anonymous schema. Prefer flat models for such bodies.

Additional Responses

status_code and response_model describe the main response. Anything else the operation can answer — 401, 403, 404, 409, a different media type — is declared with the responses parameter: a dictionary keyed by status code (or default, or a range such as 4XX) whose values are OpenAPI Response objects. A value may carry a model key with a Pydantic model; the key is FastAPI’s, not OpenAPI’s, and is replaced with a $ref to a JSON Schema. The other keys are copied as they are, so any key from the Response Object of the specification works (description, headers, content, links).

responses can be set in three places, and the three are merged: on the application (FastAPI(responses=…​)), on a router (APIRouter(responses=…​) or include_router(…​, responses=…​)) and on the decorator. The decorator wins for the same status code.

This helps generated clients: a field with a default is optional when you send the model and always present when you receive it.

Callbacks and Webhooks

Both describe requests that go from your API to the client’s server, and both are documentation only: FastAPI neither registers the client’s URL nor sends the request. The difference is who knows the URL.

  • A callback belongs to one operation: the client passes a URL in the request (or body) and your API calls it back later. The URL is an OpenAPI runtime expression that references the incoming request.

  • A webhook is an event your API may send to URLs that clients registered some other way, for instance in a dashboard. It has a name, not a path. Webhooks are an OpenAPI 3.1.0 feature, supported from FastAPI 0.99.0 (2023-06-30).

How it works:

  • Callbacks use a router as a drawing board. callback_router holds one or more path operations that describe the request the client must be ready to receive. The function bodies are never run (pass is enough). You pass callback_router.routes, not the router itself, to callbacks=.

  • The path is a runtime expression. {$callback_url}/reviews/{$request.body.id} is substituted from the incoming request: $callback_url is the query parameter, $request.body.id is the id field of the JSON body (here the subscription id). Swagger UI shows it in a Callbacks section under the operation.

  • Webhooks are declared on app.webhooks. It is an APIRouter, so @app.webhooks.post("new-review") works like a normal path operation; the string is the event name and the docstring becomes the description. The result is a top-level webhooks key in the document, next to paths.

  • Sending is your code. notify() posts the event with httpx; in the run it was replaced by an httpx.MockTransport and the request seen was POST https://partner.example.org/events/reviews/sub42 with the body {"book_id":1,"rating":5,"posted_at":"2026-10-02T09:30:00"}. The background task keeps the HTTP response fast; see Settings, Lifespan & Background Tasks. For delivery guarantees (retries, signing, dead letters) a queue is the right tool, not BackgroundTasks.

  • Operation ids are ugly here. The run produced review_notificationcallback_urlreviews_request_body_idpost for the callback and new_reviewnew_review_post for the webhook, because both derive the id from a "path" that is not a path. Set operation_id or a generate_unique_id_function (Generating Clients and Operation IDs) if clients are generated from them.

  • Secure webhooks yourself. The document cannot express a signature. Document the header that carries it (for instance an HMAC of the body computed with a per-client secret) in the webhook description, and have clients verify it before trusting the payload.

Hiding the docs is not a security measure. The operations stay reachable, any flaw in them remains, and hiding the UI only makes the API harder for honest developers to learn (and for you to debug). Serving the documentation behind HTTP Basic credentials taken from settings
import secrets

from fastapi import Depends, FastAPI, HTTPException, status
from fastapi.openapi.docs import get_swagger_ui_html
from fastapi.security import HTTPBasic, HTTPBasicCredentials
from pydantic_settings import BaseSettings


class Settings(BaseSettings):
    docs_user: str
    docs_password: str

basic = HTTPBasic()


def docs_access(credentials: Annotated[HTTPBasicCredentials, Depends(basic)]) -> None:
    user_ok = secrets.compare_digest(credentials.username.encode(), settings.docs_user.encode())
    password_ok = secrets.compare_digest(credentials.password.encode(), settings.docs_password.encode())

        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Invalid credentials",
            headers={"WWW-Authenticate": "Basic"},
        )

    return ["Dune"]

Extending the Schema with get_openapi

When a declaration cannot express what you need — a vendor extension, a global externalDocs, a change to every operation — generate the document as FastAPI does and edit the dictionary. The process is the one from How the Schema Is Generated: replace app.openapi with a function that builds the document once with get_openapi(), edits it, and caches it in app.openapi_schema.

Self-Hosting Swagger UI and ReDoc

By default /docs loads swagger-ui-bundle.js and swagger-ui.css from a CDN, and /redoc loads redoc.standalone.js from a CDN plus web fonts from Google Fonts. That fails on an air-gapped network, behind a strict Content Security Policy, offline during development, and in countries where the CDN is unreachable. The fix is to serve the files yourself:

  1. Download swagger-ui-bundle.js, swagger-ui.css and redoc.standalone.js (from the swagger-ui-dist and redoc distributions, pinned to a version you have tested) into a static/ directory.

  2. Mount it with StaticFiles.

  3. Disable the default docs routes (docs_url=None, redoc_url=None) and re-create them with get_swagger_ui_html(), get_redoc_html() and get_swagger_ui_oauth2_redirect_html() from fastapi.openapi.docs, pointing at the local files.

Generating Clients and Operation IDs

Because the document is standard OpenAPI 3.1, generators turn it into typed clients (SDKs). The FastAPI documentation walks through TypeScript with Hey API’s openapi-ts, and also names the OpenAPI Generator project for many other languages; any tool you pick must support OpenAPI 3.1.

Tags drive the client’s structure: a books tag becomes a BooksService (or equivalent), an authors tag an AuthorsService. Method names come from the operationId, and the default id (list_books_books_get) yields awkward names such as listBooksBooksGet. FastAPI therefore lets you replace the function that builds the id with generate_unique_id_function, which receives each APIRoute and returns a string.

Rules for that function:

  • The id must be unique across the document, so each function name must be unique per tag (and per module, even in different files).

  • route.tags[0] raises IndexError for an untagged route, and it raises at import time (when the decorator runs), not when the schema is built; every route needs a tag, or the function must handle an empty list.

  • A route’s own operation_id wins over the function.

  • The FastAPI documentation says the function also feeds the names of any custom models FastAPI has to create, so regenerate clients after changing it.

  • The function can be set on the application, on an APIRouter and on a single route.

  • After the tag prefix is removed (a short script over openapi.json, as the FastAPI page shows) you get the cleanest method names, listBooks instead of booksListBooks, while keeping unique ids in the document itself.

Where Older Guides Are Outdated, and What Changed Recently

  • OpenAPI version. Older guides and books show an OpenAPI 3.0.2 document with nullable: true. FastAPI emits OpenAPI 3.1.0 and JSON Schema 2020-12 since 0.99.0 (2023-06-30), so optional fields are anyOf with null, the license can use an SPDX identifier, summary exists on info, and webhooks exist. Generators and gateways must support 3.1.

  • Examples. Older guides show a single example value. The list form examples follows JSON Schema 2020-12 (0.99.0), and the named, UI-friendly openapi_examples arrived in 0.103.0 (2023-08-26).

  • Input and output schemas. Pydantic v2 can produce -Input and -Output variants of a model; FastAPI supports it since 0.102.0 (2023-08-25) with the switch separate_input_output_schemas. Clients generated from older documents show renamed schemas when they regenerate.

  • Routes in get_openapi. FastAPI 0.137.0 (2026-06-14) preserves APIRouter and APIRoute instances and makes the internal route list a tree; the supported way of building a custom document is still routes=app.routes, and get_openapi() traverses the tree. Code that loops over app.routes expecting every element to be a final APIRoute must be revisited; the release notes for 0.137.2 (2026-06-18) mention the added iter_route_contexts(), and letting get_openapi() do the walking avoids the question.

  • Pydantic v1 era advice. schema_extra, Config classes and .schema() are Pydantic v1. Use ConfigDict with json_schema_extra and model_json_schema(); FastAPI itself dropped Pydantic v1 support in 0.126.0 (2025-12-20) and pydantic.v1 in 0.128.0 (2025-12-27).

Pitfalls

  • Setting docs_url=None only removes Swagger UI; the document and ReDoc stay. Use openapi_url=None to remove everything, and remember that none of it is access control.

  • include_in_schema=False and a router-wide deprecated=True are one-way switches at the router level: the first hides without protecting, the second cannot be undone per route.

  • Changing title, version or routes after the first call to app.openapi() has no effect until app.openapi_schema = None.

  • Duplicate operation_id values produce a warning and break generators. A generate_unique_id_function that indexes route.tags[0] raises at import time for untagged routes.

  • responses= documents; it does not return anything or validate bodies. Return the JSONResponse or raise the exception yourself.

  • An openapi_extra request body is invisible to FastAPI: no parsing, no validation, no 422. Keep the declared schema and the code in sync, preferably from one Pydantic model.

  • Examples are not checked against the model. Add a test that validates them.

  • Tags in openapi_tags are shown in list order; a typo in a decorator’s tag creates a new, unlisted tag.

  • A plain default does not split input and output schemas with Pydantic 2.13; clients generated from -Input and -Output names break when you toggle the flag or add a computed field later. Decide early and regenerate.

  • The CDN is a runtime dependency of /docs and /redoc: self-host for air-gapped or restricted networks, and pin the versions you self-host.

  • swagger_ui_parameters given to FastAPI(…​) do not reach a hand-written /docs route; pass them to get_swagger_ui_html() as well.

  • persistAuthorization stores credentials in the browser. Do not enable it for production-like data on shared machines.

  • Webhook and callback blocks document a contract; they send nothing and say nothing about signatures. Document the verification scheme and implement delivery with retries elsewhere.

  • An API whose info.version never changes defeats the purpose of exporting and checking openapi.json; bump it with each release.

  • Pin FastAPI (it is still a 0.x library): schema details such as ids, titles and the route tree have changed between minor versions, and generated clients depend on them.
