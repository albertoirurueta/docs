The First Test: TestClient and pytest

fastapi.testclient.TestClient is Starlette’s test client re-exported for convenience (starlette.testclient.TestClient is the same class). It is an HTTP client in the shape of httpx whose transport calls your ASGI application directly in the same process. There is no server, no port and no network, so a test takes milliseconds. Install the test tools with pip install pytest httpx (the official tutorial uses uv add httpx); the section The httpx and httpx2 Warning in Starlette 1.7 explains why a newer package, httpx2, is now preferred.

A test is a function whose name starts with test_; it builds a TestClient for the application, makes requests with the usual get, post, put, patch and delete methods and asserts on the Response.

Three details of the example matter for everything that follows:

  • The test functions are plain def, and the client calls are plain calls, not await. TestClient runs the application on an event loop in a helper thread (an AnyIO blocking portal) and hands you the result synchronously, so pytest needs no plugin. An async def endpoint and a def endpoint (run in the thread pool) are tested identically.

  • The application is exercised through its public interface only: a URL in, a response out. The same test passes if you rewrite the endpoint, split it into routers or change the dependencies underneath (see Project Structure & Layered Architecture).

  • Validation is part of the application. The second test proves that the path parameter conversion in Path Parameters rejects three with 422 and the Pydantic error type int_parsing.

from typing import Annotated

import jwt
from fastapi import Depends, HTTPException, status

from pwdlib import PasswordHash

from app.config import Settings, get_settings

password_hash = PasswordHash.recommended()
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")

USERS = {"ada": password_hash.hash("ada-test-password")}


def create_access_token(username: str, settings: Settings) -> str:
    expires = datetime.now(UTC) + timedelta(minutes=settings.token_minutes)
    return jwt.encode(
        {"sub": username, "exp": expires},
        settings.jwt_secret.get_secret_value(),
        algorithm="HS256",
    )


def get_current_user(
    token: Annotated[str, Depends(oauth2_scheme)],
    settings: Annotated[Settings, Depends(get_settings)],
) -> str:
    try:
        payload = jwt.decode(
            token, settings.jwt_secret.get_secret_value(), algorithms=["HS256"]
        )
    except jwt.InvalidTokenError:
        raise HTTPException(
            status.HTTP_401_UNAUTHORIZED,
            "Invalid or expired token",
            headers={"WWW-Authenticate": "Bearer"},
        ) from None
    return payload["sub"]

        self.by_book[book_id].discard(websocket)

        for websocket in list(self.by_book[book_id]):

Three design choices make this application testable, and they are worth copying:

  • Everything environmental is a dependency. The settings (get_settings), the database session (get_session), the current user (get_current_user) and the external client (get_isbn_lookup) are all reached through Depends, so a test can replace each of them. Fixtures are pytest’s way of building and tearing down what a test needs; a fixture that yield`s a value runs its teardown after the test, even when the test fails. `tests/conftest.py holds the four fixtures that nearly every test of this suite uses.

What each fixture does and why it is written that way:

  • settings builds a Settings object from explicit values. _env_file=None stops pydantic-settings from reading a developer’s real .env (a test that depends on the contents of a local file is not a test), and the secret is a fresh secrets.token_hex(32) per test, so nothing real is involved and nothing needs to be hard-coded. Using Settings(…​) directly bypasses the lru_cache of get_settings.

  • session creates an in-memory SQLite database (sqlite://), creates the tables from the SQLModel metadata and yields a Session. Three details are not optional:

    • poolclass=StaticPool makes SQLAlchemy keep one single connection. An in-memory SQLite database exists inside one connection, so with the default pool every new connection would see its own empty database.

    • check_same_thread=False lets that connection be used from other threads. Synchronous path functions run in Starlette’s thread pool, so the request code and the test code touch the connection from different threads.

    • engine.dispose() after the yield closes the connection explicitly, which also keeps pytest’s unraisable-exception warnings quiet.

  • client installs two overrides and builds the TestClient. It is entered with with so that the lifespan runs (Testing the Lifespan) and all requests share one event loop and portal. The lambda: session override means that the request code uses the same Session object as the test, which makes it trivial to prepare and inspect data. The overrides are removed with app.dependency_overrides.clear() after the yield, because app is a module-level object that outlives every test.

  • auth mints a valid bearer token with the same function the application uses, so tests of protected routes do not depend on the login endpoint (Testing Auth-Protected Routes).

Naming the fixture with @pytest.fixture(name="client") and the function client_fixture is the pattern used by the SQLModel tutorial. It avoids the lint warning about a test parameter shadowing the fixture function and makes it clear that the parameter is the fixture, not an import.

Overriding Dependencies with app.dependency_overrides

Dependency injection is what makes a FastAPI application testable without patching. app.dependency_overrides is a plain dict: the key is the original dependency callable (the same object that appears in Depends(…​)), the value is a replacement callable. FastAPI calls the replacement wherever the original would have been called, for every route and every sub-dependency that declares it; the original, and the dependencies it would have used, are not called at all. The replacement may itself declare parameters (query parameters, other dependencies), which FastAPI resolves as usual. The mechanism is explained in Dependency Injection; here it is applied to the external ISBN client of the application, which is slow, rate limited and not something a unit test should call.

tests/test_overrides.py
from unittest.mock import patch

import pytest
from fastapi.testclient import TestClient

from app.isbn import IsbnLookup, get_isbn_lookup
from app.main import app


class FakeIsbnLookup:
    def __init__(self, titles: dict[str, str]) -> None:
        self.titles = titles
        self.calls: list[str] = []

    def title_for(self, isbn: str) -> str | None:
        self.calls.append(isbn)
        return self.titles.get(isbn)


@pytest.fixture(name="isbn")
def isbn_fixture(client: TestClient) -> FakeIsbnLookup:
    fake = FakeIsbnLookup({"9780441013593": "Dune"})
    app.dependency_overrides[get_isbn_lookup] = lambda: fake
    return fake  # the client fixture clears every override at teardown


def test_known_isbn(client: TestClient, isbn: FakeIsbnLookup) -> None:
    response = client.get("/isbn/9780441013593")
    assert response.json() == {"isbn": "9780441013593", "title": "Dune"}
    assert isbn.calls == ["9780441013593"]


def test_unknown_isbn(client: TestClient, isbn: FakeIsbnLookup) -> None:
    assert client.get("/isbn/0000000000").status_code == 404


def test_same_thing_with_mock_patch(client: TestClient) -> None:
    # patch() replaces an attribute of the class: it works, but it ties the test to
    # where the code looks the name up. The override ties it to the public seam instead.
    with patch.object(IsbnLookup, "title_for", return_value="Kindred"):
        response = client.get("/isbn/123")
    assert response.json()["title"] == "Kindred"

What the file demonstrates:

  • A hand-written fake (FakeIsbnLookup) replaces the dependency through a fixture. It is a small class with the same method as the real one, it records the calls it received, and the tests assert on behaviour (the response) and on the interaction (isbn.calls). The client fixture clears every override at teardown, so this fixture does not need its own cleanup.

  • unittest.mock.patch.object achieves the same result by replacing an attribute of the real class. It works, and it is the right tool for a function that is called directly and is not a dependency. For things reached through Depends, the override is better: it replaces the object at the seam the application deliberately offers, it does not depend on the module in which a name is imported and it cannot leak to other tests when a with patch(…​) block is forgotten.

  • Fakes over mocks. A fake with real behaviour (an in-memory repository, a dictionary of titles) keeps tests short and keeps them passing when the code under test is refactored; a heavily configured Mock asserts how the code does things rather than what it achieves.

Rules for overrides, each of which has caused a failing test somewhere:

  • The key must be the same function object used in Depends. An alias created with Annotated[Session, Depends(get_session)] is fine, because it wraps the same function; a different function that looks the same is not.

  • An override replaces the whole dependency, including any authorization it performs. Test the real checker separately, as Testing Auth-Protected Routes does.

  • Overriding a yield dependency with a plain function skips its setup and its teardown. If the real dependency commits or closes something that the test relies on, replicate that in the override.

  • Clear the dictionary after each test (the client fixture does it). A leaked override makes later tests pass or fail depending on their order.

  • The dictionary belongs to one application object. A mounted sub-application has its own, and overriding the parent changes nothing inside it:

What is covered, and what the status codes mean:

  • Login. The password form is sent with data=, not json=, because OAuth2PasswordRequestForm reads form fields. The test decodes the token with the settings' secret and checks the subject, then uses the token on a protected route.

  • Wrong password. 401 with WWW-Authenticate: Bearer, as the OAuth2 specification and the HTTP semantics require (see OAuth2 Password Flow & JWT).

  • No credentials. OAuth2PasswordBearer answers 401 with Not authenticated. Older FastAPI versions answered 403 here; since 0.122.0 (2025-11-24) the security classes return 401. A test that still expects 403 for missing credentials is one of the first to break after an upgrade; the official page for the previous behaviour is Use Old 403 Authentication Error Status Codes. If your application keeps the old status through a subclass, every test that builds or overrides the scheme must use the same subclass (see Security Fundamentals).

  • Expired token. The test builds a token whose lifetime is negative with settings.model_copy(update={"token_minutes": -1}): no sleeping and no mocked clock needed.

  • Wrongly signed token. The test builds a token with a different key and checks that the protected route rejects it while a public route ignores the header.

  • Overridden user. No Authorization header at all, yet the request is authenticated as grace.

Scopes and roles follow the same pattern: mint tokens with the scopes under test, or override the dependency that checks them, and test the checker once on its own. The scope tests are in OAuth2 Scopes & Authorization. Argon2 verification is deliberately slow, so only the login tests pay for it; every other test uses a minted token.

Testing the Lifespan

Startup and shutdown code lives in the lifespan context manager of the application (see Settings, Lifespan & Background Tasks). TestClient runs it only when the client is used as a context manager: the code before the yield runs when the block is entered and the code after it when the block is left. A client that is merely created does not run it.

tests/test_lifespan.py
from contextlib import asynccontextmanager

from fastapi import FastAPI
from fastapi.testclient import TestClient

from app.main import app

events: list[str] = []


@asynccontextmanager
async def recording_lifespan(app: FastAPI):
    events.append("startup")
    yield
    events.append("shutdown")


probe = FastAPI(lifespan=recording_lifespan)


@probe.get("/ping")
def ping() -> str:
    return "pong"


def test_lifespan_runs_only_inside_with() -> None:
    events.clear()

    client = TestClient(probe)  # constructed, never entered
    assert client.get("/ping").json() == "pong"
    assert events == []  # the request worked, the lifespan did not run

    with TestClient(probe) as entered:
        assert events == ["startup"]
        assert entered.get("/ping").json() == "pong"
    assert events == ["startup", "shutdown"]


def test_the_real_lifespan_warms_the_cache() -> None:
    with TestClient(app) as client:
        assert client.get("/genres").json() == ["fiction", "history", "science"]
    assert app.state.genres == []  # leaving the block ran the shutdown code

Source: FastAPI: Testing Events: lifespan and startup - shutdown

The first test builds a tiny probe application whose lifespan records what happens. The request on the plain client succeeded, but events stayed empty: the lifespan never ran. Entering the context manager runs the startup code, and leaving it runs the shutdown code. The second test checks the real application: the cache is warmed inside the block and emptied when it ends.

Consequences for a suite:

  • Use with TestClient(app) as client in a fixture (as conftest.py does) whenever the application has a lifespan, or the endpoints that depend on lifespan state fail with AttributeError or KeyError. A client without with is fine for applications and tests that do not need it, and is what the first example on this page used.

  • The deprecated @app.on_event("startup") and ("shutdown") handlers behave the same way: they also run only inside with TestClient(app). New code should use lifespan; when a lifespan is given, on_event handlers are ignored.

  • A lifespan that talks to the network or opens a real pool must be made testable: read its inputs from settings and use an in-memory fake or a container in the test environment, or the whole suite fails when the dependency is down. Overrides of dependency_overrides do not apply inside the lifespan, because it is not a dependency.

  • A mounted sub-application’s lifespan is not run by the parent’s lifespan; test it with its own client.

  • Because the context manager is entered once per fixture, a function-scoped client starts and stops the lifespan for every test. That is exactly right for isolation and cheap unless the lifespan loads something large; for that case use a wider scope and reset the state in between.

Testing WebSockets

client.websocket_connect(url) returns a context manager for a test session. Inside it, send_text, send_bytes and send_json go to the server, and receive_text, receive_bytes and receive_json read what the server sent; leaving the block closes the connection. A rejected handshake or a server-side close raises WebSocketDisconnect carrying the close code, and params= is not supported (put the query string in the URL). The details and the failure modes are on WebSockets; the minimum is a single connection:

tests/test_websockets.py
from fastapi.testclient import TestClient

from app.main import app


def test_echo() -> None:
    client = TestClient(app)
    with client.websocket_connect("/ws/books/7") as websocket:
        websocket.send_text("hello")
        assert websocket.receive_json() == {"book_id": 7, "echo": "hello"}

Source: FastAPI: Testing WebSockets

A feature that involves several connections (a feed that broadcasts a new review to every open page) needs more care. Open the clients with with TestClient(app) as client:, as the client fixture does, so that all of them share one event loop and one portal. The test below opens two sockets on the same book, posts a review through the HTTP API and checks that both sockets receive the event:

tests/test_review_feed.py
from fastapi.testclient import TestClient

from app.models import Author, Book


def test_every_open_socket_gets_the_new_review(client: TestClient, session, auth) -> None:
    author = Author(name="N. K. Jemisin")
    session.add(author)
    session.commit()
    book = Book(title="The Fifth Season", author_id=author.id)
    session.add(book)
    session.commit()

    # `client` was created with `with TestClient(app)`, so both connections share one
    # event loop and one portal. Without that, every websocket_connect() would start its own.
    with client.websocket_connect(f"/ws/books/{book.id}/reviews") as first:
        with client.websocket_connect(f"/ws/books/{book.id}/reviews") as second:
            response = client.post(
                f"/books/{book.id}/reviews", json={"rating": 5, "text": "Superb"}, headers=auth
            )
            assert response.status_code == 201
            assert first.receive_json() == {"rating": 5, "reviewer": "ada"}
            assert second.receive_json() == {"rating": 5, "reviewer": "ada"}

Source: FastAPI: Testing WebSockets

Without with TestClient(app), each websocket_connect runs in its own thread with its own event loop. Code that shares loop-bound objects such as locks, queues or futures between connections is then unsafe: the chat manager on the WebSockets page hung until its test used the context-manager form. Two small variants written for this page (the rooms above, and a queue shared between two sockets) happened to pass without it, which is the danger: they pass by luck. Treat the context-manager form as required for any test with more than one connection. Note also that the new review reaches the sockets through a background task of the HTTP request, which TestClient completes before it returns the response (Testing Background Tasks).

Testing Background Tasks

BackgroundTasks run after the response has been sent. TestClient waits for them: the call returns once the application has finished the whole ASGI exchange, background tasks included, so a test can assert on their effect right after the request:

tests/test_background.py
from fastapi.testclient import TestClient

from app.main import audit_log
from app.models import Author


def test_background_task_has_run_when_the_response_returns(client: TestClient, session, auth) -> None:
    audit_log.clear()
    author = Author(name="Terry Pratchett")
    session.add(author)
    session.commit()

    response = client.post("/books", json={"title": "Small Gods", "author_id": author.id}, headers=auth)

    assert response.status_code == 201
    assert audit_log == [f"ada created book {response.json()['id']}"]

Source: FastAPI: Background Tasks

The task here appends to a list standing for an audit log; in a real application it sends an e-mail or refreshes a cache, and you override that collaborator as in Overriding Dependencies with app.dependency_overrides. That a task ran is observable; that it ran after the response was sent is not, because the test client waits. Tasks that need retries, durability or other processes belong in a queue and are tested at the queue’s boundary (see Settings, Lifespan & Background Tasks).

Async Tests with anyio and httpx

TestClient is synchronous. That is its strength, but it creates its own event loop in a helper thread, so a test that has to await something itself cannot share that loop with the application. The typical case is a test that calls the application and then checks the database through an async driver, or an async fixture holding a connection that must live on the same loop as the app. The official recipe is an async test function, the AnyIO pytest plugin and an async HTTP client that talks to the ASGI app directly:

tests/test_async.py
import pytest
from httpx import ASGITransport, AsyncClient
from sqlmodel import Session, select

from app.main import app
from app.models import Author


@pytest.fixture
def anyio_backend() -> str:
    return "asyncio"  # run only on asyncio; add "trio" here if you support it


@pytest.mark.anyio
async def test_create_author_and_check_the_database(client, session: Session, auth) -> None:
    # `client` (the sync fixture) is only used here for its dependency overrides.
    async with AsyncClient(transport=ASGITransport(app=app), base_url="http://test") as ac:
        response = await ac.post("/authors", json={"name": "Chinua Achebe"}, headers=auth)
    assert response.status_code == 201

    names = [author.name for author in session.exec(select(Author))]
    assert names == ["Chinua Achebe"]

Source: FastAPI: Async Tests

The parts, in order:

  • @pytest.mark.anyio tells the AnyIO plugin (installed together with anyio, no extra package) to run this coroutine test on an event loop. It is the mechanism FastAPI’s documentation recommends; the pytest-asyncio plugin is an alternative with its own configuration (see pytest-asyncio); pick one of the two for a suite.

  • anyio_backend is the fixture the plugin reads to choose the loop. By default every test runs once per available backend: asyncio, and also Trio when Trio is installed. Returning "asyncio" from your own fixture, as here, pins it. Running on Trio needs Trio installed and an application written with AnyIO primitives rather than asyncio ones. See AnyIO: Testing with AnyIO.

  • AsyncClient(transport=ASGITransport(app=app), base_url="http://test") is HTTPX’s async client with a transport that calls the ASGI app in the current event loop. base_url is required but arbitrary. This is the async equivalent of TestClient, and it is what TestClient is built on.

  • await ac.post(…​) is a real await on the test’s own loop, so the test can then await anything else, here a check of the rows. The check uses the synchronous session fixture to keep the example short; with an async engine you would await the query on the same loop.

The same overrides apply, because they live on the application. The sync client fixture is requested above only to install them; an async test that needs the overrides can also set them in its own fixture.

Two limits of the async client matter in practice:

  • It does not run the lifespan. Neither AsyncClient nor ASGITransport triggers startup and shutdown. The official page recommends the asgi-lifespan package (LifespanManager) for that. The application’s own router can do it too, as the second example below shows:

tests/test_async_lifespan.py
import pytest
from asgi_lifespan import LifespanManager
from httpx import ASGITransport, AsyncClient

from app.main import app


@pytest.fixture

    return "asyncio"


@pytest.mark.anyio

    app.state.genres = None
    async with AsyncClient(transport=ASGITransport(app=app), base_url="http://test") as ac:
        assert app.state.genres is None  # no startup happened


@pytest.mark.anyio
async def test_lifespan_manager_runs_it() -> None:
    async with LifespanManager(app):
        async with AsyncClient(transport=ASGITransport(app=app), base_url="http://test") as ac:
            response = await ac.get("/genres")
    assert response.json() == ["fiction", "history", "science"]
    assert app.state.genres == []  # shutdown ran when the manager exited

Source: FastAPI: Async Tests

Both tests passed. The first shows that the lifespan did not start; the second runs it with LifespanManager, and when the manager exits the shutdown code has run. The router alternative is async with app.router.lifespan_context(app):; it started and stopped the lifespan in a test of its own (see The httpx and httpx2 Warning in Starlette 1.7 for that test, which uses the httpx2 package).

  • It does not mix with a TestClient on the same loop. Do not call TestClient from inside an async def test: it blocks the loop it is running on. Use one style per test. A RuntimeError: Task attached to a different loop usually means that an object with a loop (a driver client, a lock) was created at import time or in a sync fixture; create it inside the async test or an async fixture.

Testing Against a Database

The session fixture above is the whole database setup of the suite: an in-memory SQLite engine, the tables created from SQLModel.metadata, one session shared with the request code through the override. It has three consequences, each demonstrated below:

  • the test can read the rows the API wrote with the same session;

  • every test starts from an empty database, because the engine is created per test;

  • SQLite is not PostgreSQL, so some production rules need to be switched on explicitly.

tests/test_database.py
import pytest
from fastapi.testclient import TestClient
from sqlalchemy import event
from sqlalchemy.exc import IntegrityError
from sqlalchemy.pool import StaticPool
from sqlmodel import Session, SQLModel, create_engine, select

from app.models import Author, Book, Review


def test_the_api_wrote_the_rows_we_expect(client: TestClient, session: Session, auth) -> None:
    client.post("/authors", json={"name": "Italo Calvino"}, headers=auth)
    author = session.exec(select(Author)).one()  # same session, same in-memory database
    client.post("/books", json={"title": "Invisible Cities", "author_id": author.id}, headers=auth)

    books = session.exec(select(Book)).all()
    assert [book.title for book in books] == ["Invisible Cities"]


def test_every_test_starts_from_an_empty_database(session: Session) -> None:
    assert session.exec(select(Book)).all() == []  # nothing left over from the test above


def test_sqlite_ignores_foreign_keys_by_default(session: Session) -> None:
    session.add(Review(book_id=999, rating=3, reviewer="ada"))  # book 999 does not exist
    session.commit()  # accepted: SQLite does not enforce foreign keys unless asked to


def test_enforcing_foreign_keys_like_production_does() -> None:
    engine = create_engine("sqlite://", connect_args={"check_same_thread": False},
                           poolclass=StaticPool)

    @event.listens_for(engine, "connect")
    def enforce_foreign_keys(dbapi_connection, _record) -> None:
        dbapi_connection.execute("PRAGMA foreign_keys=ON")

    SQLModel.metadata.create_all(engine)
    with Session(engine) as session:
        session.add(Review(book_id=999, rating=3, reviewer="ada"))
        with pytest.raises(IntegrityError):
            session.commit()
    engine.dispose()

Source: FastAPI: Testing a Database

The third test is the instructive one. SQLite does not enforce foreign keys unless PRAGMA foreign_keys=ON is issued on the connection, so the first insert of a review for a book that does not exist is accepted, while PostgreSQL would reject it with an integrity error. The fourth test turns enforcement on with an engine connect event and gets the IntegrityError that production would raise. If your application relies on a constraint, make the test engine enforce it, or the suite certifies a rule that the in-memory database never checks.

Guidelines for the middle of the pyramid, where FastAPI tests live:

  • Keep logic out of path functions. A path function that parses, calls a service and shapes a response is easy to test through HTTP; one that contains a hundred lines of rules is not. Move the rules to a service and test them directly.

  • Test the HTTP contract once per route, not once per rule. A few requests per path operation (success, not found, invalid input, forbidden) are enough at the API layer; the many rule variations belong in unit tests.

  • Prefer fakes at the seams. A repository or client replaced by an in-memory fake through dependency_overrides or constructor injection tests the service realistically; reserve unittest.mock for edges that are hard to fake (time, randomness, a failing network call) and for asserting that something was not called.

  • Call path functions directly only for pure logic. A path function that was extracted from its decorator and called with plain arguments skips routing, validation, dependencies and serialization, which are the things most likely to be wrong. The old habit of unit-testing path functions as plain functions is why many suites miss 422 and 401 regressions.

  • Make one failing test point at one cause. If a unit test and an API test fail together, fix the unit test first.

At the top, a handful of tests against a deployed environment confirm that the container, the proxy, TLS and the database wiring work; they are not written with TestClient. For generated cases and load, see Beyond Example-Based Tests.

Other TestClient Options: root_path, Address, Backend

TestClient(app, root_path="/api/v1") sets the ASGI root_path for every request, which simulates an application served under a prefix by a proxy (the situation of Behind a Proxy). The important detail is what it does not do: it does not change the request URL. The test still calls /new, the response’s url stays http://testserver/new, the router matches the path without the prefix, and the prefix is visible only where the application looks at root_path: in the scope, in generated URLs and in the OpenAPI servers. Do not write client.get("/api/v1/new") expecting the prefix to be required (Starlette also tolerates the prefixed path, so a test written that way passes and proves nothing about the proxy setup).

tests/test_client_options.py, the root_path test
def test_root_path_is_not_prepended_to_the_url() -> None:
    client = TestClient(app, root_path="/api/v1")
    response = client.get("/new")
    assert response.url == "http://testserver/new"  # the request URL has no prefix
    body = response.json()
    assert body["root_path"] == "/api/v1"  # but the ASGI scope carries it ...
    assert body["url_for"] == "http://testserver/api/v1/new"  # ... so generated URLs include it

Source: Starlette: Test Client

The other constructor arguments are raise_server_exceptions (Unhandled Exceptions: raise_server_exceptions), base_url, cookies, headers, follow_redirects and client, shown above, and backend and backend_options: backend="trio" runs the application on Trio (the application must be AnyIO-compatible), and backend_options={"use_uvloop": True} selects uvloop for asyncio. The test client also exposes ASGI extensions to tests: HTTP trailers through response.extensions["http.response.trailers"] and debug information through response.extensions["http.response.debug"], which is what the template context above is built on. They are covered on the Starlette page in the references.

Coverage with pytest-cov

Coverage tells you which lines (and, with branch coverage, which if outcomes) the tests never executed. It cannot tell you that the tests are good, but a red line in a security dependency is a precise to-do list. pytest-cov plugs the coverage tool into pytest. Configure the measured package and the report in pyproject.toml, then add --cov:

The coverage configuration appended to pyproject.toml
[tool.coverage.run]
source = ["app"]   # measure the application package, not the tests
branch = true      # also report branches never taken

[tool.coverage.report]
show_missing = true
fail_under = 90    # the run fails below this total percentage

Reading the report:

  • Miss and Missing list the statements and line numbers the tests never ran. In app/main.py the lines 67 and 93 are the failure branches that no test of this suite triggers (wrong credentials are covered, but an unknown author when creating a book and an unknown book when reviewing are not), and 104 and 105 are the rating endpoint, which no test requests. app/db.py is at 56% and app/isbn.py at 78% because the real get_engine, get_session and the network call of IsbnLookup are replaced by overrides in every test, which is the expected trade-off of overriding.   • Branch and BrPart count if/else outcomes: a line can be executed while one of its two outcomes never is, which the plain line percentage hides.

  • The code that the TestClient runs in its helper thread is measured too (the main.py figures above include everything the requests executed), because coverage traces threads by default.

  • A threshold enforces a floor, not quality. fail_under (or --cov-fail-under=95 on the command line) makes the run fail with a non-zero exit code, which is what a CI step needs:

FAIL Required test coverage of 95% not reached. Total coverage: 92.04%
37 passed in 0.43s
exit code: 1

Practical advice: measure branches, exclude only what is truly untestable (if name == "main":, if TYPE_CHECKING:; configure it under [tool.coverage.report] exclude_also), ratchet the threshold upwards as the suite grows, and do not write tests whose only purpose is to touch a line. Coverage of the OpenAPI document and of generated cases is a different question, answered in Beyond Example-Based Tests.

Beyond Example-Based Tests

The tests above check examples you thought of. Two further techniques look for the ones you did not, and both reuse what is on this page:

  • Property-based testing. The OpenAPI document that FastAPI generates is a machine-readable contract. Schemathesis reads /openapi.json, generates requests with Hypothesis and checks every response against the declared schema and status codes; the same application and the same fixtures serve it. See Testing the Schema, and Testing Against It for the schema-level checks, and Property-based & Load Testing for Hypothesis, Schemathesis with pytest and Locust for load.

  • Security and load tests. Fuzzing authentication and authorization, rate limits and behaviour under load are run against a real server and are described on that page too; they complement, and do not replace, the TestClient suite.

Running the Suite in CI

A short, repeatable command is the contract between developers and the pipeline: install the test dependencies, run pytest --cov with the threshold, and publish the coverage report. Keep the environment close to production (the same Python minor version, the same pinned FastAPI, Pydantic and Starlette versions; FastAPI is still a 0.x library, so pin it) and run the database integration tests, if any, in a service container. A matrix over Python 3.10 to 3.14 is cheap insurance when you support several versions. Treat warnings as errors in CI, with the single named filter from the previous section, so that deprecations show up in a pull request instead of in an upgrade.

Pitfalls

  • Forgetting with TestClient(app). The lifespan does not run, state created at startup is missing and the failure looks like an AttributeError in the application. Use the context manager in the fixture.

  • Leaking overrides. app.dependency_overrides is global to the app object. Clear it in fixture teardown; otherwise the next test runs with the previous test’s fake.

  • Overriding the wrong application or the wrong key. The key is the function object in Depends(…​); a mounted sub-application has its own dictionary.

  • An in-memory SQLite without StaticPool or check_same_thread=False. Every connection sees an empty database, or the connection is used from another thread and SQLite raises. Both show up as no such table or a thread error.

  • Trusting SQLite for rules it does not enforce. Foreign keys, strict types and dialect details need the production engine somewhere in the pipeline.

  • Reading the real environment. A test that passes only because a developer’s .env exists. Build Settings(_env_file=None, …​) with explicit values and random secrets.

  • Hard-coded secrets in fixtures and examples. Generate throwaway keys (secrets.token_hex(32)); never reuse a production key, and never commit one.

  • Asserting on msg. Pydantic’s message text changes between releases; assert on type and loc.

  • Sleeping to wait for work. TestClient waits for background tasks, and time-dependent code (token expiry) is tested by constructing the input, as the expired-token test does with a negative lifetime.

  • Calling TestClient from an async def test. It blocks the test’s loop. Use AsyncClient with ASGITransport there.

  • Expecting the lifespan from AsyncClient. It does not run; use LifespanManager or the router’s lifespan_context.

  • A single TestClient for several WebSocket connections without with. Each connection gets its own loop; shared state can hang.

  • Expecting root_path to prefix the URL. It changes the scope and generated URLs only.

  • Expecting 403 for missing credentials. Since 0.122.0 the security classes answer 401.

  • Letting an unhandled exception surprise the test. By default it is raised in the test; pass raise_server_exceptions=False to assert on the 500.

  • Patching names instead of overriding dependencies. mock.patch ties the test to import paths; the override ties it to the seam.

  • Relying on test order. Module-level state (a global list, the app’s state, an lru_cache) survives between tests. Reset it in fixtures, as the lifespan test does with events.clear().

  • Running tests with an unpinned FastAPI. A new 0.x release can change behaviour, such as the move to 401, strict_content_type for JSON bodies or a different warning from the test client. Pin it and upgrade deliberately with the suite as the safety net.

  • Chasing 100% coverage. A threshold is a floor. A test with no assertion raises the number without checking anything.
