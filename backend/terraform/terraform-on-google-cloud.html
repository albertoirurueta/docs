Terraform on Google Cloud

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Google Cloud is the cloud Terraform is most often paired with outside AWS and Azure, and it is the one Google itself documents most heavily: there is a Google-maintained module collection, a managed Terraform service, and a set of published best practices. This page is the single place in this section where all of that comes together. It follows Providers and Backends and Remote State in the reading path, and it is the Google Cloud counterpart of Terraform on AWS and Terraform on Azure.

The baseline is Terraform 1.17 (released 2026-10-21) and OpenTofu 1.13, with the hashicorp/google and hashicorp/google-beta providers at their current major version, 8 (8.0.0 was released on 2026-08-26 and 8.8.0 on 2026-10-21). All values were checked against the provider’s own documentation and changelog, the Google Cloud documentation and the module repositories on 2026-10-23. Provider releases are weekly, so confirm the newest 8.x with terraform init -upgrade and the lock file before copying a constraint.

The examples use the Bookshelf scenario (catalog-api, reviews-api, web, PostgreSQL, Redis, a covers bucket, network, DNS, secrets and IAM). Project IDs, regions, service accounts and bucket names are placeholders (my-project-id, us-central1, bookshelf-example), and no credential, key or state of a real account appears anywhere. Secrets enter through TF_VAR_ variables, Secret Manager or federated identity, never through files in the repository.

The Google Cloud section of this site already documents the services themselves, and one page there carries a small Terraform baseline. This page does not repeat either. It adds what only Terraform users need.

Preparing a project

Terraform on Google Cloud always runs against a project. The project holds the resources, the quota and the billing link, and most provider resources take a project argument that falls back to the provider default. Creating the project (and its folder and organization) is a platform task that usually has its own configuration; see Resource hierarchy and projects. Everything on this page assumes an existing, billing-enabled project for the Bookshelf, ideally one project per environment.

Almost every Google Cloud service must be enabled before its API can be called, and the google_project_service resource does this. Its arguments are service (required), project, disable_on_destroy, disable_dependent_services, check_if_service_has_usage_on_destroy and deletion_policy.

variable "project_id" {
  type = string
}

locals {
  bookshelf_apis = [
    "artifactregistry.googleapis.com",
    "bigquery.googleapis.com",
    "cloudkms.googleapis.com",
    "cloudresourcemanager.googleapis.com",
    "compute.googleapis.com",
    "eventarc.googleapis.com",
    "iam.googleapis.com",
    "iamcredentials.googleapis.com",
    "logging.googleapis.com",
    "monitoring.googleapis.com",
    "pubsub.googleapis.com",
    "run.googleapis.com",
    "secretmanager.googleapis.com",
    "servicenetworking.googleapis.com",
    "sqladmin.googleapis.com",
    "storage.googleapis.com",
  ]
}

resource "google_project_service" "bookshelf" {
  for_each = toset(local.bookshelf_apis)

  project                    = var.project_id
  service                    = each.key
  disable_on_destroy         = false
  disable_dependent_services = false
}

Source: Terraform Registry — google_project_service

Three details matter in practice:

  • The default of disable_on_destroy changed in 7.0.0. It used to be true, which meant that destroying one google_project_service resource switched the API off for the whole project and could break unrelated workloads. Since 7.0.0 it has no default: destroying the resource only forgets it, and you must set disable_on_destroy = true explicitly to get the old behaviour. Setting it to false, as above, makes the intent visible. Google’s own module guidance goes further and says a module that activates APIs must set the equivalent option to false, because several instances of the module would otherwise disable each other’s services.

  • Enabling an API takes a moment to propagate. A resource that is created immediately afterwards can fail with a message that the API has not been used or is disabled. Give each resource a depends_on on the relevant google_project_service entry, or enable APIs in an earlier configuration (see the layered layout later on this page).

  • API calls are billed and rate-limited per project. The provider can group parallel google_project_service and IAM requests with its batching block; leave it alone unless you are certain you need it, as the provider reference advises.

The same page of the provider reference is also where Google’s quota rules appear. Service account credentials are associated with the project the account lives in, while credentials from gcloud are associated with a project owned by Google. The documented recommendation is to set the provider argument user_project_override to true for the latter, and then give billing_project (or the environment variable GOOGLE_BILLING_PROJECT) so that quota and billing are charged to your project and the caller needs serviceusage.services.use on it.

The google and google-beta providers

HashiCorp maintains two Google Cloud providers from the same code base. hashicorp/google supports generally available products and features. hashicorp/google-beta supports those plus Preview ones, and sends every request to the beta endpoint where one exists. The documentation is shared: fields and resources that exist only in the beta provider are marked in the provider reference. Using google-beta is comparable to using gcloud beta instead of gcloud.

You switch a single resource to the beta provider with its provider meta-argument. If you omit the argument, Terraform silently uses google, even when only a google-beta provider block exists. Both providers accept the same configuration arguments, but each needs its own block.

terraform {
  required_version = ">= 1.11"

  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 8.8"
    }
    google-beta = {
      source  = "hashicorp/google-beta"
      version = "~> 8.8"
    }
  }
}

variable "project_id" {
  type = string
}

variable "region" {
  type    = string
  default = "us-central1"
}

variable "environment" {
  type    = string
  default = "dev"
}

provider "google" {
  project = var.project_id
  region  = var.region

  default_labels = {
    application = "bookshelf"
    environment = var.environment
    managed-by  = "terraform"
  }
}

provider "google-beta" {
  project = var.project_id
  region  = var.region
}

# A resource that needs a Preview feature opts in explicitly:
# resource "google_compute_instance" "example" {
#   provider = google-beta
#   ...
# }

Source: Terraform Registry — Google Provider Versions and Google Provider Configuration Reference

The provider block takes defaults that most resources inherit, and a few arguments that change how the provider behaves.

Argument (environment variable) What it does

project (GOOGLE_PROJECT, GOOGLE_CLOUD_PROJECT, GCLOUD_PROJECT, CLOUDSDK_CORE_PROJECT)

The default project. A project argument on a resource takes precedence.

region and zone (GOOGLE_REGION, GOOGLE_ZONE, and CLOUDSDK_COMPUTE_REGION, CLOUDSDK_COMPUTE_ZONE)

The default region and zone for regional and zonal resources. The zone should be inside the region.

credentials, access_token, impersonate_service_account, impersonate_service_account_delegates, external_credentials

Authentication, described in the next section.

default_labels

Labels applied to every resource that has a top-level labels field. A label set on a resource overrides the default with the same key. Both end up in the computed terraform_labels and effective_labels attributes, so a label added by Google or by another tool does not produce a permanent diff on labels.

add_terraform_attribution_label and terraform_attribution_label_addition_strategy

Add the label goog-terraform-provisioned = true to resources, so they can be recognised in the console and gcloud. The label was introduced in 5.16.0 as opt-in, is added to newly created resources by default since 6.0.0, and the strategy PROACTIVE also adds it to existing resources on the next apply (CREATION_ONLY is the default).

user_project_override, billing_project

Choose which project is charged for quota and billing, see the previous section.

request_timeout, poll_interval, request_reason

The wait for one HTTP request (default 120 seconds), the pause between polls of a long-running operation (default 10 seconds; raising throughput is better done with -parallelism), and a justification sent in the X-Goog-Request-Reason header and recorded in the audit logs.

deletion_policy

A provider-wide default of DELETE, PREVENT or ABANDON. A deletion_policy set on a resource takes precedence.

batching

Groups parallel google_project_service and IAM requests. Avoid custom values unless needed.

{service}_custom_endpoint

Overrides the endpoint of one API, for example compute_custom_endpoint, for emulators or private endpoints. Best effort.

Source: Google Provider Configuration Reference

Two habits keep upgrades uneventful. First, commit .terraform.lock.hcl and constrain the minor version: Google’s own best practice for root modules is to pin each provider to a minor version and let patch releases flow in, which corresponds to a constraint like ~> 8.8.0. The ~> 8.8 used on this page accepts newer minors of the same major as well, which suits a documentation example, but a team that wants every provider change to be a reviewed pull request should use the tighter form together with a dependency bot. Second, treat a major version as a project: read the upgrade guide first, as described in the next subsection.

Upgrading across the 6, 7 and 8 majors

The provider ships a numbered upgrade guide for every major version. The guides say, in the same words each time, to upgrade to the last release of the previous major first, fix every deprecation warning, run terraform plan until it is clean, and only then raise the constraint. They also explain how to go back: if you ran only init or plan, downgrading the provider is enough; after refresh or apply, restore the previous state version from a versioned backend such as the gcs bucket described below.

Combine modules from both collections only after checking that their provider ranges overlap.

Authentication

The provider and the backend both authenticate with Application Default Credentials (ADC). ADC is the library strategy that looks for credentials in a fixed order: the GOOGLE_APPLICATION_CREDENTIALS environment variable, then the local file created by gcloud auth application-default login, then the service account attached to the compute resource that is running the code. Google documents ADC as the recommended way to authenticate Terraform, because the same configuration then runs unchanged on a laptop, in Cloud Shell and in production. The provider also has its own explicit arguments, which take precedence when set.

Where Terraform runs Recommended method Notes

A workstation

gcloud auth application-default login, optionally with impersonation of a deployer service account

User ADC credentials expire and are refreshed by logging in again. The command is separate from gcloud auth login.

Cloud Shell or Cloud Build

The identity of the session or the build’s service account

Cloud Shell already has Terraform and credentials.

A VM, GKE node or Cloud Run job on Google Cloud

An attached user-managed service account

Do not use the default compute service account: it is highly privileged. Make sure the cloud-platform scope is present.

GitHub Actions, GitLab CI, other OIDC issuers

Workload Identity Federation

No key file exists. See the section below and CI/CD and Automation.

HCP Terraform

Dynamic provider credentials, which are federation under the hood

See HCP Terraform and Terraform Enterprise.

Anywhere else

An external credential configuration file for the federation, or as a last resort a service account key

A key is a long-lived password. If one is unavoidable, store it in a secret manager, never in the repository.

Source: Google Cloud — Authentication for Terraform and Google Provider Configuration Reference

Local development with ADC

On a workstation, install the Google Cloud CLI, run gcloud init, and create the ADC file once. Nothing is written into the Terraform directory.

gcloud auth application-default login

# Optional: tell Terraform which project pays for quota when using user credentials
export GOOGLE_PROJECT="my-project-id"
export GOOGLE_BILLING_PROJECT="my-project-id"
export USER_PROJECT_OVERRIDE=true

terraform init
terraform plan -out=tfplan

Source: Google Cloud — Authentication for Terraform

Impersonating a deployer service account

A person should not run production changes with their own broad permissions. The usual pattern is to give each environment a deployer service account that holds the roles Terraform needs, and to let a small group of people (and the CI identity) act as it. Terraform then runs as that account while the caller’s own identity only needs one role on it, roles/iam.serviceAccountTokenCreator. Permissions and quotas are evaluated against the impersonated account. You can configure it in three equivalent ways:

  • with the provider argument impersonate_service_account (and impersonate_service_account_delegates for a delegation chain);

  • with the environment variable GOOGLE_IMPERSONATE_SERVICE_ACCOUNT, which is the best choice when the same configuration is run by different identities in different places;

  • with gcloud auth application-default login --impersonate-service-account=EMAIL, which writes an ADC file that already impersonates the account, so neither the provider block nor the backend block need to mention it.

variable "project_id" {
  type = string
}

resource "google_service_account" "deployer" {
  project      = var.project_id
  account_id   = "bookshelf-deployer"
  display_name = "Bookshelf Terraform deployer"
}

# Narrow roles: grant only what the configuration manages. This one lets the
# deployer manage Cloud Run services; add others per layer.
resource "google_project_iam_member" "deployer_run_admin" {
  project = var.project_id
  role    = "roles/run.admin"
  member  = google_service_account.deployer.member
}

# Who may act as the deployer: a group of platform engineers, not individuals.
resource "google_service_account_iam_member" "deployer_token_creator" {
  service_account_id = google_service_account.deployer.name
  role               = "roles/iam.serviceAccountTokenCreator"
  member             = "group:bookshelf-platform@example.com"
}

Source: Terraform Registry — google_service_account and google_service_account_iam

export GOOGLE_IMPERSONATE_SERVICE_ACCOUNT="bookshelf-deployer@my-project-id.iam.gserviceaccount.com"
terraform plan

Source: Google Provider Configuration Reference — Impersonating Service Accounts and google_service_account_iam

The provider reference also describes a variation worth knowing: an ephemeral access token. The google_service_account_access_token ephemeral resource mints a short-lived token for a target service account, and a second, aliased google provider block can take it as access_token. The token never reaches the state or the plan, which makes it a good fit when one configuration must act as several service accounts. Because Terraform cannot renew an access token, a very long apply can outlive it (the default lifetime is one hour), and the documentation recommends credentials that can be refreshed in that case.

provider "google" {
  # Bootstrap identity: ADC of the person or pipeline running Terraform.
}

ephemeral "google_service_account_access_token" "network_admin" {
  provider               = google
  target_service_account = "bookshelf-network@my-project-id.iam.gserviceaccount.com"
  scopes                 = ["cloud-platform"]
  lifetime               = "1800s"
}

provider "google" {
  alias        = "network"
  access_token = ephemeral.google_service_account_access_token.network_admin.access_token
}

Source: Terraform Registry — google_service_account_access_token (ephemeral)

Workload Identity Federation from CI

A pipeline running on GitHub, GitLab or another OIDC issuer should not hold a service account key. Instead, Google Cloud trusts the issuer through a workload identity pool and a provider in that pool, and the pipeline exchanges its short-lived OIDC token for Google credentials. The Terraform resources for the pool and provider (google_iam_workload_identity_pool, google_iam_workload_identity_pool_provider) and the roles/iam.workloadIdentityUser binding, together with the mandatory attribute condition that stops other repositories from using the trust, are shown in the Google Cloud part of CI/CD and Automation, and the Google Cloud side of the concept is explained in Identity and Access. They are not repeated here.

What belongs on this page is how the resulting credentials meet Terraform. The google-github-actions/auth action (major version 3 at the time of writing) exchanges the OIDC token and, by default, writes a credentials file and exports GOOGLE_APPLICATION_CREDENTIALS. Both the provider and the gcs backend read ADC, so no further Terraform configuration is needed. The workflow needs id-token: write, and the checkout step must run before the auth step.

name: terraform-plan
on:
  pull_request:

permissions:
  contents: read
  id-token: write

jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7

      - uses: google-github-actions/auth@v3
        with:
          workload_identity_provider: ${{ vars.GCP_WORKLOAD_IDENTITY_PROVIDER }}
          service_account: ${{ vars.GCP_TERRAFORM_SERVICE_ACCOUNT }}

      - uses: hashicorp/setup-terraform@v4

      - run: terraform init -input=false
      - run: terraform plan -input=false -lock-timeout=5m

Source: google-github-actions/auth README, actions/checkout and hashicorp/setup-terraform

With service_account set, the action uses federation through a service account, which needs roles/iam.workloadIdentityUser on it; without it, it uses direct federation and the pool principal itself receives roles on the resources. The action’s README warns that the GitHub token lives five minutes, so derived credentials last five minutes too, and that changes to pools and providers can take a few minutes to propagate.

The provider also supports federation without a credentials file. Its external_credentials block (added in 6.28.0) takes an audience, a service_account_email and an identity_token, builds a federated credential from the token, and takes precedence over credentials and access_token. It was designed for HCP Terraform Stacks, where the platform hands the configuration an identity token, and the provider has a guide for that case; see Terraform Stacks. Like an access token, the credential built from it cannot be renewed, and the documentation suggests a credentials file with a federation configuration for runs that last longer than the token.

Pitfalls of credentials

  • The environment variable GOOGLE_CREDENTIALS is read by both the provider and the gcs backend. If the state bucket and the infrastructure need different identities, set GOOGLE_BACKEND_CREDENTIALS (or the backend’s own impersonate_service_account) for the backend.

  • Service account keys end up in places they should not: a google_service_account_key resource stores the private key in state, which is why Google’s security guidance lists it, together with tls_private_key and google_client_config, among the resources that keep secrets in plain text in state.

  • A 403 shortly after granting a role is often eventual consistency. The gcs backend documentation says IAM changes to buckets can take a few minutes to take effect, during which Terraform reports 403 errors.

The gcs backend

The gcs backend stores the state as an object in a Cloud Storage bucket and supports locking. The bucket must exist before the backend is configured, which creates a bootstrap problem solved below. The Terraform documentation puts the recommendation first: turn on Object Versioning on the bucket, so an accidental deletion or a bad write can be undone.

terraform {
  required_version = ">= 1.11"

  backend "gcs" {
    bucket = "bookshelf-tfstate-my-project-id"
    prefix = "bookshelf/network"
  }
}

Source: Terraform Docs — Backend type: gcs

The configuration arguments are:

Argument (environment variable) Meaning

bucket

Required. The bucket name, globally unique.

prefix

Optional. A folder inside the bucket. The default workspace is stored at <prefix>/default.tfstate, and a named workspace at <prefix>/<name>.tfstate.

credentials (GOOGLE_BACKEND_CREDENTIALS, GOOGLE_CREDENTIALS)

Local path to credentials in JSON format. Unset means ADC. The identity needs the Storage Object Admin role on the bucket.

impersonate_service_account (GOOGLE_BACKEND_IMPERSONATE_SERVICE_ACCOUNT, GOOGLE_IMPERSONATE_SERVICE_ACCOUNT) and impersonate_service_account_delegates

Service account to impersonate for the state bucket only. The caller needs the Token Creator role on it.

access_token

A temporary OAuth 2.0 token, used instead of credentials when both are set.

kms_encryption_key (GOOGLE_KMS_ENCRYPTION_KEY)

A Cloud KMS key, in the form projects/PROJECT/locations/LOCATION/keyRings/RING/cryptoKeys/NAME, used to read and write state (customer-managed encryption key, CMEK).

encryption_key (GOOGLE_ENCRYPTION_KEY)

A 32-byte base64-encoded customer-supplied encryption key (CSEK).

storage_custom_endpoint (GOOGLE_BACKEND_STORAGE_CUSTOM_ENDPOINT, GOOGLE_STORAGE_CUSTOM_ENDPOINT)

A Private Service Connect endpoint for the Cloud Storage API: protocol, DNS name and the path /storage/v1/b.

Source: Terraform Docs — Backend type: gcs

Several behaviours are worth stating precisely:

  • Locking is implemented with a second object next to the state, <prefix>/<name>.tflock, which the backend creates only if it does not already exist and removes with a generation check when the run ends. A second run therefore fails immediately with a lock error that names the object, instead of overwriting the state. If a run is killed, remove the lock with terraform force-unlock LOCK_ID after making sure nobody is still running. The file name is visible in the backend source rather than in the documentation, so treat it as an implementation detail and rely on -lock-timeout and force-unlock in scripts. See State for locking in general.

  • Credentials in the block are copied into .terraform and into plan files. The documentation warns that values passed with -backend-config or written into the block end up in the .terraform directory and in saved plans, and recommends environment variables for credentials and other sensitive values. Keep the block free of secrets and supply the bucket through a partial configuration if the same code serves several environments, as described in Backends and Remote State.

  • A mistake from older tutorials: a gcs block takes bucket and prefix, never key or region, which are arguments of the S3 backend.

  • Encryption has two flavours with different consequences. For customer-managed keys in Cloud KMS, Terraform can migrate between keys or away from CMEK by itself, because Google keeps the key and the change takes effect on the next write. The project’s Cloud Storage service agent must be allowed to use the key (the Cloud KMS CryptoKey Encrypter/Decrypter role). For customer-supplied keys, Terraform cannot migrate state away from or between keys, because Google does not store them and Terraform loses the old key when the configuration changes: you must first rewrite the object with the old key. In both cases a lost or deleted key makes the state unrecoverable. Reading CMEK-encrypted state through terraform_remote_state needs no key in its config.

  • Private access: storage_custom_endpoint points the backend at a Private Service Connect endpoint, which keeps state traffic off the public path in locked-down networks.

Creating the state bucket

The chicken-and-egg problem has a simple resolution, which Google’s own tutorial uses: create the bucket with a small configuration that has a local backend, add the gcs backend block afterwards, and run terraform init -migrate-state to move the state into the bucket. Many teams keep this bootstrap configuration in its own repository or directory and keep its state in the bucket it created, or accept that it has a local state that is stored with the platform team’s documentation; either choice is fine as long as it is deliberate. The gcloud equivalent is in Infrastructure as Code on Google Cloud.

A state bucket has requirements that ordinary buckets do not: only the pipeline and a few administrators may touch it, object versions must be kept (with a cap, because every apply writes a new version), the bucket must not be deletable by mistake, and public access must be impossible.

Cloud Storage’s own documentation explains that versioning and soft delete have different costs; the lifecycle rule above limits the former. The num_newer_versions condition cannot be set to 0 from Terraform, as the provider documents.

terraform init

    bucket = "bookshelf-tfstate-my-project-id"

locals {
  subnet_id = data.terraform_remote_state.network.outputs.app_subnet_id

Infrastructure Manager

Infrastructure Manager (Infra Manager) is Google Cloud’s managed Terraform service. You hand it a Terraform configuration, which it calls a blueprint, from a Cloud Storage bucket, a Git repository or a local directory. It creates a deployment, runs Terraform for you inside an ephemeral Cloud Build environment under a service account that you choose, keeps the state, and records every revision with its logs, its configuration, the list of created resources and the state file. Each deployment has the same life cycle you know from the CLI: the service runs terraform init, validate and apply (or destroy when you delete the deployment), and it retries init and apply a limited number of times after transient failures such as network outages. A preview shows the plan without changing anything. The service does not deploy applications onto the resources; Google points to Cloud Build, Cloud Deploy and App Lifecycle Manager for that.

The Google Cloud section covers the first steps, roles and console flow in Infrastructure as Code on Google Cloud. This section concentrates on what changes for someone who already knows Terraform.

Constraints on the configuration

Infra Manager imposes rules that ordinary Terraform does not:

  • There is no backend block. The documentation says backend blocks should not be defined: the service owns the state. The state is available as a file by locking the deployment, downloading it through a signed URL and uploading it again (gcloud infra-manager deployments lock, export-statefile, import-statefile, unlock); the permissions for that are part of roles/config.admin.

  • The entry point must be a plain root module. Templating or generation of Terraform is not supported.

  • No personal or sensitive data in configuration values, and provisioners are discouraged because the runtime environment can change at any time.

  • The Terraform version is chosen from a short list. The page "Terraform and Infrastructure Manager" lists the supported versions with their lifecycle dates. When this page was written (the documentation was last updated on 2026-10-20) the list contained 1.2.3 (deprecated from 2026-01-08, end of support 2026-02-08, auto-migrated to 1.5.7), 1.3.10, 1.4.7 and 1.5.7, and the newest entry was 1.5.7. By default the latest supported version is used, --tf-version-constraint selects one, and an update can raise the version but never lower it. Deprecated versions give a warning, and an obsolete version fails new deployments; an organization policy can opt in to automatic migration (gcloud infra-manager automigrationconfig enable-auto-migration).

  • Creating or updating a deployment times out after two hours, and a preview after one. Large configurations should be split into several deployments.

The version list has direct consequences for how you write the code. Everything introduced after Terraform 1.5 is out of reach: ephemeral resources, write-only arguments (1.10 and 1.11), provider-defined functions, removed blocks (1.7), and terraform test (1.6) do not apply, and a module that declares a required_version of >= 1.12.2, which is what the Cloud Foundation Fabric modules do, cannot be used at all. The Cloud Foundation Toolkit network module, whose requirement is >= 1.3, can. Infra Manager can also use either the HashiCorp-maintained provider (the default) or a service-maintained copy of google and google-beta, selected with --provider-source=SERVICE_MAINTAINED; the supported provider versions per region are listed in a manifest.json in a Google-maintained bucket. Check the compatibility of your provider constraint with those versions before the first deployment.

Deploying with gcloud

Before the first deployment, enable the config.googleapis.com API and create the service account the deployment runs as. Grant it roles/config.agent in the project that runs Infra Manager, plus the roles the resources need (and, for the resources being deleted by an update, the permissions to delete them). People who create deployments need roles/config.admin and roles/iam.serviceAccountUser on that service account. When the service account lives in another project than the deployment, extra grants are needed: the organization policy constraint iam.disableCrossProjectServiceAccountUsage must not be enforced on the service account’s project, and the Infra Manager service agent needs roles/iam.serviceAccountUser there.

PROJECT_ID="my-project-id"
LOCATION="us-central1"
SA="projects/${PROJECT_ID}/serviceAccounts/bookshelf-im@${PROJECT_ID}.iam.gserviceaccount.com"

# Preview first: the plan, without changes
gcloud infra-manager previews create \
  "projects/${PROJECT_ID}/locations/${LOCATION}/previews/bookshelf-covers-preview" \
  --service-account="${SA}" \
  --local-source=./covers \
  --input-values="project_id=${PROJECT_ID}"

# Create or update the deployment
gcloud infra-manager deployments apply \
  "projects/${PROJECT_ID}/locations/${LOCATION}/deployments/bookshelf-covers" \
  --service-account="${SA}" \
  --local-source=./covers \
  --input-values="project_id=${PROJECT_ID}" \
  --quota-validation=ENFORCED

# Inspect the result
gcloud infra-manager deployments describe \
  "projects/${PROJECT_ID}/locations/${LOCATION}/deployments/bookshelf-covers"

Source: Google Cloud — Deploy infrastructure using Infrastructure Manager and Preview a deployment

Use --gcs-source gs://BUCKET/OBJECT for a zipped configuration in Cloud Storage (versioned buckets let you pin a generation), or --git-source-repo, --git-source-directory and --git-source-ref for Git. A private repository must first be connected to Cloud Build or Developer Connect. --quota-validation can be ENABLED (report) or ENFORCED (fail when quota is insufficient); leaving it out disables the check, and it only covers a limited set of resources.

A deployment is deleted with gcloud infra-manager deployments delete, which destroys the resources; the option --delete-policy=abandon removes the deployment but leaves the resources in place, which is the safe way to hand them to a different tool.

Managing deployments with Terraform itself

The provider has a resource for the deployment, google_config_deployment, so even the Infrastructure Manager layer can be code. Its required arguments are name, location, service_account and a terraform_blueprint block with either a gcs_source or a git_source (repo, directory, ref) and any number of input_values blocks. Optional arguments include tf_version_constraint, artifacts_gcs_bucket, worker_pool, quota_validation, import_existing_resources and force_destroy. The documentation describes the Git source as a public repository.

resource "google_config_deployment" "covers" {
  name            = "bookshelf-covers"
  location        = var.region
  service_account = "projects/${var.project_id}/serviceAccounts/bookshelf-im@${var.project_id}.iam.gserviceaccount.com"

  terraform_blueprint {
    git_source {
      repo      = "https://github.com/example-org/bookshelf-infrastructure"
      directory = "covers"
      ref       = "v1.0.0"
    }

    input_values {
      variable_name = "project_id"
      input_value   = var.project_id
    }
  }

  quota_validation = "ENFORCED"
}

Source: Terraform Registry — google_config_deployment

Choosing between Infrastructure Manager and a pipeline you run

Infra Manager removes the need to host a runner, to store state yourself and to hand credentials to a CI system: the deployment runs as a service account inside Google Cloud, previews and revisions are first-class, and audit logs record who changed what. The price is a Terraform version of at most 1.5.7 on the documented list, state that you reach only through the lock, export and import commands, and none of the language and CLI features added since. A pipeline that you operate (see CI/CD and Automation), or HCP Terraform (HCP Terraform and Terraform Enterprise), gives you the current language and CLI, at the cost of running more yourself. Many teams use Infra Manager for a few well-bounded foundations, for example a landing-zone repository, and a normal pipeline for application stacks. Config Connector and Deployment Manager are covered in the Google Cloud section. Deployment Manager support was discontinued on 2026-04-01, the maximum extension of support for migration blockers ends on 2027-03-31, and the service is turned down after 2027-06-30; Infra Manager is the migration target.

The generic mechanics of consuming a module (versions, source forms, ?ref= for Git, the lock of module selections in .terraform/modules) are in Modules, and writing your own is in Module Development and Publishing. Three things are specific to Google’s collections:

  1. Pin tightly and read the changelog. Both collections release frequently and make breaking changes in major versions. A registry module takes a version constraint; a Fabric module is referenced by a Git source with a tag, or by a path in a fork of the repository, which is the approach the repository itself recommends.

  2. Check the provider range. A module declares a minimum and a maximum provider version. If two modules disagree, terraform init fails; this is the usual reason an upgrade to a new provider major must wait for the modules.

  3. Check the Terraform floor. A module that needs a newer language than your runner offers (for example Fabric modules with Infrastructure Manager) cannot be used.

The network: VPC, subnets and firewall rules

A custom-mode VPC with explicit subnets is the only sensible starting point: auto_create_subnetworks creates a subnet in every region from 10.128.0.0/9 when set to true, which collides with anything you later connect.     app = {
      cidr = "10.10.0.0/24"
    }
    data = {
      cidr = "10.10.1.0/24"
    }
  }

  firewall_rules = {
    allow-iap-ssh = {
      source_ranges = ["35.235.240.0/20"] # Identity-Aware Proxy TCP forwarding
      target_tags   = ["web"]
      protocols     = { tcp = ["22"] }
    }
    allow-health-checks = {
      source_ranges = ["35.191.0.0/16"] # Google Cloud health checks
      target_tags   = ["web"]
      protocols     = { tcp = ["80", "443"] }
    }
  }
}

Google Cloud firewall rules are stateful, apply to a whole VPC network, and are matched by target tag or target service account, never by subnet. Several details of this resource explain most of the surprises people meet:

  • edition has a version-dependent default. If it is omitted, instances with POSTGRES_16 or later default to ENTERPRISE_PLUS, which supports only predefined db-perf-optimized-N-* machine types. A shared-core or custom tier such as db-f1-micro, db-g1-small or db-custom-* then fails at creation with an invalid tier error. Set edition explicitly, as above, or pick a performance-optimized tier.

  • Two protections exist and are different. deletion_protection on the resource (it defaults to protecting when unset) only stops Terraform; settings.deletion_protection_enabled is enforced by the API on every surface. Google’s best practices additionally suggest lifecycle { prevent_destroy = true } for databases and the state bucket, which makes the plan itself fail.

  • Changing database_version upgrades the engine in place, and maintenance_version controls the minor software version. Plan major version upgrades as projects of their own, and read the argument include_replicas_for_major_version_upgrade.

  • MySQL 5.7 is not a good choice. The provider’s list of database_version values still includes MYSQL_5_7, but Google’s policy page lists 5.7 with extended support (paid) since 2025-02-01 and deprecation on 2028-02-01. All instances running a community end-of-life major version are enrolled in extended support and billed for it. Use MYSQL_8_4 or later for MySQL.

  • settings.ip_configuration.require_ssl no longer exists. It was replaced by ssl_mode, with the values ALLOW_UNENCRYPTED_AND_ENCRYPTED, ENCRYPTED_ONLY and TRUSTED_CLIENT_CERTIFICATE_REQUIRED (not available for SQL Server); the removal was made in provider 6.0.1.

  • Private IP is not enough for the instance to be reachable: Cloud Run needs Direct VPC egress or a connector, and engineers need the Cloud SQL Auth Proxy or IAP. ipv4_enabled must be true or a private_network configured; here only the latter is set.

The google_sql_ssl_cert resource still exists for client certificates, but the provider documents that all its arguments, including the private key, are stored in plain text in state. Prefer ssl_mode = ENCRYPTED_ONLY together with the Cloud SQL Auth Proxy or the language connectors, which verify the server through IAM and do not need client certificates; see Cloud SQL.

A read replica is another instance that names the primary in master_instance_name; the provider documents that replication requires existing backups (and binary logging for MySQL) on the primary. Promoting a replica to a standalone instance is done by setting instance_type to CLOUD_SQL_INSTANCE and removing the master reference.

The database user and its password

A google_sql_user with a literal password argument writes the password into state, which is exactly the anti-pattern the next major section describes. Since Terraform 1.11 the resource accepts a write-only password, password_wo, which is sent to the API but never stored, together with password_wo_version, which you increment to rotate. Provider 7.0.0 made the two arguments mandatory as a pair. The value itself can come from an ephemeral read of Secret Manager, so that it never reaches state or the plan either:

resource "google_secret_manager_secret" "db_password" {
  project   = var.project_id
  secret_id = "bookshelf-${var.environment}-db-password"

  replication {
    auto {}
  }
}

# The first version is added outside Terraform, for example:
#   printf '%s' "$NEW_PASSWORD" | gcloud secrets versions add bookshelf-dev-db-password --data-file=-
# An ephemeral resource is opened during plan, so the version must exist before the user is planned.

ephemeral "google_secret_manager_secret_version" "db_password" {
  project = var.project_id
  secret  = google_secret_manager_secret.db_password.secret_id
  version = "latest"
}

resource "google_sql_user" "catalog_api" {
  project             = var.project_id
  instance            = google_sql_database_instance.main.name
  name                = "catalog_api"
  password_wo         = ephemeral.google_secret_manager_secret_version.db_password.secret_data
  password_wo_version = 1
}

Source: Terraform Registry — google_sql_user, google_secret_manager_secret_version (ephemeral) and Using write-only arguments

Ephemeral resources are explained in Sensitive Data, Ephemeral Resources and Write-only Arguments. Because the ephemeral read happens at plan time, the very first apply of a fresh environment needs two steps: create the secret container (target the google_secret_manager_secret resource, or apply a separate layer), add a version with gcloud, then apply the rest. The secret then lives in Secret Manager, its version history is controlled by IAM, and rotation is a new version plus an increment of password_wo_version.

Points worth knowing about this resource:

  • containers.env is a set since 6.0.0, so values are addressed by name and no longer by index, and several env blocks with different names never reorder. Literal values do not support variable references; secrets come from value_source.secret_key_ref, which takes the secret name and a version (latest or a number), and the runtime service account needs roles/secretmanager.secretAccessor on it, which is why the depends_on above is there.

  • Image tags are the application’s deployment mechanism. A Terraform run that changes catalog_api_tag creates a new revision. If CI deploys images with gcloud run deploy, Terraform will want to revert them; either let Terraform own the tag (as above) or add lifecycle { ignore_changes = [template[0].containers[0].image] } and let the pipeline own it. Never apply latest to production.

  • Direct VPC egress (the network_interfaces block, a single interface) needs no connector resource. With egress set to PRIVATE_RANGES_ONLY only traffic to private ranges enters the VPC. The older Serverless VPC Access connector is still available through connector but costs instances.

  • Ingress and invokers are separate controls: ingress limits where requests may come from, while roles/run.invoker decides who may call. Granting it to allUsers makes a service public; do that only for a service that must be public. The provider also has invoker_iam_disabled for services that need no IAM check.

  • Scaling has a service-level scaling block (not used here) and a revision-level template.scaling. See Cloud Run scaling, traffic and jobs for what each setting means.

Secrets, security and resilience

The second half of the rebuild is about what must not leak and what must survive. It follows the same layers: secrets and keys in the data layer, IAM in every layer, and logging, alerts and recovery in the observability layer. The general mechanics of sensitive values (the sensitive flag, ephemeral values, write-only arguments, state encryption) are in Sensitive Data, Ephemeral Resources and Write-only Arguments; this part is about how they apply to Google Cloud resources.

Where secrets leak

The usual ways a Terraform project leaks a secret on Google Cloud, in order of how often they happen, are:

Anti-pattern Better

A password or API key written as a literal in a .tf file, committed to Git

A variable with no default, supplied through a TF_VAR_ environment variable, a secret store, or an ephemeral read. See Variables, Outputs and Locals.

A terraform.tfvars file with secret values, committed or copied between machines

.tfvars files for non-secret settings only; ignore files that hold anything else.

secret_data on google_secret_manager_secret_version, a password on google_sql_user, a google_service_account_key, a tls_private_key, a google_sql_ssl_cert

These write the value into state in plain text. Use the write-only arguments (secret_data_wo, password_wo), generate or read values outside Terraform, or avoid keys altogether.

State in a bucket that many people can read, or a state file archived by CI as an artefact

Secret Manager

A secret has two parts in Secret Manager and in Terraform. The secret (google_secret_manager_secret) is a named container with replication, labels, rotation and expiry settings. A version (google_secret_manager_secret_version) holds the payload. Terraform can manage both, but the payload is the part that must stay out of state. The service itself is covered in Secret Manager and KMS.

The arguments of the secret that matter most:

Argument Effect

secret_id and replication

The ID, and either auto {} (Google chooses the replication) or user_managed with explicit replicas, optionally with a customer-managed key per replica.

ttl or expire_time

Make the secret expire (a duration in seconds such as 2592000s, or an RFC 3339 timestamp). Only one can be set. They are for temporary secrets: a database password that expires silently takes the application down.

version_destroy_ttl

A delay between a destroy request on a version and its real destruction. During the delay the version is disabled, which gives a window to notice a mistake.

rotation and topics

Secret Manager publishes a notification to the configured Pub/Sub topics at next_rotation_time and then every rotation_period. It does not rotate anything by itself; something must subscribe, create a new version and change the system the secret protects. topics must be set for rotation.

annotations, labels, tags

Metadata. Annotations and labels are non-authoritative, like other labels in this provider.

deletion_protection

Prevents Terraform from destroying the secret; defaults to false.

Source: Terraform Registry — google_secret_manager_secret

For the payload there are two options. secret_data is sensitive in plan output but is stored in state. secret_data_wo is write-only: it is sent to the API and never stored, so a rotation is expressed by changing secret_data_wo_version, which Terraform does store and compare. The two are mutually exclusive. Provider 8.0.0 changed the contract: secret_data_wo_version became a string (existing state converts on the first apply), and it is required whenever secret_data_wo is set, with the old implicit default of 0 removed. If your configuration still has an integer there, quote it before upgrading.

  sensitive = true
  ephemeral = true

  secret_data_wo         = var.reviews_api_key
  secret_data_wo_version = "1"
  deletion_policy        = "DISABLE"
}

Source: Terraform Registry — google_secret_manager_secret_version

For rotation notifications to be delivered, the Secret Manager service agent needs roles/pubsub.publisher on the topic, as the provider documents; that agent can be created with google_project_service_identity (a beta resource, as described below) and granted with google_pubsub_topic_iam_member.

Run it with TF_VAR_reviews_api_key in the environment (it is never printed because the variable is both sensitive and ephemeral), and increment secret_data_wo_version (a string) when you want a new version. deletion_policy set to DISABLE makes terraform destroy disable the version instead of destroying it, and ABANDON leaves it alone; the default destroys.

Two lifecycle points deserve care when secret_data (not the write-only argument) is used. Changing the data replaces the version resource, so a plain replacement destroys the old version before the new one exists unless you ask for the other order with lifecycle { create_before_destroy = true }; with that setting consumers that read latest never see a moment with no enabled version. And a secret that has a ttl or expire_time will disappear on schedule even though Terraform still lists it, so treat the expiry as part of the contract, not as a clean-up.

Reading secrets back into Terraform has the same two options. The google_secret_manager_secret_version data source puts the payload into state; the ephemeral resource with the same name does not (see the Cloud SQL user earlier). The only legitimate reason to use the data source is a value that is not secret.

Cloud KMS and customer-managed encryption keys

Google encrypts data at rest by default. Customer-managed encryption keys (CMEK) in Cloud KMS give you control of the key’s rotation, disablement and audit trail, and satisfy policies that require it. They are configured per resource: Cloud Storage buckets (encryption.default_kms_key_name), Cloud SQL (encryption_key_name), Pub/Sub topics (kms_key_name), BigQuery datasets (default_encryption_configuration), Secret Manager (customer_managed_encryption with kms_key_name, inside replication) and the state backend (kms_encryption_key).

Three properties of Cloud KMS shape the Terraform code. A key ring and a key cannot be deleted from a project; destroying the Terraform resource only removes it from state, and for a key it also deletes the key versions, after which anything encrypted with it is unrecoverable (versions pass through a scheduled-destruction period, 30 days by default, configurable with destroy_scheduled_duration when the key is created). The rotation_period must be longer than a day. And each Google service that uses your key does so through its own service agent, which must be granted roles/cloudkms.cryptoKeyEncrypterDecrypter on the key, before the dependent resource is created.

IAM: authoritative or not

Google Cloud IAM resources in the provider come in three flavours for every kind of resource, and mixing them is the most common source of surprising plans:

Resource Behaviour

*_iam_policy

Authoritative for the whole policy of the target: replaces everything, including bindings added by other tools or by Google. Use it only on resources you fully own; on a project it can lock you out.

*_iam_binding

Authoritative for one role on the target: the members listed are the members, others are removed.

*_iam_member

Non-authoritative: adds one member to one role and leaves everything else alone. The default choice.

Source: Terraform Registry — google_project_iam

Together with the earlier advice, the practical rules are: grant roles with the member form; scope each grant as narrowly as possible (a role on a secret, a bucket, a service or a repository beats a role on the project); use predefined roles, and a custom role only when no predefined role fits; and never grant the basic Owner, Editor or Viewer roles to workloads. The provider’s member attribute on google_service_account produces the right serviceAccount: string.

A custom role and a conditional grant look like this. IAM conditions use Common Expression Language and apply to the binding they are attached to; the example grants a contractor temporary read access to logs.

  role_id     = "bookshelfOperator"
  title       = "Bookshelf operator"
  description = "Restart Cloud Run revisions and read logs, nothing else"
  stage       = "GA"

  permissions = [
    "run.services.get",
    "run.services.list",
    "run.revisions.list",
    "logging.logEntries.list",
  ]
}

resource "google_project_iam_member" "contractor_logs" {
  project = var.project_id
  role    = "roles/logging.viewer"

The role_id of a custom role is camel case and cannot contain a hyphen. Custom roles are for a project or an organization and need stage to say whether they are in alpha, beta or general availability. The permissions list must be checked against the permissions the services actually need; use the IAM Recommender and the audit logs rather than guesswork.

The external data source, which the book uses to compute IAM values with scripts, is an escape hatch with a clear protocol: a program reads a JSON object of strings from standard input and prints a JSON object of strings on standard output, and runs on every refresh. Its documentation warns that it hurts portability and that it is not recommended in Terraform Enterprise. Almost everything IAM needs is available through provider resources and data sources (for example google_iam_policy, google_project, google_service_account), so reach for external last.

Securing the remote state

The state bucket is the most sensitive object of the whole configuration. Most of the work is in the bootstrap section; the checklist below connects the controls to Google’s guidance.

  • Access: only the deployer service accounts and a small administrator group hold roles/storage.objectAdmin or higher on the bucket. Developers get plan-only identities (read-only roles on resources, and the permission to read the state) if the pipeline cannot run plans for them.

  • Encryption: the default Google-managed encryption always applies; add a customer-managed key through kms_encryption_key for stricter control. Google’s security page also mentions customer-supplied keys through GOOGLE_ENCRYPTION_KEY, with the migration limitations described earlier. OpenTofu can additionally encrypt state client side.

  • Locking: provided by the backend; do not disable it with -lock=false in automation.

  • Versioning and soft delete: on, with a lifecycle cap, so recovery is possible without unbounded cost.

  • Audit: Data Access audit logs for Cloud Storage record reads of state objects; see the audit section below.

  • Separation: one bucket (or at least one prefix and IAM boundary) per trust boundary, as Google’s separation-of-duties guidance says. A network team’s state should not be readable by the application team that merely consumes its outputs.

  • Not in the repository: ignore .terraform/, *.tfstate* and saved plans, which hold the same secrets.

Source: Google Cloud — Best practices for security

Resilience and recovery

A Terraform configuration is a recovery plan for infrastructure, not for data. Plan for four kinds of loss:

Loss Mechanism

The database

Automated backups with a retention count, point-in-time recovery, regional high availability, and a read replica in another region for disaster recovery (all shown above). Restoring is an operation on the instance, not a Terraform action.

A VM’s disk

A snapshot schedule: a google_compute_resource_policy with a snapshot_schedule_policy (a daily schedule, a retention in days, snapshot labels and storage location), attached to each disk with google_compute_disk_resource_policy_attachment. on_source_disk_delete defaults to KEEP_AUTO_SNAPSHOTS.

Objects

Versioning and soft delete on the bucket, a lifecycle rule that caps the versions, and a backup bucket in a different location that a transfer job or the application fills. Lifecycle rules can also move old objects to colder storage classes with SetStorageClass.

The configuration and the state

Git for the former, a versioned bucket for the latter; the whole project can be rebuilt by applying the layers in order against an empty project. Test that claim in a throwaway project at least once.

Source: Terraform Registry — google_compute_resource_policy and google_storage_bucket

DNS plays a part in failover: users reach the Bookshelf through a name, so keep the TTL of the records that point at it low enough that a switch to another region takes effect quickly, and manage the zone and record sets in their own layer (google_dns_managed_zone, google_dns_record_set) so that rebuilding an application layer never touches them. Cloud DNS is described in Cloud DNS and certificates.

Clean up

Everything above creates billable resources: Cloud SQL with high availability and a replica, Cloud Run, Pub/Sub, BigQuery, Cloud KMS keys, VMs and buckets. Destroy a practice environment as soon as you finish. Because the examples deliberately resist deletion, destroying them is a short procedure, not a single command.

  1. Lower the protections first, and apply that change. Protection arguments are checked against state, so changing them and destroying in one step does not work. The arguments are deletion_protection on google_cloud_run_v2_service, google_sql_database_instance, google_bigquery_table and google_container_cluster; settings.deletion_protection_enabled on Cloud SQL; force_destroy on buckets that still hold objects; and deletion_policy where it is PREVENT. The simplest way is a variable that every protected resource reads.

  2. Destroy the layers in reverse order: observability, apps, data, network, bootstrap.

  3. Deal with the resources that cannot be deleted. Cloud KMS key rings and keys stay in the project; destroying the Terraform resource schedules the key versions for destruction (30 days by default) and makes anything encrypted with the key unrecoverable. If the key must outlive the configuration, forget it with a removed block instead.

  4. Handle the private services connection. The VPC peering behind google_service_networking_connection is not a separate resource and can block deletion of the network. Set deletion_policy to REMOVE_PEERING (or ABANDON, which leaves the peering in place) and apply before destroying.

  5. Destroy the state bucket last, after migrating the bootstrap configuration’s state back to local.

variable "protect_resources" {
  type    = bool
  default = true
}

# On each protected resource:
#   deletion_protection = var.protect_resources
#   (Cloud SQL also: settings { deletion_protection_enabled = var.protect_resources })
#   (buckets: force_destroy = !var.protect_resources)

resource "google_service_networking_connection" "private_services" {
  network                 = google_compute_network.bookshelf.id
  service                 = "servicenetworking.googleapis.com"
  reserved_peering_ranges = [google_compute_global_address.private_services.name]
  deletion_policy         = var.protect_resources ? "DELETE" : "REMOVE_PEERING"
}

# Keep the encryption key, drop it from state
removed {
  from = google_kms_crypto_key.data

  lifecycle {
    destroy = false
  }
}

Terraform and OpenTofu on Google Cloud

The Google providers are the same code for both tools, installed from the Terraform registry or the OpenTofu registry, and authentication, impersonation and federation behave identically. The differences are around them:

  • The OpenTofu gcs backend documents one more argument, universe_domain, and OpenTofu adds client-side state and plan encryption, which can be combined with the bucket’s own encryption.

  • Infrastructure Manager runs Terraform; its documentation lists only Terraform versions, so OpenTofu cannot be selected there.

  • Module version constraints compare version numbers of the tool. The Fabric modules require Terraform >= 1.12.2; the numbers of OpenTofu and Terraform are not comparable, so test modules with the tool you use instead of trusting the constraint.

Where the book is outdated or wrong

  • hashicorp/google pinned exactly to 5.38.0 (Wang). Use the current major with a ~> constraint and the lock file.

  • Retired resources and images (Wang): google_cloudfunctions_function (1st generation), google_cloud_run_service, gcr.io images, debian-10, and MySQL 5.7. Use google_cloudfunctions2_function, google_cloud_run_v2_service, Artifact Registry, debian-13 and a current PostgreSQL or MySQL major.

  • A service account with the editor role plus a downloaded JSON key (Wang). Use least-privilege roles with impersonation and Workload Identity Federation.

  • secret_data stored in state (Wang). Use write-only arguments and ephemeral reads.

  • GKE master authorized networks open to everyone (Wang). Restrict them to real administrator ranges.

  • A gcs backend with key and region (Wang). The backend takes bucket and prefix.

  • state pull and state push to adopt a remote backend (Wang). Use terraform init -migrate-state.

  • tf.tfvars loaded automatically (Wang). Only terraform.tfvars, terraform.tfvars.json and .auto.tfvars files are.

Pitfalls

  • Pinning nothing, or everything: use ~> constraints, commit the lock file, and read the upgrade guide before a major.

  • Destroying a google_project_service on a provider older than 7.0.0 with the default disable_on_destroy.

  • Leaving edition unset on PostgreSQL 16 or later with a custom tier.

  • Applying a Cloud Run change that CI also deploys, so each tool reverts the other’s image.

  • Granting roles/run.invoker to allUsers by habit.

  • Expecting a *_iam_policy resource to add to existing policy; it replaces it.

  • Using GOOGLE_CREDENTIALS for the provider and forgetting that the backend reads it too.

  • Deploying modules with a newer Terraform floor to Infrastructure Manager.

  • Forgetting that a destroyed KMS key makes data unrecoverable.

  • Running the first apply of an ephemeral secret read before the secret has a version.
