Kibana: Alert Lifecycle, Snooze & Maintenance Windows

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked on 2026-11-09 against Kibana 9.5.x. Tested with Elasticsearch 9.5.6 and Kibana 9.5.6 in the hands-on lab (trial licence): the rule snooze schedule, the per-alert snooze and the maintenance window requests were accepted.

To do this by hand, follow Manage Alerts, Maintenance Windows and Cases.

An alert is not a message. It is a record that a rule keeps updating for as long as the problem lasts, and the notifications are a side effect of that record changing state. Understanding the record answers the questions that production brings: why did the page not arrive when the condition was obviously true, why did a flapping alert page six times, what is the difference between snoozing a rule and snoozing an alert, and what should happen on Tuesday night when Bookshelf is redeployed on purpose. This page follows the life of an alert, then the four ways to silence it (rule snooze, alert snooze, untracking and maintenance windows), and ends with where to see and clean up the alerts. The rules that create alerts are on Rules & Stack Rule Types and Observability Rules; what the actions do with the state is on Actions, Frequency & Action Variables. The concepts (flapping, silences, alert fatigue) are explained tool-neutrally on Alerting Fundamentals and Designing Actionable Alerts; the Grafana counterparts are Rule Evaluation, States & Missing Data and Silences, Mute Timings & Inhibition.

Source: View and manage alerts from Kibana alerting rules.

The alert statuses

Kibana creates an alert when the conditions of a rule are met, and the alert has one of four statuses:

Status Meaning

active

The rule’s conditions are met. If the rule has actions, Kibana generates notifications according to the actions' frequency.

flapping

The alert switched repeatedly between active and recovered. Actions configured to run on status changes do not run for a flapping alert.

recovered

The conditions are no longer met. Recovery actions run only if the conditions are unmet in the current run but were met in the previous one. A flapping alert becomes recovered only after the conditions stay unmet for a number of consecutive runs (see the next section).

untracked

The rule is disabled, or somebody marked the alert as untracked (Mark as untracked in the Alerts table). Actions are no longer generated and the alert’s status can no longer change. You can choose to move active alerts to this state when you disable or delete a rule.
stateDiagram-v2 [*] --> Active: rule conditions met Active --> Recovered: conditions no longer met Active --> Flapping: repeated status changes Flapping --> Recovered: conditions unmet for N consecutive runs Active --> Untracked: rule disabled or alert marked untracked Flapping --> Untracked: rule disabled or alert marked untracked Recovered --> [*] Untracked --> [*]

Two properties of the diagram deserve a sentence each. Recovery is decided by the rule run, not by a timer: an alert is recovered because the next check found the conditions unmet, so the delay between a fix and the recovery notification is up to one check interval plus the time the query needs. And "recovered" is final for that alert: once a flapping alert has recovered it cannot flap again; only a new alert with repeated status changes becomes a candidate. The same condition occurring tomorrow creates a new alert.

The classic Kibana statuses have no "pending" state, so a rule fires as soon as one run matches; the brake that Grafana calls the pending period is the alert delay described below.

On top of the status, an alert carries a workflow state that people set. Acknowledge (generally available on the Stack since 9.4) marks the alert as being investigated: it sets kibana.alert.workflow_status to acknowledged and shows a badge in the lifecycle status cell, but it does not stop notifications and does not affect recovery. Alert tags (generally available since 9.3) group alerts into categories that you can filter with kibana.alert.workflow_tags : "Production", individually or in bulk; removing a tag deletes it permanently. Both are filters for humans, not controls for the rule.

Source: Alert statuses, Acknowledge alerts and Apply and filter alert tags.

Flapping detection

A rule that checks a noisy signal every minute can flip an alert between active and recovered over and over, and with a per-alert action on status changes each flip is a notification. Flapping detection is the built-in answer: it is on by default, and it needs a look-back window (number of runs) and a status change threshold. The documentation’s example is "at least 6 status changes in the last 10 runs". An alert that meets the criterion becomes flapping, and its status-change actions stop. To leave the flapping state the alert needs the same number of consecutive runs with the conditions unmet as the threshold (6 in the example); if the conditions match again in that period the count restarts.

The settings can be changed in two places. Per rule, in the rule flyout while creating or editing it (generally available since 9.3; in 9.0 to 9.2 there were only the global settings). For every rule of a space or Serverless project, under Rules > Settings > Alert flapping detection. In the rules API they are the flapping object of the rule:

Field Meaning

flapping.enabled

Whether the rule can enter the flapping state; on by default.

flapping.look_back_window

The number of runs to look at, between 2 and 20.

flapping.status_change_threshold

The minimum number of status switches inside the window, between 2 and 20.

Treat flapping as a symptom, not as a fix. If an alert flaps, the rule’s threshold sits on the noise of the signal and the right change is usually a longer window, a different aggregation or a warning and critical threshold pair (see Observability Rules). Flapping detection stops the notification storm while you do that. The Grafana equivalent is the keep-firing-for period; see Rule Evaluation, States & Missing Data.

Sources: Alert flapping and the Create a rule API reference (flapping).

Alert delay

The opposite problem to flapping is the single bad sample: one failed health check, one slow minute. The rules API has an alert_delay object for it: an alert occurs only when the given number of consecutive runs met the rule conditions.

"alert_delay": { "active": 3 }

With a one-minute check interval, a delay of 3 means that a Bookshelf condition must hold for three consecutive checks before an alert exists at all, and the action variable {{alert.consecutiveMatches}} shows how many consecutive runs have met the conditions. The create-and-manage-rules page does not describe this setting; the Classic rules API and the Terraform resource (elasticstack_kibana_alerting_rule) expose it, and the newer Universal Alerting rules have their own alert delay and recovery delay pages (see Universal Alerting & Watcher). Prefer a rule type’s own time window when it has one (for example a custom threshold rule over five minutes), and use the delay when the rule type evaluates a single point.

Source: Create a rule (alert_delay.active).

Snoozing a rule, disabling a rule

The rules list in Stack Management > Rules has quick controls for each rule. Disable stops the checks altogether, which also stops the load on the cluster. Snooze keeps the checks running on schedule but alerts do not generate actions; you can snooze for a period, indefinitely, or on a single or recurring schedule, and you can cancel or change a snooze that is in progress. Because the rule keeps running, alerts still appear in the Alerts table and in the rule’s alert list during a snooze; you silence the messages, not the evidence.

In the API a snooze is a schedule on the rule:

curl -s -u "elastic:${ELASTIC_PASSWORD}" -X POST "http://localhost:5601/s/bookshelf/api/alerting/rule/bookshelf-error-logs/snooze_schedule" \
  -H 'kbn-xsrf: true' -H 'Content-Type: application/json' -d '{
  "schedule": { "custom": {
    "duration": "8h",
    "start": "2026-11-10T09:00:00.000Z",
    "timezone": "UTC",
    "recurring": { "every": "1w", "occurrences": 4, "onWeekDay": ["MO"] }
  } }
}'

The request snoozes the rule for eight hours every Monday, four times; omit recurring for a single snooze. The rule ID is the one the rule was created with on the actions page.

Sources: Snooze and disable rules and Schedule a snooze for a rule.

Snoozing one alert (generally available in 9.5)

Snoozing a rule silences everything the rule says, including a second, unrelated host that starts failing during the snooze. For rules that group alerts (by host.name, by service), you want to silence one alert. Per-alert snooze does that, and it is generally available on the Stack since 9.5 and on Serverless. It replaces mute, which was generally available from 9.0 to 9.4 and never existed on Serverless; an alert that was muted before the upgrade appears as snoozed indefinitely and Unsnooze resumes its actions.

  • An active alert can be snoozed from the action menu of the Alerts table or of the alert details page. While snoozed, the rule keeps running, the alert’s state keeps updating, and only its actions are held back. If the snoozed alert recovers and becomes active again, it stays snoozed.

  • In a rule that groups alerts, snoozing the alert for web-01 does not affect web-02 or web-03.

  • Quick Snooze takes a duration: presets of 1, 8 or 24 hours, a custom duration or end date, or Indefinitely (until somebody unsnoozes it).

  • Condition based snooze resumes the actions when something about the alert itself changes, optionally with a time condition as an upper bound (at least one of the two is required, and whichever is met first unsnoozes the alert). The data conditions are Field change (a chosen alert field changes value), Severity change (the severity moves in either direction) and Severity equals (the alert reaches a given severity). With several data conditions, Any unsnoozes on the first, All waits for every one. The page’s tip is that custom threshold and metric threshold rules set the alert severity to warning or critical, so the two severity conditions work for them: stay quiet through warning, resume on critical.

  • A snoozed alert shows an icon in the status cell; hover to see when it ends or which conditions apply.

curl -s -u "elastic:${ELASTIC_PASSWORD}" -X POST \
  "http://localhost:5601/s/bookshelf/api/alerting/rule/${RULE_ID}/alert/${ALERT_ID}/_snooze" \
  -H 'kbn-xsrf: true' -H 'Content-Type: application/json' -d '{
  "condition_operator": "any",
  "conditions": [ { "type": "severity_equals", "value": "critical" } ],
  "expires_at": "2026-11-11T09:00:00.000Z"
}'

The body snoozes the alert until it reaches critical severity or until the expiry time, whichever comes first; conditions accepts up to ten entries of type field_change (with a field), severity_change or severity_equals, and omitting expires_at makes the snooze last until a condition is met or somebody unsnoozes. RULE_ID and ALERT_ID come from the alert’s details page. ALERT_ID is the alert instance id (kibana.alert.instance.id, for example query matched for an ungrouped Elasticsearch query rule, URL-encoded in the path); the kibana.alert.uuid of the alert document is answered with a 404 "Alert instance …​ does not exist". To permanently stop an alert, use Mark as untracked instead: actions stop, the status never changes again, and the choice cannot be reverted for that alert (future alerts with the same ID are unaffected).

Users need the Stack Alerts or Observability Alerts feature privilege (All for full access, Read to see snooze state only) to snooze, unsnooze and acknowledge without being able to manage rules; see Spaces, Roles & Privileges.

Sources: Snooze alerts, Mute alerts and the API reference Snooze an alert.

Maintenance windows

A planned redeploy of Bookshelf produces exactly the alerts that the rules are there to produce, and nobody should be paged for them. A maintenance window is a single or recurring schedule during which notifications are suppressed. It is generally available on the Stack since 9.2 (preview in 9.0 and 9.1) and on Serverless, and it needs a subscription tier above the one the connectors need: the subscriptions page lists Maintenance Windows at the Platinum tier and above; the lab trial licence includes it.

By default a window affects all rules in all Kibana apps in its space. Alerts continue to be generated, only the notifications are suppressed, and the precise behaviour is:

  • An alert that occurs during a window sends no notification, and when it recovers it still sends none, even if the recovery happens after the window has ended.

  • An alert that occurs before the window and recovers during or after it notifies as usual.

You create a window in Stack Management > Maintenance Windows (on Serverless, Project settings > Management) with a name and a schedule, optionally repeating daily, monthly, yearly or on a custom interval. The scope is refined with Filter alerts, a KQL query on the alert documents. The option to choose rule categories is no longer available since 9.2: existing windows keep applying to the categories they had, but editing one removes the categories and the window then applies to all rule types. Two cautions: some rules are not affected by window filters because their alerts lack the data (Stack Monitoring, tracking containment, anomaly detection job health and transform health rules), and a window can have the statuses Upcoming, Running, Finished and Archived. From 9.1.0 you can also delete running, cancelled or archived windows, and a deleted window cannot be recovered. When you open an alert’s details, the identifiers of the windows that affected it are shown, which is how you check afterwards why a notification did not arrive.

To create or manage windows you need All (or Read for view only) on the Management > Maintenance Windows feature privilege.

curl -s -u "elastic:${ELASTIC_PASSWORD}" -X POST "http://localhost:5601/s/bookshelf/api/maintenance_window" \
  -H 'kbn-xsrf: true' -H 'Content-Type: application/json' -d '{
  "title": "Bookshelf weekly deploy",
  "enabled": true,
  "schedule": { "custom": {
    "start": "2026-11-10T03:00:00.000Z",
    "duration": "2h",
    "timezone": "UTC",
    "recurring": { "every": "1w", "onWeekDay": ["TU"] }
  } },
  "scope": { "alerting": { "query": { "kql": "kibana.alert.rule.name : \"Bookshelf*\"" } } }
}'

The window starts on Tuesday 10 November 2026 at 03:00 UTC and lasts two hours, weekly on Tuesdays, for alerts whose rule name starts with "Bookshelf". duration uses d, h, m or s; every uses d, w, M or y; scope.alerting.query.kql is the filter, and if you include scope but omit alerting the window affects no Classic alerts. The API reference also has an alerting_v2 scope for Universal Alerting alerts. The field name in the filter is illustrative: confirm the alert fields in Discover on the alert indices before relying on a filter, because a filter that matches nothing suppresses nothing.

Sources: Maintenance windows and Create a maintenance window. Version badges: GA since 9.2 (preview in 9.0 and 9.1) on the Stack, generally available on Serverless.

Seeing alerts: the Alerts table and cleanup

There are three places to see alerts. A rule’s details page lists the alerts that rule generated. Stack Management > Alerts lists the alerts of Stack Management rules (the filter controls there are in technical preview): you can filter by status or rule type and use a KQL bar; by default the list excludes alerts from Security rules. And the Observability Alerts page shows the alerts of Observability rules (APM, logs, infrastructure, SLO and the rest), machine learning anomaly detection rules and Stack Management rules, with the last two visible only to users with the matching feature privileges. In all of them the table gives the status, the last update, the reason, and per-alert actions (view alert details, view in app, view rule details, snooze, acknowledge, edit tags, mark as untracked), and you can filter by status or time period, choose columns and search with KQL. The alert details show the expected and actual values, a summary of the reason and, when relevant, the maintenance windows that affected the alert. Rules use an API key to authorize all their background tasks (checks and triggered actions), which the setup page covers in Alerting Setup, Security & Scaling. The Observability alerts of the lab appear on the Alerts page, and the Alerts panel of a dashboard (see Building Dashboards) shows the same data on the "Bookshelf service health" dashboard.

GET .alerts-*/_search
{
  "size": 0,
  "aggs": { "by_status": { "terms": { "field": "kibana.alert.status" } } }
}

The query counts alerts per status across the alert indices; the index pattern and field name are the ones the alert documents are known by, so check one document in Discover first. When a case needs the alerts, attach them in Cases.

Alert cleanup removes old alerts from the alert indices. In Rules > Settings, Clean up alert history defines criteria and runs a cleanup task: active alerts (never changed since creation, older than a threshold) or inactive ones (changed to recovered, closed, acknowledged or untracked, older than a threshold), with a minimum threshold of one day; a preview shows how many alerts match, you must type Delete to confirm, alerts attached to cases are not deleted, and the deletion is permanent, so keep snapshots. It needs the Alert deletion sub-feature privilege (Management > Rule Settings, with customised sub-feature privileges). The task is generally available on the Stack since 9.4 (preview 9.1 to 9.3) and on Serverless. A separate history that you control, written by an index connector, is on Connectors.

Sources: Filter alerts, Clean up alerts and Alerting in Elastic Observability.

What can go wrong

  • The page that never came. Check, in order: a rule snooze, an alert snooze (or an old mute), a maintenance window listed in the alert details, a flapping status, a frequency that already notified (custom interval), an alerts_filter that does not match, and an untracked alert. All of them leave the alert visible in the table.

  • Snoozed forever. Indefinitely never expires and old muted alerts now show as snoozed indefinitely; review the snoozed alerts after upgrading to 9.5.

  • Untracked by accident. Mark as untracked cannot be undone for that alert, and disabling a rule can move active alerts to untracked.

  • Flapping hides a real incident. While an alert flaps its status-change actions are silent; do not rely on status-change actions for a signal that is also noisy.

  • Maintenance window with an optimistic filter. A KQL filter with a typo suppresses nothing, and a window without a filter silences the whole space, including unrelated rules.

  • Window ends before the recovery. Recovery notifications of alerts created in a window are suppressed even after it ends, which is intended but surprising; an alert from before the window notifies on recovery as usual.

  • Unaffected rule types. Stack Monitoring, tracking containment, anomaly detection job health and transform health rules ignore window filters.

  • Alerts disappear after cleanup. The cleanup task deletes alert documents permanently, including history that nobody copied elsewhere.

  • Mute versus snooze. Scripts that call the mute API on 9.5 should be moved to snooze; muted alerts from before 9.5 appear as snoozed indefinitely.

Verify it in the lab

  1. With the kibana profile and the load generator running, create the Bookshelf error-log rule of the actions page. Switch the generator to failing-request mode, open Stack Management > Alerts and watch the alert appear as active; stop the failures and see it recover.

  2. Alternate the failing and healthy modes every minute for ten minutes with a flapping threshold of 3 changes in 5 runs set on the rule; confirm that the status becomes flapping and that the webhook receiver stops receiving status-change messages. Restore the defaults afterwards.

  3. Add alert_delay of 3 through the API (or the Terraform resource) and repeat with a short failure of two minutes: no alert should be created.

  4. Snooze the rule for 30 minutes, trigger the condition, and confirm that the alert exists and no webhook message arrives; unsnooze.

  5. On a rule that groups by a field, snooze one alert and confirm that another group still notifies (Kibana 9.5).

  6. Create the weekly maintenance window with a start that includes now, trigger the condition, and confirm that the alert exists, its details list the window identifier and the webhook receiver stays silent; compare with an alert that was already active before you created the window.

  7. Run the GET .alerts-*/_search aggregation, then open Rules > Settings and look at the Clean up alert history preview without running it.

In the books

Hausenblas, Cloud Observability in Action, chapter 7, describes the Alertmanager’s notification pipeline (inhibition, silencing, routing, grouping and throttling) and the same suppression with Grafana silences, noting that the rule is still evaluated while the notification is not created. Chapman and Holmes, Observability with Grafana, chapter 9, uses silences to cover maintenance periods and an incident tool with firing, acknowledged, silenced and resolved states. Kibana’s statuses, per-alert snooze and maintenance windows are newer than the Kibana books in the collection, and none of them covers this model.
