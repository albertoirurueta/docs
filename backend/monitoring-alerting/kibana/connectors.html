Kibana: Connectors

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked on 2026-11-09 against Kibana 9.5.x. Tested with Elasticsearch 9.5.6 and Kibana 9.5.6 in the hands-on lab (trial licence): the webhook, server log and index connectors were created in the bookshelf space and their _execute calls succeeded, the webhook delivery reaching the receiver.

To do this by hand, follow Create a Rule with a Connector.

A rule detects, an action decides when and what, and a connector is the part that knows how to reach the outside world: the URL of a webhook, the SMTP server and its credentials, the PagerDuty integration key. Connectors are stored once per Kibana space and any number of rule actions can use them, so rotating a Slack webhook means editing one connector instead of fifty rules. This page covers the catalogue, how to create and test connectors in the UI and as code, the handful of connectors an alerting setup actually uses, how to ship connectors preconfigured in kibana.yml, the network settings that decide where Kibana may connect, and how to find out that a connector silently failed. When and how often actions use a connector is on Actions, Frequency & Action Variables. The tool-neutral side (who gets notified, through which channel) is on Notifications & Incident Response, and the Grafana counterpart of a connector is a contact point (Contact Points & Integrations): the difference is that Grafana contact points are chosen by a routing tree, while Kibana actions pick the connector directly.

Source: Manage connectors and Kibana connectors.

The catalogue and what it costs

The reference page groups the connectors in four sets. Only the first three matter for alerting; the fourth is a recent addition for agents and workflows.

Which tier a connector needs is the cost question people ask first, and the answer is on the subscriptions page, not in the connector pages, which only say that some connector types are paid and others free. The consequences for the lab and for a small production setup are concrete: a webhook, PagerDuty or Slack action needs Gold or above, while Index and Server log work without paying. The lab’s one-month trial licence (see Installation & Configuration) includes every feature, so everything on this page works while you learn; check the tier before you design a production notification path around a connector. Maintenance windows need a higher tier still (see Alert Lifecycle, Snooze & Maintenance Windows).

Newer connector types (the docs name Gmail, Jira Cloud and GitHub) have an Actions setting with a Custom option that limits which of the connector’s actions can run, for every caller including agents, workflows and API calls. The classic alerting connectors do not have it.

Sources: Kibana connectors (catalogue), Alerting and case management connectors, Elastic subscriptions (tiers; the page is a comparison table without stable anchors).

Creating, testing and managing connectors

Connectors live in Stack Management > Connectors, or can be created in passing from the action section of the rule flyout. The list shows the connectors of the current space; the search bar and the Type dropdown filter it. Two details of the list matter in practice. First, Kibana hides deprecated connector types by default, so a connector that was created earlier and "disappeared" is probably of a deprecated type: Display options, then Deprecated: Show, brings it back. Second, a connector can be deleted while actions still reference it; those actions then fail to run and the errors appear in the Kibana logs.

Create connector opens a flyout where you pick the type (the Filter by feature control narrows the list to types that support alerting, cases and so on) and fill in its properties. After saving, the connector is available to every rule in the space. Every connector has a Test tab that sends a sample action without a rule, which is the fastest way to prove that the credentials, the URL and the allowed-hosts list are right before a rule depends on them. The same operation is available as the _execute API.

Connector name and ID

A connector has a name (display) and an ID (the stable identifier that APIs, rules and Terraform use). Kibana suggests the ID by slugifying the name; you can edit it before saving. The ID must be unique in the space, including against preconfigured connectors, may have 1 to 36 characters of lowercase letters, numbers and hyphens, and cannot be changed after saving: to change it, create a new connector with the same configuration and update every rule that used the old one. In the API, POST /api/actions/connector generates an ID and POST /api/actions/connector/<connector_id> uses yours (outside the default space the path starts with /s/<space_id>). Choose readable IDs; they appear in rule definitions in source control.

Source: Connector name and Connector ID.

The lab connectors as code

The Bookshelf lab uses three connectors. The first is the webhook that posts to the lab’s receiver; the receiver address is http://webhook-receiver:8080/kibana, a hostname that only resolves inside the compose network, which is why Kibana reaches it and your browser does not.

# 1. The lab webhook (Gold and above; the lab trial licence covers it)
curl -s -u "elastic:${ELASTIC_PASSWORD}" -X POST "http://localhost:5601/s/bookshelf/api/actions/connector/bookshelf-webhook" \
  -H 'kbn-xsrf: true' -H 'Content-Type: application/json' -d '{
  "name": "Bookshelf webhook",
  "connector_type_id": ".webhook",
  "config": { "url": "http://webhook-receiver:8080/kibana", "method": "post", "hasAuth": false,
              "headers": { "Content-Type": "application/json" } }
}'

# 2. Server log: writes to the Kibana log, handy for the first test of any rule
curl -s -u "elastic:${ELASTIC_PASSWORD}" -X POST "http://localhost:5601/s/bookshelf/api/actions/connector/bookshelf-server-log" \
  -H 'kbn-xsrf: true' -H 'Content-Type: application/json' -d '{
  "name": "Bookshelf server log", "connector_type_id": ".server-log"
}'

# 3. Index: one document per action in the bookshelf-alerts index
curl -s -u "elastic:${ELASTIC_PASSWORD}" -X POST "http://localhost:5601/s/bookshelf/api/actions/connector/bookshelf-alert-index" \
  -H 'kbn-xsrf: true' -H 'Content-Type: application/json' -d '{
  "name": "Bookshelf alert index", "connector_type_id": ".index",
  "config": { "index": "bookshelf-alerts", "executionTimeField": "indexed_at" }
}'

# Test the webhook without a rule
curl -s -u "elastic:${ELASTIC_PASSWORD}" -X POST "http://localhost:5601/s/bookshelf/api/actions/connector/bookshelf-webhook/_execute" \
  -H 'kbn-xsrf: true' -H 'Content-Type: application/json' -d '{
  "params": { "body": "{\"rule\":\"connector test\",\"state\":\"test\"}" }
}'

The headers entry is optional, and the connector types, ID rules and the _execute call come from the API reference; the property names inside config (including hasAuth) are the connector’s own, so confirm them against the Create connectors in Kibana section of each connector page and, in the lab, by creating the same connector once in the UI and reading it back with GET /api/actions/connector/bookshelf-webhook. The Terraform equivalent is the elasticstack_kibana_action_connector resource of the elastic/elasticstack provider (not available on Serverless), described on Alerting APIs & Terraform.

Sources: Create a connector, Run a connector, Webhook, Index, Server log.

The connectors an alerting setup uses

Webhook

The webhook connector uses axios to send a request to a web service, and it is the universal adapter: anything with an HTTP endpoint (an incident tool, a chat bot, a CI job, the lab receiver) can be a target. Its configuration is the Method (POST by default; PUT, PATCH, GET and DELETE are also offered), the URL (must start with http:// or https://; internal hostnames such as http://dev-logstash:10200 are supported and must be in xpack.actions.allowedHosts when that setting restricts hosts), the Authentication (none, basic, SSL or OAuth 2.0), optional HTTP headers stored as plain text (config) or encrypted (secret), and an optional certificate authority with a verification mode. The extra HTTP methods and the OAuth 2.0 option carry version badges (9.2 and 9.3) on the page. The action itself has one property, the Body: a JSON payload sent for POST, PUT and PATCH. Mustache variables in the body have their values escaped so that the final JSON is valid, which is the reason to prefer double braces over triple braces there (see the action variables page). The lab’s bookshelf-webhook posts the body built on that page to the receiver, which logs it.

Source: Webhook connector and action.

Index

The index connector indexes a document into Elasticsearch for each action. It needs a name and an index, and optionally a time field that records when the document was indexed (executionTimeField above). The action is a JSON document, given as an object or as a JSON-encoded string (invalid strings are rejected), whose values can contain variables:

{
  "rule_id": "{{rule.id}}",
  "rule_name": "{{rule.name}}",
  "alert_id": "{{alert.id}}",
  "context_message": "{{context.message}}"
}

It is the cheapest way to keep a history of notifications that survives the alert indices' cleanup, and it needs no paid tier. Create the index with a mapping first if the default dynamic mapping would not suit the fields. For history of active alerts without writing the document yourself, see the preconfigured alert history connector below.

Source: Index connector and action.

Server log

A server log connector has only a name, and its action has a message and a log level that defaults to info (trace, debug, info, warn, error and fatal). It writes into the Kibana server log, so in the lab docker compose logs kibana shows it. It is the first connector to try with any new rule: if the message appears, the rule and its variables work and any later failure is in the real connector.

Source: Server log connector and action.

E-mail

The e-mail connector sends through SMTP, as plain text and HTML. Its configuration is the Sender, the Service (a well-known provider name, Microsoft Exchange Server with a tenant ID, client ID and client secret, or other with a host and port), the Secure flag (TLS from the start, otherwise STARTTLS is attempted) and optional authentication. Two settings change what it may do: xpack.actions.email.domain_allowlist restricts the sender and every recipient domain (a rule action whose recipient is not allowed fails with a message saying so), and a footer with a link to Kibana is added only when server.publicBaseUrl is set (and xpack.actions.enableFooterInEmail is not turned off). The Test tab sends a fixed test message to at least one recipient. The lab compose has no SMTP server or mail catcher, so e-mail is not part of the lab; use the server log or webhook connector to follow the pages, and a mail catcher container if you want to see the HTML.

Source: Email connector and action.

Slack

The Slack connector uses either an incoming webhook (one channel per connector; the message cannot contain Markdown, images or advanced formatting) or the Slack Web API, which supports several channels. For the Web API type you can list up to 500 allowed channel names (each starting with #) or channel IDs; if you list none, any channel can be named when configuring the action. Web API actions have Post message and Post Block Kit variants, with channel names, channel IDs and the text. A summary action (see the actions page) is the natural fit for a shared channel, and a per-alert action on the critical group for the on-call channel.

Source: Slack connector and action.

PagerDuty

The PagerDuty connector triggers, acknowledges and resolves PagerDuty alerts through the v2 Events API. It needs the 32-character integration key of a PagerDuty service (also called the routing key) and, optionally, an event URL (https://events.pagerduty.com/v2/enqueue by default). Its key property is the DedupKey: all actions that share the key belong to the same PagerDuty alert, and when it is not set it defaults to the rule ID and the alert ID joined by a colon, so Kibana creates one incident per alert and reuses it when a recovered alert reactivates. The Event action is Trigger (default), Resolve or Acknowledge; rule recovery actions support all three, which is how a recovered alert resolves its incident. The optional properties (class, component, group, links, custom details and severity) map onto the PagerDuty event fields.

Source: PagerDuty connector and action.

Microsoft Teams and Opsgenie

The alerting Microsoft Teams connector sends the message to an incoming webhook URL, and the documentation says that Microsoft 365 connectors are being retired: you create the webhook URL with a workflow in the Teams Workflows app, starting from a blank template (the premade template "Post to a channel when a webhook request is received" does not work with this connector), with the trigger "When a Teams webhook request is received" and a "Post message in a chat or channel" step that posts the message from the trigger body. The message supports no Markdown or images. Do not confuse it with the separate Microsoft Teams entry of the data and context sources, which uses the Microsoft Graph API for agents and workflows.

The Opsgenie connector creates and closes alerts through the Opsgenie alert API, with the Opsgenie URL (a regional URL such as the EU one is possible) and an API key. Rule actions in the active groups create alerts and recovery actions close them. The message is limited to 130 characters by Opsgenie and Kibana truncates longer values instead of failing.

Sources: Microsoft Teams connector and action, Opsgenie connector and action.

Preconfigured connectors and the alert history index

On a self-managed Kibana you can define connectors in kibana.yml so that they exist before anybody logs in. A preconfigured connector needs no setup, appears in every space (it is not a saved object), is tagged as preconfigured in the list, and cannot be edited or deleted from the UI; clicking it shows the description but not the configuration. The key of each entry is the connector ID and it must not collide with a stored connector: on a conflict Kibana logs an error at startup, skips the preconfigured one and shows a warning in the UI. Elastic Cloud Hosted provides a preconfigured e-mail connector but does not let you add more, and Serverless has neither preconfigured connectors nor the Terraform resource.

xpack.actions.preconfigured:
  bookshelf-webhook-pre:
    name: "Bookshelf webhook (preconfigured)"
    actionTypeId: .webhook
    config:
      url: http://webhook-receiver:8080/kibana
      method: post
      hasAuth: false
    exposeConfig: true
xpack.actions.preconfiguredAlertHistoryEsIndex: true

actionTypeId is the dot-prefixed type of the connector, config and secrets are specific to the type, and exposeConfig decides whether the config is visible through the actions API. Put passwords in the Kibana keystore rather than in the file. In the lab, add the fragment to the kibana.yml that the compose file mounts (see the way kibana.yml, environment variables and the keystore combine on Installation & Configuration) and restart Kibana.

Setting xpack.actions.preconfiguredAlertHistoryEsIndex to true (a technical preview feature) adds the preconfigured Alert history Elasticsearch index connector, which indexes the active alert data of a rule into Elasticsearch using a predefined schema that captures the action variables of the rule. By default documents go to kibana-alert-history-default; any other index name must start with kibana-alert-history- to use the preconfigured index template. Two operational points: writing needs all or write privileges on kibana-alert-history-*, and these indices are not managed by ILM, so you must clean them up yourself, for example with delete by query. The alerts that Kibana itself keeps are covered under Alert Lifecycle, Snooze & Maintenance Windows.

Sources: Preconfigured connectors (including the built-in alert history connector) and Preconfigured connector settings.

Where Kibana may connect: network and runtime settings

Connector traffic originates from the Kibana server, so what that server may reach matters as much as the connector itself. The action settings in kibana.yml control it:

Setting Effect

xpack.actions.allowedHosts

The hostnames Kibana may connect to when built-in actions run. The default is ["*"], which allows any host and carries the risk of server-side request forgery; an empty list blocks all external connections. Hosts of built-in actions such as Slack and PagerDuty are not added automatically, so once you restrict the list you must add their endpoints.

xpack.actions.customHostSettings

A list that overrides the global TLS settings per host. Each entry has a url (https://host:port or smtp://host:port, no path) and ssl options (verificationMode, certificateAuthoritiesFiles, certificateAuthoritiesData) and, for SMTP, requireTLS or ignoreTLS. Use it to trust an internal CA for one webhook without relaxing verification everywhere.

xpack.actions.ssl.verificationMode

The global certificate verification for outbound TLS: full (default), certificate or none.

xpack.actions.proxyUrl, xpack.actions.proxyBypassHosts, xpack.actions.proxyOnlyHosts

An outbound proxy used in CONNECT (tunnelling) mode, with a list of hosts that bypass it or use it exclusively (the two lists cannot be used together). Basic authentication to the proxy is not supported.

xpack.actions.responseTimeout, xpack.actions.maxResponseContentLength

The time allowed for an outbound request (60 s by default) and the maximum response size in bytes (1 MB by default).

xpack.actions.run.maxAttempts, xpack.actions.run.connectorTypeOverrides

How many times an action is attempted (1 to 10), globally and per connector type.

xpack.actions.queued.max

The maximum number of queued actions (1,000,000 by default).

xpack.actions.enabledActionTypes

The enabled connector types (default all). Disabled types disappear from the creation list, and existing connectors of that type stay but do not work; preconfigured connectors are not affected.

xpack.actions.email.domain_allowlist, xpack.actions.email.recipient_allowlist

Restrict e-mail domains or recipient patterns (the two cannot be combined).

A restrictive production example that allows only the receiver and one chat endpoint, and trusts a private CA for an internal webhook:

xpack.actions.allowedHosts: ["webhook-receiver", "hooks.slack.com", "events.pagerduty.com"]
xpack.actions.customHostSettings:
  - url: https://alerts.internal.example.com:8443
    ssl:
      verificationMode: full
      certificateAuthoritiesFiles: ["/usr/share/kibana/config/internal-ca.pem"]
xpack.actions.run.maxAttempts: 3

xpack.actions.allowedHosts replaces the 8.x name xpack.actions.whitelistedHosts, and the 9.0 breaking changes removed xpack.actions.rejectUnauthorized; use xpack.actions.ssl.verificationMode instead. The encryption that protects connector secrets in Elasticsearch needs xpack.encryptedSavedObjects.encryptionKey on self-managed Kibana, and a lost or changed key makes existing connectors fail to decrypt (see Alerting Setup, Security & Scaling).

Source: Alerting and action settings in Kibana (anchors #action-settings and #preconfigured-connector-settings), and Kibana breaking changes for the 9.0 removals.

Import, export and the deprecated types

Connectors are exported and imported through Saved Objects. After an import, a connector that is missing sensitive information shows a Fix button in Connectors. If an imported connector has the same ID as a preconfigured one and you import with Check for existing objects, the preconfigured connector wins and the imported one is dropped; with Create new objects with random IDs both are kept. See Sharing, Reporting & Saved Objects.

The 9.5.0 release notes deprecate the OpenAI, Amazon Bedrock, Google Gemini and Inference connector types: they remain usable and show deprecation badges, and Elasticsearch inference endpoints are the recommended route for new AI integrations. These are the connectors that Kibana hides by default in the list. They have nothing to do with alert notification; the only thing to remember here is the Deprecated: Show switch when an old connector seems to have vanished.

Sources: Manage connectors (import and export), Kibana release notes (9.5.0 deprecations).

Monitoring connectors

A failing connector is easy to miss because Kibana does not fail the rule. Two places record what happened. The rule’s History tab lists the executed actions with an Errored actions count that opens the details (for example an action that failed because the e-mail recipient was removed from xpack.actions.email.domain_allowlist). The event log index holds a record for every connector run, so it can be queried for failures:

GET .kibana-event-log-*/_search
{
  "size": 5,
  "sort": [ { "@timestamp": "desc" } ],
  "query": { "bool": { "filter": [
    { "term": { "event.provider": "actions" } },
    { "term": { "event.outcome": "failure" } }
  ] } }
}

The field names above are illustrative of the event log’s ECS-style documents; look at one document first and adjust. On the Stack the Task Manager health API also reports on tasks, but the documentation warns that when a connector fails to run it still reports as successful to Task Manager, so the failure statistics there do not reflect connector failures. Use the event log, or the page on Alerting Setup, Security & Scaling, for monitoring the alerting system itself.

Sources: Monitoring connectors and View rule details.

What can go wrong

  • A test works, the rule’s action fails. The Test tab sends the connector’s own sample; the rule sends your template. Read the Errored actions detail and compare the body.

  • Everything is "allowed" until it is not. The default ["*"] for allowedHosts hides the need to list hosts; the first time somebody restricts it, every Slack and PagerDuty connector stops until their endpoints are added.

  • Unreachable hostname. localhost inside the Kibana container is the container; use the compose service name (webhook-receiver).

  • Self-signed certificates. Use customHostSettings for the one host instead of switching verification off globally.

  • Lost encryption key. Connectors and rules cannot decrypt their secrets after a key change.

  • A paid connector on a basic licence. The connector type is offered but cannot be created or used; check the tier first.

  • Teams premade template. The template that looks like the right one does not work with the Teams connector.

  • No recovery side. A connector that opens a ticket needs a recovered-group action that closes it, as described on the actions page.

  • Preconfigured ID clash. A stored connector with the same ID as a preconfigured one prevents the latter from loading.

Verify it in the lab

  1. Start the kibana profile (and the webhook-receiver) and open Stack Management > Connectors. Create the three connectors of this page in the UI, then create them again with the curl commands under other IDs and compare them with GET /api/actions/connector/<id>.

  2. Open the webhook connector’s Test tab, send the sample, and read it in docker compose logs webhook-receiver. Break the URL and repeat to see the error.

  3. Add the kibana.yml fragment with the preconfigured webhook, restart Kibana, and confirm that the connector appears tagged as preconfigured in every space and cannot be edited.

  4. Set xpack.actions.allowedHosts to a list without webhook-receiver, restart, and see the test fail; add the host back.

  5. Use the Index connector in a rule action with the document above, then GET bookshelf-alerts/_search to read what was written.

  6. Query the event log for failed actions after one of the failures above.

In the books

Shah, Kibana 8.x Quick Start Guide, chapter 6, shows the Connectors page and the connector selection flyout of Kibana 8 while setting up an anomaly detection alert, with e-mail and Slack as the examples. The catalogue has grown since (the webhook, index, server log, PagerDuty, Opsgenie and Teams connectors here, plus the preconfigured and Terraform-managed variants), the Teams connector now needs a Workflows-based webhook, and the GenAI connector types are deprecated.
