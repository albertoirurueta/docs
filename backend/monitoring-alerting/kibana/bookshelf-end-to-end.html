Kibana: Bookshelf End to End

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked on 2026-11-09 against Kibana 9.5.x. Tested with Elasticsearch 9.5.6, Kibana 9.5.6 and the EDOT Collector 9.5.6 in the hands-on lab, on the self-generated trial licence.

The Kibana pages explain the parts one by one: data, dashboards, rules, connectors, SLOs, maintenance windows. This page puts them together for the lab service Bookshelf, using one script that calls the Kibana APIs, and then breaks the service on purpose. At the end you have the "Bookshelf service health" dashboard and five alerts, you have seen each alert reach the webhook receiver, and you have a table that sets Kibana against what Grafana: Bookshelf End to End did for the same service.

It runs in the kibana profile of the hands-on lab. Two licence facts matter here: the webhook connector needs a Gold or higher subscription and maintenance windows need Platinum, so the lab starts a self-generated trial licence (xpack.license.self_generated.type=trial on Elasticsearch, 30 days); on a Basic licence the script’s connector and maintenance window requests are refused.

Bookshelf no data (bookshelf-no-data)

Custom threshold: count of bookshelf trace documents below 1 over 5 minutes, with the no-data behaviour set to alert

custom_threshold.nodata and custom_threshold.fired

docker compose stop bookshelf loadgen

Bookshelf error-log spike (bookshelf-error-log-spike)

Elasticsearch query rule (KQL) on the data view bookshelf-logs: more than 20 documents with severity_text: "ERROR" in 5 minutes

query matched

curl -X POST localhost:8090/mode/log-errors

Bookshelf availability burn rate (bookshelf-slo-burn-rate)

SLO burn rate rule on the SLO bookshelf-availability (99.5 percent, rolling 30 days, occurrences); four windows, the first 1 hour and 5 minutes at 14.4

slo.burnRate.alert, slo.burnRate.high

curl -X POST localhost:8090/mode/failing

The thresholds are the lab values used across this section: 0.05 for the 5xx ratio and 0.5 s (500 ms) for the latency objective. All rules are tagged bookshelf (the maintenance window scope relies on that tag), live in the space bookshelf and send to the connector bookshelf-webhook, which posts JSON to http://webhook-receiver:8080/kibana.

Start the lab and create everything

cd lab
docker compose --profile kibana up -d
until curl -fsS http://localhost:5601/api/status >/dev/null; do sleep 5; done
# let the load generator produce a minute of data, then:
bash kibana/setup.sh

The script is idempotent only in the sense that a second run reports conflicts for objects that exist; run docker compose down -v for a clean start. It reads ELASTIC_PASSWORD (default lab-elastic-password) and KIBANA_URL from the environment and uses the elastic user for brevity. In a real installation use a service user or an API key, because that user’s privileges become the privileges of every rule it saves (see Alerting Setup, Security & Scaling). kibana/setup.sh 
#!/usr/bin/env bash
# Creates the Kibana objects of the Bookshelf lab in the space "bookshelf": space, data views, webhook connector,
# the five alert rules, an availability SLO, a maintenance window and the dashboard.
# Run it once, after Kibana is ready and the load generator has produced some data. Needs curl and jq.
set -euo pipefail
cd "$(dirname "$0")"

export ELASTIC_PASSWORD="${ELASTIC_PASSWORD:-lab-elastic-password}"
export KIBANA_URL="${KIBANA_URL:-http://localhost:5601}"
export KIBANA="$KIBANA_URL/s/bookshelf"
export KAUTH="elastic:$ELASTIC_PASSWORD"
api() { curl -sS -u "$KAUTH" -H 'kbn-xsrf: true' -H 'Content-Type: application/json' "$@"; }

echo "== space"
api -X POST "$KIBANA_URL/api/spaces/space" -d '{
  "id": "bookshelf", "name": "Bookshelf",
  "description": "Bookshelf service dashboards, rules and connectors", "solution": "oblt"
}' | jq -c '{id, solution}'

echo "== data views"
api -X POST "$KIBANA/api/data_views/data_view" -d '{"data_view":{"id":"bookshelf-traces","name":"Bookshelf traces","title":"traces-*","timeFieldName":"@timestamp"}}' | jq -c '.data_view.id'
api -X POST "$KIBANA/api/data_views/data_view" -d '{"data_view":{"id":"bookshelf-logs","name":"Bookshelf logs (OTel)","title":"logs-*.otel-*","timeFieldName":"@timestamp"}}' | jq -c '.data_view.id'

echo "== connector"
api -X POST "$KIBANA/api/actions/connector/bookshelf-webhook" -d '{
  "name": "bookshelf-webhook",
  "connector_type_id": ".webhook",
  "config": {
    "url": "http://webhook-receiver:8080/kibana",
    "method": "post",
    "hasAuth": false,
    "headers": { "Content-Type": "application/json" }
  }
}' | jq -c '{id, is_missing_secrets}'

echo "== helpers that read the action group ids of the rule types"
types() { curl -s -u elastic:"$ELASTIC_PASSWORD" "$KIBANA_URL/s/bookshelf/api/alerting/rule_types"; }
default_group() { types | jq -r --arg t "$1" '.[] | select(.id == $t) | .default_action_group_id'; }
group_named()   { types | jq -r --arg t "$1" --arg n "$2" '.[] | select(.id == $t) | .action_groups[] | select(.name | ascii_downcase == $n) | .id'; }

The action group ids in the script are not guessed: the helper functions read them from GET /s/bookshelf/api/alerting/rule_types. On Kibana 9.5.6 that endpoint lists custom_threshold.fired, custom_threshold.warning, custom_threshold.nodata and recovered for the custom threshold rule, threshold_met for the APM latency rule, query matched for the Elasticsearch query rule and slo.burnRate.alert, slo.burnRate.high, slo.burnRate.medium, slo.burnRate.low and slo.burnRate.suppressed for the burn rate rule.

The field names of the lab data

The stand-in sends OpenTelemetry data and the EDOT Collector writes it in the OTel-native mapping, so the documents keep OpenTelemetry names. A trace document has @timestamp, duration in nanoseconds, name, attributes.http.response.status_code, attributes.http.route, attributes.url.path and, added by the elasticapm processor, attributes.transaction.duration.us; the resource attributes are under resource.attributes.*. Passthrough fields make the short names work in KQL, ES|QL and data views, so the queries in this page use service.name, http.response.status_code and url.path. A log document has body.text, severity_text (INFO or ERROR), severity_number, trace_id and span_id; it has no log.level, which is the ECS name, and the Bookshelf JSON fields uri and status are under attributes.*. The Collector also writes the aggregated APM metrics (metrics-service_summary.1m.otel-default, metrics-service_transaction.1m.otel-default, metrics-transaction.1m.otel-default) that the APM latency rule and the Applications UI read. See Ingesting Monitoring Data.

Check them before writing a query:

curl -s -u elastic:lab-elastic-password 'http://localhost:9200/traces-*/_field_caps?fields=service.name,http.response.status_code,transaction.duration.us&filter_path=fields.*.*.type'
curl -s -u elastic:lab-elastic-password -H 'Content-Type: application/json' http://localhost:9200/_query -d '{"query":"FROM traces-* | WHERE service.name == \"bookshelf\" | STATS errors = COUNT(*) WHERE http.response.status_code >= 500, total = COUNT(*) | EVAL ratio = TO_DOUBLE(errors) / total | KEEP ratio"}'

The dashboard

The dashboard is one JSON object sent with PUT /s/bookshelf/api/dashboards/bookshelf-service-health, so the same command creates it the first time and replaces it afterwards. It has a pinned options-list control on service.name, a markdown header, four metric panels, two time series and a collapsed "Dependencies" section. Every panel is an ES|QL panel, so no data view or library visualization has to exist for it (the control is the one object that refers to the data view bookshelf-traces):

Panel ES|QL

Requests

FROM traces-* | WHERE @timestamp >= ?_tstart AND @timestamp < ?_tend AND service.name == "bookshelf" | STATS requests = COUNT(*)

5xx ratio

STATS errors = COUNT(*) WHERE http.response.status_code >= 500, total = COUNT(*), then EVAL ratio = TO_DOUBLE(errors) / total

p95 latency (s)

STATS p95 = PERCENTILE(duration, 95), then EVAL p95_s = p95 / 1000000000.0 (the field duration is in nanoseconds)

ERROR log lines

FROM logs-* | WHERE ... AND severity_text == "ERROR" | STATS error_lines = COUNT(*)

Requests over time, 5xx responses over time

STATS ... BY BUCKET(@timestamp, 75, ?_tstart, ?_tend), so the buckets follow the time picker

The six queries were run against the lab (through the _query API with ?_tstart and ?_tend supplied) and returned values for the live traffic. The stand-in exports no metrics to Elasticsearch, so the Dependencies section holds a markdown note where the Grafana dashboard has the JVM heap and connection pool panels. The request carries no access_control property: with "access_control": { "access_mode": "write_restricted" } and basic authentication, Kibana answered 500 and logged that it could not determine the user profile ID of the caller.

The SLO and its burn rate rule

The availability SLO is a custom KQL indicator on the trace documents (good: http.response.status_code < 500, total: http.response.status_code : *), 99.5 percent over a rolling 30 days, budgeting by occurrences. Two transforms are created for it (slo-bookshelf-availability-1 and slo-summary-bookshelf-availability-1; check them with GET _transform). The first attempt used the APM availability indicator over metrics-*, which is what the SLO page describes for APM data; on the lab’s OpenTelemetry metrics it reported an SLI of 1 and a burn rate of 400 whatever the failure rate, so the lab uses the KQL indicator, whose value fell to 0.92 within a minute of the failing mode.

The burn rate rule has four windows (1 hour and 5 minutes at 14.4, 6 hours and 30 minutes at 6, 24 hours and 2 hours at 3, 72 hours and 6 hours at 1). Only the critical and high groups and the recovery notify the webhook; the other two are visible on the Alerts page. Grafana’s lab rule uses the first pair only.

The maintenance window

The window "Bookshelf weekly deploy" repeats weekly on Sundays at 22:00 UTC for one hour and has the KQL scope kibana.alert.rule.tags : "bookshelf", so it covers all five rules. While it is active, alerts are still created but their notifications are suppressed, including recovery notifications for alerts that fired during the window. The request was accepted and the window reports the status upcoming; the lab does not wait for Sunday, so suppression itself was not exercised.

Break the service and watch

Run these in order, with the receiver open in a second terminal (docker compose logs -f --no-log-prefix webhook-receiver). The times were measured on the lab for this page, from the moment the load generator changed mode to the first delivery at the receiver.

Step Command First notification What you see

1. Break with 5xx errors

curl -X POST localhost:8090/mode/failing

Error-log spike after 1 min 9 s; high 5xx ratio after 1 min 15 s

The rules run every minute and the 5 minute window fills with failures, so both are active in the first runs after the switch; there is no pending state. The SLO burn rate rule was created two minutes after the switch and its first notification (critical, 1 hour and 5 minute burn rate 15.88 against 14.4) arrived 2 min after creation, which includes the start-up of the SLO’s transforms.

2. Return to normal

curl -X POST localhost:8090/mode/normal

None

The 5xx and error-log alerts recovered within 5 min 30 s, when the failures left the 5 minute window, and the rules showed no active alerts. No recovered message was sent, because the script gives these rules no action for the recovered group. The burn rate alert stays active for as long as the 1 hour and 6 hour windows hold the failures.

3. Slow responses

curl -X POST localhost:8090/mode/slow

p95 latency above SLO after 2 min 24 s (value 1,278 ms against 500)

The APM latency rule reads the aggregated metrics from the Collector. In the same period the burn rate rule’s second window crossed its threshold, because the failures of the first step were still inside the 6 hour and 30 minute windows: a high burn delivery with a burn rate of 76.36 arrived 3 min 51 s after the switch.

4. Errors in the log only

curl -X POST localhost:8090/mode/log-errors

Error-log spike after 1 min 4 s

Responses stay 200, so only the log rule reacts; the p95 alert from the previous step recovered in the same period.

5. Stop the service

No data after 5 min 25 s

The count of bookshelf trace documents must be empty for the whole 5 minute window. The notification is in the custom_threshold.nodata group and context.reason reads "requests reported no data in the last 5m", so the no-data behaviour fired, not the "count below 1" threshold. After the containers start again the rule showed no active alert within 30 seconds.

Times are minutes after the load generator changed mode (or after the containers stopped), measured from the receiver log of one run; the rules run every minute.

The links are shortened here; they open Discover or the alert details in the bookshelf space and work because SERVER_PUBLICBASEURL is set to http://localhost:5601 in the Compose file. Read the deliveries with:

docker compose logs --no-log-prefix webhook-receiver | grep WEBHOOK
curl -s localhost:8081 | jq -r '.[] | "\(.time) \(.path)"'

The reason text is free text with quotes and colons in it, so a receiver that parses the body as JSON must tolerate that, as explained on Actions, Frequency & Action Variables.

What can go wrong

  • The field is severity_text, not log.level. OTLP logs carry the OpenTelemetry level field; a KQL filter on the ECS name matches nothing and the error-log rule never fires.

  • access_control makes the dashboard request fail. With basic authentication the request that includes "access_control": { "access_mode": "write_restricted" } answered 500, and the Kibana log said it could not determine the user profile ID of the caller.

  • The APM availability SLO shows nonsense on OpenTelemetry metrics. It reported an SLI of 1 and a burn rate of 400 regardless of the failures; the KQL indicator on traces-* reflects them.

  • The machine learning job does not open in the 2 GB lab. The default model memory estimate is 1 GB and only about 600 MB is offered to machine learning; the job on the machine learning page sets analysis_limits.model_memory_limit to 20 MB.

  • No recovery messages. A rule only sends what its actions say: add an action for the recovered group, as the burn rate rule has, if the receiver should hear that the alert ended.

  • The no-data rule takes the whole window. With a 5 minute window the first notification needs 5 empty minutes; shorten the window for a faster lab, at the cost of false alarms.

  • Basic licence. The connector and maintenance window requests are refused without the trial licence; check GET _license shows trial.

  • A second run of the script reports conflicts. The objects have fixed ids; delete them or start from docker compose down -v.

In the books

Shah’s Kibana 8.x: A Quick Start Guide to Data Analysis (Packt, 2024) ends its machine learning chapter by setting up an alert: it creates a rule for an anomaly detection job from the Rules page and then a connector for the rule’s action. The sequence (a rule, then a connector, then a test) is the one the script above automates, but the book shows the Kibana 8 menus only. In 9.x the Rules page is one list for Stack and Observability rule types, rules can be created from the API with fixed ids, the Dashboards API and the SLO burn rate rule exist, and maintenance windows filter by KQL; the book’s alerts are not a replacement for the five alerts built here, which also need the data views and field names of OpenTelemetry data.
