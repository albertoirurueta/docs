Kibana: SLOs

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked on 2026-11-09 against Kibana 9.5.x. Tested with Elasticsearch 9.5.6 and Kibana 9.5.6 in the hands-on lab (trial licence): the custom KQL SLO request below created the SLO and its two transforms and the SLI value followed the failure rate.

To do this by hand, follow Observability Rules and SLOs.

An alert on a raw threshold tells you a number crossed a line; a service level objective tells you whether users are getting the service you promised, and how much room for failure is left. Kibana ships an SLO app inside Observability: you define an indicator and a target, Kibana computes the compliance and the error budget continuously, and an SLO burn rate rule alerts when the budget is being spent too fast. The concepts (SLI, SLO, error budget, burn rate, multiwindow alerts) are explained tool-neutrally on SLIs, SLOs & Error Budgets; this page is the Kibana implementation, with two SLOs for Bookshelf. The Grafana counterpart, which on Grafana Cloud is a managed feature and on a self-managed instance a set of recording and alert rules, is on Grafana: SLOs & IRM.

Source: Service-level objectives (SLOs). SLOs have been generally available since 8.12; beta definitions from 8.11 and earlier had to be migrated.

Vocabulary as Kibana uses it

The documentation uses the usual four terms. The SLI is a measurement of service performance such as latency or availability; the SLO is the target for an SLI over a time period; the error budget is how long the SLI can miss its target before the SLO is violated; the burn rate is how fast the service uses its error budget. With target as a fraction and an observed error ratio over a window, the burn rate is

so a burn rate of 1 spends the whole budget exactly at the end of the period. For Bookshelf, a 99.5 percent availability target over 30 days (720 hours) leaves a budget of hours of full outage. A burn rate of 14.4 corresponds to an error ratio of and, sustained for one hour, consumes of the budget.

The Bookshelf SLOs

Two SLOs cover the symptoms users feel; the lab alerts of the section (high 5xx ratio, p95 latency above SLO, SLO burn rate) are derived from them.

SLI type

Custom KQL on the trace documents: requests with http.response.status_code < 500 divided by all requests

APM latency: transactions faster than a threshold divided by all transactions

Scope

Service bookshelf (service.name : "bookshelf" on traces-*)

99.5 percent, rolling 30 days, occurrences

The latency SLO uses the APM SLI type, which needs no field mapping work: Kibana reads the APM metrics that the EDOT path of APM & Synthetics already produces. The availability SLO uses the custom KQL SLI because the APM availability SLI did not read the lab’s OpenTelemetry metrics correctly (see the request below). The 500 ms threshold is an assumption of the lab, not a recommendation; choose it from what your users tolerate.

Creating an SLO in the UI

Open SLOs from the main menu or global search and choose Create SLO. Three blocks follow.

Define your SLI. Pick the type:

SLI type Definition

Custom Query (KQL)

Good and total queries against an index or data view: fields Index, Timestamp field, Query filter, Good query, Total query and Group by.

Custom metric

sum aggregations on metric fields for good and total events, each with a metric letter, a filter and an equation.

Histogram metric

range or value_count aggregations for good and total events; a range includes from and excludes to.

Timeslice metric

A statistical aggregation (average, max, min, sum, cardinality, last value, standard deviation, doc count, percentile) with an equation, a comparator and a threshold per slice. Requires the Timeslices budgeting method.

APM latency

Service name, environment, transaction type, transaction name (each all or specific) and a threshold in milliseconds, plus an optional query filter.

APM availability

The same fields without the threshold.

Synthetics availability

Successful checks (monitor status up) over total checks, selected by monitor name, project and tags; results are grouped by monitor and location automatically.

Group by creates one SLO instance for each value of a field (for example url.domain), which is how a single definition covers many monitors or services. On Serverless, projects linked through cross-project search can be scoped (this project, all projects or a subset); that scope is Serverless only.

Set objectives. The time window is rolling (relative to now, for example the last 30 days) or calendar aligned (weekly or monthly); the budgeting method is occurrences (good events against total events) or timeslices (good slices against total slices across a slice duration); the target is the percentage objective. Then name the SLO, describe it and add tags.

When you save, Kibana creates a default SLO burn rate rule with default settings and no connector, so nothing is notified until you add one (see below). You can also add the SLO Overview panel to a custom dashboard.

Source: Create an SLO. The Explore SLO events action, which opens the underlying data in APM or Discover with a good, bad or all filter, is generally available on the Stack since 9.5.

The SLO list and the detail page

The overview lists every SLO, with card, list and compact views, structured filters (combined with AND and OR, and pinnable across apps), sorting by SLI value, status, error budget consumed or remaining, and grouping by none, tags, status or SLI type. The detail page shows the burn rate over 1, 6, 24 and 72 hours and the risk of exhausting the budget, the historical SLI over the window, the error budget burn-down and the active alerts from burn rate rules. Dashboards get two panels: SLO Overview (name, current SLI, target and status) and SLO Alerts (alert status, rule name, duration and reason, with the option to create cases from the panel); see Building Dashboards for panel placement and Cases for the case workflow.

The SLOs settings page (generally available on Serverless and on the Stack since 9.4) controls source settings and remote clusters (not available on Serverless), the stale SLO threshold that hides SLOs not updated within it, and stale instance cleanup.

Source: Service-level objectives (SLOs) and Configure SLO settings.

What is underneath: transforms and indices

Each SLO definition is stored as a Kibana saved object, and Kibana creates two Elasticsearch transforms for it: a rolling-up transform named slo-{id}-{revision} that aggregates the source data into the .slo-observability.sli-v* indices, and a summarizing transform named slo-summary-{id}-{revision} that keeps current values (the observed SLI and the remaining error budget) in the .slo-observability.summary-v* index. Each transform has an ingest pipeline, and Kibana installs shared index templates. That is why the requirements read the way they do: the cluster needs at least one node with the transform role and one with the ingest role (they can be the same node), and the user needs a licence that includes SLOs.

Operational consequences:

  • Changing the SLI parameters, the objective or the time window increases the revision, reinstalls the assets and deletes the data already aggregated for the SLO; changing the name, description or tags does not. Treat an SLI edit as a restart of the history.

  • Do not edit or delete the internal transforms, pipelines or .slo-observability.* indices, and do not override their templates or settings. In recent versions the transforms are protected from manual deletion: use Reset from the SLO’s Actions menu (or the reset API) to rebuild them. Reset deletes the SLI and summary data and reprocesses everything, so it is a last resort after you have confirmed that the source data and queries are valid.

  • To see the generated assets, turn on the observability:enableInspectEsQueries advanced setting and use SLO Inspect on the edit page, which shows the configuration, both transforms, both pipelines and the transform queries.

  • Typical failures are transforms that were stopped or deleted, unparsable timestamps and malformed queries in the source data, missing ingest pipelines (Reset recreates them) and cluster problems unrelated to SLOs such as missing shards or circuit breaker errors.

Source: Troubleshoot SLOs.

flowchart LR SRC["Source data: APM metrics, logs, Synthetics"] --> T1["Rolling-up transform"] T1 --> SLI[".slo-observability.sli-v*"] SLI --> T2["Summarizing transform"] T2 --> SUM[".slo-observability.summary-v*"] SUM --> UI["SLO app, SLO Overview panel"] SUM --> BR["SLO burn rate rule"] SLI --> BR BR --> CN["Connector: webhook receiver"]

Access, licence and space behaviour

Creating SLOs needs an appropriate licence, the transform and ingest roles and SLO access. The SLO Editor needs the Observability SLOs feature privilege set to All, plus the index privileges read, view_index_metadata, write and manage on .slo-observability.* and read and view_index_metadata on the source indices (for example logs-*). The SLO Viewer needs the feature privilege set to Read and read and view_index_metadata on .slo-observability.*. The built-in editor role also works but grants write access to all Kibana apps. On Observability Serverless the SLO Editor custom role is required to create SLOs. Kibana spaces limit which SLOs appear in the SLO app, but they do not restrict the index privileges on .slo-observability.*, so a user with those privileges can read the SLO data of all spaces. The wider role model is on Spaces, Roles & Privileges.

Source: Configure SLO access.

Burn rate rules

An SLO burn rate rule alerts when the burn rate is too high over two lookback periods, a long window and a short window equal to one twelfth of it (a one-hour long window pairs with a five-minute short window). The alert fires only when both exceed the threshold, which is the multiwindow, multi-burn-rate pattern of the SRE Workbook. The form has four burn rate windows by default, each with a lookback in hours, a threshold and an action group that sets the severity (critical, high, medium or low); the documentation does not list the default thresholds, so write them down yourself. The lab uses the Workbook’s values for a 30-day SLO:

Add actions with a connector, once per severity or on recovery, with the action frequency of a summary of alerts or per alert (see Actions, Frequency & Action Variables). Context variables for the message: context.sloName, context.sloId, context.sloInstanceId, context.burnRateThreshold, context.longWindow, context.shortWindow, context.reason, context.timestamp, context.viewInAppUrl, context.alertDetailsUrl (empty unless server.publicBaseUrl is set) and, on the Stack since 9.1, context.grouping. The rule reads the .slo-observability.sli* and .slo-observability.summary* indices and these cannot be overridden per rule. For the lab, the connector is the webhook to http://webhook-receiver:8080/kibana; connectors are covered on Connectors, and the rule family on Observability Rules.

Source: Create an SLO burn rate rule and Triage SLO burn rate breaches.

Composite SLOs (preview)

A composite SLO combines several SLOs into one health indicator, as a weighted average, to track reliability at the level of a system or platform (the page’s example is a "Checkout Flow Health" made of payment, cart and inventory SLOs). It is a preview feature on Serverless and on the Stack since 9.5. Members: up to 25 SLOs, each with a relative weight (default 1; 2 counts twice as much), optionally filtered to instances when the member uses group by. Objectives: a rolling window, the occurrences method (the only one listed) and a target that is independent of the members' targets. The Composite SLOs tab shows status, healthy members, SLI value (the weighted average), budget remaining, active alerts across members and burn rates over 5 minutes, 1 hour and 1 day. It is enabled automatically on Serverless and Elastic Cloud Hosted; a self-managed deployment must set slo.compositeSloEnabled: true under feature_flags.overrides in kibana.yml. The page does not describe an API for composite SLOs. For Bookshelf, one composite of the availability and latency SLOs with equal weights gives a single "is the catalogue service healthy" tile for the dashboard; since it is a preview, keep the underlying burn rate rules as the paging signal.

Source: Create a composite SLO.

SLOs as code

The REST API creates an SLO with POST /s/{spaceId}/api/observability/slos (the default space when the prefix is omitted), with the kbn-xsrf header and the SLOs feature privilege set to All. The required body fields include name, description, indicator, timeWindow, budgetingMethod and objective; objective.target is a fraction between 0 and 1 (excluding 1), and rolling windows accept 7d, 30d or 90d (calendar-aligned: 1w or 1M). Optional settings are frequency (1m to 59m, default 1m), syncDelay (1m to 359m, default 1m) and preventInitialBackfill. The APM indicators take service, environment, transactionType, transactionName and (for latency) threshold; the custom KQL indicator is shown here, because its fields are the same for any data. In the lab it reads the OpenTelemetry trace documents of Bookshelf, whose service.name and http.response.status_code are the field names shown here.

curl -s -X POST "http://localhost:5601/s/bookshelf/api/observability/slos" \
  -u "elastic:${ELASTIC_PASSWORD}" \
  -H "kbn-xsrf: true" -H "Content-Type: application/json" \
  -d '{
    "name": "Bookshelf availability",
    "description": "99.5 percent of requests do not fail with a server error",
    "indicator": {
      "type": "sli.kql.custom",
      "params": {
        "index": "traces-*",
        "timestampField": "@timestamp",
        "filter": "service.name : \"bookshelf\"",
        "good": "http.response.status_code < 500",
        "total": "http.response.status_code : *"
      }
    },
    "timeWindow": { "duration": "30d", "type": "rolling" },
    "budgetingMethod": "occurrences",
    "objective": { "target": 0.995 },
    "tags": ["bookshelf", "lab"]
  }'

The response returns the id of the new SLO. Keep SLO definitions in Git as JSON bodies and apply them from CI, in the same way as the rules of Alerting APIs & Terraform. Because changing an SLI resets its history, a pipeline should update name, description and tags freely but treat indicator, objective and window changes as deliberate.

Reference: Kibana API: Create an SLO.

What can go wrong

  • The SLO shows no data: the cluster has no transform or ingest node, the transforms are stopped, or the source index or KQL matches nothing; open SLO Inspect and run the transform query in Dev Tools.

  • A latency SLO of "p95 under X" is built as a threshold SLI, not a percentile: the compliance is the share of transactions under the threshold, so choose the target as 95 percent, not as a latency value.

  • The burn rate rule never notifies: the default rule created with the SLO has no connector.

  • Editing the SLI wipes the history and the burn-down restarts: plan edits for the start of a period.

  • Spaces do not hide SLO data from users who hold index privileges on .slo-observability.*.

  • Composite SLOs are a preview and need the feature flag on self-managed deployments.

Verify it in the lab

  1. Start the kibana profile with the load generator running and open Applications to confirm the bookshelf service reports (see APM & Synthetics).

  2. Create the availability SLO with the custom KQL SLI on the trace documents (the request of the previous section; the APM availability SLI did not read the lab’s OpenTelemetry metrics correctly), 99.5 percent, rolling 30 days, occurrences, and, if you want a latency SLO, one with the APM latency SLI and a 500 ms threshold. In Dev Tools run GET _transform and check that two slo- transforms exist for each SLO.

  3. Edit each SLO’s burn rate rule to use the four windows of the table and add a webhook connector to http://webhook-receiver:8080/kibana.

  4. Switch the load generator to failing-request mode. The SLI value falls and the 1 hour burn rate climbs on the detail page; with a healthy history the critical window needs roughly the time it takes the 1 hour ratio to pass 0.072, plus the short window, so expect the alert after several minutes, and the webhook receiver must log it with the SLO name.

  5. Return to normal traffic and check that the recovery notification arrives and the rule shows recovered.

  6. Optional: create a composite SLO of the two with equal weights (set slo.compositeSloEnabled: true in kibana.yml first on a self-managed stack) and add the SLO Overview panel to the dashboard "Bookshelf service health".

In the books

Hausenblas, Cloud Observability in Action, chapter 10, covers the fundamentals of SLOs, their implementation with Prometheus and a survey of commercial SLO offerings, and Chapman and Holmes, Observability with Grafana, chapter 9, writes alerts from SLIs and SLOs. Neither covers the Elastic SLO app: the SLI types, the transform-based computation, composite SLOs and the burn rate rule of this page are newer than the books.
