Kibana: Infrastructure & Host Monitoring

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked on 2026-11-09 against Kibana 9.5.x.

To do this by hand, follow Tour of the Observability Apps.

A service is only as healthy as the machines, containers and pods that run it. The Observability Infrastructure apps in Kibana answer the USE questions (utilisation, saturation, errors) for those resources: which hosts are busy, which pod is about to run out of memory, whether a slow Bookshelf response coincides with a saturated node. This page explains the three views (Hosts, Inventory and the metrics grid in Discover), how they get their data, which of them are deprecated or still planned in 9.5, and how infrastructure anomaly detection fits next to alert rules. The method itself (RED for services, USE for resources) is on Monitoring Methods: RED, USE & Golden Signals; the rules that alert on these metrics are on Observability Rules.

Source: Infrastructure and host monitoring. The section is generally available on Elastic Stack and Elastic Cloud Serverless.

What the Infrastructure apps read

The Infrastructure UI reads, by default, the indices that match metrics-* and metricbeat-*; settings can change that (see Configure infrastructure and host metrics settings). Elastic recommends Elastic Agent for collecting infrastructure metrics and logs, and the Elastic OpenTelemetry Collector (EDOT) as the preferred route for system metrics and logs in a new deployment. Both end up in the same data streams that the apps query, so a host reporting through EDOT and a host reporting through the Elastic System integration appear side by side. The ingestion options are on Ingesting Monitoring Data.

Two schemas therefore coexist, and the apps name them in a Schema selector. When data for both exists, the selector defaults to OpenTelemetry; you can switch to the Elastic System integration schema (hosts) or the Kubernetes integration (pods). The schema decides which fields are read, for example k8s.pod.uid for OpenTelemetry versus kubernetes.pod.uid for the Kubernetes integration, which matters as soon as you write a KQL filter, a rule or a dashboard on these fields.

Source: Analyze infrastructure and host metrics, Get started with system metrics (for the System integration: a Kibana user with All privileges on Fleet and Integrations on Stack, the Admin role or higher on Serverless).

The Hosts page

The Hosts page is the fleet view: a row per host with its CPU, load, memory and disk figures and the number of active alerts, plus overview tiles for the host count, average CPU usage, average normalised load, average memory usage and the maximum disk usage. Below the tiles, a Metrics tab charts CPU, normalised load, memory, disk usage and disk IOPS and throughput for the hosts in scope. Click a host to open its details, which has tabs for Overview, Metadata, Metrics, Processes, Universal Profiling, Logs, Anomalies and Osquery.

How to use it for monitoring:

  • Filter with KQL (for example host.os.type : "linux") or with the Operating System, Cloud Provider and Service Name lists, each of which can include or exclude values. The Service Name filter only works for services instrumented by APM, so it is the quickest way to ask "which hosts run Bookshelf?".

  • The host limit defaults to 50 and shows the top hosts by most recent timestamp. Raising it makes the page slower, and sorting the table sorts only the rows already returned. On a large fleet, narrow the scope with a filter before sorting; do not assume the table is a ranking of the whole fleet.

  • The alert count per host only appears when the rules associate alerts with hosts: a custom threshold rule needs host.name in Group alerts by, and an inventory rule needs the node type Host. A rule that groups by something else works, but the host row will show no alert badge.

  • The Schema selector, schema-adapted host details, the Processes tab and the Anomalies tab are generally available since 9.2. The Anomalies tab does not exist for OpenTelemetry hosts. Processes for OpenTelemetry hosts needs the collector to send process metrics.

  • An enhanced logs view in the host details is in preview since 9.0 on the Stack and needs the observability:newLogsOverview advanced setting.

Source: Analyze and compare hosts.

The Inventory

The Inventory is the topology-flavoured view: a waffle map with one tile per resource, coloured by a metric (CPU usage by default), which you can group by a related field (cloud region, availability zone, namespace), sort by name or metric value, filter with KQL and switch to a table. Select the Show menu to change the resource type:

Resource type What to know

Hosts (default)

Elastic System integration or OpenTelemetry schema. Details overlay with the same tabs as the Hosts page.

Kubernetes Pods

Kubernetes integration or OpenTelemetry schema; if both have data, OpenTelemetry is the default. Switching schema does not clear Group by, so the map can look empty until you clear or reselect it. Pod log usage and nginx charts are hidden for OpenTelemetry; anomaly detection is not available for OpenTelemetry pods. Schema selection for pods is generally available on Serverless and Planned for the Stack.

Docker Containers

All containers, including containerd, with Elastic integrations only (no Schema menu). The waffle map currently displays only Docker fields, so containerd containers may show 0 percent or null.

AWS

EC2 instances, S3 buckets, RDS databases and SQS queues. No Schema menu.

Select a tile to open its details overlay (it can be expanded with Open as page), hover to see its metrics, and add a custom metric from the Metric menu with Add metric. From a pod you can jump to its logs, APM traces and Uptime data. Alert rules on the Inventory (CPU, memory, network, disk, and so on, with a threshold and a node type) are the Observability Inventory rule, described on Observability Rules.

Source: View infrastructure metrics by resource type.

Kubernetes monitoring

Kubernetes is the most common reason to open the Inventory. The documented route is the Elastic Agent Kubernetes integration deployed as a DaemonSet, plus kube-state-metrics, which you must deploy yourself for state metrics. Defaults of the integration: the kubelet (port 10250), kube-state-metrics (8080), kube-apiserver and kube-proxy are collected out of the box, every 10 seconds except the apiserver (30 seconds); kube-scheduler and kube-controller-manager must be enabled; container logs and Kubernetes events are on, audit logs must be turned on and are a technical preview. Elastic’s 9.5 announcement describes Kubernetes monitoring as generally available, shipped with preconfigured dashboards, alerts, SLOs and machine learning jobs, with onboarding defaulting to the OpenTelemetry path. The tutorial page itself still describes the Elastic Agent route, so read the announcement for the scope of the 9.5 package and the integration page for what the package version contains.

Deploying the DaemonSet, setting ES_USERNAME and ES_PASSWORD and verifying with kubectl -n kube-system get pods -l app=elastic-agent are covered step by step in the tutorial; the cluster-side basics (resource requests, probes, kube-state-metrics) are on Kubernetes Observability: Logging and Metrics, which this page does not repeat. The lab does not run Kubernetes, so there is nothing to verify for this section beyond reading the manifest.

Source: Tutorial: Observe your Kubernetes deployments and What’s new in Elastic 9.5 (the generally available claim).

Metrics Explorer is deprecated: use the Discover metrics grid

Before 9.4, Metrics Explorer charted any metric against related metrics and split it by a field. It is generally available from 9.0 to 9.3 and deprecated since 9.4 on the Stack (it is not listed for Serverless). The metric threshold rule that you could create from it carries the same deprecation and is unavailable on Serverless; the custom threshold rule is the rule to use in new work (see Observability Rules).

The replacement is the Discover metrics experience: in Discover, switch to ES|QL mode and run a TS query to get a grid of charts, one per available metric, which you can search, filter, break down by a dimension and add to a dashboard. It is generally available on the Stack since 9.4 and on Serverless. The grid works on metrics stored in a time series data stream (TSDS), which is the default storage for OTLP and Prometheus remote-write ingestion; PromQL works on any metrics stored in a TSDS, whatever the ingest path (PromQL: generally available on the Stack since 9.5, preview in 9.4). Storage and downsampling of those streams are on Data Streams, TSDS & Lifecycle, the query languages on Querying with KQL, ES|QL & PromQL.

TS metrics-*

Run this in Discover with ES|QL selected: the result is the metrics grid, from which you pick the charts to keep.

Source: Explore your metrics.

Infrastructure metric anomalies

Thresholds catch known limits; anomaly detection catches "unusual for this machine". The Inventory has an Anomaly detection link: choose Enable for Hosts or Kubernetes Pods, pick a start date and a partition field (on the Stack the default is kubernetes.namespace), and enable the jobs. The jobs model system memory usage and inbound and outbound network traffic, analyse the last four weeks of data and then run indefinitely. Results appear in an Anomalies table that lists anomalies with a severity score of 50 or higher, with a summary value showing the difference from the typical value, and with actions to open the Anomaly Explorer or show the resource in the Inventory.

Things that can go wrong:

  • The job settings cannot be changed after creation; recreating the jobs removes the anomalies found so far.

  • Metric anomaly detection is not available for OpenTelemetry hosts or pods, so a fleet reporting only through EDOT shows no Anomalies tab. Use alert rules there, or run a job of your own on the OpenTelemetry fields (see Machine Learning & AIOps).

  • Machine learning needs a licence that includes it and nodes with the ml role; on Serverless the Editor role or higher creates the jobs.

  • The predefined jobs use custom rules; edit them with Actions then Configure rules, and note that changes only apply to new results unless you clone and rerun the job.

Source: Detect metric anomalies.

What can go wrong

  • An empty Inventory or Hosts page almost always means the data is in indices the app does not read, or the schema selector points at the schema with no data. Check the data streams in Discover first, then the schema selector.

  • A grouping field that does not exist in the chosen schema produces an empty map, and it persists after switching schema.

  • A host appears twice when it is monitored by both an Elastic Agent System integration and an OpenTelemetry collector; send host metrics through one path.

  • Do not install a second Elastic Agent on a host that already has one; add the inputs to the existing agent instead.

  • A rule that does not group by host.name never shows a badge on the Hosts page, even when it fires.

  • Metrics Explorer bookmarks keep working in 9.0-9.3 and are deprecated from 9.4: move saved investigations to Discover and to dashboards.

Verify it in the lab

  1. Start the kibana profile of the hands-on lab with the load generator running. The lab’s EDOT Collector has only an OTLP receiver (no hostmetrics receiver), and the Bookshelf stand-in sends traces and logs but no metrics, so the lab produces no host metrics.

  2. Open Infrastructure then Hosts. Expect no hosts, and no host data for the Schema selector to choose from. The page lists a host only after a hostmetrics receiver, or an Elastic Agent System integration, sends host metrics.

  3. Open Discover, select ES|QL and run TS metrics-*; the metrics grid lists the APM metrics that the collector’s elasticapm connector derives from the Bookshelf traces, and no host metrics.

  4. Open Infrastructure inventory and the Anomaly detection link. The Hosts job needs host data, and the page documents metric anomaly detection for Elastic System data and not for OpenTelemetry hosts, so expect no Anomalies tab in the lab.

In the books

Melachi, Elastic from A to Z, section 3.6, installs Metricbeat on Windows, enables its system module and loads its predefined assets with setup, using the 7.10 packages and a Windows-service installation. Today the Infrastructure UI reads metrics-* and metricbeat-*, Elastic Agent and the OpenTelemetry Collector are the recommended collectors, and the Hosts page, the schema selector, the Discover metrics grid and Kubernetes monitoring did not exist in that form. Publisher pages are listed in the bibliography of the section index.
