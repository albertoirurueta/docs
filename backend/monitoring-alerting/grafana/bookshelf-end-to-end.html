Grafana: Bookshelf End to End

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked on 2026-11-09 against Grafana 13.3.x. Tested with Grafana Enterprise 13.3.0 in the hands-on lab (Alloy 1.10, Prometheus 3.5, Loki 3.5, Tempo 2.8).

The earlier pages of this subsection each explain one part: data sources, panels, rules, policies, contact points, templates and provisioning. This page puts them together for the lab service Bookshelf and then breaks the service on purpose. When it is done you have the "Bookshelf service health" dashboard and five alerts that were all loaded from files, and you have seen each alert go from pending to firing to a message at the webhook receiver. The same dashboard and the same five alerts are built in Kibana on Kibana: Bookshelf End to End, which ends with the side-by-side comparison.

Everything below runs in the grafana profile of the hands-on lab; the files named here are the ones listed on that page and are loaded by the Grafana container at start, so there is nothing to click.

The thresholds are the lab values used across this section: 0.05 for the 5xx ratio and 0.5 s for the latency objective. They are deliberately low so that a breach is visible within minutes. The reasoning for each number is on Provisioning Alerting Resources and Designing Actionable Alerts.

Start the lab

cd lab
docker compose --profile grafana up -d
curl -s -u admin:admin http://localhost:3000/api/v1/provisioning/alert-rules | jq -r '.[].title'

Five titles mean the alerting file was loaded. A rule group with no folder yet creates the folder bookshelf, and the dashboard provider reuses it, so the dashboard and the rules sit in one folder.

Data sources

Three data sources are provisioned with fixed uids, so that dashboards and rules can refer to them: prometheus (the default), loki and tempo. The Loki data source has a derived field that turns the trace_id in a JSON log line into a link to Tempo, and the Tempo data source links back to the logs of a trace. The $$ in the derived field URL is how a literal $ is written in a provisioning file, because Grafana interpolates environment variables in these files (see Data Sources).

grafana/provisioning/datasources/datasources.yaml 
apiVersion: 1
datasources:
  - name: Prometheus
    uid: prometheus
    type: prometheus
    access: proxy
    url: http://prometheus:9090
    isDefault: true
    jsonData:
      timeInterval: 15s
      prometheusType: Prometheus
      prometheusVersion: 3.5.0
  - name: Loki
    uid: loki
    type: loki
    access: proxy
    url: http://loki:3100
    jsonData:
      derivedFields:
        - name: trace_id
          matcherRegex: '"trace_id":\s*"(\w+)"'
          urlDisplayLabel: Trace
          url: "$${__value.raw}"
          datasourceUid: tempo
  - name: Tempo
    uid: tempo
    type: tempo
    access: proxy
    url: http://tempo:3200
    jsonData:
      tracesToLogsV2:
        datasourceUid: loki
        filterByTraceID: true
      serviceMap:
        datasourceUid: prometheus
  - name: TestData
    uid: testdata
    type: grafana-testdata-datasource
    access: proxy
    isDefault: false

Reference: Grafana: Provisioning, data sources.

Check them with curl -s -u admin:admin http://localhost:3000/api/datasources/uid/prometheus/health; the other two work the same way and answer Data source successfully connected. and Data source is working.

The dashboard

The dashboard is a classic JSON file loaded by a file provider. The provider has allowUiUpdates: false, so the file is the source of truth, and the dashboard has the uid bookshelf-service-health, which the alert rules link to.

grafana/provisioning/dashboards/dashboards.yaml 
apiVersion: 1
providers:
  - name: bookshelf
    orgId: 1
    folder: bookshelf
    type: file
    disableDeletion: false
    allowUiUpdates: false
    options:
      path: /var/lib/grafana/dashboards/bookshelf

The layout follows the overview level of Dashboard Design Principles:

Row and panel Query Reading it

Variables job, application and route

Query variables chained on http_server_requests_seconds_count (job, then application for that job, then the uri values for both; route is multi-value with All as .+)

Filter the time series (ids 5 and 6) and the table (id 8). The stat panels keep application="bookshelf" so that they show the same numbers as the alert rules.

Annotations "Annotations & Alerts" and "Deployments"

The built-in Grafana annotations, and Grafana annotations tagged bookshelf and deploy

Alert state changes and a marker for each deploy posted to the annotations API (see Annotations and Links).

Golden signals, stat "Requests per second" (id 1)

sum(rate(http_server_requests_seconds_count{application="bookshelf"}[$__rate_interval]))

Traffic. A flat zero means no data or no clients.

Golden signals, stat "5xx ratio" (id 2)

The 5xx rate divided by the total rate; unit Percent (0.0-1.0), red from 0.05

Errors. This is the panel the alert links to (panelId 2).

Golden signals, stat "p95 latency" (id 3)

histogram_quantile(0.95, ...) over the _bucket series; unit seconds, red from 0.5

Latency against the objective.

Golden signals, stat "Instances up" (id 4)

count(up{job="bookshelf"} == 1) or vector(0), with the value 0 mapped to DOWN

Saturation of the simplest kind: is anything scraped.

Golden signals, time series (ids 5 and 6)

Request rate by status; p95 per uri with a dashed 0.5 s threshold line

The shared crosshair in a six hour window shows which route breaks first.

Logs and traces, logs (id 7) and table (id 8)

{application="bookshelf"} | json | level="ERROR"; p95 per route as a sorted table

Error lines with a link from trace_id to Tempo; slowest routes.

Dependencies (collapsed, ids 9 and 10)

jvm_memory_used_bytes{area="heap"}; hikaricp_connections_active / hikaricp_connections_max

Heap and connection pool utilisation, one scroll away.

The alert rules, contact point, template and policies

One provisioning file, grafana/provisioning/alerting/bookshelf.yaml, holds all alerting resources: two rule groups (bookshelf-service-level and bookshelf-availability-and-logs, each evaluated every minute), the contact point bookshelf-webhook, the template group bookshelf, the mute timing bookshelf-weekends and the policy tree. Every rule is a query, a Reduce expression (last, dropping non-numeric results) and a Threshold or Math expression as the condition. The three rules on the request metrics use OK for No Data, because no traffic is not an incident by itself; the no-data rule uses Alerting and the error-log rule reads Loki with an instant query. The rules carry the labels team: bookshelf-sre, application: bookshelf and a severity, and the 5xx rule carries the dashboard and panel link that fills dashboardURL and panelURL in the notification. Each rule is explained on the page named below:

  • Alert Rules, Queries and Conditions: the query, Reduce and Threshold pipeline.

  • Rule Evaluation, States and Missing Data: why noDataState differs per rule.

  • Notification Policies: the tree, with severity = critical using group wait 10 s and repeat 1 h.

  • Notification Templates: bookshelf.title and bookshelf.message.

  • Contact Points and Integrations: the webhook settings title and message.

Break the service and watch

Run these in order, with the notification receiver open in a second terminal (docker compose logs -f --no-log-prefix webhook-receiver). The times below were measured on the lab for this page, from the moment the load generator switched mode to the first WEBHOOK line of that alert; treat them as the order of magnitude, not as promises.

Step Command First notification What you see

1. Break with 5xx errors

curl -X POST localhost:8090/mode/failing

Error-log spike after 1 min 42 s; high 5xx ratio after 2 min 32 s; SLO burn rate after 2 min 38 s

Each rule is Pending, then Firing when its pending period has passed. The three arrive as three notifications, one per alertname, because the policy tree groups by alertname and grafana_folder. The critical policy waits 10 seconds (its group wait) after the instance starts firing.

2. Return to normal

curl -X POST localhost:8090/mode/normal

Resolved messages: 5xx ratio after 5 min 29 s; error-log spike after 7 min 39 s; burn rate after 10 min 35 s

The 5 minute rate windows must drain first. The burn rate rule shows Recovering for its 5 minute keep-firing period before it resolves.

3. Slow responses

curl -X POST localhost:8090/mode/slow

p95 latency above SLO after 6 min 51 s

The rule waits for its 5 minute pending period, so it is the slowest to fire. Its resolved message is held until the next group interval (5 minutes, inherited from the default policy) after the rule recovers.

4. Stop the service

docker compose stop bookshelf loadgen

No data after 3 min 20 s

The up series drops to 0 and then disappears; the rule has No Data handled as Alerting and a 2 minute pending period. Start the containers again and the resolved message follows after about 1 min 20 s (the critical group interval is 1 minute).

5. Errors in the log only

curl -X POST localhost:8090/mode/log-errors

Error-log spike after 1 min 52 s

Responses stay 200, so the 5xx, latency and burn rate rules stay quiet and only the log rule fires.

All times are from one run on a laptop with Docker Desktop; the first notification of an alert needs its pending period plus up to one evaluation interval (1 minute) plus the group wait of the policy (10 seconds for critical, 30 seconds for warning).

What the receiver gets

Each delivery is one WEBHOOK line in the receiver log. The title and message come from the template group bookshelf of the lab file:

[FIRING:1] Bookshelf high 5xx ratio
* Bookshelf high 5xx ratio (critical): Bookshelf 5xx ratio is 0.4 (threshold 0.05)
  Runbook: https://example.com/runbooks/bookshelf-5xx-ratio

The body of that delivery, with the labels alertname, application, grafana_folder, severity and team, the annotations, the dashboardURL and panelURL of the dashboard panel with id 2, and the values of the query and expression refIds, is the payload shown on Contact Points and Integrations. A resolved delivery has "status": "resolved" and an endsAt timestamp. Read the deliveries with:

docker compose logs --no-log-prefix webhook-receiver | grep WEBHOOK
curl -s localhost:8081 | jq -r '.[] | "\(.time) \(.path)"'

Read the alert history

State changes are also stored in Loki, because the lab enables the Loki state history backend (GF_UNIFIED_ALERTING_STATE_HISTORY_BACKEND=loki). Every transition of the 5xx rule, with the values that caused it, is one log line:

curl -s -G http://localhost:3100/loki/api/v1/query_range \
  --data-urlencode 'query={from="state-history"} | json | ruleTitle="Bookshelf high 5xx ratio"' \
  --data-urlencode limit=5 | jq -r '.data.result[].values[][1]'

Each line shows previous, current (Pending, Alerting, Normal), the values of the query and expression refIds and the labels. The Alerting, History views of the UI read the same data (see Monitoring Alerts and State History).

What can go wrong

  • The folder uid is generated. The rule file creates the folder bookshelf when it does not exist, because Grafana provisions alerting before dashboards, so the folder gets a random uid. Look it up (curl -s -u admin:admin http://localhost:3000/api/folders | jq) where an API call needs a folderUID.

  • The dashboardUid and panelId keys do nothing in a rule file. The export shows them, but a rule loaded from a file with those keys had no dashboard link on Grafana 13.3.0. The annotations __dashboardUid__ and __panelId__ set the link, and dashboardURL and panelURL appear in the notification.

  • A $ in a value disappears. Provisioning files interpolate environment variables, so the derived field URL in the data source file writes $$ for a literal $. Rule annotations, the query model and the template group are not interpolated.

  • The burn rate alert fires much sooner than the arithmetic says. In a lab that has run for a few minutes the 1 hour rate is computed over the minutes that exist. Start the alert test after an hour of healthy traffic to see the textbook behaviour.

  • Resolved messages arrive late. A grouped notification is sent again only after the group interval of its policy: 1 minute for critical and 5 minutes for warning in the lab tree.

  • The no-data rule never fires. The query is max(up{job="bookshelf"}); if you removed the scrape job instead of stopping the service the series is missing, which is exactly the No Data case the rule handles with noDataState: Alerting.

  • Changing the file has no effect. Rules from files are read at start; call curl -s -u admin:admin -X POST http://localhost:3000/api/admin/provisioning/alerting/reload after editing.

In the books

The three-part pattern here (a dashboard that answers "is it healthy", alert rules that page on the same numbers, and a routed notification) is the one Salituro’s Learn Grafana 10.x builds in its dashboard and alerting chapters, and the one McCollam’s Getting Started with Grafana (Apress) sketches for alert notification channels. Both predate unified alerting’s current form: the notification channels they configure per alert are replaced by contact points and a policy tree, rules are written as query, Reduce and Threshold expressions, and the whole setup can be provisioned from files as above.
