Grafana: Provisioning Alerting Resources

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked on 2026-11-09 against Grafana 13.3.x. Tested with Grafana Enterprise 13.3.0 in the hands-on lab: the complete YAML file below is the lab’s rule file: it loads, the Admin API reload applies a changed file, and the export returns the same keys; the HCL passes terraform validate with provider 4.54.0 (it was not applied).

Alerting configuration is the most fragile part of a monitoring setup: it is clicked together once, nobody remembers which rule routes where, and it is lost with the database. Grafana can take every alerting resource from files, from an HTTP API or from Terraform, and can export what already exists in the same formats. This page shows the options, what "provisioned" means for the user interface, and then the complete alerting configuration of the Bookshelf lab, twice: once as provisioning YAML and once as Terraform HCL. The tool-neutral argument for putting observability in Git, and the pipeline around it, is in Observability as Code; dashboards as code is in Grafana: Dashboards as Code.

The resources used here are explained on their own pages and are only applied here: Alert Rules, Evaluation and Missing Data, Labels and Annotations, Notification Policies, Contact Points, Notification Templates and Mute Timings.

The options

Option Use it when Watch out for

File provisioning (provisioning/alerting/*.yaml)

Grafana is self-managed (including Docker and Kubernetes) and the files ship with the image or a volume.

Not available in Grafana Cloud. Provisioned resources cannot be edited in the UI.

Terraform (grafana/grafana)

You want plan and apply, drift detection and one tool for folders, data sources and alerting; works for Cloud too.

The provider needs an API token with the alerting provisioning roles; state can hold secrets.

Alerting provisioning HTTP API

Scripts and CI jobs that create, change or delete Grafana-managed resources.

Its JSON is not the file or Terraform format; the contact point, policy, template and mute timing endpoints are deprecated.

Notifications and rules APIs (/apis/notifications.alerting.grafana.app/v1beta1/..., /apis/rules.alerting.grafana.app/v1beta1/...)

New integrations and kubectl-style tooling; the documented replacement of the provisioning endpoints.

Beta API version (v1beta1), so fields can still change.

Export (UI and .../export endpoints)

Starting from what already exists: build in the UI, export as YAML, JSON or HCL, commit.

The export format cannot be sent back to the HTTP API; notification template groups have no export.

Data source-managed rules (including their recording rules) are not part of these options; they are managed with the Mimir or Cortex tools (see Recording Rules).

Source: Grafana: Provision Alerting resources.

Provenance: why provisioned resources are read-only

Every resource has a provenance. Resources created through the HTTP API report "provenance": "api", file-provisioned ones "file", and the user interface labels them Provisioned. Provisioned resources can be edited only at their source: a rule from a file cannot be changed in the UI or in Terraform, and the reverse. That protects the code from silent drift, and it is also the first thing users hit when they try to "just quickly fix" a threshold during an incident. Two escape hatches exist, both of which give up the protection: the X-Disable-Provenance: true header on the create and update requests of the HTTP API, and disable_provenance = true on the Terraform resources. Importing a resource that already exists causes a conflict, so remove the existing one first.

Source: Grafana: Provision Alerting resources and Grafana: Alerting provisioning HTTP API (provenance and the X-Disable-Provenance header).

The Bookshelf alerting configuration

The lab defines these resources, using the values of the other lab pages: data source uids prometheus and loki, the label application="bookshelf", the folder bookshelf, the team label bookshelf-sre and the dashboard "Bookshelf service health" (uid bookshelf-service-health).

Resource Definition

Folder

bookshelf; the lab’s rule file creates it with a generated uid, other setups create it before the rules (see below), and it carries the folder permissions of the team (see Users, Teams and Permissions).

Rule group bookshelf-service-level (1 minute)

Bookshelf high 5xx ratio (5xx ratio above 5 percent for 2 minutes, critical), Bookshelf p95 latency above SLO (p95 above 0.5 s for 5 minutes, warning) and Bookshelf SLO burn rate (fast burn, 5 minute and 1 hour windows, critical).

Rule group bookshelf-availability-and-logs (1 minute)

Bookshelf no data (the up series of the service missing or 0, critical, No Data handled as Alerting) and Bookshelf error-log spike (more than 20 ERROR lines in 5 minutes, warning).

Contact point bookshelf-webhook

A webhook to the lab receiver, with title and message from the template group bookshelf.

Notification policy tree

Default policy to bookshelf-webhook; child team = bookshelf-sre; under it severity = critical (short group wait, 1 hour repeat) and severity = warning (12 hour repeat, muted by bookshelf-weekends).

Message template bookshelf

bookshelf.title and bookshelf.message.

Mute timing bookshelf-weekends

Saturday and Sunday, UTC.

How the numbers were chosen: 0.05 is a deliberately noisy lab threshold so the alert fires within minutes under load; 0.5 s is the lab latency SLO; the burn rate rule assumes a 99.5 percent availability objective (error budget 0.005), so a fast burn of 14.4 times the budget is a ratio of 0.072 in both the 1 hour and the 5 minute window, following the multiwindow pattern of the SRE workbook (see SLIs, SLOs and Error Budgets). The p95 rule needs histogram buckets, which Micrometer publishes only when percentile histograms are enabled for http.server.requests (see Metrics and Observability).

Every rule is a three or five step pipeline: instant queries (A, and B for the second window of the burn rate rule), a Reduce expression that turns each result into one number, and a Threshold (or Math) expression that is the condition. The No Data and Error handling is chosen per rule: the ratio, latency and log rules use OK for No Data because "no traffic" or "no error lines" is not an incident, and the dedicated no-data rule uses Alerting because the absence of the up series is exactly what it exists to detect (see Rule Evaluation, States and Missing Data). The labels application, team and severity are on every rule (the last two route), the 5xx rule links to its dashboard panel with the annotations __dashboardUid__ and __panelId__, and the runbook lives in an annotation, so the policy tree and the message template need no other input (see Designing Actionable Alerts).

Create the folder first

File provisioning of rules refers to the folder by name and creates it with a generated uid when it is missing, which is what happens in the lab. Terraform and the API refer to it by uid, so where the uid must be known create the folder once beforehand, for example through the folder API of the /apis family (basic authentication with the admin account):

curl -s -u admin:admin -X POST -H 'Content-Type: application/json' \
  http://localhost:3000/apis/folder.grafana.app/v1/namespaces/default/folders \
  -d '{"metadata":{"name":"bookshelf"},"spec":{"title":"bookshelf"}}'

Reference: Grafana: Folder API. Terraform creates it itself (see below).

File provisioning

Put YAML or JSON files in the provisioning/alerting directory of the instance and restart Grafana, or reload them with the Admin API. In the lab Compose file mount the directory read-only at /etc/grafana/provisioning/alerting. The file format has one top-level key per resource type, each with its own deleteX counterpart for removals.

Notes on the file format

  • Which values are interpolated. $VARIABLE in a value is replaced by the environment variable (or an empty string), and a literal dollar sign is written $$. Most properties are interpolated, but not rule annotations, the rule time range, the query model, the mute timing name and intervals and the template group name and content. That is why the Go templates in the annotations and the template group, and $C > 0.072 in the Math expression, are written with a single $, while a contact point setting that contained a template with $labels would need $$labels. Secrets belong in environment variables referenced as $WEBHOOK_PASSWORD in contact point settings.

  • The policy tree is one resource. Provisioning policies overwrites the whole tree and you cannot provision parts of it; policies that Grafana creates internally when a rule selects a contact point directly are not affected. A policy list can be reset with resetPolicies: [1].

  • Uids. A rule or receiver uid is at most 40 characters of letters, numbers, - and _. Keep them stable, because changing a uid is deleting one resource and creating another (history and state are lost).

  • Removals. Deleting a file does not delete its resources. Use deleteRules, deleteContactPoints, deleteTemplates and deleteMuteTimes entries (each addressed by orgId and uid or name).

  • Rule fields. for, keepFiringFor, noDataState, execErrState, isPaused, annotations, labels and the per-query relativeTimeRange (from and to in seconds before the evaluation) are the field names of the rule export. A rule may set notification_settings instead of relying on the tree, and recording rules use a record block (see Recording Rules).

Source: Grafana: Provision Alerting resources with files (environment variable interpolation) and the Grafana source provisioning_alert_rules.go (AlertRuleExport, keepFiringFor, isPaused, relativeTimeRange).

Apply and reload

Restarting Grafana applies the files. To apply changes without a restart use the Admin API, which works only with basic authentication of a user that has the provisioning:reload action on the provisioners:alerting scope:

curl -s -u admin:admin -X POST http://localhost:3000/api/admin/provisioning/alerting/reload

Reference: Grafana: Admin API (reload provisioning configurations).

Terraform

The grafana/grafana provider manages the same resources. The documentation pins >= 4.47.0; the latest release at the time of writing is 4.54.0. The provider needs a service account token whose role can use the alerting provisioning API, which is why the lab ci-provisioner service account holds the fixed:alerting.provisioning.* roles (see Alerting HA and Operations). For Terraform itself see Getting Started, Providers, State and Sensitive Data.

terraform {
  required_providers {
    grafana = {
      source  = "grafana/grafana"
      version = ">= 4.47.0"
    }
  }
}

variable "grafana_url" {
  type    = string
  default = "http://localhost:3000"
}

variable "grafana_token" {
  type      = string
  sensitive = true
}

Notes on the Terraform resources

  • jsonencode for model. The query model is a data source specific JSON string. The documentation recommends creating a complex rule in the UI and copying its JSON, and the same applies to Loki and Prometheus fields such as editorMode and queryType. Use datasource_uid = "__expr__" for the expression stages.

  • One policy resource. grafana_notification_policy manages the entire default tree and overwrites it; it does not overwrite internal policies created when rules select a contact point directly. Only one such resource should exist per organization. Notice how the tree refers to the contact point and the mute timing by resource reference, so Terraform creates them first, which is something file provisioning cannot express.

  • Quoting. A Go template inside an HCL string needs the inner double quotes escaped, and a $ followed by { would start an HCL interpolation, which is why the rule uses $values.B.Value (no brace) and a heredoc (<<-EOT) holds the template group.

  • Optional fields. keep_firing_for, missing_series_evals_to_resolve, notification_settings (per-rule routing that overrides the tree, needs the alertingSimplifiedRouting toggle) and record (recording rules, needs the grafanaManagedRecordingRules toggle) exist on rule; disable_provenance = true on any of the resources allows UI edits at the cost of drift.

  • Multiple routing trees. Besides the default tree, the provider has grafana_apps_notifications_routingtree_v1beta1 for named trees; a rule routes to one with notification_settings { policy = ... }, and rules without it stay on the default tree.

  • Applying and importing. terraform init, terraform plan and terraform apply as usual. Existing resources are imported with the addresses shown below. See Import and Query and, for a pipeline, CI/CD and Automation.

terraform import grafana_rule_group.name "{{ folderUID }}:{{ title }}"
terraform import grafana_message_template.name "{{ name }}"
terraform import grafana_mute_timing.name "{{ name }}"

Source: Grafana: Provision Alerting resources with Terraform and the resource pages above (schema of rule, data, notification_settings, policy).

The HTTP API and the new APIs

The alerting provisioning API (/api/v1/provisioning/...) is what the Terraform provider itself uses. Requests carry Authorization: Bearer <token>, and on Enterprise some endpoints need specific RBAC permissions.

Resource Endpoints

Alert and recording rules

POST and GET on /api/v1/provisioning/alert-rules; GET, PUT and DELETE on /api/v1/provisioning/alert-rules/:uid

Rule groups

GET, PUT and DELETE on /api/v1/provisioning/folder/:folderUid/rule-groups/:group

Contact points

GET and POST on /api/v1/provisioning/contact-points; PUT and DELETE on /api/v1/provisioning/contact-points/:uid

Notification policies

GET, PUT and DELETE on /api/v1/provisioning/policies (DELETE resets the tree to the default)

Template groups

GET on /api/v1/provisioning/templates; GET, PUT and DELETE on /api/v1/provisioning/templates/:name

Mute timings

GET and POST on /api/v1/provisioning/mute-timings; GET, PUT and DELETE on /api/v1/provisioning/mute-timings/:name

A recording rule uses the same alert rule endpoint with a record block (metric, from, target_datasource_uid) instead of condition, and for set to 0s. The X-Disable-Provenance: true header on PUT rule groups, POST alert rules, contact points and mute timings, PUT templates and PUT policies allows UI editing afterwards. PUT and DELETE of mute timings and template groups accept an optional version query parameter for optimistic concurrency.

The endpoints for contact points, notification policies, template groups and mute timings are deprecated and will be removed in a future release, and they do not return resources of a staged Alertmanager import. The documented replacements are the App Platform APIs, served under /apis with the namespace default for organization 1:

Resource Path under /apis/ (version v1beta1)

Alert rules and recording rules

rules.alerting.grafana.app/v1beta1/namespaces/{namespace}/alertrules and rules.alerting.grafana.app/v1beta1/namespaces/{namespace}/recordingrules

Contact points

notifications.alerting.grafana.app/v1beta1/namespaces/{namespace}/receivers

Notification policies

notifications.alerting.grafana.app/v1beta1/namespaces/{namespace}/routingtrees

Template groups

notifications.alerting.grafana.app/v1beta1/namespaces/{namespace}/templategroups

Mute timings

notifications.alerting.grafana.app/v1beta1/namespaces/{namespace}/timeintervals

 
# list the contact points through the notifications API (lab: basic authentication)
curl -s -u admin:admin \

Exporting existing resources

Starting from the UI is often faster than writing a model by hand: build the rule, then export it. From Alerts & IRM > Alerting, most resources export as YAML, JSON or Terraform (HCL), with copy or download.

  • Rules: Export rules for all Grafana-managed rules, the folder icon in the List view, or the rule group icon in the Grouped view. More > Modify export edits a rule for export without saving it, and exports the whole group. Export rule definition produces a new rule in HCL only.

  • Contact points: More > Export. Policies: Export on the default policy, or More actions > Export for a named tree. Mute timings: Export on the timing.

  • Template groups have no export; copy the name and content from the Notification templates tab.

The same is available over HTTP with the /api/v1/provisioning/.../export endpoints, whose format parameter (default yaml; also json and hcl) or Accept header selects the output, and download returns a file:

curl -s -u admin:admin 'http://localhost:3000/api/v1/provisioning/alert-rules/export?format=hcl'
curl -s -u admin:admin 'http://localhost:3000/api/v1/provisioning/folder/bookshelf/rule-groups/bookshelf-service-level/export?format=yaml'
curl -s -u admin:admin 'http://localhost:3000/api/v1/provisioning/contact-points/export?format=yaml'
curl -s -u admin:admin 'http://localhost:3000/api/v1/provisioning/mute-timings/export?format=yaml'

Contact point export accepts a decrypt parameter for secrets and policy export a routeName parameter for named trees; decrypted export needs the alert.provisioning.secrets:read permission. Exported output is for files and Terraform; it cannot be sent back to the provisioning API because the request format differs.

Source: Grafana: Export alerting resources and the HTTP API page above (export endpoints, format, decrypt, routeName).

What can go wrong

Symptom Cause and fix

The rule group fails to load: folder not found

The folder does not exist yet. Create it first (UI, API or grafana_folder) and reference it by the exact name.

After provisioning, a rule shows Error with "datasource not found"

The datasourceUid does not match the data source uid. Provision data sources with fixed uids (see Data Sources).

The notification policy tree was replaced and an old route vanished

The tree is a single resource; a second source (UI, another file or Terraform) overwrote or was overwritten. Keep exactly one owner.

The UI will not let you edit a rule, contact point or policy

It is provisioned. Edit the file or Terraform code, or recreate the resource with X-Disable-Provenance or disable_provenance = true.

A resource still exists after its file was removed

Files add and update only; add the matching delete... entry.

A mute timing is not applied

The name in mute_time_intervals or mute_timings does not match. The root policy cannot have mute timings.

A $ or a template disappeared from a contact point message

Environment interpolation consumed it; write $$ (annotations, queries and templates are not interpolated).

Terraform plan keeps showing a diff on model

The JSON differs from what Grafana stores. Use the exported JSON as the starting point.

Enforcement rejects a write

Alert Advisor is enforced and the rule lacks a required label or annotation (see Alerting HA and Operations).

Verify in the lab

  1. Save the YAML as provisioning/alerting/bookshelf.yaml in the lab Grafana volume, create the folder, and restart Grafana. Check the log for provisioning errors, then open Alerting > Alert rules: two groups with five rules in the folder bookshelf, each labelled Provisioned.

  2. Open a rule and try to edit it: the form is read-only. Open Contact points, Notification policies, Notification templates and Mute timings: all four carry the label.

  3. Check Notification policies: the default policy with team = bookshelf-sre and its two children, the one with severity = warning showing the bookshelf-weekends mute timing.

  4. Run the load generator in failing-request mode and watch Bookshelf high 5xx ratio go Pending then Alerting. The lab webhook receiver logs a payload whose title and message come from the bookshelf template group.

  5. Stop the Bookshelf container: Bookshelf no data goes to Alerting after the pending period, first because the up series drops to 0 and, once the series disappears from Prometheus, through the No Data handling.

  6. Export the rule group with the curl command above and compare it with the file; then apply the HCL in a clean lab with terraform apply (after removing the file) and compare again. The two exports should describe the same rules.

In the books

Chapter 10 of Observability with Grafana (Chapman and Holmes, Packt, 2023) shows grafana_rule_group with a rule block per alert and suggests a dynamic block to populate the rules from another source such as a JSON file, and it states that the Ansible collection of the time had not been updated for the new alerting. The Terraform resource is still the central one, but the book’s snippet is abbreviated and predates the attributes used here (keep_firing_for, missing_series_evals_to_resolve, notification_settings and named routing trees), the provenance behaviour and the deprecation of the older provisioning endpoints.
