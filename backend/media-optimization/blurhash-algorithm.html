BlurHash: The Algorithm

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Baseline date: 2026-10-07. This page follows the reference implementation in the woltapp/blurhash repository: its Algorithm.md and the reference TypeScript code. The numbers in the worked example were produced with the blurhash npm package (version 2.0.5) and cross-checked against a Python port. The cover examples further down were run with that package, blurhash-java 1.0.0, blurhash-python 1.2.2, blurhash 1.1.5 (the other Python package) and thumbhash 0.1.1.

A BlurHash is a short string, usually 20 to 30 characters, that describes a blurry version of an image. The backend stores it next to the image and returns it in the API response. The frontend decodes it to a few pixels in a few milliseconds, scales it up and shows it while the real image downloads, see BlurHash in the browser. Compared with a tiny JPEG or a solid colour, it is smaller than any image file, needs no extra request, and looks like the image.

The string is the image’s lowest few frequencies. It is a coarse DCT (discrete cosine transform), the same idea as JPEG but with a handful of components for the whole image instead of 8 by 8 blocks.

Pipeline

punch is a contrast knob. In the formula, values above 1 exaggerate the AC components (more contrast) and values below 1 soften them. The reference TypeScript decoder, however, sets punch = punch | 1. That bitwise OR first truncates the value to an integer and then sets its lowest bit, so 0.5 and 1.5 become 1, 2 becomes 3 and 4 becomes 5. With that decoder only odd integers (1, 3, 5, …​) take effect as given, and nothing below 1 is possible. A real hash, field by field

The running example is the Moby-Dick cover with id b81f, a 2400 by 3600 image. Its API record carries a BlurHash made from a 64 by 96 pixel reduction (exactly 2:3) with 3 columns and 4 rows of components. The reference TypeScript encoder returns TIAxG?R,4pm#f8WB01t6?aN2j[t6 for those pixels. The function below unpacks the string with nothing but the rules of the previous sections:

ALPHABET = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz#$%*+,-.:;=?@[]^_{|}~"

def b83(chars: str) -> int:
    value = 0
    for ch in chars:
        value = value * 83 + ALPHABET.index(ch)
    return value

def linear_to_srgb(v: float) -> int:
    v = max(0.0, min(1.0, v))
    return int((12.92 * v if v <= 0.0031308 else 1.055 * v ** (1 / 2.4) - 0.055) * 255 + 0.5)

def sign_pow(v: float, e: float) -> float:
    return abs(v) ** e * (1 if v >= 0 else -1)

def fields(blurhash: str) -> None:
    size = b83(blurhash[0])
    nx, ny = size % 9 + 1, size // 9 + 1
    assert len(blurhash) == 4 + 2 * nx * ny, "length does not match the size flag"
    maximum = (b83(blurhash[1]) + 1) / 166
    dc = b83(blurhash[2:6])
    print(f"size flag {size} -> {nx} x {ny} components, {len(blurhash)} characters")
    print(f"maximum AC value M = (q + 1) / 166 = {maximum:.4f}")
    print(f"DC = {dc} -> sRGB ({dc >> 16}, {(dc >> 8) & 255}, {dc & 255})")
    for index in range(1, nx * ny):
        value = b83(blurhash[4 + 2 * index: 6 + 2 * index])
        q = (value // 361, (value // 19) % 19, value % 19)
        ac = tuple(round(sign_pow((x - 9) / 9, 2) * maximum, 4) for x in q)
        i, j = index % nx, index // nx
        print(f"AC({i},{j}) = {blurhash[4 + 2 * index: 6 + 2 * index]!r:5} -> q {q} -> {ac}")

Reading it:

  • The first character T is 29 in the alphabet, so the grid is (29 mod 9) + 1 = 3 columns by (29 div 9) + 1 = 4 rows, and 4 + 2 * 12 = 28 characters, as the length check requires.

  • The DC colour (93, 120, 154) is the average of the cover, a muted blue: the sea gradient dominates the picture. This single value is what a client sees before anything else is decoded.

  • Component (0, 1) is a vertical variation (half a cosine period over the height), and its blue value 0.1145 is the maximum M: blue changes strongly between the top and the bottom of the cover. Components (2, 0) and (0, 2) are the strongest negative terms. The encoder took M from the largest signed value, the positive blue of (0, 1), so the larger negative red of (0, 2) could not be represented: it is at the lowest of the 19 levels (q = 0) and is stored as -M. The next section shows that its true size is about -0.1265.

  • The 11 two-character AC values use only 22 of the 28 characters. The other six are the size flag, the maximum and the four DC characters. That is the whole image.

Same pixels, different strings

The clipped (0, 2) component is not a bug in the hash, it is a consequence of how the maximum is chosen, and it is where implementations disagree. The same 64 by 96 pixels and the same 3 by 4 grid, encoded by four libraries:

The TypeScript and Java encoders agree character for character, and so do the two Python packages, but the two pairs differ in the maximum AC character (I is M = 0.1145, K is M = 0.1265). The first pair takes the largest signed AC value, so a strong negative component is quantised against a maximum that it exceeds and is clipped: the C-based encoders' M of 0.1265 is the size of the red channel of (0, 2), which the TypeScript encoder stored as -0.1145 (the same fields function applied to the second string shows (0, 2) as (-0.1265, -0.1, -0.0765), against (-0.1145, -0.1145, -0.0904) above). The second pair takes the largest absolute value, which leaves headroom for it. Decoded at 32 by 48 pixels, the two pictures differ by 4.6 on a 0 to 255 scale on average (largest difference 45 in one channel), and both are about as far from the cover itself (a mean error of 37.5 against a box-reduced 32 by 48 copy of the cover) as each other. Both strings are valid and every decoder reads either. What follows from it:

  • Never compare or deduplicate images by BlurHash string across services in different languages. Compare by decoding, or store the string with the implementation that wrote it.

  • Do not "fix" one side to match the other. The cost of clipping a component is below what the eye sees in a blurred placeholder.

  • Pick one encoder per platform and keep it for the lifetime of the stored strings, so a backfill produces strings that match the ones already stored.

Cost of encoding and decoding

Encoding costs time in proportion to the pixels, so encode from the reduction. In Node, the encoder took 2.3 ms for the 64 by 96 thumbnail with 3 by 4 components, and the Python wrapper took 2 ms for the same input, 300 ms for a 600 by 900 copy and 5.1 seconds for the 2400 by 3600 original, see the Python page. Decoding costs time in proportion to the output pixels times the number of components, so decode small and let the browser scale. The TypeScript decoder on the same string:

Choosing the grid

The grid should follow the aspect ratio, so the hash does not spend its few components on a direction that has no detail. A function that matches the rule used on the browser page:

def components_for(width: int, height: int, maximum: int = 4) -> tuple[int, int]:
    ratio = width / height
    if ratio >= 1:
        return maximum, max(1, min(maximum, round(maximum / ratio)))
    return max(1, min(maximum, round(maximum * ratio))), maximum

It returns (3, 4) for the 640 by 960 and the 2400 by 3600 cover (28 characters), (4, 2) for a 1920 by 1080 video cover (20 characters), (4, 4) for a square avatar (36 characters), and (4, 1) and (1, 4) for a 1200 by 300 banner and its transpose (12 characters each). Python’s round rounds halves to even and JavaScript’s Math.round rounds them up, so inputs whose product is exactly a half can differ between a Python backend and the JavaScript function. A bigger grid helps slowly: on the cover, a 1 by 1 hash had a mean error of 44.8, 3 by 4 had 37.3, 6 by 9 had 28.0 and 9 by 9 (166 characters) 27.9, see the table on the Python page.

Practical guidance

  • Components. 4 by 3 is the default and gives 28 characters. Adapt it to the aspect ratio: portrait covers do well with 3 by 4, banner images with 5 by 2. More components mean a longer string, a slower encode and a decode that looks closer to the image but costs more. Past 6 by 6 the benefit is small.

  • Encode from a downscaled image. The encoder is , so run it on a thumbnail of about 64 to 100 pixels wide, not on a 24-megapixel original. The result is practically the same.

  • Store and return the string. It is 20 to 30 characters. Keep it next to the image in the database and return it with the image in API JSON, see responsive images and thumbnails.

  • Decode small. Decode to about 20 to 32 pixels wide and let the UI scale it up with smooth interpolation (canvas CSS scaling or a blurred <img>). Never decode to the full image size.

  • Validate. A decoder should check that the length equals , as the reference does, before trusting user-supplied strings.

  • Cover images of videos. Run the same encode on the extracted frame, see video covers.

ThumbHash

ThumbHash by Evan Wallace is a similar placeholder format. It also encodes the alpha channel, keeps the aspect ratio of the image inside the hash, and stores colour in a different colour space (it uses a perceptual space and gives a slightly more detailed result in about 25 bytes). Its encoded form is binary, and is usually written as base64. Use it when you need transparency, or when the frontend library you use supports it, for example expo-image and unlazy. Use BlurHash when you need the widest set of implementations. Measured on the cover (a 43 by 64 reduction, because ThumbHash takes at most 100 by 100 pixels), thumbhash 0.1.1 produced 21 bytes, which is the 28 characters 2aUFNQQnh3Z3F7hoiH+EF2eAdvRo in base64: the same text length as the 3 by 4 BlurHash of the same pixels (TJAe8iWF4:iXa#WB02t6?aN2j[t6, also 28 characters), and a base64 string can be stored in a bytea column at 21 bytes. It decoded to a 23 by 32 image, because the aspect ratio is recovered from the hash (approximately, 0.714 for a true 0.672 here) rather than being carried by the client, and that is the practical advantage: a client needs no extra width and height to size the placeholder.
