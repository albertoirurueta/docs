Migrating & What’s Changed

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Express 5.3.0 (published 2026-10-09) and Express 4.22.3 (2026-09-14, the newest 4.x), running on Node.js 24 LTS, and the facts were checked on 2026-10-29. Express 5 requires Node.js 18 or newer; Express 4 still runs on very old Node.js releases, which is one reason many projects have not moved. npm install express has installed Express 5 since 5.1.0 on 2025-03-31, so a project that was created before that date and is installed again without a lock file can already be on the new line without anyone deciding to migrate.

The page has five jobs. It lists every Express 5 breaking change from the official migration guide, each with a before and after example and the codemod that rewrites it, when one exists. It describes how to run the codemods and gives a checklist for the upgrade, in the order that keeps the application working at every step. It reminds you of the Express 3 to 4 changes that still show up in old code. It lists the deprecated middleware. And it collects, in one place, every statement from the four reference books of this section that no longer holds, with the version that changed it and a link to the page that treats the topic in depth.

The running example is the Bookshelf API used throughout the section: a small catalogue of books and reviews. The sibling pages are Versions, Support & LTS (which Express line to run and for how long), Route Paths & Parameters (the new path syntax in depth) and Security Best Practices.

How big is the migration

Express 5 is mostly a cleanup of the 4.x API, not a new framework. The changes fall in four groups:

  • Methods and properties that were deprecated for years and are now gone. Calling them throws a TypeError or silently does something different.

  • A new routing engine. The router moved to router 2 and path-to-regexp 8, which changed the spelling of wildcards, optional segments and regular expressions in route strings, and the shape of req.params.

  • Changed defaults and changed return values: req.body, req.query, req.host, express.urlencoded, express.static, res.clearCookie, res.status, res.vary and app.listen.

  • Improvements that need no migration: rejected promises reach the error handlers, res.render() is always asynchronous, and request bodies compressed with Brotli are decompressed.

The two changes that cause most of the real-world breakage are the path syntax (any catch-all such as app.get('*', ...) stops the application at start-up) and req.body being undefined when no parser ran. Both fail loudly and early in a test run, which is why the checklist later in the page puts a test run before every change.

The Express 5 breaking changes

The sections below follow the order of the official migration guide: removed methods and properties first, then changed behaviour, then the improvements. Each example is a before and after pair. Where a codemod covers the change, its name is given; the codemods are collected in Codemods.

Removed methods and properties

These calls fail on Express 5. A test that exercises the route finds them immediately.

app.del() is app.delete()

app.del() was a deprecated alias that existed because delete was a reserved word in very old JavaScript. Use app.delete(). Codemod: route-del-to-delete.

// Express 4
app.del('/books/:id', removeBook);

// Express 5
app.delete('/books/:id', removeBook);

Source: Migrating to Express 5, "app.del()".

app.param(fn) and router.param(fn)

The form of app.param() and router.param() that took only a function, to customise how parameter callbacks are registered, was deprecated since 4.11.0 and is removed. The form with a name and a function still works. Separately, a leading colon in the name (app.param(':id', fn)) is silently ignored in Express 5, so pass the plain name.

// Express 4: global customisation, removed
app.param((name, fn) => fn);

// Express 4 and 5: name and function
app.param('bookId', async (req, res, next, id) => {
  req.book = await books.find(id);
  next();
});

Source: Migrating to Express 5, "app.param(fn)".

The singular req.accepts methods

req.acceptsCharset(), req.acceptsEncoding() and req.acceptsLanguage() are removed in favour of the plural names, which have the same meaning. Codemod: pluralize-method-names.

// Express 4
req.acceptsCharset('utf-8');
req.acceptsEncoding('br');
req.acceptsLanguage('en');

// Express 5
req.acceptsCharsets('utf-8');
req.acceptsEncodings('br');
req.acceptsLanguages('en');

Source: Migrating to Express 5, "Pluralized method names".

req.param()

req.param(name) searched the route parameters, then the body, then the query string, which made it an injection-friendly lookup. It is removed: read the source you mean. Codemod: explicit-request-params.

// Express 4
const id = req.param('id');
const body = req.param('body');
const query = req.param('query');

// Express 5
const id = req.params.id;
const body = req.body;
const query = req.query;

Source: Migrating to Express 5, "req.param(name)".

Status-first call signatures

res.json(obj, status), res.jsonp(obj, status) and res.send(body, status) are removed; chain res.status() first. res.send(status) is removed too: use res.sendStatus(status), and quote a number if you really want a numeric body. Codemod: status-send-order.

// Express 4
res.json({ title: 'Dune' }, 201);
res.jsonp({ title: 'Dune' }, 201);
res.send({ title: 'Dune' }, 200);
res.send(404);

// Express 5
res.status(201).json({ title: 'Dune' });
res.status(201).jsonp({ title: 'Dune' });
res.status(200).send({ title: 'Dune' });
res.sendStatus(404);

Source: Migrating to Express 5, "res.json(obj, status)" and the related entries.

A related trap: in Express 5, res.send(404) no longer sets a status. A number passed to res.send() is sent as a JSON body, so a leftover call produces a 200 response whose body is 404. Search for it explicitly.

res.redirect arguments and the back keyword

res.redirect(url, status) is removed; the status comes first. res.redirect('back') and res.location('back') are removed because the keyword trusted a client-controlled Referer header; redirect to an explicit URL and validate it. A redirect that relies on the default 302 is not affected. Codemods: redirect-arg-order and back-redirect-deprecated.

// Express 4
res.redirect('/books', 302);
res.redirect('back');

// Express 5
res.redirect(302, '/books');
res.redirect(req.get('Referrer') || '/');

Source: Migrating to Express 5, "res.redirect".

The Referrer fallback above mirrors the official example, but a redirect to a header value is an open redirect if the value comes from another site. Where it matters, compare the header to an allow-list of your own paths before using it.

res.sendfile() and the sendFile options

res.sendfile() (lower case) is removed; use res.sendFile(). The hidden and from options of res.sendFile() are removed in favour of dotfiles and root, and the dotfile check now also applies to hidden directories anywhere in the resolved path, so a file under /var/www/app/.cache/ returns 404 unless you opt in. Codemods: camelcase-sendfile and sendfile-options.

// Express 4
res.sendfile('/path/to/cover.png');
res.sendFile(req.params.name, { hidden: true, from: '/uploads' });

// Express 5
res.sendFile('/path/to/cover.png');
res.sendFile(req.params.name, { dotfiles: 'allow', root: '/uploads' });

Source: Migrating to Express 5, "res.sendFile".

express.static options and express.static.mime

The hidden and from options of express.static() are removed (from was an undocumented alias of root). The express.static.mime object is removed; use the mime-types package when you need a lookup. Codemods: static-dotfiles and static-mime.

// Express 4
app.use(express.static('public', { hidden: true }));
const type = express.static.mime.lookup('json');

// Express 5
import mime from 'mime-types';
app.use(express.static('public', { dotfiles: 'allow' }));
const type = mime.lookup('json');

Source: Migrating to Express 5, "express.static".

MIME types and debug namespaces

Two changes need no code change but can surprise a deployment. The MIME database moved on from mime-db 1.52.0, so express.static() and res.sendFile() serve some extensions with a different Content-Type; the most visible is .js, now text/javascript instead of application/javascript. The migration guide does not count this as breaking, so pin dependencies and test any client or proxy that matches on the old value.

The router’s debug namespaces were renamed because the router is now a separate module, so a DEBUG value from a runbook silently prints less.

Express 4 Express 5

express:router

router

express:router:layer

router:layer

express:router:route

router:route

express:* (includes the router)

express:*,router,router:*

 
# Express 4
DEBUG=express:* node index.js

# Express 5
DEBUG=express:*,router,router:* node index.js

Source: Migrating to Express 5, "MIME type changes" and "Router debug log namespaces". See also Debugging & Logging and Serving Static Files.

Changed behaviour

These do not throw, so a test suite that never checks the affected behaviour passes. Read each one against your code.

Path matching with path-to-regexp 8

Route strings in app.all(), app.use(), app.METHOD() and the matching router methods are parsed by path-to-regexp 8 (through router 2). The rules that changed:

  • Wildcards must be named: /* becomes /*splat. A named wildcard does not match the root path /; use /{*splat} when it must.

  • The ? suffix is gone; optional segments use braces.

  • Regular expression syntax inside a string path is not supported; use several paths in an array, or a real RegExp object.

  • The characters ()[]?+! are reserved and must be escaped with a backslash.

  • Parameter names must be valid JavaScript identifiers, or quoted like :"this".

// Express 4
app.get('/*', notFoundPage);
app.get('/:file.:ext?', download);
app.get('/[discussion|page]/:slug', render);

// Express 5
app.get('/*splat', notFoundPage);          // not the root
app.get('/{*splat}', notFoundPage);        // including the root
app.get('/:file{.:ext}', download);
app.get(['/discussion/:slug', '/page/:slug'], render);

Source: Migrating to Express 5, "Path route matching syntax". The full grammar, escaping rules and a decision chart are in Route Paths & Parameters; the verbs and routers are in Routing and Routers & Modular Apps.

There is no codemod for the path syntax, so it needs a manual search. The patterns to grep for are '*', /*, a ? after a parameter, a parenthesis after a parameter name, and any bracket in a string path.

Rejected promises reach the error handlers

In Express 5 a middleware or handler that returns a rejected promise, or an async function that throws, calls next(err) for you. The try/catch that existed only to forward the error can go, and so can the packages that patched Express 4 to do the same.

// Express 4
app.get('/books/:id', (req, res, next) => {
  getBook(req.params.id)
    .then((book) => res.send(book))
    .catch(next);
});

// Express 5
app.get('/books/:id', async (req, res) => {
  const book = await getBook(req.params.id);
  res.send(book);
});

Source: Migrating to Express 5, "Rejected promises handled from middleware and handlers". The consequences for error handlers are in Error Handling and Middleware Fundamentals.

express.urlencoded extended defaults to false

express.urlencoded() now parses with the querystring library unless you ask for extended: true. A form whose field names use brackets (user[name]) stops producing nested objects.

// Express 4 default behaviour is now opt-in
app.use(express.urlencoded({ extended: true }));

Source: Migrating to Express 5, "express.urlencoded". See Body Parsing.

express.static ignores dotfiles by default

The default for dotfiles is now "ignore", and the check covers hidden directories, so /.well-known/ is a 404. Serve it from its own mount with dotfiles: 'allow'.

app.use('/.well-known', express.static('public/.well-known', { dotfiles: 'allow' }));
app.use(express.static('public'));

Source: Migrating to Express 5, "express.static dotfiles".

router.param() rejects arrays

router.param(name, fn) throws a TypeError when name is not a string. app.param() still accepts an array.

// Express 4
router.param(['id', 'page'], loadParam);

// Express 5
router.param('id', loadParam);
router.param('page', loadParam);

Source: Migrating to Express 5, "router.param(name, fn)".

app.listen passes errors to its callback

A failure to listen (for example EADDRINUSE) used to be an unhandled error event on the server. In Express 5 the callback receives it as an argument.

const server = app.listen(3000, '0.0.0.0', (error) => {
  if (error) {
    throw error;
  }
  console.log(`Listening on ${JSON.stringify(server.address())}`);
});

Source: Migrating to Express 5, "app.listen". See Getting Started and Health Checks & Graceful Shutdown.

app.router is back

app.router existed in Express 3, was removed in 4, and returns in 5 as a plain reference to the application’s base router. There is still no reason to call app.use(app.router).

// Express 4
app.router; // throws Error: 'app.router' is deprecated!

// Express 5
console.log(app.router.stack.length); // the base router, created on first access

Source: Migrating to Express 5, "app.router".

req.body is undefined without a parser

Express 4 returned {} for a request that no body parser had touched. Express 5 returns undefined, so destructuring it throws.

// Express 4: {}   Express 5: undefined
console.dir(req.body);

// defensive form
const { title, isbn } = req.body ?? {};

Source: Migrating to Express 5, "req.body". See Request and Validation & Input Handling.

req.host keeps the port

Express 4 stripped the port from req.host. Express 5 returns the value of the Host header including the port. Use req.hostname when you need the host name alone, and build absolute links from configuration rather than from a header.

// GET / with Host: books.example.com:3000
// Express 4: req.host === 'books.example.com'
// Express 5: req.host === 'books.example.com:3000'
const name = req.hostname; // 'books.example.com' in both

Source: Migrating to Express 5, "req.host".

req.params has a null prototype, array wildcards and omitted parameters

For a string path, req.params is an object with a null prototype (a regular expression path still gets a normal object), so req.params.hasOwnProperty(...) fails; use Object.hasOwn(). A wildcard produces an array of path segments, not one string. A parameter that did not match is omitted instead of being '' or undefined.

app.get('/*splat', (req, res) => {
  // GET /library/fiction
  // Express 4 with '/*':   { '0': 'library/fiction' }
  // Express 5 with '/*splat': [Object: null prototype] { splat: [ 'library', 'fiction' ] }
  res.json(req.params.splat);
});

Source: Migrating to Express 5, "req.params".

req.query is a getter and uses the simple parser

req.query is no longer a writable property, so req.query.page = 1 has no effect. The default query parser setting changed from extended to simple, so ?filter[genre]=fiction is a flat key, not a nested object. Opt in with app.set('query parser', 'extended') only when you need nesting, and validate what you receive: nested objects are how operator injection reaches a database.

app.set('query parser', 'extended'); // opt back in, then validate the result
app.get('/search', (req, res) => {
  const page = Number(req.query.page ?? 1); // read, never assign
  res.json({ page });
});

Source: Migrating to Express 5, "req.query". See Application & Settings.

res.clearCookie ignores maxAge and expires

res.clearCookie(name, options) no longer honours maxAge and expires; the cookie is cleared with an expiry in the past. Pass the same path, domain, secure and sameSite as when you set it.

// Express 4
res.clearCookie('session', { maxAge: 0, expires: new Date(0) });

// Express 5
res.clearCookie('session');

Source: Migrating to Express 5, "res.clearCookie". See Cookies & Sessions.

res.status accepts only 100 to 999

res.status() throws for anything that is not an integer between 100 and 999. A computed status that can be NaN, a string or 0 now fails at the call.

// Express 4: accepted, with a deprecation warning for the string
res.status('404').send('Not found');

// Express 5
res.status('404');                 // throws TypeError: not an integer
res.status(1000);                  // throws RangeError: outside 100 to 999
res.status(404).send('Not found'); // correct

Source: Migrating to Express 5, "res.status".

res.vary needs a field

res.vary() with no argument only logged a warning in Express 4. It now throws.

res.vary();         // throws in Express 5
res.vary('Accept'); // correct

Source: Migrating to Express 5, "res.vary". See Response and Content Negotiation & HTTP Caching.

Improvements that need no migration

  • res.render() is always asynchronous, whatever the view engine does. Code that assumed a synchronous render for a particular engine must use the callback or the following middleware. See Template Engines & Views.

  • express.json(), express.urlencoded(), express.text() and express.raw() decompress Content-Encoding: br request bodies, in addition to gzip and deflate.

A worked migration of the Bookshelf API

The two files below are the same small service. The first is how the books teach it: Express 4, CommonJS, the separate body-parser package, status-first calls and a catch-all. The second is the Express 5 version.

// app.js, Express 4 style
const express = require('express');
const bodyParser = require('body-parser');

const books = new Map();
const app = express();

app.use(bodyParser.json());

app.get('/books/:id?', (req, res) => {
  const id = req.param('id');
  if (!id) return res.json([...books.values()]);
  const book = books.get(id);
  if (!book) return res.send(404);
  res.json(book);
});

app.post('/books', (req, res) => {
  const book = { id: String(books.size + 1), ...req.body };
  books.set(book.id, book);
  res.json(book, 201);
});

app.del('/books/:id', (req, res) => {
  books.delete(req.params.id);
  res.send(204);
});

app.get('*', (req, res) => {
  res.send({ error: 'Not found' }, 404);
});

app.listen(3000);
// app.js, Express 5
import express from 'express';

const books = new Map();
export const app = express();

app.use(express.json());

app.get('/books{/:id}', (req, res) => {
  const { id } = req.params;
  if (id === undefined) {
    return res.json([...books.values()]);
  }
  const book = books.get(id);
  if (!book) {
    return res.sendStatus(404);
  }
  res.json(book);
});

app.post('/books', (req, res) => {
  const book = { id: String(books.size + 1), ...(req.body ?? {}) };
  books.set(book.id, book);
  res.status(201).json(book);
});

app.delete('/books/:id', (req, res) => {
  books.delete(req.params.id);
  res.sendStatus(204);
});

app.use((req, res) => {
  res.status(404).json({ error: 'Not found' });
});

if (import.meta.url === `file://${process.argv[1]}`) {
  app.listen(3000, (error) => {
    if (error) throw error;
    console.log('Bookshelf listening on http://localhost:3000');
  });
}

Source: derived from Migrating to Express 5 and Routing. The path-less app.use() at the end replaces the catch-all, books{/:id} replaces the optional parameter, req.params.id replaces req.param(), and the export lets a test import the app without opening a port (see Testing).

Codemods

The Express team publishes codemods for the mechanical part of the migration. They run through the Codemod tool and rewrite source files in place, so run them on a clean working tree and review the diff.

The full recipe is a single command; the yarn, pnpm and bun equivalents are yarn dlx, pnpm dlx and bunx.

npx codemod@latest @expressjs/v5-migration-recipe

Each change can also be applied alone:

npx codemod@latest @expressjs/route-del-to-delete

The recipes listed in the official migration guide, checked on 2026-10-29, are these:

Codemod What it rewrites

@expressjs/route-del-to-delete

app.del() to app.delete().

@expressjs/pluralize-method-names

req.acceptsCharset, req.acceptsEncoding and req.acceptsLanguage to the plural names.

@expressjs/explicit-request-params

req.param() to req.params, req.body or req.query.

@expressjs/status-send-order

res.json, res.jsonp and res.send calls that pass a status as an argument to a chained res.status().

@expressjs/redirect-arg-order

res.redirect(url, status) to res.redirect(status, url).

@expressjs/back-redirect-deprecated

res.redirect('back') (and the equivalent res.location) to an explicit Referrer fallback.

@expressjs/camelcase-sendfile

res.sendfile() to res.sendFile().

@expressjs/sendfile-options

The hidden and from options of res.sendFile() to dotfiles and root.

@expressjs/static-dotfiles

The hidden and from options of express.static().

@expressjs/static-mime

express.static.mime to the mime-types package.

The guide lists no recipe for the path syntax, req.query, req.host, req.params, res.clearCookie, res.status, res.vary, router.param() arrays, the app.listen callback or the urlencoded default. Those are manual edits, and the checklist below covers them. The Express project keeps the up-to-date list of recipes at codemod.link/express; re-read it before a migration, because recipes are added and renamed.

Source: Migrating to Express 5, "Codemods"; expressjs/codemod.

Express 4 to 5 upgrade checklist

Do the steps in order and keep the tests green after each one. A migration that mixes the upgrade with feature work is hard to bisect.

flowchart TD A["Green tests on Express 4"] --> B["Upgrade Node.js to 18 or newer"] B --> C["Run the codemods on a clean tree"] C --> D["Install express@5 and the 5.x middleware"] D --> E["Fix paths, req.body, req.query, req.params"] E --> F["Fix the status, redirect and sendFile leftovers"] F --> G["Update tests and error handlers"] G --> H["Deploy behind a flag or to staging"]

  1. Make the test suite pass on the current Express 4 version, and add tests for the routes that use wildcards, optional parameters, req.query filters and static files. Most of the changes fail only where the code runs.

  2. Move to Node.js 18 or newer. The recommended target is the current LTS (24 at the time of writing); see Versions, Support & LTS.

  3. Upgrade to the newest 4.x first (express@4) and fix the deprecation warnings it prints. Most removals were deprecated in 4.x for years.

  4. Commit, then run npx codemod@latest @expressjs/v5-migration-recipe and review the diff.

  5. Install Express 5 and its companion types: npm install express@5 and, for TypeScript, npm install --save-dev @types/express@5. Update the sibling packages that pin Express 4 (for example the Apollo integration moves to @as-integrations/express5, and middleware that lists express as a peer dependency).

  6. Search for the path patterns that crash at start-up: '*', /*, a parameter followed by ?, a parenthesis or bracket in a string route. Rewrite them with /*splat, /{*splat} and brace groups, or with an array of paths.

  7. Check every place that reads req.body (guard against undefined), req.query (the simple parser, no assignment), req.params (arrays for wildcards, null prototype) and req.host.

  8. Search for leftovers the codemods cannot see: res.send( with a number, app.param(fn), router.param([, res.clearCookie( with maxAge, res.status( with a computed value and res.vary().

  9. Review express.static() and res.sendFile() for dotfiles (/.well-known) and for clients that match on the old .js content type.

  10. Register a JSON error handler last, remove try/catch and shims that only existed to forward async errors, and handle the error argument of the app.listen callback.

  11. Update the DEBUG value in runbooks to include router and router:*.

  12. Update the tests, run them with NODE_ENV=production, and deploy to a staging environment before production. Keep the lock file committed so the rollback to Express 4 is a revert.

Source: Migrating to Express 5; Error handling.
