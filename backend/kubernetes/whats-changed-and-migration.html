What’s Changed and Migration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Kubernetes ships about three minor releases a year and supports each for about 14 months. Older books and tutorials (including the two O’Reilly books this section was cross-checked against) describe a Kubernetes that no longer exists: they use removed API versions, removed kubectl behaviour and architecture that has since been replaced. This page is the consolidated list of what changed, written against Kubernetes 1.37 ("Garhwal", released 2026-08-26, latest patch 1.37.1). Every version and date below was re-checked on 2026-09-30 against the kubernetes.io release pages, the release notes and blogs, and the kubernetes/website and kubernetes/kubernetes repositories. The currently supported minors are 1.37, 1.36 and 1.35, with 1.34 in maintenance mode until its end of life on 2026-10-27, and 1.38 is scheduled for 2026-12-16. Re-verify anything that matters before relying on it: the topic pages linked from each row give the current details, and the section landing page gives the reading path.

Removals and deprecations worth knowing

  • Dockershim (removed in 1.24, 2022-05-03). The kubelet no longer speaks to Docker Engine directly. Images built with Docker are OCI images and run unchanged on containerd or CRI-O; only tools that mounted the Docker socket, or nodes that used docker commands to inspect containers, need to change to crictl. See Cluster Setup and Administration.

  • PodSecurityPolicy (removed in 1.25, 2022-08-23). Replaced by Pod Security Admission with the Pod Security Standards, or by ValidatingAdmissionPolicy and policy engines. See Pod Security and Admission Control and Policy.

  • Ingress-NGINX (best-effort maintenance ended March 2026). No further releases, bugfixes or security updates; existing installs keep running. The Ingress API is frozen, not removed. Migrate to Gateway API, for example with the ingress2gateway tool. See Ingress.

  • Endpoints API (deprecated in 1.33, 2025-04-23). The v1 Endpoints API still works and will not be removed, but new code should read EndpointSlices.

  • Service externalIPs (marked deprecated in the Service documentation at 1.36, 2026-04-22). The field has been discouraged since 1.21 because of CVE-2020-8554; use a load balancer or Gateway API instead, and consider the DenyServiceExternalIPs admission controller. The 1.36 announcement describes a planned removal, but the 1.37 changelog contains no removal, so the field still exists on 1.37.

  • cgroup v1 (maintenance mode in 1.31, deprecated in 1.35). The kubelet sets failCgroupV1 to true by default from 1.35, so nodes refuse to start on cgroup v1 unless it is set to false. Move nodes to cgroup v2.

  • kube-proxy IPVS mode (deprecated in 1.35, 2025-12-17). Migrate to nftables (GA in 1.33); iptables is still the default on Linux, and kube-proxy warns when no mode is set explicitly.

  • Legacy package repositories (apt.kubernetes.io and yum.kubernetes.io, frozen on 2023-09-13). Use the community pkgs.k8s.io repositories, which are versioned per minor release.

  • kubectl run generators (removed in 1.18, 2020-03-25). kubectl run creates a Pod; the ignored --filename flag was deprecated in 1.37.

Source: Kubernetes Blog — Ingress NGINX Retirement

Finding deprecated APIs

In a running cluster

The API server counts every request to a deprecated API in a metric, which is the authoritative view of what clients are doing right now:

kubectl get --raw /metrics | grep apiserver_requested_deprecated_apis
apiserver_requested_deprecated_apis{group="policy",removed_release="1.25",resource="podsecuritypolicies",subresource="",version="v1beta1"} 1

Source: Kubernetes Docs — Locate use of deprecated APIs

The metric names the removed_release, so sort on it before an upgrade. To learn which client sent the request, turn on audit logging, where each event carries an k8s.io/deprecated annotation. Third-party tools fill the rest of the picture: kubent scans the live cluster, and pluto scans manifests and Helm releases:

kubent
pluto detect-helm -o wide

In manifests

Scan Git before the cluster does: pluto detect-files -d k8s/, kubectl apply --dry-run=server -f (the server reports warnings about deprecated versions to the client) and kubectl convert rewrite old manifests. The API server also returns a Warning: header on any call to a deprecated API, which kubectl prints. In CI, validate against the target version’s schema with a tool such as kubeconform. Upgrade one minor release at a time and read the release notes first; see Cluster Setup and Administration for the upgrade sequence.
