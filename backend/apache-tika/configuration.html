Configuration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Baseline date: 2026-10-12. This page was written against Apache Tika 4.1.0 (the latest release on Maven Central on that date) with the 3.3.x differences noted, Java 21 and later for the examples (Tika 4.x needs Java 17, 3.x needs Java 11), Spring Boot 4.x on Spring Framework 7 and the Docker image apache/tika:4.1.0-1. Tika 4.x is configured with one JSON file, usually called tika-config.json, read by TikaLoader from the tika-serialization module. The same file configures the library, tika-app, tika-server, tika-grpc and Tika Pipes: which parsers and detectors run, their options, the limits in the ParseContext, the metadata filters, the output format, and, for the services, the server and the pipeline. The 3.x tika-config.xml and the TikaConfig class are gone.

This page covers the file itself: every top-level section, how components are named, the parsers list and default-parser, the TikaLoader API, where a typo is rejected and where it is silently ignored, secrets from environment variables, Windows paths, extra jars, the @TikaComponent model behind all of it, and the migration from 3.x. The per-component options are on their own pages: PDF Parsing for pdf-parser and the pages block, OCR with Tesseract for tesseract-ocr-parser and text-recognizers, VLM Parsers & Inference for engines and inference, and Extending Tika for writing your own parser or detector. The ParseContext mechanics are in Parser API & AutoDetectParser, the metadata keys that the filters work on are in Metadata, the output formats are in Content Handlers & Output Formats and the detectors are in Media Types & Detection.

The examples were compiled and run against Tika 4.1.0 (tika-core, tika-parsers-standard-package as a pom dependency, tika-serialization, and tika-app on the classpath for the CLI runs). Why a configuration file

Without a file, Tika discovers everything through the Java ServiceLoader: every parser, detector and encoding detector on the classpath, with default options and no limits beyond the defaults. That is fine for a first program. A real intake service needs to decide:

  • which formats it accepts, and which parsers it never wants to run (an executable parser for an upload form, say);

  • parser options (PDF text ordering, OCR language, timeouts);

  • limits: how much text, how deep the embedded documents go, how long a parse may take;

  • which metadata fields leave the parse, and under which names;

  • the output format of the extracted content;

  • for tika-server and Pipes, the forked JVMs, the fetchers and emitters, and which risky features are switched on.

In 4.x all of that lives in one JSON object. Two properties set it apart from the 3.x XML:

  1. It is an allow-list. Components are referenced by a registered component name (pdf-parser), never by a Java class name, so a configuration file cannot make Tika instantiate an arbitrary class.

  2. It is strict. An unknown top-level key, an unknown option in a component’s body or an unregistered component name fails at load time with a message that names the valid choices. There are four documented exceptions, listed under Strict validation: where a typo is caught.

The startup file is trusted: it is written by the operator. Per-request configuration that arrives over the wire (a tika-server request body, a Pipes FetchEmitTuple) uses the same JSON shapes but is read in a restricted mode, never reads environment variables and is off by default in tika-server. That distinction matters for every security decision on this page.

Source: Apache Tika 4.1.x, Configuration and Apache Tika 4.1.x, Serialization and Configuration.

From the file to the components

flowchart LR F["tika-config.json (comments allowed)"] --> J["TikaJsonConfig.load"] J --> I["resolve env references in string values"] I --> V["check top-level keys against the known set"] V --> L["TikaLoader"] L --> P["loadParsers / loadAutoDetectParser"] L --> D["loadDetectors"] L --> E["loadEncodingDetectors"] L --> M["loadMetadataFilters"] L --> H["loadContentHandlerFactory"] L --> C["loadParseContext"] P --> R["ComponentRegistry: name to class from META-INF/tika/*.idx"] D --> R M --> R C --> R P --> A["AutoDetectParser (shared, thread-safe)"] D --> A C --> X["ParseContext (one per parse)"] A --> Z["parse(tis, handler, metadata, context)"] X --> Z H --> Z

What happens, in order, verified in the 4.1.0 sources:

  1. TikaLoader.load(path) calls TikaJsonConfig.load, which parses the file with Jackson. // and /* */ comments are accepted (the Bookshelf file below has one).

  2. Still inside TikaJsonConfig.load, EnvInterpolator walks every string value and replaces each ${env:NAME} reference. An unset variable fails the load.

  3. validateKeys() compares every top-level key with a fixed set of 24 names. Anything else fails the load.

  4. The loader then checks that java.io.tmpdir exists and is writable (it fails early, naming the directory, rather than on the first spool) and reads the three global sections (metadata-list, service-loader, xml-reader-utils).

  5. Nothing else is built yet. Each load... method builds its component type on first call, resolving each name through the component registry (the META-INF/tika/*.idx files written by the @TikaComponent annotation processor), and caches the result: a second loadParsers() returns the same object.

  6. loadParseContext() is the exception to the caching: it builds a new ParseContext from the parse-context section on every call, which is what you want, because a context belongs to one parse.

Source: the 4.1.0 sources of TikaJsonConfig, EnvInterpolator and TikaLoader.

A tika-config.json is a single JSON object. Every section is optional, and an omitted section uses its defaults. The table lists every key that the 4.1.0 loader accepts: this is the KNOWN_KEYS set in TikaJsonConfig, and the same list appears in the error message for an unknown key. Array sections and object sections

The array sections (parsers, detectors, encoding-detectors, metadata-filters, renderers, text-recognizers) are ordered lists. Each element is either a string or an object with one key:

{
  "detectors": [
    "poifs-container-detector",
    { "default-detector": { "exclude": ["misc-ole-detector"] } }
  ],
  "metadata-filters": [
    { "include-field-metadata-filter": { "include": ["tk:content", "Content-Type", "dc:title"] } },
    "date-normalizing-metadata-filter"
  ]
}

The string form creates the component with its defaults; the object form passes the body as its configuration. Object sections (parse-context, content-handler-factory, fetchers, engines, …​) key each entry by name instead, with the configuration object as the value. In fetchers, emitters and engines there is one more level: the outer key is your instance id (covers, es), the inner key is the component name.

{
  "fetchers": {
    "inbox": { "file-system-fetcher": { "basePath": "/srv/bookshelf/inbox" } }
  },
  "parse-context": {
    "commons-digester-factory": { "digests": [ { "algorithm": "SHA256" } ] }
  }
}

Source: Apache Tika 4.1.x, Serialization and Configuration, JSON configuration format and Apache Tika 4.1.x, Pipes Configuration.

Component names

Everything in the file is referenced by its component name: a kebab-case identifier such as pdf-parser, default-detector, output-limits or file-system-fetcher. The @TikaComponent annotation processor derives it from the class’s simple name (PDFParser becomes pdf-parser, ShelfCodeFilter becomes shelf-code-filter) unless the class declares its own name, and writes it into an index file such as META-INF/tika/parsers.idx. The loader looks names up in those index files. A class name is not accepted in its place: the failure message ends with "Arbitrary class names are not allowed for security reasons".

To list the names on your classpath, use tika-app:

java -jar tika-app-4.1.0.jar --list-parser-names
java -jar tika-app-4.1.0.jar --list-detector-names

Output (first lines of the parser list, tab-separated class and name):

org.apache.tika.parser.apple.AppleSingleFileParser	apple-single-file-parser
org.apache.tika.parser.apple.PListParser	p-list-parser
org.apache.tika.parser.asm.ClassParser	class-parser
org.apache.tika.parser.audio.AudioParser	audio-parser
org.apache.tika.parser.audio.MidiParser	midi-parser

With tika-parsers-standard-package 4.1.0 the parser list had 88 lines and the detector list 8. The derived names are not always the obvious ones (p-list-parser, bp-list-detector, poifs-container-detector), so copy them from this output instead of guessing. An unknown name also fails the load with the list of the registered ones, which is the other way to find a name. Names of components outside the parser and detector lists (parse-context entries, metadata filters, digesters) are in the .idx files inside each jar; for tika-core 4.1.0 the parse-context names are embedded-limits, exception-reporting, output-limits, timeout-limits, skip-embedded-document-selector, spooling-strategy, standard-metadata-limiter-factory, auto-detect-parser-config, simple-password-provider, text-recognizers, inference, media, pages, basic-content-handler-factory and sax-output-config.

Source: Apache Tika 4.1.x, Configuration, component names, Apache Tika 4.1.x, tika-app CLI and the META-INF/tika/parse-context.idx file of the tika-core 4.1.0 jar.

The parsers list and default-parser

A parsers list loads only the parsers it names. To change one parser and keep all the others, add a default-parser entry. Configuring a parser automatically excludes its default copy, so a configured pdf-parser next to default-parser does not run twice.

{
  "parsers": [
    { "pdf-parser": { "sortByPosition": true } },
    { "default-parser": { "exclude": ["executable-parser"] } }
  ]
}

exclude on default-parser takes component names and is only needed to disable a parser without replacing it. The Bookshelf upload form never accepts programs, so executable-parser is excluded.

To see what "only the parsers it names" means, the next run loads a file with just pdf-parser and parses both sample files. tk:parsed-by shows which parser ran.

{ "parsers": [ { "pdf-parser": { "sortByPosition": true } } ] }
files/catalogue.pdf -> application/pdf parsedBy=org.apache.tika.parser.CompositeParser,org.apache.tika.parser.pdf.PDFParser chars=68
files/manuscript.docx -> application/vnd.openxmlformats-officedocument.wordprocessingml.document parsedBy=org.apache.tika.parser.EmptyParser chars=0

The manuscript is still detected as a Word document (detection is a separate section), but no parser handles it, so EmptyParser returns no text and no error. Leaving out default-parser by accident is a silent loss of every other format; keep it unless you really want a Tika limited to the listed parsers.

detectors works the same way with a default-detector entry. encoding-detectors has a default-encoding-detector, but it must not be mixed with explicit encoding-detector entries. See Character Encoding Detection.

Source: Apache Tika 4.1.x, Configuration, the parsers list and default-parser and Apache Tika 4.1.x, Encoding Detectors.

MIME filtering with _mime-include and _mime-exclude

Any parser entry can be restricted to some media types, or kept away from some, with two framework directives. The leading underscore marks them as keys read by the loader, not by the parser; the loader strips them and wraps the parser in a MIME-filtering decorator.

{
  "parsers": [
    { "pdf-parser": {
        "_mime-include": ["application/pdf"],
        "_mime-exclude": ["application/pdf+fdf"],
        "sortByPosition": true } },
    { "default-parser": { "_mime-exclude": ["image/heic"] } }
  ]
}

On a default-parser entry, a real-type filter also removes the parser for that type. A bare string is read as a one-element list, but a value that is neither a string nor an array silently becomes an empty filter. Since 4.1.0 the pre-4.1 image/ocr-* pseudo-types are refused in these lists: filter the real type (image/tiff) on the engine’s own entry instead.

This replaces the 3.x <mime> and <mime-exclude> elements, and exclude replaces <parser-exclude>.

Source: Apache Tika 4.1.x, Serialization and Configuration, framework directives and Migrating to Tika 4.x, OCR engines and the image/ocr pseudo-types.

Engines under parsers are deprecated

In 4.0 an OCR engine (tesseract-ocr-parser), a VLM parser or the image-embedding parser was configured as a parsers entry. Since 4.1.0 that is deprecated: it still works with a startup WARN that says what the entry does, and it fails config load in 4.2.0. The 4.1 shape names the engine under engines and lists it in text-recognizers, and every default parser stays loaded:

{
  "engines": {
    "tesseract": { "tesseract-ocr-parser": { "language": "eng+spa" } }
  },
  "text-recognizers": [
    { "engine": "tesseract" }
  ]
}

"text-recognizers": [] turns OCR off everywhere, and {"parse-context": {"text-recognizers": {"enabled": false}}} turns it off for one request. The engine options are on OCR with Tesseract; the VLM and inference engines are on VLM Parsers & Inference.

Source: Apache Tika 4.1.x, Configuration, the text-recognizers list and Apache Tika 4.1.x, Inference.

The other library sections

metadata-filters

metadata-filters is a top-level array run in order, each filter seeing the output of the previous one. There is no default-metadata-filter and no implicit filtering: an absent or empty section means the metadata is emitted unchanged. The built-in filters in tika-core are include-field-metadata-filter, exclude-field-metadata-filter, field-name-mapping-filter, remove-by-mime-metadata-filter, clear-by-attachment-type-metadata-filter, date-normalizing-metadata-filter, capture-group-metadata-filter, geo-point-metadata-filter, legacy-key-migration-filter and no-op-filter. The filter options and recipes are on Metadata.

Where the filters run is the important part:

  • tika-app, tika-server and Tika Pipes apply the configured chain before writing or emitting output.

  • A library caller applies it itself. AutoDetectParser.parse does not run the filters; call loader.loadMetadataFilters().filter(list, context) on the metadata, as the Bookshelf program below does.

  • In tika-app 4.1.0 the chain was applied to the -J (recursive JSON) output but not to -m or -j. With the Bookshelf include filter, -m still printed every PDF key while -J printed only the four included fields.

  • An include filter drops what it does not name, including tk:content. The same -J run returned no extracted text at all, because the filter’s list did not include tk:content. Add it when the text has to survive.

  • A per-request metadata-filters list in parse-context replaces the configured chain for that request.

Run of -J -t with the Bookshelf filter (include lists Content-Type, dc:title, dc:creator, xmpTPg:NPages):

[{"dc:creator":"Bookshelf Press","dc:title":"Spring catalogue","Content-Type":"application/pdf","xmpTPg:NPages":"1"}]

Source: Apache Tika 4.1.x, Metadata Filters and MetadataFilter, Javadoc 4.1.0.

content-handler-factory

The handler that tika-app, tika-server, Pipes and loadContentHandlerFactory() use for the extracted content. If the section is missing, the loader returns a BasicContentHandlerFactory of type MARKDOWN with no write limit, the 4.x default everywhere (3.x defaulted to XHTML).

{
  "content-handler-factory": {
    "basic-content-handler-factory": { "type": "TEXT", "writeLimit": 500000 }
  }
}

The types are those of BasicContentHandlerFactory.HANDLER_TYPE (TEXT, HTML, XML, BODY, IGNORE, MARKDOWN); see Content Handlers & Output Formats.

Source: the Javadoc of loadContentHandlerFactory in the 4.1.0 TikaLoader source and Migrating to Tika 4.x, default content handler.

auto-detect-parser

The AutoDetectParserConfig, read from the root of the file by loadAutoDetectParser(). In 4.1.0 it has two properties: throwOnZeroBytes (default true: an empty file throws ZeroByteFileException) and contentHandlerDecoratorFactory. The 3.x limits that lived here (outputThreshold, maximumCompressionRatio, maximumDepth, …​) moved to parse-context.

{ "auto-detect-parser": { "throwOnZeroBytes": false } }

Source: AutoDetectParserConfig, Javadoc 4.1.0.

parse-context

parse-context holds the objects and configs that each ParseContext from loadParseContext() carries. The ones a Bookshelf worker sets are the limits:

writeLimit, throwOnWriteLimit, maxXmlDepth, maxPackageEntryDepth, zipBombThreshold, zipBombRatio

maxDepth, throwOnMaxDepth, maxCount, throwOnMaxCount

How deep and how many embedded documents

totalTaskTimeoutMillis, progressTimeoutMillis, throwOnDeadline

Per-parse defaults for a self-configuring parser

Two kinds of entries behave differently. Plain config objects such as output-limits are deserialized when the context is built, so a misspelled property fails loadParseContext(). Self-configuring components, which include every parser, are left as JSON in the context and resolved by the component when it runs; a typo there surfaces only when that parser parses (see Strict validation: where a typo is caught). When a key has a JSON config, it wins over a value set in code with context.set(XConfig.class, ...).

The limits are explained on Parser API & AutoDetectParser and Embedded Documents & Recursive Parsing.

Source: Apache Tika 4.1.x, Setting limits, Apache Tika 4.1.x, Digesters, Apache Tika 4.1.x, Pages and the tika-core 4.1.0 signatures of OutputLimits, EmbeddedLimits, TimeoutLimits and ExceptionReporting.

translator and renderers

translator takes one translator (loadTranslator() returns DefaultTranslator when absent; tika-core registers default-translator and empty-translator, and tika-translate adds the online ones, covered in Language Detection & Translation). renderers is a list wrapped into a CompositeRenderer; the PDF renderer options are on PDF Parsing.

Source: the registerComponentConfigs() method of the 4.1.0 TikaLoader source and the META-INF/tika/translators.idx file of the tika-core 4.1.0 jar.

The Bookshelf configuration

The Bookshelf intake worker reads one file at startup. It keeps every default parser except the executable parser, orders PDF text by position, keeps four metadata fields, emits Markdown, and caps text, embedded depth and time.

{
  // Bookshelf intake: the startup configuration of every worker

How to use it well:

  • One loader per configuration, created at startup. It is cheap to keep and expensive to rebuild (the parser list is built from the registry). The components it returns are meant to be shared: AutoDetectParser, the detectors and the filters are thread-safe in the usual Tika sense. In Spring, expose the loader and the parser as singleton beans; the Spring Boot Integration page of this section covers the lifecycle.

  • A new ParseContext per parse, from loadParseContext(). A context carries per-parse state and must not be shared between concurrent parses.

  • loadDefault() is a process-wide singleton. Use it only where every caller wants the SPI defaults; anything with limits or exclusions needs its own file.

  • Fail at startup. load throws for a syntax error, an unknown top-level key or an unset environment variable, but component names and options are checked only when the matching load... method runs. Call loadAutoDetectParser(), loadParseContext() and loadMetadataFilters() once during startup so a bad entry stops the service before the first document instead of on it.

  • toJson() is a diagnostic, not a round-trip. In 4.1.0 it serialises the parsers' internal state: a file with only { "pdf-parser": { "sortByPosition": true } } came back with defaultConfig and pdfparserConfig blocks of 34 properties each, a renderer and a contentEnrichers object, plus the full SPI detector and encoding-detector lists. Loading that output again failed with Failed to instantiate component 'org.apache.tika.parser.pdf.PDFParser'. Keep your hand-written file as the source of truth. (tika-app’s old --dump-current-config and related options are commented out in the 4.1.0 TikaCLI source with the note "rework with json serialization".)

Secrets from the environment

Since 4.1.0 a string value in the startup file may reference an environment variable as ${env:NAME}, alone or inside a longer string. The loader substitutes the value when it reads the file. The exact pattern in the 4.1.0 EnvInterpolator source is \$\{env:([A-Za-z_][A-Za-z0-9_]*)}, so a variable name starts with a letter or an underscore and contains letters, digits and underscores.

{
  "server": { "port": 9998 },
  "fetchers": {
    "covers": { "file-system-fetcher": { "basePath": "${env:BOOKSHELF_INBOX}/covers" } }
  },
  "emitters": {
    "es": { "es-emitter": { "esUrl": "http://${env:ES_HOST}:9200/bookshelf",
                            "apiKey": "${env:ES_API_KEY}" } }
  }
}

The rules, checked against the source and with a run:

  • Only ${env:NAME} is interpolated. ${NAME}, $NAME, ${sys:...} and any other text stay literal, so a prompt or a regex that contains ${ is safe. In the test, "${env:BOOKSHELF_INBOX}/covers" became /srv/bookshelf/inbox/covers while a "${BOOKSHELF_INBOX} stays literal" value was left unchanged.

  • Only string values are interpolated, in objects and arrays at any depth. Keys and non-string values (numbers, booleans) are not.

  • An unset variable fails the load with its name and its JSON path, never a value: a missing secret stops the service at startup instead of reaching Elasticsearch as an empty key.

  • The forked parse workers of tika-server and Pipes inherit the parent’s environment and read the same file, so a reference resolves there too.

  • Only the startup file is interpolated. Per-request configuration (tika-server /config endpoints, Pipes tuples) never is: a request cannot read the server’s environment. Inline presets in the file resolve at startup with the rest of it.

  • The reference keeps the secret out of tika-config.json, not out of every file. With a persistent config store (configStoreType file or Ignite) the resolved fetcher and emitter configurations are written to that store; the default in-memory store writes nothing.

  • The Tika 4.1.0 release notes list environment-variable interpolation in tika-config.json as new in 4.1.0, so a 4.0.x loader does not resolve these references. This page did not check whether any 3.x component had a comparable mechanism in the XML; templating the file before start was the general workaround.

Run it with the variables set by the platform (a Kubernetes Secret, a systemd EnvironmentFile, the CI secret store), never with the values in a script:

export BOOKSHELF_INBOX=/srv/bookshelf/inbox
export ES_HOST=search.internal
# ES_API_KEY comes from the secret store, never from this file
java -jar tika-server-standard-4.1.0.jar -c tika-config.json

TikaLoader.getConfig().getRootNode() returns the JSON after interpolation. Do not log it in production: it contains the resolved secrets.

Adding extra jars: tika.extras.dir

To add components (an extra parser, encoding detector or their dependencies) to tika-app or tika-server without repackaging, put their jars in a directory and point the tika.extras.dir system property at it:

java -Dtika.extras.dir=/opt/bookshelf/tika-extras -jar tika-app-4.1.0.jar --config=tika-config.json catalogue.pdf
java -Dtika.extras.dir=/opt/bookshelf/tika-extras -jar tika-server-standard-4.1.0.jar -c tika-config.json

Every jar in that directory joins the classpath that Tika’s service loading scans, so SPI-registered components (and @TikaComponent names, through their .idx files) are picked up, and the jars are forwarded to the forked JVMs of Pipes and tika-server. The property is off by default and there is no implicit directory. In the Docker images, mount the directory at /tika-extras instead, which is already on the container classpath.

Treat that directory as trusted code: anything in it runs with the full privileges of the Tika process. It must not be writable by less-trusted users, nor reachable by request handling on a server. pf4j-managed Pipes plugins (plugins/, plugin-roots) are a separate mechanism, covered on the Tika Pipes page of this section.

In your own Java application you do not need tika.extras.dir: add the component as a normal dependency.

The @TikaComponent and serialization model

Behind the JSON is the serialization system of tika-serialization, built on Jackson. The @TikaComponent annotation (org.apache.tika.annotation.TikaComponent, shipped in tika-core) is required for any class that should be configurable from JSON. At compile time the tika-annotation-processor reads it and:

  • derives the component name (or takes name);

  • adds a name=class line to the index file of its type, such as META-INF/tika/metadata-filters.idx;

  • adds the class to META-INF/services/<interface> for ServiceLoader, unless spi = false.

The registry built from the index files is the security allow-list: only registered classes can be instantiated from JSON.

Attribute Default Meaning

name

derived from the simple class name, in kebab case

The component name used in JSON.

spi

true

Also register in META-INF/services. With false the component is only available by explicit configuration and is not loaded by default-parser; use it for opt-in components.

contextKey

auto-detected

The class used as the ParseContext key. Auto-detected for Parser, Detector, EncodingDetector, MetadataFilter, Translator, Renderer, DigesterFactory, ContentHandlerFactory, ContentHandlerDecoratorFactory, MetadataWriteLimiterFactory, UnpackSelector and EmbeddedDocumentExtractor; set it explicitly otherwise, or when a class implements several of them.

defaultFor

none

Marks the component as the default implementation of an interface, used when no explicit configuration is given (for example BasicContentHandlerFactory for ContentHandlerFactory).

Three more ideas complete the model:

  • Self-configuring components. SelfConfiguring is a marker interface. Parser extends it, so every parser reads its own JSON from the ParseContext when it runs, through ParseContextConfig.getConfig(context, "pdf-parser", PDFParserConfig.class, defaultConfig). That is how per-request configuration reaches a parser, and why a typo in a parser block under parse-context surfaces at parse time.

  • Framework directives start with an underscore (_mime-include, _mime-exclude, _min-width, _min-height) so they cannot collide with a component’s own option names. The exclude key of the default-... markers is the exception, because those markers carry only framework keys.

  • Restricted mode for wire input. The startup file is trusted. Per-request JSON (tika-server request bodies, Pipes FetchEmitTuple) is read in restricted mode: the whole tree is scanned before anything is built, and only types that shape this request’s output can be instantiated from the wire (MetadataFilter, ContentHandlerFactory, ContentHandlerDecoratorFactory, DigesterFactory, MetadataWriteLimiterFactory, UnpackSelector). Types with exec, I/O or network capability (Parser, Detector, EncodingDetector, Renderer, Translator, EmbeddedDocumentExtractor) are blocked. The check is fail-closed: a new context-key interface is blocked until it is consciously allow-listed.

The restricted mode does not stop a request from configuring an already-loaded parser, because a parser’s config subtree is passed through unexamined. A request carrying {"parse-context": {"pages": {"text": "EXTRACT_AND_OCR"}}} reaches the PDF parser and takes effect. That is why tika-server gates per-request configuration separately with allowPerRequestConfig, off by default. Treat "callers may send per-request config" as "callers may set any parser option, including ones that start external processes such as OCR".

Source: Apache Tika 4.1.x, Serialization and Configuration, the 4.1.0 TikaComponent source and TikaComponent, Javadoc 4.1.0.

The filter extends MetadataFilterBase, whose per-Metadata hook suits a filter that needs no context. Options are plain bean properties, set from the JSON body.

package com.example.bookshelf;

import java.util.Locale;

import org.apache.tika.annotation.TikaComponent;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.metadata.TikaCoreProperties;
import org.apache.tika.metadata.filter.MetadataFilterBase;

/** Derives a shelf code such as "BKS-LIG" from the document title. */
@TikaComponent
public class ShelfCodeFilter extends MetadataFilterBase {

    private String prefix = "BKS";
    private String targetField = "bookshelf:shelf-code";

    public String getPrefix() {
        return prefix;
    }

    public void setPrefix(String prefix) {
        this.prefix = prefix;
    }

    public String getTargetField() {
        return targetField;
    }

    public void setTargetField(String targetField) {
        this.targetField = targetField;
    }

    @Override
    protected void filter(Metadata metadata) {
        String title = metadata.get(TikaCoreProperties.TITLE);
        if (title == null || title.isBlank()) {
            return;
        }
        String letters = title.replaceAll("(?i)^(the|a|an)\\s+", "").replaceAll("[^\\p{L}]", "");
        String code = letters.substring(0, Math.min(3, letters.length())).toUpperCase(Locale.ROOT);
        metadata.set(targetField, prefix + "-" + code);
    }
}

Converting the parsers section

tika-app 4.1.0 has a converter. It writes the JSON to standard output and the diagnostics to standard error, and it takes no other argument:

java -jar tika-app-4.1.0.jar --convert-config-xml-to-json=tika-config.xml > tika-config.json

The Bookshelf 3.x file it was run on (3.x form, kept for migration only):

<properties>
  <parsers>
    <parser class="org.apache.tika.parser.DefaultParser">
      <parser-exclude class="org.apache.tika.parser.pdf.PDFParser"/>
      <parser-exclude class="org.apache.tika.parser.executable.ExecutableParser"/>
    </parser>
    <parser class="org.apache.tika.parser.pdf.PDFParser">

What the run shows:

  • Only parsers is converted. The <detectors> and <service-loader> sections were dropped with no message on either stream. The usage text says so ("parsers section only"), but nothing in the output does: compare section by section.

  • Class names became component names, and exclude lists for <parser-exclude>.

  • Renamed 3.x options were mapped: ocrStrategy became the 4.1 pages.text, and Tesseract’s timeoutSeconds became timeoutMillis, with the value multiplied by 1000. Tesseract’s otherTesseractSettings list becomes the otherTesseractConfig map.

  • The value auto was copied as written. The converted file loaded as it was and parsed both sample files, so the lower-case form is accepted in 4.1.0; the 4.1.x documentation spells the policy values in upper case (AUTO, EXTRACT, …​), which is the safer form to keep.

  • The Tesseract entry stays under parsers, which 4.1.0 accepts with a deprecation WARN and 4.2.0 will reject. On the test machine, with no Tesseract installed, the WARN read: org.apache.tika.parser.ocr.TesseractOCRParser is named under "parsers", which is deprecated for engines since 4.1.0 and unsupported in 4.2.0: configure it under "engines" and name it in "text-recognizers". It advertises no media types (engine unavailable, or configured to skip) and never runs; .... Move it to engines and text-recognizers as shown earlier.

  • A custom or third-party parser class that the converter cannot find in the registry gets a kebab-case name derived from its simple class name, which may not be its real registered name. Check it against --list-parser-names.

The converter class is org.apache.tika.cli.XmlToJsonConfigConverter; its supported parameter types are bool, int, long, double, float, string, list and map. The converted tika-config.json after the manual fixes:

{
  "parsers": [
    { "pdf-parser": { "sortByPosition": true, "extractInlineImages": true, "pages": { "text": "AUTO" } } },
    { "default-parser": { "exclude": ["executable-parser"] } }
  ],
  "engines": {
    "tesseract": { "tesseract-ocr-parser": { "language": "eng+spa", "timeoutMillis": 120000 } }
  },
  "text-recognizers": [ { "engine": "tesseract" } ],
  "detectors": [ { "default-detector": {} } ]
}

This final file follows the 4.1.x documentation for engines and text-recognizers. Note the behaviour change it brings: on the test machine, which had no Tesseract binary, it failed to load with Text recognizer engine "tesseract" advertises no media types (a _mime-include list does not count). Is the engine unavailable (missing native binary, unreachable inference server) or configured to skip enrichment?. An engine named in text-recognizers must be usable at startup, while the deprecated entry under parsers was quietly inert. That is the intended 4.1 behaviour (a missing OCR engine stops the service instead of silently producing no OCR text), so install Tesseract, or use the -full Docker image, before deploying the migrated file. It was not loaded with Tesseract installed for this page.

TikaConfig to TikaLoader in code

3.x form, kept for migration only:

// Tika 3.x: TikaConfig and tika-config.xml (removed in 4.x)
TikaConfig config = new TikaConfig(Path.of("tika-config.xml"));
Parser parser = config.getParser();
Detector detector = config.getDetector();
AutoDetectParser autoDetect = new AutoDetectParser(config);
ParseContext context = new ParseContext();

4.x:

// Tika 4.x: TikaLoader (tika-serialization) and tika-config.json
TikaLoader loader = TikaLoader.load(Path.of("tika-config.json"));
Parser parsers = loader.loadParsers();
Detector detector = loader.loadDetectors();
Parser autoDetect = loader.loadAutoDetectParser();   // declared type is Parser
ParseContext context = loader.loadParseContext();    // limits and per-parser config from the file

// no file: the SPI defaults, as new TikaConfig() was in 3.x
TikaLoader defaults = TikaLoader.loadDefault();

The other code-level changes that come with the move:

  • add tika-serialization to the build if you only had tika-core;

  • a 3.x AutoDetectParser(TikaConfig) constructor call becomes loadAutoDetectParser(); new AutoDetectParser() without a config still works and uses the SPI defaults;

  • JSON config now wins over a programmatic context.set(XConfig.class, ...) for the same key, the reverse of earlier 4.x builds;

  • parseContext.get(SomeConfig.class) no longer returns a config that came from JSON, because configs are cached by component name and class;

  • the Tika facade and new DefaultParser() still work without a loader for simple cases.

The 3.x TikaConfig Javadoc is linked in the references for comparison; there is no 4.1.0 Javadoc page for it.

Memory, performance and robustness

  • Load once. TikaLoader.load parses the file, and the first loadParsers() instantiates every parser in the list (with default-parser, all of them). Do it at startup and share the results; never build a loader per document.

  • Contexts are cheap and per parse. loadParseContext() builds a new context from the parsed JSON each time; that is the intended per-document call.

  • Limits belong in the file. output-limits, embedded-limits and timeout-limits in parse-context are the 4.x defences against huge outputs, zip bombs, deep nesting and parsers that hang. A configuration without them inherits the defaults, which do not cap text (writeLimit -1).

  • Fewer parsers, less risk. Excluding parsers you never need (executables, CAD, fonts for a book intake) reduces the attack surface and the memory that loaded parsers hold. Excluding them is cheaper than catching their failures.

  • Fail fast at startup with the three load... calls and one sample document per important format, as described under strict validation, so a typo in a parser block does not wait for the first PDF.

  • In-process is not isolation. A configuration file does not make in-process parsing safe for untrusted files: use PipesForkParser, tika-server or Pipes, whose forks read the same file.

Source: Apache Tika 4.1.x, Setting limits and Apache Tika 4.1.x, Robustness.

Pitfalls and security

  • A parsers list without default-parser keeps only the listed parsers; every other format falls to EmptyParser with no error. Shown above with manuscript.docx.

  • ${NAME} is not ${env:NAME}. Only the env: form is interpolated; the others are passed to the component as literal text, so a fetcher would look for a directory literally named ${BOOKSHELF_INBOX}.

  • The resolved secrets are in memory and in persistent config stores. Do not log getConfig().getRootNode(), and do not enable a file-based config store without protecting it.

  • Per-request configuration is parser configuration. allowPerRequestConfig (tika-server) and allowPerRequestConfig / allowComponentManagement (tika-grpc) let a caller set any parser option, including OCR, which starts external processes. Keep them off for untrusted callers; offer presets instead.

  • Include filters drop the content unless tk:content is listed.

  • Library callers must apply the metadata filters themselves; the parser does not.

  • tika-app -m and -j ignored the filter chain in this page’s 4.1.0 run, while -J applied it.

  • toJson() output does not reload in 4.1.0. Keep the hand-written file in version control.

  • The converter silently drops every section except parsers.

  • Engines under parsers work in 4.1.x with a WARN and fail in 4.2.0.

  • Single backslashes in Windows paths are a JSON parse error.

  • tika.extras.dir is a code directory. Anything in it runs with the process’s privileges; make it read-only for the service account.

  • Class names are refused, by design. Do not look for a way around it: register the class with @TikaComponent.

Checklist

  • Depend on tika-serialization and load the file with TikaLoader.load(Path) once, at startup.

  • Keep default-parser (and default-detector) in the lists unless you want only what you name; exclude parsers you never need by component name.

  • Copy component names from --list-parser-names or from the load error, never guess them; never use class names.

  • Put limits in parse-context: output-limits, embedded-limits, timeout-limits, and exception-reporting for services.

  • Call loadAutoDetectParser(), loadParseContext() and loadMetadataFilters() during startup, and parse one sample per important format in CI after config changes.

  • Use one ParseContext per parse, from loadParseContext().

  • Apply loadMetadataFilters() yourself in library code, and list tk:content in include filters.

  • Reference secrets as ${env:NAME}; never write them into the file, never log the resolved JSON.

  • Use forward slashes in Windows paths.

  • Treat tika.extras.dir as a trusted code location.

  • Register custom components with @TikaComponent and the tika-annotation-processor.

  • Migrating: convert parsers with --convert-config-xml-to-json, migrate every other section by hand, move OCR engines to engines and text-recognizers, switch metadata keys to tk: names, and replace TikaConfig with TikaLoader.
