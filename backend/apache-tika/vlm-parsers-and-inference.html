VLM Parsers & Inference

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Baseline date: 2026-10-12. This page was written against Apache Tika 4.1.0 (the latest release on Maven Central on that date), Java 21 and later for the examples (Tika 4.x needs Java 17), Spring Boot 4.x on Spring Framework 7 and the Docker image apache/tika:4.1.0-full. Everything on this page is new in 4.x: Tika 3.3.x has no VLM parsers and no inference section, so the 3.x notes here are about what 4.x replaced. Both modules are marked experimental by the project: the classes, the configuration keys of an engine entry, the inference section and the tk:chunks layout may change in a minor release without a deprecation cycle. The engines map and the text-recognizers list are declared stable. Pin the Tika version you validated against.

A vision-language model (VLM) reads an image and answers in text. Tika 4.x uses one in two ways. As a text recognizer, a VLM takes Tesseract’s place: it transcribes a scanned page or an embedded picture into Markdown, which Tika turns into XHTML and adds to the document text. As an inference engine, a model produces something other than text, today an embedding vector, for the extracted text, the pictures, the rendered pages or the audio and video of a document tree; the vectors land in the tk:chunks metadata field, ready for a vector index. This page covers both, for the Bookshelf intake service that receives manuscripts, catalogues, scanned loan forms and book covers.

Related pages: Configuration (the tika-config.json file and TikaLoader), PDF Parsing (the pages block that decides when a page is rendered), OCR with Tesseract (the local alternative to a VLM), Extending Tika (writing your own engine), Content Handlers & Output Formats (the Markdown handler) and Embedded Documents & Recursive Parsing (the metadata list the vectors are written to).

How this page was checked: every key name, default and class name was read from the tika-vlm and tika-inference 4.1.0 sources (tag 4.1.0 of apache/tika) and the 4.1.x documentation pages listed in References. The Java programs, the JSON configurations marked run and the tika-app command were compiled and run against Tika 4.1.0 on Java 25, talking to a small local mock of the OpenAI chat-completions and embeddings APIs on 127.0.0.1:8000 (written for this page, never a paid service). The outputs shown are therefore real Tika output, but the model answers are canned: the mock always returns the same Markdown and four-number vectors. The Claude and Gemini parsers, Ollama, vLLM, Jina, Azure OpenAI and tika-server calls were not run; their configurations follow the 4.1.x docs and the source. Every credential is read from an environment variable, and the values used in the runs were dummy strings.

Both start from the same engines map: a name you choose, mapped to one engine type and its settings. An engine knows nothing about documents. A text-recognizers entry or an inference binding names the engine and says what it is fed. Two names may point at the same endpoint with different models, and secrets live only in the engine entry.

The diagram shows the order that matters. A recognizer runs during the parse, as the PDF or image parser meets each page or picture, so its text is part of the document text. Inference runs after the walk of the tree: images, pages and media are flushed at the end of the top-level parse, and the TEXT stage runs over the finished metadata list. That is why text vectors are computed from the text the recognizer produced.

Source: Configuration, 4.1.x docs (the text-recognizers list) and Inference: engines and bindings, 4.1.x docs.

Modules and dependencies

tika-vlm holds the three VLM parsers and the Markdown-to-XHTML emitter. tika-inference holds the embedding engine, the Markdown chunker and the deprecated 4.0 embedding filters. Both live under tika-parsers-ml and are not part of tika-parsers-standard-package, so a library user adds them explicitly. Both depend on tika-http-jdk, Tika’s small client over the JDK HttpClient; no vendor SDK is pulled in. tika-vlm also brings commonmark-java (with the GFM tables and strikethrough extensions) and jsoup for the Markdown and HTML conversion.

Configuring a VLM as a text recognizer

The 4.1 shape names the engine once under engines and lists it in text-recognizers. Every default parser stays loaded; the image parser and the PDF parser call the recognizer for the bytes they have already parsed.

A local OpenAI-compatible model (run)

This is the configuration the intake service uses on a workstation, against a model served on the same machine. The key is optional for a local server; it is shown read from the environment because a shared vLLM or LiteLLM gateway usually wants one.

{
  "engines": {
    "local-vlm": {
      "openai-vlm-parser": {
        "baseUrl": "http://127.0.0.1:8000",
        "model": "mock-vlm",
        "apiKey": "${env:BOOKSHELF_VLM_KEY}",
        "timeoutMillis": 600000,
        "maxTokens": 4096
      }
    }
  },
  "text-recognizers": [ { "engine": "local-vlm" } ]
}

${env:NAME} is the 4.1 environment interpolation: the loader replaces it with the variable’s value when the file is read. Only that exact form is touched (${NAME}, $NAME and ${sys:...} stay literal), the forked workers of tika-server and Pipes inherit the variable, and per-request configuration can never read the server’s environment. A missing variable stops the load with its name and JSON path, never a value. The run without the variable failed with:

org.apache.tika.exception.TikaConfigException: environment variable BOOKSHELF_VLM_KEY is not set;
referenced at /engines/local-vlm/openai-vlm-parser/apiKey

The Java program loads that file, parses the cover and prints what the recognizer added:

import java.nio.file.Path;

import org.apache.tika.config.loader.TikaLoader;
import org.apache.tika.io.TikaInputStream;
import org.apache.tika.metadata.Metadata;
import org.apache.tika.parser.ParseContext;
import org.apache.tika.parser.RecursiveParserWrapper;
import org.apache.tika.sax.BasicContentHandlerFactory;
import org.apache.tika.sax.RecursiveParserWrapperHandler;

public class VlmIntake {
    public static void main(String[] args) throws Exception {
        TikaLoader loader = TikaLoader.load(Path.of(args[0]));              // tika-config.json
        RecursiveParserWrapper parser = new RecursiveParserWrapper(loader.loadAutoDetectParser());
        ParseContext context = loader.loadParseContext();
        RecursiveParserWrapperHandler handler = new RecursiveParserWrapperHandler(
                new BasicContentHandlerFactory(BasicContentHandlerFactory.HANDLER_TYPE.MARKDOWN, -1));
        try (TikaInputStream tis = TikaInputStream.get(Path.of(args[1]))) {  // book-cover.jpg
            parser.parse(tis, handler, new Metadata(), context);
        }
        for (Metadata m : handler.getMetadataList()) {
            System.out.println("Content-Type          : " + m.get("Content-Type"));
            System.out.println("tk:parsed-by          : " + String.join(", ", m.getValues("tk:parsed-by")));
            System.out.println("vlm:model             : " + m.get("vlm:model"));
            System.out.println("vlm:prompt-tokens     : " + m.get("vlm:prompt-tokens"));
            System.out.println("vlm:completion-tokens : " + m.get("vlm:completion-tokens"));
            System.out.println("tk:content            :\n" + m.get("tk:content"));
        }
    }
}

Azure OpenAI and custom paths

OpenAIVLMParser has a completionsPath (default /v1/chat/completions) for endpoints whose path differs, such as an Azure deployment (/openai/deployments/{deployment}/chat/completions?api-version=...). A non-default path also turns the /v1/models probe off. Azure wants the key in an api-key header with no Bearer prefix. The Java class has setApiKeyHeaderName and setApiKeyPrefix for that, but in 4.1.0 those two are not JSON keys: adding them to the engine entry failed the load with

Unrecognized field "apiKeyHeaderName" (class org.apache.tika.parser.vlm.VLMOCRConfig), not marked as ignorable
(15 known properties: "inlineContent", "maxRetries", "prompt", "apiKey", "timeoutMillis", "model", "textRecognizer",
"allowRuntimePrompt", "minFileSizeToOcr", "completionsPath", "baseUrl", "skipOcr", "maxFileSizeToOcr",
"maxImagePixels", "maxTokens")

So from tika-config.json the VLM parser always sends Authorization: Bearer. For Azure, either construct OpenAIVLMParser in Java and call the setters, or put an OpenAI-shaped gateway (LiteLLM, for instance) in front. The embedding engine is different: openai-embedding-engine does accept apiKeyHeaderName and apiKeyPrefix in JSON (see Vendor keys: requestParameters). The error message above is also the most reliable list of the VLM keys in 4.1.0.

Source: the OpenAIVLMParser 4.1.0 source and its Javadoc, and a load of that configuration on 4.1.0.

On top of the engine’s own gates, a text-recognizers entry takes engine, _mime-include, _mime-exclude, _min-width and _min-height. Use _min-width/_min-height to keep icons and logos away from a paid model: an image whose recorded tiff:ImageWidth/tiff:ImageLength is smaller is never sent. Whatever the entry says, an image under 2 x 2 pixels never reaches any engine.

    { "engine": "local-vlm", "_mime-exclude": ["image/gif"], "_min-width": 200, "_min-height": 200 }
  ]
}

Startup behaviour

What happens when the engine cannot be reached is a frequent surprise, so it is worth spelling out:

  • AbstractVLMParser.initialize() probes the health URL (OpenAI-compatible and Gemini only). If the probe fails, it logs a warning and the parser advertises no media types for the rest of the run. It does not retry later.

  • The text-recognizers loader then refuses an engine with no types. The run against a closed port failed the load with: Text recognizer engine "local-vlm" advertises no media types (a _mime-include list does not count). Is the engine unavailable (missing native binary, unreachable inference server) or configured to skip enrichment?

  • So: start the model server before Tika, and in Docker Compose or Kubernetes make Tika wait for the model’s readiness. A tika-server that restarts on failure (restart: on-failure) recovers once the model is up.

  • The OpenAI probe calls /v1/models. A home-made server that only implements /v1/chat/completions fails the probe; add the /v1/models route (the 4.1.x local-server guide does) or use a non-default completionsPath.

  • Claude has no probe, and the Gemini probe only proves that the model list is readable. A wrong key or a model your key cannot use fails at the first parse.

Source: the AbstractVLMParser 4.1.0 source and the Running a Local VLM Server, 4.1.x docs page. Both failure messages above are from runs on 4.1.0.

Scanned PDFs: the pages block decides

The PDF parser asks the recognizer for text only when its pages.text policy says so. The default is AUTO: pages whose extracted text is poor are rendered and sent. scanned-loan-form.pdf has no text layer, so AUTO sends every page; OCR sends every page of every PDF, which is what this run forced on the one-page catalogue.pdf to show the output shape:

Markdown-to-XHTML conversion

A model answers in Markdown, and Tika does not paste that answer as plain text. MarkdownToXHTMLEmitter parses it with commonmark-java and emits real XHTML elements: headings, paragraphs, <b>/<i>, lists and tables (GFM tables and strikethrough are enabled). The run above shows a Markdown pipe table becoming <table>, <thead>, <th> and <td>, wrapped in <div class="ocr">. Because the result is XHTML, every Tika output format sees structure: the Markdown handler writes the pipe table back (as in the tk:content above), the XML handler writes the <table>, the text handler writes the cell text.

Document-OCR models (the docs name jina-ocr-v1 and DeepSeek-OCR) write tables as raw HTML inside the Markdown whatever the prompt says. Tika parses such an HTML block leniently with jsoup and re-emits only the structural elements (table, tr, th, td, p, lists, headings), dropping every attribute except colspan and rowspan. Other elements give their text; script and style give nothing. Inline HTML tags are dropped and their text kept, except <br>. That is a safety property as well as a convenience: a model that echoes markup from a hostile image cannot inject scripts or event attributes into Tika’s XHTML.

The conversion is also why a VLM’s output is better than raw OCR for the RAG pipeline downstream: headings survive as headings, so the Markdown chunker can split on them (see Why Markdown is required for inference). It does not make the model correct. A VLM can misread, skip or invent text, and nothing in Tika checks the transcription against the image.

Source: Markdown-to-XHTML conversion, 4.1.x docs and the MarkdownToXHTMLEmitter 4.1.0 source.

Field Rule for caller-supplied JSON

baseUrl, apiKey

Always refused. A caller can never redirect the document, or your key, to another host.

model

Always refused. A second model is a second engine.

maxTokens

May be lowered, never raised above the load-time value. This ceiling is what bounds the cost of one call.

maxImagePixels, maxRetries, allowRuntimePrompt

Always refused.

prompt, textRecognizer

Refused unless the engine was loaded with allowRuntimePrompt: true.

skipOcr and the size gates

Allowed. Switching the engine off for one request is always safe.

Keep allowRuntimePrompt off for any server reachable by people you do not fully trust. A caller-controlled prompt is a prompt-injection surface on your key: "ignore the image and write …​" costs you tokens and puts arbitrary text into your index under the document’s name. The site’s Prompt Injection page covers the general problem; here, the image itself is also untrusted input, so a scanned page can carry instructions to the model too. Treat VLM output as untrusted text, exactly like the document’s own text.

Practical notes for local models:

  • Timeouts. The 4.1.x guide measures 15 to 30 seconds per page image for a 2.4B model on an M3 Max, and 20 to 30 seconds to load the model.   • Throughput. A single local model is a queue. More Tika workers than the model can serve only lengthen the queue; keep numClients (tika-server, Pipes) near the number of concurrent requests the model server handles.

  • Licences. Model weights carry their own licence. The guide notes that jinaai/jina-vlm (the default model name in VLMOCRConfig) is CC BY-NC 4.0, non-commercial, while Qwen/Qwen2-VL-2B-Instruct is Apache 2.0. Check before a commercial deployment.

  • Bind locally. The guide’s server binds 127.0.0.1 only. A model server has no notion of Tika’s trust model; keep it off public interfaces.

Inference: engines and bindings

Inference in 4.1 has three parts, each answering one question:

  • engines: what can be called. Name, engine type, endpoint, model, key.

  • inference: what runs on what. A list of bindings; each names an engine, an input kind and the tasks.

How it runs

Parsers do not call embedding engines. Every image, audio or video document the parse meets, however deep, is offered to one InferenceDispatcher after its own parser has run. The dispatcher keeps the units of the whole tree, as files it owns, until the top-level parse ends, then sends each binding’s units to its engine in requests of up to maxBatchSize. A .docx with twelve pictures is one embeddings request, not twelve; if the endpoint rejects one image in a batch, the rest are retried one by one. This flush is still inside parse(), under the parse’s timeout, and the unit files are deleted when it ends. A failed request marks the top-level document with a warning; it never fails the parse.

The TEXT stage is separate: it runs after parse() returns, over the finished metadata list and before the metadata filters. tika-app, tika-server and Pipes call it for you. In the Java API you call it yourself, as TikaCLI does in 4.1.0; otherwise TEXT bindings silently do nothing. This was the first thing the run below found: with a plain RecursiveParserWrapper, the page vectors appeared and the text vectors did not.

Hosted engines and concurrency

A hosted engine limits requests in flight per key and answers the excess with 429 at once, usually without Retry-After; a saturated one answers 502, 503 or 504. Tika retries those four, maxRetries times, with a jittered backoff from 250 ms doubling to 4 s (or the server’s Retry-After), and never past the time the parse granted the call. A 400 or 401 fails at once. The VLM parsers use the same policy.

The retries absorb collisions between a few workers; they do not create capacity. The rule from the docs: keep numClients (tika-server, Pipes) at or below the key’s concurrency, counting every engine the workers call (a VLM recognizer and an embedding engine on the same vendor share the key), and raise the key’s tier before raising the workers. As an example of the scale, the docs quote Jina’s limits as two requests in flight on a free key, 50 on a paid key and 500 on premium.

Vendor keys: requestParameters

Most embedding services accept the OpenAI shape plus keys of their own. requestParameters is copied verbatim into every request body next to model and input; the engine neither knows nor checks the names, so use your vendor’s. Three kinds recur: a Matryoshka dimension (dimensions, output_dimension), a query-versus-document hint (task, input_type, task_type; use the document or passage value, since Tika indexes) and normalize/truncate flags. Two rules are enforced: model and input are refused, and so is any key that changes the response away from float vectors by index (encoding_format, embedding_type, output_type, output_dtype, return_multivector).

Media, in one paragraph

A MEDIA binding embeds audio or video. Tika cuts the file with ffmpeg (found on the PATH at load; the -full image ships it) into 25-second windows starting every 20 seconds, as 360p H.264 silent clips for visual and mono Opus for audio, under the parse’s time budget. Each segment’s chunks carry a temporal locator (start_ms, end_ms) and a correlator such as t:20000-45000, so the audio and visual vectors of one segment can be grouped. The engine needs "mediaInput": "object", and the segment grid is set per request in {"parse-context": {"media": {"segment": {...}}}}. The Bookshelf intake has no audio, so this page does not go further; the 4.1.x Inference page covers the limits.

Per request

{ "parse-context": { "inference": { "bindings": ["page-vectors"], "enabled": true } } }

enabled: false runs nothing for the request; bindings names the bindings that run (every enabled binding when absent). A name that is not configured fails the request. Engines can never be defined or changed per request, and the block carries names only, so it is safe in a preset or on a Pipes tuple.

Why Markdown is required for inference

The TEXT stage, and the 4.0 embedding filters before it, chunk tk:content with MarkdownChunker. The chunker looks for boundaries in priority order:

  1. Headings (# to ######): the strongest boundary, and the only split made when a section already fits in maxChunkChars.

  2. Blank lines: paragraph boundaries, to subdivide an oversized section.

  3. A hard split at maxChunkChars: the last resort for a single paragraph that is still too long.

Each chunk overlaps the previous one by overlapChars (200 by default; it must be smaller than maxChunkChars, or the load fails). Plain text has no headings, so a ten-page report chunks at arbitrary paragraph breaks instead of its sections, the heading text that tells the embedding model what a chunk is about is lost, and tables and lists lose their structure. Nothing fails; the chunks are only worse.

Two mechanisms keep this right in 4.x:

  • The default handler is Markdown. BasicContentHandlerFactory defaults to HANDLER_TYPE.MARKDOWN, and tika-server and tika-app default to Markdown output, so an unconfigured setup already chunks well. In Java, pass HANDLER_TYPE.MARKDOWN explicitly, as the programs above do.

  • A runtime warning when it is overridden. The handler factory records its type in tk:content-handler-type (the CLI run above shows MARKDOWN), and the embedding code logs a WARN when it is anything else. It is a check on a recorded value, not a guess about the content.

The project considered failing the load, or silently switching the handler, and rejected both: the first would make deliberate plain-text chunking impossible, the second would change tk:content under consumers that asked for TEXT.

For Pipes, use the CONCATENATE or RMETA parse mode with inference. CONTENT_ONLY emits only the raw tk:content string, so the chunks and vectors are dropped at emit time. The Elasticsearch and OpenSearch emitters have a chunkStrategy option for writing chunks as their own documents.

Source: Content Handler Requirements for Inference, 4.1.x docs, Chunk Strategies, 4.1.x docs and the MarkdownChunker 4.1.0 source (Javadoc).

The site’s Document Ingestion & Chunking page compares chunking strategies in general; Tika’s chunker is a structural one with a fixed overlap.

Cost, privacy and data residency

A VLM or embedding engine is the one place where Tika sends document content to another system. Everything in Tika’s security model about untrusted input still applies, and the following comes on top. The Cost Management and Sensitive Information pages cover the general practice.

Cost:

  • Every page and every picture is a call. With AUTO, a 40-page scanned loan form is 40 VLM calls; an email with a signature logo in every reply is one call per logo unless _min-width/_min-height or minWidth/minHeight keep it out. Set ocr.maxPages in the PDF parser’s pages block, maxChunks on bindings and maxTokens on VLM engines.

  • Retries cost too. A 502 that succeeds on the fourth retry may have been billed four times, depending on the vendor.

  • Measure. Sum vlm:prompt-tokens and vlm:completion-tokens from the output. Embedding engines report no usage in Tika’s metadata, so count units (chunks) instead.

  • Re-parsing is not free. Re-indexing a corpus re-runs every model call. Store the vectors with the document version, and use a no-enrichment preset for re-parses that only need metadata.

Privacy and residency:

  • The bytes leave your network. The image or page render is sent base64-encoded in the request body. A hosted vendor’s retention, training-use and logging terms then apply, along with the region its endpoint runs in. These terms are vendor contracts, not Tika settings, and this page does not describe any vendor’s; read them before sending personal data.

  • Choose the region with the endpoint. Residency is decided by baseUrl: a regional endpoint, a private cloud deployment (an Azure resource in your region, a Vertex endpoint behind a gateway) or a local model. Tika has no routing of its own, and a caller can never change baseUrl per request.

  • Local is the default answer for sensitive files. For the loan forms, a model on your own hardware (Ollama, vLLM) keeps the data in place. Use separate engines, and if needed separate tika-server instances, for files that may go to a hosted model and files that may not; presets select the configuration per workflow.

  • Keys. Read keys with ${env:NAME}, inject them from your secret store (Kubernetes Secret, Docker secret, Vault) and never commit them. Note the limit the docs state: with a persistent config store (configStoreType file or Ignite), resolved fetcher and emitter configurations are written to that store. Gemini’s key travels in the URL.

  • Output is untrusted. A model can hallucinate text that was not on the page, and a hostile image can carry prompt injection. Never let VLM text drive actions (routing, approvals) without a check, and keep allowRuntimePrompt off.

Source: VLM Parsers, 4.1.x docs, Secrets from the environment, 4.1.x docs and Apache Tika security model.

Memory, performance and robustness

  • The whole input is held in memory. AbstractVLMParser.parse reads the file fully and base64-encodes it, so a 50 MB input (the default maxFileSizeToOcr) is about 50 MB of bytes plus about 67 MB of base64 text plus the JSON body, per concurrent parse. Lower maxFileSizeToOcr and keep page renders small.

  • The model dominates latency. Seconds per page for a hosted model, tens of seconds for a laptop model. The progress timeout counts the wait as progress, but the total task timeout still applies; size it for your longest document.

  • Use the forked paths for untrusted files. In tika-server and Pipes the parse runs in a forked JVM, so a stuck model call ends with the fork, not with your application. The engines' HTTP clients are closed when the pipes server shuts down; in a library, close the EngineRegistry.

  • Failures are contained. A failed recognizer is reported through the parser’s normal exception handling and does not stop other recognizers; a failed embedding request becomes a warning on the root document. Check tk:exception:warn (and the other tk:exception:* keys) in your intake reports.

  • Two recognizers on one type both run. If you list Tesseract and a VLM for the same images, both run and their text is concatenated (a startup WARN names them). Choose one per media type with _mime-include/_mime-exclude.

What changed: 1.x to 4.x

Line Model and inference support

1.x (Tika in Action)

None of this exists. The book (chapter 5 on parsing) predates OCR integration; Tesseract came later in the 1.x line. Later 1.x releases added machine-learning parsers such as the TensorFlow-backed object recognition parser.

2.x and 3.x

The ML parsers moved under tika-parsers-ml: in 3.3.2 that directory holds tika-dl, tika-age-recogniser, tika-parser-advancedmedia-module (with ObjectRecognitionParser), tika-parser-nlp-module and tika-transcribe-aws. No VLM parsers, no embeddings, XML configuration.

4.0

tika-vlm with the three VLM parsers (openai-vlm-parser auto-registered); embeddings as openai-embedding-filter, jina-embedding-filter and openai-image-embedding-parser; engines configured under parsers; Markdown as the default handler. The old ML modules are gone: in 4.1.0 tika-parsers-ml holds tika-inference, tika-vlm, the NLP modules, tika-parser-tess4j-module and tika-transcribe-aws.

4.1

engines map, the stable text-recognizers list and the experimental inference section with TEXT, IMAGES, PAGES and MEDIA bindings; pages.inference; textRecognizer and allowRuntimePrompt; ${env:NAME} interpolation; no VLM auto-registration; the 4.0 shapes deprecated.

4.2 (announced)

Engines under parsers fail the load; the 4.0 filters and image embedding parser are removed; batched recognition per document, document-level tasks and chat tasks (captions, tags) are planned.

Source: the 3.3.2 and 4.1.0 source trees of apache/tika (directory listings of tika-parsers/tika-parsers-ml), Migrating to Tika 4.x, 4.1.x docs and Tika in Action. The 1.x history of the ML parsers is from the project’s module layout, not re-checked release by release.

Pitfalls

  • TEXT bindings do nothing from a bare RecursiveParserWrapper. Call InferenceDispatcher.text(...) after the parse, or use tika-app, tika-server or Pipes.

  • Unreachable model at startup fails the load for OpenAI-compatible and Gemini engines. Order your containers and retry the start.

  • A wrong Claude or Jina key passes startup and fails on the first document.

  • apiKeyHeaderName/apiKeyPrefix are not JSON keys for the VLM parser in 4.1.0 (they are for the embedding engine).

  • The default model names are not a recommendation. jinaai/jina-vlm is non-commercial; the Claude and Gemini defaults will be retired by their vendors.

  • A captioning prompt with textRecognizer: true lets AUTO replace a page’s real text with a description. Set textRecognizer: false for anything that is not a transcription.

  • A non-Markdown handler degrades chunking silently except for a WARN.

  • CONTENT_ONLY in Pipes discards the vectors.

  • Engine entries under parsers stop loading in 4.2.0. Migrate now.

  • Everything here is experimental. Re-read the release notes before every Tika upgrade and pin the version.

Checklist

  • Add tika-vlm and/or tika-inference (library) or use the tika-app / tika-server distributions, which include both.

  • Configure engines under engines, recognizers in text-recognizers, embeddings in inference.

  • Read every key with ${env:NAME}; never put a key in tika-config.json or in source control.

  • Set model, maxTokens, timeoutMillis, maxFileSizeToOcr, maxImagePixels and the minimum image size explicitly.

  • Cap pages and chunks (ocr.maxPages, maxChunks) and keep numClients within the key’s concurrency.

  • Use textRecognizer: false for non-transcription prompts and keep allowRuntimePrompt: false.

  • Use the Markdown handler, and CONCATENATE or RMETA in Pipes.

  • In Java: run the TEXT stage, then the metadata filters, and close the EngineRegistry.

  • Decide per document class whether it may leave your network; use a local model or a regional endpoint where not.

  • Record vlm:* token counts and the chunk counts for cost tracking.
