Tika App (Command Line & GUI)

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Baseline date: 2026-10-12. This page was written against Apache Tika 4.1.0 (the latest release on Maven Central on that date), with the 3.3.x differences noted, Java 21 and later for the examples (Tika 4.x needs Java 17), Spring Boot 4.x on Spring Framework 7 for the integration pages, and the Docker image apache/tika:4.1.0 for the service pages. tika-app is the Tika you can use without writing code: one command that parses a file, a URL or standard input and prints the text, the metadata, the media type or the language, a small desktop window for drag-and-drop, and, since 4.0, a front end to Tika Pipes that processes whole directories in forked JVMs. This page covers the three modes, every option of the 4.1.0 release, the options that were removed, and the Bookshelf intake desk using the tool to look at the files it receives.

The tika-app CLI is still in flux for 4.x

The official 4.1.x CLI page opens with the warning that the command line interface "is still in flux for 4.x". Options and behavior may change between 4.x releases. The same page says the authoritative option list is the --help output of the version you run, and that --help wins if the two disagree. Everything on this page was therefore checked against the --help output and the source of 4.1.0. Run --help on your own version before you copy a command into a script, and pin the tika-app version in any script you keep.

Related pages: Setup & Installation (the zip distributions and Java requirement), Content Handlers & Output Formats (what each output format contains), Metadata (the tk: keys you will see in the output), Embedded Documents & Recursive Parsing (-J and unpacking), Configuration (tika-config.json) and Tika Pipes (the engine behind pipes mode).

How this page was verified: the official tika-app-4.1.0.zip was downloaded from the Apache archive (https://archive.apache.org/dist/tika/4.1.0/), its SHA-512 checksum was compared with the published .sha512 file, and it was unzipped into a working directory. Every command on this page that shows output was run from that distribution with java -jar tika-app-4.1.0.jar on Java 25 (Oracle JDK 25.0.2) on macOS, and the output is copied from the terminal, shortened only where marked. The option semantics were read from the 4.1.0 source of TikaCLI, AsyncHelper and the tika-async-cli module (TikaAsyncCLI, PluginsWriter) at the 4.1.0 Git tag. The sample files are small stand-ins written for this section: a one-heading manuscript.docx (title The Lighthouse Keeper, author Ana Torres), a one-page catalogue.pdf (785 bytes), the same PDF renamed to renamed-invoice.png, a password-protected members-only.pdf, a windows-1252 legacy-catalogue.txt, a tiny novel.epub, a Spanish reviews-es.html, a French reseñas-fr.txt and publisher-email.eml, an e-mail that carries samples.zip. The GUI was not opened for this page (see The GUI).

What tika-app is

tika-app is a Maven module and a release artifact. Its main class, org.apache.tika.cli.TikaCLI, wraps the same components the Java pages of this section use: a TikaLoader built from a configuration file, an AutoDetectParser, a ParseContext and a content handler chosen by an option. Since Tika 4.0 it also wraps PipesForkParser (fork mode) and the Tika Pipes AsyncProcessor (pipes mode). In short, it is a convenient way to see what Tika will do with a file before you write code, to script one-off extractions and, in pipes mode, to run a batch.

It runs in three modes. The official page names them standard, GUI and Tika Pipes. Fork mode is an option of the standard mode.

Mode What it does How you get it

Standard

Parses one or more files, URLs or standard input in the CLI JVM and writes the result to standard output.

A file, a URL, - or nothing on standard input, with output options.

Standard + fork

Same output, but the parse runs in a forked JVM through PipesForkParser, so a crash, an OutOfMemoryError or a hang cannot take the CLI down.

Add -f or --fork.

GUI

A Swing window. Drop a file on it and look at its metadata, text, XHTML and recursive JSON.

-g or --gui, or no arguments and nothing on standard input.

Tika Pipes

Processes every file under a directory (or a file list, or any configured pipes iterator) in forked JVMs and writes one output file per input.

Two directories, -i / -o, -z / -Z, --fileList, -a, or a single .json pipes configuration.

The mode is picked from the arguments before any option is applied. The following flow is how TikaCLI.main in 4.1.0 decides (help first, then the pipes test, then the standard per-argument loop).

flowchart TD A[java -jar tika-app.jar args] --> B{-? or --help anywhere?} B -- yes --> H[print usage and exit] B -- no --> C{pipes trigger?} C -- "two dirs, a single .json, -i, -o, -z, -Z, --extract, --fileList, -a" --> P[Tika Pipes mode: banner on stderr, AsyncProcessor, forked JVMs] C -- no --> D{any arguments?} D -- none --> E{data on stdin within 0.1 s?} E -- yes --> S[standard mode on stdin] E -- no --> G[GUI] D -- yes --> L[standard mode: options and files processed left to right] L --> F{-f or --fork set?} F -- yes --> K[parse in a forked JVM through PipesForkParser] F -- no --> I[parse in the CLI JVM]

Source: Apache Tika 4.1.x, Tika Command Line Interface and the 4.1.0 source of TikaCLI.java.

Installing the zip distribution

Tika 4.x ships tika-app as a zip, not as the single fat jar of the 1.x to 3.x lines. The jar inside the zip is a thin launcher: its manifest has a Class-Path that lists the jars in the adjacent lib/ directory, and pipes mode loads its fetcher and emitter plugins from the adjacent plugins/ directory. The zip has no top-level directory, so unzip it into one.

curl -O https://archive.apache.org/dist/tika/4.1.0/tika-app-4.1.0.zip
curl -O https://archive.apache.org/dist/tika/4.1.0/tika-app-4.1.0.zip.sha512
shasum -a 512 tika-app-4.1.0.zip    # compare with the content of the .sha512 file
cat tika-app-4.1.0.zip.sha512

unzip -q -d tika-app-4.1.0 tika-app-4.1.0.zip
ls tika-app-4.1.0

Output (the two checksum lines were identical and are shortened here):

e8ffd4b85f08b2c9...25487c8745d  tika-app-4.1.0.zip
e8ffd4b85f08b2c9...25487c8745d
LICENSE  NOTICE  lib  plugins  tika-app-4.1.0.jar

What is inside (4.1.0):

Entry Content

tika-app-4.1.0.jar

TikaCLI, the GUI, the default single-file configuration and a log4j2.xml. Its manifest declares Java-Version: 17 and a Class-Path of lib/... entries.

lib/

110 jars, about 57 MB: tika-core, every module of the standard parser package, tika-langdetect-charsoup, tika-vlm, tika-inference, tika-async-cli, the pipes core, POI, PDFBox, Bouncy Castle and the rest.

plugins/

The file-system pipes plugin (tika-pipes-file-system-4.1.0.zip and its unpacked directory), which pipes mode uses to read the input directory and write the output directory.

The Apache license and notices.

The Class-Path entries are resolved relative to the jar, not to the current directory, so java -jar /opt/tika-app-4.1.0/tika-app-4.1.0.jar works from any working directory. All the examples on this page were run that way from a directory that held the sample files. The jar on its own does not work. Copied out of the distribution it fails before reading any argument:

cp tika-app-4.1.0/tika-app-4.1.0.jar /some/other/dir/
java -jar /some/other/dir/tika-app-4.1.0.jar --version

Output:

Error: Unable to initialize main class org.apache.tika.cli.TikaCLI
Caused by: java.lang.NoClassDefFoundError: org/apache/tika/mime/MimeTypeException

This is the NoClassDefFoundError the 4.x FAQ and the CLI page describe. If pipes mode is started from an incomplete distribution, TikaCLI catches the error and prints an explanation (download the zip, run the jar from inside it); the standard mode fails in the JVM launcher, as above. The tika-app artifact on Maven Central is the same thin jar plus a POM with the dependencies, which is how the earlier pages of this section ran TikaCLI on a Maven-built classpath.

A shell alias keeps the commands short. The rest of the page writes tika for it:

alias tika='java -jar /opt/tika-app-4.1.0/tika-app-4.1.0.jar'
tika --version

Output:

Apache Tika 4.1.0

The JVM options go before -jar, as for any Java program: java -Xmx2g -jar tika-app-4.1.0.jar ... sets the heap of the CLI JVM in standard mode. The forked JVMs of fork mode and pipes mode get their own options through --fork-jvm-args and --Xmx, described below.

Source: Apache Tika, Download, Apache Tika 4.1.x, Tika Command Line Interface, Installation and Apache Tika 4.1.x, FAQ.

Logging and the convenience-defaults banner

Log lines go to standard error through Log4j 2, so standard output stays clean for redirection and pipes. The bundled log4j2.xml logs at INFO, and every standard-mode run without --config logs this notice first:

INFO  [main] 22:53:16,719 org.apache.tika.cli.TikaCLI As a convenience, TikaCLI has turned on several non-default features
as specified in tika-app/src/main/resources/tika-config-default-single-file.json.
See: TIKA-2374, TIKA-4017, TIKA-4354 and TIKA-4472).
This is not the default behavior in Tika generally or in tika-server.

The notice is accurate and worth reading. Without --config, tika-app loads a bundled configuration that turns on features the library and tika-server leave off. The file in the 4.1.0 jar is:

{
  "parsers": [
    { "default-parser": {} },
    { "pdf-parser": {
        "extractActions": true,
        "extractInlineImages": true,
        "accessCheckMode": "ALLOW_EXTRACTION_FOR_ACCESSIBILITY",
        "extractIncrementalUpdateInfo": true,
        "parseIncrementalUpdates": true } },
    { "ooxml-parser": {
        "includeDeletedContent": true,
        "includeMoveFromContent": true,
        "extractMacros": true } },
    { "office-parser": { "extractMacros": true } }
  ]
}

So tika-app shows PDF actions, inline images and incremental updates, and Word’s deleted and moved text and macros, by default. That is useful when you are inspecting a file, and it is the reason the same file can give a little more output in tika-app than in your own AutoDetectParser code. Pass --config= with your production configuration when you want to see exactly what your service will see. The pipes mode template has the same parser settings (see Defaults of pipes mode).

To keep only warnings and errors, point Log4j at your own file:

<?xml version="1.0" encoding="UTF-8"?>
<!-- quiet-log4j2.xml: only WARN and above, on standard error -->
<Configuration status="WARN">
  <Appenders>
    <Console name="stderr" target="SYSTEM_ERR">
      <PatternLayout pattern="%-5p %c{1} %m%n"/>
    </Console>
  </Appenders>
  <Loggers>
    <Root level="warn"><AppenderRef ref="stderr"/></Root>
  </Loggers>
</Configuration>
java -Dlog4j.configurationFile=quiet-log4j2.xml -jar tika-app-4.1.0.jar -t catalogue.pdf

Output (standard error was empty):

Bookshelf spring catalogue
Forty titles from independent publishers.

-v / --verbose does the opposite and raises the root logger to DEBUG (a -j -v run on manuscript.docx printed 43 DEBUG lines on standard error).

Source: Apache Tika 4.1.x, Tika-App Integration Testing (its known issue "INFO message on every default-config command") and Apache Log4j 2, Configuration.

Standard mode

In standard mode TikaCLI processes its arguments left to right. An option changes the state (the output type, the configuration, the password), and a file name, a URL or - parses that input with the current state and writes the result to standard output. Several inputs in one command are parsed one after the other and their outputs are concatenated.

The order matters in two ways. An option placed after the file name does not apply to it, and --config= must come before the first input (and before -g or -f, as the help says), because the configuration is loaded when the first input is parsed:

tika -d manuscript.docx -t novel.epub   # -d applies to the first file, -t to the second
tika novel.epub -t                      # -t comes too late: the default Markdown is printed

Output:

application/vnd.openxmlformats-officedocument.wordprocessingml.document
Chapter one
It begins at dusk.
# Chapter one

It begins at dusk.

Long options take two dashes and short options are one letter. In 4.1.0 an unknown option fails fast with exit status 1 and a hint, instead of being taken as a URL:

tika -input catalogue.pdf

Output (standard error, stack trace omitted):

Exception in thread "main" java.lang.IllegalArgumentException: Unknown option '-input'. Long-form flags require two dashes (try '--input' instead of '-input'). Run with --help for the full option list.

A missing file is still reported in an unhelpful way, because a name that is not an existing file is tried as a URL. The official integration-test page lists this as a known issue:

Exception in thread "main" java.net.MalformedURLException: no protocol: missing.pdf

Source: Apache Tika 4.1.x, Tika Command Line Interface, Standard-mode Options and Apache Tika 4.1.x, Tika-App Integration Testing.

Help, version and configuration options

Option Effect in 4.1.0

-?, --help

Prints the usage above. If it appears anywhere on the command line, nothing else runs.

-V, --version

Prints Apache Tika 4.1.0.

-v, --verbose

Raises the Log4j root level to DEBUG.

--config=<tika-config.json>

Loads this JSON configuration with TikaLoader instead of the bundled convenience defaults. Its parsers, detectors and parse-context sections apply, so for example parse-context.exception-reporting bounds the exception values of -j and -J output. A 3.x XML file is rejected; convert it first.

--convert-config-xml-to-json=<input.xml>

Converts the parsers section of a 3.x tika-config.xml to 4.x JSON on standard output, then exits. The Configuration page shows a full conversion and what it does not cover.

With --config=, the parse uses your configuration instead of the convenience defaults. The Bookshelf desk keeps one tika-config.json for the intake service and for its batch runs:

{
  // Bookshelf intake: shared by the desk CLI and the batch runs
  "parsers": [
    { "pdf-parser": { "sortByPosition": true, "extractInlineImages": false } },
    { "default-parser": { "exclude": ["executable-parser"] } }

    { "include-field-metadata-filter": {

  ],
  "parse-context": {
    "embedded-limits": { "maxDepth": 5, "maxCount": 200 },
    "timeout-limits":  { "totalTaskTimeoutMillis": 120000, "progressTimeoutMillis": 30000 }
  },
  "pipes": {
    "numClients": 2,
    "forkedJvmArgs": ["-Xmx768m"]
  }
}

Output formats

One option chooses what is written for each input. The last one given before the input wins.

Option Output Handler behind it

--md (default)

Markdown of the body. New in 4.x as the default (3.x defaulted to XHTML).

ToMarkdownContentHandler inside a BodyContentHandler

Fork mode

Fork mode is not a drop-in copy of standard mode in 4.1.0. Reading the source and running it showed these differences:

  • The output comes from a PipesForkParser result in CONCATENATE parse mode (or RMETA with -J), so -t uses the full text handler: the title from the <head> appears, with the blank lines, as above.

  • -T maps to the BODY handler, not to boilerpipe. -A, -d, -l and -y map to the IGNORE handler and print nothing useful; use them without -f.

  • --password= and TIKA_PASSWORD were not passed to the fork: -f --password=reader-pw -t members-only.pdf printed nothing, and -f -j showed tk:exception:container-exception with the "password is incorrect" error. The parse inside the fork also used its own defaults rather than the parsers of --config=, as far as the source shows (the fork configuration is built from the timeouts, JVM arguments, plugin directory and embedded limits only).

  • The result metadata includes tk:source-path with the absolute path of the input and tk:content-handler-type.

So use fork mode for what it is for (looking safely at one dangerous file) and pipes mode for batches. For production isolation inside a service, use PipesForkParser from Java (see Tika Pipes) or tika-server, whose parsing endpoints always fork.

Tika Pipes mode

Pipes mode is the batch mode of 4.x. It replaces the 1.x to 3.x tika-batch mode of tika-app (-bc, -numConsumers, -maxRestarts and the rest), which was removed with the tika-batch module. tika-app hands the arguments to the tika-async-cli module (TikaAsyncCLI), which writes a temporary tika-config.json from a template, merges your --config into it, applies the command-line overrides and runs an AsyncProcessor: a file-system pipes iterator lists the input files, a pool of forked JVMs parses them, and a file-system emitter writes one output file per input. The Tika Pipes page explains those roles; this section covers the command line.

How pipes mode is activated

tika-app 4.1.0 enters pipes mode when any of these holds (checked before anything else, except --help):

  • exactly two arguments and the first is an existing directory (tika in/ out/);

  • the last two arguments are an existing directory followed by a directory or a path that does not exist yet, with options in front;

  • a single argument ending in .json, which is read as a complete pipes configuration;

  • any of -i, --inputDir (in fact any argument starting with --input), -o, --outputDir (any argument starting with --output), --fileList, -z, -Z, --extract, --extract-dir, -a or --async.

When it switches, it prints a one-line banner on standard error, so you can tell which path ran:

tika-app: running in Tika Pipes mode (async dispatch via -a/--async); use --help for options.

Source: Apache Tika 4.1.x, Tika Command Line Interface, How Pipes mode is activated and the 4.1.0 TikaCLI.testForAsync source.

Parse mode CONTENT_ONLY: write only the content, no JSON wrapper and no metadata; the output extension follows the handler (.txt, .md, .html, .xml). Implies --concatenate.

--on-exists=<mode>

exception

What to do when an output file exists: exception, replace or skip. Also applied to a configured file-system-jsonl-reporter (skip becomes APPEND there).

-n, --numClients=<N>

2 (1 in the bare two-directory form)

Number of forked JVMs that parse in parallel. A pipes.numClients in --config is kept when -n is not given.

--Xmx=<size>

unset: heap auto-sized (-Xmx1g in the bare form)

-Xmx of each forked JVM, for example --Xmx=1g. Merged into pipes.forkedJvmArgs, replacing an existing -Xmx and keeping the other arguments. A long flag despite its look; there is no -X option.

-T, --timeoutMillis=<ms>

config or library default (30000 in the bare form)

Total task timeout per input. Sets parse-context.timeout-limits.totalTaskTimeoutMillis, merged into any timeout-limits of the config.

-c, --config=<file>

the built-in template

A tika-config.json merged over the template. Its top-level sections replace the template’s.

-p, --pluginsDir=<dir>

the distribution’s plugins/

Where the pipes plugins (fetchers, emitters, iterators) are loaded from.

-a, --async

n/a

Forces pipes mode. Redundant with any of the triggers above.

-z, --extract, -Z, --extract-dir=<dir>, --unpack-format, --unpack-mode, --unpack-include-metadata

off

Unpacking, see Unpacking attachments.

The bare-form defaults (one client, -Xmx1g, a 30-second task timeout) were read from the 4.1.0 TikaAsyncCLI source; the numClients=1 in the sizing line above confirms the client count. The other defaults are from the official CLI page and were confirmed by the runs below.

Some older notes list an --unpack pipes option. tika-app 4.1.0 has no option of that name: unpacking is -z / -Z with the --unpack-format, --unpack-mode and --unpack-include-metadata modifiers, which the 4.1.0 --help lists. The parse mode behind them is UNPACK, and the configuration section is unpack-config.

Re-runs, --on-exists and the exit status

Run the same command again and every emit fails, because the output files exist and the default is exception:

tika -i intake -o text-out --handler t --content-only
echo "exit status: $?"

Output (standard error, one of six messages shown, stack traces and paths shortened):

WARN  [pool-2-thread-1] 22:55:20,790 [fork] pipesClientId=0 org.apache.tika.pipes.core.server.EmitHandler emit exception
java.io.IOException: Output already exists (onExists=EXCEPTION, not overwritten): .../text-out/manuscript.docx.txt. Use an empty output dir, delete the file, or set onExists to REPLACE or SKIP.
INFO  [main] 22:55:22,047 tika.pipes Successfully finished processing 6 files in 9213 ms
exit status: 0

Two lessons. First, choose the policy: --on-exists skip resumes an interrupted batch (only missing outputs are written), --on-exists replace reprocesses everything. Second, the exit status is 0 and the summary says "Successfully finished" even though nothing was written. In pipes mode a per-file failure (a parse exception, a timeout, a crash of a fork, an emit failure) is recorded for that file and the batch continues; the command only fails for configuration and startup errors. A script must check the outputs, the log, or a configured reporter (the file-system-jsonl-reporter writes one status line per file), not just $?.

This run also shows that -n defaults to 2 outside the bare form: the warnings came from pipesClientId=0 and pipesClientId=1 without any -n.

Unpacking attachments

-z and -Z write the embedded files' bytes, not their text. Both run in pipes mode (parse mode UNPACK) and accept a directory or a single file. -Z extracts recursively; -z is documented as "direct attachments (depth 1)" and is implemented as an embedded depth limit of 2.

-z, --extract

Extract direct attachments.

-Z

Extract all attachments recursively.

--extract-dir=<dir>

Output directory for the bytes; the same as -o.

--unpack-format=<format>

REGULAR (default) or FRICTIONLESS (a Frictionless Data Package with datapackage.json).

--unpack-mode=<mode>

ZIPPED or DIRECTORY. DIRECTORY when --unpack-format=FRICTIONLESS is given without a mode.

--unpack-include-metadata

Metadata for every extracted file: a Frictionless package carries metadata.json anyway; this adds a .metadata.json sidecar per file to REGULAR zip output.

Memory, performance and robustness

  • JVM start-up dominates. Every standard-mode call starts a JVM and loads more than a hundred parsers: about 6 seconds for a tiny PDF here. Put several files in one call (tika -t a.pdf b.docx) or use pipes mode, which starts its forks once and reuses them.

  • Standard mode has no isolation. A parser bug, a zip bomb or an endless loop affects the CLI JVM itself. Set -Xmx before -jar, use -f for unknown files, and do not run standard mode on untrusted input in a loop.

  • Fork and pipes heap. Without --Xmx / --fork-jvm-args, each fork’s heap is sized from the machine’s memory (60 % in the fork-mode run above). With -n 4 on a shared host, set --Xmx so that n times the heap plus the parent fits.

  • Timeouts. Fork mode: --task-timeout and --progress-timeout. Pipes mode: -T for the total budget, and progressTimeoutMillis in the configuration for the stall detector.

  • Limits. The CLI defaults do not cap the output size (writeLimit: -1 in the pipes template, and unlimited embedded depth and count). Add output-limits and embedded-limits to your configuration, as described on the Robustness, Limits & Timeouts page.

  • Temporary files. Spooling and per-fork temp directories go to java.io.tmpdir (logged at start-up); point it at a volume with enough space for large batches with -Djava.io.tmpdir=... before -jar and in --fork-jvm-args.

Source: Apache Tika 4.1.x, Pipes, Performance and Isolation Trade-offs and Apache Tika 4.1.x, Robustness.

Pitfalls and security

  • Pinning. The CLI is in flux for 4.x. Pin the version (tika-app-4.1.0) in scripts and re-read --help when you upgrade.

  • Exit status in pipes mode. 0 even when every file failed; check outputs or a reporter.

  • Option order. --config= before the first file; pipes options before a positional input.

  • -T and -c mean different things in the two modes.

  • Convenience defaults. Standard mode and the pipes template turn on macro extraction, deleted Word text, PDF actions and incremental updates. That is right for inspection and forensics; for a public index, deleted text and macros may be content you do not want to publish. Use your own configuration.

  • Passwords on the command line are visible in process lists and shell history; prefer TIKA_PASSWORD from a secret store, and remember that fork mode did not pass it in 4.1.0.

  • URLs. Passing a URL makes tika-app fetch it. Do not build tika-app command lines from untrusted strings, and quote file names (a file named -input is taken as an option unless it exists).

  • Extracted names are untrusted. Original names in -J output and datapackage.json come from the documents.

  • Hostile files. The CLI parses with the same parsers as the library and has the same exposure to parser vulnerabilities (for example CVE-2025-54988 / CVE-2025-66516 in the PDF module before 3.2.2). Keep the distribution current; the Security page covers the threat model.
