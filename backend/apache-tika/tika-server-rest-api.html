Tika Server (REST API)

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

Baseline date: 2026-10-12. This page was written against Apache Tika 4.1.0 (the latest release on Maven Central on that date) with the 3.3.x differences noted, Java 21 and later for the examples (Tika 4.x needs Java 17), Spring Boot 4.x on Spring Framework 7 and the Docker image apache/tika:4.1.0 (pin apache/tika:4.1.0-1). tika-server is Tika as an HTTP service: you PUT a document and get back its text, its metadata, its media type, its language or its embedded files. In 4.x the server changed more than any other part of Tika. Every parsing request now runs in a forked JVM through Tika Pipes, so a parser crash or an out-of-memory error kills one fork instead of the server, and a saturated server says so with 429 Too Many Requests instead of just getting slower. The price is that you have to size the fork pool (pipes.numClients) yourself, and that several 3.x endpoints, headers and flags are gone.

This page covers starting the server, every endpoint with real output, PUT versus multipart POST, presets, per-request configuration, the batch endpoints, error handling, the fork pool, TLS, Prometheus metrics, clients in Java, curl and Python, and the migration from 3.x.

Related pages: Tika App (Command Line & GUI) (the same parsing from a shell), Tika gRPC (the other network front end), Docker & Kubernetes Deployment (images, Compose and Kubernetes sizing), Tika Pipes (the machinery underneath the server), Robustness, Limits & Timeouts (the limits and timeout model the forks enforce), Security (why the server is not a security boundary) and Configuration (tika-config.json and TikaLoader).

Everything on this page that shows output was run for real: the tika-server-standard-4.1.0.zip from https://downloads.apache.org/tika/4.1.0/ (SHA-512 checked) was started on Java 25 bound to 127.0.0.1 only, on a non-default port (19998, metrics on 19404), and called with curl and with the two Java clients below. What tika-server is, and what it is not

tika-server is a JAX-RS application (Apache CXF on Jetty 12 in 4.1.0) packaged as the tika-server-standard distribution. It wraps the same AutoDetectParser, detectors, metadata and content handlers you use from Java, and exposes them as HTTP resources. Two Maven modules make it up: tika-server-core (the resources, the CLI, the pipes integration, TLS and metrics) and tika-server-standard (the distribution with tika-parsers-standard-package and the XMP resource). The official guidance in the 4.x docs is to consider a service first: running parsers in your own JVM opts you out of the process isolation that is Tika’s real defence against hostile or broken files.

What it is not:

  • Not a security boundary. It does no authentication or authorization. The official server page puts it bluntly: "trusted callers only". Put it on a private network or behind a gateway that authenticates callers. See Security.

  • Not a layout engine. It returns the same text, Markdown, XHTML and metadata as the library, with the same limits (no table or reading-order recovery). See Content Handlers & Output Formats.

  • Not a queue. /async accepts a batch and processes it in the background, but results go to an emitter, not back to the caller. For durable batch work see Tika Pipes.

How a request flows: client, server, forked JVM

The parsing endpoints (/tika, /rmeta, /meta, /unpack, /detect, and /pipes when enabled) share one pool of forked JVMs. The diagram follows one PUT /rmeta/text through the server, including the two failure answers that matter most to a client: 429 (the pool was busy, nothing failed) and 503 (a fork died on this document).

sequenceDiagram autonumber participant C as Client participant S as tika-server JVM participant P as Fork pool (numClients) participant F as Forked parse JVM C->>S: PUT /rmeta/text with the document bytes S->>S: maxRequestSizeBytes check, else 413 plain text S->>S: body up to maxInlineBytes kept in memory, larger bodies spooled to a temp file S->>P: borrow a fork, waiting up to maxWaitForClientMillis alt no fork free within the wait P-->>S: CLIENT_UNAVAILABLE_WITHIN_MS S-->>C: 429 Too Many Requests, Retry-After = wait in seconds else a fork is free P-->>S: fork handle S->>F: FetchEmitTuple over the IPC channel F->>F: detect, parse, apply limits, metadata filters and timeouts alt parse completed F-->>S: status PARSE_SUCCESS, PARSE_SUCCESS_WITH_EXCEPTION or PARTIAL_TIMEOUT and the metadata list S-->>C: 200 OK with the JSON list (raw /tika endpoints answer 422 if the document threw) else fork timed out, ran out of memory or crashed F--xS: fork killed or exits S->>P: start a replacement fork S-->>C: 503 Service Unavailable, Retry-After 5, JSON status TIMEOUT, OOM or UNSPECIFIED_CRASH end S->>P: return the fork to the pool end

  1. Request-size check. A request filter rejects a body over maxRequestSizeBytes (default 1 GiB) with a plain-text 413, for a declared Content-Length and for chunked bodies alike, before any parsing starts.

  2. Inline or spooled. A body at or below pipes.maxInlineBytes (default 10 MB) travels inside the request to the fork; a larger body is written to a private temp directory that the fork reads through an internal fetcher. The startup log shows these internal fetchers (__tika-server and __unpack); you never name them yourself.

  3. Borrow a fork. The pool holds exactly numClients forks. If none frees up within pipes.maxWaitForClientMillis (default 60 s) the request ends with 429 and Retry-After set to that wait in whole seconds (minimum 1).

  4. Parse in the fork. The fork runs AutoDetectParser under the parse-context limits and timeouts of the server’s configuration. See Robustness, Limits & Timeouts.

  5. Map the result. PipesResult.RESULT_STATUS becomes an HTTP status (see Error responses and status codes). A per-document parse exception is not a fork failure: /rmeta and /tika/json answer 200 with the exception in tk:exception:container-exception.

  6. Fork failure. A timed-out, out-of-memory or crashed fork is replaced, the server stays healthy, and the client gets 503 with Retry-After: 5. Retrying the same bytes will usually fail the same way.

Source: Tika Server, Apache Tika 4.1.x and the PipesParsingHelper source in tika-server on GitHub.

/rmeta is the endpoint to build on. Presets: named configuration without /config

A preset is a named, operator-vetted piece of parse-context configuration that callers select by name, by inserting preset/{name} directly after the resource root. It is the 4.x answer to "different callers need different parser settings" without handing them arbitrary per-request configuration. Presets are new in 4.1.0 ("named server presets" in the release notes).

{
  "presets": {
    "thumbnail": true,
    "no-ocr": { "pages": { "text": "EXTRACT" } }
  }
}

Nothing is active unless the top-level presets key names it:

  • true activates a preset from the classpath catalog that ships with Tika. tika-pipes-core 4.1.0 ships two, thumbnail and render-thumbnail. Naming a catalog preset that does not exist fails startup.

  • An object defines a preset in place (and replaces a catalog preset of the same name wholesale).

  • false or null is an explicit no-op.

The server logs every active preset at startup, with the components it configures:

INFO  PresetRegistry preset 'thumbnail' active, callable by any client; configures [thumbnail-unpack-selector, pages, pdf-parser, emf-parser, wmf-parser, text-recognizers, inference, embedded-limits]
INFO  PresetRegistry preset 'no-ocr' active, callable by any client; configures [pages]
curl -T catalogue.pdf   http://localhost:9998/tika/preset/no-ocr/text
curl -T catalogue.pdf   http://localhost:9998/rmeta/preset/no-ocr/ignore
curl -T manuscript.docx http://localhost:9998/unpack/preset/thumbnail -o thumb.zip
curl -T manuscript.docx http://localhost:9998/tika/preset/missing/text
Bookshelf spring catalogue
Forty titles from independent publishers.

[{"pdf:docinfo:title":"Spring catalogue",...}]

HTTP/1.1 204 No Content        (the sample .docx has no stored thumbnail)
HTTP/1.1 404 Not Found         (unknown preset name)

The rules that make presets safe enough to expose:

  • A request selects exactly one preset, the preset routes take no config part, and a preset never combines with request-supplied configuration. A variant is another preset.

  • The preset routes do not require allowPerRequestConfig. The content is resolved in the fork from the server’s own configuration, at configuration trust, so a preset may bind components that /config input may not (detectors, embedded-document extraction, exception reporting) and raise timeouts above the per-request clamp.

  • Every active preset is resolved at startup, so a bad preset fails the server, not its first request.

  • Names are letters, digits, ., _ and -, at most 100 characters, and may not start with config. The /preset/ path segment gives a reverse proxy something to match: it can allow /rmeta/preset/ and block /rmeta/config entirely.

  • For the output format on a preset route, an explicit path segment wins; without one, a ContentHandlerFactory the preset binds decides, then the configuration’s, then Markdown.

  • /pipes and /async tuples can carry a top-level "preset": "name" field; an unknown name answers 400 with PRESET_NOT_FOUND.

An active preset is a public route: anyone who can reach the server can call it. Vet your own presets as you would allowPerRequestConfig (bounded pages and renders, no OCR unless the preset is about OCR, no raised timeouts).

Per-request configuration: allowPerRequestConfig and the /config endpoints

The /config endpoints (/tika/config, /tika/config/{text,html,xml,md,json}, /tika/config/json/{handler}, /rmeta/config, /rmeta/config/{handler}, /meta/config, /unpack/all/config) and a config part on POST /unpack take a caller-supplied parse-context fragment. They are off by default:

curl -i -X POST http://localhost:9998/tika/config/text \
  -F "file=@manuscript.docx" \
  -F 'config={"pages":{"text":"EXTRACT"}};type=application/json'
HTTP/1.1 403 Forbidden
Content-Type: text/plain;charset=iso-8859-1

Config endpoints are disabled. Set allowPerRequestConfig=true in server config.

There is no CLI flag. Turn it on in the server section, and the server logs a warning at startup that callers may now set any parser option, "including options that spawn external processes such as OCR":

{
  "server": {
    "allowPerRequestConfig": true
  }
}

With it on, the config part uses the top-level, self-configuring form: a component name as the key, not the server-config parsers array.

# PDF parser option for this request only
curl -X POST http://localhost:9998/tika/config/text \
  -F "file=@catalogue.pdf" \
  -F 'config={"pdf-parser":{"sortByPosition":true}};type=application/json'

# output limit for this request only, on /rmeta
curl -X POST http://localhost:9998/rmeta/config/text \
  -F "file=@manuscript.docx" \
  -F 'config={"output-limits":{"writeLimit":20}};type=application/json'

The /rmeta call returned the first 20 characters in tk:content and "tk:exception:write-limit-reached": "true". What the server refuses, as observed on 4.1.0:

# config={"parsers":[{"pdf-parser":{}}]}
HTTP/1.1 400 Bad Request
Could not resolve the request config: Component 'pdf-parser' (context key org.apache.tika.parser.Parser) may not be supplied via a request parseContext. Components of this type must be configured server-side in the Tika config, not at request time.

# config={"exception-reporting":{"level":"FULL"}}
HTTP/1.1 400 Bad Request
Could not resolve the request config: Component 'exception-reporting' (context key org.apache.tika.config.ExceptionReporting) may not be supplied via a request parseContext. ...

# config={"content-handler-factory":{...}}
HTTP/1.1 400 Bad Request
Could not resolve the request config: Unrecognized parse-context entry 'content-handler-factory'. Check for a typo; it does not match any registered component.

So a caller cannot swap in a parser or detector, cannot turn exception redaction back off, and cannot raise timeouts above the operator’s clamp. Naming the output format both in the path and in a content-handler-factory part is a 400 by design, so the response’s Content-Type cannot lie about its body.

Even with these guards, per-request configuration widens what anyone who can reach the server can do (the classic case is CVE-2015-3271, parsers pointed at attacker-chosen resources). Enable it only behind network controls, a reverse proxy or mutual TLS, and prefer presets. One more reason to be careful in 4.1.0: the same output-limits.writeLimit part sent to /tika/config/json/text with a PDF produced a 200 whose tk:exception:container-exception held a NullPointerException from WriteOutContentHandler, while /rmeta/config/text handled it cleanly. Set server-wide limits in parse-context rather than relying on per-request values.

About 15 seconds later (the /async pool started its own fork) manuscript.json and novel.json were in the output folder. Error responses and status codes

In 4.x every parsing endpoint reports a process-level failure with a JSON body that carries at least status, the PipesResult.RESULT_STATUS name, plus a message when one is available (3.x returned plain text such as Parse failed: TIMEOUT). Request-level problems that are detected before parsing (bad handler, bad tuple, disabled /config, body too large) still answer with short plain-text bodies.

HTTP status status values Meaning and what a client should do

200 OK

PARSE_SUCCESS, PARSE_SUCCESS_WITH_EXCEPTION, PARTIAL_TIMEOUT, EMIT_SUCCESS, …​

Success. On /rmeta and /tika/json a per-document exception is embedded in tk:exception:container-exception (or tk:exception:embedded-exception per embedded document). Read those keys.

204 No Content

none

/unpack with nothing to unpack, or /unpack/preset/thumbnail with no thumbnail.

400 Bad Request

FETCHER_NOT_FOUND, EMITTER_NOT_FOUND, PRESET_NOT_FOUND, or plain text

Malformed request: unknown handler, unknown tuple field, refused config component, oversized /async batch. Fix the request; never retry unchanged.

403 Forbidden

plain text

A /config endpoint or config part while allowPerRequestConfig is off.

404 Not Found

empty or plain text

Unknown path (including the removed 3.x paths), unknown preset, endpoint not enabled, or a missing /meta/{field}.

406 Not Acceptable

empty

An Accept header that the chosen path cannot produce, such as Accept: text/html on bare /tika.

413 Payload Too Large

plain text, or PAYLOAD_LIMIT_EXCEEDED

A body over maxRequestSizeBytes (plain text), or a parse result too big for the IPC channel (pipes.maxIpcPayloadBytes, JSON). Lower the output or split the input.

none (content in body)

Raw /tika endpoints, /meta/{field} and /unpack when the document threw. The raw body holds what was extracted; call /rmeta for the exception.

CLIENT_UNAVAILABLE_WITHIN_MS

The fork pool (or the /async queue) was full for the whole wait. Nothing failed. Wait Retry-After seconds and retry; a sustained rate means add capacity.

500 Internal Server Error

FAILED_TO_INITIALIZE, FETCH_EXCEPTION, EMIT_EXCEPTION, FETCHER_INITIALIZATION_EXCEPTION, EMITTER_INITIALIZATION_EXCEPTION

PARTIAL_TIMEOUT: success, but incomplete

When the total task deadline (totalTaskTimeoutMillis) runs out while a container’s embedded documents are still queued, the fork skips the ones not yet started and reports PARTIAL_TIMEOUT. That maps to 200 OK on every endpoint, with tk:exception:task-deadline-reached set (the TikaCoreProperties.TASK_DEADLINE_REACHED property) and whatever was extracted so far. Check for it if your index must know that a document is incomplete. The timeout-limits option throwOnDeadline makes the parse stop at once with an exception recorded in the container metadata, but in the pipes-backed server the status stays PARTIAL_TIMEOUT. A PARTIAL_TIMEOUT was not reproduced for this page; the timeout model is in Robustness, Limits & Timeouts.

Redact exception detail

By default exception detail is returned in full (FULL), and stack traces can contain the spooled file’s path, the source file name and fragments of the document, in error bodies and in tk:exception:* metadata of successful parses and /unpack zips. One operator setting governs every channel:

{
  "parse-context": {
    "exception-reporting": { "level": "MESSAGE_REDACTED", "maxLength": 2000 }
  }
}

MESSAGE_REDACTED keeps class names and frames but strips messages; REDACTED keeps class names only. With MESSAGE_REDACTED, the missing-file /pipes call above returned java.io.FileNotFoundException and the frames, without the path. A request cannot turn it off (the 400 shown earlier). It replaces the 3.x returnStackTrace option, which only ever covered error bodies.

pipes.numClients and the forked-process groups

numClients is the single most important number in a 4.x server, and the example configurations are not safe boilerplate. It does two jobs at once:

  • It caps concurrency. Each group holds exactly numClients forks. With all of them busy, the next request waits up to maxWaitForClientMillis and then gets 429. Undersize it and callers see 429 under normal load.

  • It sizes the forks' CPU view. Each fork gets -XX:ActiveProcessorCount computed from numClients and the host cores, so the forks do not each believe they own the machine. Oversize it and the forks starve each other, which shows up only as "the server got slower".

If you do not set it, the 4.1.0 source computes max(1, min(4, (cores - 2) / 2)): two cores are reserved for the server JVM and each fork gets at least two. On the 8-core machine used here that is 3. The startup line pipes-cpu-sizing: hostCores=8, numClients=2, parentReserved=2, autoCap=slice=3 shows the outcome for an explicit value.

There are two independent groups in one server:

Each group’s CPU auto-sizer cannot see the other, so enabling /async next to the sync endpoints (or leaving endpoints unset with allowPipes: true) can oversubscribe the host with no warning. Calling tika-server from Java

There is no official Java client for tika-server in 4.x, and you do not need one: the API is plain HTTP. The two clients below were compiled with --release 21 and run against the 4.1.0 server. The behaviour to copy is the status handling: retry 429 after Retry-After, do not loop on 503, treat 422 as partial content.

JDK HttpClient

package org.example.bookshelf;

import java.io.IOException;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.file.Path;
import java.time.Duration;

public class TikaHttpClientExample {

    private static final URI TIKA = URI.create(
            System.getenv().getOrDefault("TIKA_URL", "http://127.0.0.1:9998"));
    private static final int MAX_ATTEMPTS = 5;

    private final HttpClient http = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(5))
            .build();

    /** PUTs one file to /tika/text and returns the body text. */
    public String extractText(Path file) throws IOException, InterruptedException {
        HttpRequest request = HttpRequest.newBuilder(TIKA.resolve("/tika/text"))
                .timeout(Duration.ofMinutes(5))
                .header("Content-Disposition",
                        "attachment; filename=" + file.getFileName())
                .PUT(HttpRequest.BodyPublishers.ofFile(file))
                .build();

        for (int attempt = 1; ; attempt++) {
            HttpResponse<String> response =
                    http.send(request, HttpResponse.BodyHandlers.ofString());
            int status = response.statusCode();
            switch (status) {
                case 200:
                    return response.body();
                case 204:
                    return "";
                case 422:
                    // the document threw, but this is what was extracted before it did
                    System.err.println("partial parse of " + file);
                    return response.body();
                case 429:
                    if (attempt == MAX_ATTEMPTS) {
                        throw new IOException("tika-server still busy after "
                                + attempt + " attempts");
                    }
                    long waitSeconds = response.headers()
                            .firstValueAsLong("Retry-After").orElse(2L);
                    Thread.sleep(Duration.ofSeconds(waitSeconds));
                    break;
                case 503:
                    // a fork crashed, ran out of memory or timed out on THIS document:
                    // do not loop on it, hand it to a dead-letter queue instead
                    throw new IOException("fork failed on " + file + ": " + response.body());
                default:
                    throw new IOException("HTTP " + status + " for " + file + ": "
                            + response.body());
            }
        }
    }

    public static void main(String[] args) throws Exception {
        TikaHttpClientExample client = new TikaHttpClientExample();
        for (String name : args) {
            System.out.println("--- " + name);
            System.out.println(client.extractText(Path.of(name)).strip());
        }
    }
}

package org.example.bookshelf;

import java.nio.file.Path;
import java.time.Duration;

import org.springframework.core.io.FileSystemResource;
import org.springframework.http.ContentDisposition;
import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.http.client.JdkClientHttpRequestFactory;
import org.springframework.util.LinkedMultiValueMap;
import org.springframework.util.MultiValueMap;
import org.springframework.web.client.RestClient;

public class TikaRestClientExample {

    private final RestClient tika;

    public TikaRestClientExample(String baseUrl) {
        JdkClientHttpRequestFactory factory = new JdkClientHttpRequestFactory();
        factory.setReadTimeout(Duration.ofMinutes(5));
        this.tika = RestClient.builder()
                .baseUrl(baseUrl)
                .requestFactory(factory)
                .build();
    }

    /** PUT the raw bytes to /rmeta/text: one JSON object per document, embedded ones included. */
    public String recursiveMetadata(Path file) {
        return tika.put()
                .uri("/rmeta/text")
                .contentType(MediaType.APPLICATION_OCTET_STREAM)
                .headers(h -> h.setContentDisposition(ContentDisposition.attachment()
                        .filename(file.getFileName().toString()).build()))
                .body(new FileSystemResource(file))
                .retrieve()
                .onStatus(s -> s.value() == HttpStatus.TOO_MANY_REQUESTS.value(), (req, res) -> {
                    String retryAfter = res.getHeaders().getFirst("Retry-After");
                    throw new IllegalStateException("busy, retry after " + retryAfter + "s");
                })
                .onStatus(s -> s.value() == HttpStatus.SERVICE_UNAVAILABLE.value(), (req, res) -> {
                    throw new IllegalStateException("fork failed on " + file);
                })
                .body(String.class);
    }

    /** Multipart POST to /rmeta/form/text: the browser-style upload, no per-request config. */
    public String recursiveMetadataMultipart(Path file) {
        MultiValueMap<String, Object> parts = new LinkedMultiValueMap<>();
        parts.add("file", new FileSystemResource(file));
        return tika.post()
                .uri("/rmeta/form/text")
                .contentType(MediaType.MULTIPART_FORM_DATA)
                .body(parts)
                .retrieve()
                .body(String.class);
    }

    public static void main(String[] args) {
        TikaRestClientExample client = new TikaRestClientExample(
                System.getenv().getOrDefault("TIKA_URL", "http://127.0.0.1:9998"));
        Path email = Path.of(args[0]);
        String put = client.recursiveMetadata(email);
        String multipart = client.recursiveMetadataMultipart(email);
        System.out.println("PUT  /rmeta/text      -> " + put.length() + " chars, "
                + (put.split("\"tk:embedded-depth\"").length - 1) + " documents");
        System.out.println("POST /rmeta/form/text -> " + multipart.length() + " chars");
        System.out.println(put.substring(0, Math.min(160, put.length())));
    }
}

Behavioural changes a client will notice

  • Capacity is explicit. 3.x parsed in the request thread with no concurrency cap; 4.x has exactly numClients forks. Load that 3.x absorbed slowly now produces 429. Handle it, and size the pool.

  • Status codes. UNSPECIFIED_CRASH, TIMEOUT and OOM are 503, not 500; unknown fetchers are 400; error bodies are JSON. Clients that parsed Parse failed: ... text must switch to the status field.

  • Metadata keys. Responses use the tk: namespace (tk:content, tk:resource-name, tk:parsed-by). Configure LegacyKeyMigrationFilter as a metadata filter on the server during a migration window if clients cannot change at once; see Metadata.

  • Startup cost. Forks load the parsers on first use, so the first request after a start is slow; warm up before adding the instance to a load balancer.

Book-era context: Tika in Action and remote parsing

Tika in Action (written for Tika 1.0) runs Tika from the tika-app jar, including a --server mode that streamed results over a raw socket, and treats remote parsing as an advanced topic in its chapter on scaling. Both ideas survived in a very different form. The socket server and the network-client mode of tika-app were removed (see Tika App (Command Line & GUI)); tika-server became a separate JAX-RS module in 1.x, a separate distribution in 2.x, and a pipes-backed service with process isolation in 4.x. The book’s advice that a misbehaving parser should not take down your application is now the server’s default architecture.

Pitfalls

  • Running the Maven Central jar. java -jar tika-server-standard-4.1.0.jar outside the zip fails with NoClassDefFoundError. Use the zip or the Docker image.

  • Copying numClients from an example. It is both your concurrency ceiling and your CPU and memory footprint. Size it from cores and heap per fork, then watch busy_429.

  • Treating 429 and 503 the same. 429 means retry later; 503 means this document broke a fork. Retrying a 503 in a tight loop is a denial of service against yourself.

  • Exposing the port. The Docker image listens on 0.0.0.0 inside the container; publish with -p 127.0.0.1:9998:9998 or keep it on a private network, and authenticate in front. allowPipes and allowPerRequestConfig are defence in depth, not access control.

  • Leaving exception detail at FULL. Error bodies and tk:exception:* values carry server paths and document text. Set exception-reporting to MESSAGE_REDACTED when callers are less trusted than operators.

  • Assuming /language is isolated. It runs in the server JVM. Remove it from endpoints if you do not need it.

  • Expecting old headers to work. writeLimit, X-Tika-OCR... and friends are silently ignored; the request succeeds with the operator’s settings.

  • Forgetting plugin-roots with /async. The server refuses to start on 4.1.0 without it.

  • Trusting tk:resource-name. Some parsers overwrite it (the e-mail parser used the subject). Keep the upload name yourself.

  • Ignoring PARTIAL_TIMEOUT. It is a 200. Check tk:exception:task-deadline-reached before marking a document fully indexed.

  • Accept headers left over from 3.x. Accept: text/html on bare /tika is a 406 in 4.x.

  • Probing /metrics. Probe /version or /status on the parse port instead.
