Observability

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

A resilience library that nobody can see working is a liability: a breaker that stays open for an hour, a retry that quietly triples the load on a dependency, or a bulkhead that is always full all look like "the service is slow" until somebody reads the right number. Resilience4j reports through four channels: Actuator endpoints (JSON, for a person with curl), health indicators (for the platform), Micrometer meters (for Prometheus and Grafana) and events (for logs and your own code). This page covers all four for every module, shows what each one looks like in a running service, and ends with alert rules and the tracing-context question that the thread-pool bulkhead raises. It was written against Resilience4j 2.4.0, Spring Boot 4.1.x, Spring Framework 7.0.x and Java 21 and verified on 4 October 2026. Every sample on the page is output from a sample Spring Boot 4.1.1 application running on JDK 21, and the same run was repeated on Spring Boot 3.5.16 with resilience4j-spring-boot3: the endpoint JSON, the HTTP status codes and every Prometheus metric name were identical. The Boot 3 differences are in the section What changed recently.

The base setup of Actuator, Micrometer, the Prometheus registry and Micrometer Tracing is not repeated here; it is in Metrics and Observability. This page adds only what is specific to Resilience4j. The running example is Bookshelf in the package com.example.bookshelf: a pricing circuit breaker, an isbn retry, rate limiter and semaphore bulkhead, a reviews time limiter, a recommendations thread-pool bulkhead and a search timer. The sample outputs use the same instance names, and the code in the sample application was identical apart from the package name.

The Bucket4j counterpart of this page (bucket listeners, Micrometer meters and backend health) is Bucket4j: Observability.

The four channels

Channel What you get Who reads it Switched on by

Actuator endpoints

The current state of every instance and the last 100 events per instance, as JSON.

A person debugging, a script, a runbook.

management.endpoints.web.exposure.include plus the module on the classpath.

Health indicators

circuitBreakers and rateLimiters components in /actuator/health.

A load balancer, a Kubernetes readiness probe, a status page.

management.health.circuitbreakers.enabled and management.health.ratelimiters.enabled, plus registerHealthIndicator per instance.

Micrometer meters

Gauges, counters and timers per instance, with the tags name and kind or state.

Prometheus, Grafana, alerting.

On by default when a MeterRegistry bean exists; resilience4j.<module>.metrics.enabled switches a module off.

Events

One object per call outcome, state transition or rejection, delivered to a listener.

Logs, audit trails, your own counters.

Always available on every instance through getEventPublisher().

The figure shows how the first three channels connect. Metrics flow from the instances through the module’s metrics publisher into the MeterRegistry, over the Actuator Prometheus endpoint to Prometheus, and from there to Grafana and Alertmanager. Events and health take their own route and do not go through Micrometer at all.

Dependencies and the minimum configuration

With the starter from Getting Started in place, observability needs two more things: the Actuator starter, which also brings Micrometer, and a Micrometer registry for the monitoring system. For Prometheus that is micrometer-registry-prometheus.

The two dependencies that turn the endpoints and the meters on
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>

Source: Spring Boot: Metrics and Micrometer: Prometheus. The Actuator starter is not a transitive dependency of the Resilience4j starters (their POMs pull in Micrometer and Spring only at runtime scope), so it has to be added explicitly. Without it the application starts, the annotations work and there are no endpoints and no meters.

Actuator endpoints are not exposed over HTTP by default, apart from health. The next block exposes the twelve Resilience4j endpoints that this page walks through, the Prometheus scrape endpoint and health, shows health details, and moves the whole management API onto its own port. The samples below were produced with the same endpoints, but on the application port, with show-details: always and without the access line, so that every request could be made without credentials.

The Bookshelf monitoring configuration (application.yml)
management:
  server:
    port: 8081                       # management API on its own port, not reachable through the gateway
  endpoints:
    web:
      exposure:
        include: >-
          health,prometheus,
          circuitbreakers,circuitbreakerevents,
          retries,retryevents,
          ratelimiters,ratelimiterevents,
          bulkheads,bulkheadevents,
          timelimiters,timelimiterevents,
          timers,timerevents
  endpoint:
    health:
      show-details: when-authorized
    circuitbreakers:
      access: read-only              # no write operation unless an ops profile turns it on
  health:
    circuitbreakers:
      enabled: true
    ratelimiters:
      enabled: true
  metrics:
    tags:
      application: bookshelf         # the Grafana dashboard filters on this label

Source: Spring Boot: Endpoints. Putting the management API on its own port was run: with management.server.port=0 and the same endpoints exposed, /actuator/circuitbreakers answered 404 on the application port and 200 on the management port. The access property is explained in the section The circuitbreakers write operation, and the individual keys of resilience4j.* are in Spring Boot Configuration.

The Actuator endpoints

Each module that is on the classpath contributes a pair of endpoints: one that lists the instances and one that returns the buffered events. Every endpoint id below is the literal @Endpoint(id = …​) of the v2.4.0 resilience4j-spring-boot4 sources, and an endpoint exists only when it is exposed (@ConditionalOnAvailableEndpoint).

Endpoint id Paths under /actuator What it returns

circuitbreakers

GET /circuitbreakers, POST /circuitbreakers/<name>

Every breaker with its state, rates and counters. The POST is the write operation.

circuitbreakerevents

GET /circuitbreakerevents, /circuitbreakerevents/<name>, /circuitbreakerevents/<name>/<type>

Buffered events of all breakers, of one breaker, or of one breaker filtered by event type.

retries, retryevents

GET /retries, GET /retryevents[/<name>[/<type>]]

The names of the retries, and their buffered events.

ratelimiters, ratelimiterevents

GET /ratelimiters, GET /ratelimiterevents[/<name>[/<type>]]

The names of the rate limiters, and their buffered events.

bulkheads, bulkheadevents

GET /bulkheads, GET /bulkheadevents[/<name>[/<type>]]

The circuitbreakers write operation

The circuitbreakers endpoint is the only Resilience4j endpoint with a write operation. POST /actuator/circuitbreakers/<name> with a JSON body {"updateState": "<value>"} changes the state of that breaker. The operation accepts exactly three values: CLOSE (transitionToClosedState()), FORCE_OPEN (transitionToForcedOpenState()) and DISABLE (transitionToDisabledState()). The state machine side of these transitions is on CircuitBreaker.

Forcing a breaker open during an incident, then closing it again
curl -s -X POST http://localhost:8081/actuator/circuitbreakers/pricing \
     -H 'Content-Type: application/json' \
     -d '{"updateState":"FORCE_OPEN"}'
curl -s -X POST http://localhost:8081/actuator/circuitbreakers/pricing \
     -H 'Content-Type: application/json' \
     -d '{"updateState":"CLOSE"}'
{"circuitBreakerName":"pricing","currentState":"FORCED_OPEN","message":"pricing state has been changed successfully"}
{"circuitBreakerName":"pricing","currentState":"CLOSED","message":"pricing state has been changed successfully"}

Source: the output of the sample run and the CircuitBreakerEndpoint at v2.4.0. DISABLE answered "currentState":"DISABLED". Three things about the operation surprised in the run, and each is a reason to treat it carefully:

  • Any other value is rejected before the method runs: OPEN and HALF_OPEN both returned 400 Bad Request, because the body is bound to an enum with only those three constants. There is no way to open a breaker "naturally" or to force it half-open over HTTP.

  • The name is not checked. Posting {"updateState":"CLOSE"} to /actuator/circuitbreakers/nosuch returned 200 with "currentState":"CLOSED" and created a breaker named nosuch with the default configuration, which then appeared in /actuator/circuitbreakers, in the health indicator if the default config registers it, and as a new set of series in Prometheus. A typo in a runbook command creates a permanent, empty instance.

  • A body-less request is rejected with 415 Unsupported Media Type; the Content-Type: application/json header is required.

FORCE_OPEN and DISABLE change production behaviour with one request: a forced-open breaker rejects every call until somebody posts CLOSE, and a disabled breaker lets everything through and stops recording. That makes the endpoint a control plane and not a monitoring page, so it needs three layers of protection.

Layer 1: take the write operation away

Since Spring Boot 3.4 the access level of an endpoint is set with management.endpoint.<id>.access, which replaces the older enabled property. The values are none, read-only and unrestricted. With read-only, the GET stays and the POST is not registered.

Making the circuitbreakers endpoint read-only
management:
  endpoint:
    circuitbreakers:
      access: read-only

Source: Spring Boot: Endpoints (endpoint access). In the run, with access=read-only, GET /actuator/circuitbreakers returned 200 and the same POST returned 404: the write operation does not exist at all. Keep read-only as the default, and turn it to unrestricted only in a profile that operators use, if at all.

Layer 2: keep the management API off the public network

management.server.port (shown earlier) moves every endpoint to a second port, and management.server.address binds it to one interface. In the run the application port answered 404 for /actuator/circuitbreakers and the management port answered 200. The gateway, the ingress and the public load balancer should route only to the application port; reach the management port through a Service that is not exposed, a port-forward, or a network policy that admits only the monitoring namespace.

Layer 3: authenticate and authorize

Even on a private port the write operation should need a role, and a monitoring user (Prometheus, Grafana) should not have it. A Spring Security filter chain that matches the Actuator endpoints can express "everybody authenticated reads, only ops writes". The password comes from the environment and is never in the file.

Security rules for the Actuator endpoints (Spring Security 7, Spring Boot 4)
package com.example.bookshelf.config;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.security.autoconfigure.actuate.web.servlet.EndpointRequest;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.annotation.Order;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
class ActuatorSecurityConfig {

    @Bean
    @Order(1)
    SecurityFilterChain actuatorSecurity(HttpSecurity http) throws Exception {
        return http
            .securityMatcher(EndpointRequest.toAnyEndpoint())
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(EndpointRequest.to("health")).permitAll()
                .requestMatchers(HttpMethod.POST, "/actuator/circuitbreakers/**").hasRole("OPS")
                .anyRequest().hasAnyRole("OPS", "OBSERVER"))
            .httpBasic(Customizer.withDefaults())
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .csrf(csrf -> csrf.disable())      // stateless, header-authenticated management API
            .build();
    }

    @Bean
    UserDetailsService actuatorUsers(@Value("${ACTUATOR_PASSWORD}") String password) {
        var encoder = PasswordEncoderFactories.createDelegatingPasswordEncoder();
        return new InMemoryUserDetailsManager(
            User.withUsername("ops").password(encoder.encode(password)).roles("OPS").build(),
            User.withUsername("grafana").password(encoder.encode(password)).roles("OBSERVER").build());
    }
}

Source: Spring Boot: Endpoints (securing HTTP endpoints). In the run, with ACTUATOR_PASSWORD supplied as a system property: /actuator/health was reachable without credentials, /actuator/circuitbreakers returned 401 without them, the grafana user got 200 for GET /actuator/circuitbreakers, /actuator/retries and /actuator/prometheus, the same user got 403 for the POST, and the ops user got 200 with "currentState":"FORCED_OPEN". Two details matter. The POST rule has to be written with HttpMethod.POST and a path matcher, because EndpointRequest.to("circuitbreakers") matches the endpoint for every method. And the example uses one shared secret for two users only to stay short; in production give each consumer its own credential, from a secret store, and prefer a token-based scheme (OAuth2 resource server, mutual TLS) over basic authentication. The Prometheus scrape configuration later on this page shows the monitoring user’s password being read from a mounted file.

On Spring Boot 3 the matcher class is org.springframework.boot.actuate.autoconfigure.security.servlet.EndpointRequest; the rest of the example is unchanged.

There is no bulkhead, retry or time limiter indicator: those modules have no "unhealthy" condition that a health check could meaningfully report. Health groups, and keeping the indicators out of liveness

Spring Boot health groups select which indicators answer a given URL: /actuator/health/<group>. They are the right way to use Resilience4j’s indicators. A custom group gives an operator or a status page the dependency view without touching what the platform probes.

A dependency group, and the probe groups left alone
management:
  endpoint:
    health:
      group:
        dependencies:
          include: circuitBreakers,rateLimiters
          show-details: never
        readiness:
          include: readinessState

Source: Spring Boot: Health groups. In the run, /actuator/health/dependencies with pricingStrict open answered 503 {"status":"DOWN"} and the readiness group answered 200.

The liveness probe answers one question: "is this process stuck so badly that restarting it is the cure?" An open breaker means that a dependency is unhealthy, and restarting the caller does not fix a dependency. Worse, every replica of bookshelf-service sees the same open breaker at about the same time, so a liveness probe that includes circuitBreakers makes Kubernetes restart the whole deployment, which empties the breaker state, reconnects every pool at once and adds a thundering herd to the outage. In the run, a configuration that added circuitBreakers to the liveness group made /actuator/health/liveness answer 503 as soon as a strict breaker opened. Keep circuitBreakers and rateLimiters out of liveness, leave readiness with readinessState, and add the indicators to readiness only for a dependency that the service genuinely cannot serve without (and then with allowHealthIndicatorToFail), accepting that the instance leaves the load balancer while the breaker is open. The probe mechanics, timings and the Spring Boot group configuration are covered in Health Probes and Lifecycle.

Controlling the meters

  • Switch a module’s meters off: resilience4j.circuitbreaker.metrics.enabled=false (likewise retry, ratelimiter, bulkhead, thread-pool-bulkhead, timelimiter). In the run, resilience4j.retry.metrics.enabled=false removed every resilience4j_retry_* series and left the others.

  • Add tags to every instance of a module: resilience4j.<module>.tags.<key>: <value>. resilience4j.circuitbreaker.tags.team=checkout produced resilience4j_circuitbreaker_state{application="bookshelf",name="pricing",state="closed",team="checkout"}. The application label in that line comes from management.metrics.tags.application.

  • Turn on histograms or service-level objectives: these are standard Micrometer distribution settings addressed by the Micrometer meter name. management.metrics.distribution.percentiles-histogram.resilience4j.circuitbreaker.calls=true added resilience4j_circuitbreaker_calls_seconds_bucket{…​,le="0.001"} series in the run, and management.metrics.distribution.slo.resilience4j.circuitbreaker.calls=100ms,500ms adds fixed buckets. Histograms multiply the series count by the number of buckets, so enable them for the call timers you will actually query.

  • Rename a meter: declare your own publisher bean with a names object; the auto-configured one is @ConditionalOnMissingBean and backs off.

Registering listeners for every instance

A listener on an instance has to be attached before the first event, and breakers created by name at runtime would be missed by a loop over getAllCircuitBreakers() at start-up. The registry’s own event consumer solves both: a RegistryEventConsumer bean is called each time an instance is added, and the Boot auto-configuration collects every such bean.

Logging every state transition and rejection of every breaker, including ones created later
package com.example.bookshelf.config;

import io.github.resilience4j.circuitbreaker.CircuitBreaker;
import io.github.resilience4j.core.registry.EntryAddedEvent;
import io.github.resilience4j.core.registry.EntryRemovedEvent;
import io.github.resilience4j.core.registry.EntryReplacedEvent;
import io.github.resilience4j.core.registry.RegistryEventConsumer;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class ResilienceEventLogging {

    private static final Logger LOG = LoggerFactory.getLogger("bookshelf.resilience.events");

    @Bean
    RegistryEventConsumer<CircuitBreaker> circuitBreakerLogging() {
        return new RegistryEventConsumer<>() {
            @Override
            public void onEntryAddedEvent(EntryAddedEvent<CircuitBreaker> added) {
                added.getAddedEntry().getEventPublisher()
                    .onStateTransition(e -> LOG.warn("circuit breaker '{}' {}",
                        e.getCircuitBreakerName(), e.getStateTransition()))
                    .onCallNotPermitted(e -> LOG.warn("circuit breaker '{}' rejected a call",
                        e.getCircuitBreakerName()));
            }

            @Override
            public void onEntryRemovedEvent(EntryRemovedEvent<CircuitBreaker> removed) { }

            @Override
            public void onEntryReplacedEvent(EntryReplacedEvent<CircuitBreaker> replaced) { }
        };
    }
}

Source: Prometheus: Alerting rules for the rule format, and the meters of the sample run. How to read them:

  • Open breaker. The state gauge is 1.0 for exactly one state label per breaker, so selecting open and forced_open and comparing with 1 finds breakers in either condition. The for: 2m keeps a breaker that opens and recovers in one waitDurationInOpenState cycle from paging anybody. A breaker you forced open on purpose will page too, which is usually what you want.

  • Retry rate. The counter counts calls, so the ratio is "the share of calls that needed at least one retry". A steady 5 percent can be normal; a jump to 20 percent means the dependency is flaky even if users still get answers, which is exactly when retries hide an outage. failed_with_retry is the share that did not recover, which is the actionable one. Remember that retries multiply load, so a rising retry rate is also a rising load on the dependency.

  • Bulkhead saturation. The semaphore ratio uses the two gauges; a maxWaitDuration of zero makes a full bulkhead reject at once, so the ratio near 0 for minutes means users are being rejected. For the thread pool the signal is the queue filling up, and the extra queue_capacity > 0 selector keeps a pool configured with queueCapacity: 0 (a SynchronousQueue, always empty by design) from dividing zero by zero. Neither bulkhead kind has a rejection counter, so count the rejections from the fallback or from CALL_REJECTED events when you need a rate.

Tracing context through bulkhead threads

A call that goes through a ThreadPoolBulkhead runs on a pool thread, and every ThreadLocal of the caller is invisible there: the logging MDC, the Spring Security context, the current Micrometer observation and, with it, the trace and span. A trace that stops at the bulkhead, or log lines on the pool thread without a traceId, are the symptoms. The semaphore bulkhead, the circuit breaker, the retry and the rate limiter run on the caller’s thread and have no such problem. The mechanism and the MDC and security-context propagators are described in Bulkhead; this section is about the Micrometer side.

sequenceDiagram participant R as Request thread participant B as ThreadPoolBulkhead participant P as bulkhead-recommendations-1 R->>R: Observation started, traceId in MDC R->>B: submit the call B->>R: retrieve() captures a ContextSnapshot B->>P: hand the task to a pool thread P->>P: copy() restores every registered ThreadLocal P->>P: the task runs with the observation, span and MDC P->>P: clear() closes the scope in a finally block P-->>R: CompletableFuture completes

The bridge is one ContextPropagator that takes a ContextSnapshot from Micrometer’s context-propagation library on the caller thread and restores it on the pool thread. It is the propagator from the Bulkhead page, shown again here because the tracing behaviour needs it.

A ContextPropagator for every ThreadLocal registered in Micrometer’s ContextRegistry
public class SnapshotContextPropagator implements ContextPropagator<ContextSnapshot> {

    private static final ContextSnapshotFactory FACTORY = ContextSnapshotFactory.builder().build();
    private static final ThreadLocal<ContextSnapshot.Scope> SCOPE = new ThreadLocal<>();

    @Override
    public Supplier<Optional<ContextSnapshot>> retrieve() {
        return () -> Optional.of(FACTORY.captureAll());
    }

    @Override
    public Consumer<Optional<ContextSnapshot>> copy() {
        return snapshot -> snapshot.ifPresent(s -> SCOPE.set(s.setThreadLocals()));
    }

    @Override
    public Consumer<Optional<ContextSnapshot>> clear() {
        return snapshot -> {
            ContextSnapshot.Scope scope = SCOPE.get();
            if (scope != null) {
                scope.close();
                SCOPE.remove();
            }
        };
    }
}

POST /actuator/circuitbreakers/pricing with FORCE_OPEN keeps the breaker open through a deploy of the pricing-service, and CLOSE afterwards reopens the traffic at once. The ops role is required.

The pricing breaker has no slow-call settings, so a pricing-service that gets slow but never fails would not open it; the slowCallRate field of the endpoint and resilience4j_circuitbreaker_slow_call_rate would show the symptom, and the breaker page explains the settings. And the isbn retry sits outside the breaker by default (the aspect order of Annotations and Aspect Order), so when both annotate the same method the breaker’s calls timer and failedCalls count every attempt, while resilience4j_retry_calls_total counts each logical call once. Read the two together before you decide that "the breaker saw three failures".

Common pitfalls

Pitfall What to do instead

Exposing * or the circuitbreakers endpoint on the public port

Expose the endpoints by name, on management.server.port, behind authentication, with management.endpoint.circuitbreakers.access=read-only unless an operator profile needs the write operation.

Posting a state change with a typo in the name

The endpoint creates a new default breaker. Check the name against GET /actuator/circuitbreakers first, and delete nothing in a hurry: the instance stays until the JVM restarts.

Enabling management.health.circuitbreakers.enabled and not exposing health

The application fails to start for lack of a StatusAggregator bean. Expose health whenever the indicator is enabled.

Setting registerHealthIndicator but not management.health.circuitbreakers.enabled

The indicator bean is @ConditionalOnProperty with no default, so nothing appears. Set both.

Adding circuitBreakers to the liveness group

A dependency outage restarts every replica. Keep the indicators in a custom group, and out of liveness.

Using allowHealthIndicatorToFail on a breaker with a good fallback

It turns a degraded service DOWN and removes it from the load balancer. Use it only for a dependency the service cannot work without.

Expecting CIRCUIT_OPEN to turn the service DOWN

It is a custom status that the default StatusAggregator does not rank; it never worsens the aggregate. Alert on the meters, not the top-level health.

Reading the endpoint failure rate as a percentage of all calls

It is the rate over the current window, -1.0% until minimumNumberOfCalls. Do not alert on it directly; alert on the state gauge.

Alerting on a missing counter for bulkhead rejections

There is none. Bulkheads expose gauges and CALL_REJECTED events, so alert on saturation or count the fallback.

Querying rate() on the breaker state gauge, or sum of state without a selector

The gauge is one series per state with 1.0 on the current one. Select the state, then max by (name).

Importing the Grafana dashboard without the application tag

The variables and the retry and bulkhead panels are empty. Set management.metrics.tags.application.

High-cardinality tags

The failure tag of @Timer is the exception class name, and registry tags are added to every series. Keep tag values bounded, and never tag with an ISBN or a user id.

Pool threads without a propagator

A trace that ends at the bulkhead and log lines without traceId. Use the ContextSnapshot propagator, register the MDC accessor, and use an observation rather than a bare span.

Logging every success event

One log line per call. Log transitions and rejections, and count the rest with meters.

What changed recently

  • Resilience4j 2.4.0. The Spring Boot 4 starter (resilience4j-spring-boot4) moved the autoconfiguration to the Boot 4 health and Actuator packages. The meter names, the tags, the endpoint ids and the endpoint JSON described on this page are the same as on 2.3.0 and Boot 3. Two details to know when reading the older docs: the readme.io Micrometer page (written for 2.2.0) still lists resilience4j.circuitbreaker.max.buffered.calls, which the 2.4.0 source does not register, shows the retry meter as a gauge with dotted kind values such as successful.without.retry where the source has a FunctionCounter named resilience4j_retry_calls_total with underscored kinds, and its Grafana page is unchanged for years.

  • Spring Boot 4. HealthIndicator and Health moved to org.springframework.boot.health.contributor and StatusAggregator to org.springframework.boot.health.actuate.endpoint (Boot 3: org.springframework.boot.actuate.health). The Actuator security matcher EndpointRequest is in org.springframework.boot.security.autoconfigure.actuate.web.servlet (Boot 3: org.springframework.boot.actuate.autoconfigure.security.servlet). Applications that only use properties are unaffected. In the sample run the liveness and readiness groups were present without configuration on Boot 4.1.1, while on Boot 3.5.16 outside Kubernetes a liveness group that included livenessState failed at start-up until management.endpoint.health.probes.enabled=true was set.

  • Spring Boot 3.4 and later. management.endpoint.<id>.access (none, read-only, unrestricted) replaces management.endpoint.<id>.enabled; use it to remove the circuit breaker write operation.

  • Spring Boot tests. On Spring Boot 3.5.16 a @SpringBootTest does not export metrics unless the test class is annotated with @AutoConfigureObservability; without it the /actuator/prometheus response in the test had no resilience4j_ series. The Boot 4.1.1 sample tests produced the series without the annotation.

  • Micrometer 1.17 and the Prometheus client 1.x. Timers are exposed as summaries with _seconds_count, _seconds_sum and a separate _seconds_max gauge, and counters carry _total, as shown in the scrape above; dashboards built for the old _count and _sum names of Resilience4j 1.x on Micrometer 1.5 need those names updated.

  • Migration. The full Resilience4j and Spring Boot version changes are collected in Migration & What’s Changed.
