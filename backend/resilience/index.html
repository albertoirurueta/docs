Resilience

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This Backend Development section is a practical guide, focused on Spring Boot services, to making a service tolerate the failures of the services it calls (it complements the SpringBoot Reference). It documents Resilience4j 2.4.0 (released 2026-03-14, Java 17 or later) on Spring Boot 4.1.x and Spring Framework 7.0.x with Java 21, together with the pieces of the Spring ecosystem that sit around it: Spring Cloud CircuitBreaker, the Spring Cloud Gateway and OpenFeign integrations, and the native @Retryable and @ConcurrencyLimit of Spring Framework 7. Where the Spring Boot 3.5 starter differs, the pages show a short "Spring Boot 3" delta. The versions were verified on 4 October 2026.

Next to Resilience4j, the section documents Bucket4j 8.21.0 (released 2026-10-02, Java 17 or later), the token-bucket library for what an in-process limiter cannot do: per-client API quotas, limits shared by every replica through Redis, a JDBC database or a data grid, and one quota of a third-party API shared across instances. Its pages cover the library itself, its Spring Boot integration by hand, through the community bucket4j-spring-boot-starter and in Spring Cloud Gateway, and how it combines with Resilience4j; the Bucket4j pages were verified on 5 October 2026. Start with Resilience4j versus Bucket4j to see which library answers which need.

What resilience means for a Spring Boot service

A service that calls other services inherits their failures. A dependency that answers slowly holds your threads and connections; one that fails intermittently turns every request into a coin toss; one that is down makes every caller wait for a timeout; and a caller that retries aggressively can keep a struggling dependency from ever recovering. Resilience is the set of techniques that keep one failing dependency from becoming your failure:

  • timeouts so that no call waits forever (TimeLimiter, plus the HTTP client’s own timeouts)

  • retries with exponential backoff and jitter for transient errors, on idempotent operations only (Retry)

  • circuit breakers that stop calling a dependency that is clearly failing, and probe it again later (CircuitBreaker)

  • bulkheads that cap how much of your capacity one dependency can consume (Bulkhead, ThreadPoolBulkhead)

  • rate limiters that keep you under a dependency’s quota, or keep clients under yours (RateLimiter)

  • fallbacks that degrade gracefully instead of failing: a cached value, a default, an empty list

Resilience4j is the lightweight, functional fault-tolerance library that Netflix recommends in place of Hystrix, which has been in maintenance mode since 2018. Each pattern is a small module with no dependencies beyond its own modules, composed by decorating a function; the Spring Boot starter adds registries bound to application.yml, annotations, Actuator endpoints, health indicators and Micrometer metrics.

This section is for developers who:

  • build or maintain Spring Boot services that call other HTTP, gRPC or database-backed services, and want to know which pattern answers which failure

  • are on Spring Boot 4 (or still on 3.5) and need the starter, the AspectJ dependency and the configuration that actually work, because the official Resilience4j documentation does not cover Spring Boot 4

  • come from Hystrix, Spring Retry or Spring Cloud Netflix, and need the migration path

  • want to test the failure paths, observe them in production, and tune the numbers from real traffic

Running example

Every example builds on Bookshelf, the book-catalogue domain already used by the Python FastAPI, NestJS, Django, Next.js and Kubernetes sections, so that the stacks can be compared page by page. Here it is a Spring Boot 4.1 bookshelf-service (Java 21, virtual threads enabled) that calls four downstream dependencies. Each dependency motivates one set of patterns:

Dependency Behaviour Patterns

pricing-service

Slow and flaky.

CircuitBreaker, TimeLimiter and a short Retry, with a fallback to the last known price.

A third-party ISBN-metadata API

Has a request quota and answers 429 or 503.

A client-side RateLimiter, a Bulkhead, and Retry with exponential backoff and jitter that honours Retry-After.

recommendations-service

Expensive and optional.

A ThreadPoolBulkhead with a CircuitBreaker and a TimeLimiter, degrading to an empty list.

reviews-service

Called reactively through WebClient.

The Reactor operators of resilience4j-reactor.

Spring Cloud Gateway sits in front of bookshelf-service with a CircuitBreaker filter, the service’s own search endpoint is protected by a RateLimiter that answers 429 with Retry-After, and the tests inject faults with WireMock and Toxiproxy (through Testcontainers).

Figure 2. The Bookshelf dependency map, annotated with the pattern that guards each call

Rate limits and quotas with Bucket4j

The Bucket4j pages extend the same service with the limits an in-process limiter cannot enforce:

Need Behaviour Bucket4j answer

A public REST API with per-API-key plans

Most pages use a free plan of 20 requests per minute, pro 200 and partner 2 000; the comparison page uses 100 per hour plus 10 per second for free. The quota must hold across every replica.

One bucket per API key, its configuration chosen by plan, stored in Redis through Lettuce; rejections answer 429 with Retry-After, X-Rate-Limit-Remaining and an RFC 9457 ProblemDetail.

The third-party ISBN-metadata API

Its daily quota (1 000 calls) applies to the whole service, not to each replica.

One distributed bucket shared by every replica, where the Resilience4j RateLimiter above admits the limit once per replica.

The search endpoint

Expensive.

Weighted consumption: each call costs 5 tokens.

Teams without Redis

Need the same limits.

A PostgreSQL (JDBC) variant of the bucket store, with its table created by Flyway.

Spring Cloud Gateway

Sits in front of every replica.

A coarse per-client limit at the edge with the Web MVC Bucket4j filter.

Resilience4j keeps guarding the outbound calls, including the calls to the bucket store itself, so a Redis outage fails open or closed deliberately. The Bookshelf with both libraries puts the two together.

    web:
      exposure:
        include: health,circuitbreakers,circuitbreakerevents,retries,ratelimiters,bulkheads,timelimiters,metrics,prometheus
  endpoint:
    circuitbreakers:
      access: read-only                         # no CLOSE / FORCE_OPEN / DISABLE over HTTP
    health:
      show-details: when-authorized
  health:
    circuitbreakers:
      enabled: true
    ratelimiters:
      enabled: true

Source: Resilience4j: Spring Boot 2 & 3 and the property classes at the v2.4.0 tag; the same file, bound and run, is on Spring Boot Configuration.

The Grafana dashboard

Resilience4j ships a dashboard in its repository (grafana_dashboard.json). It reads the resilience4j.* meters that Micrometer exports to Prometheus and shows circuit-breaker states, failure rate, call rate and call duration, retry calls and the semaphore bulkhead. The observability page imports it for Bookshelf, explains the application tag it filters on and the panel that queries a meter 2.4.0 no longer publishes, and lists the panels to add for rate limiters, time limiters and thread-pool bulkheads. See Observability.
