Spring Framework Native Resilience

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Spring Framework 7 put a small set of resilience features into the core framework: the annotations @Retryable and @ConcurrencyLimit for method invocations, the switch that turns them on, @EnableResilientMethods, and a programmatic RetryTemplate with a RetryPolicy and a RetryListener. They replace the retry half of the Spring Retry project, which is now archived. They are deliberately minimal: there is no circuit breaker, no rate limiter, no per-call time limiter, no metrics and no Actuator endpoint. This page covers what they do, every attribute and its default, how they behave next to Resilience4j, how to migrate from Spring Retry, and how to choose between the three options a Spring Boot 4 service has today. It was written against Resilience4j 2.4.0, Spring Boot 4.1.x (4.1.1), Spring Framework 7.0.x (7.0.9) and Java 21, and every example on it was compiled and run on exactly those versions on 4 October 2026.

What changes on Spring Boot 3.5.x. Nothing on this page works there. Spring Boot 3.5.16 manages Spring Framework version 6.2.19, and in that version the packages org.springframework.resilience and org.springframework.core.retry do not exist (verified by loading the classes from the 6.2.19 jars: Retryable, ConcurrencyLimit, EnableResilientMethods, RetryTemplate and RetryPolicy are all absent). On a Boot 3.5 service the choices for retry are Resilience4j or the archived Spring Retry, which the Boot 3.5.16 dependency management still pins to 2.0.13; Spring Boot 4.1.1 no longer manages Spring Retry at all. The remainder of the page is about Boot 4.

The vocabulary (idempotency, retry storm, bulkhead) is introduced in Resilience Fundamentals. The Resilience4j equivalents are covered in Retry and Bulkhead, and the way the two worlds share one method is in Annotations & Aspect Order.

Enabling it: @EnableResilientMethods

Like most annotation-driven features of Spring, the two annotations are metadata that something has to honour. The switch is @EnableResilientMethods on a @Configuration class. It imports one configuration class that registers two infrastructure beans, a RetryAnnotationBeanPostProcessor and a ConcurrencyLimitBeanPostProcessor, each of which wraps matching beans in a Spring AOP proxy. Either processor can also be declared alone if only one feature is wanted.

Turning the annotations on
@SpringBootApplication
@EnableResilientMethods   // proxyTargetClass = false, order = LOWEST_PRECEDENCE - 1 by default
public class BookshelfApplication {
    public static void main(String[] args) {
        SpringApplication.run(BookshelfApplication.class, args);
    }
}

Source: @EnableResilientMethods Javadoc. Run on Spring Boot 4.1.1.

The annotation has two attributes:

Attribute Default Meaning

proxyTargetClass

false

true asks for subclass (CGLIB) proxies instead of interface-based JDK proxies. It only affects the two post-processors of this feature. The Javadoc recommends a global proxy default plus @Proxyable on individual classes instead.

order

Ordered.LOWEST_PRECEDENCE - 1

The order of the two post-processors among the other bean post-processors, chosen so that they run after every common post-processor except @EnableAsync. It is not an order among advice on one method; see the section on stacking below.

Three facts about the setup were verified by running it and are easy to miss:

  • Spring Boot 4.1.1 does not enable it for you. A bean with @Retryable in a Boot application that has no @EnableResilientMethods is not proxied and the method ran exactly once. There is no error and no warning.

  • The proxy type depends on the context. In a plain Spring context a bean that implements an interface gets a JDK proxy, and @Retryable on the method of the implementation class was ignored (one invocation); the same annotation on the interface method worked (two invocations), and proxyTargetClass = true produced a CGLIB proxy. In a Spring Boot application the auto-configured proxy creator forces class-based proxies, so the annotation on the implementation class works. The behaviour is the one described in the AOP chapter; the Resilience4j annotations have the same interface caveat, covered in Annotations & Aspect Order.

  • Only calls through the proxy count. A call from another method of the same class (this.lookup(…​)) is not retried, and a final method cannot be intercepted by a CGLIB proxy. A package-private method of a CGLIB-proxied bean was retried.

@Retryable

@Retryable can be placed on a method, or on a type, where it applies to every proxy-invoked method of the class hierarchy. With no attributes at all it means: retry any exception, at most three times after the initial failure, waiting one second between attempts, then rethrow the last original exception.

Every attribute

The defaults below were read from the 7.0.9 sources of org.springframework.resilience.annotation.Retryable and confirmed by running the method with each one set.

Attribute Default Meaning

value (alias of includes)

empty

The convenient single-attribute form: @Retryable(IOException.class) is @Retryable(includes = IOException.class).

includes

empty (any exception)

Exception types to retry. Each is matched against the thrown exception and its causes: with includes = IOException.class, a RuntimeException that wraps an IOException was retried.

excludes

empty

Exception types never to retry, matched the same way. Combined with includes, the exclusion narrows the inclusion.

predicate

MethodRetryPredicate.class (accept everything)

A MethodRetryPredicate with shouldRetry(Method, Throwable), instantiated per method through the bean factory, so it can use constructor injection. The Framework reference states that a predicate is always applied after includes and excludes.

maxRetries

3

The number of retries, so total invocations are 1 + maxRetries: the default calls the method up to 4 times. 0 disables retrying. Verified: maxRetries = 2 ran the method 3 times, 0 ran it once.

maxRetriesString

empty

A non-empty value overrides maxRetries; accepts ${…​} placeholders and SpEL.

delay

1000

The base wait before the first retry, in timeUnit (milliseconds by default). With a multiplier it is the first value to multiply from. Must be zero or more.

delayString

empty

Overrides delay. A plain integer (in timeUnit), an ISO-8601 duration such as PT1S, or the simple style such as 500ms, with placeholders and SpEL.

jitter

0

An absolute duration (not a factor) added to the delay to spread clients apart. See below for the range.

jitterString

empty

Overrides jitter, with the same formats as delayString.

multiplier

1.0 (a fixed delay)

Applied to the previous delay, and to the jitter, for every further retry. 2.0 doubles the wait each time.

multiplierString

empty

Overrides multiplier; placeholders and SpEL.

maxDelay

Long.MAX_VALUE (unlimited)

The ceiling for any single wait, limiting how far jitter and multiplier can grow it.

maxDelayString

empty

Overrides maxDelay, with the same formats as delayString.

timeout

0 (none)

Since 7.0.2. The maximum elapsed time for the initial invocation and all retries including the waits, in timeUnit. A retry whose pending sleep would cross the limit is not started.

timeoutString

empty

Since 7.0.2. Overrides timeout, with the same formats as delayString.

timeUnit

TimeUnit.MILLISECONDS

The unit of delay, jitter, maxDelay, timeout and their String variants (ignored for explicit Duration strings).

Source: @Retryable Javadoc and the RetryAnnotationBeanPostProcessor source at v7.0.9, which resolves the String variants through the embedded value resolver.

The jitter ranges were sampled from RetryPolicy.getBackOff().start(): with a jitter the wait lands between the delay and the delay plus the jitter, and the jitter itself is multiplied along with the delay, so it is not symmetric around the delay in practice even though the Javadoc describes "between delay minus jitter and delay plus jitter but never below the base delay".

Two traps are specific to the attributes:

  • Changing timeUnit needs an explicit maxDelay. @Retryable(delay = 1, timeUnit = TimeUnit.SECONDS, maxRetries = 1) threw ArithmeticException: long overflow before the method was invoked once (0 invocations), because the default maxDelay of Long.MAX_VALUE is converted from seconds to milliseconds. Adding maxDelay = 10 made the same annotation work (2 invocations, a gap of 1006 ms). With the default unit there is no problem.

  • The default retries every exception. That includes validation and business exceptions that will never succeed. Narrow it with includes, excludes or a predicate, and keep the call idempotent.

A predicate for HTTP status codes

For the Bookshelf, the third-party ISBN-metadata API answers 503 and 429 now and then and 404 when an ISBN is unknown. A MethodRetryPredicate expresses exactly that, in one place:

A predicate that retries transient failures only
public class TransientFailure implements MethodRetryPredicate {

    @Override
    public boolean shouldRetry(Method method, Throwable throwable) {
        return throwable instanceof ResourceAccessException            // I/O failure, timeout
            || throwable instanceof HttpServerErrorException           // any 5xx
            || throwable instanceof HttpClientErrorException.TooManyRequests; // 429
    }
}

Source: MethodRetryPredicate Javadoc. Run against WireMock: a 404 was not retried (1 request), a 429 that never cleared was retried (4 requests).

What the caller sees: the original exception

When the attempts run out the annotation rethrows the last original exception from the target method, not a wrapper. Internally it runs a RetryTemplate, which throws a RetryException, and the interceptor unwraps the cause. That is the same contract as Resilience4j’s Retry, and it means existing catch blocks keep working. The one asymmetry is the reactive form, covered next.

Reactive return types

@Retryable also works on a method that returns a reactive type: the interceptor does not call the method again, it decorates the returned publisher with Reactor’s retry, using Retry.backoff(maxRetries, delay), a jitter factor derived from jitter divided by delay (clamped to the range 0 to 1), the multiplier and maxDelay as the maximum backoff, and a timeout operator when a timeout is set. This needs Reactor on the classpath; a CompletableFuture is not treated as reactive.

A reactive method with the native retry
@Retryable(maxRetries = 2, delay = 10)
public Mono<String> title(String isbn) {
    return Mono.defer(() -> webClient.get().uri("/isbn/{isbn}", isbn).retrieve().bodyToMono(String.class));
}

Source: the AbstractRetryInterceptor source at v7.0.9 and the reference’s reactive example. Behaviour measured on 7.0.9:

Case Observed

Returned the value, 3 subscriptions, 2 MethodRetryEvent objects

3 invocations, then reactor.core.Exceptions$RetryExhaustedException: Retries exhausted: 2/2 whose cause is the original IllegalStateException. The imperative form rethrows the original exception itself, so code that catches one specific type must unwrap it for reactive methods.

MethodRetryEvent

While a @Retryable method runs, Spring publishes a MethodRetryEvent (package org.springframework.resilience.retry, since 7.0.3, a subclass of org.springframework.context.event.MethodFailureEvent) on the application context. It is the only built-in observability the feature has. It exposes getMethod(), getFailure() and isRetryAborted().

  • Every failed invocation publishes an event with retryAborted = false and the exception the method threw.

  • When the retrying ends without success (exhaustion, timeout or interruption), one more event is published with retryAborted = true. Its failure is the final exception of the retry infrastructure: a RetryException for an imperative method, a RetryExhaustedException or TimeoutException for a reactive one.

  • A successful retry publishes no retryAborted event: a method that failed twice and then succeeded produced 2 events, both with retryAborted = false.

  • A call that fails with an excluded exception on the first invocation still publishes two events: one with retryAborted = false carrying the exception, and one with retryAborted = true carrying the RetryException (verified for an imperative and for a reactive method). The number of events is therefore not the number of retries.

A default call that failed all four times produced five events: four with false and one with true carrying a RetryException. The listener below turns them into a Micrometer counter, which is how the Bookshelf makes up for the fact that the annotation registers no meters of its own.

Bridging MethodRetryEvent to Micrometer
@Component
public class RetryAudit {

    private final MeterRegistry registry;

    RetryAudit(MeterRegistry registry) {
        this.registry = registry;
    }

    @EventListener
    void onRetry(MethodRetryEvent event) {
        registry.counter("bookshelf.retry.failures",
            "method", event.getMethod().getName(),
            "aborted", Boolean.toString(event.isRetryAborted())).increment();
    }
}

Source: MethodRetryEvent Javadoc. Run: after a lookup that failed with 503 twice and then succeeded the counter with aborted=false had grown by 2; after a lookup that failed four times the counter with aborted=true had grown by 1. The event is an ordinary Spring application event, so it can feed logs, metrics or tracing; the sibling page Observability covers the Resilience4j meters and Actuator endpoints that this feature does not have.

@ConcurrencyLimit

@ConcurrencyLimit caps how many threads may be inside a method at the same time. Its Javadoc motivates it with virtual threads, where there is no thread pool to act as a natural limit; for synchronous calls it applies Spring’s long-standing ConcurrencyThrottleInterceptor. The comparison with the Resilience4j semaphore bulkhead is in Bulkhead. For a real-world use, the Spring AI production page caps concurrent model calls with @ConcurrencyLimit next to a Resilience4j RateLimiter, in Spring AI: rate limiting and concurrency. The attributes are these:

Attribute Default Meaning

value (alias of limit)

Integer.MIN_VALUE, which is invalid

The convenient form: @ConcurrencyLimit(5).

limit

Integer.MIN_VALUE, which is invalid

1 locks the instance for each invocation, a larger value is pool-like, -1 is unbounded. A limit below -1 (which includes the default) fails at the first call with IllegalStateException: …​ must be configured with a valid limit; verified.

limitString

empty

Overrides limit and value; accepts ${…​} placeholders and SpEL.

policy

ThrottlePolicy.BLOCK

Since 7.0.3. BLOCK makes callers over the limit wait, with no timeout; REJECT throws InvocationRejectedException immediately.

Source: @ConcurrencyLimit Javadoc and the ConcurrencyLimitBeanPostProcessor source at v7.0.9.

BLOCK and REJECT
@Component
class Limited {

    @ConcurrencyLimit(2)                                                    // BLOCK is the default policy
    String blocking() { return slowCall(); }

    @ConcurrencyLimit(limit = 2, policy = ConcurrencyLimit.ThrottlePolicy.REJECT)
    String rejecting() { return slowCall(); }
}

Source: the Javadoc linked above. Run with virtual threads and a 200 ms call:

  • blocking() called six times at once: all six returned done, the peak concurrency was 2 and the whole batch took 618 ms, about three waves of 200 ms.

  • rejecting() called four times at once: two returned done and two threw InvocationRejectedException with the message Concurrency limit reached: 2 - not allowed to enter …​Limited.rejecting. The rejection took 0 ms: a rejected caller does not wait. The exception is an InvocationRejectedException and, through it, a java.util.concurrent.RejectedExecutionException; getTarget() returns the bean.

  • limitString = "${lim}" with lim=3 gave a peak of 3; -1 gave a peak of 6 for six callers; 1 gave a peak of 1.

Where the throttle lives:

  • On a method, the throttle belongs to that method of that bean instance. On a class, all proxied methods of the instance share one throttle: with @ConcurrencyLimit(limit = 2, policy = REJECT) on the class, two concurrent callers of a() and b() together filled it and the other two were rejected.

  • There are no events and no meters, and no Actuator endpoint. The interceptor of 7.0.9 publishes nothing.

  • It limits the synchronous call. On a method that returns a Mono the throttle is released as soon as the method returns the Mono, so it limits nothing about the subscriptions: with limit = 1 and REJECT, four concurrent subscriptions all succeeded and the peak was 4. Use a Resilience4j bulkhead operator or a flatMap concurrency argument for reactive code.

Turning a rejection into an HTTP answer is one @ExceptionHandler. The Bookshelf rejects the fifth concurrent reviews read with a 503 and a Retry-After header:

Mapping the rejection to an HTTP response
@Service
public class ReviewsService {

    private final ReviewsRepository repository;

    ReviewsService(ReviewsRepository repository) {
        this.repository = repository;
    }

    /** At most 4 concurrent reads; the fifth caller is rejected at once instead of queueing. */
    @ConcurrencyLimit(limit = 4, policy = ThrottlePolicy.REJECT)
    public List<String> reviews(String isbn) {
        return repository.slowRead(isbn);
    }
}

@ControllerAdvice
class ApiErrors {

    @ExceptionHandler(InvocationRejectedException.class)
    ResponseEntity<Void> tooBusy() {
        return ResponseEntity.status(503).header(HttpHeaders.RETRY_AFTER, "1").build();
    }
}

Source: InvocationRejectedException Javadoc. Run: six concurrent GET /books/978/reviews against the 300 ms repository returned four 200 OK and two 503 SERVICE_UNAVAILABLE with Retry-After=1.

Stacking with Resilience4j on one method

The native annotations and the Resilience4j annotations are different mechanisms and can sit on the same method. The native ones are applied by BeanPostProcessors that call setBeforeExistingAdvisors(true), so they are added in front of whatever advisors the AspectJ auto-proxy creator already installed on the bean, which is where the Resilience4j aspects live. The result, observed in three runs on Boot 4.1.1:

  • @Retryable(maxRetries = 2) with @CircuitBreaker: the native retry is the outer layer. The backend was called 3 times and the breaker recorded 3 failed calls.

  • @Retryable(maxRetries = 2) with Resilience4j @Retry(maxAttempts = 3): the retries multiply, 3 x 3 = 9 backend calls.

  • @Retryable with @ConcurrencyLimit(limit = 1, policy = REJECT) on one method: the concurrency limit is the outer layer (the later post-processor wraps the earlier one). While one caller slept in the back-off between attempts, a second caller was rejected: the permit is held for the whole retrying, not released between attempts.

flowchart LR C([caller]) --> L["@ConcurrencyLimit advisor
(added last, outermost)"] L --> R["@Retryable advisor
(added before existing advisors)"] R --> A["Resilience4j aspects, in the order
Retry, CircuitBreaker, RateLimiter,
TimeLimiter, Bulkhead"] A --> T[("target method")]
Figure 1. The advisor chain around a bean that uses both families

The practical consequences are the ones the earlier pages warned about for two retry layers: do not put native @Retryable and Resilience4j @Retry on one method, and remember that with a native retry outside a breaker, every attempt is a call the breaker counts. In the Bookshelf the breaker has a window of 4 calls, so one lookup that fails all four times opens it by itself; a retry that then runs into the open breaker would retry CallNotPermittedException too (it is "any exception") unless it is excluded, which is why the example below has excludes = CallNotPermittedException.class. The aspect order of the Resilience4j annotations themselves is in Annotations & Aspect Order.

Programmatic retry

@Retryable only reaches methods of Spring beans called through the proxy. For any other block of code there is the RetryTemplate, a lightweight object that executes a Retryable operation under a RetryPolicy. The Framework reference notes that templates are cheap and can be created on the fly for one invocation.

RetryPolicy

A RetryPolicy decides which exceptions are retried and supplies the BackOff (how long to wait and how many retries). It is built with the factory methods or the fluent builder:

Three ways to get a policy
RetryPolicy defaults = RetryPolicy.withDefaults();          // 1000 ms fixed, 3 retries
RetryPolicy four = RetryPolicy.withMaxRetries(4);           // 1000 ms fixed, 4 retries

RetryPolicy policy = RetryPolicy.builder()
    .includes(ResourceAccessException.class, HttpServerErrorException.class)
    .excludes(HttpClientErrorException.class)
    .predicate(t -> !(t instanceof InterruptedException))   // applied after includes and excludes
    .maxRetries(2)
    .delay(Duration.ofMillis(100))
    .jitter(Duration.ofMillis(10))
    .multiplier(2.0)
    .maxDelay(Duration.ofSeconds(1))
    .timeout(Duration.ofSeconds(3))
    .build();

Source: RetryPolicy Javadoc. Defaults printed from the policies on 7.0.9:

  • RetryPolicy.withDefaults().getBackOff() is FixedBackOff[interval=1000, maxAttempts=3], with a timeout of PT0S.

  • RetryPolicy.withMaxRetries(4).getBackOff() is FixedBackOff[interval=1000, maxAttempts=4].

  • RetryPolicy.builder().build().getBackOff() is ExponentialBackOff[initialInterval=1000, jitter=0, multiplier=1.0, maxInterval=Long.MAX_VALUE, maxElapsedTime=Long.MAX_VALUE, maxAttempts=3], which behaves as a fixed one-second delay.

  • The builder defaults are DEFAULT_MAX_RETRIES = 3, DEFAULT_DELAY = 1000, DEFAULT_JITTER = 0, DEFAULT_MULTIPLIER = 1.0, DEFAULT_MAX_DELAY = Long.MAX_VALUE and DEFAULT_TIMEOUT = Duration.ZERO.

  • Invalid values are rejected when building: withMaxRetries(-1) threw IllegalArgumentException: Invalid maxRetries (-1): must be positive or zero for no retry, and maxDelay(Duration.ZERO) threw …​ must be greater than zero.

  • A custom BackOff (a FixedBackOff or ExponentialBackOff from org.springframework.util.backoff, or your own) replaces maxRetries, delay, jitter, multiplier and maxDelay; the builder’s Javadoc warns not to set both. It can be set with backOff(…​). A policy can also be implemented directly: shouldRetry(Throwable) is the only method without a default.

RetryListener

A single RetryListener can be set on a template with setRetryListener(…​); several can be combined with a CompositeRetryListener. Every callback has an empty default implementation. They fire in this order (from a template with maxRetries = 2 whose operation fails three times, and from one that fails once and then succeeds):

sequenceDiagram participant T as RetryTemplate participant R as Retryable participant L as RetryListener T->>R: execute (initial invocation) R-->>T: throws T->>L: onRetryableExecution (retryCount 0, failed) loop while the policy accepts the exception T->>T: sleep for the BackOff T->>L: beforeRetry (retryCount n) T->>R: execute alt retry throws R-->>T: throws T->>L: onRetryFailure T->>L: onRetryableExecution (failed) else retry succeeds R-->>T: result T->>L: onRetrySuccess T->>L: onRetryableExecution (successful) end end T->>L: onRetryPolicyExhaustion, Timeout or Interruption
Callback When

onRetryableExecution(policy, retryable, state)

After every invocation, including the first one and a first-time success (state.isSuccessful() tells them apart). The best single hook for counting failures.

beforeRetry(policy, retryable, state)

Before each retry, after the back-off sleep.

onRetryFailure(policy, retryable, throwable)

When a retry (not the initial invocation) throws.

onRetrySuccess(policy, retryable, result)

When a retry succeeds.

onRetryPolicyExhaustion(policy, retryable, retryException)

The policy refuses further attempts, including the case where the first exception was not retryable.

onRetryPolicyTimeout(…​)

The policy’s timeout was or would be exceeded; the message was …​ would exceed timeout (120ms) due to pending sleep time (50ms); preemptively aborting execution.

onRetryPolicyInterruption(…​)

The thread was interrupted during the back-off; the thread’s interrupt flag is restored.

Source: RetryListener Javadoc. The sequences above were printed from a listener implementing every callback: for three failures it logged onRetryableExecution, beforeRetry, onRetryFailure, onRetryableExecution, beforeRetry, onRetryFailure, onRetryableExecution and onRetryPolicyExhaustion.

A RetryTemplate bean for the Bookshelf

The Bookshelf fetches cover-image URLs from a second third-party endpoint. That call is made from a plain client, not from an annotated method, so it uses a template bean with a listener that counts failures:

A RetryTemplate bean with a listener
@Configuration
class CoverRetryConfig {

    @Bean
    RetryTemplate coverRetryTemplate(MeterRegistry registry) {
        RetryPolicy policy = RetryPolicy.builder()
            .includes(ResourceAccessException.class, HttpServerErrorException.class)
            .maxRetries(2)
            .delay(Duration.ofMillis(100))
            .multiplier(2.0)
            .maxDelay(Duration.ofSeconds(1))
            .timeout(Duration.ofSeconds(3))
            .build();

        RetryTemplate template = new RetryTemplate(policy);
        template.setRetryListener(new RetryListener() {
            @Override
            public void onRetryableExecution(RetryPolicy p, Retryable<?> retryable, RetryState state) {
                if (!state.isSuccessful()) {
                    registry.counter("bookshelf.cover.attempt.failed").increment();
                }
            }

            @Override
            public void onRetryPolicyExhaustion(RetryPolicy p, Retryable<?> retryable, RetryException e) {
                registry.counter("bookshelf.cover.exhausted").increment();
            }
        });
        return template;
    }
}

@Component
public class CoverClient {

    private final RestClient http;
    private final RetryTemplate retry;

    CoverClient(RestClient.Builder builder, RetryTemplate coverRetryTemplate,
                @Value("${bookshelf.isbn.url}") String baseUrl) {
        this.http = builder.baseUrl(baseUrl).build();
        this.retry = coverRetryTemplate;
    }

    public String coverUrl(String isbn) {
        return retry.invoke(() -> http.get().uri("/covers/{isbn}", isbn).retrieve().body(String.class));
    }
}

Spring Retry is archived

Spring Retry (org.springframework.retry:spring-retry) was for years the Spring answer to retry: @EnableRetry, @Retryable, @Recover, RetryTemplate, BackOffPolicy, RetryListener, plus a stateful @CircuitBreaker. The project moved to the spring-attic organisation and is now archived: the repository at spring-attic/spring-retry is read-only, its README announces that the project "is no longer maintained as an open-source project" and points to the Spring Framework resilience features as its replacement, and the last release is 2.0.13 (8 June 2026). The old address github.com/spring-projects/spring-retry redirects to the archive. Spring Retry 2.0.13 still ran on Spring Framework 7.0.9 in a Boot 4.1.1 test (an @EnableRetry bean with @Retryable and @Recover worked), so an application does not break the day it upgrades, but there will be no fixes. Two other facts matter for planning:

  • Spring Boot 4.1.1 no longer manages the version: its dependency BOM has no Spring Retry entry, so a build that kept the dependency must pin 2.0.13 itself. Spring Boot 3.5.16 still manages 2.0.13.

  • Other Spring projects that used Spring Retry internally (the README names Spring Batch and Spring Integration) have their own migration stories; check their release notes rather than assuming.

Source: Spring Retry (archived) and the Core Spring Resilience Features announcement. The archive state, the README text and the 2.0.13 release date were read from the GitHub API; the managed version from the spring-boot-dependencies POMs of 3.5.16 and 4.1.1 on Maven Central.

Pitfalls

Pitfall Fix

Forgetting @EnableResilientMethods

Boot 4.1.1 does not enable the annotations: the bean was not proxied and the method ran once, with no warning. Put the annotation on the application or a configuration class and test that the proxy exists.

Porting maxAttempts = 3 as maxRetries = 3

maxRetries excludes the first call. The Spring Retry value of 3 is maxRetries = 2.

The default retries every exception

Business and validation errors are retried four times for nothing. Narrow with includes, excludes or a MethodRetryPredicate, and retry only idempotent calls.

timeUnit other than milliseconds without maxDelay

ArithmeticException: long overflow before the method is called once. Set maxDelay explicitly.

Expecting jitter to be symmetric or a factor

It is an absolute duration; the waits sampled between the delay and the delay plus the jitter.

Self-invocation, final methods, an annotation on the implementation of an interface in a plain Spring context

No retry, a null-pointer on a CGLIB proxy, or one invocation. Call through another bean, avoid final, annotate the interface method or set proxyTargetClass = true. Spring Boot forces class proxies.

Expecting a fallback

There is no @Recover. Catch the original exception at the call site, or use a Resilience4j fallbackMethod.

Expecting the original exception from a reactive method

A Mono that exhausts its retries fails with RetryExhaustedException whose cause is the original; a timeout fails with TimeoutException. Unwrap it.

Throwing before the Mono exists, or returning a CompletableFuture

Neither is retried (1 invocation, no event). Defer the work into the Mono, or use Resilience4j’s CompletionStage decoration.

@ConcurrencyLimit with the default BLOCK

Callers over the limit wait without a timeout and queue up behind a slow dependency. Prefer REJECT and map InvocationRejectedException to a 503.

@ConcurrencyLimit on a method returning Mono or Flux

It is released when the method returns the publisher, so it limits nothing about subscriptions (peak 4 with a limit of 1). Limit concurrency in the pipeline.

@Retryable outside a Resilience4j breaker

Every attempt is a breaker call: one lookup that failed four times filled a window of four and opened the breaker. Count that in minimumNumberOfCalls, and exclude CallNotPermittedException from the retry.

Native @Retryable plus Resilience4j @Retry on one method

They multiply: 3 x 3 = 9 backend calls in a run. Use one retry layer.

@Retryable plus @ConcurrencyLimit on one method

The limit is outermost, so the permit is held during the back-off sleeps. Keep long delays out of a method that also limits concurrency, or split it.

Expecting metrics or Actuator output

The native features register no meters and no endpoint; /actuator/retries was empty. Listen to MethodRetryEvent or use a RetryListener.

RetryTemplate.execute throws a checked RetryException, also for a non-retryable first failure

getRetryCount() == 0 tells apart a failure that was never retried. invoke wraps checked exceptions in UndeclaredThrowableException.

Following the Spring Cloud CircuitBreaker Framework Retry page literally

RetryPolicy.withMaxDuration, withBackoff, forExceptions and and() do not exist in 7.0.9; use RetryPolicy.builder(). The fallback receives a RetryException.

Keeping Spring Retry on Boot 4 without a version

Boot 4.1.1 does not manage it. Pin 2.0.13 and plan the migration; there will be no fixes.

What changed recently

  • Spring Framework 7.0 introduced @Retryable, @ConcurrencyLimit, @EnableResilientMethods, RetryTemplate, RetryPolicy and RetryListener, and Spring Retry was archived in favour of them.

  • 7.0.2 added the timeout attribute of @Retryable and the timeout of RetryPolicy.

  • 7.0.3 added the policy attribute of @ConcurrencyLimit with InvocationRejectedException, and MethodRetryEvent.

  • 7.0.9, the version this page ran on, defines DEFAULT_JITTER and DEFAULT_TIMEOUT on RetryPolicy.Builder.

  • Spring Cloud CircuitBreaker 5.0 has a Framework Retry implementation. Its Resilience4j starter still pulls Resilience4j 2.3.0 in 5.0.3; the alignment recipe is in Spring Cloud CircuitBreaker.

  • Spring Retry 2.0.13 (8 June 2026) is the last release; the project is archived.

  • The whole move from Spring Retry and Hystrix to the current stack is collected in Migration & What’s Changed.
