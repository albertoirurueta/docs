Bucket4j: Migration & What’s Changed

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Bucket4j keeps its API stable inside the 8.x line, so most upgrades are mechanical, but four things have moved enough to deserve a page of their own: the bandwidth builder that replaced Bandwidth.simple and Refill in 8.5.0, the artifact names that changed to bucket4j_jdk17- in 8.11.x, the *builder entry points (Bucket4jLettuce.casBasedBuilder and its relatives) that replaced direct constructors, and the community Spring Boot starter, whose coordinates and supported modes changed between its versions 0.13.0, 0.14.0 and 0.20.0-RC1. The page ends with every place where the official documentation disagrees with the code, gathered from the whole Bucket4j part of this section so that you can see them in one table.

This is the one page of the section where deprecated API appears, and only as the "before" side of a migration. It was written against Bucket4j 8.21.0 (released on 2 October 2026), Spring Boot 4.1.x (4.1.1), Spring Framework 7.0.x and Java 21, with the community starter at 0.14.0 and 0.20.0-RC1 and Spring Cloud Gateway 5.0.3, and verified on 5 October 2026. Every Java example on this page, in its old and in its new form, was compiled and run against Bucket4j 8.21.0 in a scratch project, and a test proved that each old form behaves identically to its replacement on a manual clock. The vocabulary (capacity, refill, bandwidth) is in Token Bucket and Bandwidths; the Resilience4j counterpart of this page is Migration & What’s Changed.

7.x to 8.x

Bucket4j 7.0.0 was the release that redesigned the distributed facilities (a ProxyManager per backend, rolling upgrades, non-JCache backends such as Redis and relational databases), and its release notes announce that the API it deprecated would be removed "in 2023". The 8.x line then changed the platform rather than the model. The notes of 8.0.1 (31 July 2022) list the migration to JDK 11 and the change of the Maven groupId to com.bucket4j; the Spring Boot starter’s own README dates the JDK 11 move to 8.0.0 and adds that the project then published dedicated Java 8 artifacts. Maven Central confirms the groupId move: the 7.x artifacts live under com.github.vladimir-bukhtoyarov, and the group com.bucket4j starts with 7.6.1 and 8.0.0.

Inside 8.x the code that most often needs touching is the entry point of a local bucket. The utility class Bucket4j was already @Deprecated in 7.6.0 and 8.4.0 (its methods delegate to the replacements) and is absent from 8.5.0, so code that still calls it stops compiling on 8.21.0.

The 8.5.0 bandwidth builder

Until 8.4.0 a bandwidth was created with a static factory: Bandwidth.simple(capacity, period) for a bucket that refills completely every period, and Bandwidth.classic(capacity, Refill…​) for everything else, with withInitialTokens and withId as wither methods on the result. The factories are named after implementation details ("classic", "simple") rather than after the two numbers of the token-bucket algorithm, and which Refill was greedy or intervally was a question of memorising factory names. Release 8.5.0 (issue #401, "making the builder API to be more close with token-bucket description") added a staged builder: Bandwidth.builder() then capacity, then one of four refill methods, then the optional id and initialTokens, then build(). On a BucketConfiguration or Bucket builder, addLimit(limit → …​) takes the same stages as a lambda. The old factories, the withInitialTokens and withId methods and the whole Refill class were marked @Deprecated in 8.5.0; they still work in 8.21.0, and under the project’s backward-compatibility policy deprecated API is removed only in a major release, so not before 9.0.0. Version 9 has open milestones on GitHub and is not released.

The test that accompanies this page asserted that each of the six before bandwidths is equals to the corresponding after one, field by field (capacity, refill tokens and period, greedy or intervally, aligned time, adaptive initial tokens, initial tokens and id), and that the two buckets give the same answers on a manual clock: with a capacity of 10 refilled 10 per minute, the exhausted bucket reported exactly 6 seconds to wait, 5 tokens were back after 30 seconds, and 10 after five minutes, for both. The intervally variant gave 0 tokens after 59 seconds and 10 after 60, for both.

Source: Bucket4j reference: Bandwidth, Bucket4j reference: Refill types and the 8.21.0 source of Bandwidth and Refill, whose @Deprecated tags are where the migration is announced. The 8.21.0 reference no longer shows the old factories at all (a search of its page and of its AsciiDoc sources found no Bandwidth.simple, Bandwidth.classic or Refill.), so the deprecation is visible only in the Javadoc and in your compiler’s warnings.

Two details of the builder are worth knowing before you convert code in bulk. initialTokens cannot be combined with refillIntervallyAlignedWithAdaptiveInitialTokens (the builder throws), exactly as withInitialTokens could not be combined with an adaptive Refill. And withNanosecondPrecision() belongs to the local bucket builder, not to the Bandwidth builder; the aligned refills need a wall-clock time meter and refuse the nanosecond one.

Ids change what a replacement means

The builder makes it easy to add id("…​") while you are converting. Do not add ids to an existing live configuration on the way: replaceConfiguration with TokensInheritanceStrategy.PROPORTIONALLY matches the old and the new bandwidth by id (or by position when neither has one). A run in the scratch project replaced capacity(20) (no id) by capacity(40)…​id("plan") and the bucket ended with 40 tokens, not the 30 that proportional inheritance gives, because the new bandwidth had an id the old one lacked and was treated as a different bandwidth. With both ids unset the same replacement gave 30. See Bandwidth ids decide which old bandwidth is which.

MathType.IEEE_754 was removed in 8.6

Before 8.6 the MathType enum had a second, experimental value, IEEE_754, intended for testing backends written in Lua or JavaScript that lack 64-bit integer arithmetic. The 8.5.0 source still has it and the 8.6.0 source does not (commit "#410 remove experimental code", 24 October 2023, which the 8.6.0 tag contains). The 8.6.0 release notes do not mention it. On 8.21.0 MathType is @Experimental and has one value, INTEGER_64_BITS, which a test of the scratch project asserted. Code that referred to MathType.IEEE_754 has to be deleted; there is no replacement, and nothing in the 8.21.0 reference documents MathType.

Source: MathType at 8.21.0 and Bucket4j 8.6.0 release notes.

The distributed side: build(key, supplier) and the builder entry points

A ProxyManager hands out a BucketProxy for a key. The older way to pass the configuration was the BucketConfiguration itself: proxyManager.builder().build(key, configuration). In 8.21.0 that overload is @Deprecated ("use build(Object, Supplier) instead. This method will be removed soon" in the source). The replacement takes a Supplier<BucketConfiguration> that the manager calls only when the bucket does not exist yet, which saves building a configuration on every request. The other change is how the managers are created. The classes with public constructors (CaffeineProxyManager, InfinispanProxyManager and the JDBC SQLProxyConfiguration family) are deprecated in favour of entry-point classes named Bucket4j<Backend>, whose static methods return a builder that carries the client-side settings (clientClock, expirationAfterWrite, requestTimeout, maxRetries, retryStrategy, executionStrategy and the others). The 8.11.1 release notes list "unified style builders for all ProxyManagers" (#467).

The example uses the Caffeine backend because it needs no server: the old constructor keeps the buckets in a local cache, and its keepAfterRefillDuration argument means "keep an entry for that long after the bucket has refilled completely", which is ExpirationAfterWriteStrategy.basedOnTimeForRefillingBucketUpToMax(duration) in the new API.

Before: public constructor and build(key, config) (deprecated, compiles on 8.21.0 with warnings)
ProxyManager<String> proxyManager = new CaffeineProxyManager<>(
    Caffeine.newBuilder().maximumSize(10_000),
    Duration.ofMinutes(1),                                   // keep after refill
    ClientSideConfig.getDefault().withClientClock(clock));

BucketConfiguration configuration = BucketConfiguration.builder()
    .addLimit(Bandwidth.simple(100, Duration.ofMinutes(1)))
    .build();

BucketProxy bucket = proxyManager.builder().build("client-1", configuration);
After: Bucket4jCaffeine.builderFor and build(key, supplier)
ProxyManager<String> proxyManager = Bucket4jCaffeine
    .<String>builderFor(Caffeine.newBuilder().maximumSize(10_000))
    .expirationAfterWrite(ExpirationAfterWriteStrategy
        .basedOnTimeForRefillingBucketUpToMax(Duration.ofMinutes(1)))
    .clientClock(clock)
    .build();

BucketConfiguration configuration = BucketConfiguration.builder()
    .addLimit(limit -> limit.capacity(100).refillGreedy(100, Duration.ofMinutes(1)))
    .build();

BucketProxy bucket = proxyManager.builder().build("client-1", () -> configuration);
// or, when the supplier is all you need:
BucketProxy same = proxyManager.getProxy("client-1", () -> configuration);

In the test both managers were given a manual TimeMeter as clock. After consuming 70 of 100 tokens both proxies reported 30 available, and after 30 simulated seconds both reported 80. getProxy(key, supplier) returned a proxy over the same bucket as builder().build(key, supplier): a second proxy for the same key was refused a token that the first had taken. The constructors are @Deprecated in the 8.21.0 source (a reflection check in the test confirmed it for the two-argument CaffeineProxyManager constructor and for RemoteBucketBuilder.build(Object, BucketConfiguration)).

Source: Bucket4j reference: ProxyManager and the 8.21.0 source of Bucket4jCaffeine, RemoteBucketBuilder and AbstractProxyManagerBuilder. The backend-by-backend entry points and what each requires are on Bucket4j backends, and the settings of the builder on distributed rate limiting.

8.11.1: JDK 17 and the artifact rename

The 8.11.1 release notes list three items: split Redis support into individual Maven modules (#466), unified builders (#467) and the migration to JDK 17 (#474). Under "Backward incompatible changes" they say that the target JDK is now part of the artifact name: com.bucket4j:bucket4j-core became com.bucket4j:bucket4j_jdk17-core, and that the Redis dependencies were split into the Jedis, Lettuce and Redisson modules. On Maven Central bucket4j_jdk17- starts at 8.11.0 (the GitHub release 8.11.0 is dated 24 April 2024) and the notes are filed under 8.11.1. Because the *artifactId changes, a dependency bot that follows bucket4j-core never sees the new releases: the legacy bucket4j-core ends at 8.10.1 on Maven Central.

If your runtime is Java 11, 8.15.0 is the newest release you can run, with the bucket4j_jdk11- ids, and the Java 8 route is the commercial one. The project’s java-compatibility-matrix.md still shows the legacy names for JDK 11 (bucket4j-core) and bucket4j_jdk8- for Java 8, so it predates the rename; the table above is the Maven Central truth.

From 8.16 to 8.21: new entry points and modules

Since 8.16 the releases have added backends and one build tool, not new concepts. Every new module follows the entry-point rule of the previous section: a Bucket4j<Backend> class with static builder methods, no public constructor to learn. The versions below are the first on Maven Central, cross-checked against the release notes.

Two facts from this list matter at upgrade time. The redis, hazelcast-all and infinispan-all aggregator artifacts have no 8.21.0 build, so a dependency on one of them freezes at 8.14.0; use the individual modules. And the release notes of 8.20.0 and 8.21.0 repeat the items of earlier releases (#580, #588, #615, #595 and #606 appear in both), so read them as a running list and not as a per-release diff; the Maven Central versions are the reliable record of which module arrived when.

The following code shows what a new-style entry point looks like in a service and compiles on 8.21.0 with only the Caffeine module on the classpath; the other entry points above have the same shape and differ in the client object they take.

An 8.21.0 proxy manager and a bucket through the supplier form
ProxyManager<String> proxyManager = Bucket4jCaffeine
    .<String>builderFor(Caffeine.newBuilder().maximumSize(10_000))
    .expirationAfterWrite(ExpirationAfterWriteStrategy
        .basedOnTimeForRefillingBucketUpToMax(Duration.ofMinutes(5)))
    .build();

Supplier<BucketConfiguration> freePlan = () -> BucketConfiguration.builder()
    .addLimit(limit -> limit.capacity(20).refillGreedy(20, Duration.ofMinutes(1)))
    .build();

BucketProxy bucket = proxyManager.getProxy("api:alice", freePlan);
boolean allowed = bucket.tryConsume(1);

YAML: what changes and what does not

The property model is stable across the three Boot-4-era versions. The same filter YAML bound and limited identically on 0.14.0 (Spring Boot 4.0.3) and on 0.20.0-RC1 (Spring Boot 4.1.1) in the scratch project of this section, and the property classes of the two tags have the same keys and defaults for bucket4j.filters[], rate-limits[] and bandwidths[]. What changes is a mode that disappears and one property that was removed earlier.

Before: a 0.14.0 Gateway filter (the only filter-method value that disappears)
bucket4j:
  enabled: true
  filters:
    - id: gateway-books
      cache-name: buckets
      filter-method: gateway          # FilterMethod.GATEWAY exists in 0.13.0 and 0.14.0
      url: /api/.*
      rate-limits:
        - cache-key: "getRemoteAddr()"
          bandwidths:
            - capacity: 100
              time: 1
              unit: minutes
After: the servlet filter on 0.20.0-RC1 (the same keys, a supported filter-method)
bucket4j:
  enabled: true
  cache-to-use: jcache
  filters:
    - id: servlet-books
      cache-name: buckets
      filter-method: servlet          # SERVLET, WEBFLUX and JMS are the values left
      url: /api/.*
      rate-limits:
        - cache-key: "getRemoteAddr()"
          bandwidths:
            - capacity: 100
              time: 1
              unit: minutes

On a Spring Cloud Gateway application there is no replacement inside the starter: filter-method: gateway no longer binds on the 0.20.0-RC1 tag and the Gateway filter factory is gone. The supported route is the gateway’s own limiter, which uses Bucket4j directly, described on Bucket4j in Spring Cloud Gateway. And the removed expression property, which the README’s 0.12 entry names, is a plain rename:

Before and after: the 0.12 rename of expression to cache-key
# before 0.12 (the property is removed, not just deprecated)
bucket4j:
  filters:
    - cache-name: buckets
      url: /api/.*
      rate-limits:
        - expression: "getRemoteAddr()"
          bandwidths:
            - capacity: 100
              time: 1
              unit: minutes

# 0.12 and later
bucket4j:
  filters:
    - cache-name: buckets
      url: /api/.*
      rate-limits:
        - cache-key: "getRemoteAddr()"
          bandwidths:
            - capacity: 100
              time: 1
              unit: minutes

All key names in these three YAML blocks were checked against the property classes of the 0.20.0-RC1 tag (Bucket4JConfiguration, RateLimit, BandWidth) and, for filter-method: gateway, against the FilterMethod enum of 0.14.0, which has SERVLET, WEBFLUX, GATEWAY and JMS, where the 0.20.0-RC1 enum has no GATEWAY. A neighbouring expression exists only on the metric tags (MetricTag), a different property. The starter also needs a Bean Validation provider (spring-boot-starter-validation), because it validates its properties at startup.

What changed

  • 7.x to 8.0: JDK 11 baseline, groupId com.bucket4j, dedicated bucket4j_jdk8-* artifacts for Java 8.

  • 8.5.0: the Bandwidth.builder() and addLimit(limit → …​) API; Bandwidth.simple, Bandwidth.classic, withInitialTokens, withId and the Refill class are deprecated; the Bucket4j factory class is gone.

  • 8.6.0: MathType.IEEE_754 removed.

  • 8.7.0: Amazon DynamoDB support removed.

  • 8.11.x: bucket4j_jdk17-* artifacts, Redis split into redis-common plus a client, unified builders for every ProxyManager.

  • 8.15.0: the last bucket4j_jdk11-* release.

  • 8.16 to 8.21: GLIDE, Vert.x, Couchbase, Geode, Memcached, Cassandra, Ignite 3, infinispan-15 and coherence-21, the compare-and-swap retry mechanism, Redis Sentinel through Lettuce, and in 8.21.0 the bucket4j_jdk17-bom.

  • Starter: 0.13.0 on the jdk17 artifacts, 0.14.0 on Spring Boot 4, 0.20.0-RC1 on the new module layout without the Gateway filter; no GA 0.20.0 yet.

  • Version 9: not released; the policy removes deprecated API only in a major release, so everything on this page that avoids deprecated API should carry over. The state of the line is on the previous-releases page.
