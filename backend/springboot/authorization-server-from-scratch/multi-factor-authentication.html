Authorization Server from Scratch: Multi-Factor Authentication & Step-Up

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page adds a second factor to the authorization server built in the previous pages and makes the result visible to the rest of the system: the tokens say how the user signed in, and an API can demand a stronger or fresher sign-in than the one a token proves. It covers the policy that decides when a second factor is needed, the second-factor page, step-up through acr_values and max_age, the lockout that stops code guessing, and the signed "remember this device" cookie. The authenticator app itself (TOTP enrolment, verification and recovery codes) is the subject of the next page, TOTP Authenticator Apps & Recovery Codes; here it only appears as the one second factor that is registered.

What you build

The theory is in the OAuth Reference: Authentication Methods, 2FA and Passwordless explains the two axes (how the user proved who they are, and how the client learns it), the RFC 8176 amr values and the RFC 9470 step-up exchange (see its section Step-up mid-session: RFC 9470), and Spring Boot Authentication Methods: Multi-factor authentication shows the framework’s own API. This page is the worked example of both.

What Spring Security 7 gives you. Every completed authentication step adds a FactorGrantedAuthority (for example FACTOR_PASSWORD) to the Authentication, with the instant it was granted. @EnableMultiFactorAuthentication registers the authorization rules and the entry points that send a user who lacks a required factor to the page that collects it. That is all the framework knows: it has no idea what a "second" factor is, which clients require one, what goes into a token or how recent a sign-in must be.

What the example adds on top of that:

  • a registry of AuthenticationFactor beans (identifier, amr value, authority and a FactorStrength) and a pure MfaPolicy that says when a set of factors is enough, when a second factor is required (the client, or the user’s account, asks for it) and when an authentication counts as multi-factor;

  • a MfaAuthorizationManager that applies the policy to the consent page and to /oauth2/authorize;

  • a FactorTimeline that reads the factor authorities once, so the amr, acr and auth_time claims and the step-up checks always agree;

  • the second-factor page, built from SecondFactorFragment beans in the same way as the login page;

  • step-up on the authorization endpoint (max_age, acr_values) and the RFC 9470 challenge on the account API;

  • a failed-attempt lockout shared by every second factor, and a signed trusted-device cookie that skips the code on a browser the user chose to remember, without ever counting as a real second factor.

How it works

The sign-in below is the sequence of a user whose account requires a second factor (the administrator forced it, or the user has a confirmed authenticator app, or the client is registered with mfaRequired). The primary factor is the password of Storing Passwords Securely; the code is verified by the TOTP use case of the next page.

sequenceDiagram autonumber actor U as User participant B as Browser participant A as auth-server :9000 B->>A: GET /oauth2/authorize (client_id, PKCE challenge) A-->>B: 302 to /login (no session yet) U->>A: POST /login (username and password) A->>A: grant FACTOR_PASSWORD with the current instant A-->>B: 302 back to /oauth2/authorize (saved request) B->>A: GET /oauth2/authorize A->>A: MfaAuthorizationManager.evaluate: required, not satisfied A-->>B: 302 to /login/second-factor (request saved) B->>A: GET /login/second-factor A-->>B: 200 second-factor page (one fragment per factor) U->>A: POST /login/second-factor/totp (code) A->>A: check lockout, verify code, grant FACTOR_TOTP A-->>B: 302 back to /oauth2/authorize (resumed) B->>A: GET /oauth2/authorize A->>A: policy satisfied A-->>B: 302 to /oauth2/consent when consent is required U->>A: POST /oauth2/consent (approve) A-->>B: 302 to redirect_uri with the authorization code B->>A: POST /oauth2/token (code, code_verifier) A->>A: MfaClaimsContributor adds amr, acr and auth_time A-->>B: tokens with amr pwd, otp, mfa and acr urn:irurueta:acr:mfa

The policy sits in two places. MfaLoginChainCustomizer (a LoginChainCustomizer of the extension points described in Architecture) puts the manager in front of the consent page and tells Spring Security to send a user with a missing second-factor authority to the second-factor page. MfaProtocolChainCustomizer (a ProtocolChainCustomizer) wraps the authorization-code request validator, so a request that reaches /oauth2/authorize without enough factors is refused with a redirect to the same page instead of getting a code.

Factor accumulation

A factor is just an authority with an instant, and the factors a session holds decide what the next token says:

stateDiagram-v2 [*] --> Anonymous Anonymous --> PasswordOnly: password accepted (FACTOR_PASSWORD) PasswordOnly --> PasswordAndTrusted: trusted-device cookie valid (FACTOR_TRUSTED_DEVICE) PasswordOnly --> MultiFactor: second factor verified (FACTOR_TOTP) PasswordAndTrusted --> MultiFactor: step-up asks for acr mfa and a real code is verified PasswordOnly: claims amr pwd and the password acr PasswordAndTrusted: sign-in policy satisfied but claims stay amr pwd MultiFactor: claims amr pwd, otp, mfa and the mfa acr MultiFactor --> [*]

The four FactorStrength values define the rules: PRIMARY_STRONG (a passkey) is enough alone, PRIMARY (the password) needs a SECOND factor (a TOTP code) or a REMEMBERED one (the trusted device), and a REMEMBERED factor is never reported, so it can satisfy the sign-in but not a step-up. A passkey proves one thing, however strongly, so it is multi-factor only when its factor says so. auth_time is the instant of the primary factor: adding a second factor later never makes the sign-in look newer.

Step-up

Step-up is the same machinery driven by the client. It has two entry points, an authorization request and an API call, and they meet in the tokens:

sequenceDiagram autonumber participant C as Client participant R as auth-server /api (resource) participant A as auth-server /oauth2/authorize C->>R: DELETE /api/account/totp (bearer token, acr pwd) R->>R: StepUpGuard: confirmed second factor, token not multi-factor or too old R-->>C: 401 WWW-Authenticate insufficient_user_authentication, acr_values, max_age C->>A: GET /oauth2/authorize with acr_values and max_age from the challenge A->>A: StepUpAuthorizationRequestConverter: max_age exceeded or acr not reached A-->>C: sign in again, or ask for a real second factor C->>A: POST /oauth2/token A-->>C: new token with acr mfa and a fresh auth_time C->>R: DELETE /api/account/totp (new token) R-->>C: 204

Data

Two migrations hold everything this page persists, both in the authserver database. V400 adds the users.mfa_required flag (an administrator can force a second factor on an account), the security_events audit trail (type, user_id, username, detail, occurred_at; the user reference is nullable and ON DELETE SET NULL, so failed logins for unknown names can be stored and the trail outlives the account) and second_factor_attempts, one row per user with the failure counter and the instant until which the second factor is locked:

ALTER TABLE users
    ADD COLUMN mfa_required boolean NOT NULL DEFAULT FALSE;

-- Audit trail. The user is kept as a nullable reference so events of failed logins for unknown names can be stored
-- and so the trail outlives a deleted account.
CREATE TABLE security_events
(
    id          uuid                     NOT NULL,
    type        varchar(50)              NOT NULL,
    user_id     uuid REFERENCES users (id) ON DELETE SET NULL,
    username    varchar(100),
    detail      varchar(500),
    occurred_at timestamp with time zone NOT NULL,
    PRIMARY KEY (id)
);

CREATE INDEX ix_security_events_user_occurred_at ON security_events (user_id, occurred_at);

CREATE TABLE second_factor_attempts
(
    user_id      uuid                     NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    failed_count integer                  NOT NULL DEFAULT 0,
    locked_until timestamp with time zone,
    PRIMARY KEY (user_id)
);

This is plain PostgreSQL DDL run by Flyway through Spring Boot; the audit event types are the values of the SecurityEventType enum (login and second-factor successes and failures, lockouts, trusted-device events, recovery-code use).

V420 adds trusted_devices. The table never stores the token the browser holds: hashed_token is a hash of it, with a unique constraint, and a device expires (expires_at) or is deleted by revoking it:

CREATE TABLE trusted_devices
(
    id           uuid                     NOT NULL,
    user_id      uuid                     NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    hashed_token varchar(128)             NOT NULL,
    user_agent   varchar(255),
    expires_at   timestamp with time zone NOT NULL,
    created_at   timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    CONSTRAINT uq_trusted_devices_hashed_token UNIQUE (hashed_token)
);

CREATE INDEX ix_trusted_devices_user_id ON trusted_devices (user_id);
CREATE INDEX ix_trusted_devices_expires_at ON trusted_devices (expires_at);

See PostgreSQL constraints for the foreign keys and the unique constraint. The full schema of every table, with the other migrations, is in Data Model.

Code

The policy: when is a second factor required

All the settings come from one record. A value left out takes its default and an invalid one stops the application at startup: five consecutive failures lock the second factor for 15 minutes, a trusted device lasts 30 days, and a multi-factor sign-in must be at most 5 minutes old to disable a factor through the API.

/**
 * Multi-factor settings, bound once from {@code authserver.mfa.*} and injected wherever one of them is needed (the use
 * cases of this module and the step-up guard of the API). A value left out takes its default; an invalid one stops the
 * application at startup.
 *
 * @param maxFailedAttempts     consecutive failed second-factor attempts that lock the second factor (default 5).
 * @param lockout               how long the second factor stays locked (default 15 minutes).
 * @param trustedDeviceValidity how long a device stays trusted (default 30 days).
 * @param totpIssuer            issuer shown by the authenticator app (default {@code Irurueta Auth Server}).
 * @param stepUpMaxAge          how recent the multi-factor sign-in of a bearer token must be to remove or reset a
 *                              second factor through the API (default 5 minutes).
 */
@ConfigurationProperties("authserver.mfa")
public record MfaProperties(
        @DefaultValue("5") int maxFailedAttempts,
        @DefaultValue("PT15M") Duration lockout,
        @DefaultValue("P30D") Duration trustedDeviceValidity,
        @DefaultValue("Irurueta Auth Server") String totpIssuer,
        @DefaultValue("PT5M") Duration stepUpMaxAge) {

    /**
     * Validates the settings.
     *
     * @throws IllegalArgumentException if {@code maxFailedAttempts} is less than one, a duration is missing or not
     *                                  positive, or the issuer is blank.
     */
    public MfaProperties {
        if (maxFailedAttempts < 1) {
            throw new IllegalArgumentException("authserver.mfa.max-failed-attempts must be at least 1");
        }
        requirePositive(lockout, "lockout");
        requirePositive(trustedDeviceValidity, "trusted-device-validity");
        requirePositive(stepUpMaxAge, "step-up-max-age");
        if (totpIssuer == null || totpIssuer.isBlank()) {
            throw new IllegalArgumentException("authserver.mfa.totp-issuer must not be blank");
        }
    }

    /**
     * Rejects a missing or non-positive duration.
     *
     * @param value the duration.
     * @param key   the key of the setting, below {@code authserver.mfa}.
     * @throws IllegalArgumentException if the duration is missing, zero or negative.
     */
    private static void requirePositive(final Duration value, final String key) {
        if (value == null || value.isZero() || value.isNegative()) {
            throw new IllegalArgumentException("authserver.mfa." + key + " must be positive");
        }
    }
}

Spring Boot documents constructor binding and @DefaultValue in Constructor Binding.

A second factor is required when either the account or the client asks. The account asks when an administrator forced it or when the user has confirmed a factor, because a factor the user enrolled must protect every sign-in; removing the last factor lifts the second reason, never the first:

/**
 * Use case that tells whether the account of a user requires a second factor, whatever the client being served: when
 * an administrator forced it ({@code users.mfa_required}) or when the user has confirmed a second factor (asked to
 * {@link HasConfirmedSecondFactorUseCase}), since a factor the user enrolled must protect every sign-in. The two
 * stay separate: removing the last second factor lifts the second, never the first.
 */
@Service
@Transactional(readOnly = true)
@RequiredArgsConstructor
public class IsUserMfaRequiredUseCase {

    /** Port that provides the user accounts. */
    private final UserAccountRepository userAccountRepository;

    /** Port that stores the per-user multi-factor settings. */
    private final UserMfaSettingsRepository userMfaSettingsRepository;

    /** Use case that tells whether the user has confirmed a second factor. */
    private final HasConfirmedSecondFactorUseCase hasConfirmedSecondFactorUseCase;

    /**
     * Tells whether an account requires a second factor.
     *
     * @param username name the user signs in with.
     * @return {@code true} when the account exists and either an administrator requires it or the user has a
     *         confirmed second factor; {@code false} otherwise, or when the account does not exist.
     */
    public boolean execute(final String username) {
        return userAccountRepository.findByUsername(username)
                .map(UserAccount::id)
                .map(id -> userMfaSettingsRepository.isRequired(id) || hasConfirmedSecondFactorUseCase.execute(id))
                .orElse(false);
    }
}

This is application logic, not framework API; the transaction rules it relies on are in the Spring Framework @Transactional reference.

The client asks through its registration flag. How the flag is stored is the business of the clients adapter alone (see Registered Clients & Client Management):

/**
 * Use case that tells whether a client makes multi-factor authentication mandatory for every user signing in through
 * it ({@link ClientRegistration#mfaRequired()}). How the flag is stored is the business of the client port's adapter
 * alone.
 */
@Service
@Transactional(readOnly = true)
@RequiredArgsConstructor
public class IsClientMfaRequiredUseCase {

    /** Port that stores the clients. */
    private final ClientRegistrationRepository clientRegistrationRepository;

    /**
     * Tells whether a client requires a second factor.
     *
     * @param clientId public identifier of the client, or {@code null} when the request names none.
     * @return {@code true} when the client is registered and requires it; {@code false} otherwise.
     */
    public boolean execute(final String clientId) {
        return clientId != null && clientRegistrationRepository.findByClientId(clientId)
                .map(ClientRegistration::mfaRequired)
                .orElse(false);
    }
}

The unknown-client case returns false, so a request that names no registered client is never turned into a second-factor loop; the authorization endpoint rejects it on its own. See the Authorization Server core model components for the registered client.

Reading the factors: timeline and claims

FactorTimeline is the single place that reads the factor authorities. It keeps only the factors the policy reports (so a trusted device is invisible), orders them by instant, and answers the three questions the rest of the code asks: which amr values, is it multi-factor, and when did the primary factor happen.

/**
 * Reads, from the {@link FactorGrantedAuthority} instances of an authentication, the factors that prove something
 * about it and when they were presented. It is the single place the claims ({@link MfaClaimsContributor}) and the
 * step-up checks ({@link StepUpAuthorizationRequestConverter}) take {@code amr}, {@code acr} and {@code auth_time}
 * from, so both always agree:
 *
 * <ul>
 *   <li>only the factors of the {@link AuthenticationFactorRegistry} that {@link MfaPolicy#isReported} accepts count:
 *       a remembered (trusted) device does not;</li>
 *   <li>the authentication is multi-factor when {@link MfaPolicy#isMultiFactor} says so: at least two distinct
 *       factors count, or one counted factor proves a multi-factor authentication alone;</li>
 *   <li>{@code auth_time} is when the primary factor was presented (the earliest one when there are several), so a
 *       second factor added later never makes the sign-in look newer; without a primary factor it is the earliest
 *       counted factor.</li>
 * </ul>
 */
@Component
@RequiredArgsConstructor
public class FactorTimeline {

    /** Registry of the known factors. */
    private final AuthenticationFactorRegistry factorRegistry;

    /** Policy that tells which factors are reported and which are primary. */
    private final MfaPolicy mfaPolicy;

    /**
     * Lists the factor authorities of an authentication that count, oldest first.
     *
     * @param authentication the authentication.
     * @return the counted factor authorities, sorted by issue instant; empty when none.
     */
    public List<FactorGrantedAuthority> countedFactors(final Authentication authentication) {
        return factorsMatching(authentication, mfaPolicy::isReported);
    }

    /**
     * Lists the {@code amr} values of the counted factors, in the order they were presented, without duplicates.
     *
     * @param authentication the authentication.
     * @return the values; empty when no factor counts.
     */
    public List<String> amrValues(final Authentication authentication) {
        return countedFactors(authentication).stream()
                .map(authority -> factorRegistry.findByAuthority(authority.getAuthority()))
                .flatMap(Optional::stream)
                .map(AuthenticationFactor::amrValue)
                .distinct()
                .toList();
    }

    /**
     * Tells whether an authentication is multi-factor, by {@link MfaPolicy#isMultiFactor} over its counted factors.
     *
     * @param authentication the authentication.
     * @return {@code true} for a multi-factor authentication.
     */
    public boolean isMultiFactor(final Authentication authentication) {
        return mfaPolicy.isMultiFactor(countedFactors(authentication).stream()
                .map(authority -> factorRegistry.findByAuthority(authority.getAuthority()))
                .flatMap(Optional::stream)
                .collect(Collectors.toSet()));
    }

    /**
     * Finds the instant of the authentication, the one {@code auth_time} reports and {@code max_age} is measured
     * from.
     *
     * @param authentication the authentication.
     * @return the issue instant of the earliest primary factor, or else of the earliest counted factor; empty when no
     *         counted factor carries an instant.
     */
    public Optional<Instant> authTime(final Authentication authentication) {
        return earliest(factorsMatching(authentication,
                factor -> mfaPolicy.isReported(factor) && mfaPolicy.isPrimary(factor)))
                .or(() -> earliest(countedFactors(authentication)));
    }

    /**
     * Lists the factor authorities of an authentication whose registered factor passes a test, oldest first.
     *
     * @param authentication the authentication.
     * @param test           the test of the registered factor.
     * @return the matching authorities.
     */
    private List<FactorGrantedAuthority> factorsMatching(final Authentication authentication,
            final Predicate<AuthenticationFactor> test) {
        return authentication.getAuthorities().stream()
                .filter(FactorGrantedAuthority.class::isInstance)
                .map(FactorGrantedAuthority.class::cast)
                .filter(authority -> factorRegistry.findByAuthority(authority.getAuthority()).filter(test).isPresent())
                .sorted(Comparator.comparing(FactorGrantedAuthority::getIssuedAt,
                        Comparator.nullsLast(Comparator.naturalOrder())))
                .toList();
    }

    /**
     * Finds the earliest issue instant of some factor authorities.
     *
     * @param factors the authorities.
     * @return the earliest instant, or empty when none carries one.
     */
    private static Optional<Instant> earliest(final List<FactorGrantedAuthority> factors) {
        return factors.stream().map(FactorGrantedAuthority::getIssuedAt).filter(Objects::nonNull)
                .min(Comparator.naturalOrder());
    }
}

The class reads FactorGrantedAuthority, whose getIssuedAt() is the instant it works from; the claim names come from RFC 8176 (amr) and OpenID Connect Core (acr, auth_time).

MfaClaimsContributor is a JwtClaimsContributor of the token pipeline from Access, Refresh & ID Tokens. It adds amr (plus mfa when there are at least two factors), acr (the multi-factor or the password class) and auth_time (as epoch seconds, on access tokens only, because the framework sets it itself on ID tokens). A token that carries no counted factor, such as one from the client credentials grant, gets none of the three.

/**
 * Adds to the access and ID tokens how the user authenticated: {@code amr} (the RFC 8176 values of the factors really
 * presented, plus {@code mfa} when there are at least two), {@code acr} (the class of the authentication, see
 * {@link AuthenticationContextClass}) and {@code auth_time} (the epoch second the primary factor was presented, a
 * number per OIDC; access tokens only, because the framework sets it on ID tokens). Every value comes from the
 * {@link FactorTimeline}, which reads the {@link org.springframework.security.core.authority.FactorGrantedAuthority}
 * instances of the principal: authorities of an unknown factor and of a remembered (trusted) device are ignored, so a
 * browser that skipped the second factor gets {@code amr [pwd]} and the password class. A token with no counted factor
 * (for example of the client credentials grant) gets none of the claims.
 */
@Component
@Order(MfaClaimsContributor.ORDER)
@RequiredArgsConstructor
public class MfaClaimsContributor implements JwtClaimsContributor {

    /** Order of the contributor: after the built-in claims and the default contributors. */
    public static final int ORDER = 100;

    /** RFC 8176 {@code amr} value that tells that more than one factor was used. */
    public static final String MULTI_FACTOR_AMR_VALUE = "mfa";

    /** Reads the counted factors of the principal and their instants. */
    private final FactorTimeline factorTimeline;

    @Override
    public void contribute(final OAuth2TokenContext context, final Map<String, Object> claims) {
        final var principal = context.getPrincipal();
        if (principal == null) {
            return;
        }
        final var authTime = factorTimeline.authTime(principal);
        if (authTime.isEmpty()) {
            return;
        }
        // a mutable list on purpose: the authorization store only deserializes allow-listed types
        final var amr = new ArrayList<String>(factorTimeline.amrValues(principal));
        final var multiFactor = factorTimeline.isMultiFactor(principal);
        if (multiFactor) {
            amr.add(MULTI_FACTOR_AMR_VALUE);
        }
        claims.put(IdTokenClaimNames.AMR, amr);
        claims.put(IdTokenClaimNames.ACR,
                multiFactor ? AuthenticationContextClass.MULTI_FACTOR : AuthenticationContextClass.PASSWORD);
        // the framework sets auth_time itself on ID tokens (as a date it expects to read back on refresh)
        if (OAuth2TokenType.ACCESS_TOKEN.equals(context.getTokenType())) {
            claims.put(IdTokenClaimNames.AUTH_TIME, authTime.get().getEpochSecond());
        }
    }
}

This contributor plugs into OAuth2TokenCustomizer, the framework hook for custom token claims.

The second-factor page

The page follows the login page’s design: a controller renders second-factor.html, and each second factor contributes a fragment through the SecondFactorFragment interface, which names the template, the fragment, the position and the model attributes it needs for the signed-in user. Adding a factor is adding a bean; the page is not edited.

/**
 * Extension point that lets a second factor contribute a Thymeleaf fragment to the second-factor page. The page
 * template renders one fragment per bean, sorted by {@link #order()}, in the same way the login page renders the
 * {@link com.irurueta.authserver.authorization.api.web.login.LoginMethodFragment} beans. A fragment that depends on
 * the signed-in user (an enrolment form, a warning) contributes its data through
 * {@link #modelAttributes(Authentication)}.
 */
public interface SecondFactorFragment {

    /**
     * Gets the name of the template that holds the fragment.
     *
     * @return the template name.
     */
    String templateName();

    /**
     * Gets the name of the fragment inside the template.
     *
     * @return the fragment name.
     */
    String fragmentName();

    /**
     * Gets the position of the fragment in the page; lower values are rendered first.
     *
     * @return the order.
     */
    int order();

    /**
     * Gets the Thymeleaf fragment expression, such as {@code template :: fragment}.
     *
     * @return the fragment expression.
     */
    default String reference() {
        return templateName() + " :: " + fragmentName();
    }

    /**
     * Gets the model attributes the fragment needs for the signed-in user, added to the model of the page. Their
     * names should start with the factor's own prefix (for example {@code totp}), since every fragment shares the
     * model.
     *
     * @param authentication the authentication of the user the page is rendered for.
     * @return the attributes; none by default.
     */
    default Map<String, Object> modelAttributes(final Authentication authentication) {
        return Map.of();
    }
}

The interface is the example’s own, built on Thymeleaf template layout and fragment expressions.

The controller collects the model attributes of every fragment, adds the fragment list and, when the previous attempt failed, a message that tells a lockout from a wrong code and never reveals whether the code was close:

    /**
     * Renders the second-factor page.

Step-up on the authorization endpoint

The converter runs before every other authorization request converter. It only applies to a signed-in user with a counted factor (otherwise it would loop a user who could never satisfy the request through the login page). It throws ReauthenticationRequiredException when more than max_age whole seconds have passed since the primary factor, and a step-up SecondFactorRequiredException when the request asks only for authentication context classes the session has not reached. Unknown classes are ignored, because acr_values is voluntary, and the multi-factor class also satisfies a request for the password class.

    /**
     * Checks the step-up parameters of a request.
     *
     * @param request the request.
     * @return always {@code null}: this converter only vetoes requests.
     * @throws ReauthenticationRequiredException if {@code max_age} is exceeded.
     * @throws SecondFactorRequiredException     if the requested {@code acr_values} are not reached.
     */
    @Override
    public Authentication convert(final HttpServletRequest request) {
        final var user = SecurityContextHolder.getContext().getAuthentication();
        if (!MfaAuthorizationManager.isUser(user)) {
            return null;
        }
        final var authTime = factorTimeline.authTime(user);
        if (authTime.isEmpty()) {
            return null;
        }
        if (maxAgeExceeded(request.getParameter(MAX_AGE_PARAMETER), authTime.get())) {
            throw new ReauthenticationRequiredException();
        }
        if (!acrReached(request.getParameter(ACR_VALUES_PARAMETER), factorTimeline.isMultiFactor(user))) {
            throw SecondFactorRequiredException.forStepUp();
        }
        return null;
    }

The parameters are defined by OpenID Connect Core, Authentication Request (max_age, acr_values); the hook is the authorizationRequestConverter of the authorization endpoint configurer.

Step-up for the account API

The second half of step-up is the API that decides a token is not good enough. The account endpoints that remove or weaken a second factor (disable the authenticator app, generate new recovery codes, revoke a trusted device) call StepUpGuard first. If the account has a confirmed second factor, the bearer token must carry acr urn:irurueta:acr:mfa and an auth_time that is not in the future and not older than authserver.mfa.step-up-max-age. An account without a second factor cannot step up, so it is not asked to. The /api/** chain itself is unchanged: the check is a call in the controllers.

/**
 * Guards the API operations that remove or reset a second factor (disabling the authenticator app, generating new
 * recovery codes, revoking a trusted device): a stolen token, or a session left open, must not be enough to weaken the
 * account. While the account has a confirmed second factor, the bearer token must show a multi-factor sign-in
 * ({@code acr} {@value AuthenticationContextClass#MULTI_FACTOR}) whose {@code auth_time} is within
 * {@code authserver.mfa.step-up-max-age}; otherwise an {@link InsufficientUserAuthenticationException} asks the client
 * to step up (RFC 9470). An account without a second factor cannot step up, so it is not asked to. The controllers call
 * it first; the {@code /api/**} chain itself is not changed.
 */
@Component
@RequiredArgsConstructor
public class StepUpGuard {

    /** Tells whether the account has a confirmed second factor. */
    private final HasConfirmedSecondFactorUseCase hasConfirmedSecondFactorUseCase;

    /** Multi-factor settings, with the maximum age of the sign-in. */
    private final MfaProperties mfaProperties;

    /** Clock the age of the sign-in is measured with. */
    private final Clock clock;

    /**
     * Requires a recent multi-factor sign-in from the bearer token of the current request.
     *
     * @param userId identifier of the account the operation acts on.
     * @throws InsufficientUserAuthenticationException if the account has a confirmed second factor and the token does
     *                                                 not show a recent enough multi-factor sign-in.
     */
    public void requireRecentMultiFactor(final UUID userId) {
        if (!hasConfirmedSecondFactorUseCase.execute(userId)) {
            return;
        }
        final var maxAge = mfaProperties.stepUpMaxAge();
        final var authentication = SecurityContextHolder.getContext().getAuthentication();
        if (!(authentication instanceof JwtAuthenticationToken token)
                || !isRecentMultiFactor(token.getToken(), maxAge)) {
            throw new InsufficientUserAuthenticationException(AuthenticationContextClass.MULTI_FACTOR, maxAge);
        }
    }

    /**
     * Tells whether a token shows a multi-factor sign-in that is recent enough.
     *
     * @param jwt    the bearer token.
     * @param maxAge maximum age of the sign-in.
     * @return {@code true} when {@code acr} is the multi-factor class and {@code auth_time} is at most {@code maxAge}
     *         old (and not in the future).
     */
    private boolean isRecentMultiFactor(final Jwt jwt, final Duration maxAge) {
        if (!AuthenticationContextClass.MULTI_FACTOR.equals(jwt.getClaimAsString(IdTokenClaimNames.ACR))) {
            return false;
        }
        final var authTime = jwt.getClaimAsInstant(IdTokenClaimNames.AUTH_TIME);
        if (authTime == null) {
            return false;
        }
        final var age = Duration.between(authTime, clock.instant());
        return !age.isNegative() && age.compareTo(maxAge) <= 0;
    }
}

This guard reads the claims of the Jwt that the JWT resource server support puts in a JwtAuthenticationToken.

When the guard throws, the exception handler builds the answer RFC 9470 defines: 401, error insufficient_user_authentication, and the acr_values and max_age the client must send when it signs the user in again, plus a problem-details body:

    /**
     * Answers a token whose sign-in is not recent or strong enough: {@code 401} with the RFC 9470 challenge, which
     * tells the client which {@code acr_values} and {@code max_age} to ask for when it signs the user in again.
     *
     * @param exception the failure.
     * @return the {@code 401} problem detail with the {@code WWW-Authenticate} challenge.
     */
    @ExceptionHandler(InsufficientUserAuthenticationException.class)
    public ResponseEntity<ProblemDetail> handleInsufficientUserAuthentication(
            final InsufficientUserAuthenticationException exception) {
        final var problem = ProblemDetail.forStatusAndDetail(HttpStatus.UNAUTHORIZED, exception.getMessage());
        problem.setType(URI.create(TYPE_BASE + "insufficient-user-authentication"));
        problem.setTitle("Step-up authentication required");
        final var headers = new HttpHeaders();
        headers.set(HttpHeaders.WWW_AUTHENTICATE, "Bearer error=\"insufficient_user_authentication\", acr_values=\""
                + exception.getAcrValues() + "\", max_age=\"" + exception.getMaxAge().toSeconds() + "\"");
        return problemResponse(problem, headers);
    }

The challenge format is RFC 9470, section 3; the body is Spring’s ProblemDetail.

Lockout

A six-digit code has only a million values, so guessing is stopped by counting failures per user, not per IP address. Every second-factor verification (the TOTP code, a recovery code, a one-time code) is a transactional use case that starts with this check. The check locks the user’s attempt row until the end of the transaction, so two verifications of the same user run one after the other and neither can pass the check while the other is about to count a failure.

/**
 * Use case that tells whether the second factor of a user is locked after too many failed attempts. It locks the
 * user's attempt row until the end of the caller's transaction, so the verifications of the same user (each a
 * transactional use case that starts with this check) run one at a time: none of them can pass the check while
 * another one is about to count a failure.
 */
@Service
@Transactional
@RequiredArgsConstructor
public class CheckSecondFactorLockoutUseCase {

    /** Port that stores the failed-attempt counters. */
    private final SecondFactorAttemptRepository secondFactorAttemptRepository;

    /** Source of the current time. */
    private final Clock clock;

    /**
     * Checks the lockout of a user.
     *
     * @param userId identifier of the user.
     * @return {@code true} if the second factor is locked right now.
     */
    public boolean execute(final UUID userId) {
        return secondFactorAttemptRepository.lockForUpdate(userId).isLocked(clock.instant());
    }
}

The use case is plain Spring transaction management: see the Spring Framework transaction support.

The lock itself is a SELECT ... FOR UPDATE, preceded by an insert that guarantees the row exists. The repository keeps SQL as text blocks, so these two constants are the whole concurrency story:

    /** Statement that creates the clean state of a user unless one exists, so there is always a row to lock. */
    private static final String ENSURE_ATTEMPTS = """
            INSERT INTO second_factor_attempts (user_id, failed_count) VALUES (?, 0)
            ON CONFLICT (user_id) DO NOTHING
            """;

    /**
     * Query returning the state of a user and locking its row until the end of the transaction: a concurrent
     * verification of the same user waits here until the first one commits.
     */
    private static final String LOCK_ATTEMPTS = """
            SELECT failed_count, locked_until FROM second_factor_attempts WHERE user_id = ? FOR UPDATE
            """;

Row locking is documented in the PostgreSQL SELECT locking clause and ON CONFLICT DO NOTHING in INSERT …​ ON CONFLICT.

Counting a failure is one upsert statement: it increments the counter, sets locked_until when the maximum is reached, and restarts the counter at one when an earlier lock has already ended. Concurrent failures serialize on the row, so none is lost.

    /**
     * Single-statement upsert that counts one failure and sets the lock when the maximum is reached. A lock that
     * has already ended restarts the counter at one. Concurrent failures serialize on the row, so none is lost.
     */
    private static final String RECORD_FAILURE = """
            INSERT INTO second_factor_attempts AS t (user_id, failed_count, locked_until)
            VALUES (:userId, 1, CASE WHEN 1 >= :maxAttempts THEN :lockedUntil ELSE NULL END)
            ON CONFLICT (user_id) DO UPDATE SET
                failed_count = CASE WHEN t.locked_until IS NOT NULL AND t.locked_until <= :now
                                    THEN 1 ELSE t.failed_count + 1 END,
                locked_until = CASE
                    WHEN (CASE WHEN t.locked_until IS NOT NULL AND t.locked_until <= :now
                               THEN 1 ELSE t.failed_count + 1 END) >= :maxAttempts THEN :lockedUntil
                    WHEN t.locked_until <= :now THEN NULL
                    ELSE t.locked_until END
            RETURNING failed_count, locked_until
            """;

The statement is run through Spring’s JdbcClient (named parameters as in :maxAttempts); the SQL features are in INSERT …​ ON CONFLICT.

Trusted devices

After a successful second factor the user can tick "remember this device". The server creates a random token, stores only its hash in trusted_devices, and sends the browser the token plus an HMAC signature in the __Host-TRUSTED-DEVICE cookie (the __Host- prefix makes the browser accept it only over HTTPS, from the exact host, with path / and no Domain). The design has three parts.

The factor. A trusted device is registered as a factor of strength REMEMBERED. Together with the password it satisfies the sign-in policy, so the code is not asked again; but it is excluded from amr, acr and auth_time and never satisfies a step-up:

/**
 * Registers the trusted device as an authentication factor of strength {@link FactorStrength#REMEMBERED}: together
 * with the password it satisfies the sign-in policy, so a trusted browser is not asked for the code again, but it is
 * never reported in {@code amr}, {@code acr} or {@code auth_time} and never satisfies a step-up request
 * ({@code acr_values} asking for the multi-factor class, {@code max_age}), which still needs a real second factor.
 */
@Configuration(proxyBeanMethods = false)
public class TrustedDeviceFactor {

    /** Identifier of the factor. */
    public static final String ID = "trusted-device";

    /**
     * Value the factor would have in {@code amr}. RFC 8176 has none for a remembered device, and the factor is never
     * reported, so it is only a label.
     */
    public static final String AMR_VALUE = "trusted-device";

    /** Authority granted by {@link TrustedDeviceFilter} when the browser presents a valid trusted-device cookie. */
    public static final String AUTHORITY = "FACTOR_TRUSTED_DEVICE";

    /**
     * Declares the trusted-device factor.
     *
     * @return the factor.
     */
    @Bean
    public AuthenticationFactor trustedDeviceAuthenticationFactor() {
        return new AuthenticationFactor(ID, AMR_VALUE, AUTHORITY, FactorStrength.REMEMBERED);
    }
}

This is an ordinary Spring @Bean method that declares one more AuthenticationFactor; nothing else in the policy is edited.

The signature. The cookie value is token.signature. The signing port is in the domain and the HMAC-SHA256 adapter sits in the keys module, with a key derived from the key-encryption secret for this purpose only (see Signing Keys, JWS & JWT for the derivation), so the cookie key is never the key that encrypts signing keys:

/**
 * Port that signs the value of the trusted-device cookie and checks that signature, so a value the server did not
 * issue is rejected before anything is looked up. A signed value has the form {@code token.signature}.
 */
public interface TrustedDeviceTokenSigner {

    /**
     * Signs a token.
     *
     * @param token the raw token of a trusted device.
     * @return the value to put in the cookie: the token, a dot and its signature.
     */
    String sign(String token);

    /**
     * Checks the signature of a cookie value, in constant time.
     *
     * @param signedValue the value presented by the browser, possibly {@code null} or malformed.
     * @return the raw token when the value is well formed and its signature is valid; empty otherwise.
     */
    Optional<String> verify(String signedValue);
}

The port follows the hexagonal layering described in Architecture; the technique it hides is the HMAC of RFC 2104.

/**
 * {@link TrustedDeviceTokenSigner} that signs the trusted-device cookie with HMAC-SHA256, under a key derived from the
 * key-encryption secret for this purpose only ({@link PurposeKeyDerivation}). The value is
 * {@code token.signature}, the signature Base64url encoded without padding; it is compared in constant time.
 */
@Component
public class HmacTrustedDeviceTokenSigner implements TrustedDeviceTokenSigner {

    /** Label of the purpose the key is derived for. */
    public static final String PURPOSE = "trusted-device-cookie";

    /** Separator between the token and its signature. */
    private static final char SEPARATOR = '.';

    /** Name of the MAC algorithm. */
    private static final String ALGORITHM = "HmacSHA256";

    /** The signing key. */
    private final SecretKeySpec key;

    /**
     * Derives the signing key.
     *
     * @param derivation derives the key of a purpose from the key-encryption secret.
     */
    public HmacTrustedDeviceTokenSigner(final PurposeKeyDerivation derivation) {
        key = new SecretKeySpec(derivation.keyFor(PURPOSE), ALGORITHM);
    }

    @Override
    public String sign(final String token) {
        return token + SEPARATOR + Base64.getUrlEncoder().withoutPadding().encodeToString(mac(token));
    }

    @Override
    public Optional<String> verify(final String signedValue) {
        if (!StringUtils.hasText(signedValue)) {
            return Optional.empty();
        }
        final var separator = signedValue.lastIndexOf(SEPARATOR);
        if (separator <= 0 || separator == signedValue.length() - 1) {
            return Optional.empty();
        }
        final var token = signedValue.substring(0, separator);
        final byte[] presented;
        try {
            presented = Base64.getUrlDecoder().decode(signedValue.substring(separator + 1));
        } catch (final IllegalArgumentException e) {
            return Optional.empty();
        }
        return MessageDigest.isEqual(mac(token), presented) ? Optional.of(token) : Optional.empty();
    }

    /**
     * Computes the signature of a token.
     *
     * @param token the token.
     * @return the HMAC-SHA256 of its UTF-8 bytes.
     */
    private byte[] mac(final String token) {
        try {
            final var mac = Mac.getInstance(ALGORITHM);
            mac.init(key);
            return mac.doFinal(token.getBytes(StandardCharsets.UTF_8));
        } catch (final GeneralSecurityException e) {
            throw new IllegalStateException(ALGORITHM + " is not available", e);
        }
    }
}

This uses the JDK’s javax.crypto.Mac and compares with MessageDigest.isEqual, which takes the same time whatever the position of the first different byte.

The lookup. The use case verifies the signature first, so a forged or unsigned value is rejected before the account or the database is touched; then it hashes the token and finds a device of that user that has neither expired nor been revoked:

/**
 * Use case that finds the usable (not revoked, not expired) trusted device of a user from the value of the cookie.
 * The signature of the value is checked first, in constant time: a forged or unsigned value is rejected before the
 * account or the device is looked up.
 */
@Service
@Transactional(readOnly = true)
@RequiredArgsConstructor
public class FindTrustedDeviceUseCase {

    /** Port that checks the signature of the cookie value. */
    private final TrustedDeviceTokenSigner trustedDeviceTokenSigner;

    /** Port that provides the user accounts. */
    private final UserAccountRepository userAccountRepository;

    /** Port that stores the trusted devices. */
    private final TrustedDeviceRepository trustedDeviceRepository;

    /** Creator and hasher of the tokens. */
    private final TrustedDeviceTokens trustedDeviceTokens;

    /** Source of the current time. */
    private final Clock clock;

    /**
     * Finds the device.
     *
     * @param username    name the user signed in with.
     * @param cookieValue the signed value presented by the browser.
     * @return the device, or empty if the signature is wrong, the account does not exist, or the token is unknown,
     *         expired, revoked or belongs to another user.
     */
    public Optional<TrustedDevice> execute(final String username, final String cookieValue) {
        return trustedDeviceTokenSigner.verify(cookieValue)
                .flatMap(token -> userAccountRepository.findByUsername(username)
                        .flatMap(account -> trustedDeviceRepository.findUsable(
                                account.id(), trustedDeviceTokens.hash(token), clock.instant())
                                .filter(device -> account.id().equals(device.userId()))));
    }
}

Storing only a hash of the token follows the guidance of the OWASP Session Management Cheat Sheet for session identifiers.

The filter is the only place the cookie is read, and only on GET /login/second-factor, which every request that owes a second factor is sent to, so a user is not looked up on every request. On a valid cookie it replaces the authentication with one that also holds the factor, changes the session id, saves the security context and resumes the interrupted request. While a step-up is pending the cookie is ignored, because a trusted device cannot satisfy it and resuming would redirect straight back to the page:

/**
 * Lets a browser that was trusted earlier skip the second factor of a sign-in. The cookie is only looked at where it
 * matters: on the second-factor page ({@code GET /login/second-factor}), where every request that owes a second
 * factor is sent. Every other request goes through untouched, so a user who never gets the factor is not looked up on
 * each request. When a signed-in user that does not hold the {@link TrustedDeviceFactor} yet reaches that page with
 * the {@code __Host-TRUSTED-DEVICE} cookie, and its signed value belongs to a device of that same user that has
 * neither expired nor been revoked, the authentication of the session is replaced by one that also holds the factor
 * authority (a remembered factor: it satisfies the sign-in policy but is never reported in the tokens), the session
 * id is changed, the session is saved and the request that was interrupted is resumed instead of asking for a code.
 * A forged or unsigned value is rejected by {@link FindTrustedDeviceUseCase} before anything is looked up. While a
 * step-up is pending ({@link SecondFactorRequiredEntryPoint#isStepUpPending}) the cookie is ignored: a trusted
 * device cannot satisfy it, so the page is rendered and asks for a real second factor.
 */
@RequiredArgsConstructor
public class TrustedDeviceFilter extends OncePerRequestFilter {

    /** Matches the request of the second-factor page. */
    private final PathPatternRequestMatcher secondFactorPageMatcher =
            PathPatternRequestMatcher.withDefaults().matcher(HttpMethod.GET, SECOND_FACTOR_PATH);

    /** Use case that finds the trusted device of a signed cookie value. */
    private final FindTrustedDeviceUseCase findTrustedDeviceUseCase;

    /** Adds the factor authority to an authentication. */
    private final FactorGrantor factorGrantor;

    /** Repository the upgraded security context is saved to. */
    private final SecurityContextRepository securityContextRepository;

    /** Handler that resumes the request that was interrupted. */
    private final AuthenticationSuccessHandler resumeHandler;

    /** Authority granted to a trusted device. */
    private final String authority;

    /**
     * Upgrades the authentication and resumes the interrupted request when the second-factor page is requested with
     * the cookie of a valid trusted device.
     *
     * @param request  the request.
     * @param response the response.
     * @param chain    the rest of the chain.
     * @throws ServletException if the chain fails.
     * @throws IOException      if the response cannot be written.
     */
    @Override
    protected void doFilterInternal(final HttpServletRequest request, final HttpServletResponse response,
            final FilterChain chain) throws ServletException, IOException {
        if (!secondFactorPageMatcher.matches(request) || SecondFactorRequiredEntryPoint.isStepUpPending(request)) {
            chain.doFilter(request, response);
            return;
        }
        final var cookie = WebUtils.getCookie(request, TrustedDeviceCookieWriter.COOKIE_NAME);
        final var current = SecurityContextHolder.getContext().getAuthentication();
        if (cookie != null && needsSecondFactor(current) && isTrusted(current, cookie.getValue())) {
            final var upgraded = factorGrantor.grant(current, authority);
            final var context = SecurityContextHolder.getContextHolderStrategy().createEmptyContext();
            context.setAuthentication(upgraded);
            SecurityContextHolder.getContextHolderStrategy().setContext(context);
            // a new level of authentication gets a new session id, against session fixation
            if (request.getSession(false) != null) {
                request.changeSessionId();
            }
            securityContextRepository.saveContext(context, request, response);
            resumeHandler.onAuthenticationSuccess(request, response, upgraded);
            return;
        }
        chain.doFilter(request, response);
    }

    /**
     * Tells whether an authentication is a signed-in user that does not hold the trusted-device authority yet.
     *
     * @param authentication the authentication of the request, possibly {@code null}.
     * @return {@code true} when a user is signed in and the trusted-device authority is missing.
     */
    private boolean needsSecondFactor(final Authentication authentication) {
        return authentication != null && authentication.isAuthenticated()
                && !(authentication instanceof AnonymousAuthenticationToken)
                && authentication.getAuthorities().stream()
                .noneMatch(granted -> authority.equals(granted.getAuthority()));
    }

    /**
     * Tells whether a signed cookie value identifies a valid trusted device of the signed-in user.
     *
     * @param authentication the signed-in user.
     * @param cookieValue    the signed value of the cookie.
     * @return {@code true} when the signature is valid and the device exists and belongs to the user; the use case
     *         only finds devices that have been neither revoked nor expired.
     */
    private boolean isTrusted(final Authentication authentication, final String cookieValue) {
        return findTrustedDeviceUseCase.execute(authentication.getName(), cookieValue).isPresent();
    }
}

Changing the session id and saving the context explicitly are the practices of the Spring Security Authentication Persistence and Session Management page (its session fixation protection and explicit save).

API

The only REST contract of this page is the answer an account operation gives when a token has not stepped up. It is declared once as a reusable response of the OpenAPI document and referenced by the three guarded operations:

    StepUpRequired:
      description: >-
        Missing or invalid bearer token (an RFC 6750 challenge and no body), or the account has a confirmed second
        factor and the token does not show a multi-factor sign-in (acr urn:irurueta:acr:mfa) whose auth_time is within
        authserver.mfa.step-up-max-age (default 5 minutes). The latter is answered as RFC 9470 describes, with
        WWW-Authenticate Bearer error="insufficient_user_authentication", acr_values="urn:irurueta:acr:mfa",
        max_age="300" (the configured age in seconds) and a problem body; the client signs the user in again with
        those acr_values and max_age and retries with the new token.
      headers:
        WWW-Authenticate:
          $ref: '#/components/headers/WwwAuthenticate'
      content:
        application/problem+json:
          schema:
            $ref: '#/components/schemas/Problem'

The format is the OpenAPI response object; the challenge is RFC 9470, section 3.

With a bearer token that was issued after a password-only sign-in, disabling the authenticator app is refused, and nothing is removed:

curl -i -X DELETE http://localhost:9000/api/account/totp \
  -H "Authorization: Bearer $ACCESS_TOKEN"
HTTP/1.1 401
WWW-Authenticate: Bearer error="insufficient_user_authentication", acr_values="urn:irurueta:acr:mfa", max_age="300"
Content-Type: application/problem+json

{ "type": "urn:problem:mfa:insufficient-user-authentication", "title": "Step-up authentication required", ... }

The same 401 is given by POST /api/account/recovery-codes and DELETE /api/account/trusted-devices/{id}. The client reads the two parameters from the header, starts a new authorization request with them and retries with the new token (here $STEPPED_UP_TOKEN):

# 1. open in a browser, then sign in and enter the second factor
#    http://localhost:9000/oauth2/authorize?response_type=code&client_id=...&redirect_uri=...&scope=...
#      &code_challenge=...&code_challenge_method=S256&acr_values=urn:irurueta:acr:mfa&max_age=300
# 2. exchange the code at /oauth2/token, then retry
curl -i -X DELETE http://localhost:9000/api/account/totp \
  -H "Authorization: Bearer $STEPPED_UP_TOKEN"

The response is 204 No Content. Tests

Three integration tests carry tags. They run the whole server against PostgreSQL in a container and drive it with MockMvc, so each proves a behavior across the filter chains, the use cases and the database, which unit tests of one class cannot.

A user who must use a second factor but has none enrols on the page. The test forces MFA on a user, signs in for an authorization request, finds the enrolment form (an otpauth://totp/ URI and a QR image), posts the first code, reads the recovery codes page, checks the codes are shown exactly once, resumes the request and asserts that the access token’s acr is the multi-factor class.

    /**
     * Verifies that a user who must use a second factor but has none enrols an authenticator app on the second-factor

     * second factor.

     * @throws Exception if a request cannot be performed.
     */
    @Test
    void secondFactor_whenUserMustEnrol_enrolsShowsTheRecoveryCodesOnceAndResumes() throws Exception {
        final var user = getFixtures().createUser();

        final var verifier = newVerifier();
        final var authorizeUri = signInForAuthorization(user, client, verifier, Map.of(), session);

        final var page = secondFactorPage(session);
        assertTrue(page.contains(ENROL_FIELD) && page.contains("otpauth://totp/")
                && page.contains("src=\"data:image/png;base64,"), "The page must offer the enrolment");

        final var enrolled = postEnrolment(session, getTools().codeNow(userId, 0));

The test sends a password-only token and an old multi-factor token to the guarded operations and expects 401 with the exact RFC 9470 challenge and the urn:problem:mfa:insufficient-user-authentication type, then checks that the TOTP credential is still confirmed and the trusted device still exists.

    /**
     * Verifies that removing or resetting the second factor of an account that has one needs a recent multi-factor
     * sign-in: a password-only token and an old multi-factor one are answered with {@code 401} and the RFC 9470
     * challenge, and nothing is removed.
     *
     * @throws Exception if a request cannot be performed.

    @Test
    void disableTotp_whenTokenShowsNoRecentMultiFactorSignIn_answersTheStepUpChallenge() throws Exception {
        final var user = fixtures.createUser();

        final var device = trust(user, "Firefox on Linux");

        mockMvc.perform(delete(DEVICES_PATH + "/" + device).with(bearerOf(user)))

The tokens are produced with the jwt() request post processor, which lets the test choose acr and auth_time directly. The same test class also covers the TOTP endpoints, described in the next page.

Security notes and pitfalls

Downgrade attacks. A second factor is worthless if an attacker can choose not to be asked. Three rules in the code close that door. The requirement is evaluated on the server, from the account and the client, never from a request parameter (acr_values can only raise the bar). The policy is enforced at /oauth2/authorize, where the code is issued, and not only on the page the user happens to be redirected to: a request that skips the page is refused there. And the claims are computed from the factors the session really holds, so a token never says mfa because a client asked for it. Keep the fallbacks honest too: a user who has no second factor registered yet is sent to enrol (the enrolment test above), not waved through, whenever the policy requires one. Finally, do not let a weaker path, such as a social login that reports no amr, produce an acr it did not earn; the example’s trust-mfa provider settings are off by default.

Lockout versus denial of service. A per-user lockout protects the code and gives an attacker who knows only a username a way to lock the real user out. The example limits the damage: the lock is short (15 minutes by default), the counter restarts when a lock ends, the lock applies to the second factor after the password has been accepted (so the attacker must know the password to trigger it), and a lockout is recorded as a security event and shown to the user with its own message. Add the usual rate limits at the edge for the password step, notify the user on repeated lockouts and decide whether an administrator can unlock. See the OWASP Multifactor Authentication Cheat Sheet.

Trusted-device token theft. The cookie is a bearer credential: anyone who copies it gets the second factor skipped for that account on their own browser, as long as they also have the password. Mitigations in the example are that the cookie is HttpOnly, Secure and host-bound, its value is signed (a forged value costs one constant-time comparison, not a database lookup), the database holds only a hash, the device expires after 30 days, a device can be revoked from the API, removing the second factor revokes every device, and a trusted device never satisfies a step-up, so the sensitive operations still need a real code. The stronger design is a device-bound key pair; see the OAuth Reference on device-bound credentials.

Step-up replay. A step-up token is valid for as long as it lives; the guard bounds the age of the sign-in, not the number of uses. Keep step-up-max-age short, remember that auth_time is the primary factor’s instant (adding a code later does not refresh it, so max_age forces a new password entry), and never let a client reuse a stepped-up token for a different operation than the one the user approved. The guard refuses a token whose auth_time is in the future, which covers clock tampering by an issuer you do not control. Pair it with short access-token lifetimes.

Other pitfalls.

  • amr is information, not authorization: a resource server decides with acr and auth_time, and only for issuers it trusts.

  • The tokens report amr [pwd] after a trusted-device sign-in on purpose. Do not "fix" that to show two factors, or a step-up becomes satisfiable by a stolen cookie.

  • A session that has no counted factor is left alone by the max_age check, because it could never satisfy the request and would loop through the login page.

  • Change the session id whenever the level of authentication changes (the filter does), against session fixation.
