Authorization Server from Scratch: E-mail OTP & Magic Links

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

What you build

This page adds two ways to prove the possession of a mailbox: a one-time code (six digits typed into the login page) and a magic link (a single-use URL that the user opens from the e-mail). Each works in two roles:

  • as a primary login method, offered on the login page next to the password and the passkey, for a user who has a verified e-mail address;

  • as a second factor, offered on the second-factor page to a user who already signed in with a primary factor and has no stronger factor of their own.

The theory (what each mechanism proves, why a mailbox is only as strong as the way the password is reset) lives in the OAuth Reference sections backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_e_mail_one_time_code_otp, backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_e_mail_magic_link_single_use_token and backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_e_mail_or_sms_otp_as_a_second_factor, and this page does not repeat it. Rate limiting is the subject of Bucket4j: Spring Boot Manual Integration; here only the way the example applies it to these endpoints is shown. The SMS channel shares all the machinery of this page and is described in Authorization Server from Scratch: SMS One-Time Codes.

What Spring gives and what the example adds

Spring Security 7.1 provides the one-time token login: HttpSecurity.oneTimeTokenLogin() registers a filter that answers POST /ott/generate (it asks a OneTimeTokenService for a token and hands it to a OneTimeTokenGenerationSuccessHandler) and a filter that answers POST /login/ott (it turns the posted token into an authentication and calls an AuthenticationProvider). JdbcOneTimeTokenService stores the tokens in a one_time_tokens table. The framework leaves the delivery of the token to the application, and its tokens are UUIDs.

The example keeps all of that for the magic link and adds what a production login needs:

  • numeric codes. The stock service always generates a UUID and keys its table by that value alone, so six digits would collide across users. A code is stored in the example’s own table, ott_codes (migration V610), as a hash, bound to the user name and to a binding id held in the session of the browser that asked for it;

  • a confirm page for the link: the e-mail opens GET /login/ott/confirm, which only renders a button, and the button’s POST consumes the token;

  • delivery through a listener, after the database transaction commits and off the request thread;

  • rate limiting per client address and per identifier;

  • enumeration safety: the same redirect, whatever the identifier is;

  • factors that register the method in the multi-factor framework of the Multi-Factor Authentication & Step-Up page.

How it works

The code variant

The browser posts the identifier to /ott/generate. Spring’s filter asks the example’s resolver for the token to generate and the stock service stores it; the example’s success handler then discards that token (a code does not use the stock store), stores a code of its own and requests its delivery.

sequenceDiagram autonumber actor U as User participant B as Browser participant RL as OttRateLimitFilter participant G as GenerateOneTimeTokenFilter participant H as OttGenerationSuccessHandler participant UC as RequestOneTimeCodeUseCase participant DB as ott_codes participant L as OttDeliveryListener participant M as ThymeleafOttMailer U->>B: Types the user name, chooses e-mail and code B->>RL: POST /ott/generate (username, channel=email, kind=code) RL->>G: Within the per-client and per-identifier limits G->>H: A token from the resolver, stored by JdbcOneTimeTokenService H->>H: Consume and discard the stock token H->>UC: execute(identifier, EMAIL, LOGIN, bindingId) UC->>DB: Save the hash of the code, with the binding id (only if the account has a verified address) UC-->>L: EmailCodeRequested, published inside the transaction H->>B: 302 to /login/ott, binding id kept in the session L->>M: After commit, off the request thread: deliverCode M-->>U: E-mail with the code U->>B: Types the code B->>RL: POST /login/ott (token=code) RL->>B: The converter reads identifier and binding id from the session B->>DB: OttCodeAuthenticationProvider and VerifyOneTimeCodeUseCase: attempts, hash, consume DB-->>B: Authentication with FACTOR_OTT, then the saved request resumes

Two details make a code safe to be six digits. It is checked only in the browser that asked for it, because the converter reads the identifier and binding id from the session (PendingOtt), never from the form. And it is checked at most a few times: the attempt counter is incremented atomically before the comparison, and the code is burnt after the last wrong attempt.

The link variant

sequenceDiagram autonumber actor U as User participant B as Browser participant S as Mail scanner participant H as OttGenerationSuccessHandler participant T as JdbcOneTimeTokenService participant C as GET /login/ott/confirm participant P as POST /login/ott U->>B: Types the user name, chooses e-mail and link B->>H: POST /ott/generate (kind=link) H->>T: Token (UUID) stored by the framework, kept H-->>U: E-mail with the link to /login/ott/confirm, token in the query S->>C: GET the link to scan it C-->>S: A page with one button, nothing consumed U->>C: Opens the link C-->>U: The confirm page, no-store, no referrer U->>P: Clicks the button: POST token P->>T: OttLinkAuthenticationProvider: consume(token) T-->>P: The token and its user name, deleted P-->>U: Authentication with FACTOR_OTT, then the saved request resumes

The link points at a page, never at an endpoint that consumes the token. Mail clients, security gateways and link previews fetch URLs with GET before the user ever sees the message; a link that signed the user in on GET would be spent by the scanner and fail for the person. Here a GET changes nothing and only the click, a POST with the CSRF token of the page, consumes it. The page is sent with Cache-Control: no-store and Referrer-Policy: no-referrer, because the token is in its address.

Data

Two migrations hold the state. V600 is Spring Security’s one_time_tokens schema adapted to PostgreSQL; the Spring Security database schema appendix lists the original.

-- Spring Security's one_time_tokens schema (JdbcOneTimeTokenService), adapted to PostgreSQL. The service issues the
-- UUID of a magic link; its SQL is fixed, so the table and column names must not change.
CREATE TABLE one_time_tokens
(
    token_value varchar(36)              NOT NULL,
    username    varchar(100)             NOT NULL,
    expires_at  timestamp with time zone NOT NULL,
    PRIMARY KEY (token_value)
);

CREATE INDEX ix_one_time_tokens_expires_at ON one_time_tokens (expires_at);

V610 adds the table of numeric codes. The code itself is never stored, only its hash, together with the binding id that ties it to one browser.

CREATE TABLE ott_codes
(
    id         uuid                     NOT NULL,
    username   varchar(100)             NOT NULL,
    channel    varchar(16)              NOT NULL,
    purpose    varchar(32)              NOT NULL,
    code_hash  varchar(128)             NOT NULL,
    binding_id varchar(128)             NOT NULL,
    attempts   integer                  NOT NULL DEFAULT 0,
    expires_at timestamp with time zone NOT NULL,
    created_at timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    CONSTRAINT ck_ott_codes_channel CHECK (channel IN ('EMAIL', 'SMS')),
    CONSTRAINT ck_ott_codes_purpose CHECK (purpose IN ('LOGIN', 'SECOND_FACTOR')),
    CONSTRAINT ck_ott_codes_attempts CHECK (attempts >= 0)
);

CREATE INDEX ix_ott_codes_binding_username ON ott_codes (binding_id, username);
CREATE INDEX ix_ott_codes_expires_at ON ott_codes (expires_at);

These are the example’s own tables created with Flyway; see the Spring Boot Flyway how-to.

Column Type Notes

one_time_tokens.token_value

varchar(36)

The UUID of a magic link, the primary key. Written and deleted by JdbcOneTimeTokenService.

one_time_tokens.username

varchar(100)

The user the link is for. For a link requested as a second factor it carries a marker that tells the provider so (LinkTokenUsername).

one_time_tokens.expires_at

timestamp with time zone

Expiry. Indexed so the clean-up job and the service’s own clean-up are cheap.

ott_codes.id

uuid

Primary key of the code.

ott_codes.username, ott_codes.channel, ott_codes.purpose

varchar

Whose code it is, EMAIL or SMS, and LOGIN or SECOND_FACTOR. Check constraints restrict the last two.

ott_codes.code_hash

varchar(128)

SHA-256 of the code in lower-case hex, compared in constant time.

ott_codes.binding_id

varchar(128)

Random id held in the session of the browser that requested the code. A code only verifies together with it.

ott_codes.attempts

integer

Wrong submissions so far, never negative. Past the limit the code is burnt.

ott_codes.expires_at, ott_codes.created_at

timestamp with time zone

Expiry and creation time.

A plain hash of a six-digit code can be brute-forced instantly if the table leaks. That is acceptable only because a code is single use, lives for minutes and is burnt after a few wrong attempts; never reuse that hasher for a long-lived secret. The table definitions also appear, with the rest of the schema, in Data Model and Schema.

Wiring the chain

The configuration declares the resolver as a bean and assembles the customizer. The filters are built there, not exposed as beans, so Spring Boot does not also register them in the servlet container.

    /**
     * Declares the resolver of the token request of {@code POST /ott/generate}.
     *
     * @param ottPolicy the rules of one-time tokens, which set the lifetime of each kind.
     * @return the resolver.
     */
    @Bean
    public OttGenerateRequestResolver ottGenerateRequestResolver(final OttPolicy ottPolicy) {
        return new OttGenerateRequestResolver(ottPolicy);
    }

Reference: One-Time Token Login.

    /**
     * Installs the one-time token methods in the login/UI chain.
     *
     * @param rateLimiter          limits the token requests and submissions.
     * @param requestResolver      resolves the token Spring's filter generates.
     * @param successHandler       delivers the generated token.
     * @param tokenService         store of the magic link tokens.
     * @param providers            the authentication providers.
     * @param primaryFactorSession rules about the session a second factor is presented in.
     * @return the customizer.
     */
    @Bean
    @Order(OttChainCustomizer.ORDER)
    public LoginChainCustomizer ottChainCustomizer(final OttRateLimiter rateLimiter,
            final OttGenerateRequestResolver requestResolver, final OttGenerationSuccessHandler successHandler,
            final OneTimeTokenService tokenService, final OttProviders providers,
            final PrimaryFactorSession primaryFactorSession) {
        return new OttChainCustomizer(new OttRateLimitFilter(rateLimiter), requestResolver, successHandler,
                tokenService, new OttAuthenticationConverter(), providers.link(), providers.code(),
                new OttAuthenticationSuccessHandler(new SavedRequestAwareAuthenticationSuccessHandler()),
                new OttAuthenticationFailureHandler(),
                new OttSecondFactorFilter(new ProviderManager(providers.secondFactor()), primaryFactorSession));
    }

Reference: Java configuration.

The customizer is where oneTimeTokenLogin() is called. It opens the generate endpoint and the pages to everybody, requires authentication for the second-factor post, puts the rate-limit filter before Spring’s GenerateOneTimeTokenFilter (which answers POST /ott/generate itself, so a limit placed later would never run) and gives the second-factor filter the chain’s session authentication strategy.

/**
 * Adds the one-time token methods to the login/UI chain through {@code http.oneTimeTokenLogin(...)}: the request of a
 * token ({@code POST /ott/generate}), the submission of a magic link token or a numeric code ({@code POST /login/ott})
 * and, as a second factor, the submission of a code ({@code POST /login/second-factor/ott}). The pages the user lands
 * on (where the code is typed, where a magic link is confirmed) are open to everybody and the second-factor post to
 * signed-in users only. The rate limits are applied before anything else of the one-time token flow. CSRF protection
 * stays on: every form carries the token. Once the chain is configured, the second-factor filter gets the chain's
 * session authentication strategy, the one the form login uses (a new session id and a new CSRF token on success).
 * Spring's own default submit page is turned off: the pages are this server's own.
 */
@RequiredArgsConstructor
public class OttChainCustomizer implements LoginChainCustomizer {

    /** Order of this customizer in the login chain, after the TOTP ({@code 1}) and passkey ({@code 2}) ones. */
    public static final int ORDER = 3;

    /** Applies the rate limits to the endpoints. */
    private final OttRateLimitFilter rateLimitFilter;

    /** Resolves the token Spring's filter generates. */
    private final GenerateOneTimeTokenRequestResolver requestResolver;

    /** Delivers the token that was generated. */
    private final OneTimeTokenGenerationSuccessHandler generationSuccessHandler;

    /** Store of the magic link tokens. */
    private final OneTimeTokenService tokenService;

    /** Reads what is posted to the sign-in endpoint. */
    private final AuthenticationConverter authenticationConverter;

    /** Confirms a magic link. */
    private final AuthenticationProvider linkProvider;

    /** Signs a user in with a numeric code. */
    private final AuthenticationProvider codeProvider;

    /** Resumes the interrupted request after a sign-in. */
    private final AuthenticationSuccessHandler successHandler;

    /** Sends the browser back after a failed sign-in. */
    private final AuthenticationFailureHandler failureHandler;

    /** Processes the post of the second-factor code form. */
    private final OttSecondFactorFilter secondFactorFilter;

    /**
     * Customizes the login/UI chain.
     *
     * @param http security builder of the chain.
     */
    @Override
    public void customize(final HttpSecurity http) {
        http.authorizeHttpRequests(authorize -> authorize
                .requestMatchers(OttRateLimitFilter.GENERATE_PATH, OneTimeTokenPageApi.PATH_OTT_CODE_PAGE,
                        OneTimeTokenPageApi.PATH_OTT_CODE_PAGE + "/**").permitAll()
                .requestMatchers(OttSecondFactorFilter.SECOND_FACTOR_OTT_PATH).authenticated());
        http.addFilterBefore(rateLimitFilter, GenerateOneTimeTokenFilter.class);
        http.addFilterBefore(secondFactorFilter, AuthorizationFilter.class);
        http.authenticationProvider(codeProvider);
        http.oneTimeTokenLogin(ott -> ott
                .tokenGeneratingUrl(OttRateLimitFilter.GENERATE_PATH)
                .loginProcessingUrl(OneTimeTokenPageApi.PATH_OTT_CODE_PAGE)
                .loginPage(LoginController.LOGIN_PATH)
                .showDefaultSubmitPage(false)
                .tokenService(tokenService)
                .generateRequestResolver(requestResolver)
                .tokenGenerationSuccessHandler(generationSuccessHandler)
                .authenticationConverter(authenticationConverter)
                .authenticationProvider(linkProvider)
                .successHandler(successHandler)
                .failureHandler(failureHandler));
        http.with(new SessionStrategyConfigurer(secondFactorFilter));
    }

    /**
     * Hands the session authentication strategy of the chain to the second-factor filter. The strategy is a shared
     * object of the chain that only exists once every configurer has been initialised (the CSRF configurer adds its
     * {@code CsrfAuthenticationStrategy} to the session management one), so it is read in {@link #configure}, as the
     * form login does for its own filter. Package-private so its test can drive it.
     */
    @RequiredArgsConstructor
    static final class SessionStrategyConfigurer
            extends AbstractHttpConfigurer<SessionStrategyConfigurer, HttpSecurity> {

        /** The filter that gets the strategy. */
        private final OttSecondFactorFilter filter;

        /**
         * Sets the shared strategy, when the chain has one, on the filter.
         *
         * @param http security builder of the chain.
         */
        @Override
        public void configure(final HttpSecurity http) {
            final var strategy = http.getSharedObject(SessionAuthenticationStrategy.class);
            if (strategy != null) {
                filter.setSessionAuthenticationStrategy(strategy);
            }
        }
    }
}

Reference: One-Time Token Login.

Choosing the token

The resolver turns the request into a GenerateOneTimeTokenRequest. For a second factor the identifier is the name of the signed-in user, never a field a client could aim at somebody else. Whether the identifier belongs to an account is not looked at here: a token is issued for any identifier, and what is delivered is decided afterwards, so the answer cannot tell.

/**
 * Resolves the request of {@code POST /ott/generate} to the token Spring's filter asks the token service for. The
 * identifier is the {@code username} field of a sign-in and, for a second factor, the name of the signed-in user (never
 * a field a client could point at somebody else), cleaned of control characters and cut to what the token store
 * holds. The lifetime of the token is the one {@link OttPolicy} sets for its kind. A request that names no identifier
 * is not resolved, so the chain goes on as it would for any other path. Whether the identifier belongs to an account
 * is not looked at here: a token is issued for any identifier, and what is delivered is decided afterwards, so the
 * answer never tells.
 */
@RequiredArgsConstructor
public class OttGenerateRequestResolver implements GenerateOneTimeTokenRequestResolver {

    /** The rules of one-time tokens, which set the lifetime of each kind. */
    private final OttPolicy ottPolicy;

    /**
     * Resolves the request.
     *
     * @param request the request.
     * @return the token to generate, or {@code null} when the request names no identifier.
     */
    @Override
    public GenerateOneTimeTokenRequest resolve(final HttpServletRequest request) {
        final var current = SecurityContextHolder.getContext().getAuthentication();
        final var parameters = OttGenerationParameters.from(request, current);
        final var secondFactor = parameters.purpose() == OttPurpose.SECOND_FACTOR;
        final var identifier = LinkTokenUsername.clean(
                secondFactor ? current.getName() : request.getParameter(OttGenerationParameters.USERNAME_PARAMETER));
        if (!StringUtils.hasText(identifier)) {
            return null;
        }
        final var username = LinkTokenUsername.forLink(identifier,
                secondFactor && parameters.kind() == OttKind.LINK);
        return new GenerateOneTimeTokenRequest(username, ottPolicy.ttl(parameters.kind()));
    }
}

Delivery

The success handler of the framework’s filter is where the example takes over, and OttGenerationSuccessHandler always ends in the same redirect to /login/ott. For a link it asks RequestMagicLinkUseCase to e-mail the confirm link, whose host is the configured issuer, never the Host header of the request (which an attacker controls). For a code it discards the stock token and asks RequestOneTimeCodeUseCase to store a code of its own. Both use cases resolve the destination (a verified address of an enabled account) and publish an event instead of sending anything. The listener sends it:

/**
 * Delivers the one-time tokens the use cases asked for, once the transaction that stored them has committed
 * ({@link TransactionPhase#AFTER_COMMIT}; an event published outside a transaction is delivered at once) and off the
 * request thread ({@code @Async}, on Spring Boot's {@code applicationTaskExecutor}). So no mail server or SMS gateway
 * is ever called inside a transaction, a slow one holds no database connection, a rolled-back request sends nothing,
 * and the time the request takes is the same whether or not something is sent, which keeps the latency from telling
 * an existing account from an unknown one. A failure is logged without the address, the number or the token, and
 * never reaches the response.
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class OttDeliveryListener {

    /** Delivers the tokens. */
    private final DeliverOneTimeTokenUseCase deliverOneTimeTokenUseCase;

    /**
     * E-mails a code.
     *
     * @param event what to deliver.
     */
    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT, fallbackExecution = true)
    public void onEmailCode(final EmailCodeRequested event) {
        try {
            deliverOneTimeTokenUseCase.deliverEmailCode(event);
        } catch (final OttDeliveryException e) {
            log.warn("A one-time code was not delivered by e-mail: {}", e.getClass().getSimpleName());
        }
    }

    /**
     * E-mails a magic link.
     *
     * @param event what to deliver.
     */
    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT, fallbackExecution = true)
    public void onEmailLink(final EmailLinkRequested event) {
        try {
            deliverOneTimeTokenUseCase.deliverEmailLink(event);
        } catch (final OttDeliveryException e) {
            log.warn("A magic link was not delivered: {}", e.getClass().getSimpleName());
        }
    }

    /**
     * Sends a text message.
     *
     * @param event what to send.
     */
    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT, fallbackExecution = true)
    public void onSms(final SmsRequested event) {
        try {
            deliverOneTimeTokenUseCase.deliverSms(event);
        } catch (final SmsDeliveryException e) {
            log.warn("An SMS was not delivered: {}", e.getClass().getSimpleName());
        }
    }
}

Because the send happens after commit and off the request thread, no mail server is called inside a transaction, a slow one holds no database connection, a rolled-back request sends nothing, and the time a request takes is the same whether or not something is sent. A failure is logged without the address, the number or the token.

The mailer renders a text and an HTML body from Thymeleaf templates, with the locale of the mail settings and never the platform’s. Any failure becomes an OttDeliveryException that carries neither the address nor the token.

@Slf4j
@RequiredArgsConstructor
public class ThymeleafOttMailer implements OttDelivery {

    /** Template of the code message (without extension). */
    static final String CODE_TEMPLATE = "mail/ott-code";

    /** Template of the link message (without extension). */
    static final String LINK_TEMPLATE = "mail/ott-link";

    /** Extension of the HTML templates. */
    static final String HTML_EXTENSION = ".html";

    /** Extension of the plain-text templates. */
    static final String TEXT_EXTENSION = ".txt";

    /** Message key of the subject of the code message. */
    static final String CODE_SUBJECT = "ott.code.subject";

    /** Message key of the subject of the link message. */
    static final String LINK_SUBJECT = "ott.link.subject";

    /** Template variable holding the code. */
    static final String CODE_VARIABLE = "code";

    /** Template variable holding the link. */
    static final String LINK_VARIABLE = "link";

    /** Template variable holding the validity in minutes. */
    static final String VALID_MINUTES_VARIABLE = "validMinutes";

    /** Generic message of every delivery failure. */
    static final String FAILURE_MESSAGE = "Could not deliver the one-time token by e-mail";

    /** Seconds in a minute. */
    private static final long SECONDS_PER_MINUTE = 60L;

    /** Sends the messages. */
    private final JavaMailSender mailSender;

    /** Renders the templates; private to this mailer. */
    private final TemplateEngine templateEngine;

    /** Source of the subjects. */
    private final MessageSource messageSource;

    /** Sender, base URL and locale. */
    private final MailProperties properties;

    @Override
    public void deliverCode(final OttChannel channel, final String destination, final String code,
                            final Duration validFor) {
        requireEmail(channel);
        send(destination, CODE_SUBJECT, CODE_TEMPLATE, CODE_VARIABLE, code, validFor);
    }

    @Override
    public void deliverLink(final OttChannel channel, final String destination, final URI link,
                            final Duration validFor) {
        requireEmail(channel);
        send(destination, LINK_SUBJECT, LINK_TEMPLATE, LINK_VARIABLE, link.toString(), validFor);
    }

    /**
     * Renders and sends one message.
     *
     * @param destination recipient address.
     * @param subjectKey  message key of the subject.
     * @param template    template name without extension.
     * @param variable    name of the variable that holds the secret value.
     * @param value       the code or link.
     * @param validFor    validity shown to the user.
     * @throws OttDeliveryException if the message cannot be rendered or delivered.
     */
    private void send(final String destination, final String subjectKey, final String template,
                      final String variable, final String value, final Duration validFor) {
        final var locale = properties.locale();
        final var context = new Context(locale);
        context.setVariable(variable, value);
        context.setVariable(VALID_MINUTES_VARIABLE, minutes(validFor));
        try {
            final var text = templateEngine.process(template + TEXT_EXTENSION, context);
            final var html = templateEngine.process(template + HTML_EXTENSION, context);
            final var message = mailSender.createMimeMessage();
            final var helper = new MimeMessageHelper(message, true, StandardCharsets.UTF_8.name());
            helper.setFrom(properties.from());
            helper.setTo(destination);
            helper.setSubject(messageSource.getMessage(subjectKey, null, locale));
            helper.setText(text, html);
            mailSender.send(message);
        } catch (final MailException | MessagingException | TemplateEngineException e) {
            // Only the type of the failure is kept: its message may contain the address or the rendered body.
            log.warn("Could not deliver a one-time token by e-mail ({})", e.getClass().getSimpleName());
            throw new OttDeliveryException(FAILURE_MESSAGE,
                    new IllegalStateException("Delivery failed with " + e.getClass().getName()));
        }
    }

    /**
     * Rounds a duration up to whole minutes, at least one.
     *
     * @param validFor the validity.
     * @return the minutes to show.
     */
    private static long minutes(final Duration validFor) {
        final var seconds = validFor.toSeconds();
        return Math.max(1L, (seconds + SECONDS_PER_MINUTE - 1L) / SECONDS_PER_MINUTE);
    }

    /**
     * Refuses a channel other than e-mail.
     *
     * @param channel requested channel.
     * @throws IllegalArgumentException if the channel is not {@link OttChannel#EMAIL}.
     */
    private static void requireEmail(final OttChannel channel) {
        if (channel != OttChannel.EMAIL) {
            throw new IllegalArgumentException("Unsupported channel for the e-mail delivery: " + channel);
        }
    }
}

Rate limits

Token requests and submissions are limited separately, and each twice: per client address and per identifier. The identifier is limited whether or not it belongs to an account, so the limit never tells which ones exist. The limiter uses the same Bucket4j and Caffeine pattern as the account endpoints; see Bucket4j: Spring Boot Manual Integration for the technique.

/**
 * Rate limiter of the one-time token endpoints, on the pattern of the account endpoints' limiter: Bucket4j token
 * buckets in Caffeine caches ({@link FixedWindowBuckets}). Requests for a token (generation) and submissions of a token
 * or code (verification) are limited separately, and each twice: per client address and per identifier (the user name
 * the request names), so a single client cannot flood the mailboxes and the SMS budget, many clients cannot aim at one
 * account, and a code cannot be guessed faster than the limits allow, on top of the attempt counter of the code
 * itself. The identifier is limited whether or not it belongs to an account, so the limit never tells which ones
 * exist.
 *
 * <p>Each bucket holds the limit of its key and is refilled all at once every
 * {@link OttRateLimitProperties#window()}. The buckets live in this instance only: several instances each apply the
 * limits on their own. The client address is {@code request.getRemoteAddr()}, so behind a proxy
 * {@code server.forward-headers-strategy} must be set for it to be the real client.
 */
@Component
@EnableConfigurationProperties(OttRateLimitProperties.class)
public final class OttRateLimiter {

    /** Key used when the client address is unknown. */
    private static final String UNKNOWN_CLIENT = "unknown";

    /** Limits, window and bound of the tracked keys. */
    private final OttRateLimitProperties properties;

    /** Buckets of the token requests per client address. */
    private final FixedWindowBuckets generationClients;

    /** Buckets of the token requests per identifier. */
    private final FixedWindowBuckets generationIdentifiers;

    /** Buckets of the submissions per client address. */
    private final FixedWindowBuckets verificationClients;

    /** Buckets of the submissions per identifier. */
    private final FixedWindowBuckets verificationIdentifiers;

    /**
     * Creates the limiter.
     *
     * @param properties limits, window and bound of the tracked keys.
     * @param clock      source of the current time.
     */
    public OttRateLimiter(final OttRateLimitProperties properties, final Clock clock) {
        this.properties = properties;
        generationClients = buckets(clock);
        generationIdentifiers = buckets(clock);
        verificationClients = buckets(clock);
        verificationIdentifiers = buckets(clock);
    }

    /**
     * Counts one request for a token and rejects it once a limit is exceeded.
     *
     * @param clientAddress address of the calling client.
     * @param identifier    identifier the request names, or {@code null} when it names none.
     * @throws OttRateLimitExceededException if the client or the identifier exceeded its limit.
     */
    public void checkGeneration(final String clientAddress, final String identifier) {
        check(generationClients, properties.generationPerClient(), generationIdentifiers,
                properties.generationPerIdentifier(), clientAddress, identifier);
    }

    /**
     * Counts one submission of a token or a code and rejects it once a limit is exceeded.
     *
     * @param clientAddress address of the calling client.
     * @param identifier    identifier the submission is for, or {@code null} when it names none (a magic link).
     * @throws OttRateLimitExceededException if the client or the identifier exceeded its limit.
     */
    public void checkVerification(final String clientAddress, final String identifier) {
        check(verificationClients, properties.verificationPerClient(), verificationIdentifiers,
                properties.verificationPerIdentifier(), clientAddress, identifier);
    }

    /**
     * Tells how many keys are tracked, after any pending eviction.
     *
     * @return the number of keys of the four kinds.
     */
    long trackedKeys() {
        return generationClients.trackedKeys() + generationIdentifiers.trackedKeys()
                + verificationClients.trackedKeys() + verificationIdentifiers.trackedKeys();
    }

    /**
     * Applies the client and the identifier limits of one kind of request.
     *
     * @param clients         buckets per client address.
     * @param clientLimit     requests per client address per window.
     * @param identifiers     buckets per identifier.
     * @param identifierLimit requests per identifier per window.
     * @param clientAddress   address of the calling client.
     * @param identifier      identifier, or {@code null}.
     * @throws OttRateLimitExceededException if a limit is exceeded.
     */
    private void check(final FixedWindowBuckets clients, final int clientLimit, final FixedWindowBuckets identifiers,
                       final int identifierLimit, final String clientAddress, final String identifier) {
        if (!properties.enabled()) {
            return;
        }
        consume(clients, clientAddress == null ? UNKNOWN_CLIENT : clientAddress, clientLimit);
        if (identifier != null) {
            consume(identifiers, identifier.toLowerCase(Locale.ROOT), identifierLimit);
        }
    }

    /**
     * Takes one token from the bucket of a key.
     *
     * @param buckets buckets of one kind of key.
     * @param key     the key.
     * @param limit   requests the key may make per window.
     * @throws OttRateLimitExceededException if the bucket is empty.
     */
    private static void consume(final FixedWindowBuckets buckets, final String key, final int limit) {
        final var wait = buckets.tryConsume(key, limit);
        if (wait.isPresent()) {
            throw new OttRateLimitExceededException(wait.get());
        }
    }

    /**
     * Builds the buckets of one kind of key.
     *
     * @param clock source of the current time.
     * @return the buckets.
     */
    private FixedWindowBuckets buckets(final Clock clock) {
        return new FixedWindowBuckets(clock, properties.window(), properties.maxTrackedKeys());
    }
}

Factors

One authority cannot carry two strengths, and the registry refuses two factors with the same authority. So each use of each channel is a factor of its own. A code or link that signs the user in proves the possession of a mailbox, which is as strong as a password and no more (PRIMARY); the same mailbox as the second factor of a user who already signed in is SECOND. The amr values are those of RFC 8176: otp for the e-mail code or link and sms for the SMS code.

/**

 * sign-in are {@link FactorStrength#PRIMARY} (they prove the possession of a mailbox or a phone, which is as strong as
 * a password and no more), and the same two as the second factor of a user who already signed in with a primary

The second factor

As a second factor the method is a fragment of the second-factor page. It exposes two model attributes, whether the e-mail code and link are offered and whether the SMS code is, and the rule behind them is one class, shared by the page, by the token request and by the verification:

/**
 * Decides through which channels a one-time code or link may be the second factor of a signed-in user. The same rule
 * decides what the second-factor page offers, whether a requested token is delivered at all and whether a presented
 * one is accepted, so a channel that is not offered can neither be asked for nor used by posting the forms by hand:
 * <ul>
 * <li>never the channel that signed the user in (the same mailbox or phone would be proved twice);</li>
 * <li>SMS only to a user with a verified phone;</li>
 * <li>e-mail only to a user without any other confirmed second factor (authenticator app, passkey, verified phone).
 * The password is reset by e-mail too, so a mailbox is not independent from the password: whoever controls it could
 * otherwise skip the stronger factor the user enrolled. For a user whose multi-factor authentication was forced by an
 * administrator before any factor was enrolled, the e-mail is then the only second factor available.</li>
 * </ul>
 */
@Component
@RequiredArgsConstructor
public class OttSecondFactorChannels {

    /** Rules about the session a second factor is presented in. */
    private final PrimaryFactorSession primaryFactorSession;

    /** Resolves the identifier of the account of the signed-in user. */
    private final SecondFactorUserResolver userResolver;

    /** Tells whether the user has a confirmed second factor of any kind. */
    private final HasConfirmedSecondFactorUseCase hasConfirmedSecondFactorUseCase;

    /** Tells whether the user has a verified phone. */
    private final HasVerifiedPhoneUseCase hasVerifiedPhoneUseCase;

    /**
     * Gets the channels a signed-in user may use as the second factor.
     *
     * @param authentication the authentication of the session, which holds a primary factor.
     * @return the channels; empty when none may be used.
     */
    public Set<OttChannel> allowed(final Authentication authentication) {
        final var userId = userResolver.userIdOf(authentication.getName());
        final var channels = EnumSet.noneOf(OttChannel.class);
        if (!primaryFactorSession.signedInThrough(authentication, OttChannel.EMAIL)
                && !hasConfirmedSecondFactorUseCase.execute(userId)) {
            channels.add(OttChannel.EMAIL);
        }
        if (!primaryFactorSession.signedInThrough(authentication, OttChannel.SMS)
                && hasVerifiedPhoneUseCase.execute(userId)) {
            channels.add(OttChannel.SMS);
        }
        return channels;
    }

    /**
     * Tells whether a signed-in user may use a channel as the second factor.
     *
     * @param authentication the authentication of the session, which holds a primary factor.
     * @param channel        the channel.
     * @return {@code true} when the channel is one of {@link #allowed(Authentication)}.
     */
    public boolean isAllowed(final Authentication authentication, final OttChannel channel) {
        return allowed(authentication).contains(channel);
    }
}

API

The flow is made of form posts and two HTML pages, not of a JSON API, so it has no OpenAPI operation for the generate and sign-in posts: they are the framework’s endpoints.

Endpoint Who What it does

POST /ott/generate

Anyone (CSRF token required)

Fields username, channel (email or sms, default email), kind (code or link, default code) and purpose (login or second-factor, default login). Always answers a redirect to /login/ott; a second factor needs a signed-in user. A link is sent by e-mail only.

GET /login/ott

Anyone

The page that says to check the inbox and, for a code, shows the form to type it.

POST /login/ott

Anyone (CSRF token required)

Field token: the UUID of a magic link or the numeric code. Success resumes the saved request, usually /oauth2/authorize.

GET /login/ott/confirm

Anyone

Query token. The page a magic link opens; it renders one button and consumes nothing.

POST /login/second-factor/ott

Signed-in user

Field code: the second-factor code.

Beyond the status line, the rate-limit answer is 429 with application/problem+json, type urn:problem:ott:rate-limited, and a Retry-After header in seconds.

Tests

The example covers this feature at four levels. They are described in prose, since none of the test classes carries a tag for inclusion:

  • Unit tests of every class of the package, the use cases (attempt counter, burn on the last failed attempt, lockout and audit for the second factor), the providers, the converter, the resolver, the success handler, the listener, the mailer and the rate limiter.

  • Persistence: JdbcOneTimeCodeRepositoryIT runs the code repository against PostgreSQL (one active code per binding and user, atomic attempt counting, single consumption, expiry).

  • Integration tests of the sign-in, with a real SMTP relay: OttEmailCodeIT and OttMagicLinkIT sign in with a code and with a link, as primary and as second factor, reading the message through the Mailpit HTTP API (Testcontainers, axllent/mailpit). OttPagesIT renders the login fragment, the second-factor offer (e-mail only for a user without another factor), the code page and the confirm page, whose button posts the token. OttRateLimitIT checks the limits per identifier and per client, and OttEnumerationIT that status, body and delivery are identical for a known and an unknown identifier.

  • End to end: OttEndToEndIT drives the packaged jar with Playwright, signs in with an e-mail code read from Mailpit and with a magic link, and checks that a scanner’s GET does not consume the link.

Writing the rate-limit test found a real bug: the limiter was first registered before UsernamePasswordAuthenticationFilter, but Spring’s generate filter sits earlier and answers the request itself, so generation was never limited. The customizer shown above adds it before GenerateOneTimeTokenFilter.

Security notes and pitfalls

  • Enumeration. The response to POST /ott/generate is the same redirect whether the identifier exists, is disabled or has no verified address. The use cases still generate and hash a code in the unhappy case, and delivery happens after commit and off the request thread, so neither the body nor the latency tells. Only the e-mail of a real account differs.

  • Rate limiting. Limit per address and per identifier: the first stops one client flooding mailboxes, the second stops many clients aiming at one account. Both are applied before any token is stored. Behind a proxy, configure forwarded headers or every client shares one address.

  • Single use and expiry. A link is consumed by the POST that uses it and a code by the first correct submission, with the conditional consume deciding which of two concurrent submissions wins. Codes live ten minutes and links fifteen by default; short lifetimes shrink the window for a stolen message. Expired rows are removed by a scheduled clean-up.

  • Link prefetching. A mail scanner or preview fetches the URL with GET. The confirm page makes that harmless; never make the link itself sign the user in.

  • Where the link points. The link is built from the configured issuer, never from the Host header, so a forged request cannot make the server mail a valid token for the wrong host. The application refuses to start without an issuer.

  • Cross-device use. A numeric code works only in the browser that requested it, through the binding id kept in the session. A user who requests a code on a laptop and types it on a phone is refused, by design; a magic link has no such binding for a sign-in, which is the convenience and the risk of links: whoever opens the e-mail can complete the login. A second-factor link is accepted only in the session that already holds the primary factor.

  • Mailbox strength. The factor is as strong as the mailbox and as the password reset. This is why the example never lets the same mailbox be both the sign-in and the second factor, and withholds the e-mail second factor from users who enrolled a stronger one.

  • Phishing. A code typed into a fake page is lost to the attacker in real time; a magic link is no better against a user who is tricked into confirming. Neither is phishing-resistant: use a passkey where that matters.

  • Development. The compose file starts Mailpit, a local SMTP sink with a web UI, and the dev profile points the mail relay at it, so no real e-mail is ever sent; see Local services with Docker Compose.

  • Logging. Never log the code, the token, the address or a message body. Failures are logged by type only.

For the full reference see the Spring Security One-Time Token Login chapter, the NIST SP 800-63B-4 guidance on out-of-band and look-up authenticators and the OWASP Forgot Password Cheat Sheet, whose enumeration advice applies to every flow that sends a message to an address.
