Authorization Server from Scratch: Registered Clients & Client Management

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

What you build

A client is the application that asks the authorization server for tokens. This page builds the part of the example that decides which clients exist and how each one may behave: a small set of clients seeded at start-up, an administration REST API to create, change, rotate and delete clients, and, optionally, the OpenID Connect dynamic client registration endpoint. The protocol theory (what a client is, public versus confidential clients, client authentication methods) lives in the OAuth Reference, in Client Credentials and Client Authentication and in Discovery, Metadata and Client Registration. For the framework’s own description of the model see the Registered Clients section of the Spring Security Authorization Server guide.

The design has three layers, in line with the hexagonal layout of the architecture page:

  • The domain record ClientRegistration holds the definition of a client in plain Java and validates it (a public client must require PKCE, tls_client_auth needs a subject DN, private_key_jwt needs a JWK set).

  • The application layer creates and seeds clients (CreateClientUseCase, SeedRegisteredClientsUseCase) through a repository port. It never sees a Spring Security type.

  • The persistence adapter maps a ClientRegistration to Spring’s RegisteredClient (RegisteredClientMapper) and stores it with JdbcRegisteredClientRepository in the oauth2_registered_client table described in Data Model and Schema.

How it works

An administrator calls the REST API with a bearer token that has the admin scope and the API audience. The use case refuses the implicit grant and an already used client id, generates a secret only for clients that use a client_secret_* authentication method, stores it encoded, and returns the clear text exactly once.

sequenceDiagram autonumber actor A as Administrator participant API as ApiSecurityConfig (/api/**) participant UC as CreateClientUseCase participant H as PasswordHasher participant R as ClientRegistrationRepository participant M as RegisteredClientMapper participant J as JdbcRegisteredClientRepository A->>API: POST /api/admin/clients (Bearer, scope admin) API->>API: validate signature, issuer, expiry and audience API->>UC: execute(ClientRegistration) UC->>UC: refuse the implicit grant UC->>R: findByClientId(clientId) R-->>UC: empty, or ClientAlreadyExistsException (409) alt client uses client_secret_basic or client_secret_post UC->>UC: generate secret UC->>H: encode(secret) H-->>UC: encoded secret end UC->>R: save(registration, encoded secret or null) R->>M: toRegisteredClient(registration, id, issuedAt, secret) M-->>R: RegisteredClient R->>J: save(registeredClient) UC-->>A: 201 with the client and the clear secret, once

At start-up a second path creates the default clients: ClientSeeder (an ApplicationRunner) builds the definitions of DefaultClientDefinitions for every client whose redirect URIs are configured, and SeedRegisteredClientsUseCase stores the ones that do not exist yet. Running it again changes nothing.

Three points are worth noticing:

  • A client is seeded only when its redirect URIs are configured. Nothing is seeded by default, and no localhost URI exists outside the dev profile, so a fresh deployment starts with no usable client.

  • The secret of the confidential client comes from the environment and never from the source. The seed tag below shows definitions, not values.

  • The dev profile adds a device-client (public, device authorization grant) and a demo user through DevDataInitializer. It is a local development convenience and is inert without that profile.

Data

Clients live in the oauth2_registered_client table, whose columns (client_authentication_methods, authorization_grant_types, redirect_uris, scopes, client_settings, token_settings) are the schema that Spring defines. The settings columns hold JSON. The project’s own additions (audiences, mfa_required, the registered JWK set) are stored as custom keys inside client_settings, so no migration was needed. The full table is on the data model page.

Creating a client

    /**
     * Registers a client.
     *
     * @param registration the client.
     * @return the stored client and, for a client that uses a secret, its generated secret;
     *         {@code null} when the client has no {@code client_secret_*} authentication method.
     * @throws ClientAlreadyExistsException if the client id is taken.
     * @throws ImplicitClientRefusedException if the client has the implicit grant type.
     */
    public CreatedClient execute(final ClientRegistration registration) {
        if (registration.usesImplicit()) {
            throw new ImplicitClientRefusedException(registration.clientId());
        }
        if (clientRegistrationRepository.findByClientId(registration.clientId()).isPresent()) {
            throw new ClientAlreadyExistsException(registration.clientId());
        }
        if (!registration.usesClientSecret()) {
            clientRegistrationRepository.save(registration, null);
            return new CreatedClient(registration, null);
        }
        final var secret = clientSecretGenerator.generate();
        clientRegistrationRepository.save(registration, passwordHasher.encode(secret));
        return new CreatedClient(registration, secret);
    }

The secret is generated only for a client that authenticates with a client_secret_* method, and only its encoded form reaches the database. Encoding uses the delegating encoder explained in Storing Passwords Securely. Reference: Password Storage in the Spring Security reference.

The JDBC services

    /**
     * Creates the repository of registered clients.
     *
     * @param jdbcTemplate JDBC template of the application datasource.
     * @return the registered client repository.
     */
    @Bean
    public RegisteredClientRepository registeredClientRepository(final JdbcTemplate jdbcTemplate) {
        return new JdbcRegisteredClientRepository(jdbcTemplate);
    }

    /**
     * Creates the service that stores OAuth 2 authorizations, decorated to detect the reuse of rotated refresh
     * tokens.
     *
     * @param jdbcTemplate             JDBC template of the application datasource.
     * @param registeredClientRepository repository used to resolve the client of each authorization.
     * @param jsonMapperFactory        creates the mapper that serializes the stored attributes and claims.
     * @return the authorization service.
     */
    @Bean
    public OAuth2AuthorizationService authorizationService(
            final JdbcTemplate jdbcTemplate, final RegisteredClientRepository registeredClientRepository,
            final AuthorizationJsonMapperFactory jsonMapperFactory) {
        final var jsonMapper = jsonMapperFactory.create();
        final var service = new JdbcOAuth2AuthorizationService(jdbcTemplate, registeredClientRepository);
        service.setAuthorizationRowMapper(
                new JdbcOAuth2AuthorizationService.JsonMapperOAuth2AuthorizationRowMapper(
                        registeredClientRepository, jsonMapper));
        service.setAuthorizationParametersMapper(
                new JdbcOAuth2AuthorizationService.JsonMapperOAuth2AuthorizationParametersMapper(jsonMapper));
        return new ReuseDetectingAuthorizationService(service, JdbcClient.create(jdbcTemplate));
    }

    /**
     * Creates the service that stores the consents granted by users.
     *
     * @param jdbcTemplate             JDBC template of the application datasource.
     * @param registeredClientRepository repository used to resolve the client of each consent.
     * @return the authorization consent service.
     */
    @Bean
    public OAuth2AuthorizationConsentService authorizationConsentService(
            final JdbcTemplate jdbcTemplate, final RegisteredClientRepository registeredClientRepository) {
        return new JdbcOAuth2AuthorizationConsentService(jdbcTemplate, registeredClientRepository);
    }

The default in-memory repositories are replaced by the JDBC ones, so clients, authorizations and consents survive a restart and are shared by every instance. The authorization service is wrapped to detect the reuse of rotated refresh tokens, which the tokens page explains. Reference: RegisteredClientRepository in the Spring Security reference.

Advanced client authentication settings

A client may authenticate with a signed assertion (private_key_jwt, RFC 7523) or with a mutual TLS certificate (tls_client_auth, self_signed_tls_client_auth, RFC 8705) instead of a shared secret. The definition then carries a JWK set (inline or by URL), the JWS algorithm of the assertion and, for tls_client_auth, the expected certificate subject. The mapper copies them into ClientSettings:

        if (registration.jwkSetUrl() != null) {
            clientSettings.jwkSetUrl(registration.jwkSetUrl());
        }
        if (registration.jwks() != null) {
            clientSettings.setting(JWKS_SETTING, registration.jwks());
        }
        if (registration.tokenEndpointSigningAlgorithm() != null) {
            clientSettings.tokenEndpointAuthenticationSigningAlgorithm(
                    signingAlgorithmOf(registration.tokenEndpointSigningAlgorithm()));
        }
        if (registration.tlsClientAuthSubjectDn() != null) {
            clientSettings.x509CertificateSubjectDN(registration.tlsClientAuthSubjectDn());
        }

The settings used here are those of ClientSettings.Builder.

The JWK set that an administrator submits is validated before it is stored. Only public keys are accepted, and a key with private material, including a symmetric key, is refused:

    /**
     * Validates a JWK set sent by an administrator and returns its JSON text. Only public keys are accepted: a key
     * with private material (including a symmetric key) is refused.
     *
     * @param jwks the JWK set as a JSON object, or {@code null}.
     * @return the JWK set as JSON text, or {@code null} when none was given.
     * @throws InvalidClientJwksException if the object is not a JWK set, has no keys or has a private key.
     */
    public String toJson(final Map<String, Object> jwks) {
        if (jwks == null) {
            return null;
        }
        final JWKSet parsed;
        try {
            parsed = JWKSet.parse(JSONObjectUtils.toJSONString(jwks));
        } catch (ParseException | IllegalArgumentException e) {
            throw new InvalidClientJwksException("jwks is not a valid JWK set", e);
        }
        if (parsed.getKeys().isEmpty()) {
            throw new InvalidClientJwksException("jwks must contain at least one key");
        }
        if (parsed.getKeys().stream().anyMatch(JWK::isPrivate)) {
            throw new InvalidClientJwksException("jwks must contain public keys only");
        }
        return parsed.toString();
    }

Parsing uses JWKSet.parse from Nimbus JOSE + JWT; see the JWKSet Javadoc.

The OpenAPI contract of the same settings (request side):

        jwkSetUrl:
          type: string
          format: uri
          description: >-
            URL of the client's public JWK set, used to verify private_key_jwt assertions and self-signed
            certificates. Absent means none.
        jwks:
          type: object
          description: >-
            The client's public JWK set (an object with a keys array), alternative to jwkSetUrl. Only public keys
            are accepted: a key with private material is refused with 400 invalid-jwks. Absent means none.
          additionalProperties: true
        tokenEndpointAuthSigningAlgorithm:
          type: string
          description: JWS algorithm a client signs its private_key_jwt assertions with.
          enum: [ RS256, RS384, RS512, ES256, ES384, ES512, PS256, PS384, PS512 ]
        tlsClientAuthSubjectDn:
          type: string
          description: >-
            Expected subject distinguished name of the certificate of a tls_client_auth client, for example
            CN=client,O=Example. Required by tls_client_auth.
        certificateBoundAccessTokens:
          type: boolean
          description: >-
            Whether the access tokens issued to the client are bound to its mutual TLS certificate (cnf x5t#S256).
            Defaults to false.
          default: false

See the OpenAPI 3.1 Schema Object specification.

Dynamic client registration

    /**
     * Creates the customizer that turns on the client registration endpoint of the protocol chain.
     *
     * @return the customizer.
     */
    @Bean
    public ProtocolChainCustomizer clientRegistrationProtocolChainCustomizer() {
        return server -> server.oidc(oidc -> oidc.clientRegistrationEndpoint(Customizer.withDefaults()));
    }

The configuration class only exists when authserver.oidc.client-registration.enabled is true, so the endpoint is off by default. The caller needs an initial access token with scope client.create. Reference: OpenID Connect 1.0 Client Registration Endpoint and RFC 7591.

API

The administration API lives under /api/admin/clients. It is served by the stateless /api/** chain: the bearer token must be issued by this server, list the API audience and carry the admin scope. A token issued only for the resource server is refused with 401, and a valid token without the scope with 403. The examples assume a token in $ADMIN_TOKEN and the server on its development port.

Create a confidential client. The response contains the generated secret once:

curl -s -X POST http://localhost:9000/api/admin/clients \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "clientId": "reports",
    "name": "Reports service",
    "confidential": true,
    "authMethods": ["client_secret_basic"],
    "grantTypes": ["client_credentials"],
    "redirectUris": [],
    "scopes": ["documents.read"],
    "audiences": ["resource-server"],
    "accessTokenTtl": "PT5M",
    "refreshTokenTtl": "PT1H"
  }'

The answer is 201 with client (without any secret) and clientSecret. A second POST with the same clientId answers 409; a client with the implicit grant or a jwks that holds a private key answers 400.

List, read, replace and delete:

curl -s http://localhost:9000/api/admin/clients -H "Authorization: Bearer $ADMIN_TOKEN"
curl -s http://localhost:9000/api/admin/clients/reports -H "Authorization: Bearer $ADMIN_TOKEN"
curl -s -X PUT http://localhost:9000/api/admin/clients/reports \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{ "...": "the whole definition again; clientId must equal the path" }'
curl -s -X DELETE http://localhost:9000/api/admin/clients/reports -H "Authorization: Bearer $ADMIN_TOKEN"

PUT replaces the definition but never touches the secret, and it answers 400 when the clientId of the body differs from the path. DELETE answers 204 and also removes the client’s authorizations and consents. Unknown clients answer 404.

Rotate the secret of a confidential client. The old secret stops working immediately; a public client answers 400:

curl -s -X POST http://localhost:9000/api/admin/clients/reports/secret \
  -H "Authorization: Bearer $ADMIN_TOKEN"

Register a client dynamically (only when enabled). The answer contains client_id and client_secret:

curl -s -X POST http://localhost:9000/connect/register \
  -H "Authorization: Bearer $INITIAL_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"client_name": "Dynamic", "redirect_uris": ["https://app.example.test/callback"], "grant_types": ["authorization_code"], "token_endpoint_auth_method": "client_secret_basic"}'

The request and response schemas (ClientRequest, ClientResponse, CreatedClientResponse, ClientSecretResponse) are in the OpenAPI file of the example under apis/auth-server/rest-server/.

Tests

ClientAdminIT runs the application against a real PostgreSQL (Testcontainers) and proves the behaviours above: seeding is idempotent and stores an Argon2 encoded secret (and none for the public client), the whole create, read, update, delete life of a client, that updating keeps the secret, that rotating replaces it and invalidates the old one, that a non-admin caller gets 403 and a token for the wrong audience 401, that deleting a client makes its tokens inactive, and that dynamic registration needs an initial access token. The region below shows the private_key_jwt case:

    /**
     * Verifies that a {@code private_key_jwt} client is created with its public JWK set and no secret, that the
     * authentication settings round trip through the API and survive an update.
     *
     * @throws Exception if a request cannot be performed.
     */
    @Test
    void adminApi_whenClientUsesPrivateKeyJwt_storesKeysAndGeneratesNoSecret() throws Exception {
        final var admin = fixtures.adminToken();
        final var clientId = "keyed-" + UUID.randomUUID();
        final var publicSet = new JWKSet(new RSAKeyGenerator(RSA_KEY_SIZE).keyID("k1").generate().toPublicJWK());

        final var created = body(send(post(CLIENTS_PATH), admin, keyClientJson(clientId, publicSet.toString()))
                .andExpect(status().isCreated()));

        assertTrue(created.get("clientSecret") == null || created.get("clientSecret").isNull());
        assertNull(secretOf(clientId));
        final var client = created.get("client");
        assertEquals("PS256", client.get("tokenEndpointAuthSigningAlgorithm").asString());
        assertEquals("k1", client.get("jwks").get("keys").get(0).get("kid").asString());
        assertTrue(client.get("certificateBoundAccessTokens").asBoolean());
        assertEquals("CN=" + clientId, client.get("tlsClientAuthSubjectDn").asString());
        assertEquals("https://client.example.test/jwks.json", client.get("jwkSetUrl").asString());

        final var updated = body(send(put(CLIENTS_PATH + "/" + clientId), admin,
                keyClientJson(clientId, publicSet.toString())).andExpect(status().isOk()));
        assertEquals(client, updated);
        assertNull(secretOf(clientId));
        send(post(CLIENTS_PATH + "/" + clientId + "/secret"), admin, "{}").andExpect(status().isBadRequest());
    }

The test uses MockMvc and the Testcontainers PostgreSQL module.

Security notes and pitfalls

  • Exact redirect URIs. The authorization server compares redirect URIs exactly. Never register wildcards or a broad prefix; an open redirect on a registered URI is how authorization codes are stolen (RFC 9700, OAuth 2.0 Security Best Current Practice).

  • Secrets are stored encoded. Only the encoded secret is in oauth2_registered_client; the clear text is shown once at creation or rotation and is never logged. Losing it means rotating it.

  • Public clients need PKCE. ClientRegistration refuses a public client that does not require PKCE, and both seeded clients require it (RFC 7636).

  • Prefer asymmetric client authentication for high-value service clients: nothing secret is stored on the server, only a public JWK set.

  • Who may call the admin API. Only a token with the admin scope and the API audience. A role alone never grants access, and a token issued for the resource server is useless against the administration API.

  • No implicit grant. The API refuses it. Only an opt-in demo profile seeds such a client; see the legacy-implicit profile of the example.

  • Dynamic registration is off by default. Enable it only with an initial access token that is hard to obtain, and review what registered clients may request. Open registration lets anyone create a client.

  • Seeding is create-only. Changing the seed configuration after the first start does not update existing clients: use the API.
