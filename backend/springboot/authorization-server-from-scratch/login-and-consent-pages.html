Authorization Server from Scratch: Login, Consent & Logout Pages

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

What you build

The authorization server is the only place where the user types a credential, so its pages are part of the protocol surface: the authorization endpoint redirects the browser to them and expects the browser to come back. This page builds three of them, all rendered on the server with Thymeleaf and all served from the auth-server application described in Architecture:

  • the login page (/login), a thin shell that renders one fragment per sign-in method, so the password form is only the first of them;

  • the consent page (/oauth2/consent), where the user approves or denies the scopes a client asks for;

  • the logout confirmation page (/logout), which asks before ending the session and posts with a CSRF token.

Around them sit the security headers and the Content-Security-Policy that every page is served with, the branding of the pages and the PageRenderer that turns a template into the text/html answer of an operation generated from the pages' OpenAPI contract. The protocol background is in the OAuth Reference: Logout and Session Management covers RP-initiated logout, and Thymeleaf and Spring Security integration covers the login template, the CSRF hidden field that th:action adds and why logging out is a POST.

The page forms of the second factor, passkeys, one-time tokens and social sign-in are not repeated here. Each of them contributes its own LoginMethodFragment or second-factor fragment to the pages below, and the later pages of the guide describe them one by one. The example contains no custom AuthenticationSuccessHandler, no continue parameter and no custom LogoutSuccessHandler: the defaults of Spring Security do those jobs, and the sections below say which.

How it works

Login and consent

An application that needs a token redirects the browser to /oauth2/authorize. The protocol chain finds no session and ExceptionTranslationFilter saves the request in the session and the chain’s entry point (a LoginUrlAuthenticationEntryPoint) redirects to /login. The form posts to the login chain, whose default success handler returns to the saved request. If the client was registered with requireAuthorizationConsent, the authorization endpoint then redirects to /oauth2/consent, and the user’s decision is posted back to /oauth2/authorize, which answers with the authorization code, or with error=access_denied when no scope is posted.

sequenceDiagram autonumber actor U as User participant B as Browser participant P as Protocol chain (order 1) participant L as Login chain (order 2) participant C as ConsentController participant R as Client redirect_uri B->>P: GET /oauth2/authorize (client_id, scope, state, code_challenge) P-->>B: 302 /login (request saved in the session) B->>L: GET /login L-->>B: 200 login page (one fragment per LoginMethodFragment) U->>L: POST /login (username, password, _csrf) L-->>B: 302 to the saved request, /oauth2/authorize B->>P: GET /oauth2/authorize P-->>B: 302 /oauth2/consent (client_id, scope, state) B->>C: GET /oauth2/consent C-->>B: 200 consent page (scopes as checked boxes) U->>P: POST /oauth2/authorize (client_id, state, approved scopes, _csrf) P-->>B: 302 to redirect_uri with code and state B->>R: GET redirect_uri?code=...

The consent page itself never completes anything: it renders a form, and the decision goes to the framework’s authorization endpoint, which owns the state it generated for the consent step (the state field is posted back unchanged). The same page serves the device flow, in which case user_code is present and the decision is posted to the device verification endpoint instead.

Logout

There are two ways out, and the example supports both. The local logout is the confirmation page: a GET never signs anybody out, because any page could trigger it, and the confirmation form posts to /logout with the CSRF token. The RP-initiated logout is the OpenID Connect endpoint /connect/logout, which the default OIDC configuration already exposes: a client sends the user there with an id_token_hint, and the server honours a post_logout_redirect_uri only when the client registered it (the seeded clients register none by default).

sequenceDiagram autonumber actor U as User participant B as Browser participant S as Authorization server U->>B: choose "Sign out" in the client B->>S: GET /connect/logout (id_token_hint, post_logout_redirect_uri, state) S->>S: validate the hint, the client and the registered post-logout URI S->>S: invalidate the session S-->>B: 302 to the registered post_logout_redirect_uri with state Note over B,S: local logout without a client B->>S: GET /logout S-->>B: 200 confirmation page with a CSRF token U->>S: POST /logout (_csrf) S->>S: invalidate the session and delete JSESSIONID S-->>B: 302 /login?logout

Using Thymeleaf

Data

The pages keep no table of their own. The login failure lives in the HTTP session under Spring Security’s WebAttributes.AUTHENTICATION_EXCEPTION attribute, the saved authorization request in the same session, and the approved scopes in oauth2_authorization_consent, described in Data Model and Schema. The text of every page is in messages.properties, so the pages can be translated, and the branding is configuration.

Code

The login page

LoginController implements the interface generated from the pages contract, so the path, the parameters and the content type come from the OpenAPI file and the controller cannot drift from it. It sorts the LoginMethodFragment beans once, and for a request with ?error it maps the exception that Spring Security stored in the session to a message key. The key never says whether the account exists.

    /**
     * Renders the login page.
     *
     * @param error  present (even if empty) when the previous attempt failed.
     * @param logout present (even if empty) when the user has just signed out.
     * @return the login page.
     */
    @Override
    public ResponseEntity<String> loginPage(final String error, final String logout) {
        final var model = new HashMap<String, Object>();
        model.put(LOGIN_PATH_ATTRIBUTE, LOGIN_PATH);
        model.put(FRAGMENTS_ATTRIBUTE, fragments);
        if (error != null) {
            model.put(ERROR_MESSAGE_ATTRIBUTE, errorMessages.keyOf(lastFailure()));
        }
        model.put(LOGGED_OUT_ATTRIBUTE, logout != null);
        return pageRenderer.render(VIEW_NAME, model);
    }

This derives from the Spring Security form login documentation, whose loginPage customization it implements.

The template is a shell. It loops over the fragments and includes each by the single expression that LoginMethodFragment.reference() returns, so adding a sign-in method never edits login.html.

<html xmlns:th="http://www.thymeleaf.org" th:replace="~{fragments/layout :: layout(~{::title}, ~{::main})}">
<head>
  <title th:text="#{login.title}">Sign in</title>
</head>
<body>
<main>
  <h1 th:text="#{login.heading}">Sign in</h1>
  <div th:if="${errorMessageKey != null}" role="alert" th:text="#{${errorMessageKey}}">Invalid username or password.</div>
  <div th:if="${loggedOut}" role="status" th:text="#{login.logout}">You have been signed out.</div>
  <section th:each="fragment : ${fragments}" class="login-method">
    <!-- LoginMethodFragment.reference() is the single source of the "template :: fragment" expression -->
    <div th:replace="~{__${fragment.reference()}__}"></div>
  </section>
</main>
</body>
</html>

This derives from the Thymeleaf template layout documentation.

The username and password form is the first of those fragments. The autocomplete tokens let password managers fill it, and th:action makes Thymeleaf add the CSRF hidden field.

<form th:fragment="form" method="post" th:action="@{${loginPath}}">
  <p>
    <label for="username" th:text="#{login.username}">Username</label>
    <input type="text" id="username" name="username" required autofocus autocomplete="username">
  </p>
  <p>
    <label for="password" th:text="#{login.password}">Password</label>
    <input type="password" id="password" name="password" required autocomplete="current-password">
  </p>
  <button type="submit" th:text="#{login.submit}">Sign in</button>
</form>

This derives from the Spring Security CSRF documentation, which describes the token that th:action adds.

The layout fragment is shared by every page. It contains no inline script or style, which is what lets the Content-Security-Policy below forbid both, and its logo is decorative, with an empty alt.

<html xmlns:th="http://www.thymeleaf.org" th:fragment="layout(title, content)" th:lang="${#locale.language}" lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title th:replace="${title}">Authorization server</title>

</head>
<body>
<header class="branding">

       class="branding-logo">

    Irurueta Auth Server</span>

This derives from the Thymeleaf template layout documentation.

Rendering the pages

PageRenderer is what lets a page be a controller that returns a ResponseEntity<String>, which is the shape the OpenAPI generator produces. It resolves the view with the application’s view resolvers and the request’s locale, renders it against the current request into a ContentCachingResponseWrapper and returns the captured HTML. Because the view is rendered against the real request, the CSRF field, the @{...} links and the messages keep working. It also adds the branding to every model.

    /**
     * Renders a page.
     *
     * @param viewName name of the view (the Thymeleaf template).
     * @param model    model attributes of the page; the branding is added to them.
     * @return a {@code 200} with the page as {@code text/html}.
     * @throws IllegalStateException if no view resolver knows the view, or the view cannot be rendered.
     */
    public ResponseEntity<String> render(final String viewName, final Map<String, ?> model) {
        final var locale = RequestContextUtils.getLocale(request);
        final var view = resolve(viewName, locale);
        final var attributes = new LinkedHashMap<String, Object>(model);
        attributes.put(BrandingProvider.MODEL_ATTRIBUTE, brandingProvider.branding());
        final var capture = new ContentCachingResponseWrapper(response);
        try {
            view.render(attributes, request, capture);
        } catch (final Exception e) {
            throw new IllegalStateException("The page " + viewName + " cannot be rendered", e);
        }
        final var html = new String(capture.getContentAsByteArray(), Charset.forName(capture.getCharacterEncoding()));
        return ResponseEntity.ok().contentType(TEXT_HTML_UTF8).body(html);
    }

This derives from the Thymeleaf reference, whose views the renderer resolves and renders by hand.

Security headers and the Content-Security-Policy

LoginHeadersCustomizer is a LoginChainCustomizer with @Order(0), so it runs before the other customizers of the login chain. It sets the Content-Security-Policy, X-Content-Type-Options and Referrer-Policy: no-referrer.

/**
 * Adds the security headers of the server-rendered pages: the content security policy that
 * {@link LoginContentSecurityPolicy} builds (same-origin resources only, no framing, and the origin of an absolute
 * branding logo URL for images), {@code X-Content-Type-Options} and {@code Referrer-Policy}.
 *
 * <p>The policy deliberately has no {@code form-action} directive: browsers also apply it to the redirects that follow
 * a form submission, so {@code form-action 'self'} would block the redirect from the login or consent form back to the
 * client application's {@code redirect_uri}, which is on another origin.
 */
@Component
@Order(0)
@RequiredArgsConstructor
public class LoginHeadersCustomizer implements LoginChainCustomizer {

    /** Builds the content security policy from the branding. */
    private final LoginContentSecurityPolicy contentSecurityPolicy;

    @Override
    public void customize(final HttpSecurity http) {
        final var policy = contentSecurityPolicy.policy();
        http.headers(headers -> {
            headers.contentSecurityPolicy(csp -> csp.policyDirectives(policy));
            headers.contentTypeOptions(Customizer.withDefaults());
            headers.referrerPolicy(referrer -> referrer.policy(ReferrerPolicy.NO_REFERRER));
        });
    }
}

This derives from the Spring Security HTTP response headers documentation.

The policy itself is built from the branding, so an absolute logo URL on another origin adds exactly that origin to img-src and nothing else. data: images are allowed for the QR code of an authenticator app, which is rendered in memory so that its secret never becomes a resource of its own.

/**
 * Builds the content security policy of the server-rendered pages from the {@link BrandingProperties}: same-origin
 * resources only and no framing, except that images may also be {@code data:} URIs (the QR code of an authenticator
 * app, rendered in memory so its secret never becomes a resource of its own) and, when the branding logo is an
 * absolute {@code http(s)} URL, come from its origin ({@code img-src 'self' data: <scheme://host[:port]>}). A relative
 * logo URL is same-origin and needs nothing more.
 */
@Component
@RequiredArgsConstructor
public class LoginContentSecurityPolicy {

    /**
     * Policy of the pages when the logo, if any, is served by this application. Its last directive lists the image
     * sources, so the origin of an absolute logo URL is appended to it.
     */
    public static final String DEFAULT_POLICY = "default-src 'self'; frame-ancestors 'none'; img-src 'self' data:";

    /** Schemes whose origin is added for an absolute logo URL. */
    private static final Set<String> WEB_SCHEMES = Set.of("http", "https");

    /** Provider of the configured branding; absent in web slices that do not enable the properties. */
    private final ObjectProvider<BrandingProperties> branding;

    /**
     * Builds the policy.
     *
     * @return {@link #DEFAULT_POLICY}, with the logo's origin added to its {@code img-src} directive when the logo is
     *         an absolute {@code http(s)} URL.
     */
    public String policy() {
        final var logoUrl = branding.getIfAvailable(() -> new BrandingProperties(null, null, null)).logoUrl();
        return originOf(logoUrl).map(origin -> DEFAULT_POLICY + " " + origin).orElse(DEFAULT_POLICY);
    }

    /**
     * Extracts the origin of an absolute {@code http(s)} URL.
     *
     * @param url the URL; may be empty.
     * @return {@code scheme://host[:port]} in lower case, or empty when the URL is relative, not {@code http(s)},
     *         has no host or cannot be parsed.
     */
    private static Optional<String> originOf(final String url) {
        try {
            final var uri = new URI(url);
            final var scheme = uri.getScheme() == null ? "" : uri.getScheme().toLowerCase(Locale.ROOT);
            if (!WEB_SCHEMES.contains(scheme) || uri.getHost() == null) {
                return Optional.empty();
            }
            final var port = uri.getPort() < 0 ? "" : ":" + uri.getPort();
            return Optional.of(scheme + "://" + uri.getHost().toLowerCase(Locale.ROOT) + port);
        } catch (final URISyntaxException invalid) {
            return Optional.empty();
        }
    }
}

This derives from the OWASP Content Security Policy Cheat Sheet.

Branding

The application name, the logo and the footer are bound from authserver.ui.branding.*, with blank values replaced by defaults, so a deployment re-brands the pages without touching a template.

/**
 * Branding shown by the login, consent, logout and error pages, bound from {@code authserver.ui.branding.*}.
 *
 * @param applicationName name shown in the page header and title; defaults to {@link #DEFAULT_APPLICATION_NAME}.
 * @param logoUrl         optional URL of a logo image: a path served by this application, or an absolute
 *                        {@code http(s)} URL whose origin the content security policy then allows for images; empty
 *                        when there is none.
 * @param footerText      optional text shown below every page; empty when there is none.
 */
@ConfigurationProperties("authserver.ui.branding")
public record BrandingProperties(String applicationName, String logoUrl, String footerText) {

    /** Application name used when none is configured. */
    public static final String DEFAULT_APPLICATION_NAME = "Irurueta Auth Server";

    /**
     * Applies the defaults.
     *
     * @param applicationName name shown in the page header, blank for the default.
     * @param logoUrl         optional logo URL, blank for none.
     * @param footerText      optional footer text, blank for none.
     */
    public BrandingProperties {
        applicationName = StringUtils.hasText(applicationName) ? applicationName : DEFAULT_APPLICATION_NAME;
        logoUrl = StringUtils.hasText(logoUrl) ? logoUrl : "";
        footerText = StringUtils.hasText(footerText) ? footerText : "";
    }
}

This derives from the Spring Boot typesafe configuration properties documentation.

The consent page

ConsentController receives the parameters the authorization endpoint appends (client_id, scope, state, and user_code for a device), finds the client, reads the scopes the signed-in user granted earlier and builds the view model with a mapper. An unknown client is a 400. The decision path is the authorization endpoint, or the device verification endpoint when there is a user code.

    /**
     * Renders the consent page.
     *
     * @param clientId identifier of the client that asks for access.
     * @param scope    requested scopes, space delimited.
     * @param state    state of the authorization request.
     * @param userCode user code of the device the consent is asked for, {@code null} for an authorization request;
     *                 the decision of a device is posted to the device verification endpoint, with the code.
     * @return the consent page.
     * @throws ResponseStatusException with status 400 when the client is unknown.
     */
    @Override
    public ResponseEntity<String> consentPage(final String clientId, final String scope, final String state,
            final String userCode) {
        final var client = registeredClientRepository.findByClientId(clientId);
        if (client == null) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "Unknown client");
        }
        final var principalName = request.getUserPrincipal().getName();
        final var consent = authorizationConsentService.findById(client.getId(), principalName);
        final Set<String> granted = consent == null ? Set.of() : consent.getScopes();
        final var model = new HashMap<String, Object>();
        model.put(CONSENT_ATTRIBUTE, mapper.toModel(client, principalName, state, scope, granted,
                RequestContextUtils.getLocale(request)));
        if (userCode == null) {
            model.put(DECISION_PATH_ATTRIBUTE, AUTHORIZE_PATH);
        } else {
            model.put(DECISION_PATH_ATTRIBUTE, DeviceVerificationPageApi.PATH_DEVICE_VERIFICATION_PAGE);
            model.put(USER_CODE_ATTRIBUTE, userCode);
        }
        return pageRenderer.render(VIEW_NAME, model);
    }

This derives from the Spring Authorization Server protocol endpoints documentation, which defines the consent page and the parameters it receives.

The template posts the approved scopes as checked boxes. Denying posts no scope at all, which the authorization endpoint answers with access_denied. Both forms carry the CSRF token through th:action.

<html xmlns:th="http://www.thymeleaf.org" th:replace="~{fragments/layout :: layout(~{::title}, ~{::main})}">
<head>
  <title th:text="#{consent.title}">Authorize application</title>
</head>
<body>
<main>
  <h1 th:text="#{consent.heading(${consent.clientName})}">Authorize application</h1>
  <p th:text="#{consent.intro(${consent.clientName}, ${consent.principalName})}">The application wants access.</p>
  <!-- the decision is posted back to the authorization endpoint, which reads client_id, state and the approved scopes, or
       to the device verification endpoint, which also reads the user code, when the consent is asked for a device -->
  <form method="post" th:action="@{${decisionPath}}">
    <input type="hidden" name="client_id" th:value="${consent.clientId}">
    <input type="hidden" name="state" th:value="${consent.state}">
    <input type="hidden" name="user_code" th:if="${userCode}" th:value="${userCode}">
    <p th:if="${#lists.isEmpty(consent.scopesToApprove)}" th:text="#{consent.none}">No additional permission.</p>
    <ul class="scopes">
      <li th:each="scope, status : ${consent.scopesToApprove}">
        <input type="checkbox" name="scope" th:id="${'scope-' + status.index}" th:value="${scope.name}" checked>
        <label th:for="${'scope-' + status.index}" th:text="${scope.description}">Scope</label>
      </li>
    </ul>
    <button type="submit" id="allow" th:text="#{consent.allow}">Allow</button>
  </form>
  <!-- denying posts no scope at all, which the authorization endpoint answers with error=access_denied -->
  <form method="post" th:action="@{${decisionPath}}">
    <input type="hidden" name="client_id" th:value="${consent.clientId}">
    <input type="hidden" name="state" th:value="${consent.state}">
    <input type="hidden" name="user_code" th:if="${userCode}" th:value="${userCode}">
    <button type="submit" id="deny" class="secondary" th:text="#{consent.deny}">Deny</button>
  </form>
  <section th:if="${!#lists.isEmpty(consent.approvedScopes)}">
    <p th:text="#{consent.previous}">You already granted these permissions:</p>
    <ul class="scopes">
      <li th:each="scope : ${consent.approvedScopes}" th:text="${scope.description}">Scope</li>
    </ul>
  </section>
</main>
</body>
</html>

This derives from the Spring Authorization Server protocol endpoints documentation, which lists the parameters the consent decision must post.

Logout

The logout configuration is four calls: the path, the success URL, session invalidation and the deletion of the session cookie. Spring Security only accepts a POST here when CSRF protection is on, which is the default, so a third-party page cannot sign the user out.

    @Override
    public void customize(final HttpSecurity http) {
        http.logout(logout -> logout
                .logoutUrl(LOGOUT_PATH)
                .logoutSuccessUrl(LOGOUT_SUCCESS_URL)
                .invalidateHttpSession(true)
                .deleteCookies(SESSION_COOKIE));
    }

This derives from the Spring Security logout documentation.

The confirmation page asks the question and posts to /logout.

<html xmlns:th="http://www.thymeleaf.org" th:replace="~{fragments/layout :: layout(~{::title}, ~{::main})}">
<head>
  <title th:text="#{logout.title}">Sign out</title>
</head>
<body>
<main>
  <h1 th:text="#{logout.heading}">Sign out</h1>
  <p th:text="#{logout.question}">Do you want to sign out?</p>
  <!-- th:action adds the CSRF token: the logout endpoint only accepts a POST that carries it -->
  <form method="post" th:action="@{/logout}">

</body>
</html>

This derives from the Spring Security logout documentation and the OpenID Connect RP-Initiated Logout 1.0 specification, for the other way out.

Fetching the pages by hand (the example listens on port 9000 locally; the consent page needs a session of a signed-in user and the parameters the authorization endpoint generates, so it is reached through a browser):

curl -i 'http://localhost:9000/login'
curl -i 'http://localhost:9000/login?error'
curl -i 'http://localhost:9000/login?logout'
curl -i 'http://localhost:9000/logout' --cookie 'JSESSIONID=<session of a signed-in user>'

The first answers 200 with the login page and the security headers listed in the security notes, the second shows the generic failure message, and the third says the user has signed out. A POST /logout without the CSRF token is answered with 403 and keeps the session.

Tests

The behaviour of the pages is covered by tests that carry no tagged region, so they are described rather than pasted:

  • LoginPageIT renders the login page in a web slice with the real password fragment and checks the layout, the autocomplete hints and the CSRF field; that a post without the token is 403; that an unknown user and a wrong password get an identical response; the message of every kind of failure; the signed-out status; and that a successful sign-in returns to the authorization request saved before the redirect.

  • LoginContentSecurityPolicyIT checks that a logo on another origin is rendered and that only its origin is allowed as an image source.

  • ConsentPageIT drives the real authorization endpoint of a client that requires consent up to the consent page, then checks that the page lists the scope and both decisions, that denying redirects with access_denied and that allowing redirects with the authorization code.

  • LogoutIT checks the confirmation page and its CSRF field, that a confirmed logout invalidates the session and returns to /login?logout, that a logout without the token is refused, and that /connect/logout honours a post_logout_redirect_uri only when the client registered it.

  • The unit tests LoginControllerTest, LoginHeadersCustomizerTest, LoginContentSecurityPolicyTest, BrandingPropertiesTest, ConsentControllerTest and LogoutChainCustomizerTest cover each class of this page in isolation.

Security notes and pitfalls

The headers of the pages and what each one stops:

Header or directive Value in the example What it stops

Content-Security-Policy: default-src 'self'

Same-origin resources only, plus img-src 'self' data: and the origin of an absolute logo URL

Injected scripts, styles, frames and connections to other origins. The templates contain no inline script or style, so nothing needs unsafe-inline.

frame-ancestors 'none'

No page of the server may be framed

Clickjacking: a hostile page overlaying the consent or login page in an invisible frame to collect clicks. It is the modern replacement for X-Frame-Options, which Spring Security also sends by default.

X-Content-Type-Options: nosniff

Spring Security default

The browser guessing a script or style type for a response served with another type.

Referrer-Policy: no-referrer

Set in LoginHeadersCustomizer

The authorization request, with its state and PKCE challenge, leaking in the Referer header to the logo’s host or any link.

  • No form-action directive, on purpose. Browsers also apply form-action to the redirect that follows a form submission, so form-action 'self' would block the redirect from the login or consent form back to the client’s redirect_uri, which is on another origin. The CSRF token and the exact redirect URI registration protect the form instead.

  • CSRF on every form. The login, consent and logout forms use th:action, which adds the token, and Spring Security rejects a post without it. The consent form matters most: without it a hostile page could approve scopes on behalf of the signed-in user. See the Spring Security CSRF documentation.

  • Open redirect. The example has no continue or returnTo parameter on the server: after login the user returns to the request Spring Security saved in the session, which the server itself stored, and the authorization endpoint only redirects to a redirect_uri that the client registered exactly. The same holds for logout, where a post_logout_redirect_uri must be registered. A page that accepted a free redirect target would need an allow-list; see the OWASP Unvalidated Redirects and Forwards Cheat Sheet and RFC 6749, open redirectors.

  • Clickjacking and consent. The consent page is the one worth framing, and frame-ancestors 'none' is why it cannot be framed. See the OWASP Clickjacking Defense Cheat Sheet.

  • No account enumeration. The login page shows a generic message, and an unknown user gets the same response as a wrong password (LoginPageIT). The distinct messages exist only for states the user already proved they know, such as a locked or expired account.

  • GET never logs out. The confirmation page exists because a logout link that works on GET can be triggered by any image tag on any page.

  • Unregistered post-logout URIs are ignored. An RP-initiated logout that names a post_logout_redirect_uri the client did not register is not redirected there, and the seeded clients register none.

  • Extension point for later methods. A new sign-in method contributes a LoginMethodFragment for its form and a LoginChainCustomizer for its filters and permitted paths. Its form must use th:action, avoid inline script and style, and load only same-origin resources, or the policy above will block it. The passkey and one-time-token pages of the guide show the pattern.
