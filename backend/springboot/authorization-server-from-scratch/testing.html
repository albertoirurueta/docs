Authorization Server from Scratch: Testing the Authorization Server

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

What you build

An authorization server is mostly behaviour that is easy to break and hard to see: a redirect that must not happen, a claim that must be present, a code that must work once. The example tests it at four levels, and this page shows what each level proves, which classes to read, and the few tricks that keep the tests fast and honest. It is a tour of the example’s tests, not a testing course: the general techniques are on Unit and Integration Testing and, for OAuth flows, on Testing and Debugging OAuth.

The example has roughly 560 unit test classes, 94 integration test classes and 9 end-to-end test classes (counted on the main branch when this page was written; the numbers move). Every test of every page of this guide is one of them, which is why the "Tests" section of a feature page can name a class instead of showing code.

The test pyramid

That a security configuration admits, refuses and challenges the right requests, using a synthetic token or login instead of a real sign-in

ApiSecurityConfigIT, LoginPageIT, LoginContentSecurityPolicyIT and SecurityConfigIT of the authorization server (all @WebMvcTest), SecurityConfigIT of the resource server

Integration with Testcontainers

End to end

Failsafe in the e2e-tests module, Docker and a headless browser

The packaged applications talking over real HTTP: a browser signs in, a passkey ceremony completes, an e-mail link is followed, a service gets a token and calls the API

SignInSmokeIT, PasskeyEndToEndIT, OttEndToEndIT, BffEndToEndIT, ClientCredentialsEndToEndIT, TokenExchangeEndToEndIT, DeviceFlowEndToEndIT, ResourceServerEndToEndIT

The rule that separates the first two levels from the rest is the file name. *Test classes run in Surefire and start no Spring context; every test that starts Spring or a container is a *IT class run by Failsafe. ./mvnw test is therefore the fast loop, and ./mvnw -B clean verify runs everything, with the build gates. Note that some *IT classes are slices, so the suffix says "run with Failsafe", not "needs Docker".

Unit tests

A unit test builds the class with its collaborators as plain objects and asserts a result. The domain and application modules of the hexagonal layout are written for this: they have no Spring and no I/O, so a test needs no setup beyond new. TotpAlgorithmTest is the model: it keeps the shared secret and the eight-digit expected codes of RFC 6238 Appendix B, truncates them to six digits and asserts that the generator produces them at each Unix time, so a change in the algorithm cannot pass. The filter chain customizers are tested the same way, against a mocked HttpSecurity or a recorded set of calls, and HexagonalArchitectureTest (ArchUnit, one per application) fails the build when a layer imports one it should not.

No unit test of the example is a tagged region, so no listing is shown for this level. The classes above are the ones to open.

Slices with spring-security-test

Spring Security’s test support adds request post-processors to MockMvc, so a test can arrive already authenticated without signing in:

  • jwt() puts a Jwt authentication in the request, with claims set by the test. The resource server’s SecurityConfigIT uses it to prove that a missing scope is 403, a wrong audience is 401 and a password-only sign-in needs a step-up to delete. ApiSecurityConfigIT does the same for the account API chain, with a probe controller and a @WebMvcTest slice.

  • oidcLogin() is a signed-in user as the BFF sees one, with ID token claims and an authorized client. The BFF’s SecurityConfigIT, UserControllerIT and DocumentsApiIT use it for /bff/user and the relayed API calls; they run with PostgreSQL, because the BFF keeps its session there.

  • csrf() adds a valid CSRF token to a state-changing request. The example uses it in dozens of tests of the login chain and of the BFF, and a test of the opposite (a post without it is refused) for each page that posts a form.

The documentation of the post-processors is on the Spring Security testing pages linked below. The example does not use oauth2Client() or @WithMockUser; it needs a synthetic user only where the code reads an Authentication, and jwt() and oidcLogin() cover those places.

The closest tagged example is TotpApiIT in the next section. It uses jwt() as described here, but it runs with the real database, because the answer depends on stored data.

Integration tests with Testcontainers

@PostgresIT (from the test-support module) is one annotation that starts the application with the test profile and a PostgreSQL container, runs the Flyway migrations on it and a key-encryption secret made for tests. It is a @SpringBootTest that imports the container configuration, so a test class stays small. A test injects MockMvc, repositories and a JdbcClient, and uses the fixtures of the module (AuthServerFixtures) to create a user, a client and a token. The integration pages of the Spring Boot and Docker sections explain the mechanics: Spring Boot Integration Tests with Testcontainers (Locally and in GitHub Actions) and Testcontainers Fundamentals.

Four tagged tests are the examples of this level. Each proves a behaviour that no lower level can: it needs the real tables and the real chains.

A client with keys and no secret (ClientAdminIT). The administration API creates a private_key_jwt client from its public JWK set, returns no secret, stores none, and the settings survive an update:

    /**
     * Verifies that a {@code private_key_jwt} client is created with its public JWK set and no secret, that the
     * authentication settings round trip through the API and survive an update.
     *
     * @throws Exception if a request cannot be performed.
     */
    @Test
    void adminApi_whenClientUsesPrivateKeyJwt_storesKeysAndGeneratesNoSecret() throws Exception {
        final var admin = fixtures.adminToken();
        final var clientId = "keyed-" + UUID.randomUUID();
        final var publicSet = new JWKSet(new RSAKeyGenerator(RSA_KEY_SIZE).keyID("k1").generate().toPublicJWK());

        final var created = body(send(post(CLIENTS_PATH), admin, keyClientJson(clientId, publicSet.toString()))
                .andExpect(status().isCreated()));

        assertTrue(created.get("clientSecret") == null || created.get("clientSecret").isNull());
        assertNull(secretOf(clientId));
        final var client = created.get("client");
        assertEquals("PS256", client.get("tokenEndpointAuthSigningAlgorithm").asString());
        assertEquals("k1", client.get("jwks").get("keys").get(0).get("kid").asString());
        assertTrue(client.get("certificateBoundAccessTokens").asBoolean());
        assertEquals("CN=" + clientId, client.get("tlsClientAuthSubjectDn").asString());
        assertEquals("https://client.example.test/jwks.json", client.get("jwkSetUrl").asString());

        final var updated = body(send(put(CLIENTS_PATH + "/" + clientId), admin,
                keyClientJson(clientId, publicSet.toString())).andExpect(status().isOk()));
        assertEquals(client, updated);
        assertNull(secretOf(clientId));
        send(post(CLIENTS_PATH + "/" + clientId + "/secret"), admin, "{}").andExpect(status().isBadRequest());
    }

See the Spring Framework reference for MockMvc.

Step-up for the account API (TotpApiIT). A token that shows no recent multi-factor sign-in is answered with 401, the RFC 9470 challenge and the problem type of the failure, and nothing is deleted. This is also the example of jwt() with an old auth_time:

    /**
     * Verifies that removing or resetting the second factor of an account that has one needs a recent multi-factor
     * sign-in: a password-only token and an old multi-factor one are answered with {@code 401} and the RFC 9470
     * challenge, and nothing is removed.
     *
     * @throws Exception if a request cannot be performed.
     */
    @Test
    void disableTotp_whenTokenShowsNoRecentMultiFactorSignIn_answersTheStepUpChallenge() throws Exception {
        final var user = fixtures.createUser();
        enableTotp(user);
        final var device = trust(user, "Firefox on Linux");
        final var old = jwt().jwt(token -> token.subject(user.username())
                .claim("acr", AuthenticationContextClass.MULTI_FACTOR)
                .claim("auth_time", Instant.now().minusSeconds(OLD_SIGN_IN_SECONDS).getEpochSecond()));

        for (final var token : List.<RequestPostProcessor>of(bearerOf(user), old)) {
            mockMvc.perform(delete(TOTP_PATH).with(token))
                    .andExpect(status().isUnauthorized())
                    .andExpect(header().string("WWW-Authenticate", STEP_UP_CHALLENGE))
                    .andExpect(jsonPath("$.type").value("urn:problem:mfa:insufficient-user-authentication"));
        }
        mockMvc.perform(post(RECOVERY_PATH).with(bearerOf(user)))
                .andExpect(status().isUnauthorized())
                .andExpect(header().string("WWW-Authenticate", STEP_UP_CHALLENGE));
        mockMvc.perform(delete(DEVICES_PATH + "/" + device).with(bearerOf(user)))
                .andExpect(status().isUnauthorized())
                .andExpect(header().string("WWW-Authenticate", STEP_UP_CHALLENGE));

        assertTrue(totpCredentials.findByUser(idOf(user)).orElseThrow().confirmed());
        assertEquals(1, trustedDevices.findByUser(idOf(user), Instant.now()).size());
    }

The post-processors are in Testing OAuth 2.0 with MockMvc.

A trusted device (TrustedDeviceIT). A full authorization flow, then a second sign-in on a browser with the cookie that skips the second factor, a step-up that asks for it again, and a revocation that restores it:

    /**
     * Verifies that the device is remembered by the cookie and skips the second factor of a sign-in, while the tokens
     * only report the password ({@code amr [pwd]}, password {@code acr}); that a request with {@code acr_values} for
     * the multi-factor class still renders the TOTP form on the trusted browser (no redirect loop) and, once the code
     * is posted, gets multi-factor tokens; and that the device is asked for the code again after it is revoked.
     *
     * @throws Exception if a request cannot be performed.
     */
    @Test
    void secondFactor_whenDeviceIsTrusted_isSkippedUntilTheDeviceIsRevoked() throws Exception {
        final var enrolled = getFixtures().createEnrolledUser(getTools());
        final var client = getFixtures().createMfaCodeClient();

        final var first = new MockHttpSession();
        signInForAuthorization(enrolled.user(), client, newVerifier(), Map.of(), first);
        final var remembered = postSecondFactor(first, getTools().codeNow(enrolled.id(), 0), false, true);
        final var cookie = remembered.getResponse().getCookie(TRUSTED_DEVICE_COOKIE);
        assertNotNull(cookie, "The device cookie must be written");
        assertTrue(cookie.isHttpOnly());
        assertTrue(cookie.getSecure());
        assertEquals(1, trustedDevices.findByUser(enrolled.id(), Instant.now()).size());

        final var second = new MockHttpSession();
        final var verifier = newVerifier();
        final var secondUri = signInForAuthorization(enrolled.user(), client, verifier, Map.of(), second);
        final var sessionId = second.getId();
        getMockMvc().perform(get(SECOND_FACTOR_PAGE).session(second).cookie(cookie)
                        .with(AbstractMfaFlow::sendsTheSessionCookie))
                .andExpect(status().is3xxRedirection());
        assertNotEquals(sessionId, second.getId(), "The session id must change when the device is recognised");
        final var trusted = AuthServerFixtures.claimsOf(
                completeAuthorization(secondUri, client, verifier, second).get("access_token").asString());
        assertEquals(List.of(PasswordFactor.AMR_VALUE), strings(trusted.get(AMR)));
        assertEquals(AuthenticationContextClass.PASSWORD, trusted.get(ACR).asString());

        final var stepUpVerifier = newVerifier();
        final var stepUpUri = AuthServerFixtures.authorizeUri(client, stepUpVerifier,
                Map.of("acr_values", AuthenticationContextClass.MULTI_FACTOR));
        expectSecondFactorPage(stepUpUri, second);
        getMockMvc().perform(get(SECOND_FACTOR_PAGE).session(second).cookie(cookie))
                .andExpect(status().isOk())
                .andExpect(content().string(containsString("name=\"code\"")));
        assertAccepted(postSecondFactor(second, getTools().codeNow(enrolled.id(), 1), false, false));
        final var stepped = AuthServerFixtures.claimsOf(
                completeAuthorization(stepUpUri, client, stepUpVerifier, second).get("access_token").asString());
        assertEquals(AuthenticationContextClass.MULTI_FACTOR, stepped.get(ACR).asString());

        final var device = trustedDevices.findByUser(enrolled.id(), Instant.now()).getFirst();
        assertTrue(trustedDevices.revoke(enrolled.id(), device.id()));

        final var third = new MockHttpSession();
        signInForAuthorization(enrolled.user(), client, newVerifier(), Map.of(), third);
        getMockMvc().perform(get(SECOND_FACTOR_PAGE).session(third).cookie(cookie)).andExpect(status().isOk());
    }

The flow helpers come from the abstract class AbstractMfaFlow, which walks the real login, second-factor and authorization pages with a MockHttpSession; see Testing Spring Boot Applications.

Enrolment during sign-in (MfaPasswordOnlyForcedIT). A user who must use a second factor but has none enrols an authenticator on the second-factor page, sees the recovery codes once and resumes the authorization request:

    /**
     * Verifies that a user who must use a second factor but has none enrols an authenticator app on the second-factor
     * page, sees the recovery codes exactly once and then resumes the authorization request, whose tokens report the
     * second factor.
     *
     * @throws Exception if a request cannot be performed.
     */
    @Test
    void secondFactor_whenUserMustEnrol_enrolsShowsTheRecoveryCodesOnceAndResumes() throws Exception {
        final var user = getFixtures().createUser();
        getFixtures().requireMfa(user, getTools());
        final var userId = userAccounts.findByUsername(user.username()).orElseThrow().id();
        final var client = getFixtures().createCodeClient();
        final var session = new MockHttpSession();
        final var verifier = newVerifier();
        final var authorizeUri = signInForAuthorization(user, client, verifier, Map.of(), session);
        expectSecondFactorPage(authorizeUri, session);

        final var page = secondFactorPage(session);
        assertTrue(page.contains(ENROL_FIELD) && page.contains("otpauth://totp/")
                && page.contains("src=\"data:image/png;base64,"), "The page must offer the enrolment");

        final var enrolled = postEnrolment(session, getTools().codeNow(userId, 0));
        assertEquals(RecoveryCodesPageController.RECOVERY_CODES_PATH, enrolled.getResponse().getRedirectedUrl());

        final var codesPage = getMockMvc().perform(get(RecoveryCodesPageController.RECOVERY_CODES_PATH)
                .session(session)).andExpect(status().isOk()).andReturn().getResponse().getContentAsString();
        assertEquals(GenerateRecoveryCodesUseCase.CODE_COUNT, recoveryCodes.findUnused(userId).size());
        assertEquals(GenerateRecoveryCodesUseCase.CODE_COUNT, codesPage.split("<li><code>", -1).length - 1);
        assertTrue(codesPage.contains("/oauth2/authorize?"), "The Continue link must resume the authorization");
        getMockMvc().perform(get(RecoveryCodesPageController.RECOVERY_CODES_PATH).session(session))
                .andExpect(status().isOk())
                .andExpect(content().string(not(containsString("<li><code>"))));

        final var tokens = completeAuthorization(authorizeUri, client, verifier, session);
        assertEquals(AuthenticationContextClass.MULTI_FACTOR,
                AuthServerFixtures.claimsOf(tokens.get("access_token").asString()).get(ACR).asString());
    }

These are written for the features of Multi-Factor Authentication & Step-Up, TOTP & Recovery Codes and Registered Clients, where each one is explained. The same mechanics, with no tag, are in AuthorizationCodePkceIT (the full code flow with PKCE), ReuseDetectingAuthorizationServiceIT (refresh-token rotation and reuse), OttEnumerationIT (the one-time-token flow cannot tell a known address from an unknown one), and the Jdbc*RepositoryIT classes, one for each repository, which run its SQL against the migrated schema.

End-to-end tests

The nine classes of the e2e-tests module start the packaged applications as separate processes (ManagedApp, RunningAuthServer, RunningResourceServer) against a PostgreSQL container and talk to them over HTTP. They are the only tests where a browser runs the JavaScript of the pages and a second JVM calls the API, so each one covers something the others cannot:

  • SignInSmokeIT signs in through the BFF in headless Chromium, driven by Playwright for Java.

  • PasskeyEndToEndIT gives the browser a virtual authenticator through the Chrome DevTools Protocol (CTAP2, internal transport, resident key, user verified), so the real WebAuthn ceremonies of the pages run: registration, sign-in with the button and sign-in with the autofill field.

  • OttEndToEndIT starts a Mailpit container, requests a code, reads the e-mail from the Mailpit HTTP API and types the code; another scenario follows the magic link, including a mail scanner fetching it first.

  • BffEndToEndIT, ResourceServerEndToEndIT, ClientCredentialsEndToEndIT, TokenExchangeEndToEndIT, DeviceFlowEndToEndIT and LegacyImplicitEndToEndIT run the BFF, the resource server, the service-client tool and the grants end to end.

None of them is a tagged region, so they are described here instead of shown. They are slow (they start processes and a browser), so they are few and each one tests a journey, not a rule: the rules are checked below them. See the Playwright for Java documentation for the browser side.

Testing tricks

Clocks and time travel

Time is a dependency here: a code expires in ten minutes, a key rotates every thirty days, a step-up is recent for a few minutes. The application takes a Clock bean (ClockConfiguration) wherever it needs the time, and the unit tests of those classes pass Clock.fixed(...) (see FactorGrantorTest, StepUpGuardTest, TrustedDeviceCookieWriterTest and PendingIdentityLinksTest), so every boundary is exact.

The integration tests use the real clock of the context and move the data instead of the clock:

  • Key rotation. KeyRotationIT forces a rotation through the administration API, then runs UPDATE signing_keys SET retired_at = now() - interval '2 days' on the retired key and rotates again, to prove that a key outside its retention is removed from the published set while a token it signed was still valid until then.

  • Old sign-ins. TotpApiIT (above) builds its token with an auth_time older than the step-up window instead of waiting for it.

  • TOTP steps. The fixtures of the MFA tests compute the code of a stored credential for the current step or for an offset of steps (codeNow(userId, 1) is the next code), with TotpTools in AuthServerFixtures, so a test never sleeps.

The OpenAPI contract as a test

The contracts under apis/ are the source of the REST APIs, and a test keeps the running application honest to them. OpenApiContract in test-support reduces a contract and the OpenAPI document that springdoc serves to a sorted summary (operation ids, tags, security, parameters, bodies, status codes and the properties of every schema) and compares them. OpenApiContractTest is the unit test of that comparator, and each application has an OpenApiDriftIT that fails with the exact difference when an endpoint is mapped by hand outside the generated interface, a contract operation has no controller, or a status code or schema differs. The contract of the account and administration API is on API Reference, Custom APIs.

Mailpit and the logging SMS sender

E-mail codes and magic links are tested against a real SMTP server that keeps what it receives. Mailpit and MailpitTestConfiguration start the container and point the application’s mail settings at it, and MailpitClient reads the messages from its HTTP API, so OttEmailCodeIT, OttMagicLinkIT and the end-to-end test read the code or the link exactly as a user would. For local development the same service is in the example’s compose.yaml:

  mailpit:
    image: axllent/mailpit
    ports:
      - "1025:1025" # SMTP
      - "8025:8025" # web UI

See the Mailpit documentation for the API and the web interface on port 8025.

SMS never leaves the machine in a test. The default SmsSender is LoggingSmsSender, which records the message in an in-memory SmsOutbox and logs only the masked recipient. The dev and test profiles select it, and the tests read the code back from the inbox (see OttSmsIT). SmsSenderProfilesIT proves that the test and dev profiles use it and that a gateway profile replaces it; MissingSmsGatewayConfigurationTest covers the refusal to start with no sender profile.

Generated certificates

No certificate, key or key store is committed. TestPki builds a small public key infrastructure at run time with the JDK’s keytool: a certificate authority and the server and client certificates it signs, in PKCS#12 key stores in a temporary directory that is deleted on close. TestCertificates generates single self-signed client certificates the same way. They back the mutual TLS tests (X509TlsLoginIT, ClientAuthenticationIT, BoundTokenIT) and the certificate tests (X509LoginIT, CertificateApiIT). Generating the material in the test also keeps the secret scanner quiet, and expiry tests can ask for a certificate that is already expired.

Test-only CI

The workflow .github/workflows/build.yml of the example runs on pushes to main, develop and release_* branches and on pull requests, and it only builds and tests: the example is never deployed, so no workflow releases or deploys anything. The job sets up JDK 21, restores the Maven and Playwright caches, runs ./mvnw -B -ntp clean verify (the build gates, the unit tests, the integration tests and the end-to-end tests, with Docker preinstalled on the runner for Testcontainers), runs the SonarCloud analysis only when a token exists, and always uploads the reports. This is the job:

  verify:
    runs-on: ubuntu-latest
    timeout-minutes: 45
    env:
      # empty on forks and on pull requests from forks: the Sonar step is skipped then
      SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
    steps:
      - uses: actions/checkout@v5
        with:
          # SonarCloud needs the full history to attribute new code and blame
          fetch-depth: 0

      - name: Set up JDK 21
        uses: actions/setup-java@v5
        with:
          distribution: temurin
          java-version: '21'
          cache: maven

      # The e2e-tests module drives headless Chromium through Playwright for Java, which downloads the browser on
      # first use; caching it keeps later runs offline for that step. Docker (preinstalled on ubuntu-latest) backs
      # the Testcontainers PostgreSQL.
      - name: Cache Playwright browsers
        uses: actions/cache@v4
        with:
          path: ~/.cache/ms-playwright
          key: playwright-${{ runner.os }}-${{ hashFiles('pom.xml') }}
          restore-keys: playwright-${{ runner.os }}-

      - name: Build, analyse and test
        run: ./mvnw -B -ntp clean verify

      - name: SonarCloud analysis
        if: env.SONAR_TOKEN != ''
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: ./mvnw -B -ntp sonar:sonar

      - name: Upload test and coverage reports
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: test-reports
          path: |
            **/target/surefire-reports/
            **/target/failsafe-reports/
            **/target/site/jacoco*/
            **/target/checkstyle-result.xml
            **/target/pmd.xml
            **/target/spotbugsXml.xml
          if-no-files-found: ignore
          retention-days: 14
