Authorization Server from Scratch: TOTP Authenticator Apps & Recovery Codes

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

What you build

This page adds the first second factor of the example: a time-based one-time password (TOTP) produced by an authenticator app, plus the recovery codes that stand in for it when the phone is lost. A user enrols the app once, either on the second-factor page during a sign-in or through the REST API, and from then on a code is asked after the password. The pieces are:

  • the enrolment: a random shared secret, stored encrypted, handed to the app as an otpauth:// URI and a QR code, and activated only when the first code from the app is accepted;

  • the verification: a six-digit code checked against a small window of time steps, with a step that can be used only once and a lockout after repeated failures;

  • ten recovery codes, shown once, stored hashed and each valid once;

  • the Spring Security wiring that turns an accepted code into a FACTOR_TOTP authority, which the token customizers later report as amr otp and acr, and the Thymeleaf forms that collect the codes.

The theory (what TOTP and HOTP are, why recovery is the weakest link) lives in the OAuth Reference sections backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_totp_hotp_authenticator_apps and backend/oauth/authentication-methods-2fa-and-passwordless.adoc#enrolment-and-account-recovery-the-weakest-link, and this page does not repeat it. How the factor is required (per user, per client, step-up, lockout counters and trusted devices) belongs to the Multi-Factor Authentication & Step-Up page of this guide; this page only shows where the TOTP code plugs into it.

The algorithm in two formulas

RFC 4226 (HOTP) computes a code from a shared secret K and a counter C, and RFC 6238 (TOTP) makes the counter the number of time steps since the Unix epoch. With the defaults that authenticator apps use (SHA1, 6 digits, a 30-second step), and writing T for the counter:

DT is the dynamic truncation of RFC 4226: the low four bits of the last of the 20 hash bytes choose an offset o, the four bytes from there are read as a big-endian integer, and the sign bit is cleared so the result is positive. Authenticator app and server run the same computation, which is why they agree without talking to each other, and why a code stays valid only while both clocks are within a step or two.

How it works

Enrolment

The example enrols on the second-factor page during a sign-in (the path below) and through POST /api/account/totp for a client that manages the account over the REST API. Both call the same EnrollTotpUseCase and ConfirmTotpUseCase, so the secret is generated and activated the same way.

sequenceDiagram autonumber actor U as User participant B as Browser participant P as GET /login/second-factor participant F as TotpAuthenticationFilter participant C as ConfirmTotpAtSignInUseCase participant DB as totp_credentials and recovery_codes U->>B: Signs in with the password B->>P: GET /login/second-factor P->>P: TotpSecondFactorFragment calls EnrollTotpUseCase P->>DB: Insert the secret encrypted, confirmed = false P-->>B: Page with the QR code and the otpauth URI U->>B: Scans it and types the first code B->>F: POST /login/second-factor/totp (code, enroll) F->>C: TotpCodeVerifier, ENROLMENT kind C->>DB: Check the code, advance last_used_step, confirmed = true C->>DB: Replace the recovery codes with ten new ones, hashed F->>F: PendingRecoveryCodes keeps the clear codes in the session F-->>B: 302 to /login/second-factor/recovery-codes B->>P: GET the codes page, shown once P-->>B: Ten recovery codes and a Continue link

The secret is never confirmed by the act of generating it: the row is created with confirmed = false, a second EnrollTotpUseCase call replaces a pending secret, and only a code computed from the secret proves that the user really stored it in an app. A page reload during enrolment therefore shows a new QR code, and the old one stops working.

Verification

flowchart TD IN["POST /login/second-factor/totp: code, kind"] --> K{"Kind of code"} K -- TOTP --> L{"Second factor locked?"} L -- yes --> LOCKED["SecondFactorLockedException, mapped to LockedException"] L -- no --> CRED["Load the confirmed credential and decrypt the secret"] CRED --> WIN["Compute the code for each step in the window, compare in constant time"] WIN --> NEW{"Matching step greater than last_used_step?"} NEW -- no --> FAIL["Register a failure: BadCredentialsException"] NEW -- yes --> ADV{"advanceLastUsedStep updates one row?"} ADV -- no --> FAIL ADV -- yes --> OK["Reset the failure counter, record SECOND_FACTOR_SUCCESS, grant FACTOR_TOTP"] K -- RECOVERY --> RC["Normalise the code, compare with each unused hashed code, markUsed"] RC --> OK K -- ENROLMENT --> ENR["Confirm the pending credential, see the enrolment diagram"] ENR --> OK FAIL --> LIM["After the configured number of failures the second factor locks for a period"]

Three defences sit in this path. The window accepts the previous, the current and the next 30-second step, which absorbs a phone clock that is up to about a step out. Replay protection stores the last accepted step per user and accepts only a strictly greater one, with the update done as a conditional UPDATE ... WHERE last_used_step < ? so two concurrent requests with the same code cannot both succeed. The lockout counts failures per user and, after the configured number (default 5), refuses even a correct code for the configured period (default 15 minutes); both are authserver.mfa properties, described on the Multi-Factor Authentication & Step-Up page.

Data

Flyway migration V410 adds two tables to the authserver database. Both reference users with ON DELETE CASCADE, so deleting an account removes its factor and its codes.

CREATE TABLE totp_credentials
(
    user_id           uuid                     NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    encrypted_secret  bytea                    NOT NULL,
    confirmed         boolean                  NOT NULL DEFAULT FALSE,
    last_used_step    bigint                   NOT NULL DEFAULT -1,
    created_at        timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (user_id)
);

CREATE TABLE recovery_codes
(
    id          uuid                     NOT NULL,
    user_id     uuid                     NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    hashed_code varchar(128)             NOT NULL,
    used_at     timestamp with time zone,
    created_at  timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id)
);

CREATE INDEX ix_recovery_codes_user_id ON recovery_codes (user_id);

This is plain Flyway SQL for the example’s own tables, not a Spring-defined schema; see the Spring Boot Flyway how-to.

Code

Authenticating the code

The filter below is the entry point of the second factor. It refuses a request with no signed-in primary authentication, wraps the code in a token that records whether it is an authenticator code, a recovery code or an enrolment confirmation (the enroll and recovery form fields), and calls the manager. After success it can also set the trusted-device cookie when the user ticked "Remember this device".

    /**
     * Builds the verification request from the form and the authentication the user already holds, and keeps in the
     * session the recovery codes an enrolment generates, until they are shown.
     *
     * @param request  the request.
     * @param response the response.
     * @return the authentication with the TOTP factor added.
     * @throws AuthenticationException if nobody is signed in or the code is not accepted.
     */
    @Override
    public Authentication attemptAuthentication(final HttpServletRequest request, final HttpServletResponse response)
            throws AuthenticationException {
        final var current = SecurityContextHolder.getContext().getAuthentication();
        if (current == null || !current.isAuthenticated() || current instanceof AnonymousAuthenticationToken) {
            throw new InsufficientAuthenticationException("The user has not signed in yet");
        }
        final var code = StringUtils.trimWhitespace(request.getParameter(CODE_PARAMETER));
        final var verification = new TotpAuthenticationToken(current, code == null ? "" : code, kindOf(request));
        final var verified = getAuthenticationManager().authenticate(verification);
        if (!verification.issuedRecoveryCodes().isEmpty()) {
            pendingRecoveryCodes.save(request, verification.issuedRecoveryCodes());
        }
        return verified;
    }

    /**
     * Remembers the device when the user asked for it, then saves the authentication and resumes the request.
     *
     * @param request    the request.
     * @param response   the response.
     * @param chain      the rest of the chain.
     * @param authResult the verified authentication.
     * @throws IOException      if the redirect cannot be sent.
     * @throws ServletException if the success handler fails.
     */
    @Override
    protected void successfulAuthentication(final HttpServletRequest request, final HttpServletResponse response,
            final FilterChain chain, final Authentication authResult) throws IOException, ServletException {
        if (request.getParameter(REMEMBER_PARAMETER) != null) {
            final var created = createTrustedDeviceUseCase.execute(userResolver.userIdOf(authResult.getName()),
                    authResult.getName(), userAgentSummary(request));
            cookieWriter.write(response, created);
        }
        super.successfulAuthentication(request, response, chain, authResult);
    }

This is an AbstractAuthenticationProcessingFilter, described in the Spring Security authentication architecture.

The provider maps each failure of the use cases to a Spring Security exception, so the filter’s failure handler treats a wrong code, a lockout and an enrolment that is not waiting in the same way: it redirects back with an error and reveals nothing else. On success it returns the same principal with an additional FACTOR_TOTP authority.

    /**
     * Verifies the code.
     *
     * @param authentication the {@link TotpAuthenticationToken} to verify.
     * @return the authentication the user already holds with the TOTP factor added.
     * @throws AuthenticationException if the code is wrong, the second factor is locked or the account is unknown.
     */
    @Override
    public Authentication authenticate(final Authentication authentication) throws AuthenticationException {
        final var request = (TotpAuthenticationToken) authentication;
        final var primary = request.primary();
        final var username = primary.getName();
        final var userId = userResolver.userIdOf(username);
        final boolean accepted;
        try {
            accepted = totpCodeVerifier.verify(request, userId, username);
        } catch (final SecondFactorLockedException e) {
            throw new LockedException("The second factor is locked", e);
        } catch (final TotpNotEnrolledException | TotpAlreadyEnabledException e) {
            throw new BadCredentialsException("No enrolment is waiting to be confirmed", e);
        }
        if (!accepted) {
            throw new BadCredentialsException("The code is not valid");
        }
        return factorGrantor.grant(primary, TotpFactor.AUTHORITY);
    }

An AuthenticationProvider answers supports for one token type and returns a fully authenticated Authentication.

The customizer registers the filter in the login chain, before AuthorizationFilter, and requires authentication on the second-factor paths. Its nested configurer copies the chain’s own SessionAuthenticationStrategy into the filter once the chain is built, so a session fixation defence configured on the chain also applies to the second factor:

    /**
     * Hands the session authentication strategy of the chain to the TOTP filter. The strategy is a shared object of
     * the chain that only exists once every configurer has been initialised (the CSRF configurer adds its
     * {@code CsrfAuthenticationStrategy} to the session management one), so it is read in {@link #configure}, as the
     * form login does for its own filter. Package-private so its test can drive it.
     */
    @RequiredArgsConstructor
    static final class SessionStrategyConfigurer
            extends AbstractHttpConfigurer<SessionStrategyConfigurer, HttpSecurity> {

        /** The filter that gets the strategy. */
        private final TotpAuthenticationFilter filter;

        /**
         * Sets the shared strategy, when the chain has one, on the filter.
         *
         * @param http security builder of the chain.
         */
        @Override
        public void configure(final HttpSecurity http) {
            final var strategy = http.getSharedObject(SessionAuthenticationStrategy.class);
            if (strategy != null) {
                filter.setSessionAuthenticationStrategy(strategy);
            }
        }
    }

The session management section of the reference explains the strategies.

Enrolment through the API

The controller implements the interface generated from the OpenAPI contract. enrollTotp creates the pending credential and answers the URI and a QR code as a data URI; confirmTotp checks the first code and answers the new recovery codes; disableTotp requires a recent multi-factor sign-in (see the security notes) before it removes the factor. Every response that carries a secret is sent with Cache-Control: no-store.

/**
 * Enrols, confirms and disables the authenticator app of the authenticated account. The paths, status codes and
 * bodies are those of the contract {@code apis/auth-server/rest-server/auth-server-api-v1.yaml}, through the
 * generated {@link TotpApi}; failures are answered by
 * {@link com.irurueta.authserver.authorization.api.web.mfa.MfaExceptionHandler}. Answers that carry a secret are
 * never cached. Disabling the app needs a recent multi-factor sign-in ({@link StepUpGuard}).
 */
@RestController
@RequiredArgsConstructor
public class TotpController implements TotpApi {

    /** Resolves the account of the request. */
    private final CurrentAccountResolver currentAccountResolver;

    /** Starts an enrolment. */
    private final EnrollTotpUseCase enrollTotpUseCase;

    /** Confirms an enrolment. */
    private final ConfirmTotpUseCase confirmTotpUseCase;

    /** Disables the authenticator app. */
    private final DisableTotpUseCase disableTotpUseCase;

    /** Requires a recent multi-factor sign-in before the second factor is removed. */
    private final StepUpGuard stepUpGuard;

    /** Renders the enrolment URI as a QR code. */
    private final QrCodeRenderer qrCodeRenderer;

    /** Maps the results onto the contract's DTOs. */
    private final TotpDtoMapper totpDtoMapper;

    /**
     * Starts the enrolment of an authenticator app.
     *
     * @return {@code 200 OK} with the {@code otpauth} URI and its QR code.
     */
    @Override
    public ResponseEntity<TotpEnrollmentResponse> enrollTotp() {
        final var account = currentAccountResolver.resolve();
        final var uri = enrollTotpUseCase.execute(account.id(), account.username());
        return noStore(totpDtoMapper.toEnrollmentResponse(uri, qrCodeRenderer.render(uri)));
    }

    /**
     * Confirms the enrolment with a code from the authenticator app.
     *
     * @param request the code.
     * @return {@code 200 OK} with the recovery codes, shown only once.
     */
    @Override
    public ResponseEntity<RecoveryCodesResponse> confirmTotp(final ConfirmTotpRequest request) {
        final var account = currentAccountResolver.resolve();
        return noStore(totpDtoMapper.toRecoveryCodesResponse(
                confirmTotpUseCase.execute(account.id(), request.code())));
    }

    /**
     * Disables the authenticator app, removes the recovery codes and revokes the trusted devices.
     *
     * @return {@code 204 No Content}.
     * @throws com.irurueta.authserver.authorization.api.web.mfa.InsufficientUserAuthenticationException if the token
     *         does not show a recent multi-factor sign-in.
     */
    @Override
    public ResponseEntity<Void> disableTotp() {
        final var account = currentAccountResolver.resolve();
        stepUpGuard.requireRecentMultiFactor(account.id());
        disableTotpUseCase.execute(account.id(), account.username());
        return ResponseEntity.noContent().build();
    }

    /**
     * Answers a body that carries a secret, which must not be cached.
     *
     * @param body the body.
     * @param <T>  type of the body.
     * @return {@code 200 OK} with {@code Cache-Control: no-store}.
     */
    private static <T> ResponseEntity<T> noStore(final T body) {
        return ResponseEntity.ok().cacheControl(CacheControl.noStore()).body(body);
    }
}

A @RestController that implements a generated API interface is standard Spring MVC; see the Spring MVC controllers reference.

Enrolment during sign-in

When the user enrols on the second-factor page, the first code is confirmed by this use case. It is the same ConfirmTotpUseCase as the API, wrapped in the lockout check and the failure counter, so an attacker cannot use the enrolment form to guess codes without limit:

    /**
     * Confirms the enrolment with the first code of the authenticator app.
     *
     * @param userId   identifier of the user.
     * @param username name of the user, for the audit log.
     * @param code     the code as typed.
     * @return the clear-text recovery codes, to be shown once; empty when the code is wrong (the failure is counted).
     * @throws SecondFactorLockedException if the second factor of the user is locked.
     * @throws com.irurueta.authserver.authorization.domain.totp.TotpNotEnrolledException    if no enrolment was
     *                                                                                      started.
     * @throws com.irurueta.authserver.authorization.domain.totp.TotpAlreadyEnabledException if the enrolment was
     *                                                                                      already confirmed.
     */
    public Optional<List<String>> execute(final UUID userId, final String username, final String code) {
        if (checkSecondFactorLockoutUseCase.execute(userId)) {
            throw new SecondFactorLockedException("The second factor is locked after too many failed attempts");
        }
        final var recoveryCodes = confirmTotpUseCase.tryConfirm(userId, code);
        if (recoveryCodes.isPresent()) {
            resetSecondFactorFailuresUseCase.execute(userId);
            recordSecurityEventUseCase.execute(SecurityEventType.SECOND_FACTOR_SUCCESS, userId, username,
                    "totp enrolment");
        } else {
            registerSecondFactorFailureUseCase.execute(userId, username);
        }
        return recoveryCodes;
    }

Its Spring part is only @Service and @Transactional; see the @Transactional reference.

Disabling the factor

Disabling deletes the credential, the recovery codes and every trusted device of the user in one transaction and records a SECOND_FACTOR_REMOVED security event. Deleting the trusted devices matters: a "remember this device" token issued under the factor must not outlive it.

/**
 * Use case that removes the authenticator app of a user together with the recovery codes that went with it. Every
 * trusted device of the user is revoked as well, since a device trusted to skip a second factor must not outlive it,
 * and the removal is audited.
 */
@Service
@Transactional
@RequiredArgsConstructor
public class DisableTotpUseCase {

    /** Port that stores the TOTP credentials. */
    private final TotpCredentialRepository totpCredentialRepository;

    /** Port that stores the recovery codes. */
    private final RecoveryCodeRepository recoveryCodeRepository;

    /** Port that stores the trusted devices. */
    private final TrustedDeviceRepository trustedDeviceRepository;

    /** Use case that records the audit events. */
    private final RecordSecurityEventUseCase recordSecurityEventUseCase;

    /**
     * Disables TOTP.
     *
     * @param userId   identifier of the user.
     * @param username name of the user, for the audit log.
     */
    public void execute(final UUID userId, final String username) {
        totpCredentialRepository.deleteByUser(userId);
        recoveryCodeRepository.deleteByUser(userId);
        final var revoked = trustedDeviceRepository.deleteByUser(userId);
        recordSecurityEventUseCase.execute(SecurityEventType.SECOND_FACTOR_REMOVED, userId, username,
                "totp; trusted devices revoked: " + revoked);
    }
}

This is a transactional application service, as in the Spring transaction reference.

Secrets at rest

A TOTP secret has to be recoverable, because the server needs the clear bytes to compute the expected code, so it is encrypted, not hashed. The example encrypts it with Spring Security Crypto’s Encryptors.stronger, from a passphrase and a salt. The signing keys use the configured salt directly (that cipher is the listing below, which the Signing Keys, JWS & JWT page explains in full); the TOTP cipher, AesGcmTotpSecretCipher, is built the same way but takes a salt derived for the purpose totp-secret from the same configuration, so a single configured passphrase yields different keys for the secrets and for the signing keys. This page does not repeat the mechanism.

/**
 * Encrypts and decrypts the private half of signing keys with AES-256-GCM (Spring Security's
 * {@code Encryptors.stronger}). Every encryption uses a fresh random initialisation vector, so encrypting the same
 * text twice gives different results.
 */
@Component
public class AesGcmKeyCipher {

    /** The encryptor derived from the passphrase and the salt. */
    private final BytesEncryptor encryptor;

    /**
     * Derives the encryption key.
     *
     * @param properties passphrase and salt.
     */
    public AesGcmKeyCipher(final KeyEncryptionProperties properties) {
        encryptor = Encryptors.stronger(properties.password(), properties.salt());
    }

    /**
     * Encrypts a text.
     *
     * @param plain the text.
     * @return the encrypted text, Base64 encoded.
     */
    public String encrypt(final String plain) {
        return Base64.getEncoder().encodeToString(encryptor.encrypt(plain.getBytes(StandardCharsets.UTF_8)));
    }

    /**
     * Decrypts a text produced by {@link #encrypt(String)}.
     *
     * @param encrypted the encrypted text.
     * @return the original text.
     * @throws IllegalStateException if the text was not encrypted with the same passphrase and salt, or was altered.
     */
    public String decrypt(final String encrypted) {
        try {
            return new String(encryptor.decrypt(Base64.getDecoder().decode(encrypted)), StandardCharsets.UTF_8);
        } catch (final RuntimeException e) {
            throw new IllegalStateException("The private key cannot be decrypted", e);
        }
    }
}

See Spring Security Crypto and the BytesEncryptor Javadoc.

The second-factor page

TotpSecondFactorFragment is one of the fragments that the second-factor page assembles from the available factors (order 100). It exposes model attributes only: whether TOTP is offered, whether the user is enrolling (and then the URI and the QR code) or verifying (and then how many recovery codes are left, and whether that is a low number).

/**
 * Contributes the TOTP forms to the second-factor page, as every second factor does through the
 * {@link SecondFactorFragment} extension point. What the fragment shows depends on the signed-in user:
 *
 * <ul>
 *   <li>without a confirmed authenticator app but with another confirmed second factor (for example a passkey),
 *       nothing: that factor completes the sign-in, so no secret is generated and no enrolment is offered;</li>
 *   <li>without any confirmed second factor, the enrolment form: a new secret is generated (replacing any pending
 *       one), shown as a QR code and as its {@code otpauth} URI, and the first code confirms it;</li>
 *   <li>with one, the form of its code and the recovery-code form, plus a warning when
 *       {@value CountRecoveryCodesUseCase#LOW_THRESHOLD} or fewer recovery codes are left.</li>
 * </ul>
 */
@Component
@RequiredArgsConstructor
public class TotpSecondFactorFragment implements SecondFactorFragment {

    /** Position of the TOTP forms in the second-factor page. */
    public static final int ORDER = 100;

    /** Model attribute telling the fragment to show anything at all. */
    public static final String OFFERED_ATTRIBUTE = "totpOffered";

    /** Model attribute telling the fragment to show the enrolment form. */
    public static final String ENROLMENT_ATTRIBUTE = "totpEnrolment";

    /** Model attribute with the {@code otpauth} URI of the enrolment. */
    public static final String OTPAUTH_URI_ATTRIBUTE = "totpOtpauthUri";

    /** Model attribute with the QR code of the enrolment, as a {@code data:} URI. */
    public static final String QR_CODE_ATTRIBUTE = "totpQrCode";

    /** Model attribute with the number of unused recovery codes. */
    public static final String CODES_LEFT_ATTRIBUTE = "totpRecoveryCodesLeft";

    /** Model attribute telling the fragment to warn that few recovery codes are left. */
    public static final String CODES_LOW_ATTRIBUTE = "totpRecoveryCodesLow";

    /** Resolves the identifier of the account of the signed-in user. */
    private final SecondFactorUserResolver userResolver;

    /** Tells whether the user has a confirmed authenticator app. */
    private final IsTotpEnabledUseCase isTotpEnabledUseCase;

    /** Tells whether the user has confirmed another second factor. */
    private final HasConfirmedSecondFactorUseCase hasConfirmedSecondFactorUseCase;

    /** Starts an enrolment. */
    private final EnrollTotpUseCase enrollTotpUseCase;

    /** Counts the unused recovery codes. */
    private final CountRecoveryCodesUseCase countRecoveryCodesUseCase;

    /** Renders the enrolment URI as a QR code. */
    private final QrCodeRenderer qrCodeRenderer;

    @Override
    public String templateName() {
        return "totp";
    }

    @Override
    public String fragmentName() {
        return "form";
    }

    @Override
    public int order() {
        return ORDER;
    }

    /**
     * Supplies the enrolment (a new pending secret) to a user without any confirmed second factor, the number of
     * recovery codes left to a user with a confirmed authenticator app, and hides the forms from a user whose only
     * confirmed second factors are other ones.
     *
     * @param authentication the authentication of the user the page is rendered for.
     * @return the model attributes; none when nobody is signed in.
     */
    @Override
    public Map<String, Object> modelAttributes(final Authentication authentication) {
        if (!MfaAuthorizationManager.isUser(authentication)) {
            return Map.of();
        }
        final var username = authentication.getName();
        final var userId = userResolver.userIdOf(username);
        if (!isTotpEnabledUseCase.execute(userId)) {
            if (hasConfirmedSecondFactorUseCase.execute(userId)) {
                return Map.of(OFFERED_ATTRIBUTE, false);
            }
            final var otpauthUri = enrollTotpUseCase.execute(userId, username);
            return Map.of(OFFERED_ATTRIBUTE, true, ENROLMENT_ATTRIBUTE, true, OTPAUTH_URI_ATTRIBUTE, otpauthUri,
                    QR_CODE_ATTRIBUTE, qrCodeRenderer.render(otpauthUri));
        }
        final var left = countRecoveryCodesUseCase.execute(userId);
        return Map.of(OFFERED_ATTRIBUTE, true, ENROLMENT_ATTRIBUTE, false, CODES_LEFT_ATTRIBUTE, left,
                CODES_LOW_ATTRIBUTE, left <= CountRecoveryCodesUseCase.LOW_THRESHOLD);
    }
}

Showing the recovery codes once

After an enrolment during sign-in the success handler redirects to /login/second-factor/recovery-codes. The clear codes travelled there in the HTTP session (PendingRecoveryCodes), and the controller takes them out of the session as it renders, so a reload shows none:

/**
 * Serves the page that shows, once, the recovery codes generated when an authenticator app was enrolled during the
 * sign-in, as the contract {@code apis/auth-server/web-pages/auth-server-pages-v1.yaml} describes it through the
 * generated {@link RecoveryCodesPageApi}. The codes are taken out of the session as the page is rendered, so a reload
 * shows none; its "Continue" button resumes the request the sign-in interrupted (kept by the session request cache),
 * or goes to the root when there is none.
 */
@Controller
@RequiredArgsConstructor
public class RecoveryCodesPageController implements RecoveryCodesPageApi {

    /** Path of the page, taken from the contract. */
    public static final String RECOVERY_CODES_PATH = PATH_RECOVERY_CODES_PAGE;

    /** Name of the template. */
    static final String VIEW_NAME = "recovery-codes";

    /** Name of the model attribute that holds the codes. */
    static final String CODES_ATTRIBUTE = "recoveryCodes";

    /** Name of the model attribute that holds where the "Continue" button goes. */
    static final String CONTINUE_ATTRIBUTE = "continueUrl";

    /** Where the "Continue" button goes when no request is waiting to be resumed. */
    static final String DEFAULT_CONTINUE_URL = "/";

    /** Cache that keeps the interrupted request, shared with the form login and the second-factor entry point. */
    private final RequestCache requestCache = new HttpSessionRequestCache();

    /** Keeps the codes waiting to be shown. */
    private final PendingRecoveryCodes pendingRecoveryCodes;

    /** Renders the page. */
    private final PageRenderer pageRenderer;

    /** The current request, injected as a thread-bound proxy. */
    private final HttpServletRequest request;

    /** The current response, injected as a thread-bound proxy. */
    private final HttpServletResponse response;

    /**
     * Renders the page and forgets the codes.
     *
     * @return the recovery codes page.
     */
    @Override
    public ResponseEntity<String> recoveryCodesPage() {
        final var codes = pendingRecoveryCodes.take(request);
        final var saved = requestCache.getRequest(request, response);
        return pageRenderer.render(VIEW_NAME, Map.of(CODES_ATTRIBUTE, codes,
                CONTINUE_ATTRIBUTE, saved == null ? DEFAULT_CONTINUE_URL : saved.getRedirectUrl()));
    }
}

The Continue link is the saved request (typically the interrupted /oauth2/authorize), read from an HttpSessionRequestCache, or the root when there is none.

The schemas follow the OpenAPI 3.1 Schema Object rules.

Start the enrolment; the answer carries otpauthUri and qrCode:

curl -s -X POST http://localhost:9000/api/account/totp \
  -H "Authorization: Bearer ${TOKEN}"

Confirm it with the code that the app shows (code is exactly six digits); the answer carries the ten recoveryCodes and remaining, shown only this once:

curl -s -X POST http://localhost:9000/api/account/totp/confirm \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"code":"123456"}'

Replace the whole set of recovery codes (needs a confirmed factor and a recent multi-factor sign-in):

curl -s -X POST http://localhost:9000/api/account/recovery-codes \
  -H "Authorization: Bearer ${TOKEN}"

Disable the factor. The answer is 204, also when nothing was enabled:

curl -s -X DELETE http://localhost:9000/api/account/totp \
  -H "Authorization: Bearer ${TOKEN}"

Tests

The example covers this feature at three levels, which are described here in prose because only one of them is tagged for inclusion:

  • Unit tests of each class: the RFC 6238 algorithm and its window, the Base32 and otpauth:// builders, the secret generator, the cipher, the use cases (including the lockout and replay paths), the filter, the provider and the controllers.

  • Integration tests of the sign-in: TotpLoginIT checks that a right code issues tokens carrying the amr and acr of the second factor, that a user who enrolled is forced through the second factor even when the client does not require it, and that a wrong code is redirected back with an error; RecoveryCodeIT checks that a recovery code works once and only once, that it is refused when no second factor is confirmed, and that the page warns when few codes are left.

  • Integration tests of the API: TotpApiIT covers enrolment, confirmation, conflicts, malformed codes, the effect of disabling on the caller’s trusted devices only, and the step-up challenge. The region below is shared with the Multi-Factor Authentication & Step-Up page: a password-only token and an old multi-factor token are both answered with 401 and the RFC 9470 challenge, and nothing is removed.

    /**
     * Verifies that removing or resetting the second factor of an account that has one needs a recent multi-factor
     * sign-in: a password-only token and an old multi-factor one are answered with {@code 401} and the RFC 9470
     * challenge, and nothing is removed.
     *
     * @throws Exception if a request cannot be performed.
     */
    @Test

Security notes and pitfalls

  • Clock drift. The window is one step each side (about 30 seconds) of the current step. A wider window helps users with bad phone clocks but multiplies the codes an attacker may guess in one attempt, so the example keeps it at one step and relies on the lockout for the rest. Keep the server on NTP.

  • Code reuse. A valid code is a bearer secret for up to about 90 seconds. RFC 6238 requires a verifier to accept each code once; the example stores the last accepted step and updates it with a conditional UPDATE, so a code observed by someone shoulder-surfing or phishing the form cannot be replayed within its window (it does not stop a real-time phishing proxy, which uses the code immediately; only a phishing-resistant factor such as a passkey does).

  • Brute force. Six digits are one million possibilities. The lockout, counted per user in a separate table and enforced before the code is looked at, is what makes that safe; rate limiting by address in front of the endpoint is a useful second layer.

  • Secret storage. Encrypt the secret, never log it and never return it after enrolment. The otpauthUri and qrCode fields are marked as secrets in the contract and sent with Cache-Control: no-store. The key that protects the secrets belongs in a secret store, not in the repository; losing it makes every enrolment unusable.

  • Recovery codes. They are random (ten characters from a Crockford-style alphabet without look-alike letters), hashed like a password, single use through the used_at guard, and replaced as a set, so regenerating invalidates the old ones. Typed codes are normalised (case, dashes, spaces and look-alike characters) before comparison. Show them once, ask the user to store them offline, and warn when few are left, as the page does.

  • Step-up to change the factor. Disabling the app or regenerating codes through the API requires a token that shows a recent multi-factor sign-in (acr and auth_time, five minutes by default), otherwise a stolen password-only session could remove the second factor. Disabling also revokes the trusted devices.

  • The account-recovery weakest link. Recovery codes, a support desk and an e-mail reset are all ways around the factor, so the strength of the account is that of the weakest of them: a reset by e-mail that bypasses the app turns the second factor into decoration. The OAuth Reference discusses the trade-offs in backend/oauth/authentication-methods-2fa-and-passwordless.adoc#enrolment-and-account-recovery-the-weakest-link.

  • Pending enrolment. An unconfirmed credential is not a factor: verification and recovery codes ignore it. It can, however, be replaced by a reload of the second-factor page, which is why the QR code is not cached.

For the full reference on TOTP see RFC 6238, RFC 4226 and RFC 9470 for the step-up challenge; the otpauth:// format is described in the Key URI Format of Google Authenticator, and the OWASP Multifactor Authentication Cheat Sheet and NIST SP 800-63B-4 cover the policy side.
