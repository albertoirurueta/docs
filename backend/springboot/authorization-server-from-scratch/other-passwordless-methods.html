Authorization Server from Scratch: Other Passwordless Methods

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

What you build

The earlier pages of this guide cover the password, passkeys, one-time codes and social login. This page adds three methods that do not fit those pages, each with its own short treatment:

  • X.509 client-certificate login: a user whose browser or smart card holds a certificate signs in with it. The certificate reaches the server either through a dedicated TLS port that asks for it, or in a header forwarded by a reverse proxy that terminated TLS. A certificate is bound to an account by its SHA-256 fingerprint.

  • The device authorization grant (RFC 8628): a television, a command-line tool or any device without a usable keyboard shows a short code, and the user approves it on a phone or a laptop, where signing in is easy.

  • Push approval with number matching: a design only. The example does not implement it.

Push approval is not implemented in the example. Its section below is a design sketch, written so that the method could be added through the same extension points as the other factors. There is no code for it, here or in the example repository.

The theory lives in the OAuth Reference: certificate and smart-card authentication, push approval, the device authorization grant and, for the Spring side of the grant, Spring Boot flow recipes (see its device-code section). This page does not repeat them. How a factor is required (per user, per client, step-up) is the subject of the Multi-Factor Authentication & Step-Up page of this guide.

How it works

X.509 client-certificate login

The login page shows a button only while authserver.x509.enabled is true. It posts, with the CSRF token, to POST /login/x509. In front of that request sits one of two transports, both off by default.

sequenceDiagram autonumber actor U as User participant B as Browser participant T as TLS port or trusted proxy participant FF as ForwardedCertificateFilter participant X as X509LoginFilter participant E as CertificatePrincipalExtractor participant S as X509UserDetailsService participant H as X509AuthenticationSuccessHandler U->>B: Presses Use my certificate B->>T: POST /login/x509 with the CSRF token, TLS handshake with the client certificate alt Dedicated TLS port T->>X: Container leaves the certificate in the jakarta.servlet.request.X509Certificate attribute else Reverse proxy T->>FF: Request with the certificate header, from a trusted address FF->>X: Parses the header and sets the same request attribute end X->>E: extractPrincipal(certificate) E-->>X: SHA-256 fingerprint, or an empty principal when expired X->>S: loadUserDetails(fingerprint) S->>S: Resolve the binding in x509_certificates, load the account S-->>X: UserDetails, or UsernameNotFoundException X->>H: Authentication succeeded H->>H: Replace the pre-authenticated token, grant FACTOR_X509, change the session id H-->>B: 302 to the interrupted request, for example /oauth2/authorize

The same filter and the same extractor serve both transports, because both leave the certificate where a servlet container leaves one. Three decisions matter:

  • The fingerprint, not the subject, identifies the certificate. Whoever controls a certificate authority can issue a certificate with any subject name, and none with a given fingerprint. The principal is the SHA-256 digest of the DER form, and the account is found by a lookup in the bindings table.

  • The server does not validate the chain on the dedicated port. The connector asks for a certificate without requiring or validating one (optionalNoCA): the handshake proves that the client holds the private key, and the binding proves that this particular certificate was registered by the account’s owner. Validity dates are still checked, by the extractor.

  • The certificate is a strong primary factor. The factor reports the sc (smart card) value of amr by default, or hwk when the deployment says that its keys are bound to hardware, and satisfies the multi-factor policy on its own.

The device authorization grant

The grant is defined by RFC 8628. The device never sees the user’s credentials: it gets two codes, shows one of them, and polls for the result while the user signs in elsewhere.

sequenceDiagram autonumber participant D as Device or CLI participant AS as Authorization server actor U as User participant B as Browser on another device D->>AS: POST /oauth2/device_authorization (client_id) AS-->>D: device_code, user_code, verification_uri, expires_in, interval D->>U: Shows the user code and the verification URI loop Every interval seconds D->>AS: POST /oauth2/token (grant_type device_code, device_code, client_id) AS-->>D: authorization_pending (or slow_down) end U->>B: Opens the verification URI B->>AS: GET /oauth2/device_verification AS-->>B: Sign-in if needed, then the page with the code form U->>B: Types the user code B->>AS: POST /oauth2/device_verification (user_code, CSRF token) AS->>AS: Guard counts the attempt and applies the multi-factor policy AS-->>B: 302 to /oauth2/consent U->>B: Approves the scopes B->>AS: POST /oauth2/device_verification (consent decision) AS-->>B: 302 to /oauth2/device_verification?success D->>AS: POST /oauth2/token (grant_type device_code, device_code, client_id) AS-->>D: access_token, refresh_token

The example changes four things around the framework’s defaults. The device is a public client that cannot keep a secret and, unlike a browser app, has no PKCE verifier, so the example gives it its own client authentication, by client_id alone. The verification endpoint is guarded before the framework’s converters run: every request that carries a user code is counted against a limit per address and per user, and the multi-factor policy of the account and of the client is applied (the client is the one that the stored authorization names for the typed code, so a client that requires a second factor is enforced even if it skips consent). The user consents on the same consent page as the authorization code flow. And the verification page is an ordinary Thymeleaf page rendered by a controller that implements the generated pages interface.

Push approval with number matching (design)

A push approval asks an already enrolled phone to approve a sign-in. Plain approve or deny prompts are easy to abuse: an attacker who knows a password can trigger prompts until a tired user taps Approve (MFA fatigue or prompt bombing). Number matching removes that: the sign-in page shows a number, the phone shows several candidates, and the user must pick the one on the screen, which proves that the person holding the phone is looking at the sign-in being approved.

sequenceDiagram autonumber actor U as User participant W as Sign-in page participant AS as Authorization server participant P as Push provider, APNs or FCM participant A as Phone app with an enrolled device key U->>W: Starts a sign-in W->>AS: Create a challenge for this session and authorization request AS-->>W: Shows a two-digit number, waits for the approval AS->>P: Notification carrying only an opaque challenge id P->>A: Delivers the notification A->>AS: Fetch the challenge context AS-->>A: Application name, scopes, three candidate numbers U->>A: Picks the number shown on the sign-in page, or denies A->>AS: Response signed with the device key over challenge, number, client, scope and expiry AS->>AS: Verify the signature with the enrolled public key, consume the challenge AS-->>W: Approved, the page continues the authorization

The design, in the terms of the extension points that the example already uses for the other factors:

  • Enrolment. A device key pair is created on the phone, the private key stays in the secure enclave or keystore, and the public key is stored for the account. Enrolling needs a recent multi-factor sign-in, as binding a certificate or a passkey does.

  • Registration in the framework. A second factor with its own authority and an amr value, a fragment of the second-factor page that says "waiting for approval", a query that says that a user with an enrolled device must use it, and an AuthenticationProvider that reuses the shared lockout and security-event machinery.

  • Challenge. Each attempt creates a single-use challenge bound to the session and to the pending authorization request, with a lifetime of about 60 seconds, a small cap of pending challenges per user and a rate limit. The page polls or listens for the result and falls back to another factor on expiry.

  • No secret in the push. The notification carries only a challenge id. The approval is a signature, so a stolen notification cannot approve anything.

  • Relation to the device grant. The two are unrelated approvals. A device-grant verification already runs the multi-factor policy, so a user whose second factor is a push approval would approve it while signing in on the verification page; the consent screen of the device flow stays a plain click.

  • Relation to step-up. An approved push is a second factor, so it would produce amr and satisfy the step-up check of RFC 9470 as the other factors do; a sensitive operation sends the user to a fresh challenge.

Risks to review before building it: device loss (recovery through other factors or recovery codes, and revoking the device), notification availability (an offline fallback), and the push provider as a third party (hence the opaque payload).

Data

Only X.509 adds a table. The device grant stores its codes in the oauth2_authorization columns that the authorization server’s schema already has, and needs no migration.

-- One row per client certificate bound to a user. The certificate is recognised by the SHA-256 fingerprint of its DER
-- encoding (lower case hexadecimal), which is unique: one certificate belongs to one account. The subject DN is kept
-- only to tell the bindings apart.
CREATE TABLE x509_certificates
(
    id                 uuid                     NOT NULL,
    user_id            uuid                     NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    fingerprint_sha256 char(64)                 NOT NULL,
    subject_dn         varchar(1000)            NOT NULL,
    created_at         timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    CONSTRAINT uq_x509_certificates_fingerprint UNIQUE (fingerprint_sha256),
    CONSTRAINT ck_x509_certificates_fingerprint_shape CHECK (fingerprint_sha256 ~ '^[0-9a-f]{64}$')
);

CREATE INDEX ix_x509_certificates_user_id ON x509_certificates (user_id);

X.509: configuration and properties

Everything is off unless authserver.x509.enabled is true. The comments in the listing explain how the two transports and the server.forward-headers-strategy setting interact.

  x509:
    # Sign in with a client certificate, off unless enabled is true: the login page shows a button that posts to
    # POST /login/x509 with the CSRF token (a GET of that path never signs in). A certificate is bound to an account by
    # its SHA-256 fingerprint. Two transports, both off by default: a certificate a trusted reverse proxy forwards in a
    # header (forwarded-header, honoured only for a request that comes from one of trusted-proxies, addresses or CIDR
    # ranges), and a dedicated TLS port that requests a client certificate (port, with the server certificate in
    # key-store; the password comes from the environment, AUTHSERVER_X509_KEY_STORE_PASSWORD). With only the TLS port the
    # button posts to that port of the same host, so the main port must be https too (SameSite cookies are not sent
    # from an http page to an https one) or the login page must be opened on the TLS port.
    # trusted-proxies is compared with the client address the server sees after Spring Boot's handling of the forwarded
    # headers, which is the direct network peer only with server.forward-headers-strategy: none; native and framework
    # replace it with a value from X-Forwarded-For, which a client can forge, so the server refuses to start with a
    # forwarded-header and any strategy but none (also when the strategy is unset on a detected cloud platform, where
    # it defaults to native). Under the dev profile a self-signed server certificate is generated at the first start
    # under ~/.irurueta-auth-server/. amr is the value the tokens report: sc (smart card) or hwk (a key held in
    # hardware).
    enabled: ${AUTHSERVER_X509_ENABLED:false}
    forwarded-header: ${AUTHSERVER_X509_FORWARDED_HEADER:}
    trusted-proxies: ${AUTHSERVER_X509_TRUSTED_PROXIES:}
    port: ${AUTHSERVER_X509_PORT:0}
    key-store: ${AUTHSERVER_X509_KEY_STORE:}
    amr: ${AUTHSERVER_X509_AMR:sc}

The properties are a validated record. It rejects a forwarded header with no trusted proxy, and an amr value that is not sc or hwk.

/**
 * Configuration of the sign-in with a client certificate ({@code authserver.x509.*}). It is off by default.
 *
 * @param enabled           whether the sign-in with a client certificate exists at all (default {@code false}).
 * @param forwardedHeader   name of the request header in which a trusted reverse proxy forwards the client certificate
 *                          it verified (PEM, URL-encoded as {@code $ssl_client_escaped_cert} of nginx does, or the
 *                          base64 of the DER form); empty (the default) turns the forwarded transport off.
 * @param trustedProxies    addresses or CIDR ranges of the proxies that may forward a certificate; required when the
 *                          header is set, and a request from any other address never has its header read.
 * @param port              port of the dedicated TLS connector that requests a client certificate; {@code 0} (the
 *                          default) turns the direct transport off.
 * @param amr               RFC 8176 {@code amr} value the factor reports: {@code sc} (smart card, the default) or
 *                          {@code hwk} (a hardware-bound key).
 * @param keyStore          path of the key store with the server certificate of the dedicated port; with the
 *                          {@code dev} profile and none configured, a self-signed one is generated at the first start
 *                          under {@code ~/.irurueta-auth-server/}.
 * @param keyStorePassword  password of the key store (and of its key), from the environment, never from a file.
 * @param keyStoreType      type of the key store (default {@code PKCS12}).
 */
@ConfigurationProperties(prefix = "authserver.x509")
public record X509Properties(
        @DefaultValue("false") boolean enabled,
        @DefaultValue("") String forwardedHeader,
        @DefaultValue List<String> trustedProxies,
        @DefaultValue("0") int port,
        @DefaultValue("sc") String amr,
        @DefaultValue("") String keyStore,
        @DefaultValue("") String keyStorePassword,
        @DefaultValue("PKCS12") String keyStoreType) {

    /** {@code amr} value of a smart card. */
    public static final String AMR_SMART_CARD = "sc";

    /** {@code amr} value of a key held in hardware. */
    public static final String AMR_HARDWARE_KEY = "hwk";

    /** Highest TCP port. */
    private static final int MAX_PORT = 65_535;

    /**
     * Validates the configuration and copies the list.
     *
     * @throws IllegalArgumentException if the port is out of range, the {@code amr} value is not {@code sc} or
     *                                  {@code hwk}, a trusted proxy is not an address or a range, or a forwarded
     *                                  header is set without any trusted proxy.
     */
    public X509Properties {
        trustedProxies = List.copyOf(trustedProxies);
        if (port < 0 || port > MAX_PORT) {
            throw new IllegalArgumentException("port must be between 0 and " + MAX_PORT);
        }
        if (!AMR_SMART_CARD.equals(amr) && !AMR_HARDWARE_KEY.equals(amr)) {
            throw new IllegalArgumentException("amr must be " + AMR_SMART_CARD + " or " + AMR_HARDWARE_KEY);
        }
        trustedProxies.forEach(IpAddressMatcher::new);
        if (StringUtils.hasText(forwardedHeader) && trustedProxies.isEmpty()) {
            throw new IllegalArgumentException("a forwarded header needs at least one trusted proxy");
        }
    }

    /**
     * Tells whether the certificate may arrive in a header.
     *
     * @return {@code true} when a header name is configured.
     */
    public boolean forwardedEnabled() {
        return StringUtils.hasText(forwardedHeader);
    }

    /**
     * Tells whether the dedicated TLS connector is requested.
     *
     * @return {@code true} when a port is configured.
     */
    public boolean tlsEnabled() {
        return port > 0;
    }
}

X.509: the filter chain

The customizer adds the sign-in to the login chain. It opens only POST /login/x509, hands the filter the extractor, the user details service and the success handler, and puts the forwarded-certificate filter in front when a proxy may forward certificates.

/**
 * Adds the sign-in with a client certificate to the login/UI chain through {@code http.x509(...)}. The filter only
 * looks at {@code POST /login/x509}, the form of {@link X509LoginMethodFragment} on the login page, which carries the
 * CSRF token like every other form of the chain; the CSRF filter runs before the X.509 one, so a cross-site page can
 * never make a browser sign in with its certificate. The form posts to the TLS port that requests a certificate (or
 * to the proxy that forwards one); every other request of the chain is untouched, and {@code GET /login/x509} is not
 * a sign-in at all (it is not opened, so it ends with the chain's catch-all rule). A certificate that is bound to an
 * account signs it in and resumes the interrupted request, anything else goes back to the login page. The path is
 * open to everybody, because it is where the certificate is checked. When a proxy may forward the certificate,
 * {@link ForwardedCertificateFilter} runs first. Once the chain is configured, the success handler gets the chain's
 * session authentication strategy, the one the form login uses.
 */
@RequiredArgsConstructor
public class X509ChainCustomizer implements LoginChainCustomizer {

    /** Order of the customizer: after the social login one. */
    public static final int ORDER = 6;

    /** Path of the sign-in with a certificate, which is served by the security filter. */
    public static final String LOGIN_PATH = "/login/x509";

    /** Where a failed sign-in goes. */
    static final String FAILURE_URL = "/login?error";

    /** The filter that authenticates the certificate. */
    private final X509LoginFilter filter;

    /** Takes the principal of the certificate. */
    private final X509PrincipalExtractor principalExtractor;

    /** Loads the account of the certificate. */
    private final AuthenticationUserDetailsService<PreAuthenticatedAuthenticationToken> userDetailsService;

    /** The filter that reads a forwarded certificate, or {@code null} when the transport is off. */
    private final ForwardedCertificateFilter forwardedFilter;

    /** Completes the sign-in. */
    private final X509AuthenticationSuccessHandler successHandler;

    /**
     * Customizes the login/UI chain.
     *
     * @param http security builder of the chain.
     */
    @Override
    public void customize(final HttpSecurity http) {
        final var loginRequest = PathPatternRequestMatcher.withDefaults().matcher(HttpMethod.POST, LOGIN_PATH);
        http.authorizeHttpRequests(authorize -> authorize.requestMatchers(loginRequest).permitAll());
        prepare(filter, loginRequest, http);
        if (forwardedFilter != null) {
            http.addFilterBefore(forwardedFilter, X509AuthenticationFilter.class);
        }
        http.x509(x509 -> x509
                .x509AuthenticationFilter(filter)
                .x509PrincipalExtractor(principalExtractor)
                .authenticationUserDetailsService(userDetailsService));
        http.with(new SessionStrategyConfigurer(successHandler));
    }

    /**
     * Sets up the filter, which the {@code x509} configurer takes as it is.
     *
     * @param loginFilter  the filter.
     * @param loginRequest matcher of the sign-in requests.
     * @param http         security builder of the chain, whose authentication manager the filter uses once built.
     */
    private void prepare(final X509LoginFilter loginFilter, final RequestMatcher loginRequest,
            final HttpSecurity http) {
        loginFilter.setPrincipalExtractor(principalExtractor);
        loginFilter.setRequiresAuthenticationRequestMatcher(loginRequest);
        loginFilter.setMfaEnabled(true);
        loginFilter.setAuthenticationSuccessHandler(successHandler);
        loginFilter.setAuthenticationFailureHandler(
                (request, response, exception) -> response.sendRedirect(request.getContextPath() + FAILURE_URL));
        // the chain's manager only exists once the chain is built, so it is read when a request arrives
        loginFilter.setAuthenticationManager(authentication ->
                http.getSharedObject(AuthenticationManager.class)
                        .authenticate(authentication));
    }

    /**
     * Hands the session authentication strategy of the chain to the success handler. The strategy is a shared object
     * of the chain that only exists once every configurer has been initialised (the CSRF configurer adds its
     * {@code CsrfAuthenticationStrategy} to the session management one), so it is read in {@code configure}, as the
     * form login does for its own filter. Package-private so its test can drive it.
     */
    @RequiredArgsConstructor
    static final class SessionStrategyConfigurer
            extends AbstractHttpConfigurer<SessionStrategyConfigurer, HttpSecurity> {

        /** The handler that gets the strategy. */
        private final X509AuthenticationSuccessHandler handler;

        /**
         * Sets the shared strategy, when the chain has one, on the handler.
         *
         * @param http security builder of the chain.
         */
        @Override
        public void configure(final HttpSecurity http) {
            final var strategy = http.getSharedObject(SessionAuthenticationStrategy.class);
            if (strategy != null) {
                handler.setSessionAuthenticationStrategy(strategy);
            }
        }
    }
}

Directly on TLS. A second Tomcat connector asks for a certificate on its own port, so the rest of the application never prompts a browser for one. /**

 * port is left as it is, so the rest of the application never asks a browser for a certificate. The connector
 * <em>requests</em> a certificate without requiring one and without validating it against a CA

    private final X509Properties properties;

Behind a proxy. The proxy verifies the certificate and forwards it in a header. The filter reads that header only when the request comes from a trusted address, then sets the attribute that the X.509 filter reads:

/**
 * Reads the client certificate a reverse proxy that terminates TLS forwards in a header and leaves it where the
 * servlet container leaves a certificate of its own, in the {@code jakarta.servlet.request.X509Certificate} request
 * attribute, so the same X.509 filter and principal extractor serve both transports.
 *
 * <p>A header is only ever read when the request comes from one of the configured trusted proxies: anybody else could
 * send any certificate. The address checked is {@code getRemoteAddr()}, which is the address left after Spring's or
 * Tomcat's handling of the forwarded headers; only with {@code server.forward-headers-strategy=none} is it the direct
 * network peer, because the {@code native} and {@code framework} strategies replace it with a value taken from
 * {@code X-Forwarded-For}, which a client can choose. {@link X509ForwardedHeadersGuard} therefore refuses to start
 * with this transport and any strategy that rewrites the address. The header of any other request is ignored, and so
 * is one that is too long or does not hold a certificate. The proxy is responsible for verifying the certificate (the
 * chain, the dates, the revocation) and for overwriting or removing a header of the same name sent by the client; the
 * server only binds the certificate it is handed by its fingerprint. The filter only looks at the sign-in request
 * ({@code POST /login/x509}).
 */
@Slf4j
public class ForwardedCertificateFilter extends OncePerRequestFilter {

    /** Name of the request attribute the servlet container, and the X.509 filter, use for the certificates. */
    static final String CERTIFICATE_ATTRIBUTE = "jakarta.servlet.request.X509Certificate";

    /** Longest header value that is parsed, in characters (a certificate is a few kilobytes). */
    static final int MAX_HEADER_LENGTH = 16_384;

    /** Type of the certificates. */
    private static final String CERTIFICATE_TYPE = "X.509";

    /** Lines that frame a PEM certificate, and any white space. */
    private static final Pattern PEM_NOISE = Pattern.compile("-----(BEGIN|END) CERTIFICATE-----|\\s");

    /** Name of the header the certificate comes in. */
    private final String headerName;

    /** Matchers of the addresses of the trusted proxies. */
    private final List<IpAddressMatcher> trustedProxies;

    /** Matcher of the requests the filter looks at. */
    private final RequestMatcher loginRequests;

    /**
     * Creates the filter.
     *
     * @param properties settings of the sign-in with a certificate: the header and the trusted proxies.
     */
    public ForwardedCertificateFilter(final X509Properties properties) {
        headerName = properties.forwardedHeader();
        trustedProxies = properties.trustedProxies().stream().map(IpAddressMatcher::new).toList();
        loginRequests = PathPatternRequestMatcher.withDefaults()
                .matcher(HttpMethod.POST, X509ChainCustomizer.LOGIN_PATH);
    }

    /**
     * Sets the certificate attribute when a trusted proxy forwarded a valid certificate.
     *
     * @param request  the request.
     * @param response the response.
     * @param chain    the rest of the chain.
     * @throws ServletException if the chain fails.
     * @throws IOException      if the chain fails.
     */
    @Override
    protected void doFilterInternal(final HttpServletRequest request, final HttpServletResponse response,
            final FilterChain chain) throws ServletException, IOException {
        final var header = request.getHeader(headerName);
        if (header != null && loginRequests.matches(request)) {
            if (isTrusted(request.getRemoteAddr())) {
                parse(header).ifPresent(certificate -> request.setAttribute(CERTIFICATE_ATTRIBUTE,
                        new X509Certificate[] {certificate}));
            } else {
                log.warn("Ignored a forwarded client certificate from an untrusted address");
            }
        }
        chain.doFilter(request, response);
    }

    /**
     * Tells whether an address belongs to a trusted proxy.
     *
     * @param address the address of the client of the request, as the container reports it; may be {@code null}.
     * @return {@code true} when a trusted proxy matches it.
     */
    private boolean isTrusted(final String address) {
        return StringUtils.hasText(address) && trustedProxies.stream().anyMatch(proxy -> proxy.matches(address));
    }

    /**
     * Parses the certificate of a header value.
     *
     * @param value the value: the URL-encoded PEM, the PEM or the base64 of the DER form.
     * @return the certificate, or empty when the value is too long or is not a certificate.
     */
    private static Optional<X509Certificate> parse(final String value) {
        if (value.length() > MAX_HEADER_LENGTH) {
            log.debug("Ignored a forwarded client certificate that is too long");
            return Optional.empty();
        }
        try {
            final var base64 = PEM_NOISE.matcher(UriUtils.decode(value, StandardCharsets.UTF_8)).replaceAll("");
            final var der = Base64.getDecoder().decode(base64);
            final var certificate = CertificateFactory.getInstance(CERTIFICATE_TYPE)
                    .generateCertificate(new ByteArrayInputStream(der));
            return certificate instanceof X509Certificate x509 ? Optional.of(x509) : Optional.empty();
        } catch (final CertificateException | IllegalArgumentException e) {
            log.debug("Ignored a forwarded client certificate that cannot be read", e);
            return Optional.empty();
        }
    }
}

The address that the filter checks is getRemoteAddr(), and Spring Boot rewrites it from X-Forwarded-For under the framework and native strategies. A client could then name a trusted proxy in that header. This guard refuses to start in that combination:

/**
 * Refuses to start when a certificate may be forwarded in a header while the server rewrites the address of its
 * clients from the forwarded headers.
 *
 * <p>{@link ForwardedCertificateFilter} trusts a forwarded certificate only from the addresses of
 * {@code authserver.x509.trusted-proxies}, and it reads the address with {@code getRemoteAddr()}, which is the address
 * left once Spring Boot's forwarded-header handling has run. With {@code server.forward-headers-strategy=framework},
 * Spring's {@code ForwardedHeaderFilter} replaces it with the first value of {@code X-Forwarded-For} (or
 * {@code Forwarded}), which any client can send: naming a trusted proxy there would make a forged certificate header
 * look trusted. With {@code native}, Tomcat's {@code RemoteIpValve} replaces it with the client the proxies report,
 * so the address of the proxy itself is never seen and the check is made against an address that came from a header.
 * The same happens without the property on a cloud platform that Spring Boot detects, where {@code native} is the
 * default. Only with {@code none} is the address the direct network peer, which no header can change, so that is the
 * one combination allowed. The proxy is still free to send {@code X-Forwarded-*} headers; they are just not used.
 */
public final class X509ForwardedHeadersGuard {

    /** Property of Spring Boot that selects how the forwarded headers are handled. */
    static final String STRATEGY_PROPERTY = "server.forward-headers-strategy";

    /** Value of the strategy that leaves the address of the client alone. */
    private static final String NONE = "none";

    /** Value of the strategy of the servlet container. */
    private static final String NATIVE = "native";

    /** Value of the strategy of Spring's filter. */
    private static final String FRAMEWORK = "framework";

    /** Environment of the application, with the forwarded-header strategy. */
    private final Environment environment;

    /**
     * Checks the configuration.
     *
     * @param properties  settings of the sign-in with a certificate.
     * @param environment environment of the application, with the forwarded-header strategy.
     * @throws IllegalStateException if the forwarded certificate header is enabled and the strategy (configured or
     *                               deduced from the cloud platform) rewrites the address of the client.
     */
    public X509ForwardedHeadersGuard(final X509Properties properties, final Environment environment) {
        this.environment = environment;
        if (properties.forwardedEnabled() && rewritesClientAddress()) {
            throw new IllegalStateException("authserver.x509.forwarded-header needs " + STRATEGY_PROPERTY + "=" + NONE
                    + ": with any other strategy the address checked against authserver.x509.trusted-proxies comes "
                    + "from a forwarded header that a client can choose");
        }
    }

    /**
     * Tells whether the server replaces the address of its clients with one taken from the forwarded headers.
     *
     * @return {@code true} for the {@code native} and {@code framework} strategies, and without a strategy when the
     *         detected cloud platform uses the forwarded headers.
     */
    public boolean rewritesClientAddress() {
        final var strategy = environment.getProperty(STRATEGY_PROPERTY, "").strip().toLowerCase(Locale.ROOT);
        return switch (strategy) {
            case NATIVE, FRAMEWORK -> true;
            case NONE -> false;
            default -> {
                final var platform = CloudPlatform.getActive(environment);
                yield platform != null && platform.isUsingForwardHeaders();
            }
        };
    }
}

Only a public certificate is ever accepted. The reader refuses a value that carries a private key without parsing it, and computes the fingerprint exactly as the sign-in does, so the binding matches the certificate that the browser presents later:

/**
 * Reads the certificate sent to bind it to an account: exactly one X.509 certificate in PEM form, within its validity
 * period, with a subject. A value that carries a private key is refused without being parsed: only the public
 * certificate is ever sent. The fingerprint is computed exactly as {@link CertificatePrincipalExtractor} computes it at
 * sign-in, so the binding matches the certificate the browser presents later.
 */
@Component
public class PemCertificateReader {

    /** Longest subject the {@code x509_certificates} table keeps. */
    static final int MAX_SUBJECT_LENGTH = 1000;

    /** Type of the certificates. */
    private static final String CERTIFICATE_TYPE = "X.509";

    /** Marker of a PEM private key, of any algorithm. */
    private static final String PRIVATE_KEY_MARKER = "PRIVATE KEY";

    /** Computes the fingerprint the sign-in looks up. */
    private final CertificatePrincipalExtractor fingerprints = new CertificatePrincipalExtractor();

    /**
     * Reads a certificate.
     *
     * @param pem the certificate in PEM form.
     * @return its fingerprint and subject.
     * @throws InvalidCertificateException if the value carries a private key, is not exactly one X.509 certificate, is
     *                                     outside its validity period or has no usable subject.
     */
    public PresentedCertificate read(final String pem) {
        if (pem == null || pem.contains(PRIVATE_KEY_MARKER)) {
            throw new InvalidCertificateException("Only a public certificate may be sent");
        }
        final var certificate = parse(pem);
        try {
            certificate.checkValidity();
        } catch (final CertificateExpiredException | CertificateNotYetValidException e) {
            throw new InvalidCertificateException("The certificate is not within its validity period", e);
        }
        final var subject = certificate.getSubjectX500Principal().getName();
        if (subject.isBlank() || subject.length() > MAX_SUBJECT_LENGTH) {
            throw new InvalidCertificateException("The certificate has no usable subject");
        }
        try {
            return new PresentedCertificate(fingerprints.fingerprintOf(certificate.getEncoded()), subject);
        } catch (final CertificateEncodingException e) {
            throw new InvalidCertificateException("The certificate cannot be encoded", e);
        }
    }

    /**
     * Parses exactly one X.509 certificate.
     *
     * @param pem the PEM text.
     * @return the certificate.
     * @throws InvalidCertificateException if the text is not exactly one X.509 certificate.
     */
    private static X509Certificate parse(final String pem) {
        try {
            final var certificates = CertificateFactory.getInstance(CERTIFICATE_TYPE)
                    .generateCertificates(new ByteArrayInputStream(pem.getBytes(StandardCharsets.US_ASCII)));
            if (certificates.size() != 1
                    || !(certificates.iterator().next() instanceof final X509Certificate certificate)) {
                throw new InvalidCertificateException("Exactly one X.509 certificate must be sent");
            }
            return certificate;
        } catch (final CertificateException e) {
            throw new InvalidCertificateException("The value is not a PEM X.509 certificate", e);
        }
    }
}

 * remove the last way to sign in, counted under the lock of {@link LockSignInMethodsUseCase} so that concurrent
 * removals of the same account are serialized.

@RequiredArgsConstructor

    private final CertificateBindingRepository certificateBindingRepository;

    /** Locks and counts the sign-in methods of the account. */
    private final LockSignInMethodsUseCase lockSignInMethodsUseCase;

    /** Rules of removing a sign-in method. */
    private final FederatedLinkingPolicy federatedLinkingPolicy;

    /** Use case that records the audit events. */
    private final RecordSecurityEventUseCase recordSecurityEventUseCase;

    /**
     * Unbinds a certificate; a certificate of another account is never touched.
     *
     * @param userId   identifier of the account.
     * @param username name of the account, for the audit log.
     * @param id       identifier of the binding.
     * @throws CertificateNotFoundException if the account has no such binding.
     * @throws LastSignInMethodException    if the certificate is the last way the account can sign in.
     */
    public void execute(final UUID userId, final String username, final UUID id) {
        final var methods = lockSignInMethodsUseCase.execute(userId);
        if (certificateBindingRepository.findByUser(userId).stream().noneMatch(binding -> binding.id().equals(id))) {
            throw new CertificateNotFoundException("The account has no certificate " + id);
        }
        if (!federatedLinkingPolicy.mayUnlink(methods.withoutCertificate())) {
            throw new LastSignInMethodException("The certificate is the last way to sign in to the account");
        }
        if (!certificateBindingRepository.delete(id, userId)) {
            throw new CertificateNotFoundException("The account has no certificate " + id);
        }
        recordSecurityEventUseCase.execute(SecurityEventType.CERTIFICATE_UNBOUND, userId, username, id.toString());
    }
}

The page contributes a fragment through a LoginMethodFragment bean. Where the form posts depends on the transport: the relative path behind a proxy, or the same host on the dedicated TLS port.

/**
 * Contributes the sign-in with a client certificate to the login page: a form with one button that posts, with the
 * CSRF token, to {@code POST /login/x509}. The template reads {@link #action()} through this bean, because where the
 * form posts depends on the transport:

 *     other port posts to the same host on that port over {@code https}; a page already served on that port posts to
 *     the relative path.</li>
 * </ul>

Device grant: the endpoints

The protocol-chain customizer enables the two endpoints and installs the example’s pieces:

/**
 * Enables the OAuth 2.0 Device Authorization Grant on the protocol chain. The device authorization endpoint
 * ({@code POST /oauth2/device_authorization}) is where the device, authenticated as a public client by its identifier
 * alone, obtains a device code and a user code. The verification endpoint ({@code /oauth2/device_verification}) is
 * where the signed-in user approves the device; its verification URI is the framework's default, the issuer plus the
 * endpoint, whose {@code GET} without a code is the page of {@link DeviceVerificationController}. The verification
 * endpoint is customized to guard its requests ({@link DeviceVerificationRequestGuard}), to hand the consent decision
 * to the existing consent page, to answer its failures with {@link DeviceVerificationErrorHandler} and to go back to
 * the verification page when the device was approved.
 */
@RequiredArgsConstructor
public class DeviceProtocolChainCustomizer implements ProtocolChainCustomizer {

    /** Order of the customizer: after the multi-factor ({@code 0}) and step-up ({@code 1}) ones. */
    public static final int ORDER = 2;

    /** Reads the identifier of a public client of the device flow. */
    private final AuthenticationConverter clientConverter;

    /** Authenticates a public client of the device flow. */
    private final AuthenticationProvider clientProvider;

    /** Rate limit and multi-factor policy of the verification requests. */
    private final AuthenticationConverter guard;

    /** Answers the failures of the verification endpoint. */
    private final AuthenticationFailureHandler errorHandler;

    /** Answers a verification that did not need consent, or whose consent was given. */
    private final AuthenticationSuccessHandler successHandler;

    /**
     * Customizes the device endpoints.
     *
     * @param server configurer of the authorization server.
     */
    @Override
    public void customize(final OAuth2AuthorizationServerConfigurer server) {
        server.clientAuthentication(client -> client
                .authenticationConverter(clientConverter)
                .authenticationProvider(clientProvider));
        server.deviceAuthorizationEndpoint(Customizer.withDefaults());
        server.deviceVerificationEndpoint(endpoint -> endpoint
                .consentPage(ConsentController.CONSENT_PATH)
                .deviceVerificationRequestConverters(converters -> converters.addFirst(guard))
                .errorResponseHandler(errorHandler)
                .deviceVerificationResponseHandler(successHandler));
    }
}

Device grant: the public client

Spring Authorization Server’s public-client authentication needs a PKCE code verifier, which the device flow does not have. This converter reads the client_id of a request to the device authorization endpoint, and of the polling request to the token endpoint, and leaves any request that carries another credential to the converters of that credential:

/**
 * Reads the identifier of a public client of the device flow, the only kind of client authentication that flow has
 * for a device that cannot keep a secret: the {@code client_id} of the request to the device authorization endpoint
 * and of the polling request to the token endpoint with the device code grant. Spring Authorization Server's public
 * client authentication needs a PKCE code verifier, which the device flow does not have. A request that carries any
 * other credential (an {@code Authorization} header, a client secret or a client assertion) is left to the
 * converters of those credentials.
 */
public class DeviceClientAuthenticationConverter implements AuthenticationConverter {

    /** Names of the parameters that carry a credential of a confidential client. */
    private static final List<String> CREDENTIAL_PARAMETERS = List.of(
            OAuth2ParameterNames.CLIENT_SECRET, OAuth2ParameterNames.CLIENT_ASSERTION,
            OAuth2ParameterNames.CLIENT_ASSERTION_TYPE);

    /** Matches the request for the codes, which names the client. */
    private final RequestMatcher deviceAuthorizationRequest;

    /**
     * Creates the converter.
     *
     * @param deviceAuthorizationEndpoint path of the device authorization endpoint.
     */
    public DeviceClientAuthenticationConverter(final String deviceAuthorizationEndpoint) {
        deviceAuthorizationRequest = PathPatternRequestMatcher.withDefaults()
                .matcher(HttpMethod.POST, deviceAuthorizationEndpoint);
    }

    /**
     * Reads the client of a request.
     *
     * @param request the request.
     * @return the request to authenticate the public client, or {@code null} when the request is not one of the device
     *         flow's or carries a credential.
     * @throws OAuth2AuthenticationException {@code invalid_request} if the client is named more than once or not at
     *                                       all.
     */
    @Override
    public Authentication convert(final HttpServletRequest request) {
        if (!isDeviceRequest(request) || carriesCredential(request)) {
            return null;
        }
        final var clientIds = request.getParameterValues(OAuth2ParameterNames.CLIENT_ID);
        if (clientIds == null || clientIds.length != 1 || !StringUtils.hasText(clientIds[0])) {
            throw new OAuth2AuthenticationException(OAuth2ErrorCodes.INVALID_REQUEST);
        }
        return new DeviceClientAuthenticationToken(clientIds[0]);
    }

    /**
     * Tells whether the request is one of the device flow's: the request for the codes, or the poll with the device
     * code grant.
     *
     * @param request the request.
     * @return {@code true} for a device flow request that names a client.
     */
    private boolean isDeviceRequest(final HttpServletRequest request) {
        if (request.getParameter(OAuth2ParameterNames.CLIENT_ID) == null) {
            return false;
        }
        return deviceAuthorizationRequest.matches(request) || isDeviceCodePoll(request);
    }

    /**
     * Tells whether the request is a poll of the token endpoint with the device code grant.
     *
     * @param request the request.
     * @return {@code true} when it is.
     */
    private static boolean isDeviceCodePoll(final HttpServletRequest request) {
        return AuthorizationGrantType.DEVICE_CODE.getValue().equals(request.getParameter(
                OAuth2ParameterNames.GRANT_TYPE)) && request.getParameter(OAuth2ParameterNames.DEVICE_CODE) != null;
    }

    /**
     * Tells whether the request carries the credential of a confidential client.
     *
     * @param request the request.
     * @return {@code true} when it does.
     */
    private static boolean carriesCredential(final HttpServletRequest request) {
        return request.getHeader(HttpHeaders.AUTHORIZATION) != null
                || CREDENTIAL_PARAMETERS.stream().anyMatch(name -> request.getParameter(name) != null);
    }
}

Device grant: guarding the verification

The guard runs first among the converters of the verification endpoint. It never produces an authentication: it counts the attempt, applies the multi-factor policy of the account and of the client, and refuses otherwise. The framework’s own multi-factor customizer covers only /oauth2/authorize, so the device endpoint needs this one.

/**
 * Guards the device verification endpoint. It is installed first among the converters of the endpoint and never
 * converts anything: it either lets the request go on (returning {@code null}) or refuses it. Every request that
 * carries a user code (the code typed on the verification page, a link that carries it, and the consent decision) is
 * counted against the limit on the attempts, and the multi-factor policy of the account and of the client must be
 * satisfied, as the authorization endpoint requires before it issues a code: a user who owes a second factor is sent
 * to the second-factor page and resumes afterwards. The framework's own MFA customizer covers only
 * {@code /oauth2/authorize}.
 *
 * <p>The client is the one the device authorization stored for the user code was issued to, because the code typed on
 * the page (or carried by the link) is the only thing the request names: so a client that requires multi-factor
 * authentication is enforced even when it skips the consent page. Only when no authorization holds the code (an
 * unknown or expired one, which the endpoint refuses anyway) is the {@code client_id} of the consent decision used.
 */
@RequiredArgsConstructor
public class DeviceVerificationRequestGuard implements AuthenticationConverter {

    /** Type of the token the user code is stored as. */
    static final OAuth2TokenType USER_CODE_TOKEN_TYPE = new OAuth2TokenType(OAuth2ParameterNames.USER_CODE);

    /** Number of letters and digits of a user code. */
    private static final int USER_CODE_LENGTH = 8;

    /** Position of the dash the framework stores a user code with. */
    private static final int USER_CODE_GROUP = USER_CODE_LENGTH / 2;

    /** Everything a user may type around the letters and digits of a code (dashes, spaces). */
    private static final Pattern NOT_ALPHANUMERIC = Pattern.compile("[^A-Z\\d]+");

    /** Limits the attempts. */
    private final DeviceVerificationRateLimiter rateLimiter;

    /** Applies the multi-factor policy. */
    private final MfaAuthorizationManager authorizationManager;

    /** Finds the device authorization of a user code. */
    private final OAuth2AuthorizationService authorizationService;

    /** Finds the client of a device authorization. */
    private final RegisteredClientRepository registeredClientRepository;

    /**
     * Checks the request.
     *
     * @param request the request.
     * @return always {@code null}: this converter only vetoes requests.
     * @throws DeviceVerificationRateLimitedException if the client address or the user made too many attempts.
     * @throws SecondFactorRequiredException          if the user still owes a second factor.
     */
    @Override
    public Authentication convert(final HttpServletRequest request) {
        final var user = SecurityContextHolder.getContext().getAuthentication();
        if (!MfaAuthorizationManager.isUser(user)) {
            return null;
        }
        rateLimiter.check(request.getRemoteAddr(), user.getName());
        final var clientRequires = authorizationManager.clientRequiresMfa(clientIdOf(request));
        if (!authorizationManager.evaluate(user, clientRequires).isGranted()) {
            throw new SecondFactorRequiredException();
        }
        return null;
    }

    /**
     * Finds the client a request is about: the client of the device authorization stored for its user code, or the
     * {@code client_id} parameter when no authorization holds that code.
     *
     * @param request the request.
     * @return the client id, or {@code null} when neither tells it.
     */
    private String clientIdOf(final HttpServletRequest request) {
        return normalize(request.getParameter(OAuth2ParameterNames.USER_CODE))
                .map(userCode -> authorizationService.findByToken(userCode, USER_CODE_TOKEN_TYPE))
                .map(authorization -> registeredClientRepository.findById(authorization.getRegisteredClientId()))
                .map(RegisteredClient::getClientId)
                .orElseGet(() -> request.getParameter(OAuth2ParameterNames.CLIENT_ID));
    }

    /**
     * Normalises a user code as the framework stores it: upper case letters and digits in two groups of four,
     * separated by a dash.
     *
     * @param userCode the code as typed, may be {@code null}.
     * @return the stored form, or empty when the value cannot be a user code.
     */
    private static Optional<String> normalize(final String userCode) {
        if (!StringUtils.hasText(userCode)) {
            return Optional.empty();
        }
        final var compact = NOT_ALPHANUMERIC.matcher(userCode.toUpperCase(Locale.ROOT)).replaceAll("");
        if (compact.length() != USER_CODE_LENGTH) {
            return Optional.empty();
        }
        return Optional.of(compact.substring(0, USER_CODE_GROUP) + "-" + compact.substring(USER_CODE_GROUP));
    }
}

A user code is short, so it must not be guessable faster than a limit allows. The limiter keeps one bucket per client address and one per signed-in user, with Bucket4j and Caffeine, as the other limiters of the example do (see Bucket4j with Spring Boot):

/**
 * Rate limiter of the attempts to verify a user code, on the pattern of the other limiters of this server: Bucket4j
 * token buckets in Caffeine caches ({@link FixedWindowBuckets}), one per client address and one per signed-in user, so
 * a user code, which is short, cannot be guessed faster than the limits allow. The buckets live in this instance
 * only: several instances each apply the limits on their own. The client address is
 * {@code request.getRemoteAddr()}, so behind a proxy {@code server.forward-headers-strategy} must be set for it to be
 * the real client.
 */
public final class DeviceVerificationRateLimiter {

    /** Key used when the client address is unknown. */
    private static final String UNKNOWN_CLIENT = "unknown";

    /** Limits, window and bound of the tracked keys. */
    private final DeviceRateLimitProperties properties;

    /** Buckets per client address. */
    private final FixedWindowBuckets clients;

    /** Buckets per signed-in user. */
    private final FixedWindowBuckets users;

    /**
     * Creates the limiter.
     *
     * @param properties limits, window and bound of the tracked keys.
     * @param clock      source of the current time.
     */
    public DeviceVerificationRateLimiter(final DeviceRateLimitProperties properties, final Clock clock) {
        this.properties = properties;
        clients = new FixedWindowBuckets(clock, properties.window(), properties.maxTrackedKeys());
        users = new FixedWindowBuckets(clock, properties.window(), properties.maxTrackedKeys());
    }

    /**
     * Counts one attempt and rejects it once a limit is exceeded.
     *
     * @param clientAddress address of the calling client, may be {@code null}.
     * @param userName      name of the signed-in user.
     * @throws DeviceVerificationRateLimitedException if the client address or the user exceeded its limit.
     */
    public void check(final String clientAddress, final String userName) {
        if (!properties.enabled()) {
            return;
        }
        final var clientWait = clients.tryConsume(clientAddress == null ? UNKNOWN_CLIENT : clientAddress,
                properties.perClient());
        if (clientWait.isPresent()) {
            throw new DeviceVerificationRateLimitedException(clientWait.get());
        }
        final var userWait = users.tryConsume(userName, properties.perUser());
        if (userWait.isPresent()) {
            throw new DeviceVerificationRateLimitedException(userWait.get());
        }
    }
}

Unbinding the last way to sign in is refused. The sign-in itself is the form of the login page; there is no JSON API for it, because the credential is the TLS handshake.

Device verification page

The device endpoints are framework endpoints, so their request and response shapes are those of RFC 8628. The only operation of the example’s pages contract is the verification page:

      description: >-

See the OpenAPI path item object for the structure of a path.

The device requests its codes with its client_id alone (use the identifier of a client that has the urn:ietf:params:oauth:grant-type:device_code grant; the development profile seeds one named device-client):

curl -s -X POST http://localhost:9000/oauth2/device_authorization \
  -d "client_id=device-client"

The answer carries device_code, user_code, verification_uri, verification_uri_complete, expires_in and interval. The device then polls the token endpoint every interval seconds until the user has approved it:

curl -s -X POST http://localhost:9000/oauth2/token \
  -d "grant_type=urn:ietf:params:oauth:grant-type:device_code" \
  -d "device_code=${DEVICE_CODE}" \
  -d "client_id=device-client"

Until then the answer is 400 with authorization_pending, or slow_down when the device polls too fast, and expired_token once the codes have expired. After approval it is a token response.

Tests

All of these are integration tests of the example. None of them has a tagged region, so they are described here.

  • X509LoginIT (Spring MockMvc). A bound certificate signs in and the tokens report sc. An unbound certificate, no certificate, an expired certificate, a removed binding and a disabled account are all sent back to the login page. A forwarded header from an untrusted address is ignored. A certificate issued by a certificate authority works like a self-signed one. A GET never signs anybody in, and a request without the CSRF token is refused.

  • X509TlsLoginIT. A real TLS handshake on the dedicated port, with certificates generated by keytool at run time: bound, unbound, no certificate, binding removed and expired.

  • X509ForwardedHeadersGuardIT. The application refuses to start with a forwarded header and a strategy that rewrites the client address.

  • CertificateApiIT and JdbcCertificateBindingRepositoryIT. The account API (binding, listing, the step-up challenge, conflicts, the last sign-in method) and the repository against PostgreSQL in a container.

  • DeviceVerificationPageIT. The verification page for an anonymous and a signed-in user, the error and success messages, the full flow to tokens, a link that carries the code, and redirects to the second-factor page when the account or the client requires one.

  • DeviceVerificationRateLimitIT. Attempts beyond the per-address and per-user limits are refused.

  • DeviceFlowEndToEndIT, in the e2e-tests module. The packaged DeviceFlowCli obtains tokens after the user approves in a real browser driven by Playwright, and ends with a non-zero exit when the user denies.

Two production defects were found by these tests while the example was written, which is what they are for: an expired bound certificate used to sign in on both transports, and the dedicated TLS port used to advertise the JVM’s authorities, so a private authority’s certificate was never offered.

Security notes and pitfalls

  • Trust forwarded certificate headers only from the proxy. Anybody can send a header. The filter reads it only when the direct network peer is in authserver.x509.trusted-proxies, and the guard refuses a forwarded-header strategy that would let a client choose that address. The proxy must also overwrite or remove a header of that name sent by the client, and must verify the certificate.

  • Revocation is not checked. On the dedicated port no authority validates the chain, and behind a proxy the proxy does. What revokes access is deleting the binding. If you rely on a PKI, check revocation (CRL or OCSP) at the proxy and remove bindings when a certificate is revoked.

  • Expiry is checked. The extractor yields no usable principal for a certificate outside its validity period.

  • Bind only public certificates. The reader refuses anything that mentions a private key, so a user who pastes the wrong file does not send the key to the server.

  • Do not lock yourself out. Unbinding the last way to sign in is refused, and binding or unbinding need a recent multi-factor sign-in.

  • Browser prompts. A certificate prompt on the main port would affect every user. A dedicated port keeps it to the people who choose the button.

  • User-code brute force and phishing in the device flow. A user code is short, so the example limits attempts per address and per user, makes the code expire with the device code, and never says why a code failed. The user is still asked to approve a code that an attacker’s device may have started: show the client name and scopes on the consent page and tell the user to approve only a code that their own device showed. RFC 8628 discusses both in its sections on brute forcing and remote phishing.

  • The device is a public client. Its identifier is not a secret. Give it only the scopes a device needs and prefer short-lived tokens.

  • Push fatigue. A plain approve or deny prompt can be spammed until a user approves. Number matching defeats that, because the attacker cannot see the number that the real sign-in page shows. Limit pending challenges per user and keep the challenge short-lived.

For the full reference see RFC 8628, the Spring Security X.509 reference, the Spring Authorization Server protocol endpoints and NIST SP 800-63B-4 for authenticator policy.
