Authorization Server from Scratch: Client Credentials & Service-to-Service

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

What you build

Everything so far authenticated a person. This page covers the other caller of an API, a service with no browser and no user at the keyboard. The example has a command line application, service-client, that obtains access tokens on its own, calls GET /api/documents on the resource server, and can also call it on behalf of a signed-in user. The page builds four capabilities:

  • the client credentials grant: the client authenticates to the token endpoint and receives a short-lived access token whose subject is the client itself, cached and renewed shortly before it expires;

  • client authentication without a shared secret: a signed assertion with private_key_jwt (RFC 7523), or a TLS client certificate with tls_client_auth and self_signed_tls_client_auth, which also yield certificate-bound access tokens (RFC 8705);

  • sender-constrained tokens with DPoP (RFC 9449): the service-client has a code path that sends a proof of possession with every call;

  • token exchange (RFC 8693): the client trades the access token of a user, plus its own token as actor, for an audience-restricted token that names the user as subject and the client in an act claim, so a downstream call is made as the user, by the service.

The theory lives in the OAuth Reference pages Client Credentials and Client Authentication, Sender-Constrained Tokens: DPoP and mTLS and Token Exchange and Assertion Grants, and this page does not repeat it. It shows what Spring Authorization Server gives out of the box, and the parts the example adds because the framework does not do them:

  • replay protection for client assertions (the framework neither requires a jti nor remembers one);

  • registered public keys for private_key_jwt, stored with the client instead of fetched from a URL;

  • a trust anchor check for tls_client_auth (the TLS port accepts any chain, so the application validates it);

  • the audience restriction of exchanged tokens (the framework parses audience but ignores it).

The settings of a client that uses these methods (a JWK set, a signing algorithm, a certificate subject) are stored and validated as described in Registered Clients, Advanced client authentication settings. How a resource server validates the resulting tokens, including the thumbprint and proof checks, is on Protecting APIs, Sender-constrained tokens.

private_key_jwt

The client signs a short JWT (the assertion) with its private key and sends it in place of a secret. The server finds the client’s public keys, verifies the signature and the claims, and records the jti so the same assertion cannot be used twice (RFC 7523, section 3).

sequenceDiagram autonumber participant C as service-client participant T as POST /oauth2/token participant P as JwtClientAssertionAuthenticationProvider participant F as RegisteredJwksClientAssertionDecoderFactory participant V as ReplayRejectingJwtValidator participant DB as client_assertion_jtis C->>C: Sign an assertion (iss = sub = client id, aud = token URI, jti, iat, exp) C->>T: grant_type=client_credentials, client_assertion_type, client_assertion T->>P: Authenticate the client P->>F: createDecoder(registered client) F-->>P: Decoder over the registered JWK set (cached per client and settings hash) P->>P: Verify signature, issuer, subject, audience, expiry P->>V: validate(assertion) V->>V: jti, iat and exp present, lifetime within the maximum V->>DB: Insert (client id, jti) if new alt the jti was already used DB-->>V: Nothing inserted V-->>T: invalid_client, the assertion was already used T-->>C: 401 else first use DB-->>V: Inserted V-->>P: Success P-->>T: Client authenticated T-->>C: 200 with the access token end

The validators run in fail-fast order, so the replay check, which writes, runs only for an assertion that passed every default check. A refused assertion therefore never consumes its jti.

A certificate-bound token with mTLS

With tls_client_auth the client presents an X.509 certificate during the TLS handshake on a dedicated port (the authserver.x509.port connector that also serves X.509 sign-in) and identifies itself with client_id. The server validates the chain, compares the subject, and, if the client asked for certificate-bound tokens, puts the SHA-256 thumbprint of the certificate in the cnf claim of the token. The resource server accepts that token only on a connection that presents the same certificate.

sequenceDiagram autonumber participant C as service-client participant T as Token endpoint on the TLS port participant V as ClientCertificateVerifier participant R as Resource server C->>T: TLS handshake with the client certificate C->>T: grant_type=client_credentials, client_id T->>V: accept(context) V->>V: PKIX path validation against authserver.mtls.trusted-authorities V->>V: Leaf subject DN equals the registered one V-->>T: Client authenticated T->>T: Framework adds cnf with the x5t S256 thumbprint of the certificate T-->>C: Access token, certificate-bound C->>R: TLS handshake with the same certificate, then GET /api/documents R->>R: Thumbprint in cnf equals the thumbprint of the presented certificate R-->>C: 200 with the documents Note over C,R: The same token sent without the certificate, or with another one, is refused with invalid_token

For self_signed_tls_client_auth the check is different: the certificate must be self-signed and its public key must be one of the keys of the client’s registered JWK set. The server also advertises the TLS addresses of its endpoints in the mtls_endpoint_aliases metadata claim (RFC 8705, section 5), so a client can discover which URL to call with a certificate.

Token exchange

The service-client receives the access token of a user (in the end-to-end test it is obtained through the BFF) and wants to call the resource server as that user. It does not forward the user’s token; it exchanges it.

sequenceDiagram autonumber actor U as User participant S as service-client participant T as POST /oauth2/token participant X as TokenExchangeAudienceContributor participant R as Resource server U->>S: Hands over their access token (the subject token) S->>T: client_credentials, to get its own token (the actor token) T-->>S: Actor token S->>T: grant_type=token-exchange, subject_token, actor_token, audience, scope T->>T: The framework checks the grant, the subject and actor tokens, the scopes T->>X: contribute(context, claims) X->>X: Keep only the requested audiences the client may have alt none of the requested audiences is allowed X-->>T: invalid_target T-->>S: 400 else X-->>T: aud narrowed T-->>S: Access token, sub is the user, act names the service-client end S->>R: GET /api/documents with the exchanged token R-->>S: The user's own documents

The subject of the exchanged token stays the user, so the resource server applies the user’s ownership rules; the act claim records that the service-client acted. The framework writes act itself from the actor token.

Data

Spring Authorization Server does not keep a record of used client assertions. The example adds one table, client_assertion_jtis (migration V800), keyed by the client and the jti. An insert that does not add a row means the assertion was used before. A scheduled job deletes the rows after they expire, because a row matters only while its assertion could still be accepted.

-- One row per client assertion (private_key_jwt) already accepted, so the same assertion cannot be presented twice
-- (RFC 7523 section 3 allows an authorization server to refuse a replayed jti). A row is useful only until the
-- assertion expires and is purged afterwards.
CREATE TABLE client_assertion_jtis
(
    client_id  varchar(100)             NOT NULL,
    jti        varchar(255)             NOT NULL,
    expires_at timestamp with time zone NOT NULL,
    PRIMARY KEY (client_id, jti)
);

CREATE INDEX ix_client_assertion_jtis_expires_at ON client_assertion_jtis (expires_at);

Code

Settings

The assertion lifetime and the trust anchors of tls_client_auth are configuration, not code:

  client-assertion:
    # private_key_jwt / client_secret_jwt client authentication (RFC 7523): the longest lifetime accepted for an
    # assertion (exp minus iat), and the jti replay records are purged after they expire.
    max-lifetime: PT5M
    cleanup:
      # when the expired assertion identifiers are deleted (every hour)
      cron: "0 30 * * * *"

Reference: Spring Boot externalized configuration.

  mtls:
    # Mutual-TLS client authentication (RFC 8705): the certificate authorities, as PEM or key store locations, whose
    # certificates are accepted for tls_client_auth. Empty: none, only self_signed_tls_client_auth can succeed.
    trusted-authorities: []

Reference: Spring Boot externalized configuration.

With no trusted authority configured, tls_client_auth is refused for every client and only self_signed_tls_client_auth can succeed. The properties are bound by a record:

/**
 * Configuration of the mutual-TLS client authentication ({@code authserver.mtls.*}, RFC 8705).
 *
 * @param trustedAuthorities paths of the PEM files whose certificates are the trust anchors of
 *                           {@code tls_client_auth}; empty (the default) means that no CA-issued client certificate
 *                           is accepted, and only {@code self_signed_tls_client_auth} can succeed.
 */
@ConfigurationProperties(prefix = "authserver.mtls")
public record MtlsProperties(@DefaultValue List<String> trustedAuthorities) {

    /**
     * Validates the configuration and copies the list.
     *
     * @throws IllegalArgumentException if a path is blank.
     */
    public MtlsProperties {
        trustedAuthorities = trustedAuthorities == null ? List.of() : List.copyOf(trustedAuthorities);
        if (trustedAuthorities.stream().anyMatch(path -> !StringUtils.hasText(path))) {
            throw new IllegalArgumentException("authserver.mtls.trusted-authorities must not contain a blank path");
        }
    }
}

Wiring the protocol chain

The decoder factory is a bean that depends on the replay validator:

    /**
     * Declares the factory of the assertion decoders.
     *
     * @param replayValidator the validator of the lifetime and replay.
     * @return the factory.
     */
    @Bean
    public RegisteredJwksClientAssertionDecoderFactory registeredJwksClientAssertionDecoderFactory(
            final ReplayRejectingJwtValidator replayValidator) {
        return new RegisteredJwksClientAssertionDecoderFactory(replayValidator);
    }

Reference: OAuth2 Token Endpoint.

The chain customizer finds the framework’s two providers in the list of client authentication providers and sets the example’s factory on the assertion provider and the example’s verifier on the certificate provider. It also adds mtls_endpoint_aliases to both metadata documents.

/**
 * Installs {@code private_key_jwt} with replay protection and the mutual-TLS client authentication in the protocol
 * chain: the framework's assertion provider decodes with {@link RegisteredJwksClientAssertionDecoderFactory}, and its
 * certificate provider verifies with {@link ClientCertificateVerifier}. The server metadata (the OpenID provider
 * configuration and the OAuth 2.0 authorization server metadata) also advertises {@code mtls_endpoint_aliases}.
 */
@RequiredArgsConstructor
public class ClientAuthProtocolChainCustomizer implements ProtocolChainCustomizer {

    /** Order of the customizer: after the multi-factor, step-up and device ones. */
    public static final int ORDER = 3;

    /** Creates the decoders of the client assertions. */
    private final RegisteredJwksClientAssertionDecoderFactory decoderFactory;

    /** Verifies the client certificates. */
    private final ClientCertificateVerifier certificateVerifier;

    /** Builds the {@code mtls_endpoint_aliases} claim. */
    private final MtlsEndpointAliases endpointAliases;

    /**
     * Customizes the client authentication and the metadata.
     *
     * @param server configurer of the authorization server.
     */
    @Override
    public void customize(final OAuth2AuthorizationServerConfigurer server) {
        server.clientAuthentication(client -> client.authenticationProviders(this::configure));
        server.authorizationServerMetadataEndpoint(metadata -> metadata.authorizationServerMetadataCustomizer(
                builder -> endpointAliases.contribute(builder::claim)));
        server.oidc(oidc -> oidc.providerConfigurationEndpoint(configuration ->
                configuration.providerConfigurationCustomizer(builder -> endpointAliases.contribute(builder::claim))));
    }

    /**
     * Sets the decoder factory and the certificate verifier on the framework's providers.
     *
     * @param providers the providers of the client authentication.
     */
    private void configure(final List<AuthenticationProvider> providers) {
        for (final var provider : providers) {
            if (provider instanceof JwtClientAssertionAuthenticationProvider assertions) {
                assertions.setJwtDecoderFactory(decoderFactory);
            } else if (provider instanceof X509ClientCertificateAuthenticationProvider certificates) {
                certificates.setCertificateVerifier(certificateVerifier);
            }
        }
    }
}

Finding the keys of a client

The factory has two paths. A client with a registered JWK set is verified against those keys; any other client goes through the framework’s factory. Both end with the default assertion validators (issuer, subject, audience, expiry) and then the replay validator. The framework’s factory caches a decoder per client forever, so this one caches its own decoders by client identifier and a hash of the settings that decide the keys. When an administrator replaces a client’s keys, the next assertion is verified against the new ones, not the cached old ones.

/**
 * Creates the decoder of the client assertions of a client. A client with a registered JWK set
 * ({@code settings.client.jwks}) is verified against those keys; any other client goes through the framework's
 * factory, which reads the keys of its {@code jwkSetUrl} (or the shared secret of {@code client_secret_jwt}). Both
 * add the framework's default assertion validators (issuer, subject, audience including the PAR endpoint, expiry)
 * and the {@link ReplayRejectingJwtValidator}. The framework's own factory caches a decoder per client forever, so
 * this one caches the decoders itself, per client identifier and a hash of the settings that decide the keys, and a
 * client whose keys or algorithm were changed is verified against the new ones.
 */
@RequiredArgsConstructor
public class RegisteredJwksClientAssertionDecoderFactory implements JwtDecoderFactory<RegisteredClient> {

    /** Name of the custom client setting that holds the registered public JWK set as JSON. */
    public static final String JWKS_SETTING = "settings.client.jwks";

    /** Most decoders kept. */
    private static final long MAX_DECODERS = 1_000L;

    /** Time an unused decoder is kept. */
    private static final Duration IDLE = Duration.ofMinutes(10);

    /** Separator of the fields hashed into a cache key. */
    private static final char SEPARATOR = '\u0000';

    /** Algorithm of the settings hash. */
    private static final String HASH_ALGORITHM = "SHA-256";

    /** Records the use of an assertion and checks its lifetime. */
    private final ReplayRejectingJwtValidator replayValidator;

    /** Decoders by client and settings hash. */
    private final Cache<String, JwtDecoder> decoders = Caffeine.newBuilder().maximumSize(MAX_DECODERS)
            .expireAfterAccess(IDLE).build();

    /**
     * Returns the decoder of the assertions of a client.
     *
     * @param registeredClient the client that authenticates.
     * @return the decoder, which also rejects a replayed assertion.
     * @throws OAuth2AuthenticationException {@code invalid_client} if the client has registered keys but no signing
     *                                       algorithm, or the keys cannot be read; the framework's factory throws it
     *                                       too when it has no way to find the keys.
     */
    @Override
    public JwtDecoder createDecoder(final RegisteredClient registeredClient) {
        return decoders.get(cacheKey(registeredClient), key -> build(registeredClient));
    }

    /**
     * Builds a decoder.
     *
     * @param registeredClient the client that authenticates.
     * @return the decoder.
     */
    private JwtDecoder build(final RegisteredClient registeredClient) {
        final var validators = validatorsOf(registeredClient);
        final var jwks = registeredClient.getClientSettings().<Object>getSetting(JWKS_SETTING);
        if (!(jwks instanceof String json) || !StringUtils.hasText(json)) {
            final var framework = new JwtClientAssertionDecoderFactory();
            framework.setJwtValidatorFactory(client -> validators);
            return framework.createDecoder(registeredClient);
        }
        final var algorithm = registeredClient.getClientSettings().getTokenEndpointAuthenticationSigningAlgorithm();
        if (algorithm == null) {
            throw invalidClient("The token endpoint signing algorithm of the client is not registered");
        }
        final var signatureAlgorithm = SignatureAlgorithm.from(algorithm.getName());
        if (signatureAlgorithm == null) {
            throw invalidClient("The token endpoint signing algorithm of the client is not an asymmetric one");
        }
        final JWKSet keys;
        try {
            keys = JWKSet.parse(json);
        } catch (ParseException e) {
            throw invalidClient("The registered keys of the client cannot be read");
        }
        final var decoder = NimbusJwtDecoder.withJwkSource(new ImmutableJWKSet<SecurityContext>(keys))
                .jwsAlgorithm(signatureAlgorithm).build();
        decoder.setJwtValidator(validators);
        return decoder;
    }

    /**
     * Combines the default assertion validators with the replay one, failing fast so the replay validator only runs
     * (and only records the {@code jti}) for an assertion that passed every default check.
     *
     * @param registeredClient the client that authenticates.
     * @return the validator.
     */
    private OAuth2TokenValidator<Jwt> validatorsOf(final RegisteredClient registeredClient) {
        final var defaults = JwtClientAssertionDecoderFactory.DEFAULT_JWT_VALIDATOR_FACTORY.apply(registeredClient);
        final var validators = new DelegatingOAuth2TokenValidator<>(defaults, replayValidator);
        validators.setFailOnError(true);
        return validators;
    }

    /**
     * Builds the cache key: the client identifier and the hash of everything that decides which keys verify it.
     *
     * @param registeredClient the client that authenticates.
     * @return the key.
     */
    private static String cacheKey(final RegisteredClient registeredClient) {
        final var settings = registeredClient.getClientSettings();
        final var algorithm = settings.getTokenEndpointAuthenticationSigningAlgorithm();
        final var material = String.join(String.valueOf(SEPARATOR),
                String.valueOf(settings.<Object>getSetting(JWKS_SETTING)),
                String.valueOf(settings.getJwkSetUrl()),
                algorithm == null ? "" : algorithm.getName(),
                String.valueOf(registeredClient.getClientSecret()));
        try {
            final var hash = MessageDigest.getInstance(HASH_ALGORITHM)
                    .digest(material.getBytes(StandardCharsets.UTF_8));
            return registeredClient.getClientId() + SEPARATOR + HexFormat.of().formatHex(hash);
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(HASH_ALGORITHM + " is always available", e);
        }
    }

    /**
     * Builds the {@code invalid_client} error.
     *
     * @param description what is wrong.
     * @return the exception.
     */
    private static OAuth2AuthenticationException invalidClient(final String description) {
        return new OAuth2AuthenticationException(
                new OAuth2Error(OAuth2ErrorCodes.INVALID_CLIENT, description, null));
    }
}

Rejecting a replayed assertion

The framework’s default validators do not require a jti and keep no replay store, so this validator fills the gap (RFC 7523, section 3). It requires jti, iat and exp, refuses an iat in the future, limits exp minus iat to authserver.client-assertion.max-lifetime, and records the use last.

/**
 * Validates what the framework's default assertion validators leave out: the assertion must carry a {@code jti}, an
 * {@code iat} no later than now (within the same clock skew the framework's timestamp validator allows) and an
 * {@code exp} no more than the configured maximum lifetime after it, so a future {@code iat} cannot stretch the
 * window, and its {@code jti} must not
 * have been used before by the same client (RFC 7523, section 3). The use is recorded last, only for an assertion
 * that passed the other checks, so a refused assertion never consumes its identifier. The record is made through
 * {@link RegisterClientAssertionUseCase}, so the replay protection is shared by every instance of the server.
 */
@RequiredArgsConstructor
public class ReplayRejectingJwtValidator implements OAuth2TokenValidator<Jwt> {

    /** Description of the failures. */
    private static final String DESCRIPTION_PREFIX = "The client assertion ";

    /** Clock skew tolerated for {@code iat}, the default of the framework's {@code JwtTimestampValidator}. */
    private static final Duration CLOCK_SKEW = Duration.ofSeconds(60);

    /** Remembers the assertions that were accepted. */
    private final RegisterClientAssertionUseCase registerClientAssertion;

    /** Settings of the client assertions, for the longest lifetime. */
    private final ClientAssertionProperties properties;

    /** Source of the current instant. */
    private final Clock clock;

    /**
     * Checks the assertion and records its use.
     *
     * @param jwt the assertion, already verified for signature, issuer, subject, audience and expiry.
     * @return success, or a failure when the {@code jti}, {@code iat} or {@code exp} is missing, {@code iat} is in
     *         the future, the lifetime is
     *         longer than allowed or the {@code jti} was already used.
     */
    @Override
    public OAuth2TokenValidatorResult validate(final Jwt jwt) {
        if (!StringUtils.hasText(jwt.getId())) {
            return failure("must have a jti");
        }
        final var issuedAt = jwt.getIssuedAt();
        final var expiresAt = jwt.getExpiresAt();
        if (issuedAt == null) {
            return failure("must have an iat");
        }
        if (expiresAt == null) {
            return failure("must have an exp");
        }
        if (issuedAt.isAfter(clock.instant().plus(CLOCK_SKEW))) {
            return failure("is issued in the future");
        }
        final var maxLifetime = properties.maxLifetime();
        if (Duration.between(issuedAt, expiresAt).compareTo(maxLifetime) > 0) {
            return failure("lives longer than " + maxLifetime);
        }
        final var clientId = jwt.getSubject();
        if (!StringUtils.hasText(clientId)) {
            return failure("must have a sub");
        }
        if (!registerClientAssertion.execute(new ClientAssertionUse(clientId, jwt.getId(), expiresAt))) {
            return failure("was already used");
        }
        return OAuth2TokenValidatorResult.success();
    }

    /**
     * Builds a failure.
     *
     * @param reason what is wrong with the assertion.
     * @return the failed result.
     */
    private static OAuth2TokenValidatorResult failure(final String reason) {
        return OAuth2TokenValidatorResult.failure(
                new OAuth2Error(OAuth2ErrorCodes.INVALID_CLIENT, DESCRIPTION_PREFIX + reason, null));
    }
}

Reference: RFC 7523, section 3.

Verifying the client certificate

The framework’s default verifier has no trust anchors of its own, and the dedicated TLS port accepts any chain so the application can decide. The verifier below validates a CA-issued chain with PKIX and compares the subject DN for tls_client_auth, and checks the registered key for self_signed_tls_client_auth. Revocation checking is switched off because it needs a CRL or OCSP endpoint reachable from the server, which the example does not assume. Treat that as a production decision, not a default to copy.

/**
 * Verifies the certificate a client presented on the TLS port (RFC 8705), replacing the framework's verifier, which
 * has no trust anchors of its own.
 * <ul>
 * <li>{@code tls_client_auth}: the chain must validate (PKIX path validation) against the configured trust anchors,
 * and the subject DN of the leaf must equal the one registered for the client. Revocation checking is disabled: it
 * needs a CRL or OCSP endpoint reachable from the server, which this example does not assume. No configured anchor
 * means no client is accepted.</li>
 * <li>{@code self_signed_tls_client_auth}: the certificate must be self-signed and its public key one of the keys of
 * the client's registered JWK set; otherwise the decision is the framework's own (which compares it with the keys of
 * the client's {@code jwkSetUrl}), whose provider is {@code defaultProvider}.</li>
 * </ul>
 * Every refusal is {@code invalid_client}.
 */
@RequiredArgsConstructor
public class ClientCertificateVerifier implements Consumer<OAuth2ClientAuthenticationContext> {

    /** Type of the certification path. */
    private static final String CERTIFICATE_TYPE = "X.509";

    /** Algorithm of the path validation. */
    private static final String PKIX = "PKIX";

    /** The trusted certificate authorities. */
    private final MtlsTrustAnchors trustAnchors;

    /** A default-configured provider of the framework, asked about a self-signed certificate with no registered key. */
    private final AuthenticationProvider defaultProvider;

    /**
     * Verifies the certificate of the client.
     *
     * @param context the client and its authentication.
     * @throws OAuth2AuthenticationException {@code invalid_client} if the certificate is not accepted.
     */
    @Override
    public void accept(final OAuth2ClientAuthenticationContext context) {
        final OAuth2ClientAuthenticationToken authentication = context.getAuthentication();
        final var method = authentication.getClientAuthenticationMethod();
        final var chain = chainOf(authentication);
        if (ClientAuthenticationMethod.TLS_CLIENT_AUTH.equals(method)) {
            verifyCaIssued(context, chain);
        } else if (ClientAuthenticationMethod.SELF_SIGNED_TLS_CLIENT_AUTH.equals(method)) {
            verifySelfSigned(context, authentication, chain);
        } else {
            throw invalidClient();
        }
    }

    /**
     * Verifies a certificate issued by a trusted authority.
     *
     * @param context the client and its authentication.
     * @param chain   the presented chain, the leaf first.
     */
    private void verifyCaIssued(final OAuth2ClientAuthenticationContext context, final X509Certificate[] chain) {
        if (trustAnchors.anchors().isEmpty()) {
            throw invalidClient();
        }
        final var leaf = chain[0];
        // the leaf is the certificate whose key the TLS handshake proved and whose DN is compared below: it must be
        // the first certificate of the validated path, never an anchor left out of it
        if (isAnchor(leaf)) {
            throw invalidClient();
        }
        final var path = Arrays.stream(chain).filter(certificate -> !isAnchor(certificate)).toList();
        try {
            final var parameters = new PKIXParameters(trustAnchors.anchors());
            parameters.setRevocationEnabled(false);
            CertPathValidator.getInstance(PKIX).validate(
                    CertificateFactory.getInstance(CERTIFICATE_TYPE).generateCertPath(path), parameters);
        } catch (GeneralSecurityException e) {
            throw invalidClient();
        }
        final var expected = context.getRegisteredClient().getClientSettings().getX509CertificateSubjectDN();
        if (!StringUtils.hasText(expected) || !expected.equals(leaf.getSubjectX500Principal().getName())) {
            throw invalidClient();
        }
    }

    /**
     * Verifies a self-signed certificate.
     *
     * @param context        the client and its authentication.
     * @param authentication the client authentication.
     * @param chain          the presented chain, the leaf first.
     */
    private void verifySelfSigned(final OAuth2ClientAuthenticationContext context,
                                  final OAuth2ClientAuthenticationToken authentication,
                                  final X509Certificate[] chain) {
        final var leaf = chain[0];
        if (leaf.getIssuerX500Principal().equals(leaf.getSubjectX500Principal())
                && matchesRegisteredKey(context, leaf.getPublicKey())) {
            return;
        }
        // the result is not needed: the provider throws invalid_client when the certificate does not match
        defaultProvider.authenticate(authentication);
    }

    /**
     * Tells whether a key is one of the registered JWK set of the client.
     *
     * @param context the client and its authentication.
     * @param key     the public key of the certificate.
     * @return {@code true} when a registered key equals it.
     */
    private boolean matchesRegisteredKey(final OAuth2ClientAuthenticationContext context, final PublicKey key) {
        final var jwks = context.getRegisteredClient().getClientSettings()
                .<Object>getSetting(RegisteredJwksClientAssertionDecoderFactory.JWKS_SETTING);
        if (!(jwks instanceof String json) || !StringUtils.hasText(json)) {
            return false;
        }
        try {
            for (final JWK jwk : JWKSet.parse(json).getKeys()) {
                if (jwk instanceof AsymmetricJWK asymmetric && Arrays.equals(asymmetric.toPublicKey().getEncoded(),
                        key.getEncoded())) {
                    return true;
                }
            }
            return false;
        } catch (ParseException | JOSEException e) {
            return false;
        }
    }

    /**
     * Tells whether a certificate is itself a trust anchor, which a certification path must not contain.
     *
     * @param certificate the certificate.
     * @return {@code true} when an anchor holds exactly that certificate.
     */
    private boolean isAnchor(final X509Certificate certificate) {
        return trustAnchors.anchors().stream().anyMatch(anchor -> certificate.equals(anchor.getTrustedCert()));
    }

    /**
     * Reads the presented chain.
     *
     * @param authentication the client authentication.
     * @return the chain, the leaf first.
     */
    private static X509Certificate[] chainOf(final Authentication authentication) {
        if (authentication.getCredentials() instanceof X509Certificate[] chain && chain.length > 0) {
            return chain;
        }
        throw invalidClient();
    }

    /**
     * Builds the refusal.
     *
     * @return the {@code invalid_client} exception.
     */
    private static OAuth2AuthenticationException invalidClient() {
        return new OAuth2AuthenticationException(new OAuth2Error(OAuth2ErrorCodes.INVALID_CLIENT));
    }
}

Reference: RFC 8705, section 2, Mutual-TLS Client Authentication.

Restricting the audience of an exchanged token

/**
 * Honours the {@code audience} parameter of a token exchange request, which the framework parses but ignores. The
 * audiences of an exchanged access token are those the exchanging client may have (its
 * {@value IssuedTokenClaims#AUDIENCES_SETTING} setting); when the request names audiences, only the ones among them
 * are kept. An audience outside the list of the client is simply not granted, and when none of the requested ones is
 * allowed the request is refused with {@value #INVALID_TARGET} (RFC 8693, section 2.2.2), so a narrowed request never
 * comes back with every audience of the client. Tokens of any other grant type are not touched.
 */
@Component
@Order(TokenExchangeAudienceContributor.ORDER)
public class TokenExchangeAudienceContributor implements JwtClaimsContributor {

    /** Order of the contributor: after the multi-factor ({@code 100}) and identity provider ({@code 110}) ones. */
    public static final int ORDER = 120;

    /** Error code of an unacceptable target (RFC 8693, section 2.2.2), which the framework has no constant for. */
    public static final String INVALID_TARGET = "invalid_target";

    @Override
    public void contribute(final OAuth2TokenContext context, final Map<String, Object> claims) {
        if (!OAuth2TokenType.ACCESS_TOKEN.equals(context.getTokenType())
                || !AuthorizationGrantType.TOKEN_EXCHANGE.equals(context.getAuthorizationGrantType())
                || !(context.getAuthorizationGrant() instanceof OAuth2TokenExchangeAuthenticationToken exchange)
                || exchange.getAudiences().isEmpty()) {
            return;
        }
        final var allowed = context.getRegisteredClient().getClientSettings()
                .<Object>getSetting(IssuedTokenClaims.AUDIENCES_SETTING) instanceof List<?> audiences
                ? audiences : List.of();
        // a mutable list on purpose: the authorization store only deserializes allow-listed types
        final var granted = allowed.stream().map(String::valueOf).filter(exchange.getAudiences()::contains)
                .collect(Collectors.toCollection(ArrayList::new));
        if (granted.isEmpty()) {
            throw new OAuth2AuthenticationException(new OAuth2Error(INVALID_TARGET,
                    "None of the requested audiences is allowed for the client", null));
        }
        claims.put(OAuth2TokenClaimNames.AUD, granted);
    }
}

The framework parses audience and resource but ignores them, so without this contributor an exchanged token would carry every audience of the client whatever the request said. Reference: RFC 8693, section 2.2.2, the invalid_target error.

The client side: the signing key

For private_key_jwt the converter asks a function for the key of each request. The example reads an unencrypted PKCS#8 PEM RSA key from SERVICE_CLIENT_PRIVATE_KEY or from a file, derives the public half, and declares RS256. Its messages and exceptions never carry any part of the key.

    /**
     * Reads the key and builds its JWK.
     *
     * @param registration the registration the assertion is for, which is not needed to choose the key.
     * @return the signing JWK.
     * @throws IllegalStateException if no key is configured or it cannot be read as an unencrypted PKCS#8 RSA key.
     */
    @Override
    public JWK apply(final ClientRegistration registration) {
        final var pem = readPem();
        if (pem.contains(PKCS1_HEADER)) {
            throw new IllegalStateException("The private key must be PKCS#8 (BEGIN PRIVATE KEY), not PKCS#1");
        }
        try {
            final var der = Base64.getDecoder().decode(pem.replaceAll(PEM_MARKER, "").replaceAll("\\s", ""));
            final var factory = KeyFactory.getInstance("RSA");
            if (!(factory.generatePrivate(new PKCS8EncodedKeySpec(der)) instanceof RSAPrivateCrtKey privateKey)) {
                throw new IllegalStateException("The private key is not an RSA private key with CRT parameters");
            }
            final var publicKey = (RSAPublicKey) factory.generatePublic(
                    new RSAPublicKeySpec(privateKey.getModulus(), privateKey.getPublicExponent()));
            return new RSAKey.Builder(publicKey)
                    .privateKey(privateKey)
                    .keyUse(KeyUse.SIGNATURE)
                    .algorithm(JWSAlgorithm.RS256)
                    .keyID(properties.keyId())
                    .build();
        } catch (final IllegalArgumentException | GeneralSecurityException e) {
            throw new IllegalStateException("The private key is not a valid unencrypted PKCS#8 RSA key", e);
        }
    }

The client side: DPoP

When service-client.auth.dpop is true, the client generates an EC key pair for the life of the process and the token endpoint answers with a DPoP-bound token (token_type DPoP, with cnf.jkt). Spring Security’s interceptor can only send a bearer header, so the example’s interceptor sends Authorization: DPoP and a proof that binds the method, the URI and the token:

    @Override
    public ClientHttpResponse intercept(final HttpRequest request, final byte[] body,
            final ClientHttpRequestExecution execution) throws IOException {
        final var authorizeRequest = OAuth2AuthorizeRequest.withClientRegistrationId(registrationId)
                .principal(principal)
                .build();
        final var authorizedClient = manager.authorize(authorizeRequest);
        if (authorizedClient == null) {
            throw new ClientAuthorizationException(new OAuth2Error(OAuth2ErrorCodes.ACCESS_DENIED,
                    "The service client has no access token", null), registrationId);
        }
        final var token = authorizedClient.getAccessToken();
        if (OAuth2AccessToken.TokenType.DPOP.equals(token.getTokenType())) {
            request.getHeaders().set(HttpHeaders.AUTHORIZATION, DPOP_SCHEME + token.getTokenValue());
            request.getHeaders().set(DPOP_HEADER,
                    proofs.proof(request.getMethod().name(), request.getURI(), token.getTokenValue()));
        } else {
            request.getHeaders().setBearerAuth(token.getTokenValue());
        }
        return execution.execute(request, body);
    }

API

The requests below go to the token endpoint of the example’s default local address. They are the requests the Spring clients of the previous section send, written as curl so each parameter is visible. ${...} values are placeholders; none is a real secret.

Client credentials with a client assertion. The assertion is a JWT you sign with the client’s private key. Its claims are iss and sub equal to the client identifier, aud the token endpoint, a fresh jti, iat, and an exp no more than authserver.client-assertion.max-lifetime after iat. The client sends no client_secret:

curl -s -X POST http://localhost:9000/oauth2/token \
  -d grant_type=client_credentials \
  -d scope=documents.read \
  -d client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer \
  -d client_assertion="${CLIENT_ASSERTION}"

Sending the same assertion twice answers 401 with invalid_client the second time.

Client credentials with mutual TLS. The request goes to the TLS port, with the client certificate and key, and carries client_id as the only identification (RFC 8705, section 2):

curl -s -X POST https://localhost:${MTLS_PORT}/oauth2/token \
  --cacert server-ca.pem --cert client.pem --key client.key \
  -d grant_type=client_credentials \
  -d client_id="${CLIENT_ID}" \
  -d scope=documents.read

When the client is registered with certificate-bound tokens, the access token carries cnf.x5t#S256 with the thumbprint of client.pem, and the resource server accepts it only over a connection that presents that certificate.

Token exchange. The form parameters are those of RFC 8693, section 2.1. The client authenticates as usual (here with client_secret_basic), and its registration must include the grant type urn:ietf:params:oauth:grant-type:token-exchange:

curl -s -X POST http://localhost:9000/oauth2/token \
  -u "${CLIENT_ID}:${CLIENT_SECRET}" \
  -d grant_type=urn:ietf:params:oauth:grant-type:token-exchange \
  -d subject_token="${USER_ACCESS_TOKEN}" \
  -d subject_token_type=urn:ietf:params:oauth:token-type:access_token \
  -d actor_token="${CLIENT_ACCESS_TOKEN}" \
  -d actor_token_type=urn:ietf:params:oauth:token-type:access_token \
  -d requested_token_type=urn:ietf:params:oauth:token-type:access_token \
  -d audience=resource-server \
  -d scope=documents.read

The response is an ordinary token response. Its access token has the user as sub, the client in act, the audience narrowed to the requested ones the client may have, and no refresh token. The contract of the client administration API, which is how these clients are registered, is shown on Registered Clients, API.

Tests

The example covers this feature at several levels. None of these tests carries a tagged region, so they are described here and not pasted:

  • ClientAuthenticationIT (authorization server) runs the real chain against each client authentication method: secret (right and wrong), private_key_jwt with registered keys and with a jwkSetUrl, a replayed jti, an assertion that lives too long, tls_client_auth accepted only for a trusted authority, self_signed_tls_client_auth with a registered and an unregistered key, the certificate thumbprint in the token, and a DPoP-bound token.

  • TokenExchangeIT covers the exchange: a valid subject and actor token (the token is the user’s and the client is the actor), an audience that is not allowed (invalid_target), a client without the grant, a token this server did not issue, and a may_act claim that excludes or names the actor.

  • JdbcClientAssertionReplayRegistryIT runs the registry against the real database: the same pair twice is a replay, the same jti of another client is a first use, concurrent registration has exactly one winner, and the purge removes only expired rows.

  • ServiceClientApplicationIT checks that the application starts with no profile and with each of the client-credentials and token-exchange profiles. ResourceServerAdapterIT checks that a token is reused across calls, that it is renewed when it expires within the margin, that a private_key_jwt assertion is signed with the configured key, that an exchange uses the client token as actor, that DPoP sends the proof and the scheme, and that refusals become a domain exception.

  • ClientCredentialsEndToEndIT and TokenExchangeEndToEndIT start the authorization server and the resource server and run the real service-client as a process: one client per method (secret, private_key_jwt, tls_client_auth, self_signed_tls_client_auth) and DPoP, then the exchange on behalf of a user who signed in through the BFF, ending with the resource server returning that user’s documents. Keys and certificates are generated at run time; none is committed.

Security notes and pitfalls

  • Rotate client keys without downtime. A client may register several public keys in its JWK set, so a new key can be added before the old one is removed and assertions signed with either verify during the overlap. The decoder cache is keyed by a hash of the stored keys, so a change takes effect on the next assertion.

  • Keep the assertion lifetime short. The default maximum is five minutes (PT5M). A short lifetime bounds how long a captured assertion could be replayed and how many jti rows the table must keep.

  • jti replay is enforced in the database. The record is shared by every instance of the server, so a replay is refused even when it lands on another instance. If the table is unreachable, authentication fails, which is the safe direction.

  • Restrict the audience of exchanged tokens. An exchanged token should be usable at one API, not everywhere the client may call. The example narrows aud and refuses the request with invalid_target when nothing requested is allowed. Do not rely on the framework to do it.

  • Use least-privilege scopes. Register a service client with only the scopes it needs, and request only those. The framework refuses scopes outside the registration. A token exchange never widens the scopes of the subject token past those of the exchanging client.

  • Allow token exchange deliberately. The grant is explicit in the client’s registration. A subject token that carries may_act limits which client may act on it. Without may_act any actor token is accepted, so keep the grant to the clients that need it.

  • Pin trust for mutual TLS. With no trusted authority configured, tls_client_auth is refused rather than accepting every chain. Revocation is not checked by the example: add a CRL or OCSP check before relying on this in production. Terminating TLS at a proxy changes where the certificate is seen, so a forwarded certificate must be trusted only from that proxy.

  • Prefer sender-constrained tokens for powerful APIs. A bearer token works for whoever holds it. A certificate-bound or DPoP-bound token is useless to a thief without the certificate or key. The resource server must enforce the binding, as shown on the Protecting APIs page.

  • Never ship client secrets or keys in code. No client identifier of a service, secret, private key or certificate is in the repository. The tool reads the secret and the key from the environment or a file, and tests generate theirs at run time. Unencrypted PKCS#8 keys in an environment variable are acceptable for a demonstration; in production keep the key in a secret store or an HSM and mount it as a file.

  • Prefer private_key_jwt or mTLS over a shared secret for services. The server holds only a public key, so a database leak does not let anyone authenticate as the client.
