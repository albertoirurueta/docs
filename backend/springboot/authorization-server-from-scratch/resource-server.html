Authorization Server from Scratch: Protecting APIs, the Resource Server

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The resource-server application of the example (port 8081) is the smallest of the four: it owns no database, it serves a documents API from memory and its only job is to decide, for every request, whether the bearer token in the Authorization header is acceptable and what it allows. This page walks through that decision. How the tokens are issued is the subject of the authorization server pages; the protocol background of the token itself is in JWT and JOSE and Access and Refresh Tokens.

What you build

A Spring Security resource server with these properties:

  • It validates self-contained JWT access tokens: the signature against the authorization server’s JWKS, the issuer, the expiry and the aud claim. A token without an accepted audience is refused even when its signature is valid.

  • It turns the scope claim into SCOPE_* authorities and the roles claim into ROLE_* authorities.

  • It protects GET /api/documents with the scope documents.read and DELETE /api/documents/{id} with the scope documents.delete, in two places (the filter chain and method security).

  • It restricts every user to their own documents (ownership check), with ROLE_ADMIN as the only exception.

  • Deleting also requires a recent strong authentication (RFC 9470 step-up): the token must carry an accepted acr and a recent auth_time, otherwise the answer is a 401 with an insufficient_user_authentication challenge.

  • It accepts sender-constrained tokens (DPoP, RFC 9449, and certificate-bound, RFC 8705). Those mechanisms are explained on a later page of the guide; this page only shows the single line of configuration that enables them.

  • A second filter chain, active under the opaque Spring profile, validates reference tokens through introspection instead. It is mentioned where it differs and is not listed here; see Opaque Tokens, Introspection and Revocation.

The generic Spring Security mechanics (the SecurityContext built from a JWT, JwtDecoder, authorities) are in Building the SecurityContext from a JWT; this page shows how the example configures them.

How it works

The Mermaid flow below follows one DELETE /api/documents/{id} request, the most demanding one, through the chain.

flowchart TD REQ["Request with Authorization: Bearer token"] --> BT{"Token present and well formed?"} BT -- no --> E401["401, WWW-Authenticate: Bearer (BearerTokenAuthenticationEntryPoint)"] BT -- yes --> SIG{"Signature valid against the JWKS of the issuer?"} SIG -- no --> E401I["401, error=invalid_token"] SIG -- yes --> CLAIMS{"iss, exp and aud accepted?"} CLAIMS -- no --> E401I CLAIMS -- yes --> CONV["JwtAuthenticationConverter: scope to SCOPE_*, roles to ROLE_*"] CONV --> HAS{"Has SCOPE_documents.delete?"} HAS -- no --> E403["403, error=insufficient_scope"] HAS -- yes --> STEP{"StepUpAuthorizationManager: acr accepted and auth_time recent?"} STEP -- no --> E401S["401, error=insufficient_user_authentication, acr_values, max_age"] STEP -- yes --> MS{"@PreAuthorize hasAuthority SCOPE_documents.delete"} MS -- no --> E403 MS -- yes --> OWN{"DeleteDocumentUseCase: owner is the caller, or ROLE_ADMIN?"} OWN -- no --> E404["404, as if the document did not exist"] OWN -- yes --> OK["204 No Content"]

The signature check needs the public keys of the authorization server. Spring Boot builds the JwtDecoder from the issuer-uri property: on the first request it reads the issuer’s OpenID Connect discovery document, finds the jwks_uri (/oauth2/jwks), downloads the keys and caches them, refetching when it meets an unknown kid. The decoder validates iss and exp on its own and, because the example sets audiences, aud too. Nothing in the example code writes a decoder: that is the reason the JwtDecoder bean is absent from the table below.

The resource server has no database. The documents live in memory (resource-server/infrastructure/memory) and the only configuration it needs is the issuer, the accepted audience and the step-up policy, all in its application.yml. The documents it serves are plain records with an id, an owner (the token’s sub), a title and a content.

Code

The filter chain

The chain requires a token for everything except the health endpoint and the OpenAPI document, checks the scope per route and configures how failures are answered. The helper that declares the routes is private and is not part of the listing; in short, GET /api/documents needs SCOPE_documents.read, DELETE /api/documents/* goes through the step-up manager, and any other request only needs to be authenticated. The chain refuses to start without a configured audience, so a missing property can never mean "accept every token".

    /**
     * Builds the filter chain validating bearer JWTs (the decoder is built from {@code issuer-uri}, and the
     * configured audiences are validated by it).
     *
     * @param http       the HTTP security builder.
     * @param properties the resource server properties.
     * @param stepUp     requires a recent strong authentication to delete.
     * @param accessDeniedHandler answers the denials, including the step-up challenge.
     * @return the security filter chain.
     * @throws Exception if the chain cannot be built.
     * @throws IllegalStateException if no accepted audience is configured.
     */
    @Bean
    @Profile("!opaque")
    SecurityFilterChain resourceServerFilterChain(final HttpSecurity http,
            final OAuth2ResourceServerProperties properties, final StepUpAuthorizationManager stepUp,
            final StepUpAccessDeniedHandler accessDeniedHandler) throws Exception {
        requireAudiences(properties.getJwt().getAudiences());
        authorize(http, stepUp);
        http.oauth2ResourceServer(oauth2 -> oauth2
                .jwt(jwt -> jwt.jwtAuthenticationConverter(jwtAuthenticationConverter()))
                // DPoP (RFC 9449): "Authorization: DPoP <token>" plus a proof; the framework already refuses a
                // token whose cnf holds jkt when it arrives as Bearer. A cnf.x5t#S256 token is checked against the
                // TLS client certificate by the validator of the decoder Boot builds (no JwtDecoder bean here).
                .dPoP(Customizer.withDefaults())
                .authenticationEntryPoint(new BearerTokenAuthenticationEntryPoint())
                .accessDeniedHandler(accessDeniedHandler));
        return http.build();
    }

See the Spring Security reference on JWT resource servers and on authorizing HTTP requests.

Authorities from the token

The framework’s default converter maps only scope (or scp) to SCOPE_*. The example wraps it so that the roles claim of the access token also yields ROLE_* authorities (the prefix is added when missing). Scopes say what the client application may do on behalf of the user; roles say who the user is, and the two are checked separately, which is why ROLE_ADMIN alone never grants documents.delete.

    /**
     * Maps the {@code scope} claim to {@code SCOPE_*} authorities (the default converter) and the {@code roles}
     * claim to {@code ROLE_*} authorities.
     *
     * @return the converter.
     */
    JwtAuthenticationConverter jwtAuthenticationConverter() {
        final var scopes = new JwtGrantedAuthoritiesConverter();
        final var converter = new JwtAuthenticationConverter();
        converter.setJwtGrantedAuthoritiesConverter(jwt -> {
            final var authorities = new ArrayList<GrantedAuthority>(scopes.convert(jwt));
            authorities.addAll(BearerAuthorities.roleAuthorities(
                    jwt.getClaimAsStringList(BearerAuthorities.ROLES_CLAIM)));
            return authorities;
        });
        return converter;
    }

See Extracting authorities manually in the Spring Security reference.

Sender-constrained tokens

One call in the chain enables DPoP. A token bound to a key (cnf.jkt) is then accepted only with a matching proof, and the framework already refuses such a token when it arrives as a plain Bearer. A token bound to a client certificate (cnf.x5t#S256) is checked against the TLS client certificate by the validator of the decoder Spring Boot builds. The mechanism and its threats are the subject of a later page of this guide, on sender-constrained tokens; here it is enough to know that a stolen bound token is useless without the key or the certificate.

                // DPoP (RFC 9449): "Authorization: DPoP <token>" plus a proof; the framework already refuses a
                // token whose cnf holds jkt when it arrives as Bearer. A cnf.x5t#S256 token is checked against the
                // TLS client certificate by the validator of the decoder Boot builds (no JwtDecoder bean here).
                .dPoP(Customizer.withDefaults())

See DPoP-bound access tokens, RFC 9449 and RFC 8705.

The documents controller and method security

The controller implements an interface generated from the OpenAPI contract. Listing needs only the scope enforced by the chain and returns the caller’s documents (everyone’s for an administrator). Deleting repeats the scope check with @PreAuthorize, defence in depth against a URL pattern that stops matching.

    /**
     * Lists the documents of the caller; an administrator ({@code ROLE_ADMIN}) sees every document.
     *
     * @return the documents.
     */
    @Override
    public ResponseEntity<List<DocumentResponse>> listDocuments() {
        final var authentication = caller();
        final var documents = BearerAuthorities.isAdministrator(authentication)
                ? listDocumentsUseCase.listAll()
                : listDocumentsUseCase.listOwn(authentication.getName());
        return ResponseEntity.ok(documentDtoMapper.toResponses(documents));
    }

See the Spring Security reference on method security.

    /**
     * Deletes a document of the caller; an administrator ({@code ROLE_ADMIN}) may delete any document. Someone
     * else's document is answered like a missing one, so the answer never reveals that it exists.
     *
     * @param id identifier of the document.
     * @return 204 when the document was deleted, 404 when it does not exist or belongs to someone else.
     */
    @Override
    @PreAuthorize("hasAuthority('SCOPE_documents.delete')")
    public ResponseEntity<Void> deleteDocument(final String id) {
        final var authentication = caller();
        return deleteDocumentUseCase.execute(id, authentication.getName(),
                BearerAuthorities.isAdministrator(authentication))
                ? ResponseEntity.noContent().build()
                : ResponseEntity.notFound().build();
    }

See @PreAuthorize.

The ownership check

Scopes are coarse: documents.delete says the client may delete documents, not whose. The ownership rule is business logic and lives in the use case of the application layer, not in an annotation: the caller deletes the document only when its owner equals the token’s subject, or when the caller is an administrator. When the rule fails the use case returns the same result as for a missing document, which the controller turns into 404, so the API never reveals that someone else’s document exists.

    /**
     * Deletes a document when the caller owns it or is an administrator.
     *
     * @param id            identifier of the document.
     * @param caller        subject of the caller.
     * @param administrator whether the caller is an administrator, who may delete any document.
     * @return {@code true} when the document was deleted, {@code false} when it does not exist or the caller may not
     *         delete it (the two are deliberately indistinguishable).
     */
    public boolean execute(final String id, final String caller, final boolean administrator) {
        // Extension point (#4): the authentication-method check (the `amr` claim of the token, for example to require
        // a multi-factor login) attaches here, before the deletion, as a step-up requirement.
        final var allowed = documentRepository.findById(id)
                .filter(document -> administrator || document.owner().equals(caller))
                .isPresent();
        return allowed && documentRepository.deleteById(id);
    }

See the OWASP API1:2023 Broken Object Level Authorization.

Step-up: the beans

Two beans wire the step-up policy: the manager that decides, and the handler that answers.

    /**
     * Builds the manager that requires a recent strong authentication to delete a document.
     *
     * @param properties the step-up policy.
     * @return the manager.
     */
    @Bean
    StepUpAuthorizationManager stepUpAuthorizationManager(final StepUpProperties properties) {
        return new StepUpAuthorizationManager(DELETE_AUTHORITY, properties, Clock.systemUTC());
    }

    /**
     * Builds the handler that answers the step-up requirement with the RFC 9470 challenge and every other denial
     * with the RFC 6750 one.
     *
     * @param properties the step-up policy.
     * @return the handler.
     */
    @Bean
    StepUpAccessDeniedHandler stepUpAccessDeniedHandler(final StepUpProperties properties) {
        return new StepUpAccessDeniedHandler(new BearerTokenAccessDeniedHandler(), properties);
    }

See Authorization Architecture.

Step-up: the decision

StepUpAuthorizationManager first requires the delete authority (a caller without it gets an ordinary denial, answered 403 insufficient_scope). A caller that has it passes when the policy is disabled, or when the token’s acr is one of the configured values and its auth_time is not older than max-age. Otherwise it returns a dedicated StepUpRequiredDecision, so the handler can tell this denial from any other. The claims are read from the token attributes, which is why the same class serves JWTs and introspected opaque tokens. An acr is matched against the members of the configured space-separated list, never against the list as a whole, and a missing or malformed auth_time fails closed.

@RequiredArgsConstructor
public class StepUpAuthorizationManager implements AuthorizationManager<RequestAuthorizationContext> {

    /** Claim carrying the authentication context class reference. */
    static final String ACR_CLAIM = "acr";

    /** Claim carrying the time of the user's authentication, in epoch seconds. */
    static final String AUTH_TIME_CLAIM = "auth_time";

    /** Separator of the configured {@code acr-values}: any run of whitespace. */
    private static final String ACR_VALUES_SEPARATOR = "\\s+";

    /** Authority the caller needs before the step-up requirement is evaluated. */
    private final String requiredAuthority;

    /** Step-up policy. */
    private final StepUpProperties properties;

    /** Source of the current time. */
    private final Clock clock;

    @Override
    public AuthorizationResult authorize(final Supplier<? extends Authentication> authentication,
            final RequestAuthorizationContext context) {
        final var current = authentication.get();
        if (current == null || !current.isAuthenticated() || current.getAuthorities().stream()
                .noneMatch(authority -> requiredAuthority.equals(authority.getAuthority()))) {
            return new AuthorizationDecision(false);
        }
        if (!properties.enabled() || satisfied(current)) {
            return new AuthorizationDecision(true);
        }
        return new StepUpRequiredDecision();
    }

    /**
     * Tells whether the token proves the required authentication.
     *
     * @param authentication the authenticated bearer token.
     * @return {@code true} when the {@code acr} matches and {@code auth_time} is recent enough.
     */
    private boolean satisfied(final Authentication authentication) {
        if (!(authentication instanceof AbstractOAuth2TokenAuthenticationToken<?> token)) {
            return false;
        }
        final var attributes = token.getTokenAttributes();
        if (!isAccepted(attributes.get(ACR_CLAIM))) {
            return false;
        }
        final var authenticatedAt = toInstant(attributes.get(AUTH_TIME_CLAIM));
        return authenticatedAt != null
                && !authenticatedAt.plus(properties.maxAge()).isBefore(clock.instant());
    }

    /**
     * Tells whether an {@code acr} value is one of the configured ones. The configured {@code acr-values} is a
     * space-separated list, like the {@code acr_values} parameter of OpenID Connect, so the token's single value must
     * be a member of it, never equal to the whole list.
     *
     * @param acr the {@code acr} claim of the token.
     * @return {@code true} when the claim is a text listed in the configured values.
     */
    private boolean isAccepted(final Object acr) {
        return acr instanceof String value
                && Arrays.asList(properties.acrValues().trim().split(ACR_VALUES_SEPARATOR)).contains(value);
    }

    /**
     * Converts an {@code auth_time} value, which is epoch seconds in a JWT or an introspection answer.
     *
     * @param value the claim value.
     * @return the instant, or {@code null} when the value is missing or of an unexpected type.
     */
    private static Instant toInstant(final Object value) {
        return switch (value) {
            case Instant instant -> instant;
            case Number number -> Instant.ofEpochSecond(number.longValue());
            case null, default -> null;
        };
    }
}

See RFC 9470: OAuth 2.0 Step Up Authentication Challenge Protocol.

Step-up: the challenge

The handler turns that decision into the RFC 9470 response: 401 (not 403, because the token is acceptable but insufficient for this request), with the acr_values and max_age the client must ask for when it sends the user back to the authorization server. Every other denial goes to the framework’s RFC 6750 handler, which answers 403 insufficient_scope.

@RequiredArgsConstructor
public class StepUpAccessDeniedHandler implements AccessDeniedHandler {

    /** Handler of every denial that is not a step-up requirement. */
    private final AccessDeniedHandler delegate;

    /** Step-up policy, whose values are advertised in the challenge. */
    private final StepUpProperties properties;

    @Override
    public void handle(final HttpServletRequest request, final HttpServletResponse response,
            final AccessDeniedException accessDeniedException) throws IOException, ServletException {
        if (accessDeniedException instanceof AuthorizationDeniedException denied
                && denied.getAuthorizationResult() instanceof StepUpRequiredDecision) {
            response.setStatus(HttpStatus.UNAUTHORIZED.value());
            response.setHeader(HttpHeaders.WWW_AUTHENTICATE, "Bearer error=\"insufficient_user_authentication\", "
                    + "acr_values=\"" + properties.acrValues() + "\", max_age=\""
                    + properties.maxAge().toSeconds() + "\"");
            return;
        }
        delegate.handle(request, response, accessDeniedException);
    }
}

See RFC 9470, section on the protected resource response.

Step-up: the policy

The policy is bound from resourceserver.step-up.* and validated at startup. The defaults are urn:irurueta:acr:mfa and five minutes, the values also set in application.yml. The authorization server side of the exchange (how a challenged client obtains the new token) is covered by the multi-factor authentication page of this guide.

@ConfigurationProperties("resourceserver.step-up")
public record StepUpProperties(
        @DefaultValue("true") boolean enabled,
        @DefaultValue("urn:irurueta:acr:mfa") String acrValues,
        @DefaultValue("PT5M") Duration maxAge) {

    /**
     * Validates the policy.
     *
     * @throws IllegalArgumentException if {@code acrValues} is blank or {@code maxAge} is not positive.
     */
    public StepUpProperties {
        if (!StringUtils.hasText(acrValues)) {
            throw new IllegalArgumentException("resourceserver.step-up.acr-values must not be blank");
        }
        if (maxAge == null || maxAge.isNegative() || maxAge.isZero()) {
            throw new IllegalArgumentException("resourceserver.step-up.max-age must be positive");
        }
    }
}

See Typesafe Configuration Properties.

API

The contract is resource-server-api-v1.yaml:

  /api/documents:
    get:
      tags: [ documents ]
      operationId: listDocuments
      summary: Lists documents
      description: Lists the caller's documents; an administrator sees all. Needs scope documents.read.
      security:
        - bearer: [ documents.read ]
      responses:
        '200':
          description: The documents.
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/DocumentResponse'
        '401':
          $ref: '#/components/responses/Unauthorized'
        '403':
          description: The token lacks the documents.read scope.
          headers:
            WWW-Authenticate:
              $ref: '#/components/headers/WwwAuthenticate'
  /api/documents/{id}:
    delete:
      tags: [ documents ]
      operationId: deleteDocument
      summary: Deletes a document
      description: >-
        Deletes one of the caller's documents; an administrator may delete any. Needs scope documents.delete and a
        recent strong authentication (RFC 9470). Someone else's document is answered 404, like a missing one.
      security:
        - bearer: [ documents.delete ]
      parameters:
        - name: id
          in: path
          required: true
          description: Unique identifier of the document.
          schema:
            type: string
      responses:
        '204':
          description: The document was deleted.
        '401':
          description: >-
            Missing or invalid bearer token, or (RFC 9470) a valid token that does not prove a recent enough strong
            authentication: its acr claim is not the required one or its auth_time is older than the maximum age.
            The client must send the user through the authorization server again, asking for the acr_values and
            max_age of the challenge.
          headers:
            WWW-Authenticate:
              description: >-
                RFC 6750 bearer challenge. When step-up authentication is required it is
                Bearer error="insufficient_user_authentication", acr_values="urn:irurueta:acr:mfa", max_age="300"
                (the values configured under resourceserver.step-up.*).
              schema:
                type: string
        '403':
          description: The token lacks the documents.delete scope.
          headers:
            WWW-Authenticate:
              $ref: '#/components/headers/WwwAuthenticate'
        '404':
          description: The document does not exist or belongs to someone else.

See the OpenAPI Specification. The following curl calls match it; $TOKEN is an access token for the audience resource-server obtained through the authorization server (the BFF obtains it for the SPA).

# 200 with the caller's documents (scope documents.read)
curl -i -H "Authorization: Bearer $TOKEN" http://localhost:8081/api/documents

# 401 with: WWW-Authenticate: Bearer   (no token)
curl -i http://localhost:8081/api/documents

# 401 with: WWW-Authenticate: Bearer error="invalid_token"   (bad signature, expired, or wrong audience)
curl -i -H "Authorization: Bearer not-a-valid-token" http://localhost:8081/api/documents

# 403 with: WWW-Authenticate: Bearer error="insufficient_scope"   (token without documents.delete)
curl -i -X DELETE -H "Authorization: Bearer $TOKEN" http://localhost:8081/api/documents/42

# 401 with: WWW-Authenticate: Bearer error="insufficient_user_authentication",
#           acr_values="urn:irurueta:acr:mfa", max_age="300"
#   (token has documents.delete but a password-only acr, or a stale auth_time)
curl -i -X DELETE -H "Authorization: Bearer $TOKEN" http://localhost:8081/api/documents/42

# 204 (token with documents.delete, acr urn:irurueta:acr:mfa and auth_time within the last 5 minutes)
curl -i -X DELETE -H "Authorization: Bearer $STEPPED_UP_TOKEN" http://localhost:8081/api/documents/42

A client that receives the step-up challenge must not retry with the same token: it sends the user through the authorization endpoint again with the advertised acr_values and max_age, then repeats the call with the new token. The 404 for a document that is missing or owned by someone else is deliberately the same answer.

Tests

No test of this module carries a tagged region, so none is pasted. The integration tests run the real filter chain with JWTs signed by a key generated at run time (never committed):

  • SecurityConfigIT covers the validation matrix: no token, an invalid token, an accepted audience, another audience and no audience at all, the read and delete scopes, the ownership rules (own document, someone else’s, an administrator), and the step-up cases (password acr, missing claims, old auth_time).

  • StepUpDeletionIT follows the whole story a user goes through: a password-only token is challenged, the same user with a multi-factor token and a recent auth_time deletes the document, and a stale multi-factor authentication is challenged again.

  • BoundTokenIT runs over a real TLS handshake and proves that certificate-bound and DPoP-bound tokens are accepted only with their certificate or proof, and that a DPoP token sent as a plain bearer is refused.

  • OpaqueTokenSecurityIT does the same for the opaque profile against a stub introspection endpoint.

  • OpenApiDriftIT fails when the running API drifts from the OpenAPI contract, and unit tests such as StepUpAuthorizationManagerTest and StepUpAccessDeniedHandlerTest cover the step-up classes in isolation.

Security notes and pitfalls

  • Always check the audience. A signature proves who issued the token, not for whom. Without an aud check, a token issued for another API of the same issuer works here. The chain refuses to start when no audience is configured, and the integration tests cover a token with another audience and with none. See RFC 8725, JWT Best Current Practices.

  • Clock skew. exp and nbf are checked with the framework’s default tolerance of sixty seconds. Keep the clocks of the servers synchronised rather than widening it, and keep access token lifetimes short, because a JWT cannot be revoked before it expires (use reference tokens when you need that).

  • JWKS caching. The decoder caches the keys and refetches when it meets an unknown kid, which is what makes key rotation work without a restart. The authorization server publishes the retired key during an overlap window, as explained on the signing keys page. A resource server that pins one key breaks at the first rotation.

  • The issuer must be exactly what the tokens say. issuer-uri is both where the discovery document is read from and the value iss must have. A mismatch (a trailing slash, another host name) makes every token invalid.

  • Do not authorize by role alone. Use scopes for what the client may do and ownership checks for whose data it is; ROLE_ADMIN widens the ownership check and nothing else.

  • Do not leak existence. Answering 404 for someone else’s document avoids an enumeration oracle that 403 would create.

  • Step-up needs a fresh claim, not a remembered one. The rule compares auth_time with the clock on every request, so an old token cannot be reused after the window. Keep max-age as short as the operation deserves, and note that disabling resourceserver.step-up.enabled lets every caller through.

  • Failures carry no body. The answers expose only the RFC 6750 challenge, so error text never reveals why a signature failed. Log the reason on the server instead.

  • Mind the transport. Bearer tokens are credentials: send them only over TLS, never in a URL, and never log the Authorization header. See RFC 6750.
