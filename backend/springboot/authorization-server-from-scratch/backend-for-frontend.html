Authorization Server from Scratch: Backend-for-Frontend (BFF)

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page documents the second application of the example, bff: a Spring Boot web application that signs the user in with the authorization server, keeps the user’s tokens on the server and serves a small single page application (SPA). The browser only ever holds a session cookie. The theory behind this choice, the browser threat model and the alternatives are in Browser-Based Apps; the way a BFF fits among the other applications is in Architecture.

What you build

The BFF is a confidential OAuth 2.0 client (registration id bff) that uses the authorization code grant with PKCE, and a thin API in front of the resource server:

  • GET /bff/login validates a returnTo path and starts the sign-in.

  • oauth2Login() completes it: it exchanges the code for tokens and stores them, as an authorized client, in the HTTP session. The session lives in PostgreSQL (Spring Session JDBC, bff database) and the browser receives only the cookie __Host-SESSION.

  • GET /bff/user returns the signed-in user as UI-safe claims; GET /api/documents and DELETE /api/documents/{id} call the resource server with the access token of the session and return its answer.

  • POST /bff/logout ends the local session and then the session at the authorization server (RP-initiated logout).

  • The SPA (index.html and app.js, no framework and no build step) is served from the BFF itself, so the browser sees a single origin and CORS never comes into play.

The BFF listens on port 8080, the authorization server on 9000 and the resource server on 8081. The topology is the one the OAuth reference recommends, with the real ports and the real cookie of the example:

flowchart LR subgraph Browser["Browser (untrusted)"] spa["SPA\nindex.html and app.js"] end subgraph BFFApp["bff :8080 (confidential client, bff database)"] bff["oauth2Login() and the /bff and /api endpoints"] sess[("spring_session\n(tokens of the user)")] bff --- sess end as["auth-server :9000"] rs["resource-server :8081"] spa -->|"cookie __Host-SESSION and X-XSRF-TOKEN"| bff spa -.->|"top-level redirects only"| as bff -->|"authorization code, PKCE, client_secret_basic"| as bff -->|"Authorization Bearer, access token of the user"| rs

No arrow that reaches the browser carries an access, refresh or ID token. The browser takes part in the sign-in only through redirects (dotted arrow), which carry the authorization code and, at logout, the ID token hint, but are followed by the browser as top-level navigations and are never readable by a script.

How it works

Sign-in

sequenceDiagram autonumber participant S as Browser (SPA) participant L as BffLoginController participant F as oauth2Login() filters participant A as auth-server :9000 participant R as HttpSession (Spring Session JDBC) S->>L: GET /bff/login?returnTo=/ L->>L: ReturnToValidator.isAllowed(returnTo) L->>R: create session, keep returnTo and the step-up values L-->>S: 302 to /oauth2/authorization/bff (Set-Cookie __Host-SESSION) S->>F: GET /oauth2/authorization/bff F-->>S: 302 to /oauth2/authorize (state, PKCE challenge, acr_values and max_age if any) S->>A: GET /oauth2/authorize A-->>S: sign in, second factor and consent, then 302 to the redirect_uri with the code S->>F: GET /login/oauth2/code/bff (code and state) F->>A: POST /oauth2/token (code, code_verifier, client_secret_basic) A-->>F: access token, refresh token and ID token F->>R: save the authorized client and the OIDC user, change the session id F-->>S: 302 to returnTo (ReturnToAuthenticationSuccessHandler)

BffLoginController runs first, as a plain controller, because the SPA must say where to come back to. It validates the value, keeps it in the session and redirects to Spring Security’s authorization endpoint. Everything after step 4 is oauth2Login(): the authorization request resolver adds PKCE and, if /bff/login received acrValues or maxAge (a step-up, see below), the acr_values and max_age parameters; the login filter verifies state, exchanges the code and stores the result. Spring Security’s default session fixation protection changes the session id when the authentication is established (the example does not configure it), so the id issued at step 4 is not the one that ends up authenticated.

Calling the API

sequenceDiagram autonumber participant S as Browser (SPA) participant C as DocumentsController participant G as RestDocumentGateway participant I as OAuth2ClientHttpRequestInterceptor participant M as OAuth2AuthorizedClientManager participant R as resource-server :8081 S->>C: GET /api/documents (cookie) C->>G: ListDocumentsUseCase, then the gateway G->>I: DocumentsApi call over the RestClient I->>M: authorize the client bff for the user of the request M-->>I: access token (renewed with the refresh token if it expired) I->>R: GET /api/documents with Authorization Bearer R-->>G: 200 documents G-->>S: 200 documents

The SPA never sees the token: it sends its cookie, the BFF finds the session and the authorized client in it, and the interceptor puts the access token on the outgoing request. When the token cannot be obtained or renewed, the gateway raises DocumentsUnauthorizedException, which is answered 401, and the SPA restarts the sign-in. When the resource server answers 401 asking for a stronger or more recent authentication (RFC 9470), the BFF forwards that as a problem detail with the acrValues and maxAge to ask for, and the SPA sends the user to /bff/login with them, which is what the optional parameters of the login endpoint are for. How the resource server decides that is described in the resource server page and in the multi-factor authentication page of this guide.

Logout

sequenceDiagram autonumber participant S as Browser (SPA) participant B as bff :8080 participant A as auth-server :9000 S->>B: POST /bff/logout (form, _csrf parameter) B->>B: CsrfFilter checks the token B->>B: logout handlers clear the XSRF-TOKEN cookie and the security context, and invalidate the session B-->>S: 302 to the end_session_endpoint (id_token_hint, post_logout_redirect_uri) S->>A: GET /connect/logout A-->>S: 302 to the BFF root S->>B: GET / B-->>S: SPA, signed out

The SPA submits a real form so that the browser itself follows the redirect: the URL carries the ID token hint, and a fetch call would hand it to the script. The authorization server’s side of the protocol is described in Logout and Session Management.

Data

The BFF has its own database, bff, and a single Flyway migration, V300__spring_session.sql. Spring Session JDBC keeps the HTTP session there, and the serialized authorized client (with the access, refresh and ID tokens) is one of the session attributes. The schema is owned by Flyway, so spring.session.jdbc.initialize-schema is never.

Code

The security filter chain

One SecurityFilterChain secures the whole application. It permits the SPA’s static files and /bff/login, requires authentication for the rest, enables the CSRF cookie, sets a same-origin content security policy, answers 401 instead of a redirect to a login page for /bff/** and /api/** (the SPA is not a browser navigation there), and configures oauth2Login() and the logout.

    /**
     * Builds the BFF filter chain.
     *
     * @param http                 the HTTP security builder.
     * @param clientRepository     the registered OAuth2 clients.
     * @param loginSuccessHandler  sends the browser back to the {@code returnTo} of the login once signed in.
     * @param logoutSuccessHandler redirects the browser to the RP-initiated logout of the authorization server.
     * @return the security filter chain.
     * @throws Exception if the chain cannot be built.
     */
    @Bean
    SecurityFilterChain bffFilterChain(final HttpSecurity http, final ClientRegistrationRepository clientRepository,
            final ReturnToAuthenticationSuccessHandler loginSuccessHandler,
            final OidcClientInitiatedLogoutSuccessHandler logoutSuccessHandler) throws Exception {
        final var defaultResolver = new DefaultOAuth2AuthorizationRequestResolver(clientRepository,
                "/oauth2/authorization");
        // The auth server requires PKCE; Spring only enables it by default for public clients.
        defaultResolver.setAuthorizationRequestCustomizer(OAuth2AuthorizationRequestCustomizers.withPkce());
        // A login started for step-up (GET /bff/login with acrValues / maxAge) also asks for acr_values and max_age.
        final var resolver = new StepUpAuthorizationRequestResolver(defaultResolver);

        http.authorizeHttpRequests(authorize -> authorize
                        .requestMatchers("/", "/index.html", "/favicon.ico", "/assets/**", "/static/**", "/error",
                                "/bff/login", "/actuator/health/**").permitAll()
                        .anyRequest().authenticated())
                // The XSRF-TOKEN cookie is readable by the script (not HttpOnly) and the raw token is accepted from
                // the X-XSRF-TOKEN header or, for the sign-out form, from the _csrf parameter. The plain handler, not
                // csrf.spa()'s XOR one: masking against BREACH protects a token rendered in a compressed response body,
                // and the BFF never renders it in a body, only in the cookie; the XOR handler would also reject the
                // raw cookie value the sign-out form posts.
                .csrf(csrf -> csrf
                        .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
                        .csrfTokenRequestHandler(new CsrfTokenRequestAttributeHandler()))
                // The SPA is made of same-origin files only: no inline script, no third-party content, no framing.
                .headers(headers -> headers.contentSecurityPolicy(
                        csp -> csp.policyDirectives(CONTENT_SECURITY_POLICY)))
                .addFilterAfter(new CsrfCookieFilter(), CsrfFilter.class)
                .exceptionHandling(ex -> ex.defaultAuthenticationEntryPointFor(
                        new HttpStatusEntryPoint(HttpStatus.UNAUTHORIZED),
                        new OrRequestMatcher(PathPatternRequestMatcher.withDefaults().matcher("/bff/**"),
                                PathPatternRequestMatcher.withDefaults().matcher("/api/**"))))
                .oauth2Login(login -> login
                        .authorizationEndpoint(endpoint -> endpoint.authorizationRequestResolver(resolver))
                        // A refused consent or any other failed sign-in lands on the SPA, which tells the user.
                        // A handler rather than failureUrl: that would make the generated login page answer it.
                        .failureHandler(new SimpleUrlAuthenticationFailureHandler(SIGN_IN_FAILURE_URL))
                        // Back to the returnTo validated by GET /bff/login, never to a request saved elsewhere.
                        .successHandler(loginSuccessHandler))
                // POST /bff/logout (CSRF protected) runs the logout handlers (the XSRF-TOKEN cookie is cleared, the
                // security context too, and the session is invalidated), then the success handler answers 302 to the
                // end_session_endpoint of the authorization server: the browser follows it as a top-level navigation,
                // so the id_token_hint it carries never reaches a script.
                .logout(logout -> logout
                        .logoutRequestMatcher(PathPatternRequestMatcher.withDefaults()
                                .matcher(HttpMethod.POST, LOGOUT_PATH))
                        .logoutSuccessHandler(logoutSuccessHandler));
        return http.build();
    }

This derives from the Spring Security OAuth2 Login reference and from its single-page application CSRF section.

The comments in the listing carry two decisions. First, PKCE is switched on explicitly because the authorization server requires it and Spring enables it by default only for public clients. Second, the plain CsrfTokenRequestAttributeHandler is used instead of the XOR handler of csrf.spa(): masking protects against BREACH a token that is rendered in a compressed response body, and the BFF only puts it in a cookie; the XOR handler would also reject the raw cookie value that the sign-out form posts.

Where the tokens are kept

The two beans below decide where the user’s tokens live. The repository keeps them in the HTTP session (which Spring Session persists), so the BFF needs no token table of its own; the manager is the object everything else asks for the access token.

    /**
     * Keeps the authorized clients (the tokens of the signed-in user) in the HTTP session, which Spring Session JDBC
     * persists, so no table of its own is needed and the tokens never reach the browser.
     *
     * @return the repository of authorized clients.
     */
    @Bean
    OAuth2AuthorizedClientRepository authorizedClientRepository() {
        return new HttpSessionOAuth2AuthorizedClientRepository();
    }

    /**
     * Builds the manager that obtains the access token of the signed-in user and renews it with its refresh token when
     * it expires.
     *
     * @param clientRepository           the registered OAuth2 clients.
     * @param authorizedClientRepository where the authorized clients are kept.
     * @return the authorized client manager, with the {@code authorization_code} and {@code refresh_token} providers.
     */
    @Bean
    OAuth2AuthorizedClientManager authorizedClientManager(final ClientRegistrationRepository clientRepository,
            final OAuth2AuthorizedClientRepository authorizedClientRepository) {
        final var manager = new DefaultOAuth2AuthorizedClientManager(clientRepository, authorizedClientRepository);
        manager.setAuthorizedClientProvider(OAuth2AuthorizedClientProviderBuilder.builder()
                .authorizationCode()
                .refreshToken()
                .build());
        return manager;
    }

This derives from the Spring Security Authorized Clients reference, which describes the repository and the manager.

Starting the login

    /**
     * Validates {@code returnTo}, keeps it in the session for {@link ReturnToAuthenticationSuccessHandler}, which sends
     * the browser there once the OAuth2 login succeeds, keeps the step-up values (if any) for
     * {@link StepUpAuthorizationRequestResolver}, which adds them to the authorization request, and redirects to the
     * authorization request. The format and range of {@code acrValues} and {@code maxAge} are checked by the generated
     * interface.
     *
     * @param returnTo  relative path to return to after the login; the root of the application when absent.
     * @param acrValues authentication context classes to ask the authorization server for; none when absent.
     * @param maxAge    maximum age, in seconds, of the authentication to ask for; none when absent.
     * @return a redirect to the authorization request.
     * @throws ResponseStatusException answered 400 when {@code returnTo} is not an allowed relative path.
     */
    @Override
    public ResponseEntity<Void> login(final String returnTo, final String acrValues, final Long maxAge) {
        final var target = StringUtils.hasText(returnTo) ? returnTo : DEFAULT_RETURN_TO;
        if (!returnToValidator.isAllowed(target)) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "returnTo is not an allowed relative path");
        }
        final var session = request.getSession();
        session.setAttribute(ReturnToAuthenticationSuccessHandler.RETURN_TO_ATTRIBUTE, target);
        if (StringUtils.hasText(acrValues) || maxAge != null) {
            session.setAttribute(StepUpAuthorizationRequestResolver.STEP_UP_ATTRIBUTE,
                    new StepUpLoginParameters(StringUtils.hasText(acrValues) ? acrValues : null, maxAge));
        } else {
            session.removeAttribute(StepUpAuthorizationRequestResolver.STEP_UP_ATTRIBUTE);
        }
        return ResponseEntity.status(HttpStatus.FOUND).location(URI.create(AUTHORIZATION_PATH)).build();
    }

This follows the OAuth2 Login advanced configuration (a custom authorization endpoint) and the redirect safety advice of the OAuth 2.0 Security Best Current Practice.

The login is a navigation, not a fetch call: the SPA sets window.location to /bff/login. returnTo is the only input that can turn this endpoint into an open redirect, so ReturnToValidator accepts only a relative path that is listed in bff.login.allowed-return-paths (/ and /index.html in application.yml): no scheme, no authority, no //, no backslash, no control character, no dot segments and no percent-encoding.

/**
 * Sends the browser, once the OAuth2 login has succeeded, back to the {@code returnTo} that {@link BffLoginController}
 * validated and kept in the session. The attribute is read once and removed, and validated again by
 * {@link ReturnToValidator} before it is used, so a value that reached the session any other way can never become an
 * open redirect; when it is absent or not allowed, the browser goes to the root of the application.
 */
@Component
@RequiredArgsConstructor
public class ReturnToAuthenticationSuccessHandler extends SimpleUrlAuthenticationSuccessHandler {

    /** Session attribute, owned by the BFF, holding the validated {@code returnTo} of the login in progress. */
    public static final String RETURN_TO_ATTRIBUTE = ReturnToAuthenticationSuccessHandler.class.getName()
            + ".RETURN_TO";

    /** Where the browser goes when there is no allowed {@code returnTo}: the root of the application. */
    static final String DEFAULT_TARGET = "/";

    /** Decides which {@code returnTo} values are safe. */
    private final ReturnToValidator returnToValidator;

    /**
     * Takes the {@code returnTo} out of the session and decides where the browser goes.
     *
     * @param request        the request of the login callback.
     * @param response       the response.
     * @param authentication the new authentication.
     * @return the validated {@code returnTo}, or {@link #DEFAULT_TARGET}.
     */
    @Override
    protected String determineTargetUrl(final HttpServletRequest request, final HttpServletResponse response,
            final Authentication authentication) {
        final var session = request.getSession(false);
        if (session == null) {
            return DEFAULT_TARGET;
        }
        final var returnTo = session.getAttribute(RETURN_TO_ATTRIBUTE);
        session.removeAttribute(RETURN_TO_ATTRIBUTE);
        return returnTo instanceof String target && returnToValidator.isAllowed(target) ? target : DEFAULT_TARGET;
    }
}

This is a customization of the success handler described in the OAuth2 Login advanced configuration. It reads the attribute once, removes it and validates it again, so a value that reached the session by any other route can never become a redirect.

The session cookie

    /**
     * Builds the serializer of the session cookie: Secure, HttpOnly, SameSite=Lax, path {@code /} and no domain, which
     * is exactly what the {@code __Host-} prefix demands (the browser rejects the cookie otherwise).
     *
     * @return the cookie serializer.
     */
    @Bean
    CookieSerializer cookieSerializer() {
        final var serializer = new DefaultCookieSerializer();
        serializer.setCookieName(COOKIE_NAME);
        serializer.setUseSecureCookie(true);
        serializer.setUseHttpOnlyCookie(true);
        serializer.setSameSite("Lax");
        serializer.setCookiePath("/");
        return serializer;
    }

This derives from the Spring Session HTTP session reference, which describes the CookieSerializer.

The prefix __Host- makes the browser accept the cookie only when it is Secure, has Path=/ and has no Domain attribute, so a sibling subdomain cannot overwrite or shadow it. HttpOnly hides it from scripts, and SameSite=Lax keeps it off cross-site sub-requests while still allowing the top-level redirects of the sign-in. The class does not use @EnableJdbcHttpSession on purpose: that annotation switches Spring Boot’s session auto-configuration off, with every spring.session.* property (the schema initialization and the timeout among them). The Boot behavior is described in Spring Boot Spring Session support.

Relaying calls to the resource server

The example does not use Spring Cloud Gateway’s TokenRelay filter. The BFF is a servlet application whose /api/documents operations are written as a contract (bff-api-v1.yaml) and implemented by ordinary controllers, use cases and a gateway, so a hand-written relay fits: the resource server is called through a client generated from its own contract, on top of a RestClient whose interceptor adds the token. That keeps the BFF’s API explicit (the SPA can only reach the operations the contract lists, not an arbitrary proxied path), lets each failure become a domain exception and a problem detail, and avoids adding a reactive gateway to a servlet application. A gateway is the better choice when a BFF has to proxy many routes without an API of its own.

    /**
     * Builds the REST client of the resource server. Its interceptor asks the authorized client manager for the access
     * token of the user of the current request (renewing it with the refresh token when it expired) and sets it as the
     * bearer token of the outgoing request; a call whose session has no token is never sent. When the token cannot be
     * obtained or renewed it throws an {@link org.springframework.security.oauth2.core.OAuth2AuthorizationException},
     * which {@link RestDocumentGateway} reports as {@link
     * com.irurueta.authserver.bff.domain.documents.DocumentsUnauthorizedException}, answered 401 so the SPA signs in
     * again.
     *
     * @param builder the builder of REST clients, the one test slices bind a mock server to.
     * @param manager the manager of the authorized clients of the session.
     * @return the REST client of the resource server.
     */
    @Bean
    RestClient resourceServerRestClient(final RestClient.Builder builder, final OAuth2AuthorizedClientManager manager) {
        final var interceptor = new OAuth2ClientHttpRequestInterceptor(manager);
        interceptor.setClientRegistrationIdResolver(request -> REGISTRATION_ID);
        // The OAuth2 interceptor lets the call through unauthenticated when the session has no authorized client;
        // the BFF must never do that, so the call stops here and the SPA gets a 401.
        return builder.requestInterceptor(interceptor).requestInterceptor((request, body, execution) -> {
            if (!request.getHeaders().containsHeader(HttpHeaders.AUTHORIZATION)) {
                throw new ClientAuthorizationException(new OAuth2Error(OAuth2ErrorCodes.ACCESS_DENIED,
                        "The session has no access token", null), REGISTRATION_ID);
            }
            return execution.execute(request, body);
        }).build();
    }

This derives from the Spring Security RestClient support and the Javadoc of OAuth2ClientHttpRequestInterceptor. The generated client is built on that RestClient:

This uses the Spring Framework RestClient as the transport of a client generated by OpenAPI Generator.

The interceptor of Spring Security lets a call through without a token when the session has no authorized client. That is correct for a generic client and wrong for a BFF, so the example adds a second interceptor that throws when the Authorization header is missing. The gateway translates every failure of the call into a domain exception:

    /**
     * Calls the resource server and translates its failures into domain exceptions.
     *
     * @param operation the call.
     * @param <T>       type of the answer.
     * @return the answer of the resource server.
     */
    private <T> T call(final Supplier<T> operation) {
        try {
            return operation.get();
        } catch (final OAuth2AuthorizationException e) {
            log.warn("No access token for the resource server: {}", e.getError().getErrorCode());
            throw new DocumentsUnauthorizedException("The session has no valid token", e);
        } catch (final RestClientResponseException e) {
            throw translate(e);
        } catch (final RestClientException e) {
            log.warn("The resource server cannot be reached: {}", e.getClass().getSimpleName());
            throw new DocumentsUnavailableException("The resource server is unavailable", e);
        }
    }

This is the outbound adapter of the hexagonal layout described in Architectural Patterns; the exception types it throws are mapped to 401, 403, 404 and 502 problem details by the web adapter.

The signed-in user

    /**
     * Returns the subject of the authenticated user. The security chain answers 401 before reaching this method when
     * nobody is signed in, so the principal of the security context is always the OIDC user of the session.
     *
     * @return the signed-in user's subject.
     * @throws AuthenticationCredentialsNotFoundException if no OIDC user is signed in, answered 401 by the chain.
     */
    @Override
    public ResponseEntity<SessionUserResponse> getSessionUser() {
        final var authentication = SecurityContextHolder.getContext().getAuthentication();
        if (authentication == null || !(authentication.getPrincipal() instanceof final OidcUser user)) {
            throw new AuthenticationCredentialsNotFoundException("No OpenID Connect user is signed in");
        }
        return ResponseEntity.ok(sessionUserDtoMapper.toResponse(user));
    }

This derives from the OAuth2 Login reference, whose OidcUser principal it reads.

The response contains only UI-safe claims (subject, name, email, roles) mapped from the ID token; it never contains a token. A 401 here is how the SPA learns that nobody is signed in.

This derives from the Spring Security Logout reference. Only POST is matched, so the endpoint is CSRF-protected like any other state-changing request.

const XSRF_COOKIE = 'XSRF-TOKEN';
const XSRF_PARAMETER = '_csrf';

/** Media types the documents API answers: its JSON results and its problem details. */
const JSON_OR_PROBLEM = 'application/json, application/problem+json';

/**
 * Finds an element of the page by its id.
 *
 * @param {string} id the id of the element.
 * @returns {HTMLElement} the element.
 */
const element = (id) => document.getElementById(id);

/**
 * Reads a cookie the script is allowed to see (the session cookie is HttpOnly and never visible).
 *
 * @param {string} name the name of the cookie.
 * @returns {string} the decoded value, or an empty string if the cookie is missing.
 */
const readCookie = (name) => {
    const prefix = `${name}=`;
    const entry = document.cookie.split('; ').find((cookie) => cookie.startsWith(prefix));
    return entry ? decodeURIComponent(entry.substring(prefix.length)) : '';
};

/**
 * Shows an error in the live region the screen readers announce, or clears it.
 *
 * @param {string} message the message, or an empty string to clear it.
 */
const showError = (message) => {
    const error = element('error');
    error.textContent = message;
    error.hidden = message === '';
};

/**
 * Sends the browser to the BFF login, asking to come back to the current page afterwards.
 */
const login = () => {
    const returnTo = window.location.pathname === '/index.html' ? '/index.html' : '/';
    window.location.assign(`/bff/login?returnTo=${encodeURIComponent(returnTo)}`);
};

/**
 * Shows the signed-out state, with the button that starts the sign-in. Nothing is started automatically: right after a
 * sign-out the authorization server sends the browser back here, and an automatic redirect would sign it in again.
 */
const showSignedOut = () => {
    element('status').textContent = 'You are signed out.';
    element('profile').hidden = true;
    element('documents').hidden = true;
    element('signed-out').hidden = false;
};

/**
 * Fills the profile card with the signed-in user.
 *
 * @param {{subject: string, name: string, email: string, roles: string[]}} user the user of the session.
 */
const showProfile = (user) => {
    element('profile-name').textContent = user.name ?? '';
    element('profile-email').textContent = user.email ?? '';
    element('profile-subject').textContent = user.subject ?? '';
    element('profile-roles').textContent = (user.roles ?? []).join(', ');
    element('status').textContent = `Signed in as ${user.name || user.subject}.`;
    element('profile').hidden = false;
};

/**
 * Renders the documents the API returned.
 *
 * @param {{id: string, title: string, content: string}[]} documents the documents.
 */
const showDocuments = (documents) => {
    const list = element('documents-list');
    list.replaceChildren(...documents.map((doc) => {
        const item = window.document.createElement('li');
        const title = window.document.createElement('strong');
        title.textContent = doc.title;
        item.append(title, `: ${doc.content}`);
        return item;
    }));
    element('documents-empty').hidden = documents.length > 0;
    element('documents').hidden = false;
};

/**
 * Asks the BFF for the user of the session, and shows the signed-out state when there is none.
 */
const loadUser = async () => {
    const response = await fetch('/bff/user', {credentials: 'same-origin', headers: {Accept: 'application/json'}});
    if (response.status === 401) {
        showSignedOut();
        return;
    }
    if (!response.ok) {
        throw new Error(`The session could not be read (${response.status}).`);
    }
    showProfile(await response.json());
};

/**
 * Loads the documents through the BFF, which asks the resource server with the access token of the user. A 401 here
 * means the session of a signed-in user has ended (or its token could not be renewed), so the sign-in starts again.
 */
const loadDocuments = async () => {
    showError('');
    // The BFF answers its failures as RFC 9457 problem details; asking for both types gets application/problem+json.
    const response = await fetch('/api/documents', {credentials: 'same-origin', headers: {Accept: JSON_OR_PROBLEM}});
    if (response.status === 401) {
        login();
        return;
    }
    if (!response.ok) {
        throw new Error(`The documents could not be loaded (${response.status}).`);
    }
    showDocuments(await response.json());
};

/**
 * Signs out with a top-level form POST, so that the browser itself follows the redirect of the BFF to the logout of the
 * authorization server: that URL carries the ID token hint, which a script must never read. A form cannot send a
 * header, so the CSRF token travels as the _csrf parameter.
 */
const signOut = () => {
    showError('');
    const form = window.document.createElement('form');
    form.method = 'post';
    form.action = '/bff/logout';
    form.hidden = true;
    const token = window.document.createElement('input');
    token.type = 'hidden';
    token.name = XSRF_PARAMETER;
    token.value = readCookie(XSRF_COOKIE);
    form.append(token);
    window.document.body.append(form);
    form.submit();
};

/**
 * Runs an action from a button, disabling it meanwhile and reporting a failure in the live region.
 *
 * @param {HTMLButtonElement} button the button that triggered the action.
 * @param {() => Promise<void>} action the action.
 */
const run = async (button, action) => {
    button.disabled = true;
    try {
        await action();
    } catch (error) {
        showError(error.message);
    } finally {
        button.disabled = false;
    }
};

const loadButton = element('load-documents');
const signOutButton = element('sign-out');
const signInButton = element('sign-in');
loadButton.addEventListener('click', () => run(loadButton, loadDocuments));
signOutButton.addEventListener('click', () => run(signOutButton, async () => signOut()));
signInButton.addEventListener('click', login);

// The heading takes the focus so a screen reader starts reading from the top of the page.
element('main-heading').focus();
if (new URLSearchParams(window.location.search).has('error')) {
    // The sign-in failed or was cancelled (for example, the consent was denied): say so instead of looping to the login.
    element('status').textContent = '';
    showError('Sign-in failed or was cancelled. No session was created.');
    element('retry').hidden = false;
} else {
    loadUser().catch((error) => {
        element('status').textContent = '';
        showError(error.message);
    });
}

This follows the SPA pattern of the IETF OAuth 2.0 for Browser-Based Applications (RFC 10017), section on the BFF: the script only calls same-origin endpoints with credentials: 'same-origin'. Four details are worth reading:

  • The script cannot see the session cookie (it is HttpOnly); the only cookie it reads is XSRF-TOKEN.

  • A 401 from /bff/user means signed out and shows a button; nothing redirects automatically, because right after a logout the authorization server sends the browser back to this page and an automatic redirect would sign the user in again.

  • A 401 from /api/documents means the session or its token ended, so the script starts the sign-in again.

  • Sign-out is a top-level form POST with the CSRF token in the _csrf field, since a form cannot set a header.

The page itself is the SPA’s whole interface; the sign-in and logout pages belong to the authorization server and are described in the login and consent pages of this guide.

  /bff/login:
    get:
      tags: [ Login ]
      operationId: login
      summary: Starts the login
      description: >-
        Redirects the browser to the OpenID Connect authorization request of the authorization server. Once the user
        has signed in, the BFF sends the browser back to returnTo (or to the root of the application when it is
        absent). The SPA navigates to this endpoint; it is not called through fetch.
      security: [ ]
      parameters:
        - name: returnTo
          in: query
          required: false
          description: >-
            Relative path (with an optional query string) of the SPA page to return to after the login. It must be
            one of the paths listed in bff.login.allowed-return-paths; anything else (absolute URLs, scheme-relative
            URLs starting with //, backslashes, control characters) is rejected to prevent open redirects.
          schema:
            type: string
            maxLength: 2048
            examples:
              - /orders
        - name: acrValues
          in: query
          required: false
          description: >-
            Space-separated authentication context class references the authorization server must satisfy, sent as
            the acr_values parameter of the authorization request. The SPA copies it from the acrValues of a
            step-up-required problem (RFC 9470) so the user signs in again with a strong enough authentication.
            Absent, the authorization request carries no acr_values.

          in: query
          required: false

            Maximum age, in seconds, of the user's authentication, sent as the max_age parameter of the authorization

            type: integer

Tests

The example has no tagged test for the BFF, so the tests are described here and not shown. Every *IT runs the whole application, with a Testcontainers PostgreSQL where it needs a database:

  • BffSessionIT proves that signing in stores the session in spring_session, hands the browser the __Host- cookie with its attributes, and that Spring Boot’s session auto-configuration (and so spring.session.*) is in effect.

  • SecurityConfigIT exercises the filter chain: PKCE on the authorization request, the step-up parameters (and a 400 for invalid ones), the redirect of a failed sign-in, 401 for an anonymous /api/** call, the readable XSRF-TOKEN cookie, a 403 for a POST without a valid CSRF token, and the logout (POST only, from a form with the raw token).

  • UserControllerIT and DocumentsApiIT call /bff/user and /api/documents through the whole chain; the resource server is a MockRestServiceServer bound to the RestClient.Builder, so the relay, the token handling and the error translation are tested without a second application.

  • SpaStaticResourcesIT checks that the SPA’s files are served.

  • OpenApiDriftIT compares the running application with bff-api-v1.yaml.

  • The unit tests next to each class cover the returnTo validator, the step-up resolver, the CSRF cookie filter and the mappers; the Playwright test in e2e-tests signs in through the real stack.

The mocking technique is described in the Spring Framework client-side REST test support.

Security notes and pitfalls

  • Tokens never reach the browser. The access, refresh and ID tokens stay in the server-side session. The two places where a token could leak are the logout redirect (it carries id_token_hint, hence the top-level form post instead of fetch) and the SPA’s error handling (the script only ever shows a generic message). XSS is still dangerous in a BFF: a script can call /api/** with the cookie. That is why the content security policy allows same-origin resources only (default-src 'self'; frame-ancestors 'none') and why the SPA has no inline script and no third-party content.

  • CSRF with a SPA. Cookie authentication means every state-changing request is a CSRF target. The token is in the XSRF-TOKEN cookie, readable by the script (not HttpOnly, by design), and must come back in the X-XSRF-TOKEN header or the _csrf form field. SameSite=Lax is defence in depth, not a replacement. See the OWASP CSRF Prevention Cheat Sheet.

  • Cookie attributes. __Host- requires Secure, Path=/ and no Domain; the browser rejects a cookie that does not meet them. In development a browser treats localhost as a secure context for this purpose, but a development setup served over plain HTTP on another host name will not keep the cookie. See Set-Cookie on MDN.

  • Session fixation. The session is created before the user is authenticated (it holds returnTo, the PKCE verifier and state), so the session id must change at login. Spring Security’s default does that; do not disable it. See session fixation protection.

  • Open redirects. returnTo is validated twice (when the login starts and when it completes) against an allow-list. Never redirect to a value taken from a request without such a check.

  • Refresh handling. The OAuth2AuthorizedClientManager renews the access token with the refresh token when it expires. The authorization server rotates refresh tokens and detects reuse (see the tokens page of this guide), so a renewal that fails (for example after a reuse was detected) leaves the session without a usable token: the example answers 401 and the SPA signs in again. A failed renewal must end the session’s use of the token, never fall back to an unauthenticated call (hence the second interceptor).

  • Back-channel and session lifetime. The BFF session and the authorization server session are independent: ending one does not end the other, which is why logout goes through RP-initiated logout. The session timeout is the Boot spring.session.timeout, and expired rows are removed by Spring Session’s cleanup.

  • Secrets. BFF_CLIENT_SECRET comes from the environment and is never committed. The example is never deployed; do not reuse its development values.

For the general guidance see the IETF OAuth 2.0 for Browser-Based Applications and the OAuth 2.0 Security Best Current Practice.
