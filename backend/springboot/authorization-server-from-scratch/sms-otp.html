Authorization Server from Scratch: SMS One-Time Codes

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

What you build

This page adds the SMS channel to the one-time-token machinery of the example. A user first verifies a phone number: the server sends a code by SMS, the user types it back and the number is stored as the account’s verified phone. From then on the number can be used in two ways:

  • SMS login: on the sign-in page the user asks for a code by SMS and posts it, with no password. The sign-in is a primary factor that is reported as amr sms.

  • SMS as a second factor: after the password, the second-factor page offers "Send me a code by SMS", and the tokens then carry sms, otp and mfa.

A verified phone is also a confirmed second factor: as soon as an account has one, multi-factor authentication is required for it, even for clients that do not ask for it (see the Multi-Factor Authentication & Step-Up page of this guide).

The theory is in the OAuth Reference section SMS one-time code (OTP) and, for the second factor, E-mail or SMS OTP as a second factor. NIST SP 800-63B classes the public switched telephone network (SMS and voice) as a restricted authenticator: it is still permitted, but the verifier has to offer an alternative, warn the user about its limits and take the risk of SIM changes and number porting into account. See NIST SP 800-63B-4, in particular the section on authentication using the public switched telephone network. The example treats SMS as a fallback with guard rails, not as a default, which is why most of this page is about limits.

The code generation, hashing, single-use and attempt-counting machinery is the same as for e-mail codes, and it is explained once in E-mail OTP and Magic Links. This page covers only what SMS adds: the phone number, the gateway, the cost control and the account page.

How it works

Phone verification

A user adds a number on the account page (/account/phone) or through the REST API. The number is normalised to E.164, the country is checked against an allow-list, a code is hashed and stored as a pending verification, and the SMS is sent after the transaction commits. The number only becomes the verified phone when the code is confirmed.

sequenceDiagram autonumber actor U as User participant P as PhonePageController participant S as StartPhoneEnrolmentUseCase participant C as SendSmsOneTimeCodeUseCase participant L as sms_cost_ledger participant E as OttDeliveryListener participant G as SmsSender participant V as ConfirmPhoneUseCase participant DB as user_phones U->>P: POST /account/phone (number) P->>P: Step-up check, then rate limit per address and per account P->>S: execute(userId, number) S->>S: Normalise to E.164, check the country allow-list S->>DB: Save the pending number with the hashed code S->>C: execute(number, message) C->>L: tryRecord(country, cost, window cap, daily cap) C-->>E: SmsRequested event, after commit P-->>U: 303 to /account/phone?status=pending E->>G: send(number, text) G-->>U: SMS with the code U->>P: POST /account/phone/verify (code) P->>V: execute(userId, username, code) V->>DB: Match the hash, store phone_e164 and verified_at, delete the pending data P-->>U: 303 to /account/phone?status=verified

Two details are deliberate. The answer is pending whether or not the number already belongs to another account, and in that case nothing is sent, so the enrolment endpoint cannot be used to find out which numbers are registered. And the SMS is handed to the gateway only after the commit, from an @Async listener, so a slow or failing gateway never shows in the response and never holds a database connection.

Login with an SMS code

The login and second-factor flows are the one-time-token flows of the e-mail page, with the channel sms. The user names the account, the server looks up its verified phone, and a code is sent to it.

sequenceDiagram autonumber actor U as User participant B as Browser participant R as POST /ott/generate participant Q as RequestOneTimeCodeUseCase participant C as SendSmsOneTimeCodeUseCase participant E as OttDeliveryListener participant G as SmsSender participant A as POST /login/ott U->>B: Chooses the SMS method and types the username B->>R: username, channel sms, kind code, purpose login R->>Q: execute(username, SMS, LOGIN) Q->>Q: Resolve the verified phone, if there is none do nothing Q->>Q: Store the hashed code with its expiry Q->>C: execute(phone, message) C->>C: Country allowed? Spend within both caps? C-->>E: SmsRequested event, after commit R-->>B: The same redirect to the code page as for any username E->>G: send(phone, text) G-->>U: SMS with the code U->>B: Types the code B->>A: code A->>A: Check the hash, attempts and expiry, grant FACTOR_OTT_SMS A-->>B: Signed in, asked for a second factor when MFA is required

When the user is already signed in with a password and the account requires a second factor, the same flow runs with the purpose second-factor, posts to /login/second-factor/ott and grants FACTOR_OTT_SMS_2FA. Which channels the second-factor page offers is decided by one small component, shown in the Code section: SMS is offered only to an account with a verified phone, and never when SMS itself signed the user in.

Risks and mitigations

SMS is the weakest of the one-time-code channels, and some of its risks are outside the application. The table says what the example does about each one and what remains.

Risk What the example does What remains

SIM swap (an attacker ports the victim’s number to another SIM)

A verified phone is a second factor next to the password by default. Replacing the verified number requires a recent multi-factor sign-in (step-up) when the account already has a second factor, and confirming a different number revokes every trusted device of the account and records a SECOND_FACTOR_REMOVED security event.

The application cannot see a SIM change. Offer a stronger factor (a passkey or an authenticator app) and treat SMS as a fallback, as NIST recommends.

SMS pumping and toll fraud (an attacker triggers many messages to premium or attacker-controlled numbers)

Only the countries of authserver.sms.allowed-countries receive messages. Every message first records its cost in the sms_cost_ledger table through an atomic check against a per-window cap and a per-day cap, kept in the database so a restart cannot reset them. Requests are also limited per client address and per account or username (the authserver.ott.rate-limit settings).

The caps are global, not per number or per country: an attack inside an allowed country can still use up the budget and deny SMS to everyone until the window passes. Add per-country caps and gateway-side fraud protection in production.

Interception (SS7 weaknesses, malware that reads messages, shoulder surfing)

Codes are short-lived (10 minutes by default), single use, stored only as a hash, and a code is spent after five wrong attempts. A code is bound to the request that created it.

A code in transit is readable by the network and the phone. The channel is not phishing resistant: a real-time phishing site can relay the code at once.

Number recycling (an operator gives a former subscriber’s number to someone else)

A number belongs to one account (uq_user_phones_phone_e164), and a pending enrolment does not reserve it. Removing the phone is always possible.

The application cannot know that a number was reassigned. A stale number is a risk until the user changes it, so keep an alternative recovery path and expire unused phones by policy.

Enumeration (finding out which usernames or numbers exist)

The response to a request for a code is the same for an unknown user, a user without a verified phone, a number that belongs to another account, a country that is not allowed and a spent budget. Nothing is sent in those cases and the caller cannot tell them apart. The phone page and the API show only the last four digits of the number.

Timing differences are small but not eliminated: the code is generated and hashed before the destination is resolved, which keeps the work of the known and the unknown case alike.

One-Time Token Login

Phone parsing and region detection use Google’s libphonenumber, wrapped in the LibPhoneNumberNormalizer and LibPhoneNumberCountryResolver adapters, so the domain only sees a PhoneNumber that validates the E.164 shape and no third-party type. See libphonenumber.

Data

Migration V620 adds the table that holds a user’s phone, with the pending verification in the same row, and V630 adds the ledger that the cost cap reads.

-- One row per user. phone_e164 and verified_at hold the verified number (unique, so one number belongs to one user);
-- the pending_* columns hold a verification in progress, with the code hashed. A pending number does not reserve it.
CREATE TABLE user_phones
(
    user_id             uuid         NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    phone_e164          varchar(16),
    verified_at         timestamp with time zone,
    pending_phone_e164  varchar(16),
    pending_code_hash   varchar(128),
    pending_attempts    integer      NOT NULL DEFAULT 0,
    pending_expires_at  timestamp with time zone,
    PRIMARY KEY (user_id),
    CONSTRAINT uq_user_phones_phone_e164 UNIQUE (phone_e164),
    CONSTRAINT ck_user_phones_verified CHECK ((phone_e164 IS NULL) = (verified_at IS NULL)),
    CONSTRAINT ck_user_phones_pending CHECK ((pending_phone_e164 IS NULL) = (pending_code_hash IS NULL)
        AND (pending_phone_e164 IS NULL) = (pending_expires_at IS NULL)),
    CONSTRAINT ck_user_phones_phone_shape CHECK (phone_e164 IS NULL OR phone_e164 ~ '^\+[1-9][0-9]{6,14}$'),
    CONSTRAINT ck_user_phones_pending_shape CHECK (pending_phone_e164 IS NULL
        OR pending_phone_e164 ~ '^\+[1-9][0-9]{6,14}$')
);

CREATE INDEX ix_user_phones_pending_expires_at ON user_phones (pending_expires_at);

This is plain Flyway SQL for the example’s own tables; see the Spring Boot Flyway how-to.

CREATE TABLE sms_cost_ledger
(
    id         bigint GENERATED ALWAYS AS IDENTITY,
    sent_at    timestamp with time zone NOT NULL,
    country    char(2)                  NOT NULL,
    cost_micros bigint                  NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT ck_sms_cost_ledger_cost CHECK (cost_micros >= 0)
);

CREATE INDEX ix_sms_cost_ledger_sent_at ON sms_cost_ledger (sent_at);

The ledger has one row per message accepted for sending: when, to which country and at what cost, in millionths of the billing currency. The cap check sums the rows of the window and of the last day. An hourly job deletes rows older than ledger-retention. The tables are also listed, with the rest of the schema, in Data Model and Schema.

Code

Configuration

All the SMS settings live under authserver.sms. The cost values are in millionths of the billing currency, so a default of 50000 is 0.05. The gateway is chosen by profile, never by a property, which the last comment of the region explains.

  sms:
    # Region numbers typed without a country prefix are read in, and the regions SMS may be sent to (ISO 3166-1
    # alpha-2, upper case). The values shown are the defaults of SmsProperties.
    default-region: US
    allowed-countries: US,ES,GB
    # Cost caps in millionths of the billing currency, so a bug or an attack cannot run up the bill: the price assumed
    # for a country without an entry in cost-per-country-micros, and the most that may be spent per window and per day.
    default-cost-micros: 50000
    window: PT1H
    window-cap-micros: 5000000
    daily-cap-micros: 20000000
    # Verification code of a phone being enrolled, and how long the spend ledger is kept.
    verification-code-length: 6
    verification-code-ttl: PT10M
    verification-max-attempts: 5
    ledger-retention: P2D
    # Which gateway sends the messages is chosen with a Spring profile, never with a property: "twilio" sends through
    # Twilio (application-twilio.yml) and "sns" through Amazon SNS (application-sns.yml, default AWS credential chain);
    # only "dev" and "test" log the message to a bounded in-memory outbox (the dev profile shows it at
    # /dev/sms-inbox). With none of these profiles the application refuses to start, so a deployment never silently
    # keeps its messages in memory.

Settings are bound to a validated record; see the Spring Boot reference on type-safe configuration properties. The rate limits that also protect the SMS endpoints are the authserver.ott.rate-limit settings of the e-mail page.

The SmsSender port

The port is one method. It belongs to the domain module, so the use cases can be tested with a fake and no SDK reaches them.

/**
 * Port that sends a text message through a gateway. No gateway type crosses it.
 */
public interface SmsSender {

    /**
     * Sends a text message.
     *
     * @param to   recipient.
     * @param text text of the message.
     * @throws SmsDeliveryException if the gateway failed or refused the message.
     */
    void send(PhoneNumber to, String text);
}

This is a plain interface, an application of the ports and adapters style; the only Spring part is the bean that implements it, described in the @Bean reference.

Choosing the adapter

The configuration class builds the phone normaliser and country resolver, and, only under the dev or test profile and when no gateway profile is active, the outbox and the logging sender. The Twilio and SNS senders are beans of their own configuration classes, active under the profiles twilio and sns; their credentials come only from environment variables (AUTHSERVER_SMS_TWILIO_* and the default AWS credential chain).

/**
 * Wires the phone normaliser and the logging {@link SmsSender} of development and tests. The profile expressions make
 * the three senders (logging, Twilio, SNS) mutually exclusive in every combination of profiles: the logging one only
 * under {@code dev} or {@code test} and when neither gateway profile is active, Twilio unless SNS is also active, and
 * SNS whenever it is active. With none of those profiles there is no sender at all and
 * {@link MissingSmsGatewayConfiguration} stops the startup: a deployment never silently keeps its messages in memory.
 */
@Configuration(proxyBeanMethods = false)
@EnableConfigurationProperties(SmsOutboxProperties.class)
public class SmsAdapterConfiguration {

    /** Profiles under which the logging sender (and its outbox) is used: development or tests, and no gateway. */
    public static final String LOGGING_SENDER_PROFILES = "(dev | test) & !twilio & !sns";

    /**
     * Creates the phone normaliser.
     *
     * @return the libphonenumber based normaliser.
     */
    @Bean
    public PhoneNormalizer phoneNormalizer() {
        return new LibPhoneNumberNormalizer(PhoneNumberUtil.getInstance());
    }

    /**
     * Creates the resolver of the country of a phone number.
     *
     * @return the libphonenumber based resolver.
     */
    @Bean
    public PhoneCountryResolver phoneCountryResolver() {
        return new LibPhoneNumberCountryResolver(PhoneNumberUtil.getInstance());
    }

    /**
     * Creates the outbox of the logging sender.
     *
     * @param properties outbox settings.
     * @return the outbox, readable by the development inbox.
     */
    @Bean
    @Profile(LOGGING_SENDER_PROFILES)
    public SmsOutbox smsOutbox(final SmsOutboxProperties properties) {
        return new SmsOutbox(properties.capacity());
    }

    /**
     * Creates the logging sender of development and tests.
     *
     * @param outbox records the messages.
     * @param clock  source of the recording instant.
     * @return the logging sender.
     */
    @Bean
    @Profile(LOGGING_SENDER_PROFILES)
    public SmsSender loggingSmsSender(final SmsOutbox outbox, final Clock clock) {
        return new LoggingSmsSender(outbox, clock);
    }
}

The profile expression is a Spring profile expression.

Which channels the second factor offers

One component decides which one-time-token channels a signed-in user may use as a second factor. E-mail is offered only when the user has no other confirmed second factor (a mailbox that can reset the password must not stand in for a real factor), and SMS only to a user with a verified phone who did not just sign in through SMS.

/**
 * Decides through which channels a one-time code or link may be the second factor of a signed-in user. The same rule
 * decides what the second-factor page offers, whether a requested token is delivered at all and whether a presented
 * one is accepted, so a channel that is not offered can neither be asked for nor used by posting the forms by hand:
 * <ul>
 * <li>never the channel that signed the user in (the same mailbox or phone would be proved twice);</li>
 * <li>SMS only to a user with a verified phone;</li>
 * <li>e-mail only to a user without any other confirmed second factor (authenticator app, passkey, verified phone).
 * The password is reset by e-mail too, so a mailbox is not independent from the password: whoever controls it could
 * otherwise skip the stronger factor the user enrolled. For a user whose multi-factor authentication was forced by an
 * administrator before any factor was enrolled, the e-mail is then the only second factor available.</li>
 * </ul>
 */
@Component
@RequiredArgsConstructor
public class OttSecondFactorChannels {

    /** Rules about the session a second factor is presented in. */
    private final PrimaryFactorSession primaryFactorSession;

    /** Resolves the identifier of the account of the signed-in user. */
    private final SecondFactorUserResolver userResolver;

    /** Tells whether the user has a confirmed second factor of any kind. */
    private final HasConfirmedSecondFactorUseCase hasConfirmedSecondFactorUseCase;

    /** Tells whether the user has a verified phone. */
    private final HasVerifiedPhoneUseCase hasVerifiedPhoneUseCase;

    /**
     * Gets the channels a signed-in user may use as the second factor.
     *
     * @param authentication the authentication of the session, which holds a primary factor.
     * @return the channels; empty when none may be used.
     */
    public Set<OttChannel> allowed(final Authentication authentication) {
        final var userId = userResolver.userIdOf(authentication.getName());
        final var channels = EnumSet.noneOf(OttChannel.class);
        if (!primaryFactorSession.signedInThrough(authentication, OttChannel.EMAIL)
                && !hasConfirmedSecondFactorUseCase.execute(userId)) {
            channels.add(OttChannel.EMAIL);
        }
        if (!primaryFactorSession.signedInThrough(authentication, OttChannel.SMS)
                && hasVerifiedPhoneUseCase.execute(userId)) {
            channels.add(OttChannel.SMS);
        }
        return channels;
    }

    /**
     * Tells whether a signed-in user may use a channel as the second factor.
     *
     * @param authentication the authentication of the session, which holds a primary factor.
     * @param channel        the channel.
     * @return {@code true} when the channel is one of {@link #allowed(Authentication)}.
     */
    public boolean isAllowed(final Authentication authentication, final OttChannel channel) {
        return allowed(authentication).contains(channel);
    }
}

This is a Spring @Component that composes use cases; see the stereotype annotations reference.

Delivering after the commit

The use case only publishes an event. The listener below sends it after the surrounding transaction commits, on an executor, and logs only the exception class when delivery fails, never the number or the code. The same listener also delivers the e-mail codes and links.

/**
 * Delivers the one-time tokens the use cases asked for, once the transaction that stored them has committed
 * ({@link TransactionPhase#AFTER_COMMIT}; an event published outside a transaction is delivered at once) and off the
 * request thread ({@code @Async}, on Spring Boot's {@code applicationTaskExecutor}). So no mail server or SMS gateway
 * is ever called inside a transaction, a slow one holds no database connection, a rolled-back request sends nothing,
 * and the time the request takes is the same whether or not something is sent, which keeps the latency from telling
 * an existing account from an unknown one. A failure is logged without the address, the number or the token, and
 * never reaches the response.
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class OttDeliveryListener {

    /** Delivers the tokens. */
    private final DeliverOneTimeTokenUseCase deliverOneTimeTokenUseCase;

    /**
     * E-mails a code.
     *
     * @param event what to deliver.
     */
    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT, fallbackExecution = true)
    public void onEmailCode(final EmailCodeRequested event) {
        try {
            deliverOneTimeTokenUseCase.deliverEmailCode(event);
        } catch (final OttDeliveryException e) {
            log.warn("A one-time code was not delivered by e-mail: {}", e.getClass().getSimpleName());
        }
    }

    /**
     * E-mails a magic link.
     *
     * @param event what to deliver.
     */
    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT, fallbackExecution = true)
    public void onEmailLink(final EmailLinkRequested event) {
        try {
            deliverOneTimeTokenUseCase.deliverEmailLink(event);
        } catch (final OttDeliveryException e) {
            log.warn("A magic link was not delivered: {}", e.getClass().getSimpleName());
        }
    }

    /**
     * Sends a text message.
     *
     * @param event what to send.
     */
    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT, fallbackExecution = true)
    public void onSms(final SmsRequested event) {
        try {
            deliverOneTimeTokenUseCase.deliverSms(event);
        } catch (final SmsDeliveryException e) {
            log.warn("An SMS was not delivered: {}", e.getClass().getSimpleName());
        }
    }
}

See the Spring reference on transaction-bound events and on @Async.

Limiting the requests

The shared limiter keeps four sets of fixed-window buckets (generation and verification, each per client address and per identifier) and throws OttRateLimitExceededException when one is empty. The phone page uses the account id as the identifier, so one account cannot request unlimited codes from many addresses.

/**
 * Rate limiter of the one-time token endpoints, on the pattern of the account endpoints' limiter: Bucket4j token
 * buckets in Caffeine caches ({@link FixedWindowBuckets}). Requests for a token (generation) and submissions of a token
 * or code (verification) are limited separately, and each twice: per client address and per identifier (the user name
 * the request names), so a single client cannot flood the mailboxes and the SMS budget, many clients cannot aim at one
 * account, and a code cannot be guessed faster than the limits allow, on top of the attempt counter of the code
 * itself. The identifier is limited whether or not it belongs to an account, so the limit never tells which ones
 * exist.
 *
 * <p>Each bucket holds the limit of its key and is refilled all at once every
 * {@link OttRateLimitProperties#window()}. The buckets live in this instance only: several instances each apply the
 * limits on their own. The client address is {@code request.getRemoteAddr()}, so behind a proxy
 * {@code server.forward-headers-strategy} must be set for it to be the real client.
 */
@Component
@EnableConfigurationProperties(OttRateLimitProperties.class)
public final class OttRateLimiter {

    /** Key used when the client address is unknown. */
    private static final String UNKNOWN_CLIENT = "unknown";

    /** Limits, window and bound of the tracked keys. */
    private final OttRateLimitProperties properties;

    /** Buckets of the token requests per client address. */
    private final FixedWindowBuckets generationClients;

    /** Buckets of the token requests per identifier. */
    private final FixedWindowBuckets generationIdentifiers;

    /** Buckets of the submissions per client address. */
    private final FixedWindowBuckets verificationClients;

    /** Buckets of the submissions per identifier. */
    private final FixedWindowBuckets verificationIdentifiers;

    /**
     * Creates the limiter.
     *
     * @param properties limits, window and bound of the tracked keys.
     * @param clock      source of the current time.
     */
    public OttRateLimiter(final OttRateLimitProperties properties, final Clock clock) {
        this.properties = properties;
        generationClients = buckets(clock);
        generationIdentifiers = buckets(clock);
        verificationClients = buckets(clock);
        verificationIdentifiers = buckets(clock);
    }

    /**
     * Counts one request for a token and rejects it once a limit is exceeded.
     *
     * @param clientAddress address of the calling client.
     * @param identifier    identifier the request names, or {@code null} when it names none.
     * @throws OttRateLimitExceededException if the client or the identifier exceeded its limit.
     */
    public void checkGeneration(final String clientAddress, final String identifier) {
        check(generationClients, properties.generationPerClient(), generationIdentifiers,
                properties.generationPerIdentifier(), clientAddress, identifier);
    }

    /**
     * Counts one submission of a token or a code and rejects it once a limit is exceeded.
     *
     * @param clientAddress address of the calling client.
     * @param identifier    identifier the submission is for, or {@code null} when it names none (a magic link).
     * @throws OttRateLimitExceededException if the client or the identifier exceeded its limit.
     */
    public void checkVerification(final String clientAddress, final String identifier) {
        check(verificationClients, properties.verificationPerClient(), verificationIdentifiers,
                properties.verificationPerIdentifier(), clientAddress, identifier);
    }

    /**
     * Tells how many keys are tracked, after any pending eviction.
     *
     * @return the number of keys of the four kinds.
     */
    long trackedKeys() {
        return generationClients.trackedKeys() + generationIdentifiers.trackedKeys()
                + verificationClients.trackedKeys() + verificationIdentifiers.trackedKeys();
    }

    /**
     * Applies the client and the identifier limits of one kind of request.
     *
     * @param clients         buckets per client address.
     * @param clientLimit     requests per client address per window.
     * @param identifiers     buckets per identifier.
     * @param identifierLimit requests per identifier per window.
     * @param clientAddress   address of the calling client.
     * @param identifier      identifier, or {@code null}.
     * @throws OttRateLimitExceededException if a limit is exceeded.
     */
    private void check(final FixedWindowBuckets clients, final int clientLimit, final FixedWindowBuckets identifiers,
                       final int identifierLimit, final String clientAddress, final String identifier) {
        if (!properties.enabled()) {
            return;
        }
        consume(clients, clientAddress == null ? UNKNOWN_CLIENT : clientAddress, clientLimit);
        if (identifier != null) {
            consume(identifiers, identifier.toLowerCase(Locale.ROOT), identifierLimit);
        }
    }

    /**
     * Takes one token from the bucket of a key.
     *
     * @param buckets buckets of one kind of key.
     * @param key     the key.
     * @param limit   requests the key may make per window.
     * @throws OttRateLimitExceededException if the bucket is empty.
     */
    private static void consume(final FixedWindowBuckets buckets, final String key, final int limit) {
        final var wait = buckets.tryConsume(key, limit);
        if (wait.isPresent()) {
            throw new OttRateLimitExceededException(wait.get());
        }
    }

    /**
     * Builds the buckets of one kind of key.
     *
     * @param clock source of the current time.
     * @return the buckets.
     */
    private FixedWindowBuckets buckets(final Clock clock) {
        return new FixedWindowBuckets(clock, properties.window(), properties.maxTrackedKeys());
    }
}

The limiter keeps one Bucket4j bucket per key in a bounded Caffeine cache (FixedWindowBuckets), the same pattern as the e-mail one-time codes and the account endpoints; see Bucket4j with Spring Boot for the technique. Reference: Bucket4j documentation.

The phone page

PhonePageController implements the interface generated from the pages contract. Every post answers 303 See Other back to the page with a status query parameter, and the page tells only the statuses it knows. The enrolment and the removal check a recent multi-factor sign-in first; the enrolment and the verification pass through the rate limiter. A removal of a phone, or the confirmation of a different one, is audited and revokes the trusted devices (that logic is in the use cases).

/**
 * Serves the phone account page and the session-protected form posts it uses, as the contract
 * {@code apis/auth-server/web-pages/auth-server-pages-v1.yaml} describes them through the generated
 * {@link PhonePageApi}. A browser page has a session, not a bearer token, so it cannot call the REST API
 * ({@code /api/account/phone}, which {@code ApiSecurityConfig} keeps bearer-only); the forms call the same use cases
 * instead, with the same limits, and each answers by redirecting back to the page (post/redirect/get) with the outcome
 * in the {@code status} parameter. The number is shown masked, as the REST API answers it.
 */
@Controller
@RequiredArgsConstructor
public class PhonePageController implements PhonePageApi {

    /** Path of the page, taken from the contract. */
    public static final String PHONE_PATH = PATH_PHONE_PAGE;

    /** Name of the template of the page. */
    static final String VIEW_NAME = "account-phone";

    /** Name of the model attribute that holds the masked verified number, absent when there is none. */
    static final String PHONE_ATTRIBUTE = "phone";

    /** Name of the model attribute that holds the outcome of the previous post. */
    static final String STATUS_ATTRIBUTE = "status";

    /** Status of a code that was requested. */
    static final String PENDING = "pending";

    /** Status of a number that was verified. */
    static final String VERIFIED = "verified";

    /** Status of a number that was removed. */
    static final String REMOVED = "removed";

    /** Status of a number that is not valid. */
    static final String INVALID_PHONE = "invalid-phone";

    /** Status of a number of a country SMS messages are not sent to. */
    static final String COUNTRY_NOT_ALLOWED = "country-not-allowed";

    /** Status of a wrong code. */
    static final String INVALID_CODE = "invalid-code";

    /** Status of a request over a limit. */
    static final String RATE_LIMITED = "rate-limited";

    /** Status of an enrolment or a removal that needs a recent multi-factor sign-in. */
    static final String STEP_UP_REQUIRED = "step-up-required";

    /** The statuses the page tells; any other value of the parameter is ignored. */
    private static final Set<String> STATUSES = Set.of(PENDING, VERIFIED, REMOVED, INVALID_PHONE,
            COUNTRY_NOT_ALLOWED, INVALID_CODE, RATE_LIMITED, STEP_UP_REQUIRED);

    /** Resolves the account of the request. */
    private final CurrentAccountResolver currentAccountResolver;

    /** Finds the verified phone of the account. */
    private final FindUserPhoneUseCase findUserPhoneUseCase;

    /** Starts an enrolment. */
    private final StartPhoneEnrolmentUseCase startPhoneEnrolmentUseCase;

    /** Confirms an enrolment. */
    private final ConfirmPhoneUseCase confirmPhoneUseCase;

    /** Removes the phone. */
    private final RemovePhoneUseCase removePhoneUseCase;

    /** Requires a recent multi-factor sign-in before the phone is replaced or removed. */
    private final PhoneSessionStepUp stepUp;

    /** Limits the requests. */
    private final OttRateLimiter rateLimiter;

    /** Maps the phone onto its masked form. */
    private final PhoneDtoMapper phoneDtoMapper;

    /** Renders the page. */
    private final PageRenderer pageRenderer;

    /** The current request, injected as a thread-bound proxy, which tells the address of the client. */
    private final HttpServletRequest request;

    /**
     * Renders the page.
     *
     * @param status outcome of the previous post, ignored when it is not one of the known ones.
     * @return the page, never cached.
     */
    @Override
    public ResponseEntity<String> phonePage(final String status) {
        final var account = currentAccountResolver.resolve();
        final var model = new HashMap<String, Object>();
        findUserPhoneUseCase.execute(account.id())
                .ifPresent(phone -> model.put(PHONE_ATTRIBUTE, phoneDtoMapper.toResponse(phone).maskedNumber()));
        if (status != null && STATUSES.contains(status)) {
            model.put(STATUS_ATTRIBUTE, status);
        }
        final var page = pageRenderer.render(VIEW_NAME, model);
        return ResponseEntity.status(page.getStatusCode())
                .headers(page.getHeaders())
                .cacheControl(CacheControl.noStore())
                .body(page.getBody());
    }

    /**
     * Sends the verification code to the number, when the session shows a recent enough multi-factor sign-in for an
     * account that already has a confirmed second factor (the new number would replace the verified one).
     *
     * @param phone the number.
     * @return a redirect to the page; the status is {@code pending} whether or not the number belongs to another
     *         account.
     */
    @Override
    public ResponseEntity<Void> startPhoneEnrolmentPage(final String phone) {
        final var account = currentAccountResolver.resolve();
        if (!stepUp.isSatisfied(account.id(), SecurityContextHolder.getContext().getAuthentication())) {
            return redirect(STEP_UP_REQUIRED);
        }
        try {
            rateLimiter.checkGeneration(request.getRemoteAddr(), PhoneController.ACCOUNT_KEY_PREFIX + account.id());
            startPhoneEnrolmentUseCase.execute(account.id(), phone);
            return redirect(PENDING);
        } catch (final OttRateLimitExceededException e) {
            return redirect(RATE_LIMITED);
        } catch (final InvalidPhoneNumberException e) {
            return redirect(INVALID_PHONE);
        } catch (final SmsCountryNotAllowedException e) {
            return redirect(COUNTRY_NOT_ALLOWED);
        }
    }

    /**
     * Confirms the number with the code.
     *
     * @param code the code received by SMS.
     * @return a redirect to the page, with the outcome.
     */
    @Override
    public ResponseEntity<Void> verifyPhonePage(final String code) {
        final var account = currentAccountResolver.resolve();
        try {
            rateLimiter.checkVerification(request.getRemoteAddr(), PhoneController.ACCOUNT_KEY_PREFIX + account.id());
        } catch (final OttRateLimitExceededException e) {
            return redirect(RATE_LIMITED);
        }
        return redirect(confirmPhoneUseCase.execute(account.id(), account.username(), code) ? VERIFIED : INVALID_CODE);
    }

    /**
     * Removes the phone, when the session shows a recent enough multi-factor sign-in.
     *
     * @return a redirect to the page, with the outcome.
     */
    @Override
    public ResponseEntity<Void> removePhonePage() {
        final var account = currentAccountResolver.resolve();
        if (!stepUp.isSatisfied(account.id(), SecurityContextHolder.getContext().getAuthentication())) {
            return redirect(STEP_UP_REQUIRED);
        }
        removePhoneUseCase.execute(account.id(), account.username());
        return redirect(REMOVED);
    }

    /**
     * Builds the redirect back to the page.
     *
     * @param status the outcome.
     * @return {@code 303 See Other} to the page.
     */
    private ResponseEntity<Void> redirect(final String status) {
        return ResponseEntity.status(HttpStatus.SEE_OTHER)
                .header(HttpHeaders.LOCATION, URI.create(PHONE_PATH + "?" + STATUS_ATTRIBUTE + "=" + status).toString())
                .build();
    }
}

A @Controller that implements a generated interface is ordinary Spring MVC; see the Spring MVC controllers reference.

The schemas follow the OpenAPI 3.1 Schema Object rules.

Start the enrolment. The number may be international or in the national form of the default region; the answer is 202 and says how long the code is valid:

curl -s -X PUT http://localhost:9000/api/account/phone \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"phone":"+34 600 11 22 33"}'

Confirm it with the code from the SMS (four to ten digits). The answer is the masked number and the verification time:

curl -s -X POST http://localhost:9000/api/account/phone/verify \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"code":"123456"}'

Read the verified phone, masked so that only the last four digits show, and remove it:

curl -s http://localhost:9000/api/account/phone \
  -H "Authorization: Bearer ${TOKEN}"

curl -s -X DELETE http://localhost:9000/api/account/phone \
  -H "Authorization: Bearer ${TOKEN}"

The errors follow the contract: 400 for a number that is not valid (urn:problem:phone:invalid-phone), a country that receives no SMS (urn:problem:phone:country-not-allowed) or a wrong, expired or missing code (urn:problem:phone:invalid-code); 401 without a valid token or without the step-up (with the RFC 9470 challenge); 404 when the account has no verified phone; and 429 over a rate limit. Removing a phone that is not set succeeds with 204.

Tests

CI never calls a real SMS gateway: the integration tests run with the logging sender and read the codes from its outbox. The example covers the feature at three levels, described here in prose because none of these tests carries a tag:

  • Sign-in integration tests: OttSmsIT checks that a user with a verified phone who asks for a code by SMS and posts it signs in without a password and is then asked for a second factor (because a verified phone makes MFA required), that neither channel that already signed the user in is offered again, that the tokens carry sms, otp and mfa, that a code sent as the second factor after the password issues multi-factor tokens, that a wrong code is redirected back with an error, and that confirming a code stores the verified phone. OttSmsLimitsIT checks that nothing is sent to a country that is not on the allow-list, neither as a sign-in code nor as an enrolment code, and that once the spend of the window reaches its cap no more messages are sent while every request is still answered the same way.

  • API and configuration integration tests: PhoneApiIT covers the enrolment without a step-up when the account has no second factor, the step-up challenge when it has one and the token is password only, the revocation of the trusted devices and the audit event when a new number replaces the verified one or the only second factor is removed, and a number that another user verified in the meantime. SmsSenderProfilesIT proves that the logging sender is the bean under test and dev, that it is not under a gateway profile, and that the application refuses to start with no sender profile and names the profiles to choose from.

  • Persistence integration tests against a real PostgreSQL: JdbcUserPhoneRepositoryIT, JdbcPhoneVerificationRepositoryIT and JdbcSmsCostLedgerRepositoryIT check the constraints of V620 and V630 and the atomic cap check of the ledger.

The unit tests cover the use cases (normalisation, country check, attempt counting, the replacement of a number), the cost policy and the adapters with a fake gateway client.

Security notes and pitfalls

  • SMS is a restricted authenticator. NIST SP 800-63B still allows it, with an alternative on offer and a warning to the user. Offer a passkey or an authenticator app, and use SMS for the users who cannot.

  • The cost cap is a safety net, not a defence. It limits the money an attack can burn, and it does so for everyone at once. Combine it with per-country and per-number limits, a gateway-side fraud filter and an alert when the daily spend approaches its cap.

  • Keep the allow-list short. A country that is not on the list receives nothing, so the premium-rate destinations that toll fraud targets are excluded by default. Review the list when the business changes.

  • Same answer, always. The endpoints answer identically for unknown users, numbers of other accounts, refused countries and exhausted budgets. Do not add a helpful error message to any of them.

  • Never log the number or the code. The logging sender records only the last four digits, and the delivery listener logs only the class of an exception. The clear code exists only in the message and in the process memory that sends it.

  • Credentials stay in the environment. The Twilio and SNS credentials come from environment variables or the default AWS credential chain, never from a file in the repository.

  • The dev inbox shows secrets. /dev/sms-inbox lists the text of every message, codes included. It exists only under dev, and the application refuses to start with no sender profile, so a production deployment can neither expose it nor silently keep messages in memory.

  • Changing the number is changing the factor. Replacing a verified number needs a recent multi-factor sign-in and revokes the trusted devices, otherwise a stolen password-only session could redirect the second factor to the attacker’s phone.

  • Phones need a recovery path. A lost phone or a recycled number locks the user out or hands the factor to a stranger. Keep recovery codes, as on the TOTP and Recovery Codes page, and a documented support process.

For the full reference see NIST SP 800-63B-4, RFC 9470 for the step-up challenge and the OWASP Multifactor Authentication Cheat Sheet.
