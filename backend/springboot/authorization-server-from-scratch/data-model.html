Authorization Server from Scratch: Data Model and Schema

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

auth-server keeps its state in PostgreSQL, and every table is created by a Flyway migration, never by the framework. This page starts with the tables of the example’s walking skeleton: three custom tables for the users, and the three tables that Spring Authorization Server defines for registered clients, authorizations and consents. It then adds the tables of the credentials, tokens, login and multi-factor authentication pages, including the bff database, and the last section adds the tables of the passkey, one-time code, social login, certificate and client authentication pages. The two databases of the architecture are separate: the authorization server owns the authserver database and the BFF owns the bff database.

Entity relationship diagram

A solid line is a real foreign key declared in a migration. A dashed line is a logical link with no foreign key: Spring Authorization Server copies a client id or a principal name into its tables by value, so deleting a user or a client does not cascade to those rows. Entities marked custom are defined by this project; entities marked Spring use the schema of the framework.

The shape of the three custom tables follows the schema that Spring Security documents for JDBC authentication, split so a user without a password (for example one that only signs in with a passkey, added by a later page) is just a user with no row in user_passwords.

Custom tables: users, authorities and passwords

V101__users.sql creates the three tables below. Only the columns that exist after this migration are listed; a later migration adds more columns to users (see the credentials, tokens, login and MFA section).

CREATE TABLE users
(
    id         uuid                     NOT NULL,
    username   varchar(100)             NOT NULL,
    enabled    boolean                  NOT NULL DEFAULT TRUE,
    created_at timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    CONSTRAINT uq_users_username UNIQUE (username)
);

CREATE TABLE user_authorities
(
    user_id   uuid         NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    authority varchar(100) NOT NULL,
    PRIMARY KEY (user_id, authority)
);

CREATE TABLE user_passwords
(
    user_id          uuid                     NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    encoded_password varchar(255)             NOT NULL,
    updated_at       timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (user_id)
);

These tables derive from the schema in the JDBC authentication section of the Spring Security reference, with the password moved to a table of its own.

Spring Authorization Server tables

The signing keys table has no relationship to the rest: it is looked up by kid, which appears in the header of every token the server signs.

Account data and reset tokens (V200)

V200__account.sql adds the contact data and the tenant to users, and the table of single-use tokens behind the password reset and registration flows. The unique index on lower(email) makes the e-mail unique regardless of case and ignores the rows that have none.

ALTER TABLE users
    ADD COLUMN email          varchar(320),
    ADD COLUMN email_verified boolean      NOT NULL DEFAULT FALSE,
    ADD COLUMN tenant         varchar(100) NOT NULL DEFAULT 'default';

-- Existing rows have no e-mail; the unique index is case-insensitive and ignores the NULLs.
CREATE UNIQUE INDEX uq_users_email ON users (lower(email));

CREATE TABLE account_tokens
(
    id           uuid                     NOT NULL,
    user_id      uuid                     NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    purpose      varchar(50)              NOT NULL,
    hashed_token varchar(128)             NOT NULL,
    expires_at   timestamp with time zone NOT NULL,
    used_at      timestamp with time zone,
    created_at   timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    CONSTRAINT uq_account_tokens_hashed_token UNIQUE (hashed_token)
);

CREATE INDEX ix_account_tokens_expires_at ON account_tokens (expires_at);

This is project-specific, so there is no framework schema to compare it with. See the Password Storage section of the Spring Security reference for how the password itself is stored. The account_tokens table holds only a hash of each token, never the token that was e-mailed, and used_at marks a token as consumed. The password storage page explains the flows.

Signing keys (V210)

V210__signing_keys.sql stores the keys that sign the tokens. The private key is kept encrypted, and a partial unique index guarantees that at most one key has the ACTIVE status, so at most one key signs at any time.

CREATE TABLE signing_keys
(
    kid                   varchar(64)              NOT NULL,
    alg                   varchar(20)              NOT NULL,
    public_jwk            text                     NOT NULL,
    private_jwk_encrypted text                     NOT NULL,
    status                varchar(20)              NOT NULL,
    created_at            timestamp with time zone NOT NULL,
    activated_at          timestamp with time zone,
    retired_at            timestamp with time zone,
    PRIMARY KEY (kid),
    CONSTRAINT ck_signing_keys_status CHECK (status IN ('NEXT', 'ACTIVE', 'RETIRED'))
);

-- At most one key can sign at any time.
CREATE UNIQUE INDEX uq_signing_keys_single_active ON signing_keys (status) WHERE status = 'ACTIVE';

The table backs a JWKSource, described in the JWT section of the Spring Security reference. The signing keys page explains the rotation.

varchar(20)

Not null. The signature algorithm.

Not null. The public key as a JWK, published by the JWKS endpoint.

Not null. The private key as an encrypted JWK.

Not null, one of NEXT, ACTIVE or RETIRED (ck_signing_keys_status).

Not null.

timestamp with time zone

Nullable. Set when the key changes status.

Refresh token reuse detection (V230)

V230__consumed_refresh_tokens.sql records the hash of every refresh token that was rotated out of an authorization. Presenting one of them again means the token was replayed, and the authorization is revoked. The foreign key to oauth2_authorization with ON DELETE CASCADE removes the hashes together with the authorization.

-- Hashes of the refresh tokens that were rotated out of an authorization. Presenting one of them again means the
-- token was stolen or replayed, so the authorization is revoked.
CREATE TABLE consumed_refresh_tokens
(
    token_hash       varchar(64)              NOT NULL,
    authorization_id varchar(100)             NOT NULL REFERENCES oauth2_authorization (id) ON DELETE CASCADE,
    consumed_at      timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (token_hash)
);

CREATE INDEX ix_consumed_refresh_tokens_authorization ON consumed_refresh_tokens (authorization_id);

The behaviour follows the refresh token guidance of RFC 9700 (OAuth 2.0 Security Best Current Practice). The access, refresh and ID tokens page explains the flow.

Column Type Notes

token_hash

varchar(64)

Primary key. The hash of the consumed refresh token.

authorization_id

varchar(100)

Not null. Foreign key to oauth2_authorization(id) with ON DELETE CASCADE. Indexed (ix_consumed_refresh_tokens_authorization).

consumed_at

timestamp with time zone

Not null, default the current timestamp.

Authorization creation time (V240)

V240__authorization_created_at.sql adds one column to the Spring-defined oauth2_authorization table. Spring Authorization Server lists its columns explicitly, so the default value fills it in without any code change.

-- When each authorization row was created. Spring Authorization Server lists its columns explicitly, so the default
-- fills it in. An authorization that never got a token (an authorization or consent request the user abandoned) has
-- no expiry at all; the clean-up job deletes it once it is older than a configurable threshold.
ALTER TABLE oauth2_authorization
    ADD COLUMN created_at timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP;

The table itself is described in the core model components of the Spring Authorization Server reference; the only column documented here is the one this project adds: created_at, a timestamp with time zone, not null, default the current timestamp. An authorization that never got a token has no expiry, and the clean-up job described in the access, refresh and ID tokens page deletes it once it is older than a configurable threshold.

Security events and second factor lockout (V400)

V400__mfa_security_events.sql adds a flag to users, the audit trail and the counter that locks a user out after too many failed second factor attempts. security_events.user_id is nullable and uses ON DELETE SET NULL, so events for unknown user names can be stored and the trail outlives a deleted account.

ALTER TABLE users
    ADD COLUMN mfa_required boolean NOT NULL DEFAULT FALSE;

-- Audit trail. The user is kept as a nullable reference so events of failed logins for unknown names can be stored
-- and so the trail outlives a deleted account.
CREATE TABLE security_events
(
    id          uuid                     NOT NULL,
    type        varchar(50)              NOT NULL,
    user_id     uuid REFERENCES users (id) ON DELETE SET NULL,
    username    varchar(100),
    detail      varchar(500),
    occurred_at timestamp with time zone NOT NULL,
    PRIMARY KEY (id)
);

CREATE INDEX ix_security_events_user_occurred_at ON security_events (user_id, occurred_at);

CREATE TABLE second_factor_attempts
(
    user_id      uuid                     NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    failed_count integer                  NOT NULL DEFAULT 0,
    locked_until timestamp with time zone,
    PRIMARY KEY (user_id)
);

The tables are project-specific. See the authentication events section of the Spring Security reference for the framework events they record. The multi-factor authentication page explains how they are used.

CREATE TABLE totp_credentials

CREATE INDEX ix_recovery_codes_user_id ON recovery_codes (user_id);

Trusted devices (V420)

V420__trusted_devices.sql stores the browsers that the user chose to trust, so they can skip the second factor until the entry expires. Like the other tokens, only a hash is stored.

CREATE TABLE trusted_devices
(
    id           uuid                     NOT NULL,
    user_id      uuid                     NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    hashed_token varchar(128)             NOT NULL,
    user_agent   varchar(255),
    expires_at   timestamp with time zone NOT NULL,
    created_at   timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    CONSTRAINT uq_trusted_devices_hashed_token UNIQUE (hashed_token)
);

CREATE INDEX ix_trusted_devices_user_id ON trusted_devices (user_id);
CREATE INDEX ix_trusted_devices_expires_at ON trusted_devices (expires_at);

The table is project-specific. See NIST SP 800-63B-4 for the authentication assurance rules that frame remembering a device. The multi-factor authentication page explains the flow.

uuid

Not null. Foreign key to users(id) with ON DELETE CASCADE. Indexed (ix_trusted_devices_user_id).

hashed_token

varchar(128)

Generated passwords (V701)

V701__generated_passwords.sql adds a column to an existing table instead of creating one. Every account row carries a password hash, so an account created by the first sign-in with an external provider gets the hash of a random secret that nobody knows. The generated flag says so, which stops such an account from counting as having a password sign-in method. Setting a password (registration, reset or change) clears the flag.
