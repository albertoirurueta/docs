Authorization Server from Scratch: The Implicit Flow (Legacy) & Migration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Do not use the implicit flow. Treat this page as a migration guide that happens to include a demonstration.

  • The implicit grant (response_type=token) is not part of the OAuth 2.1 draft, and RFC 9700 (Best Current Practice for OAuth 2.0 Security) advises clients against it because the access token travels in the browser’s URL and can leak and be replayed.

  • Spring Authorization Server does not support response_type=token. Out of the box the example answers it with unsupported_response_type.

  • The example ships the flow only as the opt-in legacy-implicit Spring profile, off by default, for demonstration and for testing a migration. It is never part of a deployment.

The theory is in Legacy Grants: Implicit and Password and Browser-Based Apps (SPAs). Official references: RFC 9700 and The OAuth 2.1 Authorization Framework (Internet-Draft).

What you build

A single-page application that signs in with the implicit flow is the thing the rest of this guide replaces with the Backend-for-Frontend. This page does two jobs:

  • a demonstration: an opt-in profile, legacy-implicit, that makes the authorization endpoint accept response_type=token for exactly one client, legacy-implicit-spa, and a static page that signs in and shows the claims of the token it received, so a team can see on its own screen what the flow exposes;

  • a migration guide: how to move an application that still uses the flow to the backend-for-frontend or to authorization code with PKCE, how to find clients that still have the grant, and a checklist to switch it off.

The demonstration is deliberately narrow. Even with the profile on, the flow is limited to one client, one exact redirect URI, one audience and scope, a lifetime of at most 15 minutes, no refresh token, and a mandatory state. Those limits reduce the damage; they do not make the flow recommended.

How it works

Implicit next to authorization code with PKCE

In the implicit flow the authorization endpoint answers with the access token itself, in the URL fragment of the redirect. In the authorization code flow it answers with a short-lived, single-use code, and the token is fetched at the token endpoint over a back channel that the browser history never records.

A-->>B: 302 to the redirect URI, access_token in the fragment Note over B: The token is now in the address bar, the history and any script of the page end rect rgb(235, 245, 235) Note over B,A: Authorization code with PKCE (current) B->>A: GET /oauth2/authorize?response_type=code&code_challenge=... A-->>B: 302 to the redirect URI with a one-time code B->>A: POST /oauth2/token (code, code_verifier) A-->>B: Tokens in the response body end

What the profile changes

Spring Authorization Server’s authorization endpoint filter converts the request into an Authentication, passes it to a list of providers, and hands the result to one success handler and one failure handler. Its default converters understand only the authorization code (and consent) requests, so an unknown response type fails at conversion. The example plugs three pieces of its own into that chain, in order:

  1. a converter that recognises response_type=token, and refuses it, with unsupported_response_type and no redirect, for every client except the configured one;

  2. a provider that checks the client, the registered redirect URI, the signed-in user, the multi-factor policy, state and scopes, then generates and stores a short-lived access token;

  3. a response handler that turns that result into a redirect with a fragment, and hands every other result (an ordinary authorization code response) to the framework’s own handler.

sequenceDiagram autonumber participant B as Browser participant F as Authorization endpoint filter participant C as LegacyImplicitAuthorizationRequestConverter participant P as LegacyImplicitAuthenticationProvider participant H as LegacyImplicitResponseHandler B->>F: GET /oauth2/authorize?response_type=token... F->>C: convert(request) C-->>F: request token (or a 400 refusal for any other client) F->>P: authenticate(request token) P->>P: Client, redirect URI, user, MFA policy, state, scopes P->>P: Generate the access token, save the authorization P-->>F: access token result (or an error result) F->>H: onAuthenticationSuccess H-->>B: 302 to the redirect URI, token or error in the fragment

Errors are split by whether the redirect URI is trusted yet. Anything found before the client and the exact redirect URI are validated (unknown client, a client that may not use the grant, a missing or unregistered redirect URI, a repeated parameter) is answered with 400 and never redirected. A browser with no signed-in user is sent to the login page and the request resumes after sign-in, as in the code flow. A missing state or an invalid scope is returned in the fragment of the already validated redirect URI. A user who owes a second factor is sent to the second-factor page, exactly as in the code flow; see Multi-Factor Authentication & Step-Up.

RegisteredClient

Data

The flow adds no table and no migration. It reuses the two tables of the framework schema that the rest of the example uses (see Data Model and Schema):

  • oauth2_registered_client holds legacy-implicit-spa. Its authorization_grant_types column contains implicit. The domain model refuses a registration that combines implicit with a confidential client, with required consent or with a refresh token, and a public client whose only grant type is implicit is the one exception to "a public client must require PKCE", because PKCE has no meaning without a code.

  • oauth2_authorization gets a row for every token the flow issues, with authorization_grant_type = 'implicit', so the token can be introspected and revoked like any other. The migration guide below uses this to find real usage.

Code

Settings

The profile’s own settings file names the client, its only redirect URI, the scope, the audience and the lifetime. Its header comment says what the file is.

authserver:
  legacy-implicit:
    client-id: legacy-implicit-spa
    redirect-uri: ${AUTHSERVER_LEGACY_IMPLICIT_REDIRECT_URI:http://localhost:9000/legacy-implicit/}
    scopes: documents.read
    audience: resource-server
    # lifetime of the access token it issues, at most PT15M
    access-token-ttl: PT5M

Reference: Spring Boot profiles. The profile is switched on explicitly, for example with SPRING_PROFILES_ACTIVE=dev,legacy-implicit for a local run.

LegacyImplicitProperties (the implicit-properties region of the example) validates those values when the application starts: a blank client or redirect URI, empty scopes or a lifetime above 15 minutes stop the start-up. LegacyImplicitConfiguration (the implicit-chain-config region) creates everything else only under the profile: the token generator factory, the chain customizer, the client seeder, a login-chain customizer that opens the demo page, and the resource handler that serves the page from classpath:/legacy-implicit/ rather than from static/, so nothing is exposed without the profile.

Enabling the flow

The chain customizer adds the three pieces to the authorization endpoint.

/**
 * Adds the legacy implicit flow to the authorization endpoint: its converter first, its provider first and its
 * response handler in place of the framework's (which it delegates to for an authorization code).
 */
@RequiredArgsConstructor
public class LegacyImplicitProtocolChainCustomizer implements ProtocolChainCustomizer {

    /** Order of the customizer, after the client authentication one ({@code 3}). */
    public static final int ORDER = 4;

    /** Reads a request with {@code response_type=token}. */
    private final AuthenticationConverter converter;

    /** Grants the request. */
    private final AuthenticationProvider provider;

    /** Redirects with the token in the fragment. */
    private final AuthenticationSuccessHandler responseHandler;

    /**
     * Customizes the authorization endpoint.
     *
     * @param server configurer of the authorization server.
     */
    @Override
    public void customize(final OAuth2AuthorizationServerConfigurer server) {
        server.authorizationEndpoint(endpoint -> endpoint
                .authorizationRequestConverters(converters -> converters.addFirst(converter))
                .authenticationProviders(providers -> providers.addFirst(provider))
                .authorizationResponseHandler(responseHandler));
    }
}

Reading the request

/**
 * Reads an authorization request with {@code response_type=token}. The framework refuses that response type; this
 * converter, installed first, takes it over for the one client of the legacy flow and refuses it, with the same
 * {@code unsupported_response_type} and no redirect, for any other client.
 */
public class LegacyImplicitAuthorizationRequestConverter implements AuthenticationConverter {

    /** Response type of the implicit flow. */
    public static final String RESPONSE_TYPE_TOKEN = "token";

    /** Identifier of the only client that may use the flow. */
    private final String clientId;

    /** Matches a {@code GET} of the authorization endpoint. */
    private final RequestMatcher authorizationRequest;

    /**
     * Creates the converter.
     *
     * @param clientId              identifier of the only client that may use the flow.
     * @param authorizationEndpoint path of the authorization endpoint.
     */
    public LegacyImplicitAuthorizationRequestConverter(final String clientId, final String authorizationEndpoint) {
        this.clientId = clientId;
        authorizationRequest = PathPatternRequestMatcher.withDefaults()
                .matcher(HttpMethod.GET, authorizationEndpoint);
    }

    /**
     * Reads the request.
     *
     * @param request the request.
     * @return the request of the legacy flow, or {@code null} when the request is not a {@code GET} of the
     *         authorization endpoint with {@code response_type=token}.
     * @throws OAuth2AuthorizationCodeRequestAuthenticationException {@code unsupported_response_type} (no redirect)
     *                                                               when the client is not the one of the legacy
     *                                                               flow, {@code invalid_request} (no redirect) when
     *                                                               a parameter is repeated.
     */
    @Override
    public Authentication convert(final HttpServletRequest request) {
        if (!authorizationRequest.matches(request)
                || !RESPONSE_TYPE_TOKEN.equals(request.getParameter(OAuth2ParameterNames.RESPONSE_TYPE))) {
            return null;
        }
        final var requestedClient = request.getParameter(OAuth2ParameterNames.CLIENT_ID);
        if (!clientId.equals(requestedClient)) {
            throw refused(OAuth2ErrorCodes.UNSUPPORTED_RESPONSE_TYPE);
        }
        if (isRepeated(request, OAuth2ParameterNames.CLIENT_ID) || isRepeated(request, OAuth2ParameterNames.SCOPE)
                || isRepeated(request, OAuth2ParameterNames.REDIRECT_URI)
                || isRepeated(request, OAuth2ParameterNames.STATE)) {
            throw refused(OAuth2ErrorCodes.INVALID_REQUEST);
        }
        final var scope = request.getParameter(OAuth2ParameterNames.SCOPE);
        final var scopes = StringUtils.hasText(scope)
                ? new LinkedHashSet<>(Arrays.asList(StringUtils.delimitedListToStringArray(scope.trim(), " ")))
                : new LinkedHashSet<String>();
        scopes.remove("");
        return new LegacyImplicitAuthorizationRequestToken(requestedClient,
                request.getParameter(OAuth2ParameterNames.REDIRECT_URI), scopes,
                request.getParameter(OAuth2ParameterNames.STATE), currentUser());
    }

    /**
     * Tells whether a parameter is sent more than once.
     *
     * @param request the request.
     * @param name    name of the parameter.
     * @return {@code true} when it has more than one value.
     */
    private static boolean isRepeated(final HttpServletRequest request, final String name) {
        final var values = request.getParameterValues(name);
        return values != null && values.length > 1;
    }

    /**
     * Reads the user of the request from the security context, an anonymous one when there is none.
     *
     * @return the user.
     */
    private static Authentication currentUser() {
        final var current = SecurityContextHolder.getContext().getAuthentication();
        return current != null ? current : new AnonymousAuthenticationToken("anonymous", "anonymous",
                AuthorityUtils.createAuthorityList("ROLE_ANONYMOUS"));
    }

    /**
     * Builds the refusal, which carries no authentication and so is answered with {@code 400}.
     *
     * @param code error code.
     * @return the exception.
     */
    private static OAuth2AuthorizationCodeRequestAuthenticationException refused(final String code) {
        return new OAuth2AuthorizationCodeRequestAuthenticationException(new OAuth2Error(code), null);
    }
}

Granting the request

The provider is the longest piece. Read it for the order of the checks: client, grant type, exact redirect URI, signed-in user, multi-factor policy, state, scopes, and only then the token.

/**
 * Grants the legacy implicit request: after checking the client, its redirect URI, the user, the multi-factor policy,
 * the {@code state} and the scopes, it issues an access token (never a refresh token) through the token generator,
 * stores the authorization (so the token can be introspected and revoked) and returns it for the response handler.
 */
@RequiredArgsConstructor
public class LegacyImplicitAuthenticationProvider implements AuthenticationProvider {

    /** Grant type recorded for the tokens of the flow; the framework has no constant for it. */
    public static final AuthorizationGrantType IMPLICIT = new AuthorizationGrantType("implicit");

    /** Finds the client. */
    private final RegisteredClientRepository registeredClients;

    /** Stores the authorization behind the token. */
    private final OAuth2AuthorizationService authorizationService;

    /** Generates the access token, with the claims of the other flows. */
    private final OAuth2TokenGenerator<? extends OAuth2Token> tokenGenerator;

    /** Applies the multi-factor policy. */
    private final MfaAuthorizationManager authorizationManager;

    /** Longest lifetime of the tokens of the flow. */
    private final Duration maxAccessTokenTtl;

    /**
     * Grants or refuses the request.
     *
     * @param authentication the request, a {@link LegacyImplicitAuthorizationRequestToken}.
     * @return the access token, or the error that must be sent in the fragment of the redirect URI.
     * @throws AuthenticationException {@code unsupported_response_type} or {@code unauthorized_client} when the
     *                                 client is unknown or may not use the flow, {@code invalid_request} when the
     *                                 redirect URI is missing or not registered or the user is not signed in (none
     *                                 of them redirects), {@link SecondFactorRequiredException} when the user owes a
     *                                 second factor, or {@code server_error} when no token can be generated.
     */
    @Override
    public Authentication authenticate(final Authentication authentication) throws AuthenticationException {
        final var request = (LegacyImplicitAuthorizationRequestToken) authentication;
        final var client = registeredClients.findByClientId(request.getClientId());
        if (client == null) {
            throw refused(OAuth2ErrorCodes.UNSUPPORTED_RESPONSE_TYPE);
        }
        if (!client.getAuthorizationGrantTypes().contains(IMPLICIT)) {
            throw refused(OAuth2ErrorCodes.UNAUTHORIZED_CLIENT);
        }
        final var redirectUri = request.getRedirectUri();
        if (redirectUri == null || !client.getRedirectUris().contains(redirectUri)) {
            throw refused(OAuth2ErrorCodes.INVALID_REQUEST);
        }
        final var user = (Authentication) request.getPrincipal();
        if (!MfaAuthorizationManager.isUser(user)) {
            throw refused(OAuth2ErrorCodes.INVALID_REQUEST);
        }
        if (!authorizationManager.evaluate(user, authorizationManager.clientRequiresMfa(client.getClientId()))
                .isGranted()) {
            throw new SecondFactorRequiredException();
        }
        final var state = request.getState();
        if (state == null || state.isBlank()) {
            return new LegacyImplicitErrorToken(OAuth2ErrorCodes.INVALID_REQUEST, "state is required", redirectUri,
                    null);
        }
        final Set<String> scopes = request.getScopes().isEmpty()
                ? new LinkedHashSet<>(client.getScopes()) : new LinkedHashSet<>(request.getScopes());
        if (!client.getScopes().containsAll(scopes)) {
            return new LegacyImplicitErrorToken(OAuth2ErrorCodes.INVALID_SCOPE, null, redirectUri, state);
        }
        return issue(request, client, user, scopes);
    }

    /**
     * Tells which requests this provider handles.
     *
     * @param authentication the type of the request.
     * @return {@code true} for a request of the legacy flow.
     */
    @Override
    public boolean supports(final Class<?> authentication) {
        return LegacyImplicitAuthorizationRequestToken.class.isAssignableFrom(authentication);
    }

    /**
     * Issues and stores the access token.
     *
     * @param request the request.
     * @param client  the client.
     * @param user    the signed-in user.
     * @param scopes  the scopes granted.
     * @return the result.
     */
    private LegacyImplicitAccessTokenToken issue(final LegacyImplicitAuthorizationRequestToken request,
            final RegisteredClient client, final Authentication user, final Set<String> scopes) {
        final var cappedClient = withCappedLifetime(client);
        final var context = DefaultOAuth2TokenContext.builder()
                .registeredClient(cappedClient)
                .principal(user)
                .authorizationServerContext(AuthorizationServerContextHolder.getContext())
                .authorizedScopes(scopes)
                .tokenType(OAuth2TokenType.ACCESS_TOKEN)
                .authorizationGrantType(IMPLICIT)
                .authorizationGrant(request)
                .build();
        final OAuth2Token generated = tokenGenerator.generate(context);
        if (generated == null) {
            throw new OAuth2AuthenticationException(new OAuth2Error(OAuth2ErrorCodes.SERVER_ERROR,
                    "The token generator failed to generate the access token.", null));
        }
        final var accessToken = new OAuth2AccessToken(OAuth2AccessToken.TokenType.BEARER, generated.getTokenValue(),
                generated.getIssuedAt(), generated.getExpiresAt(), scopes);
        final var claims = generated instanceof ClaimAccessor accessor ? accessor.getClaims() : null;
        final var format = client.getTokenSettings().getAccessTokenFormat().getValue();
        final var authorization = OAuth2Authorization.withRegisteredClient(client)
                .principalName(user.getName())
                .authorizationGrantType(IMPLICIT)
                .authorizedScopes(scopes)
                .attribute(Principal.class.getName(), user)
                .token(accessToken, metadata -> {
                    metadata.put(OAuth2Authorization.Token.CLAIMS_METADATA_NAME, claims);
                    metadata.put(OAuth2Authorization.Token.INVALIDATED_METADATA_NAME, false);
                    metadata.put(OAuth2TokenFormat.class.getName(), format);
                })
                .build();
        authorizationService.save(authorization);
        return new LegacyImplicitAccessTokenToken(accessToken, scopes, request.getRedirectUri(), request.getState());
    }

    /**
     * Copies the client with the lifetime of its access tokens limited to the maximum of the flow.
     *
     * @param client the client.
     * @return the client with the lifetime {@code min(client, maximum)}.
     */
    private RegisteredClient withCappedLifetime(final RegisteredClient client) {
        final var settings = client.getTokenSettings();
        if (settings.getAccessTokenTimeToLive().compareTo(maxAccessTokenTtl) <= 0) {
            return client;
        }
        return RegisteredClient.from(client)
                .tokenSettings(TokenSettings.withSettings(settings.getSettings())
                        .accessTokenTimeToLive(maxAccessTokenTtl).build())
                .build();
    }

    /**
     * Builds a refusal that is answered with {@code 400}, never redirected, because the redirect URI is not trusted
     * yet or the user cannot be sent anywhere.
     *
     * @param code error code.
     * @return the exception.
     */
    private static OAuth2AuthorizationCodeRequestAuthenticationException refused(final String code) {
        return new OAuth2AuthorizationCodeRequestAuthenticationException(new OAuth2Error(code), null);
    }
}

Answering with the fragment

/**
 * Answers the authorization endpoint: for the two results of the legacy implicit flow it redirects with {@code 302} to
 * the registered redirect URI and carries the token, or the error, in its fragment (so it never reaches a server log
 * as a query would); any other result is the framework's authorization code response and goes to the delegate. The
 * response is never cached and the browser sends no referrer, so the fragment does not leak through the next request.
 */
@RequiredArgsConstructor
public class LegacyImplicitResponseHandler implements AuthenticationSuccessHandler {

    /** Value of {@code Cache-Control} of the response. */
    static final String NO_STORE = "no-store";

    /** Value of {@code Referrer-Policy} of the response. */
    static final String NO_REFERRER = "no-referrer";

    /** Name of the {@code Referrer-Policy} header. */
    private static final String REFERRER_POLICY = "Referrer-Policy";

    /** Token type reported to the client. */
    private static final String BEARER = "Bearer";

    /** Answers the results that are not the legacy flow's. */
    private final AuthenticationSuccessHandler delegate;

    /**
     * Answers a result.
     *
     * @param request        the request.
     * @param response       the response.
     * @param authentication the result of the authorization request.
     * @throws IOException      if the response cannot be written.
     * @throws ServletException if the delegate fails.
     */
    @Override
    public void onAuthenticationSuccess(final HttpServletRequest request, final HttpServletResponse response,
            final Authentication authentication) throws IOException, ServletException {
        if (authentication instanceof LegacyImplicitAccessTokenToken granted) {
            redirect(response, granted.getRedirectUri(), grantedFragment(granted));
        } else if (authentication instanceof LegacyImplicitErrorToken refused) {
            redirect(response, refused.getRedirectUri(), errorFragment(refused));
        } else {
            delegate.onAuthenticationSuccess(request, response, authentication);
        }
    }

    /**
     * Builds the fragment of a granted request.
     *
     * @param granted the result.
     * @return the encoded fragment.
     */
    private static String grantedFragment(final LegacyImplicitAccessTokenToken granted) {
        final var token = granted.getAccessToken();
        final var parameters = new ArrayList<String>();
        parameters.add(parameter(OAuth2ParameterNames.ACCESS_TOKEN, token.getTokenValue()));
        parameters.add(parameter(OAuth2ParameterNames.TOKEN_TYPE, BEARER));
        parameters.add(parameter(OAuth2ParameterNames.EXPIRES_IN, Long.toString(expiresIn(token))));
        parameters.add(parameter(OAuth2ParameterNames.SCOPE, String.join(" ", granted.getScopes())));
        addState(parameters, granted.getState());
        return String.join("&", parameters);
    }

    /**
     * Builds the fragment of a refusal.
     *
     * @param refused the result.
     * @return the encoded fragment.
     */
    private static String errorFragment(final LegacyImplicitErrorToken refused) {
        final var parameters = new ArrayList<String>();
        parameters.add(parameter(OAuth2ParameterNames.ERROR, refused.getError()));
        if (StringUtils.hasText(refused.getDescription())) {
            parameters.add(parameter(OAuth2ParameterNames.ERROR_DESCRIPTION, refused.getDescription()));
        }
        addState(parameters, refused.getState());
        return String.join("&", parameters);
    }

    /**
     * Adds the state, when the request had one.
     *
     * @param parameters the encoded parameters.
     * @param state      the state, may be {@code null}.
     */
    private static void addState(final ArrayList<String> parameters, final String state) {
        if (StringUtils.hasText(state)) {
            parameters.add(parameter(OAuth2ParameterNames.STATE, state));
        }
    }

    /**
     * Encodes one parameter.
     *
     * @param name  name of the parameter.
     * @param value value of the parameter.
     * @return {@code name=value}, with the value encoded.
     */
    private static String parameter(final String name, final String value) {
        return name + "=" + UriUtils.encodeQueryParam(value, StandardCharsets.UTF_8);
    }

    /**
     * Computes the lifetime of a token in seconds.
     *
     * @param token the token.
     * @return the seconds between its issue and its expiry.
     */
    private static long expiresIn(final OAuth2AccessToken token) {
        return Duration.between(token.getIssuedAt(), token.getExpiresAt()).getSeconds();
    }

    /**
     * Sends the redirect, with the headers that keep the fragment private.
     *
     * @param response    the response.
     * @param redirectUri the registered redirect URI.
     * @param fragment    the encoded fragment.
     * @throws IOException if the response cannot be written.
     */
    private static void redirect(final HttpServletResponse response, final String redirectUri, final String fragment)
            throws IOException {
        response.setHeader(HttpHeaders.CACHE_CONTROL, NO_STORE);
        response.setHeader(REFERRER_POLICY, NO_REFERRER);
        response.sendRedirect(redirectUri + "#" + fragment);
    }
}

Reference: Authentication architecture

The demo page

The page is static HTML plus a script. The HTML (legacy-implicit/index.html, implicit-demo-page region) carries a no-referrer meta tag and a warning that the flow is demonstration only. The script generates a random state, keeps it in sessionStorage, sends the browser to the authorization endpoint, and on return reads the fragment, removes it from the address bar and the history, checks the state, and decodes the claims of the token to show them. It exists to make the exposure visible: any script on the page could read the same token the same way.

(function () {
  'use strict';

  var STATE_KEY = 'legacy-implicit-state';
  var status = document.getElementById('status');
  var claims = document.getElementById('claims');
  var button = document.getElementById('sign-in');

  function randomState() {
    var bytes = new Uint8Array(16);
    crypto.getRandomValues(bytes);
    return Array.prototype.map.call(bytes, function (b) {
      return ('0' + b.toString(16)).slice(-2);
    }).join('');
  }

  function decodeClaims(token) {
    var parts = token.split('.');
    if (parts.length !== 3) {
      return { note: 'The access token is opaque (a reference token), there are no claims to show.' };
    }
    var base64 = parts[1].replace(/-/g, '+').replace(/_/g, '/');
    return JSON.parse(decodeURIComponent(Array.prototype.map.call(atob(base64), function (c) {
      return '%' + ('00' + c.charCodeAt(0).toString(16)).slice(-2);
    }).join('')));
  }

  function signIn() {
    var state = randomState();
    sessionStorage.setItem(STATE_KEY, state);
    var url = new URL('/oauth2/authorize', window.location.origin);
    url.searchParams.set('response_type', 'token');
    url.searchParams.set('client_id', button.dataset.clientId);
    url.searchParams.set('redirect_uri', window.location.origin + window.location.pathname);
    url.searchParams.set('scope', button.dataset.scope);
    url.searchParams.set('state', state);
    window.location.assign(url.toString());
  }

  function readFragment() {
    var fragment = window.location.hash.replace(/^#/, '');
    if (!fragment) {
      return;
    }
    var params = new URLSearchParams(fragment);
    var expected = sessionStorage.getItem(STATE_KEY);
    sessionStorage.removeItem(STATE_KEY);
    // the fragment must not stay in the address bar or in the history
    history.replaceState(null, document.title, window.location.pathname + window.location.search);
    if (!expected || params.get('state') !== expected) {
      status.textContent = 'Refused: the state of the response does not match the request (possible forgery).';
      return;
    }
    if (params.get('error')) {
      status.textContent = 'The server refused the request: ' + params.get('error');
      return;
    }
    status.textContent = 'Token received, valid for ' + params.get('expires_in') + ' seconds, scope: '
      + params.get('scope') + '.';
    claims.textContent = JSON.stringify(decodeClaims(params.get('access_token')), null, 2);
    claims.hidden = false;
  }

  button.addEventListener('click', signIn);
  readFragment();
}());

Reference: MDN, Window.sessionStorage.

API

There is no new REST endpoint. The flow uses the standard authorization endpoint, and the profile only changes how it answers response_type=token.

Situation Answer Why

Default profiles, any client

400, unsupported_response_type, no redirect

The framework does not support the response type.

Profile on, a client other than legacy-implicit-spa

400, unsupported_response_type, no redirect

The converter refuses it before any redirect URI is trusted.

Tests

None of these classes carries a documentation tag, so they are described rather than listed.

  • ImplicitRejectedIT runs with the default profiles and proves that the flow does not exist: response_type=token is answered 400 unsupported_response_type with no redirect, for a public client of the code flow and for an unknown response type alike, and the demo page is not served.

  • LegacyImplicitIT runs under the legacy-implicit profile against a real database. It proves that the legacy client gets a Bearer token in the fragment, short-lived and with the resource server audience, that a browser without a session is sent to the login page, that another client gets unsupported_response_type, that an unregistered redirect URI gets no redirect, that a missing state is refused in the fragment, that the code flow keeps working next to it, and that the demo page and its script are served.

  • LegacyImplicitEndToEndIT, in the e2e-tests module, runs the packaged server under dev,legacy-implicit: headless Chromium opens the demo page, signs the demo user in, and the page shows the claims of the token it received and that the state it sent came back. The same request from spa-public gets an error and no token.

  • Unit tests cover each class of the package: the converter, the provider, the response handler, the properties validation, the configuration, the token generator factory and the seeder.

Migration guide

Moving an application off the implicit flow is mostly a client-side change. The authorization server already supports the targets; the work is in the application and in tracking who still depends on the old behaviour.

Choosing the target

Situation Target Why

A browser application that is served by, or can sit behind, a server you control

The backend-for-frontend (Option 1)

No token ever reaches the browser. This is the recommendation of the OAuth browser-based apps guidance and the shape of this guide’s own SPA.

A static site on a CDN with no server component you can add

A public client with authorization code and PKCE (Option 2)

PKCE removes the token from the URL and binds the code to the client that asked for it. The tokens still live in the page.

A native or desktop application that used the implicit flow through an embedded browser

Authorization code and PKCE through the system browser (Option 2), with a claimed HTTPS or loopback redirect URI

RFC 8252 replaces embedded browsers and implicit with the system browser and PKCE.

A server-side application that used the implicit flow only because it was the easiest to wire

A confidential client with authorization code (and PKCE)

The application can keep a secret; it should authenticate at the token endpoint and keep tokens on the server.

A script or job that obtained a user token with the implicit flow to call an API as itself

Client credentials, see Client Credentials & Service-to-Service

A machine caller has no user; it should not borrow one.

References: RFC 8252, OAuth 2.0 for Native Apps and OAuth 2.0 for Browser-Based Applications (Internet-Draft).

Option 1: the backend-for-frontend (preferred for browser applications)

The strongest replacement is to take the tokens out of the browser altogether. A small server-side component, the backend-for-frontend (BFF), is the OAuth client: it runs the authorization code flow with PKCE, keeps the access and refresh tokens in its own session, and gives the SPA only an HttpOnly session cookie. The SPA calls the BFF, which adds the token when it relays the call to the resource server.

  • What changes in the SPA: it stops building authorization requests and parsing fragments. It starts a login by navigating to the BFF, calls the BFF’s own API with the cookie, and handles the CSRF protection the BFF requires.

  • What changes on the server: a confidential client for the BFF, a registered redirect URI on the BFF’s host, and the BFF itself.

  • What goes away: the token in the URL, the token in browser storage, and every script of the page being able to read it.

The SPA’s side of the conversation changes from talking to the authorization server to talking only to its own BFF. Before, the SPA built the authorization request itself and read the token from the fragment:

GET /oauth2/authorize?response_type=token&client_id=legacy-implicit-spa&redirect_uri=...&scope=documents.read&state=... HTTP/1.1
Host: localhost:9000

HTTP/1.1 302 Found
Location: https://spa.example/callback#access_token=...&token_type=Bearer&expires_in=...&state=...

GET /api/documents HTTP/1.1
Host: resource-server.example
Authorization: Bearer <the token read from the fragment>

After, the SPA navigates to the BFF to sign in and never sees a token; every API call carries only the session cookie and the CSRF header:

GET /bff/login?returnTo=/ HTTP/1.1
Host: localhost:8080

HTTP/1.1 302 Found
Location: /oauth2/authorization/bff
Set-Cookie: __Host-SESSION=...; Path=/; Secure; HttpOnly; SameSite=Lax

GET /bff/user HTTP/1.1
Host: localhost:8080
Cookie: __Host-SESSION=...

GET /api/documents HTTP/1.1
Host: localhost:8080
Cookie: __Host-SESSION=...; XSRF-TOKEN=...
X-XSRF-TOKEN: ...

The BFF runs authorization code with PKCE as the confidential bff client and relays /api/** to the resource server with the access token it keeps in the session. The requests above are those of the example’s BFF (GET /bff/login, GET /bff/user, POST /bff/logout, relayed /api/**); its filter chain, session handling, relaying of calls and logout are on Backend-for-Frontend (BFF). The reasoning is in Browser-Based Apps (SPAs). Reference: Spring Security OAuth 2.0 Login.

What to delete from the SPA when the BFF is in place:

  • the code that builds the authorization URL, generates state and parses location.hash;

  • every place that stores or reads a token (sessionStorage, localStorage, an in-memory store) and every Authorization header the SPA adds;

  • the silent re-authentication in a hidden iframe (prompt=none) that implicit SPAs use to renew tokens; the BFF renews tokens with its refresh token, out of sight of the browser;

  • the decoding of the access token to show the user’s name: the SPA asks GET /bff/user instead, which returns only UI-safe claims.

Option 2: a public client with authorization code and PKCE

When a BFF is not possible (a static site with no server component, or a native application), use the authorization code flow with PKCE as a public client:

  1. register the application as a public client (none for client authentication) with the grant types authorization_code and refresh_token, and with PKCE required;

  2. replace response_type=token with response_type=code, add a code_challenge (S256) and keep state;

  3. exchange the code at the token endpoint with the code_verifier;

  4. keep the redirect URI an exact match, and consider rotating refresh tokens, which the example does by default.

The requests change in two places. The authorization request asks for a code and carries the PKCE challenge, and the callback exchanges the code with the verifier that only this browser tab holds:

GET /oauth2/authorize?response_type=code&client_id=spa-public&redirect_uri=...&scope=documents.read&state=...&code_challenge=...&code_challenge_method=S256 HTTP/1.1
Host: localhost:9000

HTTP/1.1 302 Found
Location: https://spa.example/callback?code=...&state=...

POST /oauth2/token HTTP/1.1
Host: localhost:9000
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&client_id=spa-public&code=...&redirect_uri=...&code_verifier=...

The response carries the access token, and a refresh token if the client has that grant, in the body of a POST, not in the URL. Reference: RFC 7636, Proof Key for Code Exchange.

What changes in the application code:

  • the callback reads code and state from the query string instead of access_token from the fragment, and removes them from the address bar after use;

  • the code verifier is generated per sign-in (at least 43 characters from a cryptographic random source), kept only until the callback, and never sent anywhere but the token endpoint;

  • token renewal uses the refresh token instead of a hidden iframe; with refresh-token rotation, a used refresh token must be replaced by the new one in the response, and a second use of an old one revokes the family (see Access, Refresh & ID Tokens);

  • the token endpoint must accept a cross-origin POST from the SPA’s origin, so its CORS configuration must name that origin exactly.

The client settings (PKCE, consent, token lifetimes, refresh rotation) and the way the example seeds a public client, spa-public, are on Registered Clients & Client Management. A public client in a browser still keeps tokens in the page, which is why the BFF is preferred; the residual risks are listed in the Browser-Based Apps page.

Cutting over without breaking users

Run the old and the new client side by side and move traffic, not code, at the moment of the switch:

flowchart LR A["Inventory: who still asks for response_type=token"] --> B["Register the replacement client next to the legacy one"] B --> C["Release the migrated application behind a switch"] C --> D{"Tokens issued to the legacy client still above zero?"} D -- yes --> E["Find the remaining callers in the logs and contact their owners"] E --> D D -- no --> F["Make the migrated release the default"] F --> G["Rollback window ends"] G --> H["Remove implicit from the legacy client, or delete the client"] H --> I["Stop activating the legacy-implicit profile"] I --> J["response_type=token answers unsupported_response_type again"]

Points that decide whether the switch is invisible to users:

  • Tokens in flight. Access tokens issued by the implicit flow stay valid until they expire. In the example that is at most 15 minutes, so a rollback window of a day is plenty; with a longer legacy lifetime, wait at least that long before deleting the client, or revoke the tokens through /oauth2/revoke.

  • Sign-in state. The user’s session at the authorization server survives the change, so a user who signed in through the old application is not asked for a password again when the new one starts the code flow, unless the new client requires consent or a different multi-factor policy.

  • Logout. An implicit SPA usually "logs out" by dropping its token. The BFF ends its own session and the authorization server session with RP-initiated logout (POST /bff/logout). A public client should call the end-session endpoint and revoke its refresh token. Test both, because a user who believes they signed out and is silently signed in again is the most common complaint after a migration.

  • Redirect URIs. The code flow redirects with a query string, not a fragment. Register the new callback exactly; do not reuse the legacy client’s registration with an extra grant type, because the legacy client must eventually lose its grant without taking the new flow with it.

  • Stored tokens. On the first load of the migrated release, delete whatever the old release left in sessionStorage or localStorage, so no stale token is sent by a forgotten code path.

  • Content Security Policy. The implicit SPA needed a frame-src for the authorization server (silent renewal) and a connect-src for the resource server. With the BFF, both reduce to the BFF’s own origin; tighten the policy as part of the release.

Verifying the migration

Prove each step with a test rather than by inspection. The example’s own tests show the shape:

  • a test that runs without the profile and asserts unsupported_response_type and no redirect, like ImplicitRejectedIT, kept as a regression test after the profile is gone;

  • an end-to-end test of the replacement path, like the BFF sign-in tests on Backend-for-Frontend (BFF) or a code-plus-PKCE test against spa-public;

  • a check of the discovery document that response_types_supported does not list token;

  • after cut-over, a monitoring alert on any /oauth2/authorize request with response_type=token, so a forgotten caller shows up as a signal, not as a support ticket.

Auditing lingering implicit clients

Do not assume nobody uses the grant. Look at three places: the registered clients, the authorizations the server has issued, and the logs.

Registered clients. The Spring Authorization Server schema stores each client’s grant types in one comma-delimited column, oauth2_registered_client.authorization_grant_types. Select client_id, client_name, redirect_uris and client_authentication_methods from that table for the rows whose grant-type list contains the entry implicit. Match the whole entry, for example by wrapping both the column and the value in commas before comparing, so that a grant type that merely contains the word does not match. Check how your own repository writes the column before relying on it: this is the format of Spring’s JDBC repository.

Issued tokens. Every token the flow issues leaves an oauth2_authorization row whose authorization_grant_type is implicit. Join those rows to oauth2_registered_client on registered_client_id and group them by client_id, counting the rows and taking the earliest created_at and the latest access_token_issued_at, to see which clients actually received tokens and how recently.

The result is a lower bound: the example’s clean-up job deletes authorization rows that never got a token once they are old enough, and a deployment may purge others, so a client that stopped using the flow long ago may not appear. A client found among the registered clients but absent from the issued tokens is a candidate for removal, not proof that nobody uses it.

Logs. The authorization request carries its response type in the query string, so search the reverse proxy and application access logs for requests to /oauth2/authorize that contain response_type=token. On a server that does not support the flow, each of those is an application that is already failing with unsupported_response_type. Also check the authorization server’s discovery document: if response_types_supported still advertises token, the deployment has not closed the door. The Legacy Grants page lists the same signals in general terms.

Deprecation checklist

  • Inventory: run the registered-client and issued-token checks above, search the logs, and list every application and owner that still uses response_type=token.

  • Communicate: tell each owner which replacement applies (the BFF or authorization code with PKCE), give a date, and say that the server will start answering unsupported_response_type.

  • Dual-run: register the replacement client next to the old one, release the migrated application behind a switch, and watch the issued tokens of the old client drop to zero.

  • Cut over: make the migrated application the default and keep the old release only for a rollback window.

  • Remove the grant: remove implicit from every client’s grant types, then confirm the registered-client check finds none.

  • Remove the profile: stop activating legacy-implicit in every environment, so response_type=token goes back to unsupported_response_type, and confirm it with a request.

Removing the grant and removing the profile are separate steps for a reason. In the example, LegacyImplicitClientSeeder upserts legacy-implicit-spa every time the profile starts, so a client you removed comes back while the profile is on.

Security notes and pitfalls

  • The token is in the URL. A fragment is not sent to the server, but it is visible in the address bar, in the browser history, to extensions and to every script on the page. The example reduces the leak paths (the fragment is cleared from the history by the demo script, the response carries Cache-Control: no-store and Referrer-Policy: no-referrer, and the demo page has a no-referrer meta tag), and none of that is available to an application you do not control.

  • Nothing binds the token to the client. There is no code to exchange and no code_verifier, so a token injected into a victim’s session cannot be detected, and the token is a plain Bearer token. A code flow can be combined with DPoP or mTLS; see Sender-Constrained Tokens.

  • Limits are mitigations, not fixes. One client, an exact redirect URI, a mandatory state, an audience and scope restriction, a lifetime of at most 15 minutes and no refresh token make a leak less useful. They do not change what the flow is.

  • The profile is not a deployment feature. It ships in the main source set only so that the end-to-end test can exercise it. It is inert without the legacy-implicit profile, and its settings file, its class Javadoc and the demo page all say never to enable it in production. Add a check to your deployment pipeline that fails if that profile is active.

  • Do not extend the example. Adding a second client, a wildcard redirect URI or refresh tokens to this flow removes the limits above one by one. If a client needs more, it needs a different flow.

  • Spring will not help. The converter, provider and handler are the example’s own code against a documented extension point, not framework behaviour. Treat them as a demonstration to read, not as a base to build on.
