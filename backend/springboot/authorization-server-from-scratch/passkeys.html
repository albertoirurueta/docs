Authorization Server from Scratch: Passkeys (WebAuthn)

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

What you build

This page adds passkeys to the example: public-key credentials held by an authenticator (a phone, a laptop, a security key or a password manager) and bound to the host name of the server. A passkey plays two roles:

  • a passwordless primary login: the user clicks a button on the login page, or picks the passkey that the browser offers in the username field, and signs in without typing anything;

  • a second factor after a password: a user who has at least one passkey is asked for it on the second-factor page instead of, or as an alternative to, a TOTP code.

The theory (what a passkey is, why it resists phishing, how synced and device-bound passkeys differ) lives in the OAuth Reference sections backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_passkeys_webauthn_fido2 and backend/oauth/authentication-methods-2fa-and-passwordless.adoc#_hardware_otp_tokens_and_passkeys_used_as_a_second_factor, and the Spring Boot options are compared in backend/oauth/spring-boot-authentication-methods.adoc#_passkeys. This page does not repeat them. For the protocol itself see the W3C Web Authentication Level 3 specification, and for a practical introduction passkeys.dev.

Spring Security 7.1 does most of the protocol work. Its webAuthn() DSL installs the four filters that serve the registration and authentication ceremonies, verifies the signed assertions with the WebAuthn4J library, and defines the repositories that store users and credentials. The example adds what a real server needs around them:

  • the factor: a PasskeyFactor that registers the FACTOR_WEBAUTHN authority as a strong primary factor, so a passkey alone satisfies the multi-factor policy and the tokens report it in amr and acr;

  • the rules of the chain: public endpoints, registration only for a session that satisfies the multi-factor policy, no framework-owned deletion, a session strategy that changes the session id, and a user service that refuses disabled accounts;

  • the pages and the browser script: a section of the login page, a button on the second-factor page and an account page where a passkey is named and registered;

  • the account API: list, rename and delete passkeys, with a step-up for the deletion;

  • the JSON mapper module that lets the WebAuthn types be stored in the authorization server’s serialized objects.

How it works

A passkey ceremony has two halves: the server produces a random challenge and the options of the ceremony, and the authenticator, reached through the browser’s navigator.credentials API, signs it. The browser refuses to talk to an authenticator for a relying party id that does not match the host of the page, which is what makes the credential phishing resistant. The server then checks the signature, the challenge, the origin and the relying party id.

Registration

The user is already signed in and opens the account page. The script of the page asks the framework endpoints for the creation options, hands them to the authenticator and sends back the new credential together with the name the user chose.

sequenceDiagram autonumber actor U as User participant JS as Browser script passkeys.js participant N as navigator.credentials participant A as Authenticator participant O as POST /webauthn/register/options participant R as POST /webauthn/register participant DB as user_entities and user_credentials U->>JS: Types a name and clicks Register JS->>O: POST with the CSRF header O->>DB: Find or create the user entity named like the account O-->>JS: challenge, rp, user, excludeCredentials JS->>JS: Decode challenge, user.id and excludeCredentials from base64url JS->>N: create(publicKey) N->>A: Create a credential for the relying party id A->>U: Asks for user verification A-->>N: Attestation object and client data N-->>JS: PublicKeyCredential JS->>R: POST credential and label R->>R: Verify challenge, origin and relying party id R->>DB: Save the credential record with its label R-->>JS: success true JS->>JS: Reload the account page

excludeCredentials lists the passkeys the account already has, so an authenticator that holds one is not registered a second time. If the session still has a second factor to complete, the options request is redirected to the second-factor page, and the script follows that redirect instead of showing an error.

Authentication

The same ceremony serves the login page (button or autofill) and the second-factor page. The options request carries no username: the authenticator picks a discoverable credential and sends its user handle, and the server finds the account from the stored credential.

sequenceDiagram autonumber actor U as User participant JS as Browser script passkeys.js participant N as navigator.credentials participant A as Authenticator participant O as POST /webauthn/authenticate/options participant L as POST /login/webauthn participant DB as user_entities and user_credentials U->>JS: Clicks Use a passkey, or picks one in the username field JS->>O: POST with the CSRF header O-->>JS: challenge, rpId, allowCredentials JS->>N: get(publicKey), conditional mediation for autofill N->>A: Sign the challenge for the relying party id A->>U: Asks for user verification A-->>N: authenticatorData, clientDataJSON, signature, userHandle N-->>JS: PublicKeyCredential JS->>L: POST the assertion L->>DB: Load the credential by id L->>L: Verify signature, challenge, origin, relying party id and counter L->>DB: Update signature count and last use L->>L: Load the user, refuse a disabled account, grant FACTOR_WEBAUTHN L-->>JS: authenticated true and redirectUrl JS->>JS: Go to the saved authorization request

When the user already signed in with a password, the success keeps the factors of the session: Spring Security merges the existing factor authorities into the result when the names match, so the user ends with FACTOR_PASSWORD and FACTOR_WEBAUTHN. That is why the user entity is named exactly like the username of the account. Multi-factor requirements, amr and acr are explained in Multi-Factor Authentication & Step-Up.

Data

Flyway migration V500 creates the two tables that Spring’s JDBC repositories use. They mirror the schema that ships with Spring Security (user-entities-schema.sql and user-credentials-schema.sql, which are also named in the JdbcUserCredentialRepository Javadoc), with three adjustments: the account name of a user entity is unique, so looking up the passkeys of an account has one answer; the creation and last use are instants (timestamp with time zone) like every other instant of the schema; and an index on the owner column.

CREATE TABLE user_entities
(
    id           varchar(1000) NOT NULL,
    name         varchar(100)  NOT NULL,
    display_name varchar(200),
    PRIMARY KEY (id),
    CONSTRAINT uq_user_entities_name UNIQUE (name)
);

CREATE TABLE user_credentials
(
    credential_id                varchar(1000) NOT NULL,
    user_entity_user_id          varchar(1000) NOT NULL,
    public_key                   bytea         NOT NULL,
    signature_count              bigint,
    uv_initialized               boolean,
    backup_eligible              boolean       NOT NULL,
    authenticator_transports     varchar(1000),
    public_key_credential_type   varchar(100),
    backup_state                 boolean       NOT NULL,
    attestation_object           bytea,
    attestation_client_data_json bytea,
    created                      timestamp with time zone,
    last_used                    timestamp with time zone,
    label                        varchar(1000) NOT NULL,
    PRIMARY KEY (credential_id)
);

CREATE INDEX ix_user_credentials_user_entity_user_id ON user_credentials (user_entity_user_id);

This is plain Flyway SQL; see the Spring Boot Flyway how-to.

The username of the account, unique. The merge of factors and the lookup of an account’s passkeys depend on it.

Code

Configuration

The relying party settings are bound once into a validated record. An invalid value stops the application at startup. A browser only accepts a credential whose relying party id is the host of the page, or a registrable suffix of it, so a deployment must set rp-id and allowed-origins to its public host name.

  passkeys:
    # Relying party of the passkeys (WebAuthn). The id is the host name credentials are scoped to and the origins are
    # the ones browsers may run the ceremonies from: both default to the local development values and must be set to
    # the public host name of a real deployment.
    rp-name: ${AUTHSERVER_PASSKEYS_RP_NAME:Irurueta Auth Server}
    rp-id: ${AUTHSERVER_PASSKEYS_RP_ID:localhost}
    allowed-origins: ${AUTHSERVER_PASSKEYS_ALLOWED_ORIGINS:http://localhost:9000}

These are ordinary Spring Boot properties; see the externalized configuration reference.

/**
 * Relying party settings of the passkeys (WebAuthn), bound once from {@code authserver.passkeys.*} and injected
 * wherever one of them is needed. An invalid value stops the application at startup. A browser only accepts a
 * credential whose relying party id is the host of the page (or a registrable suffix of it) and whose origin is one of
 * the allowed ones, so a deployment must set {@code rp-id} and {@code allowed-origins} to its public host name; the
 * shipped {@code application.yml} defaults to {@code localhost} for local runs only.
 *
 * @param rpName         name of the relying party shown by the authenticator (default {@code Irurueta Auth Server}).
 * @param rpId           relying party id: the host name credentials are scoped to.
 * @param allowedOrigins origins (scheme, host and port) the browser may run the WebAuthn ceremonies from.
 */
@ConfigurationProperties("authserver.passkeys")
public record PasskeyProperties(
        @DefaultValue("Irurueta Auth Server") String rpName,
        String rpId,
        List<String> allowedOrigins) {

    /**
     * Validates the settings and copies the origins.
     *
     * @throws IllegalArgumentException if the name or the id is blank, or there is no allowed origin or one is blank.
     */
    public PasskeyProperties {
        if (rpName == null || rpName.isBlank()) {
            throw new IllegalArgumentException("authserver.passkeys.rp-name must not be blank");
        }
        if (rpId == null || rpId.isBlank()) {
            throw new IllegalArgumentException("authserver.passkeys.rp-id must not be blank");
        }
        if (allowedOrigins == null || allowedOrigins.isEmpty()
                || allowedOrigins.stream().anyMatch(origin -> origin == null || origin.isBlank())) {
            throw new IllegalArgumentException(
                    "authserver.passkeys.allowed-origins must list at least one origin and none may be blank");
        }
        allowedOrigins = List.copyOf(allowedOrigins);
    }
}

A @ConfigurationProperties record with constructor binding is described in the Spring Boot constructor binding reference.

Installing it in the login chain

The login chain applies every LoginChainCustomizer bean, in order, before its catch-all rule. This configuration declares the passkey one, after the TOTP one, without editing any shared file.

    /**
     * Declares the customizer that enables {@code http.webAuthn(...)}, permits its public endpoints, keeps the
     * registration endpoints behind the multi-factor policy and removes the ones that would bypass the step-up. It is
     * applied after the TOTP customizer.
     *
     * @param properties           relying party settings.
     * @param authorizationManager applies the multi-factor policy.
     * @param userDetailsService   loads the account of the user a passkey belongs to.
     * @param userResolver         resolves the account of the signed-in user, for the lockout check.
     * @param lockoutUseCase       tells whether the second factor of a user is locked.
     * @return the customizer.
     */
    @Bean
    @Order(PasskeyChainCustomizer.ORDER)
    public LoginChainCustomizer passkeyChainCustomizer(final PasskeyProperties properties,
            final MfaAuthorizationManager authorizationManager, final UserDetailsService userDetailsService,
            final SecondFactorUserResolver userResolver, final CheckSecondFactorLockoutUseCase lockoutUseCase) {
        return new PasskeyChainCustomizer(properties, authorizationManager, userDetailsService, userResolver,
                lockoutUseCase);
    }

See the @Bean reference and the ordering of beans.

The customizer is where the rules are:

  • the options, the sign-in post and the script are public (CSRF stays on, and the script sends the token);

  • the framework’s DELETE /webauthn/register/{id} is denied, so a passkey can only be removed through the account API, which asks for a recent multi-factor sign-in;

  • the registration endpoints and the account page require a session that satisfies the multi-factor policy, so a session that only presented a password cannot register a passkey and then sign in with it, skipping the second factor;

  • a passkey used as a second factor is refused while the second factor of the user is locked;

  • webAuthn() receives the relying party and a post-processor that gives its filter the chain’s session strategy.

    @Override
    public void customize(final HttpSecurity http) {
        http.setSharedObject(UserDetailsService.class, new AccountStatusUserDetailsService(userDetailsService));
        http.authorizeHttpRequests(authorize -> authorize
                .requestMatchers(SCRIPT_PATH, AUTHENTICATION_OPTIONS_PATH, AUTHENTICATION_PATH).permitAll()
                .requestMatchers(HttpMethod.DELETE, PasskeyRegistrationAuthorizationManager.REGISTRATION_PATH + "/**")
                .denyAll()
                .requestMatchers(PasskeysPageController.PASSKEYS_PATH).access(mfaAuthorizationManager));
        http.addFilterBefore(
                new PasskeyRegistrationFilter(new PasskeyRegistrationAuthorizationManager(mfaAuthorizationManager)),
                AuthorizationFilter.class);
        http.addFilterBefore(
                new PasskeySecondFactorLockoutFilter(secondFactorUserResolver, checkSecondFactorLockoutUseCase),
                BasicAuthenticationFilter.class);
        http.webAuthn(webAuthn -> webAuthn
                .rpName(properties.rpName())
                .rpId(properties.rpId())
                .allowedOrigins(new LinkedHashSet<>(properties.allowedOrigins()))
                .disableDefaultRegistrationPage(true)
                .addObjectPostProcessor(new SessionStrategyPostProcessor(http)));
    }

Reference: Passkeys configuration.

The factor

A passkey alone satisfies the policy, because the authenticator proves possession of the key and, with user verification, the user as well. The tokens report hwk (RFC 8176, a key held in hardware or in a platform authenticator) in amr, together with pwd and mfa when a password came first. A synced passkey is reported the same way; the backup flags are exposed by the account API.

    /**
     * Declares the passkey factor.
     *
     * @return the factor.
     */
    @Bean
    public AuthenticationFactor passkeyAuthenticationFactor() {
        return new AuthenticationFactor(ID, AMR_VALUE, AUTHORITY, FactorStrength.PRIMARY_STRONG);
    }

The authority is Spring’s FactorGrantedAuthority.WEBAUTHN_AUTHORITY; see the FactorGrantedAuthority Javadoc.

Storing credentials

The framework defaults to in-memory repositories, which lose every passkey on restart. Exposing the JDBC ones as beans makes the configurer use them.

    /**
     * Creates the store of WebAuthn user entities (the user handle, the account name and its display name).
     *
     * @param jdbcTemplate JDBC template of the application datasource.
     * @return the user entity repository.
     */
    @Bean
    public PublicKeyCredentialUserEntityRepository publicKeyCredentialUserEntityRepository(
            final JdbcTemplate jdbcTemplate) {
        return new JdbcPublicKeyCredentialUserEntityRepository(jdbcTemplate);
    }

    /**
     * Creates the store of WebAuthn credentials (public key, signature counter, flags and label).
     *
     * @param jdbcTemplate JDBC template of the application datasource.
     * @return the credential repository.
     */
    @Bean
    public UserCredentialRepository userCredentialRepository(final JdbcTemplate jdbcTemplate) {
        return new JdbcUserCredentialRepository(jdbcTemplate);
    }

Reference: Passkeys persistence.

The authorization server serializes some objects with a Jackson mapper that only accepts allow-listed types. This contributor adds the WebAuthn module, and allows its types, in that mapper.

    /**
     * Creates the module of the passkeys and allows its types in the validator.
     *
     * @param validator builder of the polymorphic type validator of the authorization mapper.
     * @return the configured module.
     */
    @Override
    public JacksonModule module(final BasicPolymorphicTypeValidator.Builder validator) {
        final var webauthn = new WebauthnJacksonModule();
        webauthn.configurePolymorphicTypeValidator(validator);
        return webauthn;
    }

See the Spring Security Jackson support.

The pages

The account page controller renders the passkeys of the signed-in user. Renaming and deleting happen through the REST API; registering happens through the framework endpoints, driven by the script.

    /**
     * Renders the page.
     *
     * @return the passkeys page, with the passkeys of the signed-in user.
     */
    @Override
    public ResponseEntity<String> passkeysPage() {
        final var account = currentAccountResolver.resolve();
        return pageRenderer.render(VIEW_NAME,
                Map.of(PASSKEYS_ATTRIBUTE, passkeyViewMapper.toViews(listPasskeysUseCase.execute(account.username()))));
    }

This is a Spring MVC controller operation; see the Spring MVC controllers reference.

The login page fragment holds a username field with autocomplete="username webauthn", which lets the browser offer the passkeys it knows (conditional mediation), and a button. The endpoint URLs, the CSRF header and the messages are rendered into data- attributes, so the script contains nothing inline or hard-coded and the page’s Content-Security-Policy needs no nonce.

     th:data-error-url="@{/login?error}" th:data-failure-message="#{passkeys.login.failed}">
  <h2 th:text="#{passkeys.login.heading}">Sign in with a passkey</h2>
  <p>
    <label for="passkey-username" th:text="#{passkeys.login.username}">Username</label>

  </p>

The browser script

The WebAuthn API works on binary data, while the framework endpoints speak JSON, so the script converts the binary fields between base64url and ArrayBuffer. The authentication half asks for the options, calls navigator.credentials.get (with mediation: "conditional" for autofill) and posts the assertion. The server answers with the URL to continue to, normally the saved authorization request.

  /**
   * Runs an authentication ceremony and returns the URL the server wants the browser to go to next (the saved
   * authorization request, or the root).
   */
  async function authenticate(container, conditional) {
    var optionsResponse = await post(container, container.dataset.optionsUrl);
    if (!optionsResponse.ok) {
      throw new ServerError("options " + optionsResponse.status);
    }
    var options = await optionsResponse.json();
    options.challenge = base64url.decode(options.challenge);
    options.allowCredentials = (options.allowCredentials || []).map(function (credential) {
      return Object.assign({}, credential, { id: base64url.decode(credential.id) });
    });
    var request = { publicKey: options, signal: newSignal() };
    if (conditional) {
      request.mediation = "conditional";
    }
    var credential = await navigator.credentials.get(request);
    var response = credential.response;
    var loginResponse = await post(container, container.dataset.loginUrl, {
      id: credential.id,
      rawId: base64url.encode(credential.rawId),
      response: {
        authenticatorData: base64url.encode(response.authenticatorData),
        clientDataJSON: base64url.encode(response.clientDataJSON),
        signature: base64url.encode(response.signature),
        userHandle: response.userHandle ? base64url.encode(response.userHandle) : undefined
      },
      type: credential.type,
      clientExtensionResults: credential.getClientExtensionResults(),
      authenticatorAttachment: credential.authenticatorAttachment
    });
    if (!loginResponse.ok) {
      throw new ServerError("login " + loginResponse.status);
    }
    var result = await loginResponse.json();
    if (!result || !result.authenticated || !result.redirectUrl) {
      throw new ServerError("unexpected answer");
    }
    return result.redirectUrl;
  }

See the MDN reference for CredentialsContainer.get() and the Spring Security authentication ceremony.

The registration half hands the options to navigator.credentials.create, including excludeCredentials, and posts the new credential together with the label:

  /** Runs a registration ceremony for a passkey with the given name. */
  async function register(container, label) {
    var optionsResponse = await post(container, container.dataset.optionsUrl);
    if (optionsResponse.redirected) {
      // the session still has to complete its second factor: let the server send it there
      window.location.href = optionsResponse.url;
      return false;
    }
    if (!optionsResponse.ok) {
      throw new ServerError("options " + optionsResponse.status);
    }
    var options = await optionsResponse.json();
    options.challenge = base64url.decode(options.challenge);
    options.user = Object.assign({}, options.user, { id: base64url.decode(options.user.id) });
    options.excludeCredentials = (options.excludeCredentials || []).map(function (credential) {
      return Object.assign({}, credential, { id: base64url.decode(credential.id) });
    });
    var created = await navigator.credentials.create({ publicKey: options, signal: newSignal() });
    var response = created.response;
    var registerResponse = await post(container, container.dataset.registerUrl, {
      publicKey: {
        credential: {
          id: created.id,
          rawId: base64url.encode(created.rawId),
          response: {
            attestationObject: base64url.encode(response.attestationObject),
            clientDataJSON: base64url.encode(response.clientDataJSON),
            transports: response.getTransports ? response.getTransports() : []
          },
          type: created.type,
          clientExtensionResults: created.getClientExtensionResults(),
          authenticatorAttachment: created.authenticatorAttachment
        },
        label: label
      }
    });
    if (!registerResponse.ok) {
      throw new ServerError("register " + registerResponse.status);
    }
    var result = await registerResponse.json();
    if (!result || !result.success) {
      throw new ServerError("unexpected answer");
    }
    return true;
  }

See the MDN reference for CredentialsContainer.create() and the Spring Security registration ceremony.

API

Spring Security owns four endpoints. All of them are POST and need the CSRF token, because the options endpoints change server state:

Endpoint Who may call it Purpose

POST /webauthn/authenticate/options

Anyone

Returns the challenge, the relying party id and the allowed credentials of an authentication ceremony.

POST /login/webauthn

Anyone

Verifies the assertion. The answer is JSON, {"authenticated":true,"redirectUrl":"..."} on success and 401 on failure.

POST /webauthn/register/options

A session that satisfies the multi-factor policy

Returns the creation options, including excludeCredentials.

POST /webauthn/register

A session that satisfies the multi-factor policy

Verifies the attestation and stores the credential with its label. The answer is {"success":true}.

The example’s own account API lists, renames and deletes passkeys. It requires a bearer token issued by this server. The deletion also requires a recent multi-factor sign-in when the account has a confirmed second factor (the step-up of RFC 9470), and revokes every trusted device when it removes the last second factor.

Tests

None of the passkey tests carries a tag for inclusion, so they are described here.

  • PasskeyConfigurationIT checks the sign-in as the login chain applies it: the endpoints the chain permits with CSRF on, a passkey as the second factor after a password and as the only factor, the merge of the session’s factors, the resumption of the saved authorization request with a new session id, the claims of the issued tokens (the same as a password sign-in), the refusal of a disabled account and of a locked second factor, and the same answer for an unknown credential and a rejected assertion. The relying party operations are mocked, so it needs no authenticator.

  • PasskeyRegistrationIT runs the real operations and repositories: the user entity carries the username, a session that only presented a password cannot register a passkey while the account needs a second factor, the framework’s own removal endpoint and default page are gone, and the authentication options never depend on a username.

  • PasskeyPagesIT renders the pages: the passkey section of the login page with its external script, the script served anonymously, the second-factor page with and without a passkey, and the account page.

  • PasskeyAccountIT covers the account API: list, rename (including a blank or too long label), deletion, the step-up challenge, the revocation of trusted devices, and that an account never sees or touches another account’s passkeys.

  • JdbcPasskeyRepositoryIT runs against PostgreSQL on the V500 schema: lookups by account, ownership checks on rename and delete, the unique user entity name, and the round trip of the instants.

  • PasskeyEndToEndIT drives a real headless Chromium with a virtual authenticator (CTAP2, internal, resident key, user verified) through the Chrome DevTools Protocol, so the script runs the real ceremonies. It registers a passkey and signs in through the BFF with it alone, signs in with a password and completes the second-factor page with the passkey, and lets the browser offer the passkey in the username field.

These are Spring MockMvc and Testcontainers integration tests plus a browser test; see the Spring Security MockMvc testing reference and the Chrome DevTools WebAuthn emulation.

Security notes and pitfalls

  • Phishing resistance and the RP ID. The authenticator signs for a relying party id, and the browser refuses a page whose host does not match it. Set rp-id to the public host name (or a registrable suffix) and allowed-origins to the exact origins that run the ceremonies, never to a wildcard. The default localhost is for local runs only, and a credential registered under one relying party id does not work under another, so changing it later orphans every passkey.

  • User verification. A passkey proves possession of the key; with user verification (a biometric or a PIN) it also proves the user. The example treats a passkey as a strong primary factor on that basis, so keep user verification required for registrations and sign-ins that stand alone, and check the uv_initialized data if a policy needs it.

  • Synced and device-bound passkeys. A synced passkey survives a lost phone but is only as safe as the account that syncs it. The example reports both as hwk and exposes backupEligible and backedUp in the account API, so a client can warn about, or a policy can require, a device-bound credential.

  • Registration must not weaken the second factor. Registering a passkey adds a factor that signs in on its own, so the registration endpoints require a session that satisfies the multi-factor policy. Without that rule, a stolen password would be enough to enrol a passkey and bypass the second factor.

  • Deletion and the step-up. The framework’s deletion endpoint is denied; removing a passkey goes through the account API, which needs a recent multi-factor sign-in and, when it removes the last second factor, revokes the trusted devices. Deleting a passkey also removes the credential from the server only: the authenticator may keep its copy.

  • Account status. Spring’s WebAuthn provider trusts the user it loads. The decorated UserDetailsService makes a passkey sign-in refuse the disabled, locked or expired accounts that a password sign-in refuses.

  • Account recovery. A lost authenticator is the weak point: keep at least two passkeys or another second factor, and remember that a recovery path that bypasses the passkey is the real strength of the account. See backend/oauth/authentication-methods-2fa-and-passwordless.adoc#enrolment-and-account-recovery-the-weakest-link.

  • Attestation. The example accepts attestation as received and does not restrict authenticator models, which is right for a public service. Requiring a specific attestation is only worth the privacy cost and the maintenance of trust anchors in a closed fleet of managed security keys.

  • Counters and cloning. The signature counter is stored and updated, but synced passkeys often report zero, so a counter that does not grow is not by itself a sign of cloning.

  • Pitfalls. The creation and authentication options endpoints are POST and need the CSRF token. The script must decode challenge, user.id and every credential id from base64url before calling the browser, and encode the answer back. A failure of the automatic autofill sign-in must not redirect to the error page, or the page loads the script again and loops.

For the full reference see the Spring Security Passkeys section, the W3C Web Authentication Level 3 specification, passkeys.dev, RFC 8176 for the amr values, RFC 9470 for the step-up challenge and NIST SP 800-63B-4 for the policy side.
