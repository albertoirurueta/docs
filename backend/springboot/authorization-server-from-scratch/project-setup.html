Authorization Server from Scratch: Project Setup and Running the Example

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page gets the example running on your machine and explains how it is wired: the starters each module depends on and why, the Spring profiles, the local services started from compose.yaml, the order in which to start the applications, and what the development profile seeds. The map of the applications is in Architecture; the tables are in Data Model and Schema.

Clone the example

The example is not published as a package, so you build it from source. You need a JDK between 21 and 25 (the build enforces [21,26) because SpotBugs cannot parse the class files of newer JDKs), and Docker for the integration tests and for the local services. Maven itself is optional: the repository ships the Maven wrapper.

git clone https://github.com/albertoirurueta/irurueta-auth-server.git
cd irurueta-auth-server
./mvnw -v

The wrapper downloads the Maven version pinned in .mvn/wrapper/maven-wrapper.properties on first use. See the Maven Wrapper documentation for how it works.

The starters, module by module

The root pom.xml uses spring-boot-starter-parent 4.1.2, so every Spring Boot starter below is version-managed and carries its Boot 4.1 name, for example spring-boot-starter-webmvc and spring-boot-starter-security-oauth2-authorization-server. Each application is a reactor of small modules, and a dependency sits in the narrowest module that needs it:

Module Dependency Why it is there

auth-server/api/web

spring-boot-starter-security-oauth2-authorization-server

Spring Authorization Server: the protocol endpoints, the OIDC support and the RegisteredClientRepository, OAuth2AuthorizationService and consent service abstractions.

auth-server/api/web

spring-boot-starter-security-oauth2-client

Social login: the server is itself an oauth2Login() client of Google, Microsoft, Apple and GitHub.

auth-server/api/web

spring-boot-starter-security-oauth2-resource-server

The /api/** chain validates bearer JWTs issued by this same server.

auth-server/api/web

spring-boot-starter-webmvc, spring-boot-starter-thymeleaf, spring-boot-starter-validation

Servlet MVC for the controllers, Thymeleaf for the login, consent and account pages, Bean Validation for the DTOs.

auth-server/api/web

spring-security-webauthn

Passkeys (WebAuthn), added by a later page.

auth-server/api/web

springdoc-openapi-starter-webmvc-ui, thymeleaf-extras-springsecurity6, bcprov-jdk18on

Publishes the OpenAPI document, adds Spring Security helpers to the templates and provides the Bouncy Castle crypto primitives.

auth-server/infrastructure/persistence

spring-boot-starter-jdbc, spring-boot-starter-flyway, flyway-database-postgresql, postgresql

The JDBC adapters, the Flyway migrations applied at start and the PostgreSQL driver and dialect.

auth-server/infrastructure/keys

spring-security-oauth2-jose, spring-security-crypto

The signing keys (JWK) and the encryption of the private keys at rest.

auth-server/infrastructure/mail

spring-boot-starter-mail, spring-boot-starter-thymeleaf

The AccountMailer adapter and its e-mail templates.

auth-server/infrastructure/sms

libphonenumber, twilio, software.amazon.awssdk:sns

Phone number normalisation and the Twilio and Amazon SNS senders.

auth-server/infrastructure/github

spring-boot-starter-restclient, spring-boot-starter-jackson

The generated client of GitHub’s e-mail API behind a domain port.

auth-server/boot

spring-boot-starter-actuator, spring-boot-starter-validation, spring-boot-docker-compose (runtime, optional)

Health endpoints, validation of the configuration properties and the Docker Compose integration used by the dev profile.

bff/api/web

spring-boot-starter-security-oauth2-client, spring-boot-starter-webmvc

The oauth2Login() client and the controllers that serve /bff/** and relay /api/**.

bff/infrastructure/session

bff/infrastructure/resourceserver, service-client/infrastructure/resourceserver

spring-boot-starter-security-oauth2-resource-server, spring-boot-starter-webmvc

test-support

The shared PostgreSQL container base for the integration tests.

The names above were read from the pom.xml of each module. The root pom and the poms of several modules carry tagged regions, but this page does not paste their code; it only lists the dependency names. The starters follow the naming rules in the Spring Boot build systems reference.

Profiles

A Spring profile switches a set of beans and property files on or off, as explained in Configuration and Profiles. The example uses these:

  • dev (auth-server and bff): local development only. It starts the services of compose.yaml through spring-boot-docker-compose, points the mail relay at Mailpit, sets the local redirect URIs of the seeded clients and seeds the demo data below. Never activate it outside a developer machine.

  • test: activated by the integration tests. It selects a logging SMS sender that keeps its messages in memory.

  • legacy-implicit, twilio and sns: opt-in profiles used by later pages. legacy-implicit enables a demo of the removed implicit grant, and twilio or sns choose the SMS gateway. A deployment always activates one SMS profile, because auth-server refuses to start without an SMS gateway outside dev and test.

The profile files are application-<profile>.yml in each application’s boot module. See the Spring Boot profiles reference for the mechanism itself.

Local services with Docker Compose

The root compose.yaml starts PostgreSQL 18 and Mailpit for local development; it holds throwaway development credentials that must never be reused. The compose/init-databases.sql script creates one database per application next to the authserver one. The dev profile sets spring.docker.compose.file to ../../compose.yaml, relative to the boot module directory that spring-boot:run uses as its working directory, so Spring Boot starts the containers before the application context, takes the datasource connection details from them (the published PostgreSQL port is random) and stops them when the application stops. Starting the jar or an IDE configuration from another directory needs SPRING_DOCKER_COMPOSE_FILE to point to the file.

The compose file and the dev profiles carry tagged regions, but they are described here rather than listed. The mechanism comes from the Spring Boot Docker Compose support reference.

Run order

Start each application in its own terminal, with auth-server first, because the other applications resolve its issuer metadata:

./mvnw -pl auth-server/boot -am spring-boot:run -Dspring-boot.run.profiles=dev
./mvnw -pl resource-server/boot -am spring-boot:run
./mvnw -pl bff/boot -am spring-boot:run -Dspring-boot.run.profiles=dev

auth-server listens on port 9000, resource-server on 8081 and bff on 8080. The dev profile of auth-server logs the generated secret of the seeded bff client once at start; export it as BFF_CLIENT_SECRET before starting the bff, which refuses to start without it. Then open http://localhost:8080 and sign in. The service-client has no HTTP port and is started the same way when you want to see the client credentials grant. These are the Maven commands of the Spring Boot Maven plugin run goal.

Seeded demo data

Nothing is seeded by default. With the dev profile, auth-server seeds a user named demo whose generated password is written to the log at start, the confidential bff client with a generated secret, and the public device-client of a later page. A client is seeded only when its redirect URIs are configured: the dev profile configures the BFF on port 8080 and a single-page application on port 3000, and the secret of the bff client comes from the environment, never from the file. The definitions of the two default clients are tagged in the code:

    /**
     * Defines the {@code bff} client: confidential, {@code client_secret_basic}, authorization code with PKCE and
     * refresh tokens, with refresh token rotation on. It requires the end-user's consent to the requested scopes.
     *
     * @param redirectUris redirect URIs of the deployment.
     * @param apiAudience  audience of the authorization server's own API.
     * @return the client.
     */
    public static ClientRegistration bff(final List<String> redirectUris, final String apiAudience) {
        return bff(redirectUris, apiAudience, List.of());
    }

    /**
     * Defines the {@code bff} client with the URIs it may be sent to after an OpenID Connect RP-initiated logout.
     *
     * @param redirectUris           redirect URIs of the deployment.
     * @param apiAudience            audience of the authorization server's own API.
     * @param postLogoutRedirectUris post-logout redirect URIs of the deployment; none when empty.
     * @return the client.
     */
    public static ClientRegistration bff(final List<String> redirectUris, final String apiAudience,
                                         final List<String> postLogoutRedirectUris) {
        return new ClientRegistration(BFF_CLIENT_ID, "Backend for Frontend", true,
                List.of("client_secret_basic"), List.of("authorization_code", "refresh_token"),
                redirectUris, SCOPES, true, List.of(RESOURCE_SERVER_AUDIENCE, apiAudience), ACCESS_TOKEN_TTL,
                REFRESH_TOKEN_TTL, ClientRegistration.FORMAT_SELF_CONTAINED, false,
                postLogoutRedirectUris, true, false, null, null, null, null, false);
    }

    /**
     * Defines the {@code spa-public} client: public, authorization code with PKCE, no client authentication.
     *
     * @param redirectUris redirect URIs of the deployment.
     * @param apiAudience  audience of the authorization server's own API.
     * @return the client.
     */
    public static ClientRegistration spaPublic(final List<String> redirectUris, final String apiAudience) {
        return spaPublic(redirectUris, apiAudience, List.of());
    }

    /**
     * Defines the {@code spa-public} client with the URIs it may be sent to after an OpenID Connect RP-initiated
     * logout.
     *
     * @param redirectUris           redirect URIs of the deployment.
     * @param apiAudience            audience of the authorization server's own API.
     * @param postLogoutRedirectUris post-logout redirect URIs of the deployment; none when empty.
     * @return the client.
     */
    public static ClientRegistration spaPublic(final List<String> redirectUris, final String apiAudience,
                                               final List<String> postLogoutRedirectUris) {
        return new ClientRegistration(SPA_PUBLIC_CLIENT_ID, "Single-page application", false,
                List.of("none"), List.of("authorization_code", "refresh_token"),
                redirectUris, SCOPES, true, List.of(RESOURCE_SERVER_AUDIENCE, apiAudience), ACCESS_TOKEN_TTL,
                REFRESH_TOKEN_TTL, ClientRegistration.FORMAT_SELF_CONTAINED, false,
                postLogoutRedirectUris, false, false, null, null, null, null, false);
    }

These definitions are the RegisteredClient of Spring Authorization Server expressed as the application’s own ClientRegistration; see the registered client section of the core model reference.

The properties that decide which clients are seeded and where they redirect are tagged too:

  clients:
    # Secret of the confidential bff client, from the environment only; empty means the client is not seeded.
    bff-secret: ${AUTHSERVER_BFF_CLIENT_SECRET:}
    # Redirect URIs (comma-separated) of the default clients. A client is seeded only when its redirect URIs are
    # configured: nothing is seeded by default, and no localhost URI exists outside the dev profile.
    bff:
      redirect-uris: ${AUTHSERVER_BFF_REDIRECT_URIS:}
      # URIs (comma-separated) the user may be sent to after an RP-initiated logout (/connect/logout); none by default
      post-logout-redirect-uris: ${AUTHSERVER_BFF_POST_LOGOUT_REDIRECT_URIS:}
    spa-public:
      redirect-uris: ${AUTHSERVER_SPA_REDIRECT_URIS:}
      post-logout-redirect-uris: ${AUTHSERVER_SPA_POST_LOGOUT_REDIRECT_URIS:}

The ${NAME:default} placeholders are the externalised configuration of Spring Boot, where the part after the colon is the default.

How these pages show code

The pages of this guide never paste application code. Every listing is an include:: of a tagged region of the example repository, so the code you read is the code CI compiled and tested. In the example, a region is marked with a tag::name[] and an end::name[] comment around the lines to show, and the page includes it with include::irurueta-auth-server::example$<path>[tag=name]. The example repository is an Antora component of its own (its docs/antora.yml), and the Antora Collector extension copies each module’s src/**, the OpenAPI contracts under apis/ and the root pom.xml and compose.yaml into that component’s example$ family at build time, so a path such as example$auth-server/api/web/src/main/java/... is the module path inside the repository. Each listing is followed by a link to the official page it derives from. See the AsciiDoc tagged regions reference and the Antora Collector extension documentation.

Run the tests

./mvnw verify compiles every module, runs the unit tests (*Test, Surefire) and the integration tests (*IT, Failsafe) and every build gate, and writes the reports. ./mvnw test is the fast loop: unit tests only, no Spring context and no Docker. A single class in a single module:

./mvnw verify
./mvnw test
./mvnw -pl auth-server/api/web -am test -Dtest=LoginControllerTest

The integration tests do not use compose.yaml: they start their own PostgreSQL container through the test-support module. The page Unit and Integration Testing explains the test slices and Testcontainers that the example relies on, and the Spring Boot reference describes Testcontainers support and its @ServiceConnection wiring.

Continuous integration

Two workflows run in the example repository. .github/workflows/build.yml gates every push to main, develop and release_* branches and every pull request. It sets up JDK 21, caches the Playwright browsers, runs ./mvnw -B -ntp clean verify (build gates, unit and integration tests and the Playwright sign-in smoke test) and uploads the reports. .github/workflows/docs.yml runs on every push to main: it repeats the build so the reports have real data, stages the Maven site (Javadoc, JaCoCo and the static-analysis reports), renders the OpenAPI contracts, builds the example’s own Antora site and pushes all of it to the gh-pages branch. Only documentation is published: the applications are never deployed, so there is no release or deploy job. Both workflows are part of the Collector scan and build.yml carries a tag::setup-ci-build-job region, but they are described here rather than listed. See the GitHub Actions workflow reference.
