Authorization Server from Scratch: API Reference

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

What you build

The earlier pages added the endpoints one feature at a time. This page is the map: every URL the example serves, who defines it, which Spring component answers it, and where its page is. It has four groups:

  • the protocol endpoints, defined by RFCs and OpenID Connect specifications and answered by Spring Authorization Server;

  • the Spring Security authentication endpoints behind the login page, answered by Spring Security itself;

  • the custom APIs, defined by the OpenAPI contracts under apis/ of the example and answered by the controllers of the example;

  • the error model shared by all of them.

The theory of each protocol endpoint is in the OAuth Reference, starting at Discovery, Metadata and Client Registration and Opaque Tokens, Introspection and Revocation. This page lists what the example does with them. All examples assume the authorization server on http://localhost:9000 (the dev profile), the BFF on http://localhost:8080 and the resource server on http://localhost:8081. ${...} values are placeholders, and none is a real secret.

Protocol endpoints

The endpoints and who answers them

Spring Authorization Server registers these endpoints on the protocol filter chain, which SecurityConfig builds with OpenID Connect enabled. The chain matches server.getEndpointsMatcher(), so a path is answered only when its feature is enabled.

    /**
     * Creates the chain of the OAuth 2.1 and OpenID Connect protocol endpoints.
     *
     * @param http        security builder.
     * @param customizers protocol customizers, applied in order.
     * @return the protocol filter chain.
     * @throws Exception if the chain cannot be built.
     */
    @Bean
    @Order(1)
    public SecurityFilterChain authorizationServerSecurityFilterChain(
            final HttpSecurity http, final ObjectProvider<ProtocolChainCustomizer> customizers) throws Exception {
        http
                .oauth2AuthorizationServer(server -> {
                    http.securityMatcher(server.getEndpointsMatcher());
                    server.oidc(Customizer.withDefaults());
                    customizers.orderedStream().forEach(customizer -> customizer.customize(server));
                })
                .authorizeHttpRequests(authorize -> authorize.anyRequest().authenticated())
                .exceptionHandling(exceptions -> exceptions
                        .authenticationEntryPoint(new LoginUrlAuthenticationEntryPoint(LOGIN_PATH)));
        return http.build();
    }

    /**
     * Creates the chain of the login page and the rest of the user interface.
     *
     * @param http        security builder.
     * @param customizers login method customizers, applied in order.
     * @return the login/UI filter chain.
     * @throws Exception if the chain cannot be built.
     */
    @Bean
    @Order(2)
    public SecurityFilterChain loginSecurityFilterChain(
            final HttpSecurity http, final ObjectProvider<LoginChainCustomizer> customizers) throws Exception {
        http.formLogin(form -> form.loginPage(LOGIN_PATH).permitAll());
        // customizers run before the catch-all rule below, so they can still permit their own endpoints
        for (final var customizer : customizers.orderedStream().toList()) {
            customizer.customize(http);
        }
        http.authorizeHttpRequests(authorize -> authorize
                .requestMatchers(LOGIN_PATH, "/error", "/actuator/health/**", "/v3/api-docs/**").permitAll()
                .anyRequest().authenticated());
        return http.build();
    }

The discovery document

The discovery document is the only URL a client needs to know: it lists every other endpoint, so a Spring client configured with an issuer-uri finds the rest. The listing below keeps the fields that name the endpoints of this example and the algorithms and methods it supports. The field names are those of OpenID Connect Discovery and RFC 8414, and the endpoint values follow the issuer http://localhost:9000 and the paths in the table above.

Requests you can make with curl

These endpoints need no browser. The ones that need a signed-in user (/oauth2/authorize, consent and the second factor) are HTML pages, so curl stops at the redirect to /login.

Discovery and keys. Both are public:

curl -s http://localhost:9000/.well-known/openid-configuration
curl -s http://localhost:9000/oauth2/jwks

The JWK set lists the ACTIVE, the NEXT and the still-retained RETIRED keys, with no private part. See Publishing keys and signing with the active one.

Client credentials token. The client authenticates with HTTP Basic (client_secret_basic) and gets an access token whose subject is the client:

curl -s -u "${CLIENT_ID}:${CLIENT_SECRET}" http://localhost:9000/oauth2/token \
  -d grant_type=client_credentials \
  -d scope=documents.read

The answer has access_token, token_type (Bearer), expires_in and scope, and no refresh token. Other client authentication methods (private_key_jwt, mutual TLS) and token exchange are shown in Client Credentials & Service-to-Service, API.

Introspection and revocation. Both need client authentication. Introspection answers {"active":false} for a token that is revoked, expired or unknown:

curl -s -u "${CLIENT_ID}:${CLIENT_SECRET}" http://localhost:9000/oauth2/introspect \
  -d token="${ACCESS_TOKEN}"

curl -s -u "${CLIENT_ID}:${CLIENT_SECRET}" http://localhost:9000/oauth2/revoke \
  -d token="${REFRESH_TOKEN}" -d token_type_hint=refresh_token

Device authorization. The device sends only its client_id and polls the token endpoint with the device_code it gets back:

curl -s -X POST http://localhost:9000/oauth2/device_authorization \
  -d client_id=device-client

The dev profile seeds device-client. The full poll loop and its errors are on Other Passwordless Methods.

UserInfo. The access token of a signed-in user is the credential:

curl -s -H "Authorization: Bearer ${ACCESS_TOKEN}" http://localhost:9000/userinfo

The answer always has sub; the profile and email scopes add the claims listed on Access, Refresh & ID Tokens, API.

These requests are the ones of RFC 6749, Client Credentials Grant, RFC 7662, Introspection Request, RFC 7009, Revocation Request, RFC 8628, Device Authorization Request and OpenID Connect Core, UserInfo.

Custom APIs

The REST APIs of the example are contract first: the OpenAPI documents under apis/ are the source, and the controllers implement interfaces generated from them. The OpenApiDriftIT test of each application fails when the running application serves something different (see Testing tricks). The documents are apis/auth-server/rest-server/auth-server-api-v1.yaml, apis/auth-server/web-pages/auth-server-pages-v1.yaml, apis/bff/rest-server/bff-api-v1.yaml, apis/resource-server/rest-server/resource-server-api-v1.yaml and apis/github/rest-server/github-api-v1.yaml (the GitHub calls the server makes, not an API it serves). Each is in the apis folder of the repository.

How the account and administration APIs are secured

/api/** has its own chain, ahead of the protocol chain. It is stateless, validates a bearer JWT issued by this server, requires the audience authserver.api.audience (default auth-server), refuses the purpose-bound account tokens that are signed by the server but never meant as bearer tokens, and answers /api/admin/** only to a token with the scope admin. Registration, e-mail verification and the two password-reset endpoints are the only anonymous ones.

    /**
     * Creates the chain of the REST API.
     *
     * @param http      security builder.
     * @param jwkSource the published keys of this server.
     * @param issuer    issuer of this server ({@code spring.security.oauth2.authorizationserver.issuer}).
     * @param audience  audience the API requires ({@code authserver.api.audience}).
     * @return the API filter chain.
     * @throws Exception if the chain cannot be built.
     */
    @Bean
    @Order(0)
    public SecurityFilterChain apiSecurityFilterChain(
            final HttpSecurity http, final JWKSource<SecurityContext> jwkSource,
            @Value("${spring.security.oauth2.authorizationserver.issuer}") final String issuer,
            @Value("${" + API_AUDIENCE_PROPERTY + ":" + DefaultClientDefinitions.DEFAULT_API_AUDIENCE + "}")
            final String audience) throws Exception {
        http
                .securityMatcher(API_PATTERN)
                .csrf(AbstractHttpConfigurer::disable)
                .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
                .authorizeHttpRequests(authorize -> authorize
                        .requestMatchers(HttpMethod.POST, "/api/account/register", "/api/account/password/reset",
                                "/api/account/password/reset-request")
                        .permitAll()
                        .requestMatchers(HttpMethod.GET, "/api/account/verify").permitAll()
                        .requestMatchers(ADMIN_PATTERN).hasAuthority(ADMIN_SCOPE_AUTHORITY)
                        .anyRequest().authenticated())
                .oauth2ResourceServer(resource -> resource
                        .jwt(jwt -> jwt.decoder(apiJwtDecoder(jwkSource, issuer, audience))
                                .jwtAuthenticationConverter(apiJwtAuthenticationConverter())));
        return http.build();
    }

    /**
     * Creates the decoder of the API's bearer tokens: signature against the published keys, issuer, timestamps,
     * audience, and no {@code purpose} claim.
     *
     * @param jwkSource the published keys of this server.
     * @param issuer    issuer every token must have.
     * @param audience  audience every token must list.
     * @return the decoder.
     */
    static JwtDecoder apiJwtDecoder(final JWKSource<SecurityContext> jwkSource, final String issuer,
                                    final String audience) {
        final var decoder = NimbusJwtDecoder.withJwkSource(jwkSource).jwsAlgorithm(SignatureAlgorithm.RS256).build();
        decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(List.<OAuth2TokenValidator<Jwt>>of(
                JwtValidators.createDefaultWithIssuer(issuer),
                new JwtClaimValidator<List<String>>(JwtClaimNames.AUD,
                        audiences -> audiences != null && audiences.contains(audience)),
                ApiSecurityConfig::rejectPurposeBoundToken)));
        return decoder;
    }

    /**
     * Rejects a purpose-bound account token (such as an e-mail verification JWT): it is signed by this server but
     * never meant as a bearer token.
     *
     * @param jwt the token.
     * @return a failure when the token carries the {@code purpose} claim, a success otherwise.
     */
    private static OAuth2TokenValidatorResult rejectPurposeBoundToken(final Jwt jwt) {
        if (jwt.hasClaim(SignedTokenService.PURPOSE_CLAIM)) {
            return OAuth2TokenValidatorResult.failure(new OAuth2Error(OAuth2ErrorCodes.INVALID_TOKEN,
                    "A purpose-bound account token is not a bearer token", null));
        }
        return OAuth2TokenValidatorResult.success();
    }

    /**
     * Creates the converter that maps the {@code scope} claim to {@code SCOPE_*} authorities and the {@code roles}
     * claim to {@code ROLE_*} authorities.
     *
     * @return the converter.
     */
    JwtAuthenticationConverter apiJwtAuthenticationConverter() {
        final var scopes = new JwtGrantedAuthoritiesConverter();
        final var converter = new JwtAuthenticationConverter();
        converter.setJwtGrantedAuthoritiesConverter(jwt -> {
            final var authorities = new ArrayList<GrantedAuthority>(scopes.convert(jwt));
            authorities.addAll(roleAuthorities(jwt));
            return authorities;
        });
        return converter;
    }

This is the JWT resource server support of Spring Security applied to the authorization server itself.

The contracts are described on Registered Clients, API (the clients-api region) and on Signing Keys, API. The key administration contract is short enough to read here:

  /api/admin/keys:
    get:
      tags: [ Signing keys ]
      operationId: listSigningKeys
      summary: Lists the signing keys
      description: Never exposes private key material. Needs scope admin.
      security:
        - bearer: [ admin ]
      responses:
        '200':
          description: The keys
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/SigningKeyResponse'
        '401':
          $ref: '#/components/responses/Unauthorized'
        '403':
          $ref: '#/components/responses/AdminScopeRequired'
  /api/admin/keys/rotate:
    post:
      tags: [ Signing keys ]
      operationId: rotateSigningKeys
      summary: Rotates the signing keys now
      description: >-
        Forces a rotation whatever the age of the active key: the active key is retired (it stays published until
        the tokens it signed expire), the next key becomes active and a new next key is generated. Keys retired for
        longer than the retention are deleted, and the published keys are refreshed. The scheduled rotation, in
        contrast, only rotates a key that is due. Needs scope admin.
      security:
        - bearer: [ admin ]
      responses:
        '200':
          description: The keys after the rotation
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/SigningKeyResponse'
        '401':
          $ref: '#/components/responses/Unauthorized'
        '403':
          $ref: '#/components/responses/AdminScopeRequired'

See the OpenAPI path item object for the structure of a path.

BFF API

The BFF is the only application a browser talks to. Its API is cookie-based: the session cookie (__Host-SESSION) identifies the user, and every state-changing request must also carry the X-XSRF-TOKEN header.

Method Path Purpose

GET

/bff/user

The signed-in user as UI-safe claims of the ID token; 401 when nobody is signed in. No token is ever in the answer

GET

/bff/login

Starts the sign-in and redirects to the authorization server. returnTo must be a local path

POST

/bff/logout

Ends the BFF session and redirects to the RP-initiated logout of the authorization server. Answered by Spring Security’s logout filter, CSRF protected

GET, DELETE

/api/documents, /api/documents/{id}

Relays to the resource server with the access token of the session

The signed-in-user operation as the contract writes it:

  /bff/user:
    get:
      tags: [ User ]
      operationId: getSessionUser
      summary: Returns the signed-in user
      description: >-
        Answers the user signed in to the BFF session, as UI-safe claims of its ID token. Tokens are never part of the
        response: they stay on the server.
      security:
        - session: [ ]
      responses:
        '200':
          description: The signed-in user
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/SessionUserResponse'
        '401':
          description: There is no signed-in user

The bff-login-api and bff-documents-api regions of the same file describe the other two. The request and response examples are on Backend-for-Frontend, API. /bff/logout is configured in SecurityConfig of the BFF and is not an OpenAPI operation. See the OpenAPI path item object.

Resource server API

The resource server accepts a bearer JWT (or a DPoP-bound one) and uses scopes to decide. Deleting a document also needs a recent strong authentication (RFC 9470).

  /api/documents:
    get:
      tags: [ documents ]
      operationId: listDocuments
      summary: Lists documents
      description: Lists the caller's documents; an administrator sees all. Needs scope documents.read.
      security:
        - bearer: [ documents.read ]
      responses:
        '200':
          description: The documents.
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/DocumentResponse'
        '401':
          $ref: '#/components/responses/Unauthorized'
        '403':
          description: The token lacks the documents.read scope.
          headers:
            WWW-Authenticate:
              $ref: '#/components/headers/WwwAuthenticate'
  /api/documents/{id}:
    delete:
      tags: [ documents ]
      operationId: deleteDocument
      summary: Deletes a document
      description: >-
        Deletes one of the caller's documents; an administrator may delete any. Needs scope documents.delete and a
        recent strong authentication (RFC 9470). Someone else's document is answered 404, like a missing one.
      security:
        - bearer: [ documents.delete ]
      parameters:
        - name: id
          in: path
          required: true
          description: Unique identifier of the document.
          schema:
            type: string
      responses:
        '204':
          description: The document was deleted.
        '401':
          description: >-
            Missing or invalid bearer token, or (RFC 9470) a valid token that does not prove a recent enough strong
            authentication: its acr claim is not the required one or its auth_time is older than the maximum age.
            The client must send the user through the authorization server again, asking for the acr_values and
            max_age of the challenge.
          headers:
            WWW-Authenticate:
              description: >-
                RFC 6750 bearer challenge. When step-up authentication is required it is
                Bearer error="insufficient_user_authentication", acr_values="urn:irurueta:acr:mfa", max_age="300"
                (the values configured under resourceserver.step-up.*).
              schema:
                type: string
        '403':
          description: The token lacks the documents.delete scope.
          headers:
            WWW-Authenticate:
              $ref: '#/components/headers/WwwAuthenticate'
        '404':
          description: The document does not exist or belongs to someone else.

The pages the server renders

The login, consent, second-factor, passkey, phone, identities, device-verification and one-time-token pages are also described as an OpenAPI document, auth-server-pages-v1.yaml, with one tagged region per page (login-page-api, consent-page-api, ott-pages-api, and so on). They describe HTML pages and their forms, not a JSON API, and each region is included by the page of its feature: for example the login region on Login, Consent & Logout Pages, API.

Error model

Protocol errors (RFC 6749)

The token, revocation and introspection endpoints answer failures with the JSON object of RFC 6749, section 5.2: an error code, and optionally error_description and error_uri. Spring Authorization Server writes them, so the example does not change their shape.

error Status Typical cause in the example

invalid_request

400

A required parameter is missing or repeated

invalid_client

401

Wrong secret, an unknown client, or a replayed client assertion

invalid_grant

400

A used, expired or rotated code or refresh token (presenting a rotated refresh token again also revokes the authorization it belonged to)

unauthorized_client

400

The client has no registration for that grant type

unsupported_grant_type

400

The grant type is not implemented or not enabled

invalid_scope

400

A scope the client is not registered for

invalid_target

400

A token exchange asked for an audience the client may not have

authorization_pending, slow_down, expired_token, access_denied

400

Device flow polling states (RFC 8628 section 3.5)

The authorization endpoint cannot always answer with JSON. A request with response_type=token is refused with unsupported_response_type, because the implicit flow is off by default. When the redirect URI is trusted it redirects back with error and state in the query, and otherwise it shows an error page. See Security Best Practices for why the redirect URI is validated before anything is sent to it.

Problem details on the custom APIs (RFC 9457)

Every failure of the account, administration, BFF and resource-server REST APIs is application/problem+json (RFC 9457) with type, title, status and detail. type is a URN of the form urn:problem:<area>:<name>. The areas are account, client, mfa, passkeys, phone, identity, certificate and ott on the authorization server, and documents on the BFF. Request validation failures use about:blank. A rate-limited answer carries Retry-After. The step-up handler of the account API shows the shape: it builds a ProblemDetail with its type and title, and returns it through problemResponse, a helper of the handlers' base class ProblemJsonExceptionHandler that sets the application/problem+json media type:

    /**
     * Answers a token whose sign-in is not recent or strong enough: {@code 401} with the RFC 9470 challenge, which
     * tells the client which {@code acr_values} and {@code max_age} to ask for when it signs the user in again.
     *
     * @param exception the failure.
     * @return the {@code 401} problem detail with the {@code WWW-Authenticate} challenge.
     */
    @ExceptionHandler(InsufficientUserAuthenticationException.class)
    public ResponseEntity<ProblemDetail> handleInsufficientUserAuthentication(
            final InsufficientUserAuthenticationException exception) {
        final var problem = ProblemDetail.forStatusAndDetail(HttpStatus.UNAUTHORIZED, exception.getMessage());
        problem.setType(URI.create(TYPE_BASE + "insufficient-user-authentication"));
        problem.setTitle("Step-up authentication required");
        final var headers = new HttpHeaders();
        headers.set(HttpHeaders.WWW_AUTHENTICATE, "Bearer error=\"insufficient_user_authentication\", acr_values=\""
                + exception.getAcrValues() + "\", max_age=\"" + exception.getMaxAge().toSeconds() + "\"");
        return problemResponse(problem, headers);
    }

This is Spring’s Error Responses support (ProblemDetail and ResponseEntityExceptionHandler). The same handler is the example of the next section: a problem body and a challenge in one answer.

Challenges (RFC 6750, RFC 9470 and RFC 9449)

A resource that rejects a token sets a WWW-Authenticate header, and the client acts on it:

Header Meaning Where it comes from

Bearer error="invalid_token"

The token is missing, expired, badly signed or has the wrong audience (RFC 6750 section 3.1)

BearerTokenAuthenticationEntryPoint on the resource server and on the account API chain

Bearer error="insufficient_scope"

The token is valid but lacks the scope (403)

Spring Security’s bearer token access denied handling

Bearer error="insufficient_user_authentication", acr_values="...", max_age="..."

The sign-in is too old or too weak; sign the user in again with these parameters (RFC 9470)

StepUpAccessDeniedHandler on the resource server and MfaExceptionHandler on the account API

DPoP error=...

A DPoP-bound token was sent as Bearer, or the proof is missing or invalid (RFC 9449 section 7)

The framework’s DPoP support, enabled in the resource server chain

The step-up challenge of the resource server, which a client reads to decide whether to send the user through the authorization endpoint again with acr_values and max_age:

@RequiredArgsConstructor
public class StepUpAccessDeniedHandler implements AccessDeniedHandler {

    /** Handler of every denial that is not a step-up requirement. */
    private final AccessDeniedHandler delegate;

    /** Step-up policy, whose values are advertised in the challenge. */
    private final StepUpProperties properties;

    @Override
    public void handle(final HttpServletRequest request, final HttpServletResponse response,
            final AccessDeniedException accessDeniedException) throws IOException, ServletException {
        if (accessDeniedException instanceof AuthorizationDeniedException denied
                && denied.getAuthorizationResult() instanceof StepUpRequiredDecision) {
            response.setStatus(HttpStatus.UNAUTHORIZED.value());
            response.setHeader(HttpHeaders.WWW_AUTHENTICATE, "Bearer error=\"insufficient_user_authentication\", "
                    + "acr_values=\"" + properties.acrValues() + "\", max_age=\""
                    + properties.maxAge().toSeconds() + "\"");
            return;
        }
        delegate.handle(request, response, accessDeniedException);
    }
}

This implements RFC 9470, Step Up Authentication Challenge Protocol; the other challenges are in RFC 6750, The WWW-Authenticate Response Header Field and RFC 9449, Protected Resource Access. How the resource server decides is on Protecting APIs, Step-up: the challenge, and the OAuth Reference explains the choice of error codes in Security Best Practices and Sender-Constrained Tokens: DPoP and mTLS.
