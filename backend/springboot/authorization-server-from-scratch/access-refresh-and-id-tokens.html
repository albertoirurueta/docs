Authorization Server from Scratch: Access, Refresh and ID Tokens

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page shows how the authorization server mints tokens: which formats and lifetimes the seeded clients use, how the same custom claims reach both self-contained (JWT) and reference (opaque) access tokens, how a refresh token is rotated and how the replay of a rotated token revokes the whole authorization, and what the UserInfo endpoint returns. The theory is in the OAuth Reference: Access and Refresh Tokens, ID Tokens vs. Access Tokens and Opaque Tokens, Introspection and Revocation. It is not repeated here. How the tokens are signed is the subject of the Signing Keys, JWS & JWT page of this section, and how a resource server validates them is the subject of the resource server page.

What you build

Spring Authorization Server already generates and stores the tokens. The example configures three things on top of it:

  • Token settings per client, stored with the registered client: format, lifetimes and whether refresh tokens are reused.

  • Claims: one class, IssuedTokenClaims, decides which claims a token gets, and two small customizers apply it, one for JWTs and one for reference tokens. Other features add claims through the JwtClaimsContributor extension point.

  • Refresh token reuse detection: a decorator of the OAuth2AuthorizationService that remembers rotated-out refresh tokens by their hash.

Formats and lifetimes

The values below are the ones the example sets, taken from DefaultClientDefinitions (the clients-seed region) and mapped onto Spring’s TokenSettings by RegisteredClientMapper (the tokens-settings region), not framework defaults.

How it works

Refresh rotation and reuse detection

With reuseRefreshTokens set to false, every successful refresh response carries a new refresh token and the old one stops being valid. ReuseDetectingAuthorizationService wraps the JDBC OAuth2AuthorizationService and records the SHA-256 hash of every refresh token that a save rotates out. If a token that is no longer current is presented again, findByToken cannot find it in the delegate, finds its hash in consumed_refresh_tokens, and removes the authorization the token belonged to: the thief and the legitimate client both lose the session, and the user signs in again.

sequenceDiagram autonumber participant C as Client participant T as Token endpoint participant S as ReuseDetectingAuthorizationService participant D as Delegate (JDBC) and consumed_refresh_tokens C->>T: POST /oauth2/token grant_type=refresh_token, refresh_token=R1 T->>S: findByToken(R1, refresh_token) S->>D: delegate.findByToken(R1) D-->>S: authorization (R1 is current) T->>S: save(authorization with R2) S->>D: findById, then delegate.save S->>D: INSERT hash(R1) into consumed_refresh_tokens T-->>C: new access token and R2 Note over C,D: later, the old token R1 is replayed C->>T: POST /oauth2/token grant_type=refresh_token, refresh_token=R1 T->>S: findByToken(R1, refresh_token) S->>D: delegate.findByToken(R1) D-->>S: null (R1 was rotated out) S->>D: SELECT authorization_id WHERE token_hash = hash(R1) D-->>S: the authorization id S->>D: delegate.remove(authorization): the family is revoked S-->>T: null T-->>C: 400 invalid_grant C->>T: refresh with R2 T-->>C: 400 invalid_grant (the authorization no longer exists)

The consumed_refresh_tokens rows reference oauth2_authorization with ON DELETE CASCADE, so revoking the authorization also deletes its list of consumed hashes: a second replay of R1 after the revocation finds nothing and is simply an unknown token (still invalid_grant). The ReuseDetectingAuthorizationServiceIT and TokenFlowIT tests (below) exercise this exact sequence.

Which claims a token gets

flowchart TD G[Token being issued] --> K{Token type} K -- access token JWT --> J["RolesTenantAudienceTokenCustomizer (JwtEncodingContext)"] K -- access token reference --> R["ReferenceTokenClaimsCustomizer (OAuth2TokenClaimsContext)"] K -- ID token JWT --> J J --> I[IssuedTokenClaims.apply] R --> I I --> A{Access token?} A -- yes --> B["roles, tenant (user grants only), aud from the client setting"] A -- no, ID token --> C[no built-in claims] B --> X["every JwtClaimsContributor, in order"] C --> X

A token of the client credentials grant has no user, so it gets no roles and no tenant, only the audience. roles are the authorities of the user without the FACTOR_ authorities, which record how the user signed in (see the Multi-Factor Authentication page) and are not permissions.

Data

Three tables take part. oauth2_authorization is Spring’s own table, described in the Data Model and Schema page: it stores the token values, their metadata and the serialized claims. The example adds the following two migrations.

consumed_refresh_tokens (V230)

The table stores only the hash of a rotated-out token, so a database leak does not give anyone a usable token, and the hash is the primary key, which makes the insert idempotent (ON CONFLICT DO NOTHING).

-- Hashes of the refresh tokens that were rotated out of an authorization. Presenting one of them again means the
-- token was stolen or replayed, so the authorization is revoked.
CREATE TABLE consumed_refresh_tokens
(
    token_hash       varchar(64)              NOT NULL,
    authorization_id varchar(100)             NOT NULL REFERENCES oauth2_authorization (id) ON DELETE CASCADE,
    consumed_at      timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (token_hash)
);

CREATE INDEX ix_consumed_refresh_tokens_authorization ON consumed_refresh_tokens (authorization_id);

See Flyway migrations for how versioned scripts are applied.

oauth2_authorization.created_at (V240)

-- When each authorization row was created. Spring Authorization Server lists its columns explicitly, so the default
-- fills it in. An authorization that never got a token (an authorization or consent request the user abandoned) has
-- no expiry at all; the clean-up job deletes it once it is older than a configurable threshold.
ALTER TABLE oauth2_authorization
    ADD COLUMN created_at timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP;

Spring’s JDBC service lists its columns explicitly, so a column with a default is safe to add. See the OAuth2AuthorizationService reference for the schema Spring defines.

Claims of every token

IssuedTokenClaims is the one place that knows which claims a token gets. It is a plain Spring bean, so it is tested without a framework, and both customizers delegate to it.

/**
 * The claims this server adds to the tokens it issues, whatever their format, so the self-contained (JWT) access
 * tokens and the reference (opaque) ones carry the same claims: {@link RolesTenantAudienceTokenCustomizer} applies it
 * to the JWTs and {@link ReferenceTokenClaimsCustomizer} to the claims stored for a reference token (which the
 * introspection endpoint returns).
 *
 * <p>An access token gets {@code roles}, {@code tenant} and {@code aud}: the roles are the authorities of the user,
 * the tenant comes from the user account, the audiences from the {@value #AUDIENCES_SETTING} custom setting of the
 * client. Tokens of the client credentials grant have no user, so they get no roles and no tenant. An ID token gets
 * none of them. Then every {@link JwtClaimsContributor}, in order, adds its own claims to the access and ID tokens
 * (it can tell them apart with {@link OAuth2TokenContext#getTokenType()}); no other token is touched.
 */
@Component
@RequiredArgsConstructor
public class IssuedTokenClaims {

    /**
     * Name of the custom client setting that holds the audiences of the access tokens. It is the same name the
     * persistence adapter writes (that module cannot be referenced from here).
     */
    public static final String AUDIENCES_SETTING = "settings.client.audiences";

    /** Name of the claim that holds the roles of the user. */
    public static final String ROLES_CLAIM = "roles";

    /** Name of the claim that holds the tenant of the user. */
    public static final String TENANT_CLAIM = "tenant";

    /** Type of the OpenID Connect ID token. */
    static final OAuth2TokenType ID_TOKEN = new OAuth2TokenType(OidcParameterNames.ID_TOKEN);

    /** Prefix of the authorities that record how a user authenticated, such as {@code FACTOR_PASSWORD}. */
    private static final String FACTOR_PREFIX = "FACTOR_";

    /** Finds the account of the user. */
    private final FindUserAccountUseCase findUserAccountUseCase;

    /** Contributors of additional claims, in order. */
    private final List<JwtClaimsContributor> contributors;

    /**
     * Adds the claims of the token being issued.
     *
     * @param context the token context, with the token type, the principal, the client and the grant type.
     * @param claims  the mutable claims of the token being built.
     */
    public void apply(final OAuth2TokenContext context, final Map<String, Object> claims) {
        if (OAuth2TokenType.ACCESS_TOKEN.equals(context.getTokenType())) {
            addAccessTokenClaims(context, claims);
        } else if (!ID_TOKEN.equals(context.getTokenType())) {
            return;
        }
        contributors.forEach(contributor -> contributor.contribute(context, claims));
    }

    /**
     * Adds the roles, the tenant and the audiences of an access token.
     *
     * @param context the token context.
     * @param claims  the mutable claims of the token being built.
     */
    private void addAccessTokenClaims(final OAuth2TokenContext context, final Map<String, Object> claims) {
        if (context.getAuthorizationGrantType() != null
                && !AuthorizationGrantType.CLIENT_CREDENTIALS.equals(context.getAuthorizationGrantType())) {
            final Authentication principal =
                    Objects.requireNonNull(context.getPrincipal(), "a user grant has a principal");
            // factor authorities (FACTOR_PASSWORD, ...) record how the user signed in; they are not roles. The
            // list is a mutable one on purpose: the authorization store only deserializes allow-listed types, and
            // an immutable list copy (Stream.toList) is not one of them.
            claims.put(ROLES_CLAIM, principal.getAuthorities().stream()
                    .map(GrantedAuthority::getAuthority)
                    .filter(authority -> !authority.startsWith(FACTOR_PREFIX)).sorted()
                    .collect(Collectors.toCollection(ArrayList::new)));
            findUserAccountUseCase.execute(principal.getName())
                    .ifPresent(account -> claims.put(TENANT_CLAIM, account.tenant()));
        }
        if (context.getRegisteredClient().getClientSettings().getSetting(AUDIENCES_SETTING)
                instanceof List<?> audiences && !audiences.isEmpty()) {
            claims.put(OAuth2TokenClaimNames.AUD, audiences.stream().map(String::valueOf)
                    .collect(Collectors.toCollection(ArrayList::new)));
        }
    }
}

See RFC 9068, JWT Profile for OAuth 2.0 Access Tokens for the standard claims (iss, sub, aud, exp, scope) that Spring adds before these custom ones.

/**
 * Extension point that lets a feature add claims to the tokens issued by the authorization server: the access tokens,
 * whether self-contained (JWT) or reference (their claims are returned by the introspection endpoint), and the ID
 * tokens. Every bean of this type is applied by {@link IssuedTokenClaims}, in
 * {@link org.springframework.core.annotation.Order} order, after the built-in claims, so a later contributor may
 * override them. A contributor that only concerns one kind of token checks {@link OAuth2TokenContext#getTokenType()}.
 */
@FunctionalInterface
public interface JwtClaimsContributor {

    /**
     * Adds claims to the token being issued.
     *
     * @param context the token context, with the token type, the principal, the client and the grant type.
     * @param claims  the mutable claims of the token being built.
     */
    void contribute(OAuth2TokenContext context, Map<String, Object> claims);
}

This is a plain extension point, not a Spring type. The MFA page uses it to add acr, amr and auth_time. See the OAuth2TokenCustomizer reference.

The two customizers

/**
 * Adds the claims of {@link IssuedTokenClaims} to the self-contained tokens (JWT access tokens and ID tokens): the
 * {@code roles}, {@code tenant} and {@code aud} claims of an access token, then the claims of every
 * {@link JwtClaimsContributor}, which also reach the ID tokens. It is the one
 * {@code OAuth2TokenCustomizer<JwtEncodingContext>} of the server.
 */
@Component
@RequiredArgsConstructor
public class RolesTenantAudienceTokenCustomizer implements OAuth2TokenCustomizer<JwtEncodingContext> {

    /** The claims every issued token gets. */
    private final IssuedTokenClaims issuedTokenClaims;

    @Override
    public void customize(final JwtEncodingContext context) {
        context.getClaims().claims(claims -> issuedTokenClaims.apply(context, claims));
    }
}

See the OAuth2TokenCustomizer reference (the JwtEncodingContext variant customizes JWT headers and claims).

/**
 * Adds the claims of {@link IssuedTokenClaims} to the reference (opaque) access tokens. Such a token carries no
 * claims itself: the claims are stored with the authorization and returned by the introspection endpoint, so a
 * resource server that introspects it sees the same {@code roles}, {@code tenant}, {@code aud} and contributed
 * claims as one that decodes a JWT. It is the one {@code OAuth2TokenCustomizer<OAuth2TokenClaimsContext>} of the
 * server.
 */
@Component
@RequiredArgsConstructor
public class ReferenceTokenClaimsCustomizer implements OAuth2TokenCustomizer<OAuth2TokenClaimsContext> {

    /** The claims every issued token gets. */
    private final IssuedTokenClaims issuedTokenClaims;

    @Override
    public void customize(final OAuth2TokenClaimsContext context) {
        context.getClaims().claims(claims -> issuedTokenClaims.apply(context, claims));
    }
}

See the same OAuth2TokenCustomizer reference (the OAuth2TokenClaimsContext variant customizes the claims of opaque access tokens). Because a reference token holds no claims, these are stored with the authorization and returned by introspection, so a resource server that introspects sees the same claims as one that decodes a JWT.

See the OpenID Connect 1.0 UserInfo endpoint.

/**
 * Builds the OpenID Connect UserInfo response from the account of the user, limited to the granted scopes: the
 * {@code sub} claim always; {@code preferred_username}, {@code roles} and {@code tenant} with the {@code profile}
 * scope; {@code email} and {@code email_verified} with the {@code email} scope.
 */
@Component
@RequiredArgsConstructor
public class UserInfoMapper implements Function<OidcUserInfoAuthenticationContext, OidcUserInfo> {

    /** Scope that grants the profile claims. */
    public static final String PROFILE_SCOPE = "profile";

    /** Scope that grants the e-mail claims. */
    public static final String EMAIL_SCOPE = "email";

    /** Finds the account of the user. */
    private final FindUserAccountUseCase findUserAccountUseCase;

    @Override
    public OidcUserInfo apply(final OidcUserInfoAuthenticationContext context) {
        final var username = context.getAuthorization().getPrincipalName();
        final var scopes = context.getAccessToken().getScopes();
        final var claims = new HashMap<String, Object>();
        claims.put(StandardClaimNames.SUB, username);
        findUserAccountUseCase.execute(username).ifPresent(account -> {
            if (scopes.contains(PROFILE_SCOPE)) {
                claims.put(StandardClaimNames.PREFERRED_USERNAME, account.username());
                claims.put(IssuedTokenClaims.ROLES_CLAIM, account.authorities());
                claims.put(IssuedTokenClaims.TENANT_CLAIM, account.tenant());
            }
            if (scopes.contains(EMAIL_SCOPE) && account.email() != null) {
                claims.put(StandardClaimNames.EMAIL, account.email());
                claims.put(StandardClaimNames.EMAIL_VERIFIED, account.emailVerified());
            }
        });
        return new OidcUserInfo(claims);
    }
}

See OpenID Connect Core, UserInfo Endpoint and the scope-to-claims rules.

Reuse detection

    @Override
    public void save(final OAuth2Authorization authorization) {
        final var previous = delegate.findById(authorization.getId());
        delegate.save(authorization);
        if (previous == null) {
            return;
        }
        final var oldToken = refreshTokenValue(previous);
        if (oldToken != null && !oldToken.equals(refreshTokenValue(authorization))) {
            jdbcClient.sql(INSERT_CONSUMED).params(hash(oldToken), authorization.getId()).update();
        }
    }

    @Override
    public void remove(final OAuth2Authorization authorization) {
        delegate.remove(authorization);
    }

    @Override
    public OAuth2Authorization findById(final String id) {
        return delegate.findById(id);
    }

    @Override
    public OAuth2Authorization findByToken(final String token, final OAuth2TokenType tokenType) {
        final var authorization = delegate.findByToken(token, tokenType);
        if (authorization != null || (tokenType != null && !OAuth2TokenType.REFRESH_TOKEN.equals(tokenType))) {
            return authorization;
        }
        jdbcClient.sql(FIND_CONSUMED).param(hash(token)).query(String.class).optional()
                .map(delegate::findById)
                .ifPresent(compromised -> {
                    log.warn("A rotated refresh token was presented again; revoking the authorization {}",
                            compromised.getId());
                    delegate.remove(compromised);
                });
        return null;
    }

See RFC 9700, OAuth 2.0 Security Best Current Practice for refresh token protection and rotation, and the OAuth2AuthorizationService reference.

Two details of the region matter. save compares the stored refresh token with the new one and records the hash only when it changed, so saves that do not rotate record nothing. findByToken only looks in the consumed list when the lookup is for a refresh token (or for an unknown token type) and the delegate found nothing.

API

These endpoints are defined by their specifications, so they are not part of the project’s own OpenAPI contract. The examples assume the authorization server on http://localhost:9000; replace the placeholders with your own values.

Refresh with the confidential bff client (client_secret_basic):

curl -s -u "bff:<client-secret>" http://localhost:9000/oauth2/token \
  -d grant_type=refresh_token \
  -d refresh_token=<refresh-token>

The response carries a new refresh_token and a new access_token; the old refresh token is now rotated out. The public spa-public client has no secret and sends -d client_id=spa-public instead of -u. Presenting a rotated token again returns 400 with {"error":"invalid_grant"}.

Revoke a token (RFC 7009) and introspect it (RFC 7662):

curl -s -u "bff:<client-secret>" http://localhost:9000/oauth2/revoke \
  -d token=<refresh-token> -d token_type_hint=refresh_token

curl -s -u "bff:<client-secret>" http://localhost:9000/oauth2/introspect \
  -d token=<access-token>

Revocation answers 200 with an empty body even for an unknown token. Introspection returns {"active":false} for a revoked, expired or unknown token, and for an active one active, scope, client_id, exp, aud, roles and tenant.

UserInfo, with the access token of a user:

curl -s -H "Authorization: Bearer <access-token>" http://localhost:9000/userinfo

The response always has sub. With the profile scope it adds preferred_username, roles and tenant; with the email scope, email and email_verified. A missing or invalid token is rejected with 401.

See RFC 6749, Refreshing an Access Token, RFC 7009 and RFC 7662, and the Protocol Endpoints reference.

Tests

None of the regions below is tagged, so the tests are described, not pasted:

  • TokenFlowIT (module auth-server/boot) runs the real endpoints: a user access token carries audience, roles and tenant; a client credentials token has the audience but no user claims; a refresh rotates the token; a rotated token that is reused revokes the authorization, and the current token stops working; revoking an access or a refresh token works; introspection reports active and unknown tokens and returns audience, roles and tenant for a reference token; UserInfo contains the profile and email claims for the granted scopes and is rejected without a valid token.

  • ReuseDetectingAuthorizationServiceIT runs the decorator against a real database: the replay of a rotated token revokes the authorization, and a save that does not rotate the token records nothing.

  • CleanExpiredAuthorizationsUseCaseTest covers the clean-up of expired and abandoned authorizations.

Security notes and pitfalls

  • Rotation protects public clients. A SPA cannot keep a secret, so a stolen refresh token is as good as the client. Rotation plus reuse detection turns a theft into a forced sign-in instead of a silent, lasting session.

  • Reuse detection is not instant revocation of access tokens. A JWT access token stays valid until it expires (10 minutes here). Short lifetimes, or the reference format with introspection, are the levers.

  • A benign replay revokes too. A client that loses the response to a refresh and retries with the old token revokes its own session. The design trades that for security; give clients a retry that falls back to a new sign-in.

  • Clean up abandoned authorizations. An authorization or consent request that never got a token has no expiry. The created_at column lets ExpiredAuthorizationCleanupJob (cron authserver.tokens.cleanup.cron, hourly by default) delete those older than authserver.tokens.cleanup.abandoned-after (one day by default), together with expired ones.

  • Minimise claims. Every claim in a JWT is readable by the client and the browser. Put roles and tenant in access tokens for resource servers, not in ID tokens, and keep UserInfo scope-limited, as UserInfoMapper does.

  • Never log tokens. The consumed list stores hashes for that reason; the revocation warning logs the authorization id, never the token.

  • Use the audience. aud comes from the client setting, so a token minted for one API is not accepted by another; the resource server page shows the check.
