Authorization Server from Scratch: Storing Passwords Securely

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Storing a password is a one-way operation: the server keeps a salted, deliberately slow hash and never the password itself, so a leaked database does not hand out working credentials. This page shows how the example does it with nothing but Spring Security building blocks: which encoder hashes new passwords, how an old hash is replaced the next time its owner signs in, which rules a new password must follow, how a leaked password is refused, and how the account endpoints (registration and password reset) avoid revealing which users exist. The protocol-level background, where passwords are the baseline primary factor that the other methods are compared with, is in Passwords as the baseline primary factor; this page is its implementation.

What you build

  • A PasswordEncoder bean that is a DelegatingPasswordEncoder: every stored hash starts with an {id} prefix naming the algorithm that made it, so the server can verify old hashes and still encode new ones with the current default. The example encodes with Argon2id, and still verifies bcrypt and PBKDF2 hashes.

  • Upgrade on sign-in: when a user signs in with a hash made by an older algorithm, the verified clear-text password is re-encoded with the default and stored, with no password-reset campaign.

  • A PasswordPolicy in the style of NIST SP 800-63B (length limits and a username check, no composition rules) applied everywhere a password is chosen, and a compromised-password check against the Have I Been Pwned range API.

  • A DaoAuthenticationProvider declared by hand so that a wrong password always gets the same answer, whether the account exists, is disabled or does not exist.

  • The self-service account flows: registration with e-mail verification, password change and password reset with a single-use, hashed, expiring token, all rate limited.

The external references behind the choices are the OWASP Password Storage Cheat Sheet, NIST SP 800-63B-4 (Digital Identity Guidelines: Authentication and Authenticator Management) and the Spring Security Password Storage reference.

How it works

A hash is stored as {id}encodedPassword. DelegatingPasswordEncoder.encode always uses the default id; matches reads the prefix of the stored hash and delegates to the encoder registered under that id; upgradeEncoding answers true when the prefix is not the default id (or when the delegate itself finds its parameters outdated). That last method is what makes the upgrade on sign-in possible.

The sequence below is a sign-in through the login form with a stored bcrypt hash. DaoAuthenticationProvider calls upgradeEncoding on the stored hash after the password matched, encodes the password it just verified with the default algorithm and hands the result to the UserDetailsPasswordService, which the example implements in the same class that loads the user.

sequenceDiagram autonumber actor U as User participant F as Login form (POST /login) participant P as DaoAuthenticationProvider participant S as UserAccountUserDetailsService participant E as PasswordEncoder (delegating) participant C as UpgradePasswordHashUseCase participant R as UserAccountRepository (JDBC) U->>F: username and password F->>P: authenticate(username, password) P->>S: loadUserByUsername(username) S->>R: find the account (users, user_passwords, user_authorities) R-->>S: account with the stored hash, prefix bcrypt S-->>P: UserDetails P->>E: matches(password, stored hash) E-->>P: true P->>P: post-authentication checks (account enabled, not locked) P->>E: upgradeEncoding(stored hash) E-->>P: true, the id is not the default P->>E: encode(password) E-->>P: new hash, prefix argon2 P->>S: updatePassword(user, new hash) S->>C: replaceHash(account, new hash) C->>R: updatePassword(user id, new hash) P-->>F: authenticated

If the password did not match, none of the steps from step 9 on runs, so a failed sign-in never touches the stored hash. The account status is checked only after the password, which is a deliberate choice explained in Security notes and pitfalls.

Which algorithm for new hashes

The example registers three encoders in its DelegatingPasswordEncoder and uses the defaults of each Spring Security factory method, so none of the parameters below is a value the example chose: they are the documented defaults of the ..._v5_8 factories (a version label that Spring Security keeps stable so existing hashes still verify). The scrypt and NoOp rows are not registered in the example and are listed for comparison.

Encoder ({id} prefix) Parameters used Registered in the example When to use it

Argon2PasswordEncoder (argon2@SpringSecurity_v5_8)

Argon2id with salt 16 bytes, hash 32 bytes, parallelism 1, memory 2^14 KiB (16 MiB) and 2 iterations

Yes, the default for every new hash

First choice for new systems: memory-hard, so it resists GPU and ASIC cracking. It needs BouncyCastle on the class path, which is why auth-server declares bcprov-jdk18on. The OWASP cheat sheet asks for at least 19 MiB, 2 iterations and parallelism 1, so these defaults are slightly below that floor: tune the constructor (new Argon2PasswordEncoder(...)) to your hardware, aiming at about one second per verification.

BCryptPasswordEncoder (bcrypt)

Strength 10 (the default of the no-argument constructor)

Yes, legacy hashes only

Acceptable when Argon2 is not available. It truncates passwords at 72 bytes and is not memory-hard, so keep it for verifying old hashes and let the upgrade replace them.

Pbkdf2PasswordEncoder (pbkdf2@SpringSecurity_v5_8)

PBKDF2-HMAC-SHA-256 with salt 16 bytes, 310,000 iterations and a 256-bit hash, no extra secret

Yes, legacy hashes only

When FIPS 140 validated algorithms are mandatory. OWASP currently recommends 600,000 iterations for HMAC-SHA-256, so 310,000 is outdated for new hashes.

SCryptPasswordEncoder (scrypt@SpringSecurity_v5_8)

CPU cost 65,536, memory cost 8, parallelization 1, key length 32, salt 16 bytes

No

The fallback OWASP names when Argon2id is unavailable; the Spring default is weaker than OWASP’s minimum (N = 2^17), so raise it if you choose it.

NoOpPasswordEncoder

none, the password is stored as typed

No

Never. It is deprecated and exists only for tests and tutorials.

The prefix gives the migration path between encoders: to move to a new algorithm, register it, make it the default id and keep the old encoders registered until upgradeEncoding has rewritten the hashes of every active user.

Data

Accounts are stored by the walking-skeleton tables users, user_passwords and user_authorities, described in Data Model and Schema: the encoded password, with its {id} prefix, is the column user_passwords.encoded_password, so a different algorithm needs no schema change. Migration V200 adds the account columns of users (email, email_verified and tenant) and the account_tokens table that holds the e-mail verification and password-reset tokens:

ALTER TABLE users
    ADD COLUMN email          varchar(320),
    ADD COLUMN email_verified boolean      NOT NULL DEFAULT FALSE,
    ADD COLUMN tenant         varchar(100) NOT NULL DEFAULT 'default';

-- Existing rows have no e-mail; the unique index is case-insensitive and ignores the NULLs.
CREATE UNIQUE INDEX uq_users_email ON users (lower(email));

CREATE TABLE account_tokens
(
    id           uuid                     NOT NULL,
    user_id      uuid                     NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    purpose      varchar(50)              NOT NULL,
    hashed_token varchar(128)             NOT NULL,
    expires_at   timestamp with time zone NOT NULL,
    used_at      timestamp with time zone,
    created_at   timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    CONSTRAINT uq_account_tokens_hashed_token UNIQUE (hashed_token)
);

CREATE INDEX ix_account_tokens_expires_at ON account_tokens (expires_at);

This table follows the token storage advice of the OWASP Forgot Password Cheat Sheet: only hashed_token is stored, so a leaked table cannot be replayed, the column is unique, expires_at bounds the lifetime and used_at records the single use.

Code

The encoder

    /**
     * Creates the password encoder: a delegating encoder whose default is Argon2, with bcrypt and PBKDF2 kept for
     * legacy hashes.
     *
     * @return the delegating password encoder.
     */
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new DelegatingPasswordEncoder(DEFAULT_ENCODING_ID, Map.of(
                DEFAULT_ENCODING_ID, Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8(),
                BCRYPT_ENCODING_ID, new BCryptPasswordEncoder(),
                PBKDF2_ENCODING_ID, Pbkdf2PasswordEncoder.defaultsForSpringSecurity_v5_8()));
    }

This derives from the Spring Security DelegatingPasswordEncoder reference, which describes the {id} storage format and the default-plus-legacy mapping that the bean builds.

The same bean encodes the client secrets of the registered clients, which is why the class documentation says it serves both. Those secrets are covered by the registered clients page of the guide.

The password policy

    /**
     * Finds the rules a candidate password breaks.
     *
     * @param username name of the account the password is for; the username rule is skipped when it is {@code null}
     *                 or blank.
     * @param password the candidate password; {@code null} is treated as an empty password.
     * @return the broken rules, empty when the password is acceptable.
     */
    public List<PasswordViolation> violations(final String username, final String password) {
        final var candidate = password == null ? "" : password;
        final var violations = new ArrayList<PasswordViolation>();
        final var length = candidate.codePointCount(0, candidate.length());
        if (length < MIN_LENGTH) {
            violations.add(PasswordViolation.TOO_SHORT);
        }
        if (length > MAX_LENGTH) {
            violations.add(PasswordViolation.TOO_LONG);
        }
        if (!isBlank(username)
                && candidate.toLowerCase(Locale.ROOT).contains(username.toLowerCase(Locale.ROOT))) {
            violations.add(PasswordViolation.CONTAINS_USERNAME);
        }
        return List.copyOf(violations);
    }

    /**
     * Tells whether a candidate password follows every rule.
     *
     * @param username name of the account the password is for.
     * @param password the candidate password.
     * @return {@code true} when no rule is broken.
     */
    public boolean isValid(final String username, final String password) {
        return violations(username, password).isEmpty();
    }

This derives from the NIST SP 800-63B-4 password requirements, which ask for a minimum length, a generous maximum and no composition rules.

The policy is a plain domain class with no Spring dependency, exposed as a bean by PasswordPolicyConfiguration so a deployment can replace it. The constants are MIN_LENGTH 12 and MAX_LENGTH 128, counted in code points; the only content rule is that the password does not contain the username, compared ignoring case. A broken rule is reported as a PasswordViolation (TOO_SHORT, TOO_LONG, CONTAINS_USERNAME), which the use cases turn into a 400 answer.

The compromised-password check

    /**
     * Creates the check backed by the Have I Been Pwned range API.
     *
     * @return the enabled check.
     */
    @Bean
    @ConditionalOnProperty(name = ENABLED_PROPERTY, havingValue = "true", matchIfMissing = true)
    public CompromisedPasswordCheck haveIBeenPwnedCompromisedPasswordCheck() {
        return new SpringCompromisedPasswordCheck(new HaveIBeenPwnedRestApiPasswordChecker());
    }

    /**
     * Creates the no-op check used when the property disables the check.
     *
     * @return a check that never reports a password as compromised.
     */
    @Bean
    @ConditionalOnProperty(name = ENABLED_PROPERTY, havingValue = "false")
    public CompromisedPasswordCheck noOpCompromisedPasswordCheck() {
        return password -> false;
    }

This derives from the Spring Security Compromised Password Checking reference, which describes HaveIBeenPwnedRestApiPasswordChecker.

The check is on by default and is switched off with the property authserver.password.compromised-check.enabled=false, which registers a no-op check instead (useful offline and in tests). The range API (Pwned Passwords) only receives the first characters of the password’s SHA-1 hash, so the password is never sent. Note that the check is wired into the use cases that set a password; the example does not declare a Spring CompromisedPasswordChecker bean, so the sign-in provider below does not check a password at every login.

The authentication provider

    /**
     * Creates the authentication provider of the username and password sign-in.
     *
     * @param userDetailsService         loads the account by username.
     * @param userDetailsPasswordService stores the upgraded hash after a sign-in with an outdated encoding.
     * @param passwordEncoder            verifies the password, and tells when its hash needs upgrading.
     * @param compromisedPasswordChecker the compromised-password checker of Spring Security, when one is declared.
     * @return the provider, which checks the account status only after a correct password.
     */
    @Bean
    public DaoAuthenticationProvider passwordAuthenticationProvider(final UserDetailsService userDetailsService,
            final UserDetailsPasswordService userDetailsPasswordService, final PasswordEncoder passwordEncoder,
            final ObjectProvider<CompromisedPasswordChecker> compromisedPasswordChecker) {
        final var provider = new DaoAuthenticationProvider(userDetailsService);
        provider.setPasswordEncoder(passwordEncoder);
        provider.setUserDetailsPasswordService(userDetailsPasswordService);
        compromisedPasswordChecker.ifUnique(provider::setCompromisedPasswordChecker);
        provider.setHideUserNotFoundExceptions(true);
        provider.setPreAuthenticationChecks(NO_PRE_AUTHENTICATION_CHECKS);
        provider.setPostAuthenticationChecks(new AccountStatusUserDetailsChecker());
        return provider;
    }

This derives from the Spring Security DaoAuthenticationProvider reference, whose provider the bean replaces to change the order of its checks.

DaoAuthenticationProvider normally checks the account status (disabled, locked, expired) before the password. The bean sets no pre-authentication checks and an AccountStatusUserDetailsChecker as post-authentication check, and it keeps hideUserNotFoundExceptions on, so the answer to a wrong password is the same generic one for a known account, a disabled account and an unknown username. Because the bean is the only AuthenticationProvider, Spring Security logs a startup warning that the UserDetailsService bean is not used to build one; the example silences that warning on purpose in application.yml.

Loading the user

    /** Columns selected for an account. */
    private static final String SELECT_USER = """
            SELECT u.id, u.username, u.enabled, u.email, u.email_verified, u.tenant, p.encoded_password
            FROM users u JOIN user_passwords p ON p.user_id = u.id
            """;

    /** Query returning the user and its encoded password by username. */
    private static final String FIND_USER = SELECT_USER + "WHERE u.username = ?";
    /** Query returning the authorities of a user by user id. */
    private static final String FIND_AUTHORITIES = """
            SELECT authority
            FROM user_authorities
            WHERE user_id = ?
            ORDER BY authority
            """;
    @Override
    public Optional<UserAccount> findByUsername(final String username) {
        return findOne(FIND_USER, username);
    }
    /**
     * Loads one account, with its authorities.
     *
     * @param sql   query selecting the user row by one parameter.
     * @param value value of the parameter.
     * @return the account, or an empty optional when no row matches.
     */
    private Optional<UserAccount> findOne(final String sql, final Object value) {
        return jdbcClient.sql(sql).param(value)
                .query(userAccountRowMapper)
                .optional()
                .map(row -> row.toUserAccount(
                        jdbcClient.sql(FIND_AUTHORITIES).param(row.id()).query(String.class).list()));
    }
/**
 * Maps a row of the {@code users} table joined with {@code user_passwords} to a {@link UserAccountRow}. The
 * authorities are not part of the row: the repository loads them with a second query.
 */
@Component
public class UserAccountRowMapper implements RowMapper<UserAccountRow> {

    /**
     * Maps the current row.
     *
     * @param rs     result set positioned on the row.
     * @param rowNum number of the row.
     * @return the row.
     * @throws SQLException if a column cannot be read.
     */
    @Override
    public UserAccountRow mapRow(final ResultSet rs, final int rowNum) throws SQLException {
        return new UserAccountRow(rs.getObject("id", UUID.class), rs.getString("username"),
                rs.getString("encoded_password"), rs.getBoolean("enabled"), rs.getString("email"),
                rs.getBoolean("email_verified"), rs.getString("tenant"));
    }
}

These derive from the Spring Framework JdbcClient reference, which describes the fluent sql(...).param(...).query(...) calls the repository uses.

The first listing is made of several regions of one file, shown one after the other: the select that joins users and user_passwords, the authorities query, the findByUsername method and the private findOne that runs the query and loads the authorities with a second one. The row mapper keeps the authorities out of the row, so the join stays one row per user.

Upgrading a hash on sign-in

The two halves of the upgrade are the adapter that Spring Security calls and the use case that stores the result.

    @Override
    public UserDetails updatePassword(final UserDetails user, final String newPassword) {
        final var account = findUserAccountUseCase.execute(user.getUsername())
                .orElseThrow(() -> new UsernameNotFoundException("User not found: " + user.getUsername()));
        upgradePasswordHashUseCase.replaceHash(account, newPassword);
        return userDetailsMapper.toUserDetails(account, newPassword);
    }
    /**
     * Stores a password hash that was already produced by the current algorithm, as the authentication framework
     * does after a sign-in (it re-encodes the verified clear-text password itself).
     *
     * @param account         the account that just signed in.
     * @param encodedPassword the new encoded password.
     */
    public void replaceHash(final UserAccount account, final String encodedPassword) {
        userAccountRepository.updatePassword(account.id(), encodedPassword);
    }

These derive from the UserDetailsPasswordService contract, whose updatePassword(user, newPassword) receives the already encoded new hash.

The newPassword parameter of updatePassword is therefore the new hash, not a clear-text password, which is why the use case is called replaceHash and does no encoding of its own. The adapter looks the account up again to get its id; the use case then runs in its own transaction and calls updatePassword on the repository.

Registration

    /**
     * Registers an account.
     *
     * @param username name the user will sign in with.
     * @param email    e-mail address of the user.
     * @param password the chosen clear-text password.
     * @throws InvalidPasswordException     if the password breaks the policy.
     * @throws CompromisedPasswordException if the password is known to be compromised.
     */
    @Transactional
    public void execute(final String username, final String email, final String password) {
        final var violations = passwordPolicy.violations(username, password);
        if (!violations.isEmpty()) {
            throw new InvalidPasswordException(violations);
        }
        if (compromisedPasswordCheck.isCompromised(password)) {
            throw new CompromisedPasswordException("The chosen password is known to be compromised");
        }
        // hashed in every case, so that a taken address or username costs the same as a new one
        final var encodedPassword = passwordHasher.encode(password);
        if (userAccountRepository.findByEmail(email).isPresent()) {
            accountMailer.sendAlreadyRegistered(email);
            return;
        }
        final var id = UUID.randomUUID();
        // issued in every remaining case; with a taken username it names no account and verifies nothing
        final var token = signedTokenService.issue(id.toString(), AccountToken.PURPOSE_EMAIL_VERIFICATION,
                VERIFICATION_TTL);
        if (!userAccountRepository.existsByUsername(username)) {
            userAccountRepository.save(new UserAccount(id, username, encodedPassword, false,
                    List.of(DEFAULT_AUTHORITY), email, false, UserAccount.DEFAULT_TENANT));
        }
        accountMailer.sendEmailVerification(email, token);
    }

This derives from the OWASP Authentication Cheat Sheet guidance on uniform messages, which the use case follows for taken addresses and usernames.

The order matters. The policy and the compromised check run first, so a bad password is rejected whatever the account state is. The password is then hashed in every case, before the taken-address check, so a registration costs the same time whether or not the address or username exists. A registered address receives a neutral "already registered" e-mail, and a new address with a taken username receives a normal verification message whose token names no account (it fails like an expired link), so the endpoint reveals no username. The account is created disabled and unverified, and saving it and sending the message happen in one transaction: if the mail cannot be sent, nothing is registered.

Password reset

sequenceDiagram autonumber actor U as User participant A as AccountController participant Q as RequestPasswordResetUseCase participant X as ResetPasswordUseCase participant T as AccountTokenRepository participant M as AccountMailer U->>A: POST /api/account/password/reset-request (email) A->>Q: execute(email) Q->>Q: generate a token and hash it (always) Q->>T: store(hashed token, purpose, expiry), only for a known address Q->>M: sendPasswordReset(email, token), only for a known address A-->>U: 202 Accepted (same answer for any address) U->>A: POST /api/account/password/reset (token, newPassword) A->>X: execute(token, newPassword) X->>T: findUsable(hash of token), not used and not expired X->>X: password policy and compromised check X->>T: consume(hash of token), atomic X->>X: store the new hash and revoke the user's authorizations A-->>U: 204 No Content
    /**
     * Requests a password reset.
     *
     * @param email e-mail address of the user.
     */
    @Transactional
    public void execute(final String email) {
        final var token = tokenGenerator.generate();
        final var hashedToken = tokenGenerator.hash(token);
        // an unknown address gets nothing: the token above was generated and hashed all the same
        userAccountRepository.findByEmail(email)
                .ifPresent(account -> sendReset(account, email, token, hashedToken));
    }

    /**
     * Stores the reset token and mails it.
     *
     * @param account     the account to reset.
     * @param email       address to send the message to.
     * @param token       the reset token.
     * @param hashedToken hash of the reset token.
     */
    private void sendReset(final UserAccount account, final String email, final String token,
                           final String hashedToken) {
        accountTokenRepository.store(new AccountToken(UUID.randomUUID(), account.id(),
                AccountToken.PURPOSE_PASSWORD_RESET, hashedToken, clock.instant().plus(RESET_TTL), null));
        accountMailer.sendPasswordReset(email, token);
    }

This derives from the OWASP Forgot Password Cheat Sheet, which asks for a uniform response, a random single-use token with a short lifetime and a stored hash of it.

    /**
     * Resets the password of the user the token was issued to. The token is looked up without being consumed, every
     * check runs, and only then is the token consumed; the consumption is atomic, so of two concurrent resets with
     * the same token only one succeeds.
     *
     * @param token       the reset token received by e-mail.
     * @param newPassword the clear-text new password.
     * @throws InvalidPasswordException     if the password breaks the policy.
     * @throws CompromisedPasswordException if the password is known to be compromised.
     * @throws InvalidAccountTokenException if the token is unknown, expired, used or its account is gone.
     */
    @Transactional
    public void execute(final String token, final String newPassword) {
        final var hashedToken = tokenGenerator.hash(token);
        final var now = clock.instant();
        final var stored = accountTokenRepository
                .findUsable(hashedToken, AccountToken.PURPOSE_PASSWORD_RESET, now)
                .orElseThrow(InvalidAccountTokenException::new);
        final var account = userAccountRepository.findById(stored.userId())
                .orElseThrow(InvalidAccountTokenException::new);
        requirePolicy(account.username(), newPassword);
        requireNotCompromised(newPassword);
        accountTokenRepository.consume(hashedToken, AccountToken.PURPOSE_PASSWORD_RESET, now)
                .orElseThrow(InvalidAccountTokenException::new);
        userAccountRepository.updatePassword(account.id(), passwordHasher.encode(newPassword));
        revokeUserAuthorizationsUseCase.execute(account.username());
    }

This derives from the same OWASP Forgot Password Cheat Sheet, whose last steps are to invalidate the token after use and to end the user’s existing sessions.

Every check runs before the token is consumed, so a rejected password never burns the token and the user can try another one. Consuming it is a single conditional UPDATE, which is what makes it single use even under concurrent requests:

    /** Statement that marks a token as used and returns it, only when it is unused and not expired. */
    private static final String CONSUME_TOKEN = """
            UPDATE account_tokens SET used_at = ?
            WHERE hashed_token = ? AND purpose = ? AND used_at IS NULL AND expires_at > ?
            RETURNING id, user_id, purpose, hashed_token, expires_at, used_at
            """;

This derives from the PostgreSQL RETURNING documentation: the statement marks the token used and returns it only if it was still unused and unexpired, in one atomic step.

Once the password is replaced, RevokeUserAuthorizationsUseCase revokes the user’s tokens, so a stolen session or refresh token does not survive the reset. The reset token lifetime is 30 minutes and the e-mail verification token lasts 24 hours (RESET_TTL and VERIFICATION_TTL in the use cases above).

curl -i 'http://localhost:9000/api/account/verify?token=<token from the e-mail>'

# request a reset link: always 202
curl -i -X POST http://localhost:9000/api/account/password/reset-request \
  -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com"}'

# choose a new password with the token from the e-mail: 204, or 400 for a bad token or a rejected password
curl -i -X POST http://localhost:9000/api/account/password/reset \
  -H 'Content-Type: application/json' \
  -d '{"token":"<token from the e-mail>","newPassword":"<a new passphrase>"}'

# change the password of the signed-in account (bearer token issued by this server): 204, 400 or 401
curl -i -X POST http://localhost:9000/api/account/password \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"currentPassword":"<current>","newPassword":"<new>"}'

A rejected password answers 400 with a problem body; a request over the limit answers 429 with a Retry-After header in seconds (RFC 6585). A registration whose confirmation e-mail cannot be sent answers 503 and registers nothing.

Tests

The behaviours above are covered by tests that this page describes and does not paste, because none of them carries an include tag:

  • PasswordConfigurationTest encodes with the bean and checks that the hash is Argon2 and matches, that a different value does not match, that a bcrypt hash matches and asks for an upgrade, and that a PBKDF2 hash matches.

  • PasswordUpgradeIT (PostgreSQL container, real login form) stores a bcrypt hash, signs in and checks that the stored hash now starts with the Argon2 prefix, still matches and no longer asks for an upgrade; a wrong password leaves the hash untouched and a hash that is already current is not rewritten.

  • PasswordAuthenticationIT checks that a disabled account with a wrong password shows the same page as an unknown user, and that only the correct password reveals the "disabled" message.

  • ResetPasswordUseCaseTest covers an unusable token, a concurrently consumed token, a password that breaks the policy, contains the username or is compromised, each without consuming the token.

  • AccountApiIT drives the endpoints above end to end: e-mail verification enables the account, a taken address answers like a new one, a token works once, a rejected password keeps the token usable, a replayed verification link does not re-enable a disabled account, and a limit exceeded answers 429.

  • PasswordPolicyTest covers the length bounds and the username rule.

Security notes and pitfalls

  • User enumeration. Registration, reset request and sign-in answer identically for known and unknown identifiers, and the work done is made equal (the password is hashed and a token is generated either way) so timing does not leak it either. The only message that depends on the account, "disabled", appears after the correct password. Equalising the time of an unknown username at sign-in relies on DaoAuthenticationProvider encoding a dummy password for it; keep hideUserNotFoundExceptions on.

  • Rate limiting. The unauthenticated account endpoints are limited twice, per client address and per e-mail address, with Bucket4j buckets in AccountRateLimiter. The limits in application.yml are 20 requests per client and 5 per address in a 15 minute window, with at most 10,000 tracked keys; the buckets live in the memory of one instance, so several instances need a shared store. Behind a proxy, server.forward-headers-strategy must be set or every request appears to come from the proxy.

    /**
 * Rate limiter of the unauthenticated account endpoints (register, verify, reset request, reset), built on
 * <a href="https://bucket4j.com">Bucket4j</a> token buckets ({@link FixedWindowBuckets}). Requests are limited twice:
 * per client address, and per e-mail address when the request names one, so neither a single client nor many clients
 * aiming at one address can flood the server (and the mailboxes) with account mail or guess reset tokens. Each bucket
 * holds the limit of its key and is refilled all at once every {@link AccountRateLimitProperties#window()}.
 *
 * <p>The buckets of each kind of key live in a Caffeine cache bounded to
 * {@link AccountRateLimitProperties#maxTrackedKeys()} entries, which also drops a bucket idle for a whole window
 * (it would be full again anyway). They live in this instance only: several instances each apply the limits on
 * their own, until the buckets move to a shared store through a Bucket4j {@code ProxyManager} (for example
 * {@code bucket4j-postgresql}). The client address is {@code request.getRemoteAddr()}, so behind a proxy
 * {@code server.forward-headers-strategy} must be set for it to be the real client.
 */
@Component
@EnableConfigurationProperties(AccountRateLimitProperties.class)
public final class AccountRateLimiter {

    /** Limits, window and bound of the tracked keys. */
    private final AccountRateLimitProperties properties;

    /** Buckets per client address. */
    private final FixedWindowBuckets clients;

    /** Buckets per (lower-cased) e-mail address. */
    private final FixedWindowBuckets emails;

    /**
     * Creates the limiter.
     *
     * @param properties limits, window and bound of the tracked keys.
     * @param clock      source of the current time.
     */
    public AccountRateLimiter(final AccountRateLimitProperties properties, final Clock clock) {
        this.properties = properties;
        clients = new FixedWindowBuckets(clock, properties.window(), properties.maxTrackedKeys());
        emails = new FixedWindowBuckets(clock, properties.window(), properties.maxTrackedKeys());
    }

    /**
     * Counts one request and rejects it once a limit is exceeded.
     *
     * @param clientAddress address of the calling client.
     * @param email         e-mail address the request names, or {@code null}.
     * @throws AccountRateLimitExceededException if the client or the e-mail address exceeded its limit.
     */
    public void check(final String clientAddress, final String email) {
        if (!properties.enabled()) {
            return;
        }
        consume(clients, clientAddress, properties.perClient());
        if (email != null) {
            consume(emails, email.toLowerCase(Locale.ROOT), properties.perEmail());
        }
    }

    /**
     * Tells how many keys of each kind are tracked, after any pending eviction.
     *
     * @return the number of client keys plus the number of e-mail keys.
     */
    long trackedKeys() {
        return clients.trackedKeys() + emails.trackedKeys();
    }

    /**
     * Takes one token from the bucket of a key, creating the bucket on first use.
     *
     * @param buckets buckets of one kind of key.
     * @param key     the key.
     * @param limit   requests the key may make per window.
     * @throws AccountRateLimitExceededException if the bucket is empty.
     */
    private static void consume(final FixedWindowBuckets buckets, final String key, final int limit) {
        final var wait = buckets.tryConsume(key, limit);
        if (wait.isPresent()) {
            throw new AccountRateLimitExceededException(wait.get());
        }
    }
}

    This derives from the Bucket4j token-bucket library that the class builds on.

  • Token hygiene. Reset and verification tokens are random, stored only as a hash, expire, and are consumed by one atomic statement. A reset also revokes the user’s authorizations. The OWASP cheat sheet explains why the link must be single use and short lived.

  • Pepper. The example does not use a pepper (a secret added to every password before hashing and kept outside the database, in a vault or HSM). OWASP describes it as an optional extra layer; if you add one, it must survive a migration between encoders, so version it (for example in the encoder id) like the algorithm.

  • Migration between encoders. Keep every legacy encoder registered until no active user has a hash with its prefix. Accounts that never sign in are never upgraded; decide when to expire or force a reset for them.

  • Parameters age. The Spring factory defaults are a floor for compatibility, not a recommendation for your hardware: measure a verification on production-like machines, and raise the Argon2 memory and iterations before the next hash rotation.

  • Never log or return a password or a token. The OpenAPI schemas mark them with the password format for that reason, and the compromised-password check sends only a hash prefix.

  • Length limit. The policy caps passwords at 128 characters so a very long input cannot be used to make a hash computation expensive.
