Inheritance Mapping

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Java’s class hierarchies have no direct SQL counterpart — one of the paradigm-mismatch friction points named in Architecture. Hibernate offers three strategies for flattening a hierarchy onto tables, plus @MappedSuperclass for sharing mapped state without the hierarchy itself being polymorphic in queries.

SINGLE_TABLE

The whole hierarchy lives in one table; a discriminator column says which subtype each row represents.

@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "payment_type")
public abstract class Payment {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private BigDecimal amount;
}

@Entity
@DiscriminatorValue("CARD")
public class CardPayment extends Payment {
    private String last4Digits;
}

@Entity
@DiscriminatorValue("BANK_TRANSFER")
public class BankTransferPayment extends Payment {
    private String iban;
}

Fastest strategy — every query is against one table, no joins ever needed for polymorphic access. The cost: every subclass-specific column (last4Digits, iban) must be nullable, since any given row uses only the columns for its own subtype, and the table grows a column per subtype added over time. @DiscriminatorFormula replaces the plain column with a SQL expression when the discriminator has to be derived (e.g. from an existing legacy column) rather than stored directly.

JOINED

One table per class in the hierarchy, each holding only that class’s own columns, joined to the parent table on the shared primary key.

@Entity
@Inheritance(strategy = InheritanceType.JOINED)
public abstract class Payment {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private BigDecimal amount;
}

@Entity
public class CardPayment extends Payment {
    private String last4Digits; // in its own "card_payment" table, PK = FK to payment.id
}

Fully normalized (no nullable-by-construction columns, no wasted space), but a CardPayment row now requires a join across payment and card_payment, and a polymorphic query across the whole hierarchy joins in every subtype’s table.

TABLE_PER_CLASS

One table per concrete class, each repeating every inherited column:

@Entity
@Inheritance(strategy = InheritanceType.TABLE_PER_CLASS)
public abstract class Payment {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;
    private BigDecimal amount; // repeated in every concrete subtype's table
}

No joins for accessing one concrete subtype directly, but a polymorphic query across the hierarchy needs a UNION ALL across every concrete table — generally the least-used of the three strategies, since it combines denormalization (repeated columns) with the worst polymorphic-query cost. IDENTITY generation cannot be used with this strategy (each subtype’s own auto-increment sequence would collide across tables); use SEQUENCE or TABLE instead.

@MappedSuperclass

For sharing mapped attributes (an id-generation pattern, audit columns) across otherwise-unrelated entities without the hierarchy being queryable polymorphically — there is no common entity table or query root, just inherited mapping metadata:

@MappedSuperclass
public abstract class AuditableEntity {
    @Column(updatable = false)
    private Instant createdAt;
    private Instant updatedAt;
}

@Entity
public class Book extends AuditableEntity { /* ... */ }

@Entity
public class Author extends AuditableEntity { /* ... */ }

Book and Author each get their own independent created_at/updated_at columns; there is no FROM AuditableEntity query and no common table. Compare with Spring Data JPA's auditing support, which is commonly layered on top of exactly this pattern via AbstractAuditable/@EntityListeners(AuditingEntityListener.class).

SINGLE_TABLE is Hibernate’s default and the right starting point for most hierarchies; reach for JOINED when subtype-specific columns are numerous or storage waste from the nullable columns of SINGLE_TABLE becomes a real concern.

Table shapes compared

One hierarchy, three schemas, real SQL

The comparison table above is easy to believe and easy to misjudge, so the same Payment hierarchy was mapped three times and run on H2 with Hibernate ORM 7.4: one CardPayment and one BankTransferPayment were persisted under each strategy, and a polymorphic query (select p from Payment p) and a concrete query (select p from CardPayment p) were issued.

classDiagram Payment <|-- CardPayment Payment <|-- BankTransferPayment class Payment { Long id BigDecimal amount } class CardPayment { String last4Digits } class BankTransferPayment { String iban }

SINGLE_TABLE

create table payment (amount numeric(38,2), id bigint not null,
  payment_type varchar(31) not null check ((payment_type in ('CARD','BANK_TRANSFER'))),
  iban varchar(255), last4Digits varchar(255), primary key (id))

insert into payment (amount,last4Digits,payment_type,id) values (?,?,'CARD',?)
insert into payment (amount,iban,payment_type,id) values (?,?,'BANK_TRANSFER',?)

-- polymorphic
select p1_0.id,p1_0.payment_type,p1_0.amount,p1_0.iban,p1_0.last4Digits from payment p1_0
-- concrete
select cp1_0.id,cp1_0.amount,cp1_0.last4Digits from payment cp1_0 where cp1_0.payment_type='CARD'

Note the discriminator: it is not null, and Hibernate adds a check constraint listing the legal values — so a new subclass needs a schema change even though no column is added for it. The concrete query reads one table with a where on the discriminator, which is why it is the cheapest of the three.

JOINED

create table payment (amount numeric(38,2), id bigint not null, primary key (id))
create table card_payment (id bigint not null, last4Digits varchar(255), primary key (id))
create table bank_transfer_payment (id bigint not null, iban varchar(255), primary key (id))

insert into payment (amount,id) values (?,?)
insert into card_payment (last4Digits,id) values (?,?)

-- polymorphic
select p1_0.id,
       case when p1_2.id is not null then 1 when p1_1.id is not null then 2 end,
       p1_0.amount, p1_1.iban, p1_2.last4Digits
from payment p1_0
left join bank_transfer_payment p1_1 on p1_0.id=p1_1.id
left join card_payment p1_2 on p1_0.id=p1_2.id
-- concrete
select cp1_0.id, cp1_1.amount, cp1_0.last4Digits
from card_payment cp1_0 join payment cp1_1 on cp1_0.id=cp1_1.id

Every persisted subtype row costs two inserts. The polymorphic select has no discriminator column: the subtype is derived from which of the left-joined tables has a matching row (the case expression), so the query needs one left join per subclass and grows with each new subclass. The concrete query needs one inner join. Adding a subclass adds a table and no column anywhere.

TABLE_PER_CLASS

create table bank_transfer_payment (amount numeric(38,2), id bigint not null, iban varchar(255), primary key (id))
create table card_payment (amount numeric(38,2), id bigint not null, last4Digits varchar(255), primary key (id))

-- polymorphic
select p1_0.id, p1_0.clazz_, p1_0.amount, p1_0.iban, p1_0.last4Digits
from (select amount, id, last4Digits, null as iban, 1 as clazz_ from card_payment
      union all
      select amount, id, null as last4Digits, iban, 2 as clazz_ from bank_transfer_payment) p1_0
-- concrete
select cp1_0.id, cp1_0.amount, cp1_0.last4Digits from card_payment cp1_0

The abstract root has no table; each concrete table repeats amount. The polymorphic query is a union all subquery with a synthetic clazz_ column that Hibernate uses to instantiate the right subclass, and it grows by one select per concrete class. The concrete query is as cheap as it gets.

The rule that IDENTITY cannot be combined with this strategy was confirmed: building the factory failed with a MappingException whose message begins "Cannot use identity column key generation with <union-subclass> mapping" and names the root entity. Use SEQUENCE (the pooled default) so that identifiers are unique across all the concrete tables at once.

flowchart LR Q["select p from Payment p"] Q --> SINGLE["SINGLE_TABLE: one scan of payment"] Q --> JOINED["JOINED: payment left join every subclass table"] Q --> TPC["TABLE_PER_CLASS: union all of every concrete table"] C["select c from CardPayment c"] C --> SINGLE2["SINGLE_TABLE: scan with discriminator filter"] C --> JOINED2["JOINED: card_payment inner join payment"] C --> TPC2["TABLE_PER_CLASS: scan of card_payment"]

@MappedSuperclass, verified

The AuditableEntity pattern was run with Book and Author extending it. Each entity’s table got its own createdAt and updatedAt columns (timestamp(6) with time zone on H2), and @PrePersist/@PreUpdate callback methods declared on the mapped superclass fired for both subclasses, so audit timestamps need no repeated code. Querying the superclass is impossible by design: select a from AuditableEntity a failed with UnknownEntityException: Could not resolve root entity 'AuditableEntity', because a mapped superclass is not an entity and has no table. If one query must range over both Book and Author, they need a common @Entity root (and one of the strategies above) rather than a mapped superclass.

Choosing, in practice

Three questions settle most hierarchies:

  1. Are polymorphic queries frequent? If most reads are from Payment, prefer SINGLE_TABLE; the single scan wins and the nullable subtype columns are the price.

  2. Do subtypes have many distinct columns that must be not null? Only JOINED and TABLE_PER_CLASS can declare them non-nullable in the schema; with SINGLE_TABLE the database cannot enforce that a card payment has last4Digits, so the check moves into application code or into a conditional check constraint.

  3. Will subclasses be added often? JOINED adds a table and never touches existing ones; SINGLE_TABLE adds nullable columns (and updates the discriminator check) to a table that may be large.

TABLE_PER_CLASS rarely wins any of the three, which matches its low use in practice.
