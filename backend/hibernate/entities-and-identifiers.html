Entities and Identifiers

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The identifier is the one mapping every entity must have. This page covers declaring an entity, choosing an access strategy, the identifier-generation strategies, composite keys, and the equals()/hashCode() question every entity eventually raises.

@Entity and @Table

@Entity
@Table(name = "book", schema = "library")
public class Book {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;

    // ...
}

@Entity is required; @Table is optional — omitted, Hibernate derives a table name from the entity name using its naming strategy. @Table also accepts uniqueConstraints and indexes, honored only by schema-generation tooling (see Schema Generation & Tooling), never enforced by Hibernate at runtime.

Field vs. property access

Hibernate decides access type by where @Id (or, for property access, the corresponding getter) is placed:

  • Field access — annotations on fields; Hibernate reads/writes fields directly (via reflection or bytecode enhancement), bypassing getters/setters entirely. Simpler, but any custom logic in a setter is skipped by Hibernate itself.

  • Property access — annotations on getters; Hibernate always goes through the accessor methods, so a computed or validated getter/setter runs on every read/write, including Hibernate’s own.

Mixing the two per-entity is allowed (@Access(AccessType.PROPERTY) on an individual field/getter) but adds a surprising edge case for every reader — pick one access type per entity and stay consistent.

@GeneratedValue strategies

Strategy Behavior

GenerationType.IDENTITY

Delegates to an auto-increment/identity column (SERIAL/IDENTITY). Simple, but the ID is known only after the INSERT executes, which disables JDBC batching for inserts of that entity (see Bulk Operations & Batching).

GenerationType.SEQUENCE

Uses a database sequence, optionally with @SequenceGenerator (allocationSize lets Hibernate pre-fetch a block of values in memory, avoiding a round-trip per insert). The generally preferred strategy on databases that support sequences (PostgreSQL, Oracle) because the ID is known before the insert, keeping batching intact.

GenerationType.TABLE

Emulates a sequence with a dedicated table row, for databases with neither identity columns nor sequences. Portable but the slowest option (extra SELECT/UPDATE per allocation) — rarely the right choice today.

GenerationType.UUID

Generates a random UUID client-side, no database round-trip. Good for distributed/sharded systems where a centrally-issued numeric key is a bottleneck; the trade-off is a wider key (16 bytes vs. 8) and worse index locality on inserts unless a time-ordered UUID scheme is used.

Custom (org.hibernate.generator.BeforeExecutionGenerator)

Implement the SPI directly (see Distributed ID Generation for a TSID/Snowflake-style example) and bind it with a generator annotation marked @IdGeneratorType; @GenericGenerator is deprecated since 6.2. A worked example follows below.

Composite keys

Two ways to model a multi-column primary key:

// (a) @EmbeddedId -- the key is a first-class @Embeddable value type
@Embeddable
public class OrderLineId implements Serializable {
    private Long orderId;
    private Integer lineNumber;
    // equals()/hashCode() over both fields, getters/setters omitted
}

@Entity
public class OrderLine {
    @EmbeddedId
    private OrderLineId id;
    private int quantity;
}

// (b) @IdClass -- the entity itself carries the plain @Id fields; the class named in
// @IdClass mirrors them and supplies equals()/hashCode()
@Entity
@IdClass(OrderLinePk.class)
public class OrderLine2 {
    @Id
    private Long orderId;
    @Id
    private Integer lineNumber;
}

@EmbeddedId is generally preferred: the key is one navigable object (orderLine.getId().getLineNumber()), and it composes naturally with @MapsId below. @IdClass avoids introducing a wrapper type when the composite fields are also meaningful as plain entity fields, at the cost of duplicating them (once as @Id fields, once in the @IdClass shadow class).

@NaturalId

@NaturalId marks a business key — unique, rarely-changing, but not the primary key (an ISBN, a username, a tax ID). It is not itself a generation strategy; it is a lookup optimization: Session.byNaturalId(Book.class) resolves an entity by its natural id through the same identity-map/first-level-cache machinery as find() by primary key, and, with @NaturalIdCache, through the second-level cache too (see Second-Level Cache).

@Entity
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @NaturalId
    private String isbn;
}

// ...
Book book = session.byNaturalId(Book.class).using("isbn", "9781617290459").load();

Derived identity with @MapsId

@MapsId lets a @OneToOne (or @ManyToOne) child share its parent’s primary key value instead of having its own generated one — the classic "one row per parent, same PK" shared-primary-key pattern:

@Entity
public class Employee {
    @Id
    private Long id;
}

@Entity
public class EmployeeDetails {
    @Id
    private Long id; // same value as the owning Employee's id

    @MapsId
    @OneToOne
    @JoinColumn(name = "id")
    private Employee employee;
}

See Associations for the general @OneToOne shapes this composes with.

equals() and hashCode() for entities

The three plausible strategies, and why business-key equality is usually the right default:

  • Reference equality (no override) — correct only while both instances live in the same persistence context (the identity map already guarantees == there); breaks the moment an entity crosses contexts or ends up in a Set alongside a detached/newly-loaded duplicate.

  • Primary-key equality — compares the @Id value, but a transient entity has no id yet (null), so two distinct new entities can spuriously look "equal" (both null), and an entity’s identity/hash code changes the instant it gets an id assigned after persist() — a HashSet<Book> corrupts itself if the entity’s hash code changes while it is a member.

  • Business-key equality (recommended) — compare a stable, non-null attribute the domain considers the "real" identity (an @NaturalId, or a manually chosen field). This is what the User Guide recommends, and it is the only strategy stable across transient, managed, and detached states.

There is no single answer that fits every entity; an entity with no natural business key at all is one of the few legitimate cases for leaving equals()/hashCode() at their default Object behavior and simply avoiding putting transient instances into hash-based collections.

Generated identifiers compared on a running example

The strategies in the table above differ in when the identifier becomes known and therefore in when the INSERT can run. That timing is easiest to see by persisting three entities inside one transaction with JDBC batching enabled (hibernate.jdbc.batch_size=10) and printing the SQL as it is issued. Two minimal entities were used, identical except for the generation strategy:

@Entity
public class IdentityBook {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String title;
}

@Entity
public class SequenceBook {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;
    private String title;
}
em.getTransaction().begin();
for (int i = 0; i < 3; i++) {
    em.persist(new IdentityBook("b" + i));
    System.out.println("-- after persist " + i);
}
em.getTransaction().commit();

The IDENTITY entity prints one insert during each persist call, three statements in all (insert into identity_book (title,id) values (?,default)), and the statistics report three prepared statements. The SEQUENCE entity behaves differently:

Hibernate: select next value for sequence_book_SEQ
-- after persist 0
Hibernate: select next value for sequence_book_SEQ
-- after persist 1
-- after persist 2
-- commit
Hibernate: insert into sequence_book (title,id) values (?,?)
Hibernate: insert into sequence_book (title,id) values (?,?)
Hibernate: insert into sequence_book (title,id) values (?,?)

Three observations follow from that output:

  • The inserts are delayed until the flush at commit, and the three statements share one prepared statement that is sent to the database as a single JDBC batch (the statistics counted three prepared statements in each case: three single inserts for IDENTITY, but two sequence reads plus one batched insert for SEQUENCE). With IDENTITY the insert has to run immediately to learn the key, so the batch size setting has no effect.

  • The sequence was read only twice for three entities. The generated default is a pooled optimizer with an increment of 50, and the DDL Hibernate emitted confirms it: create sequence sequence_book_SEQ start with 1 increment by 50. Identifiers are handed out from an in-memory block, so most persist calls cost no round trip at all. An application that also inserts rows by hand into such a table must use the same increment, or identifiers will collide.

  • The default sequence name is derived from the entity’s table name (sequence_book_SEQ for the table sequence_book), one sequence per entity — not one global hibernate_sequence as in Hibernate 5. Existing schemas migrated from Hibernate 5 usually need an explicit @SequenceGenerator to keep working.

sequenceDiagram participant App as Application participant PC as Persistence context participant DB as Database Note over App,DB: IDENTITY App->>PC: persist PC->>DB: insert, key generated by the database DB-->>PC: generated id Note over App,DB: SEQUENCE App->>PC: persist PC->>DB: next value, only when the pooled block is empty DB-->>PC: id block Note over PC: insert queued until flush App->>PC: commit PC->>DB: batched inserts

GenerationType.UUID needs neither a sequence read nor an immediate insert: the identifier is assigned in memory by persist, the insert is queued like the sequence case, and on H2 the column was created with the database’s native uuid type.

Composite keys and natural ids in practice

An @EmbeddedId key is looked up with an instance of the embeddable class, and Hibernate renders the match as a tuple comparison:

em.persist(new OrderLine(new OrderLineId(7L, 1), 3));
// ...
OrderLine line = em.find(OrderLine.class, new OrderLineId(7L, 1));
Hibernate: select ol1_0.lineNumber,ol1_0.orderId,ol1_0.quantity from order_line ol1_0
           where (ol1_0.lineNumber,ol1_0.orderId) in ((?,?))

The same run exposed a detail that matters for index design: the generated primary key is declared as primary key (lineNumber, orderId). Hibernate orders the columns of a composite key alphabetically by attribute name, not in field declaration order, so a key declared as (orderId, lineNumber) in Java has its index leading with lineNumber in the schema. Queries that filter only by orderId then cannot use the primary-key index prefix. When the column order matters, generate the schema from a migration script instead of from the annotations, or add an explicit index (see Schema Generation and Tooling).

@NaturalId adds a unique (isbn) constraint to the DDL and gives lookups by business key their own API. Two consecutive byNaturalId loads in one session printed a single statement:

Book b = session.byNaturalId(Book.class).using("isbn", "9781617290459").load();
Book b2 = session.byNaturalId(Book.class).using("isbn", "9781617290459").load();
// b == b2, and only one "select ... where isbn=?" ran

Why primary-key equals() bites: a demonstration

The earlier section warns that an identifier-based hashCode() changes when the identifier is assigned. The following entity implements exactly that strategy, and the program shows both failure modes:

@Entity
public class PkEqBook {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;

    @Override public boolean equals(Object o) {
        return o instanceof PkEqBook b && Objects.equals(id, b.id);
    }
    @Override public int hashCode() { return Objects.hashCode(id); }
}

Set<PkEqBook> set = new HashSet<>();
PkEqBook x = new PkEqBook(), y = new PkEqBook();
System.out.println("two new instances equal: " + x.equals(y));   // true
set.add(x);
em.getTransaction().begin();
em.persist(x);                                                  // id assigned here
em.getTransaction().commit();
System.out.println("set.contains(x): " + set.contains(x));       // false

The program prints two new instances equal: true and then set.contains(x) after persist: false: two distinct transient objects compare equal because both identifiers are null, and the very instance that was put into the set can no longer be found once persist has given it an identifier, because its hash code moved to a different bucket. A business-key implementation (isbn for a Book) avoids both, as long as the key is assigned before the entity is added to any hash-based collection.

Shared primary keys with @MapsId, verified

For the Employee/EmployeeDetails pair shown earlier, the generated schema makes the child’s primary key also its foreign key: create table employee_details (id bigint not null, badge varchar(255), primary key (id)) plus alter table employee_details add constraint ... foreign key (id) references employee. Persisting both in one transaction produced two inserts, employee first, and em.find(EmployeeDetails.class, 42L) returned a row whose id was 42 — the child never has an identifier of its own to generate.

A custom generator in Hibernate 7

The table above lists custom generators. The older way of binding one, @GenericGenerator, has been deprecated since Hibernate 6.2; the current way is a generator annotation meta-annotated with @IdGeneratorType, plus a class implementing BeforeExecutionGenerator (the interface IdentifierGenerator now extends). Run on H2 with Hibernate ORM 7.4, this gives an entity whose identifier is a prefixed string:

@IdGeneratorType(PrefixedGenerator.class)
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.FIELD, ElementType.METHOD})
public @interface PrefixedId {
    String prefix();
}

public class PrefixedGenerator implements BeforeExecutionGenerator {
    private static final AtomicLong COUNTER = new AtomicLong();
    private final String prefix;

    public PrefixedGenerator(PrefixedId config) { this.prefix = config.prefix(); }

    @Override
    public Object generate(SharedSessionContractImplementor session, Object owner,
                           Object currentValue, EventType eventType) {
        return prefix + "-" + COUNTER.incrementAndGet();
    }

    @Override
    public EnumSet<EventType> getEventTypes() { return EventTypeSets.INSERT_ONLY; }
}

@Entity
public class Book {
    @Id @PrefixedId(prefix = "BK")
    private String id;
    private String title;
}

Persisting two books printed assigned: BK-1, BK-2 straight after persist, and the inserts were the plain insert into book (title,id) values (?,?): a BeforeExecutionGenerator assigns the value in memory before the statement, so it behaves like SEQUENCE and UUID rather than IDENTITY. A real implementation would use a database sequence or a time-ordered scheme instead of an in-process counter, which is not unique across JVMs or restarts.
