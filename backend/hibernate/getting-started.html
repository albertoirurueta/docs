Getting Started with Hibernate

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page gets a bare Hibernate ORM project running: what Hibernate is in relation to Jakarta Persistence, the Maven coordinates, the two ways to bootstrap it, and a minimal "Hello, Hibernate" example.

Hibernate and Jakarta Persistence

Jakarta Persistence (formerly JPA, Java Persistence API) is a specification: a set of interfaces and annotations (jakarta.persistence.*) that describe object/relational mapping without prescribing an implementation. Hibernate ORM is the reference, most widely used implementation of that specification — it also exposes a richer native API (org.hibernate.*: SessionFactory, Session, StatelessSession) that goes beyond what the spec defines. Code written purely against jakarta.persistence.* can, in principle, run against another provider (EclipseLink, OpenJPA); code that uses org.hibernate.* types is tied to Hibernate.

Jakarta Persistence 3.2 is the current specification version, aligned with Hibernate ORM 7.x. A prior, easy to trip over, historical detail: Java EE’s rebrand to Jakarta EE 9 moved every javax.* namespace to jakarta.*, so javax.persistence.Entity became jakarta.persistence.Entity. Always use jakarta.persistence.* in new code — this section never uses the old javax.persistence package.

Adding Hibernate to a build

Maven, using the hibernate-platform BOM to pin compatible versions of Hibernate and its transitive dependencies:

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.hibernate.orm</groupId>
            <artifactId>hibernate-platform</artifactId>
            <version>7.4.15.Final</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>org.hibernate.orm</groupId>
        <artifactId>hibernate-core</artifactId>
    </dependency>
    <dependency>
        <groupId>org.postgresql</groupId>
        <artifactId>postgresql</artifactId>
        <scope>runtime</scope>
    </dependency>
</dependencies>

Gradle equivalent: implementation platform("org.hibernate.orm:hibernate-platform:7.4.15.Final") plus implementation "org.hibernate.orm:hibernate-core". Under Spring Boot, none of this is needed directly — spring-boot-starter-data-jpa already brings in a compatible hibernate-core (see Hibernate (JPA & ORM)); this section documents plain Jakarta Persistence/Hibernate, with Spring Boot noted only where it changes something.

Bootstrapping: persistence.xml vs. programmatic

The standard, portable way to describe a persistence unit is META-INF/persistence.xml on the classpath:

<persistence xmlns="https://jakarta.ee/xml/ns/persistence" version="3.2">
    <persistence-unit name="library" transaction-type="RESOURCE_LOCAL">
        <class>com.example.library.Book</class>
        <properties>
            <property name="jakarta.persistence.jdbc.url" value="jdbc:postgresql://localhost:5432/library"/>
            <property name="jakarta.persistence.jdbc.user" value="library"/>
            <property name="jakarta.persistence.jdbc.password" value="library"/>
            <property name="hibernate.hbm2ddl.auto" value="validate"/>
        </properties>
    </persistence-unit>
</persistence>
EntityManagerFactory emf = Persistence.createEntityManagerFactory("library");

Hibernate also supports a fully programmatic bootstrap via org.hibernate.cfg.Configuration or the native bootstrap SPI (StandardServiceRegistryBuilder + MetadataSources), useful when settings come from code rather than a static file, or when embedding Hibernate in a framework that supplies its own DataSource — this is how Spring Boot builds the EntityManagerFactory bean without a persistence.xml at all.

"Hello, Hibernate"

@Entity
public class Book {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;

    protected Book() {
        // required no-arg constructor for Hibernate's proxying/reflection
    }

    public Book(String title) {
        this.title = title;
    }

    // getters and setters omitted
}

public class HelloHibernate {
    public static void main(String[] args) {
        EntityManagerFactory emf = Persistence.createEntityManagerFactory("library");
        try (EntityManager em = emf.createEntityManager()) {
            em.getTransaction().begin();
            em.persist(new Book("Hello, Hibernate"));
            em.getTransaction().commit();

            List<Book> books = em.createQuery("select b from Book b", Book.class).getResultList();
            books.forEach(b -> System.out.println(b.getTitle()));
        } finally {
            emf.close();
        }
    }
}

hibernate.properties and the most-used settings

An alternative to embedding properties in persistence.xml is a hibernate.properties file on the classpath, read automatically at bootstrap. The settings reached for most often:

Property Purpose

hibernate.hbm2ddl.auto

Schema-generation mode (none/validate/update/create/create-drop) — see Schema Generation & Tooling.

hibernate.show_sql / hibernate.format_sql / hibernate.highlight_sql

Log generated SQL to stdout, pretty-printed and syntax-highlighted — useful while learning, noisy in production (prefer a JDBC-driver-level or logger-based approach there).

hibernate.dialect

Usually auto-detected from the JDBC URL/driver since Hibernate 6; set explicitly only when detection is ambiguous.

hibernate.connection.provider_class / hibernate.hikari.*

Connection-pool selection and tuning when not letting a framework (Spring Boot) supply the DataSource.

hibernate.jdbc.batch_size

JDBC statement batching — see Bulk Operations & Batching.

Logging generated SQL through a real logger (rather than hibernate.show_sql) uses the org.hibernate.SQL (statement) and org.hibernate.orm.jdbc.bind (bound parameter values) logger categories.

Worked example: a runnable Book application on H2

The fragments above are enough to read; the following project is enough to run. It uses an in-memory H2 database so that nothing has to be installed, and Hibernate ORM 7.4.15.Final (any 7.4.x behaves the same for everything on this page). The only additions to the earlier pom.xml are the H2 driver and a Java 17 compiler level, because Hibernate ORM 7 requires Java 17 or newer:

<properties>
    <maven.compiler.release>17</maven.compiler.release>
</properties>

<dependencies>
    <dependency>
        <groupId>org.hibernate.orm</groupId>
        <artifactId>hibernate-core</artifactId>
        <version>7.4.15.Final</version>
    </dependency>
    <dependency>
        <groupId>com.h2database</groupId>
        <artifactId>h2</artifactId>
        <version>2.3.232</version>
        <scope>runtime</scope>
    </dependency>
</dependencies>

Jakarta Persistence 3.2 added a standard, code-based alternative to persistence.xml: jakarta.persistence.PersistenceConfiguration. Hibernate’s implementation is org.hibernate.jpa.HibernatePersistenceConfiguration, which adds Hibernate-specific conveniences such as showSql(...). It needs no XML file and no META-INF directory:

EntityManagerFactory emf = new HibernatePersistenceConfiguration("library")
        .managedClass(Book.class)
        .jdbcUrl("jdbc:h2:mem:library;DB_CLOSE_DELAY=-1")
        .jdbcUsername("sa")
        .jdbcPassword("")
        .property("jakarta.persistence.schema-generation.database.action", "create")
        .showSql(true, false, false)   // show, format, highlight
        .createEntityManagerFactory();

System.out.println("Hibernate " + org.hibernate.Version.getVersionString());
try (EntityManager em = emf.createEntityManager()) {
    em.getTransaction().begin();
    em.persist(new Book("Hello, Hibernate"));
    em.getTransaction().commit();

    em.createQuery("select b from Book b", Book.class)
      .getResultList()
      .forEach(b -> System.out.println(b.getTitle()));
}
emf.close();

Running it with the Book entity from the previous section prints (the order matters: the table is created while the factory is built, before the first line of application code runs):

Hibernate: create table book (id bigint generated by default as identity, title varchar(255), primary key (id))
Hibernate 7.4.15.Final
Hibernate: insert into book (title,id) values (?,default)
Hibernate: select b1_0.id,b1_0.title from book b1_0
Hello, Hibernate

Two details of that SQL are worth reading once. The insert lists default for the id column because the entity uses GenerationType.IDENTITY: the database produces the key. The select uses the generated alias b1_0 (first entity, first occurrence) for every column, which is how Hibernate 6 and 7 name table aliases in all of their SQL.

Four ways to bootstrap, one result

All of Hibernate’s bootstrap routes end in the same object: a SessionFactory, which is also an EntityManagerFactory. They differ only in how the settings and the list of mapped classes arrive.

flowchart LR XML["persistence.xml"] --> P["Persistence.createEntityManagerFactory"] CODE["HibernatePersistenceConfiguration"] --> F["EntityManagerFactory"] CFG["Configuration"] --> SF["SessionFactory"] REG["StandardServiceRegistryBuilder plus MetadataSources"] --> SF P --> F F -->|"unwrap(SessionFactory.class)"| SF SF -->|"is an"| F
Style Typical use Notes

persistence.xml plus Persistence.createEntityManagerFactory

Portable Jakarta Persistence applications, application servers.

Listing <class> elements is the portable way to name the entities; the resulting factory can still be unwrapped to a SessionFactory.

HibernatePersistenceConfiguration

Plain Java SE applications and tests that want no XML.

The Jakarta Persistence 3.2 PersistenceConfiguration API plus Hibernate additions.

Configuration

Older native-API code and quick experiments.

new Configuration().addAnnotatedClass(Book.class).setProperty(...).buildSessionFactory().

StandardServiceRegistryBuilder plus MetadataSources

Frameworks and anyone who needs to hook into individual bootstrap stages.

The lowest-level route; Configuration is a thin convenience over it.

Each of the four was run against H2 and produced a working factory that persisted and read back a Book. A persistence.xml unit looks like the one earlier on this page with the H2 URL, and Persistence.createEntityManagerFactory("library-xml") found it on the classpath. The native route reads:

StandardServiceRegistry registry = new StandardServiceRegistryBuilder()
        .applySetting("hibernate.connection.url", "jdbc:h2:mem:library;DB_CLOSE_DELAY=-1")
        .applySetting("hibernate.connection.username", "sa")
        .applySetting("hibernate.hbm2ddl.auto", "create-drop")
        .build();
SessionFactory sf = new MetadataSources(registry)
        .addAnnotatedClass(Book.class)
        .buildMetadata()
        .buildSessionFactory();

sf.inTransaction(session -> session.persist(new Book("Native bootstrap")));
List<String> titles = sf.fromSession(session ->
        session.createSelectionQuery("select b.title from Book b", String.class).getResultList());

SessionFactory.inTransaction(...) and fromSession(...) are the shortest way to run a unit of work with the native API: they open a session, begin a transaction, commit on success, roll back if the lambda throws, and close the session either way.

Reading the startup log

The first lines Hibernate logs say more than most people read. On the H2 run above they include the pieces that matter when a deployment misbehaves:

  • HHH10001005: Database info names the JDBC URL, the driver, the dialect it detected (H2Dialect), the database version, the default catalog/schema, whether autocommit is on (false — Hibernate manages the transaction itself), and the isolation level (READ_COMMITTED).

  • HHH10001002: Using built-in connection pool (not intended for production use) is a warning and means no connection pool was configured; production setups name one (hibernate.hikari.*, or a container DataSource).

  • The pool line reports the minimum and maximum size of the built-in pool; it is a placeholder for tests.

If the dialect line shows an unexpected product, fix the JDBC URL before looking anywhere else — every SQL decision downstream follows from it.

Seeing the SQL: show_sql versus loggers

hibernate.show_sql prints with System.out and is what the run above used. The logger-based route is the one to keep in real configuration, because it goes through the application’s logging backend and can be switched per category. With the default JBoss Logging to java.util.logging binding, a logging.properties containing the two categories

org.hibernate.SQL.level=FINE
org.hibernate.orm.jdbc.bind.level=FINEST

(plus a console handler at ALL) printed, for the same insert:

LOG DEBUG org.hibernate.SQL: insert into book (title,id) values (?,default)
LOG TRACE org.hibernate.orm.jdbc.bind: binding parameter (1:VARCHAR) <- [Hello, Hibernate]

org.hibernate.SQL carries the statement text; org.hibernate.orm.jdbc.bind carries the bound values and is the one that should stay off in production logs, since it prints data.
