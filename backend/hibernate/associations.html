Associations

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Associations are where the paradigm mismatch bites hardest: a directional Java reference has to become an undirected foreign key, navigable from either table. This page covers the four association shapes, the owning/inverse distinction every bidirectional association needs, and cascading.

@ManyToOne — the simple, owning case

@Entity
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "author_id", nullable = false)
    private Author author;
}

@ManyToOne always owns the foreign-key column (@JoinColumn) — there is nothing to configure about which side is owning here, since only the "many" side has a column to hold the key.

@OneToMany — owning vs. inverse

The "one" side of a to-many association has no column of its own to store; it can only ever be the inverse (non-owning) side, declared with mappedBy naming the owning @ManyToOne field on the other entity:

@Entity
public class Author {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToMany(mappedBy = "author", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Book> books = new ArrayList<>();

    // bidirectional-sync helper methods -- see below
    public void addBook(Book book) {
        books.add(book);
        book.setAuthor(this);
    }

    public void removeBook(Book book) {
        books.remove(book);
        book.setAuthor(null);
    }
}

Owning side is the side whose column changes actually get written — Hibernate only looks at the owning side’s in-memory state to decide what SQL to issue. Mutating only the inverse side’s collection (author.getBooks().add(book) without also setting book.setAuthor(author)) persists nothing: no INSERT/UPDATE is generated, because the owning @ManyToOne field never changed. This is the single most common bidirectional-association bug, and the reason for the helper-method pattern above: addBook/removeBook keep both sides of the in-memory graph consistent, so callers never have to remember to touch both fields themselves. It is also possible, and often simpler, to map an association unidirectionally — keep only the owning @ManyToOne (or @OneToMany with an explicit @JoinColumn, avoiding mappedBy and the inverse collection entirely) when the reverse navigation is never actually needed.

@OneToOne

Two shapes:

// (a) Foreign-key shared column, unidirectional/owning
@Entity
public class Employee {
    @Id
    private Long id;

    @OneToOne
    @JoinColumn(name = "parking_spot_id")
    private ParkingSpot parkingSpot;
}

// (b) Shared primary key via @MapsId -- see entities-and-identifiers.adoc
@Entity
public class EmployeeDetails {
    @Id
    private Long id;

    @MapsId
    @OneToOne
    @JoinColumn(name = "id")
    private Employee employee;
}

Bidirectional @OneToOne needs the same mappedBy treatment as @OneToMany: the non-owning side declares @OneToOne(mappedBy = "employee") and holds no column. See Entities and Identifiers for the shared-primary-key variant in full.

@ManyToMany and @JoinTable

@Entity
public class Book {
    @ManyToMany
    @JoinTable(
        name = "book_category",
        joinColumns = @JoinColumn(name = "book_id"),
        inverseJoinColumns = @JoinColumn(name = "category_id"))
    private Set<Category> categories = new HashSet<>();
}

@Entity
public class Category {
    @ManyToMany(mappedBy = "categories")
    private Set<Book> books = new HashSet<>();
}

A many-to-many needs a join table with no object-model counterpart — one more instance of the associations half of the paradigm mismatch. When the link itself needs its own attributes (a timestamp, a role, a quantity), @ManyToMany cannot express it; model the join table as its own @Entity with two @ManyToOne associations instead (an explicit "link entity"), which is also the only shape that supports adding a link-specific @Version column for optimistic locking on the association itself.

Cascading and orphan removal

cascade on an association propagates JPA operations from the owning entity to the associated one(s): PERSIST, MERGE, REMOVE, REFRESH, DETACH, or ALL for all five. orphanRemoval = true (available on @OneToOne/@OneToMany) goes further: removing a child from the collection, or reassigning a @OneToOne to a different value, deletes the orphaned row — not just skips cascading a later remove() call, but actively issues a DELETE for anything that fell out of the association. Reach for cascade = CascadeType.ALL, orphanRemoval = true on a true parent/child ("composition") relationship whose children have no independent existence or lifecycle outside their parent (order/order-line is the textbook case); avoid it on associations between independently-lifecycled entities, where cascading a remove() would delete something the rest of the system still expects to exist.

@OnDelete(action = OnDeleteAction.CASCADE) is a different mechanism entirely: it tells schema-generation tooling to add ON DELETE CASCADE to the foreign-key constraint itself, so the database enforces the cascade even for deletes that bypass Hibernate (a raw SQL DELETE, another application). It composes with, but does not replace, JPA-level orphanRemoval/cascade = REMOVE, which only fire for deletes that go through Hibernate’s own EntityManager.

Object graph vs. foreign keys

The model, and the SQL each association shape produces

Everything below uses the library running example — Author, Book, and a free-form tag or category on a book — and was run against H2 with Hibernate ORM 7.4 and the SQL printed as it was issued.

erDiagram AUTHOR ||--o{ BOOK : "book.author_id" BOOK }o--o{ TAG : "join table book_tag" AUTHOR { bigint id PK varchar name } BOOK { bigint id PK varchar title bigint author_id FK } TAG { bigint id PK varchar name }

The BOOK.author_id column belongs to the table of the many side, so Book.author is the owning side and Author.books is the inverse (mappedBy). The join table has no entity of its own.

The inverse-side bug, observed

The text above says that changing only the inverse collection persists nothing. This is that program:

Author a = new Author("Alice");
em.persist(a);

Book b = new Book("Orphan by mistake");
a.getBooks().add(b);      // inverse side only -- b.setAuthor(a) is never called
em.persist(b);
// commit

The statements issued were insert into author (...) and insert into book (author_id,title,id) values (?,?,?), with null bound for author_id; a following select count(b) from Book b where b.author is not null returned 0. The Author entity even listed the book in its collection, in memory, for the rest of that persistence context — the in-memory graph and the database simply disagreed. The helper methods addBook and removeBook exist so that this state cannot be reached by accident.

Cascade and orphan removal, observed

With cascade = CascadeType.ALL, orphanRemoval = true on Author.books and the helper methods:

Author a = new Author("Bob");
a.addBook(new Book("B1"));
a.addBook(new Book("B2"));
em.persist(a);                          // one persist, three inserts

// later, in a new transaction:
Author found = em.find(Author.class, id);
found.removeBook(found.getBooks().get(0));   // orphan removal

// and later still:
em.remove(em.find(Author.class, id));        // cascade REMOVE
insert into author (name,id) values (?,?)
insert into book (author_id,title,id) values (?,?,?)
insert into book (author_id,title,id) values (?,?,?)
-- orphan removal
select a1_0.id,a1_0.name from author a1_0 where a1_0.id=?
select b1_0.author_id,b1_0.id,b1_0.title from book b1_0 where b1_0.author_id=?
delete from book where id=?
-- cascading remove
select a1_0.id,a1_0.name from author a1_0 where a1_0.id=?
select b1_0.author_id,b1_0.id,b1_0.title from book b1_0 where b1_0.author_id=?
delete from book where id=?
delete from author where id=?

Two things to notice. Orphan removal has to load the collection before it can detect that something left it, so a removal is never free. And cascading REMOVE deletes the children one statement at a time, children first, which is why a parent with thousands of children is deleted with a bulk DELETE or @OnDelete instead (see Bulk Operations and Batching).

Unidirectional @OneToMany: two physical shapes

The text above mentions a unidirectional @OneToMany without mappedBy. It has two shapes with very different SQL, both verified:

// (a) with @JoinColumn: a foreign key in the child table
@OneToMany(cascade = CascadeType.ALL)
@JoinColumn(name = "shelf_id")
private List<Volume> volumes = new ArrayList<>();

// (b) without it: a join table
@OneToMany(cascade = CascadeType.ALL)
private List<Item> items = new ArrayList<>();
-- (a) one shelf with two volumes
insert into shelf (id) values (?)
insert into volume (title,id) values (?,?)
insert into volume (title,id) values (?,?)
update volume set shelf_id=? where id=?
update volume set shelf_id=? where id=?

-- (b) one crate with one item
insert into crate (id) values (?)
insert into item (label,id) values (?,?)
insert into crate_item (Crate_id,items_id) values (?,?)

Shape (a) writes each child row twice — an insert without the key, then an update that sets it — because the child entity has no attribute that could carry the key into the first insert. Shape (b) needs a whole extra table. A bidirectional pair with the @ManyToOne on the child (the model at the top of this page) inserts each child once, with its key.

@ManyToMany: why Set beats List

Two otherwise identical entities map the same many-to-many, one as List<Tag> and one as Set<Tag>, each holding three tags. Removing one tag produced:

-- List<Tag> (a bag)
delete from bag_book_tag where BagBook_id=?
insert into bag_book_tag (BagBook_id,tags_id) values (?,?)
insert into bag_book_tag (BagBook_id,tags_id) values (?,?)

-- Set<Tag>
delete from set_book_tag where SetBook_id=? and tags_id=?

The bag deleted every join row of the owner and re-inserted the two survivors; the set deleted exactly the one removed row. That is the "delete and re-insert the whole collection" cost described in Collections, seen here on a join table. It applies to the owning, join-table side; an inverse @OneToMany(mappedBy = ...) bag writes nothing for the collection at all, because the foreign key lives in the child table. Use a Set with a business-key equals() for any many-to-many.

Finally, em.getReference(Author.class, 1L) assigned to book.setAuthor(...) followed by persist issued a single insert into book (author_id,...) and no select for the author: the foreign key needs only the identifier, and the proxy supplies it.
