Events, Interceptors, and Filters

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Hibernate exposes several extension points for running code around persistence operations, from the standardized JPA callbacks up to Hibernate’s own lower-level event system.

JPA lifecycle callbacks and entity listeners

@Entity
@EntityListeners(AuditListener.class)
public class Book {
    @PrePersist
    void onPrePersist() {
        this.createdAt = Instant.now();
    }

    @PreUpdate
    void onPreUpdate() {
        this.updatedAt = Instant.now();
    }
}

public class AuditListener {
    @PostLoad
    void onLoad(Object entity) {
        // external listener -- entity does not need to know about it
    }
}

The full set: @PrePersist/@PostPersist, @PreUpdate/@PostUpdate, @PreRemove/@PostRemove, and @PostLoad. A callback method can live directly on the entity (self-callback, as onPrePersist above) or on a separate class named via @EntityListeners (external listener, as AuditListener above) — external listeners keep cross-cutting concerns (auditing, validation) out of the entity class itself. Compare with Spring Data’s own @CreatedDate/@LastModifiedDate auditing (Spring Data JPA), which is itself implemented as an @EntityListeners(AuditingEntityListener.class) on top of exactly this mechanism — reach for the Spring Data annotations directly rather than hand-rolling the same thing again in a Spring Boot application.

The Hibernate Interceptor

A single, session-wide (or SessionFactory-wide) hook that sees every entity operation, not just callbacks declared per-entity — useful for a cross-cutting concern that needs to touch every entity type uniformly without annotating each one:

public class AuditInterceptor implements Interceptor {
    @Override
    public boolean onFlushDirty(Object entity, Object id, Object[] currentState,
            Object[] previousState, String[] propertyNames, Type[] types) {
        // inspect/modify currentState before the UPDATE is generated
        return true; // state was modified -- tell Hibernate to use it
    }
}

// registered at bootstrap:
Session session = sessionFactory.withOptions().interceptor(new AuditInterceptor()).openSession();

Interceptor methods (onLoad, onPersist, onFlushDirty, onRemove, …​ — Hibernate 7 also keeps the older onSave/onDelete names) are called for every entity that passes through the session, in contrast to @EntityListeners, which is opted into per entity class.

The native event system: EventType, listeners, and Integrator

Beneath both of the above, every Hibernate operation is actually implemented as firing a typed event (EventType.PERSIST, EventType.LOAD, EventType.FLUSH_ENTITY, …​) to a chain of registered listeners — PrePersistEventListener, PreInsertEventListener, and so on for each event type. This is the lowest-level, most powerful extension point (it is literally how Hibernate implements its own default persistence behavior), and correspondingly the least commonly needed directly — reach for it only when neither JPA callbacks nor Interceptor can express what is needed (e.g. replacing, rather than just observing, part of the default insert/update algorithm for one specific event type).

An Integrator (org.hibernate.integrator.spi.Integrator, discovered via Java’s ServiceLoader) is how a library registers its own event listeners, type contributors, or other SPI hooks into Hibernate at bootstrap without the application needing to wire it manually — the mechanism third-party Hibernate extensions (Envers included, see Envers Auditing) use to attach themselves.

Dynamic data filters: @FilterDef/@Filter

A filter is a named, parameterized WHERE clause fragment that can be turned on or off per session, applied transparently to every query (and lazy-load) against the filtered entity/collection while active:

@Entity
@FilterDef(name = "activeOnly", parameters = @ParamDef(name = "isActive", type = Boolean.class))
@Filter(name = "activeOnly", condition = "active = :isActive")
public class Book {
    private boolean active;
}

// ...
session.enableFilter("activeOnly").setParameter("isActive", true);
List<Book> activeBooks = session.createQuery("FROM Book", Book.class).getResultList(); // filter applied automatically

Filters are per-session and off by default — forgetting to enable one is a silent no-op (the query just runs unfiltered), unlike a missing WHERE clause typo in HQL, which at least fails loudly if the syntax is wrong.

Soft delete with @SoftDelete

@SoftDelete (Hibernate 6.4+) marks an entity so a remove()/bulk-delete DELETE becomes, transparently, an UPDATE setting a deleted-marker column instead of removing the row, and every subsequent query against that entity automatically excludes soft-deleted rows — without hand-writing a filter or an active/deleted column check into every query:

@Entity
@SoftDelete(columnName = "deleted", strategy = SoftDeleteType.DELETED)
public class Book {
    // no explicit "deleted" field needed -- Hibernate manages the column directly
}

This differs from the @FilterDef/@Filter approach above in that soft-delete exclusion is always on (not an opt-in per-session toggle) and remove() itself changes meaning, rather than queries against an already-present boolean column being filtered.

Worked example: one Book through every hook

The experiment uses an entity with the same mapping as the section’s Book (a title, an active flag, createdAt/updatedAt timestamps and a lastModifiedBy column) carrying a self-callback pair (@PrePersist/@PreUpdate) and an external @EntityListeners class with @PostLoad, @PostPersist and @PostRemove. Alongside, a session-scoped Interceptor and an Integrator that registers native event listeners were active. Each line below is printed by the hook named in brackets, on Hibernate ORM 7.4.15.

JPA callbacks, in the order they fire

Persisting, then updating, then removing the book printed:

[callback] @PrePersist Callbacks
insert into ev_book (active,created_at,last_modified_by,title,updated_at,id) values (?,?,?,?,?,?)
[listener] @PostPersist Callbacks
-- new transaction: find and change the title
select ... from ev_book eb1_0 where eb1_0.id=?
[listener] @PostLoad Callbacks
[callback] @PreUpdate Callbacks v2
update ev_book set active=?,created_at=?,last_modified_by=?,title=?,updated_at=? where id=?
-- new transaction: find, no change
select ... from ev_book eb1_0 where eb1_0.id=?
[listener] @PostLoad Callbacks v2                       (no @PreUpdate, no UPDATE)
-- bulk HQL: update ev_book eb1_0 set title='bulk'     (no callback of any kind)
-- remove
delete from ev_book where id=?
[listener] @PostRemove bulk

Three behaviors to remember. @PrePersist runs when persist is called, before the insert is even scheduled; @PreUpdate runs only at flush and only if dirty checking found a change; and a bulk HQL statement fires no JPA callbacks and no entity listeners (it never materializes the rows as entities), so audit-style hooks silently miss bulk changes.

The Interceptor

With sessionFactory.withOptions().interceptor(new StampInterceptor()).openSession(), the interceptor saw onPersist before the insert and onFlushDirty when the title change was flushed, in the same flush as the @PreUpdate callback:

@Override
public boolean onFlushDirty(Object entity, Object id, Object[] currentState, Object[] previousState,
        String[] propertyNames, Type[] types) {
    if (entity instanceof Book) {
        for (int i = 0; i < propertyNames.length; i++) {
            if (propertyNames[i].equals("lastModifiedBy")) {
                currentState[i] = currentUser();     // written into the UPDATE statement
                return true;                         // tell Hibernate the state array changed
            }
        }
    }
    return false;
}

After the flush, book.getLastModifiedBy() returned the stamped value: modifying currentState and returning true changes both the SQL and the managed instance.

Native event listeners and the Integrator

An Integrator registered through META-INF/services/org.hibernate.integrator.spi.Integrator obtains the EventListenerRegistry from the SessionFactory and appends listeners per EventType:

public class AuditIntegrator implements Integrator {
    @Override
    public void integrate(Metadata metadata, BootstrapContext context, SessionFactoryImplementor sessionFactory) {
        EventListenerRegistry registry = sessionFactory.getServiceRegistry().getService(EventListenerRegistry.class);
        registry.prependListeners(EventType.PRE_INSERT, (PreInsertEventListener) event ->
                event.getEntity() instanceof Book book && book.getTitle().startsWith("FORBIDDEN")); // true = veto
        registry.appendListeners(EventType.POST_INSERT, new CountingPostInsertListener());
    }
}

A PreInsertEventListener returning true vetoes the SQL insert. In the run, persisting two books, one with a title starting with FORBIDDEN, executed a single insert; a later count of rows with that title returned 0. The veto does not undo the in-memory persist: @PostPersist and the POST_INSERT listener still ran for the vetoed book, and the instance stays managed with an id. A veto is therefore a data-integrity brake, not a validation mechanism — use Bean Validation or an exception for that.

Filters, measured

Three rows were stored (two with active = true, one false). With no filter enabled, from EvBook returned all of them; after session.enableFilter("activeOnly").setParameter("isActive", true) the same query returned 2 and its SQL gained the condition (where eb1_0.active = ?). Loading by key behaves differently:

@FilterDef(name = "activeOnly", defaultCondition = "active = :isActive",
           parameters = @ParamDef(name = "isActive", type = Boolean.class), applyToLoadByKey = true)
@Filter(name = "activeOnly")
public class Book { ... }

  • With the default applyToLoadByKey = false, session.find(FilteredNote.class, id) with the filter enabled still returned the inactive row, while a query counting rows returned 0.

  • With applyToLoadByKey = true, a find of the inactive id in a fresh session ran select ... where eb1_0.id=? and eb1_0.active = ? and returned null.

The first-level cache also bypasses filters: when the inactive row had already been loaded earlier in the same session (for example by an unfiltered query), find returned it from the persistence context without any SQL.

Soft delete, measured

@SoftDelete(columnName = "deleted", strategy = SoftDeleteType.DELETED) stores deleted = true for removed rows. The run printed:

insert into sd_book (title,deleted,id) values (?,false,?)
select sb1_0.id,sb1_0.title from sd_book sb1_0 where sb1_0.deleted=false and sb1_0.id=?
update sd_book set deleted=true where id=? and deleted=false          -- remove()
select count(*) from sd_book sb1_0 where sb1_0.deleted=false           -- HQL count: 1
update sd_book sb1_0 set deleted=true where sb1_0.title='Other' and sb1_0.deleted=false   -- bulk HQL delete

A native query sees the physical rows ([1, Soft, true] and [2, Other, false] before the bulk delete), and a find of the removed id returned null. Both remove() and a bulk delete from SdBook were rewritten to updates, and the bulk statement reported its row count normally.
