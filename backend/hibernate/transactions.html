Transactions

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Hibernate never commits or rolls back a database change on its own — every write is scoped to an explicit transaction. This page covers the two transaction models Hibernate supports natively and how a session’s lifetime is usually scoped to one.

Resource-local vs. JTA

  • Resource-local — the simplest model: one EntityManager/Session talks to exactly one DataSource/JDBC connection, and the transaction is demarcated directly against it (EntityTransaction/Hibernate’s Transaction). No transaction manager or application server involvement. The transaction-type="RESOURCE_LOCAL" attribute in persistence.xml selects this.

  • JTA — a container-managed, potentially distributed transaction spanning multiple resources (two databases, a database and a JMS queue) coordinated by a jakarta.transaction.UserTransaction/ TransactionManager. Hibernate participates by registering a synchronization with the JTA transaction rather than owning commit/rollback itself. transaction-type="JTA" selects this; it needs an application server or a standalone JTA provider (Narayana, Atomikos, Bitronix).

Spring Boot applications almost always use resource-local transactions under the hood (via DataSourceTransactionManager/JpaTransactionManager) even though the application code only ever sees @Transactional — see Spring Data JPA's @Transactional/propagation section for how Spring’s declarative model maps onto this.

The Hibernate transaction API

Resource-local, using the JPA EntityTransaction:

EntityManager em = emf.createEntityManager();
try {
    em.getTransaction().begin();

    Book book = em.find(Book.class, id);
    book.setTitle("New title");

    em.getTransaction().commit();
} catch (RuntimeException e) {
    if (em.getTransaction().isActive()) {
        em.getTransaction().rollback();
    }
    throw e;
} finally {
    em.close();
}

The native Hibernate API (session.beginTransaction() / Transaction.commit() / Transaction.rollback()) is functionally equivalent for resource-local use and additionally exposes Transaction.registerSynchronization(...) for hooking into the commit/rollback lifecycle without a full JTA setup.

Session-per-request and contextual sessions

The recommended session-scoping pattern — one Session/EntityManager per logical unit of work, typically one HTTP request or one message-processing invocation, opened at the start and closed at the end — rather than one long-lived session for the whole application or one per entity. A long-lived session accumulates managed entities indefinitely (unbounded first-level-cache growth, stale snapshots) and turns every stray lazy-load into a LazyInitializationException risk once the caller assumes it is still attached.

Hibernate can also expose a contextual current session (sessionFactory.getCurrentSession()) whose lifetime and scope is delegated to a pluggable CurrentSessionContext strategy configured via hibernate.current_session_context_class — thread (one session per thread, which must be configured explicitly — see below), jta (bound to the active JTA transaction), or a container-specific implementation. Frameworks (Spring) usually supply their own strategy rather than using this mechanism directly, since they already own request/transaction scoping.

Rollback and the persistence context

A transaction rollback does not revert the in-memory state of entity objects — the instances keep whatever values the application set, which were never committed. Current Hibernate versions do detach the entities on rollback (the persistence context is cleared, measured below), but the Java objects still hold the discarded values. JPA’s own rule of thumb applies: after a rollback, the EntityManager should be treated as unusable and discarded (a new one obtained) rather than reused, precisely because its in-memory entities no longer reliably reflect the database. EntityManager.clear() mitigates this for entity state, but the persistence context’s own internal bookkeeping is not guaranteed consistent afterward — discarding it is the robust choice, and is exactly what session-per-request scoping already does naturally.

The life of a transaction, observed

The program behind this page used the library example’s Book (with a unique isbn) on H2 and Hibernate ORM 7.4, and looked at what each way of ending a transaction leaves behind.

Rollback: what remains in memory

em.getTransaction().begin();
Book b = em.find(Book.class, id);
b.setTitle("Changed");
em.getTransaction().rollback();

b.getTitle();                 // "Changed"
em.contains(b);               // false
em.find(Book.class, id);      // a fresh select; title is "Original"

The output was title in memory after rollback: Changed, still contained: false, then find again returns: Original. Two things follow. The entity object keeps the uncommitted value — Hibernate does not reset it — but the rollback also detached it: the persistence context was cleared, so the next find read the committed row. The same experiment through a native Session gave contained: false too. A reference to an entity from before the rollback is therefore a detached object holding values that were never stored; discard it, and let the next unit of work load fresh state. The surviving Java objects are misleading, which is why a new EntityManager after a failure remains the robust rule.

A failed flush poisons the transaction

em.getTransaction().begin();
em.persist(new Book("1", "duplicate isbn"));        // isbn "1" already exists
try { em.flush(); } catch (PersistenceException e) { /* ConstraintViolationException */ }

em.getTransaction().isActive();        // true
em.getTransaction().getRollbackOnly(); // true
em.getTransaction().commit();          // RollbackException

The flush failed with ConstraintViolationException and the transaction stayed active but marked rollback-only: the program printed active=true rollbackOnly=true. Catching the exception and carrying on is a bug, because the commit can no longer succeed and, worse, the context no longer matches what the database accepted. Any PersistenceException other than NoResultException/NonUniqueResultException and a few others should be treated as the end of the unit of work.

stateDiagram-v2 [*] --> NOT_ACTIVE NOT_ACTIVE --> ACTIVE: begin ACTIVE --> COMMITTING: commit COMMITTING --> COMMITTED: success COMMITTING --> FAILED_COMMIT: flush or commit error ACTIVE --> MARKED_ROLLBACK: failed flush or setRollbackOnly MARKED_ROLLBACK --> ROLLING_BACK: rollback ACTIVE --> ROLLING_BACK: rollback ROLLING_BACK --> ROLLED_BACK: success COMMITTED --> [*] ROLLED_BACK --> [*]

The state names are those of Hibernate’s TransactionStatus, which Transaction.getStatus() returns; the program printed ACTIVE right after beginTransaction() and COMMITTED after commit().

The native Transaction API and its helpers

Transaction tx = session.beginTransaction();
tx.registerSynchronization(new Synchronization() {
    public void beforeCompletion() { System.out.println("beforeCompletion"); }
    public void afterCompletion(int status) { System.out.println("afterCompletion " + status); }
});
session.find(Book.class, id).setTitle("Via native API");
tx.commit();

registerSynchronization takes a jakarta.transaction.Synchronization; the callbacks ran in the order update statement, beforeCompletion, afterCompletion (status COMMITTED). beforeCompletion runs before the commit completes (in the run above, after the update had been flushed), which makes it the hook for last-moment checks, and afterCompletion is the place for cache eviction or notifications that must only happen if the commit succeeded.

For code that does not need that control, the SessionFactory helpers manage the whole lifecycle:

sf.inTransaction(s -> s.find(Book.class, id).setTitle("Via inTransaction"));      // commits

try {
    sf.inTransaction(s -> {
        s.find(Book.class, id).setTitle("will roll back");
        throw new IllegalStateException("boom");
    });
} catch (IllegalStateException e) { /* rolled back */ }

String title = sf.fromSession(s -> s.find(Book.class, id).getTitle());   // "Via inTransaction"

The title after the failed lambda was still Via inTransaction: the helper rolled back because the lambda threw, and rethrew the original exception unchanged.

getCurrentSession: what each configuration does

thread is not a default: with no hibernate.current_session_context_class on a plain Java SE factory, getCurrentSession() throws. The three cases observed:

hibernate.current_session_context_class Observed behavior

not set

HibernateException: No CurrentSessionContext configured.

thread

The second call returned the same session; after commit() the session had been closed automatically, so the next call in the thread would open a fresh one.

jta (no JTA platform on the classpath)

HibernateException: Could not obtain TransactionManager from JtaPlatform — the strategy needs a real JTA environment.

Inside a container with JTA, or under a framework that supplies its own session context, the strategy is chosen for you, which is why most applications never see this property. When running plain, either set thread explicitly or keep passing sessions around — or, simpler, use inTransaction as above.
