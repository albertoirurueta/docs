Flushing and Dirty Checking

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Nothing in Hibernate ever calls "save" on a managed entity’s field change — that is the point of automatic dirty checking. This page covers how it works, when it runs, and the two annotations that tune the SQL it generates.

Automatic dirty checking and the load-time snapshot

When an entity becomes managed (loaded by find, a query, or just-persisted), Hibernate takes a snapshot of its state at that moment. At flush time, every managed entity in the persistence context is compared against its snapshot, field by field; any entity with at least one changed field gets an UPDATE (by default naming every column, regardless of which fields actually changed — see @DynamicUpdate below to change that). No explicit update()/save() call is required or, for a managed entity, meaningful — mutating it with a plain setter is the entire API:

@Transactional
public void rename(Long bookId, String newTitle) {
    Book book = em.find(Book.class, bookId); // now managed, snapshot taken
    book.setTitle(newTitle);                 // no further call needed
}                                             // UPDATE issued at flush/commit

Flush modes

FlushModeType (JPA) / Hibernate’s own FlushMode control when the persistence context is synchronized to the database, independent of when the transaction commits:

Mode Behavior

AUTO (default)

Flushes automatically before a query whose results could plausibly be affected by pending changes in the context, and always before transaction commit.

COMMIT

Flushes only at transaction commit — skips the pre-query auto-flush. Faster when a query is known not to touch data the current transaction just modified, but risks the query returning stale results if that assumption is wrong.

ALWAYS

Flushes before every query unconditionally, even ones AUTO would judge unaffected — rarely needed, mainly a debugging aid.

MANUAL

No automatic flush at all — the application must call flush() explicitly. Suited to read-only units of work and to batch loops that flush on their own schedule (see Bulk Operations & Batching). A StatelessSession has no persistence context and therefore no flush mode at all.

Set per-Session/EntityManager via setFlushMode(...), or per-query via Query.setFlushMode(...).

Auto-flush before queries: what "affected" means

Under AUTO, Hibernate’s heuristic for "could this query be affected" is table-based, not row-based: if any pending change in the context touches a table the query’s FROM/JOIN clauses reference, the whole context is flushed first. This is deliberately conservative (it would rather flush unnecessarily than return a stale result) and is the reason interleaving writes and reads inside one transaction generally "just works" without manual flush calls — at the cost of losing some batching opportunity, since each such flush can break up what would otherwise be one batched round of INSERT/UPDATE statements.

Flush ordering

Within one flush, Hibernate groups pending SQL by statement type and orders them: INSERT statements first, then UPDATE statements, then collection removals, then DELETE statements — not the order operations were called in Java. This ordering exists to satisfy foreign-key constraints without requiring the application to sequence its own calls carefully, but it also means flush-time constraint violations can surface in an order that looks unrelated to the code that triggered them; reading the flush order is often the fastest way to make sense of such an error.

@DynamicUpdate and @DynamicInsert

By default, Hibernate’s UPDATE/INSERT statements include every mapped column, whether or not it actually changed (or has a non-null value) — this lets Hibernate use one prepared, cacheable SQL statement per entity type regardless of which fields changed on a given flush.

@Entity
@DynamicUpdate  // UPDATE only the columns that actually changed
@DynamicInsert  // INSERT only the columns with non-null values (let DB defaults apply to the rest)
public class Book { /* ... */ }

@DynamicUpdate trades a cacheable statement for a smaller UPDATE — worthwhile on wide entities where most flushes touch only one or two columns (reduces lock contention and write-ahead-log volume on those columns), and required for optimistic-locking configurations that only want to check/update the columns that actually changed (@OptimisticLocking(type = OptimisticLockType.DIRTY), see Locking). @DynamicInsert matters mainly when several columns have database-side DEFAULT expressions that should apply whenever the Java field is left null, rather than Hibernate explicitly inserting NULL and overriding the default.

Dirty checking, observed

The library example’s Book has an isbn, a title, a summary and a price. Loading it and changing only the title, then committing, issued (Hibernate ORM 7.4 on H2, SQL printed as issued):

select b1_0.id,b1_0.isbn,b1_0.price,b1_0.summary,b1_0.title from book b1_0 where b1_0.id=?
update book set isbn=?,price=?,summary=?,title=? where id=?

So the default UPDATE lists every mapped column even though only one changed. Assigning a field its own current value (b.title = b.title) issued no UPDATE at all: dirty checking compares values, not assignments. On the @DynamicUpdate twin, SlimBook, the same one-column edit produced

update slim_book set title=? where id=?

Auto-flush in action

Under FlushModeType.AUTO the pending title change was flushed only when a query touched book. With a dirty Book in the context, the sequence was:

-- query on Author (a different table)
select a1_0.id,a1_0.name from author a1_0
-- query on Book
update book set isbn=?,price=?,summary=?,title=? where id=?
select b1_0.id,b1_0.isbn,b1_0.price,b1_0.summary,b1_0.title from book b1_0 where b1_0.title='pending'

The query on Author ran straight away; the query on Book was preceded by the update, so it could see the change. Setting FlushModeType.COMMIT on the same scenario changed the outcome: the query for title = 'pending' found 0 rows, because the pending change had not been written — the stale read that the mode’s description warns about.

Native SQL is where the two APIs differ, and the difference is easy to trip over:

  • Through an EntityManager obtained from a persistence.xml or HibernatePersistenceConfiguration factory, createNativeQuery("select count(*) from author") flushed the pending Book update first, because in Jakarta Persistence mode Hibernate cannot know which tables a native statement touches and flushes everything.

  • Through a Session from a factory bootstrapped with Configuration, the same native query ran without a flush. Declaring the affected table with addSynchronizedEntityClass(Book.class) (or addSynchronizedQuerySpace(...)) made Hibernate flush before running it.

A native query that reads data written earlier in the same transaction should therefore always declare its query space when it is used through the native API.

Flush order, and a unique-constraint trap

The flush order described above matters in one very common case: replacing a row that has a unique constraint. Book.isbn is unique; the test removed the existing book and persisted a new one with the same isbn in one transaction:

em.getTransaction().begin();
em.remove(em.find(Book.class, id));
em.persist(new Book("111", "replacement"));    // same isbn
em.getTransaction().commit();                  // fails

The SQL issued was the insert first, which violated the unique index (H2 reported a unique index or primary key violation on ISBN) and surfaced as a RollbackException from commit; the delete never ran, because inserts are executed before deletes. Calling em.flush() between the two statements produced delete, then insert, and the commit succeeded:

em.remove(em.find(Book.class, id));
em.flush();                                    // delete now
em.persist(new Book("111", "replacement"));

The other flush-related modes, verified

FlushMode.MANUAL on a Session (via session.setHibernateFlushMode(FlushMode.MANUAL)) let a changed Book commit with no UPDATE at all; the change was silently dropped unless flush() was called. It suits read-only units of work, where an accidental setter call must not become a write.

@DynamicInsert omitted a null column from the INSERT, so the database default applied: insert into slim_book (title,id) values (?,?) stored status = 'DRAFT' from the column’s default 'DRAFT', while the in-memory entity still had status == null until it was refreshed. That mismatch is the price of letting the database fill a value in.
