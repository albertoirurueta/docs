Multitenancy

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A multitenant application serves multiple isolated customers ("tenants") from one deployment. Hibernate supports three isolation strategies, each trading isolation strength against operational complexity.

Three approaches

Strategy Behavior

Separate database

Each tenant gets a fully separate database (its own connection, credentials, and physical storage). Strongest isolation — one tenant’s data is not even reachable from another tenant’s connection — at the highest operational cost (schema migrations, backups, and connection-pool management multiply per tenant).

Separate schema

One database, one schema per tenant, selected by switching the JDBC connection’s schema/search-path per request. Strong logical isolation with shared infrastructure (one database instance, one connection pool to size); a compromise between the other two.

Discriminator column

One database, one schema, one set of tables shared by every tenant, with a tenant_id column on every multitenant-aware row and an implicit WHERE tenant_id = ? applied to every query. Cheapest operationally (one schema to migrate, one connection pool), weakest isolation (a bug that omits the tenant filter leaks data across tenants at the query level, not the infrastructure level).

CurrentTenantIdentifierResolver and MultiTenantConnectionProvider

Two SPIs Hibernate needs regardless of strategy:

public class RequestTenantResolver implements CurrentTenantIdentifierResolver<String> {
    @Override
    public String resolveCurrentTenantIdentifier() {
        return TenantContext.getCurrentTenant(); // e.g. from a request header or JWT claim
    }

    @Override
    public boolean validateExistingCurrentSessions() {
        return true;
    }
}

CurrentTenantIdentifierResolver answers "which tenant is this unit of work for" — consulted whenever Hibernate needs a tenant identifier and none was supplied explicitly. MultiTenantConnectionProvider answers "given a tenant identifier, how do I get the right JDBC connection" — for the separate-database strategy, it routes to a different DataSource per tenant; for separate-schema, it switches schema/search-path on a shared connection pool’s connection before handing it out. The discriminator-column strategy needs neither of the connection-routing pieces — both strategies still need CurrentTenantIdentifierResolver to know which tenant’s filter to apply.

@TenantId

For the discriminator-column strategy, @TenantId marks the entity field Hibernate should automatically filter every query by, using the value CurrentTenantIdentifierResolver supplies — no manual WHERE tenant_id = :t needed in application-written HQL/Criteria queries:

@Entity
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @TenantId
    private String tenantId;

    // every query against Order is automatically scoped to the current tenant
}

@TenantId is conceptually similar to a @Filter, except it is always active for the resolved tenant (not manually enabled per session) and is specifically designed around the tenant-resolution SPI above rather than an arbitrary session parameter.

Second-level-cache considerations

A shared second-level cache (see Second-Level Cache) must be tenant-aware for the separate-database and separate-schema strategies — the same entity class/id pair means a different row per tenant, so cache keys need the tenant identifier folded in; Hibernate does this automatically when multitenancy is configured. For the discriminator-column strategy, caching is naturally per-row already (the tenant_id is part of the row’s own data), but a cache region shared across tenants means one very active tenant’s cache churn can evict entries a quieter tenant would otherwise have kept hot — worth monitoring per Performance & Statistics's cache hit-rate statistics.

Spring Boot wiring note

Spring Boot has no built-in multitenancy auto-configuration; wiring CurrentTenantIdentifierResolver and (for separate-database/schema) MultiTenantConnectionProvider as Spring @Beans, and resolving the current tenant from a request-scoped context (a servlet filter populating a ThreadLocal, or a header/JWT claim read per request), is application code. hibernate.tenant_identifier_resolver and hibernate.multi_tenant_connection_provider (both accept a class name or an instance) are set via spring.jpa.properties.hibernate.*. No separate "enable multitenancy" flag is needed: in the runs below only those two properties were set, and Hibernate 7.4.15 derived the strategy from the mapping (@TenantId) or from the presence of a connection provider.

The three strategies compared

Worked example: the same Book under all three strategies

The three runs below use a minimal Book-shaped entity (id, title, and for the discriminator strategy a @TenantId String tenantId) and two tenants, acme and globex, on Hibernate ORM 7.4.15 with H2. The tenant comes from a ThreadLocal read by this resolver:

public class Resolver implements CurrentTenantIdentifierResolver<String> {
    @Override public String resolveCurrentTenantIdentifier() {
        String tenant = TenantContext.get();
        return tenant == null ? "unknown" : tenant;    // fail loudly here in real code
    }
    @Override public boolean validateExistingCurrentSessions() { return true; }
}

Discriminator column

Only the resolver is registered (hibernate.tenant_identifier_resolver). Inserting three books (two as acme, one as globex) wrote the tenant into every row (insert into tenant_book (tenant_id,title,id) values (?,?,?)), and each tenant then saw only its own rows, because every statement carries the predicate:

select tb1_0.title from tenant_book tb1_0 where tb1_0.tenant_id = ? order by tb1_0.id
-- acme sees:   [Acme secret plan, Acme handbook]
-- globex sees: [Globex handbook]

Loading by key is scoped too: as globex, find(TenantBook.class, 1L) — an id that belongs to acme — ran ... where tb1_0.id=? and tb1_0.tenant_id = ? and returned null. A native query is not scoped: the raw select id, tenant_id, title from tenant_book returned all three rows with their tenant ids (acme, acme, globex), which is the data-leak risk of this strategy in one line. Two more observations: the id sequence is shared by every tenant (ids were 1, 2 and 52), so gaps and interleaving between tenants are normal, and a session can be pinned to a tenant explicitly with sessionFactory.withOptions().tenantIdentifier("acme").openSession(), which takes precedence over the resolver (the count for that session was 2).

Separate schema

One H2 database with a acme and a globex schema, each holding a tenant_book table and its sequence. The MultiTenantConnectionProvider switches the schema when Hibernate asks for a tenant’s connection and resets it on release:

public class SchemaProvider implements MultiTenantConnectionProvider<String> {
    @Override public Connection getConnection(String tenant) throws SQLException {
        Connection connection = dataSource.getConnection();
        connection.createStatement().execute("SET SCHEMA " + tenant);   // use a whitelist, never raw input
        return connection;
    }
    @Override public void releaseConnection(String tenant, Connection connection) throws SQLException {
        connection.createStatement().execute("SET SCHEMA PUBLIC");
        connection.close();
    }
    @Override public Connection getAnyConnection() throws SQLException { return dataSource.getConnection(); }
    @Override public void releaseAnyConnection(Connection connection) throws SQLException { connection.close(); }
    @Override public boolean supportsAggressiveRelease() { return false; }
    @Override public boolean isUnwrappableAs(Class<?> type) { return false; }
    @Override public <T> T unwrap(Class<T> type) { return null; }
}

The entity carries no tenant column and the SQL carries no tenant predicate (select tbp1_0.title from tenant_book tbp1_0); isolation comes from the connection. The runs returned acme sees: [in schema acme] and globex sees: [in schema globex 1, in schema globex 2]. The tables were created by hand per schema: with a multitenant connection provider there is no single schema for hbm2ddl to target, so schema creation for tenants belongs to provisioning (see Schema Generation and Tooling and the migration tools it points to).

Separate database

The provider chooses a JDBC URL (or a DataSource) per tenant, and releases the connection with a plain close; no schema switch is needed. Each tenant database holds its own copy of the table, and the same Book queries returned acme sees: [in database acme] and globex sees: [in database globex].

Choosing, from the measurements

  • A native or JDBC statement is the weak point of the discriminator strategy: it bypasses @TenantId entirely. Route native SQL through a repository that adds the tenant predicate explicitly, and consider database row-level security as a second line of defense.

  • The schema and database strategies isolate native SQL too, at the cost of provisioning and migrating every tenant, and of one connection pool per database in the database strategy.

  • All three strategies need the tenant identifier to be resolved before the session opens; a ThreadLocal that is cleared too early or never set (the resolver above returns "unknown") silently queries a tenant that does not exist (an empty result for the discriminator strategy), so fail loudly at the edge of the application instead.
