Spring Batch Integration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

spring-batch-integration connects batch jobs to messaging. It covers three distinct needs: starting a job because a message arrived, overlapping slow processing with reading, and distributing work across JVMs.

Launching a job from a message

A file lands on a share, an event arrives on a queue — and a job should start. JobLaunchRequest packages a Job and its JobParameters as a message payload; JobLaunchingMessageHandler (or the JobLaunchingGateway wrapper) executes it.

The usual shape is a transformer that turns the inbound payload into a request, then the gateway:

@Component
public class FileToJobLaunchRequestTransformer {

    private final Job importJob;

    public FileToJobLaunchRequestTransformer(Job importJob) {
        this.importJob = importJob;
    }

    @Transformer(inputChannel = "incomingFiles", outputChannel = "jobRequests")
    public JobLaunchRequest toRequest(Message<File> message) {
        File file = message.getPayload();
        JobParameters parameters = new JobParametersBuilder()
                .addString("input.file", file.getAbsolutePath())
                .addLocalDateTime("arrival.time", LocalDateTime.now())
                .toJobParameters();
        return new JobLaunchRequest(importJob, parameters);
    }
}
@Configuration
public class JobLaunchingFlowConfiguration {

    @Bean
    @ServiceActivator(inputChannel = "jobRequests")
    public JobLaunchingGateway jobLaunchingGateway(JobOperator jobOperator) {
        JobLaunchingGateway gateway = new JobLaunchingGateway(jobOperator);
        gateway.setOutputChannelName("jobExecutions");   // not allowed as an attribute of @ServiceActivator on a @Bean handler
        return gateway;
    }

    @Bean
    public IntegrationFlow incomingFileFlow() {
        return IntegrationFlow
                .from(Files.inboundAdapter(new File("/data/in"))
                                .patternFilter("trades-*.csv"),
                        poller -> poller.poller(Pollers.fixedDelay(Duration.ofSeconds(10))))
                .channel("incomingFiles")
                .get();
    }
}

The gateway’s reply is the resulting JobExecution, so a downstream endpoint can report on the outcome — informational feedback without polling the repository:

@ServiceActivator(inputChannel = "jobExecutions")
public void report(JobExecution execution) {
    log.info("{} #{} finished as {}",
            execution.getJobInstance().getJobName(),
            execution.getId(),
            execution.getStatus());
    if (execution.getStatus() == BatchStatus.FAILED) {
        alertService.raise(execution);
    }
}

Whether the gateway blocks depends on the TaskExecutor of the JobOperator — synchronous means the reply carries a finished execution, asynchronous means it carries one that has only just started. See Running a job.

The outputChannel of a @ServiceActivator cannot be combined with a @Bean that already is a MessageHandler: Spring Integration rejects it at startup with "can not be populated because of ambiguity with annotation attributes", and the output channel has to be set on the handler itself, as above.

Worked example: a file arrives

With the three pieces above (inbound adapter, transformer, gateway) and an importTradesJob that reads #{jobParameters['input.file']} with a FlatFileItemReader and writes the settled trades, a partner system drops trades-eod.csv (three trades) into the inbox. The application prints:

dropped trades-eod.csv
importTradesJob #1 finished as COMPLETED (trades-eod.csv) on thread scheduling-1
  step importTradesStep read=3 write=3

The reply was handled on scheduling-1, the poller’s thread: Spring Boot’s JobOperator runs jobs synchronously, so the poller was blocked until the job finished and the reply carried a completed execution. On Spring Batch 6.0.6 that is a reasonable default (one file at a time, no overlap), but a long import will hold the poller; give the operator a TaskExecutor and the reply becomes a STARTED execution. Write the file elsewhere and rename it into the inbox, as the example does: the patternFilter matches by name, so a file that is still being written would otherwise be picked up half-written.

sequenceDiagram participant P as Partner system participant F as Files.inboundAdapter participant T as Transformer participant G as JobLaunchingGateway participant J as importTradesJob participant R as Reporter P->>F: rename trades-eod.csv into the inbox F->>T: Message of File on incomingFiles T->>G: JobLaunchRequest on jobRequests (input.file, arrival.time) G->>J: JobOperator.start(job, parameters) J-->>G: JobExecution G->>R: JobExecution on jobExecutions

Because arrival.time is an identifying parameter, a re-delivery of the same file creates a new job instance. If a file must be processed at most once, make the file name or a checksum the only identifying parameter and let the second launch fail with "already complete" — see Jobs, instances & parameters.

Asynchronous processing inside a step

AsyncItemProcessor submits each process() call to a TaskExecutor and returns a Future; AsyncItemWriter collects the futures and passes the resolved items to its delegate. Together they overlap a slow, I/O-bound processor with reading and writing:

@Bean
public AsyncItemProcessor<Trade, EnrichedTrade> asyncEnrichingProcessor(
        ItemProcessor<Trade, EnrichedTrade> delegate, TaskExecutor taskExecutor) {
    AsyncItemProcessor<Trade, EnrichedTrade> processor = new AsyncItemProcessor<>(delegate);   // slow pricing service
    processor.setTaskExecutor(taskExecutor);
    return processor;
}

@Bean
public AsyncItemWriter<EnrichedTrade> asyncEnrichedWriter(ItemWriter<EnrichedTrade> delegate) {
    return new AsyncItemWriter<>(delegate);
}

The step’s output type becomes Future<EnrichedTrade>, as shown in Scaling & parallel processing. The delegate processor must be thread-safe, and it still must be idempotent (ItemProcessors).

SEDA-style stage decoupling

BlockingQueueItemWriter and BlockingQueueItemReader let one step’s output become another step’s input through an in-memory queue, so producer and consumer run concurrently at their own paces — the staged event-driven architecture idea applied to a job:

@Bean
public BlockingQueue<Trade> stagingQueue() {
    return new LinkedBlockingQueue<>(10_000);   // bounded: back-pressure on the producer
}

@Bean
public BlockingQueueItemWriter<Trade> queueWriter(BlockingQueue<Trade> stagingQueue) {
    return new BlockingQueueItemWriter<>(stagingQueue);
}

@Bean
public BlockingQueueItemReader<Trade> queueReader(BlockingQueue<Trade> stagingQueue) {
    BlockingQueueItemReader<Trade> reader = new BlockingQueueItemReader<>(stagingQueue);
    reader.setTimeout(5, TimeUnit.SECONDS);   // how long to wait before deciding the queue is exhausted
    return reader;
}

Bound the queue: an unbounded one turns a fast producer into an out-of-memory error. And note the trade-off — items in the queue are in memory only, so a crash loses them; the two stages are not restartable as one.

The reader and the writer do nothing until two steps run at the same time, and sequential steps would just fill the queue and then drain it. The concurrency comes from a split flow:

Step produce = new StepBuilder("produceStep", jobRepository)
        .<Trade, Trade>chunk(50, tx)
        .reader(tradeReader)
        .writer(new BlockingQueueItemWriter<>(stagingQueue))
        .build();

Step consume = new StepBuilder("consumeStep", jobRepository)
        .<Trade, SettledTrade>chunk(50, tx)
        .reader(queueReader)               // BlockingQueueItemReader with a 500 ms timeout
        .processor(settlementProcessor)
        .writer(settlementWriter)
        .build();

Flow producerFlow = new FlowBuilder<Flow>("producerFlow").start(produce).build();
Flow consumerFlow = new FlowBuilder<Flow>("consumerFlow").start(consume).build();

return new JobBuilder("sedaJob", jobRepository)
        .start(producerFlow)
        .split(new SimpleAsyncTaskExecutor("seda-"))
        .add(consumerFlow)
        .end()
        .build();
flowchart LR DB[("trade table")] --> PS["produceStep"] PS -->|"BlockingQueueItemWriter.put"| Q["LinkedBlockingQueue, capacity 100"] Q -->|"BlockingQueueItemReader.poll with timeout"| CS["consumeStep"] CS --> OUT[("settled_trade table")]

BlockingQueueItemWriter calls put, which blocks when the queue is full: that is the back-pressure, and it makes the producer run at the consumer’s pace. BlockingQueueItemReader calls poll(timeout), and a null ends its step, so the timeout is both the shutdown signal and the longest producer stall it tolerates. Run on the settlement example with a 3 ms consumer, both steps start in the same millisecond, the producer finishes about 3.7 s later, and all 1000 trades are written (the full output is on Scaling & parallel processing). The caveat of the design is also visible there: a producer failure leaves the consumer waiting for its timeout, and a restart reruns both steps against an empty queue.

Remote chunking

The manager reads and dispatches; workers process and write. On the manager, the writer is a ChunkMessageChannelItemWriter that sends the chunk to a request channel and correlates the reply. The Amqp.outboundAdapter/Amqp.inboundAdapter wiring below rides on the same spring-boot-starter-amqp and ConnectionFactory covered in Spring Boot: RabbitMQ (add spring-integration-amqp for the adapters).

Both this section and the remote-partitioning one below rely on @EnableBatchIntegration: it is what registers RemoteChunkingManagerStepBuilderFactory, RemotePartitioningManagerStepBuilderFactory and RemotePartitioningWorkerStepBuilderFactory as beans, so without it these configurations fail to autowire. These builder factories belong to spring-batch-integration and are distinct from the core JobBuilderFactory/StepBuilderFactory that Getting started lists as removed — the factory.get("name") idiom below is the current one for remote steps.

sequenceDiagram participant M as Manager JVM (managerStep) participant Q1 as Queue batch.chunk.requests participant W as Worker JVM (processor and writer) participant Q2 as Queue batch.chunk.replies M->>M: read 50 trades (one chunk) M->>Q1: ChunkRequest (items, job instance id, step contribution) Q1->>W: deliver to one of the workers W->>W: process each trade, write the chunk W->>Q2: ChunkResponse (write count, success flag) Q2->>M: reply correlates with the request M->>M: apply the contribution, read the next chunk

The manager side, with the two queues declared so the broker creates them:

@Configuration
@EnableBatchIntegration          // registers the remote step builder factories
@Profile("manager")
public class RemoteChunkingManagerConfiguration {

    @Bean
    public Queue chunkRequestsQueue() { return new Queue("batch.chunk.requests", true); }

    @Bean
    public Queue chunkRepliesQueue() { return new Queue("batch.chunk.replies", true); }

    @Bean
    public DirectChannel chunkRequests() { return new DirectChannel(); }

    @Bean
    public QueueChannel chunkReplies() { return new QueueChannel(); }

    /** Java serialization is allow-listed by Spring AMQP: only these packages may be deserialized. */
    @Bean
    public SimpleMessageConverter allowListConverter() {
        SimpleMessageConverter converter = new SimpleMessageConverter();
        converter.setAllowedListPatterns(List.of("org.springframework.batch.*", "com.example.trades.*", "java.*"));
        return converter;
    }

    @Bean
    public IntegrationFlow outboundChunks(ConnectionFactory connectionFactory) {
        return IntegrationFlow.from(chunkRequests())
                .handle(Amqp.outboundAdapter(new RabbitTemplate(connectionFactory))
                        .routingKey("batch.chunk.requests"))
                .get();
    }

    @Bean
    public IntegrationFlow inboundReplies(ConnectionFactory connectionFactory,
                                          SimpleMessageConverter allowListConverter) {
        return IntegrationFlow
                .from(Amqp.inboundAdapter(connectionFactory, "batch.chunk.replies")
                        .messageConverter(allowListConverter))
                .channel(chunkReplies())
                .get();
    }

    @Bean
    public Step managerStep(RemoteChunkingManagerStepBuilderFactory managerStepBuilderFactory,
                            ItemReader<Trade> reader) {
        return managerStepBuilderFactory.get("managerStep")
                .<Trade, Trade>chunk(50)
                .reader(reader)
                .outputChannel(chunkRequests())
                .inputChannel(chunkReplies())
                .build();
    }
}

On the worker, a RemoteChunkingWorkerBuilder builds the IntegrationFlow that applies the processor and writer and replies. It needs the mirror image of the manager’s plumbing — an inbound adapter for the requests, an outbound adapter for the replies, and the same allow-list converter:

@Configuration
@EnableBatchIntegration
@Profile("worker")
public class RemoteChunkingWorkerConfiguration {

    @Bean
    public DirectChannel workerRequests() { return new DirectChannel(); }

    @Bean
    public DirectChannel workerReplies() { return new DirectChannel(); }

    @Bean
    public IntegrationFlow inboundRequests(ConnectionFactory connectionFactory,
                                           SimpleMessageConverter allowListConverter) {
        return IntegrationFlow
                .from(Amqp.inboundAdapter(connectionFactory, "batch.chunk.requests")
                        .messageConverter(allowListConverter))
                .channel(workerRequests())
                .get();
    }

    @Bean
    public IntegrationFlow outboundReplies(ConnectionFactory connectionFactory) {
        return IntegrationFlow.from(workerReplies())
                .handle(Amqp.outboundAdapter(new RabbitTemplate(connectionFactory))
                        .routingKey("batch.chunk.replies"))
                .get();
    }

    @Bean
    public IntegrationFlow workerFlow(ItemProcessor<Trade, SettledTrade> processor,
                                      ItemWriter<SettledTrade> writer) {
        return new RemoteChunkingWorkerBuilder<Trade, SettledTrade>()
                .itemProcessor(processor)
                .itemWriter(writer)
                .inputChannel(workerRequests())
                .outputChannel(workerReplies())
                .build();
    }
}

Requirements worth repeating: the middleware must be durable and transactional, and items must be serialisable. The topology and its trade-offs are pictured in Scaling & parallel processing.

The allow-list is not optional. The default message converter uses Java serialization, and Spring AMQP refuses to deserialize a class it has not been told to trust. Without the converter above, every worker fails each message with SecurityException: Attempt to deserialize unauthorized class org.springframework.batch.integration.chunk.ChunkRequest (the rejected messages go back to the queue, and the manager waits for replies that never come). List the Spring Batch package, the package of the item classes and java.*, or switch to a JSON converter and make the items JSON-friendly. The same applies to the manager’s reply listener.

The pattern was run for the settlement example with two worker JVMs on a shared PostgreSQL database (the workers need the business table, not the batch metadata) and RabbitMQ 4: the manager reported COMPLETED, read 1000 trades in 21 transactions, and the writes were split 500 and 500 between worker-1 and worker-2. If a manager is killed during a run, queued chunks stay on the broker — purge the queues before a fresh run, and recover the stranded STARTED execution (see Cloud-native batch).

Remote partitioning

Remote partitioning sends step execution requests, not chunks — each worker reads its own slice. The manager builds the partitions, persists a StepExecution for each, and sends one request per partition; a worker step executes the request against the shared JobRepository. There are two ways for the manager to learn that a partition finished: a reply channel, or polling the repository. The polling form needs no reply queue:

@Configuration
@EnableBatchIntegration
@Profile("manager")
public class RemotePartitioningManagerConfiguration {

    @Bean
    public Queue partitionRequestsQueue() { return new Queue("batch.partition.requests", true); }

    @Bean
    public DirectChannel partitionRequests() { return new DirectChannel(); }

    @Bean
    public IntegrationFlow outboundPartitions(ConnectionFactory connectionFactory) {
        return IntegrationFlow.from(partitionRequests())
                .handle(Amqp.outboundAdapter(new RabbitTemplate(connectionFactory))
                        .routingKey("batch.partition.requests"))
                .get();
    }

    @Bean
    public Step remotePartitionedStep(RemotePartitioningManagerStepBuilderFactory factory,
                                      Partitioner tradeIdRangePartitioner) {
        return factory.get("remotePartitionedStep")
                .partitioner("workerStep", tradeIdRangePartitioner)
                .gridSize(4)
                .outputChannel(partitionRequests())
                .pollInterval(500)              // poll the repository; or .inputChannel(replies) for a reply channel
                .build();
    }
}

The worker declares a step named in the manager’s partitioner(...) call and binds it to the inbound channel:

@Configuration
@EnableBatchIntegration
@Profile("worker")
public class RemotePartitioningWorkerConfiguration {

    @Bean
    public DirectChannel workerRequests() { return new DirectChannel(); }

    @Bean
    public IntegrationFlow inboundPartitions(ConnectionFactory connectionFactory,
                                             SimpleMessageConverter allowListConverter) {
        return IntegrationFlow
                .from(Amqp.inboundAdapter(connectionFactory, "batch.partition.requests")
                        .messageConverter(allowListConverter))
                .channel(workerRequests())
                .get();
    }

    @Bean
    public Step workerStep(RemotePartitioningWorkerStepBuilderFactory workerStepBuilderFactory,
                           JdbcPagingItemReader<Trade> partitionedReader,    // @StepScope, bound to its slice
                           ItemProcessor<Trade, SettledTrade> processor,
                           ItemWriter<SettledTrade> writer) {
        return workerStepBuilderFactory.get("workerStep")
                .inputChannel(workerRequests())
                .<Trade, SettledTrade>chunk(50)
                .reader(partitionedReader)
                .processor(processor)
                .writer(writer)
                .build();
    }
}
sequenceDiagram participant M as Manager (remotePartitionedStep) participant R as Shared JobRepository participant Q as Queue batch.partition.requests participant W as Worker JVMs (workerStep) M->>R: create four StepExecutions, partition0 to partition3 M->>Q: four StepExecutionRequest messages Q->>W: each request goes to one worker W->>R: load the StepExecution, run the step, update counters loop every pollInterval M->>R: are all partition executions finished? end M->>R: aggregate counters, complete the manager step

Because each partition is a real, persisted StepExecution, remote partitioning keeps normal restart semantics: only the partitions that failed are rerun. Both JVMs need the metadata database (the manager creates the executions, the workers update them) as well as the business database. In the run for this page, two worker JVMs shared a PostgreSQL repository with the manager; the manager step finished COMPLETED with 1000 trades read and written, split 500 and 500 between the workers, and the repository held four workerStep:partitionN executions with 250 items each (the rows are on Scaling & parallel processing). The manager’s in-memory JobExecution is not updated by the workers: read partition status from the repository.

Writers that publish to a channel, a JMS destination or an SMTP server also live here, which is where the messaging and mail destinations mentioned in ItemWriters: databases & alternative destinations come from.

Choosing between the integration features

Need Feature

Start a job because a file or event arrived

JobLaunchRequest plus JobLaunchingGateway

Overlap a slow remote call with reading and writing, one JVM

AsyncItemProcessor and AsyncItemWriter

Overlap two stages at different speeds, one JVM, no durability

BlockingQueueItemWriter/Reader in a split flow

Reading is cheap, processing and writing are heavy, durable broker available

Remote chunking

Input splits by key, workers can reach the data

Remote partitioning (restartable per partition)
