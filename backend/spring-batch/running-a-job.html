Running a job

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Spring Batch runs a job; it does not decide when. This page covers the launching API, the ways Spring Boot triggers it, and how to wire a job to an endpoint, a scheduler or a queue.

JobOperator is the launching interface

In 6.0 JobOperator extends JobLauncher, so one interface both launches and controls:

Method What it does

start(job, parameters)

Runs the given Job with these parameters; fails if the resulting instance already completed, and restarts the instance if its last execution failed or was stopped. If the job defines a JobParametersIncrementer the parameters are ignored and the next instance is started instead.

startNextInstance(job)

Applies the job’s JobParametersIncrementer and starts the next instance.

restart(jobExecution)

Creates a new JobExecution for the instance of a FAILED/STOPPED execution, resuming after the last completed step.

stop(jobExecution)

Requests a graceful stop; the execution moves to STOPPING and then STOPPED at the next checkpoint.

abandon(jobExecution)

Marks a stopped or crashed execution ABANDONED so it is skipped by restart logic.

recover(jobExecution)

(6.0) Cleans up executions stranded in STARTED/STOPPING after a crash — see Stopping, restart & recovery.

Each of these takes a domain object. The older overloads that took a job name or an execution id (startNextInstance(String), restart(long), stop(long), abandon(long)) are deprecated for removal in 6.0; fetch the JobExecution from the JobRepository first and pass the object.

TaskExecutorJobOperator is the standard implementation, and its TaskExecutor decides the launching semantics. It has no setTransactionManager; the supported way to assemble it with a transactional proxy is JobOperatorFactoryBean:

@Bean
public JobOperator jobOperator(JobRepository jobRepository, JobRegistry jobRegistry,
                               PlatformTransactionManager transactionManager) throws Exception {
    JobOperatorFactoryBean factory = new JobOperatorFactoryBean();
    factory.setJobRepository(jobRepository);
    factory.setJobRegistry(jobRegistry);
    factory.setTransactionManager(transactionManager);
    // synchronous by default (SyncTaskExecutor): start() returns when the job ends
    factory.setTaskExecutor(new SimpleAsyncTaskExecutor("batch-"));   // asynchronous
    factory.afterPropertiesSet();
    return factory.getObject();
}

  • Synchronous (the default SyncTaskExecutor): start() blocks and returns a finished JobExecution. Right for a command-line process whose exit code should reflect the outcome.

  • Asynchronous (any real TaskExecutor): start() returns as soon as the execution is created, typically in STARTING. Right for an HTTP endpoint, which must not hold a request thread for an hour. The caller gets an execution id and polls the repository for progress. A second start for an instance whose execution is still running throws JobExecutionAlreadyRunningException.

Under Spring Boot, do not build the operator by hand to get asynchronous launching: declare a TaskExecutor bean annotated @BatchTaskExecutor and Boot’s auto-configured operator uses it (see Infrastructure configuration).

Spring Boot: running at startup

Spring Boot registers a JobLauncherApplicationRunner that runs jobs after the context is ready. Two properties control it:

spring:
  batch:
    job:
      enabled: true          # false => never run a job at startup
      name: endOfDayJob      # which job bean to run

Command-line arguments become JobParameters; non-option arguments in key=value form are converted by the DefaultJobParametersConverter; without a type suffix a value is a String, which is why the date below carries its type. The full form of an argument is name=value,type,identifying: a trailing ,java.lang.Long pins the type, and a third element false makes the parameter non-identifying. A launch with run.date=2026-01-30,java.time.LocalDate, input.file=data/in/trades-2026-01-30.csv,java.lang.String,false and dry.run=true,java.lang.Boolean,false stored a LocalDate identifying parameter and two non-identifying ones, and a repeat of the same command was refused as already complete. A complete command line looks like this:

java -jar batch-app.jar \
     --spring.batch.job.name=endOfDayJob \
     run.date=2026-01-31,java.time.LocalDate \
     chunk.size=500,java.lang.Long \
     output.dir=/data/out

The process exits when the runner finishes. To make the exit code reflect the job outcome, add Boot’s ExitCodeGenerator support. With it, a job that failed ended the process with exit code 5, a launch that restarted it successfully with 0, and a launch that was refused (JobInstanceAlreadyCompleteException) with 1:

@SpringBootApplication
public class BatchApplication {
    public static void main(String[] args) {
        System.exit(SpringApplication.exit(SpringApplication.run(BatchApplication.class, args)));
    }
}

Boot’s side of this is documented at Batch Applications and on Spring Batch (SpringBoot Reference).

CommandLineJobOperator

For a standalone launch outside Spring Boot — a shell script, a scheduler that invokes java directly — Spring Batch 6.0 provides CommandLineJobOperator. It replaces CommandLineJobRunner, which is still on the classpath but deprecated for removal; scripts that invoke the old class should be moved over.

The class has its own main, so no launcher class is needed. It takes the fully qualified name of a Spring configuration class, an operation and the operation’s arguments:

java -cp app.jar org.springframework.batch.core.launch.support.CommandLineJobOperator \
     com.example.cli.CliConfig start helloWorldJob \
     "run.date=2026-01-30,java.time.LocalDate,true" "dry.run=true,java.lang.Boolean,false"

The operations are start <jobName> [parameters], startNextInstance <jobName>, and restart, stop, abandon and recover, each taking a job execution id. Parameters use the name=value,type,identifying form — note that the type and the flag are part of the same argument, which is why a launcher that splits arguments on commas breaks them. The exit code is 0 for a completed job and 1 for any failure; 2 means the configuration class was not found.

The configuration class must provide a JobOperator, a JobRepository and a JobRegistry bean, and the jobs must be registered in it. A configuration without the registry bean ended with A required bean was not found in the application context: No qualifying bean of type 'org.springframework.batch.core.configuration.JobRegistry' and exit code 1; adding a MapJobRegistry bean fixed it:

@Configuration
@EnableBatchProcessing
@EnableJdbcJobRepository(dataSourceRef = "batchDataSource")
@Import(HelloJob.class)
public class CliConfig {

    @Bean
    public JobRegistry jobRegistry() {
        return new MapJobRegistry();
    }

    @Bean
    public DataSource batchDataSource() {
        return new DriverManagerDataSource("jdbc:h2:file:./data/clidb", "sa", "");
    }

    @Bean
    public PlatformTransactionManager transactionManager(DataSource batchDataSource) {
        return new DataSourceTransactionManager(batchDataSource);
    }
}

Against that configuration the operations behaved as follows:

It supports the full lifecycle — start, stop, restart, abandon, recover — so a scheduler can drive a job from the shell without any Java of its own.

Launching on demand

From a REST endpoint

Launch asynchronously and hand the caller an execution id; never block the request thread on a batch job:

@RestController
@RequestMapping("/batch")
public class BatchController {

    private final JobOperator jobOperator;
    private final JobRepository jobRepository;
    private final Job endOfDayJob;

    public BatchController(JobOperator jobOperator, JobRepository jobRepository, Job endOfDayJob) {
        this.jobOperator = jobOperator;
        this.jobRepository = jobRepository;
        this.endOfDayJob = endOfDayJob;
    }

    @PostMapping("/end-of-day")
    public ResponseEntity<Map<String, Object>> launch(@RequestParam LocalDate runDate) throws Exception {
        JobParameters parameters = new JobParametersBuilder()
                .addLocalDate("run.date", runDate)
                .toJobParameters();
        JobExecution execution = jobOperator.start(endOfDayJob, parameters);
        return ResponseEntity.accepted()
                .body(Map.of("executionId", execution.getId(), "status", execution.getStatus()));
    }

    @GetMapping("/executions/{id}")
    public Map<String, Object> status(@PathVariable long id) {
        JobExecution execution = jobRepository.getJobExecution(id);
        return Map.of("status", execution.getStatus(),
                      "exitCode", execution.getExitStatus().getExitCode());
    }
}

Catch JobInstanceAlreadyCompleteException, JobExecutionAlreadyRunningException and InvalidJobParametersException and map them to 409/400 rather than letting them surface as 500. Run against a real server with the asynchronous operator, POST /batch/end-of-day?runDate=2026-01-30 answered 202 with {"status":"STARTED","executionId":2}, polling GET /batch/executions/{id} returned COMPLETED once the one-and-a-half second job was over, repeating the POST for the completed date answered 500 — the unmapped JobInstanceAlreadyCompleteException — and a malformed runDate=1/30/26 answered 400. An ISO date needs no @DateTimeFormat under Spring Boot.

From a scheduled method

@Component
public class EndOfDaySchedule {   // needs @EnableScheduling on a configuration class

    private final JobOperator jobOperator;
    private final Job endOfDayJob;

    public EndOfDaySchedule(JobOperator jobOperator, Job endOfDayJob) {
        this.jobOperator = jobOperator;
        this.endOfDayJob = endOfDayJob;
    }

    @Scheduled(cron = "0 30 2 * * MON-FRI")
    public void runNightly() throws Exception {
        JobParameters parameters = new JobParametersBuilder()
                .addLocalDate("run.date", LocalDate.now().minusDays(1))
                .toJobParameters();
        jobOperator.start(endOfDayJob, parameters);
    }
}

The schedule only fires if scheduling is enabled (@EnableScheduling on a configuration class). Because the parameters are fixed per day, a second firing for the same run.date is refused: with the cron temporarily set to every two seconds, the first tick launched the job and every later tick logged an error from the scheduler (Unexpected error occurred in scheduled task) caused by JobInstanceAlreadyCompleteException — the instance identity doing its work as a guard against double runs.

In a multi-instance deployment, guard the schedule so only one node fires — see Scheduling & ShedLock.

From Quartz

A Quartz job is a thin adapter that resolves the JobOperator from the application context and launches:

public class BatchQuartzJob extends QuartzJobBean {

    private JobOperator jobOperator;
    private Job endOfDayJob;

    public void setJobOperator(JobOperator jobOperator) { this.jobOperator = jobOperator; }
    public void setEndOfDayJob(Job endOfDayJob) { this.endOfDayJob = endOfDayJob; }

    @Override
    protected void executeInternal(JobExecutionContext context) throws JobExecutionException {
        try {
            jobOperator.start(endOfDayJob, new JobParametersBuilder()
                    .addLocalDate("run.date", LocalDate.now())
                    .toJobParameters());
        } catch (Exception exception) {
            throw new JobExecutionException(exception);
        }
    }
}

For Quartz itself — jobs, triggers, persistence and clustering — see the Scheduling section.

Launching from a message — a file-arrival event or a queue — is covered in Spring Batch Integration.

Synchronous and asynchronous launches side by side

The two launching modes differ in when start returns and, therefore, in what the caller can do with the returned JobExecution:

sequenceDiagram participant C as Caller participant Op as JobOperator participant T as TaskExecutor participant J as Job Note over C,J: synchronous: SyncTaskExecutor C->>Op: start(job, parameters) Op->>T: execute(job) T->>J: run on the caller thread J-->>Op: COMPLETED Op-->>C: JobExecution COMPLETED Note over C,J: asynchronous: SimpleAsyncTaskExecutor C->>Op: start(job, parameters) Op->>T: execute(job) Op-->>C: JobExecution STARTING, id known T->>J: run on a batch thread C->>Op: poll the repository by id

The measured difference: with a synchronous operator start() returned COMPLETED and a second call with the same parameters threw JobInstanceAlreadyCompleteException; with an asynchronous one start() returned in STARTING (STARTED through the REST controller, a few milliseconds later) and a second call while the job still ran threw JobExecutionAlreadyRunningException. Both exceptions come from the same rule — one instance, one live execution — seen at different moments, and a REST or scheduler caller should expect both.

Whatever the entry point, the outcome has to be translated for the caller, and the three entry points of this page do it differently: the Boot runner through the process exit code (0 completed, 5 failed, 1 refused), the CommandLineJobOperator through its own exit code (0 completed, 1 for every failure it reported), and a REST controller through the HTTP status (202 for an accepted launch, 500 for an unmapped refusal). Choosing the mapping is part of the design of the entry point, not something the framework decides.

Graceful shutdown

A batch process that is killed mid-chunk leaves an execution in STARTED. To shut down cleanly:

  • request a stop first (jobOperator.stop(jobExecution)), let the current chunk commit, and wait for STOPPED;

  • in a container, set terminationGracePeriodSeconds long enough for one chunk plus a margin;

  • register a shutdown hook, or rely on Spring Boot’s graceful shutdown, so SIGTERM triggers the stop instead of an abrupt exit;

  • on the next start, use JobOperator.recover() to clean up anything that was stranded anyway.

Both the stop protocol and recovery are detailed in Stopping, restart & recovery.
