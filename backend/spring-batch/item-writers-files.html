ItemWriters: files & XML/JSON

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

An ItemWriter receives the whole chunk at once, which is what lets it write efficiently — one batched statement, one flush, one file append — instead of one operation per item.

The contract

public interface ItemWriter<T> {
    void write(Chunk<? extends T> chunk) throws Exception;
}

Chunk<T> is the list of items the reader and processor produced for this transaction. Two consequences:

  • the writer must handle a chunk of any size, including one — during a skip scan a fault-tolerant step writes items one at a time (Fault tolerance: skip & retry);

  • the writer is the right home for side effects, because it runs once per chunk inside the chunk’s transaction (ItemProcessors).

ItemStreamWriter<T> adds the ItemStream callbacks. Every file writer implements it, because the current file position has to be saved at each commit point for a restart to append rather than overwrite.

FlatFileItemWriter

Writing a flat file is the mirror image of reading one:

flowchart LR Item["item"] --> FE["FieldExtractor
object to Object[]"] FE --> LA["LineAggregator
Object[] to one line of text"] LA --> File["Resource
one line appended"]
@Bean
@StepScope
public FlatFileItemWriter<Trade> tradeCsvWriter(
        @Value("#{jobParameters['output.file']}") WritableResource outputFile) {
    return new FlatFileItemWriterBuilder<Trade>()
            .name("tradeCsvWriter")
            .resource(outputFile)
            .delimited()
            .delimiter(",")
            .names("externalId", "isin", "quantity", "price", "notional")
            .headerCallback(writer -> writer.write("externalId,isin,quantity,price,notional"))
            .shouldDeleteIfExists(true)
            .build();
}

.delimited() builds a DelimitedLineAggregator over a BeanWrapperFieldExtractor that reads the named properties. For fixed-width output use .formatted() with a java.util.Formatter pattern:

@Bean
public FlatFileItemWriter<Trade> tradeReportWriter() {
    return new FlatFileItemWriterBuilder<Trade>()
            .name("tradeReportWriter")
            .resource(new FileSystemResource("/data/out/trades.txt"))
            .formatted()
            .format("%-12s%-14s%10.2f%12.2f")
            .locale(Locale.ROOT)           // otherwise the JVM default locale decides the decimal separator
            .names("externalId", "isin", "quantity", "price")
            .build();
}

A custom FieldExtractor takes over when the output columns are computed rather than read straight off the object:

public class TradeFieldExtractor implements FieldExtractor<Trade> {

    @Override
    public Object[] extract(Trade trade) {
        return new Object[] {
                trade.getExternalId(),
                trade.getInstrument().getIsin(),
                trade.getQuantity(),
                trade.getPrice(),
                trade.getQuantity().multiply(trade.getPrice())   // computed
        };
    }
}

And a custom LineAggregator takes over when the line format is not "fields joined by something".

Headers and footers

FlatFileHeaderCallback writes before the first item; FlatFileFooterCallback writes after the last one, and is where control totals belong. A footer usually needs state gathered during the step, so it also implements StepExecutionListener:

public class TotalsFooterCallback implements FlatFileFooterCallback, StepExecutionListener {

    private StepExecution stepExecution;

    @Override
    public void beforeStep(StepExecution stepExecution) {
        this.stepExecution = stepExecution;
    }

    @Override
    public void writeFooter(Writer writer) throws IOException {
        writer.write("TRL" + String.format("%09d", stepExecution.getWriteCount()));
    }
}

Register the callback both on the writer (.footerCallback(...)) and as a step listener, so beforeStep is called.

The footer above is only right for an execution that is not a restart: StepExecution.getWriteCount() counts the items written by this execution. When a failed execution is restarted, the new one writes only the remaining items, and the footer reports that smaller number (the worked example below shows TRL000000007 at the end of a file that holds eleven trades). A control total that must survive a restart has to be kept in the ExecutionContext, for instance by a writer wrapper that adds the chunk size to a context entry in update(...), and read from there in the footer. The footer is also written without a trailing line separator.

On restart, the header callback would otherwise run again and write a second header. FlatFileItemWriter handles this by tracking the written position in the ExecutionContext and appending — which is exactly why .name(...) and stream registration matter.

File-management flags

Flag Effect

shouldDeleteIfExists(true) (default)

Delete an existing output file when the step starts fresh. Prevents stale data from a previous run.

shouldDeleteIfEmpty(true)

Remove the file at the end if nothing was written — no empty files for downstream systems to misinterpret.

append(true) on the builder (setAppendAllowed on the writer)

Append to an existing file instead of deleting it. It takes precedence over shouldDeleteIfExists, which is still true by default: two runs of a step with append(true) and a header callback left one header and both runs' lines.

transactional(true) (default)

Buffer the chunk’s lines and flush them only on commit, so a rolled-back chunk leaves nothing behind. Set false only when the performance cost is proven and duplicates are acceptable.

forceSync(true)

fsync after each flush — durable, and considerably slower.

saveState(false)

Do not record the position; the writer becomes non-restartable but slightly cheaper (see Profiling & tuning).

XML with StaxEventItemWriter

@Bean
public StaxEventItemWriter<Trade> xmlTradeWriter() {
    Jaxb2Marshaller marshaller = new Jaxb2Marshaller();
    marshaller.setClassesToBeBound(Trade.class);

    return new StaxEventItemWriterBuilder<Trade>()
            .name("xmlTradeWriter")
            .resource(new FileSystemResource("/data/out/trades.xml"))
            .marshaller(marshaller)
            .rootTagName("trades")
            .overwriteOutput(true)
            .build();
}

The root tag is opened once and closed at the end, so the file is well-formed even though it was streamed.

JSON with JsonFileItemWriter

@Bean
public JsonFileItemWriter<Trade> jsonTradeWriter() {
    return new JsonFileItemWriterBuilder<Trade>()
            .name("jsonTradeWriter")
            .resource(new FileSystemResource("/data/out/trades.json"))
            .jsonObjectMarshaller(new JacksonJsonObjectMarshaller<>())
            .build();
}

The output is a JSON array: an opening bracket, comma-separated objects, a closing bracket.

Rolling output over several files

MultiResourceItemWriter starts a new file every itemCountLimitPerResource items, using a ResourceSuffixCreator for the numbering. It keeps a single output file from growing past what downstream systems can ingest:

@Bean
public MultiResourceItemWriter<Trade> rollingTradeWriter(FlatFileItemWriter<Trade> tradeCsvWriter) {
    MultiResourceItemWriter<Trade> writer = new MultiResourceItemWriter<>(tradeCsvWriter);
    writer.setName("rollingTradeWriter");
    writer.setResource(new FileSystemResource("/data/out/trades"));   // trades-1.csv, trades-2.csv, ...
    writer.setItemCountLimitPerResource(100_000);
    writer.setResourceSuffixCreator(index -> "-" + index + ".csv");
    return writer;
}

Composing writers

CompositeItemWriter sends every chunk to each delegate in turn — write to the database and an audit file:

@Bean
public CompositeItemWriter<Trade> auditingWriter(JdbcBatchItemWriter<Trade> databaseWriter,
                                                 FlatFileItemWriter<Trade> auditFileWriter) {
    return new CompositeItemWriter<>(List.of(databaseWriter, auditFileWriter));
}

ClassifierCompositeItemWriter routes each item to one delegate instead:

@Bean
public ClassifierCompositeItemWriter<Trade> routingWriter(ItemWriter<Trade> domesticWriter,
                                                         ItemWriter<Trade> foreignWriter) {
    ClassifierCompositeItemWriter<Trade> writer = new ClassifierCompositeItemWriter<>();
    writer.setClassifier(trade -> trade.isDomestic() ? domesticWriter : foreignWriter);
    return writer;
}

The delegates of a CompositeItemWriter are constructor arguments in 6.0, and the composite is itself an ItemStreamWriter that opens, updates and closes any delegate that is an ItemStream: a step whose composite wraps a FlatFileItemWriter writes the whole file without a .stream(...) registration. A ClassifierCompositeItemWriter is only an ItemWriter, so its delegates are hidden from the step and must be registered with .stream(...); omitted, the step fails on the first chunk with

org.springframework.batch.infrastructure.item.WriterNotOpenException: Writer must be open before it can be written to

See Chunk-oriented processing for the registration rule.

Worked example: exporting the trade table

The running example of this section exports the trades loaded by the reader pages. One job reads the trade table with a JdbcPagingItemReader (page size 4) and has one step per output format. The eleven trades of the table produce these files.

The delimited file, written with delimited(), a header callback and the totals footer:

externalId,isin,quantity,price,notional
T-0001,US0378331005,100.00,189.95,18995.00
T-0002,US5949181045,250.00,415.10,103775.00
...
T-0012,JP3633400001,300.00,15.50,4650.00
TRL000000011

The fixed-width report, written with formatted() and the format %-8s%-14s%10.2f%12.2f:

T-0001  US0378331005      100.00      189.95
T-0002  US5949181045      250.00      415.10

Without .locale(Locale.ROOT) the same run on a JVM whose default locale uses the comma printed 100,00 and 189,95, because the format is handed to java.util.Formatter with the default locale.

The JSON file, from JsonFileItemWriter with a JacksonJsonObjectMarshaller (Jackson 3), is an array with one object per line:

[
 {"externalId":"T-0001","isin":"US0378331005","quantity":100.00,"price":189.95,"notional":18995.00,"tradeDate":"2026-03-02","domestic":true},
 {"externalId":"T-0002", ... "domestic":true},
 ...
]

The marshaller serialises every readable property, which is why the derived isDomestic() getter appears as "domestic"; annotate such a getter with @JsonIgnore when it must not be exported. The XML file, with the JAXB annotations of the item class, is written as one line wrapped in the root tag:

<?xml version="1.0" encoding="UTF-8"?><trades><trade><externalId>T-0001</externalId><isin>US0378331005</isin><quantity>100.00</quantity>...</trade>...</trades>

The seven steps all report read=11 write=11; the commit counts are 3 for a chunk of 4 or 5, and 2 for a chunk of 6.

Rolling and routing

With a chunk of 5 and setItemCountLimitPerResource(5) the eleven trades land in roll-1.csv, roll-2.csv and roll-3.csv, each starting with its own header because the delegate’s header callback runs for every file. MultiResourceItemWriter splits a chunk when the limit falls inside it: with a chunk of 4 and the same limit the files hold 5, 5 and 1 items, not 4, 8 and 3.

ClassifierCompositeItemWriter with trade.isDomestic() ? domestic : foreign sends the six trades whose ISIN starts with US to domestic.csv and the other five to foreign.csv, both written by the same chunk of six.

What a restart does to a file

With the default transactional(true) the writer buffers a chunk’s lines and flushes them to the file only when the transaction commits, and it saves the file position in the ExecutionContext at every commit. A chunk that fails therefore leaves nothing in the file, and a restart appends after the last committed position instead of starting over. The example writes the second chunk to the writer and then throws, and restarts the execution:

sequenceDiagram participant S as Step participant W as FlatFileItemWriter participant F as out/restart.csv participant J as JobRepository Note over S,J: first execution, chunk size 4 S->>W: open S->>W: write chunk 1 W->>F: header and 4 lines flushed at the commit S->>J: commit, save the file position S->>W: write chunk 2 Note over W: the lines are only buffered Note over S,F: the step throws, the transaction rolls back, nothing reaches the file Note over S,J: restart of the same execution S->>W: open with the saved position Note over W: no second header S->>W: write the remaining 7 items W->>F: 7 lines, then the footer

The first execution ends FAILED with write=4; the restarted execution reports read=7 write=7 commit=2, and the file contains the header once, each of the eleven trades once and the footer. Only the footer is wrong, for the reason given under the footer callbacks: it reads TRL000000007.
