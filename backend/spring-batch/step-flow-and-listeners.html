Step flow & listeners

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A job is more than a straight line of steps: it branches on outcomes, runs branches in parallel, and reports on itself through listeners. This page covers the flow API, the listener interfaces, and late binding.

Sequential flow

The simplest job runs its steps in order, stopping at the first failure:

@Bean
public Job endOfDayJob(JobRepository jobRepository, Step stageStep, Step loadStep, Step reportStep) {
    return new JobBuilder("endOfDayJob", jobRepository)
            .start(stageStep)
            .next(loadStep)
            .next(reportStep)
            .build();
}

Conditional flow

.on(exitCode) matches a step’s ExitStatus exit code and .to(step) names where to go next. .from(step) adds further transitions from a step already mentioned:

@Bean
public Job conditionalJob(JobRepository jobRepository,
                          Step loadStep, Step reconcileStep, Step alertStep, Step reportStep) {
    return new JobBuilder("conditionalJob", jobRepository)
            .start(loadStep)
                .on("FAILED").to(alertStep)
            .from(loadStep)
                .on("COMPLETED WITH SKIPS").to(reconcileStep)
            .from(loadStep)
                .on("*").to(reportStep)
            .end()
            .build();
}

Matching is on the exit code string, and two wildcards are available: * matches any sequence of characters (including none) and ? matches exactly one. .on("*") is therefore the catch-all, and ordering matters only in that the most specific pattern wins.

Three terminators end a flow explicitly:

Terminator Resulting job status

.end()

COMPLETED. The instance is finished and cannot be rerun.

.fail()

FAILED. The instance is restartable.

.stopAndRestart(step)

STOPPED, recording that a restart should resume at the named step.

 
.start(validateStep)
    .on("INVALID_INPUT").fail()
.from(validateStep)
    .on("MANUAL_REVIEW").stopAndRestart(loadStep)
.from(validateStep)
    .on("*").to(loadStep)
.end()

Custom exit codes come from a StepExecutionListener that returns a new ExitStatus — see Jobs, instances & parameters.

JobExecutionDecider

When the branch depends on something other than the previous step’s outcome — the day of the week, a row count, a feature flag — use a decider. It returns a FlowExecutionStatus, which transitions match exactly as they match an exit code:

@Component
public class WeekendDecider implements JobExecutionDecider {

    @Override
    public FlowExecutionStatus decide(JobExecution jobExecution, StepExecution stepExecution) {
        LocalDate runDate = jobExecution.getJobParameters().getLocalDate("run.date");
        DayOfWeek day = runDate.getDayOfWeek();
        boolean weekend = day == DayOfWeek.SATURDAY || day == DayOfWeek.SUNDAY;
        return new FlowExecutionStatus(weekend ? "WEEKEND" : "WEEKDAY");
    }
}
@Bean
public Job decidedJob(JobRepository jobRepository, WeekendDecider weekendDecider,
                      Step loadStep, Step fullReportStep, Step shortReportStep) {
    return new JobBuilder("decidedJob", jobRepository)
            .start(loadStep)
            .next(weekendDecider)
                .on("WEEKEND").to(shortReportStep)
            .from(weekendDecider)
                .on("WEEKDAY").to(fullReportStep)
            .end()
            .build();
}

Split flows

A split runs several flows concurrently, each on a thread from the supplied TaskExecutor. The job waits for all of them and continues only if all succeeded:

@Bean
public Flow customerFlow(Step loadCustomersStep) {
    return new FlowBuilder<SimpleFlow>("customerFlow").start(loadCustomersStep).build();
}

@Bean
public Flow productFlow(Step loadProductsStep) {
    return new FlowBuilder<SimpleFlow>("productFlow").start(loadProductsStep).build();
}

@Bean
public Job parallelLoadJob(JobRepository jobRepository, Flow customerFlow, Flow productFlow,
                           Step aggregateStep) {
    return new JobBuilder("parallelLoadJob", jobRepository)
            .start(customerFlow)
            .split(new SimpleAsyncTaskExecutor("split-"))
            .add(productFlow)
            .next(aggregateStep)
            .end()
            .build();
}

The branches must be genuinely independent — no shared mutable state, no contended tables. Other parallelism options, and how to choose between them, are in Scaling & parallel processing.

Externalized and reusable flows

A Flow is a bean, so a sequence used by several jobs can be defined once:

@Bean
public Flow stagingFlow(Step downloadStep, Step unzipStep, Step validateStep) {
    return new FlowBuilder<SimpleFlow>("stagingFlow")
            .start(downloadStep)
            .next(unzipStep)
            .next(validateStep)
            .build();
}

Embedding it in a job is .start(stagingFlow). Wrapping it in a FlowStep instead gives the whole flow a name of its own in the metadata. In 6.0 a FlowStep has no no-argument constructor; build it with the step builder:

@Bean
public Step stagingStep(JobRepository jobRepository, Flow stagingFlow) {
    return new StepBuilder("stagingStep", jobRepository).flow(stagingFlow).build();
}

The wrapper adds one row; it does not hide the steps inside. Run in a job with a final aggregateStep, the flow step produced these BATCH_STEP_EXECUTION rows, against four rows for the same flow embedded directly:

-- flow wrapped in stagingStep                          -- flow embedded with .start(stagingFlow)
stagingStep   COMPLETED  commit 0                       downloadStep   COMPLETED  commit 1
downloadStep  COMPLETED  commit 1                       unzipStep      COMPLETED  commit 1
unzipStep     COMPLETED  commit 1                       checkStep      COMPLETED  commit 1
checkStep     COMPLETED  commit 1                       aggregateStep  COMPLETED  commit 1
aggregateStep COMPLETED  commit 1

So the wrapped form records the outcome of the flow as a whole under the name stagingStep (with no commits of its own, since it runs no transaction), and the inner steps are still recorded individually. It is a naming and grouping device, not a way to shorten the step list.

Listeners

Listeners are the observation points around every phase. Each has an interface and an annotation equivalent; the annotations are convenient on an existing bean, the interfaces when the component is dedicated.

Interface Annotations Fires

StepExecutionListener

@BeforeStep, @AfterStep

Around a whole step. afterStep may return a new ExitStatus.

ChunkListener

@BeforeChunk, @AfterChunk, @AfterChunkError, @OnChunkError

Around each chunk, inside/outside the transaction boundary. In 6.0 the annotated methods take a Chunk; see the note below the example.

ItemReadListener

@BeforeRead, @AfterRead, @OnReadError

Around each read().

ItemProcessListener

@BeforeProcess, @AfterProcess, @OnProcessError

Around each process().

ItemWriteListener

@BeforeWrite, @AfterWrite, @OnWriteError

Around each write(chunk).

SkipListener

@OnSkipInRead, @OnSkipInProcess, @OnSkipInWrite

When an item is skipped — see Fault tolerance: skip & retry.

RetryListener

 — 

Around a retried operation.

JobExecutionListener

@BeforeJob, @AfterJob

Around the whole job — see Configuring a job.

 
@Component
public class StepAuditListener {

    private static final Logger log = LoggerFactory.getLogger(StepAuditListener.class);

    @BeforeStep
    public void before(StepExecution stepExecution) {
        log.info("step {} starting", stepExecution.getStepName());
    }

    @AfterStep
    public ExitStatus after(StepExecution stepExecution) {
        if (stepExecution.getSkipCount() > 0) {
            return new ExitStatus("COMPLETED WITH SKIPS",
                    stepExecution.getSkipCount() + " items were skipped");
        }
        return stepExecution.getExitStatus();
    }
}

@Component
public class ChunkAuditListener implements ChunkListener<TradeCsv, Trade> {

    private static final Logger log = LoggerFactory.getLogger(ChunkAuditListener.class);

    @Override
    public void afterChunk(ChunkContext context) {
        StepExecution stepExecution = context.getStepContext().getStepExecution();
        log.info("committed chunk {}: read={} write={}",
                stepExecution.getCommitCount(),
                stepExecution.getReadCount(),
                stepExecution.getWriteCount());
    }
}
@Bean
public Step loadStep(JobRepository jobRepository, PlatformTransactionManager tx,
                     ItemReader<TradeCsv> reader, ItemProcessor<TradeCsv, Trade> processor,
                     ItemWriter<Trade> writer,
                     StepAuditListener stepAuditListener, ChunkAuditListener chunkAuditListener) {
    return new StepBuilder("loadStep", jobRepository)
            .<TradeCsv, Trade>chunk(3, tx)
            .reader(reader)
            .processor(processor)
            .writer(writer)
            .listener((Object) stepAuditListener)    // annotation-based: @BeforeStep, @AfterStep
            .listener(chunkAuditListener)            // interface-based: ChunkListener
            .build();
}

The chunk callbacks are split from the step callbacks for a reason found by running it. In Spring Batch 6.0 the ChunkListener methods and the @BeforeChunk/@AfterChunk annotations take a Chunk, but the step built by .chunk(size, transactionManager) — the legacy implementation, which logs a deprecation note at startup and is removed in 7.0 — still invokes the older ChunkContext variants. Putting @AfterChunk on a method that takes a ChunkContext fails at startup (The method [afterChunk] on target class [...] is incompatible with the signature [(Chunk)]); a method that takes a Chunk starts, and then fails at run time with argument type mismatch; and registering one object that implements ChunkListener through the Object overload of listener failed the same way. Implementing the interface and registering it through the typed .listener(chunkListener) overload worked, and an annotation-only object registered through that overload kept its @BeforeStep and @AfterStep methods — hence two listeners.

Keep item-level listeners cheap: @AfterRead runs once per item, so logging there at INFO level will dwarf the job’s real work.

Late binding with @StepScope and @JobScope

Job parameters are not known when the application context is built, so a bean that needs one must be created when the step runs. That is what @StepScope (and @JobScope, one level up) provides: a proxy is injected, and the real bean is instantiated per step execution, at which point the parameter is available through SpEL.

@Bean
@StepScope
public FlatFileItemReader<TradeCsv> tradeReader(
        @Value("#{jobParameters['input.file']}") Resource inputFile) {
    return new FlatFileItemReaderBuilder<TradeCsv>()
            .name("tradeReader")
            .resource(inputFile)
            .delimited()
            .names("id", "isin", "quantity", "price")
            .targetType(TradeCsv.class)
            .build();
}

@Bean
@StepScope
public TradeItemProcessor tradeProcessor(
        @Value("#{jobParameters['run.date']}") LocalDate runDate,
        @Value("#{jobParameters['dry.run'] ?: false}") boolean dryRun) {
    return new TradeItemProcessor(runDate, dryRun);
}

Four SpEL roots are available in a step-scoped bean:

Expression root Contains

jobParameters

The launch parameters, typed.

jobExecutionContext

The job-scoped ExecutionContext — values promoted by an earlier step (Steps, executions & the ExecutionContext).

stepExecutionContext

The step-scoped ExecutionContext — notably the per-partition values set by a Partitioner.

stepExecution / jobExecution

The execution objects themselves, for anything else.

Partitioned steps rely on this to give each worker its slice:

@Bean
@StepScope
public JdbcPagingItemReader<Trade> partitionedTradeReader(
        DataSource dataSource,
        @Value("#{stepExecutionContext['minId']}") Long minId,
        @Value("#{stepExecutionContext['maxId']}") Long maxId) throws Exception {
    return new JdbcPagingItemReaderBuilder<Trade>()
            .name("partitionedTradeReader")
            .dataSource(dataSource)
            .selectClause("SELECT id, isin, quantity, price")
            .fromClause("FROM trade")
            .whereClause("WHERE id BETWEEN :minId AND :maxId")
            .parameterValues(Map.of("minId", minId, "maxId", maxId))
            .sortKeys(Map.of("id", Order.ASCENDING))
            .pageSize(1000)
            .rowMapper(new TradeRowMapper())
            .build();
}

The full partitioning picture is in Scaling & parallel processing.

Two practical notes on these expressions:

  • they belong in @Value (or XML) inside code, where the braces are literal; a ?: default works, and @Value("#{jobParameters['dry.run'] ?: false}") boolean dryRun gave false without the parameter and true with a Boolean one;

  • a @StepScope bean method that is declared to return an interface (for example ItemProcessor) is not inspected for annotation-based listener methods — the framework logs a warning saying so — so return the implementing class;

  • a step-scoped bean must be referenced through its proxy. Injecting a @StepScope bean into a singleton by type works because the proxy is a singleton, but calling its methods outside a running step throws ScopeNotActiveException: ... Scope 'step' is not active for the current thread.

Worked example: routing the end-of-day load

The conditionalJob of this page, with the loadSkipStep of Steps, executions & the ExecutionContext as its first step, was run twice. With the defective file (one read skip, one process skip, one write skip, one filtered item) the step ended with exit code COMPLETED WITH SKIPS, which the @AfterStep listener set, and the job took the second transition:

step loadSkipStep starting
reconcileStep on thread main
result: COMPLETED / COMPLETED

With the clean file the step ended COMPLETED (no skips, so the listener returned the step’s own exit status), no transition named it, and the "*" catch-all sent the job to the summary step. A FAILED exit would have gone to the alert step. The transition that matched was chosen by the exit code string alone — including a code with a space in it.

Declaration order did not matter either. Re-declaring the flow with the catch-all first — .on("*").to(summaryStep) followed by .from(validateStep).on("INVALID_INPUT").fail() — and then running it with an INVALID_INPUT exit code still ended the job FAILED: the most specific pattern won, as stated above.

The terminators were run from a validateStep whose exit code was set by a launch parameter. The three jobs below differ only in that parameter:

Exit code of validateStep Transition Job after the run

INVALID_INPUT

.fail()

FAILED / FAILED; no further step ran

MANUAL_REVIEW

.stopAndRestart(terminalLoadStep)

STOPPED / STOPPED; restarting that execution ran only terminalLoadStep and ended COMPLETED

any other code

"*" to terminalLoadStep, then .end()

COMPLETED / COMPLETED

The restart of the stopped execution is visible in the metadata: execution 2 has the completed validateStep, and the restart (execution 4, same instance) has a single terminalLoadStep row — the validation was not repeated.

Split flows run concurrently

The parallelLoadJob was run with a 400 ms customer flow and a 300 ms product flow. Each ran on its own thread of the SimpleAsyncTaskExecutor("split-"), and the aggregate step started only after both had ended, on the launching thread:

The two step executions of the split are separate rows (loadProductsStep, loadCustomersStep) in the same job execution, and the job’s total time was close to the longer branch, not their sum.

The deciders and the listeners in the log

A WeekendDecider inserted after a prepStep was launched with run.date 2026-01-30 (a Friday) and 2026-01-31 (a Saturday). The first run executed prepStep then fullReportStep, the second prepStep then shortReportStep; nothing about the decision is stored in a step row of its own, because a decider is not a step.

The firing order of the listeners of this page, as logged around one run of the load step with the job, step and chunk listeners attached, is the order of their nesting:

JobTimingListener  starting endOfDayJob execution 1 ...
StepAuditListener  step loadStep starting
ChunkAuditListener committed chunk 1: read=3 write=3
ChunkAuditListener committed chunk 2: read=6 write=5
ChunkAuditListener committed chunk 3: read=9 write=8
ChunkAuditListener committed chunk 4: read=10 write=9
JobTimingListener  endOfDayJob finished as COMPLETED in 86ms

(stageStep, which has no listener, runs between the first two lines.) The chunk listener fired after each commit: commitCount was already incremented when it ran. The write counter lags the read counter by exactly the filtered item, from the second chunk on.
