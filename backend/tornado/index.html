Python Tornado

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This section is written against Tornado 6.5.10 (released 2026-09-15) on Python 3.13, checked on 2026-10-07. Tornado 6.5 supports Python 3.9 and newer. Tornado 6.6 is not released yet: only the alpha 6.6a1 (2026-09-22) is on PyPI and its final release notes are still dated "Oct XX, 2026", so everything described as 6.6 in this section (Python 3.11 as the minimum, the cross_origin_protection and trusted_origins settings, the deprecation of OpenIdMixin) is upcoming and can still change. Every page notes the version in which a feature appeared, because Tornado changed a lot between 4.x and 6.x and most tutorials on the web still show the older idioms.

What Tornado is

Tornado is a Python web framework and asynchronous networking library that started life at FriendFeed. It bundles four things that other stacks keep in separate projects: a web framework (tornado.web: Application, RequestHandler, templates, cookies, XSRF protection, WebSockets), an HTTP server and client (HTTPServer, AsyncHTTPClient), a non-blocking networking layer (IOLoop and IOStream, now thin wrappers around asyncio), and coroutine tools (tornado.gen, tornado.queues, tornado.locks).

The defining design choice is that Tornado is not a WSGI framework. It brings its own HTTP server and runs every request of a process on one thread and one event loop. A handler that waits (for a database, a remote service or a client) does so with await and lets the loop serve other connections meanwhile. That makes Tornado a good fit for workloads with many long-lived or idle connections, such as WebSockets, long polling and Server-Sent Events, and for services that spend their time calling other services. It is a poor fit for CPU-heavy handlers and for code built on blocking libraries, unless that work is moved off the loop.

This section is for developers who:

  • know Python and want to build real-time or high-concurrency services without a second framework for the networking layer

  • are coming from Flask, Django, FastAPI or Pyramid and want to understand what a single-threaded, single-loop server changes about handlers, databases, tests and deployment

  • maintain Tornado 4.x or 5.x code (callbacks, @gen.coroutine, IOLoop.instance()) and need the current async def idioms and the upgrade path

  • need one coherent path from a first handler to WebSockets, security, testing and a multi-process deployment behind nginx

The Bookshelf Live scenario

Every example builds one small original service, Bookshelf Live, so the pages fit together instead of being isolated snippets. It is the real-time companion of the Flask Bookshelf and the FastAPI Bookshelf API, and it shows what Tornado is for:

  • a JSON API for books and reviews backed by an async driver

  • a WebSocket chat room per book, and a "new reviews" feed over long polling and Server-Sent Events

  • cover metadata fetched concurrently from an external service with AsyncHTTPClient, driven by a bounded queue of workers (a local fake service in tests)

  • signed-cookie login, XSRF and cross-origin protection, and Google OAuth 2.0 sign-in

  • tests with AsyncHTTPTestCase, and deployment as one process per CPU behind nginx
