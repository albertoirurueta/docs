Rate Limiting & Load Shedding

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against axum 0.8.9 on Rust 1.99 (edition 2024) with tower 0.5.3, tower_governor 0.8.0 and redis 1.7, checked on 2026-10-06. Rate limiting caps how often one client may call the service; load shedding rejects work the service as a whole cannot absorb right now. Both answer quickly with an error instead of letting queues grow until everything is slow. The algorithms — token bucket, leaky bucket, GCRA, sliding windows — are explained on Rate Limiter and, for Java, on the Bucket4j pages of the Resilience section; this page shows the axum side.

Per-client limits with tower_governor

tower_governor wraps the governor crate, which implements the Generic Cell Rate Algorithm (GCRA) — a token bucket that stores a single timestamp per key, so it is cheap in memory and lock-free. Its configuration is a replenish period and a burst size:

[dependencies]
tower_governor = "0.8.0" # depends on tower-http 0.6: a second tower-http compiles alongside 0.7

Source: tower_governor 0.8.0 and Cargo: specifying dependencies

use std::net::SocketAddr;
use std::sync::Arc;
use std::time::Duration;

use axum::{Router, routing::get};
use tower_governor::{GovernorLayer, governor::GovernorConfigBuilder, key_extractor::SmartIpKeyExtractor};

#[tokio::main]
async fn main() {
    // Bursts of up to 5 requests per client, then one more every 2 seconds.
    let config = Arc::new(
        GovernorConfigBuilder::default()
            .per_second(2)
            .burst_size(5)
            .key_extractor(SmartIpKeyExtractor) // X-Forwarded-For / X-Real-IP / Forwarded, else the peer address
            .use_headers() // x-ratelimit-* headers on every response
            .finish()
            .expect("valid rate-limit configuration"),
    );

    // The limiter keeps one entry per key; purge idle keys periodically.
    let limiter = config.limiter().clone();
    tokio::spawn(async move {
        let mut tick = tokio::time::interval(Duration::from_secs(60));
        loop {
            tick.tick().await;
            limiter.retain_recent();
        }
    });

    let app = Router::new().route("/api/v1/books", get(|| async { "books\n" })).layer(GovernorLayer::new(config));

    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000").await.unwrap();
    // the peer-IP extractors need the connection's address
    axum::serve(listener, app.into_make_service_with_connect_info::<SocketAddr>()).await.unwrap();
}

Source: tower_governor 0.8.0

  • Which key? PeerIpKeyExtractor (the default) uses the TCP peer address from ConnectInfo — correct only when clients connect directly. Behind a reverse proxy every request comes from the proxy, so use SmartIpKeyExtractor, which reads X-Forwarded-For, X-Real-IP and Forwarded. Those headers are client-controlled unless your proxy overwrites them: configure the proxy to set them, and never trust them on a directly exposed service, or an attacker rotates fake IPs to evade the limit.

  • Authenticated clients should be limited by user or API key rather than by IP (many users share one NAT address); implement KeyExtractor for a type that reads the token, and stack two GovernorLayers with different quotas.

  • Limits are per process. With three replicas the effective limit is three times higher; use a shared store for strict global limits (below).

  • tower_governor 0.8 depends on tower-http 0.6 while this section uses 0.7, so cargo tree -d shows two tower-http versions. It works — the layers are independent — at the cost of compile time. The same applies to leptos_axum.

Load shedding and concurrency limits with tower

tower ships generic layers that protect the service as a whole:

Layer Behaviour

ConcurrencyLimitLayer::new(n)

at most n requests in flight; others wait (back-pressure via poll_ready)

LoadShedLayer

when the inner service is not ready, fail immediately with Overloaded instead of waiting

RateLimitLayer::new(n, period)

at most n requests per period for the whole service (not per client)

BufferLayer::new(n)

a bounded queue in front of a service, making it Clone and shareable

The flow below shows how the capacity limit and the shedding layer decide the fate of each request.

flowchart TD R[Incoming request] --> S{"Is the service ready, with fewer than n requests in flight?"} S -- yes --> H[Run the handler and return its response] S -- "no, with LoadShed" --> O["Fail immediately with Overloaded"] O --> E["HandleErrorLayer maps it to 503"] S -- "no, without LoadShed" --> W["Wait in poll_ready (back-pressure)"] W --> S

ConcurrencyLimit + LoadShed is the useful pair: the first defines capacity, the second turns "wait" into a fast 503 so clients can retry elsewhere (the rejected requests finish first in the output below). Both fail with BoxError, so a HandleErrorLayer must sit outside them, and both must wrap the whole router (axum’s router is always ready, see Tower Service Model):

use std::time::Duration;

use axum::{
    BoxError, Router,
    error_handling::HandleErrorLayer,
    http::{StatusCode, header},
    response::IntoResponse,
    routing::get,
};
use tower::ServiceBuilder;

async fn overloaded(err: BoxError) -> impl IntoResponse {
    if err.is::<tower::load_shed::error::Overloaded>() {
        (StatusCode::SERVICE_UNAVAILABLE, [(header::RETRY_AFTER, "1")], "server busy, retry shortly\n")
    } else {
        (StatusCode::INTERNAL_SERVER_ERROR, [(header::RETRY_AFTER, "5")], "internal error\n")
    }
}

#[tokio::main]
async fn main() {
    let app = Router::new()
        .route("/api/v1/reports/heavy", get(|| async {
            tokio::time::sleep(Duration::from_millis(500)).await; // simulate expensive work
            "report\n"
        }))
        .layer(
            ServiceBuilder::new()
                .layer(HandleErrorLayer::new(overloaded))
                .load_shed()
                .concurrency_limit(2), // capacity: two concurrent reports per instance
        );
    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000").await.unwrap();
    // into_make_service() builds the layer stack once, so all connections share one limit (see below)
    axum::serve(listener, app.into_make_service()).await.unwrap();
}

Source: tower: load_shed and tower: limit

503 503 200 200

Source: tower: load_shed and tower: limit

Pitfall: per-connection layer state. ConcurrencyLimitLayer, RateLimitLayer and BufferLayer create their semaphore, counter or queue in Layer::layer. When a router without state is passed directly to axum::serve(listener, app), axum finishes building its routes — and calls Layer::layer — once per connection, so each connection gets its own limit and the stack above lets every request through (verified with axum 0.8.9: six concurrent requests on six connections all succeeded). Build the routes once with app.into_make_service() or app.with_state(()) (routers that already called with_state(state) are built at that point and are not affected). Layers that keep their state behind an Arc created before the layer — GovernorLayer, InFlightRequestsLayer — are shared either way.

Choose the concurrency limit from measurements — roughly the throughput at which latency starts to climb, per instance — and keep it per expensive route group rather than global. Kubernetes readiness probes should report "not ready" while an instance sheds load for long periods (see Metrics & SLOs).

A distributed limiter with Redis

When several instances must share one limit — "100 searches per API key per minute, across the fleet" — keep the counters in Redis. A fixed window counter is the simplest correct scheme: INCR a key named after the client and the current minute, set its expiry on first use, and reject when the count exceeds the limit. It allows up to twice the limit across a window boundary; sliding-window or GCRA scripts in Lua remove that at the cost of complexity.

use std::time::{SystemTime, UNIX_EPOCH};

use axum::{
    Router,
    extract::{Request, State},
    http::{HeaderValue, StatusCode, header},
    middleware::{self, Next},
    response::{IntoResponse, Response},
    routing::get,
};
use redis::aio::ConnectionManager;

const LIMIT: u64 = 3;
const WINDOW_SECS: u64 = 60;

#[derive(Clone)]
struct AppState {
    redis: ConnectionManager,
}

async fn rate_limit(State(state): State<AppState>, req: Request, next: Next) -> Response {
    let client = req
        .headers()
        .get("x-api-key")
        .and_then(|v| v.to_str().ok())
        .unwrap_or("anonymous")
        .to_owned();
    let now = SystemTime::now().duration_since(UNIX_EPOCH).expect("clock after 1970").as_secs();
    let window = now / WINDOW_SECS;
    let key = format!("ratelimit:{client}:{window}");

    let mut redis = state.redis.clone();
    let count: redis::RedisResult<(u64,)> =
        redis::pipe().atomic().incr(&key, 1u64).expire(&key, WINDOW_SECS as i64).ignore().query_async(&mut redis).await;

    match count {
        Ok((n,)) if n > LIMIT => {
            let retry_after = WINDOW_SECS - now % WINDOW_SECS;
            (StatusCode::TOO_MANY_REQUESTS, [(header::RETRY_AFTER, retry_after.to_string())], "rate limit exceeded\n")
                .into_response()
        }
        Ok((n,)) => {
            let mut response = next.run(req).await;
            let remaining = HeaderValue::from(LIMIT - n);
            response.headers_mut().insert("ratelimit-remaining", remaining);
            response
        }
        Err(err) => {
            // fail open: a Redis outage must not take the API down
            tracing::warn!(%err, "rate limiter unavailable");
            next.run(req).await
        }
    }
}

#[tokio::main]
async fn main() {
    let url = std::env::var("REDIS_URL").unwrap_or_else(|_| "redis://127.0.0.1:6379".to_owned());
    let client = redis::Client::open(url).expect("valid Redis URL");
    let state = AppState { redis: ConnectionManager::new(client).await.expect("Redis reachable") };

    let app = Router::new()
        .route("/api/v1/search", get(|| async { "results\n" }))
        .route_layer(middleware::from_fn_with_state(state.clone(), rate_limit))
        .with_state(state);
    let listener = tokio::net::TcpListener::bind("127.0.0.1:3000").await.unwrap();
    axum::serve(listener, app).await.unwrap();
}

Source: redis: ConnectionManager and Redis: INCR rate limiter pattern

results
results

Source: redis: ConnectionManager and Redis: INCR rate limiter pattern

  • MULTI/EXEC (.atomic()) makes INCR and EXPIRE one step, so a crash cannot leave a counter without expiry.

  • Decide explicitly whether to fail open (allow traffic when Redis is down, as here) or fail closed (reject); login and payment endpoints usually fail closed.

  • The RateLimit-* header fields are being standardised by the IETF HTTPAPI working group; Retry-After (RFC 9110) is the one every client understands today.

Redis setup and connection management are covered on Redis & Caching.

429 or 503?

Status Meaning

429 Too Many Requests

this client exceeded its quota; retrying sooner will not help. Include Retry-After.

503 Service Unavailable

the service is overloaded or degraded for everyone; a retry, possibly to another instance, may succeed. Retry-After is optional.

Clients should retry 503 and 429 with exponential backoff and jitter, honouring Retry-After when present.

Spotting abuse

Rate limits stop volumetric abuse; slower abuse — credential stuffing at a few requests per minute, scraping by many IPs, enumeration of IDs — shows up in telemetry instead. Gangappa & Rangaraj (Mastering Distributed Observability in Rust, chapter 13) recommend recording security-relevant attributes on request spans and alerting on patterns:

  • failed logins per account and per IP (span attributes enduser.id, client.address, auth.outcome);

  • 404 and 403 rates per client, which reveal ID enumeration;

  • unusual request mixes (many GET /books/{isbn} with sequential ISBNs, no static assets);

  • responses with 429, to tune limits and detect clients that ignore them.

Log the matched route (/api/v1/books/{isbn}), not the raw path, to keep cardinality bounded; see Logging & Tracing.

Where the books are outdated

Yoon (Beginning Axum) and Gangappa & Rangaraj use tower_governor with tower-http 0.6, which matches what tower_governor 0.8 still depends on; with an application on tower-http 0.7, expect the duplicate-version caveat above. The rate-limiting theory in this site’s Resilience section applies unchanged.
