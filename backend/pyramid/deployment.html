Deployment

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Pyramid 2.1 (released 2026-03-11) on Python 3.13, checked on 2026-10-07, with Waitress 3.0.2, Gunicorn 26.2.0, pyuwsgi 2.0.30.post1 (uWSGI 2.0.30), mod_wsgi 6.1.0, rutter 1.0, PasteDeploy 3.1.0, asgiref 3.12.1, Uvicorn 0.54.0, SQLAlchemy 2.0.54 and WebTest 3.0.7. Every Python example was executed. The servers were started for real on loopback ports, queried over HTTP and stopped with signals, and the outputs shown come from those runs. The nginx configuration was checked with nginx -t (nginx 1.29), and the Dockerfile was built with Docker 29.8.2 and run behind an nginx container with a read-only root file system and a non-root user. The Kubernetes manifest was parsed as YAML but not applied, because no cluster was available. Three things could not be executed in the verification environment and are marked as such where they appear: mod_wsgi itself (mod_wsgi-express refuses to load the interpreter library of the macOS host because it is not code signed), the systemd unit (the host is not Linux) and the Apache httpd directives taken from the official tutorial. The running example is the Bookshelf Shelves scenario: public shelves owned by users, which grew over the earlier pages of this section.

Pyramid does not ship a production server. It is a WSGI application, and the only thing it asks of the outside world is a server that can call that application. The official documentation therefore treats deployment as a short list of choices rather than a chapter: Waitress is the default server of every generated project, Gunicorn, uWSGI and mod_wsgi load the same .ini file or the same pyramid.wsgi script, and a reverse proxy sits in front. The decisions that are specific to Pyramid are small but easy to miss: the settings that must be off, the fact that request.client_addr trusts a header by itself, the two different ways a URL prefix reaches the application, and the fact that Pyramid itself never becomes asynchronous. This page walks through them in the order a deployment meets them, from the application and its production.ini to the server, the proxy, the container and finally the cases that go beyond plain WSGI.

Sibling frameworks of this site have the same page with their own details: Flask: Deployment, WSGI Servers & Proxies covers Gunicorn, uWSGI, mod_wsgi and ProxyFix for Flask and is the better reference for the servers themselves; Tornado: Running & Deploying covers a server that is its own HTTP server; and Tornado: WSGI Interoperability shows how a WSGI application such as Pyramid can be mounted inside a Tornado process, and why that is not a way to deploy it. The earlier pages of this section that this one builds on are Cookiecutter Projects & pserve, Settings, Environment & .ini Files, Logging & Debug Toolbar, Static Assets and Command Line & p-scripts.

The Production Topology

A development setup has one process: pserve development.ini --reload starts Waitress, which serves everything, including the debug toolbar and the static files. A production setup separates the jobs. A reverse proxy faces the internet, terminates TLS, buffers slow clients and serves the static files from disk; a WSGI server runs several worker processes that import the application once and answer the dynamic requests; configuration comes from a hardened production.ini plus environment variables; and every worker owns its own pool of database connections.

The Bookshelf Shelves Application to Deploy

Deployment does not change how an application is written, but it adds three habits that the example below follows. The application is created by an entry point that every server can load by name (main(global_config, **settings), the PasteDeploy convention from the cookiecutter project). Its secret comes from the environment and the process refuses to start without it, so a missing secret is found at deployment time and not at the first login. And its cookies are configured for HTTPS: SignedCookieSessionFactory takes secure, httponly and samesite arguments.

The first example writes a small project into a temporary directory: the package, a static file, and a production.ini. A project generated by the cookiecutter has the same shape; the only difference is the first line of [app:main], which is use = egg:bookshelf_shelves there (an entry point of an installed package) and is use = call:bookshelf_shelves:main here because the temporary directory is not installed. Everything else on this page loads that file. The secret is generated with secrets.token_hex() and passed through an environment variable, which stands for what systemd, Docker or Kubernetes would provide.

import json
import os
import pathlib
import secrets
import signal
import socket
import subprocess
import sys
import tempfile
import textwrap
import time
import urllib.request

root = pathlib.Path(tempfile.mkdtemp(prefix="shelves-deploy-"))
package = root / "bookshelf_shelves"
(package / "static").mkdir(parents=True)
(package / "static" / "shelves.css").write_text("body { font-family: sans-serif; }\n")

(package / "__init__.py").write_text(textwrap.dedent('''\
    import os

    from pyramid.config import Configurator
    from pyramid.session import SignedCookieSessionFactory
    from pyramid.settings import asbool


    def main(global_config, **settings):
        secret = os.environ.get("BOOKSHELF_SESSION_SECRET")
        if not secret:
            raise RuntimeError("BOOKSHELF_SESSION_SECRET must be set")
        with Configurator(settings=settings) as config:
            config.set_session_factory(
                SignedCookieSessionFactory(
                    secret,
                    secure=asbool(settings.get("bookshelf.cookie_secure", "true")),
                    httponly=True,
                    samesite="Lax",
                )
            )
            config.add_static_view("static", "static", cache_max_age=3600)
            config.add_route("healthz", "/healthz")
            config.add_route("whoami", "/whoami")
            config.add_route("visit", "/visit")
            config.scan(".views")

Waitress

Waitress is the server named in every generated .ini file (use = egg:waitress#main). It is a pure-Python, multi-threaded WSGI server with no dependencies, it runs on Windows as well as Unix, and its documentation describes it as production quality. It has one process and a pool of threads (threads, default 4), so it uses one core for Python code at a time; scale it by running several processes behind the proxy, or choose Gunicorn if you want the server to manage the processes for you. It does not terminate TLS, which is the first reason it always sits behind a proxy in production.

Behind a Proxy: trusted_proxy

Behind a reverse proxy, the connection that reaches Waitress comes from the proxy, so by default the application sees the proxy’s address, scheme http and whatever Host the proxy forwards. The fix is Waitress’s own proxy support, which is the reason production.ini above has five trusted_proxy* lines. With trusted_proxy set to the proxy’s address, Waitress rewrites REMOTE_ADDR, HTTP_HOST and wsgi.url_scheme from the trusted headers and removes the others. With the address of anybody else, the same headers are ignored and cleared.

The next example starts pserve twice on the same file, once with the loopback address as the trusted proxy (the test client plays the proxy) and once with a proxy address that is not the sender. The request carries forged-looking forwarding headers in both runs.

Waitress finishes the request on SIGINT (the Python interrupt, what Ctrl+C sends) but dies at once on SIGTERM, the signal that systemd, Docker and Kubernetes send first; the connection is cut and the client sees an error. Gunicorn’s master treats SIGTERM as the graceful stop (workers get graceful_timeout seconds to finish) and SIGQUIT as the quick one. This is a practical reason to prefer Gunicorn, or a wrapper that converts the signal, in containers and under supervisors, and the reason the proxy should retry idempotent requests on another upstream during a rolling deployment.

Forking and Connection Pools

Pre-fork servers (Gunicorn with preload_app, uWSGI by default) import the application once and fork the workers, so anything created at import time is shared by every worker: open sockets, file descriptors, random-number generator state and connection pools. The Community Cookbook has a short page on this ("Forked and Threaded Servers") and its main example is still right: an SQLAlchemy Engine that has opened a connection before the fork hands the same socket to every worker, and two workers speaking on one database connection corrupt each other. A Pyramid application that connects only inside requests (the usual request.dbsession pattern of the SQLAlchemy page) is safe, because pools connect lazily; one that connects while the application is created, to check the schema or to warm a cache, must reset the pool in every child. SQLAlchemy’s documentation gives the recipe: engine.dispose(close=False) in the child, which discards the inherited connections without closing the sockets that the parent still uses.

The example builds a small application with an engine that connects during import, runs it under Gunicorn with --preload, and has the hook report the pool before and after.

    with engine.connect() as connection:  # connects before the fork, as a start-up check would
        connection.exec_driver_sql("select 1")


    def app(environ, start_response):
        start_response("200 OK", [("Content-Type", "application/json")])
        return [json.dumps({"status": "ok", "pid": os.getpid()}).encode()]
    '''))

The three non-obvious lines are the ones the tutorial explains. nginx in Front

The proxy does what the Python server should not: TLS, slow clients, limits, static files, compression and the Host/X-Forwarded-* headers. The configuration below is the one used with the Docker example later in the page. It was validated with nginx -t in an nginx 1.29 container; the proxy-to-Pyramid path was checked with the servers and header combinations of the earlier examples.

upstream shelves_app {
    server shelves-app:8000;
    keepalive 16;
}

server {
    listen 80;
    server_name books.example.org;
    client_max_body_size 10m;

    # Static files straight from disk, with the cache lifetime the application asked for.
    location /static/ {
        alias /srv/shelves/static/;
        expires 1h;
        access_log off;
    }

    location / {
        proxy_pass http://shelves_app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }
}

Source: nginx: ngx_http_proxy_module

Source: Gunicorn: Deploy

Line by line: Host $host passes the public host name, which Pyramid uses for every absolute URL (route_url, redirects, resource_url); the Waitress documentation asks for exactly this header. X-Forwarded-Proto $scheme tells the application that the client used HTTPS, so that links and secure cookies come out right. keepalive together with proxy_http_version 1.1 and an empty Connection header reuses upstream connections. location /static/ serves the files without Python; the alias directory must hold the same files as the package’s static directory (mount or copy them into the proxy’s file system at deployment time), and the URL prefix must match the path of the static view. The generated project’s static view is /static, which is why no rewrite is needed. With a sync Gunicorn worker the proxy is not optional: the worker handles one request at a time, so a client that sends its request slowly would occupy it, and nginx buffers the request until it is complete.

X-Forwarded-For and request.client_addr

One line of that configuration is deliberate and different from many copies found on the web: X-Forwarded-For $remote_addr replaces the header, where the usual $proxy_add_x_forwarded_for appends to whatever the client sent. The reason is request.client_addr. Pyramid’s request is a WebOb request, and client_addr returns the first address of X-Forwarded-For if the header exists, and REMOTE_ADDR only if it does not. The official API page carries a warning about it: a client can put any value there, and the value can be trusted only if the server sits behind a proxy that controls the header. Behind Waitress with trusted_proxy, the server rewrites REMOTE_ADDR and clears the header, and the property is safe. Behind Gunicorn or uWSGI, which leave X-Forwarded-For alone, it is only as good as the proxy’s configuration. The next example makes the difference visible with a request that arrives with a forged first entry.

forged = {"X-Forwarded-For": "198.51.100.77", "X-Forwarded-Proto": "https", "Host": "books.example.org"}

stop(proc)
print("gunicorn", {key: seen[key] for key in ("scheme", "client_addr", "remote_addr")})

# What nginx does with "X-Forwarded-For $remote_addr": the client-supplied value is replaced.
overwritten = dict(forged, **{"X-Forwarded-For": "203.0.113.9"})
port = free_port()
proc = start([BIN / "gunicorn", "--paste", "production.ini", "--bind", f"127.0.0.1:{port}", "--no-control-socket"], port)

stop(proc)
print("gunicorn behind a proxy that overwrites the header", {key: seen[key] for key in ("client_addr", "remote_addr")})

Virtual Hosting and URL Prefixes

Sometimes the application does not live at the root of the site: https://example.org/bookshelf/ is the application, https://example.org/ is something else. The WSGI answer is SCRIPT_NAME, the part of the path that the server has consumed before the application starts; Pyramid’s route_url, route_path, static_url and resource_url prepend it, and routing matches against PATH_INFO, the rest. The official Virtual Hosting chapter describes the two situations, and there are several ways to set SCRIPT_NAME, each with a different trust model.

Read the outputs against the table. rutter mounts the application and builds prefixed URLs from the path, and it does not look at X-Forwarded-Host: the generated URL keeps the Host it received, which is the official chapter’s warning. Process Supervision

Nothing in the topology restarts itself. A supervisor starts the services at boot, restarts them when they crash, stops them with the signal the server expects, and collects their logs. On a Linux host that is systemd. In a container the runtime plays that role and the server runs in the foreground (see Docker and Kubernetes). A unit for the Gunicorn setup of this page runs as an unprivileged user, reads the secrets from an environment file owned by root with mode 0600, stops with SIGTERM (the graceful signal measured above) and reloads with SIGHUP, which makes the master start new workers and retire the old ones gracefully. It was not run: the verification host is not Linux.

TimeoutStopSec is a little longer than graceful_timeout, so that systemd does not kill the workers before Gunicorn does. pserve is not a supervisor: the Cookbook’s "nginx + pserve + supervisord" recipe combines it with Supervisor, which still works, but a unit file gives the same with less. A --reload start never belongs in a unit, and the process must stay in the foreground.

Docker and Kubernetes

A container image of a Pyramid application is a Python image, the installed package, production.ini and Gunicorn as the entry point; pserve and Waitress are fine for a single replica but do not stop gracefully on SIGTERM. The generic material (layers, multi-stage builds, non-root users, image scanning) is covered by the Dockerfile fundamentals, multi-stage builds and image best practices pages. The Pyramid-specific points are few: install the package into the image and not from the source tree, so that the entry point egg:bookshelf_shelves resolves; install Gunicorn there and not the debug toolbar; keep the secrets out of the image; and point --worker-tmp-dir at memory.

The Dockerfile below builds wheels in a first stage and installs them into a slim image that runs as a numeric non-root user (Kubernetes' runAsNonRoot check needs a numeric id). Sizing, Reloading and Zero-Downtime Deploys

The sizing rules are the generic ones of the Flask deployment page, and nothing in Pyramid changes them, but the Pyramid-specific parts are worth stating.

  • Workers times threads equals concurrency. A Gunicorn sync worker serves one request at a time; with --threads 4 it serves four. A Waitress process serves threads requests at a time. Python’s global interpreter lock means that threads help only while a request waits (database, network); CPU-bound work needs processes.

  • Every worker has its own pool. The connection pool of the SQLAlchemy page is per process, so workers x (pool_size + max_overflow) connections must fit in the database’s connection limit, before counting replicas.

  • Keep requests short. Gunicorn kills a worker that does not answer within timeout; Waitress does not, and a hung request holds one of the few threads. Long work belongs to a task queue, not a view.

  • Reload with a signal, not a restart. kill -HUP on the Gunicorn master starts new workers and retires the old ones gracefully; without preload_app the application code is reloaded too, with it only the configuration is. A change of the .ini file takes effect on that reload. pserve --reload and hupper are development tools.

  • Roll replicas, not processes. In containers the orchestrator replaces replicas one by one (the Kubernetes Deployment above), and the health probe decides when a new one receives traffic.

  • Warm up after the fork, not before. Template compilation caches and other lazy state fill on the first request; a readiness probe on a lightweight view followed by one request to the heaviest page moves the cost off the user.

Pitfalls

  • *:6543 in production.ini listens on every interface. Combined with a proxy, that leaves a second, unprotected entrance. Bind to loopback, a socket or a private address.

  • Waitress dies on SIGTERM. In-flight requests are cut. Use Gunicorn (or a wrapper) under systemd, Docker and Kubernetes, or accept the cut and let the proxy retry.

  • request.client_addr trusts X-Forwarded-For. Overwrite the header in the proxy, use Waitress’s trusted_proxy, or use request.remote_addr.

  • Gunicorn and the scheme. X-Forwarded-Proto is honoured only from forwarded_allow_ips. In a container whose proxy is not on loopback, links come out http:// and secure cookies break until the variable is set; * fixes it and is safe only if nothing else can reach the port.

  • PrefixMiddleware trusts whoever talks to it. It is a convenience behind a proxy, not a security boundary.

  • A prefix that only the proxy knows. If SCRIPT_NAME is not set by the server, the application, or a filter, generated links ignore the prefix.

  • Secrets in the image or in production.ini. Environment variables and mounted files only; the application refuses to start without them.

  • PYRAMID_* variables overrule the file. Audit the environment, as above.

  • The toolbar in the production dependencies. Keep pyramid_debugtoolbar in a development extra and out of the production image; it must never appear in pyramid.includes of a production file.

  • pserve --daemon. Pyramid 1.8 (2016) removed the daemon commands and options of pserve (--daemon, --pid-file, --log-file, --stop-daemon, --status); older tutorials still show them. Run the process in the foreground under a supervisor.

  • Preloading and pools. Reset database pools in post_fork.

  • Static files through the application. A Pyramid static view works, but a Python worker that serves a stylesheet is a worker that cannot serve a page. Let the proxy do it.

Recent Changes and Outdated Material

  • Pyramid 2.0 (2021) and 2.1 (2026-03-11). Nothing in either release changes how a Pyramid application is deployed; the loaders and the entry points are those of 1.x. Pyramid 2.1 still imports pkg_resources and pins setuptools below 82, so a production image that installs Pyramid must not upgrade setuptools past that.

  • Waitress 3.0 (2024). clear_untrusted_proxy_headers is now true by default, which is the setting this page relies on; older documentation and tutorials still show the opt-in form.

  • Gunicorn 26. The control socket is opened by default; the examples and the Dockerfile switch it off. The project’s documentation moved to gunicorn.org; some old docs.gunicorn.org addresses found in older pages no longer resolve.

  • The Community Cookbook was last built in 2022; read it with the table above in hand. Serving a WSGI application such as Pyramid from Tornado’s WSGIContainer is possible but not a way to deploy it; see Tornado: WSGI Interoperability.

  • Python versions. Pyramid 2.1 needs Python 3.10 or newer, while the generated pyproject.toml still says requires-python >= 3.8; build images on a current Python.

Summary

  • A Pyramid deployment is a hardened production.ini, a WSGI server that loads it, and a reverse proxy; the same file serves pserve, Gunicorn --paste, uWSGI --paste and a pyramid.wsgi script.

  • Keep the debug switches off, in the file and in the environment, keep secrets in the environment, and make the application refuse to start without them.

  • Waitress is the default server and has its own proxy support (trusted_proxy); Gunicorn stops gracefully and is the usual choice in containers; both want a reverse proxy.

  • request.client_addr trusts X-Forwarded-For; overwrite the header in the proxy.

  • SCRIPT_NAME decides URL prefixes: set it with Waitress, rutter, PrefixMiddleware or mod_wsgi, and know whom each trusts.

  • Pools must be reset after a fork; pods and processes must be stopped with the graceful signal.

  • ASGI is a wrapper, not a feature; the Cookbook’s deployment recipes are partly obsolete.
