Python Pyramid

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This section is written against Pyramid 2.1 (released 2026-03-11, Python 3.10 or newer), checked on 2026-10-07. That release follows 2.0 (2021) and 2.0.2 (2023), so Pyramid is a mature, slow-moving project: releases are rare, the PyPI status is "Mature", and the companion packages (pyramid_tm, pyramid_jinja2, pyramid_debugtoolbar, pyramid_retry) change even less often. That stability is part of the appeal, and it also means that many tutorials and books still describe the 1.x APIs that 2.0 deprecated. Every page says which version introduced or removed a feature, and What’s Changed & Migration collects the differences.

What Pyramid is

Pyramid is a general-purpose Python web framework from the Pylons Project. It began as repoze.bfg in 2008, inherits ideas from Zope, and was renamed Pyramid in 2010. Its motto is "start small, finish big": a complete application fits in one file, and the same configuration system scales to large applications assembled from reusable pieces.

Three ideas set it apart from Flask and Django:

  • Explicit, conflict-checked configuration. A Configurator records what you register (routes, views, predicates, tweens, security policy). Pyramid detects conflicting registrations at startup and resolves them with a clear rule, which makes config.include() a safe composition mechanism for large applications and add-ons.

  • Two ways to find a view. URL dispatch maps patterns such as /api/books/{id} to routes, and traversal walks a tree of resources, so the URL /shelves/ada/dune becomes a context object that carries its own permissions. Both can be combined in one application.

  • Security as a first-class layer. A single security policy decides who the user is and what they may do, and per-object access control lists are inherited down the resource tree.

Pyramid is a WSGI and synchronous framework. There are no async views in 2.1, so concurrency comes from the WSGI server’s threads or workers, and the Pyramid Community Cookbook describes an ASGI wrapping recipe for the rare case where it is needed. For frameworks built around an event loop, see the ref:backend/tornado/introduction-and-architecture.adoc[Tornado] and ref:backend/fastapi/index.adoc[FastAPI] sections.

This section is for developers who:

  • know Python and want a framework that stays out of the way for small services but offers fine-grained authorization, hierarchical resources and extensibility for large ones

  • are coming from Flask or Django and want to understand what Pyramid does differently, and when it is the better choice (see Introduction & Architecture, the Flask introduction and the Django introduction)

  • maintain an existing Pyramid application and need the 2.x idioms (security policy, pyproject.toml, SQLAlchemy 2.0, JSON-only sessions) rather than the patterns in older tutorials

The Bookshelf Shelves scenario

Every example builds one small original application, Bookshelf Shelves, so the pages fit together instead of being isolated snippets:

  • public shelves owned by users, addressed by traversal (/shelves/{shelf}/{book}), with access control lists inherited from the shelf: owners edit, everyone else reads

  • a JSON API under URL dispatch (/api/books/{id}) using the json renderer and __json__

  • SQLAlchemy 2.0 with pyramid_tm and Alembic (the cookiecutter sqlalchemy backend) and Jinja2 templates through pyramid_jinja2

  • a security policy built on AuthTktCookieHelper, CSRF protection on forms, and Deform and Colander forms

  • English and Spanish translations, a timing tween, the debug toolbar in development, WebTest functional tests, and Waitress or Gunicorn deployment
