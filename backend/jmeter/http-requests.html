HTTP Requests

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page was written against Apache JMeter 5.6.3, the latest release on 2026-10-14. It runs on Java 8 or later, and Java 17 or later (21 recommended) is the baseline used throughout this section. JMeter 6.0 is not released: the changes planned for it in xdocs/changes.xml on the master branch (several of which touch the HTTP sampler, listed at the end of this page) are described as planned, not as shipped behaviour. HTTP/2 needs the community bzm-http2 plugin from the JMeter Plugins catalogue (Plugins Manager 2.0); everything else on this page is core JMeter. Field names, menu paths, properties and defaults come from the component reference, the properties reference and, where those are silent, the 5.6.3 source code, which is then named as the source. The books that cover the HTTP sampler (Sai Matam and Jagdeep Jain, Pro Apache JMeter, chapters 3 and 5, on JMeter 3.0; Bayo Erinle, JMeter Cookbook, chapter 8, on JMeter 2.11) still offer the HttpClient3.1 implementation, which no longer exists.

The HTTP Request sampler is the element most JMeter plans are built around. It sends one HTTP or HTTPS request, waits for the response and records a sample: the status, headers, body, timings and byte counts that every listener, assertion and report works from. Around it sit configuration elements that supply what the sampler leaves out: the HTTP Request Defaults (protocol, host, port, timeouts), the HTTP Header Manager, the HTTP Cookie Manager, the Keystore Configuration and the DNS Cache Manager. This page sets up an HTTP test from scratch against the Bookshelf API, explains every field of the sampler and of its defaults, covers HTTPS, client certificates, DNS and bandwidth emulation, and ends with the first run of bookshelf-load.jmx in CLI mode. Headers, cookies, sessions and authentication have their own page, HTTP Sessions, Headers, Cookies & Authentication; JSON bodies, GraphQL and SOAP are on REST, JSON, GraphQL & SOAP APIs.

JMeter works at the protocol level. It is not a browser: it sends the requests it is told to send, does not run JavaScript and does not render pages, so its timings are server and network timings, not page-load times as a user experiences them. Choosing between JMeter and the browser-driven tools is covered in Choosing a Tool.

Where the HTTP elements sit in a test plan

A minimal HTTP test needs a Thread Group, one HTTP Request Defaults, the managers the requests need and the samplers. Defaults and managers placed directly under the Thread Group (or the Test Plan) apply to every sampler below them; placed under one sampler, they apply to that sampler only. The scoping and merging rules are explained on Test Plan Elements, Execution Order & Scoping.

Test Plan  bookshelf-load.jmx
└── Thread Group "Borrowers"            threads, ramp-up, loops from properties
    ├── HTTP Request Defaults           http, ${__P(host,localhost)}, ${__P(port,8080)}, timeouts
    ├── HTTP Header Manager             Accept: application/json
    ├── HTTP Cookie Manager             one per thread group
    ├── DNS Cache Manager               optional: per-thread DNS, static hosts
    ├── Keystore Configuration          optional: client certificates (mTLS)
    ├── GET /api/books                  HTTP Request: method and path only
    │   └── (assertions, extractors for this request)
    └── GET /api/books/{id}             HTTP Request

When a thread reaches a sampler, JMeter merges the configuration in scope into a copy of the sampler, runs the pre-processors and timers, sends the request and hands the result to post-processors, assertions and listeners. The sequence for one HTTP sample:

sequenceDiagram participant T as Thread (virtual user) participant S as HTTP Request sampler participant D as HTTP Request Defaults participant H as Header Manager participant C as Cookie Manager participant API as Bookshelf API participant R as SampleResult T->>S: next sampler in tree order D-->>S: fill empty fields: protocol, host, port, timeouts, implementation T->>T: pre-processors, then timers (think time) H-->>S: request headers (Accept, Authorization) C-->>S: Cookie header for cookies matching the URL S->>API: GET /api/books?query=java API-->>S: 200 + response headers + JSON body S->>C: store Set-Cookie values for later requests S->>R: elapsed, latency, connect time, code, bytes, headers, body R-->>T: post-processors, assertions, listeners

Source: Elements of a Test Plan (User Manual) and HTTP Request (Component Reference)

The timings in the result are defined in the glossary: elapsed time runs from just before the request is sent to just after the last byte of the response is received; latency from just before sending to just after the first part of the response arrives; connect time is the time to open the connection, including the TLS handshake. Connect time is not subtracted from latency, and it is only non-zero when a new connection is opened, so with keep-alive most samples of a thread show a connect time of 0.

Source: Glossary (User Manual)

Setting up an HTTP test from scratch

The steps below create the first version of bookshelf-load.jmx: one Thread Group, the HTTP Request Defaults pointing at the local Bookshelf API, and one GET /api/books request. The Bookshelf API runs on localhost:8080, started with Docker Compose as described in Compose for Local Development; its endpoints are the ones built on REST APIs.

  1. Start JMeter in GUI mode (bin/jmeter), which is meant for building the plan, not for running load. Choose File → New, select Test Plan and set Name to Bookshelf load.

  2. Right-click Test Plan and choose Add → Threads (Users) → Thread Group. Name it Borrowers and set Number of Threads to ${__P(threads,1)}, Ramp-up period to ${__P(rampup,1)} and Loop Count to ${__P(loops,10)}. The fields are explained on Thread Groups: Concurrent Users & Ramp-up.

  3. Right-click Borrowers and choose Add → Config Element → HTTP Request Defaults. On the Basic tab set Protocol to http, Server Name or IP to ${__P(host,localhost)} and Port Number to ${__P(port,8080)}. On the Advanced tab set Timeouts (milliseconds) to Connect 5000 and Response 30000, and leave the implementation as HttpClient4.

  4. Right-click Borrowers and choose Add → Config Element → HTTP Header Manager. Add a row Name Accept, Value application/json.

  5. Right-click Borrowers and choose Add → Config Element → HTTP Cookie Manager. The Bookshelf API is stateless (JWT), but adding the manager now costs nothing and is the normal arrangement for a user that keeps cookies.

  6. Right-click Borrowers and choose Add → Sampler → HTTP Request. Name it GET /api/books, leave Protocol, Server Name or IP and Port Number empty (they come from the defaults), set Method to GET, Path to /api/books, and on the Parameters tab add a row with Name query, Value java and URL Encode? selected.

  7. Save with File → Save as bookshelf-load.jmx.

Because host and port are properties with defaults, the same plan runs against localhost:8080 by default and against any other environment with -Jhost=... -Jport=..., without editing the file. Property names threads, rampup, duration, host and port are used for the same purposes on every page of this section.

Source: Building a Web Test Plan (User Manual)

The Defaults path is not a prefix

The HTTP Request Defaults Path field is the default for the whole path, used only by samplers whose path is empty; it is not a prefix added in front of the sampler paths. The component reference states this explicitly. To keep a common prefix such as /api in one place, define it as a variable on the Test Plan (User Defined Variables: basePath = ${__P(basePath,/api)}) and write the sampler paths as ${basePath}/books and ${basePath}/books/${id}. Variables, properties and the __P function are explained on Properties, Variables & Functions.

Source: HTTP Request Defaults (Component Reference)

How a field gets its value

flowchart TD A[Sampler field] --> B{Set on the sampler?} B -- Yes --> V[Use the sampler value] B -- No --> C{Set on an HTTP Request Defaults in scope?} C -- Yes --> W[Use the nearest defaults value] C -- No --> X[Built-in default: HTTP, port 80 or 443, no timeout, jmeter.httpsampler]

Two exceptions follow from the GUI. Check boxes have only two states, so the component reference explains that an unselected box means "use the default" and a selected one means "on": a later element can switch an option on, but cannot switch it off. And a Path that starts with http:// or https:// is a full URL: the protocol, server and port fields, including those from the defaults, are then ignored.

Source: HTTP Request Defaults (Component Reference)

Every field of the HTTP Request

The HTTP Request panel has two tabs, Basic and Advanced. The tables list every field in JMeter 5.6.3 with the English GUI label, the property stored in the .jmx file and what the component reference says about it. The defaults column gives the value of a newly added sampler.

Basic tab: web server and request

GUI field .jmx property Default Meaning

Name, Comments

testname attribute, TestPlan.comments

HTTP Request

The name is the sample label in every listener and report, so give each request a stable, readable name such as GET /api/books. Do not put changing values (IDs, variables) in it, or the report gets one row per value.

Protocol [http]

HTTPSampler.protocol

empty (http)

http, https or file. Empty means the defaults or http. The file protocol is for testing purposes only.

Server Name or IP

HTTPSampler.domain

empty

Host name or IP address, without http://. Required unless HTTP Request Defaults provide it or the path is a full URL. If a Host header is set in a Header Manager, it is used as the virtual host name.

Port Number

HTTPSampler.port

empty (80, or 443 for https)

Port of the web server. All port values are treated equally: a sampler without a port uses the defaults' port.

Method

HTTPSampler.method

GET

GET, POST, HEAD, TRACE, OPTIONS, PUT, DELETE, PATCH (PATCH not with the Java implementation). With HttpClient4 the WebDAV methods COPY, LOCK, MKCOL, MOVE, PROPFIND, PROPPATCH, UNLOCK, REPORT, MKCALENDAR and SEARCH are also available, plus the methods listed in httpsampler.user_defined_methods.

Path

HTTPSampler.path

empty

Path to the resource, for example /api/books. Query parameters go in the Parameters tab. A path starting with http:// or https:// is used as the full URL (protocol, server and port are then ignored, and so are parameters for GET and DELETE). The path is not encoded apart from spaces becoming %20, so unsafe characters must be encoded by hand to avoid a URISyntaxException.

Content encoding

HTTPSampler.contentEncoding

empty (UTF-8 since 5.6.1)

The character encoding used for the request (for POST, PUT, PATCH and FILE). It is not the Content-Encoding header (gzip and so on), which is set in a Header Manager.

Redirect Automatically

HTTPSampler.auto_redirects

cleared

Lets the HTTP library follow redirects itself, so they are invisible to JMeter and do not appear as samples. Only for GET and HEAD; the HttpClient sampler rejects it for POST and PUT. Cookies and headers are only sent with the first request, which breaks cross-host redirects.

Follow Redirects

HTTPSampler.follow_redirects

selected

Only effective when Redirect Automatically is off. JMeter follows the redirect itself and records each hop as a sub-sample; the parent sample takes its URL and data from the final response, its elapsed time and bytes from all hops and its latency from the first response.

Use KeepAlive

HTTPSampler.use_keepalive

selected

Sends Connection: keep-alive and reuses connections. It works properly with HttpClient4; with the Java implementation connection reuse is not under JMeter’s control.

Use multipart/form-data

HTTPSampler.DO_MULTIPART_POST

cleared

Sends the parameters as multipart/form-data instead of application/x-www-form-urlencoded. Since 3.1 only POST supports multipart requests and file upload.

Browser-compatible headers

HTTPSampler.BROWSER_COMPATIBLE_MULTIPART

cleared

With multipart, suppresses the per-part Content-Type and Content-Transfer-Encoding headers and sends only Content-Disposition, as browsers do.

Parameters tab

HTTPsampler.Arguments (HTTPArgument rows)

empty table

Rows of Name, Value, URL Encode?, Content-Type and Include Equals?. For GET and DELETE they become the query string; for POST and PUT they are sent in the body (form-encoded, or multipart). A row without a name is ignored for methods other than POST and PUT, which is a way to make a parameter optional through a variable.

Body Data tab

HTTPSampler.postBodyRaw = true and one unnamed argument

empty

The raw request body, typically JSON or XML. Each line is sent with CRLF appended except the last. Available when the request has only unnamed parameters or none; switching from Parameters converts them, and switching back is only possible after clearing the body.

Files Upload tab

HTTPsampler.Files (HTTPFileArg rows: File.path, File.paramname, File.mimetype)

empty table

Files to send, with File Path, Parameter Name and MIME Type. A file makes the request multipart. For POST, PUT and PATCH, a single file with an empty parameter name is sent as the whole body, with MIME Type as its Content-Type. See File upload.

Source: HTTP Request (Component Reference)

Advanced tab: client, timeouts, resources, source address and proxy

GUI field .jmx property Default Meaning

Client implementation: Implementation

HTTPSampler.implementation

empty

HttpClient4, Java, or empty. Empty uses the HTTP Request Defaults, then the jmeter.httpsampler property, then HttpClient4. See HttpClient4 or Java.

Timeouts (milliseconds): Connect

HTTPSampler.connect_timeout

empty (no timeout)

Milliseconds to wait for a connection to open. A failed connect is recorded with a connect time equal to the time to fail.

Timeouts (milliseconds): Response

HTTPSampler.response_timeout

empty (no timeout)

Milliseconds to wait for a response. It applies to each wait for data: a response sent in several chunks can take longer overall than the timeout. Use a Duration Assertion to fail slow responses as a whole (see Assertions).

Retrieve All Embedded Resources

HTTPSampler.image_parser

cleared

Parses HTML responses and downloads the images, scripts, style sheets (and resources referenced from them), frames and background images they reference, as sub-samples of this request.

Parallel downloads. Number

HTTPSampler.concurrentDwn, HTTPSampler.concurrentPool

cleared, 6

Downloads embedded resources over a pool of concurrent connections of the given size, as browsers do.

URLs must match

HTTPSampler.embedded_url_re

empty

If set, a regular expression that embedded URLs must match to be downloaded (for example only resources from the application’s own host).

URLs must not match

HTTPSampler.embedded_url_exclude_re

empty

If set, a regular expression for embedded URLs to skip (for example images, or third-party analytics).

Source address: type and value

HTTPSampler.ipSourceType, HTTPSampler.ipSource

IP/Hostname, empty

HttpClient implementation only. Overrides the local address the request is sent from ("IP spoofing"); the JMeter host needs several addresses. The type is IP/Hostname, Device (first address of an interface such as eth0), Device IPv4 or Device IPv6. The property httpclient.localaddress sets one address for all HttpClient requests instead.

Proxy Server: Scheme, Server Name or IP, Port Number, Username, Password

HTTPSampler.proxyScheme, proxyHost, proxyPort, proxyUser, proxyPass (all with the HTTPSampler. prefix)

empty

A proxy for this request, without http:// in the host. The port is required when a host is given. The password is stored unencrypted in the .jmx file, so read it from a property (${__P(proxyPass)}) instead of typing it.

Optional Tasks: Save response as MD5 hash?

HTTPSampler.md5

cleared

Stores the 32-character MD5 hash of the response instead of the body. Intended for large responses; it saves memory but makes the body unavailable to extractors and content assertions.

Source: HTTP Request (Component Reference)

The Proxy Server panel’s Scheme field and the Optional Tasks grouping are labels of the 5.6.3 GUI (resource bundle messages.properties); the component reference table lists the other proxy fields and the MD5 option without those headings.

Parameters, Body Data and content encoding

The method decides where parameters go. The table summarises the rules of the component reference’s "Parameter Handling" and "Method Handling" notes.

Method Parameters tab Body

GET, DELETE

Appended to the URL as the query string.

DELETE may carry a body through Body Data; GET normally does not.

POST

Sent in the body, form-encoded or (with Use multipart/form-data or files) multipart.

Body Data, unnamed parameter values concatenated, or a single file without a parameter name.

PUT, PATCH

Not used as form parameters: the body must be given another way.

Body Data, unnamed parameter values, or a single file with an empty parameter name.

GET, DELETE, PUT and PATCH requests that carry a body need a Content-Type: add a Header Manager under the sampler and set it there. For POST, the property http.post_add_content_type_if_missing decides whether JMeter adds application/x-www-form-urlencoded when the header is missing; it defaults to false since 5.0 (Bug 60190).

URL encoding. Selecting URL Encode? on a parameter is almost always right: values with spaces, non-ASCII characters or reserved characters such as &, =, +, ? or / must be encoded. A value that is already encoded (copied from a browser address bar) must not be encoded twice.

Content encoding. Since 5.6.1 an empty Content encoding means UTF-8: parameter names, values and file names with Unicode characters are sent correctly without setting anything. The property sampleresult.default.encoding, which decides how a response without a charset is decoded, also defaults to UTF-8 since 5.6.1. Plans written for older versions sometimes set UTF-8 explicitly; that is harmless.

Redirects

Two check boxes control redirects, and they behave very differently:

Follow Redirects (default) Redirect Automatically

Who follows

JMeter’s sampler code.

The underlying HTTP library.

Visible in results

Yes: each hop is a sub-sample of the parent sample (label-0, label-1 and so on since 5.0).

No: only the final response is seen.

Cookies and headers on later hops

Handled by JMeter for every hop (Cookie Manager, Header Manager).

Sent only with the first request.

Methods

All.

GET and HEAD only (HttpClient rejects POST and PUT).

Timing

Parent elapsed time and bytes include all hops; latency comes from the first response.

One sample with the library’s total time.

Related properties: httpsampler.max_redirects (default 20) limits the redirects followed in one sequence, and JMeter collapses /../segment in redirect URLs unless httpsampler.redirect.removeslashdotdot=false. Keep-alive and connection reuse

With Use KeepAlive and HttpClient4, a thread reuses its connection from one request to the next, as a browser or an HTTP client library in a microservice would. The server then sees a fixed number of long-lived connections (one or a few per virtual user) and most samples show a connect time of 0. Without keep-alive every request opens a new TCP connection and, with HTTPS, performs a new TLS handshake: that measures connection setup as much as the API, costs CPU on both sides and can exhaust ephemeral ports on the load generator.

Connection lifetime is tuned with properties of the HttpClient4 implementation:

Property Default Meaning

httpclient4.time_to_live

60000

Absolute TTL of a connection in milliseconds; it is never reused beyond it.

httpclient4.validate_after_inactivity

4900

Check a connection that has been idle longer than this before reusing it. Keep it at least 150 ms below httpclient4.time_to_live.

httpclient4.idletimeout

0

Idle timeout applied when the server sends no Keep-Alive timeout header.

httpclient4.retrycount

0

Retries for idempotent methods; httpclient4.request_sent_retry_enabled=true retries all methods.

httpclient.reset_state_on_thread_group_iteration

true

Closes connections and resets the SSL state at the start of each Thread Group iteration, so each iteration behaves as a new user. The Thread Group’s Same user on each iteration option controls the same behaviour per group.

Retries hide errors: a request that fails once and succeeds on retry is recorded as one successful sample. Keep the retry count at 0 for load tests unless a load balancer that drops idle connections makes it unavoidable.

Source: Properties Reference (HTTPClient4) and Properties Reference (SSL configuration)

File upload

Files go in the Files Upload tab: one row per file with File Path (relative to the .jmx directory, or absolute), Parameter Name (the form field name) and MIME Type (guessed from the file when empty). With at least one file the request becomes multipart/form-data; any other parameters become parts of the same form. Multipart and file upload work with POST only. For PUT or PATCH, or for a POST whose body is just the file, leave Parameter Name empty: the file is then sent as the whole body, with MIME Type as Content-Type.

Load-generator cost of uploads. JMeter reads the file for every request, so 50 threads uploading a 2 MB file at one upload per second each send about 100 MB/s, which saturates a 1 Gbit/s network link (about 125 MB/s) before the server does anything. Keep files small, or make sure the network and disk of the generator are part of the capacity check. In a distributed run, the files must exist on every load generator, like CSV data files.

Embedded resources

Retrieve All Embedded Resources makes JMeter behave a little like a browser for HTML pages: it parses each HTML (and CSS) response and fetches the referenced resources. The parsers are configured with HTTPResponse.parsers (default htmlParser wmlParser cssParser); the HTML parser is LagartoBasedHtmlParser by default (htmlParser.className), and httpsampler.max_frame_depth (default 5) limits frame nesting. Resources are recorded as sub-samples of the page; httpsampler.ignore_failed_embedded_resources=true stops a failed resource from failing the parent, and httpsampler.embedded_resources_use_md5=true keeps only their size and MD5.

Filters keep the download to what a real browser of the application would fetch from the system under test. To fetch only resources from the Bookshelf host and skip images in any case:

URLs must match:      https?://localhost(:8080)?/.*
URLs must not match:  .*\.(?i:svg|png|jpe?g|gif|ico)

For a JSON API, as Bookshelf is, leave the option off: there is nothing to parse, and parsing costs CPU. JMeter has no browser cache unless an HTTP Cache Manager is added, and it never executes JavaScript, so resources loaded by scripts are not fetched.

Source: HTTP Request (Component Reference) and Properties Reference (HTML Parser configuration)

Load-generator cost. Each page with embedded resources becomes many requests: a page with 30 resources and 50 users is 1 550 requests per page view. With Parallel downloads each thread uses up to the pool size (default 6) extra download threads, so 50 users can mean 300 extra threads on the generator; their keep-alive time is httpsampler.parallel_download_thread_keepalive_inseconds (default 60).

HTTPS

HTTPS needs nothing more than https in Protocol (and usually port 443 or 8443). JMeter uses the TLS implementation of the JVM (JSSE), so the protocol versions and cipher suites available are those of the Java runtime that runs JMeter.

Self-signed and untrusted server certificates

The getting-started guide states that the JMeter HTTP samplers accept all server certificates, trusted or not and whatever their validity period, to allow maximum flexibility when testing. A Bookshelf API on https://localhost:8443 with a self-signed certificate therefore works without importing anything into a trust store. This is convenient and also means a load test never detects an expired or wrong certificate: check certificates with a functional test, not with JMeter.

The one certificate error JMeter can still raise comes from the JVM’s algorithm constraints: a server certificate (or one in its chain) signed with MD2, or with a key shorter than 1024 bits, fails with "Certificates does not conform to algorithm constraints". The component reference describes relaxing jdk.certpath.disabledAlgorithms in the JVM’s java.security file; on a test environment the better fix is a proper certificate.

Source: Getting Started (SSL Encryption) and HTTP Request (Component Reference)

SSL Manager

The SSL Manager is the GUI way to choose a client certificate: Options → SSL Manager opens a file chooser; a file with the .p12 extension is read as PKCS12, anything else as a JKS keystore, and JMeter asks for the password (which it assumes is also the private key’s password). If the keystore has several keys, the first is used, and there is no way to choose another. Because it is interactive, the SSL Manager is useful for trying a certificate while building a plan; CLI runs use the system properties and the Keystore Configuration shown above. The same section of the reference explains that a private CA can be trusted for the whole JVM by importing it into a jssecacerts file in the JRE’s lib/security folder, which is read before cacerts; JMeter’s own HTTP samplers do not need it, since they accept all server certificates.

Source: SSL Manager (Component Reference)

DNS Cache Manager

By default JMeter resolves host names through the JVM, which caches the result. Behind a DNS-based load balancer or CDN, every virtual user then talks to the same address and only one server of the cluster gets the load. The DNS Cache Manager (Add → Config Element → DNS Cache Manager) resolves names separately for each thread and keeps the result in its own cache, independent of the JVM and operating system caches. It can also map names to addresses like an /etc/hosts file, so a plan can use the real host name while the requests go to a test server.

It belongs at the root of the Thread Group or Test Plan, never under a single sampler, and it works only with the HttpClient4 implementation.

Bandwidth throttling

A load generator on the same network as the server downloads responses far faster than users on mobile networks do, which keeps connections short and hides the effect of slow clients on server threads and connection pools. JMeter can emulate slow connections with two properties, in characters (bytes) per second; 0, the default, disables throttling:

# user.properties: emulate about 1 Mbit/s per connection (1 000 000 / 8 = 125 000 bytes/s)
httpclient.socket.http.cps=125000
httpclient.socket.https.cps=125000

Worked numbers: a Bookshelf search response of 24 KB takes about 24 000 / 125 000 = 0.19 s to read at that rate, on top of the server time. With 50 threads and a server time of 50 ms, each thread completes a request about every 0.24 s instead of every 0.05 s, so the closed-model throughput falls from about 1 000 to about 210 requests per second, while the server holds about four times as many open responses at any moment. The HttpClient4 implementation supports both properties; the Java implementation only the HTTPS one.

Source: Properties Reference (Apache HttpClient common properties) and HTTP Request (Component Reference, Emulating slow connections)

Bandwidth throttling with these properties is the technique described in the JMeter Cookbook (chapter 8) and Pro Apache JMeter (chapter 10); it is unchanged in 5.6.3.

HTTP/2

Core JMeter speaks HTTP/1.1 (httpclient.version defaults to 1.1); it has no HTTP/2 support. HTTP/2 load comes from the community BlazeMeter - HTTP Plugin (Plugins Manager id bzm-http2, version 3.2.0 in the catalogue, covering HTTP/1.1, HTTP/2 and HTTP/3; the older Java 8 bzm-http2-legacy is deprecated), which adds its own sampler. It is installed through the Plugins Manager like any plugin, and is covered with the other plugins later in this section. jmeter-plugins.org is an independent community catalogue, not an Apache project.

Worked example: the first Bookshelf test in CLI mode

The plan built above, bookshelf-load.jmx, now runs as a smoke test: one user, ten iterations of GET /api/books?query=java. GUI mode is for building and debugging; tests run in CLI mode.

  1. Start the Bookshelf API (docker compose up -d in its project) and check it answers:

    curl -s -o /dev/null -w '%{http_code}\n' 'http://localhost:8080/api/books?query=java'

  2. Run the plan in CLI mode with its property defaults (1 thread, 1 s ramp-up, 10 loops, localhost:8080):

Worked numbers for this profile: 50 threads over 60 s start 0.83 threads per second. Load-generator cost of HTTP requests

The HTTP sampler is cheap per request compared with the server’s work, but a few options multiply its cost:

  • Response bodies in memory. Every sample keeps its full response until post-processors, assertions and listeners have used it. Large downloads with many threads consume heap; httpsampler.max_bytes_to_store_per_request truncates what is stored (default 0, no truncation) and Save response as MD5 hash? keeps only a hash. Extractors and content assertions then see the truncated data or none.

  • Embedded resources and parallel downloads. Many requests and extra threads per page view (see above).

  • TLS without keep-alive. A full handshake per request is CPU-intensive on the generator as well as on the server. Per-thread SSL contexts are realistic; a reset per iteration (httpclient.reset_state_on_thread_group_iteration=true) adds a handshake per iteration and user.

  • Per-thread DNS. The DNS Cache Manager adds lookups per thread and iteration.

  • Listeners that keep responses. View Results Tree in a load test keeps every response in memory; the listeners page explains which listeners are safe.

The JMeter best practices are to run load in CLI mode, with few listeners and assertions and results saved as CSV; they apply to every HTTP plan.

Source: Best Practices and Properties Reference (Miscellaneous configuration)

Pitfalls

  • Host or port typed in every sampler. Moving to another environment then means editing every request. Put them in HTTP Request Defaults, read from properties.

  • Expecting the Defaults path to be a prefix. It is a full default path; use a variable for a prefix.

  • Variable values in sampler names. GET /api/books/${id} as a name creates one report row per ID; keep the variable in the Path and a fixed name such as GET /api/books/{id}.

  • Redirect Automatically on a POST. HttpClient rejects it; use Follow Redirects.

  • A body without Content-Type. PUT, PATCH and bodies on GET or DELETE need a Header Manager setting it; servers answer 415 Unsupported Media Type otherwise.

  • Double encoding. Selecting URL Encode? on a value that is already percent-encoded encodes it twice.

  • No timeouts. Without connect and response timeouts a hung server keeps threads waiting forever and the closed model stalls; set them in the defaults.

  • Retries switched on. They hide errors and distort response times.

  • Treating HTTP success as functional success. A 200 is not proof that the right data came back: add assertions.

  • Embedded resources against an API or a CDN. Parsing JSON for resources wastes CPU; fetching third-party resources loads systems you do not own. Filter with URLs must match.

  • Testing certificates with JMeter. The samplers accept every server certificate, so certificate problems go unnoticed.

  • Proxy passwords and keystore passwords in the plan. The proxy password is stored unencrypted; read secrets from properties or environment variables.
