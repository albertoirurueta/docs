Assertions

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page was written against Apache JMeter 5.6.3 (latest release on 2026-10-14; it runs on Java 8 and later, Java 17 or later is recommended), with the differences planned for JMeter 6.0 noted where they matter. JMeter 6.0 is not released: the planned changes come from xdocs/changes.xml on the master branch, need Java 17 or later (Java 21 recommended) and are described as planned, not as shipped behaviour. The JSR223 Assertion examples use the Groovy engine bundled with 5.6.3 (Groovy 5 is planned for 6.0). The books on the market target JMeter 2.11 to 3.0: they assert on JSON through the jp@gc JSON Path plugin, which core JMeter replaced with the JSON Assertion in 4.0, and they predate the JMESPath and XPath2 assertions (both 5.2). Every field name, property and rule on this page is taken from the official component reference, best practices and properties reference; where the documentation is silent (JMX property names, defaults, the extra Size Assertion fields), the 5.6.3 source code is the reference, and that is said explicitly.

A sampler only knows whether the transport worked: an HTTP Request is successful when it gets a response whose status is not 4xx or 5xx, whatever the body says. A Bookshelf search that returns 200 OK with an empty list because the search index is down, or a login that returns 200 with an error page from a proxy, would count as a success and pull the response-time statistics down with fast, wrong answers. Assertions close that gap: they inspect each result and mark the sample failed when it is not what the user would have needed. This page covers what assertions are, which samples they apply to, every core assertion type, how failures show up in results, and what each type costs on the load generator, because in a load test every assertion runs once per sample, thousands of times per minute. The running example is the Bookshelf API journey used throughout the section: log in, search, view a book, create a loan, view the loan.

What an assertion does

An assertion is a test element that receives the SampleResult of a sampler after the sampler and its post-processors have run, performs a check, and returns an assertion result. If the check fails, the sample is marked as failed and the assertion’s failure message is attached to it. Nothing else changes: the response time, bytes and response code are recorded exactly as measured. The failed sample then counts as an error everywhere results are aggregated (the summariser’s Err: column, the success column of the JTL file, the dashboard error rate and Errors tables).

The official definition is short: assertions perform additional checks on samplers and are processed after every sampler in the same scope. Three rules follow from it.

  • Order. Within the processing of one sampler, assertions run after the post-processors and before the listeners. An assertion can therefore check a variable that a JSON Extractor has just set, and the listeners always see the final pass or fail status.

  • Scope. An assertion applies to every sampler in its scope: a child of a sampler checks only that sampler; an assertion at the Thread Group or controller level checks every sampler below it.

  • Parent sample only, by default. Unless documented otherwise, assertions are not applied to sub-samples (embedded resources, the samples generated by a Transaction Controller, the messages of a Mail Reader), only to the parent sample. Scoped assertions offer an Apply to choice to change that.

After all the assertions of a sampler have run, JMeter updates the variable ${JMeterThread.last_sample_ok} to true or false. The Thread Group’s Action to be taken after a Sampler error treats a failed assertion exactly like a failed sample: Continue, Start Next Thread Loop, Stop Thread, Stop Test or Stop Test Now.

flowchart TD S[Sampler runs and produces a SampleResult] --> P[Post-processors in scope, e.g. JSON Extractor] P --> A{Assertions in scope} A -- all pass --> OK[Sample stays successful] A -- one fails --> F[Sample marked failed, failure message attached] OK --> V[JMeterThread.last_sample_ok = true] F --> W[JMeterThread.last_sample_ok = false] W --> T{Thread Group: action after sampler error} T -- Continue --> L T -- Start Next Thread Loop / Stop Thread / Stop Test --> L V --> L[Listeners and the results file receive the sample]

Source: Assertions (Component Reference) and Elements of a Test Plan: Assertions (User Manual)

The full ordering of config elements, pre-processors, timers, post-processors, assertions and listeners, and the scoping rules with worked examples, are on Test Plan Elements, Execution Order & Scoping.

Failure versus error

An assertion result carries two flags. A failure means the check ran and the response did not satisfy it ("expected to contain `token`"). An error means the check itself could not run properly, for example a Response Assertion whose regular expression does not compile ("Bad test configuration") or a JMESPath expression that cannot be parsed. Both make the sample unsuccessful. The distinction matters when reading results: a sudden 100 percent error rate on one sampler right after editing an assertion is usually a broken pattern, not a broken server.

Adding an assertion in the GUI

  1. Select the sampler the check belongs to, for example POST /api/auth/login.

  2. Right-click it and choose Add → Assertions → Response Assertion (or any other assertion in that menu). The shortcut Ctrl+3 adds a Response Assertion to the selected element.

  3. Fill in the fields described below and give the assertion a descriptive name, because the name is what appears next to a failure in the View Results Tree and the Assertion Results listener.

  4. Run the plan once with one thread, open the View Results Tree and check the Assertion result view of each sample before moving to load.

Source: Assertions (Component Reference) and Hints and Tips (User Manual)

Apply to: main sample, sub-samples or a variable

Assertions that support scoping show an Apply to: group. In 5.6.3 these are the Response, Duration, Size and XPath2 assertions (the scope panel is part of their GUIs in the source; the component reference lists it for Response and Size). The JSON, JMESPath, MD5Hex, XML Schema and JSR223 assertions always look at the main sample; a JSR223 script can read sub-samples itself with prev.getSubResults(), which returns an array (empty if there are none).

The assertion checks the content of the named variable instead of the response; the variable name goes in the text field next to the option.

The variable option is the cheap way to assert on something an extractor has already pulled out. For Bookshelf, the JSON Extractor of the login request stores the token in token; a Size Assertion with Apply to: JMeter Variable Name to use = token can check that the extracted value is not empty without scanning the body again. Note that the Size Assertion parses the variable as a number when this option is used (5.6.3 source), so for a string length use a Response Assertion on the variable instead.

Response Assertion

The Response Assertion is the general-purpose check: it compares one field of the request or the response with a list of patterns. It has been in JMeter since the beginning, and most load tests need nothing else.

Pattern Matching Rules

How each pattern is compared with the field:

  • Contains: the text contains the regular expression;

  • Matches: the whole text matches the regular expression;

  • Equals: the whole text equals the string, case-sensitive;

  • Substring: the text contains the string, case-sensitive (default since 2.11).

Two check boxes modify the rule: Not inverts the result of every pattern, and Or passes the assertion if any one pattern passes (the default is AND: all patterns must pass).

Yes

Assertion.test_type, a bit set: Matches 1, Contains 2, Not 4, Equals 8, Substring 16, Or 32 (e.g. Substring + Not = 20)

Patterns to Test

The list of patterns, one per row. Add, Add from Clipboard and Delete manage the rows. Each pattern is tested separately; with AND, the first failing pattern stops the evaluation. One assertion with three patterns behaves like three assertions with one pattern each.

Yes

Asserion.test_strings (sic), a collectionProp of stringProp

Custom failure message

Replaces the generated failure message. Since 4.0.

No

Assertion.custom_message

Source: Response Assertion (Component Reference)

The property name Asserion.test_strings (sic) is the spelling JMeter really writes in .jmx files.

Regular expression flavour. Contains and Matches use Perl5-style regular expressions (the Jakarta ORO engine by default). Patterns are written without delimiters (Price: \d+, not /Price: \d+/). By default the pattern is in multi-line mode: . does not match a newline, while ^ and $ match at the start and end of any line; \s does match a newline. Inline flags change that: (?i) ignores case, (?s) lets . match a newline, and (?is) does both. The property jmeter.regex.engine (default oro) switches to the JDK java.util.regex engine when set to any other value; the properties reference says the JMeter team intends to make the JDK engine the default in a later version, but the planned 6.0 change list does not include it. The JDK engine caches compiled patterns (jmeter.regex.patterncache.size, default 1000).

Equals diffs. When an Equals comparison fails, the failure message shows the received text and the expected text with the differing section marked. Three properties tune it: assertion.equals_section_diff_len (characters shown per section, default 100), and assertion.equals_diff_delta_start and assertion.equals_diff_delta_end (the markers, default [[[ and ]]]).

Empty fields. If the field to test is empty, the assertion fails with "Response was null", unless Not is selected, in which case it always passes.

Example: the login response

The Bookshelf login (POST /api/auth/login) must return 200 and a JSON body with a token. Two Response Assertions, both children of the sampler, check it: one on the response code with Equals, one on the body with Contains and a custom message so that failures group cleanly in the dashboard.

<HTTPSamplerProxy guiclass="HttpTestSampleGui" testclass="HTTPSamplerProxy" testname="POST /api/auth/login">

  <stringProp name="HTTPSampler.method">POST</stringProp>
  <boolProp name="HTTPSampler.postBodyRaw">true</boolProp>
  <elementProp name="HTTPsampler.Arguments" elementType="Arguments">
    <collectionProp name="Arguments.arguments">
      <elementProp name="" elementType="HTTPArgument">
        <boolProp name="HTTPArgument.always_encode">false</boolProp>
        <stringProp name="Argument.value">{"username":"${username}","password":"${password}"}</stringProp>
        <stringProp name="Argument.metadata">=</stringProp>
      </elementProp>
    </collectionProp>
  </elementProp>
</HTTPSamplerProxy>

JSON Assertion

The JSON Assertion parses the response as JSON, evaluates a JSONPath expression (Jayway JsonPath syntax), and checks that the path exists and, optionally, that its value equals an expected value, matches a regular expression or is null. It arrived in core JMeter 4.0, donated from the jmeter-plugins jp@gc JSON Path Assertion that the books use.

Add → Assertions → JSON Assertion (class JSONPathAssertion, GUI JSONPathAssertionGui).

Expected Value

The value to compare with, or the regular expression. Without the regular-expression option, it is parsed as a JSON value, so 2 matches the number 2. To match an empty array, use [].

No

The value at the path must be null.

No

Source: JSON Assertion (Component Reference)

The evaluation has three steps: parse the body (fail if it is not JSON), find the path (fail if it is absent), then compare the value if requested. If the path returns an array, each element is compared and the assertion passes if any one matches; a dictionary is converted to a string before comparison.

Indefinite paths. A path such as $.items[*].id or $..id is indefinite: it returns a list. Without an expected value, older versions passed even when the list was empty. Since 5.5, the assertion fails if an indefinite path returns an empty list and no expected value is set. With an expected value, the list is searched for a match.

Example: search returns results

The Bookshelf search must return at least one item for a term from search-terms.csv:

<JSONPathAssertion guiclass="JSONPathAssertionGui" testclass="JSONPathAssertion" testname="Search: at least one item">
  <stringProp name="JSON_PATH">$.items[0].id</stringProp>
  <stringProp name="EXPECTED_VALUE"></stringProp>
  <boolProp name="JSONVALIDATION">false</boolProp>
  <boolProp name="EXPECT_NULL">false</boolProp>
  <boolProp name="INVERT">false</boolProp>
  <boolProp name="ISREGEX">true</boolProp>
</JSONPathAssertion>
<hashTree/>

The definite path $.items[0].id exists only if the list has a first element, which is a sharper check than the indefinite $.items[*].id. A second example checks a value: on GET /api/loans/{id}, the path $.status with Additionally assert value ticked, Match as regular expression ticked and the expected value ACTIVE|PENDING accepts either state, because the regular expression must match the whole value.

Duration Assertion

The Duration Assertion fails any response that took longer than a given number of milliseconds. It is the per-request service-level check: "every search must answer within 800 ms".

Add → Assertions → Duration Assertion (class DurationAssertion, GUI DurationAssertionGui).

Field Meaning Required JMX property

Name

Descriptive name shown in the tree.

No

testname attribute

Apply to

Main sample, sub-samples, both, or a variable. Present in the 5.6.3 GUI (the component reference table omits it).

No

Assertion.scope

Duration in milliseconds

The maximum elapsed time of each response. A value of 0 disables the check (5.6.3 source). Variables and functions are accepted.

Yes

DurationAssertion.duration

Source: Duration Assertion (Component Reference)

The time compared is the sample’s elapsed time, the same value that appears in the elapsed column. For an HTTP Request that downloads embedded resources, the parent sample’s time includes them.

Example: a search SLA that can change per run

<DurationAssertion guiclass="DurationAssertionGui" testclass="DurationAssertion" testname="Search under SLA">
  <stringProp name="DurationAssertion.duration">${__P(search_sla_ms,800)}</stringProp>
</DurationAssertion>
<hashTree/>
jmeter -n -t bookshelf-load.jmx -l results.jtl -Jthreads=50 -Jrampup=60 -Jduration=660 -Jsearch_sla_ms=600

Use it with care in load tests. A Duration Assertion turns slow responses into errors. That is what a pass-or-fail CI gate needs, but it hides a distinction the analysis needs: the dashboard then shows a high error rate where the real problem is latency, and response-time percentiles still include the failed samples. For the load profile, prefer to record everything and judge latency from percentiles and APDEX in the dashboard (see Performance Testing Fundamentals); keep the Duration Assertion for smoke tests and for hard per-request limits that the business really treats as failures.

Source: Duration Assertion (Component Reference) and Properties Reference

XPath2 Assertion

The XPath2 Assertion parses an XML response and passes if an XPath 2.0 expression matches, or, for a boolean expression such as count(//*error)=2, returns true. It was added in 5.2 as a faster replacement for the XPath Assertion, and it uses Saxon. Use it for SOAP and other XML APIs; SOAP itself is sent with the HTTP Request sampler, as described on REST, JSON, GraphQL & SOAP APIs.

The cost of assertions on the load generator

An assertion runs on the load generator, in the thread of the sampler it checks, once per sample. Its cost is added to the work every virtual user does between two requests; it does not add to the measured elapsed time of the sample, but it does consume CPU and memory that the generator needs to keep its threads on schedule. The best-practices page lists "Use as few Assertions as possible" among its ways to reduce resource requirements, next to running in CLI mode and using few listeners.

Worked numbers

The Bookshelf load profile runs 50 threads, a 60 s ramp-up and a scheduler duration of 660 s (a 10-minute hold). With the section’s 3 s average think time (Z = 3 s) and a typical 0.2 s response, each thread issues one request about every 3.2 s, so at full load the plan produces about 50 / 3.2 ≈ 15.6 samples/s, or about 15.6 × 600 ≈ 9,400 samples during the hold.

  • Two Response Assertions per sampler (code and a substring) mean about 31 checks/s. On a 4 KB search body, the substring scan reads about 15.6 × 4 KB ≈ 62 KB/s: negligible on any machine.

  • A JSON Assertion on every sampler means about 16 JSON parses per second, each producing a short-lived object tree. Still modest at this rate, but it scales with the body: if search pages were 200 KB, that would be about 3 MB/s of JSON parsed and as much garbage for the collector.

  • Moving the same plan to an arrival-rate profile of 500 samples/s multiplies everything by about 32. Parsing the whole body several times per sample (a JSON Assertion, a JMESPath Assertion and a JSR223 Assertion that parses it again) is then a real share of the generator’s CPU, and it competes with the threads that should be sending requests on time. That is when the "assert just enough" rule below stops being a style choice.

Watch the load generator’s own CPU and heap during the run. If CPU stays above about 80 percent or garbage collection pauses grow, the generator is distorting the measurement, whatever the assertions report.

Assert just enough

The goal of assertions in a load test is not to prove the application correct (the functional tests did that) but to make sure every sample counted as a success really was a usable answer. That leads to a short policy:

  1. Check the status on every request. A Response Assertion on Response Code at the Thread Group level, or a scoped one per controller, costs almost nothing and catches redirects to login pages and error responses that the sampler treats as success (2xx and 3xx).

  2. Check one content marker per request. One substring or one definite JSON path that only a correct response contains: "token" for login, $.items[0].id for search, "status":"ACTIVE" for a loan. Not the whole document.

  3. Prefer the cheapest assertion that answers the question. Size over content when "not empty or truncated" is the question; Substring over Contains when no regular expression is needed; Response Code over body when the API’s codes are reliable.

  4. Do not parse twice. If a JSON Extractor already pulls a value out, assert on the extracted variable (Response Assertion with Apply to: JMeter Variable Name to use) instead of parsing the body again. Extractors are covered on Correlation & Extractors.

  5. Keep deep checks in the smoke profile. Schema validation, page-size checks, Equals on whole bodies and JSR223 rules run once per sampler with one thread, before the load run, in the same .jmx file if needed (enable them with an If Controller on a property, or keep them in a separate Thread Group that only runs in the smoke profile).

  6. Use stable custom failure messages, so that the dashboard groups failures into a handful of meaningful rows.

  7. Disable debugging assertions and listeners (Compare Assertion, HTML Assertion, Assertion Results, View Results Tree) before running at load.

Scoping an assertion to one sampler

The most common assertion bug is scope: an assertion placed at the wrong level of the tree checks samplers it was never meant for.

Thread Group
├── Response Assertion "200 OK"          <- applies to every sampler in the Thread Group
├── POST /api/auth/login
│   └── Response Assertion "token"       <- applies to the login sampler only
├── Simple Controller "Catalogue"
│   ├── JSON Assertion "items present"   <- applies to BOTH samplers below
│   ├── GET /api/books?query=
│   └── GET /api/books/{id}              <- fails: a book detail has no $.items
└── POST /api/loans

The JSON Assertion under the Catalogue controller applies to both catalogue requests, and the book detail request fails because its body has no items. The fix is to move the assertion under GET /api/books?query= as a child. To apply an assertion to exactly one sampler, make it a child of that sampler. Controllers are useful for scoping a check to a group of samplers on purpose, as on Logic Controllers & Transactions, where the Catalogue controller carries a shared 200 OK check.

Transaction Controllers. An assertion placed under a Transaction Controller in its default (non-parent) mode applies to the samplers inside it; the transaction sample itself is generated after them and fails if any child failed. In Generate parent sample mode, the children become sub-samples, and only scoped assertions with Sub-samples only or Main sample and sub-samples see them.

Embedded resources. For an HTTP Request that downloads embedded resources, a Response Assertion with Main sample only checks only the main page. A Main sample and sub-samples status check turns any missing image into a failed page, which is usually not what a backend load test wants.

Source: Elements of a Test Plan: Scoping Rules (User Manual) and Assertions (Component Reference)

Pitfalls

  • Regular expression in a Substring rule, or the reverse. Substring and Equals take plain text; \d+ there is looked for literally. Contains and Matches take regular expressions; a . or ? in a plain-text pattern then means something else.

  • Matches instead of Contains. Matches must match the whole field. A pattern that works with Contains usually fails with Matches on a full JSON body.

  • Ignore Status on a later assertion. It wipes the failures recorded by the assertions before it. Put it first.

  • Regex default on in the JSON assertions. Match as regular expression is ticked by default; an expected value such as 1.5 or a+b is then a pattern, not a literal. Untick it for literal comparisons.

  • Indefinite JSONPath without an expected value. It only proves the list exists (and, since 5.5, is not empty), not that it contains what you expect.

  • ${...} inside a cached JSR223 script. Only the first value is compiled in; every later sample is checked against it. Use vars.get() or Parameters.

  • Assertions in the wrong place. An assertion at the Thread Group level checks every sampler, including setup requests and JSR223 samplers that have no HTTP code. See the scoping section above.

  • Asserting on large bodies at high rates. Parsing or scanning megabytes per sample makes the generator the bottleneck; see the cost table.

  • Duration Assertions in the load profile. They mix latency and errors; analyse latency from percentiles instead.

  • Failure messages with variable text. They scatter one problem over many dashboard rows.
