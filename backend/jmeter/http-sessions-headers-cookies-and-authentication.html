HTTP Sessions, Headers, Cookies & Authentication

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page was written against Apache JMeter 5.6.3 (latest release on 2026-10-14; it runs on Java 8 and later, Java 17 or later is recommended), with the differences planned for JMeter 6.0 noted where they matter. JMeter 6.0 is not released: the planned changes come from xdocs/changes.xml on the master branch, need Java 17 or later (Java 21 recommended) and are described as planned, not as shipped behaviour. No plugin is needed: the four managers and the URL Re-writing Modifier ship with core JMeter. The HTTP Request sampler implementations discussed are the two that remain in 5.6.3, HttpClient4 (Apache HttpComponents 4.5.x) and Java. The books on the market target JMeter 2.11 to 3.0; the managers they describe still exist, but defaults such as the cookie policy and pre-emptive authentication have changed since (listed at the end of the page). Every field name, property and rule in this page is taken from the official component reference, properties reference and user manual, and, where the documentation is ambiguous, from the 5.6.3 source code of the Apache JMeter project.

A browser keeps state between requests without being asked: it stores the cookies a server sets and sends them back, it remembers which resources it already has, it adds the same headers to every request and it answers authentication challenges. JMeter does none of that unless the test plan says so. An HTTP Request sampler on its own sends exactly what it is configured with, and every thread starts from nothing. The managers are configuration elements that give each virtual user that browser-like memory: the HTTP Header Manager (headers), the HTTP Cookie Manager (cookies), the HTTP Cache Manager (conditional and cached GETs) and the HTTP Authorization Manager (server authentication). For applications that carry the session in the URL instead of a cookie, the HTTP URL Re-writing Modifier does the same job.

This page describes each element field by field, then explains how several of them in scope are combined, and ends with a complete worked example for the Bookshelf API: log in once per virtual user, extract the JWT from the login response and send it as a bearer token on every later request. It builds on Test Plan Elements, Execution Order & Scoping and Properties, Variables & Functions, and pairs with HTTP Requests. The OAuth and JWT background (what a bearer token is, how it is obtained and refreshed) is in the OAuth Reference and is not repeated here.

Several Header Managers: merged in 5.6.3

The official documentation contradicts itself here. The Elements of a Test Plan chapter of the user manual says that the Header Manager, Cookie Manager and Authorization Manager are not merged: if more than one is in scope only one is used, with no way to say which. The HTTP Header Manager entry of the component reference says that JMeter supports multiple Header Managers, that their entries are merged to form the list for the sampler, and that an entry whose name matches an existing header replaces it.

The component reference describes the 5.6.3 behaviour. In the 5.6.3 source, the HTTP sampler merges every Header Manager it receives into the one it already has (HeaderManager.merge), while for the Cookie, Cache and Authorization managers it keeps only one and logs a warning that the existing manager was superseded. The configuration elements are handed to the sampler starting with the one closest to it, and the merge keeps a header that is already present, so in practice:

  • every header name from every Header Manager in scope is sent once;

  • when two managers define the same header name (compared case-insensitively), the manager closest to the sampler wins, so a sampler-level manager overrides a Thread Group-level one, exactly like a field of HTTP Request Defaults;

  • a header with an empty value in the closer manager does not remove the header: it replaces its value with an empty one, as the component reference warns.

The test-plan chapter sentence is therefore accurate for the Cookie and Authorization managers but out of date for the Header Manager. As on the scoping page, keep the layering simple (one Header Manager per scope) and confirm the headers that were really sent in the Request tab of View Results Tree, which shows the request headers, or in the jmeter.log debug output of the sampler.

Cost and pitfalls

The Header Manager is cheap: the headers are a short list resolved per request, and a merge copies that list. The practical problems are about correctness rather than load:

  • An unresolved variable is sent literally. If ${token} has not been set yet (the login failed, or the header is in scope of the login request itself), JMeter sends the text Bearer ${token}. The server answers 401, which looks like a server problem in the report. Scope the Authorization header so that the login request does not get it, give the JSON Extractor a recognisable default value, and assert on the login response.

  • Content-Type for files and forms. A Thread Group-wide Content-Type: application/json also reaches multipart uploads and form posts, where the sampler builds its own content type. Override it in a closer manager for those samplers or keep the JSON content type at the level of the samplers that send JSON.

  • Do not copy browser headers blindly. Recorded plans carry Cookie, Authorization and caching headers in Header Managers. Those values belong to the recording session; the Cookie and Cache managers and an extracted token must produce them at run time instead. The recording page later in this guide explains which headers the recorder drops.

  • Secrets in the plan. A literal token or API key in a Header Manager is saved in the .jmx file. Read it from a property (${__P(apiKey)}, set with -JapiKey=... on the command line) or from a CSV file instead.

HTTP Cookie Manager

The Cookie Manager has two functions. First, it stores and sends cookies like a browser: when a response contains a cookie, the manager stores it and sends it on later requests to the same site. Each thread has its own cookie storage area, so a site that keeps the session in a cookie gets one session per virtual user. Cookies received this way do not appear in the manager’s table; they are visible in the request and response headers in View Results Tree. Second, a plan can type cookies into the manager by hand; those cookies are shared by every thread and are created with an expiry time far in the future.

The manager checks that a received cookie is valid for the URL that set it, so cross-domain cookies are not stored. Cookies with null (empty) values are ignored, and a cookie name must be unique in the table: a second row with the same name replaces the first.

Cost, pitfalls and the 6.0 change

Memory grows with the number of threads times the cookies each thread holds; for an API that sets one or two cookies this is negligible. The points that matter are:

  • No Cookie Manager, no session. Without one, a cookie-based login works for the login request and every later request is anonymous. Most "everything after login fails" reports in a new plan come from a missing Cookie Manager.

  • Hand-typed cookies are global. A session cookie copied from a browser into the table makes every thread share one session, which is neither realistic nor usually allowed by the server.

  • More than one Cookie Manager in scope. Only one is used, there is no way to choose which, and a cookie stored in one manager is not available to another. Keep one per Thread Group.

  • Planned for 6.0: expired cookies stop being sent. The 6.0 change log (on master, not released) lists as an incompatible change that the Cookie Manager no longer sends cookies after their expiry time; in 5.6.3 and earlier they kept being sent indefinitely. A long soak test that outlives a session cookie therefore starts failing with authentication or session errors in 6.0 unless the plan logs in again or refreshes the session. Design soak tests with re-authentication now, and they will behave the same on both versions.

Source: HTTP Cookie Manager (Component Reference) and changes.xml on master (planned 6.0)

HTTP Cache Manager

The Cache Manager adds browser-like caching to the HTTP requests in its scope. Each virtual user thread has its own cache, which holds up to 5000 entries by default with a least-recently-used eviction policy.

How it works, according to the component reference:

  1. When a sample succeeds (a 2xx response code), the manager saves the Last-Modified and Etag values (and the expiry, when relevant) for the URL.

  2. Before the next request to that URL, the sampler looks for an entry in the cache. If there is one, it sets the conditional headers (If-Modified-Since and If-None-Match).

  3. If Use Cache-Control/Expires header when processing GET requests is selected, the stored Cache-Control / Expires value is also checked against the current time. For a GET whose entry has not expired, the sampler returns immediately without contacting the server, as a browser would.

  4. A Cache-Control: no-cache response is stored as already expired, so it always produces a conditional GET. For any other Cache-Control value, max-age gives the lifetime; without it, Expires is used; without both, the lifetime is derived from Last-Modified and the response Date as in RFC 2616 section 13.2.4.

When the document has not changed since it was cached, or its expiry is in the future, the response body is empty, which can break assertions that check the body.

When to use it, and what it costs

For a site test with embedded resources (images, scripts, style sheets), the Cache Manager is what keeps a returning user from downloading every resource again, and leaving it out overstates the load. For a JSON API such as Bookshelf, it matters only if the API sends validators (ETag, Last-Modified) or freshness headers and real clients honour them. Many APIs send Cache-Control: no-store or nothing, and then the manager only adds work.

Worked numbers. The cache is per thread, so the worst-case number of entries is threads × max size: 50 threads × 5000 = 250,000 entries in the load generator’s heap. In practice the number of entries per thread is the number of distinct cacheable URLs a user requests. A Bookshelf user who draws from 200 search terms and views up to 300 books creates at most 200 + 300 = 500 entries, 25,000 for 50 threads, well below the limit. Raising the maximum to cache everything for a site with thousands of resources multiplies heap use by the thread count, so adjust -Xmx (the HEAP variable) accordingly, as the component reference advises.

Reporting pitfall. With the default RETURN_NO_SAMPLE, a fresh cache hit produces no sample, so the sample count and throughput in the report drop while users keep "using" the page. That is realistic for server load, but it makes the request count in the report lower than the iteration count suggests. Choose RETURN_200_CACHE if the report must show every logical request.

Cost and pitfalls

Pre-emptive Basic adds a header and nothing else. Digest and challenge-based Basic add a 401 round trip whenever the client has no cached authentication state, which shows up as extra samples or extra latency. Kerberos adds the ticket exchange with the KDC; with Clear auth on each iteration? every iteration repeats it, which loads the KDC as well as the system under test. Other points:

  • It is not for form logins or tokens. A login form or POST /api/auth/login is a normal sampler; the session it creates lives in a cookie (Cookie Manager) or a token (extractor plus Header Manager).

  • Base URL mismatch. A Base URL with https while the requests use http, or with a host name while the requests use an IP address, never matches, and the requests go out without credentials.

  • Passwords in clear. Anything typed into the table is saved in the .jmx file and in any copy of it. Use variables.

Clearing state between iterations

A Thread Group iteration is one pass of the user journey. Whether the next pass is the same user (keeps cookies, cache and authentication) or a new one (starts clean) is a modelling decision. Since 5.2 it can be made in one place, the Thread Group’s Same user on each iteration option, which the three managers obey when their Use Thread Group configuration…​ box is selected. The reference describes the option: if selected, cookie and cache data from earlier responses are used in later iterations; if not, they are not, and a new connection is opened between iterations, which increases response times and resource use.

URL-rewriting sessions: the HTTP URL Re-writing Modifier

Why only one manager applies per sampler

The managers are configuration elements and follow the hierarchical scoping rules: a sampler collects every configuration element on the path from itself up to the Test Plan. Defaults elements (HTTP Request Defaults) are merged field by field, and so, in 5.6.3, are Header Managers. The Cookie, Cache and Authorization managers are different: a sampler can hold only one of each. When several are in scope, the 5.6.3 sampler replaces the one it has with the next one it is given and writes a warning such as Existing CookieManager ... superseded by ... to jmeter.log. Because the elements are handed over starting with the closest one, the one that survives is not the closest, which is the opposite of what most people expect, and the documentation says only that there is "no way to specify which one is used". Two practical consequences:

  • State is split. Cookies stored by one Cookie Manager are not visible to another, so a login handled by a controller-level manager and later requests handled by the Thread Group manager lose the session.

  • Overriding does not work. A Cookie or Authorization manager under one sampler cannot reliably override the Thread Group’s one, the way a Header Manager or an HTTP Request Defaults can.

The rule that follows is the one the user manual and component reference suggest: one Cookie Manager, one Cache Manager and at most one Authorization Manager per Thread Group, with all URLs the Authorization Manager must cover in its single table. If the jmeter.log of a run contains superseded by, the plan has more than one in scope.

Worked example: a JWT bearer flow for Bookshelf

The Bookshelf API authenticates with a JSON Web Token: POST /api/auth/login with a JSON body containing a user name and password returns a JSON document with the token, and every other endpoint expects it in an Authorization: Bearer <token> header. This is the common shape of a token-protected API: the JWT and the JOSE Family page describes the token itself, and Access and Refresh Tokens describes lifetimes and refresh. A real OAuth 2.0 authorization server would issue the token from its token endpoint instead (for a machine client, the client credentials grant); the JMeter side is the same: one request obtains the token, an extractor stores it, a Header Manager sends it.

Worked numbers: login once versus login every iteration

Assume one journey iteration, including think time, takes 12 s per user. During the 10-minute hold each of the 50 threads runs 600 / 12 = 50 iterations, 2,500 in total.

  • Login once per user (Once Only Controller): 50 login requests in the whole test, all during the 60 s ramp-up (about 50 / 60 ≈ 0.8 logins/s), and 0 during the hold.

  • Login on every iteration: 2,500 logins during the hold, 2,500 / 600 ≈ 4.2 logins/s on top of the other traffic. Password hashing makes a login one of the most expensive requests a service has, so this second plan measures a different system.

Neither is right in general: the workload model decides. The Bookshelf mix includes 10 % login-heavy iterations (short sessions that authenticate every time), which add 0.10 × 2,500 = 250 logins over the hold, about 0.4/s, on top of the 50 initial ones.

Token expiry in long tests

The token in this example lives 900 s (15 minutes). The 660 s load test ends before it expires, so logging in once is enough. A soak test of several hours is not: after 15 minutes every request fails with 401. Replace the Once Only Controller with an If Controller that logs in when there is no token yet or the token is older than a safety margin, and record the login time after the extraction:

// JSR223 PostProcessor under POST /api/auth/login, after the JSON Extractor
vars.put('tokenTime', String.valueOf(System.currentTimeMillis()))

If Controller condition, with Interpret Condition as Variable Expression? selected (re-login after 12 of the 15 minutes):

${__groovy(vars.get('tokenTime') == null || System.currentTimeMillis() - Long.parseLong(vars.get('tokenTime')) > 720000)}

If the server issues refresh tokens, the If Controller can call the refresh endpoint instead of logging in again; how refresh tokens work is described in Access and Refresh Tokens, and token-related failure modes in Testing and Debugging OAuth. The same design also covers the planned 6.0 Cookie Manager change for cookie-based sessions.

Element Cost on the load generator

HTTP Header Manager

A few strings per request; negligible. Many managers in scope mean a list merge per request.

HTTP Cookie Manager

Cookie parsing and matching per request; memory = threads × cookies per thread, usually small.

HTTP Cache Manager

Up to maxSize entries per thread (default 5000); the largest memory consumer of the four on a site with many resources. Saves network time when hits are served locally.

HTTP Authorization Manager

Negligible for pre-emptive Basic; an extra round trip for challenge-based schemes; Kerberos ticket exchanges, repeated per iteration when clearing is on.

HTTP URL Re-writing Modifier

Scans the previous response body for the session parameter on every request in scope.

Pitfalls

  • Missing Cookie Manager: a cookie-based session is lost after the login request.

  • More than one Cookie, Cache or Authorization manager in scope: one is silently superseded; look for superseded by in jmeter.log.

  • Assuming the closest Cookie Manager wins: it does not; only Header Managers (and Defaults) merge with the closest value winning.

  • Authorization header in scope of the login: the literal Bearer ${token} is sent; scope the Header Manager to the authenticated requests.

  • Hand-typed cookies or tokens from a browser: shared by every thread, expire mid-test, and leak into the .jmx.

  • Cache Manager on a JSON API: empty 304 bodies break body assertions, and cache hits produce no sample by default.

  • Same user on each iteration unchecked: with Use Thread Group configuration…​ selected on the managers, every iteration loses cookies and cache while variables (such as a token) survive, a mix that matches no real user.

  • Passwords in the Authorization Manager: stored unencrypted; use variables.

  • Distributed runs with URL rewriting: a stripping sample sender mode breaks the modifier.
