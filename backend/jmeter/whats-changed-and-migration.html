What’s Changed & Migration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Most of what is written about JMeter, including the three books this section draws on, describes JMeter 2.11, 2.12 or 3.0. The test-plan model has not changed since then: thread groups, samplers, config elements, timers, extractors, assertions and listeners still run in the same order and with the same scoping rules. What changed is almost everything around that model: the scripting language, the JSON and XML tooling, the way plugins are installed, how results are reported and monitored, how distributed runs are secured, and the Java version underneath. This page collects those changes in one place. It gives a timeline, a release-by-release summary, a table that maps each book idiom to its current replacement, a measured procedure for migrating an old .jmx file and a checklist for the next major version. The topic pages linked from each row carry the detail.

The page was written against Apache JMeter 5.6.3 (released 2024-01-07), the latest release on 2026-10-14. JMeter 6.0 is not released. On that date the download page offered 5.6.3, the newest tag in the apache/jmeter repository was v5.6.3-rc2, and the newest ApacheJMeter_core artifact on Maven Central was 5.6.3. The master branch declares version 6.0.0, and its xdocs/changes.xml lists what 6.0 is planned to contain. Everything said here about 6.0 is planned, not released behaviour, and may change before the release. Other versions used on this page are Java 17 or later (21 recommended; 5.6.3 itself runs on Java 8 or later), Groovy 3.0.20 as bundled with 5.6.3, JMeter Plugins Manager 2.0, jmeter-maven-plugin 3.8.0, the gRPC Request plugin 2.0.x and JMeter Java DSL 2.3. The legacy-plan runs shown below were made on a real 5.6.3 installation with Java 21.

Confirming which version is the latest.

Release dates on this page are the publication dates of the release artifacts in the Apache archive and on Maven Central. The change logs themselves do not date most releases.

A quick way to check whether a newer release exists is to ask Maven Central for the newest ApacheJMeter_core version:

curl -s https://repo1.maven.org/maven2/org/apache/jmeter/ApacheJMeter_core/maven-metadata.xml \
  | grep -E '<latest>|<release>|<lastUpdated>'

Output on 2026-10-14:

    <latest>5.6.3</latest>
    <release>5.6.3</release>
    <lastUpdated>20240107170103</lastUpdated>

Release by release

The tables below keep only the changes that alter how a plan is written, run or read. Each change links to the page that explains the element today. Dependency bumps and bug fixes are left out unless they change behaviour.

The books' baseline: 2.11 to 3.0

Version Released Changes that matter for plans written today

2.11

January 2014

The version of JMeter Cookbook. The summariser is on by default in non-GUI mode. New Transaction Controllers exclude timer and pre/post-processor time by default (see Logic Controllers & Transactions).

2.12

November 2014

The version of Performance Testing with JMeter. Adds the Critical Section Controller, JMS Priority and Expiration, SMTP timeouts and the Synchronizing Timer timeout.

2.13

March 2015

Adds the asynchronous Backend Listener with a Graphite client, the ancestor of today’s real-time monitoring (see Real-time Monitoring with Backend Listener). Test Fragments are disabled by default. The WebService(SOAP) Request is deprecated.

3.0

May 2016

The version of Pro Apache JMeter. Requires Java 7. Adds the HTML dashboard report (-e -o, -g), bundles Groovy 2.4.6 in lib, adds the JSON Path PostProcessor (renamed JSON Extractor in 3.1), moves to HttpClient 4.5.2 with SNI, changes the recorder’s default port to 8888 and adds Validate for thread groups. Deprecates the MongoDB elements (hidden from the menus) and the HttpClient 3.1 implementation, and removes the WebService(SOAP) Request.

3.1 to 3.3: Groovy first, Java 8, Log4j 2

Version Released Changes

3.1

November 2016

Groovy becomes the default JSR223 language and the __groovy function is added. The six BSF elements (Sampler, Listener, Assertion, Timer, PreProcessor, PostProcessor) are deprecated in favour of JSR223. The __jexl function is dropped (use __jexl3). The dashboard gains new graphs and ignores empty transaction samples, and the summariser ignores Transaction Controller samples. timer.factor scales the random timers. The Distribution Graph and Spline Visualizer listeners are removed.

3.2

April 2017

Requires Java 8 (Java 7 support dropped). Logging moves to SLF4J and Log4j 2 with log4j2.xml. Adds the InfluxDB client for the Backend Listener. Removes the SOAP/XML-RPC Request ("Use HTTP Request element as a replacement"), the Monitor Results listener and the HttpClient 3.1 implementation and its jar. Basic authentication becomes pre-emptive with HttpClient4. View Results Tree is capped at 500 entries.

3.3

September 2017

InfluxDB over UDP and error counts per response code, TCP Sampler latency, JDBC driver and validation-query drop-downs, the __timeShift and __RandomDate functions. _StringFromFile (one underscore) stops working.

4.0: the WorkBench goes, SSL comes

Released February 2018. This is the release that breaks the most book instructions.

Change Detail

WorkBench removed

Non-test elements (the HTTP(S) Test Script Recorder, Mirror Server, Property Display) become direct children of the Test Plan. When an old plan is loaded, JMeter moves those three elements under the Test Plan and puts any other WorkBench content in a Test Fragment called Workbench Test Fragment. Recording starts from the Recording template (see Recording & cURL Import).

RMI over SSL by default

"Since JMeter 4.0 the default transport mechanism for RMI will use SSL": create a keystore with create-rmi-keystore.sh and copy it to every node, or set server.rmi.ssl.disable=true on a trusted network. The Hold sample sender mode is removed. Distributed testing is covered later in this section, in the distributed testing page.

New core elements

Boundary Extractor, JSON Assertion (the AtlantBH JSON Path Assertion migrated from jmeter-plugins) and Precise Throughput Timer (Poisson arrivals at a constant throughput). See Correlation & Extractors, Assertions and Open Model & Throughput Control.

Safer defaults

New If Controllers interpret the condition as a variable expression, new JSR223 elements cache compiled scripts, and Loop and ForEach Controllers expose __jm__<Name>__idx.

Thread Group scheduler

The absolute Start Time and End Time fields are removed; only Duration and Startup delay remain (see Thread Groups: Concurrent Users & Ramp-up).

Other

Java 9 support, the Darcula look and feel by default, bin/setenv.sh for JVM settings, tearDown Thread Groups run after stop and shutdown by default, the plan is saved before each run, and the __digest, __dateTimeConvert, __changeCase, __isVarDefined and __isPropDefined functions.

5.0 to 5.4

Version Released Changes

5.0

September 2018

XPath2 Extractor. Test Action renamed Flow Control Action and CSS/JQuery Extractor renamed CSS Selector Extractor. Go to next iteration of Current Loop and Break Current Loop added to the Flow Control Action and the Result Status Action Handler. HTTP state (connections and SSL) is reset on each thread-group iteration with HttpClient4. Sub-results are written to CSV results files and renamed with -N suffixes. Multipart works for PUT and DELETE, and JMeter no longer adds a form Content-Type to a POST that has none (Bug 60190). The dashboard gains Total Transactions Per Second and custom graphs. Distributed runs prefix thread names with the engine host and port.

5.1

February 2019

The documentation renames non-GUI mode to CLI mode (the option is still -n). Tools → Import from cURL, Tools → Compile JSR223 Test Elements, template parameters (used by the Recording template), statistics.json next to the dashboard. 5.1.1 adds Tools → Generate HTML report.

5.2

October 2019

Same user on each iteration on the Thread Group (drives the Cookie Manager, Cache Manager and HTTP state reset). JMESPath Extractor and Assertion, XPath2 Assertion, empty Boundary Extractor boundaries, InfluxDB 2 support, the Bolt Request for Neo4j, PKCS11 keystores, Preinit Pool in the JDBC Connection Configuration. XML parsing refuses insecure XML.

5.3

May 2020

Groovy 3.0.3, listed as an incompatible change: "The update to Groovy 3 might break some old Groovy code". The default httpclient4.time_to_live goes from 2000 to 60000 ms. The dashboard gains a Median column and decimal percentiles.

5.4

November 2020

GraphQL HTTP Request (see REST, JSON, GraphQL & SOAP APIs). A Backend Listener client that sends raw results to InfluxDB. The dashboard says PASS and FAIL instead of OK and KO. cURL import handles backslash line continuations and PUT with data.

5.4.1, 5.4.2, 5.4.3

January and December 2021

5.4.2 is a fix release for CVE-2021-44228 (Log4j 2 JNDI lookups) and 5.4.3 for CVE-2021-45105. Any installation older than 5.4.3 ships a vulnerable Log4j 2 and should not be kept around for "compatibility".

5.5: the open model

Released June 2022. Adds the Open Model Thread Group (experimental), which drives arrivals from a schedule such as rate(0/sec) random_arrivals(1 min) rate(10/sec) instead of a thread count, and the experimental jmeter.regex.engine=java switch from Jakarta ORO to the JDK regular expression engine (ORO remains the default in 5.6.3). JMeter now supports Java 17, ships Log4j 2.17.2 and starts using Kotlin in core classes. The GraphQL HTTP Request accepts variables, the JSON Assertion fails on an indefinite path with an empty result, and the dashboard’s percentile estimator becomes configurable. See Open Model & Throughput Control.

5.6 to 5.6.3: the current line

Version Released Changes

5.6

June 2023

Plugins are found through Java’s ServiceLoader instead of classpath scanning, for faster start-up (see Plugins & Plugins Manager). An experimental Kotlin and Java DSL for programmatic test-plan generation (covered later in this section, in the programmatic test plans page). Caffeine replaces the LRU maps for compiled JSR223 scripts and HTTP headers. Functions are no longer cached per iteration (function.cache.per.iteration restores the old behaviour). The Open Model Thread Group no longer skips CSV rows. Recorder name templates gain #{url}, #{method}, #{scheme}, #{host} and #{port}. Groovy 3.0.17.

5.6.1

July 2023

UTF-8 becomes the default encoding of the HTTP sampler and of sampleresult.default.encoding; the recorder decodes arguments as UTF-8. Fixes 5.6 thread groups that ran endlessly in non-GUI mode.

5.6.2

July 2023

A single fix for Maven pom.xml parsing of JMeter’s artifacts.

5.6.3

January 2024

${...} expressions allowed in the Transaction Controller, Thread Group scheduler and HTTP Request check boxes; JDBCSampler.maxRows passed to Statement.setMaxRows; NullPointerException fixes for variables in the Constant and Constant Throughput Timers; Groovy 3.0.20. Java 17 is required to build JMeter, Java 8 still runs it.

There is no Groovy 4 release of JMeter: every 5.x release from 5.3 to 5.6.3 bundles Groovy 3, and the planned 6.0 jumps to Groovy 5.1.3. The bundled Groovy version per release is in Scripting with JSR223 & Groovy.

Source: Changes history (Apache JMeter), Changes (Apache JMeter) and Remote Testing (User Manual)

Migrating a book-era plan to 5.6.3

A plan saved by JMeter 2.x or 3.0 usually opens in 5.6.3, which is exactly the problem: some obsolete elements load without any error and then do nothing. The procedure below finds them before a test result is trusted.

What happens when 5.6.3 loads old elements

Three small plans with book-era elements were run on JMeter 5.6.3 (Java 21) in CLI mode. Each has one thread and one iteration, and none needs a server.

Plan contains Exit code What happened

A Debug Sampler with a BeanShell PostProcessor and a BSF PostProcessor (language groovy)

0

The plan ran and the sample passed. The BeanShell script ran. The BSF script did not: jmeter.log shows BSFException: unable to load language: groovy, logged as a warning, and the sample still counts as a success.

A SOAP/XML-RPC Request

0

"Created the tree successfully", then summary = 0: the log shows NameUpdater: Upgrading class org.apache.jmeter.protocol.http.sampler.SoapSampler to org.apache.jmeter.config.ConfigTestElement. The sampler became an empty config element and the test produced no samples.

A jp@gc JSON Path Extractor, plugin not installed

1

Problem loading XML ... CannotResolveClassException: com.atlantbh.jmeter.plugins.jsonutils.jsonpathextractor.JSONPathExtractor. Nothing ran.

The relevant lines of the first run:

bin/jmeter -n -t legacy-scripting.jmx -l legacy-scripting.jtl -j legacy-scripting.log
grep -E 'WARN|ERROR' legacy-scripting.log
Created the tree successfully using legacy-scripting.jmx
summary =      1 in 00:00:00 =   12.3/s Avg:     2 Min:     2 Max:     2 Err:     0 (0.00%)
... end of run

2026-10-14 13:31:26,571 ERROR o.a.b.BSFManager: Exception :
2026-10-14 13:31:26,581 WARN o.a.j.e.BSFPostProcessor: Problem in BSF script: org.apache.bsf.BSFException: unable to load language: groovy

The conversions come from bin/upgrade.properties, which maps removed classes (SoapSampler, WebServiceSampler, HTTPSampler2, MonitorHealthVisualizer and others) to ConfigTestElement or ObsoleteGui, and the hidden elements come from not_in_menu in bin/jmeter.properties, which in 5.6.3 lists the two MongoDB elements, the six BSF elements and the SOAP sampler GUI. The lesson: an exit code of 0 and "Created the tree successfully" do not prove that an old plan does what it did on 2.x.

Step 1: inventory the plans

Because the .jmx format is XML with one element per test element, a plain text search finds the obsolete ones. The script below reports every match with its line number and the replacement, and exits with 1 when it finds any, so it can also run in CI before the load test:

#!/usr/bin/env bash
# jmx-legacy-scan.sh: report elements in .jmx files that current JMeter removed, hides or discourages,
# or that JMeter 6.0 plans to remove or change. Usage: jmx-legacy-scan.sh plan.jmx...
set -u
rules='testclass="BSF|BSF element: deprecated in 3.1, hidden from menus; use JSR223 + Groovy
testclass="BeanShell|BeanShell element: discouraged; use JSR223 + Groovy
testclass="SoapSampler"|SOAP/XML-RPC Request: removed in 3.2, loads as an empty element; use HTTP Request
testclass="WebServiceSampler"|WebService(SOAP) Request: removed in 3.0; use HTTP Request
testclass="HTTPSampler2"|HttpClient 3.1 sampler: removed in 3.2; use HTTP Request (HttpClient4)
>HttpClient3.1<|HttpClient3.1 implementation: removed in 3.2; leave the implementation empty or HttpClient4
guiclass="MonitorHealthVisualizer"|Monitor Results listener: removed in 3.2; use Backend Listener + server metrics
testclass="WorkBench"|WorkBench: dropped in 4.0; use a Test Fragment or the Recording template
testclass="Mongo|MongoDB element: deprecated in 3.0, removal planned for 6.0; use JSR223 + MongoDB driver
testclass="com.atlantbh.jmeter.plugins.jsonutils|jp@gc JSON plugin: deprecated; use core JSON Extractor / JSON Assertion
testclass="kg.apc.jmeter.threads.SteppingThreadGroup"|Stepping Thread Group: use the Concurrency Thread Group
testclass="kg.apc.jmeter.perfmon.PerfMonCollector"|PerfMon: use Backend Listener + Prometheus/Grafana
com.mysql.jdbc.Driver|old MySQL driver class: 6.0 references com.mysql.cj.jdbc.Driver'
status=0
for plan in "$@"; do
  while IFS='|' read -r pattern advice; do
    grep -n -F -- "$pattern" "$plan" | while IFS=: read -r line _; do
      printf '%s:%s: %s\n' "$plan" "$line" "$advice"
    done
    grep -q -F -- "$pattern" "$plan" && status=1
  done <<< "$rules"
done
exit "$status"

exit=1

The class names come from bin/saveservice.properties and bin/upgrade.properties of 5.6.3 and, for the plugin elements, from the markerClass and componentClasses of their entries in the jmeter-plugins.org catalogue. Extend the list with the classes of any other plugin a plan uses.

Source: jmeter-plugins.org plugin repository and Changes history (Apache JMeter)

Step 2: open, fix and re-save in 5.6.3

  1. Install the plugins the plan needs first, with Options → Plugins Manager or with PluginsManagerCMD.sh install-for-jmx plan.jmx, so the plan can load at all (see Plugins & Plugins Manager).

  2. Open the plan with File → Open. A WorkBench is converted on load: the recorder moves under the Test Plan and other content into Workbench Test Fragment. Delete what is no longer needed.

  3. Replace each element reported by the scan, using the table above. The scripting case is the most common; it is shown next.

  4. Run Validate on each thread group (right-click the Thread Group) to execute one iteration with one thread and no pauses, and check the results in a View Results Tree that you disable again afterwards.

  5. File → Save writes the plan in the 5.6.3 format (jmeter="5.6.3" in the root element). Commit the result so the diff shows exactly what changed.

The 623 ms of the single sample includes initialising the Groovy engine and compiling the script on first use; with Cache compiled script if available ticked, later iterations reuse the compiled script. That cost is why the best-practices page recommends JSR223 with Groovy over BeanShell and why the books' interpreted scripts are the first thing to replace in a plan that runs many iterations.

Step 3: align the toolchain

  • Java. Run 5.6.3 on Java 17 or 21. That is also what 6.0 will need, so the upgrade does not change the runtime twice.

  • Every node, same versions. Distributed runs need the same JMeter, Java and plugin versions on the controller and every worker.

  • Maven builds. jmeter-maven-plugin 3.8.0 defaults to JMeter 5.6.2 (its changelog: "Default to JMeter 5.6.2"), so pin the version explicitly:

<plugin>
  <groupId>com.lazerycode.jmeter</groupId>
  <artifactId>jmeter-maven-plugin</artifactId>
  <version>3.8.0</version>
  <executions>
    <execution>
      <id>configuration</id>
      <goals>
        <goal>configure</goal>
      </goals>
    </execution>
    <execution>
      <id>jmeter-tests</id>
      <goals>
        <goal>jmeter</goal>
      </goals>

      <id>jmeter-check-results</id>
      <goals>
        <goal>results</goal>
      </goals>
    </execution>
  </executions>
  <configuration>

Step 4: re-baseline

A migrated plan is a new measuring instrument. Before comparing it with any old result, run the Bookshelf baseline profile on 5.6.3 and keep it as the new reference:

bin/jmeter -n -t bookshelf-load.jmx -Jthreads=50 -Jrampup=60 -Jduration=660 \
  -l baseline-5.6.3.jtl -e -o baseline-5.6.3-report

With 50 threads, a 60 s ramp-up and a 660 s duration, the hold at full load lasts 10 minutes. With the Bookshelf think time of 3 s and a typical response time of 0.2 s, each thread completes one request every 3.2 s, about 0.31 requests per second, so the plan settles near 50 / 3.2 ≈ 15.6 requests per second. If the migrated plan lands far from that number against the same build of the API, look for an element that no longer does what it did (a missing timer, a script that no longer runs) before blaming the server. Even a correct migration changes some numbers on purpose: since 5.0 HTTP state is reset on each thread-group iteration unless Same user on each iteration is ticked, and since 3.1 transaction samples are excluded from the summariser and empty ones from the dashboard.

Source: Getting Started: CLI mode (User Manual) and Thread Group (Component Reference)

Preparing for 6.0

None of the following needs to wait for the release. Each item can be checked on 5.6.3 today, so that the upgrade becomes a version bump plus a re-run.

Planned change What can break What to do on 5.6.3 now

Java 17 minimum

Generators, CI images and Docker images still on Java 8 or 11.

Move every node to Java 17 or 21 now; 5.6.3 runs on both.

MongoDB elements removed (PR 6573)

Plans with a MongoDB Script sampler or MongoDB Source Config no longer load.

Run the inventory script; rewrite those steps as a JSR223 Sampler with a current MongoDB driver in lib.

Expired cookies no longer sent (issue 6428)

Long soak tests whose session cookie expires mid-run start failing with authentication or session errors.

Check the cookie lifetimes of the system under test against the test duration; add a re-login path (for Bookshelf, repeat POST /api/auth/login when the token or session is rejected).

307 and 308 keep the method (issue 6080)

A POST that is redirected with 307 or 308 is repeated as a POST at the new location, so a write can happen twice where 5.6.3 sent a GET.

Find redirects in the responses (View Results Tree during Validate, or the response codes in the JTL) and decide whether the test should follow them.

No automatic charset on multipart/form-data (issue 6250)

A server that relied on the charset parameter in the header.

Check multipart uploads against the server; set the header explicitly if it needs one.

Open Model and Precise Throughput Timer delays from the Thread Group start (issue 6352)

Schedules of thread groups that start after the test starts.

See the worked example below; avoid workarounds you will have to remove.

com.mysql.cj.jdbc.Driver (PR 6274)

Plans and templates that still name com.mysql.jdbc.Driver.

Use com.mysql.cj.jdbc.Driver with a current Connector/J jar now (see Database Testing with JDBC).

Groovy 5.1.3

Groovy 3 scripts that use APIs removed in Groovy 4 or 5, such as groovy.util.XmlSlurper.

Use groovy.xml.XmlSlurper, keep scripts to vars, props, prev, the JDK and groovy.json, and run Tools → Compile JSR223 Test Elements after the upgrade.

json-path 3.0.0, Saxon-HE 13, Tika 4.x, Rhino 1.9.1, Neo4j driver 6.x

Edge cases in JSONPath and XPath expressions, Document (text) assertions, JavaScript conditions, Bolt requests.

Keep a functional smoke plan with assertions on extracted values, to run on 6.0 before any load test.

Numeric properties trimmed

Nothing should break; the change log says the trimming is there "so accidental spaces do not silently change configuration values".

Keep property values clean anyway, so that runs behave the same on 5.6.3 and 6.0.

Plugins

Plugins compiled against the old libraries, or bundling their own copies, may fail; Kotlin 1.9 or later is required.

Pin plugin versions (Plugins Manager or <jmeterExtensions>) and re-run the smoke plan with each plugin on 6.0 before upgrading generators. The gRPC Request plugin’s compatibility with 6.0 cannot be checked until 6.0 exists.

Source: changes.xml on master (planned 6.0)

Worked example: the Open Model timing change

Bookshelf seeds its test data in a setUp Thread Group that takes about 30 s, then an Open Model Thread Group runs the schedule rate(20/sec) random_arrivals(10 min).

  • On 5.6.3 arrival times are offsets from the start of the test. When the Open Model Thread Group starts at 30 s, the arrivals planned for the first 30 s are already overdue and are released at once: 20 arrivals per second × 30 s ≈ 600 iterations in a burst, then the schedule continues at 20 per second. The burst is not a property of the system under test, and it distorts the first minute of the dashboard.

  • The 5.6.3 workaround is to start the schedule with a pause that covers the setUp phase: pause(30 sec) rate(20/sec) random_arrivals(10 min).

  • On 6.0 (planned) delays are measured from the start of the Thread Group, so the burst disappears without a workaround, and the same workaround then delays the real load by an extra 30 s. Remove the leading pause when upgrading, and keep the schedule in a property (${__P(schedule,...)}) so that it is changed in one place.

Source: Open Model Thread Group (Component Reference) and changes.xml on master (planned 6.0)

Related tools that changed too

  • JMeter Plugins Manager: version 2.0 is the one this section uses; cmdrunner 2.3 for the command-line installer. The catalogue at jmeter-plugins.org is a community project, not part of Apache JMeter.

  • gRPC Request plugin: the original zalopay-oss/jmeter-grpc-request repository was archived in April 2024 after 1.2.6; the catalogue now points to the bakthava continuation (2.0.0 to 2.0.2, 2026, with mTLS and Java 21 support). It supports unary calls only. See gRPC Load Testing.

  • Programmatic plans: the experimental Kotlin and Java DSL in core 5.6 is different from JMeter Java DSL 2.3, a third-party library from Abstracta. Both are covered later in this section, in the programmatic test plans page.

  • Docker and Gradle: there is still no official Apache JMeter Docker image and no official Gradle plugin; book recipes based on Vagrant, Flood.io or specific cloud images are dated.

Pitfalls when upgrading

  • Trusting the exit code. JMeter exits with 0 even when a converted element produced no samples or every sample failed (see Running Tests in CLI Mode); check the sample count and the error rate in statistics.json or the JTL.

  • Comparing across versions without a new baseline. Changes such as the 5.0 HTTP state reset or the 3.1 transaction handling in reports alter numbers by design.

  • Mixing versions in a distributed run. The controller and the workers must run the same JMeter, Java and plugins.

  • Keeping an old copy of Groovy. Since 3.0 Groovy is bundled in lib; a copy in search_paths or user.classpath left over from a 2.x setup conflicts with it.

  • Editing jmeter.properties to restore old behaviour. Put overrides in user.properties so that the next upgrade does not discard them (see Installation & Configuration).

  • Treating master-branch behaviour as released. Anything described as 6.0 on this page comes from the development branch and may still change.
