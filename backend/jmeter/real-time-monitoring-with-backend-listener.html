Real-time Monitoring with Backend Listener

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page was written against Apache JMeter 5.6.3 (latest release on 2026-10-14; it runs on Java 8 and later, Java 17 or later is recommended, and the examples use Java 21). JMeter 6.0 is not released: its planned changes come from xdocs/changes.xml on the master branch, need Java 17 or later (Java 21 recommended) and are described as planned, not as shipped behaviour. At the time of writing that file lists no change to the Backend Listener or its clients, so everything below applies to both. The monitoring stack uses the images current on Docker Hub on the same date: InfluxDB 2.9.1 (influxdb:2.9.1, the version the latest tag points to), Grafana 13.2.4 (grafana/grafana:13.2.4) and Prometheus from the Prometheus section of this site. InfluxDB 1.x (1.11 to 1.13) and InfluxDB 3 Core are covered where they differ. No plugin is needed: the Backend Listener and its three clients are core JMeter.

See also Monitoring & Alerting for building dashboards and alerts in Grafana and Kibana.

Every parameter, property and default on this page comes from the Backend Listener component reference, the Real-time results chapter and the properties reference. Where the documentation is silent or disagrees with the code (the InfluxDB field names, the statut tag, the default of summaryOnly, how the percentile window slides), the behaviour is read from the 5.6.3 source code in org.apache.jmeter.visualizers.backend, and the page says so.

Why watch a test while it runs

A CLI run (the way every load test should run, as explained in GUI & Test Plan Workflow) prints a summary + line every 30 seconds and writes a JTL file that becomes an HTML dashboard once the run ends. For a ten-minute Bookshelf load test that is fine. For a two-hour soak test, a stress test that climbs until something breaks, or a test against a shared environment, waiting until the end is expensive:

  • Stop early. If the error rate jumps to 30 % in minute three, there is no point in running for another hour.

  • See the shape, not the average. A summary line averages 30 seconds; a graph shows the moment p95 started to climb and whether it recovered.

  • Correlate. The interesting question is never "what was p95" but "what was the server doing when p95 doubled". That needs client-side and server-side metrics on the same time axis, in the same tool.

  • Compare runs. Metrics stored in a time-series database with a run identifier can be overlaid run against run.

JMeter’s answer since 2.13 is the Backend Listener: an asynchronous listener that aggregates sample results in the load generator and pushes the aggregates to a time-series database, from which Grafana draws live graphs. The application under test exports its own metrics (Spring Boot Actuator with Micrometer, Quarkus Micrometer) to Prometheus, and Grafana reads both.

flowchart LR subgraph GEN [Load generator] TP[bookshelf-load.jmx samplers] --> BL[Backend Listener and async queue] end TP -->|HTTP requests| API[Bookshelf API] BL -->|InfluxDB client: HTTP line protocol every 5 s| IF[(InfluxDB 1.x or 2.x)] BL -.->|Graphite client: plaintext 2003 or pickle 2004 every 1 s| GR[(Graphite)] PR[(Prometheus)] -->|scrapes /actuator/prometheus| API IF --> GF[Grafana dashboards] GR -.-> GF PR --> GF

The solid path (InfluxDB) is the one this page builds; Graphite is the older alternative and is described in its own section. The JMeter side ends at the database: the HTML dashboard described in HTML Dashboard Report is still the record of the run, and the live graphs are a view on aggregates that are deliberately lossy (see How the aggregates are computed).

The Backend Listener element

Where it sits in the plan

Add → Listener → Backend Listener. It is a listener, so it follows the listener scoping rules from Test Plan Elements, Execution Order & Scoping: placed directly under the Test Plan it receives the results of every sampler in every Thread Group; placed inside a Thread Group or controller it only receives the samples in that scope. For live monitoring it almost always belongs at Test Plan level, once. Two Backend Listeners with different names run two independent clients with two queues (for example one to InfluxDB and one to Graphite); two with the same name share one client, because the listener keeps one client and one queue per element name in the JVM.

It does not slow the samplers in the normal case: sampleOccurred only puts the result into a bounded ArrayBlockingQueue, and a single daemon worker thread takes results out and hands them to the client in batches. The client aggregates them in memory, and a scheduler thread sends the aggregates every few seconds. Results only reach the samplers' threads again when the queue is full (see The async queue).

Test plan validation (Validate on a Thread Group) ignores Backend Listeners by default, so a validation run does not write a test into the database: property testplan_validation.ignore_backends, default true.

The async queue

The queue decouples the samplers from the client. A sampler thread calls offer on the queue; if the queue is full it counts a "queue wait" and blocks in put until the worker has made room. That blocking is the one way a Backend Listener can distort a test: sampler threads waiting for the listener do not send requests, so throughput drops for a reason that has nothing to do with the system under test.

The InfluxDB and Graphite clients only add each result to in-memory statistics in the worker thread, which is fast, so the queue rarely fills with them. It fills when the worker is slow: the raw-results client (which writes every sample), a third-party client that does I/O per batch, or a load generator whose CPU is saturated. At the end of the test, if any wait happened, jmeter.log contains a warning of this form (from the 5.6.3 source):

WARN o.a.j.v.b.BackendListener: QueueWaits: 1834; QueueWaitTime: 912345678 (nanoseconds), you may need to increase queue capacity, see property 'backend_queue_capacity'

The message names a property backend_queue_capacity, but in 5.6.3 neither the properties reference nor jmeter.properties defines one, and the listener reads its capacity from the Async Queue size field only. Raise that field instead.

Worked numbers. The Bookshelf load profile (50 threads, 3 s think time, about 0.2 s response time) produces about 15.6 samples per second, so the default capacity of 5000 holds about 320 seconds of results: the worker could stall for five minutes before a sampler waited. At 2,000 samples per second the same queue holds 2.5 seconds. Each queued SampleResult keeps its response data until the worker has processed it, so a larger queue costs heap in proportion to the response size; with 20 KB responses, 50,000 queued results can hold about 1 GB. Size the queue to cover a few seconds of peak throughput, not "as large as possible", and keep response bodies small (see the listeners page for jmeter.save.saveservice.*).

The InfluxDB client

InfluxdbBackendListenerClient (since 3.2) aggregates results per sampler label and per status and writes them to InfluxDB in line protocol over HTTP, by default every 5 seconds. InfluxDB 2.x support (the influxdbToken parameter) arrived in 5.2.

What the client writes

The documentation describes the metrics; the exact InfluxDB schema is in the 5.6.3 source of InfluxdbBackendListenerClient. Every send interval it writes these points to the measurement (default jmeter):

Rows Tags Fields

One cumulated row

application, transaction=all, statut=all, user TAG_ tags

count, countError, avg, min, max, hit, sb, rb, pct<p> for each percentile

Per matching sampler label, one row each for statut=all, ok and ko (only summaryOnly=false; a status with no samples in the interval is skipped)

application, transaction=<label>, statut, user tags

count, avg, min, max, hit, sb, rb, pct<p>

Per sampler label and distinct error, one row

application, transaction, responseCode, responseMessage, user tags

count

One thread row

application, transaction=internal, user tags

minAT, maxAT, meanAT, startedT, endedT

Things that surprise people when they write their own Grafana queries:

  • The status tag is spelled statut. The 3.3 release notes announced a rename to status, but the 5.6.3 code still writes statut ("keep the old name for backward compatibility"). The raw-results client below does use status.

  • Percentile field names keep a decimal. The percentile list 90;95;99 produces the fields pct90.0, pct95.0 and pct99.0; 99.9 produces pct99.9. In InfluxQL they must be double-quoted: "pct95.0".

  • count and hit differ. count is the number of sample results in the interval (on the all row, Transaction Controller results are counted as well as the requests inside them); hit counts requests, including sub-results, and skips the Transaction Controller’s own result.

  • The all row’s avg, min and max are computed over successful samples only, while its percentiles use all samples.

  • events measurement. Annotations are points in events with the tags application, title=ApacheJMeter, the user tags and, if set, tags=<eventTags>, and a single field text.

jmeter,application=bookshelf,transaction=TX\ Search\ only,statut=ok,runId=load-2026-10-14 count=27,avg=188.1,min=97.0,max=544.0,hit=27,sb=8910,rb=171003,pct90.0=310.0,pct95.0=388.0,pct99.0=544.0 1791964865000000000

Adding it to the Bookshelf plan

The Bookshelf plan names its Transaction Controllers TX Search only, TX Browse and borrow and TX Login heavy, and its requests after their HTTP method and path (POST /api/auth/login, GET /api/books). Live graphs are most useful per business transaction, so the listener sends per-label rows only for labels starting with TX, and the all row for everything.

  1. Select the Test Plan and choose Add → Listener → Backend Listener. Rename it InfluxDB live metrics.

  2. In Backend Listener implementation choose org.apache.jmeter.visualizers.backend.influxdb.InfluxdbBackendListenerClient. The Parameters table is refilled with the defaults.

  3. Set the parameters from the table below; click Add for influxdbToken and TAG_runId.

  4. Leave Async Queue size at 5000.

  5. Save the plan. Disable the listener (Disable in the context menu) when running without the monitoring stack, or keep it enabled: a missing InfluxDB only produces errors in jmeter.log, not failed samples.

The figures are illustrative. jmeter.log confirms that the listener started: it logs InfluxDB live metrics: Starting worker with class: ... and queue capacity: 5000 and, at the end, Sending last metrics to InfluxDB. A token passed with -J on the command line is visible in the process list and the shell history; -q with a file readable only by the user, or an environment variable expanded by a wrapper script, is safer.

Checking that data arrives. Before opening Grafana, query the bucket directly through the InfluxDB 2 query API (Flux):

curl -s --request POST "http://localhost:8086/api/v2/query?org=bookshelf" \
  --header "Authorization: Token $INFLUXDB_TOKEN" \
  --header "Accept: application/csv" \
  --header "Content-Type: application/vnd.flux" \
  --data 'from(bucket: "jmeter")
    |> range(start: -5m)
    |> filter(fn: (r) => r._measurement == "jmeter" and r.transaction == "all" and r._field == "count")
    |> last()'

The answer is an annotated CSV table with one row and the _value of the last count. An empty answer with HTTP 200 means nothing was written: check jmeter.log for Error writing metrics to influxDB Url: ..., responseCode: 401 (bad token), 404 (wrong org or bucket) or failed to send data to influxDB server (unreachable host).

Each point has the tags status (ok or ko), transaction (the label) and threadName, and the fields duration, ttfb (latency) and connectTime, all in milliseconds (from the 5.6.3 source). With raw points Grafana or InfluxDB compute exact percentiles over any interval, which the aggregating client cannot. The cost: at the Bookshelf load of about 15.6 samples per second the client writes 15.6 points per second, about 10,300 points in an 11-minute run, which is trivial; at 2,000 samples per second it is 7.2 million points per hour, one HTTP write per worker batch, and the series cardinality grows with every thread name. Use it for short or moderate tests, or when exact distributions matter more than the load on the monitoring stack; use the aggregating client for long or heavy runs.

Source: Backend Listener: InfluxDBRawBackendListenerClient (Component Reference)

How the aggregates are computed

Both aggregating clients (InfluxDB and Graphite) keep per-label statistics and send them every send interval. The counts (count, hit, sb, rb, errors) are reset after each send. The response-time statistics (avg, min, max and the percentiles) are computed over a sliding window whose behaviour is set by properties:

Property Default Meaning

backend_influxdb.send_interval

5

Seconds between two InfluxDB writes.

backend_graphite.send_interval

1

Seconds between two Graphite writes.

backend_influxdb.connection_timeout

1000

Connection timeout to InfluxDB, ms.

backend_influxdb.socket_timeout

3000

Socket read timeout, ms.

backend_influxdb.connection_request_timeout

100

Time to obtain a connection from the client’s pool, ms.

backend_metrics_window_mode

fixed

fixed: the last N samples, never cleared. timed: the samples of the current send interval, cleared after each send.

backend_metrics_window

100

N for fixed mode: window size for percentiles, min and max.

backend_metrics_large_window

Source: Properties Reference: BackendListener configuration

Worked example of the default window. The Bookshelf load produces about 15.6 samples per second, or 78 per 5-second interval. In fixed mode the all percentiles describe the last 100 samples, about 6.4 seconds, which is close to the interval. TX Login heavy is 10 % of the journeys; at about 1.5 samples per second, its 100-sample window spans about 65 seconds, so its p95 line in Grafana is a one-minute moving percentile that reacts to a regression a minute late and still shows it a minute after it is over. In timed mode each point describes exactly the samples of its interval, but with 7 or 8 samples per 5 seconds for that transaction a "p99" is just the maximum. Neither mode gives exact percentiles over the run; the HTML dashboard, computed from the JTL, does.

To make the live graphs closer to the report, either raise the window (for example backend_metrics_window=1000) or switch to the time-boxed mode:

# user.properties on the load generator
backend_metrics_window_mode=timed
backend_metrics_large_window=5000
backend_metrics_percentile_estimator=R_3
backend_influxdb.send_interval=5

Source: Properties Reference: BackendListener configuration

Cost on the load generator. Each tracked label keeps up to three windows (all, ok, ko) of backend_metrics_window doubles, about 2.4 KB at the default of 100, or up to 3 × 5000 doubles (120 KB) in timed mode. Ten labels cost well under 2 MB either way. CPU is dominated by sorting the windows for percentiles once per interval. The aggregating clients are cheap; what costs is a high number of labels (do not let samplersRegex match dynamic labels such as GET /api/books/1234) and the raw client at high throughput.

A Grafana dashboard for JMeter metrics

Installing Grafana and provisioning data sources are covered in Grafana: Dashboards & visualization; only the JMeter-specific part follows.

Community dashboard. The JMeter manual shows a Grafana dashboard without naming one. A widely used community dashboard is Apache JMeter Dashboard using Core InfluxdbBackendListenerClient on grafana.com (ID 5496, published by Philippe M. of Ubik Load Pack). It uses InfluxQL, asks for an InfluxDB data source pointing at the jmeter database and for two constants, the measurement name (jmeter) and the send interval (5, which must match backend_influxdb.send_interval). It is not part of JMeter and is not maintained by the Apache project: import it with Dashboards → New → Import, enter 5496, choose the data source, and review the queries before relying on them.

Your own panels. Writing the few panels that matter teaches the schema and avoids surprises. These InfluxQL queries assume the InfluxQL data source provisioned in the Compose stack below (database jmeter) and a dashboard variable runId built from SHOW TAG VALUES FROM "jmeter" WITH KEY = "runId":

-- Throughput, requests per second (count per 5 s interval divided by 5)
SELECT sum("hit") / 5 FROM "jmeter"
WHERE "application" = 'bookshelf' AND "transaction" = 'all' AND "runId" =~ /^$runId$/ AND $timeFilter
GROUP BY time(5s) fill(0)

-- Error percentage
SELECT sum("countError") * 100 / sum("count") FROM "jmeter"
WHERE "application" = 'bookshelf' AND "transaction" = 'all' AND "runId" =~ /^$runId$/ AND $timeFilter
GROUP BY time(5s)

-- p95 per business transaction (successful samples)
SELECT mean("pct95.0") FROM "jmeter"
WHERE "application" = 'bookshelf' AND "statut" = 'ok' AND "transaction" =~ /^TX / AND "runId" =~ /^$runId$/ AND $timeFilter
GROUP BY time(5s), "transaction"

-- Active threads
SELECT last("meanAT") FROM "jmeter"
WHERE "application" = 'bookshelf' AND "transaction" = 'internal' AND "runId" =~ /^$runId$/ AND $timeFilter
GROUP BY time(5s)

-- Errors by response code and message (table panel)
SELECT sum("count") FROM "jmeter"
WHERE "application" = 'bookshelf' AND "responseCode" != '' AND $timeFilter
GROUP BY "transaction", "responseCode", "responseMessage"

-- Annotation query (Dashboard settings, Annotations, InfluxDB data source)
SELECT "text" FROM "events" WHERE "application" = 'bookshelf' AND $timeFilter

Source: Grafana configuration (User Manual) and InfluxDB data source (Grafana documentation)

A sensible dashboard has one row per question: Is the load the one requested? (active threads, throughput), Is it working? (error %, errors by code), How fast? (p95 and p99 per transaction, all average), and What is the server doing? (the Prometheus panels below). Set the dashboard refresh to 5 s, the send interval; refreshing faster only redraws the same points.

Correlating with server-side metrics

The Backend Listener measures the client side. The causes of a slowdown (CPU, heap and garbage collection, a full connection pool, a saturated request thread pool) live in the server’s metrics. Bookshelf, as a Spring Boot application, exposes them through Actuator and Micrometer at /actuator/prometheus; the setup, the meters and the Prometheus scrape configuration are on Metrics and Observability: Micrometer, Actuator, and Distributed Tracing. A Quarkus service exposes the same kind of meters at /q/metrics, see Observability: Health, Logging, Metrics, Tracing. Prometheus itself is covered in Prometheus & Monitoring, starting with Installing & running Prometheus, Instrumenting applications and PromQL: Functions. The workflow for reading the two timelines together is on Performance Testing with Apache JMeter in the Spring Boot section; it is not repeated here.

What this page adds is putting both on one Grafana dashboard:

  • One time axis. Both data sources in one dashboard share its time range. JMeter’s events annotations ("started", "ended") appear as vertical markers on every panel, Prometheus panels included.

  • Matching resolution. JMeter writes every 5 s; scrape Bookshelf every 5 s during tests (the Prometheus default of 1 minute hides short spikes), and use rate(...[30s]) or similar so a Prometheus point covers a few scrapes.

  • Panels side by side. Put JMeter p95 for TX Browse and borrow above process_cpu_usage, hikaricp_connections_active and jvm_gc_pause_seconds. A latency rise that starts when the pool reaches its maximum points at the pool, not the CPU.

# PromQL panels next to the JMeter panels (Micrometer metric names)
process_cpu_usage{application="bookshelf"}
sum(hikaricp_connections_active{application="bookshelf"})
sum(rate(jvm_gc_pause_seconds_sum{application="bookshelf"}[30s]))
sum by (uri) (rate(http_server_requests_seconds_count{application="bookshelf"}[30s]))

Source: Metrics (Spring Boot reference) and Querying Prometheus (Prometheus documentation)

The application label assumes that Bookshelf adds a common application tag to its meters (Spring Boot’s management.metrics.tags.application property, or a MeterRegistry customizer); adapt the selectors to your own labels. The server’s http_server_requests_seconds_count rate is a useful cross-check: it should match JMeter’s throughput panel. If JMeter reports 15.6 requests per second and the server counts 12, requests are being lost or queued in between (a proxy, a connection limit), or the load generator itself is saturated.

PerfMon and ServerAgent (legacy)

The books monitor servers with the jmeter-plugins PerfMon Metrics Collector listener and the ServerAgent process installed on each server (PTwJ ch. 5, Pro ch. 9). The agent uses the SIGAR native library to report CPU, memory, swap, disk and network to the listener over TCP, and the listener draws them in the JMeter GUI. It still installs through the Plugins Manager as jpgc-perfmon, but it has not changed since 2016 (see Plugins & Plugins Manager), it puts an unauthenticated agent on every server, its graphs live in the GUI listener (which should not run during a load test), and it knows nothing about the JVM, pools or requests inside the application. The Monitor Results listener that the books use for Tomcat was removed in 3.2. For new work use the application’s own metrics through Prometheus, plus node or container exporters for the host (see Exporters & the Pushgateway and Containers & Kubernetes monitoring).

A Docker Compose stack: JMeter, InfluxDB and Grafana next to Bookshelf

The stack below runs InfluxDB 2.9.1, Grafana 13.2.4 and Prometheus beside the Bookshelf API’s own Compose file (see Compose for Local Development). JMeter runs on the host, as in the rest of this section; Apache publishes no official JMeter image. Every port is bound to 127.0.0.1, so nothing is reachable from the network, and all credentials are random local values generated by a setup script, never typed into a file under version control.

The directory layout:

bookshelf-monitoring/
├── compose.monitoring.yaml
├── prometheus.yml
├── grafana/provisioning/datasources/datasources.yaml
├── setup-secrets.sh          # generates secrets/ and .env (both in .gitignore)

1. Generate local credentials.

#!/usr/bin/env bash
# setup-secrets.sh: random, local-only credentials; run once
set -euo pipefail
mkdir -p secrets
umask 077
printf 'admin' > secrets/influxdb2-admin-username
openssl rand -hex 16 > secrets/influxdb2-admin-password
openssl rand -hex 32 | tr -d '\n' > secrets/influxdb2-admin-token
openssl rand -hex 16 > secrets/grafana-admin-password
printf 'INFLUXDB_TOKEN=%s\n' "$(cat secrets/influxdb2-admin-token)" > .env
printf 'influxdb_host=localhost\ninfluxdb_org=bookshelf\ninfluxdb_bucket=jmeter\ninfluxdb_token=%s\n' \
  "$(cat secrets/influxdb2-admin-token)" > monitoring.properties
printf 'secrets/\n.env\nmonitoring.properties\n' >> .gitignore

Running with several load generators

In a distributed test every JMeter server runs the whole plan, Backend Listener included, and each server’s client writes its own aggregates. Two consequences:

  • Tell generators apart. Add a row TAG_generator with the value ${__machineName()}. Without it, points from two servers with the same tags and timestamp overwrite each other in InfluxDB (a point is identified by measurement, tag set and timestamp).

  • Aggregate correctly. Counts and throughput can be summed across generators. Percentiles cannot: the p95 of two p95 values is not the p95 of the combined traffic. Show per-generator percentiles, or use the raw client and compute them in InfluxDB.

Distributed testing itself is covered on a later page of this section.

Pitfalls

  • No data in Grafana, no error in the test. The listener never fails samples: look in jmeter.log for Error writing metrics to influxDB and the HTTP status.

  • InfluxDB 2 URL in 1.x form. /write?db=jmeter against 2.x uses the 1.x compatibility API and its own authentication rules; use /api/v2/write?org=...&bucket=... with influxdbToken, as the manual says.

  • statut, not status. Queries copied from the raw client or from the 3.3 release notes find nothing.

  • Unquoted percentile fields. SELECT pct95.0 is a syntax error in InfluxQL; write "pct95.0".

  • Regex too broad. samplersRegex uses find(), so .* (the default) sends every label, and labels that contain ids (GET /api/books/1234) create a new series per id. Name samplers with templates, not values, and anchor the regex.

  • responseMessage cardinality. Error rows tag the response message; an application that puts ids or timestamps in error messages creates unbounded series.

  • Percentiles that lag. The default 100-sample window turns low-volume transactions into a moving percentile over a minute or more. Use timed mode or a larger window, and trust the HTML report for the final numbers.

  • Queue waits. The QueueWaits warning means samplers blocked; raise Async Queue size (the property named in the message does not exist in 5.6.3) and check the generator’s CPU.

  • Duplicate points from several generators. Add a TAG_generator tag.

  • Secrets in the plan. A token typed into the Parameters table is saved in clear text in the .jmx. Use ${__P(influxdb_token,)} and a local properties file.

  • Monitoring stack on the generator. InfluxDB and Grafana on the load generator steal CPU from the samplers; run them elsewhere for real measurements.
