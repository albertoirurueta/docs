Requests and Responses

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Vapor 4.122.2 (the latest 4.x release on 2026-10-17) on Swift 6.4 in the Swift 6 language mode (swift-tools-version:6.3, the version of the current vapor/template; Vapor itself needs tools 6.0), with SwiftNIO 2.104.0. Vapor 5 is at 5.0.0-beta.4 and is not generally available; its changes to Request and Response are summarised in the last sections. Every example below was compiled in a scratch package with those versions pinned, with no warnings, and the HTTP examples were run against a live server with curl (the output shown is real, trimmed for the date and connection headers) and covered by Swift Testing tests that use VaporTesting.

Every Vapor handler receives one Request and produces one Response. Everything else in the framework (routing, Content decoding, validation, middleware, authentication, Fluent) is machinery for building the second from the first. This page covers the two types themselves, with every property, initialiser and helper that matters in day-to-day work:

  1. What HTTP guarantees and what it leaves open, so that handlers return the right status code and headers.

  2. How Request exposes the method, URL, headers, body, cookies, client address and identity of the exchange.

  3. How a request body is collected or streamed, and how the size limit works.

  4. How a Response is built: status, headers, body (buffer, string, stream), cookies.

  5. How handlers return things that are not a Response: HTTPStatus, String, Content types and your own AsyncResponseEncodable types.

  6. Redirects, caching headers, downloads, pagination links, compression and HTTP/2.

Decoding bodies and query strings into Swift types (req.content, req.query) is a topic of its own (Content and Codable and Validation); this page only shows the two lines needed to use it. The language features used here are explained in the Swift Reference, for example Async/await and tasks, Actors, isolation and Sendable and Codable and serialization. For the Vapor application that these handlers live in see Getting started and Project structure and SwiftPM targets; for the threading model behind async handlers see Swift concurrency in Vapor.

A refresher on HTTP

HTTP is a request/response protocol: a client sends one request, the server sends one response. HTTP semantics (what the methods, status codes and headers mean) are defined by RFC 9110; the wire formats are RFC 9112 (HTTP/1.1) and RFC 9113 (HTTP/2); caching is RFC 9111. A request and its response on the wire (HTTP/1.1) look like this:

POST /books HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json
Content-Length: 44

{"title":"Emma","author":"Jane Austen"}

HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Location: /books/4
Content-Length: 46

{"author":"Jane Austen","id":4,"title":"Emma"}

The first line of the request is the request line (method, target, version); the first line of the response is the status line (version, status code, reason phrase). Then come header fields, an empty line and an optional body. Vapor parses the request into a Request before your code runs and serialises the Response you return.

Methods: safe, idempotent, cacheable

The method states the intent of the request. Two properties decide how clients, proxies and retry logic treat it: a safe method does not change server state (so crawlers and prefetchers may send it), and an idempotent method has the same effect when sent once or several times (so a client may retry it after a timeout).

In Vapor each method is a HTTPMethod value (.GET, .POST, .PUT, .PATCH, .DELETE, …​) and a route is registered per method (app.get, app.post, …​). A few behaviours are worth knowing before they surprise you. A HEAD request is answered by the GET route for the same path, and Vapor drops the body (checked against the example server: curl -I on a GET and POST route returns 200 with the headers and no body). OPTIONS is not answered automatically: without CORSMiddleware a preflight request to a route that has no OPTIONS handler gets 404. A path that exists but not for that method also gets 404 in Vapor, not 405 Method Not Allowed.

Error responses and the Abort type are covered on the Error Handling page; this page uses only throw Abort(.status, reason:).

Headers

Header fields are name/value pairs; names are case-insensitive and a field may repeat. The ones that control the exchange:

  • Content negotiation: Accept (what the client can read), Content-Type (what the body is), Content-Language, Accept-Encoding and Content-Encoding (compression).

  • Body framing: Content-Length (exact size) or Transfer-Encoding: chunked (size unknown in advance, a stream).

  • Caching and conditional requests: Cache-Control, ETag, Last-Modified, Expires, If-None-Match, If-Modified-Since.

  • Identity and security: Authorization, Cookie, Set-Cookie, WWW-Authenticate.

  • Navigation: Location (where a created or moved resource is), Link (related resources such as the next page).

  • Proxies: Forwarded and X-Forwarded-For (the original client address), Host.

HTTP/1.1 and HTTP/2

HTTP/2 keeps the same methods, status codes and headers but changes the framing: one connection carries many concurrent streams (multiplexing, no head-of-line blocking at the HTTP layer), header fields are compressed, and browsers only speak it over TLS. Your handlers do not change. In Vapor, app.http.server.configuration.supportVersions defaults to [.one] when no TLS is configured and [.one, .two] when tlsConfiguration is set (HTTP/2 is negotiated with ALPN); cleartext HTTP/2 (h2c) is not supported by the server in 4.122.2 (the source calls fatalError on that configuration). In production TLS is usually terminated by a reverse proxy, which is why req.peerAddress (below) exists.

Where requests and responses sit in the lifecycle

The server decodes bytes into a Request, passes it through the middleware you registered (in registration order, so ErrorMiddleware is outermost), then through the router, which picks a route, fills req.parameters, sets req.route and applies the route’s body strategy. Your handler returns something; Vapor turns it into a Response with encodeResponse(for:); the response travels back out through the same middleware in reverse, and the server serialises it.

flowchart LR C([Client]) -->|bytes| D["HTTP decoder: Request (method, URL, headers, body strategy)"] D --> M1["Middleware 1 (ErrorMiddleware)"] M1 --> M2["Middleware 2 ... n"] M2 --> R["Router: route match, req.parameters, req.route"] R --> H["Handler: async throws -> some AsyncResponseEncodable"] H --> E["encodeResponse(for: req) builds the Response"] E --> M2o["Middleware n ... 2 (response phase)"] M2o --> M1o["Middleware 1 (turns thrown errors into responses)"] M1o --> S["HTTP encoder: status line, headers, body"] S -->|bytes| C

Two consequences follow. First, anything a middleware changes on the Request (headers, req.storage, req.logger metadata) is visible to the handler, and anything it changes on the Response is visible to the client. Second, the body is read from the socket after the headers: by default the router collects it before calling the handler, but a route can ask for a stream instead, which changes what req.body contains (see Request bodies).

Inspecting a request

The first example builds a RequestSummary that reports each of the properties above. The BookDTO and Library types are the small in-memory Bookshelf data set used by all examples on this page.

import Vapor

struct BookDTO: Content {
    var id: Int
    var title: String
    var author: String
}

enum Library {
    static let books: [BookDTO] = [
        BookDTO(id: 1, title: "Dune", author: "Frank Herbert"),
        BookDTO(id: 2, title: "Hyperion", author: "Dan Simmons"),
        BookDTO(id: 3, title: "Solaris", author: "Stanislaw Lem"),
    ]
}
import Vapor

struct RequestSummary: Content {
    var id: String
    var method: String
    var path: String
    var query: String?
    var httpVersion: String
    var host: String?
    var userAgent: String?
    var contentType: String?
    var contentLength: Int?
    var remote: String?
    var peer: String?
    var route: String?
    var bodyBytes: Int
}

func summarize(_ req: Request) -> RequestSummary {
    RequestSummary(
        id: req.id,
        method: req.method.rawValue,
        path: req.url.path,
        query: req.url.query,
        httpVersion: "\(req.version.major).\(req.version.minor)",
        host: req.headers.first(name: .host),
        userAgent: req.headers.first(name: .userAgent),
        contentType: req.headers.contentType?.serialize(),
        contentLength: req.headers.first(name: .contentLength).flatMap { Int($0) },
        remote: req.remoteAddress?.description,
        peer: req.peerAddress?.ipAddress,
        route: req.route?.description,
        bodyBytes: req.body.data?.readableBytes ?? 0
    )
}

func inspectRoutes(_ routes: some RoutesBuilder) {
    routes.get("inspect") { req in summarize(req) }
    routes.post("inspect") { req in summarize(req) }
}

And req.remoteAddress prints SwiftNIO’s debug format; use ipAddress or port on SocketAddress when you need a clean value.

The client address behind a proxy

Behind a load balancer remoteAddress is always the proxy. peerAddress looks first at the Forwarded header (RFC 7239), then at X-Forwarded-For, and falls back to remoteAddress. Two cautions follow from the source: when a forwarded value is used, the port is set to 80 regardless of the real one, and the headers are client controlled unless your proxy overwrites them. Use peerAddress for logging and rate-limit keys only if the proxy strips incoming Forwarded and X-Forwarded-For headers; never for access control based on a spoofable value.

Request identity and logging

Every request has an id: the incoming X-Request-Id header if there is one, a generated UUID otherwise. The same value is added to req.logger as the request-id metadata key, so all log lines written through req.logger during the request can be correlated. A common pattern is to echo the id on the response so that clients can quote it in bug reports; a middleware that sets the response header for every route is shown on the Middleware page. A per-request key/value store is req.storage, keyed by a type that conforms to StorageKey (whose Value must be Sendable):

import Vapor

func headerRoutes(_ routes: some RoutesBuilder) {
    routes.get("headers") { req async throws -> HeaderReport in
        // Typed accessors parse the raw header for you.
        let accept = req.headers.accept
        let preference = accept.comparePreference(for: .json, to: .html)
        let preferred = preference == .orderedAscending ? "html" : "json"

        // Raw access: names are case-insensitive, a header can occur several times.
        let allAccept = req.headers[.accept]
        _ = allAccept

        return HeaderReport(
            preferredFormat: preferred,
            acceptedTypes: accept.mediaTypes.map { $0.serialize() },
            bearerToken: req.headers.bearerAuthorization?.token,
            basicUser: req.headers.basicAuthorization?.username,
            forwardedFor: req.headers.forwarded.compactMap { $0.for },
            range: req.headers.range.map { $0.serialize() },
            cookieNames: req.cookies.all.keys.sorted()
        )
    }

    routes.get("headers", "set") { req async throws -> Response in
        let response = Response(status: .ok)
        response.headers.add(name: "X-Library", value: "bookshelf")
        response.headers.replaceOrAdd(name: .cacheControl, value: "no-store")
        response.headers.contentType = .plainText
        response.headers.remove(name: "X-Debug")
        response.body = .init(string: "headers set\n")
        return response
    }

Request bodies

A request body is a sequence of bytes whose length is announced by Content-Length or, for streams, by Transfer-Encoding: chunked. Vapor offers two ways to deal with it, chosen per route with the body: parameter of the route registration methods (HTTPBodyStreamStrategy):

Strategy What the handler sees Use for

.collect (default) or .collect(maxSize: "2mb")

the whole body is read into memory before the handler runs, up to the limit; req.body.data and req.body.string are non-nil; req.content.decode works

JSON and form APIs, small uploads

.stream

the handler starts when the headers have arrived; req.body.data is nil; read chunks with for try await chunk in req.body, req.body.drain(_:) or req.body.collect(max:)

large uploads, proxying, anything you do not want in memory

The default limit comes from app.routes.defaultMaxBodySize, which is 16kb (the value type is ByteCount, expressible as a string literal with the suffixes kb, mb, gb and tb, or as an integer number of bytes). A larger body gets 413 Payload Too Large. This surprises people who upload a 100 kB JSON document or a photo to a default route; raise the limit for the route that needs it with .collect(maxSize:) rather than raising it for the whole app, because every collected body is held in memory per connection, which is a denial-of-service lever. The Request.Body API:

  • data: ByteBuffer? and string: String?: the collected bytes (string decodes the bytes as UTF-8 text). nil when the body is streamed or absent.

  • collect(max: Int? = 1 << 14) -> EventLoopFuture<ByteBuffer?>: collect a streamed body now, failing with 413 above max. The default of 16 KiB is not defaultMaxBodySize. It is the legacy futures API; call .get() to use it from async code. nil means "no limit", so never pass nil for untrusted input.

  • drain(_:): legacy callback API with BodyStreamResult values (.buffer, .error, .end) and back-pressure through the returned future.

  • AsyncSequence conformance with Element == ByteBuffer: for try await chunk in req.body. It applies back-pressure with a high/low watermark of 20 and 5 chunks, so a slow consumer slows the sender.

If the body is not collected, req.content.decode(...) fails: the source throws Abort(.unprocessableEntity) and logs that decoding streaming bodies is not supported. A route that must both stream and decode small JSON has to collect explicitly first with try await req.body.collect(max: 1 << 20).get().

import Vapor

struct UploadResult: Content {
    var bytes: Int
    var lines: Int
}

func bodyRoutes(_ routes: some RoutesBuilder) {
    // Default: the body is collected (up to app.routes.defaultMaxBodySize, 16kb) before the handler runs.
    routes.post("echo") { req async throws -> String in
        guard let text = req.body.string else {
            throw Abort(.badRequest, reason: "Expected a UTF-8 body")
        }
        return text
    }

    // A larger collected limit for one route.
    routes.on(.POST, "import", body: .collect(maxSize: "2mb")) { req async throws -> UploadResult in
        guard let buffer = req.body.data else { throw Abort(.badRequest) }
        let lines = buffer.readableBytesView.filter { $0 == UInt8(ascii: "\n") }.count
        return UploadResult(bytes: buffer.readableBytes, lines: lines)
    }

    // Streaming: the handler starts as soon as the headers are in; the body arrives chunk by chunk.
    routes.on(.PUT, "blobs", ":name", body: .stream) { req async throws -> UploadResult in
        let limit = 50 * 1024 * 1024
        var bytes = 0
        var lines = 0
        for try await chunk in req.body {
            bytes += chunk.readableBytes
            if bytes > limit { throw Abort(.payloadTooLarge) }
            lines += chunk.readableBytesView.filter { $0 == UInt8(ascii: "\n") }.count
        }
        return UploadResult(bytes: bytes, lines: lines)
    }
}

Cookies

req.cookies is an HTTPCookies: a dictionary-like value keyed by cookie name whose elements are HTTPCookies.Value. Reading req.cookies["visits"] parses the Cookie header; each Value has a string and, on the response side, the attributes of Set-Cookie (RFC 6265). The HTTPCookies.Value initialiser:

string

the cookie value (required)

expires, maxAge

lifetime as an absolute Date or in seconds; maxAge wins in modern browsers

scope of the cookie; path defaults to "/"

isSecure

send only over HTTPS; forced to true when sameSite is .none

isHTTPOnly

hide the cookie from JavaScript (document.cookie)

sameSite

.lax (default), .strict or .none, controlling cross-site sending

import Vapor

    var title: String
    var author: String

func responseRoutes(_ routes: some RoutesBuilder) {
    // 1. Build a Response by hand: status, headers, body.
    routes.get("hello-response") { req async throws -> Response in
        var headers = HTTPHeaders()
        headers.contentType = .plainText
        headers.add(name: "X-Greeting", value: "hello")
        return Response(status: .ok, headers: headers, body: .init(string: "Hello from a Response\n"))
    }

    // 2. Encode a Content value into a Response, then adjust it.
    routes.get("books", ":id") { req async throws -> Response in
        guard let id = req.parameters.get("id", as: Int.self),
              let book = Library.books.first(where: { $0.id == id })
        else { throw Abort(.notFound, reason: "No book with that id") }
        let response = Response()
        try response.content.encode(book, as: .json)
        response.headers.replaceOrAdd(name: .cacheControl, value: "max-age=60")
        return response
    }

    // 3. Status-only responses.
    routes.delete("books", ":id") { req async throws -> HTTPStatus in
        .noContent
    }

    // 4. 201 Created with a Location header, using encodeResponse(status:headers:for:).
    routes.post("books") { req async throws -> Response in
        let input = try req.content.decode(NewBook.self)
        let created = BookDTO(id: 4, title: input.title, author: input.author)
        return try await created.encodeResponse(
            status: .created,
            headers: ["Location": "/books/\(created.id)"],
            for: req
        )
    }

    // 5. Redirects.
    routes.get("old-books") { req in
        req.redirect(to: "/books", redirectType: .permanent)
    }
    routes.post("login-form") { req in
        req.redirect(to: "/account", redirectType: .normal)
    }
}

import Vapor

/// A handler result that is either a book, or a tombstone.
enum BookLookup: AsyncResponseEncodable {
    case found(BookDTO)
    case gone(reason: String)

    func encodeResponse(for request: Request) async throws -> Response {
        switch self {
        case .found(let book):
            return try await book.encodeResponse(for: request)
        case .gone(let reason):
            let response = Response(status: .gone)
            try response.content.encode(["error": reason], as: .json)
            return response
        }
    }
}

        response.headers.contentDisposition = .init(.attachment, filename: filename)
        return response

Streaming responses

A response body can be produced incrementally with an async closure. managedAsyncStream is the one to prefer: Vapor ends the response when your closure returns and reports a failure to the client when it throws; with plain asyncStream you must write .end or .error yourself, and forgetting to do so leaves the connection hanging. Without a count, the response is chunked. With a count, Vapor sends Content-Length and the closure must write exactly that many bytes.

import Vapor
import NIOCore

func streamingRoutes(_ routes: some RoutesBuilder) {
    // Chunked response (no Content-Length): lines of newline-delimited JSON.
    routes.get("books", "stream") { req async throws -> Response in
        let response = Response(status: .ok)
        response.headers.contentType = HTTPMediaType(type: "application", subType: "x-ndjson")
        let encoder = JSONEncoder()
        response.body = .init(managedAsyncStream: { writer in
            for book in Library.books {
                try Task.checkCancellation()
                var line = ByteBuffer(bytes: try encoder.encode(book))
                line.writeString("\n")
                try await writer.writeBuffer(line)
                try await Task.sleep(for: .milliseconds(50))
            }
        })
        return response
    }

    // Known size: a Content-Length is sent, and the closure must write exactly that many bytes.
    routes.get("fixed-size") { req async throws -> Response in
        let payload = "0123456789"
        let response = Response(status: .ok)
        response.headers.contentType = .plainText
        response.body = .init(managedAsyncStream: { writer in
            try await writer.writeBuffer(ByteBuffer(string: payload))
        }, count: payload.utf8.count)
        return response
    }
}

The stream closure is @Sendable, so under Swift 6 it cannot mutate a captured var. The compiler rejects this immediately:

error: mutation of captured var 'sent' in concurrently-executing code

Keep counters inside the closure, or in an actor or a Mutex. The writer applies back-pressure: try await writer.writeBuffer(_:) suspends while the connection cannot accept more data, so a slow client does not make the process buffer the whole export. A client that disconnects makes the write throw, which ends your closure; check try Task.checkCancellation() in long loops as shown. To send a file from disk prefer req.fileio.streamFile, which sets ETag, handles Range and If-None-Match, and reads in chunks.

Caching, downloads and pagination headers

Typed accessors turn the usual response headers into one-liners: cacheControl, lastModified, expires, contentDisposition and links. The conditional GET pattern below saves bandwidth: the server sends an ETag (a version token of the representation); the client repeats it in If-None-Match; if it still matches, the server answers 304 with no body (RFC 9111, RFC 9110 section 13).

import Vapor

func cachingRoutes(_ routes: some RoutesBuilder) {
    let published = Date(timeIntervalSince1970: 1_700_000_000)

    routes.get("catalog") { req async throws -> Response in
        let etag = "\"catalog-v\(Library.books.count)\""

        // Conditional GET: If-None-Match matches, so no body is sent.
        if req.headers.first(name: .ifNoneMatch) == etag {
            let notModified = Response(status: .notModified)
            notModified.headers.replaceOrAdd(name: .eTag, value: etag)
            return notModified
        }

        let response = Response()
        try response.content.encode(Library.books, as: .json)
        response.headers.replaceOrAdd(name: .eTag, value: etag)
        response.headers.lastModified = .init(published)
        response.headers.cacheControl = .init(isPublic: true, maxAge: 300)
        return response
    }

    routes.get("books", "page", ":n") { req async throws -> Response in
        let page = try req.parameters.require("n", as: Int.self)
        let response = Response()
        try response.content.encode(Library.books, as: .json)
        response.headers.links = [
            .init(uri: "/books/page/\(page + 1)", relation: .next, attributes: [:]),
            .init(uri: "/books/page/1", relation: .first, attributes: [:]),
        ]
        return response
    }
}

The ETag here is a made-up version string to keep the example short; derive a real one from a content hash or a database version column. Weak validators (W/"...") and If-None-Match lists ("a", "b") need a small parser; the file API in Vapor generates its ETag from the modification time and size and handles the comparison for you. Cache-Control: private (not public) is mandatory for responses that depend on the user, and no-store for sensitive data.

Compression, decompression and body limits in the server configuration

Several body-related settings live on the application rather than on a route. They are normally set in configure:

import Vapor

func configure(_ app: Application) async throws {
    // Body limit for routes that use the default .collect strategy (the default is 16kb).
    app.routes.defaultMaxBodySize = "1mb"

    // Compression of responses (only if the client sends Accept-Encoding) and of request bodies.
    app.http.server.configuration.responseCompression = .enabledForCompressibleTypes
    app.http.server.configuration.requestDecompression = .enabled(limit: .ratio(10))
    app.http.server.configuration.serverName = "bookshelf"

    try routes(app)
}

Source: Vapor docs: Server and vapor/vapor 4.122.2: HTTPServer.swift

  • app.routes.defaultMaxBodySize is the limit of the default .collect strategy (default 16kb).

  • responseCompression can be .disabled (default, but routes may opt in), .enabledForCompressibleTypes (text-like content types only), .enabled (everything except already compressed types such as images) or .forceDisabled. The server compresses only when the client sends Accept-Encoding. A single route or group opts in or out with ResponseCompressionMiddleware or route.responseCompression(.enable); a middleware may also set response.headers.responseCompression.

  • requestDecompression is .disabled by default. When enabled, always pass a limit (.ratio(10) here: an upload that expands more than ten times is rejected). Without a limit, a small compressed body can expand to gigabytes.

  • serverName adds a Server header; leave it unset (or generic) in production if you do not want to advertise the stack.

With the configuration above, a text response larger than a few bytes is gzip-compressed when the client asks for it. The check against the live server (100,000 bytes of x posted to /echo come back as 132 bytes):

Testing requests and responses

See also the Testing page for the general setup.

VaporTesting (the testing library bundled in the vapor package since 4.110) runs a request through the complete middleware and routing stack without a socket. app.testing().test(.METHOD, path, headers:, body:, beforeRequest:, afterResponse:) takes a configure closure for the request and an assertion closure that receives a TestingHTTPResponse with status, headers, body and content. The default in-memory mode does not run the HTTP server: the body-size limit is not enforced (a 4 KiB body posted to a route with a 1 KiB limit answers 200 in memory and 413 when running), and compression, which is applied by the server pipeline, is not exercised either. Chunked streaming responses do work in memory. For limits and compression use app.testing(method: .running(port: 0)), which binds an ephemeral port and goes through a real HTTP client. Port 0 matters: with the default port, tests that run in parallel (Swift Testing runs tests concurrently) collide with Address already in use.

import VaporTesting
import Testing
@testable import App

@Suite("Request and response")
struct RequestAndResponseTests {
    private func withApp(_ test: (Application) async throws -> Void) async throws {
        let app = try await Application.make(.testing)
        do {
            try await configure(app)
            try await test(app)
        } catch {
            try await app.asyncShutdown()
            throw error
        }
        try await app.asyncShutdown()
    }

    @Test("inspect reports method, path, query, id and body size")
    func inspect() async throws {
        try await withApp { app in
            try await app.testing().test(
                .POST, "inspect?x=1",
                headers: ["X-Request-Id": "test-1", "Content-Type": "text/plain"],
                body: ByteBuffer(string: "hello")
            ) { res async throws in
                #expect(res.status == .ok)
                let summary = try res.content.decode(RequestSummary.self)
                #expect(summary.id == "test-1")
                #expect(summary.method == "POST")
                #expect(summary.query == "x=1")
                #expect(summary.bodyBytes == 5)
                #expect(summary.route == "POST /inspect")
            }
        }
    }

    @Test("POST /books answers 201 with a Location header")
    func created() async throws {
        try await withApp { app in
            try await app.testing().test(.POST, "books", beforeRequest: { req in
                try req.content.encode(NewBook(title: "Emma", author: "Jane Austen"))
            }, afterResponse: { res async throws in
                #expect(res.status == .created)
                #expect(res.headers.first(name: .location) == "/books/4")
                #expect(try res.content.decode(BookDTO.self).title == "Emma")
            })
        }
    }

    @Test("a body over the limit is rejected with 413")
    func tooLarge() async throws {
        try await withApp { app in
            app.routes.defaultMaxBodySize = "1kb"

            }
        }
    }

        }

                #expect(res.headers.first(name: .transferEncoding) == "chunked")

            }
        }
    }

Swift 6 and concurrency notes

  • Request and Response are Sendable classes. Reading and writing their properties from several tasks is safe (every property is behind a lock), but order is yours to manage.

  • Route closures are @Sendable; they may capture only Sendable values. Models, DTOs and services you capture must be Sendable too (structs of Sendable values are, classes need locks or an actor). Mutable state belongs in an actor or a Mutex, or in app.storage / req.storage behind a Sendable value.

  • Do not block inside a handler or a stream closure: no Thread.sleep, no synchronous file reads of large files, no .wait() on a future. Use Task.sleep, req.fileio and .get().

  • for try await chunk in req.body runs on the cooperative pool and suspends while waiting for data; the NIO event loop keeps reading the socket and applies back-pressure through the watermark.

  • The legacy EventLoopFuture API (req.body.collect, Body.collect(on:), drain) is still present in 4.122; the .get() bridge is documented in the concurrency page.

Version notes

  • Vapor 3 (the era of most books and tutorials) had Request.http, wrapped request and response in HTTPRequest and HTTPResponse, returned Future<Response> and read bodies with req.content.decode(User.self).flatMap. Vapor 4 (2020) removed req.http, made Request and Response the HTTP types and added req.content as a container; the handler signature (Request) throws -> ResponseEncodable is the one that survives.

  • Later 4.x releases added async/await handlers and AsyncResponseEncodable (Swift 5.5), then the Sendable conformances that make Request and Response safe to capture under Swift 6, async body streaming (Body(managedAsyncStream:), Request.Body as an AsyncSequence) and the response-compression configuration. The exact release of each is in the GitHub release notes; the page documents the 4.122.2 behaviour, so check them if you must support an older 4.x.

  • Vapor 5 (5.0.0-beta.4, not generally available): per the 5.0.0-beta.4 sources, Request and Response become struct`s (still `Sendable, with the request body exposed as a non-escapable view), method, status and header types come from swift-http-types (HTTPRequest.Method, HTTPResponse.Status, HTTPFields) instead of SwiftNIO’s HTTPMethod, HTTPStatus and HTTPHeaders, ResponseEncodable is the single async throws protocol (the EventLoopFuture flavour and AsyncResponseEncodable are gone), and response streaming uses Body(stream:) with an HTTPBodyWriter instead of the writer protocols above. Application code written for 4.122 with async/await handlers, Content types and Abort ports with mechanical renames; code that touches req.eventLoop, futures or HTTPHeaders.Name does not.

Where the books are outdated

  • Condon et al. (Server-Side Swift with Vapor, Kodeco) introduces HTTP, Request and Response with EventLoopFuture return types and req.content.decode(...).flatMap. The concepts (methods, status codes, headers, Content) are unchanged; the signatures are now async throws and .get() bridges the old API.

  • Yeung and Patel (Packt) show Vapor 3 and early Vapor 4 code with req.http, HTTPResponse, req.response(), try req.parameters.next(Int.self) and Future<...> handlers. In Vapor 4.122 those are req.method/req.headers, Response, req.parameters.get(_:as:) and async throws handlers.

  • Older material rarely mentions body size limits: Vapor 3 collected whole bodies without a small default. In Vapor 4 the default of 16kb (and .stream for large uploads) is something every upload feature has to handle.

  • Cookie and caching advice in older tutorials predates SameSite=Lax as the browser default; set sameSite, isSecure and isHTTPOnly explicitly.
