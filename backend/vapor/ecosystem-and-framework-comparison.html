Ecosystem and Framework Comparison

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page was written on 2026-10-17 against Vapor 4.122.2 (the latest 4.x release) on Swift 6 (the local toolchain is Swift 6.4; the official template needs swift-tools-version 6.3, while Vapor 4.122.2 itself needs 6.0). Vapor 5 is at 5.0.0-beta.4 and is not generally available, so everything here is about Vapor 4 unless it says otherwise. It contains no Swift code: it is a map. Its tables hold the facts that were read from the GitHub API on 2026-10-17 (whether a repository is archived, the date of its latest push and the tag and date of its latest GitHub release), plus the comparison with other frameworks and a lookup table from a need to the package and to the page of this section that explains it.

Two limits apply to what follows.

  1. The status columns say what GitHub reported on the check date. A recent release does not prove that a package is good, and an old one does not prove that it is broken; read the repository, its open issues and its Package.swift (tools version and platforms) before depending on it. The pushed_at date also moves for reasons such as a bot updating a workflow file, so the tables give the date of the latest release as well.

  2. The comparison with other frameworks is a description of design, not a benchmark. No performance claim is made, and no numbers were measured for this page. The versions of the other frameworks are not repeated here; their own sections on this site state them.

How the Vapor ecosystem is organised

Four groups publish packages that a Vapor application uses:

  • vapor (https://github.com/vapor) — the framework itself and the packages that the Vapor team maintains: vapor/vapor, the Fluent family, Leaf, Redis, Queues, JWT, APNS and their kits. The versions are in the closing section of each page of this section.

  • vapor-community (https://github.com/vapor-community) — an organisation for packages that the community maintains under the Vapor name. It holds a lot of repositories that have not been touched for years (Vapor 1 to 3 providers), so every package taken from there needs the date check this page performs.

  • Swift Server Workgroup (SSWG) and Apple packages — SwiftNIO, swift-log, swift-metrics, swift-distributed-tracing, AsyncHTTPClient, swift-service-lifecycle, swift-configuration, swift-openapi-generator and swift-crypto. Vapor builds on these and they are shared with every other Swift server framework; see Introduction & Architecture.

  • Independent maintainers — Soto, MongoKitten, Graphiti, APNSwift, VaporSecurityHeaders and similar. Vapor documents some of them, but a Vapor release does not wait for them.

A Fluent or Leaf package that is not yet compatible with Vapor 5 will not resolve next to it, and several community packages declare a dependency on Vapor 4; check the dependency range before planning a move, as described in What’s New, Upgrading and Vapor 5.

Not found or not recommended

Some packages that books and blog posts mention could not be confirmed on 2026-10-17:

  • ml-archive/gatekeeper, the rate-limiting middleware, is archived; the alternatives are in Security Hardening.

  • vapor-community/postgresql is archived (last release 2.2.0, 2020-05-18), and many Vapor 1 to 3 providers in the same organisation (for example mysql-provider, fluent-provider, jwt-provider, leaf-provider) have had no push since 2016 to 2019. They belong to the Droplet era; see What’s New, Upgrading and Vapor 5.

  • Repository names such as vapor-community/vapor-oauth, vapor-community/vapor-ses and vapor-community/sentry returned "not found" from the GitHub API under those exact names. They may have moved or never existed under that name; this page does not recommend them, and the status of Sentry or Amazon SES integrations was not verified.

Vapor and Hummingbird 2

Hummingbird is the main alternative among Swift server frameworks. On 2026-10-17 hummingbird-project/hummingbird was not archived, its latest release was 2.28.0 (2026-10-13), the previous ones 2.27.1 (2026-10-09) and 2.27.0 (2026-09-21), and its Package.swift declared swift-tools-version:6.2. Two companion packages in the same organisation were also active: hummingbird-auth 2.5.0 (2026-09-27) and hummingbird-fluent 2.0.0 (2025-01-10, which lets Hummingbird use Fluent).

Aspect Vapor 4.122 Hummingbird 2.28

Shape

Batteries included: routing, Content, validation, sessions, authentication helpers, commands, a test helper and an application lifecycle in the one package, with Fluent, Leaf, Queues and Redis as sibling packages.

A small core (router, middleware, server, request context) and separate packages for authentication, Fluent, WebSocket, and so on. You assemble what you need.

Concurrency

SwiftNIO under an async/await API; EventLoopFuture remains in the public API for legacy code.

SwiftNIO and structured concurrency; the HTTP server is built to run as a swift-service-lifecycle service.

Per-request state

The Request object, req.storage, req.application.

A generic request context type that you define, with the data a handler needs.

Data access

Fluent, with SQLKit underneath, is the default and is documented as part of the framework.

You choose: hummingbird-fluent, or a database driver such as PostgresNIO, directly.

Documentation and books

The most documentation, books (the three consulted for this section) and community packages in Swift server development.

Its own official documentation; fewer books were found and fewer third-party integrations are listed in this section.

Next major

5.0.0-beta.4, not generally available (see What’s New, Upgrading and Vapor 5).

Version 2 is the current major.

The rows describe design as documented by the two projects and as seen in their repositories; no benchmark was run. Both are built on SwiftNIO and the SSWG libraries, so many packages (AsyncHTTPClient, swift-log, swift-otel, Soto, MongoKitten, swift-openapi-generator, APNSwift) work with either. Choose Vapor for an integrated stack with a large body of tutorials; consider Hummingbird for a small service or when you want to choose each piece. Neither choice is irreversible: handlers written against Content, services behind protocols and a separate data layer move more easily, as discussed in Services, Storage and Dependency Injection.

When Vapor is a good fit: you want one language across an iOS or macOS client and the backend and can share model types (see Full-Stack Swift with iOS Clients); you want strong typing with a compiler that checks data-race safety; the team already writes Swift. When it is not: you need the larger hiring pool, library choice and operational experience that the Java, JavaScript and Python ecosystems offer, or integrations that only have a Java, PHP or Node client. These are judgements, not measurements.

A broader comparison of backend and web frameworks across all the languages of this site is planned in issue #263; this table covers only the five frameworks named above.

A checklist for adding a dependency

  1. Open the repository and note whether it is archived and the date of the latest release; a package that has not changed in three years may still be fine if it is small, but you own that decision.

  2. Read Package.swift for the swift-tools-version and the platforms. A tools version of 5.x compiles as Swift 5 code, which does not get the Swift 6 data-race checks in your build for that target.

  3. Check which Vapor major it depends on. A dependency on Vapor 4 will not resolve with Vapor 5.

  4. Pin it with from: or exact: and let Dependabot or a manual swift package update review the changes; see Security Hardening.

  5. Put it behind a protocol of your own when it is a service you may replace (email, push, storage), as the pages for email and Apple push notifications do.

What could not be verified

  • Whether the packages marked "not evaluated" work with Vapor 4.122.2 on Swift 6. Only their GitHub status was read.

  • The GitHub status of repositories whose exact names could not be found (see "Not found or not recommended").

  • No benchmark and no feature count of the other frameworks was taken; the framework table reflects design, not measured behaviour.

  • The Kitura and Perfect dates come from the GitHub API on 2026-10-17 and may differ on other branches.
