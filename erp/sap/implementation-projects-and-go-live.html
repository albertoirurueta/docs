Implementation Projects and Go-Live

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Installing an SAP system is the smaller part of an SAP project. Most of the work is deciding what the company needs, shaping the standard software to fit it, moving the data of the old systems into the new one, proving that everything works, and switching the business over on one chosen weekend. This page walks through that journey in the order a project lives it, using the vocabulary that SAP uses: the methodology called SAP Activate, the three ways to move to SAP S/4HANA (a new implementation, a system conversion and a selective data transition), the fit-to-standard workshops, the data migration with the SAP S/4HANA migration cockpit, the test stages, the cutover, the go-live and the hypercare support that follows. After reading it you can follow what a project plan is saying and know which tool or checkpoint belongs to which step. The page is written against SAP S/4HANA 2025 FPS02, which applies to the on-premise edition and to SAP S/4HANA Cloud Private Edition, and against SAP S/4HANA Cloud Public Edition 2608. Where the two differ, the text says which one it means.

Before you read

  • Familiarity with what an ERP system does for a company, in the pages of the ERP section (for example ERP Overview and What Is SAP), is enough.

  • Packages, Transports, gCTS and abapGit: how a change travels from the development system to the quality system and on to production. Cutover and go-live depend on it.

  • Batch Input, Direct Input and Data Migration: the developer view of loading data, and the older tools that the migration cockpit replaces.

  • Clean Core and Cloud Readiness: why fewer custom changes make a project shorter and an upgrade easier.

Key terms

  • SAP Activate: SAP’s methodology for implementing its solutions, made of phases, deliverables, tasks, workstreams and accelerators.

  • Fit-to-standard: the workshops in which the business sees the standard SAP processes and records only the differences it still needs.

  • Greenfield (new implementation): building a new SAP S/4HANA system from scratch and migrating only the data that is needed.

  • System conversion (brownfield): turning an existing SAP ERP system into SAP S/4HANA while keeping its data, custom code and configuration.

  • Selective data transition: a tailored path between the two, which carves chosen data and configuration out of the old system into the new one.

  • Central Finance: an SAP S/4HANA system that receives the financial postings of other systems so they can be reported in one place.

  • SAP S/4HANA migration cockpit: the SAP Fiori app that migrates business data with migration objects.

  • Cutover: the activities of the last days before go-live, between switching off the old systems and switching on the new one.

  • Hypercare: the intensive support by the project team in the first weeks after go-live.

What makes an SAP project different from installing software

A company runs its finance, purchasing, sales and production in the same system. Changing the system therefore changes how people work, so an implementation project has two halves that must move together: the technical half (systems, interfaces, data, code) and the business half (processes, roles, training, decisions). SAP S/4HANA adds a third consideration. It has a simplified data model and a new database, so moving an existing SAP ERP system to it is not an ordinary upgrade. SAP describes the conversion as a set of steps in which the system is updated, the data is converted to the new data model, and simplification items are worked through. The sections below follow the order of a project, and the Mermaid chart in the next section shows how the phases line up in time.

SAP Activate: the methodology

SAP Activate is the methodology that SAP provides for projects on its solutions. SAP Learning describes its structure with five terms.

  • A phase is a stage of the project. At the end of each phase a quality gate checks that its deliverables are complete.

  • A deliverable is an outcome produced during the project. A phase contains several.

  • A task is the work that produces a deliverable.

  • A workstream is a group of related deliverables that can span several phases, for example project management or application design and configuration.

  • An accelerator is help linked to a task: a how-to guide, a template, a best-practice recommendation or a link to learning material.

There are six phases. SAP Learning calls the four from Prepare to Deploy the core of project delivery, with Discover and Run as additional phases.

Phase What happens

Discover

A non-committal phase in which a customer researches the SAP portfolio. Deliverables include an innovation strategy and roadmap, a value and impact analysis and an implementation strategy. For a system conversion the conversion readiness of the existing system is also checked.

Prepare

Scope, governance and resources are defined, roles are assigned, the starter or sandbox systems are prepared, and the tools for application lifecycle management are set up. The project starts for real.

Explore

The fit-to-standard workshops run on the SAP Best Practices content in a starter or sandbox system. Differences from the standard are captured as delta requirements in a backlog. The test strategy is finalized here.

Realize

The team builds the backlog in iterations: configuration and development on top of the Best Practices content, unit and string testing in the sprints, then integration and user acceptance testing. Data loads and the planning of production operation also belong here.

Deploy

The production environment is finalized, readiness is confirmed, the cutover runs, the system goes live and the hypercare period starts.

Run

Operation of the live solution: support, monitoring, regression tests for upgrades and activation of additional functions. SAP names 16 standards for solution operations, and models such as a Customer Center of Expertise.

In an agile Realize phase SAP uses the following units of time. A sprint lasts two to four weeks and ends with a show-and-tell for the business people who raised the requirement. A wave is a larger period of one to three months with many sprints. A release is all the functions built up to one go-live, and a project can have one or several releases. After the first release goes live the project enters hypercare, and the work on the second release continues through the same phases.

The SAP Activate Roadmap Viewer is the catalog of this content. SAP Learning explains that it lists, for each solution, the deliverables of each phase (the "what"), the tasks that describe the "how", and the accelerators, and that you can search it by phase, workstream or accelerator. Its roadmaps come in four types: cloud-specific, on-premise-specific, upgrade and a general one. The Public Edition course adds that the viewer is part of SAP for Me and needs an S-user to sign in. This guide did not sign in to it, so the description of the viewer rests on those two SAP Learning pages.

Source: SAP Learning: Describing the Methodology Structure, SAP Learning: Accessing Content and SAP Learning: SAP Activate Roadmaps for the Administrator

Three ways to move to SAP S/4HANA

SAP calls these the transition paths. The choice between them is the first big decision of a project, and the names below are used by SAP Learning and by most books.

Path What it means Typical reason to choose it

New implementation (greenfield)

A new SAP S/4HANA system is set up from scratch. Business data is migrated from the old system, which is treated like any other legacy source.

The processes and the custom code of the old system are mostly obsolete, or the company is new to SAP.

System conversion (brownfield)

An existing SAP ERP system is converted to SAP S/4HANA, keeping business data, custom development and configuration.

The company wants to minimize change at first and innovate selectively afterwards.

Selective data transition

Chosen data and configuration are carved out of one or more existing systems and moved to the target.

The company wants a redesign and wants to keep selected history, or to merge several systems.

In a system conversion SAP Learning lists five primary steps: prepare the ERP system by cleaning up custom code and reducing data volumes, migrate the database to SAP HANA if the source is on another database, update the system, convert the table content to the new data model, and implement the mandatory and simplification items. The Software Update Manager (SUM) performs the database migration, update and data conversion. Its Database Migration Option (DMO) combines the three into one procedure. The conversion normally starts with a sandbox copy of the ERP system, where SUM runs its checks and lists the components that are not suitable for conversion. The team repeats the conversion of the sandbox until it is satisfied and only then plans the development, quality and production systems. SAP Readiness Check analyzes add-ons, custom code, data volumes, recommended SAP Fiori apps and sizing, and the simplification item check tells you which simplification items are relevant and whether data inconsistencies would make the conversion fail. The Maintenance planner calculates the upgrade path. SAP Learning presents SAP S/4HANA Cloud Public Edition, a software-as-a-service offering, under the new implementation path.

A new implementation follows the cloud-specific or on-premise-specific roadmap. In the Public Edition SAP Learning describes a landscape of a starter system with preconfigured processes and master data, a quality system and a production system, all provisioned and configured through SAP Central Business Configuration (CBC), plus an optional sandbox tenant. Configuration moves from CBC to the systems through transports, and the production system is kept in sync with quality through weekly or bi-weekly transports. A three-system landscape with a development system is available as an option.

A selective data transition selects among the ABAP repository, the configuration, the master data and the transaction data (for the transactions, open items and a time slice of closed ones, for example two years). SAP Learning names two common patterns. In a shell conversion, a copy of the production system without master and transaction data is converted to SAP S/4HANA and the chosen data is carried over afterwards. In mix and match, a new SAP S/4HANA system is installed and parts of the existing configuration and ABAP repository are transferred. This path uses SAP Landscape Transformation (SAP LT), which is also used for consolidating several systems into one and for moving business units.

Source: SAP Learning: Analyzing System Conversion, SAP Learning: Illustrating Selective Data Transition and SAP Learning: Analyzing options for a new implementation

Choosing a path

No formula decides it, and the book Configuring SAP S/4HANA Finance is honest about that. It names four factors to weigh. Data volume: a company with large volumes gains the most from the speed of SAP S/4HANA, which favors conversion. Business processes: a company happy with its processes leans to conversion, one with many obsolete processes leans to a new start. Custom code: a system with few modifications converts more easily, a heavily customized one may be cheaper to rebuild. Technical readiness: a conversion needs a Unicode system and a recent enough source release, and bringing an old system up to that level adds time and cost. These are the author’s experience-based criteria. For the Public Edition, SAP Learning describes a new implementation.

Central Finance as an option

Central Finance is not a fourth path but a way to start with finance without touching the source systems. SAP describes it as a way to transition to a central SAP S/4HANA system without disruption to the current landscape, which can mix SAP systems of different releases and non-SAP systems. You map the accounts, profit centers and cost centers of the source systems to one common set of master data, replicate the financial and management accounting postings, and report on them in one place. In a typical set-up several source systems connect to one SAP Landscape Transformation Replication Server, which connects to one Central Finance system. The documentation lists SAP ERP, SAP S/4HANA, SAP S/4HANA Cloud Private Edition and Public Edition and non-SAP systems as possible sources, and the target is an SAP S/4HANA system or a Private Edition system. The business function that enables the scenario has the technical name FINS_CFIN. SAP states that before you switch it on you should contact your SAP account executive to verify whether you need a license for Central Finance.

Source: Central Finance and Business function: Central Finance

Fit-to-standard and localization

The old way of starting an ERP project was to write down every wish in a long requirements document. SAP Activate turns this around. In the Explore phase the business people see the standard process running in the starter system and say what does not fit. SAP Learning gives the principles: adopt the standard to lower delivery risk and cost, justify every customization against business value, show instead of tell, involve the business actively, keep the design simple, and reach design acceptance together. The workshop activities are to set a reference value, validate the SAP solution by show and tell, collect delta requirements, create the initial backlog with priorities and estimates, enhance the solution documentation, verify and accept, and plan sprints and releases. The Public Edition adds Business Driven Configuration Questionnaires as a reference for the discussion, and the standard processes themselves are described as scope items in SAP Signavio Process Navigator, with fact sheets, process flows, test scripts and set-up instructions.

Localization is the same exercise for each country. Laws about tax, reporting and accounting standards differ, and not every business scenario is available in every country. SAP Learning notes that in SAP Central Business Configuration the available configuration activities depend on the active scope and the country selections, and that some activities are mandatory, some recommended and some optional. A project with many countries therefore runs a template first, with the processes shared by all, and then one smaller localization exercise per country or country cluster.

Source: SAP Learning: Analyzing each phase of SAP Activate and the Public Edition lesson linked in the previous source block

The project team

SAP Learning describes agile Scrum teams of 5 to 9 members, organized by workstream or by application area, with a Scrum Master and a product owner, usually a business user, who sets priorities. Several teams are coordinated in a "scrum of scrums" for topics of overlap and integration. In a large project each person wears one hat: the project manager only manages, and a testing team tests so that the functional consultants do not. In a small project each person wears several hats, and the consultants may also test. The book adds practical advice that still holds: structure the team by process area, such as record to report, purchase to pay and order to cash, with a lead from the consulting side and a lead from the customer side for each; add architects who watch the end-to-end integration, because that is where problems appear; keep a technical team for custom development and Basis; staff testing with a test lead; and form a separate team for go-live and hypercare that hands over to the long-term support team.

Source: SAP Learning: Analyzing each phase of SAP Activate

Data migration

Data migration is the work that surprises most newcomers by its size. The tool SAP provides for it in SAP S/4HANA is the SAP Fiori app Migrate Your Data - Migration Cockpit. SAP describes its key features: you create migration projects and monitor them, select the migration objects relevant for the scenario, process mapping tasks, simulate the migration before loading and then migrate. A migration object describes how the data of one business object is moved. There are two approaches. With staging tables, the cockpit creates a table for each migration object of the project, you fill it from the template file of the object or with your own tool, and the cockpit migrates from the tables into the target. When you create the project you choose where the tables live, in the local schema of the system or in a remote SAP HANA schema. With the direct transfer, the cockpit reads certain SAP source systems itself. The Public Edition has the same app. The earlier tool, the transaction LTMC, is deprecated and can no longer be used to migrate data, although projects created in it can still be viewed. The ABAP page on batch input and data migration explains the staging-table and direct-transfer approaches in detail and why LSMW and batch input are legacy tools.

For a project the practical steps are the same under both approaches: decide which objects to migrate and from which year (for open items and balances this is a business decision, not a technical one); clean the source data before it is loaded, because the cockpit migrates what it is given; map the values of the old system to those of the new one; simulate, correct the reported errors and simulate again; and repeat the whole migration several times in a test system before the final run. SAP’s data protection note on the staging tables adds a point that is easy to forget. Personal data that should have been deleted must not be migrated, because loading it into the new system can be processing without a legal purpose, and the staging tables must be protected so that only authorized users can read and change them.

In a system conversion the conversion itself carries the existing data over to the new data model, so the cockpit plays no role for that data. In the selective data transition, SAP LT carves out the chosen data. In Central Finance, replication carries the postings.

Source: Migrate Your Data - Migration Cockpit (on premise), Migrate Your Data - Migration Cockpit (Public Edition), Migrate Data Using Staging Tables, Data Migration and Migration Cockpit (Transaction LTMC) - Deprecated

Testing

Testing is planned early and run in stages. SAP Activate finalizes the test strategy in the Explore phase and recommends that the testers join the fit-to-standard workshops, so that they understand the solution before they test it. The test cycle that SAP lists is unit testing (if applicable), business process (string) testing, integration testing, data conversion testing, business or user acceptance testing, performance testing, translation testing (if applicable) and load testing (if applicable). In plain words:

  • Unit test: one function or one configured piece works on its own. The consultant does it, usually in the sprint that builds it.

  • String test: a short chain of steps across the pieces built in earlier sprints still works.

  • Integration test: all functions built, across all processes and interfaces, work together. It is the last test by the consulting team before the business tests.

  • Data conversion test: the migrated data is complete and correct.

  • User acceptance test (UAT): business users run their own processes and sign off.

SAP separates the user acceptance testing done during the sprints from the final business acceptance test planned just before the end of Realize. The final test is an extensive end-to-end test on migrated business data that confirms the solution, the data and the organization’s readiness to go live. The test strategy also states which data, systems and environments each stage uses and how test data is refreshed.

In the Public Edition, SAP delivers help with this. The Manage your test processes app lets the team build test plans from test processes that match the active scope items and that are automated versions of the test scripts in SAP Signavio Process Navigator. A test data refresh service can copy master and transaction data from production to quality, with depersonalization, because transports only flow from quality to production. SAP Cloud ALM can prepare and run manual and automated test cases and track which transports belong to which feature.

Source: SAP Learning: Analyzing Testing and Deploy and SAP Learning: Analyzing options for a new implementation

Cutover, go-live and hypercare

Cutover is the set of activities carried out on the last weekend before go-live, in the period between switching off access to the old systems and switching on access to the new one. SAP plans the cutover in the Realize phase and executes it in the Deploy phase, and the cutover tasks can themselves be managed in sprints. The Activate roadmap offers a cutover template. Before the real go-live SAP recommends a dry run or dress rehearsal, which exposes planning or technical problems. The issues it finds are analyzed and fixed according to their criticality, the remaining risk is estimated, and only then does the go or no-go decision follow.

A cutover plan answers three questions: which tasks run in which order, who does each one, and what happens if something fails. The book lists items that any plan for finance should contain, and they are good examples of why cutover is more than a data load. All transports must have reached production, because nothing configured in development helps if it was never transported. Master data and then balances and open items are loaded. Number ranges are checked, because they are not transported. Tax codes may need a manual step. The book also recommends a written backup plan that describes how to return to the legacy system, with short and specific timelines, and advises choosing the go-live date to coincide with the start of a fiscal year, planning the first go-live in one or two less complex countries, and avoiding a go-live in the last one or two months of a fiscal year. It treats a big-bang go-live of many countries at once as risky for all but small companies. This is practical advice from the author’s experience and not an SAP rule.

After go-live the Deploy phase continues with hypercare. SAP Learning says the team stays on site for a predetermined period, usually fixed in the contract or in the plan for the transition to operations, and helps IT and business people adopt the function. The book speaks of about a month and gives a useful picture of the first day: a defect system to which users report issues with a priority, quick answers to simple matters such as lost passwords, and explicit checks that the critical processes run, such as sales orders, invoicing, payments, tax determination and account determination. Typical background jobs are scheduled in production, and the team transfers knowledge to the long-term support team. After hypercare comes the Run phase and its standards for operation.

Source: SAP Learning: Analyzing each phase of SAP Activate and SAP Learning: Analyzing Testing and Deploy

Where older books are outdated

The book Configuring SAP S/4HANA Finance (3rd edition, 2025, SAP S/4HANA 2023) is the most current source for the finance side of a project, and its chapters on project preparation, requirements, data migration, testing and go-live remain sound as practice. Measured against the baseline of this page, some things changed or were never covered.

  • Methodology. The book speaks of a business blueprint and requirement documents, and does not use SAP Activate, its six phases or the fit-to-standard workshops with a backlog. Today SAP Activate is the way SAP describes projects, and the Public Edition expects the fit-to-standard approach.

  • Project tool. The book organizes requirements, configuration and tests in SAP Solution Manager. SAP Learning for the current methodology presents SAP Cloud ALM as the system that manages the implementation and the landscape, and it mentions Solution Manager only in the context of the Run standards.

  • Testing tools. The book compares third-party test management tools and plans testing in a sandbox client, a unit-test client and an integration client of the development landscape. In the Public Edition there are no such clients to create: the starter, quality and production systems come from SAP Central Business Configuration, a sandbox tenant has no transport path, and test automation is built in.

  • Release facts. The book targets SAP S/4HANA 2023 and mentions the move to a release every second year. SAP S/4HANA 2025 FPS02 is the on-premise baseline of this page, and the Public Edition is on release 2608.

  • Readiness checks. The book runs individual check programs and Customizing checks for finance before a conversion. Current SAP material adds SAP Readiness Check and the simplification item check for the whole system, the Maintenance planner for the path, and SUM with DMO for the conversion itself. Treat the finance checks as one part of that picture.

  • Central Finance. The book describes it as a real-time replication from SAP and non-SAP systems. The documentation also lists SAP S/4HANA Private and Public Edition systems as possible sources.

  • Cutover rehearsal. The go-live chapters describe a cutover plan and a backup plan but do not discuss a dress rehearsal with a go or no-go decision, which SAP Activate treats as part of Deploy.

  • Data migration. The chapter on migration is current in naming the app Migrate Your Data - Migration Cockpit and in recommending it over LSMW. It does not cover the Public Edition variant or the remote staging schema in depth.

Source: SAP PRESS: Configuring SAP S/4HANA Finance

Summary

  • An SAP project follows SAP Activate: Discover, Prepare, Explore, Realize, Deploy and Run, each ending in a quality gate.

  • The first decision is the transition path: new implementation, system conversion or selective data transition. The Public Edition is described as a new implementation, and Central Finance is an option to start with finance only.

  • Fit-to-standard workshops replace the long requirements document. Only the differences from the standard are built, and localization repeats the exercise per country.

  • The SAP S/4HANA migration cockpit migrates data with migration objects, from staging tables or directly from a source system, and it replaces the deprecated LTMC and the legacy LSMW.

  • Testing runs in stages, from unit to final business acceptance on migrated data, and the cutover is rehearsed before the go or no-go decision.

  • Hypercare follows go-live inside the Deploy phase and ends with a handover to Run. Older books describe a blueprint-and-Solution-Manager project and miss SAP Activate, Cloud ALM and the Public Edition tooling.
