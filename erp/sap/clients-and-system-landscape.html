Clients and the System Landscape

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

When you log on to an SAP system you do not only choose a user name: you also choose a number called the client. A newcomer meets the client on the very first logon screen, and meets the system landscape the first time somebody says "that change is in DEV, it is not in QAS yet". This page explains both ideas in plain words: what a client is, which data belongs to a single client and which data is shared by every client of the system, why companies run several systems (development, quality assurance and production) instead of one, and which extra clients (Customizing, sandbox, test and training) are common inside them. After reading it you can understand a sentence such as "test it in client 200 of QAS" and know what it implies for your data and your changes. It is written against SAP S/4HANA 2025 FPS02 on premise and Private Edition, where clients and systems are managed by the customer or the hosting partner, and against SAP S/4HANA Cloud Public Edition 2608, where SAP runs the systems and the documentation speaks of systems and tenants instead of clients (see the section on Public Edition below). The client rules in the ABAP platform documentation apply to every classic ABAP system, so they hold for SAP S/4HANA on premise and Private Edition. The page uses the fictitious "Example Trading Co." and its client and system names are examples, not values SAP prescribes.

Before you read

  • Getting Started: what an ABAP system and a development object are.

  • DDIC Tables and Structures: how a table gets its client field.

  • Packages, Transports, gCTS and abapGit: how changes travel from one system to the next.

Key terms

  • Client: a self-contained commercial, organizational and technical unit inside one SAP system, with its own master records and its own set of tables.

  • Client-dependent data: data that belongs to exactly one client and cannot be read or changed from another client.

  • Cross-client data: data that exists once per system and is identical and visible in every client of that system.

  • System landscape: all the SAP systems of a company or application area, linked by transport routes.

  • Customizing client: the client where configuration settings, and possibly development, are made before they are transported on.

  • Sandbox client: a client for trying client-specific settings without any commitment; what you keep is entered again in the Customizing client.

  • Transport request: the container that carries a change to the next system.

What a client is

SAP defines a client as a self-contained commercial, organizational and technical unit within an SAP system. All business data inside a client is protected from the other clients, and each client has its own customer data, which the documentation calls the exclusive property of that client. The idea came from service providers that wanted to serve many customers from one installation without installing and administering a separate physical system for each one. In a company the same idea is used differently: one installation, several clients for different jobs. Teams that speak Spanish often say mandante for client. In the data model the client stands for the customer entity: it does not take part in modeling the business application, it only makes sure that everything created in business processes is assigned to its owner.

A client is chosen at logon, and everything you do afterwards happens in that one client. For a newcomer the practical consequences are these.

  • The same user name can exist in several clients with different rights, because users are maintained per client.

  • A material, a customer or an open invoice that you create in client 100 does not exist in client 200 of the same system, even though both clients live on the same database.

  • A table row belongs to one client through a client field. In the ABAP Dictionary this is the first key field, usually called MANDT in older tables and client in newer ones, as described in the client field section of the DDIC page. ABAP SQL restricts reads and writes on such a table to the logon client automatically.

Source: Customer Data and System Data (ABAP platform, Client Concept) and Client Concept

Client-dependent and client-independent data

The most important sentence of this page is that some data is private to a client and some is shared by all clients of the system. The ABAP platform documentation states the basic rule: only the assigned client can read or write its customer data, and every client can read the centrally stored data, which only the system operator may change. SAP data models map customer data to client-specific tables and central data to cross-client tables, also called client-independent tables.

Kind of data Examples Seen from

Client-dependent: application data

master data and transaction data, for example the customers and invoices of one company

only the client that owns it

Client-dependent: Customizing

organizational structures such as the company codes of the enterprise, and parameters that control business processes

only the client where it was set

Client-independent: repository

programs, classes, ABAP Dictionary definitions and other development objects

every client of the system, immediately

Client-independent: Customizing

cross-client control data and Customizing tables without a client field

every client of the system, immediately

Application tables, which hold master and transaction data, carry the value A in the attribute delivery class in the ABAP Dictionary, which is how the documentation identifies them. Customizing tables are usually changed in groups rather than one by one: a Customizing object bundles the related tables so that edits stay consistent. A Customizing object is client-specific if every table it maintains is client-specific. If at least one cross-client table that it maintains can be changed, the whole object counts as cross-client, which is why changing one setting in a client can sometimes change the behavior of every other client. The majority of business Customizing is client-specific.

The consequence for the landscape below is easy to state and easy to forget. A development object that you change in one client is changed for all clients of that system at the same moment, because the repository is client-independent. A client-specific Customizing value changes in that client only. Both kinds of change are recorded in transport requests, but of different kinds: changes to repository objects and to client-independent Customizing are recorded in Workbench requests, and changes to client-specific Customizing are recorded in Customizing requests. Using only Customizing requests lets the result of a Customizing project reach a target client of another system without touching its other clients, while a Workbench request cannot give that guarantee, so its import has to be checked for cross-client objects.

Source: Customer Data and System Data and Client Control

Why more than one system

If every change were made directly in the system where people work, a faulty setting could stop invoicing. SAP therefore recommends separating the places where you change things, test them, and use them for real. The documentation names three central roles. The Customizing and development client, abbreviated CUST, is where configuration settings and possibly ABAP development are made. The quality assurance client, QTST, is where those results are tested, because the many dependencies between Customizing settings mean that correctness can only be guaranteed by extensive testing. The production client, PROD, is used for real business, and no Customizing, no development and no tests are done there. These three clients exist in every landscape.

Where the three roles are placed decides how safe the arrangement is. SAP describes three groupings.

  • In the three-system group, which SAP recommends, each central client has its own system: a development system DEV with the Customizing client, a quality assurance system QAS with the quality assurance client, and a production system PRD with the production client. All changes to Customizing data and repository objects are made in the Customizing client. When the change requests are released, they are transported into the quality assurance client, so a change to cross-client data appears in QAS only after the transport. There the team tests whether the transports are complete or whether linked changes are still sitting in unreleased requests. If the test succeeds, the requests go on to production, whose cross-client data is completely separate from the other clients.

  • In the two-system group, meant for smaller implementations where little workbench development takes place, the quality assurance client lives in the development system. The disadvantage is that cross-client data is shared between the Customizing client and the quality assurance client, so a change in one can disturb tests in the other and the completeness of transports cannot be guaranteed: tests may pass and errors still appear after the transport to production.

  • A one-system group, with all central clients in a single system, is not recommended. Shared hardware and shared cross-client data restrict the system, and once it is productive you can no longer develop in it unless you stop production for the development and test phases.

Source: System Landscape (Change and Transport System) and Clients and Their Roles

The extra clients

Besides the three central clients, you can set up further clients for other tasks. Each extra client takes additional main memory and database space and has to be administered: you maintain user authorizations in it and distribute changes to it with the Change and Transport System. The documentation tells you to weigh advantages against that cost. It names these examples.

  • The development test client (TEST) lets developers test their Customizing and development before releasing the change requests, and create test application data for realistic tests. It always sits in the same system as the Customizing client, so changes to cross-client data are visible there at once. Client-specific changes are copied from the Customizing client with a special client copy that uses the unreleased change requests. In this client you cannot change Customizing data and repository objects.

  • The prototype or sandbox client (SAND) is where you try client-specific Customizing settings when you are not sure you want them. Settings you want to keep are entered again in the Customizing client. To avoid conflicts, you cannot change cross-client Customizing data and repository objects in the sandbox client, and the Change and Transport System does not record or transport client-specific Customizing changes made there.

  • The training client (TRNG) prepares end users for new functions that are about to be transported into production. Users practise with specially created application data. The documentation sets up the training client in the quality assurance system, and, like the test client, it does not allow changes to Customizing data and repository objects.

For Example Trading Co. this could mean: the Customizing client of DEV holds the company code EX01; an accountant who wants to try a new payment-terms variant uses the sandbox client and, if she likes it, asks the configuration team to enter it in the Customizing client, from where it is transported to QAS and later PRD. A trainer teaches the new process to the sales team in the training client of QAS using invented orders, so no real customer is touched.

Source: Clients and Their Roles

How a client is protected: client control

If every change in every client were recorded for transport, a sandbox or training client could produce unintended transports that damage a target client. The system therefore lets you give each client attributes, which you maintain in table T000 with the generic table maintenance transaction SM30. These are the settings the documentation lists.

  • Role of the client: whether the client is production, test, training, demo or Customizing.

  • Changes and transports for client-specific Customizing objects: changes without automatic recording, automatic recording of changes, no changes possible, or changes without automatic recording and no transports allowed.

  • Changes to cross-client objects: whether changes to repository objects and client-independent Customizing objects are allowed in the client.

  • Further protections: a lock on the logon procedure that the client copy program sets in the target client during a copy, after which only the users SAP* or DDIC may log on, and protection against SAP upgrade, which stops the client from receiving SAP upgrades.

The setting selected for a client applies only to its client-specific Customizing, not to client-independent settings, which are recorded together with repository objects. In a production client the client control does not influence current settings, the Customizing activities reachable directly in the application menu; these can always be changed and are not recorded in Customizing requests. A practical rule follows from the roles: allow recorded changes in CUST, forbid changes in QTST, PROD, TEST and TRNG, and allow unrecorded changes in SAND.

Source: Client Control

Clients delivered with a new system

A freshly installed classic ABAP system contains two delivered clients. Client 000 is the SAP reference client. It holds all SAP tables, sample entries for the tables that store the organizational structure, default Customizing, but no master or transaction data. SAP updates it with each release, so client 000 always has the current status, and it is used to copy default settings into other clients. The documentation says you must not make it productive. Client 001 is the production preparation client: it is identical to client 000, so it is not used for production either, but the Customizing is meant to be made in it. A new company usually creates its own clients by copying one of these, using the client copy function that is reached through the administration menu for clients. The documentation describes this for the ABAP platform; whether your hosting partner pre-creates other clients is a project matter.

Source: Customizing Clients (ABAP platform)

Public Edition: systems and tenants

SAP S/4HANA Cloud Public Edition is run by SAP, and its documentation describes systems and tenants, not the clients of a classic installation. Depending on the installation, it is based on a two-system or a three-system landscape, and the availability of the three-system landscape has to be checked with the SAP account executive. The three-system landscape has a development system, a test system and a production system. The development system is divided into a customizing tenant, for configuration and low-code key user extensions, and a development tenant, which gives access to the ABAP environment for developer extensibility; a parallel customizing tenant belongs to the optional parallel line. The test system has a test tenant, and the production system a production tenant. The two-system landscape consists of a quality system, which combines development, configuration and testing, and a production system.

The same separation of duties applies: as a rule, extensibility and business configuration changes cannot be made directly in the test and production tenants, except for system-specific settings such as number ranges. Transports of different categories (customizing, key user extensibility and developer extensibility) cannot be merged into one request, and the administrator moves them with the Import Collection app. You can check which tenant you are in through the About screen, which shows the tenant role.

Common mistakes

  • Testing in the wrong client. A test in the development client sees the same repository objects as production will, but not the same Customizing or data. Always test in the quality assurance client after the transport.

  • Forgetting that repository changes are system-wide. A report you change while working in the sandbox client changes it for every client of DEV. This is why the sandbox client does not allow repository changes.

  • Making Customizing changes in several clients. Make them in the Customizing client and transport them, as SAP recommends, otherwise the clients drift apart.

  • Missing transports. In a two-system group, cross-client data is shared, so tests can pass although a transport is missing; SAP names this as the main weakness of that arrangement.

Summary

  • A client is a separate business view inside one SAP system, chosen at logon; client-dependent data is visible only in its client, cross-client data is shared by all clients of the system.

  • Repository objects are client-independent and Customizing may be either; Customizing requests carry client-specific settings and Workbench requests carry the rest.

  • SAP recommends a three-system group DEV, QAS and PRD with the Customizing, quality assurance and production clients, and describes sandbox, development test and training clients as optional extras.

  • Client control in table T000 decides in each client whether changes are recorded, allowed or forbidden.

  • In SAP S/4HANA Cloud Public Edition the same separation is described with systems and tenants rather than clients.
