Security and Operations

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

An ERP system holds the money, the employees and the customers of a company, so two questions never go away: who may do what, and how can we prove afterwards who did what. Security is the first question: locking the doors, giving each person only the keys they need, and keeping the building repaired. Operations is the second: the cameras and the visitor book that run every day, and the routine of installing fixes. This page explains the topics of the official SAP S/4HANA Security Guide in that order: protecting communication, handing out the smallest possible permissions, the logs (above all the security audit log read with the transactions SM19 and SM20, and read access logging), and the habit of patching. It is written for S/4HANA 2025 FPS02 on premise and in the Private Edition, where your own administrators run the system and the Security Guide applies in full, and it says for each topic what changes in the Cloud Public Edition 2608, where SAP runs the system and you work through apps and business roles. Every procedure here needs an SAP system, so nothing on this page was run here; the steps are described in words from the official pages.

Before you read

  • The SAP pages on users, roles and authorizations and on transports and change management go deeper into two topics that this page only summarizes.

  • Authorization Checks: how an ABAP program asks the system whether a user may do something, which is the code-level side of least privilege.

  • Transports, Packages and gCTS: how changes travel from development to production, which matters for the change and transport log below.

Key terms

  • Security audit log: a record of security-relevant events on a technical level, such as logons and transaction starts, kept for auditors.

  • Read access logging: a record of who looked at particularly sensitive data and when, switched on for the data you choose.

  • Least privilege: the rule that a user, or a technical connection, gets only the permissions its task needs and nothing more.

  • Secure by default: SAP’s approach of installing a system with the recommended protective settings already switched on.

  • SAP Note: a document from SAP that describes a correction or a recommendation and is referred to by its number.

  • Transport Layer Security (TLS): the protocol that encrypts web connections, known earlier as Secure Sockets Layer (SSL).

Where the Security Guide sits

SAP publishes a Security Guide for SAP S/4HANA and SAP S/4HANA Cloud Private Edition 2025 (the copy read for this page is document version 3.0 of 2026-10-07). Its introduction says that it covers the security information that applies to S/4HANA in general, with area-specific chapters for particular applications, and that, unlike an installation or migration guide, it is relevant in every phase of the life cycle. Its readers are technology consultants, security consultants and system administrators.

Because S/4HANA runs on the ABAP Platform and the SAP HANA database, the guide does not repeat what those layers already document. It points to the Application Server ABAP security guide, to the ABAP Platform Security Guide and to the SAP HANA Security Guide, and to the SAP Fiori and SAP Gateway security documentation for the web front end. It also tells readers to use the Secure Operations Map, a reference model for structuring the whole field of security, and to read the security whitepapers that SAP lists on its support site. For SAP S/4HANA Cloud Private Edition the guide adds that some of the tasks it describes are covered by services that SAP offers; the scope of these services is agreed in your subscription.

The chapters used on this page are user administration and authentication, system hardening and patching, network and communication security, frontend security, file system access security, SAP HANA security, virus scanning, security logging, additional system hardening and data protection and privacy.

The Cloud Public Edition has its own documentation, "Protect Your SAP S/4HANA Cloud Public Edition", and its security recommendations page states that the product is delivered with secure default configurations wherever this is possible, while you should still review settings such as user and authorization management against your own policies. The sections below name the matching Public Edition pages.

Source: Security Guide for SAP S/4HANA and SAP S/4HANA Cloud Private Edition 2025 (PDF) and Security Recommendations (Public Edition)

The layers of protection

A security measure belongs to one layer, and the guide is organized by layers. The figure below follows a request from the user to the data, and names where each chapter of the guide applies.

Securing communication ("transport security")

The word transport has two meanings in an SAP system. This section uses the networking meaning: data traveling between a user’s device, the server and other systems, which the guide covers under network and communication security. The other meaning, a transport request that carries changes from development to production, is covered in the logs section below, because the Security Guide treats it through the change and transport log.

The guide lists the protocols with which S/4HANA talks to internal and external applications and how each one is protected.

  • HTTPS: web connections are protected by Transport Layer Security (TLS).

  • Remote Function Call (RFC): connections can be protected with Secure Network Communications (SNC). The guide refers to SAP Note 2008727 and the whitepaper on securing remote function calls.

  • SOAP: connections are protected with web services security.

  • IDoc and REST are also named as protocols in use.

The guide’s advice is short: use the secure protocols (TLS, SNC) whenever possible. For internet communication it points to SAP Note 1616535.

The guide also gives the network advice of any server room: a system that offers internet services should at least sit behind a firewall, the systems can be divided into groups placed in different network segments with a firewall for each segment, and unauthorized access can also come from the inside once a malicious user controls one of your systems. Because S/4HANA runs in the ABAP Platform it uses the ports of the Application Server ABAP, documented in the corresponding security guides.

For connections between systems (communication destinations) the guide lists general rules.

  • Use the user types "system" and "communication" for such connections.

  • Grant such a user only the minimum of authorizations.

  • Tell users to choose a secure password and not to share it.

  • Store user-specific logon data only for users of the types "system" and "communication".

  • Use trusted system functions instead of user-specific logon data wherever possible.

In the Cloud Public Edition the same idea is expressed through communication arrangements. For outbound calls the external system must present a trusted server certificate, and the S/4HANA system can present a client certificate in return. For inbound calls the authentication method is set in the communication arrangement, and for certificate-based authentication the external system must present the certificate that is stored there, signed by an approved certification authority. Other methods such as OAuth or user and password are possible depending on the external system.

Source: Security Guide for SAP S/4HANA and SAP S/4HANA Cloud Private Edition 2025 (PDF), chapter Network and Communication Security and Server Communication Security (Public Edition)

Protecting the browser side

The front end is the user’s own computer, and the guide treats it as a layer of its own. SAP’s measures are configured on the server but enforced in the browser. The guide names these points.

  • Internet Communication Framework (ICF) services: activate only the services your applications need, using transaction SICF.

  • Session cookies: activate HTTP security session management with transaction SICF_SESSIONS, and set the profile parameters icf/set_HTTPonly_flag_on_cookies (recommended value 0, which adds the HttpOnly flag) and login/ticket_only_by_https (recommended value 1, which adds the Secure flag).

  • Content Security Policy: a browser-side list of the places scripts, styles and fonts may be loaded from, defined in transaction ICF_HEADER_FRAMEWORK.

  • Click-jacking protection: the HTTP allowlist of the ABAP Platform, maintained with transaction UCON_CHW, decides which pages may show your application in a frame. From S/4HANA 2021 onwards it is active by default for new and for converted systems.

  • Cross-site request forgery: defended inside each web application, so the guide refers to the application chapters.

  • Additional headers: the guide recommends adding the header X-Content-Type-Options with the value nosniff in the SAP Web Dispatcher or the Internet Communication Manager, and warns that header rewrites change application behavior and need careful tests.

  • SAP GUI scripting: it can change data on a large scale, so the guide says to activate it only if necessary.

Source: Security Guide for SAP S/4HANA and SAP S/4HANA Cloud Private Edition 2025 (PDF), chapter Frontend Security

Least privilege

Least privilege means that nobody, and no program, can do more than the job needs. The guide returns to it in several places, and together they form a practical checklist.

  • Users and roles. S/4HANA uses the user management of the Application Server ABAP; business roles structure what a user may reach in the SAP Fiori launchpad. The guide sends the reader to the role maintenance documentation and to the topic "From the Programmed Authorization Check to a Role" for custom code. The code side of that chain is described in Authorization Checks; the administration side is the subject of the page on users, roles and authorizations, roles and authorizations of this section.

  • Technical connections. Connections between systems use the minimum of authorizations (see the rules above).

  • The database schema. Business authorizations only work inside the application. A person who can read the tables directly on the database skips them, so the guide says to restrict permissions on the ABAP schema as much as possible, ideally to no database user at all. Data transfers on the SAP HANA level, for example with the tools SDI or SLT, are critical: if one is needed, use a dedicated user per transfer scenario with only the privileges that scenario needs, and consider auditing and logging carefully.

  • Remote function calls. The Unified Connectivity (UCON) framework lets you decide which remote function modules can be called from outside: a module can be called externally only if it is assigned to a communication assembly, and external access is blocked for all others, whatever the user’s roles say.

  • Switchable authorization checks. The Switchable Authorizations Check Framework (SACF) adds extra checks for specific scenarios that stay inactive until you activate the scenario. Most of them are inactive by default for compatibility, and the guide strongly recommends activating all of them. Transaction SACF is used for customizing and SACF_COMPARE for comparison; the guide also refers to SAP Note 1922808.

  • Starting transactions from code. When a user starts a transaction by hand, the kernel checks the authorization object S_TCODE. When a program starts it with the ABAP statement CALL TRANSACTION, whether that check happens depends on the setting made with transaction SE97 and the profile parameter auth/check/calltransaction. For new installations the guide recommends the value 3, which switches the check on; for a system moved from SAP ERP the value 2 keeps the earlier behavior for a smooth transition, but it is not recommended as a permanent setting.

  • File access. Applications that write files must use logical paths and file names that map to physical paths, so that nobody can reach other directories (directory traversal). For compatibility the validation is off by default; you switch it on per path with the transactions SFILE (client-independent) and SF01 (client-dependent). For new installations the guide recommends setting REJECT_EMPTY_PATH=ON in the table FILECMCUST with transaction SM30 (see SAP Note 2251231), and it names the security audit log events CUQ, CUR, CUS, CUT, DU5 and EU4 as a way to find out which paths a system uses.

In the Cloud Public Edition the model is business roles built from business catalogs, with restrictions on the values a user may see. The Public Edition also offers authorization trace logs, which can be activated on demand to develop, test and analyze the authorization concept.

Source: Security Guide for SAP S/4HANA and SAP S/4HANA Cloud Private Edition 2025 (PDF), chapters User Administration and Authentication, SAP HANA Security, File System Access Security and Additional System Hardening Activities and Security Logging (Public Edition)

The logs of an S/4HANA system

Logging answers "what happened". The guide strongly recommends activating the security logs for monitoring, compliance and traceability, consolidating them in a central security information and event management (SIEM) solution, reviewing every log configuration against your corporate logging policy, restricting access to the logs on a need-to-know basis, and configuring retention policies for each kind of log. It splits the logs into those that are always active and those you can switch.

The SAP HANA database has its own audit log. The guide recommends activating it with suitable audit policies in all systems and refers to SAP Note 3016478. A newly installed S/4HANA system comes with the mandatory policies of that note installed, the logs are written into an SAP HANA table, and the retention is 20 days for the policies on failed connections and on all user validations and 180 days for all other policies. During a system conversion policies are set only if no audit policies existed before, so that your own logging concept is not disturbed.

Source: Security Guide for SAP S/4HANA and SAP S/4HANA Cloud Private Edition 2025 (PDF), chapters Security Logging and SAP HANA Security

In the Public Edition the log types are security audit logs, change documents (shown with a Display Changes button in the apps), read access logs, authorization trace logs and SAP support user request logs. The last one records when and why SAP support users accessed your system and is kept for 12 months, shown in the Display Technical Users app on the tab SAP Support User Request Log. Unless noted otherwise, these logs are active and cannot be deactivated. Timestamps are synchronized with Network Time Protocol (NTP) servers so that logs of different systems can be correlated.

Source: Security Logging (Public Edition)

The security audit log with SM19 and SM20

The security audit log is the log for auditors. The ABAP Platform documentation says it records, among other things, successful and unsuccessful dialog and RFC logon attempts, RFC calls to function modules, successful and unsuccessful transaction and report starts, changes to user master records, changes to the audit configuration, file downloads, use of digital signatures and viruses found by the Virus Scan Interface. It adds a caution that the log contains personal information that may be protected by data protection law, so check the rules that apply to you before you use it. The log complements the system log: the system log is for administrators and signals system problems, is needed continuously and is circular, while the audit log is for auditors, can be activated and deactivated as needed, is kept per day on each application server and must be archived or deleted by hand.

The work happens in three steps, each with its own transaction.

  1. Prepare. Before configuring, set the parameters, which the documentation describes on the screen of transaction RSAU_CONFIG in its Parameters folder. Some of them need a restart of the Application Server ABAP, and the screen shows a warning icon next to those. The documentation recommends setting them dynamically in the audit configuration, after which the system ignores the same profile parameters of the instance profile except DIR_AUDIT and FN_AUDIT. An older page of the ABAP Platform documentation lists the classic profile parameters, among them rsau/enable, which is 0 by default, meaning the log is not active.

  2. Configure with SM19. The transaction SM19, "Security Audit Log - Display of Current Configuration", is the place to configure the log. You decide which events to record in filters. A filter set can be saved in a static profile in the database, which the system loads at startup and applies to all instances, or you can change filters dynamically on one or several application servers without a restart. The technical description of the events is in transaction SE92.

  3. Read with SM20. The transaction SM20, "Selection of Audit Events from the Audit Files", produces the audit analysis report. You restrict it by date and time, instance name, client, user, terminal and a text in the message, and you choose between a general or detailed selection or a profile and filter defined in SM19. You can choose the data source, audit files, table or both, and a statistics-only display. The transaction SM20_ADM offers a pseudonymized view in which user names and terminal names are replaced by a generated hash code. Double-clicking a message shows more about an event.

The same documentation set describes statistical analysis (for workload analysis and threat detection), the management of security alerts through a CCMS alert monitor or an external interface, and the management and archiving of audit data. The older page also names transaction SM18 for deleting old logs.

What the Security Guide adds is the stance toward configuration. Security audit logging is active by default in new systems, and SAP recommends switching it on in existing systems at least for the events that are logged by default in new systems; SAP Note 2926224 lists those defaults. SAP Note 2676384 gives best practices for configuring it, and SAP Notes 539404 and 2191612 answer frequent questions. After a system conversion, the secure-by-default audit configuration is activated only when the source system had no audit configuration of its own.

In the Public Edition there is no transaction to start. The app Display Security Audit Log shows security-relevant events, with a default retention of 45 days that is configured in the Manage Security Audit Log app. To open it a user needs a business role that contains the business catalog Security - Security Audit Log (SAP_CORE_BC_SEC_SAL), which is part of the business role template External Auditor (SAP_BR_EXTERNAL_AUDITOR) and of the Administrator role (SAP_BR_ADMINISTRATOR). Entries can be archived with the archiving object BC_SAL, and an interface lets a SIEM download the entries.

Source: ABAP Platform: Security Audit Log, Preparing the Security Audit Log, Configuring the Security Audit Log, Displaying the Audit Analysis Report, Comparing the Security Audit Log and the System Log, The Security Audit Log (older page, version 201909), Security Audit Log (Public Edition) and Display Security Audit Log (Public Edition)

Read access logging

The security audit log records technical events; it does not tell you which person looked at which bank account. Read access logging (RAL) does. The ABAP Platform documentation defines it as monitoring and logging read access to sensitive data, and lists the questions it answers: who accessed the data of a business entity such as a bank account, who accessed personal data of a business partner, and which accounts or business partners were accessed by which users within a time frame. All the interfaces that read the data must be enabled for logging; the channels named are remote function calls, Dynpro, Web Dynpro, web services and ALE and IDoc.

Three concepts define what is logged.

  • A logging purpose classifies each log entry, for example data protection or finance records.

  • A log domain classifies and groups the fields that appear in an entry, for example "HR - User data".

  • A configuration says which read access is logged and under which conditions. It has a log context (the key field the other fields belong to, such as the employee number, so that a salary is logged with the correct employee), one or more log groups (the fields displayed together) and optional conditions.

SAP delivers sample configurations for applications, but the documentation expects the customer’s administrator to adapt them, because the legal requirements of an organization are not all known to SAP. A configuration is loaded only when logging is active in the client, the user is not on the exclusion list and the field to log is part of an active configuration. The documentation also reminds that logging has a cost: the more data and the more complex the conditions, the greater the effect on performance.

The Security Guide gives the practical steps for delivered configurations. In transaction SRALMANAGER, on the Administration tab page, choose Configuration, choose a channel such as WebDynpro, choose Search to list the available configurations, and choose Display Configuration for the details. Before the delivered configurations work, you must activate them and enable read access logging in each system client. SAP Note 2347271 lists the delivered configurations. The guide warns that read access logs contain very sensitive data, so access to them must be restricted carefully, and that personal data entering the system in uncontrolled ways (free-text fields, APIs, customer extensions) is not covered by the example configurations. To evaluate the log, the app Read Access Logging: Monitor needs the business catalog SAP_CORE_BC_RAL, which is in the business role template SAP_BR_DATA_PRIVACY_SPECIALIST.

In the Public Edition, read access logs must also be configured by the customer to match the purpose and requirements of the business, and the same documentation applies.

The Security Guide ties RAL to data protection. It lists the functions that support data protection compliance: Read Access Logging, the deletion of personal data with SAP Information Lifecycle Management (ILM), the Information Retrieval Framework (reports run with the transactions DTINF_START_COLL and DTINF_PROC_COLL) and Consent Administration. It states that in most cases compliance with data privacy laws is not a product feature, that SAP does not give legal advice, and that decisions on data protection must be made case by case. This page repeats that: it is not legal advice.

Source: ABAP Platform: Read Access Logging, Configuring Read Access Logging, Read Access Logging: Monitor, Security Guide, chapter Data Protection and Privacy (PDF) and Read Access Logging (Public Edition)

Hardening, patching and SAP Notes

Hardening means removing the weak spots that a default installation leaves. The guide’s approach is secure by default: during installation, system copy and system conversion from SAP ERP, SAP applies protective settings to the profile parameters, to ABAP platform configurations and to SAP HANA auditing. The rules differ by case.

  • New installations and system copies: you may skip the activation of the secure profile parameters; the ABAP platform configurations and the HANA auditing are always enabled.

  • System conversions: you may skip the profile parameters; the platform configurations and the auditing are enabled only when the source system has no customer configuration for that topic. The guide’s example is the security audit log, which is switched on only when the source system has no audit configuration.

SAP Note 2926224 describes the secure-by-default settings. Beyond that the guide asks for four habits.

  • Define a baseline, a set of requirements every system must fulfill, and check systems against it regularly (SAP Note 2253549).

  • Implement all applicable security patches. SAP releases them on the second Tuesday of every month and publishes them on its security notes page.

  • Run a virus scanner that is compliant with the Virus Scan Interface (VSI) 2.x, with scan profiles for signature scans, detection of the type of a file and blocking of files with active content, for example PDF files containing JavaScript.

  • Encrypt data at rest in SAP HANA: always activate persistence encryption, activate backup encryption and log encryption according to business needs (backup encryption increases backup size, log encryption affects performance), and back up the encryption keys separately, because they are not part of the database backup.

The Security Guide speaks of patches and SAP Notes, not of support packages, so how an on-premise system receives packages is a topic for the page on transports and change management and the SAP maintenance documentation; this page does not describe it. In the Public Edition you do not install anything: SAP applies hotfixes bi-weekly and release upgrades twice a year. In a three-system landscape the software upgrade reaches the test system first and the development and production systems four weeks later, which gives you time for regression tests focused on your own developments.

Source: Security Guide for SAP S/4HANA and SAP S/4HANA Cloud Private Edition 2025 (PDF), chapters System Hardening and Patching, Virus Scanning and SAP HANA Security, SAP updates and upgrades (Public Edition) and Overview of Software and Content Upgrade (Public Edition)

Summary

  • The SAP S/4HANA Security Guide is organized by layer and relies on the ABAP Platform and SAP HANA guides for the layers below it; read it together with those.

  • Communication is protected with TLS for web traffic and SNC for RFC, and technical connections follow least privilege with the user types "system" and "communication".

  • Least privilege shows up as roles, a restricted database schema, UCON for remote function calls, activated SACF scenarios and a controlled CALL TRANSACTION check.

  • The security audit log is configured with SM19 and read with SM20, with RSAU_CONFIG for its parameters; read access logging is configured by you and shows who read sensitive data.

  • Keep the guide’s retention, restricted-access and SIEM advice in mind, since logs contain personal data themselves.

  • Patch regularly and follow SAP Notes; on premise you do it, in the Public Edition SAP does it on a fixed cycle.
