CAP Java

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The SAP Cloud Application Programming Model (CAP) lets you describe business data and services in a modeling language and write only the business rules by hand. CAP has two runtimes that read the same models: one for Node.js and one for Java. This page is for developers who already know Java and want the Java runtime. You will create a CAP Java project, see what the generator produces, write an event handler class that validates expense claims, and read data with query builders instead of SQL text. It is written for CAP Java 5.2, which needs Java 21 or newer (SAP recommends Java 25) and Apache Maven 3.9.14 or newer. The CAP command line tools are the ones of CAP Node.js 10.2 (@sap/cds-dk 10.2.1), because they generate the project even for a Java application. Everything on this page runs on a laptop and works the same wherever the application is later deployed; the choice between the SAP BTP Cloud Foundry environment and the Kyma environment only matters at deployment, where it changes which starter bundle you add. The product is still documented as SAP Business Technology Platform (SAP BTP), and SAP now presents BTP capabilities as part of SAP Business AI Platform; the pages cited at the end say so.

The project listings on this page were run for real: the project was generated with cds init --java, built with Maven and started on a JDK installed on the author’s machine, then called over HTTP. Nothing on this page needs an SAP BTP account. The pieces that do need one (the Cloud Foundry and Kyma starter bundles) are described from the official pages and labeled "requires an SAP BTP account; not run here".

Before you read

  • CAP Concepts: models, services, events, queries and protocol adapters; this page puts the Java notation to them.

  • CAP Getting Started: installing the command line tools and the project layout, which Java projects share.

  • Java Getting Started and Java Build and Tooling: installing a JDK and reading a Maven pom.xml.

  • Spring Boot Core Concepts: beans, @Component and constructor injection, which CAP Java handler classes use.

  • Reading Java annotations and lambdas: Annotations and Reflection and Lambdas and Method References.

Key terms

  • Event handler: a Java method that CAP calls before, on or after an event, in which your business logic lives.

  • Generic provider: built-in handlers that serve reads and writes from the model alone, so that a service works before you write any Java.

  • Protocol adapter: the part of the runtime that turns web requests, here OData V4, into CAP events.

  • CQN (Core Query Notation): the plain-data form of a query that the Java builders produce and the database service turns into SQL.

  • CQL (Conceptual Query Language): the database-independent query language whose Java form is the Select builder.

  • CDS (Core Data Services): the modeling language of CAP, shared by the Node.js and Java runtimes.

  • Application service: the service CAP creates for every service in the model; it is the one your handlers extend.

  • Persistence service: the database client of CAP, which accepts queries on any stored entity.

The running example

The example is the same teaching model as in the other CAP pages of this site: expense claims that employees of Example Trading Co. (EX01) submit. The model is shown in full here, because this page builds a new Java project from it. The domain model is a copy of the CAP lab’s db/schema.cds.

using { cuid, managed } from '@sap/cds/common';
namespace sap.guide.expenses;
entity Claims : cuid, managed {
  title  : String(80);
  status : String(1) default 'N';
  amount : Decimal(9,2);
}

Source: CAP: Core Concepts

The service file differs from the lab’s in one line. The lab marks the entity with @odata.draft.enabled, which switches on the draft mode of SAP Fiori elements; this page leaves that annotation out to keep the Java handler small. The service therefore is a teaching variant of the lab’s service.

using { sap.guide.expenses as db } from '../db/schema';
service ExpenseService {
  entity Claims as projection on db.Claims;
}

Source: CAP: Core Concepts

The lab also seeds one claim in db/data/sap.guide.expenses-Claims.csv, which this page copies unchanged: the claim Train ticket with status N and amount 45.50.

Creating the project

There are two ways to create a CAP Java project, and the official page shows both. The first calls the Maven archetype directly (Maven prompts for the group ID and the artifact ID, and the artifact ID is also the name of the new root folder).

mvn archetype:generate -DarchetypeArtifactId="cds-services-archetype" -DarchetypeGroupId="com.sap.cds" -DarchetypeVersion="RELEASE" -DinteractiveMode=true

Source: CAP Java: Getting Started

The archetype coordinates are therefore group com.sap.cds and artifact cds-services-archetype. The page on building projects lists the command-line options of the archetype, among them -DgroupId, -DartifactId, -Dpackage, -DincludeModel=true (adds a minimal sample model), -DodataVersion=[v2|v4] (default v4), -DinMemoryDatabase=[h2|sqlite] (default h2) and -DjdkVersion=[21|25] (default 25). The last default matters for readers on Java 21: pass -DjdkVersion=21.

Generated type What it gives you

Claims

A data accessor interface that extends CdsData (a map of the row) and adds getters and setters such as getTitle(), getAmount() and setStatus(...), so that you read a claim without casting map values.

ExpenseService_

A constant interface: CDS_NAME is ExpenseService, and CLAIMS points to Claims_.

ExpenseService

A service interface that extends CqnService, with nested Application and Remote interfaces, which you can inject to call the service from code.

Event handlers

In CAP everything that happens at run time is an event sent to a service. The generic providers handle the standard events for a service from the model. Your own code joins in with event handlers: ordinary Java methods that you mark with an annotation saying in which phase of the event they run. The official page describes three phases that run one after another. Before is meant for filtering, validation and other preprocessing of the incoming data. On is meant for the core processing of the event; as soon as an On handler completes the event, the remaining On handlers are skipped. After starts only after the On phase completed successfully and is meant for post-processing the result or for side effects. A handler that throws an exception ends the processing immediately.

flowchart LR A["OData request"] --> B["Before handlers: validate input"] B --> C["On handlers: core processing"] C --> D["After handlers: post-process result"] D --> E["OData response"] B -. "exception" .-> F["Error response"]

Source: CAP Java: Event Handlers

The generic providers run around your handlers: the page lists the order as generic framework handlers, then your handlers marked early, then your ordinary Before, On and After handlers, then your handlers marked late, then the generic handlers again. A handler class has three parts, all visible in the next listing.

  • The class implements the marker interface EventHandler; the page says CAP needs it to find the class among all beans and to scan it for handler methods.

  • In Spring Boot the class must also be a bean, which @Component provides, so Spring can inject dependencies into it.

  • The annotation @ServiceName names the default service for all methods of the class. The page recommends the generated constant (ExpenseService_.CDS_NAME) over a string.

Each method carries @Before, @On or @After, with the attributes event and entity. The constants CqnService.EVENT_CREATE, EVENT_READ, EVENT_UPDATE, EVENT_UPSERT and EVENT_DELETE name the standard events, and Claims_.CDS_NAME names the entity. An OData POST becomes a CREATE event, a GET becomes READ, and PATCH and PUT become UPDATE.

A validation handler

This is the Java version of the lab’s Node.js handler. The Node.js handler of the lab is a class with an init() method that registers one function.

import cds from '@sap/cds'
export default class ExpenseService extends cds.ApplicationService {
  init() {
    this.before('SAVE', 'Claims', req => {
      if (req.data.amount < 0) req.error(400, 'Amount must not be negative', 'in/amount')
    })
    return super.init()
  }
}

Source: real file srv/expense-service.js of this site’s CAP lab (modules/ROOT/examples/sap-lab/expenses)

The Java class below does the same check and adds a second rule that reads the database: it refuses a new claim whose title already exists. This second rule is a teaching rule of this page, not a feature of CAP or of the lab. The file is srv/src/main/java/customer/expenses_java/handlers/ExpenseServiceHandler.java, and it compiled and ran (requires JDK 21 or newer and Maven; no account).

package customer.expenses_java.handlers;

import cds.gen.expenseservice.Claims;
import cds.gen.expenseservice.Claims_;
import cds.gen.expenseservice.ExpenseService_;
import com.sap.cds.ql.Select;
import com.sap.cds.services.ErrorStatuses;
import com.sap.cds.services.ServiceException;
import com.sap.cds.services.cds.CqnService;
import com.sap.cds.services.handler.EventHandler;
import com.sap.cds.services.handler.annotations.Before;
import com.sap.cds.services.handler.annotations.ServiceName;
import com.sap.cds.services.persistence.PersistenceService;
import java.math.BigDecimal;
import java.util.List;
import org.springframework.stereotype.Component;

@Component
@ServiceName(ExpenseService_.CDS_NAME)
public class ExpenseServiceHandler implements EventHandler {

  private final PersistenceService db;

  public ExpenseServiceHandler(PersistenceService db) {
    this.db = db;
  }

  @Before(event = { CqnService.EVENT_CREATE, CqnService.EVENT_UPDATE }, entity = Claims_.CDS_NAME)
  public void validateAmount(List<Claims> claims) {
    for (Claims claim : claims) {
      if (claim.getAmount() != null && claim.getAmount().compareTo(BigDecimal.ZERO) < 0) {
        throw new ServiceException(ErrorStatuses.BAD_REQUEST, "Amount must not be negative");
      }
    }
  }

  @Before(event = CqnService.EVENT_CREATE, entity = Claims_.CDS_NAME)
  public void rejectDuplicateTitle(List<Claims> claims) {
    for (Claims claim : claims) {
      var sameTitle = db.run(Select.from(Claims_.class).where(c -> c.title().eq(claim.getTitle())));
      if (!sameTitle.listOf(Claims.class).isEmpty()) {
        throw new ServiceException(ErrorStatuses.CONFLICT, "A claim titled '{}' exists already", claim.getTitle());
      }
    }
  }
}

Source: real handler of the scratch project, built on CAP Java 5.2; the annotations and signatures are described at CAP Java: Event Handlers, the error API at CAP Java: Indicating Errors, and a handler with the same constructor injection of PersistenceService is in the SAP sample cloud-cap-samples-java

Read the listing from the top. The constructor receives the PersistenceService, the default database client; Spring supplies it, which is why the class has to be a bean. The method validateAmount is registered on two events at once. Its parameter List<Claims> is an entity data argument: the page says that in the Before and On phases the data comes from the query of the request and that changes to it are safe, so a handler can also correct the data before it is stored. Because the annotation names two events, CAP registers the method for both. The handler fails a request by throwing ServiceException. The ErrorStatuses enum maps the failure to an HTTP status: BAD_REQUEST is a 400 and CONFLICT a 409, and without a status the exception defaults to a 500. In the message of the second exception, {} is a placeholder that CAP fills with the argument that follows, a formatting the page documents. The page also describes a second route for validation errors, the Messages API, which collects several errors and ends the Before phase with one exception, and says it is the recommended way for validation errors; a single check like this one can throw directly.

Querying with the CQN builders

The second handler method built a query: Select.from(Claims_.class).where(c -> c.title().eq(claim.getTitle())). This is CQL in Java form. The method from takes the generated query builder interface, and the lambda receives a typed reference to the entity, so c.title() is checked by the Java compiler: a misspelled element does not compile. The result of the builder is a CQN object. To see it, the handler was run once with one extra line that prints the query before running it (the extra line is not part of the listing above).

CQN: {"SELECT":{"from":{"ref":["ExpenseService.Claims"]},"where":[{"ref":["title"]},"=",{"val":"Taxi"}]}}

Source: real output of the scratch project with one added System.out.println of the query; the builders are described at CAP Java: Building CQN Queries

That JSON is a CQN object, the notation that the concepts page describes for both runtimes. A trace line of the same run read CQN SELECT Claims; the official page describes the persistence service as the component that translates CQN to SQL for the database, here H2. The page on query execution lists the ways to take a result apart: listOf(Claims.class) returns a typed list, single(...) returns the one expected row, and first() returns an optional. The official page on building queries shows more builder forms; for example, for its bookshop model (shown here from the page, not run on this page’s model):

Select.from(BOOKS).columns(b -> b.title()).byId(101);
Select.from(BOOKS)
    .where(b -> b.author().name().startsWith("A"));

Source: CAP Java: Building CQN Queries; shown from the page, not run here

The first line picks one column of one book by key. The second follows the association from a book to its author inside the lambda, as a path expression. The same page names a text-based form, Select.from("bookshop.Books"), for code that does not use the generated interfaces.

Two services can run a query, and the difference matters. The application service is the facade that clients call and that runs your handlers and the generic providers (authorization and input validation among them). The persistence service is the database client. It is not bound to one service definition and accepts statements on any stored entity, which is why a handler that needs extra data for a check, like rejectDuplicateTitle, uses it. The official page says the persistence service is used inside handlers when additional data must be read for custom validation. The application service, injected as the generated interface ExpenseService, is the one to call when the generic providers and your handlers should run for the call too.

On Cloud Foundry and Kyma

The project above runs locally. To run it on SAP BTP the project needs the starter bundle of the target environment. The official page names them. The bundle cds-starter-cloudfoundry is described as production-ready for the SAP BTP Cloud Foundry environment: it comprises XSUAA authentication, SAP HANA persistence, the Cloud Foundry environment and multitenancy support. The bundle cds-starter-k8s is its counterpart for the SAP BTP Kyma environment. For Cloud Foundry the page shows a command that adds the first one (requires CAP Java and Maven to run the command; the deployment itself requires an SAP BTP account; not run here).

mvn com.sap.cds:cds-maven-plugin:add -Dfeature=CF

Source: CAP Java: Getting Started; not run here

According to the page, this adds cds-starter-cloudfoundry to pom.xml. The same plugin command with -Dfeature=TINY_SAMPLE adds a sample model and with -Dfeature=INTEGRATION_TEST creates the module integration-tests. Running the application on Cloud Foundry or Kyma also needs a SAP HANA database, an XSUAA service instance for the login and a deployment descriptor; they are the subject of the pages on BTP environments and XSUAA and identity, and of the pages CAP Security and Deploying CAP: HANA, XSUAA and MTA, all of which need an SAP BTP account. The Java code of the handler class does not change between the two environments.

Where the Java handler differs from the Node.js one

The two handlers of this page agree on the rule and differ in the way they say it. The Node.js class extends cds.ApplicationService and registers a function in init(); the Java class implements EventHandler and lets annotations register its methods. In Node.js req.data is a plain record; in Java an entity data argument is typed by the generated interface, which still is a map underneath, because Claims extends CdsData. In Node.js the validation error is reported with req.error; in Java it is a thrown ServiceException or a message in the Messages API. Queries are text or fluent objects in Node.js, and builders over generated interfaces in Java. The rest is shared: the same CDS files, the same events, the same generic providers and the same OData URLs.

Summary

  • CAP Java 5.2 needs Java 21 or newer (25 recommended) and Maven 3.9.14 or newer; cds init <name> --java runs the Maven archetype com.sap.cds:cds-services-archetype and produces a Spring Boot project with a parent pom.xml, the srv module and the H2 database.

  • The CDS Maven plugin builds the model and generates Java interfaces (Claims, Claims_, ExpenseService, ExpenseService_) at every build; run mvn compile once so that the IDE sees them.

  • A handler class implements EventHandler, is a Spring @Component, names its service with @ServiceName and marks methods with @Before, @On and @After; the generic providers run the standard events around your code.

  • A handler fails a request with ServiceException and an ErrorStatuses value; on the lab model a negative amount returned HTTP 400 and a duplicate title HTTP 409.

  • Queries are built with Select.from(...) over the generated interfaces and run on the persistence service; the builder produces the same CQN as Node.js.

  • Cloud Foundry and Kyma differ only in the starter bundle and the deployment, which need an SAP BTP account; the handler code stays the same.
