SuccessFactors Talent Modules

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Employee Central keeps the core record of an employee, but a company also needs software for the steps around that record: finding and hiring people, welcoming them, agreeing goals and reviewing performance, deciding pay changes, and training. SAP SuccessFactors offers one product for each of these, often called the talent modules. This page explains what each of the five products is for, which business objects it works with, and where a programmer starts when reading its data through the SAP SuccessFactors OData API. After reading it you can tell which module a requirement belongs to and which part of the API reference to open first. It is written against SAP SuccessFactors release 2H 2026 (2611). Every module runs in the cloud, in a customer’s own tenant, so every step in this page needs a tenant and an account, and nothing here was run.

Before you read

  • SAP HCM, H4S4 and SuccessFactors: the products SAP offers for human resources and where SuccessFactors fits.

  • HR and Payroll Basics: what an employee record, a hire and a payroll run are.

Key terms

  • SuccessFactors: SAP’s cloud suite for human resources.

  • Employee Central: the core human resources application of SuccessFactors, which holds the employee record.

  • Tenant: the private instance of a cloud product that one customer uses.

  • Talent module: a SuccessFactors product for one stage of an employee’s relationship with the company, such as Recruiting or Learning.

  • OData: a standard way of reading and changing data over HTTP, which SuccessFactors offers as its main API.

  • MDF: the Metadata Framework, a SuccessFactors mechanism for defining business objects that can be exposed as OData entities.

The example used on this page

The made-up business is Example Trading Co. (company code EX01, currency EUR). All names, codes and numbers below are invented for this site and are not SAP-delivered values. The page follows the people of the example through the modules. Before Ana Torres was hired as Sales Manager on 01.03.2024, the company needed someone for the position Sales Manager (51000001): that is a Recruiting story. When Ana joined, she went through Onboarding. Each year she and her manager agree goals and a review (Performance and Goals), and a pay change for Ben Okoye or Ana belongs to Compensation. Chloe Martin, hired on 15.01.2025 as hourly Warehouse Clerk, receives safety training, which belongs to Learning.

The five modules and the employee record

The five products serve different stages. The following diagram shows the order in which an employee typically meets them. It is a simplification: the product pages state that Onboarding integrates with Recruiting and Employee Central, that Compensation integrates with Employee Central, and that Learning aims to align learning outcomes with performance goals. The other arrows only show the usual business order.

flowchart LR REC["Recruiting - find and select"] --> ONB["Onboarding - welcome the hire"] ONB --> EC["Employee Central - the employee record"] EC --> PG["Performance and Goals - goals and reviews"] EC --> COMP["Compensation - pay decisions"] EC --> LRN["Learning - courses and training"] PG --- LRN PG --> COMP

Because each module is a separate product with its own documentation, its own permissions and its own API entities, a project plans each one as its own work package. Employee data, such as the person, the job and the organization, is read from Employee Central rather than kept again in each module.

Recruiting

SAP describes SAP SuccessFactors Recruiting as providing results-oriented recruiting practices with embedded engagement and automation for sourcing, engaging and hiring the best talent. Its documentation has a configuration guide for setting up and maintaining an end-to-end recruiting process, integration guides for third-party assessment vendors, and best practices. Recruiting Marketing is covered by the same product page.

Key objects, as the API reference names them in its Recruiting chapter:

  • JobRequisition: the core data of one opening, made of system, standard and custom fields. In the example, the opening for the Sales Manager position would be one job requisition.

  • JobApplication: one candidate’s application to one requisition, again made of system, standard and custom fields.

  • Candidate: the candidate’s profile data, including attachments such as a resume, background elements, comments and data privacy setting information. The reference states that this entity is not effective dated.

  • JobOffer: the core data of the offer made to a candidate.

The reference states that the metadata of the requisition, application and candidate entities shows only the fields configured in the active templates, so two tenants can expose different custom fields on the same entity name.

API entry point: the OData v2 API, with the entities above. The reference also lists function imports for requisition approval (for example getJobReqApprovalActions and sendJobReqToNextStep).

Onboarding

SAP describes SAP SuccessFactors Onboarding as a way to engage internal and external new hires so that they quickly become productive members of the organization. The documentation distinguishes Onboarding 1.0, which the pages describe as configurable stand-alone or integrated with SAP ERP, Recruiting and Employee Central, from the guide called Implementing Onboarding. The API reference has one chapter for both, with three groups of entities: Onboarding 1.0, Onboarding 1.0 MDF entities and Onboarding.

Key objects:

  • OnboardingCandidateInfo: an MDF entity that keeps metadata about a candidate’s onboarding activity, so that activities can be queried by metadata (Onboarding 1.0).

  • ONB2Process: described as the entry point for all Onboarding tasks. The reference recommends starting a process with the function import initiateOnboardingForUser instead of inserting an ONB2Process directly, because a direct insert does not initiate the new hire’s process.

  • createOnboardee: a function import that creates an onboarding external user record from data collected in an external applicant tracking system, and performs preliminary checks on whether the person is a new hire or a rehire.

  • Compliance entities such as ComplianceProcess and ComplianceFormData for compliance forms.

In the example, Ana’s first day on 01.03.2024 would start from a hire decision made in Recruiting. The onboarding process collects the forms and tasks, and the finished hire becomes a record in Employee Central.

API entry point: OData v2 with the entities and function imports above. The documentation also has an overview page for the Onboarding 1.0 and Offboarding 1.0 API.

Performance and Goals

SAP describes SAP SuccessFactors Performance and Goals as aligning employee goals to business targets, conducting evaluations and continuously improving workforce performance. The implementation guides name four parts: 360 reviews, calibration, goal management and performance management. Continuous performance management is covered in an administration guide.

Key objects, from the API reference chapter Performance and Goals:

  • FormHeader: meta information of one form or a list of forms, such as the form data ID, start date, end date and due date.

  • FormTemplate and FormContent: the layout of a performance form and the content of one form. The chapter also has entities for the sections of a form, such as objectives, competencies and summary sections.

  • Form360ReviewContentDetail and related entities whose names start with Form360 for 360 reviews.

  • Goal_<GoalPlanID>: the goal entity. Each goal plan template has its own entity, so for the template with goal plan ID 1 the entity is Goal_1. The reference states that this API does not support $batch requests.

  • GoalPlanTemplate, GoalComment and GoalMilestone_<GoalPlanID> for the plan template, comments and milestones.

In the example, Ana’s yearly review is one form: FormHeader tells who it belongs to and when it is due, and the other form entities hold the objectives and ratings.

API entry point: OData v2. The reference lists function imports that move a form along its route, for example sendToNextStep and signForm.

Compensation

SAP describes SAP SuccessFactors Compensation as using compensation planning and management to attract, motivate and retain a workforce. Its documentation covers Compensation, Reward and Recognition, Variable Pay and the Total Compensation Plan, and has integration guides for Compensation and Variable Pay with Employee Central.

The OData v2 reference chapter named Compensation describes the Reward and Recognition entities:

  • SpotAward, SpotAwardProgram and SpotAwardCategory: a spot award, the program it belongs to and its categories.

  • SpotAwardBudget: the budget details of a budget holder for a program.

  • UserRewardInfo: retrieves the total available reward balance of a user.

The pages read for this page do not name an API entity for the compensation planning forms themselves, so this page does not either. A project that needs them looks in the API reference of its own release and in the API center of its tenant. Employee data that planning needs is read from Employee Central, as the integration guide states.

Learning

SAP describes SAP SuccessFactors Learning as promoting continuous corporate training and development, aligning learning outcomes with performance goals, boosting compliance and training external audiences. Its documentation has getting-started topics such as choosing between curricula and programs (both bundle courses into a single assignment), and implementation topics such as approval processes, cancellation policies and a learning credit system.

Key objects, from the API reference chapter Learning:

  • Learning items, the courses and other things a user can learn, and their assignment to users.

  • Curricula: sets of learning requirements that make up a qualification, most often used when customers must qualify users to a regulatory organization.

  • Learning events: an observable moment of learning, such as a course attended or a test passed.

  • Learning plans: the collection of courses or learning to-do items of a user.

  • Learning history: the set of courses that users have finished, successfully or not.

  • Scheduled offerings: a course offered at a specific time and place, including a virtual room.

The Learning chapter differs from the other four: it is organized around microservices, and the reference states that SAP prefers services whose names end in -service because they are the most actively maintained. It also states that OData services are not yet deprecated.

In the example, Chloe’s assigned safety course would be an assignment of a learning item to her, and her result would appear in her learning history.

API entry point: the Learning microservices and OData v4 services listed in the reference, for example the learning history service.

Reading data from the API

The three requests below show the shape of each call. They use placeholders for the server and the identifiers, and the shapes follow the examples in the API reference. They need a tenant, an API server address and an authorized API user, so none was run.

GET https://<api-server>/odata/v2/FormHeader(272L)?$format=json

GET https://<api-server>/odata/v2/ONB2Process?

GET https://<api-server>/learning/odatav4/public/user/learningHistory/v1/learninghistorys?$filter=criteria/maxNumberToRetrieve eq 10

Requires an SAP SuccessFactors system; not run here. Source: the API Reference Guide, chapters Performance and Goals, Onboarding and Learning (https://help.sap.com/doc/a7c08a422cc14e1eaaffee83610a981d/2611/en-US/SF_HCM_OData_API_DEV.pdf).

Summary

  • SuccessFactors splits the talent steps into separate products: Recruiting, Onboarding, Performance and Goals, Compensation and Learning, each with its own documentation.

  • Employee Central holds the employee record. Onboarding integrates with Recruiting and Employee Central, and Compensation integrates with Employee Central.

  • Each module has its own entities in the OData API reference: JobRequisition, JobApplication, Candidate and JobOffer for Recruiting; ONB2Process and OnboardingCandidateInfo for Onboarding; FormHeader and Goal_<GoalPlanID> for Performance and Goals; the Spot Award entities for Reward and Recognition; and microservices for Learning.

  • Names and fields depend on the tenant’s configured templates, so read the metadata of your own tenant.

  • Everything on this page needs a tenant and an account; no step was run here.
