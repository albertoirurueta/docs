Employee Central Data Models and MDF

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Every HR system has to answer one question before anything else: which pieces of information does it keep about a person, and how are those pieces connected? In classic SAP HCM the answer is a set of infotypes stored in tables. In SAP SuccessFactors Employee Central, the cloud core HR application, the answer is a set of data models, which are configuration files that describe the fields of a person and of an employment, and a second set that describes the company itself (legal entities, departments, jobs). On top of these sits the Metadata Framework (MDF), which lets a company add its own objects without writing code, and business rules, which react when data is saved or changed. After reading this page you can name the models, tell a foundation object from a generic object, and read a simple business rule. The page is written against SAP SuccessFactors release 2H 2026 (documentation version 2611) and describes the cloud product only. Nothing here needs, or was run on, a tenant: every step in the cloud needs a tenant and an account, so the page describes what the official documentation states and runs nothing.

Before you read

  • SAP HCM, H4S4 and SuccessFactors: where Employee Central sits next to the classic HR products.

  • Infotypes: how classic SAP HCM stores the data of one person, which this page compares with Employee Central.

  • Time Constraints and Validity: validity periods of HR records, which Employee Central calls effective dating.

Key terms

  • Employee Central: the core human resources application of SAP SuccessFactors.

  • Corporate Data Model: the data model that describes the organization of the company, made of foundation objects.

  • Succession Data Model: the data model that describes the fields of people and their employments.

  • HRIS element: one named block of fields in a data model, such as personal information or job information.

  • Foundation object: a master data object that describes the company, such as a department or a job classification.

  • Metadata Framework (MDF): the SuccessFactors platform for building custom objects and rules without code.

  • Generic object: a custom MDF object that a company defines itself.

  • Business rule: an If, Then, Else definition that sets values, raises messages or starts a workflow when data changes.

  • Event reason: the stated reason for a change to an employee’s job or pay data, such as a hire or a promotion.

  • Effective dating: keeping each version of a record with the date range in which it is valid.

The example used on this page

The page keeps the made-up business of this section: Example Trading Co. (company code EX01, currency EUR). Its employees are Ana Torres (personnel number 00001234, Sales Manager, hired 01.03.2024), Ben Okoye (00001235, Sales Clerk, hired 01.09.2024) and Chloe Martin (00001236, Warehouse Clerk, hired 15.01.2025). All codes and values are invented for this site. A personnel number is an SAP HCM concept; Employee Central identifies people differently, as the section on the two worlds explains. Where the page invents something that the example does not define, it says that it extends the example.

Two families of data

SAP’s data model guide for the SuccessFactors suite sorts the data of a company into two kinds, and the rest of this page follows that split.

  • Employee data describes the people: name, date of birth and nationality, and employment data such as job title or compensation. Two models hold it: the Succession Data Model, and the Country/Region-Specific Succession Data Model for fields that need to be localized or that exist only in one country or region.

  • Organization data describes the company: departments, divisions, legal entities, and the job and pay structure. These objects are called foundation objects. The Corporate Data Model holds their definitions and the relationships between them, and a Country/Region-Specific Corporate Data Model holds those that need to be localized.

When a country or region has no entry in a country-specific model, the guide says the definition from the general model is used. The data model files are normally edited offline: the guide explains that you download them from a tool called Provisioning, change them in an editor and upload them again, and that after the first implementation a customer can also change the files in the Admin Center with the Business Configuration UI (BCUI). The guide also states that a customer has no access to Provisioning and has to ask the implementation partner or the account executive for the steps done there. The configuration files for Employee Central, such as the master data models and the country-specific files, have moved from the SAP Help Portal to the Software Download Center.

Sources: Data Models in SAP SuccessFactors (SAP Help Portal) and Succession Data Model (SAP Help Portal)

The Succession Data Model: person and employment

The Succession Data Model describes the person side of Employee Central. Its fields fall into two areas: person data, which does not depend on the job (for example an address or a national ID), and employment data, which is job-related (for example compensation or the hire date). The model is an XML file in which each block of fields is an HRIS element with an ID, a standard label shown on the screen, and a data object type of either person object or employment object. Person objects appear on the Personal Information page of the employee file and employment objects on the Employment Information page. A company can overwrite labels and add its own fields.

A reader who knows classic SAP HCM can treat an HRIS element as the closest counterpart of an infotype: both are a named block of fields about one person. That comparison is an analogy made on this page, not a statement of the documentation, and the two differ in many details (for example, infotypes are numbered and stored in database tables).

The same official page for required fields also lists the employment side. It names, for example, jobInfo (required fields job code, company and business unit), compInfo (currency code) and employmentInfo (start date and end date). Each person has one Person record and one or more Employment records, and Job Information, Compensation Information and similar data hang below an employment.

Effective dating: one record, many versions

Employee Central keeps history by effective dating. Some entities are effective-dated, such as Job Information, Compensation Information and Job Relationships. Others are not, such as Employment Information, which records the hire date or the termination details, and One-Time Payment. The rule for effective-dated entities is the one that readers of the time constraints page already know in another form: when a new record is inserted, the end date of the previous record is set to the day before the new record’s start date, and the new record gets the end date 12-31-9999, the same high date as 31.12.9999 in SAP HCM.

For Ana, the example gives a hire date of 01.03.2024, so her first Job Information record starts on 01.03.2024 and runs to 31.12.9999. To show the rule, suppose, as an extension of the example and not a fact about Ana, that a new Compensation Information record is inserted with an effective start date of 01.07.2026. The previous record then ends on 30.06.2026, the day before, and the new one runs from 01.07.2026 to 31.12.9999. Ana’s March 2026 payslip is untouched, because 01.03.2026 to 31.03.2026 still belongs to the earlier record.

Source: Employment Information Entities (SAP Help Portal)

The Corporate Data Model and foundation objects

Foundation objects describe the company. The SAP documentation names, among others, the Legal Entity, Business Unit, Division, Department, Location, Job Classification, Cost Center and Pay Group. Most standard foundation objects of Employee Central have been migrated to the Metadata Framework and are exposed in the OData API as entities. Foundation objects are connected by associations. The documentation shows a company structure in which a Legal Entity has many Business Units, a Business Unit has many Divisions and a Division has many Departments (one-to-many), while a Location Group relates to one Location and a Geo Zone to one Location Group (one-to-one). It states that many-to-one associations are not supported and must not be configured. When the standard objects do not give enough levels, a company can add custom levels with generic objects, for example an Area above a Division, and a department can have a parent-child association with itself, which is possible for every object except the Legal Entity, which stays at the top.

The Metadata Framework and generic objects

The Metadata Framework is described by SAP as an in-app extensibility platform for building new and simple applications without writing code. It does two things. It lets a company customize predelivered MDF-based applications (the page names Position Management, Time Off, JDM 2.0 and Picklist Center), and it lets a company create its own objects, called MDF custom objects or generic objects. MDF works together with role-based permissions, business rules, OData and People Profile.

SAP also states a limit of purpose. MDF is meant for basic details whose data does not grow substantially over time, with an example of tracking the vaccination status of each employee. It is not meant for full-scale application development such as a complete clock-in and clock-out application, or for putting all historical payroll data into custom objects. For such uses SAP recommends an SAP-delivered solution or SAP Business Technology Platform. Usage limits are set out in a topic called Important Guidelines and Usage Limits.

For Example Trading Co. the page invents one generic object that extends the example: a "Warehouse safety training" object that records, for each employee such as Chloe Martin, the date of the last training. It is small, grows slowly and belongs to MDF; storing Chloe’s daily time records there would not.

Source: What Is the Metadata Framework? (SAP Help Portal)

Business rules

A business rule adds custom logic and validation to predelivered and custom objects. Employee Central and MDF both use the rules engine, and a rule always has the same shape.

  1. A rule is created in the Admin Center under Configure Business Rules, with a scenario that fits what it should do. The scenario limits the base objects, conditions and actions offered, which helps avoid configuration errors.

  2. The If section holds the conditions. Choosing Always True makes the rule run on any change to the object it is assigned to.

  3. The Then section holds the statements that run when the conditions are met, for example raising a message, setting a field to a value or creating data.

  4. Optional Else If sections add further conditions; only the Then statements after the first true condition run. An Else section says what happens when no condition is true.

  5. After the rule is saved, it has no effect until it is assigned to the object, field or entity it belongs to.

Rules have an event: the moment at which the system evaluates them. The Employee Central pages name the event types onInit, onSave, onChange, onView and onPostSave, and say that which of them can be used depends on the page on which the user acts. In the documentation’s overview table, for example, onInit applies to the Manage Organization, Pay and Job Structures page and to the Add New Employee page, and onPostSave applies to Job Information in People Profile.

For MDF objects, the scenario Rules for MDF Objects handles object data and events, such as workflows and MDF alerts, and a second scenario, Rules for Metadata of MDF Objects, handles metadata such as visibility and required settings. The documentation states that the older basic rule scenario is no longer available for creating new rules and recommends converting existing basic rules to scenario-based rules.

A rule in prose: deriving the event reason

An event reason says why a change to an employee’s data happened. SAP’s example: the event Termination might be split into the reasons "Terminated - Performance Issues" and "Terminated - By Employee". Technically event reasons are foundation objects, they are mandatory, and the event reason sets the employee status. When an administrator saves a change to Job Information, someone has to fill in the event reason, and the Event Reason Derivation setting lets a rule do it instead of the user.

The following rule is described in words, in the shape the documentation recommends. It is an illustration for the example and is not a rule delivered by SAP, and it requires an SAP SuccessFactors system; not run here.

Part of the rule What it says in the example

Scenario

Event Reason Derivation, which the documentation recommends for this purpose.

Event

onSave: the rule runs when a change to Ana’s Job Information, or anyone else’s, is saved.

If

The event reason has not been set yet (the documentation recommends checking that the value is empty before setting it, so that an earlier choice is not overwritten).

Then

Set the event reason to the default reason for a data change, for example one called "Data Change". The documentation names this as a good default.

Else

Nothing: when a reason is already set, it is kept.

The documentation adds ordering rules that matter when several rules exist: for Job Information changes the order is the Job Information rules, then the Event Reason Derivation rules, then the HRIS element validation, then the workflow derivation rules. It also recommends one workflow derivation rule per HRIS element and one event reason derivation rule per Job Information or Compensation Information. If the event reason is not set by any rule, the system raises an error, so the default rule above protects the user.

Two worlds: Employee Central and classic HCM

Employee Central and classic SAP HCM model the link between a person and the employer differently. SAP’s integration documentation puts it this way: in Employee Central the relation is reflected by the objects Person and Employment, with dependent objects such as Job Information and Compensation Information, while in SAP ERP HCM it is reflected by the objects Central Person and personnel number. Because of this, several employments of one person in Employee Central lead to several personnel numbers in SAP ERP HCM, each with its own timelines. For Ana, a person with one employment in the example, there is one Person, one Employment starting 01.03.2024, and, after replication to an SAP HCM system, one personnel number 00001234.

The organizational objects map as follows when they are replicated to SAP S/4HANA: Business Unit, Division and Department all become an organizational unit (object type O), Job Classification becomes a job (C) and Position becomes a position (S). The example’s Sales and Warehouse would thus arrive as organizational units 50000002 and 50000003 and the jobs Manager and Clerk as 52000001 and 52000002 in organizational management. The replication itself is the subject of the integration page that follows this one in the section; here only the mapping is of interest.

Sources: Data Models in Employee Central and SAP ERP HCM (SAP Help Portal) and Organizational Object Types in Employee Central Compared to SAP S/4HANA (SAP Help Portal)

What older books show, and what has changed

The book SAP ERP HCM: Technical Principles and Programming, 1st edition (2013), by Dirk Liepold and Steve Ritter, closes with a chapter on integrating SAP ERP HCM with the SuccessFactors Business Execution Suite (BizX), a product name from that time. It describes the cloud side as a set of process areas, among them Employee Central HR Core, that complement the on-premise system, and it calls the integration brand new. It does not describe the data models of this page: the Corporate Data Model, the Succession Data Model, the Metadata Framework and the business rules of today are not part of that chapter. Since 2013 SAP has renamed and reorganized the products, and the current documentation, cited above, is the reference for names and behavior. The publisher’s page lists a later edition of the book.

Common mistakes

  • Treating a foundation object as a free-form list. Foundation objects have associations, and the documentation says many-to-one associations are not supported.

  • Putting large or fast-growing data into a generic object. SAP states that MDF is for basic details and not for complete applications or historical payroll data.

  • Editing a data model without access. Provisioning is not available to customers, so a change that needs it goes through the implementation partner or SAP.

  • Assuming one personnel number per person. Several employments in Employee Central lead to several personnel numbers in SAP ERP HCM.

Summary

  • Employee Central describes people in the Succession Data Model and its country-specific version, and the company in the Corporate Data Model and its country-specific version.

  • An HRIS element is a named block of fields (personalInfo, jobInfo); person objects and employment objects differ in where they appear.

  • Job Information and Compensation Information are effective-dated: a new record ends the previous one on the day before and runs to 12-31-9999.

  • Foundation objects (Legal Entity, Business Unit, Division, Department, Job Classification and others) are linked by associations and are MDF objects exposed as OData entities.

  • MDF generic objects extend the model for small, slow-growing data, and business rules (If, Then, Else with an event and a scenario) react to changes.

  • In replication to SAP S/4HANA, business units, divisions and departments become organizational units, job classifications become jobs and positions become positions.
