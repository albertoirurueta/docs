The Payroll Process

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Payroll is not one button. Many people are paid for the same period, some of their data is wrong on the first try, and nobody may change an employee’s salary or working time while a payment is being calculated, because then the pay and the records would disagree. SAP therefore wraps the calculation in a small process with steps and a status that the system keeps for you: release the payroll for a group of employees, run it, check it, correct what failed, run only the corrected employees again, test the accounting postings and finally exit, which closes the period. This page explains that process from the first release to the exit, and it adds the off-cycle runs that pay one person between regular periods. After reading it you can name each step, say what the payroll control record is and which statuses it passes through, and explain why a rejected employee does not stop everybody else. It is written against SAP S/4HANA 2025 FPS02 on premise and Private Edition, where payroll comes from SAP HCM for SAP S/4HANA (H4S4), a separately licensed component. SAP S/4HANA Cloud Public Edition and SAP SuccessFactors are not covered here; the landscape page compares the options. What the calculation itself does inside the run (schemas, rules, wage types) is the subject of the next pages.

Before you read

  • HR and Payroll Basics: gross and net pay, the payroll period and the payroll run in plain words.

  • Infotypes: the Payroll Status infotype (0003) that this page uses is one of them.

  • Enterprise and Personnel Structure: which payroll area an employee belongs to.

  • Time Evaluation: where the hours of an hourly employee such as Chloe come from before payroll uses them.

Key terms

  • Payroll area: a group of employees for whom payroll is run together and at the same time.

  • Payroll control record: the record of a payroll area that holds its next payroll period, its payroll status and its retroactive accounting limit.

  • Payroll driver: the program that runs payroll, one version for each country.

  • Payroll simulation: a payroll run for single employees that saves nothing and changes no status.

  • Matchcode W: the list of personnel numbers that payroll rejected or that were corrected, so that a correction run can pick up exactly those.

  • Payroll correction run: a payroll run restricted to the personnel numbers of matchcode W.

  • Off-cycle payroll: a payroll run for one employee on any day, outside the regular period schedule.

The example used on this page

Every page of this section uses one made-up business, Example Trading Co. All keys, names, numbers and dates are invented example values for this site, not values delivered by SAP. Dates are written DD.MM.YYYY, as an SAP screen shows them.

  • Payroll area E1 "Monthly EX01": a monthly period from the first to the last day of the month. The example puts all three employees in it, which is the example’s own choice; Chloe is paid hourly but belongs to the monthly area.

  • 00001234 Ana Torres, Sales Manager, monthly basic pay 4,000.00 EUR. 00001235 Ben Okoye, Sales Clerk, 2,400.00 EUR. 00001236 Chloe Martin, Warehouse Clerk, hourly rate 14.00 EUR.

  • The period used throughout is March 2026, 01.03.2026 to 31.03.2026 (31 days). Ana’s payslip for it is the one from the basics page: gross 4,000.00, employee social contributions 800.00, income tax 480.00, net 2,720.00 and employer contributions 840.00. Those rates are generic flat example rates and are not the rules of any country. The arithmetic was checked by hand and with a small script, not by running an SAP system.

What the process is for

SAP’s documentation describes the payroll program as something you run at a specific point in time, to calculate not only an employee’s basic remuneration but also any special payments, overtime payments or bonuses due for that period. The process around it exists for the reasons in the introduction: the system must know which payroll area is being paid, for which period, and whether employee data may still change. Two behaviors explain most of what follows.

  • Data is locked while payroll is open. After the release, you cannot change master data and time data of the employees in the payroll area if the change affects the payroll past or present. Changes that affect only the future are still possible.

  • Errors are per employee. If the data of one employee is wrong, payroll rejects that personnel number and keeps going. The rejected ones are collected, corrected and run again, and only then is the period closed.

Source: The Payroll Process (SAP Help Portal, SAP S/4HANA 2025 FPS02)

The payroll area and its period

The payroll area decides who is paid together and which period applies. SAP’s documentation says the area carries text, period parameters, a "run payroll until" indicator and a date modifier. The period parameters define what a period is, for example a month, and the date modifier shifts the dates of the period. When you run payroll you must name the payroll area on the selection screen of the payroll driver: there it determines the exact payroll period and selects the personnel numbers that are processed together. The documentation also warns that you must not change the period parameters or the date modifier of an area for which payroll has already been run. Every payroll area needs its own payroll control record. A payroll area for which the "run payroll" indicator is not selected is how a company keeps certain employees out of payroll altogether.

In the example, E1 is monthly, so the period of March 2026 runs from 01.03.2026 to 31.03.2026, and the same run pays Ana, Ben and Chloe. The page on the enterprise and personnel structure explains how the payroll area is assigned to an employee.

Source: Payroll Area (SAP Help Portal, SAP S/4HANA 2025 FPS02)

The payroll control record

The payroll control record is the object that steers the whole process. SAP’s documentation defines it as a payroll object that is important for the run and contains all the information about a payroll area. It has three jobs.

  • It locks the personnel numbers for which payroll is run against master data changes that affect the payroll past or present.

  • It locks payroll for the period during which payroll-relevant master data of the processed personnel numbers is being changed.

  • It tells the system three things: the next payroll period for which regular payroll should run, the date up to which retroactive accounting is performed, and the status of payroll, for example Released for payroll or Check payroll results.

The documentation lists the content of the record as the payroll area, the payroll status, the payroll period, the retroactive accounting limit and the last change made to the record. The system changes the payroll status itself with each step you carry out, and you can also change it by hand from the payroll menu, under Tools, Control Record. That manual route is the easy one when you handle several payroll areas at once: the documentation says each payroll area must be released individually, and the control record is the quick way to do it for many areas.

One detail surprises newcomers and the documentation singles it out. When you create the control record in a production system, the period you enter at the start must be one lower than the period of the first live run, because releasing increases the period by one. The documentation’s example: to run the first payroll in period 5 1999, enter period 4 1999 in the record, set the status to Released for payroll, and the system raises the period to 5 1999.

In the example, after February 2026 was completed, the control record of E1 holds period 02.2026 and a closed status. Releasing E1 raises the period to 03.2026, and the record now says March 2026 may be run. If the example company were starting payroll for the first time in March 2026, it would have to create the record with period 02.2026, for the same reason as in the documentation’s example. The status names below are the ones the documentation uses; the screens and menu texts of your release may word them slightly differently.

Source: Payroll Control Record (SAP Help Portal, SAP S/4HANA 2025 FPS02)

The steps from release to exit

SAP’s description of the process lists these steps, and the statuses in the diagram below are the ones the individual step pages name. The diagram is a reading aid drawn for this page from those pages, not a figure from SAP.

stateDiagram-v2 [*] --> ExitPayroll : previous period closed ExitPayroll : Exit payroll ReleasedForPayroll : Released for payroll CheckResults : Check payroll results ReleasedForCorrection : Released for correction ExitPayroll --> ReleasedForPayroll : Release payroll, period + 1 ReleasedForPayroll --> ReleasedForPayroll : Run payroll or correction run ReleasedForPayroll --> CheckResults : Check result ReleasedForPayroll --> ReleasedForCorrection : Corrections CheckResults --> ReleasedForCorrection : Corrections ReleasedForCorrection --> ReleasedForPayroll : Release again, same period ReleasedForPayroll --> ExitPayroll : Exit payroll, no rejected numbers left

  1. Release payroll. You release one payroll area, or several, one by one. The system raises the period number in the control record by one and locks the payroll-relevant master and time data for the past and present. The menu path is Human Resources, Payroll, the country, Payroll, Tools, Release Payroll.

  2. Run payroll. The system calls the country-specific payroll program, which reads the current period from the control record and calculates with the values you entered on its selection screen. You usually run it as a background job, so that large runs do not tie up a screen.

  3. Check the run. If payroll did not run cleanly, the system lists error messages. You can set the status Check payroll results, which locks the payroll area against further payroll and data changes so that nothing moves while you inspect. A report reads the stored results and shows every table of an employee’s result for a spot check.

  4. Correct the data. You set the status to Released for correction, which allows master and time data maintenance again, and fix the infotypes of the rejected employees.

  5. Release again and run the correction run. The period does not change. Only the corrected personnel numbers are calculated again.

  6. Simulate the posting to Accounting and repeat the correction cycle if it finds errors.

  7. Exit payroll. The period is complete and the personnel numbers of the area can be processed again.

Exit is only possible when payroll has run successfully for all personnel numbers of the area, including those that were rejected earlier. After exit you can create remuneration statements, make the wage and salary payments, whose details differ from country to country, and post the results to Accounting.

Source: The Payroll Process (SAP Help Portal, SAP S/4HANA 2025 FPS02) and Releasing Payroll (SAP Help Portal)

The payroll driver and its selection screen

The program that does the calculation is the payroll driver. SAP’s documentation says every payroll country version has a country-specific driver whose technical name is RPCALCx0 or HxxCALC0: in the first form the x is a country indicator (the documentation names D for Germany, F for France and X for "other countries"), and in the second the xx is the ISO country code (it names MX for Mexico and ID for Indonesia). The international driver RPCALCX0 contains no statutory tax or social insurance information for net pay, while the other drivers contain it. The steps a driver performs are not hard-coded: they come from the country’s personnel calculation schema, which stores rules and functions, and the driver keeps its working data in internal tables that are saved as payroll results. The next pages of this section explain schemas and results.

On the selection screen of the driver, the documentation names these controls for the regular run.

  • Payroll area and payroll period. In the Payroll Period group the indicator Current Period is set by default, and the system then takes the period from the payroll control record of the named area.

  • Test Run (No Update). This indicator must not be set in a live run, because with it the system does not save the results. (A simulation, below, always sets it.)

  • Display Log. This gives a detailed payroll log, which the documentation says is only useful when you simulate payroll for individual employees. In a background run the log would create too much data and is not recommended.

  • Ignore Payroll Control Record. It switches off the check against the control record status. In a productive run it is shown but disabled and unchecked, so payroll only runs if the status is Released for payroll.

The menu path for the regular run is Human Resources, Payroll, the country, Payroll, Start Payroll, then Program, Execute (or Execute + Print). Requires an SAP system; not run here.

Source: Payroll Driver (SAP Help Portal, SAP S/4HANA 2025 FPS02) and Run Payroll (SAP Help Portal)

Locking an employee and the Payroll Status infotype

The Payroll Status infotype (0003) holds payroll and time management status data for one employee. The system creates it automatically when the employee is hired, and mostly updates it itself. For example, it stores the date of the last payroll run of that employee, and it can flag an employee who was rejected in the run. In it you can exclude an employee from payroll by locking the personnel number, but not for the current period if payroll for it is already completed or the employee has already been paid in it. Other fields you can maintain there are the personal retroactive accounting limit and the "Run Payroll Up To" and "Do Not Account After" dates. An extended editing mode, which needs a special authorization because the changes are critical, lets you exclude employees from payroll or remove them from the correction run list.

In the example, if Ben were on an unpaid leave that the company handles outside payroll, an administrator could lock 00001235 in infotype 0003 so that the run for E1 skips him, without touching the other two.

Source: Payroll Status (Infotype 0003) (SAP Help Portal), Editing the Payroll Status (SAP Help Portal) and Locked Personnel Numbers (SAP Help Portal)

Simulation

A simulation is a payroll run for individual employees that leaves no trace. SAP’s documentation recommends it when you made complex changes to an employee’s master data that may change the payroll results a lot, and you can also simulate at any moment of the regular process to find the cause of an error. A simulation is a regular run with four restrictions.

  • The results are not saved on the database. You view and print them in the payroll log.

  • The system locks no master data.

  • The current payroll period in the payroll control record does not change.

  • The steps Release payroll and Exit payroll do not apply.

The Test Run (No Update) indicator is set on the selection screen and cannot be changed. The menu path is Human Resources, Payroll, the country, Payroll, Simulation. The documentation adds that you do not have to simulate everybody before every regular run, because corrections are possible at any time in the regular process.

Source: Simulating Payroll (SAP Help Portal, SAP S/4HANA 2025 FPS02)

The payroll log

The payroll log is the detailed trace of a run. It has levels: the General data level shows the processed data and the payroll schema used, and the levels for successful and for rejected personnel numbers show how the schema was processed for each personnel number. The rejected level is always expanded. You can search the log for a term such as a wage type name, ask for documentation on a function, a personnel calculation rule or a schema, and create display variants. The documentation advises against switching on the log in background runs because the spool could overflow. The summary information (schema used, rejected personnel numbers, statistics) is still printed.

Source: Displaying the Payroll Log (SAP Help Portal, SAP S/4HANA 2025 FPS02)

Rejected employees, matchcode W and the correction run

When payroll rejects an employee because of incorrect data, the system sets the Payroll Correction field in infotype 0003 and puts the personnel number in a list called matchcode W (Payroll Correction Run). The same flag is set when you correct master or time data of a personnel number during the correction phase, so the list contains the rejected employees and the corrected ones. Personnel numbers rejected for other reasons, for example because payroll was already run for them in the period, are not stored there. You can see the list in the payroll control record under Goto, Incorrect Pers.Nos, and on the selection screen of the driver as a search help.

The correction cycle in the documentation is: after a run with errors, set the status to Released for correction, correct the infotypes, release payroll a second time (the personnel numbers are locked again), then start payroll, choose the search help for the payroll area, select matchcode W, optionally narrow it by a personnel number or an interval, and execute. Only the personnel numbers of matchcode W are calculated. With few employees you run it online, with many as a background job. If errors appear again, repeat until matchcode W is empty. A rejected or unselected personnel number means you must never exit payroll: you correct and run the correction run first. The same holds for a qualified advance payment, which the documentation says is handled like a correction.

In the example, March 2026 runs for E1. Suppose, as an invented case, that Chloe’s time data is incomplete and payroll rejects 00001236 while Ana and Ben are calculated. The run has stored Ana’s result with her net pay of 2,720.00. The administrator sets the status to Released for correction, completes Chloe’s time data, releases E1 again (the period stays 03.2026), and runs payroll with matchcode W. Only Chloe is calculated, Ana’s stored result is not touched, and matchcode W is empty at the end.

Source: Correcting Payroll-Relevant Master and Time Data (SAP Help Portal), Displaying Personnel Numbers not Included in the Payroll Run (SAP Help Portal) and Performing a Payroll Correction Run (SAP Help Portal)

Checking results and simulating the posting

For a spot check after a successful run, the documentation names the report Displaying the Payroll Results (H99_DISPLAY_PAYRESULT). Reached through the check-result step of the payroll menu, it lists the selected personnel numbers, their payroll results and the tables of each result with their contents. Setting the status Check payroll results first locks the area so that nothing changes while you look.

Before exiting, and again afterwards, SAP recommends simulating the posting run so that posting errors in the results show up early. There are two ways. A test run (value T in the Type of Document Creation field) selects the results and determines the posting-relevant information, symbolic accounts and the employee grouping for account determination, builds individual items without saving them and checks that the items of each result balance to zero. A simulation run (value S) also creates a posting run marked as a simulation, so its documents are checked like live ones but never posted. A simulation run can be repeated as often as needed, because unlike a live posting run it does not select the payroll results. In the example, Ana’s payslip would be checked for the posting to the accounts that the company configured. How those accounts are found is explained in Account Determination and Automatic Postings.

Source: Checking the Payroll Results (SAP Help Portal) and Simulating a Posting Run (SAP Help Portal)

Exiting payroll and the retroactive accounting limit

Exit closes the period. The prerequisites are that all corrections are done and, if you made a qualified advance payment, that payroll was run for all wage and salary elements. After exit, payroll is finished for all personnel numbers of the area. You can exit through the payroll menu, or through the payroll control record, which is easier for several areas and which also lets you change the earliest retroactive accounting period of the area in the same step. That limit says how far back master and time data may still be changed, and how far back payroll accounts retroactively for a late change. The documentation advises against changing it as long as the run has not been clean, and says the field is open for entry only after you choose End of payroll and before you save the record.

When a retroactive calculation replaces an earlier result, the old result is not deleted: the system gives each result a status indicator, A for the current one, P for the previous one and O for all older ones, so that for one period there is only one A and one P. Retroactive accounting itself is explained on Time Constraints and Validity.

Source: Exiting Payroll (SAP Help Portal), Changing the Retroactive Accounting Limit for a Payroll Area (SAP Help Portal) and Status Indicator (SAP Help Portal)

Off-cycle payroll

Regular payroll runs at fixed intervals for a whole area. Sometimes one person must be paid on another day: a bonus, a missing amount after a mistake, an advance. SAP’s off-cycle payroll function does this for individual employees on any day. It is documented in a separate component of the international payroll documentation, Off-Cycle Activities (PY-XX-OC), which is why it does not appear in the process pages above. (Many countries also document their own off-cycle pages.) The main points follow.

  • The Off-Cycle Workbench is the user interface for it. For a specific employee it can display payroll results, run several types of off-cycle payroll, replace a payment that was not received, and reverse an incorrect payroll result. It has the tab pages History, Payroll and Replace Payments, and the Payroll tab is where the payroll run starts.

  • Off-cycle reasons tell the system what kind of run you want. The standard system already contains reasons for the usual kinds, and in Customizing for Payroll you can define your own, such as the documentation’s example "Holiday bonus", and assign each to a category such as bonus. The system then derives the off-cycle reason type and the payroll type. The documentation lists the reason types On demand, Advance Payment, Bonus, Absence and Other, and the payroll types blank (regular run), A (bonus payment), B (correction run) and C (manual check, which it says exists for the USA and Canada only).

  • The payroll activities offered depend on the Customizing: bonus accounting, correction accounting, regular payroll on demand, advance payment, absence payment and payroll results adjustment.

  • Subsequent processing follows the run. The system writes a flag to an indicator table, and a country-specific batch report that you schedule as a background job (the documentation recommends daily) starts the process model of its report variant, which can produce the remuneration statement, print checks or start transfers, and post the results.

  • The control record check differs. For off-cycle runs the documentation says that, with the Ignore Payroll Control Record indicator off in a production system, payroll only runs if the control record status is Exit payroll.

In the example, suppose Chloe’s overtime hours for March were paid wrongly and she wants the missing amount at once. After the correct hours are entered in the time infotype, a payroll administrator opens the Off-Cycle Workbench for 00001236, selects an off-cycle reason of the correction category, and starts payroll. The system runs a retroactive calculation back to the earliest master data change date and creates an original result for the payment date of the off-cycle run, instead of waiting for the next regular run. This follows the documentation’s own example of a missed overtime payment. Requires an SAP system; not run here.

SAP also documents the Payroll Control Center, which can manage ad hoc and planned off-cycle payroll processes as well. Its documentation page "What Is Manage Off-Cycle Payrolls?" describes ad hoc requests created on a single-employee basis and planned off-cycle processes that are managed like regular processes. This page does not go further into that tool.

Source: Off-Cycle Workbench (SAP Help Portal), Off-Cycle Payroll (SAP Help Portal), Reasons, Types and Categories for Off-Cycle Payroll (SAP Help Portal), Correction Payroll (SAP Help Portal) and What Is Manage Off-Cycle Payrolls? (SAP Help Portal)

What older books show, and what has changed

The book SAP ERP HCM: Technical Principles and Programming, 1st edition (SAP PRESS, 2013), covers the payroll control record, the payroll driver programs named RPCALCx0 for each country, and off-cycle payroll, so the ideas on this page are the ones it teaches. Several things differ today. The book comes from the SAP ERP era, when this software was simply "SAP HCM"; since SAP S/4HANA 2025 it continues as SAP HCM for SAP S/4HANA (H4S4), a separately licensed component, and the Business Function is active by default so that it cannot run in compatibility mode. The book names the control record transaction code, while this page gives the menu paths that the current documentation uses. The current documentation also shows a second driver name pattern, HxxCALC0 with an ISO country code, in the driver documentation. And the Payroll Control Center, which the book does not cover, has its own documentation for managing off-cycle payroll processes.

Summary

  • Payroll runs for a payroll area and a period. The payroll control record of the area holds the next period, the status and the retroactive accounting limit, and its status changes as you move through the process.

  • The process is release, run, check, correct, correction run, posting simulation and exit. Releasing raises the period by one and locks payroll-relevant data for the past and present.

  • The country-specific payroll driver runs the calculation. One rejected employee does not stop the others: rejected and corrected personnel numbers wait in matchcode W for a correction run.

  • A simulation calculates single employees without saving, locking or changing the period. The payroll log and a results report help find the cause of errors.

  • You can exit only when every personnel number of the area has run successfully. The exit closes the period.

  • Off-cycle payroll, in the Off-Cycle Workbench or the Payroll Control Center, pays one employee on any day, for example a bonus or a correction.
