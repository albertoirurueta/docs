Custom Infotypes and Enhancements

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Sooner or later a business asks HR for something the delivered record types do not hold: the laptop an employee was given, a certificate that expires, a company-specific allowance. SAP’s answer is that you can create your own record type, a customer infotype with a number from 9000 to 9999, and that you can add fields and checks to a delivered infotype without changing SAP’s code. This page explains the choices in plain words: creating an infotype with the transaction PM01, what the system generates for you, where your own checks go, how to enhance a standard infotype, how dynamic actions chain follow-up work, which business add-ins (BAdIs) SAP documents for HR, and how customers add their own functions and operations to payroll and time evaluation. It is written for SAP S/4HANA 2025 FPS02 on premise and Private Edition with SAP HCM for SAP S/4HANA (H4S4), whose documentation was read for this page. The techniques come from the classic ABAP-based HR programming model; SAP SuccessFactors has its own extension tools, which other pages cover.

Before you read

  • Infotypes: what an infotype, a subtype and a record are.

  • Time Constraints and Validity Periods: why every infotype has a time constraint.

  • HR Data Structures and Tables: the tables behind an infotype.

  • Personnel Actions: the procedure that dynamic actions are compared with.

  • Organizational Management: the planning infotypes (1000 and up) that have their own copier.

  • Enhancements and BAdIs: the general ABAP techniques (customer exits, enhancement points, BAdIs) that this page applies to HR.

  • Classes and Objects: check classes are ABAP Objects classes.

  • Transports, Packages and gCTS: customer objects are transported.

Key terms

  • Customer infotype: an infotype you create yourself, with a number from 9000 to 9999, so that an upgrade does not overwrite it.

  • Check class: the ABAP Objects class that holds the business logic and checks of one decoupled infotype.

  • Decoupled infotype framework: the way of building infotypes in which the business logic lives in classes and not in the screen program.

  • Screen structure: a dictionary structure with every field the user interface of an infotype shows.

  • Conversion class: a class that converts between the stored data and what the screen displays.

  • CI include: the customer include CI_Pnnnn that holds your additional fields for a standard infotype.

  • Dynamic action: a rule, started automatically when an infotype record is saved, that leads to follow-up processing.

  • Dynamic processing rule: the successor of dynamic actions for the Web Dynpro ABAP master data application.

  • BAdI: a Business Add-In, a predefined place where a customer implementation can replace or extend SAP’s logic without modification.

  • Personnel calculation rule: a payroll or time evaluation rule made of operations; functions are the building blocks of schemas.

The example used on this page

All HR pages use one fictitious business, Example Trading Co. Every key, number and name below is an invented example value and not a value delivered by SAP. Dates are written DD.MM.YYYY, as an SAP screen shows them, and the high date is 31.12.9999.

  • Personnel number 00001234, Ana Torres, Sales Manager, hired 01.03.2024, employee subgroup AA, personnel subarea 0001, payroll area E1 "Monthly EX01".

  • This page extends the shared example with one record type that the other pages do not have: a customer infotype 9001 called "Work Equipment". Its fields are an invented example: an equipment type (such as laptop) and an asset tag. Ana’s record says she received a laptop with the asset tag EX-L-0001, valid from 01.03.2024 to 31.12.9999. The one check the example needs is that the asset tag must not be empty.

Creating a customer infotype with PM01

What SAP says you need first

The official topic Developing an Infotype says the transaction Create Infotype (PM01) is used by customers and by SAP to develop new infotypes. Before you start you should have finished modeling and designing the infotype, you must use customer development packages (called development classes in the topic) for every subobject so that an upgrade does not touch them, and you must use the number range 9000 to 9999, which is reserved for customer infotypes. A new infotype is limited to 1000 positions in its data field structure, because the container structure that carries a record during processing has that length.

PM01 has no help page of its own on help.sap.com. SAP Help describes it through the topics that name it, which the references list, and the transaction’s own screens and documentation (in-system documentation, transaction PM01) carry the rest.

The steps

The topic Creating an Infotype lists the procedure, which this page condenses.

  1. Open PM01, choose the tab page Create Infotype, and choose a free number from the customer range, here 9001.

  2. Say whether the infotype is for Personnel Administration (an employee infotype), for Recruitment (an applicant infotype) or for both. An employee infotype gets the table PA9001, an applicant infotype the table PB9001.

  3. Choose Generate Objects. The system offers to create the data field structure PS9001 and takes you to the ABAP Dictionary.

  4. Enter a short description and the fields. You can type components or copy them from the PS structure of a similar delivered infotype. The topic gives the example of an emergency telephone number built from the Addresses infotype (0006).

  5. Set the enhancement category to "Can be enhanced (character-type)" (only character-type enhancement is allowed), check, save and activate the structure.

  6. Confirm the object directory entries, including the one for the screen structure, and enter a transport request.

  7. Write the check class by hand (the next section) and maintain the infotype characteristics (the section after it).

The system confirms that the table entry of view T582ITVCLAS (which links the infotype to its check class and container) still has to be transported. The topic warns that this entry is client-dependent and exists only in the client where it was created, so you must transport it yourself.

Requires an SAP system; not run here. The steps above are taken from the documentation and were not executed.

Source: Developing an Infotype (SAP Help, Human Resources), Creating an Infotype (SAP Help, Human Resources)

What the system generates

The same topics list what PM01 creates, so you do not build the surrounding objects yourself. For infotype 9001 the pattern gives these objects.

Once the infotype exists it is an integral part of the Personnel Administration and Recruitment transactions, and it is automatically included in the logical databases PNP and PNPCE. A customer infotype that follows the naming convention keeps working after an upgrade because everything lives in customer names and customer packages.

Source: Developing an Infotype (SAP Help, Human Resources), Creating an Infotype (SAP Help, Human Resources), Infotype Module Pool (SAP Help, Human Resources), Infotype Dialog Module (SAP Help, Human Resources)

Where your own checks go: the check class

Under the decoupled infotype framework, the business logic of an infotype is programmed in ABAP Objects classes and not in the module pool. The documentation lists five methods of the delivered superclass CL_HRPA_INFOTYPE_NNNN that you may redefine. You must implement your checks in one or more of them, but you do not have to redefine all of them.

Method Purpose

SPECIFIC_INITIAL_COMPUTATIONS

Fills default values when a record is created anew.

SPECIFIC_READ_COMPUTATIONS

Adds values to a record after it is read and before the user sees it.

SPECIFIC_MODIFY_COMPUTATIONS

Decides whether a record may be changed.

SPECIFIC_INSERT_COMPUTATIONS

Decides whether a record may be inserted.

SPECIFIC_DELETE_COMPUTATIONS

Decides whether a record may be deleted.

SAP calls them computations, not checks, because a method may also fill derived values, write further records into the buffer, or prepare updates of tables outside the PAnnnn name range. Three rules from the topics matter in practice.

  • Write each method as if an update will be requested and as if the database will not be updated, because the buffer can be rolled back at any time. A user who only presses Enter makes the system run all checks and then roll the buffer back.

  • Never update a table directly from a check class. Updates of tables outside the PAnnnn range go through the so-called additional update mechanism.

  • The screen’s PBO flows into the initial and read methods, and its PAI flows into the insert, modify and delete methods; there is no one-to-one mapping between screen events and methods.

For Ana’s Work Equipment record, the one example check (the asset tag must not be empty) belongs in the insert and the modify method. The default for the equipment type, if the business wants one, belongs in the initial method. This page shows no ABAP listing for the class: the superclass methods have exact signatures that you read in the Class Builder of your own system (in-system documentation), and a signature taken from memory could be wrong for your release.

Two more details. A simple customer infotype can inherit from CL_HRPA_INFOTYPE_NNNN; if the check class must write data to the buffer, it must inherit from CL_HRPA_INFTY_NNNN instead. And a country-specific check class inherits from the international one, which in turn inherits from CL_HRPA_INFOTYPE_NNNN; for that, the international class must not be marked final.

Source: Implementing Checks, Processing Methods: The Standard Sequence, Creating Single Check Classes, Creating Country-Specific Check Classes, Editing the Check Class (all SAP Help, Human Resources)

Screen structure and conversion class

The screen structure carries every field the user sees, including fields that are derived and not stored. SAP names two kinds: MAIN structures with single fields and LINE structures for repeating fields. The conversion class converts input and output between the stored format and the displayed one and can control screen field attributes; applications such as the self-service adapter and the HR administrative services call it at runtime. A conversion class uses one of two interfaces, IF_HRPA_UI_CONVERT_STANDARD for the individual infotype structures or IF_HRPA_UI_CONVERT_ADVANCED for the whole container. If no special conversion is needed, the default class CL_HRPA_UI_CONVERT_BASIC is assigned. The assignment is stored in the view V_T588UICONVCLAS, and an entry there is mandatory for every screen structure; without one the screen structure cannot be used. For 9001 the generator creates that entry for you, with the default class.

Source: Structure and Task of the Screen Structure, Conversion Class, Assigning Conversion Classes to Screen Structures (all SAP Help, Human Resources)

Decoupled or not

SAP Help describes an old and a new method for creating infotypes. In the old method, the business logic lives in the module pool next to the screens. In the new, decoupled method, it lives in the check class. PM01 creates decoupled infotypes. SAP Help states that it is irrelevant for the maintenance transaction PA30 whether an infotype is decoupled, because both are supported, but that newer applications (it names some self-service scenarios and the HR administrative services) can only process decoupled infotypes. The recommendation is therefore to always create a decoupled infotype when you create a new one. Older customer infotypes can be migrated: SAP says it is not mandatory but advisable, and that the migration generates the screen structure and the table entries, while the infotype-specific logic must be decoupled by hand. The page on reading and writing infotypes explains how the framework reads and writes records.

Source: Decoupling Infotypes, Migrating an Infotype, Business Logic Guidelines for Creating and Migrating Infotypes (all SAP Help, Human Resources)

Infotype characteristics

After generation you maintain the infotype characteristics: the time constraint, the subtype table, how the infotype is selected and displayed, whether a change triggers retroactive accounting for a payroll infotype, and which screens it uses. SAP lists the tables behind them: T582A (basic characteristics such as the screens and the time constraint), T582S (short texts), T591A (subtype characteristics, if the infotype has subtypes), T588G (field-specific retroactive accounting), T588M (screen control), T588B (infotype menus) and T588Z (dynamic actions). The tables T777D and T77ID are maintained automatically by PM01; the others you maintain yourself, and the Customizing entries must be transported. For Ana’s example, the business picks a time constraint that allows more than one record at a time, because an employee may hold several devices; the page Time Constraints and Validity Periods explains the choices.

Source: Defining Infotype Characteristics, Infotype Characteristics (both SAP Help, Human Resources)

Deleting one

SAP Help documents a function that deletes a customer-specific, country-specific or industry-specific infotype: it removes the generated structures, the screen structure, the tables PA9nnn and PB9nnn, the module pool, the dialog module, the check class and the table entries. Deleting an infotype that holds records is destructive; check the data first, and handle the personal data in it as the page on data privacy, blocking and destruction describes.

Source: Deleting an Infotype (SAP Help, Human Resources)

Enhancing a delivered infotype

The enhancement concept lets you add fields and your own checks to a standard Personnel Administration or Recruitment infotype. Added fields behave like SAP’s own in reporting, in infotype logs and in dynamic actions. The steps from the topics are these.

  1. Create the customer include CI_Pnnnn in the dictionary and add your fields. The structure must have an enhancement category. Do not put these fields into CI_Pnnnn as part of editing subobjects; use the enhancement functions.

  2. Enhance the single screen (choose Enhance Single Screen, then Generate Objects, and edit the include screen, default number 0200, by hand). Optionally enhance the list screen the same way; that creates a structure ZPLISnnnn and an include in the program ZPnnnn00.

  3. Store the checks for the customer fields in the BAdI HRPAS00INFTYBL (reached through the BAdI in the check class). Enter the same code in the module pool, as the topic says.

  4. Enhance the screen structure so that the new fields reach the decoupled framework, and write the conversion class BAdI for a standard infotype. After this the enhancement is decoupled.

Limits SAP states: the length of PSnnnn together with the include must not exceed 1500 bytes; fields added to Organizational Assignment (0001) cannot be used as selection fields; and these infotypes are not covered at all: Actions (0000), Additional Actions (0302), all Time Management infotypes (2nnn), Leave Entitlement (0005), Maternity Protection/Parental Leave (0080), Military Service (0081), Leave Entitlement Compensation (0083), Time Quota Compensation (0416), Electronic Data Exchange (0700) and Applicant Actions (4000).

Where the enhancement concept is not enough, SAP lists modification options, such as exchanging a screen or changing the screen control through table T588M. These are changes to SAP objects. SAP names customer ranges so that they survive an upgrade: single screens 2900 to 2999, list screens 3900 to 3999, and includes MPnnnn5x, MPnnnn6x, MPnnnn7x and MPnnnn8x for data declarations, PBO modules, PAI modules and subroutines. The page Modifications and the Modification Assistant explains why modifications cost you at every upgrade.

Requires an SAP system; not run here.

Source: Enhancing an Infotype Included in the SAP Standard System, Enhancing the Single Screen, Enhancing the List Screen, Enhancing the Screen Structure, Modifying an Infotype Included in the SAP Standard System (all SAP Help, Human Resources)

Custom infotypes for organizational data

Organizational Management infotypes (1000 and up) are not created with PM01. SAP provides the Personnel Planning Infotype Copier, transaction PPCI, to create customer infotypes for organizational objects and to enhance existing ones. It copies templates for the repository objects (module pools, IDoc segments, dialog modules), and you then edit them. The documentation names four kinds: field infotypes and table infotypes, each in a language-dependent and a language-independent form. For a field infotype you first create a structure HRI9nnn in the dictionary and then let the copier generate the objects; for a customer infotype whose data is not yet in a transparent table, the copier can create the table HRP9nnn. A Check Environment function creates or repairs the repository objects and the entries in the infotype tables. SAP adds that you can enhance only infotypes that can be maintained directly, and that the standard infotypes 1000 (object) and 1001 (relationships) cannot be enhanced. The documentation also warns that a customer infotype must have at least the enhancement category of the infotype it was copied from. The practical rule is the same as for PA: customer numbers, customer packages, and a transport for every generated object.

Source: Personnel Planning Infotype Copier, Creating Field Infotypes, Creating Transparent Tables, Enhancing Infotypes, Infotype Generation: Environment Check (all SAP Help, Human Resources)

Dynamic actions and dynamic processing rules

A dynamic action starts automatically when infotype records are maintained and leads to follow-up processing: when a change in one infotype affects another, the system brings that infotype up. This differs from a personnel action, which a person starts. The actions are defined in the table T588Z in Customizing of Personnel Administration, and SAP says you can set up processing chains that fit your company. They run in the SAP GUI transactions PA30 and PA40.

For the Web Dynpro ABAP master data application, SAP describes dynamic processing rules (DPRs) as the successors of dynamic actions, and a conversion report turns existing dynamic actions into DPRs. A rule is defined in the Customizing activity under Personnel & Organization, Master Data Application, Dynamic Processing Rules. The documentation compares the two like this.

For Ana’s example, a possible rule is "when a Work Equipment record is created for an employee, remind the administrator to check the Communication infotype". This is an illustration of what a chain looks like, not a rule SAP delivers, and the page does not show the exact entries because they depend on your release and country. SAP adds that a customer’s rule status can be overridden in the Rule Manager, and that the status of a DPR is stored in a client-dependent view.

Source: Dynamic Actions, Dynamic Actions and Dynamic Processing Rules, Maintaining Dynamic Processing Rules (all SAP Help, Human Resources)

BAdIs that SAP documents for HR authorizations

For authorization checks, SAP Help has a section called Customer Enhancements with three BAdIs.

  • HRPAD00AUTH_CHECK lets you replace the standard authorization check for HR master data and infotypes without modification. The documentation says that as soon as an implementation is active, all HR master data authorization checks stop and only the active implementation runs, and that all the methods of the interface must be implemented. For one small change, SAP suggests copying the standard class CL_HRPAD00AUTH_CHECK_STD and activating the adjusted copy.

  • HRBAS00_STRUAUTH lets you implement a customer test procedure for the structural authorization check.

  • HRBAS00_GET_PROFL determines the assigned structural profiles.

The IMG nodes sit under Personnel Management, in Personnel Administration, Tools, Authorization Management for the first and in Organizational Management, Basic Settings, Authorization Management for the structural one. Because an active implementation replaces SAP’s check completely, a mistake opens or closes access for everyone; test it as carefully as a security change. The page Users, Roles and Authorizations and the page on HR authorizations cover the surrounding model.

Source: Customer Enhancements, HRPAD00AUTH_CHECK, HRBAS00_STRUAUTH (all SAP Help, Human Resources)

Custom functions and operations for payroll and time

Payroll and time evaluation run on schemas made of functions, and on personnel calculation rules made of operations. When delivered functions and operations are not enough, a developer writes a new one. The topics describe the steps.

  1. Write the source text of the form routine in an include and check and save it. SAP names the country-specific include PCBURZxx0 for payroll and RPTMOZ00 for time management.

  2. Open the function and operation editor (menu path Payroll, Payroll, the country, Tools, Customizing Tools, Function/Operation). The editor has no help page that names a transaction code in its own text; the code PE04 appears in the title of an SAP Note that the activation topic refers to, so treat the menu path as the sure way and the code as a shortcut to check in your system.

  3. Enter the name and choose Create. A customer function or operation must contain a special character in its name. By default the routine is named FU<function name> or OP<operation name>; a different name is possible if you mark the field as self-defined.

  4. Maintain the characteristics: country assignment, the parameter list and the parameter values.

  5. Activate it. The system starts the required reports and generates the indexed PERFORM. Only then can schemas and rules use it.

Saving creates a transport request. The logical transport objects separate SAP and customer names and the two areas: PFCS and PFCC for payroll functions (SAP and customer), PFTS and PFTC for time functions, POCS and POCC for payroll operations, and POTS and POTC for time operations.

Names follow rules too. Customer personnel calculation rules start with one of the characters & ( ) / : ; < > = or the letter Z; a name starting with a question mark is in the SAP name range. For newly created rules, SAP recommends starting with a round parenthesis, the digit 9, the letter Z or an exclamation mark. For schemas, SAP recommends changing the name when you change a schema, so you can see where your system differs from the standard, and recommends parentheses and the letters Z and Y at the start of a new name. The page Time Evaluation and the page on payroll schemas and personnel calculation rules show where such functions are used.

Requires an SAP system; not run here.

Source: Editor for Functions and Operations, Editing Functions and Operations, Creating Functions and Operations, Activating Functions and Operations, Transport Connections, Name Assignment for Standard and Customer Rules, Assigning Names for Standard and Customer Schemas (all SAP Help, Human Resources)

What can go wrong

Problem What to do

The infotype number is outside 9000 to 9999.

Use the customer range. SAP reserves it so that your development survives an upgrade.

Objects are created in an SAP package.

Use customer packages for all subobjects.

The new infotype works in PA30 but not in a newer application.

Create it decoupled (PM01 does) and keep NITF_ADM at its default; SAP says some self-service scenarios and the HR administrative services process only decoupled infotypes.

The table entry for the check class exists only in the development client.

Transport the entry of T582ITVCLAS and the entries of the Customizing tables by hand.

A check class updates a table directly.

Do not. The buffer can roll back; use the additional update mechanism for tables outside the PAnnnn range.

An enhancement field is added to an infotype that is excluded.

Check the list of excluded infotypes first (for example Actions 0000 and all 2nnn infotypes).

The PS structure plus the include grows too long.

Keep PSnnnn with CI_Pnnnn within 1500 bytes; a new customer infotype is limited to 1000 positions.

An active HRPAD00AUTH_CHECK implementation lets users see too much or too little.

Remember it replaces the whole HR master data check. Test it, and implement every method.

A customer function is not found in the schema.

Activate it in the editor; activation generates the indexed PERFORM.

What older books show, and what has changed

The book SAP ERP HCM: Technical Principles and Programming, 1st edition (2013), covers the same ground in its chapters on custom enhancements and on enhancing applications: customer exits through the transaction SMOD, BAdIs, enhancement points and modifications, then PA infotype enhancement, custom PA infotypes with PM01, processing infotypes in the decoupled infotype framework, dynamic actions through the table T588Z, OM infotypes with PPCI, time infotypes and custom payroll functions and operations. Its concepts are still the ones SAP Help describes. What has changed since 2013 is the following.

  • The decoupled infotype framework, which the book introduces as a newer architecture beside the module-pool method, is now the way SAP Help tells you to create every new infotype, because newer applications process only decoupled ones.

  • Dynamic actions have a successor for the Web Dynpro ABAP master data application, the dynamic processing rules, with a conversion tool; the book describes the route through the table T588Z.

  • HR is now delivered as SAP HCM for SAP S/4HANA, a separately licensed component that is active by default from SAP S/4HANA 2025 and cannot run in compatibility mode, so a 2013 book’s ERP context differs from today’s S/4HANA one. SAP SuccessFactors has its own extension tools, which are outside this page.

  • Customer exits are one of the older enhancement techniques; the Enhancements and BAdIs page explains how the newer BAdI and the enhancement framework compare.

Source: SAP ERP HCM: Technical Principles and Programming (SAP PRESS, publisher page; the consulted copy is the 1st edition, the page lists the 2nd), SAP Human Capital Management for SAP S/4HANA (SAP Help Portal)

Summary

  • A customer infotype takes a number from 9000 to 9999, is created with transaction PM01, and the system generates the structures, tables, module pool, screens, dialog module, screen structure and check class for you; you code the check class and maintain the infotype characteristics.

  • The business logic of a new infotype goes into five methods of the check class, which must tolerate buffer rollbacks and never update a table directly.

  • A delivered infotype is enhanced through the customer include CI_Pnnnn, the screen structure and the BAdI in the check class, with documented limits and a list of excluded infotypes.

  • Organizational infotypes are created with transaction PPCI; dynamic actions (table T588Z) and dynamic processing rules chain follow-up work.

  • SAP documents BAdIs for HR authorizations, and the function and operation editor adds customer functions and operations to payroll and time evaluation, with SAP and customer transport objects.

  • PM01 and the HR check class methods are described by SAP Help topics that name them; their exact screens and method signatures are in-system documentation of your own release.
