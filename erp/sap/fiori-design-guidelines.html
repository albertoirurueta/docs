SAP Fiori Design Guidelines

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Every SAP app that you meet in a browser, from an expense claim list to a manager’s approval screen, follows the same set of design rules, and those rules are written down in public. They are the SAP Fiori design guidelines. If you build apps with SAPUI5, SAP Fiori elements or the SAP Cloud Application Programming Model, or if you only need to understand why every SAP screen looks alike, this is the document that explains the reasons. This page reads the guidelines for a newcomer. It explains the five design principles and what role-based design means, how a floorplan (a ready-made page template) is chosen, how the dynamic page layout underlies all of them, how themes and content density change the look, and where the guidelines are published today, because the address that older books and blog posts give no longer leads to a page of its own. It is written against guideline version 1.154, which the guidelines site marks as the latest version on 2026-11-13; that version number follows SAPUI5, and the SAPUI5 baseline of this documentation is 1.154. The guidelines apply to web apps on SAP S/4HANA (on premise and Cloud Public Edition), to apps on SAP BTP, and to apps built with CAP and SAP Fiori elements. They describe design, not code, so nothing on this page needs an SAP system.

Before you read

  • SAP Fiori Launchpad: the web entry point that starts SAP Fiori apps, because the guidelines describe how an app behaves inside it.

  • What Is SAP: the business products whose screens these guidelines shape.

  • CAP Getting Started: how a small CAP service is made, which is what a generated SAP Fiori elements screen sits on.

Key terms

  • SAP Fiori design guidelines: the public documentation of how SAP web apps are designed, now hosted as SAP Fiori for Web in the SAP Design System.

  • SAP Design System: the system that covers all design at SAP, of which the SAP Fiori guidelines are the product-design part for the web.

  • Design principles: the five rules (role-based, adaptive, simple, coherent, delightful) that every SAP Fiori screen is meant to follow.

  • Floorplan: a page template for one kind of task, such as listing objects or showing one object.

  • Dynamic page: the standard page layout, made of a header, a content area and a footer toolbar, on which floorplans are based.

  • SAP Fiori elements: the framework that builds the screens of several floorplans from annotations instead of hand-written UI code.

  • SAPUI5: the SAP library of browser UI controls, whose release numbers are also the version numbers of the guidelines.

  • Horizon theme: the current SAP Fiori look, in a light and a dark variant and two high-contrast variants.

  • Content density: the cozy (touch) or compact (mouse and keyboard) sizing of controls.

What the guidelines are and where they live

The guidelines answer one practical question: how should an SAP app look and behave so that a person who learned one app can use the next one without training? The Get Started page of the site lists what a team gets from them: a harmonized look and feel across the SAP Fiori app suite, faster builds because ready-made building blocks exist, easier quality checks, a shared vocabulary for talking about changes, and a good way to onboard new team members. The content is organized in the top-level areas Discover, Foundations, UI Elements, Page Types and Resources. Foundations cover visual design (color, typography, icons, theming, content density), interaction, writing and wording, and services such as the launchpad. UI Elements is the library of single controls. Page Types holds the page layouts and the floorplans. Resources has the UI kits (for example for Figma), fonts and user research material.

Two changes of name matter when you read older material. First, the guidelines used to be a stand-alone site, and older books, blog posts and bookmarks point at the address experience.sap.com/fiori-design-web. On 2026-11-13 opening that address led to the page "SAP Fiori for Web" under www.sap.com/design-system/fiori-design-web, so the content is now part of the SAP Design System site on sap.com. Second, the thing that is described changed its name. The SAP Design System page says that the current definition of the SAP Design System was introduced in 2023, that its predecessor was the SAP Fiori Design System, and that the SAP Design System covers all design at SAP: product design, website design for marketing, sales and service, and the design of marketing and communication assets. The Fiori guidelines for the web are the part of it that this page is about. The same page lists the pieces that make up the system, from naming conventions and design tokens through themes, components, patterns and floorplans to design specifications.

The site is versioned like SAPUI5. The page on guideline versions states that the version of the site is based on the versioning of the SAPUI5 framework, that the latest version is 1.154, and that older content is consolidated into long-term support versions based on the SAPUI5 long-term maintenance versions (1.148, 1.136, 1.120 and earlier ones). The page adds that the latest guideline version does not always reflect the latest available implementation, and points to the SAPUI5 and UI5 Web Components development documentation for that. So, when a book describes a control or floorplan differently from the guidelines, first check which version each one describes.

Source: Guideline Versions, SAP Design System, Get Started

The five design principles

The Design Principles page says the design philosophy of SAP Fiori rests on five core principles: the user experience is role-based, adaptive, simple, coherent and delightful. In plain words:

  • Role-based: the app is designed for the business, the needs and the way of working of a specific kind of user, and gives the right information at the right time.

  • Adaptive: people can work how and where they want, whatever the device, and still get relevant information.

  • Simple: essential functions are easy to use, and the experience can be personalized to focus on the relevant tasks.

  • Coherent: whether you fulfill a sales order, review KPIs or manage leave requests, the same interaction and visual design language applies.

  • Delightful: besides helping you work smarter, the app should make the work itself more pleasant.

The history page of the design system shows where these principles came from. SAP Fiori started in 2013 as an initiative to re-imagine business software with a mobile-first approach. Its first version broke large, monolithic business transactions into focused, task-based apps, and it was first implemented in SAPUI5 versions 1.26 to 1.38. The page then describes SAP Fiori 2.0 (launched in October 2016, with floorplans for complex scenarios, the SAP Fiori launchpad as the user environment, and the Belize theme), SAP Fiori 3 (announced in 2018, with the Quartz theme, a redesigned shell bar and the idea of spaces) and SAP Fiori with the Horizon theme. That story is the reason why the older SAP GUI transactions and the newer apps coexist: SAP Fiori 2.0 was also applied to classic technologies such as SAP GUI for the web and Web Dynpro, so they would look more coherent next to the new apps.

Role-based design in practice

Role-based design is the principle that a beginner finds most surprising, because it is a design decision and not a setting. Instead of one large transaction that every department uses with its own subset of fields, SAP designs one app per task for one kind of person. The two ends meet in the launchpad, where the apps a person sees follow that person’s business roles; see SAP Fiori Launchpad for spaces and pages, and Users, Roles and Authorizations for how a role is assigned. The overview page floorplan (below) is the clearest example in the guidelines: it provides "all the information a user needs in a single page, based on the user’s specific domain or role".

The running example of this documentation, an expense claim, shows the idea. An employee needs an app to enter and track their own claims. A manager needs a different one, to review and approve what the team submitted. A finance clerk needs yet another one, to check amounts and statuses across many claims. Under the role-based principle these are three apps (or three views of one service), not one screen with every field and button.

Source: Design Principles

Page layouts and floorplans

The Page Layouts and Floorplans page defines two ideas. The standard page layout in SAP Fiori is the dynamic page, made of a header, a content area and a footer toolbar. Floorplans are usually based on the dynamic page, and each one serves a specific use case, so each comes with a particular combination of controls in the header, the content area and the footer toolbar. The page also gives a rule: never insert a whole floorplan into only the content area of a dynamic page layout.

The Dynamic Page Layout page (control sap.f.DynamicPage) says that one part of its header is collapsible, which helps people focus on the page content while important header information and actions stay at hand, and that the optional footer toolbar holds closing or finalizing actions that affect the whole page. It lists the floorplans that use the dynamic page (analytical list page, list report, overview page, wizard and worklist) and those that use only the dynamic page header (initial page and object page). Its "Do not use" list says not to build on the bare dynamic page when you plan to use SAP Fiori elements for a list report, analytical list page, overview page or object page, because those floorplans already include it.

Source: Page Layouts and Floorplans, Dynamic Page Layout

Choosing a floorplan

The page "When to Use Which Floorplan" groups the floorplans by what the user needs. It states that, except for the wizard and the initial page, all floorplans are available as SAP Fiori elements.

Overview page

get an overview of the key tasks and information for one role, and react to it

Filter bar with a search field; content from different apps on one page; charts, lists and tables

List report

find objects in a large data set and act on the relevant ones

Filter bar with a search field; table or chart; predefined views such as All, Open, Assigned

Analytical list page

extract insight from objects with business intelligence features, such as drilldown for root cause analysis

Visual filter bar; chart and table on one page; the impact of an action on a global KPI

Worklist

process a predefined set of objects

No filter bar needed; predefined views such as All, To Be Assigned, To Be Ordered

display, create or edit one object, and see an overview of it

Flexible header; anchor or tab navigation; flexible layout for the content

Wizard

Minimum of 3 steps and maximum of 8; a summary of the data of all steps

List report and object page, the pair you meet first

Most business apps combine two floorplans. The list report page says that a list report lets users view and work with a large set of items, that it offers powerful features for finding and acting on relevant items, and that it is often the entry point to the item details, which are usually shown on an object page. It is based on the dynamic page. In its header area it has the page title or variant, filter information and global actions, and the filter bar, which is mandatory; the content area shows a table or a chart. It also says when not to use it: to see or edit one item with all its details use the object page, to find one known item use the initial page, to work through a small set one by one use the worklist, and to analyze data or see the impact of an action on a KPI use the analytical list page.

The object page floorplan is used to display and categorize all relevant information about an object. Content is reached quickly through anchor or tab navigation, and users can switch from display to edit to create mode. The page warns builders to always build the object page with the dynamic page header and not with the former object page header, because the old header creates issues that cannot be fixed afterwards.

In the expense claim example, the list of claims is a list report: filters by status and employee, a table of claims, and create and delete actions. Opening a claim shows an object page: a header with the key facts of the claim, and sections for its items and its audit data. The account-free CAP lab described in SAP Fiori Launchpad has a Fiori elements preview that shows such a generated list report, and the ABAP side of the same pair is described in RAP Services and OData V4 and CDS Annotations and Metadata Extensions.

Source: When to Use Which Floorplan, List Report Floorplan, Object Page Floorplan

Overview page and analytical list page

The overview page is a data-driven floorplan in which each task or topic is a card. It is meant for one context and one role, shows content from different sources side by side, and offers micro actions so that users can react on the spot. The guidelines suggest it when users must filter and react to information from at least two applications, and when you plan at least three cards that are not all of the same type. They say not to use it when you only want the user to launch an application (use the launchpad home page), or when you present one object or fewer than three cards (use the object page). A manager’s expense overview, with a card of claims waiting for approval, a chart of spending per month and a list of rejected claims, is the kind of case that fits.

The analytical list page lets users analyze data step by step from different perspectives, investigate a root cause by drilldown, and act on transactional content in the same page. Its tools are KPIs, a visual filter in which filter values are enriched by measures and charts, and a combined table and chart view called the hybrid view. Use it when users need these insights, not when a plain filtered table is enough. The guidelines place a plain table with filters under the list report.

Source: Overview Page (OVP) Floorplan, Analytical List Page Floorplan

Floorplans and SAP Fiori elements

The SAP Fiori Elements page of the guidelines lists, for the framework, the supported floorplans (list report, worklist, object page, analytical list page and overview page), the supported features of each header and content area, table types, and the AI features of the framework: AI-assisted error explanation and AI input assistance. This is why a developer who writes annotations rather than UI code still gets a screen that follows the guidelines: the framework implements the floorplans, and the guidelines describe the options it offers. The guidelines also point to the SAP Fiori development portal, where the behavior of the OData V4 version of each floorplan can be tried.

Source: SAP Fiori Elements

Themes, content density and devices

The look of a screen comes from a theme. The Theming page says that the latest theme for SAP applications is Morning Horizon, that Evening Horizon is an optional dark theme, and that Quartz Light, Quartz Dark and the accessibility themes High-Contrast Black and High-Contrast White are also provided. The design system page adds that the Horizon theme has a new color palette, rounded corners, a new icon font and optimized typography, and that it follows the recommendations of WCAG 2.2. If you meet a book that shows the Belize theme or the Quartz theme as the current look, that book is older than the Horizon theme.

Themes are built from design tokens, values for repeated design decisions that are mapped one to one to theming variables (CSS variables, LESS, SASS and JSON). The page says customers can apply their own brand through the UI theme designer, from quick theming (replace the logo and main brand colors) to detailed theming (change colors of individual controls).

Content density answers a different question: how large should the controls be? The Content Density page explains that the cozy factor shows controls large enough to use with fingertips and is for touch devices, while the compact factor reduces the size of controls and the spaces between them so more information fits, and is for mouse and keyboard. It gives the default cozy touch area as 2.75 rem (44 px) and says rows and toolbars can use 2 rem (32 px) in compact mode. Developers are told to set the density actively, because components can have different defaults and leaving it unset can produce inconsistent density on one screen.

The Multi-Device Support page separates two approaches. Responsive design adjusts the same app to different screen sizes through controls and a responsive grid, with no extra coding. Adaptive design means designing different versions for different devices, because some use cases fit a device better, such as entering large amounts of data on a desktop and only viewing it on a phone. The page says the SAP Fiori apps are developed, configured and maintained once for all devices where the responsive approach applies.

Source: Theming, Content Density (Cozy and Compact), Multi-Device Support: Responsive vs. Adaptive

How to use the guidelines in a project

A practical order for a newcomer who has to design or review an app:

  1. Read the five principles and name the role the app is for.

  2. Decide the floorplan with the page "When to Use Which Floorplan". If the app uses SAP Fiori elements, check that the floorplan is one the framework supports.

  3. Look up each control you plan to use in the UI Elements library, then check the Foundations pages on interaction, writing and wording.

  4. Pick the theme and content density, and test the app on both touch and keyboard devices.

  5. Use the guidelines again at review time as a checklist: the Get Started page describes them as a quick way to check quality, although neither the guidelines nor the control library are identical to an app.

  6. Choose the guideline version that matches the SAPUI5 version of your system, because the content differs between versions.

The launchpad has its own section in the guidelines (home page and spaces, My Home, enterprise search, services and the app finder), which matches the user-side description in SAP Fiori Launchpad.

Source: SAP Fiori Launchpad

Summary

  • The SAP Fiori design guidelines are public and now live as SAP Fiori for Web in the SAP Design System on sap.com; the older experience.sap.com address leads there.

  • The guidelines are versioned like SAPUI5: 1.154 is the latest version, and older content is consolidated in long-term support versions.

  • Five principles drive every screen: role-based, adaptive, simple, coherent and delightful.

  • The dynamic page is the standard layout, and floorplans (overview page, list report, analytical list page, worklist, object page, wizard and initial page) are templates for specific tasks. Most of them are available as SAP Fiori elements.

  • Themes (Morning Horizon and others) and content density (cozy and compact) change the look without changing the structure.

  • A book that shows Belize or Quartz as the current theme, or the old stand-alone site address, predates the current guidelines.
