Async and Await

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Visual Basic 17.13 on .NET 10 (SDK 10.0.402) and was checked on 2026-10-19. Every example marked "built and run" is a complete console program that starts with Option Strict On, was built with warnings treated as errors (except where the text says otherwise) and was run in the .NET 10 SDK container (Linux); the output shown is real output. The root namespace of the scratch projects was App. No example needs the internet: the HTTP examples use either an in-process HttpMessageHandler that plays the part of the web service, or an HttpListener bound to the loopback address inside the same process. The Windows Forms example can only run on Windows and is labelled "built, not run": it was compiled against the net10.0-windows targeting pack and nothing more is claimed.

Asynchronous code lets a method start an operation that will take a while (a web request, a file read, a timer) and give the thread back to its caller until the operation finishes. Visual Basic has had Async and Await since Visual Basic 11 (Visual Studio 2012). The compiler rewrites an Async method into a state machine, so the code still reads top to bottom, with Try/Catch, loops and Using working as usual, while no thread is blocked during the waits. The running example is the shelf library catalogue, which looks up the title of a book by ISBN in a remote catalogue service. The platform side (the task-based asynchronous pattern, the thread pool and the state machine’s shape) is shared with every .NET language and is covered in more detail from the C# side in Async and Await (C#); this page is about what the Visual Basic compiler accepts, rejects and does differently. Threads, locks and parallel loops are in Threads, Parallelism and Synchronization.

The model in one picture

An Await is a pause with a promise to come back. The sequence below follows one click in a Windows Forms (or WPF) window that awaits an HttpClient call, which is the case that matters most because the code after the Await touches controls again. The important detail is the last three steps: the continuation does not run on whichever thread finished the download, it is posted to the SynchronizationContext that was current when the Await began, and that context runs it on the UI thread.

sequenceDiagram participant UI as UI thread (message loop) participant H as LookupClicked (Async Sub) participant C as HttpClient participant IO as Network and I/O completion participant SC as SynchronizationContext UI->>H: Click event H->>H: _lookup.Enabled = False H->>C: GetStringAsync(url) C->>IO: start the request (no thread is blocked) C-->>H: returns an incomplete Task(Of String) H-->>UI: Await saves the state and returns Note over UI: the UI keeps pumping messages IO-->>C: response arrives on a pool thread C->>SC: the task completes, Post(continuation) SC->>UI: the continuation is queued as a message UI->>H: resume after the Await (UI thread again) H->>H: _result.Text = body

Three facts in the diagram drive the rest of the page. The call that starts the operation returns before the operation has finished, handing back a Task that stands for the result. Await does not wait in the usual sense: if the task is not yet complete, the method returns to its caller and the rest of the method is scheduled as a continuation. And where the continuation runs is decided by the context captured at the Await, which is why a console program, a Windows Forms form and an ASP.NET Core request behave differently.

Async and Await in one example

An Async method is declared with the Async modifier and returns a Task or a Task(Of T) (or is a Sub). Inside it the Await operator takes a task and produces its result, without blocking. The caller of an Async Function receives the Task immediately, after the method has run synchronously up to its first Await that has to wait.

Read the output as the control flow:

  1. RunAsync calls LookupTitleAsync, which runs synchronously until it reaches an Await on an incomplete task. It prints "sending the request", starts GetStringAsync and returns an incomplete Task(Of String) to RunAsync.

  2. RunAsync prints that the task is not complete (IsCompleted = False) and does its own Await, so it returns to Main, which is blocked in GetResult().

  3. 50 milliseconds later the stub answers, LookupTitleAsync resumes, parses the JSON and returns the title. That Return completes the task RunAsync is waiting for.

Four rules follow from this example and hold for every Async method.

  • Tasks are hot. Calling an Async Function starts the work. You do not start a task you got from such a method; you await it, or hold it to await later (to run several in parallel).

  • Return title returns a String, not a Task(Of String). The compiler wraps the value. In a function declared As Task there is no value and Return takes no operand (BC36952 when you try).

  • The method runs on the caller’s thread until the first Await that has to wait. An Async method is not a way to run code on another thread; it is a way to not hold a thread while waiting. For CPU-bound work use Task.Run (see CPU-bound work and Task.Run).

  • An exception thrown in the method is stored in the returned task. It appears at the Await, not at the call (see Exceptions in async code).

The JSON in the stub is parsed with System.Text.Json; the data types and serialization are covered in Serialization: JSON and XML.

The compiler accepts only Task, Task(Of T) and Sub as the return types of an Async method. That excludes ValueTask and ValueTask(Of T) (an Async Function returning one is BC36945, shown below) and the "task-like" types that C# allows through AsyncMethodBuilder. Visual Basic code can still consume a ValueTask(Of T) returned by a library, awaiting it directly, and it can build one with the constructors that take a result or a Task, as FastPath does. A ValueTask must be awaited at most once; if you need to await it twice or combine it with WhenAll, call AsTask() first.

The task’s type name in the output, AsyncStateMachineBox`1, is an implementation detail of the runtime: the object returned by an Async Function is the box holding the compiler-generated state machine, and it derives from Task(Of T). Do not depend on it.

The Await operator accepts any expression whose type has a GetAwaiter method with the shape the compiler expects: Task, Task(Of T), ValueTask, ValueTask(Of T), Task.Yield(), the result of ConfigureAwait. As in C#, GetAwaiter may be an extension method, which lets you make an existing type awaitable:

The Await operator and where it may appear

Await is a unary operator that can be used only inside an Async method or an Async lambda. Outside one, the compiler does not even recognise it as an operator: Await is an ordinary identifier there, which is why the first message below is a generic syntax error rather than a message about Async.

Option Strict On

Module Program
    Sub Plain()
        Dim n As Integer = Await Task.FromResult(1)           ' not in an Async method
    End Sub

    Sub Main()
    End Sub
End Module
Program.vb(5,34): error BC30205: End of statement expected.

Source: Async

The same happens inside a lambda that is not itself Async. Declaring the lambda Async fixes it:

Option Strict On

Module Program
    Async Function InQuery() As Task
        Dim numbers As Integer() = {1, 2, 3}
        Dim doubled = numbers.Select(Function(n) Await Task.FromResult(n * 2))
        Await Task.Delay(1)
    End Function

    Sub Main()
    End Sub
End Module
Program.vb(6,56): error BC32017: Comma, ')', or a valid expression continuation expected.

Await binds tighter than the arithmetic operators, so Await Compute() + 1 adds one to the awaited result, and because it applies to the whole operand that follows (a primary expression with its member accesses), a member of the result needs parentheses: (Await TitleAsync()).Length. Without them the compiler tries to read Length from the Task, as the last error in the next program shows.

Await inside Try, Catch, Finally and SyncLock

This is the largest difference from current C#. Await is allowed in the body of Try, in Using, in loops and in If statements, but it is not allowed in a Catch block, a Finally block or a SyncLock block:

Module Program
    Async Function InCatchAndFinally() As Task
        Try
            Await Task.Delay(1)
            Throw New InvalidOperationException("boom")
        Catch ex As InvalidOperationException
            Await Task.Delay(1)
        Finally
            Await Task.Delay(1)
        End Try
    End Function

    Sub Main()
    End Sub
End Module

The compiler reports the error at the Await; the message is the same for all three places (BC36943). C# has allowed await in catch and finally since C# 6 and it works in lock replacements such as SemaphoreSlim.WaitAsync. The Visual Basic workarounds are mechanical:

  • Catch: record the exception in a variable inside the Catch, leave the Try block, then Await the recovery code after End Try (the ForEachAsync helper later on this page captures the exception with ExceptionDispatchInfo for exactly this reason).

  • Finally: put the awaited cleanup after End Try, and arrange that every exit path reaches it. If the cleanup must run even on an exception, catch the exception, run the cleanup, then rethrow with ExceptionDispatchInfo.Capture(ex).Throw(), which keeps the original stack trace.

  • SyncLock: do not hold a monitor across an Await at all. A monitor belongs to a thread and the continuation may run on a different one. Use SemaphoreSlim(1, 1) and WaitAsync (see Limiting concurrency) or restructure so the locked region has no Await.

Console programs and the missing Async Main

A task that nobody waits for does not keep a process alive, so a console program needs something at the bottom of the call chain that blocks until the asynchronous work is done. C# 7.1 added async Task Main for this. Visual Basic has no such feature, in any language version, as of this writing:

Option Strict On

Module Program
    Async Function Main() As Task
        Await Task.Delay(1)
        Console.WriteLine("never runs")
    End Function
End Module
vbc : error BC30737: No accessible 'Main' method with an appropriate signature was found in 'App'.
Option Strict On

Module Program
    Async Sub Main()
        Await Task.Delay(1)
        Console.WriteLine("Async Sub Main continued after the Await")
    End Sub
End Module
Program.vb(4,15): error BC36934: The 'Main' method cannot be marked 'Async'.

Source: Async

The first program is the natural attempt (Async Function Main() As Task). The compiler does not treat it as an entry point at all, so it reports that no Main exists (BC30737). The second uses Async Sub Main, which the compiler refuses by name (BC36934). The pattern is a synchronous Main that starts the real work and blocks once, at the very edge of the program, with GetAwaiter().GetResult(), as every example on this page does:

Module Program
    Async Function RunAsync() As Task
        ' the whole program, written as ordinary Async code
    End Function

    Sub Main()
        RunAsync().GetAwaiter().GetResult()
    End Sub
End Module

GetAwaiter().GetResult() is preferred over .Wait() and .Result in this one place because it rethrows the original exception instead of wrapping it in an AggregateException (shown in the next section). Blocking on a task is acceptable only here, at the top of a console program that has no synchronization context. Everywhere else, see [Deadlocks and sync-over-async].

When the application has a framework that owns Main (Windows Forms with the Application Framework, WPF, ASP.NET Core) you never write this bridge: the framework’s event loop or request pipeline is the one that runs Async event handlers and controllers.

Exceptions in async code

An exception thrown in an Async method does not unwind to the caller. It is caught by the generated state machine and stored in the returned task, which becomes Faulted. Await then rethrows it at the point where you await. Because Await rethrows the first inner exception of the task, you catch the same exception types you would catch from synchronous code. Wait() and Result behave differently: they throw an AggregateException that contains the original.

Module Program
    Async Function FailAsync(message As String, delayMs As Integer) As Task
        Await Task.Delay(delayMs)
        Throw New InvalidOperationException(message)
    End Function

    Async Function GuardedAsync(title As String) As Task(Of Integer)
        ' An exception thrown before the first Await still ends up inside the returned Task.
        ArgumentException.ThrowIfNullOrEmpty(title)
        Await Task.Delay(1)
        Return title.Length
    End Function

    Function NotAsync(title As String) As Task(Of Integer)
        ArgumentException.ThrowIfNullOrEmpty(title)   ' thrown synchronously, to the caller
        Return Task.FromResult(title.Length)
    End Function

    Async Function RunAsync() As Task
        Try
            Await FailAsync("one", 10)
        Catch ex As InvalidOperationException
            Console.WriteLine("Await rethrew: " & ex.GetType().Name & " '" & ex.Message & "'")
        End Try

        Try
            FailAsync("two", 10).Wait()
        Catch ex As AggregateException
            Console.WriteLine("Wait threw: " & ex.GetType().Name & " wrapping " & ex.InnerException.GetType().Name)
        End Try

        Try
            Await all
        Catch ex As InvalidOperationException
            Console.WriteLine("WhenAll + Await threw only: '" & ex.Message & "'")
        End Try

        For Each inner As Exception In all.Exception.InnerExceptions
            Console.WriteLine("  " & inner.Message)
        Next

        Dim pending As Task(Of Integer) = GuardedAsync("")
        Console.WriteLine("GuardedAsync returned a task in state " & pending.Status.ToString())
        Try
            Await pending
        Catch ex As ArgumentException
            Console.WriteLine("  the exception surfaces at the Await: " & ex.GetType().Name)
        End Try

        Try

            Console.WriteLine("never printed " & t.Status.ToString())
        Catch ex As ArgumentException
            Console.WriteLine("NotAsync threw synchronously: " & ex.GetType().Name)
        End Try

        Try

            Console.WriteLine("GetAsync completed with " & CInt(response.StatusCode).ToString())

            Console.WriteLine("EnsureSuccessStatusCode: " & ex.StatusCode.ToString())
        End Try
    End Function

        RunAsync().GetAwaiter().GetResult()
    End Sub
End Module

  • Await throws the original type (InvalidOperationException); Wait() throws AggregateException.

  • With Task.WhenAll, all failures are kept in task.Exception.InnerExceptions, but Await throws only the first one. That first one is not necessarily the first argument: here it was second, which finished before first. To report every failure, keep the WhenAll task in a variable, await it inside Try, and read Exception.InnerExceptions in the Catch.

  • A guard clause such as ArgumentException.ThrowIfNullOrEmpty in an Async method does not throw at the call: the caller gets a faulted task and the exception appears at the Await. A method that validates arguments and then returns a task built without Async (NotAsync) throws synchronously. Either can be right; choose one convention for a code base and keep to it. Remember it when writing tests that expect the exception.

  • A completed HttpClient call with a 404 status is not an exception. The task completes with the response; throw with EnsureSuccessStatusCode() (which sets HttpRequestException.StatusCode), or use a helper such as GetFromJsonAsync, which does the same check.

  • A faulted task whose exception is never observed (never awaited, Wait`ed or read through `Exception) is reported through TaskScheduler.UnobservedTaskException when the task is garbage collected. Since .NET 4.5 that does not terminate the process, but it hides a bug: await every task you start, or store it somewhere that will.

Composing tasks

Awaiting tasks one after another runs them one after another. To run independent operations at the same time, start them all (calling the Async Function is what starts them), then await them together.

Built and run: sequential awaits against WhenAll, and WhenAny in completion order
Option Strict On

Imports System.Diagnostics
Imports System.Net.Http
Imports System.Threading

    Inherits HttpMessageHandler

    Protected Overrides Async Function SendAsync(request As HttpRequestMessage,
                                                 cancellationToken As CancellationToken) As Task(Of HttpResponseMessage)

        Dim delay As Integer = If(isbn.EndsWith("1", StringComparison.Ordinal), 300, 100)
        Await Task.Delay(delay, cancellationToken)
        Return New HttpResponseMessage(Net.HttpStatusCode.OK) With {.Content = New StringContent("Title of " & isbn)}

  • Task.WhenAll returns the results in the order of the input, whichever task finished first.

  • Task.WhenAny returns the first task to finish; loop with it to process results as they complete. For many tasks the loop is quadratic; .NET 9 added Task.WhenEach, which yields tasks in completion order (shown under Consuming async streams).

  • There is no Await Task.WhenAll(a, b) returning a tuple. When the tasks have different result types, await the combined task and then read a.Result and b.Result, which are completed and therefore safe to read.

Limiting concurrency

Starting a thousand requests at once is rarely what you want. A SemaphoreSlim with WaitAsync is the asynchronous equivalent of a bounded lock. Note that the release goes in a Finally, which is fine because it contains no Await:

    Private _peak As Integer

    Async Function LookupAsync(gate As SemaphoreSlim, isbn As String) As Task(Of String)

            Dim seen As Integer

            gate.Release()
        End Try

Cancellation and timeouts

Cancellation in .NET is cooperative. The caller creates a CancellationTokenSource, passes its Token down, and calls Cancel(). Every library method that accepts a token checks it and, when cancelled, completes its task in the Canceled state; awaiting that task throws OperationCanceledException (or the derived TaskCanceledException). Your own code takes part by calling token.ThrowIfCancellationRequested() in loops and by passing the token to the awaitable calls it makes.

  • After a plain Await the code is back on the loop thread; after Await ... ConfigureAwait(False) it is on a pool thread.

  • Never block on a task from a thread that has a context (.Wait(), .Result, .GetAwaiter().GetResult()). Make the caller Async instead.

  • In library code, add .ConfigureAwait(False) to every Await. The library does not need the caller’s thread, and it protects callers who do block. In application code (an event handler that updates controls) do not use it.

  • ASP.NET Core and the console have no context, so ConfigureAwait(False) changes nothing there, but library code that targets several application models should still use it. .NET 8 added ConfigureAwait(ConfigureAwaitOptions) for finer control.

  • The ConfigureAwait call applies to one Await. After the first Await ... ConfigureAwait(False) the rest of the method runs without a context.

HttpClient practice

HttpClient is the only HTTP client to use in new Visual Basic code; the older request classes of the Framework era remain only for compatibility and are marked obsolete or discouraged. The points that matter in practice:

  • Create one HttpClient and reuse it (a Shared ReadOnly field, or a typed client from IHttpClientFactory). One instance per request exhausts sockets under load and, because connections are pooled per handler, also ignores DNS changes. A long-lived client with a SocketsHttpHandler whose PooledConnectionLifetime is set handles both. The Using client As New HttpClient(...) in the examples on this page is for short programs only.

  • Dispose the HttpResponseMessage when you handle it yourself (Using response As HttpResponseMessage = Await client.GetAsync(...)). The GetStringAsync and GetFromJsonAsync helpers dispose it for you.

  • Prefer the helpers. GetStringAsync, GetByteArrayAsync, GetStreamAsync, GetFromJsonAsync(Of T) (namespace System.Net.Http.Json, part of the shared framework) and PostAsJsonAsync cover most calls. Use HttpRequestMessage when you need headers per request.

  • Check the status. GetAsync completes on any status; EnsureSuccessStatusCode() throws HttpRequestException with StatusCode for non-2xx responses, as does GetFromJsonAsync.

  • Every call should accept a CancellationToken. HttpClient.Timeout defaults to 100 seconds, which is rarely the right limit.

  • Read large bodies as streams (GetStreamAsync, or ResponseHeadersRead with GetAsync) instead of buffering a String.

CPU-bound work and Task.Run

Async/Await is for waiting. It does not make computation faster, and it does not move computation to another thread.

Built and run: where the code runs after each kind of wait
Option Strict On

Imports System.Threading

Module Program
    Function Where() As String
        Return If(Thread.CurrentThread.IsThreadPoolThread, "pool thread", "main thread")
    End Function

    Async Function TitleAsync() As Task(Of String)
        Await Task.Delay(1)
        Return "Title of a book"
    End Function

    Async Function RunAsync() As Task
        Console.WriteLine("start:                     " & Where())

        ' I/O-bound work: no thread is blocked while waiting, nothing needs Task.Run.
        Await Task.Delay(20)
        Console.WriteLine("after Task.Delay:          " & Where())

        ' CPU-bound work: Task.Run moves it off the calling thread.
        Dim primes As Integer = Await Task.Run(Function()
                                                  Console.WriteLine("inside Task.Run:          " & Where())
                                                  Return Enumerable.Range(2, 20000).Count(Function(n) Enumerable.Range(2, CInt(Math.Sqrt(n)) - 1).All(Function(d) n Mod d <> 0))
                                              End Function)
        Console.WriteLine("primes below 20002:        " & primes.ToString())

        ' Await binds tighter than the arithmetic operators; use parentheses to call a member of the result.
        Dim length As Integer = (Await TitleAsync()).Length + 1
        Console.WriteLine("length + 1 =               " & length.ToString())

        ' Task.Yield forces the rest of the method to run as a new work item.
        Await Task.Yield()
        Console.WriteLine("after Task.Yield:          " & Where())
    End Function

        RunAsync().GetAwaiter().GetResult()
    End Sub

Source: Task-based asynchronous pattern (TAP)

  • The program starts on the main thread. After Await Task.Delay it is on a pool thread (a console program has no context to return to).

  • Task.Run runs the lambda on a pool thread. Use it for CPU-bound work, on the caller’s side: expose the asynchronous operation (Function LoadAsync() As Task(Of T)) and let the caller decide whether to wrap CPU-bound work in Task.Run. A library method named ...Async that merely wraps a synchronous call in Task.Run misleads its callers about scalability.

  • Await Task.Yield() forces the rest of the method to be queued as a new work item, which is occasionally useful to keep a long loop from monopolising a context.

For parallel CPU-bound work (many items, many cores) prefer Parallel.For, Parallel.ForEach and PLINQ, covered on the threads page.

The state machine

The compiler rewrites each Async method into a type that implements IAsyncStateMachine. Locals and parameters become fields, each Await becomes a numbered state, and MoveNext is called to resume the method. The type is nested in the module or class and linked to the method through AsyncStateMachineAttribute; this is visible with reflection:

Built and run: the generated state machine, and Await taking the fast path
Option Strict On

Imports System.Reflection
Imports System.Runtime.CompilerServices

Module Program
    Async Function SlowAsync() As Task(Of Integer)
        Await Task.Delay(10)
        Return 1
    End Function

    Async Function FastAsync() As Task(Of Integer)
        Await Task.CompletedTask
        Return 2
    End Function

    Async Function RunAsync() As Task
        ' The compiler turns every Async method into a state machine type nested in the module.
        Dim method As MethodInfo = GetType(Program).GetMethod("SlowAsync", BindingFlags.NonPublic Or BindingFlags.Public Or BindingFlags.Static)
        Dim attribute As AsyncStateMachineAttribute = method.GetCustomAttribute(Of AsyncStateMachineAttribute)()
        Console.WriteLine("state machine: " & attribute.StateMachineType.Name & " (value type: " & attribute.StateMachineType.IsValueType.ToString() & ")")
        Console.WriteLine("implements IAsyncStateMachine: " & GetType(IAsyncStateMachine).IsAssignableFrom(attribute.StateMachineType).ToString())

        ' Await only suspends when the awaited task is not yet complete.
        Dim slow As Task(Of Integer) = SlowAsync()
        Dim fast As Task(Of Integer) = FastAsync()
        Console.WriteLine("SlowAsync completed synchronously: " & slow.IsCompleted.ToString())
        Console.WriteLine("FastAsync completed synchronously: " & fast.IsCompleted.ToString())
        Console.WriteLine("sum = " & ((Await slow) + (Await fast)).ToString())
    End Function

    End Sub

Source: AsyncStateMachineAttribute

  • In a Release build the state machine is a structure (IsValueType is True), so an Async method that never actually suspends does not allocate for it; Debug builds use a class so that edit-and-continue works.

  • FastAsync awaited an already completed task, so Await did not suspend and the method finished before the call returned (completed synchronously: True). SlowAsync awaited an incomplete task and returned an incomplete task. Do not write code that depends on which case occurs.

  • Locals that cross an Await live in fields of the state machine, which is why ByRef parameters (BC36926) and ref-like types such cannot be used in Async methods.

Async Sub and event handlers

An Async Sub returns void to its caller, so nobody can await it, wait for it or catch its exceptions. Use it for one thing: event handlers, because the event’s delegate returns nothing. For everything else write Async Function ... As Task. The behaviour of Async Sub handlers (the publisher continues before the handler finishes, an unhandled exception after the first Await ends the process in a console program, the Try rule) is shown with built and run examples on Events and Handlers.

A related trap is passing an Async Sub where a Func(Of Task) was meant. Task.Run(Async Sub() ...) binds to the Action overload, so the returned task completes at the lambda’s first Await and its exceptions are lost. The compiler warns about it (BC42357, an error when warnings are errors); always use Async Function for anything you intend to await:

Option Strict On

Module Program
    Sub Main()
        ' Task.Run(Async Sub ...) binds to the Action overload: the returned task is complete when the lambda reaches its first Await.
        Dim t As Task = Task.Run(Async Sub()
                                     Await Task.Delay(100)
                                     Console.WriteLine("the Async Sub finished")
                                 End Sub)
        t.Wait()
        Console.WriteLine("Task.Run(Async Sub) completed early: " & t.IsCompletedSuccessfully.ToString())
        Threading.Thread.Sleep(300)
    End Sub
End Module

Built and run: ForEachAsync over IAsyncEnumerable, Task.WhenEach and IAsyncDisposable
Option Strict On

Imports System.Runtime.ExceptionServices
Imports System.Threading
Imports System.Threading.Channels

Friend Module AsyncStreams
    ' VB has no "Await For Each": enumerate an IAsyncEnumerable(Of T) by hand.
    <Runtime.CompilerServices.Extension>
    Async Function ForEachAsync(Of T)(source As IAsyncEnumerable(Of T), body As Action(Of T)) As Task
        Dim enumerator As IAsyncEnumerator(Of T) = source.GetAsyncEnumerator()
        Dim failure As ExceptionDispatchInfo = Nothing
        Try
            Do While Await enumerator.MoveNextAsync()
                body(enumerator.Current)
            Loop
        Catch ex As Exception
            failure = ExceptionDispatchInfo.Capture(ex)      ' no Await is allowed in Catch or Finally
        End Try
        Await enumerator.DisposeAsync()                      ' so dispose after the Try block
        If failure IsNot Nothing Then
            failure.Throw()
        End If
    End Function
End Module

Module Program
    Async Function RunAsync() As Task
        Dim channel As Channel(Of String) = System.Threading.Channels.Channel.CreateUnbounded(Of String)()
        Dim producer As Task = Task.Run(Async Function()
                                            For Each isbn As String In {"9780000000011", "9780000000022", "9780000000033"}
                                                Await Task.Delay(10)
                                                Await channel.Writer.WriteAsync(isbn)
                                            Next
                                            channel.Writer.Complete()
                                        End Function)

        Await channel.Reader.ReadAllAsync().ForEachAsync(Sub(isbn) Console.WriteLine("received " & isbn))
        Await producer

        ' Task.WhenEach (.NET 9) yields tasks in completion order.
        Dim jobs As Task(Of String)() = {Delayed("slow", 90), Delayed("fast", 10), Delayed("medium", 50)}
        Dim order As New List(Of String)
        Await Task.WhenEach(jobs).ForEachAsync(Sub(job) order.Add(job.Result))
        Console.WriteLine("completion order: " & String.Join(", ", order))

        ' IAsyncDisposable: there is no "Await Using", so call DisposeAsync yourself.
        Dim resource As New AuditLog()
        Console.WriteLine("using the resource")
        Await resource.DisposeAsync()
    End Function

    Async Function Delayed(value As String, ms As Integer) As Task(Of String)

        Return value
    End Function

    End Sub

Older material you may meet

  • Visual Basic 2010 and earlier used the Begin/End asynchronous pattern, BackgroundWorker and raw threads. They still compile, but Async/Await replaces them (see the threads page for BackgroundWorker). Delegate BeginInvoke and EndInvoke throw PlatformNotSupportedException on .NET 5 and later.

  • Books and blog posts that show Async Sub Main or Async Function Main for console programs do not compile with any Visual Basic version (BC36934, BC30737): use the GetAwaiter().GetResult() bridge.

  • Samples that fetch pages with the older HTTP classes belong to the .NET Framework era; the HttpClient code here is the current form. Samples that create a new HttpClient per request in a Using block, as the examples here do for brevity, are a known source of socket exhaustion in services.

  • Code from the Framework era that calls .Result or .Wait() inside a UI or ASP.NET event handler works only by luck; it is the deadlock shown above. Make the handler Async.

  • Some tutorials for real-time apps (SignalR chat samples, for instance) show console clients with Async Sub Main; the equivalent is the Sub Main bridge with RunAsync().GetAwaiter().GetResult().

Pitfalls checklist

Pitfall What to do

Async Sub anywhere but an event handler

Use Async Function ... As Task.

Blocking on a task (.Result, .Wait(), GetAwaiter().GetResult()) on a thread with a context

Make the caller Async; in libraries use ConfigureAwait(False).

Forgetting Await (BC42358)

Treat the warning as an error. The call runs, the result and failure are lost.

Await in Catch, Finally or SyncLock (BC36943)

Capture, leave the block, then await.

Holding a SyncLock across an Await

Use SemaphoreSlim(1, 1) and WaitAsync.

Throwing exceptions in a method named ...Async before returning the task

Decide whether validation throws synchronously or via the task, and be consistent.

Task.WhenAll hides all but the first exception at the Await

Keep the WhenAll task and read Exception.InnerExceptions.

A new HttpClient for every call

Reuse one, or use IHttpClientFactory.

No time-out or token on network calls

Pass a CancellationToken; set HttpClient.Timeout deliberately.

Task.Run around an I/O call

Remove it; Await the I/O method directly.

Capturing the loop variable of For in an async lambda

Copy it to a local first (BC42324).

Unobserved exceptions in tasks that were never awaited

Await, store or ContinueWith every task you start.

Dim f = Async Function() ... passed where a Func(Of Task) is needed

Declare Dim f As Func(Of Task) = Async Function() ....

Calling Task.Result before completion in "fire and forget" code

Await, or check IsCompleted.
