Option Statements

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Visual Basic 17.13 on .NET 10 (SDK 10.0.402) and was checked on 2026-10-19. Four statements, written at the top of a source file or set once for a whole project, decide how strict the compiler is: Option Explicit (must a variable be declared), Option Infer (may the compiler infer a type from an initializer), Option Strict (which conversions and which kinds of late binding are errors) and Option Compare (how strings are compared by default). They are the most consequential settings of the language. A project that compiles with Option Strict Off is silently a different dialect: values change type at run time, a typo in a member name becomes a run-time exception, and a conversion that loses data raises no diagnostic.

The page covers each statement, where its value comes from and which value wins, exactly what Option Strict On rejects (with the real compiler message of each case), the Custom mode that turns the same checks into warnings, the way the .NET SDK silently suppresses those warnings, the effect of Option Compare Text on operators and on runtime-library functions, and a recommended configuration for a solution. Conversions are the subject of Type Conversions; late binding of Object is covered on Early and Late Binding; the type system on Data Types and Literals; and the build properties on Projects, MSBuild and the dotnet CLI.

Every example is a complete program of the shelf library-catalogue scenario or a small project that uses its vocabulary. Each program was built and run on the .NET 10 SDK in a container with Option Strict On, Option Explicit On, Option Infer On and warnings as errors, and the output shown is the real one. Examples that are deliberately wrong are labelled, and the real compiler messages of the build that rejects them are shown instead of run output.

Where a setting comes from

A setting is resolved from three places, and the most specific one wins:

  1. The file. An Option statement at the top of a source file applies to that file only. It overrides everything below it.

  2. The project. An MSBuild property (OptionStrict, OptionExplicit, OptionInfer, OptionCompare) is passed to the compiler as /optionstrict, /optionexplicit, /optioninfer and /optioncompare for every file that has no statement of its own. In Visual Studio the same values appear on the project’s Compile page. Putting the properties in a Directory.Build.props file gives the whole directory tree the same value.

  3. The compiler default, which on vbc is -optionstrict-, -optionexplicit+, -optioncompare:binary and, through the response file shipped with the compiler, -optioninfer+. Visual Studio’s Tools > Options > Projects and Solutions > VB Defaults page supplies the initial values for new projects (documented as Explicit On, Strict Off, Compare Binary and Infer On).

The Option statements of a file are subject to three placement rules, each enforced by the compiler:

  • They must appear before any other statement of the file: before Imports, attributes and declarations. The order among the Option statements themselves is free, and conventionally Option Strict On comes first.

  • Each of the four statements may appear at most once per file.

  • They have file scope. There is no way to switch a setting on for a part of a file, and Option statements cannot be placed in a Module, Class or procedure.

The compiler reports the violations like this (a file with a doubled Option Strict, a doubled Option Compare, and, in a second build, an Option Explicit placed inside a module):

Program.vb(2,1): error BC30225: 'Option Strict' statement can only appear once per file.
Program.vb(4,1): error BC30225: 'Option Compare' statement can only appear once per file.
Program.vb(7,5): error BC30627: 'Option' statements must precede any declarations or 'Imports' statements.

Because the file wins over the project, the settings of an individual file can be tightened or relaxed without touching the project. The next program shows it for Option Compare, the one statement that has a legitimate reason to differ between files. The project sets <OptionCompare>Text</OptionCompare>; Program.vb has no statement and follows the project, and Exact.vb declares Option Compare Binary and overrides it.

    <TargetFramework>net10.0</TargetFramework>
    <OptionStrict>On</OptionStrict>
    <OptionCompare>Text</OptionCompare>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>
</Project>

A reader of a file alone cannot see the project property, which is the argument for repeating Option Strict On at the top of every file of a library that is published as source.

Option Explicit

Option Explicit On makes the use of an undeclared name a compile-time error. It is on by default in the SDK, in vbc and in Visual Studio, and it is what makes a misspelled variable name fail to compile instead of creating a new variable. The declaration statements it refers to are Dim, ReDim, Static, Const, For/For Each control variables, Using, Catch and the like (the declaration statements themselves are explained on Variables, Constants and Scope).

With Option Explicit Off, using a name that is not declared creates a local variable of type Object on the spot. The compiler accepts a typo, and on Option Strict Off nothing flags it either. The next file combines Option Explicit Off with Option Strict On, which is the only combination that is not completely silent: Option Strict On rejects what is done with the implicitly declared variables, because they are Object. The program is deliberately wrong; it is built to show the diagnostics.

Option Strict On
Option Explicit Off

Module Program
    Function CountCopies(loans As Integer(), onShelf As Integer) As Integer
        copies = onShelf
        For Each loaned As Integer In loans
            copes = copies - loaned
        Next
        Return copies
    End Function

    Sub Main()
        Console.WriteLine(CountCopies(New Integer() {1, 2}, 10))
    End Sub
End Module
Program.vb(8,21): error BC30038: Option Strict On prohibits operands of type Object for operator '-'.
Program.vb(10,16): error BC30512: Option Strict On disallows implicit conversions from 'Object' to 'Integer'.

Source: Option Explicit Statement

Line 6 declares copies implicitly and line 8 misspells it as copes. Under Option Strict On both uses are flagged because the implicit variables are Object (BC30038 for the subtraction, BC30512 for the Return). With Option Strict Off as well, the same file builds, and CountCopies returns the wrong value or throws at run time depending on what the variables hold. A file that only assigns and prints an implicitly declared variable, such as total = 5 followed by Console.WriteLine(total), also builds under Option Strict On on SDK 10.0.402. Option Explicit Off is therefore not made safe by Option Strict On.

Facts worth knowing about Option Explicit:

  • Learn documents the page’s own recommendation: Option Explicit Off is "generally not a good practice". There is no scenario in new code that needs it. It exists for source compatibility with Visual Basic 6, where implicit declaration was the default.

  • The Option Explicit statement overrides the -optionexplicit compiler option and the OptionExplicit MSBuild property for its file, in the same way as the other three.

  • The correct fix for BC30451, "'name' is not declared. It may be inaccessible due to its protection level", is not always a Dim: the name may be misspelled, out of scope, or declared Private in another type. The message lists the protection level because it is the second most common cause.

  • A C# program has no counterpart: C# always requires a declaration, and its var is the counterpart of Option Infer On, not of implicit declaration.

Option Infer

Option Infer On allows a local variable declared without an As clause to take the type of its initializer. It was added in Visual Basic 9.0 together with LINQ, whose anonymous types and query variables need it, and it applies to local variables of procedures only: not to fields, properties, parameters or function return types.

The exception on the fourth row is worth remembering: Dim something = Nothing is the one declaration without As that Option Strict On accepts, and the variable it creates is an Object. Write Dim something As Book = Nothing instead. The type of the variable is the type of the initializer, not what the program later assigns to it, and a numeric literal is as narrow as its form says: Dim copies = 3 is an Integer, Dim big = 3000000000 is a Long, Dim price = 19.99 is a Double and Dim price = 19.99D is a Decimal. The literal rules are on Data Types and Literals.

Turning Option Infer off on top of Option Strict On makes Dim without As an error (BC30209) and also rejects the For Each item In collection form, because the control variable’s type is inferred too (the compiler reports the loop variable as undeclared, BC30451). There is no benefit in Option Infer Off for new code. It can be useful for one purpose: to find every declaration without a type in code that was written without caution, by turning it off and reading the errors.

Option Strict

Option Strict On has three effects, which Learn lists as the three conditions that cause a compile-time error. They correspond to the three warning settings of the project designer’s Compile page:

  1. Implicit narrowing conversions are errors. A conversion that can lose data or fail at run time (Double to Integer, Long to Integer, String to a number, Object to anything, a base type to a derived type) must be written out with a conversion function or CType/DirectCast/TryCast.

  2. Late binding is an error. A member access on an expression of type Object is resolved at run time only with Option Strict Off; with On, it does not compile.

  3. Implicit Object typing is an error. A declaration, a function result, a parameter or a property without an As clause is an error, except for the Dim x = Nothing case above.

Two further groups of rules are consequences of the first. Operators do not accept Object operands (=, + and the others raise BC32013 or BC30038), and a number is never converted to Boolean, String or Date implicitly. The widening direction is unrestricted: Integer to Long, Double or Decimal, Char to String, a derived type to its base, anything to Object, an enumeration to its underlying type, and a constant to any numeric type that can hold its value.

What Option Strict Off does instead

Rewriting a legacy project for Option Strict On is easier when you know what each error replaces. The following behaviour was observed on SDK 10.0.402 in a throwaway project with a file-level Option Strict Off; it is listed here as a description of what the conversions do, and the page deliberately contains no listing of that code.

Statement under Option Strict Off What happens

Dim x As Integer = 3.7

Compiles; x is 4. The conversion is CInt, which rounds to even.

Dim n As Integer = "12"

Compiles; n is 12. A non-numeric string throws InvalidCastException at run time.

Dim flag As Boolean = "True"

Compiles and parses the string.

Dim d As Date = "2026-10-19"

Compiles and parses the string with the current culture.

Dim text As String = 7

Compiles; the text is 7.

Dim s = "5" then s + 1

Compiles; throws MissingMemberException: "Public member 'Lenght' on type 'String' not found."

Widening, inference and the constants

What Option Strict On still accepts is the reason it is practical. The following program is complete and warning-free. It shows the inferred types, the widening conversions that stay implicit, the rule for constants, the For Each exception and the operators that return a fixed type:

Option Strict On
Option Infer On

Imports System.Collections.Generic

Module Program
    Sub Main()
        ' Option Infer On: the type comes from the initializer.
        Dim title = "Dune"
        Dim copies = 3
        Dim price = 19.99D
        Dim ratio = copies / 2
        Dim shelf = New List(Of String) From {"Dune", "Emma"}
        Dim nothingYet = Nothing
        Console.WriteLine(TypeName(title) & ", " & TypeName(copies) & ", " & TypeName(price))
        Console.WriteLine(TypeName(ratio) & ", " & TypeName(shelf) & ", " & TypeName(nothingYet))

        ' Widening conversions are implicit and allowed under Option Strict On.
        Dim small As Short = 12
        Dim wide As Long = copies
        Dim real As Double = wide
        Dim money As Decimal = copies
        Dim letter As Char = "A"c
        Dim text As String = letter
        Dim boxed As Object = text
        Console.WriteLine(small.ToString() & " " & wide.ToString() & " " & real.ToString() & " " & money.ToString() & " " & text & " " & TypeName(boxed))

        ' A constant that fits needs no cast, a run-time value does.
        Dim byteValue As Byte = 200
        Dim fromRuntime As Integer = copies * 100
        Dim narrowed As Byte = CByte(fromRuntime Mod 256)
        Console.WriteLine(byteValue.ToString() & " " & narrowed.ToString())

        ' For Each is the documented exception: element conversions are not checked.
        For Each n As Integer In New Long() {1L, 2L}
            Console.Write(n.ToString() & " ")
        Next
        Console.WriteLine()

        ' Integer division and Mod keep integers, / and ^ always return Double.
        Console.WriteLine((7 \ 2).ToString() & " " & (7 Mod 2).ToString() & " " & (7 / 2).ToString() & " " & (2 ^ 3).ToString())

    End Sub

Custom mode and the SDK NoWarn trap

Option Strict has a third state, Custom, in which the compiler applies the Strict-On analysis but reports each finding as a warning instead of an error. It is what Visual Studio shows on the Compile page when the three warning configurations are not all Error and not all None, and it is what the -optionstrict:custom switch of vbc selects. It is the right tool for a migration: turn it on, then move warnings to errors one category at a time. The ten warnings are BC41999, BC42016 to BC42022, BC42032 and BC42036 (implicit conversion, late bound resolution, implicit Object types and the related cases).

An SDK-style project has two traps that the documentation does not mention:

  • The MSBuild property OptionStrict is a Boolean for the compiler task. Writing <OptionStrict>Custom</OptionStrict> fails the build with error MSB4030: "Custom" is an invalid value for the "OptionStrict" parameter of the "Vbc" task. Custom mode is selected with the separate property OptionStrictType: <OptionStrictType>Custom</OptionStrictType>.

  • The SDK’s props file defines NoWarn as 41999,42016,42017,42018,42019,42020,42021,42022,42032,42036 when the project has not set it. Those are exactly the warnings of Custom mode, so a project that sets OptionStrictType to Custom and nothing else builds with no diagnostics at all. Any non-empty NoWarn value of your own replaces the default, and a project that wants Custom mode has to set one (the number is arbitrary; 42353 is a warning number that this project never produces).

The following project does both and escalates two of the ten warnings. The source file has no Option statements, so the project properties decide:

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <RootNamespace>Ex5</RootNamespace>
    <OptionStrictType>Custom</OptionStrictType>
    <!-- The SDK suppresses the Option Strict warnings by default; any non-empty NoWarn replaces that list. -->
    <NoWarn>42353</NoWarn>
    <!-- Escalate two of the ten: implicit conversion and late binding. -->
    <WarningsAsErrors>$(WarningsAsErrors);42016;42017</WarningsAsErrors>
    <NuGetAudit>false</NuGetAudit>
  </PropertyGroup>
</Project>

Option Compare

Option Compare selects the default method used when two strings are compared:

  • Binary compares the numeric values of the characters (UTF-16 code units, in practice). The comparison is case-sensitive and culture-independent, fast, and gives the order A < B < Z < a < b < z.

  • Text compares by the lexical meaning of the characters in the current culture, ignoring case, kana type and character width. It is slower and gives the order A = a < B = b < Z = z (Learn’s example adds the accented letters of code page 1252).

Learn’s description of Text is "determined by your system’s locale", so a program that depends on the culture-specific part can behave differently on two machines. The case-insensitive part is reliable.

The setting affects:

  • The comparison operators =, <>, <, <=, >, >= over String operands.

  • Like, whose literal characters and ranges are compared by the same method ("abc" Like "A*" is True under Text and False under Binary; the Like operator is supported on .NET, contrary to a stale note on its Learn page).

  • Select Case over strings.

  • The runtime-library functions that have an optional Compare parameter: InStr, InStrRev, StrComp, Replace, Split, Filter. The compiler passes the file’s setting for that argument, which means that the default value shown in the documentation is not what the function receives (see the next listing: Replace defaults to Binary in its signature, but on a Text file it replaces both cases).

The setting does not affect anything in the .NET Base Class Library:

  • String.Equals, String.Compare, String.Contains, String.StartsWith and the ==-like methods follow their own rules (StringComparison), which default to ordinal for Equals and Contains.

  • Collections and hashes: Dictionary(Of String, T) uses the default comparer (ordinal) unless one is given. It is the most common surprise: "Shelf" = "SHELF" is True in the file but ContainsKey("SHELF") on a dictionary keyed by "Shelf" is False.

  • LINQ methods such as Distinct, Contains and GroupBy over strings use the comparer of the method (ordinal by default), not the file’s option. A Where t = "DUNE" inside a query expression is different: there = is the Visual Basic operator, so it follows Option Compare. The ordering of Order By is culture-dependent and is not controlled by the option either.

The next program shows the whole matrix on one file with Option Compare Text:

        Console.WriteLine("stored = typed          : " & (stored = typed).ToString())

InStr("Library Shelf", "shelf") is 9 because the match ignores case; the explicit CompareMethod.Binary argument in the next line gives 0. StrComp returns 0, -1 or 1 and follows the same rule. The last three lines are the .NET side: the dictionary, Equals and Contains are ordinal whatever the file says.

Guidance on the choice:

  • Use Binary (the default) everywhere you can. It is predictable, matches C#, and is the best performing option. For identifiers, keys, ISBNs, file names and protocol text the ordinal comparison is the correct one. Case-insensitive logic belongs at the call site, where it is visible: String.Equals(a, b, StringComparison.OrdinalIgnoreCase) for identifiers, or StringComparer.CurrentCultureIgnoreCase for user-facing sorting.

  • Use Option Compare Text only in a file whose whole purpose is case-insensitive text matching with the VB operators (a small command-parsing module, for example), and say so in a comment. It is a file-level setting precisely so that it stays local.

  • Never set Text for a whole project. Code in other files then compares differently from what its author expects, and a reader cannot see why.

  • In a library meant for others, state Option Compare Binary explicitly at the top of the file if the logic depends on it, so that a project-level OptionCompare property cannot change it.

The recommended configuration

For a new solution, set the four values once in a Directory.Build.props file at the repository root. This is the file the shelf solution uses (it builds all of its projects, including the library, the console application and the tests, warning-free):

<Project>
  <PropertyGroup>
    <OptionExplicit>On</OptionExplicit>
    <OptionStrict>On</OptionStrict>
    <OptionInfer>On</OptionInfer>
    <OptionCompare>Binary</OptionCompare>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
  </PropertyGroup>
</Project>

Source: -optionstrict

Notes on the choice:

  • Explicit On and Infer On are already the SDK defaults, and are written out so that the file documents the intent and survives a change of defaults. Strict On is the one that changes behaviour.

  • Infer On is not a loophole of Strict On; it is what lets Dim books = catalog.Search(term) stay readable. The type is still static and checked.

  • In an existing project, the migration path is OptionStrictType Custom with the SDK NoWarn replaced, escalating one category of warning at a time. Late binding (BC42017) is the category that needs the most thought, because it points at Office automation, COM and reflection code where a typed alternative may not exist. For such a file, the file-level statement is the supported escape hatch, and the page Early and Late Binding shows its single legitimate use.

  • The .editorconfig severities (dotnet_diagnostic.BCnnnnn.severity) complement the options and do not replace them.

  • Generated files such as designer files carry their own Option statements and are not affected by the properties of the project for the settings they declare.

  • The Visual Studio VB Defaults page changes only the initial values of new projects. Changing them in the IDE does not change an existing project; the property in the project file does.

Pitfalls

Pitfall What to do

A project created from the SDK template has Option Strict Off.

Set the properties in Directory.Build.props the day the solution is created. A project with Off accumulates conversions that are expensive to fix later.

Option Strict On in a file but not in the project: one file is safe, the others are not.

Grep for files without the statement, or set the property. A Directory.Build.props plus the Option Strict On line on every file is the redundant-but-safe pair.

OptionStrict set to Custom fails with MSB4030.

Use OptionStrictType.

Custom mode builds with no warnings at all.

The SDK NoWarn default hides them. Replace it.

A Text comparison in the file and an ordinal dictionary in the code.

The option affects operators and VB functions only. Give the dictionary a comparer.

A culture-dependent Text result in tests.

Tests that run on a machine with another culture may order or compare differently. Use Binary, or an explicit culture.

The For Each loop variable of a narrower type than the elements.

Not checked at compile time. Use For Each x In sequence with inference, or convert explicitly inside the loop.

Option Explicit Off with Option Strict On still compiles a bare assignment.

Keep Explicit on. It costs nothing.

Where the books are silent or wrong

Neither of the two reference books for this section mentions Option Strict: they teach Option Explicit as a historical Visual Basic 6 setting and mix declared and implicit variables. Quickstart Guide p. 31 labels "implicit declaration" what is really type inference through Option Infer, and its Option Explicit example is wrong in both dialects. The correct reading is the one on this page: Option Explicit is about declaring names, Option Infer is about typing a declared name from its initializer, and Option Strict is about what may be converted and bound at run time. Mastering VB.NET p. 43 assigns the result of / and of ^ to an Integer variable, which is an error under Option Strict On because both operators return Double; the correct forms are the \ operator or an explicit conversion, as shown above. Both books were written for a toolchain whose templates compile such code, and the SDK’s own Option Strict Off default is the reason it still compiles in a new project today.
