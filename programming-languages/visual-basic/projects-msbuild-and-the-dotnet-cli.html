Projects, MSBuild and the dotnet CLI

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Visual Basic 17.13 on .NET 10 (SDK 10.0.402, vbc compiler version 5.9.0-1.26505.111) and was checked on 2026-10-19. Everything marked "built and run" was produced in the .NET 10 SDK container (Linux, arm64) with the real dotnet and vbc commands; the output shown is the output printed. Compiler and MSBuild messages are quoted as printed, so root namespaces and paths in them (/w/...) come from the scratch projects. Project examples are small console programs that start with Option Strict On, or are project files with no code at all. Anything that needs Windows is labelled "built, not run" or "evaluated only". Properties and options are listed by their real names, and the lists were checked against the files the SDK ships (the VB .props and .targets files, Microsoft.VisualBasic.Core.targets and the output of vbc -help).

The project file is where almost every compiler setting in a Visual Basic program lives, and the VB defaults differ from the C# defaults in ways that matter: the SDK ships OptionStrict as Off and a NoWarn list that hides the Option Strict warnings, and several properties known from C# do nothing. Reading this page you will learn what a modern .vbproj contains, how each property becomes a vbc option (all of them, by name), which properties are shared with C# and which exist only for VB, how to set the language version, imports, conditional-compilation symbols and warning policy, how to share settings across a solution, how the dotnet command line drives the same machinery, how Visual Studio’s property pages map onto it, and how the legacy (non-SDK) project format differs. The language-level meaning of Option Strict and its siblings is on Option Statements, the #If directive and symbols on Conditional Compilation and Directives, the My types on The My Namespace, and packaging and publish modes on Libraries, Packaging and Deployment.

The SDK-style project file

A Visual Basic project today is an SDK-style project: a short XML file whose root element names an SDK (Sdk="Microsoft.NET.Sdk"). The SDK supplies, through imported .props and .targets files, everything a project used to list by hand: the source files (a glob), the references to the framework, the default imports, the compiler settings and the build targets. This is what dotnet new writes for the three most common project types (the sources are in the next sections; the listing shows the project files exactly as the templates wrote them):

<!-- dotnet new classlib -lang VB -o Shelf.Core -->
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <RootNamespace>Shelf.Core</RootNamespace>
    <TargetFramework>net10.0</TargetFramework>
  </PropertyGroup>

</Project>

<!-- dotnet new console -lang VB -o Shelf.Cli, then: dotnet add Shelf.Cli reference Shelf.Core -->
<Project Sdk="Microsoft.NET.Sdk">

  <ItemGroup>
    <ProjectReference Include="..\Shelf.Core\Shelf.Core.vbproj" />
  </ItemGroup>

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <RootNamespace>Shelf.Cli</RootNamespace>
    <TargetFramework>net10.0</TargetFramework>
  </PropertyGroup>

</Project>

<!-- dotnet new mstest -lang VB -o Shelf.Tests -->
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <LangVersion>latest</LangVersion>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="MSTest" Version="4.0.2" />
  </ItemGroup>

  <ItemGroup>
    <Using Include="Microsoft.VisualStudio.TestTools.UnitTesting" />
  </ItemGroup>

</Project>

Three things stand out. A library has no OutputType (the default is Library), a console application has OutputType Exe, and RootNamespace is written into Visual Basic templates (C# templates have no such property, see the next table). The test template carries LangVersion latest (harmless: it means the newest version) and three C#-isms, ImplicitUsings, Nullable and a Using item, that have no effect in a Visual Basic project: the captured vbc command lines in this page do not change when they are set (see Properties that do nothing in Visual Basic). The test template’s own sources and the way the tests run are on Testing.

What the SDK adds to your project

The following are not in the project file above, but are in force for every Microsoft.NET.Sdk Visual Basic project. Each was observed with dotnet msbuild -getProperty / -getItem, or in the captured command line below.

Implicit What it is

Source files

Compile Include="**/*.vb", minus bin, obj and other default excludes; switched off by EnableDefaultCompileItems = false. **/*.resx become EmbeddedResource items, everything else is None. Putting a file into the folder is enough; listing it again is an error (NETSDK1022, shown below).

Framework reference

The Microsoft.NETCore.App reference pack for the target framework: 167 reference assemblies (for net10.0 on this SDK) passed as /reference:, plus /nostdlib /nosdkpath so the compiler never looks anywhere else.

Microsoft.VisualBasic.dll (which type-forwards to Microsoft.VisualBasic.Core) passed as /vbruntime:<path>, so Left, Mid, CInt, Format, Like and the My machinery are available without a Reference.

Warning defaults

NoWarn = 41999,42016,42017,42018,42019,42020,42021,42022,42032,42036 (plus BC41997 added on .NET targets), WarningLevel 1, and WarningsAsErrors NU1605;SYSLIB0011.

CONFIG, DEBUG, TRACE, PLATFORM, _MyType, and the target framework symbols (NET, NET10_0, NETCOREAPP, …​); see DefineConstants and the implicit symbols.

The .NET analyzers (Microsoft.CodeAnalysis.VisualBasic.NetAnalyzers.dll and Microsoft.CodeAnalysis.NetAnalyzers.dll) and a global analyzer config for AnalysisLevel.

Where does it come from? The Sdk attribute makes MSBuild import Sdk.props before the project body and Sdk.targets after it. The VB-specific pieces are two small files in the SDK’s Sdks/Microsoft.NET.Sdk/targets folder, selected by the project extension:

File (under the SDK folder) Contents

Sdks/Microsoft.NET.Sdk/targets/Microsoft.NET.Sdk.VisualBasic.props

Imported by Microsoft.NET.Sdk.props when the project extension is .vbproj. Defaults for WarningLevel, NoWarn, OptionExplicit, OptionCompare, OptionStrict, OptionInfer, WarningsAsErrors (adds NU1605) and DefineDebug / DefineTrace per configuration.

Sdks/Microsoft.NET.Sdk/targets/Microsoft.NET.Sdk.VisualBasic.targets

Imported by Microsoft.NET.Sdk.targets when the language is VB. The implicit Import items, FinalDefineConstants, the VBRuntime / UseReferencedVBRuntime logic, DisableSdkPath, the _MyType="Empty" define, the SupportsHotReload capability and the SYSLIB0011 rule.

Roslyn/Microsoft.VisualBasic.Core.targets

The CoreCompile target, which calls the Vbc task with 90 parameters, each fed by one property or item (listed below).

Roslyn/Microsoft.Managed.Core.targets

Behaviour shared with C#: UseSharedCompilation (default true), analyzer skipping, the Features property, source link and embedded files.

Because those are plain text files in the installed SDK, every statement about defaults on this page can be checked on your machine with dotnet msbuild -getProperty:Name, and the files are the authoritative reference when the documentation lags behind (it does, as the sections below point out).

The default items and the NETSDK1022 error

The glob is the single most common cause of a first migration error: a project converted from the old format still lists every file, so the SDK sees each file twice.

<!-- P.vbproj : SDK-style project that also lists a file the glob already included -->
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <RootNamespace>P</RootNamespace>
    <NuGetAudit>false</NuGetAudit>
  </PropertyGroup>

  <ItemGroup>
    <Compile Include="Program.vb" />
  </ItemGroup>

</Project>
$ dotnet build
/usr/share/dotnet/sdk/10.0.402/Sdks/Microsoft.NET.Sdk/targets/Microsoft.NET.Sdk.DefaultItems.Shared.targets(190,5): error NETSDK1022: Duplicate 'Compile' items were included. The .NET SDK includes 'Compile' items from your project directory by default. You can

(The message continues with the two ways out; the line is cut here.) You either delete the Compile item, or switch the glob off with EnableDefaultCompileItems set to false and list every file yourself. To exclude files from the glob, use Remove:

  <ItemGroup>
    <Compile Remove="Old/**" />
  </ItemGroup>

With Old/Legacy.vb (a second Sub Main in the same folder tree) the project built with 0 warnings and 0 errors and printed main, and dotnet msbuild -getItem:Compile listed only Program.vb: the removed file was never compiled. With EnableDefaultCompileItems set to false and <Compile Include="Program.vb" /> the same query also listed only Program.vb. Built and run: 2 projects.

From project properties to vbc options

dotnet build does not understand Visual Basic; it asks MSBuild to evaluate the project and run its targets. One of those targets, CoreCompile, calls the Vbc task, and the task turns property values into a command line for the Roslyn Visual Basic compiler. So a property is never "applied" by the compiler: each property named below is read by the SDK’s targets and turned into zero or more vbc options. Printing the command line without compiling

Reading -v:diag output (it is roughly 50,000 lines for a tiny project) is clumsy. The SDK has a switch meant for IDEs, ProvideCommandLineArgs, which makes the Vbc task return its arguments as an item instead of running the compiler. With the -getTargetResult switch of dotnet msbuild you get one JSON entry per argument:

dotnet msbuild Map.vbproj -nologo -v:q -t:ResolveReferences,CoreCompile \
  -p:SkipCompilerExecution=true -p:ProvideCommandLineArgs=true -getTargetResult:CoreCompile

This is how every row of the property table below was produced: the command is run with the baseline project and once more with one extra -p:Name=Value, and the lines that changed are the option(s) that property controls. The first surprise is /optionstrict:custom. The SDK’s default of OptionStrict Off does not become /optionstrict-; it becomes custom, a mode that raises the individual Option Strict diagnostics as warnings. Those warnings (BC42016 to BC42022 and a few more) are then silenced by the SDK’s default NoWarn, which is why a default project accepts implicit narrowing silently. The consequence is demonstrated in The NoWarn trap.

<DefineConstants>ALPHA=1;BETA=True</DefineConstants>

built, and a program using #If ALPHA = 1, #If BETA and #If DEBUG printed ALPHA is 1, BETA is on, DEBUG is on. Sharing settings across a solution

Every setting above belongs in the project file if it is specific to the project and in one of four solution-level files if it is shared. MSBuild looks upward from each project directory, and the first file of each kind it finds is imported automatically: Directory.Build.props before the project body (so project files can override it), Directory.Build.targets after the SDK targets (so it can override them), Directory.Packages.props for central package versions, and global.json (read by the dotnet host) for the SDK version. The buildprops, buildtargets, packagesprops, globaljson, editorconfig, nugetconfig and gitignore short names of dotnet new create starters for them.

The vbc option reference

vbc is the Roslyn Visual Basic compiler. In the .NET SDK it is Roslyn/bincore/vbc.dll under the SDK folder (/usr/share/dotnet/sdk/10.0.402/Roslyn/bincore/vbc.dll in the container), a framework-dependent program started with dotnet; the vbc file next to it is its apphost. vbc -version printed 5.9.0-1.26505.111: that is the compiler version, not the language version (17.13, see above). Learn’s "compiler options listed by category" page and the individual option pages describe an older compiler; the table below is the output of vbc -help of this compiler, in its eight groups, plus five options the compiler accepts but does not list. The Learn page of an option (where one exists) is linked in the references. In the "Option" column [+|-] means the option may be followed by + (on), - (off) or nothing (on).

Each option below was passed to the SDK 10.0.402 compiler on a small module. All were accepted; the ones that take a file reported a problem with the (deliberately missing) file instead of "unrecognized option", which proves the option itself was understood. A made-up option produces warning BC2007 and is ignored: vbc : warning BC2007: unrecognized option '-bogusoption'; ignored. That is also why a misspelled switch in a response file does not stop a build, which is worth knowing when you read a build log.

Running vbc by hand

Nothing prevents compiling without MSBuild; you need the reference assemblies and the right standard-library options because vbc on .NET does not find them itself. The project below is one source file, a response file with the options and a response file listing the 167 reference assemblies (made with ls $REF/*.dll | sed 's|^|-reference:|' > refs.rsp, where REF is the microsoft.netcore.app.ref folder .../ref/net10.0 of the reference pack):

Option Strict On

Public Module Hello

    Public Sub Main()
        Console.WriteLine("Hello from vbc " & Left("compiled by hand", 11))
    End Sub

End Module
# build.rsp
-nologo
-noconfig
-nostdlib
-nosdkpath
-target:exe
-out:Hello.dll
-optionstrict+
-rootnamespace:Hand
-define:_MyType="Empty"
-imports:System,Microsoft.VisualBasic
-vbruntime:<ref>/Microsoft.VisualBasic.dll
@refs.rsp
Hello.vb
dotnet /usr/share/dotnet/sdk/10.0.402/Roslyn/bincore/vbc.dll @build.rsp
vbc : warning BC2025: ignoring /noconfig option because it was specified in a response file
vbc exit code: 0

The Hello.runtimeconfig.json that dotnet needs to run a framework-dependent program (the SDK writes it for you in a project build) is three lines of JSON that name the framework Microsoft.NETCore.App version 10.0.0; with it, dotnet Hello.dll printed:

Legacy (non-SDK) project files

Until .NET Core, every Visual Basic project used a verbose format that listed everything by hand. You meet it in .NET Framework solutions, in older repositories and in the books that predate the SDK. Almost every property name is the same in both formats (OutputType, RootNamespace, OptionStrict, MyType, DefineConstants), which is why a conversion is mostly deletion. A reasonable order is: create an SDK-style project that targets the same .NET Framework version (net48, net481: it compiles anywhere with the reference assemblies package, as the multi-targeting example showed), delete the lists the SDK now provides, replace packages.config with PackageReference, fix the AssemblyInfo duplicates, get the build green on the old framework, and only then change the target to net10.0 and deal with the APIs that moved. Microsoft’s Upgrade Assistant and the app-modernization tooling can automate part of this; their current capabilities were not tested for this page. Web Forms and ASP.NET MVC projects are .NET Framework projects, normally in the legacy format, as described in Web, HTTP and Services. The strategy side is on Migrating Legacy Visual Basic.

Where the books and the older documentation are outdated

The books that predate the SDK-style format describe Visual Basic through a .NET Framework console template and a Visual Studio of that time; on current tooling the same programs are created with dotnet new console -lang VB or File > New in Visual Studio 2026 and build against .NET 10 (see Getting Started). Beyond the books, a few official pages lag behind the product, and a reader following them gets a wrong picture:

  • The Learn pages -langversion and Select the Visual Basic language version list LangVersion values only up to 16.9 (the compiler also accepts 17.13), and the first says the option can be set only on the command line, which is not true for a project.

  • The Learn Vbc task page lists 53 parameters, 50 of them still current; the targets pass 90.

  • The Learn MSBuild properties for Microsoft.NET.Sdk page does not mention the Visual Basic-specific properties (OptionStrict, OptionExplicit, OptionInfer, OptionCompare, RemoveIntegerChecks, MyType, VBRuntime, RootNamespace, StartupObject and DefineConstants each had zero matches in the page), so this page’s tables come from the SDK files themselves.

  • The Learn compiler-option pages do not cover everything vbc -help prints; the options -analyzer, -additionalfile, -checksumalgorithm, -errorlog, -ruleset, -reportanalyzer, -skipanalyzers, -instrument, -sourcelink, -publicsign, -generatedfilesout, -parallel, -preferreduilang, -nosdkpath, -reportivts and -version have no page named after them.

  • The Learn Compile Page and Application Page of the Project Designer say they apply to Visual Studio 2017.

  • The default OptionStrict is Off in the SDK although Learn and every style guide recommend On; there is no project template that changes it.

Summary

  • A Visual Basic project is an SDK-style .vbproj; the SDK adds the sources (glob), the references, eight global imports, the option defaults and a NoWarn list.

  • Properties become vbc options through the Vbc task (90 parameters). dotnet msbuild -getTargetResult:CoreCompile with ProvideCommandLineArgs shows the result without compiling.

  • OptionStrict Off is passed as /optionstrict:custom and relies on the default NoWarn; write $(NoWarn);..., or better set OptionStrict On in Directory.Build.props.

  • DefineConstants is comma separated; DefineDebug false does not remove DEBUG; Import items replace ImplicitUsings; Nullable and Using are inert.

  • LangVersion accepts 9 to 16.9, 17.13, default and latest; the syntax gates are those of the language history, and no syntax has been added since 15.5.

  • MyType, VBRuntime and UseReferencedVBRuntime choose the My classes and the runtime; they differ for net10.0, net10.0-windows, net481 and netstandard2.0.

  • Share settings with Directory.Build.props, Directory.Packages.props and global.json; a command-line -p: property wins over all of them.

  • dotnet new -lang VB, sln, add, build, run, test, pack, publish and format are the day-to-day commands; dotnet msbuild -pp shows the expanded project.
