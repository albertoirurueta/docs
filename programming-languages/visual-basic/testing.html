Testing Visual Basic Code

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Visual Basic 17.13 on .NET 10 (SDK 10.0.402) and was checked on 2026-10-19. Every test project and test shown here was built with warnings treated as errors and Option Strict On, and run with dotnet test in the .NET 10 SDK container (Linux, arm64); the test counts and messages are the ones the tools printed. Container paths such as /w/... are shortened in the output blocks. The reference scenario is the shelf (Isbn, Book, Magazine, Loan, ICatalogStore, Catalog); the library under test has the root namespace Shelf.Core and the three test projects are Shelf.Tests.MSTest, Shelf.Tests.XUnit and Shelf.Tests.NUnit.

Visual Basic has first-class support in all three .NET test frameworks. The framework packages are language-neutral libraries, the dotnet new templates exist for VB, and dotnet test does not care which language the tests are written in. What changes from C# is the spelling: attributes use angle brackets, lambdas are Sub() and Function(), Is is a keyword that NUnit’s constraint syntax collides with, Async Sub tests are rejected, and a few things that C# test code takes for granted (await using, tuple deconstruction, an async method returning ValueTask) do not exist in VB. This page shows the complete working programs for the three frameworks, then explains each topic across the three at once. The shared .NET background (what a test runner is, the pyramid, naming, isolation) is on the C# page Testing, which this page does not repeat; here the focus is the VB syntax, the VB-specific traps and the tooling that is verified to work from VB.

The template output shows the points to adjust in a VB test project:

  • The templates do not turn Option Strict on. The SDK default for VB is OptionStrict off, so the test projects of a strict solution need <OptionStrict>On</OptionStrict> in the project or, better, in a Directory.Build.props for the whole solution (see Projects, MSBuild and the dotnet CLI and Option Statements). The shelf solution uses OptionStrict, TreatWarningsAsErrors and NuGetAudit set in one Directory.Build.props, so every file below starts with Option Strict On and every analyzer warning is an error.

  • Only the MSTest template sets LangVersion, ImplicitUsings and Nullable. They are C#-centred settings: Nullable has no effect on VB, and ImplicitUsings only adds a few namespace imports.

  • The MSTest template adds MSTestSettings.vb, an assembly-level Parallelize attribute, because the MSTest analyzers demand a decision about parallelism (shown below).

  • The xUnit and NUnit templates add coverlet.collector for code coverage, and the NUnit one adds NUnit.Analyzers.

  • The template folder name becomes the project name. A hyphenated name such as Shelf-Tests has no valid root namespace, so set RootNamespace (BC30113 otherwise; see Program Structure and Code Conventions).

  • There is no xUnit v3 template in the SDK’s list. dotnet new list -lang VB lists xunit (the v2 template shown above) and no xunit3, and neither does dotnet new list test for any language in the 10.0.402 SDK. The 11.0.100-rc.2 SDK image lists the same VB test templates. A VB project can still use xUnit v3 by hand; see Microsoft.Testing.Platform and xUnit v3.

The code under test

The tests use Shelf.Core, whose domain types are the shelf types used throughout this section, plus one small file added for this page, LoanDesk.vb, that gives the tests something to mock (IBookLookup), something time-dependent (IsOverdue) and something Friend (ComputeFine). Its project file declares which test assemblies may see the Friend members:

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <RootNamespace>Shelf.Core</RootNamespace>
  </PropertyGroup>
  <ItemGroup>
    <InternalsVisibleTo Include="Shelf.Tests.MSTest" />
    <InternalsVisibleTo Include="Shelf.Tests.XUnit" />
    <InternalsVisibleTo Include="Shelf.Tests.NUnit" />
  </ItemGroup>
</Project>
Option Strict On

Public Interface IBookLookup
    Function FindTitleAsync(isbn As Isbn) As Task(Of String)
End Interface

Public Class LoanDesk
    Private ReadOnly _lookup As IBookLookup
    Private ReadOnly _clock As TimeProvider

    Public Sub New(lookup As IBookLookup, clock As TimeProvider)
        _lookup = lookup
        _clock = clock
    End Sub

    Public Async Function DescribeAsync(isbn As Isbn) As Task(Of String)
        Dim title = Await _lookup.FindTitleAsync(isbn)
        Return If(title, "unknown title")
    End Function

    Public Function IsOverdue(loan As Loan) As Boolean
        Return _clock.GetLocalNow().Date > loan.DueOn.Date
    End Function

    Friend Shared Function ComputeFine(dueOn As Date, returnedOn As Date) As Decimal
        Dim lateDays = Math.Max(0, (returnedOn.Date - dueOn.Date).Days)
        Return lateDays * 0.25D
    End Function
End Class

The domain types (Isbn.Parse, Isbn.TryParse, Catalog.Search, Catalog.Lend, Loan.Return) are the ones defined on Classes and Objects and Structures and Value Types. Isbn.Parse throws FormatException with the message 'text' is not a valid ISBN-13. for a bad check digit, Loan.Return throws InvalidOperationException the second time it is called, and Catalog.Search is a case-insensitive title search.

Design for testability pays for itself here: LoanDesk receives a TimeProvider and an IBookLookup through its constructor, and Catalog receives its ICatalogStore. No test needs the real clock, the network or a database. The TimeProvider abstraction is described on Dates, Times and Formatting.

A hand-written fake of the store, identical in the three test projects, keeps the catalog tests free of the data project:

Option Strict On

Imports Shelf.Core

Public Class FakeStore
    Implements ICatalogStore

    Private ReadOnly _items As New List(Of CatalogItem)

    Public Sub Add(item As CatalogItem) Implements ICatalogStore.Add
        item.Id = _items.Count + 1
        _items.Add(item)
    End Sub

    Public Function GetAll() As IReadOnlyList(Of CatalogItem) Implements ICatalogStore.GetAll
        Return _items
    End Function

    Public Function Find(id As Integer) As CatalogItem Implements ICatalogStore.Find
        Return _items.FirstOrDefault(Function(i) i.Id = id)
    End Function
End Class

Notes on the MSTest file:

  • <TestClass> is mandatory; without it the methods are silently not discovered. <TestMethod> methods are Public Sub or Public Function ... As Task, never Async Sub.

  • Public Property TestContext As TestContext is filled in by the framework before each test; a property of that exact type is all it needs, and the TestInitialize/TestCleanup methods can use it (TestContext.TestName, WriteLine).

  • MSTest 4 has Assert.ThrowsExactly(Of T)(Sub() ...) for the exact type and Assert.Throws(Of T) for the type or a subclass. Both return the exception, so the message can be asserted (the test Isbn_RejectsBadCheckDigit uses StringAssert.Contains). Assert.ThrowsExactlyAsync(Of T)(Function() ...) is the async version.

  • Assert.HasCount(1, found) is the collection-size assertion that replaced Assert.AreEqual(1, found.Count); the analyzer insists on it (see Analyzers and what they do in VB).

  • The attribute-based expected exception and the old assertion are gone. MSTest 4 has no ExpectedException attribute and no Assert.ThrowsException: the former gives BC30002 (Type 'ExpectedException' is not defined.) and the latter BC30456 ('ThrowsException' is not a member of 'Assert'.). Tutorials and books written for MSTest 1 and 2 use both.

The practical rules that follow:

  • Do not keep state in fields and expect it to survive a test in MSTest and xUnit: each test gets a new instance, so state shared between tests must go in a fixture, a Shared field or a static helper (and that state must be thread-safe, because tests may run in parallel).

  • In NUnit, do reset any field a test mutates in <SetUp>, because the instance is shared. A test class that passes alone and fails after another is the symptom.

  • The trace of the MSTest class has <DoNotParallelize> on it. Without it the MSTest template’s assembly attribute runs the methods of one class in parallel, and the lines of First and Second interleave (the same constructor, TestInitialize and TestCleanup lines appear next to each other). Hooks per test must not touch shared state unless that state is thread-safe.

  • A Shared method in VB is the equivalent of C#'s static, so <ClassInitialize> and <AssemblyInitialize> methods are Public Shared Sub Name(context As TestContext). Leaving out Shared is an analyzer error in the MSTest project (real message: MSTEST0010: ClassInitialize method 'NotShared' signature is invalid).

Fixtures with an async lifetime

xUnit’s IAsyncLifetime is the place for asynchronous setup. In xUnit v2 its two methods return Task; in xUnit v3 they return ValueTask, and VB cannot write an Async Function that returns ValueTask (BC36945: The 'Async' modifier can only be used on Subs, or on Functions that return Task or Task(Of T).). The v3 form therefore returns the ValueTask of an existing task, or ValueTask.CompletedTask, from an ordinary Function:

Data-driven tests

One test method, many inputs. The attribute that carries the data differs, but the shelf scenarios are the same: three ISBN strings with an expected result, and three loan date pairs with an expected fine.

Constant data

DataRow, InlineData and TestCase put the values in the attribute, so they must be constants. Date and Decimal are not valid attribute-argument types in .NET, and the VB compiler reports it as a conversion error. The real messages for a Date and a Decimal argument in <DataRow>:

error BC30934: Conversion from 'Date' to 'Object' cannot occur in a constant expression used as an argument to an attribute.
error BC30934: Conversion from 'Decimal' to 'Object' cannot occur in a constant expression used as an argument to an attribute.

Strings, Integer, Long, Double, Boolean, Char, enumeration values and Type (through GetType) are fine, which is what the ISBN rows use:

Async tests

A test that awaits is an Async Function ... As Task, and the three frameworks await the returned task. All three test files contain Describe_UsesLookup and Describe_PropagatesLookupFailure; the MSTest ones are shown above in the full listing.

Moq in VB

The expressions Moq reads are VB lambdas, Function(l) l.FindTitleAsync(...) for a method with a result and a single-line Sub(s) s.Add(magazine) for a method without. The extracts from the MSTest file:

        Dim lookup As New Mock(Of IBookLookup)()
        lookup.Setup(Function(l) l.FindTitleAsync(It.IsAny(Of Isbn)())).ReturnsAsync("Dune")
        Dim desk As New LoanDesk(lookup.Object, TimeProvider.System)
        ...
        lookup.Verify(Function(l) l.FindTitleAsync(It.IsAny(Of Isbn)()), Times.Once)
        ...
        store.Verify(Sub(s) s.Add(magazine), Times.Once)
        store.VerifyNoOtherCalls()

VB-specific points that these tests rely on and that were verified:

  • It.IsAny(Of Isbn)() is written with parentheses here; VB also accepts It.IsAny(Of CatalogItem) without them for a parameterless method (built and run), so both forms work.

  • Moq’s Setup/Verify for a method that returns nothing take Expression(Of Action(Of T)); the single-line Sub lambda converts to an expression tree. A multi-line Sub lambda is a statement lambda and cannot: the compiler reports BC36675 (Statement lambdas cannot be converted to expression trees.), so keep the expression to one call per lambda.

  • Mock.Of(Of IBookLookup)() creates a mock with default behaviour in one expression, which is what the clock test uses when the lookup is irrelevant.

  • ReturnsAsync and ThrowsAsync (from Moq) wrap results in a completed or faulted Task. The test Describe_PropagatesLookupFailure shows ThrowsAsync(New InvalidOperationException("offline")).

  • The mocked type must be an interface or a class with Overridable members: a VB member that is not Overridable is not virtual and cannot be mocked, the same restriction that C# has for non-virtual.

NSubstitute in VB

NSubstitute needs no lambdas for most checks, so it reads naturally in VB. From the xUnit file:

        Dim lookup = Substitute.For(Of IBookLookup)()

Faking time with TimeProvider

System.TimeProvider (since .NET 8) is the way to inject the clock. The Microsoft.Extensions.TimeProvider.Testing package provides FakeTimeProvider, whose clock only moves when the test says so:

    <Fact>
    Public Sub Loan_BecomesOverdueWhenClockAdvances()
        Dim clock As New FakeTimeProvider(New DateTimeOffset(2026, 10, 1, 9, 0, 0, TimeSpan.Zero))
        clock.SetLocalTimeZone(TimeZoneInfo.Utc)
        Dim desk As New LoanDesk(Substitute.For(Of IBookLookup)(), clock)
        Dim loan = _catalog.Lend(_catalog.Search("Dune").First(), "Ada", clock.GetLocalNow().Date)

        Assert.False(desk.IsOverdue(loan))
        clock.Advance(TimeSpan.FromDays(15))
        Assert.True(desk.IsOverdue(loan))
    End Sub

SetLocalTimeZone(TimeZoneInfo.Utc) makes GetLocalNow() independent of the machine’s time zone, so the test gives the same result on a developer laptop and a CI agent. Parallelism

Test frameworks run tests in parallel by default or by configuration, and parallel tests cannot share mutable state:

  • MSTest: the assembly attribute from the template, <Assembly: Parallelize(Workers:=0, Scope:=ExecutionScope.MethodLevel)>, runs methods in parallel with as many workers as processors. The analyzer MSTEST0001 requires an explicit decision, either Parallelize or DoNotParallelize, and it is an error in a project that treats warnings as errors.

  • xUnit.net: test classes are different collections and run in parallel with each other, while the tests of one class run one after another; Collection groups classes that must not overlap.

  • NUnit: no parallelism unless the assembly or a fixture asks for it.

A static field, a file in a temporary folder with a fixed name, an environment variable or a My.Settings value are the usual victims; the cure is a unique name per test, an injected dependency or a fixture.

Analyzers and what they do in VB

Each framework ships Roslyn analyzers that look for common test mistakes. In VB the experience is uneven, and it is worth knowing what is really checked:

Points for CI with VB:

  • Use ubuntu-latest unless the solution has Windows Forms or WPF projects; the test projects themselves are cross-platform, and the shelf’s Windows-only projects only build with EnableWindowsTargeting set.

  • Treat warnings as errors in the test projects as well; the MSTest analyzers are only useful if they fail the build.

  • Pin the .NET SDK with global.json so CI and developers run the same MSBuild and compiler (see Projects, MSBuild and the dotnet CLI).

  • Publish the TRX and Cobertura files with if: always() so a failing run still has a report.

  • A job that runs the unit tests of the library before it packs it is the first stage of the pipeline described on Libraries, Packaging and Deployment.

Practices that work well in VB

  • Name tests for behaviour: Isbn_RejectsBadCheckDigit, Return_Twice_Throws. VB identifiers are case-insensitive, so two test methods that differ only in case are a duplicate-definition error, and a local named like a type or member can hide it silently (see Variables, Constants and Scope).

  • Arrange, act, assert with blank lines between the parts, as the tests above do. One logical assertion per test; several Assert calls about the same result are fine.

  • Test through the public API; use InternalsVisibleTo for the few helpers that deserve their own tests.

  • Avoid default instances and My in code that must be tested: My.Settings and default form instances are global state (see The My Namespace).

  • Keep the VB runtime functions out of the logic where a test needs control: Now, Rnd, Dir and InputBox are untestable; TimeProvider, Random instances with a seed and interfaces are testable.

  • Test the error paths with the exact type: ThrowsExactly or Throws ensure that the failure is the one you meant, not a NullReferenceException from an earlier bug (exceptions are on Structured Exception Handling).

  • Do not test the framework or the language: a test that Isbn.Parse("x") returns an Isbn is a test of nothing; test the rules.

  • Coverage is a flashlight, not a goal: use the report to find untested branches, not to chase a number.

Common errors in test projects

Code Where and why

BC30456

'ComputeFine' is not a member of 'LoanDesk' — the member is Friend and the test assembly is not a friend; also 'AreEqual' is not a member of 'Assert' (NUnit 4) and 'ThrowsException' is not a member of 'Assert' (MSTest 4)

BC30002

Type 'ExpectedException' is not defined. — the attribute was removed in MSTest 4

BC30934

Conversion from 'Date' to 'Object' cannot occur in a constant expression used as an argument to an attribute. — Date or Decimal in DataRow, InlineData or TestCase

BC36945

The 'Async' modifier can only be used on Subs, or on Functions that return Task or Task(Of T). — Async Function returning ValueTask, as the xUnit v3 lifetime interfaces require

MSTEST0001

explicit parallelism decision missing: add MSTestSettings.vb

MSTEST0003

invalid test method signature, for instance Async Sub

MSTEST0037

use the specific assertion (Assert.HasCount) instead of Assert.AreEqual on a count

MSBuild MSB1001

Unknown switch. — dotnet test --project in VSTest mode; pass the project positionally, or switch the solution to MTP with global.json

Pitfalls checklist

  • Put Option Strict On in the test projects too, through Directory.Build.props; the templates do not.

  • Test methods are Public; test classes are Public.

  • <TestClass> is required in MSTest and invisible in the other two: forgetting it gives "0 tests found", not an error.

  • [Is] in NUnit constraints; Async Function ... As Task for async tests; never Async Sub.

  • Attribute data must be constants; use a source member for Date, Decimal and objects.

  • The same fixture rules do not hold across frameworks: instance per test (MSTest, xUnit) versus per fixture (NUnit).

  • Do not put shared mutable state in Shared fields or My.Settings when tests run in parallel.

  • Match the filter property to the adapter: TestCategory for MSTest and NUnit, the trait name for xUnit.

  • Pin the versions of Moq, NSubstitute and the test frameworks, and update them deliberately; they are third-party packages.

  • Do not mix VSTest and MTP in one folder that has a global.json selecting MTP.

  • A VB Async Function shows up in coverage as a separate state-machine class.

  • The shared platform background (the test pyramid, isolation, naming) is on the C# Testing page; test projects can be written in VB for a C# library and the reverse (see Interop with C# and Other .NET Languages).
