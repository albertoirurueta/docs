Inheritance and Polymorphism

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Visual Basic 17.13 on .NET 10 (SDK 10.0.402) and was checked on 2026-10-19. Every example is a complete console program that starts with Option Strict On. The examples were built (with warnings treated as errors, except the ones that are meant to show compiler messages, which say so) and run in the .NET 10 SDK container (Linux), and the output shown is the real output. The project root namespace is Shelf, which is why runtime messages say Shelf.Book. The project-level imports that the SDK adds (System, System.Collections.Generic, System.Linq and others) are why Console and List(Of T) need no Imports statement.

Inheritance lets a class reuse and specialise the members of another class: a Book is a CatalogItem, so code that works with catalogue items works with books, and the same call on the same variable behaves differently depending on the object it holds. That second property is polymorphism, and it is the reason to inherit at all; sharing code is better done by composition. The running example is the shelf library catalogue: an abstract CatalogItem with Book and Magazine derived from it, held by a Catalog and lent through a Loan.

Visual Basic has had implementation inheritance since Visual Basic .NET 1.0 (2002). Visual Basic 6 and VBA had only interface inheritance (Implements), so a programmer who comes from them must learn everything on this page; a programmer who comes from C# knows the ideas but meets different keywords and a handful of rules that differ in ways that matter (the order in which field initializers run, hiding by name, no covariant return types, no type patterns).

The shelf hierarchy

classDiagram class CatalogItem { <<abstract>> +Id Integer +Title String +Year Integer #New(title, year) +Kind() String* +Describe() String } class Book { +Isbn Isbn +Authors List~Author~ +Kind() String +Describe() String } class Magazine { +IssueNumber Integer +Kind() String } class Author { +Name String +BornOn Date } class Loan { +Item CatalogItem +Borrower String +DueOn Date } CatalogItem <|-- Book CatalogItem <|-- Magazine Book "1" o-- "*" Author : Authors Loan --> CatalogItem : Item

CatalogItem is abstract (MustInherit): there is no such thing as a catalogue item that is neither a book nor a magazine, so the class cannot be instantiated, and Kind is a MustOverride member that every concrete class must supply (the asterisk marks it as abstract in the diagram). Describe is Overridable, with a default implementation that Book extends. Loan depends on the abstraction, so it lends books and magazines alike.

Declaring a derived class

[attributes] [access] [Shadows] [MustInherit | NotInheritable] Class Name
    Inherits BaseClass
    ...
End Class

  • Inherits must be the first statement in the class body, before any declaration (only comments and blank lines may precede it). A class has at most one base class (BC30121 is reported for a second name). The statement may also follow the class header after a colon: Public Class LoudFormatter : Inherits Formatter.

  • The base must be a class. Inherits IDisposable is BC30258 ("Classes can inherit only from other classes"): to implement an interface use Implements (see Interfaces). A class cannot inherit from a class declared NotInheritable (BC30299), which includes String and every structure.

  • A class that has no Inherits statement inherits from System.Object. Every class, structure, enumeration, delegate and array is therefore also an Object.

  • Structures cannot use Inherits (BC30628): they derive from System.ValueType implicitly, and enumerations from System.Enum. Modules are sealed classes that cannot be inherited either (see Modules and Shared Members).

  • A derived class inherits every member of its base class except constructors and finalizers, but it can only use the ones its access level allows (see Access modifiers and inheritance).

  • Classes are inheritable by default in Visual Basic, as in C#. Add NotInheritable to forbid it. The framework design guidelines recommend sealing a class that was not designed to be extended.

  • A class nested in a base class is inherited as a member and can be shadowed by a nested class of the same name in the derived class (see Shadows versus Overloads versus Overrides).

Four facts follow from the output.

A complete hierarchy

The following program declares CatalogItem, Book and Magazine as in the diagram (the ISBN is simplified to a string so that the program stays self-contained) and uses them polymorphically through a List(Of CatalogItem).

    Public Property Year As Integer

What the example shows.

  • Protected Sub New in an abstract class: only derived classes can call it (through MyBase.New), so the constructor does not appear in the public surface of the class. When a MustInherit class declares no constructor, the compiler generates a Protected one; a concrete class gets a Public one (verified by reflection in Constructors in a hierarchy).

  • MustOverride ReadOnly Property Kind has no body and no End Property. Book overrides it with an explicit Get block, Magazine with a read-only auto-property that has an initializer (read-only auto-properties with initializers arrived in Visual Basic 14; overriding them is allowed).

  • Describe is Overridable; Book.Describe calls MyBase.Describe() to extend the base behaviour instead of replacing it, and Magazine inherits the default.

  • Dim first As CatalogItem = items(0) holds a Book. first.GetType() and TypeName(first) report the run-time class (Book), while the compiler only knows the static type (CatalogItem).

  • The commented line shows the error BC30569 for New CatalogItem(...): an abstract class is never instantiated.

Abstract and sealed classes

MustInherit and MustOverride define a contract that the compiler enforces; NotInheritable and NotOverridable close a hierarchy at the places where the design says it is finished.

Modifier Meaning C# equivalent

MustInherit (class)

Cannot be instantiated; may contain implemented members, fields and constructors, and MustOverride members

abstract class

MustOverride (member)

No body, implicitly Overridable; derived concrete classes must override it; the class must be MustInherit (BC31411)

abstract member

NotInheritable (class)

Cannot be the base of another class (BC30299)

sealed class

NotOverridable (member)

Only on an Overrides member: further derived classes cannot override it again (BC31088 without Overrides)

sealed override

  • A concrete class that inherits a MustOverride member without overriding it is rejected with BC30610 (the message lists the missing members). Declaring the class MustInherit too postpones the obligation to its own derived classes.

  • MyBase.Kind or MyClass.Id() on a MustOverride member is BC30399 or BC30614: there is no implementation to call.

  • NotOverridable in a NotInheritable class is BC30607, because nothing can override anyway. Seal the class, or seal the individual member, not both.

  • An abstract class can implement an interface without implementing its members, by redeclaring them MustOverride (see Interfaces).

  • Visual Basic has no static class equivalent other than a Module; a NotInheritable class with only Shared members and a Private Sub New is the other way to say it.

The template method pattern

A public method that fixes an algorithm and calls Protected steps that derived classes may replace is the safest way to offer extension: the base class keeps control of the order of the steps, and the extension points are small. Protected MustOverride forces a subclass to supply the essential step, Protected Overridable offers an optional one, and NotOverridable Overrides seals the diagnostic text, which is the same in every subclass.

Option Strict On

Public MustInherit Class LoanPolicy
    ' Template method: the algorithm is fixed, the steps are overridable.
    Public Function DueDate(borrowed As Date) As Date
        Dim days = BaseDays()
        Dim due = borrowed.AddDays(days)
        Return AdjustForHolidays(due)
    End Function

    Protected MustOverride Function BaseDays() As Integer

    Protected Overridable Function AdjustForHolidays(due As Date) As Date
        Return due                                     ' default: no adjustment
    End Function

    Public NotOverridable Overrides Function ToString() As String
        Return Me.GetType().Name & "(" & BaseDays() & " days)"
    End Function
End Class

Public Class StandardPolicy
    Inherits LoanPolicy

    Protected Overrides Function BaseDays() As Integer
        Return 14
    End Function
End Class

Public Class WeekdayPolicy
    Inherits StandardPolicy

    Protected Overrides Function AdjustForHolidays(due As Date) As Date
        Select Case due.DayOfWeek
            Case DayOfWeek.Saturday : Return due.AddDays(2)
            Case DayOfWeek.Sunday : Return due.AddDays(1)
            Case Else : Return due
        End Select
    End Function
End Class

Public NotInheritable Class ShortPolicy
    Inherits WeekdayPolicy

    Protected Overrides Function BaseDays() As Integer
        Return MyBase.BaseDays() \ 2
    End Function
End Class

            Console.WriteLine(policy.ToString() & " -> " & due.ToString("yyyy-MM-dd ddd", Globalization.CultureInfo.InvariantCulture))
        Next
    End Sub

Shadows versus Overloads versus Overrides

Three keywords decide what a derived-class member with the same name as an inherited one means.

  • Overrides replaces an inherited member: the slot is shared, and the call is resolved at run time from the real class of the object.

  • Overloads adds a member with a different signature, and keeps every inherited member of that name visible.

  • Shadows introduces a new member that hides the inherited one by name, with no relation to it. A call through a base-typed reference still reaches the base member, and a call through a derived-typed reference reaches the new one.

MyBase, MyClass and Me

  • Me is the current object, of its run-time class. A call Me.Name() of an Overridable member reaches the most derived override (virtual dispatch).

  • MyBase accesses members of the immediate base class. MyBase.Name() is a non-virtual call of the base implementation, whatever the object is. It is how an override extends the base behaviour. MyBase is not a value: it must be followed by a dot and a member (Return MyBase is BC32027, see the error listing below).

  • MyClass calls a member of the class where the call is written, ignoring overrides in derived classes: a non-virtual call of an Overridable method. C# has no equivalent. Use it to guarantee that the algorithm in the base class always uses the base implementation of a helper, or when a constructor has to call an overridable member without reaching the derived class.

  • Me.New(...), MyClass.New(...) and MyBase.New(...) are constructor calls; each must be the first statement of an instance constructor.

Run-time and compile-time polymorphism

Polymorphism in Visual Basic comes in two forms, and mixing them up is a classic source of confusion.

  • Run-time polymorphism (also called overriding, subtype or dynamic polymorphism): the same call on a base-typed reference runs the method of the object’s real class. It needs Overridable/Overrides (or an interface implementation) and is decided when the program runs.

  • Compile-time polymorphism (overloading): several procedures with the same name but different parameters; the compiler picks one from the static types of the arguments. The object that a base-typed variable holds is not considered.

Option Strict On

Public MustInherit Class CatalogItem
    Public Property Title As String = ""
    Public Overridable Function Describe() As String
        Return "item"
    End Function
End Class

Public Class Book
    Inherits CatalogItem
    Public Overrides Function Describe() As String
        Return "book"
    End Function
End Class

    Sub Print(item As CatalogItem)
        Console.WriteLine("Print(CatalogItem): " & item.Describe())
    End Sub

        Console.WriteLine("Print(Book): " & book.Describe())

    Sub Main()

Print(asItem) calls Print(CatalogItem) although the object is a Book, and inside it item.Describe() is dispatched at run time and still prints book. The choice of overload was made at compile time; the choice of Describe at run time. To select the overload from the real class, cast first (DirectCast(asItem, Book)), or move the behaviour into an overridable member of the hierarchy, which is the polymorphic solution and does not need a type test.

With Option Strict Off, a variable typed Object is late bound: the member is looked up when the program runs, from the real class. That is a third form of dispatch, and it is why the late-bound code of old tutorials seems to do polymorphism with no inheritance at all (see Early and Late Binding). Keep Option Strict On and use an interface or a base class instead.

Events in a hierarchy

An event can be raised only by the class that declares it. A derived class that wants to raise it cannot (BC30029); the base class offers a Protected Overridable Sub OnXxx method instead, which raises the event, and the derived class overrides it to add behaviour before or after. This is the pattern of the .NET class libraries.

Members every object inherits

Object contributes ToString, Equals, GetHashCode, GetType, the protected MemberwiseClone and Finalize, and the static Equals and ReferenceEquals. The ones worth overriding in a domain class are described here only as they relate to inheritance; the details are in other pages.

  • ToString is Overridable; override it with Public Overrides Function ToString() As String. Seal it with NotOverridable when subclasses must not change the text, as the template-method example does.

  • Equals/GetHashCode must be overridden together and be consistent across the hierarchy; a derived class that adds fields to the equality must be careful not to break symmetry with its base class (see Operator Overloading and Equality).

  • Finalize is Protected Overrides in Visual Basic and almost never needed; implement IDisposable instead (see Object Lifetime and Disposal).

  • MemberwiseClone is Protected, so only the class itself (or a derived class) can call it, from a method such as ShallowCopy. It copies the fields bit by bit: value-type fields are duplicated, but reference-type fields are shared between the original and the copy.

Changing b.Label did not change a.Label (the field of the copy was reassigned), but b.Owner.Name and b.Tags changed the objects that both copies refer to, which ReferenceEquals confirms. If a deep copy is needed, write it by hand or use a copy constructor; a clone method on a hierarchy needs an override on every class, which is one more reason to prefer copy constructors.

Designing hierarchies

  • Is-a, not has-a. A Loan is not a CatalogItem; it has one. Inheritance couples a class to the internals of its base class. Prefer composition (a field that holds another object, and delegates to it) and interfaces unless the derived class really is a specialisation that can stand in for the base in every context (the Liskov substitution principle).

  • Design for inheritance or prohibit it. A class that is meant to be extended documents which Overridable members call which others, and which are safe to override. A class that is not meant to be extended is NotInheritable. Every Overridable member is a promise that the next version of the base class has to keep, so add extension points deliberately, as the framework design guidelines advise.

  • Fragile base class. Adding or changing an Overridable member in the base class can break derived classes in other assemblies even without changing the signature, for example by calling it from a different place. Another reason to make the template method the only extension mechanism.

  • Keep hierarchies shallow. Two or three levels are common; five are a design question. Abstract base classes are most useful when they hold shared state and algorithms (the LoanPolicy example), interfaces when only a contract is shared.

  • Do not use inheritance for reuse alone. A Stack that inherits from List exposes insert and remove at any position. Wrap, do not inherit.

  • Inheriting from framework classes is the common case: Exception, EventArgs, Collection(Of T) (override InsertItem, SetItem, RemoveItem), Stream, DbContext, Form and UserControl. Read the documentation of the base for the members intended to be overridden, and call the MyBase version unless it says otherwise.

  • Where a hierarchy would need more than one base class, use interfaces plus composition. Visual Basic has no multiple class inheritance, and no mixins or traits.

public abstract class CatalogItem

    protected CatalogItem(string title, int year) { Title = title; Year = year; }

Older material you may meet

  • Visual Basic 6 and VBA have no implementation inheritance. Tutorials for them simulate it with Implements and delegation (a field that holds an inner object, and wrapper methods); in Visual Basic .NET use Inherits where the relation is is-a, and keep the delegation where it is has-a.

  • Class_Initialize and Class_Terminate correspond to Sub New and, rarely, Finalize or IDisposable; the base class constructor must be called with MyBase.New, which VB6 had no concept of.

  • Early Visual Basic .NET texts (2002 and 2003) derive exceptions from ApplicationException and omit Option Strict On; the examples here use neither.

  • Texts that explain polymorphism with a hierarchy of shapes or animals and a cascade of TypeOf ... Is tests are showing the pattern that this page recommends replacing with an overridable member.

  • Code written for Option Strict Off can call members on an Object variable and appear to be polymorphic without a common base; that is late binding (see Early and Late Binding).
