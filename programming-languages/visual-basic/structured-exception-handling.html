Structured Exception Handling

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Visual Basic 17.13 on .NET 10 (SDK 10.0.402) and was checked on 2026-10-19. Every example is a complete console program that starts with Option Strict On, was built with warnings treated as errors (except where a warning is the point, and the page says so) and was run in the .NET 10 SDK container (Linux); the output shown is real output. The project’s root namespace is ShelfDocs, which is why CLR messages and stack frames show names such as ShelfDocs.Program.Main. Compiler diagnostics are shown with the file name Program.vb, and absolute build paths in stack traces are shortened. The error examples are separate failing programs, because a declaration-level or syntax error hides the errors inside method bodies. The project-level imports that the SDK adds (System, System.Collections.Generic, System.Linq, System.Threading.Tasks and others) are why Console, List(Of T) and Task need no Imports line; System.IO is imported where files or readers appear.

Visual Basic reports run-time failures with exceptions: objects derived from System.Exception that are thrown by Throw or by the runtime and caught by a Try block further up the call stack. The model is the one the whole .NET platform shares, so a VB program catches exceptions thrown by C# libraries and the other way round. The older VB6 model (On Error GoTo, Resume Next, the Err object) still compiles and is covered on Unstructured Error Handling: On Error; new code should not use it, and it cannot be combined with Try in the same method. The C# side of the same material is on C# Exceptions and Error Handling.

How a Try statement executes

A Try statement has a Try block, any number of Catch blocks and an optional Finally block; at least one Catch or the Finally is required (BC30030 otherwise). When code in the Try block throws, the runtime searches the Catch blocks of that statement from top to bottom, then of the enclosing Try statements in the same method, then of the callers, for the first block whose type matches and whose When condition is True. Only after that search has found a handler does the runtime unwind the stack, running the Finally blocks of the frames it leaves, and then enter the Catch block. If the search finds nothing, the exception is unhandled and the process ends (see Global handlers below).

flowchart TD A(["Code in a Try block throws"]) --> B{"Search: a Catch whose type matches and whose When is True?"} B -->|"yes, in this Try or a caller"| C["Unwind the stack and run the Finally blocks of the frames being left"] C --> D["Run the matching Catch block"] D --> E["Run the Finally block of the Try that caught it"] E --> F(["Continue after End Try"]) B -->|"no handler anywhere"| G["Unhandled: UnhandledException event, then the process ends"]

Try, Catch and Finally

The first example parses text with Integer.Parse and handles three cases with three Catch blocks. Each block names an exception type, so only that type (and types derived from it) enter it. The Finally block runs after every iteration, whether the Try block completed or a Catch block ran.

Option Strict On

Module Program
    Sub Main()
        For Each text As String In {"3", "three", "", "99999999999"}
            Try
                Dim copies As Integer = Integer.Parse(text)
                Console.WriteLine("copies = " & copies)
            Catch ex As OverflowException
                Console.WriteLine("too big: " & ex.GetType().Name)
            Catch ex As FormatException
                Console.WriteLine("not a number: " & ex.Message)
            Catch ex As Exception
                Console.WriteLine("anything else: " & ex.GetType().Name)
            Finally
                Console.WriteLine("  finished '" & text & "'")
            End Try
        Next
    End Sub
End Module

The rules in one place:

Rule Detail

Matching

a Catch block handles an exception when the exception is an instance of the named type, including derived types; Catch ex As Exception handles everything that derives from Exception

Order

the first matching block wins; blocks are not searched for the best match, so put derived types before base types

Variable scope

the variable declared in Catch ex As T exists only inside that block, so sibling blocks can reuse the name ex; reusing it for another local in the same method is BC30616

Finally

runs when the Try block ends normally, when a Catch block runs, when Exit Try, Return or Exit Sub leaves the statement, and when an exception goes unhandled to an outer handler

Locals

a variable declared inside the Try block is not visible in Catch or Finally (BC30451); declare it before the Try

Result

a Try statement is a statement, not an expression; it has no value

Catch order

Because the first matching block wins, a base type placed before a derived type makes the derived block unreachable. The compiler notices it, but as a warning, not an error: BC42029 is a warning, so it becomes an error only when the project treats warnings as errors (as the other examples on this page do).

Option Strict On

Module Program
    Sub Main()
        Try
            Console.WriteLine("a")
        Catch ex As Exception
            Console.WriteLine("general")
        Catch ex As ArgumentException
            Console.WriteLine("specific")
        End Try
    End Sub
End Module

Built without TreatWarningsAsErrors; the compiler printed:

Program.vb(9,9): warning BC42029: 'Catch' block never reached, because 'ArgumentException' inherits from 'Exception'.

Put Catch ex As ArgumentException first and Catch ex As Exception last. Catching Exception is legitimate at the outermost layer of a program (a request handler, a worker loop, Sub Main) where the aim is to log and continue or stop cleanly; deep in a library it hides bugs, which is what the code-analysis rule CA1031 warns about.

Catch forms

A bare Catch with no type handles everything, and each Catch block has its own scope for the exception variable. When may use TypeOf ... Is to treat several types alike without repeating the body.

Option Strict On

Module Program
    Function Quiet() As Integer
        Try
            Return 1
        Catch
            Return -1
        End Try
    End Function

    Sub Main()
        ' Catch without a type catches Exception
        Try
            Throw New FormatException("bare Catch")
        Catch
            Console.WriteLine("caught without naming a type")
        End Try

        ' Each Catch block has its own scope, so the same name can be reused
        For Each code As Integer In {1, 2}
            Try
                If code = 1 Then Throw New ArgumentException("one")
                Throw New InvalidOperationException("two")
            Catch ex As ArgumentException
                Console.WriteLine("A: " & ex.Message)
            Catch ex As InvalidOperationException
                Console.WriteLine("B: " & ex.Message)
            End Try
        Next

        ' TypeOf in a filter instead of a separate Catch
        Try
            Throw New TimeoutException("slow")
        Catch ex As Exception When TypeOf ex Is TimeoutException OrElse TypeOf ex Is OperationCanceledException
            Console.WriteLine("timeout or cancellation: " & ex.GetType().Name)
        End Try

        Console.WriteLine(Quiet())
    End Sub
End Module

Exception filters: Catch …​ When

Catch ex As T When condition adds a Boolean expression to the match. If the expression is False, the runtime behaves as if the block were not there and keeps searching. Visual Basic compiles When to a real CLR exception filter, not to an If inside the block followed by a rethrow, and the difference is observable:

  • The filter runs during the search phase, before the Finally blocks of inner frames run. In the first case below, the filter prints before inner Finally.

  • Because the stack has not been unwound when the filter runs, the original stack trace and the debugger’s view of the throwing frame are intact.

  • An exception thrown inside a filter is swallowed and counts as False (case 3).

  • A filter that logs and returns False observes every exception without ever catching it (case 4). Compare this with Catch ex As Exception followed by Throw, which changes the trace and unwinds first.

Option Strict On

Module Program
    Private Function Check(label As String, result As Boolean) As Boolean
        Console.WriteLine("  filter " & label & " -> " & result)
        Return result
    End Function

    Private Sub Inner()
        Try
            Throw New InvalidOperationException("loan table locked")
        Finally
            Console.WriteLine("  inner Finally")
        End Try
    End Sub

    Private Function Faulty() As Boolean
        Throw New NotSupportedException("filter bug")
    End Function

    Sub Main()
        Console.WriteLine("1. filters run before inner Finally blocks:")
        Try
            Inner()
        Catch ex As InvalidOperationException When Check("outer", True)
            Console.WriteLine("  caught " & ex.Message)
        End Try

        Console.WriteLine("2. a False filter lets the next Catch look:")
        Try
            Throw New ArgumentException("code 7")
        Catch ex As ArgumentException When ex.Message.EndsWith("9")
            Console.WriteLine("  nine")
        Catch ex As ArgumentException When ex.Message.EndsWith("7")
            Console.WriteLine("  seven")
        Catch ex As ArgumentException
            Console.WriteLine("  other")
        End Try

        Console.WriteLine("3. an exception inside a filter is swallowed (filter = False):")
        Try
            Try
                Throw New InvalidOperationException("original")
            Catch ex As InvalidOperationException When Faulty()
                Console.WriteLine("  never printed")
            End Try
        Catch ex As Exception
            Console.WriteLine("  outer caught " & ex.GetType().Name & ": " & ex.Message)
        End Try

        Console.WriteLine("4. logging filter that never catches:")
        Try
            Try
                Throw New TimeoutException("lookup timed out")
            Catch ex As Exception When Check("log " & ex.Message, False)
                Console.WriteLine("  never printed")
            End Try
        Catch ex As TimeoutException
            Console.WriteLine("  handled by the outer Catch")
        End Try
    End Sub
End Module

Keep filters short, free of side effects other than logging, and cheap: they run for exceptions the block will not handle too. Typical uses are matching on a property (ex.HResult, ex.ParamName, ex.StatusCode), on the type of the inner exception, or on a retry counter held in a local variable.

Finally, Exit Try and Using

Finally is for cleanup that must happen on every path. Exit Try leaves the Try or Catch part immediately, skipping the rest of that block, but it does not skip the Finally. A Return inside Try evaluates its value first, then runs the Finally, then returns. A Using statement is a Try ... Finally that calls Dispose: the resources are disposed (in reverse order of declaration) before the Catch block of an enclosing Try runs, because the unwinding happens before the handler starts.

Option Strict On

Public Class Connection
    Implements IDisposable

    Private ReadOnly _name As String

    Public Sub New(name As String)
        _name = name
        Console.WriteLine("  open " & _name)
    End Sub

    Public Sub Dispose() Implements IDisposable.Dispose
        Console.WriteLine("  close " & _name)
    End Sub
End Class

Module Program
    Private Function Work() As String
        Try
            Return "value from Try"
        Finally
            Console.WriteLine("  Finally runs after Return was evaluated")
        End Try
    End Function

    Sub Main()
        Console.WriteLine("Using inside Try:")
        Try
            Using first As New Connection("catalog"), second As New Connection("loans")
                Console.WriteLine("  working")
                Throw New InvalidOperationException("lost connection")
            End Using
        Catch ex As InvalidOperationException
            Console.WriteLine("  Catch: " & ex.Message)
        Finally
            Console.WriteLine("  Finally")
        End Try

        Console.WriteLine("Exit Try still runs Finally:")
        Try
            Console.WriteLine("  before Exit Try")
            Exit Try
            Console.WriteLine("  never printed")
        Finally
            Console.WriteLine("  Finally")
        End Try

        Console.WriteLine(Work())

        Console.WriteLine("An exception thrown in Finally replaces the original:")
        Try
            Try
                Throw New InvalidOperationException("original")
            Finally
                Throw New ApplicationException("from Finally")
            End Try
        Catch ex As Exception
            Console.WriteLine("  " & ex.GetType().Name & ": " & ex.Message & " (inner is Nothing: " & (ex.InnerException Is Nothing) & ")")
        End Try
    End Sub
End Module

Two rules matter in Finally:

  • An exception thrown from Finally replaces the one in flight. The original is lost unless you wrap it as the InnerException of the new one. So Finally code should be small and should not throw; Dispose implementations must not throw.

  • Control cannot leave a Finally block: Return, Exit For, Exit Do, GoTo and Exit Sub out of it are errors (BC30101). C# has the same rule (CS0157).

Option Strict On

Module Program
    Function Finish() As Integer
        Try
            Return 1
        Finally
            Return 2
        End Try
    End Function
    Sub Loop2()
        For i As Integer = 1 To 3
            Try
                Console.WriteLine(i)
            Finally
                Exit For
            End Try
        Next
    End Sub
    Sub Main()
    End Sub
End Module
Program.vb(8,13): error BC30101: Branching out of a 'Finally' is not valid.
Program.vb(16,17): error BC30101: Branching out of a 'Finally' is not valid.

Cleanup of memory is not the job of Finally: the garbage collector reclaims managed memory. Use Finally/Using for files, sockets, locks, database connections, temporary state and anything with a Dispose. See Object Lifetime and Disposal.

Throw and rethrow

Throw expression raises an exception object (it must derive from System.Exception). A bare Throw inside a Catch block rethrows the exception being handled and preserves its original stack trace. Throw ex also compiles, but it throws the same object as if it were new at that point: the trace restarts at the Throw ex statement and the frames below it are lost. The analyzer CA2200 warns about this, and it is a warning by default, so the example below was built without TreatWarningsAsErrors. (With warnings as errors the SDK reports error CA2200 for the same line.) Throwing a new exception that carries the caught one as its InnerException, the third case, keeps both traces.

Option Strict On

Public Class CatalogException
    Inherits Exception

    Public Sub New(message As String, innerException As Exception)
        MyBase.New(message, innerException)
    End Sub
End Class

Module Program
    Private Sub Level3()
        Throw New InvalidOperationException("level 3 failed")
    End Sub

    Private Sub Level2(mode As Integer)
        Try
            Level3()
        Catch ex As InvalidOperationException
            Select Case mode
                Case 1
                    Throw                     ' rethrow, keeps the original stack trace
                Case 2
                    Throw ex                  ' throws the same object, restarts the stack trace here
                Case Else
                    Throw New CatalogException("catalog lookup failed", ex)
            End Select
        End Try
    End Sub

    Private Sub Level1(mode As Integer)
        Level2(mode)
    End Sub

    Private Function Frames(ex As Exception) As String
        Dim names As New List(Of String)
        For Each line As String In ex.StackTrace.Split(New String() {Environment.NewLine}, StringSplitOptions.RemoveEmptyEntries)
            Dim text As String = line.Trim().Substring(3)
            names.Add(text.Substring(0, text.IndexOf("("c)))
        Next
        Return String.Join(" <- ", names)
    End Function

    Sub Main()
        For mode As Integer = 1 To 3
            Try
                Level1(mode)
            Catch ex As Exception
                Console.WriteLine("mode " & mode & ": " & ex.GetType().Name & " | " & Frames(ex))
                If ex.InnerException IsNot Nothing Then
                    Console.WriteLine("        inner: " & ex.InnerException.GetType().Name & " | " & Frames(ex.InnerException))
                End If
            End Try
        Next
    End Sub
End Module

Built with one warning (warning CA2200: Re-throwing caught exception changes stack information). Output:

mode 1: InvalidOperationException | ShelfDocs.Program.Level3 <- ShelfDocs.Program.Level2 <- ShelfDocs.Program.Level1 <- ShelfDocs.Program.Main
mode 2: InvalidOperationException | ShelfDocs.Program.Level2 <- ShelfDocs.Program.Level1 <- ShelfDocs.Program.Main
mode 3: CatalogException | ShelfDocs.Program.Level2 <- ShelfDocs.Program.Level1 <- ShelfDocs.Program.Main
        inner: InvalidOperationException | ShelfDocs.Program.Level3 <- ShelfDocs.Program.Level2

Source: CA2200: Rethrow to preserve stack details

In mode 1 the trace still starts in Level3, where the failure happened. In mode 2, after Throw ex, Level3 is gone from the trace. In mode 3 the new CatalogException starts in Level2 and the original, with its full trace, is its InnerException.

To keep a trace while moving an exception between threads or to a later point, capture it with ExceptionDispatchInfo (shown in the properties example below); rethrowing it appends to the original trace instead of replacing it.

Throw is a statement, not an expression

C# can write value = text ?? throw new ArgumentNullException(...), and C# 7.0 allows throw in a conditional or lambda expression body. Visual Basic has no throw expression: Throw is a statement and cannot appear where a value is expected. Use a guard clause (ArgumentNullException.ThrowIfNull, below), an If statement, or a small helper Function that throws and is used as the second argument of If(a, b).

Option Strict On

Module Program
    Private Function Fail() As Integer
        Throw New InvalidOperationException("fail")
    End Function

    Sub Main()
        ' C# writes: value = text ?? throw new ArgumentNullException(...)   VB has no throw expression.
        Dim text As String = Nothing
        Try
            Dim value As String = If(text, Throw())
        Catch ex As Exception
        End Try
    End Sub
End Module
Program.vb(12,44): error BC30201: Expression expected.

Exception properties

The members worth knowing, shown in one program: Message, Source (the assembly name by default), TargetSite, HResult, the Data dictionary for extra context, InnerException and GetBaseException, AggregateException.Flatten, and ExceptionDispatchInfo.

Option Strict On
Imports System.Runtime.ExceptionServices

Module Program
    Private Function Boom(code As Integer) As Exception
        Try
            Throw New InvalidOperationException("boom " & code)
        Catch ex As InvalidOperationException
            Return ex
        End Try
    End Function

    Sub Main()
        Dim never As New InvalidOperationException("never thrown")
        Console.WriteLine("StackTrace of an exception that was never thrown is Nothing: " & (never.StackTrace Is Nothing))

        Dim ex As Exception = Boom(1)
        ex.Data("isbn") = "9780306406157"
        ex.Data("attempt") = 2
        ex.HelpLink = "https://example.org/help/boom"
        Console.WriteLine("Message   : " & ex.Message)
        Console.WriteLine("Source    : " & ex.Source)
        Console.WriteLine("TargetSite: " & ex.TargetSite.Name)
        Console.WriteLine("HResult   : 0x" & ex.HResult.ToString("X8"))
        For Each entry As System.Collections.DictionaryEntry In ex.Data
            Console.WriteLine("Data      : " & entry.Key.ToString() & " = " & entry.Value.ToString())
        Next
        Console.WriteLine("GetBaseException: " & ex.GetBaseException().Message)

        Dim wrapped As New InvalidOperationException("outer", New FormatException("middle", New ArgumentException("inner")))
        Console.WriteLine("Base exception of a chain: " & wrapped.GetBaseException().GetType().Name)
        Dim current As Exception = wrapped
        Dim depth As Integer = 0
        Do While current IsNot Nothing
            Console.WriteLine(New String(" "c, depth * 2) & current.GetType().Name & ": " & current.Message)
            current = current.InnerException
            depth += 1
        Loop

        Dim agg As New AggregateException("several", New Exception() {
            New TimeoutException("a"),
            New AggregateException(New Exception() {New FormatException("b"), New KeyNotFoundException("c")})})
        Console.WriteLine("Flatten: " & String.Join(", ", agg.Flatten().InnerExceptions.Select(Function(e) e.GetType().Name)))

        ' Capture an exception here and rethrow it later, keeping its original stack trace
        Dim captured As ExceptionDispatchInfo = ExceptionDispatchInfo.Capture(Boom(2))
        Try
            captured.Throw()
        Catch e2 As InvalidOperationException
            Console.WriteLine("Rethrown with ExceptionDispatchInfo: " & e2.Message & ", trace still mentions Boom: " & e2.StackTrace.Contains("Boom"))
        End Try
    End Sub
End Module

Member Notes

Message

human-readable description; for the user or the log, not for program logic

StackTrace

Nothing until the exception is thrown; a text rendering of the frames between the throw and the catch

InnerException

the exception that caused this one; walk it in a loop, or use GetBaseException() for the innermost

Data

an IDictionary for values that explain the failure (an ISBN, an attempt count)

HResult

a number; 0x80131509 is the default for InvalidOperationException, 0x80070002 for FileNotFoundException

Three consequences:

  • FileNotFoundException derives from IOException, and ObjectDisposedException from InvalidOperationException, so order matters when catching both a family and a member.

Divide by zero, and exceptions as flow control

Introductory material often says that dividing by zero throws DivideByZeroException. In Visual Basic that is true only for some operators. / converts both operands to Double and divides, so 10 / 0 is Infinity and 0 / 0 is NaN, with no exception at all. Integer division \, Mod, and Decimal division throw. Integer.MinValue \ -1 throws OverflowException.

Option Strict On

Module Program
    Private Sub Try1(label As String, action As Func(Of Object))
        Try
            Console.WriteLine(label & " = " & Convert.ToString(action()))
        Catch ex As Exception
            Console.WriteLine(label & " throws " & ex.GetType().Name)
        End Try
    End Sub

    Private Function Average(values As IReadOnlyList(Of Integer)) As Double
        If values.Count = 0 Then
            Return 0.0
        End If
        Return CDbl(values.Sum()) / values.Count
    End Function

    Sub Main()
        Dim ten As Integer = 10
        Dim zero As Integer = 0
        Dim minusOne As Integer = -1
        Dim minimum As Integer = Integer.MinValue
        Dim d As Double = 0.0
        Dim m As Decimal = 0D

        Try1("10 \ 0 (integer division)", Function() ten \ zero)
        Try1("10 Mod 0", Function() ten Mod zero)
        Try1("10.0 Mod 0.0", Function() CDbl(ten) Mod d)

The practical lessons are the same as for any exception:

  • Validate the input instead of catching the failure when the failure is expected: test If divisor = 0 Then, return a default, or return a result type. Average of an empty list is a design decision (zero, Nothing, an error), not a case for Try.

  • Do not use exceptions for ordinary control flow. The Try pattern (Integer.TryParse, Dictionary.TryGetValue, the shelf’s Isbn.TryParse) produces the same results without throwing; a thrown-and-caught exception captures a stack trace and unwinds frames, which costs far more than a failed parse.     Sub Main()

        Dim bad1 As Integer = 0
        Dim sum1 As Long = 0
        For Each text As String In inputs
            Try
                sum1 += Integer.Parse(text)
            Catch ex As FormatException
                bad1 += 1
            End Try

        Dim bad2 As Integer = 0
        Dim sum2 As Long = 0
        For Each text As String In inputs
            Dim value As Integer

                sum2 += value
            Else
                bad2 += 1
            End If
        Next

        Console.WriteLine("Parse + Catch    : bad=" & bad1 & " sum=" & sum1)
        Console.WriteLine("TryParse         : bad=" & bad2 & " sum=" & sum2)

Custom exceptions and guard clauses

Derive custom exceptions from Exception (or from a more specific type), not from ApplicationException: the .NET design guidelines no longer recommend that base class, and it adds nothing. Name them with the Exception suffix, offer the standard constructors (no arguments, a message, a message and an inner exception), and add properties for the data a handler needs. Create a custom type only when callers will handle it differently from the existing ones; otherwise throw a standard type (ArgumentException, InvalidOperationException, NotSupportedException).

Guard clauses check arguments first and throw before any work is done. The throw helpers on ArgumentNullException, ArgumentException and ArgumentOutOfRangeException capture the parameter name from the argument expression, so the message names the parameter without a string literal. They are ordinary shared methods, so they work from Visual Basic exactly as from C#.

Option Strict On

Public Class CatalogException
    Inherits Exception

    Public Sub New()
        MyBase.New()
    End Sub

    Public Sub New(message As String)
        MyBase.New(message)
    End Sub

    Public Sub New(message As String, innerException As Exception)
        MyBase.New(message, innerException)
    End Sub
End Class

Public Class BookNotFoundException
    Inherits CatalogException

    Public ReadOnly Property IsbnText As String

    Public Sub New(isbnText As String)
        MyBase.New("No book with ISBN " & isbnText & " is in the catalog.")
        Me.IsbnText = isbnText
    End Sub
End Class

Public Class Catalog
    Private ReadOnly _titles As New Dictionary(Of String, String)

    Public Sub Add(isbnText As String, title As String, copies As Integer)
        ArgumentException.ThrowIfNullOrWhiteSpace(isbnText)
        ArgumentNullException.ThrowIfNull(title)
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(copies)
        _titles(isbnText) = title
    End Sub

    Public Function TitleOf(isbnText As String) As String
        Dim title As String = Nothing
        If Not _titles.TryGetValue(isbnText, title) Then
            Throw New BookNotFoundException(isbnText)
        End If
        Return title
    End Function
End Class

Global handlers and logging

An exception that no Catch handles is unhandled and, in a .NET process, ends the process after the runtime has given the application one chance to log it. Global handlers are for logging and for a clean shutdown (or, in a UI, for keeping the window open), not for routine error handling: after an AppDomain.UnhandledException the process terminates whatever the handler does.

Hook Fires for Where it applies

AppDomain.CurrentDomain.UnhandledException

an exception not caught on any thread; the process ends afterwards (IsTerminating is True)

every application type

AppDomain.CurrentDomain.FirstChanceException

every exception when first thrown, before any handler is searched; observation only

every application type

TaskScheduler.UnobservedTaskException

a faulted Task that nobody awaited, observed when the task is finalized; SetObserved() marks it handled

every application type

Application.ThreadException

an exception from a Windows Forms event handler or message-loop callback on the UI thread

Windows Forms

My.Application.UnhandledException

the same, in a Windows Forms project that uses the VB Application Framework; e.ExitApplication = False keeps the app running

Windows Forms with the Application Framework

Dispatcher.UnhandledException

an exception on a WPF dispatcher thread

WPF

The console program below registers three of the hooks, handles one exception normally, leaves a faulted task unobserved and then throws an exception that nothing catches. The runtime prints its own report after the handler finishes and the process aborts (exit code 134 on Linux; Windows reports a different code).

Imports System.Runtime.CompilerServices
Imports System.Runtime.ExceptionServices

Module Program
    <MethodImpl(MethodImplOptions.NoInlining)>
    Private Sub FaultAndForget()
        Task.Run(Sub() Throw New TimeoutException("task nobody awaited"))
        Threading.Thread.Sleep(200)
    End Sub

    Sub Main()

            Sub(sender As Object, e As FirstChanceExceptionEventArgs)

                Console.WriteLine("Unobserved  : " & e.Exception.InnerException.Message)

            End Sub

        Catch ex As FormatException

        End Try

        FaultAndForget()

Two details. The LogError(ex, template, args) overload takes the exception first. And the Throw after logging rethrows to the caller; the outcome is a logged and still-propagating exception, which is right when this layer cannot recover. Logging and then swallowing is only right at a boundary that really handles the failure. The console provider writes on a background thread, so the order of its lines relative to Console.WriteLine is not guaranteed (here caller still sees came out before the fail entry). Because the logging namespace contains a child namespace called Console, the program qualifies System.Console.WriteLine; with Imports Microsoft.Extensions.Logging an unqualified Console.WriteLine fails with BC30456, because Console now binds to Microsoft.Extensions.Logging.Console.

Exceptions in asynchronous code

Exceptions thrown inside an Async method are stored in the returned Task, and Await rethrows them with their original type at the awaiting line. Task.WhenAll collects several failures, but Await rethrows only the first; the full list is in Task.Exception. Blocking with Wait() or .Result wraps everything in an AggregateException.

Option Strict On

Module Program
    Private Async Function LookupAsync(isbnText As String) As Task(Of String)
        Await Task.Delay(10)
        Throw New KeyNotFoundException("no book " & isbnText)
    End Function

    Private Async Function FailAfterAsync(ms As Integer, label As String) As Task
        Await Task.Delay(ms)
        Throw New InvalidOperationException(label)
    End Function

    Private Async Function RunAsync() As Task
        Try
            Dim title As String = Await LookupAsync("9780306406157")
            Console.WriteLine(title)
        Catch ex As KeyNotFoundException
            Console.WriteLine("Await rethrows the original type: " & ex.Message)
        End Try

        Dim both As Task = Task.WhenAll(FailAfterAsync(10, "first"), FailAfterAsync(30, "second"))
        Try
            Await both
        Catch ex As InvalidOperationException
            Console.WriteLine("Await keeps only the first: " & ex.Message)
            Console.WriteLine("Task.Exception has them all: " & both.Exception.InnerExceptions.Count)
        End Try

        Try
            both.Wait()
        Catch ex As AggregateException
            Console.WriteLine("Wait wraps them: " & ex.GetType().Name & " with " & ex.InnerExceptions.Count & " inner exceptions")
        End Try
    End Function

    Sub Main()
        RunAsync().GetAwaiter().GetResult()
    End Sub
End Module

Await keeps only the first: first
Task.Exception has them all: 2
Wait wraps them: AggregateException with 2 inner exceptions

Visual Basic has a restriction that C# no longer has: Await cannot appear inside a Catch block, a Finally block or a SyncLock (BC36943). Move the awaited call after the Try statement, record the outcome in a local variable, or restructure the loop.

    Private Async Function RunAsync() As Task
        Try
            Throw New InvalidOperationException("in Try")
        Catch ex As InvalidOperationException
            Await Task.Delay(1)
        Finally
            Await Task.Delay(1)
        End Try
    End Function

    Sub Main()
        RunAsync().GetAwaiter().GetResult()
    End Sub
End Module

Where introductory material is out of date

Introductory VB.NET books and tutorials, including popular ones, were mostly written for earlier Visual Studio versions. For exceptions, check these points when you meet them:

  • 10 / 0 does not throw: it is Infinity. Only \, Mod and Decimal division throw DivideByZeroException.

  • ApplicationException as the base of custom exceptions is outdated advice; derive from Exception.

  • A serialization constructor and <Serializable> on custom exceptions are no longer needed and warn on .NET 10 (SYSLIB0051).

  • Catch order matters, and a base type first produces BC42029, not a working program.

  • CInt, CDbl and CDate on text throw InvalidCastException, not FormatException. Prefer the TryParse methods.

  • Logging with Debug.WriteLine or a text file is replaced by Microsoft.Extensions.Logging (or a framework behind it).

  • A global handler cannot keep a console or service process alive after AppDomain.UnhandledException; only a UI framework event such as Application.ThreadException can.

  • On Error is not how new Visual Basic is written; see On Error.

Version notes and pitfalls

Topic Note

Try/Catch/Finally, Throw

available since the first .NET version of Visual Basic; the replacement for the VB6 On Error model

When filters

compile to CLR exception filters (observable in the first-pass behaviour above)

Throw helpers

ThrowIfNull since .NET 6; ThrowIfNullOrWhiteSpace, ThrowIfNegativeOrZero, ThrowIfGreaterThan since .NET 8

Obsolete serialization constructor

SYSLIB0051 on current .NET versions

Windows-only hooks

Application.ThreadException and My.Application.UnhandledException are Windows Forms; WPF has Dispatcher events

.NET Framework

the same Try model; Microsoft.Extensions.Logging is a NuGet package there; the Application Framework hooks are the same

Pitfalls:

  • Catching Exception and doing nothing hides defects. Log and rethrow, or handle a specific type.

  • Throw ex loses the trace; use Throw.

  • Messages are for people. Do not parse ex.Message; branch on the type, on HResult or on a property.

  • An exception in Finally or Dispose masks the original.

  • Do not catch NullReferenceException, IndexOutOfRangeException or InvalidCastException to cope with bad input; test the input. They indicate defects.

  • Using and Finally do not run when the process is terminated (stack overflow, End, Environment.FailFast).
