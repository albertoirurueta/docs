Getting Started with TypeScript

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

TypeScript is JavaScript with a static type layer that the compiler checks and then throws away. You write .ts, tsc verifies the types and emits ordinary .js — nothing about the running program changes. If you have five minutes, read TypeScript in 5 minutes first; this page is the hands-on version.

An erasable typed superset of JavaScript

Every valid JavaScript file is already a valid TypeScript file. TypeScript only adds annotations, and those annotations exist only at compile time: they are checked, then stripped. There are no runtime types, no reflection, and no runtime cost.

function greet(user: { name: string; age: number }): string {
  return `Hello, ${user.name} (${user.age})`;
}

const alice = { name: "Alice", age: 30 };
console.log(greet(alice));

Compiled with tsc (targeting a modern runtime), the emitted JavaScript is what you would have written by hand — the shape at runtime is identical:

function greet(user) {
    return `Hello, ${user.name} (${user.age})`;
}
const alice = { name: "Alice", age: 30 };
console.log(greet(alice));

Type-checking and code generation are independent passes. By default a type error is reported but does not stop the emit:

let count: number = 1;
count = "two";
$ npx tsc bad.ts
bad.ts:2:1 - error TS2322: Type 'string' is not assignable to type 'number'.

2 count = "two";
  ~~~~~

Found 1 error in bad.ts:2

bad.js is still written, containing count = "two". Set noEmitOnError in tsconfig.json (or pass --noEmitOnError) when you want a failed check to suppress output — the usual choice for CI. See tsconfig and Compiler Options for the switches that shape the emit.

Install and first compile

Install TypeScript as a per-project dev dependency so every checkout builds against a known version:

npm i -D typescript          # local dev dependency
npx tsc --version

npx tsc --init               # writes tsconfig.json with strict defaults
npx tsc                      # compile every file the tsconfig includes
npx tsc --watch              # recompile on save (alias: -w)
npx tsc hello.ts             # one-off: compile a single file, ignoring tsconfig

The download page covers global installs, other package managers, and the nightly build.

Create hello.ts:

const who: string = process.argv[2] ?? "world";
console.log(`Hello, ${who}!`);

Compile it and run the output with Node:

npx tsc hello.ts        # produces hello.js
node hello.js TypeScript
# -> Hello, TypeScript!

Running .ts directly with type-stripping runners

Several tools run a .ts file without a separate build step by erasing the types in memory:

npx tsx hello.ts                          # tsx
npx ts-node hello.ts                      # ts-node
node --experimental-strip-types hello.ts  # Node (built-in; unflagged in current releases)
deno run hello.ts                         # Deno -- TS support is native
bun hello.ts                              # Bun -- TS support is native

Caveat: these run but do not type-check. The count = "two" program above executes to completion under every one of them. Keep npx tsc --noEmit, your editor, or a CI step as the real type gate. Node’s built-in stripping is the strictest — it rejects TypeScript syntax that emits code (enum, namespace, parameter properties), so it only accepts genuinely erasable syntax.

For Node’s type stripping in depth, see TypeScript in Node.js.

The Playground and your editor

The TypeScript Playground is the compiler running in your browser: paste TypeScript and see the emitted JavaScript, the errors, the generated .d.ts, and every compiler option as a toggle. Each session is a shareable URL, which is why most examples in the official docs link straight into it.

Locally, VS Code bundles the TypeScript language service, so hover, go-to-definition, autocomplete, rename, and inline errors work in .ts (and .js) files with no extension to install; other editors reach the same service over the Language Server Protocol (see TypeScript IDEs & Tools for the common choices). Use your editor to interrogate the type system — hover a value to see what TypeScript inferred, rather than guessing:

const ids = [1, 2, 3].map((n) => n.toString());
//    ^? const ids: string[]
// Hover `ids` in the editor, or use the `//   ^?` twoslash query in the Playground.

What TypeScript is not

  • Not a runtime. There is no "TypeScript engine". The output is plain JavaScript for Node, Deno, Bun, or a browser. tsc itself is TypeScript compiled to JavaScript.

  • Not a linter. It checks types, not style or best practices. Run ESLint alongside it for rules like "unused variables are an error" or "prefer const declarations".

  • Not a rewrite of your logic. Erasing the annotations from a .ts file gives back working .js. The few constructs that do emit extra code (enum, namespace, constructor parameter properties, legacy experimentalDecorators) are opt-in and avoidable.

  • Not slower JavaScript. Types cost compile time only. The shipped code carries zero type-related overhead — nothing is added, checked, or reflected at runtime.

The compile pipeline

flowchart LR A[".ts source"] --> B["parse
(build AST)"] B --> C["bind
(symbols and scopes)"] C --> D["type-check
(report errors)"] D --> E["transform
(strip types, downlevel syntax)"] E --> F["emit"] F --> G[".js"] F --> H[".d.ts — with declaration"] F --> I[".js.map — with sourceMap"] D -. "errors are reported but do NOT stop emit
unless noEmitOnError is set" .-> E

The type-check and transform stages share the parsed AST but are otherwise decoupled: by default tsc prints every error and still writes the .js. noEmitOnError is what ties a clean type-check to a successful build. Declaration files (.d.ts) and source maps (.js.map) are produced by the same emit step when declaration and sourceMap are enabled.

A first project, end to end

A single file is enough to see the idea, but a real project has a tsconfig.json, a source folder and an output folder. This walk-through builds the smallest version of that shape using the request-state type that the worked example develops. The layout is:

proj/
  package.json        { "type": "module" }
  tsconfig.json
  src/
    state.ts          the RequestState union and describe()
    main.ts           uses it
  dist/               created by tsc

Create tsconfig.json. tsc --init writes a config with many options commented out and a handful switched on (strict, module: nodenext, verbatimModuleSyntax, skipLibCheck and others); the version below keeps only what this project needs, plus noEmitOnError so a failed check never produces output:

{
  "compilerOptions": {
    "target": "es2022",
    "module": "nodenext",
    "strict": true,
    "rootDir": "src",
    "outDir": "dist",
    "sourceMap": true,
    "declaration": true,
    "noEmitOnError": true
  },
  "include": ["src"]
}

src/state.ts:

export type RequestState<T> =
  | { readonly kind: "idle" }
  | { readonly kind: "loading" }
  | { readonly kind: "success"; readonly data: T }
  | { readonly kind: "error"; readonly error: string };

export function describe<T>(state: RequestState<T>): string {
  switch (state.kind) {
    case "idle":
      return "nothing yet";
    case "loading":
      return "loading...";
    case "success":
      return "got " + JSON.stringify(state.data);
    case "error":
      return "failed: " + state.error;
  }
}

src/main.ts:

import { describe, type RequestState } from "./state.js";

const states: RequestState<{ name: string }>[] = [
  { kind: "idle" },
  { kind: "loading" },
  { kind: "success", data: { name: "Ada" } },
  { kind: "error", error: "HTTP 500" },
];

for (const s of states) {
  console.log(describe(s));
}

Build and run it. The import specifier says ./state.js even though the file on disk is state.ts: TypeScript checks the specifier as it will exist after compilation, which is what Node will load. --listEmittedFiles shows exactly what the compiler wrote:

$ npx tsc -p . --listEmittedFiles
TSFILE: .../dist/state.js
TSFILE: .../dist/state.js.map
TSFILE: .../dist/state.d.ts
TSFILE: .../dist/main.js
TSFILE: .../dist/main.js.map
TSFILE: .../dist/main.d.ts

$ node dist/main.js
nothing yet
loading...
got {"name":"Ada"}
failed: HTTP 500

What the compiler produced

Three files come out for each input, each with a different audience. dist/state.js is what runs: the type alias and every annotation are gone, and nothing else changed.

export function describe(state) {
    switch (state.kind) {
        case "idle":
            return "nothing yet";
        case "loading":
            return "loading...";
        case "success":
            return "got " + JSON.stringify(state.data);
        case "error":
            return "failed: " + state.error;
    }
}
//# sourceMappingURL=state.js.map

dist/state.d.ts is what other TypeScript projects read when they import this module. It keeps only the type information, with no function bodies:

export type RequestState<T> = {
    readonly kind: "idle";
} | {
    readonly kind: "loading";
} | {
    readonly kind: "success";
    readonly data: T;
} | {
    readonly kind: "error";
    readonly error: string;
};
export declare function describe<T>(state: RequestState<T>): string;

state.js.map is a source map, which lets a debugger or a stack trace point back at state.ts. Notice also that dist/main.js begins import { describe } from "./state.js";: the type RequestState specifier was erased because it names only a type.

and errors?"} G -->|"no"| J["dist/*.js"] G -->|"no"| D["dist/*.d.ts"] G -->|"no"| M["dist/*.js.map"] G -->|"yes"| X["nothing written,

A failed check, with and without noEmitOnError

Change one return value so it has the wrong type, return 42; in the loading case, and run the build again. The checker rejects it, and because noEmitOnError is set, dist is not created:

$ npx tsc -p .
src/state.ts(12,7): error TS2322: Type 'number' is not assignable to type 'string'.
$ echo $?
1
$ ls dist
ls: dist: No such file or directory

Remove noEmitOnError and the same error is still reported, the exit code is still non-zero, but the JavaScript is written anyway. That is the behaviour of a bare tsc file.ts and of the type-stripping runners: types are one pass, code generation is another. The exit code is what a CI job should look at.

Type stripping in Node, in practice

Recent Node releases can execute .ts files directly by erasing annotations in memory. Two behaviours are worth seeing once, so they do not surprise you later. The first is that nothing is checked: a program with a type error runs normally.

$ cat bad.ts
let count: number = 1;
count = "two";
console.log(count);
$ node bad.ts
two

The second is that only erasable syntax is accepted. enum needs generated code, so the stripper refuses it:

$ cat en.ts
enum Color { Red, Green }
console.log(Color.Green);
$ node en.ts
SyntaxError [ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX]: TypeScript enum is not supported in strip-only mode

Pair stripping with "erasableSyntaxOnly": true in tsconfig.json so that your editor flags such syntax before Node does, and keep tsc --noEmit as the type gate.

Two beginner pitfalls

  • Host APIs need their types. console comes from the default lib (which includes the DOM typings), but process, Buffer and Node’s modules come from @types/node. tsc --init writes "types": [], so after npm i -D @types/node you must also list it ("types": ["node"]) or the compiler will report that it cannot find the name process. See TypeScript in Node.js.

  • Defaults differ between compiler versions. A bare tsc hello.ts with no config and no --target emits ES5-level JavaScript (let becomes var) under TypeScript 5.9, while the 7.0 compiler emits modern syntax with a "use strict" prologue. Do not depend on defaults: set target, module and strict explicitly, as in the config above.
