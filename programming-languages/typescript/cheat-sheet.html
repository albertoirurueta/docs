Which construct do I reach for?

The sheet is organised by syntax, but in practice you start from a question. The chart below maps the common questions to the construct, and the page that explains it.

flowchart TD Q["What am I describing?"] --> A{"A value that can be
one of several shapes?"} A -->|yes| U["Union type
narrow with typeof / in / kind"] A -->|no| B{"A fixed set of
named constants?"} B -->|yes| L["String-literal union
or as const object"] B -->|no| C{"An object whose shape
others will extend or implement?"} C -->|yes| I["interface"] C -->|no| D{"Derived from another type?"} D -->|yes| M["keyof / indexed access /
mapped / conditional / utility type"] D -->|no| T["type alias or
inline object type"] U --> N["unions-and-narrowing"] L --> E["enums-and-literal-alternatives"] I --> O["objects-and-interfaces"] M --> G["type-manipulation, utility-types"]

When two answers both fit, prefer the one that leaves the least room for an invalid value: a discriminated union over an interface full of optional properties, a literal union over string, unknown over any.

Erased versus emitted

The single most useful fact for reading any TypeScript file is which parts survive to run time. Everything in the left column vanishes from the emitted JavaScript; the right column is real code.

Erased (type space only) Emitted (value space)

type annotations, type aliases, interface

enum (compiled to an object) and namespace that contains values

generics, satisfies, as assertions, !

class bodies and field initialisers, including #private fields

import type and type-only specifiers

constructor parameter properties (constructor(private x: number))

declare statements and .d.ts files

decorators (standard or legacy), which compile to helper calls

Anything in the right column conflicts with erasable-only tooling such as Node’s built-in type stripping or the --erasableSyntaxOnly flag, so the sheet’s "erased vs. emitted" strip doubles as a compatibility checklist.

The errors you will meet most

A short key to the diagnostics that account for most day-to-day failures. The code (TSxxxx) is stable and searchable; the text is what the compiler printed for the snippet shown.

Code Message Usual cause and fix

TS2322

Type 'string' is not assignable to type 'number'.

A value of the wrong type was assigned or returned. Fix the value or widen the declared type.

TS2339

Property 'b' does not exist on type '{ a: number; }'.

Misspelled property, or a union that is not yet narrowed. Narrow first, or add the property to the type.

TS2345

Argument of type 'number' is not assignable to parameter of type 'string'.

The same assignability check at a call. Convert the argument or loosen the parameter.

TS2741

Property 'b' is missing in type '{ a: string; }' but required in type 'P'.

An object literal omits a required member. Provide it, or mark it optional.

TS7006

Parameter 'x' implicitly has an 'any' type.

noImplicitAny could not infer the parameter. Annotate it.

TS2564

Property 'name' has no initializer and is not definitely assigned in the constructor.

strictPropertyInitialization. Assign in the constructor, give a default, or use ! if you truly initialise it elsewhere.

TS18047

's' is possibly 'null'.

strictNullChecks. Check for null before use. The sibling code TS18048 says undefined.

TS2307

Cannot find module './nothing' or its corresponding type declarations.

A wrong path or moduleResolution, or a JavaScript package without types. Install @types/... or declare the module.

For the longer explanation of a code, paste it into the TypeScript Playground together with the snippet, or search the number.
