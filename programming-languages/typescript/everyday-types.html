Everyday Types

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

TypeScript attaches a static type to every value JavaScript already has. This page is the working vocabulary — the handful of types that show up in almost every file. It follows the official Everyday Types handbook chapter, and pairs with the JavaScript-side Types, Values & Conversions page for how the underlying values behave at runtime.

Primitives

The three most common primitives are string, number, and boolean. Note the lowercase names — they are the TypeScript types, distinct from the wrapper objects below.

const name: string = "Ada";
const age: number = 36;          // one numeric type, no int/float split
const active: boolean = true;

bigint (arbitrary-precision integers) and symbol (unique keys) round out the set:

const big: bigint = 9007199254740993n;
const id: symbol = Symbol("id");

symbol has its own handbook page, Symbols, covering unique symbol and the well-known symbols.

null and undefined are both types and values. With strictNullChecks on (part of strict), they are only assignable where you name them explicitly:

let end: number | null = null;
end = 42;

function greet(x?: string) {   // x: string | undefined
  return x ?? "stranger";
}

Wrapper objects — avoid String, Number, Boolean

The capitalized String, Number, and Boolean types refer to the boxed wrapper objects, not the primitives. They are almost never what you want: a primitive is assignable to the wrapper type but not the other way round, and the ergonomics are worse.

let a: string = "hi";
let b: String = a;   // allowed, but pointless
a = b;               // Error: 'String' is not assignable to 'string'

Rule of thumb: lowercase string / number / boolean always. The uppercase forms exist only for rare interop edge cases.

Arrays and tuples

Write an array type as T[] or the equivalent Array<T>:

const xs: number[] = [1, 2, 3];
const ys: Array<string> = ["a", "b"];

readonly T[] (or ReadonlyArray<T>) drops the mutating members — push, splice, index assignment:

const frozen: readonly number[] = [1, 2, 3];
frozen.push(4);   // Error: 'push' does not exist on 'readonly number[]'

A tuple fixes the length and the type at each position:

const origin: [number, number] = [10, 20];
const entry: [string, number] = ["age", 36];

Arrays, readonly arrays, tuples, labelled elements, and variadic tuple types get the full treatment on Arrays and Tuples.

Object types

An object type lists its properties and their types. Written inline it is an object type literal, e.g. { x: number; y: number }:

function distance(p: { x: number; y: number }): number {
  return Math.hypot(p.x, p.y);
}
distance({ x: 3, y: 4 });   // 5

A ? marks a property optional (its type becomes T | undefined); readonly blocks reassignment after the object is built:

interface User {
  readonly id: string;
  name: string;
  nickname?: string;      // string | undefined
}

const u: User = { id: "u1", name: "Ada" };
u.name = "Ada L.";        // ok
u.id = "u2";              // Error: 'id' is a read-only property

A function-valued member can use method syntax or property syntax. Property syntax with an arrow type is checked more strictly for parameter variance and is the modern default:

interface Store {
  get(key: string): string;                    // method syntax
  set: (key: string, value: string) => void;   // property syntax
}

Interfaces versus type aliases, index signatures, and excess-property checks are covered on Objects and Interfaces.

What each primitive type actually is

The primitive types are a thin layer over JavaScript’s own runtime values, so every quirk of the value shows up in the type. Knowing the handful of quirks avoids most beginner bugs.

Type What to remember

number

A 64-bit IEEE-754 float. There is no int, so 3.5 and 3 have the same type, and 0.1 + 0.2 is 0.30000000000000004. NaN, Infinity and -Infinity are number values, and typeof NaN is "number".

bigint

Arbitrary-precision integers, written with an n suffix. It never mixes with number in arithmetic.

string

An immutable sequence of UTF-16 code units. Template literals keep the type string.

boolean

true or false, which are also the two literal types that boolean is the union of.

symbol

A unique value, usually used as a property key. Two Symbol("id") calls are never equal.

null, undefined

Two distinct types with one value each. typeof null is "object", a historical accident the type system does not repeat.

Run these facts to see them, as plain JavaScript semantics that the types describe:

console.log(2n ** 64n, typeof 2n, 0.1 + 0.2);
console.log(Number.MAX_SAFE_INTEGER + 2, 9007199254740993, 9007199254740993n);
console.log(Symbol("id") === Symbol("id"));
console.log(`${1 / 0} ${-1 / 0} ${0 / 0} ${Number("x")}`);
console.log(typeof null, typeof undefined, typeof NaN, NaN === NaN, Number.isNaN(NaN));
18446744073709551616n bigint 0.30000000000000004
9007199254740992 9007199254740992 9007199254740993n
false
Infinity -Infinity NaN NaN
object undefined number false true

The second line is the reason bigint exists: above Number.MAX_SAFE_INTEGER a number silently rounds, while the bigint literal stays exact. The type system keeps the two apart so a mix is an error rather than a runtime crash:

const big: bigint = 10n;
const mix = big + 1;            // error
const n: number = big;          // error
ev.ts(2,13): error TS2365: Operator '+' cannot be applied to types 'bigint' and '1'.
ev.ts(3,7): error TS2322: Type 'bigint' is not assignable to type 'number'.

Without the check, the first line would fail at run time with TypeError: Cannot mix BigInt and other types, use explicit conversions. Convert explicitly with BigInt(1) or Number(big), remembering that Number(big) may lose precision.

unique symbol and comparing symbols

Because every symbol is distinct, the checker can tell two symbol constants apart when they are declared as unique symbol. This is the mechanism behind the branded types on Type Design and Best Practices:

const s1 = Symbol("id");
const s2 = Symbol("id");
console.log(s1 === s2);          // error: no overlap between 'typeof s1' and 'typeof s2'

declare const k1: unique symbol;
const tag: typeof k1 = k1;       // ok
const tag2: typeof k1 = Symbol();  // error: a fresh symbol is not k1
ev.ts(9,13): error TS2367: This comparison appears to be unintentional because the types 'typeof s1' and 'typeof s2' have no overlap.
ev.ts(12,7): error TS2322: Type 'typeof tag2' is not assignable to type 'typeof k1'.

Literal types and where they widen

Every primitive value also has a literal type: "GET" is a type with one value, a subtype of string. A const binding keeps the literal type, a let binding widens it, and an object property widens too, because a property can be reassigned. This is the single most common source of "Argument of type 'string' is not assignable to parameter of type '"GET" | "POST"'" errors.

function send(method: "GET" | "POST", url: string) {}

const req = { method: "GET", url: "/users" };
send(req.method, req.url);                      // error: req.method widened to string

const req2 = { method: "GET", url: "/users" } as const;
send(req2.method, req2.url);                    // ok: literal types preserved (and readonly)

const req3: { method: "GET" | "POST"; url: string } = { method: "GET", url: "/u" };
send(req3.method, req3.url);                    // ok: the annotation says what the property may be

let method = "GET";
send(method, "/");                              // error: a let widens to string
const method2 = "GET";
send(method2, "/");                             // ok
ev.ts(17,6): error TS2345: Argument of type 'string' is not assignable to parameter of type '"GET" | "POST"'.
ev.ts(23,6): error TS2345: Argument of type 'string' is not assignable to parameter of type '"GET" | "POST"'.
flowchart LR LIT["literal expression
'GET'"] --> C{"declared with"} C -->|"const"| K["type 'GET'
(literal kept)"] C -->|"let or var"| W["type string
(widened)"] C -->|"object property"| W C -->|"property + as const"| K2["type 'GET'
(readonly)"] C -->|"annotation 'GET' or 'POST'"| K3["type 'GET' or 'POST'"]

The cure is always one of three: write the literal where it is used, annotate the container, or add as const.

Optional values and the ?. and ?? operators

With strictNullChecks the optional property nickname?: string has the type string | undefined, and reading through a possibly-undefined value is an error until you handle it. Optional chaining and nullish coalescing are the compact forms of handling it:

interface Profile { nickname?: string; address?: { city?: string } }
declare const p: Profile | undefined;

const city = p?.address?.city ?? "unknown";   // string
const len = p?.nickname?.length;               // number | undefined
const nn = p.nickname;                         // error
ev.ts(32,12): error TS18048: 'p' is possibly 'undefined'.

?. short-circuits the whole chain to undefined as soon as one link is null or undefined; ?? replaces only null and undefined, unlike ||, which also replaces 0, "" and false. That difference matters for values such as a port number 0 or an empty string title.

Arrays and readonly: one more check

Arrays are covered in depth in Arrays and Tuples. The one rule worth stating here is that mutability is part of the type: string[] is assignable to readonly string[] but not the reverse.

const mut: string[] = ["a"];
const ro: readonly string[] = mut;     // ok
const back: string[] = ro;             // error
const l1: [string, number] = ["a", 1, 2];   // error: tuples have a fixed length
ev.ts(37,7): error TS4104: The type 'readonly string[]' is 'readonly' and cannot be assigned to the mutable type 'string[]'.
ev.ts(42,7): error TS2322: Type '[string, number, number]' is not assignable to type '[string, number]'.
  Source has 3 element(s) but target allows only 2.

Accepting readonly string[] in a function parameter is therefore the polite choice: callers can pass either kind, and the function promises not to change the argument.

any, unknown, void, never

any opts a value out of type checking entirely. It is contagious and should be rare — prefer a real type, or unknown.

let loose: any = 4;
loose.toUpperCase();   // no compile error, throws at runtime

unknown is the safe counterpart: anything is assignable to it, but you must narrow before you can use it.

function parse(json: string): unknown {
  return JSON.parse(json);
}

const data = parse('{"n":1}');
// data.n;                       // Error: 'data' is of type 'unknown'
if (data && typeof data === "object" && "n" in data) {
  console.log(data.n);          // ok after narrowing
}

void is the return type of a function that returns nothing meaningful:

function report(msg: string): void {
  console.log(msg);
}

never is the type with no values — the return type of a function that never finishes normally (it throws or loops forever), or a branch that cannot be reached. It powers exhaustiveness checks:

function fail(msg: string): never {
  throw new Error(msg);
}

type Shape = { kind: "circle"; r: number } | { kind: "square"; side: number };

function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return Math.PI * s.r ** 2;
    case "square": return s.side ** 2;
    default: {
      const _exhaustive: never = s;   // errors here if a case is missed
      return _exhaustive;
    }
  }
}

Literal types and inference

A literal type is a single exact value — "GET", 42, true. Alone it is rarely written by hand; combined in a union it models a fixed set of options:

type Method = "GET" | "POST" | "PUT" | "DELETE";

function request(url: string, method: Method) { /* ... */ }
request("/api", "POST");     // ok
request("/api", "PATCH");    // Error: '"PATCH"' is not assignable to 'Method'

Widening

How TypeScript infers a literal depends on let versus const. A const binding to a literal keeps the literal type; a let binding widens to the base primitive:

const a = "GET";     // type "GET"
let b = "GET";        // type string  (widened)

The same widening happens to object properties, which is why handing an object literal to a Method parameter can fail:

const req = { url: "/api", method: "POST" };   // method: string
request(req.url, req.method);   // Error: string is not assignable to 'Method'

as const

as const freezes an expression to its narrowest, deeply readonly form — literal types preserved, arrays turned into readonly tuples:

const req = { url: "/api", method: "POST" } as const;
// { readonly url: "/api"; readonly method: "POST" }
request(req.url, req.method);   // ok now

const methods = ["GET", "POST"] as const;
// readonly ["GET", "POST"]
type M = (typeof methods)[number];   // "GET" | "POST"

A narrower alternative for one value is an explicit type annotation on the binding, or an annotation inside a destructuring pattern:

const req2: { url: string; method: Method } = { url: "/api", method: "POST" };

function handle({ method }: { method: Method }) { /* ... */ }

In a destructuring pattern the annotation goes on the whole pattern — { method }: { method: Method } — not { method: Method }, which would instead rename the binding to Method. The Objects, Properties & Destructuring page covers the runtime destructuring syntax; the complete set of inference and widening rules is in the handbook’s Variable Declarations chapter.

Modifiers such as readonly and as const, along with satisfies and the assertion forms (as, !), are detailed on Type Assertions and Modifiers.
