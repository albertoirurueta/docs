Testing

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Swift has two testing frameworks in active use. Swift Testing (import Testing) is the modern, macro-based default for new packages and targets — see Macros for the @Test/#expect machinery underneath it. XCTest predates it, remains the framework for UI testing and much existing code, and is what swift test/Xcode ran exclusively before Swift Testing existed. Both run under the same swift test command and can coexist in one test target during a migration.

Swift Testing

import Testing
@testable import WeatherKit

@Test func parsesCelsius() {
    let reading = Reading(raw: "21.5C")
    #expect(reading.celsius == 21.5)
}

@Test func forecastRequiresACity() throws {
    let city = try #require(City(name: "Madrid"))   // unwraps, or fails and stops this test immediately
    #expect(city.name == "Madrid")
}

@Test marks an ordinary top-level or type-member function as a test case — no base class, no test-prefixed naming convention, and discovery is automatic. #expect(_:) records a failure (with the failing expression’s sub-values captured automatically) but lets the test keep running; #require(_:) does the same for an Optional or a Bool but throws on failure, stopping that test immediately — the right choice once a later line would crash or be meaningless without the value it unwraps.

@Suite and Parameterized Tests

@Suite("Reading parsing")
struct ReadingParsingTests {
    @Test("parses common temperature formats", arguments: [
        ("21.5C", 21.5), ("70F", 21.1), ("294K", 20.85)
    ])
    func parses(raw: String, expectedCelsius: Double) {
        let reading = Reading(raw: raw)
        #expect(abs(reading.celsius - expectedCelsius) < 0.1)
    }
}

@Suite groups related tests in a type (a struct, class or actor) and can nest suites inside suites, mirroring how the test report is organised. A parameterized test's arguments: runs the function once per element — each argument set is reported as its own test case, so one failing temperature format fails only that case rather than the whole function.

Traits

Trait Effect

.tags(.networking)

Attach a custom Tag, used to group tests and to include or exclude them in Xcode’s test navigator and test plans.

.enabled(if: condition)

Skip the test at run time unless condition holds (e.g. a platform check).

.disabled("reason")

Always skip, with the reason shown in the test report.

.timeLimit(.minutes(1))

Fail the test if it runs longer than the limit (expressed in whole minutes).

.serialized

On a @Suite, force its tests to run one at a time instead of Swift Testing’s default parallel execution — for tests that share mutable state.

 
@Test(.tags(.networking), .timeLimit(.minutes(1)))
func downloadsForecast() async throws { ... }

@Suite(.serialized)
struct DatabaseTests { ... }        // these tests touch a shared file and must not interleave

confirmation, Exit Tests and Known Issues

@Test func downloadInvokesCallbackExactlyOnce() async {
    await confirmation(expectedCount: 1) { confirm in
        downloader.fetch { _ in confirm() }
    }
}

@Test func crashesOnCorruptHeader() async {
    await #expect(processExitsWith: .failure) {
        Reading(raw: "\u{0}\u{0}").parseOrFatalError()
    }
}

@Test func rateLimitingIsAKnownIssue() {
    withKnownIssue("rate limiter is disabled in CI, see TICKET-123") {
        #expect(rateLimiter.isEnabled)
    }
}

confirmation replaces XCTest’s XCTestExpectation for callback-based asynchronous code: the test fails if confirm() is not called the expected number of times before the closure returns. An exit test (#expect(processExitsWith:)) runs its body in a separate process and asserts on how that process terminates — the only way to test code that is expected to crash or call fatalError, without taking the whole test run down with it. withKnownIssue records a failure inside it as expected rather than a regression, so a genuinely broken but already-tracked behaviour doesn’t block the rest of the suite.

Attachments (Attachment) let a test save arbitrary data — a captured image, a log file, an intermediate JSON payload — alongside its result, viewable from Xcode’s or swift test's test report when diagnosing a failure after the fact.

Both swift test (which discovers and runs Swift Testing and XCTest tests in the same invocation) and Xcode’s Test navigator run Swift Testing tests identically; no separate command is needed.

XCTest

import XCTest
@testable import WeatherKit

final class ReadingTests: XCTestCase {
    var reading: Reading!

    override func setUp() {
        super.setUp()
        reading = Reading(raw: "21.5C")
    }

    override func tearDown() {
        reading = nil
        super.tearDown()
    }

    func testCelsiusIsParsed() {
        XCTAssertEqual(reading.celsius, 21.5, accuracy: 0.01)
    }

    func testDownloadCallsCompletionOnce() {
        let expectation = expectation(description: "download completes")
        downloader.fetch { _ in expectation.fulfill() }
        wait(for: [expectation], timeout: 5)
    }

    func testParsingPerformance() {
        measure {
            _ = Reading(raw: "21.5C")
        }
    }
}

XCTestCase is the base class every XCTest test type inherits; setUp/tearDown run around each test method (always call super first/last), and a test-prefixed method with no parameters is discovered automatically — the same shape as Objective-C’s XCTest, since it is the same framework. The XCTAssert… family (XCTAssertEqual, XCTAssertNil, XCTAssertThrowsError, XCTAssertTrue, and so on) reports a failure at the exact call site with both the expected and actual values. XCTestExpectation (via expectation(description:) and wait(for:timeout:)) is XCTest’s answer to asynchronous callbacks — Swift Testing’s confirmation above is its direct successor. measure { ... } runs its block repeatedly and reports a performance baseline, exactly as in Objective-C’s XCTest.

Apple’s official migration guide from XCTest to Swift Testing documents the mechanical translation for every construct above (XCTAssertEqual to #expect(==), XCTestExpectation to confirmation, and so on) — most existing XCTest suites can adopt Swift Testing incrementally, file by file, since both frameworks run side by side under swift test.

@testable import (see Attributes and Compiler Control) is what lets either framework’s test target reach a module’s internal declarations without those declarations being public — private/fileprivate symbols remain unreachable regardless.

XCTest also covers UI testing through XCUITest (XCUIApplication, element queries, tap()/typeText(_:)), which drives the app’s real UI in a separate process — this is Apple-platform-only (Xcode/iOS/macOS simulators and devices) and out of scope for this reference; see Apple’s XCTest — User Interface Tests documentation.

Running Tests

swift test                                        # every test target, both frameworks
swift test --filter ReadingParsingTests            # a suite/class by name
swift test --filter ReadingParsingTests/parses     # one test within it
swift test --parallel                              # explicit parallel execution across test targets
swift test --enable-code-coverage

In Xcode, ⌘U runs the whole plan and the diamond gutter icon next to a @Test/test… method runs that one test alone — both frameworks share the same Test navigator and report.

Worked Example: Testing the Bookshelf Package

The best way to see Swift Testing is on a real package. The bookshelf library is a Swift package with one library target and one test target (the manifest is shown on Swift Package Manager); its source is a Shelf that rejects duplicate titles and can report its longest book.

public struct Book: Equatable, Sendable {
    public let title: String
    public let pages: Int
    public init(title: String, pages: Int) {
        self.title = title
        self.pages = pages
    }
}

public enum ShelfError: Error, Equatable {
    case duplicate(String)
    case empty
}

public struct Shelf: Sendable {
    public private(set) var books: [Book] = []
    public init() {}

    public mutating func add(_ book: Book) throws {
        guard !books.contains(where: { $0.title == book.title }) else {
            throw ShelfError.duplicate(book.title)
        }
        books.append(book)
    }

    public func longest() throws -> Book {
        guard let book = books.max(by: { $0.pages < $1.pages }) else { throw ShelfError.empty }
        return book
    }
}

The tests exercise success, error and parameterised cases:

import Testing
@testable import Bookshelf

@Suite("Shelf")
struct ShelfTests {
    var shelf = Shelf()

    @Test("adding a book stores it")
    mutating func addStoresBook() throws {
        try shelf.add(Book(title: "Dune", pages: 412))
        #expect(shelf.books.count == 1)
    }

    @Test("duplicate titles are rejected")
    mutating func duplicateRejected() throws {
        try shelf.add(Book(title: "Dune", pages: 412))
        #expect(throws: ShelfError.duplicate("Dune")) {
            try shelf.add(Book(title: "Dune", pages: 100))
        }
    }

    @Test("the longest book of an empty shelf is an error")
    func emptyLongest() {
        #expect(throws: ShelfError.empty) { try Shelf().longest() }
    }

    @Test("page counts are positive", arguments: [120, 336, 412, 474])
    func positivePages(pages: Int) {
        #expect(Book(title: "x", pages: pages).pages > 0)
    }

    @Test("longest picks the largest page count", arguments: [
        (["Kim", "Emma"], [336, 474], "Emma"),
        (["Dune", "Kim"], [412, 336], "Dune"),
    ])
    func longestPicksMax(titles: [String], pages: [Int], expected: String) throws {
        var s = Shelf()
        for (t, p) in zip(titles, pages) { try s.add(Book(title: t, pages: p)) }
        #expect(try s.longest().title == expected)
    }
}

swift test builds the package and runs every test (the lines may appear in a different order from run to run, because tests execute in parallel):

◇ Test run started.
◇ Suite "Shelf" started.
✔ Test "the longest book of an empty shelf is an error" passed after 0.001 seconds.
✔ Test "longest picks the largest page count" with 2 test cases passed after 0.001 seconds.
✔ Test "page counts are positive" with 4 test cases passed after 0.001 seconds.
✔ Test "duplicate titles are rejected" passed after 0.001 seconds.
✔ Test "adding a book stores it" passed after 0.001 seconds.
✔ Suite "Shelf" passed after 0.002 seconds.
✔ Test run with 5 tests in 1 suite passed after 0.002 seconds.

A deliberately failing expectation such as #expect(shelf.books.count == 1) on an empty shelf is reported with the expansion of the expression, which is the headline feature of the #expect macro:

✘ Test deliberatelyFailing() recorded an issue at ShelfTests.swift:45:5: Expectation failed: shelf.books.count == 1
↳ shelf.books.count == 1 → false
↳   shelf.books.count → 0

What to take from this:

  • A suite is a type, each test a function. @Suite is optional but gives a display name; a test needs only @Test. Instance tests get a fresh instance of the suite per test, so the var shelf = Shelf() property is a clean shelf every time and tests cannot leak state into each other.

  • #expect records and continues; #require stops. #expect(a == b) reports a failure but lets the test carry on, so you see every problem; try #require(x) throws on failure and is the right way to unwrap an optional or check a precondition.

  • #expect(throws:) asserts an error. With a concrete error value, as here, it checks both that it throws and which error; this needs ShelfError to be Equatable.

  • Parameterised tests replace loops. arguments: runs the function once per value, and each case is reported separately; with a tuple array the cases are the rows of a table.

  • The tests are parallel by default. Shared state therefore needs care or the .serialized trait.

  • @testable import gives the test target access to internal declarations.

flowchart LR A[swift test] --> B[build package and test target] B --> C[discover tests: @Test functions] C --> D[expand parameterised arguments into test cases] D --> E[run cases in parallel, new suite instance per test] E --> F["expect failures recorded with expression expansion"] F --> G[report: pass or fail per test and for the run]

Running a Subset

swift test --filter duplicate runs only tests whose name contains duplicate (one test in this package), swift test list prints their identifiers (for example BookshelfTests.ShelfTests/addStoresBook()), and swift test --parallel or --no-parallel controls XCTest parallelism.

Pitfalls

  • Swift Testing and XCTest can live in the same target; XCTest-only features (UI tests, performance measure) stay in XCTest, and XCTAssert calls do not work inside @Test functions.

  • Do not put real network calls or the current date in unit tests; inject a clock or a stub so tests are deterministic.

  • A test that only asserts "does not crash" is weak; assert the observable outcome (#expect(throws: ShelfError.empty)).

  • Test names are free text, but keep the function name meaningful too, because it appears in failure traces.
