Macros

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A Swift macro is a piece of code that runs at compile time and expands into new Swift code — unlike C’s textual preprocessor macros, a Swift macro operates on the parsed syntax tree, is type-checked like any other code, and can be inspected (via "Expand Macro" in Xcode) as ordinary Swift source.

Freestanding and Attached Macros

#warning("remove before release")            // freestanding macro: stands in for a piece of code/expression
let value = #Predicate<Person> { $0.age > 18 }  // freestanding macro producing a value

@Observable
class Model {                                 // attached macro: attaches to a declaration, adding to it
    var count = 0
}

@Test func additionWorks() {                  // attached macro from Swift Testing
    #expect(2 + 2 == 4)                        // freestanding macro asserting a condition
}

Freestanding macros (#name) stand in for a value or a statement at the point they’re written — #warning emits a compiler warning, #expect (from Swift Testing) evaluates a condition and records a test failure with a source-accurate message if it’s false. Attached macros (@Name) are written on a declaration — a type, property, or function — and add to that declaration rather than replacing it: @Observable (see Properties) adds change-tracking machinery to a class’s stored properties, and @Test (from Swift Testing) marks a function as a test case, both without the developer writing that boilerplate by hand.

Macro Declarations and Roles

@freestanding(expression)
macro stringify<T>(_ value: T) -> (T, String) =
    #externalMacro(module: "MyMacros", type: "StringifyMacro")

@attached(member, names: named(_storage))
macro AddStorage() = #externalMacro(module: "MyMacros", type: "AddStorageMacro")

@attached(accessor)
macro Clamped(_ range: ClosedRange<Int>) = #externalMacro(module: "MyMacros", type: "ClampedMacro")

A macro’s own declaration is a macro keyword paired with a role attribute stating what kind of code it may produce and where: @freestanding(expression) (produces a value, like #stringify) or @freestanding(declaration) (produces one or more declarations); @attached(member) (adds new members to a type), @attached(accessor) (adds a getter/setter to a property), @attached(peer) (adds a sibling declaration alongside the one it’s attached to), @attached(extension) (adds a protocol conformance via an extension), and @attached(memberAttribute) (adds attributes to a type’s existing members). A macro’s names: argument declares up front which new identifiers it may introduce, so callers and tooling can see a declaration’s full shape without expanding the macro. The body after = is always #externalMacro(module:type:) — the macro’s actual implementation lives in a separate compiler-plugin module, never inline.

Macro Expansion and Hygiene

#stringify(1 + 2)     // expands to: (1 + 2, "1 + 2") -- the macro sees the unevaluated expression AND its source text

The compiler expands a macro by handing its implementation the argument as a syntax tree (not a runtime value) and receiving back another syntax tree, which the compiler then splices into the program and type-checks as if it had been written by hand. Macro hygiene guarantees this splicing can’t accidentally capture or collide with identifiers at the call site: any new local name a macro’s expansion introduces is invisible to, and cannot clash with, names already in scope where the macro is used, and vice versa — a guarantee textual preprocessor macros never provide.

Implementing a Macro

import SwiftSyntax
import SwiftSyntaxMacros

public struct StringifyMacro: ExpressionMacro {
    public static func expansion(
        of node: some FreestandingMacroExpansionSyntax,
        in context: some MacroExpansionContext
    ) throws -> ExprSyntax {
        guard let argument = node.arguments.first?.expression else {
            throw MacroError.missingArgument
        }
        return "(\(argument), \(literal: argument.description))"
    }
}

@main
struct MyMacrosPlugin: CompilerPlugin {
    let providingMacros: [Macro.Type] = [StringifyMacro.self]
}

A macro’s implementation lives in a separate Swift package target that depends on SwiftSyntax/ SwiftSyntaxMacros (from the open-source swift-syntax project) and conforms to a role-specific protocol (ExpressionMacro, MemberMacro, AccessorMacro, …​) whose expansion method receives the call site’s syntax tree and returns the expanded syntax; a CompilerPlugin conformance registers which macro types the plugin module exposes to the compiler. Package layout, expanding/debugging a macro (Xcode’s "Expand Macro" context menu, or swift package dump-macro-expansion) and testing a macro’s expansion against expected output are covered in Swift Package Manager (macro targets) and Testing (asserting on expanded output with Swift Testing).

flowchart TD A["Macro client target\ncalls @AddStorage / #stringify"] -->|depends on| B["Macro declaration target\nmacro AddStorage() = #externalMacro(...)"] B -->|references by name| C["Macro plugin target\nCompilerPlugin conforming type"] C -->|built with| D["SwiftSyntax / SwiftSyntaxMacros\nExpressionMacro / MemberMacro / ..."] E["swiftc compiling the client"] -->|loads plugin executable| C C -->|returns expanded SyntaxTree| E E --> F["Type-checked, compiled\nexpanded Swift code"]

A macro-bearing package therefore has (at least) three targets: the client code that writes @AddStorage or #stringify; a thin macro-declaration target the client depends on, holding only the macro declarations themselves; and a macro-plugin target (built as a separate executable the compiler invokes out-of-process) that does the actual syntax-tree expansion using swift-syntax.

How a Macro Expansion Happens

A macro is code that writes code, and the part that matters in practice is when it runs. The compiler does not execute macro implementations inside your program; it hands the syntax tree of the macro call to a separate compiler plugin process, receives a replacement syntax tree back and type checks that result as if you had typed it. Nothing about the expansion is visible at run time, and the expansion can be inspected in Xcode (Expand Macro) or with swiftc -dump-macro-expansions.

sequenceDiagram participant Src as Source file participant Compiler as Swift compiler participant Plugin as Macro plugin process participant Out as Type checker and codegen Src->>Compiler: parse and find each macro use Compiler->>Plugin: syntax tree of the call and its context Plugin-->>Compiler: expanded declarations or expression Compiler->>Out: type check expansion like hand written code Out-->>Src: diagnostics point back to the call site

The plugin runs in a sandbox and can only read the syntax it is given. It cannot read other files, so a macro cannot look at the rest of the module; this is deliberate, because it keeps builds incremental and reproducible. The implementation lives in a separate macro target that depends on swift-syntax, which is why the package layout described on Swift Package Manager has three targets for one macro: the declaration, the implementation and the client.

The Macros You Already Use

Several familiar # expressions are macros provided by the standard library and compiler. They need no package and make the "expression is replaced by a value" idea concrete. The example uses them as default arguments, which are evaluated at the call site, so the reported location is the caller’s and not the function’s.

// Built-in freestanding macros are expanded by the compiler before type checking finishes.
func describeCall(file: String = #fileID, line: Int = #line, function: String = #function) -> String {
    "\(file):\(line) in \(function)"
}

struct Shelf {
    func report() -> String { describeCall() }
}

print(describeCall())
print(Shelf().report())

// #if compiler(...) and #if swift(...) select code at compile time.
#if compiler(>=6.0)
let language = "Swift 6 or newer compiler"
#else
let language = "older compiler"
#endif
print(language)

// #if canImport asks whether a module exists in this build.
#if canImport(Foundation)
print("Foundation available")
#endif

// #warning and #error are diagnostics; #warning does not stop the build.
// #warning("revisit the loan limit")
let loanLimit = 5
assert(loanLimit > 0, "loan limit must be positive")
print(#line)
Bookshelf/mac1.swift:10 in Bookshelf
Bookshelf/mac1.swift:7 in report()
Swift 6 or newer compiler
Foundation available
30

Notice that Shelf().report() reports the line inside report, while the top-level call reports its own line: a default argument that is a macro is expanded where the call is written. That is the property logging and testing helpers rely on (#fileID, #line, #function; see Attributes and Compiler Control).

Roles and What They Can Produce

Every macro declares one or more roles, and the role fixes what the expansion may generate:

Role Attached or freestanding Typical output

@freestanding(expression)

freestanding

a value, as in #stringify(a + b)

@freestanding(declaration)

freestanding

new top-level or member declarations

@attached(peer)

attached

a sibling declaration, such as an async twin of a function

@attached(accessor)

attached

getters and setters for a property

@attached(member)

attached

members added inside the type

@attached(memberAttribute)

attached

attributes applied to existing members

@attached(extension)

attached

an extension, usually adding a protocol conformance

Macros are additive: they can add declarations or replace an expression, but they cannot delete or rewrite code the programmer wrote. That guarantee is why a macro-heavy codebase remains understandable.

Pitfalls

  • Macro implementations depend on swift-syntax, which is slow to compile the first time; a clean build of a project with macros takes noticeably longer until the dependency is cached.

  • A macro cannot see other declarations. It can only generate code that the compiler later checks, so an error in the expansion is reported at the call site and can be confusing.

  • Unit-test macros with the testing support in swift-syntax (assert the expansion text) rather than by running the generated code only.
