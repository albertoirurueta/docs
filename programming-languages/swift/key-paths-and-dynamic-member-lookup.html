Key Paths and Dynamic Member Lookup

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A key path is a first-class value that refers to a property without reading it — \Type.property rather than instance.property — so a property reference can itself be stored, passed around, and applied to more than one instance later. @dynamicMemberLookup builds on the same .member syntax to route arbitrary member access through custom logic instead of a compile-time-known stored property.

Key-Path Expressions

struct Person {
    var name: String
    var age: Int
}

let ada = Person(name: "Ada", age: 36)
let nameKeyPath = \Person.name          // KeyPath<Person, String> -- refers to the property, doesn't read it
ada[keyPath: nameKeyPath]                // "Ada" -- reading through the key path

A key-path expression \Type.path.to.property evaluates to a KeyPath<Root, Value> value — Root is the type the path starts from, Value the type at the end of it — and works through nested properties and optional chaining the same way ordinary dot syntax does (\Person.address?.city).

The Key Path Hierarchy

class Counter {
    var count = 0
}

let readOnlyPath: KeyPath<Person, String> = \Person.name                     // read-only
let writablePath: WritableKeyPath<Person, Int> = \Person.age                  // read-write, value type
let referenceWritablePath: ReferenceWritableKeyPath<Counter, Int> = \Counter.count // read-write through a reference

var mutableAda = ada
mutableAda[keyPath: writablePath] = 37                                         // writes through a WritableKeyPath

let counter = Counter()
counter[keyPath: referenceWritablePath] = 5    // ReferenceWritableKeyPath can write even through a `let` counter

let partial: PartialKeyPath<Person> = \Person.age    // Root known, Value erased
let anyPath: AnyKeyPath = \Person.name                // both Root and Value erased

KeyPath<Root, Value> is the read-only base; WritableKeyPath<Root, Value> adds writing through a var (or an inout value-type root); ReferenceWritableKeyPath<Root, Value> further specializes this for a reference-type root, letting the write happen even when the variable holding the reference is itself a let — mirroring the value-vs-reference distinction from Structures and Classes. PartialKeyPath<Root> erases the value type while keeping the root type known (useful for heterogeneous collections of key paths into the same root), and AnyKeyPath erases both, at the cost of needing as? casts to use the value on the other end.

Key Paths as Functions

let people = [Person(name: "Ada", age: 36), Person(name: "Grace", age: 85)]
let names = people.map(\.name)                    // KeyPath<Person, String> used directly as a (Person) -> String
let sorted = people.sorted(using: KeyPathComparator(\.age))

let fullPath = (\Person.name).appending(path: \String.count)   // KeyPath<Person, Int> -- composed key path
people.map(fullPath)                               // [2, 5] -- length of each name

The standard library overloads map, sorted(using:) and similar higher-order algorithms to accept a KeyPath<Root, Value> directly wherever a (Root) -> Value closure is expected — \.name reads exactly like the equivalent { $0.name } closure but as data rather than executable code, which is what makes it usable with KeyPathComparator and other APIs that need to inspect which property was chosen, not just call a function. appending(path:) composes two key paths end to end, producing a single key path from the first’s root to the second’s value — the key-path equivalent of chaining .a.b.

@dynamicMemberLookup

@dynamicMemberLookup
struct JSON {
    private var storage: [String: Any]

    subscript(dynamicMember member: String) -> Any? {
        storage[member]
    }
}

let json = JSON(storage: ["name": "Ada", "age": 36])
json.name    // Any? -- rewritten by the compiler to json[dynamicMember: "name"]
@dynamicMemberLookup
struct Wrapper<Value> {
    var value: Value
    subscript<T>(dynamicMember keyPath: KeyPath<Value, T>) -> T {
        value[keyPath: keyPath]
    }
}

let wrapped = Wrapper(value: ada)
wrapped.name    // rewritten to wrapped[dynamicMember: \Value.name] -- fully type-checked, no `Any` involved

@dynamicMemberLookup tells the compiler to rewrite any .member access the type doesn’t already have a stored/computed property for into a call to a subscript(dynamicMember:) it must implement. A String-keyed overload (first example) trades away compile-time member checking for maximum flexibility — useful for wrapping loosely-typed data like decoded JSON — while a KeyPath-keyed overload (second example) keeps full static type checking: the compiler still verifies \Value.name is a real, correctly-typed key path on Value, it just routes the access through the wrapper rather than exposing Value's properties directly. A type may provide both overloads simultaneously, and the compiler picks whichever one type-checks at each call site.

Worked Example: Key Paths Across a Bookshelf

The rest of this section’s running example is a small bookshelf: Book, Author, Shelf and Library types that grow a little on every page. Key paths are a good place to start because they remove a whole family of boilerplate closures. The program below stores key paths in constants, composes them, uses them as functions, writes through them and builds a reusable sorted(by:) helper.

struct Author {
    var name: String
    var born: Int
}

struct Book {
    var title: String
    var author: Author
    var pages: Int
    var rating: Double?
}

let books = [
    Book(title: "Dune", author: Author(name: "Frank Herbert", born: 1920), pages: 412, rating: 4.5),
    Book(title: "Emma", author: Author(name: "Jane Austen", born: 1775), pages: 474, rating: nil),
    Book(title: "Kim", author: Author(name: "Rudyard Kipling", born: 1865), pages: 336, rating: 3.8),
]

// 1. A key path is a value: store it, pass it, compose it.
let titlePath: KeyPath<Book, String> = \.title
let authorNamePath = \Book.author.name           // inferred WritableKeyPath<Book, String>
let authorOnly = \Book.author                     // WritableKeyPath<Book, Author>
let nameOnly = \Author.name                       // WritableKeyPath<Author, String>
let joined = authorOnly.appending(path: nameOnly) // WritableKeyPath<Book, String>

print(books[0][keyPath: titlePath])
print(books[0][keyPath: authorNamePath])
print(books[0][keyPath: joined] == books[0][keyPath: authorNamePath])
print(type(of: authorNamePath))

// 2. Key paths as functions: \Root.value can stand in for (Root) -> Value.
print(books.map(\.title))
print(books.sorted(by: { $0.pages < $1.pages }).map(\.title))
print(books.compactMap(\.rating))

// 3. Optional chaining inside a key path produces an optional value.
let ratingPath = \Book.rating                      // WritableKeyPath<Book, Double?>
let roundedPath = \Book.rating?.magnitude         // KeyPath<Book, Double?>
print(books.map { $0[keyPath: roundedPath] })

// 4. Writing: var roots give WritableKeyPath, class roots give ReferenceWritableKeyPath.
var kim = books[2]
let pagesPath: WritableKeyPath<Book, Int> = \.pages
kim[keyPath: pagesPath] += 10
print(kim.pages, books[2].pages)

// 5. A generic helper that sorts by any Comparable property.
extension Sequence {
    func sorted<Value: Comparable>(by path: KeyPath<Element, Value>) -> [Element] {
        sorted { $0[keyPath: path] < $1[keyPath: path] }
    }
}
print(books.sorted(by: \.author.born).map(\.title))
print(ratingPath == \Book.rating)

Some points are worth drawing out of that output.

  • A key path is a value, not an access. \Book.author.name does not read anything; it records the route Book -> author -> name and its static type, KeyPath<Book, String>. The route is resolved when you apply it with the [keyPath:] subscript, so the same path can be applied to a thousand books.

  • The runtime type is the most capable one. Because every component of authorNamePath is a var, the compiler infers WritableKeyPath<Book, String>, which type(of:) reports; it picks the most capable class it can prove, and annotating the constant as KeyPath<Book, String> would restrict it to reading.

  • Composition is type-checked. appending(path:) only compiles when the value type of the first path equals the root type of the second. The result of joined is equal to the directly written \Book.author.name, which is why the comparison prints true.

  • Key paths are functions. An expression \Root.value can be used wherever a (Root) -> Value closure is expected, so books.map(\.title) replaces books.map { $0.title }. The compiler infers the root from context, which is why the leading type can be omitted.

  • Optional chaining stays optional. A path containing ? always ends in an optional value, even when the final property is not optional (\Book.rating?.magnitude has the value type Double?).

  • The writability of the path follows the root. Paths rooted in a var struct give a WritableKeyPath; the copy kim is mutated while books[2] keeps its 336 pages, because a struct is copied on assignment (see Structures and Classes).

The class hierarchy of key-path types is a chain of progressively more capable types. Each arrow below means "is a subclass of":

classDiagram direction LR AnyKeyPath <|-- PartialKeyPath PartialKeyPath <|-- KeyPath KeyPath <|-- WritableKeyPath WritableKeyPath <|-- ReferenceWritableKeyPath class AnyKeyPath { root and value types erased } class PartialKeyPath { Root known, Value erased } class KeyPath { Root and Value known, read only } class WritableKeyPath { can mutate a var root } class ReferenceWritableKeyPath { can mutate through a let class reference }

Erasing Types with PartialKeyPath

Erasing the value type is what lets a heterogeneous list of properties live in one array, for example the columns of a generic report or a table of property labels. The price is that reading a value gives back Any.

struct Book {
    var title: String
    var pages: Int
}

// A type-erased list of "columns" for a report: PartialKeyPath forgets Value, keeps Root.
let columns: [PartialKeyPath<Book>] = [\Book.title, \Book.pages]
let dune = Book(title: "Dune", pages: 412)
for column in columns {
    // The value comes back as Any, so a cast is needed to use it.
    let value = dune[keyPath: column]
    print(value, type(of: value))
}

// Class roots: a ReferenceWritableKeyPath writes through a let constant.
final class Counter { var loans = 0 }
let counter = Counter()
let loansPath: ReferenceWritableKeyPath<Counter, Int> = \.loans
counter[keyPath: loansPath] += 3
print(counter.loans)

// Key paths are Hashable, so they can be dictionary keys: a tiny cache per property.
var labels: [PartialKeyPath<Book>: String] = [:]
labels[\Book.title] = "Title"
labels[\Book.pages] = "Pages"
print(labels[\Book.title] ?? "?", labels[\Book.pages] ?? "?")
Dune String
412 Int
3
Title Pages

Two details are easy to miss. First, a ReferenceWritableKeyPath can write through a let constant, because the constant holds a reference and the object it points to is mutable, exactly as with counter.loans += 3. Second, key paths conform to Hashable, so they can be dictionary keys; that is the basis of several SwiftUI and Observation style APIs.

Pitfalls

  • A key path cannot capture a method call or a function. Only properties, subscripts, optional chaining and forced unwrapping can appear in the path.

  • A key path to a computed property is read-only unless the property has a setter; a let property can never be written through a path.

  • Applying a key path is slightly slower than a direct property access, because the path is interpreted by the runtime. In hot loops, prefer a direct closure.

  • Under Swift 6 strict concurrency, a key path used across isolation domains must be Sendable. Key-path literals whose components are all Sendable are inferred to be Sendable automatically.
