Swift IDEs & Tools

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page lists the IDEs and editors commonly used to write and debug Swift code. Use Xcode for Apple-platform apps, and an editor with the Swift extension for cross-platform packages and server-side work.

IDEs

  • Xcode — Apple’s IDE, bundling a Swift toolchain, SwiftUI and UIKit previews, the debugger, Instruments and the simulators.

Editors with extensions

  • VS Code Swift extension — completion, diagnostics and debugging for Swift packages in Visual Studio Code, built on SourceKit-LSP.

Discontinued products

  • AppCode — the JetBrains IDE for Swift and Objective-C is discontinued; Xcode is the recommended environment.

What Ships With a Toolchain

An IDE is a front end; the toolchain underneath does the work, and the same toolchain is behind every editor. A toolchain installed with Xcode (or with Swiftly, or the packages from swift.org) provides the compiler, the package manager, the language server, the debugger, the formatter and the documentation compiler:

$ swift --version
Apple Swift version 6.4.2 (swiftlang-6.4.2.1.9 clang-2100.4.1.1)
Target: arm64-apple-macosx27.2.0
$ xcrun --find sourcekit-lsp
.../XcodeDefault.xctoolchain/usr/bin/sourcekit-lsp
$ xcrun --find swift-format
.../XcodeDefault.xctoolchain/usr/bin/swift-format
$ xcrun --find docc
.../XcodeDefault.xctoolchain/usr/bin/docc

(The version printed is that of the machine the page was checked on; the Swift 6 language mode is available from Swift 6.0 onwards.) xcrun is the macOS way to locate a tool in the active developer directory; on Linux and Windows the same binaries are in the toolchain’s bin directory and on PATH.

flowchart TB subgraph tc [Swift toolchain] SW[swift and swiftc: build and run] SPM[swift package: dependencies and builds] LSP[sourcekit-lsp: completion, diagnostics, navigation] LLDB[lldb: debugger] FMT[swift-format: formatter and linter] DOCC[docc: documentation compiler] end XC[Xcode] --> SW XC --> LLDB XC --> DOCC VSC[VS Code Swift extension] --> LSP VSC --> LLDB VSC --> SPM ED[Any editor with an LSP client] --> LSP CI[CI and the command line] --> SW CI --> SPM CI --> FMT

Choosing an Environment

You are building Reasonable choice Why

an iOS, macOS, watchOS or visionOS app

Xcode

simulators, Interface Builder previews, Instruments, signing and the App Store workflow only exist there

a cross-platform library or a command-line tool

VS Code with the Swift extension, or any editor with an LSP client

works on macOS, Linux and Windows, built on the same SourceKit-LSP that Xcode uses

server-side Swift

VS Code or Xcode, plus containers for Linux builds

the production target is Linux, so build and test there too

scripts and experiments

swift file.swift and the REPL

no project needed

Whatever the editor, the project is a Swift package, so the build, the tests and CI commands are the same for everyone on the team: swift build, swift test, swift format lint --recursive Sources Tests. See Swift Package Manager and Build and Tooling for the details.

Pitfalls

  • Two toolchains on one machine (the Xcode one and one from swift.org or Swiftly) can make swift --version in the terminal differ from the version Xcode builds with; check which is active before diagnosing a "works in Xcode" mismatch.

  • SourceKit-LSP indexes a package after its first build; a package that has never built shows weak completion and navigation.

  • Keep formatter and linter versions pinned (in a CI image or a lock file) so that formatting does not change between machines.
