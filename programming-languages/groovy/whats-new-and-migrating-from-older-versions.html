What’s New & Migrating from Older Versions

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page collects in one place what changed between Groovy releases and how to move code forward. The baseline is Groovy 6.0.0 (released 2026-09-22, JDK 17 or newer); every example on the page was run with Groovy 6.0.0 on JDK 26 on 2026-10-14. Version numbers, dates and maintained lines were checked on that day against the official change log and the release notes. Features introduced after Groovy 4.0 name their release, and a feature described as incubating may still change in a minor release. Each change is explained in depth on the guide page linked from it.

The page has four parts: the release-by-release table and timeline, the legacy-to-modern table, the breaking changes with migration steps and a checklist.

Release by release: 1.0 to 6.0

Groovy follows semantic versioning. Two release numbers never shipped under their original name: 1.1 was renamed 1.5 and 1.9 was renamed 2.0. A 2.6 line was planned as a JDK 7 back-port of the 3.0 parser but was retired after four alpha releases (the last on 2018-06-23), so it is not in the table. A 7.0 release-notes page exists but is marked as under development with no release on the change log; nothing on this page depends on it.

Older books, blog posts and Stack Overflow answers describe Groovy 1.x and 2.x. Most of what they teach still works, but several statements are now wrong and many idioms have a better replacement. Writing the same code in the old and the new style

The script below uses only forms that Groovy 1.0 did not have or that arrived with the Parrot parser and later. It runs unchanged on Groovy 6.0.0:

// Forms that Groovy 1.0 lacked or that only arrived with the Parrot parser (3.0) and later.
import java.util.function.Function

// classic for loop (1.5), do/while (3.0), Java-style array initializer (3.0)
int[] sizes = [3, 5, 8] as int[]
int[] more = new int[]{4, 6}
def total = 0
for (int i = 0; i < sizes.length; i++) { total += sizes[i] }
int n = 3
do { n-- } while (n > 0)

// lambdas and method references (3.0)
Function<String, Integer> len = s -> s.length()
def upper = 'tomato'.&toUpperCase

// negated operators, identity, Elvis assignment, safe indexing (3.0)
def seed = null
seed ?= 'basil'
List<String> none = null

// try-with-resources (3.0)
String first
try (def r = new StringReader('line1\nline2')) { first = new BufferedReader(r).readLine() }

// 5.0: loop with an index variable
def idx = []
for (int i, var item in ["a", "b", "c"]) { idx << "$i$item" }

// 6.0: val
val final1 = 42

assert total == 16 && more.length == 2 && n == 0
assert len('lettuce') == 7 && upper() == 'TOMATO'
assert 'x' !in ['a', 'b'] && !('x' instanceof Integer)
assert seed == 'basil' && none?[0] == null
assert first == 'line1'
assert idx == ['0a', '1b', '2c']
assert (false ==> true) && !(true ==> false)
assert final1 == 42
println 'modern syntax ok'

Output of the real run:

modern syntax ok

Breaking changes and how to migrate

Groovy keeps minor releases compatible; the breaking changes cluster in the major releases and are listed in the "Breaking changes" section of each release-notes page. The tables below cover the ones that affect typical projects.

Moving to Groovy 3.0

Groovy 3.0 introduced the Parrot parser (enabled by default; the old parser could still be selected by a system property) and, to prepare for the Java module system, duplicated many classes into JPMS-friendly packages. Nothing had to change yet, but this is the release in which you should start moving to the new package names, because 4.0 removes the old ones.

Moving to Groovy 4.0

Change What to do Where

Maven coordinates: the groupId changed from org.codehaus.groovy to org.apache.groovy

Update Gradle, Maven and Ant build files (the Gradle and Maven snippets are below)

Build Tools

Legacy packages removed: the duplicated classes in the old packages are gone

Replace groovy.util.XmlSlurper with groovy.xml.XmlSlurper, groovy.util.XmlParser with groovy.xml.XmlParser, groovy.util.AntBuilder with groovy.ant.AntBuilder, groovy.util.GroovyTestCase with groovy.test.GroovyTestCase, and so on for the classes listed in the 3.0 notes

XML Parsing, GPath & Security

Old parser removed: the Antlr 2 based parser no longer exists

Fix any source that only compiled with the old parser; if you cannot, stay on 3.0

Lexical Structure

invokedynamic is on by default: one set of jars, no -indy variants

Remove the indy classifier; set groovy.target.indy=false only if you must disable it

Performance, invokedynamic & Native Images

groovy-all contents: groovy-yaml is now included, groovy-testng is not

Add groovy-testng explicitly if you use it

Build Tools

Modules removed: groovy-jaxb (JAXB left the JDK) and groovy-bsf (BSF 2 reached end of life)

Use the Groovy 3 version of those modules or switch libraries

Integrating Groovy into Java Applications

intersect with a projection now draws elements from the receiver, as in other languages

Re-check calls of intersect that pass a closure or comparator

Working with Collections

A build file moves like this (build snippets, not run here; the coordinates were checked against Maven Central):

// Gradle: Groovy 3 and earlier

Moving to Groovy 5.0

The runtime minimum rises to JDK 11. The notable breaking changes:

Change What to do Where

Duplicate imports are errors: two imports of the same simple name, or an import and a class with that name, used to let the last one win

Remove or alias the duplicates

Program Structure, Packages, Imports & Scripts

java.time is a default import, so classes such as Year, Month and Duration in the default package now conflict

Rename them, move them into a package or alias the import

Dates & Times

File and Path truthiness: a path that does not exist is falsy

Test file != null for "is it set"; -Dgroovy.truth.file.exists.enabled=false restores the old behaviour while you port (from 5.0.7)

Booleans & the Groovy Truth

% calls remainder instead of mod

Rename an overload named mod; the fallback keeps old classes working

Operator Overloading

Scripts with only a static main no longer extend Script (JEP 512 compatibility)

Turn them into plain scripts or use an instance run method

Running Scripts & the groovy Command

Visibility and property access tightened for package-private members, anonymous classes and map-like classes; abstract/final on an enum is an error; some AST annotations have SOURCE retention

Compile and fix; framework authors should re-test AST transform annotations

Classes, Fields & Properties

Iterator extension methods such as findIndexValues and chop now return iterators; chop stops when the collection is used up

Add .toList() where you need a list

Working with Collections

Moving to Groovy 5.1

Groovy 5.1 keeps the 5.0 JDK requirements. Its breaking changes are small and security-motivated:

  • deleteDir() on File and Path treats symbolic links as leaves instead of following them into their targets. If you relied on deleting the contents of a linked directory, resolve the link and delete the target yourself.

  • Grape coordinates containing .. sequences are rejected.

  • The deprecated run(JApplet) method was removed from the Groovy Console so that it loads on JDK 26 and later.

Source: Groovy documentation: Groovy 5.1 release notes

Moving to Groovy 6.0

The runtime minimum rises to JDK 17 (Groovy 6.0 was tested on JDK 17 to 27). The headline breaking changes:

Change What to do Where

Security Manager support removed: Groovy no longer calls AccessController.doPrivileged or uses the related infrastructure (the Security Manager itself is deprecated for removal in the JDK)

Stop relying on policy files; restrict scripts with SecureASTCustomizer and isolate with containers and the operating system

Compilation Customizers & Secure Scripting

The launchers no longer add . to a classpath you supply

Add . yourself (-cp lib.jar:., or -cp lib.jar;. on Windows)

Running Scripts & the groovy Command

Switch: position decides: a switch whose value is used is an expression (an unmatched selector throws IllegalStateException, a missing default is an error under static checking); a switch whose value is unused is a statement

Add a default arm to expression switches; statement switches behave as in 4.x and 5.x

Control Structures

Generic types must be well formed: generic array creation, a generic class extending Throwable, wildcards in instance creation, primitive type arguments, new T() and similar constructs that older versions silently erased are compile errors

Use the workaround shown in the Generics section of the release notes (for example Array.newInstance or a raw array)

Inheritance, Interfaces & Generics

val is a keyword (contextual) for final locals

Rename a field or variable named val in the ambiguous positions, or set -Dgroovy.val.enabled=false while porting

Variables, Typing, def, var & val

key in map tests the key

Use map.containsValue(v) or v in map.values() to test values

Maps

A for-in loop variable captured by a closure or lambda has a fresh binding per iteration

Nothing, unless your code relied on the final value; -Dgroovy.forin.per.iteration.capture=false restores the old behaviour

Closures

The classic call-site runtime moved to the optional groovy-callsite module

Add the module only if you run with invokedynamic disabled

Performance, invokedynamic & Native Images

XML is secure by default; GroovyServlet hides error details; groovy-sql rejects GString queries with a quoted dynamic expression; JsonSlurper rejects numbers longer than 1000 characters

Use the documented opt-out properties only as porting aids

XML Parsing, GPath & Security

String-to-Class coercion no longer initialises the class

Call Class.forName(name) where the static initialiser matters

Databases with Groovy SQL

Method-level @TypeChecked/@CompileStatic now overrides a class-level SKIP

Remove the method annotation or give it SKIP mode

Static Type Checking & @CompileStatic

The classpath dot

A script that loads a class from the working directory while you also pass -cp for a library used to work because the launcher appended the current directory. With 6.0 the classpath you pass is used as is. The demonstration compiles a class Watering into the current directory and runs use.groovy, which calls it, three ways:

groovyc Watering.groovy
groovy use.groovy                        # no classpath given: falls back to the current directory
groovy -cp /nonexistent-dir use.groovy   # explicit classpath: the current directory is not added
groovy -cp "/nonexistent-dir:." use.groovy
water at dawn

Replacing the Security Manager

Setting a Security Manager is not possible on current JDKs, and Groovy 6 no longer cooperates with one. On JDK 26 the call fails immediately:

println System.getSecurityManager()
try { System.setSecurityManager(null) } catch (e) { println e.class.name }
null
java.lang.UnsupportedOperationException

For scripts that you do not fully trust, restrict what they may compile with a SecureASTCustomizer (and still run them in a container or an unprivileged operating-system account, because a compile-time allow-list is not a full sandbox):

import org.codehaus.groovy.control.CompilerConfiguration
import org.codehaus.groovy.control.customizers.SecureASTCustomizer
import org.codehaus.groovy.control.MultipleCompilationErrorsException

def secure = new SecureASTCustomizer()
secure.with {
    // allow-list of receiver types for method calls: System.exit(...) is not on it
    allowedReceiversClasses = [Object, Integer, String, Math]
}
def config = new CompilerConfiguration()
config.addCompilationCustomizers(secure)
def shell = new GroovyShell(config)

println shell.evaluate('Math.max(2, 7)')
try {
    shell.evaluate('System.exit(1)')
} catch (MultipleCompilationErrorsException e) {
    println 'rejected at compile time: ' + e.errorCollector.getError(0).cause.message.readLines().first()
}
7
rejected at compile time: Method calls not allowed on [java.lang.System]

The switch position rule

Whether a switch is a statement or an expression no longer depends on the arrow: it depends on whether the value is used. A switch that ends a method is a statement whose matched value is returned by the implicit return (and is null when nothing matches, as in 4.x and 5.x); a switch on the right of an assignment is an expression and must be exhaustive:

def label(int i) {
    switch (i) {
        case 1 -> 'one'
        case 2 -> 'two'
    }
}
println label(1)
println label(9)
def viaExpr = { int i -> def r = switch (i) { case 1 -> 'one'; default -> 'many' }; r }
println viaExpr(7)
try {
    def s = 9
    def r = switch (s) { case 1 -> 'one' }
} catch (IllegalStateException e) { println "expression with no match: ${e.class.simpleName}" }
one
null
many
expression with no match: IllegalStateException

Generic syntax

Groovy 4 and 5 accepted generic constructs that Java rejects by quietly treating them as raw types. Groovy 6 applies the Java rules in every compilation unit, scripts included. The real error for generic array creation:

List<String>[] buckets = new List<String>[3]
generics.groovy: 1: generic array creation of List<java.lang.String>
 @ line 1, column 26.
   List<String>[] buckets = new List<String>[3]
                            ^

Use a List<List<String>> or a raw array with a cast instead. Source: Groovy documentation: Generic type syntax

Two behaviours that change silently

Two 6.0 changes compile and run without any message, so they deserve a test in your suite. The first is the in operator on a map, which now tests keys; the second is the for-in capture rule:

def stock = [basil: 0, mint: 3]
println('basil' in stock)      // key-based since 6.0
println(0 in stock)            // values are no longer tested
println(0 in stock.values())
true
false
true
def tasks = []
for (crop in ['basil', 'mint', 'sage']) { tasks << { crop } }
println tasks*.call()
[basil, mint, sage]

With -Dgroovy.forin.per.iteration.capture=false the same script prints [sage, sage, sage], which is what earlier releases did (every closure shared one binding).

Upgrade checklist

  1. Pick the target line. Use the maintained-lines table above; a project on JDK 8 can stay on 4.0, JDK 11 on 5.x, JDK 17 or later can take 6.0.

  2. Upgrade one major at a time if you are far behind (3.0, then 4.0, then 5.0, then 6.0): each release-notes page lists the breaking changes for that step only.

  3. Fix coordinates and imports first. Switch org.codehaus.groovy to org.apache.groovy, move legacy packages to their groovy.xml, groovy.ant, groovy.test and similar homes, and add any optional module that groovy-all no longer includes.

  4. Build and run the tests on the new line. Read compile errors against the tables above; run with the documented porting flags only to separate behavioural changes from syntax changes, and remove them afterwards.

  5. Check the toolchain. Gradle, Maven plugins, IDEs, Jenkins and JMeter embed their own Groovy line; see Build Tools: Gradle, Maven & Ant.

  6. Re-check tests and frameworks. Spock publishes one artifact per Groovy line (for example 2.5-groovy-6.0), see Testing with Spock & Geb.

  7. Adopt new features gradually. var, val, switch expressions, records and @CompileStatic are low risk; treat async/await and other incubating features as subject to change.

For the Java side of the same questions (language levels, the module system and build tooling) see Java: Build & Tooling and Java: Packages & Modules.
