Error Handling and Declaratives

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against ISO/IEC 1989:2023 (edition 3, January 2023; an upcoming 4th edition is in ballot), where the conditional phrases and declaratives come from COBOL 85 and the exception conditions (EC-*) with RAISE, RESUME and the >>TURN directive were added by COBOL 2002; against IBM Enterprise COBOL for z/OS 6.5 (PTFs through September 2026) on z/OS 3.2; and against GnuCOBOL 3.2 (28 July 2023, the latest release), with which every program on it was compiled and run on 2026-10-20 with cobc -x -Wall (and again with -std=ibm, which printed the same output unless the text says otherwise). The programs that are deliberately wrong say so, and the messages shown are the ones cobc (GnuCOBOL) 3.2.0 and its run-time library printed. The programs that stop with a run-time error end with exit status 1; the exit status is quoted where it matters.

Error handling in COBOL is spread over four mechanisms that are easy to confuse. The conditional phrases (ON SIZE ERROR, AT END, INVALID KEY, and so on) are part of a single statement. The FILE STATUS clause leaves a two-character code after every file operation. Declaratives are sections that the run time performs when a file operation fails. Exception conditions are the standard’s named, checkable conditions (EC-SIZE-OVERFLOW, EC-BOUND-SUBSCRIPT and many more), which Enterprise COBOL does not implement as such but GnuCOBOL does, in part. A program ends by handing a condition code to the operating system through RETURN-CODE. The page covers them in that order and ends with what happens on z/OS when none of them catches the problem. The code examples use the Circulation public-library scenario: the member master MEMBMAST, the book master BOOKMAST and the loan transactions LOANTRAN. The mechanics of the file statements are on File Concepts: SELECT and FD and Sequential Files, and the complete list of status codes is on File Status Codes.

Where the book is outdated: Taulli’s Modern Mainframe Development (2022, chapter 5) introduces FILE STATUS as the way to learn whether a file operation worked, and that idea is still current. Two of its details are wrong and the correct rules are these: the status item is a separate two-character item in WORKING-STORAGE, not a field declared inside the record group (which would make it part of the data read from the file), and a file is opened with OPEN INPUT, not "OPEN READ". The book does not cover declaratives or the exception conditions at all, so everything from the declaratives section onward comes from the official documentation.

How an error travels through a COBOL program

When a file statement raises a condition, the standard and Enterprise COBOL take their actions in a fixed order, and GnuCOBOL 3.2 behaves the same way in every case tried here. The statement first stores the code in the FILE STATUS item, if the file has one. Then, if the condition is an AT END or INVALID KEY condition and the statement has the matching phrase, the phrase runs and the declarative is not executed. Otherwise an applicable USE AFTER ERROR declarative runs. If neither exists the outcome depends on the kind of error: a status-only error continues with the next statement when a FILE STATUS clause exists, and ends the run unit with a run-time error when none does.

flowchart TD A["READ, WRITE, OPEN or another file statement"] --> B{"Condition raised?"} B -- "No" --> C["NOT AT END or NOT INVALID KEY phrase runs, if coded"] B -- "Yes" --> D["FILE STATUS item is set, if the file has one"] D --> E{"AT END or INVALID KEY condition with its phrase coded?"} E -- "Yes" --> F["The phrase runs and the declarative is skipped"] E -- "No" --> G{"A USE AFTER ERROR declarative applies?"} G -- "Yes" --> H["The declarative runs, then control returns after the statement"] G -- "No" --> I{"FILE STATUS coded?"} I -- "Yes" --> J["Execution continues and the program must test the status"] I -- "No" --> K["Run-time error: libcob message and exit 1 in GnuCOBOL, Language Environment condition on z/OS"]

Conditional phrases

A conditional statement is a statement that carries a phrase which depends on a condition that the statement itself detects. Every phrase comes in a pair: the positive one runs when the condition occurs, and the NOT form runs when the statement completes without it. Both contain imperative statements, and both are optional.

Phrase pair Statements Condition detected Notes

ON SIZE ERROR / NOT ON SIZE ERROR

ADD, SUBTRACT, MULTIPLY, DIVIDE, COMPUTE

The result does not fit the receiving item, or the divisor is zero; also the invalid exponentiations of the next section

On a size error the receiving item keeps its old value; ROUNDED is applied before the check

ON OVERFLOW / NOT ON OVERFLOW

STRING, UNSTRING, and CALL (a synonym there for ON EXCEPTION)

The pointer or the receiving item is too small for the operation

The operation stops at once; with STRING the part already moved stays in the receiving item

ON EXCEPTION / NOT ON EXCEPTION

CALL, INVOKE, JSON and XML statements (Enterprise COBOL); ACCEPT and DISPLAY too in the standard and GnuCOBOL

The called program cannot be loaded, the system cannot supply the input, and so on

For CALL it covers only the first load of the program

AT END / NOT AT END

READ (sequential access), RETURN, SEARCH

No next record, no next sorted record, or no match in the table

On a file it corresponds to status 10

INVALID KEY / NOT INVALID KEY

READ, WRITE, REWRITE, DELETE, START on indexed and relative files

The key is missing, duplicated or out of sequence

Not allowed on sequential files; status class 2

AT END-OF-PAGE / NOT AT END-OF-PAGE

WRITE ... ADVANCING on a file with LINAGE

The logical page is full

Used by report programs

Source: Enterprise COBOL for z/OS 6.5 Language Reference: Conditional statements; SIZE ERROR phrases; GnuCOBOL Programmer’s Guide: ON SIZE ERROR + NOT ON SIZE ERROR

A statement with one of these phrases is conditional and must be closed with its explicit scope terminator (END-ADD, END-READ, END-CALL, and so on) whenever it sits inside another statement, such as an IF branch. Without the terminator the next phrase or the period decides where the statement ends, which silently moves the following statements into the phrase. The scope terminators and the period rules are on Conditions: IF and EVALUATE. If a phrase’s imperative statement transfers control explicitly (a PERFORM of a paragraph that ends the program, for example), the rest of the statement is not executed.

Arithmetic: ON SIZE ERROR

A size error happens when the absolute value of the result, after decimal alignment, is larger than the receiving item can hold, or when a division by zero occurs. IBM adds three exponentiation cases: zero raised to the zero power (with the phrase the SIZE ERROR imperative runs; without it the value 1 is returned and a message is issued), zero raised to a negative number, and a negative number raised to a fractional power. The check applies only to final results, never to intermediate ones.

With the phrase coded and a size error present, the receiving item is not altered, the imperative statement runs, and the NOT ON SIZE ERROR branch is skipped. Without the phrase, the standard truncation rules apply, so the result is silently cut on the left, and a division by zero has no defined result. On z/OS, the fixed-point overflow and decimal overflow cases only reach the phrase when the TRAP(ON) run-time option is in effect, and a floating-point exponent overflow never causes a size error: an abend occurs instead.

The first program shows the phrases of MULTIPLY, DIVIDE, ADD, STRING and CALL in one place. The fine of 20000 days at 5.25 does not fit S9(5)V99, a divide by zero is a size error too, and the ADD without a phrase wraps around silently, which is the case to be afraid of.

What an unprotected division by zero does is a difference between the compilers. This program is deliberately unprotected: it divides by a zero member count with neither ON SIZE ERROR nor any checking.

       IDENTIFICATION DIVISION.
       PROGRAM-ID. DIV0.
      * Deliberately unprotected: division by zero without SIZE ERROR.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-FINES            PIC 9(5)V99 VALUE 62.50.
       01  WS-MEMBERS          PIC 9(3)    VALUE ZERO.
       01  WS-AVERAGE          PIC 9(5)V99 VALUE 777.
       PROCEDURE DIVISION.
           DIVIDE WS-FINES BY WS-MEMBERS GIVING WS-AVERAGE
           DISPLAY "average " WS-AVERAGE
           COMPUTE WS-AVERAGE = WS-FINES / WS-MEMBERS
           DISPLAY "average " WS-AVERAGE
           STOP RUN.
average 00777.00
average 00777.00

GnuCOBOL 3.2.0 carries on, leaves the result field alone and prints nothing (its manual says the run time prints an error message and aborts; the 3.2.0 binary used here did not, with or without -debug). Under -std=ibm the same program shows the value without a decimal point (0077700), because that dialect displays implied-decimal items as raw digits. On z/OS the same statement with a binary result is a fixed-point divide exception, which Language Environment reports as message CEE3209S with system completion code 0C9 and an abend, as the Programming Guide’s debugging chapter shows for a COMPUTE of a binary item by itself. This is z/OS only and was not run here. The portable rule is therefore to protect every division whose divisor can be zero, either with ON SIZE ERROR or with an explicit test before it.

Source: GnuCOBOL Programmer’s Guide: ON SIZE ERROR + NOT ON SIZE ERROR; Enterprise COBOL for z/OS 6.5 Programming Guide: Debugging an AMODE 64 program (the CEE3209S example)

STRING and UNSTRING: ON OVERFLOW

When the pointer of a STRING or UNSTRING falls outside the receiving field, COBOL does not let the overflow happen: the operation is not completed, the receiving field stays unchanged in the pointer case, and control passes to the next statement. If the program does not code ON OVERFLOW, nothing tells it that the operation was incomplete, which is the usual way truncated report lines are produced. Code the phrase on every STRING and UNSTRING whose result length is not obviously safe, and see Strings: STRING, UNSTRING and INSPECT for the statements themselves.

Source: Enterprise COBOL for z/OS 6.5 Programming Guide: Handling errors in joining and splitting strings

CALL: ON EXCEPTION and ON OVERFLOW

A dynamic CALL of a program that cannot be loaded (not found, or the system is out of storage) triggers ON EXCEPTION; without the phrase the application can abend on z/OS and stops with a run-time error in GnuCOBOL. The phrase applies only to the availability of the called program on its first load: if the program is loaded and then fails for another reason, such as its own initialization, the phrase does not run. ON OVERFLOW is a synonym of ON EXCEPTION on CALL. The usual pattern is to fall back to another program, as in the Programming Guide’s REPORTA/REPORTB fragment; subprogram calls are covered on Subprograms: CALL and LINKAGE.

This program is deliberately unprotected. It calls a program that does not exist, with no phrase:

       IDENTIFICATION DIVISION.
       PROGRAM-ID. NOCALL.
      * Deliberately unprotected CALL of a missing program.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-ID               PIC 9(6) VALUE 101.
       PROCEDURE DIVISION.
           CALL "NOSUCHPG" USING WS-ID
           DISPLAY "not reached"
           STOP RUN.
libcob: error: module 'NOSUCHPG' not found

The run-time library printed one line and the process ended with exit status 1; the DISPLAY after the CALL never ran.

Source: Enterprise COBOL for z/OS 6.5 Programming Guide: Handling errors when calling programs

One GnuCOBOL 3.2.0 behaviour needs care when both phrases are coded. The code that cobc generates tests the NOT ON EXCEPTION branch after the ON EXCEPTION branch has run, and a DISPLAY inside the first branch clears the exception that the second branch tests, so the NOT ON EXCEPTION statements ran as well. The arithmetic phrases are not affected (the same check on ADD ... ON SIZE ERROR ... NOT ON SIZE ERROR ran only the right branch). The portable form records the outcome in a flag and decides afterwards:

       IDENTIFICATION DIVISION.
       PROGRAM-ID. CALLQUIRK.
      * NOT ON EXCEPTION after a DISPLAY inside ON EXCEPTION (GnuCOBOL).
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-MEMBER-ID        PIC 9(6) VALUE 101.
       01  WS-LOADED           PIC X VALUE "Y".
           88  PROGRAM-LOADED  VALUE "Y".
           88  PROGRAM-MISSING VALUE "N".
       PROCEDURE DIVISION.
       MAIN-PARA.
           CALL "NOSUCHPG" USING WS-MEMBER-ID
               ON EXCEPTION
                   DISPLAY "ON EXCEPTION ran"
               NOT ON EXCEPTION
                   DISPLAY "NOT ON EXCEPTION ran"
           END-CALL
      *    Portable form: record the outcome, decide afterwards.
           SET PROGRAM-LOADED TO TRUE
           CALL "NOSUCHPG" USING WS-MEMBER-ID
               ON EXCEPTION
                   SET PROGRAM-MISSING TO TRUE
           END-CALL
           IF PROGRAM-MISSING
               DISPLAY "NOSUCHPG is not available"
           ELSE
               DISPLAY "NOSUCHPG ran"
           END-IF
           STOP RUN.
ON EXCEPTION ran
NOT ON EXCEPTION ran
NOSUCHPG is not available

The standard and the Enterprise COBOL documentation describe only one of the two branches running; the second CALL above does what such a program is expected to do, and the first shows the 3.2.0 deviation. The run is the same under -std=ibm.

Source: Enterprise COBOL for z/OS 6.5 Programming Guide: Handling errors when calling programs; Language Reference: CALL statement; GnuCOBOL Programmer’s Guide: ON EXCEPTION + NOT ON EXCEPTION

Files: AT END and INVALID KEY

AT END belongs to sequential reads: it runs when status 10 is set because no next record exists, and the NOT AT END branch runs only when the read succeeded. A read that fails for any other reason runs neither branch; control passes to the end of the statement after any declarative has run. INVALID KEY belongs to the keyed statements on indexed and relative files, and the NOT INVALID KEY branch runs when the key condition does not exist. The next program builds an indexed copy of BOOKMAST, reads the day’s LOANTRAN with AT END, and looks each book up with INVALID KEY. The file status items sit in WORKING-STORAGE, outside the record, as the errata above say.

       IDENTIFICATION DIVISION.
       PROGRAM-ID. FILES1.

               ORGANIZATION IS LINE SEQUENTIAL

       IDENTIFICATION DIVISION.
       PROGRAM-ID. WRONG2.
      * Deliberately wrong: AT END on a random read of an indexed file.

       INPUT-OUTPUT SECTION.

The run-time library reported status 23 as a fatal error and closed the files itself ("implicit CLOSE"), so after the READ was never displayed. An invalid key condition needs an INVALID KEY phrase, a declarative or at least a FILE STATUS clause to be survivable.

FILE STATUS in brief

After every file statement the two-character FILE STATUS item holds a code whose first digit gives the class: 0 successful, 1 at end, 2 invalid key, 3 permanent error, 4 logic error, and on z/OS 9 for IBM-defined conditions. The code is stored before any declarative, INVALID KEY phrase or AT END phrase runs, and it is not reset by the program: every statement sets it again. The rules that apply to every program are to give each file its own status item and to test it after each statement, or to rely on a declarative that does.

Declaratives

A declarative is a section that the run time performs when an exceptional condition occurs, so that file errors are handled in one place and not after every statement. It is the oldest of COBOL’s handler mechanisms and still the only one that works in both Enterprise COBOL and GnuCOBOL.

Structure of the DECLARATIVES region

Declaratives sit at the very beginning of the PROCEDURE DIVISION, and as soon as there are any, the whole PROCEDURE DIVISION must be divided into sections. The rules from the Language Reference are:

  • The word DECLARATIVES is written on the line after the PROCEDURE DIVISION header, and END DECLARATIVES closes the group. Each must begin in Area A, be followed by a separator period, and be alone on its line.

  • Each declarative is a section whose header is followed by a period, and whose first sentence is a USE statement ending in a period. The USE statement is never executed; it only tells the run time when to perform the paragraphs that follow it.

  • Declarative sections take priority numbers from 0 through 49 if segmentation is used, which is rare.

  • A declarative procedure can be performed from an ordinary procedure and the reverse, and GO TO between them is allowed, but a declarative that runs a procedure that is already in control can loop forever.

  • Execution of the program starts at the first statement after END DECLARATIVES; declaratives never run by falling into them. Control returns to the I/O system when the last statement of the declarative has run, and the statement that failed then completes.

The full format of the statement is USE [GLOBAL] AFTER STANDARD {EXCEPTION | ERROR} PROCEDURE ON {file-name ... | INPUT | OUTPUT | I-O | EXTEND}. EXCEPTION and ERROR are synonyms, and GLOBAL makes the declarative available to the programs nested inside. With a file name, only that file’s errors are handled; with a mode, every file opened in that mode, or being opened in it, is handled. A file-specific declarative takes precedence over a mode declarative, and only one declarative may apply to a given file. GnuCOBOL’s manual adds that the words AFTER, FOR, ON, PROCEDURE and STANDARD are optional and that no two declaratives should be coded for the same event.

For nested programs the order of precedence is: a file-specific declarative in the program that contains the failing statement, then a mode-specific one in that program, then the same two with GLOBAL in the enclosing program, and so on outward until the outermost program. Only the first applicable declarative runs.

When the declarative runs

The error procedure is performed after the system’s own error routine has finished, when the failing statement is a READ, WRITE, REWRITE, START, OPEN, CLOSE or DELETE; when an AT END or INVALID KEY condition occurs and the statement has no matching phrase; and on the IBM-defined conditions that set file status key 1 to 9. If the file status does not indicate a critical error, the statement after the failed one runs when the declarative ends.

A few limits from the Language Reference matter for declaratives that do real work:

  • A declarative must not execute GOBACK or STOP RUN while it is active because of a QSAM abend on a READ, WRITE or REWRITE (file status 34 or 90), nor EXIT PROGRAM in a non-nested subprogram; and GOBACK and EXIT PROGRAM are not allowed in a declarative active in a nested program or a method. The portable pattern, used by the batch program below, is to set a flag and a condition code in the declarative and to stop in the main line.

  • In a multithreaded application, the lock of the file stays held while its declarative runs, so a declarative that reads another file whose declarative reads the first one can deadlock. Keep declaratives short and free of file operations.

  • A declarative for a file is executed in addition to the system’s standard routine, not instead of it.

Other USE formats

The USE statement has more formats than the error one:

  • USE BEFORE REPORTING identifier (Report Writer, COBOL 85; it runs just before a report group is presented, to adjust its SUM and SOURCE items or to SUPPRESS it) is the subject of Reports and Report Writer.

  • USE AFTER EXCEPTION CONDITION exception-name (COBOL 2002) attaches a declarative to an exception condition and is described in the next section.

  • USE FOR DEBUGGING is an obsolete COBOL 85 debugging aid. It is mentioned only so that old code can be recognized: a USE FOR DEBUGGING ON procedure, ALL PROCEDURES or REFERENCES OF identifier declarative is performed whenever that procedure runs or that item is referenced, and the program must say WITH DEBUGGING MODE in SOURCE-COMPUTER. Enterprise COBOL 6.5 still accepts it (not in nested programs, methods, recursive programs or programs compiled with THREAD) and supplies the DEBUG-ITEM special register. GnuCOBOL 3.2 parses it, but it takes effect only when WITH DEBUGGING MODE is present at compile time and the environment variable COB_SET_DEBUG is set to Y, y or 1 at run time; in a test with those two switches on, the declarative ran after each ADD to the named item and a default build was silent, and under -std=ibm the compiler warns that the clause is obsolete. New code should use a debugger, DISPLAY tracing under a compiler-directive switch, or the unit tests described on Testing COBOL Programs; the debugging tools are on Debugging and Troubleshooting.

Exception conditions (the EC names)

COBOL 2002 introduced a different idea: instead of each statement having its own phrase, the language defines a hierarchy of named exception conditions that the program can enable, test and handle uniformly. The top names are groups, the bottom names are specific. EC-ALL contains everything; EC-SIZE contains EC-SIZE-OVERFLOW, EC-SIZE-ZERO-DIVIDE, EC-SIZE-EXPONENTIATION and the other arithmetic size conditions; EC-BOUND contains EC-BOUND-SUBSCRIPT, EC-BOUND-REF-MOD and EC-BOUND-ODO; EC-I-O contains EC-I-O-AT-END, EC-I-O-INVALID-KEY, EC-I-O-PERMANENT-ERROR and the other file conditions; and there are groups for data (EC-DATA), arguments, program calls (EC-PROGRAM), ranges, storage, sort and merge, report, screen and others. In the standard each condition is either fatal, which ends the run unit when it is checked and occurs, or non-fatal, which only records the exception. The standard text itself is paywalled; the names and the fatal flag used here are those printed by cobc --list-exceptions and in Appendix F of the GnuCOBOL manual.

The >>TURN directive and the cobc options

In GnuCOBOL the checks are generated into the program only when asked for. There are two ways to ask:

  • The compiler directive >>TURN exception-name [file-name]... CHECKING ON [WITH LOCATION] (or CHECKING OFF) switches the check on for the statements that follow it, down to a group name (EC-I-O and a file name, EC-SIZE, EC-ALL).

Run-time error procedures and Language Environment

When no phrase, status or declarative catches an error, the run-time system decides what happens, and each platform lets a program get control first.

GnuCOBOL. The routine CBL_ERROR_PROC registers one subprogram that the library calls when a run-time error is about to stop the program. In the test below it received the message text in its first parameter and could display the EXCEPTION-* functions (which need -debug, -g or -ftraceall for the location and statement) ; it cannot prevent the termination, because when the procedure returns the standard error routine runs. Only one procedure is in effect at a time. This program registers a procedure for the Circulation nightly run and then calls the missing program of the earlier example:

       IDENTIFICATION DIVISION.
       PROGRAM-ID. ERRPROC.
      * A runtime error procedure registered with CBL_ERROR_PROC.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-HANDLER          USAGE PROGRAM-POINTER.
       01  WS-MEMBER-ID        PIC 9(6) VALUE 101.
       PROCEDURE DIVISION.
       MAIN-PARA.
           SET WS-HANDLER TO ENTRY "CIRCERR"
           CALL "CBL_ERROR_PROC" USING 0, WS-HANDLER
           DISPLAY "nightly run starting"
           CALL "NOSUCHPG" USING WS-MEMBER-ID
           DISPLAY "not reached"
           STOP RUN.
       END PROGRAM ERRPROC.

       IDENTIFICATION DIVISION.
       PROGRAM-ID. CIRCERR.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-TEXT             PIC X(80).
       01  WS-KIND             PIC X(31).
       LINKAGE SECTION.
       01  LK-MESSAGE          PIC X(80).
       PROCEDURE DIVISION USING LK-MESSAGE.
           MOVE FUNCTION EXCEPTION-STATUS TO WS-KIND
           UNSTRING LK-MESSAGE DELIMITED BY LOW-VALUE INTO WS-TEXT
           DISPLAY "CIRCERR: " FUNCTION TRIM(WS-TEXT)
           DISPLAY "CIRCERR: status " FUNCTION TRIM(WS-KIND)

       END PROGRAM CIRCERR.

The handler read the message from its LINKAGE item and the condition name from EXCEPTION-STATUS before it did anything else, because the UNSTRING that cleans the message would overwrite the recorded exception (an earlier version of this program printed EC-OVERFLOW-UNSTRING). The process still ended with exit status 1. The message area ends in low-values rather than spaces, which is why the handler cuts it with UNSTRING before displaying it.

Enterprise COBOL on z/OS. A condition that is not handled is a Language Environment condition. COBOL can handle most errors with the phrases above, but for extraordinary conditions the program can register its own condition handler with the Language Environment callable service CEEHDLR, passing the entry address in a PROCEDURE-POINTER, and the handler can report, analyse, or even fix up a program and let it resume. The runtime messages are produced by signaling the matching condition, so a handler that does not deal with an information or warning level condition should percolate it. Two other callable services are used for diagnosis: CEE3DMP produces a formatted dump at a chosen point (symbolic names appear when the program is compiled with TEST and the dump uses the VARIABLES suboption), and CEE3ABD stops the run unit at once with an abend and a system dump when called with a cleanup value of zero. When the run unit ends abnormally with TRAP(ON), the run time closes the open files. If a handler reads or changes data defined in other programs (for example EXTERNAL items), the handler should declare them VOLATILE when the program is compiled with OPTIMIZE(1) or OPTIMIZE(2) and without TEST. How to read the resulting CEE messages, traceback and dump is on Debugging and Troubleshooting, and the run-time option defaults are on Compiling, Linking and Language Environment. The z/OS material here is documented behaviour that was not run.

RETURN-CODE, STOP RUN and the condition code

A COBOL program tells its caller how it went through the RETURN-CODE special register, implicitly defined as 01 RETURN-CODE GLOBAL PICTURE S9(4) USAGE BINARY VALUE ZERO in Enterprise COBOL (GnuCOBOL holds a larger binary value, as the earlier run showed). When the program ends, the value goes to the operating system as the user return code, or, when control returns to a calling program, to that program’s own RETURN-CODE. It is the batch condition code that JCL tests with COND or IF (see JCL for COBOL Programmers). A CALL ... RETURNING or a method does not set it, and Language Environment service calls do not return their feedback in it.

In Enterprise COBOL the STOP statement has two formats only: STOP RUN (the current RETURN-CODE, modulo 4096, becomes the return code; all files of the run unit are closed) and the obsolete STOP literal, which suspends execution until the operator acts and is better replaced by ACCEPT and DISPLAY. It has no status phrase. GOBACK is the usual way to leave a program that may be called or run on its own, and in a main program it acts like STOP RUN.

GnuCOBOL accepts more. In STOP RUN, RETURNING and GIVING are interchangeable and WITH ERROR STATUS and WITH NORMAL STATUS are alternatives, each optionally followed by a number (WITH and STATUS are optional words): without a number NORMAL gives 0 and ERROR gives 1. A program always returns a status, which is RETURN-CODE unless the statement says otherwise. The values returned by each form, measured on the Linux container used for this page, are:

MOVE 8 TO RETURN-CODE, then STOP RUN      exit status 8
STOP RUN WITH NORMAL STATUS               exit status 0
STOP RUN WITH ERROR STATUS                exit status 1
STOP RUN WITH ERROR STATUS 12             exit status 12
STOP RUN RETURNING 16                     exit status 16
MOVE 4 TO RETURN-CODE, then GOBACK        exit status 4
MOVE 5000 TO RETURN-CODE, then STOP RUN   exit status 136
MOVE -3 TO RETURN-CODE, then STOP RUN     exit status 253

The last two lines show that a Unix process keeps only the low 8 bits of the value (5000 modulo 256, and -3 as 253), whereas z/OS takes the value modulo 4096; code that returns large condition codes must be written with the smaller range in mind. By convention a batch step returns 0 for success, 4 for warnings, 8 for errors, 12 for serious errors and 16 for severe errors, which is what the nightly validation program below uses.

STOP ERROR (GnuCOBOL 3.2). GnuCOBOL 3.2 added a STOP ERROR statement that stops the run with a run-time error. It belongs only to the GCOS dialect: it is rejected in the default dialect and in every other dialect tried, with the compile-time error "STOP ERROR does not conform to GnuCOBOL" (and the same wording naming IBM COBOL (lax), COBOL 2014 and the other dialects), and the dialect configuration files list stop-error-statement as ok only in gcos-strict. With -std=gcos the statement compiles, prints libcob: error: STOP ERROR when executed, and ends with exit status 1; it takes no value. STOP RUN WITH ERROR STATUS is the portable way to return a failure code.

The Circulation nightly validation step

The last program puts the mechanisms together in the shape a z/OS batch step has. A declarative covers both input files, sets a flag and the severe condition code 16 and does nothing else, so the main line stays in charge of stopping; the members are loaded into a table, each loan transaction is checked with SEARCH ... AT END, a suspended member is rejected, and the step ends with 0 when all is well, 4 when any transaction was rejected and 16 when a file failed.

Common mistakes

  • No FILE STATUS, no phrase and no declarative on a file: the first failing OPEN or READ ends the run unit (GnuCOBOL: libcob: error: file does not exist (status = 35) and exit status 1).

  • A FILE STATUS item declared inside the record: it becomes part of the data transferred; declare it in WORKING-STORAGE.

  • INVALID KEY on a sequential file, or AT END for a random read: the first is a compile-time error, the second compiles in GnuCOBOL and then fails at run time on a missing key.

  • Testing the status only after the loop: the code is overwritten by every later statement on the file; test it right after the statement.

  • A STOP RUN or GOBACK inside a declarative that was entered because of a QSAM abend: not allowed on z/OS; set a flag and stop in the main line.

  • A declarative that reads a second file: it can deadlock in a multithreaded program and it obscures the original failure.

  • ADD or COMPUTE without ON SIZE ERROR on a field that can overflow: the result is truncated silently (2.50 instead of 100002.50 above).

  • A division without a zero test or ON SIZE ERROR: an abend on z/OS and a silent no-op in GnuCOBOL 3.2.0.

  • NOT ON EXCEPTION after DISPLAY in ON EXCEPTION: the 3.2.0 deviation shown above; use a flag.

  • Relying on EC-*, RAISE or USE AFTER EXCEPTION CONDITION in code that must also run on z/OS: Enterprise COBOL has no equivalent; use the phrases, FILE STATUS and declaratives, and SSRANGE and NUMCHECK.

  • Large RETURN-CODE values: z/OS keeps 12 bits, Unix 8; keep to 0, 4, 8, 12 and 16.

  • Reading the EXCEPTION-* functions after another statement: any later statement, even an UNSTRING or a DISPLAY of the functions, replaces the recorded exception; copy it first.

  • Compiling production code with -debug: it adds checks and slows the program; use it for tests and compile without it for the release.
