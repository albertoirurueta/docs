Conditions, IF and EVALUATE

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against ISO/IEC 1989:2023 (edition 3, January 2023; an edition 4 is upcoming, in DIS ballot), GnuCOBOL 3.2 (28 July 2023, the latest release) and IBM Enterprise COBOL for z/OS 6.5 (PTFs through September 2026), and was checked on 2026-10-20. Every portable example below was compiled with cobc -x -Wall (GnuCOBOL 3.2.0, fixed reference format) without a single warning and run; the output and the diagnostics shown are real, and the few examples that need another option or that are deliberately wrong say so. The ISO standard is paywalled and was not read: the rules come from the Enterprise COBOL Language Reference and Programming Guide and from the GnuCOBOL Programmer’s Guide, and where the two differ the page says so.

A COBOL program makes decisions with a conditional expression: an expression whose value is true or false. The Language Reference lists the statements that take one: IF, EVALUATE, PERFORM (the UNTIL phrase) and SEARCH (the WHEN phrase). This page covers how conditions are written and combined, then the two statements that branch on them, IF and EVALUATE. The data items the examples test come from the Circulation library back office: the 88-level names BOOK-ACTIVE, BOOK-WITHDRAWN, MEMBER-ACTIVE, MEMBER-SUSPENDED, LOAN-CHECKOUT and LOAN-RETURN are defined in the copybooks BOOKREC, MEMBREC and LOANREC, and how a level-88 entry is declared and set is in VALUE, INITIALIZE and Condition Names. Loops that end on a condition are in PERFORM and Structured Programming, and the table search that uses the same conditions is in Searching and Sorting Tables.

The six simple conditions

A condition is simple or complex. Enterprise COBOL 6.5 defines six simple conditions. Any number of paired parentheses may enclose a condition without changing whether it is simple or complex.

Simple condition What it tests Example

Relation

Compares two operands: data items, literals, functions, arithmetic expressions, index-names, pointers

WS-COPIES > 2, BOOK-STATUS = "W"

Class

Whether a data item holds only digits, only letters, only lowercase or uppercase letters, or only the characters of a user-defined class

BOOK-ISBN IS NUMERIC, BOOK-ISBN IS ISBN-CHAR

Sign

Whether a numeric operand is positive, negative or zero

MEMBER-FINES IS POSITIVE

Condition-name

Whether a conditional variable has one of the values of a level-88 entry

MEMBER-SUSPENDED

Switch-status

Whether an external switch is on or off

DRY-RUN

Omitted-argument

Whether the caller left out an optional argument

LK-DAYS IS OMITTED

Relation conditions

A relation condition compares two operands with a relational operator. The word forms and the symbols are interchangeable; NOT in front of the operator reverses it. The two characters of >= and <= must not be separated by a space, and every operator must be preceded and followed by a space.

Words Symbol Meaning

IS GREATER THAN

IS >

greater than

IS LESS THAN

IS <

less than

IS EQUAL TO

IS =

equal to

IS GREATER THAN OR EQUAL TO

IS >=

greater than or equal to

IS LESS THAN OR EQUAL TO

IS <=

less than or equal to

IS NOT GREATER THAN, IS NOT LESS THAN, IS NOT EQUAL TO

IS NOT >, IS NOT <, IS NOT =

the opposite of each

The comparison that is performed depends on the classes of the two operands (Enterprise COBOL Language Reference, Tables 23 and 24; the operand pairs that are not allowed are the blank cells in those tables). The rules that matter every day:

  • Numeric against numeric compares algebraic values. The number of digits, the USAGE, the position of the decimal point and the sign representation are not significant; unsigned operands are positive, and all zero values are equal. 12.50 in a PIC S9(5)V99 item equals 12.5 in a PIC 9(3)V9 item, as in the example above.

  • Alphanumeric against alphanumeric compares character by character from the left, using the collating sequence in use (the native one, or the one selected with PROGRAM COLLATING SEQUENCE). If the operands differ in length, the shorter is treated as if it were extended to the right with spaces, so "ABC" equals "ABC ".

  • A numeric integer against an alphanumeric item is allowed only for integers: the integer is treated as if it had been moved to an alphanumeric item with as many characters as the integer has digits. 00042 in a PIC X(5) item equals the PIC 9(5) value 42. A numeric item with decimals against an alphanumeric item is not allowed by Enterprise COBOL (the table marks only integer items as permitted). GnuCOBOL 3.2.0 accepts IF BOOK-TITLE = 12.5 in every dialect without a diagnostic and the test is simply false, so the compiler will not catch it for you.

  • Group items are compared as alphanumeric strings of bytes, without any conversion. Comparing a group that contains a packed or binary field with a numeric literal is therefore a comparison of bytes, which gives a result that is predictable only when both sides have the same data representation.

  • Figurative constants take the class of the other operand: ZERO against a numeric item is a numeric comparison, against an alphanumeric item it is the character 0; SPACE and HIGH-VALUE are characters (see Words, Literals and Figurative Constants).

  • National and UTF-8 operands are compared in their own encodings, and a PROGRAM COLLATING SEQUENCE has no effect on UTF-8 comparisons. National Data, UTF-8 and Code Pages covers them.

  • Pointers, index-names and object references have their own relation conditions (only equal and not equal for pointers; an index-name is compared by its occurrence number). See Pointers and Dynamic Storage and Tables and OCCURS.

A relation condition must contain at least one reference to an identifier, which is why IF "A" = "B" is not a meaningful test; the next sections show what GnuCOBOL says about it.

Source: Enterprise COBOL for z/OS 6.5 Language Reference: General relation conditions

Class conditions

A class condition tests the content of a data item. The Language Reference gives the forms that are valid for each kind of item (Table 21):

Item referenced Valid tests (each also with NOT)

Alphabetic (PIC A)

ALPHABETIC, ALPHABETIC-LOWER, ALPHABETIC-UPPER, a class-name

Alphanumeric, alphanumeric-edited, numeric-edited

NUMERIC, ALPHABETIC, ALPHABETIC-LOWER, ALPHABETIC-UPPER, a class-name

Zoned decimal (USAGE DISPLAY) or packed decimal (COMP-3)

NUMERIC

National

NUMERIC, ALPHABETIC, ALPHABETIC-LOWER, ALPHABETIC-UPPER

DBCS

DBCS, KANJI

What each test means:

  • NUMERIC: only the digits 0 to 9, with or without an operational sign. If the PICTURE has no sign, a sign in the data makes the item not numeric. If it has a sign, the item must be elementary and carry a valid sign. Which sign codes are valid depends on the NUMPROC compiler option and the NUMCLS installation option, and invalid zone codes are treated as nonnumeric by the test even when INVDATA tolerates them in comparisons. A group item can take NUMERIC only if it has no signed elementary item.

  • ALPHABETIC is the letters A to Z, a to z and the space; ALPHABETIC-LOWER and ALPHABETIC-UPPER are the lowercase and uppercase letters and the space. An all-spaces item therefore passes all three, and a numeric-looking PIC X item passes none of them.

  • A class-name is a user-defined class declared in SPECIAL-NAMES: the item passes if it contains only the listed characters.

  • DBCS and KANJI apply to DISPLAY-1 items and range-check the byte pairs.

The example above declares CLASS ISBN-CHAR IS "0" THRU "9" "X", the character set of an ISBN-10 or ISBN-13 (the X check digit), and tests BOOK-ISBN IS ISBN-CHAR. A value with an X in the middle still passes ISBN-CHAR but fails NUMERIC, as the output shows.

GnuCOBOL is more permissive than the table above: its Programmer’s Guide says it has no restriction on group items or PIC A items with NUMERIC, nor on PIC 9 items with ALPHABETIC, and 3.2.0 compiled an ALPHABETIC test on PIC 9 and COMP-3 items without any diagnostic. Code that is meant to run on z/OS should stay inside Table 21.

Source: Enterprise COBOL for z/OS 6.5 Language Reference: Class condition

Validating input with class tests

The numeric class test is the standard guard against invalid data. The compiler assumes that the contents of a data item agree with its PICTURE and USAGE; when they do not (a record from another system, a field overwritten through a REDEFINES), references to the item are undefined. Test before using. The program checks five raw transaction records before it trusts LOANREC:

       IDENTIFICATION DIVISION.
       PROGRAM-ID. LOANVALID.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
           COPY LOANREC.
       01  WS-RAW-VALUES.
           05  FILLER  PIC X(21)   VALUE "O00010000000120261020".
           05  FILLER  PIC X(21)   VALUE "O00A10000000120261020".
           05  FILLER  PIC X(21)   VALUE "R      00000120261020".
           05  FILLER  PIC X(21)   VALUE "X00010000000120261020".
           05  FILLER  PIC X(21)   VALUE "O0001000000012026102 ".
       01  WS-RAW-TABLE REDEFINES WS-RAW-VALUES.
           05  WS-RAW              PIC X(21)   OCCURS 5 TIMES.
       01  WS-SUB                  PIC 9       VALUE ZERO.
       01  WS-MEMBER-TEXT          PIC X(6)    VALUE SPACES.
       PROCEDURE DIVISION.
       MAIN-PARA.
           PERFORM VARYING WS-SUB FROM 1 BY 1 UNTIL WS-SUB > 5
               MOVE WS-RAW (WS-SUB) TO LOAN-RECORD
               IF (LOAN-CHECKOUT OR LOAN-RETURN)
                   AND LOAN-MEMBER-ID IS NUMERIC
                   AND LOAN-BOOK-ID IS NUMERIC
                   AND LOAN-DATE IS NUMERIC
                   DISPLAY WS-SUB ": VALID " WS-RAW (WS-SUB)
               ELSE
                   DISPLAY WS-SUB ": REJECT " WS-RAW (WS-SUB)
               END-IF
           END-PERFORM
           IF WS-MEMBER-TEXT IS NUMERIC
               DISPLAY "SPACES ARE NUMERIC"
           ELSE
               DISPLAY "SPACES ARE NOT NUMERIC"
           END-IF
           IF WS-MEMBER-TEXT IS ALPHABETIC
               DISPLAY "SPACES ARE ALPHABETIC"
           END-IF
           STOP RUN.
1: VALID O00010000000120261020
2: REJECT O00A10000000120261020
3: REJECT R      00000120261020
4: REJECT X00010000000120261020
5: REJECT O0001000000012026102
SPACES ARE NOT NUMERIC
SPACES ARE ALPHABETIC

Source: Enterprise COBOL for z/OS 6.5 Programming Guide: Checking for incompatible data (numeric class test)

The parentheses around LOAN-CHECKOUT OR LOAN-RETURN matter, and the next sections explain why. Record 3 shows that a blank field is not numeric (but is alphabetic, as the last two lines show for a PIC X item). On z/OS the NUMCHECK(ZON,PAC) compiler option can have the compiler generate implicit numeric class tests for zoned and packed decimal items that are sending items, which validates sign fields against the NUMPROC option too. Where the data comes from and how a MOVE treats it is in MOVE and Data Movement.

Sign conditions

A sign condition tests whether a numeric operand is POSITIVE (greater than zero), NEGATIVE (less than zero) or ZERO; NOT reverses it, and NOT ZERO is true for a positive or a negative value. The operand can be a numeric identifier or an arithmetic expression that contains at least one variable, so IF WS-ADJUST + 7 IS ZERO is valid, as in the example. An unsigned operand is either positive or zero. On z/OS the result depends on the NUMPROC option.

Source: Enterprise COBOL for z/OS 6.5 Language Reference: Sign condition

Condition-name conditions

A condition-name is the name of a level-88 entry. The condition MEMBER-SUSPENDED is true when the conditional variable MEMBER-STATUS has any of the values (or lies in any of the THRU ranges) of the entry. The rules of comparison are those of relation conditions, and it is the same as writing the relation by hand: IF MEMBER-SUSPENDED replaces IF MEMBER-STATUS = "S". Condition-names are allowed for alphanumeric, DBCS, national, UTF-8 and floating-point items as well as numeric ones. Prefer the name to the literal: the meaning of the value is written once, in the data division, and SET MEMBER-SUSPENDED TO TRUE changes the state without repeating the code. That SET statement, and the WHEN SET TO FALSE phrase, are in the page on VALUE, INITIALIZE and Condition Names.

Source: Enterprise COBOL for z/OS 6.5 Language Reference: Condition-name condition

Switch-status conditions

A switch-status condition tests an external on/off switch. The programmer associates a condition-name with the on or off value of a switch in SPECIAL-NAMES, then tests the name:

  • In Enterprise COBOL the switch is one of the eight UPSI (user-programmable status indicator) switches UPSI-0 to UPSI-7; the name is associated with the value 1 (on) or 0 (off). The value is set outside the program, for example to select a year-end run.

  • In GnuCOBOL the switch is SWITCH-0 to SWITCH-36, and it is set from the environment with COB_SWITCH_n=ON before the run (COB_SWITCH_1 for SWITCH-1).

  • GnuCOBOL 3.2.0 accepts UPSI-0 as a synonym of SWITCH-0 only with -std=ibm. Compiled without it, the example gives the error below, and with -std=ibm the name SWITCH-1 is rejected in the same way. Setting COB_SWITCH_0=ON for the -std=ibm build of the example made DRY-RUN true, and COB_SWITCH_1=ON left it false.

kinds.cob:7: error: invalid system-name 'UPSI-0'
    5 |        SPECIAL-NAMES.
    6 |            CLASS ISBN-CHAR IS "0" THRU "9" "X"
    7 >            UPSI-0 IS DRY-RUN-SWITCH

This output is from compiling the example above without -std=ibm. Switch conditions are a way to vary a run without recompiling, such as a dry-run mode for the nightly run; for anything more than a few modes, read the setting from a parameter or a file instead.

Source: Enterprise COBOL for z/OS 6.5 Language Reference: Switch-status condition

The omitted-argument condition

A called program can make a parameter optional and test whether the caller passed it. Enterprise COBOL 6.5 documents the OPTIONAL phrase of PROCEDURE DIVISION USING (it is not allowed when the LP(64) compiler option is in effect) and the condition data-name IS [NOT] OMITTED. The condition is true when the caller passed OMITTED for that argument, when the argument was a trailing one that the call left out, or when the argument is itself an omitted formal parameter of the caller. The data item must be defined in the program that tests it and be named in an OPTIONAL phrase. The GnuCOBOL 3.2 Programmer’s Guide lists OMITTED among its class conditions. The example is a program pair that calls LOANDAYS once with a loan period and once without:

       IDENTIFICATION DIVISION.
       PROGRAM-ID. OMITMAIN.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-LIMIT                PIC 9(3)    VALUE 21.
       PROCEDURE DIVISION.
       MAIN-PARA.
           CALL "LOANDAYS" USING WS-LIMIT
           CALL "LOANDAYS" USING OMITTED
           STOP RUN.
       END PROGRAM OMITMAIN.

       IDENTIFICATION DIVISION.
       PROGRAM-ID. LOANDAYS.
       DATA DIVISION.
       LINKAGE SECTION.
       01  LK-DAYS                 PIC 9(3).
       PROCEDURE DIVISION USING OPTIONAL LK-DAYS.
       MAIN-PARA.
           IF LK-DAYS IS OMITTED
               DISPLAY "NO LIMIT PASSED: DEFAULT 14 DAYS"
           ELSE
               DISPLAY "LIMIT PASSED: " LK-DAYS " DAYS"
           END-IF
           GOBACK.
       END PROGRAM LOANDAYS.

Compiled with cobc -x -Wall omit.cob:

LIMIT PASSED: 021 DAYS
NO LIMIT PASSED: DEFAULT 14 DAYS

Source: Enterprise COBOL for z/OS 6.5 Language Reference: Omitted argument condition

With -std=ibm the same file compiles, runs identically, and gives warning: USING OPTIONAL used [-Wdialect], so a build that must be free of warnings in that dialect cannot use it. The way arguments are passed, BY REFERENCE, BY CONTENT and BY VALUE, and what OMITTED means in the CALL statement, are in Subprograms, CALL and Linkage.

Complex conditions: NOT, AND and OR

Simple conditions are combined with the logical operators, each of which must be preceded and followed by a space.

Operator Name True when

NOT

logical negation

the condition after it is false

AND

logical conjunction

both conditions are true

OR

logical inclusive or

either or both conditions are true

Precedence from highest to lowest: arithmetic operations, the simple conditions themselves, NOT, AND, OR. Parentheses override it. The Language Reference gives this example, which is evaluated as the parenthesized form below it:

       NOT A IS GREATER THAN B OR A + B IS EQUAL TO C AND D IS POSITIVE
       (NOT (A IS GREATER THAN B)) OR
       (((A + B) IS EQUAL TO C) AND (D IS POSITIVE))

Order of evaluation. Conditions within one level are evaluated from left to right, and evaluation of that level stops as soon as its truth value is known; arithmetic expressions and functions inside a condition are evaluated only if and when that condition is reached. This is what makes a guard such as "is the subscript valid, and only then the table entry" safe. GnuCOBOL 3.2.0 behaves the same way. In the program below the first test is guarded and the second is not; with -debug the second one is caught by the subscript check:

       IDENTIFICATION DIVISION.
       PROGRAM-ID. SHORTCIRC.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-I                    PIC 9       VALUE ZERO.
       01  WS-TABLE.
           05  WS-ENTRY            PIC X       OCCURS 3 TIMES VALUE "A".
       PROCEDURE DIVISION.
       MAIN-PARA.
           IF WS-I > 0 AND WS-ENTRY (WS-I) = "A"
               DISPLAY "FOUND"
           ELSE
               DISPLAY "GUARDED"
           END-IF
           IF WS-ENTRY (WS-I) = "A" AND WS-I > 0
               DISPLAY "FOUND"
           ELSE
               DISPLAY "NOT GUARDED"
           END-IF
           STOP RUN.

Compiled with cobc -x -Wall -debug shortcirc.cob; the first line is the output of the guarded test and the rest is the runtime error of the second one (the program stops there and returns exit status 1):

Abbreviated combined relation conditions

When relation conditions are written one after another, any condition after the first can omit its subject, or its subject and its relational operator. The omitted parts are taken from the last stated subject and the last stated operator:

Abbreviated Unabbreviated equivalent

A = B AND NOT < C OR D

A = B) AND (A NOT < C OR (A NOT < D)

A NOT > B OR C

(A NOT > B) OR (A NOT > C)

NOT A = B OR C

(NOT (A = B)) OR (A = C)

NOT (A = B OR < C)

NOT A = B) OR (A < C

(The first four rows of Table 31 in the Language Reference.) The rules, in the order in which they cause trouble:

  • NOT is part of the relational operator when it is immediately followed by GREATER THAN, >, LESS THAN, <, EQUAL TO or =. In any other position it is a logical NOT that negates only the single relation condition that follows it: the negation is not carried to the objects that are abbreviated after it.

  • A parenthesis right after a relational operator distributes that operator over the objects inside it, as in WS-COPIES = (3 OR 4 OR 5). A distributed operator may not contain a simple condition, another relational operator, or a NOT immediately after the left parenthesis.

  • The insertion of an omitted subject or operator stops when another simple condition (including a condition-name) is found, or at the right parenthesis that closes a parenthesis opened to the left of the subject.

  • Two consecutive logical NOT`s cancel each other and produce an S-level message; `A = B AND NOT NOT = C is legal, because the second NOT belongs to the operator.

The IF statement

IF evaluates a condition and runs one of two alternative statements. In the form to use today:

       IF condition [THEN]
           statement-1 ...
       [ELSE
           statement-2 ...]
       END-IF

  • THEN is optional and has no effect on the program.

  • statement-1 runs when the condition is true and statement-2 when it is false. Each is a series of imperative statements, and may include another conditional statement, in which case the IF is nested.

  • END-IF is the explicit scope terminator. Without it, the scope of the IF ends at the next separator period (and an ELSE belongs to the nearest preceding IF that has not been terminated).

  • NEXT SENTENCE, or CONTINUE, can stand where a statement is required. See the section below.

Nested IF statements are matched left to right: an ELSE goes with the nearest preceding IF that has no ELSE and has not been terminated, and an END-IF goes with the nearest preceding IF that has not been terminated. With END-IF on every IF the matching is explicit and the indentation tells the truth. If the ELSE is omitted, every statement between the condition and the END-IF (or the period) belongs to the true branch.

Explicit scope terminators and the period

Every conditional statement (IF, EVALUATE, READ, SEARCH, an ADD with an ON SIZE ERROR phrase, and so on) has an explicit scope terminator (END-IF, END-EVALUATE, END-READ, END-SEARCH, END-ADD) that turns it into an imperative statement. A sentence is one or more statements ended by a period. The period is the implicit scope terminator: it ends every statement that is still open, however deeply nested, and that is the cause of the best-known COBOL bug.

The EVALUATE statement

EVALUATE is COBOL’s multi-way decision: a shorthand for a series of nested `IF`s that can test several things at once. It is the right tool for decision tables.

       EVALUATE subject [ALSO subject] ...
           WHEN object [ALSO object] ...
               imperative-statement ...
           [WHEN object [ALSO object] ...
               imperative-statement ...] ...
           [WHEN OTHER
               imperative-statement ...]
       END-EVALUATE

The operands between EVALUATE and the first WHEN are the selection subjects, separated by ALSO. Each WHEN has one selection object for every subject, separated by ALSO, and the objects are matched with the subjects by position. The rules:

  • A subject is an identifier, a literal, an arithmetic expression, a conditional expression (a condition), or the words TRUE or FALSE.

  • An object is an identifier, a literal or an arithmetic expression (compared for equality with the subject), a range value-1 THRU value-2 (both ends of the same class; the subject matches if it is within the range, ends included; a range whose first operand is greater than the second matches nothing), a condition, TRUE or FALSE, or ANY, which matches whatever the subject is. NOT in front of a value or a range matches everything but it.

  • Subject and object kinds must correspond: a condition or TRUE/FALSE as an object needs a conditional expression (or TRUE/FALSE) as the subject in the same position.

  • The WHEN phrases are tried in the order written and the first one whose objects are all satisfied is selected. There is no fall-through to the next WHEN after its statements, so no break is needed, and order is the way to give one rule priority over another.

  • Several WHEN phrases can share one set of statements: a WHEN with no statement of its own uses the statements of the next WHEN that has some (the "O" ALSO "A" and "o" ALSO "A" phrases below).

  • WHEN OTHER runs when no WHEN matched. If it is missing and nothing matched, execution continues after END-EVALUATE and nothing happens, which is rarely what you want for a business rule; code WHEN OTHER and make it report.

  • The number of objects in each WHEN must be the same as the number of subjects (the compiler checks it; see the diagnostics below).

                   MOVE "REJECT: MEMBER SUSPENDED" TO WS-DECISION
               WHEN LOAN-CHECKOUT ALSO ANY ALSO BOOK-WITHDRAWN
                   MOVE "REJECT: BOOK WITHDRAWN" TO WS-DECISION
               WHEN LOAN-CHECKOUT ALSO ANY ALSO BOOK-COPIES = ZERO
                   MOVE "REJECT: NO COPY AVAILABLE" TO WS-DECISION
               WHEN LOAN-CHECKOUT ALSO MEMBER-FINES > WS-FINE-LIMIT
                       ALSO ANY
                   MOVE "HOLD: FINES OVER LIMIT" TO WS-DECISION
               WHEN LOAN-CHECKOUT ALSO ANY ALSO ANY
                   MOVE "ACCEPT CHECKOUT" TO WS-DECISION
               WHEN OTHER
                   MOVE "REJECT: UNKNOWN TYPE" TO WS-DECISION
           END-EVALUATE.
CASE 1: ACCEPT CHECKOUT
CASE 2: REJECT: MEMBER SUSPENDED
CASE 3: HOLD: FINES OVER LIMIT
CASE 4: REJECT: BOOK WITHDRAWN
CASE 5: REJECT: NO COPY AVAILABLE
CASE 6: ACCEPT RETURN
CASE 7: REJECT: UNKNOWN TYPE

Source: Enterprise COBOL for z/OS 6.5 Programming Guide: Using the EVALUATE statement

Case 6 is a suspended member who returns a book: the first WHEN accepts it before the suspension rule is ever reached. Case 3 has fines of 12.50 against a limit of 10.00. The rows are in the order of the diagram, which is the order in which the compiler tries them:

flowchart TD START(["EVALUATE TRUE ALSO TRUE ALSO TRUE"]) --> R1{"LOAN-RETURN?"} R1 -- "yes" --> A1["ACCEPT RETURN"] R1 -- "no" --> R2{"LOAN-CHECKOUT and MEMBER-SUSPENDED?"} R2 -- "yes" --> X1["REJECT: MEMBER SUSPENDED"] R2 -- "no" --> R3{"LOAN-CHECKOUT and BOOK-WITHDRAWN?"} R3 -- "yes" --> X2["REJECT: BOOK WITHDRAWN"] R3 -- "no" --> R4{"LOAN-CHECKOUT and BOOK-COPIES = ZERO?"} R4 -- "yes" --> X3["REJECT: NO COPY AVAILABLE"] R4 -- "no" --> R5{"LOAN-CHECKOUT and fines over limit?"} R5 -- "yes" --> H1["HOLD: FINES OVER LIMIT"] R5 -- "no" --> R6{"LOAN-CHECKOUT?"} R6 -- "yes" --> A2["ACCEPT CHECKOUT"] R6 -- "no" --> O1["WHEN OTHER: REJECT, UNKNOWN TYPE"]

The diagram shows the decision order of the EVALUATE: each diamond is one WHEN phrase, the first test that passes picks the action, and WHEN OTHER is what remains. The ANY objects are the conditions missing from a diamond. Reordering the phrases changes the answer for a suspended member who returns a book, so the order is part of the specification. A comment next to the statement, or a test for each row, is how that specification is kept (see Coding Standards and Best Practices).

Pitfalls, with the real diagnostics

The program below is deliberately wrong. It contains the errors that the compiler does catch:

       IDENTIFICATION DIVISION.
       PROGRAM-ID. BADCOND.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
           COPY BOOKREC.
           COPY LOANREC.
       PROCEDURE DIVISION.
       MAIN-PARA.
           IF "A" = "B"
               DISPLAY "C"
           END-IF
           EVALUATE LOAN-TYPE ALSO BOOK-STATUS
               WHEN "O"
                   DISPLAY "D"
           END-EVALUATE
           EVALUATE BOOK-COPIES
               WHEN "A" THRU 9
                   DISPLAY "E"
           END-EVALUATE
           IF BOOK-COPIES NOT > 5 AND NOT <
               DISPLAY "F"
           END-IF
           STOP RUN.

Real output of cobc -x -Wall bad.cob:

   18 |                    DISPLAY "E"

   22 |            END-IF

Source: GnuCOBOL manual: cobc options and warnings

  • IF "A" = "B" compares two literals; the answer is known at compile time, and the compiler says so. Such tests are usually left over from debugging or from a copybook expansion.

  • An EVALUATE with two subjects and a WHEN with one object is an error: the objects must match the subjects one to one.

  • WHEN "A" THRU 9 mixes classes. Here the compiler warns and the test can never be true; Enterprise COBOL requires the two operands of a THRU to be of the same class.

  • NOT > with no operand is an incomplete expression, an error.

What the compiler does not catch matters more: the stray period, the abbreviated NOT = 1 OR 2, an ALPHABETIC test on a numeric item, = 12.5 against an alphanumeric item, and a numeric class test on data that was never validated. The first three have examples above; the rest need review and test cases, as does the rule of every decision table, which is one test per row.

Where the book is outdated

The book consulted for this section (Taulli, Modern Mainframe Development, 2022) was written around Enterprise COBOL 6.3 and covers IF, class conditions and EVALUATE at the survey level it gives the rest of the language; nothing is copied from it. What a reader should update, using the current manuals:

  • The OMITTED class test and the OPTIONAL phrase on BY REFERENCE parameters are documented by the 6.5 Language Reference; the section outline for this site lists them as new in 6.5, a release the book (6.3) predates. The book could not describe them.

  • The book’s examples were run with GnuCOBOL (OpenCobolIDE), which accepts several things that Enterprise COBOL rejects or that compile only with an option, as shown above: ALPHABETIC on a numeric item, a non-integer literal compared with an alphanumeric item, and partial expressions in EVALUATE. A test that passes on a PC can fail the z/OS compile.

  • COBOL has moved to explicit scope terminators since 1985. The period-terminated nested IF and NEXT SENTENCE that old examples (and programs) use survive for compatibility only; new code uses END-IF, END-EVALUATE and CONTINUE.
