Dates and Times

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against ISO/IEC 1989:2023 (edition 3, January 2023; an edition 4 is upcoming, in DIS ballot), GnuCOBOL 3.2 (28 July 2023, the latest release) and IBM Enterprise COBOL for z/OS 6.5 (PTFs through September 2026), and was checked on 2026-10-20. Every portable example below was compiled with cobc -x -Wall (GnuCOBOL 3.2.0, fixed reference format) without a single warning (except the two examples that are deliberately wrong and say so) and run; the output and the diagnostics shown are real. The ISO standard is paywalled and was not read: the rules come from the Enterprise COBOL manuals and the GnuCOBOL manuals, and where the two differ the page says so.

A date in a COBOL program is not a type: it is a number or a string that the program interprets. The language gives three families of tools for working with that number, and the page follows them in turn:

  • the ACCEPT ... FROM DATE|DAY|DAY-OF-WEEK|TIME statement, which is among the oldest features of the language and reads the system clock into a data item;

  • FUNCTION CURRENT-DATE and the other intrinsic functions, which return four-digit years and the offset from UTC and can convert a calendar date into a number of days, add to it and convert it back;

  • the ISO 8601 functions (FORMATTED-DATE, FORMATTED-DATETIME, INTEGER-OF-FORMATTED-DATE and their relatives), which read and write the text forms that web services and JSON use.

The examples use the layouts of the Circulation library back office, in particular LOAN-DATE in LOANREC, and the page ends with the rule that computes when a book is due and how many days late it is. The general syntax of intrinsic functions, and the table of every function, are in Intrinsic Functions; the numeric items that hold the dates are described in PICTURE Clause and USAGE and Numeric Representation.

A word about reproducibility. Anything that reads the clock produces a different result every time it is run, so the examples below are of two kinds. Those that use fixed dates (a literal, a VALUE clause or a record from a file) print the same output on any day and any machine. The two that read the clock (accept-demo and live-clock, and the last lines of current-date) are labelled "varies": the output shown is what the run on 2026-10-20 printed, with a container whose time zone is UTC.

ACCEPT FROM DATE, DAY, DAY-OF-WEEK and TIME

Format 2 of the ACCEPT statement (Enterprise COBOL Language Reference, ACCEPT statement; GnuCOBOL Programmer’s Guide, ACCEPT FROM DATE/TIME) moves the date or the time kept by the system into a receiving item. Nothing is read from a device: the source is one of six conceptual data items that cannot be declared in the program and that behave as USAGE DISPLAY numbers, moved to the receiver by the rules of MOVE (without CORRESPONDING).

The YYYYMMDD and YYYYDDD forms came with COBOL 2002; Enterprise COBOL accepts them and so does GnuCOBOL. The receiver does not have to be a numeric item: an alphanumeric item receives the digits as text, and an alphanumeric group item is allowed as the receiver. The TIME and DATE receivers are therefore often declared as groups whose subordinate items pick the fields apart, as the first example does by redefining the time.

The program prints the clock in every format it supports. This output varies with every run: it is the run of 2026-10-20 at 13:04:21 UTC, a Tuesday (DAY-OF-WEEK 2) and the 293rd day of 2026.

DATE YYYYMMDD 20261020
DAY           26293
DAY YYYYDDD   2026293

TIME          13095666

Source: GnuCOBOL Programmer’s Guide, ACCEPT FROM DATE/TIME

The same program also compiled and ran under -std=ibm and printed the same kinds of values. Three habits make the statement safer:

  • Take the date once. ACCEPT FROM DATE followed by ACCEPT FROM TIME are two reads of the clock. A job that runs at 23:59:59 can get yesterday’s date and tomorrow’s time. Reading one FUNCTION CURRENT-DATE (next section) returns a consistent date and time.

  • Prefer the four-digit forms. ACCEPT FROM DATE and ACCEPT FROM DAY return two-digit years, so 990101 and 000101 do not sort in time order. The YYYYMMDD and YYYYDDD phrases, or CURRENT-DATE, return the century.

  • Remember that this is local time. DATE and TIME are the system’s local time, which with GnuCOBOL follows the TZ environment variable of the process and on z/OS follows the system’s time settings. A server in another time zone reports another day for the same instant.

FUNCTION CURRENT-DATE

FUNCTION CURRENT-DATE takes no arguments and returns a 21-character alphanumeric value, so a single MOVE fills a group that names the pieces. The layout is defined by the standard and is the same in Enterprise COBOL and GnuCOBOL:

Positions Length Contents

1-4

4

year in the Gregorian calendar

5-6

2

month, 01 to 12

7-8

2

day of the month, 01 to 31

9-10

2

hours past midnight, 00 to 23

11-12

2

minutes, 00 to 59

13-14

2

seconds, 00 to 59

15-16

2

hundredths of a second (00 where the system has no fractions)

17

1

- if local time is behind Greenwich mean time, + if the same or ahead, 0 if the offset is not available

18-19

2

hours of the offset (00 to 12 behind, 00 to 13 ahead)

20-21

2

additional minutes of the offset (00 to 59)

Enterprise COBOL’s manual works the example of 15 February 1995, 05:14:27.81 in Eastern Standard Time, where the value is 1995021505142781-0500. The following program redefines the 21 characters in a group, parses that literal (so that its first part prints the same every day) and then reads the live clock. The last lines vary.

Two details are visible in the output. The live line ends in +0000 because the container runs in UTC; running the same binary with TZ=America/New_York printed -0400 at that moment (daylight saving time), so the offset really follows the time zone of the process. And the reference-modified form FUNCTION CURRENT-DATE(1:8) gives the yyyymmdd run date directly, which is how the nightly Circulation run obtains "today". The offset in positions 17 to 21 is the difference between local time and Greenwich mean time, which is why a value stored with it can be reduced to UTC later; the formatted functions below return the same information in ISO 8601 form.

Integer dates: arithmetic on calendar dates

Subtracting two yyyymmdd numbers does not give a number of days, because the digits are a calendar and not a count. The standard solves this with an integer date: the number of days since a fixed day zero, which can be added to and subtracted from, and converted back. Day 1 is Monday 1 January 1601 (in the Gregorian calendar, reckoned backwards), and the range is integer 1 (16010101) to 3,067,671 (99991231). The functions are:

Function Argument Result

INTEGER-OF-DATE

standard date yyyymmdd

integer date

DATE-OF-INTEGER

integer date

standard date yyyymmdd

INTEGER-OF-DAY

Julian date yyyyddd

integer date

DAY-OF-INTEGER

integer date

Julian date yyyyddd

TEST-DATE-YYYYMMDD

an integer

0 if valid, 1 bad year, 2 bad month, 3 bad day

TEST-DAY-YYYYDDD

an integer

0 if valid, 1 bad year, 2 bad day of the year

The next program does the usual things: converts a date to an integer, adds 14 days (the loan period used below), converts back, gets the Julian form, finds the weekday and counts days between two dates. It prints the same output on any day because every date is fixed.

       IDENTIFICATION DIVISION.
       PROGRAM-ID. INTEGER-DATES.
      * Integer dates: day 1 is Monday 1 January 1601.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-DATE              PIC 9(8) VALUE 20261020.
       01  WS-JULIAN            PIC 9(7).
       01  WS-INT               PIC 9(7).
       01  WS-OUT               PIC 9(8).
       01  WS-OUT-JULIAN        PIC 9(7).
       01  WS-WEEKDAY           PIC 9.
       01  WS-DAYS              PIC S9(5).
       PROCEDURE DIVISION.
       MAIN-PARAGRAPH.
           COMPUTE WS-INT = FUNCTION INTEGER-OF-DATE(WS-DATE)
           DISPLAY "integer date of " WS-DATE " = " WS-INT
           COMPUTE WS-OUT = FUNCTION DATE-OF-INTEGER(WS-INT + 14)
           DISPLAY "14 days later          = " WS-OUT
           COMPUTE WS-OUT-JULIAN = FUNCTION DAY-OF-INTEGER(WS-INT)
           DISPLAY "Julian form            = " WS-OUT-JULIAN
           MOVE WS-OUT-JULIAN TO WS-JULIAN
           COMPUTE WS-INT = FUNCTION INTEGER-OF-DAY(WS-JULIAN)
           DISPLAY "back from Julian       = " WS-INT
           COMPUTE WS-WEEKDAY = FUNCTION MOD(WS-INT - 1, 7) + 1
           DISPLAY "day of week (1=Mon)    = " WS-WEEKDAY
           COMPUTE WS-DAYS = FUNCTION INTEGER-OF-DATE(20261231)
                           - FUNCTION INTEGER-OF-DATE(20261020)
           DISPLAY "days to 31 Dec 2026    = " WS-DAYS
           DISPLAY "day 1                  = "
                   FUNCTION DATE-OF-INTEGER(1)
           DISPLAY "day 3067671            = "
                   FUNCTION DATE-OF-INTEGER(3067671)
      *    29 February: only leap years have it.
           DISPLAY "2028-02-28 + 1         = "
                   FUNCTION DATE-OF-INTEGER(
                       FUNCTION INTEGER-OF-DATE(20280228) + 1)
           DISPLAY "2100-02-28 + 1         = "
                   FUNCTION DATE-OF-INTEGER(
                       FUNCTION INTEGER-OF-DATE(21000228) + 1)
           STOP RUN.

The output shows the leap-year rule at work: 2028 has a 29 February and 2100, being a multiple of 100 and not of 400, does not. The weekday expression MOD(integer - 1, 7) + 1 gives 1 for Monday to 7 for Sunday, the same numbering as ACCEPT FROM DAY-OF-WEEK; it is valid because day 1 is a Monday, and it needs care in Enterprise COBOL, where the INTDATE option can move the origin (see the table below).

Validate before converting

The conversion functions require a valid argument (the Enterprise COBOL manual states the valid forms and ranges, and TEST-DATE-YYYYMMDD exists to check them). The test function returns which part is wrong, in the order year, month, day, so a rejection message can be specific. Here are six candidates, the Julian test, and what GnuCOBOL’s INTEGER-OF-DATE does with an invalid date that nobody tested.

       IDENTIFICATION DIVISION.
       PROGRAM-ID. TEST-DATES.
      * Validating dates before using them.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-CANDIDATES.
           05  FILLER PIC 9(8) VALUE 20261020.
           05  FILLER PIC 9(8) VALUE 20260230.
           05  FILLER PIC 9(8) VALUE 20261320.
           05  FILLER PIC 9(8) VALUE 15991231.
           05  FILLER PIC 9(8) VALUE 20280229.
           05  FILLER PIC 9(8) VALUE 21000229.
       01  WS-TABLE REDEFINES WS-CANDIDATES.
           05  WS-CANDIDATE     PIC 9(8) OCCURS 6 TIMES.
       01  WS-I                 PIC 9.
       01  WS-RESULT            PIC 9.
       01  WS-JULIAN-RESULT     PIC 9.
       01  WS-BAD               PIC 9(8) VALUE 20260230.
       01  WS-INT               PIC 9(7).
       PROCEDURE DIVISION.
       MAIN-PARAGRAPH.
           PERFORM VARYING WS-I FROM 1 BY 1 UNTIL WS-I > 6
               COMPUTE WS-RESULT =
                   FUNCTION TEST-DATE-YYYYMMDD(WS-CANDIDATE(WS-I))
               DISPLAY WS-CANDIDATE(WS-I) " -> " WS-RESULT
           END-PERFORM
           COMPUTE WS-JULIAN-RESULT = FUNCTION TEST-DAY-YYYYDDD(2027366)
           DISPLAY "Julian 2027366 -> " WS-JULIAN-RESULT
           COMPUTE WS-JULIAN-RESULT = FUNCTION TEST-DAY-YYYYDDD(2028366)
           DISPLAY "Julian 2028366 -> " WS-JULIAN-RESULT
      *    An unchecked invalid date reaches INTEGER-OF-DATE.
           COMPUTE WS-INT = FUNCTION INTEGER-OF-DATE(WS-BAD)
           DISPLAY "INTEGER-OF-DATE(20260230) = " WS-INT
           STOP RUN.
20261020 -> 0
20260230 -> 3
20261320 -> 2
15991231 -> 1
20280229 -> 0
21000229 -> 3
Julian 2027366 -> 2
Julian 2028366 -> 0
INTEGER-OF-DATE(20260230) = 0000000

Source: Enterprise COBOL for z/OS 6.5 Language Reference, TEST-DATE-YYYYMMDD and TEST-DAY-YYYYDDD

The returned codes match the manual: 15991231 is year 1 (below 1601), 20261320 is month 2 and 20260230 is day 3. The last line is the trap: GnuCOBOL does not stop for 20260230; it returns 0, which a program that computes with it treats as "no such day". The Enterprise COBOL function descriptions state the valid range and do not promise a result outside it, so the portable rule is the same in both: call TEST-DATE-YYYYMMDD first and reject the record.

Where integer day 1 is: INTDATE

On z/OS the compiler option INTDATE(ANSI) (the default) makes day 1 January 1, 1601, as above. INTDATE(LILIAN) makes day 1 October 15, 1582, the origin used by Language Environment’s own date services. The Programming Guide tabulates which combinations agree:

Option Intrinsic function Language Environment service

INTDATE(ANSI)

INTEGER-OF-DATE

compatible with CEECBLDY; not with CEEDAYS

INTDATE(ANSI)

DATE-OF-INTEGER, DAY-OF-INTEGER

not compatible with CEEDATE

INTDATE(LILIAN)

INTEGER-OF-DATE

compatible with CEEDAYS; not with CEECBLDY

INTDATE(LILIAN)

DATE-OF-INTEGER, DAY-OF-INTEGER

compatible with CEEDATE

A program that exchanges integer dates with other programs or with those services must say which origin it uses, and the difference of two integer dates (a count of days) is the same in both. GnuCOBOL has no INTDATE option: its integer dates always start at 1600-12-31, like INTDATE(ANSI). These are z/OS facts and are not run here.

The ISO 8601 date and time functions

The standard of 2014 added a second family that reads and writes dates as text in ISO 8601 shapes. Enterprise COBOL 6.5 lists it among the 2002/2014 standard features it implements; the outline for this section dates it to the 6.3 service stream, a release this page could not re-check, so it names no release. GnuCOBOL 3.2 implements the family too. The functions are:

Function Purpose

FORMATTED-DATE(format, integer-date)

integer date to text in a date format

FORMATTED-TIME(format, seconds [, offset-minutes])

seconds past midnight to text in a time format

FORMATTED-DATETIME(format, integer-date, seconds [, offset-minutes])

both, to text in a combined format

FORMATTED-CURRENT-DATE(format)

the current date and time in a combined format

INTEGER-OF-FORMATTED-DATE(format, text)

text in a date (or combined) format to an integer date

SECONDS-FROM-FORMATTED-TIME(format, text)

text in a time (or combined) format to seconds past midnight

TEST-FORMATTED-DATETIME(format, text)

0 if the text fits the format, otherwise the position of the first bad character

COMBINED-DATETIME(integer-date, seconds)

one number: the integer date, a decimal point and the seconds as five digits

SECONDS-PAST-MIDNIGHT

the current local time of day in seconds

The format is an alphanumeric (or national, or UTF-8) literal built from the strings in the Language Reference. Date formats: YYYYMMDD and YYYY-MM-DD (calendar), YYYYDDD and YYYY-DDD (ordinal, the day of the year) and YYYYWwwD and YYYY-Www-D (ISO week date: year, week 01 to 52, day 1 to 7). Time formats: hhmmss and hh:mm:ss, a fraction after the seconds written .s to .sssssssss (one to nine digits), the suffix Z for UTC, and the offset forms hhmmss+hhmm and hh:mm:ss+hh:mm. A combined format joins a date format and a time format with an uppercase T, both in the basic or both in the extended style: YYYY-MM-DDThh:mm:ss+hh:mm is allowed and YYYYMMDDThh:mm:ss is not.

The program below formats a fixed date and time (14:30:25 is 52,225 seconds past midnight), shows the same instant as UTC for a time zone two hours ahead (offset 120 minutes), and parses text back. The TEST-FORMATTED-DATETIME results are positions: month 13 is wrong at character 7 of 2026-13-03, and 0 means valid.

       IDENTIFICATION DIVISION.
       PROGRAM-ID. FORMATTED-DEMO.
      * ISO 8601 style date and time functions (Enterprise COBOL 6.x,
      * GnuCOBOL 3.2). Every value here is fixed, so the output is too.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-INT               PIC 9(7).
       01  WS-TEXT              PIC X(32).
       01  WS-SECONDS           PIC 9(5)V99.
       01  WS-CHECK             PIC 99.
       01  WS-COMBINED          PIC 9(7)V9(5).
       PROCEDURE DIVISION.
       MAIN-PARAGRAPH.
           COMPUTE WS-INT = FUNCTION INTEGER-OF-DATE(20261020)
           MOVE FUNCTION FORMATTED-DATE("YYYY-MM-DD", WS-INT)
               TO WS-TEXT
           DISPLAY "extended calendar : " WS-TEXT
           MOVE FUNCTION FORMATTED-DATE("YYYYDDD", WS-INT) TO WS-TEXT
           DISPLAY "basic ordinal     : " WS-TEXT
           MOVE FUNCTION FORMATTED-DATE("YYYY-Www-D", WS-INT)
               TO WS-TEXT
           DISPLAY "extended week     : " WS-TEXT
           MOVE FUNCTION FORMATTED-TIME("hh:mm:ss", 52225) TO WS-TEXT
           DISPLAY "time of day       : " WS-TEXT
           MOVE FUNCTION FORMATTED-DATETIME(
                    "YYYY-MM-DDThh:mm:ss", WS-INT, 52225)
               TO WS-TEXT
           DISPLAY "date and time     : " WS-TEXT
           MOVE FUNCTION FORMATTED-DATETIME(

Computing a due date and days overdue in Circulation

The Circulation rule is simple: a book is due 14 days after the checkout, and every day after the due date costs a daily fine, with a maximum per loan. The steps are the ones the page has built: validate the loan date, convert it to an integer date, add the loan period, convert back to print, subtract from the run date’s integer to count the days late (never below zero), and multiply. The run date is a fixed 20261105 so that the output is reproducible; a real run would replace its VALUE clause with MOVE FUNCTION CURRENT-DATE(1:8) TO WS-AS-OF, or, better, would read it from a control card so that a rerun after a failure uses the original date. The daily fine (0.25) and its cap (10.00) are values invented for the example.

A second sample file has five transactions chosen to hit the interesting cases: an ordinary loan, a loan from February whose due date is long past, a loan on the last day of the year (whose due date falls in the next year), a loan with an impossible date and a return.

From 20 October to 5 November is 16 days, and the subtraction of the raw numbers says 85, because 20261105 - 20261020 is a difference between two digit strings that skips the whole gap between 31 and 100 in the month position. The compiler reports nothing, and a fine computed from it is wrong without anyone being told. Dates are converted to integer dates before they are subtracted or compared for distance (a plain IF DATE-A > DATE-B on two yyyymmdd values is fine for ordering).

Two-digit years and windowing (legacy)

Everything above uses four-digit years. Old programs, and records that still carry a yymmdd field, do not. Before the year 2000 the usual way to save two digits per date was ACCEPT ... FROM DATE, and the Y2K work of the late 1990s was largely the job of finding such fields. The two practical ways out were to expand the field to four digits (the permanent fix) or to window it: keep two digits and decide the century from a pivot. The standard has intrinsic functions for the second approach, which are the only part of the old Y2K tooling that is still current:

Function Argument Returns

YEAR-TO-YYYY(yy [, window])

two-digit year

four-digit year

DATE-TO-YYYYMMDD(yymmdd [, window])

six-digit date

yyyymmdd

DAY-TO-YYYYDDD(yyddd [, window])

five-digit Julian date

yyyyddd

The window argument, default 50, is added to the year at execution time to give the last year of a 100-year interval into which the two-digit year must fall. The IBM manual’s table makes the sliding rule concrete: in 2002, 851003 with window 120 is 20851003 (interval 2023 to 2122), with window -20 it is 18851003 (1883 to 1982) and with window 10 it is 19851003 (1913 to 2012). Because the interval moves with the clock, the same data gives different results in different years; the result is only stable when the data is regularly rewritten. GnuCOBOL’s functions accept a third argument, the "year of execution" (an extension, with no counterpart in the Enterprise COBOL syntax), which lets this program fix the year so that its output is repeatable. The first four lines reproduce the IBM table, and the last two reproduce the YEAR-TO-YYYY table.

The Millennium Language Extensions: removed

Old code you may meet. Earlier Enterprise COBOL releases (up to V4) shipped the Millennium Language Extensions: the DATE FORMAT clause on a data item (for example DATE FORMAT YYXXXX for a yymmdd-like field), the DATEPROC compiler option and YEARWINDOW, with which the compiler windowed such fields automatically during comparisons and moves. IBM removed them in Enterprise COBOL V5 and V6, and searching the 6.5 Language Reference and Programming Guide for DATEPROC, YEARWINDOW and the DATE FORMAT clause finds nothing. A program that uses them does not compile on 6.5; the migration is one of:

  • widen the field to PIC 9(8) or PIC 9(7) with a four-digit year and convert the stored data once (the preferred one);

  • keep the stored yymmdd and call DATE-TO-YYYYMMDD or YEAR-TO-YYYY where the program needs a full date, as the program above does;

  • leave a note beside the field naming the window and the planned year when it must be revisited.

The details of the V4 options are not documented for 6.5 and are not repeated here; the description above is from memory of the V4 documentation and is not re-verified.

Where the book is outdated

The book consulted for this section (Taulli, Modern Mainframe Development, 2022) is a survey of mainframe work and is used here only for the topic list and the Y2K narrative; nothing is copied from it. The points to carry into new code are:

  • Two-digit years are not a design to follow. Teaching material that shows ACCEPT ... FROM DATE and then stores or compares the six digits is preserving a Y2K-era habit; new code uses FUNCTION CURRENT-DATE(1:8) or ACCEPT ... FROM DATE YYYYMMDD and a four-digit year in the record layout.

  • The Millennium Language Extensions that the Y2K literature describes no longer exist in the current compiler (above); windowing survives only as the three intrinsic functions.

  • The ISO 8601 functions are newer than most introductory books and than COBOL 2002; they are the way to produce and read the text dates of JSON and REST payloads, which the data-interchange pages of this section depend on.

  • The book’s Enterprise COBOL baseline (6.3) predates 6.4 and 6.5; the date functions above are in the 6.5 reference, which is the version this page follows.
