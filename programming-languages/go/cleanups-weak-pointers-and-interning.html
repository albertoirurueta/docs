Cleanups, Weak Pointers and Interning

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Go 1.27 (go1.27.2), checked on 2026-10-18; every go.mod shown has the line go 1.27. A garbage-collected language hides the death of objects: memory is never freed explicitly, so a program normally cannot tell when a value became unreachable. Go’s runtime library offers four deliberate exceptions, and one related tool for the opposite problem. runtime.SetFinalizer (the original) and runtime.AddCleanup (Go 1.24) run a function some time after an object became unreachable. The weak package (Go 1.24) refers to an object without keeping it alive. The unique package (Go 1.23) canonicalizes ("interns") comparable values and is built on top of weak pointers and cleanups. runtime.KeepAlive and runtime.Pinner go the other way: they stop the runtime from collecting or moving something too early. These are low-level tools with sharp edges, and the official advice is to hide them inside a package and use them rarely. This page explains each one, shows what actually happens when they are used correctly and incorrectly, and ends with a guide to choosing between them and to testing code that depends on them.

It builds on Memory Management and Garbage Collection (reachability, the GC cycle and GOGC), Pointers and Value Semantics and Goroutines and the Scheduler (cleanups and finalizers run on their own goroutines). Related pages are unsafe and Low-Level Programming, cgo and C Interoperability (the pointer-passing rules that Pinner serves), Sync and Atomics, Memory Model and Data Races, Testing, Generics (all three packages are generic) and I/O, Files and the Filesystem (os.File is the standard example of an explicit Close backed by a safety net). Other languages offer similar tools under other names: see WeakReference<T> and finalizers in C# Memory Management and Disposal, Weak<T> in Rust Smart Pointers, weak references in Swift Automatic Reference Counting and weak_ptr in C++ Memory Management and Smart Pointers.

Every example was compiled, vetted with go vet and run with Go 1.27.2; the output shown is the real output. Examples that call the garbage collector print only facts that do not vary between runs (whether something was collected, not when); sizes and timings that do vary by machine are labelled. Panic and fatal error traces are shortened to the lines that matter: file paths are replaced by .../main.go, $GOROOT stands for the toolchain directory, and the addresses in the traces change on every run. Observing object death

The Go specification does not say when memory is reclaimed, and the death of an object is not an observable event at the language level. The GC guide describes the three features that break the illusion:

  • cleanups (runtime.AddCleanup): run cleanup(arg) on a runtime goroutine some time after the object became unreachable;

  • weak pointers (weak.Pointer[T]): a pointer the collector does not count when it decides whether the object is reachable;

  • finalizers (runtime.SetFinalizer): run finalizer(obj) some time after the object became unreachable, which makes the object reachable again for the duration of the call.

Everything in this page follows from one property: the runtime decides when. A cleanup, a finalizer or a cleared weak pointer can appear at any garbage collection after the object’s last use, and the object’s last use is not the end of the enclosing block but the last point where the compiler’s liveness analysis sees it mentioned. A function argument or receiver may become unreachable at the last point where the function mentions it. Nothing is guaranteed to run before the program exits, and nothing is guaranteed to run at all.

Finalizers: runtime.SetFinalizer

SetFinalizer(obj, finalizer) associates a function with the object obj points to. When the collector finds the object unreachable it clears the association, makes the object reachable again, and calls finalizer(obj) on the single goroutine that runs every finalizer in the program. If nothing resurrects the object further, the next cycle that finds it unreachable frees it. SetFinalizer(obj, nil) removes the finalizer.

package main

import (
	"fmt"
	"runtime"
	"time"
)

// Scanner wraps a barcode-scanner device identified by a descriptor.
type Scanner struct {
	fd int
}

func closeDevice(fd int) { fmt.Println("device closed:", fd) }

func openScanner(fd int, done chan<- struct{}) *Scanner {
	s := &Scanner{fd: fd}
	// The finalizer receives the object itself, so the object is
	// resurrected for the duration of the call.
	runtime.SetFinalizer(s, func(s *Scanner) {
		closeDevice(s.fd)
		close(done)
	})
	return s
}

func main() {
	done := make(chan struct{})
	s := openScanner(3, done)
	fmt.Println("scanner open:", s.fd)
	s = nil // the last reference is dropped

	for range 5 {
		runtime.GC()
		select {
		case <-done:
			fmt.Println("finalizer ran")
			return
		case <-time.After(50 * time.Millisecond):
		}
	}
	fmt.Println("finalizer did not run")
}
scanner open: 3
device closed: 3
finalizer ran

Source: runtime.SetFinalizer

The argument must be a pointer to an object allocated by new, by taking the address of a composite literal or by taking the address of a local variable, and the finalizer must be a function taking one parameter that obj's type is assignable to. Because both parameters are any, the compiler cannot check this; a violation is a run-time fatal error, not a panic you can recover from:

package main

import "runtime"

type Scanner struct{ fd int }

func main() {
	s := Scanner{fd: 3}
	// A value, not a pointer: the runtime refuses.
	runtime.SetFinalizer(s, func(*Scanner) {})
}

Why finalizers are error-prone

The GC guide lists the problems, and each one is a consequence of resurrection:

  • One per object, at the first byte. An object can have a single finalizer, and it must be attached to the first byte of the allocation. A second SetFinalizer call on an object that already has one is a fatal error ("finalizer already set"), and packages that cannot add their own bookkeeping to an object they were handed cannot clean it up.

  • Cycles are never freed. Finalizers run in dependency order: if A points at B and both have finalizers, only A’s finalizer runs, and B’s runs after A is freed. If a cyclic structure includes an object with a finalizer, there is no order that respects the dependencies, so the cycle is not guaranteed to be collected and the finalizer is not guaranteed to run.

  • Chains take one cycle per link. A linked list in which every node has a finalizer needs at least as many GC cycles as there are nodes.

  • One goroutine runs them all, sequentially. A finalizer that blocks delays every other finalizer; one that must run long should start a goroutine.

  • The object lives at least one more cycle. Its memory cannot be reused until the cycle after the finalizer ran.

  • Not at exit, not for zero-size objects, not guaranteed for package-level initializers. The documentation says so explicitly for each case.

  • Visibility. SetFinalizer happens before the finalizer call, but nothing orders the program’s other writes to the object before the finalizer reads them; a finalizer that touches mutable state needs a mutex or atomics, just like any other goroutine.

The first two are easy to see. The next program builds a pair of objects that point at each other, as a device and its owning session often do, and attaches a finalizer to one pair and a cleanup (next section) to another:

package main

import (
	"fmt"
	"runtime"
	"sync/atomic"
	"time"
)

// Scanner and Session point at each other, as a device and its owner often do.
type Scanner struct {
	fd      int
	session *Session
}

type Session struct {
	scanner *Scanner
}

var finalized, cleaned atomic.Int32

func newPair(fd int) *Scanner {
	s := &Scanner{fd: fd}
	s.session = &Session{scanner: s}
	return s
}

func makeWithFinalizer() {
	s := newPair(1)
	runtime.SetFinalizer(s, func(*Scanner) { finalized.Add(1) })
}

func makeWithCleanup() {
	s := newPair(2)
	runtime.AddCleanup(s, func(int) { cleaned.Add(1) }, s.fd)
}

func main() {
	makeWithFinalizer()
	makeWithCleanup()

	for range 10 {
		runtime.GC()
		time.Sleep(10 * time.Millisecond)
	}
	fmt.Println("finalizers run for the cyclic pair:", finalized.Load())
	fmt.Println("cleanups run for the cyclic pair:  ", cleaned.Load())
}
finalizers run for the cyclic pair: 0
cleanups run for the cyclic pair:   1

The finalizer never ran: the cyclic pair contains an object with a finalizer, there is no order that respects the dependencies, and the pair leaks until the program ends. The cleanup ran. The chain problem is just as visible; each GC cycle releases exactly one node of a five-node chain, because a node can only be finalized after the node pointing to it has been freed:

package main

import (
	"fmt"
	"runtime"
	"sync/atomic"
	"time"
)

type node struct{ next *node }

var finalized atomic.Int32

func build(n int) {
	var head *node
	for range n {
		head = &node{next: head}
		runtime.SetFinalizer(head, func(*node) { finalized.Add(1) })
	}
}

func main() {
	build(5)
	for cycle := 1; cycle <= 8; cycle++ {
		runtime.GC()
		time.Sleep(20 * time.Millisecond)
		fmt.Printf("after GC %d: %d of 5 finalizers have run\n", cycle, finalized.Load())
	}
}

Finalizers still have one advantage: their execution order is defined, which can matter for structures with complex destruction order. The GC guide calls them potentially useful but rarely so; for all other uses in Go 1.24 and later it recommends cleanups.

Cleanups: runtime.AddCleanup

AddCleanup(ptr, cleanup, arg) arranges for cleanup(arg) to run on a runtime goroutine some time after ptr is no longer reachable. It is generic, func AddCleanup[T, S any](ptr *T, cleanup func(S), arg S) Cleanup, so the compiler checks the cleanup against its argument. The typical use is the one in the documentation: ptr is an object that wraps an underlying resource, arg is the resource itself (a descriptor, a handle, a C pointer) and cleanup releases it.

package main

import (
	"fmt"
	"runtime"
	"time"
)

// Scanner wraps a barcode-scanner device identified by a descriptor.
type Scanner struct {
	fd int
}

func closeDevice(fd int) { fmt.Println("device closed:", fd) }

func openScanner(fd int, done chan<- struct{}) *Scanner {
	s := &Scanner{fd: fd}
	// The cleanup receives only the argument (fd), never the object, so the
	// object is not resurrected and can be freed immediately.
	runtime.AddCleanup(s, func(fd int) {
		closeDevice(fd)
		close(done)
	}, fd)
	return s
}

func main() {
	done := make(chan struct{})
	s := openScanner(3, done)
	fmt.Println("scanner open:", s.fd)
	s = nil // the last reference is dropped

	for range 5 {
		runtime.GC()
		select {
		case <-done:
			fmt.Println("cleanup ran")
			return
		case <-time.After(50 * time.Millisecond):
		}
	}
	fmt.Println("cleanup did not run")
}
scanner open: 3
device closed: 3
cleanup ran

Source: runtime.AddCleanup

The difference from the finalizer version is the one that matters: the cleanup receives fd, never the scanner. The object is not resurrected, so it is freed in the same cycle that finds it unreachable, and the cleanup runs afterwards with whatever it needs to release the resource. The release notes for Go 1.24 give the practical advantages:

  • multiple cleanups may be attached to a single object;

  • cleanups may be attached to interior pointers (a field of a struct, an element of an array);

  • cleanups do not generally cause leaks when objects form a cycle;

  • cleanups do not delay the freeing of an object or of the objects it points to.

package main

import (
	"fmt"
	"runtime"
	"sync"
)

type Scanner struct {
	fd   int
	name string
}

func main() {
	var wg sync.WaitGroup
	wg.Add(2)

	func() {
		s := &Scanner{fd: 7, name: "desk"}
		// Several independent cleanups on one object are allowed,
		// and one may even target an interior pointer (a field).
		runtime.AddCleanup(s, func(fd int) {
			fmt.Println("release descriptor", fd)
			wg.Done()
		}, s.fd)
		runtime.AddCleanup(&s.name, func(label string) {
			fmt.Println("forget label", label)
			wg.Done()
		}, "desk")
	}()

	for range 3 {
		runtime.GC()
	}
	wg.Wait()
	fmt.Println("both cleanups ran (their order is unspecified)")
}
release descriptor 7
forget label desk
both cleanups ran (their order is unspecified)

Source: runtime.AddCleanup

Because the compiler checks types, mistakes in the argument are ordinary compile errors:

package main

import "runtime"

The one rule: the cleanup must not reach the object

If ptr is reachable from the cleanup function or from arg, it is reachable from the runtime’s own record of the cleanup, so it never becomes unreachable and the cleanup never runs. AddCleanup panics for the two simple cases it can detect, passing the pointer itself as the argument and a function literal that captures the pointer:

package main

import "runtime"

type Scanner struct{ fd int }

func main() {
	s := &Scanner{fd: 3}
	// The argument equals the pointer: the cleanup could never run.
	runtime.AddCleanup(s, func(*Scanner) {}, s)
}
panic: runtime.AddCleanup: ptr is equal to arg, cleanup will never run

goroutine 1 [running]:

	.../main.go:10 +0x50

The runtime cannot see indirect paths. In the next program the argument is a *job that holds the scanner, so the scanner stays reachable through the runtime’s own cleanup record. There is no panic, no error and no log line; the cleanup silently never runs, which is the worst failure mode in this page, because the leak looks like a working program:

package main

import (
	"fmt"
	"runtime"
	"time"
)

type Scanner struct{ fd int }

func (s *Scanner) release() { fmt.Println("closing", s.fd) }

// job refers back to the scanner, e.g. a queue entry that records its owner.
type job struct{ owner *Scanner }

func openScanner(ran *bool) {
	s := &Scanner{fd: 3}
	// Wrong: the argument reaches s, so s stays reachable from the
	// runtime's own cleanup record. The runtime cannot spot this
	// indirect path, so there is no panic: the cleanup silently never runs.
	runtime.AddCleanup(s, func(j *job) {
		*ran = true
		j.owner.release()
	}, &job{owner: s})
}

func main() {
	ran := false
	openScanner(&ran)

	for range 5 {
		runtime.GC()
		time.Sleep(20 * time.Millisecond)
	}
	fmt.Println("cleanup ran:", ran)
}
cleanup ran: false

Source: GC guide: Common cleanup issues

The analysis is conservative: it flags any path back to the original object, even one that might be cut later. In this mode the runtime also prints one line to standard error per GC cycle with the finalizer and cleanup queue lengths, which helps find finalizers or cleanups that run too long. Use it in tests and staging, not in production.

Stopping a cleanup: the safety-net pattern

AddCleanup returns a runtime.Cleanup. Its Stop method cancels the cleanup, which is what an explicit Close should do. This is the pattern the GC guide recommends for non-memory resources such as file descriptors: release them deterministically with Close, and keep the cleanup only as a best-effort handler for programmers who forget (os.File does exactly this). File descriptors and similar resources have system limits the runtime knows nothing about, and the collector’s timing is outside the package author’s control (GOGC is set by operators), so a cleanup alone is a bad way to release them.

package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
)

// Scanner has an explicit Close and a cleanup as a safety net for callers
// that forget to call it.
type Scanner struct {
	fd      int
	cleanup runtime.Cleanup
	once    sync.Once
}

func openScanner(fd int) *Scanner {
	s := &Scanner{fd: fd}
	s.cleanup = runtime.AddCleanup(s, func(fd int) {
		fmt.Println("cleanup: forgotten Close, closing device", fd)
	}, fd)
	return s
}

// Close releases the device deterministically and cancels the cleanup.
func (s *Scanner) Close() {
	s.once.Do(func() {
		s.cleanup.Stop()
		fmt.Println("Close: closing device", s.fd)
	})
}

func main() {
	openScanner(1).Close() // explicit Close: the cleanup is stopped
	openScanner(2)         // forgotten: the cleanup is the safety net

	for range 5 {
		runtime.GC()
		time.Sleep(20 * time.Millisecond)
	}
}
Close: closing device 1
cleanup: forgotten Close, closing device 2

Source: runtime.Cleanup

Cleanup rules

  • cleanup(arg) runs on a separate goroutine. Since Go 1.25 cleanups run concurrently and in parallel with one another, which makes them viable for heavy use (the unique package relies on that); before that they shared a single goroutine. A cleanup that must run for a long time should start a new goroutine so it does not block the cleanup queue.

  • There is no specified order, even for objects that point at each other. Do not rely on one cleanup running before another.

  • runtime.GC waits until the cleanups for unreachable objects are queued, not until they have run.

  • If an object has both a cleanup and a finalizer, the cleanup runs only after the object has been finalized and becomes unreachable again.

  • Cleanups are not guaranteed to run before the program exits, for objects of zero size, for objects allocated in package-level variable initializers (the linker may allocate those statically), or for tiny pointer-free objects that share an allocation slot with live neighbours (see Tiny objects and other cases where nothing happens).

  • A cleanup may run as soon as the object is unreachable, so the object must stay reachable until it is safe to release the resource: see Staying alive: runtime.KeepAlive.

  • Cleanups touch shared state from another goroutine. Protect it with a mutex or atomics and run your tests with -race.

Weak pointers: the weak package

A weak.Pointer[T] refers to a value without making it reachable. weak.Make(ptr) creates one; Value() returns the original pointer, or nil if the collector reclaimed the object. The zero value behaves as if created from nil.

package main

import (
	"fmt"
	"runtime"
	"weak"
)

// Cover is a large cover image that we are happy to reload when needed.
type Cover struct {
	ISBN string
	PNG  []byte
}

func main() {
	c := &Cover{ISBN: "9780134190440", PNG: make([]byte, 1<<20)}
	w := weak.Make(c)

	fmt.Println("before GC, strong ref alive:", w.Value() != nil)

	runtime.GC()
	// The strong reference c is used again below, so it stayed reachable.
	fmt.Println("after GC, strong ref alive: ", w.Value() != nil)
	fmt.Println("isbn:", c.ISBN)

	// c is not used after this point: the object may now be reclaimed.
	runtime.GC()
	fmt.Println("after GC, no strong ref:    ", w.Value() != nil)

	// Weak pointers are comparable and keep their identity.
	var zero weak.Pointer[Cover]
	fmt.Println("zero value equals Make(nil):", zero == weak.Make[Cover](nil))
	fmt.Println("same object, same weak ptr: ", w == w)
}
before GC, strong ref alive: true
after GC, strong ref alive:  true
isbn: 9780134190440
after GC, no strong ref:     false
zero value equals Make(nil): true
same object, same weak ptr:  true

Source: weak

The first Value() calls returned non-nil because the strong pointer c was used again below them. The last call came after the last use of c, so the object was unreachable and the collector cleared the weak pointer. The documentation puts it precisely: Value may return nil as soon as the object becomes unreachable, and a function argument or receiver may become unreachable at the last point where the function mentions it.

Properties worth knowing

  • Comparable. Two weak.Pointer values are equal if and only if the pointers they were made from are equal, and that stays true after the object was reclaimed. So a weak pointer works as a map key that identifies an object without keeping it alive.

  • Objects and offsets. Weak pointers map to an object and an offset, not to a bare address. Weak pointers made from pointers to different fields of the same struct are not equal. A weak pointer may point into the middle of an object, such as a field or an array element.

  • Never guaranteed to become nil. Value is not guaranteed to eventually return nil, either. Objects reachable from global variables stay reachable, and tiny pointer-free objects may share an allocation slot with live neighbours (see Tiny objects and other cases where nothing happens).

  • Weak keys do not protect values. A map keyed by weak pointers does not affect reachability of the map values. If a value contains a strong pointer back to the object its key points to, the object stays reachable. This is the classic way to turn a "weak" map into a strong one by accident.

  • Finalizers. If the object has a finalizer, Value returns nil as soon as the finalizer is queued, even though the object is resurrected for the finalizer call. A weak pointer made from an object that a finalizer resurrected does not compare equal to weak pointers made after the resurrection.

package main

import (
	"fmt"
	"runtime"
	"weak"
)

type Scanner struct {
	fd   int
	name string
}

func main() {
	var w weak.Pointer[Scanner]
	resurrected := make(chan *Scanner, 1)

	func() {
		s := &Scanner{fd: 3, name: "desk"}
		w = weak.Make(s)
		// The finalizer resurrects the object by handing it to another goroutine.
		runtime.SetFinalizer(s, func(s *Scanner) { resurrected <- s })
	}()

	runtime.GC()
	// The weak pointer is already cleared although the object still exists:
	// it is waiting in the finalizer queue and then in the channel.
	fmt.Println("weak pointer cleared:", w.Value() == nil)
	s := <-resurrected
	fmt.Println("object still usable, fd:", s.fd)
}
weak pointer cleared: true
object still usable, fd: 3

Source: weak.Pointer

(When this demonstration was first written with a struct holding only an integer, the weak pointer was not cleared by the single runtime.GC call: a tiny pointer-free object may be batched with other objects in one allocation slot, which is exactly the caveat in the documentation. The name field makes the struct contain a pointer and so avoids tiny batching.)

A cache that does not leak

The documentation names caches as the primary use. A cache that holds values only weakly keeps an entry for exactly as long as some caller still uses the value, with no size limit and no eviction policy to tune. The map itself still needs cleaning: the entry (a weak.Pointer and its key) stays in the map after the value has gone, so a cleanup removes it. The cleanup receives only the key; it captures the cache and the weak pointer, neither of which keeps the value alive.

package main

import (
	"fmt"
	"runtime"
	"sync"
	"time"
	"weak"
)

// Cache memoizes values by key. It holds them only weakly: a value stays in
// the cache for as long as some caller still uses it, and no longer.
type Cache[K comparable, V any] struct {
	mu    sync.Mutex
	items map[K]weak.Pointer[V]
	load  func(K) *V
}

// NewCache returns a cache that calls load on a miss.
func NewCache[K comparable, V any](load func(K) *V) *Cache[K, V] {
	return &Cache[K, V]{items: make(map[K]weak.Pointer[V]), load: load}
}

// Get returns the cached value for key, loading it if needed.
func (c *Cache[K, V]) Get(key K) *V {
	c.mu.Lock()
	defer c.mu.Unlock()

	if wp, ok := c.items[key]; ok {
		if v := wp.Value(); v != nil {
			return v
		}
	}
	v := c.load(key)
	wp := weak.Make(v)
	c.items[key] = wp
	// The cleanup receives only the key. It captures c and wp, neither of
	// which keeps v reachable (wp is weak).
	runtime.AddCleanup(v, func(key K) {
		c.mu.Lock()
		defer c.mu.Unlock()
		// Delete only our own entry: a newer value may have replaced it.
		if c.items[key] == wp {
			delete(c.items, key)
		}
	}, key)
	return v
}

// Len reports how many entries (live or not yet cleaned up) the map holds.
func (c *Cache[K, V]) Len() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return len(c.items)
}

// Cover is a large cover image that can be reloaded on demand.
type Cover struct {
	ISBN string
	PNG  []byte
}

func heapMiB() uint64 {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return m.HeapAlloc >> 20
}

func main() {
	loads := 0
	covers := NewCache(func(isbn string) *Cover {
		loads++
		return &Cover{ISBN: isbn, PNG: make([]byte, 4<<20)}
	})

	keep := covers.Get("9780134190440") // a caller that keeps using it
	covers.Get("9781492077213")         // used once and dropped
	covers.Get("9781784395438")         // used once and dropped
	fmt.Printf("loaded %d covers, entries: %d, heap: %d MiB\n", loads, covers.Len(), heapMiB())

	// Cleanups run asynchronously: collect and poll until they have run.
	for range 50 {
		runtime.GC()
		if covers.Len() == 1 {
			break
		}
		time.Sleep(10 * time.Millisecond)
	}
	fmt.Printf("after GC, entries: %d, heap: %d MiB\n", covers.Len(), heapMiB())

	again := covers.Get("9780134190440") // still cached: same pointer
	fmt.Println("same cover returned:", again == keep, "loads:", loads)
	covers.Get("9781492077213") // was reclaimed, so it is loaded again
	fmt.Println("loads after re-requesting a dropped cover:", loads)
	runtime.KeepAlive(keep)
}

after GC, entries: 1, heap: 4 MiB

Source: The Go Blog: From unique to cleanups and weak

The heap figures are machine-specific (three 4 MiB covers before collection, one after); the entry counts and the loads values are what the program guarantees. Three details of the design deserve attention:

  • the lookup in Get treats a nil result of Value() like a miss, because a weak pointer can be cleared before its cleanup has removed the map entry;

  • the cleanup compares c.items[key] == wp before deleting, because a newer value may already have replaced the entry for that key (weak pointers are comparable, which is what makes this check possible);

  • the final runtime.KeepAlive(keep) keeps the strongly held cover alive up to that line, otherwise the compiler may consider it dead after its last use.

The same program also shows the contract callers must follow: a *Cover returned from the cache must be treated as read-only, because it is shared by everybody who asked for the same key.

Interning: the unique package

Interning stores one canonical copy of each distinct value and lets everything else refer to it. unique.Make(v) returns a unique.Handle[T] for any comparable T. Two handles are equal exactly when the values they were made from are equal, so comparing handles is a single pointer comparison instead of a comparison of the contents. Handle.Value() returns a shallow copy of the value and is safe for concurrent use; so is Make.

package main

import (
	"fmt"
	"unique"
	"unsafe"
)

// Edition identifies a printing by publisher and year. Any comparable type
// can be interned.
type Edition struct {
	Publisher string
	Year      int
}

func main() {
	// Two strings with equal contents but separate backing arrays.
	a := string([]byte("O'Reilly Media"))
	b := string([]byte("O'Reilly Media"))
	fmt.Println("same backing data:", unsafe.StringData(a) == unsafe.StringData(b))

	ha := unique.Make(a)
	hb := unique.Make(b)
	hc := unique.Make("Packt Publishing")

	// Handles are equal exactly when the values are equal, and comparing
	// them is a single pointer comparison.
	fmt.Println("ha == hb:", ha == hb)
	fmt.Println("ha == hc:", ha == hc)
	fmt.Println("value:", ha.Value())
	fmt.Println("handle size:", unsafe.Sizeof(ha), "bytes; string header:", unsafe.Sizeof(a), "bytes")

	// The canonical copy is shared: both handles give back the same data.
	fmt.Println("shared canonical data:", unsafe.StringData(ha.Value()) == unsafe.StringData(hb.Value()))

	e1 := unique.Make(Edition{"O'Reilly Media", 2021})
	e2 := unique.Make(Edition{string([]byte("O'Reilly Media")), 2021})
	e3 := unique.Make(Edition{"O'Reilly Media", 2024})
	fmt.Println("e1 == e2:", e1 == e2)
	fmt.Println("e1 == e3:", e1 == e3)
	fmt.Printf("%+v\n", e1.Value())
}

Why use it

Two benefits, one for memory and one for speed. The memory benefit appears when a program holds many copies of a few distinct values, for example the publisher name in every record parsed from a feed:

package main

import (
	"fmt"
	"runtime"
	"strconv"
	"unique"
)

// Book keeps the publisher either as a plain string or as a handle.
type Book struct {
	Title     string
	Publisher string
}

type InternedBook struct {
	Title     string
	Publisher unique.Handle[string]
}

var publishers = []string{
	"O'Reilly Media", "Packt Publishing", "Addison-Wesley",
	"Manning Publications", "No Starch Press",
}

func heapKiB() uint64 {
	runtime.GC()
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return m.HeapAlloc >> 10
}

func main() {
	const n = 200_000
	base := heapKiB()

	// Each record parsed from a feed owns a fresh copy of the publisher name.
	plain := make([]Book, n)
	for i := range plain {
		plain[i] = Book{
			Title:     "Book " + strconv.Itoa(i),
			Publisher: string([]byte(publishers[i%len(publishers)])),
		}
	}
	withPlain := heapKiB()
	runtime.KeepAlive(plain)
	plain = nil

	interned := make([]InternedBook, n)
	for i := range interned {
		interned[i] = InternedBook{
			Title:     "Book " + strconv.Itoa(i),
			Publisher: unique.Make(string([]byte(publishers[i%len(publishers)]))),
		}
	}
	withInterned := heapKiB()
	runtime.KeepAlive(interned)

	fmt.Printf("plain strings:    %d KiB\n", withPlain-base)
	fmt.Printf("unique handles:   %d KiB\n", withInterned-base)
	fmt.Println("same publisher:", interned[0].Publisher == interned[5].Publisher)
}

The canonical copy is reclaimed

A naive interner never forgets its entries. unique is built on weak pointers and cleanups, so a canonical copy that no handle refers to any more becomes garbage and its map entry is removed:

package main

import (
	"fmt"
	"runtime"
	"strconv"
	"time"
	"unique"
)

func heapKiB() uint64 {
	runtime.GC()
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	return m.HeapAlloc >> 10
}

func main() {
	base := heapKiB()

	handles := make([]unique.Handle[string], 0, 300_000)
	for i := range 300_000 {
		handles = append(handles, unique.Make("member-"+strconv.Itoa(i)))
	}
	fmt.Println("interned, heap grew by KiB:", heapKiB()-base)
	runtime.KeepAlive(handles)

	// Drop every handle: the canonical copies become unreachable and the
	// package reclaims them (and its internal map entries) on later cycles.
	handles = nil
	for range 20 {
		runtime.GC()
		time.Sleep(10 * time.Millisecond)
	}
	fmt.Println("handles dropped, heap grew by KiB:", heapKiB()-base)
}
interned, heap grew by KiB: 65513
handles dropped, heap grew by KiB: 22

Source: The Go Blog: New unique package

After the handles were dropped and a few collections ran, the heap returned to roughly its starting size (the residue here is a few KiB; figures are machine-specific). The GC guide uses this package as its example of encapsulation: it uses weak pointers under the hood but completely hides the objects pointed to. Callers can only copy them out through Value, so the weak machinery cannot be misused from outside.

What unique does not do

  • It does not make values immutable beyond what their types already are; Value returns a shallow copy, so a pointer inside the value still points to shared data.

  • It does not order or hash for you: a handle is an identity, so it is a good map key but has no meaningful ordering (compare the values for that).

  • It does not guarantee when memory is reclaimed. It follows the same rules as every other weak mechanism.

  • It is global: all callers of unique.Make share one map per type, which is the point, and also the reason for concurrency-friendly internals. Interning very large numbers of short-lived values can still cost time.

Interning that is local to a data structure (a custom map[string]string used while parsing, discarded afterwards) is still a fine technique; reach for unique when the canonical set is long-lived or process-wide.

Staying alive: runtime.KeepAlive

The inverse problem of finalization is premature finalization. Reachability is decided by liveness analysis, not by scope: an object is dead after its last mention. If the object’s cleanup (or finalizer, or weak pointer) releases a resource that the program is still using through a raw copy, the resource can be released while it is in use.

runtime.KeepAlive(x) marks its argument as reachable at that point, so the object cannot be collected, and its cleanup or finalizer cannot run, before the call. In the next program the "device" is represented by a flag that the cleanup sets. slowRead stands for a system call that takes the raw descriptor while the garbage collector runs in another goroutine:

package main

import (
	"fmt"
	"runtime"
	"sync/atomic"
)

// Scanner owns a device descriptor. Its cleanup "closes" the device by
// setting a flag that lives outside the Scanner.
type Scanner struct {
	fd     int
	closed *atomic.Bool
}

func open(fd int) *Scanner {
	s := &Scanner{fd: fd, closed: new(atomic.Bool)}
	runtime.AddCleanup(s, func(c *atomic.Bool) { c.Store(true) }, s.closed)
	return s
}

// slowRead stands for a system call that takes the raw descriptor. While it
// runs, the garbage collector may run, too. It reports whether the device was
// closed underneath it.
func slowRead(fd int, closed *atomic.Bool) bool {
	for range 3 {
		runtime.GC()
		runtime.Gosched()
	}
	return closed.Load()
}

// readUnsafe never mentions s after loading its fields, so s may be collected
// (and its cleanup may run) while slowRead is still executing.
func (s *Scanner) readUnsafe() bool {
	return slowRead(s.fd, s.closed)
}

// readSafe keeps s reachable until the call has returned.
func (s *Scanner) readSafe() bool {
	defer runtime.KeepAlive(s)
	return slowRead(s.fd, s.closed)
}

func main() {
	for range 3 {
		fmt.Println("unsafe: device closed during read:", open(3).readUnsafe())
	}
	for range 3 {
		fmt.Println("safe:   device closed during read:", open(3).readSafe())
	}
}

readUnsafe loads s.fd and s.closed and never mentions s again, so s is dead while slowRead runs and its cleanup fires underneath the read. readSafe defers runtime.KeepAlive(s), which keeps s reachable until the function returns. The effect depends on the garbage collector’s timing in general; this loop makes it deterministic enough to show, and it is exactly the bug that appears in production as a rare "file already closed" under load.

Guidelines for KeepAlive:

  • call it (usually with defer) after the last point where the object must remain reachable, in every method that passes a resource extracted from the object to something that outlives the method’s mention of the object, such as a system call, a cgo call or a goroutine;

  • it only prevents early cleanups and finalizers; it is not a substitute for the unsafe.Pointer rules (see unsafe and Low-Level Programming);

  • values stored in global variables, or reachable from one, are always reachable, so a global resource needs no KeepAlive;

  • it is also the right tool in tests that check a weak pointer is still non-nil after a collection (see Testing object death).

Tiny objects and other cases where nothing happens

Cleanups, finalizers and weak pointers all carry the same warnings, and the documentation repeats them for good reason. The runtime may batch tiny, pointer-free objects (on the order of 16 bytes or less) into one allocation slot to save space. If an unreferenced object always shares a slot with a referenced one, its cleanup may never run and its weak pointer may never become nil. The practical rules are:

  • attach cleanups and weak pointers to substantial objects, typically the wrapper struct for a resource (a struct with a pointer field is not tiny);

  • never attach one to a zero-size value (struct{}, [0]int): it may share an address with other zero-size values;

  • do not rely on a cleanup for an object allocated in a package-level variable initializer: the linker may place it in static memory;

  • GODEBUG=checkfinalizers=1 also tracks tiny blocks, so it reports a cleanup attached to one.

Pinning memory for C: runtime.Pinner

Goroutine stacks do move, and the language does not promise that heap objects stay where they are. cgo therefore forbids C code from keeping Go pointers around unless the rules allow it. runtime.Pinner (Go 1.21) is the sanctioned exception: a set of Go objects each pinned to a fixed location. Pin pins one object (any pointer, or unsafe.Pointer; pinning a non-Go pointer does nothing), and Unpin unpins all of them. A pointer to a pinned object may be stored in C memory or contained in Go memory passed to C functions, and C memory may retain a pinned pointer after the call returns, as long as the object stays pinned. The Pinner itself must stay alive across the cgo call (it unpins automatically some time after it becomes unreachable), and it is cheap to reuse. If the pinned object itself holds pointers to other Go objects that C code will access, those must be pinned separately.

The next program passes a C struct that lives in Go memory and holds a pointer to a Go array. Without pinning, the cgo pointer check rejects the call at run time:

Testing object death

The GC guide’s advice is to write tests precisely because these features are subtle, and to make them deterministic:

  • do not run these tests in parallel with other tests;

  • call runtime.GC to establish a baseline, to force weak pointers to nil and to queue cleanups and finalizers;

  • remember that runtime.GC does not wait for cleanups or finalizers to run, only until they are queued: inject a channel the cleanup writes to, or spin on the post-cleanup state with a deadline;

  • for a chain of objects with finalizers, call runtime.GC at least as many times as the longest chain;

  • run the tests with -race to find races between cleanups and the rest of the code.

The package below is a small slice of the shelf module: a Scanner whose descriptor is released by a cleanup, injected so that a test can observe it.

// Package scanner wraps a barcode-scanner device.
package scanner

import "runtime"

// Scanner owns a device descriptor.
type Scanner struct {
	fd int
}

// Open returns a scanner for fd. onRelease is called with the descriptor
// when the scanner is collected without having been closed.
func Open(fd int, onRelease func(fd int)) *Scanner {
	s := &Scanner{fd: fd}
	runtime.AddCleanup(s, onRelease, fd)
	return s
}

// FD returns the device descriptor.
func (s *Scanner) FD() int { return s.fd }

The tests use a helper that runs the collector until a condition holds, with a deadline, instead of sleeping for a fixed time:

package scanner

import (
	"runtime"
	"testing"
	"time"
	"weak"
)

// waitFor runs the garbage collector until cond reports true, so the test
// neither sleeps for a fixed time nor fails because a cycle came late.
func waitFor(t *testing.T, what string, cond func() bool) {
	t.Helper()
	deadline := time.Now().Add(5 * time.Second)
	for !cond() {
		if time.Now().After(deadline) {
			t.Fatalf("timed out waiting for %s", what)
		}
		runtime.GC()
		time.Sleep(time.Millisecond)
	}
}

func TestCleanupRunsWhenUnreachable(t *testing.T) {
	released := make(chan int, 1)
	func() {
		s := Open(5, func(fd int) { released <- fd })
		_ = s.FD()
	}() // s is unreachable once the function returns

	waitFor(t, "cleanup", func() bool { return len(released) == 1 })
	if fd := <-released; fd != 5 {
		t.Fatalf("cleanup got descriptor %d, want 5", fd)
	}
}

Other languages

Every garbage-collected platform offers some of these tools, and the differences explain Go’s cautious documentation.

Language Weak reference Death notification

Go

weak.Pointer[T], Value() returns nil after reclamation

runtime.AddCleanup (no resurrection), SetFinalizer (resurrects)

C#

WeakReference<T>.TryGetTarget

finalizers and SafeHandle; deterministic IDisposable

weak and unowned references (ARC)

C++

std::weak_ptr

Reference-counting languages observe death deterministically, so their Drop, deinit and destructors can release resources at a known point. A tracing collector cannot, which is why Go (like C# and Java) steers authors toward an explicit Close method and treats cleanups as a safety net.

Pitfalls

  • Relying on a cleanup to release a scarce resource. File descriptors, database connections and locks must be released with Close; the collector knows nothing about their limits.

  • Referencing the object from the cleanup. Through a closure, through the argument, or through a structure the argument holds. Direct cases panic; indirect ones silently leak. Run GODEBUG=checkfinalizers=1 in tests.

  • Expecting a cleanup before exit. Short-lived programs and os.Exit skip them. Flush and sync explicitly: a buffered writer must not depend on a cleanup.

  • Using a finalizer in new code. The only reason is a destruction order requirement; otherwise it resurrects the object, blocks freeing it for a cycle and breaks on cycles.

  • Long cleanups. A blocking cleanup stalls the cleanup queue; start a goroutine for slow work.

  • Treating Value() as stable. It may return nil between any two calls (it returns the pointer only while something else keeps the object alive). Always check for nil and have a fallback, such as reloading.

  • A weak map that is actually strong. A value in the map that points back at the key’s object keeps it reachable.

  • Weak pointers to interior fields. Pointers to different fields of one struct are different weak pointers.

  • Exposing the mechanism in the public API. The GC guide recommends encapsulating cleanups, weak pointers and finalizers inside a package, as unique does, and not letting users set their own finalizers on objects you return.

  • Not testing. These features can seem to work through many consecutive runs and still be wrong.

Version notes

  • Go 1.0: runtime.SetFinalizer and runtime.KeepAlive (KeepAlive since Go 1.7).

  • Go 1.21: runtime.Pinner.

  • Go 1.23: the unique package.

  • Go 1.24: runtime.AddCleanup, runtime.Cleanup and the weak package; the SetFinalizer documentation now points new code to AddCleanup.

  • Go 1.25: cleanups run concurrently and in parallel; GODEBUG=checkfinalizers=1 is added.

  • Go 1.26: the release notes list no changes to these APIs. The Green Tea collector became the default; it changes how the heap is scanned, not the semantics described here.

  • Go 1.27: no changes to runtime.AddCleanup, weak or unique. Examples were checked with go 1.27 in go.mod.

The Go books that predate Go 1.23 do not mention unique, weak or runtime.AddCleanup; they know only runtime.SetFinalizer, if at all. Code and advice written against them should use AddCleanup for new cleanup code and weak.Pointer for caches that must not retain their values. The old technique of keeping a map from key to value plus a finalizer to delete the entry is replaced by the weak-pointer cache above.
