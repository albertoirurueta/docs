Command-Line Interface

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Gradle 9.8.1 (released on 2026-10-07). Every example was run on JDK 26 on macOS on 2026-10-16, through the Gradle Wrapper of a scratch copy of the tidepool project (described below); the JDK 26 that started the client also ran the daemon, because no daemon JVM criteria were set. Console output is shown as printed, except that the scratch directory was shortened to <tidepool>, that the line Consider enabling configuration cache to speed up this build that Gradle prints at the end of a build run without the configuration cache and the daemon start-up notices were removed, and that long listings were cut with grep (the filter is part of the command shown) or with an explicit ellipsis line. Gradle 8.14.x was not installed for this page, so differences with it are taken from the official documentation and the release notes and are marked "not run here".

The command line is the primary way to drive Gradle: IDEs, CI servers and scripts all end up running the same gradlew command (see CI & IDE Integration). This page covers how to name the work to do (task selectors, project paths, abbreviations), how to change which tasks run (-x, --rerun, --continue), the reporting tasks that answer "what is in this build?", the options that change speed, logging and the environment, and continuous builds. Which options can be moved into gradle.properties is on Build Environment & Properties; the daemon options are on Gradle Daemon; the wrapper itself is on Gradle Wrapper. The equivalents in Ant and Maven are at the end.

The synopsis

The official page gives the structure of a Gradle command as follows:

gradle [taskName...] [--option-name...]
gradle [--option-name...] [taskName...]

Source: Gradle: Command-Line Interface

Four rules from that page govern everything below:

  • Options may come before or after the task names. ./gradlew build --parallel and ./gradlew --parallel build are the same command. The only exception is a task option (below), which must follow its task.

  • Several tasks are separated by spaces (./gradlew clean build) and run in one build, in the order their dependencies allow.

  • Options that take a value accept it with or without =, and the documentation recommends = (--console=plain).

  • Options that switch a behaviour on have a --no- inverse: --build-cache and --no-build-cache, --parallel and --no-parallel. Many long options also have a short one (--help and -h, --continuous and -t).

All of the examples use ./gradlew, the wrapper script, as the official page recommends; gradle (a locally installed distribution, see Installation) accepts exactly the same arguments. The built-in help prints the usage line and the options in groups:

./gradlew -h | head -12
To see help contextual to the project, use gradlew help

To see more detail about a task, run gradlew help --task <task>

To see a list of available tasks, run gradlew tasks

USAGE: gradlew [option...] [task...]

--                                   Signals the end of built-in options. Parses subsequent parameters as tasks or task options only.

Help:

(The first lines of the output are the hint about the contextual help task. The complete list is reproduced in the option reference below.)

A build that fails ends the process with a non-zero exit code: the runs on this page ended with 0 on success and 1 on failure, which is what CI servers and shell scripts test.

The scratch project

The examples use a copy of the running tidepool project with three subprojects: tidepool-model, tidepool-engine (depends on the model, uses Commons CSV) and tidepool-cli (depends on the engine, uses picocli and the application plugin). The settings file declares the repositories once and the subprojects; the root build file configures every subproject, including the JUnit 5 test dependencies. The versions of the libraries are written inline here to keep the page short; the recommended place for them is a version catalog, see Version Catalogs.

The test in tidepool-engine fails on request: it reads the system property tidepool.fail, which the root build file sets from the project property failTests (so -PfailTests=true makes one test fail). That gives the failure options something to act on.

Kotlin DSL
// settings.gradle.kts
rootProject.name = "tidepool"

dependencyResolutionManagement {
    repositories {
        mavenCentral()
    }
}

include("tidepool-model", "tidepool-engine", "tidepool-cli")

The subproject build files are one-liners. tidepool-model applies java-library; tidepool-engine applies it too and adds the dependencies; tidepool-cli applies application. The run task is told to format numbers in the English locale so that the output below does not depend on the machine:

    systemProperty("user.language.format", "en")
    systemProperty("user.country.format", "US")

Executing tasks

Task selectors and project paths

A task is named with its path: the project path, a colon, and the task name. A leading colon makes the path absolute from the root project:

./gradlew :tidepool-cli:run --args="../data/stations.csv BOS" -q
Boston: -0.662 m

(-q keeps only what the program prints. The decimal point follows the JVM default locale: this run used an English locale, and a locale such as Spanish prints -0,662 m. The relative path in --args is relative to the working directory of the run task, the project directory of tidepool-cli.) The ways of writing a task name behave as follows:

Command Meaning

./gradlew :tidepool-cli:jar

The jar task of that project, spelled with an absolute path.

./gradlew tidepool-cli:jar

The same task; the leading colon is optional when the command is run from the root.

./gradlew jar

A task selector: the jar task of every project that has one, reached from the root project where the command is run.

./gradlew :jar

The jar task of the root project only. The root project of tidepool has no Java plugin, so here it fails with Cannot locate tasks that match ':jar' as task 'jar' not found in root project 'tidepool'.

A selector is the common case. ./gradlew test ran the test tasks of all three subprojects above, and ./gradlew run found the single run task in tidepool-cli:

./gradlew run --dry-run
:tidepool-model:compileJava SKIPPED
:tidepool-engine:compileJava SKIPPED
:tidepool-cli:compileJava SKIPPED
:tidepool-cli:processResources SKIPPED
:tidepool-cli:classes SKIPPED
:tidepool-engine:processResources SKIPPED
:tidepool-engine:classes SKIPPED
:tidepool-engine:jar SKIPPED
:tidepool-model:processResources SKIPPED
:tidepool-model:classes SKIPPED
:tidepool-model:jar SKIPPED
:tidepool-cli:run SKIPPED

BUILD SUCCESSFUL in 918ms

Some selectors run only in the project the command is invoked on and not in its subprojects; the official page names help and dependencies as examples. When Gradle is invoked from inside a subproject directory the project name is omitted (cd tidepool-engine && ../gradlew test), and the -p option (--project-dir) starts the build in another directory without changing into it.

Source: Gradle: Executing tasks in multi-project builds

Several tasks, and their order

Tasks are run in the order their dependencies require, which may differ from the order on the command line when the command line does not constrain it. One constraint is kept: the command line order safety rule. ./gradlew clean build runs clean before build even if running them the other way round would be faster, because clean removes what build creates; the order depends on tasks declaring what they create, consume or remove (see Incremental Build).

Source: Gradle: Executing tasks, Gradle: Command line order safety

Task options

An option placed right after a task name belongs to that task, not to Gradle: run --args=... above, or test --tests=.... Task options are listed by help --task, which also prints the task’s type, its description and all the projects that have it:

./gradlew help --task test -q
Detailed task information for test

Paths
     :tidepool-cli:test (registered by plugin 'org.gradle.jvm-test-suite')
     :tidepool-engine:test (registered by plugin 'org.gradle.jvm-test-suite')
     :tidepool-model:test (registered by plugin 'org.gradle.jvm-test-suite')

Type
     Test (org.gradle.api.tasks.testing.Test)

Options
     --debug-jvm     Enable debugging for the test process. The process is started suspended and listening on port 5005.

     --no-debug-jvm     Disables option --debug-jvm.

     --fail-fast     Stops test execution after the first failed test.

     --no-fail-fast     Disables option --fail-fast.

     --test-dry-run     Simulate test execution.

     --no-test-dry-run     Disables option --test-dry-run.

     --tests     Sets test class or method name to be included (in addition to the test task filters), '*' is supported.

     --rerun     Causes the task to be re-run even if up-to-date.

Description
     Runs the test suite.

     verification

If a task defines an option with the same name as a built-in Gradle option (the official page uses the example of a profile option), the built-in one wins unless the task name is preceded by --: gradle mytask --profile passes --profile to Gradle, while gradle — mytask --profile=value passes it to the task. Every task also has the built-in --rerun option (below). How to declare an option on your own task is on Writing Custom Tasks.

Source: Gradle: Show task usage details, Gradle: Task options, Gradle: Declaring and using command line options

Name abbreviation

Neither the project nor the task name needs to be written in full. Any prefix that identifies it uniquely works, and camel-case patterns are expanded against camel-case and kebab-case names: tEn:tes is tidepool-engine:test, and :t-c:jar is :tidepool-cli:jar (the pattern t-c matches tidepool-cli because both words start with the given letters). Abbreviations also work after -x. When the abbreviation matches two names Gradle refuses to guess:

Choosing which tasks run

Forcing tasks to run

Gradle skips a task whose inputs and outputs have not changed (the task is reported UP-TO-DATE; see Incremental Build). Two options override that. --rerun is a task option and re-runs only the task it follows; --rerun-tasks is a Gradle option and re-runs every task in the build, as if everything had been cleaned, but without deleting the outputs.

The first run of :tidepool-engine:test after a clean, the second run (nothing changed), the third run with --rerun, and a run of two test tasks with --rerun-tasks (the filter keeps the task line, the result and the counts):

./gradlew clean
./gradlew :tidepool-engine:test | grep -E 'engine:test( |$)|BUILD|actionable'
./gradlew :tidepool-engine:test | grep -E 'engine:test( |$)|BUILD|actionable'
./gradlew :tidepool-engine:test --rerun | grep -E 'engine:test( |$)|BUILD|actionable'
./gradlew :tidepool-engine:test :tidepool-model:test --rerun-tasks | grep -E 'engine:test( |$)|BUILD|actionable'
> Task :tidepool-engine:test
BUILD SUCCESSFUL in 1s
5 actionable tasks: 5 executed

> Task :tidepool-engine:test UP-TO-DATE
BUILD SUCCESSFUL in 355ms
5 actionable tasks: 5 up-to-date

> Task :tidepool-engine:test
BUILD SUCCESSFUL in 673ms
5 actionable tasks: 1 executed, 4 up-to-date

> Task :tidepool-engine:test
BUILD SUCCESSFUL in 1s
7 actionable tasks: 7 executed

(The four outputs are printed one after the other, separated by blank lines; the clean output is omitted.) Note the counts: --rerun executed one task and left the four it depends on up to date, while --rerun-tasks executed all seven.

Source: Gradle: Forcing tasks to execute, Gradle: Built-in task options

When a task fails: --continue

By default Gradle stops at the first task failure, which shortens the build and avoids cascades of unrelated errors. --continue runs every task whose own dependencies succeeded and reports all the failures at the end. The tests of the engine are made to fail with -PfailTests=true; without --continue the model’s tests are never reached, with it they run:

./gradlew build -PfailTests=true | grep -E 'engine:test|model:test|BUILD|failing|FAILED|went wrong|Execution failed|AssertionFailed|tests completed|TideEngineTest'
./gradlew build -PfailTests=true --continue | grep -E 'engine:test|model:test|BUILD|failing|FAILED|went wrong|Execution failed|AssertionFailed|tests completed|TideEngineTest'
> Task :tidepool-engine:testClasses UP-TO-DATE
> Task :tidepool-engine:test FAILED
TideEngineTest > failsOnRequest() FAILED
    org.opentest4j.AssertionFailedError at TideEngineTest.java:24
2 tests completed, 1 failed
* What went wrong:
Execution failed for task ':tidepool-engine:test'.
> There were failing tests. See the report at: file://<tidepool>/tidepool-engine/build/reports/tests/test/index.html
BUILD FAILED in 603ms

> Task :tidepool-engine:testClasses UP-TO-DATE
> Task :tidepool-engine:test FAILED
TideEngineTest > failsOnRequest() FAILED
    org.opentest4j.AssertionFailedError at TideEngineTest.java:24
2 tests completed, 1 failed
> Task :tidepool-model:testClasses UP-TO-DATE
> Task :tidepool-model:test
* What went wrong:
Execution failed for task ':tidepool-engine:test'.
> There were failing tests. See the report at: file://<tidepool>/tidepool-engine/build/reports/tests/test/index.html
BUILD FAILED in 801ms

(The two outputs are printed one after the other, separated by a blank line.) The second build still ends with BUILD FAILED and exit code 1; --continue changes what is executed, not the verdict. --no-continue is the inverse and is the default. A task is skipped even under --continue when something it depends on failed: tests do not run when the code they test does not compile. --continue is the natural option for CI, where one run should report all failing modules and all failing checks; the failure of the test task here also names the HTML report to open.

Source: Gradle: Continue the build after a task failure

Running the application

The run task of the application plugin passes --args to the program’s main method. The program exits with 1 for an unknown station, and the task turns a non-zero exit value into a build failure:

./gradlew :tidepool-cli:run --args="../data/stations.csv XXX" | grep -E 'Unknown|BUILD|FAILED|went wrong|non-zero'
> Task :tidepool-cli:run FAILED
Unknown station: XXX
* What went wrong:
> Process 'command '/Library/Java/JavaVirtualMachines/jdk-26.jdk/Contents/Home/bin/java'' finished with non-zero exit value 1
BUILD FAILED in 727ms

Source: Gradle User Manual: Command-Line Interface, running applications, Gradle User Manual: The Application Plugin

Looking at the build

Gradle ships reporting tasks that answer questions about a build without changing anything. They are ordinary tasks and take part in the usual selection rules (the "run only in the project invoked on" ones are projects, dependencies, properties and help).

Projects and tasks

projects prints the project hierarchy and the directory of each subproject:

./gradlew projects -q
Projects:

------------------------------------------------------------
Root project 'tidepool'
------------------------------------------------------------

Root project 'tidepool'
+--- Project ':tidepool-cli'
+--- Project ':tidepool-engine'
\--- Project ':tidepool-model'

Project locations:

project ':tidepool-cli' - /tidepool-cli
project ':tidepool-engine' - /tidepool-engine
project ':tidepool-model' - /tidepool-model

Log levels and stack traces

The default log level is lifecycle. The options, from least to most verbose, are -q (--quiet, errors only), -w (--warn), the default, -i (--info) and -d (--debug, which includes the normal stack trace). The property org.gradle.logging.level sets the same thing from gradle.properties. A small build that logs one message at each level shows what each option keeps:

Kotlin DSL
// build.gradle.kts
tasks.register("levels") {
    doLast {
        logger.error("error message")
        logger.quiet("quiet message")
        logger.warn("warn message")
        logger.lifecycle("lifecycle message")
        logger.info("info message")
        logger.debug("debug message")
    }
}

The console

--console takes auto (default: rich on a terminal, plain otherwise), plain, colored, rich and verbose; plain is the default when the output is not a terminal, which is why the listings on this page have no progress bar. verbose prints the task names and outcomes as in Gradle 3.5 and earlier. --console-unicode allows or forbids Unicode characters, and org.gradle.console sets the mode from a property.

Since Gradle 9.6 the NO_COLOR environment variable is honoured: when it is set and non-empty, colour is suppressed while the other styling (bold, underline, progress bars) is kept. Continuous builds

-t (--continuous) keeps Gradle running after the tasks have finished and runs them again whenever the inputs of the tasks change. It needs file system watching (so it does not work with --no-daemon), waits for a quiet period after a change before building (the property org.gradle.continuous.quietperiod, in milliseconds), and, in a terminal, ends with CTRL-D. This run was time-bounded: the build was started in the background, the Java source of the model was edited after twelve seconds (a comment line appended, then removed again afterwards), and the process was stopped after another eight seconds, because without a terminal there is no CTRL-D:

sleep 12; echo "// edit" >> tidepool-model/src/main/java/io/tidepool/model/Height.java
sleep 8; kill %1

> Task :tidepool-model:test UP-TO-DATE

IDEs have their own continuous compilation, and the official page suggests running ./gradlew <task> --continuous in a terminal next to the IDE.

These options choose the files and properties a build starts from. Their long-term home is gradle.properties and the environment (see Build Environment & Properties); on the command line they are the per-run override:

Gradle 8.14 and the books

The command line of Gradle 8.14 (the last 8.x line) is the same as above for everything that is not tagged with a release in this page, but four additions are missing there. Not run here, taken from the release notes: --task-graph appeared in 9.1, tasks --provenance in 9.5, and --non-interactive and NO_COLOR in 9.6. Gradle 8.14 can run on a JVM as old as 8, while Gradle 9 needs JVM 17 or later to run the build (the wrapper, the client and the Tooling API client can still start on JVM 8); every example here started on JDK 26. How this reads for a migration from 8.14 is on Upgrading Gradle.

The command-line text of the Gradle 1.x books is only partly current:

Old text or practice Today

--daemon to opt in to the daemon

The daemon has been the default since Gradle 3.0; --no-daemon switches it off. See Gradle Daemon.

-u (--no-search-upward) to stop the search for settings.gradle

Removed in Gradle 5.0 (the upgrade notes say all builds need a settings file). Since Gradle 7.0 a build without a settings file is an error, except for init and diagnostic flags such as --version.

--recompile-scripts, -Dtest.single=..., -Dtest.debug

Removed in Gradle 5.0; use test filtering (test --tests=...) and test --debug-jvm.

task name << { } in build scripts

Removed in 5.0; see Tasks.

Source: Gradle: Upgrading from Gradle 4.x to 5.0, potential breaking changes, Gradle: Upgrading from Gradle 6.x to 7.0, Gradle 9.1.0 release notes, Gradle 9.6.0 release notes
