Gradle Ant Integration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Gradle 9.8.1 and was run on 2026-10-16 on JDK 26 (the daemon and the compiler both ran on JDK 26; no toolchain was involved). Every example was run through the wrapper, once with Kotlin DSL build files and once with Groovy DSL build files, and the console output is the same in both apart from the timings, the order of unrelated tasks and the messages that are stated below. The scratch copies pointed their wrapper at a local copy of the same distribution archive; the properties file that a real project commits is

The commands use --console=plain. In the listings the "Consider enabling configuration cache" hint, the link to the problems report and the daemon start-up line are left out, and the scratch directory is shown as /work/ant-integration. Where a listing is shortened the shortening is marked with a line of three dots on its own. The Ant comparison runs used Apache Ant 1.10.18 and Ivy 2.6.0. Gradle 8.14.x was not installed here, so statements about it come from the official documentation and are labelled "not run here".

Gradle can use Ant in two ways, and they answer two different questions. The first is using Ant’s tasks (javac, zip, checksum, a company’s own deploy task) from a Gradle build script, where Gradle is the build and Ant is a library of steps. The second is importing an Ant build, where every target of a build.xml becomes a Gradle task, so that an Ant build can be adopted by Gradle first and rewritten afterwards. Both are old features and both are still supported in 9.8.1, but they have a cost that did not exist when they were written: neither of them works with the configuration cache that is the preferred way to run Gradle since 9.0, with one exception that is shown below. The page ends with the migration of the tidepool Ant and Ivy build, one verified stage at a time. The shorter version of that migration, next to the Ant to Maven and Ivy to Resolver Ant Tasks routes, is in Migrating Between Tools; the Maven direction is Migrating from Maven.

Source: Gradle User Manual: Using Ant from Gradle; Gradle User Manual: Migrating Builds From Apache Ant

Not supported. Gradle turns the cache off for the whole build and says so.

The Ant that is inside Gradle

Gradle does not call the ant command and does not use an installed Ant. It carries its own Ant, as libraries, and the ant object runs the tasks in that one. Using Ant tasks and types

The ant property of a build script is an AntBuilder. You run an Ant task by calling a method with the task’s name, pass the XML attributes as named arguments, pass nested text as the first plain argument, and pass nested elements in a closure. The translation from the XML that an Ant user knows is mechanical, and Kotlin needs one extra wrapper because the Kotlin compiler cannot call methods that exist only at run time.

Ant XML Groovy DSL Kotlin DSL

<echo message="hi"/>

ant.echo(message: 'hi')

ant.withGroovyBuilder { "echo"("message" to "hi") }

<echo>hi</echo>

ant.echo('hi')

ant.withGroovyBuilder { "echo"("hi") }

<zip destfile="a.zip"> <fileset dir="d"/> </zip>

ant.zip(destfile: 'a.zip') { fileset(dir: 'd') }

"zip"("destfile" to "a.zip") { "fileset"("dir" to "d") } inside withGroovyBuilder

<path id="cp"> ... </path> (a type)

ant.path(id: 'cp') { ... } returns the Path

"path"("id" to "cp") { ... } returns the Path, cast it with as Path

A task name with a hyphen is a string in both languages (ant.'check-stations'(...) in Groovy, "check-stations"(...) in Kotlin), which the custom task example below uses. The example project has a data directory with the tidepool stations.csv and a libs directory with commons-csv-1.14.1.jar; the tasks echo a message, copy, zip and checksum the data, and list a path:

        }

tasks.register("pack") {

The ant object of the project and of the task

There are two ant objects. Every Project has one, and every Task has one too (Task.ant, an AntBuilder of its own). Inside tasks.register("x") { doLast { ant... } } the name ant resolves to the task’s, because the task is the closest receiver. Custom Ant tasks and Ant libraries

A custom Ant task is a Java class that extends org.apache.tools.ant.Task (see Writing Custom Tasks for the Ant side). The tidepool build has one, CheckStations, which checks the header and the length of the stations file. It was compiled against the Ant 1.10.18 ant.jar with --release 17 and packaged with the jar tool, so that the same JAR runs under the standalone Ant and under the Ant inside Gradle:

package io.tidepool.ant;

import java.io.IOException;
import java.nio.file.Files;
import java.util.List;
import org.apache.tools.ant.BuildException;
import org.apache.tools.ant.Task;

/** Ant task: fails the build when a stations CSV is malformed or too short. */
public class CheckStations extends Task {
    private java.io.File file;
    private int min = 1;

    public void setFile(java.io.File file) { this.file = file; }
    public void setMin(int min) { this.min = min; }

    @Override
    public void execute() {
        if (file == null) {
            throw new BuildException("The file attribute is required");
        }
        try {
            List<String> lines = Files.readAllLines(file.toPath());
            if (lines.isEmpty() || !lines.get(0).equals("id,name,latitude,longitude,constituents")) {
                throw new BuildException(file + " must start with the header id,name,latitude,longitude,constituents");
            }
            int stations = lines.size() - 1;
            if (stations < min) {
                throw new BuildException(file + " has " + stations + " stations, at least " + min + " required");
            }
            log("Checked " + stations + " stations in " + file.getName());
        } catch (IOException e) {
            throw new BuildException("Cannot read " + file, e, getLocation());
        }
    }
}
javac --release 17 -cp apache-ant-1.10.18/lib/ant.jar -d classes src/io/tidepool/ant/CheckStations.java
jar --create --file tools/tidepool-ant-tasks.jar --date 2026-10-16T00:00:00Z -C classes .

Neither command prints anything. Gradle’s taskdef is Ant’s: it takes either a name and a classname, or a resource that is a properties file or an antlib, and a classpath. The manual says taskdef is usually the easier of the two for tasks, and builds the classpath from Gradle’s dependency management by putting the JAR in a configuration and passing asPath as the classpath. A configuration of its own keeps the Ant task JAR off the compile classpath of the code:

Kotlin DSL
// The custom Ant task, taken from a jar on a Gradle configuration instead of a taskdef in build.xml.
val antTasks = configurations.create("antTasks")

dependencies {
    antTasks(files("tools/tidepool-ant-tasks.jar"))
}

tasks.register("checkStations") {
    group = "verification"
    description = "Runs the custom Ant task check-stations"
    doLast {
        ant.withGroovyBuilder {
            "taskdef"(
                "name" to "check-stations",
                "classname" to "io.tidepool.ant.CheckStations",
                "classpath" to antTasks.asPath
            )
            "check-stations"("file" to "data/stations.csv", "min" to 3)
        }
    }
}

The task name has a hyphen, so Kotlin passes it as a string and Groovy quotes the method name. Note the prefix: [ant:check-stations] is the log message that the task wrote with log(...), and that is at Ant’s INFO priority, which Gradle hides by default. The output above is shown with a build file that raises the Ant INFO messages to Gradle’s lifecycle level; the next section explains the one line that does it (ant.lifecycleLogLevel). Without that line the task runs and prints nothing. The taskdef does the job of the taskdef element of a build.xml; nothing has to be copied into the Ant installation.

An Ant library from Maven Central

A task library is a JAR, and Gradle can resolve it. The Apache Ant Compress Antlib (org.apache.ant:ant-compress:1.5) is an Ant library, not part of the Ant inside Gradle (1.10.17), whose tasks are in the antlib namespace antlib:org.apache.ant.compress. It is also a good example of why the configuration is separate: the library declares a dependency on org.apache.ant:ant with the version range [1.8.0,), so the resolution adds a second Ant (1.10.18, as the dependency report below shows) to that configuration, which is one more reason to keep Ant task libraries out of the configurations that the code uses.

Kotlin DSL
repositories {
    mavenCentral()
}

// Gradle ships Ant 1.10.17 and the core tasks only; optional Ant libraries need their own classpath.
val antLibs = configurations.create("antLibs")

dependencies {
    antLibs("org.apache.ant:ant-compress:1.5")
}

tasks.register("gzipStations") {
    val classpath = antLibs.incoming.files
    val out = layout.buildDirectory.dir("gz")
    doLast {
        ant.withGroovyBuilder {
            "taskdef"(
                "resource" to "org/apache/ant/compress/antlib.xml",
                "uri" to "antlib:org.apache.ant.compress",
                "classpath" to classpath.asPath
            )
            "mkdir"("dir" to out.get().asFile)
            "antlib:org.apache.ant.compress:gzip"("src" to "data/stations.csv", "destfile" to out.get().file("stations.csv.gz").asFile)
        }
        println(out.get().asFile.list()!!.sorted())
    }
}

This build is compatible with the configuration cache, with one change that the listing already contains: the task copies antLibs.incoming.files into a local variable instead of using the Configuration object itself, because a Configuration cannot be stored. Ant properties and references

Ant keeps two global tables for a build: properties (strings that cannot be changed once they are set) and references (objects with an id, such as a path). The AntBuilder exposes both as maps, and also lets you use the Ant tasks that fill them:

Kotlin DSL

    doLast {
        ant.properties["buildName"] = "tidepool"
        ant.withGroovyBuilder {
            "property"("name" to "dataDir", "location" to "data")

        ant.withGroovyBuilder { "echo"("message" to "name=\${buildName} dataDir=\${dataDir}") }
        ant.withGroovyBuilder { "path"("id" to "libs.path", "location" to "libs") }
        println(ant.references["libs.path"].toString().substringAfterLast('/'))
        println(ant.properties["dataDir"].toString().substringAfterLast('/'))
    }
}
Groovy DSL

Importing an Ant build

ant.importBuild("build.xml") reads an Ant file and registers one Gradle task for every target. Dependencies between targets (depends) are kept, a target’s description becomes the task’s description, and the properties and references of the file become ant.properties and ant.references. The example Ant file has four targets and the Gradle build wires it up in four ways: it passes a property in before the import, renames what it imports, adds a Gradle task that an Ant target depends on, and attaches a Gradle action to an Ant target.

build.xml
<project name="tidepool-ant" default="hello" basedir=".">
    <property name="greeting" value="Hello"/>
    <property name="out.dir" location="build/ant"/>

    <target name="hello" description="Greets from Ant">
        <echo>${greeting}, from Ant</echo>
    </target>

    <target name="pack" depends="hello,stamp" description="Zips data/ (needs the Gradle task stamp)">
        <mkdir dir="${out.dir}"/>
        <zip destfile="${out.dir}/data.zip" basedir="data"/>
    </target>

    <target name="again" description="Calls hello through antcall">
        <antcall target="hello"/>
    </target>

    <target name="maybe" if="do.maybe" description="Runs only when do.maybe is set">
        <echo>maybe ran</echo>
    </target>
</project>
Kotlin DSL

ant.importBuild("build.xml") { antTargetName ->
    if (antTargetName == "stamp") antTargetName else "ant-$antTargetName"

        println("Gradle task stamp, greeting is ${ant.properties["greeting"]}")

}

// The Ant target "pack" names "stamp" in depends; "hello" gets an extra Gradle action.
tasks.named("ant-hello") {
    doLast {
        println("Hello, from Gradle")
    }
}

// Ant targets have no inputs or outputs; declare them to get UP-TO-DATE checking.
tasks.named("ant-pack") {
    inputs.dir("data")
    outputs.dir(layout.buildDirectory.dir("ant"))
}

The imported tasks are real Gradle tasks of the type org.gradle.api.tasks.ant.AntTarget; they have a path, a description, and dependencies, and you can configure them as you would configure any other task.

Renaming targets, and an Ant target that depends on a Gradle task

The one-argument importBuild keeps the Ant names, and the two-argument form takes a transformer that maps each name. Why rename? When a plugin that is applied to the project adds a task with the same name as an Ant target, the build stops; the case for jar is in Migrating Between Tools and the case for build and clean is in the migration below. A prefix is the simplest rule, but there is a trap in it. Gradle applies the transformer to every name in a depends attribute, not only to the targets that exist in the file. In the example, pack names stamp, which is a Gradle task. With the plain rule "ant-$antTargetName" the dependency becomes ant-stamp:

ant.importBuild("build.xml") { antTargetName -> "ant-$antTargetName" }
./gradlew ant-pack
FAILURE: Build failed with an exception.

* What went wrong:
Could not determine the dependencies of task ':ant-pack'.
> Imported Ant target 'ant-pack' depends on target or task 'ant-stamp' which does not exist

The Groovy build fails in the same way, and the rule that fixes it is the one in the build file above: the transformer returns the name unchanged for the names that are not Ant targets (stamp). Gradle looks the transformed name up among the Gradle tasks, so a Gradle task (stamp here) can be named in an Ant depends, as long as the transformer lets the name through.

Source: Gradle User Manual: Importing an Ant build

Passing properties to Ant

Properties flow from Gradle to Ant through ant.properties, and they have to be set before the import, because an Ant property that is already defined is not changed by a later property element. The first lines of the build file above do this for a Gradle project property:

Ant’s antcall and ant tasks start another target, or another build file, by name inside Ant. Gradle handles them, but what they run is the Ant target, not the Gradle task that was imported from it. In a copy of the example whose pack does not depend on stamp, the Ant file has a target

    <antcall target="hello"/>
</target>

and the Gradle build still has the extra action on ant-hello:

The Hello, from Gradle line of the ant-hello action did not run, because antcall called the Ant target hello and not the Gradle task ant-hello. Multi-project builds

In a multi-project build every project can import its own Ant file, which is the first step of the manual’s recipe: a Gradle build file with a single ant.importBuild line for each project that has a build.xml, and an empty one where there is none. A typical Ant multi-project build calls the build of the project that it needs with <ant dir=... target=...>. The example has two projects, util and web, and web builds util this way:

<project name="web" default="compile">
    <property name="root.dir" location=".."/>

    <target name="buildRequiredProjects">
        <ant dir="${root.dir}/util" target="build"/>
    </target>

    <target name="compile" depends="buildRequiredProjects" description="Compiles the web module">
        <echo>compiling web</echo>
    </target>
</project>

With only the import in web/build.gradle(.kts), ./gradlew :web:compile runs the util Ant target inside the web task:

> Task :web:buildRequiredProjects
[ant:echo] building util

> Task :web:compile
[ant:echo] compiling web

BUILD SUCCESSFUL in 648ms
2 actionable tasks: 2 executed

util was built by the buildRequiredProjects task of web, and the Gradle project util never took part: its tasks, caching and up-to-date checks were bypassed. The manual replaces the Ant detour with a task dependency between the Gradle projects and warns to remove the old one.

Kotlin DSL
ant.importBuild("build.xml")

// Replace the <ant dir="../util" target="build"/> detour with a Gradle task dependency.
tasks.named("compile") {
    setDependsOn(listOf(":util:build"))
}
Groovy DSL
ant.importBuild 'build.xml'

// Replace the <ant dir="../util" target="build"/> detour with a Gradle task dependency.
tasks.named('compile') {
    dependsOn = [':util:build']
}
> Task :util:build
[ant:echo] building util

> Task :web:compile
[ant:echo] compiling web

BUILD SUCCESSFUL in 675ms
2 actionable tasks: 2 executed

setDependsOn (Groovy: assigning dependsOn =) replaces the dependencies of compile, which is what removes buildRequiredProjects; dependsOn(...) would have added to them. The manual calls this less robust than Gradle’s project dependencies, but enough for the immediate problem; the real replacement is a project(":util") dependency once the two projects are native. The order the manual suggests is: leaf projects first (those with no dependencies on other projects of the build), then the projects that depend only on migrated ones, and finally remove the copy tasks that the unmigrated Ant builds needed. See Multi Project Builds.

Stage 2: compile with Gradle

Applying the Java Library plugin brings compileJava, assemble, build, clean and check. The manual’s recipe has four steps: apply the plugin before the import, rename the Ant targets that clash, point the source set at the existing layout, and rewire the dependencies. The plugin’s clean and build collide with the Ant targets of the same names, so the transformer renames those two. The sources are read from the Ant property src.dir and the output goes to classes.dir, so Gradle compiles exactly where the Ant build did. The dependencies are still the JARs that Ivy retrieved.

Kotlin DSL
plugins {
    `java-library`
}

group = "io.tidepool"
version = "1.0.0"

// Targets "build" and "clean" collide with the lifecycle tasks of the Java plugin; the others keep their names.
ant.importBuild("build.xml") { antTargetName ->
    if (antTargetName == "build" || antTargetName == "clean") "ant_$antTargetName" else antTargetName
}

// Reuse the layout of the Ant build through its properties.
sourceSets {
    main {
        java.setSrcDirs(listOf(ant.properties["src.dir"]))
        java.destinationDirectory.set(file(ant.properties["classes.dir"] as String))
    }
}

dependencies {
    // Still the jars that Ivy retrieved into lib/ by the Ant "resolve" target.
    implementation(fileTree("lib") { include("*.jar") })
}

tasks.compileJava {
    options.release = 17
    dependsOn("prepare", "resolve")
}

// "package" no longer waits for the Ant compile; "assemble" builds the Ant jar instead of Gradle's.
tasks.named("package") {
    setDependsOn(listOf(tasks.compileJava))
}

tasks.assemble {
    setDependsOn(listOf("package"))
}

The details of the Kotlin DSL fragment: java.setSrcDirs(listOf(...)) and java.destinationDirectory.set(...) configure the source directory set; dependsOn("prepare", "resolve") adds the Ant targets that make the directories and fetch the JARs; and setDependsOn(listOf(...)) replaces the dependencies, which is what detaches package from the Ant build target and assemble from Gradle’s own jar. The Groovy form assigns dependsOn = [...]. The jar task of the plugin is not used yet; the Ant package target still builds the jar.

The assignment options.release = 17 replaces the release="17" of the Ant javac. Gradle’s toolchains are the better way to say which JDK compiles, see Toolchains and Java Projects.

Stage 4: the custom Ant task

The manual gives two options for custom Ant tasks: use the existing task from Gradle, which is quick but needs the incremental build API for it to take part in up-to-date checks and has awkward Ant paths and filesets, or rewrite it as a Gradle task type, which is the better long-term choice because task types are typed, simpler and incremental. Both are shown.

The first is the taskdef in a Gradle task from the custom tasks section above, where the JAR sits on a configuration (checkStations there). It replaces the imported check-data, and check depends on it; for the log message to be visible the build file raises the Ant INFO messages to the lifecycle level, as in the logging section. At this stage the check-data Ant target and its taskdef can still stay in build.xml. They are unused.

The second is a task class with declared inputs and outputs. It does what the Ant task did, writes a report file so that Gradle has an output to track, and fails the same way. The class is in the build script here, because it is a few lines; in a real build it belongs to a build-logic included build or buildSrc (see Convention Plugins & Sharing Build Logic and Writing Custom Tasks). The stage also removes the rest of the Ant build: Gradle’s jar task writes the jar where the Ant package target did, so build.xml, ivy.xml, ivysettings.xml, tools and lib are all deleted and there is no ant.importBuild left.

// The custom Ant task, rewritten as a task type with declared inputs and outputs.
abstract class CheckStations : DefaultTask() {
    @get:InputFile
    @get:PathSensitive(PathSensitivity.NONE)
    abstract val stations: RegularFileProperty

    @get:Input
    abstract val minStations: Property<Int>

    @get:OutputFile
    abstract val report: RegularFileProperty

    @TaskAction
    fun check() {
        val file = stations.get().asFile
        val lines = file.readLines()
        if (lines.firstOrNull() != "id,name,latitude,longitude,constituents") {
            throw GradleException("$file must start with the header id,name,latitude,longitude,constituents")
        }
        val count = lines.size - 1
        if (count < minStations.get()) {
            throw GradleException("${file.name} has $count stations, at least ${minStations.get()} required")
        }
        report.get().asFile.writeText("$count stations\n")
        logger.lifecycle("Checked $count stations in ${file.name}")
    }
}

    group = "verification"
    description = "Checks data/stations.csv"
    stations = layout.projectDirectory.file("data/stations.csv")
    minStations = 3
    report = layout.buildDirectory.file("reports/stations.txt")
}

tasks.check {
    dependsOn(checkStations)
}
