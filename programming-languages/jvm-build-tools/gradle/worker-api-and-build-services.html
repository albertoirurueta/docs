Worker API & Build Services

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Gradle 9.8.1 (released 2026-10-07). Every example was run through the 9.8.1 wrapper on 2026-10-16, on macOS, with a JDK 26 daemon (the task classes were compiled by that JDK in buildSrc; no toolchain was involved), once with Kotlin DSL build files and once with Groovy DSL build files. The two builds share the same Java classes, so the output is the same apart from the order of lines that are produced by parallel work. Each example was run with --configuration-cache and is compatible with it; the one that is not (a task calling Task.project while it runs) is shown on purpose. Where a listing shows a line with only ..., output was left out. The listings leave out blank lines and the "Calculating task graph", "Reusing configuration cache" and "Configuration cache entry" lines; the daemon process id in the output (91866 here) and the ports and process ids of worker processes differ from run to run. Gradle 8.14 was not available here, so what the text says about 8.14 comes from the release notes and the user manual and is labelled "not run here".

A build is parallel at three levels, and this page is about the two lowest ones. Gradle’s --parallel option runs tasks of different projects at the same time; the Build Environment & Properties page lists it with org.gradle.workers.max. The Worker API runs the independent pieces of one task action at the same time, optionally in an isolated classloader or in a separate process. Shared build services are the objects that such concurrent tasks and workers share, and that can limit how many of them use a resource at once. A third API, dataflow actions, runs small pieces of work that are not tasks, such as reacting to the build result. The task side is on Writing Custom Tasks and the lazy Property types used for parameters on Lazy Configuration & Providers.

Source: Gradle: Worker API

The example build

The tidepool build used on all the Gradle pages predicts tide heights from harmonic constituents. For this page the build has a root project, which holds the data file and a tideTables task, and three small subprojects, tides-a, tides-b and tides-c, that apply a plugin from buildSrc. The classes live in buildSrc (see Writing Custom Tasks for the other places task classes can go). The data file is the one the other pages use:

BOS,Boston,42.3539,-71.0503,M2:1.35:15;S2:0.21:42;N2:0.28:350
HNL,Honolulu,21.3067,-157.8645,M2:0.14:90;K1:0.17:250;O1:0.10:230

The Worker API

A task action runs on one thread. If the action is a loop whose iterations do not depend on each other, such as one tide table per station, it can submit each iteration as a unit of work to a WorkerExecutor and let Gradle run them concurrently. Three types describe a unit of work:

  • WorkParameters is an interface with the inputs of one unit, declared as getters of lazy Property, RegularFileProperty or DirectoryProperty types. Gradle generates the implementation, as it does for task classes. The parameters must be Gradle-managed properties, not plain fields.

  • WorkAction<P> is an interface with an execute() method; you write an abstract class that implements it. It reads its inputs through getParameters(), which Gradle implements, and is created by Gradle for each unit.

  • WorkQueue (since 5.6) is what noIsolation(), classLoaderIsolation() or processIsolation() return; every unit submitted to one queue has the same isolation requirements.

The task gets the WorkerExecutor service by declaring an abstract getter annotated with @Inject. Here are the parameters, the action and the task:

TideParameters.java
package io.tidepool.build;

import org.gradle.api.file.RegularFileProperty;
import org.gradle.api.provider.Property;
import org.gradle.workers.WorkParameters;

/** The parameters of one unit of work: one station, one output file. */
public interface TideParameters extends WorkParameters {
    Property<String> getStationLine();

    RegularFileProperty getTableFile();
}
TideTableAction.java
package io.tidepool.build;

import java.io.IOException;
import java.nio.file.Files;
import java.util.ArrayList;
import java.util.List;
import org.gradle.workers.WorkAction;

/** One unit of work: a 24-hour tide table for one station (harmonic sum, as in the tidepool engine). */
public abstract class TideTableAction implements WorkAction<TideParameters> {
    @Override
    public void execute() {
        String[] f = getParameters().getStationLine().get().split(",");
        String id = f[0];
        System.out.printf("%s: thread=%s pid=%d classLoader=%s%n", id, Thread.currentThread().getName(),
                ProcessHandle.current().pid(), getClass().getClassLoader().getClass().getSimpleName());
        try {
            Thread.sleep(2000); // stands in for an expensive computation
            List<String> lines = new ArrayList<>();
            for (int hour = 0; hour < 24; hour++) {
                double sum = 0;
                for (String c : f[4].split(";")) {
                    String[] p = c.split(":");
                    double speed = switch (p[0]) {
                        case "M2" -> 28.984104;
                        case "S2" -> 30.0;
                        case "N2" -> 28.43973;
                        case "K1" -> 15.041069;
                        case "O1" -> 13.943036;
                        default -> 0;
                    };
                    sum += Double.parseDouble(p[1]) * Math.cos(Math.toRadians(speed * hour - Double.parseDouble(p[2])));
                }
                lines.add(String.format(java.util.Locale.ROOT, "%02d:00 %.3f", hour, sum));
            }
            Files.write(getParameters().getTableFile().get().getAsFile().toPath(), lines);
        } catch (IOException | InterruptedException e) {
            throw new RuntimeException(e);
        }
    }
}
TideTables.java
package io.tidepool.build;

import java.io.IOException;
import java.nio.file.Files;
import java.util.List;
import javax.inject.Inject;
import org.gradle.api.DefaultTask;
import org.gradle.api.file.DirectoryProperty;
import org.gradle.api.file.RegularFileProperty;
import org.gradle.api.provider.Property;
import org.gradle.api.tasks.Input;
import org.gradle.api.tasks.InputFile;
import org.gradle.api.tasks.OutputDirectory;
import org.gradle.api.tasks.PathSensitive;
import org.gradle.api.tasks.PathSensitivity;
import org.gradle.api.tasks.TaskAction;
import org.gradle.api.tasks.options.Option;
import org.gradle.workers.WorkQueue;
import org.gradle.workers.WorkerExecutor;

/** Writes one tide table per station, one work item per station. */
public abstract class TideTables extends DefaultTask {
    @InputFile
    @PathSensitive(PathSensitivity.NONE)
    public abstract RegularFileProperty getStations();

    @Input
    @Option(option = "isolation", description = "none, classloader or process")
    public abstract Property<String> getIsolation();

    @OutputDirectory
    public abstract DirectoryProperty getOutputDir();

    @Inject
    protected abstract WorkerExecutor getWorkerExecutor();

    @TaskAction
    public void run() throws IOException {
        WorkQueue queue = switch (getIsolation().get()) {
            case "none" -> getWorkerExecutor().noIsolation();
            case "classloader" -> getWorkerExecutor().classLoaderIsolation();
            case "process" -> getWorkerExecutor().processIsolation(spec ->
                    spec.forkOptions(options -> options.setMaxHeapSize("64m")));
            default -> throw new IllegalArgumentException("unknown isolation " + getIsolation().get());
        };
        List<String> lines = Files.readAllLines(getStations().get().getAsFile().toPath());
        for (String line : lines.subList(1, lines.size())) {
            String id = line.substring(0, line.indexOf(','));
            queue.submit(TideTableAction.class, parameters -> {
                parameters.getStationLine().set(line);
                parameters.getTableFile().set(getOutputDir().file(id + ".txt"));
            });
        }
    }
}

The action prints which thread, process and class loader it runs on, and sleeps for two seconds to stand in for a computation that is worth parallelising. The task chooses the isolation mode from an --isolation command-line option (@Option, covered on Writing Custom Tasks). getOutputDir() is declared as @OutputDirectory, so Gradle knows what the task produces. The task action itself only submits; Gradle waits for every submitted unit before it reports the task as finished. WorkQueue.await() (since 5.6) waits explicitly, for a task that needs the results before it continues.

Source: Gradle: Convert to the Worker API

Isolation modes

The three methods of WorkerExecutor trade isolation against start-up cost:

Method Where the unit runs Class path Cost and use

noIsolation()

a thread of the build daemon

the class loader the task class was loaded from; shared by all units, so static state is shared

the cheapest; units run concurrently but cannot be given a different library version

classLoaderIsolation()

a thread of the build daemon

a new class loader with the class path of the action plus the entries added with getClasspath() of the worker spec

a little more set-up; use it to run a different, compatible version of a library, or to keep static state of different units apart

processIsolation()

a separate Java process, a worker daemon

the class path of the action plus the entries added to the spec

the most expensive; use it for a different JVM, heap size, system properties or a library that is not safe to run in the Gradle JVM

Source: Gradle: Isolation modes

Worker daemons

With processIsolation() Gradle starts a JVM for the unit, or reuses an idle one that is compatible with what the unit asked for. The compatibility rules compare what is set on the worker spec with what each running worker was started with:

  • the Java executable must be the same;

  • the class path of the worker must contain exactly the requested entries;

  • the heap size of the worker must be at least the requested size; the default maximum heap is 512 MB, and forkOptions { maxHeapSize = "64m" } (as the TideTables task does) is a request;

  • the worker must have all requested JVM arguments, system properties, environment variables and bootstrap class path entries (it may have more);

  • debug, enable-assertions and the default character encoding must be equal.

A worker daemon is session-scoped: it lives for one build and can be reused only inside it. Gradle stops idle workers when the build finishes or when memory runs low. Running the same processIsolation() build a second time shows it: the worker processes of the first run are gone and three new ones (new process ids) do the work, while the build daemon is the same one:

$ ./gradlew --configuration-cache clean tideTables --isolation=process
> Task :clean
> Task :tideTables
SF: thread=/127.0.0.1:53642 to /127.0.0.1:53640 workers pid=16769 classLoader=VisitableURLClassLoader
HNL: thread=/127.0.0.1:53644 to /127.0.0.1:53641 workers pid=16771 classLoader=VisitableURLClassLoader
BOS: thread=/127.0.0.1:53643 to /127.0.0.1:53639 workers pid=16770 classLoader=VisitableURLClassLoader
BUILD SUCCESSFUL in 3s
2 actionable tasks: 2 executed

A task that does not react to an interrupt of its thread within ten seconds makes Gradle shut the build daemon down, so work should respond to thread interruption to support Ctrl+C and task timeouts.

Source: Gradle: Worker daemons

Build services

A build service is an object that Gradle creates and owns for the duration of one build. Tasks, other services, artifact transforms and work actions use it to share state or a resource: a cache of pre-computed values, a web server or database used by the tests, a rate limiter. Gradle creates the service on first use, closes it when the last user is done if it is AutoCloseable, and can limit how many tasks use it at the same time. Build services are compatible with the configuration cache. They are also the configuration-cache-compatible place for build-wide state that older builds kept in a static field or in a gradle.taskGraph listener.

Source: Gradle: Shared build services

Defining a service

A service is an abstract class that implements BuildService<P>, where P extends BuildServiceParameters (or is BuildServiceParameters.None). The parameters follow the Gradle-managed property rules: JavaBeans getters of Property types. Gradle implements getParameters(). A service must be thread safe, because several tasks may call it at once.

ArchiveService.java
package io.tidepool.build;

import java.util.concurrent.atomic.AtomicBoolean;
import java.util.concurrent.atomic.AtomicInteger;
import org.gradle.api.provider.Property;
import org.gradle.api.services.BuildService;
import org.gradle.api.services.BuildServiceParameters;

/** A shared, thread-safe resource: pretends to be a single-writer archive. */
public abstract class ArchiveService implements BuildService<ArchiveService.Params>, AutoCloseable {
    public interface Params extends BuildServiceParameters {
        Property<String> getName();
    }

    private final long created = System.nanoTime();
    private final AtomicBoolean opened = new AtomicBoolean();
    private final AtomicInteger writes = new AtomicInteger();

    public void write(String who) throws InterruptedException {
        if (opened.compareAndSet(false, true)) {
            System.out.println("[archive] opened " + getParameters().getName().get());
        }
        System.out.printf(java.util.Locale.ROOT, "[archive] %s start at %.1fs%n", who, seconds());
        Thread.sleep(1500);
        writes.incrementAndGet();
        System.out.printf(java.util.Locale.ROOT, "[archive] %s end   at %.1fs%n", who, seconds());
    }

    public int getWrites() {
        return writes.get();
    }

    private double seconds() {
        return (System.nanoTime() - created) / 1e9;
    }

    @Override
    public void close() {
        if (opened.get()) {
            System.out.println("[archive] closed after " + writes.get() + " writes");
        }
    }
}

The write method stands in for an operation that must not be run by too many tasks at once: it announces its start, waits 1.5 seconds and announces its end, with times counted from the creation of the service. Because the service implements AutoCloseable, Gradle calls close() when it discards the service, sometime between the last task that used it and the end of the build.

Source: Gradle: Implementing a build service

Registering a service and connecting it to a task

A service is registered once with gradle.sharedServices.registerIfAbsent(name, type) { ... }, usually by a plugin. Registering does not create the instance. The same name registered again (by the plugin applied in another project) returns the existing registration, so every project shares one instance; a build service is scoped to a build, not to a project. There are two ways for a task to receive the service:

  • a property annotated with @ServiceReference("archive"), as the example below does; Gradle assigns the service registered under that name (or of that type, when the name is left out and only one matches) and records that the task uses it;

  • a property annotated with @Internal, assigned with the provider that registerIfAbsent returned, plus a call to usesService(provider) on the task. Both are needed with @Internal: without the declaration, Gradle does not know the task uses the service and cannot apply the limit described below.

Any other annotation on a service property is not supported; a service cannot be a task input.

ArchiveTask.java
package io.tidepool.build;

import org.gradle.api.DefaultTask;
import org.gradle.api.provider.Property;
import org.gradle.api.services.ServiceReference;
import org.gradle.api.tasks.Input;
import org.gradle.api.tasks.TaskAction;

/** Writes to the shared archive; Gradle wires the service through the reference. */
public abstract class ArchiveTask extends DefaultTask {
    @ServiceReference("archive")
    protected abstract Property<ArchiveService> getArchive();

    @Input
    public abstract Property<String> getLabel();

    @TaskAction
    public void run() throws InterruptedException {
        getArchive().get().write(getLabel().get());
    }
}
ArchivePlugin.java
package io.tidepool.build;

import javax.inject.Inject;
import org.gradle.api.Plugin;
import org.gradle.api.Project;
import org.gradle.api.flow.FlowProviders;
import org.gradle.api.flow.FlowScope;

public abstract class ArchivePlugin implements Plugin<Project> {
    @Inject
    protected abstract FlowScope getFlowScope();

    @Inject
    protected abstract FlowProviders getFlowProviders();

    @Override
    public void apply(Project project) {
        int max = project.getProviders().gradleProperty("archive.maxParallelUsages")
                .map(Integer::parseInt).getOrElse(1);
        project.getGradle().getSharedServices().registerIfAbsent("archive", ArchiveService.class, spec -> {
            spec.getParameters().getName().set("tide-archive");
            if (max > 0) {
                spec.getMaxParallelUsages().set(max);
            }
        });
        project.getTasks().register("archive", ArchiveTask.class, task -> task.getLabel().set(project.getPath()));
        if (project == project.getRootProject()) {
            getFlowScope().always(BuildSummary.class, spec ->
                    spec.getParameters().getStatus().set(getFlowProviders().getBuildWorkResult()
                            .map(result -> result.getFailure().isPresent() ? "FAILED" : "OK")));
        }
    }
}

Source: Gradle: Registering a build service to be consumed via @ServiceReference task properties

The plugin reads the Gradle property archive.maxParallelUsages (default 1) and sets getMaxParallelUsages() on the registration when it is greater than zero. With a limit of one, the four archive tasks (one in the root project and one in each subproject) cannot overlap, although the configuration cache lets Gradle run them all at once, as a later section explains. Without a limit, they run together:

$ ./gradlew --configuration-cache archive
> Task :archive
[archive] opened tide-archive
[archive] : start at 0.0s

The start and end times are counted from the creation of the service: with one usage at a time the four writes follow each other (0.0 to 6.0 seconds, six seconds for the build), without a limit the four run at the same time (1.5 seconds of work, two seconds for the build). Changing the Gradle property invalidated the configuration cache entry, which is why the second run recalculates the task graph. The limit applies when the consuming property is @ServiceReference, or @Internal with usesService. Gradle does not discover indirect use: a service used only by another service must be declared on the task as well, with another @ServiceReference property or usesService.

Using a service from a worker, a configuration action or a listener

A work action receives a service the same way as other inputs: a Property<ServiceType> in its parameters, set from the task’s own reference. The user manual states two limits: this works with noIsolation() only, because the service cannot be passed to a classloader-isolated or process-isolated worker, and the service should be used at configuration time (provider.get()) only when that is really needed, because services are usually expensive to create (not run here; both limits are quoted from the manual).

A service that also implements OperationCompletionListener can receive task-finish events when it is registered with the BuildEventsListenerRegistry service (onTaskCompletion(serviceProvider)), which is the replacement the configuration cache documentation gives for the gradle.taskGraph.afterTask callback (not run here; see the manual page).

Source: Gradle: Using a build service with the Worker API

Build services, tasks and the configuration cache

Build services are serialised into the configuration cache entry as their parameters, and the instance is created again in every build, so a service must not keep state that has to survive from one build to the next. Task classes must not reach into the project at execution time. This is a classic mistake in a task that wants to know where it belongs; the example below uses getProject() in @TaskAction:

    @TaskAction
    public void run() throws InterruptedException {
        getArchive().get().write(getProject().getPath());
    }

Source: Gradle: Using the Project at execution time

The configuration cache has a second effect on the example. With it enabled, Gradle runs the tasks of a build in parallel, even within one project, subject to the declared dependencies; the --parallel option no longer controls this, and --no-parallel or org.gradle.parallel=false has no effect on a build that uses the cache. The build services, not the order of tasks, then have to be what keeps tasks apart: that is why maxParallelUsages is useful. The user manual says builds that depend on sequential tasks should wire inputs and outputs, or use build services to limit concurrency (see Lazy Configuration & Providers for the properties involved).

Dataflow actions

Some work does not fit a task, such as reacting to the outcome of the whole build. A dataflow action is a small, isolated piece of work that Gradle runs as soon as all its input parameters are available. It replaces the gradle.buildFinished callback, which does not work with the configuration cache. Dataflow actions are incubating in 9.8.1 (see Versions, Compatibility & Release History for what incubating means) and the API may change.

You implement FlowAction<P>, where P extends FlowParameters; every parameter must be annotated, with @Input or with @ServiceReference for a build service. You do not create the action; you ask the FlowScope service to run it with always(actionClass, spec -> ...), in the scope of the build. A parameter that should wait for the build result is derived from the provider FlowProviders.getBuildWorkResult(), which makes Gradle run the action after the work is done. The example’s BuildSummary takes the result and the archive service, and prints only if the archive was used:

BuildSummary.java
package io.tidepool.build;

import org.gradle.api.flow.FlowAction;
import org.gradle.api.flow.FlowParameters;
import org.gradle.api.provider.Property;
import org.gradle.api.services.ServiceReference;
import org.gradle.api.tasks.Input;

/** A dataflow action: runs once the build result is known. */
public abstract class BuildSummary implements FlowAction<BuildSummary.Params> {
    public interface Params extends FlowParameters {
        @ServiceReference("archive")
        Property<ArchiveService> getArchive();

        @Input
        Property<String> getStatus();
    }

    @Override
    public void execute(Params parameters) {
        int writes = parameters.getArchive().get().getWrites();
        if (writes > 0) {
            System.out.println("[summary] build " + parameters.getStatus().get() + ", archive writes: " + writes);
        }
    }
}

The plugin shown earlier registers it in the root project, which is the line starting getFlowScope().always(. It produced the [summary] line at the end of the two archive runs above, after the last task, and [archive] closed after 4 writes follows it as Gradle closes the service. A failed build calls the action as well, with status FAILED. FlowScope and FlowProviders can be injected into project and settings plugins.

Source: Gradle: Dataflow actions

Where the book is outdated

Gradle in Action (Gradle 1.7, 2014) has neither of these APIs. The Worker API arrived in 3.5 (WorkerExecutor is annotated "Since: 3.5" in the API docs), in its current WorkAction form in 5.6 and stable in 7.0; shared build services became stable in 7.4; dataflow actions are newer still. The book’s mechanisms for the same needs, gradle.buildFinished, gradle.taskGraph listeners and static fields, either have been removed or do not work with the configuration cache; the replacements are the build services and dataflow actions above. The book’s idea of parallel execution is the --parallel option across projects; running the tasks of one project in parallel, which the configuration cache does, did not exist.

Summary

  • The Worker API splits one task action into units that run concurrently: WorkParameters and WorkAction describe a unit, WorkerExecutor gives a WorkQueue in one of three isolation modes.

  • noIsolation() is a thread with a shared class loader, classLoaderIsolation() a thread with its own, processIsolation() a worker daemon; worker daemons live for one build and are reused only inside it.

  • The number of concurrent units is limited by --max-workers / org.gradle.workers.max.

  • A build service is a thread-safe, parameterised, lazily created object shared by a build; register it with registerIfAbsent and consume it with @ServiceReference or @Internal plus usesService.

  • maxParallelUsages limits how many tasks use a service at once, which matters because the configuration cache runs tasks in parallel.

  • Services are not available to class-loader or process-isolated workers.

  • A task must not call Task.project while it runs; copy the value into an @Input property.

  • Dataflow actions (incubating) replace buildFinished: derive the parameters from FlowProviders.getBuildWorkResult().
