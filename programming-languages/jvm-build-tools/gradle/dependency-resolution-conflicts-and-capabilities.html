Gradle Dependency Resolution, Conflicts & Capabilities

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Resolving dependencies is the part of a Gradle build that takes the most thought and goes wrong in the most surprising ways: a library that nobody declared is on the classpath, a version is not the one that was written in the build file, or two libraries that do the same job are both there. This page explains what Gradle does, step by step, and then shows the three tools that Gradle gives you for the three kinds of surprise: the rules for version conflicts, the capability mechanism for two modules that provide the same functionality, and exclusions for a dependency that should not be there at all. Declaring dependencies and the configurations they live in is on Declaring Dependencies & Configurations; rich versions, platforms and constraints in depth are on Platforms, Constraints & Rich Versions; forcing versions, substitution and metadata rules are on Resolution Rules & Substitution; variants and attributes are on Variant-Aware Resolution & Module Metadata. The vocabulary that all three build tools share (coordinates, transitive dependencies, scopes) is on Dependency Management Fundamentals, which also runs one version conflict through Ant with Ivy, Maven and Gradle; this page goes deeper on the Gradle half of that comparison.

The resolution model

Dependency resolution in Gradle is a two-step process. In the first step, graph resolution, Gradle builds the dependency graph from the declared dependencies and the metadata of the modules they point to. In the second step, artifact resolution, it turns the nodes of that graph into files and fetches them. The two steps are separate on purpose: many questions (which version? why is this here?) can be answered from the graph alone, without downloading a single JAR.

flowchart LR decl["Declared dependencies and constraints of one resolvable configuration"] --> gres["Graph resolution: read metadata, resolve conflicts, select a variant per component"] meta[("Repositories: POM, Gradle Module Metadata, ivy.xml")] --> gres gres --> rgraph["Resolved graph: components, variants, edges and selection reasons"] rgraph --> reports["Tasks and reports that need only the graph: dependencies, dependencyInsight"] rgraph --> ares["Artifact resolution: pick an artifact set per variant, transform if needed, download"] ares --> files["Files: the compile or runtime classpath"]

Source: Gradle User Manual: Dependency Resolution

Graph resolution

The documentation names the building blocks in the order Gradle meets them.

Term Meaning

Module

A published unit such as commons-io:commons-io. A dependency is a reference to a module.

Component

One version of a module, such as commons-io:commons-io:2.20.0.

Metadata

The description of a component in the repository: a Gradle Module Metadata file (.module), a Maven .pom or an Ivy ivy.xml.

Variant

A variation of a component for one use, such as the API a library exposes to compilation or the runtime elements it needs when executed. Each variant lists its own dependencies and its own files.

Attributes

Key-value pairs (org.gradle.usage = java-runtime) that describe a variant and that Gradle matches against the request of the configuration being resolved.

Node and edge

The graph is made of nodes, one per selected variant, and edges, one per dependency between two variants.

Each resolvable configuration resolves to its own graph. That is why compileClasspath and runtimeClasspath of the same project can contain different versions and even different modules: they ask for different attributes, and the metadata answers differently.

The loop that builds the graph works on one node at a time, starting from a queue that contains only the root node, which is the resolvable configuration itself. For every node it takes out of the queue, Gradle evaluates the node’s dependencies, decides which version each of them targets (this is where conflict resolution happens), downloads the metadata of all the components involved, selects a variant of each, and puts the selected variants back into the queue. The loop ends when the queue is empty. The documentation points out that this alternates between parallel metadata downloads and single-threaded logic.

Source: Gradle User Manual: Graph Resolution Flow

Metadata comes from the repositories, and the rules for fetching it explain several surprises.

  • For a concrete version, Gradle checks the repositories in the order in which they are declared and stops at the first one that has metadata (a .module, a .pom or an ivy.xml) for it; a module that has only an artifact file ranks below one with metadata. All artifacts of the component are then taken from that same repository.

  • For a dynamic version (1.+, latest.release) Gradle must know which versions exist, so it asks all the repositories and does not stop at the first answer. For Maven repositories it reads maven-metadata.xml; for Ivy repositories it lists a directory.

  • A POM with a parent is resolved recursively, and everything, including misses, is stored in the dependency cache.

  • A repository that cannot be reached (unknown host, repeated connection failures, HTTP 5xx) is no longer checked for the rest of the build, after Gradle has retried with increasing wait times. Gradle does not move on to the next repository unless told to, so the resolution usually fails, which keeps builds reproducible: a build that silently skipped a faulty repository could give different results once it came back. The Repositories & Content Filtering page covers repository declaration and filtering, and Dependency Locking, Verification & Caching covers the cache.

  • mavenLocal() behaves like a cache of whatever Maven installed, so it can lack artifacts of a module whose metadata is there; the documentation warns about this in the same section.

Source: Gradle User Manual: How Gradle downloads dependencies

Variant selection, the step that matches the attributes of the configuration against the variants in the metadata, has its own page: Variant-Aware Resolution & Module Metadata.

Two kinds of conflict are settled during graph resolution. A version conflict is two requests for different versions of the same module. A capability (or implementation) conflict is two different modules that declare the same capability. Both are the subject of this page.

Source: Gradle User Manual: Graph Resolution, conflict resolution

Artifact resolution

Once the graph exists, Gradle maps each node to the files it needs. A variant can offer several artifact sets: the packaged JAR, the directory of compiled classes, the directory of resources, an archive of another type. For each node Gradle matches the requested attributes against the artifact sets it offers and picks one; if none matches, it tries to build a chain of artifact transforms that produces the requested form. How a project component hands out its classes directory instead of its JAR is the same mechanism.

The APIs that expose the result come in two groups. ResolutionResult gives the graph without downloading anything (components, variants, edges, selection reasons); the files of a configuration, an ArtifactCollection or an ArtifactView trigger artifact selection and the download. The older ResolvedConfiguration and LenientConfiguration APIs also trigger it and are in maintenance mode, so the documentation discourages them for new code.

Source: Gradle User Manual: Artifact Resolution, artifact sets and implicit artifact selection

Version conflicts

The highest version wins

When two paths of the graph request different versions of the same module, Gradle considers every requested version, wherever it appears in the graph, and by default selects the highest. The tidepool graph has such a conflict: tidepool-cli declares commons-io 2.11.0, while Commons CSV 1.14.1, reached through tidepool-engine, requires 2.20.0.

"Highest" has consequences. The default rule compares versions and nothing else, so a direct declaration of an older version cannot downgrade a library that needs a newer one: the 2.11.0 written in the cli build file is only a request, and it lost to a request that came from deeper in the graph. A newer version is also not always compatible; when the winner is a major version that nobody tested with the library that asked for the older one, the build compiles and the problem appears at run time. The two tools of the sections below, constraints and strictly, are the way to say what you want instead of accepting the default.

How versions are compared

The comparison is not alphabetical and not purely numeric. The versions of a module are split into parts at ., -, _ and +, and also where digits and letters meet (1a1 is 1.a.1). The parts are compared one by one: numbers numerically, a number is higher than a word (1.a is lower than 1.1), words alphabetically and case-sensitively, an extra numeric part makes a version higher (1.1 is lower than 1.1.0), and an extra word makes it lower (1.1.a is lower than 1.1). A few words are special: dev is lower than any other word, and rc, snapshot, final, ga, release and sp are higher than any other word, in that order.

Source: Gradle User Manual: Understanding version ordering

Conflict resolution adds one rule on top of the ordering: it compares base versions first. The part of a version after a non-dot separator is its qualifier (beta in 1.0-beta); Gradle selects the versions with the highest base version, discards all the others, and only then, between versions that share that base, prefers the ones without a qualifier. Two experiments with slf4j-api show both halves. The experiment used a scratch pair of configurations, a dependency scope (where the versions are declared) and a resolvable one that extends it, because the point was only to resolve and read the report.

Gradle does not know that 2.1.0-alpha1 is a pre-release in any sense that matters for your project, so a transitive dependency on a pre-release can pull one into the build. Rejecting it is what reject and strictly ranges are for (see Platforms, Constraints & Rich Versions).

Ranges take part in the same decision. Without ranges, the highest non-rejected version is selected. When a non-range version fits within a range, or is higher than its upper bound, it is selected. When there are only ranges, the highest version in their intersection is selected if they overlap; otherwise the highest version of the largest range, or a failure if there is no such version. Resolving a range needs the list of versions, which Gradle reads from the repository (see the metadata rules above).

Source: Gradle User Manual: Version conflicts and Base version comparison

A constraint is a request, not an override

A dependency constraint is a statement about a version that applies only if the module is part of the graph for some other reason. It is the supported way to influence the version of a transitive dependency without making it a direct one. The cli build file below constrains commons-io to 2.21.0:

Kotlin DSL
plugins {
    application
}

dependencies {
    implementation(project(":tidepool-engine"))
    implementation("info.picocli:picocli:4.7.7")
    implementation("commons-io:commons-io:2.11.0")

Capability conflicts

What a capability is

Version conflicts are about one module at two versions. A different failure is two different modules that do the same job: two logging bindings, two connection pools, a library and its relocated successor. Their coordinates differ, so a tool that looks only at coordinates (Maven, or Gradle’s version conflict logic) sees no conflict, and both end up on the classpath. Gradle’s answer is the capability: a name, written as group, name and version, that a component declares in order to say "I provide this functionality". It is illegal for a dependency graph to contain two components that provide the same capability; Gradle fails the build and names the modules.

Every component has an implicit capability, its own coordinates: org.apache.commons:commons-lang3:3.8 provides the capability org.apache.commons:commons-lang3, at version 3.8. Capabilities are versioned, which is what lets Gradle choose the highest one. A component can declare more capabilities, and doing so is the whole mechanism. Two places can declare them: the metadata of a published component (Gradle Module Metadata has a capabilities section for each variant), and a build, either through a component metadata rule for an external module that did not declare them or through the outgoing configurations of your own project.

Source: Gradle User Manual: Capabilities and capability coordinates

Declaring capabilities for an external module

Most libraries do not declare capabilities, so the conflict must be declared by the build. The two modules of the documentation’s example are log4j:log4j (Log4j 1.x) and org.slf4j:log4j-over-slf4j (a bridge that supplies the Log4j 1 API on top of SLF4J): different coordinates, same API, and both are fatal on one classpath. A ComponentMetadataRule can add a capability to every variant of both. The components.all call registers the rule. The rule is a class and not a closure, which is what keeps the build compatible with the configuration cache (the build ran with it, and stored the entry); a rule can also be marked @CacheableRule so that Gradle caches its result, as described on Resolution Rules & Substitution.

Kotlin DSL
plugins {
    application
}

// Metadata rule: two unrelated coordinates provide the same capability.
class Log4jApiCapability : ComponentMetadataRule {
    override fun execute(context: ComponentMetadataContext) = context.details.run {
        if (id.name == "log4j" || id.name == "log4j-over-slf4j") {
            allVariants {
                withCapabilities {
                    addCapability("io.tidepool", "log4j-api", id.version)
                }
            }
        }
    }
}

dependencies {
    components.all<Log4jApiCapability>()

    implementation(project(":tidepool-engine"))
    implementation("info.picocli:picocli:4.7.7")
    implementation("log4j:log4j:1.2.17")
    implementation("org.slf4j:log4j-over-slf4j:2.0.17")
}

    mainClass = "io.tidepool.cli.Main"

Declaring capabilities on your own components

A project that publishes a library can declare the capabilities of its own variants. Capabilities live on consumable configurations (apiElements and runtimeElements of a Java library). The tidepool build gains a second implementation of the model, tidepool-model-lite, which is an alternative to tidepool-model: both provide the capability io.tidepool:tide-api. One rule from the documentation applies: as soon as any explicit capability is declared, all of them must be, including the implicit one, so each project lists its own coordinates as well.

Excluding transitive dependencies

An exclusion removes a module from the graph. It is the bluntest of the tools, and the one that is easiest to overuse: the library that declared the dependency needed it, and removing it is a decision that only a test can validate. The documentation lists the legitimate reasons: a library includes dependencies your application does not need, you want to shrink what you ship, or a conflict can only be solved by not having the module. For the last case, constraints, a metadata rule or a capability are usually better.

Choosing the right tool

The documentation closes its guide with a list of alternatives to try before an exclusion: a constraint if the problem is a version, a component metadata rule if the metadata of the library is wrong (for example, a compile-time dependency that was published as a runtime one), and a capability if two modules are alternatives to each other. An exclusion remains right for the case it was designed for: a module that is on the classpath and should not be, and that no one needs.

Maven’s <exclusions> element is the same device with the same limits (it applies per dependency; Maven also accepts the wildcard * for group and artifact), and Ivy has <exclude>; both are covered in Maven Dependencies, Scopes & Mediation and Ivy: Module Descriptors & Configurations.

Source: Gradle User Manual: exclusion summary

Reading a resolution failure

The failures on this page follow a few shapes. This table is a quick way to map one to its cause; each message was produced by a run above.

What Gradle printed What it means What to do

Conflict found for module 'commons-io:commons-io': between versions 2.20.0 and 2.11.0

failOnVersionConflict() is on and two versions were requested.

Pick one with a constraint or strictly, or accept the highest and disable the check.

Cannot find a version of 'commons-io:commons-io' that satisfies the version constraints

Two strict declarations at the same level ask for versions that exclude each other.

Make one of them non-strict, or change one of the versions.

Module 'x' has been rejected: Cannot select module because of conflict with y ... Both provide capability 'g:n:v'

Two modules provide one capability.

Choose a provider with capabilitiesResolution, or remove one of the modules.

a:b:1.0 -> c:d:2.0 in a tree

The request for a:b resolved to a different module (a capability replacement or a substitution).

Check dependencyInsight for the reason, which names the capability or the rule.

a:b:1.0 -> 2.0 in a tree

The request for 1.0 was resolved to 2.0 by conflict resolution, a constraint or a rule.

Read the selection reasons.

A NoClassDefFoundError after adding an exclude

The excluded module was needed at run time.

Remove the exclusion, or provide the module another way.
