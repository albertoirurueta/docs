Multi Project Builds

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Gradle 9.8.1 (the current release on 2026-10-16). Every example was run on JDK 26 through the Gradle wrapper on 2026-10-16, on macOS, with the configuration cache enabled (org.gradle.configuration-cache=true in gradle.properties), and every example on this page is compatible with it unless the text says otherwise. The Kotlin DSL is shown first and the Groovy DSL second wherever the syntax differs, and both versions were run. Paths of the scratch workspace are shortened to <work>; lines that were left out of an output are marked with .... Gradle 8.14 was not available here: what differs in it is described from the official documentation in the section "Gradle 8.14 and Gradle 9" and is labelled "not run here".

A build that outgrows one source tree is split into projects. In Gradle that is a multi-project build: one root project and any number of subprojects, all declared by the single settings file and all configured, scheduled and cached by the one build around them. The vocabulary (build, project, task) is on Core Concepts, the settings file on Settings & Build Scripts, and the phases in which the projects are configured on Build Lifecycle. This page is about what is specific to having several projects: how they find each other, what a dependency between them means for the task graph, how to run part of the build, why configuring one project from another is discouraged, how to hand a file from one project to another without reaching into it, and how to turn a single-project build into several projects. Sharing build logic between the projects is the subject of Convention Plugins & Sharing Build Logic, and combining separate builds that live in different repositories is that of Composite Builds.

The layout of a multi-project build

The running example of the section is tidepool, a small tide prediction toolkit with a model library, an engine library on top of it and a command line application. As a Gradle build it is one root project and three subprojects:

tidepool
├── gradle
│   ├── libs.versions.toml
│   └── wrapper
├── gradle.properties
├── gradlew
├── gradlew.bat
├── settings.gradle.kts            (settings.gradle for the Groovy DSL)
├── build.gradle.kts               (build.gradle; the root project's script, here nearly empty)
├── data
│   └── stations.csv
├── tidepool-model
│   ├── build.gradle.kts
│   └── src/{main,test}/java/io/tidepool/model/...
├── tidepool-engine
│   ├── build.gradle.kts
│   └── src/{main,test}/java/io/tidepool/engine/...
└── tidepool-cli
    ├── build.gradle.kts
    └── src/main/java/io/tidepool/cli/...
graph TD root["root project 'tidepool': settings, base plugin, no sources"] cli["tidepool-cli: application"] engine["tidepool-engine: java-library"] model["tidepool-model: java-library"] root -.->|include| cli root -.->|include| engine root -.->|include| model cli -->|implementation| engine engine -->|api| model

Dotted arrows are the include calls of the settings file; solid arrows are the dependencies between the projects. The settings file is the only place where the projects are listed, and the user manual’s advice is that a build has exactly one settings file.

Kotlin DSL: settings.gradle.kts
dependencyResolutionManagement {
    repositoriesMode = RepositoriesMode.FAIL_ON_PROJECT_REPOS
    repositories {
        mavenCentral()
    }
}

rootProject.name = "tidepool"

include("tidepool-model", "tidepool-engine", "tidepool-cli")
Groovy DSL: settings.gradle
dependencyResolutionManagement {
    repositoriesMode = RepositoriesMode.FAIL_ON_PROJECT_REPOS
    repositories {
        mavenCentral()
    }
}

rootProject.name = 'tidepool'

include 'tidepool-model', 'tidepool-engine', 'tidepool-cli'

The root script has nothing to configure. The base plugin gives the root project the lifecycle tasks (assemble, check, build, clean), and nothing else is applied:

Kotlin DSL: build.gradle.kts
plugins {
    base
}
Groovy DSL: build.gradle
plugins {
    id 'base'
}

The group and the version are properties set once in the gradle.properties of the root, which Gradle applies to every project of the build; the jar of the model project is therefore tidepool-model-1.0.0.jar. The catalog gradle/libs.versions.toml declares the libraries and the JUnit version (see Version Catalogs).

gradle.properties
org.gradle.configuration-cache=true
group=io.tidepool
version=1.0.0
gradle/libs.versions.toml (the same for both DSLs; highlight.js has no TOML grammar, so it is shown as plain text)
[versions]
commons-csv = "1.14.1"
picocli = "4.7.7"
junit = "6.1.3"

[libraries]
commons-csv = { module = "org.apache.commons:commons-csv", version.ref = "commons-csv" }
picocli = { module = "info.picocli:picocli", version.ref = "picocli" }

Source: Gradle User Manual: Multi-Project Layout

Project paths and names

Projects are addressed by their path: : is the root project, :tidepool-model a direct child, and :libs:model a project model below a project libs. The path decides the default directory (libs/model), and a task is addressed with the path of its project in front (:tidepool-engine:test), as explained on Command-Line Interface. Nested projects, a project directory mapped with projectDir, and the strict check of 9.0 that an included project must have a directory are shown on Settings & Build Scripts and not repeated here.

The user manual gives three recommendations for names, and the example follows them:

  • keep the default project name, which is the name of its directory, instead of mapping names to other folders;

  • use lower-case words separated by hyphens (tidepool-engine, not TidePoolEngine);

  • set rootProject.name in the settings file. Without it, the name of the build is the name of the directory it was checked out in, which differs from machine to machine (and is generated at random at the root of a file system), and appears in reports and Build Scans.

Source: Gradle User Manual: Naming recommendations and Gradle User Manual: Project descriptors

Project dependencies

A project declares that it needs another project with a project dependency, written with the path of the other project. The three build scripts of the example are the whole of the wiring. The model has no dependencies, the engine exposes the model in its API and uses Commons CSV internally, and the command line application uses the engine and picocli:

Kotlin DSL: tidepool-model/build.gradle.kts
plugins {
    `java-library`
}

tasks.withType<JavaCompile>().configureEach {
    options.release = 21
}

testing {
    suites {
        named<JvmTestSuite>("test") {
            useJUnitJupiter(libs.versions.junit)
        }
    }
}
Groovy DSL: tidepool-model/build.gradle
plugins {
    id 'java-library'
}

tasks.withType(JavaCompile).configureEach {
    options.release = 21
}

testing {
    suites {
        test {
            useJUnitJupiter(libs.versions.junit)
        }
    }
}
Kotlin DSL: tidepool-engine/build.gradle.kts
plugins {
    `java-library`
}

dependencies {
    api(project(":tidepool-model"))
    implementation(libs.commons.csv)
}

tasks.withType<JavaCompile>().configureEach {
    options.release = 21
}

testing {
    suites {
        named<JvmTestSuite>("test") {
            useJUnitJupiter(libs.versions.junit)
        }
    }
}
Groovy DSL: tidepool-engine/build.gradle
plugins {
    id 'java-library'
}

    api project(':tidepool-model')
    implementation libs.commons.csv
}

tasks.withType(JavaCompile).configureEach {
    options.release = 21
}

testing {
    suites {
        test {
            useJUnitJupiter(libs.versions.junit)
        }
    }
}
Kotlin DSL: tidepool-cli/build.gradle.kts
plugins {
    application
}

dependencies {
    implementation(project(":tidepool-engine"))
    implementation(libs.picocli)
}

application {
    mainClass = "io.tidepool.cli.Main"
}

tasks.withType<JavaCompile>().configureEach {
    options.release = 21
}
Groovy DSL: tidepool-cli/build.gradle
plugins {
    id 'application'
}

    implementation project(':tidepool-engine')
    implementation libs.picocli
}

application {
    mainClass = 'io.tidepool.cli.Main'
}

tasks.withType(JavaCompile).configureEach {
    options.release = 21
}

(The same three lines options.release = 21 appear in every script. That repetition is deliberate: the ways to remove it, and what each of them costs, are the subject of "Configuring projects from the root" below.) Run with the Kotlin and then the Groovy scripts, ./gradlew build built all three projects, ran the two test classes, and ./gradlew :tidepool-cli:run printed the same station:

./gradlew :tidepool-cli:run --args="../data/stations.csv SF" -q
San Francisco: -0.869 m

(The decimal separator follows the locale of the JVM; the run used -Duser.language=en -Duser.country=US.)

A project dependency does two things, and the user manual puts them in one sentence: the required project is built first, and its compiled classes and its transitive dependencies are added to the classpath of the consuming project. Starting from a clean tree, one task of the command line application shows the order:

./gradlew clean -q
./gradlew :tidepool-cli:compileJava
Calculating task graph as no cached configuration is available for tasks: :tidepool-cli:compileJava
> Task :tidepool-model:compileJava
> Task :tidepool-engine:compileJava
> Task :tidepool-cli:compileJava

BUILD SUCCESSFUL in 941ms
3 actionable tasks: 3 executed
Configuration cache entry stored.

Nothing in the command line named the model or the engine. Gradle followed the dependencies from tidepool-cli, found that its compile classpath contains the classes of the engine and, through the engine’s api dependency, those of the model, and scheduled their compilation first. No jar was built: the compile classpath of a java-library project uses the classes directory of its dependency, and only the runtime classpath uses the jar. That is why the :jar tasks appear when something needs a runtime classpath (running the application, running the tests of the engine), not when something only compiles. The classpaths themselves are shown by the dependencies task, here for the compile and the runtime classpath of the command line application:

./gradlew :tidepool-cli:dependencies --configuration compileClasspath
./gradlew :tidepool-cli:dependencies --configuration runtimeClasspath
compileClasspath - Compile classpath for source set 'main'.
+--- project ':tidepool-engine'
|    \--- project ':tidepool-model'
\--- info.picocli:picocli:4.7.7

runtimeClasspath - Runtime classpath of source set 'main'.
+--- project ':tidepool-engine'
|    +--- project ':tidepool-model'
|    \--- org.apache.commons:commons-csv:1.14.1
|         +--- commons-io:commons-io:2.20.0
|         \--- commons-codec:commons-codec:1.19.0
\--- info.picocli:picocli:4.7.7

(Each output was cut to its tree, and the A web-based, searchable dependency report hint that follows it was left out.) This is the difference between api and implementation made visible. The model is on the compile classpath of the command line application because the engine declared it with api; Commons CSV, declared with implementation in the engine, is a runtime detail of the engine and absent from the compile classpath of its consumers, so the application cannot import it by accident. Both declarations, the configurations behind them and dependencyInsight are the subject of Declaring Dependencies & Configurations.

Source: Gradle User Manual: Declaring dependencies between subprojects and Gradle User Manual: Depending on another project

Type-safe project accessors

The path of project(":tidepool-model") is a string, so a typo or a renamed project is found only when the build is configured. The type-safe project accessors replace the string with a generated accessor, projects.tidepoolModel, which an IDE completes and the compiler checks. They are an incubating feature and must be switched on in the settings file before they exist. Without the switch the Kotlin DSL does not know the name, and the message is not about the missing feature:

e: file://<work>/tidepool-cli/build.gradle.kts:6:20: Unresolved reference. None of the following candidates is applicable because of a receiver type mismatch:
val TaskContainer.projects: TaskProvider<ProjectReportTask>

The Groovy DSL fails with Could not get unknown property 'tidepoolEngine' for task ':tidepool-cli:projects' of type org.gradle.api.tasks.diagnostics.ProjectReportTask. In both languages projects resolved to the projects task described above. With the feature preview enabled, both DSLs compile and build:

Kotlin DSL: settings.gradle.kts (added line) and tidepool-cli/build.gradle.kts
enableFeaturePreview("TYPESAFE_PROJECT_ACCESSORS")

// tidepool-cli/build.gradle.kts
dependencies {
    implementation(projects.tidepoolEngine)
    implementation(libs.picocli)
}
Groovy DSL: settings.gradle (added line) and tidepool-cli/build.gradle
enableFeaturePreview('TYPESAFE_PROJECT_ACCESSORS')

// tidepool-cli/build.gradle
dependencies {
    implementation projects.tidepoolEngine
    implementation libs.picocli
}
Type-safe project accessors is an incubating feature.
> Task :tidepool-model:compileJava
> Task :tidepool-engine:compileJava
> Task :tidepool-cli:compileJava

BUILD SUCCESSFUL in 1s

The hyphenated project name became a camel-case accessor. The rest of this page keeps the string form, which works without any switch.

Source: Gradle User Manual: Type-safe project dependencies

A Project object is not a dependency notation

Since Gradle 9.6, handing a Project object to a dependency configuration is deprecated: val model = project(":tidepool-model") outside a dependencies block returns the Project, and api(model) then uses it as a notation. The build works and prints a warning (shown here for the Kotlin DSL; the Groovy DSL printed the same message):

Using a Project object as a dependency notation has been deprecated. This will fail with an error in Gradle 10. Please use the project(String) method on DependencyHandler or the createProjectDependency(String) method on DependencyFactory instead. Consult the upgrading guide for further information: https://docs.gradle.org/9.8.1/userguide/upgrading_version_9.html#dependency_project_notation

Inside the dependencies block project(":tidepool-model") is the method of the dependency handler and is fine.

Source: Gradle User Manual: Deprecation of using Project objects as dependency notation

Running tasks across projects

Which tasks run, and in which projects, is decided by the path on the command line. The selectors (test in every project that has it, :tidepool-cli:run for one) are documented with their variations on Command-Line Interface. Three things are specific to multi-project builds and are shown here.

From a subdirectory, and with -p

Gradle looks for the settings file in the working directory and then in its parents. A command run inside a subproject therefore still runs in the whole build, and the task names that are not qualified are resolved against the project of the working directory:

cd tidepool-engine
../gradlew test
> Task :tidepool-engine:processTestResources NO-SOURCE
> Task :tidepool-engine:processResources NO-SOURCE
> Task :tidepool-model:processResources NO-SOURCE
> Task :tidepool-model:compileJava UP-TO-DATE
> Task :tidepool-model:classes UP-TO-DATE
> Task :tidepool-engine:compileJava UP-TO-DATE
> Task :tidepool-engine:classes UP-TO-DATE
> Task :tidepool-model:jar
> Task :tidepool-engine:compileTestJava
> Task :tidepool-engine:testClasses
> Task :tidepool-engine:test

BUILD SUCCESSFUL in 2s
5 actionable tasks: 3 executed, 2 up-to-date

(The first line of the output, about the task graph, was left out.) Only the test task of the engine ran; the test of the model did not. The model contributed what the engine needs to run its tests: its classes and, because a test runs on the runtime classpath, its jar. ./gradlew -p tidepool-engine test from the root does the same without changing directory, and so does ./gradlew :tidepool-engine:test; the three spellings differ only in where the command is typed.

buildNeeded and buildDependents

The Java plugins give every project two lifecycle tasks whose names say what they do: buildNeeded builds the project and every project it depends on, buildDependents builds the project and every project that depends on it. They are the Gradle counterparts of mvn -am and mvn -amd. The difference to build is the tests of the other projects. A dry run of the three tasks for the engine and the model, with the list cut to the tasks that name the lifecycle (the order of tasks that do not depend on each other is not fixed and differs between runs):

./gradlew :tidepool-engine:build --dry-run | grep -E ':(test|build|buildNeeded|buildDependents) '
./gradlew :tidepool-engine:buildNeeded --dry-run | grep -E ':(test|build|buildNeeded|buildDependents) '
./gradlew :tidepool-model:buildDependents --dry-run | grep -E ':(test|build|buildNeeded|buildDependents) '
:tidepool-engine:test SKIPPED
:tidepool-engine:build SKIPPED

:tidepool-engine:test SKIPPED
:tidepool-engine:build SKIPPED
:tidepool-model:test SKIPPED
:tidepool-model:build SKIPPED
:tidepool-model:buildNeeded SKIPPED
:tidepool-engine:buildNeeded SKIPPED

:tidepool-cli:test SKIPPED
:tidepool-cli:build SKIPPED
:tidepool-cli:buildDependents SKIPPED
:tidepool-engine:test SKIPPED
:tidepool-engine:build SKIPPED
:tidepool-engine:buildDependents SKIPPED
:tidepool-model:test SKIPPED
:tidepool-model:build SKIPPED
:tidepool-model:buildDependents SKIPPED

(The three outputs are separated by blank lines here.) :tidepool-engine:build tests only the engine; buildNeeded adds the build, and thus the tests, of the model; buildDependents of the model adds the engine and the command line application. Both tasks are deprecated since Gradle 9.6 and scheduled for removal in Gradle 10, because their implementation is incompatible with configuration on demand and with Isolated Projects and too rigid for the range of uses. Running one prints the warning, with --warning-mode=all for the text:

> Task :tidepool-model:build
> Task :tidepool-model:buildNeeded
The buildNeeded task has been deprecated. This is scheduled to be removed in Gradle 10. Consult the upgrading guide for further information: https://docs.gradle.org/9.8.1/userguide/upgrading_version_9.html#deprecate_build_needed_build_dependents_tasks
> Task :tidepool-engine:build
> Task :tidepool-engine:buildNeeded

The upgrade guide names the replacements: run the task you need directly (./gradlew :tidepool-engine:build and let Gradle resolve its dependencies), run a task by name in every project (./gradlew test) and rely on up-to-date checks and the build cache to skip the projects that did not change, use test report aggregation to run the tests of all dependencies, or, in build logic, use artifact views. ./gradlew :tidepool-model:build :tidepool-engine:build is the explicit spelling of what buildNeeded did for the engine.

Source: Gradle User Manual: Deprecation of buildNeeded and buildDependents tasks

Work avoidance across projects

The reason to split a build is that Gradle then skips the projects an edit cannot have affected. With the three projects built and up to date, an edit to the body of a method in the engine (no change to any signature) recompiled and repackaged the engine, and nothing else:

./gradlew build | grep -E 'compileJava|:jar|BUILD|actionable'
> Task :tidepool-model:compileJava UP-TO-DATE
> Task :tidepool-model:jar UP-TO-DATE
> Task :tidepool-engine:compileJava
> Task :tidepool-engine:jar
> Task :tidepool-cli:compileJava UP-TO-DATE
> Task :tidepool-cli:jar UP-TO-DATE
BUILD SUCCESSFUL in 1s
13 actionable tasks: 6 executed, 7 up-to-date

The command line application was not recompiled even though it depends on the engine, because the public interface of the engine’s classes did not change (compile avoidance); the six executed tasks are the compilation and jar of the engine, its tests, and the packaging tasks of the application that take the engine jar into the distribution. After adding a method to a class of the model (a change to its public interface), every project that compiles against the model was recompiled:

> Task :tidepool-model:compileJava
> Task :tidepool-model:jar
> Task :tidepool-engine:compileJava
> Task :tidepool-engine:jar UP-TO-DATE
> Task :tidepool-cli:compileJava
> Task :tidepool-cli:jar UP-TO-DATE
BUILD SUCCESSFUL in 1s
13 actionable tasks: 11 executed, 2 up-to-date

The jars of the engine and the application were up to date because recompiling their unchanged sources produced identical classes. A single project holding the same sources has no such boundaries, which is the first of the user manual’s reasons to modularize. How Gradle decides that a task is up to date is on Incremental Build. The user manual’s advice on where to cut is to split early and along natural lines (API and implementation, front end and back end, core logic and UI, vertical feature slices, the inputs of a code generator and its users), and to prefer more projects to fewer; projects containing a single class are the extreme at which this stops paying off.

Parallel execution and configuration on demand

Two switches make a multi-project build faster, and both are covered elsewhere: org.gradle.parallel lets independent tasks run at the same time (see Build Environment & Properties), and configuration on demand configures only the projects needed for the requested tasks (see Build Lifecycle). With the configuration cache enabled, as in every example here, independent tasks already run in parallel, within a project as well as across projects, and --no-parallel has no effect (see Worker API & Build Services), so the build logic of the projects must not rely on the order of tasks that are not connected by a dependency.

Source: Gradle User Manual: Modularize your builds

Configuring projects from the root

The three options.release = 21 blocks are the smallest possible example of a problem every multi-project build has: what the projects have in common. The oldest answer is to configure the subprojects from the root script, with allprojects { } (the root and all subprojects), subprojects { } (all subprojects) or project(":tidepool-cli") { } (one of them). It is shown here because the existing builds are full of it, and because its failure modes explain why the manual steers away from it.

The root script runs first

The configuration phase evaluates the root script before the scripts of the subprojects (see Build Lifecycle). A subprojects { } block that reaches into something a plugin of the subproject creates therefore finds nothing yet. This root script adds a JUnit dependency to every subproject:

Kotlin DSL: build.gradle.kts
plugins {
    base
}

subprojects {
    dependencies {
        "testImplementation"("org.junit.jupiter:junit-jupiter:6.1.3")
    }
}
Groovy DSL: build.gradle
plugins {
    id 'base'
}

subprojects {
    dependencies {
        testImplementation 'org.junit.jupiter:junit-jupiter:6.1.3'
    }
}
* What went wrong:
Configuration with name 'testImplementation' not found.

The Groovy DSL fails in the same place with Could not find method testImplementation() for arguments [org.junit.jupiter:junit-jupiter:6.1.3] on object of type org.gradle.api.internal.artifacts.dsl.dependencies.DefaultDependencyHandler. Why the manual discourages it

The user manual’s chapter on sharing build logic calls subprojects { } and allprojects { } an improper way to share build logic: the logic injected into a subproject is not obvious from its build script, it usually grows in complexity and becomes a burden, and it introduces configuration-time coupling between projects, which can stop optimizations such as configuration on demand from working. It names two common uses and their replacements. Applying plugins or configuration to the subprojects of a certain type is better modelled by a convention plugin, which each such project applies with one line, so that a project’s script states its own conventions (see Convention Plugins & Sharing Build Logic). Extracting information from subprojects of a certain type is better modelled with outgoing configuration variants, which is the subject of the next section.

The coupling is not only a matter of taste. With Isolated Projects (incubating, see below) the projects of a build must not reach into each other’s mutable state, and the root script above is exactly that. This root script configures the compile tasks of the subprojects directly:

Kotlin DSL: build.gradle.kts
plugins {
    base
}

subprojects {
    tasks.withType<JavaCompile>().configureEach {
        options.release = 21
    }
}
Groovy DSL: build.gradle

    id 'base'
}

        options.release = 21
    }
}

Gradle’s other recommendation for the root is the one the example follows: it should not contain source files, and plugins that only affect source code should not be applied to it. The root project is the entry point that tells Gradle which projects exist, and a root project with the java-library plugin and its own src/main mixes that role with a module’s. The implicit lookup in parent projects

The other implicit coupling is about names. When a property or method is not found in a project, Gradle looks in its parent, then in the grandparent, up to the root. Since Gradle 9.6 that walk emits a deprecation warning, and Gradle 10 will remove it. The warning, and the cases it covers (findProperty, property, hasProperty, bare names and the Kotlin by project delegate), are shown on Build Environment & Properties. Sharing outputs between projects

Sometimes a project needs a file another project produces: not its classes, but a generated index, a schema, a report. The tempting way is the task-to-task wire, which the manual discourages because it couples two projects through the internals of one of them:

Kotlin DSL: tidepool-cli/build.gradle.kts, the discouraged form
tasks.register<Copy>("copyStationIndex") {
    dependsOn(":tidepool-model:stationIndex")
    from(project(":tidepool-model").layout.buildDirectory.dir("station-index"))
    into(layout.buildDirectory.dir("station-index"))
}
Groovy DSL: tidepool-cli/build.gradle, the discouraged form
tasks.register('copyStationIndex', Copy) {
    dependsOn(':tidepool-model:stationIndex')
    from(project(':tidepool-model').layout.buildDirectory.dir('station-index'))
    into(layout.buildDirectory.dir('station-index'))
}

The stationIndex task writes one station id per line of data/stations.csv; the consumable configuration stationIndexElements exposes its output, tagged with a custom value of the standard Usage attribute so that it matches nothing else the model project offers (its Java variants have the usages java-api and java-runtime):

Kotlin DSL: tidepool-model/build.gradle.kts (added)
val stationIndex = tasks.register("stationIndex") {
    val csv = layout.settingsDirectory.file("data/stations.csv")
    val index = layout.buildDirectory.file("station-index/stations.txt")
    inputs.file(csv)
    outputs.file(index)
    doLast {
        val ids = csv.asFile.readLines().drop(1).map { it.substringBefore(",") }
        index.get().asFile.apply { parentFile.mkdirs() }.writeText(ids.joinToString("\n", postfix = "\n"))
    }
}

val stationIndexUsage = objects.named<Usage>("tidepool-station-index")

configurations.consumable("stationIndexElements") {
    attributes {
        attribute(Usage.USAGE_ATTRIBUTE, stationIndexUsage)
    }
    outgoing.artifact(layout.buildDirectory.file("station-index/stations.txt")) {
        builtBy(stationIndex)
    }
}
Groovy DSL: tidepool-model/build.gradle (added)
def stationIndex = tasks.register('stationIndex') {
    def csv = layout.settingsDirectory.file('data/stations.csv')
    def index = layout.buildDirectory.file('station-index/stations.txt')
    inputs.file(csv)
    outputs.file(index)

    }

Isolated Projects constraints

Isolated Projects is the feature that the examples above kept hitting. It runs on top of the configuration cache and lets Gradle configure the projects in parallel and cache each project’s configuration on its own, which needs the projects not to read or change each other. It is incubating since Gradle 9.7 and is enabled with org.gradle.isolated-projects=true in gradle.properties or --isolated-projects on the command line (the unsafe spellings of the property are deprecated since 9.7). The rules that matter to the structure of a multi-project build are short:

  • A project’s build logic must not use the mutable state of another project: project(":x").layout, rootProject.tasks, subprojects { tasks... } and allprojects { } that touch other projects are violations (both shown above).

  • There is no implicit lookup of properties and methods in parent projects.

  • Dependencies between projects are fine, because a project dependency is data, not access; so is sharing outputs through variants, as the example above passed with --isolated-projects.

  • Convention plugins are the way to apply the same logic to every project, which is why they are the migration path.

The feature, its status, the diagnostics mode and the migration are on Configuration Cache & Isolated Projects.

Source: Gradle User Manual: Isolated Projects constraints and Gradle User Manual: Deprecation of unsafe Isolated Projects properties

Multi-project or composite

A multi-project build is one build: one settings file, one set of rules for repositories and plugins, one task graph, one configuration cache entry. When the parts have their own repositories, release cycles and settings, the manual’s guidance is to keep them as separate builds and combine them with includeBuild, which substitutes a local checkout for a published dependency, and the build logic of the projects as an included build too. That is the subject of Composite Builds. Publishing the projects of a multi-project build (and the 9.3 deprecation of publishing a project that depends on a project with no publication) is covered by Publishing.

Source: Gradle User Manual: Favor composite builds over buildSrc

Where the books are outdated

Gradle in Action (Muschko, Manning 2014) was written for Gradle 1.7 and has a chapter on multi-project builds. The model it teaches (a root and subprojects, settings.gradle with include, dependencies between projects) is still correct. What changed around it:

  • compile project(':x'). The compile, runtime, testCompile and testRuntime configurations were removed in Gradle 7.0. A project dependency is declared with implementation or api (run above).

  • Configuration injection from the root. allprojects { } and subprojects { } were the way to share configuration. They still work, but the manual now recommends convention plugins, and Isolated Projects rejects them (run above).

  • buildNeeded and buildDependents. They date from Gradle 0.8 and were in the book’s era the way to build a project and what it needs. They are deprecated since Gradle 9.6.

  • The project object used freely at execution time. The configuration cache, preferred since Gradle 9.0, does not allow it, and the cross-project access of Isolated Projects does not either.

For the same topics in the other tools see Maven Multi-Module Builds & the Reactor and Ant Multi-File Builds.
