Version Catalogs

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Gradle 9.8.1 and was run on JDK 26 on 2026-10-16 (macOS; the daemon ran on JDK 26 and no toolchain was involved). Every example was run through the wrapper in scratch copies of the tidepool project, once with Kotlin DSL build files and once with Groovy DSL build files. The TOML file and its error messages are the same for both DSLs, so the experiments that change only the TOML file (the error gallery, the alias names) were run in the Kotlin DSL copy; everything that involves a build script or a settings script was run in both. The scratch copies pointed their wrapper at a local copy of the same distribution archive; the properties file that a real project commits is

The commands use --console=plain, and gradle.properties contains org.gradle.configuration-cache=true, so every example ran with the configuration cache on and each one says whether it is compatible with it. In the listings the blank lines, the Try: hints of failures, the [Incubating] Problems report line and the Calculating task graph line of the first run are left out, the order of unrelated tasks varies from run to run (a line with three dots marks trimmed lines), and the scratch directory is shown as /work/tidepool. Gradle 8.14.x was not installed here, so statements about it come from the official documentation and the release notes and are labelled "not run here". Publishing a catalog goes only to a file:// repository below the catalog project’s build directory; publishing to a remote repository is not run here.

A version catalog is a list of dependency coordinates and plugin versions kept in one file, from which Gradle generates type-safe names for the build scripts. It is the answer to the oldest maintenance problem of a multi-project build: the same version number typed in a dozen places, and a dozen places to change when a library moves. This page covers the file format, the generated accessors, every way of declaring, sharing and publishing a catalog, how a catalog interacts with platforms and with buildSrc or build-logic, and the problems Gradle reports, using the tidepool toolkit of the section (a model library, an engine library that reads a CSV file with Commons CSV, and a command line application that uses picocli). The dependency vocabulary (configurations, api and implementation) is on Declaring Dependencies & Configurations, where the versions end up being chosen is on Platforms, Constraints & Rich Versions and Dependency Resolution, Conflicts & Capabilities, and the cross-tool picture is on Dependency Management Fundamentals.

Why a catalog

Before catalogs, the usual place for a shared version was an ext property in the root build script (or a gradle.properties entry). That is the style of the book Gradle in Action (Gradle 1.7), and it still works on Gradle 9.8.1: the same tidepool build with the versions in ext resolves to exactly the same graph.

Kotlin DSL: build.gradle.kts (root project)
group = "io.tidepool"
version = "1.0.0"

val commonsCsvVersion by extra("1.14.1")
val picocliVersion by extra("4.7.7")
Kotlin DSL: tidepool-engine/build.gradle.kts
plugins {
    `java-library`
}

val commonsCsvVersion: String by rootProject.extra

dependencies {
    api(project(":tidepool-model"))
    implementation("org.apache.commons:commons-csv:$commonsCsvVersion")
}
Groovy DSL: build.gradle (root project)
group = 'io.tidepool'
version = '1.0.0'

ext {
    commonsCsvVersion = '1.14.1'
    picocliVersion = '4.7.7'
}
Groovy DSL: tidepool-engine/build.gradle
plugins {
    id 'java-library'
}

dependencies {
    api project(':tidepool-model')
    implementation "org.apache.commons:commons-csv:${rootProject.ext.commonsCsvVersion}"
}

Both versions printed the same tree for the command line application:

$ ./gradlew :tidepool-cli:dependencies --configuration runtimeClasspath
...
runtimeClasspath - Runtime classpath of source set 'main'.
+--- project ':tidepool-engine'
|    +--- project ':tidepool-model'
|    \--- org.apache.commons:commons-csv:1.14.1
|         +--- commons-io:commons-io:2.20.0
|         \--- commons-codec:commons-codec:1.19.0
\--- info.picocli:picocli:4.7.7

The ext approach has three weaknesses that a catalog removes. A version is a bare String property, so nothing says which coordinates it belongs to and a typo in the property name is found only when the script runs; there is no name for a library, so the group and artifact are retyped in every project; and an IDE cannot offer completion or navigation for it. A catalog declares the whole coordinate once, gives it a name, and generates a typed accessor for the name. The Gradle best practices page for dependencies says it plainly: define versions in a catalog instead of in project.ext, constants or local variables.

Source: Gradle User Manual: Use Version Catalogs to Centralize Dependency Versions

A catalog is a declaration device and nothing else. It does not change how Gradle resolves the graph: a version in the catalog is an ordinary requirement of the project that uses it, exactly as if the string had been typed in the build script, and the resolved version can still be higher (conflict resolution) or different (a platform, a constraint, a rule). Consumers of the project cannot see whether a dependency came from a catalog. The section on platforms below shows this on the tidepool build.

Source: Gradle User Manual: Version Catalogs (catalog or platform)

History

Release Change

Gradle 7.0 (2021-04-09)

Version catalogs appear as an experimental feature, switched on in settings with enableFeaturePreview("VERSION_CATALOGS"): the file gradle/libs.versions.toml, bundles, sharing between builds and the Settings API.

Gradle 7.2

Still a feature preview. Aliases can now have sub-aliases (jackson and jackson-xml side by side) and a [plugins] table lets the plugins {} block use alias(libs.plugins.name).

Gradle 7.4 (2022-02-08)

Version catalogs are stable.

Gradle 8.1

Plugin aliases in the plugins {} block are no longer shown as errors in the Kotlin script editor of IntelliJ IDEA and Android Studio. Accessing libraries or bundles in the plugins {} block is deprecated.

Gradle 8.5

The gradle init task generates projects that use a catalog in gradle/libs.versions.toml; the versionCatalogs extension is available in precompiled Kotlin script plugins; the Javadoc of the generated accessors shows the version.

Gradle 8.7

The TOML parser is upgraded and is now compliant with version 1.0.0 of the TOML specification.

Gradle 8.8

A plugin alias without a version is explicitly allowed.

Gradle 9.0.0 (2025-07-31)

The deprecated use of libraries and bundles in the plugins {} block of Kotlin DSL scripts is removed (the build fails).

Source: Gradle 7.0 release notes: Centralized dependency versions, 7.2: Version catalog improvements, 7.4: Version catalogs, 8.5: Build init utilizing version catalogs, 8.5: Version catalog API in precompiled scripts, Upgrading from 8.x: parser upgrade, 8.8: aliases without a version and Upgrading to 9.0: removal in the plugins block

The book Gradle in Action was written for Gradle 1.7 and predates catalogs by eight years: its builds keep versions in ext or in plain local variables and declare them with the compile and testCompile configurations, which were removed in Gradle 7.0 (see Versions, Compatibility & Release History). Translate the idea (one place for versions) into a catalog and the configurations into implementation and testImplementation.

The tidepool catalog

The catalog file lives in the gradle directory of the root build, with exactly the name libs.versions.toml. Gradle imports that file automatically, under the catalog name libs, so nothing in settings.gradle(.kts) mentions it. The file below is the one used on the whole page. It is shown as plain text because the syntax highlighter has no TOML grammar:

The TOML format

The file has four tables. Everything is optional; an alias in one table never conflicts with the same alias in another.

Table Purpose

[versions]

Named versions that libraries and plugins refer to with version.ref. A version can be a plain string (a required version) or a rich version.

[libraries]

Aliases for coordinates: group, name and (optionally) a version.

[bundles]

Aliases for lists of library aliases, so that a group that always travels together is declared with one name.

[plugins]

Aliases for a plugin id and its version.

Source: Gradle User Manual: The TOML format

Versions

[versions]
other-lib = "5.5.0"                                      # a required version
my-lib = { strictly = "[1.0, 2.0[", prefer = "1.2" }     # a rich version

The members of a version table are require, strictly, prefer, reject (a list of rejected versions) and rejectAll (a boolean). Their meaning is the one of rich versions in a build script, described on Platforms, Constraints & Rich Versions. The catalog is only a way to write the same thing down. With the catalog changed to

[versions]
commons-csv = { strictly = "[1.10, 2.0[", prefer = "1.13.0", reject = ["1.12.0"] }

and nothing else touched, the engine project resolves the preferred version, and the tree prints the whole rich version before the arrow (the same in both DSLs):

$ ./gradlew :tidepool-engine:dependencies --configuration runtimeClasspath
...
runtimeClasspath - Runtime classpath of source set 'main'.
+--- project ':tidepool-model'
\--- org.apache.commons:commons-csv:{strictly [1.10, 2.0[; prefer 1.13.0; reject 1.12.0} -> 1.13.0
     +--- commons-io:commons-io:2.18.0
     \--- commons-codec:commons-codec:1.17.2

Source: Gradle User Manual: Versions

The transitive versions changed with the library (commons-io 2.18.0 instead of 2.20.0), which is the reason a catalog entry is a requirement and not a pin; pinning every transitive version is the job of dependency locking (see Dependency Locking, Verification & Caching).

Libraries

A library is a string with the coordinates, or a table. All the forms below are valid; the first column is what the manual shows:

Declaration Meaning

my-lib = "com.mycompany:mylib:1.4"

A string is group, name and version.

my-lib-no-version.module = "com.mycompany:mylib"

A dotted key (a TOML shortcut for a table) with no version; the version comes from somewhere else (a platform).

my-other-lib = { module = "com.mycompany:other", version = "1.4" }

module is group and name in one string; version is a literal version.

my-other-lib2 = { group = "com.mycompany", name = "alternate", version = "1.4" }

Group and name written separately.

mylib-full-format = { group = "com.mycompany", name = "alternate", version = { require = "1.4" } }

The version is itself a table with require, strictly, prefer, reject or rejectAll.

my-lib = { group = "com.mycompany", name = "mylib", version.ref = "some" }

version.ref names an entry of [versions], so several libraries share one version.

Source: Gradle User Manual: Libraries

What a library entry cannot say matters as much. Version catalogs capture only the coordinates and a version: classifiers, artifact types, exclusion rules and capability requirements are not supported in the TOML file, and an unknown key is a failure (see the problems below). The workarounds are in the section on classifiers.

Bundles

[libraries]
junit-jupiter = { module = "org.junit.jupiter:junit-jupiter" }
assertj-core = { module = "org.assertj:assertj-core", version.ref = "assertj" }

[bundles]
testing = ["junit-jupiter", "assertj-core"]

A bundle is used wherever a dependency is, and adds every member to that one configuration: testImplementation(libs.bundles.testing). A bundle cannot say that one member is an api dependency and another runtimeOnly; the tidepool catalog therefore keeps junit-launcher out of the bundle, since it belongs to testRuntimeOnly. A bundle can refer only to aliases of the same catalog; an alias that does not exist is a failure.

Source: Gradle User Manual: Bundles

Plugins

[plugins]
versions = { id = "io.github.ben-manes.versions", version = "0.66.0" }

Two rules about plugin aliases come straight from the manual and from the release notes:

  • A plugin from a catalog can be used in a plugins {} block of a build script, but not in the plugins {} block of the settings file or a settings plugin. In the Kotlin DSL the attempt fails to compile with Unresolved reference 'libs', because there is no catalog yet while settings are being evaluated.

Aliases and type-safe accessors

When the settings are evaluated, Gradle reads the catalog and generates one class per catalog (org.gradle.accessors.dm.LibrariesForLibs for libs), registers an instance as the extension libs on every project, and exposes the catalog in four namespaces:

Accessor Type of the value Example from the tidepool catalog

libs.<alias>

A provider of a MinimalExternalModuleDependency

libs.commons.csv, libs.picocli

libs.versions.<alias>

A provider of the version as a String

libs.versions.picocli.get() is 4.7.7

libs.bundles.<alias>

A provider of an ExternalModuleDependencyBundle

libs.bundles.testing

libs.plugins.<alias>

A provider of a PluginDependency (id and version)

libs.plugins.versions

Source: Gradle Javadoc: MinimalExternalModuleDependency, Gradle Javadoc: ExternalModuleDependencyBundle and Gradle Javadoc: PluginDependency

Because the accessors are providers, they are lazy and safe for the configuration cache, and they can be passed to any API that takes a provider of a dependency (dependencies.add(...), constraints, testImplementation(...)) without calling get().

How an alias becomes an accessor

An alias is made of identifiers separated by a dash or an underscore. Gradle normalises the separators to dots and each dot starts a nested group, so that an IDE can offer completion level by level:

Alias in the file Accessor Notes

commons-csv

Naming rules and the errors for breaking them

An alias must match the regular expression below. Experiments with the tidepool catalog show what Gradle does with names that do not:

[a-z]([a-zA-Z0-9_.\-])+
Alias added to the catalog Result on Gradle 9.8.1

my_lib

Accepted, becomes libs.my.lib.

groovyCore

Accepted, becomes libs.groovyCore.

Upper or 1abc

Invalid alias notation: library aliases must match the following regular expression.

Alias!

TOML syntax error: Unexpected '!', expected = (in a TOML file the character is rejected by the TOML parser before Gradle’s alias check).

my.lib

TOML syntax error: Dots (.) in TOML keys create nested entries and cannot be used in alias names.

extensions

Reserved alias name: extensions and convention are reserved.

versions-dependency

Reserved alias name: Prefix for dependency shouldn't be equal to 'versions'. The first segment of a library cannot be bundles, plugins or versions, because those are the namespaces above.

The rules this example shows, with the reproduction of each:

  • from can be called once per catalog. The default file gradle/libs.versions.toml is imported automatically, so declaring create("libs") { from(files("gradle/libs.versions.toml")) } calls from a second time and fails in both DSLs. That is the reason the example moved the file to another name. The same applies to a catalog built from two files. The failure:

    $ ./gradlew help

* What went wrong:

    The method was called more than once
    For more information, please refer to https://docs.gradle.org/9.8.1/userguide/version_catalog_problems.html#too_many_import_invocation in the Gradle documentation.
    Possible solution: Remove further usages of the method call.

  • from takes exactly one file. Importing a missing file and importing two files at once each fail with their own message:

    > Import of external catalog file failed
    In version catalog tools, import of external catalog file failed
      File '/work/tidepool/gradle/tools.versions.toml' doesn't exist

  • Calls after from add or override entries. version("picocli", "4.7.6") replaced the version that the TOML file declared, and every library that refers to it with version.ref followed. An override affects only what is imported and what is written in dependency declarations: the resolved version can still differ because of conflict resolution.

  • The programmatic API has the same four verbs as the file: version, library, bundle and plugin. A library declared without a version in its notation is finished by versionRef, version or withoutVersion; one that is not finished is the problem alias_not_finished, an alias that was created but not registered.

  • Every catalog is its own extension on all projects. Pick a name that cannot collide with an existing extension (the manual suggests a name that ends with Libs, as testLibs above), and do not use libs for a programmatic catalog when a gradle/libs.versions.toml exists.

Changing the name of the default catalog

The default catalog is called libs. If that name is taken (for example by an extension of a plugin), rename it for the whole build:

Kotlin DSL: settings.gradle.kts
dependencyResolutionManagement {
    defaultLibrariesExtensionName = "tidepoolLibs"
}
Groovy DSL: settings.gradle
dependencyResolutionManagement {
    defaultLibrariesExtensionName = 'tidepoolLibs'
}

With the setting in place gradle/libs.versions.toml is still imported, but as tidepoolLibs, and the scripts must use the new name (implementation(tidepoolLibs.picocli)). Scripts that still said libs failed with Unresolved reference 'libs' (Kotlin DSL) and with a script compilation problem (Groovy DSL); after renaming them, both DSLs built and printed the same graph as before.

Source: Gradle User Manual: Changing the catalog name

More than one catalog, or one

The manual is sceptical about splitting. A single catalog centralises every coordinate, avoids version duplication and gives every project the same accessors; use alias prefixes to group entries (junit-..., mockito-...) inside it. Split only when you need a boundary the file itself cannot express:

  • Auditing what ships. When you must distinguish the dependencies of a published distribution from those used only for tests or code generation, separate catalogs make the difference visible where the dependency is declared.

  • Independent build logic. Plugins applied inside build-logic or buildSrc may need their own catalog, resolved before the main build’s catalog exists.

  • Organisational sharing. A company-wide catalog is published as an artifact and imported by many repositories, while each repository keeps a local catalog for its own dependencies.

Source: Gradle User Manual: Working with multiple version catalogs

Sharing one version between catalogs

Each TOML file is self-contained. There is no include and no version.ref that reaches into another file, and from is allowed once, so two files cannot be merged. If a version must be the same in two catalogs, the manual describes three workarounds: declare it in both files and add a check that they agree; keep the shared versions in a properties file that settings.gradle(.kts) injects into each catalog (what the Gradle project itself does); or publish a base catalog and layer local overrides on top (the section on publishing below). The second workaround, run on tidepool with gradle/shared-versions.properties holding commons-csv=1.14.1 and picocli=4.7.7 and those two versions removed from the TOML file:

Kotlin DSL: settings.gradle.kts
val shared = java.util.Properties().apply {
    file("gradle/shared-versions.properties").inputStream().use { load(it) }
}

dependencyResolutionManagement {
    repositoriesMode = RepositoriesMode.FAIL_ON_PROJECT_REPOS
    repositories {
        mavenCentral()
    }
    versionCatalogs {
        create("libs") {
            from(files("gradle/tidepool.versions.toml"))
            version("commons-csv", shared.getProperty("commons-csv"))
            version("picocli", shared.getProperty("picocli"))
        }
    }
}

Publishing and importing a catalog

There are three ways to share a catalog between builds, in increasing effort: check the TOML file into a shared repository that all builds can see; write a settings plugin that declares the entries and publish it; or publish the catalog as an artifact with the version-catalog plugin. The last is the way for an organisation that distributes one catalog to many independent builds, and it is the one run here.

Publishing

Applying version-catalog adds a catalog extension, the task generateCatalogAsToml, and a software component versionCatalog that a publication attaches. The easiest source is the existing TOML file, which then stays the single source of truth:

Kotlin DSL: tidepool-catalog/build.gradle.kts
plugins {
    `version-catalog`
    `maven-publish`
}

group = "io.tidepool"
version = "1.0.0"

catalog {
    versionCatalog {
        from(files("gradle/libs.versions.toml"))
    }
}

publishing {
    publications {
        create<MavenPublication>("catalog") {
            from(components["versionCatalog"])
        }
    }
    repositories {
        maven {
            name = "local"
            url = uri(layout.buildDirectory.dir("repo"))
        }
    }
}

The consumer imports the catalog in settings with ordinary dependency notation. Gradle downloads the TOML file from the repositories declared in dependencyResolutionManagement (so the repository that serves the catalog must be listed there), and any entry can be overridden afterwards:

Catalogs and platforms

A catalog and a platform answer different questions. A catalog decides what you write; a platform decides what Gradle selects.

Version catalog Platform (java-platform, BOM)

Purpose

Names the coordinates and versions that a build declares, with type-safe accessors.

A module in the dependency graph that supplies or enforces versions for dependencies, including transitive ones.

Effect on resolution

None by itself: a version from the catalog is an ordinary requirement.

Constraints take part in conflict resolution and are propagated to consumers.

Visible to consumers of your library

No: they cannot tell that a dependency came from a catalog.

Yes: it is part of your published metadata.

Typical use

Share coordinates across the projects of one build, or across builds.

Align versions across modules and enforce them.

Classifiers, artifact types and the TOML limits

The TOML file cannot express classifiers, artifact types (@aar, @zip), exclusion rules or capability requirements. The workaround is to declare these where the dependency is declared, using the catalog entry as the base. A classifier is added with variantOf:

Kotlin DSL: tidepool-engine/build.gradle.kts
plugins {
    `java-library`
}

val sources by configurations.creating {
    isCanBeConsumed = false
    isTransitive = false
}

dependencies {
    api(project(":tidepool-model"))
    implementation(libs.commons.csv)
    sources(variantOf(libs.commons.csv) { classifier("sources") })
}

tasks.register("showSources") {
    val jars = sources.incoming.files
    doLast { jars.forEach { println(it.name) } }
}
Groovy DSL: tidepool-engine/build.gradle
plugins {
    id 'java-library'
}

configurations {
    sources {
        canBeConsumed = false
        transitive = false
    }
}

dependencies {
    api project(':tidepool-model')
    implementation libs.commons.csv
    sources variantOf(libs.commons.csv) { classifier('sources') }
}

tasks.register('showSources') {
    def jars = configurations.sources.incoming.files
    doLast { jars.each { println it.name } }
}
$ ./gradlew -q :tidepool-engine:showSources
commons-csv-1.14.1-sources.jar

Both DSLs resolved the sources JAR from the same catalog entry that the production dependency uses, and the task is configuration cache compatible (a second run said Configuration cache entry reused). The same variantOf is used for platform-specific native artifacts (classifier("linux-x86_64")); for test fixtures the manual prefers testFixtures(libs.my.lib) over spelling the classifier. An artifact type is set in an artifact {} block of the dependency (artifact { name = "my-lib"; type = "aar" }), the form that Android builds use; it was not run here because it needs an Android library (see Project Structure & Gradle for a catalog in an Android project). Exclusions and capabilities are written in the dependency’s own configuration closure, as on Dependency Resolution, Conflicts & Capabilities.

Naming entries

The best practices page asks for consistent, descriptive aliases and gives rules that make the accessors read well. They are guidelines, not checked by Gradle:

  • Separate segments with dashes, not underscores (log4j-api).

  • Derive the first segment from the group, without the top-level domain (jackson-databind, armeria-grpc), and the second from the artifact.

  • Leave out generic terms such as core, java, gradle, module or sdk when they stand alone (google-java-format, not google-java).

  • Omit a repeated segment when group and artifact agree (ktor-client-core, not ktor-ktor-client-core).

  • Turn internal dashes of the artifact into camelCase (springBootStarterWeb), which also avoids unwanted sub-groups.

  • Suffix a plugin that is declared as a library (not in [plugins]) with -plugin (dependency-check-plugin).

The same page warns against the opposite misuse: a catalog is for coordinates and versions, not for shared strings, constants or build logic. It also says that a catalog only influences declared versions, so combine it with dependency locking and version alignment when the resolved versions must be pinned.

Source: Gradle User Manual: Name Version Catalog Entries Appropriately

Classic mistakes

Mistake What happens and the fix

Treating the catalog version as the resolved version

A platform, a constraint, a higher transitive requirement or a rule changes the selection. Check with dependencies or dependencyInsight.

create("libs") { from(files("gradle/libs.versions.toml")) } in settings

The file is already imported, so from is called twice: Multiple 'from' invocations. Delete the block, or rename the file.

Using libs in buildSrc or build-logic without importing the file

Unresolved reference 'libs' (Kotlin DSL) or Could not get unknown property 'libs' (Groovy DSL). Import the file in the settings of that build.

A library or bundle in the plugins {} block

Fails on Gradle 9 (Accessing libraries or bundles from version catalogs in the plugins block is not allowed). Use plugin aliases only.

A catalog plugin alias in the settings file

Not supported: the catalog does not exist yet while the settings are evaluated.

Aliases that differ only in separators or case

Accessor name clash. One spelling per name.

libs.versions.jackson.get() when jackson-databind also exists

The sub-group has no get(); use asProvider(), or camelCase names.

A version-less alias without a platform

Could not find org.junit.jupiter:junit-jupiter:. (empty version). Import the BOM, or give the alias a version.

Putting a classifier, an exclusion or a capability in the TOML file

Not supported (Invalid TOML definition for an unknown key). Declare it in the build script around the catalog entry.

Reading the catalog extension inside doLast

Captures the project and breaks the configuration cache; read it while configuring and keep only values.

Editing the published TOML or trusting a floating catalog version

Pin an exact catalog version and verify it like any other artifact.
