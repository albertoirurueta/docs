Migrating from Maven to Gradle

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Gradle 9.8.1 (released on 7 October 2026) and Apache Maven 3.10.0, with Gradle 8.14.6, the last 8.x release, mentioned where it differs. Every example marked as run was executed on 2026-10-16 on macOS (Apple silicon), on Oracle JDK 26 (java version "26", the default JDK of the machine), once with *.gradle.kts files and once with *.gradle files. The Gradle runs used the 9.8.1 distribution, and the Maven runs used 3.10.0 with a local repository created for the page. The Java code is compiled for Java 17 (release 17), so the same builds work on JDK 17 and 21. The Gradle examples are compatible with the configuration cache (org.gradle.configuration-cache=true was set and the second run reused the entry), except the one failure that is shown on purpose. The numbers in the output use the English locale (-Duser.language=en -Duser.country=US), because the machine’s default would print a decimal comma. Long output is shortened with a line that contains only …, and the scratch directory is shown as …. Gradle 8.14.x was not available, so what is said about it comes from the official documentation and is labelled "not run here". Two more things were not run and are labelled the same way: Build Scans (publishing to the Develocity service needs the acceptance of its terms of use) and publishing to a remote repository such as Maven Central; the publishing runs went to a file: repository inside the build directory.

The usual path from Maven to Gradle is to keep the Maven build, add a Gradle build next to it, convert the structure with gradle init, and then repair what the converter cannot know. This page follows that path with a real multi-module build and records every failure on the way. The shared page Migrating Between Tools has the overview of all migration directions and a single-module Maven to Gradle conversion; this page goes deeper into the Gradle side and into the parts of a multi-module POM that the shared page does not cover: the parent POM, dependencyManagement, inherited plugin configuration, Failsafe, Shade and the published POMs. For the vocabulary behind the two tools see Build Automation Fundamentals, Dependency Management Fundamentals and Comparing Ant, Maven & Gradle.

The migration in seven steps

The Gradle user manual recommends this order for any Maven build, and the sections of this page follow it. Do not change the source layout, the artifact coordinates or the Maven build while you migrate: the Gradle build should produce the same artifacts, so that the switch is a matter of the CI pipeline.

flowchart TD A[1. Keep the Maven build and run it in CI] --> B[2. Add the Gradle build beside it: gradle init] B --> C[3. Fix what init could not know: Java release, test framework, filtering, profiles] C --> D[4. Verify dependencies against mvn dependency:tree] D --> E[5. Rebuild integration tests and replace Maven plugins] E --> F[6. Compare artifacts, POMs and test results] F --> G{Same outputs?} G -- no --> C G -- yes --> H[7. Switch CI and releases, then delete the pom.xml files]

Source: Gradle User Manual: Migrating from Maven, general guidelines

The manual also suggests creating a Build Scan of both builds and comparing them. That was not run here (publishing a scan needs the acceptance of the terms of use of the Develocity service); the local --profile report and the dependency reports used below give the same information without leaving the machine. See Performance Profiling & Build Scans.

Step 1 and 2: automatic conversion with gradle init

gradle init run in a directory that has a pom.xml offers to convert it, and the type pom is inferred automatically when the file exists. The conversion reads the effective POM and the effective settings, so inheritance, dependencyManagement and properties are already resolved when it writes the Gradle files, and it handles single-module and multi-module builds. It leaves every Maven file untouched, so both builds can live in the same directory: Maven writes target/, Gradle writes build/, and nothing in the sources changes. The manual lists what is converted: the general metadata (group, name, version, description), the plugins maven-publish, java-library and war, the compiler settings, the external and inter-module dependencies, the repositories (including the local Maven repository), sources and Javadoc packaging, the TestNG runner, exclusions, and global exclusions from the Enforcer plugin; whatever else the POM does is not converted. A Maven compile dependency is mapped to api, which keeps the exposed dependencies of the Maven project and which the manual asks you to revisit after the conversion.

Source: Gradle User Manual: Build Init plugin, Maven conversion and Gradle User Manual: Migrating from Maven, automatic conversion

2. The JUnit Platform launcher has no version. In the POM, junit-jupiter and the launcher that Surefire adds by itself take their versions from the imported junit-bom. The conversion copied the resolved version of junit-jupiter as a literal, did not import the BOM and did not select the JUnit Platform for the test task. Maven has an implicit repository, Central; Gradle has none, so every build must declare at least one. Managed versions: properties, dependencyManagement and the catalog

A parent POM manages versions in two places: properties such as <commons-csv.version> and the <dependencyManagement> block that uses them. Gradle has three tools for the same job, and they are not interchangeable:

Maven idiom Gradle replacement

A version property used by one or two dependencies

An entry in the [versions] table of gradle/libs.versions.toml, referenced with version.ref. The catalog is the same for every project of the build, and for the included build-logic build.

<dependencyManagement> entry for a third-party library, with the dependency declared without a version in the module

A catalog library (libs.commons.csv) with the version; the module declares the library. If the version must also apply to transitive dependencies, add a dependency constraint (constraints { }) or a platform.

<dependencyManagement> entry for a sibling module

Nothing: project(":tidepool-model") has no version, because the project is part of the build.

import of a BOM

platform(...) or enforcedPlatform(...).

A parent POM of a company that only manages versions (a BOM that other builds import)

The java-platform plugin, which publishes a BOM.

BOMs, platforms and java-platform

The import of the JUnit BOM, in the convention plugin above, is testImplementation(platform(libs.findLibrary("junit-bom").get())). A platform adds the version constraints of the BOM to the dependency graph; junit-jupiter and the launcher then need no version of their own. platform() takes the <dependencyManagement> constraints of the POM and ignores the <dependencies> block of the BOM; enforcedPlatform() makes the constraints strict, so that a higher version requested elsewhere in the graph cannot override them. The Maven scope of a BOM import is always import; in Gradle the import is a normal dependency declaration in the configuration where you want the constraints (implementation, testImplementation, or both).

A Maven <modules> block is an include(...) in settings.gradle(.kts) (the conversion did this for the three modules). The dependency of one module on another becomes project(":name"), and a project dependency is both the ordering and the artifact reference; the order of the reactor, which Maven derives from the dependencies, is derived in the same way. ./gradlew projects lists the result:

Inheritance has no direct counterpart. In Maven, a child POM inherits dependencies, plugins, properties and configuration from its parent in a fixed model. In Gradle the same sharing is a convention plugin (a plugin that configures other plugins), and the allprojects { } and subprojects { } blocks that injected configuration in older builds are the form the manual discourages, because they couple projects to each other. The parts of the parent POM map as follows:

Parent POM Convention plugin or settings

<groupId>, <version>

<dependencies> (inherited by every module)

The dependencies { } block of the plugin

<dependencyManagement>

Catalog, platform or constraints (see above)

<pluginManagement> (plugin versions)

<build><plugins> (plugins applied to every module)

plugins { } in the convention plugin

<properties>

gradle.properties, the catalog, or local vals

<profiles>

Project properties tested in the scripts (see below)

<repositories>

dependencyResolutionManagement { repositories { } } in the settings file

A module that does not belong to the parent (an aggregator without inheritance, or a parent in another repository) maps to a build with its own convention plugin, published to a plugin repository or included as a build with includeBuild. The shared logic of this build is in the included build build-logic; the conversion’s buildSrc is the same idea in a fixed location, and the page on convention plugins compares the two. Profiles and properties

A Maven profile is, as the manual says, a limited if statement. Gradle does not need formal profiles because the build script is a program: it can test a project property, an environment variable, the operating system or the JDK. The profile ci of tidepool only sets the property deploy.env; the equivalent is a project property:

Kotlin DSL: tidepool-cli/build.gradle.kts (the part about the profile and the filtering)
// Maven profile "ci" -> a project property: ./gradlew build -Pci
val deployEnv = providers.gradleProperty("ci").map { "ci" }.orElse("dev")
val projectVersion = version.toString()
Groovy DSL: tidepool-cli/build.gradle (the part about the profile and the filtering)
// Maven profile "ci" -> a project property: ./gradlew build -Pci
def deployEnv = providers.gradleProperty('ci').map { 'ci' }.orElse('dev')
def projectVersion = version.toString()

providers.gradleProperty is a lazy, configuration-cache aware way of reading a project property: Gradle remembers that the build used the property and discards the cached configuration if its value changes. A -Pci on the command line has no value (-Pci sets it to an empty string), so the map ignores the value and tests only the presence. The usual forms are -Penv=ci read with orElse("dev"), or a switch in gradle.properties of a CI image.

Three differences between the two systems cause most surprises:

  • -P means a profile in Maven and a project property in Gradle. mvn -Pci activates all the settings of the profile; ./gradlew -Pci changes nothing unless a script reads the property. A converted build ignores the profiles silently; the conversion does not warn about them.

  • Profile activation by the JDK, the operating system, the presence of a file or a property (<activation>) becomes plain code. The manual shows a technique with profile scripts (profile-test.gradle, profile-prod.gradle) applied with apply(from = ...) according to a property, and warns that conditions in the build make it harder to understand; prefer several tasks of the same type (the manual’s example is that the Maven Publish plugin creates one publish task per publication and repository) over a switch.

  • The properties of the POM that the maven-resources-plugin reads (${project.version}, ${deploy.env}) exist only in Maven. The Gradle replacement is shown in the next section; the environment of the build (JVM options, parallelism, caches) goes into gradle.properties and is described in Build Environment & Properties. A gradle.properties in the project root is overridden by the one in the Gradle user home and by command line options; a property set in the build script wins over every external file.

The profiles of a settings.xml (credentials, mirrors, repository URLs for a company network) are a user-level matter: credentials go to ~/.gradle/gradle.properties or to environment variables, and the mirror to the setting described in Repositories & Content Filtering. See Maven Profiles and Maven settings.xml & Password Encryption.

Resource filtering

The filtered resource of the CLI is tidepool.properties, with the Maven placeholders ${project.version} and ${deploy.env}. The Gradle task processResources does the same copy, and its expand method treats the file as a Groovy template. If you keep the file unchanged during the parallel period, both builds must be able to fill the placeholders. The trick is that the template engine resolves ${project.version} as property version of an object called project, so the binding can provide maps with those names:

Kotlin DSL: tidepool-cli/build.gradle.kts
tasks.processResources {
    val env = deployEnv
    val ver = projectVersion
    inputs.property("deployEnv", env)
    inputs.property("projectVersion", ver)
    filesMatching("tidepool.properties") {
        expand(
            "project" to mapOf("version" to ver),
            "deploy" to mapOf("env" to env.get())
        )
    }
}
Groovy DSL: tidepool-cli/build.gradle
tasks.named('processResources') {
    def env = deployEnv
    def ver = projectVersion
    inputs.property('deployEnv', env)
    inputs.property('projectVersion', ver)
    filesMatching('tidepool.properties') {
        expand(project: [version: ver], deploy: [env: env.get()])
    }
}

The two inputs.property lines declare the values as inputs, so that a build with another profile re-runs the task instead of reusing the output. Without the property, processResources would be up to date after a change from dev to ci. Both values were checked:

./gradlew :tidepool-cli:processResources
cat tidepool-cli/build/resources/main/tidepool.properties
./gradlew :tidepool-cli:processResources -Pci
cat tidepool-cli/build/resources/main/tidepool.properties
version=1.0.0
env=dev
> Task :tidepool-cli:processResources
version=1.0.0
env=ci

(The first command’s task line, UP-TO-DATE, and the build summaries are left out.) The second run executed the task, as the line shows.

The same code written the obvious way fails with the configuration cache, which is why the val env = deployEnv lines exist. The first version of the script read the script-level val deployEnv and val projectVersion inside the filesMatching action. The action is stored in the configuration cache, and a reference to a top-level val of a Kotlin script is a reference to the script object, which cannot be stored:

FAILURE: Build failed with an exception.

* What went wrong:
Configuration cache problems found in this build.

1 problem was found storing the configuration cache.
- Task `:tidepool-cli:processResources` of type `org.gradle.language.jvm.tasks.ProcessResources`: cannot serialize Gradle script object references as these are not supported with the configuration cache.
  See https://docs.gradle.org/9.8.1/userguide/configuration_cache_requirements.html#config_cache:requirements:disallowed_types

The remedy is to copy the values into local variables of the configuration block, as in the script above (the failing version was the same without the two local val lines). Reading project.version or other project properties in the action, at execution time, is a related error: it is deprecated by Gradle 9.x and will fail in Gradle 10; read it into a variable first.

Two details differ from Maven. expand treats the whole file as a template, so every $ is interpreted; a file with literal dollars needs filter with org.apache.tools.ant.filters.ReplaceTokens (the @token@ style that Maven also supports). And the Maven <propertiesEncoding> setting corresponds to nothing here: Gradle copies with the platform encoding for expand, so set filteringCharset = "UTF-8" on processResources if the files contain non-ASCII characters. See Working with Files and Maven Resources & Filtering.

Tests and integration tests

Surefire runs the *Test classes in the test phase, and Failsafe runs the *IT classes in integration-test, then checks the result in verify; the split exists so that a failing integration test does not skip the cleanup that follows it. Gradle runs the test source set with the Test task, and check depends on it. Three things are needed:

  • Select the JUnit Platform for every Test task (useJUnitPlatform(), in the convention plugin) and give the test runtime classpath the launcher. Surefire brings both by itself.

  • Pass the system properties that the plugin configuration passed. systemPropertyVariables is systemProperty(...) on the task; the data file location comes from the root project directory instead of the project.parent.basedir of the POM.

  • Keep integration tests apart from the unit tests.

For the period in which both builds must work on the same sources, the engine module above uses the file naming convention: the test task excludes **/*IT.class, and a second Test task, integrationTest, reuses the class directories and the classpath of the test source set and includes only those classes, and check depends on it. That mimics Surefire plus Failsafe in the Maven layout. The recommended form for a finished migration is the JVM test suite plugin, with the integration tests in src/integrationTest/java, where check depends on the suite and each suite has its own dependencies; the manual’s integration-test section describes it and Migrating Between Tools shows a complete example. Failsafe keeps the build alive until verify; a Gradle suite fails the build unless ignoreFailures is set. Cleanup that must always run goes into a task attached with finalizedBy. See Testing JVM Projects, Testing with Surefire and Maven Integration Testing with Failsafe.

The manual makes this the most important step: a Gradle build that produces the same outputs lets you switch with confidence. Both builds in the same directory

The two builds can live side by side for as long as needed. pom.xml and settings.gradle(.kts) do not interfere, the Maven output is in target/ and the Gradle output in build/, and neither tool reads the other’s files. Three precautions avoid surprises:

  • Ignore both output directories (target/, build/ and .gradle/) in version control.

  • Give each build its own -D and -P conventions and test both in CI: run mvn verify and ./gradlew build on the same commit, then compare the outputs as shown above. When the Gradle build is trusted, make it the build that releases, and remove the pom.xml files in a later commit.

  • Do not use mavenLocal() or publishToMavenLocal to hand artifacts between the two builds unless a downstream Maven project requires them. A stale artifact in ~/.m2 is a typical cause of "it works on my machine" in a migration.

Classic mistakes

  • Trusting the converted build. The generated build compiled for Java 8, did not select the JUnit Platform, dropped the profile, the filtering, the system properties, Failsafe and Shade, and wrote api for every dependency. Treat gradle init as the way to get the module list and the dependency coordinates, and review every file it wrote.

  • Passing -Pci and expecting a profile. Nothing happens unless a script reads the property. Search the POMs for <profile> before you start and list the settings each profile changes.

  • Comparing only the build result. A green ./gradlew build says nothing about the version of commons-io that is on the classpath. Compare the dependency trees (mediation), the JAR contents and the POMs.

  • Leaving mavenLocal() as the first repository. It resolves artifacts that no repository provides and hides missing publications.

  • Reading project in a task action. The configuration cache rejects or warns about it; capture the value in a local variable (or a provider) while the task is configured.

  • Moving everything at once. Converting the build, the layout and the CI pipeline in one change makes a failure impossible to diagnose. Convert the build first; keep the layout and the artifacts the same; change them later.

  • Forgetting that the wrapper is a file of the project. gradle init writes a wrapper without a checksum. Add distributionSha256Sum and commit gradle/wrapper/gradle-wrapper.jar and the properties.

  • Expecting the same task order. A Gradle build runs what the task graph requires, in an order that is only partly defined, and runs independent tasks in parallel with the configuration cache. Declare real dependencies (dependsOn, inputs and outputs), not sequences.

Where the books are outdated

Gradle in Action (Muschko, Manning 2014) covers the Ant and Maven migration in chapter 9, for Gradle 1.7. What it describes and what replaced it:

  • The maven2gradle tool. The conversion of a POM is now the pom type of the init task of the Build Init plugin, whose implementation was inspired by maven2gradle; it also reads the effective POM, so it handles inheritance and dependencyManagement. The incubating setupBuild task of Gradle 1.x is the same init task.

  • The compile, runtime, testCompile and testRuntime configurations in the converted dependency blocks, removed in Gradle 7.0. Use implementation, api, compileOnly, runtimeOnly, testImplementation and testRuntimeOnly.

  • The maven plugin and uploadArchives for publishing and installing, removed in Gradle 7.0. Use maven-publish with publish and publishToMavenLocal.

  • Declaring dependency versions in ext properties in the root build. Use a version catalog (stable since 7.4) or a platform.

  • Injecting configuration with allprojects and subprojects from the root build. Use convention plugins in build-logic.

  • apply plugin: 'x'. Use the plugins { } block.

  • jcenter() as the repository of the examples. Removed in 9.0.0, and Bintray, which hosted JCenter, was shut down in 2021. Use mavenCentral().
