Gradle Build Cache

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Gradle 9.8.1 (the current release on 2026-10-16). Every example was run through the Gradle wrapper on macOS with JDK 26 (Oracle java version "26"), which was both the JVM of the daemon and the JDK that compiled and tested the code, except in the one section that deliberately switches the JDK with a toolchain (JBR 21.0.10, found in the user’s JDK directory; automatic JDK downloads were switched off with org.gradle.java.installations.auto-download=false). The Kotlin DSL is shown first and the Groovy DSL second wherever the syntax differs, and both versions of the tidepool build were run with the same commands; the console output is the same apart from timings, from the order of independent tasks, from the names of script classes (Build_gradle.StationSummary in the Kotlin DSL against StationSummary in the Groovy DSL) and the hashes that depend on them, and from the differences named in the text. Every build ran with the configuration cache on (org.gradle.configuration-cache=true in gradle.properties) and reported no configuration cache problems, except the one example that is labelled as a configuration cache failure. A build cache example must start from an empty cache, so the examples ran with a scratch Gradle User Home (GRADLE_USER_HOME) of their own, whose caches/build-cache-1 directory was emptied before each group of runs; nothing of the real user home was read or deleted. Gradle can skip a task in two ways. The first is the up-to-date check: if the inputs and outputs of the task are the same as in the previous execution in the same workspace, the task is skipped with the outcome UP-TO-DATE (see Gradle Incremental Build). That memory is short: it holds the last execution of each task and nothing else, so switching a branch back and forth, running clean, or building the same commit in a second checkout all start from scratch. The second way is the build cache: Gradle stores the outputs of a task under a key computed from everything that influences them, and any later build, in any directory on the machine or, with a remote cache, on any machine, that computes the same key unpacks the stored outputs instead of running the task. That outcome is FROM-CACHE. The Ant answer to this problem is a time-stamp comparison that the build author writes (see Ant Conditions & Control Flow) and nothing that outlives the workspace; the Maven answer is an optional core extension, the Apache Maven Build Cache Extension (see Maven Build Performance). The shared vocabulary is on Build Automation Fundamentals. The reason why Gradle can do this reliably is the model described on Gradle Tasks and Writing Custom Tasks: every task declares what it reads and what it writes.

Gradle has several things called a cache, and the build cache is only one of them. Most of the confusion about "the cache" in a Gradle question comes from mixing them up.

The build cache is the only one of the four that is shared between checkouts and, if you configure a remote node, between machines; it is also the only one that can make a wrong result appear (a cache hit for a task whose inputs were not fully declared), which is why most of this page is about declaring inputs correctly.

Release history

Task output caching arrived in 2017 as an incubating feature and has been stable since the 4.x series; its configuration and its cleanup changed since. The dates are those of the Gradle versions list; the changes are from the release notes and upgrade guides of each version.

Release (date) Change

3.3 (2017-01-03)

Task output properties get unique names, which prepares Gradle for the build cache that followed.

3.5 (2017-04-10)

The build cache is introduced as an incubating feature: a local directory cache and a remote HTTP cache, task output caching.

4.0 (2017-06-14)

Production-ready for Java and Groovy compilation and Java test tasks; overlapping task outputs disable caching; configurable input normalization (ignore runtime classpath resources); the remote cache honours --offline; automatic cleanup of the local cache.

4.5 (2018-01-24)

Included builds of a composite share the build cache configuration of the root build; C/C++ compilation caching stable; the ANTLR task becomes cacheable.

5.0 (2018-11-26)

buildSrc builds use the build cache configuration of the top-level settings; the local cache must be a DirectoryBuildCache; the JaCoCo plugin works with the build cache.

6.0 (2019-11-08)

Announced deprecation warning for pulling cache hits from a remote cache over insecure HTTP; tasks with incorrectly declared inputs or outputs are called out during the build.

7.0 (2021-04-09)

A task that fails input/output validation runs without parallel execution, up-to-date checks and the build cache.

8.8 (2024-05-31)

Cleanup of the local cache is configured like the other caches of the Gradle User Home, in an init script (caches { buildCache.setRemoveUnusedEntriesAfterDays(...) }); Cleanup.DISABLED and Cleanup.ALWAYS apply to it; the remote cache is disabled for Groovy build script compilation (introduced in 8.7).

9.0.0 (2025-07-31)

buildCache.local.removeUnusedEntriesAfterDays (deprecated in 8.8) and the org.gradle.cache.cleanup property are removed.

9.7.0 (2026-08-06)

Kotlin DSL accessor generation is no longer stored in the build cache.

How a cached task execution works

When a task is about to execute, Gradle goes through the steps of the figure. The up-to-date check comes first and is purely local; the build cache is consulted only for a task that is not up to date, and only if the cache is enabled and the task is cacheable.

flowchart TD start["Task is selected for execution"] --> utd{"Inputs and outputs equal to the last execution?"} utd -- "yes" --> uptodate(["UP-TO-DATE"]) utd -- "no" --> cacheable{"Build cache enabled, task cacheable, no doNotCacheIf predicate true?"} cacheable -- "no" --> run cacheable -- "yes" --> key["Compute the build cache key from the task implementation, the action implementations, the input property values, the normalized input files and the output property names"] key --> local{"Entry for the key in the local cache?"} local -- "yes" --> hit(["FROM-CACHE: unpack the outputs"]) local -- "no" --> remote{"Remote cache enabled and entry for the key found?"} remote -- "yes" --> download["Download and unpack the outputs, keep a copy in the local cache"] download --> hit remote -- "no" --> run["Execute the task actions"] run --> store["Store the outputs in every enabled cache whose push setting is true"]

Source: Gradle User Manual: Configure the Build Cache, Build cache key, Task outcomes

Three consequences follow from the figure and are worth keeping in mind. A task that is cached is still skipped for its actions, so anything it did as a side effect (printing, registering, writing outside its declared outputs) does not happen. A cache hit replaces the outputs on disk, so the result is the same as an execution if, and only if, the inputs were declared completely. And the order of the lookups matters for cost: local first, then remote, and an entry found remotely is copied into the local cache, so the second time it is found locally.

Enabling the build cache

The build cache is off by default. There are two switches, and the command line wins over the property.

Switch Effect

--build-cache

Use the build cache for this build only.

org.gradle.caching=true in gradle.properties

Use the build cache for every build that reads the file (the project, or the Gradle User Home for all projects), unless --no-build-cache is given.

--no-build-cache

Do not use the build cache in this build, whatever the property says.

-Dorg.gradle.caching.debug=true

Print how the build cache key of each task was computed (see the debugging section).

These are the only intended switches. Turning the cache on from build logic, with gradle.startParameter.buildCacheEnabled = true in a settings file or an init script, is deprecated since Gradle 9.8.0 and will be removed in Gradle 10 (not run here).

Source: Gradle User Manual: Enable the Build Cache, Gradle User Manual: Upgrading within Gradle 9.x.y, deprecation of enabling the Build Cache from build logic

The build cache key

The key is a 128-bit hash, written as 32 hexadecimal digits, computed for each cacheable task from the following ingredients. Two tasks whose keys are equal are the same function applied to the same arguments, whatever they are called and wherever they live.

Ingredient What it covers

The task implementation

The class of the task and the hash of the class loader that defined it (for a task class declared in a build script, the compiled script; for a plugin task, the plugin JAR). The Gradle version is part of this through the classpath of Gradle itself.

The task action implementations

The classes of the actions added with doFirst {} and doLast {}, with the same class loader hash.

The names of the output properties

destinationDirectory, archiveFile, summary, and so on, but not the output paths.

The input properties

The names and the values (hashed) of the properties annotated with @Input and the like, and of those added with inputs.property(...).

The input files

The names of the file properties and the fingerprint of their content, normalized according to the declared path sensitivity or classpath normalization (see below).

Two things are deliberately not in the key. The task path is not (the documentation says so explicitly), so :tidepool-engine:stationSummary and a task of another project can reuse each other’s entries when everything else is the same; and the absolute location of the project is not, unless a property is declared with ABSOLUTE path sensitivity. Both are what make the cache useful across checkouts and also what make an incomplete declaration dangerous.

Why Copy, Jar and Zip are not cached

Tasks such as Copy, Sync, Jar, Zip and Tar are not worth caching: they move bytes from one place on the disk to another, which is usually faster than downloading a stored copy, and caching them would waste space. The annotation @DisableCachingByDefault(because = "...") documents that on a task class (the build can still override it with the runtime API, see below), and @CacheableTask opts in. A subclass does not inherit @CacheableTask; a custom task type is not cacheable until you say so. Test tasks are cacheable, and that has a consequence that the next section comes back to: a cached test is a test that was not run in this build.

Making a custom task cacheable

The tidepool engine gets a small custom task that counts the stations in the CSV file and writes the count. It has one input file and one output file. The first version declares both and nothing else; it is a perfectly good task for incremental builds:

The runtime API for tasks you cannot subclass

When the task is of a type you do not control (an Exec, a generic task of a plugin, an ad hoc task), the same information is declared with the runtime API: outputs.cacheIf { true } opts the task in, and inputs.file(...) and outputs.file(...) with withPropertyName and withPathSensitivity declare the inputs and outputs. The declarations have the same effect as the annotations; file inputs and outputs declared in a base class cannot be overridden this way, input properties can. The example is an ad hoc task with the same behaviour as the class above; it was run in both DSLs and was cached and restored:

Kotlin DSL
// tidepool-engine/build.gradle.kts
val stationCount = tasks.register("stationCount") {
    val stations = rootProject.layout.projectDirectory.file("data/stations.csv")
    val count = layout.buildDirectory.file("station-count.txt")

    inputs.file(stations)
        .withPropertyName("stations")
        .withPathSensitivity(PathSensitivity.NONE)
    outputs.file(count)
        .withPropertyName("count")
    outputs.cacheIf { true }

    doLast {
        val rows = stations.asFile.readLines().drop(1).filter { it.isNotBlank() }
        count.get().asFile.writeText("stations=${rows.size}\n")
    }
}

A remote HTTP build cache

A remote cache lets one machine reuse the work of another. Gradle ships a client for it, HttpBuildCache, and the protocol is almost nothing: a GET of <url><key> that answers 200 with the entry, or 404 when there is none; a PUT of the same URL that stores an entry (any 2xx is success, a 413 means "too big" and is not an error). Any HTTP server that does this can be a cache node. When both caches are enabled, Gradle looks in the local cache first, then in the remote one, and copies a remote hit into the local cache; it pushes to every enabled cache whose push is true. The local cache pushes by default, a remote one does not.

The recommended topology: CI pushes, developers pull

The official recommendation, and the one every serious setup converges to, is that a continuous integration server populates the cache from clean builds, while developers only load from it. A developer can change the inputs or the outputs of a task while it is executing, for instance by saving a file in the IDE while the build runs; Gradle has no defence against that and would cache whatever is in the output directory when the task finishes, which can poison the cache for everybody. A CI agent builds a pristine checkout and does not suffer from it. In the settings file that is one line:

Kotlin DSL
// settings.gradle.kts
val isCi = providers.environmentVariable("CI").isPresent

buildCache {
    remote<HttpBuildCache> {
        url = uri("http://127.0.0.1:5071/cache/")
        isAllowInsecureProtocol = true
        isPush = isCi
    }
}
Groovy DSL
// settings.gradle
boolean isCi = providers.environmentVariable('CI').present

buildCache {
    remote(HttpBuildCache) {
        url = 'http://127.0.0.1:5071/cache/'
        allowInsecureProtocol = true
        push = isCi
    }
}

The property is required for plain HTTP. A toy cache node

To show the protocol and the topology without installing anything, the examples use this node: a PUT writes a file named by the key, a GET reads it, anything else is 404. It can require HTTP Basic authentication (--user, the password is read from an environment variable and never printed) and it logs one line per request. It has no eviction, no TLS and no limits, so it is a teaching tool, not a cache for a team; for that see the next sections.

#!/usr/bin/env python3
"""A toy Gradle HTTP build cache node: GET and PUT of opaque entries, one file per cache key.

Not for production use: no eviction, no TLS and (unless --user is given) no authentication.
"""
import argparse
import base64
import hmac
import os
import sys
from http import HTTPStatus
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

parser = argparse.ArgumentParser()
parser.add_argument("--port", type=int, default=5071)
parser.add_argument("--dir", default="entries")
parser.add_argument("--user")
parser.add_argument("--password-env", default="CACHE_PASSWORD")
args = parser.parse_args()
os.makedirs(args.dir, exist_ok=True)
EXPECTED = None
if args.user:
    token = f"{args.user}:{os.environ[args.password_env]}".encode()
    EXPECTED = "Basic " + base64.b64encode(token).decode()


class Handler(BaseHTTPRequestHandler):
    def log_message(self, fmt, *a):
        pass

    def _key(self):
        key = self.path.rsplit("/", 1)[-1]
        return key if key.isalnum() else None

    def _authorized(self):
        if EXPECTED is None:
            return True
        return hmac.compare_digest(self.headers.get("Authorization", ""), EXPECTED)

    def _log(self, status, size):
        key = self.path.rsplit("/", 1)[-1]
        print(f"{self.command} {key} {status.value} {size}", flush=True)

    def _reply(self, status, body=b"", logged=None):
        self.send_response(status)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)
        self._log(status, len(body) if logged is None else logged)

    def do_GET(self):
        key = self._key()
        if not self._authorized():
            return self._reply(HTTPStatus.UNAUTHORIZED)
        path = os.path.join(args.dir, key or "")
        if key and os.path.isfile(path):
            with open(path, "rb") as f:
                return self._reply(HTTPStatus.OK, f.read())
        self._reply(HTTPStatus.NOT_FOUND)

    def do_PUT(self):
        key = self._key()
        length = int(self.headers.get("Content-Length", "0"))
        body = self.rfile.read(length)
        if not self._authorized():
            return self._reply(HTTPStatus.UNAUTHORIZED)
        with open(os.path.join(args.dir, key), "wb") as f:
            f.write(body)
        self._reply(HTTPStatus.CREATED, logged=len(body))


ThreadingHTTPServer(("127.0.0.1", args.port), Handler).serve_forever()

Security of a shared cache

Whoever can write to the cache can make every other build run what they wrote: a cache hit is an executable result (a JAR, a class file) that never went through the compiler of the machine that uses it. So the push right deserves the same care as the right to publish an artifact. Push only from builds that run on trusted, clean, ephemeral agents from reviewed code (not from pull requests of forks); give the push credentials only to those, and give developers read-only access; use HTTPS; never use allowUntrustedServer in a build that is not a throw-away. The wider picture is on Supply-Chain Security for JVM Builds and CI and IDE Integration.

Composite builds and buildSrc

The build cache configuration of the root build applies to the whole composite: included builds, and buildSrc of the root and of the included builds, inherit it and their own settings are ignored (since 4.5 and 5.0). Plugin builds included with pluginManagement { includeBuild(...) } are the exception, because they are loaded before the cache is configured. See Gradle Composite Builds.

Relocatability and path sensitivity

A task is relocatable if its outputs can be reused when the same task runs somewhere else: in another directory, another user’s home, another operating system. Whether it is depends on which paths the key contains. Every file input has a path sensitivity, declared with @PathSensitive:

PathSensitivity The key contains

ABSOLUTE

The full path of every file and directory. Not relocatable; this is also what you get for an input without declaration, and Gradle now insists that a cacheable task declare something.

RELATIVE

The location relative to the root of the file collection (the source directory, for example). Relocatable.

NAME_ONLY

Only the file name. Relocatable and tolerant of moved files.

NONE

No path at all, only the content. Relocatable and tolerant of renames.

The right value is the least sensitive one that is still correct: a task whose result depends on the file names (a compiler that derives class names from them) needs NAME_ONLY or RELATIVE; one that only reads the content, like StationSummary, needs NONE. The Java compiler’s sources are NAME_ONLY/RELATIVE, as the documentation explains: only the relative path matters for incremental compilation, not where the project lives.

Stable inputs and input normalization

A cacheable task needs repeatable outputs (running it twice on the same inputs produces the same files, otherwise what is stored and what is executed differ) and stable inputs (the same logical inputs produce the same key). The usual enemies of stable inputs are in the manual’s list: a version number with a time stamp in a manifest, a commit hash written into a properties file, the output of another task that writes the time. A task consuming such data gets a new key on every build and is never served from the cache.

Ignore it on the runtime classpath

The file is irrelevant for what the tests check. Gradle lets the consumer of the classpath say so with input normalization: normalization { runtimeClasspath { ignore("build-info.txt") } } removes the file from the fingerprint of every runtime classpath input of the project, for up-to-date checks and for the build cache alike. Kotlin DSL
// build.gradle.kts (root)
allprojects {
    normalization {
        runtimeClasspath {
            ignore("build-info.txt")
        }
    }
}
Groovy DSL
// build.gradle (root)
allprojects {
    normalization {
        runtimeClasspath {
            ignore 'build-info.txt'

The time stamp is in a comment line, and comments do not count. If the stamp were a value (built-at=...) it would count, which is why the experiment above uses a plain text file; a plain text file, a manifest attribute and a class file are all compared byte for byte. Manifests and the properties under META-INF have their own normalization, with ignoreAttribute, ignoreProperty and friends; all of it is described on Gradle Incremental Build.

The JDK is an input

The Java compiler, and the Java version that runs the tests, change the output, so they are part of the key. compileJava with a toolchain for JDK 21 does not reuse the entry that a JDK 26 compilation stored, and vice versa. The model project selects the JDK from a property (the toolchain mechanism is on Gradle Toolchains):

// tidepool-model/build.gradle.kts
java {
    toolchain {
        languageVersion = providers.gradleProperty("jdk")
            .map { JavaLanguageVersion.of(it.toInt()) }
            .orElse(JavaLanguageVersion.of(26))
    }
}

Debugging cache misses

When a task that should have been FROM-CACHE was executed, the question is which input differed. The official guide gives a procedure that works because it narrows the search step by step:

  1. Make the build correct without the cache first. Run clean and the build twice without --build-cache; every task that produces files should be UP-TO-DATE the second time. A task that is not up to date in an unchanged workspace is a task with unstable inputs or outputs, and it will also miss in the cache (see Gradle Incremental Build for how to find out why). Tasks with no outputs always run, which does not matter.

  2. In-place test. Empty the local cache, clean, build with --build-cache, clean, build again. Every cacheable task must be FROM-CACHE (the first listing of this page).

  3. Relocation test. Check the same commit out twice, build in one, clean and build in the other with the same local cache. Absolute paths among the inputs show up here (the StationSummary listing above). Run it with no remote cache configured and with push on.

  4. Cross-platform test. If developers and CI use different operating systems, populate a remote cache from one and consume it from the other; line endings, file permissions and the JDK distribution are the usual differences.

  5. Incremental use. Make typical changes (a comment, a method body, a new class, a dependency bump) and watch how much is still cached; if too little, restructure the project to reduce the dependencies between tasks.

For a single miss, collect the data in the order from coarse to fine: the build cache key; the implementation of the task and its actions (class names and class loader hashes); the names of the output properties; the hashes of the individual input properties; and the hashes of the files in the file inputs. --info gives the first, -Dorg.gradle.caching.debug=true gives all the others. The workflow with two builds is mechanical: save the debug output of both, strip the paths with sed if the locations differ, and diff them. The lines that differ are the answer.

./gradlew clean :tidepool-engine:test --build-cache -Dorg.gradle.caching.debug=true > build-a.txt
./gradlew clean :tidepool-engine:test --build-cache -Dorg.gradle.caching.debug=true > build-b.txt
diff build-a.txt build-b.txt

Using the cache on a team

A sequence that has worked for many teams, in the order in which it reduces risk:

  1. Local cache for everybody. org.gradle.caching=true in the project’s gradle.properties. A single developer already gains from branch switching and git bisect.

  2. Make the build cache-safe. Run the in-place and relocation tests above until every cacheable task is a hit; fix the declarations; put the build logic in build-logic so that script edits do not change keys.

  3. Remote cache, CI only. Start with the cache on CI agents, whose environment is stable, with the node reachable by them only. Push from CI after a clean build of a checked-out commit, never from a build that restores a previous workspace.

  4. Developers pull. Give developers read access to the node. The first build of the day, after pulling everybody’s changes, is then mostly FROM-CACHE for everything that CI already built.

  5. Keep the local cache next to the remote one: on CI it mirrors the remote cache and saves network traffic, on a laptop it makes branch switching free.

  6. Do not let developers push until the build has proven that incremental builds are flawless. The cache exposes stale-output problems in tasks and plugins that incremental builds hide, which is useful, but until the build has been fixed only clean builds should upload.

  7. Audit requirements. If you must prove which build produced a shipped artifact, disable the cache for the release build, or use a service that records which build produced which entry.

The build cache accelerates tasks; it does not replace the dependency cache or the wrapper (a CI job still needs both, kept between jobs or restored from a CI cache), and it works together with parallel execution, the daemon and the configuration cache, which are the other items of the performance checklist on Performance Profiling & Build Scans and Best Practices & Troubleshooting.

Gradle 8.14 and later

What is on this page is the behaviour of 9.8.1; the differences with the 8.x line, from the release notes and upgrade guides (not run here, Gradle 8.14.x was not installed):

  • The build cache itself, the key, the @CacheableTask rules and the HTTP protocol are the same in 8.14 and 9.8.1.

  • Before 8.8 the retention of the local cache was set with buildCache { local { removeUnusedEntriesAfterDays = n } } and the cleanup ran every 24 hours; from 8.8 the init script caches { buildCache... } is the way, and the old property is deprecated; it is removed in 9.0.0 (the settings file then fails to compile).

  • Gradle 8.7 stored Groovy build script compilation in the remote cache; 8.8 stopped doing that.

  • Gradle 9.8.0 deprecated enabling the build cache from build logic (gradle.startParameter.buildCacheEnabled = true in a settings file or init script), with removal in Gradle 10; --build-cache and org.gradle.caching remain the switches.

  • Gradle 9.7 stopped storing the Kotlin DSL accessor generation in the build cache; the log line Build caching of Kotlin script accessor generation disabled by property appears in --info output of 9.8.1.

  • The configuration cache is the preferred mode since 9.0 (and announced as the default for Gradle 10); a task action that uses Project at execution time, such as the predicate in the failing example above, is incompatible with it. See Configuration Cache & Isolated Projects. The upgrade path is on Upgrading Gradle.

Summary

  • The build cache stores the outputs of cacheable tasks under a key computed from the task implementation, its actions, the input values, the normalized input files and the names of the outputs. A hit is FROM-CACHE, and a task is only consulted after the up-to-date check fails.

  • Enable it with --build-cache or org.gradle.caching=true; the local cache in $GRADLE_USER_HOME/caches/build-cache-1 is cleaned up after 7 days of non-use by default, configurable in an init script.

  • Copy, Jar and Zip are deliberately not cacheable; compilation, Javadoc and Test are. Custom tasks opt in with @CacheableTask and must declare a path sensitivity; ad hoc tasks use outputs.cacheIf.

  • A remote HTTP cache is a GET/PUT node; let CI push (from clean builds) and let developers pull; credentials and TLS belong to the node, and the push right is a supply-chain right.

  • Relocatability (@PathSensitive), stable inputs, input normalization, the JDK and the build script are what usually decide whether the cache works; --info and -Dorg.gradle.caching.debug=true plus diff find the input that differs.
