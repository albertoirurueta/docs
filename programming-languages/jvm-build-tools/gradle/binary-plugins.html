Binary Plugins

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Gradle 9.8.1 and was run on JDK 26 on 2026-10-16 (the daemon ran on JDK 26; the plugin is compiled with options.release = 17, because Gradle 9 itself needs JVM 17 or newer, and no toolchain was involved). Every example was run through the wrapper in scratch copies of the tidepool project, once with Kotlin DSL build files and once with Groovy DSL build files. The plugin itself is written once, in Java, and is the same in both copies: only the build files differ, and the console output is the same in both apart from timings, the Where: line of a failure (build.gradle.kts or build.gradle) and the scratch path. The scratch copies pointed their wrapper at a local copy of the same distribution archive; the properties file that a real project commits is

The commands use --console=plain. In the listings the blank lines, the "Consider enabling configuration cache" hint and the Try: hints of failures are left out, the tasks of the included plugin build (:tidepool-gradle-plugin:compileJava and the like, all up to date after the first build) are not shown in builds that use the plugin, and the scratch directory is shown as /work/tidepool. Examples run with --configuration-cache say so, and each example states whether it is compatible with the configuration cache. Gradle 8.14.x was not installed here, so statements about it come from the official documentation and are labelled "not run here". Publishing to the Gradle Plugin Portal is not shown at all (not run here); the plugin is published only to a file:// repository below the plugin’s build directory.

A script plugin (a .gradle file applied with apply from) or a precompiled script plugin is the quickest way to share build logic, and a build that only wants to share its own conventions should start there (see Convention Plugins & Sharing Build Logic). A binary plugin is the next step: a class that implements Plugin<Project>, compiled and packaged like any other JVM library, with its own version, its own tests and, if you want, a public id on a plugin repository. That is the shape of nearly every plugin you apply from the plugins {} block, from the core java plugin to third-party ones; the overview of the kinds of plugin is on Plugins Overview. This page writes one: tidepool.station-check, which gives a build a checkStations task that validates the data/stations.csv file the tidepool engine reads, an extension to configure it and a place on the check lifecycle. It is the Gradle version of the check that Writing Maven Plugins builds as the goal tidepool:check-stations and that Writing Custom Ant Tasks builds as the task <checkstations>. The task class has the same contract as the buildSrc task on Writing Custom Gradle Tasks; what this page adds is everything around it: packaging, id, extension, wiring and reactions.

The anatomy of a binary plugin

A plugin is made of three cooperating parts, and the tidepool plugin has all three:

Part Purpose In the tidepool plugin

Plugin class

Implements Plugin<Project> (or Plugin<Settings>, Plugin<Gradle>); apply is the entry point. It registers tasks, creates extensions and wires defaults, and should do no real work.

StationCheckPlugin

Extension

A managed object that exposes the plugin’s configuration as a DSL block of the build script, built from lazy Property, SetProperty, ConfigurableFileCollection and nested objects.

StationCheckExtension, with Limits and a container of DataSet objects

Task type

The work, with annotated inputs and outputs so that Gradle can skip it, cache it and run it in parallel.

CheckStations

Source: Gradle User Manual: Anatomy of a binary plugin

The flow from the id in a plugins {} block to the finished task graph is the same for every plugin: Gradle finds the id in the plugin descriptor inside the plugin’s JAR, instantiates the class named there and calls apply once per project. Everything the plugin contributes happens inside that call, or in callbacks that it registers there:

flowchart LR ID["plugins block: id tidepool.station-check"] --> DESC["META-INF/gradle-plugins/tidepool.station-check.properties"] DESC --> CLS["implementation-class: StationCheckPlugin"] CLS --> APPLY["apply of the project"] APPLY --> EXT["extensions.create stationCheck"] APPLY --> TASK["tasks.register checkStations"] APPLY --> DS["dataSets.all registers one task per data set"] APPLY --> REACT["pluginManager.withPlugin lifecycle-base"] EXT -->|"conventions wire lazily"| TASK EXT -->|"conventions wire lazily"| DS REACT --> CHECK["check dependsOn every CheckStations"]

The plugin project

A plugin is built by an ordinary Gradle build. Because the plugin is only used by tidepool, the quickest layout puts it in an included build next to the project that applies it, and the consumer finds it through pluginManagement. That layout and its trade-offs are covered on Composite Builds and Convention Plugins & Sharing Build Logic; here it is simply a directory:

The java-gradle-plugin plugin

The build file of the plugin build applies java-gradle-plugin, the Java Gradle Plugin Development plugin. It applies the java-library plugin, adds the Gradle API to the compile classpath (gradleApi() in compileOnlyApi, so the plugin does not ship it), generates the plugin descriptor from the gradlePlugin {} block, configures the plugin marker publication, and adds validations. Its id for a plugin is whatever the id property says; implementationClass names the Plugin<Project> class:

Kotlin DSL: tidepool-gradle-plugin/build.gradle.kts
plugins {
    `java-gradle-plugin`
    `maven-publish`
}

group = "io.tidepool"
version = "1.0.0"

tasks.withType<JavaCompile>().configureEach {
    options.release = 17
}

gradlePlugin {
    plugins {
        create("stationCheck") {
            id = "tidepool.station-check"
            implementationClass = "io.tidepool.gradle.StationCheckPlugin"
            displayName = "Tidepool station check"
            description = "Validates the tidepool station data files."
        }
    }
}

publishing {
    repositories {
        maven {
            name = "local"
            url = uri(layout.buildDirectory.dir("repo"))

maven-publish is only there for the repository example further down; displayName and description are what a plugin repository shows. The plugin build has a one-line settings file, rootProject.name = "tidepool-gradle-plugin" in the Kotlin DSL and rootProject.name = 'tidepool-gradle-plugin' in the Groovy DSL. The plugin is written in Java, which needs no extra compiler plugin and gives one source for both DSLs; Kotlin works the same way with the kotlin-dsl plugin (which also applies java-gradle-plugin) or the Kotlin JVM plugin, and since Gradle 9.0 that plugin compiles with Kotlin language version 2.2.

Source: Gradle User Manual: Java Gradle Plugin Development, usage and Using the Plugin Development plugin

The descriptor is a properties file whose name is the plugin id and whose single entry points at the class. That is all the id is: when a build asks for tidepool.station-check, Gradle looks for a descriptor of that name on the plugin classpath. A plugin can ship several descriptors, one per plugins.create entry, and there is no limit on the number of ids in one JAR.

Choosing a plugin id

The id is global, so choose it as you would choose a package name. The user guide lists the rules: only alphanumeric characters, . and -; at least one . separating a namespace from the name; lowercase by convention; no leading, trailing or doubled .; and nothing in the org.gradle, com.gradle or com.gradleware namespaces. Ids for a plugin published for others should start with a reverse domain name or a GitHub-style namespace that you own (com.github.foo.bar, org.baz.bar). tidepool.station-check follows the rules; a plugin published for others would use a namespace that its author owns. The id and the Maven coordinates of the plugin’s JAR are independent (the JAR here is io.tidepool:tidepool-gradle-plugin:1.0.0); the link between them is the marker artifact described below.

Source: Gradle User Manual: Creating a plugin ID

The plugin

The extension is the plugin’s public face, so it comes first. It is an abstract class whose getters Gradle implements (managed properties, see Lazy Configuration & Providers), so there are no fields, no constructors and no setters, and every value is a lazy Property, SetProperty or ConfigurableFileCollection that can still be changed after apply has run. Three kinds of nested structure show how a DSL grows beyond flat properties:

  • limits is a nested object. The getter is annotated @Nested, and a method that takes an Action lets the build script write a block.

  • dataSets is a NamedDomainObjectContainer of DataSet objects: the build script names as many groups of station files as it likes.

  • stations, required, failOnError, report and reportDirectory are the flat settings of the default check.

StationCheckExtension.java
package io.tidepool.gradle;

import org.gradle.api.Action;
import org.gradle.api.NamedDomainObjectContainer;
import org.gradle.api.file.ConfigurableFileCollection;
import org.gradle.api.file.DirectoryProperty;
import org.gradle.api.provider.Property;
import org.gradle.api.provider.SetProperty;
import org.gradle.api.tasks.Nested;

/** The stationCheck { } block. */
public abstract class StationCheckExtension {

    /** The files checked by the checkStations task. */
    public abstract ConfigurableFileCollection getStations();

    @Nested
    public abstract Limits getLimits();

    public void limits(Action<? super Limits> action) {
        action.execute(getLimits());
    }

    public abstract SetProperty<String> getRequired();

    public abstract Property<Boolean> getFailOnError();

    public abstract Property<ReportMode> getReport();

    public abstract DirectoryProperty getReportDirectory();

    /** Extra, named groups of station files: dataSets { register("x") { ... } }. */
    public abstract NamedDomainObjectContainer<DataSet> getDataSets();
}

import org.gradle.api.provider.SetProperty;

/** One named group of station files; the plugin registers a check task for each one. */

package io.tidepool.gradle;

Limits is annotated with @Input because the same interface is also the @Nested bean of the task: the extension and the task share the type, so the task can copy the values lazily. DataSet implements Named, which is all a type needs to be an element of a container whose elements Gradle creates; the interface is a managed type, so Gradle generates the implementation and the name property. The extension’s container is declared as an abstract getter of the type NamedDomainObjectContainer<DataSet> and Gradle creates that too (the older way, calling objects.domainObjectContainer(...) in apply, still works and is the way the user guide shows it).

Source: Gradle User Manual: Declaring a DSL configuration container and Modeling DSL-like APIs

The plugin class creates the extension, gives every property a convention (a default that the build script can override and that is used only when nothing has been set), registers the tasks and reacts to the lifecycle-base plugin:

StationCheckPlugin.java
package io.tidepool.gradle;

import org.gradle.api.NamedDomainObjectContainer;
import org.gradle.api.Plugin;
import org.gradle.api.Project;
import org.gradle.api.tasks.TaskContainer;
import org.gradle.api.tasks.TaskProvider;

public class StationCheckPlugin implements Plugin<Project> {

    @Override
    public void apply(Project project) {
        StationCheckExtension ext = project.getExtensions().create("stationCheck", StationCheckExtension.class);

        // conventions: the defaults a build script can override
        ext.getStations().convention(project.getLayout().getProjectDirectory().file("data/stations.csv"));
        ext.getLimits().getMinConstituents().convention(1);
        ext.getLimits().getMaxConstituents().convention(8);
        ext.getFailOnError().convention(true);
        ext.getReport().convention(ReportMode.SUMMARY);
        ext.getReportDirectory().convention(project.getLayout().getBuildDirectory().dir("reports/tidepool"));

        TaskContainer tasks = project.getTasks();
        tasks.register("checkStations", CheckStations.class, task -> {
            task.setGroup("verification");
            task.setDescription("Validates the station files.");
            task.getStations().from(ext.getStations());
            task.getRequired().convention(ext.getRequired());
            task.getFailOnError().convention(ext.getFailOnError());
            task.getReportFile().convention(ext.getReportDirectory().file("checkStations.txt"));
            wireCommon(task, ext);
        });

        // one more task for every data set the build script declares
        NamedDomainObjectContainer<DataSet> dataSets = ext.getDataSets();
        dataSets.all(dataSet -> {
            String name = "check" + capitalize(dataSet.getName()) + "Stations";
            tasks.register(name, CheckStations.class, task -> {
                task.setGroup("verification");
                task.setDescription("Validates the station files of the data set '" + dataSet.getName() + "'.");
                task.getStations().from(dataSet.getFiles());
                task.getRequired().convention(dataSet.getRequired().orElse(ext.getRequired()));
                task.getFailOnError().convention(dataSet.getFailOnError().orElse(ext.getFailOnError()));
                task.getReportFile().convention(ext.getReportDirectory().file(name + ".txt"));
                wireCommon(task, ext);
            });
        });

        // react to another plugin instead of applying it: attach to "check" when the build has one
        project.getPluginManager().withPlugin("lifecycle-base", applied ->
            tasks.named("check", check -> check.dependsOn(tasks.withType(CheckStations.class))));
    }

    private static void wireCommon(CheckStations task, StationCheckExtension ext) {
        task.getLimits().getMinConstituents().convention(ext.getLimits().getMinConstituents());
        task.getLimits().getMaxConstituents().convention(ext.getLimits().getMaxConstituents());
        task.getReport().convention(ext.getReport());
    }

    private static String capitalize(String name) {
        return name.substring(0, 1).toUpperCase() + name.substring(1);
    }
}

Points worth noting:

  • project.getExtensions().create("stationCheck", StationCheckExtension.class) instantiates the class through Gradle’s object factory (which is what implements the abstract getters), registers it under the name stationCheck and adds a block of that name to the build script’s DSL, plus a type-safe accessor to the Kotlin DSL.

  • Every default is a convention, not a set. A build script that writes failOnError = false replaces the convention; a build script that writes nothing gets it. The user guide recommends conventions for exactly this reason.

  • ext.getStations().convention(...) on a ConfigurableFileCollection is an incubating API since Gradle 8.8: the convention applies only while no file has been added to the collection. If data/stations.csv does not exist at all, the task has no source and is skipped (shown below).

  • The task wiring never calls get(). task.getRequired().convention(ext.getRequired()) hands the task a provider of the extension’s value, so a required.add("SF") that appears in the build script after the plugin was applied is still seen. Calling ext.getRequired().get() inside apply would freeze the value as it is at that moment and ignore the build script; it is the classic mistake of the lazy API, and apply is the place where it is easiest to make it.

  • orElse on a data set’s required property means "the data set’s own value if it set one, otherwise the extension’s value", which is exactly what a per-data-set override of a project-wide default means.

  • Data set tasks are registered inside dataSets.all, not configureEach: the container’s elements are only realized when something asks for them, and a task registered after the task graph is built does not exist for the command line. all realizes every element as soon as it is declared. The user guide uses all for the same reason. The mistake and its error message are shown below.

  • withPlugin("lifecycle-base", ...) runs now if the plugin is already applied and later if it is applied after this one. The check lifecycle task belongs to lifecycle-base (the base plugin and the java plugin both apply it), and the callback makes the plugin useful when it is there and harmless when it is not. The alternative, applying base from the plugin, would force a conventions layer on every project that applies it.

  • The tasks.withType(CheckStations.class) collection given to dependsOn is lazy: tasks registered later are included.

Source: Gradle User Manual: Mapping extension properties to task properties and Adding default configuration with conventions

The task class

The task is the check from the Writing Custom Gradle Tasks page, translated to Java so that the plugin has one source for both DSLs. It has the same seven properties (stations, limits, required, failOnError, report, maxMessages and reportFile), the same annotations (@CacheableTask, @InputFiles with @SkipWhenEmpty and @PathSensitive, @Nested, @Optional, @OutputFile, @Internal) and the same command-line options (--require, --fail-on-error, --report), explained annotation by annotation there. Two things are new. The task no longer carries conventions for failOnError, report and the limits, because the plugin sets them from the extension; only maxMessages keeps one. And it reports its findings through the Problems API (see below), which needs an injected Problems service:

/** The task of the plugin; the same contract as the buildSrc task on the Writing Custom Tasks page. */
@CacheableTask
public abstract class CheckStations extends DefaultTask {

    private static final ProblemGroup GROUP = ProblemGroup.create("io.tidepool", "Tidepool");
    private static final ProblemId BAD_ROW = ProblemId.create("bad-station-row", "Invalid station data", GROUP);
    private static final ProblemId FAILED = ProblemId.create("station-check-failed", "Station data check failed", GROUP);

    private record Issue(String file, String path, int line, String text) {
        @Override
        public String toString() {
            return line > 0 ? file + ":" + line + " " + text : text;
        }
    }

    @InputFiles
    @SkipWhenEmpty
    @PathSensitive(PathSensitivity.RELATIVE)
    public abstract ConfigurableFileCollection getStations();

    @Nested
    public abstract Limits getLimits();

    @Input
    @Optional
    @Option(option = "require", description = "A station id that must be present.")
    public abstract SetProperty<String> getRequired();

    @Input
    @Option(option = "fail-on-error", description = "Fails the build when a problem is found.")
    public abstract Property<Boolean> getFailOnError();

    @Input
    @Option(option = "report", description = "How much the report file lists.")
    public abstract Property<ReportMode> getReport();

    @Internal
    public abstract Property<Integer> getMaxMessages();

    @OutputFile
    public abstract RegularFileProperty getReportFile();

    @Inject
    protected abstract Problems getProblems();

    public CheckStations() {
        getMaxMessages().convention(10);
    }

    public void limits(Action<? super Limits> action) {
        action.execute(getLimits());
    }

    @TaskAction
    public void check() throws IOException {
        int min = getLimits().getMinConstituents().get();
        int max = getLimits().getMaxConstituents().get();
        var seen = new TreeSet<String>();
        var issues = new ArrayList<Issue>();

        List<File> files = new ArrayList<>(getStations().getFiles());
        files.sort(Comparator.comparing(File::getName));
        for (File file : files) {
            List<String> lines = Files.readAllLines(file.toPath());
            for (int i = 1; i < lines.size(); i++) {
                String[] columns = lines.get(i).split(",", -1);
                String name = file.getName();
                String path = file.getAbsolutePath();
                int row = i + 1;
                if (columns.length != 5) {
                    issues.add(new Issue(name, path, row, "expected 5 columns, found " + columns.length));
                    continue;
                }
                if (!seen.add(columns[0])) {
                    issues.add(new Issue(name, path, row, "duplicate station id " + columns[0]));
                }
                range(file, row, "latitude", columns[2], -90.0, 90.0, issues);
                range(file, row, "longitude", columns[3], -180.0, 180.0, issues);
                int n = columns[4].isEmpty() ? 0 : columns[4].split(";").length;
                if (n < min) issues.add(new Issue(name, path, row, "has " + n + " constituent(s), at least " + min + " required"));
                if (n > max) issues.add(new Issue(name, path, row, "has " + n + " constituent(s), at most " + max + " allowed"));
            }
        }
        for (String id : getRequired().get()) {
            if (!seen.contains(id)) issues.add(new Issue("", "", 0, "required station " + id + " is missing"));
        }

        File out = getReportFile().get().getAsFile();
        out.getParentFile().mkdirs();
        StringBuilder text = new StringBuilder();
        text.append("stations=").append(seen.size()).append('\n');
        text.append("problems=").append(issues.size()).append('\n');
        if (getReport().get() == ReportMode.FULL) text.append("ids=").append(String.join(",", seen)).append('\n');
        Files.writeString(out.toPath(), text);

        String summary = issues.size() + " problem(s) found in station data";
        ProblemReporter reporter = getProblems().getReporter();
        if (issues.isEmpty()) {
            getLogger().lifecycle(files.size() + " file(s), " + seen.size() + " station(s): OK");
        } else if (getFailOnError().get()) {
            throw reporter.throwing(new GradleException(summary), FAILED, spec -> spec
                .contextualLabel(summary)
                .details(String.join("\n", issues.stream().limit(getMaxMessages().get()).map(Issue::toString).toList()))
                .solution("Fix the station files, or set failOnError = false to only report the problems"));
        } else {
            issues.stream().limit(getMaxMessages().get()).forEach(issue -> getLogger().warn(issue.toString()));
            for (Issue issue : issues) {
                reporter.report(BAD_ROW, spec -> {
                    spec.contextualLabel(issue.toString());
                    if (issue.line() > 0) spec.lineInFileLocation(issue.path(), issue.line());
                });
            }
            getLogger().warn(summary);
        }
    }

    private static void range(File file, int row, String what, String text, double min, double max, List<Issue> issues) {
        double value;
        try {
            value = Double.parseDouble(text);
        } catch (NumberFormatException e) {
            issues.add(new Issue(file.getName(), file.getAbsolutePath(), row, what + " is not a number: '" + text + "'"));
            return;
        }
        if (value < min || value > max) {
            issues.add(new Issue(file.getName(), file.getAbsolutePath(), row, what + " " + value + " is outside [" + min + ", " + max + "]"));
        }
    }
}

The task class is public API of the plugin. It is also, as the validatePlugins task will confirm, the part where a forgotten annotation costs the most, because a property without an input or output annotation silently falls out of the up-to-date check in a build that does not run the validation.

Reacting to other plugins

The plugin did not apply base: it asked to be told when lifecycle-base is applied. The two ways of building on another plugin differ in what they impose. Applying a plugin (project.getPluginManager().apply(JavaPlugin.class)) gives the consuming project everything that plugin brings, whether it wants it or not; reacting (withPlugin) configures the extra behaviour only if the project already has the plugin. For the same reason the user guide suggests splitting a plugin into a base plugin that provides capabilities (tasks, extensions, no opinions) and a plugin that applies the base plugin and adds conventions; java-base and java are the model.

The java plugin applies lifecycle-base, so with it the plugin adds checkStations to the dependencies of check, next to the compile and test tasks. A dry run shows the graph:

Nothing orders checkStations against the compile tasks, so their relative order in this list is not defined and can differ from run to run. Without any of those plugins, the project has no check lifecycle task at all, and the callback never fires. The same pattern applies to task types: tasks.withType(SomeTask.class).configureEach { ... } configures every task of that type that the build creates, now or later. BuildFeatures, injected into a plugin, tells it whether the configuration cache or Isolated Projects is requested or active, for the rare plugin that must disable a feature that is incompatible with them; the user guide treats that as a last resort.

Reporting problems with the Problems API

A task that fails with GradleException("6 problems") tells the user that something is wrong and nothing else. The Problems API lets a plugin attach structure to what it reports: an id and a group, a label, details, a solution, a documentation link and a file location. The same data reaches the console, the generated HTML report, Build Scans and IDEs through the Tooling API. The API is incubating (Problems since Gradle 8.4, getReporter() since 8.11, report and throwing with a ProblemId since 8.13), and its types are in org.gradle.api.problems. CheckStations uses both ways to report:

  • reporter.report(id, spec -> ...) reports a recoverable problem and the build goes on. The lenient data set reports one problem per row, with lineInFileLocation(path, line) so that a client can point at the row.

  • throw reporter.throwing(exception, id, spec -> ...) reports a fatal problem and builds the exception to throw. The display name of the id becomes the first line under "What went wrong", the contextual label and the details follow, and the solution becomes the "Possible solution" line, as in the failing run above.

A ProblemId is created from a name, a display name and a ProblemGroup (ProblemGroup.create("io.tidepool", "Tidepool")); the constants in CheckStations are what the report shows as "Invalid station data" and "Station data check failed". The service is injected with @Inject into the task class (an abstract getter of type Problems), or into the constructor of a plugin class. When any problem has been reported, Gradle writes build/reports/problems/problems-report.html and prints a link to it; with --no-problems-report the report is not written, and with --warning-mode=all the console shows the problems as they are reported. Repeated problems are summarised: after the first few instances of a problem, the rest arrive as a summary at the end of the build.

ProblemSpec.severity(Severity) is deprecated in the Javadoc of Gradle 9.8.1: the severity is now implied by the method used, report for a warning and throwing for an error. The sample in the user guide still calls severity(...), and a first version of this plugin did; the build then recorded a deprecation problem for the call in its own problems report. The plugin on this page does not call it.

The additional data (additionalData(Class, Action)) that a plugin can attach is meant for clients, appears in neither the CLI output nor the HTML report, and is not used here.

Source: Gradle User Manual: Problems API usage, Reporting a recoverable problem, Reporting a fatal problem and Generated HTML report

Testing and publishing

A plugin deserves tests at three levels: unit tests with ProjectBuilder, functional tests that run a real build with the TestKit GradleRunner against the plugin under test (this is what pluginUnderTestMetadata is for), and integration tests against several Gradle versions. They, and publishing the plugin to the Plugin Portal or to a Maven repository, are the subject of Testing & Publishing Plugins. For several related plugins in one build, the structure of the build that contains them is on Multi-Project Builds and Composite Builds.

What changed from Gradle 8.14 and from the Gradle 1.x book

Nothing on this page was run on Gradle 8.14.6; the notes below come from the official documentation and are labelled "not run here". The book is Gradle in Action, written for Gradle 1.7.

Item Status

Problems API (getReporter(), report, throwing with a ProblemId)

Available from 8.11 (the reporter) and 8.13 (the id-based methods), incubating; so the plugin’s calls exist on 8.14. Not run here.

ProblemSpec.severity(Severity)

Deprecated in the Javadoc of 9.8.1, with the severity implied by report and throwing; still callable.

ConfigurableFileCollection.convention(...)

Incubating, since Gradle 8.8. On 8.7 and earlier the default would have to be applied with from(...) inside a condition.

registered by plugin 'tidepool.station-check' in task errors

Task provenance in failure messages is a 9.5 feature, so 8.14 prints the failure without that part of the line. Not run here.

Project.getConvention(), the Convention type and project.convention.plugins.x = ...

The Gradle 1.x way of exposing plugin configuration. Deprecated in 8.2 and removed in 9.0; use extensions (extensions.create), which have been available since the Gradle 1.x line.

apply plugin: 'name' and classes declared in the build script

Still work (the legacy apply and a plugin class in a build script), but a plugin that others use is a project of its own, applied from the plugins {} block.

Descriptor META-INF/gradle-plugins/name.properties written by hand

Generated by java-gradle-plugin from the gradlePlugin {} block.

Plugin tests with ProjectBuilder only

TestKit GradleRunner for functional tests; see the testing page.

Plugins written in Kotlin

Since 9.0 compiled with Kotlin language version 2.2 (it was 1.8 in 8.x, with an embedded Kotlin 2.0 since 8.11); not run here on 8.14.
