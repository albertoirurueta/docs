Gradle Java Projects

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Every example was run through the Gradle wrapper on macOS with JDK 26 (Oracle java version "26", which is both the JVM that runs the daemon and the JDK that compiles the code, because no toolchain is configured; toolchains are the subject of Gradle Toolchains). A Java build looks the same in every JVM build tool: put sources and resources in agreed places, compile them against a classpath that comes from the dependency declarations, run the tests, and pack the result. What differs is who knows the conventions. Ant knows none of them, so a build file lists every directory and every classpath (see Compiling Java with Ant). Maven knows one fixed set, which it calls the standard directory layout (see Maven Philosophy, Coordinates & Directory Layout). Gradle ships the conventions as plugins, every one of them can be changed in the build script, and the plugin you apply decides how much of the Java build you get: compilation only, a library with a public API, or a runnable application. This page is about those plugins, about the objects underneath them (source sets, configurations and tasks), and about the parts of a Java build that are specific to Gradle: compile avoidance, incremental compilation, annotation processors, and the split between api and implementation. The shared vocabulary (build, project, task) is on Core Concepts; the dependency notation used here is explained on Declaring Dependencies & Configurations; running tests, test suites and coverage are on Testing JVM Projects; publishing the JARs built here is on Publishing. For the language itself see Java Build & Tooling; for the Kotlin side see Kotlin Build & Tooling.

The JVM plugins at a glance

The plugins build on each other. Applying one applies the plugins below it, so a build script almost always names exactly one of them (the one at the top of the stack it needs).

Plugin id What it adds Use it for

java-base

The java extension, and the rules that give every source set a compile task, a resources task and a classes task. It creates no source set of its own.

Plugin authors who want the Java model without the main and test source sets; build authors almost never apply it directly.

java

The source sets main and test, the tasks compileJava, processResources, classes, jar, javadoc, test and the other tasks of the table below, and the configurations implementation, compileOnly, runtimeOnly, annotationProcessor and their test counterparts.

A module that is compiled, tested and packed, but that is not consumed as a library by other projects.

java-library

Everything of java, plus the configurations api and compileOnlyApi, and a separation between the dependencies that consumers need to compile against and the ones that are an implementation detail. Consumers of a project dependency compile against its classes directory instead of its JAR.

Any project that other projects depend on, such as tidepool-model and tidepool-engine.

application

Everything of java, plus the distribution plugin and the tasks run, startScripts, installDist, distZip and distTar, and the application extension (main class, JVM arguments, script name).

A program with a main method, such as tidepool-cli.

war

Everything of java, plus the war task, src/main/webapp, the configurations providedCompile and providedRuntime, and a web software component.

Web applications for a servlet container (see below).

groovy, scala

Everything of java, plus compileGroovy and groovydoc, or compileScala and scaladoc, and joint compilation of the language with Java.

Projects written wholly or partly in those languages (see below).

java-platform, java-test-fixtures, jvm-test-suite, jvm-toolchains

A platform of constraints without code, the testFixtures source set, the testing { suites { ... } } DSL, and the toolchain support that every JVM plugin applies.

Each has its own page: Platforms, Constraints & Rich Versions, Testing JVM Projects and Gradle Toolchains.

Source: Gradle User Manual: Building Java & JVM projects, The Java Plugin, The Java Library Plugin, The Application Plugin

The role of java-library in a build with several projects is the reason it is the default choice for libraries: the api configuration says which dependencies are part of the library’s public face, and everything else stays out of the compile classpath of the consumers (see "Libraries: api and implementation" below).

The example build: three projects, in both DSLs

The running example of the section is tidepool, a small tide prediction toolkit: a model library (Station, Constituent, Height, TideEvent records), an engine library on top of it (the TideEngine and a StationReader that uses Commons CSV), and a command line application built with picocli. As a Gradle build it is one root project with three subprojects, which is the structure described on Multi Project Builds. This page uses the build to show what the Java plugins do; the files are shown once, here, and the sections below refer to them.

Source sets and the standard layout

A source set is Gradle’s name for a group of sources that are compiled together and run with one classpath: it bundles a source directory, a resources directory, an output directory, and a set of dependency configurations. The Java plugin creates two, main (the production code, which ends up in the JAR) and test (compiled against main and used to run tests). The layout it expects is the one every Java developer knows, and nothing has to exist: the plugin compiles whatever it finds and ignores what is missing.

The Maven equivalent of "source set" does not exist: the project has exactly one main and one test tree, and anything else (integration tests, generated sources) needs plugins that add source roots. The Ant equivalent is a <javac> task per tree (see the comparison table at the end of the page).

Changing the layout

Setting a property replaces its value; calling the matching method adds to it. That distinction, setSrcDirs against srcDir in the Kotlin DSL (srcDirs = against srcDir in the Groovy DSL), is the way to read most of the source set API. A legacy project whose sources live in src/java instead of src/main/java is described to Gradle like this:

Kotlin DSL
sourceSets {
    main {
        java {
            setSrcDirs(listOf("src/java"))
        }
    }
}
Groovy DSL
sourceSets {
    main {
        java {
            srcDirs = ['src/java']
        }
    }
}

A source set exists to give a set of sources its own classpath and its own output, so the guidance of the user manual is: if the sources need a unique classpath, produce classes that are handled differently from main and test, and are a natural part of the project, define a source set; generated sources that belong in the production JAR are better added to main (with the compile task depending on the generator).

Resources need no configuration at all: files in src/main/resources are copied by processResources into build/resources/main and packed into the JAR, and the task has no sources (NO-SOURCE in the listings below) when the directory is absent. Replacing tokens in resource files uses the expand and filter methods of the Copy family described on Working with Files; the Maven equivalent, resource filtering, is on Maven Resources & Filtering.

Compiling Java

Which Java version does the code target?

Three settings answer the question, with very different guarantees, and mixing them up is the classic Java-on-Gradle bug.

Setting What it does Guarantee

Toolchain (java { toolchain { languageVersion = ... } })

Compiles, tests, documents and runs with a JDK of that version, found on the machine or provisioned.

The strongest: language level, class file version and the JDK API all match. See Gradle Toolchains.

Almost as strong, and cheap: one newer JDK can build for older targets. Gradle supports it when the compiling JDK is Java 10 or later.

Weak, and the user manual says it is "not generally advised".

Compiler options and lint

The projects pass -Xlint:all through options.compilerArgs, so every warning category of javac is on. Other options that builds commonly add are -Werror (warnings fail the build), -parameters (keep parameter names in the class files, which some frameworks and annotation processors need), options.encoding = "UTF-8" (the default of the JDK 18 and later is already UTF-8, but older JDKs use the platform charset), and options.isFork = true with options.forkOptions to compile in a separate JVM. Compile avoidance and incremental compilation

Two separate features keep compilation cheap, and both look at the binary interface of classes rather than at the files.

Compile avoidance concerns consumers of a project. The compile classpath of a task is fingerprinted by the ABI of the classes on it (the part of a class that other classes can see: public and protected members, signatures, constants), and a change that does not alter the ABI does not make dependents out of date. Changing a method body, a comment, private members, a resource or the name of a JAR leaves downstream compileJava tasks UP-TO-DATE. With the java-library plugin the consumer even compiles against the classes directory of the project, so a change of a resource or the work of the jar task is not part of the compile at all.

Incremental compilation concerns one compile task. Gradle recompiles the classes affected by a change (the changed ones and the ones that depend on them, by type references in bytecode) and leaves the others in the output directory untouched.

Libraries: api and implementation

Which dependencies a consumer sees is the one question that separates a library from a plain Java module. The java-library plugin adds the configuration api and the rule that decides what goes on whose classpath. The user manual’s test for placing a dependency is the binary interface of the library: a dependency belongs in api if at least one of its types is used in a superclass or interface, a public or protected method signature (parameters, return types, generic arguments), a public field, or a public annotation. A type that appears only in method bodies or private members belongs in implementation. Prefer implementation: if a type leaks, the consumers fail to compile at once, which is the signal to move the dependency.

A custom source set: integration tests

Integration tests are the textbook use of a second source set: they need their own classpath (they may run against real files or servers), they are compiled against main, and they are a natural part of the project. The engine script above builds the source set by hand. Gradle also has the JVM Test Suite plugin (testing { suites { ... } }), which does the same in a handful of declarative lines and is what the user manual recommends today; it is the subject of Testing JVM Projects. Reproducible archives

Since Gradle 9.0.0 all archive tasks (Jar, War, Ear, Zip, Tar) produce reproducible archives by default: the order of the entries is deterministic, every entry has a fixed time stamp (the first of February 1980 for ZIP-based archives such as JARs, as in the unzip -l output above, and the second of January 1970 for TAR archives, which tar -tvf shows for the distTar output of this build), directories have the permissions 0755 and files 0644. A single executable JAR (fat JAR, uber JAR)

Gradle has no built-in fat JAR; the standard answer is a Jar task that unpacks the runtime classpath into the archive. The CLI script above contains it, because the way it handles the runtime classpath is the part that breaks under the configuration cache: the classpath must be a lazy Provider (or a closure) that is evaluated at execution time, not a configurations.runtimeClasspath.get() call made while the build is being configured. The dependsOn(configurations.runtimeClasspath) line is not optional: zipTree of a JAR file carries no task dependency, so without it Gradle does not build the JARs of the other two projects first, and after a clean the task fails with Cannot expand ZIP '…/tidepool-engine-1.0.0.jar' as it does not exist (reproduced on 9.8.1). The manual’s uber JAR example has the same line.

Kotlin DSL
tasks.register<Jar>("fatJar") {
    description = "Assembles a single executable JAR."
    group = "build"
    archiveClassifier = "all"
    duplicatesStrategy = DuplicatesStrategy.EXCLUDE
    manifest {
        attributes("Main-Class" to application.mainClass)
    }
    from(sourceSets.main.map { it.output })
    dependsOn(configurations.runtimeClasspath)
    from(configurations.runtimeClasspath.map { classpath ->
        classpath.map { if (it.isDirectory) it else zipTree(it) }
    })
}
Groovy DSL
tasks.register('fatJar', Jar) {

}

Applications: the application plugin

The application plugin turns a Java project into a program. The only mandatory setting is the main class. It adds the run task for development, and the tasks that build a distribution: startScripts (generates a Unix shell script and a Windows batch file), distZip and distTar (archives of the scripts, the project JAR and its runtime dependencies), and installDist (the same content copied into build/install/<name>). The settings of the application { ... } block that the CLI uses are mainClass, applicationName (the name of the scripts and the distribution; the default is the project name) and applicationDefaultJvmArgs (the JVM arguments of run and the scripts). Others are executableDir (the bin directory name), mainModule (a main class inside a Java module, which makes the scripts use the module path), and applicationDistribution, a copy specification for extra files. The distributions { main { contents { ... } } } block of the CLI script adds the data file to the distribution.

Web applications, Groovy and Scala, and Java modules

These three topics are plugins and settings that follow the same pattern as the rest of the page, so each is one paragraph here; none of the following was run for this page (not run here), and each statement comes from the user manual.

The war plugin extends java with a war task that assembles a WAR: the content of src/main/webapp goes to the root, compiled classes to WEB-INF/classes and the runtime classpath to WEB-INF/lib. Dependencies that the servlet container provides are declared in providedCompile (visible to compilation and tests, excluded from the WAR) or providedRuntime; both work transitively, which is why a provided dependency’s own dependencies are also left out of the WAR. These configurations are the old providedCompile of the Gradle 1.x books, still present; since Gradle 7.0 they cannot be consumed by other projects. Since Gradle 9.0 applying war together with java or ear builds all the archives during assemble (before 9.0 the WAR replaced the JAR), and the war project convention is gone, so the settings live on the war task itself (webAppDirectory, webXml, webInf { ... }). The Maven counterpart is the packaging type war (see Maven Packaging: JARs, WARs & Manifests), and a JSP/Struts project is described on the pages of the web section.

The groovy and scala plugins extend java with src/main/groovy and src/main/scala source directories that may also contain Java, and compile both languages together (joint compilation). The Groovy and Scala source directories may contain Java files next to the Groovy or Scala ones, and the compile tasks compileGroovy and compileScala, which run after compileJava, compile such mixed sources in one go, so classes may depend on each other in both directions. The Java source directories may contain only Java, and Java code that must call Groovy or Scala code has to live in the Groovy or Scala tree. The doc tasks are groovydoc and scaladoc. Applying java-library as well gives the API and implementation separation to a Groovy or Scala library. A Groovy project declares a Groovy dependency in implementation; a Scala project sets scalaVersion (an incubating property, which makes the Scala SDK dependency implicit) or declares the Scala library itself. The languages and their toolchains are described on Groovy Compiling: groovyc & Joint Compilation and Scala sbt & Build Tools; the Groovy side of Gradle (the build language) is on Groovy DSL & Migrating to Kotlin.

Java modules (a module-info.java) need no extra plugin. With a module-info.java in a source set, Gradle puts the dependencies on the module path instead of the class path (java.modularity.inferModulePath, true by default; the java extension can switch it off), the application plugin can run a modular program if mainModule is set next to mainClass, and a library that is not a module can still be used as an automatic module. The classpath-versus-module-path distinction is explained for the language on Java Packages & Modules.

The configuration cache and the Java plugins

The core Java plugins are compatible with the configuration cache, and every build on this page ran with it on and stored or reused an entry without problems. The pitfalls are all in code that a build adds around the plugins:

  • Resolving a configuration while the build is configured (configurations.runtimeClasspath.get().files in the body of a task registration) makes the configuration phase slow and, with the cache on, produces a problem as soon as the result is used in a task. The fatJar task reads the classpath lazily, through map in the Kotlin DSL and through a closure in the Groovy DSL (the closure is evaluated when the task runs).

  • Reaching into project from a task action (project.copy, project.exec, project.file) is not allowed in a cached task; use the properties of the task, or an injected service (see Configuration Cache & Isolated Projects).

  • A compiler argument built from a project property, such as -Aproject=... in the CLI script, is read at configuration time and becomes part of the cached configuration. That is fine, because it is an input of compileJava (a different value gives a different up-to-date state).

Classic mistakes

  • sourceCompatibility instead of release. The build compiles, then fails on the older JVM with NoSuchMethodError (run above). Use options.release or a toolchain.

  • An implementation type in the public API. The consumers fail with "package …​ does not exist" (run above). Check the type against the api rules, or turn the dependency into api.

  • A new Test task that is not attached to check. The tests exist and nobody runs them. Attach with tasks.check { dependsOn(...) }.

  • The old configuration names. compile, runtime, testCompile and testRuntime were removed in Gradle 7.0. The error is Could not find method compile() for arguments ... in the Groovy DSL and an unresolved reference in the Kotlin DSL; the replacements are api, implementation, compileOnly, runtimeOnly, testImplementation and testRuntimeOnly.

  • A fat JAR that fails with Invalid signature file digest (a classic JVM error; not reproduced here). A signed dependency has been unpacked into the archive. Exclude META-INF/*.SF, META-INF/*.DSA and META-INF/*.RSA in the fatJar task, or do not build a fat JAR.

  • A processor on the wrong classpath. An annotation processor in implementation or compileOnly is not run by Gradle (Gradle ignores processors on the compile classpath); declare it in annotationProcessor.

  • A version mismatch between projects. The "only compatible with JVM runtime version 21 or newer" message (run above) is the build telling you that a consumer targets an older Java than a library. Raise the consumer, lower the library’s release, or change both through one convention plugin (see Convention Plugins & Sharing Build Logic).

  • Running the program with the wrong working directory. run starts in the project directory of the application, not in the root of the build. The relative path of the data file differs between run, the installed script and the IDE.

  • The configurations compile, runtime, testCompile, testRuntime. Removed in Gradle 7.0. Use implementation, api, compileOnly, runtimeOnly, testImplementation and testRuntimeOnly.

  • Project-level sourceCompatibility = 1.7. The convention was deprecated in 8.2 and removed in 9.0.0. Use java { toolchain { ... } }, or options.release on the compile task.

  • mainClassName, archivesBaseName, jar.archiveName, jar.baseName. mainClassName was removed in 8.0 in favour of mainClass; archiveName, baseName and the other old archive task properties were removed in 8.0 in favour of archiveFileName and archiveBaseName; the project property archivesBaseName went in 9.0.0 (base.archivesName).

  • A single compile classpath that exposes everything. There was no api/implementation split; it came with the java-library plugin, together with compile avoidance and the incremental compiler.

  • apply plugin: 'java'. The plugins { } block is the current form, and it is the only form the Kotlin DSL gives type-safe accessors for.

  • The Jetty plugin (jettyRun) for web applications. Removed in Gradle 4.0; the third-party Gretty plugin covers that need. The War plugin itself, with providedCompile, is current.

  • Groovy and Scala plugins and joint compilation (chapter 11). The plugins are still there with the same layout; Scala builds now declare the Scala version with scalaVersion or the Scala library dependency.

  • Hand-made source sets for integration tests. Still valid, and shown above, but the JVM Test Suite plugin is the recommended form.
