Gradle Tasks

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Gradle 9.8.1 and was run on JDK 26 on 2026-10-16 (the daemon ran on JDK 26; no toolchain was involved). Every example was run through the wrapper in a scratch copy of the tidepool project, once with Kotlin DSL build files and once with Groovy DSL build files, with --console=plain and --configuration-cache, and every working example on this page is compatible with the configuration cache (none reported a configuration cache problem). The listings leave out blank lines, the "Calculating task graph" and "Configuration cache entry" lines and the closing configuration cache hint to keep the focus on tasks; the two removed-syntax examples near the end of the registering section are the only builds run without the cache, because they fail before the cache matters. The scratch copy pointed its wrapper at a local copy of the same distribution archive; the properties file that a real project commits is

distributionPath=wrapper/dists
distributionSha256Sum=dce76f55f8e251a3a1f130eb120f30b3d271de2b76c9b0729d316b5a1b6dc01f
distributionUrl=https\://services.gradle.org/distributions/gradle-9.8.1-bin.zip
networkTimeout=10000
retries=0
retryBackOffMs=500
validateDistributionUrl=true
zipStoreBase=GRADLE_USER_HOME
zipStorePath=wrapper/dists

Features newer than Gradle 8.14 name their release and say whether they are incubating, deprecated or removed. Gradle 8.14.x was not installed here, so statements about it come from the official documentation and are labelled "not run here".

A Gradle build is a graph of tasks, and everything else (plugins, dependency resolution, the build cache, the configuration cache) exists to decide which tasks run, in which order, and whether they can be skipped. A task is the unit of work that Gradle schedules, orders, skips and caches. In Ant the unit is the target (see Ant Targets & Extension Points); in Maven the unit is a plugin goal bound to a lifecycle phase (see Maven Build Lifecycle). The shared comparison is in Build Automation Fundamentals. This page is about using tasks that plugins and scripts already define: listing them, registering simple ones, wiring and ordering them, skipping them and reading their outcomes. Writing a task class with typed inputs and outputs is in Writing Custom Tasks, how Gradle decides that a task is up to date is in Incremental Build, and the Property and Provider types that connect tasks lazily are in Lazy Configuration & Providers. For the vocabulary (build, project, task graph) see Gradle Core Concepts, and for when task code runs see Build Lifecycle.

What a task is

A task is an object of type org.gradle.api.Task that belongs to a project. It has

  • a name and a path: the name is unique inside the project, the path adds the project (:tidepool-model:jar is the task jar of the project :tidepool-model; :stageData is a task of the root project);

  • a type: plain Task (a task defined by a script), or a class such as Copy, Zip, Jar, JavaCompile or Test that carries behaviour and typed properties;

  • actions: Kotlin or Groovy blocks run in order when the task executes (doFirst adds one at the front, doLast at the end), plus the single @TaskAction method of a task class;

  • inputs and outputs, which Gradle uses to decide whether the task is up to date and whether its result can be taken from the build cache;

  • dependencies on other tasks, ordering rules and finalizers;

  • a group and a description, which only matter for display.

Gradle builds the set of tasks to run from the names on the command line. A name such as build selects the task of that name in the current project and in every subproject; a path such as :tidepool-model:build selects one task. The camel-case abbreviation sR for stationReport, -x to exclude a task and the other command-line rules are on Command-Line Interface. The shared page that sets the three tools side by side is Comparing Ant, Maven & Gradle.

Source: Gradle User Manual: Task Basics

Listing tasks, groups and descriptions

Two tasks of the help family answer "what can I run here?": tasks lists the tasks of a project that have a group (the groups are the headings of the listing, and a task without a group is a hidden task), and help --task <name> describes one task. The root project of this example has two tasks in the group tidepool, a Copy task that stages the station data and a plain task that reports how many rows were staged, and one task with no group:

Kotlin DSL
val stageData = tasks.register<Copy>("stageData") {
    group = "tidepool"
    description = "Copies the station data into build/staging."
    from("data")
    into(layout.buildDirectory.dir("staging"))
}

tasks.register("stationReport") {
    group = "tidepool"
    description = "Prints the number of staged station rows."
    dependsOn(stageData)
    val staged = layout.buildDirectory.file("staging/stations.csv")
    doLast {
        val rows = staged.get().asFile.readLines().size - 1
        println("$rows stations staged")
    }
}

tasks.register("cleanupHelper") {
    doLast { println("not listed: no group") }
}
Groovy DSL
def stageData = tasks.register('stageData', Copy) {
    group = 'tidepool'
    description = 'Copies the station data into build/staging.'
    from 'data'
    into layout.buildDirectory.dir('staging')
}

tasks.register('stationReport') {
    group = 'tidepool'
    description = 'Prints the number of staged station rows.'
    dependsOn stageData
    def staged = layout.buildDirectory.file('staging/stations.csv')
    doLast {
        def rows = staged.get().asFile.readLines().size() - 1
        println "${rows} stations staged"

}

The task graph of a build

A lifecycle task has no actions of its own; it exists to give a name to a set of other tasks. The tasks of the Java plugins that every JVM build runs are a good example: build is a lifecycle task that depends on assemble (everything that produces outputs) and check (everything that verifies them), and each of those fans out to the tasks that do the work. This is the graph that ./gradlew :tidepool-model:build runs, with the dependencies that Gradle itself reported for each task (read from the task graph in a throw-away copy of the build):

flowchart TD build["build (lifecycle)"] --> assemble["assemble (lifecycle)"] build --> check["check (lifecycle)"] assemble --> jar jar --> classes["classes (lifecycle)"] classes --> compileJava classes --> processResources check --> test test --> testClasses["testClasses (lifecycle)"] test --> classes testClasses --> compileTestJava testClasses --> processTestResources compileTestJava --> classes

Gradle runs the tasks in an order that respects every arrow, running a task at most once. --dry-run (-m) prints that order without executing anything; it is the quickest way to answer "what will this command do?". For the application module, which depends on the other two, the dry run lists the compile tasks of all three modules before the packaging tasks of the application (the order of tasks that do not depend on each other is not specified and may differ between runs):

:tidepool-cli:classes SKIPPED

:tidepool-engine:processResources SKIPPED

:tidepool-engine:jar SKIPPED

Task outcomes

When a task finishes, Gradle labels it in the console with one of five outcomes. The label tells you why the task did or did not do work, and reading the labels is the fastest way to see whether the incremental build and the build cache work:

Label Meaning Typical cause

none, or EXECUTED

The task ran its actions.

The task has actions and Gradle executed them; a lifecycle task shows no label when one of its dependencies executed.

UP-TO-DATE

The task’s outputs are still valid, so nothing ran.

Inputs and outputs did not change since the last run (see Incremental Build); a lifecycle task whose dependencies are all UP-TO-DATE, SKIPPED or FROM-CACHE.

FROM-CACHE

The outputs were restored from the build cache instead of running the task.

The build cache holds an entry for the same inputs, for example after clean (see Build Cache).

SKIPPED

The task did not run, although it was selected.

An onlyIf predicate returned false, or the task is enabled = false. The user guide also lists exclusion with -x as a cause, but the plain log below shows an excluded task not at all. A dry run labels every task SKIPPED, see above.

NO-SOURCE

The task has inputs and outputs but no source files, so it had nothing to do.

compileTestJava and test in a module without tests, or processResources without a resources directory.

The labels come from real runs of the tidepool-model module, which has no resources and no tests. From a clean checkout the first build executes the compile and packaging tasks and gives NO-SOURCE to the tasks that have no inputs. The first run is cold, so compileJava and jar are executed:

Lifecycle tasks and actionable tasks

An actionable task has actions (a copy, a compile, a script block) and usually inputs and outputs. A lifecycle task has no actions: it only collects other tasks under one name, so that ./gradlew build means "everything that makes the project buildable". The Java and base plugins define assemble, check and build for that purpose, and your own build should follow the same pattern: give people a few lifecycle tasks with clear names (dataset, qualityCheck) and put the work in actionable tasks that the lifecycle tasks depend on. dependsOn is the right tool only for this: a lifecycle task has nothing to wire to, so it can only name tasks.

In this example stageData copies the station files, packData zips what stageData produced, and dataset is the lifecycle task that people run:

Kotlin DSL
val stageData = tasks.register<Copy>("stageData") {
    from("data")
    into(layout.buildDirectory.dir("staging"))
}

// Wired input: packData consumes the outputs of stageData, so Gradle adds the
// dependency by itself and knows which files are inputs.
val packData = tasks.register<Zip>("packData") {
    from(stageData)
    archiveFileName = "stations.zip"
    destinationDirectory = layout.buildDirectory.dir("dist")
}

// Lifecycle task: no actions, only dependencies.
tasks.register("dataset") {
    group = "tidepool"
    description = "Builds the station data package."
    dependsOn(packData)
}
Groovy DSL
def stageData = tasks.register('stageData', Copy) {
    from 'data'
    into layout.buildDirectory.dir('staging')
}

// Wired input: packData consumes the outputs of stageData, so Gradle adds the
// dependency by itself and knows which files are inputs.
def packData = tasks.register('packData', Zip) {
    from stageData
    archiveFileName = 'stations.zip'
    destinationDirectory = layout.buildDirectory.dir('dist')
}

// Lifecycle task: no actions, only dependencies.
tasks.register('dataset') {
    group = 'tidepool'
    description = 'Builds the station data package.'
    dependsOn packData
}

Note what is missing: packData does not use dependsOn. Its from(stageData) passes the task provider as a source, and Gradle understands that the files to zip are the outputs of stageData, so it adds the dependency itself; this is called wiring an input to an output. The dry run shows the order, and the first real run executes all three tasks. The second run finds everything up to date, including the lifecycle task:

./gradlew --console=plain --dry-run packData
:stageData SKIPPED
:packData SKIPPED
BUILD SUCCESSFUL in 684ms
./gradlew --console=plain dataset
> Task :stageData
> Task :packData
> Task :dataset
BUILD SUCCESSFUL in 723ms
2 actionable tasks: 2 executed
> Task :stageData UP-TO-DATE
> Task :packData UP-TO-DATE
> Task :dataset UP-TO-DATE
BUILD SUCCESSFUL in 662ms
2 actionable tasks: 2 up-to-date

The Groovy DSL run printed the same lines. The "2 actionable tasks" count excludes dataset, because it has no actions.

Source: Gradle User Manual: Lifecycle tasks, Best practices: Avoid DependsOn

Registering and configuring tasks

There are two generations of the API that creates tasks, and the difference decides how long the configuration phase takes in a large build.

  • The eager API (tasks.create(...), the Groovy task name { } shorthand, tasks.getByName(...)) creates the task and runs its configuration block immediately, while the build script is evaluated, for every task, whether or not the command line needs it.

  • The lazy API (tasks.register(...), tasks.named(...), configureEach) records a recipe, returns a TaskProvider and creates and configures the task only when something needs the task: the command line selected it, another task depends on it, or code called get() on the provider. This is called task configuration avoidance. It arrived as an incubating API in Gradle 4.9 (2018), and the Gradle documentation has recommended it ever since.

This build registers one task the eager way and two the lazy way, and prints a line from every configuration block, so that the output shows when each block ran:

Kotlin DSL
// Eager: the configuration block runs while the script is evaluated.
tasks.create("eagerReport") {
    println("configuring eagerReport")
    doLast { println("running eagerReport") }
}

// Lazy: the block runs only if something asks for the task.
tasks.register("lazyReport") {
    println("configuring lazyReport")
    doLast { println("running lazyReport") }
}

// Lazy configuration of every task of a type, without realizing unused tasks.
tasks.withType<Copy>().configureEach {
    println("configuring Copy task $name")
}
tasks.register<Copy>("stageData") {
    from("data")
    into(layout.buildDirectory.dir("staging"))
}
tasks.register<Copy>("stageBackup") {
    from("data")
    into(layout.buildDirectory.dir("backup"))
}

// Configure an existing task lazily, by name and type.
tasks.named<Copy>("stageBackup") {
    description = "Copies the station data to build/backup."
}
Groovy DSL
// Eager: the configuration block runs while the script is evaluated.
tasks.create('eagerReport') {
    println 'configuring eagerReport'
    doLast { println 'running eagerReport' }
}

// Lazy: the block runs only if something asks for the task.
tasks.register('lazyReport') {
    println 'configuring lazyReport'
    doLast { println 'running lazyReport' }
}

// Lazy configuration of every task of a type, without realizing unused tasks.
tasks.withType(Copy).configureEach {
    println "configuring Copy task ${name}"
}
tasks.register('stageData', Copy) {
    from 'data'
    into layout.buildDirectory.dir('staging')
}
tasks.register('stageBackup', Copy) {
    from 'data'
    into layout.buildDirectory.dir('backup')
}

// Configure an existing task lazily, by name and type.
tasks.named('stageBackup', Copy) {
    description = 'Copies the station data to build/backup.'
}

Removed task syntax

Two spellings from older builds no longer compile. Both were run on 9.8.1.

The first is the left-shift form task name << { ... } that was the standard way to add an action in the first Gradle releases. It was removed in Gradle 5.0 (the upgrade guide for 4.x lists it among the changes that arrive as deprecation warnings in 4.10 and stop working in 5.0); doLast replaces it. The Groovy DSL build file

task hello << {
    println 'Hello from a Gradle 1.x task'
}

fails during configuration, and the fix is tasks.register('hello') { doLast { ... } }. This was run without the configuration cache, because the build fails before the cache matters:

The second is the Kotlin DSL notation "name"() that referenced a task by a string. It was deprecated in the 8.x line (the upgrade guide for 8.x announces its removal in 9.0.0) and removed in Gradle 9.0.0; use named("name"). Dependencies and ordering

Four methods connect tasks, and they answer two different questions. Dependency methods decide what runs; ordering methods decide in which order, if both run anyway.

Method Meaning Adds the other task to the build?

dependsOn(x)

x must run, and run first, before this task.

Yes.

mustRunAfter(x)

If both tasks are in the build, this task runs after x. A hard ordering rule.

No. Running this task alone does not run x.

shouldRunAfter(x)

The same, but only a preference: Gradle ignores it when honouring it would create a cycle, and in a parallel build when every other dependency of the task is satisfied and only the "should run after" task is still pending.

No.

finalizedBy(x)

x runs after this task, whether this task succeeds or fails, and is added to the build automatically.

Yes (the finalizer).

All of them accept a task provider, a task name, or anything else that dependsOn accepts. The next build has four tasks. publish needs fetch, must run after validate when both are requested, and is finalized by notify. Two Gradle properties switch on a failing publish and a circular dependency, so that the same file shows the error cases:

Kotlin DSL
fun step(name: String) = tasks.register(name) {
    doLast { println("running $name") }
}

val fetch = step("fetch")
val validate = step("validate")
val publish = step("publish")
val notify = step("notify")

publish {
    dependsOn(fetch)         // publish needs fetch, so fetch joins the graph
    mustRunAfter(validate)   // if validate is also requested, it goes first
    finalizedBy(notify)      // notify runs after publish, even if publish fails
}

if (providers.gradleProperty("failPublish").isPresent) {
    publish { doLast { throw GradleException("publish failed on purpose") } }
}

if (providers.gradleProperty("cycle").isPresent) {
    fetch { dependsOn(publish) }
}
Groovy DSL
def step(String name) {
    tasks.register(name) {
        doLast { println "running ${name}" }
    }
}

def fetch = step('fetch')
def validate = step('validate')
def publish = step('publish')
def notify = step('notify')

publish.configure {
    dependsOn fetch         // publish needs fetch, so fetch joins the graph
    mustRunAfter validate   // if validate is also requested, it goes first
    finalizedBy notify      // notify runs after publish, even if publish fails
}

if (providers.gradleProperty('failPublish').present) {
    publish.configure { doLast { throw new GradleException('publish failed on purpose') } }
}

if (providers.gradleProperty('cycle').present) {
    fetch.configure { dependsOn publish }
}

Wire inputs instead of using dependsOn

dependsOn between two tasks with actions is the coarsest way to express a relationship: it says "this task needs that task to have run" and nothing about which files it needs. Gradle must then assume that every file the first task produces is an input of the second, which can cause tasks to rerun when an unrelated output changes. The best practices guide therefore reserves dependsOn for lifecycle tasks (as in the dataset task above) and recommends connecting actionable tasks through inputs and outputs, as packData did with from(stageData). With a custom task class this means declaring an @InputFile property and setting it from the output property of the producer; Gradle derives the dependency and the up-to-date check from that wiring (see Writing Custom Tasks and Lazy Configuration & Providers). A related guideline says not to hard-code task names unless they are documented as public API, because most task names of Gradle and of third-party plugins are internal details that can be renamed or removed; prefer a plugin’s DSL, then task types, then names. Passing a task provider, as from(stageData) does, avoids a name altogether.

In the build of "Listing tasks, groups and descriptions" above, stationReport used dependsOn(stageData) on purpose, because it is a simple script task that reads a file in doLast and has no declared inputs. In a real build the report would be a task class whose input is the staged directory.

Source: Gradle User Manual: Best practices, Avoid DependsOn, Don’t hardcode task names

Skipping and limiting tasks

Gradle offers several ways to keep a selected task from doing its work. They differ in what the build log shows and in whether dependants are affected.

Mechanism Effect Log label

onlyIf { ... }

The predicate is evaluated just before execution; false skips the task’s actions. It can carry a reason string (onlyIf("reason") { ... }) that --info prints.

SKIPPED

enabled = false

The task never runs its actions.

SKIPPED

throw StopExecutionException()

Thrown from an action, it stops that action and the following ones of the task; the build goes on with the next task.

none (the task counts as executed)

-x taskName / --exclude-task

Removes the named task from the build; tasks that only it needed also drop out of the log (see below). The user guide calls this a practice to avoid and recommends a suitable lifecycle task instead.

The task does not appear in the log.

timeout

Interrupts the task when it runs too long and fails it.

FAILED

This build has one example of each (the Gradle properties let the same file show the skipped and the executed cases):

Kotlin DSL
import java.time.Duration

val upload = tasks.register("upload") {
    doLast { println("uploading") }
}

upload {
    val offline = providers.gradleProperty("offline")
    onlyIf("the 'offline' property is not set") { !offline.isPresent }
}

tasks.register("legacyExport") {
    enabled = false
    doLast { println("never printed") }
}

tasks.register("guarded") {
    doFirst {
        throw StopExecutionException("nothing to do")
    }
    doLast { println("never printed either") }
}

tasks.register("slow") {
    timeout = Duration.ofMillis(500)
    doLast { Thread.sleep(60_000) }
}

tasks.register("afterSlow") {
    mustRunAfter("slow")
    doLast { println("afterSlow ran") }
}
Groovy DSL
import java.time.Duration

def upload = tasks.register('upload') {
    doLast { println 'uploading' }
}

upload.configure {
    def offline = providers.gradleProperty('offline')
    onlyIf("the 'offline' property is not set") { !offline.present }
}

tasks.register('legacyExport') {
    enabled = false
    doLast { println 'never printed' }
}

tasks.register('guarded') {
    doFirst {
        throw new StopExecutionException('nothing to do')
    }
    doLast { println 'never printed either' }
}

tasks.register('slow') {
    timeout = Duration.ofMillis(500)
    doLast { Thread.sleep(60_000) }
}

tasks.register('afterSlow') {
    mustRunAfter 'slow'
    doLast { println 'afterSlow ran' }
}

Where the books are outdated

Gradle in Action (Muschko, Manning 2014) was written for Gradle 1.7. Its model of tasks (a task is an object with actions, dependencies and a type) is still right, but some of what Gradle 1.7 allowed no longer works or is no longer advised:

  • task name << { ... }. The left-shift operator was the short way to add an action in the Gradle 1.x era. It was removed in Gradle 5.0; use doLast { ... } or, better, tasks.register("name") { doLast { ... } } (run above).

  • Eager task creation. The only task API in Gradle 1.7 was eager (task name(type: Copy), tasks.create, tasks.getByName). The lazy tasks.register and tasks.named arrived in Gradle 4.9 (2018) and are the recommended API now.

  • dependsOn as the main wiring tool. Prefer inputs and outputs wired through properties; dependsOn stays right for lifecycle tasks.

  • The Kotlin DSL. Builds from that era are Groovy only. The Kotlin DSL has been stable since Gradle 5.0 and is the default for gradle init since 8.2, and its "name"() notation is gone (run above).

For the same topics in the other tools see Maven Build Lifecycle and Ant Targets & Extension Points; for the next steps in Gradle see Writing Custom Tasks and Incremental Build.
