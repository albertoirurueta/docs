Gradle Platforms, Constraints & Rich Versions

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Gradle 9.8.1 and was run on JDK 26 on 2026-10-16 (the daemon ran on JDK 26; nothing is compiled, so no toolchain was involved). Every example was run through the wrapper in scratch copies of a small project, once with Kotlin DSL build files and once with Groovy DSL build files, and the output is the same in both except where the text says otherwise. The legend lines that Gradle prints under a dependency report ((c) and (*)) and the Try: hints at the end of a failure are left out, and so is the table of variant attributes in a dependencyInsight report, which is shown as .... The reports (dependencies, dependencyInsight), the probeVersions helper and publishing were checked with --configuration-cache (stored, then reused) and are compatible with it; the examples that fail on purpose were run without it. Gradle 8.14.x was not installed here, so statements about it come from the official documentation and are labelled "not run here".

A version in a dependency declaration is a small program: it says which versions are acceptable, which one is preferred, and how strongly the declaring build cares. Gradle collects those statements from the whole dependency graph and picks one version per module. This page is about the vocabulary for those statements and the objects that carry them:

  • rich versions (require, strictly, prefer, reject) say how much a single declaration cares;

  • dependency constraints say something about a module without adding it to the graph;

  • platforms, either imported from a Maven BOM or built in Gradle, are sets of constraints that travel as one dependency;

  • alignment makes modules that belong together use one version.

How the chosen version is then computed (graph resolution, capability conflicts, the "highest wins" rule itself) is on Dependency Resolution, Conflicts & Capabilities; declaring dependencies and the configurations they live in on Declaring Dependencies & Configurations; catalogs that centralise the coordinates on Version Catalogs; forcing and substituting on Resolution Rules & Substitution; and pinning the result on Dependency Locking, Verification & Caching. The tool-neutral comparison of coordinates, scopes, conflicts and BOMs is Dependency Management Fundamentals.

The scenario used on this page

To make every dependency graph exact, the examples resolve against two kinds of modules. The first is a small local file repository of made-up modules in the group io.tidepool.demo (a POM and an empty JAR for each version, generated by a script), so that the result does not change when someone publishes a new release to Maven Central. Version declarations and ordering

A version string is one of five shapes. The shapes decide which versions are candidates; the rest of this page decides which candidate wins.

Shape Examples Meaning

Exact version

1.3, 1.3.0-beta3

One version. As a plain declaration it is a require (see below), not a pin.

Maven-style range

[1.0,), [1.1, 2.0[, (1.2, 1.5]

[ and ] include the bound, ( and ) exclude it, and ] or [ may be used in place of ( or ) for an exclusive bound. A missing bound is open. An exclusive upper bound acts as a prefix exclude.

Prefix range

1.+, 1.3.+

Versions that start with the part before the +. A bare + is any version.

Latest status

latest.release, latest.integration

The highest version with that status in the repository metadata.

Maven SNAPSHOT

1.0-SNAPSHOT

A changing version: the same coordinates may point to different content over time.

Source: Gradle User Manual: Declaring Versions and Ranges

Whether a version lies in a range, and which of two versions is newer in a conflict, is decided by the version ordering. It is not semantic versioning, and it is not Maven’s comparator either (see Versions, SNAPSHOTs & Ranges):

  • A version is cut into parts at ., -, _ and +, and at every change between digits and letters, so 1a1 is 1.a.1. Only the parts are compared, never the separators: 1.a.1, 1-a+1, 1.a-1 and 1a1 are equal.

  • A number is lower than a bigger number, and any number is higher than a non-number: 1.a is older than 1.1.

  • Non-numbers compare alphabetically and case-sensitively: 1.A < 1.B < 1.a < 1.b.

  • A version with an extra numeric part is higher, even when the part is zero, so 1.1 is older than 1.1.0. A version with an extra non-numeric part is lower: 1.1.a is older than 1.1.

  • dev is lower than any other word, so 1.0-dev < 1.0-ALPHA < 1.0-alpha < 1.0-rc. And rc, snapshot, final, ga, release and sp are higher than any other word, in that order, regardless of case.

Source: Gradle User Manual: Version ordering

The "extra numeric part" rule bites in ranges: 1.3 is not the same version as 1.3.0, and 1.3.0 is higher. A range whose upper bound is written 1.3 therefore does not include 1.3.0, as the dynamic-version run in Dynamic versions and changing modules shows.

Rich versions

A dependency declaration that only carries a version string is a shorthand. The full form is a version constraint with up to four parts, reached through the version { } block of a dependency or a constraint. From the weakest to the strongest:

Term What it says Dynamic versions allowed

prefer

The softest statement: "use this if nobody has a stronger opinion". It applies only when no stronger, non-dynamic version is specified, and it complements require or strictly.

No

require

The selected version can not be lower than this, but conflict resolution may select a higher one, even above an exclusive upper bound. It is what a plain "g:a:1.2" means, and the default for a direct dependency.

Yes

strictly (or !!)

Only versions inside this range are acceptable, nothing outside it can be selected, and on a direct dependency it may downgrade. For a transitive dependency with no acceptable version, resolution fails. It overrides a require and clears earlier reject`s, and it is meant to replace `force.

Yes

reject

Outside the hierarchy: versions that must not be selected. If one would be selected, resolution fails or moves on. It does not constrain the rest of the range.

Yes

Source: Gradle User Manual: Declaring rich versions

The manual’s guidance on which one to use is worth keeping next to this page:

Goal Declaration Why

Prevent a transitive upgrade past a known-good version

strictly("[1.9, 1.10[")

A strict range can not be overridden by a deeper participant in the graph.

Exclude one known-broken version

require("[1.0, 2.0[") and reject("1.4")

reject removes versions from the candidate set without constraining the range.

Bound the versions for the consumers of a library, but stay flexible

strictly("[1.0, 2.0[") and prefer("1.7.25")

The strict range caps consumers; prefer is the default inside it.

Enforce a minimum for a security fix

strictly("[2.17.1, 2.18[") inside constraints { }

A constraint only applies when the module is in the graph.

Make a constraint really cap a version

strictly inside the constraint

A bare version in constraints { } is a require, which still permits upgrades.

Source: Gradle User Manual: Choosing between strictly, reject, and require

strictly: a range that can downgrade

rich-strictly-range declares harmonics with strictly("[1.0, 1.2[") and adds tides-api:1.1.0 (which wants harmonics:1.1.0) and tides-chart:1.0.0 (which wants harmonics:1.2.0, outside the range). Without the strict range the highest requirement, 1.2.0, would win. With it, 1.2.0 can not be selected, so tides-chart's requirement is overridden and the highest version inside the range, 1.1.0, is chosen:

Kotlin DSL
dependencies {
    implementation("io.tidepool.demo:harmonics") {
        version { strictly("[1.0, 1.2[") }
    }
    implementation("io.tidepool.demo:tides-api:1.1.0")
    implementation("io.tidepool.demo:tides-chart:1.0.0")
}
Groovy DSL
dependencies {
    implementation('io.tidepool.demo:harmonics') {
        version { strictly '[1.0, 1.2[' }
    }
    implementation 'io.tidepool.demo:tides-api:1.1.0'
    implementation 'io.tidepool.demo:tides-chart:1.0.0'
}

+--- io.tidepool.demo:tides-api:1.1.0
|    \--- io.tidepool.demo:harmonics:1.1.0
\--- io.tidepool.demo:tides-chart:1.0.0

The Maven way to downgrade a transitive version is a dependencyManagement entry (see Dependency Management & BOMs); Gradle makes the statement on the dependency itself, and the report shows it as {strictly [1.0, 1.2[} followed by the selected version.

Source: Gradle User Manual: Use strictly when you need to prevent version upgrades

strictly with prefer: the preferred version wins inside the range

Adding prefer("1.0.0") to the same range changes the result. Nobody requires 1.0.0, and tides-api requires 1.1.0, which is inside the range, so one could expect 1.1.0. The result is 1.0.0:

Kotlin DSL
dependencies {
    implementation("io.tidepool.demo:harmonics") {
        version {
            strictly("[1.0, 1.2[")
            prefer("1.0.0")
        }
    }
    implementation("io.tidepool.demo:tides-api:1.1.0")
    implementation("io.tidepool.demo:tides-chart:1.0.0")
}
Groovy DSL
dependencies {
    implementation('io.tidepool.demo:harmonics') {
        version {
            strictly '[1.0, 1.2['
            prefer '1.0.0'
        }
    }
    implementation 'io.tidepool.demo:tides-api:1.1.0'
    implementation 'io.tidepool.demo:tides-chart:1.0.0'
}

+--- io.tidepool.demo:tides-api:1.1.0
|    \--- io.tidepool.demo:harmonics:1.1.0 -> 1.0.0
\--- io.tidepool.demo:tides-chart:1.0.0

Requirements of transitive dependencies are overridden by a direct strictly, including the ones that are inside its range. Once they are out of the way, nothing but the prefer is left to choose between 1.0.0 and 1.1.0, and prefer picks 1.0.0. Pairing strictly with prefer therefore says "inside this range, use exactly this unless a direct requirement or a constraint asks for something else". It is the right shape for a library that wants to give its consumers room to move (strictly("[1.0, 2.0[") and prefer("1.1.0")), as the publishing example below shows; for an application that only wants a ceiling, a strictly range without prefer, as in the previous example, selects the highest version in the range.

The !! shorthand

Both strictly and prefer can be written in the string notation: 1.7.15!! is strictly("1.7.15"), and [1.7, 1.8[!!1.7.25 is strictly("[1.7, 1.8[") with prefer("1.7.25"). A project with the shorthand for the range above resolves exactly as the one with the version { } block:

Kotlin DSL
dependencies {
    implementation("io.tidepool.demo:harmonics:[1.0, 1.2[!!1.0.0")
    implementation("io.tidepool.demo:tides-api:1.1.0")
}
Groovy DSL
dependencies {
    implementation 'io.tidepool.demo:harmonics:[1.0, 1.2[!!1.0.0'

Dynamic versions and changing modules

A dynamic version is a range or a latest-status placeholder where an exact version would be: 1.+, [1.1,), latest.release. Gradle asks the repository for the list of versions and picks one at resolution time, so the same build file can resolve differently tomorrow. The helper below creates one resolvable configuration per notation and prints what each one selected, against the five versions of harmonics (1.0.0, 1.1.0, 1.2.0, 1.3.0, 2.0.0). It is compatible with the configuration cache (the second run reused the entry) because it only captures providers:

Kotlin DSL
plugins { `java-library` }

val notations = listOf("1.+", "1.1.+", "[1.0, 1.3[", "(1.0, 1.3]", "(1.0.0, 1.3.0]", "[1.1,)", "latest.release", "latest.integration", "+")

val probes = notations.mapIndexed { i, notation ->
    val bucket = configurations.dependencyScope("probe$i")
    dependencies.add(bucket.name, "io.tidepool.demo:harmonics:$notation")
    val classpath = configurations.resolvable("probe${i}Classpath") { extendsFrom(bucket.get()) }
    notation to classpath.flatMap { it.incoming.resolutionResult.rootComponent }.map { root ->
        root.dependencies.filterIsInstance<ResolvedDependencyResult>()
            .joinToString { it.selected.moduleVersion!!.version }
    }
}

tasks.register("probeVersions") {
    val rows = probes
    doLast {
        rows.forEach { (notation, version) -> println("%-20s -> %s".format(notation, version.get())) }
    }
}
Groovy DSL

Dependency constraints

A dependency constraint sets a version requirement for a module without adding the module to the graph. If something else brings the module in, the constraint takes part in conflict resolution like a declared version; if nothing does, it is ignored. That is what makes it the right tool for transitive dependencies: a security floor, a "tested with" version, a way to keep the version declaration out of the places that use the module. Constraints are declared in a constraints { } block inside dependencies { }, are scoped to a configuration like any dependency, and can carry a because message.

Raising a transitive version

tides-api:1.0.0 pulls in harmonics:1.0.0. The project has no dependency on harmonics of its own and wants at least 1.2.0 whenever it appears. A second constraint is on a module that nothing in the graph uses:

Kotlin DSL

        implementation("io.tidepool.demo:harmonics:1.2.0") {

        }
        implementation("io.tidepool.demo:tides-chart:1.0.0")

}

Why enforcedPlatform is discouraged for libraries. The strictness is part of what the build declares, and a library publishes it. The manual adds a rule of thumb: enforcedPlatform to pin all the versions of a BOM as a group, strictly on individual dependencies when one or two modules need control, and it warns that mixing a platform with a strictly on one of its modules lets the strictly drive the result for that module and its own transitive dependencies, leaving the BOM’s other members where the BOM put them.

The three solutions differ in who has to act. Preventing accidental upgrades

Gradle upgrades optimistically: if two parts of the graph want different versions of a module, the highest wins, even above what your own build declared. That is the right default for a library ecosystem and the wrong one when you depend on an API that a newer version removed. The manual names three ways to say "not this time", and they differ in how loud they are.

Releases, Gradle 8.14 and where the books are outdated

The mechanisms on this page arrived over several releases, each from its release notes.

Release What changed

4.6

Dependency constraints for transitive dependencies; importing BOMs and compile/runtime separation when consuming POMs, as a feature preview that had to be enabled in the settings file.

5.0

Dependency version alignment, usable with Maven BOMs; the release notes show platform() and enforcedPlatform() for importing a BOM.

5.3

Fixes a bug of 5.0 to 5.2.1 in which an enforcedPlatform import of a POM that had both dependencies and dependencyManagement included the dependencies instead of only the constraints; platform and enforcedPlatform dependencies no longer try to download JARs.

6.0

Gradle Module Metadata is published by default; rich versions (strictly, prefer, reject), constraints and alignment are stable and production-ready.

7.0

The compile, runtime and testCompile configurations and the maven plugin are removed; version catalogs appear as a preview (stable in 7.4).

9.0

jcenter() is removed and Gradle runs on JVM 17 and later.

9.8

Reuse of Maven mirror settings (org.gradle.mirror.maven.settings=true), relevant to where BOMs are downloaded from.

Pitfalls

Pitfall What to do

A bare version in constraints { } does not cap a version

It is a require. Use version { strictly(...) } inside the constraint.

strictly plus prefer selects the preferred version, not the highest in the range

Intentional: a direct strictly overrides the transitive requirements. Drop the prefer to get the highest.

(1.0, 1.3] does not include 1.3.0

1.3 is older than 1.3.0. Write the full version in the bound.

A strictly in a dependency’s constraints is dropped when the root project is strict about the same module

Root-most wins. Put the statement in the root project, or accept that the dependency’s is ignored.

enforcedPlatform in a library

Its strictness is published and spreads to consumers. Use it only in applications.

doNotEndorseStrictVersions() fails the build

The platform’s strict constraint is no longer applied to other dependencies' requests, but it still stands. Change the dependency that asks for the out-of-range version, or the platform.

The manual’s Kotlin snippet for doNotEndorseStrictVersions() does not compile

The lambda of platform(...) is typed Dependency; cast to ModuleDependency.

The manual’s Groovy ctx.details.run { } rule fails in Gradle 9.8.1

Read ctx.details.id and call belongsTo on ctx.details instead.

Dynamic versions are cached for 24 hours

cacheDynamicVersionsFor for a build that must see new releases at once; locking for builds that must not.

A POM-only consumer loses strictly, prefer and reject

Publish Gradle Module Metadata (the default) and keep the strict ranges wide.
