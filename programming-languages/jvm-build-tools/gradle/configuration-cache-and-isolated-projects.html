Gradle Configuration Cache & Isolated Projects

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Gradle 9.8.1 (released on 7 October 2026, the current release on 2026-10-16), with Gradle 8.14.6, the last 8.x release, mentioned where it differs. Every example marked as run was executed with the 9.8.1 wrapper on 2026-10-16, on macOS (Apple silicon), in scratch copies of the tidepool build used throughout this section (a model library, an engine library that reads a CSV file with Commons CSV, and a command line application that uses picocli), once with *.gradle.kts files and once with *.gradle files. The Gradle daemon ran on Oracle JDK 26 (java version "26"), the machine’s default JDK; the modules compile with a Java 21 toolchain, which is a JetBrains Runtime (JBR) 21.0.10 that Gradle found on the machine (see Gradle Toolchains). Every run used a Gradle User Home created for the page (the GRADLE_USER_HOME environment variable), so that no daemon or cache of the real ~/.gradle was touched; its gradle.properties holds org.gradle.java.installations.auto-download=false, so that no JDK could be downloaded, and org.gradle.jvmargs=-Xmx512m -Duser.language=en -Duser.country=US, so that the JVM messages are in English. In the listings the scratch directory is shown as <work>, output is shortened only by leaving out, in some listings, blank lines, the summary line N actionable tasks, the * Try: hints that end a failure message or the > Task lines, and the --console=plain option of the runs is left out of the command lines. Gradle 8.14.x was not available here, so what is said about it comes from the official release notes and upgrade guides and is labelled "not run here"; five more things were not run, and are labelled the same way: the Gradle properties org.gradle.configuration-cache.parallel and org.gradle.configuration-cache.integrity-check, the STABLE_CONFIGURATION_CACHE feature preview, a configuration cache shared between machines (it does not exist yet), and IDE syncs (no IDE was used).

The configuration cache is the answer to a cost that every Gradle build pays on every run: before the first task can start, Gradle has to execute the settings file, every build script and every plugin, to find out which tasks exist and how they depend on each other (see The Gradle Build Lifecycle). That is the configuration phase, and in a large build it can take longer than the tasks themselves. With the configuration cache, Gradle stores the result of that phase and, if nothing it depended on has changed, loads it instead of computing it again. This page covers how that works, how to switch it on, what invalidates it, the rules that build logic must follow so that it can be stored, how to read the problem report, what it does to task execution, and what its status is. The second half covers Isolated Projects, the incubating feature built on top of it that makes the configuration of the subprojects of a multi-project build run in parallel. The related caches are separate pages: the build cache reuses task outputs (Gradle Build Cache) and the dependency cache stores downloaded files (Dependency Locking, Verification & Caching).

How the configuration cache works

Without the configuration cache, every invocation goes through the three phases of the build lifecycle: initialization (find the settings file and the projects), configuration (run the init scripts, the settings file, buildSrc, the build scripts and the plugins, then calculate the task graph) and execution. With it, Gradle writes the result of configuration to disk the first time and, at the start of the next invocation, decides whether it can load that result instead:

flowchart TD A["Invocation: requested tasks and arguments"] --> B{"Entry stored for this key?"} B -- no --> M["Cache miss: run the configuration phase"] B -- yes --> C{"Every recorded input unchanged?"} C -- no --> M C -- yes --> H["Cache hit: skip the configuration phase"] M --> S["Serialize the task graph into .gradle/configuration-cache"] S --> L["Load the graph back from the entry"] H --> L L --> X["Execute the tasks, in parallel where they are independent"]

The pieces, from the manual:

  • The key of an entry is the set of requested tasks, their arguments and some environment information; ./gradlew build and ./gradlew check have different entries.

  • The entry is a snapshot of the task graph: which tasks run, in which order, with the complete state of every task instance (every field, including private ones) and the objects reachable from it. Gradle does not use Java serialization for this, although it understands classes that implement Externalizable or define writeObject and readObject.

  • Next to the snapshot is a fingerprint, the list of everything configuration read from the outside world (see the next section). On a hit Gradle first replays the fingerprint to check that it still holds, and only then deserializes the graph.

  • Even on a miss, Gradle loads the graph back from the entry it has just written and executes the loaded copy. That makes hits and misses run through the same code, so a task that cannot survive serialization fails on the first run with the cache on, not on a later one. It also means that the parallel execution described below is available on a miss.

  • On a hit nothing from configuration runs again: init scripts, the settings file, build scripts and plugins are not evaluated. Code that was registered during configuration to be called later, such as gradle.taskGraph.whenReady { }, does not run either.

Source: Gradle: Configuration Cache, how it works and serialization

The configuration cache and the build cache are different things that compose:

Configuration cache Build cache

What it stores

The result of the configuration phase: the task graph, each task’s configured state and the dependency information.

The outputs of tasks, and of artifact transforms.

The build logic and environment: scripts, init scripts, environment variables and properties read at configuration time, and more.

The first run, and the second

The first experiment shows what a miss and a hit look like. The root project has a build script that prints when it is configured and when the task graph is ready, and that sleeps for two seconds, to stand in for an expensive configuration phase (a real build gets this from many plugins and many projects; the sleep is only a way to make the effect visible in a build this small):

Kotlin DSL: build.gradle.kts
println("configuring the root project")
Thread.sleep(2000) // stands in for an expensive configuration phase

gradle.taskGraph.whenReady {
    println("task graph ready: ${allTasks.size} tasks")
}
Groovy DSL: build.gradle
println 'configuring the root project'
Thread.sleep(2000) // stands in for an expensive configuration phase

gradle.taskGraph.whenReady {
    println "task graph ready: ${it.allTasks.size()} tasks"

Enabling the configuration cache

By default, Gradle 9.8.1 does not use the configuration cache. There are two ways to ask for it, and one to switch it off again:

Command line Gradle property (gradle.properties) Effect

--configuration-cache

org.gradle.configuration-cache=true

Use the cache for this build, or for every build.

--no-configuration-cache

org.gradle.configuration-cache=false

Do not use it. The command line wins over the property, so --no-configuration-cache switches off a cache that gradle.properties turned on. Setting false in the file also silences the Gradle 9 hint described below.

--configuration-cache-problems=warn

org.gradle.configuration-cache.problems=warn

Report problems as warnings instead of failing the build. The default is fail. A migration aid, discussed below.

-Dorg.gradle.configuration-cache.max-problems=5

org.gradle.configuration-cache.max-problems=5

Stop after this many problems. The default is 512, which only matters in warning mode.

-Dorg.gradle.configuration-cache.read-only=true

org.gradle.configuration-cache.read-only=true

Use entries but never write them (incubating, 9.1.0).

-Dorg.gradle.configuration-cache.parallel=true

org.gradle.configuration-cache.parallel=true

Store entries in parallel (incubating; not run here).

-Dorg.gradle.configuration-cache.integrity-check=true

org.gradle.configuration-cache.integrity-check=true

Stricter checks when writing and reading, for tracking down serialization bugs (8.14; not run here).

The list of all org.gradle.* properties is in Build Environment & Properties, and the command line options are in The Gradle Command Line Interface. To keep the cache on for a project, commit the property:

gradle.properties
org.gradle.jvmargs=-Xmx512m -Duser.language=en -Duser.country=US
org.gradle.java.installations.auto-download=false
org.gradle.configuration-cache=true

With that file, a plain ./gradlew hello stores an entry on the first run and reuses it on the second, and --no-configuration-cache turns it off for one build (the root project has a task hello that prints a line):

$ ./gradlew hello

BUILD SUCCESSFUL in 873ms

$ ./gradlew hello --no-configuration-cache

Source: Gradle: Enabling the Configuration Cache and ignoring problems

IDEs that delegate builds to Gradle pick up gradle.properties, so the property above enables the cache for the whole team, which is usually what is wanted. To enable it only in your IDE, add -Dorg.gradle.configuration-cache=true to the VM options of the Gradle run configuration template in IntelliJ IDEA (Run > Edit configurations > Templates > Gradle), or use the Gradle preferences of Buildship in Eclipse. Only running tasks from the IDE uses the cache; the project import and sync do not (not run here: no IDE was used). The manual says not to put problems=warn into an IDE configuration.

Source: Gradle: Configuration Cache, IDE support

The Gradle 9 hint

The first listing of this page ended with "Consider enabling configuration cache to speed up this build". Gradle 9.0.0 made the configuration cache the preferred mode of execution: it is still off by default, but a build that has no known incompatibility prints that hint, to encourage adoption. The release notes say that some problems can only be found with the cache on, so the hint is not a guarantee that the build is compatible. The way to say "not yet" is org.gradle.configuration-cache=false in gradle.properties.

Source: Gradle 9.0.0 release notes: Configuration Cache improvements

Detecting the cache from build logic

A plugin can adapt to the cache, for example to disable an optional feature that is not yet compatible, by asking the BuildFeatures service. The manual says to use this sparingly, because the goal is the same behaviour with and without the cache. The service is injected, which a build script does through a small interface:

Kotlin DSL: build.gradle.kts
import org.gradle.api.configuration.BuildFeatures

interface Injected {
    @get:Inject
    val buildFeatures: BuildFeatures
}

val features = objects.newInstance<Injected>().buildFeatures

tasks.register("hello") {
    val requested = features.configurationCache.requested.orNull
    val active = features.configurationCache.active.get()
    doLast {
        println("configuration cache requested=$requested active=$active")
    }
}
Groovy DSL: build.gradle
import org.gradle.api.configuration.BuildFeatures

interface Injected {
    @Inject
    BuildFeatures getBuildFeatures()
}

def features = objects.newInstance(Injected).buildFeatures

tasks.register('hello') {
    def requested = features.configurationCache.requested.orNull
    def active = features.configurationCache.active.get()
    doLast {
        println "configuration cache requested=$requested active=$active"
    }
}
Output (Gradle 9.8.1, Kotlin DSL; the Groovy DSL printed the same)
$ ./gradlew --no-configuration-cache hello
> Task :hello
configuration cache requested=false active=false
BUILD SUCCESSFUL in 1s

$ ./gradlew --configuration-cache hello
Calculating task graph as no cached configuration is available for tasks: hello
> Task :hello
configuration cache requested=true active=true
BUILD SUCCESSFUL in 821ms
Configuration cache entry stored.

What invalidates an entry

An entry is valid as long as every input that configuration read has the same value. The manual lists them:

Input Examples

The Gradle environment

GRADLE_USER_HOME and the daemon JVM.

Build logic

Init scripts; the contents of buildSrc and of included builds that provide build logic; build and settings scripts, including scripts applied with apply from.

Gradle configuration files

Version catalogs, dependency verification files, dependency lock files and gradle.properties files.

Files read at configuration time, and the file system state checked then

The contents of any file the build reads; whether a file exists; the contents of a directory.

Values obtained at configuration time

System properties, environment variables, ValueSource values (including the built-in providers.exec and providers.fileContents), and Gradle properties (-P).

Source: Gradle: Configuration Cache, build configuration inputs

Gradle records these inputs while the configuration phase runs. To see them without declaring anything, it instruments the bytecode of build scripts and plugins with a Java agent, which detects reads such as System.getenv. The next experiment reads one file, one system property and one environment variable while the task is configured, and prints them when it runs. The values are read inside the configuration block of the task, not at the top of the script; the reason is explained in the requirements section below.

Kotlin DSL: build.gradle.kts
tasks.register("report") {
    val stations = file("data/stations.csv").readLines().size - 1
    val region = System.getProperty("tidepool.region", "global")
    val stage = System.getenv("TIDEPOOL_STAGE") ?: "dev"
    doLast {
        println("stations=$stations region=$region stage=$stage")
    }
}
Groovy DSL: build.gradle
tasks.register('report') {
    def stations = file('data/stations.csv').readLines().size() - 1
    def region = System.getProperty('tidepool.region', 'global')
    def stage = System.getenv('TIDEPOOL_STAGE') ?: 'dev'
    doLast {
        println "stations=$stations region=$region stage=$stage"
    }
}

Read lazily, and the entry survives

The remedy for needless invalidation is not to read at configuration time but to wire a provider into the task, so that the value is read when the task runs (see Lazy Configuration & Providers). The same experiment, with a task class whose inputs are properties (providers.systemProperty and providers.environmentVariable return providers that are resolved at execution time):

Kotlin DSL: build.gradle.kts
abstract class Report : DefaultTask() {
    @get:Input
    abstract val region: Property<String>

    @get:Input
    abstract val stage: Property<String>

    @TaskAction
    fun run() {
        println("region=${region.get()} stage=${stage.get()}")
    }
}

tasks.register<Report>("report") {
    region = providers.systemProperty("tidepool.region").orElse("global")
    stage = providers.environmentVariable("TIDEPOOL_STAGE").orElse("dev")
}
Groovy DSL: build.gradle
abstract class Report extends DefaultTask {
    @Input
    abstract Property<String> getRegion()

    @Input

Invalidating by hand, and how long entries live

Gradle invalidates automatically when a tracked input changes. If you have ignored problems, or if a build reads something that Gradle cannot see, you may need to delete the cache yourself:

$ rm -rf .gradle/configuration-cache

Gradle also cleans up after itself: at most every 24 hours it checks whether entries are still in use, and entries unused for 7 days are deleted. The cache lives with the project, so a fresh checkout, a clean CI agent or a deleted .gradle directory starts with a miss.

Source: Gradle: Invalidating the Configuration Cache

Temporary opt-outs

Every Gradle release tightens the cache in two directions: it detects more reads of the environment, so that a changed value correctly invalidates, and it requires more things to be serializable. When a stricter rule breaks a build whose problem is in a plugin you cannot fix, the manual offers properties that revert to the old behaviour. They are meant to be temporary and will be removed in later releases:

Property What it reverts

org.gradle.configuration-cache.inputs.unsafe.ignore.file-system-checks

Tracking of File.exists(), File.isFile() and similar checks as inputs. The value is a list of paths relative to the root project, separated by ;, with * and ** wildcards; a path starting with ~/ is relative to the home directory.

org.gradle.configuration-cache.inputs.unsafe.ignore.in-serialization

Requirements for build logic

To store the task graph, Gradle must be able to turn every scheduled task, and everything the task refers to, into bytes and back, and the result of configuration must not depend on anything that Gradle did not see. That puts rules on build scripts, plugins and tasks. The manual calls them requirements. Most violations are detected and reported as problems, which fail the build; some cannot be detected (a process started through a code path that Gradle does not instrument is the example the manual gives) and produce stale results on a hit, because the value is not tracked as an input. In nearly all cases a requirement exposes an undeclared input, so that using the cache is, as the manual puts it, an opt-in to a stricter and more correct build. The sections below take the rules that break builds most often, each with a real failure and the repair.

Source: Gradle: Configuration Cache Requirements for your Build Logic

Values from outside the build: providers, ValueSource, processes and files

Environment variables, system properties, files and external commands are external information. Gradle tracks the first three when scripts read them with the ordinary APIs, as the invalidation experiments above showed, and offers lazy providers for them so that they are read at execution time. For anything else, and for anything where "any change" invalidates too much, the tool is a ValueSource (see Lazy Configuration & Providers). Its obtain() method runs on every build; only the value it returns is tracked. The cache entry is reused as long as that value is the same. The next experiment decides whether the build is running on a CI server from the presence of the CI variable, and records the operating system with providers.exec:

Kotlin DSL: build.gradle.kts
abstract class RunningOnCi : ValueSource<Boolean, ValueSourceParameters.None> {
    override fun obtain(): Boolean = System.getenv("CI") != null
}

val onCi = providers.of(RunningOnCi::class) {}
val os = providers.exec { commandLine("uname", "-s") }.standardOutput.asText.map { it.trim() }

tasks.register("describe") {
    val mode = if (onCi.get()) "ci" else "local"
    val system = os.get()
    doLast {
        println("mode=$mode os=$system")
    }
}

Build listeners and build services

Callbacks that are registered during configuration to be called during execution cannot survive a hit, because the code that registered them did not run. The manual names BuildListener, TaskExecutionListener, gradle.taskGraph.afterTask and gradle.buildFinished. The first experiment of this page already showed the symptom with gradle.taskGraph.whenReady: its line was printed on the miss and not on the hit. The supported replacement for "observe task execution events" is a build service that implements OperationCompletionListener and is registered with BuildEventsListenerRegistry.onTaskCompletion; for "run something when the build is over" it is the close() of an AutoCloseable service, or a flow action (both are covered in The Gradle Build Lifecycle, which also tabulates the listeners). A minimal listener that counts the tasks finished in a build:

Kotlin DSL: build.gradle.kts

abstract class TaskCounter : BuildService<BuildServiceParameters.None>, OperationCompletionListener, AutoCloseable {

        if (event is TaskFinishEvent) {
            finished++
        }
    }

    override fun close() {
        println("tasks finished in this build: $finished")
    }
}

interface Injected {
    @get:Inject
    val events: BuildEventsListenerRegistry
}

The other rules, in short

Rule What to do instead

Tasks must not hold live JVM state or Gradle model types: ClassLoader, Thread, streams, sockets, locks and other java.util.concurrent synchronization types; Project, Gradle, Settings; unresolved Configuration objects.

Declare inputs as properties and file collections. Task fields of type Configuration are resolved at store time and come back as a FileCollection, so declare a FileCollection in the first place.

A task must not read the state of another task instance at execution time.

Connect tasks with outputs and inputs (a task output is a provider); a task that configures other tasks at execution time is unsupported.

Every instance field of a task is stored, so tasks that shared a mutable object at configuration time get independent copies.

Share mutable state through a build service. Reference identity is kept for instances of your own classes but not for String, File or most collections.

A task must not read conventions, extensions or extra properties (the ext block) at execution time. Without the cache this is already a deprecation warning, and it becomes an error in Gradle 10.

Model the value as a task property.

Libraries that check their own bytecode can fail, because Gradle rewrites build-logic bytecode with a Java agent to track inputs.

Run them through the Worker API with classloader or process isolation (see Worker API & Build Services). Gradle 9.7.0 also made third-party -javaagent attachments work with the cache and TestKit.

Secrets in task fields end up in the entry.

See the security section below.

Source: Gradle: Types that must not be referenced by tasks, accessing a task from another and bytecode modifications and the Java agent

Problems, the report and incompatible tasks

By default, a build with a configuration cache problem fails and its entry is discarded; that is what the project.copy experiment showed. The report linked from the output is the main tool, and the manual recommends this routine: read the report, group by message to find the pattern, group by task to find the owner, expand the problem tree to find the field that holds the offending object, follow the link next to the problem to the matching requirement, and test the repair with TestKit (see Testing & Publishing Gradle Plugins) if the code is a plugin.

Diagnosing obscure failures

Gradle writes entries with only minimal integrity checks, for speed. When loading an entry fails with an obscure error such as "Index 4 out of bounds for length 3", Gradle 8.14 added the property org.gradle.configuration-cache.integrity-check=true, which gives a precise error naming the field and the task whose state could not be read back. It makes entries bigger and slower, so it is for troubleshooting only (not run here). Typical causes are classes that implement Serializable with a writeObject that does not match readObject; Gradle supports a subset of Java serialization for them, with the limitations listed in the status page.

Source: Gradle: Use Integrity Checks and Gradle 8.14 release notes: integrity check mode

Parallel task execution

When the configuration cache is on, the tasks of one invocation run in parallel when they are independent, even inside a single project. Without it, Gradle’s --parallel runs tasks of different projects at once, but tasks of one project cannot, because they share the Project object and contend for project-level locks. With the cache, every task works on its own deserialized copy of its state, so it needs no project lock. Two tasks that each sleep for two seconds and print the clock make it visible:

Kotlin DSL: build.gradle.kts
import java.time.LocalTime

    @TaskAction

        val clock = DateTimeFormatter.ofPattern("HH:mm:ss")
        println("$name started ${LocalTime.now().format(clock)}")
        Thread.sleep(2000)
        println("$name finished ${LocalTime.now().format(clock)}")
    }
}

tasks.register<Nap>("napA")
tasks.register<Nap>("napB")

Security

The entry contains the complete state of every scheduled task, including private fields, so a password, token or key that a task field holds is stored too. Gradle encrypts the entry and the fingerprint with a machine-specific key that it creates as needed and keeps in the Gradle User Home (in this run, caches/9.8.1/cc-keystore/gradle.keystore under the Gradle User Home); the encryption has been on since Gradle 8.1. It does not help if an attacker can read both the project’s .gradle/configuration-cache directory and the key, so the manual’s advice is:

  • Keep credentials in GRADLE_USER_HOME/gradle.properties: that file is not serialized, only its fingerprint is recorded. Use the credentials API of repositories (see Gradle Repositories & Content Filtering) so that Gradle looks the values up when it needs them.

  • Do not pass secrets through system properties or environment variables read at configuration time: they go into the fingerprint. Wire providers.environmentVariable() into the task instead, so that the value is read at execution time.

  • Mark fields that are not needed after loading as transient; there is no Gradle annotation to exclude one field from the entry.

  • Do not let .gradle/configuration-cache be committed or published, and restrict access to it and to the key on shared and CI machines. The GRADLE_ENCRYPTION_KEY environment variable sets the key explicitly where a per-machine keystore is not suitable, for example when the Gradle User Home is shared between machines.

Source: Gradle: Configuration Cache, security considerations, Handling of Credentials and Secrets and Gradle 8.1 release notes: securing the configuration cache

Status

The configuration cache has been through four stages: experimental in Gradle 6.6 (2020-08-10), stable in 8.1 (2023-04-12, when the properties lost their unsafe prefix and the cache became encrypted), the preferred mode of execution in 9.0.0 (2025-07-31; still off by default, with a hint and a graceful fallback), and, announced for the future, on by default in Gradle 10. The manual says the same in its own words: "This feature will be enabled by default in Gradle 10", with these limitations today: some core plugins and features have partial or pending support, builds and their plugins may need changes, IDE imports and syncs do not use the cache, and support for CI is still evolving.

Plugin support, as listed on the status page for 9.8.1: the core plugins for JVM languages and frameworks (Java, Java Library, Java Platform, Groovy, Scala, ANTLR), the native ones, Application, WAR, EAR, Distribution, code analysis (Checkstyle, CodeNarc, JaCoCo, PMD), the aggregation plugins, Signing, Build Init and the plugin-development plugins are all supported. Maven Publish and Ivy Publish are marked as partially supported: some of their features disable the cache (see Publishing with Gradle). Of the community plugins, the manual names the Android Gradle Plugin and the Kotlin Gradle Plugin as supported, and points to a Gradle issue that tracks the rest.

What is not yet implemented, per the same page:

  • Sharing the cache. It is stored locally only: hot and cold daemons on the same machine can reuse it, but developers and CI machines cannot share entries. This is why the CI recommendation is the read-only mode above, and why, until sharing exists, the build cache is what carries work between machines.

  • Parallel storing independent of --parallel.

  • Only part of Java serialization: classes that implement Externalizable, or define writeObject and/or readObject, writeReplace or readResolve; serialPersistentFields and several stream methods are not supported.

  • Calling top-level methods and variables of a build script at execution time (the experiment above).

  • A build service, or a provider derived from one, as a ValueSource parameter that is read at configuration time; arbitrary providers as build event listeners.

  • Selective exclusion of sensitive values from the entry.

Source: Gradle: Configuration Cache Status, core plugins and not yet implemented; the practical recommendation is in Gradle: Best Practices, use the configuration cache

Isolated Projects

The configuration cache skips configuration when nothing changed. Everything else still configures all the projects, one after another: a change to any build script, the first build on a clean checkout, and every IDE sync. In a build with hundreds of projects that is minutes. Isolated Projects attacks that cost differently: it forbids a project’s build logic from reaching into another project’s mutable state, and as a result Gradle can configure the projects in parallel, and, in the future, cache and re-run them individually. Isolated Projects reached Gradle 9.7.0 (2026-08-06) as an incubating feature (it was experimental before, with property names starting with org.gradle.unsafe), so its API and behaviour may still change and the release notes mark the changes. The 9.7.0 release notes say it is not enabled by default and not yet recommended for production, and that compatibility with the configuration cache is a prerequisite.

Source: Gradle: Isolated Projects and Gradle 9.7.0 release notes: Isolated Projects

What it speeds up

Isolated Projects changes one phase. Initialization (init scripts and the settings file) stays sequential. Configuration of the projects runs in parallel, including the compilation of their build scripts. Execution is not affected, because with the configuration cache tasks already run in parallel. On a hit, the whole initialization and configuration are skipped, with or without Isolated Projects. The manual points out that the gain is bounded by the share of configuration in the total build time: on a machine with N cores the build does not become N times faster, and if configuration is 40 percent of the build the ceiling is 40 percent. Two more limits apply today: all projects are always configured (there is no project configuration avoidance, and configuration on demand has no effect), and a subproject cannot start until its parents are done, so siblings are the unit of parallelism. The degree of parallelism is org.gradle.workers.max (the number of cores by default). For IDE sync, parallel model building is switched on automatically with Isolated Projects in Android Studio Electric Eel or later and IntelliJ IDEA 2026.1.1 or later (not run here).

The constraints

During configuration Gradle does many small things (evaluate the settings, configure each project), and each of them mutates live objects such as Project, Settings and Gradle. Isolated Projects does not change how a project is configured: plugins still mutate the project they are applied to. It adds boundaries so that one unit cannot observe or change the mutable state of another:

Kind What is not allowed

Cross-project access

A project reading or changing mutable state of another project: description, group, version, buildDir; its tasks, dependencies, configurations, artifacts, repositories, plugins, extensions and ext; its layout, providers and objects. Allowed: the immutable data fixed during settings evaluation (name, path, depth, projectDir, buildFile, rootDir) and navigating the project tree (rootProject, parent, project(...), subprojects, allprojects), but then only to read that data. group, version, buildDir and layout are mutable.

Project-to-build access

A project using mutable state of its Gradle object: registering listeners or evaluation callbacks (addBuildListener, beforeProject, afterProject), applying plugins, using extensions. Allowed: gradleVersion, gradleUserHomeDir, buildPath, includedBuilds, providers, startParameter. Registering a build service with registerIfAbsent is safe; querying the set of registrations is limited to findByName.

Cross-build access

Using gradle.parent from an included build. Not fully enforced yet; avoid it.

Build-to-project access

Settings or init-script callbacks that capture mutable build state and run during the configuration of projects, possibly in parallel. Not fully enforced yet; use the state-isolating callbacks below.

Behavior changes

Isolated Projects changes the behaviour of a few APIs, because it validates what would have given a different result. The one that matters is that a project no longer finds properties and methods of its parent projects implicitly: a reference to a property that only the root project defines does not fall through to the root. Gradle 9.6.0 deprecated that lookup also without Isolated Projects, and it is announced as removed in Gradle 10. Lenient lookups such as Project.findProperty() do not fail, they return a different value, so the manual recommends fixing the deprecation warnings first, and offers a feature preview flag, enableFeaturePreview("NO_IMPLICIT_LOOKUP_IN_PARENT_PROJECTS") in the settings file, that gives the same behaviour in all modes (not run here). In the same way, the properties report of a subproject no longer lists the properties it would have inherited, and Project.getProperties() is a violation.

Source: Gradle: No implicit lookup of properties and methods in parent projects

Migrating a build

The manual’s path, in the order to follow it:

  1. Upgrade Gradle to the latest release (a milestone or nightly if you want the freshest fixes while the feature is incubating), update the plugins, and use a recent IDE (IntelliJ IDEA 2026.1.1 or later is recommended).

  2. Make the build compatible with the configuration cache first. Isolated Projects is built on it.

  3. Address the deprecations that concern the behaviour changes above.

  4. Run ./gradlew help --isolated-projects -Dorg.gradle.isolated-projects.diagnostics=true and read the violations in the report. They are the ones that appear in virtually any workflow, so they come first.

  5. Report violations that come from community plugins to their maintainers, and fix your own build logic. An incompatible plugin takes away the benefit.

  6. Repeat for IDE sync (both properties in gradle.properties, because sync does not read the command line), then for the other workflows: tests, checks and so on, since lazy configuration hides violations until a task is realized.

  7. Switch the Diagnostics mode off once the violations are gone.

If you want to estimate the gain before fixing everything, -Dorg.gradle.isolated-projects.dangerously-ignore-problems=true reports the violations but does not fail the build. Making build logic compatible

The strategies of the manual, in order of preference:

  1. Convention plugins. A project applies the plugin to itself, so nothing configures another project. This is also the recommended way to share build logic for other reasons; see Convention Plugins & Sharing Build Logic. Plugins compose, so reuse does not cost compatibility.

  2. State-isolating lifecycle callbacks. When configuring many projects from one place is really wanted, gradle.lifecycle.beforeProject { } and afterProject { } (the GradleLifecycle API) register actions that run in a context private to each project, which is what the configuration cache does for tasks. They must be registered from the settings file or a settings plugin, not from a project.

  3. IsolatedProject instead of Project. Where a project must read something about another one, isolated (for example isolated.rootProject.projectDirectory) gives the immutable data.

  4. Guard incompatible code as a last resort.

The experiment replaces the violating build with the second and third strategies. The allprojects block and the root build script are gone; the settings file sets the group and version of every project from a version.txt in the root, and tidepool-engine reads its own coordinates:

A limitation applies to the callbacks: a beforeProject callback only registers an action and does not resolve plugins, so it can apply a plugin that is already on the project’s classpath, such as the core base plugin used by the manual, but not one that is resolved lazily from a repository or from an included build registered with pluginManagement.includeBuild. The manual’s recommended workaround is to register the callback from a settings convention plugin, where the included build’s classpath is available; the other is to declare the plugin in the settings plugins { } block with apply false, which forces its resolution. Plugins from buildSrc are not affected, but the manual advises against moving logic into buildSrc just to avoid this. Plugin authors can declare in their descriptor that the plugin is compatible, with the compatibility { features { isolatedProjects = true } } block of the Plugin Publish plugin (Gradle 9.8.0; see Testing & Publishing Gradle Plugins).

Isolated Projects and the other features

  • Configuration cache. A prerequisite, and a base: violations are reported as configuration cache problems, and --configuration-cache-problems=warn no longer downgrades them (9.7.0). Storing the entry in parallel is the same mechanism as the parallel storing of the cache, now made safe by the constraints.

  • --parallel. It concerns the execution of tasks of different projects and is independent of project configuration.

  • Configuration on demand has no effect, since all projects are configured; see The Gradle Build Lifecycle.

  • Included builds. A change to an included build invalidates all cached results, even unrelated ones (a current limitation); see Gradle Composite Builds.

  • Build Scan and profile reports are the way to measure the configuration phase before and after (see Performance Profiling & Build Scans).

Where the books are outdated

The book Gradle in Action (Gradle 1.7) predates the cache by seven years. Its builds read the environment and the project freely at execution time, which was normal; the statement "no configuration cache; project used freely at execution" is the one this page replaces. Today the configuration cache has been stable since 8.1 and preferred since 9.0, Task.project at execution time is a problem (a deprecation in the 8.x upgrade guide), and the book’s idiom of cross-project configuration with allprojects and subprojects is what Isolated Projects forbids, in favour of convention plugins. See Gradle Versions, Compatibility & Release History for the other version changes.

Summary

  • The configuration cache stores the result of the configuration phase (the task graph, with the state of every task) in .gradle/configuration-cache and, if every recorded input is unchanged, loads it instead of configuring the build; on a hit the scripts and plugins do not run at all.

  • Switch it on with --configuration-cache or org.gradle.configuration-cache=true. It is stable since 8.1, the preferred mode since 9.0 and announced as the default for Gradle 10.

  • An entry is invalidated by changes to build scripts, gradle.properties, catalogs, init scripts, files read at configuration time, and the system properties, environment variables and -P properties that configuration read. Gradle names the reason. Read values lazily, with providers and ValueSource, to avoid needless invalidation.

  • Build logic must not use Project while a task runs, must not capture the Kotlin script object or call script methods from actions, must not start processes or register listeners at configuration time, and should resolve dependencies lazily: eager resolution at store time shows latent errors.

  • Problems fail the build and discard the entry; the HTML report explains them. --configuration-cache-problems=warn and notCompatibleWithConfigurationCache() are migration tools, not a way of life.

  • With the cache tasks run in parallel even inside one project, and --no-parallel does not change that. In CI, the read-only mode avoids the cost of writing an entry nobody will read, but does not detect problems.

  • Entries contain the state of all tasks, are encrypted with a key in the Gradle User Home, and are local only; keep secrets out of task fields and in GRADLE_USER_HOME/gradle.properties.

  • Isolated Projects (incubating since 9.7.0, --isolated-projects) forbids a project from touching another project’s mutable state so that projects configure in parallel. Migrate with the Diagnostics mode, convention plugins, gradle.lifecycle.beforeProject and IsolatedProject.
