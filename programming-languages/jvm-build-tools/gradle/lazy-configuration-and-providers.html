Lazy Configuration & Providers

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Gradle 9.8.1 (the current release on 2026-10-16; 8.14.6 is the last 8.x release). Every example was run through the Gradle wrapper on JDK 26, on macOS, in small scratch builds that read the tidepool data/stations.csv, once with the Kotlin DSL and once with the Groovy DSL, and both were run. The daemon used JDK 26; Java toolchains are the subject of a later page. Each example was run with --configuration-cache, and the text says whether it is compatible; the examples that fail on purpose say so. Gradle 8.14 was not available here, so what is said about it comes from the release notes and the user manual and is labelled "not run here". The build output was trimmed only where a line says so, blank lines and the problems-report link were left out, and the scratch directory was replaced by <work>. Gradle does not promise an order for independent tasks, so the order of such lines in the output is not significant.

A Gradle build runs in two phases that matter here: configuration, when the build scripts run and the task graph is built, and execution, when the selected tasks run (see Build Lifecycle). Anything a script computes while it is being configured is computed for every build, including gradle help, and it is computed before later lines of the same script and before other plugins have had their say. Lazy configuration is Gradle’s answer: instead of holding a value, the build model holds an object that knows how to compute the value later. Those objects are Provider<T> and Property<T>, and much of the public Gradle API takes or returns them. This page covers the types, how to chain and wire them, the places they come from, and the mistakes that defeat them. Tasks that declare lazy inputs are written on Writing Custom Tasks; how those inputs make a task skip work is on Incremental Build; creating and ordering tasks lazily is on Tasks; the vocabulary is on Gradle Core Concepts.

Source: Gradle: Understanding lazy properties

Why a value should not be read at configuration time

Here is the problem the API exists to solve. A build script sets a task input from an extension property, and the extension property is assigned later, by the same script or by another plugin. The task below announces a station. Two tasks are registered: one reads the extension property now, with get(), and one passes the property itself:

Kotlin DSL (build.gradle.kts)
interface StationExtension {
    val stationId: Property<String>
}

abstract class Announce : DefaultTask() {
    @get:Input
    abstract val station: Property<String>

    @TaskAction
    fun announce() {
        println("${path}: station = ${station.get()}")
    }
}

val tidepool = extensions.create<StationExtension>("tidepool")
tidepool.stationId.convention("SF")

tasks.create<Announce>("announceEager") {
    station = tidepool.stationId.get()   // create runs this block now: the value is read now
}
tasks.register<Announce>("announceLazy") {
    station = tidepool.stationId         // evaluated when the task runs
}

// Later in the same script, the build author picks the real station.
tidepool.stationId = "BOS"
Groovy DSL (build.gradle)
interface StationExtension {
    Property<String> getStationId()
}

abstract class Announce extends DefaultTask {
    @Input
    abstract Property<String> getStation()

    @TaskAction
    void announce() {
        println "${path}: station = ${station.get()}"
    }
}

def tidepool = extensions.create('tidepool', StationExtension)
tidepool.stationId.convention('SF')

tasks.create('announceEager', Announce) {
    station = tidepool.stationId.get()   // create runs this block now: the value is read now
}
tasks.register('announceLazy', Announce) {
    station = tidepool.stationId         // evaluated when the task runs
}

// Later in the same script, the build author picks the real station.
tidepool.stationId = 'BOS'
./gradlew announceLazy announceEager --configuration-cache
Calculating task graph as no cached configuration is available for tasks: announceLazy announceEager
> Task :announceLazy
:announceLazy: station = BOS
> Task :announceEager
:announceEager: station = SF
BUILD SUCCESSFUL in 677ms
2 actionable tasks: 2 executed
Configuration cache entry stored.

The Groovy DSL build printed the same two station lines and ended with Configuration cache entry stored. The task that was connected to the property saw the final value, BOS. The task that called get() saw SF, the convention that was current when the script reached that line: tasks.create runs its configuration block immediately, so the read happened before tidepool.stationId = "BOS", and nothing can correct it afterwards. Nothing failed and nothing warned, which is what makes this a bug that is found late. Both builds are compatible with the configuration cache and reused the entry on a second run; the incorrectness here is in the value, not in the cache. The Kotlin DSL also printed a compile warning for tasks.create ('fun <reified T : Task> TaskContainer.create(...)' is deprecated. Use register instead), which is the same lesson from another angle and is taken up in Registering tasks lazily.

The official page lists three benefits of lazy properties: the value of the model can be wired before it is known, an output wired to an input carries the task that produces it (so task dependencies are inferred), and expensive work done to compute a value only happens when something needs it. The rest of the page shows each of them.

Source: Gradle: Lazy vs eager evaluation

Property and Provider

Gradle models lazy values with two interfaces:

  • Provider<T> is a read-only value that can be queried. Provider.get() returns the value, and a Provider can be derived from another one with map.

  • Property<T> extends Provider<T> and adds a way to change the value: set(T), set(Provider) and, in the Kotlin DSL and in the Groovy DSL, plain assignment with =. Setting a Property to a Provider is what connects one part of the model to another.

Neither interface is implemented by build code. Gradle creates the instances through factories, so a build script or plugin never writes new Property anywhere:

Need Type Factory

A configurable single value

Property<T>

objects.property(String::class) in the Kotlin DSL, objects.property(String) in the Groovy DSL, or an abstract getter on a task or extension

A read-only computed value

Provider<T>

provider.map { }, provider.flatMap { }, providers.provider { }

A configurable file or directory

RegularFileProperty, DirectoryProperty

objects.fileProperty(), objects.directoryProperty(), or an abstract getter

A read-only file or directory

Provider<RegularFile>, Provider<Directory>

layout.buildDirectory.file("x"), directoryProperty.dir("x")

A configurable list, set or map

ListProperty<T>, SetProperty<T>, MapProperty<K, V>

objects.listProperty(), objects.setProperty(), objects.mapProperty(), or an abstract getter

A set of files

ConfigurableFileCollection, ConfigurableFileTree

objects.fileCollection(), objects.fileTree()

A read-only set of files

FileCollection, FileTree

files(...), fileTree(...), directoryProperty.files(...), directoryProperty.asFileTree

Source: Gradle: Creating a Property or Provider instance

A Provider can also be created from a lambda with providers.provider { }, but the Gradle documentation says to always prefer one of the other factory methods over it. The Javadoc page for Provider documents every method named below.

A property has two kinds of states besides its value: "no value yet" and a convention. A missing value is not an error until somebody asks for it: isPresent() tells, getOrElse(default) and orNull ask without failing, and get() fails with a message that names the source of the value. The next section runs all of them.

Transforming and combining providers

Provider has a handful of operations, all lazy: each returns a new provider and none evaluates its input until the result is queried.

Method Result

map { }

A provider of the transformed value. When the source has no value, the result has no value either and the lambda is not called.

flatMap { }

The lambda returns another provider and the result is flattened. Use it when the transformation itself yields a Provider, such as a task output property.

zip(other) { a, b -> }

Combines two providers. Added in Gradle 6.6; if either side has no value, the result has none and the combiner is not called.

orElse(value) or orElse(provider)

A fallback used when the source has no value. Added in Gradle 5.6.

filter { }

The value only if the predicate holds, otherwise no value. Incubating, since Gradle 8.5.

isPresent, getOrElse(v), orNull, get()

Queries. get() fails when there is no value; use them in a task action, or inside another lambda that is itself lazy.

Sources: Gradle: Chaining providers, Gradle 6.6 release notes and Gradle 5.6 release notes

The example reads a station id from a Gradle property, falls back to SF, reads the tidepool CSV lazily with providers.fileContents, finds the row for the station by zipping the file with the id, and derives the name and a flag from it. The only get() calls are inside the task action:

Kotlin DSL (build.gradle.kts)
// A provider for a Gradle property: absent unless -Pstation=... is given
val requested: Provider<String> = providers.gradleProperty("station")

// orElse supplies a fallback
val stationId: Provider<String> = requested.orElse("SF")

// the CSV file is read lazily; fileContents is configuration-cache friendly
val csv = providers.fileContents(layout.projectDirectory.file("data/stations.csv")).asText

// map transforms the value, zip combines two providers
val row: Provider<String> = csv.zip(stationId) { text, id ->
    text.lines().first { it.startsWith("$id,") }
}
val stationName: Provider<String> = row.map { it.split(",")[1] }
val upper: Provider<String> = stationName.map { it.uppercase() }

// filter drops the value unless the predicate holds: stations west of 100 degrees west
val western: Provider<String> = row
    .filter { it.split(",")[3].toDouble() < -100 }
    .map { it.split(",")[1] }

tasks.register("describe") {
    val requested = requested
    val stationId = stationId
    val upper = upper
    val western = western
    doLast {
        println("requested present? " + requested.isPresent)
        println("requested orNull    = " + requested.orNull)
        println("requested getOrElse = " + requested.getOrElse("(none)"))
        println("station id          = " + stationId.get())
        println("station name        = " + upper.get())
        println("west of 100 W       = " + western.isPresent)
    }
}

tasks.register("missing") {
    val requested = requested
    doLast { println(requested.get()) }
}
Groovy DSL (build.gradle)
// A provider for a Gradle property: absent unless -Pstation=... is given
Provider<String> requested = providers.gradleProperty('station')

// orElse supplies a fallback
Provider<String> stationId = requested.orElse('SF')

// the CSV file is read lazily; fileContents is configuration-cache friendly
def csv = providers.fileContents(layout.projectDirectory.file('data/stations.csv')).asText

// map transforms the value, zip combines two providers
Provider<String> row = csv.zip(stationId) { text, id ->
    text.readLines().find { it.startsWith("${id},") }
}
Provider<String> stationName = row.map { it.split(',')[1] }
Provider<String> upper = stationName.map { it.toUpperCase() }

// filter drops the value unless the predicate holds: stations west of 100 degrees west
Provider<String> western = row
        .filter { it.split(',')[3].toDouble() < -100 }
        .map { it.split(',')[1] }

tasks.register('describe') {
    doLast {
        println 'requested present? ' + requested.isPresent()
        println 'requested orNull    = ' + requested.orNull
        println 'requested getOrElse = ' + requested.getOrElse('(none)')
        println 'station id          = ' + stationId.get()
        println 'station name        = ' + upper.get()
        println 'west of 100 W       = ' + western.isPresent()
    }
}

tasks.register('missing') {
    doLast { println requested.get() }
}

The Kotlin task copies the providers into local val`s before `doLast, so the lambda does not capture the script object (which the configuration cache cannot serialize); the Groovy closure captures the script variables directly and the configuration cache accepted both. Without a property, then with -Pstation=BOS:

./gradlew describe --configuration-cache -q
./gradlew describe -Pstation=BOS --configuration-cache -q
requested present? false
requested orNull    = null
requested getOrElse = (none)
station id          = SF
station name        = SAN FRANCISCO
west of 100 W       = true
requested present? true
requested orNull    = BOS
requested getOrElse = BOS
station id          = BOS
station name        = BOSTON
west of 100 W       = false

The Groovy DSL printed exactly the same lines. San Francisco lies west of 100 degrees west and Boston does not, so filter leaves western without a value for BOS. Both builds stored a configuration cache entry and reused it on a second run. Asking a provider for a value that is not there fails with a message that names the source:

./gradlew missing --configuration-cache -q
FAILURE: Build failed with an exception.
* What went wrong:
Execution failed for task ':missing' (registered in build file 'build.gradle.kts').
> Cannot query the value of Gradle property 'station' because it has no value available.
BUILD FAILED in 729ms

The Groovy DSL run printed the same message, preceded by a Where: line with the build file and the line number, and with build.gradle in place of build.gradle.kts.

The distinction between map and flatMap matters when the lambda’s result is itself a provider. map { it.outputFile } on a Provider<Task> would produce a Provider<RegularFileProperty>, which is not what any input accepts; flatMap { it.outputFile } produces a Provider<RegularFile> and, as the next section shows, keeps the information about which task produced the file. The official best practices list four rules for this: do not call get() inside map or flatMap, do not wrap a task output in a standalone provider { }, expose task outputs as annotated abstract getters, and use map for plain values and flatMap for provider-typed ones.

Source: Gradle: Wire lazy task outputs using map and flatMap

Connecting properties and tasks

A Property can be set to another Provider, and from then on it follows that provider. Connecting an extension property to a task property (as the Why a value should not be read at configuration time example did with announceLazy) means the build author can set the extension at any point and the task sees the final value. The same mechanism connects tasks to each other.

Two tidepool tasks: extractNames reads the stations CSV and writes the station names to a file, and report reads that file. report is wired to the output of extractNames with flatMap, and the build directory is changed at the end of the script to show that no path was copied. A third task, reportEager, reads the same value with get() to show what that costs:

Kotlin DSL (build.gradle.kts)
abstract class ExtractNames : DefaultTask() {
    @get:InputFile
    abstract val csv: RegularFileProperty

    @get:OutputFile
    abstract val names: RegularFileProperty

    @TaskAction
    fun extract() {
        val lines = csv.get().asFile.readLines().drop(1)
        names.get().asFile.writeText(lines.joinToString("\n") { it.split(",")[1] })
    }
}

abstract class Report : DefaultTask() {
    @get:InputFile
    abstract val names: RegularFileProperty

    @TaskAction
    fun report() {
        println("Stations:")
        names.get().asFile.forEachLine { println("  $it") }
    }
}

val extract = tasks.register<ExtractNames>("extractNames") {
    csv = layout.projectDirectory.file("data/stations.csv")
    names = layout.buildDirectory.file("names.txt")
}

tasks.register<Report>("report") {
    // flatMap keeps the link to the producing task: no dependsOn is needed
    names = extract.flatMap { it.names }
}

tasks.register<Report>("reportEager") {
    // get() twice: the task is realized now and the path is frozen now
    names = extract.get().names.get()
}

// The build directory is changed after the wiring was written.
layout.buildDirectory = layout.projectDirectory.dir("out")
Groovy DSL (build.gradle)
abstract class ExtractNames extends DefaultTask {
    @InputFile
    abstract RegularFileProperty getCsv()

    @OutputFile
    abstract RegularFileProperty getNames()

    @TaskAction
    void extract() {
        def lines = csv.get().asFile.readLines().drop(1)
        names.get().asFile.text = lines.collect { it.split(',')[1] }.join('\n')
    }
}

abstract class Report extends DefaultTask {
    @InputFile
    abstract RegularFileProperty getNames()

    @TaskAction
    void report() {
        println 'Stations:'
        names.get().asFile.eachLine { println "  $it" }
    }
}

def extract = tasks.register('extractNames', ExtractNames) {
    csv = layout.projectDirectory.file('data/stations.csv')
    names = layout.buildDirectory.file('names.txt')
}

tasks.register('report', Report) {
    // flatMap keeps the link to the producing task: no dependsOn is needed
    names = extract.flatMap { it.names }
}

tasks.register('reportEager', Report) {
    // get() twice: the task is realized now and the path is frozen now
    names = extract.get().names.get()
}

// The build directory is changed after the wiring was written.
layout.buildDirectory = layout.projectDirectory.dir('out')

The dependency is inferred because extractNames.names is a task output property: it knows which task produces its value, and every provider derived from it with flatMap or map inherits that knowledge. When such a provider is used as a task input, Gradle adds the task dependency itself. The official lazy-configuration page shows the same for non-file inputs, where a String input is derived with producer.flatMap { it.outputFile }.map { it.asFile.readText() }; since Gradle 5.6 the dependency is honored for any @Input property of type Provider.

reportEager is the opposite. extract.get() forces the extractNames task to be realized while the script is running, and .names.get() turns the property into a plain RegularFile that no longer carries the producing task. Files and directories

Files and directories have their own property types, because a File says nothing about whether it is a file or a directory and carries no task dependency: RegularFileProperty and DirectoryProperty, with the read-only RegularFile and Directory as their values. Their values are relative to something, and that something is a provider too, so the location follows the build directory when the build directory is changed (as the build in "Connecting properties and tasks" did with layout.buildDirectory =):

  • layout.projectDirectory and layout.buildDirectory (a DirectoryProperty) are the two roots. layout.buildDirectory.file("names.txt") is a Provider<RegularFile>, and .dir("x") a Provider<Directory>; both follow later changes.

  • DirectoryProperty.file(path) and .dir(path) give lazily resolved children; .files(...) gives a FileCollection; .asFileTree gives a FileTree of the directory’s contents.

  • A FileTree has no stable order, so it should not be used where order matters.

  • providers.fileContents(file) reads a file lazily, as text or bytes, and the configuration cache tracks it as an input (it was used in the previous section). Reading the same file with readText() while the script is configured is an eager read.

Copying, archiving and the file-tree types in detail are on Working with Files.

Source: Gradle: Working with files

Collections and maps

Collection-valued properties have their own types, so that several contributors can add to the same value without knowing about each other. ListProperty<T> and SetProperty<T> offer add(element), add(provider), addAll(...) and set(...); MapProperty<K, V> offers put(key, value), put(key, provider), putAll(map) and set(...). Each addition is lazy, and the collection is computed when it is queried. The example adds a literal element, a lazily computed list, an element that may be absent, a duplicated set element, and map entries whose value is only known later:

Kotlin DSL (build.gradle.kts)
abstract class Summary : DefaultTask() {
    @get:Input
    abstract val ids: ListProperty<String>

    @get:Input
    abstract val tags: SetProperty<String>

    @get:Input
    abstract val limits: MapProperty<String, Double>

    @TaskAction
    fun summarize() {
        println("ids    = ${ids.get()}")
        println("tags   = ${tags.get()}")
        println("limits = ${limits.get()}")
    }
}

var maxHeight = 0.0   // not known yet when the task is configured

tasks.register<Summary>("summary") {
    ids.add("SF")                                          // one element
    ids.addAll(providers.provider { listOf("BOS", "HNL") }) // a lazily computed list
    ids.add(providers.gradleProperty("extraStation"))      // an element that may be absent

    tags.addAll("harmonic", "tidal", "harmonic")           // a set drops the duplicate

    limits.put("min", 0.0)
    limits.put("max", providers.provider { maxHeight })    // evaluated when the task runs
    limits.putAll(mapOf("alarm" to 4.5))
}

maxHeight = 5.25
Groovy DSL (build.gradle)
abstract class Summary extends DefaultTask {
    @Input
    abstract ListProperty<String> getIds()

    @Input
    abstract SetProperty<String> getTags()

    @Input
    abstract MapProperty<String, Double> getLimits()

    @TaskAction
    void summarize() {
        println "ids    = ${ids.get()}"
        println "tags   = ${tags.get()}"
        println "limits = ${limits.get()}"
    }
}

double maxHeight = 0.0   // not known yet when the task is configured

tasks.register('summary', Summary) {
    ids.add('SF')                                            // one element
    ids.addAll(providers.provider { ['BOS', 'HNL'] })        // a lazily computed list
    ids.add(providers.gradleProperty('extraStation'))        // an element that may be absent

    tags.addAll('harmonic', 'tidal', 'harmonic')             // a set drops the duplicate

    limits.put('min', 0.0d)
    limits.put('max', providers.provider { maxHeight })      // evaluated when the task runs

}

Conventions and finalizing

A convention is a default that is used while no explicit value has been set. A plugin applies it, a build script overrides it with set, and unset() returns to it. Setting a convention never overrides an explicit value, so a plugin does not have to run first or last. A property can also take its convention at its declaration; the Tides task in the example does that in its constructor. The task below shows each step and then freezes the value with finalizeValue():

Kotlin DSL (build.gradle.kts)
abstract class Tides : DefaultTask() {
    @get:Input
    abstract val interval: Property<Int>        // minutes between predictions

    @get:Input
    abstract val unit: Property<String>

    // a convention declared next to the property
    init {
        unit.convention("m")
    }

    @TaskAction
    fun run() {
        println("interval = ${interval.get()} ${unit.get()}")
    }
}

val tides = tasks.register<Tides>("tides") {
    interval.convention(60)          // default from a plugin or the build
}

tides {
    println("1. before any set: ${interval.get()}")
    interval.set(30)                 // explicit value wins over the convention
    println("2. after set(30): ${interval.get()}")
    interval.unset()                 // back to the convention
    println("3. after unset(): ${interval.get()}")
    interval.set(10)
    interval.finalizeValue()         // freeze the value now
    println("4. finalized: ${interval.get()}")
    try {
        interval.set(5)
    } catch (e: IllegalStateException) {
        println("5. ${e.message}")
    }
}

tasks.register<Tides>("late") {
    interval = 15
    doFirst {
        interval = 1     // too late: Gradle finalizes task properties when the task starts
    }
}

Both are compatible with the configuration cache. The methods come from HasConfigurableValue and Property:

Method Effect

convention(value) or convention(provider)

The value used until one is set. Calling it again replaces the convention; unsetConvention() removes it.

set(value) or set(provider), value(...)

Sets an explicit value, replacing whatever was there. value(...) is the same as set but returns the property, and passing null to it discards the value.

unset()

Discards the explicit value, so the convention applies again.

finalizeValue()

Computes the final value now, replacing a provider with its result, and disallows further changes.

finalizeValueOnRead()

The same, but the value is computed on the first read. It suits values that are expensive or may not be configured yet and that every reader must see identically.

disallowChanges()

Disallows direct changes without computing the value, so the source of the value is still used until the value is finalized. Since Gradle 5.6.

disallowUnsafeRead()

Reading the value during project configuration fails, so every plugin has a chance to configure it; the property is also finalized on read. Since Gradle 6.4.

ObjectFactory, managed properties and managed types

ObjectFactory (in a script: objects) creates the objects a model is made of: property, listProperty, setProperty, mapProperty, fileProperty, directoryProperty, fileCollection, fileTree, domainObjectContainer and newInstance, which creates a class with its constructor arguments and services injected. It is the way a plugin creates a lazy model without implementing any of the property interfaces.

For most types there is a shorter way. Declare an abstract getter (or an abstract val in Kotlin) of a lazy type, and Gradle generates the implementation and manages the state. The conditions are the ones of a JavaBeans property: the getter is named getFoo, it has no setter and it is public or protected. A type whose properties are all managed is a managed type; it can be a class or an interface, it has no fields, and Gradle supplies the implementation. A nested managed type, used by a task or an extension as a property, is declared with an abstract getter annotated @Nested. If the type contains an abstract String property called name, Gradle fills it in and adds a name parameter to each constructor, which is what makes Named types the elements of a NamedDomainObjectContainer.

The next build uses all of that: a nested Constituent type, a named Station type in a container, an extension created with extensions.create (whose constructor gets an ObjectFactory), and a task that has a nested property, a property that receives the container’s names, and an injected ObjectFactory used to create a throw-away instance in the action:

Kotlin DSL (build.gradle.kts)
import javax.inject.Inject

// A managed nested type: Gradle supplies the implementation
interface Constituent {
    @get:Input
    val speed: Property<Double>

    @get:Input
    val amplitude: Property<Double>
}

// A named managed type for use in a container
interface Station : Named {
    val latitude: Property<Double>
}

// An extension: its properties are all managed
abstract class TidepoolExtension @Inject constructor(objects: ObjectFactory) {
    abstract val title: Property<String>
    abstract val outputDir: DirectoryProperty
    @get:Nested
    abstract val primary: Constituent                       // nested, read-only property, created by Gradle
    val stations: NamedDomainObjectContainer<Station> =
        objects.domainObjectContainer(Station::class.java)
    fun primary(action: Action<in Constituent>) = action.execute(primary)
}

abstract class Describe : DefaultTask() {
    // property injection: Gradle supplies the service
    @get:Inject
    abstract val objects: ObjectFactory

    @get:Input
    abstract val title: Property<String>

    @get:Nested
    abstract val primary: Constituent

    @get:Input
    abstract val stationNames: SetProperty<String>

    @TaskAction
    fun run() {
        val extra = objects.newInstance<Constituent>()      // a throw-away managed instance
        extra.speed.set(primary.speed.get() * 2)
        println("${title.get()}: M2 speed ${primary.speed.get()}, doubled ${extra.speed.get()}")
        println("stations: ${stationNames.get()}")
    }
}

Service injection

Gradle exposes services (file operations, process execution, worker scheduling, ObjectFactory, ProjectLayout, ProviderFactory, BuildFeatures and more) that custom types request instead of constructing, because the instances depend on internal state. A type declares the dependency and Gradle supplies it, for anything Gradle instantiates: tasks, plugins, extensions, build services, value sources and worker actions. There are two forms:

  • constructor injection, with @Inject on the constructor of an abstract class, which is the usual form for tasks and plugins;

  • property injection, with @Inject on an abstract getter (the objects property of Describe in the previous example), which also works for interfaces.

The Locate task asks for a ProviderFactory and a ProjectLayout in its constructor, and uses them in its action. No Project is needed at execution time, which is what the configuration cache requires:

Kotlin DSL (build.gradle.kts)
import javax.inject.Inject

abstract class Locate @Inject constructor(
    private val providers: ProviderFactory,
    private val layout: ProjectLayout
) : DefaultTask() {

    @TaskAction
    fun locate() {
        val station = providers.gradleProperty("station").getOrElse("SF")
        val build = layout.buildDirectory.get().asFile.relativeTo(layout.projectDirectory.asFile)
        println("station $station, output in ./$build")
    }
}

tasks.register<Locate>("locate")

Registering tasks lazily

Properties are lazy values; the task containers have lazy counterparts too. Task configuration avoidance means that a task is only created and configured if the build needs it. The eager forms do the work for every task in every build. The old and new APIs, from the official overview:

Eager API to avoid Lazy API Difference

task myTask(type: MyTask) { } (Groovy shorthand) and tasks.create("x") { }

tasks.register("x") { }

register stores a recipe and returns a TaskProvider; the block runs only if the task is needed.

tasks.getByName("x") { }

tasks.named("x") { }

named returns a TaskProvider and configures the task only if it is created anyway.

tasks.withType(T) { }

tasks.withType(T).configureEach { }

Adding a closure to withType makes it eager: every task of the type is created at once. configureEach applies the action to each task as it is created.

tasks.whenTaskAdded { }

tasks.configureEach { }

configureEach returns void, so it cannot be chained.

Source: Gradle: Old vs new configuration API overview

The classic bug: Provider.get() outside a task action

Every section above ends on the same rule, and the official best practices state it as one: do not call get() on a provider outside a task action. When configuring tasks and extensions, use map or flatMap instead. Calling get() while a script is being configured has three consequences, taken from the page:

  • the value becomes an input of configuration, so a change can cost a configuration cache miss;

  • the value may be read too early, before another plugin or the script itself has set the final value (the first example on this page);

  • the dependency information is lost, so Gradle cannot infer task dependencies or track inputs and outputs (the reportEager example).

The same rule has companions: do not use layout.buildDirectory.get().asFile where layout.buildDirectory.file("x") fits; do not resolve a Configuration before execution; do not keep the result of a provider in a script variable that a task action reads; and do not access project at execution time. A quick audit of a build: search the scripts and plugins for .get() and .getOrElse outside doLast, doFirst, @TaskAction and lambdas passed to map, flatMap and zip.

The Kotlin side adds a type-level rule: since Gradle 9.0, the API carries JSpecify nullability annotations, so Property<String?> no longer compiles and a Kotlin extension on Provider<T> has to declare T : Any. Use a property with no value in place of a nullable value.

Sources: Gradle: Do not call get() on a Provider outside a Task action and Gradle: Gradle API now uses JSpecify nullability annotations

Guidelines for plugin and task authors

The user manual gives these rules for exposing lazy properties in types that other people use:

  • For a configurable value, expose the Property directly through a single getter. For a computed value, expose a Provider directly through a single getter.

  • Do not add extra getters and setters that wrap obj.getProperty().get() and obj.getProperty().set(T); they read the value immediately and prevent wiring.

  • When migrating a plugin, expose a new property as a Property or Provider; for an existing stable property, add the new one and deprecate the old, wiring the old getter and setter into the new property.

  • Use the dedicated collection and file types, not a Property of a collection, a File or a String path.

  • Prefer to set conventions in the plugin and let the build script override them.

Source: Gradle: Using the Provider API

Gradle 8.14 and older builds

Everything on this page works on 8.14 with the exceptions below, from the release notes and the upgrade guides (not run here, because Gradle 8.14 was not available):

  • Provider.zip, orElse, MapProperty, convention() and the collection types exist long before 8.14. providers.exec has been available since 7.5, and Provider.filter since 8.5, still incubating.

  • The = assignment of lazy properties in the Kotlin DSL works since 8.2; older scripts write prop.set(value), which works in both lines.

  • The deprecations described above (ExecOperations at configuration time, an injected Project in a task action) are announced in the 9.x line, as the upgrade guide says, and are not in 8.14.

  • The strict nullability of Property<T> in the Kotlin DSL is new in 9.0, with the JSpecify annotations.

  • The configuration cache is stable since 8.1 and the preferred mode in 9.0, but it still has to be enabled in both lines; it is announced as the default of Gradle 10.

Summary

  • Model values as Property (configurable) and Provider (read-only); a Property can be set to a Provider, which is how the model is wired before its values are known.

  • Chain with map, flatMap, zip, orElse and filter, and call get() only in a task action or inside a lambda that is itself lazy.

  • Connect task outputs to inputs with flatMap; the task dependency is then inferred. An early get() loses it.

  • Use ListProperty, SetProperty, MapProperty, RegularFileProperty and DirectoryProperty; an absent element makes a collection absent, and Property<List<T>> is rejected.

  • Use conventions for defaults, set to override, finalizeValue() to freeze; Gradle finalizes a task’s properties when it starts.

  • Read the outside world with providers (gradleProperty, environmentVariable, systemProperty, fileContents, exec) rather than directly, which is eager.

  • Declare properties as abstract getters (@Nested for nested managed types, @Input and friends for task inputs) and inject services with @Inject.

  • Register tasks with register, find them with named, and configure them with withType<T>().configureEach; one eager call can undo the laziness of a whole type.
