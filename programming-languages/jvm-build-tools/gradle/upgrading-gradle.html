Upgrading Gradle

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Gradle 9.8.1 (released on 7 October 2026) and the upgrade guides of the user manual as of 16 October 2026. Gradle 8.14.6 (released on 8 October 2026) is the last 8.x release and is the starting point of the main upgrade described here. Every example marked as run was executed with the 9.8.1 wrapper on macOS (Apple silicon), in scratch copies of the tidepool build, once with *.gradle.kts files and once with *.gradle files wherever the syntax differs. The Gradle daemon ran on Oracle JDK 26 (java version "26"), the default JDK of the machine, except where the text says that JetBrains Runtime 17.0.14 was used. A gradle.properties file in each scratch build set org.gradle.jvmargs=-Xmx512m -Duser.language=en -Duser.country=US, so that the messages are in English, and org.gradle.java.installations.auto-download=false, so that no JDK could be downloaded. The scratch directory is shown as <work>; the at ... stack frame and (Run with --stacktrace ...) lines that follow each deprecation warning, the lines announcing the start of a daemon, and the long Welcome to Gradle text of the help task are left out of the listings. The examples are compatible with the configuration cache and ran with --configuration-cache except where the text says otherwise: a configuration cache hit does not repeat the warnings that are printed while the build is configured, so every run that looks for deprecations ran with --no-configuration-cache.

Gradle 8.14.x was not available here, and no Gradle distribution was downloaded. Everything said about 8.14, and every difference between 8.14 and 9.x that was not observable on 9.8.1, comes from the official upgrade guides and release notes and is labelled "not run here". Three more things were not run: --scan (publishing a Build Scan to a Develocity service requires accepting its terms of use), running Gradle 9 on a Java older than 17 (no such Java is installed) and any wrapper run that would download a distribution from services.gradle.org. The wrapper properties shown on this page are the official ones, with the services.gradle.org URL; the scratch builds pointed the same wrapper at a local copy of the 9.8.1 archive.

An upgrade of a Gradle build is not one step. A Gradle release changes three things at once: the engine that runs your build (the JVM it needs, the Kotlin and Groovy that compile your scripts, the defaults of the bundled plugins), the API that your scripts and plugins call (deprecated in one release and removed in a later one), and the behavior of tasks that you did not change. The user manual answers with one upgrade guide per major line and a fixed procedure, and this page walks through the procedure, then through each guide that matters for a build that is on 8.14 today, then through the older majors, because the build files that Gradle users still find in books, blog posts and old repositories (including the examples of Gradle in Action, which targets Gradle 1.7) stop working on 9.8.1 in specific, recognizable ways. The release history behind all of this is on Gradle Versions, Compatibility & Release History; this page is where each removal is explained and fixed. The wrapper task itself is described on Gradle Wrapper, the option --warning-mode on Gradle Command Line, the configuration cache on Configuration Cache & Isolated Projects, and the other two tools' equivalents are in the last section: Maven’s are on Migrating to Maven 4 and Maven Wrapper, Ant’s on Ant: Deprecations & Migration.

How Gradle versions and deprecations work

Since Gradle 9.0.0 the version number follows semantic versioning: MAJOR.MINOR.PATCH, where a major release may remove public APIs, a minor release adds features and deprecates others, and a patch release fixes bugs and vulnerabilities (9.8.1 is a patch release of 9.8.0 that closes three high-severity vulnerabilities in the communication between client, daemon and workers, and in the handling of repositories that fail to establish an SSL connection). Before 9.0 the versions were MAJOR.MINOR (8.14) with the patch number appearing only when needed (8.14.6), and a "minor" release such as 7.3 or 8.2 could already contain large features.

The feature lifecycle turns the numbering into a promise. A documented feature is public, and is not removed or changed incompatibly without first being deprecated; a deprecated feature keeps working, prints a warning when it is used, and "may be removed in the next major release"; the manual adds that deprecated features may be supported across major releases but that this is not guaranteed. The deprecation messages of Gradle 9.8.1 state a target release in each message: "This will fail with an error in Gradle 10" for most, "scheduled to be removed in Gradle 11" for a few that were deprecated recently. The incubating state is the exception to the promise: an incubating API may change in any release and the changes are listed in the release notes. The full lifecycle is explained on the versions page.

The consequence for upgrading is simple. A build that is free of deprecation warnings on the last minor release of a line (8.14.x) will, with very few exceptions, compile and run on the first release of the next line (9.0.0), and a build that is free of warnings on a 9.x release will run on every later 9.x release. Almost all upgrade pain comes from skipping that discipline: from moving more than one major release at once, from ignoring the warning summary, or from plugins that use internal APIs.

The upgrade guides of the user manual have a naming scheme that is easy to misread. Each file upgrading_version_N.html covers the minor releases of line N and the move from the last N.x to the first release of the next line; the move to Gradle 9.0.0 has a page of its own. The upgrade procedure

The user manual gives the same four steps at the top of every upgrade guide, from the 4.x guide to the 9.x one, and they are the whole method. In the guide for moving to Gradle 9.0.0 they read:

  1. Run gradle help --scan and look at the Deprecations view of the Build Scan; alternatively run gradle help --warning-mode=all to see the deprecations in the console, "though it may not report as much detailed information".

  2. Update your plugins, "because a major release can remove public APIs" and the newest version of a plugin is the most likely to be compatible.

  3. Run gradle :wrapper --gradle-version 9.0.0 (or the version you are moving to).

  4. Run the project and debug any errors with the troubleshooting guide.

The guide for moving to 9.0.0 adds a precondition before the first step (for migrating within Gradle 8.x, read the older migration guide first), and the guide for the 9.x releases says the same about the 9.0.0 guide. The 4.x guide adds two more pieces of advice that remain good: move to the latest release of your current line before moving to the next major one, because "Gradle 5.x will generate (potentially less obvious) errors if you try to upgrade directly to it", and do not upgrade Gradle and migrate to the Kotlin DSL at the same time, so that a failure has one cause. The flow, with the commands, is:

Step 1: find the deprecations

By default Gradle prints the deprecation warnings of a build only as a one-sentence summary at the end of the build. That is useful as a signal, and useless as a list. This is the summary on 9.8.1 for a build that uses a deprecated Groovy DSL idiom (group 'io.tidepool', the "space assignment" syntax) and Project.getProperties(); the build succeeds:

$ ./gradlew :child:help --warning-mode=summary --no-configuration-cache --console=plain
> Configure project :child
hello

> Task :child:help

Deprecated Gradle features were used in this build, making it incompatible with Gradle 10.

You can use '--warning-mode all' to show the individual deprecation warnings and determine if they come from your own scripts or plugins.

For more on this, please refer to https://docs.gradle.org/9.8.1/userguide/command_line_interface.html#sec:command_line_warnings in the Gradle documentation.

BUILD SUCCESSFUL in 1s
1 actionable task: 1 executed

--warning-mode selects what is printed: summary (the default, shown above), all (every warning, with the build file and line), fail (every warning, and the build fails if there was any) and none. The same choice can be made persistent with the Gradle property org.gradle.warning.mode, in gradle.properties or with -D on the command line, and the command line wins over the file. With fail the same build prints each warning, and ends with a failure that names the first offending line of the build file:

$ ./gradlew :child:help --warning-mode=fail --no-configuration-cache --console=plain
> Configure project :child

Properties should be assigned using the 'propName = value' syntax. Setting a property via the Gradle-generated 'propName value' or 'propName(value)' syntax in Groovy DSL has been deprecated. This is scheduled to be removed in Gradle 10. Use assignment ('group = <value>') instead. Consult the upgrading guide for further information: https://docs.gradle.org/9.8.1/userguide/upgrading_version_8.html#groovy_space_assignment_syntax
Build file '<work>/child/build.gradle': line 3
The Project.getProperties method has been deprecated. This will fail with an error in Gradle 10. Consult the upgrading guide for further information: https://docs.gradle.org/9.8.1/userguide/upgrading_version_9.html#deprecated_get_properties
hello

> Task :child:help

[Incubating] Problems report is available at: file://<work>/build/reports/problems/problems-report.html

FAILURE: Build failed with an exception.

Build file '<work>/child/build.gradle' line: 2

* What went wrong:

Each warning has the same anatomy, which is worth knowing because the target of the link is the upgrade guide. First the sentence of what was used; then when it stops working ("This will fail with an error in Gradle 10", or "scheduled to be removed in Gradle 11"); then the replacement; and last the link to the section of the guide that explains the change, upgrading_version_9.html#deprecated_get_properties in the second warning above, followed by the place in the build ("Build file …​: line 3", or the at line that was left out of the listing). In a Kotlin DSL build the Kotlin compiler adds its own w: lines for the deprecated declarations before Gradle’s message, as the by registering delegates below show. The at line says which script or class made the call, and --stacktrace prints the whole stack of a warning, which is how a deprecation that is triggered by a plugin is traced to the plugin.

The run also wrote a report, and the output announced it (the line starting with [Incubating] Problems report, which the other listings of this page leave out): build/reports/problems/problems-report.html lists the deprecations and other problems of the build as an HTML page that can be opened without a Build Scan. The report is incubating in 9.8.1.

The second way is the Build Scan: gradle help --scan collects the same deprecations in a Deprecations view that groups them by the plugin or script that caused them, with the stack trace and the link to the upgrade guide, which is why the guides recommend it first. Publishing a scan sends build data to a Develocity service and requires accepting its terms of use, so --scan was not run here; the scan options are described on Performance Profiling & Build Scans.

Three rules make the output reliable. Run with --no-configuration-cache, or after changing a file of the build, because a configuration cache hit skips the configuration phase where most of the warnings are produced. Run the tasks that your CI runs, not only help, because a deprecation that is triggered by a task action (reading Task.project, for example) is printed only when the task executes. Run the build of every included build and of buildSrc or build-logic too: they are separate builds and their warnings are reported with the others.

A plugin author who needs to support Gradle older than 8.11 must build the plugin with Gradle 8.x, because the Kotlin 2.2 compiler of Gradle 9 rejects language versions below 1.8 and always writes Kotlin metadata version 2; the guide shows the languageVersion and apiVersion setting for an 8.x build and says it fails on Gradle 9. Third-party plugins that fail with a NoSuchMethodError, NoClassDefFoundError or "Could not find method" during configuration are the typical symptom of a plugin that uses an API Gradle removed; the fix is the plugin’s own newest release, and if there is none, replacing the plugin.

Step 3: update the wrapper

The wrapper is how the version of Gradle becomes part of the repository (see Gradle Wrapper for every key of gradle-wrapper.properties), so upgrading is running the wrapper task with the new version and committing the result. The manual recommends the task over editing distributionUrl, because the task also refreshes the scripts and the JAR. The guides give the command as gradle :wrapper --gradle-version 9.0.0, and the wrapper chapter gives the pair that is needed to update the JAR as well:

./gradlew wrapper --gradle-version 9.8.1 --gradle-distribution-sha256-sum <sha-256 of the -bin.zip> && ./gradlew wrapper

The first call runs with the old Gradle and rewrites gradle-wrapper.properties; the second runs with the new Gradle, which downloads it and writes the new gradle-wrapper.jar and scripts. When the properties file contains a distributionSha256Sum (a project that verifies its distribution has one) the task refuses to leave a stale checksum behind, so the new sum has to be passed with --gradle-distribution-sha256-sum; the checksums of all releases are on gradle.org/release-checksums. Moving from 8.14.6 to 9.0.0 is the same command with 9.0.0, and it was not run here, because it would download the distribution of 9.0.0 on the second call.

Behavior changes that do not fail

The dangerous changes of a major release are the ones that keep the build green. The 9.0.0 guide has several; each of the next three was reproduced.

Archives are reproducible by default. The tasks Jar, War, Ear, Zip and every AbstractArchiveTask now sort entries deterministically, give every file a fixed timestamp (1 February 1980 for ZIP-based archives; the exact value depends on the archive type) and permissions 0644, and every directory 0755. Before 9.0 the order depended on the file system and the times and permissions were those of the files. The change helps builds that hash their outputs or compare them between machines (see Supply-Chain Security and, for Maven’s project.build.outputTimestamp, Maven Security & Reproducible Builds), and surprises builds that read the time or the permissions back, such as a distribution whose scripts must be executable. Restoring the old behavior is per property, or for permissions with the Gradle property org.gradle.archives.use-file-system-permissions=true. The other changes of this kind, in the order of the guide:

  • assemble stops building artifacts of arbitrary configurations. The assemble task used to build the artifacts of every configuration whose visible flag was not false, and the archives configuration collected them. Both were removed in 9.0; a custom artifact now needs tasks.named("assemble") { dependsOn(theArtifactTask) }. The archives configuration (deprecated for artifact declaration in 9.1) and Configuration.visible (deprecated, to be removed in Gradle 11) remain only as deprecated shells.

  • Packaging plugins combine. The ear and war plugins no longer suppress each other and the jar: applying java, war and ear builds a JAR, a WAR and an EAR with assemble.

  • Stale class files outside the build directory are no longer deleted, a special case of source set outputs that forced every compile task to be created eagerly.

  • The signing plugin writes OpenPGP signatures that match the version of the key (RFC 9580, version 6 keys); before 9.0 it always wrote version 4 signatures.

  • Gradle Module Metadata that is modified after an eagerly created publication is an error instead of a warning.

  • ValidatePlugins needs the toolchain plugin (jvm-toolchains, applied by every JVM plugin) and, since 9.2, a Java version that the daemon supports.

  • The default versions of the bundled tools moved: Checkstyle 10.24.0, CodeNarc 3.6.0, PMD 7.13.0, JUnit Jupiter 5.12.2, TestNG 7.11.0, Spock 2.3 and Eclipse JGit 7.2.1. A new Checkstyle or PMD version brings new rules, so a quality gate that was green can turn red without a source change; pin the tool version (toolVersion) while upgrading and move it afterwards as a separate step.

The older majors: 4 to 8

An old build rarely sits on 8.14. Builds copied from books and blog posts sit on 1.x to 4.x, and the practical question is what a 4.x build needs. The upgrade guides were written one hop at a time, and the supported way to move is to follow them one hop at a time: first to the last release of the old line, then to the next major, using the deprecation warnings of the old line to find the changes. The table lists, for each hop, the changes that a build file written in the style of the Gradle 1.x and 2.x era notices first (the guides list many more).

Hop Changes that break typical build files

4.10 to 5.0 (2018-11-26)

Gradle 5 needs Java 8 to run (4.x needs Java 7). task name << { } no longer works; use doLast. The publishing { } block is no longer evaluated lazily. Dependencies declared by a POM are separated into compile and runtime scopes. Implicit wildcards in POM exclusions are honored. Annotation processors are added through the annotationProcessor configuration. Memory defaults of the client, daemon and workers were greatly reduced. enableFeaturePreview('IMPROVED_POM_SUPPORT') and 'STABLE_PUBLISHING' are no longer needed (they became the default). The release added the Kotlin DSL 1.0, native BOM import (platform()), the Worker API and tasks.register.

5.6 to 6.0 (2019-11-08)

The FindBugs, JDepend, OSGi, announce and build-announcements, and Compare Gradle Builds plugins are removed. Dependencies should no longer be declared using the compile and runtime configurations (deprecated). The legacy publication system (the maven plugin and uploadArchives) is deprecated in favor of maven-publish and ivy-publish. Gradle Module Metadata is always published, with stricter validation. Maven or Ivy repositories are no longer queried for artifacts without metadata by default. buildSrc is reserved as a project name. Executing Gradle without a settings file and calling afterEvaluate on an evaluated project are deprecated (errors in 7.0).

6.9 to 7.0 (2021-04-09)

The compile, runtime, testCompile and testRuntime configurations are removed (use implementation, api, runtimeOnly, testImplementation, testRuntimeOnly; a Groovy extendsFrom runtime silently creates a configuration named runtime instead of failing). The maven plugin and uploadArchives are removed. jcenter() is deprecated. The experimental JavaScript plugins (coffeescript-base, envjs, javascript-base, jshint, rhino), the Play plugins and the unmaintained JVM plugins are removed. Groovy 3. Executing a build without a settings file, and calling afterEvaluate on an evaluated project, are errors. Dependency locking defaults to a single file per project.

7.6 to 8.0 (2023-02-13)

Warnings that became errors: referencing tasks of an included build with finalizedBy, mustRunAfter or shouldRunAfter; invalid Java toolchain specifications; automatic toolchain download without a repository; changing the test framework after setting its options. Removed legacy APIs: the old ArtifactTransform, IncrementalTaskInputs, JacocoMerge, and many API clean-ups. Plugin, task and extension classes are abstract; the lowest supported Kotlin and Android plugins were raised. Kotlin 1.8.

8.14 to 9.0.0

Gradle, Maven and Ant

The three tools differ in what "version of the tool" means, and so in what an upgrade is.

Ant Maven Gradle

Pin the tool version in the repository

No wrapper; the Ant on the path is used. Ant 1.10 needs Java 8 or later, and Ant 1.9, which ran on Java 5, has been end of life since 19 June 2024 (Ant: Deprecations & Migration).

The Maven Wrapper: mvn wrapper:wrapper -Dmaven=<version> rewrites .mvn/wrapper/maven-wrapper.properties (Maven Wrapper).

The wrapper task: ./gradlew wrapper --gradle-version <version>, with --gradle-distribution-sha256-sum when the properties file has a checksum.

Checklist for an upgrade

  1. Commit a green build. Note the Gradle version (./gradlew --version), the Java of the daemon and the plugin versions (./gradlew buildEnvironment).

  2. Move to the last release of the current line (for 8.x, 8.14.6) and read its section in the upgrade guide.

  3. Run ./gradlew <the tasks CI runs> --warning-mode=all --no-configuration-cache, and help --scan when the scan is allowed. Fix every warning, starting with the ones that your own scripts cause; update the plugins that cause the others.

  4. Run again with --warning-mode=fail until it passes. Run with --configuration-cache and fix the problems it reports.

  5. Make sure the daemon will have a Java the target Gradle supports (17 or newer for 9.x), and that toolchains say which Java compiles, tests and runs the code.

  6. Move the wrapper: ./gradlew wrapper --gradle-version <target> --gradle-distribution-sha256-sum <sum>, then ./gradlew wrapper again; check the gradle-wrapper.properties diff and commit the four wrapper files.

  7. Run the build and the tests. Compare the produced archives if you depend on their bytes, and check that every test task still runs tests.

  8. Pin the versions of the quality tools (Checkstyle, PMD, JaCoCo) until the upgrade has settled.

  9. Set org.gradle.warning.mode=fail (or -Dorg.gradle.warning.mode=fail) on CI so that the next deprecation is a failing build before it becomes an error.

  10. Do not migrate to the Kotlin DSL, a version catalog or a new plugin in the same change.
