Gradle Testing JVM Projects

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Gradle 9.8.1 (the current release on 2026-10-16). Every example was run through the Gradle wrapper on macOS with JDK 26 (Oracle java version "26"), which is the JVM that runs the daemon and that compiles the code, apart from the one example that moves the tests to another JDK. The Kotlin DSL is shown first and the Groovy DSL second wherever the syntax differs, and the tidepool build was run in both DSLs with the same commands; the console output is the same apart from timings and from the order in which independent tasks are reported. Every example ran with the configuration cache on (org.gradle.configuration-cache=true in gradle.properties) and reported no configuration cache problems, so all of them are compatible with it (a run with --warning-mode all printed no deprecation warning for the build of this page). Testing is where the three build tools differ least in what they do and most in how they are told to do it. All of them compile the test sources against the production classes, start a JVM, hand the test classes to a framework and turn the result into a report that CI servers can read. Ant has no idea what a test is until you call the <junit> or <junitlauncher> task (see Testing with JUnit & junitlauncher); Maven binds the Surefire plugin to the test phase and the Failsafe plugin to integration-test (see Maven Testing with Surefire and Maven Integration Testing with Failsafe). Gradle has a task type, Test, that every JVM plugin instantiates for you, plus a declarative layer on top of it, the JVM Test Suite plugin, that is the recommended way to describe more than one kind of test. This page is about both layers, about the test frameworks Gradle can drive, about the reports it writes and about the plugins that measure and police tests: JaCoCo for coverage, Checkstyle and PMD for static checks. The Java plugins whose source sets the tests live in are on Gradle Java Projects; choosing the JDK that runs the tests is on Gradle Toolchains; testing a Gradle plugin with TestKit is on Testing & Publishing Plugins. For the language-level view of testing see Java Testing, Kotlin Testing and Groovy Testing with Spock & Geb.

The pieces: source set, Test task, test suite

Three objects take part in every test run, and most of the confusion about Gradle testing comes from not keeping them apart.

Object What it is Where it comes from

Source set test

A directory tree (src/test/java, src/test/resources) and the compile task, classes directory and configurations (testImplementation, testRuntimeOnly, testCompileClasspath, testRuntimeClasspath) derived from its name.

The java plugin creates it. Its classpath contains the production classes, which is why tests can call main code without declaring a dependency.

Test task test

A task that starts a separate JVM (the test worker), loads the test classes in it, runs them with a test framework and writes the results. Its inputs are the test classes, the runtime classpath and its own settings; its outputs are the XML results and the HTML report.

Registered for each suite, so test for the default suite, integrationTest for a suite of that name, and so on.

Test suite test (type JvmTestSuite)

A named bundle of sources, dependencies, testing framework and one or more targets, each backed by a Test task.

The JVM Test Suite plugin, applied by the java plugin. It is the declarative front end of the two objects above.

Before 7.3 (2021) only the first two existed, and a second kind of tests meant a hand-made source set, configurations and a Test task, as shown on Gradle Java Projects. The JVM Test Suite plugin was introduced in Gradle 7.3 as an incubating feature and does the same in a few declarative lines. The java-test-fixtures plugin (Gradle 5.6) shares test helpers between projects, JUnit 5 support arrived in Gradle 4.6, and the sections below add what came later: richer HTML reports (9.3), non-class-based tests (9.4) and the changes of Gradle 9.0 that made the conventions of Test tasks explicit.

Source: Gradle User Manual: Testing in Java & JVM projects, JVM Test Suite plugin: terminology, Gradle 7.3 release notes, Gradle 5.6 release notes, Gradle 4.6 release notes

The tests themselves are plain JUnit Jupiter. The engine’s unit tests, in tidepool-engine/src/test/java/io/tidepool/engine/TideEngineTest.java, use a parameterized test and the Stations fixture of the model project:

package io.tidepool.engine;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

import io.tidepool.model.Stations;
import java.time.Instant;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;

class TideEngineTest {
    @Test
    void flatWaterStaysFlat() {
        assertEquals(0.0, TideEngine.predict(Stations.flatWater(), Instant.EPOCH).metres());
    }

    @Test
    void pureM2StartsAtItsAmplitude() {
        assertEquals(1.0, TideEngine.predict(Stations.pureM2(), Instant.EPOCH).metres(), 1e-9);
    }

    @ParameterizedTest(name = "t = {0} s")
    @ValueSource(longs = {0, 3_600, 21_600, 43_200, 86_400})
    void heightNeverExceedsTheAmplitude(long epochSecond) {
        double metres = TideEngine.predict(Stations.pureM2(), Instant.ofEpochSecond(epochSecond)).metres();
        assertTrue(Math.abs(metres) <= 1.0 + 1e-9, "height " + metres);
    }
}

StationReaderTest parses a text block of CSV and has one test tagged @Tag("slow") that parses 20,000 stations; HeightTest in the model project checks a record and the fixture. The whole project was built with ./gradlew check (after clean in the Kotlin DSL copy) and ended with BUILD SUCCESSFUL in both DSLs.

The Test task

A Test task does five things, and each is a place where a build can be configured or can go wrong.

  1. It resolves the test runtime classpath and the directories of compiled test classes (testClassesDirs). Both are properties of the task; for the test task of the java plugin they are wired to the test source set.

  2. It starts a JVM, the test worker (the console calls it Gradle Test Executor N), with the settings of the task: maxHeapSize, jvmArgs, systemProperty, environment, workingDir (the project directory by default), the javaLauncher (the JDK) and so on.

  3. In that JVM, the tests are detected by inspecting the compiled test classes, with criteria that depend on the framework: for JUnit 3 and 4 a class that inherits from TestCase, carries @RunWith or has an @Test method; for TestNG the methods annotated with @Test. scanForTestClasses = false switches the scan off so that only the include and exclude patterns select classes. With the JUnit Platform the scan setting has no effect: only include and exclude filter the classes, and the engines found on the classpath do the discovery. Abstract classes are not executed.

  4. It executes the tests and streams the events to the build, which prints them according to testLogging, writes the XML result files and the HTML report, and fails the task when a test failed (unless ignoreFailures is true).

  5. It records inputs and outputs, so that a second run with nothing changed is UP-TO-DATE.

The properties used most often:

Property or option Effect

useJUnitPlatform(), useJUnit(), useTestNG()

Selects the framework of a hand-made Test task. With the test suite DSL you use useJUnitJupiter(), useJUnit(), useTestNG() or useSpock() on the suite instead, which also adds the framework’s dependencies.

maxHeapSize, minHeapSize, jvmArgs, jvmArgumentProviders, enableAssertions

JVM settings of the worker. Assertions (-ea) are on by default.

systemProperty(name, value), systemProperties, environment(name, value), workingDir

Properties, environment variables and working directory of the worker. System properties of the Gradle process are not passed on, so only the ones set here reach the worker; environment variables are: the worker starts with the environment of the build process, and environment adds to it or overrides entries.

include, exclude, filter { ... }, --tests

Select which classes or methods run (see "Selecting tests" below).

maxParallelForks, forkEvery

How many worker JVMs run at the same time and after how many test classes a worker is replaced.

failFast, --fail-fast, ignoreFailures

Stop at the first failed test; let the build go on after failures.

failOnNoDiscoveredTests

Since Gradle 9.0, fail when there are test sources but no test was discovered (default true).

testLogging { ... }

What is printed to the console while the tests run.

reports { html, junitXml }, binaryResultsDirectory

Where and whether the HTML report and the XML result files are written.

javaLauncher

The JDK that runs the worker (a toolchain launcher).

testDefinitionDirs

Directories with non-class-based test definition files (incubating, Gradle 9.4).

dryRun, --test-dry-run

Incubating: report the tests without executing them.

The JUnit Platform and its launcher

Gradle runs JUnit 5 and 6 (JUnit Jupiter) on the JUnit Platform. Since Gradle 4.6 a Test task switches to the platform with useJUnitPlatform(). What the task needs on the test runtime classpath is more than the Jupiter API: it needs a Jupiter engine, and it needs the JUnit Platform launcher, which is the entry point that Gradle calls inside the worker. The launcher and the engines must have versions that belong together, which is why the JUnit team publishes a bill of materials (org.junit:junit-bom).

Older builds got the launcher for free: Gradle loaded some test framework classes from its own distribution. That behavior was deprecated in Gradle 8.x ("Relying on automatic test framework implementation dependencies", announced for removal in 9.0.0) because it caused version conflicts with the test classpath, and in Gradle 9 it is gone. A hand-written Test task therefore has to declare the launcher. The following engine build, which wires the framework by hand, shows what happens when it does not (the build was otherwise the same as the one above; this is a scratch variation):

The JVM Test Suite plugin

A test suite is declared under the testing extension. The java plugin has already created the suite test, which is the only one that sees the production code automatically (its source set output and the implementation dependencies of the project); every other suite has to ask for it. In tidepool-engine/build.gradle.kts the suite section is

Kotlin DSL: tidepool-engine/build.gradle.kts (excerpt)
testing {
    suites {
        named<JvmTestSuite>("test") {
            useJUnitJupiter(libs.versions.junit)
        }

        register<JvmTestSuite>("integrationTest") {
            useJUnitJupiter(libs.versions.junit)
            dependencies {
                implementation(project())
            }
            targets.all {
                testTask.configure {
                    shouldRunAfter(tasks.test)
                }
            }
        }
        // the goldenTest suite is shown in the section on non-class-based tests
    }
}

tasks.check {
    dependsOn(testing.suites.named("integrationTest"), testing.suites.named("goldenTest"))
}
Groovy DSL: tidepool-engine/build.gradle (excerpt)
testing {
    suites {
        test {
            useJUnitJupiter(libs.versions.junit)
        }

        integrationTest(JvmTestSuite) {
            useJUnitJupiter(libs.versions.junit)
            dependencies {
                implementation project()
            }
            targets.all {
                testTask.configure {
                    shouldRunAfter tasks.test
                }
            }
        }
        // the goldenTest suite is shown in the section on non-class-based tests
    }
}

tasks.check {
    dependsOn testing.suites.integrationTest, testing.suites.goldenTest
}

The pieces, in the order of the listing:

  • useJUnitJupiter(version) selects the framework and adds junit-jupiter and the launcher to the suite’s configurations, at the version given. Without an argument the plugin uses its built-in default, which is not necessarily the newest JUnit; in Gradle 9.8.1 the default is JUnit Jupiter 5.12.2 (a dependencies report of a project that called useJUnitJupiter() without argument resolved junit-jupiter:5.12.2, platform 1.12.2). The Gradle 9.0 upgrade notes name the defaults of that release (JUnit Jupiter 5.12.2, TestNG 7.11.0, Spock 2.3). Pass the version, or a provider such as libs.versions.junit, so that the framework is pinned in the version catalog.

  • dependencies { implementation(project()) } adds the project’s own production classes to the suite. project() with no argument means "this project"; in the test suite this is implicit. The dependencies block inside a suite is scoped to the suite, so implementation, compileOnly, runtimeOnly and annotationProcessor there mean the integrationTestImplementation and friends, and it is equivalent to using the long names in the top-level block.

  • targets.all { testTask.configure { ... } } configures the Test task of every target of the suite. Today a suite has exactly one target and its task has the suite’s name; the structure leaves room for several targets, for example one per JDK.

  • shouldRunAfter(tasks.test) is only an ordering hint: the slower integration tests start after the unit tests when both are in the task graph, but nothing makes one a prerequisite of the other. It is a soft rule that Gradle may break to keep workers busy: in the clean check run of this page integrationTest started before test. mustRunAfter is the strict form.

  • The suite does not attach itself to check. A suite other than test is not part of the verification lifecycle until the build says so, which is the last block above. Forgetting it is the classic bug: the task exists, the tests pass when it is run by name, and no CI build that runs build ever executes it. More of what the suite DSL offers, from the manual:

  • Sources: sources { java { setSrcDirs(listOf("src/it/java")) } } (Groovy: srcDirs = ['src/it/java']) moves a suite’s source directory; the default is src/<suite>/java. A suite’s Test task can be configured in targets.all { testTask.configure { ... } }, as the manual does for maxHeapSize.

  • Sharing configuration between suites: a block applied to every suite (withType<JvmTestSuite> { ... } in the Kotlin DSL, configureEach { ... } in Groovy), a filtered matching { ... }.configureEach { ... }, or a configuration block extracted to a variable (the three methods of the manual).

  • The frameworks: useJUnitJupiter(), useJUnit() (JUnit 4), useTestNG() and useSpock(); any suite other than the built-in test works as if useJUnitJupiter() had been called, and test must always name its framework.

  • Outgoing variants: each suite publishes its results as a variant that the aggregation plugins consume (see below).

A hand-made Test task, and the Gradle 9 change

The suite is a convenience over the Test task; a builder who registers a task by hand still can. Forks, parallelism and the JDK of the tests

A test worker is a JVM, and there are three levers over how many of them run and what they run on.

Kotlin DSL
tasks.withType<Test>().configureEach {
    maxParallelForks = 2   // at most two worker JVMs at the same time
    forkEvery = 1          // replace the worker after every test class
}
Groovy DSL
tasks.withType(Test).configureEach {
    maxParallelForks = 2   // at most two worker JVMs at the same time
    forkEvery = 1          // replace the worker after every test class
}

maxParallelForks (default 1) divides the test classes between that many workers, so several classes run at the same time and each one in its own JVM; a common value is half the number of cores, Runtime.getRuntime().availableProcessors().div(2).coerceAtLeast(1) (not run here). forkEvery (default 0, no limit) restarts the worker after that many classes, which isolates tests that leak state at a high startup cost. The effect was observed with four scratch classes that sleep for 400 ms and print the worker that ran them (org.gradle.test.worker), run with --tests selecting only those four:

(default: one worker)
    AlphaTest ran in worker 39
    BravoTest ran in worker 39
    CharlieTest ran in worker 39
    DeltaTest ran in worker 39

(maxParallelForks = 2)
    AlphaTest ran in worker 2
    BravoTest ran in worker 1
    CharlieTest ran in worker 2
    DeltaTest ran in worker 1

(maxParallelForks = 2 and forkEvery = 1)
    BravoTest ran in worker 40
    AlphaTest ran in worker 41
    DeltaTest ran in worker 42
    CharlieTest ran in worker 43

The number is the value of the org.gradle.test.worker system property, which the manual describes as unique for each test process (and useful for naming files and other resources so that parallel tests do not collide). What matters here is how many different values appear: one, two, and four (a new JVM for every class). The Groovy DSL run printed four distinct workers for the last setting as well. Forks are process level parallelism, between test classes. Inside a worker, JUnit Jupiter can also run classes and methods on several threads: set junit.jupiter.execution.parallel.enabled=true (and junit.jupiter.execution.parallel.mode.default=concurrent) in junit-platform.properties on the test classpath, or as systemProperty of the task; tests that share mutable state or files must then be written for it. Parallel forks need tests that do not share ports, files or databases.

Test helpers (builders, sample data, fake servers, custom assertions) are needed by the tests of several projects. Non-class-based tests (Gradle 9.4)

Some test frameworks do not describe tests as classes: Cucumber with its .feature files, tools that read XML, YAML or CSV scripts, golden-file tests. They run on the JUnit Platform as test engines that discover tests in files. Before Gradle 9.4 such a build needed a workaround (an empty test class to satisfy Gradle’s class-based discovery, or a JUnit extension). Gradle 9.4.0 added direct support: the Test task takes a property testDefinitionDirs with the directories to scan, gives the engine a DirectorySelector for each of them and reports the tests it finds. The feature is incubating, as are the filtering rules for non-class-based tests.

The example is a tiny engine, tide-test-engine, that reads *.tide files. Each non-comment line name amplitude phase epochSecond expected is one test: it builds a one-constituent station, asks the TideEngine for the height at the instant and compares it with the expected value within 1 mm. package io.tidepool.testengine;

import io.tidepool.engine.TideEngine;
import io.tidepool.model.Constituent;
import io.tidepool.model.Station;
import java.io.IOException;
import java.io.UncheckedIOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.time.Instant;
import java.util.List;
import java.util.stream.Stream;
import org.junit.platform.engine.EngineDiscoveryRequest;
import org.junit.platform.engine.ExecutionRequest;
import org.junit.platform.engine.TestDescriptor;
import org.junit.platform.engine.TestExecutionResult;
import org.junit.platform.engine.TestEngine;
import org.junit.platform.engine.UniqueId;
import org.junit.platform.engine.discovery.DirectorySelector;
import org.junit.platform.engine.support.descriptor.AbstractTestDescriptor;
import org.junit.platform.engine.support.descriptor.EngineDescriptor;
import org.junit.platform.engine.support.descriptor.FileSource;

/**
 * A tiny JUnit Platform engine for non-class-based tests: every line of a *.tide file
 * "name amplitude phase epochSecond expected" is one test that compares the prediction of the
 * tide engine for a one-constituent station with the expected height in metres.
 */
public final class TideTestEngine implements TestEngine {
    @Override
    public String getId() {
        return "tide-engine";
    }

    @Override
    public TestDescriptor discover(EngineDiscoveryRequest request, UniqueId uniqueId) {
        EngineDescriptor root = new EngineDescriptor(uniqueId, "Tide golden files");
        for (DirectorySelector selector : request.getSelectorsByType(DirectorySelector.class)) {
            Path dir = selector.getPath();
            try (Stream<Path> files = Files.walk(dir)) {
                files.filter(f -> f.toString().endsWith(".tide")).sorted().forEach(f -> addFile(root, dir, f));
            } catch (IOException e) {
                throw new UncheckedIOException(e);
            }
        }
        return root;
    }

    private static void addFile(EngineDescriptor root, Path dir, Path file) {
        String name = dir.relativize(file).toString().replace('/', '.').replaceAll("\\.tide$", "");
        FileDescriptor container = new FileDescriptor(root.getUniqueId().append("file", name), name, file);
        try {
            List<String> lines = Files.readAllLines(file);
            for (int i = 0; i < lines.size(); i++) {
                String line = lines.get(i).strip();
                if (!line.isEmpty() && !line.startsWith("#")) {
                    container.addChild(new CaseDescriptor(container.getUniqueId().append("line", String.valueOf(i + 1)),
                            file, i + 1, line));
                }
            }
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
        root.addChild(container);
    }

    @Override
    public void execute(ExecutionRequest request) {
        var listener = request.getEngineExecutionListener();
        TestDescriptor root = request.getRootTestDescriptor();
        listener.executionStarted(root);
        for (TestDescriptor container : root.getChildren()) {
            listener.executionStarted(container);
            for (TestDescriptor test : container.getChildren()) {
                listener.executionStarted(test);
                try {
                    ((CaseDescriptor) test).run();
                    listener.executionFinished(test, TestExecutionResult.successful());
                } catch (Throwable t) {
                    listener.executionFinished(test, TestExecutionResult.failed(t));
                }
            }
            listener.executionFinished(container, TestExecutionResult.successful());
        }
        listener.executionFinished(root, TestExecutionResult.successful());
    }

    private static final class FileDescriptor extends AbstractTestDescriptor {
        FileDescriptor(UniqueId id, String name, Path file) {
            super(id, name, FileSource.from(file.toFile()));
        }

        @Override
        public Type getType() {
            return Type.CONTAINER;
        }
    }

    private static final class CaseDescriptor extends AbstractTestDescriptor {
        private final String line;

        CaseDescriptor(UniqueId id, Path file, int number, String line) {
            super(id, line, FileSource.from(file.toFile(), org.junit.platform.engine.support.descriptor.FilePosition.from(number)));
            this.line = line;
        }

        @Override
        public Type getType() {
            return Type.TEST;
        }

        void run() {
            String[] p = line.split("\\s+");
            Station station = new Station(p[0], p[0], 0, 0, List.of(new Constituent(p[0], Double.parseDouble(p[1]), Double.parseDouble(p[2]))));
            double actual = TideEngine.predict(station, Instant.ofEpochSecond(Long.parseLong(p[3]))).metres();
            double expected = Double.parseDouble(p[4]);
            if (Math.abs(actual - expected) > 0.001) {
                throw new AssertionError("expected " + expected + " m but the engine predicted " + actual + " m");
            }
        }
    }
}

Code coverage with JaCoCo

The jacoco plugin attaches the JaCoCo agent to every Test task of the project, records coverage in a .exec file per task, and adds two tasks for the test task: jacocoTestReport (reports) and jacocoTestCoverageVerification (rules that can fail the build). It replaces the EMMA and Cobertura of the era of the book: EMMA is dead, the Cobertura plugin was always third party and unmaintained, and JaCoCo is the core Gradle plugin.

Kotlin DSL: tidepool-engine/build.gradle.kts (excerpt)
plugins {
    `java-library`
    jacoco
}

tasks.test {
    finalizedBy(tasks.jacocoTestReport)
}

tasks.jacocoTestReport {
    dependsOn(tasks.test)
    reports {
        xml.required = true
        csv.required = true
    }
}

tasks.jacocoTestCoverageVerification {
    violationRules {
        rule {
            limit {
                minimum = "0.80".toBigDecimal()
            }
        }
    }
}

tasks.check {
    dependsOn(tasks.jacocoTestCoverageVerification)
}
Groovy DSL: tidepool-engine/build.gradle (excerpt)

The pieces:

  • finalizedBy(tasks.jacocoTestReport) makes the report run after every test, even when tests fail (a failed run is when the report is most useful). dependsOn(tasks.test) on the report does the reverse, so that asking for the report runs the tests first. The plugin does neither for you, and a report with no execution data is skipped.

  • Report formats: HTML (default, in build/reports/jacoco/test/html), XML (xml.required, the input of SonarQube, Codecov and most CI integrations) and CSV. Each has an outputLocation.

  • Coverage counters are INSTRUCTION, BRANCH, LINE, COMPLEXITY, METHOD and CLASS; their values are COVEREDRATIO, MISSEDRATIO, COVEREDCOUNT, MISSEDCOUNT and TOTALCOUNT. A rule applies to an element (BUNDLE, the default, or PACKAGE, CLASS, SOURCEFILE, METHOD) and has limit blocks; includes and excludes narrow it to classes. In the Kotlin DSL a limit’s minimum is a BigDecimal, which is why the value is written "0.80".toBigDecimal().

  • jacoco { toolVersion = "..." } selects the JaCoCo version. The default of Gradle 9.8.1, taken from the resolved jacocoAgent configuration of the build, is 0.8.15 (8.14 used 0.8.13). The JaCoCo version limits the class file versions that can be instrumented, so a build on a new JDK needs a new enough JaCoCo, which is one more reason to keep Gradle current.

  • The agent attached to every Test task. After a full check, the engine’s build/jacoco directory contains test.exec, integrationTest.exec and goldenTest.exec; jacocoTestReport reads only the first one, because it is configured for the test task. To report the combined coverage of several suites, a JacocoReport task of your own has to be given the execution data of all of them (not run here). The extension that the plugin adds to every Test task, jacoco { ... } in Groovy and extensions.configure<JacocoTaskExtension> { ... } in Kotlin, moves the .exec file (destinationFile) and controls the agent’s options.

Aggregating test and coverage reports

In a multi-project build every project writes its own report, which is what you do not want on a CI summary page. Classic mistakes

  • The integration suite is not part of check. Fix: tasks.check { dependsOn(testing.suites.named("integrationTest")) }. The dry run above proves it.

  • JUnit 4 tests vanish after a move to Jupiter. The junit-vintage-engine is missing; only when no test is discovered does Gradle 9 fail the task.

  • Failed to load JUnit Platform on a hand-wired Test task: the launcher is not on the runtime classpath. Use test suites, which add it, or add junit-platform-launcher.

  • A Test task registered without configuration runs nothing since 9.0 and says only NO-SOURCE.

  • A red test stays hidden with ignoreFailures = true plus the up-to-date check, until --rerun.

  • Tests that depend on the working directory. The worker’s working directory is the project directory, not the root; the example passes the data location as a system property computed from the project layout instead of hard-coding ../.

  • Sharing state between parallel forks: files in a fixed location, fixed ports, a shared database.

  • Shipping test code in main instead of using test fixtures.

  • Coverage thresholds as the goal: a violation rule with an overall percentage rewards trivial tests; per-class rules on branches, as above, or new-code rules from a quality server catch more.

  • Reading project properties inside a test task action (project.property) breaks the configuration cache; use providers (providers.gradleProperty) at configuration time, as in the -Pfast example.

  • Timing claims from a first run. The 21 s of the first goldenTest run include building the projects and the daemon start; compare runs only after a warm-up.

Configuration cache

Every build script of this page was run with --configuration-cache and stored the entry without problems, and a second invocation reused it. What makes test builds compatible: only task properties and providers are read at configuration time (the system property of Test uses layout.projectDirectory, not a File captured from project); the JVM Test Suite plugin, JaCoCo, Checkstyle, PMD and the aggregation plugins are compatible, which is also true of the Test task. With the cache on, tasks of one project can run in parallel, which the page’s clean check output shows through the interleaved order of independent tasks. Incompatible things to avoid in test configuration: project in doFirst/doLast of a test task, a TestListener that holds on to Project, and build scripts that read environment variables at configuration time without declaring them. The configuration cache is on page Configuration Cache & Isolated Projects; a test task is cacheable by the build cache (see Build Cache) only if the tests are deterministic and do not depend on undeclared inputs: pass the inputs through inputs.file(...), inputs.property(...) or systemProperty with a provider, not by reading them in the test.

Where the books are outdated

Gradle in Action (Muschko, Manning 2014, Gradle 1.7) devotes its testing chapter to the test pyramid, to JUnit, TestNG and Spock, to forking and parallel execution, to logging, filtering and listeners, to reports, and to integration and functional tests with hand-made source sets and tasks. The concepts survive and the mechanics changed:

  • Integration tests with a hand-made source set, configurations and Test task are replaced by the JVM Test Suite plugin (7.3); the hand-made form still works and is shown on Gradle Java Projects.

  • compile, testCompile, runtime and testRuntime are gone since 7.0; use implementation, testImplementation, runtimeOnly and testRuntimeOnly.

  • The book’s JUnit is JUnit 4 and the old runner. JUnit 5 support arrived in 4.6, JUnit 6 is the current line here, and the Vintage engine bridges old tests.

  • The book’s quality chapter covers JaCoCo, Checkstyle, PMD and Sonar. JaCoCo, Checkstyle and PMD remain core plugins; FindBugs and JDepend, core plugins of the era, were removed in 6.0; the legacy sonar plugin was removed in 3.0 and replaced by SonarQube’s own org.sonarqube plugin; the Cobertura plugin was third party and unmaintained.

  • The book’s ProjectBuilder-only tests of plugins are replaced by TestKit’s GradleRunner (see Testing & Publishing Plugins).

  • The book’s test listeners are one way to observe results; for results consumed by CI, the XML files and the aggregation plugins are the supported path, and in a build with the configuration cache on, listeners that capture the project are a problem (see above).

  • The book predates the configuration cache, version catalogs, toolchains and javaLauncher; the page numbers of the book were not checked, and the statements follow the research notes behind this section.
