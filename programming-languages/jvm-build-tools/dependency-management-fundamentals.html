Dependency Management Fundamentals

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Ant 1.10.18 with Apache Ivy 2.6.0 and the Maven Resolver Ant Tasks 2.0.0, Apache Maven 3.10.0 (3.9.16 and Maven 4.0.0-rc-7, a release candidate, are named where they differ) and Gradle 9.8.1, and every example was run on JDK 26 (checked on 2026-10-16). The examples that print a result were run with exactly those releases from a scratch directory; an example that was not run is labelled "not run here".

A dependency is a piece of software your build needs that somebody else produced: a library to compile against, a library to run with, a test framework, a compiler plugin. Dependency management is everything a build tool does about that: it names the piece (the coordinates), finds it in a repository, finds what it needs in turn (the transitive dependencies), decides which one of two competing versions wins, puts the right files on the right classpath, and ideally makes the answer the same tomorrow as it is today. Ant itself does none of this — it copies files you point it to — so the Ant world borrows the machinery from Apache Ivy or from the Maven Resolver Ant Tasks. Maven and Gradle have it built in, and the three tools turn out to share more than they disagree on: all of them read the same Maven repository layout and the same POM files, and almost all the real differences are in two places, the conflict policy and how they let you pin versions.

This page is the shared vocabulary. The running scenario is the tidepool toolkit described in the section landing page. The examples take a small slice of the tidepool-cli dependency graph and run it through every tool. The details of each tool live on its own pages, linked from Where to go next; how the repositories are laid out and published to is in Repositories & Publishing Across Tools; the build-graph side (targets, phases, tasks) is in Build Automation Fundamentals.

Coordinates: naming a piece of software

Every tool needs a name for a dependency that is unique across all repositories. They all converge on the Maven idea of coordinates, with different spellings.

Tool Spelling Elements

Maven

groupId:artifactId:version, written as child elements of a <dependency>; command-line plugin parameters use groupId:artifactId:version[:packaging[:classifier]]

groupId, artifactId, version, type (default jar, which decides the file extension) and classifier

Gradle

group:name:version[:classifier][@extension], for example commons-io:commons-io:2.20.0:sources@jar

group, name, version, classifier, extension; the component also has capabilities, by default group:name:version itself

Ivy (and so Ant with Ivy)

org, name and rev attributes on a <dependency>; printed as organisation#module;revision, for example org.apache.commons#commons-csv;1.14.1

organisation, module, optionally branch, revision; artifacts are described separately

Maven Resolver Ant Tasks

coords="groupId:artifactId:version" on <dependency>, or the groupId, artifactId, version attributes

the same as Maven; it reads and writes Maven repositories

Source: Maven: Coordinates of Dependencies and Ivy: Terminology, module

Three distinctions are worth fixing at once, because the three tools mix them up in different ways.

  • A module (Ivy), component (Gradle) or project (Maven) is the unit that has a version and a descriptor. An artifact is one file that the module publishes: the main JAR, a -sources.jar, a -javadoc.jar, a .pom. A module with one version publishes one descriptor and any number of artifacts. A dependency is declared on a module, and the build then picks which of its artifacts it wants.

  • The classifier is a suffix that tells two artifacts of the same module apart: commons-io-2.20.0.jar and commons-io-2.20.0-sources.jar. The type in Maven or the extension in Gradle is the file extension. Maven maps a type to an extension (and sometimes a classifier) through an ArtifactHandler; Gradle writes the extension after an @.

  • A module has one version in a given graph. That sounds obvious, and it is the root of the whole conflict problem below: two paths through the graph can ask for two different versions of the same group:name, and the tool has to keep only one.

The same file is named in the three tools. The example resolves only the sources artifact of commons-io 2.20.0 and prints the file it got.

Direct and transitive dependencies, and the graph

A direct dependency is one you declare. A transitive dependency is one that a direct dependency (or one of its own dependencies) needs. The tools learn about transitive dependencies by reading the descriptor each dependency published next to its JAR — a POM for a Maven repository, an ivy.xml for an Ivy one, a .module file for a Gradle one (see Module metadata). There is no depth limit; only a cycle is an error. The result is a graph, and it grows fast: a project with ten direct dependencies routinely resolves a few dozen modules.

The slice of tidepool-cli used below is deliberately tiny. tidepool-cli depends on commons-csv 1.14.1, which in turn needs commons-io 2.20.0 and commons-codec 1.19.0. To make a conflict, tidepool-cli also declares commons-io 2.11.0 directly, as a project often does for a library it uses itself. Two different versions of one module are now requested, and the tools disagree about the winner.

Ant with Ivy resolves a graph from an ivy.xml and prints the selected modules; Ant with the Maven Resolver Ant Tasks resolves from the dependencies written in the build file. Ivy kept commons-io 2.20.0 and the Resolver Ant Tasks kept 2.11.0. The next-but-one section explains why.

The three habits that keep a graph healthy are the same in every tool. Declare every library your own source code imports directly, even if it also arrives transitively, because the transitive path is somebody else’s implementation detail and can change. Look at the resolved graph whenever a dependency changes. And pin or constrain a version only with a reason you can write down.

Scopes and configurations

Not every dependency belongs on every classpath. A compiler plugin should not ship; a test framework should not be needed by a consumer; a servlet API is provided by the container. The tools express "which classpath, and does it travel to my consumers" differently.

  • Maven calls it a scope on each dependency. A scope fixes which of the classpaths (compile, runtime, test) the dependency joins, and whether it is passed on transitively and in which scope.

  • Ivy calls it a configuration (conf) of the module, and a dependency maps one of my configurations to one of the dependency’s configurations: compile->default reads "my compile needs the dependency’s default".

  • Gradle also calls it a configuration, but a configuration is a named bucket of dependencies that is declared, resolved or consumed; the Java plugins create implementation, api, runtimeOnly, compileOnly, testImplementation and others for you.

Two points matter in practice. First, the Ivy names are a convention, not a rule: a conf can be called anything, and you choose which ones extend which (in the descriptor above runtime extends compile, so a runtime classpath contains everything the compile classpath does). Second, the three vocabularies have a faithful translation at the boundary where a module is published, because a Maven consumer reads a POM, not a Gradle build file. The translation goes the other way too. When Ivy reads a Maven POM, it builds a module descriptor whose configurations are the Maven scopes. This is the <configurations> element of the descriptor Ivy wrote for commons-csv 1.14.1 (the descriptions are shortened), taken from the Ivy cache after the Ant resolve run above:

<configurations>

  <conf name="master" visibility="public" description="contains only the artifact published by this module itself, with no transitive dependencies"/>
  <conf name="compile" visibility="public"/>
  <conf name="provided" visibility="public"/>
  <conf name="runtime" visibility="public" extends="compile"/>
  <conf name="test" visibility="public" extends="runtime"/>
  <conf name="system" visibility="public"/>
  <conf name="sources" visibility="public"/>
  <conf name="javadoc" visibility="public"/>
  <conf name="optional" visibility="public"/>
</configurations>

That is why compile->default in the tidepool-cli descriptor works against a module that has no ivy.xml of its own: default is the configuration that extends runtime and master.

Exclusions and optional dependencies are the other ways to cut a graph: Maven has <exclusions> and <optional>, Gradle has exclude(group = ..., module = ...) and isTransitive = false, Ivy has <exclude> and per-dependency transitive="false". They are listed here so the vocabulary is complete; they are not run on this page.

Conflict resolution

When two paths of the graph request different versions of the same module, a tool must keep one. The three policies are easy to state and have different failure modes.

Tool Policy What it means for tidepool-cli

Maven (and Maven Resolver Ant Tasks)

"Nearest definition": the version closest to the root of the graph wins; if two are at the same depth, the first declaration wins

commons-io 2.11.0 (depth 1) beats the 2.20.0 requested by commons-csv (depth 2)

Gradle

The highest of all requested versions wins, wherever it appears in the graph, unless a constraint or a strictly says otherwise

commons-io 2.20.0

Ivy

A conflict manager, per module or for all: latest-revision (the default), latest-time, latest-compatible, strict, and nearest (since 2.6.0)

2.20.0 by default; 2.11.0 with nearest; a build failure with strict

Source: Maven: transitive dependencies, dependency mediation, Gradle: Resolving version conflicts and Ivy: conflict managers

Each policy has a pitfall that the others do not have.

  • Nearest definition looks only at the shape of the graph. It never compares versions, so a direct dependency on an older version silently downgrades a library that needs a newer one, as the tidepool-cli graph shows: commons-csv 1.14.1 was built against commons-io 2.20.0 and now runs with 2.11.0. Nothing fails until a method that does not exist in 2.11.0 is called. The -Dverbose tree above is how you see it.

  • Highest version looks only at the numbers. A higher version is not always a compatible one, and the winning version can come from a dependency four levels down that you never looked at.

  • Ivy’s latest-revision is "latest" by a string-oriented comparison of revisions (the documentation points out that latest-time is more costly to compute). Ivy also honours the force attribute of a direct dependency under the two latest managers.

Maven: nearest definition, and what dependencyManagement does and does not change

Maven’s way out of a bad mediation is to take the decision yourself. A dependencyManagement entry fixes the version of a dependency wherever it appears, but only where the version is not already written down: a direct dependency that carries its own <version> keeps it. Both effects were run. Gradle: highest wins, and how to say otherwise

The plain build above selected 2.20.0 without a word from you. When the highest version is wrong, or when you want a floor under it, Gradle has three tools, each stronger than the last: a constraint (a floor that adds no dependency), a rich version with strictly (a ceiling or an exact version that fails the build if somebody asks for something outside it), and forcing via resolution rules, which belongs to the dedicated pages. A constraint on commons-io:

Kotlin DSL
dependencies {
    implementation("org.apache.commons:commons-csv:1.14.1")
    implementation("commons-io:commons-io:2.11.0")
    constraints {
        implementation("commons-io:commons-io:2.20.0") {
            because("commons-csv 1.14.1 was built against 2.20.0")
        }
    }
}
Groovy DSL
dependencies {
    implementation 'org.apache.commons:commons-csv:1.14.1'
    implementation 'commons-io:commons-io:2.11.0'
    constraints {
        implementation('commons-io:commons-io:2.20.0') {
            because 'commons-csv 1.14.1 was built against 2.20.0'
        }
    }
}
runtimeClasspath - Runtime classpath of source set 'main'.
+--- org.apache.commons:commons-csv:1.14.1
|    +--- commons-io:commons-io:2.20.0
|    \--- commons-codec:commons-codec:1.19.0
+--- commons-io:commons-io:2.11.0 -> 2.20.0
\--- commons-io:commons-io:2.20.0 (c)

(c) - A dependency constraint, not a dependency. The dependency affected by the constraint occurs elsewhere in the tree.

A constraint can only raise the result, never lower it, because the winner is still the highest. To force the older version (which is what Maven did without being asked) the version must be strict. A range with a strictly bound and a prefer is read as "anything in [2.11.0, 2.15[, and if nothing else decides, 2.11.0", and the strict bound beats the higher version that commons-csv asked for:

Kotlin DSL
dependencies {
    implementation("org.apache.commons:commons-csv:1.14.1")
    implementation("commons-io:commons-io") {
        version {
            strictly("[2.11.0, 2.15[")
            prefer("2.11.0")
        }
    }
}
Groovy DSL
dependencies {
    implementation 'org.apache.commons:commons-csv:1.14.1'
    implementation('commons-io:commons-io') {
        version {
            strictly '[2.11.0, 2.15['
            prefer '2.11.0'
        }
    }
}
runtimeClasspath - Runtime classpath of source set 'main'.
+--- org.apache.commons:commons-csv:1.14.1
|    +--- commons-io:commons-io:2.20.0 -> 2.11.0
|    \--- commons-codec:commons-codec:1.19.0
\--- commons-io:commons-io:{strictly [2.11.0, 2.15[; prefer 2.11.0} -> 2.11.0

Source: Gradle: Rich version constraints and Gradle: Resolving version conflicts

Gradle has a second kind of conflict that the other two tools do not model: a capability conflict. Two components that claim the same capability, say two logging bindings that both provide com.example:logging, cannot both be on the classpath, and Gradle fails the build unless a rule picks one. See Gradle: Resolving capability conflicts and Dependency Resolution, Conflicts & Capabilities.

Ivy: pick a conflict manager

Ivy resolves conflicts with a pluggable conflict manager. The default is latest-revision, which is what selected commons-io 2.20.0 above. Setting <conflict manager="nearest"/> in the descriptor (Ivy 2.6.0 and later, "compatible with the Maven conflict handling") makes Ivy choose what Maven chose:

  <dependencies>
    <dependency org="org.apache.commons" name="commons-csv" rev="1.14.1" conf="compile->default"/>
    <dependency org="commons-io" name="commons-io" rev="2.11.0" conf="compile->default"/>
    <conflict manager="nearest"/>
  </dependencies>

     [echo] commons-codec-1.19.0.jar
     [echo] commons-io-2.11.0.jar

Snapshots and changing modules

A snapshot (Maven) or a changing module (Gradle, Ivy) is a version that can be republished under the same number, the usual way to share work in progress between projects. Maven writes -SNAPSHOT after the version and a repository stores timestamped files, resolved according to an update policy (always, daily, interval:X, never; -U forces a check). Gradle calls a Maven snapshot a changing version. By default Gradle caches dynamic versions and changing modules for 24 hours and then re-checks; the cache window is set with cacheDynamicVersionsFor and cacheChangingModulesFor. Snapshot and changing-module resolution needs a repository to republish into, so it is not run on this page; the details are on Versions, Snapshots & Ranges and Dependency Locking, Verification & Caching.

Source: Gradle: Declaring changing versions, Gradle: Controlling dynamic version caching and Maven: Consuming snapshot artifacts

Determinism: pin what a range picked

A build is deterministic when the same sources produce the same dependency set, today and in a year. Ranges, latest.* and snapshots all break that, and so does a transitive dependency whose version a library maintainer moved. The tools offer three kinds of pin.

Tool Pin What it records

Maven

Explicit versions, dependencyManagement, and a BOM import; no lockfile in the core

The versions are written in the POM; a transitive range is only as stable as the repository

Gradle

Dependency locking: lockAllConfigurations() and --write-locks

A gradle.lockfile with the complete resolved set of each configuration

Ivy

ivy:deliver, which replaces dynamic revisions with the resolved ones in the published descriptor

A resolved ivy.xml, with the requested range kept in revConstraint

Gradle writes the lockfile when asked. The project below combines a range, a platform and locking; gradle dependencies --write-locks produced gradle.lockfile, whose first lines for the dependencies above are:

Ivy’s deliver task turns a dynamic descriptor into a static one. Given a descriptor with rev="[4.7,5.0)", after ivy:resolve the delivered file was

  <info organisation="io.tidepool" module="tidepool-cli" revision="1.0.0" status="release" publication="20261016111605"/>

The cheapest rule of all is not to use ranges in anything you release, and to keep them, if at all, behind a lock.

BOMs and platforms

Libraries that ship as a family (JUnit, Spring, Jackson) must agree on their versions. Listing every member with its own version is noisy and error prone, so the family publishes a bill of materials (BOM): a POM, with no code, whose dependencyManagement lists the versions of all members. The three tools consume one differently.

Tool How a BOM is used Effect

Maven

<scope>import</scope> with <type>pom</type> in dependencyManagement

Copies the BOM’s managed versions into the importing POM; members can then be declared without a <version>

Gradle

platform("g:n:v") (or enforcedPlatform)

Treats the BOM as a set of constraints; members are declared without a version and get the platform’s version

Ivy

The Ivy POM parser expands the BOM into <override> elements

Overrides the version of every managed module without declaring a dependency on it

A tidepool module that uses JUnit 6.1.3, as in the Gradle block above, imports the JUnit BOM in Maven like this. The dependency:tree run below it shows junit-jupiter resolving with no version in the dependency entry, and every member marked as managed:

</dependencyManagement>

Ivy has no BOM concept of its own. It reads Maven’s, and the descriptor it wrote for commons-csv 1.14.1 (whose POM imports BOMs) shows the translation: dependencyManagement versions became force="true" on the dependency and the BOM entries became <override>:

The difference in strength between the Maven import and the Gradle platform is worth remembering. A Maven import changes the version of a dependency that is declared without one and of a transitive dependency that is mediated; it does not beat a version written on a direct dependency, as the dependencyManagement example above showed. A Gradle platform is a constraint, so it behaves like the constraints block above: it raises, it does not lower. For a platform that must win over everything, Gradle offers enforcedPlatform, and strictly versions in the BOM itself. Authoring a BOM, ordering several imports, and the Maven 4 (release candidate) bom packaging are on Dependency Management & BOMs and Platforms, Constraints & Rich Versions.

Module metadata: POM, ivy.xml and Gradle Module Metadata

The descriptor that sits next to a JAR is what turns a pile of files into a graph. Three formats are in use.

Format File What it can say

Maven POM

artifact-version.pom

coordinates, parent, packaging, dependencies with scope, optional and exclusions, dependencyManagement, properties, licences, developers, SCM; no way to say which artifacts differ in what they are for

Ivy module descriptor

ivy-revision.xml, or ivy.xml in a build

configurations and the mapping between them, published artifacts per configuration, dependency exclusions, conflict managers, overrides, branch

Gradle Module Metadata

artifact-version.module, JSON

variants (named sets of files and dependencies with attributes), capabilities, rich versions, dependency constraints, an explicit link to the files to download

Source: Ivy: Terminology, module and Gradle: Gradle Module Metadata

A POM describes one set of dependencies. A real library often needs two: what a consumer needs to compile against, and what it needs to run with. Maven encodes that with scopes, Ivy with configurations, and Gradle with variants that carry attributes describing their purpose. During resolution, Gradle matches the attributes its consumer asks for (a Java API at JDK 26, say) against the variants the module offers. This is what the Variant runtime table printed by dependencyInsight above was about. The org.gradle.usage attribute is how a library’s API variant (java-api) is told from its runtime variant (java-runtime).

Libraries published by Gradle carry a .module file. This is the summary of the file for org.junit.jupiter:junit-jupiter-api 6.1.3, printed by a ten-line script from the file Gradle downloaded into its cache (the script reads the JSON and prints the variant name, its usage attribute and the dependencies):

import json, sys
d = json.load(open(sys.argv[1]))
print("formatVersion", d["formatVersion"])
for v in d["variants"]:
    deps = [f'{x["group"]}:{x["module"]}' for x in v.get("dependencies", [])]
    print(v["name"], v["attributes"].get("org.gradle.usage"), deps)

The file was published with Gradle 9.5.1 (its createdBy field), had formatVersion 1.1 and these variants (the dependency lists are cut to the first three; the sources and javadoc variants have none):

apiElements java-api ['org.junit:junit-bom', 'org.opentest4j:opentest4j', 'org.junit.platform:junit-platform-commons']
runtimeElements java-runtime ['org.junit:junit-bom', 'org.opentest4j:opentest4j', 'org.junit.platform:junit-platform-commons']
javadocElements java-runtime []
sourcesElements java-runtime []

The javadocElements and sourcesElements variants are the point of the format: a consumer asking for documentation, or an IDE asking for sources, is told which files to fetch, where a Maven client has to guess a classifier. The Gradle project we published earlier wrote the same kind of file next to its POM. Its summary, with Gradle 9.8.1, was

formatVersion 1.1
apiElements java-api ['org.apache.commons:commons-csv']
runtimeElements java-runtime ['info.picocli:picocli', 'org.apache.commons:commons-csv', 'commons-io:commons-io']

Here the api/implementation split that the POM could not carry is explicit: commons-csv is part of the API variant, the other two only of the runtime variant. Compatibility is the other half of the design: the POM written next to the .module file begins with a comment saying that the module was also published with a richer model and asking tools not to delete the line that follows it, and a Maven or Ant consumer simply ignores the .module file and reads the POM. Gradle warns at publication time when a build uses a feature that only the .module file can express.

Source: Gradle: Variant-aware dependency resolution and Gradle: Mapping with other formats
