JVM Build Tools: Ant, Maven & Gradle

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This section is a reference for the three build tools of the Java Virtual Machine world: Apache Ant, Apache Maven and Gradle. Build automation is the practice of describing how source code becomes a tested, packaged and published artifact once, in a file the tool can run, so that every developer and every CI server builds the same way. Dependency management is the companion practice of naming the libraries a project needs by coordinates, resolving them (and everything they need) from repositories, choosing one version when several are requested, and publishing the project’s own artifacts for others to consume. Ant describes the build as a graph of targets made of tasks, Maven as a fixed lifecycle of phases that plugin goals attach to, and Gradle as a graph of tasks that plugins and build scripts add and wire up. The pages here cover each tool from its first command to its extension points, and a set of shared pages put the three side by side.

The three tools

Tool What it is Build model Configuration files Current version and Java needed to run

Apache Ant

An XML-driven build tool and a Java library of tasks, born in 2000 (first stand-alone release 1.1 on 19 July 2000). It has no built-in conventions and no dependency management of its own.

Imperative: named targets that depend on each other, each made of tasks, run in dependency order.

build.xml (plus imported files and build.properties); dependencies through Apache Ivy (ivy.xml, ivysettings.xml) or the Maven Resolver Ant Tasks.

Ant 1.10.18 (6 September 2026), Ivy 2.6.0, Resolver Ant Tasks 2.0.0. Java 8 or later.

Apache Maven

A declarative build and project-management tool: a project object model, a standard directory layout, a fixed lifecycle and a repository system with coordinates.

Declarative: the POM describes the project, the lifecycle phases are bound to plugin goals by the packaging, and convention supplies the rest.

pom.xml, settings.xml, and the .mvn directory (maven.config, jvm.config, extensions.xml).

Maven 3.10.0 and the previous series' 3.9.16 (Java 8 or later); Maven 4.0.0-rc-7 is a release candidate (Java 17).

Gradle

A build tool with a programmable task graph, a rich plugin ecosystem, incremental builds, a build cache and variant-aware dependency management.

Programmable: build scripts in the Kotlin or Groovy DSL configure plugins, which register tasks that Gradle wires into a graph and runs only when their inputs or outputs changed.

settings.gradle.kts and build.gradle.kts (or the .gradle Groovy forms), gradle.properties, gradle/libs.versions.toml, and the wrapper files in gradle/wrapper.

Gradle 9.8.1 (and 8.14.6, the last 8.x release). A JVM from 17 to 27 to run it.

Each tool has its own landing page with the details: Apache Ant, Apache Maven and Gradle. How they differ, and when to use which, is the topic of Comparing Ant, Maven & Gradle; the shared ideas (build graphs, conventions, caching) are in Build Automation Fundamentals and Dependency Management Fundamentals.

Version baseline

Unreleased work (an Ant 1.10.19 section in the Ant change log, Gradle 9.9 milestones) is not documented. Every page states what differs on the other maintained lines of its tool and how the tool’s support policy treats older releases. The examples were run on JDK 26 on macOS, using the tool releases named above, and the output shown on a page is the real output of the run; examples that could not be run (for instance publishing to the real Maven Central, which needs credentials) are labelled "not run here" on their page. The tidepool scenario

The examples share one small, original project: tidepool, a toolkit that predicts tide heights for coastal stations from harmonic constituents. The same project is built with all three tools, so a page can show the same task in each of them and the pages build on one another. It has three modules:

  • tidepool-model, a library with the Java records Station, Constituent and TideEvent and the value type Height.

  • tidepool-engine, a library that depends on tidepool-model and on Apache Commons CSV to read the sample file data/stations.csv; it shows api versus implementation in Gradle, compile versus runtime scope in Maven and Ivy configurations.

  • tidepool-cli, an application with a main class that uses picocli (an annotation processor, which exercises processor paths in all three tools); it is packaged as an executable JAR, an uber JAR and a distribution archive.

Around the modules the scenario adds unit tests in each module with JUnit Jupiter, an integration test of the command line program against data/stations.csv, shared build logic (an Ant common.xml imported by each module, a Maven parent POM and bill of materials, a Gradle convention plugin in build-logic), one custom build extension written once per tool (the Ant task checkstations, the Maven plugin goal tidepool:check-stations and the Gradle plugin tidepool.station-check, each validating the stations file), and publishing to a local file repository under build/repo or to a repository on localhost. A page whose concept fits the scenario poorly uses a minimal standalone example instead (for instance Ant selectors or Maven archetypes). No example uses a real credential or a real remote server.

How the books were used

Three books were consulted as references for concept coverage and structure: Erik Hatcher and Steve Loughran’s Java Development with Ant (Manning, 2002), written for Ant 1.5; Maria Odea Ching and Brett Porter’s Apache Maven 2 Effective Implementation (Packt, 2009), written for Maven 2.2; and Benjamin Muschko’s Gradle in Action (Manning, 2014), written for Gradle 1.7. None of them is the source of any example: every example is written against the current official documentation, the official documentation wins wherever they differ, and no text, code listing or figure is copied from a book. Each page states in prose where the books are outdated for the concepts it touches. The headline items are these.

  • Ant: Ant 1.10 needs Java 8 or later; import, include, macrodef and antlibs (Ant 1.6 and later) replace antcall-heavy builds and most of Ant-Contrib; JUnit 5 and later need junitlauncher; javah, rmic and apt no longer work; the Nashorn engine is gone from the JDK; XDoclet, Cactus, Axis 1, CruiseControl and Tomcat 4 deployment are obsolete; and the book has no dependency management, which today means Ivy or the Maven Resolver Ant Tasks.

  • Maven: Maven 2 reached end of life in 2014; Continuum and Archiva are retired Apache projects; plugin versions must be pinned; plain HTTP repositories have been blocked since Maven 3.8.1; EMMA and Cobertura are replaced by JaCoCo, FindBugs by SpotBugs and Clirr by japicmp or Revapi; OSSRH was shut down on 30 June 2025 in favour of the Central Portal; and Maven 4 brings the consumer POM and model version 4.1.0.

  • Gradle: the << task definition and the compile, runtime and testCompile configurations were removed, as were the maven plugin with uploadArchives and the jetty plugin; apply plugin: gave way to the plugins block, the Kotlin DSL is the default of gradle init, version catalogs and convention plugins replaced ad-hoc versions and allprojects blocks; the book has no toolchains, build cache, configuration cache or test suites; and JCenter and Bintray are gone.

The collected legacy-to-modern replacements are on Ant: Deprecations & Migration, Maven: Versions & Release History and Upgrading Gradle. The books are cited only through their publishers' pages in the bibliography.
