Maven Archetypes

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Maven 3.10.0 with the Maven Archetype Plugin 3.4.1 (the version Maven 3.10.0 resolves for the archetype prefix when nothing pins it). Every example was run on JDK 26 on 2026-10-16 with a scratch local repository, except where the text says JDK 21; the commands that could differ between releases were repeated on Maven 3.9.16 and on Maven 4.0.0-rc-7 (a release candidate, not a final release), and the differences are in What differs between Maven versions. Paths in the console output were shortened to /work/... and /work/m2 is the scratch local repository; long Maven output was filtered to the lines of the plugin involved, and a line made of ... marks where lines were removed. Anything that was not run is labelled "not run here".

An archetype is a project template. It is packaged as a JAR that holds a description of the project (the archetype descriptor) and a set of files with placeholders (the prototype); the Archetype Plugin combines them with a few values that you give (group id, artifact id, version, package, and anything the template author asked for) and writes a ready-to-build project. The first project of Getting Started was made that way. This page explains how generating works, where the list of archetypes comes from, and how to write, test and publish one of your own. The Ant and Gradle counterparts are in The same idea in Ant and Gradle.

What an archetype is made of

Source: Maven: Introduction to Archetypes

An archetype is an ordinary Maven artifact whose packaging is maven-archetype. Inside its JAR there are exactly these parts:

Path in the JAR Role

META-INF/maven/archetype-metadata.xml

The archetype descriptor: lists which files make up the project and how each group of files is processed (copied as is, filtered, moved under the package directory), and which properties the user must supply.

archetype-resources/

The prototype: the files and directories of the project to generate. The pom.xml in it is the prototype POM of the new project, not the POM of the archetype.

META-INF/archetype-post-generate.groovy

Optional script that runs after the project was written (see The post-generation script).

META-INF/maven/<groupId>/<artifactId>/pom.xml

Added by the build, like in every JAR: the archetype’s own POM.

The archetype’s own pom.xml (at the root of the archetype project) is small, because nothing is compiled. It declares the packaging maven-archetype and the archetype-packaging extension, which supplies that packaging:

<project xmlns="http://maven.apache.org/POM/4.0.0" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 http://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <groupId>io.tidepool</groupId>
  <artifactId>tidepool-lib-archetype</artifactId>
  <version>1.0.0-SNAPSHOT</version>
  <packaging>maven-archetype</packaging>

  <name>tidepool-lib-archetype</name>

  <build>
    <extensions>
      <extension>
        <groupId>org.apache.maven.archetype</groupId>
        <artifactId>archetype-packaging</artifactId>
        <version>3.4.1</version>
      </extension>
    </extensions>
  </build>
</project>

This is the POM that create-from-project wrote for the tidepool archetype built below. The extension is what gives the packaging its lifecycle; see Extensions for how build extensions work and Build Lifecycle for the phases it binds.

Generating a project

In batch mode

The goal that uses an archetype is archetype:generate, with the prefix archetype mapped to org.apache.maven.plugins:maven-archetype-plugin. Batch mode (-B, or -DinteractiveMode=false) takes everything from the command line:

mvn -B -ntp archetype:generate \
    -DarchetypeGroupId=org.apache.maven.archetypes \
    -DarchetypeArtifactId=maven-archetype-quickstart \
    -DarchetypeVersion=1.5 \
    -DgroupId=io.tidepool -DartifactId=tidepool-lib \
    -Dversion=1.0.0-SNAPSHOT -Dpackage=io.tidepool.lib

The parameters of the goal (from mvn archetype:help -Ddetail -Dgoal=generate on 3.4.1):

Property Default Meaning

archetypeGroupId, archetypeArtifactId, archetypeVersion

none

The coordinates of the archetype. When all are omitted the goal asks (interactive) or uses maven-archetype-quickstart (batch).

archetypeCatalog

remote,local

Comma-separated catalogs to search: remote, local or internal (see Catalogs).

filter

none

Narrows the list shown in interactive mode (see Filtering the list).

groupId, artifactId, version, package

version defaults to 1.0-SNAPSHOT; package to the group id

The coordinates of the new project. artifactId is also the name of the directory that is created, under outputDirectory.

outputDirectory

current directory

Where the project directory is created.

goals

none

Maven goals to run on the new project right after it was generated (see Running goals after generating).

interactiveMode

${settings.interactiveMode}, so false with -B

Whether to ask. Any other property that the archetype declares (such as junitVersion above) is also given as -Dname=value.

askForDefaultPropertyValues

false

Documented as asking also for properties that have defaults, in interactive mode. In a run with -DaskForDefaultPropertyValues=true on 3.10.0 it did not change the prompts: properties with defaults were still taken silently.

Source: Archetype Plugin: archetype:generate

The archetype itself accepts properties too: maven-archetype-quickstart:1.5 declares javaCompilerVersion (default 17) and junitVersion (default 5.11.0), and -DjavaCompilerVersion=21 -DjunitVersion=5.12.2 produced a POM with maven.compiler.release set to 21 and the JUnit BOM at 5.12.2.

Two behaviours of batch mode surprise people:

  • The directory must not exist. A second run for the same artifactId fails with A Maven project already exists in the directory /work/use/tidepool-boston, and nothing is overwritten.

  • Leaving out the archetype version is risky. With only -DarchetypeArtifactId=maven-archetype-quickstart, batch mode silently used the old 1.0 archetype, whose POM has no maven.compiler.release and depends on JUnit 3.8.1. The goal’s output said so only in one word: Using following parameters for creating project from Old (1.x) Archetype: maven-archetype-quickstart:1.0. Always pass archetypeVersion.

In interactive mode

Without -B and without archetype coordinates the goal lists the catalog and asks. The real list has thousands of entries (the remote catalog held 3767 on 2026-10-16), so you type a filter instead of a number:

mvn archetype:generate -Dfilter=org.apache.maven.archetypes: -DgroupId=io.tidepool -DartifactId=tp-inter -Dversion=1.0.0-SNAPSHOT

Filtering the list

Source: Archetype Plugin: Filtering to reduce archetype list

The filter is a case-sensitive contains match, either -Dfilter= on the command line or typed at the Choose a number or apply filter prompt:

Filter Shows

org.apache.maven.archetypes:

every archetype whose group id contains org.apache.maven.archetypes (14 entries on 2026-10-16)

:jee or jee

every archetype whose artifact id contains jee

org.apache:jee

group id contains org.apache and artifact id contains jee

A trap, found while testing: the prompt’s default is the quickstart archetype. If your filter hides it (for example -Dfilter=org.apache.maven.archetypes:site-simple leaves one entry), pressing Enter does not choose the single remaining entry; the goal prints the list again and asks again, and with input from a closed pipe it loops without end, printing the same list. Type the number (1), or use a filter that keeps maven-archetype-quickstart in the list.

The archetypes Maven provides

Source: Maven: Introduction to Archetypes, Provided Archetypes

The guide lists ten archetypes under the group id org.apache.maven.archetypes. The catalog of 2026-10-16 listed fourteen with that group id. The ones that matter:

Artifact id Generates

maven-archetype-quickstart

A jar project with App and AppTest (JUnit 5 in 1.5, JUnit 3.8.1 in 1.0); the one used by almost every tutorial.

maven-archetype-simple

A simple Maven project (the catalog’s description); same group id.

maven-archetype-archetype

A sample archetype project: the quickest way to start writing your own (see Starting an archetype from a template).

maven-archetype-webapp

A war project (see Packaging JARs, WARs & Manifests).

maven-archetype-plugin, maven-archetype-mojo

A sample Maven plugin project (see Writing Plugins).

maven-archetype-site, maven-archetype-site-simple, maven-archetype-plugin-site

Site sources, meant to be layered on an existing project (see Site & Reporting).

maven-archetype-j2ee-simple, maven-archetype-portlet

Old Java EE and portlet samples; not maintained for current platforms.

maven-archetype-profiles, maven-archetype-marmalade-mojo

In the catalog (without a description) but missing from the guide’s table.

The archetypes of other projects (frameworks, vendors) live in the same catalog under their own group ids, which is why a filter is needed.

Catalogs

An archetype is found through an archetype catalog: an archetype-catalog.xml that lists group id, artifact id, version and description of archetypes. -DarchetypeCatalog takes a comma-separated list of these schemes (default remote,local):

Scheme Meaning

remote

The archetype-catalog.xml at the root of a repository: the repository with the id archetype if you defined one, otherwise Maven Central (id central) or the first mirror of either (see Repositories, Mirrors & Repository Managers).

local

The archetype-catalog.xml at the root of your local repository, kept up to date by mvn install of an archetype project.

internal

A small catalog built into the plugin: ten entries, all of the org.apache.maven.archetypes group (no simple, mojo, marmalade-mojo or profiles; still spelled simplifed in the J2EE description).

Source: Archetype Plugin: archetypeCatalog

The default merges remote and local, which is why an archetype you installed yourself is found without extra options: running the batch command with the coordinates of the tidepool archetype (built below) but without -DarchetypeCatalog generated a project, with the Maven Central catalog consulted as well. Internally the catalog is the fallback: if the remote catalog is empty or cannot be read, the goal says so and uses internal.

A request for an archetype that no consulted catalog lists does not stop at once. -DarchetypeCatalog=local and a wrong artifact id gives The desired archetype does not exist (io.tidepool:nope:1.0); with the default catalogs the goal first prints Archetype not found in any catalog. Falling back to central repository. and then tries to resolve the coordinates from Maven Central. Note that the missing version was filled in as 1.0.

Serving a catalog from your own repository

A company that distributes archetypes needs a repository where archetype-catalog.xml lives next to the artifacts. The goal looks for a repository with the id archetype. The recommended way (from the plugin documentation) is to put that repository in a profile that is not active by default, so that normal builds do not download from it, and to activate the profile only when generating:

<settings xmlns="http://maven.apache.org/SETTINGS/1.2.0">
  <profiles>
    <profile>
      <id>tidepool-archetypes</id>
      <repositories>
        <repository>
          <id>archetype</id>
          <url>http://localhost:19473/</url>
        </repository>
      </repositories>
    </profile>
  </profiles>
</settings>

If the repository needs credentials, add a <server> with the same id archetype (see Settings.xml & Password Encryption). To test it without a repository manager, a read-only static file server on localhost is enough: here the local repository of the build that installed the archetype was served with python3 -m http.server 19473 --bind 127.0.0.1 (a repository manager such as Nexus, Artifactory or Reposilite would be the production choice; none was installed, so that case is not run here):

mvn -B -ntp -s settings-archetype.xml -Ptidepool-archetypes archetype:generate \
    -DarchetypeCatalog=remote -Dfilter=io.tidepool: \
    -DarchetypeGroupId=io.tidepool -DarchetypeArtifactId=tidepool-lib-archetype -DarchetypeVersion=1.0.0-SNAPSHOT \
    -DgroupId=io.tidepool -DartifactId=tidepool-remote -Dpackage=io.tidepool.remote
[INFO] Generating project in Batch mode
[WARNING] Could not validate integrity of download from http://localhost:19473/archetype-catalog.xml: no checksums available
[INFO] Archetype repository not defined. Using the one from [io.tidepool:tidepool-lib-archetype:1.0.0-SNAPSHOT] found in catalog remote
[WARNING] Could not validate integrity of download from http://localhost:19473/io/tidepool/tidepool-lib-archetype/1.0.0-SNAPSHOT/tidepool-lib-archetype-1.0.0-SNAPSHOT.jar: no checksums available

Creating and refreshing a catalog file

Two more goals work on catalog files:

  • archetype:update-local-catalog adds the archetype of the current project to the local catalog. It is bound to the maven-archetype lifecycle (after install), so you rarely call it. After the install below the local repository’s archetype-catalog.xml held:

    <archetype-catalog ...>
  <archetypes>
    <archetype>
      <groupId>io.tidepool</groupId>
      <artifactId>tidepool-lib-archetype</artifactId>
      <version>1.0.0-SNAPSHOT</version>
      <description>tidepool-lib-archetype</description>
    </archetype>
  </archetypes>
</archetype-catalog>

  • archetype:crawl walks a repository on the file system (not HTTP) and writes a catalog of every archetype JAR it finds, for you to publish at the root of a repository: mvn archetype:crawl -Dcatalog=/work/crawl/archetype-catalog.xml -Drepository=/work/m2. It printed a Scanning line for each of the more than a hundred JARs of that scratch repository, and wrote a catalog with maven-archetype-quickstart, maven-archetype-site-simple and the tidepool archetype (the three JARs that contain an archetype descriptor).

Source: Archetype Plugin: archetype:crawl

Source: Archetype Plugin: archetype:update-local-catalog

Running goals after generating

-Dgoals makes the plugin invoke Maven on the new project once it exists, which is useful in scripts:

mvn -B -ntp archetype:generate -DarchetypeGroupId=org.apache.maven.archetypes -DarchetypeArtifactId=maven-archetype-quickstart \
    -DarchetypeVersion=1.5 -DgroupId=io.tidepool -DartifactId=goals2 -Dgoals=verify

Creating an archetype

From an existing project

The archetype plugin can turn a working project into an archetype. That is how the tidepool archetype was made: a small project from the quickstart archetype, with two files added to it:

tidepool-lib
|-- README.md                                # Built as io.tidepool:tidepool-lib.
|-- pom.xml
`-- src
    |-- main
    |   |-- java/io/tidepool/lib/{App.java, Station.java}
    |   `-- resources/stations.csv
    `-- test/java/io/tidepool/lib/AppTest.java

Run the goal in that project (it does not need a lifecycle; it reads the project and writes files):

mvn -B -ntp -s /work/settings.xml archetype:create-from-project

[INFO] Setting default package: io.tidepool.lib

The -s /work/settings.xml is not decoration. After writing the archetype project, the goal starts a nested Maven build of it (default phase package, the parameter archetypePostPhase) and passes it the path of the user settings file, ~/.m2/settings.xml, even if that file does not exist. Without the option the goal wrote the archetype project and then failed with:

[ERROR] Error executing Maven.

and what it did to the files:

  • It read the coordinates of the project and replaced them with properties: in the prototype POM <groupId>io.tidepool</groupId> became <groupId>${groupId}</groupId>, likewise artifactId and version, and <name>tidepool-lib</name> became <name>${artifactId}</name>.

  • It detected the base package of the sources (io.tidepool.lib), removed it from the directory names (src/main/java/App.java) and replaced package io.tidepool.lib; with package ${package}; in every source. In the project generated later, the files go under whatever -Dpackage says.

  • It put a Velocity header on each filtered file that defines $symbol_pound, $symbol_dollar and $symbol_escape, so that a literal # or $ in your file can be written as ${symbol_pound}, ${symbol_dollar}: Velocity treats those characters as syntax.

  • It wrote a first integration test (src/test/resources/projects/basic), see Testing the archetype.

The goal does not know which of your files are templates. It filtered .java and the POM, but it copied stations.csv and README.md as they were, so the README of every generated project would still say tidepool-lib. Turning a copy into a template is what the next part is for.

The archetype descriptor

The descriptor is src/main/resources/META-INF/maven/archetype-metadata.xml. Its elements, from the reference page:

Element or attribute Meaning

archetype-descriptor@name

The name shown to the user while choosing.

archetype-descriptor@partial

true for an archetype that adds files to an existing project instead of making a whole one. Default false.

requiredProperties/requiredProperty@key

A property the user must supply. Children: defaultValue, and (since descriptor 1.1.0) validationRegex.

fileSets/fileSet

A group of files: directory, includes, excludes, and the attributes filtered (treat the files as Velocity templates; default false), packaged (put the files under the package directory; default false), encoding, and (since 1.2.0) includeCondition: a Velocity expression that includes the file set only when it is true.

The generated descriptor listed every file group but had no required properties and did not filter the README or the CSV. After editing, the descriptor of the tidepool archetype is:

<archetype-descriptor name="tidepool-lib"

    <requiredProperty key="defaultStation">
      <defaultValue>SF</defaultValue>

  </requiredProperties>
  <fileSets>

Source: Archetype Descriptor reference: requiredProperty

The changes against the generated file: the requiredProperties block, filtered="true" on the CSV and README sets, and a new docs set. The prototype files that go with it:

README.md
# ${artifactId}

Built as ${groupId}:${artifactId}:${version}, default station ${defaultStation}.
src/main/resources/stations.csv
id,name,latitude,longitude
${defaultStation},Default station,0.0,0.0
The docs file (its name carries the property between double underscores)
Default station: ${defaultStation}

How filtering and naming work:

  • In a filtered set every file is a Velocity template: ${name} is replaced by the property, and #set, #if, #foreach directives work. A $ or # that must stay needs the ${symbol_dollar}/${symbol_pound} variables from the header that create-from-project added. This is Velocity, not the Resources Plugin: the @name@ delimiter, filter files and the other rules of Resources & Filtering do not apply.

  • A file or directory name that contains __name__ has that part replaced by the property’s value, filtered or not: docs/__defaultStation__.txt became docs/BOS.txt.

  • packaged="true" prepends the package directory (io/tidepool/boston) to the paths of the set; packaged="false" keeps the paths as they are.

  • The descriptor cannot create an empty directory ("one can only specify individual files"); put a placeholder file in it.

  • Only the files that the includes/excludes patterns (**/*.java) select are part of the archetype. A file that no set matches is silently left out.

Source: Maven: Guide to Creating Archetypes, prototype files

What validationRegex does and does not do

Declared as [A-Z]{2,4} on defaultStation, the check was exercised on 3.10.0 in four ways, against the archetype with a default (SF) and against a copy of it without a default (tidepool-strict-archetype):

generated

generated

[WARNING] Property defaultStation is missing. Add -DdefaultStation=someValue, then Failed to execute goal ... :generate (default-cli) on project standalone-pom: Archetype io.tidepool:tidepool-strict-archetype:1.0.0-SNAPSHOT is not configured.

A property that has a default and is not given in batch mode silently takes the default: the first batch run of the default-carrying archetype without -DdefaultStation produced README.md saying "default station SF" and no error.

Testing the archetype

create-from-project wrote src/test/resources/projects/basic with archetype.properties (the values for a throw-away project: groupId=archetype.it, artifactId=basic, package=it.pkg, version=0.1-SNAPSHOT) and an empty goal.txt. They are the input of the archetype:integration-test goal, which the maven-archetype lifecycle runs in the integration-test phase: for each directory under src/test/resources/projects it generates a project from the archetype just built, runs the goals listed in goal.txt on it, and then runs an optional verify.groovy. A reference/ directory with an expected tree can also be compared; that option was not run here.

The Groovy catch on a new JDK

verify.groovy and the post-generation script are Groovy, run by the Groovy that the plugin carries (4.0.28 in the local repository of these runs). That Groovy cannot read class files of JDK 26. With verify.groovy added to the IT:

def project = new File(basedir, "project/basic")
assert new File(project, "src/main/java/it/pkg/Station.java").isFile()
assert new File(project, "src/main/resources/stations.csv").text.contains("NY,Default station")
assert new File(project, "README.md").text.contains("archetype.it:basic:0.1-SNAPSHOT")

the build on JDK 26 failed in the integration-test phase:

[INFO] run post-build script verify.groovy
[INFO] Running post-build script: /work/tidepool-archetype/target/test-classes/projects/basic/verify.groovy
[ERROR] BUILD FAILURE
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-archetype-plugin:3.4.1:integration-test (default-integration-test) on project tidepool-lib-archetype:
[ERROR] Archetype IT 'basic' failed: post build script failure failure: BUG! exception in phase 'semantic analysis' in source unit 'Script1.groovy' Unsupported class file major version 70

The same build with JAVA_HOME set to JDK 21 ran the script, passed, and installed the archetype. Unsupported class file major version 70 is the signature of that mismatch (major version 70 is Java 26). To share the archetype, publish it like any other artifact. The archetype project is an ordinary Maven project, so mvn deploy with a distributionManagement repository (see Install, Deploy & Distribution Management) puts the JAR and POM on your repository, and a catalog file at its root, written by archetype:crawl, makes it listable. Publishing an archetype to Maven Central follows the same rules as any library (see Publishing to Maven Central); that step is not run here.

The post-generation script

META-INF/archetype-post-generate.groovy in the archetype JAR (the file src/main/resources/META-INF/archetype-post-generate.groovy in the archetype project) runs after the project was written. It sees a variable request (the generation request) in addition to the properties. This script writes a file with the chosen station:

def project = new File(request.getOutputDirectory(), request.getArtifactId())
new File(project, "STATION.txt").text = "Default station: " + request.getProperties().getProperty("defaultStation") + "\n"
println "post-generate: wrote STATION.txt in " + project.name
[INFO] Executing META-INF/archetype-post-generate.groovy post-generation script
post-generate: wrote STATION.txt in pg-21
[INFO] BUILD SUCCESS

(Run with -DartifactId=pg-21 on JDK 21; the project directory then held README.md STATION.txt pom.xml src.) On JDK 26 the same archetype failed after the files had been written:

[INFO] Executing META-INF/archetype-post-generate.groovy post-generation script
[ERROR] BUILD FAILURE
Exception in thread "main" BUG! exception in phase 'semantic analysis' in source unit 'Script1.groovy' Unsupported class file major version 70
...
Caused by: java.lang.IllegalArgumentException: Unsupported class file major version 70

and the half-generated project (README.md pom.xml src, without the file the script would have added) was left on disk, so a retry fails with "A Maven project already exists" until you delete it. That is the practical argument for keeping post-generation scripts rare: they run on the JDK of whoever generates a project, not on the JDK you tested with.

Removed: archetype:create, and where the documentation is out of date

  • archetype:create is gone. On Maven 3.10.0 it fails with Could not find goal 'create' in plugin org.apache.maven.plugins:maven-archetype-plugin:3.4.1 among available goals crawl, create-from-project, generate, help, integration-test, jar, update-local-catalog. The goals the plugin has are exactly these seven. Books and older blog posts that use create need generate.

  • The Advanced Usage page of the plugin still shows a 2008-era console (task-segment, BUILD SUCCESSFUL, an archetype:add-archetype-metadata goal that no longer runs). The goal names and the three-step flow (create-from-project, install, generate) are still right; the output is not what you see today.

  • The Guide to Creating Archetypes shows a prototype POM with JUnit 4.12 (the current quickstart imports the JUnit 5 BOM) and says that a missing -DarchetypeVersion may fail with a message that version:RELEASE was not found (3.4.1 names version 1.0).

  • The guide’s table of provided archetypes lists ten; the catalog has fourteen with that group id (see The archetypes Maven provides).

  • The create-from-project documentation says to put integration tests in src/it/projects; the goal, as run here, wrote the generated one to src/test/resources/projects/basic, which is where archetype:integration-test looks (testProjectsDirectory defaults to target/test-classes/projects).

The same idea in Ant and Gradle

Ant has no equivalent: a project template is a directory that you copy, or a shell script. Gradle’s counterpart is the init task, which generates a project from built-in types, and there is no per-organization template format in core Gradle (organizations write a plugin or use a template repository). The three tools are compared in Comparing Ant, Maven & Gradle. That Gradle sentence is background, not something run on this page.
