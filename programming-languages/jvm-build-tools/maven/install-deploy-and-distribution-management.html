Install, Deploy & Distribution Management

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Maven 3.10.0 with the Apache Maven Install Plugin 3.2.0, the Apache Maven Deploy Plugin 3.2.0, the Source Plugin 3.4.0, the Javadoc Plugin 3.12.0 and the Site Plugin 3.22.0. Every example marked as run was executed on JDK 26 on 2026-10-16 in scratch copies of the tidepool project (the parent io.tidepool:tidepool-parent with tidepool-model, tidepool-engine and tidepool-cli). Maven 3.9.16 and Maven 4.0.0-rc-7 (a release candidate) were run wherever the page says so. In the output, <lab> is the scratch directory, <proj> is the directory of the project being built, the local repository was <lab>/m2 (set with -Dmaven.repo.local, so the real ~/.m2/repository was not used), lines were filtered with grep (said each time), transfer sizes and speeds were cut, and the timestamp of a snapshot upload is written TS because it changes on every run. Nothing was published to a real server. The repositories were directories reached through file: URLs, and, for credentials, a small Python HTTP server on localhost that is described below. Publishing to Maven Central is on Publishing to Maven Central and is "not run here".

Building an artifact is only half of a build’s job; the other half is making it available to somebody else. Maven splits that into two steps that are easy to confuse. Install copies the result into the local repository of the machine, so that other projects built on the same machine can use it. Deploy uploads it to a remote repository, so that the rest of the world can. The address of that remote repository is not a property of the plugin but of the project, and lives in the POM element distributionManagement. This page covers the two plugins, that element, the credentials a remote repository asks for, what exactly gets written, and what changed in Maven 3.10 and Maven 4. The repositories themselves (layout, mirrors, managers) are on Repositories, Mirrors & Repository Managers; settings.xml and encrypted passwords on settings.xml & Password Encryption; the release process that ends in a deploy on Releasing. The scenario is on the section landing page.

Where install and deploy sit

install and deploy are the last two phases of the default lifecycle (the others are on Build Lifecycle). Each is a phase with one default binding, and both are bound to the goal of the same name for every packaging that produces an artifact:

Phase Default goal What it does

package

jar:jar for a JAR

Builds the artifact in target/; it is not copied anywhere yet.

verify

none for most packagings

Where checks on the package (integration tests, quality gates) belong.

install

install:install

Copies the project’s artifacts into the local repository.

deploy

deploy:deploy

Uploads the project’s artifacts to the remote repository named in distributionManagement.

A phase runs every phase before it, so mvn deploy also installs; there is no way to deploy without installing except by calling the goal directly (mvn deploy:deploy, which needs an already built package) or skipping the install (below).

flowchart LR PKG["package: target/*.jar"] --> VER["verify"] VER --> INS["install:install"] INS --> LOCAL[("local repository (default: user home .m2/repository)")] INS --> DEP["deploy:deploy"] DEP --> REL["distributionManagement/repository (release versions)"] DEP --> SNAP["distributionManagement/snapshotRepository (SNAPSHOT versions)"] SITE["site:deploy (separate goal)"] --> STE["distributionManagement/site"]

The diagram shows the two uploads that deploy:deploy chooses between by the version of the project, and the site, which is not part of the default lifecycle and has its own goal.

Source: Maven: Introduction to the Build Lifecycle

The lab: tidepool with a distributionManagement

The parent POM of the lab pins the plugins in pluginManagement (which is why the versions above are known, see Maven Plugins & Their Configuration) and declares two repositories. Their URLs are built from a property, so that a command line can point the same POM somewhere else, and the base is a directory inside the project:

pom.xml (parent, abridged)
  <properties>
    <repo.url>file://${maven.multiModuleProjectDirectory}/build/repo</repo.url>
  </properties>

  <distributionManagement>
    <repository>
      <id>tidepool-releases</id>
      <url>${repo.url}/releases</url>
    </repository>
    <snapshotRepository>
      <id>tidepool-snapshots</id>
      <url>${repo.url}/snapshots</url>
    </snapshotRepository>
  </distributionManagement>

${maven.multiModuleProjectDirectory} is the directory that contains the .mvn directory (or the directory Maven was started in, when there is none), and it exists on 3.9.16, 3.10.0 and 4.0.0-rc-7. Maven 3.10 and 4 also have ${project.rootDirectory}, but 3.9.16 leaves that expression unresolved in a URL, so the older name is the portable one (see Inheritance, Aggregation & the Effective POM). The id values, not the URLs, are what links the repository to the credentials in settings.xml.

Source: Maven: POM Reference, Distribution Management

The parent installs only its POM, because a pom packaging has no JAR (the packaging is in POM Fundamentals). In the local repository a module looks like this (find tidepool-model -type f | sort):

There are no checksum files: the Install Plugin 3.2.0 writes none (a deploy does, below). _remote.repositories is a record of where each file came from, kept by Maven Resolver:

#NOTE: This is a Maven Resolver internal implementation file, its format can be changed without prior notice.
tidepool-model-1.0.0-SNAPSHOT.jar>=
tidepool-model-1.0.0-SNAPSHOT.pom>=

The >= with nothing after it means the file was put there by an install, from no repository; a file downloaded from the repository with the id central reads >central=, and Resolver then uses it only for builds that list that repository (the effect is on Repositories, Mirrors & Repository Managers). maven-metadata-local.xml is the local version of the metadata that a remote repository keeps, here for a snapshot:

<?xml version="1.0" encoding="UTF-8"?>
<metadata modelVersion="1.1.0">
  <groupId>io.tidepool</groupId>
  <artifactId>tidepool-model</artifactId>
  <versioning>
    <lastUpdated>TIMESTAMP</lastUpdated>
    <snapshot>
      <localCopy>true</localCopy>
    </snapshot>
    <snapshotVersions>
      <snapshotVersion>
        <extension>pom</extension>
        <value>1.0.0-SNAPSHOT</value>
        <updated>TIMESTAMP</updated>
      </snapshotVersion>
      <snapshotVersion>
        <extension>jar</extension>
        <value>1.0.0-SNAPSHOT</value>
        <updated>TIMESTAMP</updated>
      </snapshotVersion>
    </snapshotVersions>
  </versioning>
  <version>1.0.0-SNAPSHOT</version>
</metadata>

(TIMESTAMP replaces the install time, which changes on every run.) localCopy tells the resolver that this snapshot is a copy that was installed locally, not downloaded from a timestamped build in a remote repository.

distributionManagement

distributionManagement says where the outputs of this project go. It is not to be confused with <repositories>, which says where the project’s inputs come from. The element has these children:

Element Meaning

repository

Where release versions are uploaded. Children: id, name, url, layout, uniqueVersion.

snapshotRepository

Where -SNAPSHOT versions are uploaded. If it is absent, repository is used for snapshots too.

site

Where site:deploy uploads the generated site (id, name, url), see below.

relocation

Tells consumers that the artifact moved to other coordinates.

downloadUrl

A page where users can download the artifact, for people; no tool reads it.

status

The status of the artifact in the remote repository (none, converted, partner, deployed, verified). The reference says never to write it by hand, because Maven sets it when the project is transported to the repository.

The layout (default or legacy) and uniqueVersion children date from Maven 2. Maven 3 supports only the default layout, and uniqueVersion is ignored: a run with <uniqueVersion>false</uniqueVersion> in the repository, on a project without a snapshotRepository, still wrote a timestamped file with a build number (see the next section).

The id is the link to the credentials

The <id> of a repository, snapshotRepository or site is the name that Maven looks up in the <servers> of settings.xml for the user name and password (below). The id is arbitrary, but it identifies the repository among all the others of the build, so it must be unique. A typo in the id does not fail the build: the upload is simply attempted without credentials, and a protected repository answers 401.

snapshotRepository is optional

Without a snapshotRepository, a snapshot version is sent to repository. Removing it from the lab and deploying tidepool-model (filtered with grep -E "Uploaded to.*(jar|pom) |BUILD") printed:

[INFO] Uploaded to tidepool-releases: file://<proj>/build/repo/releases/io/tidepool/tidepool-model/1.0.0-SNAPSHOT/tidepool-model-1.0.0-TS-1.pom
[INFO] Uploaded to tidepool-releases: file://<proj>/build/repo/releases/io/tidepool/tidepool-model/1.0.0-SNAPSHOT/tidepool-model-1.0.0-TS-1.jar
[INFO] BUILD SUCCESS

The files of a snapshot landed under releases, which is a trap: a repository manager that keeps release and snapshot repositories apart may reject the upload. Keep both elements.

No distributionManagement at all

A project without the element cannot be deployed by the lifecycle. Deploying the same module from a POM without it failed in the Deploy Plugin, after the build had succeeded:

[ERROR] Failed to execute goal org.apache.maven.plugins:maven-deploy-plugin:3.2.0:deploy (default-deploy) on project tidepool-model: Deployment failed: repository element was not specified in the POM inside distributionManagement element or in -DaltDeploymentRepository=id::url parameter -> [Help 1]

The message names the two ways out, the POM element and the altDeploymentRepository parameter described below.

Source: Maven: POM Reference, Distribution Management

Checksums

For every file Maven also uploads a checksum, by default .sha1 and .md5. They are the hash of the bytes sent, so a consumer (or a repository manager) can detect corruption:

$ cat tidepool-model-1.0.0-TS-1.jar.sha1
4323ad73b2363318d68170288e32a1c41bd8d42b
$ shasum -a 1 tidepool-model-1.0.0-TS-1.jar
4323ad73b2363318d68170288e32a1c41bd8d42b  tidepool-model-1.0.0-TS-1.jar

The algorithms are a Maven Resolver setting, aether.checksums.algorithms, a comma-separated list that defaults to SHA-1,MD5. A deploy with -Daether.checksums.algorithms=SHA-1,SHA-256,SHA-512,MD5 on 3.10.0 listed (ls | grep jar):

tidepool-model-1.0.0-TS-1.jar
tidepool-model-1.0.0-TS-1.jar.md5
tidepool-model-1.0.0-TS-1.jar.sha1
tidepool-model-1.0.0-TS-1.jar.sha256
tidepool-model-1.0.0-TS-1.jar.sha512

The same property with SHA-1,SHA-256 also worked on Maven 3.9.16 and 4.0.0-rc-7. Central requires .md5 and .sha1 files and accepts the stronger ones in addition (see Publishing to Maven Central); the verification a consumer can do with them is on Supply Chain Security.

Maven 3.10: credentials are scoped to an origin

According to the release notes of 3.10.0, the credentials of a server are sent only to the origin (scheme, host and port) of the repositories and mirrors that have that id, and the match on the id is exact. Maven finds those repositories among the ones declared in settings.xml and on the command line; a distributionManagement repository of the POM is not among them in these runs, because the warning appeared for the tidepool-releases id that the POM itself declares. To bind the credentials explicitly, name the origin in the server, which the same release notes document as repositoryOrigins (the full description is on the settings page):

settings-origins.xml (the snapshots server is the same)
    <server>
      <id>tidepool-releases</id>
      <username>deployer</username>
      <password>changeit-example</password>
      <repositoryOrigins>
        <repositoryOrigin>http://localhost:18090</repositoryOrigin>
      </repositoryOrigins>
    </server>

HTTP Status: 400 here is the lab’s imitation of a repository manager that does not allow redeploying a release. A plain file repository (file:) has no such rule and overwrites silently, so a local test does not catch a pipeline that redeploys a release. The rule is right: a consumer that cached 1.0.0 must never see different bytes under that name. The way out is a new version, not a deploy of the same one (see Releasing).

Other transports and how the password is protected

file: and http:/https: work with the native HTTP transport of Maven 3.9 and later. scp:, sftp: and ftp: need a Wagon provider added as a build extension, which the repositories page describes as "Transports: native and Wagon"; they were not run here, and their privateKey and passphrase settings are in the server table of the settings page. The password in the file should be encrypted with the master-password mechanism of Maven 3 or mvnenc of Maven 4 (the settings page runs both), or come from an environment variable in the CI job.

Classic problems

  • HTTP Status: 401 on deploy. No <server> with the right <id>, a wrong password, or a password encrypted with a master password the build cannot read. Check the id of distributionManagement against settings.xml, and the log of the server.

  • HTTP Status: 400 or 409 on the second deploy of a release. The repository does not allow redeploying a release. Release a new version.

  • repository element was not specified in the POM. No distributionManagement and no altDeploymentRepository.

  • The snapshots end up in the releases repository, or are rejected: no snapshotRepository.

  • deploy-file uploads a POM with other coordinates. The JAR has an embedded pom.xml; pass -DpomFile.

  • Some modules were deployed and the build failed. The default deploys per module; use deployAtEnd, and know it is not atomic.

  • Unrecognized value ... for maven.deploy.skip. The value must be true, false, releases or snapshots.

  • A deploy from a CI job overwrites a developer’s snapshot. Snapshots are shared by design; use CI-friendly versions that put the commit in the version (see CI-Friendly Versions).

  • A POM with ${revision} is published unresolved on Maven 3. See the same page.

  • A plugin 4.0 line on Maven 3. has unmet prerequisites, above.

Where the books are outdated

  • Older books describe deploy:deploy with the layout in altDeploymentRepository (id::default::url), the layout and uniqueVersion children of distributionManagement, and SCP or WebDAV as the normal transports. Maven 3 has one layout, ignores uniqueVersion, uses the native HTTP transport and needs a Wagon extension for SCP and FTP.

  • Plain http: repository URLs for downloads are blocked by default since Maven 3.8.1 (the settings and repositories pages); uploads to localhost over HTTP, as here, are for tests.

  • Publishing to Central through OSSRH (oss.sonatype.org) ended on 2025-06-30; see Publishing to Maven Central.

  • The release-profile of the super POM, which added sources and Javadoc JARs to a release, is removed in Maven 3.10 (see Releasing); attach them with the executions shown above.

What was not run here

  • Any real repository manager, Central, or an authenticated remote server other than the localhost lab server; the scp, sftp and ftp transports with Wagon extensions; privateKey authentication.

  • retryFailedDeploymentCount, allowIncompleteProjects, installAtEnd combined with failing builds, and the status and downloadUrl elements of distributionManagement.

  • The test JAR (test-jar) and assembly attachments (shown on the pages named above).
