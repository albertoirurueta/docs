Migrating to Maven 4

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page migrates a real, small Maven 3 project to Maven 4 and records everything that went wrong on the way. It follows the three steps of the official migration guide: prepare on the latest Maven 3, test with Maven 4 using only changes that Maven 3 still accepts, and migrate by dropping Maven 3 and adopting the Maven 4 features, with the help of the Maven Upgrade Tool mvnup. Maven 4.0.0-rc-7 is a release candidate, not a final release: the guide itself says it will keep changing, and no 4.0.0 had been published when this page was written (see Maven Versions & Release History). Everything shown was run on 2026-10-16 with Maven 3.9.16, Maven 3.10.0 and Maven 4.0.0-rc-7, on JDK 26 (JDK 17 where stated), against a scratch local repository so that nothing touched ~/.m2. Paths in the output were shortened to /work/... and the lines Loaded N auto-discovered prefixes ... that rc-7 prints on its first contact with each repository were filtered out; other trimming is marked.

What is new in Maven 4, and why, is on Maven 4: What’s New, the model changes are on Maven 4: POM Model & Consumer POM and the lifecycle on Maven 4: Lifecycle. This page does not repeat them; it shows the steps of moving a project and the failures you will meet. Books about Maven were written for Maven 2 and 3 and say nothing about any of this; the official guide is the only source that is kept up to date, and it says so about itself.

flowchart LR P["Step 1, prepare: latest Maven 3.9 or 3.10 and latest Maven 3 plugins"] T["Step 2, test: JDK 17 and Maven 4 beside Maven 3, build POM stays 4.0.0"] M["Step 3, migrate: drop Maven 3, model 4.1.0, mvnup apply"] P --> T --> M

The project that gets migrated

The project is tidepool: a parent POM and three subprojects, tidepool-model (a Java record), tidepool-engine and tidepool-cli, built for Java 17. It is committed to a scratch git repository so that every change below is a git diff. It is written the way a Maven 3 project of a few years ago often is, so that it carries the problems the guide lists:

  • the CLI POM declares maven-jar-plugin twice;

  • a script of the engine binds maven-antrun-plugin to pre-integration-test, and one of the model binds it to post-clean;

  • maven-antrun-plugin is at 3.1.0, and every other plugin version is pinned in the parent;

  • there is no .mvn directory and no root attribute;

  • the install and deploy plugins are the Maven 3 lines (3.2.0), and the deploy target is a file: repository below the project.

Step 1: prepare on the latest Maven 3

The guide’s first step has two prerequisites: the project builds with the latest Maven 3, and it uses the latest Maven 3 versions of its plugins (and, it adds, not yet a plugin version that needs Maven 4). Nothing in this step needs Maven 4, but it is where the first failure appears, and it appears earlier than the guide suggests.

Maven 3.9.16 warns, Maven 3.10.0 fails

The same project, the same command, the two Maven 3 lines:

Maven 3.9.16: mvn clean verify
[INFO] Scanning for projects...
[WARNING]
[WARNING] Some problems were encountered while building the effective model for io.tidepool:tidepool-cli:jar:1.0.0-SNAPSHOT
[WARNING] 'build.plugins.plugin.(groupId:artifactId)' must be unique but found duplicate declaration of plugin org.apache.maven.plugins:maven-jar-plugin @ line 37, column 15
[WARNING]
[WARNING] It is highly recommended to fix these problems because they threaten the stability of your build.
[WARNING]
[WARNING] For this reason, future Maven versions might no longer support building such malformed projects.

The build then succeeds (BUILD SUCCESS), and the jar manifest has the Main-Class of the first declaration: Maven 3.9 merged the two declarations itself. Maven 3.10.0 does not:

Maven 3.10.0: mvn clean verify
[INFO] Scanning for projects...
[ERROR] [ERROR] Some problems were encountered while processing the POMs:
[ERROR] 'build.plugins.plugin.(groupId:artifactId)' must be unique but found duplicate declaration of plugin org.apache.maven.plugins:maven-jar-plugin @ line 37, column 15
 @
[ERROR] The build could not read 1 project -> [Help 1]
[ERROR]
[ERROR]   The project io.tidepool:tidepool-cli:1.0.0-SNAPSHOT (/work/tidepool-cli/pom.xml) has 1 error
[ERROR]     'build.plugins.plugin.(groupId:artifactId)' must be unique but found duplicate declaration of plugin org.apache.maven.plugins:maven-jar-plugin @ line 37, column 15

This is documented: the Maven 3.10.0 release notes list "Stricter POM validation" among the changes that can break a build coming from 3.9.x ("many WARNINGs from the 3.9 lineage …​ will now FAIL the build"), with duplicated dependency entries and duplicated plugin entries as the examples. The practical consequence for a migration is that Maven 3.10.0 is the better Maven 3 to prepare on: it fails on what Maven 4 will fail on, while 3.9.16 only warns, so a project that is clean on 3.10.0 has already passed the first Maven 4 hurdle.

Source: Maven 3.10.0 Release Notes: Stricter POM validation

The fix is to merge the two declarations into one, which is what Maven 3.9 did silently:

             </manifest>
           </archive>
-        </configuration>
-      </plugin>
-      <plugin>
-        <artifactId>maven-jar-plugin</artifactId>
-        <configuration>

After the merge the project builds on 3.9.16 and on 3.10.0 (BUILD SUCCESS, tests 1 and 1), and the manifest of tidepool-cli carries Main-Class: io.tidepool.cli.Main.

Plugin versions: ask the plugins, not only the versions plugin

The guide recommends versions:display-plugin-updates of the Versions Maven Plugin to find the latest Maven 3 version of each plugin, and to avoid, for now, the versions that need Maven 4. Run on tidepool with versions-maven-plugin 2.23.0 on Maven 3.9.16, it separates the two groups by the Maven version each plugin release requires (excerpt, the older Maven 2 lines trimmed):

[INFO] All plugins with a version specified are using the latest versions.

[INFO]   maven-deploy-plugin ......................... 3.2.0 -> 4.0.0-beta-3

So on this project the Maven 3 lines of compiler, jar, resources, clean, install, deploy and surefire are the right ones for steps 1 and 2, and the 4.0.0-beta lines are the ones that need Maven 4 (they are pre-releases, not stable). The report has a blind spot, though. It said the specified plugins are "using the latest versions" while maven-antrun-plugin 3.1.0 was pinned and 3.2.0 had been on Central for a year. What flagged the old antrun was Maven’s own plugin validation, which is the other tool of this step:

Maven 3.10.0 and Maven 4.0.0-rc-7: -Dmaven.plugin.validation=verbose
[WARNING] Plugin [INTERNAL, EXTERNAL] validation issues were detected in following plugin(s)

[WARNING]    * Mojo antrun:run (org.apache.maven.plugins.antrun.AntRunMojo)

Maven 3.9.16 printed no such report with the same property, so this check also needs 3.10.0 or Maven 4. The cause is the Plexus injection that Maven 4 no longer promises to support (see the plugins section of the overview). The report suggests upgrading; maven-antrun-plugin 3.2.0 is a Maven 3 release (Central lists it from October 2025), and bumping the single version in the parent removed the report on both 3.10.0 and Maven 4 and left every build green on all three Maven versions. Plugin versions and configuration in general are on Plugins & Their Configuration.

Step 2: test on Maven 4

Java 17 to run Maven

Maven 4 needs Java 17 to run, while Maven 3.9 and 3.10 run on Java 8 and later. That is a statement about the JVM that runs Maven, not about the release your code compiles for, which stays 17 here but could stay 8 or 11 with a toolchain (Compiling & Toolchains). Everything on this page ran on JDK 26. Because Maven 3 also runs on JDK 17, the guide suggests moving the build machines (laptops, CI images, containers) to a JDK 17 first. The prepared project builds unchanged on JDK 17 (JetBrains Runtime 17.0.14) with Maven 3.10.0 and with rc-7:

$ JAVA_HOME=.../jbr-17.0.14/Contents/Home mvn -v
Apache Maven 4.0.0-rc-7 (6d8f301b38af7399b36b862969d520974944f0b9)
Maven home: /.../apache-maven-4.0.0-rc-7
Java version: 17.0.14, vendor: JetBrains s.r.o., runtime: /.../jbr-17.0.14/Contents/Home

Where Maven is selected is part of this step too: the distributionUrl in .mvn/wrapper/maven-wrapper.properties (Maven Wrapper), a requireMavenVersion enforcer rule (Enforcer), and the CI scripts. The recommended trial is a CI job that builds with Maven 4 beside the one that builds with Maven 3, reports Maven 4 failures as feedback and does not gate releases yet.

Source: Starting with Maven 4: Duplicate plugin declaration

The root directory warning

The first line of the output above is the next thing to fix. Maven 4 wants to know where the root of a multi-project build is, and warns when it cannot find out. There are two ways to tell it. A .mvn directory in the root works with Maven 3 too (a committed empty file keeps git from dropping the empty directory), and the root="true" attribute on the root <project> needs model version 4.1.0, so it is for step 3. For the test step use .mvn:

mkdir .mvn
touch .mvn/.gitkeep

There is a trap here that makes the warning disappear without anyone fixing anything. On a project without a .mvn directory, the first Maven 4 build prints the warning and then creates .mvn/target/project-local-repo itself, so the second build finds a .mvn directory and prints nothing:

$ git clone tidepool trap && mvn -B validate     # first run
[WARNING] Unable to find the root directory. Create a .mvn directory in the root directory or add the root="true" attribute on the root project's model to identify it.
[INFO] Scanning for projects...
$ mvn -B validate                                # second run, same checkout
[INFO] Scanning for projects...

The directory is ignored by a target/ rule in .gitignore, so git status shows nothing and the warning never comes back, while the checkout of a colleague or of CI still warns. Commit a real .mvn entry. What the root is used for follows.

Source: Starting with Maven 4: Define project’s root directory

Make the build fail on warnings

Maven 4’s --fail-on-severity (-fos) option turns log output of a given severity into a build failure and is the guide’s tool for finding what the build is complaining about. It fails before the .mvn fix and passes after it:

Maven 4.0.0-rc-7, mvn -B -fos WARN clean verify, without .mvn
[INFO] Enabled to break the build on log level WARN.
[WARNING] Unable to find the root directory. Create a .mvn directory in the root directory or add the root="true" attribute on the root project's model to identify it.
...
[ERROR] BUILD FAILURE
...
[ERROR] Build failed due to log statements with a higher severity than allowed. Fix the logged issues or remove flag --fail-on-severity (-fos).

With .mvn in place the same command ends in BUILD SUCCESS. Note that any plugin message logged at WARNING counts: the antrun scripts of tidepool print with <echo level="info"> for exactly this reason, because the default level of the Ant echo task is warning, and the first run of this experiment failed on the scripts' own messages. Keep -fos WARN for a CI trial, not as a permanent flag, until your plugins stop logging warnings for normal operation.

Directory properties: what resolves where

The guide says Maven 4 adds ${project.rootDirectory}, ${session.topDirectory} and ${session.rootDirectory} for paths, and that several internal properties, among them executionRootDirectory and multiModuleProjectDirectory, are deprecated or removed. "Not resolved" means the text stayed as written, ${...} included. Two lessons. The names the guide calls removed were never available to a POM in this form on the Maven 3 versions tested, so a POM that uses them either never worked or only worked through a plugin’s own expression evaluator; search for them. And the one spelling that works everywhere is the system property ${maven.multiModuleProjectDirectory}, which is why the tidepool deploy URL uses it. The Maven 3.10.0 release notes say session.topDirectory, session.rootDirectory and project.rootDirectory were promoted to regular properties; in this experiment only ${project.rootDirectory} was substituted in POM interpolation on 3.10.0, so test your own expressions before relying on the session.* names in a build that must also run on Maven 3. Replacing a hand-rolled root lookup with ${project.rootDirectory} worked on 3.10.0 and 4 in this experiment (the test project had a .mvn directory).

pre- and post- phases

The guide says the pre-integration-test, post-integration-test, pre-clean, post-clean and similar phases are replaced by before: and after: phases for every phase, and tells you to move bindings. In rc-7 the old names are still accepted: tidepool’s pre-integration-test and post-clean antrun bindings ran without any message. What changed is when a post-clean binding runs. On Maven 3 the clean phase stops before post-clean, so a script bound there ran only when you asked for it by name. On rc-7 it runs as part of every mvn clean:

Command (project with a post-clean binding) Maven 3.9.16 Maven 3.10.0 Maven 4.0.0-rc-7

mvn clean

script did not run

script did not run

script ran

mvn post-clean

script ran

script ran

script ran

A script that deletes or regenerates something at post-clean therefore starts firing on every clean build when the project moves to Maven 4. mvnup rewrites the phase names (see below); read the diff, since the new name does what rc-7 already does. The lifecycle tree and the before:/after: phases are on Maven 4: Lifecycle.

Source: Starting with Maven 4: Replace plugin bindings to pre- and post- lifecycle phase

Install and deploy at the end of the build

The guide marks as a breaking change that installAtEnd and deployAtEnd default to true in Maven 4: the artifacts of a multi-project build are installed or deployed together after every project has built, so a failure in a later subproject no longer leaves earlier ones half-published. The default belongs to the plugins, not to Maven 4 itself, and the plugin version decides. Pinned to the Maven 3 plugin lines (install 3.2.0), a Maven 4 build behaves like Maven 3. To make the difference visible, the test of tidepool-cli fails on request (-Dfail=true), so the last subproject breaks after model and engine have been built:

mvn install -Dfail=true with maven-install-plugin 3.2.0 Maven 3.9.16 Maven 3.10.0 Maven 4.0.0-rc-7

Step 3: migrate with mvnup

Step 3 drops Maven 3 and adopts the Maven 4 features. mvnup is shipped with Maven 4 from 4.0.0-rc-4 on and has two goals: check reports what it would change and writes nothing, and apply writes the changes. Its options, from mvnup --help of rc-7:

Option Meaning

-m, --model-version

target model version, 4.0.0 (the default, still buildable with Maven 3) or 4.1.0

-d, --directory

directory at which POM discovery starts (otherwise the current directory)

-a, --all

equivalent to --model-version 4.1.0 --infer --model --plugins

--model

fix constructs that are incompatible with Maven 4

--plugins

upgrade plugins known to fail with Maven 4 to the minimum compatible version

-i, --infer

remove information Maven 4 can infer (parent coordinates, subproject lists and similar)

-B, -q, -X, -s, -fos and others

the usual Maven batch, quiet, verbose and settings options

With no option, --model --plugins --infer apply and the model version stays 4.0.0. Run mvnup in the project directory: started from another directory with -d, it printed Project root directory and multiModuleProjectDirectory are not aligned before every strategy. Commit your work first so that git diff is the review tool.

What happened, item by item, and what to check:

  • Namespace, schema and model version. The modelVersion element is removed because Maven 4 infers it from the namespace. From now on Maven 3 cannot read these POMs.

  • <modules> removed. The list matched the direct child directories, so it is redundant: Maven 4 discovers subprojects. If a subproject must be excluded or lives elsewhere, use <subprojects>.

  • Parent coordinates trimmed. groupId, artifactId and version are inferred from the parent in the same project. The result <parent> followed by </parent> on the next line is valid but not pretty; <parent/> is the same thing.

  • Phase names. pre-integration-test became before:integration-test and post-clean became after:clean.

  • maven.compiler.release migrated to <sources>. This is the one that breaks the build, below.

The tool left alone what it does not understand or does not consider wrong: the dependency <version>${project.version}</version> entries (valid, though 4.1.0 can drop them for projects in the same reactor), the pinned plugin versions, the deploy URL, and it did not add root="true", since .mvn was already there.

  • The enforcer range. [3.6.3,4.0.0) is a trap on a release candidate: Maven 4.0.0-rc-7 sorts below 4.0.0, so the rule passed on rc-7 (Rule 0: ...RequireMavenVersion passed) and will fail on 4.0.0.   • Nashorn. Inline JavaScript in Ant scripts has not worked since Java 15 removed the engine, on any Maven version: the unmodified project failed on JDK 26 with Unable to create javax script engine for javascript on Maven 3.9.16 and on rc-7. After apply the same script prints answer=42 on rc-7. mvnup only added the engine as a plugin dependency, which its own log calls a quick fix and recommends GraalVM JavaScript for the long term.

The strategy for the toolchains plugin did nothing here, because --source 8 is accepted by the JDK used. It acts when the source level is too old for the JDK that runs Maven.

A checklist for your own project

  1. Build with Maven 3.10.0 (-Dmaven.plugin.validation=verbose) and fix every duplicate and every plugin report, in the POM and by upgrading plugins to their latest Maven 3 lines.

  2. Move the build machines to JDK 17 and keep building with Maven 3. Add a Maven 4 job that does not block releases.

  3. Commit a .mvn directory. Search the POMs for ${pom., executionRootDirectory, multiModuleProjectDirectory, pre- and post- phase names, installAtEnd and deployAtEnd.

  4. Run mvn -fos WARN verify with Maven 4 once and read what it complains about.

  5. Commit everything, run mvnup check --model-version 4.1.0 --all, then apply, and review the diff: duplicates, <sources> against the compiler plugin version, the phase names, the plugin versions.

  6. Build with Maven 4 on JDK 17 and on the JDK you ship with; update the wrapper, the CI images and the enforcer range at the same time. After this commit Maven 3 cannot build the project.

  7. Adopt the rest in small steps: CI-friendly versions without the flatten plugin, the bom packaging, root="true", the all and each phases.

  8. Keep the rc-7 caveat in mind: re-run the migration when 4.0.0 is released, since mvnup itself is still being fixed (the rc-7 release notes list several mvnup fixes).

Troubleshooting a build that still fails, with -e, -X and help:effective-pom, is on Troubleshooting & Best Practices.

Equivalents in Ant and Gradle

Apache Ant has no model version, no plugin versions and no lifecycle, so there is nothing to migrate in the Maven 4 sense; what changes between Ant lines is on Ant Deprecations & Migration. Gradle’s equivalent of a Maven major upgrade is a Gradle major upgrade, which is done in the same three steps (run the latest minor first, fix the deprecation warnings, then change the wrapper version), and ./gradlew wrapper plays the part of the Maven wrapper properties. Moving a project between the tools, rather than between versions, is on Migrating Between Tools, and the three tools are compared on Comparing Ant, Maven & Gradle.
