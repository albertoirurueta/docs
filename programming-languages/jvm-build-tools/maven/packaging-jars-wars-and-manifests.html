Maven Packaging: JARs, WARs & Manifests

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Apache Maven 3.10.0, maven-jar-plugin 3.5.1 (which uses Maven Archiver 3.6.6), maven-war-plugin 3.5.1 and maven-artifact-plugin 3.7.0. Every example was run on JDK 26 on 2026-10-16, in a scratch copy of the tidepool project (a parent POM and the tidepool-model, tidepool-engine and tidepool-cli modules, all compiled with maven.compiler.release 21 and every plugin version pinned). Where the behaviour differs, the same command was also run on Maven 3.9.16 and on Maven 4.0.0-rc-7 (a release candidate, not a final release). Paths in the console output were shortened to /work/packaging/..., and long console output was filtered with grep, which is said each time.

Packaging is the last step that is specific to the kind of project: the package phase of the build lifecycle turns target/classes into a file that can be installed, deployed or run. For <packaging>jar</packaging> (the default) the jar:jar goal does it, for war the war:war goal. Both plugins build the archive with the same component, Maven Archiver, and so share one <archive> configuration element. A JAR that bundles all its dependencies (a "fat" or "uber" JAR) is a separate topic, covered in Uber JARs with Shade & Assembly. This page covers the plain archives and what is inside their manifests. How a plugin is declared, pinned and configured is in Plugins & Their Configuration, and how the archive then gets into a repository is in Install, Deploy & Distribution Management.

A runnable JAR with a lib directory

The most common use of the manifest is a JAR that java -jar can start. tidepool-cli has a Main class, and its dependencies (tidepool-engine, tidepool-model, Commons CSV with its two transitive libraries, and picocli) have to be found at run time. The manifest can name them through Class-Path, as paths relative to the location of the JAR, so the dependencies have to be copied next to it. The dependency:copy-dependencies goal of the dependency plugin does that.

tidepool-cli/pom.xml (build section; the dependencies and parent are as in the other pages)
<build>
  <plugins>
    <plugin>
      <artifactId>maven-jar-plugin</artifactId>
      <configuration>
        <archive>
          <manifest>
            <mainClass>io.tidepool.cli.Main</mainClass>
            <addClasspath>true</addClasspath>
            <classpathPrefix>lib/</classpathPrefix>
            <addDefaultImplementationEntries>true</addDefaultImplementationEntries>
          </manifest>
          <manifestEntries>
            <Built-By>tidepool-build</Built-By>
            <Automatic-Module-Name>io.tidepool.cli</Automatic-Module-Name>
          </manifestEntries>
        </archive>
      </configuration>
    </plugin>
    <plugin>
      <artifactId>maven-dependency-plugin</artifactId>
      <version>3.11.0</version>
      <executions>
        <execution>
          <id>copy-runtime-libs</id>
          <phase>package</phase>
          <goals>
            <goal>copy-dependencies</goal>
          </goals>
          <configuration>
            <outputDirectory>${project.build.directory}/lib</outputDirectory>
            <includeScope>runtime</includeScope>
          </configuration>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

A few details of that output:

  • The manifest specification limits a line to 72 bytes, so the long Class-Path is wrapped, and each continuation line begins with a single space. Concatenate the lines after removing that space to read the value.

  • The Class-Path order is the order of the plugin’s dependency list. Maven 3.10 changed how the resolver flattens the dependency graph to breadth-first, but the change showed up only in plugin class realms, not in the project’s own compile classpath (see Dependencies, Scopes & Mediation), and the order written to this manifest was identical when the same project was built with 3.9.16.

  • Built-By and Automatic-Module-Name are ordinary manifestEntries; any name can be added. Automatic-Module-Name gives a stable module name to a library JAR that has no module-info.class, and is the usual reason to touch manifestEntries in a library.

  • The number decoration (-0,869 with a comma) is the JVM’s default locale at run time, not part of the packaging.

The Class-Path entries are resolved relative to the JAR, not to the current directory. Copying the JAR alone to another directory and starting it there fails with Exception in thread "main" java.lang.NoClassDefFoundError: picocli/CommandLine, and starting it from another directory (java -jar with an absolute path to the original) still works. This is why a runnable JAR of this kind is distributed as a directory, usually zipped by the assembly plugin (see Uber JARs with Shade & Assembly); one file with everything inside is the shade or assembly approach on that page.

Other Class-Path layouts

classpathLayoutType changes what each Class-Path entry looks like. repository writes the path the artifact has in a Maven repository, which is useful when the JAR is started from a directory that is a copy of a repository (an application server’s lib/ is not that). Building a copy of the CLI with this configuration (and with addMavenDescriptor set to false) gave:

<archive>
  <addMavenDescriptor>false</addMavenDescriptor>
  <manifest>
    <addClasspath>true</addClasspath>
    <classpathLayoutType>repository</classpathLayoutType>
    <mainClass>io.tidepool.cli.Main</mainClass>

What the configuration did:

  • finalName is a build-level setting, not a war plugin one, and renames tidepool-web-1.0.0-SNAPSHOT.war to tidepool.war. A war with a fixed name is what a servlet container deploys under a stable context path. The artifact installed and deployed to a repository is still named by the coordinates, so the file name is only about the file in target.

  • packagingExcludes removed static/notes.txt (a file in src/main/webapp that must not ship) and the Commons Codec JAR from WEB-INF/lib (it is a transitive dependency that the container is assumed to provide). The war plugin documents this as the way to include or exclude files after the webapp has been assembled; warSourceExcludes does the equivalent on the source directory before assembly.   • webResources adds a directory that is not under src/main/webapp, with an optional targetPath, includes, excludes and filtering. The example copies one file into WEB-INF.

  • The provided servlet API is not in WEB-INF/lib, as it must not be: the container supplies it.

  • The servlet class is in WEB-INF/classes, because a module with war packaging compiles like any Java module; only the last step differs.

web.xml and the Servlet API

Since the Servlet 3.0 specification a web.xml is optional, because servlets can be declared with annotations (the example uses @WebServlet). The war plugin’s failOnMissingWebXml parameter is documented as defaulting to false since 3.1.0 if the project depends on the Servlet 3.0 API or newer, and the example above worked with the line removed, because jakarta.servlet-api is on its classpath. Reproducible builds

A build is reproducible when the same sources, build environment and build instructions give bit-by-bit identical files. For packaging the main enemy is time: ZIP entries carry a modification time. The plugins that write archives therefore accept a single outputTimestamp, which the whole build sets through the project.build.outputTimestamp property, as an ISO 8601 date-time (2026-10-16T00:00:00Z) or as epoch seconds. With it set the jar, war, source, javadoc, assembly and shade plugins write that value into every entry.

The default since Maven 3.10

Before Maven 3.10 a project opted in by defining the property itself. Since Maven 3.10.0 (and 4.0.0-beta-5) the super POM defines it, so that every project is in the reproducible mode without touching its POM, with the fixed value 1980-02-01T00:00:00Z. The same lookup in the three Maven versions:

What else breaks reproducibility

Two elements of the archive configuration of this page make a JAR depend on the environment: addBuildEnvironmentEntries (operating system, JDK and Maven version) and a Built-By/Build-Time entry computed at build time. Dependency version ranges (see Versions, Snapshots & Ranges) and unpinned plugin versions change the content with no change in your project: an unpinned jar or war plugin gets the version in the running Maven’s lifecycle bindings, which changes with every Maven upgrade, so pin every plugin (see Enforcer and Security & Reproducible Builds for the checks and the supply-chain side). The JDK is also a factor: even with the same release, different major JDK versions generate different bytecode, and the guide advises recording it.

Changes between Maven versions

Version What changes for packaging

3.9.16

project.build.outputTimestamp is not defined unless the project sets it, so a JAR built twice differs. The archive plugins behave as described on this page.

3.10.0

project.build.outputTimestamp defaults to 1980-02-01T00:00:00Z through the super POM, so the plugins' reproducible mode is on for every project. The super POM no longer manages the antrun, assembly, dependency and release plugins; the jar and war plugin versions still come from the lifecycle bindings (maven-war-plugin 3.5.1 in the effective POM of a bare war project on 3.10.0), but they change with Maven, so pinning them is advised (this page’s examples pin them in the parent).

Same default timestamp (checked with the lookup above and the entry dates of the engine JAR). The Maven 2 book that informed these pages (Maven 2.2) has little to say on packaging beyond the lifecycle, but a few things that circulate with it are out of date:

  • Plugin versions were commonly left out of the POM. Maven 3 warns about it, and an unpinned maven-jar-plugin or maven-war-plugin takes the version in the running Maven’s lifecycle bindings, which changes from one Maven release to the next; declare them with a version (directly or in pluginManagement).

  • A manifest Class-Path plus a lib/ directory is documented for the old maven-assembly-plugin, but for an executable JAR the assembly plugin’s descriptor and the shade plugin have taken over (see Uber JARs with Shade & Assembly).

  • The jar.useDefaultManifestFile parameter and the manifestFile-only recipes of old posts: the former now only breaks the build, and the manifest is configured with archive.

  • A web.xml is not required for a servlet 3.0 WAR, and the javax.servlet coordinates were replaced by jakarta.servlet in Servlet 5 and later.

  • Reproducibility was not a concept in Maven 2. The timestamp in the archives was the build time.
