Installing Third-Party JARs & Relocation

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Maven 3.10.0 with the Apache Maven Install Plugin 3.2.0 and Deploy Plugin 3.2.0. Every example was run on JDK 26 on 2026-10-16. Maven 3.9.16 (Install and Deploy Plugin 3.1.4) and Maven 4.0.0-rc-7 (a release candidate) were run where the page says so. Paths in the console output were shortened to ./, the working directory of the experiment, and from every listing the Scanning for projects line, the banner and separator lines, blank [INFO] lines, the Total time and Finished at lines, the standard Help 1 trailer of a failed build and the Loaded N auto-discovered prefixes line that Maven 3.10 prints while resolving were left out. Nothing was published anywhere except to file:// repositories inside the scratch directory. A command against a real remote repository is marked "not run here".

Sooner or later a build needs a JAR that no public repository has: a vendor SDK with a closed licence, a driver that cannot be redistributed, a legacy library nobody publishes any more. Maven resolves dependencies by coordinates, so the job is always the same: give the file coordinates and put it, with a POM, at the right place in a repository. This page shows the tools Maven has for that, in the order you should consider them, and then the other side of the coin: telling consumers that an artifact moved. The repositories themselves are on Repositories, Mirrors & Repository Managers and the everyday install and deploy phases on Install, Deploy & Distribution Management.

Which way to put a JAR into a build

Approach Good for Cost

A repository manager (Nexus, Artifactory, Reposilite) with deploy:deploy-file

A team or a CI server. The JAR is uploaded once and every developer and build resolves it like any other artifact.

You need the manager and credentials.

install:install-file into ~/.m2

One developer, a quick experiment, a CI job that installs the JAR before the build.

The JAR exists only on that machine; everybody repeats the step.

A project-local repository (install:install-file with -DlocalRepositoryPath, plus a file:// <repository>)

A small project that must build from a plain clone, with the JAR committed next to the code.

A binary in version control, and a repository declaration in the POM.

<scope>system</scope> with <systemPath>

Nothing. It is deprecated, and dependent projects cannot resolve it.

Warnings on every build; see below.

A JAR that must be redistributed is a licensing question before it is a Maven question. Check the vendor’s terms before you upload it to a shared repository.

The vendor JAR used in this page

The experiments use a stand-in for a vendor library: one class in the package acme.gauge, built into acme-gauge-sdk-2.4.jar, plus a sources JAR. It has no pom.xml inside, like most vendor JARs. These files, the consumer class and its POM below are this page’s own lab setup, not examples from the Maven documentation.

javac -d classes src/acme/gauge/TideGauge.java
jar --create --file acme-gauge-sdk-2.4.jar -C classes .
jar --create --file acme-gauge-sdk-2.4-sources.jar -C src .
META-INF/
META-INF/MANIFEST.MF
acme/
acme/gauge/
acme/gauge/TideGauge.class

(That is the content of acme-gauge-sdk-2.4.jar.) The consuming project is the tidepool ingest module, io.tidepool:tidepool-ingest, with one class that calls the vendor library:

package io.tidepool.ingest;

import acme.gauge.TideGauge;

public final class GaugeFeed {
    public static String latest() {
        return TideGauge.reading("Bilbao");
    }
}

Its POM declares the dependency the normal way, with coordinates of your choosing (the vendor’s name is a fine groupId, you pick the rest) and nothing else special:

<dependencies>
  <dependency>
    <groupId>com.acme.gauge</groupId>
    <artifactId>acme-gauge-sdk</artifactId>
    <version>2.4</version>
  </dependency>
</dependencies>

To keep ~/.m2 clean every experiment used a throw-away local repository, set once through the MAVEN_ARGS environment variable (Maven 3.9 and later; see Configuring Maven):

export MAVEN_ARGS="-B -ntp -Dmaven.repo.local=$PWD/local-repo"

Source: Maven: Configuring Apache Maven, MAVEN_ARGS environment variable

The failure you are fixing

With nothing installed, the build cannot resolve the dependency. On Maven 3.10.0:

$ mvn compile
[INFO] Building tidepool-ingest 1.0.0-SNAPSHOT
[WARNING] The POM for com.acme.gauge:acme-gauge-sdk:jar:2.4 is missing, no dependency information available
[ERROR] BUILD FAILURE
[ERROR] Failed to execute goal on project tidepool-ingest: Could not resolve dependencies for project io.tidepool:tidepool-ingest:jar:1.0.0-SNAPSHOT
[ERROR] dependency: com.acme.gauge:acme-gauge-sdk:jar:2.4 (compile)
[ERROR] 	prefixes: Path com/acme/gauge/acme-gauge-sdk/2.4/acme-gauge-sdk-2.4.jar NOT allowed from central

Maven 3.10 loads the list of path prefixes that exist on Central (the Loaded ... auto-discovered prefixes line that was filtered out) and does not even ask Central for a path outside it, so the message is prefixes: Path ... NOT allowed from central. Maven 4.0.0-rc-7 gives the same reason and adds an explanation with the properties -Daether.remoteRepositoryFilter.prefixes=false and -Daether.remoteRepositoryFilter.groupId=false, which switch the filtering off for repository managers that do not publish prefix files. Maven 3.9.16 does not filter and asks Central, so the first failure is:

$ mvn compile
[INFO] Building tidepool-ingest 1.0.0-SNAPSHOT
[WARNING] The POM for com.acme.gauge:acme-gauge-sdk:jar:2.4 is missing, no dependency information available
[INFO] BUILD FAILURE
[ERROR] Failed to execute goal on project tidepool-ingest: Could not resolve dependencies for project io.tidepool:tidepool-ingest:jar:1.0.0-SNAPSHOT
[ERROR] dependency: com.acme.gauge:acme-gauge-sdk:jar:2.4 (compile)
[ERROR] 	Could not find artifact com.acme.gauge:acme-gauge-sdk:jar:2.4 in central (https://repo.maven.apache.org/maven2)

A second attempt in the same local repository does not ask again and reports the cached failure: ... was not found in https://repo.maven.apache.org/maven2 during a previous attempt. This failure was cached in the local repository and resolution is not reattempted until the update interval of central has elapsed or updates are forced. The cached failure matters later. Maven writes small .lastUpdated marker files in the local repository for a lookup that failed, and does not retry until the update interval has passed or you force it with -U. Installing the file afterwards still works, as the next section shows.

Source: Maven: Guide to installing 3rd party JARs

install:install-file

install:install-file copies one file into the local repository at the path its coordinates dictate. It needs no project, so Maven prints Maven Stub Project (No POM) as the project name.

mvn install:install-file -Dfile=vendor/acme-gauge-sdk-2.4.jar -DgroupId=com.acme.gauge -DartifactId=acme-gauge-sdk -Dversion=2.4 -Dpackaging=jar
$ mvn install:install-file -Dfile=vendor/acme-gauge-sdk-2.4.jar -DgroupId=com.acme.gauge -DartifactId=acme-gauge-sdk -Dversion=2.4 -Dpackaging=jar
[INFO] --- install:3.2.0:install-file (default-cli) @ standalone-pom ---
[INFO] Ignoring any POM embedded in acme-gauge-sdk-2.4.jar: complete coordinates were supplied, so a minimal POM will be generated instead. Use -DpomFile to install a specific POM.
[INFO] Installing ./vendor/acme-gauge-sdk-2.4.jar to ./local-repo/com/acme/gauge/acme-gauge-sdk/2.4/acme-gauge-sdk-2.4.jar
[INFO] Installing /tmp/mvninstall15916797829772843492.pom to ./local-repo/com/acme/gauge/acme-gauge-sdk/2.4/acme-gauge-sdk-2.4.pom
[INFO] BUILD SUCCESS

The Ignoring any POM embedded line is printed by Install Plugin 3.2.0 (Maven 3.9.16 runs 3.1.4 and does not print it): when you supply all four coordinates the plugin does not read a POM from inside the JAR and writes a minimal one instead. The temporary file /tmp/mvninstall...pom is that generated POM. This is what is in the local repository afterwards:

com/acme/gauge/acme-gauge-sdk/2.4/_remote.repositories
com/acme/gauge/acme-gauge-sdk/2.4/acme-gauge-sdk-2.4.jar
com/acme/gauge/acme-gauge-sdk/2.4/acme-gauge-sdk-2.4.jar.lastUpdated
com/acme/gauge/acme-gauge-sdk/2.4/acme-gauge-sdk-2.4.pom
com/acme/gauge/acme-gauge-sdk/2.4/acme-gauge-sdk-2.4.pom.lastUpdated
com/acme/gauge/acme-gauge-sdk/maven-metadata-local.xml

The two .lastUpdated files are the cache of the failed lookup from the previous section, and are harmless. The generated POM is the minimum Maven needs:

<?xml version="1.0" encoding="UTF-8"?>
<project xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd" xmlns="http://maven.apache.org/POM/4.0.0"
    xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance">
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.acme.gauge</groupId>
  <artifactId>acme-gauge-sdk</artifactId>
  <version>2.4</version>
  <description>POM was created from install:install-file</description>
</project>

A POM like this says nothing about the library’s own dependencies. If the vendor JAR needs other libraries, nothing brings them in; see the -DpomFile form below. Two more files are written. _remote.repositories records where each file came from, and the empty name after > means "installed locally, not downloaded":

#NOTE: This is a Maven Resolver internal implementation file, its format can be changed without prior notice.
#Fri Oct 16 14:39:53 CEST 2026
acme-gauge-sdk-2.4.jar>=
acme-gauge-sdk-2.4.pom>=

(The timestamp comment line was removed.) maven-metadata-local.xml lists the versions installed locally under the artifactId; the repository files themselves are described on Repositories, Mirrors & Repository Managers.

The four coordinates are required

Unless the JAR carries its own POM (see below), groupId, artifactId, version and packaging must all be given. Leaving groupId, version and packaging out fails before anything is written:

$ mvn install:install-file -Dfile=vendor/acme-gauge-sdk-2.4.jar -DartifactId=oops
[INFO] --- install:3.2.0:install-file (default-cli) @ standalone-pom ---
[INFO] pom.xml not found in acme-gauge-sdk-2.4.jar
[ERROR] BUILD FAILURE
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-install-plugin:3.2.0:install-file (default-cli) on project standalone-pom: The artifact information is incomplete: 'groupId', 'artifactId', 'version' and 'packaging' are required. -> [Help 1]

A real POM, a sources JAR and a Javadoc JAR

If you have the vendor’s POM, or write one that lists the library’s dependencies, pass it with -DpomFile. The coordinates then come from the POM, and -Dsources and -Djavadoc install the companion JARs with the sources and javadoc classifiers, which is what an IDE looks for. Version 2.5 of the stand-in has this POM, which declares one dependency on Apache Commons CSV:

<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <groupId>com.acme.gauge</groupId>
  <artifactId>acme-gauge-sdk</artifactId>
  <version>2.5</version>
  <name>ACME Gauge SDK</name>

  <dependencies>
    <dependency>
      <groupId>org.apache.commons</groupId>
      <artifactId>commons-csv</artifactId>
      <version>1.14.1</version>
    </dependency>
  </dependencies>
</project>
mvn install:install-file -Dfile=vendor/acme-gauge-sdk-2.5.jar -DpomFile=vendor/acme-gauge-sdk-2.5.pom -Dsources=vendor/acme-gauge-sdk-2.5-sources.jar
$ mvn install:install-file -Dfile=vendor/acme-gauge-sdk-2.5.jar -DpomFile=vendor/acme-gauge-sdk-2.5.pom -Dsources=vendor/acme-gauge-sdk-2.5-sources.jar

A JAR built by Maven carries its own POM

A JAR produced by Maven contains its POM under META-INF/maven/<groupId>/<artifactId>/. Packaging the consumer module shows it:

META-INF/maven/
META-INF/maven/io.tidepool/
META-INF/maven/io.tidepool/tidepool-ingest/

The parameters that matter

The plugin’s own reference lists them all; the Since column is from the Install Plugin documentation.

Parameter Since Meaning

file

Required. The file to install.

groupId, artifactId, version, packaging

The coordinates. Read from -DpomFile or from the embedded POM when not given.

pomFile

2.1

An existing POM to install next to the file.

generatePom

2.1

Generate a minimal POM when none is supplied. Defaults to true if there is no POM in the local repository yet.

classifier

2.2

For example sources or javadoc; empty means the main artifact.

localRepositoryPath

2.2

Install into this directory instead of the configured local repository.

sources, javadoc

2.3

Companion JARs installed with the sources and javadoc classifiers.

extension

3.1.3

Override the file extension that the packaging would choose.

Source: Maven Install Plugin: install:install-file

A project-local repository

-DlocalRepositoryPath points the install at a directory of your choice. The result is a complete Maven repository layout that you can commit. Here it is project-repo/:

mvn install:install-file -Dfile=vendor/acme-gauge-sdk-2.4.jar -DgroupId=com.acme.gauge -DartifactId=acme-gauge-sdk -Dversion=2.4 -Dpackaging=jar -DlocalRepositoryPath=project-repo
$ mvn install:install-file -Dfile=vendor/acme-gauge-sdk-2.4.jar -DgroupId=com.acme.gauge -DartifactId=acme-gauge-sdk -Dversion=2.4 -Dpackaging=jar -DlocalRepositoryPath=project-repo

The consumer then declares that directory as a repository, using the ${project.basedir} property so the path does not depend on where you start Maven:

<repositories>
  <repository>
    <id>project-libs</id>
    <url>file://${project.basedir}/../project-repo</url>
  </repository>
</repositories>

The two warnings say the repository has no checksum files, because install-file does not write any. Maven still uses the files. deploy-file (next) does write checksums, so a repository created with it does not warn. If you use this approach, commit the repository directory and give the repository an id of its own: Maven remembers which repository each downloaded file came from.

deploy:deploy-file

deploy:deploy-file uploads a file to a remote repository and updates the repository metadata. It is the right tool when more than one person or machine needs the JAR. It does not install into the local repository: after all the deploys below, the local repository of the experiment contained no version 2.6, which only deploy-file ever touched. (The Maven guide says the JAR goes to the local and the remote repository; with Deploy Plugin 3.2.0 it goes only to the remote one.)

Generic POM, custom POM

Attaching extra artifacts with build-helper (third party)

install-file and deploy-file handle files that already exist. When a project’s own build produces an extra file that must be installed and deployed with it (a data file, a generated schema, a native library), the usual tool is the attach-artifact goal of the MojoHaus Build Helper Plugin. It is not an Apache Maven plugin, it is a third-party plugin that is used widely. It registers the file as an attached artifact with a classifier, and the standard install and deploy goals do the rest. This example, version 3.6.2 of the plugin, attaches the tidepool station list as seed data to a POM-packaged project:

<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <groupId>io.tidepool</groupId>
  <artifactId>tidepool-stations</artifactId>
  <version>1.0.0</version>
  <packaging>pom</packaging>

  <build>
    <plugins>
      <plugin>
        <groupId>org.codehaus.mojo</groupId>
        <artifactId>build-helper-maven-plugin</artifactId>
        <version>3.6.2</version>
        <executions>
          <execution>
            <id>attach-stations</id>
            <phase>package</phase>
            <goals>
              <goal>attach-artifact</goal>
            </goals>
            <configuration>
              <artifacts>
                <artifact>
                  <file>data/stations.csv</file>
                  <type>csv</type>
                  <classifier>seed</classifier>
                </artifact>
              </artifacts>
            </configuration>
          </execution>

</project>

Relocation

Sometimes the problem is the opposite one: the artifact is on a repository, but under the wrong name. A project changes its groupId, its artifactId or both, and consumers still ask for the old coordinates. Published repository content must never change, so Maven’s answer is a relocation: a POM published at the old coordinates that contains no code and says "go there instead". The element is <distributionManagement><relocation>, described on POM Fundamentals. It may hold groupId, artifactId, version and a message; every element you leave out keeps the old value, so a project that only changed its groupId writes only the groupId.

A real relocation on Maven Central

Apache Ant published its releases up to 1.6.5 as ant:ant and, from 1.7.0, as org.apache.ant:ant, and left one relocation POM at the old coordinates. This is that file, fetched from Central:

<project>
  <modelVersion>4.0.0</modelVersion>
  <groupId>ant</groupId>
  <artifactId>ant</artifactId>
  <version>1.7.0</version>

  <distributionManagement>
    <relocation>
      <groupId>org.apache.ant</groupId>
    </relocation>
  </distributionManagement>

</project>

A project that still depends on ant:ant:1.7.0 builds, with a warning (Maven 3.10.0):

Relocating your own artifact

The tidepool project decides that its modules move from io.tidepool to io.tidepool.core. The new artifact is deployed under the new groupId, as usual. Under the old coordinates goes a minimal POM, relocation.pom: coordinates, the relocation, and a message that tells the consumer what to do:

<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <groupId>io.tidepool</groupId>
  <artifactId>tidepool-model</artifactId>
  <version>1.0.0</version>

  <distributionManagement>
    <relocation>
      <groupId>io.tidepool.core</groupId>
      <message>The tidepool modules moved to io.tidepool.core; update your dependency.</message>
    </relocation>
  </distributionManagement>
</project>

Both are deployed with deploy-file. The relocation POM is itself the file to upload, so -Dpackaging=pom is needed; without it the plugin would take its extension from the default packaging and name it .jar.

The procedure for a real project

The Maven guide to relocation describes the steps for an artifact that has already been published to a repository under the old name. In outline:

  1. Copy all files of the old artifact to the new location (the new groupId path), and change the groupId inside the copied POMs.

  2. At the old location, replace the POM of every released version by a minimal relocation POM. Back the old POMs up first.

  3. If the repository uses checksums or signatures, recreate them for the POMs you changed. If it syncs to Central, start the sync.

  4. At the next release, publish two POMs: the real one under the new groupId and a relocation POM under the old groupId for the new version, because Maven does not download a POM again once it has it, and users of the previous version would otherwise never see the move. From the release after that, publish only under the new groupId.

The guide itself points out that Central content should not be changed once published, which is why Ant left the old POMs alone and published one relocation POM for 1.7.0 only. It also carries a note that a rework of the guide is in progress; treat the steps as the long-standing practice and check them against your repository manager’s documentation. A repository manager (Nexus, Artifactory) may let you do the same through its UI. The relocation itself was run here only on a file:// repository.

Where the books are outdated

The Maven 2 era books show Maven 2.2 and a repository workflow of that time. Today:

  • Archiva, the repository manager those books use for deploying a shared JAR, was retired in 2024 (see the Apache Attic page); the same deploy:deploy-file workflow works against Nexus, Artifactory or Reposilite.

  • A deploy-file needing wagon-ftp, wagon-ssh or wagon-file in ${maven.home}/lib is Maven 2 practice. Native HTTP transport has been the default since Maven 3.9.0, and file:// repositories need nothing.

  • mvn install:install-file examples that name a plugin version such as 2.5.2 in full are obsolete: the version is bound by the lifecycle, 3.2.0 on Maven 3.10.0, and -Dsources and -Djavadoc make a separate call for the companion JARs unnecessary.

  • The system scope was shown as a convenience; Maven 3.10 flags it as deprecated.

Summary of pitfalls

  • install-file without a POM writes a POM with no dependencies; the library’s own dependencies are not resolved. Use -DpomFile.

  • A JAR installed only on your machine breaks everybody else’s build and CI. Deploy it to a repository.

  • deploy-file does not install into the local repository; run both when you need both.

  • -DrepositoryId must equal a <server> id in settings.xml, or Maven sends no credentials.

  • A sources JAR deployed with generatePom left at its default makes the plugin generate a POM with packaging java-source at the coordinates of the main artifact, which would replace its real POM; use -DgeneratePom=false.

  • <scope>system</scope> is deprecated and never reaches dependent projects.

  • A failed lookup is cached in the local repository (.lastUpdated files); -U forces the update.

  • A relocation POM must be published for every old version you want to redirect, and it is only a hint: consumers keep the warning until they edit their dependency.

  • Do not change a published JAR or POM; relocate and release again.
