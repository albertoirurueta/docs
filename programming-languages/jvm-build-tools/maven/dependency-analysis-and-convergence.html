Maven Dependency Analysis & Convergence

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Maven 3.10.0 with the Apache Maven Dependency Plugin 3.11.0 and the Apache Maven Enforcer Plugin 3.6.3; the third-party MojoHaus Versions Maven Plugin 2.23.0 is covered at the end. Every example was run on JDK 26 on 2026-10-16. Where the output is identical on Maven 3.9.16 and Maven 4.0.0-rc-7 (a release candidate) the text says so; where it differs the difference is named. Paths in the console output were shortened to /work/mvn-dep-analysis/..., and the one line Loaded N auto-discovered prefixes for remote repository ... that Maven 3.10 prints while resolving was left out.

A Maven dependency graph is computed, not written: the build you read in the POM and the build that actually runs differ by every transitive dependency, every mediation decision and every management override. Declaring a dependency is easy; knowing what you really got, whether you still use it, and whether two libraries agree about a third one needs tools. This page collects them. How the graph is built (scopes, nearest-wins mediation, exclusions) is explained on Dependencies, Scopes & Mediation; dependencyManagement and BOMs are on Dependency Management & BOMs; version syntax and snapshots are on Versions, Snapshots & Ranges; the enforcer plugin as a whole is on The Enforcer Plugin. The cross-tool vocabulary is in Dependency Management Fundamentals.

Two example projects

Two scratch projects are used. The first is the multi-module tidepool build (tidepool-model, tidepool-engine, tidepool-cli, a JUnit Jupiter 6.1.3 test in the engine, Commons CSV 1.14.1 and picocli 4.7.7), with the dependency plugin pinned to 3.11.0 in pluginManagement. The second is a small module, tidepool-report, that is deliberately inconsistent:

<dependencies>
  <dependency>
    <groupId>commons-fileupload</groupId>
    <artifactId>commons-fileupload</artifactId>
    <version>1.5</version>
  </dependency>
  <dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-csv</artifactId>
    <version>1.14.1</version>
  </dependency>
</dependencies>

Both libraries need Commons IO, but Commons FileUpload 1.5 asks for 2.11.0 and Commons CSV 1.14.1 asks for 2.20.0. The rest of the page is largely about finding, explaining and ending that disagreement. Both projects are this page’s own lab setup, not examples from the Maven documentation.

graph TD R["tidepool-report 1.0.0"] --> F["commons-fileupload 1.5"] R --> C["commons-csv 1.14.1"] F --> IO11["commons-io 2.11.0 - selected, first declared"] C -.-> IO20["commons-io 2.20.0 - omitted for conflict"] C --> CD["commons-codec 1.19.0"]

Why is this version here? -Dverbose

By default the tree shows only the winners. With -Dverbose the losers of mediation appear in parentheses, with the reason. On tidepool-report:

[INFO] --- dependency:3.11.0:tree (default-cli) @ tidepool-report ---
[INFO] io.tidepool:tidepool-report:jar:1.0.0
[INFO] +- commons-fileupload:commons-fileupload:jar:1.5:compile
[INFO] |  \- commons-io:commons-io:jar:2.11.0:compile
[INFO] \- org.apache.commons:commons-csv:jar:1.14.1:compile
[INFO]    +- (commons-io:commons-io:jar:2.20.0:compile - omitted for conflict with 2.11.0)
[INFO]    \- commons-codec:commons-codec:jar:1.19.0:compile

The plain tree shows only commons-io:2.11.0 below Commons FileUpload and nothing below Commons CSV except Commons Codec; the verbose tree shows that Commons CSV wanted 2.20.0 and lost. Both versions sit at depth 2, so the tie is broken by declaration order: Commons FileUpload is declared first, so its Commons IO wins. Commons CSV 1.14.1 will run against a Commons IO two minor lines older than the one it was built and tested with. The three Maven releases print exactly the same verbose tree: the output above was identical on 3.10.0, 3.9.16 and 4.0.0-rc-7.

Finding one artifact: -Dincludes

On a real project the tree has hundreds of lines. -Dincludes keeps only the paths that lead to the artifact you ask about:

$ mvn -pl tidepool-cli dependency:tree -Dincludes=org.apache.commons,commons-io
[INFO] --- dependency:3.11.0:tree (default-cli) @ tidepool-cli ---
[INFO] io.tidepool:tidepool-cli:jar:1.0.0
[INFO] \- io.tidepool:tidepool-engine:jar:1.0.0:compile
[INFO]    \- org.apache.commons:commons-csv:jar:1.14.1:compile
[INFO]       \- commons-io:commons-io:jar:2.20.0:compile

-Dincludes=... takes a comma-separated list, and each entry is a full filter pattern, so commons-io matches by group and org.apache.commons matches the Commons CSV group. The complementary -Dexcludes removes noise, such as the whole JUnit subtree, when it is the test scope you do not care about; -Dscope=runtime does it more simply by not resolving test dependencies at all.

Output formats

-DoutputType renders the same tree for other tools. dot is a Graphviz digraph; tgf is Trivial Graph Format (a node list, a # line, then the edges); graphml and json (3.7.0) are for graph viewers and scripts. For the runtime scope of the CLI:

$ mvn -pl tidepool-cli dependency:tree -Dscope=runtime -DoutputType=dot
[INFO] digraph "io.tidepool:tidepool-cli:jar:1.0.0" {
[INFO] 	"io.tidepool:tidepool-cli:jar:1.0.0" -> "io.tidepool:tidepool-engine:jar:1.0.0:compile" ;
[INFO] 	"io.tidepool:tidepool-cli:jar:1.0.0" -> "info.picocli:picocli:jar:4.7.7:compile" ;
[INFO] 	"io.tidepool:tidepool-engine:jar:1.0.0:compile" -> "io.tidepool:tidepool-model:jar:1.0.0:compile" ;
[INFO] 	"io.tidepool:tidepool-engine:jar:1.0.0:compile" -> "org.apache.commons:commons-csv:jar:1.14.1:compile" ;
[INFO] 	"org.apache.commons:commons-csv:jar:1.14.1:compile" -> "commons-io:commons-io:jar:2.20.0:compile" ;
[INFO] 	"org.apache.commons:commons-csv:jar:1.14.1:compile" -> "commons-codec:commons-codec:jar:1.19.0:compile" ;

(Trailing spaces on the console lines were trimmed.) Add -DoutputFile=graph.dot to write the graph without the [INFO] prefix. With -DoutputType=tgf the same graph is printed as seven numbered nodes followed by # and six from to scope edges, each node number being a hash of the coordinates.

Auditing the declarations: dependency:analyze

The tree shows what you got. dependency:analyze asks whether the POM declares what the code uses. It reads the compiled bytecode of your classes and tests with the Maven Dependency Analyzer, computes which dependency JARs the bytecode refers to, and compares that with the declared dependencies. It reports three groups:

  • Used undeclared: the code uses a class from a JAR that arrives only transitively. If the library that brought it drops it, your build breaks.

  • Unused declared: a declared dependency that no class refers to. Dead weight, or a runtime-only dependency the analysis cannot see.

  • Non-test scoped, test only: a compile-scope dependency that only test classes use (should be test scope).

analyze, analyze-only, analyze-report and analyze-duplicate

For the command line. It always forks the lifecycle up to test-compile first, so there are classes to analyse (since 2.0-alpha-3).

The same analysis for binding in the POM; it assumes test-compile already ran. Default phase verify (since 2.0).

dependency:analyze-dep-mgt

Run over the whole tidepool reactor (output reduced to the plugin lines and warnings; the compiler and resources lines of the forked test-compile were left out):

$ mvn dependency:analyze
[INFO] --- dependency:3.11.0:analyze (default-cli) @ tidepool ---
[INFO] Skipping pom project
[INFO] --- dependency:3.11.0:analyze (default-cli) @ tidepool-model ---
[WARNING] Unused declared dependencies found:
[WARNING]    org.junit.jupiter:junit-jupiter:jar:6.1.3:test
[INFO] --- dependency:3.11.0:analyze (default-cli) @ tidepool-engine ---
[WARNING] Used undeclared dependencies found:
[WARNING]    org.junit.jupiter:junit-jupiter-api:jar:6.1.3:test
[WARNING] Unused declared dependencies found:
[WARNING]    org.junit.jupiter:junit-jupiter:jar:6.1.3:test
[INFO] --- dependency:3.11.0:analyze (default-cli) @ tidepool-cli ---
[WARNING] Used undeclared dependencies found:
[WARNING]    io.tidepool:tidepool-model:jar:1.0.0:compile
[WARNING] Unused declared dependencies found:
[WARNING]    org.junit.jupiter:junit-jupiter:jar:6.1.3:test
[INFO] BUILD SUCCESS

Three real findings, and one that is not a finding:

  • tidepool-cli uses io.tidepool.model.Station but declares only tidepool-engine; tidepool-model arrives through the engine. This is the textbook used undeclared case and it is a true positive.

  • tidepool-model and tidepool-cli have no tests, so junit-jupiter is truly unused there. The parent POM declares it for every module, which is the cause.

  • tidepool-engine has a test that imports org.junit.jupiter.api.Test. The declared artifact is the aggregator junit-jupiter, which contains no classes of its own; the classes live in junit-jupiter-api, so the analysis reports the aggregator as unused and the API artifact as used but undeclared. This is a false positive produced by how the JUnit aggregator is packaged, and the usual reason for the ignore settings below.

The same warnings, in the same order, were produced by Maven 3.9.16 and by 4.0.0-rc-7. (4.0.0-rc-7 additionally prints Unable to find the root directory. Create a .mvn directory... when the project has no .mvn directory.)

Failing the build

By default the report is only advice. -DfailOnWarning=true (or <failOnWarning> in the POM) turns it into an error:

$ mvn -pl tidepool-cli dependency:analyze -DfailOnWarning
[ERROR] Used undeclared dependencies found:
[ERROR]    io.tidepool:tidepool-model:jar:1.0.0:compile
[ERROR] Unused declared dependencies found:
[ERROR]    org.junit.jupiter:junit-jupiter:jar:6.1.3:test
[ERROR] BUILD FAILURE
...
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-dependency-plugin:3.11.0:analyze (default-cli) on project tidepool-cli: Dependency problems found -> [Help 1]

For a permanent gate bind analyze-only to verify, and ignore the known false positives. The configuration below was added to the parent POM; the two ignore lists name the aggregator and its API (the pattern is groupId:artifactId, with the same optional type:version tail and * wildcards as the other filters):

<build>
  <plugins>
    <plugin>
      <artifactId>maven-dependency-plugin</artifactId>
      <executions>
        <execution>
          <id>analyze</id>
          <goals>
            <goal>analyze-only</goal>
          </goals>
          <configuration>
            <failOnWarning>true</failOnWarning>
            <ignoredUnusedDeclaredDependencies>
              <ignoredUnusedDeclaredDependency>org.junit.jupiter:junit-jupiter</ignoredUnusedDeclaredDependency>
            </ignoredUnusedDeclaredDependencies>
            <ignoredUsedUndeclaredDependencies>
              <ignoredUsedUndeclaredDependency>org.junit.jupiter:junit-jupiter-api</ignoredUsedUndeclaredDependency>
            </ignoredUsedUndeclaredDependencies>
          </configuration>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

With the fault in tidepool-cli still there, mvn verify stops exactly at the real problem and the false positives are silent:

[INFO] --- dependency:3.11.0:analyze-only (analyze) @ tidepool-cli ---
[ERROR] Used undeclared dependencies found:
[ERROR]    io.tidepool:tidepool-model:jar:1.0.0:compile
[INFO] ------------------------------------------------------------------------
[INFO] Reactor Summary for tidepool 1.0.0:
[INFO]
[INFO] tidepool ........................................... SUCCESS [  1.186 s]
[INFO] tidepool-model ..................................... SUCCESS [  1.026 s]
[INFO] tidepool-engine .................................... SUCCESS [  0.919 s]
[ERROR] tidepool-cli ....................................... FAILURE [  0.085 s]
[INFO] ------------------------------------------------------------------------
[ERROR] BUILD FAILURE
...
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-dependency-plugin:3.11.0:analyze-only (analyze) on project tidepool-cli: Dependency problems found -> [Help 1]

The fix is one command, described in Editing the POM from the command line: add and remove; afterwards the same mvn verify prints BUILD SUCCESS and the analyze-only (analyze) execution is silent in all four modules.

The plugin does not warn about a few dependencies where bytecode analysis is known to be unreliable, SLF4J being the example the documentation gives. Two causes of false positives are named in the documentation: annotations with source retention, which do not appear in bytecode, and classes loaded by reflection at runtime. For those use usedDependencies or the ignore lists. Because the analysis is on bytecode, it cannot see a dependency that is only needed at runtime (a JDBC driver, a logging backend); declare those with runtime scope and add ignoreUnusedRuntime.

Management overrides: dependency:analyze-dep-mgt

Maven applies dependencyManagement to transitive dependencies, so a managed version always wins there. A mismatch can only remain where a direct declaration overrides the managed version, which is why the goal ignores direct dependencies by default (ignoreDirect=true, user property mdep.analyze.ignore.direct). In a copy of tidepool-report the management section pins Commons IO 2.20.0 while a direct declaration asks for 2.11.0:

$ mvn -f pom-mgt.xml dependency:analyze-dep-mgt
[INFO] --- dependency:3.11.0:analyze-dep-mgt (default-cli) @ tidepool-report ---
[INFO] Found Resolved Dependency/DependencyManagement mismatches:
[INFO] 	Ignoring Direct Dependencies.
[INFO] 	None

$ mvn -f pom-mgt.xml dependency:analyze-dep-mgt -Dmdep.analyze.ignore.direct=false
[INFO] --- dependency:3.11.0:analyze-dep-mgt (default-cli) @ tidepool-report ---
[INFO] Found Resolved Dependency/DependencyManagement mismatches:
[INFO] 	Dependency: commons-io:commons-io:jar
[INFO] 		DepMgt  : 2.20.0
[INFO] 		Resolved: 2.11.0
[WARNING] Potential problems found in Dependency Management

-Dmdep.analyze.failBuild=true turns the warning into Failed to execute goal ...:analyze-dep-mgt (default-cli) on project tidepool-report: Found Dependency errors. Use the goal to keep a parent’s or BOM’s management section honest: a child that silently declares its own version defeats the point of managing versions.

Stale exclusions: dependency:analyze-exclusions

An <exclusion> records a decision ("do not bring me X through this dependency"). When the dependency is later upgraded and stops bringing X, the exclusion silently becomes noise. Since 3.7.0 analyze-exclusions finds those. Here Commons FileUpload excludes Commons IO (effective) and Commons Logging (which Commons FileUpload 1.5 does not depend on):

$ mvn -f pom-excl.xml dependency:analyze-exclusions
[INFO] --- dependency:3.11.0:analyze-exclusions (default-cli) @ tidepool-report ---
[WARNING] tidepool-report defines following unnecessary excludes
[WARNING]     commons-fileupload:commons-fileupload:1.5
[WARNING]         - commons-logging:commons-logging @ line: 26

The report carries the POM line number. With -Dmdep.exclusion.fail=true (exclusionFail, since 3.7.0) the same lines are logged at ERROR level and the build fails with Invalid exclusions found.   <dependencies>
    <dependency>
      <groupId>org.apache.maven.surefire</groupId>
      <artifactId>surefire-junit-platform</artifactId>
      <version>3.6.0</version>
    </dependency>
  </dependencies>
</plugin>

Adding only the provider moved the failure to org.junit.platform:junit-platform-launcher:jar:6.1.3 (absent) (165 JARs). Enforcing convergence: the enforcer rules

The analysis goals tell you; the enforcer plugin makes the build refuse. Two built-in rules police the shape of the graph:

  • dependencyConvergence requires that every artifact resolves to one version in all paths of the tree. If A needs C 1.0 and B needs C 2.0 the rule fails, even if mediation would pick one of them quietly.

  • requireUpperBoundDeps requires that the version Maven selected is equal to or higher than the highest version requested anywhere in the tree. It targets the dangerous half of the problem: a library running against an older version than it asked for.

Both are bound to the enforcer’s enforce goal. This was added to the tidepool-report POM (the enforcer plugin is pinned to 3.6.3 in pluginManagement):

<build>
  <plugins>
    <plugin>
      <artifactId>maven-enforcer-plugin</artifactId>
      <executions>
        <execution>
          <id>enforce-dependencies</id>
          <goals>
            <goal>enforce</goal>
          </goals>
          <configuration>
            <rules>
              <dependencyConvergence/>
              <requireUpperBoundDeps/>
            </rules>
          </configuration>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

mvn validate (the enforce goal’s default phase) fails, with both rules reported and the paths to both versions:

Keeping up: the MojoHaus Versions plugin (third party)

The Versions Maven Plugin, org.codehaus.mojo:versions-maven-plugin, is not an Apache Maven plugin. It belongs to MojoHaus, which took over the former Codehaus Mojo project (the org.codehaus.mojo coordinates were kept). Version 2.23.0 was used. Pin it like any plugin; mvn versions:... resolves the prefix through the default org.codehaus.mojo plugin group, but an unpinned plugin is a moving target. The examples use the full coordinates.

$ mvn org.codehaus.mojo:versions-maven-plugin:2.23.0:display-dependency-updates
[INFO] --- versions:2.23.0:display-dependency-updates (default-cli) @ tidepool-report ---
[INFO] The following dependencies in Dependencies have newer versions:
[INFO]   commons-fileupload:commons-fileupload ................... 1.5 -> 1.6.0

Only Commons FileUpload is listed: Commons CSV 1.14.1 is already the newest, and the transitive Commons IO is not reported because the goal looks at the project’s own declarations (and management); -Dverbose would also list the dependencies without updates. Useful parameters: allowMajorUpdates, allowMinorUpdates, allowIncrementalUpdates (all default true), allowSnapshots, dependencyIncludes/dependencyExcludes, processDependencyManagement, ignoredVersions (regex list, to skip milestones) and showNewestPerSegment (since 2.23.0).

display-plugin-updates does the same for plugins and also checks the minimum Maven version. In the test project it reported that all plugins use the latest versions, then printed the warning Project does not define minimum Maven version required for build and a long list of old plugin versions that "require Maven 2.0" and so on; read only the first lines.

$ mvn org.codehaus.mojo:versions-maven-plugin:2.23.0:use-latest-releases -DgenerateBackupPoms=false
[INFO] --- versions:2.23.0:use-latest-releases (default-cli) @ tidepool-report ---

By default the plugin leaves a pom.xml.versionsBackup; the run without -DgenerateBackupPoms=false produced a backup byte identical to the original, and versions:revert restored it (Restoring ...pom.xml from ...pom.xml.versionsBackup). In a Git repository the backup file is unnecessary; use the flag. use-latest-releases honours the same allow*Updates switches, plus includes/excludes, scope, processParent (default false) and excludeReactor (default true). Where the books are outdated

The Maven 2 era books (the issue’s AM2 table) show dependency:analyze and dependency:tree from the plugin’s 2.x line. Today the plugin is 3.11.0 and a chapter written then is missing a lot:

  • dependency:analyze-exclusions (3.7.0), the json tree format (3.7.0), graphRoots (3.10.0) and dependency:add/remove (3.11.0) did not exist.

  • A POM with duplicate dependencies, once a warning, is a build error on Maven 3.10.0.

  • dependency:sources and the silent parameter are deprecated; -q replaces silent.

  • The Codehaus Mojo plugins were renamed to MojoHaus; the Versions plugin lives at mojohaus.org, and the old dependency plugin at Mojo (dependency-maven-plugin) is the same project, renamed and moved to Apache (the plugin FAQ says so).

  • Convergence enforcement was usually described with the old enforcer rule names and -Drules; the rule parameters and the enforcer.rules property above are current.

Summary of pitfalls

  • dependency:tree without -Dverbose hides the loser of every conflict; use -Dverbose before blaming a library.

  • On a tie in depth, the first declaration wins; reordering dependencies can change the classpath silently.

  • dependency:analyze forks test-compile; on a large build prefer analyze-only bound to verify and ignore known false positives instead of turning failOnWarning off.

  • Aggregator artifacts (junit-jupiter, many BOM-like starters) always look unused; the real classes belong to the artifacts below them.

  • A direct declaration of a managed dependency overrides the management; analyze-dep-mgt ignores that unless -Dmdep.analyze.ignore.direct=false.

  • go-offline does not fetch the Surefire provider or the JUnit launcher; pre-declare them, or warm the cache with a real build.

  • purge-local-repository with the default reResolve=true goes online; with a shared ~/.m2 it deletes for every project.

  • dependency:add and remove change only what you ask; they do not check that child modules still build.

  • Direct declaration is not convergence. Use dependencyManagement, a BOM or an exclusion.
