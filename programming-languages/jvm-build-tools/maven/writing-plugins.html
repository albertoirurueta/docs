Writing Maven Plugins

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Maven 3.10.0 with Maven Plugin Tools 3.16.0 (the Maven Plugin Plugin and the annotations), the Maven Plugin Testing Harness 3.5.1 and the Maven Invoker Plugin 3.10.1. Every example was run on JDK 26 on 2026-10-16 in a scratch directory with its own local repository, so that the example plugin never touched the real one. The plugin is compiled with release 21 against the Maven 3.9.16 API, which makes the same JAR run on Maven 3.9.16, 3.10.0 and Maven 4.0.0-rc-7 (a release candidate, not a final release); the build of the plugin itself and the consumer builds were run on all three, and the differences are stated. Paths in console output were shortened to /work/writing-plugins/... and $MAVEN_HOME; the three banner lines of each project, blank [INFO] lines and download lines were left out, lines longer than about 200 characters end in [...], and the long lists of artifacts that the Invoker Plugin copies were filtered out and say so. The scenario is the tidepool project used across this section, here as a data-quality goal for the data/stations.csv file that the other modules of tidepool read: the same check that Writing Custom Ant Tasks builds as an Ant task.

Almost everything that Maven does is done by a plugin, and a plugin is not a special kind of thing: it is a JAR with a descriptor, built by an ordinary Maven project, and stored in an ordinary repository. That is why writing one is a small exercise: a Java class per goal, a few annotations, one packaging value in the POM. The page walks through all of it, builds tidepool:check-stations step by step, runs it, breaks it on purpose to collect the real error messages, tests it three ways, and finishes with the Maven 4 plugin API. How to use plugins is on Plugins & Their Configuration; the phases a goal can be bound to are on Maven Build Lifecycle; the alternative that changes how Maven itself builds, a core extension, is on Extensions.

What a plugin is made of

A plugin is a JAR whose META-INF/maven/plugin.xml describes one or more goals. Each goal is implemented by a Mojo, the name being a play on POJO (plain old Java object) with "Maven" in place of "plain". The descriptor says, for every goal, its name, the class that implements it, the phase it fits into by default, the Maven features it needs and every parameter with its type, default value and the user property that sets it. Maven reads the descriptor to decide what to run and how to configure it; the Java code is loaded only when the goal runs.

The descriptor is not written by hand. The Maven Plugin Plugin (maven-plugin-plugin, from the Maven Plugin Tools project) generates it from the annotations and the Javadoc of the Mojo classes while the plugin is built, and the maven-plugin packaging wires that into the lifecycle. The two diagrams show the two halves: how the JAR comes to be, and what Maven does with it when someone types a goal:

The tidepool goal

tidepool:check-stations validates the station files that the tidepool engine reads (data/stations.csv, one station per row with id, name, latitude, longitude and a semicolon-separated list of constituents). The checks are the ones of the Ant task: five columns per row, latitude within [-90, 90], longitude within [-180, 180], no duplicate ids, enough constituents, every required id present. What each part does:

  • The coordinates. The artifactId follows the convention <prefix>-maven-plugin, which is what lets Maven derive the goal prefix tidepool by itself. The pattern maven-<prefix>-plugin is reserved for the plugins of the Apache Maven project under the groupId org.apache.maven.plugins, and the official guide calls using it an infringement of the Apache Maven trademark.

  • The packaging. maven-plugin gives the project its own set of lifecycle bindings (next section) and tells Maven that the artifact has to carry a descriptor.

  • Three provided dependencies. maven-plugin-api for AbstractMojo and the exceptions, maven-core for MavenProject, RuntimeInformation and the other build objects, and maven-plugin-annotations for @Mojo and @Parameter. They are provided because Maven supplies them at run time. Their version is the oldest Maven that the plugin supports: the descriptor generated below records requiredMavenVersion 3.9.16 from it and requiredJavaVersion 21 from maven.compiler.release. Maven enforces the Java requirement (see the mistakes section for the message). In a test with a plugin that declared requiredMavenVersion 3.99.0, Maven 3.9.16, 3.10.0 and 4.0.0-rc-7 ran the goal without any complaint, so that entry is documentation rather than a guard.

  • maven-reporting-impl is the one compile-scope dependency, needed only by the report goal. It brings the Doxia sink API and a few helper libraries into the plugin class realm, which is why a plugin without report goals should not have it.

  • maven-plugin-plugin with a helpmojo execution. The descriptor goal is bound by the packaging; the helpmojo goal is not, and generates the help goal described below. Its version is pinned to the Plugin Tools version, as the official guide does.

  • project.build.outputTimestamp makes the JAR reproducible, see Security & Reproducible Builds.

  • Every plugin version is pinned in pluginManagement, as everywhere in this section.

The Mojo class

The checks live in a plain class that knows nothing about Maven. It reports findings through two callbacks, so a Mojo can send them to the Maven log and a unit test can collect them in a list:

tidepool-maven-plugin/src/main/java/io/tidepool/maven/StationChecker.java
package io.tidepool.maven;

import java.io.File;
import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.util.List;
import java.util.Set;
import java.util.function.BiConsumer;

/** The checks behind the goals, kept free of Maven types so that they are easy to test. */
final class StationChecker {

    /** Receives one finding: the severity and the text. */
    enum Severity { ERROR, WARNING }

    private final int minConstituents;
    private final BiConsumer<Severity, String> findings;
    private final BiConsumer<String, String> rows;

    StationChecker(int minConstituents, BiConsumer<Severity, String> findings, BiConsumer<String, String> rows) {
        this.minConstituents = minConstituents;
        this.findings = findings;
        this.rows = rows;
    }

    /** Checks one file, adds the station ids to {@code seen} and returns the number of problems. */
    int check(File input, Set<String> seen) throws IOException {
        List<String> lines = Files.readAllLines(input.toPath(), StandardCharsets.UTF_8);
        int problems = 0;
        for (int i = 1; i < lines.size(); i++) {      // line 0 is the header
            String[] f = lines.get(i).split(",", -1);
            String where = input.getName() + ":" + (i + 1);
            rows.accept(where, lines.get(i));
            if (f.length != 5) {
                findings.accept(Severity.ERROR, where + " expected 5 columns, found " + f.length);
                problems++;
                continue;
            }
            if (!seen.add(f[0])) {
                findings.accept(Severity.ERROR, where + " duplicate station id " + f[0]);
                problems++;
            }
            problems += range(where, "latitude", f[2], -90, 90);
            problems += range(where, "longitude", f[3], -180, 180);
            int n = f[4].isEmpty() ? 0 : f[4].split(";").length;
            if (n < minConstituents) {
                findings.accept(Severity.WARNING,
                        where + " has " + n + " constituent(s), at least " + minConstituents + " required");
                problems++;
            }
        }
        return problems;
    }

    private int range(String where, String what, String text, double min, double max) {
        try {
            double v = Double.parseDouble(text);
            if (v < min || v > max) {
                findings.accept(Severity.ERROR, where + " " + what + " " + v + " is outside [" + min + ", " + max + "]");
                return 1;
            }
            return 0;
        } catch (NumberFormatException e) {
            findings.accept(Severity.ERROR, where + " " + what + " is not a number: '" + text + "'");
            return 1;
        }
    }
}

The goal itself extends org.apache.maven.plugin.AbstractMojo, which supplies getLog() and the Mojo interface, and implements execute():

import java.io.File;

/**
 * Validates tidepool station files: five columns per row, latitude within [-90, 90], longitude within
 * [-180, 180], no duplicate ids, enough constituents and every required id present.
 *
 * @since 1.0.0
 */
@Mojo(name = "check-stations", defaultPhase = LifecyclePhase.VALIDATE, threadSafe = true)
public class CheckStationsMojo extends AbstractMojo {

    /** The station file to check. */
    @Parameter(property = "tidepool.file", defaultValue = "${project.basedir}/data/stations.csv")
    private File file;

    /** More station files, checked together with {@code file}. */
    @Parameter
    private List<File> files;

    /** Station ids that must be present in the checked files. */
    @Parameter(property = "tidepool.required")
    private List<String> required;

    /** Every station needs at least this many constituents. */
    @Parameter(property = "tidepool.minConstituents", defaultValue = "1")
    private int minConstituents;

    /** Fail the build when a problem is found, or only warn. */
    @Parameter(property = "tidepool.failOnError", defaultValue = "true")
    private boolean failOnError;

    /** {@code SUMMARY} or {@code FULL}; {@code FULL} also lists the station ids that were seen. */
    @Parameter(property = "tidepool.report", defaultValue = "SUMMARY")
    private ReportMode report;

    /** Name of a project property that receives the number of problems. */
    @Parameter(property = "tidepool.resultProperty")
    private String resultProperty;

    /** Skip the check. */
    @Parameter(property = "tidepool.skip", defaultValue = "false")
    private boolean skip;

    private final MavenProject project;
    private final RuntimeInformation runtime;

    @Inject
    public CheckStationsMojo(MavenProject project, RuntimeInformation runtime) {
        this.project = project;
        this.runtime = runtime;
    }

    @Override
    public void execute() throws MojoExecutionException, MojoFailureException {
        if (skip) {
            getLog().info("Skipping the station check");
            return;
        }
        getLog().debug("Running on Maven " + runtime.getMavenVersion());
        List<File> inputs = new ArrayList<>();
        if (file != null) {
            inputs.add(file);
        }
        if (files != null) {
            inputs.addAll(files);
        }
        if (inputs.isEmpty()) {
            throw new MojoExecutionException("Set file or files");
        }

        StationChecker checker = new StationChecker(minConstituents,
                (severity, text) -> {
                    if (severity == StationChecker.Severity.ERROR) {
                        getLog().error(text);
                    } else {
                        getLog().warn(text);
                    }
                },
                (where, row) -> getLog().debug("Row " + where + " -> " + row));

        int problems = 0;
        Set<String> seen = new TreeSet<>();
        for (File input : inputs) {
            getLog().debug("Checking " + input.getName());
            try {
                problems += checker.check(input, seen);
            } catch (IOException e) {
                throw new MojoExecutionException(
                        "Cannot read " + input + " (" + e.getClass().getSimpleName() + ")", e);
            }
        }
        if (required != null) {
            for (String id : required) {
                if (!seen.contains(id)) {
                    getLog().error("Required station " + id + " is missing");
                    problems++;
                }
            }
        }

        if (report == ReportMode.FULL) {
            getLog().info("Stations seen: " + String.join(",", seen));
        }
        if (resultProperty != null) {
            project.getProperties().setProperty(resultProperty, Integer.toString(problems));
        }
        if (problems == 0) {
            getLog().info(inputs.size() + " file(s), " + seen.size() + " station(s): OK");
        } else if (failOnError) {
            throw new MojoFailureException(problems + " problem(s) found in station data");
        } else {
            getLog().warn(problems + " problem(s) found in station data");
        }
    }
}

Types and conversion

Maven converts the text of a <configuration> element, or of a -D property, to the type of the field. The rules are in the configuration guide; these are the types that check-stations uses, and what the runs below show:

Field type Conversion

boolean, int and the other primitives and wrappers

The wrapper’s own parser. A bad value fails before execute().

java.io.File

new File(String) with the separators normalized; a relative file is made absolute against the project’s base directory, which is why -Dtidepool.file=data/bad.csv works.

an enum

Enum.valueOf(String), so the case must match the constant exactly.

String

The text as it is, after expression evaluation.

One child element per item, whatever its name; the element name does not matter. Since Maven 3.3.9 a comma-separated text also works, and that is what -Dtidepool.required=SF,HNL relies on. Items are converted by the type argument of the list.

Build objects and injection

A Mojo usually needs more than its own parameters: the project, the session, the plugin’s own descriptor, the Maven version, the settings. Maven offers them in three ways; the first is used by check-stations.

Constructor injection with JSR-330 is the form to use in new code. The Mojo has one public constructor annotated with @Inject (javax.inject.Inject on Maven 3), and Maven (through its Eclipse Sisu container) passes the objects in. The official annotations page lists the injectable build objects: MavenSession, MavenProject, MojoExecution, and any component of Maven or of another extension, such as RuntimeInformation used here to log the Maven version. A Mojo with a constructor has final fields and can be created in a unit test with plain new, or with Mockito mocks, without a container. No annotation processing is needed: the descriptor does not list injected constructor arguments, as the plugin.xml excerpt above shows.

Pseudo-parameters are the older way: a read-only parameter whose default is an expression. @Parameter(defaultValue = "${project}", readonly = true) injects the MavenProject; ${session}, ${mojoExecution}, ${plugin} (the plugin descriptor), ${settings}, ${reactorProjects} and the ${project.*} paths work the same. They appear in the descriptor as parameters, and the official page now recommends constructor injection for plugins that target Maven 3.2.5 or later.

Plexus @Component fields are the oldest form, and the one to leave behind. @Component from maven-plugin-annotations injects a Plexus component by role; the build above warns about it, for a field of the report base class: "Mojo station-report uses Plexus Component requirements (@Component annotation) for fields …​ Use JSR 330 annotations to inject dependencies instead." Maven 4 removed Plexus dependency injection as an API (Sisu still ships for compatibility), and the Maven 4 notes say that a plugin that still relies on it must be updated to JSR-330.

Logging and failing

getLog() returns the Maven logger with four levels: debug (shown with -X), info, warn and error. Since Maven 3.1.0 the logging is backed by SLF4J, and the logger is the way to let -q, -X and the logging configuration of the Maven installation decide what the user sees. Ant’s five priorities map onto these four: errors to error, warnings to warn, the verdict to info, and both the per-file and the per-row detail to debug, because Maven has no verbose level between info and debug. The run with -X above shows the rows that check-stations writes at debug level.

A Mojo ends a build by throwing:

  • MojoFailureException: the build failed for a reason that the user can fix, an expected failure such as a failed assertion or a compilation error. check-stations throws it when it found problems.

  • MojoExecutionException: an unexpected problem while the goal ran, such as an unreadable file; the constructor takes the cause, which -e prints. check-stations throws it for an I/O error and for missing input.

  • The Mojo API specification also allows a RuntimeException. It ends the build in the same way, but it signals a bug in the plugin rather than a problem that the user can fix.

The Javadoc of the two classes says that throwing a failure shows "BUILD FAILURE" and an execution exception shows "BUILD ERROR". That is not what Maven 3.10.0 prints: the output of the missing file above shows "BUILD FAILURE" for the MojoExecutionException as well. The difference is only the name in the help link at the end of the message (MojoFailureException against MojoExecutionException, or PluginConfigurationException for the conversion errors), which tools such as IDEs and CI scripts can use. The message of the exception is what users read, so name the file, the value and the reason; the build adds the goal, the execution id and the project. On Maven 4 the exceptions of the new API are different; see the last section.

import org.apache.maven.plugins.annotations.Execute;
import org.apache.maven.plugins.annotations.Mojo;
import org.apache.maven.plugins.annotations.Parameter;

/**
 * Lists the station ids of a file, after the {@code check-stations} goal accepted it.
 *
 * @since 1.0.0
 */
@Mojo(name = "list-stations", threadSafe = true)
@Execute(goal = "check-stations")
public class ListStationsMojo extends AbstractMojo {

    /** The station file to list. */
    @Parameter(property = "tidepool.file", defaultValue = "${project.basedir}/data/stations.csv")
    private File file;

    @Override
    public void execute() throws MojoExecutionException {
        try {
            List<String> lines = Files.readAllLines(file.toPath(), StandardCharsets.UTF_8);
            for (String line : lines.subList(1, lines.size())) {
                String[] f = line.split(",", -1);
                getLog().info(f[0] + " " + f[1]);
            }
        } catch (IOException e) {
            throw new MojoExecutionException("Cannot read " + file, e);
        }
    }
}

A report goal

A plugin can contribute pages to the project site. A report Mojo is a goal that also implements org.apache.maven.reporting.MavenReport; the easy way is to extend AbstractMavenReport from maven-reporting-impl, the dependency of the POM above. The required methods are getOutputPath() (the page name; getOutputName() is deprecated in favour of it but still abstract, so it delegates), getName(Locale), getDescription(Locale) and executeReport(Locale), which writes the page through the Doxia sink:

tidepool-maven-plugin/src/main/java/io/tidepool/maven/StationReportMojo.java
package io.tidepool.maven;

import java.io.File;
import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.util.List;
import java.util.Locale;

import org.apache.maven.doxia.sink.Sink;
import org.apache.maven.plugins.annotations.LifecyclePhase;
import org.apache.maven.plugins.annotations.Mojo;
import org.apache.maven.plugins.annotations.Parameter;
import org.apache.maven.reporting.AbstractMavenReport;
import org.apache.maven.reporting.MavenReportException;

/**
 * Writes a one-page report listing the stations of a file; the page becomes part of the project site.
 *
 * @since 1.0.0
 */
@Mojo(name = "station-report", defaultPhase = LifecyclePhase.SITE, threadSafe = true)
public class StationReportMojo extends AbstractMavenReport {

    /** The station file to report on. */
    @Parameter(property = "tidepool.file", defaultValue = "${project.basedir}/data/stations.csv")
    private File file;

    @Override
    public String getOutputPath() {
        return "station-report";
    }

    /**
     * @deprecated use {@link #getOutputPath()} instead
     */
    @Override
    @Deprecated
    public String getOutputName() {
        return getOutputPath();
    }

    @Override
    public String getName(Locale locale) {
        return "Tidepool Stations";
    }

    @Override
    public String getDescription(Locale locale) {
        return "The tide stations known to this project.";
    }

    @Override
    protected void executeReport(Locale locale) throws MavenReportException {
        List<String> lines;
        try {
            lines = Files.readAllLines(file.toPath(), StandardCharsets.UTF_8);
        } catch (IOException e) {
            throw new MavenReportException("Cannot read " + file, e);
        }
        Sink sink = getSink();
        sink.head();
        sink.title();
        sink.text(getName(locale));
        sink.title_();
        sink.head_();
        sink.body();
        sink.section1();
        sink.sectionTitle1();
        sink.text(getName(locale));
        sink.sectionTitle1_();
        sink.table();
        sink.tableRows(new int[] {Sink.JUSTIFY_LEFT, Sink.JUSTIFY_LEFT, Sink.JUSTIFY_RIGHT, Sink.JUSTIFY_RIGHT}, false);
        sink.tableRow();
        for (String heading : new String[] {"Id", "Name", "Latitude", "Longitude"}) {
            sink.tableHeaderCell();
            sink.text(heading);
            sink.tableHeaderCell_();
        }
        sink.tableRow_();
        for (String line : lines.subList(1, lines.size())) {
            String[] f = line.split(",", -1);
            sink.tableRow();
            for (int i = 0; i < 4; i++) {
                sink.tableCell();
                sink.text(f[i]);
                sink.tableCell_();
            }
            sink.tableRow_();
        }
        sink.tableRows_();
        sink.table_();
        sink.section1_();
        sink.body_();
    }
}

Testing a plugin

The official guide to testing plugins separates the unit test, which checks a Mojo as an isolated unit without a real Maven build, from the functional or integration test, which launches Maven on a project and looks at the result. The advice is to write mostly unit tests and some functional tests. The tidepool plugin has three layers.

Unit tests of the logic

The checks are in StationChecker, free of Maven types, so JUnit alone is enough:

tidepool-maven-plugin/src/test/java/io/tidepool/maven/StationCheckerTest.java
package io.tidepool.maven;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.ArrayList;
import java.util.List;
import java.util.Set;
import java.util.TreeSet;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.io.TempDir;

class StationCheckerTest {

    @TempDir
    Path dir;

    private int check(String csv, int minConstituents, List<String> messages) throws IOException {
        Path file = Files.writeString(dir.resolve("stations.csv"), csv);
        StationChecker checker = new StationChecker(minConstituents,
                (severity, text) -> messages.add(severity + " " + text), (where, row) -> { });
        Set<String> seen = new TreeSet<>();
        return checker.check(file.toFile(), seen);
    }

    @Test
    void acceptsAValidFile() throws IOException {
        List<String> messages = new ArrayList<>();
        int problems = check("id,name,latitude,longitude,constituents\n"
                + "SF,San Francisco,37.8,-122.4,M2:0.5:1;S2:0.1:2\n", 2, messages);
        assertEquals(0, problems);
        assertTrue(messages.isEmpty());
    }

    @Test
    void reportsLatitudeOutOfRangeAndDuplicates() throws IOException {
        List<String> messages = new ArrayList<>();
        int problems = check("id,name,latitude,longitude,constituents\n"
                + "SF,San Francisco,137.8,-122.4,M2:0.5:1\n"
                + "SF,Again,37.8,-122.4,M2:0.5:1\n", 1, messages);
        assertEquals(2, problems);
        assertEquals("ERROR stations.csv:2 latitude 137.8 is outside [-90.0, 90.0]", messages.get(0));
        assertEquals("ERROR stations.csv:3 duplicate station id SF", messages.get(1));
    }

    @Test
    void warnsAboutTooFewConstituents() throws IOException {
        List<String> messages = new ArrayList<>();
        int problems = check("id,name,latitude,longitude,constituents\n"
                + "BOS,Boston,42.3,-71.0,M2:1.3:15\n", 2, messages);
        assertEquals(1, problems);
        assertEquals("WARNING stations.csv:2 has 1 constituent(s), at least 2 required", messages.get(0));
    }
}

This layer needs no Maven API at all, runs in milliseconds and is where the many cases go (one per rule). The official page adds the other plain-JUnit technique: Mojos with constructor injection can be created with new and Mockito mocks for the injected objects.

The plugin testing harness

The Maven Plugin Testing Harness runs a Mojo inside a minimal Maven container: it reads the plugin descriptor from the classpath, builds the Mojo with its injected components and sets the parameters. Version 3.4.0 added a JUnit 5 extension in the package org.apache.maven.api.plugin.testing (@MojoTest, @InjectMojo, @MojoParameter, @Basedir), which the page of the project describes as having similar functionality to the Maven 4 test support, to ease migration. The older JUnit 3 and 4 classes (AbstractMojoTestCase and MojoRule) remain in the 3.5.1 JAR for backward compatibility, and the project says that new tests should use JUnit 5. The dependency, in the POM above, is maven-plugin-testing-harness at the test scope. A test:

tidepool-maven-plugin/src/test/java/io/tidepool/maven/CheckStationsMojoTest.java

The Maven Invoker Plugin runs real Maven builds on small projects kept under src/it and checks the result with a script. It is what Maven’s own plugins use for their integration tests, and the official testing page points to it for functional tests. The Maven 4 plugin API (experimental)

Maven 4 (release candidate) comes with a new plugin API: an immutable model, interfaces in org.apache.maven.api.* and a dependency injection framework, Maven DI, with its own annotations. The Maven 4 notes call it experimental in 4.0.0, advise against using it unless one knows precisely what one is doing, and cite the Maven Compiler Plugin 4.x as a user of it. The Mojo specification page says that it does not cover this API. A plugin written against it runs only on Maven 4, so a plugin that must also run on Maven 3 stays on the Maven 3 API, which Maven 4 is expected to run for every Maven 3 plugin that follows the current practices, as tidepool-maven-plugin did in all the runs above. This section writes the same check against the new API, to show how it differs, and runs it. Plugin Tools 4.x is still a pre-release (4.0.0-beta-2 for the plugin and 4.0.0-beta-3 for the tools on Maven Central on 2026-10-16), so versions and details can change.

The POM declares the Maven 4 API instead of the Maven 3 one: maven-api-core for the interfaces and the Mojo annotations, maven-api-di for @Inject, both at provided; the Maven Plugin Plugin 4.0.0-beta-2 generates a descriptor in the new XML format. The artifactId does not follow the -maven-plugin convention here, so the prefix has to be set:

package io.tidepool.maven4;

import java.io.IOException;
import java.nio.file.Path;
import java.util.List;
import java.util.Set;
import java.util.TreeSet;

import org.apache.maven.api.Project;
import org.apache.maven.api.di.Inject;
import org.apache.maven.api.plugin.Log;
import org.apache.maven.api.plugin.Mojo;
import org.apache.maven.api.plugin.MojoException;
import org.apache.maven.api.plugin.annotations.Parameter;

/**
 * Validates tidepool station files, written against the Maven 4 plugin API.
 *
 * @since 1.0.0
 */
@org.apache.maven.api.plugin.annotations.Mojo(name = "check-stations", defaultPhase = "validate")
public class CheckStationsMojo implements Mojo {

    /** The station file to check. */
    @Parameter(property = "tidepool.file", defaultValue = "${project.basedir}/data/stations.csv")
    Path file;

    /** Station ids that must be present. */
    @Parameter(property = "tidepool.required")
    List<String> required;

    /** Every station needs at least this many constituents. */
    @Parameter(property = "tidepool.minConstituents", defaultValue = "1")
    int minConstituents;

    @Inject
    Log log;

    @Inject
    Project project;

    @Override
    public void execute() throws MojoException {
        log.debug("Project " + project.getArtifactId());
        StationChecker checker = new StationChecker(minConstituents,
                (severity, text) -> {
                    if (severity == StationChecker.Severity.ERROR) {
                        log.error(text);
                    } else {
                        log.warn(text);
                    }
                },
                (where, row) -> log.debug("Row " + where + " -> " + row));
        Set<String> seen = new TreeSet<>();
        int problems;
        try {
            problems = checker.check(file.toFile(), seen);
        } catch (IOException e) {
            throw new MojoException("Cannot read " + file + " (" + e.getClass().getSimpleName() + ")", e);
        }
        if (required != null) {
            for (String id : required) {
                if (!seen.contains(id)) {
                    log.error("Required station " + id + " is missing");
                    problems++;
                }
            }
        }
        if (problems == 0) {
            log.info("1 file(s), " + seen.size() + " station(s): OK");
        } else {
            throw new MojoException(problems + " problem(s) found in station data");
        }
    }
}

Changing the plugin and not reinstalling it

Consumers resolve the plugin from the local repository, so they keep running the old JAR until install (or deploy) runs again.

The last row is the one that costs the most time in practice. It is not an error message: the consumer simply uses the JAR it finds in the local repository. The cure is to run mvn install in the plugin project before running the consumer.

Where older material is outdated

  • Javadoc-tag Mojos. Maven 2 era plugins declared the goal with Javadoc tags (@goal, @phase, @parameter). Plugin Tools still has an extractor for them (it ran on this page’s build and found nothing), but the supported form is the Java annotations of this page, and the official cookbook explains how to upgrade. Maven 4 breaks plugins that still depend on the Maven 2 API.

  • Plexus @Component and plexus-component-annotations. The old way of injecting objects; Maven 4 removed Plexus dependency injection, and the Maven 4 notes ask for JSR-330. Constructor injection also made the Mojo testable without a container.

  • maven-<name>-plugin for your own plugin. The guide now states that the pattern is reserved for the Apache Maven project and that using it infringes the trademark; name plugins <name>-maven-plugin.

  • JUnit 3 AbstractMojoTestCase. Still present in the harness, but the project says that new tests should use the JUnit 5 extension (since 3.4.0).

  • "BUILD ERROR" for MojoExecutionException. The Javadoc of the exception still says so; Maven 3.10.0 prints "BUILD FAILURE" for both exceptions.

  • Books written for Maven 2 and 3.0. They declare Mojos with Javadoc tags. The workflow in this page is the current one: annotations, the generated descriptor, the harness and the Invoker Plugin.
