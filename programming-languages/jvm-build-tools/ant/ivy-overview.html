Ivy: Overview

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Apache Ivy 2.6.0 (announced on 15 July 2026) running inside Apache Ant 1.10.18. Every example marked as run was executed on JDK 26 on 2026-10-16, on macOS, in a scratch directory with its own Ivy cache; output that comes from a run is shown as printed, with the long scratch path shortened to <scratch>, the home directory to <home> and the machine name to <host>. Anything that could not be run here is labelled "not run here". The commands use a POSIX shell.

Ant has no idea what a dependency is. It compiles, copies and packages whatever sits in directories you name, and the JARs those directories need have to get there some other way: checked into version control, copied by hand, or fetched by a get task from a fixed URL. Ivy is the answer the Ant project itself gives to that gap. It is a dependency manager that runs inside Ant (and also on its own from the command line): given a description of what a module needs, it finds those modules in one or more repositories, follows their own dependencies, decides which revision wins when two parts of the graph disagree, downloads the files into a local cache and hands them to the build as a classpath or a directory of JARs. This page is the first of six on Ivy. It covers what Ivy is, how it is installed, and a complete first run; the other five go deep on each part, and are linked where they apply: module descriptors and configurations, settings and resolvers, conflicts and versions, the Ant tasks and publishing and multi-project builds. The other Ant dependency tool, the Resolver Ant Tasks that wrap Maven’s own resolver, has its own page: Maven Resolver Ant Tasks. The language-neutral ideas (coordinates, scopes, transitivity, mediation) are in Dependency Management Fundamentals. The running scenario (tidepool) is described on the section landing page.

What Ivy is, and its status

Ivy describes itself as a tool for managing (recording, tracking, resolving and reporting) project dependencies, characterized by flexibility and configurability and by tight integration with Ant. Three properties follow from that and shape everything else:

  • It is process agnostic. Nothing in Ivy says where files live, how modules are named in a repository, or what a build looks like. Those are settings you provide (or accept from the default settings that ship inside the JAR, which look like Maven Central).

  • It reads Maven metadata. A POM in a repository is a module descriptor to Ivy, so the whole of Maven Central is usable without any conversion. That is what makes the first example below work with no repository configuration at all.

  • Its model is richer than Maven’s scopes. A module can define any number of named configurations (views of itself), and every dependency says which configuration of the other module it needs in which of its own. That is the subject of the next page; this page only introduces the word.

As of the date of this page Ivy is an active subproject of Apache Ant, not in the Attic, and 2.6.0 is the current release. The facts worth knowing before adopting it:

  • Java. Ivy 2.6.0 needs Java 8 or later (the compatibility page gives the floors of every line, reproduced in the table below). Ivy does not require any particular Ant version beyond one that runs on that Java.

  • Not thread-safe. The compatibility page states that Ivy does not support multithreaded use and so should not be used with the Ant <parallel> task. Parallel builds that each run Ivy in a separate JVM are fine; two Ivy resolves inside one JVM are not.

  • IvyDE is archived. The Eclipse plugin, IvyDE, was archived by an Ant PMC vote: its home page says all resources are read only and no further development will be done. Ivy itself is unaffected. IDE support for Ivy-managed projects today means importing the resolved JARs, as the CI & IDE Integration page describes.

  • Security. The 2.6.0 release fixes CVE-2026-26032, a path traversal in the PackagerResolver, reachable only by someone able to add coordinates containing ../ to a packager repository. The release notes also say that if you resolved with a version before 2.6.0, you may need to remove your Ivy cache for some of the fixes to take effect. Earlier advisories (CVE-2022-37865, CVE-2022-37866, CVE-2022-46751) are listed on the same security page.

  • A new conflict manager. 2.6.0 added nearest, which resolves conflicts the way Maven does. The default stays latest-revision. Conflicts are the subject of their own page.

The principle: configure, resolve, retrieve, report, publish

Every use of Ivy is one or more of five steps. They are the same whether you drive them from Ant tasks, as this page does, or from the command line.

flowchart LR S["configure: settings file or built-in default"] --> R["resolve: ivy.xml plus the resolvers"] R --> C[("Ivy cache: repository cache and resolution cache")] C --> T["retrieve: copy the JARs to a directory"] C --> P["cachepath: build a classpath from the cache"] C --> RP["report: HTML and GraphML"] R -.-> PB["publish: deliver ivy.xml and artifacts to a repository"]

  • Configure. Ivy needs a set of dependency resolvers, each able to find descriptors and artifacts given organisation, module, revision, artifact name, type and extension, and a rule saying which resolver serves which module. That is the settings file. When you give none, Ivy uses a built-in default that points an ibiblio resolver at Maven Central (details below). The settings and resolvers page covers everything you can put there.

  • Resolve. The resolve is the moment Ivy actually works out the dependencies of one module. It reads the module’s ivy.xml, asks the resolvers for each dependency’s descriptor, goes through the transitive graph depth first, applies conflict management while it goes so that a losing branch is never downloaded, and finally downloads the artifacts of the winners into the cache. It then writes an XML report per configuration, so that later steps do not walk the graph again. Resolve is also where dynamic revisions such as 1.+ become fixed ones.

  • Retrieve. Copy the resolved artifacts from the cache into a directory structure you choose with a pattern such as build/lib/[conf]/[artifact]-[revision].[ext].

  • Build a path from the cache. Instead of copying, use the files where they are: cachepath turns the resolve report into an Ant path. This is what you want for compiling, and what IDE integrations do. cachefileset does the same as a fileset.

  • Report. An XSL transformation of the resolve report gives an HTML page (and a GraphML file for graph tools) of who needed what.

  • Publish. Deliver a version of your own module, a resolved ivy.xml plus its artifacts, into a repository so others can depend on it. That is the subject of the publishing page; the dashed arrow in the figure marks that it is a separate step that starts from the same module, not part of a dependency resolve.

Installing Ivy

Ivy is one JAR, ivy-2.6.0.jar, 1,413,973 bytes, 889 entries, published as org.apache.ivy:ivy:2.6.0 on Maven Central. Its only job at install time is to be on Ant’s classpath so that the antlib:org.apache.ivy.ant tasks exist. The JAR has optional dependencies, such as Apache HttpClient and Jsch (the compatibility page names both) and Commons Compress for pack200 (the 2.6.0 release notes); their versions are in Ivy’s own descriptor, and you add them only when you use the feature that needs them.

mkdir -p lib
curl -fsSL -o lib/ivy-2.6.0.jar https://repo1.maven.org/maven2/org/apache/ivy/ivy/2.6.0/ivy-2.6.0.jar
curl -fsSL https://repo1.maven.org/maven2/org/apache/ivy/ivy/2.6.0/ivy-2.6.0.jar.sha1
shasum -a 1 lib/ivy-2.6.0.jar

Letting the build file fetch Ivy

The documentation’s "automatic" installation is a self-contained snippet: download the JAR once into a directory under the user’s home, then taskdef from there. Its pinned version in the documentation is 2.5.0, which is out of date; below it is set to 2.6.0. This is the complete build file used for the compile example later on this page, so it is shown whole:

<project name="tidepool-engine" default="compile" xmlns:ivy="antlib:org.apache.ivy.ant">
  <property name="ivy.install.version" value="2.6.0"/>
  <condition property="ivy.home" value="${env.IVY_HOME}">
    <isset property="env.IVY_HOME"/>
  </condition>
  <property name="ivy.home" value="${user.home}/.ant"/>
  <property name="ivy.jar.dir" value="${ivy.home}/lib"/>
  <property name="ivy.jar.file" value="${ivy.jar.dir}/ivy.jar"/>

  <target name="download-ivy" unless="offline">
    <mkdir dir="${ivy.jar.dir}"/>
    <get src="https://repo1.maven.org/maven2/org/apache/ivy/ivy/${ivy.install.version}/ivy-${ivy.install.version}.jar"
         dest="${ivy.jar.file}" usetimestamp="true"/>
  </target>

  <target name="init-ivy" depends="download-ivy">
    <path id="ivy.lib.path">
      <fileset dir="${ivy.jar.dir}" includes="*.jar"/>
    </path>
    <taskdef resource="org/apache/ivy/ant/antlib.xml" uri="antlib:org.apache.ivy.ant" classpathref="ivy.lib.path"/>
  </target>

  <target name="resolve" depends="init-ivy" description="resolve the dependencies">
    <ivy:resolve/>
  </target>

  <target name="compile" depends="resolve" description="compile the model and the engine">
    <ivy:cachepath pathid="compile.classpath" conf="compile"/>
    <mkdir dir="build/classes"/>
    <javac destdir="build/classes" release="21" includeantruntime="false" classpathref="compile.classpath">
      <src path="src/model"/>
      <src path="src/engine"/>
    </javac>
    <pathconvert property="cp.names" refid="compile.classpath" pathsep=" ">
      <mapper type="flatten"/>
    </pathconvert>
    <echo message="compiled against: ${cp.names}"/>
  </target>

  <target name="report" depends="resolve" description="write the HTML resolve reports">
    <ivy:report todir="build/report"/>
  </target>
</project>

How it works, line by line: ivy.home is IVY_HOME if that environment variable is set and <home>/.ant otherwise (the condition sets it only when the variable exists, and the later property is then ignored because properties are immutable). download-ivy fetches the JAR with get and usetimestamp, so it is downloaded again only when Maven Central has a newer file; -Doffline=true skips it through unless. init-ivy builds a path from every JAR in that directory and taskdef`s the Antlib resource under the Antlib URI. Because `<home>/.ant/lib is also one of the directories Ant puts on its own classpath, a JAR downloaded by the first run is picked up automatically by later runs; the explicit taskdef is what makes the first run work. A first resolve and retrieve

The smallest useful Ivy project is two files. ivy.xml says what the tidepool engine module needs; build.xml runs resolve and retrieve.

<ivy-module version="2.0">
  <info organisation="io.tidepool" module="tidepool-engine" revision="1.0.0"/>
  <configurations>
    <conf name="compile" description="needed to compile"/>
    <conf name="runtime" extends="compile" description="needed to run"/>
  </configurations>
  <dependencies>
    <dependency org="org.apache.commons" name="commons-csv" rev="1.14.1" conf="compile->default"/>
  </dependencies>
</ivy-module>
<project name="tidepool-engine" default="resolve" xmlns:ivy="antlib:org.apache.ivy.ant">
  <target name="resolve" description="resolve and retrieve the dependencies">
    <ivy:resolve/>
    <ivy:retrieve pattern="build/lib/[conf]/[artifact]-[revision].[ext]"/>
  </target>
</project>

Reading ivy.xml: info identifies the module (organisation, module, revision). configurations declares two views of it; runtime extends compile, which means everything required in compile is also required in runtime. The one dependency is commons-csv at an exact revision, and conf="compile->default" reads "in my compile configuration I need the default configuration of that module". Because the Maven POM of commons-csv is converted to Ivy configurations on the fly, default there means its own JAR plus its runtime dependencies. The ivy:resolve task with no attributes reads ivy.xml from the project directory, and ivy:retrieve copies into the pattern, where [conf], [artifact], [revision] and [ext] are tokens Ivy replaces. The next page, Ivy: Module Descriptors & Configurations, explains every part of that file.

What the default settings do

The default configuration is not a single resolver. It is five small files inside the JAR that are included in turn, and reading them explains the word public in the log and where local and shared come from. This is their content, read from the 2.6.0 JAR:

<ivysettings>
    <settings defaultResolver="default"/>
    <include url="${ivy.default.settings.dir}/ivysettings-public.xml"/>
    <include url="${ivy.default.settings.dir}/ivysettings-shared.xml"/>
    <include url="${ivy.default.settings.dir}/ivysettings-local.xml"/>
    <include url="${ivy.default.settings.dir}/ivysettings-main-chain.xml"/>
    <include url="${ivy.default.settings.dir}/ivysettings-default-chain.xml"/>
</ivysettings>
<ivysettings>
    <resolvers>
        <ibiblio name="public" m2compatible="true"/>
    </resolvers>
</ivysettings>

The other files define a filesystem resolver shared rooted at ${ivy.default.ivy.user.dir}/shared, a filesystem resolver local rooted at ${ivy.default.ivy.user.dir}/local, a chain named main with dual="true" that tries shared then public, and a chain named default with returnFirst="true" and checkmodified="true" that tries local then main. So, in plain words, a dependency is looked up in the local repository (the repository the Ivy tutorials publish to, a rough counterpart of Maven’s local repository for your own builds), then in a shared file repository, then in Maven Central, and the first hit wins. The ibiblio resolver with no root attribute points at Maven Central, as the principle page says. That is the whole reason a descriptor with a Maven coordinate works with no settings.

ivy.default.ivy.user.dir is the variable that points at the Ivy home directory; unless set it is .ivy2 in the user’s home directory (confirmed here by running with a different user.home, which created .ivy2/cache under it). The cache is in its cache subdirectory. All the examples on these pages set -Divy.default.ivy.user.dir=<scratch>/ivyuser on the command line, because Ant properties are imported as Ivy variables, so that nothing was written to the real ~/.ivy2 and the examples start from a known cache. That variable is used by the default settings but is not described on the settings reference page; treat setting it from the command line as a convenience, not a contract. For a project you would write your own settings file (and set the cache there with the caches element). The settings and resolvers page covers that.

The Ivy cache

Ivy’s cache has two parts, and the difference matters for sharing it and for cleaning it:

  • The repository cache holds what was downloaded from repositories, with a small properties file per module recording where each file came from. It can be shared between machines or users if you pick a suitable lock strategy.

  • The resolution cache holds the results of resolves, so that retrieve, cachepath and report can reuse them. It is overwritten by every resolve and must never be used by two processes at once.

The directory under the module is the artifact type with an s added, from the default cache pattern [organisation]/[module](/[branch])/[type]s/[artifact]-[revision](-[classifier])(.[ext]) (no branch here, so that part is dropped), so a source artifact would go in sources and a bundle in bundles.

Three points from the Ivy side of the comparison are still true, and one is not. Still true: Ivy is far more configurable, since resolvers, conflict managers, version matchers and parsers are all plug-in points, and it can split metadata and artifacts into different repositories; the Maven comparison page notes that Maven has no repository chaining. Still true: Ivy’s reference documentation is extensive and covers every feature with examples. No longer true as stated: the comparison page says that in Maven "none of your dependencies will ever manage to get foo 1.1" without a change in your own declaration, as if that were a limitation. That is Maven’s nearest-wins rule, which Ivy can now apply itself with the nearest conflict manager, and which Maven has long complemented with dependencyManagement and BOMs (Maven dependencies, scopes and mediation). Gradle can also consume Ivy repositories and modules, which is the common bridge when a company has an Ivy repository and a Gradle build (Gradle repositories and content filtering).

When to choose Ivy today: you have an Ant build you do not want to migrate, you need configurations richer than Maven’s scopes, or you run a repository with a layout or a metadata format that Maven’s resolver cannot read. When not to: a new project with no Ant legacy will be better served by Maven or Gradle, and an Ant build that only needs to download a few JARs from Maven Central may be simpler with the Maven Resolver Ant Tasks, whose model is the same as Maven’s. Common problems

  • The ivy: tasks are undefined. The Ivy JAR is not on Ant’s classpath. See the failing run above: use -lib, copy the JAR to <home>/.ant/lib, or taskdef it.

  • Two Ivy resolves in parallel in one JVM. Ivy is not thread-safe. Do not call ivy:* tasks from within <parallel>, and be careful with subant and antcall inside <parallel>.

  • ~/.ivy2 full of stale modules after an Ivy upgrade. Delete the cache once after moving to a new Ivy line, as the release notes advise.

  • The wrong Ivy version is used. A JAR in ANT_HOME/lib always takes precedence over one added with taskdef, as a comment in the documentation’s own snippet says; ant -diagnostics includes a listing of the JARs in ANT_HOME/lib. Keep one Ivy on the classpath.

  • Everything resolves, but far more than expected is downloaded. The default configuration mapping of a dependency with no conf is *->*, which for a Maven module includes its test dependencies. This is the most expensive Ivy surprise and is demonstrated, with real output, on the next page.
