Maven Resolver Ant Tasks

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against the Maven Resolver Ant Tasks 2.0.0, released on 6 August 2026, running on Apache Ant 1.10.18 with JDK 26 on macOS. Every example was run on 2026-10-16 in a scratch directory (the tidepool toolkit described on the section landing page), and the one example that matters for the Java floor was run again on JDK 17. Output is shown as Ant printed it; the scratch directory is shortened to . and Ant’s own directory to $ANT_HOME. Lines of download progress that do not matter for the point being made are left out, and the text says so each time. Maven Central and the project pages were reached on the same day.

The Maven Resolver Ant Tasks are the Apache Maven project’s answer to the question "how does an Ant build use Maven repositories?". They put the library that Maven itself uses to find and download artifacts, Maven Resolver, behind a few Ant tasks and types: resolve collects and downloads dependencies and turns them into paths, file sets or properties, install copies built artifacts into a local repository, and deploy uploads them to a remote one. The same coordinates, the same settings.xml, the same mirror and proxy rules and the same repository layout as Maven apply, so an Ant build can consume what Maven builds publish and the other way round. The sibling page Ivy Overview describes the other way to manage dependencies in Ant; the table near the end of this page helps to choose between them. Dependency concepts such as scopes and mediation are explained in Dependency Management Fundamentals.

Making Ant load the tasks

The tasks are an antlib: a JAR with a descriptor, org/apache/maven/resolver/ant/antlib.xml, that lists the task and type names. Antlibs are used through an XML namespace whose URI starts with antlib:; for this one it is antlib:org.apache.maven.resolver.ant. The prefix is free; this page uses resolver:, matching the log lines Ant prints. There are two ways to make Ant find the JAR, and both were run.

Declare it in the build file. The official page recommends copying the JAR into the project’s lib directory and loading it with taskdef, so the build carries its own copy and needs no Ant installation changes:

resolve-basic.xml
<?xml version="1.0" encoding="UTF-8"?>
<project name="resolve-basic" default="resolve" basedir="."
         xmlns:resolver="antlib:org.apache.maven.resolver.ant">
  <taskdef uri="antlib:org.apache.maven.resolver.ant"
           resource="org/apache/maven/resolver/ant/antlib.xml"
           classpath="lib/maven-resolver-ant-tasks-2.0.0-uber.jar"/>

  <resolver:localrepo dir="build/m2"/>

  <target name="resolve">
    <resolver:resolve>
      <dependencies>
        <dependency coords="org.apache.commons:commons-csv:1.14.1"/>
      </dependencies>
      <path refid="compile.classpath" classpath="compile"/>
      <files refid="lib.files" dir="build/lib" layout="{artifactId}-{version}.{extension}"/>
      <properties prefix="dep."/>
    </resolver:resolve>
    <echo>path   : ${toString:compile.classpath}</echo>
    <echo>dep.org.apache.commons:commons-csv:jar = ${dep.org.apache.commons:commons-csv:jar}</echo>
  </target>
</project>

Put it on Ant’s own classpath. With the JAR in -lib, in ~/.ant/lib or in $ANT_HOME/lib, the taskdef line is unnecessary, because Ant looks up an antlib: namespace on its classpath. The same build file without the taskdef failed without the library and worked with it:

What the antlib defines

The descriptor inside the JAR defines these names. Notice that pom is declared as a task although the site documents it as a type, and that createPom is not described on the site’s main page at all (it is in the usage.md guide and the API documentation):

Kind Names

Tasks

resolve, install, deploy, createPom, pom

Types

authentication, proxy, mirror, localrepo, remoterepo, remoterepos, dependency, dependencies, artifact, artifacts, settings, dependencyManagement

The nested elements of a task are matched by Ant’s introspection on the local element name, not on the namespace, so inside a <resolver:resolve> a nested <dependencies> needs no prefix (a prefixed <resolver:dependencies> works too, and a top-level definition outside a task needs the prefix). All examples below use the unprefixed form for nested elements.

Settings, repositories and mirrors

Where the settings come from

The tasks read the same settings.xml as Maven. By default the user file is ${user.home}/.m2/settings.xml; for the global file the site lists ${ant.home}/etc/settings.xml and ${maven.home}/conf/settings.xml. The <settings> type changes both locations. The global-file search order is taken from the site and was not run here. With no settings file and no localrepo, the local repository was the Maven default, ~/.m2/repository: the first, throw-away experiment of this page resolved commons-csv-1.14.1.jar to /Users/…/.m2/repository/org/apache/commons/commons-csv/1.14.1/…. That sharing is usually what a developer wants, because Maven and Ant builds reuse each other’s downloads, and sometimes what a CI job does not want, so a project-local <localrepo dir="build/m2"/> (as used in this page) is the way to isolate it.

A settings file can supply the local repository, mirrors, servers (credentials) and proxies. This settings.xml was used in the next example; the credentials are placeholders that read environment variables, and the example does not contact any server that needs them, so credential handling was not run here:

settings/settings.xml
<?xml version="1.0" encoding="UTF-8"?>
<settings xmlns="http://maven.apache.org/SETTINGS/1.2.0">
  <localRepository>${user.dir}/build/m2-from-settings</localRepository>
  <mirrors>
    <mirror>
      <id>tidepool-mirror</id>
      <mirrorOf>central</mirrorOf>
      <url>https://repo.maven.apache.org/maven2/</url>
    </mirror>
  </mirrors>
  <servers>
    <server>
      <id>internal</id>
      <username>${env.REPO_USER}</username>
      <password>${env.REPO_TOKEN}</password>
    </server>
  </servers>
</settings>

The repository and network types

These types can be declared at the project level (then they apply to every task) or nested in a task. Attribute names come from the site and from the classes in the JAR.

Element Attributes and notes

localrepo

dir. Only one local repository can be in use at a time. Its default is Maven’s.

remoterepo

id, url, type (default default), releases and snapshots (booleans, or nested <releases enabled updates checksums/> and <snapshots .../>), updates (always, daily, never or an interval), checksums (fail, warn, ignore), a nested <authentication> or authref. The site says only file:, http: and https: URLs are supported.

remoterepos

A named group of <remoterepo> elements (and nested <remoterepos>), usable "in every place that is legal for a remote repository". A refid reuses a definition.

mirror

id, url, type, mirrorOf (the same patterns as Maven), a nested authentication.

proxy

host, port, type, nonProxyHosts, a nested authentication. There can be several; the first whose nonProxyHosts does not match the host is used. Not run here (it needs a proxy).

authentication

username, password, privateKeyFile, passphrase, servers (the repository ids it applies to; without it the authentication must be referenced explicitly). Not run here.

settings

file, globalfile.

The project-level declaration of two repositories and a group, taken from the consuming build that appears later in this page, shows the syntax:

<resolver:localrepo dir="build/m2-consumer"/>
<resolver:remoterepo id="tidepool.local" url="file://${basedir}/build/repo" snapshots="false" checksums="fail"/>
<resolver:remoterepos id="all">
  <remoterepo refid="tidepool.local"/>
  <remoterepo id="central" url="https://repo.maven.apache.org/maven2/" snapshots="false"/>
</resolver:remoterepos>

Which repositories does resolve use? The task uses the repositories nested in it or referenced with remoteReposRef; if it has none, it uses the group with the id resolver.repositories, which by default contains only Central. Declaring your own <remoterepos id="resolver.repositories"> replaces that default for every resolve in the build:

<resolver:remoterepos id="resolver.repositories">
  <remoterepo id="tidepool.local" url="file://${basedir}/build/repo"/>
  <remoterepo id="central" url="https://repo.maven.apache.org/maven2/"/>
</resolver:remoterepos>

Run with ant -v, the task then reported Using remote repository tidepool.local (file://./build/repo, default, releases) followed by Using remote repository central, and resolved io.tidepool:tidepool-engine:1.0.0 from the first.

Explicit repositories do not stop Central from being used for transitive dependencies. In the checksum experiment below, resolve was given only one repository, a file repository holding only the tidepool artifacts. The tidepool POM was read from it, but commons-csv and its parents came from Central:

[resolver:resolve] Downloaded from central https://repo.maven.apache.org/maven2/org/apache/commons/commons-csv/1.14.1/commons-csv-1.14.1.pom

Maven works the same way: the repositories declared inside a dependency’s POM, including the central repository of the Super POM that every POM inherits, are added when that dependency’s own dependencies are collected. A build that must not contact Central has to say so with a mirror (<mirrorOf>*</mirrorOf>) in the settings file, not only with its own repository list. For a build that has no mirror a safe check is an offline run, below.

Offline mode

Setting the property resolver.offline to true suppresses all network traffic: only artifacts and metadata already in the local repository are used. It can be set in the build file or, as here, on the command line. With an empty local repository the build fails, with a message that names the cause; with a populated one it succeeds:

rm -rf build/m2
ant -Dresolver.offline=true -f resolve-basic.xml      # cold
ant -f resolve-basic.xml                              # fill the cache
ant -Dresolver.offline=true -f resolve-basic.xml      # warm

Declaring dependencies

Dependencies are Ant types, so they can be declared once, given an id and reused by several resolve tasks. A <dependency> has two spellings that mean the same:

<dependency coords="org.apache.commons:commons-csv:1.14.1"/>
<dependency groupId="org.apache.commons" artifactId="commons-csv" version="1.14.1"
            classifier="" type="jar" scope="compile">
  <exclusion groupId="commons-codec" artifactId="commons-codec"/>
</dependency>

The coords format is groupId:artifactId:version[[:type[:classifier]]:scope]: the type and classifier are optional, the scope is last. The attributes are groupId, artifactId, version, classifier, type, scope and systemPath (for system scope dependencies), and nested <exclusion> elements take groupId, artifactId, classifier, extension or coords (g:a). A <dependencies> element groups dependencies, global <exclusion> elements and other <dependencies> groups (refid), and can be filled from a POM or from a text file. The three sources of dependencies can be mixed.

This run answers most questions about the pom type and about scopes:

  • Properties. A POM registered from a file makes its effective model available as Ant properties, prefixed with the id of the <pom> element (pom. when it has none): ${pom.groupId}, ${pom.artifactId}, ${pom.version}, ${pom.name}, and the POM’s own <properties> as ${pom.properties.csv.version}. A <pom> can also be declared without a file, with groupId, artifactId, version and packaging, or with coords="g:a:v"; then there is no POM file to install, and install and deploy refuse to run (see the errors table).

  • The default POM. A <pom> built from a file becomes the default for install, deploy and resolve when it has no id, and also when it has one but no default POM exists yet (Pom.execute() in 2.0.0); a later <pom> with an id does not replace an existing default, a later one without an id does. The log says Using default POM (…) when that happens. The default id is resolver.pom, a constant in the JAR.

  • Scope filters. The classpath shortcut on a <path>, <files> or <properties> target is shorthand for a list of scopes. The site defines classpath="compile" as provided,system,compile.   • Transitive scope. The transitive dependencies of junit-jupiter-api (opentest4j, junit-platform-commons, apiguardian-api and jspecify) arrived with the test scope of the dependency that brought them.

Versions without a version: BOMs with dependencyManagement

Since 1.6.0 the dependencyManagement type brings Maven’s dependency management to an Ant build: a BOM imported with type="pom" scope="import" supplies the versions that dependency elements leave out. It is combined with the dependencies by a registered POM, which createPom produces (next section). The resolve task in detail

<resolve> has one required input, <dependencies> (nested, or dependenciesRef, or the default POM) and any number of outputs.

Element or attribute Meaning

<dependencies>, dependenciesRef

The dependencies to resolve. At most one per task. Without one, the default POM is used; with neither, the build fails with No <dependencies> set for resolution.

<remoterepo>, <remoterepos>, remoteReposRef

Repositories to use for this task instead of resolver.repositories.

failOnMissingAttachments

Fail when a requested sources or javadoc attachment does not exist (see below). The default is false. It is an attribute of the task only; <properties> and <files> take attachments but not this flag.

<path refid classpath scopes>

Defines an Ant path with the resolved JARs.

<files refid dir layout attachments classpath scopes>

Defines a resource collection with refid, and copies the files to dir when it is given. layout is allowed only with dir; its placeholders are {groupId}, {groupIdDirs} (the group with slashes), {artifactId}, {version}, {baseVersion} (the -SNAPSHOT form), {extension} and {classifier}. attachments is sources or javadoc (a single value; a comma-separated list is rejected).

<properties prefix attachments classpath scopes>

Sets one property per artifact, prefix first, then groupId:artifactId:extension.

Each of the three targets can appear more than once in the same task, which is how the examples above produced the compile, runtime and test paths from one dependency graph and one set of downloads.

Attachments: sources and Javadoc

attachments="sources" or "javadoc" asks for the -sources or -javadoc classifier of every resolved artifact. That is how an Ant build feeds an IDE or a documentation task. Many artifacts do not publish both, so the behaviour for the missing ones is configurable. ant-launcher 1.10.15 has sources but no Javadoc on Central:

attachments.xml
<?xml version="1.0" encoding="UTF-8"?>
<project name="attachments" default="sources" basedir="."
         xmlns:resolver="antlib:org.apache.maven.resolver.ant">
  <taskdef uri="antlib:org.apache.maven.resolver.ant"
           resource="org/apache/maven/resolver/ant/antlib.xml"
           classpath="lib/maven-resolver-ant-tasks-2.0.0-uber.jar"/>
  <resolver:localrepo dir="build/m2"/>

  <target name="sources">
    <resolver:resolve failOnMissingAttachments="${strict}">
      <dependencies>
        <dependency coords="org.apache.ant:ant-launcher:1.10.15"/>
      </dependencies>
      <files dir="build/attachments" attachments="sources" layout="{artifactId}-{version}-{classifier}.{extension}"/>
      <files dir="build/attachments" attachments="javadoc" layout="{artifactId}-{version}-{classifier}.{extension}"/>
    </resolver:resolve>
  </target>
</project>

Publishing: install and deploy

Where resolve reads, install and deploy write. Both need to know what is being published (the artifacts) and as what (the POM that gives group, artifact and version). The artifacts are <artifact file="…" type="…" classifier="…"/> elements, nested or grouped under an <artifacts id="…"> and referenced with artifactsRef. The POM is a <pom file="…"/> registered earlier, nested in the task, or referenced with pomRef. A <pom> that has a file is required: the site states "you need to set a POM that references a file", because the POM file itself is uploaded next to the artifacts.

publish.xml
<?xml version="1.0" encoding="UTF-8"?>
<project name="tidepool" default="install" basedir="."
         xmlns:resolver="antlib:org.apache.maven.resolver.ant">
  <taskdef uri="antlib:org.apache.maven.resolver.ant"
           resource="org/apache/maven/resolver/ant/antlib.xml"
           classpath="lib/maven-resolver-ant-tasks-2.0.0-uber.jar"/>

  <property name="build.dir" location="build"/>
  <resolver:pom file="pom.xml" id="pom"/>

  <target name="package">
    <mkdir dir="${build.dir}/classes"/>
    <javac srcdir="src/main/java" destdir="${build.dir}/classes" release="17" includeantruntime="false"/>
    <jar destfile="${build.dir}/${pom.artifactId}-${pom.version}.jar" basedir="${build.dir}/classes"/>
    <jar destfile="${build.dir}/${pom.artifactId}-${pom.version}-sources.jar" basedir="src/main/java"/>
  </target>

  <target name="install" depends="package">
    <resolver:localrepo dir="${build.dir}/m2-install"/>
    <resolver:install>
      <artifact file="${build.dir}/${pom.artifactId}-${pom.version}.jar"/>
      <artifact file="${build.dir}/${pom.artifactId}-${pom.version}-sources.jar" classifier="sources"/>
    </resolver:install>
  </target>

  <target name="deploy" depends="package">
    <resolver:localrepo dir="${build.dir}/m2-install"/>
    <resolver:remoterepo id="local.release" url="file://${build.dir}/repo"/>
    <resolver:deploy>
      <remoterepo refid="local.release"/>

      <artifact file="${build.dir}/${pom.artifactId}-${pom.version}-sources.jar" classifier="sources"/>

Generating a POM with createPom

A published artifact needs a POM so that consumers can resolve its dependencies, and an Ant-only project does not have one. The createPom task writes one from the Ant-side description: group, artifact and version, name and description, the dependencies and dependencyManagement types by reference, and nested licenses, developers, repositories and scm elements. It also registers the POM it wrote as the default one, unless skipPomRegistration is true. The task is not described on the site’s main page; its attributes (pomTarget, groupId, artifactId, version, name, description, dependenciesRef, dependencyManagementRef, skipPomRegistration) come from the usage guide and the API.

create-pom.xml
<?xml version="1.0" encoding="UTF-8"?>
<project name="tidepool" default="publish" basedir="."
         xmlns:resolver="antlib:org.apache.maven.resolver.ant">
  <taskdef uri="antlib:org.apache.maven.resolver.ant"
           resource="org/apache/maven/resolver/ant/antlib.xml"
           classpath="lib/maven-resolver-ant-tasks-2.0.0-uber.jar"/>

  <property name="groupId" value="io.tidepool"/>
  <property name="artifactId" value="tidepool-engine"/>
  <property name="version" value="1.0.0"/>
  <property name="build.dir" location="build"/>

  <resolver:localrepo dir="build/m2-pom"/>

  <resolver:dependencyManagement id="dm">
    <dependencies>
      <dependency groupId="org.junit" artifactId="junit-bom" version="6.1.3" type="pom" scope="import"/>
    </dependencies>
  </resolver:dependencyManagement>

  <resolver:dependencies id="deps">
    <dependency coords="org.apache.commons:commons-csv:1.14.1"/>
    <dependency groupId="org.junit.jupiter" artifactId="junit-jupiter-api" scope="test"/>
  </resolver:dependencies>

  <target name="pom">
    <mkdir dir="${build.dir}"/>
    <resolver:createPom pomTarget="${build.dir}/${artifactId}-${version}.pom"
                        groupId="${groupId}" artifactId="${artifactId}" version="${version}"
                        name="Tidepool engine" description="Tide prediction engine"
                        dependenciesRef="deps" dependencyManagementRef="dm">
      <licenses>
        <license>
          <name>Apache License, Version 2.0</name>
          <url>https://www.apache.org/licenses/LICENSE-2.0.txt</url>
        </license>
      </licenses>
    </resolver:createPom>
    <echo message="registered POM: ${pom.groupId}:${pom.artifactId}:${pom.version}"/>
  </target>

  <target name="publish" depends="pom">
    <mkdir dir="${build.dir}/classes"/>
    <javac srcdir="src/main/java" destdir="${build.dir}/classes" release="17" includeantruntime="false"/>
    <jar destfile="${build.dir}/${artifactId}-${version}.jar" basedir="${build.dir}/classes"/>
    <resolver:install>
      <artifact file="${build.dir}/${artifactId}-${version}.jar"/>
    </resolver:install>
    <resolver:resolve>
      <path refid="cp.test" classpath="test"/>
    </resolver:resolve>
    <pathconvert property="cp.flat" refid="cp.test" pathsep=" "><mapper type="flatten"/></pathconvert>
    <echo>test classpath: ${cp.flat}</echo>
  </target>
</project>

Where the books are outdated

Older Ant books and tutorials predate these tasks. They teach a lib/ directory with the JARs checked in, then the older Maven Ant Tasks (maven-ant-tasks, last release 2.1.3, project site last published in 2014) or Ivy. The Resolver Ant Tasks take over from the Maven Ant Tasks, and they are the route into Ant that the Maven project maintains today. Anything in an older book that says "Ant has no dependency management of its own, so check the JARs in" is still true of Ant’s core, but there are three maintained answers now: Ivy, the Resolver Ant Tasks, or a different tool (see Deprecations & Migration).
