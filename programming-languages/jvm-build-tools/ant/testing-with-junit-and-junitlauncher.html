Testing with JUnit & junitlauncher

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Ant 1.10.18 and JUnit 6.1.3 (JUnit Platform, JUnit Jupiter and JUnit Vintage all share the version 6.1.3). Every example marked as run was executed on JDK 26 on 2026-10-16 in a scratch directory; output that comes from a run is shown as it was printed, with the long absolute path of the scratch directory shortened to <scratch>. Ant prints the elapsed time with the machine’s decimal separator, which is why the timings below have a comma. Anything that could not be run here is labelled "not run here".

Ant ships two tasks that run unit tests, and they belong to different generations of JUnit. The junit task runs JUnit 3 and 4. The junitlauncher task, added in Ant 1.10.3, talks to the JUnit Platform and therefore runs anything that has a test engine: JUnit Jupiter (the @Test of JUnit 5 and 6), JUnit Vintage (JUnit 3 and 4 tests) and third-party engines. This page covers both, the junitreport task that turns their XML into an HTML report, and the build-file techniques that make test failures stop (or deliberately not stop) a build. The running scenario is the tidepool tidepool-engine module described on the section landing page. For compiling the test sources see Compiling Java; for the structure of the build file see Build File Structure.

junit junitlauncher

Source: Ant manual: junit

Both tasks are optional tasks. That has two consequences that cause most of the support questions: the task’s jar has to be visible to Ant before the build file is parsed, and the JUnit jars are not part of Ant at all. The next section is about exactly that.

Release history of the junitlauncher task

The task changed quite a lot during the 1.10 line. When a build file written for a recent release is run by an older Ant, the symptom is an unsupported attribute error, so the table lists the first release that has each feature.

Release Change

1.10.3

junitlauncher is added, and junitreport can use Saxon for its XSL transformation.

1.10.4

The printSummary attribute is added.

1.10.6

The fork element, the outputDir attribute of listener, and the recommended setup with ant-junitlauncher.jar in ANT_HOME/lib and the other jars in a nested classpath. The task’s classes were renamed and moved to a new package; build files that only use the junitlauncher element are not affected.

1.10.7

includeTags and excludeTags.

1.10.10

The task generates its own summary (closely matching the junit task’s), and listener gets useLegacyReportingName.

1.10.13

listener gets extension.

1.10.14

fork gets java and forkMode="perTestClass"; outputDir of test and listener is now resolved against the project’s base directory instead of the current directory (Bugzilla 66504). The same release made Java 18 and newer run without a SecurityManager, so a non-forked System.exit() in a test ends the build.

1.10.15

The legacy-xml reporter stops using an unbuffered writer.

Source: Ant WHATSNEW (raw text: https://raw.githubusercontent.com/apache/ant/master/WHATSNEW)

The libraries the task needs

The junitlauncher task does not understand tests. It builds a JUnit Platform launcher request, hands it to the launcher and reports what the engines did. So three groups of libraries have to be present, and they do not all live in the same place.

Group Jars (6.1.3 on the baseline) Needed for

The task

ant-junitlauncher.jar, delivered with Ant in ANT_HOME/lib.

The junitlauncher element itself.

JUnit Platform

junit-platform-commons, junit-platform-engine, junit-platform-launcher, opentest4j.

Every run, whatever the engine.

Jupiter engine

junit-jupiter-api, junit-jupiter-engine (and apiguardian-api, which the API jar refers to).

Tests written with org.junit.jupiter.api. The API jar is also on the compile classpath of the tests.

Vintage engine

junit-vintage-engine, junit (4.x; 4.13.2 here) and hamcrest-core (JUnit 4.13.2 depends on it).

Tests written with org.junit.Test.

The manual lists the first three groups (under JUnit Platform libraries, the Jupiter engine libraries and the Vintage engine libraries). Two things the manual does not state in this form deserve a sentence each. JUnit 6 requires Java 17 or newer at runtime, so the JVM running Ant (or the forked JVM) must be at least that, even when the code under test is compiled for an older release. And the Vintage engine is deprecated in the JUnit 6 line: it logs an INFO message about it every time it takes part in a run (the exact text is in the output further down).

The page for Ant’s own installation, Installation, explains the optional-library mechanics. For junitlauncher the manual gives three ways to make the jars visible.

  1. Recommended since Ant 1.10.6. Leave ant-junitlauncher.jar where it is, in ANT_HOME/lib, and put every JUnit jar on the classpath nested in the junitlauncher element. Nothing outside the project has to change, and different projects can use different JUnit versions with the same Ant installation.

  2. Put the JUnit jars into ANT_HOME/lib together with ant-junitlauncher.jar. This pins every build on the machine to one JUnit.

  3. Keep ant-junitlauncher.jar in ANT_HOME/lib and pass the JUnit jars with the command-line option -lib (see Running Ant).

Getting the jars without a repository manager

Ant has no dependency management of its own. The examples on this page keep the jars in a lib directory next to the build file, in four sub-directories (main for the libraries of the code under test, platform, jupiter and vintage), which were filled with curl from Maven Central. The chapters that follow in this section show the two proper answers: Ivy Ant Tasks and Maven Resolver Ant Tasks, which resolve the same coordinates (and their transitive dependencies) into a path for you. The difference between "download one jar" and "resolve the dependency graph" is the subject of the first error you will meet below: commons-csv needs commons-io.

A first test run

The module has six classes under src/main/java (the model records and the engine) and three test classes. Two of them are JUnit Jupiter tests, tagged so that the later sections can select by tag; one is a JUnit 4 test.

package io.tidepool.engine;

class StationReaderTest {

    @Test
    @Tag("fast")
    void readsThreeStations() throws IOException {
        try (Reader in = Files.newBufferedReader(Path.of("data/stations.csv"))) {
            List<Station> stations = StationReader.read(in);
            assertEquals(3, stations.size());
            assertEquals("Boston", stations.get(1).name());
        }
    }
    // firstStationHasThreeConstituents(): the same file, asserts 3 constituents for the first station
}

TideEngineTest has three methods: a @Tag("fast") test that checks a prediction is bounded by the sum of the amplitudes, a @Tag("slow") test that scans one day minute by minute, and an untagged one that prints scanned Boston. LegacyHeightTest is a JUnit 4 class (org.junit.Test) with one method. The import lines and the second test of StationReaderTest are omitted in the listing above; all other listings on this page are complete.

The build file starts with the paths and the compile targets. Each library group is a path by itself (see Paths, Filesets & Patterns), so that the compile classpath and the runtime classpath of the tests can be assembled from the same pieces.

<?xml version="1.0" encoding="UTF-8"?>
<project name="tidepool-engine" default="test" basedir=".">
  <property name="build.dir" value="${basedir}/build"/>
  <property name="main.classes" value="${build.dir}/classes"/>
  <property name="test.classes" value="${build.dir}/test-classes"/>
  <property name="reports.dir" value="${build.dir}/test-reports"/>

  <path id="main.libs">
    <fileset dir="lib/main" includes="*.jar"/>
  </path>
  <path id="junit.platform.libs">
    <fileset dir="lib/platform" includes="*.jar"/>
  </path>
  <path id="jupiter.libs">
    <fileset dir="lib/jupiter" includes="*.jar"/>
  </path>
  <path id="vintage.libs">
    <fileset dir="lib/vintage" includes="*.jar"/>
  </path>
  <path id="test.compile.classpath">
    <pathelement location="${main.classes}"/>
    <path refid="main.libs"/>
    <path refid="jupiter.libs"/>
    <path refid="vintage.libs"/>
  </path>
  <path id="test.runtime.classpath">
    <path refid="test.compile.classpath"/>
    <path refid="junit.platform.libs"/>
    <pathelement location="${test.classes}"/>
  </path>

  <target name="init">
    <mkdir dir="${reports.dir}"/>
  </target>

  <target name="compile">
    <mkdir dir="${main.classes}"/>
    <javac srcdir="src/main/java" destdir="${main.classes}" release="21"
           includeantruntime="false">
      <classpath refid="main.libs"/>
    </javac>
  </target>

  <target name="compile-tests" depends="compile">
    <mkdir dir="${test.classes}"/>
    <javac srcdir="src/test/java" destdir="${test.classes}" release="21"
           includeantruntime="false">
      <classpath refid="test.compile.classpath"/>
    </javac>
  </target>
</project>

The init target exists for a reason that is easy to miss: junitlauncher does not create the directory its listeners write into. The error you get otherwise is in Errors you will meet.

The test target is the heart of it. It is also the target the later snippets build on; every further target is added to the same file before the closing </project> tag.

  <target name="test" depends="compile-tests,init" description="Runs all unit tests">
    <junitlauncher printSummary="true" haltOnFailure="true">
      <classpath refid="test.runtime.classpath"/>
      <testclasses outputdir="${reports.dir}">
        <fileset dir="${test.classes}"/>
        <listener type="legacy-brief" sendSysOut="true"/>
        <listener type="legacy-xml" sendSysOut="true" sendSysErr="true"/>
      </testclasses>
    </junitlauncher>
  </target>

The junitlauncher task in detail

Attributes of the task

Attribute Meaning Default

includeTags

Comma-separated JUnit tags; only tests with at least one of them run. Since Ant 1.10.7.

all tests

excludeTags

Comma-separated JUnit tags; tests with any of them are skipped. Since Ant 1.10.7.

none

haltOnFailure

Stop the build when a test fails. JUnit 4 and later classify assertion failures and thrown exceptions together, and so does the task: it does not distinguish failures from errors.

false

failureProperty

Name of a property to set when a test fails (exceptions in tests included).

not set

printSummary

Print the statistics line after each test class. Since 1.10.10 the task itself generates the line instead of using the platform’s.

false

Everything else is nested. The classpath element can be repeated and the parts are concatenated, which is what the manual’s own example does (one classpath per library group).

Nested elements

Element Role

classpath

A path-like structure. It is used to find the test classes, to find the test engines and, if configured that way, to find every JUnit library. If the element is missing, Ant’s own classpath is used, which only works when everything was installed in ANT_HOME/lib.

test

One test class: name (required, fully qualified), methods (comma-separated method names to run), haltOnFailure, failureProperty, outputDir, if, unless, includeEngines, excludeEngines. Its own listener and fork children apply to this test.

testclasses

Any number of resource collections; every resource whose name ends in .class is passed to the platform. Attributes: haltOnFailure, failureProperty, outputDir, if, unless, includeEngines, excludeEngines. All the classes of one testclasses run in one launcher (and, when forked, in one JVM unless forkMode says otherwise).

listener

A result formatter or any TestExecutionListener; see the next section. Allowed inside junitlauncher (as a default for every test), test and testclasses.

fork

Run the tests in a new JVM; see the section on forking.

The attributes haltOnFailure and failureProperty can be given on junitlauncher and are overridden by the same attribute on a nested test or testclasses. Note the spelling: the manual writes outputDir and Ant’s attribute matching is case insensitive, which is why the examples on this page can spell it outputdir.

Source: Ant manual: junitlauncher, nested elements

Listeners and result files

A listener receives the events of a run. The task defines three formatters, all of them named after the output of the junit task whose formatters they imitate:

type Output

legacy-plain

A short statistics line for every test case, written to a .txt file.

legacy-brief

Details only for tests that failed or were skipped, written to a .txt file.

legacy-xml

The statistics and the output of the tests in XML, written to an .xml file, using the schema of the junit task’s XML formatter. That is what makes it usable as input of junitreport.

Instead of type a listener can name a classname: a class implementing the platform’s TestExecutionListener, or the Ant-specific sub-interface TestResultFormatter for listeners that want a file name and the captured output. The attributes of listener:

Attribute Meaning Default

type

One of legacy-xml, legacy-plain, legacy-brief. Exactly one of type and classname is required.

not set

classname

A listener class.

not set

resultFile

File name of the result, relative to outputDir; only used for TestResultFormatter implementations.

TEST-testname.extension

extension

Extension of the result file. Since Ant 1.10.13.

xml for legacy-xml, txt otherwise

outputDir

Directory of the result, for this listener only. Since Ant 1.10.6.

the outputDir of the enclosing test/testclasses

sendSysOut, sendSysErr

Hand the captured standard output (error) of the tests to the listener. Only meaningful for TestResultFormatter implementations.

false

if, unless

Use the listener only when the named property is (not) set.

none

useLegacyReportingName

true reports JUnit 4 style test names, false reports the identifiers of the platform. Since Ant 1.10.10.

true

Selecting what runs

Tags are the platform’s mechanism for categories (@Tag("fast")), so they replace the old habit of keeping slow tests in a differently named class and picking them with a batchtest pattern. Add a target that runs only the fast tests:

  <target name="test-fast" depends="compile-tests,init" description="Only tests tagged fast">
    <junitlauncher includeTags="fast" printSummary="true" haltOnFailure="true">
      <classpath refid="test.runtime.classpath"/>
      <testclasses outputdir="${reports.dir}">
        <fileset dir="${test.classes}"/>
        <listener type="legacy-plain" sendSysOut="true"/>
      </testclasses>
    </junitlauncher>
  </target>

Running one test

During development the most useful target is the one that runs a single class, or a few methods of it, taking both from the command line. The fail task checks the mandatory property, and two test elements, one with if and one with unless, cover the two cases (see Conditions & Control Flow for fail).

  <target name="test-one" depends="compile-tests,init" description="-Dtest.class=... -Dtest.methods=...">
    <fail unless="test.class" message="Set -Dtest.class=fully.qualified.TestClass"/>
    <junitlauncher printSummary="true" haltOnFailure="true">
      <classpath refid="test.runtime.classpath"/>
      <test name="${test.class}" methods="${test.methods}" if="test.methods"
            outputdir="${reports.dir}">
        <listener type="legacy-plain"/>
      </test>
      <test name="${test.class}" unless="test.methods" outputdir="${reports.dir}">
        <listener type="legacy-plain"/>
      </test>
    </junitlauncher>
  </target>
ant test-one -Dtest.class=io.tidepool.engine.TideEngineTest -Dtest.methods="scanningADayStaysWithinBounds,printsAProgressLine"
…

Forking

By default the tests run in the JVM that runs Ant. That is fast but it shares the process: a test that calls System.exit() ends the build (Java 18+ has no SecurityManager to catch it, since Ant 1.10.14), a leaked thread keeps Ant alive, static state leaks between test classes, and the JVM options cannot be chosen. A nested fork element (Ant 1.10.6 and later) starts a new JVM instead.

Attribute Meaning Default

dir

Working directory of the forked JVM.

the project’s base directory

timeout

Maximum run time in milliseconds; the JVM is killed when it is exceeded. With forkMode="perTestClass" it is the time all classes use together, not one.

none

includeJUnitPlatformLibraries

Add the JUnit Platform jars that Ant knows about to the classpath of the forked JVM; when false the task’s classpath must contain them.

true

Making failures fail the build

By default a failing test does not fail the Ant build. The task records the failure in its output and goes on, and the build ends with BUILD SUCCESSFUL. There are two ways to change that, and they serve different needs.

Stop at once. haltOnFailure="true" (on the task, or per test/testclasses) throws a BuildException as soon as a test class has a failure. The next test classes do not run. With a deliberately broken test (BrokenTest.addsUp asserts that 2 + 3 equals 4) placed before the good one, this is what Ant 1.10.18 printed:

  <property name="failing.classes" value="${build.dir}/failing-classes"/>

  <target name="compile-failing" depends="compile-tests">
    <mkdir dir="${failing.classes}"/>
    <javac srcdir="src/test-failing/java" destdir="${failing.classes}" release="21"
           includeantruntime="false">
      <classpath refid="test.compile.classpath"/>
    </javac>
  </target>

  <target name="test-failing-halt" depends="compile-failing,init" description="Stops at the first failure">
    <junitlauncher haltOnFailure="true" printSummary="true">
      <classpath refid="test.runtime.classpath"/>
      <classpath location="${failing.classes}"/>
      <test name="io.tidepool.engine.BrokenTest" outputdir="${reports.dir}">
        <listener type="legacy-brief" sendSysOut="true"/>
      </test>
      <test name="io.tidepool.engine.TideEngineTest" outputdir="${reports.dir}"/>
    </junitlauncher>
  </target>

      <testclasses outputdir="${reports.dir}">
        <fileset dir="${failing.classes}"/>

        <listener type="legacy-xml"/>

The legacy junit task (JUnit 3 and 4)

The junit task is still the right tool in exactly one situation: a code base that is on JUnit 3 or 4 and has no reason to move. It needs ant-junit.jar (and ant-junit4.jar, both are in ANT_HOME/lib) and junit.jar, which the manual allows you to supply in several ways, of which the simplest is to include junit.jar in the classpath passed to the task (since Ant 1.7). The FAQ entry "Why do I get a ClassNotFoundException for JUnit" describes the older ways.

Nested elements are classpath, jvmarg, sysproperty, syspropertyset, env, bootclasspath, permissions, assertions, modulepath and upgrademodulepath (both need fork), formatter, test and batchtest. The permissions element is no longer supported on Java 18 and newer (the reason is the removal of the SecurityManager; see Running Programs).

Formatters: plain (statistics for every test case), brief (details only for failures), xml and failure (since 1.8.0; it collects the failing test methods into a new test case class). A formatter can use classname for a custom class together with the mandatory extension, can be silenced with usefile="false" so that it prints to the console, and takes if and unless.

batchtest is the counterpart of testclasses. It takes any resource collection and turns each resource into a class name, so here the fileset has to select the classes with a pattern. skipNonTests="true" drops classes that have no tests (identified by @Test annotations, methods whose names start with test in TestCase subclasses, @RunWith/@SuiteClasses or a suite() method), which prevents helpers from appearing as test errors.

An example with JUnit 4

<?xml version="1.0" encoding="UTF-8"?>

  <property name="legacy.reports" value="${build.dir}/legacy-reports"/>

  <path id="junit4.classpath">
    <pathelement location="${build.dir}/classes"/>
    <pathelement location="${build.dir}/test-classes"/>
    <fileset dir="lib/vintage" includes="junit-4*.jar,hamcrest-core-*.jar"/>

  <target name="legacy-test">
    <mkdir dir="${legacy.reports}/raw"/>
    <junit printsummary="yes" fork="yes" forkmode="once" haltonfailure="no"
           failureproperty="legacy.failed" errorproperty="legacy.failed">
      <classpath refid="junit4.classpath"/>
      <formatter type="plain"/>
      <formatter type="xml"/>
      <batchtest todir="${legacy.reports}/raw">
        <fileset dir="${build.dir}/test-classes">
          <include name="io/tidepool/legacy/*Test.class"/>
        </fileset>
      </batchtest>
    </junit>
  </target>

  <target name="junit-report" depends="legacy-test">
    <junitreport todir="${legacy.reports}">
      <fileset dir="${legacy.reports}/raw" includes="TEST-*.xml"/>
      <report format="noframes" todir="${legacy.reports}/html"/>
    </junitreport>
    <fail if="legacy.failed" message="legacy tests failed"/>
  </target>

Where the book is outdated

Java Development with Ant (Hatcher and Loughran, Manning, 2002) was written for Ant 1.5, JDK 1.3 and 1.4 and JUnit 3. Its chapter on testing is built around the junit task and around TestCase subclasses, and the task itself is still there and still works for exactly that. What the book cannot know: JUnit 4 (annotation-based tests, which the junit task does run), JUnit 5 and 6 (supported only by junitlauncher, from Ant 1.10.3), tags, engines, fork for junitlauncher, listeners instead of formatters, the removal of the SecurityManager (Java 18+, which makes the permissions element of junit non-functional and System.exit() in a non-forked test fatal for the build), and the need for Java 8 or newer for Ant 1.10. Its practice of installing every optional jar into one lib directory corresponds to the second way in the list of ways to make the jars visible, now not the recommended one. For the full list of statements in the book that no longer hold see Deprecations & Migration. The book is a publication of Manning: the second edition, Ant in Action, is on the publisher’s page.

For the release-by-release changes of Ant itself see Versions & Release History.
