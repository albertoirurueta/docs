Choosing and Combining the Tools

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The .NET tool chain offers several front ends to the same engine. For a modern repository the answer is short — use the dotnet CLI — but code bases with .NET Framework projects, packages.config, Visual Studio-only workflows or scripts written for nuget.exe still need the others, and knowing which command is equivalent to which avoids most "works in Visual Studio, fails on CI" surprises. This page was written against MSBuild 18.9, .NET SDK 10.0.402 and NuGet 7.9.0; nuget.exe 7.9.0 (2026-08-11, the latest on dist.nuget.org/tools.json) and Visual Studio 2026 18.11 are described from their documentation and are not run here (no Windows machine).

Which tool for which job

Tool Use it for Platforms

dotnet CLI (.NET SDK)

Everything in an SDK-style repository: new, restore, build, test, pack, publish, run, tools, workloads, package and source management, push, signing. The default on developer machines and CI.

Windows, macOS, Linux

msbuild.exe (Visual Studio, Build Tools)

Projects that need the .NET Framework MSBuild: non-SDK .csproj, C++/CLI, WPF/WinForms projects with Visual Studio components, build tasks compiled for .NET Framework. Also what Visual Studio itself runs.

Windows

nuget.exe

packages.config projects (restore, install, update), .nuspec-only packing, a few commands without a dotnet equivalent (mirror/replicate, init). Runs on macOS/Linux only under Mono, with limitations.

Windows (Mono elsewhere)

Visual Studio / Package Manager UI

Interactive package management, design-time builds, publish profiles.

Windows

Package Manager Console (PMC)

PowerShell commands (Install-Package, Update-Package) inside Visual Studio; does not work in other PowerShell hosts.

Windows (Visual Studio only)

The NuGet documentation’s rule of thumb: target .NET or .NET Standard, or any SDK-style project → the dotnet CLI; .NET Framework with non-SDK projects → nuget.exe; once such a project is migrated to PackageReference, switch to the dotnet CLI. MSBuild can also restore and pack, "but MSBuild isn’t a general-purpose tool for working with NuGet"; it is mainly useful on build servers.

Source: NuGet: Install NuGet client tools, Tools overview, Feature availability.

The equivalences are real, not approximate: dotnet pack is dotnet msbuild -restore -t:Pack, and both produce the same package. For the Ledgerline library:

dotnet msbuild src/Ledgerline -restore -t:Pack -p:Configuration=Release -p:PackageOutputPath=$PWD/artifacts/msbuild-pack -tl:off -v:m
dotnet pack src/Ledgerline -c Release -o artifacts/dotnet-pack -tl:off -v:m

The differences that matter are the defaults the CLI adds (-restore, parallel nodes, the Terminal Logger, the Release configuration for pack and publish since .NET 8) and which MSBuild runs: dotnet msbuild runs the .NET MSBuild inside the SDK, msbuild.exe runs the .NET Framework MSBuild from Visual Studio, which can load tasks compiled only for .NET Framework. A custom task should therefore target netstandard2.0 (as Ledgerline.Build does) to work under both (Writing Custom Tasks).

Source: .NET CLI: dotnet msbuild, NuGet CLI reference: Commands and applicability.

Migrating old projects

Two migrations are usually needed before a .NET Framework code base can use the dotnet CLI, and they are independent:

  1. packages.config → PackageReference. Visual Studio’s Migrate packages.config to PackageReference command (on the packages.config file or the References node) moves the dependencies into the project file, keeping only the top-level packages, and backs up the old files. The documented limitations: migration "is not currently available for C++ and ASP.NET projects", migrated projects need Visual Studio 2017 or later, some packages (for example those that rely on install.ps1 scripts or content transformations) are not fully compatible, and allowedVersions constraints have no PackageReference equivalent. The step-by-step procedure and the limitations are on nuget.exe, Visual Studio and packages.config.

  2. Non-SDK project → SDK-style project. Replace the project body by <Project Sdk="Microsoft.NET.Sdk"> with <TargetFramework>net48</TargetFramework> (or a multi-target list), delete the explicit Compile list and AssemblyInfo.cs, and keep only what differs from the defaults (SDK-Style Project Files). An SDK-style project can still target .NET Framework, so this step does not force a runtime change; retargeting to net10.0 is a third, separate step.

Microsoft’s .NET Upgrade Assistant automates parts of both; it is listed on Ecosystem and Learning Resources.

Source: NuGet: Migrate from packages.config to PackageReference, Migration steps, Limitations.

Common mistakes

  • Mixing nuget.exe restore and dotnet restore in one repository — they can resolve differently (packages.config vs PackageReference); pick one per project format.

  • Assuming msbuild.exe and dotnet build load the same tasks — a task built for net10.0 cannot load in msbuild.exe; one built for .NET Framework cannot load in dotnet build.

  • Scripts that call nuget.exe on Linux agents — requires Mono; use the dotnet nuget commands.

  • Expecting Package Manager Console commands in a normal PowerShell — they exist only inside Visual Studio.

  • Using dotnet add package in new scripts — it still works but is the older, verb-first form; .NET 10 documents dotnet package add.

Release notes

  • .NET 8: dotnet pack and dotnet publish default to the Release configuration (breaking change).

  • .NET 10: noun-first commands (dotnet package add/list/remove/update, dotnet reference add); the verb-first forms remain as aliases.

  • nuget.exe 7.9.0 (2026-08-11) is the current recommended nuget.exe.
