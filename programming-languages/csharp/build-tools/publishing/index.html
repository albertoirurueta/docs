Publishing and Distributing Libraries

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The NuGet group covers consuming packages; this group covers producing them: designing a library for reuse, describing it, packing, validating, signing, versioning and publishing it, and looking after it once it is public. Every example was run with .NET SDK 10.0.402 (MSBuild 18.9, NuGet 7.9.0) on Linux, against the Ledgerline scenario of this section. Packages were pushed only to a local folder feed and to a BaGetter 1.6.5 container on localhost:5555; pushes to nuget.org, GitHub Packages and Azure Artifacts, Trusted Publishing and signing with a real certificate are shown as "not run here" examples, checked against the documentation, with placeholder keys. Ledgerline is never pushed to a public feed.

A release starts long before dotnet pack: the target frameworks and dependency ranges chosen at design time decide who can consume the package, and the metadata decides whether anyone finds and trusts it. Packing turns a project into a .nupkg; validation compares it with the previous release; signing is optional on nuget.org, which adds its own repository signature. Pushing to a test feed first catches packaging mistakes before they become permanent, because a version on nuget.org can be unlisted but never replaced.

Source: Package creation workflow, Open-source library guidance: NuGet and open-source libraries, Publishing.

A minimal local release of Ledgerline is two commands:

dotnet pack src/Ledgerline -o artifacts/rel -p:Version=1.0.1 -p:IncludeSymbols=true -p:SymbolPackageFormat=snupkg
dotnet nuget push artifacts/rel/Ledgerline.1.0.1.nupkg -s ledgerline-bagetter -k "$BAGETTER_API_KEY"

Where packages can go

  • nuget.org — the public registry, the default source of every client (Publishing to nuget.org).

  • GitHub Packages and Azure Artifacts — hosted private (or public) feeds tied to a repository or an Azure DevOps organization.

  • Self-hosted servers — BaGetter, NuGet.Server, or any server implementing the NuGet V3 API.

  • Folders and file shares — the simplest feed, with no server at all.

The last three are covered on Private Feeds.

Source: Hosting your own NuGet feeds.

Common mistakes

  • Pushing to nuget.org first — a version is permanent; try a local or test feed first.

  • Treating the API key as long-lived — since 2026-08-17 it lasts 30 days at most; prefer Trusted Publishing.

  • Skipping package validation — a removed public member is a breaking change that consumers find at run time.
