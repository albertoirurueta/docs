Modifications, Modification Assistant and SPAU/SPDD

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Sooner or later a business asks for something that the delivered SAP software does not do, and the quickest-looking answer is to open the SAP program and change it. That change is called a modification. It works at once, but it has a price: every upgrade, Support Package and enhancement package replaces SAP objects with new versions, and your change is overwritten unless somebody puts it back. This page explains what a modification is, the registration keys that SAP asks for before you may make one, the tool that records modifications (the Modification Assistant) and the tool that lists them (the Modification Browser), the two adjustment transactions SPDD and SPAU that bring modifications back after an update, how SAP Cloud ALM tracks modifications as a figure to reduce, and which tools to use instead. It is written against Standard ABAP release 8.16 and ABAP for Cloud Development release 9.20 (2608), with the help pages of the ABAP Platform 2025 FPS02 documentation. Modifications and their adjustment exist in classic Standard ABAP systems, such as SAP S/4HANA on premise and Private Edition; the page does not claim anything about modifications in the Public Edition or in the SAP BTP ABAP environment, where the extension options of ABAP Cloud are the intended way. Every procedure here needs an SAP system, so the page has no listing that was run here.

Before you read

  • Classic Tools: SE80, SE38, SE11, SE37 and SE16: the ABAP Workbench editors in which the Modification Assistant works.

  • Language Versions and Released APIs: classic ABAP against ABAP Cloud and the released APIs that clean core level A is built on.

  • Database Tables and Structures: includes and append structures, the modification-free way to add a field to a table.

Key terms

  • Modification: a change to an object that SAP delivered, made in the customer system, so that the object no longer matches SAP’s original.

  • SSCR: the SAP Software Change Registration procedure, which registers developers and manual changes to SAP source code and ABAP Dictionary objects with an access key.

  • Modification Assistant: the Workbench function that puts an SAP object into a protected modification mode and logs every change in detail.

  • Modification Browser: the overview of all modifications and enhancements of a system, opened with transaction SE95 or inside the adjustment transactions.

  • SPDD: the transaction that adjusts modified ABAP Dictionary objects during an update, before the dictionary is mass-activated.

  • SPAU: the transaction that adjusts the other modified repository objects, such as programs, function modules, screens and interfaces, and SAP Notes, after the new objects arrive.

  • Clean core level: one of the levels A to D that SAP assigns to an extension, according to the APIs it uses; SAP Cloud ALM tracks modifications separately.

  • Enhancement Framework: the technology that adds code to SAP objects through enhancement options without changing the original object.

  • Append structure: a customer-owned structure attached to an SAP table or structure, which adds fields without modifying it.

  • Transport request: the container that carries development changes from one system to the next.

Where a modification sits among the ways to change SAP

The documentation of the Modification Assistant lists five levels at which an SAP system is adapted to a company.

  1. Customizing, the settings that SAP provides in the Implementation Guide.

  2. Personalization, the settings of one user or one role.

  3. Predefined enhancements, such as Business Add-Ins (BAdIs), that SAP built as places for customer code.

  4. Modifications to the standard, which change SAP’s own objects.

  5. Customer development, which creates new objects in the customer namespace.

The page says that the first, second, third and fifth are supported by tools made for them (the IMG, the BAdI Builder, the development environment), and that the Modification Assistant is the tool for the fourth. The page that introduces modifications states the rule that the rest of this page repeats: modify only when the requirement cannot be met by Customizing, personalization, exits or Business Add-Ins. It also states who carries the risk: the person who modifies is responsible for the semantic correctness of the change.

Source: ABAP Platform: The Modification Assistant and ABAP Platform: Modifying the Standard

Why a modification costs more than it seems

During an update, which the documentation defines as an upgrade, a Support Package or an enhancement package, SAP objects are overwritten by the delivered objects, and the overwrite also removes every modification. The adjustment tools SPDD and SPAU exist so that the modifications can be implemented again. There is a second, contractual cost. The SSCR page says that modifications severely reduce SAP’s warranty obligations for the software it delivers, although SAP will still try to support customers who modified their systems themselves.

An invented example for the claims application of this section: the standard purchasing program in the system rejects a document above a fixed amount, and the claims department wants the limit raised for travel. Editing the program’s check is a modification. It takes minutes. At the next Support Package that program is probably delivered again, the system detects that you changed an object that SAP also delivered, and somebody must compare your change with the new SAP code, line by line, before the update can finish. If the program changed in the area of your edit, the person has to decide by hand how both changes fit together, which is why the rest of the page keeps repeating "avoid".

Source: ABAP Platform: Installing Upgrades, Support Packages, and Enhancement Packages and ABAP Platform: The SAP Software Change Registration Procedure (SSCR). The purchasing example is invented for this page and names no real object.

Modification keys: SSCR

SSCR is the procedure with which SAP registers all manual changes to SAP source code and ABAP Dictionary objects. Tuning measures such as database indexes and buffer settings are exempt. Two registrations are involved, and both end in an access key that you type into a dialog the first time it is needed.

Registration What it means

Developer registration

You must register once per system, with a 20-digit access key, before you create, edit or delete a development object for the first time. The key is tied to the installation number of the customer system and the user name. Once saved, the key is read automatically for later changes and, according to the classic documentation, stays valid across upgrades.

Object registration

You need a 20-digit access key to create, change or delete an object in the SAP namespace. The registration is needed once per SAP object, and it covers the later modifications of that one object. It is tied to the installation number, the transport ID, the transport type, the object name and the release.

The classic documentation lists when registration happens: when SAP source code is changed, when ABAP Dictionary elements are changed manually, and when code from an SAP Note is included (in that case the keys arrive with the Note, so the registration is automatic). It does not happen for database indexes, buffer settings, customer objects outside the SAP namespace, objects changed by automatic generation, such as from Customizing, and customer development that uses exits. Object keys are valid for one release: after an upgrade they become invalid. The documentation says that to copy the modifications into the new release you use the SAP Patch Manager (transaction SPAM) and need no new keys, but a new modification of an object after the upgrade needs a new object key. You obtain keys in the SAP support portal under SSCR keys, which the classic page reaches through the SAP Service Marketplace; that page is older than the portal’s current look, so treat the menu path as a hint, not a guide.

The ADT documentation describes the same two registrations for developers who work in Eclipse. The point to take for design: the dialog that asks for an object key is SAP’s last checkpoint before a modification, and it is also the best moment to stop and ask whether an enhancement would do.

Source: ABAP Platform: SSCR, ABAP Platform: When Are Objects Registered?, ABAP Platform: Registering a Development Authorization (older page) and ADT: Registering SAP Objects as a Developer

The Modification Assistant

Changing an SAP object with nothing to guide you leaves no record of what you changed, and the upgrade then has nothing to compare. The Modification Assistant fixes that. When you edit an SAP object in a supported Workbench editor, you branch into a modification mode. In it the original is protected and you can change it only through additional pushbuttons, and the Assistant logs every change. The documentation says that this log gives a readable overview of the modifications and sharply reduces the work of an upgrade.

The Assistant supports the ABAP Editor, the Class Builder, the Screen Painter, the Menu Painter, text element maintenance, the Function Builder, the ABAP Dictionary and documentation. Modifications to Workbench objects that it does not support are logged and displayed in an overview, but they are adjusted in the conventional way at upgrade. The first time you edit an object it supports, a dialog tells you that the editing functions are limited; it appears once per user for each kind of transport object.

Modifying a program

In the ABAP Editor, you change a program with the pushbuttons Insert, Replace and Delete. The code you insert is framed by comment lines that say what kind of modification it is, together with a number that identifies the modification internally. Replace turns the old line into a comment and copies it into a new line you can edit. Delete removes whole lines. The editor also has Modification overview, which lists all modifications of the include, and Undo modification, which removes one modification when the cursor is on it.

The Assistant divides a program into modularization units (modules, subroutines, events and method implementations) and assigns each modification to its unit. If no modularization unit that SAP delivered is altered, the modification can be adopted automatically at upgrade. For that reason the documentation advises that a new modularization unit goes into a customer include, and that code you insert into the program is moved into subroutines of a customer include. That reduces upgrade time and helps when conflicts arise.

Source: ABAP Platform: Modifications in Programs and ABAP Platform: The Modification Assistant. The documentation does not show the exact form of the comment lines, and this page does not either.

Switching the Assistant off, and resetting to the original

The Workbench menu Edit, Modification operations offers Switch off assistant, and the authorization to use it can be assigned explicitly through the authorization object S_DEVELOP. SAP recommends leaving the Assistant on. If you switch it off, the system issues a warning, and three things follow.

  • The modification overview shows that something changed but not what.

  • No support for upgrade adjustments exists; you must use version management.

  • The modification log, which records the differences from the original imported with the last upgrade or Support Package, loses that information, so you cannot simply switch the Assistant on again without losing it.

If you switch it off only to test, create a temporary version first. The documentation also says that versions created during or before the last import must not be retrieved, because the incomplete log would cause inconsistencies at the next import.

Resetting to the original undoes modifications of an object. You can do it from the initial screen of the Workbench tool (Edit, Modifications, Reset to original) or in the Modification Browser by selecting the object and choosing Discard Modification (Reset). The reset covers the entire repository object, with its sub-objects, and the documentation warns that a reset modification cannot be retrieved. Only to undo one single modification, for example on one status, do you go to it directly in the tool.

Source: ABAP Platform: Switching the Modification Assistant Off / On and ABAP Platform: Resetting to the Original

The Modification Browser

Transaction SE95 shows an overview of all modifications and enhancements in the system. On its selection screen you narrow down the objects by a selection method (standard, by assigned processors, by transport requests) and by options such as the last user, the transport request, the package, the software component or the object name. You can also consider usage data, from a SUSG snapshot or from usage and procedure logging, so that you adjust the objects that are really used first. The resulting view groups objects in adjustment categories.

Category Contents

Notes

SAP Notes that are obsolete or have to be implemented again.

With Assistant

Standard objects supported by the Modification Assistant. You can reset a modification here.

Without Assistant

Everything else, including objects modified before the Assistant existed. You can delete the modification log here; then the active version counts as the original, with the risk that modifications are lost at upgrade.

Objects that are being adjusted cannot be changed at the same time.

Source: ABAP Platform: The Modification Browser

Adjusting modifications during an update: SPDD and SPAU

When an update tool imports new SAP objects, the system recognizes automatically whether a modification adjustment is needed, and an adjustment is required for every object that you modified and SAP also delivered. The tool asks you to run SPDD for the ABAP Dictionary objects and SPAU for the others. The update tool is the Software Update Manager (SUM) for an upgrade, the Support Package Manager (transaction SPAM) for Support Packages, or the Add-On Installation Tool (transaction SAINT). Both transactions have the same user interface.

flowchart TD U["Update tool: SUM, SPAM or SAINT"] --> D["SPDD: adjust ABAP Dictionary objects"] D --> T1["Transport request with tasks per user; mark it with Assign Transport"] T1 --> M["Mass activation of ABAP Dictionary objects"] M --> S["SPAU: adjust SAP Notes first, then repository objects; SPAU_ENH for enhancements"] S --> T2["Transport request marked with Assign Transport"] T2 --> C["Update continues; marked requests are reused in the later systems"]

Source: ABAP Platform: Adjusting ABAP Dictionary Objects Using Transaction SPDD, ABAP Platform: Adjusting Remaining Objects with Transaction SPAU and ABAP Platform: Adjusting Repository and ABAP Dictionary Objects

SPDD: the dictionary first

The order matters because of data. A modified table or structure must be adjusted before the dictionary is mass-activated, otherwise the new SAP version could drop your fields and, with them, data. The documentation lists the object types that SPDD handles, including domains, data elements, database tables (with their technical settings and indexes), and, depending on release, data definitions, views, table types and ABAP packages. Changes to other dictionary objects, such as type groups, search helps and lock objects, cannot lose data, so they are handled by SPAU after the upgrade. You do not need SPDD at all if you changed no SAP dictionary object, or only added your own domains, data elements or tables in the customer namespace.

The documented procedure is short. Create a workbench request for the adjustment, with a task for each project member (when SUM runs downtime-minimized, you first create extra users as copies of the user DDIC in the shadow system). Adjust SAP Notes, then adjust or reset the objects, without activating adjusted objects. Release the tasks, mark the request with Modification Adjustment, Assign Transport, and continue the update. SUM releases the request itself; with SPAM or SAINT you release it by hand after SPAU. If you adjust nothing, the new SAP standard becomes active and your modifications are lost, and a later upgrade asks you again.

An adjustment depends on the adjustment mode. A green traffic light means the system can adopt the modification automatically, and several such objects can be adjusted in one step. A yellow light means tool-supported adjustment with a dialog that shows the differences. For objects without the Assistant, such as domains, structures and tables, the comparison uses the version database, and an object can be a reset candidate (the new SAP object already covers your change; you decide whether that is intended or a name clash), tool-supported (SPDD proposes, for example, moving your own new fields into an append structure and resetting SAP’s structure) or manual (SPDD opens SE11, and the object counts as adjusted once it is in the SPDD transport request). The documentation recommends the Z prefix for customer fields to avoid clashes.

Source: ABAP Platform: Specifics for Adjusting ABAP Dictionary Objects Using Transaction SPDD, ABAP Platform: Process Flow and ABAP Platform: Adjustment Category: Without Modification Assistant

SPAU: everything else

SPAU adjusts repository objects such as programs, function modules, screens and interfaces. The tool you update with asks you to start it. You again create a transport request with a task per user, adjust SAP Notes first, because that resolves conflicts with modifications, then the repository objects, release the tasks, and mark the request with Assign Transport. Enhancements of repository objects are adjusted in the separate transaction SPAU_ENH. Its categories mirror the Modification Browser: SAP Notes, With Modification Assistant, Without Modification Assistant, and also Deletions, Migrations and Translations. For objects with the Assistant, a green light means automatic adoption, and a yellow light opens a tool, for example the splitscreen editor for program sections, or a dialog for conflicting data; in rare cases manual maintenance is needed, and the adjustment protocol lists unresolved problems.

Source: ABAP Platform: Adjusting Remaining Objects with Transaction SPAU, ABAP Platform: Specifics for Adjusting Repository Objects with Transaction SPAU and ABAP Platform: Adjustment Category: With Modification Assistant

How clean core treats a modification

SAP’s clean core approach rates an extension by what it builds on. The SAP Cloud ALM documentation describes four levels. Level A means objects built only on released APIs and extension points, with the ABAP language version ABAP for Cloud Development; they are upgrade-stable and clean core. Level B means objects built with classic ABAP on classic APIs or released APIs; they are upgrade-stable too, though the stability rests on nominations by SAP product experts, not on a stability contract. Level C means objects that use SAP internal objects that are neither classified nor meant for customers; SAP gives no stability or usage guarantee, so the level is called conditional clean core. Level D is the most critical risk category and the highest technical debt: its description reads "not clean core, not upgrade-stable, not recommended", and it covers objects that SAP classifies as not recommended, including the label noAPI. The page that lists the levels does not assign modifications to a level; it treats them in a separate figure, described next.

Cloud ALM also tracks business modifications, the subset of the modifications logged in the table SMODILOG that address functionality gaps in the SAP standard. It states that you should avoid them, because they are neither clean-core-compliant nor upgrade-stable. They are found by Custom Code Analytics, not by the ABAP Test Cockpit, and they appear on their own card, so they are not counted in the clean core share. The documentation warns that the tools may flag some changes as business modifications that come from SAP Notes with manual steps, so check each one.

Source: SAP Cloud ALM: Extensibility and SAP Cloud ALM: Business Modifications

Replacing a modification with an enhancement

The decision before every change is the same, and it follows the order of the five levels above.

flowchart TD R["Requirement the standard does not meet"] --> Q1{"Customizing or personalization enough?"} Q1 -- yes --> A["Use them; no code change"] Q1 -- no --> Q2{"Released API or extension point available?"} Q2 -- yes --> B["Extend with ABAP for Cloud Development: level A"] Q2 -- no --> Q3{"Exit, BAdI or enhancement option available?"} Q3 -- yes --> C["Enhancement Framework or BAdI implementation in a customer package"] Q3 -- no --> Q4{"Only a field missing in a table or structure?"} Q4 -- yes --> E["Append structure"] Q4 -- no --> F["Modification with Modification Assistant: last resort"]

The Enhancement Framework is the main replacement. Its goal, as the documentation states it, is to add functionality to SAP software without changing the original repository objects and to keep the enhancements organized separately. It works through enhancement options, which are positions in a repository object that behave like hooks. Implicit options exist without any preparation. Explicit options are inserted in the source by the object’s owner and published through enhancement spots. Your code goes into enhancement implementations. At runtime the enhancement behaves as if it belonged to the object, but as a transport object it does not, and it is stored in a customer package in the customer namespace. So an upgrade never overwrites it. After an upgrade you adjust only the enhancements that are no longer compatible, for example because an enhanced object was deleted, whereas with modifications you touch every single one. The documentation adds that enhancements are changes at a very low technical level, need even more planning than normal development, and need a process that says who may design and implement them. It also says that the classic append technology for dictionary objects still cooperates with the framework and is still needed to enhance every layer.

A software component can be set as Modifiable or as Not modifiable, enhanceable only, which is the system-wide switch that forbids modifications where enhancements must do. The Enhancement Framework pages are written for older releases (they mention release 7.0 as their start and say the framework is meant to gradually replace the previous concepts) but remain in the current ABAP Platform documentation.

The table below lists the options by what each protects, which is the question that matters at upgrade.

Option What you can add Survives an upgrade without adjustment?

Customizing, personalization

Settings that SAP built in.

Yes; no code is involved.

BAdI, customer exit

Code in a place SAP prepared; the standard guarantees the call and the interface stay valid.

Yes, as long as SAP keeps the interface.

Enhancement Framework

Code at implicit or explicit enhancement options.

Yes in a customer package; only enhancements that no longer fit need adjustment, through SPAU_ENH.

Append structure

Fields in an SAP table or structure.

Yes; the append belongs to the customer, which is why SPDD proposes it as the repair for new fields.

Modification

Any change, anywhere.

No; every modification must be adjusted or reset.

Source: ABAP Platform: Enhancement Framework, ABAP Platform: Enhancement Concept and ABAP Platform: Enhancements to the Standard. The decision chart is this page’s summary of those pages and of the clean core levels, not an SAP diagram.

Common mistakes

  • Modifying because it is quick. The cost arrives at the next update, and it is paid by whoever runs SPDD and SPAU.

  • Switching the Modification Assistant off to save time. The log of differences is lost, and the documentation says you cannot switch it on again without losing it.

  • Deleting a modification log in the Modification Browser to make the list shorter. An object without an original is then treated as an SAP original, and modifications may be lost at upgrade.

  • Resetting an object and expecting to undo the reset. The documentation says a reset modification cannot be retrieved, so create a temporary version first.

  • Activating adjusted dictionary objects during SPDD. The documentation says not to.

  • Adjusting repository objects before SAP Notes in SPAU. Notes first, to resolve conflicts with modifications.

  • Treating a green traffic light as proof that the change is still right. It means the system can adopt the change without conflict, not that the new standard still behaves as you assumed.

  • Assuming the object key of the old release still works after the upgrade. Object keys are valid for one release.

What older books show, and what has changed

A book written for AS ABAP 7.x, such as the first edition of Complete ABAP or a book on HCM programming of the same era, treats modifications as one normal extension technique beside user exits, customer exits and BAdIs, and describes SPDD, SPAU and the Modification Assistant as routine upgrade chores. Their description of the tools is still useful. Three things to correct. First, SAP Cloud ALM now tracks business modifications as a figure to reduce, so the advice has shifted from "modify carefully" to "enhance instead", and the Enhancement Framework and released APIs are the first choice. Second, the SPDD documentation of the current ABAP Platform lists dictionary object types, such as data definitions, views and table types, that depend on a release number, so a book’s list of SPDD objects is shorter than today’s. Third, the classic path for getting an SSCR key goes through the SAP Service Marketplace pages of older documentation, which the current SAP support portal has replaced, so follow the current SAP support portal for the registration itself.

Source: ABAP Platform: Specifics for Adjusting ABAP Dictionary Objects Using Transaction SPDD, SAP Cloud ALM: Extensibility, Complete ABAP, SAP PRESS (publisher page; the page shows the current edition) and SAP ERP HCM Technical Principles and Programming, SAP PRESS (publisher page; the page shows a later edition)

Summary

  • A modification is a change to an SAP-delivered object. Updates overwrite it, and SAP’s warranty for the changed object is reduced, so it is the last resort after Customizing, personalization, exits, BAdIs and enhancements.

  • SSCR asks for a developer key once per system and for an object key once per SAP object and release; objects outside the SAP namespace, indexes and buffer settings are not registered.

  • The Modification Assistant protects the original, logs every Insert, Replace and Delete, lets you undo or reset, and feeds the Modification Browser (SE95). Switching it off loses the log.

  • At an update, SPDD adjusts modified ABAP Dictionary objects before mass activation, and SPAU adjusts the rest, SAP Notes first, with SPAU_ENH for enhancements. Both use transport requests that are marked for the later systems.

  • Cloud ALM tracks business modifications from the table SMODILOG, calls them neither clean-core-compliant nor upgrade-stable, and counts them apart from the clean core levels.

  • The Enhancement Framework, BAdIs and append structures keep your code in your own objects, so the upgrade leaves it alone.
