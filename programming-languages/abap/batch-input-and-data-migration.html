Batch Input, Direct Input and Data Migration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Sooner or later every SAP project has to get old data into the new system: thousands of customers, materials, open items or, in the running example of this section, expense claims that a legacy tool has held for years. Typing them in by hand is out of the question, and writing straight into the database tables would skip every check that the SAP application makes. This page explains the tools that SAP has offered for this job and says which of them are still the right choice. Batch input feeds the screens of an ordinary transaction with prepared values, as if a very fast user typed them, so every screen check runs. Direct input skips the screens and calls function modules that carry out the checks. The Legacy System Migration Workbench (LSMW) wraps these techniques in a guided tool, and the SAP S/4HANA migration cockpit is the tool of the current product documentation. The page is written for classic Standard ABAP release 8.16 (ABAP Platform 2025 in SAP S/4HANA 2025 FPS02) and SAP S/4HANA Cloud Public Edition 2608. Batch input, direct input and LSMW are classic technology: the statements and function modules exist only in Standard ABAP, and the ABAP for Cloud Development release 9.20 (2608) has no entry for CALL TRANSACTION. The migration cockpit exists for SAP S/4HANA on premise, the Private Edition and the Public Edition. After reading, you can build a batch input table for a transaction, run it with CALL TRANSACTION USING or store it in a session, explain what direct input and LSMW do and why they are legacy, and choose the migration cockpit or an API for a new project.

Before you read

  • Calling Programs, Transactions and Memory: what CALL TRANSACTION does to the caller and how its authority check works, because batch input is the second form of that statement.

  • Dynpros, Module Pools and Transactions: what a dynpro (screen), a field name, an OK code and a function code are, because a batch input table is a script of screens.

  • SAP LUW, Update Tasks and Commit: the update task and COMMIT WORK, because the update mode of a batch input run decides when data is saved.

  • RFC, BAPIs and IDocs: BAPIs and IDocs, the two other data transfer techniques that SAP names next to batch input and direct input.

Key terms

  • Batch input: a technique that transfers data automatically into the screens of transactions, controlled by batch input sessions or batch input tables.

  • Batch input table: an internal table of line type BDCDATA that holds the screens and field values for one transaction.

  • BDCDATA: the dictionary structure of one line of a batch input table, with the components PROGRAM, DYNPRO, DYNBEGIN, FNAM and FVAL.

  • Batch input session: a stored series of transaction calls with their input data, managed in transaction SM35.

  • Direct input: a technique that checks the data and writes it to the database through function modules, without processing any screen.

  • Legacy System Migration Workbench (LSMW): the guided tool, started with transaction LSMW, that reads, converts and imports legacy data with batch input, direct input, BAPIs or IDocs.

  • SAP S/4HANA migration cockpit: the tool of SAP S/4HANA that migrates business data with migration objects, from staging tables or directly from an SAP system.

  • Migration object: the description of how one kind of business data, such as a customer, is migrated: source and target structures, field mappings and conversion rules.

  • Staging table: a temporary table in which the data waits, filled from template files or by a tool, before the migration cockpit moves it into the system.

Which technique for which job

SAP’s documentation names four standard techniques for loading data: BAPIs, IDocs, batch input and direct input. They differ in what they run and in what they check, and the choice follows from that.

Technique What it does What to know

Batch input

Simulates the dialog: the data goes through the screens of a transaction, as if entered online.

All transaction checks run, which guarantees data consistency. It depends on screen numbers and field names, so a changed screen breaks the script.

Direct input

Calls function modules that do the checks, and writes to the database tables without screens.

Fast, and restartable when run in the background. Only for the data transfer objects that have a direct input program.

BAPI

Calls a remote-enabled function module of a business object.

A stable, documented interface; see RFC, BAPIs and IDocs.

IDoc

Loads data from IDocs through inbound processing.

Close to the BAPI technique; the application must provide the inbound processing.

Migration cockpit

Migrates with migration objects from staging tables or directly from an SAP system.

The tool of current SAP S/4HANA documentation, for the initial load of a new system.

The first four rows are the techniques of the Data Transfer Workbench documentation: it states that batch input transfers large volumes by simulating the transaction flow, and that direct input applies the same checks as the online transaction before it writes straight to the database. The migration cockpit row comes from the S/4HANA data migration documentation, which says the cockpit is meant for an initial load, specifically for a new implementation, and not to keep systems in sync.

Source: Data Transfer Workbench: Data Transfer Techniques and SAP S/4HANA Data Migration: Migrate Data Directly from SAP System

The batch input table

A batch input table is the script that the system follows. It is an internal table whose line type is the dictionary structure BDCDATA, and the Keyword Documentation lists its five components in this way.

Component Meaning

PROGRAM

Name of the program of the called transaction.

DYNPRO

Number of the dynpro to be processed.

DYNBEGIN

Flag for the start of a new dynpro: X or blank.

FNAM

Name of a dynpro field to be filled, or a batch input control statement, for example to position the cursor.

FVAL

Value for the dynpro field, or for the control statement.

The batch input documentation gives the recipe. For each screen you add one entry with PROGRAM, DYNPRO and DYNBEGIN set to X. For each field you add an entry with FNAM (the technical field name) and FVAL (the value); a field in a step loop or table control carries the line number in its name, for example field(5). Two control entries steer the screen: FNAM set to BDC_CURSOR puts the cursor on the field named in FVAL, and FNAM set to BDC_OKCODE triggers the function code in FVAL. The function code must start with a slash and the function key number, or with an equals sign for every other function code. You repeat this for each screen of the transaction, and you start the table empty for each new transaction call.

The running example is the claim entry dialog of Dynpros, Module Pools and Transactions: the transaction ZEXPC starts the program ZEXP_CLAIM_DIALOG at screen 0100, which has the input fields ZEXP_CLAIM-CLAIM_ID and ZEXP_CLAIM-TOTAL_AMOUNT and a Save pushbutton with the function code SAVE. The table behind it is the full ZEXP_CLAIM of Database Tables and Structures (client, claim_id, employee_id, status, currency_code, total_amount and the included structure zexp_s_audit); the dialog fills only the claim number and the total, so a migration through it leaves the other fields to the screen logic. The script for one legacy claim has one screen and five entries.

The listing builds that script and prints it. It runs in the lab of this site, which has no ABAP Dictionary, so the lab declares a local type with the same five component names instead of the dictionary structure BDCDATA, and uses string fields where the real structure uses fixed-length character fields. The legacy row is fictitious data.

REPORT zbdc_demo.

TYPES: BEGIN OF ty_bdcdata,
         program  TYPE string,
         dynpro   TYPE string,
         dynbegin TYPE string,
         fnam     TYPE string,
         fval     TYPE string,
       END OF ty_bdcdata.
TYPES ty_bdc_tab TYPE STANDARD TABLE OF ty_bdcdata WITH EMPTY KEY.

TYPES: BEGIN OF ty_legacy,
         claim_id TYPE string,
         amount   TYPE string,
       END OF ty_legacy.

CLASS lcl_script DEFINITION.
  PUBLIC SECTION.
    CLASS-METHODS for_claim
      IMPORTING legacy        TYPE ty_legacy
      RETURNING VALUE(result) TYPE ty_bdc_tab.
ENDCLASS.

CLASS lcl_script IMPLEMENTATION.
  METHOD for_claim.
    result = VALUE #(
      ( program = 'ZEXP_CLAIM_DIALOG' dynpro = '0100' dynbegin = 'X' )
      ( fnam = 'BDC_CURSOR'              fval = 'ZEXP_CLAIM-CLAIM_ID' )
      ( fnam = 'ZEXP_CLAIM-CLAIM_ID'     fval = legacy-claim_id )
      ( fnam = 'ZEXP_CLAIM-TOTAL_AMOUNT' fval = legacy-amount )
      ( fnam = 'BDC_OKCODE'              fval = '=SAVE' ) ).
  ENDMETHOD.
ENDCLASS.

START-OF-SELECTION.
  DATA(legacy_rows) = VALUE ty_legacy( claim_id = 'C-0001' amount = '125.50' ).
  DATA(script) = lcl_script=>for_claim( legacy_rows ).
  LOOP AT script INTO DATA(entry).
    IF entry-dynbegin = 'X'.
      WRITE / |screen { entry-program } { entry-dynpro }|.
    ELSE.
      WRITE / |  { entry-fnam } = { entry-fval }|.
    ENDIF.
  ENDLOOP.
  WRITE / |entries: { lines( script ) }|.

Run in the lab of this site (open-abap), with this output:

screen ZEXP_CLAIM_DIALOG 0100
  BDC_CURSOR = ZEXP_CLAIM-CLAIM_ID
  ZEXP_CLAIM-CLAIM_ID = C-0001
  ZEXP_CLAIM-TOTAL_AMOUNT = 125.50
  BDC_OKCODE = =SAVE
entries: 5

Source: Using the Data Transfer Data Structure and Keyword Documentation for Standard ABAP: CALL TRANSACTION, USING

The same documentation page contains a worked table for the ABAP editor SE38, and the Keyword Documentation example CL_DEMO_CALL_TRANSACTION_BDC fills a table in the same way for the Class Builder SE24. Never guess the program name, screen number and field names of a transaction: take them from the screen itself. In SAP GUI the technical information of a field shows them, and the batch input recorder (transaction SHDB) writes them for you, as the next sections explain.

Source: Keyword Documentation for Standard ABAP: Transaction Call, BDC Table

CALL TRANSACTION USING

The statement CALL TRANSACTION ta WITH|WITHOUT AUTHORITY-CHECK USING bdc_tab runs the transaction with the table. The call works as every CALL TRANSACTION: the calling program and its data are kept, and the statement returns when the transaction is finished. The called program runs in its own SAP LUW, but in the same database LUW, so a database commit or rollback in the called program acts on the caller too. Three facts are specific to the USING form:

  • In the called program the system field sy-binpt has the value X, and while it runs no other transaction can be called with USING. A recursive call ends with the runtime error CALL_TRANSACTION_USING_NESTED.

  • sy-subrc is 0 when the transaction was processed successfully, below 1000 for an error in the called transaction, and 1001 for a processing error including runtime errors. A runtime error in the called transaction does not show a short dump; control returns to the caller with sy-subrc 1001 and the name of the runtime error in a status message.

  • The documentation says that calling a transaction with a batch input table is not exactly the same as running batch input sessions, and that the control options of the table include those of sessions and sometimes exceed them.

Three additions control the run. MODE sets the processing mode: A shows the screens, E shows them only when an error occurs, and N or P run without any screen display; without MODE and OPTIONS FROM, A applies. UPDATE sets the update mode: A asynchronous, S synchronous (as COMMIT WORK AND WAIT) and L local; the default is A. OPTIONS FROM opt covers both and adds more, in a structure of the dictionary type CTU_PARAMS with the components DISMODE and UPMODE (the same values as MODE and UPDATE), CATTMODE, DEFSIZE (standard screen size), RACOMMIT (whether COMMIT WORK ends the processing), NOBINPT and NOBIEND (the content of sy-binpt). MESSAGES INTO itab stores all the messages of the run in an internal table of line type BDCMSGCOLL, including the status message of a runtime error.

The authority check follows the rule of Authority Checks: with WITH AUTHORITY-CHECK the system checks the authorization object S_TCODE and the authorization object entered in the definition of the transaction code in SE93, and a missing authorization raises the catchable CX_SY_AUTHORIZATION_ERROR. Leaving both additions out is obsolete.

The listing loads one claim through the transaction ZEXPC. The script is the one built above, with the dictionary structure BDCDATA as line type. The listing needs an SAP system with the dialog transaction of the running example; it is not run here.

DATA bdc_tab TYPE TABLE OF bdcdata WITH EMPTY KEY.
DATA messages TYPE TABLE OF bdcmsgcoll WITH EMPTY KEY.

bdc_tab = VALUE #(
  ( program = 'ZEXP_CLAIM_DIALOG' dynpro = '0100' dynbegin = 'X' )
  ( fnam = 'BDC_CURSOR'              fval = 'ZEXP_CLAIM-CLAIM_ID' )
  ( fnam = 'ZEXP_CLAIM-CLAIM_ID'     fval = 'C-0001' )
  ( fnam = 'ZEXP_CLAIM-TOTAL_AMOUNT' fval = '125.50' )
  ( fnam = 'BDC_OKCODE'              fval = '=SAVE' ) ).

FINAL(opt) = VALUE ctu_params( dismode = 'N'
                               upmode  = 'S'
                               defsize = 'X' ).

TRY.
    CALL TRANSACTION 'ZEXPC' WITH AUTHORITY-CHECK
                             USING bdc_tab
                             OPTIONS FROM opt
                             MESSAGES INTO messages.
  CATCH cx_sy_authorization_error.
    WRITE / 'no authorization for transaction ZEXPC'.
    RETURN.
ENDTRY.

IF sy-subrc = 0.
  WRITE / 'claim loaded'.
ELSEIF sy-subrc < 1000.
  WRITE / |error in the transaction, { lines( messages ) } messages collected|.
ELSE.
  WRITE / 'runtime error in the transaction'.
ENDIF.

Source: Keyword Documentation for Standard ABAP: CALL TRANSACTION, USING, CALL TRANSACTION and CALL TRANSACTION, AUTHORITY-CHECK

Two traps are worth knowing. First, mode N hides every screen, so a wrong screen number or field name shows only as a non-zero sy-subrc and messages; test a new script with mode A or E first. The Data Transfer Workbench documentation likewise advises processing sessions in the foreground or with error display for tests and in the background for the real transfer. Second, a transaction with its own COMMIT WORK ends the run unless RACOMMIT is set, and the update mode decides whether the data is saved when the call returns. With the default asynchronous update the call can return before the update has finished, which is why the listing sets S. The statement is also hard on loops: every call starts a fresh internal session, and the Keyword Documentation limits a call sequence to nine internal sessions.

Source: Keyword Documentation for Standard ABAP: CALL TRANSACTION and Data Transfer Workbench: Data Transfer Techniques

Batch input sessions and SM35

The other way to use the table is to store it. A batch input session is a series of transaction calls with their input data, stored persistently in the batch input queue and managed in transaction SM35. The data is entered into the system only when the session is processed, and that is the main difference from CALL TRANSACTION USING: creating and running are two steps that can be done by different people at different times. The documentation calls the session one of the two recommended ways to process batch input data. A program creates a session with three function modules.

  1. BDC_OPEN_GROUP creates the session. GROUP is the session name (at most 12 characters, no default), CLIENT the client in which it is processed, USER the user whose authorizations are checked when the session runs in the background, HOLDDATE a lock date in the format YYYYMMDD before which the session cannot be processed, and KEEP set to X keeps the session after successful processing; otherwise a successfully processed session is deleted and only the log stays. A session with errors in a transaction is kept in any case. A program may have only one session open at a time, and a closed session cannot be reopened: opening the same name again creates an additional session with that name.

  2. BDC_INSERT adds one transaction: TCODE is the transaction code and the table parameter DYNPROTAB is the batch input table, which must contain all the data the transaction needs. POST_LOCAL requests a local update.

  3. BDC_CLOSE_GROUP closes the session that is open in the program, after all the data is inserted. It needs no parameters. A closed session can be processed.

The listing creates one session for several legacy claims. The script building is the same as above and is shown as a call to a method build_script, which stands for the construction of the bdc_tab of the previous listing for one legacy row. The legacy table legacy_rows is assumed to be filled by the program. The listing needs an SAP system; it is not run here.

DATA bdc_tab TYPE TABLE OF bdcdata WITH EMPTY KEY.

CALL FUNCTION 'BDC_OPEN_GROUP'
  EXPORTING
    client = sy-mandt
    group  = 'ZEXP_CLAIMS'
    user   = sy-uname
    keep   = 'X'
  EXCEPTIONS
    OTHERS = 1.
IF sy-subrc <> 0.
  RETURN.
ENDIF.

LOOP AT legacy_rows INTO DATA(legacy).
  bdc_tab = build_script( legacy ).
  CALL FUNCTION 'BDC_INSERT'
    EXPORTING
      tcode     = 'ZEXPC'
    TABLES
      dynprotab = bdc_tab
    EXCEPTIONS
      OTHERS    = 1.
ENDLOOP.

CALL FUNCTION 'BDC_CLOSE_GROUP'.

Source: Creating Batch Input Sessions, Creating a Session with BDC_OPEN_GROUP, Adding Data to a Session: BDC_INSERT and Closing a Session: BDC_CLOSE_GROUP

Creating a session needs no special authorization beyond the one to run the program (the authorization object S_PROGRAM); processing it does, which is the point of the USER parameter. A session stays in the queue until somebody starts it. Two ways are documented: an online user starts it through the batch input menu (System, Services, Batch Input), or the background job RSBDCSUB starts every session of a given name. The generation and the processing can be chained in the background: make the batch input job the predecessor of RSBDCSUB, which then starts when it finishes successfully, or schedule both as steps of one job, in which case RSBDCSUB starts even if the batch input program ended abnormally.

SM35 is the place to administer sessions: selecting, running and correcting a session, locking, deleting, restarting an interrupted one, and reading the logs. The documentation also names the tiles and transactions SM35SM (my batch input folders), SM35SA (folders in my area), SM35PSM (my logs) and SM35PSA (logs in my area). Its process overview describes the routine: the administrator checks daily that all sessions finished, and a session with errors needs the help of the person responsible for the data. The batch input recorder, transaction SHDB, records a transaction as you use it and can create a session from the recording, so you do not have to write a program; the page of the batch input manager sends the reader to the guide "Programming Interface for Background Processing" for it. Some SM35 functions are not available in the cloud edition, which the page writes as "S/4HANA CE".

Source: Processing Batch Input Sessions, Managing Batch Input Sessions, Process Overview: Batch Input and Batch Input Authorizations

The two uses side by side:

CALL TRANSACTION USING Batch input session

When the data enters the system

At once, inside the program.

When the session is processed, later.

Where the result is

sy-subrc and the messages table of the program.

The session log in SM35.

Update

Chosen with UPDATE or UPMODE; default asynchronous.

Always synchronous.

Restart after an error

Your program must do it.

SM35 can correct and restart the session.

The update row is taken from the documentation of UPDATE, which says the option is not available for batch input sessions because updates are always synchronous there.

Source: Keyword Documentation for Standard ABAP: CALL TRANSACTION, USING

Direct input

Direct input is the faster sibling of batch input. It creates no session and processes no screen. The program reads the data from the transfer file and calls function modules that run the checks of the application before the database is updated. That is why SAP describes it as a way to enhance batch input, especially for large amounts of data. Its restart mechanism works only when the program runs in the background: processing can then continue where it stopped, which prevents data being posted twice. Started directly in the foreground, the program writes no error log and cannot be restarted. The Basis documentation lists these direct input programs as examples: RFBIBL00 for FI, RMDATIND for MM, RVAFSS00 for SD, RAALTD11 for asset accounting and RKEVEXT0 for CO-PA. The Data Transfer Workbench lists the data transfer objects that can use direct input: material masters, accounting documents, sales documents, attachments and classification, and shows the direct input transaction BMV0 as the place to start them. For test data it suggests starting the program directly, and for the final transfer it strongly recommends running it through that transaction in the background.

Direct input exists only for the objects that have such a program. For every other business object the classic choices were batch input, a BAPI or an IDoc.

Source: Direct Input (Application Development on AS ABAP) and Legacy System Migration Workbench: Direct Input

LSMW, the guided tool

The Legacy System Migration Workbench is a cross-application tool, started with transaction LSMW, that supports data migration from non-SAP systems to SAP systems. It does not migrate single tables but user-defined data sets, called objects, combined by business criteria. Its main functions are three steps: read the legacy data from spreadsheet tables or sequential files, convert it from the source into the target format, and import it into the database. For the import it offers the standard batch input and direct input, recordings (which let you generate objects of your own from a recorded transaction), BAPIs and IDocs. It adds a field assignment editor with ABAP code at several processing times, an action log, and project export and import.

The documentation draws its limits clearly. LSMW supports a one-time transfer of data, the initial data load, and only a restricted form of permanent interfaces; it has no functions to monitor permanent interfaces and supports no export of data. It should not be used before the system is installed and the customizing of the applications is complete, and a basic knowledge of ABAP is useful for it. Its help still sits in the ABAP Platform documentation. The product documentation of SAP S/4HANA names a different tool for the data migration of a new system, described next; which classic tools a given S/4HANA release still allows is stated in the SAP Notes for that release, which need an S-user login.

Source: Legacy System Migration Workbench and Using LSMW

The SAP S/4HANA migration cockpit

The migration cockpit is the tool of the S/4HANA data migration documentation. It transfers business data with migration objects: a migration object describes how to migrate data for one business object. It holds the source and target structures, the relationships between them, the mapping of the fields and the rules that convert values. SAP delivers predefined migration objects, and which ones you see depends on the scope you activated and on the approach you chose. The cockpit is designed for an initial load, specifically for a new implementation. It does not keep data in sync between systems and does not realize a continuous exchange or an integration scenario; the documentation points to other SAP products for that.

You work in the Fiori app Migrate Your Data - Migration Cockpit (app ID F3473), in both the on-premise documentation and the Public Edition documentation. With it you create migration projects, select the migration objects of your scenario, process the mapping tasks, simulate the migration before it runs, and migrate and monitor the status. The app Data Migration Status (app ID F3280) shows the simulated and migrated instances of the projects; it supports only the staging table approach. The earlier app of the Migration Cockpit, transaction LTMC, is deprecated: the Migrate Your Data app is its successor, LTMC can no longer be used to migrate data to SAP S/4HANA, and its old projects can still be viewed. Migration objects are enhanced with the migration object modeler, started with transaction LTMOM. A regular check with transaction CNV_NA_MC (the note analyzer) confirms that all correction notes for the cockpit are implemented.

There are two approaches.

Staging tables Direct transfer from an SAP system

How data arrives

The cockpit creates a staging table for every migration object of the project; you fill it from the template file of the object or with a tool of your choice, and the cockpit migrates from the tables to the target.

The cockpit reads the data of certain SAP source systems through a connection and converts it to the S/4HANA data model.

Where it lives

When you create the project you choose the staging location: the local schema of the S/4HANA system, or a remote SAP HANA schema reached through a connection.

Nothing is staged by you; a project is bound to one source system and cannot change it.

In the Public Edition

Local schema filled from template files; a remote schema for large volumes (SAP Learning describes both options, with XML or CSV templates, in its Private Edition course). Needs a communication arrangement for the scenario SAP_COM_0678 when a remote schema is used.

Lowest source release ECC 6.0 (SAP NetWeaver 7.0). Needs the communication scenario SAP_COM_0816 and the DMIS 2011 add-on in the source system. An S/4HANA system cannot be the source.

Two cautions come from the documentation itself. A migration copies personal data too, and data protection law can require that data that has served its purpose is deleted; migrating data that should have been deleted can count as processing without a justified purpose, so such data must not be migrated. And a user who may view or change the staging tables in a remote schema can read all the data there, so only authorized users should have that access.

Source: SAP S/4HANA Data Migration, Migrate Data Using Staging Tables, Migrate Data Directly from SAP System, Migrate Your Data - Migration Cockpit, Data Migration Status, SAP S/4HANA Migration Object Modeler, Migration Cockpit (Transaction LTMC) - Deprecated, Public Edition: Migrate Your Data - Migration Cockpit, Public Edition: Before You Start and SAP Learning: Migrating Data to SAP S/4HANA Cloud Private Edition

For the claims of the running example the choice is therefore plain. If the expense claims live in an SAP ERP system and a migration object covers the business data, the cockpit moves them with the direct transfer approach; if they live in a spreadsheet or another tool, they go through staging tables. The ZEXP_CLAIM table is a custom table, so no predefined migration object covers it. Such data is loaded with a program that writes to the table, as in ABAP SQL: Writing Data, or the migration object modeler is used to enhance a migration object where one is close enough.

What older books show, and what has changed

Older ABAP books, including the 2016 edition of Complete ABAP that this chapter was cross-checked against for coverage, present batch input, LSMW and BAPIs as the three everyday ways to load data. Today:

  • LSMW is a tool for the initial data load of a classic system. For a new SAP S/4HANA system the data migration documentation names the migration cockpit, and its predecessor app, transaction LTMC, is itself deprecated, so a book that teaches LTMC or LSMW as the S/4HANA route is out of date.

  • Batch input still works in classic Standard ABAP, but it depends on screen numbers and field names, which change with releases and enhancements. A BAPI, a released API or a RAP business object is the stable way where one exists.

  • Books show CALL TRANSACTION USING without WITH AUTHORITY-CHECK or WITHOUT AUTHORITY-CHECK. Leaving both out is obsolete.

  • Books do not cover the cloud: neither the statements of this page nor the batch input function modules are part of the ABAP Cloud language, and the Public Edition migrates with the cockpit.

Common mistakes

Mistake Remedy

The script fills a field that is not on the screen.

The value is lost or the transaction ends with an error message. Take every program, screen and field name from the screen, or record it with SHDB.

Mode N is used before the script works.

Test with mode A or E and the screens visible, then switch to N.

The data is not saved when the call returns.

The default update mode is asynchronous. Set the update mode to synchronous (S) when the next step reads the data.

A session is opened inside the loop.

One session per record. Open once before the loop and close once after it; a program may have only one session open.

A closed session is opened again.

A closed session cannot be reopened; the same name creates an additional session.

Authorizations are tested with a powerful user.

A session started in the background uses the USER of BDC_OPEN_GROUP; give that user the authorizations for every transaction in the session.

Direct input is started in the foreground for the final load.

No error log and no restart. Run it in the background.

The migration cockpit is used to keep two systems in sync.

It is meant for the initial load of a new implementation, not for a continuous exchange.

Source: Keyword Documentation for Standard ABAP: CALL TRANSACTION, USING, Creating a Session with BDC_OPEN_GROUP and Direct Input

Summary

  • Batch input feeds the screens of a transaction from a batch input table (line type BDCDATA), so every check of the transaction runs. The script depends on program, screen and field names.

  • CALL TRANSACTION USING runs the table at once and reports sy-subrc (0, below 1000, or 1001) and a messages table; a batch input session built with BDC_OPEN_GROUP, BDC_INSERT and BDC_CLOSE_GROUP runs later from SM35 or the job RSBDCSUB.

  • Direct input skips the screens and calls function modules for the checks. It is restartable only in the background.

  • LSMW wraps these techniques with BAPIs and IDocs for a one-time load of a classic system.

  • For SAP S/4HANA the documented tool is the migration cockpit (Migrate Your Data app, staging tables or direct transfer); the older LTMC app is deprecated. Where a BAPI, a released API or a RAP business object exists, use it.
