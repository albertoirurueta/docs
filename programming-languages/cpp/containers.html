Containers

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Sequence Containers

#include <vector>
#include <array>
#include <deque>
#include <list>
#include <forward_list>

std::vector<int> v = {1, 2, 3};          // contiguous, growable -- the default choice for almost everything
std::array<int, 3> a = {1, 2, 3};         // fixed-size, contiguous, stack-allocated -- a "safe C array"
std::deque<int> d = {1, 2, 3};             // double-ended queue: fast push/pop at both ends, NOT contiguous
std::list<int> l = {1, 2, 3};               // doubly-linked list: O(1) insert/erase anywhere, no random access
std::forward_list<int> fl = {1, 2, 3};       // singly-linked list: smaller than list, forward iteration only

Associative Containers

Ordered by key (typically a red-black tree), giving O(log n) lookup/insert/erase and in-order iteration:

#include <map>
#include <set>

std::map<std::string, int> ages = {{"Ada", 36}};            // unique keys, sorted
std::multimap<std::string, int> scores;                       // duplicate keys allowed, sorted
scores.insert({"Ada", 90});
scores.insert({"Ada", 85});                                    // both entries kept

std::set<int> unique = {3, 1, 2};                              // sorted, unique elements: {1, 2, 3}
std::multiset<int> withDupes = {3, 1, 2, 1};                    // sorted, duplicates allowed: {1, 1, 2, 3}

Unordered Containers

Hash-table based, giving average O(1) lookup/insert/erase but no ordering guarantee — needs std::hash<Key> for a custom key type (see Standard Library Overview):

#include <unordered_map>
#include <unordered_set>

std::unordered_map<std::string, int> fastAges = {{"Ada", 36}};
std::unordered_set<int> fastUnique = {3, 1, 2};                 // no ordering guarantee when iterated

flat_map/flat_set (C++23)

std::flat_map/std::flat_set store keys and values in sorted, contiguous vectors rather than a tree — much better cache locality and lower memory overhead for read-heavy workloads, at the cost of O(n) insertion (shifting elements) instead of a tree’s O(log n):

#include <flat_map>

std::flat_map<std::string, int> config = {{"retries", 3}, {"timeout", 30}};
config["retries"] = 5;             // same interface as std::map for lookup/insert
// internally: two sorted vectors (keys, values), not a tree -- far fewer allocations, better cache behavior
<flat_map>/<flat_set> are standard-conformant C++23 (verified against cppreference and the working draft) and are recent additions to the standard libraries: libstdc++ ships both from GCC 15, libc++ ships <flat_map> from LLVM 20 and <flat_set> from LLVM 21 (both are available with the Apple clang 21 and libc++ toolchain used for this section), and MSVC ships them too (see Getting Started).

Container Adaptors

An adaptor restricts a sequence container’s interface to a specific access pattern, rather than implementing storage itself:

#include <stack>
#include <queue>

std::stack<int> s;              // LIFO, backed by std::deque by default
s.push(1); s.push(2);
s.pop();                          // removes 2

std::queue<int> q;               // FIFO, backed by std::deque by default
q.push(1); q.push(2);
q.pop();                           // removes 1

std::priority_queue<int> pq;      // max-heap, backed by std::vector by default
pq.push(3); pq.push(1); pq.push(2);
pq.top();                          // 3 -- the largest

std::span and std::mdspan

std::span<T> (C++20) is a non-owning (pointer, length) view over a contiguous sequence — the array/vector analogue of std::string_view:

#include <span>
#include <vector>
#include <array>

void printAll(std::span<const int> values) {   // accepts a C array, std::array, or std::vector -- no copy
    for (int v : values) { (void)v; }
}

int carr[3] = {1, 2, 3};
std::vector<int> vec = {4, 5, 6};
std::array<int, 3> arr = {7, 8, 9};
// printAll(carr); printAll(vec); printAll(arr);   // all three bind without any conversion overhead

std::mdspan<T, Extents> (C++23) generalizes std::span to multiple dimensions over one flat buffer, with a customizable layout (row-major, column-major, or a custom stride) — useful for numeric/matrix code that would otherwise hand-roll index arithmetic:

#include <mdspan>
#include <vector>

std::vector<double> buffer(6, 0.0);
std::mdspan<double, std::extents<std::size_t, 2, 3>> matrix(buffer.data());
matrix[1, 2] = 5.0;    // row 1, column 2 -- no manual "row * cols + col" arithmetic
<mdspan> is standard-conformant C++23 syntax (verified against cppreference and the working draft) but needs a recent standard library: libc++ provides it fully from LLVM 18 (including the Apple clang 21 and libc++ toolchain used for this section), libstdc++ from GCC 16, and MSVC as well; std::span (C++20) is available in all three.

std::bitset and vector<bool>

std::bitset<N> was covered in Numbers and Math. std::vector<bool> is a notorious special case: it’s specialized to pack bits (8 per byte) rather than storing one bool per element, so operator[] returns a proxy object, not bool& — code generic over vector<T> that assumes T& from operator[] breaks for T = bool:

#include <vector>

std::vector<bool> flags = {true, false, true};
// bool& ref = flags[0];         // error: vector<bool>::reference is a proxy, not bool&
auto ref = flags[0];              // fine: deduces the proxy type
bool copy = flags[0];              // fine: converts to a real bool

For a genuine array-of-bool with real references, prefer std::vector<char>, std::array<bool, N>, or std::deque<bool> (which is not specialized this way).

Choosing the Right Container

Iterator/Reference Invalidation

Modifying a container can invalidate existing iterators/references/pointers into it — the exact rule differs per container and operation, and using an invalidated iterator is undefined behavior:

Container Invalidation on insert/erase

vector

push_back beyond capacity invalidates everything; erase invalidates from the erased point onward.

deque

Insert/erase at either end rarely invalidates; insert/erase in the middle invalidates everything.

list/forward_list

Erase invalidates only the erased element’s iterator; insert never invalidates any.

map/set

Erase invalidates only the erased element’s iterator; insert never invalidates any.

std::erase_if (covered in Iterators and Algorithms) sidesteps hand-writing an erase-in-a-loop that must reason about which iterators survive each step.

Choosing and Using Containers, With Evidence

The right container is usually decided by two questions: do you need the elements in a particular order, and how do you look elements up. The standard offers contiguous arrays, linked lists, trees, hash tables and sorted arrays; each has a different cost profile and a different promise about when pointers and iterators stay valid.

containers.cpp
#include <array>
#include <deque>
#include <flat_map>
#include <list>
#include <map>
#include <mdspan>
#include <print>
#include <span>
#include <string>
#include <unordered_map>
#include <vector>

void total(std::span<const int> xs) {   // accepts vector, array, C array without copying
    int s = 0;
    for (int x : xs) s += x;
    std::println("span of {} sums to {}", xs.size(), s);
}

int main() {
    // vector growth and reallocation: capacity doubles (the factor is implementation-defined).
    std::vector<int> v;
    std::size_t last = 0;
    for (int i = 0; i < 20; ++i) {
        v.push_back(i);
        if (v.capacity() != last) { std::print("{} ", v.capacity()); last = v.capacity(); }
    }
    std::println("<- capacities seen while pushing 20 elements");

    // Invalidation: push_back may reallocate and invalidate pointers/iterators; list never does.
    std::vector<int> w{1, 2, 3};
    w.shrink_to_fit();
    int* before = &w[0];
    w.push_back(4);
    std::println("vector element moved after growth: {}", before != &w[0]);
    std::list<int> l{1, 2, 3};
    int* lbefore = &l.front();
    l.push_back(4);
    std::println("list element moved after growth: {}", lbefore != &l.front());

    // map (ordered, tree) vs unordered_map (hash) vs flat_map (sorted vector).
    std::map<std::string, int> ordered{{"emma", 2}, {"dune", 3}, {"alien", 1}};
    std::unordered_map<std::string, int> hashed(ordered.begin(), ordered.end());
    std::flat_map<std::string, int> flat(ordered.begin(), ordered.end());
    std::print("map iteration order:");
    for (const auto& [k, n] : ordered) std::print(" {}={}", k, n);
    std::println("");
    std::print("flat_map iteration order:");
    for (const auto& [k, n] : flat) std::print(" {}={}", k, n);
    std::println("");
    std::println("hashed has {} entries (order unspecified)", hashed.size());

    // operator[] inserts a missing key; at() and find() do not.
    std::println("size before lookup {}", ordered.size());
    int missing = ordered["zzz"];
    std::println("after ordered[\"zzz\"] = {}: size {}", missing, ordered.size());

    // span and mdspan: non-owning views.
    std::array<int, 4> arr{1, 2, 3, 4};
    int c_array[] = {10, 20};
    total(v);
    total(arr);
    total(c_array);
    std::vector<int> cells{1, 2, 3, 4, 5, 6};
    std::mdspan grid(cells.data(), 2, 3);   // 2 rows x 3 columns over the same memory
    std::println("grid[1, 2] = {}, extent(0) = {}, extent(1) = {}", grid[1, 2], grid.extent(0), grid.extent(1));

    std::deque<int> d{2, 3};
    d.push_front(1);
    std::println("deque front {} back {} size {}", d.front(), d.back(), d.size());
}

  • The capacity sequence 1 2 4 8 16 32 shows geometric growth: each reallocation copies or moves every element, which is why the total cost of N push_back calls is still O(N) amortized. If you know the size, reserve(n) avoids every intermediate reallocation.

  • The vector element moved after push_back because the buffer was full; a pointer or iterator taken before the call would now dangle (undefined behaviour to use). The list element stayed where it was. Rule: holding an iterator, pointer or reference into a vector across anything that can insert is a bug.

  • map iterates in key order; flat_map has the same interface and order but stores keys and values in sorted contiguous arrays; unordered_map has no order you may rely on.

  • operator[] on a map inserts a default value for a missing key, which is why the size grew from 3 to 4 above. Use find, at or contains for a read that must not insert, and try_emplace or insert_or_assign to say what you mean when writing.

  • std::span is a pointer and a length: one function parameter accepted a vector, a std::array and a C array. std::mdspan gives a multidimensional view over existing memory; the C++23 grid[1, 2] subscript is the operator[] with several arguments described in Operator Overloading and Conversions. Neither owns its data, so neither may outlive it.
