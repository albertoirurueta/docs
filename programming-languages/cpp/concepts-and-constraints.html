Concepts and Constraints

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Before C++20, a template argument that didn’t satisfy a function’s implicit expectations produced a wall of cryptic errors deep inside the template’s body. Concepts name those expectations and check them before instantiation, turning that wall into one clear message at the call site.

concept and requires Clauses

#include <concepts>

template <typename T>
concept Numeric = std::integral<T> || std::floating_point<T>;   // a named, reusable predicate on types

template <typename T>
requires Numeric<T>                       // a requires clause: constrains this overload to Numeric types
T doubleIt(T value) {
    return value * 2;
}

template <Numeric T>                       // equivalent, more concise: the concept used directly as the
T doubleItV2(T value) {                     // template-parameter's "type"
    return value * 2;
}

Calling doubleIt("hello") now fails with "constraints not satisfied: Numeric<const char*>" at the call site, instead of a multi-page error from inside doubleIt's body.

requires Expressions

A requires expression (as opposed to a requires clause, which uses one) directly describes what syntax must be valid, for ad hoc constraints with no pre-existing named concept:

template <typename T>
concept Printable = requires(T value, std::ostream& os) {
    { os << value } -> std::same_as<std::ostream&>;   // "os << value" must compile and yield exactly ostream&
};

template <typename T>
concept Container = requires(T c) {
    typename T::value_type;         // a nested type must exist
    c.begin();                       // these expressions must be valid
    c.end();
    { c.size() } -> std::convertible_to<std::size_t>;
};

Standard Concepts

<concepts> ships a library of ready-made concepts covering the most common constraints, so most code never needs to hand-write one:

Concept Constrains to

std::integral<T>

Any integer type (int, long, bool, char, …​).

std::floating_point<T>

float, double, long double.

std::same_as<T, U>

Exactly the same type (order-sensitive; same_as<T,U> and same_as<U,T> are both checked).

std::convertible_to<From, To>

From implicitly converts to To.

std::default_initializable<T>

T can be default-constructed.

std::copyable<T> / std::movable<T>

T supports copy / move.

std::regular<T>

Default-constructible, copyable, and equality-comparable — a "well-behaved value type".

Abbreviated Function Templates

C++20 lets a function parameter’s type itself be auto (optionally constrained), implicitly making the function a template with no template<...> header needed:

auto add(auto a, auto b) {              // implicitly: template<typename T, typename U> auto add(T a, U b)
    return a + b;
}

auto addNumeric(Numeric auto a, Numeric auto b) {   // constrained abbreviated template
    return a + b;
}

Subsumption

When two constrained overloads could both match, the compiler prefers the one whose constraints are strictly more specific — this ordering is called subsumption:

template <typename T>
requires std::integral<T>
void process(T) { /* generic integral handling */ }

template <typename T>
requires std::integral<T> && std::signed_integral<T>
void process(T) { /* signed-specific handling */ }

// process(5) calls the SECOND overload: std::signed_integral<T> && std::integral<T>
// subsumes (is more specific than) std::integral<T> alone, so it wins overload resolution
// instead of being ambiguous.

Constraints That Produce Readable Errors

Concepts name the requirements a template places on its arguments, and the compiler checks them before instantiating the body. A violation produces one clear message at the call site instead of a chain of errors from inside the library. The example models the inventory’s Titled and Loanable capabilities as concepts and overloads on them.

flowchart TB CALL["describe(book)"] --> C1{"Titled<Book>?"} C1 -->|"yes"| C2{"Loanable<Book>?"} C1 -->|"no"| X["candidate removed"] C2 -->|"yes"| BOTH["both overloads viable"] BOTH --> SUB["Loanable<T> is defined as Titled<T> and more,
so it subsumes Titled: the Loanable overload is MORE SPECIALIZED"] SUB --> WIN["Loanable overload chosen, no ambiguity"] C2 -->|"no (Poster)"| ONLY["only the Titled overload viable"]
concepts.cpp
#include <concepts>
#include <print>
#include <string>
#include <vector>

// A concept names a requirement; a requires-expression checks syntax and types.
template <typename T>
concept Titled = requires(const T& t) {
    { t.title() } -> std::convertible_to<std::string>;
};

template <typename T>
concept Loanable = Titled<T> && requires(const T& t) {
    { t.loan_days() } -> std::integral;
};

struct Book {
    std::string title() const { return "Dune"; }
    int loan_days() const { return 21; }
};
struct Poster {
    std::string title() const { return "Metropolis"; }   // titled, but cannot be borrowed
};

// Constrained function templates: overload on concepts instead of enable_if.
template <Titled T>
std::string describe(const T& t) { return "item: " + t.title(); }

template <Loanable T>   // subsumes Titled, so this overload wins for Book
std::string describe(const T& t) { return "loanable: " + t.title() + " for " + std::to_string(t.loan_days()) + " days"; }

// Abbreviated function template with a standard concept.
auto twice(std::integral auto n) { return n * 2; }

// Constraining with requires-clause on a class template member.
template <typename T>
class Box {
public:
    explicit Box(T v) : v_(std::move(v)) {}
    std::string show() const requires std::convertible_to<T, std::string> { return v_; }
    T value() const { return v_; }

private:
    T v_;
};

static_assert(Titled<Poster>);
static_assert(!Loanable<Poster>);
static_assert(Loanable<Book>);

int main() {
    std::println("{}", describe(Poster{}));
    std::println("{}", describe(Book{}));
    std::println("{} {}", twice(21), twice(7L));
    // twice(2.5);       // error: no matching function; the note says 'double' does not satisfy 'integral'
    Box<std::string> s("Emma");
    std::println("{}", s.show());
    Box<int> i(3);
    std::println("{}", i.value());
    // i.show();         // error: invalid reference to function 'show': constraints not satisfied
}
$ clang++ -std=c++23 -Wall -Wextra concepts.cpp -o concepts
$ ./concepts
item: Metropolis
loanable: Dune for 21 days
42 14
Emma
3

  • A concept is a named compile-time predicate. A requires expression is a list of requirements checked for validity: { t.title() } -> std::convertible_to<std::string>; means "the expression is valid and its type is convertible". It checks that code would compile; it never runs it.

  • Subsumption is why the Loanable overload wins for Book without ambiguity: its constraint is Titled<T> && ..., so the compiler can prove it implies the Titled constraint. Subsumption only works through named concepts combined with && and ||; two textually identical requires clauses on different templates do not subsume each other, which is a reason to name concepts instead of repeating expressions.

  • std::integral auto n (an abbreviated template) is shorthand for template <std::integral T> auto twice(T n).

  • A trailing requires clause on a member (show() above) removes that member from classes whose arguments do not satisfy it, without making the whole class fail. Box<int> is fine until show() is called.

What a violation looks like

badconcept.cpp
#include <concepts>
#include <print>
auto twice(std::integral auto n) { return n * 2; }
int main() { std::println("{}", twice(2.5)); }
$ clang++ -std=c++23 badconcept.cpp -o bad 2>&1 | head -8
badconcept.cpp:4:33: error: no matching function for call to 'twice'
    4 | int main() { std::println("{}", twice(2.5)); }
      |                                 ^~~~~
badconcept.cpp:3:6: note: candidate template ignored: constraints not satisfied [with n:auto = double]
    3 | auto twice(std::integral auto n) { return n * 2; }
      |      ^
badconcept.cpp:3:12: note: because 'double' does not satisfy 'integral'
    3 | auto twice(std::integral auto n) { return n * 2; }

The message states the failing constraint ('double' does not satisfy 'integral'+) and names the candidate. Compare that with the error in Templates for the unconstrained template, which only reports a failed < inside the body. Concepts also document intent: std::integral auto reads as a requirement; typename T says nothing.
