Generics and Variance

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Generics let one class or function work with many types while the compiler still checks the types at each use. Kotlin generics are Java generics at run time (the type arguments are erased) but with a different and, once understood, simpler variance model: instead of wildcards, a type parameter is declared out (a producer) or in (a consumer), and where that is not possible a use-site projection or a star projection fills the gap. This page covers type parameters and bounds, erasure and what it prevents, declaration-site and use-site variance with the reasoning behind them, star projections, reified type parameters, and the differences from Java. The examples use a small hierarchy of lendable items from the library domain of this section: a base class Item, with Book and Dvd below it.

Generic Classes and Functions

A type parameter is declared in angle brackets after the class or function name, and the compiler infers the type arguments at call sites whenever it can:

open class Item(val title: String)
class Book(title: String, val author: String) : Item(title)
class Dvd(title: String, val minutes: Int) : Item(title)

class Box<T>(var content: T)                         // generic class

fun <T> firstOr(list: List<T>, default: T): T =      // generic function; the type parameter precedes the name
    if (list.isEmpty()) default else list[0]

fun main() {
    val box = Box(Book("Dune", "Herbert"))           // T inferred as Book
    println(box.content.author)

    val first = firstOr(emptyList<String>(), "none") // T inferred as String
    println(first)

    val explicit = firstOr<Item>(listOf(Dvd("Alien", 117)), Book("Emma", "Austen"))   // explicit type argument
    println(explicit.title)
}

Output:

Herbert
none
Alien

An unbounded type parameter has the implicit upper bound Any?, so T may itself be nullable. Use T : Any to forbid null, or T & Any (a definitely non-nullable type) to say that null is removed from T inside a function.

Upper bounds

A bound restricts the type arguments and makes the members of the bound available on values of T. The default bound is Any?; a single bound is written with a colon, and several bounds need a where clause:

fun <T : Comparable<T>> larger(a: T, b: T): T = if (a >= b) a else b

fun <T> aboveThreshold(list: List<T>, threshold: T): List<String>
    where T : CharSequence, T : Comparable<T> =
    list.filter { it > threshold }.map { it.toString() }

fun main() {
    println(larger(3, 7))                                            // 7
    println(larger("pear", "apple"))                                 // pear
    println(aboveThreshold(listOf("a", "c", "e"), "b"))              // [c, e]
    // larger(Book("a", "b"), Book("c", "d"))   // does not compile: Book is not Comparable<Book>
}

Type Erasure and Its Consequences

On the JVM the type arguments of a generic class are not available at run time: List<Book> and List<String> are both java.util.List. The compiler checks the types statically and inserts casts, and the consequences are the same as in Java:

  • x is List<Book> is rejected, because the element type cannot be checked at run time; use x is List<*> and then check the elements, or use a reified parameter in an inline function.

  • x as List<Book> compiles with an unchecked cast warning, and a wrong list is detected only later, when an element is used and fails with ClassCastException far away from the cast.

  • You cannot call T() or T::class for an ordinary type parameter, and you cannot create an Array<T> of an unreified T.

The compiler does remember some information: it knows that val items: List<Item> = ... holds Item, and a function that returns T gets a checkcast inserted at its call site.

Declaration-Site Variance: in and out

Generic types are invariant by default: even though Book is a subtype of Item, a Box<Book> is not a Box<Item>. That protects mutable containers; if a MutableList<Book> could be used as a MutableList<Item>, one could add a Dvd to it and later read it back as a Book. But many types only ever produce values of T, or only ever consume them, and for those the restriction is needlessly strict. Kotlin lets the declaration say so:

  • out T — covariant: the class only returns T. A Producer<Book> can be used where a Producer<Item> is expected.

  • in T — contravariant: the class only accepts T. A Consumer<Item> can be used where a Consumer<Book> is expected.

flowchart TD subgraph Subtypes Book["Book"] -->|"is a subtype of"| Item["Item"] end subgraph Covariant PB["Source of Book"] -->|"is a subtype of"| PI["Source of Item"] end subgraph Contravariant CI["Sink of Item"] -->|"is a subtype of"| CB["Sink of Book"] end subgraph Invariant MB["MutableList of Book"] ---|"unrelated to"| MI["MutableList of Item"] end

The compiler enforces the declaration: an out parameter may appear only in output positions (return types, val properties), an in parameter only in input positions (function parameters):

interface Source<out T> {
    fun next(): T                      // T in output position: allowed
    // fun put(item: T)                // compile error: T is declared out but used in an input position
}

interface Sink<in T> {
    fun accept(item: T)                // T in input position: allowed
    // fun last(): T                   // compile error: T is declared in but used in an output position
}

class BookSource(private val books: List<Book>) : Source<Book> {
    private var index = 0
    override fun next(): Book = books[index++]
}

class PrintSink : Sink<Item> {
    override fun accept(item: Item) = println("received ${item.title}")
}

fun main() {
    val books = BookSource(listOf(Book("Dune", "Herbert"), Book("Emma", "Austen")))

    val itemSource: Source<Item> = books        // covariant: Source<Book> is a Source<Item>
    println(itemSource.next().title)

    val bookSink: Sink<Book> = PrintSink()      // contravariant: Sink<Item> is a Sink<Book>
    bookSink.accept(books.next())               // a sink of any Item happily accepts a Book
}

Output:

Dune
received Emma

Examples from the standard library: List<out E>, Iterator<out T>, Sequence<out T> and function results are covariant (so a List<Book> is a List<Item>); Comparable<in T> and function parameter types are contravariant; MutableList<E>, Array<T> and MutableMap<K, V> are invariant. A function type (A) -> R is therefore Function1<in A, out R>: it accepts anything more general than A and may return anything more specific than R.

When a covariant class legitimately needs T in an input position that cannot break type safety (an equals-like parameter, say), annotate the use @UnsafeVariance; the compiler then trusts you.

Variance on the JVM

The variance is erased as well. For a parameter of type Source<Item>, Kotlin generates the Java signature Source<? extends Item>; for Sink<Book> it generates Sink<? super Book>. Return types and final parameter types are not given wildcards, so Java callers of Kotlin code see predictable signatures.

Use-Site Variance and Star Projections

When a class cannot be declared out or in because it does both, a single function can still limit itself to one direction with a use-site projection. Array<out Item> means "an array I will only read items from", and MutableList<in Book> means "a list I will only add books to":

fun copyBooks(from: Array<out Book>, to: Array<in Book>) {
    for (i in from.indices) to[i] = from[i]       // reading from 'from' is safe; writing to 'to' is safe
}

fun main() {
    val books = arrayOf(Book("Dune", "Herbert"), Book("Emma", "Austen"))
    val items: Array<Item> = arrayOf(Item("x"), Item("y"))
    copyBooks(books, items)                       // Array<Item> accepted as Array<in Book>
    println(items.map { it.title })
}

Output:

[Dune, Emma]

A star projection * says "some type argument, I do not know or care which". For List<*> that is List<out Any?>: elements can be read as Any?. For MutableList<*> it is out Any? for reading and in Nothing for writing, so nothing can be added:

fun printAll(list: List<*>) {
    for (element in list) println(element)        // element has type Any?
}

fun describeSize(any: Any): String = when (any) {
    is List<*> -> "a list of ${any.size}"         // the only legal form of is-check on a generic type
    is Map<*, *> -> "a map of ${any.size}"
    else -> "something else"
}

fun main() {
    printAll(listOf(1, "two", null))
    println(describeSize(listOf(1, 2, 3)))
    println(describeSize(mapOf(1 to 2)))
}

Output:

1
two
null
a list of 3
a map of 1

Reified Type Parameters with inline Functions

Because of erasure, an ordinary generic function does not know its T at run time. An inline function is copied into each call site at compile time, so the compiler can substitute the actual type argument into the copy; marking the parameter reified exposes that knowledge: T::class, is T and as T all work.

inline fun <reified T : Item> List<Item>.firstOfType(): T? =
    firstOrNull { it is T } as T?                 // 'is T' is only legal because T is reified

inline fun <reified T> typeName(): String = T::class.simpleName ?: "anonymous"

fun main() {
    val library: List<Item> = listOf(Book("Dune", "Herbert"), Dvd("Alien", 117), Book("Emma", "Austen"))

    println(library.firstOfType<Dvd>()?.minutes)                    // 117
    println(library.firstOfType<Book>()?.author)                    // Herbert
    println(library.filterIsInstance<Book>().map { it.title })      // the standard library uses the same trick
    println(typeName<Dvd>())                                        // Dvd
}

Output:

117
Herbert
[Dune, Emma]
Dvd

Reified parameters are the reason APIs such as filterIsInstance<T>(), Gson().fromJson<T>() wrappers and Koin’s get<T>() can be written without passing a Class argument. The restrictions are that the function must be inline (so it cannot be called from Java and its body grows each call site) and that a reified type argument cannot itself be a non-reified type parameter of the caller.

Contrast with Java

  • Java’s use-site wildcards (List<? extends Item>, List<? super Book>) are written once per use; Kotlin’s out and in are written once per declaration, so every user of List<Item> gets covariance without writing anything. The mnemonic "producer extends, consumer super" of Java becomes producer out, consumer in in Kotlin.

  • Kotlin has no raw types: List without a type argument is an error, and List<*> is the correct spelling.

  • Kotlin Array<T> is invariant, unlike Java arrays, which are covariant and therefore unsafe at run time (ArrayStoreException).

  • Java cannot write new T[n] or T.class for a type parameter; Kotlin allows T::class for a reified T.

  • Kotlin has declaration-site type aliases (typealias Shelf = MutableList<Book>) for long generic types; an alias gives a new name, not a new type.
