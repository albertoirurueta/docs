Kotlin for Android

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Building on Kotlin and the JVM — which established that Kotlin is a general-purpose JVM language and Android is one target among several — this page covers what Android specifically adds on top of the Kotlin language itself: why Kotlin is the default there, the Kotlin features that matter most on Android and the mistakes they prevent, the KTX extension libraries, the Jetpack components that Kotlin code leans on, and how coroutines and flows are tied to Android lifecycles. The examples extend the lending library used in this section (Book, Member, Loan) into a screen that lists a member’s loans. Android UI toolkits, navigation and the build of an Android app are covered in the dedicated Android section; this page keeps to the language-level view.

Google’s Preferred Android Language Since 2019

At Google I/O 2019, Google announced that Android app development would be Kotlin-first: new Jetpack APIs are designed Kotlin-first (often exposing Kotlin-only ergonomics such as coroutine support or DSL-style builders), official samples and documentation default to Kotlin, and Java remains fully supported but is no longer the primary language new guidance is written against. This did not change anything about Kotlin/JVM itself — the .kt files in an Android app compile through the exact same Kotlin/JVM pipeline described in Kotlin and the JVM — it changed which platform-specific libraries and tooling exist to make Kotlin code on Android pleasant to write.

Language Features That Matter Most on Android

The Android framework is a large Java API with many nullable results, callbacks and verbose builders. Kotlin features map onto its pain points directly:

Kotlin feature What it fixes on Android

Null safety (Null Safety)

the framework’s NullPointerException sources: findViewById, Bundle values and Intent extras are nullable and must be handled; a crash on a user’s device is the cost of ignoring it.

Data classes (Data Classes and Destructuring)

UI models and database entities with equals() and copy(); the immutable copy style is what state-driven UI needs. With the kotlin-parcelize plugin, @Parcelize data class replaces hand-written Parcelable code.

Sealed classes (Sealed Classes and Enums)

UI state (Loading, Loaded, Error) with exhaustive when: a screen cannot forget to render a state.

Extension functions

KTX (below), and project-level helpers such as fun Context.toast(message: String).

Lambdas with receiver and trailing lambdas

builder-style APIs, edit { }, Jetpack Compose’s whole UI model.

Coroutines and Flow

main-thread safety without callbacks or AsyncTask (removed from the platform): see the last section.

Property delegation

val viewModel: LoansViewModel by viewModels() and by lazy for expensive initialisation.

Android runs Kotlin on the same JVM semantics as everywhere else, with these practical differences: the bytecode is converted to DEX by the build and shrunk by R8, reflection-heavy libraries need keep rules, and the kotlin-stdlib is linked into the app (R8 removes what is unused).

Android KTX

KTX is a family of Kotlin extension libraries (core-ktx, fragment-ktx, activity-ktx, and more) that add idiomatic Kotlin extension functions and properties (Extension Functions and Scope Functions) over verbose Android framework APIs:

// without KTX
val bundle = Bundle()
bundle.putString("name", "Ada")

val editor = sharedPreferences.edit()
editor.putBoolean("dark_mode", true)
editor.apply()

// with core-ktx
val bundle = bundleOf("name" to "Ada")            // Pair-based builder, see Data Classes and Destructuring
sharedPreferences.edit { putBoolean("dark_mode", true) }   // "edit { }" auto-applies when the block completes

// with fragment-ktx and activity-ktx: property delegates replace factory boilerplate
class LoansFragment : Fragment() {
    private val viewModel: LoansViewModel by viewModels()   // the ViewModel is created and scoped for you
}

KTX changes nothing about what the underlying Android APIs do — it is a thin, additive layer, so any Java Android knowledge (the Activity and Fragment lifecycle, Intents, Bundles) transfers directly. The extensions are ordinary functions in the sense of Extension Functions and Scope Functions: you can read their source and write your own in the same style.

Jetpack Pointers

Jetpack is Android’s official library suite; three components come up constantly in Kotlin Android code and are worth a one-paragraph orientation each (a full treatment of any one is out of scope for this Kotlin-language section):

  • ViewModel — survives configuration changes (like a screen rotation) and is the conventional home for UI state exposed as a StateFlow (Flows) that a screen observes.

  • Room — a SQLite persistence library with compile-time-verified queries; its DAOs are commonly declared as suspend funs or as functions returning Flow<T> directly, integrating persistence with coroutines with no manual thread-switching. It uses KSP to generate its code (see Build and Tooling).

  • Jetpack Compose — Android’s modern, Kotlin-only declarative UI toolkit (not covered here in depth — Compose is a large enough topic for its own dedicated reference; this section only notes that it exists and is built entirely around Kotlin language features, particularly lambdas with receiver (Type-Safe Builders and DSLs) and coroutines).

Together they form the usual unidirectional data flow: the UI sends events to the ViewModel, the ViewModel updates immutable state, and the UI renders that state.

sequenceDiagram participant UI as Fragment or Composable participant VM as ViewModel participant R as Repository and Room UI->>VM: onRefresh() event VM->>VM: viewModelScope.launch VM->>R: loansFor(member) suspend call R-->>VM: List of Loan VM->>VM: update the StateFlow with UiState.Loaded VM-->>UI: new state emitted UI->>UI: render(state) with an exhaustive when

The state side of that flow, using the library domain, is a sealed hierarchy and a ViewModel that exposes it:

data class Loan(val title: String, val dueDate: String)

sealed interface UiState {
    data object Loading : UiState
    data class Loaded(val loans: List<Loan>) : UiState
    data class Error(val message: String) : UiState
}

interface LoanRepository {
    suspend fun loansFor(member: String): List<Loan>
}

class LoansViewModel(private val repository: LoanRepository) : ViewModel() {
    private val _uiState = MutableStateFlow<UiState>(UiState.Loading)
    val uiState: StateFlow<UiState> = _uiState.asStateFlow()       // read-only view exposed publicly

    fun load(member: String) {
        viewModelScope.launch {                                     // see "Coroutines on Android" below
            _uiState.value = UiState.Loading
            _uiState.value = try {
                UiState.Loaded(repository.loansFor(member))
            } catch (e: CancellationException) {
                throw e                                             // never swallow cancellation
            } catch (e: Exception) {
                UiState.Error(e.message ?: "unknown error")
            }
        }
    }
}

Keep the mutable flow private and expose only the read-only StateFlow: that is the one place state changes, which makes the screen’s behaviour easy to follow and to test (see Testing for Dispatchers.setMain and runTest).

Coroutines on Android: viewModelScope and lifecycleScope

Coroutines Basics introduced CoroutineScope as the mechanism that ties a coroutine’s lifetime to something meaningful; on Android, two ready-made scopes are provided so an app rarely needs to build its own:

Scope Tied to

viewModelScope

a ViewModel instance — automatically cancelled when the ViewModel is cleared (the screen is finished for good, not just rotated).

lifecycleScope

a LifecycleOwner (an Activity or Fragment) — automatically cancelled when that component is destroyed.

Both scopes use Dispatchers.Main.immediate, so code in a launch starts on the main thread; blocking work must be moved off it with withContext(Dispatchers.IO) (Room and Retrofit suspend functions already do this themselves, so a suspend repository call is main-safe). Collecting a flow needs one more precaution: lifecycleScope is alive from creation to destruction, so a collector in onCreate keeps running while the screen is in the background. The repeatOnLifecycle function starts the collection when the lifecycle reaches a state and cancels it when it falls below:

class LoansFragment : Fragment() {
    private val viewModel: LoansViewModel by viewModels()

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        viewLifecycleOwner.lifecycleScope.launch {
            viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.uiState.collect { state ->     // collected only while the view is at least STARTED
                    render(state)
                }
            }
        }
    }

    private fun render(state: UiState) = when (state) {   // exhaustive: adding a state breaks the build here
        UiState.Loading -> showSpinner()
        is UiState.Loaded -> showLoans(state.loans)
        is UiState.Error -> showError(state.message)
    }
}

In Compose the equivalent is viewModel.uiState.collectAsStateWithLifecycle(), which turns the flow into Compose state and applies the same lifecycle-aware rule. A cold flow from Room can be converted into the ViewModel’s state with stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), UiState.Loading), which keeps the upstream query alive for five seconds after the last subscriber leaves, so a rotation does not restart it.

Using these scopes instead of a manually created CoroutineScope is what makes structured concurrency actually pay off on Android: a coroutine launched this way simply cannot outlive the screen that started it. Two cautions: work that must outlive the screen (an upload) belongs in WorkManager or an application-level scope, not in viewModelScope; and GlobalScope is as discouraged on Android as anywhere (see Coroutine Context, Cancellation and Exceptions).
