Equality and Operator Overloading

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Kotlin separates what two objects are (identity) from what they contain (equality) with two distinct operators, and it turns every operator symbol into a call to a named function that any type may provide. This page covers structural and referential equality, how to write equals() and hashCode() correctly (and when a data class does it for you), the special cases of floating-point numbers, this expressions, and the full set of overloadable operator conventions with the rules that keep overloading predictable. The examples use the lending library of this section (Book, Member, Loan).

Structural (==) vs. Referential (===) Equality

  • == calls equals() (with a null-safe check built in) — structural equality, comparing content. This is the Kotlin equivalent of what Java code has to remember to write as Objects.equals(a, b) or a.equals(b). a != b is the negation.

  • === compares referential equality — whether both sides are literally the same object instance. This is what Java’s == does for reference types. !== is the negation.

data class Book(val isbn: String, val title: String)       // a data class: generated equals()

fun main() {
    val a = Book("1", "Dune")
    val b = Book("1", "Dune")
    val c = a

    println(a == b)    // true: same content (structural), calls the generated equals()
    println(a === b)   // false: different instances
    println(a === c)   // true: the exact same instance

    val missing: Book? = null
    println(missing == null)         // true: == is null-safe, no NullPointerException
    println(missing == a)            // false
    println("Du" + "ne" == "Dune")   // true: String compares by content, unlike Java's ==
}

Output:

true
false
true
true
false
true

This split removes the single most common Java equality bug — accidentally comparing two boxed or String objects with == and getting a reference comparison instead of the intended content comparison. The compiler translates a == b to a?.equals(b) ?: (b === null), so the left side may be null, and === on values of primitive-backed types (Int, Long, …​) is not allowed or warns, because boxing makes the result meaningless.

The three-way relationship: == is for values, === for identity, and compareTo (through <, >) for order.

flowchart TD A["a == b"] --> B{"a is null?"} B -->|"yes"| C["result: b === null"] B -->|"no"| D["a.equals(b)"] D --> E{"equals overridden?"} E -->|"data class or explicit override"| F["compare the content"] E -->|"no"| G["Any.equals: same as ==="]

Writing equals() and hashCode()

A class that is not a data class inherits Any.equals(), which is identity. To give it value semantics, override both equals() and hashCode() and keep them consistent: objects that are equal must have equal hash codes, otherwise HashSet and HashMap misbehave. The contract for equals is reflexive, symmetric, transitive, consistent and returns false for null:

class Isbn(val value: String) {
    override fun equals(other: Any?): Boolean {
        if (this === other) return true            // fast path: the very same instance
        if (other !is Isbn) return false           // wrong type, or null: !is is true for null
        return value == other.value                // compare each significant property
    }

    override fun hashCode(): Int = value.hashCode()   // use the same properties as equals()

    override fun toString() = "Isbn($value)"
}

fun main() {
    val set = hashSetOf(Isbn("978-0132350884"))
    println(Isbn("978-0132350884") in set)         // true: equals and hashCode agree
    println(Isbn("978-0132350884") == Isbn("978-0132350884"))
    println(Isbn("1") == Isbn("2"))
}

Output:

true
true
false

Overriding only equals() is the classic bug: two equal objects land in different hash buckets and the set holds both. Two rules cover almost every case: use a data class when all the primary-constructor properties define identity (see Data Classes and Destructuring), and when you write the methods by hand, use the same set of properties in both. For inheritance, equality across a class hierarchy is hard to make symmetric; prefer a final class or composition.

Floating-point numbers and boxed values

== between statically known Double or Float values follows the IEEE 754 rules, while on values typed as Any or Comparable it uses equals(), which has a different, total ordering. The two results differ for NaN and signed zero:

fun main() {
    val nan = Double.NaN
    println(nan == nan)                  // false: IEEE says NaN is not equal to anything, including itself
    println(0.0 == -0.0)                 // true: IEEE says the two zeros are equal

    val boxedNan: Any = nan
    println(boxedNan == boxedNan)        // true: Double.equals treats NaN as equal to itself
    val zero: Any = 0.0
    val negativeZero: Any = -0.0
    println(zero == negativeZero)        // false: equals() distinguishes the two zeros
    println(listOf(nan) == listOf(nan))  // true: List equality uses equals() on elements
}

Output:

false
true
true
false
true

The practical consequence: do not use floating-point values as keys, and compare them with a tolerance (kotlin.math.abs(a - b) < 1e-9) rather than with ==.

this Expressions

this refers to the current receiver, exactly as in Java, with one addition: inside a class with several nested scopes (a lambda with receiver, an inner class, an extension function), a labeled this@Label disambiguates which enclosing receiver is meant:

class Outer {
    val name = "outer"

    inner class Inner {
        val name = "inner"

        fun show() {
            println(this.name)               // "inner": the Inner instance itself
            println(this@Outer.name)         // "outer": explicitly the enclosing Outer instance
        }
    }
}

fun main() {
    Outer().Inner().show()
}

Output:

inner
outer

The same label syntax works for lambdas with receiver (this@apply) and extension functions (this@isPalindrome).

Overloadable Operator Conventions

Every operator symbol in Kotlin — arithmetic, comparison, indexing, function-call syntax, iteration — is, under the hood, a call to a specifically named function that any type can provide by marking it operator. Providing that function is what makes the symbol usable on your own type:

The next example gives two library types operators: Money is a value with arithmetic and ordering, and Shelf is a collection-like object with indexing, membership, iteration, += and call syntax:

data class Money(val cents: Long) : Comparable<Money> {
    operator fun plus(other: Money) = Money(cents + other.cents)
    operator fun minus(other: Money) = Money(cents - other.cents)
    operator fun times(count: Int) = Money(cents * count)
    override fun compareTo(other: Money) = cents.compareTo(other.cents)
    override fun toString() = "${cents / 100}.${(cents % 100).toString().padStart(2, '0')}"
}

class Shelf {
    private val titles = mutableListOf<String>()

    operator fun plusAssign(title: String) { titles += title }          // shelf += "Dune"
    operator fun get(index: Int) = titles[index]                        // shelf[0]
    operator fun contains(title: String) = title in titles              // "Dune" in shelf
    operator fun iterator() = titles.iterator()                         // for (t in shelf)
    operator fun invoke() = titles.size                                 // shelf()
}

fun main() {
    val fee = Money(250) + Money(125)
    println(fee)                                  // 3.75
    println(fee * 2)                              // 7.50
    println(Money(100) < Money(200))              // true: the compareTo convention gives all four comparisons
    println(maxOf(Money(300), Money(150)))        // 3.00: Comparable is enough for the standard library functions

    val shelf = Shelf()
    shelf += "Dune"
    shelf += "Emma"
    println(shelf[0])                             // Dune
    println("Emma" in shelf)                      // true
    for (title in shelf) print("$title ")
    println()
    println(shelf())                              // 2
}

7.50
true
3.00

true

plus or plusAssign?

a += b is resolved in a fixed order, and the choice depends on whether a is a val or a var and on which functions exist:

flowchart TD A["a += b"] --> B{"plusAssign available?"} B -->|"yes"| C{"plus also available and a is var?"} C -->|"yes"| D["compile error: ambiguous"] C -->|"no"| E["a.plusAssign(b)"] B -->|"no"| F{"a is var and plus available?"} F -->|"yes"| G["a = a.plus(b)"] F -->|"no"| H["compile error"]

That is why val list = mutableListOf(1) allows list += 2 (it calls plusAssign, which adds in place), while var list = listOf(1) also allows list += 2 (it calls plus and reassigns the variable). A mutable collection held in a var makes += ambiguous, which the compiler reports.

Rules and style

  • Operators exist only for the fixed set above: Kotlin has no way to invent a new operator symbol, only to give an existing symbol meaning for a new type. Named infix functions cover the "new operator" need.

  • The function must be marked operator; the compiler checks the signature (for example compareTo returns Int, invoke is any signature).

  • Keep overloads unsurprising: + should be commutative-looking arithmetic or concatenation, [] should index, in should test membership. A + that mutates its receiver, or a * that sends an email, is a trap. plus returns a new value; plusAssign mutates.

  • Operators can be extension functions, so you can give existing types behaviour: operator fun String.times(n: Int) = repeat(n) makes "ab" * 3 work. Resolution rules for extensions apply (members win; static dispatch).

  • On the JVM an operator is an ordinary method; Java code calls plus, get and so on by name.
