Annotations and Reflection

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Annotations and reflection in Kotlin build directly on the JVM’s own annotation and reflection facilities, with a Kotlin-specific reflection API (kotlin.reflect) layered on top for Kotlin-only concepts (properties, nullability, data classes). Annotations attach metadata to declarations; reflection reads that metadata, and the declarations themselves, at run time. This page covers how an annotation is declared, which types its parameters may have, the meta-annotations that control where it can be used and how long it survives, use-site targets, the built-in and Java-interop annotations, the reflection API in kotlin.reflect and its relation to java.lang.Class, a worked example that reads a custom annotation, the cost of reflection and the alternative of compile-time processing. The examples use the lending library of this section (Book, Member, Loan).

The lifecycle of an annotation, and who can see it at each stage, is the key to choosing a retention:

flowchart LR S["Source code with annotations"] --> C["Compiler"] C --> B["Class files"] B --> R["Running JVM"] C --- SRC["SOURCE: seen by the compiler and processors, then dropped"] B --- BIN["BINARY: stored in the class file, invisible to reflection"] R --- RUN["RUNTIME: readable through reflection"]

Declaring an Annotation

An annotation class carries no body of its own — only constructor parameters, which become the annotation’s attributes. Allowed parameter types are the primitive types, String, KClass, enums, other annotations, and arrays of these; arbitrary objects are not allowed, because the value must be a compile-time constant:

annotation class Author(val name: String)

annotation class Review(
    val stars: Int = 3,                       // default values are allowed
    val tags: Array<String> = [],             // array parameter, written with square brackets in the annotation
)

@Author(name = "Ada Lovelace")
class Calculator

@Review(stars = 5, tags = ["classic", "must-read"])
class Library

Annotation arguments use named or positional syntax, as ordinary calls do. When the annotation has a single parameter that is an array, declare it vararg value so that callers can write @Tags("a", "b"). An annotation can itself be annotated, and can be applied to a declaration together with other annotations in any order. When an annotation takes no arguments, the parentheses are omitted: @Experimental, not @Experimental().

Meta-Annotations: @Target and @Retention

Two built-in meta-annotations control where a custom annotation may be applied and how long it survives:

@Target(AnnotationTarget.FUNCTION, AnnotationTarget.PROPERTY)
@Retention(AnnotationRetention.RUNTIME)
@MustBeDocumented
annotation class Experimental(val reason: String)

class Api {
    @Experimental("subject to change before 1.0")
    fun betaFeature() { /* ... */ }
}

@Target restricts which declarations (classes, functions, properties, constructor parameters, expressions, type usages) the annotation may decorate; the default when omitted is every declaration that makes sense for an annotation. @Retention mirrors Java’s RetentionPolicy — SOURCE (compiler and annotation processors only, never written to the class file), BINARY (kept in the .class file but invisible to reflection) or RUNTIME (readable via reflection, and the default in Kotlin; Java’s default is CLASS, which Kotlin calls BINARY). Two more meta-annotations are common: @Repeatable lets the annotation be written several times on one declaration, and @MustBeDocumented makes the annotation show up in the generated documentation of the elements it marks.

Use-Site Targets

A single Kotlin declaration can produce several JVM elements. The constructor property val title: String in a primary constructor generates a constructor parameter, a property, a backing field and a getter, so an annotation written in front of it is ambiguous. Kotlin picks the first applicable of param, property and field, and a use-site target prefix selects another one explicitly:

data class Member(
    @get:JvmName("identifier") val id: Int,       // renames the generated getter for Java callers
    @field:Transient val sessionToken: String = "",  // annotates the JVM field, not the Kotlin property
)

The available targets are file, property, field, get, set, receiver, param, setparam and delegate. Frameworks that read Java annotations from fields or getters, such as Jackson, JPA or Bean Validation, usually need @field: or @get: (for example @field:NotBlank), which is the most frequent reason for the prefix. Several annotations can share a target with the bracket form: @field:[Inject Named("lib")].

Using Built-In Annotations

Several annotations recur throughout ordinary Kotlin code:

@Deprecated("use borrowBook() instead", ReplaceWith("borrowBook(book)"))
fun borrow(book: String) { /* ... */ }

class Catalog {
    companion object {
        @JvmStatic                    // exposes the function as a real static method for Java callers
        fun empty(): Catalog = Catalog()
    }
}

@Suppress("UNCHECKED_CAST")
fun <T> unsafeCast(value: Any): T = value as T

@JvmOverloads                         // generates Java overloads for each default-argument combination
fun loan(book: String, days: Int = 14, renewable: Boolean = true) { /* ... */ }

@Throws(java.io.IOException::class)   // declares the checked exception in the class file for Java callers
fun loadCatalog(path: String): String = java.io.File(path).readText()

@Deprecated has a level (WARNING, ERROR, HIDDEN) and, with ReplaceWith, gives the IDE enough information to rewrite call sites automatically. @JvmStatic, @JvmOverloads, @JvmName, @JvmField and @Throws are a family of Java-interop annotations: because Kotlin has no static keyword, supports default arguments (see Functions) and has no checked exceptions, Java callers would otherwise not see a plain static method, an overload per default-argument combination or the exception a Java try block needs to catch. These annotations ask the compiler to generate that extra, Java-friendly surface. @JvmInline marks a value class, and @Volatile and @Synchronized map to the JVM keyword and monitor.

Opt-in markers are annotations too: a library annotates an API with a custom @RequiresOptIn annotation, and callers must acknowledge it with @OptIn(...) or by propagating the marker. This is how @ExperimentalCoroutinesApi and @ExperimentalStdlibApi work.

Basic kotlin.reflect

::class produces a KClass<T> — Kotlin’s own reflection handle, richer than Java’s Class<T> for Kotlin-specific constructs (nullable types, properties as first-class members, primary-constructor parameters). Many members of KClass (simpleName, qualifiedName, isInstance) work with the standard library alone. Most of the introspection API (members, memberProperties, declaredFunctions, primaryConstructor, findAnnotation) needs the kotlin-reflect artifact on the classpath; it is not part of the standard library to keep the standard library small. The functions live in kotlin.reflect.full.

import kotlin.reflect.full.memberProperties

data class Book(val isbn: String, val title: String, val year: Int)

fun main() {
    val kClass = Book::class                 // KClass<Book>
    println(kClass.simpleName)               // Book
    println(kClass.isData)                   // true (needs kotlin-reflect)

    val javaClass = Book::class.java         // the underlying java.lang.Class<Book>, for Java-facing APIs
    println(javaClass.name)                  // Book

    val book = Book("1", "Clean Code", 2008)
    println(book::class == Book::class)      // true: ::class on an instance gives its runtime class

    for (prop in Book::class.memberProperties.sortedBy { it.name }) {   // needs kotlin-reflect
        println("${prop.name} = ${prop.get(book)}")
    }
}

Output:

Book
true
Book
true
isbn = 1
title = Clean Code
year = 2008

::class.java is the bridge back to java.lang.Class whenever a Java API (a JSON library, a dependency injection framework) expects one — KClass itself is not a drop-in replacement for Class at every call site, and javaClass.kotlin converts the other way. The :: operator also creates callable references to functions and properties (Book::title, ::loan), which are KFunction and KProperty objects and usable as function values without needing kotlin-reflect.

Reading a Custom Annotation at Run Time

Putting the pieces together, the following example defines a @Label annotation with run-time retention and uses it to print a human-readable description of any object, the way a form generator or a serialiser would:

import kotlin.reflect.full.findAnnotation
import kotlin.reflect.full.memberProperties

@Target(AnnotationTarget.PROPERTY)
@Retention(AnnotationRetention.RUNTIME)
annotation class Label(val text: String)

data class Book(
    @Label("ISBN") val isbn: String,
    @Label("Title") val title: String,
    val year: Int,
)

fun describe(obj: Any): List<String> =
    obj::class.memberProperties
        .sortedBy { it.name }
        .map { prop ->
            val label = prop.findAnnotation<Label>()?.text ?: prop.name   // fall back to the property name
            "$label: ${prop.getter.call(obj)}"
        }

fun main() {
    describe(Book("978-0132350884", "Clean Code", 2008)).forEach(::println)
}

Output:

ISBN: 978-0132350884
Title: Clean Code
year: 2008

Because @Label is restricted to PROPERTY, an annotation written on a constructor property is attached to the property rather than to the constructor parameter, which is what findAnnotation on a KProperty looks for. Without the @Target restriction, the annotation would go to the param target first and the lookup would return null: a frequent trap, fixed by writing @property:Label("ISBN").

Costs and Alternatives

  • Reflection is slower than a direct call and is opaque to the compiler: renaming a property does not update a string that names it, and tools such as R8 or ProGuard on Android need keep rules for reflected classes.

  • Reflection with kotlin-reflect adds a sizeable library and parses the Kotlin metadata stored in each class, which is why it is slower on first use than plain Java reflection.

  • Compile-time processing avoids both costs. KSP (Kotlin Symbol Processing) and, for older libraries, kapt run during the build, read annotations with the retention SOURCE or higher, and generate ordinary Kotlin or Java code, which is how Room, Dagger, Hilt and Moshi codegen avoid runtime reflection. A compiler plugin such as kotlinx.serialization goes a step further and generates serialisers directly.

  • Prefer an explicit data structure over reflection where the set of types is small and known.
