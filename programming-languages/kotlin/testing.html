Testing

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Kotlin testing builds directly on the JVM testing ecosystem covered in Testing with JUnit 5 and Mockito — JUnit 5 runs Kotlin test classes with no changes needed — plus two Kotlin-specific additions: kotlin.test and MockK, and coroutine-aware test support. This page sets up a Gradle test build, shows kotlin.test and JUnit 5 assertions, the test-naming idiom Kotlin makes possible, mocking with MockK compared with writing a fake, and testing coroutines and flows with virtual time. The examples test the small lending library of this section (Book, Member, Loan).

Setting Up

A Gradle build needs the test dependency and the JUnit platform switch; the kotlin("test") artifact then selects the right adapter (JUnit 5 here) automatically:

// build.gradle.kts
plugins {
    kotlin("jvm") version "<kotlin version>"
}

dependencies {
    testImplementation(kotlin("test"))                                   // kotlin.test + the JUnit 5 adapter
    testImplementation("io.mockk:mockk:<version>")                       // MockK
    testImplementation("org.jetbrains.kotlinx:kotlinx-coroutines-test:<version>")
}

tasks.test {
    useJUnitPlatform()                                                   // run tests on JUnit 5
}

Test sources live in src/test/kotlin, mirroring the package structure of src/main/kotlin, and ./gradlew test runs them. The code under test throughout the page is this small class:

data class Book(val isbn: String, val title: String)

class Library(private val copies: MutableMap<String, Int>) {
    fun borrow(title: String): Int {
        val available = copies[title] ?: throw NoSuchElementException("unknown title $title")
        check(available > 0) { "no copies left of $title" }
        copies[title] = available - 1
        return available - 1
    }

    fun titles(): List<String> = copies.keys.sorted()
}

kotlin.test

kotlin.test is a thin, multiplatform-friendly facade over whichever underlying test framework is on the classpath (JUnit 4, JUnit 5, or a JS or Native test runner for a Kotlin Multiplatform project) — useful when test code itself needs to stay platform-agnostic, though a JVM-only project commonly just uses JUnit 5’s own org.junit.jupiter.api.Assertions directly instead. Its assertions are top-level functions, and assertFailsWith is generic and returns the exception so that it can be inspected:

import kotlin.test.Test
import kotlin.test.assertContentEquals
import kotlin.test.assertEquals
import kotlin.test.assertFailsWith
import kotlin.test.assertNull
import kotlin.test.assertTrue

class LibraryTest {
    private val library = Library(mutableMapOf("Dune" to 1, "Emma" to 0))

    @Test
    fun borrowReducesTheCopies() {
        assertEquals(0, library.borrow("Dune"))
    }

    @Test
    fun borrowingAnUnavailableTitleFails() {
        val error = assertFailsWith<IllegalStateException> { library.borrow("Emma") }
        assertEquals("no copies left of Emma", error.message)
    }

    @Test
    fun titlesAreSorted() {
        assertContentEquals(listOf("Dune", "Emma"), library.titles())
        assertTrue(library.titles().isNotEmpty())
        assertNull(library.titles().firstOrNull { it.startsWith("Z") })
    }
}

The assertions take (expected, actual) in that order, and a trailing message parameter is shown on failure. fail() and assertIs<T>() (which also smart-casts) round out the set.

JUnit 5 with Kotlin

Backtick-escaped test names (Lexical Structure and Style) are the single most visible Kotlin-specific idiom in test code — a descriptive sentence as the method name, with no separate @DisplayName needed. The JUnit 5 API also has Kotlin-friendly extensions, such as assertThrows<T> { } with a reified type, in org.junit.jupiter.api:

import org.junit.jupiter.api.Assertions.assertEquals
import org.junit.jupiter.api.BeforeEach
import org.junit.jupiter.api.Test
import org.junit.jupiter.api.assertThrows

class LibraryJUnitTest {
    private lateinit var library: Library

    @BeforeEach
    fun setUp() {
        library = Library(mutableMapOf("Dune" to 2, "Emma" to 0))      // a fresh fixture for each test
    }

    @Test
    fun `borrow reduces the copies by one`() {
        assertEquals(1, library.borrow("Dune"))
        assertEquals(0, library.borrow("Dune"))
    }

    @Test
    fun `borrowing a title with no copies left throws`() {
        val error = assertThrows<IllegalStateException> { library.borrow("Emma") }
        assertEquals("no copies left of Emma", error.message)
    }

    @Test
    fun `borrowing an unknown title throws`() {
        assertThrows<NoSuchElementException> { library.borrow("Walden") }
    }
}

@ParameterizedTest, @BeforeEach and @AfterEach, @Nested classes and every other JUnit 5 Jupiter feature from Testing with JUnit 5 and Mockito apply unchanged. Two Kotlin particulars: JUnit creates a new test class instance per test method by default, so a plain private val library = ... is already a fresh fixture (the lateinit + @BeforeEach form is needed only for setup that cannot be an initialiser), and @TestInstance(Lifecycle.PER_CLASS) lets @BeforeAll and @AfterAll be ordinary (non-static) methods, avoiding the companion object with @JvmStatic that Java’s static requirement would otherwise force.

Method names in backticks may contain spaces on the JVM, but not some characters (., ;, [, ], /, <, >, : are rejected by the JVM, and Android instrumented tests on older API levels reject spaces), so avoid punctuation in test names.

MockK

MockK is a mocking library built for Kotlin’s language features: suspend functions, object singletons, and top-level and extension functions, which Mockito — built for Java — handles only awkwardly or not at all. Final classes are no longer the reason to switch: since Mockito 5 the inline mock maker is the default, so Mockito mocks Kotlin’s final classes without the all-open plugin or any extra configuration:

import io.mockk.every
import io.mockk.mockk
import io.mockk.slot
import io.mockk.verify
import kotlin.test.Test
import kotlin.test.assertEquals

interface BookCatalog {
    fun find(isbn: String): Book?
}

interface Notifier {
    fun send(member: String, message: String)
}

class LoanService(private val catalog: BookCatalog, private val notifier: Notifier) {
    fun lend(isbn: String, member: String): Boolean {
        val book = catalog.find(isbn) ?: return false
        notifier.send(member, "You borrowed ${book.title}")
        return true
    }
}

class LoanServiceTest {
    @Test
    fun `lending a known book notifies the member`() {
        val catalog = mockk<BookCatalog>()
        val notifier = mockk<Notifier>(relaxed = true)               // relaxed: Unit functions need no stubbing
        every { catalog.find("1") } returns Book("1", "Dune")        // stub a return value

        val message = slot<String>()                                 // capture an argument
        val lent = LoanService(catalog, notifier).lend("1", "Ada")

        assertEquals(true, lent)
        verify(exactly = 1) { notifier.send("Ada", capture(message)) }
        assertEquals("You borrowed Dune", message.captured)
    }

    @Test
    fun `lending an unknown book sends nothing`() {
        val catalog = mockk<BookCatalog>()
        val notifier = mockk<Notifier>()
        every { catalog.find(any()) } returns null                   // any() matches every argument

        assertEquals(false, LoanService(catalog, notifier).lend("9", "Ada"))
        verify(exactly = 0) { notifier.send(any(), any()) }
    }
}

What makes MockK the natural choice for Kotlin is the rest of its API. It stubs and verifies a suspend function directly with coEvery { ... } returns ... and coVerify { ... }, where Mockito sees the hidden Continuation parameter of the compiled method and needs the mockito-kotlin helpers to hide it. It replaces the behaviour of a Kotlin object singleton in place with mockkObject, which Mockito cannot do because the singleton instance is created by the class itself. And it mocks top-level and extension functions with mockkStatic on the generated file class (for example mockkStatic("library.LoanRulesKt")), or on the function reference for an extension function. Like Mockito 5, it mocks final classes with no extra configuration. A fake is often simpler than either: a small hand-written implementation of the interface that keeps state.

Mock, stub or fake?

Test double What it is

Stub

returns canned answers (every { catalog.find("1") } returns ...); the test asserts on the outcome.

Mock

records calls and the test asserts on the interaction (verify { notifier.send(...) }).

Fake

a working but simplified implementation, such as an in-memory repository; the test asserts on the final state.

Prefer a fake for collaborators with behaviour (repositories) and a mock where the interaction itself is the requirement (a message must be sent). Over-mocking ties tests to the implementation: they break on refactoring even when the behaviour is unchanged.

kotlinx-coroutines-test for Testing Suspend Functions and Flows

Testing a suspend function or a Flow (Coroutines Basics, Flows) needs a coroutine to call it from, plus control over virtual time so a test with delay(5_000) inside it does not actually take five seconds to run. runTest provides both: it runs the test body in a TestScope whose scheduler skips delays, advancing a virtual clock to the next scheduled task whenever every coroutine is suspended:

import kotlinx.coroutines.delay
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.flow
import kotlinx.coroutines.flow.toList
import kotlinx.coroutines.launch
import kotlinx.coroutines.test.advanceTimeBy
import kotlinx.coroutines.test.currentTime
import kotlinx.coroutines.test.runTest
import kotlin.test.Test
import kotlin.test.assertEquals

suspend fun fetchBook(isbn: String): Book {
    delay(2_000)                                  // a slow network call in production
    return Book(isbn, "Dune")
}

fun readings(): Flow<Int> = flow {
    for (i in 1..3) {
        delay(1_000)
        emit(i)
    }
}

class CoroutineTests {
    @Test
    fun `fetchBook returns the expected book`() = runTest {
        val book = fetchBook("1")                 // runTest provides a TestScope to call suspend functions from
        assertEquals("Dune", book.title)
        assertEquals(2_000L, currentTime)          // virtual time: the 2 seconds passed instantly
    }

    @Test
    fun `a periodic refresh runs once a minute`() = runTest {
        var refreshes = 0
        backgroundScope.launch {                   // cancelled automatically when the test ends
            while (true) {
                delay(60_000)
                refreshes++
            }
        }
        advanceTimeBy(150_000)                     // moves virtual time forward without waiting
        assertEquals(2, refreshes)                 // the ticks at 60 s and 120 s have run
    }

    @Test
    fun `emits the expected values`() = runTest {
        val values = readings().toList()           // collecting a Flow into a List for straightforward assertions
        assertEquals(listOf(1, 2, 3), values)
        assertEquals(3_000L, currentTime)
    }
}

runTest is the direct, coroutine-aware replacement for runBlocking in test code — using plain runBlocking in a test with real delay() calls would make the suite slow for no benefit, since nothing about the delay itself is under test. All of the test suspend functions run on a StandardTestDispatcher, which queues coroutines until the test yields or calls advanceUntilIdle() and runCurrent(); UnconfinedTestDispatcher runs them eagerly instead.

Replacing Dispatchers.Main

Code that uses Dispatchers.Main (an Android ViewModel, for example) fails in a plain JVM unit test because there is no UI thread. Install a test dispatcher for the duration of the test:

import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.ExperimentalCoroutinesApi
import kotlinx.coroutines.test.StandardTestDispatcher
import kotlinx.coroutines.test.resetMain
import kotlinx.coroutines.test.setMain
import org.junit.jupiter.api.AfterEach
import org.junit.jupiter.api.BeforeEach

@OptIn(ExperimentalCoroutinesApi::class)
class MainDispatcherTest {
    @BeforeEach
    fun setUp() = Dispatchers.setMain(StandardTestDispatcher())

    @AfterEach
    fun tearDown() = Dispatchers.resetMain()           // always restore the real dispatcher
}

Also inject the dispatcher into the class under test (a constructor parameter with a default of Dispatchers.Default), so a test can pass its own: hard-coded dispatchers are the commonest reason a coroutine is hard to test.

What to Test, and Pitfalls

  • Test behaviour through the public API, one behaviour per test, with the Arrange-Act-Assert structure visible. Names such as borrowing a title with no copies left throws read as a specification.

  • Keep unit tests free of real time, network and disk: inject clocks (java.time.Clock), dispatchers and repositories.

  • In coroutine tests, never use Thread.sleep or real delay waits, and do not catch CancellationException.

  • A coroutine launched in a test that never finishes makes runTest hang until its timeout (60 seconds by default, reported as a failure): use backgroundScope for infinite loops, or cancel the job.

  • Run the build with ./gradlew test; the HTML report in build/reports/tests/test lists each test by its backtick name.
