Lambdas and Higher-Order Functions

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Functions are first-class values in Kotlin: they have types, can be stored in variables, passed as arguments and returned from other functions. A lambda is the compact literal for such a value, and a higher-order function is one that takes or returns a function. This page covers function types, lambda syntax, the trailing-lambda convention, closures and what the compiler does to make a captured var mutable, function references, SAM conversion and fun interface, returns from lambdas, and the three modifiers (inline, noinline, crossinline) that control how lambdas are compiled. The examples use the lending library of this section (Book, Member, Loan).

Lambda Syntax and Function Types

A lambda’s type is written (ParamTypes) -> ReturnType. Parameter types are usually inferred from context, so most lambdas at a call site carry no type annotations at all:

fun main() {
    val square: (Int) -> Int = { x -> x * x }
    val add = { a: Int, b: Int -> a + b }             // types come from the explicit parameter annotations

    println(square(5))       // 25
    println(add(2, 3))       // 5

    // a single-parameter lambda can refer to it as "it" instead of naming it
    val doubled = listOf(1, 2, 3).map { it * 2 }      // [2, 4, 6]
    println(doubled)

    // the last expression of a lambda is its result; Unit-returning lambdas simply end
    val greet: (String) -> Unit = { name -> println("Hello, $name") }
    greet("Ada")

    // a parameter that is not needed can be named _
    val pairs = mapOf("Dune" to 1965, "Emma" to 1815)
    pairs.forEach { (title, _) -> println(title) }
}

Output:

25
5
[2, 4, 6]
Hello, Ada
Dune
Emma

The function-type notation has a few more forms: () -> Unit takes nothing and returns nothing meaningful, (Int, Int) -> Int takes two parameters, ((Int) -> Int) -> Int takes a function, (() -> Unit)? is a nullable function type (call it with f?.invoke()), and Book.() -> String is a function type with receiver (see Type-Safe Builders and DSLs). A function value is an object implementing Function0, Function1, and so on, and calling f(x) is sugar for f.invoke(x).

An anonymous function is the alternative literal when the return type must be explicit or when return should return from the function itself: val isLong = fun(b: Book): Boolean { return b.pages > 400 }. Inside a lambda, a bare return is not allowed unless the lambda is inlined (see below), and return@label returns from the lambda.

Trailing-Lambda Convention

If a function’s last parameter is a lambda, it can be written outside the parentheses — and if it is the only argument, the parentheses can be omitted entirely. This is why higher-order library functions like map { }, filter { } and repeat(n) { } read like built-in control-flow syntax rather than ordinary function calls:

fun main() {
    println(listOf(1, 2, 3).map({ it * 2 }))     // legal but unidiomatic
    println(listOf(1, 2, 3).map { it * 2 })      // idiomatic: trailing lambda, no parentheses needed at all

    repeat(2) { i -> println("iteration $i") }   // repeat takes (times: Int, action: (Int) -> Unit)

    val total = listOf(1, 2, 3).fold(10) { acc, n -> acc + n }   // other arguments stay in parentheses
    println(total)                                                // 16
}

Output:

[2, 4, 6]
[2, 4, 6]
iteration 0
iteration 1
16

The consequence for API design: put the lambda parameter last, so that callers can use the trailing form. This is the convention the standard library follows everywhere, and the convention that type-safe builders exploit.

Closures

A lambda captures (closes over) variables from its enclosing scope, and — unlike Java’s lambdas, which can only capture effectively final variables — a Kotlin lambda can mutate a captured var:

fun makeCounter(): () -> Int {
    var count = 0
    return { count++ }        // captures and mutates "count" across calls
}

fun main() {
    val a = makeCounter()
    val b = makeCounter()                  // each call creates a separate captured variable
    println("${a()} ${a()} ${a()}")        // 0 1 2
    println(b())                           // 0
}

Output:

0 1 2
0

On the JVM a captured var cannot live on the stack frame that is about to disappear, so the compiler boxes it in a small kotlin.jvm.internal.Ref.IntRef object (one class per primitive kind, and ObjectRef for the rest), and both the function and the lambda read and write the field of that box. A lambda that captures nothing needs no new object per evaluation; one that captures values creates one per evaluation. Since Kotlin 2.0 lambdas are generated through invokedynamic by default, but the boxing of captured variables is unchanged. Captured variables that stay val are simply copied.

Closures are the basis of the usual functional patterns: a function that returns a configured function (a partial application), memoisation, callbacks that remember state, and function composition:

fun <A, B, C> compose(f: (A) -> B, g: (B) -> C): (A) -> C = { a -> g(f(a)) }

fun lateFee(ratePerDay: Double): (Int) -> Double = { days -> days * ratePerDay }   // returns a function

fun main() {
    val standard = lateFee(0.25)
    val titleLength = compose({ s: String -> s.trim() }, { s: String -> s.length })
    println(standard(8))                   // 2.0
    println(titleLength("  Dune  "))       // 4
}

Function References

::name creates a function value from an existing function or property, which is shorter than a lambda that only forwards its argument. A bound reference (instance::method) captures the receiver:

data class Book(val title: String, val pages: Int)

fun isLong(b: Book) = b.pages > 400

fun main() {
    val books = listOf(Book("Clean Code", 464), Book("Refactoring", 431), Book("Dune", 412), Book("Emma", 320))

    println(books.filter(::isLong).map(Book::title))            // top-level function and property references
    println(books.map(Book::pages).sum())

    val printer: (String) -> Unit = System.out::println                            // bound reference: receiver is System.out
    books.map(Book::title).forEach(printer)

    val create = ::Book                                          // constructor reference: (String, Int) -> Book
    println(create("Walden", 352))
}

Output:

[Clean Code, Refactoring, Dune]
1627
Clean Code
Refactoring
Dune
Emma
Book(title=Walden, pages=352)

Higher-Order Functions

A function that takes another function as a parameter, or returns one, is a higher-order function — the foundation that map, filter and every other functional collection operation (Collections and Sequences) are built on. Write your own when several call sites differ in one step of an otherwise identical algorithm:

fun <T, R> transform(value: T, operation: (T) -> R): R = operation(value)

fun <T> retry(times: Int, block: () -> T): T {
    var lastError: Exception? = null
    repeat(times) { attempt ->
        try {
            return block()                  // non-local return: only legal because repeat is inline
        } catch (e: Exception) {
            lastError = e
            println("attempt ${attempt + 1} failed: ${e.message}")
        }
    }
    throw IllegalStateException("gave up after $times attempts", lastError)
}

fun main() {
    println(transform(5) { it * it })       // 25: "operation" is the trailing lambda

    var calls = 0
    val value = retry(3) {
        calls++
        if (calls < 3) error("not yet") else "success on call $calls"
    }
    println(value)
}

Output:

25
attempt 1 failed: not yet
attempt 2 failed: not yet
success on call 3

SAM Conversion and fun interface

A Java interface with a single abstract method (a SAM interface, such as Runnable or Comparator) can be implemented with a lambda wherever it is expected. Kotlin interfaces get the same treatment when declared fun interface, which lets you name the concept and still call it with a lambda:

fun interface LoanPolicy {
    fun maxDays(genre: String): Int
}

fun renew(policy: LoanPolicy, genre: String) = policy.maxDays(genre) * 2

fun main() {
    val policy = LoanPolicy { genre -> if (genre == "reference") 0 else 14 }   // SAM constructor
    println(renew(policy, "fiction"))
    println(renew({ 7 }, "any"))                  // a lambda is accepted directly where a fun interface is expected
    Thread { println("running on a thread") }.also { it.start(); it.join() }   // Java's Runnable
}

Output:

28
14
running on a thread

A plain Kotlin interface with one method does not accept a lambda unless it is a fun interface — a design choice: function types for ordinary callbacks, fun interface when the callback deserves a name or Java callers will implement it.

inline, noinline, and crossinline

Ordinarily, passing a lambda allocates a function-object instance at run time (if it captures state), and calling it goes through an indirect call — overhead that matters in a hot loop. Marking a higher-order function inline tells the compiler to paste the function’s bytecode, and its lambda arguments' bodies, directly at each call site — eliminating both the allocation and the indirection entirely. This is also what lets return inside an inlined lambda perform a non-local return from the enclosing function (the behaviour seen in Control Flow's forEach example, which is itself inline):

inline fun <T> measureAndRun(label: String, block: () -> T): T {
    val result = block()
    println("$label done")
    return result
}

fun findFirstEven(numbers: List<Int>): Int? {
    measureAndRun("search") {
        for (n in numbers) {
            if (n % 2 == 0) return n     // non-local return: exits findFirstEven, not just the lambda;
        }                                // only legal because measureAndRun is "inline"
    }
    return null
}

fun main() {
    println(findFirstEven(listOf(1, 3, 6, 7)))   // 6, and "search done" is NOT printed: the return skipped it
    println(findFirstEven(listOf(1, 3)))         // search done, then null
}

Output:

6
search done
null

The effect of inline on the generated code is the difference between creating a function object and branching in place:

flowchart LR subgraph NonInline["Ordinary higher-order function"] C1["call site"] --> L1["allocate Function object for the lambda"] L1 --> F1["call run(block)"] F1 --> I1["block.invoke(): indirect call"] end subgraph Inline["inline function"] C2["call site"] --> P2["function body and lambda body pasted here"] P2 --> D2["no allocation, no indirect call"] end

Two refinements narrow what an inline function’s lambda parameters may do:

  • noinline — exempts one specific lambda parameter from being inlined (so it can be stored in a variable or passed to a non-inline function), when the rest of the function’s lambdas should still be inlined.

  • crossinline — still inlines the lambda’s code, but forbids a non-local return from inside it, needed when the lambda is itself invoked from another, non-inline context (for example inside a nested object expression or another lambda) where an early return would be ambiguous.

inline fun runTwice(first: () -> Unit, noinline second: () -> Unit, crossinline third: () -> Unit) {
    first()                                  // inlined: may use a non-local return
    val saved: () -> Unit = second           // allowed because 'second' is noinline: it is a real object
    saved()
    Thread { third() }.also { it.start(); it.join() }   // third() runs inside a Runnable, so it must be crossinline
}

When not to use inline: functions without lambda parameters gain nothing, a large body is duplicated at every call site and bloats the bytecode, and an inline function cannot call non-public API of its module unless annotated @PublishedApi. The standard library marks map, filter, let, run, repeat and use inline, and reified type parameters (see Generics and Variance) depend on it.
