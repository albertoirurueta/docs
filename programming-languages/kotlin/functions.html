Functions

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Functions are the basic unit of Kotlin code, and they are more flexible than Java methods: they can live at the top level of a file, be nested in other functions, take default and named arguments, return Unit or Nothing, and be rewritten by the compiler into loops. This page covers declaring functions and how return types are inferred, parameters (they are always read-only), default and named arguments including their JVM consequences, single-expression functions, vararg and the spread operator, local functions, and tailrec, with the generated JVM structure where it matters. The examples use the lending library of this section (Book, Member, Loan).

Function Declarations

A function is declared with fun, a name, a parameter list where every parameter has a type, and an optional return type. With a block body the return type must be written unless it is Unit; the compiler never infers it from return statements in a block:

fun add(a: Int, b: Int): Int {
    return a + b
}

fun greet(name: String) {           // no return type: implicitly Unit (see Basic Types and Variables)
    println("Hello, $name!")
}

fun fail(message: String): Nothing {  // never returns normally: always throws
    throw IllegalStateException(message)
}

fun main() {
    println(add(2, 3))
    greet("Ada")
    val title: String = readTitle() ?: fail("no title")   // type Nothing lets the Elvis branch type-check
    println(title)
}

fun readTitle(): String? = "Dune"

Output:

5
Hello, Ada!
Dune

Function parameters are always read-only: inside the function a = 5 does not compile, which removes a class of bugs where a parameter is reused as a scratch variable. Functions are top-level declarations when they sit in a file outside any class, so there is no need for static utility classes: a file Library.kt with fun add(...) is compiled to a class LibraryKt with a static method add, which Java calls as LibraryKt.add(2, 3). Put @file:JvmName("Library") at the top of the file to choose the class name. Member functions are declared inside classes (see Classes and Objects), and a trailing comma after the last parameter is allowed, which makes diffs smaller.

Default and Named Arguments

A parameter can declare a default value, letting callers omit it — eliminating most of the reason Java code resorts to overloaded methods:

data class Loan(val title: String, val member: String, val days: Int, val renewable: Boolean)

fun lend(title: String, member: String, days: Int = 14, renewable: Boolean = true) =
    Loan(title, member, days, renewable)

fun main() {
    println(lend("Dune", "Ada"))                                    // days = 14, renewable = true
    println(lend("Emma", "Grace", renewable = false))               // named argument skips days, order-independent
    println(lend(member = "Bo", title = "Walden", days = 7))        // named arguments may appear in any order
}

Output:

Loan(title=Dune, member=Ada, days=14, renewable=true)
Loan(title=Emma, member=Grace, days=14, renewable=false)
Loan(title=Walden, member=Bo, days=7, renewable=true)

Named arguments (renewable = false) can be combined with positional ones and are especially valuable at a call site with several Boolean or numeric parameters, where positional-only Java code is easy to misread (lend("Ada", "Dune", 7, false) — what does false mean, exactly?). Since Kotlin 1.4 a positional argument may follow named ones as long as all named arguments stay in their own positions.

Default values are expressions evaluated at each call, not once at declaration, and can refer to earlier parameters (fun log(msg: String, tag: String = msg.take(3))). An overriding function inherits the defaults of the function it overrides and may not redeclare them.

Defaults on the JVM

The JVM has no default arguments, so the compiler generates a synthetic bridge lend$default(...) that takes a bitmask of which parameters were omitted and fills in the defaults, and Kotlin call sites call that bridge. Java callers see only the full signature, which is a nuisance. @JvmOverloads asks the compiler to generate one overload per omitted trailing default parameter:

@JvmOverloads
fun lend(title: String, member: String, days: Int = 14, renewable: Boolean = true): Loan = Loan(title, member, days, renewable)

This yields lend(title, member), lend(title, member, days) and the full form for Java.

Single-Expression Functions

A function whose body is one expression can drop the braces and return, using = instead. The return type may then be inferred, but for public API it is good practice to write it so that a change of body cannot change the signature:

fun square(x: Int): Int = x * x
fun isEven(n: Int) = n % 2 == 0                    // return type inferred as Boolean

fun describe(pages: Int) = when {                  // when and if are expressions too
    pages < 100 -> "short"
    pages < 400 -> "medium"
    else -> "long"
}

fun main() {
    println(square(7))
    println(isEven(10))
    println(describe(250))
}

Output:

49
true
medium

This form is used throughout this section wherever a function body is a single expression — it is not a separate feature so much as the natural consequence of if and when already being expressions (Control Flow). A recursive single-expression function must declare its return type, because the compiler cannot infer a type from the function being defined.

vararg

A parameter marked vararg accepts zero or more arguments, collected as an Array inside the function — Kotlin’s equivalent of Java’s ...:

fun sum(vararg numbers: Int): Int = numbers.sum()

fun describeAll(prefix: String, vararg titles: String) = titles.joinToString(prefix = "$prefix: ")

fun main() {
    println(sum(1, 2, 3))        // 6
    println(sum())               // 0

    val values = intArrayOf(4, 5, 6)
    println(sum(*values))        // the "spread" operator (*) expands an array into vararg positions
    println(sum(1, *values, 7))  // spread can be mixed with individual values

    println(describeAll("books", "Dune", "Emma"))
    println(describeAll(prefix = "none"))          // zero vararg arguments
}

Output:

6
0
15
23
books: Dune, Emma
none:

Only one parameter may be vararg. When it is not last, the following parameters must be passed by name or the last parameter must be a lambda in trailing position. The spread operator copies the array (vararg receives a fresh array), so changes inside the function do not affect the caller’s. For a String vararg, the parameter’s type inside the function is Array<out String>; vararg of a primitive type gives IntArray, so sum(*values) needs an IntArray, not a List (convert with toIntArray()).

Local Functions

A function may be declared inside another function, nesting arbitrarily and closing over the enclosing function’s local variables — useful for a small helper that has no reason to be visible outside its caller, and for avoiding repeating the same validation arguments:

fun printFactorial(n: Int) {
    fun factorial(x: Int): Int =           // local function, only visible inside printFactorial
        if (x <= 1) 1 else x * factorial(x - 1)

    println("$n! = ${factorial(n)}")
}

fun saveLoan(title: String, member: String, days: Int) {
    fun require(condition: Boolean, field: String) {      // closes over title, member and days
        if (!condition) throw IllegalArgumentException("invalid $field for the loan of '$title' to $member")
    }
    require(title.isNotBlank(), "title")
    require(days in 1..60, "days")
    println("saved $title for $member, $days days")
}

fun main() {
    printFactorial(5)
    saveLoan("Dune", "Ada", 14)
    runCatching { saveLoan("Emma", "Grace", 90) }.onFailure { println(it.message) }
}

Output:

5! = 120
saved Dune for Ada, 14 days
invalid days for the loan of 'Emma' to Grace

Local functions can capture the enclosing variables, which the compiler implements by passing them as extra parameters or by a hidden object. Prefer a private top-level or member function when the helper has no need to capture, because it is easier to test and does not clutter the enclosing function.

tailrec

Marking a recursive function tailrec tells the compiler to rewrite a tail-recursive call (the recursive call is the very last operation performed) into an equivalent loop, avoiding both the call-stack growth and the StackOverflowError risk that plain recursion carries for large inputs:

tailrec fun factorial(n: Long, accumulator: Long = 1): Long =
    if (n <= 1) accumulator else factorial(n - 1, n * accumulator)

fun plainSum(n: Int): Long = if (n == 0) 0 else n + plainSum(n - 1)       // not tail: adds after the call

tailrec fun sumTo(n: Int, acc: Long = 0): Long = if (n == 0) acc else sumTo(n - 1, acc + n)

fun main() {
    println(factorial(20))                       // 2432902008176640000
    println(sumTo(1_000_000))                    // 500000500000: works, compiled as a loop
    // plainSum(1_000_000)                       // would overflow the stack
}

Output:

2432902008176640000
500000500000

The difference is what remains to be done after the recursive call returns:

flowchart LR subgraph Plain["plainSum: n + plainSum(n - 1)"] P1["plainSum(3)"] --> P2["plainSum(2)"] --> P3["plainSum(1)"] --> P4["plainSum(0)"] P4 --> R4["returns 0"] --> R3["adds 1"] --> R2["adds 2"] --> R1["adds 3"] end subgraph Tail["sumTo: the call is the last action"] T1["sumTo(3, 0)"] --> T2["sumTo(2, 3)"] --> T3["sumTo(1, 5)"] --> T4["sumTo(0, 6): returns 6"] end

In plainSum each frame waits to add its n after the callee returns, so the stack grows with the depth. In sumTo there is nothing left to do after the call, so the compiler reuses the same frame (a loop with updated parameters). The compiler verifies the function actually is in tail form and emits a warning (not silently ignoring the modifier) if it is not. Three limits apply: the recursive call must be the last operation, it cannot be inside a try/catch/finally block, and tailrec works only for direct self-recursion, not mutual recursion between functions, and not on open members.
