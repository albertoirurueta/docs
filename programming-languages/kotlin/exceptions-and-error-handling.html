Exceptions and Error Handling

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Kotlin’s exception mechanism is the JVM’s, minus the checked-exception rules and plus several ideas that make error handling expressions rather than statements: try returns a value, throw has the type Nothing, precondition functions (require, check) state contracts in one line, use closes resources, and Result represents an expected failure as an ordinary value. This page covers each of them, the exception hierarchy, the finally pitfalls, designing custom exceptions, the choice between exceptions, Result and sealed result types, and the interaction with Java. The examples use the lending library of this section (Book, Member, Loan).

The standard hierarchy, which is Java’s with Kotlin aliases for the common names:

classDiagram Throwable <|-- Error Throwable <|-- Exception Error <|-- OutOfMemoryError Error <|-- StackOverflowError Exception <|-- IOException Exception <|-- RuntimeException RuntimeException <|-- IllegalArgumentException RuntimeException <|-- IllegalStateException RuntimeException <|-- NoSuchElementException RuntimeException <|-- ArithmeticException IllegalArgumentException <|-- NumberFormatException Exception <|-- CancellationException note for Error "Not meant to be caught: the JVM is in trouble" note for CancellationException "Used by coroutines to signal cancellation, never swallow it"

try/catch/finally as an Expression

Like if and when (Control Flow), try can produce a value — the value of whichever branch (the try block or a matching catch) actually ran:

fun parseOrDefault(text: String): Int =
    try {
        text.toInt()
    } catch (e: NumberFormatException) {
        0
    } finally {
        println("attempted to parse \"$text\"")   // finally still runs; its value is never the expression's
    }

fun main() {
    println(parseOrDefault("42"))     // prints the finally message, then 42
    println(parseOrDefault("oops"))   // prints the finally message, then 0
}

Output:

attempted to parse "42"
42
attempted to parse "oops"
0

Multiple catch blocks work as in Java, matched top to bottom, so put the most specific type first. A catch can only catch Throwable subtypes, and there is no multi-catch syntax (catch (A | B e)): catch the common supertype, or use when (e) { is A, is B -> ... } inside one catch. Because try is an expression you can write val n = try { text.toInt() } catch (e: NumberFormatException) { null }, which gives an Int? and is the idiom the standard library packages as toIntOrNull().

A return inside finally overrides the value or exception from try, exactly as in Java, and silently swallows a pending exception, so avoid return, break and continue inside finally.

throw Is an Expression of Type Nothing

throw is an expression whose type is Nothing, the type with no values, which is a subtype of every type. That is why it can stand on the right of an Elvis operator or in a when branch while the surrounding expression keeps its type:

data class Book(val isbn: String, val title: String)

class Catalog(private val books: Map<String, Book>) {
    fun find(isbn: String): Book =
        books[isbn] ?: throw NoSuchElementException("no book with ISBN $isbn")   // type of the right side: Nothing
}

fun main() {
    val catalog = Catalog(mapOf("1" to Book("1", "Dune")))
    println(catalog.find("1").title)
    try {
        catalog.find("2")
    } catch (e: NoSuchElementException) {
        println("caught: ${e.message}")
    }
}

Output:

Dune
caught: no book with ISBN 2

The compiler uses Nothing for flow analysis: code after a call to a function returning Nothing is unreachable, and smart casts from x ?: return and x ?: error("...") work because the alternative never completes normally.

Preconditions: require, check, error

The standard library offers short functions for the commonest throwing patterns, with a clear convention about whose fault the failure is:

  • require(condition) { message } throws IllegalArgumentException: a caller passed a bad argument.

  • check(condition) { message } throws IllegalStateException: the object is in the wrong state for this call.

  • error(message) throws IllegalStateException unconditionally.

  • requireNotNull(x) { message } and checkNotNull(x) { message } throw the same two exceptions when x is null, and, through contracts, smart cast x to non-null afterwards.

  • TODO("reason") throws NotImplementedError, marking unfinished code.

class Loan(val title: String, private val maxRenewals: Int = 2) {
    var renewals = 0
        private set
    var closed = false
        private set

    fun renew() {
        check(!closed) { "cannot renew a closed loan" }
        check(renewals < maxRenewals) { "no renewals left for $title" }
        renewals++
    }

    fun close() { closed = true }
}

fun lend(title: String, days: Int): Loan {
    require(title.isNotBlank()) { "title must not be blank" }
    require(days in 1..60) { "days must be between 1 and 60 but was $days" }
    return Loan(title)
}

fun main() {
    val loan = lend("Dune", 14)
    loan.renew()
    loan.renew()
    for (action in listOf<() -> Unit>({ loan.renew() }, { lend("", 5) }, { lend("Dune", 90) })) {
        try {
            action()
        } catch (e: IllegalStateException) {
            println("state: ${e.message}")
        } catch (e: IllegalArgumentException) {
            println("argument: ${e.message}")
        }
    }
}

Output:

state: no renewals left for Dune
argument: title must not be blank
argument: days must be between 1 and 60 but was 90

The message argument is a lambda, evaluated only when the condition fails, so building the message costs nothing on the happy path. assert(condition) exists too, but it is disabled unless the JVM runs with -ea, so it must never be used for validation.

No Checked Exceptions

Kotlin has no checked-exception distinction at the language level — every exception behaves like Java’s unchecked (RuntimeException) ones: nothing forces a caller to declare throws or wrap a call in try/catch, even when calling Java code whose method signature does declare checked exceptions:

import java.io.File

fun loadTitles(path: String): List<String> =
    File(path).readLines()     // readLines may throw IOException; Kotlin does not force a try/catch or a throws clause

This was a deliberate design choice: JetBrains observed that Java’s checked exceptions, in practice, tend to be either genuinely handled (which still works fine in Kotlin) or immediately wrapped, rethrown or swallowed as boilerplate — so Kotlin drops the compiler enforcement and leaves the decision of what to catch entirely to the code’s own logic. The cost is that the signature no longer documents the failure modes: document them in KDoc with @throws. For Java callers of a Kotlin function, the @Throws(IOException::class) annotation writes the exception into the method signature, which a Java try/catch needs to compile (see Annotations and Reflection).

Custom Exceptions

Custom exceptions extend Exception (or a more specific existing type) exactly as in Java. Keep the message and the cause parameters so the stack trace chain is preserved, and add typed properties for data a handler needs:

class LoanLimitExceededException(
    val memberName: String,
    val limit: Int,
    cause: Throwable? = null,
) : Exception("$memberName reached the limit of $limit loans", cause)

fun borrow(memberName: String, current: Int, limit: Int = 3) {
    if (current >= limit) throw LoanLimitExceededException(memberName, limit)
    println("$memberName borrows book number ${current + 1}")
}

fun main() {
    borrow("Ada", 2)
    try {
        borrow("Ada", 3)
    } catch (e: LoanLimitExceededException) {
        println("${e.message} (limit ${e.limit})")
    }
}

Output:

Ada borrows book number 3
Ada reached the limit of 3 loans (limit 3)

To wrap a lower-level failure, pass it as cause: throw LoanLimitExceededException(name, 3, cause = e). A sealed hierarchy of exceptions (sealed class LibraryException : Exception()) lets callers write an exhaustive when (e) over the failures a module can produce.

Releasing Resources: use

Java’s try-with-resources is the extension function use on AutoCloseable (and Closeable). It closes the resource whether or not the block throws, and if closing also throws it attaches the secondary exception as suppressed:

import java.io.StringReader

fun main() {
    val firstLine = StringReader("Dune\nEmma").buffered().use { reader ->
        reader.readLine()          // the reader is closed when this block ends, normally or not
    }
    println(firstLine)             // Dune
}

The Result Type and runCatching

kotlin.Result<T> models a computation that either succeeded (holding a value) or failed (holding a Throwable), as an alternative to throw/catch for error paths that are an ordinary, expected part of a function’s contract rather than an exceptional condition. runCatching { } builds one from a block that may throw:

fun parseYear(text: String): Result<Int> = runCatching {
    val year = text.trim().toInt()      // throws NumberFormatException on bad input
    require(year in 1450..2100) { "implausible year $year" }
    year
}

fun main() {
    for (input in listOf("2008", "abc", "1200")) {
        parseYear(input)
            .onSuccess { println("ok: $it") }
            .onFailure { println("failed: ${it.javaClass.simpleName}: ${it.message}") }
    }

    val year: Int? = parseYear("x").getOrNull()                 // null on failure
    val safe: Int = parseYear("x").getOrDefault(0)              // fallback value
    val message = parseYear("1200").fold(
        onSuccess = { "year $it" },
        onFailure = { "invalid: ${it.message}" },
    )
    val recovered = parseYear("oops").recover { 1970 }.getOrThrow()
    println("$year $safe $message $recovered")
}

Output:

ok: 2008
failed: NumberFormatException: For input string: "abc"
failed: IllegalArgumentException: implausible year 1200
null 0 invalid: implausible year 1200 1970

Result is especially useful at API boundaries where a caller should be able to inspect success or failure without setting up a try/catch for every call — it composes with the rest of the functional collection and Sequence API (Collections and Sequences) more naturally than an exception can, since it is an ordinary value rather than a special control-flow event. map, mapCatching, recover, recoverCatching, fold and getOrElse transform and unwrap it.

Pitfalls of runCatching

  • runCatching catches every Throwable, including OutOfMemoryError and, inside a coroutine, CancellationException. Swallowing the latter breaks structured concurrency: rethrow it, or catch specific exception types with try. See Coroutine Context, Cancellation and Exceptions.

  • A Result that is never inspected hides the failure; unlike an exception it does not crash anything on its own.

  • Result is meant to be returned and consumed locally; avoid it as a generic type argument stored in collections without need, and prefer a domain-specific sealed type when the failure carries meaning.

A domain result type with a sealed class

When the failures are part of the domain, a sealed hierarchy is more precise than Result, because the compiler checks that when handles every case (see Sealed Classes and Enums):

sealed interface BorrowResult {
    data class Success(val dueDate: String) : BorrowResult
    data object NotAvailable : BorrowResult
    data class LimitReached(val limit: Int) : BorrowResult
}

fun describe(r: BorrowResult): String = when (r) {      // no else branch: the compiler checks exhaustiveness
    is BorrowResult.Success -> "due ${r.dueDate}"
    BorrowResult.NotAvailable -> "not available"
    is BorrowResult.LimitReached -> "limit of ${r.limit} reached"
}

fun main() {
    println(describe(BorrowResult.Success("2026-12-01")))
    println(describe(BorrowResult.LimitReached(3)))
}

Choosing a Strategy

  • Programming errors and violated contracts (a null that must not be null, an illegal argument): throw, with require/check.

  • Failures the immediate caller should handle as part of normal flow (parse, lookup, validation): return a nullable (toIntOrNull()), a sealed result or Result.

  • Failures of external systems (I/O, network): exceptions at the low level, translated into a domain result at the boundary of your module.

  • Never use exceptions for ordinary control flow: building a stack trace is expensive.
