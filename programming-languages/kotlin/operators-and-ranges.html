Operators and Ranges

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Kotlin’s arithmetic, comparison and logical operators read almost identically to Java’s, but underneath they are all calls to functions with fixed names, and that is the idea that explains the whole page. Ranges and infix notation are the two features with no direct Java equivalent. This page covers operator semantics (integer division, overflow, precedence, the bitwise functions), the .., ..<, downTo and step ranges and the progressions they build, membership tests with in, iteration cost, and how to write your own infix functions, using the lending library of this section (Book, Member, Loan) for the examples.

Operators Are Function Calls

val sum = 5 + 2            // +  -  *  /  %  (same precedence and associativity as Java)
val isEqual = 5 == 2       // structural equality (calls equals() for objects -- see the Equality page)
val isBigger = 5 > 2       // <  >  <=  >=  (call compareTo() for objects)
val both = true && false   // short-circuiting && and ||, plus ! for negation

Every arithmetic and comparison operator is, under the hood, a call to a named function (a + b is a.plus(b), a < b is a.compareTo(b) < 0, a..b is a.rangeTo(b)) that any type can implement — see Equality and Operator Overloading for the full overloadable set. For the primitive types the compiler does not emit a call: a + b on two Int values becomes the JVM iadd instruction, exactly as in Java.

Kotlin has no bitwise operator symbols (no &, |, ^, <<, >> tokens); the same operations are ordinary infix functions, covered below. && and || short-circuit as in Java. The infix functions and, or and xor also exist for Boolean, and they always evaluate both operands.

Arithmetic: Integer Division and Remainder

The type of an arithmetic expression is decided by its operands, never by the variable it is assigned to. Two Int operands give an Int result, so / is integer division and truncates toward zero, and % is the remainder, whose sign follows the dividend. When the mathematical behaviour is needed, floorDiv rounds toward negative infinity and mod returns a result with the sign of the divisor (both since Kotlin 1.5):

fun main() {
    println(7 / 2)              // Int / Int is integer division, truncated toward zero
    println(-7 / 2)
    println(7 % 2)
    println(-7 % 2)             // the remainder takes the sign of the dividend
    println((-7).mod(2))        // mod takes the sign of the divisor
    println((-7).floorDiv(2))   // rounds toward negative infinity
    println(7 / 2.0)            // one Double operand makes it floating-point division
    println(7.toDouble() / 2)
    println(1.0 / 0)            // floating-point division by zero is Infinity; 1 / 0 throws ArithmeticException
}

-3
1
-1
1
-4
3.5
3.5
Infinity

Two further rules follow from the operand types. Byte and Short arithmetic returns Int (val b: Byte = 1 makes b + b an Int), and there is no implicit widening between number types, so an Int result must be converted explicitly with toLong() or toDouble() before it is mixed with a Long or Double variable.

In the lending library, fees are kept in integer cents (never in Double, see Basic Types and Variables) and integer division counts whole weeks:

data class Book(val isbn: String, val title: String, val pages: Int)
data class Member(val name: String)
data class Loan(val book: Book, val member: Member, val days: Int)

const val LOAN_DAYS = 21
const val FEE_PER_WEEK_CENTS = 50

fun lateFeeCents(loan: Loan): Int {
    val daysLate = loan.days - LOAN_DAYS
    if (daysLate <= 0) return 0
    val weeksLate = (daysLate + 6) / 7          // integer division rounds down, so add 6 to round up
    return weeksLate * FEE_PER_WEEK_CENTS
}

fun main() {
    val dune = Book("978-0441172719", "Dune", 896)
    val ada = Member("Ada")
    println(lateFeeCents(Loan(dune, ada, 21)))
    println(lateFeeCents(Loan(dune, ada, 22)))
    println(lateFeeCents(Loan(dune, ada, 35)))
    val cents = lateFeeCents(Loan(dune, ada, 36))
    println("${cents / 100}.${(cents % 100).toString().padStart(2, '0')} EUR")
}

Output:

0
50
100
1.50 EUR

Overflow

Integer arithmetic on the JVM wraps around silently on overflow, and Kotlin keeps that behaviour: there is no checked arithmetic by default and no automatic promotion to a wider type. Widen before the operation, or use the Math.addExact family when an overflow must be an error:

fun main() {
    val max = Int.MAX_VALUE
    println(max + 1)                       // wraps around silently, as in Java
    println(max.toLong() + 1)              // widen first to get the real value
    println(Long.MAX_VALUE + 1)
    try {
        Math.addExact(max, 1)              // throws instead of wrapping
    } catch (e: ArithmeticException) {
        println("ArithmeticException: ${e.message}")
    }
}

Output:

-2147483648
2147483648
-9223372036854775808
ArithmeticException: integer overflow

The typical bug is val totalPages: Long = pages * copies with two Int operands: the multiplication overflows as an Int, and only the wrong result is widened. Write pages.toLong() * copies instead. The unsigned types (UInt, ULong) wrap around in the same way.

The infix-function level is the one to remember. It sits below arithmetic and ranges, so 1 shl 2 + 3 shifts by 5, and above comparison and equality, so a flag test needs no parentheses, the reverse of the Java trap where flags & MASK != 0 does not compile:

fun main() {
    println(2 + 3 * 4)              // multiplicative before additive
    println(1 shl 2 + 3)            // infix functions bind more loosely than +, so this is 1 shl 5
    println((1 shl 2) + 3)
    println(1..2 + 3)               // + before .., so this is 1..5
    val read = 1
    val write = 2
    val perms = read or write
    println(perms and write != 0)   // (perms and write) != 0: infix before equality
}

Output:

14
32
7
1..5
true

Bitwise Functions

The bitwise operations are infix functions on Int and Long (and on the unsigned types): and, or, xor, shl (shift left), shr (arithmetic shift right, which keeps the sign), ushr (logical shift right, which fills with zeros), plus the ordinary function inv() for the bitwise complement:

fun main() {
    val a = 0b1100
    val b = 0b1010
    println(a and b)
    println(a or b)
    println(a xor b)
    println(5.inv())                  // two's complement: -(5 + 1)
    println(1 shl 3)
    println(-16 shr 2)                // arithmetic shift keeps the sign
    println(-16 ushr 28)              // logical shift fills with zeros
    println((a and b).toString(2))    // binary representation
}

14

-6

-4

A member’s permissions in the lending library can be stored as a bit set, which shows the usual set, test and toggle idioms:

const val CAN_BORROW = 1        // 0b001
const val CAN_RESERVE = 2       // 0b010
const val CAN_RENEW = 4         // 0b100

fun describe(perms: Int): String = buildList {
    if (perms and CAN_BORROW != 0) add("borrow")
    if (perms and CAN_RESERVE != 0) add("reserve")
    if (perms and CAN_RENEW != 0) add("renew")
}.joinToString()

fun main() {
    val student = CAN_BORROW or CAN_RENEW            // set two flags
    println(student)
    println(describe(student))
    println(describe(student xor CAN_RENEW))         // toggle a flag off
}

Output:

5
borrow, renew
borrow

Bit sets are the right tool for wire formats, file formats and hashing. For ordinary flags in domain code, an enum with an EnumSet (or a Set of enum values) is clearer and just as compact; see Sealed Classes and Enums.

Ranges and Progressions

A range is a value, not loop syntax: a..b calls rangeTo and builds a closed range that includes both ends, and a..<b (stable since Kotlin 1.9) calls rangeUntil and builds an open-ended range that excludes b. The older infix function until builds the same range as ..<. For the integral types (Int, Long, Char and the unsigned types) a range is also a progression: an arithmetic sequence with a first element, a last element and a non-zero step. downTo builds a descending progression, and step derives a new progression with a different step from an existing one:

fun main() {
    println(1..5)                      // rangeTo: closed, includes 5
    println(1..<5)                     // rangeUntil: excludes 5
    println(1 until 5)                 // the older spelling of ..<
    println(5 downTo 1)                // a descending progression
    println(1..10 step 3)
    println((1..10 step 3).toList())
    println((1..10 step 4).last)       // last is the last value actually reached
    println((5..1).isEmpty())          // .. never counts down
    println(('a'..'e').joinToString(""))
    println(1.5 in 1.0..2.0)           // a Double range supports membership, not iteration
}

Output:

1..5
1..4
1..4
5 downTo 1 step 1
1..10 step 3
[1, 4, 7, 10]
9
true
abcde
true

Building a progression normalises its bounds. step must be positive (a zero or negative step throws IllegalArgumentException; the direction comes from .. or downTo), and the last property is the last element the progression actually reaches, not the bound that was written: 1..10 step 4 reaches 1, 5 and 9, so last is 9 and the 10 is never visited. 5..1 is an empty range rather than a descending one, which is why counting down needs downTo. reversed() turns a progression around ((1..5).reversed() is 5 downTo 1).

flowchart LR A["1..10"] -->|"rangeTo"| R["IntRange: first 1, last 10, step 1"] B["1..<10 or 1 until 10"] -->|"rangeUntil"| R2["IntRange: first 1, last 9, step 1"] C["10 downTo 1"] -->|"downTo"| D["IntProgression: first 10, last 1, step -1"] R -->|"step 4"| P["IntProgression.fromClosedRange(1, 10, 4)"] P --> L["last = last element reached: 10 - (10 - 1) mod 4 = 9"] L --> E["elements 1, 5, 9"] D -->|"step 3"| P2["IntProgression: first 10, last 1, step -3"] P2 --> E2["elements 10, 7, 4, 1"]

Ranges of other types exist wherever the type is Comparable. 1.0..2.0 is a ClosedFloatingPointRange<Double>, and any Comparable type gets .. from the generic rangeTo extension. Such ranges support in but cannot be iterated, because there is no "next" value of a Double or of an arbitrary type, and a for loop over one does not compile.

Membership with in

x in r calls r.contains(x) and x !in r calls !r.contains(x), so in works on anything with a contains operator: ranges, collections, strings, maps (by key) and your own types. Inside a when, in branches test ranges directly (see Control Flow):

data class Book(val isbn: String, val title: String, val pages: Int)

data class CallNumber(val value: Int) : Comparable<CallNumber> {
    override fun compareTo(other: CallNumber) = value.compareTo(other.value)
}

val loanPeriod = 1..28

fun sizeLabel(book: Book): String = when (book.pages) {
    in 0..<150 -> "short"
    in 150..<500 -> "medium"
    else -> "long"
}

fun main() {
    val shelf = listOf(
        Book("978-0441172719", "Dune", 896),
        Book("978-0141439587", "Emma", 474),
        Book("978-0451526342", "Animal Farm", 112),
    )
    println(21 in loanPeriod)                          // two comparisons: 1 <= 21 && 21 <= 28
    println(35 !in loanPeriod)
    println(shelf.map(::sizeLabel))
    println(shelf[0] in shelf)                         // List.contains, which uses equals()
    println("un" in "Dune")                            // CharSequence.contains

    val scienceAisle = CallNumber(500)..CallNumber(599)  // a ClosedRange<CallNumber>
    println(CallNumber(530) in scienceAisle)
    println(CallNumber(820) !in scienceAisle)
}

Output:

true
true
[long, medium, short]
true
true
true
true

The cost of in is the cost of the contains it calls. On a range it is two comparisons, whatever the size of the range. On a List it is a linear scan, and on a HashSet it is a hash lookup, so a membership test inside a loop over a large collection belongs on a Set. A stepped progression such as 1..100 step 2 is not a ClosedRange and has no constant-time contains: in on it falls back to Iterable.contains, which walks the elements.

Iteration Cost

A for loop over a range or progression expression (1..n, 0..<n, n downTo 0, 0..<n step 2, list.indices) is compiled to a counted loop over primitive int or long values, the same bytecode as Java’s for (int i = 0; i < n; i++): no range object is allocated, there is no Iterator, and nothing is boxed. A membership test against a range literal (x in 1..28) compiles to the two comparisons, again with no object.

The cost appears when the range is used as a general Iterable<Int>. Collection functions such as map, filter or sumOf iterate it through an Iterator<Int>, map and toList allocate a list of boxed Int values, and a range passed as an Iterable<Int> parameter loses the counted-loop translation. A range kept in a val is one small object created once, which is cheap; the issue is only the per-element work:

fun main() {
    val n = 1_000_000
    var total = 0L
    for (i in 0..<n) total += i                    // counted loop: no range object, no Iterator
    println(total)
    println((0..<n).sumOf { it.toLong() })         // same result through Iterable: an Iterator over the range
    println(999_999 in 0..<n)                      // two comparisons, whatever n is
}

Output:

499999500000
499999500000
true

For loops over large ranges in hot code, prefer the plain for loop or repeat(n); for everything else, choose the form that reads best, and measure with a benchmark harness such as JMH before rewriting one for speed.

Infix Notation

A function marked infix can be called without the dot and parentheses — a to b instead of a.to(b) — which is what makes downTo, step, until, and/or/xor/shl/shr (see above), and the Pair-building to ("key" to "value") all read as if they were built-in operators, even though they are ordinary library functions:

infix fun Int.timesRepeated(action: () -> Unit) {
    repeat(this) { action() }
}

fun main() {
    3 timesRepeated { println("hi") }   // reads like a sentence
}

An infix function must be a member or an extension function, take exactly one parameter, and that parameter can have neither a default value nor vararg. An infix call always needs an explicit receiver: inside a class, write this borrows book, not borrows book. This is purely a call-syntax convenience — it compiles to an ordinary method call with no runtime difference from a.timesRepeated { ... }.

In the lending library, two infix functions let the code that creates and extends loans read as a sentence. Infix calls are left-associative and, as the precedence table shows, bind more loosely than arithmetic:

data class Book(val title: String)
data class Member(val name: String)
data class Loan(val book: Book, val member: Member, val days: Int)

infix fun Member.borrows(book: Book): Loan = Loan(book, this, days = 21)
infix fun Loan.extendedBy(days: Int): Loan = copy(days = this.days + days)

fun main() {
    val ada = Member("Ada")
    val dune = Book("Dune")
    println(ada borrows dune)
    println(ada borrows dune extendedBy 7)          // left to right: (ada borrows dune) extendedBy 7
    println(ada borrows dune extendedBy 7 + 7)      // + binds tighter: extendedBy 14
    println(dune to ada)                            // to is the standard library infix that builds a Pair
}

Output:

Loan(book=Book(title=Dune), member=Member(name=Ada), days=21)
Loan(book=Book(title=Dune), member=Member(name=Ada), days=28)
Loan(book=Book(title=Dune), member=Member(name=Ada), days=35)
(Book(title=Dune), Member(name=Ada))

Use infix sparingly: it suits functions whose name reads as a verb or a preposition between two values (to, downTo, shouldBe in test libraries, a DSL), and it hurts readability for ordinary operations that a reader expects to see called with a dot. Mixing infix calls with arithmetic or ?: in one expression is a good reason to add parentheses even where they are not required. See Extension Functions and Scope Functions for what an extension function is.
