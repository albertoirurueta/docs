Reflection, Introspection and Tracing

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Ruby 4.0 (4.0.7, checked on 2026-10-18). Reflection is a program asking questions about itself: which class is this object, which methods does it answer to, where was this method defined, who called me, which objects are alive, which line of code is running, which warnings did the interpreter raise, and how was this source turned into instructions. Ruby answers all of them from inside the language, and that is why tools such as debuggers, test frameworks, linters, profilers and documentation generators can be written in Ruby itself.

The page goes from the cheap and portable to the expensive and CRuby-specific. The first half (objects, classes, Method objects, bindings and backtraces) is plain Ruby that works on every implementation and costs almost nothing. The second half (ObjectSpace, TracePoint, Warning, Coverage, RubyVM::InstructionSequence, RubyVM::AbstractSyntaxTree and Prism) looks at the running interpreter and its compiled form, is partly CRuby-only, and some of it is documented as experimental or unstable.

It builds on Classes and Objects, Modules and Mixins and Method Lookup and super (the ancestor chain that the reflection methods report), and it is the read-only companion of Dynamic Dispatch and Method Definition (send, define_method, method_missing) and Hooks, eval and DSLs (inherited, method_added, instance_eval, eval), which change a program instead of looking at it. Exceptions and Error Handling covers raise, backtrace and cause; this page covers the Thread::Backtrace::Location objects behind them. Object Lifecycle, Freezing and Copying and Garbage Collection and Memory go further on finalizers and the heap, and IRB and Debugging, Performance, Benchmarking and Profiling, Testing with Minitest and YJIT, ZJIT and the VM show the tools that are built on these interfaces. For how other languages expose the same ideas, see Java, Go, PHP and C#.

Every example was syntax-checked with ruby -wc, run with ruby -w on Ruby 4.0.7 and linted with RuboCop 1.92 using the configuration of the running shelf gem (double-quoted strings, NewCops: enable, Style/Documentation off, and Style/OneClassPerFile off because several small classes share one example file). The output shown is the real output; memory addresses and absolute paths are removed from it on purpose (the examples print File.basename), because they differ from run to run. The examples that need the gem are run with ruby -Ilib, so require "shelf" finds it (see the shelf gem source). The warnings example is run under plain ruby (it is also warning-free under -w) so that the default warning settings are visible. The few places where an example silences a cop on purpose carry a rubocop:disable-next comment and say why.

Asking an object about itself

An object answers three kinds of question: what is it (its class and identity), what does it hold (instance variables) and what can it do (methods). Every one of the methods below is defined on Object (most through Kernel), so it is available on nearly every value; BasicObject instances have none of them.

# frozen_string_literal: true

require "shelf"

def show(label, value) = puts("#{label.ljust(38)}#{value}")

isbn = Shelf::Isbn.new("978-0-306-40615-7")
author = Shelf::Author.new("Ursula K. Le Guin")
book = Shelf::Book.new(isbn:, title: "The Dispossessed", author:)
loan = Shelf::Loan.new(book, state: :lent)

loan.instance_variables lists the variables that have been assigned, in order of first assignment, and instance_variable_set creates one on the fly, as the @due line shows. This is why instance variables are not declared: an object has exactly the variables that some code has assigned to it, and reflection is the only way to see the list without reading the class. Since Ruby 3.0, reading a variable that was never assigned no longer warns (it just returns nil), so instance_variable_defined? is the way to tell "never set" from "set to `nil`".

Methods an object answers to

Call Returns

obj.methods

Public and protected methods the object responds to, from its singleton class up through the whole ancestor chain. Includes everything inherited from Object and Kernel, so it is long: subtract Object.instance_methods to see the interesting part.

obj.methods(false)

Only the singleton methods (the same as singleton_methods). The false does not mean "the class’s own methods".

obj.public_methods, obj.private_methods, obj.protected_methods

The methods of that visibility, again through the whole chain. Pass false to stop at the receiver’s own class: loan.public_methods(false) lists the methods of its singleton class and its class, but not those of modules the class includes or of Object.

obj.singleton_methods

The public and protected methods defined on the object itself, and (for a class or module) the ones it gained by extend. singleton_methods(false) leaves out the `extend`ed ones.

obj.respond_to?(name, include_all = false)

Whether a public method is available; pass true to include private and protected methods. It also consults respond_to_missing?, which methods does not.

obj.method(name), obj.public_method(name), obj.singleton_method(name)

A Method object (see Method objects) or a NameError.

respond_to? is the duck-typing question ("can I send you this message?"), and it is the one to ask in application code. The methods family answers the introspection question ("what is defined?"), and it deliberately does not see methods that exist only through method_missing: those need the respond_to_missing? hook to appear in respond_to? and method (see method_missing and respond_to_missing?).

Source: Object#methods, Object#public_methods, Object#singleton_methods and Object#respond_to?

Reading and writing state

instance_variable_get, instance_variable_set, instance_variable_defined? and remove_instance_variable take a Symbol or a String that must start with @; anything else raises NameError ("'state' is not allowed as an instance variable name"). They go around the class’s public interface, and the interface is the contract. Use them where bypassing is the point: serializers, test helpers, debuggers, Marshal, inspect and copying code. In application logic, an attr_reader or a method is almost always the better tool, because the reflective call breaks silently when the variable is renamed. A frozen object refuses instance_variable_set and remove_instance_variable with FrozenError; see Object Lifecycle, Freezing and Copying.

Ruby 4.0 adds a hook that makes Kernel#inspect print only some of the variables: if the object has a private method instance_variables_to_inspect returning an array of names, inspect shows just those. That is the supported way to keep secrets out of logs and p output without overriding inspect (see Classes and Objects).

Source: Object#instance_variables, Object#instance_variable_get and Object#instance_variable_set

Asking a class or module about itself

Classes and modules are objects too, so everything above works on them, and Module adds the questions that concern a definition: its place in the hierarchy, the methods and constants it defines, and its name.

The hierarchy

  • Module#ancestors is the method lookup chain, the same order super follows: the class, then the modules it prepends, includes or inherits, then the superclasses. It is the first thing to print when "the wrong method runs". For a class with a prepend, the prepended module appears before the class. The chain is explained in Method Lookup and super.

  • Class#superclass is the direct parent (nil for BasicObject); Module#included_modules and Module#include? ask about mixins. Both report the modules brought in by include and prepend, not those added by extend (those are on the singleton class).

  • Class#subclasses (Ruby 3.1) returns the direct subclasses, in no guaranteed order and without singleton classes. There is no descendants in Ruby 4.0, so the example above recurses; before 3.1 the standard idiom was ObjectSpace.each_object(Class).select { |c| c < klass }, which is slower and sees singleton classes (see Looking at the heap with ObjectSpace). The inherited hook in Hooks, eval and DSLs is the way to be told about subclasses as they are created, rather than asking later.

  • Class#attached_object (Ruby 3.2) goes the other way from singleton_class: given a singleton class, it returns the one object it belongs to, and raises TypeError for any other class. Module#singleton_class? tests the same thing without raising.

The methods a module defines

Call Returns

instance_methods(inherit = true)

Public and protected instance methods, including inherited ones. instance_methods(false) limits it to the module itself.

public_instance_methods, protected_instance_methods, private_instance_methods

The methods of one visibility; false again limits them to the module’s own definitions. initialize is a private instance method, which is why it is missing from instance_methods.

method_defined?(name, inherit = true), public_method_defined?, protected_method_defined?, private_method_defined?

A Boolean for one name. method_defined? is true for public and protected methods and false for private ones; the second argument (false) ignores ancestors.

undefined_instance_methods (Ruby 3.2)

The names removed with undef_method. They are not listed by instance_methods, yet they still block the lookup, so a call raises NoMethodError instead of reaching the parent.

instance_method(name), public_instance_method(name)

An UnboundMethod (see Method objects) or NameError. The public variant refuses private methods.

refinements (Ruby 3.2)

The Refinement modules created inside the module by refine; see Refinements and Monkey Patching.

Methods generated by attr_reader, Struct, Data and define_method are listed like any other. Methods that exist only through method_missing are not listed anywhere.

Constants, names and class variables

  • Module#constants lists the constants a module defines and, for a class, the inherited ones; constants(false) keeps just its own. const_get accepts a Symbol, a String, or a qualified "Store::Memory" String, and const_defined? answers without raising; both take an inherit flag, which is why Shelf.const_defined?(:String) is true (found through Object) and Shelf.const_defined?(:String, false) is false. const_get raises NameError ("uninitialized constant Shelf::Nope") for a missing name and ("wrong constant name lower") for a name that is not a constant. A missing constant first calls const_missing, the hook that autoloaders such as Zeitwerk build on (see Code Loading: require and autoload).

  • Module#const_source_location returns [file, line] for the place the constant was defined, which is how an editor jumps to a constant, and the answer for a class is where its first class keyword ran. It returns [] for constants defined in C and nil when the constant does not exist.

  • Module#name is the constant path the module was first assigned to, or nil for an anonymous one. Ruby 3.3’s set_temporary_name gives an anonymous class a readable label in error messages and inspect without making it a constant; the label must not look like a constant path ("fake<Draft>" is accepted, "Foo::Bar" and "" raise ArgumentError). Once the class is assigned to a constant it has a permanent name that replaces the temporary one, and set_temporary_name then raises RuntimeError ("can’t change permanent name").

  • Module#class_variables, class_variable_get and class_variable_defined? read @@x variables. Class variables are shared down the whole inheritance tree and are rarely the right design; see Variables, Constants and Scope.

Source: Module#instance_methods, Module#const_source_location, Module#set_temporary_name and Class#attached_object

Method objects

obj.method(:name) returns a Method, a method already bound to its receiver. Module#instance_method(:name) returns an UnboundMethod, the same method not yet bound to any receiver. Both are plain objects that describe a method and can be called; they are the reflective view of the definition, while Proc is the view of a block (see Blocks, Procs and Lambdas).

# frozen_string_literal: true

require "shelf"

def where(method)
  file, line = method.source_location
  file ? "#{File.basename(file)}:#{line}" : "(C code)"
end

puts describe.class
puts "owner          #{describe.owner}"
puts "name           #{describe.name}"
puts "arity          #{describe.arity}"
puts "parameters     #{describe.parameters}"
puts "location       #{where(describe)}"

puts "initialize     #{init.parameters}  arity #{init.arity}"

author = Shelf::Author.new("Ursula K. Le Guin")

puts "call           #{bound.call}"
puts "unbind + bind  #{bound.unbind.bind_call(Shelf::Loan.new(book, state: :returned))}"

What a Method can tell you

Call Answer

name, original_name

The name used to look it up, and the name it was defined with. They differ for an alias: alias aliased trace_it gives name :aliased and original_name :trace_it.

owner

The class or module in which the method is defined, which is not necessarily receiver.class. Shelf::Catalog.instance_method(:map).owner is Enumerable.

receiver (Method only)

The object the method is bound to.

source_location

[file, line] of the def (for a method generated by attr_reader or define_method, the line of that call or block), or nil for a method implemented in C, as Integer#+ and Enumerable#map are.

parameters

An array of [kind, name] pairs, with kinds :req, :opt, :rest, :keyreq, :key, :keyrest, :nokey and :block. Anonymous forwarding parameters appear as [:rest, :*], [:keyrest, :**] and [:block, :&]; the parameters of C methods and of attr_writer methods have no names ().

arity

The number of required arguments, or -n-1 when there are n required ones and some optional or rest ones. A group of required keywords counts as one more required argument (def m(a, k:) has arity 2), optional keywords alone make the arity negative (def m(a, k: 1) has arity -2). See Methods and Parameters.

super_method

The Method that super would call, or nil when the method is the last one in the chain.

unbind, UnboundMethod#bind(obj), UnboundMethod#bind_call(obj, *args)

Detach a method from its receiver and attach it to another object of the right class (a TypeError otherwise: "bind argument must be an instance of Shelf::Loan"). bind_call binds and calls in one step without allocating a Method.

to_proc, curry, >>, <<, ===

A lambda that calls the method, a curried lambda, composition, and Method#=== as call (so case x when obj.method(:valid?) works).

The inspect format shows the owner, the signature in terse form and the location: #<Method: Shelf::Loan#describe() loan.rb:17>, with (_) for a C method’s single required argument. Since Ruby 3.2 an UnboundMethod no longer shows the class it was fetched from, only the owner, and two UnboundMethod`s are `== when they are the same underlying method, so String.instance_method(:object_id) == Array.instance_method(:object_id) is true. The predicates Method#public?, private? and protected? that existed in 3.1 were removed again in 3.2; ask the class (public_method_defined?) instead.

Method#source_location and Module#const_source_location are what editors and IRB’s show_source and edit commands use to find the right file (see IRB and Debugging). Method#owner is what to ask first when a method behaves unexpectedly: the owner tells you whether it came from your class, a mixin or core.

Procs and blocks

A Proc answers the same questions: parameters, arity, source_location, lambda? and binding. proc { |a, (b, c), *d, e: 1| }.parameters is : a plain proc reports its parameters as optional, because a proc tolerates missing and extra arguments, and a destructured parameter is unnamed. Proc#parameters(lambda: true) (Ruby 3.2) reports them as a lambda would (:req). Proc#binding returns the Binding the block closes over (see Local variables, bindings and backtraces).

method_missing and respond_to_missing?

A method that exists only because method_missing answers for it is invisible to every query on this page. The rule that keeps reflection honest is to define respond_to_missing? with the same condition: Ruby then reports the name from respond_to? and, more importantly, builds a Method object for it, so obj.method(:find_by_title) works, map(&obj.method(:find_by_title)) works, and Object#public_send and Enumerable#map(&:sym) behave as callers expect. methods still does not list the name, because nothing is defined. RuboCop’s Style/MissingRespondToMissing enforces the pair; the example below disables it on one class on purpose to show what the omission costs.

# frozen_string_literal: true

Book = Struct.new(:title)

# A catalogue front-end that answers find_by_<field> calls dynamically.
class Finder
  def initialize(books) = @books = books

  def method_missing(name, *args)
    return super unless name.start_with?("find_by_")

    field = name.to_s.delete_prefix("find_by_")

  end

  def respond_to_missing?(name, include_private = false) = name.start_with?("find_by_") || super
end

The file as the interpreter was given it, and its absolute form (nil for -e and eval without a file).

The line of the call inside that frame.

The frame’s name. Since Ruby 3.4 it carries the owner: Reporter#trace_it, Shelf::Isbn.new, block in Reporter#report, <main>.

The bare method name without the owner or the block in prefix: trace_it.

Walking and counting objects

  • ObjectSpace.each_object([module]) { |obj| ... } calls the block for every living, non-immediate object (optionally only instances of module, which can be a class or a module) and returns how many it found; without a block it returns an Enumerator. Immediate values (small integers, nil, true, static Symbols and flonums) are not objects on the heap and are never yielded. The result depends on garbage that has not been collected yet, so counts can be higher than expected; call GC.start first when a test needs an exact number. each_object(Class) also yields every singleton class (dozens, even in a bare process), so filter with singleton_class? or by name. The documentation warns that once the first Ractor.new has run, each_object stops yielding objects that are not shareable.

  • ObjectSpace.count_objects returns a Hash of counts by internal type (:TOTAL, :FREE, :T_OBJECT, :T_STRING, :T_ARRAY, :T_HASH, …​). The example compares two snapshots to confirm that a thousand objects were allocated. It is a cheap, coarse tool for leak hunting: take a snapshot, run the suspect code in a loop, take another and compare the types that grew. It accepts a Hash to fill, so a measurement can avoid allocating a new one.

  • ObjectSpace.garbage_collect is GC.start; see Garbage Collection and Memory.

  • Use ObjectSpace.each_object to find live instances for debugging, never for application logic such as a registry. A registry is a Hash filled by initialize or by the inherited hook, and it behaves the same on every run.

Weak references and finalizers

ObjectSpace::WeakMap holds both keys and values weakly and compares keys by identity. ObjectSpace::WeakKeyMap (Ruby 3.3) holds only its keys weakly, keeps values strongly, compares keys by value with eql?, and offers getkey to fetch the stored key object, which makes it the right structure for an interning cache keyed by a string. WeakMap#delete was added in 3.3. Both let an entry disappear once nothing else refers to the key, so the size is only meaningful right after you have looked at it, and their entries are not stable across a garbage collection.

ObjectSpace.define_finalizer(obj, callable) and undefine_finalizer register code to run after an object has been collected. The callable must not hold a reference to the object, or it will never be collected, and finalizers run late and in unspecified order; the rules are in Object Lifecycle, Freezing and Copying.

_id2ref is deprecated

ObjectSpace._id2ref(id) turns an object_id back into the object. Ruby 4.0 deprecates it (Feature #15408): it prints warning: ObjectSpace._id2ref is deprecated when deprecation warnings are on (-W:deprecated or -w; the example turns the category on and routes the message to puts so you can see its category). An id says nothing about whether its object is still alive, so the lookup could always fail or find a different object. Hold the object itself, or keep a WeakMap when you need a cache that does not keep objects alive.

Tracing with TracePoint

TracePoint is the object-oriented interface to the interpreter’s event hooks. You describe the events you want, give a block, and Ruby calls the block each time one of them happens, with a TracePoint argument that describes the event. It replaces the old Kernel#set_trace_func, whose callback received six positional arguments and which is only kept for compatibility; new code should not use it. Debuggers (the debug gem), coverage tools, profilers, loggers that print "who called what" and test frameworks that detect unexpected calls are built on it.

Two rules protect the interpreter from confusing itself. The TracePoint argument is only valid inside the block, and touching it later raises RuntimeError ("access from outside"); copy the values you need instead of keeping the object. And TracePoints are active per Ractor: enabling one in the main Ractor does not trace code that runs in another.

Turning it on and off, and limiting its scope

enable and disable return the previous state, so enable returns false the first time and true the second. enable { ... } activates the hook for the duration of a block, and disable { ... } suspends it for a block while it is on. TracePoint.trace(*events) { ... } creates and enables in one step. enabled? tells you which state it is in, and inspect prints #<TracePoint:disabled> or #<TracePoint:enabled>, and inside the hook the event, the method and the location.

  • target: restricts the hook to one method, UnboundMethod, Proc or other code object for which RubyVM::InstructionSequence.of returns an instruction sequence. The example traces only Catalog#add even though Catalog#each is also called. With target_line: it narrows further to one line, but only together with the :line event (otherwise ArgumentError: "target_line is specified, but line event is not specified"). Targeted tracing is the cheap form, because the interpreter instruments just that code.

  • target_thread: limits the hook to one thread. Since Ruby 3.2, enable with a block and without target, target_line or target_thread defaults to the current thread, which is why the first thread_begin hook sees nothing: the event is fired in the new thread. Pass target_thread: nil to listen on every thread.

  • While a hook runs, other TracePoint hooks are not called, so a hook that calls traced methods does not recurse (the catalog.add inside the hook is invisible to it). TracePoint.allow_reentry { ... } (Ruby 3.1) lifts that restriction inside its block; it raises RuntimeError if reentrance is already allowed, and the hook must make sure it does not trigger itself endlessly.

  • TracePoint.new needs a block (ArgumentError: "must be called with a block") and known events (ArgumentError: "unknown event: nope").

What tracing costs

Every enabled event adds work to the interpreter, and :line, :call and :c_call happen constantly. Tracing a tiny method in a loop is several times slower than running it untraced on the same machine, and enabling a TracePoint can force the VM to throw away optimized code: Ruby 4.0 adds an invalidate_everything counter to the default YJIT statistics that counts the times all compiled code was invalidated because of a TracePoint (and it fixed a bug where TracePoints stopped working after a garbage collection). Practical rules:

  • Enable a hook for the narrowest scope: a block, a target, a thread, and only the events you need.

  • Filter inside the block as the first statement (next unless ...), because the block is called for every event of the chosen kinds, including those from gems and from the standard library.

  • Never leave a tracer enabled in production unless that is its purpose. Use it in tests, development and diagnostics; for steady-state observation, prefer sampling profilers (see Performance, Benchmarking and Profiling).

  • A tracer that reads tp.binding or tp.parameters on every event is the most expensive kind; ask for them only when you report.

A reusable call tracer

The class below is the useful core of most "print every call" tools: it wraps a TracePoint, keeps only one namespace, indents by call depth and summarizes return values by type so that logs do not contain object addresses.

# frozen_string_literal: true

require "shelf"

# Records an indented call tree for the methods of one namespace.
class CallTracer
  def initialize(namespace) = @namespace = namespace

  def trace(&)
    lines = []
    depth = 0
    hook = TracePoint.new(:call, :return) do |point|
      next unless point.defined_class.to_s.start_with?(@namespace)

      depth -= 1 if point.event == :return
      lines << "#{'  ' * depth}#{describe(point)}"
      depth += 1 if point.event == :call
    end
    hook.enable(&)
    lines
  end

  private

  def describe(point)
    name = "#{point.defined_class.to_s.delete_prefix('Shelf::')}##{point.method_id}"
    point.event == :call ? "-> #{name}" : "<- #{name} = #{summary(point.return_value)}"
  end

  def summary(value)
    case value
    in String | Symbol | Integer | nil | true | false then value.inspect
    else value.class.to_s.delete_prefix("Shelf::")
    end
  end
end

Warnings

Ruby’s warnings are an introspection channel too: the interpreter reports questionable code and deprecated features through one hook, Warning.warn, and a program can switch categories on and off, filter them and capture them. This is how test suites turn warnings into failures and how libraries announce their own deprecations.

Verbosity and categories

Two independent settings decide what is printed.

  • $VERBOSE has three states. false (the default, -W1) prints the important warnings. true (-w or -W2) prints every warning, including style and unused-code diagnostics (assigned but unused variable, method redefined). nil (-W0) prints none: Kernel#warn does nothing at all.

  • Warning categories are Boolean switches for groups of warnings. Warning.categories (Ruby 3.4) lists them: :deprecated, :experimental, :performance and :strict_unused_block.

Category Covers Default

:deprecated

Features slated for removal: mutating a chilled string literal (Ruby 3.4), ObjectSpace._id2ref (4.0), the old behaviour of keyword arguments, the definition of the top-level constant ::Ruby (3.4).

off; -w and -W:deprecated turn it on

:experimental

Features still marked experimental, such as the Ractor API in 4.0.

on; -W:no-experimental turns it off

:performance (Ruby 3.3)

Hints about slow patterns, such as redefining a core method the interpreter and JIT optimize (String#freeze, Integer#+; Ruby 3.4).

off; -W:performance turns it on

:strict_unused_block (Ruby 3.4)

A block passed to a method that never uses it (the block passed to 'Object#m' defined at ... may be ignored).

off; -W:strict_unused_block turns it on. Under -w the same unused-block warning is shown for every such method.

 
$ ruby -W:deprecated script.rb      # one category on
$ ruby -W:no-experimental script.rb # one category off
$ ruby -w script.rb                 # verbose: $VERBOSE = true, deprecated on
$ ruby -W0 script.rb                # silent: $VERBOSE = nil
$ RUBYOPT="-W:deprecated" ruby script.rb

Source: Command-line options

The same switches exist in code: Warning[:deprecated] = true and Warning[:experimental] read and write a category, and an unknown name raises ArgumentError ("unknown category: nope"). RUBYOPT applies the options to every Ruby process started from that shell, which is how CI jobs raise the level of the whole test run without editing scripts.

Emitting, capturing and filtering

  • Kernel#warn(*messages, uplevel: nil, category: nil) writes to $stderr through Warning.warn. uplevel: n prefixes the message with the file and line of the caller n frames up and the word warning: (the standard form for deprecation messages, so users see their line, not yours). category: (Ruby 3.0) names the category, and the message is dropped if that category is off, which is how a library emits a deprecation that stays quiet by default.

  • Warning.warn(message, category: nil) is the single method every warning passes through, from the interpreter and from Kernel#warn. Overriding it redirects, filters or collects warnings. The documentation recommends extending Warning with a module that calls super for the default behaviour, and says never to redefine the instance method Warning#warn. A hook should accept **kwargs to survive additions to the signature.

  • Ruby only calls Warning.warn for categories that are switched on, so a capture hook sees exactly what would have been printed.

# frozen_string_literal: true

# Capture every warning instead of printing it (useful in tests).
module WarningCapture
  Entry = Data.define(:category, :message)

  def self.entries = @entries ||= []

  def warn(message, category: nil)
    WarningCapture.entries << Entry.new(category:, message: message.chomp)
    nil
  end
end
Warning.extend(WarningCapture)

def report(label)
  before = WarningCapture.entries.size
  yield
  fresh = WarningCapture.entries.drop(before)
  puts "#{label.ljust(26)} #{fresh.empty? ? 'nothing' : fresh.map { [it.category, it.message] }}"
end

Code coverage

Coverage (in the standard library, require "coverage") counts how often each line, branch and method of the files loaded while it is running was executed. It is the engine under test-coverage tools such as the community SimpleCov gem (https://github.com/simplecov-ruby/simplecov); the documentation labels the module experimental, and it measures the whole process, not one thread.

The one rule that surprises everyone: start Coverage before the code to measure is loaded. A file that was already loaded when Coverage.start ran is not instrumented, and a file reloaded with load after the start is measured from then on.

Instruction sequences, syntax trees and Prism

Between the text of a program and its execution, CRuby parses the source into a syntax tree and compiles the tree into YARV instructions (see YJIT, ZJIT and the VM). Three APIs expose those stages, and they differ greatly in how far you can rely on them.

API Stage Stability

RubyVM::InstructionSequence

Compiled YARV bytecode

CRuby only. The documentation states that the behaviour of its methods can change in any version and that the instruction output will almost certainly change as Ruby changes.

RubyVM::AbstractSyntaxTree

Syntax tree from the legacy parse.y parser

CRuby only and documented as experimental: the order and number of child nodes are not guaranteed. It points to Prism as the stable choice.

Prism (require "prism")

Syntax tree from the parser CRuby itself uses (default since Ruby 3.4)

The official, versioned API. A default gem since Ruby 3.3, portable across Ruby implementations, with a documented node set.

Ripper (require "ripper")

Event-based lexer and parser API

Older and still shipped. Prism provides a Ripper-compatible Prism::Translation::Ripper and translation layers for the parser and ruby_parser gems.

The whole RubyVM module exists only on MRI (the reference implementation), and the documentation says normal users must not use it. Use these APIs to learn, to debug and to build tools that you control the Ruby version of, not in application code.

The tree of the three-line price method shows the quirks that make the API unsuitable as a tool foundation: days * 2 + 1 is an OPCALL of + whose receiver is another OPCALL, an operator call has a LIST of arguments, and the parameter list ARGS is a ten-slot array of mostly nil and numbers whose meaning is only in the C source.

The last lines of the output hide the most important pitfall. AbstractSyntaxTree.of(method) needs a method compiled by the legacy parser. Since Ruby 3.4 the default parser is Prism, so the iseq of any method in your program was compiled by Prism and of raises RuntimeError ("cannot get AST for ISEQ compiled by prism"); on Ruby 3.3 the same call returns the tree. parse and parse_file keep working because they always use the legacy parser, and they print the legacy parser’s own diagnostics to $stderr under -w; ruby --parser=parse.y restores the old behaviour of of. Code that needs to analyse source it finds through Method#source_location should read the file and parse it with Prism, as in the next section.

Prism

Prism is a portable, error-tolerant recursive-descent parser for Ruby. It is both a C library, which CRuby uses internally, and a gem with a Ruby API for any tool that needs to parse Ruby. It became the default parser of CRuby in 3.4 (selected with --parser=prism or --parser=parse.y), and the Ruby documentation names it as the official API for parsing Ruby code that works across implementations. Because it is error tolerant, broken code still yields a tree and a list of errors. Prism versions follow the gem, not Ruby’s version: Ruby 4.0.0 bundled Prism 1.7.0 and the 4.0.7 used here reports Prism::VERSION 1.8.1.

The entry points are Prism.parse(source, version: ...), parse_file, parse_success?, parse_comments, lex and dump. A Prism::ParseResult has value (the ProgramNode), errors, warnings, comments and magic_comments. Every node is a typed class (DefNode, CallNode, LocalVariableReadNode, ItLocalVariableReadNode, …​), with named accessors instead of positional children, a location with start_line, end_line, start_column and slice, and accept for visitors. Prism::Visitor walks the tree, and you override visit_*_node for the nodes you care about, calling super to continue into the children.

What the example shows, in order:

  • a successful parse (success?, no errors) and the typed DefNode with its name, lines, parameters and the exact source slice, plus the comment that was found;

  • Prism.lex returning tokens, and parse_success? as the quick validity check;

  • a broken file producing four errors, each with a line, a message and a stable type symbol, and still a tree;

  • a Prism::Visitor subclass collecting the methods of isbn.rb, a file that was found through reflection (source_location) and parsed with Prism, the pattern behind every documentation, lint and refactoring tool;

  • the version: option: it in [1].map { it } is parsed as a method call when the target is Ruby 3.3 and as the implicit block parameter (ItLocalVariableReadNode) when it is 3.4, which is what lets a tool analyse code for an older Ruby than the one it runs on; and

  • Ripper.sexp compared with the same call on Prism::Translation::Ripper, which returns the same result for that input.

Prism::Translation::Parser and RubyParser produce the trees that the community parser and ruby_parser gems return, so tools written for those gems (RuboCop’s cops are built on the parser AST) can run on Prism without rewriting. Ripper (Ripper.sexp, Ripper.lex, Ripper.tokenize) is still available and is how older tools such as syntax highlighters work; for new code, choose Prism.

Putting it together: an API report

The pieces combine into small tools. This one prints, for each class, the methods it defines itself with their visibility, a signature rebuilt from Method#parameters, and the file and line from source_location. It uses only Module and Method reflection, so it works on any Ruby.

# frozen_string_literal: true

require "shelf"

# Renders Method#parameters back into something that looks like a signature.
module Signature
  FORMATS = {
    req: "%<name>s", opt: "%<name>s = ...", rest: "*%<name>s", keyreq: "%<name>s:",
    key: "%<name>s: ...", keyrest: "**%<name>s", block: "&%<name>s"
  }.freeze
  ANONYMOUS = %i[* ** &].freeze

  def self.render(parameters)
    parameters.map do |kind, name|
      format(FORMATS.fetch(kind), name: ANONYMOUS.include?(name) ? nil : name)
    end.join(", ")
  end
end

# The instance methods a class defines itself: visibility, method and location.
def own_methods(klass)
  %i[public private].flat_map do |visibility|
    klass.public_send(:"#{visibility}_instance_methods", false).map { [visibility, klass.instance_method(it)] }
  end
end

def location(method)
  file, line = method.source_location
  file ? "#{File.basename(file)}:#{line}" : "(generated)"
end

def api_report(klass)
  puts klass
  own_methods(klass).sort_by { |_, method| method.source_location&.last || 0 }.each do |visibility, method|
    signature = "#{method.name}(#{Signature.render(method.parameters)})"
    puts format("  %<visibility>-7s #%<signature>-34s %<where>s", visibility:, signature:, where: location(method))
  end
end

Costs, safety and portability

  • Speed. respond_to?, instance_variable_get and Method objects are cheap enough for ordinary code, though a Method allocation per call adds up in a tight loop. ObjectSpace.each_object, count_objects_size, allocation tracing and every TracePoint are diagnostic tools with real cost. Never put them in a request path.

  • Safety. Reflective calls take names, and names that come from outside are input: obj.public_send(params[:action]), Object.const_get(params[:type]), Binding#eval and instance_variable_set(params[:name], ...) let a caller reach methods, classes and state that you never meant to expose. Allow-list the names, and read Security.

  • Encapsulation. Reflection ignores private (instance_variable_get, send, instance_method of a private method) by design. Using it in application code ties the caller to the implementation. Tests are the usual exception, and even there prefer the public interface; see Visibility and Encapsulation.

  • Portability. RubyVM exists only on MRI, and several ObjectSpace methods, TracePoint#instruction_sequence and the objspace extension are documented as MRI specific. Method, Binding, caller_locations and the Module queries are core Ruby and the safe subset. The shared, versioned API for parsing is Prism.

  • Stability. Everything under RubyVM and the output of disasm, ObjectSpace.count_objects keys, TracePoint.stat and the text of backtrace lines and warnings can change in any release (3.4 changed backtraces and 4.0 changed them again). Do not parse them in code you ship; use the structured APIs (caller_locations, Warning.warn with category:, Prism).

  • Retention. Binding objects, Method objects with a bound receiver, Proc#binding and a TracePoint argument kept after the hook returns all hold on to their scope or receiver; collect values, not the reflective objects.

Pitfalls

  • obj.methods(false) is not "the methods the class defines"; it is the singleton methods. Use obj.class.instance_methods(false) for the class’s own, or public_methods(false) for singleton plus class.

  • instance_methods hides private methods, so a class can look empty (initialize is private). Ask for private_instance_methods(false) as well, or respond_to?(name, true).

  • Comparing Method#owner with receiver.class is wrong for inherited and mixed-in methods: Catalog.new.method(:map).owner is Enumerable.

  • Method#source_location is nil for C methods and const_source_location is [] for constants defined in C; check before indexing. For attr_* and define_method it points at the generating call, not at a def.

  • method_missing without respond_to_missing? breaks respond_to?, method and anything built on them.

  • ObjectSpace.each_object(Class) includes singleton classes. Counting objects with it is also affected by garbage that has not yet been collected.

  • A TracePoint block runs for every matching event in every file, including gems. Filter first and narrow the scope. The hook cannot trace code it calls itself unless you use allow_reentry.

  • A TracePoint attribute used on the wrong event raises; a stored TracePoint argument raises later. binding is nil for C events.

  • TracePoint#enable { } is scoped to the current thread only. Use target_thread: nil for others.

  • Coverage.start after require measures nothing for the files already loaded. Start it first, at the top of the test helper or the script that loads the code.

  • $VERBOSE = nil turns off warn entirely, even your own deprecation messages. Prefer Warning[:deprecated] = false when you only want to silence one category.

  • RubyVM::AbstractSyntaxTree.of raises with Prism-compiled code (3.4+). Do not build tools on it.

  • Parsing a backtrace or a warning message with a regexp breaks on the next Ruby upgrade: 3.4 changed the quoting and added owners, 4.0 changed internal frames and the ArgumentError text.

  • binding and eval run code that was never written in the file you are reading. Do not pass them input from outside.
