IRB and Debugging

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Ruby 4.0 (4.0.7, checked on 2026-10-18), which ships IRB 1.16.0, the debug gem 1.11.1, error_highlight 0.7.x, did_you_mean 2.0.0 and syntax_suggest 2.0.3. A Ruby program rarely does what you expect the first time, and Ruby gives you four distinct ways to find out why, which this page covers in the order you reach for them:

  • Ask the language in a REPL: IRB lets you load your code, call it, inspect the result, read the source and the documentation of any method, and, with binding.irb, do all of that from inside a running program.

  • Stop the program and walk through it with the debug gem (rdbg, binding.break): breakpoints, stepping, frame navigation, exception breakpoints, watchpoints, tracing, replay, remote attach and an editor integration.

  • Print what you need to see with p, pp, inspect and a few small idioms, which is still the fastest tool for most bugs.

  • Read what the interpreter already tells you: the error message, its source snippet (error_highlight), its spelling suggestion (did_you_mean) and its syntax diagnosis (syntax_suggest).

flowchart TD A[A bug or a surprise] --> B{Do you know roughly where?} B -- no --> C[Read the message: error_highlight and did_you_mean] C --> D{Still unclear?} D -- yes --> E[Reproduce it in IRB: load the code and call it] B -- yes --> F{Can you see the values you need?} F -- "yes, print them" --> G[p, pp, warn, tap] F -- "need to look around" --> H{Can you edit the code?} H -- yes --> I[binding.irb or binding.break] H -- no --> J[rdbg script.rb or rdbg -c command] E --> I G --> K[Fixed?] I --> K J --> K

The page builds on Getting Started (installing Ruby and running scripts), Reflection, Introspection and Tracing (the Binding, caller and TracePoint machinery that every tool here is built on), Exceptions and Error Handling (raise, backtrace, detailed_message) and RubyGems and Bundler (why a gem that is installed can still fail to load under bundle exec). Unit tests are the other half of debugging; see Testing with Minitest and RSpec and Test Doubles. Profilers and benchmarks are in Performance, Benchmarking and Profiling, and the ruby flags that this page mentions (-w, -r, -I, --disable) are explained in Ruby Command Line and Environment.

Every example was syntax-checked with ruby -wc, run with ruby -w on Ruby 4.0.7 and linted with RuboCop 1.92 using the configuration of the running shelf gem (double-quoted strings, NewCops: enable, Style/Documentation off). The two scripts that start an interactive session on purpose (binding.irb and binding.break) carry a rubocop:disable Lint/Debugger comment, because that cop exists to keep such calls out of committed code. The interactive transcripts are real sessions copied from a terminal, trimmed to the relevant lines; absolute paths are replaced by /path/to/shelf and memory addresses are the ones the session printed. The examples that need the gem are run with ruby -I/path/to/shelf/lib, so require "shelf" finds it (see the shelf gem source).

IRB

IRB (*I*nteractive *R*u*B*y) reads an expression, evaluates it, prints the result with inspect and loops. It is what you get from the irb command, and the same engine runs inside a program when you call binding.irb. Its documentation lives with the gem, at https://ruby.github.io/irb/ and in irb --help; since IRB is a bundled gem in 4.0, the core documentation at docs.ruby-lang.org/en/4.0 no longer has an IRB page.

Starting IRB

$ irb                                # an empty session
$ irb -I lib -r shelf                # put lib on the load path and require the gem first
$ irb -w                             # same as ruby -w: show warnings
$ irb -f                             # do not read any .irbrc
$ irb --nocolorize --noautocomplete  # plain output, useful in logs and CI consoles

A first session

At the prompt, every complete expression is evaluated and its result printed after =>. A statement that is not yet complete (an open do, a trailing operator, an unclosed bracket) makes the editor continue on the next line, and the editor indents it for you. The result of the last expression is available as _, which is the quickest way to keep working on a value you forgot to assign.

irb(main):001> isbn = Shelf::Isbn.new("978-0-596-51774-8")
=> #<data Shelf::Isbn digits="9780596517748">
irb(main):002> isbn.digits.length
=> 13
irb(main):003> _ + 1
=> 14

Source: IRB documentation: Evaluation History

An assignment prints its value too, but truncated when it is long (the default --truncate-echo-on-assignment), so that loading a large object into a variable does not flood the terminal:

irb(main):002> book = Shelf::Book.new(isbn:, title: "The Ruby Programming Language", author: Shelf::Author.new("Flanagan"))
=>
#<data Shelf::Book
...

Evaluating the variable on its own prints the whole value, laid out with pp (see pp and p). Two details are worth remembering. The value printed after => is the return value of the expression, not what the expression printed: puts "x" shows x and then => nil. And in Ruby 3.4 and later Hash#inspect prints {isbn: 1} and {"a" => 1}, so the output you see in IRB matches what p prints in a script of the same version.

Source: IRB documentation

Commands

IRB has two kinds of input. Anything that is valid Ruby is evaluated. A command is a name followed by free text that does not have to be valid Ruby, such as ls -g pattern or show_source Shelf::Isbn#to_s. A command is recognised only when it is the first word of the input and no local variable of that name exists: if you assign ls = 3, the word ls means the variable until you leave it. Type help for the list in your version and help command for one command.

Pitfalls in the REPL

  • The history is global. Every session appends to the same history file, by default ~/.irb_history, which is why the history numbers in a long-lived shell are large. IRB.conf[:SAVE_HISTORY] (default 1000 lines) and IRB.conf[:HISTORY_FILE] control it, and a secret typed at the prompt stays in the file.

  • Redefinition is silent. Reloading a class by pasting it again adds methods to the existing class instead of replacing it, exactly as in a file. Restart the session, or use load "file.rb", when stale methods matter.

  • _ is overwritten by every expression, including the ones IRB evaluates for you, so assign anything you need to keep.

  • A command is shadowed by a local variable. After history = [] the word history is the array. Use binding.local_variables to see what you have defined.

  • Output is inspect, not to_s. A Data or Struct whose to_s you overrode still prints with its structure in IRB.

  • Ctrl-C interrupts the running expression, not the shell (the default IRB.conf[:IGNORE_SIGINT] is true), and Ctrl-D at an empty prompt exits.

binding.irb

binding.irb starts an IRB session inside the running program, with the local variables, self and the current method of the line where it is written. It is Binding#irb, so you can call it on any binding, and it is the Ruby counterpart of debugger in other languages.

# frozen_string_literal: true

require "shelf"

isbn = Shelf::Isbn.new("978-0-596-51774-8")
author = Shelf::Author.new("Flanagan")
book = Shelf::Book.new(isbn:, title: "The Ruby Programming Language", author:)
catalog = Shelf::Catalog.new.add(book)

titles = catalog.map(&:title)
binding.irb # rubocop:disable Lint/Debugger

puts titles.size

The error in the last command is the point: an exception raised by what you type is printed and the session continues, so trying things out cannot end the program. Typing exit (or Ctrl-D) resumes the program after the binding.irb line, which is why 1 was printed by the puts after the session. exit! ends the whole process, and disable_irb makes every later binding.irb call do nothing, which is useful when a call sits in a loop.

Where binding.irb is useful and where it is not:

  • It is for a developer at a terminal. A program without a terminal on standard input (a service, a job, a test run with piped input) has nothing for IRB to read; use the remote mode of the debugger instead (see Remote debugging).

  • Put it where the interesting values are in scope, including inside a rescue clause (rescue => e then binding.irb), inside a block, or in a method called from a test. binding.irb in a test run waits forever in CI, so remove it before committing; RuboCop’s Lint/Debugger cop exists to catch it.

  • Under Bundler it needs irb in the Gemfile (see Debugging under Bundler).

  • From IRB you can reach the debugger without restarting (see Using IRB and the debugger together).

The .irbrc file

IRB reads Ruby code from a configuration file at startup (unless -f is given). The first file found in this order is used:

  1. the path in the IRBRC environment variable;

  2. $XDG_CONFIG_HOME/irb/irbrc;

  3. ~/.irbrc;

  4. ~/.config/irb/irbrc (only when XDG_CONFIG_HOME is not set);

  5. .irbrc, _irbrc or $irbrc in the current directory.

Because the file is plain Ruby, it can configure IRB through the IRB.conf hash and define commands and helpers. Hash entries set in the file win over command-line options, and IRB.conf is read once, when the file is interpreted, so changes made later in a session do not affect the running context (use conf, the current context, for that).

# frozen_string_literal: true

# ~/.irbrc or ./.irbrc: Ruby code that runs once when IRB starts.
require "irb/command"
require "irb/helper_method"

IRB.conf[:SAVE_HISTORY] = 5_000              # lines kept in the history file
IRB.conf[:HISTORY_FILE] = File.join(Dir.home, ".irb_history")
IRB.conf[:PROMPT_MODE] = :SIMPLE             # ">> " instead of "irb(main):001> "
IRB.conf[:USE_PAGER] = false
IRB.conf[:ECHO_ON_ASSIGNMENT] = false        # do not print the value on `x = ...`
IRB.conf[:COMPLETOR] = :type                 # :type or :regexp
IRB.conf[:LOAD_MODULES] = %w[json]           # same as irb -r json (the rc file wins over -r)

# A command: it receives the raw text after its name, so the argument need not be valid Ruby.
class Isbn13Command < IRB::Command::Base
  category "Shelf"
  description "Convert an ISBN-10 to an ISBN-13"
  help_message "Usage: isbn13 <isbn-10>"

  def execute(arg)
    body = "978#{arg.delete('-')[0, 9]}"
    weighted = body.chars.each_with_index.sum { |digit, i| digit.to_i * (i.even? ? 1 : 3) }
    puts "#{body}#{(10 - (weighted % 10)) % 10}"
  end
end
IRB::Command.register(:isbn13, Isbn13Command)

# A helper method: an ordinary method call that returns a value.
sample_catalog = Class.new(IRB::HelperMethod::Base) do
  description "A catalog with one book in it"

  def execute
    require "shelf"
    isbn = Shelf::Isbn.new("978-0-596-51774-8")
    book = Shelf::Book.new(isbn:, title: "The Ruby Programming Language", author: Shelf::Author.new("Flanagan"))
    Shelf::Catalog.new.add(book)
  end
end
IRB::HelperMethod.register(:sample_catalog, sample_catalog)

Extending IRB: commands and helper methods

Since IRB 1.13 there is a supported API to add features, shown in the .irbrc above. Choose between the two by what the input looks like:

  • A command (IRB::Command::Base subclass registered with IRB::Command.register) receives the raw text after its name as one String, so it can accept things that are not Ruby (isbn13 0-596-51774-0, ls -g pattern). It does not return a value to the session. Use category, description and help_message to put it in help.

  • A helper method (IRB::HelperMethod::Base subclass registered with IRB::HelperMethod.register) is an ordinary method call that returns an object (sample_catalog.first). It shows up under "Helper methods" in help, next to the built-in conf.

A gem can ship its own commands and helpers, loaded from its .irbrc or from a library that the user requires, which is how framework consoles add their shortcuts. If you do not know which to pick, the guide recommends a command first, because it handles more kinds of input.

Type-based completion

IRB offers completion in two forms: pressing Tab, and the dialog that opens automatically while you type, showing candidates and, for the selected one, its documentation. How candidates are computed depends on the completor:

  • The regexp completor looks at the text before the cursor with regular expressions and may evaluate the receiver of a simple method call. It is simple and works everywhere.

  • The type completor (repl_type_completor, a bundled gem since Ruby 3.4) parses the code with Prism and infers the type of the receiver from the code and from the RBS signatures of the core classes, without running anything. After titles.map { it. it knows it is a String. It is the default in IRB on Ruby 3.4 and later when the gem is available; IRB_COMPLETOR=regexp, --regexp-completor or IRB.conf[:COMPLETOR] = :regexp switches back, and --type-completor forces it (printing a warning when the gem cannot be loaded).

The debug gem

The debug gem is the debugger that comes with Ruby 3.1 and later. Until Ruby 3.0 the standard library had a different debug.rb; the gem was written to replace it, and it also replaces, for most people, the community debuggers that earlier tutorials describe. It is a bundled gem (installed with Ruby), is built on TracePoint, supports threads, can be driven from a terminal, a script, a remote socket, VS Code or Chrome DevTools, and is maintained at https://github.com/ruby/debug.

Three ways to start it

$ ruby -r debug target.rb         # or put `require "debug"` at the top: stops only at binding.break / debugger
$ rdbg target.rb                  # run under the debugger, stopped at the first line
$ rdbg -c -- bundle exec rake test   # run another Ruby command under the debugger

Source: ruby/debug repository: invoke with the debugger

  • In the source. Add require "debug" and call binding.break (aliases binding.b and debugger) where you want to stop. The program runs normally until that line, then opens the debug console. It is binding.irb with a debugger instead of a REPL, and require "debug" is the same as rdbg --nonstop --no-sigint-hook.

Debugging threads and forks

Debugger stops are per thread: info threads (or th) lists the threads, th 2 switches to one, and a breakpoint hit in one thread suspends the others while you inspect. fork_mode chooses whether the parent, the child or both keep a debugger after a fork. The README lists support for Ractors as not done yet, so do not rely on stepping inside one (see Ractors and Threads and the GVL).

pp and p

p is the oldest debugging tool and is often enough. Kernel#p writes inspect of each argument followed by a newline and returns its argument, so it can be put in the middle of an expression without changing it. Kernel#pp does the same but lays long values out over several lines. Both write to standard output (use warn or $stderr.puts if the output must not mix with the program’s).

The differences to remember:

  • p x prints x.inspect; puts x and print x print x.to_s (and puts also expands arrays one element per line). For an object whose to_s is overridden, p is the one that shows the structure.

  • p with one argument returns it, with several returns an array of them, with none returns nil and prints nothing. pp returns its argument in the same way. Because p returns its argument, p(x) + 1 and foo(p(bar)) are safe probes.

  • pp wraps at the terminal width minus one (it asks the output with io/console, then the COLUMNS variable, then assumes 80, so 79 when it cannot tell). With the output redirected to a file the width is 79 unless COLUMNS is set, which is why a pp in a test log can look different from the same call in a terminal. PP.pp(obj, out, width) chooses one, and PP.singleline_pp(obj, out) writes a single line.

  • pretty_inspect returns the pp text as a String, with the trailing newline. Kernel#pp is available without a require: it loads the pp library on first use.

  • Both call inspect on the objects. A default inspect shows every instance variable, which for a large object graph (an ActiveRecord-style model, a catalog with a mutex) is thousands of characters. Override inspect for a short form, or pretty_print for a layout, or limit the variables (pretty_print_instance_variables).

  • p(isbn:, author:) uses the value-omission shorthand of Ruby 3.1 to print {isbn: ..., author: ...}, a labelled print that names the variables. In Ruby 3.3 and older that hash prints as {:isbn=>...}; the new {isbn: ...} format is the Ruby 3.4 Hash#inspect.

Customising inspect and pretty_print

inspect is what IRB, p, error messages and the debugger show. pretty_print(q) is what pp, IRB’s result printing (IRB uses pp) and the debugger’s pp show. The q argument is a PP object with group, text, breakable, comma_breakable and seplist:

# frozen_string_literal: true

require "shelf"

# Reopening Catalog here only to show the two hooks; real code would put them in the class.
module Shelf
  class Catalog
    # `inspect` feeds p, IRB and error messages: keep it short and free of internals such as the mutex.
    def inspect = "#<Shelf::Catalog #{count} books>"

    # `pretty_print` feeds pp (and IRB). It receives a PP object and builds a layout.
    def pretty_print(pp)
      pp.group(1, "#<Shelf::Catalog", ">") do
        pp.breakable
        pp.seplist(to_a, -> { pp.comma_breakable }) { |book| pp.text(book.title.inspect) }
      end
    end
  end
end

Printing without a debugger

A few idioms cover most print debugging, and all of them keep working in a script that has no debugger, a container or a CI log:

# frozen_string_literal: true

require "shelf"

# A tiny tracing helper: prints to $stderr (so it never mixes with program output),
# names the caller, and returns the value so it can wrap any expression.
def dbg(value, label = nil)
  where = caller_locations(1, 1).first
  warn "[#{File.basename(where.path)}:#{where.lineno} #{where.base_label}] #{label || value.class}: #{value.inspect}"
  value
end

def title_letters(books)
  books.sum { |book| dbg(book.title.length, "title length") }
end

isbn = Shelf::Isbn.new("978-0-596-51774-8")
author = Shelf::Author.new("Flanagan")
books = [Shelf::Book.new(isbn:, title: "Ruby", author:), Shelf::Book.new(isbn:, title: "Rails", author:)]

# tap: look at an intermediate value without breaking the chain.
titles = books.map(&:title).tap { |list| warn "titles: #{list.inspect}" }.map(&:upcase)
puts titles.inspect

# dbg: wrap an expression, keep its value.
puts dbg(title_letters(books))

# warn with uplevel: reports the caller's line, like a library deprecation warning.
def old_title_letters(books)
  warn "old_title_letters is deprecated, use title_letters", uplevel: 1
  title_letters(books)
end
old_title_letters(books)

did_you_mean (also a default gem and loaded by default) appends Did you mean? and up to a few candidates to NameError, NoMethodError, KeyError, NoMatchingPatternKeyError and LoadError (for require paths).    4 |   class Report
   5 |     def initialize(catalog)
  ~~~~~~
  14 |     def count = @catalog.count
  15 |   end
> 16 | end
     |    ^ unexpected end-of-input, assuming it is closing the parent top level context

The first part is syntax_suggest: it narrows the problem to def titles and @catalog.map do, whose do has no end. The second part is the parser’s own message. With ruby --disable=syntax_suggest only the second part is printed, and Ruby 3.2 prints the older syntax error, unexpected end-of-input form after the suggestion. The gem also provides a syntax_suggest command that takes a file name, and SyntaxSuggest.call for tools. Its guess is a heuristic based on indentation, so it works best on a consistently indented file; when the highlighted block looks right, look at the line above it.

Where the books are outdated

Older books and blog posts on debugging Ruby describe tools that have since changed or gone:

Old advice Ruby 4.0 reality

ruby -r debug opening the (rdb:1) debugger of the standard library, with its own command set

That library was replaced. require "debug" loads the debug gem, whose console is (rdbg) and whose commands are in this page. Under Bundler it fails with a LoadError unless debug is in the Gemfile

byebug, ruby-debug, debugger and pry plus pry-byebug as the standard debugging setup; binding.pry

byebug is superseded by debug; binding.irb and binding.break cover what binding.pry was used for. These gems still exist and are community-maintained; this page does not cover them

require "irb/completion" and require "irb/ext/save-history" in .irbrc, plus IRB.conf[:AUTO_INDENT] = true

Completion and history are built into the Reline editor and are on by default; irb/ext/save-history no longer exists (require raises LoadError) and history is controlled with IRB.conf[:SAVE_HISTORY]

IRB is a part of the standard library, irb always available

IRB is a bundled gem in 4.0, and with Bundler it must be in the Gemfile

Tab completion by regular expressions; readline as the line editor

Reline is the editor, and the type-based completor is the default on 3.4 and later. readline is itself a bundled gem

=> {:a=>1} in every REPL transcript

=> {a: 1} since 3.4, so copy-pasted outputs in old text do not match what you see

undefined method `x' for nil:NilClass in error messages and NoMethodError with the receiver’s whole inspect

undefined method 'x' for nil and for an instance of Foo (3.3 and 3.4)

require "pp" before using pp

pp is available without require, and wraps at the terminal width

ruby -w and $DEBUG as the way to see problems

Still valid, plus Warning[:category] switches and the tools above (see Reflection, Introspection and Tracing)
