Pattern Matching

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Ruby 4.0 (4.0.7, checked on 2026-10-18). Pattern matching is Ruby’s way of describing the shape of a value and taking it apart in one step. A pattern states what the value must look like (its class, its length, which keys it has, what those hold), and, if it does, binds the interesting parts to local variables. It replaces chains of is_a?, [], dig, fetch and == calls with one declarative expression, and it fails loudly (an exception) instead of quietly producing nil when the shape is not the one you expected.

The feature arrived in Ruby 2.7 as an experiment, case/in became stable in 3.0, the one-line forms in 3.1 and the find pattern in 3.2 (see Version notes), so everything on this page works on any recent Ruby; the exceptions (the it block parameter and the {a: 1} form of Hash#inspect in messages) need 3.4 and are called out where they appear. The page builds on Control Expressions (case/when and truthiness), Arrays, Hashes and Assignment and Multiple Assignment (the destructuring that patterns generalise). The value types most often matched are covered in Struct, Data and Value Objects and Regular Expressions; the equality protocol that value patterns rely on is in Equality, Hashing and Comparison; failures are exceptions as described in Exceptions and Error Handling; and Enumerable shows the iterator methods that combine well with the one-line in form.

Every example was syntax-checked with ruby -wc, run with ruby -w on Ruby 4.0.7 and linted with RuboCop 1.92 using the configuration of the running shelf gem (double-quoted strings, NewCops: enable and Style/Documentation off). The output shown is the real output. The examples that need the gem are run with ruby -Ilib so that require "shelf" finds it (see the shelf gem source). Two examples deliberately step outside that configuration and say so.

The decision flow below is what Ruby does for each branch. It stops at the first branch whose pattern matches (and whose guard, if any, is true).

The three forms

# frozen_string_literal: true

config = { db: { user: "admin", host: "localhost", port: 5432 } }

# 1. case/in picks a branch and binds variables.
case config
in { db: { user:, host: } }
  puts "connect #{user}@#{host}"
in { database: { username: } }
  puts "legacy key, user #{username}"
else
  puts "unrecognised shape"
end

# 2. => unpacks or raises when the shape is wrong.
config => { db: { port: } }
puts "port #{port}"

# 3. in answers true or false.
puts((config in { db: { port: Integer } }))
puts((config in { db: { port: String } }))
connect admin@localhost
port 5432
true
false

Source: Ruby documentation: Pattern matching

case/in is for choosing between shapes. => is for the case where only one shape is acceptable: it unpacks the parts you want and raises if the data is not what the code assumes, which makes it a compact assertion at a boundary (a parsed configuration file, a decoded message). in is a predicate: because it returns a boolean it fits in if, &&, select and count.

Rules for case/in

  • The subject is followed by a newline or a semicolon. case value in pattern then ... end on one line does not work: Ruby reads value in pattern as the subject, a boolean test, and then looks for when or in branches that never come (see Syntax errors you will meet).

  • Each branch starts with in, then the pattern, then a newline, a semicolon or then. One-line branches use then (in Integer then "integer"). RuboCop’s Style/InPatternThen rejects the in pattern; body form and Style/MultilineInPatternThen rejects then on branches whose body is on the next line.

  • case is an expression: the value of the chosen branch is the value of the whole case, so it can be assigned, returned or passed on.

  • when and in branches cannot be mixed in one case.

  • Branches are tried top to bottom and the first match wins. Variables bound by that branch are ordinary local variables that outlive the case.

  • else is optional. Without it the case is exhaustive in the sense that a value matching no branch raises (see the next section); this is the deliberate difference from case/when, which silently evaluates to nil.

  • Unlike case/when, one in branch takes one pattern. A comma-separated list is not a list of alternatives: it is an array pattern without brackets (see Array patterns). Use | for alternatives.

Exhaustiveness: NoMatchingPatternError

# frozen_string_literal: true

def classify(value)
  case value
  in Integer then "integer"
  in String then "string"
  end
end

puts classify(1)
begin
  classify(:sym)
rescue NoMatchingPatternError => e
  puts "#{e.class}: #{e.message}"
end

def classify_total(value)
  case value
  in Integer then "integer"
  else "other"
  end
end

puts classify_total(:sym)

begin
  { title: "Dune" } => { title: String, year: }
  puts year
rescue NoMatchingPatternKeyError => e
  puts "#{e.class}: #{e.message}"
  puts "key=#{e.key.inspect} matchee=#{e.matchee.inspect}"
end

Source: NoMatchingPatternError and NoMatchingPatternKeyError

NoMatchingPatternError is a StandardError, so a bare rescue catches it. NoMatchingPatternKeyError is its subclass, raised when the reason for the failure is a missing key in a hash pattern; it adds key and matchee and includes DidYouMean::Correctable, so a near-miss key gets a suggestion: matching { nme: 1 } against { name: } reports key not found: :name and then Did you mean? :nme in the detailed message. Rescue the parent when you do not care which of the two happened.

The checking is dynamic: Ruby does not verify at load time that every case is covered. The exception at run time is the safety net against forgetting one, and an else that raises a domain-specific error (as in State machines) turns it into a better message.

The message format is a diagnostic aid, not an interface, and it varies with how the match was written. Observed on Ruby 4.0 (the same on 3.3 and 3.4 except that 3.3 prints hashes in the old {:a=>1} form):

Value patterns

A value pattern is any literal, constant or expression-free object. Ruby tests it with the case equality operator, pattern === value, the same operator case/when uses. That one rule explains every behaviour below.

# frozen_string_literal: true

ALLOWED = Set[:available, :lent].freeze

[0, 7, 42, -3, 2.5, "", "123", "abc", :overdue, :available, nil, [1], 1 / 3r].each do |value|
  label =
    case value
    in 0 then "zero"
    in 1..9 then "digit"
    in 10.. then "large"
    in ..-1 then "negative"
    in "" then "empty string"
    in /\A\d+\z/ then "numeric string"
    in String then "string"
    in :overdue then "overdue symbol"
    in ALLOWED then "allowed state"
    in nil then "nothing"
    in ->(x) { x.respond_to?(:each) } then "iterable"
    else "something else"
    end
  puts "#{value.inspect} -> #{label}"
end
0 -> zero
7 -> digit
42 -> large
-3 -> negative
2.5 -> digit
"" -> empty string
"123" -> numeric string
"abc" -> string
:overdue -> overdue symbol
:available -> allowed state
nil -> nothing
[1] -> iterable
(1/3) -> something else

Source: Pattern matching: Patterns

What === means depends on the receiver, which is the pattern:

Pattern === tests

A class or module (Integer, Shelf::Book, Comparable)

value.is_a?(pattern), see Module#===

A Range (1..9, 10.., ..-1, "a".."z")

pattern.cover?(value), so 1..9 === 2.5 is true, see Range#===

A Regexp

A String or Symbol that matches; any other class is simply false, see Regexp#===

A Proc or lambda

Calls it with the value and uses the truthiness of the result, see Proc#===

A Set

Membership (include?), see Set#===

Any other object (0, "x", :lent, nil, true)

==, see Object#===

An Array or Hash constant

==: :lent in %i[available lent] is false, not "is a member"

Four consequences are worth remembering.

  • Order matters when patterns overlap. In the example 2.5 is a "digit" because it falls inside 1..9; the Float branch would have to come first (or the range be written with Integer-only checks) to treat it differently.

  • Only values, constants and ^ pins are allowed. A method call or arbitrary expression is a syntax error as a bare pattern; wrap it in ^(...) (see The pin operator) or hoist it into a constant such as the ALLOWED set above.

  • A lambda is a pattern. in ->(x) { x.respond_to?(:each) } is the escape hatch when a condition cannot be expressed structurally. Prefer a guard (in x if x.respond_to?(:each)) when the condition needs the bound variables.

  • Literals of every kind work: integers, floats, rationals (3r), complex numbers (2i), strings, symbols, ranges, regexps, nil, true, false and __FILE__. A string literal is compared with String#===, which is ==.

Array patterns

An array pattern is a bracketed, comma-separated list of sub-patterns. It matches an Array, or any object that responds to deconstruct (see deconstruct and deconstruct_keys), when it has exactly that many elements and each element matches its sub-pattern. A splat (* or *name) absorbs the rest; only one is allowed per array pattern.

# frozen_string_literal: true

def describe(row)
  case row
  in [] then "empty row"
  in [String => title] then "title only: #{title}"
  in [String => title, Integer => year] then "#{title} (#{year})"
  in [String => title, Integer => year, *tags] then "#{title} (#{year}) tagged #{tags.join(', ')}"
  in [_, _, _, *] then "unexpected extra columns"
  else "not a row"
  end
end

puts describe([])
puts describe(["Dune"])
puts describe(["Dune", 1965])
puts describe(["Dune", 1965, "sf", "classic"])
puts describe([1965, "Dune"])
puts describe("Dune")

# Brackets are optional, and a leading element can be split from the rest.
case ["978-0-306-40615-7", "The Dispossessed", 1974]
in String => isbn, String => title, Integer => year
  puts "#{isbn}: #{title}, #{year}"
end

first, *rest = [1, 2, 3]
[1, 2, 3] => head, *tail
p [first, rest, head, tail]

# The splat can sit anywhere, once.
case [1, 2, 3, 4, 5]
in [first_item, *middle, last_item]
  p [first_item, middle, last_item]
end
empty row
title only: Dune
Dune (1965)
Dune (1965) tagged sf, classic
not a row
not a row
978-0-306-40615-7: The Dispossessed, 1974
[1, [2, 3], 1, [2, 3]]
[1, [2, 3, 4], 5]

Source: Pattern matching: Patterns

  • [] matches only the empty array; [String] matches only one-element arrays holding a String.

  • * alone discards the rest; *rest binds it as an Array (possibly empty). [first, *] and [first, *_] are the same.

  • A splat may sit at the front, the middle or the end: [first, *middle, last].

  • The brackets can be dropped when the pattern is the whole in clause (in String => isbn, String => title, Integer) and after =>/in ([1, 2, 3] => head, *tail). Keep them when a pattern is nested, and write in [x, *] rather than in x, * when the splat would end the line: Ruby then reads the first word of the next line as the name of the splat and the branch body is lost (usually a syntax error).

  • The destructuring assignment first, *rest = array is a different construct: it never fails, it pads with nil. The => form checks the shape and raises.

  • Const(...) and Const[...] are the same pattern with a prefix check; see deconstruct and deconstruct_keys.

Find patterns

A find pattern has a splat at both ends and one or more sub-patterns in between: [*pre, x, y, *post]. It scans the array for the first position where the middle sub-patterns match consecutive elements, and binds what lies before and after. It was added in Ruby 3.0 as an experiment and became stable in 3.2.

# frozen_string_literal: true

require "shelf"

author = Shelf::Author.new("Ursula K. Le Guin")
isbn = Shelf::Isbn.new("978-0-306-40615-7")
book = Shelf::Book.new(isbn:, title: "The Dispossessed", author:)

events = [:created, :lent, "note: damaged cover", :returned, "note: repaired"]

case events
in [*before, String => note, *after]
  puts "first note: #{note}"
  puts "before: #{before.inspect}"
  puts "after: #{after.inspect}"
end

case events
in [*, :lent, String => remark, *]
  puts "#{book.title} was lent, then noted: #{remark}"
end

puts((events in [*, :overdue, *]))

case [1, 42, "x", 7, "y"]
in [*, Integer => n, String => s, *]
  puts "first Integer followed by a String: #{n}, #{s}"
end
first note: note: damaged cover
before: [:created, :lent]
after: [:returned, "note: repaired"]
The Dispossessed was lent, then noted: note: damaged cover
false
first Integer followed by a String: 42, x

Source: Pattern matching: Patterns

  • The middle sub-patterns must match adjacent elements. Two separate searches ([*, :lent, *, :returned, *]) are not a find pattern and are a syntax error.

  • It tries each starting position in turn, so it is O(n times m) for n elements and m inner patterns. Fine for event lists and tokens, not for a hot loop over large arrays.

  • The first match wins and the outer splats are bound from that match only.

  • *pre and *post are optional names: [*, x, *] just asks "is there an element that matches x?".

Hash patterns

A hash pattern is { key: pattern, ... }. It matches a Hash, or an object responding to deconstruct_keys, that contains every listed key with a value matching the sub-pattern.

# frozen_string_literal: true

entry = { title: "Dune", year: 1965, tags: %w[sf classic] }

case entry
in { title: String => title }
  puts "extra keys are fine: #{title}"
end

case entry
in { title:, **nil }
  puts "never reached"
in { title:, year:, tags:, **nil }
  puts "closed pattern matched: #{title}, #{year}, #{tags}"
end

case entry
in { title:, **others }
  puts "title #{title}, others #{others}"
end

puts((entry in {}))
puts(({} in {}))

# Only symbol keys are matched; a string key never matches.
puts(({ "title" => "Dune" } in { title: "Dune" }))
puts(({ "content-type": "text/plain" } in { "content-type": String }))

# Nested hashes and arrays compose.
case { name: "Ada", loans: [{ title: "Dune" }, { title: "Emma" }] }
in { name:, loans: [{ title: first_title }, *] }
  puts "#{name} first borrowed #{first_title}"
end
extra keys are fine: Dune
closed pattern matched: Dune, 1965, ["sf", "classic"]
title Dune, others {year: 1965, tags: ["sf", "classic"]}
false
true
false
true
Ada first borrowed Dune

Source: Pattern matching: Patterns

  • Subset semantics. Extra keys are ignored. This is the opposite of array patterns, where the length must match.

  • {} is the exception. It matches only an empty hash.

  • **nil demands that there are no other keys: { title:, **nil } matches a hash whose only key is :title.

  • **rest binds the remaining pairs as a new Hash.

  • Key-only form. { title: } has no sub-pattern; it matches when the key exists (its value may be nil) and binds a local variable with the key’s name. { title: String => t } binds to a different name.

  • Braces are optional where a bare hash pattern is the whole clause: in title:, year: and hash => title:.

  • Only symbol keys. { "title" => ... } with a rocket is a syntax error, and a hash with string keys never matches a symbol-keyed pattern (convert first, for example JSON.parse(text, symbolize_names: true)). A key with characters that are not valid in a label is written as a quoted symbol label, { "content-type": String }, which cannot contain interpolation.

  • Missing key vs nil value. { a: } and { a: _ } match { a: nil } but not {}; { a: nil } matches only the former (see Pitfalls).

  • A key may be listed only once per hash pattern.

Alternative patterns and binding

pattern1 | pattern2 matches if either side does, trying left to right. It is written between two value, array, hash or nested patterns, and the alternation can be given a name afterwards with => name because the capture sits outside the alternation.

Variable binding has three spellings:

  • A bare name as a pattern, in [x, *rest], matches anything and binds it. It never compares: in [expected, *] does not check against an existing expected, it overwrites it (use the pin operator for that).

  • pattern => name matches the pattern first and binds the value only if it matched (Integer => year).

  • A key-only hash entry ({ title: }) binds the key’s name.

# frozen_string_literal: true

[1, 2.5, "3", :four, nil].each do |value|
  case value
  in Integer | Float => number
    puts "number #{number}"
  in String | Symbol => text
    puts "text #{text}"
  else
    puts "neither: #{value.inspect}"
  end
end

# A variable inside an alternative is a syntax error.
begin
  RubyVM::InstructionSequence.compile("case 1\nin a | 2 then a\nend", "alternative.rb")
rescue SyntaxError => e
  puts e.message
end

# Variables starting with an underscore are allowed there.
case [1, 2]
in [_first, _second] | [_, _, _]
  puts "two or three items"
end

# Bare names bind; they never compare.
expected = 18
case [1, 2]
in [expected, *]
  puts "matched, expected is now #{expected}"
end
number 1
number 2.5
text 3
text four
neither: nil
alternative.rb:2: syntax error found
  1 | case 1
> 2 | in a | 2 then a
    |    ^ variable capture in alternative pattern
  3 | end
two or three items
matched, expected is now 1

Source: Pattern matching: Variable binding

  • No variables inside an alternative, because Ruby could not know which one was set. The compiler rejects in a | 2 and in [Integer => a] | [Float => a]. Variables whose names start with _ are the documented exception: _first and _ are allowed, but the value they hold is not meant to be used.

  • Binding the alternation as a whole is fine: Integer | Float => number.

  • Bound variables are plain locals. They are visible after the case, they are never in a new scope, and a branch that fails after binding some of them can leave those variables set. The documentation lists that as undefined behaviour: do not read a variable from a branch that did not run.

  • A repeated name is an error (in [a, a]). To require the same value in two places, pin the first (see the next section).

  • _ is a normal variable name with a convention. It can appear any number of times in one pattern.

  • A key-only hash pattern shadows a method of the same name after the case, like any local variable.

The pin operator

A bare name binds, so an existing variable cannot be used as a sub-pattern directly. The pin operator ^ says "use the current value of this variable".

# frozen_string_literal: true

expected = 18
pair = [1, 2]
case pair
in [^expected, *]
  puts "matched"
else
  puts "not matched, expected is still #{expected}"
end

# rubocop:disable Style/GlobalVars, Style/ClassVars
$limit = 2
class Window
  @size = 3
  @@depth = 4

  def self.check(values)
    case values
    in [^$limit, ^@size, ^@@depth]
      "globals, ivars and class variables can be pinned"
    else
      "no match"
    end
  end
end
puts Window.check([2, 3, 4])
# rubocop:enable Style/GlobalVars, Style/ClassVars

a = 1
b = 2
total = 3
case total
in ^(a + b)

Guards

A case/in branch can end with if or unless and a condition that may use the variables the pattern bound. The branch is chosen only when both the pattern matches and the guard is true.

# frozen_string_literal: true

[[:lent, 3], [:lent, 20], [:returned, 0], [:overdue, 40]].each do |pair|
  label =
    case pair
    in [:lent, days] if days > 14 then "lent too long (#{days} days)"
    in [:lent, days] then "lent for #{days} days"
    in [state, days] unless days.zero? then "#{state}, #{days} days"
    in [state, _] then state.to_s
    end
  puts label
end

# Guards belong to case/in only. After => or in, "if" is a plain modifier,
# evaluated first, so the pattern variables are still nil.
begin
  pair = [1, 1]
  result = (pair in [first, second]) if second == first * 2
  p result
rescue NoMethodError => e
  puts e.message
end
lent for 3 days
lent too long (20 days)
returned
overdue, 40 days
undefined method '*' for nil

Source: Pattern matching: Guard clauses

  • Guards exist only on in clauses of case. => and in as one-line expressions have no guard: a trailing if is an ordinary statement modifier that is evaluated first (the pattern variables are still nil, as the example shows).

  • A false guard falls through to the next branch, exactly like a failed pattern, so guards can be stacked (in [:lent, days] if days > 14 before in [:lent, days]).

  • Put cheap structural checks in the pattern and only the remaining logic in the guard. A pattern documents the shape; a guard hides it.

  • When a single-branch case fails only because of its guard, the message is guard clause does not return true.

One-line forms

value => pattern and value in pattern are expressions in the grammar sense but with different roles. Both were experimental in 3.0, where in also changed to return a boolean (in 2.7 it raised), and both are stable since 3.1, which also made the parentheses around the pattern optional.

deconstruct and deconstruct_keys

An array or find pattern asks the matched object for an array with deconstruct; a hash pattern asks for a hash with deconstruct_keys(keys). Array and Hash have this built in; every other class has to provide it. A class implements them to take part in pattern matching.

# frozen_string_literal: true

# A loan receipt that can be matched as a list or as a hash.
class Receipt
  attr_reader :title, :state, :days

  def initialize(title, state, days)
    @title = title
    @state = state
    @days = days
  end

  def deconstruct
    puts "  deconstruct"
    [title, state, days]
  end

  def deconstruct_keys(keys)
    puts "  deconstruct_keys(#{keys.inspect})"
    { title:, state:, days: }
  end
end

The rules:

  • deconstruct takes no arguments and returns an Array; deconstruct_keys(keys) returns a Hash with symbol keys. Any other return type raises TypeError (deconstruct must return Array, deconstruct_keys must return Hash).

  • keys is an Array of the symbols the pattern is going to look at, or nil when the pattern has **rest and needs everything. It exists for optimisation: an object whose full hash is expensive to build may return only the requested keys. Returning more keys than requested is allowed; the extra keys are ignored.

  • An object that lacks the method simply does not match (1: 1 does not respond to #deconstruct); that is a normal failed branch, not a NoMethodError.

  • Const(...) and Const[...] first test Const === object, then match the contents against the parentheses: arrays for positional contents, hashes for keyword contents. A subclass check is therefore a free type guard: a Receipt is not a LateReceipt.

  • The number of calls is unspecified. Ruby may call deconstruct once for all the branches of one case and may call deconstruct_keys once per branch, as the output above shows. Keep both methods free of side effects and cheap, and never rely on how often they run (the documentation lists this as undefined behaviour).

  • Both methods must be public. A private deconstruct or deconstruct_keys is ignored and the branch fails as if the method did not exist.

State machines

Array patterns over a [state, event] pair are a compact way to write a transition table. Each in is a row; alternatives (|) merge rows that share an outcome, _ is a wildcard and else rejects anything not listed, so an unexpected event is an explicit error rather than a silent no-op.

# frozen_string_literal: true

# Pure transition function: (state, event) -> next state.
def transition(state, event)
  case [state, event]
  in [:available, :lend] then :lent
  in [:lent | :overdue, :expire] then :overdue
  in [:lent | :overdue, :return] then :returned
  in [:returned, :shelve] then :available
  in [_, :tick] then state
  else raise ArgumentError, "cannot #{event} while #{state}"
  end
end

state = :available
%i[lend tick expire return shelve].each do |event|
  following = transition(state, event)
  puts "#{state.to_s.ljust(9)} --#{event}--> #{following}"
  state = following
end

begin
  transition(:available, :return)
rescue ArgumentError => e
  puts "#{e.class}: #{e.message}"
end

  • The function is pure (no mutation), which makes it trivial to test one row at a time.

  • Alternatives such as [:lent | :overdue, :return] keep rows that share a target together. Order rows from specific to general; the wildcard row [_, :tick] must come after the specific rows.

  • The else branch raises, so an invalid transition is caught at the call site instead of leaving the loan in a wrong state. Shelf::Loan itself validates its state: argument against STATES.

  • RuboCop’s Lint/DuplicateMatchPattern flags two rows with the same pattern and Lint/UnreachablePatternBranch flags a row hidden behind a catch-all.

Matching decoded payloads

Data decoded from JSON, YAML or a message queue is exactly the nested hash-and-array shape that patterns were designed for. Parse with symbol keys, route on the discriminating field, bind what you need, and finish with an else for anything that is not understood.

# frozen_string_literal: true

require "json"

def describe_loan(type, data)
  case [type, data]
  in ["loan.created", { isbn:, member: { id: Integer => member_id } }]
    "lend #{isbn} to member #{member_id}"
  in ["loan.returned", { isbn:, late_days: Integer => late }] if late.positive?
    "return #{isbn}, #{late} days late"
  in ["loan.returned", { isbn: }]
    "return #{isbn} on time"
  end
end

def describe(event)
  case event
  in { type: "loan.created" | "loan.returned" => type, data: } then describe_loan(type, data)
  in { type: String => type } then "ignore unknown event #{type}"
  else "reject payload without a type"
  end
end

def handle(raw)
  describe(JSON.parse(raw, symbolize_names: true))
rescue JSON::ParserError
  "reject invalid JSON"
end

  • JSON.parse(raw, symbolize_names: true) is what makes hash patterns usable. See Serialization: JSON, YAML, CSV and Marshal.

  • The two-level dispatch keeps each case short: the outer one picks the family of events ("loan.created" | "loan.returned" => type), the inner one the exact shape and the guard (late.positive?).

  • The inner case has no else on purpose: a family event with a malformed payload should raise NoMatchingPatternError and be noticed, while an unknown event type is deliberately ignored by the outer case.

  • A bare name is a catch-all. in value matches anything and cannot be followed by useful branches. Write in Integer or in _ to say what you mean; RuboCop’s Lint/UnreachablePatternBranch finds branches hidden behind one.

  • A non-matching branch may still leak variables, as the last line of the output shows. Use fresh names per branch or rely on the variables only after a match.

  • Arrays are exact; hashes are open. A hash pattern accepting extra keys is useful for forward compatibility; add **nil where an unknown key should be rejected.

  • nil is a value, not "missing". Use { a: nil } to require a key that is present and holds nil, and { a: _ } (or { a: } when you need the value) to require only that the key is present.

  • Strings are not symbols. "a" keys never match; symbolise at the boundary.

  • Floats in integer ranges. A range value pattern uses cover?; add a class check (Integer => n if (1..9).cover?(n)) or order a Float branch first.

  • Array and hash constants compare with ==, not membership; use a Set constant or a range.

  • The in and => precedence traps described in One-line forms.

  • A binding that shadows a method. After in { name: }, name is a local variable and name no longer calls a method of that name inside the scope.

  • Do not use patterns to hide a long conditional. If a case/in has branches whose patterns are almost identical and distinguished by guards, the logic probably belongs in a method or a polymorphic call.

  • Hash default values are ignored. deconstruct_keys on a Hash uses the keys actually stored, so a hash with Hash.new(0) does not match { missing: 0 }.

Tooling and warnings

ruby -w reports a pattern variable that is never used, the same warning as for any local variable:

# frozen_string_literal: true

config = { db: { user: "admin", port: 5432 } }
config => { db: { user:, port: } }
puts port
w.rb:4: warning: assigned but unused variable - user
5432

Source: Ruby documentation: Pattern matching

That run is the one deliberate exception to "no warnings" on this page: it shows the warning itself. Remove the unused name from the pattern (port only), or give it a leading underscore (_user, or _). RuboCop 1.92 does not report an unused pattern variable (this file is clean for it), so the interpreter warning is the check to keep. The cops that do look at patterns are Lint/DuplicateMatchPattern, Lint/EmptyInPattern, Lint/UnreachablePatternBranch, Style/InPatternThen and Style/MultilineInPatternThen. See Style, Linting and Static Analysis.

Pattern matching is also visible to tools: Prism has nodes for each pattern kind (CaseMatchNode, InNode, ArrayPatternNode, FindPatternNode, HashPatternNode, AlternationPatternNode, CapturePatternNode, PinnedVariableNode and PinnedExpressionNode, MatchPredicateNode for in and MatchRequiredNode for =>), which is how editors and linters analyse it (see Reflection, Introspection and Tracing).

Version notes

Version Change

2.7

case/in, array, hash, alternative, capture and pin of local variables are introduced as an experimental feature. Struct#deconstruct and deconstruct_keys.

3.0

case/in is no longer experimental. => is added (experimental). in changes from raising to returning true or false. The find pattern is added (experimental).

3.1

The pin operator takes an expression ^(...) and works on instance, class and global variables. The one-line forms are no longer experimental. Parentheses are optional in one-line patterns.

3.2

The find pattern is no longer experimental. MatchData#deconstruct and #deconstruct_keys, Time#deconstruct_keys and Date#deconstruct_keys are added. Data with deconstruct and deconstruct_keys arrives.

3.4

Error messages print hashes as {a: 1} instead of {:a=>1}. The it block parameter makes select { it in pattern } possible.

4.0

Nothing pattern-specific is listed in the release notes. The error messages shown on this page are the same as on 3.4, and Prism is the parser that reports the syntax errors.
