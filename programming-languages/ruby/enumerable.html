Enumerable

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Ruby 4.0 (4.0.7, checked on 2026-10-18); features newer than Ruby 3.0 name the version that introduced them. Enumerable is the module behind most of what makes Ruby collections pleasant: a class that defines each and includes Enumerable receives sixty-one more methods, from map and select to group_by, each_slice, sum, min_by, tally and lazy, without writing any of them. Array, Hash, Range, Struct, Set, Dir, IO and Enumerator all use it, and so does the shelf Catalog built in this reference. This page explains the contract between each and the module, shows every method family with output that was produced by running the code, covers the points where block parameters and return values surprise people, and explains why an iterator is almost always a better choice than a for or while loop.

Enumerators that wrap each (external iteration with next, Enumerator.new, Enumerator::Lazy, Enumerator::Chain, Enumerator.produce and ArithmeticSequence) are the subject of Enumerators and Lazy Evaluation; this page only shows how a block-less call returns one. Blocks themselves, yield, break, next and the it parameter are described in Blocks, Procs and Lambdas, the loop and case syntax in Control Expressions, and include and the ancestor chain in Modules and Mixins. The collection classes are in Arrays, Hashes, Ranges, Sets and Struct, Data and Value Objects. The <=> operator that sort, min and max depend on is covered in Equality, Hashing and Comparison, and case/in over the results in Pattern Matching. For the same ideas in other languages, see Rust iterators and Go iterators and range-over-func.

Every example was syntax-checked with ruby -wc, run with ruby -w on Ruby 4.0.7 and linted with RuboCop 1.92 using the configuration of the running shelf gem (target Ruby 4.0, double-quoted strings, NewCops: enable). The values after # => are the real results, written in the Ruby 3.4+ inspect format ({"a" => 1}, {name: "Ico"}), and a comment starting with # prints: or # | is real standard output. The module and the each protocol

Enumerable is an ordinary module with one requirement: the object that includes it must define each, and each must yield the elements one at a time. Almost every other method is written in terms of each: map calls each and collects what the block returns, first(3) calls each and stops after the third element, include? calls each and stops at the first match. The module does not know or care how the elements are produced. They may live in an array, be read from a file, come from a database cursor or be computed on demand, and the same sixty-one methods work on all of them.

The methods that rank or compare elements (sort, min, max, minmax and their _by variants without a custom block) additionally need the elements to respond to <=>; that is a requirement on the elements, not on the collection, and it is described under Sorting and extremes.

The next file uses the real shelf Catalog, which is a class with an each that iterates over a snapshot of its store (taken while holding a Thread::Mutex) and an include Enumerable. Note that it is a collection of Book values, and that no map, sort_by, count, first or include? is defined in the library: they all come from the module. Catalog does not respond to size either, because Enumerable has no size or length; count walks the elements.

Writing a correct each

A good each follows five rules, all of them visible in the real Catalog#each:

  1. Yield every element, and return self when a block is given. Callers chain on the result, and Array#each, Hash#each and Range#each all return the receiver. each_slice and each_cons return the receiver since Ruby 3.1 (they returned nil in Ruby 3.0).

  2. Return an Enumerator when no block is given, with return to_enum(:each) unless block_given? or enum_for. Without it each raises LocalJumpError ("no block given (yield)") as soon as someone calls map without a block, each_slice or lazy on the object. An optional block after to_enum(:each) computes the enumerator’s size; without it size is nil.

  3. Forward the block with an anonymous & (Ruby 3.1) when the elements come from another enumerable: @store.all.each(&) passes the caller’s block straight through, whatever its arity.

  4. Yield one value per element, or a deliberate pair. yield a, b is not the same as yield [a, b]: see Yielding several values.

  5. Do not mutate the collection while iterating and, if other threads may add elements, iterate over a snapshot as Catalog does (the lock is held only while the snapshot is taken, never while the caller’s block runs).

Methods that need every element (sort, sort_by, min, max, sum, cycle, reverse_each, to_a) call each to completion, and sort, cycle and reverse_each also buffer the result, so an each that never ends makes them hang. Methods that stop early (first, take, take_while, find, include?, any?, all?, none?, each_slice(n).first, lazy.first) are safe on an endless each.

Yielding several values

If each yields two values, Enumerable methods that collect elements pack them into an Array, while methods that pass the element to your block split or take the first value depending on the block’s parameters. each_entry is the variant that always passes exactly one object to its block: several yielded values arrive as one Array. Hash#each yields one two-element Array, so a Hash behaves like the packed case.

# frozen_string_literal: true

module Shelf
  # Shelf sections with a book count, yielding two values per step.
  class Sections
    include Enumerable

    def initialize(**counts)
      @counts = counts
    end

    # Yields (name, count). Returns self with a block, an Enumerator without.
    def each
      return to_enum(:each) { @counts.size } unless block_given?

      # Two values per step, on purpose: not one packed pair.
      @counts.each { |name, count| yield name, count } # rubocop:disable Style/ExplicitBlockArgument
      self
    end
  end
end

sections = Shelf::Sections.new(fiction: 12, science: 7, history: 3)

sections.to_a # => [[:fiction, 12], [:science, 7], [:history, 3]]
sections.map { |name, count| "#{name}=#{count}" } # => ["fiction=12", "science=7", "history=3"]
sections.map { |pair| pair } # => [:fiction, :science, :history]
sections.each_entry.to_a # => [[:fiction, 12], [:science, 7], [:history, 3]]
sections.first # => [:fiction, 12]
sections.min_by { |_name, count| count } # => [:history, 3]
sections.sort_by { |_name, count| -count }.first(2) # => [[:fiction, 12], [:science, 7]]
sections.each.size # => 3

sections.include?([:fiction, 12]) # => true

Source: Ruby 4.0 documentation: Enumerable#each_entry

The pair-per-step results show three rules at once. to_a, first, min_by, to_h and each_slice see the packed pair; map { |name, count| } destructures it, and map { |pair| } receives only the first yielded value. Do not rely on the last behaviour: when an each yields several values, document it, and prefer yield [a, b] so that the single-parameter form also receives both.

What goes wrong without a proper each

# frozen_string_literal: true

module Demo
  # Enumerable calls each on the including object; without one, nothing works.
  class Hollow
    include Enumerable
  end

  # An each that always yields fails when it is called without a block.
  class Eager
    include Enumerable

    def each
      yield 1
      yield 2
    end
  end

  # An endless each is fine as long as the caller stops early.
  class Counter
    include Enumerable

    def each
      return to_enum(:each) unless block_given?

      n = 0
      loop { yield(n += 1) }
    end
  end
end

begin
  Demo::Hollow.new.map { |x| x }
rescue NoMethodError => e
  e.message # => "undefined method 'each' for an instance of Demo::Hollow"
end

Demo::Eager.new.map { |x| x * 2 } # => [2, 4]
begin
  Demo::Eager.new.each
rescue LocalJumpError => e
  e.message # => "no block given (yield)"
end

Demo::Counter.new.first(3) # => [1, 2, 3]
Demo::Counter.new.lazy.select(&:even?).first(2) # => [2, 4]
Demo::Counter.new.each_slice(2).first # => [1, 2]
Demo::Counter.new.take_while { |n| n < 4 } # => [1, 2, 3]
Demo::Counter.new.each.next # => 1

Source: Ruby 4.0 documentation: Enumerable usage

The three failures are the three rules above. A class that includes Enumerable without each raises NoMethodError the first time any module method runs, an each that yields without checking block_given? raises LocalJumpError when called bare, and an endless each is fine for first, take_while, lazy and each_slice(2).first, which stop pulling elements as soon as they have enough.

Transforming: map, flat_map, filter_map, zip, to_h

map (alias collect) returns an Array of the block’s results, always the same size as the input. flat_map (alias collect_concat) concatenates the block’s Array results one level deep, so it is map followed by flatten(1), and filter_map (Ruby 2.7) is map that drops falsy results, replacing the idiom map { }.compact or select { }.map { }. each_with_index, each_with_object and with_index supply positions and a memo object, zip walks several enumerables in step (padding with nil when the arguments are shorter and returning nil when given a block), and to_h with a block (Ruby 2.6) builds a Hash from [key, value] pairs. compact (Ruby 3.1) removes nil, uniq (Ruby 2.4) removes duplicates by eql? and hash, or by the value the block returns.

# frozen_string_literal: true

titles = ["Ruby Basics", "Iterators", "Blocks and Procs"]

titles.map(&:length) # => [11, 9, 16]
titles.collect { |t| t.split.first } # => ["Ruby", "Iterators", "Blocks"]
titles.flat_map(&:split) # => ["Ruby", "Basics", "Iterators", "Blocks", "and", "Procs"]
titles.map(&:split) # => [["Ruby", "Basics"], ["Iterators"], ["Blocks", "and", "Procs"]]
titles.flat_map { |t| [t.split] } # => [["Ruby", "Basics"], ["Iterators"], ["Blocks", "and", "Procs"]]
titles.filter_map { |t| t.split.first if t.size > 12 } # => ["Blocks"]
titles.each_with_index.map { |t, i| "#{i}: #{t}" } # => ["0: Ruby Basics", "1: Iterators", "2: Blocks and Procs"]
titles.each.with_index(1).map { |t, i| "#{i}. #{t[0, 4]}" } # => ["1. Ruby", "2. Iter", "3. Bloc"]
titles.each_with_object(Hash.new(0)) { |t, memo| memo[t.size.odd?] += 1 } # => {true => 2, false => 1}
titles.zip([1, 2, 3], %w[a b c]) # => [["Ruby Basics", 1, "a"], ["Iterators", 2, "b"], ["Blocks and Procs", 3, "c"]]
titles.zip([1]) # => [["Ruby Basics", 1], ["Iterators", nil], ["Blocks and Procs", nil]]
titles.zip([1, 2, 3]) { |_pair| nil } # => nil
titles.to_h { |t| [t.split.first, t.size] } # => {"Ruby" => 11, "Iterators" => 9, "Blocks" => 16}
titles.each_entry.to_a # => ["Ruby Basics", "Iterators", "Blocks and Procs"]
[3, 1, 3, nil, 2, nil, 1].compact # => [3, 1, 3, 2, 1]
[3, 1, 3, 2, 1].uniq # => [3, 1, 2]
titles.uniq { |t| t.size.odd? } # => ["Ruby Basics", "Blocks and Procs"]
titles.to_set.size # => 3
titles.entries # => ["Ruby Basics", "Iterators", "Blocks and Procs"]
titles.cycle.first(4) # => ["Ruby Basics", "Iterators", "Blocks and Procs", "Ruby Basics"]
titles.chain(%w[extra]).to_a # => ["Ruby Basics", "Iterators", "Blocks and Procs", "extra"]
(titles.each + %w[extra]).class # => Enumerator::Chain

Source: Ruby 4.0 documentation: Enumerable#flat_map

Two details deserve attention. flat_map flattens only one level: a block that returns [t.split] leaves the inner Array in place, and titles.map(&:split) and titles.flat_map { |t| [t.split] } are identical. And each.with_index(1) starts counting at one, which is clearer than adding one inside the block. Enumerable#each_entry and entries are rarely needed in application code; they exist so that code can turn any enumerable, whatever it yields, into an Array of its elements.

Searching and filtering

select (aliases filter, since Ruby 2.6, and find_all) keeps the elements for which the block is truthy; reject keeps the others; partition returns both groups in one pass. find (alias detect) returns the first match and stops, and takes an optional callable that is invoked, and its result returned, when nothing matches. find_index returns the position of the first match (or of the first element == to the argument), first, take and drop cut by position, and take_while and drop_while cut by a condition that is checked until it first fails. count counts everything, equal elements or matching elements. include? (alias member?) tests equality with ==.

grep and grep_v select with the case-equality operator ===, so they accept classes, ranges and regular expressions, and grep takes a block that transforms what it matched. Since Ruby 3.0 a block-less grep no longer sets $~, but with a block Regexp.last_match is still available inside the block.

# frozen_string_literal: true

titles = ["Ruby Basics", "Iterators", "Blocks and Procs", "ruby tips", "Pattern Matching"]

titles.select { |t| t.size > 10 } # => ["Ruby Basics", "Blocks and Procs", "Pattern Matching"]
titles.filter { |t| t.size > 10 } # => ["Ruby Basics", "Blocks and Procs", "Pattern Matching"]
titles.find_all { |t| t.size > 10 } # => ["Ruby Basics", "Blocks and Procs", "Pattern Matching"]
titles.reject { |t| t.downcase.start_with?("r") } # => ["Iterators", "Blocks and Procs", "Pattern Matching"]
titles.find { |t| t.start_with?("B") } # => "Blocks and Procs"
titles.detect { |t| t.start_with?("Z") } # => nil
titles.find(-> { "none" }) { |t| t.start_with?("Z") } # => "none"
titles.find_index { |t| t.include?("Procs") } # => 2
titles.find_index("Iterators") # => 1
titles.first # => "Ruby Basics"
titles.first(2) # => ["Ruby Basics", "Iterators"]
titles.take(2) # => ["Ruby Basics", "Iterators"]
titles.drop(3) # => ["ruby tips", "Pattern Matching"]
titles.take_while { |t| t.size > 9 } # => ["Ruby Basics"]
titles.drop_while { |t| t.size > 9 } # => ["Iterators", "Blocks and Procs", "ruby tips", "Pattern Matching"]
titles.partition { |t| t.match?(/\A[A-Z]/) }.map(&:size) # => [4, 1]
titles.grep(/ruby/i) # => ["Ruby Basics", "ruby tips"]
titles.grep(/(\w+) tips/) { Regexp.last_match(1) } # => ["ruby"]
titles.grep_v(/ruby/i) # => ["Iterators", "Blocks and Procs", "Pattern Matching"]
titles.grep(10..12) # => []
titles.map(&:size).grep(10..12) # => [11]
titles.map(&:size).grep_v(Integer) # => []
titles.count # => 5
titles.count("Iterators") # => 1
titles.count { |t| t.size.even? } # => 2
titles.include?("ruby tips") # => true
titles.member?("nothing") # => false

Source: Ruby 4.0 documentation: Enumerable#grep

titles.grep(10..12) returned [] because (10..12) === "Ruby Basics" is false: grep uses === of the argument on each element, so a range matches numbers, not their string lengths. The last two lines show the correct form on the sizes.

Array#find is a native method since Ruby 4.0 (it is faster than the inherited Enumerable#find and has the same semantics), and Ruby 4.0 also adds Array#rfind, which replaces reverse_each.find. On any other enumerable find is still the module’s. The same holds for first, take, min, sum, uniq and the other methods listed as overridden in the earlier table.

Predicates: all?, any?, none?, one?

The four predicates take a block, a pattern (Ruby 2.5) or nothing. With a pattern, an element matches when pattern === element; with nothing, an element matches when it is truthy. They short-circuit: any? stops at the first match, all? at the first failure, none? and one? as soon as the answer is known. On an empty collection all? and none? are true (vacuous truth) and any? and one? are false.

# frozen_string_literal: true

loans = [
  { title: "Ruby Basics", days: 3, state: :lent },
  { title: "Iterators", days: 20, state: :overdue },
  { title: "Blocks and Procs", days: 1, state: :returned }
]

loans.all? { |l| l[:days].positive? } # => true

Sorting and extremes

sort compares elements with <=> (or with a block that returns a negative number, zero or a positive number), sort_by computes a key for each element once and sorts by the keys, and min, max and minmax return the extremes. All three accept a count (max(2)) that returns an Array, and a block that replaces <=>. min_by, max_by and minmax_by extract a key per element like sort_by. sort_by evaluates the block once per element and compares the keys, so it is the right choice when the key is expensive; sort { |a, b| ... } calls the block for every comparison.

The documentation states that the ordering of equal elements is indeterminate for sort, sort_by, min, max and their variants, so none of them is guaranteed to be stable. When ties must keep their original order, add the position as a tie-breaker: sort_by.with_index { |x, i| [key(x), i] }. Sorting by several criteria is done by returning an Array as the key, and descending order by negating a numeric key (-t.size) or by reversing the comparison.

Comparing values that <=> cannot compare (it returns nil) raises ArgumentError with the message comparison of A with B failed. This is the most common error in this family: a nil among the keys, or a mix of Integers and Strings.

Reducing: inject, reduce and sum

inject (alias reduce) folds the elements into one value. It has four forms: a block (inject { |acc, x| ... }, where the first element is the initial accumulator), an initial value and a block, a method name as a Symbol (inject(:+)), and an initial value and a Symbol (inject(10, :+)). The block’s return value becomes the next accumulator, which is the cause of the most common bug with it. On an empty collection the block forms return the initial value or nil.

sum is a specialised inject(:+) that starts at 0 (or at the argument, which is required for anything that is not a number: %w[a b].sum("")), accepts a block, and, for Floats, uses Kahan-Babuska compensated summation, so it is more precise than a naive loop. Integer ranges are summed arithmetically without visiting the elements. Array#sum has existed since Ruby 2.4 and does not call each; Enumerable#sum calls it.

tally (Ruby 2.7) counts occurrences and returns a Hash; since Ruby 3.1 it accepts a Hash to add to. There is no tally_by in core Ruby (the example below shows the NoMethodError): count by a derived key with group_by then transform_values(&:size), or map then tally.

Grouping, chunking and slicing

These methods restructure a sequence. group_by returns a Hash from the block’s value to the Array of elements that produced it. partition splits into two Arrays. each_slice(n) produces non-overlapping groups of at most n elements (the last may be shorter), and each_cons(n) produces every run of n consecutive elements, overlapping. Both return the receiver when given a block (Ruby 3.1) and an Enumerator without one, and both raise ArgumentError ("invalid slice size") for 0.

The sequence-splitting methods return Enumerators, so call to_a, map or first on them:

  • chunk { |x| key } groups consecutive elements with the same key. A key of nil or :_separator drops the element and ends the chunk; a key of :_alone makes the element a chunk of its own; any other Symbol that starts with an underscore raises RuntimeError ("symbols beginning with an underscore are reserved").

  • chunk_while { |a, b| ... } keeps two neighbours in the same chunk while the block is true for them, and slice_when starts a new chunk when the block is true. They are complements: chunk_while { |a, b| b == a + 1 } and slice_when { |a, b| b != a + 1 } give the same runs.

  • slice_before(pattern or block) starts a new slice before a matching element, and slice_after ends the slice after one.

Choosing iterators over loops

Ruby has while, until, for and loop, but application code is overwhelmingly written with iterators, for four reasons.

  1. The iterator owns the bookkeeping. An index variable, an accumulator and an end condition are three places for an off-by-one error; each_with_index, sum and each_slice have none of them.

  2. Scope. The variable of a for loop is not local to it, so it leaks into the surrounding method, whereas a block parameter does not. A for loop is implemented with each, so it is not a faster alternative.

  3. A result. map, select and sum are expressions that produce the value, where a loop needs a variable that is initialised before it and mutated inside.

  4. A name for the intent. select, reject, partition and group_by say what is being done; a loop with an if makes the reader work it out.

Loops still have a place in algorithms that are not a traversal of a collection: a counter with a complex step, a loop that changes its own bounds (binary search, a two-pointer scan), or a state machine. For fixed counts, prefer times, upto, downto and step (on Integer, Float and ranges; Numeric#step and Range#step return an arithmetic sequence). loop is the idiomatic endless loop; it ends when the block raises StopIteration and returns the exception’s result, which is the enumerator’s result when you drive an external iterator with next.

And break value leaves the whole iterator and makes it return value, while next value only ends the current block call, the way return ends a method.

Extracting named methods from blocks

A block body longer than a line or two, or one that is reused, is easier to read and test as a method. &method(:name) turns a method into a block, a lambda stored in a constant can be passed with &, and a refactoring such as select(&method(:short?)) makes the call site read as a sentence. Name the predicate after the question it answers (overdue?, short?), and keep the iteration (select, map) in the caller.

Pitfalls

# frozen_string_literal: true

# Deleting from an array while iterating over it skips elements.
queue = %w[a b c d]
seen = []
queue.each do |item|
  seen << item
  queue.delete(item)
end
[seen, queue] # => [["a", "c"], ["b", "d"]]

# Iterate over a copy, or build a new collection instead.
queue = %w[a b c d]
queue.dup.each { |item| queue.delete(item) if item < "c" }
queue.size # => 2
%w[a b c d].reject { |item| item < "c" } # => ["c", "d"]

# A hash may not gain keys while it is iterated.
stock = { "Ruby Basics" => 3 }
begin
  stock.each { |title, n| stock["#{title} 2"] = n }
rescue RuntimeError => e
  [e.class, e.message] # => [RuntimeError, "can't add a new key into hash during iteration"]
end
stock.each_key { |title| stock.delete(title) }
stock.size # => 0

# Bad sizes, bad arguments and an accumulator that is not returned.
begin
  [1, 2, 3].first(-1)
rescue ArgumentError => e
  e.message # => "negative array size"
end

begin
  [1, 2, 3].each_slice(0)
rescue ArgumentError => e
  e.message # => "invalid slice size"
end

begin
  [1, 2, 3].zip(4)
rescue TypeError => e
  e.message # => "wrong argument type Integer (must respond to :each)"
end

begin
  [1, 2, 3].inject({}) { |acc, n| acc[n] = true } # rubocop:disable Lint/UnmodifiedReduceAccumulator
rescue NoMethodError => e
  e.message # => "undefined method '[]=' for true"
end

# The accumulator must be returned from inject's block, not from each_with_object's.
[1, 2, 3].each_with_object(Hash.new(0)) { |n, acc| acc[n.odd?] += n } # => {true => 4, false => 2}
[1, 2, 3].inject(Hash.new(0)) { |acc, n| acc.merge(n.odd? => acc[n.odd?] + n) } # => {true => 4, false => 2}

# first stops early; to_a and map on an endless range never return.
(1..).first(3) # => [1, 2, 3]
(1..).lazy.map { |n| n * 2 }.first(3) # => [2, 4, 6]
(1..).each_slice(2).first # => [1, 2]

# break leaves the whole iteration; next only the current block call.
[1, 2, 3, 4].each { |n| break n * 10 if n > 2 } # => 30
[1, 2, 3, 4].map { |n| n > 2 ? break : n } # => nil
[1, 2, 3, 4].select { |n| next true if n.odd? } # => [1, 3]

Source: Ruby 4.0 documentation: Hash

  • Mutation during iteration. Removing from an Array while iterating skips the element after each removal; iterate over a copy (dup) or build a new collection with reject/select. A Hash raises RuntimeError ("can’t add a new key into hash during iteration") if a key is added in each; deleting or updating existing keys is allowed.

  • The accumulator. inject needs the block to return the accumulator; each_with_object does not.

  • Endless sources. first, take, find, lazy and each_slice(n).first stop early; to_a, map, sort, sum, cycle without a count and reverse_each on an endless range never return.

  • break, next and return. break inside map ends the whole call and returns nil (or the value given to break); next ends the current block call only and supplies that element’s value; return inside a block returns from the enclosing method.

  • first versus take. Both return the leading elements; first without an argument returns one element (or nil), take(n) always returns an Array and raises ArgumentError ("attempt to take negative size") for a negative n.

  • Empty collections. min, max, min_by, inject without an initial value and first return nil; sum returns 0; all? and none? return true. State what you want in the code or pass an initial value.

  • Strings are not Enumerable. String#each_char, each_line and each_byte return enumerators, but a String does not include the module, so "abc".map is a NoMethodError; use chars.map or each_char.map.

The Iterator pattern and Comparable

The classic Iterator pattern, in which a collection exposes a way to walk its elements without exposing its structure, is include Enumerable plus each in Ruby. Internal iteration (each with a block) is the default; external iteration (next, peek, rewind on the enumerator returned by each) covers the cases where the caller needs to control the pace, such as merging two sequences. Comparable plus <=> on the element type is the matching pattern for ordering.

# frozen_string_literal: true

require "shelf"

def book(isbn, title, author) = Shelf::Book.new(Shelf::Isbn.new(isbn), title, Shelf::Author.new(author))

catalog = Shelf::Catalog.new
catalog.add(book("978-0-306-40615-7", "Ruby Basics", "A. Writer"))
       .add(book("978-1-234-56789-7", "Iterators in Depth", "B. Coder"))

# Catalog#each iterates over a snapshot, so adding while iterating is safe.
catalog.each { |b| catalog.add(b) if catalog.count < 4 }
catalog.count # => 4

# External iteration: the Iterator pattern, built into the language.
cursor = catalog.each
cursor.next.title # => "Ruby Basics"
cursor.peek.title # => "Iterators in Depth"
cursor.next.title # => "Iterators in Depth"
cursor.rewind.next.title # => "Ruby Basics"
begin
  loop { cursor.next }
  cursor.next
rescue StopIteration => e
  e.message # => "iteration reached an end"
end

# Enumerable gives the Iterator pattern lazy, chained, composable views.
catalog.lazy.map(&:title).select { |t| t.include?("Depth") }.first # => "Iterators in Depth"
catalog.each_slice(2).map { |pair| pair.map { |b| b.title[0, 4] } } # => [["Ruby", "Iter"], ["Ruby", "Iter"]]
catalog.each_with_index.to_h { |b, i| [i, b.isbn.to_s] }.values.first # => "9780306406157"

# Comparable on the element turns on sort, min, max and minmax.
Edition = Data.define(:title, :year) do
  include Comparable

  def <=>(other) = year <=> other.year
end

editions = [Edition.new("Ruby Basics", 2019), Edition.new("Iterators", 2021), Edition.new("Blocks", 2017)]
editions.min.title # => "Blocks"
editions.max.title # => "Iterators"
editions.sort.map(&:year) # => [2017, 2019, 2021]
editions.minmax.map(&:title) # => ["Blocks", "Iterators"]
editions.sort { |a, b| b <=> a }.map(&:year) # => [2021, 2019, 2017]
editions.first.between?(editions.last, editions[1]) # => true

Source: Ruby 4.0 documentation: Comparable

The message of StopIteration is "iteration reached an end", and loop rescues it. The Catalog snapshot is what keeps catalog.each { catalog.add(b) } from looping forever or raising: a naive each over a live Array would see the appended elements. Edition is declared with Data.define ... do include Comparable ... end (the current form; subclassing Data.define(...) with class X < Data.define creates an extra anonymous class in the ancestors).

Performance and laziness

An eager chain such as select { }.map { }.first(3) runs every stage over every element and builds an intermediate Array for each stage. Three techniques reduce that work, in this order of preference:

  1. Use the most specific method. find instead of select.first, any? instead of select.any?, count { } instead of select { }.size, filter_map instead of select { }.map { }, min_by instead of sort_by { }.first, sum { } instead of map { }.sum, each_slice instead of manual slicing.

  2. Stop early. first, take_while, find and any? do not evaluate the rest of the collection.

  3. Go lazy with lazy when the source is very large, endless, or each stage is expensive and only the first few results matter; then first(n) or take(n).to_a pulls only what is needed.

# frozen_string_literal: true

numbers = (1..1000).to_a
calls = Hash.new(0)

# An eager chain runs every stage over every element...
numbers.select { |n| calls[:select] += 1 and n.even? }
       .map { |n| calls[:map] += 1 and n * 2 }
       .first(3)
calls.dup # => {select: 1000, map: 500}

# ...a lazy chain pulls only as many elements as the result needs.
calls.clear
numbers.lazy
       .select { |n| calls[:select] += 1 and n.even? }
       .map { |n| calls[:map] += 1 and n * 2 }
       .first(3)
calls.dup # => {select: 6, map: 3}

# find and first stop at the first hit; select.first does not.
calls.clear
numbers.find { |n| calls[:find] += 1 and n > 2 } # => 3
numbers.select { |n| calls[:select] += 1 and n > 2 }.first # => 3
calls.dup # => {find: 3, select: 1000}

# An integer Range is summed arithmetically, without visiting its elements.
(1..(10**18)).sum # => 500000000000000000500000000000000000
(1..(10**18)).each_entry.first(2).sum # => 3

Source: Ruby 4.0 documentation: Enumerator::Lazy

The first block shows 1000 evaluations of select and 500 of map for the eager chain, and six and three for the lazy one, which pulls elements one at a time through all the stages until first(3) has its three results. Lazy evaluation has its own overhead, so on a small Array of cheap operations it can be slower than the eager chain; measure before changing, with the tools in Performance, Benchmarking and Profiling.

Where older material is outdated

Tutorials and books written for Ruby 2.x and early 3.x teach correct ideas about iteration but show some details that have since changed. When reading older code or text on this topic, note these differences:

use it (Ruby 3.4) for a single parameter; _1/_2 still work

undefined method `map' for nil:NilClass

hash output such as {:name=>"Ico"}

When a book builds an Iterator class with has_next? and next_item methods, replace it with each plus include Enumerable and, if external stepping is needed, with enum_for and Enumerator#next.

Design guidance

  • Prefer Enumerable methods over index-based loops, and the most specific method over a chain of general ones.

  • Give a collection class each first, then include Enumerable. Add <=> to the elements if they must sort.

  • Return an Enumerator from each when no block is given, with a size when it is cheap to compute.

  • Keep blocks to one or two lines and extract a named method when a block grows, is reused or needs a test.

  • Treat the empty case as part of the contract: pass an initial value to inject and sum when the element type is not Integer.

  • Use lazy for large or endless sources, each_slice for batching and each_cons for neighbours.

  • Do not mutate a collection while iterating over it; iterate a copy or build a new collection.

  • Remember which methods return what: Hash#select returns a Hash, Hash#map and Set#map return an Array.
