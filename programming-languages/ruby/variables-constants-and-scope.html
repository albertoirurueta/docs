Variables, Constants and Scope

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Ruby 4.0 (4.0.7, checked on 2026-10-18). It covers the five kinds of names a Ruby program can bind a value to: local variables, instance variables, class variables, global variables and constants. For each it explains where the name is visible, what an unset name evaluates to, how to inspect it at run time, and which mistakes show up in real code. The running scenario is the shelf library-catalogue gem used throughout this section. Features newer than Ruby 3.0 carry their version in the text, and the version table near the end collects them.

Every example was syntax-checked with ruby -wc, run with Ruby 4.0.7, and linted with RuboCop 1.92 using its default cops and TargetRubyVersion: 4.0. The output under each example is the real output of that run. A # rubocop:disable comment marks the few places where an example breaks a cop on purpose because the cop is what the page is explaining. Error messages use the Ruby 3.4 format ('name' with straight quotes and for main or for an instance of X).

The neighbouring pages build on this one: Assignment and Multiple Assignment covers the = operator itself, Blocks, Procs and Lambdas covers closures in depth, and Modules and Mixins covers what a module contributes to a lookup chain.

Local variables

A local variable name starts with a lower-case letter, an underscore or a non-ASCII character, and continues with letters, digits and underscores. By convention it is snake_case. A local variable is created by assigning to it; there is no declaration, no let, and no type. It stays visible for the rest of its scope and nothing outside that scope can see it.

The parse-time rule

Ruby decides whether a bare lower-case word is a variable or a method call when it parses the file, not when it runs the code. The first time the parser sees an assignment to a name, every later occurrence of that name in the same scope is a local-variable read, whether or not the assignment ever executes. Before that point, the word is a method call with no arguments and no receiver.

parse_time_local.rb
# frozen_string_literal: true

# A bare name is a method call until the parser has seen an assignment to it.
def title = 'from the method'

puts title # the method

on_loan = false
title = 'from the local' if on_loan # never assigned, but the parser saw it
p title # the local variable, which is nil

title = 'now assigned'
puts title
puts self.title # rubocop:disable Style/RedundantSelf
p local_variables
from the method
nil
now assigned
from the method
[:on_loan, :title]

Source: Assignment: Local Variables and Methods

Three consequences follow from the output:

  • title = '...' if on_loan never ran its assignment, yet title is now a local variable holding nil. The method title is shadowed for the rest of the scope. Call it with empty parentheses (title()) or with an explicit receiver (self.title) to reach the method again.

  • A modifier condition is evaluated first, but it is written second. p copies if (copies = 3).positive? fails with a NameError because the parser reaches p copies before it has seen the assignment (the non_gates.rb example later on this page prints the real message).

  • The classic trap big_calculation = big_calculation() is legal: the right-hand side is a method call because of the parentheses, and from then on the name is a local variable.

x ||= 10 is the same rule used on purpose: the parser sees the assignment, so x is a local variable (with value nil) by the time ||= reads it.

Scope gates

A scope gate is a construct that starts a new local-variable scope with no access to the enclosing one. Ruby has three keyword gates (def, class and module), plus the top level of each file. Everything else, blocks included, leaves the surrounding variables visible.

Constructs that open a new, isolated scope (a gate):

  • def: the method body sees none of the variables around the def;

  • class, module and class << obj: the body starts a fresh scope;

  • the top level of each file, including files loaded with require and load.

Constructs that do not isolate anything:

  • if, unless, case, while, until, for, begin, rescue and ensure open no scope at all;

  • a block ({ ... } or do ... end), a lambda written with ->, and the blocks given to define_method, Class.new, Module.new, Struct.new and Data.define open a nested scope: they can read and write the outer variables, and their own variables die with them;

  • a string passed to eval, instance_eval or class_eval is a nested scope too: it sees the caller’s locals, and the variables it creates stay private to it.

A gate cuts the scope off completely, and a block is the way to cross a gate on purpose.

scope_gates.rb
# frozen_string_literal: true

limit = 14

# def, class and module open a new scope: nothing outside is visible inside.
def days_allowed
  limit
rescue NameError => e
  e.message
end
puts days_allowed

# A block is a closure: it sees, and can change, the surrounding locals.
renewals = 0
3.times { renewals += 1 }
p renewals

# define_method takes a block, so it can capture a local from the class body.
class Reader
  max_books = 3
  define_method(:max_books) { max_books }
end
puts Reader.new.max_books

The if, while and begin family never opens a scope, so a variable first assigned inside them is visible after them. This is different from JavaScript’s let and from most C-family languages.

Blocks, closures and shadowing

A block sees the variables of the scope it was written in, and those variables live as long as any block still refers to them. Variables first assigned inside the block do not survive it.

blocks_and_shadowing.rb
# frozen_string_literal: true

# Variables first assigned inside a block disappear when it ends.
[1, 2].each { |n| puts n * 2 }
p defined?(n)

# for does not open a scope, so its variable leaks.
for i in 1..3 do end # rubocop:disable Style/For
p i

# A block-local variable (after the semicolon) shadows an outer one on purpose.
total = 100
[1, 2, 3].each do |n; total|
  total = n * 10
  puts total
end
p total

# A plain block parameter with the same name also shadows the outer variable.
name = :outer
[:inner].each { |name| puts name }
p name

# Implicit parameters: it (3.4) and _1 to _9 (2.7).
tens = [1, 2, 3].map { it * 10 }
sums = [[1, 2], [3, 4]].map { _1 + _2 }
p tens, sums

  • defined?(n) is nil after the first loop because the block parameter n exists only inside the block.

  • for i in 1..3 does not open a scope. i is still readable afterwards and holds 3. This is the main reason idiomatic Ruby prefers each; RuboCop’s Style/For flags it.

  • A block-local variable, declared after a semicolon in the parameter list (|n; total|), is a fresh variable that shadows the outer total and leaves it untouched. Use it when a block needs a scratch variable and the same name already exists outside.

  • A plain block parameter with the name of an outer variable also shadows it, and Ruby prints no warning for it any more (the old "shadowing outer local variable" warning was removed in 2.6). The outer name is unchanged afterwards, and the block’s name is a different variable.

  • it (Ruby 3.4) and _1 to _9 (Ruby 2.7) are implicit block parameters. it is the name of the only parameter; _1 and _2 are the first and second parameters of a block that takes several. Assigning to a numbered parameter is a SyntaxError since 3.0, and a block cannot mix numbered parameters with an ordinary parameter list. Ruby 4.0 stops Binding#local_variables from listing implicit parameters; Binding#implicit_parameters lists them instead.

See Blocks, Procs and Lambdas for the it and numbered-parameter rules in full.

Flat scopes and closures

Because blocks cross scope gates, Ruby code that needs to hand a local variable to a method body uses a flat scope: it replaces def with define_method, and class Name with Class.new do ... end. The block closes over the surrounding locals, and the closure holds the variable, not a copy of its value.

flat_scope.rb
# frozen_string_literal: true

prefix = '978'

# Class.new, Module.new and Data.define take blocks, so they can close over locals
# (the "flat scope" technique). A def inside would open a new scope and lose them.
Catalogued = Class.new do
  define_method(:catalogue_prefix) { prefix }

  def broken_prefix
    prefix
  rescue NameError => e
    e.message.lines.first.chomp
  end
end

item = Catalogued.new
p item.catalogue_prefix
p item.broken_prefix

prefix = '979' # the closure shares the variable, it does not copy it
p item.catalogue_prefix

# A lambda keeps its variables alive after the defining scope has ended.
def counter
  count = 0
  -> { count += 1 }
end

next_id = counter
next_id.call
p next_id.call
p next_id.binding.local_variables

Source: Module#define_method

broken_prefix is written with def, so it opens a new scope; prefix there is a method call, and since the class has no method of that name the error message names the receiver as an instance of Catalogued. After prefix = '979' the define_method body returns '979': the block shares the variable, so a later assignment is visible inside it. The lambda returned by counter keeps its own count alive after counter has returned, which is the usual way to build private mutable state without an object.

Unused variables and the underscore

Under -w, Ruby warns when a local variable is assigned and never read. The message names the variable, for example warning: assigned but unused variable - copies. A leading underscore (_copies, or just _) silences the warning, and the convention tells readers the value is deliberately ignored. A name that starts with an underscore is an ordinary variable otherwise: it can still be read, and it still appears in local_variables.

Inspecting scope: local_variables, Binding and eval

Kernel#local_variables lists the names visible in the current scope, including names the parser has seen but the program has not yet reached. Kernel#binding captures the current scope as a Binding object, which can read, write and evaluate code in it.

binding_locals.rb
# frozen_string_literal: true

# Binding exposes the locals of a scope as data.
def describe_scope(isbn)
  _copies = 2
  binding.local_variables.to_h { |name| [name, binding.local_variable_get(name)] }
end
p describe_scope('9780596516178')

# local_variable_set on a name the parser has not seen lives only in the binding.
scope = binding
scope.local_variable_set(:late, 1)
p scope.local_variable_get(:late)
p scope.local_variable_defined?(:late)
p defined?(late)
p scope.eval('late')

Source: Binding#local_variable_set

  • binding.local_variables lists names; local_variable_get reads a value, and local_variable_set writes one.

  • local_variable_set on a name the parser has not seen creates the variable only inside that Binding. The scope itself still treats late as a method call, so defined?(late) is nil; code evaluated through the binding (scope.eval('late')) does see it.

  • eval with a string is a nested scope of its own: assignments inside the string are not visible to the code around it, and two eval calls in the same scope do not see each other’s new variables. Instance variables

An instance variable begins with a single @ and belongs to one object. Any method of that object reads and writes it, including methods inherited from a superclass: there is no separate namespace per class, so a subclass and its superclass see the same @name. No other object sees it. Unlike Java or C#, Ruby has no declaration: the variable comes into existence the first time something assigns it, and different instances of one class may end up with different sets.

instance_variables.rb
# frozen_string_literal: true

# A library member who borrows titles.
class Reader
  attr_reader :name

  def initialize(name)
    @name = name
  end

  def borrow(title)
    @borrowed ||= []
    @borrowed << title
    self
  end

  def borrowed? = !@borrowed.nil?
end

ana = Reader.new('Ana')

ana.borrow('Dune').borrow('Emma')

p ana.instance_variable_get(:@borrowed)
p ana.instance_variable_defined?(:@name)

ana.instance_variable_set(:@vip, true) # any object accepts any ivar
p ana.instance_variables
p ana.remove_instance_variable(:@vip)
p ana.instance_variables

Points worth knowing:

  • An unset instance variable reads as nil. Before Ruby 3.0 that read printed a warning under -w; the warning was removed in 3.0, so code that relies on @x ||= [] or on @x.nil? is warning-free. It also means a typo such as @nmae is silently nil: tests catch it, the interpreter does not.

  • instance_variable_get(:@name), instance_variable_set, instance_variable_defined? and remove_instance_variable are the reflective API. The name must start with @: the string 'borrowed' raises NameError with 'borrowed' is not allowed as an instance variable name.

  • The default inspect (and so p) prints every instance variable. Ruby 4.0 lets a class narrow that output by defining a private instance_variables_to_inspect method that returns an array of names (see the example below).

  • Instance variables are private to the object: the only way another object reads them is through a method. attr_reader, attr_writer and attr_accessor generate those methods. See Classes and Objects and Visibility and Encapsulation.

  • Everything is an object, so self at the top level (main) can have instance variables, and so can a class or a module. @top_level_ivar above is nil because nothing assigned it. These are the "class-level instance variables" discussed in the next section.

  • Since Ruby 3.2 the VM represents the instance-variable layout of an object as a shape, which makes ivar access faster. Objects whose variables are assigned in a consistent order share a shape, so assign every variable in initialize, always in the same order, instead of adding new ones from random methods.

inspect_ivars.rb
# frozen_string_literal: true

# A reader with a private token that should stay out of inspect output.
class Account
  def initialize(name, token)
    @name = name
    @token = token
  end

  private

  def instance_variables_to_inspect = [:@name]
end

puts Account.new('ana', 'demo-token').inspect.sub(/0x\h+/, '0x0')
#<Account:0x0 @name="ana">

Source: Object#inspect

An object that has been frozen (freeze) refuses new assignments to its instance variables with a FrozenError; see Object Lifecycle, Freezing and Copying.

The setter pitfall

Inside a method, count = 5 always creates a local variable, even when the class has a count= writer. To call the writer, write self.count = 5. RuboCop’s Style/RedundantSelf leaves such a self. alone for that reason.

setter_pitfall.rb
# frozen_string_literal: true

# Setters need an explicit receiver: a bare assignment creates a local variable.
class Counter
  attr_accessor :count

  def initialize = @count = 0

  def wrong
    count = 5
    [count, @count]
  end

  def right
    self.count = 5
    [count, @count]
  end
end

counter = Counter.new
p counter.wrong
p counter.right
[5, 0]
[5, 5]

Source: Assignment: Assignment Methods

wrong returns [5, 0]: the local variable is 5 and the instance variable never changed. right goes through the attr_accessor setter. The same applies to compound assignment: pass:c[self.count += 1] is correct and pass:c[count += 1] creates a new local.

Source: Assignment: Instance Variables

Class variables

A class variable begins with @@. It is shared by the class that defines it, by every subclass and by every instance of any of them. Reading one that has not been set raises NameError (unlike instance variables, which are nil).

The example also sets up the preferred alternative: a class-level instance variable, written @count inside the class body. A class is an object, so it has its own instance variables, and the subclass Annex has its own @count.

class_variables.rb
# frozen_string_literal: true

# A branch library; @@opened is shared, @count is per class.
class Branch
  @@opened = 0 # rubocop:disable Style/ClassVars
  @count = 0

  class << self
    attr_accessor :count
  end

  def self.opened = @@opened

  def initialize
    @@opened += 1 # rubocop:disable Style/ClassVars
    self.class.count += 1
  end
end

# A smaller branch with its own counter.
class Annex < Branch
  @count = 0
end

The advice in most style guides is to prefer the class-level instance variable. A class variable is shared mutable state across an inheritance tree, which makes tests order-dependent and means that a library’s subclass can change the behaviour of its superclass.

Errors specific to class variables

Two rules were tightened in Ruby 3.0:

Accessing a class variable from the top level (outside any class or module body) is a RuntimeError for the same reason: the variable would be defined on Object and shared with every class in the program.

A constant is a name that begins with an upper-case letter, usually written SCREAMING_SNAKE_CASE for values and CamelCase for classes and modules. Lookup: lexical scope, then ancestors

A reference to a bare constant NAME is resolved in this order:

  1. The lexical scopes in Module.nesting, from the innermost outward, each searched for its own constants only (not its ancestors). The top-level Object is not part of this step.

  2. The ancestors of the innermost lexical scope (Module.nesting.first), in method-resolution order, including included modules and the superclass chain. For a class this reaches Object.

  3. If the innermost scope is a module (which has no Object among its ancestors), Object is searched too, so top-level constants stay visible.

  4. If nothing was found, Ruby calls const_missing(:NAME) on the innermost scope. The default raises NameError.

  • Module.nesting is [Lending] at the module level and [Lending::Book, Lending] inside Book. It lists the lexical scopes, innermost first.

  • Book#kind finds KIND in Lending (step 1) before it ever reaches Media::KIND (step 2, through the superclass). A nearer lexical definition beats an inherited one.

  • Book#days has no DAYS in Lending, so step 2 finds Media::DAYS through the ancestors, not the top-level DAYS.

The nested form (module Lending; class Dvd) and the compact form are not interchangeable when constants are involved. RuboCop’s Style/ClassAndModuleChildren prefers the nested form.

A constant reached through a mixin is an ancestor constant, so it is not seen from every lexical position:

mixin_lookup.rb
# frozen_string_literal: true

# Constants come from the lexical scope, then the ancestors, including mixins.
module Greeting
  WORD = 'hello'
end

# A class that mixes the module in and defines one constant of its own.
class Desk
  include Greeting

  OWN = 'own'

  def word = WORD

  class << self
    # Desk is in the lexical scope of the singleton class body.
    def own_word = OWN

    # Greeting is only an ancestor of Desk, and lexical lookup ignores ancestors.
    def mixin_word = WORD
  end
end

p Desk.new.word, Desk.own_word, Desk::WORD
begin
  Desk.mixin_word
rescue NameError => e
  puts e.message
end
p Desk.const_defined?(:WORD, false)
p Desk.constants.sort
"hello"
"own"
"hello"

false

Inside class << self, the lexical scope includes Desk (so OWN, defined directly in Desk, is found), but the ancestors searched are those of the singleton class, which does not include Greeting. Desk::WORD and the instance method word both work, since they search the ancestors of Desk. Desk.constants lists WORD because the inherited ones count, while const_defined?(:WORD, false) is false. When a mixin’s constant must be visible from class methods, qualify it (Greeting::WORD).

Qualified lookup and the top level

The :: operator looks a constant up in one specific module and its ancestors, skipping the lexical scopes. A leading :: starts at Object.

scoped_lookup.rb
# frozen_string_literal: true

DAYS = 'top level'

# A kind of lendable item.
class Media
  KIND = 'media'
end

# Items that can be lent.
module Lending
  # A book that can be lent.
  class Book < Media
  end
end

p Lending::Book::KIND # scoped lookup: Book, then its ancestors
p ::DAYS              # an explicit top-level constant
p Lending.const_get(:DAYS)
begin
  Lending.const_get(:DAYS, false) # inherit = false: only Lending itself
rescue NameError => e
  puts e.message
end

begin
  Lending::Book::String # scoped lookup does not fall back to Object
rescue NameError => e
  puts e.message
end
p Lending::Book.const_get(:String) # const_get does
p Lending::Book.const_get('Media::KIND')
"media"
"top level"
"top level"
uninitialized constant Lending::DAYS
uninitialized constant Lending::Book::String
String
"media"

Source: Module#const_get

  • Lending::Book::KIND finds Media::KIND through `Book’s ancestors.

  • ::DAYS names the top-level constant explicitly, which is useful when a nearer DAYS would otherwise win.

  • Lending.const_get(:DAYS) returns the top-level value, because const_get with inherit true checks Object for a module. With false it raises uninitialized constant Lending::DAYS.

  • A scoped reference such as Lending::Book::String does not fall back to Object; it raises NameError. Ruby 2.5 removed the old behaviour that returned top-level constants through a class path with a warning. Book.const_get(:String) still reaches it, because const_get follows Object by design.

  • const_get accepts a path as a string, 'Media::KIND', and walks it one segment at a time.

Top-level constants are defined on Object. Every class and every module (through step 3) can therefore see them, and a top-level class Policy is simply the constant Object::Policy. Keep application constants in a namespace so they do not collide with a gem’s constants.

Hiding and retiring constants

private_constant makes a constant unreachable with the Module::NAME syntax while leaving it usable by name inside the module. deprecate_constant keeps a constant working but makes references to it print a deprecation warning.

private_deprecated_constants.rb
# frozen_string_literal: true

# Item kinds known to the catalogue.
module Kinds
  BOOK = :book
  LEGACY_MAGAZINE = :magazine
  INTERNAL_CODES = %w[b m].freeze

  private_constant :INTERNAL_CODES
  deprecate_constant :LEGACY_MAGAZINE

  # Inside the module the private constant is an ordinary name.
  def self.codes = INTERNAL_CODES
end

p Kinds::LEGACY_MAGAZINE

  Kinds::INTERNAL_CODES
rescue NameError => e
  puts e.message
end

  • Kinds::INTERNAL_CODES raises NameError: private constant Kinds::INTERNAL_CODES referenced.

  end

That interaction can hide a mistake. If you define const_missing and also use private_constant, check that the hook re-raises with super for names it does not recognise.

const_missing, const_added and autoload

When lookup fails, const_missing(name) is called on the innermost scope. Its result becomes the value of the reference. Code loaders use it to load a file on demand and gems use it to generate constants.

const_missing_hook.rb
# frozen_string_literal: true

# Shelf codes resolved on demand: Codes::FICTION gives 'F', Codes::HISTORY gives 'H'.
module Codes
  # Called when a constant is not found anywhere in the lookup path.
  def self.const_missing(name)
    code = name.to_s[0]
    return super if code.nil? || name.to_s.length < 4

    const_set(name, code) # define it so const_missing runs only once
  end
end

p Codes::FICTION
p Codes.constants
begin
  Codes::X
rescue NameError => e
  puts e.message
end
"F"
[:FICTION]
uninitialized constant Codes::X

Source: Module#const_missing

const_set inside the hook defines the constant so the hook runs only once per name. return super for names the hook does not handle keeps the standard NameError. A const_missing that returns a value without defining the constant runs again for every reference, and one that hides typos by returning a default makes failures harder to find; use it with care. The standard, declarative alternative is Module#autoload (and, for whole applications, a code loader such as Zeitwerk), covered in Code Loading: require and autoload.

Module#const_added (Ruby 3.2) is the opposite hook: it runs each time a constant is defined, including constants that name nested classes and modules.

const_added_hook.rb
# frozen_string_literal: true

# Module#const_added (3.2) runs every time a constant is defined.
class Registry
  def self.const_added(name)
    super
    puts "defined #{self}::#{name}"
  end

  LIMIT = 3

  # A nested class is a constant too.
  class Entry; end
end

p Ruby::VERSION == RUBY_VERSION

defined Registry::Entry

Define const_added before the constants it should observe, and call super. The hook gives registries, DSLs and documentation tools a supported alternative to polling constants.
