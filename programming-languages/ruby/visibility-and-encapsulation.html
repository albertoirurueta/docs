Visibility and Encapsulation

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Ruby 4.0 (4.0.7, checked on 2026-10-18); features newer than Ruby 3.0 name the version that introduced them. Encapsulation is the practice of exposing a small, deliberate interface and keeping everything else free to change. Ruby supports it with three method visibilities (public, protected and private), a separate visibility for constants (private_constant), and a handful of conventions around them. Unlike Java, C# or Swift, none of this is a security boundary: visibility is a rule about how a method is called, it is checked when the call happens, and reflection can step around it on purpose. This page covers the rules exactly, the syntax that sets them (and what each form returns), the traps in the scope of the private mode switch, class-level and constant visibility, module_function, top-level methods, the ways round the rules, the reflection queries, and how to design a narrow public surface that stays easy to refactor.

It builds on Classes and Objects (instance variables, attr_*, initialize), Methods and Parameters (what def returns) and Modules and Mixins. The lookup rules that decide which method is found are in Method Lookup and super, class-level methods in Singleton Classes and Class-Level Behavior, and the reflection that bypasses visibility in Dynamic Dispatch and Method Definition and Reflection, Introspection and Tracing. Refinements, the controlled alternative to monkey patching, are in Refinements and Monkey Patching; immutable value objects, which need far less hiding, are in Struct, Data and Value Objects. Design advice continues in Idioms, Style and Clean Code and SOLID and Design Patterns. For how other languages control access, see Java, C#, Kotlin, Swift access control, PHP visibility, Rust modules and visibility and Python (which has only naming conventions).

Encapsulation in Ruby

What is hidden, and what is not

Ruby has no package, internal, friend or final keyword and no per-file privacy. What it has is a small set of mechanisms, each with a different reach:

  • Instance variables are always private to the object. There is no syntax for reading obj.@name from outside, so the only way to expose state is a method: attr_reader, attr_writer, attr_accessor, or one you write.

  • Methods are public by default and can be made protected or private. The visibility belongs to the method entry in a class or module, not to the name.

  • Constants are public by default and can be hidden from scoped lookup (Mod::NAME) with private_constant.

  • Local variables are visible only in their lexical scope; blocks and define_method bodies capture them, which makes closures the strongest hiding mechanism Ruby has (see Real information hiding).

The consequence is that "private" in Ruby describes the interface of an object: which messages other objects are meant to send it. The guard exists to stop accidents and to document intent, and it is checked against the form of the call (the receiver), never against the identity of the caller’s class, with one exception, protected.

The three visibilities

Visibility Who may call it Typical use

public

Anyone, with any receiver. The default for methods defined with def.

The contract: the messages callers are meant to send.

protected

A method call whose receiver is explicit, when the caller’s self is an instance of the class or module that owns the method (subclass instances included).

Comparison operators and similar methods that need the other object’s internals without making them public.

private

A method call with no explicit receiver, or with the literal self as receiver (Ruby 2.7 and later). Never other.method, even for another instance of the same class.

Helpers, steps of an algorithm, template-method hooks, setters used internally.

The next figure is the complete decision for a call written as receiver.name(args). Reflective calls (send, __send__, Method#call, instance_eval and friends) skip the visibility check, which is why the rules are advisory.

flowchart TD S(["receiver.name(args)"]) --> L{"method found in the receiver's ancestors?"} L -->|no| MM["method_missing runs; by default it raises NoMethodError: undefined method"] L -->|yes| V{"visibility of the method found"} V -->|public| OK(["method runs"]) V -->|private| R{"receiver omitted, or the literal self?"} R -->|yes| OK R -->|no| MM2["method_missing runs; by default it raises NoMethodError: private method called"] V -->|protected| P{"is the caller's self a kind_of? the owner of the method?"} P -->|yes| OK P -->|no| MM3["method_missing runs; by default it raises NoMethodError: protected method called"] RF["send, __send__, Method#call, instance_eval, bind_call"] -.->|skips the check| OK

Three details in the figure matter in practice. The check is made against the method that lookup finds first, so a private method in a subclass hides a public method of the same name in the parent. A failed check goes through method_missing, which is how a catch-all method_missing can accidentally answer for a private method (shown in the NoMethodError example below). And the check happens at call time: you can define a method that calls a private method wrongly, and nothing complains until it runs.

A first complete example

A Member of the library has a small public interface (borrow, books, owes_more_than?), a protected reader that only other members may use, and a private guard method. The class diagram uses the UML markers for the three levels (+ public, # protected, - private).

classDiagram class Member { +name +borrow(book) +books() +owes_more_than(other) #fines_cents() -ensure_below_limit() }
# frozen_string_literal: true

require "shelf"

module Shelf
  # A library member: the public API is small, the details are hidden.
  class Member
    LIMIT = 2

    attr_reader :name

    def initialize(name, fines_cents: 0)
      @name = name
      @fines_cents = fines_cents
      @books = []
    end

    # Public: part of the contract with callers.
    def borrow(book)
      ensure_below_limit
      @books << book
      self
    end

    def books = @books.dup

    # Callable on another Member, because the caller is a Member too.
    def owes_more_than?(other) = fines_cents > other.fines_cents

    protected

    attr_reader :fines_cents

    private

    def ensure_below_limit
      raise Shelf::Error, "#{name} has reached the limit of #{LIMIT} books" if @books.size >= LIMIT
    end
  end
end

author = Shelf::Author.new("Ursula K. Le Guin")
book = Shelf::Book.new(isbn: Shelf::Isbn.new("978-0-306-40615-7"), title: "The Dispossessed", author:)
ana = Shelf::Member.new("Ana", fines_cents: 250)
ben = Shelf::Member.new("Ben")

ana.borrow(book).books.size # => 1
ana.owes_more_than?(ben) # => true

begin
  ana.fines_cents
rescue NoMethodError => e
  e.message # => "protected method 'fines_cents' called for an instance of Shelf::Member"
end

begin
  ana.ensure_below_limit
rescue NoMethodError => e
  e.message # => "private method 'ensure_below_limit' called for an instance of Shelf::Member"
end

begin
  ana.borrow(book).borrow(book)
rescue Shelf::Error => e
  e.message # => "Ana has reached the limit of 2 books"
end

Source: Ruby 4.0 documentation: Modules and Classes, Visibility

Notice what the example relies on. books returns a copy (dup), so callers cannot mutate the internal Array through the reader: hiding the variable is not enough if a method hands out the object. LIMIT is an ordinary public constant, and the private keyword above ensure_below_limit does not affect constants (see Constants: private_constant, public_constant and deprecate_constant).

public: the default, and the methods Ruby makes private for you

A method defined with def is public unless the surrounding class body has switched mode (see Choosing a visibility: the four syntactic forms). public with names re-publishes methods, and public with no arguments switches the mode back after a private or protected section. A public method is a promise: anything that can be called from outside will eventually be called from outside, and removing it later is a breaking change.

Five method names are an exception. initialize, initialize_copy, initialize_clone, initialize_dup and respond_to_missing? are always private, however they are written and wherever the mode switch stands. They are hooks that the runtime calls (new calls initialize, dup calls initialize_dup and then initialize_copy), and calling them directly would corrupt an object’s state or bypass the protocol. Most of the infrastructure that Ruby gives every object is private for the same reason: Kernel#puts, format, raise, require and Integer() are private instance methods of Kernel, so "text".puts is a NoMethodError, while puts "text" works from anywhere because it has no receiver.

# frozen_string_literal: true

require "shelf"

module Shelf
  # A receipt printed when a book is returned.
  class Receipt
    # No access modifier anywhere: Ruby makes these hooks private by itself.
    def initialize(book) = @book = book

    def initialize_copy(source)
      super
      @book = source.instance_variable_get(:@book)
    end

    def respond_to_missing?(name, include_private = false) = name == :total || super

    def to_s = "Receipt for #{@book.title}"
  end
end

Shelf::Receipt.public_instance_methods(false).sort # => [:to_s]

The same listing shows the other side of the rule: BasicObject itself defines private hooks (initialize, method_missing, singleton_method_added and two more), which is why you override method_missing as a private method by convention even though a public one also works (a public method_missing lets callers invoke it directly).

private

The rule: no explicit receiver

A private method can be called only in the function-call form, name(args) or just name, where the receiver is implicitly self. The consequence that surprises programmers from Java and C# is that private is per call form, not per class: another instance of the same class is still "someone else", so other.balance fails even inside Account. Ruby’s protected exists for exactly that case.

# frozen_string_literal: true

require "shelf"

module Shelf
  # Private is a rule about the call site, not about the object: a second
  # Account cannot use the first one's private methods.
  class Account
    def initialize(cents) = @cents = cents

    def same_balance_as?(other) = balance == other.balance

    private

    def balance = @cents
  end

  # A catch-all that also answers for names that exist but are private.
  class Forgiving
    def method_missing(name, *args)
      name.start_with?("fetch_") ? "ghost #{name} #{args.inspect}" : super
    end

    def respond_to_missing?(name, include_private = false) = name.start_with?("fetch_") || super

    private

    def fetch_title = "real private method"
  end
end

mine = Shelf::Account.new(500)
begin
  mine.same_balance_as?(Shelf::Account.new(500))
rescue NoMethodError => e
  [e.name, e.receiver.class, e.args, e.private_call?] # => [:balance, Shelf::Account, [], false]
  e.message # => "private method 'balance' called for an instance of Shelf::Account"
end

begin
  mine.instance_eval { missing_helper(1) }
rescue NoMethodError => e
  [e.private_call?, e.message] # => [true, "undefined method 'missing_helper' for an instance of Shelf::Account"]
end

forgiving = Shelf::Forgiving.new
forgiving.fetch_title # => "ghost fetch_title []"
forgiving.send(:fetch_title) # => "real private method"
forgiving.fetch_author # => "ghost fetch_author []"
forgiving.respond_to?(:fetch_title) # => true

begin
  forgiving.other
rescue NoMethodError => e
  e.message # => "undefined method 'other' for an instance of Shelf::Forgiving"
end

Source: Ruby 4.0 documentation: NoMethodError

NoMethodError carries the details: name is the method, receiver the object, args the arguments given, and private_call? tells how the call was written, which is true only for a function-style call (no receiver) that failed, not for a private method called with an explicit receiver. That is why the first handler printed false. The second part of the example shows the interaction with method_missing: a failed visibility check dispatches to method_missing like any unknown name, so a catch-all that answers every name starting with fetch_ also answers for the private fetch_title. send finds the real private method because it skips the check and never reaches method_missing. Guard such handlers with a narrow pattern, call super for everything else (as the example does), and keep respond_to_missing? consistent.

The literal self exception (Ruby 2.7)

Before Ruby 2.7 the only private methods that could be called with self. in front were setters (self.position = 1), because the assignment syntax needs an explicit receiver. Since Ruby 2.7 any private method can be called with the literal self as receiver, which is why self.advance_position is no longer an error. The rule is syntactic: it applies to the keyword self written directly as the receiver. A variable that holds the same object, a parenthesised (self), and a method that returns self do not qualify. The scope operator form self::name and the safe navigation form self&.name are parsed with a literal self and are accepted.

# frozen_string_literal: true

require "shelf"

module Shelf
  # A reservation queue position; the setter is private.
  class Hold
    attr_reader :title

    def initialize(title, position)
      @title = title
      self.position = position
    end

    def advance
      self.position -= 1
      self
    end

    def position_text = "#{title}: place #{position}"

    # Different ways of writing the receiver of a private call. RuboCop flags the
    # redundant forms, so its cops are switched off for this one method.
    # rubocop:disable Style/RedundantSelf, Style/ColonMethodCall, Lint/RedundantSafeNavigation
    # rubocop:disable Style/RedundantParentheses, Metrics/MethodLength
    def receivers
      me = self
      forms = {
        implicit: -> { position },
        literal_self: -> { self.position },
        scope_operator: -> { self::position },
        safe_navigation: -> { self&.position },
        parenthesised: -> { (self).position },
        through_variable: -> { me.position }
      }
      forms.transform_values do |form|
        form.call
      rescue NoMethodError => e
        e.message
      end
    end
    # rubocop:enable Style/RedundantSelf, Style/ColonMethodCall, Lint/RedundantSafeNavigation
    # rubocop:enable Style/RedundantParentheses, Metrics/MethodLength

    # A local variable shadows the private setter: it does NOT call position=.
    def reset_wrongly
      position = 0
      [position, self.position]
    end

    private

    attr_accessor :position
  end
end

hold = Shelf::Hold.new("Kindred", 3)
hold.advance.position_text # => "Kindred: place 2"
results = hold.receivers
results.values_at(:implicit, :literal_self, :scope_operator, :safe_navigation) # => [2, 2, 2, 2]
results[:parenthesised] # => "private method 'position' called for an instance of Shelf::Hold"
results[:through_variable] # => "private method 'position' called for an instance of Shelf::Hold"

begin
  hold.position
rescue NoMethodError => e
  e.message # => "private method 'position' called for an instance of Shelf::Hold"
end

begin
  hold.position = 1
rescue NoMethodError => e
  e.message # => "private method 'position=' called for an instance of Shelf::Hold"
end

hold.reset_wrongly # => [0, 2]
hold.position_text # => "Kindred: place 2"
hold.send(:position) # => 2

Source: Ruby 2.7.0 released: calling a private method with a literal self and Modules and Classes, Visibility

Two lessons come out of the example. First, a private writer needs the explicit self., both for self.position = x and for compound assignment, self.position -= 1, because without self the parser reads position = x as the creation of a local variable and never calls the writer; that is what reset_wrongly shows with its [0, 2] result. Second, RuboCop’s Style/RedundantSelf knows this and flags self. only where it is not required, which is why the demonstration of the redundant forms had to switch the cops off. In normal code the only self. you write is on a setter, on a call to a method that shares its name with a local variable, or on a method such as class whose name is also a keyword.

Private methods and inheritance

Since private looks only at the call form, a private method of a parent class is visible to every subclass: the subclass body calls fee_cents or helper without a receiver and it works. This is the opposite of Java and C++ (where private stops at the class boundary and protected is the inheritance level) and is why Ruby code is full of private methods that subclasses call and override. The rest of this page keeps it in mind: a private method is part of the protocol between a class and its subclasses, not a sealed detail.

protected

A protected method may be called with an explicit receiver, but only from code whose self is an instance of the class or module that defines the method. The official documentation puts the typical use plainly: protected visibility is most often applied to == and other comparison methods, where the author does not want to expose an object’s state to every caller but still needs to read it from another object of the same kind.

The check compares the caller’s self with the owner of the method, using kind_of?. That has three consequences, all shown in the next example:

  • Instances of different subclasses of the owner can call each other’s protected methods (a Student can read the rank of a Teacher when both inherit it from Patron).

  • A module’s methods run with the includer as self, so a module included into the owner can call the protected method (rank_of).

  • An unrelated class, such as Auditor, cannot, even if it holds a Patron.

# frozen_string_literal: true

require "shelf"

module Shelf
  # Members with a protected rank: comparable, but the rank is not public API.
  class Patron
    include Comparable

    attr_reader :name

    def initialize(name, loans_count)
      @name = name
      @loans_count = loans_count
    end

    def <=>(other) = other.is_a?(Patron) ? rank <=> other.rank : nil

    protected

    def rank = @loans_count
  end

  class Student < Patron; end
  class Teacher < Patron; end

  # Not a Patron: the same call is rejected.
  class Auditor
    def peek(patron) = patron.rank
  end

  # A module included into Patron: its methods run with a Patron as self.
  module Ranking
    def rank_of(other) = other.rank
  end
  Patron.include(Ranking)
end

ana = Shelf::Student.new("Ana", 4)
ben = Shelf::Teacher.new("Ben", 9)

[ana < ben, ben < ana] # => [true, false]
[ben, ana].min.name # => "Ana"
ana.between?(ana, ben) # => true
ana.rank_of(ben) # => 9

begin
  ana.rank
rescue NoMethodError => e
  e.message # => "protected method 'rank' called for an instance of Shelf::Student"
end

begin
  Shelf::Auditor.new.peek(ana)
rescue NoMethodError => e
  e.message # => "protected method 'rank' called for an instance of Shelf::Student"
end

method_name = :rank
begin
  ana.public_send(method_name)
rescue NoMethodError => e
  e.message # => "protected method 'rank' called for an instance of Shelf::Student"
end

ana.send(method_name) # => 4
ana.respond_to?(:rank) # => false
ana.respond_to?(:rank, true) # => true
Shelf::Patron.protected_instance_methods(false) # => [:rank]
Shelf::Patron.instance_methods(false).sort # => [:<=>, :name, :rank]

Source: Ruby 4.0 documentation: Modules and Classes, Visibility and Comparable

public_send honours protected as well as private, send does not, and respond_to? answers false for a protected method unless the second argument asks for private and protected methods too. protected_instance_methods lists protected names; instance_methods and methods include them, public_instance_methods and public_methods do not.

When is protected the right tool? It is useful when two objects of the same type must see each other’s internals, and no more. Most designs get along without it:

  • Value objects made with Data.define or Struct expose their members through public readers and compare by value, so there is nothing to protect (see Struct, Data and Value Objects).

  • A comparison can be built on a public to_h or a public key method (sort_key), which also works for callers that are not Patrons.

  • Where protected is used, keep the protected surface to one or two readers. Every protected method is reachable from every subclass instance and from every module that is later mixed in, which is a wider door than it looks.

The Comparable mix-in fits this pattern well: it needs only the public <=>, and the protected reader is read inside <=> where the caller’s self is a Patron. The protected detail never leaks into the public interface.

Choosing a visibility: the four syntactic forms

All the visibility methods live on Module (so they are available in every class and module body) and accept method names as Symbols or Strings. public, protected, private and module_function are private methods of Module, which is why they are written without a receiver inside the body, and why calling SomeClass.private(:name) from outside fails (see Changing visibility in subclasses and after the fact). private_class_method, public_class_method, private_constant and public_constant are public.

  • The mode switch: private (or protected, public) with no arguments. It changes the default visibility of every def that follows in the same class body, up to the end of the body, or until another switch.

  • Names after the definition: private :name, private :first, :second, private [:name] (an Array is accepted since Ruby 3.0). The methods must already exist or NameError is raised.

  • Inline: private def name ... end. This works because def returns the Symbol of the method it defines (since Ruby 2.1), and private then receives that Symbol. It reads well for a single method and is the standard way to protect a single endless method (private def helper = 1).

  • With attribute macros: private attr_reader :serial. Since Ruby 3.0 attr_reader, attr_writer, attr_accessor and attr return an Array of the Symbols they define, so they compose with every modifier.

Since Ruby 3.1 the modifiers also return something useful: with one argument the argument itself, with several arguments an Array of them, and with none, nil. Before 3.1 they returned nil in every case, which is why older code and older books treat the return value as meaningless.

Which form to use

The Ruby Style Guide asks you to assign proper visibility levels instead of leaving everything public, to indent the modifier as deep as the method definitions it governs, and to put a blank line before and after it. RuboCop enforces the indentation (Layout/AccessModifierIndentation) and the blank lines (Layout/EmptyLinesAroundAccessModifier). Which form the project uses is a style decision that Style/AccessModifierDeclarations encodes: its default EnforcedStyle: group wants the mode switch (private on a line of its own), and allows the symbol, attribute and alias forms by default (AllowModifiersOnSymbols, AllowModifiersOnAttrs, AllowModifiersOnAliasMethod). Setting it to inline makes private def the norm. Both are fine; mixing them in one class is the only wrong answer. The grouped form has the advantage of showing the public interface at the top of the file and the private tail below it, in the "stepdown" order: public methods first, then protected, then private, each private helper below the method that calls it first (the example of the Ruby Style Guide groups protected and private methods near the end of the class too).

The scope of the mode switch

The mode switch is lexically scoped to the class body (more exactly, to the current frame of the class definition), and it reaches less than people expect. The next example collects the cases.

# frozen_string_literal: true

module Shelf
  # What the `private` mode switch does and does not reach.
  class Scope
    LIMIT = 6

    def self.define_later(name, &) = define_method(name, &)

    private

    def plain_def = 1
    attr_reader :reader
    alias copy_of_plain plain_def
    define_method(:direct_define) { 3 }

    # A method that calls define_method does it from another scope: the new method is public.
    define_later(:indirect_define) { 4 }

    # Singleton methods defined with class << self have their own mode.
    class << self
      def singleton_default = 7

      private

      def singleton_hidden = 8
    end

    # A block given to Data.define has its own default visibility.
    Point = Data.define(:x) do
      def public_in_block = 9

      private

      def private_in_block = 10
    end
  end

  # Reopening the class starts again in public mode.
  class Scope
    def after_reopen = 11
  end
end

scope::Point.private_instance_methods(false) # => [:private_in_block]

Source: Ruby 4.0 documentation: Module#define_method and Module#private

What the example shows, point by point:

  • def and attr_* obey the mode, and alias copies the visibility of the original (here the alias is private because plain_def was private at the time). alias_method does the same.

  • define_method obeys the mode only when it is called directly in the class body (direct_define is private). A helper method that calls define_method (define_later) runs in a different frame, so the method it creates is public. When you generate methods in a loop or a hook, set the visibility explicitly with private name afterwards.

  • A class << self block starts its own scope in public mode, so singleton_hidden needs its own private there. A private above def self.name has no effect on the class method (see the cops below).

  • Constants are never affected by the mode switch (LIMIT was defined before it, but one defined after would be public too).

  • The block of Data.define, Struct.new and Class.new is a fresh class body with its own mode.

  • Reopening the class resets the mode to public: the private in the first class Scope does not carry over to the second.

Calling private without arguments inside a method (for example in a helper such as def self.setup; private; end) is unreliable, and Ruby warns about it: "calling private without arguments inside a method may not have the intended effect". Use the modifier directly in the class body, or pass names.

Changing visibility in subclasses and after the fact

Visibility is a property of the method entry, so a subclass can change what it inherits, and a private method takes part in dynamic dispatch like any other.

  • A private method is looked up and overridden like a public one. If a parent’s public run calls a private fee_cents, a subclass that defines its own fee_cents replaces it, which is the foundation of the template-method pattern (the parent defines the skeleton, the subclasses fill in private hooks). There is no final.

  • The same fact makes accidental overriding possible: a subclass that happens to define a method with the same name as one of the parent’s private helpers silently replaces it, and the parent’s code then calls the subclass method. Give helpers distinctive names, keep the inheritance hierarchy shallow, and prefer composition (see SOLID and Design Patterns).

  • An override is public unless it is marked otherwise, even if the parent’s method was private. Forgetting private in the override turns an implementation hook into public API.

  • private :name in a subclass for a method inherited from a parent creates a new entry that forwards to the parent’s implementation (super semantics) but is private. public :name does the opposite for a private method. In both cases instance_method(:name).owner is the subclass, and public_instance_methods(false) or private_instance_methods(false) lists the name.

  • Narrowing the visibility of an inherited public method breaks substitutability: code written against the parent type fails with NoMethodError on the subclass.

# frozen_string_literal: true

require "shelf"

module Shelf
  # A template method: `fee_cents` is a private hook that subclasses override.
  class Pricing
    def quote(days) = "#{format('%<euros>.2f', euros: days * fee_cents / 100.0)} EUR"

    def code = "BASE"

Class-level visibility

The mode switch never affects def self.name, so class methods have their own tools:

  • private_class_method :name makes class methods private, and accepts several names or an Array. It returns the module it was called on.

  • public_class_method :name reverses it, most commonly for new.

  • A class << self block with private inside it (or private def inside it) hides several singleton methods at once.

  • private_class_method def self.helper ... end works, because def returns a Symbol.

The classic use is the factory with a private constructor: private_class_method :new and a public factory method (from_isbn, for_book) that calls new from inside the class, where the receiver is implicit. The standard library’s Singleton module uses exactly this and adds instance.

Constants: private_constant, public_constant and deprecate_constant

Constants have their own visibility, set per name with private_constant, public_constant and deprecate_constant. The private keyword, the mode switch and private_class_method never apply to constants, which is why RuboCop’s Lint/UselessConstantScoping flags a constant written below a private line.

  • A private constant can be referenced by its bare name from inside the class, its subclasses and nested classes (the lexical and inheritance lookup works), but not with a scope: Limits::SECRET_SALT raises NameError ("private constant Shelf::Limits::SECRET_SALT referenced"). That is the mechanism for hiding helper classes and internal tables inside a namespace.

  • constants and const_defined?-style listings behave accordingly: constants omits private constants, and const_get ignores the restriction, which is the reflective back door.

  • public_constant reverses private_constant. Both return the module in Ruby 4.0, so they can be chained, but their return value is rarely used.

  • deprecate_constant keeps a constant working and prints a warning when it is referenced. The warning belongs to the :deprecated category, which has been off by default since Ruby 2.7.2, so it appears only with -w, -W:deprecated or Warning[:deprecated] = true. It is the supported way to retire a public constant over several releases.

# frozen_string_literal: true

module Shelf

module_function and extend self

A module is a bag of methods, and a bag of utility functions (no state, no instances) is the case where visibility needs special handling. module_function turns the methods it is applied to into module functions: a public singleton method on the module (Slug.for_title) and, at the same time, a private instance method (so a class that includes the module can call for_title without a receiver but does not expose it to its own callers). Like the other modifiers it has the mode form (everything below it), and the form with names (module_function :dashes), and it returns its arguments by the rules of Ruby 3.1. It exists only on modules, not on classes (Class undefines it).

    def squeeze(text) = text.gsub(/\A-+|-+\z/, "")

  module Dashes

Top-level methods and Kernel

A method defined with def at the top level of a script or in the irb console is not a function in the sense of other languages. It becomes a private instance method of Object, and since every class inherits from Object, every object can call it without a receiver. That is why banner("x") works from inside a method of a class that knows nothing about the script, and why "text".banner("x") is a NoMethodError: the method is private.

At the top level, self is a special object called main, which has its own public and private singleton methods (since Ruby 3.0 they also accept an Array of names). public def loud made the method callable on any receiver, so "quiet".loud("hey") worked: you have added a method to every object in the process, the most extreme form of monkey patching. The Ruby Style Guide’s advice for "global" helper methods is the opposite: if you really need them, add them to Kernel and keep them private, or better, put them in a module as module functions and include that module only where needed. A script with a handful of top-level helpers is fine; a library must never define any, because they leak into every object of the application that loads it.

rescue NameError => e

end

vault.instance_variable_set(:@opened, 100) # => 100

vault.opened # => 101

Shelf::Vault.class_eval { public :open_door }

# Constants: const_get ignores private_constant.
Shelf::Vault.const_get(:PIN).length # => 19

When going round the rule is legitimate

  • Tests and debugging. A debugger or an IRB session needs to look inside. For tests, prefer to exercise the public interface (see the design section below); reach a private method with send only as a last resort and never for protected state that the public interface already exposes.

  • Frameworks and metaprogramming. Serialization, dependency injection and DSL libraries use instance_variable_get, instance_eval and send as their building blocks (see Hooks, eval and DSLs).

  • Dynamic dispatch on a method name you control: send over a fixed table of known names is fine.

When it is dangerous

send and public_send on a user-supplied name are an injection point. With send, a request parameter such as "exit", "system" or "instance_eval" reaches private Kernel methods; even public_send exposes every public method of the receiver (delete, destroy, freeze). Always check the name against an allow-list first (see Security). The Ruby Style Guide and RuboCop’s Style/Send cop (disabled by default) prefer public_send precisely because it does not circumvent private and protected, and because a class that defines its own method named send (a mail-sending object, say) breaks plain send; use __send__ in that case.

In short: treat the rule as a contract with the reader of the code. A caller who uses send(:internal) takes responsibility for breakage in the next release.

Real information hiding

If the goal is to prevent access rather than to signal intent, private is the wrong tool. Four techniques give stronger guarantees:

  • Closures. A variable captured by a lambda is not an instance variable and cannot be listed by instance_variables. The Counter below keeps its count in a local variable of the factory; instance_variables lists only the @step that holds the lambda, and the only way to change the count is to call it.

  • Immutability. Freezing (freeze) stops mutation but not reading. Data.define objects are frozen and expose only their readers (see Object Lifecycle, Freezing and Copying).

  • Isolation. Ractors isolate objects between execution contexts, so a non-shareable object cannot be referenced directly from another Ractor (see Ractors). Process boundaries are stronger still.

  • Controlling what is printed. inspect, pp, error messages and logs print every instance variable, which is the usual way a token ends up in a log file. Ruby 4.0 lets Object#inspect ask a method named instance_variables_to_inspect which instance variables to show; define it private and return an Array of names (or nil for the default).

# frozen_string_literal: true

require "shelf"

module Shelf
  # Plain object: inspect, pp and error messages print every instance variable.
  class Session
    def initialize(user, token)
      @user = user
      @token = token
    end
  end

  # Ruby 4.0: a private instance_variables_to_inspect hook chooses what inspect shows.
  class QuietSession
    def initialize(user, token)
      @user = user
      @token = token
    end

    private

    def instance_variables_to_inspect = [:@user]
  end

  # State kept only in a closure: there is no instance variable to reach.
  class Counter
    def self.build
      count = 0
      new(-> { count += 1 })
    end

    def initialize(step) = @step = step

    def next = @step.call
  end
end

token = "fake-token"
open = Shelf::Session.new("ana", token)
open.inspect.sub(/0x\h+/, "0x0") # => "#<Shelf::Session:0x0 @user=\"ana\", @token=\"fake-token\">"
quiet = Shelf::QuietSession.new("ana", token)
quiet.inspect.sub(/0x\h+/, "0x0") # => "#<Shelf::QuietSession:0x0 @user=\"ana\">"

counter = Shelf::Counter.build
[counter.next, counter.next] # => [1, 2]
counter.instance_variables # => [:@step]

# Freezing protects against mutation, not against reading.
session = Shelf::Session.new("ben", token).freeze
session.frozen? # => true
session.instance_variable_get(:@user) # => "ben"

begin
  session.instance_variable_set(:@user, "eve")
rescue FrozenError => e
  e.message.include?("fake-token") # => true
end

begin
  quiet.freeze.instance_variable_set(:@user, "eve")
rescue FrozenError => e
  e.message.include?("fake-token") # => false
end

Source: Ruby 4.0 documentation: Object#inspect and NEWS for Ruby 4.0

The last two handlers show the other lesson: a FrozenError message is built with inspect, so a frozen object with a secret prints it in the exception message (and from there into logs and error trackers). Defining instance_variables_to_inspect fixes both the direct inspect and the message. The @token values in the example are made-up placeholders; real credentials belong in the environment or a secrets store, never in an object that gets inspected or logged (see Security).

Designing the public surface

The mechanics above support a few design habits. They follow the guidance of the object-oriented chapters of the books listed on the section landing page, restated for current Ruby.

  • Start narrow. Make methods private by default and widen them when a caller needs them. The direction matters: turning a private method public never breaks anyone, while turning a public method private breaks every caller. A useful trick when refactoring: make a suspicious public method private and run the tests. The NoMethodError list is the exact set of external callers.

  • Hide the variables, then hide the objects. Expose state with attr_reader, not attr_accessor, unless callers really set it, and make setters private when only the class mutates the field. Return copies or frozen values for mutable collections (books returned @books.dup).

  • Tell, do not ask. An object that exposes many readers invites callers to make decisions with its data. Put the behaviour that needs the data inside the object, and the callers need fewer public methods.

  • Order the file by call depth ("stepdown"): the public interface first, each private method below the first public method that uses it, so a reader goes from the contract down to the details.

  • Keep constructors passive. initialize should assign state and validate it, not read files or call services. Factory class methods (Isbn.parse, Barcode.for_book) with a private new make the construction path explicit.

  • Test through the public interface. If a private method seems to need its own tests, it is usually a class waiting to be extracted, with its own public interface (the refactoring approach of breaking up a large class in small, tested steps).

  • Do not use protected as a default for "private but visible to subclasses". In Ruby a private method is already visible to subclasses. protected is for other instances.

  • Prefer composition over deep inheritance when the private protocol between parent and child grows: every private method a subclass calls or overrides is coupling.

  • Document the boundary. YARD’s @api private tag and the # @!visibility private directive, and RDoc’s :nodoc:, keep internals out of the generated documentation (see Documentation with RDoc and YARD).

A narrow public interface in the shelf scenario looks like this. The LoanDesk has three public methods; every step of the checkout is a private method defined below the public one that calls it.

# frozen_string_literal: true

require "shelf"

module Shelf
  # A narrow public interface (checkout, receipt) over private steps, in stepdown order:
  # each private method sits below the first method that calls it.
  class LoanDesk
    Receipt = Data.define(:title, :due_day, :fee_cents)

    attr_reader :catalog

    def initialize(catalog: Catalog.new, today: 1)
      @catalog = catalog
      @today = today
      @lent = {}
    end

    def checkout(book, member: "guest")
      ensure_available(book)
      record_loan(book, member)
      receipt_for(book)
    end

    def lent?(book) = @lent.key?(book.isbn)

    private

    def ensure_available(book)
      raise Shelf::Error, "#{book.title} is already lent" if lent?(book)
    end

    def record_loan(book, member)
      @catalog.add(book)
      @lent[book.isbn] = member
    end

    def receipt_for(book) = Receipt.new(title: book.title, due_day: due_date, fee_cents: daily_fee_cents)

    def due_date = @today + Shelf.config.loan_days

    def daily_fee_cents = 10
  end
end

Retiring a public method

Making a published method private is a breaking change. Libraries that follow semantic versioning do it in two releases: first keep the method public and make it warn, then make it private in the next major release. Kernel#warn takes uplevel: (the caller’s file and line) and category: :deprecated, so the message points at the code that must change and is silent unless deprecation warnings are on.

# frozen_string_literal: true

require "shelf"
require "stringio"

module Shelf
  # Release 1.1: the old public method still works but warns. Release 2.0: it becomes private.
  class Inventory
    def initialize(books) = @books = books

    def total = @books.size

    def book_count
      warn "Inventory#book_count is deprecated, use #total", uplevel: 1, category: :deprecated
      total
    end
  end

  class NextInventory < Inventory
    private :book_count
  end
end

def capture_stderr
  original = $stderr
  $stderr = StringIO.new
  yield
  $stderr.string
ensure
  $stderr = original
end

Warning[:deprecated] = true
inventory = Shelf::Inventory.new(%w[a b c])

capture_stderr { inventory.book_count } # => "e17.rb:36: warning: Inventory#book_count is deprecated, use #total\n"
Warning[:deprecated] = false
capture_stderr { inventory.book_count } # => ""

begin
  Shelf::NextInventory.new(%w[a]).book_count
rescue NoMethodError => e
  e.message # => "private method 'book_count' called for an instance of Shelf::NextInventory"
end

Where the books are outdated

Much of the printed advice on visibility was written for Ruby 1.9 to 2.x and is still repeated. The current rules:

  • "A private method can never be called with a receiver." The rule changed in Ruby 2.7: the literal self is allowed as the receiver for any private method. Before that only setters could use it. Books that warn against self.method for private methods are describing Ruby 2.6 and older.

  • Return values of the modifiers. Before Ruby 3.0 attr_reader returned nil, so the inline form private attr_reader :name could not work; before 3.1 private, public, protected and module_function returned nil. Today they return their arguments, so the inline forms are idiomatic.

  • Array arguments (private [:a, :b]) arrived in Ruby 3.0, and the private def idiom needs Ruby 2.1 or later.

  • Error messages. The wording of NoMethodError changed twice, and tests that match the text must follow:

    Ruby 3.2 and older:  private method `x' called for #<Foo:0x000071c4>
Ruby 3.3:            private method `x' called for an instance of Foo
Ruby 3.4 and later:  private method 'x' called for an instance of Foo

    Source: Ruby 4.0 documentation: NoMethodError

    Until 3.2 the message printed the receiver’s inspect, which was slow and could leak data. Prefer assert_raises(NoMethodError) and check error.name instead of matching the message.

  • send as the universal tool. Older tutorials call send for everything. Today public_send is the default for dynamic dispatch on public methods, and send or __send__ is reserved for the cases that intend to bypass visibility.

  • protected everywhere. Some books recommend protected readers for all "internal but shared" state. Value objects built with Data or Struct make that unnecessary.

  • Hiding constants by convention. private_constant has existed since Ruby 1.9.3; leading underscores or comments are no longer needed.

  • Method#public? was added in 3.1 and removed in 3.2, so articles that use it are wrong for current Ruby.

  • inspect always shows everything. True before Ruby 4.0. Now instance_variables_to_inspect controls it.
