Incompatibilities & Dropped Features

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Scala 3.10 (3.10.0, released 2026-10-12). Every program, diagnostic and rewrite on it was produced with Scala CLI 1.17.1 on JDK 26 on 2026-10-16. Where a result depends on another compiler it was produced with Scala 3.9.0 (the LTS line), 3.3.8 (the previous LTS) or 2.13.18, each fetched from Maven Central through the same Scala CLI. The page answers one question: what stops a piece of Scala 2.13 code, or a pattern remembered from an older book, from compiling or from behaving the same under Scala 3.10, and what replaces it.

The official migration guide groups the answers into an incompatibility table (syntactic changes, dropped features, contextual abstractions, other changed features, type checker, type inference and macros), and the language reference has a separate dropped features chapter. Both are covered row by row below, then merged with the changes that Scala 3 itself made between 3.3 and 3.10, and finally with the outdated forms found in books. Planning a whole migration is the subject of Migrating from Scala 2; which compiler can read whose output is covered in Scala 2 & Scala 3 Compatibility; moving between Scala 3 versions is in Upgrading Between Scala 3 Versions. This page is the reference those pages point to.

The examples use the trailhead scenario (trails, huts and a Planner) where it fits, and a minimal standalone program where it does not. Each failing example shows the exact compiler message from 3.10.0, with the file path removed.

What counts as an incompatibility

An incompatibility is a piece of code that compiles with Scala 2.13 and does not compile with Scala 3. Two refinements matter in practice:

  • A runtime incompatibility is code that compiles on both but behaves differently. They are rare and dangerous, so this page flags every one it knows: implicit views (Implicit views), the inferred type of an overriding method (Return type of an override), a -> defined through an implicit class (-> is now an extension method), and private[this] fields (private[this] and protected[this]).

  • A removal is not always an incompatibility in the strict sense. Scala 3.0 to 3.3 kept some Scala 2 syntax alive for migration, then Scala 3.4 started to warn about it and Scala 3.10 turned some of those warnings into errors, so code that was fine on the 3.3 LTS can stop compiling on 3.10 even though it is Scala 3 code. The timeline is in From warnings to errors: the 3.3 to 3.10 timeline.

Three outcomes appear in the tables below. Error means the compiler rejects the code on 3.10. Warning means it compiles and the message names the replacement. Silent means it compiles with no message at the default settings.

Letting the compiler do the work first

Most syntactic and dropped-feature rows have an automatic rewrite. It lives in the compiler’s migration mode: -source:3.0-migration turns the hard errors of the rows above into migration warnings and, together with -rewrite, patches the files in place. Run it on a clean working tree so that git diff shows exactly what changed.

The source file below packs eight rows of the table into Scala 2 style code. It is deliberately brace-based, the style the rewrite expects.

//> using scala 3.10.0

object given {
  val enum = 1
}

class Trail {
  val km = 2
}

object Walk {
  val km = 9
  class Day extends Trail {
    def show(): Unit = println(km)
  }

  def print() { println("walk") }

  val labels = Map('easy -> 1)
  val square = { x: Int => x * x }
  val ascent = 40
  val lazyAscent: () => Int = ascent _

  def message(): String = "hello"

  def run(): Unit = {
    var i = 0
    do {
      i += 1
    } while (i < 3)
    println(message)
    println(i)
  }
}

Compiling it with the default settings fails with eight errors, one per row (the messages are shown in the sections below). Compiling it with scala compile --scalac-option -rewrite --scalac-option -source:3.0-migration Legacy.scala prints a single migration warning for the auto-application and the line [patched file Legacy.scala]. This is the diff the rewrite produced:

The patched file compiles on 3.10 with exit code 0. The rewritten code is correct but not pretty (while ({ { ... } ; c }) () is the literal desugaring of do), so review it as ordinary source.

Two remarks about the rewrite. First, it only repairs rows marked "migration mode" in the table above; the other rows need a human. Second, a rewrite run does not replay earlier ones: -source:3.4-migration patches only what became deprecated in 3.4 (see From warnings to errors: the 3.3 to 3.10 timeline), not the 3.0 items. The Scala 2.13 compiler can find the same constructs before migration starts when run with -Xsource:3, and Scalafix has rules for the rows marked "Scalafix" (procedure syntax, auto-application, eta-expansion, any2stringadd, explicit implicit types). Scalafix is a third-party tool from the Scala Center; it is not part of the Scala distribution. See Migrating from Scala 2 for the full workflow.

Syntactic changes

Scala 3 introduced optional braces and the new control syntax. That costs a few restrictions on the older syntax and removes some oddities. The migration guide lists seven rows.

Restricted keywords

enum, export, given, then, =>> and ?=> are regular keywords in Scala 3 and cannot be identifiers any more (soft keywords such as inline, opaque, extension, using, open, transparent and infix are unaffected). The migration guide’s example is object given { val enum = ... }:

//> using scala 3.10.0

object given:
  val enum = 1
  println(enum)
-- [E040] Syntax Error: kw.scala:3:7
3 |object given:
  |       ^^^^^
  |       an identifier expected, but 'given' found
-- [E103] Syntax Error: kw.scala:5:2
5 |  println(enum)
  |  ^^^^^^^
  |  Illegal start of toplevel definition
2 errors found

The fix is a different name or backticks around the name, and the migration rewrite chooses backticks (see the diff above, where both given and enum are quoted). A Java method with such a name, for example then, is called with the same backticks, but the practical remedy is to rename on your side.

Source: Scala 3 Migration Guide: Restricted Keywords

Procedure syntax

def print() { ... }, with no =, declared a method returning Unit in Scala 2. It was deprecated in 2.13 and is dropped in Scala 3.

//> using scala 3.10.0

object Bar:
  def print() {
    println("bar")
  }
-- [E040] Syntax Error: proc.scala:4:14
4 |  def print() {
  |              ^
  |              '=' expected, but '{' found
1 error found

Write def print(): Unit = .... The rewrite inserts : Unit = (see the diff above). Note that the form made a method return Unit whatever its body computed.

Source: Scala 3 Reference: Dropped: Procedure Syntax

Parentheses around a lambda parameter

A lambda parameter followed by a type must be parenthesized: { x: Int => x * x } is ambiguous with the optional-braces syntax and is rejected.

-- Error: lambda.scala:3:17
3 |val f = { x: Int => x * x }
  |                 ^
  |parentheses are required around the parameter of a lambda
  |This construct can be rewritten automatically under -rewrite -source 3.0-migration.
1 error found

The fix is { (x: Int) => x * x }, which also compiles on 2.13, so the change can be made before the migration. The message itself tells you the rewrite switch.

Source: Scala 3 Migration Guide: Parentheses Around Lambda Parameter

Open brace indentation for passing an argument

A Scala 2 style that puts the argument block on the next line, after the call, is no longer parsed as an argument.

//> using scala 3.10.0

def test(name: String)(body: => Unit): Unit = body

@main def braceDemo(): Unit =
  test("my test")
  {
    assert(1 == 1)
  }

On 3.10 the brace is a new statement, and the call before it lacks its second argument list:

-- [E178] Type Error: brace.scala:6:2
6 |  test("my test")
  |  ^^^^^^^^^^^^^^^
  |  missing argument list for value of type (=> Unit) => Unit
1 error found

The migration rewrite indents the brace so that it belongs to the call; the cleaner fix is to move it up: test("my test") {. The same rewrite handles a refinement placed after a new line (type Bar = Foo followed by {).

Source: Scala 3 Migration Guide: Open Brace Indentation For Passing An Argument

Wrong indentation

Scala 3 uses indentation to find the end of a statement more strictly. In the guide’s example an indented line after a value is read as an application of that value, not a new statement:

//> using scala 3.10.0

def bar: (Int, Int) = {
  val foo = 1.0
  val bar = foo
    (1, 1)
}
-- [E050] Type Error: indent.scala:5:12
5 |  val bar = foo
  |            ^^^
  |            value foo does not take parameters
6 |    (1, 1)
-- [E007] Type Mismatch Error: indent.scala:7:1
7 |}
  | ^
  |Found:    Unit
  |Required: (Int, Int)
  |
  |Maybe the enclosing block is missing a final expression after the definition of `bar`?
2 errors found

There is no automatic rewrite; fix the indentation so that (1, 1) lines up with val. A formatter such as scalafmt prevents the mistake, but it may restyle the whole project, so adopt it as a separate commit. The rest of the indentation rules are in Optional Braces & Indentation.

Source: Scala 3 Migration Guide: Wrong indentation

_ as a type parameter

Scala 2 accepted def foo[_: Foo], a type parameter named _ together with a context bound, a trick the fastparse library used. Martin Odersky called it a "clever exploit of a scalac compiler bug", and Scala 3 closes it.

-- [E040] Syntax Error: under.scala:4:8
4 |def foo[_: Foo]: Unit = ()
  |        ^
  |        an identifier expected, but '_' found
1 error found

Give the parameter a real name (def foo[T: Foo]). Binary compatibility is unaffected because type parameters are erased.

Source: Scala 3 Migration Guide: _ As A Type Parameter

+ and - as type parameters

def foo[+] named a type parameter + in Scala 2. Scala 3 reads the sign as a variance annotation and finds no name.

-- Error: plusminus.scala:3:8
3 |def foo[+]: Unit = ()
  |        ^
  |        no `+/-` variance annotation allowed here
1 error found

Choose an ordinary name. + and - remain valid as type names in general (type +), only the parameter position changed.

Source: Scala 3 Migration Guide: + And - As Type Parameters

Dropped features

The second group of rows removes features "to simplify the language". Eight rows, all of which fail on 3.10.

Symbol literals

'abc was a literal of type Symbol in Scala 2. The syntax is deprecated in 2.13 and gone in Scala 3, where ' begins a quote for metaprogramming. The class scala.Symbol itself still exists.

//> using scala 3.10.0

val values: Map[Symbol, Int] = Map('abc -> 1)
val abc = values('abc)
-- Error: sym.scala:3:35
3 |val values: Map[Symbol, Int] = Map('abc -> 1)
  |                                   ^
  |symbol literal 'abc is no longer supported,
  |use a string literal "abc" or an application Symbol("abc") instead,
  |or enclose in braces '{abc} if you want a quoted expression.
  |For now, you can also `import language.deprecated.symbolLiterals` to accept
  |the idiom, but this possibility might no longer be available in the future.
-- Error: sym.scala:4:17
4 |val abc = values('abc)
  |                 ^
  |symbol literal 'abc is no longer supported,
  ...
2 errors found

The rewrite produces Symbol("abc"). The migration guide recommends a second step: replace Symbol with plain strings or a dedicated class, because Symbol itself is deprecated. The message names the escape hatch import language.deprecated.symbolLiterals, which keeps old files compiling while they are being converted.

Source: Scala 3 Reference: Dropped: Symbol Literals

do-while

do now introduces the body of for, while and if in the new control syntax, so do { ... } while (cond) could not stay. The program below shows what 3.10 says:

//> using scala 3.10.0

@main def doWhileDemo(): Unit =
  var i = 0
  do {
    i += 1
  } while (i < 3)
  println(i)
-- Error: dowhile.scala:5:2
5 |  do {
  |  ^^
  |  end of toplevel definition expected but 'do' found
-- [E103] Syntax Error: dowhile.scala:8:2
8 |  println(i)
  |  ^^^^^^^
  |  Illegal start of toplevel definition
2 errors found

Source: Scala 3 Reference: Dropped: Do-While

The replacements are while ({ body; cond }) (), which also compiles on Scala 2 and is what the rewrite emits, or the Scala 3 form below. The loop-and-a-half style, a while whose condition block runs the body first, is the idiom:

//> using scala 3.10.0

@main def whileDemo(): Unit =
  var i = 0
  while
    i += 1
    i < 3
  do ()
  println(i)

which prints 3. For a loop that walks a collection, prefer for or a higher-order function; see Conditionals & Loops.

Source: Scala 3 Reference: Dropped: Do-While

Auto-application

A method declared with an empty parameter list, def message(): String, could be called as message in Scala 2. Scala 3 requires the parentheses; Java-defined methods are exempt, because their signatures cannot express the difference.

//> using scala 3.10.0

object Hello:
  def message(): String = "Hello"

@main def autoDemo(): Unit =
  println(Hello.message)
  println("abc".length)
-- [E100] Syntax Error: autoapp.scala:7:16
7 |  println(Hello.message)
  |          ^^^^^^^^^^^^^
  |          method message in object Hello must be called with () argument
1 error found

Only the first call fails: "abc".length calls a Java method and compiles. The rewrite adds the () (println(message()) in the diff above) and Scalafix can do it on 2.13 beforehand. The convention that follows is the one the style guide gives: use () for methods with side effects and no () for pure accessors.

Source: Scala 3 Reference: Dropped: Auto-Application

Value eta-expansion

Scala 3 expands a method to a function automatically (automatic eta-expansion), which makes the trailing m _ syntax unnecessary. It also stops turning a plain value into a nullary function:

//> using scala 3.10.0

def twice(n: Int): Int = n * 2

@main def etaDemo(): Unit =
  val x = 1
  val f: () => Int = x _
  val g = twice _
  println((f(), g(4)))
-- [E099] Syntax Error: eta.scala:7:23
7 |  val f: () => Int = x _
  |                     ^^^
  |Only function types can be followed by _ but the current expression has type Int
-- Warning: eta.scala:8:16
8 |  val g = twice _
  |          ^^^^^^^
  |The trailing ` _` for eta-expansion is unnecessary;
  |the compiler performs eta-expansion automatically, so you can write the function value directly instead.
  |This construct can be rewritten automatically under -rewrite -source 3.4-migration.
1 warning found
1 error found

The two lines differ in severity. x _ on a value is an error; the rewrite replaces it with (() => x). twice _ on a method is only a warning since Scala 3.4 (write plain twice). The migration guide lists the row as a Scala 2.13 deprecation, but 2.13.18 itself rejects x _ on an Int with _ must follow method; cannot follow Int, so in practice the row concerns method references.

Source: Scala 3 Migration Guide: Value eta-expansion

any2stringadd

Scala 2 had an implicit conversion Predef.any2stringadd that added + to every type, so new AnyRef + "foo" compiled. It is deprecated in 2.13 and removed in Scala 3.

-- [E008] Not Found Error: any2.scala:4:23
4 |  val str = new AnyRef + "foo"
  |            ^^^^^^^^^^^^
  |            value + is not a member of Object
1 error found

The replacement is an explicit conversion, String.valueOf(x) + "foo", or string interpolation (see Strings & Interpolation). The Scalafix rule fix.scala213.Any2StringAdd from scala/scala-rewrites applies it on 2.13.

Source: Scala 3 Migration Guide: any2stringadd conversion

Early initializers

extends { val name = "Foo" } with Bar initialized fields before the parent trait’s body. They were rarely used and mostly compensated for the lack of trait parameters, which Scala 3 now has.

//> using scala 3.10.0

trait Bar:
  val name: String
  val size: Int = name.size

object Foo extends {
  val name = "Foo"
} with Bar
-- Error: early.scala:7:19
7 |object Foo extends {
  |                   ^
  |                   `extends` must be followed by at least one parent
-- [E009] Syntax Error: early.scala:9:2
9 |} with Bar
  |  ^^^^
  |  Early definitions are not supported; use trait parameters instead
...
3 errors found

Source: Scala 3 Reference: Dropped: Early Initializers

The Scala 3 form passes the value as a trait parameter:

//> using scala 3.10.0

trait Bar(val name: String):
  val size: Int = name.size

object Foo extends Bar("Foo")

@main def earlyFix(): Unit =
  println(Foo.size)

prints 3. A trait parameter is not available in 2.13, so code that cross-compiles needs an intermediate class (abstract class BarEarlyInit(val name: String) extends Bar) or a secondary constructor. Early initializers were also used to give a subclass private state that the superclass constructor reads through an overridden method; the migration guide moves that state into a nested private object state, which is initialized on demand. Trait parameters are covered in Traits & Mixins.

Existential types

T forSome { type T } is dropped. The reference gives three reasons: it violates the soundness principle on which DOT (the calculus under Scala 3) is built, it interacts badly with other features, and it overlaps path-dependent types.

-- [E034] Syntax Error: exist.scala:3:24
3 |def foo: List[Class[T]] forSome { type T } = Nil
  |                        ^^^^^^^
  |                        Existential types are no longer supported -
  |                        use a wildcard or dependent type instead
...
3 errors found

Wildcard-only existentials remain legal and are treated as refined types, so List[?] replaces List[T] forSome { type T }. When a wildcard is not enough, wrap the type in an enclosing type that carries it as a member:

trait Bar:
  type T
  val value: List[Class[T]]

When the compiler reads a Scala 2 class file that contains an existential, it approximates it and warns that a precise emulation is not possible. Wildcards are written ? since 3.4; _ still works but warns (see From warnings to errors: the 3.3 to 3.10 timeline).

Implicit views

//> using scala 3.10.0

  val print: String

  ev(a).print

    for (x, i) <- xs.zipWithIndex do
      if x == elem then break(i)
    -1

The compiler now infers that a private member only accessed through this is object-private, which was the purpose of private[this]. The qualified form is deprecated, and protected[this] is dropped without replacement. On 3.10 the old form compiles with a warning:

-> is now an extension method

The standard a -> b pair syntax became an inline extension method on 3.10, and Predef.ArrowAssoc stopped being an implicit conversion. That can silently change which -> runs. A DSL that defines -> through an implicit class loses to the standard one:

//> using scala 3.10.0

object dsl:
  implicit class Arrow[A](a: A):
    def ->[B](b: B): String = s"custom($a, $b)"

import dsl.*

@main def arrow2Demo(): Unit =
  println(1 -> "a")

On 3.10.0 this prints the tuple (1,a). The same file prints custom(1, a) on 3.9.0 and 3.3.8. No error, no warning: the program compiles and the meaning changes. The version defined as an extension method keeps its priority and prints custom(1, a) on 3.10 when dsl.* is imported. So a DSL that ships its own -> has to be rewritten as an extension. See Domain Specific Languages.

Using the old names directly produces deprecation warnings, both since 3.10.0:

class RichInt in package scala.runtime is deprecated since 3.10.0: use the extension methods available on primitive types instead
method ArrowAssoc in object Predef is deprecated since 3.10.0: Use `->` extension method instead.

Ordinary uses (1 to 3, 3.max(4), 5.abs) are unaffected. Macros and compiler plugins that inspect the old Rich* trees must match the new shape.

Related forms that still work

Three Scala 2 forms look like candidates for removal but behave as follows on 3.10:

  • Type lambdas written with a projection compile: lift[({ type L[x] = List[x] })#L](List(1)) is accepted, because the prefix is a concrete refinement. The Scala 3 form is [x] =>> List[x]. The kind-projector syntax Either[String, *] is not accepted by default (Not found: type *); it needs -Xkind-projector, which then prints Right(1) for lift[Either[String, *]](Right(1)) and Right(2) for lift[[x] =>> Either[String, x]](Right(2)).

  • Implicit conversions and implicit classes still compile and run. implicit def intToString(i: Int): String followed by val s: String = 42 prints 42, with the feature warning Definition of implicit conversion method intToString should be enabled by adding the import clause 'import scala.language.implicitConversions'. Implicit classes stay, too ("hi".shout printed HI!), though extension is preferred. Only the resolution rules changed.

  • Deprecated Scala 2.13 library names still compile with warnings: Traversable (use Iterable), Stream (use LazyList), CanBuildFrom (use BuildFrom), JavaConverters (use scala.jdk.CollectionConverters) and the strict Map.mapValues (use .view.mapValues(f), then .toMap). The replacement program runs and prints (6,List(1, 2, 3),Map(1 -> 3),List(1, 2)).

Type lambdas have their own page, Type Lambdas & Higher Kinds.

Comparing with other languages

Scala is not alone in removing forms after years of deprecation. The path Scala 3.4 to 3.10 followed, a warning that names its replacement, a rewrite switch, and an error only a few minor releases later, can be compared with the breaking changes that Groovy collects release by release in Groovy: What’s New & Migrating from Older Versions. A different kind of constraint is the Java floor: Scala 3.8 and later need JDK 17, and the Maven release setting and toolchains that pin a build to a Java version are covered in Java Build and Tooling. Calling Java from Scala is covered in Using Java from Scala.

Pitfalls

  • A green 2.13 build is not a green Scala 3 build. Only about a third of the 32 rows have a 2.13 deprecation or feature warning; the rest (open brace, wrong indentation, inheritance shadowing, abstract override, case-class companions, variance checks and the type-checker fixes) fail only on Scala 3.

  • The rewrite assumes the Scala 2 meaning. this.x for inheritance shadowing, Symbol("abc") for a literal and () => x for value eta-expansion all keep the old behavior, even where the old behavior was the bug. Review the diff.

  • -source:3.0-migration will not run on brace-and-indent mixes. Rewriting a file that already uses Scala 3 optional braces together with Scala 2 constructs can fail with new syntax errors (it did here with def print() { inside a braceless object); run the rewrite on the Scala 2 style file first and convert to braceless afterwards.

  • Silent behavior changes need tests. Four changes do not produce an error: the inferred type of an override (Return type of an override), an implicit view resolved to a different conversion (Implicit views), -> through an implicit class (-> is now an extension method) and a private[this] field that is not generated (private[this] and protected[this]).

  • Binary compatibility is separate from source compatibility. 3.10 keeps loading libraries compiled with older Scala 3 versions that used the removed features; only the source of the library being compiled has to change. A 3.10-compiled library cannot be used by a project on 3.9 (see Versions, Compatibility & JDKs).

  • Libraries that must stay cross-compilable with Scala 2 should stay on the 3.9 LTS. The 3.10 release notes expect cross-compiled libraries to remain on the LTS indefinitely, and recommend 3.9 LTS for the longest support window.

  • Check MiMa. After a migration, run MiMa 1.2.1 or newer against the previous artifact: the removed features can change generic signatures, and the 3.10 notes mention IncompatibleSignatureProblem reports as an example.

What was run and what was not

All the [source,scala] programs marked with //> using scala 3.10.0 were compiled with Scala CLI 1.17.1 (using scala run for the @main programs and scala compile where there is no entry point), and their diagnostics and outputs are the ones printed above. The -rewrite experiments were run with --scalac-option -rewrite --scalac-option -source:3.0-migration and -source:3.4-migration on copies of the sources. The version comparisons used 3.3.8 and 3.9.0 for with, the vararg and wildcard forms, the refutable generator, the top-level this, the inaccessible companion given, the -> priority and inheritance shadowing, and 2.13.18 for the legacy program. The scala-xml dependency (2.4.0) and the scala-reflect dependency (2.13.18) were fetched from Maven Central.

Not run: the Scalafix rules (ExplicitResultTypes, Any2StringAdd and others), because they need sbt or the Scalafix CLI; sbt-scala3-migrate; and the Scala 2 macro cross-building recipes. These are described from the migration guide and are covered in Migrating from Scala 2. The claims about the intermediate releases 3.4 to 3.8 come from the release notes and were not run on those compilers.
