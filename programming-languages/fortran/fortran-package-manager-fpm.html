Fortran Package Manager (fpm)

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Fortran 2023 (ISO/IEC 1539-1:2023, J3/23-007r1) and was checked on 2026-10-19. fpm is not part of the standard: it is a community tool of the fortran-lang project, written in Fortran, and everything on this page describes fpm 0.13.0, released on 2026-02-17 (the binary used here prints 0.13.0, alpha for fpm --version, the label this release carries). Every fpm project on the page was built and run with fpm 0.13.0 using GNU Fortran 16.2 and, where stated, LLVM Flang 23, inside a Linux container; the output shown is real output, abridged where it is long, and the Fortran sources compile warning-free under gfortran -std=f2023 -Wall -Wextra -pedantic -fimplicit-none -fcheck=all (passed to fpm with --flag). Parts that need services or tools that are not in the container (the package registry, publishing, HDF5, NetCDF and MINPACK metapackages, GitHub Actions, the installation channels) are documented from the official fpm pages and are marked as not run. The source of a build is always one of the heatflow modules introduced in Getting Started and used throughout this section (heatflow_kinds, heatflow_grid, heatflow_solver and the rest, see Modules and Submodules).

A Fortran build has three jobs: find the sources, compile them in an order that respects module dependencies, and link the result. The standard says nothing about any of it, and Fortran’s module files (.mod) make the order a real problem (see the section on module files in Getting Started). fpm solves it for the common case by reading the sources: it scans every use, submodule and include statement, builds the dependency graph itself, and needs only a short TOML manifest, fpm.toml, and a conventional directory layout. It also downloads and builds dependencies from git repositories, local paths or a registry, which is what the "package manager" part of the name means. The two other tools in the section that do the same job from a different angle, CMake and Meson, are compared on Building with Make, CMake and Meson; the compiler flags fpm passes are explained on Compilers and Compiler Options; the unit-test framework fpm projects usually use, test-drive, is on Testing, Debugging and Profiling; and the standard library that fpm can fetch as a dependency is on Fortran stdlib.

The project layout and fpm new

fpm projects follow a layout that fpm discovers without configuration. The rules, from the manifest reference and the output of fpm new:

Path Meaning

fpm.toml

the manifest; the only required file is this one, containing at least name

src/

the library: every module and procedure file; compiled into lib<name>.a and visible to every other target and to packages that depend on this one

app/

executables: every file containing a program unit; the executable is named after the file (probe.f90 gives probe), except main.f90, which gives the package name

test/

tests: programs run by fpm test; they may use the library and any dev-dependency; files without a program in this directory (such as a test module) are support code for them

example/

examples: programs run by fpm run --example

include/

files for the Fortran include statement and the preprocessor #include; its presence also makes fpm generate the library target

build/

everything fpm generates (objects, modules, archives, executables, fetched dependencies); safe to delete

The discovery is recursive: app/tools/probe.f90 is found as well. Which directories exist decides which targets exist; an explicit [[executable]], [[test]] or [[example]] table in the manifest adds or renames targets, and auto-executables, auto-tests and auto-examples can switch the discovery off (see The manifest fpm.toml).

fpm new NAME creates the directory, runs git init in it and writes sample files. The name must be ASCII letters, digits, underscores or hyphens, at most 63 characters, and start with a letter:

fpm new first_steps
cd first_steps
find . -path ./.git -prune -o -type f -print | sort
cat fpm.toml
./README.md
./app/main.f90
./fpm.toml
./src/first_steps.f90
./test/check.f90
name = "first_steps"
version = "0.1.0"
license = "license"
author = "Jane Doe"
maintainer = "jane.doe@example.com"
copyright = "Copyright 2026, Jane Doe"

The author fields are placeholders (fpm fills them from the Git identity when one is configured; the container had none), and the generated manifest has no [build] or [install] table, because the defaults already do what is wanted. The generated src/first_steps.f90 is a module with a say_hello subroutine, app/main.f90 uses it, and test/check.f90 prints a placeholder message. Building, running and testing it:

fpm run and fpm test first make sure the targets are built, which is why fpm run reports Project is up to date after the explicit build. The options of fpm new choose which directories are created:

Option Effect

--lib or --src

only src/ and a placeholder module (the result of fpm new libonly --lib is README.md, fpm.toml and src/libonly.f90)

--app

only app/ and a main program

--test

only test/ and a placeholder test program

--example

only example/ and a placeholder; with none of these options the default is --lib --app --test

--full

an extensively annotated fpm.toml that documents every key, and example/demo.f90, with explicit [[executable]], [[test]] and [[example]] tables

--bare

only fpm.toml and README.md, no directories and no Fortran

--backfill

allow an existing directory and create only the files that are missing

A name that fpm cannot accept is rejected by fpm new with the rule above and exit status 4 (STOP 4). The --full manifest is the best offline reference for the format: it documents multi-level library sources (a file src/a/b/c/d.f90 should define the module a_b_c_d, a convention fpm asks for but does not enforce), library types and every dependency form.

The commands

fpm has ten subcommands, listed by fpm --list or fpm help. Everything is built into build/, which can always be removed and rebuilt (a rebuild from scratch needs the network again when git dependencies are used).

Command What it does

fpm new

create a package directory with sample files (above)

fpm build

fetch dependencies, scan the sources, compile and link everything the targets need

fpm run

build and run the executables in app/ (or --example programs from example/); without a name it runs all of them

fpm test

build and run the programs in test/; a test fails when its program exits with a nonzero status

fpm install

install executables, and with [install] library = true also the library archive and the .mod files

fpm clean

delete the build directories, with a confirmation prompt unless --skip or --all is given

fpm update

re-resolve and re-fetch dependencies

fpm publish

upload the package to the registry

fpm list

a one-line description of every subcommand

fpm help

the manual page of a subcommand, for example fpm help runner for the --runner option

The options shared by build, run, test and install, from fpm build --help and the sibling help pages, are:

Option Meaning

--profile PROF

a built-in compilation profile (release or debug) or a profile defined in the manifest (see Features and profiles)

--features LIST

comma-separated features from the manifest; cannot be combined with --profile

--flag FFLAGS, --c-flag, --cxx-flag, --link-flag

extra Fortran, C, C++ and linker flags

--compiler NAME, --c-compiler, --cxx-compiler, --archiver

choose the tools

--build-dir DIR

use another build directory (default build)

--no-prune

do not drop unused module dependencies (see below)

--list

list targets without building or running them; for build it downloads dependencies and writes compile_commands.json without compiling

--verbose

show the commands fpm runs

--config-file PATH

another global configuration file

-- ARGS

on run and test, the arguments passed to the program

--runner CMD, --runner-args ARGS

prefix the program with a command such as a debugger, valgrind or mpiexec (see Running with a runner)

Two further options belong to individual commands: fpm build --tests builds all tests even when nothing needs them, and fpm install --no-rebuild installs what is already built. -C DIR (or --directory DIR) changes to another directory first. It is given after the subcommand, fpm run -C /work/first_steps; written before the subcommand in the container it was rejected, and the command printed the help text instead. Long option lists can be kept in a response file: fpm @release reads release.rsp from the current directory, each line written as options followed by one argument.

options run
options --profile release

Selecting targets and passing arguments

fpm run and fpm test take target names, with simple globbing: ? matches one character and * any string, quoted against the shell. --all is an alias for --target '*', and in fpm 0.13.0 a bare fpm run also runs every executable (the help text says a list is printed when several candidates exist and no name is given, but the version tested ran them all). In a project with app/main.f90, app/tools/probe.f90 and two test programs the commands behave like this:

fpm run --list
fpm test --list
fpm run --all
fpm run "pro*"
 Matched names:
first_steps  probe
 Matched names:
check  more
 Hello, first_steps!
 probe
 probe

Everything after -- goes to the program. The heatflow application takes the name of a namelist file, and its error stop 2 for a missing file is reported by fpm as a failed execution:

fpm run -- heatflow.nml
fpm run -- missing.nml
steps=2000 residual= 1.38E-04
max temperature=   0.139
cannot read configuration: Cannot open file 'missing.nml': No such file or directory
ERROR STOP 2

Error termination. Backtrace:
#0  0xffffae8f196f in ???
...
<ERROR> Execution for object " heatflow " returned exit code  2
<ERROR> *cmd_run*:stopping due to failed executions
STOP 2

The same applies to fpm test: a test program signals failure with a nonzero exit status, for example through error stop, and fpm test itself then exits with status 1 (checked with a one-line test program that executes error stop "boom"). That is the contract that makes fpm usable in continuous integration; the statements are described in Error Handling and Program Termination.

Running with a runner

--runner CMD puts a command in front of the program path. It is available for run and test, which makes it the hook for debuggers, valgrind, mpiexec and tracing tools. Without a value the runner is echo, which prints the paths of the executables instead of running them. --runner-args passes arguments to the runner itself, as opposed to -- ARGS, which goes to the program. A value that begins with a dash is read by fpm’s argument parser as options, so write --runner-args=" -np 4" with an equals sign and a leading space:

fpm test --runner "valgrind -q"
fpm run --runner echo
fpm run --runner "mpiexec" --runner-args=" -n 3"

The first command ran the test program under valgrind and printed the same two PASSED lines, the second printed build/gfortran_DF6D0BB80A7053CC/app/heatflow, and the third started the MPI program of the mpi metapackage example below on three ranks. With the value -np 4 and no equals sign the container’s fpm answered UNKNOWN COMPOUND SHORT KEYWORD:n in -np 4 followed by a table of its options.

Source: fpm: Built-in dependencies (metapackages)

Incremental builds and the recompilation cascade

fpm decides whether a file must be rebuilt from the content of the source, not from its timestamp, and it rebuilds every file that depends on a changed module. Touching a file changes nothing:

touch src/heatflow_kinds.f90
fpm build
Project is up to date

A real change in a deep module cascades through everything that uses it, directly or not (here a comment was appended to heatflow_kinds.f90, which every other module uses; only heatflow_boundary, which does not use it, was left alone):

[  6%]             heatflow_kinds.f90  done.
[ 13%]         heatflow_constants.f90  done.
[ 20%]              heatflow_grid.f90  done.
[ 26%]           heatflow_kernels.f90  done.
[ 33%]              heatflow_capi.f90  done.
[ 40%]            heatflow_config.f90  done.
[ 46%]                heatflow_io.f90  done.
[ 53%]            heatflow_solver.f90  done.
[ 60%]      do_concurrent_stencil.f90  done.
[ 66%]              heatflow_ftcs.f90  done.
[ 73%]            heatflow_jacobi.f90  done.
[ 80%]                       main.f90  done.
[ 86%]                  libheatflow.a  done.
[ 93%]                       heatflow  done.
[100%]          do_concurrent_stencil  done.

The same comment appended to a submodule, heatflow_jacobi.f90, rebuilds only that file, relinks the archive and the application (do_concurrent_stencil does not use the solver and is not relinked):

[ 25%]            heatflow_jacobi.f90  done.
[ 50%]                  libheatflow.a  done.
[ 75%]                       heatflow  done.
[100%] Project compiled successfully.

That measurement is the whole argument for splitting implementations into submodules, discussed in Modules and Submodules: fpm cannot tell that a comment does not change a module’s interface, so a changed module file recompiles its users, but a changed submodule has no users.

The build directory

Objects, .mod files, archives and executables live in subdirectories of build/ named after the compiler and a hash (build/gfortran_DD609D2CDA6636FC). Builds with different compilers, profiles or flags normally get different directories and do not overwrite each other, and a cache of the resolved dependencies is kept in build/cache.toml. With --build-dir DIR or the environment variable FPM_BUILD_DIR the whole directory moves (fpm build --build-dir /tmp/mybuild produced cache.toml, compile_commands.json, dependencies and the hashed directories there).

The module files are written to the hashed directory itself and the objects to a subdirectory named after the package; the directory is passed with -J and -I, which is the "module directory" of the compiler options in Compilers and Compiler Options. To see exactly what fpm runs, use --verbose, or read build/compile_commands.json (see compile_commands.json and editors). For heatflow_grid.f90 with --profile release:

gfortran -c ././src/heatflow_grid.f90 -O3 -Wimplicit-interface -fPIC -fmax-errors=1 -funroll-loops -fcoarray=single -fimplicit-none -Werror=implicit-interface -ffree-form -I././include -J build/gfortran_C40FC9334A6DC5D6 -Ibuild/gfortran_C40FC9334A6DC5D6 -o build/gfortran_C40FC9334A6DC5D6/heatflow/src_heatflow_grid.f90.o

The last four options before -I././include come from the manifest, not from the profile: -fimplicit-none and -Werror=implicit-interface follow from implicit-typing = false and implicit-external = false (the defaults), and -ffree-form from source-form = "free". With implicit-typing = true and implicit-external = true and source-form = "default", the same file was compiled with none of the three. A missing implicit none is therefore caught in fpm projects by the flag (see The fortran table).

Pruning ("tree-shaking"): in the default monolithic library mode, the archive contains only the objects that the applications, tests and examples actually need; the others are still compiled. --no-prune keeps all of them.

Profiles, flags and environment variables

What a build passes by default

A plain fpm build in fpm 0.13.0 passed no optimisation, warning or run-time checking options at all, whatever the documentation suggests about an "implicit debug build": the compile line for first_steps.f90 was gfortran -c ././src/first_steps.f90 -fimplicit-none -Werror=implicit-interface -ffree-form -J ... -I... -o ..., and fpm build --verbose printed an empty COMPILER OPTIONS line. The profile has to be named. With the GNU compiler the two built-in profiles gave:

Profile gfortran options (from fpm build --profile NAME --verbose)

debug

-Wall -Wextra -Wimplicit-interface -Wno-external-argument-mismatch -fPIC -fmax-errors=1 -g -fcheck=bounds -fcheck=array-temps -fbacktrace -fcoarray=single

release

-O3 -Wimplicit-interface -fPIC -fmax-errors=1 -funroll-loops -fcoarray=single

The exact lists belong to fpm and may change between versions; read them with --verbose. -fcoarray=single is one of the three values gfortran accepts (none, single, lib) and compiles coarray code for a single image, see Coarrays, Images and Synchronization. The C and C++ options are derived in the same way for projects with C sources (-Wall -Wextra -fPIC -fmax-errors=1 -g for debug).

A consequence worth knowing: because the debug profile includes -fPIC and a plain build does not, a plain build cannot link a shared library (see Library types and installation).

Adding flags with --flag and the environment

--flag FFLAGS is added to the options of the named profile; without a profile it is the only option fpm passes, replacing the defaults. It has the strongest use in continuous integration, to impose strict standard checking whatever the profile does:

fpm run --profile release --flag "-march=native"
fpm test --flag "-std=f2023 -Wall -Wextra -pedantic -fcheck=all"

The install table and the extra table

[install] library = true makes fpm install also install the library archive and the module files; without it only executables are installed. module-dir (since 0.13.0) changes the subdirectory of the prefix for the .mod files (default include). See Library types and installation.

Third-party tools keep their own configuration in [extra], which fpm itself never evaluates; the convention is one subtable per tool (extra.fpm.<plugin> for fpm plugins), keys in lowercase with dashes.

The preprocess table

[preprocess.cpp] enables the C preprocessor for the package, with the keys suffixes (file suffixes to preprocess), directories (limit it to directories) and macros (a list of NAME or NAME=VALUE). See Preprocessing and conditional compilation.

Dependencies

Dependencies are declared in [dependencies] of the manifest (exported to packages that use this one), in [dev-dependencies] (available to tests and examples of this package, not exported), or inside an individual target table. Pin to a tag or a full rev in anything that must be reproducible; a branch (or no reference) moves under you. Registry dependencies

A package from the registry names a namespace and, optionally, a version:

Features and profiles

Features and profiles arrived in fpm 0.13.0. A feature is a named collection of manifest properties that is switched on by name, by compiler or by operating system. A profile is a named list of features. They replace the practice of keeping flag lists in shell scripts, and they are how a single manifest can say "strict standard checking with gfortran, -pedantic only with Flang, OpenMP in production".

Defining features

Features live in the [features] table, written with dotted keys:

feature.property = value
feature.compiler.property = value
feature.os.property = value
feature.compiler.os.property = value

A feature can set compiler flags (flags, c-flags, cxx-flags, link-time-flags), build, Fortran and library settings (build.link, fortran.source-form, library.type), dependencies, dev-dependencies, extra executable, test and example targets, preprocess macros, and install and description entries. Compiler names are the list in Selecting the compiler; operating systems are linux, macos, windows, cygwin, solaris, freebsd and openbsd.

When several variants of a feature match, fpm merges them in this order: the base properties, then the compiler’s, then the operating system’s, then the combined compiler-and-system’s. Flags (flags, c-flags, cxx-flags, link-time-flags) are concatenated with spaces, the lists (dependencies, dev-dependencies, executable, test, example, preprocess) are appended, and the tables build, install, fortran and library are exclusive: defining the same one in two variants of the same feature is an error.

Profiles

Profiles group features in [profiles]. debug and release exist as built-in profiles with the flags of the table above; if the manifest defines debug or release, its definition replaces the built-in one completely. A profile named default holds features that are applied together with debug and release, but not with a custom profile or with --features.

Here is a manifest for heatflow, added to the one shown earlier, with a ci profile for strict checking and a production profile for speed with OpenMP. The flang sections show how one feature serves two compilers:

[features]
strict.gfortran.flags = "-std=f2023 -Wall -Wextra -pedantic"
strict.flang.flags = "-pedantic"
checks.gfortran.flags = "-g -fcheck=all -fbacktrace"
fast.flags = "-O3"
fast.gfortran.flags = "-march=native -funroll-loops"
openmp.dependencies.openmp = "*"

[profiles]
ci = ["strict", "checks"]
production = ["fast", "openmp"]

Conditional module use. Since 0.13.0, fpm evaluates #ifdef, #ifndef, #if defined(NAME), #if NAME == VALUE, #elif, #else and #endif against the manifest macros while it scans the sources, so a use mpi_f08 inside #ifdef USE_MPI is a dependency only when the macro is defined. A macro without a value is true for #ifdef; a macro with value 0 is false in #if; an undefined macro is false; names are case-sensitive. The compiler does the actual preprocessing, so the files need the right extension.

A stale-build hazard. Switching between profiles that differ only in preprocessor macros, back and forth, produced a wrong executable in fpm 0.13.0. In a clean tree, --profile sp, then --profile dp, then --profile sp again gave:

fpm run --profile sp
fpm run --profile dp
fpm run --profile sp
kind=4 epsilon= 1.19209E-07
kind=8 epsilon= 2.22045E-16
Project is up to date
kind=8 epsilon= 2.22045E-16

The third run claims the project is up to date and runs the executable of the dp build. fpm clean --apps followed by fpm run --profile sp printed kind=4 again, and so did fpm clean --skip (all build directories, keeping dependencies). Delete the build directory when you change macros by hand, and in CI build each variant in a clean tree or with its own --build-dir.

fypp. The documentation lists [preprocess.fypp] next to cpp, but fpm 0.13.0 answered a package with [preprocess.fypp] and a .fypp source with Warning: Preprocessor fypp is not supported; will ignore it and then Unable to find source for module dependency. Run fypp as a separate step and keep the generated .f90 or .F90 files under src/ (this is also the usual way the stdlib and other fypp-using projects are built).

Static, shared and monolithic libraries

[library] type selects the output (since 0.12.0), and since 0.13.0 it may be an array:

type Result

"monolithic" (default)

one static archive with the package and all its dependencies, pruned to what the targets use; cannot be combined with other types

"static"

one static archive per package (.a, or .lib on Windows), for integration into other build systems

"shared"

one shared library per package (.so, .dylib, .dll), linked dynamically

["static", "shared"]

both variants at once

With type = ["static", "shared"], a plain fpm build failed in the link of the shared library, because the objects were built without -fPIC (the aarch64 linker named the relocation R_AARCH64_ADR_PREL_PG_HI21 and asked to recompile with -fPIC):

<ERROR> Compilation failed for object " libheatflow.so "
<ERROR> stopping due to failed compilation

With --profile release, which includes -fPIC, the build produced both libheatflow.a and libheatflow.so, and fpm install --profile release --prefix /tmp/i2 installed both to lib/. The installed executable linked the shared library (ldd printed libheatflow.so => not found): fpm sets the library search path itself for fpm run, but an installed executable needs LD_LIBRARY_PATH or an rpath. On Windows fpm also generates an import .lib for every .dll.

Module naming and the registry

Fortran has no namespaces, so two packages that define a module with the same name cannot be linked together. fpm offers a convention that avoids collisions and requires it only for registry packages. The manifest switch is module-naming in [build]: true selects the default prefix, the package name followed by a double underscore (my_pkg, my_pkg__core, never my_pkg__1__2 or a name over 63 characters), and a string selects a custom prefix of letters and digits followed by a single underscore, which the registry reserves per package. With module-naming = true, heatflow, whose modules are called heatflow_kinds and so on, fails:

 ERROR: Module heatflow_io in ././src/heatflow_io.f90 does not match its package name (heatflow).
 ERROR: Module heatflow_kinds in ././src/heatflow_kinds.f90 does not match its package name (heatflow).
 ERROR: Module heatflow_solver in ././src/heatflow_solver.f90 does not match its package name (heatflow).
        Hint: Try disabling module naming in the manifest: [build] module-naming=false .
<ERROR> *cmd_build* Model error: The package contains invalid module names. Naming conventions are being requested.

(Three of the module lines.) With the custom prefix module-naming = "heatflow" the same sources build, since heatflow_kinds is the prefix followed by one underscore. Package names follow the same rules as Fortran names: hyphens read as underscores, a name ending in an underscore or containing __ is invalid.

fpm publish creates a tarball and uploads it, and enforces the convention. It needs a registry account, a namespace, a token (do not share it), a semantic version and an SPDX license in the manifest, and an upload cannot be deleted. --show-package-version, --show-upload-data and --dry-run inspect what would be sent. Two checks were run on heatflow, no upload:

fpm publish --show-package-version
fpm publish --show-upload-data
 0.1.0
<ERROR> The package does not meet the module naming requirements. Please set "module-naming = true" in fpm.toml [build] or specify a custom module prefix.

Publishing itself was not attempted, because the registry did not respond (see Registry dependencies). A top-level module named like the package that re-exports the others is the recommended public API (datetime using datetime__dates and datetime__time), the facade pattern of Modules and Submodules.

Tests, examples and cleaning

fpm test builds and runs the programs of test/; each program is a test, and its exit status is the verdict. The usual structure is the one in the heatflow project: test/check.f90 is the driver, test/test_grid.f90 a module of test cases using test-drive, declared as a dev-dependency (the framework is explained on Testing, Debugging and Profiling). The suites run under any profile or compiler (fpm test --profile ci, fpm test --compiler flang-23 --profile debug), and fpm test --runner "valgrind -q" puts a memory checker around them. A test name selects one program, fpm test check; a name that matches nothing prints <INFO> No tests to run and exits normally.

fpm run --example runs the programs from example/; the do_concurrent_stencil program of heatflow is one.

fpm clean deletes build directories after asking; --skip and --all skip the question, and --all also removes the fetched dependencies. Since 0.13.0 the selective options --test, --apps and --examples delete only the executables of that kind, leaving the objects, so a rebuild only relinks (fpm clean --test printed <INFO> Deleted test target: check). --registry-cache clears the registry cache.

Source: fpm: Cleaning build artifacts with fpm

compile_commands.json and editors

Every successful build, or fpm build --list (which downloads dependencies and writes the file without compiling), writes build/compile_commands.json in the Clang compilation database format (since 0.12.0). Each entry has the directory, the argument list and the file, so editors and language servers get the real flags, include paths and module directories without configuration. For heatflow the file had 13 entries (one per source file). It is regenerated at each build, cannot be configured from the manifest, and exists only after a successful build or dry run. fortls and clangd-based editors read it; the setup is on Documentation and Editor Tooling. fpm build --dump model.toml (or a .json+ name) writes fpm’s complete internal model, and +fpm build --show-model prints it, which is the tool for understanding why fpm sees a dependency that you do not.

Source: fpm: compile_commands.json and JSON Compilation Database Format Specification

Plugins

The manifest reserves [extra.fpm.<plugin>] for the configuration of fpm plugins, and the reference calls them a convention for third-party tools. fpm 0.13.0 has no mechanism that dispatches an unknown subcommand to an external program: fpm frobnicate answers <ERROR> unknown subcommand [frobnicate] followed by the usage text, and the subcommand list is fixed. Tools that work with fpm projects, such as formatters, linters, FORD and fortls, therefore run as separate programs and read fpm.toml or compile_commands.json, see Documentation and Editor Tooling.

Where the books are outdated

The Fortran books consulted for this section predate fpm or mention only the tool of their time. The current practice:

Area Outdated in the books, current approach

Build tools

the module chapters explain the recompilation cascade under make (Modern Fortran Explained, the chapter on modules) and no build tool beyond it; today fpm, CMake and Meson scan the modules and compute the order, and fpm needs no makefile at all

Package management

no dependency manager is described; fpm fetches git, path and registry dependencies and metapackages, and the community publishes packages on the fortran-lang package index

no unit-test framework is described; fpm test runs the programs of test/, normally with test-drive

compiler options are taken from the vendor manual one at a time; fpm profiles and features keep them in the manifest

Pitfalls

  • A plain fpm build passes no warning or checking flags. Name a profile (--profile debug) or pass --flag; check with --verbose.

  • --profile and --features cannot be combined. Put the features into a profile.

  • Profile flags may be duplicated in the compile line when a feature combines base, compiler and metapackage settings. It is harmless; read compile_commands.json.

  • Flang gets no profile flags. In 0.13.0 --profile debug and --profile release left the Flang options empty here; use --flag or a flang section of a feature.

  • A branch or no reference in a git dependency moves. Pin a tag or a full rev; an abbreviated hash fails.

  • A dev-dependency is not exported, so a module used by library code must be a normal dependency.

  • Macro-only profile changes are not tracked reliably. Switching between profiles that differ only in preprocess macros can leave a stale executable; clean or use separate build directories.

  • The mpi metapackage needs implicit-typing = true and implicit-external = true in the main package.

  • external-modules finds nothing. It only silences the dependency scan; add the include paths, the libraries and, for OpenMP, -fopenmp.

  • A shared library needs -fPIC. The plain build lacks it; the debug and release profiles include it.

  • An installed shared library is not on the loader path. Set LD_LIBRARY_PATH or use an rpath.

  • Module names are global. Two packages with a module of the same name collide; use module-naming before publishing.

  • A comment in a module recompiles all its users. Keep implementations in submodules, so that editing them does not cascade.

  • A registry dependency can fail at the network layer. On the day of the check the official registry answered with a server error; use git dependencies.

  • fypp sources are not preprocessed. Generate .f90 files before the fpm build.

  • -C DIR goes after the subcommand, fpm run -C dir; before it, the container’s fpm printed the help text.
