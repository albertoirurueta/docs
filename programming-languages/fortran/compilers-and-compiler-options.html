Compilers and Compiler Options

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Fortran 2023 (ISO/IEC 1539-1:2023, J3/23-007r1) and was checked on 2026-10-19. Every example was compiled with GNU Fortran 16.2 (gfortran, -std=f2023 -Wall -Wextra -pedantic unless the example is about a flag) and run, and the examples whose flags exist in both compilers were also built and run with LLVM Flang 23 (flang, release 23.1.4 as installed from apt.llvm.org in the test container, an aarch64 Debian image). The output shown is real output. The deliberate-error examples show the real diagnostics and say which compiler printed them. The Intel ifx and NAG compilers, and the HPE Cray, NVIDIA and AMD compilers, are not installed; what this page says about them is named as such and is not run. Where a table row comes from a vendor manual that could not be read as text on the check date (the Intel Fortran Compiler Developer Guide pages for 2026.1 load as an empty shell for a text extractor), the row says so instead of quoting an option from memory.

A compiler option is by definition outside the language: the standard (J3/23-007r1, clause 4.2, "Conformance") says what a processor shall be able to detect and report, which includes obsolescent forms, forms that violate the numbered syntax rules and constraints, nonstandard intrinsic procedures and nonstandard intrinsic modules, and says that the processor may accept additional forms. How a user asks the processor to report those things, to check the program at run time, to optimize it, or to place its module files is entirely processor-dependent. That is why this page is a per-compiler reference: the same programs, built with the right options, are the cheapest bug-finding tool the language has, and the options differ between GNU Fortran, LLVM Flang, ifx and NAG. The running example is heatflow; its fpm project and the Jacobi kernel appear in several listings. This page covers one compiler invocation. The order in which many files are compiled, and the tools that automate it, are in Building with Make, CMake and Meson and Fortran Package Manager (fpm), module files in Modules and Submodules, the compiler landscape and the per-compiler F2023 support table in History, Standards and Compilers, floating-point exceptions in Floating-Point and IEEE Arithmetic, and debugger, valgrind and profiler workflows in Testing, Debugging and Profiling.

Which manual to read

The compiler version decides which options exist, and documentation sites are not always versioned the way the compiler is:

  • The GNU Fortran manual at gcc.gnu.org/onlinedocs/gfortran/ (no version in the path) is the development branch. Compared with the installed 16.2 compiler it documents -fcoarray=shared and -Wundefined-vars, and 16.2 rejects both (gfortran: error: Unrecognized option: 'shared', with the note that the valid arguments to -fcoarray= are lib none single). Use the versioned manual, gcc.gnu.org/onlinedocs/gcc-16.2.0/gfortran/, for the release you run. The manual has no Fortran 2023 status page (the Fortran-2023-status.html address does not exist), so the support of individual F2023 features comes from the table in History, Standards and Compilers and the compiler’s own diagnostics.

  • LLVM Flang documents its driver at flang.llvm.org/docs/, the standards support in FortranStandardsSupport.html and the extensions in Extensions.html. The executable is flang (it was flang-new before LLVM 20; the Debian package used here installs flang-23, which the examples invoke).

  • Intel’s compiler is ifx. The classic ifort was discontinued in oneAPI 2025.0, so older options lists and answers that say ifort describe a compiler that no longer ships.

  • The authoritative list of a compiler’s options is always the compiler itself: gfortran --help=fortran, gfortran --help=warnings, gfortran --help=optimizers and flang --help printed the tables used below. Every flag shown on this page was run against the installed compiler. A flag the compiler does not know is an error (flang: error: unknown argument: '-fcheck=all'), except where a driver deliberately warns and ignores it, as Flang does for -Wextra.

What a compiler invocation does

gfortran and flang are drivers. One command line is expanded into up to four programs, each with its own options, and the options you give are routed to the stage that understands them:

flowchart LR SRC["source file
.f90 .F90 .f .for"] --> PP["preprocess
cpp or built-in (.F90, -cpp)"] PP --> FE["compile
parse, check, optimize"] FE --> MOD["module files
.mod .smod (-J, -module-dir)"] FE --> AS["assemble
.o"] AS --> LD["link
libgfortran or libflang_rt, libm, -l libs"] LD --> EXE["executable"]

gfortran -dumpversion and gfortran -dumpmachine print 16.2.0 and aarch64-linux-gnu in the test container, and flang --version prints the Debian packaging version string. The file extension chooses the source form and whether the preprocessor runs: .f90, .f95, .f03 and .f08 are free form without preprocessing, .F90 and friends are free form with preprocessing, .f, .for, .ftn are fixed form (see Program Structure and Source Form), and -ffree-form/-ffixed-form override the guess in both compilers. The details of each stage are below; the build-system view (compiling_source, linking_pieces, runtime_libraries) is on the Fortran-lang build pages listed in the References.

Choosing the language level: -std and -pedantic

The first decision for a portable code base is which language it promises. GNU Fortran takes the answer from -std=:

Option Meaning in GNU Fortran 16.2 (gfortran --help=fortran)

-std=f95, -std=f2003, -std=f2008, -std=f2018, -std=f2023

conform to that edition; features from a later edition and GNU extensions are errors or warnings

-std=f2008ts

Fortran 2008 including the TS 29113 features (the C-interoperability descriptors)

-std=f202y

"experimental Fortran 202y features", the working name of the revision after 2023

-std=gnu

the default: the standard language plus the GNU extensions

-std=legacy

accept extensions to support legacy code

-pedantic, -Wpedantic

warn about the use of extensions to the selected standard, and make the GNU extensions an error under a -std=f... option; -pedantic-errors makes them errors in every mode

-fall-intrinsics

all intrinsic procedures are available whatever -std says

The unflagged default is -std=gnu, so a program that compiles silently with plain gfortran file.f90 can still be nonconforming. Flang’s -std= is far narrower: it accepts only f2018 and says so for every other value (error: Only -std=f2018 is allowed currently., printed for -std=f2023, -std=f2008, -std=f2003 and -std=legacy in LLVM 23.1.4). Its -pedantic option turns on portability warnings. Flang accepts the F2023 features it implements without any switch, so -std=f2018 is a diagnostics setting and not a feature gate. The next program uses sind, one of the degree-argument trigonometric functions that Fortran 2023 added; gfortran prints the edition in its own diagnostic.

program std_levels
  use, intrinsic :: iso_fortran_env, only: real64
  implicit none
  real(real64) :: angle, s
  character(len=:), allocatable :: label
  angle = 30.0_real64
  s = sind(angle)                       ! degree-argument trigonometry, Fortran 2023
  label = 'sind(30) = '
  print '(a, f0.3)', label, s
end program std_levels
gfortran -std=f2023 std_levels.f90 -o std_levels && ./std_levels
gfortran -std=f2018 std_levels.f90 -o std_levels
flang std_levels.f90 -o std_levels && ./std_levels
flang -std=f2023 std_levels.f90 -o std_levels

The matching options elsewhere, as far as the vendor manuals name them: Intel ifx selects the checked standard with -stand (the issue baseline for this section names -stand f23), NAG has one switch per edition, and the Flang documentation notes that all the compilers' conformance options "issue warnings if non-standard features are used" (Flang OptionComparison page, which lists -Mstandard for classic Flang, -std=level for GNU and -stand level for Intel). The ifx page for -stand could not be read as text on 2026-10-19, so the argument list is not repeated here.

A conforming program should compile under -std=f2023 on gfortran with no warnings from -pedantic. That is the single most valuable portability test, and the one used for every example in this guide. It does not prove portability: the standard leaves much processor-dependent, and the other compilers support different subsets of Fortran 2023 (see the support table in History, Standards and Compilers).

Warnings

GNU Fortran

-Wall in GNU Fortran is not "every warning": it enables a documented list, and -Wextra adds more. The versioned manual for 16.2 gives:

module scale_lib
  use, intrinsic :: iso_fortran_env, only: real64
  implicit none
contains
  function grown(a) result(b)

Runtime checks and finding bugs

Static warnings cannot see an index computed at run time. The cheapest way to find out-of-range subscripts, use of undefined values and floating-point exceptions is to run the real program with checks switched on, in a build used by tests and by developers, never in a performance run.

Backtraces

On a fatal runtime error or signal the GNU Fortran runtime prints a backtrace by default: the 16.2 manual documents -fno-backtrace as the way to turn it off, and the runs above printed backtraces without -fbacktrace (that option is still accepted and is what most examples on the web quote). module kernel_mod
  use, intrinsic :: iso_fortran_env, only: real64
  implicit none
  private
  public :: jacobi_sweep
contains
  subroutine jacobi_sweep(u, unew, residual)
    real(real64), intent(in) :: u(:, :)
    real(real64), intent(out) :: unew(:, :)
    real(real64), intent(out) :: residual
    integer :: i, j
    residual = 0.0_real64
    unew = u
    do j = 2, size(u, 2) - 1
      do i = 2, size(u, 1) - 1
        unew(i, j) = 0.25_real64 * (u(i-1, j) + u(i+1, j) + u(i, j-1) + u(i, j+1))
        residual = max(residual, abs(unew(i, j) - u(i, j)))
      end do
    end do
  end subroutine jacobi_sweep
end module kernel_mod

Automatic arrays and the stack

Where a local array lives is processor-dependent: the standard does not say stack or heap. The two compilers differ, and the difference can be the difference between a program that runs and one that crashes.

module work_mod
  use, intrinsic :: iso_fortran_env, only: real64
  implicit none
contains
  function mean_of_scaled(n) result(m)
    integer, intent(in) :: n
    real(real64) :: m

    do i = 1, n
      tmp(i) = real(i, real64)
    end do

  end function mean_of_scaled
end module work_mod

Preprocessing

The Fortran standard has no preprocessor (it has include lines, 6.4 in J3/23-007r1); everything on this section is vendor behavior. By convention .F90 runs the C-style preprocessor and .f90 does not.

program pp_demo
  implicit none
#ifdef __GFORTRAN__
  print '(a)', 'compiled by gfortran'
#elif defined(__flang__)
  print '(a)', 'compiled by flang'
#else
  print '(a)', 'compiled by another compiler'
#endif
#ifdef USE_CHECKS
  print '(a)', 'checks enabled'
#endif
end program pp_demo

Saved as pp_demo.F90:

gfortran pp_demo.F90 -o pp_demo && ./pp_demo
gfortran -DUSE_CHECKS pp_demo.F90 -o pp_demo && ./pp_demo
flang pp_demo.F90 -o pp_demo && ./pp_demo
flang -DUSE_CHECKS pp_demo.F90 -o pp_demo && ./pp_demo
compiled by gfortran
compiled by gfortran
checks enabled
compiled by flang
compiled by flang
checks enabled

Source: GNU Fortran 16.2 manual: Options controlling Fortran preprocessing

Saved as pp_lower.f90 instead, with no flags, gfortran treats the # lines as source and prints Warning: Illegal preprocessor directive for each one; Flang preprocesses the file but defines neither predefined macro, so it runs and prints compiled by another compiler; and gfortran -cpp pp_lower.f90 prints compiled by gfortran. The rule is therefore: -cpp (both compilers) or an upper-case extension switches on predefined macros; -nocpp switches them off; -D<macro>[=<value>] and -U<macro> define and remove macros, -I finds includes, -E shows the result, and -M, -MD, -MF, -MT write make-style dependency files in gfortran (see Building with Make, CMake and Meson). The macros __GFORTRAN__ and __flang__ identify the compiler. The preprocessor is a C one: it does not understand Fortran’s // concatenation or ' quotes, which causes real bugs in long lines. Prefer a plain-Fortran logical, parameter constant and if over conditional compilation, and keep #ifdef for platform and library differences. gfortran’s -fpre-include=<file> pre-includes a header in every unit.

Linking and the runtime libraries

Fortran is linked like C. Each compiler’s runtime provides the I/O, formatted output, intrinsics and error handling that a Fortran program calls, and the driver adds it to the link line. The example is the same module-and-external-subroutine program in three files, so that the symbol names and the link steps can be inspected.

module shapes_mod
  use, intrinsic :: iso_fortran_env, only: real64
  implicit none
  private
  public :: disc_area
contains
  pure function disc_area(r) result(a)
    real(real64), intent(in) :: r
    real(real64) :: a
    a = acos(-1.0_real64) * r * r
  end function disc_area
end module shapes_mod

Source: GNU Fortran 16.2 manual: Options for influencing the linking step

subroutine report_area(r)
  use, intrinsic :: iso_fortran_env, only: real64
  use shapes_mod, only: disc_area
  implicit none
  real(real64), intent(in) :: r
  print '(a, f0.4)', 'area = ', disc_area(r)
end subroutine report_area
program main_link
  use, intrinsic :: iso_fortran_env, only: real64
  implicit none
  external :: report_area
  call report_area(2.0_real64)
end program main_link
gfortran -std=f2023 -Wall -Wextra -pedantic -c shapes_mod.f90 legacy.f90 main_link.f90   # one compile per file
nm -C shapes_mod.o legacy.o main_link.o | grep -E ' [TU] '
gfortran shapes_mod.o legacy.o main_link.o -o app && ./app

Fortran code that uses coarrays also needs the coarray library: gfortran 16 takes -fcoarray=lib and links libcaf_shmem, and its valid values are none, single and lib only (see Coarrays, Images and Synchronization); Flang has an experimental -fcoarray. Vendor extensions and staying portable

The standard allows a processor to accept additional forms and relationships as long as they do not conflict with the standard ones (4.2), and every compiler does. A program that uses them is not standard-conforming and fails on the next compiler. Both compilers publish their lists: the GNU Fortran manual’s "Extensions" chapter has a list of "Extensions implemented in GNU Fortran" and one of "Extensions not implemented in GNU Fortran" (abbreviated GF Extensions in the outline of this guide), and the Flang documentation page "Fortran Extensions supported by Flang" (Extensions.html, FN Extensions) groups them as intentional violations of the standard, default-on extensions, opt-in extensions and unsupported features. The practical recipe for portable code:

  • build with -std=f2023 -pedantic -Wall -Wextra on gfortran and without any special option on Flang, in CI;

  • never use real*8, integer*4, double precision in new code (use iso_fortran_env kinds), non-standard intrinsics, %val, Cray pointers (-fcray-pointer, -funsafe-cray-pointers), DEC structures (-fdec-structure, -fdec), -fbackslash, -fdollar-ok, hollerith constants or .xor.;

  • use iso_c_binding, iso_fortran_env and the ieee_* modules for everything the old extensions provided;

  • put a vendor extension that you cannot avoid behind a module, so one file changes on the next compiler;

  • label the minimum compiler versions in the README and test them.

The Flang options that make a legacy extension available are opt-in and named after the extension: -fbackslash, -flogical-abbreviations (.t., .f.), -fxor-operator (.xor.), -falternative-parameter-statement, -funsigned and -fimplicit-none-ext; gfortran groups the DEC-compatible ones under -fdec (-fdec-structure, -fdec-math, -fdec-include, -fdec-static, -fdec-blank-format-item and others). -funsigned in both compilers enables the experimental unsigned integer type (a Fortran 202y item, see What’s New and Fortran 2028 Preview). Also worth a look is -fc-prototypes, which makes gfortran print a C prototype for each bind(c) interface.

Where the books are outdated

  • Option names. Older textbooks teach -fbounds-check, -Mbounds, -ffloat-store, -pg as the way to debug and tune. -fbounds-check and -fcheck-array-temporaries are deprecated aliases of -fcheck=bounds and -fcheck=array-temps in GNU Fortran; -fcheck=all is the complete form.

  • Compiler identities. Pre-2025 material names ifort (discontinued in oneAPI 2025.0 in favor of ifx), flang-new (renamed flang in LLVM 20), and old NAG releases. Option lists written for those still mostly apply to ifx and Flang, but check each one with --help.

  • Standard level. -std=f95 and -std=f2003 are what the old books assume; the current level is -std=f2023, with -std=f202y for experiments.

  • Build tools. Books describe make; fpm, CMake and Meson now set most of these flags for you.

  • Stack and kind flags. -fno-automatic and -fdefault-real-8 are legacy g77 habits. They still exist and still have side effects (above).

  • Debugging. Traceback is on by default in gfortran; and -g is what produces line numbers.

Pitfalls

  • The default is -std=gnu. A clean gfortran file.f90 proves nothing about portability; add -std=f2023 -pedantic.

  • -Wall is not all. -Wextra, -Wconversion-extra, -Wimplicit-interface, -Wuse-without-only and -Wrealloc-lhs are separate.

  • Flang has no checking build. No bounds, uninitialized-variable or exception-trap flags exist in 23.1; do not assume a Flang build is a debugging build.

  • Documentation is not versioned like the compiler. The unversioned GNU Fortran manual describes the development branch (-fcoarray=shared, -Wundefined-vars do not exist in 16.2).

  • -finit-local-zero hides bugs. Use -finit-real=snan for finding them.

  • -O3 and -Ofast change the stack. -fstack-arrays can turn a working program into a segmentation fault with the same source.

  • -ffast-math removes NaN checks. ieee_is_nan returns false for a real NaN; keep it out of any code that tests for NaN or relies on ieee_arithmetic.

  • -march=native produces a non-portable binary.

  • -fdefault-real-8 turns double precision into 16 bytes.

  • Module files and objects of different compilers do not mix. Use a separate directory (and separate libraries) per compiler.

  • Link errors with C drivers. Add -lgfortran -lm (or the Flang runtime) when the final link is not done by the Fortran driver.

  • -J needs an existing directory.

  • The preprocessor depends on the extension. .f90 with #ifdef lines is not preprocessed by gfortran.

  • A runtime check can change timing and hide a race. Test with and without -fcheck=all.
