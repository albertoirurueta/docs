Floating-Point and IEEE Arithmetic

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Fortran 2023 (ISO/IEC 1539-1:2023, J3/23-007r1) and was checked on 2026-10-19. Every example was compiled warning-free with gfortran -std=f2023 -Wall -Wextra -pedantic -fimplicit-none -fcheck=all (GNU Fortran 16.2) and run, and every example was also built and run with LLVM Flang 23 unless the text says otherwise; the output shown is real output. Both compilers ran in a Linux container on an aarch64 (Arm) processor, which matters on this page more than on most: the floating-point status registers, trapping behaviour and a few support inquiries differ between processor families, so results that depend on the processor are labelled and were not checked on x86-64. Examples that are deliberately wrong, or that expose a difference between the compilers, are labelled as such and show the real diagnostics. The two compilers differ more here than on any other topic of this section, and the text says where. Exceptions and IEEE arithmetic are clause 17 of the standard: 17.1 gives the overview, 17.3 the exceptions, 17.4 the rounding modes, 17.5 the underflow mode, 17.6 halting, 17.7 the floating-point modes and status, 17.10 the summary of the procedures and 17.11 their specifications. The numeric model is 16.4, the real type is 7.4.3.2 and the evaluation of numeric operations is 10.1.5.2.4.

Floating-point numbers are the one numeric type whose values are not what they look like. 0.1 is not a number a real variable can hold, a sum can depend on the order of its terms, a comparison with == is almost always a bug, and a division by zero is not necessarily an error. Fortran leaves most of this to the processor and, since Fortran 2003, offers the three intrinsic modules ieee_exceptions, ieee_arithmetic and ieee_features to ask what the processor does and to control it. They expose the facilities of ISO/IEC 60559:2020, the standard that is also published as IEEE 754-2019 and which Fortran 2023 adopts. This page explains the model, the special values, the comparison problem, every entity of the three modules, the exception flags and halting, the rounding and underflow modes, and the compiler options that quietly switch these guarantees off. The numeric model functions (epsilon, fraction, spacing, transfer and the bit intrinsics) are in Numeric Model, Bit Manipulation and Conversion, the kinds in Intrinsic Types and Kinds, the edit descriptors in Format Specifications and Edit Descriptors, stop and error reporting in Error Handling and Program Termination and the compiler flags in Compilers and Compiler Options. The running example is the heatflow solver: an explicit time stepper whose arithmetic stays finite only below a stability limit, which makes it a natural place to use ieee_is_finite and the exception flags (see Worked example: detecting a diverging heatflow run).

Fortran and IEEE: what is promised and what is not

Fortran is older than IEEE arithmetic, and the standard is written so that a processor without IEEE arithmetic can conform. The language therefore has two layers.

  • The numeric model (16.4). A real kind is described by a set of model numbers, zero or s * b**e * (f1/b + f2/b**2 + ... + fp/b**p) with a sign s, a radix b, a number of digits p, digits fk and an exponent e between a minimum and a maximum, and the inquiry functions radix, digits, minexponent, maxexponent, epsilon, tiny, huge, precision and range report its parameters. This layer says nothing about how arithmetic is rounded or what happens on overflow. 10.1.5.2.4 lets a processor evaluate any mathematically equivalent expression provided the integrity of parentheses is kept, and says plainly that mathematically equivalent expressions can give different results. An operation whose result is not defined by the arithmetic of the processor, such as an overflow where the processor has no infinity, is prohibited.

  • The IEEE modules (clause 17). Whether the modules are provided at all is processor dependent (17.1). When they are, the inquiry functions ieee_support_datatype, ieee_support_nan and the others tell, kind by kind, which parts of ISO/IEC 60559:2020 the processor implements, and the other procedures read and change the exception flags, the halting mode, the rounding mode and the underflow mode. Complete conformance is not required, even for a kind for which ieee_support_datatype is true: it requires only that the normal numbers are exactly those of an IEEE format, that addition, subtraction and multiplication conform in at least one rounding mode for normal operands and results, and that abs, ieee_rem, ieee_copy_sign, ieee_logb and ieee_unordered provide the corresponding IEEE operations (17.9).

Nothing in the language says that default real is a 32-bit IEEE number, that double precision is 64-bit, or that the processor rounds to nearest. In practice the compilers tested use IEEE binary32 for default real and binary64 for double precision, and the examples below confirm it with ieee_support_standard on both. The portable reading of the standard is: do not rely on IEEE behaviour without asking, and ask with the inquiry functions of ieee_arithmetic.

The first example prints the model parameters of three kinds and then the bit pattern of a few real32 values, taken apart with transfer into an integer. The fraction field of 0.1 shows why it has no exact representation: the pattern 1100 1100 1100 ... repeats and is rounded at the end.

program model_and_bits
  use, intrinsic :: iso_fortran_env, only: real32, real64, real128, int32, int64
  implicit none
  integer, parameter :: sp = real32, dp = real64, qp = real128
  real(sp) :: a
  real(dp) :: b
  real(qp) :: c

  print '(a)', 'kind  radix digits precision  range minexp maxexp    epsilon      tiny         huge'
  print '(a, 6(1x, i6), 3(1x, es12.4e4))', 'sp  ', radix(a), digits(a), precision(a), range(a), &
    minexponent(a), maxexponent(a), epsilon(a), tiny(a), huge(a)
  print '(a, 6(1x, i6), 3(1x, es12.4e4))', 'dp  ', radix(b), digits(b), precision(b), range(b), &
    minexponent(b), maxexponent(b), epsilon(b), tiny(b), huge(b)
  print '(a, 6(1x, i6), 3(1x, es12.4e4))', 'qp  ', radix(c), digits(c), precision(c), range(c), &
    minexponent(c), maxexponent(c), epsilon(c), tiny(c), huge(c)

  ! smallest positive subnormal = 2**(minexponent - digits)
  print '(a, es15.7e3)', 'smallest subnormal sp: ', scale(1.0_sp, minexponent(a) - digits(a))
  print '(a, es15.7e3)', 'smallest subnormal dp: ', scale(1.0_dp, minexponent(b) - digits(b))
  print '(a, es15.7e3)', 'tiny(sp) / 2**23     : ', scale(tiny(a), -(digits(a) - 1))

  call show_bits(1.0_sp)
  call show_bits(-0.0_sp)
  call show_bits(0.1_sp)
  call show_bits(tiny(a))
  call show_bits(scale(1.0_sp, minexponent(a) - digits(a)))
  call show_bits(huge(a))

contains

  subroutine show_bits(x)
    real(sp), intent(in) :: x
    integer(int32) :: w
    character(len=32) :: s
    integer :: k
    w = transfer(x, w)
    do k = 0, 31
      s(32 - k:32 - k) = merge('1', '0', btest(w, k))
    end do
    print '(es15.7e3, 2x, a, 1x, a, 1x, a)', x, s(1:1), s(2:9), s(10:32)
  end subroutine show_bits

end program model_and_bits

The output is identical with Flang. Reading it:

  • The model parameters match the table: digits is 24, 53 and 113, minexponent is -125, -1021 and -16381 and maxexponent is 128, 1024 and 16384. Fortran’s exponent range is one more than the IEEE one because Fortran writes the significand as 0.1xxx times a power of two, with the point before the leading digit, where IEEE writes 1.xxx. IEEE’s smallest normal exponent -126 is Fortran’s minexponent -125, and the largest, 127, is 128.

  • tiny is the smallest positive normal number (2^-126 for real32, 1.1755E-38) and huge the largest finite number ((2 - 2^-23) * 2^127, 3.4028E+38). epsilon is the spacing of the numbers just above 1, 2^-23 for real32 (1.1921E-07). It is not the smallest number that can be added to 1, and it is not the unit roundoff: with round-to-nearest the unit roundoff is half of it.

  • The bit patterns confirm the layout. 1.0 has biased exponent 01111111 (127, a true exponent of 0) and an all-zero fraction. -0.0 has the sign bit set and everything else zero: signed zero exists. tiny has biased exponent 1 and a zero fraction. The line before the last shows the smallest subnormal: biased exponent 0 and fraction 1, a value of 2^-149 (1.4013E-45), which the program also computes as scale(1.0_sp, minexponent - digits). huge has the largest finite exponent 11111110 and an all-ones fraction. The exponent field 11111111 is reserved for infinities (fraction zero) and NaNs (fraction nonzero).

  • The table on the first lines uses es12.4e4, because the real128 tiny and huge have four-digit exponents, and i6 for the integers, because -16381 does not fit in i5 (a first attempt with i5 printed asterisks for that entry), see Format Specifications and Edit Descriptors.

The number line, subnormals and spacing

The floating-point numbers are not evenly spaced. Within each interval between consecutive powers of two (a binade) the numbers are evenly spaced, and the spacing doubles from one binade to the next, so the relative spacing is nearly constant. That is what epsilon measures. Below tiny, the IEEE standard fills the gap with subnormal numbers (also called denormal numbers): numbers with the minimum exponent and a leading significand digit of 0, which are evenly spaced down to zero with the same spacing as the first binade. This gradual underflow means that the difference of two distinct floating-point numbers is never zero, a property that many convergence tests and divisions silently rely on.

Four consequences are worth keeping in mind.

  • Absolute spacing grows with magnitude. spacing(1.0e10) is 1024 for real32, so adding 1 to 1.0e10 changes nothing. Panel C of the figure shows the doubling at 1.0. A tolerance chosen for numbers near 1 is wrong for numbers near 1e10 or 1e-10.

  • Subnormals are slow and imprecise. They have fewer significant digits than normal numbers and, on many processors, arithmetic that produces or consumes them is much slower than normal arithmetic. Some processors can flush them to zero (abrupt underflow), which is why the underflow mode exists, see Underflow mode and subnormals.

  • Overflow is not a hard limit. A result larger than huge is rounded: in round-to-nearest it becomes infinity when it is at least huge plus half the spacing of the top binade, otherwise it stays huge. In directed rounding modes the rule differs, see Rounding modes.

  • nearest, spacing, rrspacing, fraction, exponent, scale and set_exponent are the Fortran functions that navigate the model without bit tricks; they are described in the numeric model page and used above.

Exceptional values: signed zero, infinity, NaN and subnormals

ISO/IEC 60559:2020 specifies four kinds of value besides the ordinary normal numbers (17.8): signed zeros, subnormal values, infinities created by overflow and division by zero, and NaN (not-a-number) values created by undefined operations. The following table says how each arises, what the usual arithmetic does with it and how Fortran tests for it.

NaNs come in two forms. A quiet NaN propagates silently through arithmetic. A signaling NaN raises the invalid exception when it is used as an operand; it is meant to mark uninitialised data, and -ffpe-trap=invalid or -fsignaling-nans can turn that into a trap. The fraction field of a NaN can carry extra information, which is why a Fortran NaN may print as NaN(...) on some compilers (13.7.2.3.2).

Classifying values with ieee_class and creating them with ieee_value

ieee_class(x) returns a value of the derived type ieee_class_type, which has exactly eleven values: the constants ieee_signaling_nan, ieee_quiet_nan, ieee_negative_inf, ieee_negative_normal, ieee_negative_subnormal, ieee_negative_zero, ieee_positive_zero, ieee_positive_subnormal, ieee_positive_normal, ieee_positive_inf and ieee_other_value, plus the aliases ieee_negative_denormal and ieee_positive_denormal (17.2). Values of this type can be compared only with == and /=, there is no select case on them and no conversion to a string, so the example has to write one. ieee_value(x, class) is the inverse: it returns a value of the kind of x belonging to the requested class. The value of x is not used, only its kind, so the call can be written with a scalar of any value of the right kind. Which subnormal or NaN ieee_value returns is processor dependent, but it does not vary between calls (17.11.66).

program classes_and_values
  use, intrinsic :: iso_fortran_env, only: real64
  use, intrinsic :: ieee_arithmetic
  implicit none
  integer, parameter :: dp = real64
  real(dp) :: nan, pinf, ninf, pzero, nzero, sub, one, x(8)
  character(len=18) :: names(8)
  integer :: i

  print '(a, l1, 1x, l1, 1x, l1, 1x, l1, 1x, l1)', 'support datatype/nan/inf/subnormal/standard: ', &
    ieee_support_datatype(1.0_dp), ieee_support_nan(1.0_dp), ieee_support_inf(1.0_dp), &
    ieee_support_subnormal(1.0_dp), ieee_support_standard(1.0_dp)

  one = 1.0_dp
  nan = ieee_value(one, ieee_quiet_nan)
  pinf = ieee_value(one, ieee_positive_inf)
  ninf = ieee_value(one, ieee_negative_inf)
  pzero = ieee_value(one, ieee_positive_zero)
  nzero = ieee_value(one, ieee_negative_zero)
  sub = ieee_value(one, ieee_positive_subnormal)

  x = [nan, pinf, ninf, pzero, nzero, sub, -one, one]
  names = [character(len=18) :: 'quiet NaN', '+Infinity', '-Infinity', '+0', '-0', 'subnormal', '-1', '1']
  print '(a, t20, a, t45, a, t52, a, t61, a)', 'value', 'class', 'finite', 'normal', 'neg.'
  do i = 1, size(x)
    print '(a18, 1x, a24, 3(2x, l5))', names(i), class_name(ieee_class(x(i))), &
      ieee_is_finite(x(i)), ieee_is_normal(x(i)), ieee_is_negative(x(i))
  end do

  print *
  print '(a, 2(1x, es10.3e3), 2(1x, g0))', 'list of values  : ', pinf, sub, nan, ninf
  print '(a, f8.2, 1x, f8.2, 1x, f8.2)', 'f8.2 of NaN/+Inf/-Inf: ', nan, pinf, ninf
  print '(a, f3.0, 1x, f3.0, 1x, f3.0)', 'f3.0 of NaN/+Inf/-Inf: ', nan, pinf, ninf
  print '(a, f2.0)', 'f2.0 of +Inf: ', pinf
  print '(a, e10.3, 1x, e10.3)', 'e10.3 of +0/-0: ', pzero, nzero
  print '(a, 2(1x, l1), 1x, es11.3e3, 1x, es10.3e3)', 'pzero == nzero, signbit differs: ', &
    ieee_quiet_eq(pzero, nzero), ieee_signbit(pzero) .neqv. ieee_signbit(nzero), &
    sign(1.0_dp, nzero), atan2(pzero, nzero)

contains

  function class_name(c) result(s)
    type(ieee_class_type), intent(in) :: c
    character(len=24) :: s
    if (c == ieee_signaling_nan) then
      s = 'ieee_signaling_nan'
    else if (c == ieee_quiet_nan) then
      s = 'ieee_quiet_nan'
    else if (c == ieee_negative_inf) then
      s = 'ieee_negative_inf'
    else if (c == ieee_negative_normal) then
      s = 'ieee_negative_normal'
    else if (c == ieee_negative_subnormal) then
      s = 'ieee_negative_subnormal'
    else if (c == ieee_negative_zero) then
      s = 'ieee_negative_zero'
    else if (c == ieee_positive_zero) then
      s = 'ieee_positive_zero'
    else if (c == ieee_positive_subnormal) then
      s = 'ieee_positive_subnormal'
    else if (c == ieee_positive_normal) then
      s = 'ieee_positive_normal'
    else if (c == ieee_positive_inf) then
      s = 'ieee_positive_inf'
    else
      s = 'ieee_other_value'
    end if
  end function class_name

end program classes_and_values

Reading and writing exceptional values

Formatted output of an infinity or NaN follows 13.7.2.3.2: the field is right-justified and contains Inf or Infinity for an infinity (with a minus sign for a negative one, a plus sign optional) and NaN for a NaN, and a field too narrow for either is filled with asterisks. For widths of at least 8 (9 with a sign) the long form Infinity is used, for a shorter width that fits the short form is used, and a zero width gives the short form. Formatted input accepts the same forms on input (INF, INFINITY, NAN, optionally NAN(...), case-insensitive), and since Fortran 2018 it also accepts hexadecimal-significand numbers such as 0x1.8p+1 (13.7.2.3.2), with the EX edit descriptor for output. The standard function ieee_support_io says whether base conversion on formatted input/output conforms to ISO/IEC 60559:2020 for the four IEEE rounding modes.

program io_exceptional

Rounding error and comparing floating-point numbers

Every floating-point operation rounds its exact result to a representable number, so a computation accumulates errors, and two computations that are equal in real arithmetic can differ. The root cause is representation: 0.1 is the binary number 0.0001100110011…​, repeating forever, and the stored value is the nearest representable one. The classic symptom is that 0.1 + 0.2 is not 0.3. Whether it is depends on the kind, which is what makes a test pass on one machine and fail on another.

The next program is deliberately problematic: it uses == and /= on reals. The compiler options this section uses include -Wextra, which turns on -Wcompare-reals, and GNU Fortran warns at every comparison. The program is in default real, which is real32.

program nan_compare_warning
  use, intrinsic :: ieee_arithmetic, only: ieee_value, ieee_quiet_nan, ieee_is_nan, ieee_unordered
  implicit none
  real :: x, y, nan
  nan = ieee_value(x, ieee_quiet_nan)
  x = 0.1
  y = 0.2
  if (x + y == 0.3) print '(a)', 'sum equals 0.3'
  if (nan == nan) print '(a)', 'NaN equals itself'
  if (nan /= nan) print '(a)', 'NaN differs from itself'
  if (.not. (nan < 1.0) .and. .not. (nan >= 1.0)) print '(a)', 'NaN is neither below nor above 1'
  print '(a, l1, 1x, l1)', 'ieee_is_nan, ieee_unordered: ', ieee_is_nan(nan), ieee_unordered(nan, 1.0)

A comparison that works

An equality test on computed reals should be a test of closeness. There is no universal tolerance; the right one depends on what is being compared. The rules that work in general are:

  • Compare with a relative tolerance scaled by the larger magnitude, so that the test means the same at 1e-10 and at 1e10.

  • Add an absolute tolerance for numbers near zero, where the relative test fails because one of the numbers is zero. This one has to come from the problem, for example temperatures within 1e-9 kelvin, and has no useful universal default.

  • Treat NaN as unequal to everything, and make the infinities equal only to themselves.

  • Choose the relative tolerance from epsilon of the kind, as a small multiple (a few ulps), not a literal such as 1.0e-6. A literal that is too small for real32 is never satisfied, and one that is too large for real64 hides real errors.

  • When the question is exactly how many representable numbers apart two values are, count units in the last place (ulps) by mapping the bit pattern to an integer that increases with the value.

module heatflow_compare
  use, intrinsic :: iso_fortran_env, only: real64, int64
  use, intrinsic :: ieee_arithmetic, only: ieee_is_finite, ieee_is_nan, ieee_quiet_eq
  implicit none
  private
  public :: dp, nearly_equal, ulp_distance
  integer, parameter :: dp = real64

contains

  !> Absolute-or-relative comparison: equal if they differ by at most abs_tol,
  !> or by at most rel_tol times the larger magnitude. NaN is never equal to anything.
  pure logical function nearly_equal(a, b, rel_tol, abs_tol) result(ok)
    real(dp), intent(in) :: a, b
    real(dp), intent(in), optional :: rel_tol, abs_tol
    real(dp) :: rt, at
    rt = 4.0_dp*epsilon(a)
    at = tiny(a)
    if (present(rel_tol)) rt = rel_tol
    if (present(abs_tol)) at = abs_tol
    if (ieee_is_nan(a) .or. ieee_is_nan(b)) then
      ok = .false.
    else if (ieee_quiet_eq(a, b)) then       ! also true for +0 and -0, and for equal infinities
      ok = .true.
    else if (.not. (ieee_is_finite(a) .and. ieee_is_finite(b))) then
      ok = .false.                           ! one infinity, or opposite infinities
    else
      ok = abs(a - b) <= max(at, rt*max(abs(a), abs(b)))
    end if
  end function nearly_equal

  !> Number of representable doubles between a and b (monotonic integer mapping).
  pure integer(int64) function ulp_distance(a, b) result(d)
    real(dp), intent(in) :: a, b
    d = abs(ordered(a) - ordered(b))
  end function ulp_distance

  pure integer(int64) function ordered(x) result(k)
    real(dp), intent(in) :: x
    k = transfer(x, k)
    if (k < 0_int64) k = -iand(k, huge(k))   ! sign-magnitude to two's complement: -0 maps to 0
  end function ordered

end module heatflow_compare

program comparison
  use heatflow_compare
  use, intrinsic :: ieee_arithmetic, only: ieee_quiet_eq, ieee_value, ieee_quiet_nan, ieee_positive_inf
  implicit none
  real(dp) :: a, b, c, nan, inf, s
  integer :: i

  a = 0.1_dp
  b = 0.2_dp
  c = 0.3_dp

  print '(a, l1)', 'nearly_equal(0.1 + 0.2, 0.3)      : ', nearly_equal(a + b, c)
  print '(a, es10.3e3)', 'difference 0.1 + 0.2 - 0.3        : ', (a + b) - c

Quiet and signaling comparisons

ISO/IEC 60559:2020 defines two kinds of comparison predicate. A signaling predicate raises the invalid exception when an operand is a NaN. A quiet predicate raises it only for a signaling NaN. Fortran 2018 added both (Annex C.1): the intrinsic relational operators <, <=, >, >= are signaling and ==, /= are quiet (Table 17.1), and the functions ieee_quiet_eq, _ne, _lt, _le, _gt, _ge and ieee_signaling_eq through _ge (17.11.28 to 17.11.33 and 17.11.45 to 17.11.50) select the behaviour explicitly. ieee_unordered(x, y) tests whether either argument is a NaN without any exception for a quiet NaN.

program quiet_signaling
  use, intrinsic :: iso_fortran_env, only: real64
  use, intrinsic :: ieee_arithmetic
  implicit none
  integer, parameter :: dp = real64
  real(dp) :: one, nan, snan
  logical :: res, inv

  one = 1.0_dp + real(command_argument_count(), dp)
  nan = ieee_value(one, ieee_quiet_nan)
  snan = ieee_value(one, ieee_signaling_nan)

  print '(a26, 2x, a8, 2x, a)', 'comparison (NaN, 1)', 'result', 'invalid flag afterwards'

  call ieee_set_flag(ieee_invalid, .false.)
  res = nan < one
  call ieee_get_flag(ieee_invalid, inv)
  print '(a26, 2x, l8, 2x, l1)', 'nan < 1 (relational)', res, inv

  call ieee_set_flag(ieee_invalid, .false.)
  res = ieee_quiet_lt(nan, one)
  call ieee_get_flag(ieee_invalid, inv)
  print '(a26, 2x, l8, 2x, l1)', 'ieee_quiet_lt', res, inv

  call ieee_set_flag(ieee_invalid, .false.)
  res = ieee_signaling_lt(nan, one)
  call ieee_get_flag(ieee_invalid, inv)
  print '(a26, 2x, l8, 2x, l1)', 'ieee_signaling_lt', res, inv

  call ieee_set_flag(ieee_invalid, .false.)
  res = ieee_quiet_eq(snan, one)
  call ieee_get_flag(ieee_invalid, inv)
  print '(a26, 2x, l8, 2x, l1)', 'quiet_eq, signaling NaN', res, inv

  call ieee_set_flag(ieee_invalid, .false.)
  res = ieee_unordered(nan, one)
  call ieee_get_flag(ieee_invalid, inv)
  print '(a26, 2x, l8, 2x, l1)', 'ieee_unordered', res, inv
end program quiet_signaling

The three IEEE modules

The three modules are intrinsic modules (14.2.1). They are accessed with a use statement whose nature is intrinsic, written use, intrinsic :: ieee_arithmetic. Their types and procedures are not themselves intrinsic (17.1, Note 1). In a scoping unit that accesses ieee_exceptions or ieee_arithmetic the exceptions ieee_overflow and ieee_divide_by_zero are supported for all kinds of real and complex IEEE floating-point data (17.1); whether the others are is for ieee_support_flag to say.

  • ieee_exceptions defines the exception flag type and its constants, the modes and status types and the procedures that get, set and save flags, halting modes and the status.

  • ieee_arithmetic behaves as if it contained use ieee_exceptions (everything public in ieee_exceptions is public in it), and adds the class and rounding types and everything else: the inquiry functions, the elemental functions, the rounding and underflow procedures.

  • ieee_features defines only the type ieee_features_type and named constants: ieee_datatype, ieee_denormal, ieee_divide, ieee_halting, ieee_inexact_flag, ieee_inf, ieee_invalid_flag, ieee_nan, ieee_rounding, ieee_sqrt, ieee_subnormal and ieee_underflow_flag. They are not data to be passed to procedures: their accessibility is a request to the compiler. If a scoping unit accesses a constant of ieee_features, the processor must support that feature for at least one kind of real (17.1). If ieee_exceptions or ieee_arithmetic is accessed but ieee_features is not, the supported subset is processor dependent, and the fullest support comes from accessing both ieee_arithmetic and all of ieee_features, at the cost that execution might be slowed by features that are not needed.

If a scoping unit does not access any of the three modules, the processor decides the level of support, which need not include any exception, and a flag that is signaling on entry is still signaling on exit (17.1).

! Requesting the fullest IEEE support in a scoping unit (17.1): access all of IEEE_FEATURES as well.
module numerics_ieee
  use, intrinsic :: ieee_arithmetic
  use, intrinsic :: ieee_features
  implicit none
  private
  public :: describe
contains

    print '(a, l1)', 'ieee_support_standard() for all kinds: ', ieee_support_standard()
    print '(a, l1)', 'ieee_support_datatype() for all kinds: ', ieee_support_datatype()
    print '(a, l1)', 'ieee_support_underflow_control() for all kinds: ', ieee_support_underflow_control()
  end subroutine describe
end module numerics_ieee

Rules for using the inquiry functions:

  • The result describes a kind, not a value. The argument may be an unallocated or undefined variable, a literal or an array.

  • ieee_support_datatype(x) is the gate: if it is false, almost every other IEEE function must not be invoked with x (the restriction is on the program, 17.11.1). Write if (ieee_support_datatype(x)) then ... else ... end if around calls in portable libraries.

  • ieee_support_standard(x) is true when the datatype, divide, flag, halting, inf, nan, rounding, sqrt and subnormal inquiries are all true for x: it is the quick test of whether a kind is IEEE.

  • ieee_support_flag(flag, x) and ieee_support_halting(flag) are transformational: they may be used in a constant expression where x is a constant, but Flang notes that where the answer is not known at compile time (on Arm processors, where halting is a hardware option that varies between processors) it generates a runtime check and rejects ieee_support_halting in a context that needs a constant (Flang documentation, Extensions).

  • ieee_support_rounding(mode, x) is also transformational; ieee_support_io says that formatted base conversion conforms for the rounding modes up, down, zero and nearest.

Exceptions, flags and halting

IEEE arithmetic separates signalling an exception from stopping. When an exceptional condition arises, the operation delivers a default result, and a sticky status flag is raised. The flag stays raised until the program clears it. Nothing else happens unless the program has asked for halting, which turns the condition into a trap. This is the model the Fortran procedures expose. The five exceptions (17.3) are:

Each flag has a value, quiet or signaling, read by ieee_get_flag(flag, value) where value is true when the flag is signaling, set by ieee_set_flag(flag, .true. or .false.). The flag arguments may be arrays, so the whole usual set is read or cleared in one call with the constants ieee_usual (overflow, divide-by-zero, invalid) and ieee_all. The flag is initially quiet and stays signaling once set within a procedure, unless cleared. The first example performs several operations and prints the five flags after each. The values the compiler cannot see through come from command_argument_count(), because a division by the literal 0.0 would be rejected or folded at compile time.

program flags
  use, intrinsic :: iso_fortran_env, only: real64
  use, intrinsic :: ieee_arithmetic          ! also makes everything of ieee_exceptions available
  implicit none
  integer, parameter :: dp = real64
  type(ieee_flag_type), parameter :: all_flags(5) = [ieee_invalid, ieee_overflow, ieee_divide_by_zero, &
                                                      ieee_underflow, ieee_inexact]
  real(dp) :: zero, big, small, neg, three, r
  logical :: raised(5)
  integer :: i

  print '(a, 5(1x, l1))', 'ieee_support_flag (invalid overflow div0 underflow inexact):', &
    [(ieee_support_flag(all_flags(i), 1.0_dp), i = 1, 5)]
  print '(a, 5(1x, l1))', 'ieee_support_halting for the same flags                  :', &
    [(ieee_support_halting(all_flags(i)), i = 1, 5)]

  ! values the optimizer cannot see through: computed from a run-time quantity
  zero = real(command_argument_count(), dp)
  big = huge(1.0_dp)*(1.0_dp + zero)
  small = tiny(1.0_dp)*(1.0_dp + zero)
  neg = -1.0_dp - zero
  three = 3.0_dp + zero

  print '(a24, 5(1x, a9), 2x, a)', 'operation', 'invalid', 'overflow', 'div-by-0', 'underflow', 'inexact', 'result'
  call ieee_set_flag(ieee_all, .false.)
  call ieee_get_flag(all_flags, raised)
  call report('all flags cleared', raised, 0.0_dp)
  call ieee_set_flag(ieee_all, .false.)     ! formatted output may itself set the inexact flag

  r = 1.0_dp/zero
  call ieee_get_flag(all_flags, raised)
  call report('1/0', raised, r)
  call ieee_set_flag(ieee_all, .false.)

  r = sqrt(neg)
  call ieee_get_flag(all_flags, raised)
  call report('sqrt(-1)', raised, r)
  call ieee_set_flag(ieee_all, .false.)

  r = big*2.0_dp
  call ieee_get_flag(all_flags, raised)
  call report('huge*2', raised, r)
  call ieee_set_flag(ieee_all, .false.)

  r = small/1.0e10_dp
  call ieee_get_flag(all_flags, raised)
  call report('tiny/1e10', raised, r)
  call ieee_set_flag(ieee_all, .false.)

  r = 1.0_dp/three
  call ieee_get_flag(all_flags, raised)
  call report('1/3', raised, r)
  call ieee_set_flag(ieee_all, .false.)

  r = 0.5_dp/(1.0_dp + zero)
  call ieee_get_flag(all_flags, raised)
  call report('0.5/1 (exact)', raised, r)
  call ieee_set_flag(ieee_all, .false.)

  ! flags are sticky: they stay signaling until they are cleared
  r = sqrt(neg)
  r = 1.0_dp + r*zero
  call ieee_get_flag(all_flags, raised)
  call report('NaN propagates', raised, r)

contains

  ! Prints a row. It must not query the flags itself: see the text about flags on entry to a procedure.
  subroutine report(label, signaling, value)
    character(len=*), intent(in) :: label
    logical, intent(in) :: signaling(:)
    real(dp), intent(in) :: value
    print '(a24, 5(1x, a9), 2x, es24.17e3)', label, merge('SIGNALING', 'quiet    ', signaling), value
  end subroutine report

end program flags

Reading the table:

  • 1/0 signals only divide-by-zero, sqrt(-1) only invalid, as the standard says.

  • huge * 2 signals overflow and inexact, and tiny / 1e10 signals underflow and inexact. This is IEEE behaviour: an overflowed or underflowed result is inexact. The Flang documentation notes that on Arm processors the inexact flag is raised together with overflow or underflow, both by expression evaluation and by a call to ieee_set_flag.

  • 1/3 is inexact only. 0.5 / 1 is exact, so nothing is signaled.

  • The last row performs sqrt(-1) and then arithmetic on the resulting quiet NaN: only invalid is signaling, from the sqrt; the later arithmetic on a quiet NaN signals nothing new. Flags are sticky, so the program clears them after each row; without that, each row would also show the flags of every row before it.

Flags on entry to a procedure

The standard has a rule that surprises most programmers, and the two compilers disagree about it. 17.3 says that if a flag is signaling on entry to a procedure other than ieee_get_flag or ieee_get_status, the processor will set it to quiet on entry and restore it to signaling on return, and that a flag that signals during the procedure stays signaling on return. The purpose is to let each procedure examine only its own exceptions, as the standard’s example module dot does (17.12, Note 1): a function clears nothing, tests the flag after the loop, and does not see the caller’s history. The rule applies to procedures in general, not only to those that use the IEEE modules.

The next program sets overflow in the caller, calls a module procedure that only reads the flag, and reads it again in the caller afterwards.

module probe
  use, intrinsic :: ieee_arithmetic, only: ieee_get_flag, ieee_overflow
  implicit none
contains
  ! Does a callee see a flag that was signaling in its caller?
  subroutine overflow_seen_in_callee(seen)
    logical, intent(out) :: seen
    call ieee_get_flag(ieee_overflow, seen)
  end subroutine overflow_seen_in_callee
end module probe

program flags_on_entry
  use, intrinsic :: iso_fortran_env, only: real64
  use, intrinsic :: ieee_arithmetic, only: ieee_get_flag, ieee_set_flag, ieee_overflow
  use probe, only: overflow_seen_in_callee
  implicit none
  real(real64) :: big, r
  logical :: in_caller_before, in_callee, in_caller_after

  big = huge(1.0_real64)*(1.0_real64 + real(command_argument_count(), real64))
  call ieee_set_flag(ieee_overflow, .false.)
  r = big*2.0_real64                                   ! signals overflow in this scoping unit
  call ieee_get_flag(ieee_overflow, in_caller_before)
  call overflow_seen_in_callee(in_callee)
  call ieee_get_flag(ieee_overflow, in_caller_after)
  print '(a, l1)', 'caller, before the call : ', in_caller_before
  print '(a, l1)', 'callee, on entry        : ', in_callee
  print '(a, l1)', 'caller, after the call  : ', in_caller_after
  print '(a, g0)', 'result                  : ', r
end program flags_on_entry

This difference means that code which calls a helper procedure to query the flags is not portable. The portable pattern is to query the flags in the same procedure that performs the operations, as the table program above does, with the printing routine taking the already-read logicals as arguments. The report subroutine of that example takes the results as arguments and does not query anything, because under Flang 23 it would otherwise see all flags quiet.

Further rules about flags that follow from 17.3:

  • An operation whose value is never used need not signal. In a statement sequence without calls to the flag procedures, if no variable depends on an operation, whether it signals is processor dependent: the standard’s example is X = 1.0/Y followed by X = 3.0. An optimizing compiler removes dead computations, along with their flags. Use the result, as the examples here do, or print it.

  • The compiler may not signal an exception that only a not-required operation would raise. if (f(x) > 0.0) y = 1.0/z shall not signal divide-by-zero when f(x) and z are both zero, and neither shall where (a > 0.0) a = 1.0/a.

  • An unsupported exception is always quiet. ieee_invalid, ieee_underflow and ieee_inexact need not be supported.

  • Each image has its own floating-point status (17.7, Note 1), see Coarrays, Images and Synchronization.

  • The flag procedures are forbidden in a do concurrent construct (11.1.7.5, C1145 for ieee_get_flag, ieee_get_halting_mode, ieee_get_status, ieee_set_halting_mode, ieee_set_modes and ieee_set_status; C1146 for ieee_set_rounding_mode and ieee_set_underflow_mode).

Saving and restoring the status

ieee_get_status(s) stores all flags and modes in a variable of type ieee_status_type, and ieee_set_status(s) restores them. The pattern that the standard’s example (17.12, Note 2) shows for a library routine is to save the status, clear the flags, compute, test the flags and restore the status, so that a routine that expects and handles exceptions neither depends on nor disturbs its caller’s flags. The type has private components and no way to look inside, and there is no way to read a particular flag back from it (17.7). ieee_get_modes and ieee_set_modes do the same for the modes only, and may be cheaper because some processors keep modes in a register apart from the flags (17.7, Note 2).

Halting

ieee_set_halting_mode(flag, .true.) asks the processor to stop the program when the exception occurs. The halting is not precise: it may occur any time after the exception has occurred (17.6), and what stopping means is processor dependent; on Linux it is a SIGFPE signal. The initial mode is processor dependent: on both compilers here halting for ieee_divide_by_zero is initially off. ieee_get_halting_mode reads the setting, ieee_support_halting(flag) says if the processor can do it. Halting is one of the modes that ieee_get_modes saves.

program halting
  use, intrinsic :: iso_fortran_env, only: real64, output_unit
  use, intrinsic :: ieee_arithmetic
  implicit none
  real(real64) :: zero, r
  logical :: h
  type(ieee_status_type) :: saved

  zero = real(command_argument_count(), real64)
  call ieee_get_halting_mode(ieee_divide_by_zero, h)
  print '(a, l1)', 'halting on divide_by_zero by default: ', h

  ! 1. compute with halting off and inspect the flag afterwards
  call ieee_get_status(saved)
  call ieee_set_halting_mode(ieee_usual, .false.)
  r = 1.0_real64/zero
  call ieee_get_flag(ieee_divide_by_zero, h)
  print '(a, g0, a, l1)', 'halting off: 1/0 = ', r, ', flag signaling: ', h
  call ieee_set_status(saved)               ! restores flags, modes and halting
  call ieee_get_flag(ieee_divide_by_zero, h)
  print '(a, l1)', 'after ieee_set_status the flag is signaling: ', h

  ! 2. turn halting on: the next division by zero stops the program
  call ieee_set_halting_mode(ieee_divide_by_zero, .true.)
  call ieee_get_halting_mode(ieee_divide_by_zero, h)
  print '(a, l1)', 'halting on divide_by_zero now: ', h
  flush (output_unit)                       ! a trapped program does not flush its buffers
  r = 1.0_real64/zero
  print '(a, g0)', 'not reached when halting works: ', r
end program halting

Rounding modes, underflow mode and saving modes

Rounding modes

IEEE specifies five rounding-direction attributes, which correspond to the Fortran constants ieee_nearest (ties to even, the default), ieee_to_zero, ieee_up (toward +infinity), ieee_down (toward -infinity) and ieee_away (ties away from zero, required by 60559 only for decimal formats), with ieee_other for a processor-defined mode (17.4). ieee_get_rounding_mode(m) reads the mode and ieee_set_rounding_mode(m) sets it, and the initial mode is processor dependent. The mode affects arithmetic on reals of the radix in question (binary or, with radix=10, decimal), and, in some compilers, the conversion of data in formatted I/O (see below). It does not affect the value of a literal constant in the source: all literals of the same form have the same value (17.4, Note 3).

Two rules limit what the program may expect. A procedure other than the setters shall not change the rounding mode on entry and shall restore it on return (17.4), so a callee never leaves the caller’s mode changed. And constant expressions folded by the compiler are evaluated by the compiler under its rounding mode, which is why the example takes its operands from run-time data: with literals, the sum would be computed once at compile time in round-to-nearest whatever the program sets. GNU Fortran documents -frounding-math, recommended by the manual for programs that change the mode, that disables constant folding of floating-point expressions and unsafe transformations; it is documented as experimental and as not guaranteed to disable every optimization that depends on the rounding mode.

program rounding
  use, intrinsic :: iso_fortran_env, only: real32, real64
  use, intrinsic :: ieee_arithmetic
  implicit none
  type(ieee_round_type), parameter :: modes(4) = [ieee_nearest, ieee_to_zero, ieee_up, ieee_down]
  character(len=*), parameter :: mode_names(4) = [character(len=12) :: 'nearest', 'to_zero', 'up', 'down']
  type(ieee_round_type) :: current
  real(real32) :: one, three, tenth, s
  real(real64) :: x(6), rints(6, 4)
  real(real32) :: thirds(4), sums(4)
  integer :: m, i

  print '(a, 6(1x, l1))', 'ieee_support_rounding nearest/to_zero/up/down/away/other (real32): ', &
    ieee_support_rounding(ieee_nearest, 1.0_real32), ieee_support_rounding(ieee_to_zero, 1.0_real32), &
    ieee_support_rounding(ieee_up, 1.0_real32), ieee_support_rounding(ieee_down, 1.0_real32), &
    ieee_support_rounding(ieee_away, 1.0_real32), ieee_support_rounding(ieee_other, 1.0_real32)

  call ieee_get_rounding_mode(current)
  print '(a, l1)', 'the initial mode is round to nearest: ', current == ieee_nearest

  one = real(command_argument_count() + 1, real32)         ! run-time values, so nothing is folded
  three = 3.0_real32*one
  tenth = 0.1_real32*one
  x = [2.5_real64, 1.5_real64, 0.5_real64, -0.5_real64, -1.5_real64, -2.5_real64]*real(one, real64)

  do m = 1, 4
    call ieee_set_rounding_mode(modes(m))
    thirds(m) = one/three
    s = 0.0_real32
    do i = 1, 10
      s = s + tenth
    end do
    sums(m) = s
    rints(:, m) = ieee_rint(x)
  end do
  call ieee_set_rounding_mode(ieee_nearest)   ! restore before any formatted output

  print '(a)', 'mode          1/3 (real32)        ten times 0.1       ieee_rint of 2.5 1.5 0.5 -0.5 -1.5 -2.5'
  do m = 1, 4
    print '(a12, 2x, es18.10e3, 2x, es18.10e3, 2x, 6(f5.1))', mode_names(m), thirds(m), sums(m), rints(:, m)
  end do

  print '(a, 4(1x, f5.1))', 'ieee_rint(2.5, round) for nearest/to_zero/up/down: ', &
    (ieee_rint(2.5_real64*real(one, real64), modes(m)), m = 1, 4)
  print '(a, 4(1x, i0))', 'ieee_int(2.5, round) for up/down/to_zero/nearest   : ', &
    ieee_int(2.5_real64*real(one, real64), ieee_up), ieee_int(2.5_real64*real(one, real64), ieee_down), &
    ieee_int(2.5_real64*real(one, real64), ieee_to_zero), ieee_int(2.5_real64*real(one, real64), ieee_nearest)
end program rounding

Underflow mode and subnormals

Some processors let a program choose between gradual underflow (results below tiny become subnormal numbers, the IEEE behaviour) and abrupt underflow (they flush to zero), which can be faster. ieee_support_underflow_control(x) says if the control exists for the kind of x, ieee_get_underflow_mode(gradual) reads it and ieee_set_underflow_mode(gradual) sets it, and the standard forbids calling the two subroutines when the inquiry is false for every kind (restriction of 17.11.10 and 17.11.44). The underflow mode affects only reals of kinds for which the inquiry is true (17.5). The program below uses ieee_get_modes and ieee_set_modes to restore the mode in one call, and refuses to run the procedures when the control is not available.

program underflow_mode
  use, intrinsic :: iso_fortran_env, only: real32, real64
  use, intrinsic :: ieee_arithmetic
  implicit none
  real(real32) :: t32, h32
  real(real64) :: t64, h64
  logical :: gradual
  type(ieee_modes_type) :: saved

  print '(a, 2(1x, l1))', 'support underflow_control (real32, real64): ', ieee_support_underflow_control(1.0_real32), &
    ieee_support_underflow_control(1.0_real64)
  print '(a, 2(1x, l1))', 'support subnormal         (real32, real64): ', ieee_support_subnormal(1.0_real32), &
    ieee_support_subnormal(1.0_real64)

  t32 = tiny(1.0_real32)*real(1 + command_argument_count(), real32)
  t64 = tiny(1.0_real64)*real(1 + command_argument_count(), real64)

  if (.not. ieee_support_underflow_control(1.0_real32) .or. .not. ieee_support_underflow_control(1.0_real64)) then
    ! calling the underflow-mode procedures would violate their restrictions (17.11.10, 17.11.44)
    print '(a)', 'underflow mode cannot be controlled for these kinds on this processor and compiler'
  else
    call ieee_get_modes(saved)
    call ieee_get_underflow_mode(gradual)
    print '(a, l1)', 'initial underflow mode is gradual: ', gradual
    h32 = t32/2.0_real32
    h64 = t64/4.0_real64
    print '(a, es14.6e3, a, l1)', 'gradual : tiny/2 (real32) = ', h32, '  subnormal: ', ieee_class(h32) == ieee_positive_subnormal
    print '(a, es14.6e3, a, l1)', 'gradual : tiny/4 (real64) = ', h64, '  subnormal: ', ieee_class(h64) == ieee_positive_subnormal

    call ieee_set_underflow_mode(.false.)
    call ieee_get_underflow_mode(gradual)
    print '(a, l1)', 'after ieee_set_underflow_mode(.false.), gradual: ', gradual
    h32 = t32/2.0_real32
    h64 = t64/4.0_real64
    print '(a, es14.6e3, a, l1)', 'abrupt  : tiny/2 (real32) = ', h32, '  subnormal: ', ieee_class(h32) == ieee_positive_subnormal
    print '(a, es14.6e3, a, l1)', 'abrupt  : tiny/4 (real64) = ', h64, '  subnormal: ', ieee_class(h64) == ieee_positive_subnormal

    call ieee_set_modes(saved)                ! one call restores rounding, underflow and halting modes
    call ieee_get_underflow_mode(gradual)
    print '(a, l1)', 'after ieee_set_modes(saved), gradual: ', gradual
  end if
end program underflow_mode

The IEEE functions in practice

Neighbours, scaling, remainder, signs and fused multiply-add

ieee_next_after(x, y) returns the representable number next to x in the direction of y (and x if they are equal). The neighbours of zero are nonzero, the neighbour of huge toward infinity is infinity, and the difference ieee_next_after(x, +1) - x equals spacing(x). ieee_logb(x) returns the unbiased exponent as a real, equal to exponent(x) - 1, and ieee_scalb(x, i) is x * 2**i, exact whenever the result is representable. ieee_rem(x, y) is the IEEE remainder: x - y*n with n the integer nearest to x/y, so unlike mod, whose result has the sign of x, it can be negative for positive operands. ieee_copy_sign is defined for every IEEE value, including NaN and infinity. ieee_fma(a, b, c) computes a*b + c with a single rounding, and signals overflow, underflow and inexact according to the final result.

program functions
  use, intrinsic :: iso_fortran_env, only: real32, real64
  use, intrinsic :: ieee_arithmetic
  implicit none
  integer, parameter :: dp = real64
  real(dp) :: one, x, nan, pz, nz
  real(real32) :: xs

  one = 1.0_dp + real(command_argument_count(), dp)
  x = 0.1_dp*one
  nan = ieee_value(one, ieee_quiet_nan)
  pz = 0.0_dp*one
  nz = -pz

  print '(a, es25.17e3)', 'x                       = ', x
  print '(a, es25.17e3)', 'next_after(x, 1)        = ', ieee_next_after(x, 1.0_dp)
  print '(a, es25.17e3)', 'next_after(x, 0)        = ', ieee_next_after(x, 0.0_dp)
  print '(a, l1)', 'next_after(x, 1) - x == spacing(x): ', ieee_quiet_eq(ieee_next_after(x, 1.0_dp) - x, spacing(x))
  print '(a, es25.17e3)', 'next_after(+0, 1)       = ', ieee_next_after(pz, 1.0_dp)
  print '(a, es25.17e3)', 'next_after(+0, -1)      = ', ieee_next_after(pz, -1.0_dp)
  print '(a, es25.17e3)', 'next_after(huge, +Inf)  = ', ieee_next_after(huge(x), ieee_value(x, ieee_positive_inf))
  print *
  print '(a, es25.17e3)', 'ieee_logb(10)           = ', ieee_logb(10.0_dp*one)
  print '(a, i0, a, i0)', 'exponent(10) = ', exponent(10.0_dp*one), ', so ieee_logb = exponent - 1 = ', exponent(10.0_dp*one) - 1

Worked examples

A reliable hypot

The length of a vector, sqrt(x**2 + y**2), overflows when x**2 is larger than huge although the result is representable, and underflows to zero when both squares are below tiny. The cure is to scale both arguments by a power of two before squaring, which is exact, and to undo the scaling afterwards. The module below implements it with exponent and scale, handles the infinities and NaNs as C99 hypot does (a NaN with an infinity gives infinity), and also implements the pattern of the standard’s example (17.12): try the fast way, check the flags, and fall back if an exception was signaled, while saving and restoring the caller’s status.

module heatflow_norms
  use, intrinsic :: iso_fortran_env, only: real64
  use, intrinsic :: ieee_arithmetic, only: ieee_get_flag, ieee_set_flag, ieee_overflow, ieee_underflow, &
                                            ieee_is_finite, ieee_is_nan, ieee_get_status, ieee_set_status, &
                                            ieee_status_type, ieee_all, ieee_value, ieee_positive_inf
  implicit none
  private
  public :: dp, naive_hypot, safe_hypot, checked_hypot
  integer, parameter :: dp = real64

contains

  !> sqrt(x*x + y*y): the squares can overflow or underflow although the result is representable.
  elemental function naive_hypot(x, y) result(h)
    real(dp), intent(in) :: x, y
    real(dp) :: h
    h = sqrt(x*x + y*y)
  end function naive_hypot

  !> Scale both arguments by a power of two so the squares stay in range, then undo the scaling.
  elemental function safe_hypot(x, y) result(h)
    real(dp), intent(in) :: x, y
    real(dp) :: h, ax, ay, big, small, ratio
    integer :: e
    ax = abs(x)
    ay = abs(y)
    if (.not. (ieee_is_finite(ax) .and. ieee_is_finite(ay))) then
      if (ieee_is_nan(ax) .and. .not. ieee_is_finite(ay) .and. .not. ieee_is_nan(ay)) then
        h = ay                                     ! hypot(NaN, Inf) = Inf, as in C99
      else if (ieee_is_nan(ay) .and. .not. ieee_is_finite(ax) .and. .not. ieee_is_nan(ax)) then
        h = ax
      else
        h = ax + ay                                ! Inf if either is infinite, NaN if either is a NaN
      end if
      return
    end if
    big = max(ax, ay)
    small = min(ax, ay)
    if (big <= 0.0_dp) then
      h = 0.0_dp
      return
    end if
    e = exponent(big)
    ratio = scale(small, -e)                       ! small / 2**e, exact unless it underflows
    h = scale(sqrt(scale(big, -e)**2 + ratio*ratio), e)
  end function safe_hypot

  !> The "try the fast way, check the flags, fall back" pattern of the standard's own example (17.12).
  function checked_hypot(x, y, fell_back) result(h)
    real(dp), intent(in) :: x, y
    logical, intent(out) :: fell_back
    real(dp) :: h
    type(ieee_status_type) :: status
    logical :: ovf, unf
    call ieee_get_status(status)                   ! save all flags and modes
    call ieee_set_flag(ieee_all, .false.)
    h = naive_hypot(x, y)
    call ieee_get_flag(ieee_overflow, ovf)
    call ieee_get_flag(ieee_underflow, unf)
    fell_back = ovf .or. unf
    call ieee_set_status(status)                   ! put the caller's flags back
    if (fell_back) h = safe_hypot(x, y)
  end function checked_hypot

end module heatflow_norms

Worked example: detecting a diverging heatflow run

The explicit FTCS scheme of the heatflow solver is stable only if alpha * dt / dx**2 is at most 0.25 in two dimensions. Beyond that, rounding errors grow by a factor at each step, and after a few thousand steps the values overflow and then turn to NaN. The program uses the kernel ftcs_sweep of the module heatflow_kernels (the explicit step used by the solvers, see Object Oriented Programming) and checks the residual of each step with ieee_is_finite instead of waiting for garbage output. It was built together with the two module files: gfortran ... heatflow_kinds.f90 heatflow_kernels.f90 13_divergence_guard.f90.

! Detect a diverging explicit (FTCS) heat-flow run with IEEE tests instead of waiting for garbage output.
program divergence_guard
  use heatflow_kinds, only: dp, ip
  use heatflow_kernels, only: ftcs_sweep
  use, intrinsic :: ieee_arithmetic, only: ieee_is_finite, ieee_get_flag, ieee_set_flag, ieee_all, &
                                            ieee_overflow, ieee_invalid, ieee_flag_type
  implicit none
  integer, parameter :: n = 21
  real(dp), parameter :: dx = 1.0_dp/(n - 1), alpha = 1.0_dp
  real(dp) :: dt_stable, dt_unstable

  dt_stable = 0.2_dp*dx**2/alpha          ! alpha*dt/dx**2 = 0.2, below the 2D limit of 0.25
  dt_unstable = 0.3_dp*dx**2/alpha        ! 0.3 is above the limit
  call run('stable  ', dt_stable)
  call run('unstable', dt_unstable)

contains

  subroutine run(label, dt)
    character(len=*), intent(in) :: label
    real(dp), intent(in) :: dt
    real(dp) :: u(n, n), unew(n, n), residual
    integer(ip) :: step
    logical :: overflowed, invalid

    u = 0.0_dp
    u((n + 1)/2, (n + 1)/2) = 100.0_dp
    unew = u
    call ieee_set_flag(ieee_all, .false.)
    do step = 1, 4000
      call ftcs_sweep(u, unew, alpha, dt, dx, dx, residual)
      u = unew
      if (.not. ieee_is_finite(residual)) then
        call ieee_get_flag(ieee_overflow, overflowed)
        call ieee_get_flag(ieee_invalid, invalid)
        print '(a, a, i0, a, l1, a, l1)', label, ': residual is not finite at step ', step, &
          '; overflow flag ', overflowed, ', invalid flag ', invalid
        return
      end if
    end do
    print '(a, a, es10.3e3, a, f7.3)', label, ': finished, last residual ', residual, ', max temperature ', maxval(u)
  end subroutine run

end program divergence_guard

unstable: residual is not finite at step 2155; overflow flag T, invalid flag F

Source: J3/23-007r1: 17.11.12 IEEE_IS_FINITE and 17.3 The exceptions

The stable run, at a ratio of 0.2, ends with a residual of 6.4E-20 and the unstable one, at 0.3, makes the residual non-finite at step 2155 with the overflow flag signaling. Detecting the blow-up in the first step it becomes non-finite is cheap: one ieee_is_finite per step on a scalar that the loop already computes. The flags are a second channel: the ieee_overflow flag was raised by the kernel, a procedure called from here, and stays signaling in the caller on return (17.3). In a larger program, leave halting off, check ieee_is_finite on summary quantities, and report which flags are signaling when you stop.

What -ffast-math does to a program

The next program has the two kinds of damage in one place. plain_sum adds ten million real32 values of 0.1 in a loop, kahan_sum does it with compensated (Kahan) summation (it keeps the rounding error of each addition in a second variable and feeds it back), and the last two lines test a NaN in two ways.

module kahan
  use, intrinsic :: iso_fortran_env, only: real32
  implicit none
  private
  public :: plain_sum, kahan_sum
  integer, parameter :: sp = real32
contains

  function plain_sum(x) result(s)
    real(sp), intent(in) :: x(:)
    real(sp) :: s
    integer :: i
    s = 0.0_sp
    do i = 1, size(x)
      s = s + x(i)
    end do
  end function plain_sum

  ! Compensated (Kahan) summation: c carries the low-order bits lost by each addition.
  function kahan_sum(x) result(s)
    real(sp), intent(in) :: x(:)
    real(sp) :: s, c, y, t
    integer :: i
    s = 0.0_sp
    c = 0.0_sp
    do i = 1, size(x)
      y = x(i) - c
      t = s + y
      c = (t - s) - y        ! algebraically zero; exactly the rounding error of the addition
      s = t
    end do
  end function kahan_sum

end module kahan

program fast_math
  use, intrinsic :: iso_fortran_env, only: real32, real64
  use, intrinsic :: ieee_arithmetic, only: ieee_is_nan, ieee_value, ieee_quiet_nan, ieee_quiet_eq
  use kahan, only: plain_sum, kahan_sum
  implicit none
  integer, parameter :: sp = real32
  real(sp), allocatable :: x(:)
  real(sp) :: nan, y
  integer :: n

  n = 10000000 + command_argument_count()
  allocate (x(n), source=0.1_sp)

  print '(a, f14.2)', 'exact sum 10^7 * 0.1 (in real32 data) : ', real(n, real64)*real(0.1_sp, real64)
  print '(a, f14.2)', 'plain_sum                             : ', plain_sum(x)
  print '(a, f14.2)', 'kahan_sum                             : ', kahan_sum(x)

  nan = ieee_value(nan, ieee_quiet_nan)
  y = nan*real(n, sp)
  print '(a, l1)', 'ieee_is_nan(y) (should be T)          : ', ieee_is_nan(y)
  print '(a, l1)', '.not. ieee_quiet_eq(y, y) (should be T): ', .not. ieee_quiet_eq(y, y)
end program fast_math

What the table says:

  • The exact sum is 1000000.01. The naive loop returns 1087937: ten million additions of a small number to a growing total, each rounded, drift by almost 9%. Compensated summation gives 1000000.00, the correctly rounded value. (Summing in real64, or using the intrinsic sum on real64 data, would also be accurate.)

  • -ffast-math removes the compensation. With -fassociative-math (enabled by -ffast-math) the compiler is allowed to regard (t - s) - y as zero, and the compensated sum collapses to the naive one. Adding -fno-associative-math brings the Kahan sum back. A numerically careful routine can be silently ruined by a build option.

  • -Ofast vectorizes the reduction (adds in a different order) and gives a third answer, 975599.12, which is not better or worse in principle, only different. The sum of a large array depends on the compiler, the option and the processor vector width, so exact reproducibility of sums needs a fixed order or compensation.

  • The NaN tests are removed under -ffast-math in both compilers: ieee_is_nan(y) and the quiet comparison of y with itself print F for a value that really is a NaN. Under -ffinite-math-only the compiler is told that NaNs cannot occur, so it believes the answer. Any code that checks NaN must not be built with fast-math: put it in a separate source file with its own options, or do not use fast-math for the project.

Fused multiply-add and expression contraction

A processor with a fused multiply-add instruction can compute a*b + c in one step with one rounding. The compiler is allowed to use it for an expression written as a multiplication followed by an addition, because it is a mathematically equivalent expression (10.1.5.2.4), and parentheses do not stop it: the standard’s rule is about the integrity of the parenthesized operation, not about the rounding of its intermediate value. Results change at the last bit, between optimization levels of the same compiler.

program contraction
  use, intrinsic :: iso_fortran_env, only: real32, real64
  implicit none
  real(real32) :: a, c, r
  a = (1.0_real32 + 2.0_real32**(-12))*real(1 + command_argument_count(), real32)
  c = -1.0_real32
  r = a*a + c
  print '(a, es24.16e3)', 'a*a + c, as written       : ', real(r, real64)
  print '(a, es24.16e3)', 'exact value of a*a + c    : ', real(a, real64)*real(a, real64) + real(c, real64)
end program contraction

Pitfalls

  • Comparing reals with == works by luck in one kind and fails in another. Compare with a tolerance, count ulps, or use ieee_quiet_eq when exactness is the intent.

  • Testing for NaN with x /= x is folded by -ffast-math. Use ieee_is_nan, and keep NaN-aware code out of fast-math builds.

  • A tolerance copied from another kind: 1.0e-6 is a few ulps in real32 and a million ulps in real64. Derive it from epsilon(x).

  • Using epsilon as the smallest positive number: that is tiny (normal) or the smallest subnormal. epsilon is the spacing at 1.

  • Flags tested in a helper procedure that the compiler may reset on entry (Flang does, gfortran does not). Read flags in the procedure that computes.

  • Computations whose result is not used do not signal on an optimizing compiler.

  • Formatted output can leave a flag signaling (g0 did under gfortran 16.2) and, under gfortran, follows the current rounding mode. Read the flags before printing, and restore the mode before printing.

  • Changing the rounding mode and then calling a library that assumes round-to-nearest. Restore it, ideally with ieee_get_modes and ieee_set_modes around the region.

  • Calling an IEEE function without checking the support inquiry, especially ieee_support_underflow_control before ieee_set_underflow_mode, which the standard forbids when it is false.

  • Assuming every compiler has the F2018 and F2023 functions: ieee_next_up, ieee_int, ieee_max and others are missing in gfortran 16.2.

  • Using the intrinsic max or min on data that may contain a NaN: the result is not defined and depends on the compiler and the optimization level.

  • Trapping on underflow or inexact: they happen in almost every program, so -ffpe-trap=invalid,zero,overflow is the sensible set; the traps are a hardware feature that some Arm processors do not have.

  • Reading the sign of zero: x < 0.0 is false for -0.0; use ieee_signbit or ieee_is_negative.

  • Trusting a sum: a loop over millions of values, a reduction vectorized by the compiler and a parallel reduction give different results. Compare with a tolerance and, where accuracy matters, use compensated summation (and no -ffast-math).

  • Fast-math on shared libraries: with -ffast-math the linker may add startup code that sets the flush-to-zero bits for the whole program, including libraries compiled without it.
