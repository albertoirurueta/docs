Expressions and Assignment

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Fortran 2023 (ISO/IEC 1539-1:2023, working draft J3/23-007r1) and was checked on 2026-10-18. Every complete program on it was compiled warning-free with GNU Fortran 16.2 under gfortran -std=f2023 -Wall -Wextra -pedantic -fimplicit-none -fcheck=all and run, and the examples that LLVM Flang 23 accepts were run with it as well. The output shown is the output that was produced. Examples that are deliberately wrong, rejected or warned about are labelled as such in the text and in a comment on their first line. Clause numbers refer to J3/23-007r1: expressions are clause 10.1, assignment is clause 10.2.

An expression computes a value, an assignment stores it, and most of the surprises in Fortran numerical code live in the gap between the two: an integer division where a real one was meant, a comparison that the processor may or may not short-circuit, a left-hand side that is silently reallocated, an array section whose shape does not conform. The page follows the running heat-diffusion scenario of this section, heatflow, and uses its module and type names (heatflow_kinds, grid_t, u, unew). The types that the operators work on are described in Intrinsic Types and Kinds and the declarations that give variables their attributes in Variables, Declarations and Attributes. The statements that consume logical expressions are in Control Flow, and whole-array expressions are developed further in Arrays Fundamentals and Allocatable Arrays and Dynamic Memory. Readers coming from C will find the same family of operators in the C Reference; the differences that matter are called out below.

How an expression is built

An expression is formed from operands, operators and parentheses (10.1.2.1). An operand is a scalar or an array, and an operation is either intrinsic, with a meaning built into the language, or defined, with a meaning supplied by a function through a generic interface. The standard organises the grammar into a primary, five levels of expression and the expression itself, and these levels are what give the precedence table its shape.

A scalar and an array operand can be mixed: an elemental operation applies element by element, and a scalar is treated as an array of the right shape with every element equal to the scalar (10.1.10). Two array operands of an elemental binary operation must be conformable, that is, have the same shape. The result of an operation has the shape of the array operand (10.1.9.3), and the order in which the elements are computed is unspecified: for an operation that is intrinsically pure the element operations may be performed simultaneously or in any order (10.1.4).

A few consequences of the grammar are worth memorising, because they differ from C and from most other languages:

  • ** associates from right to left, so 2**3**2 is 2**(3**2), which is 512, and it binds tighter than unary minus, so -2**2 is -(2**2), which is -4 (10.1.3, NOTE 1 and NOTE 2).

  • A unary - or + may only appear at the start of a level-2 expression, so a * -b and a ** -b are not valid. The compiler asks for parentheses, a * (-b). Because unary minus is looser than * and /, -a*b is -(a*b).

  • There is no bitwise .and. on integers. Bit operations are intrinsic functions (iand, ior, ieor, not, shiftl), described in Numeric Model, Bit Manipulation and Conversion.

  • A relational expression has at most one relational operator, so a < b < c is rejected; write a < b .and. b < c.

  • .not. is looser than the relational operators, so .not. a == b negates the comparison, and a second .not. directly after the first is not allowed (.not. .not. a is rejected; write .not. (.not. a)).

  • .and. binds tighter than .or., which binds tighter than .eqv., so a .eqv. b .or. c means a .eqv. (b .or. c).

  • A defined unary operator binds tighter than anything, a defined binary operator looser than anything, and an extended intrinsic operator keeps its intrinsic precedence (10.1.3, last sentence).

The first example evaluates each of these rules, using the heatflow_kinds module of the scenario so that every constant has an explicit kind.

module heatflow_kinds
  use, intrinsic :: iso_fortran_env, only: int32, int64, real32, real64
  implicit none
  private
  public :: sp, dp, ip, lp
  integer, parameter :: sp = real32
  integer, parameter :: dp = real64
  integer, parameter :: ip = int32
  integer, parameter :: lp = int64
end module heatflow_kinds

program precedence_demo
  use heatflow_kinds, only: dp, ip
  implicit none
  integer(ip) :: two, three
  real(dp) :: a
  logical :: p, q, r
  character(len=:), allocatable :: label

  two = 2_ip
  three = 3_ip
  a = 3.0_dp
  p = .true.
  q = .false.
  r = .false.
  label = 'ab'

  ! Numeric: ** binds tighter than unary minus and is right-associative.
  print '(a, i0)', '-two**2        = ', -two**2
  print '(a, i0)', '(-two)**2      = ', (-two)**2
  print '(a, i0)', 'two**three**2  = ', two**three**2
  print '(a, i0)', '(two**three)**2 = ', (two**three)**2
  print '(a, f0.1)', '-a*a           = ', -a*a
  ! Numeric operators bind tighter than relational ones.
  print '(a, l1)', 'two + 1 == three = ', two + 1_ip == three
  ! Concatenation binds tighter than relational ones.
  print '(a, l1)', 'label // "c" == "abc" = ', label // 'c' == 'abc'
  ! .not. is below relational operators, so it applies to the whole comparison.
  print '(a, l1)', '.not. two == three = ', .not. two == three
  ! .and. binds tighter than .or., which binds tighter than .eqv. / .neqv.
  print '(a, l1)', 'p .or. q .and. r   = ', p .or. q .and. r
  print '(a, l1)', '(p .or. q) .and. r = ', (p .or. q) .and. r
  print '(a, l1)', 'q .eqv. r .or. p   = ', q .eqv. r .or. p
  print '(a, l1)', '(q .eqv. r) .or. p = ', (q .eqv. r) .or. p
end program precedence_demo

Numeric operations

The operands of a numeric operation may differ in type or kind (10.1.5.2.1). Except for a real or complex base raised to an integer power, the operand with the lower type or kind is converted first. The result type is the higher of the two types in the order integer, real, complex, and the result kind is the one with the greater decimal exponent range (integer) or precision (real, complex), as 10.1.9.3 specifies:

Three rules deserve their own paragraph, because they produce wrong numbers without any diagnostic:

  • Integer division truncates toward zero (10.1.5.2.2), so (-8)/3 is -2 and 5/2 is 2, whatever the type of the variable that receives the result. mod(a, p) has the sign of a, modulo(a, p) the sign of p. An integer raised to a negative integer power is the integer division 1/(x**abs(n)), which is 0 for every x with abs(x) > 1 (10.1.5.2.1). gfortran reports integer division of constants through -Winteger-division, part of -Wall, which is why the examples divide variables.

  • Operators of the same precedence combine left to right, so nx/ny*x divides two integers first and nx*x/ny does not. Convert explicitly with real(nx, dp) before dividing.

  • A real constant without a kind suffix has the default kind, which is single precision on every mainstream processor. x = 0.1 for a real(dp) variable stores a double-precision number that carries the single-precision error; 0.1_dp does not.

  integer, parameter :: sp = real32
  integer, parameter :: dp = real64
  integer, parameter :: ip = int32
  integer, parameter :: lp = int64

program numeric_operations
  use heatflow_kinds, only: sp, dp, ip
  implicit none
  integer(ip) :: nx, ny, i, j
  real(dp) :: lx, dx, x
  real(sp) :: tenth_sp
  real(dp) :: tenth_dp

  ! Integer division truncates toward zero (10.1.5.2.2); mod follows the
  ! dividend, modulo follows the divisor.
  i = -8_ip
  j = 3_ip
  print '(a, i0)', 'i / j          = ', i/j
  print '(a, i0)', 'mod(i, j)      = ', mod(i, j)
  print '(a, i0)', 'modulo(i, j)   = ', modulo(i, j)
  print '(a, i0)', 'j ** (-2)      = ', j**(-2_ip)

  ! Mixed mode: the integer operand is converted to the real kind of the
  ! other operand. Convert before dividing to avoid integer division.
  nx = 5_ip
  ny = 2_ip
  lx = 1.0_dp
  dx = lx/real(nx - 1_ip, dp)
  print '(a, i0)', 'nx / ny        = ', nx/ny
  print '(a, f6.4)', 'real(nx, dp)/ny = ', real(nx, dp)/ny
  print '(a, f6.4)', 'dx = lx/(nx-1)  = ', dx

  ! Operators of equal precedence combine left to right, so the integer
  ! division in the first form happens before the multiplication.
  x = 2.5_dp
  print '(a, f6.4)', 'nx / ny * x    = ', nx/ny*x
  print '(a, f6.4)', 'nx * x / ny    = ', nx*x/ny

  ! A default real constant is single precision; its error survives
  ! assignment to a double precision variable.
  tenth_sp = 0.1
  tenth_dp = real(tenth_sp, dp)
  print '(a, es24.16)', 'real(0.1, dp)  = ', tenth_dp
  tenth_dp = 0.1_dp
  print '(a, es24.16)', '0.1_dp         = ', tenth_dp
end program numeric_operations

Character and relational operations

The only intrinsic character operator is concatenation, // (10.1.5.3). Both operands must have the same character kind, and the result has the sum of the two lengths. Parentheses have no effect on its value, and a processor only has to evaluate as much of a concatenation as the context needs (for example, when the target has the length of the first operand only, the second operand need not be evaluated at all). Substrings, trim, adjustl and the rest of string handling are in Characters and Strings.

A relational operation always gives a result of default logical kind (10.1.5.5.1). The symbols ==, /=, <, <=, > and >= mean exactly what .eq., .ne., .lt., .le., .gt. and .ge. mean, and neither spelling is obsolescent. The rules that follow are the ones that cause trouble:

  • Numeric operands of different type or kind are converted to the type and kind of the expression x1 + x2 before comparing.

  • A complex operand can only be compared with == and /=; ordering complex numbers is a compile-time error.

  • Two logical operands cannot be compared with ==. Use .eqv. and .neqv..

  • Character operands are compared one character at a time. The shorter operand is treated as if it were extended on the right with blanks, so 'abc' == 'abc ' is true. The result of an ordering test depends on the processor’s collating sequence; == and /= do not. For comparisons that are guaranteed to use the ASCII sequence, use lge, lgt, lle and llt.

  • If an operand can be an IEEE NaN, .not. (x < y) and x >= y are not equivalent (10.1.5.5.2, NOTE), because every ordered comparison with a NaN is false.

  • Comparing real values for equality is rarely what a numerical program wants. gfortran’s -Wcompare-reals, part of -Wextra, flags == and /= on real and complex operands. Compare a difference with a tolerance instead.

program relational_and_logical
  use, intrinsic :: ieee_arithmetic, only: ieee_value, ieee_quiet_nan
  use heatflow_kinds, only: dp
  implicit none
  real(dp) :: x, y, nan, residual, tolerance
  logical :: converged, hot, stable
  character(len=8) :: solver

  ! Character comparison pads the shorter operand with blanks (10.1.5.5.1).
  solver = 'jacobi'
  print '(a, l1)', "solver == 'jacobi'          = ", solver == 'jacobi'
  print '(a, l1)', "'abc' == 'abc   '           = ", 'abc' == 'abc   '
  print '(a, l1)', "'Jacobi' < 'jacobi'         = ", 'Jacobi' < 'jacobi'
  print '(a, l1)', "lgt('b', 'a')               = ", lgt('b', 'a')

  ! Logical values are compared with .eqv. and .neqv., never with ==.
  hot = .true.
  stable = .false.
  print '(a, l1)', 'hot .eqv. stable            = ', hot .eqv. stable
  print '(a, l1)', 'hot .neqv. stable           = ', hot .neqv. stable

  ! Real values: compare a difference with a tolerance instead of testing
  ! equality (gfortran -Wextra warns about == on reals).
  x = 0.1_dp + 0.2_dp
  y = 0.3_dp
  print '(a, es10.3)', 'abs(x - y)                  = ', abs(x - y)
  tolerance = 1.0e-12_dp
  residual = abs(x - y)
  converged = residual <= tolerance
  print '(a, l1)', 'residual <= tolerance       = ', converged

  ! With a NaN operand, .not. (a < b) and a >= b are different expressions.
  nan = ieee_value(nan, ieee_quiet_nan)
  x = 1.0_dp
  print '(a, l1)', '.not. (nan < x)             = ', .not. (nan < x)
  print '(a, l1)', 'nan >= x                    = ', nan >= x
end program relational_and_logical

The logical operators .not., .and., .or., .eqv. and .neqv. take operands of type logical (10.1.5.4). If the operands have different kinds, the kind of the result is processor dependent but is that of one of the operands. Fortran has no .xor. operator in the standard; .neqv. is the exclusive or. Using integer operands with .and. or .or. as a bitwise operation, an extension that some other compilers offer, is not standard: GNU Fortran 16.2 and LLVM Flang 23 both reject i .and. j for integers. The comparison traps above, and the others that bite numerical code, are collected in Common Gotchas and Pitfalls.

Defined operations

A program can extend an intrinsic operator to new types, and can create new operators spelled .name., by writing a function and naming it in a generic interface operator(...) block (10.1.6). A defined unary operation needs a function with one dummy argument and a defined binary operation one with two, and the dummy arguments must be non-optional with intent(in) or value, as for every function that implements an operator. The same function can be bound to a type with a generic type-bound operator(...). Defined assignment, assignment(=), is implemented by a subroutine whose first argument is the left-hand side (intent(out) or intent(inout)) and whose second is the right-hand side (intent(in)).

The precedence of a defined operation is that of its operator: an extended + keeps the precedence of +, a .name. unary operator binds tighter than everything, and a .name. binary operator is the loosest. The following module keeps a temperature as a derived type and defines one extended operator, one unary operator, one binary operator and the assignment from a Celsius number. The full treatment of generic interfaces, including type-bound generics and elemental operators, is in Interfaces, Generics and Operator Overloading.

module heatflow_kinds

  implicit none
  private
  public :: sp, dp, ip, lp
  integer, parameter :: sp = real32
  integer, parameter :: dp = real64
  integer, parameter :: ip = int32
  integer, parameter :: lp = int64
end module heatflow_kinds

module temperature_demo
  use heatflow_kinds, only: dp
  implicit none
  private
  public :: temperature_t, operator(+), operator(.celsius.), operator(.diff.), assignment(=)

  ! A temperature stored in kelvin; the type keeps scales from being mixed.
  type :: temperature_t
    real(dp) :: kelvin = 0.0_dp
  end type temperature_t

Evaluation rules: what the processor may do

Fortran specifies the value an expression has, not the steps by which a processor reaches it. The freedom this gives an optimizing compiler is large and is the reason Fortran code vectorizes well. It is also the source of three rules that programmers from C and Java must unlearn.

No guaranteed short-circuit evaluation

"It is not necessary for a processor to evaluate all of the operands of an expression, or to evaluate entirely each operand, if the value of the expression can be determined otherwise" (10.1.7). The sentence cuts both ways: the processor may skip the right operand of .and. when the left one is false, and it may evaluate it anyway. Neither .and. nor .or. promises an order, and a test written to protect a subscript or a division with a guard does not protect it.

! NON-CONFORMING on purpose: the guard does not protect the subscript.
! The standard lets the processor evaluate both operands of .and. (10.1.7).
module guard_demo
  implicit none
contains
  function first_positive(a, i) result(ok)
    real, intent(in) :: a(:)
    integer, intent(in) :: i
    logical :: ok
    ok = i <= size(a) .and. a(i) > 0.0
  end function first_positive
end module guard_demo

program no_short_circuit
  use guard_demo, only: first_positive
  implicit none
  real :: a(3)
  a = [1.0, -2.0, 3.0]
  print '(a, l1)', 'i = 2: ', first_positive(a, 2)
  print '(a, l1)', 'i = 4: ', first_positive(a, 4)

A related statement of the same clause: if a function reference sits in a part of an expression that need not be evaluated, every entity that the function would have defined becomes undefined, whether or not the processor really skipped the call (10.1.7, NOTE 2). A function that has side effects therefore makes the whole statement fragile.

Function side effects and why they are restricted

A function reference in an expression may not change anything that the same statement also uses (10.1.4). The standard puts it as two rules: the evaluation of a function reference shall neither affect nor be affected by the evaluation of any other entity in the statement, and if the reference defines or undefines an actual argument, that argument shall not appear elsewhere in the statement. So a(i) = f(i) is prohibited if f modifies i, and so is y = g(x) + x if g modifies x. The only exceptions are the logical expression of an if statement and the mask of a where statement, whose subsidiary statement may be affected.

The reason is the freedom described above. The processor may reorder operands, evaluate a function once instead of twice, or not at all. GNU Fortran does exactly this on request: -ffrontend-optimize, enabled by default at every -O level except -O0 and -Og, eliminates identical function calls within an expression for pure functions, and -faggressive-function-elimination does it even for functions not marked pure, so a = f(b, c) + f(b, c) calls f once. A function with side effects can then be called fewer times than the source suggests.

The language gives the programmer a way to say that a function is safe: pure functions have no side effects (they may not modify their dummy arguments, module variables or perform I/O), elemental functions are pure unless declared impure, and Fortran 2023 adds simple procedures, pure procedures that are further restricted from referencing variables accessed by host or use association. Procedure attributes are described in Procedures, Functions and Subroutines. The consequence for expressions is practical: use subroutines for work with side effects, and use pure functions for values.

Mathematically equivalent expressions and the integrity of parentheses

Once the interpretation of a numeric expression is fixed by the precedence rules, "the processor may evaluate any mathematically equivalent expression, provided that the integrity of parentheses is not violated" (10.1.5.2.4). The standard lists allowed rewrites, for example x + y + z as x + (y + z), a / b / c as a / (b * c) and a / 5.0 as 0.2 * a, and forbidden ones, for example x * i / j as x * (i / j), i / 2 as 0.5 * i and the regrouping of (x + y) + z. Two numeric expressions are mathematically equivalent when they are equal for all values of their operands, but "mathematically equivalent expressions of numeric type can produce different computational results". The same freedom exists for logical expressions (l1 .and. l2 .and. l3 may become l1 .and. (l2 .and. l3)) and relational ones (10.1.5.4.2 and 10.1.5.5.2).

A parenthesised expression "shall be treated as a data entity" (10.1.8): a + (b - c) evaluates b - c before the addition and may not become (a + b) - c. Parentheses are the programmer’s tool for controlling intermediate magnitude and rounding.

Conditional expressions (Fortran 2023)

Fortran 2023 adds a conditional expression, a primary written ( condition ? value : alternative ) (R1002 in 10.1.2.3):

( scalar-logical-expr ? expr [ : scalar-logical-expr ? expr ]... : expr )

The evaluation rule (10.1.4) is what makes it useful: the logical expressions are evaluated in order until one is true, the expr after it is chosen, and otherwise the last expr is chosen. Only the chosen expr is evaluated. "Only one expr of a conditional expression is evaluated, and any of its scalar-logical-exprs subsequent to one that evaluates to true are not evaluated" (10.1.4, NOTE 3). That is the guaranteed short-circuit that .and. and merge do not give.

The rules for the branches (C1004) are short: every expr must have the same declared type, kind type parameters and rank; the lengths of character branches may differ, and the length (and, for a polymorphic branch, the dynamic type) is that of the chosen branch. A conditional expression is a primary, so it can appear wherever an expression can. It is not a constant expression (10.1.12 does not list it), so it cannot initialise a named constant. GNU Fortran 16.2 stops with an internal compiler error when a conditional expression is used directly as a print item; assigning it to a variable first works, see What’s New and Fortran 2028 Preview.

The next module uses the three typical idioms: a guard that protects a subscript, an optional argument with a default value (an absent optional argument may only be referenced in a few permitted ways, and a conditional expression with present is one of the cleanest), and a character result whose branches differ in length.

  use heatflow_kinds, only: dp, ip
  implicit none
  private
  public :: positive_at, sample, describe

contains

  ! Safe guard: the subscript is only evaluated when the condition is true.
  pure function positive_at(a, i) result(ok)
    real(dp), intent(in) :: a(:)
    integer(ip), intent(in) :: i
    logical :: ok
    ok = (i >= 1_ip .and. i <= size(a, kind=ip) ? a(i) > 0.0_dp : .false.)
  end function positive_at

  ! Optional argument with a default, without a second variable.
  pure function sample(a, i, fill) result(v)
    real(dp), intent(in) :: a(:)
    integer(ip), intent(in) :: i
    real(dp), intent(in), optional :: fill
    real(dp) :: v
    v = (i >= 1_ip .and. i <= size(a, kind=ip) ? a(i) : present(fill) ? fill : 0.0_dp)
  end function sample

  ! The branches may have different character lengths; the result takes the
  ! length of the chosen one.
  function describe(residual, tolerance) result(text)
    real(dp), intent(in) :: residual, tolerance
    character(len=:), allocatable :: text
    text = (abs(residual) <= tolerance ? 'ok' : 'did not converge')
  end function describe

end module guard_demo

Intrinsic assignment

An assignment statement has the form variable = expr (R1033, 10.2.1.1). It is either an intrinsic assignment, whose meaning is built into the language, or a defined assignment through assignment(=) (shown above). Execution of an intrinsic assignment "shall have the same effect as if the evaluation of expr and the evaluation of all expressions in variable occurred before any portion of the variable is defined" (10.2.1.3). Character assignment

A character variable of fixed length always keeps its length (10.2.1.3): a shorter value is extended on the right with blanks and a longer value is truncated from the right. There is no error, and gfortran’s -Wcharacter-truncation can warn when the truncation is visible at compile time. If the kinds differ, each character is converted by achar(iachar(c), kind(variable)); a character that is not representable in the target kind is replaced by a processor-dependent one.

The assignment may reference the variable on the right: s(2:5) = s(1:4) on 'ABCDEF' gives 'AABCDF', because the right-hand side is evaluated completely first. And a character variable with a deferred length (character(len=:), allocatable) takes the length of the value, as described in the next section, unless the left-hand side is written with the substring name(:), which assigns to the existing allocation:

program character_assignment
  implicit none
  character(len=8) :: fixed
  character(len=:), allocatable :: label, first, surname
  character(len=6) :: work

  ! Fixed-length target: the value is padded with blanks or truncated on the right.
  first = 'Joseph'
  surname = 'Fourier'
  fixed = first
  print '(3a)', '[', fixed, ']'
  fixed = first // ' ' // surname
  print '(3a)', '[', fixed, ']'

  ! Deferred-length allocatable target: reallocated to the length of the value.
  label = first
  print '(a, i0, 3a)', 'len=', len(label), ' [', label, ']'
  label = 'Dr. ' // first // ' ' // surname
  print '(a, i0, 3a)', 'len=', len(label), ' [', label, ']'

  ! With (:) the target keeps its length: pad or truncate again.
  label(:) = first
  print '(a, i0, 3a)', 'len=', len(label), ' [', label, ']'

  ! The right-hand side is evaluated completely before the target changes.
  work = 'ABCDEF'
  work(2:5) = work(1:4)
  print '(3a)', '[', work, ']'
end program character_assignment

Automatic (re)allocation of allocatable left-hand sides

Since Fortran 2003 the left-hand side of an intrinsic assignment may be an allocatable variable that is unallocated or has a different shape, and the assignment then allocates or reallocates it (10.2.1.3). The rules in the standard, applied in this order, are:

  1. The expression expr and every expression inside variable are evaluated.

  2. If the variable is unallocated, expr must have the same rank, and the variable is allocated (below).

  3. If the variable is allocated and expr is an array of a different shape, or the length type parameters differ, or the variable is polymorphic and the dynamic type or kind parameters differ, the variable is deallocated and allocated again.

  4. The new allocation takes the dynamic type and kind parameters of expr if the variable is polymorphic, each deferred length parameter from expr, the shape of expr with each lower bound equal to lbound(expr), and, if expr is a scalar and the variable an array, the same bounds as before.

  5. The values are copied, with the conversions of the previous section.

flowchart TD start(["v = expr (v allocatable)"]) --> ev["evaluate expr and all subscripts of v"] ev --> alloc{"v allocated?"} alloc -- no --> rank{"same rank as expr?"} rank -- no --> bad(["not conforming: expr scalar or other rank"]) rank -- yes --> make["allocate v: shape, lower bounds, deferred length, dynamic type from expr"] alloc -- yes --> diff{"shape, length parameters or dynamic type differ?"} diff -- yes --> redo["deallocate v, then allocate as above"] diff -- no --> keep["keep the existing allocation and its bounds"] make --> copy["copy expr into v, converting if needed"] redo --> copy keep --> copy copy --> done(["v is allocated and defined"])

Notice what the example shows:

  • u = fine allocated an unallocated u. unew = u allocated unew with the shape of u.

  • u = coarsen(fine) changed the shape, so u was reallocated. If the shape had been equal, the existing allocation would have been reused, with its old bounds.

  • A section and a function result have lower bounds of 1, but a whole array keeps its declared lower bounds, and the reallocated u takes them over (lbound 0 after u = halo).

  • A scalar on the right does not reallocate an allocated array; it is broadcast.

The two ways to get this wrong are not the same error, and compilers diagnose them differently. The first program is non-conforming on purpose: a scalar cannot supply a shape, so assigning it to an unallocated array is not allowed.

Reallocation has a cost, and it can hide mistakes. A hot loop that assigns a new array to the same variable on every iteration pays an allocation check each time, and a typo that gives u = unew(2:nx-1, :) a smaller shape changes the grid without a diagnostic. GNU Fortran’s -Wrealloc-lhs warns where the compiler might insert allocation or reallocation code for an array of intrinsic type and -Wrealloc-lhs-all also covers scalars and derived types. The manual recommends writing the left-hand side as a whole-array section such as u(:, :) where the array is known to be allocated with the right shape, which removes the check. -frealloc-lhs is on by default except with -std=f95, and -fno-realloc-lhs returns to the Fortran 95 behaviour where the left-hand side must already match. Other compilers have equivalent switches; see their manuals, and Allocatable Arrays and Dynamic Memory for allocate, move_alloc and the lifetime rules.

Array assignment and conformance

If the variable is an array, an intrinsic assignment is performed element by element; a scalar expr is treated as an array of the same shape with every element equal to the scalar (10.2.1.3). The shape rule is strict: unless the variable is an allocatable array of the same rank, the variable and expr must be conformable, that is, have the same shape. An array is not conformable with another array of a different shape even if the number of elements matches. The element assignments may be performed in any order, and the whole of expr is evaluated before anything is stored, which is why x(1:10) = x(10:1:-1) reverses x (10.2.1.3, NOTE 4).

Array syntax is not just shorthand for a loop; it is a statement that tells the compiler there is no dependence between element computations. The solver kernels of heatflow express a time step of the finite-difference scheme as one array assignment on sections. In the program below the section arithmetic updates the interior of a 5 by 5 field after a single hot cell, then reverses a vector, and finally clips values with a masked assignment, where.

module heatflow_kinds
  use, intrinsic :: iso_fortran_env, only: int32, int64, real32, real64
  implicit none
  private
  public :: sp, dp, ip, lp
  integer, parameter :: sp = real32
  integer, parameter :: dp = real64
  integer, parameter :: ip = int32
  integer, parameter :: lp = int64
end module heatflow_kinds

program array_assignment_and_where
  use heatflow_kinds, only: dp, ip
  implicit none
  integer(ip), parameter :: nx = 5_ip, ny = 5_ip
  real(dp), parameter :: dx = 0.25_dp, dy = 0.25_dp, alpha = 1.0_dp, dt = 0.01_dp
  real(dp) :: u(nx, ny), unew(nx, ny)
  real(dp) :: line(6)
  integer(ip) :: j

  ! A scalar is broadcast to every element.
  u = 0.0_dp
  u(3, 3) = 1.0_dp

  ! Whole-array arithmetic on conformable sections: one FTCS step of the heat
  ! equation. Every right-hand side is evaluated before unew is changed.
  unew = u
  unew(2:nx - 1, 2:ny - 1) = u(2:nx - 1, 2:ny - 1) + alpha*dt*( &
    (u(3:nx, 2:ny - 1) - 2.0_dp*u(2:nx - 1, 2:ny - 1) + u(1:nx - 2, 2:ny - 1))/dx**2 + &
    (u(2:nx - 1, 3:ny) - 2.0_dp*u(2:nx - 1, 2:ny - 1) + u(2:nx - 1, 1:ny - 2))/dy**2)
  do j = 1_ip, ny
    print '(5f8.4)', unew(:, j)
  end do

  ! Overlapping sections: the whole right-hand side is evaluated first.
  line = [1.0_dp, 2.0_dp, 3.0_dp, 4.0_dp, 5.0_dp, 6.0_dp]
  line(1:6) = line(6:1:-1)
  print '(6f5.1)', line

  ! Masked assignment: clip temperatures, element by element.
  where (unew > 0.3_dp)
    unew = 0.3_dp
  elsewhere (unew < 0.01_dp)
    unew = 0.0_dp
  end where
  print '(a, f6.3, a, f6.3)', 'max = ', maxval(unew), '  min = ', minval(unew)
  print '(a, i0)', 'cells above zero = ', count(unew > 0.0_dp)
end program array_assignment_and_where

The stencil update reads the old u on the right and writes unew on the left, so there is no aliasing to reason about. An update in place, u(2:nx-1, :) = u(1:nx-2, :) + u(3:nx, :), would also be well defined (the right-hand side is evaluated first), but the compiler may need a temporary for it, which costs memory and time.

where selects elements by a logical mask array of the same shape. In the construct form the first mask is evaluated once, the statements of the where body run for the true elements, and each elsewhere branch runs for those that are still false, optionally with its own mask (10.2.3.2). Only the assignments in the body are masked. Function references in the body are evaluated for the whole array unless they are elemental. forall, the Fortran 95 relative of where, is obsolescent since Fortran 2018; use do concurrent, described in do concurrent and GPU Offload. The array-oriented intrinsics (maxval, count, pack and the rest) are in Array Intrinsics and Reductions.

Derived-type assignment

For a variable of derived type, an intrinsic assignment is performed "as if each component of the variable were assigned from the corresponding component of expr" (10.2.1.3). What "assigned" means depends on the kind of component:

Component Assignment

ordinary (nonpointer, nonallocatable)

intrinsic assignment, or defined assignment if its type has a type-bound assignment(=) that fits

allocatable

a deep copy: the target component is deallocated, then allocated with the shape and type parameters of the source if the source is allocated, then assigned; an unallocated source leaves the target unallocated

pointer

pointer assignment: the target component becomes associated with the same target as the source, and no data is copied

The distinction between "owns its data" and "refers to data" is the reason to prefer allocatable components over pointer components in types like grid_t in heatflow: copying a grid copies its field, and final procedures and ownership are simple. The next program has one of each kind of component:

Pointer assignment

Pointer assignment, written =>, associates a pointer with a target; it does not copy anything (10.2.2). The forms, from 10.2.2.2, are:

  • p => target for a data pointer. The pointer takes the shape of the target, with lower bounds equal to lbound of the target. For a section the lower bounds are 1.

  • p(lb1:, lb2:) => target, a list of lower bounds that replaces the default ones (Fortran 2003).

  • p(lb1:ub1, lb2:ub2) => target, bounds remapping, which gives the pointer a different rank from its rank-one target (Fortran 2003) or from any simply contiguous target (Fortran 2008). The target must have at least as many elements as the new shape needs.

  • q => procedure_name for a procedure pointer, whose interface must be compatible with the procedure.

A data pointer can only be associated with an object that has the target attribute (or is itself a pointer), a restriction that lets the compiler assume that only target objects are aliased. A pointer assignment never changes the target, while an ordinary assignment through a pointer, p = 99.0_dp, assigns to the target. associated(p) and associated(p, target) test the association, nullify(p) or p => null() disassociates it, and a polymorphic pointer takes the dynamic type of the target (10.2.2.3).

  real(dp), target :: flat(12)

  row => u(2, :)

Where the books are outdated

This page draws on the chapter on expressions and assignment of Metcalf, Reid, Cohen and Bader’s Modern Fortran Explained: Incorporating Fortran 2023 (referred to as MRCB, Chapter 3) and on its section on the Fortran 2023 expression features (section 23.2.3). Only the concepts are used; nothing is reproduced. Where an older source, including older printings and the MATLAB book’s example style, differs from the current practice, the current practice is as follows.

  • Conditional expressions are new. A book written before Fortran 2023 cannot show them, and MRCB covers them only among the Fortran 2023 additions. Pre-2023 code uses a nested if or merge; the section on conditional expressions above states where each is appropriate. The book has no compiler-support information. On 2026-10-18 GNU Fortran 16.2 supports scalar conditional expressions but not array-valued ones, and LLVM Flang 23 accepts both although its support table still lists the feature as not supported.

  • The authors' recommendations are not the standard’s deprecations. MRCB’s appendix on features it advises against includes the dotted relational spellings .eq., .ne., .lt., .le., .gt. and .ge.. They are not obsolescent or deleted in Fortran 2023, and the compiler does not warn about them. The symbols ==, /=, <, <=, > and >= are a style choice.

  • forall is obsolescent. Older texts present forall as the way to write parallel assignment; since Fortran 2018 it is obsolescent and do concurrent replaces it.

  • Allocation on assignment is the default. Material written for Fortran 95 compilers warns against assigning to unallocated arrays. Since Fortran 2003 it is standard, and gfortran enables it unless -std=f95 is given. The newer hazards are the silent reallocation and the cost, covered above.

  • Source-form limits changed. Long right-hand sides are easier to write in Fortran 2023, which allows lines of 10,000 characters and no limit on the number of continuation lines (1,000,000 characters per statement), where the F2018 limits were 132 and 255. The statements in this page are nevertheless wrapped at conventional widths.

  • IEEE references are older than the standard. The book’s references to IEEE 754-2008 and ISO/IEC/IEEE 60559:2011 are superseded by IEEE 754-2019 and ISO/IEC 60559:2020, which Fortran 2023 adopts. The comparison rules for NaN used on this page are unchanged by that revision.
