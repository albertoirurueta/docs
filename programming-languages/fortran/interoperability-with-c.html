Interoperability with C

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Fortran 2023 (ISO/IEC 1539-1:2023, J3/23-007r1) and was checked on 2026-10-19. Every Fortran example was compiled warning-free with gfortran -std=f2023 -Wall -Wextra -pedantic -fimplicit-none -fcheck=all (GNU Fortran 16.2) and run, each C file was compiled with gcc -std=c17 -Wall -Wextra -pedantic (GCC 16.2), and the examples were also built and run with LLVM Flang 23 (23.1.4), in a Debian container on an AArch64 (64-bit Arm) machine. The output shown is real output; where the two compilers differ, or reject a feature, the page says so and shows the real diagnostics. Sizes and kind values are the ones of that platform (Linux, LP64 data model). Interoperability with C is clause 18 of the standard: 18.2 is the iso_c_binding module, 18.3 says which Fortran entities interoperate with which C entities, 18.9 covers global variables and 18.10 procedures. The bind attribute is in 8.5.5 and in 15.6.2.1 (proc-language-binding-spec), value in 8.5.19.

Fortran has had a standard way to call C, and to be called from C, since Fortran 2003: the iso_c_binding module supplies the kinds, pointer types and conversion procedures, and the bind(c) attribute gives a procedure, variable or derived type the C view of itself. Both directions need nothing but the compilers' normal object files. Fortran 2018 absorbed the technical specification ISO/IEC TS 29113 and relaxed most of the restrictions of the first design (assumed-type, optional, allocatable and assumed-shape dummy arguments; the latter two through C descriptors, the subject of C Descriptors and ISO_Fortran_binding), and Fortran 2023 added f_c_string, c_f_strpointer and the lower argument of c_f_pointer. This page covers the data and procedures that cross the boundary as plain C values and pointers, using the running example heatflow, whose Jacobi and FTCS kernels are exposed to C through the module heatflow_capi and the header heatflow.h. How to build that library for C, C++ and Python callers is in Calling Fortran from C, C++ and Python, and the same ideas for a MATLAB gateway in MATLAB: MEX, Engine and MAT-File APIs. The C language side (pointers, structures, linkage) is described in C Pointers, Structures, Unions and Type Aliases and Storage Duration, Scope and Linkage; the same boundary seen from Rust is in FFI & C Interop and from Go in cgo and C Interoperability.

The model: four pieces and a companion processor

The standard speaks of a companion processor: the C compiler whose types and calling conventions the Fortran processor agrees to follow. Interoperability is then a statement about entities, not about languages. A Fortran entity is interoperable if an equivalent C entity could be written (18.1), whether or not one exists. A call across the boundary involves four pieces (18.3.7, Note 4): the reference in the caller, the interface or prototype the caller sees, the interface or prototype the callee is described by, and the function itself. The compiler can check only the pieces it sees, so a wrong interface body is a silent error, not a diagnostic: nothing compares a Fortran interface body with a C definition.

Direction What you write

Fortran calls C

an interface block describing the C function with bind(c) (and name= when the names differ), and the C object file or library at link time

C calls Fortran

a Fortran procedure with bind(c), a C prototype that matches it (usually in a header), and the Fortran object file or library, plus the Fortran runtime library at link time

C data seen from Fortran

a module variable with bind(c), a bind(c) derived type for a struct, c_ptr for void *, c_funptr for function pointers

Fortran data seen from C

the same declarations read the other way; arrays are passed as the address of the first element

The rules for the arguments of an interoperable procedure (15.6.2.1, C1561-C1568) are short. A function result must be an interoperable scalar. Each dummy argument must be an interoperable variable or procedure, or, since Fortran 2018, assumed-shape, assumed-rank, assumed-type, of assumed character length, allocatable or a pointer; with the latter group the C function receives a pointer to a descriptor, not to the data (18.3.7). A dummy argument cannot be a coarray, and an array dummy argument cannot have value. An interoperable procedure cannot be elemental, optional and value cannot both be given to a dummy argument of the same procedure (C869), and a C function with a variable argument list (...) cannot be described (18.3.7, item 7); Fortran has no portable way to call printf.

Calling C from Fortran

A C function is described to Fortran by an interface body with bind(c). The body has the same shape as for any external procedure (see Interfaces, Generics and Operator Overloading), with three differences: the dummy arguments have interoperable types; a scalar argument that C receives by value has the value attribute; and a scalar that C receives as a pointer does not. With the value attribute the dummy argument is passed as a copy, as in C, and the actual argument may be an expression; without it, the compiler passes the address. The intent of a value dummy argument may be only in or omitted (C868). The import statement brings the kind names into the interface body, which does not see its host’s names automatically.

The C side of the first program below has three small functions, one with an unusual case in its name:

/* C side of the first calls from Fortran. */
int hf_add_value(int a, int b) { return a + b; }

void hf_add_ref(const int *a, const int *b, int *sum) { *sum = *a + *b; }

double HF_Mixed_Case(double x) { return 2.0 * x; }

Source: J3/23-007r1 (Fortran 2023), 18.10 Interoperation with C functions, 18.10.2 Binding labels for procedures

program c_calls
  use, intrinsic :: iso_c_binding, only: c_int, c_double
  implicit none

  interface
    ! Fortran name and C name differ: name= gives the binding label, whose case is significant.
    function add_by_value(a, b) bind(c, name='hf_add_value') result(s)
      import :: c_int
      integer(c_int), value, intent(in) :: a, b      ! passed like a C int
      integer(c_int) :: s
    end function add_by_value

    subroutine add_by_reference(a, b, s) bind(c, name='hf_add_ref')
      import :: c_int
      integer(c_int), intent(in) :: a, b             ! no value: C receives int *
      integer(c_int), intent(out) :: s
    end subroutine add_by_reference

    function twice(x) bind(c, name='HF_Mixed_Case') result(y)
      import :: c_double
      real(c_double), value, intent(in) :: x
      real(c_double) :: y
    end function twice

    ! A function of the C library, no C source of our own needed.
    function c_hypot(x, y) bind(c, name='hypot') result(h)
      import :: c_double
      real(c_double), value, intent(in) :: x, y
      real(c_double) :: h
    end function c_hypot
  end interface

  integer(c_int) :: total

  print '(a, i0)', 'by value:     3 + 4 = ', add_by_value(3_c_int, 4_c_int)
  call add_by_reference(3_c_int, 4_c_int, total)
  print '(a, i0)', 'by reference: 3 + 4 = ', total
  print '(a, f4.1)', 'HF_Mixed_Case(1.5) = ', twice(1.5_c_double)
  print '(a, f4.1)', 'hypot(3, 4)        = ', c_hypot(3.0_c_double, 4.0_c_double)
end program c_calls

Source: J3/23-007r1 (Fortran 2023), 18.10 Interoperation with C functions, 18.10.2 Binding labels for procedures

Three things happen here. First, name= sets the binding label (18.10.2): the name by which the procedure is known to the C linker. Without name= the label is the Fortran name in lower case, so bind(c) on a procedure Add_Values would be called add_values in C. The case of a label given with name= is significant, which is why HF_Mixed_Case can be reached from a Fortran interface called twice. Second, hf_add_value has value arguments because the C prototype takes int, while hf_add_ref takes int * and is described without value. Third, hypot shows that the interface body does not care who wrote the function: any symbol the linker can find, including those of the C library, can be described this way, and the interface can use a Fortran name of its own. A C function that returns void is a subroutine; any other return type is a function with an interoperable scalar result.

A mistake in the value attribute does not produce a diagnostic. Writing the interface of hf_add_value without value (integer(c_int), intent(in) for both a and b) compiled warning-free with the strict flags, and the program printed 3 + 4 = 8394212 on three runs in a row: the compiler passed the addresses of the two integers where C expects the integers themselves, and C added two addresses, truncated to an int. The opposite mistake, value on the third argument of hf_add_ref, which C takes as int *, also compiled without a message; the call made C store through the address 0 and the program ended with Program received signal SIGSEGV: Segmentation fault - invalid memory reference. (the two interface bodies were the ones of the first program with value removed from a and b, and with value added to s). Check every interface body against the C prototype, argument by argument, as 18.3.7 lists.

What the compiler checks

The compiler does check that the dummy arguments and the result are interoperable types (C1562-C1567), and so it can reject an interface that no C prototype could match. This deliberately non-conforming module contains a dummy argument of default logical, one of a derived type that lacks bind(c) and one of default real:

! Deliberately non-conforming: arguments that cannot be interoperable.
module bad_binding
  use, intrinsic :: iso_c_binding, only: c_int
  implicit none

  type :: plain_t                        ! no bind(c): not interoperable
    integer(c_int) :: id
  end type plain_t

contains

  subroutine set_flag(flag) bind(c)
    logical, value, intent(in) :: flag   ! default logical has no C counterpart; c_bool is required
  end subroutine set_flag

  subroutine take_plain(p) bind(c)
    type(plain_t), intent(in) :: p       ! derived type without bind(c)
  end subroutine take_plain

  subroutine take_default_real(x) bind(c)
    real, value, intent(in) :: x         ! default real is c_float only by coincidence of the kind value
  end subroutine take_default_real
end module bad_binding

Exposing heatflow to C

The heatflow project ships one C-callable function, heatflow_step: it advances an nx by ny temperature field by one FTCS step and returns a status. It lives in the module heatflow_capi, which wraps the module procedure ftcs_sweep of heatflow_kernels (the kernel that the solvers of Modules and Submodules and Object Oriented Programming also use):

!> C API: heatflow_step advances an nx-by-ny field by one FTCS step.
module heatflow_capi
  use, intrinsic :: iso_c_binding, only: c_int, c_double
  use heatflow_kernels, only: ftcs_sweep
  implicit none
  private
  public :: heatflow_step

contains

  function heatflow_step(nx, ny, u, unew, alpha, dt, dx, dy, residual) &
      bind(c, name='heatflow_step') result(status)
    integer(c_int), value, intent(in) :: nx, ny
    real(c_double), intent(in) :: u(nx, ny)
    real(c_double), intent(inout) :: unew(nx, ny)
    real(c_double), value, intent(in) :: alpha, dt, dx, dy
    real(c_double), intent(out) :: residual
    integer(c_int) :: status
    if (nx < 3 .or. ny < 3) then
      residual = 0.0_c_double
      status = 1_c_int
      return
    end if
    call ftcs_sweep(u, unew, alpha, dt, dx, dy, residual)
    status = 0_c_int
  end function heatflow_step
end module heatflow_capi

Source: J3/23-007r1 (Fortran 2023), 18.10 Interoperation with C functions

Every dummy argument is either value (the sizes and the scalar coefficients) or passed by address (the two fields and the residual). The field u(nx, ny) is an explicit-shape array whose bounds are the other value dummy arguments: the bounds of an explicit-shape array may be specified from earlier dummy arguments, and an explicit-shape array is exactly what a C double * pointing at nx * ny contiguous values corresponds to (18.3.6). The bind(c, name='heatflow_step') clause is redundant, since the default label is the lower-case Fortran name, but writing the label makes the exported symbol grep-able. Inside, the code calls the ordinary Fortran kernel, whose assumed-shape arguments receive a normal Fortran descriptor built by the compiler, so there is nothing C-specific below the interface.

The header is what C and C++ callers include. It is hand-written and has to be kept in step with the Fortran interface by the author, because no tool checks one against the other. extern "C" is needed only for C++:

#ifndef HEATFLOW_H
#define HEATFLOW_H
#ifdef __cplusplus
extern "C" {
#endif
/* Advance the nx-by-ny column-major field u by one FTCS step into unew.
   Returns 0 on success, 1 if the grid is smaller than 3x3. */

Name mangling, and why bind(c) replaced the underscore convention

A Fortran compiler does not export a procedure under the name in the source. What it does with the name is the mangling scheme of the compiler and is not defined by the standard. nm on the archive shows both what bind(c) gives and what an ordinary module procedure gets (the address column is removed):

GNU Fortran 16.2:
T __heatflow_kernels_MOD_ftcs_sweep
T __heatflow_kernels_MOD_jacobi_sweep
T heatflow_step

LLVM Flang 23:
T _QMheatflow_kernelsPftcs_sweep
T _QMheatflow_kernelsPjacobi_sweep
T heatflow_step

The two compilers disagree about every name except the one with bind(c): the module procedures are encoded with the module name, in different formats. That is why a C file cannot reasonably call a module procedure without bind(c), and why a library mixing compilers must expose only bind(c) names.

Before Fortran 2003 the only way to call Fortran from C was to guess the symbol. The common convention of Unix compilers was the lower-case name followed by one trailing underscore, with every argument passed by reference and, for each character argument, a hidden length argument appended at the end of the argument list. Code written for it still exists in large numerical libraries (BLAS and LAPACK among them, see BLAS, LAPACK and Numerical Libraries), and is shown here only to explain what bind(c) removed. The external subroutine below has no bind(c):

! Not interoperable: no bind(c). The linker name is chosen by the compiler.

  double precision, intent(in) :: factor

A caller of old code must also know that an argument by reference is the default, and that a character argument adds a hidden length argument which is passed by the compiler, not described by the name; a mistake in either corrupts the stack or the data silently. New code uses bind(c): the symbol is the binding label on every compiler and platform, the argument passing is stated in the interface (value or by address), and a string is a plain char *.

Arrays: column-major, explicit-shape and assumed-size

A Fortran array stores its first index fastest; a C array stores its last index fastest. An interoperable Fortran array argument is an explicit-shape or assumed-size array (18.3.6), and its dimension list reads in the opposite order to the C declaration: Fortran a(18, 3:7, *) interoperates with C int b[][5][18] (18.3.6, Note 3). The last (slowest) Fortran dimension corresponds to the first (outermost) C dimension, which is the one that may be * in Fortran and empty in C. A pointer to the first element serves for the whole array, and the shape is communicated by other arguments, which is the contract of heatflow_step. The next program makes the mapping visible: C fills a[i][j] with 10*i + j for 2 rows and 3 columns, and the Fortran declaration is a(3, 2).

/* A C array of 2 rows by 3 columns: a[i][j] with j varying fastest in memory. */
void hf_fill_rows(double a[2][3]) {
  for (int i = 0; i < 2; ++i)
    for (int j = 0; j < 3; ++j) a[i][j] = 10.0 * i + j;
}

C element a[1][2] is Fortran a(3, 2): the C row index becomes the last Fortran index, and the C column index the first. There is nothing to transpose in memory; both languages are looking at the same bytes, and a loop that wants unit stride runs over the first Fortran index and the last C index. For a two-dimensional field such as heatflow's u(nx, ny) the C code reads u[j * nx + i] (or declares double u[ny][nx]), which is what c_client.c does with u[(NX / 2) + NX * (NY / 2)]. The layout rules for Fortran arrays are in Arrays Fundamentals.

Four more facts about arrays at the boundary:

  • An array section that is not contiguous, such as u(1:10:2), is passed to an explicit-shape or assumed-size dummy argument through a contiguous temporary that the compiler creates and copies back after the call for intent(out) and intent(inout). C then sees contiguous memory, and a C routine that keeps the pointer after the call keeps a pointer to a dead temporary.

  • An allocatable array or a pointer array is never an interoperable variable (18.3.6, Note 2). Pass the first element (u(1, 1)), the section, or c_loc(u), or declare the dummy argument allocatable, assumed-shape or assumed-rank and let the C side deal with a descriptor, as in C Descriptors and ISO_Fortran_binding.

  • An assumed-size dummy x(*) has no bounds; C cannot ask Fortran for the size, so a count travels in another argument. Bounds checking (-fcheck=bounds) cannot catch an overrun made inside the C function.

  • c_loc does not accept a zero-sized array (18.2.3.7), and a C function must not dereference the address that a zero-sized actual argument produces.

Derived types and enumerations

A Fortran derived type is interoperable with a C struct if it has the bind(c) attribute, has the same number of components, and the components in the same positions interoperate (18.3.4). The names of the type and of the components do not matter. Constraints C1801-C1806 forbid sequence, type parameters, extends, type-bound procedures, an empty component list, and any pointer or allocatable component. A bit field, a flexible array member and a union have no Fortran counterpart. A C void * member becomes type(c_ptr), which is how an allocatable, a pointer or a procedure reaches a structure. Global variables

A C variable with external linkage can be a module variable in Fortran, and the other way round (18.9). The Fortran variable needs bind(c), which can be given with name= as in the example, and must be declared in the specification part of a module (C819) or be a common block. C pointers and function pointers

type(c_ptr) and type(c_funptr) are derived types with private components that are interoperable with any C object pointer and any C function pointer (18.3.2). They are opaque in Fortran: there is no arithmetic, no dereference and no comparison with ==. They get their values from C, from c_loc and c_funloc, or from the constants c_null_ptr and c_null_funptr, and are turned back into Fortran pointers with c_f_pointer and c_f_procpointer. A type(c_ptr) with the value attribute is the Fortran spelling of void *.

  • Lifetime. A C pointer to part of a Fortran object becomes undefined under the same conditions as a Fortran pointer to it would (18.8). If the target is a local variable, an automatic array or an allocatable that is deallocated, the address is dangling after return or deallocation; and if a Fortran dummy argument has neither target nor asynchronous, every C pointer into the object it was associated with becomes undefined when the call returns. The target attribute is also what stops the compiler from assuming that nothing else can alias the variable.

  • Ownership. Whoever allocated frees: memory from C’s malloc is released with free, never with Fortran’s deallocate, and memory from Fortran’s allocate never with free. The program above nullifies the Fortran pointers before the owner frees, since fptr has no way to know.

  • Alignment and type. c_f_pointer trusts the address; the type of fptr has to match the data, and the standard (18.2.3.3) states that the target must be the C address of an interoperable entity, a c_loc of a noninteroperable one, or storage not in use by any other Fortran entity.

  • Allocatable and pointer arrays. They are not interoperable variables; to hand one to a C function that wants a plain pointer, pass c_loc(a) (or a(1)) of an allocated, contiguous, non-empty array, as the program does with local.

Strings across the boundary

A C string is a char array ended by a null character, and a Fortran string is a character value with a length and no terminator. The two meet in three situations: passing a Fortran string to C, filling a Fortran buffer from C, and viewing a C string that C owns. Each has an idiom, and the Fortran 2023 procedures remove the boilerplate of the first and the last.

  • Fortran to C. trim(s) // c_null_char builds a C string by hand. Fortran 2023 adds f_c_string(s [, asis]) (18.2.3.9): the result has the characters of s (without trailing blanks unless asis is true) followed by c_null_char. Either value can be passed straight to a dummy argument character(kind=c_char) with dimension(*), because a character scalar actual argument may be associated with an array dummy argument by sequence association (15.5.2.12, and the note at the end of 18.3.7).

  • C fills a Fortran buffer. The buffer is an array of character(kind=c_char), and the code converts it to a character variable of the right length by looping over the characters up to the null, or by findloc as before.

  • C owns the string. The function returns a c_ptr. Find the length with strlen (a one-line interface to the C library), then c_f_pointer(p, chars, [n]) gives an array of n characters, or Fortran 2023 c_f_strpointer gives a deferred-length character(len=:), pointer that can be used as a string.

Optional arguments and assumed type

Since Fortran 2018 an interoperable procedure can have optional dummy arguments (18.3.7). When Fortran calls a C function and the actual argument is absent, C receives a null pointer; when C calls a Fortran procedure, the argument is absent exactly when C passes a null pointer. An optional dummy argument cannot also have value (C869), since a value has no null. A type(*) (assumed-type) dummy argument accepts an actual argument of any type and kind, with no type information: the Fortran way of writing const void *. With dimension(*) it receives the address of the first element of an array of any type, and c_sizeof of the actual array provides the byte count:

#include <stddef.h>

/* XOR checksum of nbytes bytes, any element type. */
unsigned int hf_checksum(const void *buf, size_t nbytes) {
  const unsigned char *b = buf;
  unsigned int sum = 0;
  for (size_t i = 0; i < nbytes; ++i) sum ^= (unsigned int)b[i] << (8 * (i % 4));
  return sum;
}

/* Scales x in place by factor, or by 2 when factor is a null pointer. */
void hf_scale(double *x, int n, const double *factor) {
  double f = factor == NULL ? 2.0 : *factor;
  for (int i = 0; i < n; ++i) x[i] *= f;
}

Fortran calling back into C, and the order of output

The example below is the pattern behind most real C-to-Fortran libraries: a C main calls a Fortran routine for the heavy work, hands it a function pointer to report progress and an opaque void * that the Fortran code passes back unchanged (the context pointer, which lets the C callback find its state without a global variable). The Fortran routine is the Jacobi iteration of heatflow with the kernel of heatflow_kernels; its tolerance is an optional argument (a null pointer in C) and its callback may be null too.

module heatflow_run

  use heatflow_kernels, only: jacobi_sweep
  implicit none
  private
  public :: hf_run

  abstract interface
    ! void (*report)(int step, double residual, void *context)
    subroutine report_cb(step, residual, context) bind(c)
      import :: c_int, c_double, c_ptr
      integer(c_int), value, intent(in) :: step
      real(c_double), value, intent(in) :: residual
      type(c_ptr), value, intent(in) :: context
    end subroutine report_cb
  end interface

contains

  ! int hf_run(int nx, int ny, int max_steps, const double *tolerance, void (*report)(...), void *context);
  function hf_run(nx, ny, max_steps, tolerance, report, context) bind(c, name='hf_run') result(steps)
    integer(c_int), value, intent(in) :: nx, ny, max_steps
    real(c_double), intent(in), optional :: tolerance    ! optional: a null pointer from C means "absent"
    type(c_funptr), value, intent(in) :: report          ! may be NULL
    type(c_ptr), value, intent(in) :: context            ! handed back untouched
    integer(c_int) :: steps

    real(c_double), allocatable :: u(:, :), unew(:, :)
    real(c_double) :: residual, tol
    procedure(report_cb), pointer :: notify

    tol = 1.0e-3_c_double
    if (present(tolerance)) tol = tolerance
    notify => null()
    if (c_associated(report)) call c_f_procpointer(report, notify)

    allocate (u(nx, ny), source=0.0_c_double)
    u(1, :) = 100.0_c_double                              ! hot left edge, fixed
    unew = u
    steps = 0_c_int
    do while (steps < max_steps)
      call jacobi_sweep(u, unew, residual)
      u = unew
      steps = steps + 1_c_int
      if (associated(notify) .and. mod(steps, 50_c_int) == 0_c_int) call notify(steps, residual, context)
      if (residual < tol) exit
    end do
  end function hf_run
end module heatflow_run

Input/output: Fortran and C each have their own buffers for standard output, and when both write to the same file the order is processor dependent (18.10.1). subroutine fortran_line(flush_after) bind(c, name='fortran_line')
  use, intrinsic :: iso_c_binding, only: c_int
  use, intrinsic :: iso_fortran_env, only: output_unit
  implicit none
  integer(c_int), value, intent(in) :: flush_after
  print '(a)', 'Fortran line'
  if (flush_after /= 0_c_int) flush (output_unit)
end subroutine fortran_line
#include <stdio.h>
#include <stdlib.h>

void fortran_line(int flush_after);

int main(int argc, char **argv) {
  int flush_after = argc > 1 ? atoi(argv[1]) : 0;
  printf("C line 1\n");
  if (flush_after) fflush(stdout);
  fortran_line(flush_after);
  printf("C line 2\n");
  return 0;
}

With nothing flushed, GNU Fortran 16.2 produced the call order, while Flang 23 printed the Fortran line first. After a flush (and fflush) on each side before control crosses the boundary, both agree. The standard does not promise either order, so a library that prints from both languages should flush before every call that crosses (or better: write from one language only). Exceptions and signals: a procedure defined by something other than Fortran must not use signal to change how a floating-point exception is handled, and must not alter the floating-point status other than by raising flags (18.10.3), and the flag values on entry to it are processor dependent. stop and error stop end the whole program, not only the Fortran part; see Error Handling and Program Termination and Floating-Point and IEEE Arithmetic.

Pitfalls

  • A kind that is not an iso_c_binding constant. integer, real and logical of default kind work on one platform and break on another; use c_int, c_double, c_bool.

  • value missing or extra. The compiler cannot see the C prototype. A missing value passes an address where C wants a number; an extra one passes a number where C wants an address.

  • A character(len=*) dummy argument for a char *. Use character(kind=c_char) with dimension(*); assumed length means a descriptor.

  • Forgetting the terminator. A Fortran string passed to a C const char * without c_null_char is read past its end.

  • Printing a c_char array with a. One element per format item; convert it to a string first.

  • Column-major, row-major. a[i][j] in C is a(j+1, i+1) in Fortran; a transposed loop is correct but slow.

  • Dangling c_loc. The address of a local, automatic or deallocated target; and c_loc of an array section that was copied to a temporary.

  • Freeing across allocators. deallocate on malloc memory, or free on allocate memory.

  • Linking without the Fortran runtime. an undefined reference to a name starting with _gfortran_ means -lgfortran is missing.

  • Mixing object files of different compilers' modules. Only the bind(c) names are stable.

  • Variable arguments. printf and other ... functions have no interoperable interface (18.3.7).

  • Exceptions, longjmp and signals through Fortran frames. Not permitted (18.10.1).

  • I/O ordering. Fortran and C buffers are separate; flush before crossing the boundary when both write to one file.

  • A c_f_strpointer call with a larger nchars than the string. Allowed by the standard, but it crashed LLVM Flang 23 in the experiment above; pass the exact length from strlen.

  • Trusting the compiler to compare interface and prototype. Keep one header, review it with the Fortran interface and test c_sizeof against sizeof for every shared structure.
