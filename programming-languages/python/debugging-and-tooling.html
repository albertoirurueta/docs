Debugging and Tooling

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Beyond print(), Python ships an interactive debugger and profilers in the standard library, and the ecosystem has settled on a small set of linters and formatters for keeping code consistent.

Debugging with pdb

breakpoint() and stepping commands

Calling the built-in breakpoint() drops into the Python Debugger (pdb) at that exact line, documented at the pdb module:

def total(items: list[int]) -> int:
    result = 0
    for item in items:
        breakpoint()          # pauses here on the first iteration
        result += item
    return result


total([1, 2, 3])

Running the script drops into the (Pdb) prompt, where a handful of one-letter commands drive execution:

$ python3 sums.py
> sums.py(5)total()
-> result += item
(Pdb) p item
1
(Pdb) n
> sums.py(3)total()
-> for item in items:
(Pdb) p result
1
(Pdb) c

The core commands are n (next — run the current line, step over calls), s (step — step into a function call), c (continue — run until the next breakpoint), p <expr> (print an expression), and l (list — show source around the current line). q quits the debugger entirely.

PYTHONBREAKPOINT=0 python3 sums.py disables every breakpoint() call without editing the source — useful for leaving them in during development and skipping them in CI.

Post-mortem debugging

pdb.pm() inspects the stack of the last uncaught exception, after the fact, from the interactive interpreter — no need to have set a breakpoint in advance:

$ python3 -i crashy.py
Traceback (most recent call last):
  File "crashy.py", line 2, in <module>
    1 / 0
    ~~^~~
ZeroDivisionError: division by zero
>>> import pdb; pdb.pm()
> crashy.py(2)<module>()
-> 1 / 0
(Pdb) l

Running a whole script under the debugger from the start, so it stops automatically at the first unhandled exception, uses python3 -m pdb:

$ python3 -m pdb crashy.py
> crashy.py(1)<module>()
(Pdb) c
Traceback (most recent call last):
  ...
ZeroDivisionError: division by zero
Uncaught exception. Entering post mortem debugging
Running 'cont' or 'step' will restart the program
> crashy.py(2)<module>()
-> 1 / 0
(Pdb)

Performance Basics

Micro-benchmarks with timeit

timeit runs a snippet many times and reports the best timing, avoiding the noise of a single time.time() measurement:

python3 -m timeit -s "data = list(range(1000))" "sorted(data)"
$ python3 -m timeit -s "data = list(range(1000))" "sorted(data)"
20000 loops, best of 5: 12.3 usec per loop

The -s option runs a one-time setup statement (building data) that is excluded from the timing; the timed statement (sorted(data)) is what gets repeated.

Profiling a script with cProfile

cProfile instruments every function call in a run and reports where the time actually went:

python3 -m cProfile -s cumulative slow_script.py
$ python3 -m cProfile -s cumulative slow_script.py
         2814 function calls in 0.842 seconds

   Ordered by: cumulative time

   ncalls  tottime  percall  cumtime  percall filename:lineno(function)
        1    0.001    0.001    0.842    0.842 slow_script.py:1(<module>)
        1    0.003    0.003    0.841    0.841 slow_script.py:4(main)
     1000    0.812    0.001    0.812    0.001 slow_script.py:9(fib)

-s cumulative sorts by cumulative time (a function plus everything it calls), which is usually the fastest way to spot the actual bottleneck before reaching for timeit on the specific line found.

Linters and Formatters

The ecosystem has no single mandated tool — any of the following is a reasonable choice, and many projects combine a formatter with a linter:

  • ruff — a fast linter (and formatter) that replaces most of what flake8 plus several plugins used to do:

    pip install ruff
ruff check .

  • black — an opinionated formatter with almost no configuration; it rewrites code to one consistent style instead of just flagging violations:

    pip install black
black .

  • flake8 — the longer-standing linter combining pyflakes (error detection) and pycodestyle (style checks), documented at flake8.pycqa.org:

    pip install flake8
flake8 .

Editor Tooling Recap

IDLE, VS Code, and PyCharm were already introduced for writing and running a first script in Getting Started with Python; all three also drive the debugger described here directly from the editor — clicking a line number to set a breakpoint instead of typing breakpoint(), and stepping with buttons that map to the n/s/c commands of pdb underneath. See Python IDEs & Tools for more editors and IDEs.

Debugging and Measuring Systematically

A debugging loop that converges

Debugging is hypothesis testing. Reproduce the failure with the smallest input, read the last line of the traceback first (the exception type and message) and then walk up to the frame in your own code, form a hypothesis about which value is wrong, and check it by running code rather than rereading it. Prefer tools that show state (print with !r, breakpoint(), pdb.post_mortem, logging) over guessing, and stop when a failing test captures the bug so it cannot return.

flowchart TD A["Failure observed"] --> B["Reproduce with the smallest input"] B --> C["Read the traceback bottom-up"] C --> D["State a hypothesis about a wrong value"] D --> E["Inspect: print !r, breakpoint, or logging"] E --> F{"Hypothesis confirmed?"} F -- No --> D F -- Yes --> G["Write a failing test"] G --> H["Fix, run tests, remove debug output"]

Driving pdb and what the commands mean

breakpoint() (3.7+) calls sys.breakpointhook, which starts pdb by default and can be redirected or disabled with the PYTHONBREAKPOINT environment variable (PYTHONBREAKPOINT=0 disables every call, handy before shipping). Inside the debugger n (next) runs the current line without entering calls, s (step) enters them, c continues to the next breakpoint, r runs until the function returns, p expr and pp expr print values, w shows the stack, u and d move between frames, b file:line or b function sets a breakpoint (with an optional condition), and q quits. The sample drives the debugger with a script of commands instead of a keyboard, so the transcript is reproducible.

import io
import pdb


def average(values):
    total = 0
    for v in values:
        total += v
    return total / len(values)


# drive pdb with scripted commands instead of a keyboard (the same commands you would type)
# runcall stops at the first line of average, so no breakpoint is needed
script = "next\nnext\nnext\nnext\nnext\np (total, v)\nquit\n"
out = io.StringIO()
debugger = pdb.Pdb(stdin=io.StringIO(script), stdout=out)
debugger.use_rawinput = False                          # read the script, not the terminal
try:
    debugger.runcall(average, [2, 4, 6])
except pdb.bdb.BdbQuit:
    pass

for line in out.getvalue().splitlines():
    line = line.replace("(Pdb) ", "")
    if line.startswith("->") or line.startswith("(") and "Pdb" not in line:
        print(line)

Output:

-> total = 0
-> for v in values:
-> total += v
-> for v in values:
-> total += v
-> for v in values:
(6, 4)

The arrow lines are the next line to execute, so the total += v at the end of the stepping shows the loop running; p (total, v) printed the running total and the loop variable at that moment. Post-mortem debugging (python -m pdb script.py, then c after the crash, or pdb.post_mortem() in an except block) opens the debugger at the frame where an exception occurred, with all locals intact.

Measure before optimising

Performance work follows a fixed order: make it correct, measure to find the hot spot, change one thing, measure again. timeit times small snippets and repeat with the minimum of several runs is the least noisy estimate, because the other runs are slowed by unrelated activity. cProfile records every function call and reports counts and cumulative times, which locates the expensive function; pstats sorts and filters the result. Call counts are exact and repeatable while times are not, which is why the sample prints counts only. tracemalloc does for memory what cProfile does for time: it records where allocations happen and can compare two snapshots to find growth, which is how you hunt a leak.

import cProfile
import io
import pstats
import timeit


def normalise(title):
    return " ".join(title.lower().split())


def build_index(titles):
    index = {}
    for t in titles:
        index.setdefault(normalise(t)[0], []).append(t)
    return index


titles = ["Dune", "  Emma ", "Ulysses", "dubliners"] * 2500

profiler = cProfile.Profile()
profiler.runcall(build_index, titles)
stats = pstats.Stats(profiler, stream=io.StringIO()).sort_stats("ncalls")
rows = [(func[2], st[0]) for func, st in stats.stats.items() if func[2] in ("build_index", "normalise")]
print(sorted(rows))                                  # call counts are exact; times vary per run

# timeit: repeat and take the minimum, which is the least noisy estimate
best_join = min(timeit.repeat("''.join(parts)", "parts=['ab']*1000", number=200, repeat=5))
best_plus = min(timeit.repeat("s=''\nfor p in parts: s += p", "parts=['ab']*1000", number=200, repeat=5))
print("both measured:", best_join > 0 and best_plus > 0)

Output:

[('build_index', 1), ('normalise', 10000)]
both measured: True
import tracemalloc

tracemalloc.start()
before = tracemalloc.take_snapshot()

leaky_cache = []
for n in range(2000):
    leaky_cache.append(("title-%d" % n) * 10)          # something that keeps growing

after = tracemalloc.take_snapshot()
top = after.compare_to(before, "lineno")[0]
print(top.size_diff > 50_000, top.count_diff >= 2000)
print(top.traceback[0].lineno, top.traceback[0].filename.endswith("dbg_mem.py"))
current, peak = tracemalloc.get_traced_memory()
print(peak >= current > 0)
tracemalloc.stop()

Output:

True True
8 True
True

The profile shows that normalise ran 10000 times for one call of build_index: that is the number to cut (for example by caching repeated titles) before touching anything else. Use python -m cProfile -s cumtime script.py for a whole program, and a sampling profiler such as py-spy for a running process you cannot modify.

Tooling checklist

  • run python -X dev (development mode) or -W error in tests to surface resource warnings and deprecations early;

  • faulthandler (python -X faulthandler) prints a traceback on a crash or a hang signal in native code;

  • a formatter (Black or Ruff format), a linter (Ruff or Flake8) and a type checker (mypy or pyright) run in CI and as a pre-commit hook catch most mistakes before a debugger is needed;

  • read the bytecode with dis only when you need to explain surprising behaviour; the output changes between Python versions.

Every snippet in this section was run with CPython 3.14.8 and the output shown is the real output.
