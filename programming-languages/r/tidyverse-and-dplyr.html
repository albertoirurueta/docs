The tidyverse and dplyr

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. The tidyverse is a collection of add-on packages that share one design: tables are tidy data frames, functions are small verbs whose first argument is the data and whose result is the same kind of table, and the verbs are chained with a pipe. dplyr is its package for working on a table, the one every other tidyverse page starts from, and this page is about it. It covers what the tidyverse is and what library(tidyverse) attaches, how a tibble differs from a base data frame, the little tidy evaluation that the verbs need (data masking, .data, .env and {{ }}), the verbs themselves (filter(), select(), mutate(), arrange(), summarise(), group_by() and .by, across(), rowwise(), window functions, joins, case_when()), the shelf analyses rewritten with them, a table of the base R equivalents, the real error messages, and the functions that newer releases have superseded. The packages used were checked at these versions: tidyverse 2.0.0 (the package that installs and attaches the others), dplyr 1.2.1 and tibble 3.3.1; the examples also call functions of rlang 1.3.0 (rlang::cnd_message()), and use tidyselect 1.2.1, pillar 1.11.1 and vctrs 0.7.3, which dplyr and tibble load for themselves. One example attaches the whole tidyverse, which attaches ggplot2 4.0.3, forcats 1.0.1, lubridate 1.9.5, purrr 1.2.2, readr 2.2.0, stringr 1.6.0 and tidyr 1.3.2 along with dplyr and tibble; only their startup message is shown, and their own pages are ggplot2 and the Grammar of Graphics and tidyr, purrr and stringr. magrittr 2.0.5 supplies the %>% pipe that dplyr re-exports (one example runs it), and conflicted 1.2.0 is named in prose and not run.

Every example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines that start with #> are what it printed, with the messages that R writes to the standard error stream (such as the startup message of a package) placed where they appeared. The scripts also pass the default lintr 3.4.0 linters; the one # nolint: comment marks the line that deliberately uses the %>% pipe. Most scripts load only dplyr, with library(dplyr, warn.conflicts = FALSE): the section on attaching the tidyverse explains the masking message that warn.conflicts = FALSE hides, and repeating it in every block would only add noise. The characters ×, ℹ and ✖ in the output are the ones R prints in a UTF-8 console, and the quotation marks around the strings of a tibble are the tibble’s own. Errors and warnings that a script shows on purpose are caught, and printed either with conditionMessage() or, where the header matters, in the form the console shows. The examples use the library-shelf scenario of the section: the data frames books and loans, the constants shelf_today and loan_days and the helper normalise_isbn() come from the scenario.R file described on the section index, and a script that needs them starts with source("scenario.R"), which reads books.csv with read.csv("books.csv") and loans.csv with read.csv("loans.csv", colClasses = "character"). books has 16 rows and loans has 60, both deliberately untidy; Data Frames cleans them with base R, and this page repeats the same analyses with dplyr so that the numbers can be compared (they agree).

This page is the first of the three data-ecosystem pages. The data frame that dplyr works on is the one of Data Frames, the data-mask idea is the one of Evaluation and Non-Standard Evaluation, and the pipe is the one of Pipes and the Native Pipe. Reshaping with tidyr, iteration with purrr and strings with stringr are in tidyr, purrr and stringr, and the same operations in data.table’s syntax are in data.table.

What the tidyverse is

The tidyverse web site calls it an opinionated collection of packages for data science whose members share one design philosophy, one grammar and common data structures (tidyverse.org). It is not a language extension and it is not part of R: every package in it is an ordinary add-on package, installed from CRAN with install.packages("tidyverse"), which installs the whole collection. What makes it recognisable is a small set of design principles, written down by its creator as the tidy tools manifesto, which describes itself as aspirational and likely to change. Its four principles are to reuse existing data structures, to compose simple functions with the pipe, to embrace functional programming, and to design for humans. Three of them are the ones that show on every line of tidyverse code.

  • Tidy data. Tidy data is a way of laying out a table so that every tool can rely on it: each variable is a column, each observation is a row and each value is a cell (the tidyr article on tidy data calls this Codd’s third normal form in statistical language). A tidy table is a plain data frame, so the first principle, reuse existing data structures, is met by the tibble, a data frame with stricter behaviour.

  • Consistent APIs. The functions of dplyr are verbs. The first argument is the table, the other arguments describe what to do in terms of the table’s columns, and the result is a table of the same kind: a tibble in, a tibble out; a grouped tibble in, a grouped tibble out. A verb either computes with the columns (mutate(), filter(), summarise()) or selects some of them (select(), rename(), relocate()), and the helpers that select columns are the same everywhere.

  • Pipes. Because every verb takes a table and returns a table, a step can be chained to the next one with a pipe, so that code reads in the order in which the work is done. The tidyverse used magrittr’s %>% for years; since R 4.1.0 the language has its own pipe, |>, and the documentation of dplyr uses it throughout since version 1.2.0 (the NEWS). This page uses |>; the pipes page explains the pipe itself.

Source: tidyverse package documentation: The tidy tools manifesto

The principles describe the design; what is installed is a set of packages with a division of work. The core of the tidyverse is the set of nine packages that library(tidyverse) attaches. lubridate joined the core in tidyverse 2.0.0, and stringr and forcats had been added in 1.2.0 (the tidyverse NEWS).

Tidy data in practice

A table is tidy or untidy relative to the question. The shelf loans table is tidy in the sense above (one loan per row, one variable per column), but a summary of it can be laid out in either way. The script counts the loans of every member per year twice. table() returns a matrix whose column headings are the values of a variable (2025, 2026): the variable year is hidden in the layout and the cell is the value of the variable n. count() returns one row per combination, with member, year and n as columns, which is the form that filter(), group_by() and ggplot2 expect. table() leaves a missing value out unless it is asked not to, where count() keeps it as a group.

library(dplyr, warn.conflicts = FALSE)
source("scenario.R")
few <- as_tibble(loans) |>
  filter(member %in% c("Farid Karimi", "Ben Okafor"))

# Untidy: the years are column headings, and the cells hold a count.
table(few$member, format(few$loan_date, "%Y"))
#>
#>                2025 2026
#>   Ben Okafor      5    0
#>   Farid Karimi    1    1

# Tidy: one row per member and year, one column per variable.
few |> count(member, year = format(loan_date, "%Y"))
#> # A tibble: 3 × 3
#>   member       year      n
#>   <chr>        <chr> <int>
#> 1 Ben Okafor   2025      5
#> 2 Farid Karimi 2025      1
#> 3 Farid Karimi 2026      1

Source: tidyr package documentation: Tidy data

Turning one layout into the other, wide to long and back, is what pivot_longer() and pivot_wider() of tidyr do, and they are the subject of the next page.

Attaching the tidyverse

library(tidyverse) attaches the nine core packages in one call. The startup message lists them with their versions (the header’s "tidyverse 2.0.0" is the version of the meta-package), and then reports the conflicts: names that one of the newly attached packages defines and that were already defined by a package attached earlier. A conflict is not an error, but from that moment the name refers to the tidyverse function, and the older one is hidden ("masked") and has to be called as package::name().

The report names the two conflicts of an ordinary session: dplyr::filter() masks stats::filter() and dplyr::lag() masks stats::lag(). The help page adds that four conflicts are deliberately left out: dplyr’s intersect(), union(), setequal() and setdiff(), which make the base functions generic and should not harm existing code. tidyverse_conflicts() prints the same report on demand, options(tidyverse.quiet = TRUE) silences the startup message (the tidyverse 1.2.0 NEWS), and loading the conflicted package first (named here, not run) turns every conflict into an error that asks for an explicit package::name(); tidyverse 2.0.0 advertises it in the message for that reason, and omits its own report when conflicted is loaded. search() shows the order the packages were attached in: the last one attached, lubridate, comes first, and the earliest, package:stats, comes after all of them. For the base-R view of that mechanism see Scoping, Environments and Closures.

Attaching dplyr alone prints the longer message that warn.conflicts = FALSE hides: the objects filter and lag are masked from package:stats, and intersect, setdiff, setequal and union from package:base. The masking has an effect. filter(1:5, rep(1 / 3, 3)) is the moving-average filter of the stats package, and with dplyr attached it fails with no applicable method for 'filter' applied to an object of class "c('integer', 'numeric')", because dplyr’s filter() is a generic for data frames (the last line of the script in the section on errors shows it). stats::filter() and stats::lag() are still there under their qualified names.

Two habits follow. A script that uses only dplyr should attach only dplyr (library(dplyr)), so that the reader and the next maintainer see what the code depends on. And code in a package should not depend on tidyverse at all: the tidyverse package exists to install and attach the others (its few functions, such as tidyverse_conflicts(), are about the collection itself), so a package lists only the packages it calls in Imports and writes dplyr::filter() or imports the names it needs (see Packages, Libraries and Namespaces).

Tibbles

A tibble is a data frame with a different print method and a few stricter rules. Its class is c("tbl_df", "tbl", "data.frame"), so every function that accepts a data frame accepts a tibble, and base R functions such as nrow(), lm() and aggregate() work on it. A tibble is created with tibble(), converted from a data frame (or a list, a matrix) with as_tibble(), and written row by row with tribble(); all three come from the tibble package, which dplyr re-exports. read.csv() returns a plain data frame, so the scripts convert the shelf data with as_tibble(): readr’s read_csv() returns a tibble directly (see tidyr, purrr and stringr).

library(dplyr, warn.conflicts = FALSE)
source("scenario.R")

# read.csv() returns a data frame; as_tibble() converts it.
books_tbl <- as_tibble(books)
class(books_tbl)
#> [1] "tbl_df"     "tbl"        "data.frame"

The print method shows the dimensions in the first line (# A tibble: 60 × 5), the type of every column in angle brackets under its name (<chr> character, <date>, <int>, <dbl> double, <lgl>, <fct> factor, <list>), and only as many rows as fit the options: a table with more than 20 rows prints its first 10, and a footer says how many rows (and columns, if they do not fit the width) were left out. NA in a character column prints as <NA>, and in other types as NA. The print is for reading: the data are unchanged, and a tibble is converted back with as.data.frame().

How a tibble differs from a data frame

The differences are the reason for tibbles, and they are the traps of data frames that Data Frames lists, closed. The tibble package states them as invariants, a small set of rules for [[, $ and [ that always hold (tibble package documentation: Invariants).

library(dplyr, warn.conflicts = FALSE)
source("scenario.R")
books_tbl <- as_tibble(books)

# [ with one column: a vector for a data frame, a tibble for a tibble.
class(books[, "year"])
#> [1] "integer"
class(books_tbl[, "year"])
#> [1] "tbl_df"     "tbl"        "data.frame"

# $ matches a partial name on a data frame, never on a tibble.
books$ye[1:3]
#> [1] 1974 1813 2019
tryCatch(books_tbl$ye, warning = conditionMessage)
#> [1] "Unknown or uninitialised column: `ye`."

# Only length-one values are recycled; a column may use an earlier one.
tryCatch(tibble(a = 1:3, b = 1:2), error = conditionMessage)
#> [1] "Tibble columns must have compatible sizes.\n• Size 3: Existing data.\n• Size 2: Column `b`.\nℹ Only values of size one are recycled."
tibble(x = 1:3, y = x * 2)
#> # A tibble: 3 × 2
#>       x     y
#>   <int> <dbl>
#> 1     1     2
#> 2     2     4
#> 3     3     6
tryCatch(data.frame(x = 1:3, y = x * 2), error = conditionMessage)
#> [1] "object 'x' not found"

# Row names are dropped on conversion; ask for them as a column.
named <- data.frame(pages = c(387, 432), row.names = c("dispossessed", "pride"))
as_tibble(named, rownames = "key")
#> # A tibble: 2 × 2
#>   key          pages
#>   <chr>        <dbl>
#> 1 dispossessed   387
#> 2 pride          432

# Names are taken as given, with no check.names mangling.
names(data.frame(`my col` = 1))
#> [1] "my.col"
names(tibble(`my col` = 1))
#> [1] "my col"

The partial matching of $ deserves emphasis because it is silent in a data frame: books$ye returns year today and NULL, with no warning, as soon as a second column starting with ye is added. Tidy evaluation in brief

Inside a dplyr verb, filter(books, year > 2020) refers to the column year as if it were a variable. That is data masking: the arguments are not evaluated in the calling environment but in a mask built from the columns of the table, with the calling environment behind it. It is the same idea as with() and subset() of base R, described in Evaluation and Non-Standard Evaluation, extended by the rlang package into tidy evaluation with a few tools for the cases where the mask is in the way. A second mechanism, tidy selection, is used by the arguments that choose columns (select(), rename(), relocate(), across(), pull()): there title:isbn, starts_with("t") and where(is.numeric) are not ordinary R expressions but a small selection language of the tidyselect package.

The tools, in the order in which they are needed:

  • .data and .env. A column and a variable in the workspace with the same name collide, and the column wins: with a variable year in the global environment, filter(books, year > year) compares the column with itself. .data$year is the column and .env$year is the variable, whatever else exists. .data[[col]] takes the column from a string col, which is how a function receives a column name as text.

  • {{ }} ("embrace"). In a function that passes its argument on to a verb, {{ var }} says: this argument holds a column name that the caller wrote unquoted, evaluate it inside the mask. It lets a function be called as count_by(books, genre).

  • all_of() and any_of(). A character vector of column names in select() is selected with all_of(x), which fails if one is missing, or any_of(x), which ignores the missing ones. A bare character vector is ambiguous (is it a column or a variable?) and tidyselect warns that this use is deprecated.

The dplyr verbs

dplyr’s functions are grouped by what they work on: rows (filter(), arrange(), distinct(), slice(), count()), columns (select(), rename(), relocate(), mutate(), pull()), groups (group_by(), summarise(), reframe(), .by), and pairs of tables (the joins, bind_rows() and the set operations). The reference index and the introductory article (dplyr package documentation: Introduction to dplyr) list them all. The sections below take them in that order, using the shelf data.

filter(): choose rows

filter() keeps the rows for which the conditions are TRUE. Several conditions separated by commas are combined with &, so a comma is the idiomatic spelling of "and" (filter(a > 1, b == "x")). A row where the condition is NA is dropped, like a FALSE, which is the difference to base R’s df[df$year > 2000, ] that returns a row of NA. dplyr 1.2.0 added the companion filter_out(), which names the rows to drop and keeps the NA ones, and when_any() and when_all(), the element-wise | and & of any number of conditions; if_any() and if_all() build a condition over several columns. between(), %in% and is.na() are the usual helpers.

arrange(), distinct(), count() and slice_*()

arrange() sorts rows by one or more columns; desc() reverses one column, and missing values always come last. Character columns are sorted in the C locale, not in the locale of the session: capital letters before small letters, not the order of a dictionary. This changed in dplyr 1.1.0 (the NEWS: arrange() and group_by() now use the C locale, for speed and reproducibility), and .locale gives the order of a language when it matters (arrange(x, .locale = "en"); it needs the stringi package, which the tidyverse installs). Base R’s order() uses the locale of the session (Data Frames has the section on sorting).

distinct() keeps the first row of each combination of the columns named (all columns when none are named; .keep_all = TRUE also keeps the other columns). count() is group_by() plus summarise(n = n()) plus ungroup() in one call, with sort = TRUE to put the largest group first, wt = to sum a column instead of counting, and name = to rename the count; add_count() adds the count as a column and keeps every row. The slice_*() functions choose rows by position (slice_head(), slice_tail()), by value (slice_max(), slice_min(), which keep ties unless with_ties = FALSE) and at random (slice_sample()); all take by =.

mutate(): create and change columns

mutate() adds columns, replaces columns that exist under the same name and removes a column that is set to NULL. The expressions are evaluated one after the other, so a later one can use an earlier one, and a result of length one is recycled to every row (a result of any other wrong length is an error). The arguments .before and .after place new columns, and .keep says which columns survive: "all" (the default), "used" (the inputs and the results), "unused" (the columns not used) or "none" (only the results, like transmute(), which is superseded). .before, .after and .keep were experimental in dplyr 1.0.0 and became stable in 1.1.0. On a grouped table, or with .by, an expression is evaluated once per group, so mean(pages) is the group mean next to every row.

case_when() and if_else()

if_else(condition, true, false, missing = ) is the vectorised if: both branches are checked for type, so mixing an integer and a string is an error, where base ifelse() coerces silently. case_when() takes a sequence of condition ~ value formulas, tries them in order and gives, for each row, the value of the first condition that is TRUE. A row that matches no condition gets .default (NA if none is given) and so does a row whose conditions are all NA. dplyr 1.2.0 added .unmatched = "error", which turns a forgotten case into an error instead of an NA, and recode_values(), replace_values() and replace_when() for lookups by value; they supersede case_match() (deprecated in 1.2.0) and recode().

Groups: group_by(), summarise() and .by

group_by() does not change the data: it records which columns define the groups, and the later verbs work group by group. summarise() collapses each group to one row, with one column for the grouping columns and one for every expression, and ungroup() removes the grouping. A grouped tibble prints a Groups: line with the number of groups, group_vars() returns the grouping columns and n_groups() their number. n() (the size of the group) and n_distinct() (the number of different values, which counts NA as one) are the two summaries that need no column. The result of a grouped summarise() is sorted by the grouping columns, with NA as the last group.

When summarise() groups by several columns it drops only the last one, so the result is still grouped by the others, and a message says so. The message is one of the most seen in tidyverse code, and its wording changed: dplyr 1.2.0 reworded it to be clearer (the NEWS), and a tutorial may show the older one-line form that begins with `summarise()` has grouped output by. The .groups argument chooses the grouping of the result ("drop_last", "drop", "keep", "rowwise") and silences the message.

library(dplyr, warn.conflicts = FALSE)

The .by argument

A grouping that sticks to the table is a source of bugs: an ungroup() that was forgotten changes the meaning of the next verb. dplyr 1.1.0 added .by (and by in the slice_*() functions), which groups for one operation only: the result is ungrouped, and the argument works in mutate(), summarise(), reframe(), filter() and slice_*(). A second difference is the order: group_by() sorts the groups by their keys, and .by keeps the order in which the groups first appear. .by was experimental when it appeared and the 1.2.0 NEWS lists it as stable. Giving .by to a table that is already grouped is an error.

reframe() (new in 1.1.0, stable in 1.2.0) is summarise() for the case where each group yields any number of rows; since dplyr 1.2.0 a summarise() expression that returns more or fewer than one row is an error that points to reframe(), and reframe() always returns an ungrouped table.

across(), pick(), if_any() and if_all(): the same thing on many columns

across(.cols, .fns) applies a function (or a named list of functions) to a tidyselect selection of columns, inside mutate() or summarise(). The result columns keep the input name when one function is given and get name_fn when a list is given; the .names argument is a glue pattern ({.col} by default for one function, {.col}_{.fn} for several, or your own such as "median_{.col}") that controls the names. across() was added in dplyr 1.0.0 (the 1.0.0 NEWS), and the family of scoped verbs with the suffixes _if, _at and _all is superseded by across() and pick(). Two details of the current release matter. Extra arguments for .fns must be put in an anonymous function, \(x) mean(x, na.rm = TRUE): passing them through the ... of across() was deprecated in dplyr 1.1.0, and the script shows the warning. And across() is not for filter(): if_any() and if_all() combine a predicate over several columns with | and &. pick() (new in 1.1.0) selects columns and returns them as a data frame, for functions that take a whole data frame; it replaces cur_data() and across() without .fns.

rowwise(): one row at a time

Most dplyr and R functions are vectorised, so a calculation across columns is written as arithmetic (back - start) or with pmin() and pmax(). A function that collapses its input, such as max() or median(), sees the whole column and returns one number. rowwise() treats every row as a group of one, so the function is called once per row; c_across() gathers the columns of the current row into a vector. A rowwise table prints as Rowwise:, and ungroup() removes the mode. For sums and means, rowSums() and rowMeans() on pick() are faster than a rowwise computation, and the column-wise across() is faster than both when the operation is the same for every column. The row-wise operations article is the full reference.

library(dplyr, warn.conflicts = FALSE)

# The day each loan started, was due and came back.
days <- tibble(start = c(1, 3, 7), due = c(22, 24, 28), back = c(21, 30, 8))

# max() collapses its input, so it needs rowwise(); c_across() collects the
# columns of one row. For sums, rowSums() on pick() is much faster.
days |>
  rowwise() |>
  mutate(
    latest = max(start, due, back),
    span = diff(range(c_across(start:back)))
  ) |>
  ungroup() |>
  mutate(total = rowSums(pick(start:back)))
#> # A tibble: 3 × 6
#>   start   due  back latest  span total
#>   <dbl> <dbl> <dbl>  <dbl> <dbl> <dbl>
#> 1     1    22    21     22    21    44
#> 2     3    24    30     30    27    57
#> 3     7    28     8     28    21    43

Window functions

A window function takes a vector and returns a vector of the same length, so it can be used in mutate() and filter() next to the rows, on the whole table or within groups. Three families are used most. The offsets lag() and lead() look at the previous and next row (the first or last is the default, NA); dplyr’s lag() masks stats::lag(), the time-series function with the same name, and both are for a different job. The cumulative functions are cumsum(), cummean(), cummax() and friends. The ranking functions differ in how they treat ties: row_number() breaks them by position, min_rank() gives tied values the lowest rank and leaves gaps (1, 1, 3), dense_rank() leaves no gaps (1, 1, 2), percent_rank() rescales the minimum rank to the range 0 to 1 and ntile(x, n) cuts the ordered values into n buckets of nearly equal size. The ranks are ascending: min_rank(desc(x)) ranks the largest first. Since mutate() and filter() apply the function per group when the data are grouped or .by is given, "the longest loan of each member" is filter(held == max(held), .by = member). The window functions article is the long version.

Joins

A join combines the columns of two tables by matching rows on a key. In x |> left_join(y) the table x is on the left. Mutating joins add the columns of y to x: left_join() keeps every row of x, right_join() every row of y, inner_join() only the rows that match in both, and full_join() all of them; a row without a match gets NA in the columns that came from the other table. Filtering joins use y only to select the rows of x: semi_join() keeps the rows that have a match, anti_join() the rows that have none (the base-R idiom x[x$k %in% y$k, ] and x[!x$k %in% y$k, ]). cross_join() returns every combination.

The key is given by by: a character vector (by = "isbn"), or join_by(), the specification of dplyr 1.1.0, which takes unquoted names and operators (join_by(isbn == book_isbn) for different names). Without by, the join uses the columns the two tables have in common and prints Joining with `by = join_by(isbn)`; a script should name the key. Columns with the same name that are not keys get the suffix (.x and .y by default). dplyr preserves the order of the rows of x, where merge() sorts on the key. The join compares the key columns exactly, so a key of two different types is an error (isbn as text in loans and a number in another table) and a key written differently in two tables silently matches nothing: the shelf ISBNs have to be normalised with normalise_isbn() first, as in Data Frames.

Duplicate keys: relationship

When a key is not unique in y, or in x, a row is matched more than once and the result has more rows than x. dplyr 1.1.1 added relationship, which states the expected cardinality ("one-to-one", "one-to-many", "many-to-one", "many-to-many") and signals an error when the data do not satisfy it; without it, an equality join checks only for the rarer and almost always unintended many-to-many case and warns. The 1.1.1 NEWS records the history: dplyr 1.1.0 warned about both one-to-many and many-to-many matches, which was too often, so 1.1.1 limited the warning to many-to-many (which can multiply the rows beyond recognition) and added relationship; relationship = "many-to-one" is the replacement for multiple = "error", and the values "error" and "warning" of multiple were deprecated in 1.1.1 and are now defunct. The remedy for a many-to-many warning is to find the duplicate key (count(y, key) |> filter(n > 1)), then either make the key unique, join a different table, or declare the relationship.

join_by(): inequality, rolling and overlap joins

join_by() is not only an equality. It accepts <, <=, > and >= for inequality joins, closest() for rolling joins (the nearest match), and between(), within() and overlaps() for ranges. The condition has to be written in terms of the columns of the two tables; an arbitrary expression such as due - 40 >= date is not allowed, so compute the column with mutate() first. Inequality joins return all the matches by default, and keep defaults to keeping both key columns for them. This is the dplyr form of the SQL range join and of data.table’s on = with a non-equi condition. See join_by and the two-table verbs article.

library(dplyr, warn.conflicts = FALSE)

A pitfall: a summary hides its own input

In summarise() (and mutate()) the expressions are evaluated in order, and a name created by one is visible to the next ones. If a summary is named like the column it summarises, the expressions after it see the summary instead of the column: mean(overdue) after overdue = sum(overdue) is the mean of a single number, 32. There is no error and no warning.

library(dplyr, warn.conflicts = FALSE)
source("scenario.R")

  mutate(
    held = as.integer(coalesce(return_date, shelf_today) - loan_date),
    overdue = held > loan_days
  ) |>
  filter(!is.na(overdue))

# A name created in summarise() hides the column for the expressions after
# it: mean(overdue) is the mean of the number just made.
loans |> summarise(overdue = sum(overdue), share = mean(overdue))
#> # A tibble: 1 × 2
#>   overdue share
#>     <int> <dbl>
#> 1      32    32

loans |> summarise(share = mean(overdue), n_overdue = sum(overdue))

dplyr and base R side by side

The table is the dplyr article on dplyr and base R lined up with the base-R operations of Data Frames. Pitfalls

  • A summary hides its own input. In summarise(overdue = sum(overdue), share = mean(overdue)), the second expression sees the new overdue. Name results differently.

  • A grouping that was forgotten. group_by() leaves the table grouped for every following verb, and a later mutate(), filter() or slice() works per group. Finish with ungroup(), give .groups = "drop", or use .by, which never leaves a grouping behind.

  • NA in conditions. filter() drops the NA rows, case_when() does not match them, and mean() returns NA unless na.rm = TRUE. count() and group_by() keep NA as a group; table() drops it.

  • The order of text. arrange() and group_by() use the C locale: capitals first, no accents folded. Pass .locale to arrange() when a language’s order is wanted, and expect a different order from base order() and sort() in a non-C locale.

  • Joins are exact. Differently formatted keys match nothing (the hyphens in the shelf ISBNs), duplicate keys multiply rows, and a key of two types is an error. Name by, normalise the key first, and state relationship.

  • The masked names. With the tidyverse attached filter() and lag() are dplyr’s, not stats'. .data$x and .env$x settle a clash between a column and a variable; a bare character vector in a selection needs all_of().

  • Partial matching is gone. tb$ye is NULL with a warning on a tibble and a silent year on a data frame, and code that works on one may not work on the other.

  • rowwise() is slow. It calls the expression once per row. Prefer vectorised arithmetic, pmin(), pmax(), rowSums() or across().

  • slice_max() and slice_min() keep ties. Set with_ties = FALSE for exactly n rows.

  • Printing is not the data. A tibble print rounds to a few significant digits (pillar.sigfig) and cuts strings; pull() or as.data.frame() shows the stored values.
