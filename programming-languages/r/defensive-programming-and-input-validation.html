Defensive Programming and Input Validation

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. Everything on this page is base R (the base, utils and stats packages that ship with R) except one short section on the checkmate package, which was checked at version 2.3.4; the lintr 3.4.0 default linters were used only to check the scripts. A defensive function states what it expects, checks it where the data enters, and stops at once with a message that names the argument and the rule when the expectation is not met, instead of letting a wrong value travel through the program until some unrelated line fails, or worse, until it silently produces a wrong number. This page collects the base R tools for that job: stopifnot() and its named messages, the type and class predicates, match.arg() for a closed set of choices, the safe forms of looping and comparing (vapply(), seq_along(), identical(), all.equal(), isTRUE()), the options that report partial matching, classed custom conditions for errors that callers should be able to tell apart, and the .Deprecated() and .Defunct() pair for retiring an old function.

Every example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines that start with #> are what it printed. The scripts also pass the default lintr linters; a # nolint: comment marks a line where the idiom on show is what a default linter dislikes (or where the linter cannot see a function that source("scenario.R") defines), so the linter does not hide the lesson. The names books, loans, shelf_today, loan_days and the book() constructor come from the running library-shelf scenario described on the section index: a script that needs them starts with source("scenario.R"). Where a message contains quotation marks, they are the typographic quotes R prints in a UTF-8 locale. A call that is evaluated only for its effect, such as a validator that returns its argument invisibly, prints nothing, and the text says so. Almost every error on this page is caught with tryCatch(..., error = conditionMessage) so that the script keeps running and the message can be shown; how tryCatch() and the condition system work is the subject of Conditions and Error Handling, and finding the line that raised an error is covered on Debugging.

Fail fast, and where to check

The idea behind defensive programming is to move a failure as close as possible to its cause. A function that receives "300" where it wants a number can fail in three ways. It can fail late and far away: the first arithmetic on the string raises non-numeric argument to binary operator from inside some helper, and the message names an operator, not the argument that was wrong. It can fail silently: mean("300") returns NA with a warning that is easy to miss, and the NA then flows into a report. Or it can fail at once, at the top of the function, with a message that says which argument was wrong and what was expected. The first script shows the first two failures on the shelf scenario and the third as the repair.

source("scenario.R")

# Without a check the mistake surfaces far from its cause, or not at all.
due_date <- function(loan_date,
                     days = loan_days) { # nolint: object_usage_linter.
  loan_date + days
}
tryCatch(due_date("2026-06-01"), error = conditionMessage)
#> [1] "non-numeric argument to binary operator"

average_pages <- function(pages) {
  mean(pages)
}
tryCatch(average_pages("300"), warning = conditionMessage)
#> [1] "argument is not numeric or logical: returning NA"
suppressWarnings(average_pages("300"))
#> [1] NA
average_pages(books$pages)
#> [1] NA

# With a check at the top the message names the argument and the rule.
average_pages <- function(pages) {
  stopifnot(
    "pages must be a numeric vector" = is.numeric(pages),
    "pages must not be empty" = length(pages) > 0L
  )
  mean(pages, na.rm = TRUE)
}
tryCatch(average_pages("300"), error = conditionMessage)
#> [1] "pages must be a numeric vector"
average_pages(books$pages)
#> [1] 268.2143

Source: R documentation: stopifnot

average_pages("300") first returns NA with the warning argument is not numeric or logical: returning NA, which tryCatch(warning = ) turns into a value so the text can be shown; with the warning suppressed the caller sees only NA. The checked version also repairs a second, quieter problem: books$pages contains two NA values, and the checked function computes the mean of the known page counts on purpose (na.rm = TRUE) instead of returning NA by accident of the data. The point of a check is not only to reject bad input but to make the decisions about edge cases explicit.

Where to put the checks matters as much as how to write them. Three kinds of problem call for three different tools:

  • A programming error is a call that no correct program makes, such as passing a character vector where a function documents a number. stopifnot() and the type predicates are the tool: the message is for the developer, one cheap check at the top of the function is enough, and nobody is expected to recover from it.

  • A data error is a value that is wrong because the outside world is untidy, such as the ISBN with a wrong check digit in books.csv. The caller may well want to skip the row and go on, so the error should carry a class that a handler can select; that is the subject of the section on classed conditions below.

  • A recoverable state is something the program can handle by itself, such as a missing optional argument. It is not an error at all: a default, missing() or the %||% operator handles it.

The checks belong at the boundary of the system: the exported functions of a package, the constructor of a class, the function that reads a file or a request. Inside, the functions can trust what the boundary let through and do one cheap check or none. This is also how the book class of the shelf scenario is layered, which the second script shows.

source("scenario.R")

# Layer 1: the constructor checks types, programmer errors.
tryCatch(
  new_book(title = "Orchard Logic", year = 2019),
  error = conditionMessage
)
#> [1] "is.integer(year) is not TRUE"

# Layer 2: the validator checks values, user errors with plain messages.
tryCatch(book("   "), error = conditionMessage)
#> [1] "a book needs a title"
tryCatch(
  book("Orchard Logic", isbn = "9780306406158"),
  error = conditionMessage
)
#> [1] "invalid ISBN-13: 9780306406158"
tryCatch(book("Orchard Logic", year = 2200), error = conditionMessage)
#> [1] "implausible year: 2200"

# Layer 3: the user-facing helper cleans the input before it checks it.
book("  Orchard Logic ", "Iris Fenwick", "978-0-306-40615-7", 2019)
#> <book> Orchard Logic (Iris Fenwick, 2019)

# Inside the package a function trusts its input and does one cheap check.
page_count <- function(x) {
  stopifnot("x must be a book" = inherits(x, "book"))
  if (is.na(x$pages)) "unknown" else x$pages
}
page_count(book("Orchard Logic", pages = 310))
#> [1] 310
page_count(book("Orchard Logic"))
#> [1] "unknown"
tryCatch(page_count(list(title = "Orchard Logic")), error = conditionMessage)
#> [1] "x must be a book"

Source: R documentation: stopifnot

new_book() is the low-level constructor: it checks only the types, with an unnamed stopifnot(), and its message is the text of the failed expression. The pitfall in the first call is typical: 2019 is a double, and the constructor asks for an integer, so year = 2019L (or as.integer()) is needed; the user-facing book() helper does the conversion itself, which is why book("Orchard Logic", year = 2200) reaches the value check and not the type check. validate_book() checks values and signals plain errors with stop(..., call. = FALSE), which is a reasonable choice for messages that go to the end user, and the helper cleans the input (trimws(), normalise_isbn(), as.integer()) before the checks run. Inside, page_count() trusts a book and verifies only that it was given one.

stopifnot(): assertions with messages

stopifnot() is the most used validation tool in base R. Its help page says it is meant for regression tests and for checking the arguments of functions, where it makes the code easier to read (R documentation: stopifnot). It takes any number of expressions, evaluates them one after the other, and if one of them is not a logical vector of TRUE values it calls stop() with a message naming that expression. The help page gives the equivalent code: stopifnot(A, B) is conceptually if (any(is.na(A)) || !all(A)) stop(...) followed by the same for B. Two consequences follow. An NA is not good enough, because the point of an assertion is that the condition is known to hold. And a vector passes only when all of its elements are TRUE, so the idiom stopifnot(x > 0) checks a whole vector in one expression.

The default messages

The message is built from the failed expression: "<expression> is not TRUE" for a single value, and "<expression> are not all TRUE" when the value has a length other than one, a vector or NULL. When the expression is a call to all.equal(), the message reports the first difference found instead; that arrived in R 3.4.0 and was extended in R 4.3.0 to any call whose name partially matches all.equal, such as a user’s all.equalShow(), so that a customised comparison keeps working. The error is an ordinary simpleError whose call is the function that called stopifnot() (since R 3.6.0 stopifnot() no longer wraps every expression in its own error handling and may use sys.call() to report a short, meaningful call, which makes it considerably cheaper), so the console shows Error in check_count("a") : is.numeric(x) is not TRUE, a message that names the function the user called.

# The default message is the deparsed expression plus "is not TRUE".
check_count <- function(x) {
  stopifnot(is.numeric(x), length(x) == 1L)
  x
}
e <- tryCatch(check_count("a"), error = identity)
print(e)
#> <simpleError in check_count("a"): is.numeric(x) is not TRUE>
class(e)
#> [1] "simpleError" "error"       "condition"
conditionCall(e)
#> check_count("a")
conditionMessage(e)
#> [1] "is.numeric(x) is not TRUE"
tryCatch(check_count(1:2), error = conditionMessage)
#> [1] "length(x) == 1L is not TRUE"
check_count(5)
#> [1] 5

# A vector of logicals: "are not all TRUE" when more than one element.
positive <- function(x) stopifnot(x > 0)
tryCatch(positive(-1), error = conditionMessage)
#> [1] "x > 0 is not TRUE"
tryCatch(positive(c(1, -1, 2, -5)), error = conditionMessage)
#> [1] "x > 0 are not all TRUE"
tryCatch(positive(c(1, NA)), error = conditionMessage)
#> [1] "x > 0 are not all TRUE"
tryCatch(positive(NA), error = conditionMessage)
#> [1] "x > 0 is not TRUE"

# At the top level there is no calling function, so the call is empty.
e <- tryCatch(stopifnot("a" == "b"), error = identity)
print(e)
#> <simpleError: "a" == "b" is not TRUE>
conditionCall(e)
#> NULL

# Expressions are evaluated one by one; the first failure is reported.
e <- tryCatch(stopifnot(1 == 1, 2 < 1, 3 < 2), error = identity)
conditionMessage(e)
#> [1] "2 < 1 is not TRUE"

# A long expression is shortened in the message.
long_check <- function(x) {
  stopifnot(is.character(x) && length(x) == 1L && nzchar(x) && !is.na(x) &&
              x != "forbidden words here")
}
tryCatch(long_check(""), error = conditionMessage)
#> [1] "is.character(x) && length(x) == 1L && nzchar(x) && !is.na(x) &&  .... is not TRUE"

# all.equal() failures report the difference (R 3.4.0).
tryCatch(stopifnot(all.equal(pi, 3.14)), error = conditionMessage)
#> [1] "pi and 3.14 are not equal:\n  Mean relative difference: 0.0005069574"
stopifnot(all.equal(pi, 3.14159265))

Source: R documentation: stopifnot

Four details of the output are worth a pause. The condition has class c("simpleError", "error", "condition") and its call is check_count("a"), the call of the function that contains the assertion, not a call to stopifnot(); at the top level, with no enclosing function, the call is NULL and the console shows only Error:. The expressions are evaluated sequentially (since R 3.5.0), so stopifnot(is.numeric(x), x > 0) can safely put the type check first: the second expression is never evaluated when the first fails. A long expression is cut after a fixed length, and .... marks the cut. And the all.equal() form shows what differed (Mean relative difference: 0.0005069574) instead of just is not TRUE, which makes comparisons of computed numbers much easier to debug.

What the user sees

At the console, an uncaught error prints Error in <call> : <message>, or Error: <message> when there is no call. try() builds the same text as the value of a failed call, which makes it a convenient way to show the user’s view, and it keeps the condition object in the "condition" attribute for the programmer’s view. The named form of the message, introduced below, changes only the message, not the call.

check_count <- function(x) {
  stopifnot(is.numeric(x), length(x) == 1L)
  x
}

# try() keeps the error as a "try-error" and prints the text a user would see.
res <- try(check_count("a"), silent = TRUE)
class(res)
#> [1] "try-error"
cat(res)
#> Error in check_count("a") : is.numeric(x) is not TRUE
conditionMessage(attr(res, "condition"))
#> [1] "is.numeric(x) is not TRUE"
inherits(res, "try-error")
#> [1] TRUE

# The same call with the named form of the message.
check_count_named <- function(x) {
  stopifnot("x must be one number" = is.numeric(x) && length(x) == 1L)
  x
}
res <- try(check_count_named("a"), silent = TRUE)
cat(res)
#> Error in check_count_named("a") : x must be one number

# With no calling function the message starts with "Error:" only.
res <- try(stopifnot("pages must be positive" = -1 > 0), silent = TRUE)
cat(res)
#> Error : pages must be positive

Source: R documentation: try

The last call has no enclosing function, so try() builds the text without a call: Error : followed by the message, with a space before the colon.

Pitfalls of the default behaviour

The rules of the previous section have edge cases that surprise people who think of stopifnot() as "an if that stops". The help page warns about the first: positive numbers are not TRUE, even though they are coerced to TRUE inside if(). So stopifnot(length(x)) fails for length(x) == 1, although if (length(x)) would take the branch. The script collects the others.

err <- function(expr) {
  tryCatch({
    expr
    "no error"
  }, error = conditionMessage)
}

# Positive numbers are not TRUE, even though if (1) works.
err(stopifnot(1))
#> [1] "1 is not TRUE"
err(stopifnot(length(10)))
#> [1] "length(10) is not TRUE"
if (1) "if accepts a number"
#> [1] "if accepts a number"

# NA is not TRUE.

The surprising results, in order. A condition that evaluates to NA fails, with NA is not TRUE. A logical vector of length zero passes, because "all of nothing" is TRUE: check_all(logical()) is silent, which matters for code that checks x > 0 on a vector that may be empty, so a check that must reject empty input needs its own length(x) > 0L expression. NULL and a character string are not logical vectors, so they fail even though "TRUE" looks right. And a comparison such as x > 0 is not a type check at all: when x is the string "a", R converts 0 to "0" and compares strings with the collation order of the locale, which gives TRUE for "a" > 0, and "10" > 9 is FALSE because "10" sorts before "9". That is why positive_number() puts is.numeric(x) before x > 0 in the same stopifnot() call, where the sequential evaluation makes the order safe. Note also that positive_number(numeric()) passes: an empty vector satisfies both expressions, so add a length condition when a single value is required, as in the next section.

Named messages (R 4.0.0)

Before R 4.0.0 the message of stopifnot() was always generated from the expression, and a message written for the user needed an if and a stop(). The R 4.0.0 NEWS lists this as a change to stopifnot(): error messages can be customised through the names of the arguments (R NEWS: Changes in R 4.0.0). The name of an argument replaces the generated text, and an argument without a name keeps the default. Because the names are character strings, they are written with quotes: "x must be a number" = is.numeric(x). The help page demonstrates the form with a symmetric-matrix check whose name replaces the default message.

A good message states the rule from the caller’s point of view, in the present tense, and names the argument: "pages must be positive" says what is required, where all(pages > 0) is not TRUE says only what the code computed. When several named conditions are given, they are evaluated in order and the name of the first one that fails is reported, so they can be arranged from the cheapest and most basic check to the most specific. Inside one condition, && evaluates from left to right and stops at the first FALSE, so is.numeric(x) && length(x) == 1L && x > 0 never reaches the comparison for a string or a vector.

exprs, exprObject and local

Three more arguments of stopifnot() are about how the expressions are supplied. Since R 3.5.0 the expressions can be given as a block, stopifnot(exprs = { ... }), one expression per line without separating commas, which the help page describes as more convenient to evaluate interactively, line by line. R 4.0.0 added exprObject, which takes an object that is already a language object: an expression() vector, a call, a name, or a constant such as TRUE. The argument local says in which environment the block is evaluated and defaults to the calling frame; the help page documents it for exprs only.

Second, a shortcut for the block form needs care. Type and shape checks

A check has two halves: the type of the value (is it a character vector, a function, a data frame?) and its shape (how long, how many missing values, within what range?). Most mistakes in real programs come from forgetting the second half, so the examples below combine them.

The is.* predicates

The predicates ask about the storage type or the interpretation of a value, and a few of them are subtler than their names. is.numeric() is the one most often misunderstood: it is not the same as is.double(). It is TRUE for integer and double vectors and FALSE for factors, which are stored as integers, and for objects with a class that opts out: the help page lists methods for "Date", "POSIXt", "difftime" and "complex" that return FALSE (R documentation: numeric). The intent is that is.numeric(x) means "arithmetic on x makes sense and the values are numbers", which is what a function that computes a mean wants to know. is.integer() and is.double() ask about the storage type instead, so is.integer(5) is FALSE. is.character() is FALSE for factors and for a bare NA, which is logical, while NA_character_ is character. is.function() accepts closures and primitives but not the string with a function’s name. is.null() is TRUE only for NULL itself, not for an empty list or an empty vector.

Classes: inherits() and isa()

For a value with an S3 class, the right question is not the storage type but the class vector. inherits(x, what) is TRUE when any of the classes in what appears in class(x); which = TRUE returns the position of each match instead (zero for no match), which tells how far down the class vector each match is (R documentation: class). isa(x, what) is stricter: it is TRUE only when all the classes in what are in class(x), and for an S4 object it uses is(). Both look at class(x), which is defined for every object: inherits(1L, "integer") is TRUE, inherits(1L, "numeric") is FALSE (the class of an integer vector is "integer"; "numeric" is the class of a double), and inherits(matrix(1:4, 2), "matrix") is TRUE.

The one comparison to avoid is class(x) == "name". Since R 4.0.0 a matrix has the class vector c("matrix", "array"), so class(m) == "matrix" has length two, if (class(m) == "matrix") has been an error since R 4.2.0, and older code that tested class(x) == "matrix" broke when matrices gained their second class. inherits() is robust to a longer class vector and to subclasses, which the book scenario depends on: a validator written with inherits(x, "book") still accepts an object of a class derived from book.

One value, not a vector

Most R values are vectors, and a vector is the wrong shape for if(), && and ||, which need exactly one logical value. The old behaviour was lenient: if (c(TRUE, FALSE)) used the first element and warned, and && silently used the first element of each operand. The language has become stricter in two steps. R 4.2.0 made if() and while() with a condition of length greater than one an error, and && and || with such an operand a warning; R 4.3.0 made the && and || case an error too, with a message of the form 'length = 2' in coercion to 'logical(1)' (R NEWS: Changes in R 4.3.0). A validator that begins with the type and the length therefore never reaches a vector in a position that needs a scalar.

# The usual "one valid string" test: type, length and missingness together.
is_scalar_string <- function(x) {
  is.character(x) && length(x) == 1L && !is.na(x) && nzchar(x)

In is_count(), the order of the operands matters: && stops at the first FALSE, so x == round(x) is evaluated only for a number of length one that is not NA. The error messages of if() are worth knowing by heart because they point at a missing check: missing value where TRUE/FALSE needed means the condition was NA, argument is of length zero that it was empty or NULL, the condition has length > 1 that a vector reached if(), and argument is not interpretable as logical that the condition was text that R cannot read as a logical value. any() and all() are the bridge from a vector to the single value that if() needs, with the two empty-input conventions that every R programmer should remember: all(logical()) is TRUE and any(logical()) is FALSE.

Closed sets of choices: match.arg()

An argument that must be one of a few strings is the classic case for match.arg(). The function declares the set as the default value, status = c("all", "out", "overdue", "returned"), and match.arg(status) replaces the vector by the validated choice: the first element when the caller passed nothing, the full name when the caller passed an abbreviation, and an error for anything else. In the one-argument form the choices are read from the default of the formal argument of the calling function, so the set is written once, in the signature, where args() and the help page show it. Matching uses pmatch(), so an abbreviation is accepted when it is unambiguous, and the empty string never matches (R documentation: match.arg). The mechanics and the interaction with the dots are described on Functions; this page looks at it as a validator.

The error message lists the allowed values, which is what the user needs, but three of its properties are worth knowing. Its call is match.arg(status), not the call of loan_report(), so the console shows Error in match.arg(status) : 'arg' should be one of ...; the user sees the name of the argument but not the function they called, and the traceback described on Debugging is the way to find the caller when many functions share an argument name. The wording depends on the input: a number gives 'arg' must be NULL or a character vector, a vector of length two or a zero-length vector gives 'arg' must be of length 1, and anything else that does not match gives the should be one of message. And the help page warns that the wording of these messages is liable to change, and that it did change in R 4.2.0, so a package must not test for them. A test should check that an error is signalled, or catch it and check only the part that matters. When the call or the wording is important, validate by hand with %in% and signal a classed condition, as shown below.

NULL is accepted and means "take the first choice", which matters for a caller that builds the argument programmatically and passes NULL for "use the default". The R 4.2.0 NEWS records a better error message for match.arg("", ...).

Several values at once

With several.ok = TRUE the argument may have more than one element, and every element that matches is returned; the elements that do not match are dropped without a word, so a typo goes unnoticed and the caller gets fewer columns than they asked for. R 4.6.0 added a third value for several.ok: any string starting with "all" keeps the several-values behaviour but requires every element to match. The R 4.6.0 NEWS entry says that match.arg() gets this option, fulfilling a wish recorded as PR#16659 (R NEWS: Changes in R 4.6.0). It replaces the check that people wrote by hand after several.ok = TRUE, shown in the second function of the script.

# several.ok = "all" (R 4.6.0) accepts several values and checks every one.
shelf_columns <- c("title", "author", "isbn", "year", "genre", "pages")
pick_columns <- function(cols = shelf_columns) {
  match.arg(cols, shelf_columns, several.ok = "all")
}

Missing arguments, NULL defaults and %||%

An argument without a default that the caller did not supply is an error only when the function first evaluates it, which can be far from the top of the function, so the message argument "x" is missing, with no default appears at the use, not at the call. The error names the call (here double_it()) but not the position in the body. The error has the class missingArgError: the R 4.5.0 NEWS mentions that class, with a subclass "getMissingError" for get(), and uses f <- function(x) exp(x); try(f()) as the example of the situation. A handler can therefore select on the class instead of on the message (R NEWS: Changes in R 4.5.0). The class vector has further subclasses whose names depend on how the error was signalled, so test for "missingArgError" with inherits() and do not print the whole vector.

missing(x) is TRUE when the caller did not supply x, and is the way to turn the late, obscure error into an early one with a clear message. A stricter alternative to the default NULL is not to give a default at all and to check with missing() at the top, as borrow() does with named conditions. nargs() counts the arguments that were supplied, including empty ones, which is useful for functions that accept one of several argument combinations. The mechanics of missing() (for example that it follows an argument forwarded through another function, and that it becomes FALSE once the argument is assigned to) are described on Functions, and the deferred evaluation that explains the late error is the subject of Lazy Evaluation and Promises.

Looping and mapping safely

Loops and the apply family are where defensive habits pay off, because the input that breaks them is usually the empty one, and the empty case rarely appears in the data used while writing the code.

vapply() instead of sapply()

sapply() applies a function and then simplifies the result by guessing: a vector if every result has length one, a matrix if they all have the same longer length, otherwise a list. That guess is made from the data, so the same code returns different types for different inputs. On empty input it has nothing to guess from and returns an empty list(), so code that expects a vector fails or, worse, keeps going with a list. vapply() takes the expected shape as an argument, FUN.VALUE, and checks every result against it: the result always has the declared type, empty input gives an empty vector of that type, and a result of the wrong length or type is an error that names the element. The help page states the rule: the values of FUN must have the same length and type as FUN.VALUE, where "type" may be promoted along logical, integer, double and complex but not demoted (R documentation: lapply).

Three details of the output. The result of sapply(character(), nchar) is named list(), because with USE.NAMES = TRUE the names are taken from the character input, which is empty, while vapply(character(), nchar, integer(1)) is named integer(0): pass USE.NAMES = FALSE when the names are not wanted, as in the second call on books$isbn, where they are the ISBNs themselves. The two error messages say which element broke the contract: values must be length 1, but FUN(X[[1]]) result is length 2 for a shape error, and values must be type 'character', but FUN(X[[1]]) result is type 'integer' for a type error; promotion is allowed, so a logical result is accepted for integer(1) and an integer for numeric(1), but a double is not accepted for integer(1). And a FUN.VALUE with a length greater than one and names, like c(first = 0, last = 0), gives a matrix whose rows carry those names, which turns vapply() into a typed way to compute several summaries per group. The last two lines show the validation use: one call tests each element of a list against a rule and returns a plain logical vector that all() can reduce, with no chance of a list result.

The older tutorials use sapply() everywhere, which is fine at the console where the output is inspected; in a function that other code depends on, the guess is a latent bug. The other members of the family and their simplification rules are covered on The apply Family and Functionals.

seq_along() and seq_len() instead of 1:length(x)

1:length(x) is the other idiom that works until the input is empty. The colon operator counts down when the second number is smaller, so 1:0 is c(1, 0), and a loop over 1:length(x) for an empty x runs twice, with i equal to 1 and then 0, and x[1] is NA while x[0] is empty. The fix is seq_along(x), which is integer(0) for an empty vector, so the loop body never runs, or seq_len(n) when the count comes from a number such as nrow(df). The help page recommends both over seq() with one argument, because seq(x) for a numeric x of length one is 1:x, even for seq(0), which is c(1, 0) (R documentation: seq).

Comparing values: ==, identical(), all.equal() and isTRUE()

The comparison operators answer a different question from the one if() asks. == compares element by element and returns a vector of the same length as its operands, with NA wherever an operand is NA; if() needs one TRUE or FALSE. The help page of identical() makes the point directly: identical() is the way to test exact equality in if and while conditions and in logical expressions with && and ||, because it always returns a single logical value, where == returns an object like its arguments (R documentation: identical). Three functions cover the three questions a program asks:

  • Are these exactly the same object? identical(x, y). It compares type, values and attributes: identical(1L, 1) is FALSE because one is an integer and the other a double, identical(c(a = 1), 1) is FALSE because of the names, identical(NA, NA_integer_) is FALSE, and identical(NaN, NaN) is TRUE although NaN == NaN is NA.

  • Are these numbers equal within rounding error? all.equal(target, current), whose default tolerance is about 1.5e-8, the square root of the machine epsilon. It returns TRUE or a character vector describing the differences, so it must not be used directly in if().

  • Is this one value TRUE? isTRUE(x) and isFALSE(x).

The reason to prefer all.equal() for computed numbers is R FAQ 7.31, "Why doesn’t R think these numbers are equal?": only integers and fractions whose denominator is a power of two are represented exactly, every other number is rounded to about 53 binary digits, so two floating point numbers are not reliably equal unless they were computed by the same algorithm, and not always even then. The FAQ uses sqrt(2) squared as its example and recommends all.equal(), which compares with a tolerance of .Machine$double.eps ^ 0.5 (R FAQ 7.31: Why doesn’t R think these numbers are equal?).

The output of all.equal() is the part that people forget. all.equal(1, 1.1) is not FALSE but the string Mean relative difference: 0.1, and a string in if() gives argument is not interpretable as logical, so the idiom is isTRUE(all.equal(x, y)). isTRUE(x) is documented as the same as { is.logical(x) && length(x) == 1 && !is.na(x) && x }, so it is TRUE for exactly one logical TRUE and for nothing else: not for 1, not for "TRUE", not for NA, and not for a vector of two TRUE values. The help page adds the reason it exists: if (isTRUE(cond)) may be preferable to if (cond) because of NA (R documentation: Logic). R 3.5.0 made isTRUE() tolerant of attributes, so a named TRUE such as c(a = TRUE) now passes (the previous definition identical(x, TRUE) rejected it), and added isFALSE() defined in the same way. isFALSE(NA) is FALSE, so the pair gives a three-way test of a condition that may be NA: isTRUE(cond), isFALSE(cond), and otherwise unknown. %in% is another comparison that never returns NA and so is safe in a condition: NA %in% "Fiction" is FALSE, where NA == "Fiction" is NA.

Partial matching and how to catch it

R is generous about names, and the generosity hides typos. Three places allow a partial name. The $ operator on a list or a data frame returns the single element whose name starts with the given text. A function call matches an argument name partially when the formal comes before the dots; the manual states the three passes of the matching, exact, then partial, then positional, and that formals after ... can be matched only exactly (R-lang: Argument matching). And attr(x, "name") matches an attribute name partially unless exact = TRUE. The matching is sensible at the console, where it saves keystrokes, and a liability in a script, where books$yea works today and silently returns the wrong column the day somebody adds a year_end column, because after that the prefix is ambiguous and the result becomes NULL (the script shows two$ye returning NULL).

Fail fast with classed custom conditions

stopifnot() and stop("message") produce errors that differ only in their text, and text is a poor interface. A caller who wants to skip a row with a bad ISBN but let every other error through would have to search the message for "invalid ISBN", which breaks when someone fixes the wording. The scenario’s own validate_book() has this limitation on purpose: its errors are plain simpleError conditions with call. = FALSE, so conditionCall() is NULL and only conditionMessage() tells them apart.

R lets a condition be an object with a class and with data. errorCondition(message, ..., class, call) and its sibling warningCondition() were added in R 3.6.0 to build such objects: the first argument is the message, any further named arguments become fields of the condition, class is prepended to the standard class vector, and call records the call to show. stop(cond) signals the object, and tryCatch() selects a handler by class (R documentation: conditions). The class hierarchy gives the same specific-to-general selection that exceptions give in other languages: the most specific class first, then a package-wide parent class such as shelf_error, then the built-in error. The full machinery is on Conditions and Error Handling; the script below is the validation side of it.

source("scenario.R")

# The scenario's validate_book() signals a plain error: only the text tells
# the callers apart.
e <- tryCatch(book("Orchard Logic", isbn = "9780306406158"), error = identity)
class(e)
#> [1] "simpleError" "error"       "condition"
conditionMessage(e)
#> [1] "invalid ISBN-13: 9780306406158"
conditionCall(e)
#> NULL

# A classed condition carries a class to catch and the offending data.
shelf_abort <- function(message, class, ..., call = sys.call(-1L)) {
  stop(errorCondition(message, ..., class = c(class, "shelf_error"),
                      call = call))
}

check_book <- function(isbn) {
  stopifnot("isbn must be a single string" = is.character(isbn) &&
              length(isbn) == 1L)
  if (is.na(isbn) || !is_valid_isbn13(isbn)) { # nolint: object_usage_linter.
    shelf_abort(paste0("invalid ISBN-13: ", isbn),
                class = "shelf_invalid_isbn", isbn = isbn)
  }
  invisible(isbn)
}

e <- tryCatch(check_book("9780306406158"), error = identity)
class(e)
#> [1] "shelf_invalid_isbn" "shelf_error"        "error"
#> [4] "condition"
conditionMessage(e)
#> [1] "invalid ISBN-13: 9780306406158"
conditionCall(e)
#> check_book("9780306406158")
e$isbn
#> [1] "9780306406158"
print(e)
#> <shelf_invalid_isbn in check_book("9780306406158"): invalid ISBN-13: 9780306406158>

# The caller chooses by class, from the most specific to the most general.
import_one <- function(isbn) {
  tryCatch(
    {
      check_book(isbn)
      "imported"
    },
    shelf_invalid_isbn = \(e) paste("skipped", e$isbn),
    shelf_error = \(e) "other shelf problem"
  )
}
import_one(books$isbn[1])
#> [1] "imported"
import_one(books$isbn[13])
#> [1] "skipped 978-0-01-100112-9"
import_one(books$isbn[9])
#> [1] "skipped "

# A programming error is not a shelf error and keeps its own type.
tryCatch(import_one(42), error = conditionMessage)
#> [1] "isbn must be a single string"

# Collect the failures of a whole column instead of stopping at the first.
results <- vapply(books$isbn, import_one, character(1), USE.NAMES = FALSE)
sum(startsWith(results, "skipped"))
#> [1] 2
books$title[startsWith(results, "skipped")]
#> [1] "Rivers of Glass" "Orchard Logic"

#> [1] TRUE

#> [1] "shelf_invalid_isbn" "shelf_error"        "error"
#> [4] "condition"

Four design points in the script. The helper shelf_abort() is the single place that builds the condition, so every error of the package has the parent class shelf_error and the same shape. Its default call = sys.call(-1L) records the call of the function that called the helper, check_book(...), and not the call of the helper itself, which is what stop() does for a plain message. The data that triggered the error travels as a field, e$isbn, so the handler reports the offending value without parsing a message. And the two layers stay separate: the type check at the top of check_book() is a stopifnot() that raises a plain error for a programming mistake, which import_one(42) shows passing through the shelf handlers untouched, and only the data error is classed. The last block applies the pattern to a whole column: vapply() over books$isbn, each element wrapped by a handler that returns a status string, finds the two bad rows (the empty ISBN and the one with a wrong check digit) in one pass without stopping at the first, the situation that a plain stop() cannot express without text matching.

A custom class is part of a package’s interface: document it, keep the names stable, and prefix them with the package name to avoid clashes (shelf_invalid_isbn, not invalid_isbn). R 4.4.0 made tools::xgettext() stop extracting the class names in errorCondition() and warningCondition() calls as translatable strings, since they are identifiers and not messages. R-devel NEWS (4.7.0, under development, not available in R 4.6.1) lists two new built-in classes for failed lookups, objectNotFoundError for an object that is not found and functionNotFoundError for a function that is not found, and says that the classes used internally for signalling some errors are now documented in ?conditions; that would let a handler select a missing function without parsing the message, and it is mentioned here only as upcoming (R-devel NEWS).

Evolving an API: .Deprecated() and .Defunct()

Validation also protects the callers of an old function. A function that is going to be removed should say so for a release or two, and then fail with an explanation, and base R has a pair of helpers for the two steps. .Deprecated(new, package, msg, old) signals a warning whose default text names the old function and the one to use instead, and tells the user to see help("Deprecated"); .Defunct() signals an error for a function that has been retired (R documentation: Deprecated). Since R 3.6.0 the warning has class deprecatedWarning and the error class defunctError, so a test or a caller can select them without matching text, and the condition keeps the fields old, new and package.

# .Deprecated() signals a warning of class "deprecatedWarning" (R 3.6.0).
new_fn <- function(x) x + 1
old_fn <- function(x) {
  .Deprecated("new_fn")
  new_fn(x)
}
w <- tryCatch(old_fn(1), warning = identity)
class(w)
#> [1] "deprecatedWarning" "warning"           "condition"
conditionMessage(w)
#> [1] "'old_fn' is deprecated.\nUse 'new_fn' instead.\nSee help(\"Deprecated\")"
conditionCall(w)
#> old_fn(1)
suppressWarnings(old_fn(1))
#> [1] 2

# A custom message, and the fields the condition keeps.
shelf_old <- function() {
  .Deprecated(
    new = "shelf_new", package = "shelf", old = "shelf_old",
    msg = "shelf_old() will be removed in shelf 2.0"
  )
}
w <- tryCatch(shelf_old(), warning = identity)
conditionMessage(w)
#> [1] "shelf_old() will be removed in shelf 2.0"
c(w$old, w$new, w$package)
#> [1] "shelf_old" "shelf_new" "shelf"

# .Defunct() is the next step: an error of class "defunctError".
shelf_gone <- function() .Defunct("shelf_new", package = "shelf")
e <- tryCatch(shelf_gone(), error = identity)
class(e)
#> [1] "defunctError" "error"        "condition"
conditionMessage(e)
#> [1] "'shelf_gone' is defunct.\nUse 'shelf_new' instead.\nSee help(\"Defunct\") and help(\"shelf-defunct\")."

# Callers can handle one without touching the others.
res <- withCallingHandlers(
  old_fn(1),
  deprecatedWarning = \(w) invokeRestart("muffleWarning")
)
res
#> [1] 2

Source: R documentation: Deprecated

Base R follows the same two steps for its own functions. is.R(), which asked whether code ran in R rather than in S-PLUS, was deprecated in R 4.4.0 and is defunct since R 4.5.0, whose NEWS also says that the environment variable _R_DEPRECATED_IS_R_ no longer has any effect. A guard such as exists("is.R") && is.R() in older code now stops with 'is.R' is defunct., and the repair is to delete the test (R documentation: base-defunct; What’s New and Migrating Older Code).

The wording of the default message is built from the name of the function that called .Deprecated() unless old is given, which is why shelf_old() passes old = "shelf_old" and package = "shelf" explicitly when the function lives in a package. The msg argument replaces the whole text for a case like a renamed argument. A common policy is to deprecate in one release, keep the function working while it warns, make it defunct in a later one, and remove it after that, with an entry in the package NEWS at each step; the final block shows how a caller that knows about the deprecation and wants the old behaviour for now can mute exactly that warning class with a calling handler and the muffleWarning restart, leaving other warnings visible. The mechanism is described on Conditions and Error Handling.

The checkmate package

Writing the checks by hand for every argument gets repetitive, and several packages provide a vocabulary for it. This section covers one of them, checkmate (checkmate package documentation, version 2.3.4 here), a CRAN package of argument checks, a substantial part of which is written in C so that the checks can sit in frequently called functions. It is optional: everything above is base R, and a package that wants to stay dependency-free can ship a few of its own is_* helpers. For each kind of check checkmate provides three functions: assert_*() stops with an informative message that names the checked expression and returns its argument invisibly, check_*() returns TRUE or the text of the problem, and test_*() returns TRUE or FALSE. The camel-case spellings (assertString(), checkString()) are equivalent. qassert() states a whole rule in a short string, "I1" for one integer, "N1" for one number, with optional bounds. Functions such as assert_choice(), assert_data_frame() and assert_class() cover the cases that match.arg(), is.data.frame() and inherits() handle in base R, and assert() combines several checks with "or" semantics (checkmate package documentation: assert).

library(checkmate)
source("scenario.R")

add_pages <- function(pages, title) {
  assert_integerish(pages, lower = 1, len = 1, any.missing = FALSE)
  assert_string(title, min.chars = 1)
  invisible(TRUE)

The messages follow a fixed pattern, Assertion on '<expression>' failed: <what is wrong>., and the call recorded in the condition is the function that contains the assertion, as with stopifnot(). assert_integerish() accepts a double that holds a whole number, which is what a user typing 300 at the console supplies, and rejects 1.5 with a message that says the element is not close to an integer; the arguments lower, len and any.missing express the range, the length and the NA rule that the hand-written is_count() above checks with four operands. The second line, assert_string(title, min.chars = 1), states in one call that the title is a single string that is not missing and not empty. The classes are plain simpleError conditions, so tryCatch() can select them only by message, not by class, which is one reason to use the classed conditions of the previous section for data errors and to keep checkmate for programming errors. Further documentation: checkmate package documentation: qassert, checkmate package documentation: checkString and checkmate package documentation: checkChoice.
