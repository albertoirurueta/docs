Base Graphics and Devices

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. Everything on this page is base R: the graphics package, which draws, the grDevices package, which owns the devices and the colours, and a handful of functions from stats and utils; smoothScatter() and densCols() use the recommended package KernSmooth, which ships with R. One example compares the SVG written by base R with the SVG written by the add-on package svglite 2.2.2, and the lintr 3.4.0 default linters were used only to check the scripts. Base graphics is the oldest plotting system of R and the one that the rest of R assumes: plot() is the generic that models, densities and time series hook into, hist() and boxplot() are how most people first look at a variable, and the devices that write PNG, PDF and SVG files are shared by every graphics system. The model is simple, which is its strength and its limit. Each call draws on the current page of the current device at once, like a pen on paper, so there is nothing to edit afterwards, only more to add; a high-level function starts a page, low-level functions add to it, and a list of graphical parameters set with par() controls the look of both. This page explains that model, the functions of both kinds, the parameters, the colour system and the palettes, and the devices that turn the drawing into pixels or vector files.

Every example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines that start with #> are what it printed. A picture cannot be printed as text, so the scripts draw to pdf(NULL) (a device that writes no file) or to a file in tempfile() that is checked and removed (the one script that shows Rplots.pdf writes it in the working directory and removes it), and the #> lines show what a plot call returns and what the graphical parameters become: par("usr"), the bar midpoints, the histogram object, the rectangle of a legend, the pixel size of a PNG. None of those plots is reproduced here; the one exception is the figure of the shelf loans in the last section, which R itself wrote and which is shown with the script that produced it. The scripts also pass the default lintr linters; a # nolint: comment would mark a line where the idiom on show is what a default linter dislikes. A script that needs the running library-shelf scenario, which the section index describes, starts with source("scenario.R"), which defines books, loans, shelf_today, loan_days and the book class. The genre column of books holds nine spellings of six genres, so a script that plots by genre first runs books$genre <- tolower(trimws(books$genre)); cleaning text is the subject of Strings and Regular Expressions and loans has the dates of Dates and Times. Where a message contains quotation marks, they are the typographic quotes R prints in a UTF-8 locale.

This page is the graphics half of the statistics and graphics group. The data frames that the charts draw come from Data Frames, the formula pages ~ genre that boxplot() and plot() accept is explained in Formulas, the distributions that curve() draws are in Distributions and Random Numbers, and the summaries behind a box plot are in Descriptive Statistics and Tests. The diagnostic plots of a fitted model are in Statistical Models. The two other graphics systems, which sit on the same devices, have their own pages: Grid Graphics and Lattice and ggplot2 and the Grammar of Graphics. The base graphics model

Devices, the engine and two graphics systems

The manual An Introduction to R describes the facilities in three groups: high-level plotting functions that create a new plot, low-level plotting functions that add to an existing plot, and interactive functions that read from or add to a plot with a pointing device, together with a list of graphical parameters that customise all of them (An Introduction to R: Graphical procedures). It describes only base graphics and says in its first paragraphs that a separate subsystem in the package grid coexists with base graphics, and that the recommended package lattice builds on it. R Internals explains the reason: the graphics internals were redesigned so that several graphics systems can be installed on top of one graphics engine, and two exist, base graphics (based on the graphics of the S language, with its R code in the package graphics) and grid (R Internals: Graphics). The layers are these.

Layer What it does Where it lives

Graphics systems

The functions a user calls: plot(), hist(), par() for base graphics, viewports and grobs for grid. Lattice and ggplot2 are built on grid.

packages graphics and grid

Graphics engine

Clips lines, rectangles and polygons, draws the plotting symbols selected by pch, centres and adjusts text, typesets mathematical expressions (plotmath), maps colour names to colours, and keeps display lists and snapshots.

R’s C code, with recordPlot() and the colour functions in grDevices

Device

Owns the plotting surface, a window or a file, and implements a few primitives: circle, rectangle, line, polyline, polygon, path, text, an optional raster image and a clipping rectangle. It also answers questions such as the width of a string and the size of the surface, and starts a new page.

pdf(), png(), svg(), x11(), quartz(), windows() and the devices of add-on packages

Source: R Internals: Graphics

The practical consequence is that everything a device can do is available to every system, and that a chart is not tied to a file format: the same call draws on a screen window, into a PNG file or into an SVG file, and only the device changes. A device works in its own units (pixels, big points of 1/72 inch, twips) and the engine hides that from the plotting code. A line of R Internals matters for the rest of this page: some devices keep a display list, a record of the operations that produced the current page, and others do not. Screen devices keep one so they can repaint and resize, file devices normally do not, and dev.copy() and recordPlot() depend on it (see Graphics devices).

Two packages, and where plot() lives

The base graphics system is spread over two packages that are always present. The package graphics holds the plotting functions and par(); the package grDevices holds the devices, the colour functions (palette(), colors(), rgb(), hcl.colors()), plotmath, recordPlot() and some helpers that the plotting functions call (boxplot.stats(), nclass.Sturges(), xy.coords(), n2mfrow(), axisTicks()). The split has a historical reason: R Internals says grDevices was created to hold the basic devices and later received functionality that grid also needs, mainly colour handling and the recording and replaying of plots. The generic function plot() is the one exception. R 4.0.0 moved it into base, because it is reasonable to have methods that do not use the graphics package, and the graphics namespace re-exports it so that code importing it from there keeps working (R NEWS: Changes in R 4.0.0). The script asks R where each function lives.

A device is a separate object with its own graphical parameters, a point that returns throughout the page.

The pen-on-paper model

Base graphics draws immediately. A call such as points() or text() changes the pixels or the vector page of the current device as it runs and keeps no object that could be edited later, which is the model R inherited from the S language. This differs from lattice and ggplot2, where a plot is an object that can be changed and then printed, and it has three consequences that explain most of the idioms in the rest of the page. First, order matters: the background (a grid, a shaded band) has to be drawn before the marks that sit on it, which is why panel.first exists. Second, the coordinate system has to be fixed before the first mark is drawn: a point outside xlim and ylim is drawn outside the plot region and clipped, and no later call enlarges the page. Third, there is no undo. To change a plot, run the code again from the high-level call.

A high-level function does these things for you in a fixed order. The script builds the same picture from the pieces: plot.new() starts a new page and plot.window() sets the user coordinates, then marks, axes, a box and titles are added. The long vector of names that the script prints is the body of plot.default() itself, read with deparse(): it calls plot.new() and the window, evaluates panel.first, draws the points with plot.xy(), evaluates panel.last, then draws the two axes, the frame and the titles.

pdf(NULL, width = 6, height = 4)
x <- c(1, 2, 3, 4)
y <- c(2.1, 3.9, 6.2, 7.8)

# plot.default() is these calls in this order: a new page, the coordinate
# system, the marks, the axes, the frame and the annotation.
plot.new()
plot.window(xlim = range(x), ylim = range(y))
par("usr")
#> [1] 0.880 4.120 1.872 8.028
points(x, y)
axis(1)
axis(2)
box()
title(main = "By hand", xlab = "x", ylab = "y")

# Marks are added, never edited: a second call draws on top of the first.
lines(x, y)
abline(h = mean(y), lty = 2)

# What plot.default() runs, in order (from its own body): the window first,
# then panel.first, the marks, panel.last, the axes, the frame, the titles.
steps <- grep("<-", deparse(body(graphics::plot.default)),
              invert = TRUE, value = TRUE)
pat <- paste0("^ {4,8}(plot.new|localWindow|panel.first|plot.xy|panel.last|",
              "localAxis|localBox|localTitle)")
sub("\\(.*", "", trimws(grep(pat, steps, value = TRUE)))
#> [1] "plot.new"    "localWindow" "panel.first" "plot.xy"     "panel.last"
#> [6] "localAxis"   "localAxis"   "localBox"    "localTitle"

# The same picture from one high-level call. It starts a new page, so
# everything drawn above is gone from the new page.
plot(x, y, main = "By plot()")
par("usr")
#> [1] 0.880 4.120 1.872 8.028
dev.off()
#> null device
#>           1

The first par("usr") is c(0.88, 4.12, 1.872, 8.028): the ranges of x (1 to 4) and y (2.1 to 7.8) extended by 4 per cent on each side, the default of the parameters xaxs and yaxs ("r", "regular"). Drawing the same picture with one plot() call gives the same usr. The calls after plot.window() add to the page: the lines() and abline() calls draw on top of what was there and change nothing that was drawn. Calling plot() again starts a new page, which is why a script that wants two charts side by side needs par(mfrow = ...) or layout() (see Several plots on one page).

Regions, margins and coordinates

A single plot is a figure: a plot region surrounded by margins that hold the axes, tick labels and titles. With several figures on a page an outer margin may surround them all (An Introduction to R: Figure margins). Each nesting level has a parameter in lines of text and, usually, a twin in inches or in fractions of the page, and setting one changes the other.

Device

din (read-only)

The whole page, in inches.

Outer margins

oma in lines, omi in inches, omd as a fraction

The border around all figures of a multi-figure page, zero by default.

Figure

The area of one plot including its inner margins.

mar in lines, mai in inches, mex the size of a line

The border inside the figure for axes, labels and titles. The default mar is c(5.1, 4.1, 4.1, 2.1): bottom, left, top, right.

The rectangle where data are drawn, bounded by the axes.

High-level plotting functions

Histograms: hist()

hist() computes the counts of a numeric vector in cells and draws them as bars; with plot = FALSE it only computes. The result is an object of class histogram with six components, and plot() on it draws the bars, so the computation and the drawing can be separated (hist() calls plot.histogram() with the result). The number of cells comes from breaks: a vector of break points, a single number (a suggestion, because pretty() chooses round numbers), a name ("Sturges", the default, "Scott" or "FD") or a function; nclass.Sturges() is the rule of the default. Cells are right-closed, (a, b], by default, and include.lowest = TRUE closes the first one on the left; right = FALSE makes them left-closed, [a, b). The scale is counts for freq = TRUE (the default when the breaks are equally spaced) and a density for freq = FALSE or probability = TRUE, where the area of the bars is 1.

The script uses the number of days between loan and return of the returned loans (a loan returned before it was lent is a data error in the scenario and is dropped). It prints the six components, shows how the break rules differ, and shows the closed side matters when values fall exactly on a break: four loans lasted exactly 21 days, so with right = TRUE they count in the cell (14, 21] and with right = FALSE in [21, 28).

Bar plots: barplot()

barplot() draws bars whose heights are the values of its first argument and, unlike hist(), treats them as categories: it does not count anything, so the input is a table or a vector of counts. A vector gives one bar per element, named by the vector’s names; a matrix gives stacked bars (one bar per column) or, with beside = TRUE, groups of bars side by side. The arguments to know are names.arg, horiz, space (a fraction of the bar width, a pair for grouped bars), legend.text (and args.legend to position it), col, density and angle for shaded bars, ylim, and add. The value is the vector (or, for beside = TRUE, the matrix) of bar midpoints, which is what text(), axis() and segments() need to annotate the bars. For grouped bars colMeans(mp) is the centre of each group.

R 4.6.0 adds orderH for stacked bars: "incr" or "decr" orders the segments of every stack by size, each stack on its own, in increasing or decreasing order instead of the row order (the default "none"). The argument applies when beside is false, that is, to stacked bars (R NEWS: Changes in R 4.6.0). There is also a formula method, barplot(n ~ genre, data = df), that takes the heights from a data frame; it was added in R 3.6.0 (R NEWS: Changes in R 3.6.0).

Box plots: boxplot() and boxplot.stats()

boxplot() computes five-number-style summaries per group and draws them with bxp(). It accepts a formula and a data frame (boxplot(pages ~ genre, data = books)), a list of vectors, a matrix (one box per column) or a single vector. The box spans the lower and upper hinges (the median of each half of the data, computed by fivenum()), the thick line is the median, the whiskers reach the most extreme data within range times the hinge spread (the argument range, 1.5 by default, passed to boxplot.stats() as coef), and the points beyond are outliers. range = 0 sends the whiskers to the data extremes. The other arguments are horizontal, notch (a confidence interval for the median, drawn as a notch), varwidth (box width proportional to the square root of the group size), outline (draw the outliers or not), names, at for positions, add and boxwex.

The value is a list with stats (a 5-row matrix, one column per box), n, conf (the notch limits), out and group (the outlying values and the box each belongs to) and names. boxplot.stats() (R documentation: boxplot.stats) computes one such summary for one vector, so it can be used without drawing. Four groups of the shelf have only two books each, so their columns of stats show a box that collapses: with n = 2 the hinges are the two data values, the whiskers end at them and no outlier can exist. The notched version warns when a notch extends past its hinges, which it does here for the small groups; the warning text is some notches went outside hinges ('box'): maybe set notch=FALSE.

Curves and functions: curve()

curve() draws the curve of an expression in x or of a function over an interval and returns the points it computed as a list with the components x and y, so curve() doubles as a sampler: curve(dnorm(x, 21, 8), 0, 42, n = 5) returns five points. The arguments are from, to, n (101 points by default), add, type ("l" by default) and xname (the name of the variable when it is not x). Without from and to (or xlim) the interval is 0 to 1 for a new plot and, for add = TRUE, the x-limits used for the previous plot; the points are equally spaced on the scale of the axis, so on a logarithmic axis they are equally spaced in log scale. plot() on a function calls the same code with the same arguments, as plot.function(). The scripts in the page and in Distributions and Random Numbers use it for densities.

Low-level additions

A low-level function adds to the current plot: it needs a page that a high-level function (or plot.new() and plot.window()) has already set up, and it fails with plot.new has not been called yet on a device where nothing was drawn. All of them return NULL or a value that describes what they drew, and none starts a new page. The coordinates are the user coordinates of the plot region, par("usr").

Points, lines and shapes

panel.first and panel.last

Because the page is drawn with a pen, drawing a grid or a shaded band behind the data needs the call to be made after the coordinates exist and before the marks. The argument panel.first of plot.default() is evaluated after the plot window is set up and before any plotting takes place, panel.last after the plotting but before the axes and the title are added. Both are expressions evaluated lazily by the method, which is why they work as arguments: plot(x, y, panel.first = grid()). The help warns that this works by lazy evaluation and that passing the argument on from another function may well not work, because it may be evaluated too early.

R 4.6.0 extended the idea (R NEWS: Changes in R 4.6.0). Its NEWS lists a new argument panel.first for hist() (through plot.histogram()), barplot() and bxp(), and with it boxplot(), and says that all of them except hist() also gain panel.last. So hist() has panel.first only. Two things differ between the functions, and the script shows both. plot.default(), barplot() and hist() take an expression; bxp() takes a function that it calls without arguments (its help page stresses that it is a function and not an expression), so for a box plot it is boxplot(y, panel.first = \() grid()), with a lambda. Passing an expression there evaluates it too early, on whatever plot is current, and bxp() then warns panel.first ignored, it is not a function. And hist() has no panel.last: the argument travels on to the graphical parameters of axis() and title(), which warn "panel.last" is not a graphical parameter.

Dynamic graphics

locator() and identify() are as far as base graphics goes: R itself has no built-in dynamic or interactive graphics, such as rotating a point cloud or "brushing" (interactively highlighting) points across linked plots (An Introduction to R: Dynamic graphics). The manual points to two add-ons for that. The first is the GGobi system, reached from R through the rggobi package; that route is out of date, because rggobi was archived from CRAN on 2020-07-15 (CRAN: rggobi). The second is the rgl package, which is still maintained and draws interactive 3D plots with OpenGL, such as surfaces that can be rotated with the mouse (CRAN: rgl, package documentation). Interactive charts in a web browser are a different route again: a Shiny app re-draws a base or ggplot2 plot when an input changes, as Shiny, plumber and Web APIs shows.

Mathematical annotation: plotmath

When the text argument of text(), mtext(), axis() or legend() is an expression, R does not print it as a string: it typesets it as mathematics, with rules that resemble TeX. Other language objects, such as names, calls and formulas, are coerced to expressions, so they can be used too (R documentation: plotmath). Graphical parameters: par()

The parameters of base graphics are kept per device and read and set with par(). They hold things a single call should not have to repeat: the margins, the number of plots per page, the size of text, the colours, the orientation of the axis labels. The manual separates two ways to change them: permanently, with par(), until the device is closed, and temporarily, as arguments of one graphics function (An Introduction to R: Using graphics parameters). The page of par() says each device has its own set of parameters and that, if the current device is the null device, par() opens a new device before it queries or sets anything. That is why a batch script that only asks par("mar") leaves an Rplots.pdf behind (see The default device and Rplots.pdf).

Query, set, restore

A single parameter that is queried comes back as a plain vector, several come back as a list named by the parameters, and par() with no arguments returns all of them (72 on R 4.6.1), of which par(no.readonly = TRUE) returns the 66 that can be set. Setting parameters returns their previous values, invisibly, as a list that par() accepts back, and the help page points out the inconsistency: setting one parameter returns a list while querying one returns a vector. This gives the idiom for code that must not leave the device changed: save the old values, change what is needed, restore them, and put the restoring call in on.exit() so that it runs even when the drawing code fails.

layout() and split.screen()

layout() is the general form of mfrow. It takes a matrix of figure numbers, with 0 for an empty cell and a repeated number for a figure that spans cells, and optional widths and heights (relative numbers, or absolute centimetres with lcm()) and respect to keep a unit of width and height the same physical size. It returns the number of figures, layout.show(n) draws the outlines of the next n figures, and layout(1) returns to a single figure. The matrix must contain every number from 1 to the largest, or R stops with layout matrix must contain at least one reference to each of the values {1 ... 3}. The help page gives a limit of 200 rows and columns and 10007 cells. n2mfrow() proposes a grid for a number of plots (3 by 2 for five), and the older split.screen() divides a device into screens that screen(n) selects. The help page of split.screen() says its functions are totally incompatible with par(mfrow), par(mfcol) and layout(), so choose one mechanism per page. For anything more flexible than a grid of plots, grid viewports (see Grid Graphics and Lattice) are the better tool.

A colour in base graphics is one of three things: a colour name (the 657 names in colors(), 502 once synonyms such as "gray50" and "grey50" are removed with colors(distinct = TRUE)), a hexadecimal string "#RRGGBB" or "#RRGGBBAA" whose last pair is the opacity, or a positive integer, which indexes palette(). The default palette and the named palettes

hcl.colors(), rainbow() and lightness

hcl.colors(n, palette) (R 3.6.0) makes n colours from one of more than a hundred named palettes defined in the HCL space (hue, chroma, luminance), and hcl.pals(type) lists them by type: "qualitative", "sequential", "diverging" and "divergingx". It was introduced to give a wide range of palettes with much better perceptual properties than the RGB- and HSV-based ones such as rainbow(); R 3.6.0 also based the default colours of image() and filled.contour() on it and gave rainbow() and the other generators a rev argument (R NEWS: Changes in R 3.6.0). The palettes "Rocket" and "Mako" came in R 4.1.0, the handling of alpha in the palette functions was fixed in R 4.3.0, and a bug in hcl.colors(2, ...) was fixed in R 4.3.1 (R NEWS: Changes in R 4.1.0, R NEWS: Changes in R 4.3.0 and R NEWS: Changes in R 4.3.1). The help page makes recommendations that are worth following: "viridis" is a robust default, "Dark 3" works for shading points or lines in up to five groups, "YlGnBu" is a sequential palette similar to viridis but with aligned chroma and luminance, and "Green-Brown" and "Blue-Red 3" are colourblind-safe diverging palettes (R documentation: hcl.colors and palettes). The legacy generators rainbow(), heat.colors(), terrain.colors(), topo.colors() and cm.colors() are defined by hue sweeps in RGB or HSV space; the same help page says the rainbow palette has been widely criticised for its many perceptual problems, is very flashy and unbalanced in chroma and luminance, and recommends a palette from hcl.colors() instead.

The script puts a number on that. It converts the colours to the CIE Lab space and prints the lightness of each: hcl.colors(7, "viridis") steps up from 16 to 90 without a reversal, rainbow(7) jumps between 35 and 89 (yellow, green and cyan are about equally light and the blue-violet is dark), and the Okabe-Ito colours differ in lightness on purpose so that they stay distinguishable in grey. Lightness that rises monotonically survives photocopying or a greyscale print; rainbow() does not.

# Lightness (L in CIE Lab, 0 to 100) of each colour of three palettes. A good
# sequential palette steps up in lightness; rainbow() jumps up and down.
lightness <- \(cols) {
  rgb <- t(col2rgb(cols)) / 255
  convertColor(rgb, from = "sRGB", to = "Lab")[, "L"]
}
rb <- rainbow(7)
hc <- hcl.colors(7, "viridis")
ok <- palette.colors(7, "Okabe-Ito")

A short rule follows. For categories up to about eight, use palette.colors(n, "Okabe-Ito") or hcl.colors(n, "Dark 3"); for an ordered quantity, a sequential palette such as hcl.colors(n, "YlGnBu") (rev = TRUE puts the light end where the small values are); for values that diverge from a centre, hcl.colors(n, "Blue-Red 3"); and give col = explicitly in functions that you share, because the session palette is global.

Packages may add devices: the help page of Devices names svglite (SVG written as text elements) and tikzDevice (TeX-based graphics), and front ends such as RStudio provide their own screen device (dev.new() has an argument noRStudioGD to avoid it). A device has a name and a number from 1 to 63, and the null device, a placeholder that opens the default device when something tries to draw on it, is always device 1.

Opening, listing and closing

Each call to a device function opens a new device and makes it the current one, to which all drawing goes. The manual lists the functions that manage several devices: dev.list() gives the number and name of every active device (position 1, the null device, is never in the list), dev.cur() the current one, dev.set(which) switches, dev.next() and dev.prev() walk the list, and dev.off(which) closes one and returns the device that becomes current (An Introduction to R: Multiple graphics devices). graphics.off() closes them all. The return value of dev.off() is the one that is visible in a console after every plot: it is null device 1 when it closed the last one.

Closing is not optional for a file device. The file is written while the device is open and finished when it is closed; an SVG file is empty until dev.off(), a PDF lacks its trailer, and a script that forgets the call leaves a damaged or empty file and a device that the next plot call draws on. The safe pattern is the one in Wrapping a device in a function.

The default device and Rplots.pdf

If no device is open, any high-level graphics function opens one. Which one is the value of the option device: a screen device for most interactive use, and pdf(), or the setting of the environment variable R_DEFAULT_DEVICE, otherwise (R documentation: Devices). With Rscript that is pdf() with its default file name, Rplots.pdf, in the working directory. This is the most common way to find a stray file in a project directory, and anything that calls a plotting function or par() triggers it, including a package function that plots as a side effect. The script shows the file appearing and removes it; the getOption("device") value is a function in this setting, not a name. options(device = ) replaces the default with any function that opens a device, such as one that writes no file, and dev.new() opens a device of the default kind; if Rplots.pdf is taken it picks Rplots1.pdf and says so in a message.

Bitmap devices: png(), jpeg(), tiff() and bmp()

The four bitmap devices take the same arguments: filename (with a C integer format for the page number, Rplot%03d.png by default), width and height, units, pointsize, bg, res and type. The units are the trap. The default is pixels, 480 by 480, which at the nominal 72 ppi is a 6.7 inch square; units = "in" (or "cm", "mm") needs res, the resolution in pixels per inch, and without it png() stops with 'res' must be specified unless 'units = "px"'. The script reads the dimensions back from the PNG header, so the pixel size is checked and not assumed: 6 by 4 inches at 300 ppi is 1800 by 1200 pixels.

Text is sized in points, and a point is 1/72 inch at the resolution of the device, so the same pixel size at a different res is a different page in inches while 12 point text stays 0.2 inch tall. A 1800 by 1200 pixel device at 300 ppi is a 6 by 4 inch page, a good size for a figure; at 72 ppi it is a 25 by 16.7 inch page on which the same text is small. When a figure comes out with tiny text, res is the first thing to set. The opposite problem is a device too small for the default margins: a 200 by 100 pixel PNG at 72 ppi is 2.8 by 1.4 inches, the default vertical margins alone take 1.8 inches, and plot() stops with figure margins too large. Set mar smaller or make the device larger. Every bitmap device writes a new file for every new page, and the file name should contain %03d or later pages are lost: with a fixed name the file contains the last page plotted (R documentation: png).

# The size of a PNG file in pixels, read from its header (bytes 17 to 24).
png_size <- \(path) {
  hdr <- readBin(path, "raw", 24L)
  px <- \(i) sum(as.integer(hdr[i:(i + 3L)]) * 256^(3:0))
  c(width = px(17L), height = px(21L))
}

capabilities() reports what the build supports: in the container cairo, png, jpeg and tiff are TRUE and X11 is FALSE, which is why no screen device can open there. type = "cairo" is the default where cairo is available (getOption("bitmapType") says which), and it is the variant that works without a display, allows semi-transparent colours and gives anti-aliased text and lines. The help page lists others, "Xlib" (needs an X11 display) and "quartz" (macOS), and "cairo-png", which uses cairographics' own PNG writer, never uses a palette and normally gives a larger 32-bit file. On Windows the bitmap devices are drawn with the operating system’s GDI calls and their usage differs; the page of png() documents the platform differences, and this page was run on Linux. bg = "transparent" makes a PNG with a transparent background; JPEG supports only opaque ones. PNG is the right format for charts, lines and blocks of colour, JPEG is lossy and suits photographs and image plots, tiff() writes uncompressed lossless files by default, with compression choices, and bmp() is a standard Windows format. By default no resolution is recorded in the file (except for BMP), and viewers often assume 72 ppi, so set res when the file will be placed in a document at a known size.

Vector devices: pdf(), cairo_pdf() and postscript()

pdf() is the default file device and a multi-page one: with onefile = TRUE every new plot is a new page of the same file, and with onefile = FALSE it writes one file per page, using a C integer format in the name. The script counts three pages in a three-plot file and shows page01.pdf and page02.pdf for the other mode. Notable arguments are width and height in inches (7 by 7 by default), paper ("special" by default, a page size such as "a4" centres the device region on it), family (a PDF font family, Helvetica by default), pointsize, bg, title, compress, and, since R 4.5.0, author, timestamp and producer, where timestamp = FALSE omits the creation and modification dates and producer = FALSE the producer field, which helps to produce identical files. Since R 4.0.0 the default of useDingbats is FALSE, so no symbol font is used for the plotting symbols (R NEWS: Changes in R 4.0.0). The device does not embed fonts in the file, so only the standard families (Helvetica, Times, Courier and their aliases "sans", "serif" and "mono") are safe everywhere, and the 8-bit encoding of the font limits the characters: a character outside it is a warning, and R 4.4.0 made the warning show the UTF-8 character and one dot per character instead of per byte (R NEWS: Changes in R 4.4.0). For text with accents beyond Latin-1, Greek or symbols, cairo_pdf() supports a much wider range of UTF-8 glyphs and embeds the fonts it uses; the price is that it may record bitmaps instead of vector graphics in some cases, and it needs cairo (capabilities("cairo")). cairo_pdf() and cairo_ps() default to onefile = TRUE since R 4.4.0, to match pdf() and postscript().

pdf(NULL) is the device of this page. With file = NULL no file is created and, effectively, nothing is drawn, but the device can still be asked for text widths, which is why scripts and tests that need a device without a file, and the examples of this page, use it; par() and strwidth() work on it as on any other device. postscript() is the older vector format: with onefile = FALSE it writes Encapsulated PostScript (the first line of the file says EPSF). Since R 4.3.3, passing filename = NA to svg(), cairo_pdf(), cairo_ps() or the cairo bitmap devices is an error and no longer opens a file called NA, and postscript(NULL), which some people expected to work as pdf(NULL) does, is an error too (R NEWS: Changes in R 4.3.3).

SVG and the glyph-as-path output

svg() is a cairo device and writes SVG 1.1 (the multi-page form is SVG 1.2, which never passed the draft stage and which few viewers can display, so keep onefile = FALSE). Its arguments are filename (Rplot%03d.svg by default, one file per page), width and height in inches, pointsize, family, bg and antialias. A file name without a %03d format overwrites the file on every page, so the file contains the last page plotted. The text of an SVG written by cairo is not text: it is a set of glyph outlines, each character defined once as a path in a defs section and then placed with a use element. The script counts them: for a small plot there is no <text element, tens of <path elements and a glyph definition per distinct character. The consequence is that the picture looks the same on every machine, with no font dependency and no substitution, but the text cannot be searched, selected or edited in a vector editor, and the file is larger than the equivalent with real text. This is why the SVG at the end of this page has no <text> element.

svglite is an add-on package that writes SVG with real <text> elements: the script shows 11 of them and no <path> for the same plot, because it keeps the text as text and leaves the choice of font to the viewer. That gives searchable, editable text, and a figure whose text uses whatever font the viewer finds for the family named, so it can look different on a machine without the font. Which is better depends on where the file goes: a web page that styles the text with its own fonts wants svglite, a figure that must look exactly the same everywhere wants the cairo glyph paths. Both are valid answers to the same task.

Copying, printing and recording

dev.copy(device, ...) replays the current plot on a new device, which is how a plot that was drawn on the screen is saved to a file afterwards, and dev.print() and dev.copy2pdf() do the same and return to the original device. They copy the display list, not the pixels, so they need a device that keeps one: screen devices do by default, and print devices do not, so on a file device the first step is dev.control("enable"), which the help page says is safe only at the beginning of a plot. dev.copy() copies the device region and not just the plot, including the background colour, which on a screen device is transparent by default and probably not wanted on a PNG; dev.print() produces a PostScript print by default, and when it is given a device it sets the width and height in inches, which is wrong for the bitmap devices (png, jpeg, tiff, bmp) unless their units are set to inches. recordPlot() snapshots the display list into an object of class recordedplot and replayPlot() draws it again, on another device or at another size (dev.size() reports the device size in inches, pixels or centimetres). The help page of recordPlot() (R documentation: recordPlot) warns that recorded plots must not be used as a permanent storage format, because the format may change between R versions, and that replay of a plot drawn with ggplot2 may fail unless the package is loaded.

dev.capabilities() (new in R 4.2.0) reports what a device supports, as a named list: semi-transparency, transparent backgrounds, raster images, locator(), and the features of the graphics engine that arrived with R 4.1.0 and later for the grid system: gradients and patterns, clipping paths, masks, compositing, affine transformations, paths and glyphs, supported so far on Cairo-based devices and pdf() (R NEWS: Changes in R 4.1.0 and R NEWS: Changes in R 4.3.0). Base graphics does not use them; they are mentioned here because they explain why some devices report more than others, and the graphics engine version, R_GE_version, went from 14 in R 4.1.0 to 17 in R 4.6.0, each bump requiring packages that provide devices to be reinstalled.

Wrapping a device in a function

The pattern for scripts is to open the device, draw and close, with on.exit() closing it when the drawing code fails. Without it, a function that errors leaves the device open and the file half-written, and the next call draws on the same device, which is a hard mistake to find in a long script. dev.list() in the script confirms that no device is left, including after the error. The same pattern with par() in two_panels() keeps the graphical parameters of the caller intact.

# Open, draw, close: on.exit() closes the device even when the drawing code
# fails, so a failed plot does not leave a device (and a half-written file).
save_chart <- \(path, draw, width = 6, height = 4, res = 150) {
  png(path, width = width, height = height, units = "in", res = res)
  on.exit(dev.off())
  draw()
  invisible(path)
}
path <- tempfile(fileext = ".png")
save_chart(path, \() plot(1:3))
file.exists(path)
#> [1] TRUE
dev.list()
#> NULL

res <- try(save_chart(path, \() stop("the data are missing")), silent = TRUE)
class(res)
#> [1] "try-error"
dev.list()
#> NULL

# The same pattern keeps par() tidy: a function that sets parameters
# restores them, whatever happens inside.
two_panels <- \(a, b) {
  op <- par(mfrow = c(1, 2), mar = c(4, 4, 1, 1))
  on.exit(par(op))
  plot(a)
  plot(b)
}

The shelf loans figure

The last example is the figure of this page: four charts of the shelf loans on one page, made with base graphics and written by R itself to an SVG file. It is the only plot on the page that is reproduced, because it is the one that shows what the pieces above add up to. The script starts from source("scenario.R"), prepares one data frame (each loan with the genre and the page count of its book, matched through the normalised ISBN, and the duration of the loan in days), opens svg("r-shelf-loans-base-graphics.svg", width = 10, height = 7), divides the page with par(mfrow = c(2, 2)) and draws four charts before dev.off(). No random numbers are involved, so no set.seed() is needed.

The charts show the following. Top left, a barplot() of the number of loans per month, from a table() of format(loan_date, "%Y-%m"), with the month labels turned by las = 2: July and October 2025 are the busiest months with seven loans each. Top right, a hist() of the days between loan and return in cells of five days, with a background grid drawn through panel.first = grid() (the R 4.6.0 argument of hist()), a dashed abline(v = loan_days) at the 21-day loan period, and a legend() for the line. Bottom left, a horizontal boxplot() of the duration by genre with the cleaned genre names, with the loan period drawn through panel.last given as a function (R 4.6.0), which runs after the boxes and before the axes, and a wider left margin set with par(mar = ) for the genre names. Bottom right, a scatter plot() of the page count against the duration, abline(fit) with the fitted lm() line, and a legend() and an mtext() that use plotmath, hat(beta)[1] == 0.0068 and R^2 == 0.007: the slope is close to zero, so the number of pages explains almost none of the variation in duration. The colours are three of the colour-blind-safe Okabe-Ito palette (palette.colors(4, "Okabe-Ito")[-1], which drops the black) and one translucent version made with adjustcolor().

The loans that are not usable are dropped on purpose and the script says why: a loan that has not been returned has no duration, one loan has a return date before its loan date (a data-entry error planted in the scenario) and one has no loan date at all; in the scatter plot the books with an unknown page count are left out as well. The script needs R 4.6.0 or later because of panel.first for hist() and panel.last for boxplot().

source("scenario.R")

# Data preparation: one row per loan, with the genre and pages of its book.
key <- normalise_isbn(books$isbn)
loans$genre <- tolower(trimws(books$genre))[match(loans$isbn, key)]
loans$pages <- books$pages[match(loans$isbn, key)]
loans$days <- as.integer(loans$return_date - loans$loan_date)
loans$month <- format(loans$loan_date, "%Y-%m")

# Returned loans with a sensible duration (one row returns before the loan).
returned <- loans[!is.na(loans$days) & loans$days >= 0, ]
with_pages <- returned[!is.na(returned$pages), ]
per_month <- table(loans$month)
fit <- lm(days ~ pages, data = with_pages)
slope <- round(coef(fit)[["pages"]], 4)
r2 <- round(summary(fit)$r.squared, 3)
cols <- palette.colors(4, "Okabe-Ito")[-1]

svg("r-shelf-loans-base-graphics.svg", width = 10, height = 7)
par(mfrow = c(2, 2), mar = c(5, 4, 3, 1) + 0.1)

# 1. Loans per month: a bar plot of a table, labels turned with las = 2.
barplot(per_month, las = 2, cex.names = 0.7, col = cols[1], border = NA,
        main = "Loans per month", ylab = "Loans")

# 2. Loan duration: hist() with a background grid (panel.first, R 4.6.0)
#    and a reference line at the loan period.
hist(returned$days, breaks = seq(0, 40, by = 5), col = cols[2],
     border = "white", panel.first = grid(), ylim = c(0, 16),
     main = "Loan duration", xlab = "Days between loan and return")
abline(v = loan_days, lty = 2, lwd = 2, col = cols[3])
legend("topright", legend = "loan period (21 days)", lty = 2, lwd = 2,
       col = cols[3], bty = "n")

# 3. Duration by genre: boxplot() passes panel.last to bxp(), a function.
par(mar = c(5, 8, 3, 1) + 0.1)
boxplot(days ~ genre, data = returned, horizontal = TRUE, las = 1,
        col = cols[1], main = "Duration by genre",
        xlab = "Days between loan and return", ylab = "",
        panel.last = \() abline(v = loan_days, lty = 2, lwd = 2, col = cols[3]))

# 4. Pages against duration, with the fitted line and plotmath in the legend.
par(mar = c(5, 4, 3, 1) + 0.1)
plot(days ~ pages, data = with_pages, pch = 19,
     col = adjustcolor(cols[2], alpha.f = 0.7), ylim = c(0, 50),
     main = "Pages and duration", xlab = "Pages",
     ylab = "Days between loan and return")
abline(fit, lwd = 2, col = cols[3])
legend("topright", bty = "n", pch = c(19, NA), lty = c(NA, 1), lwd = c(NA, 2),
       col = c(cols[2], cols[3]),
       legend = c("loans", as.expression(bquote(hat(beta)[1] == .(slope)))))
mtext(bquote(R^2 == .(r2)), side = 3, line = 0, adj = 1, cex = 0.8)
dev.off()
