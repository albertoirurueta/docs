The apply Family and Functionals

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. Everything on this page is base R (the base, stats and utils packages that ship with R) except the comparison table near the end, whose short example uses the purrr 1.2.2 package (a labelled add-on package); the lintr 3.4.0 default linters were used only to check the scripts. R has for, while and repeat, but much idiomatic R code replaces the loop by a function that takes another function as an argument and calls it for every element, row, group or pair of a data structure. These form a family: the apply family (lapply(), sapply(), vapply(), mapply(), Map(), apply(), tapply(), outer(), rapply() and eapply()) and the functionals that fold or select (Reduce(), Filter(), Find(), Position(), do.call() and Vectorize()). This page explains what each one returns, how the result is shaped and why that shape sometimes surprises, which one to choose, and what the failures look like.

Every example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines that start with #> are what it printed. The scripts also pass the default lintr linters; a # nolint: comment marks a line where the idiom on show is what a default linter dislikes, so the linter does not hide the lesson. The names books, loans, shelf_today, loan_days and the book() constructor come from the running library-shelf scenario described on the section index: a script that needs them starts with source("scenario.R"). Where a message contains quotation marks, they are the typographic quotes R prints in a UTF-8 locale. Lists and data frames are the subject of Lists and Data Frames, matrices and arrays of Matrices and Arrays; the language underneath, namely functions as values, closures and lazy arguments, is in Functions, Scoping, Environments and Closures and Lazy Evaluation and Promises.

What the family is for

The Language Definition mentions the apply functions in its section on looping: R has three statements for explicit looping (for, while and repeat), it also provides functions for implicit looping, tapply(), apply() and lapply() among them, and many operations, especially arithmetic ones, are vectorized, so a loop may not be needed at all (R-lang: Looping). Three ideas follow from that sentence and organise this page.

  • A function is a value you can hand to another function. lapply(x, f) does not know what f does; it only knows how to call it once for every element of x and how to collect the answers. That is why the same few functions serve for counting rows, validating ISBNs and fitting models.

  • The family differs in two things: what is looped over and how the answers are gathered. lapply() loops over the elements of a vector or list, apply() over the rows or columns of a matrix, tapply() over groups, mapply() over several vectors in step, outer() over all pairs, rapply() over the leaves of a tree, eapply() over the objects of an environment. The answers are gathered as a list (lapply(), Map()), as a vector, matrix or array guessed from the answers (sapply(), mapply(), apply(), tapply()) or as a vector or array whose type you declared (vapply()).

  • None of them is a vectorised kernel. They are loops. lapply() and vapply() run the loop in C, but the function you pass is still an R function called once per element, so the speed is in the same range as a well-written for loop that preallocates its result (no timings are shown on this page, because they are platform-specific). The reason to prefer them is not speed but clarity: they say what is being computed and they return the result instead of filling a variable in a loop. Genuinely vectorised operations (x + 1, cumsum(), rowSums(), ifelse()) are faster and are the subject of Vectorisation and Iteration.

The figure summarises the family in one table: for each function, what you pass in, what comes back, and how much of the result type is known before the call. The rest of the page goes through the rows in the same order.

The single most useful column of that table is the last one. A function whose result type depends on the data (sapply() is the famous case) works in a test with three elements and fails in production with none. The recommendation used for every example on this page is therefore simple: use lapply() when you want a list, vapply() when you want a vector, a matrix or an array, and Map(), mapply() or apply() when the shape of the problem is pairs or margins. sapply() appears in the "surprise" demonstrations and in the section on older tutorials, and nowhere else.

lapply(): the one the others are built on

lapply(X, FUN, ...) returns a list of the same length as X, each element of which is the result of applying FUN to the corresponding element of X. The names of X are kept. X is a vector (atomic or list) or an expression object; the help page says that other objects, including classed objects, are coerced by base::as.list(), which is why a data frame (a list of columns) is visited column by column. FUN is found by match.fun(), so it can be a function, a symbol such as a backquoted operator, or a character string naming a function. Anything after FUN is passed on to every call, which is how na.rm = TRUE reaches mean(). If X is an atomic vector, FUN is always passed a length-one vector of the same type (R documentation: lapply).

source("scenario.R")

# lapply() returns a list with one element per element of X, in order.
squares <- lapply(1:3, \(i) i^2)
str(squares)
#> List of 3
#>  $ : num 1
#>  $ : num 4

#> [1] 10
#>

#> $a
#> [1] 2
#>
#> $b
#> [1] 5

Three details of the output are worth a look. First, lapply(loans_by_member, nrow) is the idiom behind the shelf question "how many loans per member": split() turns the data frame into a list of data frames, one per member, and lapply() maps nrow() over them (the script first folds the "Ana Ruiz" and "ana ruiz " spellings together and drops the loan whose member is empty, as the scenario intends). Second, a list of one-column answers prints as $name entries because the names of X were kept, and as [[1]] entries when X has no names. Third, FUN may be written as a string, but that is an inheritance from S: an anonymous function or a function name is clearer, and a string is not checked until the call runs.

Arguments in ... cannot have the same name as any of the other arguments of lapply(), and the help page warns that care may be needed to avoid partial matching to FUN: an argument named F or FU in the dots would be taken as FUN. In general-purpose code that passes ... through, it is good practice to name the first two arguments X and FUN, which both avoids the partial match and gives a sensible error message if an argument named X or FUN arrives through the dots. The argument-matching rules behind this are in Functions.

It is a loop, and the loop is in C

The next script writes lapply() by hand to show what it does, then looks at the real one. The hand-written version allocates the result with vector("list", n), calls FUN on X[[i]] in a for loop and copies the names. The real function has the same contract; its R code is a call to match.fun(), a conversion with as.list() when X is not a plain vector, and a call to .Internal(), and the loop is in C. One consequence is visible from the inside: the call that FUN sees (and that sys.call() and match.call() would return) is always FUN(X[[i]], ...), whatever you wrote, because the C code builds that call itself. The help page notes that this is for historical reasons and can matter for a primitive that inspects its call; wrap such a primitive in a function, as in lapply(ll, function(x) is.numeric(x)), so that method dispatch happens normally.

# A hand-written lapply(): allocate the result, loop over the positions of X,
# call FUN on X[[i]], keep the names.
my_lapply <- function(X, FUN, ...) { # nolint: object_name_linter.
  FUN <- match.fun(FUN) # nolint: object_name_linter.
  X <- as.list(X) # nolint: object_name_linter.
  out <- vector("list", length(X))
  for (i in seq_along(X)) {
    out[[i]] <- FUN(X[[i]], ...)
  }
  names(out) <- names(X)
  out
}

x <- list(a = 1:3, b = c(10, 20))
identical(my_lapply(x, sum), lapply(x, sum))
#> [1] TRUE
identical(my_lapply(x, rev), lapply(x, rev))
#> [1] TRUE

# The real one is a call to the C code behind .Internal(): the loop is
# in C, but FUN is still called from R once per element.
deparse(body(lapply))
#> [1] "{"
#> [2] "    FUN <- match.fun(FUN)"
#> [3] "    if (!is.vector(X) || is.object(X)) "
#> [4] "        X <- as.list(X)"
#> [5] "    .Internal(lapply(X, FUN))"
#> [6] "}"

# The call that FUN sees is always FUN(X[[i]], ...), whatever you wrote.
lapply(1:2, \(x) sys.call())
#> [[1]]
#> FUN(X[[i]], ...)
#>
#> [[2]]
#> FUN(X[[i]], ...)
#>

The same note explains a subtlety that older R versions got wrong. When FUN is a closure factory the elements reach it through promises, and a promise that is never forced captures the loop variable. R 3.2.0 changed the higher-order functions (the apply functions and Reduce()) to force the arguments of the functions they call, so lapply(1:3, make_adder) returns three adders for 1, 2 and 3 (R NEWS: Changes in R 3.2.0). The mechanism is explained, with an example, in Lazy Evaluation and Promises; the point here is that code on the web that calls force() inside every closure factory used with lapply() is from before that release.

sapply(): the user-friendly one, and its surprises

sapply() is a wrapper of lapply() that tries to make the answer simpler: by default it returns a vector or a matrix when that is appropriate, or an array with simplify = "array", by calling simplify2array() on the list that lapply() produced. The "when appropriate" is where the trouble is: whether you get a vector, a matrix or a list depends on the lengths of the answers, and the lengths depend on the data. The rules from the help page are:

  • Simplification is only attempted if X has length greater than zero and all the return values have the same positive length.

  • If the common length is 1 the result is a vector, with the type of the highest type among the answers in the order NULL, raw, logical, integer, double, complex, character, list, expression.

  • If the common length is greater than 1 the result is a matrix with one column per element of X.

  • Otherwise the result is what lapply() returned, a list.

The next script shows each of the three outcomes with the shelf data, the two cases where "nothing to simplify" produces list(), and then two silent changes that simplification makes to a result: it can turn a "vector of classes" into a matrix, and it drops the class of dates, because unlisting a list of Date objects leaves their numbers.

Names, arrays and the simplify argument

USE.NAMES = TRUE (the default) names the result by X when X is a character vector that has no names itself. simplify = FALSE gives the same answer as lapply(), and sapply(x, f, simplify = FALSE, USE.NAMES = FALSE) is exactly lapply(x, f). simplify = "array" returns an array of one rank higher than the answers when they are themselves arrays, instead of flattening them into a matrix; that option was added in R 2.13.0, together with the change that made replicate() and vapply() return a higher-dimensional array for array answers (R NEWS: Changes in R 2.13.0). Because the arguments simplify and USE.NAMES come after the dots, their names cannot be abbreviated: simp = FALSE does not partially match, it is passed to FUN, and the failure is about FUN, not about sapply(). replicate(n, expr) is the related wrapper for the repeated evaluation of an expression, usually one that draws random numbers; its simplify argument defaults to "array".

simplify2array(x, higher = TRUE, except = c(0L, 1L)) is the function that does the work for sapply() and mapply(). Its except argument controls the two exceptions to simplification: a list whose elements all have length 0 is returned as it is, and one whose elements all have length 1 is only unlisted into a vector, not made into an array. The argument was added in R 4.2.0 and can be set to NULL to always simplify to an array if possible.

# USE.NAMES: a character X becomes the names of the result ...

#> fiction  poetry

# ... unless you turn it off; a list of strings is not named this way.
sapply(c("fiction", "poetry"), nchar, USE.NAMES = FALSE)

sapply(list("fiction", "poetry"), nchar)
#> [1] 7 6

dim(sapply(v, square_of))

vapply(): the same, with a contract

vapply(X, FUN, FUN.VALUE, ..., USE.NAMES = TRUE) is sapply() with a promise. FUN.VALUE is a template, "a (generalized) vector" in the help page’s words: a value of the type and length that every call of FUN must return. Simplification is always done; every result is checked against the template, and a result that does not fit is an error, not a different shape. The type of the template decides the type of the answer, so the empty input has the right type too. If FUN.VALUE has length 1 the answer is a vector of the length of X; if it has length greater than 1 the answer is a matrix with length(FUN.VALUE) rows and one column per element of X; if the template is itself an array the answer is an array of one more dimension, dim(FUN.VALUE) followed by length(X). The names of the rows come from the template when it has names and otherwise from the first result, and the names of the columns, or of the vector, come from X exactly as for sapply() (R documentation: vapply).

vapply() was added in R 2.11.0, "based on a suggestion from Bill Dunlap", with the stated purpose of requiring a template for the function value in order to determine the output type and check for consistency (R NEWS: Changes in R 2.11.0). The shelf example is the ISBN check: is_valid_isbn13() returns one logical per ISBN, so the template is logical(1).

What goes wrong, in R’s own words

The point of the template is the error. The next script prints the real messages. Each one names the element that failed, as FUN(X[[1]]), and what it found; the line break before "but" is part of the message. Types may be promoted along the order logical, integer, double, complex, so a template of numeric(1) accepts an integer or a logical result, and may not be demoted: a double result for an integer(1) template is an error even when the value is a whole number. A NULL result has length 0 and fails a template of length 1; if "no answer" is legitimate, return NA of the right type instead.

# Print an error or warning message exactly as R words it.
show_message <- function(expr) {
  res <- tryCatch(expr, error = identity, warning = identity)
  cat(conditionMessage(res), "\n")
}

#>  but FUN(X[[1]]) result is length 2
# ... or of the wrong type.
show_message(vapply(1:2, \(i) "a", numeric(1)))
#> values must be type 'double',
#>  but FUN(X[[1]]) result is type 'character'
show_message(vapply(c(1.5, 2), \(x) x, integer(1)))
#> values must be type 'integer',
#>  but FUN(X[[1]]) result is type 'double'
show_message(vapply(1:2, \(i) i > 1, character(1)))
#> values must be type 'character',
#>  but FUN(X[[1]]) result is type 'logical'

# Types may be promoted along logical < integer < double < complex, not demoted.
vapply(c(TRUE, FALSE), \(x) x, numeric(1))
#> [1] 1 0
vapply(1:3, \(i) i, numeric(1))
#> [1] 1 2 3

#> 'FUN.VALUE' must be a vector

The messages are values must be length 1, followed by but FUN(X[[1]]) result is length 2, and values must be type 'double', followed by but FUN(X[[1]]) result is type 'character'. mapply() and Map(): several vectors in step

lapply() visits one vector. When the function needs a title and a year together, or a lower and an upper bound, the arguments come from several vectors and have to be walked in step: first elements, second elements, and so on. mapply(FUN, ..., MoreArgs = NULL, SIMPLIFY = TRUE, USE.NAMES = TRUE) does that. It is "a multivariate version of sapply" in the help page’s description: the vectors to loop over go in ..., arguments that do not vary go in the list MoreArgs, SIMPLIFY controls the same simplification as in sapply() (it can also be the string "array"), and USE.NAMES takes the names from the first argument or, if that is an unnamed character vector, uses it as the names. The arguments in the call are named if ... or MoreArgs are named, so named vectors match named parameters of FUN (R documentation: mapply).

Map(f, ...) is a wrapper of mapply() that never simplifies, in the words of the help page of funprog "similar to Common Lisp’s mapcar (with arguments being recycled, however)": it is mapply(FUN = f, ..., SIMPLIFY = FALSE). Its first argument is called f, not FUN, and it takes MoreArgs through the dots. For a result that you will index or loop over again, Map() is the safer choice; mapply() is for the case where you know the answers are scalars and want the vector (R documentation: funprog).

Recycling, zero length and the warning

The arguments in ... are recycled to the length of the longest, the same rule as for arithmetic. apply(): the margins of a matrix

apply(X, MARGIN, FUN, ..., simplify = TRUE) calls FUN on the slices of an array. X is a matrix or array (an object with a dim, such as a data frame, is first converted with as.matrix() or as.array()); MARGIN says which subscripts are kept: for a matrix 1 is the rows, 2 the columns and c(1, 2) every cell, and where X has named dimnames, MARGIN can be a character vector selecting them. FUN receives one slice (a row, a column, or a matrix for higher-rank arrays) and the extra arguments in ... (R documentation: apply).

The shape of the result follows the help page. If every call returns a vector of length n and simplify is TRUE, the answer is an array of dimension c(n, dim(X)[MARGIN]) when n > 1; when n is 1 the answer is a vector if MARGIN has length 1 and an array of dimension dim(X)[MARGIN] otherwise. If the calls return vectors of different lengths, or simplify is FALSE, the answer is a list of length prod(dim(X)[MARGIN]), with dim set to MARGIN when that has length greater than 1. In every case the result is coerced by as.vector() to one of the basic vector types first, so a factor result becomes a character array. The practical consequence is one famous surprise, which the next script shows with a table of loans per member and year.

apply() on a data frame

apply() on a data frame converts it with as.matrix() first. If any column is not numeric, the whole matrix is character, and as.matrix() formats the numbers to a common width, with blanks on the left, as the first lines of the next script show. tapply(): a function per group

tapply(X, INDEX, FUN = NULL, ..., default = NA, simplify = TRUE) applies FUN to each group of values of X defined by the unique combinations of one or more factors. If it returns a single atomic value and simplify is TRUE, the answer is an array with one dimension per element of INDEX, with NA for the empty cells, and the dimnames are named by the names of INDEX (R documentation: tapply). An Introduction to R presents it as the function for ragged arrays, groups of different sizes (An Introduction to R: The function tapply() and ragged arrays). outer(): every pair

outer(X, Y, FUN = "*", ...) computes FUN for every combination of an element of X with an element of Y. The result is the array of dimension c(dim(X), dim(Y)) (the lengths, for plain vectors) whose element [i, j] is FUN(X[i], Y[j]); the dimnames of X and Y are copied to it. X %o% Y is the operator form of outer(X, Y, "*"), and FUN = "*" is handled as a special case through the matrix product, "intended only for numeric vectors and arrays" (R documentation: outer, An Introduction to R: The outer product of two arrays).

Why outer() "behaves strangely": R FAQ 7.17

outer() is the one member of the family that does not call FUN once per pair. It builds two long vectors that hold every combination, with X repeated to length length(X) * length(Y) and Y extended the same way, and calls FUN once on these. So FUN must be a vectorised function (or the name of one) that takes at least two arguments and returns a value of the same length as its first argument. A function that works only on single values breaks that, either with an error from the body or with a length check. This is R FAQ 7.17: the entry says that outer() does not work on arbitrary functions the way the apply() family does, because it passes two large vectors to the function at once, and gives the fix: wrap a scalar function so that it simulates vectorised behaviour, or use Vectorize().

show_message <- function(expr) {
  res <- tryCatch(expr, error = identity, warning = identity)
  cat(conditionMessage(res), "\n")
}

# outer() calls FUN *once*, with two long vectors holding every combination.
# A function written for scalars is the wrong shape for that.
due <- function(loan, extra) if (extra > 0) loan + 14 + extra else loan + 14
show_message(outer(1:3, c(0, 7), due))
#> the condition has length > 1

# A function that always returns one value breaks the length check.
show_message(outer(1:3, 1:3, \(x, y) max(x, y)))
#> dims [product 9] do not match the length of object [1]

# Fix 1: use the vectorised form of the operation.
outer(1:3, 1:3, pmax)
#>      [,1] [,2] [,3]
#> [1,]    1    2    3
#> [2,]    2    2    3
#> [3,]    3    3    3

# Fix 2: Vectorize() the scalar function.
outer(1:3, c(0, 7), Vectorize(due))
#>      [,1] [,2]
#> [1,]   15   22
#> [2,]   16   23
#> [3,]   17   24

# Fix 3 (R FAQ 7.17): a wrapper that loops over the pairs by position.
wrapper <- function(x, y, my_fun, ...) {
  vapply(seq_along(x), \(i) my_fun(x[i], y[i], ...), numeric(1))
}
outer(1:3, c(0, 7), wrapper, my_fun = due)
#>      [,1] [,2]
#> [1,]   15   22
#> [2,]   16   23
#> [3,]   17   24

Source: R FAQ 7.17: Why does outer() behave strangely with my function?

The two failures have two messages. A function with an if on a vector condition stops with the condition has length > 1 (an error since R 4.2.0, a warning before). A function that returns one value for the whole input, such as max(x, y) instead of pmax(x, y), makes outer() stop with dims [product 9] do not match the length of object [1]: it expected nine values, one per pair, and got one. The three fixes in the script are the three in the FAQ: use the vectorised relative of the operation (pmax()), apply Vectorize() to the scalar function, or write a wrapper that loops over the pairs by position (here with vapply() instead of the FAQ’s sapply()).

rapply(): the leaves of a tree

lapply() visits the top-level elements of a list and passes a sublist as a whole to FUN. rapply(object, f, classes = "ANY", deflt = NULL, how = c("unlist", "replace", "list"), ...) is the recursive version: it applies f to the leaves, the elements that are not list-like, whose class is in classes, and how decides the shape of the answer (R documentation: rapply). With how = "replace" each matching leaf is replaced by the result of f and every other leaf is kept as it was. With how = "list" or how = "unlist" the object is conceptually copied, the matching leaves are replaced by the result of f and all the others by deflt; with "unlist" the copy is then flattened by unlist(recursive = TRUE), which drops the NULL defaults. f is a function, not the name of a function, on purpose: the help page says rapply() is more recent than lapply() and does not accept a string. Since R 3.6.0 rapply() also accepts list-like objects of length 2^31 and more; in R 3.5.x and earlier object had to be a list (R NEWS: Changes in R 3.6.0). The page Lists has a first walk through the same function on a nested list; this section concentrates on the three values of how and on classes.

eapply(): the objects of an environment

An environment holds named objects, and eapply(env, FUN, ..., all.names = FALSE, USE.NAMES = TRUE) applies FUN to each of them and returns the results as a list. Names that begin with a dot are skipped unless all.names = TRUE; no enclosing environment is searched, only the one given; the result is named unless USE.NAMES = FALSE; and, the help page stresses, the order of the elements is not sorted and is arbitrary for hashed environments (R documentation: eapply). That last point is the one to remember: an environment is a hash table, not a sequence, so code that depends on the order of eapply() should sort the names itself.

An environment is the right container for a keyed store that is modified in place: a cache, a registry or a lookup table keyed by a string (see Scoping, Environments and Closures for how environments work and why they have reference semantics). The shelf example is a store of book objects keyed by ISBN.

source("scenario.R")

# An environment used as a keyed store: ISBN -> book.
store <- new.env(hash = FALSE)
for (i in c(1, 2, 4)) {
  b <- book(
    books$title[[i]], books$author[[i]], books$isbn[[i]],
    books$year[[i]], books$genre[[i]], books$pages[[i]]
  )
  assign(b$isbn, b, envir = store)
}
ls(store)
#> [1] "9780002000291" "9780141439518" "9780306406157"

# eapply() returns a named list; with a non-hashed environment the order is
# the order R keeps, otherwise it is arbitrary: sort the names to be safe.
pages <- eapply(store, \(b) b$pages)
unlist(pages[sort(names(pages))])
#> 9780002000291 9780141439518 9780306406157
#>           198           432           387

# Names starting with a dot are skipped unless all.names = TRUE.
assign(".cache", "internal", envir = store)
length(eapply(store, identity))
#> [1] 3
length(eapply(store, identity, all.names = TRUE))
#> [1] 4

# USE.NAMES = FALSE drops the names; no enclosing environment is searched.
class(eapply(store, identity, USE.NAMES = FALSE))
#> [1] "list"
length(eapply(new.env(), identity))
#> [1] 0

vapply(mget(keys, envir = store), format, character(1))

Reduce(): folding a vector into one value

Reduce(f, x, init, right = FALSE, accumulate = FALSE, simplify = TRUE) uses a binary function to combine the elements of x successively. This is the operation that other languages call fold (Haskell), reduce (Python, JavaScript) or accumulate (the C++ standard library); the help page says it is patterned after Common Lisp’s reduce. A left reduce computes f(f(f(x1, x2), x3), x4); a right reduce (right = TRUE) computes f(x1, f(x2, f(x3, x4))). If init is given it is added logically at the start (or at the end, when proceeding from the right), so f is called with init and the first element. With a single element that element is returned, with no elements NULL is returned (or init, if given), and f is always called with exactly two arguments. The current implementation is not recursive, so it does not hit the stack limit that a hand-written recursion would on a long vector (R documentation: funprog).

With accumulate = TRUE the successive combinations are all kept, which Haskell calls a scan (cumsum() is the special case for addition). simplify = TRUE then unlists the accumulated results when they all have length one.

# Reduce(f, x) folds x with a binary function: f(f(f(1, 2), 3), 4).

#> [1] 10
Reduce(\(a, b) paste0("(", a, b, ")"), c("a", "b", "c", "d"))
#> [1] "(((ab)c)d)"

# right = TRUE folds from the right: f(1, f(2, f(3, 4))).

#> [1] 110
Reduce(`+`, integer(0))
#> NULL
Reduce(`+`, integer(0), 0L)
#> [1] 0

Folding functions: composition

A fold needs no numbers. Reduce() over a list of functions, with the value as the accumulator and function(value, step) step(value) as the combining function, is a pipeline; it is the standard way to compose functions in base R. The next script builds a title cleaner from three steps and a second function that keeps the intermediate values. Function factories and the planned Compose() of R-devel are on Function Factories and Higher-Order Functions.

# Reduce() over a list of functions composes them; the accumulator is the value.
pipeline <- function(...) {
  steps <- list(...)
  function(x) Reduce(\(value, step) step(value), steps, x)
}

clean_title <- pipeline(trimws, tolower, \(s) gsub("[^a-z ]", "", s))
clean_title("  The Quiet STREETS! ")
#> [1] "the quiet streets"

# The same fold, keeping every intermediate value.
trace_steps <- function(x, ...) {
  Reduce(\(value, step) step(value), list(...), x, accumulate = TRUE)
}
trace_steps("  The Quiet STREETS! ", trimws, tolower)
#> [1] "  The Quiet STREETS! " "The Quiet STREETS!"    "the quiet streets!"

Filter(), Find(), Position() and Negate()

Filter(f, x) applies the unary predicate f to each element of x, coercing to logical if necessary, and returns the subset of x for which the result is true. The help page notes that NA values from the predicate are currently always taken as false, and that control over NA handling may be added in the future. Find(f, x, right = FALSE, nomatch = NULL) returns the first (or, with right = TRUE, the last) element for which f is true; Position(f, x, right = FALSE, nomatch = NA_integer_) returns its index. Negate(f) builds the predicate that returns the logical negation of what f returns. They are patterned after Common Lisp’s remove-if-not, find-if, position-if and complement, and the help page adds that the current implementation of Find() and Position() is not optimised for performance (R documentation: funprog).

do.call(): calling with a list

do.call(what, args, quote = FALSE, envir = parent.frame()) constructs and executes a call from a function (or a non-empty string naming one) and a list of arguments. The names of args become the argument names. It is the bridge between a list and a function that takes its arguments separately: if you have a list of data frames, do.call(rbind, frames) is rbind(frames[[1]], frames[[2]], ...) for however many there are. If the argument list already exists and you need to add arguments, combine them with c(), as in do.call(paste, c(parts, sep = "")). With quote = FALSE the arguments are evaluated (in the calling environment, not in envir); with quote = TRUE each is quoted, so a symbol or call stays unevaluated. envir is where a function given by name is looked up (R documentation: do.call).

Vectorize(): a loop in disguise

Vectorize(FUN, vectorize.args = arg.names, SIMPLIFY = TRUE, USE.NAMES = TRUE) returns a function with the same arguments as FUN that accepts vectors for the arguments named in vectorize.args (all of them, by default) and calls FUN once per element through mapply(). Only the arguments that are actually passed are vectorised, default values are not, and the function cannot be used with a primitive, which has no formals. It also cannot be used with a function that has an argument named FUN, vectorize.args, SIMPLIFY or USE.NAMES, as they would clash with its own (R documentation: Vectorize). R 3.2.4 added a check for such argument-name clashes, and R 4.1.0 stopped the result function’s environment from keeping unneeded objects (R NEWS: Changes in R 3.2.4).

The body of the wrapper is the best explanation of what Vectorize() does: it captures the arguments of the call with match.call(), evaluates them, and calls mapply() through do.call(), with FUN as the function and the vectorised arguments as the varying ones. There is no vectorisation in the sense of a compiled loop; Vectorize() is a convenience that makes a scalar function accept vectors, with the speed of a loop in R. The name is therefore misleading: if you need speed, rewrite the function with vectorised building blocks (ifelse(), pmin(), cumsum(), indexing; see Vectorisation and Iteration); if you need convenience, Vectorize() is the right tool, in particular for outer() (see above) and for callers such as integrate() that expect a function of a vector.

Pitfalls collected

  • sapply() returns a list for an empty input. Anything that sums, indexes or combines the result breaks for a filter that matches nothing. Use vapply() with a template; the empty case is then integer(0) or numeric(0).

  • sapply() and Reduce(accumulate = TRUE) drop classes. A list of Date objects becomes numbers, and a list of factors becomes integer codes. Keep the list with lapply() or simplify = FALSE and combine it with do.call(c, ...).

  • apply() returns the transposed matrix when FUN returns a vector. The answers are the columns. Transpose with t(), or use prop.table(), sweep() or scale() when the operation already exists.

  • apply() on a data frame converts it to a matrix. A character column turns every number into text, padded to a common width. Work on the numeric columns only, or loop over row positions.

  • tapply() groups by exactly what is in the data. "Fiction", "fiction" and "Fiction " are three groups; a missing value in the grouping factor drops the row; an empty combination is NA, not zero.

  • outer() calls FUN once with all the pairs (R FAQ 7.17). A function that was written for single values must be vectorised first.

  • mapply() and Map() recycle. A warning for lengths that do not divide evenly, silence for lengths that do; a zero-length argument gives list().

  • Reduce() of an empty vector is NULL. Give init, so that the empty case is the identity of the operation.

  • Filter() treats NA as false. That is convenient for a count and dangerous for a selection that must not silently lose rows.

  • eapply() has no order. Sort the names, or use mget() with the keys in the order you want.

  • Vectorize() is a loop. It makes a scalar function accept vectors; it does not make it fast.

  • do.call() puts the argument values in the call. The call shown in an error message is as long as the arguments; for large data pass a symbol with quote = TRUE or call the function directly.

  • FUN as a string is looked up when the call runs. A misspelt name fails at run time, not at the point where the call is written.
