Publishing to CRAN

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. CRAN is the main repository of R packages: the place install.packages("name") looks first, a set of volunteer-run check machines that rebuild every package on several operating systems all the time, and a policy that a package has to satisfy before it is admitted and while it stays. This page follows a package on that road: what the CRAN Repository Policy asks, how to choose a name, how R CMD check --as-cran reproduces the incoming checks on your own machine, which other machines to try (win-builder, mac-builder, R-hub v2 and GitHub Actions), how to test the packages that depend on yours, what happens when you submit and resubmit, how version numbers, deprecation and archival work afterwards, and which repositories to use when CRAN is not the right place. The tools run for real are base R with its tools and utils packages, devtools 2.5.2, usethis 3.2.2, rcmdcheck 1.4.0 and desc 1.4.3, with the default linters of lintr 3.4.0 used only to check the scripts. The shelf package is built with the Suggests testthat 3.3.2, knitr 1.52 and rmarkdown 2.32. Named in a sentence and not run, because they are not installed or need an account or a remote service: rhub 2.0.1, revdepcheck, available 1.1.0, lifecycle, BiocCheck and BiocManager; pak 0.11.1 is installed and only named. Nothing is submitted to CRAN, win-builder, mac-builder, R-hub or Bioconductor on this page: the submission flow is described from the official documents, and every fragment that is not run says so right before it.

Every example is a script that was run with Rscript on R 4.6.1, and the lines that start with #> are what it printed; the scripts also pass the default lintr linters. The names books, loans and shelf_today and the book() constructor belong to the running library-shelf scenario described on the section index. The shelf package shown here was created, documented, tested, built and checked for real with the tools of the previous pages, and its files are shown as the tools wrote them: Creating Packages builds it, Documentation with Rd, roxygen2 and Vignettes documents it and Testing with testthat tests it. The checks below ran on a copy of that package. Paths are shortened to ~/shelf (the directory of the package) and ~ (the directory that holds the tarball), and the header of an R CMD check log, which names the platform, the compilers, the locale and the time, is left out of every excerpt; so are timings, because they differ on every machine. The policy opens with the idea that explains most of what follows: CRAN is a home for polished, non-trivial packages and not a place to develop them. The people who read submissions are volunteers whose time the policy calls CRAN’s most precious resource, which is why the rules are strict about checks that run clean, about not submitting too often and about answering feedback in the next submission and not by email. A development version, an experiment, a package that exists to track a moving service and a package that a single project uses are all better served by GitHub or by r-universe (see Alternatives: Bioconductor, r-universe and GitHub), and a CRAN release is the stable point you choose to publish.

What the CRAN Repository Policy requires

The policy is a short document (the revision used here is 6875, read on 2026-10-21) split into source packages, binary packages, submission and re-submission. It binds everyone who submits: sending in a package, an update included, counts as agreeing to it. The parts that decide whether a first submission survives are below; the policy page remains the authority, and CRAN may change it.

Authors, copyright holders, the maintainer and the licence

The ownership of copyright and intellectual property rights of every component of the package has to be clear, including the components downloaded at installation or during use. In the DESCRIPTION file that means an Authors@R field, which Writing R Extensions says is required for CRAN submissions, built with person() and the role codes: aut for an author, cre for the maintainer, ctb for a contributor and cph for a copyright holder. Code copied or derived from other work keeps its copyright and licence statements and its authors, preferably as ctb entries. Where the copyright belongs to someone other than the authors, the policy asks for cph entries in Authors@R, or for a Copyright field that may refer to a file inst/COPYRIGHTS. An ORCID or ROR identifier goes into the comment argument of person(), which CRAN strongly encourages.

There must be one designated maintainer, a person and not a mailing list, with a name and a valid email address that stays current and is usable without filtering, confirmation steps or forwarding, because the CRAN team and the automatic systems write to that address. The maintainer warrants that they act for all credited authors. The licence has to give CRAN the right to distribute the package in perpetuity, licences that are not in the licence database shipped with R (license.db) are generally refused, and a change of licence has to be highlighted in the next submission. The shelf package follows all of this with the placeholder maintainer maintainer@example.com, one person() carrying the roles aut, cre and cph, and License: MIT + file LICENSE.

The LICENSE file written by usethis::use_mit_license() holds two lines, YEAR: 2026 and COPYRIGHT HOLDER: shelf authors, which is the form that the + file LICENSE part of the field refers to; the longer LICENSE.md the same function writes is left out of the tarball through .Rbuildignore. The text fields have conventions of their own, which the incoming check enforces and which the section on the incoming checks below shows failing: the Title is in title case, at most about 65 characters, without a final period and without repeating the package name; the Description is one paragraph of complete sentences that does not start with the package name or "This package"; names of other packages and external software are in single quotes, function names are written with parentheses and without quotes, citations are in author-year style with a DOI in angle brackets, and URLs are in angle brackets too. What a package may and may not do on the user’s machine

The policy lists behaviour that a package must avoid because CRAN checks run unattended on shared machines and a package is code that runs on other people’s computers. It must not write anywhere in the user’s file space (the home directory and the clipboard included) apart from the temporary directory of the R session, and what it writes there has to be cleaned up. Since R 4.0.0 a package that must keep data, configuration or a cache between sessions may use the per-package user directories returned by tools::R_user_dir(), provided it needs a version dependency on R (>= 4.0) or uses the function conditionally, keeps the files small and removes outdated material. A package must not modify the global environment (the workspace), must not call q(), must not tamper with the code of the standard and recommended packages, must not use ::: or .Internal() and .Call() entry points that base R does not declare as API, must not start external programs such as viewers or browsers during examples and tests without closing them, must not send information about the session to third parties without the user’s confirmation, and must not turn off security provisions such as the verification of TLS certificates. Downloads of anything at installation or startup use https and, for more than a few megabytes, a large enough timeout.

Two limits are checked mechanically. A package must never use more than two cores at the same time, and R CMD check --as-cran sets the environment variable _R_CHECK_LIMIT_CORES_ so that code in the parallel package that starts more than two workers fails (R Internals, "Tools"). The usual pattern is to default to one core and to cap at two whenever that variable is set.

# R CMD check --as-cran sets _R_CHECK_LIMIT_CORES_ (to TRUE) so that parallel
# code that starts more than two workers fails the check. A package should
# never use more than two cores by default.
default_cores <- function() {
  limit <- Sys.getenv("_R_CHECK_LIMIT_CORES_", "")
  if (nzchar(limit) && !identical(toupper(limit), "FALSE")) {
    2L
  } else {
    getOption("shelf.cores", 1L)
  }
}

default_cores()
#> [1] 1
Sys.setenv("_R_CHECK_LIMIT_CORES_" = "TRUE")
default_cores()
#> [1] 2
Sys.unsetenv("_R_CHECK_LIMIT_CORES_")

Source: R Internals: Tools

The second limit is the Internet. The policy says that a package that uses an Internet resource has to cope with the resource being unavailable or changed, with an informative message and neither a check warning nor a check error, that the use of external resources should be kept to a minimum, and that rate-limit errors such as the HTTP codes 429 and 403 must be avoided because other packages may use the same site. Writing R Extensions adds that installation itself should avoid the Internet where possible. The usual shape is a function that catches the failure, says what happened and returns an empty result, and tests and examples that skip when the resource is missing. The address below is a local port on which nothing listens, so no outside network is involved; the message that readLines() produces is the text R itself prints.

# A function that needs a web resource must fail gracefully: an informative
# message and NULL, not a check warning or error. The address below is a
# local port nobody listens on, so no outside network is involved.
fetch_catalogue <- function(url) {
  tryCatch(
    suppressWarnings(readLines(url)),
    error = \(e) {
      message("catalogue not available: ", conditionMessage(e))
      NULL
    }
  )
}

res <- fetch_catalogue("http://localhost:1/books.csv")
#> catalogue not available: cannot open the connection to 'http://localhost:1/books.csv'
is.null(res)
#> [1] TRUE

# The same idea in a test or an example: skip when the resource is missing.
if (is.null(res)) message("skipping the example that needs the catalogue")
#> skipping the example that needs the catalogue

Source: CRAN Repository Policy: Source packages

Writing R Extensions, in its chapter on portable packages, adds a list of things not to do in tests and examples because they pass on one machine and fail on another: do not test how long a command takes, do not test the exact format of messages from R or from other packages (they change and they can be translated, and the message text of the system’s C library or of libcurl changes between versions), do not test for the absence of warnings, compare numbers with a tolerance and only when you have done an error analysis, canonicalise file paths before comparing them, set a seed for anything random, use options(warn = 1) so that warnings are reported when they happen, and test your package in more than one time zone when it handles dates. A package must also run on at least two of the major R platforms; a Windows-only package is considered, though CRAN may not be the right place.

Time, size and examples

Checking a package should take as little CPU time as possible, because the check farm runs thousands of packages. The policy asks for examples that run for a few seconds at most, for long-running tests and vignette code to be made optional while the tests that are left still exercise every feature, and for tarballs that are small: neither data nor documentation should normally exceed 5 MB, the source tarball should not exceed 10 MB, and large data belongs in a separate data package that is rarely updated. R CMD check --as-cran sets --timings, which lists examples taking more than 5 seconds of CPU or elapsed time, and _R_CHECK_TIMINGS_ to 10 so that timings of 10 seconds or more are reported for installation, examples, tests and vignettes (Writing R Extensions, "Check timing"; R Internals, "Tools").

The Rd macro \donttest is how an example that is correct but slow, or that depends on something the check machine may lack, is kept out of the quick path of a plain check. Since R 4.0.0, R CMD check --as-cran runs the \donttest examples too, so the macro no longer hides code from CRAN: it only keeps it out of example() in a non-interactive session and out of a plain R CMD check. Writing R Extensions says that code inside \donttest has to be correct R code whose packages are declared in DESCRIPTION, and that the code should carry a comment saying why it needs the macro. \dontrun is for code that cannot run at all. The first script shows how the three kinds of example are treated by the Rd tools; the text block under it comes from a throw-away package whose single help page holds a plain example, a \donttest example and a \dontrun example, checked once with a plain R CMD check and once with --as-cran.

  "x <- 1 + 1",

Dependencies and other repositories

The packages a CRAN package needs in Depends, Imports or LinkingTo (its strong dependencies) have to be available from CRAN or from the Bioconductor software repository. A package named in Suggests or Enhances that is on neither has to be located through the Additional_repositories field, a comma-separated list of repository URLs that R CMD check uses to confirm the package can be found, as a source package at least. The field does not install anything; it lets CRAN check that the optional package exists. A suggested package should be used conditionally in examples and tests when it cannot be installed easily on every major platform, which Writing R Extensions recommends doing always: requireNamespace("pkg", quietly = TRUE) before using it. Orphaned CRAN packages must not be strong dependencies. Updates, frequency and archival

The policy asks for updates to be submitted responsibly, with respect for the volunteers' time: once a package is established, the interval it considers appropriate is "no more than every 1-2 months". Before submitting a correction, look at the CRAN check page of the package at https://CRAN.R-project.org/web/checks/check_results_NAME.html (replace NAME with the package name) and wait until that page has been fully updated after the previous publication, which can take at least 48 hours. A package that shows an issue on the macOS arm64 flavour should be checked with mac-builder before resubmission. Packages are not normally removed from CRAN, but they are archived when the maintainer asks, when R CMD check gives an ERROR at the release of a new R x.y.0 and the maintainer has not set a firm deadline for an update and kept it, or when warnings and significant notes are left unfixed after the maintainer was asked to update. An archived package keeps its place in the Archive area, and its name stays reserved: the name check of the next section reports a clash with "CRAN archive" as well as with the current index. If an update changes the API of a package that others depend on, the policy expects you to contact their maintainers, suggest changes, give them at least two weeks, ideally more, and mention in the submission which packages are affected and that their maintainers were told.

Keep a NEWS.md (or NEWS) file that says what changed in each version: since R 4.3.0 R CMD check also reports problems it meets when reading that file, CRAN links the news from the package page, and news() reads it back from the installed package, as shown in the section on versions below. Keep README.md for the repository and cran-comments.md for the people who review the submission; the latter is excluded from the tarball with .Rbuildignore. None of the files that a GitHub project accumulates (workflow files, .github, issue templates, pkgdown sources) belongs in the tarball either: they are listed in .Rbuildignore by the usethis functions that create them. The tarball that CRAN receives should contain the package and nothing else, which the listing in the next section shows for shelf.

Choosing a package name

Settle the name before anything else, because a rename touches every file. The Package field of Writing R Extensions says that a name contains only ASCII letters, numbers and dots, has at least two characters, starts with a letter and does not end in a dot; if it needs explaining, the explanation goes into the Description field, not the Title. The CRAN policy adds the rule that matters most: a name must not conflict, irrespective of case, with any current or past CRAN package (the Archive area can be consulted), nor with any current Bioconductor package. Names are persistent, and changing the name of a published package is in general not permitted. By submitting, the maintainer gives CRAN the right to use the name, so the team can orphan a package and let another maintainer take it over. The first script applies the syntax rule as a regular expression and the case-insensitive rule to a small hand-typed list; the next one reads the real index.

# Writing R Extensions: a package name has only ASCII letters, numbers and
# dots, at least two characters, starts with a letter and does not end in a dot.
valid_name <- \(x) grepl("^[A-Za-z][A-Za-z0-9.]*[A-Za-z0-9]$", x)

candidates <- c(
  "shelf", "shelfdesk", "shelf.loans", "shelf-tools", "shelf_tools",
  "2shelf", "s", "shelf."
)
data.frame(name = candidates, valid = valid_name(candidates))

What --as-cran changes

The help of R CMD check describes --as-cran as a selection of customizations similar to those CRAN uses. It is a bundle of settings, not a separate program: it sets a number of _R_CHECK_*_ environment variables (the full list with their meaning is in the "Tools" chapter of R Internals), turns on some options such as --timings, and adds checks to the default list. The environment variables that matter most are these. _R_CHECK_CRAN_INCOMING_ turns on the check of whether the package is suitable for publication on CRAN, and _R_CHECK_CRAN_INCOMING_REMOTE_ (default: the value of the first) includes the part of it that needs remote access, the name lookup above and the URL checks. _R_CHECK_FORCE_SUGGESTS_ makes missing suggested packages an error; it defaults to true, but not for the submission checks of CRAN itself, and devtools::check() sets it to false through its argument force_suggests. _R_CHECK_LIMIT_CORES_ caps the cores that code can use, _R_CHECK_TIMINGS_ and --timings report slow steps, _R_CHECK_SYSTEM_CLOCK_ compares the clock of the machine with an external clock as part of "checking for future file timestamps", and _R_CHECK_DONTTEST_EXAMPLES_ can be set to a false value to skip the \donttest examples temporarily while developing. Checking on other systems

A check on your own machine tells you about your own machine. CRAN checks a package on several flavours of Linux, on macOS and on Windows, with the released R, R-patched and R-devel, and a bug that depends on the operating system, the compiler, the C library, the locale or the version of R shows up there first. The submission checklist of CRAN names two services to use before submitting, win-builder and R-hub, and the policy adds mac-builder for the macOS arm64 flavour. Everything in this section is described from the official documents and none of it was run: the services need an account, an upload or a GitHub repository, and a result by email or on a web page.

win-builder

win-builder (https://win-builder.r-project.org/) is the R project’s service for building and checking source packages on Windows, meant for people who have no Windows machine, and the one the CRAN submission checklist names, saying that the CRAN team uses the same infrastructure for the packages submitted. It builds and checks a source package on Windows with R-devel, R-release or R-oldrelease, each under its own upload directory; the page lists the R version each directory currently holds and the Rtools release it uses. The procedure is to build the tarball with R CMD build, make sure the Maintainer field of DESCRIPTION holds your own email address (the answer is sent there and nowhere else), upload the file by passive FTP in binary mode as an anonymous user to the directory of the R version, or through the upload form, and wait about half an hour for an email that links to a randomly named directory with the binary and the check logs, which is deleted after roughly 72 hours. All CRAN and Bioconductor software packages are already installed on the service; a package that needs another one can be preceded by uploading that one first. The service is a shared machine, so the disclaimer on its page applies: do not upload other people’s packages, and do not expect confidentiality.

devtools wraps the upload so that you do not leave R. The functions check_win_devel(), check_win_release() and check_win_oldrelease() bundle the source package, upload it and make the answer arrive by email at the maintainer’s address (or at email =), which usually takes about 30 minutes; webform = TRUE uses the web form instead of passive FTP. They are a fragment here: running them submits the package to a remote machine.

R-hub v2

R-hub is the community service for checking a package on many platforms; it is not maintained by CRAN, so its settings can differ from the ones CRAN uses. Since rhub 2.0.0 (2024-04-11) it is a completely new system: R-hub v2 runs R CMD check and similar checks on GitHub Actions, and the functions of the first version (rhub::check(), rhub::check_for_cran(), rhub::validate_email() and friends) are deprecated and defunct. The current release is rhub 2.0.1 (2025-03-06). It is not installed in the image used for this page, so what follows is the documented workflow with its command names, and nothing was run.

The requirements are a GitHub account, a package in a GitHub repository whose origin remote points to it, and a GitHub personal access token stored in the git credential store (for instance with gitcreds::gitcreds_set()). rhub_setup() adds the workflow file .github/workflows/rhub.yaml to the package, which then has to be committed and pushed to the default branch of the repository, rhub_doctor() checks that everything is set up, rhub_platforms() lists the platforms, and rhub_check() starts a check on the platforms you choose, in an interactive menu or through the platforms argument. Reverse dependencies

A package that other packages use cannot be updated as if it were private. The packages that list yours in Depends, Imports or LinkingTo are its reverse strong dependencies, those that list it in Suggests or Enhances are the weaker ones, and each of them is checked against your new version by CRAN. The policy tells you to check, for an update, that the packages depending on yours still pass R CMD check, and to check the reverse strong dependencies, the reverse suggests and the recursive strong dependencies of these. A new package has no reverse dependencies, but the same habit starts on the day someone depends on it.

Finding them

tools::package_dependencies(reverse = TRUE) computes the reverse dependencies from a matrix shaped like the result of available.packages(): a Package column and the dependency fields Depends, Imports, LinkingTo, Suggests and Enhances. Its which argument takes the field names or the shorthands "strong" (the default), "most" (adds Suggests) and "all", and recursive follows the chain of dependencies. The first script builds that matrix by hand for four imaginary packages that use shelf, so it needs no network and its output never changes. The second one asks the live index about a long-established package and prints only comparisons, because the counts change every day; it needs the network.

Submitting to CRAN

Nothing in this section was run: it describes the submission flow from the CRAN policy, the submission page and the guidance of the usethis and devtools packages. The shelf package is not submitted anywhere, and, as shown above, would be refused because of its name.

The web form and the confirmation email

A package is submitted through the form at https://cran.r-project.org/submit.html, and not by email: the policy is explicit that the submission form is the way in, and that the package itself must never be emailed. The form has three steps (upload, submission, confirmation). In the first you give your name, the email address of the maintainer, the package file (only .tar.gz files, at most 100 MB) and an optional comment; the page reminds you that the tarball has to come from R CMD build, that DESCRIPTION must hold a valid maintainer field of the form NAME <EMAIL>, and that you have to know the rest of the policies. The upload must be a source tarball made by R CMD build and named PACKAGE_VERSION.tar.gz. If someone other than the maintainer submits (a co-author, for instance), say so in the comment: the designated maintainer will have to confirm the submission. If the maintainer’s email address changed, explain it in the comment and, if possible, send a confirmation from the previous address to the submissions mailbox of CRAN as a separate message. If the package needs special treatment (vignettes that can only be rebuilt on the maintainer’s machine or that take very long), say so in the comment too.

CRAN then sends a confirmation email to the maintainer’s address, with a link that must be followed: at that link you are asked to confirm that you have followed the policies and that you want the package submitted. Until you do, the package is not submitted. The email check also confirms that the address in DESCRIPTION works, which is why that address has to be valid and unfiltered. After the confirmation the package enters CRAN’s automatic checks, which the R Packages book (community material) describes as a first round of R CMD check on Windows and Linux, probably with released and development R, with a second email with links to the results usually within hours. A new package is then looked at by a member of the CRAN team; the book adds that the process can be fully automated for an update of a package that is already on CRAN, and that reverse dependency checks follow when the update passes the first round.

Do not submit a package again while the first upload is pending and no reply has arrived, which can take a few days. The policy says you can check that the upload was received by looking at the directory listing at https://CRAN.R-project.org/incoming/. The listing shows, at the time of writing (2026-10-21), the folders archive, inspect, newbies, pending, pretest, publish, recheck, special and waiting, next to folders named after people, each with a last-modified time. CRAN does not document on the policy or submission pages what each folder means, and the names are an implementation detail of the submission system that may change, so use the listing only for what the policy says it is for, to see that a file arrived, and expect the answer by email.

Feedback and resubmission

CRAN’s reply is either an acceptance (the usual short message from the CRAN team saying, in community write-ups, that the package is "on its way to CRAN") or a list of things to change. Feedback is normally about something automatic that failed, about the text of DESCRIPTION (the title and the description are real hotspots, according to the R Packages book), about examples and tests that take too long, about the policy items in this page, or about a note that you did not explain. Fix everything in the list, not just the first item.

Resubmission is done in the same way as submission, using the optional comment field of the web form to explain how the feedback was addressed, and not a separate email. Updates to a package that is already on CRAN must have a higher version number, and the policy says that increasing the version at each submission reduces confusion, so it is preferred even when the previous submission was rejected: a new package that was rejected with version 0.1.0 is resubmitted as 0.1.1. The R Packages book adds that this means gaps in released version numbers, which does not matter. Start the comment with a "Resubmission" heading and a list of the changes made, and keep the results of the new checks below it (the next section shows the file).

Versions and the life of a package

Version numbers

A package version is a sequence of at least two, and usually three, non-negative integers separated by single . or - characters, and it is not a decimal number: 0.9 is smaller than 0.75, because 9 is smaller than 75. R parses and compares versions with the class package_version (a numeric_version), which compares component by component. The convention that the R Packages book and usethis follow is major.minor.patch for a released version (a patch for a bug fix without new features, a minor version for compatible new features, a major version for changes that can break users), with a fourth component, .9000, for the development version between releases: usethis::use_dev_version() raises 0.1.0 to 0.1.0.9000 right after a release, so that the development version sorts after the release and before the next one. R accepts - as a separator (1.2-3 is 1.2.3), but the dot form is the recommended one.

# A package version is a sequence of integers separated by "." or "-"; it is
# compared component by component, not as a decimal number.
package_version("0.9") < package_version("0.75")
#> [1] TRUE
package_version("1.10.0") > package_version("1.9.0")
#> [1] TRUE
sort(c("1.9.0", "1.10.0", "1.2.0"))
#> [1] "1.10.0" "1.2.0"  "1.9.0"
sort(package_version(c("1.9.0", "1.10.0", "1.2.0")))
#> [1] ‘1.2.0’  ‘1.9.0’  ‘1.10.0’

# A development version adds a fourth component and sorts after the release.
package_version("0.1.0.9000") > package_version("0.1.0")
#> [1] TRUE
package_version("0.1.0.9000") < package_version("0.2.0")
#> [1] TRUE
package_version("1.2-3") == package_version("1.2.3")
#> [1] TRUE
unlist(package_version("1.2-3"))
#> [1] 1 2 3

# "1.0-beta" is not a valid version.
tryCatch(package_version("1.0-beta"), error = conditionMessage)
#> [1] "invalid version specification ‘1.0-beta’"

# Depends: R (>= 4.1.0) is a test of this kind, made against R's own version.
getRversion() >= "4.1.0"
#> [1] TRUE

The version of R is part of the contract as well. The Imports and Suggests fields take version requirements the same way, testthat (>= 3.0.0), and the policy says that CRAN versions are expected to work with the current CRAN releases of their dependencies.

Deprecating and removing functions

A function that is going away is first deprecated, then defunct, then removed, with the steps spread over releases so that users and the packages that depend on yours can adapt; this is the practice base R itself follows for its own functions (see help("base-deprecated")). .Deprecated() goes in the body of the old function with the name of the replacement; it signals a warning of class deprecatedWarning with the fields old, new and package. When package is given, the message points to the help page <package>-deprecated that should list the deprecated functions of the package (the help page of Deprecated says so), so the package needs such a help page. .Defunct() does the same with an error of class defunctError. The script shows the messages as R 4.6.1 prints them; the code that the check looks for is _R_CHECK_DEPRECATED_DEFUNCT_, which is on for CRAN submissions and notes the use of recently deprecated or defunct functions in other people’s code.

# Retiring a function in steps: first a deprecation warning, later an error.
# `package = "shelf"` makes the message point to the package's
# shelf-deprecated help page (see the roxygen2 chapter for writing it).
old_summary <- function(...) {
  .Deprecated("loan_summary", package = "shelf")
  invisible(NULL)
}
gone_summary <- function(...) {
  .Defunct("loan_summary", package = "shelf")
}

w <- tryCatch(old_summary(), warning = identity)
class(w)
#> [1] "deprecatedWarning" "warning"           "condition"
writeLines(conditionMessage(w))
#> 'old_summary' is deprecated.
#> Use 'loan_summary' instead.
#> See help("Deprecated") and help("shelf-deprecated").

e <- tryCatch(gone_summary(), error = identity)
class(e)
#> [1] "defunctError" "error"        "condition"
writeLines(conditionMessage(e))
#> 'gone_summary' is defunct.
#> Use 'loan_summary' instead.
#> See help("Defunct") and help("shelf-defunct").

# Without a replacement the message is shorter.
retired <- function() .Deprecated()
writeLines(conditionMessage(tryCatch(retired(), warning = identity)))
#> 'retired' is deprecated.
#> See help("Deprecated")

Source: R documentation: Deprecated

For anything more than a handful of functions, the lifecycle package (not installed here, not run) from the tidyverse team provides a vocabulary and tools: badges (experimental, stable, superseded, deprecated) in the documentation and functions such as lifecycle::deprecate_warn() that warn once every so often and not at every call, and lifecycle::deprecate_stop() for the defunct stage. The R Packages book and the lifecycle site describe the stages. Whatever the tool, give users at least one release with a warning before an error, say in NEWS.md which function replaces which, and use the reverse-dependency check to see who is affected.

A breaking change is not only a removed function. A different return type, a changed default, a warning that becomes an error, a different order of arguments and a changed class all break callers. The policy expects the maintainers of affected packages to be told in advance (at least two weeks, ideally more), expects the submission to name those packages, and warns that a change which causes significant disruption to other packages has to be agreed with the CRAN maintainers well before any publicity. If breaking is inevitable, a new major version, a new function name next to the old one, or a new package for the new design are all better than a silent change.

Archival, orphaned packages and the CRAN checks page

CRAN re-checks every package continuously, on the flavours listed on the page https://cran.r-project.org/web/checks/ (the three current flavours of R on Debian GNU/Linux, Fedora, macOS and Windows), and each package has its own page at https://CRAN.R-project.org/web/checks/check_results_NAME.html with the status per flavour, the logs and the additional issues (compiler warnings, sanitizers, the donttest run and so on). A maintainer who no longer wants to maintain a package can ask for it to be archived; a package whose check gives an ERROR when a new R x.y.0 is released is archived unless the maintainer has promised and kept a firm date for an update; a package whose maintainer cannot be reached is archived or orphaned. The policy keeps the name: the Archive remains, names stay reserved, and a new maintainer can take over a package with the written agreement of the previous maintainer, or without it for a formally orphaned package. A package whose strong dependency leaves CRAN no longer meets the dependency rule described earlier, which is why the policy treats strong dependencies so strictly.

The checks page is also where a mistake after publication shows. Binary packages for Windows and macOS are built by CRAN, not by the maintainer, by batch jobs, and can take a day or two to appear, longer to reach mirrors. Look at the checks page a few days after each release, and wait until it is fully updated (at least 48 hours) before submitting a fix; the policy asks for exactly that.

After the package is accepted

When the CRAN team accepts the package it is published on the master site, and CRAN builds the binaries itself: the policy says that binary packages are not accepted from maintainers, that they are made automatically and that the Windows and macOS binaries can take a day or two to appear. The package page has the canonical address https://cran.r-project.org/package=NAME (Writing R Extensions prefers it to the longer /web/packages/NAME form), built from the Title, Description, authors, links (URL and BugReports), the NEWS file, the vignettes and the reference manual; install it with install.packages("NAME"). The package cranlogs (2.1.1 on CRAN; not installed, not run) queries a web service that keeps the download counts of the RStudio CRAN mirror, and the same service makes the download badges; usethis::use_cran_badge() adds a CRAN status badge to the README. Tag the release on GitHub (usethis::use_github_release() does it from the CRAN-SUBMISSION file that devtools::submit_cran() writes) and move the version to .9000 with usethis::use_dev_version(). The development of the next version goes on in the repository, which is why the policy can say that CRAN is not a development platform: between releases the work lives on GitHub.

Alternatives: Bioconductor, r-universe and GitHub

CRAN is not the only repository, and it is not always the right one.

Bioconductor (https://contributions.bioconductor.org/) is the project for high-throughput genomic analysis (sequencing, expression and other microarrays, flow cytometry, mass spectrometry and image analysis), and its software packages must address that area and interoperate with other Bioconductor packages by reusing their data structures. A package can be submitted to Bioconductor or to CRAN, not to both. Bioconductor releases twice a year, around April and October, tied to a version of R, with a devel branch where new features go and a release branch for bug fixes. Version numbers are x.y.z with an even y in a release and an odd y in devel, and a new package starts at 0.99.0. Packages live in git: you submit by opening an issue in the Bioconductor contributions repository on GitHub with the link to your repository (the default branch is used, so it must contain only package code), and the build system checks the package against devel; after acceptance you push to the Bioconductor git server and your package is built on a schedule against the release and devel branches (the maintainer is expected to read the build reports, which come weekly to daily). The package must pass R CMD build, R CMD check and BiocCheck (a package of the Bioconductor project, not installed here, not run) without ERROR; the DESCRIPTION carries at least two leaf terms of biocViews, which place the package in the Bioconductor taxonomy, and its description should be at least three complete sentences. Its guidelines on names follow CRAN’s (unique irrespective of case among current and past Bioconductor and CRAN packages). Install packages with BiocManager::install() (not installed here; see Packages, Libraries and Namespaces).

r-universe (https://docs.r-universe.dev/) is a platform from rOpenSci, now a project of the R Consortium, that builds packages from Git repositories and serves them as a CRAN-like repository with binaries, documentation and a catalogue. To publish, create a repository named <user>.r-universe.dev in lower case on your GitHub account, containing a file packages.json that lists the Git repositories of the packages (the packages do not have to be on GitHub; any public Git server works), and install the r-universe app on the account. The packages then appear at https://<user>.r-universe.dev after they are built. A registry entry has a package name and a url, with optional fields such as subdir for a package in a subdirectory and branch for a branch, a tag or the value "*release" for the most recent GitHub release.

4.2.0

R CMD check can optionally, and under --as-cran, validate the HTML produced from the Rd files with HTML Tidy; --as-cran also sets _R_CHECK_MATRIX_DATA_. R on Windows uses UTF-8 and the UCRT toolchain.

4.3.0

R CMD check reports problems in reading NEWS.md; --as-cran traps leftover browser() calls and checks the KaTeX rendering of mathematics in Rd files; _R_CHECK_TIMINGS_ takes its value from the environment even for --as-cran.

4.4.0

R CMD check notes S4-style exports used without declaring a dependence on methods.

4.5.0

--as-cran notes bad parts of the URL fields of DESCRIPTION; the time lookup of the future-timestamps step is more robust against unexpected replies; a C23 compiler is selected by default when available (a package can ask for C17 with USE_C17 in SystemRequirements); R CMD check no longer reports marked UTF-8 or Latin-1 strings in datasets by default.

4.6.0

The default C++ standard is C++20 where available (a package can request C++17 if essential); R CMD check notes on a number of non-API entry points are upgraded to warnings; a tarball is inspected for the package name instead of deriving it from the file name.

Source: R NEWS: Changes in R 4.0.0 to 4.6.0

The portability notes follow the compilers: a package with compiled code is compiled with C23 and C++20 by default on the R versions above, so code that relied on the older standards needs a SystemRequirements entry or a fix. The details of compiled code are in Interfacing C, C++ and Fortran. The shelf package has no compiled code and none of these apply to it. R 4.6.2 is scheduled for 2026-10-29 (a bug-fix release) and R-devel is 4.7.0; the policy asks for the final checks to be made with the current development version, or with R-patched or the current release when R-devel is not possible and the submission says so.
