Reference Classes and R6

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. Almost everything in R copies: assign a vector, a list or a data frame to a second name, change the second one, and the first is untouched. This page is about the exceptions, the objects that every holder of a reference sees change. R has two mainstream systems for writing them as classes with methods in the style of Java or C++: Reference Classes, created with setRefClass() and shipped in the methods package of base R, and the add-on package R6, created with R6Class(). Both are built on environments. This page uses base R only for the Reference Class sections and R6 2.6.1 (CRAN) for the R6 sections, so those sections begin with library(R6); the methods package is attached by Rscript by default (since R 3.5.0), so the Reference Class examples need no library() call. Two other pages of this section are close relatives: S3 Classes and Generics and S4 Classes and Methods are the value-semantics systems, and The S7 Object System ends with a script that builds a trimmed book in S3, S4, R6, S7 and as a Reference Class, and with a table that compares S3, S4, R6 and S7 (the Reference Class is described in the prose next to it).

Every example below is a complete script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)); the lines starting with #> are what it printed, and the scripts pass the default lintr linters. Class generators are conventionally written in CamelCase (BookRC, BookR6), which the default object_name_linter dislikes, so each of those assignments carries # nolint: object_name_linter.. The names books, loans, shelf_today, loan_days and the book class come from the scenario.R file of the running library-shelf scenario described on the section index; scripts that use them start with source("scenario.R"). The three object-oriented systems of the section model the same book with the same six fields in the same order, title, author, isbn, year, genre and pages, and the same validation rules as validate_book() in that file, so that the classes of the different pages line up field by field. Errors and warnings that the scripts provoke on purpose are caught so that every script exits with status 0, and the message text shown is the real one. Memory addresses are never printed: the output shows class names, never the address of an environment.

Why objects with reference semantics exist

R is built around values. When a function receives a vector it receives what behaves like a copy, and an assignment such as y <- x makes a second name for the same value that is copied only when one of them is modified (see Assignment, Names and Values and Memory and Copy Semantics). That is exactly what is wanted for data analysis, and it is why a function can never change the data frame it was given by accident. The help page of Reference Classes describes the functional model in these terms and then names the situations in which it is the wrong one: sometimes one would like all the code dealing with an object to see the exact same content, so that a change made in any computation is reflected everywhere, which suits an object with some objective reality such as a window in a user interface.

R already has one kind of object that is never copied: the environment. The manual lists environments among the basic object types and describes them as a frame plus an enclosure (R-lang: Environments); Scoping, Environments and Closures covers the mechanism. Assigning an environment to a second name, or passing it to a function, copies the reference and not the environment, so every holder sees every change.

# A list is a value: a function that "modifies" it works on a copy.
shelf_list <- list(log = character())
add_to_list <- function(x, entry) {
  x$log <- c(x$log, entry)
  x
}
add_to_list(shelf_list, "L001 out")$log
#> [1] "L001 out"
shelf_list$log
#> character(0)

# An environment is a reference: the function and the caller share it.
shelf_env <- new.env()
shelf_env$log <- character()
add_to_env <- function(e, entry) {
  e$log <- c(e$log, entry)
  invisible(e)
}
add_to_env(shelf_env, "L001 out")
shelf_env$log
#> [1] "L001 out"

# Assignment copies the reference, not the environment.
alias <- shelf_env
alias$log <- c(alias$log, "L002 out")
shelf_env$log
#> [1] "L001 out" "L002 out"
identical(alias, shelf_env)
#> [1] TRUE

Source: The R Language Definition: Environments

The list shelf_list behaves as a value: the function returned a changed copy and left the original empty. The environment shelf_env behaves as a reference: the function changed it in place, and alias is not a copy of it but a second name for it, which is why identical() reports TRUE. The R FAQ draws the same line when it separates the frame of a function from its enclosing environment (R FAQ 7.12: What are the enclosing and parent environments?).

A bare environment is a poor class: nothing says which names it is supposed to hold, nothing checks what is stored in them, and the functions that operate on it are just functions that happen to receive it. Reference Classes and R6 both add the missing parts on top of an environment:

  • a class: a named definition of the fields (state) and the methods (functions that work on that state), so that objects of the class all look the same;

  • methods called with $: obj$lend(...) runs a function that belongs to the object and can read and change its fields, which is the style of Java, C++ and Python;

  • inheritance: a subclass adds fields and methods and can override the methods of its superclass;

  • initialisation and printing hooks, and, in R6 and (partly) in Reference Classes, locking and active bindings.

"R5" is not a separate system. It is a community nickname for Reference Classes (R’s other systems are S3 and S4, so the third was jokingly called R5), and the R6 package, which is a different implementation, took its own name from the joke. The R6 documentation also records that "R5" had been the code name of a different, never released object system. This page says Reference Classes for the base R system and R6 for the package.

Reference Classes with setRefClass()

A Reference Class is an S4 class whose instances contain an environment. The documentation says so directly: reference classes are implemented as S4 classes with a data part of type environment, fields correspond to named objects in that environment, and a field with a declared class is implemented as a special form of active binding that enforces the class on assignment (R documentation: refClass). That is why they live in the methods package, why they are created with a function from the S4 family, and why isVirtualClass(), validObject() and is() work on them.

Fields and the generator

setRefClass(Class, fields = , contains = , methods = ) defines the class and returns a generator. The fields argument is either a character vector of field names, which gives every field the class "ANY", or a named list in which each element is usually the name of a class. A field of a declared class accepts only objects of that class or a subclass. The six fields of the scenario book are declared in that way, and BookRC$new(...) (equivalently BookRC(...)) creates an object:

Several things in that output are worth reading slowly. BookRC is not a class definition but an object of class refObjectGenerator, which is a function (it can be called as BookRC(...)) and also a reference object with methods of its own: $new(), $methods(), $fields(), $help(), $lock() and $accessors(). BookRC$fields() returns the declared class of every field. The default print method, $show() of the parent class envRefClass, prints Reference class object of class "BookRC" followed by every field. A field that is not supplied is not NA but the empty vector of its class (integer(0), character(0)): the object exists in a state the book rules forbid, which is the reason the next subsection writes an initialize method. And is.environment(b1) is TRUE: the object is an environment with an S4 class attached.

Two reserved names exist as fields of every object: .self is the whole object and .refClassDef is its class definition. Both are read-only, and the documentation advises against defining any field whose name begins with a dot.

Methods, initialize() and validation

Methods are ordinary functions in a named list passed as methods, or added later with Gen$methods(...). Inside a method the object itself is not an argument. The environment of the method is the object, so fields and other methods are used by name, and the whole object is available as .self. A field is changed with the non-local assignment <<-: the documentation stresses that non-local assignment is required, because title <- value just creates a local variable as it would in any function. The reason is the one explained on the scoping page: <<- starts the search for the name in the enclosing environment of the function, which for a method is the object, where the field lives.

Two method names are special. initialize is called when an object is created, and its job here is the work of the scenario’s book() function: trim the strings, normalise the ISBN, convert the numbers to integer and apply the rules of validate_book(). finalize is called before the object is garbage collected (see the section on debugging and finalizers below). The documentation’s advice for an initialize method comes to three rules, and the example follows all of them:

  1. It should pass ... on, with callSuper(...) or initFields(...), so that subclasses can add fields.

  2. It must work when called with no arguments, because $copy() calls the generator that way; here that is the missing(title) branch.

  3. The standard initialisation, which is callSuper(...) and ends in initFields(...), assigns the named arguments to the fields. Any computation on the arguments (here trimws() and as.integer()) comes before it and any check of the finished object after it.

source("scenario.R")

BookRC <- setRefClass("BookRC", # nolint: object_name_linter.
  fields = list(
    title = "character", author = "character", isbn = "character",
    year = "integer", genre = "character", pages = "integer"
  ),
  methods = list(
    initialize = function(title, author = NA_character_, isbn = NA_character_,
                          year = NA_integer_, genre = NA_character_,
                          pages = NA_integer_, ...) {
      "Create a book; with no title (as copy() does) create an empty shell."
      if (missing(title)) {
        return(callSuper(...))
      }
      callSuper(
        title = trimws(title), author = trimws(author),
        isbn = if (is.na(isbn)) isbn else normalise_isbn(isbn),
        year = as.integer(year), genre = trimws(genre),
        pages = as.integer(pages), ...
      )
      validate()
    },
    validate = function() {
      "Apply the rules of validate_book(); return the object invisibly."
      lens <- c(length(title), length(author), length(isbn),
                length(year), length(genre), length(pages))
      if (any(lens != 1L)) {
        stop("every field of a book must have length 1", call. = FALSE)
      }
      if (is.na(title) || !nzchar(title)) {
        stop("a book needs a title", call. = FALSE)
      }
      if (!is.na(isbn) && !is_valid_isbn13(isbn)) {
        stop("invalid ISBN-13: ", isbn, call. = FALSE)
      }
      if (!is.na(year) && year > 2100L) {
        stop("implausible year: ", year, call. = FALSE)
      }
      invisible(.self)
    },
    describe = function() {
      yr <- if (is.na(year)) "n.d." else year
      sprintf("%s (%s, %s)", title, author, yr)
    },
    show = function() {
      cat("<", class(.self)[[1L]], "> ", describe(), "\n", sep = "")
    }
  )
)

Look at what the listing shows. The strings arrive trimmed and the ISBN arrives normalised, because callSuper() received the cleaned values. The year 1999 was a double in the call and is an integer in the object, because the field would otherwise have rejected it (the error text is in the section on what goes wrong). Each failed validation raises the same message as validate_book() does for the S3 class: the rules moved from a function that checks a list to a method that checks .self. The class check of a field is not a validity rule, though: title = c("A", "B") is a perfectly good character vector, which is why the length check is still needed.

The docstring at the start of initialize and validate is a convention of Reference Classes: if the first element of a method body is a literal string, Gen$help("validate") prints it. The method show is also special by name. It is what the console calls to print an object, and the documentation recommends printing the class name explicitly so that subclasses can reuse the method, which is why class(.self)[[1L]] appears instead of the literal "BookRC".

Methods call each other by name (validate() inside initialize()), and the object is searched first, so the names of fields and methods must not collide. For that reason the scenario’s format() became describe(): a method named format would hide base::format() inside every other method of the class. When a method uses another method indirectly, through lapply() or do.call(), the documentation asks for a usingMethods(describe) call, because only the methods that the code analysis sees are installed in the object.

Gen$methods(...) adds a method after the class exists, and the documentation prefers it to the methods argument of setRefClass() for the sake of readability. In the listing b was created before age was defined and can still call it, because methods are looked up when they are first used. The caveat in the documentation concerns methods that were already analysed: a method defined earlier is not re-analysed, so it will not call a new method of the same name unless it is redefined too. The R 3.3.2 NEWS records the repair of an earlier bug in this area (calls to $methods() did not re-analyse previously defined methods). The listing also shows Gen$help() printing the docstring, Gen$methods() returning the names of the inherited helpers (callSuper, copy, field, export, import, initFields, show, trace, untrace, usingMethods, getClass, getRefClass, and two internal ones whose names begin with a dot), and obj$field(name, value) for a field whose name is computed.

The documentation also warns that all the methods of a class belong in the source that defines it. In a package with a namespace the class definition is locked once the package is loaded, so $methods() and $lock() raise an error if they are called later from outside the package.

Aliasing and $copy()

An assignment of a reference object copies the reference. The scenario’s S3 book has value semantics, so the same three lines give different answers:

Inheritance and callSuper()

A subclass is declared with contains = "BookRC". Fields and methods are inherited, a subclass may add fields, and it may override a field only with a subclass of the inherited class. The scenario’s audio book adds a narrator and a length in minutes. An overriding method reaches the method it overrides with callSuper(...). The documentation points out that the arguments of the superclass method must be supplied explicitly: there is no convention that passes them on automatically, unlike NextMethod() for S3 or callNextMethod() for S4.

BookRC <- setRefClass("BookRC", # nolint: object_name_linter.

R6 with R6Class()

R6 is a CRAN package by Winston Chang. Its documentation describes it as an implementation of encapsulated (classical) object-oriented programming that is similar to Reference Classes but more efficient and independent of S4 and the methods package. The first R6 release on CRAN was 1.0.1 (2014-07-17, from the CRAN archive); version 2.0 (2014-08-19) added the portable option and the $set() method; this page was checked against R6 2.6.1, which CRAN lists as published in February 2025. R6 is an add-on package and not part of R: library(R6) is needed, and a package that uses it lists R6 under Imports in its DESCRIPTION.

Public members, initialize() and printing

The R6 version of the book re-implements the same rules in the same order as the Reference Class: initialize trims and converts, then calls validate(). Because R6 fields have no declared class, the conversion with as.integer() is the only thing that keeps year an integer, and nothing stops a later b1$year <- "x"; this is the main thing the Reference Class gives that R6 does not, and the active bindings of the next subsection are how R6 restores it where it matters.

library(R6)
source("scenario.R")

BookR6 <- R6Class("BookR6", # nolint: object_name_linter.
  public = list(
    title = NULL,
    author = NULL,
    isbn = NULL,
    year = NULL,
    genre = NULL,
    pages = NULL,
    initialize = function(title, author = NA_character_,
                          isbn = NA_character_, year = NA_integer_,
                          genre = NA_character_, pages = NA_integer_) {
      self$title <- trimws(title)
      self$author <- trimws(author)
      self$isbn <- if (is.na(isbn)) isbn else normalise_isbn(isbn)
      self$year <- as.integer(year)
      self$genre <- trimws(genre)
      self$pages <- as.integer(pages)
      self$validate()
    },
    validate = function() {
      fields <- list(self$title, self$author, self$isbn,
                     self$year, self$genre, self$pages)

        stop("every field of a book must have length 1", call. = FALSE)

        stop("invalid ISBN-13: ", self$isbn, call. = FALSE)
      }

        stop("implausible year: ", self$year, call. = FALSE)

      invisible(self)
    },

    },
    print = function(...) {
      cat("<BookR6> ", self$format(), "\n", sep = "")

    }

Private members and active bindings

The private list holds members that are reachable only from methods, through private$name; the object itself does not carry them, so b$.isbn is NULL. Active bindings look like fields but call a function every time they are read or assigned: the function takes one argument, which is missing on a read and holds the right-hand side on an assignment. They are always public. The listing moves isbn behind an active binding that normalises and validates on assignment (the Reference Class version validates only in initialize) and adds a read-only age, computed from year and the scenario’s fixed shelf_today.

Inheritance and super

inherit = BookR6 makes a subclass. The expression is captured unevaluated and evaluated when an object is created, so the superclass may be defined in another package. A subclass sees the superclass through super: super$initialize(...) and super$format(...) call the superclass methods, which is the counterpart of callSuper() in Reference Classes. Unlike classical OOP in C++, a subclass can also call the private methods of its superclass through super$. The class vector of an object lists the whole chain, subclass first and "R6" last.

Cloning

R6 objects have reference semantics, so alias <- b is another name for b and a change through one name is seen through the other. $clone() makes an independent copy. The copy is shallow by default: a field that holds another R6 object, an environment or a Reference Class object is copied as a reference, so the clone and the original share it. $clone(deep = TRUE) clones the fields that are R6 objects but, as the documentation says, not environments, Reference Class objects, or reference objects stored inside other data structures such as a list. For any other behaviour a class can define a private method deep_clone(name, value), which is called once for each field and returns the value that the clone gets.

Portable and non-portable classes

By default (portable = TRUE) an R6 class can be inherited from another package, and every member must be reached with self$ or private$. With portable = FALSE an R6 class behaves more like a Reference Class: members are found by name and <<- assigns them, but inheritance across packages does not work well. The difference is the enclosing environment of the methods. In a portable class each method is enclosed in a small environment that holds self (and private, super), and that environment’s parent is given by parent_env (by default the environment where the class was defined); this is why an inherited method that calls a non-exported function of its own package still finds it. In a non-portable class the methods are enclosed in the object’s own environment, so fields are visible by name but a subclass defined in another package cannot see the helper functions that the superclass used. The Portable article explains it with two simulated packages, which this page does not repeat.

library(R6)

    increment = function() {
      n <<- n + 1L

)

Debugging and finalizers

The R6 Debugging article gives the tools: add browser() where the debugger should stop (the article warns that RStudio breakpoints do not work in R6 methods); call debug() on one method of one object, debug(s$getx); or call the generator’s $debug("getx"), which flags the method for objects created afterwards, and $undebug("getx") to stop. trace() can insert a breakpoint at a given place. For Reference Classes, debug(obj$method) and obj$trace(what, browser) do the same. A non-interactive script cannot answer the browser prompt, so the listing only checks the flags with isdebugged(). See Debugging for the interactive tools.

A finalizer is a function that R runs when an object is garbage collected, and also when R exits. In R6 it is a private method named finalize (R6 2.4.0 allowed it to be private; 2.6.0 prints a message when it is public). In Reference Classes it is the method finalize, registered by the object with atexit = TRUE. Both are implemented with reg.finalizer() and are meant for releasing a resource, such as a file or a database connection, that the object owns.

Performance notes

The R6 Performance article compares Reference Classes, R6 and plain environments created by a function. Its conclusions are qualitative and are worth knowing, but the numbers depend on the machine and on the versions, so this page quotes none of them. Creating a Reference Class object is much slower than creating an R6 object, the first Reference Class object in a session costs a large amount of memory that later Reference Class objects share, and reading and writing a field is slower in a Reference Class (partly because of the class check on every assignment). Within R6, a class attribute adds a small cost to $ (so class = FALSE is faster), portable = FALSE avoids the self$ lookup, and cloneable = FALSE saves the memory of the $clone method. The article says that for most uses these differences are negligible; choose between the systems on features, not on speed, and measure (see Performance, Profiling and Benchmarking) before changing the options.

Living with S4 and S3

Because the two systems are built on different foundations, they meet the rest of R differently. A Reference Class is an S4 class: S4 methods defined with setMethod() apply to its objects, setValidity() rules are run by validObject() (and, since R 3.4.0, automatically by the default initialiser), and isVirtualClass("BookRC") is FALSE while is(b, "envRefClass") is TRUE. An R6 object is an S3 object whose class attribute is c("BookR6", "R6"): S3 methods such as length.BookR6, summary.BookR6 and as.character.BookR6 dispatch on it, and S4 needs setOldClass(c("BookR6", "R6")) to treat the class as a registered old class; after that setMethod() and setGeneric() can name "BookR6". The registered class is a virtual S4 class (isVirtualClass("BookR6") is TRUE in the listing): it exists so that S4 can talk about the S3 class, not to create instances.

A worked example: lending books

The scenario needs an object that lends books and takes them back, and whose log of what happened is mutated in place as the day goes by. That is state with an identity: there is one shelf, every part of the program that talks to the shelf must talk to the same one, and a function that lends a book must not have to return a new shelf. The listing builds BookR6 objects from the valid rows of books (it reuses the scenario’s book() for the cleaning and validation), puts them on a ShelfR6, and keeps the loan log as a private character vector. The methods that change the shelf return invisible(self) so that calls can be chained, and each business rule raises an error with a message of its own.

library(R6)
source("scenario.R")

BookR6 <- R6Class("BookR6", # nolint: object_name_linter.
  public = list(
    title = NULL, author = NULL, isbn = NULL, year = NULL,
    genre = NULL, pages = NULL,
    initialize = function(title, author = NA_character_,
                          isbn = NA_character_, year = NA_integer_,
                          genre = NA_character_, pages = NA_integer_) {
      b <- book(title, author, isbn, year, genre, pages)
      for (name in names(b)) {
        self[[name]] <- b[[name]]
      }
    },
    format = function(...) {
      sprintf("%s (%s)", self$title, self$isbn)
    }
  )
)

ShelfR6 <- R6Class("ShelfR6", # nolint: object_name_linter.
  public = list(
    initialize = function(books) {
      names(books) <- vapply(books, \(b) b$isbn, character(1L))
      private$books <- books
    },
    lend = function(isbn, member, on) {
      if (is.null(private$books[[isbn]])) {
        stop("no book with ISBN ", isbn, call. = FALSE)
      }
      if (isbn %in% names(private$out)) {
        stop("already on loan to ", private$out[[isbn]], call. = FALSE)
      }
      private$out[[isbn]] <- member
      private$record("out", isbn, member, on)
      invisible(self)
    },
    give_back = function(isbn, on) {
      if (!isbn %in% names(private$out)) {
        stop("not on loan: ", isbn, call. = FALSE)
      }
      private$record("back", isbn, private$out[[isbn]], on)
      private$out <- private$out[names(private$out) != isbn]
      invisible(self)
    },
    available = function() {
      private$books[!names(private$books) %in% names(private$out)]
    },
    history = function() private$log
  ),
  private = list(
    books = list(),
    out = character(),
    log = character(),
    record = function(what, isbn, member, on) {
      entry <- sprintf("%s %-4s %s %s", format(on), what, isbn, member)
      private$log <- c(private$log, entry)
    }
  )
)

Points to read in the output. length(catalogue) is 14: fourteen of the sixteen ISBNs in books are valid (the scenario’s reference result), and the two rows left out are the empty ISBN and the one with the wrong check digit. The chained call shelf$lend(...)$lend(...) works because lend() returns invisible(self). desk is the same shelf under a second name, so desk$give_back(...) appears in shelf$history(); passing the shelf to a function would behave the same way. Private state (books, out, log) can only be read through the methods, so history() returns a copy of the log vector that callers can keep without affecting the shelf. The vapply() over shelf$available() is the usual way to use a list of reference objects: each element is an object with a method, and vapply() asks each for a string.

The same design in a Reference Class would use fields = list(out = "character", log = "character"), an assignment log <<- c(log, entry) in record(), and callSuper(...) in initialize. The behaviour is identical; what changes is the vocabulary of the class and the cost of creating the objects.

When reference semantics are the right tool

Reference semantics are a tool for state that has an identity and a lifetime. A rule of thumb that fits the examples of this page: use a reference object when "the same one" matters more than "an equal one".

  • Connections and other resources. A file, a database connection or a socket is a handle that must be opened once, used by several pieces of code and closed once. R’s own connections are reference-like (see Connections and the File System), and a class that owns one can open it in initialize, expose methods that use it, and close it in a close() method and, as a safety net, in finalize.

  • Caches and memoisation. A cache must outlive any one call and must be shared by all callers. IsbnCache below keeps its state in an environment; compare it with the closure-based memoisation of Function Factories and Higher-Order Functions, which gets the same effect without a class.

  • Shiny and web servers. A Shiny session and its reactive values are shared mutable objects: reactiveValues() returns an object that is read and written like a list but is modified in place by values$a <- 3 and shared by every reactive that holds it, and modules and plumber routers hold state between requests (see Shiny, plumber and Web APIs). Many of the packages in that area are themselves written with R6, as the listing below shows.

  • Stateful parsers, queues and loggers. A tokenizer that remembers its position, a queue of members waiting for a book, a logger that appends to one file: each is an object whose methods advance or consume its state.

  • Simulation entities. Agents that each have a position and a history, and that are updated one step at a time, are the textbook case in other languages as well.

  public = list(
    hits = 0L,

      private$store <- new.env(parent = emptyenv())

The cases where reference semantics are the wrong tool are as clear:

  • Value-like data. A book, a date, a money amount or a data frame is a value: two books with the same fields are the same book, and nobody wants a function to change the argument it was given. Use a list, an S3, S4 or S7 object and copy-on-modify. The S3 book of the scenario is the model; the table at the end of The S7 Object System compares the four ways of writing it.

  • Code that is run in parallel. Workers started with parallel or future receive a copy of an object (or a forked copy-on-write image), so changes made to a reference object in a worker never reach the parent; see Parallel and Asynchronous Computing.

  • Code that is saved and restored. saveRDS() serialises the environment with its contents, so a restored object is a copy that no longer shares anything with the session it came from (Serialization: RDS, RData and JSON).

  • Pipelines. The native pipe |> passes the result of one step to the next, which reads naturally for functions that take and return values (Pipes and the Native Pipe). Methods that change one object in place are chained with $ and invisible(self) instead, and mixing the two styles in one expression is confusing.

  • Anything that needs to be reasoned about locally. When a function can change what it receives, a reader of the calling code can no longer assume that its variables keep their values. Keep the reference object small, hide its fields behind methods, and document which methods change it.

Reference Classes or R6?

Both systems give the same capabilities in different dress. R6 is the choice in new code that needs mutable objects, for the reasons given in its documentation (lighter objects, private members, cross-package inheritance that works) and because so much infrastructure already uses it. Reference Classes remain the right tool when a class must be an S4 class (typed fields checked on every assignment, setValidity(), setMethod() on the class) or when no add-on package may be used. S4 and S7 are better choices when objects are values and behaviour is attached to functions rather than to objects.

Where older tutorials differ

  • "R5". Older material calls Reference Classes R5. They are not a separate system and R does not use the name; they are setRefClass() in the methods package. The R6 package was named after the joke.

  • Creating objects and adding methods. Older tutorials create objects with Gen$new(...) or new("BookRC", ...) and add methods in separate Gen$methods(...) calls. All of that still works. Since R 3.0.0 the value of setRefClass() is also a function, so BookRC(...) is the same as BookRC$new(...), and supplying the methods in the call to setRefClass() or in one or more $methods() calls has the same effect; the help page recommends the second for readability.

  • Closures with <<- as the only way to keep state. A function that returns a list of functions sharing an environment was the classic idiom for objects with state, and it still works (see Scoping, Environments and Closures). It gives no class, no inheritance and no printing; Reference Classes and R6 are the supported ways to write classes of mutable objects.

  • The proto package. Tutorials from the era before Reference Classes recommend the proto package for prototype-based programming (objects that inherit from other objects). It is still on CRAN, but its last release is from 2016 and R6 or Reference Classes are the usual choices now.

  • R6 in non-portable style. Some tutorials write portable = FALSE everywhere, so that methods can use x and x <<- value without self$. It works in a single package and is a little faster, but it breaks inheritance across packages and, when the habit is carried into a portable class, invites the global-variable mistake described above. The R6 documentation makes portable classes the default for that reason.

  • The lock argument of R6Class(). It was deprecated and has been removed in R6 2.6.0; use lock_objects.

  • Public finalize. Before R6 2.4.0 a finalizer had to be public. Since 2.4.0 it can (and should) be private, and 2.6.0 prints a message for a public one.

  • $copy() and $clone() confusion. Many tutorials show y <- x and then are surprised that y changes x; the cure is $copy() for Reference Classes and $clone() for R6, and for R6 deep = TRUE only when a field is another R6 object (an environment or an object in a list needs a deep_clone method). Both names appear in older material for the other system.

  • "Reference classes are slow, so avoid them." The R6 performance article shows that creating a Reference Class object costs more than an R6 object and field access is slower. It does not say that Reference Classes are unusable, and R Core has not deprecated them: there is no NEWS entry about them in R 4.0.0 to 4.6.1.

  • Typed fields in R6. Tutorials sometimes say that R6 has no way to check a field. The usual way is an active binding that validates assignment, as isbn does above.
