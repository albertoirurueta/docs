Parallel and Asynchronous Computing

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. The core of this page is base R: the parallel package that ships with R (version 4.6.1, the same as R itself). Add-on packages are named with the versions they were checked against: future 1.80.0 (with parallelly 1.48.0, which it installs), future.apply 1.21.0, mirai 2.7.3, later 1.4.8, promises 1.5.0, callr 3.8.0 and data.table 1.18.6.1; purrr 1.2.2 and Shiny 1.14.0 are named where their parallel features come up, and the lintr 3.4.0 default linters were used only to check the scripts. Several packages named in the text were not available in the test image and are described, not run, wherever they appear: furrr, doParallel and foreach, RhpcBLASctl, progressr, and carrier (which purrr’s in_parallel() needs). R runs one stream of R code per process. Doing more than one thing at a time therefore means starting more processes, or calling libraries that use threads inside compiled code. This page explains the first, in the three flavours R offers today: copying the running process (forking), starting fresh R sessions that talk over sockets, and the frameworks future and mirai that wrap those ideas in a different interface. It explains how to give every worker reproducible random numbers, then how R code can wait for something without blocking (the later and promises packages, and a background R process from callr), and last how the threads of a multi-threaded BLAS and of data.table interact with all of it.

Every example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines that start with #> are what it printed. The scripts also pass the default lintr linters; a # nolint: comment marks a line where the idiom on show is what a default linter dislikes. Every example uses two workers, the smallest number that is parallel. Timings depend on the machine, on the BLAS and on what else is running, so no example prints seconds: where speed matters the script prints a comparison that is robust to the machine (for example t_serial / t_forked > 1.5, with tasks made of Sys.sleep() so that the answer does not depend on the speed of the CPU). The number of cores of the machine that ran the examples is never printed either. The names books, loans, shelf_today, loan_days and the book() constructor come from the running library-shelf scenario described on the section index: a script that needs them starts with source("scenario.R"). The work that is parallelised is always the same: the share of overdue loans of each member of the shelf, and a bootstrap of the mean loan duration. Where a message contains quotation marks, they are the typographic quotes R prints in a UTF-8 locale.

The page leans on The apply Family and Functionals and Vectorisation and Iteration for lapply() and vapply(), which every parallel function below imitates. It continues the story of Distributions and Random Numbers, which introduced the L’Ecuyer-CMRG generator and its streams but ran them on one process. The first thing to do before parallelising anything is to find out what is slow, which is the subject of Performance, Profiling and Benchmarking; the copying that makes a worker start with a copy of your data is described in Memory and Copy Semantics; and the compiled-code route to speed, which is often better than parallel R, is in Interfacing C, C++ and Fortran.

R, processes and threads

R evaluates one expression at a time in one thread. The vignette of the parallel package says why workers are processes and not threads: in principle the workers could be implemented by threads, but only in principle, because the R interpreter is not thread-safe (The parallel package vignette, footnote to the introduction). A loop in a plain R session keeps one core busy however many cores the machine has. What does use several cores inside one R process is compiled code that starts its own threads: a multi-threaded BLAS for matrix algebra, OpenMP loops in packages such as data.table, and a few packages with their own thread pools. These are the subject of the last section.

The parallel package was first included in R 2.14.0. It merged two older CRAN packages, multicore (forking) and snow (sockets, "simple network of workstations"), and added the random-number handling described below. Its vignette describes the model that every function on this page follows, whatever its name: start M worker processes and initialise them; send them the data; split the task into chunks and send each worker its chunk with the R code; wait for the results; repeat; shut the workers down. The tasks must be unrelated: parallel R of this kind is "coarse-grained", suited to running the same function on many sets of data, such as the bootstrap replicates, simulations and per-group fits that fill the rest of this page. The vignette also says that all methods of communication use serialize() and unserialize() to move R objects between processes, which has limits (typically hundreds of millions of elements) that a well-designed parallel algorithm should not approach (R documentation: serialize).

Three consequences follow, and they explain most of what goes wrong in practice.

  • Starting workers and moving data costs time, so a task has to be long enough to repay it. Parallelising a million tasks of a microsecond each makes the program slower.

  • A worker is a separate process with its own memory and its own copy of whatever it was sent. Changing a variable in a worker never changes it in the master, and a worker only sees what it was given or what it can load itself.

  • The workers compete for the machine. Two workers that each start a multi-threaded BLAS or a threaded data.table can ask for more threads than there are cores, and the result is slower than running serially.

The unit of work

All the examples use one function. overdue_rate() takes the loans of one member and returns the share of them that are overdue: a returned loan is overdue when it was kept more than days days, and a loan still out is measured against today. It takes today and days as arguments and uses no global variable, which is what makes it safe to send to another process. The script cleans the member names, drops the empty one, and splits loans into one data frame per member, so there is one task per member.

source("scenario.R")

# The unit of work: the share of one member's loans that are overdue.
# It takes everything it needs as arguments and uses no globals.
overdue_rate <- function(rows, today, days) {
  end <- rows$return_date
  end[is.na(end)] <- today
  mean(as.integer(end - rows$loan_date) > days, na.rm = TRUE)
}

# Clean the member names, drop the empty one, and split loans by member.
members <- tolower(trimws(loans$member))
keep <- nzchar(members)
by_member <- split(loans[keep, ], members[keep])
length(by_member)

Two ways to make a worker

There are two ways to get a worker process, and the choice decides what the worker knows when it starts. The vignette lists three and describes the third (message-passing systems such as MPI, and grid schedulers) as outside its scope; the first two cover a laptop or one server.

Forking is a feature of POSIX operating systems (Linux and macOS, not Windows). The fork() system call creates a child process that is a complete copy of the parent: the workspace, the attached packages, the options and the state of the random number generator. Because the operating system shares the memory pages between parent and child until one of them writes to a page ("copy on write"), forking is fast and costs little memory. The child needs nothing to be sent: the code and the data are simply there. Results come back through a pipe that the parent opened before forking. The price is that the child shares everything else too, including the graphical user interface, open graphics devices and open files, which the vignette says can cause havoc, and the threads of any multi-threaded library, because only the thread that called fork() survives in the child. This is mclapply(), pvec(), mcparallel() and makeForkCluster(), and it is what the future package calls a "multicore" backend.

Sockets start a new R session for each worker, using Rscript, and connect to it over a socket on localhost (or, for a real cluster, on another machine through ssh). The worker is a clean R session with the default packages and an empty workspace: whatever it needs has to be sent over the socket, with clusterExport() or as arguments, or loaded there with clusterEvalQ(). Starting the workers takes a fraction of a second each, and sending data costs serialisation. In return it works everywhere, including Windows, it is safe with GUIs and threads, and the same code can run on workers on other machines. This is makeCluster() (type "PSOCK", the default), and what future calls "multisession".

The left half is a fork: the children exist the moment fork() returns and already hold everything the parent held. The right half is a socket cluster: each worker is started from nothing, so every object it needs has to travel over a socket. The cost model follows. A fork is cheap to start and expensive to share a GUI or threads with; a socket worker is cheap to share (it shares nothing) and has to be fed. makeForkCluster() is the hybrid: a socket cluster whose workers are forks, so it has the speed of a fork and the parLapply() interface of a cluster. The parallel documentation states the rule for Windows in one line each: mclapply() relies on forking and is not available there unless mc.cores = 1, and makeForkCluster() is only a stub.

Forking: mclapply and its relatives

mclapply

mclapply(X, FUN, ..., mc.cores) is lapply() with the elements shared among forked children. Its help page says that it relies on forking and is therefore not available on Windows unless mc.cores = 1; on Windows it exists only as a stub that calls lapply() (the vignette says so). The default of mc.cores is getOption("mc.cores", 2L), and the option takes its initial value from the environment variable MC_CORES when the package is loaded, so a forked job uses two cores unless told otherwise (the vignette notes that this differs from the multicore package). Setting mc.cores to 1 does not fork at all: the function calls lapply(). The help page adds that parallelisation requires at least two cores, so mc.cores = 1 is the standard way to switch parallel execution off for debugging.

The script below checks the four facts that are easy to forget. The result is identical to lapply(): same list, same names. The work ran in child processes (their process ids differ from the parent’s). mc.cores = 1 gives the same answer without forking. And with tasks that last a quarter of a second, two cores make the job clearly faster than one; the script prints only whether the speed-up is more than 1.5, because the exact ratio depends on the machine and what else is running.

Arguments that change what happens

Four of the arguments of mclapply() decide how the work is shared and what happens when a task fails.

  • mc.preschedule (default TRUE) deals the values of X out to the cores in turn, value 1 to core 1, value 2 to core 2, value mc.cores + 1 to core 1 again, and forks one process per core, each handling its share. With FALSE one process is forked for each value, and the parent waits for a child to finish before it forks the next once mc.cores are running. The help page recommends the first for short tasks or many values, and the second for tasks with a high variance of completion time and not too many values compared with mc.cores: it is a load-balancing mode, at the price of a fork per value.

  • mc.set.seed (default TRUE) controls the random number generator in the children; see Reproducible streams with forking.

  • mc.silent suppresses the standard output of the children (standard error is not affected), and mc.cleanup kills the children when the call is interrupted (the default is to send SIGTERM; a signal number can be given instead).

  • mc.allow.recursive (default TRUE): if it is false, an mclapply() called inside a child uses that child and does not fork again. The vignette recalls a case of mclapply() called recursively that generated 2n + n^2 processes on a machine estimated to have n = 16 cores.

The second script shows prescheduling, error handling and what a child cannot do. Each forked job runs inside try(..., silent = TRUE), so an error becomes a "try-error" value in the result and a warning, and because a job usually covers several values, all of them are marked, not only the one that failed (the help page says so). A child that is killed delivers nothing and its values are NULL; for that reason FUN should never return NULL, or the two cases cannot be told apart. And changes made in a child, here a counter incremented with <<-, never reach the parent: the parent’s copy was not touched.

library(parallel)

# mc.preschedule = TRUE (the default): the values are dealt out to the
# cores in turn, one forked process per core.
pids <- unlist(mclapply(1:6, \(i) Sys.getpid(), mc.cores = 2))
match(pids, unique(pids))
#> [1] 1 2 1 2 1 2

# mc.preschedule = FALSE: one forked process per value.
pids <- unlist(
  mclapply(1:6, \(i) Sys.getpid(), mc.cores = 2, mc.preschedule = FALSE)
)
length(unique(pids))
#> [1] 6

With the default mc.preschedule = TRUE the values 1, 3 and 5 ran in the first child and 2, 4 and 6 in the second, which is the pattern 1 2 1 2 1 2. The error in value 3 therefore also took value 1 with it; with mc.preschedule = FALSE only value 3 failed. The text of the warning is the one the help page implies: scheduled core 1 encountered error in user code, all values of the job will be affected. The last check is mcaffinity(), which returns the CPUs the process may run on (or NULL where the system gives no access to them); the argument affinity.list of mclapply(), which needs mc.preschedule = FALSE, can pin the value i to the CPUs listed in element i. It is for tuning on a known machine and is not used further here.

pvec, mcparallel and mccollect

pvec(v, FUN, ...) is the variant for functions that are already vectorised. It splits the vector into as many nearly equal pieces as there are cores, calls FUN once on each piece in a forked child and joins the pieces. FUN must be a pure vectorised map: it takes a vector and returns a vector of exactly the same length, and the value for an element must not depend on which piece the element is in. is_valid_isbn13() from the scenario is such a function. The help page warns that side effects of FUN are not collected from the children, and it warns when FUN is not a vectorised map.

mcparallel(expr) is the low-level building block: it forks one child that evaluates the expression and returns at once with a "parallelJob" object; mccollect(jobs) waits for the results (all jobs if none are named) and returns a list named by the name given to mcparallel() or else by the process ids. With wait = FALSE, mccollect() only looks, for timeout seconds, and returns NULL if nothing is ready: it is the polling interface. The help page notes that expr must not return NULL, because mccollect() uses NULL to signal an error, and that raw vectors cannot be returned. mcmapply() and mcMap() are the forking versions of mapply() and Map(); since R 4.0.0 mcmapply() returns a list, and never simplifies, whenever it must hold "try-error" values.

source("scenario.R")
library(parallel)

# pvec() splits a vector, runs the function on each piece, and joins the
# pieces. The function must be a pure vectorised map.
valid <- pvec(loans$isbn, is_valid_isbn13, mc.cores = 2)
identical(valid, is_valid_isbn13(loans$isbn))
#> [1] TRUE

When not to fork

The help pages of mclapply(), mcparallel() and makeForkCluster() are explicit about the limits of forking. Using these functions in a GUI or an embedded environment is strongly discouraged: the parent and the children share the same GUI, which will likely cause chaos and possibly crashes, and children should never use on-screen graphics devices (the page adds that the Tcl/Tk package counts as a GUI because it runs an event loop). RStudio is the common case, and the future package disables forking there for the same reason (see Plans). Using forking with multi-threaded libraries or packages is strongly discouraged as well, and the help page suggests a non-fork cluster if in doubt; the page for the low-level mcfork() gives the details. Other limits: the operating system limits the number of open files and processes, so using more than about 100 cores can fail with the error unable to create a pipe unless the limit on open file descriptors is raised; children share the per-session temporary directory tempdir() with the parent (before R 2.14.1 two of them could even pick the same temporary file name); and the results come back serialised through a pipe, so returning very large objects from children is inefficient, and before R 3.4.0 on a 32-bit platform they were limited to 2^31 - 1 bytes.

Where none of that applies, forking is the least effort of the three flavours on this page: nothing has to be exported, because the children already hold the workspace. That is also its trap. Code that works with mclapply() because it silently relies on a global variable fails when it is moved to a socket cluster, a future plan or a Windows machine, where there is no copy of the global environment to rely on.

Socket clusters

makeCluster and stopCluster

makeCluster(spec, type) creates a cluster of one of the registered types. The default type, "PSOCK", calls makePSOCKcluster(), which runs Rscript for each worker and has the worker connect back to a socket on the master; spec is a number of workers on localhost or a character vector of host names. The result is an object of class c("SOCKcluster", "cluster"). Every function that takes a cluster takes it as its first argument, called cl.

The cluster is a pool of persistent workers: mclapply() sets up a pool just for one computation, whereas a cluster lives until stopCluster(cl), serving any number of parLapply() calls (the vignette’s distinction). Two consequences follow. The workers keep their workspaces between calls, so objects accumulate and packages stay attached; they are state, and the script below shows it with a counter. And a cluster you forget to stop stays alive as a set of idle processes holding sockets. The help page says the workers terminate themselves when the socket they listen on becomes unavailable, which should happen when the master session ends; that is a safety net, not a plan. Write on.exit(stopCluster(cl)) in the function that makes the cluster, as with_cluster() does at the end of the script.

clusterCall(cl, fun, ...) calls the function with the same arguments on every worker, clusterEvalQ(cl, expr) evaluates a literal expression on every worker (an evalq() for the cluster), and clusterApply(cl, x, fun, ...) sends element i of x to worker i, recycling the workers. All return a list with one element per worker (or per element of x), so a value you do not want is best wrapped in invisible() or ended with NULL, as in the script. parLapply(cl, X, fun, ...) is built on clusterApply(): it splits X into one consecutive chunk per worker, runs lapply() on each chunk and joins the results, so a call needs only one round trip per worker. If any worker produces an error, the master signals an error.

Getting code and data to the workers

A fresh worker has the base packages and an empty global environment. A function you send is serialised with its arguments, but the variables it refers to are not captured: R looks them up where the function is evaluated, and for a function defined at top level, that place is the worker’s own global environment. The error below is the most common one in parallel R, and the message names the first variable that is missing. It says "2 nodes produced errors" because every worker failed in the same way, and the call it comes from is checkForRemoteErrors(val), which tells you nothing about which of your functions it was.

There are three ways to fix it and they have different costs.

  • Pass it as an argument. Anything in ... is sent along with the function. It is explicit and works everywhere (sockets, forks, future, mirai); the data is serialised on every call, which is fine for a number and slow for a large object. This is the first choice.

  • clusterExport(cl, varlist, envir) copies the named variables from envir to the global environment of every worker, once. Use it for something large that every call needs. The default envir is the global environment, so inside a function the variable is local and clusterExport() fails on the master with object 'secret' not found; give envir = environment().

  • clusterEvalQ(cl, expr) runs code on every worker, which is how you load packages (library(stats)) or define helper functions there.

Do not forget that a function defined inside another function carries its enclosing environment when it is serialised. A task made by a factory function can drag along every local variable of the factory, even an argument the task never uses, and the whole object is sent to every worker. The last lines of the script measure that with serialize(), without timing anything: the closure that captured an 8 MB vector serialises to more than 8 MB, while a function defined at top level serialises to a few hundred bytes, because the global environment is sent as a reference and not as a copy.

The load-balancing versions are for tasks whose durations differ a lot: the worker that finishes first gets the next task. Two caveats come with them. The result of a computation that draws random numbers cannot be reproduced when the work is balanced dynamically, because which worker runs which task changes from run to run (the help pages and the vignette both say so), and more communication costs more time than one chunk per worker. The vignette suggests having substantially more tasks than workers, but not by a factor of 100.

The script shows each in turn. The static functions put element 1 on worker 1, element 2 on worker 2, then element 3 on worker 1 again (1 2 1 2 1 2). clusterSplit(cl, 1:7) shows the chunks parLapply() would use. All the versions return the same list as lapply(); the load-balanced clusterApplyLB() drops the names, as clusterApply() does, so its result is compared with unname(serial). clusterMap() is used with a function passed as a value and not by name, which matters: the function body of an anonymous function that calls overdue_rate() would look for it on the worker and not find it, for the reason given above. The last lines show a trap of the ... of all these functions: an extra argument you name is matched against the formals of the function first, with partial matching. parSapply(cl, 1:3, \(i, x) i + x, x = 10) fails because x also names a formal argument of the clusterApply() that parLapply() calls internally. Cluster types, defaults, logging and timeouts

registerClusterType() with no arguments lists the registered types. In R 4.6.1 they are "PSOCK", "FORK", "MIRAI", "MPI", "RPSOCK" and "SOCK"; the last four need the packages named in the help page (snow for "SOCK" and "MPI", parallelly for "RPSOCK", mirai for "MIRAI"). The NEWS file of R 4.x does not mention when registerClusterType() and the extra types were added, and the mirai documentation says that the "MIRAI" type is an official cluster type in R 4.5, so this page does not give an exact version; the type is shown in Mirai and the parallel package.

makeCluster(2, type = "FORK") is makeForkCluster(2): a socket cluster whose workers are forks of the master, so they inherit its workspace as it is at that moment (the script shows that a variable created after the fork does not exist on the workers). It is not available on Windows and shares the cautions about forking above.

setDefaultCluster(cl) registers a cluster as the default for the session, so the cl argument of parLapply() and friends can be NULL or omitted; getDefaultCluster() returns it, and stopping that cluster, or setDefaultCluster(NULL), removes it. The convenience has a cost: a hidden global is exactly what makes code hard to reuse, so it suits scripts better than packages.

When things go wrong

An error on a worker reaches the master as one error whose message starts with the number of nodes that failed and then gives the first message. The call recorded in the condition is always checkForRemoteErrors(val): the traceback of the worker is lost. When debugging, run the same function with lapply() on a small input first. The messages worth recognising are in the script: a task calling a function that the worker does not have (could not find function), a package missing from the worker (there is no package called), a worker whose process died (error reading from connection), and a cluster that was already stopped (invalid connection). After a worker has died the other workers are still alive but the cluster object is damaged; stop it (try(stopCluster(cl))) and make a new one.

How many workers?

Not detectCores(). Reproducible random numbers in parallel

Random numbers are where parallel code most often goes quietly wrong. A worker is a separate R process with its own .Random.seed, and three things can happen to it, none of them good by default. A forked child starts with a copy of the parent’s generator state, so if the parent has drawn any numbers, every child continues the same sequence and all of them draw the same numbers. A fresh PSOCK worker seeds itself from the clock and its process id, so the numbers are different in every worker and different in every run: independent with very high probability, but not reproducible. And seeding each worker with set.seed(i) for different i is the tempting repair, but it does not guarantee that the streams are independent: for the default Mersenne-Twister generator nothing says that streams started from different seeds do not overlap. The vignette of the parallel package describes the problem and the repair, which is to use one generator and place the streams far apart in its sequence.

The generator is L’Ecuyer-CMRG (RNGkind("L'Ecuyer-CMRG")), a combined multiple-recursive generator of L’Ecuyer (1999) with a period of about 2^191 and a seed of six integers (seven in .Random.seed, with the leading code). Unlike the Mersenne-Twister, it is simple to advance by a fixed number of steps. The package implements L’Ecuyer, Simard, Chen and Kelton (2002): the sequence is cut into streams of length 2^127, each cut again into substreams of length 2^76, and each parallel computation gets a stream (and may use substreams) so that the numbers never get in step. nextRNGStream(seed) and nextRNGSubStream(seed) take a seed of this generator and return the seed of the next stream or substream; the result can be assigned to .Random.seed. Distributions and Random Numbers showed the streams on one process; the three ways to use them in parallel follow.

  • clusterSetRNGStream(cl, iseed) selects L’Ecuyer-CMRG in the master, calls set.seed(iseed) (or, if iseed is NULL, uses the current seed of the master) and gives each worker the next stream.

  • mclapply() and mcparallel() with mc.set.seed = TRUE give each forked child the next stream, provided the generator is L’Ecuyer-CMRG; mc.reset.stream() restarts the sequence of streams after set.seed(), and mclapply() and pvec() call it themselves.

  • Hand-made seeds, one per task, as in the last example of this section, which is the one whose result does not depend on the number of workers.

A socket cluster: clusterSetRNGStream

The script bootstraps the mean loan duration of the returned loans. It runs the same six replicates three times on a cluster: first without seeding, which differs between the two runs; then twice after clusterSetRNGStream(cl, 282), which gives identical results; then with a different seed, which differs. Two side effects are worth seeing. clusterSetRNGStream() also changed the generator of the master (the RNGkind() line shows "L'Ecuyer-CMRG"), so call it after any code in the master that depends on the default generator. And the result depends on the number of workers: with three workers the same six replicates are shared differently and the streams differ, so the numbers differ even with the same seed. A seed fixes the streams of the workers, not the stream of each task.

The argument that carries the data is called values and not x, for the partial-matching reason given above.

source("scenario.R")
library(parallel)

# The loan durations, in days, of the loans that were returned.
durations <- as.integer(loans$return_date - loans$loan_date)
durations <- durations[!is.na(durations) & durations >= 0L]

# One bootstrap replicate: the mean of a resample.
boot_mean <- function(i, values) mean(sample(values, replace = TRUE))

# Without seeding, every run draws different numbers.
cl <- makeCluster(2)

Forking: mc.set.seed and mc.reset.stream

For forked children the rule is stricter, because the three cases of the help page of mcparallel() all show up in one script. With the generator set to L’Ecuyer-CMRG and a seed set, mclapply() gives the children the next streams and the result is reproducible, as long as the same tasks go to the first, second, …​ child: the first lines of the script show this, and also that three cores give different numbers from two. With the default Mersenne-Twister and mc.set.seed = TRUE, the children are seeded from the clock and process id: the code of the unexported function parallel:::mc.set.stream() removes .Random.seed in the child for any generator other than L’Ecuyer-CMRG, so the child draws a fresh seed when it first needs one. The children differ from each other and the run cannot be reproduced. (The help page of mcparallel() says the behaviour with mc.set.seed = TRUE is different only for L’Ecuyer-CMRG; the script shows what happens in practice.) And with mc.set.seed = FALSE the children inherit the state of the parent: once the parent has a generator state (here made by set.seed()), every child draws the same numbers, which is almost never what you want. The help page of mclapply() makes its example reproducible with set.seed(123, "L'Ecuyer"), which sets the kind and the seed in one call. mc.reset.stream() after setting the seed makes mcparallel() reproducible in the same way (the help page notes that it does not set the seed in the master, so it does not affect the fall-back to serial execution when mc.cores = 1).

One stream per task

Both results above depend on how many workers ran. For a result that is the same whatever ran the tasks, give each task its stream, not each worker. The master makes one seed per task with nextRNGStream() from a single set.seed(), passes the seed as an argument, and the task installs it as its .Random.seed before drawing. The script runs the six replicates in a loop, with mclapply(), on a cluster of two workers and on a cluster of three, and the four results are identical. RNGkind("L'Ecuyer-CMRG") appears inside the task because a fresh worker starts with the Mersenne-Twister and a .Random.seed of seven integers means something else there; assigning it first selects the right generator. This is also what the future and mirai frameworks do for you, as shown below.

source("scenario.R")
library(parallel)

durations <- as.integer(loans$return_date - loans$loan_date)

# One seed per task, made in the master from a single set.seed().
make_streams <- function(n, seed) {
  RNGkind("L'Ecuyer-CMRG")
  set.seed(seed)
  stream <- get(".Random.seed", envir = globalenv())
  out <- vector("list", n)
  for (i in seq_len(n)) {
    out[[i]] <- stream
    stream <- nextRNGStream(stream)
  }
  out
}

# The task installs its own stream, whatever process runs it.
boot_task <- function(stream, values) {
  RNGkind("L'Ecuyer-CMRG")
  assign(".Random.seed", # nolint: object_name_linter.
         stream, envir = globalenv())
  mean(sample(values, replace = TRUE))
}

The future package

The future package (version 1.80.0 here) puts one interface over all of the above. A future is a value that is computed somewhere else and fetched when needed. You write the code once, in terms of future() and value(), and the user says where it runs with plan(): in this process, in background R sessions, in forked processes, on a cluster. The help page of future() puts the point in one sentence: any R code using futures remains the same regardless of these settings, and there is no need to modify the code when switching from sequential to parallel processing. Sequential evaluation is the default, so code written with futures runs everywhere, in parallel only when somebody asks.

Plans, futures and values

The built-in plans (help page plan) are sequential (in this process), multisession (background R sessions on this machine, which are PSOCK workers), multicore (forked processes; not on Windows) and cluster (R sessions on one or more machines). Other backends live in other packages, among them future.callr, future.mirai and future.batchtools for job schedulers. The documentation tells package authors to leave the plan to the user: do not call plan() in a package, and if a function must change it, undo the change on exit. For multisession, workers defaults to availableCores(constraints = "connections-16"), which keeps 16 connection slots free on machines with very many cores (future 1.67.0).

future(expr) starts evaluating expr at once (lazy = FALSE is the default) and returns a future; resolved(f) asks without waiting whether it has finished; value(f) waits for it and returns the value. x %<-% expr is the future assignment: it creates a future and binds x to a promise that fetches the value when x is first used. nbrOfWorkers() is the number of workers of the current plan. plan() returns the current plan when called with no argument and the previous plan, invisibly, when it sets a new one. Printing a plan is not done in the script: in future 1.80.0 it starts the backend and prints the details of the machine, so the script asks inherits(plan(), "sequential") instead.

The behaviour the script shows is the part of the contract that matters. Globals are found by inspecting the code of the expression (globals = TRUE is the default) and are copied to the worker: the future g needed the function overdue_days() and, through it, loans and loan_days, and the script reads their names from g$globals. (This is the automatic export that clusterExport() does by hand; it also means a large global is copied every time.) Standard output and conditions (messages and warnings) raised on the worker are relayed when value() is called; the script shows cat() output arriving and a message handled by withCallingHandlers() in the master. Errors are re-signalled by value(). And the plan is put back with plan(sequential) at the end, which is the habit to keep: a plan set in a script stays set for the rest of the session.

Changing the plan safely

A plan should be set once, at the top of a script. When a block of code or a function must use a different plan temporarily, with(plan(multisession, workers = 2), { ... }) evaluates the block under the temporary plan and then restores the previous one, and with(plan(...), local = TRUE) inside a function lasts until the function exits (future 1.40.0, April 2025). The older idiom saves the old plan, old_plan <- plan(multisession), and restores it with plan(old_plan). The script also shows the other two plans in use. parallelly::supportsMulticore() says whether forking is supported and allowed: it is false on Windows and in RStudio, where future disables forking, and the help page of multicore quotes a member of R Core advising against forking in packages except as an option the user sets. On a system without support, plan(multicore) falls back to sequential, with a one-time warning in RStudio. plan(cluster, workers = cl) accepts a cluster you made yourself, here with parallel::makeCluster(), so it can be shared with code that does not use futures; value(f) %in% unlist(parallel::clusterCall(cl, Sys.getpid)) checks that the future ran on one of its workers. Finally plan(multiprocess), which older tutorials use, was deprecated in future 1.20.0 (2020), declared defunct in 1.32.0 and removed in 1.33.0 (2023): use multisession, or multicore where forking is allowed.

Random numbers in futures

The future package takes random numbers seriously, because they are the commonest silent error in parallel code. A future that draws random numbers without having declared it with seed = is detected, and the value comes with a warning: UNRELIABLE VALUE: Future (<unnamed-n>) unexpectedly generated random numbers without specifying argument 'seed'. followed by an explanation (the script shortens the label that contains a counter and removes the trailing session identifiers, which differ every run). The class of the warning is RngFutureWarning. The option future.rng.onMisuse controls the check: "warning" is the default, "ignore" disables it, and "error" makes it an error of class RngFutureError.

The remedy is the seed argument. seed = TRUE gives the future a parallel-safe L’Ecuyer-CMRG stream; seed = 282, a single integer, gives a fixed stream from which the result is reproducible; a full seed of seven integers can be given as well. This is the same generator and the same streams as in the previous section, assigned for you and per future, not per worker.

furrr

furrr (not installed in the test image, so nothing here was run) combines the purrr mapping functions with future: future_map(), future_map_dbl(), future_map2(), future_pmap(), future_walk(), future_imap() and their variants are near drop-in replacements for map() and its relatives, run according to the current plan(). Random numbers are handled with the .options argument: future_map(x, f, .options = furrr_options(seed = TRUE)), with an integer to fix the seed, and its documentation guarantees the same results whatever the type of future and scheduling (furrr package documentation: furrr_options). furrr shares the globals detection of future, and its documentation has an article on common gotchas (furrr package documentation). Newer code has the alternative of purrr::in_parallel(), described with mirai in the next section.

The mirai package

mirai (2.7.3; the word is Japanese for "future") is a newer framework for the same job, built for low latency and for scaling from a laptop to a scheduler. Its documentation describes the architecture: mirai() sends tasks to daemons, persistent R worker processes that dial in to the host; a dispatcher thread schedules the tasks first in, first out, and handles cancellation. The model differs from a future in three ways that show in the code. The code of a task runs in a clean environment, so everything it needs is named in the call. The result is read from the object, m$data, with an unresolved state that is a logical NA, or collected with m[], and there are no value() calls to forget. And errors and timeouts are values, not conditions: an error comes back as a miraiError and a timeout as the integer 5, so a batch of tasks never loses the tasks that succeeded.

Daemons and mirai()

daemons(n) starts n daemons on the local machine and returns invisibly TRUE (daemons(0) returns FALSE and resets). Calling daemons() again replaces the existing ones, and the daemons exit by themselves when the session ends. Without any daemons, mirai() still works but starts a new background R process for every request, which is slow; mirai_map() refuses to run and says so. mirai(.expr, ..., .args, .timeout) evaluates the expression in a daemon and returns at once. Objects named in ... are assigned to the global environment of the daemon, as if the code ran in your global environment, so they are the way to pass helper functions that call each other; objects in .args stay local to the evaluation. .timeout is in milliseconds: the task resolves to the integer 5 (printed 'errorValue' int 5 | Timed out) if it takes longer. unresolved(m) is TRUE while the task runs and is meant for while and if; call_mirai(m) waits; m[] waits and returns the value; is_mirai_error() and is_error_value() classify the result. The help page lists the other error value, 19 (connection reset), which a task gets if its daemon dies or if daemons(0) is called while it is unresolved.

mirai_map(.x, .f, ..., .args) maps over a vector, list, matrix or data frame (over the rows of the last two), one mirai per element, scheduled to minimise the total time. The arguments are not those of parLapply(): named arguments in ... are objects that .f references and that daemons must have (they go to the global environment of the daemons), while .args is a list of constant arguments passed to .f. Mixing them up is the mistake on the list in the script: y = 10 in ... is not an argument of the function, and the result is the error argument "y" is missing, with no default, returned for every element. The collection options are written in the brackets: x[] returns a list; x[.flat] flattens to a vector and fails on an error or a mixed type; x[.progress] shows a progress bar; x[.stop] stops at the first failure and cancels the rest. A failure in one element does not lose the others, as the script shows with list(1, "a", 3), so only the failures need to be rerun. everywhere() evaluates an expression on every daemon, to load a package or set an option.

Random numbers have their own argument. daemons(n, seed = NULL) gives each daemon a L’Ecuyer-CMRG stream, which is sound but not reproducible; an integer seed makes a stream per mirai, so that mirai_map() gives the same numbers whatever the number of daemons and whichever daemon runs which task. The script runs the same four draws with two daemons and with three and compares them. (The help page of daemons() documents this argument.)

Asynchronous without parallel: later, promises and callr

"Asynchronous" and "parallel" are different words, and R needs both. Parallel means several computations progress at the same time on several cores. Asynchronous means that you ask for something, carry on, and are told when the answer arrives; it can be built on one thread. The parallel, future and mirai packages above are asynchronous when you use mcparallel(), future() or mirai() and fetch later. The packages in this section are asynchronous in the second sense, for code that must stay responsive: a Shiny session, a plumber API, an interactive console.

later and promises

The later package (1.4.8) is an event loop for R. later(func, delay) schedules a function to run after a delay in seconds, like JavaScript’s setTimeout; R is single-threaded, so there is no promise that the function runs exactly on time, only that at least the delay has passed. By default scheduled work runs only when no other R code is on the stack, which means when R is sitting at the console prompt; run_now() lets a script, which never reaches the prompt, run the work that is due, and loop_empty() says whether anything is left. The value returned by later() is a function that cancels the callback. The script shows that the function does not run until run_now().

The promises package (1.5.0) represents a value that is not there yet. promise(\(resolve, reject) ...) creates a promise from a function that starts the work and calls resolve(value) or reject(reason) when it finishes; the help page says it is mainly for package authors. You consume it with then(promise, onFulfilled, onRejected), catch() and finally(), which return new promises and so chain with the native pipe: promise |> then(f) |> catch(g). The older promise pipes, %...>% for success and %...!% for errors, are marked superseded in the help page of promises 1.5.0, because the native pipe and the function shorthand made then() and catch() as short. The key point of the script is the order of output: the line after then() prints before the value, because then() only registers what to do and returns. A mirai is a promise through as.promise() (mirai needs the event loop to deliver it, so the script runs the loop until the task has resolved), and future_promise() is a promise-friendly future() that returns a promise and keeps the event loop free. The mirai package has an article on Shiny and plumber (mirai package documentation: Promises (Shiny and Plumber)).

Threads inside a process: BLAS and data.table

A single R process can use several cores without any of the machinery above, when the compiled code it calls is multi-threaded. Two cases matter, and both interact with the workers you start.

BLAS and LAPACK. R does not implement matrix algebra itself; %*%, crossprod(), solve(), chol(), eigen() and svd() end up in the BLAS and LAPACK libraries, which the Installation and Administration manual says can be replaced by external, usually tuned, libraries (R Installation and Administration: Linear algebra). Several of those, among them OpenBLAS, Intel MKL and Apple’s Accelerate, use multiple threads. The test image has an OpenBLAS build. The manual warns about three consequences: R’s profiling (which uses the SIGPROF signal) may cause problems with a multi-threaded BLAS; a multi-threaded BLAS can take more CPU time, and even more elapsed time, than a single-threaded one, especially on a machine running other tasks; and BLAS calls inside threaded code, such as OpenMP sections in packages like mgcv, may be unsafe with some external libraries. The number of threads is set by environment variables read when the library is loaded: OPENBLAS_NUM_THREADS or OMP_NUM_THREADS for OpenBLAS (depending on the build, as the manual explains for the Fedora packages), and MKL_NUM_THREADS or OMP_NUM_THREADS for MKL (R Installation and Administration: OpenBLAS and BLIS). Changing the variable inside a running session is too late for the library. The RhpcBLASctl package (not installed in the test image, so not run) exists to change the BLAS thread count at run time, with functions such as blas_set_num_threads() and omp_set_num_threads(); setting the variable before the worker starts, as below, needs no package.

data.table. data.table (1.18.6.1) parallelises fread(), fwrite(), grouping, ordering and other operations with OpenMP. Its help page for setDTthreads() says the number of threads is initialised when data.table is loaded, from environment variables, to 50% of the logical CPUs by default; getDTthreads() reports it; setDTthreads(threads) changes it for the session (0 means all logical CPUs); setDTthreads(NULL) reads the environment variables again; and the variables R_DATATABLE_NUM_THREADS (a fixed number), R_DATATABLE_NUM_PROCS_PERCENT and OMP_THREAD_LIMIT (which caps everything) control the initial value. The help page also says that data.table automatically switches to single-threaded mode in a fork, as the one made by mclapply() (and by the foreach package), because nested parallelism would overload the CPUs, and that by default it is multi-threaded again afterwards (restore_after_fork). A PSOCK worker is not a fork, it loads data.table fresh and gets the full default, which is why two workers can oversubscribe a machine.

How many cores a job keeps busy can be measured without timing anything: it is the CPU time (user plus system) divided by the elapsed time. The first part of the script does that in three fresh R processes started with callr, which can be given a different environment: with the default environment the matrix products keep more than two cores busy; with OPENBLAS_NUM_THREADS=1 they keep one; with 2 they keep two. The ratios are rounded, and the first only compared with 2, because it depends on the machine and the BLAS. The rest shows data.table: the thread count in the master, in two forked children (one thread each), and in two PSOCK workers that were started after the environment variables had been set (also one: the variables are read when each worker loads data.table). The master loaded data.table before the variables were set, so it needed setDTthreads(threads = NULL) to read them. The usual rule of thumb is that workers multiplied by threads per worker should not exceed the cores available: with n workers, give each cores / n threads, or one.

busy <- function() {
  set.seed(1)

Pitfalls at a glance

  • Parallelising before measuring. Find the slow part first (Performance, Profiling and Benchmarking); a vectorised or compiled version of the same step is often faster than any number of workers.

  • Tasks that are too small. Dispatch and serialisation cost more than the work. Make fewer, larger chunks (chunk.size, future.chunk.size, a function that handles a whole group).

  • Globals. A worker has none of your variables. Pass them as arguments, export them once with clusterExport(), or use a framework that finds them (future) or asks for them by name (mirai).

  • Random numbers. Use L’Ecuyer-CMRG streams, one per task if the result must not depend on the number of workers; never set.seed(i) in each worker.

  • Too many workers. More workers than cores, or workers times threads above the cores, makes everything slower. Use parallelly::availableCores(), leave a core free, and limit BLAS and data.table threads in the workers.

  • Forking where it is unsafe. In RStudio and other GUIs, with graphics devices open, and with multi-threaded libraries; use a PSOCK cluster or plan(multisession).

  • Forgotten clusters and plans. on.exit(stopCluster(cl)), plan(sequential) at the end of a script, daemons(0) when done.

  • Order and errors. The results come back in the order of the input, but a worker’s error is reported once, with a useless call; reproduce a failure with lapply() on a small input.

  • Large results. Everything returned is serialised through a pipe or a socket; reduce on the worker and return the summary.

Fork clusters could hang because of a race condition in the initialisation of makeCluster(); fixed.

The default method of generating from a discrete uniform distribution, used by sample(), changes (sample.kind = "Rejection"); RNGkind() also returns the kind used by sample(). On Windows detectCores() detects processors in all processor groups, and clusterApplyLB() no longer hangs with more than 64 workers.

R 4.0.0

Starting a homogeneous PSOCK cluster on localhost with many nodes is much faster. mcmapply() preserves the attributes of "try-error" results and never simplifies them.
