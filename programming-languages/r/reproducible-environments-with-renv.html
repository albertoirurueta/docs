Reproducible Environments with renv

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. This page uses renv 1.3.1. The scratch project it builds has two packages of its own, jsonlite 2.0.0 and R6 2.6.1, and the examples add two more from CRAN, tinytest 1.4.3 and magrittr 2.0.5; the lintr 3.4.0 default linters were used only to check the scripts, and git is used for the history example. Everything else (rig, Docker, the rocker images, GitHub Actions) is described from its documentation and shown as a fragment that was not run, except that the rocker/r-ver:4.6.1 image was started once to check that it reports R 4.6.1. R finds the packages a script loads in a library, a directory of installed packages, and by default every project on a machine shares one or two of them. That is convenient until two projects need different versions of the same package, until an update for one project breaks another, or until a colleague runs your script with newer versions and gets different numbers. The renv package gives each project its own library, records exactly which versions are in it in a text file called a lockfile, and can rebuild the library from that file on another machine. This page explains the project library, the lockfile and the cache, the cycle of snapshot(), status() and restore(), how renv decides which packages a project uses, the settings that change its behaviour, and how to put renv into CI and Docker. It then looks at what renv cannot do on its own, which is to pin the version of R itself, and at the tools that can: rig and the rocker images.

Every example is a script that was run with Rscript on R 4.6.1, and the lines that start with #> are what it printed. The scripts also pass the default lintr linters. They run in the order in which they appear on the page, inside one scratch project, so a later script depends on the state the earlier ones left. Some of the scripts need the network (renv::install() of a package that is not already cached downloads it from CRAN, and the fresh checkout downloads renv and the packages), and each such script says so in a comment. Paths in the output are shortened: the project directory is shown as ~/project, the cache as ~/.cache/R/renv/cache (its default location on Linux; in these runs RENV_PATHS_CACHE pointed at a scratch directory), and the operating-system and platform parts of library and cache paths as <os> and <platform>. Progress bars, timings and terminal control characters, which renv writes while it installs, are filtered out of the output; the scripts that need this say so. The running shelf scenario of the section (books, loans, shelf_today) is not needed here, because the point of this page is the environment and not the analysis; the example project is a tiny report.R whose member names come from the scenario.

Why a project library

R’s own vocabulary is the first thing to get straight. The R FAQ answers "What is the difference between package and library?" with a definition that renv’s documentation repeats: a library is a directory that contains installed packages, and a package is what library(dplyr) loads from one. A repository is a source of packages, such as CRAN, Bioconductor, Posit Public Package Manager or an r-universe, that install.packages() downloads from into a library. .libPaths() lists the libraries R searches, in order, and getOption("repos") lists the repositories it installs from. Both are covered, with install.packages() and update.packages(), on Packages, Libraries and Namespaces. renv changes the first list: a project that uses renv has its own library first on .libPaths(), and nothing from the user or site libraries after it except the packages that ship with R.

The renv introduction names the three gains this buys. Isolation: installing, updating or removing a package in one project cannot affect another. Portability: the lockfile records enough metadata about every package for it to be installed again on another computer. Reproducibility: the lockfile records the versions, so the same versions come back. The cost is also stated in the documentation: an isolated project never benefits from bug fixes in its packages unless somebody updates it, so the advice is to run renv::update() regularly (at least once a year, says the introduction), re-run the code, and snapshot again.

renv is also explicit about what it does not do. It tracks the version of R in the lockfile but cannot change it, because it runs inside R. It does not restore pandoc, which rmarkdown needs and does not bundle. It does not control the operating system, the system libraries, the compilers or the BLAS and LAPACK libraries that compiled packages are built against, and package installation can fail if a package was originally installed from a binary that is no longer available, because renv then tries to build it from source and may lack the system prerequisites. The last sections of this page return to R itself, and to the system layer, with rig and Docker. The renv documentation also notes that the workflow is generally a poor fit for a CRAN package, because CRAN checks a package against the latest versions of its dependencies; the usual place for renv is an analysis, an application or a report, not a library.

How renv finds the packages a project uses

Three of renv’s functions start from the same question: which packages does this project use? init() installs them, snapshot() (with the default snapshot type) records them, and status() compares them with the lockfile and the library. The answer comes from renv::dependencies(), which is static analysis: it parses the code and looks at what it says, and it does not run anything. The help page lists what it recognises: calls of the form library(package), require(package), requireNamespace("package") and package::method() (and :::), the box::use() and pacman::p_load() loaders, the rlang::check_installed() and rlang::is_installed() checks, and, in later releases, base::use() (renv 1.1.5), data(dataset, package = "package") (1.1.6) and system.file(..., package = "package") (1.2.0). It reads .R files, R Markdown and Quarto documents, DESCRIPTION files and Jupyter notebooks. R Markdown files need the rmarkdown package, and the YAML header needs yaml; in a project library that has neither, dependencies() warns that the yaml package is required to parse dependencies within R Markdown files, and suggests installing it.

The script builds a scratch tree with a script, a notebook-style document and a DESCRIPTION, and prints which package was found in which file. It runs before the project is initialised, because the project library below will not contain rmarkdown and yaml.

Each step shows a rule of the scan. The first listing finds dplyr (a library() call), ggplot2 (a quoted library() argument), stringr (requireNamespace()), jsonlite (a :: call) and data.table (a ::: call) in analysis.R, rmarkdown and knitr in the document, and cli from the Imports field of the DESCRIPTION. It does not find DBI, whose library() call is in a chunk with eval=FALSE, because renv skips chunks that are not evaluated, nor shiny, in a chunk marked renv.ignore=TRUE; renv.ignore=FALSE forces a chunk to be read. It also does not find lubridate and forcats, because the loop for (p in c(...)) library(p, character.only = TRUE) hides the names from a parser. The documentation gives that very loop as an example of what static analysis cannot see, and gives the escape hatch used in the script: a file called _dependencies.R that holds plain library() calls. A package that only another package needs at run time cannot be seen either (tidyr::separate_wider_delim() needs stringr, which tidyr only suggests); for a few common cases renv infers the indirect dependency (dplyr with DBI and RSQLite implies dbplyr), and options(renv.dependencies.implied = list()) turns the inference off.

testthat appears in the second listing, with Dev set to TRUE: a package in the Suggests field of the project’s DESCRIPTION is a development dependency, one that people need while working on the project and the computer deploying it does not. snapshot() and status() leave development dependencies out of the lockfile by default (renv 1.0.0), while renv::install() with no arguments installs them. The snapshot.dev setting (renv 1.1.6) turns them on for snapshot() and status(). Packages used in the user’s ~/.Rprofile also count as development dependencies, when config$user.profile() is TRUE.

The last listing shows the other control on the scan. renv reads the project’s .gitignore files to decide which files to skip, and a .renvignore file with the same syntax takes its place in the folder that contains it; data/old-script.R disappears once data/ is ignored. Ignoring matters for speed (renv reports when a scan finds more than 1000 files, renv.config.dependencies.limit) and for errors: a file that does not parse is reported, not fatal, unless errors = "fatal" or the config option dependency.errors says so. Profile-specific sections in these files start with a comment of the form #| profile == "dev".

The renv FAQ turns this into the answer to the most common question: a package enters the lockfile only if it is both installed in the project library and used by the project according to dependencies(). To record every installed package whatever the code says, use the all snapshot type below; to list packages one by one, use explicit; to keep a package out, add it to the ignored.packages setting.

Starting with renv::init()

renv::init() turns a project into an renv project. Its help page lists four steps: set up the project infrastructure (the project library and the .Rprofile line that activates it), discover the packages the project uses with dependencies() and install them into the project library (the job of hydrate()), write a lockfile that records the library (the job of snapshot()), and restart R if it runs inside RStudio. If the project already uses renv, init() restores the library when it is missing and otherwise asks what to do. The main arguments are in the table.

Argument Meaning

project

The project directory; the default is the working directory, and R’s working directory is changed to match a different one.

bare

TRUE creates an empty project library and does not discover or install any packages.

profile

The renv profile to activate, for projects that keep several libraries and lockfiles side by side (see the profiles article).

settings

A list of project settings for the new project, for example list(snapshot.type = "explicit").

repos

The repositories to use in this project and to record in the lockfile.

bioconductor

The Bioconductor version to use; TRUE takes the version the BiocManager package recommends.

force

Allow initialising the home directory, which renv otherwise refuses.

load, restart

Whether to load the project after initialising it, and whether to try to restart the R session.

There is one point about repositories that decides what the lockfile will say. If the repos option has not been set by some other means, init() uses the Posit Public Package Manager CRAN mirror, because it can serve pre-built binaries on common Linux distributions; the NEWS for renv 1.0.0 introduced this. The scripts here set the option to the public CRAN address first so that the lockfile records that address, which is also what a project does when its .Rprofile or Rprofile.site sets repos. renv::init(bare = TRUE) is the variant for starting with an empty library, and it is the form the examples in the renv help pages use. A project that needs no packages yet, or one that wants to install everything itself, can use it, and a later renv::snapshot() records whatever has been installed and used.

Four details in the output are worth reading slowly. The project library is first on .libPaths(), and the only other entry is R’s own library of base and recommended packages: the user and site libraries are gone, which is why library(dplyr) fails in the script even though dplyr is installed on the machine. The error is the ordinary one for a missing package; a project that needs dplyr has to install it into its own library. jsonlite and R6 in the project library are symbolic links into the cache, which the later section on the cache explains, while renv itself is a real directory, not a link. And find("install.packages") reports renv:shims before package:utils: renv puts shims on the search path so that the habitual install.packages(), update.packages() and remove.packages() call renv::install(), renv::update() and renv::remove() instead, and the shim can be bypassed by writing utils::install.packages(). renv::load(), which the autoloader calls, is the function that sets all this up, including a sandbox of the system library that hides non-base packages (the sandbox is configurable, renv.config.sandbox.enabled).

Activation: how R finds the project

The activation path is plain R startup. When R starts it runs the user profile, which is the .Rprofile of the working directory (or of the home directory when the working directory has none), unless R_PROFILE_USER names another file or --no-init-file is given. This is the mechanism described on Sessions, Workspaces and Startup, and renv depends on it. Three consequences are worth knowing.

  • A session is only in the project if it started in the project directory, or the project was loaded with renv::load("path/to/project"). Opening the project folder in RStudio or Positron, or running Rscript report.R from that folder, gets the autoloader; running Rscript ~/project/report.R from the home directory does not, and neither does starting R with a different R_PROFILE_USER.

  • activate.R does nothing when the autoloader is disabled. options(renv.config.autoloader.enabled = FALSE) or the environment variable RENV_CONFIG_AUTOLOADER_ENABLED=FALSE turn it off, and so does a sub-process of R CMD in which R_LIBS is already set (the script takes it that the parent process has set up the library paths). In that case the script loads the user profile by hand, so the rest of the user’s startup is not lost.

  • The autoloader sets options(renv.consent = TRUE). renv writes into the project and into its global cache directory, and CRAN policy says a package may only do that with the user’s consent; renv::consent() records it, and the autoloader and renv::init() take care of it.

The daily cycle: install, snapshot, status, restore

The working loop has four verbs, and the first two are the ones a person types most. The code starts to use a package, which is installed into the project library; once the code works, renv::snapshot() records the library in the lockfile; the lockfile goes into version control; and anybody else, or the same person on another computer, runs renv::restore() to get the library back. renv::status() reports whether the three things that should agree really do: the code (what dependencies() finds), the library and the lockfile.

snapshot() prints what it would change in the lockfile, in the form [old -> new] where a star means "not recorded", writes the file, and when called interactively it asks first (prompt = interactive()); renv 1.0.0 stopped asking for confirmation when the lockfile does not exist yet, since deleting it undoes the write. It checks the library before writing (the snapshot.validate config option, on by default) and diagnoses problems such as an installed package whose dependency is missing. Its other arguments are worth knowing: lockfile writes elsewhere, and lockfile = NULL returns the lockfile as an R object without writing, which the snapshot-type section uses; packages and exclude restrict what is recorded (a package’s dependencies are always added, so the lockfile stays complete); update = TRUE keeps the records of packages that are not in the library any more; repos chooses the repositories recorded; type selects the snapshot type; and force writes even when the checks failed. Setting renv.config.auto.snapshot to TRUE makes renv snapshot after each change without being asked, and is off by default.

restore() compares the lockfile with the project library and installs, from the lockfile’s records, the packages that differ. Its arguments change how it does that.

TRUE, or a vector of package names, forces them to be built again, bypassing the installed copies and the cache.

The global cache

Restoring a project that needs forty packages would be slow if every project had to download, and for packages with C or Fortran code compile, its own copies. The renv package avoids that with a cache that all of a user’s renv projects share. The package-installation article describes what happens when a package is requested, whether by install.packages() (through the shim), renv::install() or restore(). If the requested version is in the cache, it is linked into the project library, and that is all. Otherwise the package is downloaded and installed into the project library, then copied into the cache and linked back. A project library entry is therefore a link into the cache, and two projects that use the same version of a package share one copy on disk. The script looks at the cache and at one of those links; the last two lines call renv::isolate(), which undoes the sharing for this project.

The paths reference adds two warnings. Set the variables in an R startup file so that they apply to every session: a project-local .Renviron, the user’s ~/.Renviron, or the site-wide Renviron.site, which is the right place for a cache shared by all users of an R installation (the startup order is on Sessions, Workspaces and Startup). And if reproducibility on a machine matters, back up and persist the cache: restoring from it is much easier than installing an old package from source again. A shared cache needs more care: the files in it must be readable by every user, access control lists included, and the RENV_CACHE_USER variable makes renv change the owner of cached packages. Two failure modes have their own tools. renv::purge("pkg") removes a corrupted package from the cache, and renv::restore(rebuild = TRUE), renv::install("pkg", rebuild = TRUE) or renv::rebuild() install again past it.

The cache can be turned off per project with renv::settings$use.cache(FALSE), or for a user with renv.config.cache.enabled. renv.config.cache.symlinks chooses between links and copies. It matters when the library and the cache are on different volumes, or when the project goes somewhere the links cannot follow, such as the image of a Docker build: renv.config.cache.symlinks = FALSE copies, so that nothing in the project library points outside it. renv::isolate(), which the script ran, copies the linked packages into the project library and leaves the cache in use for future installs. Finally, renv.config.install.shortcuts, on by default, lets renv install a local copy of a package it finds already installed in the user or site libraries, and renv::hydrate(), which init() calls, does the same job for a whole project: it copies the packages the project uses from the system libraries, then the cache, and installs from the repositories only what it does not find. That is why the init() run above needed no download.

Installing, updating and removing packages

After init() the usual commands keep working, because of the shims, and renv has its own. The introduction says that one of renv’s philosophies is that existing package-management habits should continue to work. renv::install() differs from install.packages() in that it uses the cache, knows several sources, and, when it is called with no arguments, installs every package the project requires, development dependencies included. It does not read the lockfile: it installs the latest versions available, unless a version is given. The other arguments are include and exclude (restrict the packages of a project-wide install), library, type ("source" or "binary", default getOption("pkgType")), rebuild, repos, dependencies (which DESCRIPTION fields count; the default is the package.dependency.fields setting), transactional, and lock = TRUE, which updates renv.lock after the packages have installed. renv::update() brings installed packages up to date. It looks only at the source a package was installed from, so a package installed from GitHub is not updated from CRAN. With check = TRUE it reports what is available without installing anything, which is what the script below does; with lock = TRUE it updates the lockfile afterwards; since renv 1.1.3 it looks only at the project library unless all = TRUE. It updates renv itself too (renv::upgrade() updates only renv, or installs a development version from GitHub). The recommended routine, from the introduction, is to run update(), then the project’s code, and then snapshot(); if the update breaks something, restore() goes back to the lockfile. renv::remove("pkg") removes a package from the project library; it asks for confirmation only when the target is not the project library (renv 1.2.4).

History and revert

A lockfile in version control is a history of the project’s dependencies. renv::history() uses git to list the commits that changed the lockfile, as a data frame with the columns commit, author_date, committer_date and subject; renv::revert(commit) checks the lockfile out of an older commit. Both are implemented for git only. revert() changes the lockfile and nothing else, and leaves it as an uncommitted modification, so it is followed by restore(), which makes the library match, and by a commit if the change is to be kept. When the project is not activated

Everything above relies on the project being active. Scripts that carry their own packages: use() and embed()

A project is the right unit for an analysis with many files, and the wrong one for a script that is sent by itself. renv::use() is renv’s lightweight answer: it describes the packages in the script and their versions, builds a library for the script in R’s temporary directory, installs the requested packages and their recursive dependencies into it, and puts it on the library paths for the rest of the session. Settings and config

Two mechanisms change how renv behaves. Settings belong to the project, are written to renv/settings.json and travel with the code; config options belong to the user or the machine. The settings are read and written with a function per setting, renv::settings$snapshot.type() to read and renv::settings$snapshot.type("explicit") to write; the value is saved straight away (persist = FALSE keeps a change to the session), and a hand edit of the file needs a restart of R. The defaults for new projects come from options(renv.settings = list(snapshot.type = "all")) or options(renv.settings.snapshot.type = "all"), typically in a user’s ~/.Rprofile. Config options are read with renv::config$name(). For a given name, an R option renv.config.<name> wins; otherwise the environment variable RENV_CONFIG_<NAME> is used, with periods turned into underscores; otherwise the default applies. The environment variable is inherited by child processes and the R option is not, which is the reason to pick one over the other. Config is best set in ~/.Renviron or the site’s Renviron.site; in a project .Rprofile it must come before source("renv/activate.R").

renv in Docker

A container fixes what renv cannot: the operating system, the system libraries, the compilers and the BLAS. The renv Docker article describes the most common case, an existing renv project that is to be built into an image, and the recommended structure is to copy the renv metadata first, restore, and only then copy the rest of the project, so that Docker’s layer cache is reused whenever the code changes and the lockfile does not (the same ordering rule as on Dockerfile Fundamentals and Build Cache and Multi-Stage Builds). Pinning R itself

The lockfile records the version of R; renv cannot select it. renv::status() compares the two, and the script shows the message by pointing it at a copy of the lockfile that claims R 4.5.2. The r.version setting is the knob for projects where several people use different R versions, and the load-time check warns when the major and minor version differ. This status message appeared in renv 1.0.4. What snapshot() does is overwrite the recorded version with the running one, so changing R and snapshotting is the way to declare a deliberate upgrade.

# The lockfile records the R version it was written with ...
lock <- renv::lockfile_read()
lock$R$Version
#> [1] "4.6.1"
getRversion()
#> [1] ‘4.6.1’

# ... and status() compares it with the R that is running. Here a copy of
# the lockfile claims to come from R 4.5.2.
lock$R$Version <- "4.5.2"

Source: rig (community tool): README

For a reproducible machine rather than a reproducible R, the usual answer is a container. The rocker project’s rocker/r-ver images are described as an alternative to the Debian-based r-base image with an emphasis on reproducibility. Its page lists what that means. The images build on an LTS release of a Linux distribution chosen when the R version was released; they install a fixed version of R from source rather than whatever the distribution packages; and they set Posit Public Package Manager as the default CRAN mirror, which serves compiled Linux binaries for the amd64 platform. And, for versions of R that are not the latest, they install all R packages from a fixed snapshot of CRAN mirror taken at a given date, which the page says makes the same version of a package install whenever the installation happens. So rocker/r-ver:4.6.1 pins R and the system layer, and, once a newer R exists, the CRAN snapshot that plain install.packages() uses by default. The 4.6.1 image used for checking this page reported R 4.6.1 and had the package manager’s latest address as its default repository, not a dated snapshot, which fits the statement that only the images that are not the latest are frozen; the page does not list the snapshot date of each version. The same page shows how to change the mirror in an image by writing a new options(repos = ...) line into Rprofile.site. Combined with renv, the two layers pin different things: the base image fixes R and system libraries, and the lockfile fixes the packages, whatever the mirror says. The Dockerfile earlier on this page does exactly that: the tag in its FROM line is the pin of R.

Packrat and migration

Before renv there was packrat, which also gave a project a private library and a snapshot, with a packrat/ directory and a packrat.lock file. Its repository now says that packrat has been soft-deprecated and is superseded by renv, that it will continue to be maintained while all new development focuses on renv, and that renv::migrate() migrates a project from packrat to renv. migrate() can move the lockfile (packrat/packrat.lock to renv.lock), the sources, the library, compatible options and the cache; the packrat argument selects the components. A project that still uses packrat is a candidate for renv::migrate() followed by renv::status(). The rest of this page applies to the result. Common messages and errors

The messages that renv prints are part of its interface, and most are a call to action. This script collects the ones that have not appeared yet: a restore in a directory that has no lockfile, a status in one that never used renv, a lockfile that is not JSON, and an install of a package that does not exist (this one queries the repository, so it needs the network). The error from install() is a condition that can be caught, and its message lists the failures.

# A directory that never saw renv.
empty <- file.path(tempdir(), "empty")
dir.create(empty)
tryCatch(renv::restore(project = empty), error = \(e) conditionMessage(e))
#> [1] "This project does not contain a lockfile.\nHave you called `snapshot()` yet?"
renv::status(project = empty)
#> This project does not appear to be using renv.
#> Use `renv::init()` to initialize the project.

# A lockfile that is not JSON.
bad <- tempfile(fileext = ".lock")
writeLines("{ not json", bad)
tryCatch(renv::lockfile_read(bad), error = \(e) conditionMessage(e))
#> [1] "Failed to parse 'renv.lock':\n3:14: unexpected symbol\n2:         object( \n3:          not json\n                ^"

# A package that does not exist (network: the repository is queried first).
output <- capture.output(
  res <- tryCatch(
    renv::install("no.such.pkg.xyz"),
    error = \(e) conditionMessage(e)
  )
)
grep("not available", output, value = TRUE)
#> [1] "- [no.such.pkg.xyz]: package 'no.such.pkg.xyz' is not available"
res
#> [1] "package installation failed\n- no.such.pkg.xyz: package 'no.such.pkg.xyz' is not available"

The messages with "will be updated in the lockfile" list package, old and new version in the form [* -> 2.0.0], and the ones that are "already" something say there is nothing to do. The remaining two are failures that stop the work: "Failed to parse 'renv.lock'" followed by the position, which means the file was damaged, for example by a bad merge, so restore it from version control; and "package installation failed", which lists the packages that did not install, usually with a reason such as "is not available". When a restore fails because a package from an old lockfile no longer builds, restore(retry = TRUE) tries the latest version of the failing packages.

Turning renv off

The introduction describes two levels. renv::deactivate() removes the autoloader line from .Rprofile and leaves the other renv files alone, so that renv::activate() brings it back; renv::deactivate(clean = TRUE) removes the lockfile and the renv/ directory too, leaving the project as it was found. In an interactive session both restart R; in a script the change is for the next session. The script below deactivates the project and activates it again. It is the last script, because after deactivate() the project is not active in this session.

# deactivate() removes the autoloader from .Rprofile; renv.lock and renv/ stay.
readLines(".Rprofile")
#> [1] "source(\"renv/activate.R\")"
renv::deactivate()
file.exists(".Rprofile")
#> [1] FALSE
file.exists("renv.lock")
#> [1] TRUE

# activate() writes it again; it takes effect in the next R session.
renv::activate()
readLines(".Rprofile")
#> [1] "source(\"renv/activate.R\")"

Source: renv package documentation: activate and deactivate

To stop using renv for all projects, delete renv’s global state, which is the root directory given by renv::paths$root(), and then remove the package. The block below is a fragment that was not run, and it is destructive: it deletes the cache of every renv project on the machine.

root <- renv::paths$root()
unlink(root, recursive = TRUE)
utils::remove.packages("renv")

Source: renv package documentation: Introduction to renv

The environment variable RENV_CONFIG_AUTOLOADER_ENABLED=FALSE is the way to turn the autoloader off for one session without changing any file.

  • renv 0.17.1 (2023-03-16): Project settings are stored in renv/settings.json instead of renv/settings.dcf; old settings are migrated automatically.

  • renv 1.0.0 (2023-07-07): Added renv::checkout(). deactivate(clean = TRUE). init() uses Posit Public Package Manager by default when the repositories have not been configured. The lockfile_create(), lockfile_read(), lockfile_write() and lockfile_modify() family. snapshot() and status() no longer track development dependencies, while install() still installs them. MRAN integration disabled by default. restore() can use pak (opt-in). init() prompts for a snapshot type when a DESCRIPTION exists.

  • renv 1.0.4 (2024-02-21): status() reports when the R version in the lockfile differs from the running one. Historical binaries come from Posit Public Package Manager instead of MRAN, described as now defunct. init() respects Remotes:.

  • renv 1.0.6 (2024-04-11): With R 4.4.0 or later, the operating-system prefix of library and cache paths is generated by default (the paths reference).

  • renv 1.0.8 (2024-09-20): renv::lockfile_validate() checks a lockfile against a schema.

  • renv 1.1.0 (2025-01-29): Lockfile records include more DESCRIPTION fields; options(renv.lockfile.version = 1) writes the older compact format.

  • renv 1.1.2 (2025-03-02): renv::sysreqs() and, on Linux, a check of the system libraries a package needs.

  • renv 1.1.3 (2025-03-18): update() looks only at the project library by default (all = TRUE for the rest); RENV_PATHS_VERSION; install() gains transactional; profile comments in ignore files.

  • renv 1.1.6 (2026-01-16): The snapshot.dev setting; renv::vulns(); RENV_CONFIG_REPOS_OVERRIDE takes NAME=URL pairs; RENV_LOCKFILE_VERSION=1.

  • renv 1.2.0 (2026-03-25): Parallel downloads and installs (install.jobs, default 4); Posit Package Manager enabled by default on arm64 Linux; renv::plan(); the strict argument of restore(); credentials stripped from repository URLs in the lockfile; the crandb.enabled option.

  • renv 1.2.4 (2026-08-03): Config/renv/snapshot/include-self in a package DESCRIPTION; remove() gains prompt.

  • renv 1.3.0 (2026-09-29): Version constraints in the project’s DESCRIPTION are honoured by install() and validated by snapshot(); git lockfile records are quoted and checked before use; restore(retry = TRUE) keeps the packages that installed in the first pass; dependencies() follows Quarto’s engine-binding rules.

The 1.0.0 release is the first one numbered 1.x, after the 0.x releases that began with the initial CRAN release, and the 1.x line is the one all of this page applies to. Where older tutorials differ

Material about renv written before 2023, and material about its predecessors, differs from the current tool in the following ways.

Older advice Today

Start with renv::init(bare = TRUE) and install everything again.

renv::init() discovers the packages the project uses and links them from the libraries that exist (hydrate()), so a new project starts working at once. bare = TRUE is for an empty library on purpose.

Use packrat (packrat::init(), packrat/, packrat.lock).

Packrat is soft-deprecated and superseded by renv; renv::migrate() moves a project.

Freeze the date with the checkpoint package, which relied on MRAN snapshots (community material).

Microsoft’s MRAN service was shut down; the renv NEWS first says its shutdown is upcoming (1.0.0) and later calls it defunct (1.0.4). Use the lockfile; to choose a date, renv::checkout(date = ...) takes a Posit Public Package Manager snapshot, and a dated Posit Package Manager repository in repos does the same.

A lockfile entry looks like "Hash": "..." and nothing else.

Since renv 1.1.0 the record holds the installed package’s DESCRIPTION fields; the compact form needs options(renv.lockfile.version = 1).

Settings live in renv/settings.dcf.

They live in renv/settings.json (since renv 0.17.1).

Call install.packages() inside the analysis script so that it "just works" on another machine.

A script should not install packages: declare them in the project and let restore(), or renv::use() for a single file, do it. Interactive install.packages() is fine in an renv project, since it is routed to renv.

Put .libPaths(c("renv/library", .libPaths())) or R_LIBS in .Rprofile for isolation.

The autoloader sets the library paths, hides the user and site libraries, and checks the lockfile; leaving the others visible breaks isolation.

renv pins everything.

It records the R version and warns about differences, but does not choose it: pin R with rig or the rocker images, and the system layer with a container.

A project is reproducible if the lockfile is.

The documentation lists what is not covered: R, pandoc, the operating system and its libraries, compilers and the availability of old binaries.
