Function Factories and Higher-Order Functions

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. Almost everything on this page is base R (the base, utils and stats packages that ship with R); the one add-on package is purrr 1.2.2, used in a single short example to compare its compose() and partial() with the hand-written versions, and the lintr 3.4.0 default linters were used only to check the scripts. A function in R is a value like any other, so functions can be passed to functions and returned from them. This page is about the second half of that sentence and about the patterns built on it: functions that make functions (function factories), functions that wrap a function to change how it behaves (function operators), the glue that combines functions into pipelines, and the recursion that functional code leans on, with the limits R puts on it and the experimental Tailcall() that lifts one of them.

Every example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines that start with #> are what it printed. The scripts also pass the default lintr linters; a # nolint: comment marks a line where the idiom on show is what a default linter dislikes, so the linter does not hide the lesson. The names books, loans, shelf_today, loan_days and the helper is_valid_isbn13() come from the running library-shelf scenario described on the section index: a script that needs them starts with source("scenario.R"). Where a message contains quotation marks, they are the typographic quotes R prints in a UTF-8 locale. Memory addresses of environments and platform-specific numbers (the size of the C stack, the usage reported in a stack error) never appear in the output on this page; where R prints one, the example prints a class, a name or a generic form and the text says so. The mechanics that factories build on, environments, enclosures and <<-, are the subject of Scoping, Environments and Closures, and the promises behind force() are in Lazy Evaluation and Promises; this page uses them and does not repeat them.

Functions that take and return functions

R’s own documentation calls Reduce(), Filter(), Map(), Find(), Position() and Negate() the "common higher-order functions in functional programming languages" (the title of their shared help page, funprog). A higher-order function is one that takes a function as an argument, returns a function as its value, or both. The community book Advanced R, which is not part of the official documentation, separates three kinds that are worth having names for, and this page follows its vocabulary:

  • A functional takes a function and returns data: lapply(), vapply(), Reduce(), do.call(). They are the subject of The apply Family and Functionals.

  • A function factory takes data and returns a function: make_limit_check(21L) returns a function that tests loan lengths against 21 days. The returned function is a closure that remembers the arguments of the call that made it.

  • A function operator takes one or more functions and returns a function: Vectorize(), Negate() and the logging, retry and memoising wrappers below. It is a decorator in the vocabulary of other languages.

All three exist because of two facts from the language definition. Functions are first-class objects: a function value can be stored, passed and returned. And a closure carries the environment in which it was created: the manual says that a closure "will contain the environment in which it is created as part of its definition", and that when the function is called its evaluation environment is created with that environment as enclosure, which "is not necessarily the environment of the caller" (The R Language Definition: Lexical environment; the structure of a function object, formals plus body plus environment, is in Function objects). R FAQ 7.12 explains the difference between the enclosing environment (where the function was created) and the parent environment (where it was called from), and R FAQ 3.3.1 lists lexical scoping as the main difference from S (R FAQ 7.12: What are the enclosing and parent environments?, R FAQ 3.3.1: Lexical scoping). A factory is nothing more than a function whose last expression is a function expression: the call that runs the factory has an evaluation frame, the returned function captures it as its enclosure, and the frame stays alive for as long as the returned function does.

Function factories

A function that returns a function

The first script builds two checkers from one factory. over_21 and over_7 have the same code; they differ only in the environment each one carries, and each of those environments holds its own limit. The script also looks at the environments, because they are the whole mechanism: environment() returns the enclosure, ls() lists what it holds, and its parent is the environment in which the factory itself was defined (here the global environment, whose name environmentName() prints; the anonymous call environments have an empty name, and printing one would show a memory address, which this page avoids).

source("scenario.R")

# A function factory: a function whose value is a function.
make_limit_check <- function(limit) {
  function(days) days > limit
}
over_21 <- make_limit_check(21L)
over_7 <- make_limit_check(7L)
over_21(c(5L, 21L, 30L))
#> [1] FALSE FALSE  TRUE
over_7(c(5L, 21L, 30L))
#> [1] FALSE  TRUE  TRUE

# Every call of the factory creates a new environment, and that environment
# is the enclosure of the function that call returned.
env_21 <- environment(over_21)
env_7 <- environment(over_7)
identical(env_21, env_7)
#> [1] FALSE
ls(env_21)
#> [1] "limit"
get("limit", envir = env_21)
#> [1] 21
env_7$limit
#> [1] 7
class(env_21)
#> [1] "environment"
environmentName(env_21)
#> [1] ""

# The enclosure of that environment is where the factory was defined.
environmentName(parent.env(env_21))
#> [1] "R_GlobalEnv"
identical(parent.env(env_21), environment(make_limit_check))
#> [1] TRUE

# The returned function is a normal closure: its formals and body are its own.
names(formals(over_21))
#> [1] "days"
body(over_21)
#> days > limit

# On the shelf: one checker per limit, applied to the length of every loan.
loan_length <- as.integer(loans$return_date - loans$loan_date)
sum(over_21(loan_length), na.rm = TRUE)
#> [1] 25
sum(over_7(loan_length), na.rm = TRUE)
#> [1] 47

Source: The R Language Definition: Lexical environment

The two checkers are different closures: identical(env_21, env_7) is FALSE, limit is 21 in one and 7 in the other, and body(over_21) shows that the code refers to limit without defining it. That is a free variable, found by lexical scoping in the enclosure, which is the environment of the call make_limit_check(21L). Its only content is limit, the factory’s argument; had the factory created local variables before returning the function, they would be there too, and they would be kept alive with it (the "What a closure keeps alive" part of Scoping, Environments and Closures shows that and how to avoid it). The last two lines apply the checkers to the loan lengths of the shelf scenario: 25 of the returned loans lasted more than 21 days and 47 more than 7.

Two properties explain why factories are used. They give a function configuration that is fixed at creation time, so that a function with the interface f(x) that a caller such as vapply() expects can still depend on a threshold, a connection or a table that the caller knows nothing about. And they make the configuration private to the function: nothing outside can reach limit except through the environment, which is a deliberate act (environment(over_21)$limit), not an accident of naming.

The lazy-evaluation trap and force()

The arguments of the factory are promises (Lazy Evaluation and Promises; the language definition describes them under Argument evaluation), and a promise is evaluated the first time its value is needed. A factory whose closure reads its argument only when the closure is called therefore reads it late, after the caller may have changed the variable that was passed. force(x) evaluates the promise x immediately; the help page says it is useful when an argument will be captured in a closure and later altered by an explicit assignment, or by an implicit one such as the assignment of a loop or an apply function (R documentation: force). It is plain "semantic sugar": evaluating the bare symbol would do the same, and force() states the intent.

The first example uses a changed variable, and then a for loop, where the implicit assignment is the loop variable. The last two blocks show the two apply-style constructors that do not have the problem on R 4.6.1: the NEWS entry of R 3.2.0 says that higher-order functions such as the apply functions and Reduce() now force the arguments to the functions they apply, to eliminate undesirable interactions between lazy evaluation and variable capture in closures (R NEWS: Changes in R 3.2.0). The element that lapply() or Map() hands to the factory is therefore forced, and the loop version of the same code is not.

# The factory keeps its argument n, but n is a promise until it is used.
make_adder <- function(n) {
  function(x) x + n
}
n <- 1L
add <- make_adder(n)
n <- 100L
add(1L)
#> [1] 101

# force() evaluates the promise while n is still 1.
make_adder_forced <- function(n) {
  force(n)
  function(x) x + n
}
n <- 1L
add_forced <- make_adder_forced(n)
n <- 100L
add_forced(1L)
#> [1] 2

# A for loop builds closures that all read the last value of i.
adders <- list()
for (i in 1:3) {
  adders[[i]] <- make_adder(i)
}
vapply(adders, \(add) add(10L), integer(1))
#> [1] 13 13 13

# lapply() and Map() force the element they pass (R 3.2.0), so no trap here.
adders <- lapply(1:3, make_adder)
vapply(adders, \(add) add(10L), integer(1))
#> [1] 11 12 13
adders <- Map(make_adder, 1:3)
vapply(adders, \(add) add(10L), integer(1))
#> [1] 11 12 13

Source: R documentation: force

add(1L) is 101: the factory returned before n was needed, n was then reassigned to 100, and the promise read the new value when add was first called. After force(n) the same sequence gives 2. The for loop version is the one that appears in the force() help page itself: every closure was created while i was still counting, none of them forced it, and all three read the final 3 afterwards, so the results are 13, 13 and 13. lapply() and Map() give 11, 12 and 13 because of the 3.2.0 change. A for loop is a language construct and not a function, so it is not covered by that change and nothing in R 4.6.1 forces the loop variable for you.

The 3.2.0 change has a limit that is easy to miss: it concerns the element that the apply function passes, not the extra arguments it forwards through the dots. The next script passes a configuration value through the dots of lapply(). The value is still a promise when the factory returns, so the same trap appears even though lapply() is used; force() in the factory fixes it, and Map(), whose dots are the vectors it iterates over and are forwarded to mapply(), forces them.

# What lapply() forces is the element it passes, not the arguments it forwards
# through the dots.
make_offset <- function(i, k) {
  function(x) x + k
}
shift <- 1
offsets <- lapply(1:2, make_offset, k = shift)
shift <- 100
offsets[[1L]](0)
#> [1] 100

# Forcing in the factory fixes it for every caller.
make_offset_forced <- function(i, k) {
  force(k)
  function(x) x + k
}
shift <- 1
offsets <- lapply(1:2, make_offset_forced, k = shift)
shift <- 100
offsets[[1L]](0)
#> [1] 1

# Map() forwards its dots as arguments of mapply(), which forces them.
shift <- 1
offsets <- Map(make_offset, 1:2, k = shift)
shift <- 100
offsets[[1L]](0)
#> [1] 1

Source: R documentation: lapply

The practical rule is the one that the language gives anyway: a factory that stores an argument in the closure should call force() on it as its first statement, whatever the caller does. It costs one line, it makes the factory safe for every caller, and a reviewer reading force(limit) knows that the argument was meant to be read now. The cost of leaving it out is a bug that produces plausible numbers (the lazy evaluation page shows the shelf version: the same count three times for three different limits) and that can disappear when the code is run line by line in a debugger, because inspecting a variable there forces the promise.

Stateful functions

Counters with <<-

A closure can also change the variables of its enclosure, and then the factory makes a function with memory. The operator for that is <<-, which assigns not in the current frame but in the first enclosing environment where the name already exists (the details and the lookup rules are in Scoping, Environments and Closures). A counter is the standard example, and the ordinary case on the shelf is an id source that continues the numbering of the loans table. Every counter has its own state, because every call of the factory creates its own environment; environment(counter)$count reads the state from outside. The last function in the script uses <- by mistake: it increments a local copy that dies with each call, so the counter never advances, and no error or warning is produced.

source("scenario.R")

# A counter: the state lives in the environment of the call that made it.
make_counter <- function(start = 0L) {
  count <- start
  function() {
    count <<- count + 1L # nolint: assignment_linter.
    count
  }
}
counter_a <- make_counter()
counter_b <- make_counter(10L)
counter_a()
#> [1] 1
counter_a()
#> [1] 2
counter_b()
#> [1] 11
counter_a()
#> [1] 3
environment(counter_a)$count
#> [1] 3
environment(counter_b)$count
#> [1] 11

# The next free loan id, continuing the numbering of the loans table.
make_id_source <- function(used) {
  last <- max(as.integer(sub("^L", "", used)))
  function() {
    last <<- last + 1L # nolint: assignment_linter.
    sprintf("L%03d", last)
  }
}
next_loan_id <- make_id_source(loans$loan_id)
next_loan_id()
#> [1] "L061"
next_loan_id()
#> [1] "L062"
tail(loans$loan_id, 1L)
#> [1] "L060"

# With <- the counter changes a local copy, so it never advances.
make_broken_counter <- function() {
  count <- 0L # nolint: object_usage_linter.
  function() {
    count <- count + 1L
    count
  }
}
broken <- make_broken_counter()
broken()
#> [1] 1
broken()
#> [1] 1
environment(broken)$count
#> [1] 0

Source: An Introduction to R: Scope

The default lintr linters flag <<- through assignment_linter in this configuration, which is why the lines carry # nolint: assignment_linter.: the use is deliberate. R-intro builds its bank-account example on exactly this pattern, as an illustration of lexical scope used to give functions mutable state.

What <<- does when the name is not found

The rule of <<- has a consequence that older tutorials never mention. If the name is not found in any enclosing environment, the assignment creates it in the global environment. A typo in the name of the state variable then does not fail; it silently writes a global variable and leaves the real state untouched. The next script has such a typo (cont for count) and shows the consequence: the function returns 1 every time, and a variable called cont has appeared in the global environment. It then shows two alternatives that do not rely on <<- finding the right name: a state environment that is modified in place, and assign() with an explicit target.

# <<- starts searching in the enclosing environment of the running function
# and walks up the chain. If it finds nothing, it assigns in the global env.
exists("typo_count")
#> [1] FALSE
make_typo_counter <- function() {
  count <- 0L
  function() {
    cont <<- count + 1L # nolint: assignment_linter, object_usage_linter.
    cont # nolint: object_usage_linter.
  }
}
typo_counter <- make_typo_counter()
typo_counter()
#> [1] 1
typo_counter()
#> [1] 1
exists("cont")
#> [1] TRUE
rm("cont", envir = globalenv())

# A mutable environment needs no <<-: its contents change in place.
make_tally <- function() {
  state <- new.env()
  state$n <- 0L
  function() {
    state$n <- state$n + 1L
    state$n
  }
}
tally <- make_tally()
tally()
#> [1] 1
tally()
#> [1] 2
# assign() with an explicit environment states the target.
make_total <- function() {
  total <- 0
  function(x) {
    assign("total", total + x, envir = parent.env(environment()))
    total
  }
}
add_to_total <- make_total()
add_to_total(5)
#> [1] 5
add_to_total(7)
#> [1] 12

Source: R documentation: assign

An environment is the one mutable container in the language: state$n <- state$n + 1L changes the object that state refers to, so no <<- is needed and a typo in n creates a new entry in state, not a global variable. Reference semantics of this kind are the base of Reference Classes and R6 (Reference Classes and R6), which are environments with methods attached. When the state grows past a counter or two, an R6 class is usually easier to read than a factory that returns a list of five functions.

Private state with local()

A factory function is not the only way to give a function a private environment. local() evaluates an expression in a new environment; the help page says that it is equivalent to evalq() except that its default environment is new and empty, and that this makes it useful for anonymous recursive functions and as a kind of limited namespace (R documentation: eval, evalq, local). If the block ends in a function (or a list of functions), the variables created in the block become that function’s private state, and there is no factory to call twice. It is the right tool for a one-off object, such as a receipt number source for the whole script, and for a small group of functions that share a variable.

source("scenario.R")

Memoisation

A memoised function remembers the results it has already computed, keyed by its arguments, and returns the stored value instead of computing it again. It is a function operator that needs a mutable cache, and the natural cache in R is an environment: it is a hash table keyed by strings, it is modified in place, and it lives in the closure. new.env(hash = TRUE, parent = emptyenv()) creates it (hash = TRUE is the default; the empty parent is a second safety net, because with the default inherits = TRUE the functions exists() and get() follow the enclosure chain and would find a key such as "sum" in the base package), exists(key, envir = cache, inherits = FALSE) asks whether a key is present, and assign() and get() write and read it (R documentation: environment, exists, assign, get). The keys are names, so the cache converts the argument with as.character().

The classic demonstration is the Fibonacci function, which in its naive form recomputes the same values exponentially often. The script counts the calls of the naive version and then memoises the same definition. Two details matter. The memoised function has to call itself through the memoised name (fib calls fib), because the recursive calls inside the body are what fill the cache; a body that used Recall() would call the unwrapped function and the cache would not help. And the counters hits and misses live in the same closure as the cache, so they can be read from outside with environment().

source("scenario.R")

# memoise(): a function operator that caches results in an environment.
memoise <- function(f) {
  force(f)
  cache <- new.env(hash = TRUE, parent = emptyenv())
  hits <- 0L
  misses <- 0L
  function(x) {
    key <- as.character(x)
    if (exists(key, envir = cache, inherits = FALSE)) {
      hits <<- hits + 1L # nolint: assignment_linter.
      return(get(key, envir = cache, inherits = FALSE))
    }
    misses <<- misses + 1L # nolint: assignment_linter.
    value <- f(x)
    assign(key, value, envir = cache)
    value
  }
}

# The naive Fibonacci function repeats the same sub-problems.
calls <- 0L
fib_plain <- function(n) {
  calls <<- calls + 1L # nolint: assignment_linter.
  if (n < 2) n else fib_plain(n - 1) + fib_plain(n - 2)
}

The value 12586269025 is exact because it is below 2^53, the limit up to which a double represents every integer exactly; fib(80) would not be (see Numbers and Arithmetic).

Memoisation helps when a function is expensive, pure and called repeatedly with the same arguments. The shelf has such a case only in a mild form: the loans table has 60 rows but 16 distinct ISBNs, so validating the ISBN of every loan with a memoising wrapper around is_valid_isbn13() calls the checker 16 times instead of 60. The checker is cheap, so this is a demonstration and not a recommendation; for a function this cheap the lookup costs as much as the work. The script also shows the two edge cases a cache needs to think about: a key that is not a legal name, and a function that is not pure.

  misses <- 0L

Function operators

A function operator takes a function and returns a function with changed behaviour. The returned function has to accept whatever the original does, which is why the wrappers on this page take ... and pass it on; it has to be created with force() on the function and on any option it will read later (the trap above applies to every argument of a factory, and f is an argument like the others); and it should return what the original returns, so that it can replace the original at the call site without anything else changing. Memoising is one such operator. The next ones are those that come up in practice: logging, timing, delaying, retrying and checking arguments.

Logging, timing and delay

with_logging() prints what it is about to call and what came back. Its label defaults to deparse(substitute(f)), the name the caller used, which works because substitute() still sees the expression of the promise after f has been forced. The timing wrapper keeps the elapsed seconds in the closure; to keep this page free of timings the script prints only whether the value is a number, and uses on.exit() so that the time is recorded even if f signals an error. with_delay() waits before every call, which is how a client keeps under a rate limit; a delay of 0 seconds keeps the script fast.

source("scenario.R")

# A function operator takes a function and returns a (decorated) function.
with_logging <- function(f, label = deparse(substitute(f))) {
  force(f)
  force(label)
  function(...) {
    cat("calling ", label, " with ", ...length(), " argument(s)\n", sep = "")
    result <- f(...)
    cat(label, " returned ", length(result), " value(s)\n", sep = "")
    result
  }
}

#> calling is_valid_isbn13 with 1 argument(s)
#> is_valid_isbn13 returned 3 value(s)
#> [1] TRUE TRUE TRUE

#> calling round with 2 argument(s)
#> round returned 1 value(s)
#> [1] 3.14

# Timing: keep the elapsed seconds in the closure; print no timings.
with_timing <- function(f) {
  force(f)
  elapsed <- NA_real_ # nolint: object_usage_linter.
  wrapper <- function(...) {
    start <- proc.time()[["elapsed"]]
    on.exit({
      stop_at <- proc.time()[["elapsed"]]
      elapsed <<- stop_at - start # nolint: assignment_linter.
    })
    f(...)
  }
  wrapper
}

#> [1] TRUE

#> [1] TRUE

# Delay: wait before every call (here 0 seconds, so the script is fast).
with_delay <- function(f, seconds) {
  force(f)
  force(seconds)
  function(...) {
    Sys.sleep(seconds)
    f(...)
  }
}

Retry

A retry operator calls a function again when it fails, up to a number of times. The test below uses a deterministic stand-in for an unreliable service: make_flaky() is itself a factory with a counter, and it fails a fixed number of times before it succeeds. The wrapper catches the condition with tryCatch() (Conditions and Error Handling), logs the failure, and finally re-signals the last condition object with stop(result), so the caller sees the original message.

# A function that fails a given number of times and then works.
make_flaky <- function(failures) {
  calls <- 0L
  function(x) {
    calls <<- calls + 1L # nolint: assignment_linter.
    if (calls <= failures) {
      stop("temporary failure number ", calls, call. = FALSE)
    }
    x * 2
  }
}

with_retry <- function(f, times = 3L) {
  force(f)
  force(times)
  function(...) {
    for (attempt in seq_len(times)) {
      result <- tryCatch(f(...), error = \(e) e)
      if (!inherits(result, "error")) {
        return(result)
      }
      cat("attempt", attempt, "failed:", conditionMessage(result), "\n")
    }
    stop(result)
  }
}

sturdy <- with_retry(make_flaky(failures = 2L))
sturdy(21)
#> attempt 1 failed: temporary failure number 1
#> attempt 2 failed: temporary failure number 2
#> [1] 42

hopeless <- with_retry(make_flaky(failures = 5L), times = 2L)
tryCatch(hopeless(21), error = \(e) conditionMessage(e))
#> attempt 1 failed: temporary failure number 1
#> attempt 2 failed: temporary failure number 2
#> [1] "temporary failure number 2"

Source: R documentation: tryCatch

sturdy fails twice and succeeds on the third attempt, so the result is 42 after two log lines. hopeless is allowed two attempts for a function that fails five times, logs both failures and passes the second error to the caller, which prints its message. In real code a retry should also wait between attempts (compose it with with_delay()), catch only the error classes that are worth repeating and not every error, and give up quickly on errors that cannot go away, such as a bad argument.

Checking arguments

A decorator can also hold preconditions, so that the function it wraps stays focused on its job. with_checks() takes a named list of predicates, whose names are the messages, and tests the first argument against each of them before the call. The function it returns has the formals (x, ...), not those of is_valid_isbn13(); the last two lines show the difference, which is the cost of this style: the original function’s argument names are no longer visible with args() or in the editor’s tooltip. The defensive-programming page (Defensive Programming and Input Validation) covers checking inside the function with stopifnot() and friends, which is usually simpler when the checks belong to one function and are not shared.

source("scenario.R")

# Argument checking as a decorator: the checks live outside the function.
with_checks <- function(f, ...) {
  force(f)
  checks <- list(...)
  function(x, ...) {
    for (name in names(checks)) {
      if (!isTRUE(checks[[name]](x))) {
        stop("argument x must satisfy: ", name, call. = FALSE)
      }
    }
    f(x, ...)
  }
}
valid_isbn <- with_checks(
  is_valid_isbn13,
  "be a character vector" = is.character,
  "have no missing values" = \(x) !anyNA(x)
)
valid_isbn(books$isbn[1:2])
#> [1] TRUE TRUE
tryCatch(valid_isbn(123), error = \(e) conditionMessage(e))
#> [1] "argument x must satisfy: be a character vector"
tryCatch(valid_isbn(c("9780306406157", NA)), error = \(e) conditionMessage(e))
#> [1] "argument x must satisfy: have no missing values"

match.call() and sys.function() in a wrapper

Two tools from Functions help wrappers behave well. match.call() returns the call to the function that is running, with the arguments matched to the formals; inside a wrapper it describes the call to the wrapper, which is what the user typed, so an error message can show it (R documentation: match.call). sys.function() returns the function that is running, which is the wrapper itself, so a wrapper can read attributes that were attached to it, or refer to itself without a name (R documentation: sys.function). The last part of the script keeps the formals of the original function: formals(wrapper) <- formals(f) gives the wrapper the right interface; the body must then use those names, for instance by forwarding with match.call(), do.call() or explicit arguments.

# match.call() inside a wrapper reports the call to the wrapper, so an error
# can name what the user typed.
with_context <- function(f) {
  force(f)
  function(...) {
    call <- match.call()
    tryCatch(
      f(...),
      error = \(e) {
        stop("in ", deparse(call), ": ", conditionMessage(e), call. = FALSE)
      }
    )
  }
}
safe_log <- with_context(\(x) if (x < 0) stop("negative input") else log(x))
safe_log(1)
#> [1] 0
tryCatch(safe_log(-1), error = \(e) conditionMessage(e))
#> [1] "in safe_log(-1): negative input"

# sys.function() is the running function itself, so a wrapper can read its own
# attributes or call itself without a name.
with_name <- function(f, label) {
  force(f)
  force(label)
  structure(
    function(...) {
      me <- sys.function()
      cat("running", attr(me, "label"), "\n")
      f(...)
    },
    label = label
  )
}

#> running square root
#> [1] 4
attr(named_sqrt, "label")
#> [1] "square root"

keep_formals <- function(wrapper, f) {

}

Composing functions

Composition by hand

To compose two functions is to build one that applies the first and passes the result to the second. R has no operator for it in base R 4.6.1; the definition is one line, and the order of the arguments is a choice that you document: this page uses compose(f, g) to mean "f first, then g", which reads in the order of the calls. As in every factory, f and g must be forced. The script composes normalise_isbn() and is_valid_isbn13() and then shows what happens when they are not forced: a composed function whose parts are reassigned before its first call uses the new parts (a double that has become x - 100 gives -98 for an input of 1 where 4 was expected). The worst case is the trap that every tutorial author falls into once: f <- lazy_compose(f, f) makes the promise f refer to the variable f that has just been overwritten by the composed function itself, and calling it recurses until R reports a stack overflow. The script checks only the class of that error with inherits(failure, "stackOverflowError"), because the message depends on which stack runs out first.

source("scenario.R")

# Composition by hand: compose(f, g) runs f first, then g.
compose <- function(f, g) {
  force(f)
  force(g)
  \(x) g(f(x))
}
check_isbn <- compose(normalise_isbn, is_valid_isbn13)
check_isbn(c("978-0-306-40615-7", "978-0-306-40615-8"))
#> [1]  TRUE FALSE

# Without force(), the composed function reads f and g when it is first called.
lazy_compose <- \(f, g) \(x) g(f(x))
add_one <- \(x) x + 1
double <- \(x) x * 2
h <- lazy_compose(add_one, double)
double <- \(x) x - 100
h(1)
#> [1] -98

# The classic way to hit it: reassigning the name that was composed.
f <- \(x) x + 1
f <- lazy_compose(f, f)
failure <- tryCatch(f(1), error = \(e) e)
inherits(failure, "stackOverflowError")
#> [1] TRUE

# With force() the old f is captured and the reassignment is harmless.
f <- \(x) x + 1
f <- compose(f, f)

#> [1] 3

Composing many functions with Reduce()

Reduce(f, x) folds a list with a binary function. When the elements are functions and the binary function is compose, the result is the composition of all of them in the order of the list (R documentation: funprog). Reduce() forces the functions it applies since R 3.2.0, so the inline form Reduce(\(f, g) \(x) g(f(x)), fs) is safe even without force(); a named compose() that forces its arguments is still the clearer version. A pipeline that applies the functions to a value, without building the composed function, is a Reduce() where the accumulator is the value: Reduce(\(acc, step) step(acc), steps, x). With accumulate = TRUE the intermediate values are kept, which makes it easy to inspect where a pipeline went wrong.

source("scenario.R")

compose <- function(f, g) {
  force(f)
  force(g)
  \(x) g(f(x))
}

# Reduce() folds a list of functions into one: the first runs first.
clean_title <- Reduce(
  compose,

clean_title(c("  The Quiet   Streets ", "THE LONG TABLE"))

pipeline <- Reduce(\(f, g) \(x) g(f(x)), list(trimws, toupper, nchar))

#> [1] 2 3

# A variadic version: feed each function the result of the previous one.
pipe_through <- function(...) {

known <- \(y) y[!is.na(y)]

Partial application, do.call() and match.fun()

Partial application fixes some arguments of a function now and leaves the others for later. The hand-written version stores the fixed arguments in the closure and builds the call with do.call(), which takes a function (or its name) and a list of arguments (R documentation: do.call); match.fun() turns a function or a character string into a function and fails otherwise, so a helper can accept either (R documentation: match.fun). Negate() is the small function operator that base R provides next to Reduce() and Filter(): it returns the opposite predicate.

source("scenario.R")

# Partial application by hand: fix some arguments now, supply the rest later.
partial <- function(f, ...) {
  force(f)
  fixed <- list(...)
  function(...) do.call(f, c(fixed, list(...)))
}
round_1 <- partial(round, digits = 1)
round_1(3.14159)
#> [1] 3.1

Recursion

A recursive function calls itself on a smaller part of its input until a base case stops it. R-intro says that functions may be recursive and may themselves define functions within themselves, and its worked example is a recursive numerical integration (An Introduction to R: Recursive numerical integration). Recursion fits data that is itself nested, such as a tree, a directory or the result of parsing JSON: the function mirrors the shape of the data, and a loop would need an explicit stack. For a flat vector a vectorised function or a loop is shorter and faster; the question of when to recurse and when to iterate is taken further in Vectorisation and Iteration.

Walking a tree

The shelf as a tree: the genres of books (trimmed and lower-cased), each split by decade, with the titles as leaves. A node is either a character vector (a leaf) or a list of child nodes, so every walker has the same shape: handle the leaf, otherwise combine the results of the children. vapply() over the children keeps the combination type-safe, and the recursive call is count_titles itself, passed by name, which is how a recursive function is normally handed to an apply function.

Recall() and sys.function()

Recall() calls the function in which it appears, whatever its current name; the help page describes it as a placeholder for the name of the function in which it is called, which lets a recursive function keep working after it is renamed (R documentation: Recall). That is its entire use, and it is rare in practice: functions are almost always called by their name, and a name that is visible in the file is easier to read than a placeholder. The help page also carries a caveat: Recall() does not work correctly when it is passed as a function argument, for instance to the apply family. The script shows the working case, the renaming case that Recall() was invented for, the failure inside vapply() with its real message, and the alternative that works in an apply call, sys.function(), which returns the running function itself (R documentation: sys.function). The help page also points to local() as another way to write anonymous recursive functions.

# Recall() calls the function it appears in, whatever its current name.
fact <- function(n) if (n <= 1) 1 else n * Recall(n - 1)
fact(5)
#> [1] 120
factorial_of <- fact
rm(fact)
factorial_of(5)
#> [1] 120

fact_copy() fails because fact_named() looks for the name it was defined under, and that name was removed. Recall() has no such dependency. Passed to vapply() the call Recall is made by vapply() and not by the function, and R reports argument "FUN" is missing, with no default; in this situation name the function or capture sys.function() in a variable first, as depth_sys() does. Outside any function Recall() fails with 'Recall' called from outside a closure.

Stack limits

Every call of a closure creates an evaluation frame, and R keeps several stacks and limits in order to survive runaway recursion. The help page of Cstack_info() says that the "evaluation depth" is the number of nested R expressions currently under evaluation, and that this has a limit controlled by options("expressions") (R documentation: Cstack_info). The same help page documents the other values it reports: size and current (the size and the estimated usage of the C stack in bytes, or NA if unknown), direction and eval_depth. The sizes depend on the platform and on how R was started, so this page prints only the names. The expressions option sets a limit on the number of nested expressions that will be evaluated, with valid values from 25 to 500000 and a default of 5000; the help page warns that raising it may cause a segfault from overflow of the C stack, and that once the limit is reached an error is thrown (R documentation: options).

# Cstack_info() reports the C stack and the evaluation depth. The sizes are
# platform-specific, so only the names are shown here.

#> [1] "size"       "current"    "direction"  "eval_depth"
Cstack_info()[["eval_depth"]] > 0L
#> [1] TRUE
getOption("expressions")
#> [1] 5000

count_down <- function(n) if (n == 0) 0 else 1 + count_down(n - 1)
count_down(1000)
#> [1] 1000

# Too deep for the default limit of 5000 nested expressions.
too_deep <- tryCatch(count_down(10000), error = \(e) e)
conditionMessage(too_deep)
#> [1] "evaluation nested too deeply: infinite recursion / options(expressions=)?"
class(too_deep)
#> [1] "expressionStackOverflowError" "stackOverflowError"
#> [3] "error"                        "condition"

# A lower limit makes the same call fail earlier; restore it afterwards.
old <- options(expressions = 100)
low <- tryCatch(count_down(1000), error = \(e) conditionMessage(e))
options(old)
low
#> [1] "evaluation nested too deeply: infinite recursion / options(expressions=)?"

#> [1] 5000

The recursion count_down(1000) works, count_down(10000) hits the default limit of 5000 nested expressions, and the error text is evaluation nested too deeply: infinite recursion / options(expressions=)?. Lowering expressions to 100 makes the thousand-level call fail with the same message; the example restores the option afterwards with the value returned by options(), which is the pattern to use whenever a script changes an option temporarily. How many levels of recursion fit under 5000 depends on the function and on whether it has already been byte-compiled by the JIT compiler (the evaluation depth that Cstack_info() reports for the same call can differ between the first calls and later ones), which is why the example does not state a depth.

Tail calls: Tailcall() and Exec() (experimental)

A call is a tail call when it is the last thing a function does: its value is returned as the value of the caller, with nothing left to compute. A language that eliminates tail calls can run a tail-recursive function in constant stack space. R does not do this by itself. R 4.4.0 added two functions to make it possible, and the NEWS entry describes them like this: "New experimental functions Tailcall() and Exec() to support writing stack-space-efficient recursive functions." (R NEWS: Changes in R 4.4.0). They are experimental: the help page says they "may be changed or dropped in future released versions of R", so code that uses them for production work should be isolated behind one function and tested on every R upgrade. They are documented on one help page (R documentation: Tailcall and Exec).

Tailcall(FUN, ...) evaluates a call to FUN (a function or the name of one) with the arguments in the current environment. If the Tailcall() expression is in tail position in an R function and no on.exit() expression is set, the evaluation context of the new call replaces the currently executing one instead of being added to the stack. The help page adds two consequences: because of lazy evaluation it may be necessary to force some arguments to avoid accumulating deferred evaluations, and stack traces from traceback() or sys.calls() show only the call given to Tailcall(), not the call whose stack entry was replaced.

A tail-recursive sum

The first script sums the integers from 1 to n with an accumulator. The plain recursive version works for a thousand levels and fails for 100000 with a stack error (here the node stack message). The Tailcall() version computes the same sum for a hundred thousand and for a million levels, and its result for 1e5 is the Gauss formula n(n+1)/2 = 5000050000. Note the line acc <- acc + n before the call: without it the argument acc + n would be passed as an unevaluated promise, each promise referring to the previous one, and the chain of 100000 promises would be forced at once at the end, which overflows the stack even though the calls themselves took no space. The last part of the script shows exactly that, under the expressions error. This is the "force some arguments" caveat from the help page, and it is the same lesson as the function-factory trap above, in a different place.

# Plain recursion: one evaluation frame per element.
sum_plain <- function(n, acc = 0) {
  if (n == 0) {
    return(acc)
  }
  sum_plain(n - 1, acc + n)
}
sum_plain(1000)
#> [1] 500500
tryCatch(sum_plain(1e5), error = \(e) conditionMessage(e))
#> [1] "node stack overflow"

# Tailcall() (R 4.4.0, experimental) replaces the running call with the new one.
sum_tail <- function(n, acc = 0) {
  if (n == 0) {
    return(acc)
  }
  acc <- acc + n # evaluate the accumulator now, not as a chain of promises
  Tailcall(sum_tail, n - 1, acc)
}
sum_tail(1000)
#> [1] 500500
sum_tail(1e5)
#> [1] 5000050000
sum_tail(1e6)
#> [1] 500000500000

count_to <- function(n, i = 0L) {

}

When the context is not reused

The reuse of the frame is a property of the call, not of the function name. The script below counts the frames on the stack at the bottom of a 50-level recursion: 51 for plain recursion (the call from the top level plus fifty more), 1 for Tailcall(), which is the stack-trace remark of the help page in numbers. It then adds an on.exit() expression to the function, which turns the reuse off; the frame count goes back to 51 and a deep call fails with the C stack error. A Tailcall() that is not in tail position, such as 1 + Tailcall(...), is evaluated in the ordinary way and gives the correct value for a small input (10), but it grows the stack and fails for 1e5.

# The number of frames on the call stack at the bottom of the recursion.
probe_plain <- function(n) {
  if (n == 0) length(sys.calls()) else probe_plain(n - 1)
}
probe_tail <- function(n) {
  if (n == 0) length(sys.calls()) else Tailcall(probe_tail, n - 1)
}
probe_plain(50)
#> [1] 51
probe_tail(50)
#> [1] 1

# An on.exit() expression stops the context from being reused.
probe_exit <- function(n) {
  on.exit(invisible(NULL))
  if (n == 0) length(sys.calls()) else Tailcall(probe_exit, n - 1)
}
probe_exit(50)
#> [1] 51
generic <- \(e) gsub("[0-9]+", "<n>", conditionMessage(e))
tryCatch(probe_exit(1e5), error = generic)
#> [1] "C stack usage  <n> is too close to the limit"

Exec()

Exec(expr, envir) evaluates a call expression expr in the environment envir (by default the environment from which Exec() is called), replacing the current call context under the same rules as Tailcall(). The help page suggests it for simplifying the call stack of functions that build an expression and then evaluate it, and its example is a simplified do.call(). The script uses the stack depth to show the effect (a function called through Exec() has one frame fewer) and adapts the help page’s docall() so that the frames of do.call() and of docall() can be listed: the do.call() frame stays on the stack (it is called runner in the output because that is the name it was called under) and the Exec()-based version leaves nothing behind.

# Exec() evaluates a call expression in place of the current call context.
inner <- function() length(sys.calls())
via_call <- function() inner()
via_exec <- function() Exec(quote(inner()), environment())
via_call()
#> [1] 2
via_exec()
#> [1] 1

# A simplified do.call() written with Exec() (adapted from the help page):
# its own frame is not left on the call stack.
docall <- function(what, args) {
  Exec(as.call(c(list(substitute(what)), args)), parent.frame())
}
frames <- function() {
  vapply(sys.calls(), \(cl) as.character(cl[[1L]])[[1L]], character(1))
}
run <- function(runner) runner("frames", list())
run(do.call)
#> [1] "run"    "runner" "frames"
run(docall)
#> [1] "run"    "frames"

Trampolines: the alternative before R 4.4.0

Before Tailcall(), the way to run a deeply tail-recursive computation in constant stack space was a trampoline: the recursive function does not call itself but returns a function (a thunk) that would make the next step, and a driver loop keeps calling the thunks until a plain value comes back. The stack never holds more than the driver and one step. It works on every R version, it needs no experimental feature, and it asks the author to write the recursion in the thunk-returning style; the acc <- acc + n line is needed here for the same reason as above. Today a plain loop is shorter than either a trampoline or Tailcall() for a computation like this, and recursion remains the right shape only when the problem is recursive (the tree above) and shallow.

# A trampoline: each step returns a function (a thunk) instead of calling
# itself, and a loop keeps calling thunks until a plain value comes back.
trampoline <- function(f, ...) {
  result <- f(...)
  while (is.function(result)) {
    result <- result()
  }
  result
}
sum_thunk <- function(n, acc = 0) {
  if (n == 0) {
    return(acc)
  }
  acc <- acc + n
  \() sum_thunk(n - 1, acc)
}
trampoline(sum_thunk, 1e5)
#> [1] 5000050000
trampoline(sum_thunk, 10)
#> [1] 55
