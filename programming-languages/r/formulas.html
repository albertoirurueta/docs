Formulas

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. Everything on this page is base R (the base, stats, graphics and utils packages that ship with R), and every example runs; the lintr 3.4.0 default linters were used only to check the scripts. Two add-on packages are named in a sentence each and not run: purrr 1.2.2 and ggplot2 4.0.3. A formula is the small piece of R syntax that looks like y ~ x. It is how R programmers say "y depends on x" to a function, and it is the way almost every statistical modelling function in R is told what to fit. It is also an ordinary R object with a class, a length, an environment and a place in the language, and base R reuses it well outside modelling: aggregate(pages ~ genre, ...) summarises by group, xtabs(~ genre, ...) counts, boxplot(pages ~ genre, ...) splits. This page explains what the tilde operator builds, how the formula language expands the operators +, -, :, *, /, ^, %in%, . and I(), how terms(), model.frame() and model.matrix() turn a formula and a data frame into a design matrix, how factors are coded by contrasts, how to change a formula with update() and build one with reformulate(), and how the other formula-using functions of base R read it.

Every example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines that start with #> are what it printed. The scripts also pass the default lintr linters; a # nolint: comment marks a line where the idiom on show is what a default linter dislikes, so the linter does not hide the lesson. The names books, loans, shelf_today, loan_days and the book() constructor come from the running library-shelf scenario described on the section index: a script that needs them starts with source("scenario.R"). The books data frame has the columns pages, year and genre that most formulas below use. Its genre column holds nine spellings of six genres ("Fiction", "fiction", "Fiction " and so on), so the scripts that model by genre first run books$genre <- tolower(trimws(books$genre)); cleaning data is the subject of Strings and Regular Expressions and Data Frames. Where a message contains quotation marks, they are the typographic quotes R prints in a UTF-8 locale. A formula created inside a function prints an extra <environment: ...> line holding a memory address that changes on every run; the examples avoid printing that line and use environmentName() or deparse1() instead, and say so where it matters.

This page is the third of the three metaprogramming pages. A formula is a call, so everything in Language Objects and Quoting applies to it, and the way model functions evaluate formulas against a data frame is the data-mask idea of Evaluation and Non-Standard Evaluation. The fitting of models themselves (lm(), glm(), residual diagnostics, anova()) belongs to Statistical Models; this page stops where the model is fitted and only uses lm() to show what a formula does.

What a formula is

The tilde operator

The tilde ~ separates the left-hand side and the right-hand side of a model formula. Its help page is short: the left-hand side is optional, and a formula has mode call whose components are ~, the left-hand side (if present) and the right-hand side, in that order, so a one-sided formula has two components. The operator does not evaluate either side. ~ is a primitive of the kind called a "special" (the same kind as quote() and if): R hands it the unevaluated expressions on both sides, and it returns the call itself, with two additions that make it a formula, a class attribute and an environment. That is why a formula can mention variables that do not exist (no_such_response ~ no_such_predictor is a perfectly good object), why y ~ x costs nothing to create, and why it is the model-fitting function, not the tilde, that later decides what the names mean.

source("scenario.R")

# `~` quotes both sides and returns a formula.
f <- pages ~ genre
f
#> pages ~ genre
class(f)
#> [1] "formula"
typeof(f)
#> [1] "language"
length(f)
#> [1] 3
f[[1]]
#> `~`
f[[2]]
#> pages
f[[3]]
#> genre

# A one-sided formula has no left-hand side: length 2, and [[2]] is the rhs.
g <- ~genre
length(g)
#> [1] 2
g[[2]]
#> genre

# Nothing is evaluated, so the names need not exist.
no_such_response ~ no_such_predictor
#> no_such_response ~ no_such_predictor
exists("no_such_response")
#> [1] FALSE

# `~` is a primitive "special": its arguments are not evaluated.
typeof(`~`)
#> [1] "special"
is.primitive(`~`)
#> [1] TRUE

Source: R documentation: ~

The tilde has a very low precedence: it binds more loosely than | and || and more tightly than the assignments and ?, so pages ~ year + genre is read as pages ~ (year + genre) without parentheses, and a formula can contain whole logical expressions on either side. The table of operators in Operators and Precedence lists it, and the manual lists it as the operator used for model formulae, either unary or binary (The R Language Definition: Operators). The unary form is the one-sided formula: ~ genre has no response, which is what xtabs() and cor.test() expect, and what model.matrix() needs when there is nothing to predict.

A formula is a call until it is evaluated

Quoting a formula gives a call of class "call", and evaluating that call is what produces the formula. Everything R can do to a call it can do to a formula: index it with [[ (f[[2]] is the left-hand side), replace parts, convert it to a list, ask for all the names in it with all.vars(). This is how the model-fitting functions take a formula apart, and how a program can build or edit one (see Building and inspecting formulas below).

# Quoting `y ~ x` gives a call; evaluating the call makes the formula.
cl <- quote(pages ~ year)
class(cl)
#> [1] "call"
is.call(cl)
#> [1] TRUE
f <- eval(cl)
class(f)
#> [1] "formula"
identical(f, pages ~ year)
#> [1] TRUE

# A formula is a call with two attributes: the class and the environment.
names(attributes(f))
#> [1] "class"        ".Environment"
attr(f, "class")
#> [1] "formula"
attr(f, ".Environment")
#> <environment: R_GlobalEnv>

# Because it is a call, it can be indexed and modified like one.
f[[3]] <- quote(year + genre)
f
#> pages ~ year + genre
f[[2]] <- quote(log(pages))
f
#> log(pages) ~ year + genre
as.list(f)
#> [[1]]
#> `~`
#>
#> [[2]]
#> log(pages)
#>
#> [[3]]
#> year + genre
#>
deparse1(f)
#> [1] "log(pages) ~ year + genre"
all.vars(f)
#> [1] "pages" "year"  "genre"

Source: R documentation: ~

The two attributes are the whole difference between the call quote(pages ~ year) and the formula pages ~ year. print() of a formula (the print.formula() method) shows the environment only when it is not the global environment, through its showEnv argument, whose default is !identical(e, .GlobalEnv); that is the reason a formula built in a function prints an extra line. The same formula can be turned back into text with deparse1(), which is the safest way to show or compare formulas in output.

The environment of a formula

The formula keeps the environment in which it was created, and that is its second purpose. The help page of formula() says it plainly: a formula object has an associated environment, and model.frame() uses that environment, not the parent environment of the call, to evaluate the variables that are not found in the supplied data argument. So when lm(pages ~ year, data = books, subset = year > cutoff) runs, pages and year are looked up in books first, and cutoff, which is not a column, is looked up in the environment of the formula, which is the frame of the function that wrote the formula. The R language definition makes a related point about the call stack: some functions, in particular those that use and manipulate model formulas, need to simulate dynamic scope by accessing the call stack directly (The R Language Definition: The call stack). The environments themselves, and parent.frame(), are the subject of Scoping, Environments and Closures.

source("scenario.R")

# A formula made at the console remembers the global environment.
f <- pages ~ year
environment(f)
#> <environment: R_GlobalEnv>
environmentName(environment(f))
#> [1] "R_GlobalEnv"

# A formula made inside a function remembers that call's frame.
make_formula <- function() {
  cutoff <- 2000 # nolint: object_usage_linter.
  pages ~ year
}
g <- make_formula()
environmentName(environment(g))
#> [1] ""
identical(environment(g), globalenv())
#> [1] FALSE
ls(environment(g))
#> [1] "cutoff"
get("cutoff", envir = environment(g))
#> [1] 2000

# print() shows the environment when it is not the global one. That line holds
# a memory address, which changes on every run, so the page omits it.
print(g, showEnv = FALSE)
#> pages ~ year

# Variables that are not columns of `data` are looked up in that environment.
fit_since <- function(data) {
  cutoff <- 2000
  lm(pages ~ year, data = data,
     subset = year > cutoff) # nolint: object_usage_linter.
}
coef(fit_since(books))
#> (Intercept)        year
#> -5747.76495     2.97732

# The same call fails at the console: `cutoff` does not exist there.
cutoff_missing <- tryCatch(
  lm(pages ~ year, data = books, subset = year > cutoff),
  error = \(e) conditionMessage(e)
)
cutoff_missing
#> [1] "object 'cutoff' not found"

Source: R documentation: formula

Two practical consequences follow. A formula that is stored and used later (in a list, in a package function, saved with saveRDS()) carries a whole environment with it, and everything that environment references stays alive and is serialized with it; a formula built at the console carries only the global environment, which is saved as a reference to the global environment and not as a copy, but a formula built inside a function carries a copy of the function’s frame. And a formula that works in one place can fail in another: the last call above works inside fit_since() and fails at the console, because the two formulas see different environments. When the data and every variable the formula needs are columns of data, none of this matters; it starts to matter as soon as a formula refers to a variable that is not a column, or is passed between functions.

formula() and as.formula()

A string, a fitted model or a data frame can be turned into a formula with formula(), which is a generic function, or as.formula(), which is almost identical and additionally keeps the attributes of an object that already is a formula. The help page describes the methods: for a fitted model the default method looks for a "formula" component, then a "terms" component, then the formula argument of the call, and finally a "formula" attribute; for a data frame the first column becomes the response and the remaining columns the right-hand side, or, with one column, a one-sided formula. DF2formula() is the helper behind the data frame method. The argument env of as.formula() (default parent.frame()) sets the environment of a formula built from a string; an existing formula keeps its own.

source("scenario.R")

# formula() and as.formula() turn a string into a formula.
f <- as.formula("pages ~ year + genre")
f
#> pages ~ year + genre
class(f)
#> [1] "formula"
environmentName(environment(f))
#> [1] "R_GlobalEnv"

# The default `env` is parent.frame(): inside a function, the function's frame.
build <- function(text) as.formula(text)
environmentName(environment(build("pages ~ year")))
#> [1] ""
identical(environment(build("pages ~ year")), globalenv())
#> [1] FALSE

# env makes the environment explicit.
shared <- new.env()
h <- as.formula("pages ~ year", env = shared)
identical(environment(h), shared)
#> [1] TRUE

# A formula passes through unchanged, so as.formula() is safe on either form.
identical(as.formula(f), f)
#> [1] TRUE
identical(formula(f), f)
#> [1] TRUE

# formula() also reads the formula out of a fitted model, and a data frame
# becomes first column ~ the rest.
fit <- lm(pages ~ year, data = books)
formula(fit)
#> pages ~ year
formula(books[c("pages", "year", "genre")])
#> pages ~ year + genre
formula(data.frame(pages = 1))
#> ~pages

# A length-one character vector is the supported input. Longer ones are
# deprecated since R 4.0.0.
res <- tryCatch(
  formula(c("pages ~", "year")),
  warning = \(w) conditionMessage(w)
)
res
#> [1] "Using formula(x) is deprecated when x is a character vector of length > 1.\n  Consider formula(paste(x, collapse = \" \")) instead."

Source: R documentation: formula

Two version details are worth knowing (full list in Version notes). Since R 3.6.0 formula(model.frame(frml, ...)) returns the original frml in every case, and the earlier behaviour is available as DF2formula(). And since R 4.0.0 a character vector of length greater than one is deprecated as input: the old behaviour parsed the elements as separate lines of code and used the first complete expression, which silently truncated bad input. The last example above shows the real warning text, which also suggests the replacement, formula(paste(x, collapse = " ")). The help page adds that building the formula by evaluating a call, eval(call("~", quote(foo + bar))), is an order of magnitude more efficient than formula(c("~", "foo + bar")).

The formula language

The right-hand side of a model formula is written in a small language of its own, in which the usual arithmetic operators mean something different. The formula operators are similar in effect to the Wilkinson and Rogers notation of programs such as Glim and Genstat, with one inevitable change: the operator written . there becomes : in R, because the period is a valid character in a name (An Introduction to R: Defining statistical models; formulae). The notation is summarised there (based on Chambers and Hastie, 1992), and the help page ?formula repeats it.

The best way to learn the language is to look at what terms() makes of an expression, because the term labels are exactly the columns that will be built. The script below applies the operators to the abstract names a, b and c (nothing is evaluated, so they need not exist) and prints the term labels, and then the intercept for the six ways of writing it.

# What each operator expands to: the term labels and the intercept of terms().
expand <- function(f) {
  tt <- terms(f)
  paste(attr(tt, "term.labels"), collapse = ", ")
}

forms <- list(
  y ~ a + b,
  y ~ a:b,
  y ~ a * b,
  y ~ (a + b + c)^2,
  y ~ (a + b + c)^2 - a:b,
  y ~ a + b %in% a,
  y ~ a / b,
  y ~ a + b - a,
  y ~ a * b - a,
  y ~ a + a
)
expansions <- data.frame(
  formula = vapply(forms, deparse1, character(1L)),
  terms = vapply(forms, expand, character(1L))
)
print(expansions, right = FALSE)
#>    formula                 terms
#> 1  y ~ a + b               a, b
#> 2  y ~ a:b                 a:b
#> 3  y ~ a * b               a, b, a:b
#> 4  y ~ (a + b + c)^2       a, b, c, a:b, a:c, b:c
#> 5  y ~ (a + b + c)^2 - a:b a, b, c, a:c, b:c
#> 6  y ~ a + b %in% a        a, a:b
#> 7  y ~ a/b                 a, a:b
#> 8  y ~ a + b - a           b
#> 9  y ~ a * b - a           b, a:b
#> 10 y ~ a + a               a

# The intercept is the attribute "intercept": 1 when present, 0 when removed.
with_without <- list(
  y ~ x, y ~ x - 1, y ~ x + 0, y ~ 0 + x, y ~ 1, y ~ x - 1 + 1
)
data.frame(
  formula = vapply(with_without, deparse1, character(1L)),
  intercept = vapply(
    with_without, \(f) attr(terms(f), "intercept"), numeric(1L)
  )
)
#>         formula intercept
#> 1         y ~ x         1
#> 2     y ~ x - 1         0
#> 3     y ~ x + 0         0
#> 4     y ~ 0 + x         0
#> 5         y ~ 1         1
#> 6 y ~ x - 1 + 1         1

Source: R documentation: terms.formula

A few lines of the table deserve a remark. Row 8, y ~ a + b - a, shows that - removes a term, not a variable, and row 9, y ~ a * b - a, shows the trap in the language: removing the main effect a while keeping the interaction a:b produces a model that violates marginality. R does what it is told, and An Introduction to R warns that fitting a model with an interaction but without the corresponding main effects will in general lead to surprising results and is for experts only. Row 10 shows that a repeated term is counted once. The intercept rows agree with the R FAQ on the differences from S: in R y ~ x + 0 is an alternative to y ~ x - 1, and a model with no parameters at all is written y ~ 0 (R FAQ 3.3.2: Models). The last row, y ~ x - 1 + 1, shows that later terms win: the 1 puts the intercept back.

Arithmetic inside a formula: I() and function calls

The symbols +, -, *, ^ and / therefore have two lives. In the formula language they combine terms; inside the parentheses of a function call they are plain arithmetic, so log(pages), sqrt(year) or poly(year, 2) are calls whose value becomes a column, and the label of that term is the text of the call. To use an operator arithmetically at the top level of a term the expression is wrapped in I(), the "as is" function (R documentation: I); it adds the class "AsIs" to its argument, and model code treats the result as the plain value. The R FAQ states the classic difference from S: where S regressed on a power with lm(y ~ x^3), R needs the power insulated, lm(y ~ I(x^3)).

source("scenario.R")

# Inside a formula, ^ means "crossing to degree 2", not squaring.
attr(terms(pages ~ year^2), "term.labels")
#> [1] "year"
# I() ("as is") protects arithmetic.
attr(terms(pages ~ year + I(year^2)), "term.labels")
#> [1] "year"      "I(year^2)"

# The columns of the design matrix show the difference.
colnames(model.matrix(pages ~ year^2, data = books))
#> [1] "(Intercept)" "year"
colnames(model.matrix(pages ~ year + I(year^2), data = books))
#> [1] "(Intercept)" "year"        "I(year^2)"
colnames(model.matrix(pages ~ I(year - 2000), data = books))
#> [1] "(Intercept)"    "I(year - 2000)"

# Functions of a variable are terms of their own. poly() does not accept NA,
# and it runs before any na.action can drop the row (year is NA in one book).
poly_error <- tryCatch(
  model.matrix(pages ~ poly(year, 2), data = books),
  error = \(e) conditionMessage(e)
)
poly_error
#> [1] "missing values are not allowed in 'poly'"
dated <- books[!is.na(books$year), ]
colnames(model.matrix(pages ~ log(year) + poly(year, 2), data = dated))
#> [1] "(Intercept)"    "log(year)"      "poly(year, 2)1" "poly(year, 2)2"

# a + b means two terms; I(a + b) means one term, the sum.
d <- data.frame(y = 1:4, a = c(1, 2, 3, 4), b = c(2, 1, 4, 3))
colnames(model.matrix(y ~ a + b, d))
#> [1] "(Intercept)" "a"           "b"
colnames(model.matrix(y ~ I(a + b), d))
#> [1] "(Intercept)" "I(a + b)"
model.matrix(y ~ I(a + b), d)[, 2]
#> 1 2 3 4
#> 3 3 7 7

# AsIs objects keep the class "AsIs" and print like the value.
class(I(books$year[1:3]))
#> [1] "AsIs"
I(books$year[1:3])
#> [1] 1974 1813 2019

# Variable names that are not syntactic are quoted with backticks.
odd <- data.frame(y = 1:3, `page count` = c(10, 20, 35), check.names = FALSE)
coef(lm(y ~ `page count`, odd))
#>  (Intercept) `page count`
#>   0.28947368   0.07894737

Source: R documentation: I

Note the first lines: pages ~ year^2 does not square the year, because ^ means "crossing to the given degree", and crossing a single variable with itself gives the variable, so the model has the single column year. The poly() error is a real subtlety of how formulas are evaluated: the variables in the formula (including calls such as poly(year, 2)) are evaluated first, in model.frame(), and rows with missing values are dropped afterwards by the na.action, so a function that rejects NA fails before the action can drop the row. The help page of model.frame() adds a related warning: because the variables are evaluated before the rows are dropped by subset, data-dependent bases such as orthogonal polynomials (poly()) or splines (bs() of the splines package) are computed on the full data set rather than on the subset, and the same holds for summary statistics such as mean(). A variable name that is not syntactic is written between backticks, as in the last example; the help page of formula() cautions that not all code that uses formulas will accept such names.

The dot, the intercept and the other conventions

The symbol . has two special meanings, and the help page of formula() keeps them apart. In a formula given to a model-fitting function together with a data argument it stands for all the columns of data that are not otherwise in the formula, and terms(formula, data = data) expands it. In the context of update.formula() only, it stands for whatever was previously in that part of the formula (see Updating formulas and fitted models). Without data, terms() cannot expand it, and says so.

The intercept is always part of the model unless it is removed with -1, + 0 or 0 +; a model without an intercept changes how summary.lm() computes R squared, which is the subject of R FAQ 7.41 and is shown in Pitfalls.

Anything else in a formula is a call to an ordinary function: the vertical bar in y ~ a | b has no meaning to terms() (lattice, which ships with R, gives it one), and s(a) is a term labelled s(a) unless it is declared a "special" in terms(). The specials argument marks calls of the named functions in the "specials" attribute, which is how aov() finds Error() terms and how the survival package (3.8-6, which ships with R) finds strata() and cluster(). The help page cautions that specials are nothing more than syntax, so y ~ stats::offset(w) + x does not fix the coefficient of w: the call is to stats::offset, not to offset.

The rule is about margins. In genre:era the factor era is coded by contrasts (1) when the term left after removing era, which is genre, is in the model, and the factor genre is coded by dummy variables (2) when the term left after removing genre, which is era, is not. In the first model the interaction therefore has one column for each level of genre, times the single contrast column of era; in the second model neither margin is present, so both factors are coded by dummy variables and the interaction has one column for each of the six combinations. R tracks this automatically, which is why terms(), and not the formula text, is the reliable description of the model.

From a formula to a model frame

model.frame() evaluates the variables of the formula and returns a data frame with one column per variable or expression, in the order of the variables attribute, plus the terms object as the "terms" attribute. The procedure is given in the help page: all the variables in formula, subset and the extra arguments are looked up first in data and then in the environment of the formula; then the subset expression is evaluated and used as a row index; then the na.action function is applied (and may add attributes to the frame); and finally the levels of factors are adjusted according to drop.unused.levels and xlev. The na.action is taken, in order, from an attribute of data, from options("na.action"), and then na.fail; the factory-fresh option is na.omit, so rows with a missing value in any variable of the model disappear silently, and the number of observations can be smaller than the number of rows. The "na.action" attribute of the result records which rows went (this is what summary.lm() reports as observations deleted due to missingness).

The model matrix

model.matrix() converts the terms and a model frame into the numeric design matrix, the matrix X of the equation in An Introduction to R, in which each term defines a collection of columns. Character variables are coerced to factors; after that, all variables on the right-hand side must be logical, integer, numeric or factor. A factor of k levels contributes k - 1 columns coded by the contrasts in force (unordered factors by treatment contrasts by default, as the next section explains), unless the intercept is missing, in which case the first factor is coded by dummy variables for all its levels. An interaction contributes the products of the columns of its components. The matrix has two attributes: "assign", an integer vector giving for each column the term that created it (0 is the intercept and positive values count the terms in the order of term.labels), and "contrasts", a named list that says which contrasts were used for each factor.

The help page states a rule that explains the column order of interactions: the variable whose levels vary fastest is the first one to appear in the formula, not in the term, so in ~ a + b + b:a the interaction has a varying fastest. It also says that, by convention, a response variable that also appears on the right-hand side is dropped from there with a warning, although interactions involving it are retained. The number of rows of the last three calls is the practical thing to remember: pages ~ year loses the three rows with a missing pages or year, the one-sided ~year loses only the row with a missing year, and ~genre loses none because every genre is present. When lm() reports fewer observations than the data frame has rows, this is the reason. For a very large model with mostly zero columns, the Matrix package provides sparse.model.matrix(); the help page points to it.

Contrasts

How is a factor with k levels turned into columns? An Introduction to R explains it (An Introduction to R: Contrasts): an unordered factor generates k - 1 columns, the indicators of its second to last levels, so that the implicit parameterisation contrasts the response at each level with the response at the first; an ordered factor generates k - 1 columns that are the orthogonal polynomials on 1, ..., k without the constant term. The setting is options("contrasts"), a pair of function names for unordered and ordered factors, with the default c("contr.treatment", "contr.poly"). The manual adds a difference from the S language that older textbooks may follow: S used Helmert contrasts for unordered factors, and R’s default is a deliberate choice because treatment contrasts are thought easier for newcomers to interpret.

The coding functions are all documented in the same help page. Each takes the number of levels (or the vector of level names) and returns a matrix with one row per level and one column per coefficient: contr.treatment() compares each level with a base level (the first by default; the base argument chooses another), contr.SAS() is the same with the last level as base, contr.sum() compares each level with the grand mean and makes the last level the negative sum of the others, contr.helmert() compares each level with the mean of the previous ones, and contr.poly() gives orthogonal polynomials, labelled .L, .Q, .C, ^4 and so on for linear, quadratic, cubic and higher degrees.

The coding changes what the coefficients mean, but not the model: the fitted values, residuals and tests of the whole factor are the same. The script below fits one model with three codings and compares the coefficients against the group means.

A coefficient in a model with an interaction or in a model without a baseline cannot be interpreted without knowing the coding, which is the point of having "contrasts" attached to the model matrix. The model matrix of the previous section is built with the contrasts of each factor, and there are three ways to change them, from the widest to the narrowest:

  • options(contrasts = c(unordered, ordered)) changes the default for every later model fit in the session.

  • contrasts(f) <- value stores a contrast matrix (or the name of a coding function) in the factor f itself; the "contrasts" attribute travels with the factor into the model frame. A how.many argument limits the number of columns.

  • C(f, contr, how.many) sets the contrasts of f inside the formula, leaving the data untouched (C(genre, sum) or C(genre, base = 3)), and contrasts.arg = list(f = ...) passes them to model.matrix() and to the fitting functions (lm(..., contrasts = list(...))).

The argument contrasts.arg of model.matrix() overrides both the default and any contrasts stored on the factor. R 4.3.0 made C() and contrasts<- preserve the level names when given a function object as well as a function name (before that only a name did), and R 3.6.0 started to warn about an invalid contrasts.arg.

How modelling functions use a formula

The functions of the lm() family do not interpret the formula themselves. They all follow the same recipe, which is worth knowing because a package that offers a new kind of model almost always copies it: capture the call, keep the arguments that model.frame() understands, call model.frame() with them, extract the response with model.response(), build the design matrix with model.matrix(), and hand the numbers to the fitting code. The script below is a complete model function that fits a least-squares line that way; its first lines are the standard idiom (match.call(), match() on the argument names, mf[[1L]] <- quote(stats::model.frame) and eval(mf, parent.frame())), which also explains why subset and na.action are arguments of lm() and why subset can use the names of the columns. The machinery of match.call(), eval() and parent.frame() is the subject of Evaluation and Non-Standard Evaluation.

source("scenario.R")
books$genre <- tolower(trimws(books$genre))

# The skeleton of nearly every modelling function: capture the call, keep the
# formula-related arguments, turn the call into model.frame(), evaluate it in
# the caller's frame, then pull out the response and the design matrix.
slope_fit <- function(formula, data, subset,
                      na.action) { # nolint: object_name_linter.
  cl <- match.call()
  mf <- match.call(expand.dots = FALSE)
  keep <- match(c("formula", "data", "subset", "na.action"), names(mf), 0L)
  mf <- mf[c(1L, keep)]
  mf[[1L]] <- quote(stats::model.frame)
  mf <- eval(mf, parent.frame())
  y <- model.response(mf)
  x <- model.matrix(attr(mf, "terms"), mf)
  beta <- solve(crossprod(x), crossprod(x, y))[, 1L]
  list(call = cl, coefficients = beta, n = length(y))
}

offset()

A term wrapped in offset() has its coefficient fixed at one. Modelling functions such as glm() use it for exposure (for instance offset(log(population)) in a Poisson model). In terms() the offset has an entry in the "offset" attribute but not in term.labels; model.frame() keeps its column under the label of the call; model.matrix() has no column for it; and model.offset() extracts the sum of the offsets. The offset argument of the fitting function is an equivalent way, and the two add up.

Updating formulas and fitted models

update() is a generic function with two ways to use it that share an idea. For a formula, update.formula(old, new) takes the new formula as a template: a dot on the left of the new formula stands for the left-hand side of the old one, and a dot on the right for its right-hand side. The result is simplified with terms.formula(simplify = TRUE), so terms that are added twice appear once and - removes a term; either argument may also be a length-one character vector, which is coerced with as.formula(), and the environment of the result is the environment of the old formula. For a fitted model, update(model, new.formula, ...) edits the call that created the model and evaluates it again, which is a convenient way to fit a model that differs from a previous one by a few added or removed terms (An Introduction to R: Updating fitted models).

source("scenario.R")

# `.` in the new formula means "what was there before", left and right.

#> pages ~ year + genre
update(f, log(.) ~ .)
#> log(pages) ~ year
update(f, ~ . + I(year^2))
#> pages ~ year + I(year^2)
update(f, . ~ . - 1)
#> pages ~ year - 1
update(pages ~ genre * year, . ~ . - genre:year)
#> pages ~ genre + year
update(f, sqrt(.) ~ . + genre)
#> sqrt(pages) ~ year + genre

# The right-hand side is simplified the way terms(simplify = TRUE) does.
update(pages ~ year + genre, . ~ . - year)
#> pages ~ genre
update(pages ~ year, . ~ . + year)
#> pages ~ year

# The new formula may be a string; it is coerced with as.formula().

#> pages ~ year + genre

Building and inspecting formulas

A formula can be built from text, from term labels or by editing another formula. reformulate() is the base tool for the second case: it takes a character vector of term labels and, optionally, a response, and returns a formula in the environment of the caller. Its help page describes the arguments: the labels are joined with + when there are several, a zero-length vector gives an intercept-only (or empty) right-hand side, response is a character string, a symbol or a call, intercept = FALSE appends -1, and env sets the environment of the result (added in R 3.6.0). Non-syntactic names must be protected with backticks by the caller. Anything else that terms() can parse, such as "year * genre", can be a label.

source("scenario.R")

predictors <- c("year", "genre")

# reformulate() builds a formula from term labels; no string pasting.

#> pages ~ year + genre
reformulate(predictors)
#> ~year + genre
reformulate(predictors, response = "pages", intercept = FALSE)
#> pages ~ year + genre - 1
reformulate("year * genre", response = "pages")
#> pages ~ year * genre

# The response can be a symbol or a call.
reformulate("year", response = quote(log(pages)))
#> log(pages) ~ year
reformulate(predictors, response = as.name("pages"))
#> pages ~ year + genre

# Non-syntactic names are protected with backticks.
cols <- c("page count", "year")
tryCatch(reformulate(cols), error = \(e) "Syntax error.")
#> [1] "Syntax error."
reformulate(sprintf("`%s`", cols), response = "pages")
#> pages ~ `page count` + year

# The string-pasting way produces the same formula, with more room for typos.
identical(
  as.formula(paste("pages ~", paste(predictors, collapse = " + "))),
  reformulate(predictors, response = "pages")
)
#> [1] TRUE

#> [1] "R_GlobalEnv"
shared <- new.env()
identical(environment(reformulate(predictors, "pages", env = shared)), shared)
#> [1] TRUE

reformulate(character(), response = "pages")

Formulas outside modelling

The formula is a convenient piece of syntax for "this variable by these groups", and several functions of base R take it for that purpose, with data and sometimes subset and na.action arguments that work as in model.frame(). All of them build their model frame the same way, so the same rules apply: the variables are looked up in data and then in the environment of the formula, and rows with missing values are dropped by default.

  • aggregate(formula, data, FUN) applies FUN to the left-hand variable(s) within the groups of the right-hand side. cbind(a, b) ~ g has two responses; a dot on the left means all other columns; a dot on the right means all other columns as groups. Since R 4.2.0 the first argument of the formula method is called x, like the generic’s, so portable code does not name it.

  • xtabs(formula, data) builds contingency tables: a one-sided formula counts rows, a left-hand side sums that variable per cell. Missing values in the left-hand side make the sum NA unless na.rm = TRUE (and since R 4.4.0 xtabs(Freq ~ .) consistently uses na.pass); R 3.4.0 added the addNA argument to count missing values.

  • boxplot(formula, data) groups the response by the factor(s) on the right and draws one box per group. With plot = FALSE it returns the statistics it would have drawn (a list with stats, n, conf, out, group and names) and opens no graphics device, which is the form used here; the drawing itself is in Base Graphics and Devices. plot(y ~ x) and plot(y ~ g) use the same formula for scatter plots and box plots.

  • The formula methods of the classical tests: t.test(pages ~ genre), wilcox.test(), kruskal.test(), bartlett.test(), var.test() and cor.test(~ a + b) (a one-sided formula with two variables); the paired tests use Pair(x1, x2) ~ 1, which came with R 4.0.0, when the formula interface of t.test() and wilcox.test() was extended to one-sample and paired tests; since R 4.4.0 these formula methods reject a paired argument with cannot use 'paired' in formula method. R 4.3.0 fixed the formula method of cor.test() when environment(formula) was not the calling environment.

  • sort_by(x, y) (new in R 4.4.0) sorts a data frame by one or more columns, and its y can be a one-sided formula such as ~year (R documentation: sort_by).

  • lm(), glm(), aov(), nls() and the rest of the modelling functions, covered in Statistical Models.

The two sums that print as blanks come from the NA in pages for one fiction and one non-fiction book; print() of an xtabs table leaves NA empty, which is easy to read as zero, so check for missing values or use na.rm = TRUE on purpose. Packages repeat the convention and extend it. lattice (a recommended package that ships with R, 0.22-9) uses y ~ x | g to draw one panel per group, and ggplot2 4.0.3 uses facet_wrap(~ genre) with a one-sided formula (ggplot2 package documentation: facet_wrap); neither is run on this page. purrr 1.2.2 accepts a one-sided formula such as ~ .x + 2 as a short anonymous function; its documentation marks that form as "no longer recommended" (purrr package documentation: as_mapper), and since R 4.1.0 the base lambda \(x) x + 2 does the same without a package. That use of the tilde has nothing to do with models: the formula is only a quoted expression that the package turns into a function, a use of the same "quote, keep the environment" mechanism described at the top of this page. The tidyverse side of formulas is in tidyr, purrr and stringr.

Pitfalls

Most formula problems come from a few places. Two of them have entries in the R FAQ. The model without an intercept changes the definition of R squared, so the two numbers in the output are not comparable, and the sequential sums of squares of anova() depend on the order of the terms.

source("scenario.R")

with_intercept <- lm(pages ~ year, data = books)
through_origin <- lm(pages ~ year - 1, data = books)
identical(coef(lm(pages ~ 0 + year, data = books)), coef(through_origin))
#> [1] TRUE

# summary() uses a different formula for R squared when there is no intercept
# (R FAQ 7.41), so the two numbers are not comparable.
round(summary(with_intercept)$r.squared, 3)
#> [1] 0.257
round(summary(through_origin)$r.squared, 3)
#> [1] 0.887
colnames(model.matrix(through_origin))
#> [1] "year"

Source: R FAQ 7.41: Why does summary() report strange results for the R^2 estimate when I fit a linear model with no intercept?

The FAQ explains that with a zero intercept summary.lm() compares the fit with a model whose mean is zero, not with the mean of the response, because otherwise R squared could be negative; if you do not know a priori that the response is zero when the predictor is zero, you probably should not be fitting a line through the origin. The second entry is about the order of the terms.

Because the data are unbalanced (and the terms correlated), the year line of the first table tests year alone and the year line of the second tests year after genre; the sums of squares and the p-values differ. The FAQ points out that anova(model1, model2) compares any two models directly and drop1(model1) shows the sums of squares of dropping each term once. The last two lines show that terms() keeps the main effects in the order written, which is why the order in the formula is the order of the sequential table.

The next script shows the dropped rows at work. The two models are fitted on 14 and 13 rows, so anova() refuses to compare them and gives the real message; fitting both on the complete rows fixes it; na.exclude keeps a slot for each dropped row; and a factor level without data stays in the model frame and the model matrix, while lm() drops it.

source("scenario.R")
books$genre <- tolower(trimws(books$genre))

# Two models on different rows cannot be compared with anova().
small <- lm(pages ~ genre, data = books)
large <- lm(pages ~ genre + year, data = books)
c(small = nobs(small), large = nobs(large))
#> small large
#>    14    13
mismatch <- tryCatch(
  anova(small, large),
  error = \(e) conditionMessage(e)
)
mismatch
#> [1] "models were not all fitted to the same size of dataset"

# Fitting both on the rows that have every variable makes them comparable.
complete <- books[complete.cases(books[c("pages", "genre", "year")]), ]
anova(
  lm(pages ~ genre, data = complete),
  lm(pages ~ genre + year, data = complete)
)

The other pitfalls, with what R does:

  • Missing values vanish silently. The default na.omit drops every row with an NA in any variable in the model, so a model with an extra covariate can be fitted on fewer rows than the one without it, and anova(fit1, fit2) then fails with the message models were not all fitted to the same size of dataset, as in the script above. nobs(fit) and fit$na.action tell you what happened; na.action = na.exclude keeps a slot, filled with NA, for each dropped row in the residuals and predictions.

  • The power operator. y ~ x^2 is not a square; use I(x^2) (R FAQ 3.3.2). In the same way y ~ x + z is two terms, y ~ I(x + z) is one, and y ~ log(x + 1) is fine because the operator is inside a function call.

  • Variables that are not columns. A name that is not a column of data is looked up in the environment of the formula (the global environment for a console formula), which may be a different variable of the same name than you meant. When a function builds a formula, pass the data explicitly, keep the variables as columns, and avoid formulas that depend on a variable defined in the caller; if the formula is passed on to another function, environment(f) is the thing to check.

  • The formula travels with its environment. A large environment is kept alive and serialized with every object that stores the formula, including fitted models; lm() objects from a function that held a big data frame can become very large for that reason, and one remedy is to build the formula with env = globalenv() or to assign environment(f) <- globalenv().

  • Data-dependent terms. poly(), scale(), bs() and mean(x) inside a formula are computed on the full data before subset is applied, and poly() rejects NA.

  • Names with spaces or operators. Use backticks in the formula and in reformulate(), or rename the column with make.names() first.

  • Factors with unused levels. model.frame() keeps a level with no observations (drop.unused.levels = FALSE is its default), so model.matrix() gives it a column of zeros; lm() and glm() ask model.frame() to drop unused levels, and other code can use droplevels().

  • The character vector of length greater than one passed to formula() is deprecated (R 4.0.0): build one string with paste(x, collapse = " ").
