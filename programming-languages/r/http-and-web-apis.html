HTTP and Web APIs

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. Most of this page is base R (the base, utils and tools packages that ship with R): download.file(), url() connections, curlGetHeaders(), URLencode(). The rest uses add-on packages, each labelled as a package where it appears and each checked at the version shown: httr2 1.3.0 (the request and response client), jsonlite 2.0.0 (JSON, which httr2 uses), curl 8.1.0 (the R binding to libcurl underneath httr2), plumber 1.3.3 with httpuv 1.6.17 under it (only to build the local test server) and callr 3.8.0 (only to start that server in a background R process). The older httr and RCurl packages are described in the older-tutorials section and are not run, and the lintr 3.4.0 default linters were used only to check the scripts. Reading the web is the most network-dependent thing R does, and the least reproducible in a document, so this page is built around one rule: nothing on it depends on the internet. Every request that is actually sent goes to a small local server on 127.0.0.1 that the script itself starts and stops; the other examples are dry runs that print the request instead of sending it, mocked responses that never leave R, or file:// URLs.

Every example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines that start with #> are what it printed. The scripts also pass the default lintr linters. The names books, loans and the other objects of the running library-shelf scenario come from the section index: a script that needs them starts with source("scenario.R"), and the local server in these examples serves the books data frame and the books.csv file of that scenario. Where a message contains quotation marks or a bullet, it is the typographic character R prints in a UTF-8 locale. A few values change from run to run (a Date: header, a number of milliseconds in a timeout message): the scripts remove or mask them and say so, so that what you see here is what you get. Dry runs and mocked examples use https://api.example.com/... as a placeholder host that is never contacted; the placeholder is the only host on the page that is not real.

This page belongs to the data import and export group. Reading a CSV from a URL is a case of the connections explained in Connections and the File System and the readers in Reading and Writing Text Data; JSON is covered by Serialization: RDS, RData and JSON. Serving an API of your own with plumber, and Shiny, are the subject of Shiny, plumber and Web APIs; here plumber appears only as a way to have something to talk to. Error classes and tryCatch() are explained in Conditions and Error Handling.

How R talks to the web

An HTTP exchange is small. The client sends a request: a method (GET to read, POST to create, PUT or PATCH to change, DELETE, and HEAD to ask for the headers only), a URL, headers (Accept, Authorization, User-Agent) and sometimes a body. The server answers with a response: a status code, headers (Content-Type, Retry-After) and usually a body. Everything an R package for the web does is some way of building that request, sending it and reading that response. The status codes that matter most are in this table.

Status Meaning What a client does

200 OK

the request worked and the body is the result

read the body

201 Created

a POST created something, often with a Location header

read the Location header or the returned body

301, 302

the resource moved

follow the Location header (libcurl does by default)

400 Bad Request

the server did not understand the request

fix the request; do not retry

401 Unauthorized

credentials are missing or wrong

send or refresh credentials

403 Forbidden

credentials are valid but not allowed

do not retry

404 Not Found

there is nothing at that URL

handle it as "no such thing"

429 Too Many Requests

a rate limit was hit, often with Retry-After

wait and retry

500, 503

the server failed or is overloaded

retry a few times, then give up

R offers four levels for doing this, and a script should pick the lowest one that does the job. The table is the map for the rest of the page.

Level Functions Use it for

R Data Import/Export says it in two sentences. Base R has "some limited facilities" to exchange data across network connections, and download.file() reads a file from a Web resource via FTP or HTTP (including HTTPS) and writes it to a file; often this can be avoided, because functions such as read.table() and scan() can read directly from a URL, either explicitly through url() or implicitly by being given a URL as the file argument (R Data Import/Export: Using download.file). The same chapter has a section on reading from sockets, with the advice to use socket connections (socketConnection()) in new projects rather than the earlier make.socket() family (R Data Import/Export: Reading from sockets). Sockets are the layer below HTTP and are rarely what a data script needs; this page stays at the HTTP level.

Underneath, all of it is libcurl, the C library that R was built with for its own functions and that the curl package binds for httr2. This is why the same things go wrong everywhere in the same way: a proxy, a certificate that cannot be verified, a timeout.

A local test server for the examples

To show a client at work without the internet, the examples need something to talk to. The page builds a miniature "shelf" web service with plumber (plumber package documentation: pr). pr() makes an empty router; pr_get(), pr_post() and the general pr_handle() add routes, each a path and a handler function; pr_set_serializer() chooses how return values become a body; pr_run() starts the server. A handler can take the arguments req (the request: headers such as req$HTTP_AUTHORIZATION, a parsed JSON body in req$body) and res (the response: res$status, res$setHeader()), the query-string parameters by name (limit = "5" arrives as a character string), and the parts of a path written in angle brackets: "/books/<isbn>" passes isbn. A returned list or data frame is turned into JSON; serializer_unboxed_json() writes length-one values as JSON scalars instead of one-element arrays, which is what most APIs do, and serializer_text(type = "text/csv") sends a string as CSV. When a route throws an error, or no route matches, plumber answers with a JSON body of its own: {"error":"404 - Resource Not Found"} and {"error":"500 - Internal server error"}.

pr_run() does not return: it serves requests until it is interrupted. A script cannot start the server and then act as its client in the same R process, because the client call blocks R while the server is waiting for R to serve (tried while preparing this page: an httpuv server started in the same process and a blocking curl request to it timed out, because a blocked R cannot run the server’s event loop; a non-blocking client plus a loop calling httpuv::service() does work, but it is far more awkward). So the examples start the server in a second R process with callr, and all of it lives inside the one script: start, wait until it answers, run the client code, stop. The labelled "local test server" function below is the pattern every later script repeats with different routes.

library(httr2)
source("scenario.R")

# A local test server: a plumber API that serves the shelf books as JSON.
shelf_api <- function(books, port) {
  plumber::pr() |>
    plumber::pr_set_serializer(plumber::serializer_unboxed_json()) |>
    plumber::pr_get("/ping", \() list(ok = TRUE)) |>
    plumber::pr_get("/books", \() books[, c("title", "isbn", "year")]) |>
    plumber::pr_run(host = "127.0.0.1", port = port, docs = FALSE, quiet = TRUE)
}

# pr_run() blocks, so run the API in a background R process.
srv <- callr::r_bg(shelf_api, args = list(books = books, port = 8765L))

Four details of this script matter for every later one.

  • The function is self-contained. callr documents that the function passed to r_bg() has its environment set to the global environment before it is sent to the child process, so it should only refer to other functions and variables from other packages "using the :: notation". That is why shelf_api() takes books and port as arguments, passed in args, and calls plumber::pr() rather than assuming library(plumber). A closure over books in the parent session finds no books in the child, and every request answers 500: this was the first error met while writing these examples.

  • The port is fixed (8765) and the host is 127.0.0.1, the loopback address: the server is reachable only from the same machine. Each script stops its server before it ends, so scripts can run one after another on the same port.

  • The wait is a retry. The server needs a moment to start, and a request sent too early fails with "Couldn’t connect to server". req_retry(retry_on_failure = TRUE) treats that low-level failure as transient and tries again after backoff seconds, up to max_tries attempts (it is explained in the section on retries below). The base R scripts use a short loop around curlGetHeaders(), which also fails until the port is open.

  • The server is stopped explicitly. srv$kill() stops the background process and srv$is_alive() confirms it. A callr process is also stopped when its R object is garbage collected or the parent R session ends, so an error in the middle of a script does not leave the server behind; do not rely on that, and inside a function use on.exit(srv$kill()).

The server could be written with httpuv directly (httpuv package documentation: startServer): plumber is a routing layer on top of it. A different approach for the tests of a package is to mock the responses instead of serving them; httr2 supports it and the last example script shows it. From here on, each script starts its own server with the routes it needs. The routes are part of the example (a real API has its own), and a script shows only the routes it uses.

Base R: download.file()

What it does and its arguments

download.file() copies the resource at a URL to a local file. Its signature in R 4.6.1 is

download.file(url, destfile, method, quiet = FALSE, mode = "w",
              cacheOK = TRUE, extra = getOption("download.file.extra"),
              headers = NULL, ...)

Source: R documentation: download.file

and its arguments are:

  • url is a character string naming the resource, starting with a scheme such as http://, https:// or file://; with the "libcurl" method it may be a longer vector. destfile is the path to write, tilde-expanded, a vector of the same length when url is.

  • method is one of "internal", "libcurl", "wget", "curl", "wininet" (Windows only) or "auto", and when it is missing it comes from getOption("download.file.method"). With "auto" (the default when nothing is set) the "internal" method is used for file:// URLs and "libcurl" for all others. Today "internal" supports only the file:// scheme. The "wget" and "curl" methods run an external program, which must be installed and on the search path; they block R until they finish and exist mainly for historical compatibility. The help page’s advice is that setting the method "should be left to the end user", so a script written for others should not hard-code it unless it needs a feature, several files at once for instance, that "libcurl" provides.

  • quiet = TRUE suppresses the status messages and the progress bar. With the default FALSE a download prints trying URL ..., the content type and length, a text progress bar and downloaded N bytes; they are messages, written to standard error.

  • mode is how the file is written: "w", "wb", "a" or "ab". The choice matters only on Windows, where a text-mode transfer changes \n line endings to \r\n and so corrupts a binary file; the help page says the problems of a text transfer "will only be seen on Windows", so code written on Linux or macOS must still use mode = "wb" for everything that is not text. (On Windows, when mode is missing and the URL ends in .gz, .bz2, .xz, .tgz, .zip, .jar, .rda, .rds, .RData or .pdf, R chooses "wb" itself.)

  • cacheOK = FALSE asks for a copy from the site rather than from an intermediate cache, for http:// and https:// URLs.

  • extra is for the "wget" and "curl" methods only. headers is a named character vector of extra HTTP headers for http:// and https:// URLs (added in R 3.6.0); the User-Agent header comes from the HTTPUserAgent option and is sent first.

  • The value is an invisible integer: 0 for success and non-zero for failure. When several files are downloaded at once and at least one succeeds, it is 0 with an attribute "retvals" holding the code of each file.

The timeout for many parts of the transfer comes from the option timeout, in seconds, default 60, which can be set for the whole session with the environment variable R_DEFAULT_INTERNET_TIMEOUT (R 4.0.3 NEWS). The documentation points out that 60 seconds is often insufficient for downloads of 50 MB or more, and that a package should write options(timeout = max(300, getOption("timeout"))) rather than lower the value. The timeout is for a response that does not arrive, not for the whole operation (R documentation: connections).

libcurl, the default method

The "libcurl" method is the one you will use. It uses the external library of that name; capabilities("libcurl") tells whether R was built with it, and libcurlVersion() reports the version in use and the URL schemes it supports (R documentation: libcurlVersion). It was added as an optional method in R 3.2.0, became the default on Unix-alikes in R 3.4.0 for everything except file:// URLs, and became the default on Windows in R 4.2.0, where it had been optional until then; R 4.2.0 also made libcurl required for building R from source and reduced the "internal" method to file:// only. The section "Version notes" has the table.

The first example starts the local server, downloads the book list with method = "libcurl" and mode = "wb", and checks that the downloaded file reads back as the books data frame it came from. Its later parts download several files at once, read a file:// URL and use the curl package.

source("scenario.R")

capabilities("libcurl")
#> libcurl
#>    TRUE

# A local test server: plumber serving the shelf CSV files. HEAD is allowed
# too, because curlGetHeaders() sends a HEAD request.
shelf_api <- function(files, port) {
  plumber::pr() |>
    plumber::pr_handle(
      c("GET", "HEAD"), "/csv/<name>",
      \(res, name) {
        if (!name %in% names(files)) {
          res$status <- 404L
          return("no such file")
        }
        files[[name]]
      },
      serializer = plumber::serializer_text(type = "text/csv")
    ) |>
    plumber::pr_run(host = "127.0.0.1", port = port, docs = FALSE, quiet = TRUE)
}

files <- list(
  books = readChar("books.csv", file.size("books.csv")),
  loans = readChar("loans.csv", file.size("loans.csv"))
)
srv <- callr::r_bg(shelf_api, args = list(files = files, port = 8765L))
base <- "http://127.0.0.1:8765"

# curlGetHeaders() fails until the port is open: a handy readiness probe.
for (i in seq_len(40L)) {
  probe <- try(curlGetHeaders(paste0(base, "/csv/books")), silent = TRUE)
  if (!inherits(probe, "try-error")) break
  Sys.sleep(0.25)
}

dest <- tempfile(fileext = ".csv")
status <- download.file(
  paste0(base, "/csv/books"), dest,
  method = "libcurl", mode = "wb", quiet = TRUE
)
status
#> [1] 0
file.exists(dest)
#> [1] TRUE
identical(read.csv(dest), books)
#> [1] TRUE
unname(tools::md5sum(dest) == tools::md5sum("books.csv"))
#> [1] TRUE

# With quiet = FALSE the progress messages go to the message stream.
download.file(paste0(base, "/csv/books"), dest, mode = "wb")
#> trying URL 'http://127.0.0.1:8765/csv/books'
#> Content type 'text/csv' length 1187 bytes
#> ==================================================
#> downloaded 1187 bytes

# Several files at once: url and destfile are vectors (libcurl only).
dests <- c(tempfile(), tempfile())
urls <- paste0(base, "/csv/", c("books", "loans"))
download.file(urls, dests, method = "libcurl", quiet = TRUE)
file.size(dests) == file.size(c("books.csv", "loans.csv"))
#> [1] TRUE TRUE

# A file:// URL is read by R's own code, with an empty host field.
local_url <- paste0("file://", normalizePath("books.csv"))
substr(local_url, 1L, 8L)
#> [1] "file:///"
dest_file <- tempfile()
download.file(local_url, dest_file, quiet = TRUE)
identical(readLines(dest_file), readLines("books.csv"))
#> [1] TRUE

# The curl package: curl_download() is a simpler, cross-platform equivalent.
dest_curl <- tempfile()
invisible(curl::curl_download(paste0(base, "/csv/books"), dest_curl))
identical(readLines(dest_curl), readLines("books.csv"))
#> [1] TRUE

invisible(srv$kill())

Source: R documentation: download.file, R documentation: capabilities and curl package documentation: curl_download

Reading the output from the top:

  • capabilities("libcurl") is TRUE.

  • The first download returned 0 and wrote a file, which read.csv() turns back into an identical books and whose MD5 sum equals that of books.csv: the server delivered the bytes unchanged. The path of the temporary file is never printed, because tempfile() returns a path under the session’s temporary directory that differs from run to run; the script prints file.exists() and a comparison instead.

  • With quiet = FALSE the progress messages appear. They are written to standard error, so in a script’s merged output they can come before the output of the call that produced them; they are shown under their call.

  • A vector of URLs and a vector of destinations download several files at once. Only the "libcurl" method does this, and only when it is requested explicitly (not through "auto"). In R 4.5.0 install.packages() and download.packages() started using it to download packages simultaneously, and download.file() reports the outcome for individual files (R NEWS).

  • A file:// URL has an empty host field, so a local file is file:// followed by an absolute path that starts with /: three slashes in all on a Unix-alike. The script builds it with paste0("file://", normalizePath("books.csv")) and prints only its first eight characters, because the rest is the absolute path of this machine. R handles file:// URLs with its own code whatever the method is, does not decode percent-encoded characters in them (call URLdecode() if needed), and cannot express a relative path with them.

  • curl::curl_download(url, destfile, quiet = TRUE, mode = "wb", handle = new_handle()) is the same job in the curl package (curl package documentation: curl_download). It uses the same libcurl, is quiet and binary by default, and behaves the same on every platform. Its handle argument takes a curl::new_handle() object (curl package documentation: handle) holding libcurl options, headers and cookies.

When the download fails

download.file() is not all-or-nothing: in some cases a non-zero status is returned without any error, in others a warning comes first and an error after it. The help page’s advice is firm: a package or script that uses it must check the return value, because a download can fail with a non-zero status and no R error. The next script produces each failure against the local server: a 404, several downloads of which one fails, a status check, and a server that is gone. The helper diagnose() evaluates an expression and returns the warnings it raised and the message of the error it ended with (conditions are explained in Conditions and Error Handling).

source("scenario.R")

shelf_api <- function(files, port) {
  plumber::pr() |>
    plumber::pr_handle(
      c("GET", "HEAD"), "/csv/<name>",
      \(res, name) {
        if (!name %in% names(files)) {
          res$status <- 404L
          return("no such file")
        }
        files[[name]]
      },
      serializer = plumber::serializer_text(type = "text/csv")
    ) |>
    plumber::pr_run(host = "127.0.0.1", port = port, docs = FALSE, quiet = TRUE)
}

files <- list(books = readChar("books.csv", file.size("books.csv")))
srv <- callr::r_bg(shelf_api, args = list(files = files, port = 8765L))
base <- "http://127.0.0.1:8765"
for (i in seq_len(40L)) {
  probe <- try(curlGetHeaders(paste0(base, "/csv/books")), silent = TRUE)
  if (!inherits(probe, "try-error")) break
  Sys.sleep(0.25)
}

# Run an expression and return its warnings and its error message.
diagnose <- function(expr) {
  warnings <- character()
  error <- withCallingHandlers(
    tryCatch({
      expr
      NA_character_
    }, error = \(e) conditionMessage(e)),
    warning = \(w) {
      warnings <<- c(warnings, conditionMessage(w))
      invokeRestart("muffleWarning")
    }
  )
  list(warnings = warnings, error = error)
}

# 1. The server answers 404: two warnings, then an error.
dest <- tempfile()
diagnose(download.file(paste0(base, "/csv/shelves"), dest, quiet = TRUE))
#> $warnings
#> [1] "downloaded length 0 != reported length 12"
#> [2] "cannot open URL 'http://127.0.0.1:8765/csv/shelves': HTTP status was '404 Not Found'"
#>
#> $error
#> [1] "cannot open URL 'http://127.0.0.1:8765/csv/shelves'"
#>
file.exists(dest)
#> [1] FALSE

# 2. One of several downloads fails: no error, but attribute "retvals".
dests <- c(tempfile(), tempfile())
urls <- paste0(base, "/csv/", c("books", "shelves"))
status <- suppressWarnings(
  download.file(urls, dests, method = "libcurl", quiet = TRUE)

Credentials

A URL may carry credentials, https://username:password@machine/..., but the help page does not recommend it: with HTTP they are sent in plain text, and even with HTTPS they may appear in server logs. The alternatives are the Authorization entry of the headers argument (R 3.6.0 and later) and, with the "libcurl" method, a netrc file named by the option netrc: R 4.6.0 added credentials for basic HTTP authentication in a netrc file, whose path is options("netrc") and can be set from the environment variable R_DEFAULT_NETRC; the file should not be readable by other users. Never put a password or a token in a script. Read it with Sys.getenv() from the environment, from a .Renviron file (Sessions, Workspaces and Startup) or from a secrets store. For anything beyond one header, httr2 (below) is the better tool.

URL connections and curlGetHeaders()

Reading from a URL with url()

url() creates a connection to a resource, and file() and every reader that takes a file name also accept a URL string. For url() the description is a complete URL including the scheme (http://, https://, ftp:// or file://). The signature is url(description, open = "", blocking = TRUE, encoding = getOption("encoding"), method = getOption("url.method", "default"), headers = NULL): the method "default" is "internal" for file:// URLs and "libcurl" for all others, headers is a named character vector of HTTP headers (the User-Agent comes from the HTTPUserAgent option), and all the methods attempt to follow redirections. The help page notes that "server-side cached data is always accepted", so there is no cacheOK here. Connections in general are explained in Connections and the File System. What is special about url() is that blocking operations on an HTTP connection are subject to the timeout option, which is set when the connection is opened.

In the script below, a function that opens a connection by itself (readLines(url(...)), read.csv(url(...))) closes it again, which is the form to prefer. A connection that is created, opened and read in pieces must be closed with close(), ideally registered right after creation with on.exit(close(con)) inside a function.

Notes on this script:

  • The class of a url() connection under the default method is "url-libcurl", and it starts "closed". readLines(con, n = 1L) on an open connection continues where the previous read stopped, which is how a large resource is read in pieces.

  • read.csv(url_string) and read.csv(url(url_string)) give the same data frame; the first is the usual way to write it. The same holds for scan(), readLines() and read.table().

  • The headers argument of url() (R 3.6.0 and later) is how a request header reaches the server; the local /whoami route echoes the custom header back as JSON. readLines() of a response with no final newline warns "incomplete final line"; warn = FALSE silences it.

  • jsonlite::fromJSON() accepts a URL directly and returns a data frame for a JSON array of records. It is only suitable for a plain GET; for anything else, parse the body after an httr2 call.

Looking at the headers: curlGetHeaders()

curlGetHeaders(url, redirect = TRUE, verify = TRUE, timeout = 0L, TLS = "") retrieves the headers for a URL without the body. The help page says it reports what curl -I -L or curl -I would report, so it sends a HEAD request, and the server must accept one. A route declared with pr_get() alone answers HEAD with 405 Method Not Allowed and an empty Allow: header (seen with the checked version of plumber), so the local server declares its routes for GET and HEAD with pr_handle(c("GET", "HEAD"), ...). HTTP servers are allowed to refuse a HEAD and some do; the help page says it results in a status of 405.

The value is a character vector of header lines, each ending in \r\n and the last one blank, with an integer attribute "status", the last-received status code. With redirections, which are followed by default, up to 20, it contains the headers of every URL visited, so counting the HTTP/ lines counts the hops: the /old-books.csv route redirects with 302 Found and a Location header, and redirect = FALSE stops at the first answer. In the script above Date: is removed with h[!grepl("^Date:", h)] because it changes on every run, and trimws() drops the line endings for display.

The other arguments are verify = FALSE (skip certificate verification: the help page notes the risk is slight because only the headers are captured, and that looking at the URL in a browser usually reveals what is wrong), timeout (seconds, added in R 4.1.0; a value that is not positive means getOption("timeout") is used) and TLS (the minimum TLS version for https:// URLs: "1.1", "1.2" or "1.3", also R 4.1.0, if libcurl and its SSL library support it). Only 500 header lines are reported. curlGetHeaders() was added in R 3.2.0 together with capabilities("libcurl") and libcurlVersion(), and R uses it in R CMD check --as-cran to check that URLs exist (R 3.2.0 NEWS). R 4.0.3 fixed internet access based on libcurl, including curlGetHeaders(), not respecting the timeout option (R NEWS).

Encoding URLs

A URL may contain only a small set of characters; the others are written as % and two hexadecimal digits (percent-encoding; multi-byte characters are encoded byte by byte). utils::URLencode(URL, reserved = FALSE, repeated = FALSE) and URLdecode() do this. The reserved characters ! $ & ' ( ) * + , ; = : / ? @ # [ ] are left alone by default, "which is appropriate for file:// URLs, but probably not for http:// ones" (the help page). So URLencode() is right for a whole URL that contains a space, and wrong for the value of a query parameter, which may itself contain & or =: encode each value with reserved = TRUE and then build the query. With repeated = FALSE an apparently already-encoded %41 is left alone; TRUE encodes the percent sign again, which is rarely what you want.

# Percent-encoding with utils::URLencode() and URLdecode().
title <- "Salt & Static"
URLencode(title)
#> [1] "Salt%20&%20Static"
URLencode(title, reserved = TRUE)
#> [1] "Salt%20%26%20Static"
URLdecode("Salt%20%26%20Static")
#> [1] "Salt & Static"

# URLencode() leaves a whole URL's separators alone ...
URLencode("https://api.example.com/v1/books?title=Salt & Static")
#> [1] "https://api.example.com/v1/books?title=Salt%20&%20Static"

# ... so encode each value on its own and build the query by hand.
query <- paste0("title=", URLencode(title, reserved = TRUE), "&limit=5")
paste0("https://api.example.com/v1/books?", query)
#> [1] "https://api.example.com/v1/books?title=Salt%20%26%20Static&limit=5"

# repeated = TRUE encodes characters that are already encoded.
URLencode("100%", repeated = FALSE)
#> [1] "100%25"
URLencode("%41", repeated = FALSE)
#> [1] "%41"
URLencode("%41", repeated = TRUE)
#> [1] "%2541"

# The curl package escapes a value the same way.
curl::curl_escape(title)
#> [1] "Salt%20%26%20Static"
curl::curl_unescape("Salt%20%26%20Static")
#> [1] "Salt & Static"

https, certificates and proxies

None of this can run here, because it needs real remote servers, so this section is prose. The R FAQ entry 7.43 is the whole answer to "how do I enable https": from R 4.2.0 the "libcurl" download method is always available and used for HTTPS by default on all platforms, as it had been since R 3.3.0 everywhere but Windows (where the default "wininet" also supported HTTPS), so "nothing needs to be done to access https:// websites in recent versions of R" (R FAQ 7.43: How can I enable secure https downloads in R?). A tutorial that starts with options(download.file.method = "wininet") or method = "curl" to get https working describes R before 3.3.0 or before 4.2.0.

What can still go wrong is the same set of problems as in a browser:

  • Certificates. HTTPS methods try to verify the server’s certificate with the CA root certificates installed by the operating system, which can be missing or out of date, and the browser may use a different bundle, so a site that opens in a browser can still fail in R. On Windows with method = "libcurl" the certificates come from the OS when R was linked with Schannel (check that libcurlVersion() contains "Schannel"); otherwise set the environment variable CURL_CA_BUNDLE to the path of a certificate bundle file such as ca-bundle.crt. The help page points to curl documentation: SSL certificates for the details.

  • Revocation checks behind a proxy. On Windows with Schannel the connection fails if it cannot be established that the certificate has not been revoked, which some corporate man-in-the-middle proxies prevent. R 4.2.2 added the environment variable R_LIBCURL_SSL_REVOKE_BEST_EFFORT: set to TRUE it makes the revocation check best-effort, "with the consequence of reducing security" (?download.file and R NEWS: Changes in R 4.2.2). It is a workaround for one environment, not a setting to ship in a script.

  • Not verifying. curlGetHeaders(verify = FALSE) skips verification, and httr2 can pass libcurl options with req_options(); both defeat the purpose of HTTPS and are for diagnosing a problem, never for a fix that stays in a script.

  • Proxies. For the "libcurl" and "curl" methods proxies are set through environment variables. ?download.file names http_proxy and ftp_proxy; libcurl’s tutorial, which R’s help page links, explains that the variables are built as the lower-case protocol name followed by _proxy, so https_proxy applies to https:// URLs, all_proxy is the fallback and no_proxy lists hosts that bypass the proxy (libcurl tutorial). Set them in .Renviron or in the shell, not in code. httr2 has req_proxy(url, port, username, password, auth) for a proxy that applies to one request.

  • Timeouts and the user agent. options(timeout) and R_DEFAULT_INTERNET_TIMEOUT were described above. The HTTPUserAgent option sets the user agent string used by download.file(), url() and curlGetHeaders(); with libcurl the default is "libcurl/<version>" (a value starting with the "R " prefix is reserved and ignored). options(internet.info) sets how much is printed about URL downloads: the default 2 prints the failure causes, and 1 or 0 give more detail for the libcurl method (R documentation: options).

A fragment, not run (it needs a real server, and api.example.com is the placeholder host), shows the shape of a download that survives a slow network:

httr2: requests and responses

Why httr2

httr2 is a package for talking to web APIs from R. It is a wrapper for the curl package, which binds libcurl, "customised to the demands of modern web APIs", and it is the successor of httr: the httr site calls its own package superseded, says that only changes needed to keep it on CRAN will be made, and recommends httr2 instead (httr package documentation). The design is the pipe: request() makes an immutable request object, req_*() functions return a modified copy, req_perform() sends it and returns a response object, and resp_*() functions read the response. Nothing is changed in place and there is no global configuration, apart from the session’s record of the last_request() and last_response() used for debugging. httr2 turns HTTP failures into R conditions with classes (httr2_http_404), supports retries, throttling, caching, paging and mocking, and has the OAuth flows. It uses jsonlite to write (req_body_json()) and to read (resp_body_json()) JSON. Its own examples run on R 4.2 and later, because they use the native pipe and the lambda syntax (httr2 1.0.0 NEWS).

  • The request is a value. req_url_path_append("books") and req_url_query(...) return new requests; req is unchanged. req_get_url(), req_get_method() and req_get_headers() (httr2 1.2.0) read a request back.

  • req_url_path_append() does not escape its argument. A segment with a space is appended as it is, and the next req_url_query() fails to parse the URL with Failed to parse URL: Malformed input to a URL function (the message seen with the checked versions of httr2 and curl). Escape a segment that came from data with curl::curl_escape() first. Query values, on the other hand, are escaped by req_url_query().

  • A vector needs a strategy. req_url_query(genre = c("fiction", "poetry")) is an error ("All vector elements of ... must be length 1"). The argument .multi (httr2 1.0.0) chooses: "explode" repeats the parameter (genre=fiction&genre=poetry), "comma" joins with commas, "pipe" with |. Which one an API expects is in its documentation. .space = "form" (httr2 1.1.0) writes spaces as + instead of %20.

  • Headers. Names are case-insensitive and a later req_headers() replaces an earlier one (so the second call replaced Accept, keeping the new spelling accept). .redact names headers whose values must not be shown when the request is printed. req_get_headers() leaves the redacted ones out unless you ask redacted = "reveal". The printed request marks them <REDACTED>. req_headers_redacted() (httr2 1.1.0) is the shortcut for a header that is all secret.

  • User agent, method and timeout. req_user_agent() sets the User-Agent; without it httr2 sends httr2/<version> r-curl/<version> libcurl/<version>. It is polite, and sometimes required, to identify the client with a name and a contact. req_method("HEAD") or "DELETE" changes the method; a body makes it POST by default. req_timeout(seconds) sets the total time; the printed request shows the libcurl options (timeout_ms, connecttimeout) it set. Since httr2 1.0.1 req_timeout() also resets the connection timeout, so it can be used to raise it above libcurl’s default of 10 seconds.

  • req_template("GET /books/{isbn}", isbn = ...) builds the method and path from a template, and req_options() passes raw libcurl options (req_options(ssl_verifypeer = FALSE) is how verification is switched off, with the risks described above).

Performing a request and reading the response

HTTP errors and failed requests

httr2 distinguishes two ways for a request to fail, as ?req_error explains. The request may not complete at all (the connection drops, the server does not exist, the time runs out): the condition has the classes httr2_failure and httr2_error, and its parent is the curl error. Or the request may succeed but the status code is an error, 4xx or 5xx: the classes are, for a 404, httr2_http_404, httr2_http and httr2_error. Since httr2 1.0.0 every error httr2 throws inherits from httr2_error. These classes are meant for tryCatch() (the Conditions and Error Handling page explains class-based handling), so a script can answer "no such book" differently from "the server is down".

# that always fails (500), a protected route (401) and a slow one.
shelf_api <- function(books, port) {

  plumber::pr() |>
    plumber::pr_set_serializer(plumber::serializer_unboxed_json()) |>
    plumber::pr_get("/books/<isbn>", \(res, isbn) {

Retries and rate limits

Many APIs limit how fast a client may call them and answer 429 Too Many Requests with a Retry-After header, or fail now and then with a 503. httr2 has two tools, which work together. req_retry() reacts to what the server says; req_throttle() keeps the client under a limit that the server does not report. A third idea, in httr2 1.1.0, is a circuit breaker: failure_threshold makes requests to a host that keeps failing error at once for failure_timeout seconds, without waiting for the server each time.

req_retry(req, max_tries, max_seconds, retry_on_failure = FALSE, is_transient, backoff, after, failure_threshold, failure_timeout, failure_realm) retries when the response is a 429 or a 503, or whatever is_transient(resp) says. max_tries is the total number of attempts, so it should be greater than one; when neither max_tries nor max_seconds is set, httr2 uses max_tries = 2 (since httr2 1.1.0). The delay before the next attempt is the number of seconds in the Retry-After header when there is one (after overrides how that is read: a function from the response to a number of seconds, or NA for "fall back to the backoff"); otherwise it is the backoff function, whose default is truncated exponential backoff with full jitter, a random wait between one second and 2^tries seconds, capped at 60. retry_on_failure = TRUE also retries when the request itself failed, which is how the examples wait for the local server to start; since httr2 1.0.4 such failures are no longer retried by default.

library(httr2)

# A local test server with a rate limit: /busy answers 429 with a Retry-After
# header twice and then succeeds; /limited never succeeds; /flaky fails once
# with a 500; /ok always succeeds.
shelf_api <- function(port) {
  seen <- new.env()
  seen$busy <- 0L
  seen$flaky <- 0L
  plumber::pr() |>
    plumber::pr_set_serializer(plumber::serializer_unboxed_json()) |>
    plumber::pr_get("/ok", \() list(ok = TRUE)) |>
    plumber::pr_get("/busy", \(res) {
      seen$busy <- seen$busy + 1L
      if (seen$busy <= 2L) {
        res$status <- 429L
        res$setHeader("Retry-After", "1")
        return(list(error = "slow down"))
      }
      list(ok = TRUE, attempt = seen$busy)
    }) |>
    plumber::pr_get("/flaky", \(res) {
      seen$flaky <- seen$flaky + 1L
      if (seen$flaky <= 1L) {
        res$status <- 500L
        return(list(error = "hiccup"))
      }
      list(ok = TRUE, attempt = seen$flaky)
    }) |>
    plumber::pr_get("/limited", \(res) {
      res$status <- 429L
      res$setHeader("Retry-After", "1")
      list(error = "slow down")
    }) |>
    plumber::pr_run(host = "127.0.0.1", port = port, docs = FALSE, quiet = TRUE)
}

Reading the output:

  • Without req_retry() the 429 is an ordinary HTTP error, class httr2_http_429.

  • With req_retry(max_tries = 4) the same request succeeded on the third attempt: the server counted three requests (attempt is 3) and answered 429 with Retry-After: 1 for the first two. httr2 waited the two seconds that the header asked for, which the script checks (the elapsed time is at least 2 seconds). A req_retry() that gives up raises the error of the last response: with max_tries = 2 against the route that never succeeds, the error is HTTP 429 Too Many Requests., class httr2_http_429, and resp_retry_after(err$resp) reads the header, 1.

  • after = retry_after is the same wait written out: it reads Retry-After as a number and returns NA when the header is absent, which makes httr2 use backoff. Many APIs report the limit in other headers (GitHub uses X-RateLimit-Reset); after is how to read them, and is_transient is how to say that a 403 with X-RateLimit-Remaining: 0 is a rate limit (the examples in ?req_retry).

  • is_transient replaced the default test: the /flaky route failed once with a 500; without it the call errors with HTTP 500 Internal Server Error., with it the second attempt succeeds. Only retry what is safe to repeat: a GET is, a POST that creates something may not be.

  • Throttling. req_throttle() is a token bucket (httr2 1.1.1): the bucket holds at most capacity tokens and refills over fill_time_s seconds, every request takes a token, and an empty bucket makes the request wait. capacity = 2, fill_time_s = 1 means two requests at once and then one every half second, so five requests took more than one second. The older argument rate is still accepted: rate times fill_time_s (60 s by default) becomes the capacity, so rate = 2 / 1 is a bucket of 120 tokens per minute and nothing waited. A vector of capacities and times enforces several limits at once, such as 10 requests per second and 100 per minute (httr2 1.2.3). The throttle applies to every request with the same realm, by default the host name; since httr2 1.2.2 req_throttle() no longer resets the bucket when it is used repeatedly with the same host and never produces negative waits.

  • req_perform_parallel() supports simplified versions of req_throttle() and req_retry() (httr2 1.1.1). Mocked responses are not retried (see the mocking section).

Pagination and several requests

An API that returns many records pages them: a limit and an offset, a cursor, or Link headers. req_perform_iterative(req, next_req, max_reqs = 20, on_error) (httr2 1.0.0) performs a request, passes the response to next_req(resp, req), which returns the next request or NULL to stop, and so on, returning the list of responses. The helpers iterate_with_offset(param_name, start, offset, resp_pages, resp_complete), iterate_with_cursor() and iterate_with_link_url() build next_req for the usual designs. resps_data(resps, resp_data) combines the parsed bodies, and resps_successes(), resps_failures(), resps_requests() and resps_ok() (httr2 1.2.2) sort the list. When the number of pages is known, req_perform_parallel(reqs, max_active = 10, on_error = c("stop", "return", "continue")) sends the requests at once, and req_perform_sequential() one by one with the same interface. The local server reports the total in the X-Total-Count header.

# A local test server: /books returns one page, "limit" rows from "offset",
# and reports the total in the X-Total-Count header.
shelf_api <- function(books, port) {
  plumber::pr() |>
    plumber::pr_set_serializer(plumber::serializer_unboxed_json()) |>

Caching

req_cache(req, path, use_on_error = FALSE, debug, max_age, max_n, max_size) stores the responses to GET requests that have status 200 and at least one standard caching header (Expires, ETag, Last-Modified, Cache-Control), unless Cache-Control: no-store forbids it. Most API requests are not cacheable; static files often are. A request is still sent to check that the cached value is up to date, unless the cached value is still fresh by max-age, in which case the server is not contacted at all. path is a directory that is created automatically (tempfile() for a session cache, tools::R_user_dir() for a persistent one); the cache prunes itself to max_age, max_n and max_size (the default size limit is 1 GB). debug = TRUE (or options(httr2_cache_debug = TRUE)) prints messages about cache hits and misses; they include a hash that is not printed in the example. httr2 1.3.0 requires rlang 1.3.0, which changes the hash that names the cache files, so files cached by an earlier version are silently ignored and cleaned up over time.

library(httr2)

# A local test server: /count increments a counter on every request that
# reaches it, and /fresh/count marks the response cacheable for 60 seconds.
shelf_api <- function(port) {
  seen <- new.env()
  seen$plain <- 0L
  seen$fresh <- 0L
  plumber::pr() |>
    plumber::pr_set_serializer(plumber::serializer_unboxed_json()) |>
    plumber::pr_get("/count", \() {
      seen$plain <- seen$plain + 1L
      list(served = seen$plain)
    }) |>
    plumber::pr_get("/fresh/count", \(res) {
      seen$fresh <- seen$fresh + 1L
      res$setHeader("Cache-Control", "max-age=60")
      list(served = seen$fresh)
    }) |>
    plumber::pr_run(host = "127.0.0.1", port = port, docs = FALSE, quiet = TRUE)
}

Testing without a server: mocking

The best test of code that calls an API does not call it. with_mocked_responses(mock, code) and local_mocked_responses(mock) replace the network call of req_perform() (and of req_perform_parallel(), req_perform_sequential() and req_perform_iterative() since httr2 1.2.0) for the duration of code or of the calling function. mock is a function from the request to a response, or a list of responses served in order. response() and response_json() build responses of any status. They were introduced in httr2 1.0.0 as the replacement for with_mock() and local_mock(), which were deprecated then and removed in 1.2.0. Responses retrieved from a mock include the originating request, as real ones do (httr2 1.2.3). local_mocked_responses() is the form used in test_that() blocks of a package (Testing with testthat); this needs no server, no port and no network.

library(httr2)

# A function that talks to a web API (a placeholder host; never contacted).
book_title <- function(isbn) {
  request("https://api.example.com/v1") |>
    req_url_path_append("books", isbn) |>
    req_perform() |>
    resp_body_json() |>
    _$title
}

OAuth, streaming and background requests

The remaining parts of httr2 need a real server or a user, so this section is prose. The req_oauth_*() functions implement the OAuth flows: req_oauth_auth_code() (opens a browser; for interactive use), req_oauth_client_credentials() and req_oauth_bearer_jwt() (server-to-server), req_oauth_device(), req_oauth_password(), req_oauth_refresh() and req_oauth_token_exchange(). They take an oauth_client() and cache the token, encrypted, in a directory (oauth_cache_path(), which defaults to a standard R user cache directory since httr2 1.3.0); tokens are refreshed automatically and oauth_cache_prune() and oauth_cache_clear() delete old ones. httr2 1.3.0 raised the default margin before expiry at which a cached token is treated as expired from 5 to 30 seconds (the expiry_margin argument) and fixed the pruning of cached tokens, which had not matched the encrypted files written to disk. The httr2 OAuth article is httr2 package documentation: OAuth. Credentials never belong in the script; use Sys.getenv() and obfuscate().

Large or open-ended responses are streamed rather than loaded: req_perform_connection() returns a response whose body is a connection, read in pieces with resp_stream_lines(), resp_stream_sse() (server-sent events) and resp_stream_bytes() (httr2 1.0.4; req_perform_stream() is superseded by it, and soft-deprecated since httr2 1.2.0). req_perform_promise() (httr2 1.0.3) returns a promise so a request can run in the background of a Shiny app or an async pipeline; the Parallel and Asynchronous Computing page puts it in context. is_online() wraps curl::has_internet(). httr2_translate() (httr2 1.2.3) and curl_translate() turn a request into the equivalent curl command and back, which is useful for copying a call from an API’s documentation.

JSON with jsonlite

JSON is the body format of most web APIs, and httr2 reads and writes it with jsonlite: req_body_json(req, data, auto_unbox = TRUE, digits = 22, null = "null") calls jsonlite::toJSON(), and resp_body_json(resp, simplifyVector = FALSE, ...) calls jsonlite::fromJSON(). The defaults differ in one important way: httr2 writes length-one vectors as JSON scalars (auto_unbox = TRUE), whereas toJSON() on its own writes them as one-element arrays, and resp_body_json() returns lists (simplifyVector = FALSE), while jsonlite::fromJSON() simplifies by default. simplifyVector = TRUE turns an array of records into a data frame, the form that data.frame code wants (the scripts above do it for the /books route); digits = 22 keeps the full double precision of numbers on the way out. The rules of simplification and the handling of NA and NULL belong to Serialization: RDS, RData and JSON. For XML and HTML bodies, resp_body_xml() and resp_body_html() use xml2.

Pitfalls

  • A download that "worked". download.file() returns 0 or a non-zero status, and with several URLs it may not raise an error at all. Test the value, and for a vector of URLs read attr(status, "retvals"). Never assume the file is there because the call returned.

  • A text-mode transfer on Windows. mode = "w" (the default) changes line endings and corrupts binary files; the damage is invisible on Linux and macOS. Always pass mode = "wb" for anything that is not text.

  • Secrets in code and in logs. A token or password belongs in an environment variable (Sys.getenv("SHELF_API_TOKEN")), a .Renviron file outside version control or a secrets store; never in a URL (https://user:password@host/ shows up in server logs) and never in a script that is committed. Printing a request is safe for Authorization and for headers marked .redact; printing req_get_headers(req, redacted = "reveal"), a saved log or curlGetHeaders() output of an authenticated URL is not.

  • Unescaped path segments and query values. URLencode() leaves reserved characters alone, so it is wrong for a query value (reserved = TRUE, or req_url_query(), which encodes for you); req_url_path_append() does not escape, so curl::curl_escape() a segment that came from data.

  • Treating a 404 as a connection error, or the reverse. HTTP errors are httr2_http_<status>; failures to connect, resolve or finish in time are httr2_failure. Handle them by class, and use req_error(body = ) so the R error carries what the API said.

  • Retrying what must not be repeated. req_retry() is safe for GET; for a POST that creates a record, check that the API is idempotent or uses an idempotency key. Without max_tries (or max_seconds) httr2 makes only two attempts.

  • Polling with Sys.sleep(). Use req_retry() with retry_on_failure = TRUE, or a loop with a limit, as the examples do; an unbounded while loop that waits for a service hangs forever when the service never comes up.

  • The default 60 seconds. options(timeout) limits the time without a response, not the whole transfer, and 60 seconds is too short for large files; set it in the script with max() so a user’s higher value stays.

  • Tests that depend on the internet. A test that calls a real API fails when the network, the API or the credentials change. Mock the responses (with_mocked_responses(), local_mocked_responses()) or serve them locally, and guard live tests with testthat::skip_if_offline() or an environment variable.

  • Reading a CSV from https:// on an old R. Before R 3.3.0 read.csv("https://...") needed a method choice on Windows; since 4.2.0 nothing needs to be done (R FAQ 7.43).

libcurl is available as an optional method: capabilities("libcurl"), libcurlVersion(), curlGetHeaders(), download.file(method = "libcurl") (several URLs at once, redirections) and url(method = "libcurl"), with the option url.method

R 3.2.2

on non-Windows platforms download.file(method = "auto") chooses libcurl for https:// and ftps:// URLs when it is available

R 3.4.0

on Unix-alikes the default methods of download.file() and url() choose "libcurl" except for file:// URLs; the "wget" and "curl" methods give an R error rather than a non-zero return value when the external command fails

R 3.6.0

download.file() and url() get the argument headers for custom HTTP headers (for example basic authentication)

R 4.0.3

the option timeout can be set from R_DEFAULT_INTERNET_TIMEOUT; libcurl-based access, including curlGetHeaders(), now respects timeout

R 4.1.0

curlGetHeaders() gets the arguments timeout and TLS

R 4.1.1

ftp:// URLs are deprecated; the non-default "internal" method is deprecated for http:// and ftp://

R 4.2.0

on Windows download.file(method = "auto") and url(method = "default") use libcurl for everything except file://; the "internal" method supports only file://; "wininet" no longer supports ftp://; libcurl is required to build R from source

R 4.2.2

on Windows, R_LIBCURL_SSL_REVOKE_BEST_EFFORT switches to best-effort certificate revocation checks for the libcurl method

R 4.3.0

download.file() gives a helpful error for an invalid download.file.method option; libcurl 8.x is accepted by configure

R 4.5.0

install.packages() and download.packages() download packages simultaneously with libcurl; download.file() reports the outcome of individual files

R 4.5.2

install.packages() and download.packages() again consult download.file.method when the method is unspecified

R 4.6.0

credentials for basic authentication with the libcurl method can be provided in a netrc file named by options("netrc")

Where older tutorials differ

Much of the advice on the web about R and HTTP predates httr2 1.0.0 (2023) and the Windows libcurl default (R 4.2.0). It still works in many cases, and it is not wrong to read it; it is a map of what replaced what.
