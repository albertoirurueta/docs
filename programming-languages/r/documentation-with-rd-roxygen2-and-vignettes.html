Documentation with Rd, roxygen2 and Vignettes

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. A package is only as usable as its documentation: every exported function, dataset and class needs a help page, R CMD check reports the ones that do not have one, and a long-form guide (a vignette) is what turns a set of functions into something a newcomer can start from. R’s own documentation format is Rd, a LaTeX-like markup language that R converts to plain text, HTML, LaTeX and runnable example code, and that nobody writes by hand any more if they can avoid it: roxygen2 generates the Rd files from comments written next to the code. This page covers the whole chain. It starts with Rd itself and the base-R tools that parse, convert and check it, goes on to roxygen2 (its tags, its markdown, the way it documents data and S3, S4, R6 and S7 classes, how it reuses text), and then to vignettes (knitr and R Markdown, and Quarto), pkgdown websites, the inst/CITATION file and NEWS.md. The tools that ran for real are base R with its tools and utils packages, roxygen2 8.1.1, devtools 2.5.2, usethis 3.2.2, knitr 1.52, rmarkdown 2.32 (with the Pandoc that rmarkdown finds), pkgdown 2.2.1 and withr 3.0.3; S7 0.2.2 and R6 2.6.1 are only documented, not used; the Quarto command-line program 1.10.19 rendered one file; and the default linters of lintr 3.4.0 were used only to check the scripts. The quarto R package (the vignette engine for Quarto) is not installed in the image, so what it adds is described and not run, and the same holds for the doclisting package, the GitHub Actions workflow of a pkgdown site and every command that needs a GitHub account. The image also has no TeX installation, so the conversion to PDF is shown failing and the conversions that work without TeX are shown instead.

Every example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines that start with #> are what it printed. The scripts also pass the default lintr linters. The names books, loans and the book() constructor belong to the running library-shelf scenario described on the section index. The shelf package shown here was created, documented, tested, built and checked for real with these tools, and its files are shown as the tools wrote them: the man/*.Rd files, the NAMESPACE and the DESCRIPTION fields were written by roxygen2 and usethis, and vignettes/shelf.Rmd, inst/CITATION and NEWS.md are the files of the package. Scripts that change the package (devtools::document(), R CMD build, R CMD check) worked on a copy of it. Paths are shortened to ~/shelf (the directory of the package) and ~ (the directory that holds it), the platform lines at the top of an R CMD check log are left out, and so are timings and temporary directories. Quotation marks in messages are the typographic quotes that R prints in a UTF-8 locale. Where a script writes an Rd file or a throwaway package, it writes it to a temporary directory, builds a small package there and prints the generated file: the file text on the page is what roxygen2 wrote.

This page continues the package pages. Creating Packages builds the shelf package and explains DESCRIPTION, NAMESPACE and the R CMD commands, Testing with testthat tests it and Publishing to CRAN submits it. How to read the documentation that this page teaches you to write is in Getting Help and Documentation.

Rd: the documentation format of R

R objects are documented in files written in the R documentation format, Rd. Writing R Extensions describes it as a simple markup language, much of which closely resembles (La)TeX, that can be processed into a variety of formats including LaTeX, HTML and plain text. The R distribution contains more than 1400 such files, one or more per function of the base and recommended packages, and every help page you have read in R was produced from one. When a package is installed, its Rd files are parsed and stored in the library in a binary form (the help directory of the installed package), and help() renders them on demand: as text in a terminal, as HTML in the browser. That design is the reason that the same source gives a page in the console, a page on the CRAN site, a chapter of the PDF reference manual and the examples that example() runs.

The anatomy of a file

An Rd file has three parts. The header is mandatory and gives the name of the file, the topics documented, a title, a short description and the usage of the objects documented. The body (arguments, value, details, examples and so on) gives the rest, and an optional footer carries keywords. The sections are macros that start with a backslash and take their arguments in braces, and they can appear in any order. Unless a section is allowed to repeat, only the first occurrence of a standard section is kept, with a warning. This is the file that roxygen2 wrote for normalise_isbn() and is_valid_isbn13(), which share one page:

% Generated by roxygen2: do not edit by hand
% Please edit documentation in R/isbn.R
\name{normalise_isbn}
\alias{normalise_isbn}
\alias{is_valid_isbn13}
\title{Normalise and validate ISBN-13 strings}
\usage{
normalise_isbn(x)

is_valid_isbn13(x)
}
\arguments{
\item{x}{A character vector of ISBNs; \code{NA} and empty strings are allowed.}
}
\value{
\code{normalise_isbn()} returns a character vector of the same length;
\code{is_valid_isbn13()} a logical vector of the same length, \code{FALSE} for
\code{NA} and for the empty string.
}
\description{
\code{normalise_isbn()} drops everything except digits and \code{X} and upper-cases
the result, so \code{"978-0-00-100010-0"} and \code{"9780001000100"} compare equal.
\code{is_valid_isbn13()} checks that a (normalised) string has 13 digits and a
correct check digit: the digits are multiplied alternately by 1 and 3 and
the sum must be divisible by 10.
}
\examples{
normalise_isbn("978-0-00-100010-0")
is_valid_isbn13(c("978-0-00-100010-0", "9780001000101", "", NA))
}

The first two lines are Rd comments (a percent sign starts a comment that runs to the end of the line) and tell a human not to edit the file. Then come the sections, in the order roxygen2 writes them. The most used ones, with the kind of text each takes, are in the table. Writing R Extensions distinguishes four kinds of input: LaTeX-like text with markup macros, verbatim text where nothing but the comment marker is interpreted, R-like text for code with some embedded macros, and a rare verbatim variant, used in the first argument of \eqn, \deqn, \figure and \newcommand, in which the comment marker need not be escaped.

An Rd file therefore has the same skeleton as every help page you have read in R: the title, Description, Usage, Arguments, Details, Value, Note, References, See Also and Examples. Writing R Extensions also states a rule for the title: capitalised, without a final period, no more than about 65 characters. R 4.4.0 made tools::checkRd() report titles and section names that end in a period; R CMD check ignores that finding unless the environment variable _R_CHECK_RD_CHECKRD_MINLEVEL_ is set to -5 or smaller (the NEWS entry is in the version notes below).

Looking at the parse tree

Rd is parsed by tools::parse_Rd(), which returns a list of class Rd in which every element carries its macro in the attribute Rd_tag. That is the structure that every converter and every check below walks. The script parses man/book.Rd (written by roxygen2 from R/book.R) and looks at the top level: the two comment lines, then \name, three \alias entries and the sections.

# Parse man/book.Rd (written by roxygen2) and look at the parse tree.

#> [13] "\\seealso"     "\\concept"

Rd markup in one file

The macros for marking text, building lists and tables, linking, writing mathematics and running code are the part of Rd that people look up. This is a hand-written Rd file that uses most of them, rendered as text with tools::Rd2txt(). The script writes the Rd text to a temporary file with a raw string, so that the page shows the Rd as it is typed, and then converts it, running the three stages of evaluation of \Sexpr (explained below). The option underline_titles = FALSE only keeps the backspace-based underlining of the section titles, which a terminal shows and a page cannot, out of the output.

Every macro on the page has a purpose, and the plain-text conversion shows what happens to each one. The marking macros are logical, not physical: \code{} says "a piece of R code or the name of an R object" and each output format chooses the typography (typewriter font in HTML and PDF, typographic quotes in text). \emph{} and \strong{} emphasise (the text conversion uses underscores and asterisks), \sQuote{} and \dQuote{} quote without hard-wiring the quotation marks, \pkg{} names a package, \file{} a file, \env{} an environment variable, \option{} a command-line option, \command{} a command, \email{} an address, \var{} a metasyntactic variable, \kbd{} keyboard input, \samp{} a literal sequence of characters, \dfn{} a defining use of a term, \cite{} a reference without a link, \acronym{} and \abbr{} abbreviations. \verb{} and \preformatted{} keep their text exactly, and \url{} and \href{url}{text} write links to the web (the first argument of both is verbatim, with percent signs and braces escaped by a backslash). Two macros are built in for text that cannot be written plainly: \R for the name of the language and \ldots or \dots for an ellipsis; both should be followed by {} unless a space follows.

Lists and tables have three list macros and one table macro. \itemize and \enumerate take \item followed by a space and the text, with no braces; \describe takes \item{label}{body} with two arguments, exactly like the entries of \arguments and \value; \tabular{lrr}{...} takes the alignment of each column (l, r or c) and then lines separated by \cr with fields separated by \tab. There must be the same number of fields on each line as columns, and there is no white space between \tabular and its first argument. Mathematics uses \eqn{latex}{ascii} for inline formulas and \deqn{latex}{ascii} for displayed ones: the first argument is typeset by KaTeX or MathJax in HTML help (from R 4.2.0) and by LaTeX in the PDF manual, the second is what the plain-text help shows, and a single argument serves for both when the LaTeX source is readable as text (the text converter also knows the relations \le, \ge and \ne). In the output above \eqn{d > 21} has the one-argument form and \eqn{n \le 5}{n <= 5} has two.

Three macros decide what an output format sees. \if{format}{text} and \ifelse{format}{text}{alternate} select by output format (example, html, latex or text; TRUE matches all formats); \out{literal} writes its text unescaped and is used inside \if{html}{} to emit raw HTML; and a block between a line #ifdef windows (or #ifdef unix, or #ifndef with either) and a line #endif is included or excluded for one operating system before the page is processed. Examples: what is shown, what is run

The \examples section is both documentation and a test: its code is shown on the page, run by example() and run by R CMD check, so an example must be executable on any machine, without Internet access, without interaction and without writing outside a temporary directory. Four macros control that. They appear in the output of the previous script: the code in \dontrun{} is shown (as a comment, ## Not run:) but never run; \donttest{} code is shown and run by example() but, by default, not by R CMD check; \dontshow{} code is run but not shown (it used to be called \testonly, which is still accepted); and \dontdiff{} (new in R 4.4.0) marks code whose output is ignored when the check output is compared with a saved reference output.

R 4.0.0 changed what \donttest means for a CRAN submission: R CMD check --as-cran now runs the \donttest examples too, instead of telling the tester to run them (setting _R_CHECK_DONTTEST_EXAMPLES_ to a false value turns that off during development). So \donttest no longer hides slow or fragile examples from the CRAN checks; it only hides them from a plain R CMD check. The documentation recommends it only for code that may fail in circumstances that are hard to test for, with a comment that explains why. Code that needs a service, a key or a program that may be missing is better guarded by a condition, which is what the roxygen2 tag @examplesIf below writes. Examples that read from stdin, such as scan(), cannot run, because example() uses source(). Data for examples comes from random numbers or from the standard data sets (data()).

Dynamic pages: \Sexpr and \RdOpts

\Sexpr[options]{code} evaluates R code inside an Rd file and inserts the result. The options follow Sweave’s format: eval (default TRUE), echo (default FALSE), keep.source (default TRUE), results (text, the default, applies as.character() to the value; verbatim shows the printed value; rd parses the result as Rd and inserts it, which is how aliases can be computed; hide), strip.white and stage. stage is the important one: stage=build runs when the source tarball is built, stage=install (the default) when the package is installed from source, and stage=render each time the page is displayed. The order is always build, then the #ifdef conditionals, then install, then render, and code runs once in each stage, so a \Sexpr[results=rd] can output a \Sexpr for a later stage but not for the current or an earlier one. \RdOpts{} sets new defaults for the \Sexpr that follow it. The file above has a build-stage and a render-stage \Sexpr in one sentence. The first conversion ran all three stages with stages = c("build", "install", "render") and printed "26 letters" and "R"; the second, at the end of the script, ran a small file with the default stages = "render" and left the build-stage macro exactly as written, because for a package that stage is over by the time the page is rendered. In a package the build stage is the way to compute something once, when the tarball is made (the R 4.6.0 macros for bibliographic citations are built that way), the install stage fits text that depends on the installation, and the render stage text that must be current every time the page is shown. Since R 4.6.0 the error message of a failed \Sexpr includes the call of the original condition, and warnings include the Rd source location.

User-defined macros, encoding and figures

\newcommand and \renewcommand define macros inside an Rd file. They take two verbatim arguments, the name of the new macro with its backslash and its definition, and the definition may use placeholders #1 to #4; the number of arguments is the highest placeholder seen, and the arguments are substituted as text before the result is parsed. \newcommand refuses a name that is already defined, \renewcommand replaces one, built-in macros included. The file above defined \isbn as \code{ISBN-13} in its first line. R ships a set of system macros in the file share/Rd/macros/system.Rd that are available in every Rd file: \doi{} for a digital object identifier, \CRANpkg{} for a package on CRAN, \sspace for a space after a period that does not end a sentence, \packageTitle{} and its relatives (\packageDescription, \packageAuthor, \packageMaintainer, \packageDESCRIPTION, \packageIndices) that read the fields of DESCRIPTION when the package is built, and, new in R 4.6.0, \manual{name}{node} to refer to a section of one of the R manuals. Macros that several pages of a package share go into an Rd file in man/macros, which is installed into help/macros, and a package can use the macros of another by naming it in the RdMacros field of DESCRIPTION.

An Rd file with a character outside ASCII needs an \encoding{} line, unless DESCRIPTION declares Encoding: UTF-8, which shelf does; the file is converted to UTF-8 before parsing and UTF-8 is the preferred encoding. The manual advises avoiding non-ASCII characters in Rd files wherever possible, and also the symbols <, >, $, ^, &, |, @, ~ and * outside verbatim environments, because some fonts used for PDF manuals do not render them; tools::showNonASCIIfile() finds the offending bytes. For one word that must be written differently where an encoding is unavailable, \enc{Jöreskog}{Joreskog} gives the encoded and the ASCII form.

Figures for help pages go into man/figures, and \figure{file}{alternate text} includes one: the file types .jpg, .jpeg, .pdf, .png and .svg in that directory are copied to the help/figures directory of the installed package. The text conversion shows the alternate text instead. PDF figures show in the PDF manual and not in a browser, and SVG the other way round, which is why roxygen2 has the option restrict_image_formats for images added through markdown.

Special characters

Four characters need care in Rd. A percent sign starts a comment in every kind of text and has to be written \%, except in the rare verbatim variant. A backslash is written \\. A brace that is not balanced has to be escaped, and all of %, {, } and \ must be escaped in LaTeX-like text. In R-like text (the usage and examples sections) quoted strings are handled differently: braces inside a string do not need escapes. The mistake that costs most time is the percent sign, because the rest of the line, including a closing brace, disappears into the comment. tools::checkRd() is the tool that finds these mistakes, and the next script feeds it six small broken files and shows what it reports for each. It writes every file to a temporary directory and removes that directory from the messages.

# tools::checkRd() on small broken Rd files; each case shows what R reports.
check_rd <- \(label, lines) {
  f <- file.path(tempdir(), "broken.Rd")
  writeLines(lines, f)
  res <- NULL
  msg <- capture.output(
    res <- tryCatch(tools::checkRd(f), error = \(e) conditionMessage(e)),
    type = "message"
  )
  out <- capture.output(print(res))
  # Keep the temporary directory out of the messages.
  cat(label, ":\n", sep = "")
  cat(sub(paste0(tempdir(), "/"), "", c(msg, out), fixed = TRUE), sep = "\n")
}

The messages are worth learning to read. A file without a \title fails the structural check at once. roxygen2: Rd files from comments

Rd is a good format for a machine and a poor one to maintain: the usage section has to repeat the signature of the function exactly, every argument has to be described in a separate block, and each of these is far from the code that changes. roxygen2 moves the documentation into the R source, in special comments that start with #' and sit immediately above the object they document, and writes the Rd files, the NAMESPACE and the Collate field from them. The usage section is taken from the function itself, so it cannot disagree with the code, and the arguments, the exports and the documentation of a function are in one place. roxygen2 is a CRAN package (8.1.1 on 2026-10-08); the 8.0.0 release of 2026-05-01 is the one that requires R 4.1 and moved the package’s settings into Config/roxygen2/ fields of DESCRIPTION, as the section on DESCRIPTION below explains.

Blocks, tags and the first paragraphs

A block is a run of #' lines. The first paragraph is the title, the second is the description, and any further paragraph is the details, unless a tag says otherwise. A tag is a word that starts with @ at the start of a line, and everything up to the next tag belongs to it. The example below uses a throwaway package in a temporary directory, so that nothing but the generated files is involved: one function with a title, a description with markdown code and a link, a details paragraph with a list, a parameter tag that documents two parameters, a return value, an example, and the two namespace tags @importFrom and @export. The script runs roxygen2::roxygenise() and prints the Rd file and the NAMESPACE that came out.

What roxygenise() does

roxygen2::roxygenise() (spelt roxygenize() too) takes a package directory, loads the package code, parses the blocks and runs the roclets. A roclet is a processor of the parsed blocks that produces one kind of output: rd writes man/*.Rd, namespace writes NAMESPACE, collate writes the Collate field of DESCRIPTION from the @include tags. Those three run by default. By default the package is loaded with pkgload, and the code is evaluated, so that roxygen2 knows what a function, a dataset or a class looks like. devtools::document() is the usual front end: it calls roxygenise() and prints its progress. roxygen2::needs_roxygenize() (new in 8.0.0) answers cheaply whether the Rd files are older than their sources. Every file roxygen2 writes starts with the comment lines "Generated by roxygen2: do not edit by hand" and "Please edit documentation in R/book.R", and roxygen2 only rewrites files that carry that header. The script reads the settings of shelf as roxygen2 sees them.

DESCRIPTION: version and options

roxygen2 8 keeps its settings in Config/roxygen2/ fields of DESCRIPTION. The version of roxygen2 that last documented the package is Config/roxygen2/version; the field that roxygen2 7.x used for this purpose, a note-style field written under another name, is no longer written, and roxygen2 8 migrates a package automatically the next time it documents it (the message "First time using roxygen2. Parameters and returns

Every argument of every exported function needs an @param entry, and R CMD check reports a WARNING otherwise: the steps "checking for code/documentation mismatches" and "checking Rd \usage sections" compare the arguments in the usage with the \arguments section, and report arguments that are undocumented and arguments that are documented but do not exist. @param takes one or several names (@param member,days), the description may use markdown, and a description that applies to many functions is documented once and inherited, which is the subject of the next section. @returns documents the value: what class it has, what its length is, and whether it is returned invisibly. The tidyverse project’s own conventions (community material, not part of R) ask every function to say what it returns, because \value is the first thing a reader of the page checks. The shelf function overdue_loans() documents the days_out column it adds, loan_summary() the four columns it returns, and print.book() says that it returns its argument invisibly.

Links, topics and aliases

The markdown forms above are the usual way to link. For a topic in the same package [book()] links the alias book; for another package [pkg::fun()] writes a link with that package as an anchor, and the package should be listed in Imports or Suggests of DESCRIPTION, because the check for cross-references needs it ("Always list the linked package as a dependency", in the roxygen2 message that the first run of document() printed). Since roxygen2 8.0.0 all generated links share one code path, links to external packages use the topic alias as the anchor (which removed the R CMD check note about non-topic package-anchored links), and infix operators such as [%in%] can be linked. A link to a class is [Book-class] for S4, [book] for S3 (when the page’s alias is the class name), and [Book] for S7. The alias lists of the shelf pages show that one page often serves several topics; help.search() finds them by title, alias, concept and keyword.

Namespace tags

The same comments write the NAMESPACE. @export is the one every package uses, and its meaning depends on what it is on: a function gives export(name), an S3 method gives S3method(generic,class), an S4 class gives exportClasses(). The rule for S3 methods is strict: always export them, even when the generic is internal, since exporting is what registers the method; a method that is not exported is not found by dispatch in the installed package, although devtools::load_all() hides that mistake by exposing every function. roxygen2 warns about a method without a tag, as the "Messages" section below shows, and @exportS3Method NULL silences the warning for a method that is registered another way. For a method of a generic that lives in another package there are two ways: import the generic with @importFrom pkg generic and @export the method, or write @exportS3Method pkg::generic, which registers the method when the other package is loaded and needs no import. Documenting data, the package and classes

Functions are the easy case. Three other kinds of object need their own habits: data sets, which are not exported and are documented by name; the package itself, which has an overview page; and classes of the four object systems, which are documented through their constructors, generics and methods.

S3 classes and methods

An S3 class has no definition to document: the constructor is a function, the generics and methods are functions, and the class is described by the constructor’s page. The roxygen2 article gives the working rules: document a generic like any function and say that it is a generic, document a class by its constructor, and document a method only when it has behaviour of its own, with a link back to the generic; always export S3 methods, because exporting registers them. shelf follows them. The constructor family book(), new_book() and validate_book() is one page (the @rdname book tags put the three blocks into the same file), and the four methods of the class are one more page, book-methods, that has no object of its own: the first block is written above NULL with @name book-methods, and the method blocks are @rdname book-methods and @export. S4 classes and methods

Vignettes

A help page documents one function. A vignette documents how the functions work together: a long-form guide, written in a literate format in which prose and R code are mixed, whose code is run when the document is built, so that the output it shows is real and a change that breaks it is noticed. R’s name for the idea (and for the document) is "vignette", and it is part of the package system: sources live in vignettes/, R CMD build turns them into HTML or PDF in inst/doc, the installed package has them in its doc directory, vignette() and browseVignettes() find them, and R CMD check runs their code and checks that the outputs are up to date. Sweave is the engine that ships with R, for LaTeX documents with the extension .Rnw; every other engine is provided by a package, so a package with vignettes in another format says which in DESCRIPTION.

The files and the fields

The shelf vignette is an R Markdown file, vignettes/shelf.Rmd, processed by knitr (1.52) and rmarkdown (2.32), which uses Pandoc for the final conversion to HTML. Three things in DESCRIPTION make that work: Suggests: knitr, rmarkdown (the packages must be available when the package is built and checked, and are not needed to use it), VignetteBuilder: knitr (the name of the package that provides the vignette engine; without the field, R CMD check does not know that the package has non-Sweave vignettes) and, in the file itself, a \VignetteEngine line. The file, as usethis::use_vignette() created it and as the package has it, is the following. The vignette: block in the YAML header carries the three lines that R reads (the %\Vignette... lines are comments for R and are ignored by Pandoc), and output: rmarkdown::html_vignette selects an HTML format with a light style and small output that was designed for package vignettes.

knitr and R Markdown in a vignette

A knitr-based vignette is an ordinary R Markdown document with the header lines above; the knitr site and the rmarkdown site document the chunk options and the output formats. The R chunks are evaluated in order, each chunk’s results and figures are inserted, and the chunk options (collapse, comment, fig.width, eval, echo, include) are knitr’s; a chunk with eval = FALSE is shown and not run, which is how a vignette shows code that needs a service or a long computation. All the chunks run when the package is checked, so a vignette is a test too. Of the engines that knitr registers, listed by the script above, knitr::rmarkdown (R Markdown to HTML or PDF) is the one used here, knitr::knitr processes Sweave-like .Rnw files with knitr, and the names that end in _notangle are the same engines without the extraction of the code. A vignette in HTML needs Pandoc, and one in PDF needs LaTeX.

Four rules keep a vignette from causing trouble on CRAN. Make it deterministic, as the shelf vignette does by fixing the reference date (today <- as.Date("2026-06-30")) instead of asking the system for the current date. Keep it fast, since the CRAN Repository Policy asks for the checks to take as little CPU time as possible (see Publishing to CRAN). Keep files small: PDF or HTML output that is too large is a known problem (the manual mentions a PDF of 72 MB), and the CRAN policy sets a 5 MB guideline for documentation. And use only packages that are declared, because the check "unstated dependencies in vignettes" fails on a package that is used but not listed in Suggests or Imports.

If a document should be on the website of the package but not in the tarball (because it is large, or needs a service), usethis::use_article() creates an "article" that only pkgdown builds, in the next section.

Sweave and other vignette formats

inst/CITATION: how to cite the package

README and the other files

A README.md is not part of R’s documentation system but is where people arrive: GitHub shows it, CRAN shows it on the package’s page, and pkgdown uses it as the home page. It should say what the package is for, how to install it and one short example. When the example should run, README.Rmd is rendered to README.md with devtools::build_readme(), as usethis::use_readme_rmd() sets up (the script of the package-page section created one). usethis adds README.Rmd to .Rbuildignore when it creates it, as the output of that script shows. CONTRIBUTING.md and CODE_OF_CONDUCT.md are other files of the same kind, and shelf also has a cran-comments.md, the notes that the author sends to CRAN with a submission, which is explained in Publishing to CRAN.

Pitfalls

  • Editing a generated file. A file that starts with "Generated by roxygen2: do not edit by hand" is overwritten by the next devtools::document(); edit the comment in the R file. The reverse also holds: roxygen2 leaves a hand-written Rd file alone (it says so, as shown above), so a package can mix the two, and a file that was once generated and is now edited by hand must lose its header.

  • Forgetting to document after a change. R CMD build does not run roxygen2: it packages man/ and NAMESPACE as they are. Commit both, run devtools::document() before every commit that touches a tag, and let devtools::check() catch the rest. devtools::load_all() does not regenerate documentation either, and it exposes every function, which hides an S3 method that lacks @export.

  • The percent sign and the braces in Rd. In hand-written Rd, % starts a comment and eats the closing brace, and unbalanced braces are an error: \% and balanced braces. roxygen2 with markdown escapes the percent signs for you; roxygen2 without markdown does not.

  • Examples that cannot run on a check farm. Examples may not need a network, a key, a display or write access outside a temporary directory. \dontrun{} hides code from every check, which reviewers dislike for code that could run; \donttest{} is run by --as-cran since R 4.0.0; @examplesIf runs the example only when its condition holds. Examples are also run by pkgdown and by example().

  • Arguments that do not match. The usage is taken from the code, so a renamed argument shows in the usage at once, but the @param for the old name stays and is reported ("Documented arguments not in \usage"), and the new one is "Undocumented". Run devtools::check_man() after every change of a signature.

  • A description that repeats the title. A block with a title and nothing else gives a page whose description is the title, as the generated page for overdue_rate() above shows. R CMD check accepts it; readers and CRAN reviewers do not.

  • Markdown surprises. A sentence in a comment that starts with 1. becomes a list. [word] becomes a link. A heading level 1 makes a new section. Inline code that does not parse as R becomes \verb{}, not \code{}. Block quotes, inline HTML and horizontal rules are not supported.

  • The warnings of the first run. The first document() of a new package warns about links to topics that are written in the same run, and the second run is clean. If a warning is still there on the second run, the link is wrong, or the linked package is not in DESCRIPTION.

  • The index of a pkgdown site. Once _pkgdown.yml has a reference field, every topic has to be listed in it or be internal. pkgdown::check_pkgdown() finds the missing ones, before a build fails.

  • Non-deterministic vignettes. A vignette that prints the current date, uses a random number without a seed, or reads the current state of a service changes at every build, and a changed output with no changed source confuses reviewers. The shelf vignette fixes the date.

  • Built vignettes in the repository. inst/doc and the files in vignettes/ that the build leaves (*.html, *.R) are products. usethis::use_vignette() ignores them with .gitignore; the tarball gets them from R CMD build.

  • A CITATION file that depends on installation. The file is run when the package is not installed; calling packageDescription() or utils::packageVersion() in it works on the author’s machine and fails on CRAN. Use meta.

  • A PDF manual needs TeX. Without pdflatex, R CMD Rd2pdf fails as shown above, and a plain R CMD check reports a WARNING and an ERROR for the PDF manual. The Rd files themselves are checked by checkRd() and by the other steps of the check without TeX, so --no-manual loses only the PDF.

  • A hand-written man directory and roxygen2 together. A page of the same name that roxygen2 would write is skipped, and nothing says that the roxygen2 block above the function is then not documentation: read the "Skipping" line.
