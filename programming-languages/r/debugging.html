Debugging

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. Everything on this page is base R (the base, utils, methods and stats packages that ship with R), so no add-on package version applies; the lintr 3.4.0 default linters were used only to check the scripts. Debugging is the part of programming where you stop guessing: you ask R which calls were active when something failed, you stop the program at a chosen point and look at the variables, or you step through a function one statement at a time. R’s tools for this are small and old, they work the same way in a terminal, in RStudio, in Positron and in a batch job, and the graphical debuggers are front ends to them. This page describes each tool, shows what it prints, and says which one to reach for when. The error-handling side, catching and signalling conditions, is in Conditions and Error Handling; checking inputs early so that the failure is close to its cause is in Defensive Programming and Input Validation.

There are two kinds of example. The first kind is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)); the lines that start with #> are what it printed, in the order R printed them, so a message that R writes to the error stream appears where it was written. The scripts pass the default lintr linters; a # nolint: comment marks a line where the code is what a default linter dislikes. The second kind is a transcript of an interactive session, shown as a text block with the prompts exactly as R printed them: > for a new command, + for a continued one, Browse[1]> inside the browser and Selection: in the menus of recover() and debugger(). Debugging is conversational, and the prompts are the point, so these blocks are not scripts and carry no #> lines. They were captured by feeding the commands to R --interactive --no-save --quiet, which makes R echo the commands it reads, and a final empty prompt is left out. An interactive session keeps the source text of the functions you type (options(keep.source = TRUE) is the default there), which is why the transcripts show source references such as at #3 and debug at #2: that Rscript output does not have. The names books, loans, shelf_today, loan_days and the book() constructor come from the running library-shelf scenario described on the section index: a script that needs them starts with source("scenario.R"). Where a message contains quotation marks, they are the typographic quotes R prints in a UTF-8 locale.

The tools at a glance

The R Language Definition puts it in one paragraph: most debugging takes place through calls to browser() or debug(), which rely on the same internal mechanism and give the user a special prompt at which any command can be typed, evaluated in the currently active environment (R-lang: Debugging). Everything else on this page is a way of arriving at that prompt, or of finding out where to arrive. The debugger only sees interpreted R code: if a function calls compiled code, execution halts at the next statement that is evaluated in R, and a symbolic debugger such as gdb is needed for the compiled part (a pointer to that is in the section on compiled code below).

A debugging session has a rhythm that does not depend on the tool: find where the failure happens, form a guess about the state that causes it, look at that state, change something, and run again. The tools differ in how much they make you re-run. traceback() and options(error = recover) work on an error that has already happened. browser() and trace() ask you to run the code again with a stop in it. debug() asks for a new run with the stop at the start of a function. The cheapest tool that answers the question is the right one, and the sections below follow that order.

The error message is the first tool

R reports an uncaught error as Error in <call> : <message>. The call is the function call that was being evaluated when the error was signalled, and the message is the text given to stop() or produced by R itself. When the pair does not fit on one line the message moves to the next line. Both parts are available as data when the error is caught: a caught error is a condition object, a list with the fields message and call, and conditionMessage() and conditionCall() read them (R documentation: conditions).

The running example for this page is a small piece of the shelf scenario. member_report() counts a member’s loans and how many were overdue; it calls count_overdue(), which calls is_overdue() once per loan through vapply(). The scenario data has a loan whose date is the impossible 2025-02-30, which as.Date() turned into NA, and the member is Ana Ruiz, so the first report that touches that loan fails. The script defines the three functions, runs the report for another member (which works), and then catches the failing one as a condition object.

source("scenario.R")

# A chain of three functions with a bug: a loan with an impossible date.
is_overdue <- function(loan_date, return_date,
                       today = shelf_today) { # nolint: object_usage_linter.
  end <- if (is.na(return_date)) today else return_date
  if (as.integer(end - loan_date) > loan_days) TRUE else FALSE # nolint: object_usage_linter, line_length_linter.
}

count_overdue <- function(rows) {
  flags <- vapply(seq_len(nrow(rows)), \(i) {
    is_overdue(rows$loan_date[i], rows$return_date[i])
  }, logical(1L))
  sum(flags)
}

member_report <- function(loans, who) {
  rows <- loans[loans$member == who, ]
  c(loans = nrow(rows), overdue = count_overdue(rows))
}

member_report(loans, "Ben Okafor")
#>   loans overdue
#>       5       3

The message, missing value where TRUE/FALSE needed, is what R says when an if condition is NA, and the call is the if expression itself, not the function around it: for errors that R detects in a language construct the "call" is that construct, which is why the call shown does not look like a function call. Nothing in the message says which member, which loan or which function called is_overdue(). That is what the next tools are for. Two details in the output matter. The error raised with call. = FALSE has no call at all: conditionCall() is NULL and the printed condition is <simpleError: ...> with no in part. validate_book() and book() in the scenario signal their errors that way, so for them the stack is the only record of where the error came from. And the final traceback() says No traceback available, because both errors were caught by tryCatch() and only an error that reaches the top level leaves a stack behind.

What the same error looks like when nobody catches it depends on how R was started. In an interactive session R prints the message and returns to the prompt, ready for traceback(). In a non-interactive session, such as Rscript or R -f, R prints the message, adds a Calls: line, prints Execution halted and exits with status 1. The next block is a script that fails on purpose and the complete output of running it with Rscript; it is a fragment, not a runnable example, because it ends in the error.

The first report printed its answer, and the second stopped the script: not reached never appears. The Calls: line is a compact traceback, outermost call first and joined with ->, and it is there because the showErrorCalls option is on by default in non-interactive sessions (the options help page says that the call stacks are shown by default for errors there). The anonymous function that vapply() calls appears as FUN. The line is shortened when the sequence is long: showNCalls, by default 50 bytes, sets the length at which ellipses are used, and options(showErrorCalls = FALSE) removes the line altogether, as a later script shows. It is a summary, not a traceback: it has no arguments and no source locations, and it says nothing about which iteration of vapply() failed.

Reading the stack with traceback()

traceback() prints the call stack of the last uncaught error: the sequence of calls that led to it. The help page calls it useful when an error occurs with an unidentifiable error message, and Writing R Extensions recommends running it whenever the cause of an error is not immediately obvious, because errors are often reported as being in some package when the traceback shows that they were raised by another package or by base R (Writing R Extensions: Debugging R code). The calls are listed in reverse order, innermost first, each with the number of its frame, so frame 1 is the call you typed. The help page adds that calls to builtins are included in the stack but calls to specials are not.

The last command, .traceback()[[1]], shows that the stack is data: .traceback() returns the stack as a list or pairlist of calls, deepest first, with each call as a character vector of deparsed lines, and traceback() formats and prints that list. .traceback() was added in R 3.3.0, and since R 4.0.0 the stack that R records when the error is signalled (.Traceback) holds the calls themselves and deparses them only when traceback() or .traceback() is called; the help page warns that where .Traceback is stored is undocumented, so use the functions, not the variable.

traceback() in a script

An Rscript run ends at the first uncaught error, so there is no prompt at which to type traceback(). The error option fixes that: it holds a function, or an expression, that R runs when an error reaches the top level, after printing the message and before it halts. The next script prints the traceback from such a handler and then leaves with q(status = 0). The argument 3 of traceback() means "skip three entries at the top of the stack": the entries for traceback(), .traceback() and the handler that called them, which the help page recommends for exactly this use.

source("scenario.R")

The handler appears in the traceback as an anonymous function call, (function () {...})(), because R evaluates the error option as a call to the function. The stop("boom in h") entry is frame 4, above h(x), since stop() is itself a function call and the error is signalled from inside it. The class: pairlist line is a detail worth knowing when you process the result: the help page says .traceback() returns a list or a pairlist, and for the stack of an error it is a pairlist, so wrap it in as.list() before using lengths() or vapply() on it (the script below does).

The error option takes any of three forms. A function is called with no arguments (options(error = function() ...), or the name of one such as recover). An expression is evaluated: options(error = quote(...)) or an expression() vector, which is the form that fits the one-liners in the manuals. And NULL, the default, restores the standard behaviour: return to the prompt in an interactive session, halt in a non-interactive one. In start-up files the functions of the utils package have to be written with the namespace, as options(error = utils::recover), because the package is not yet attached when the file runs (the options help page says so). A traceback() that is very long can be shortened: max.lines limits the number of lines printed per call, and the options traceback.max.lines and deparse.max.lines set the limit for the whole session. A long call is what do.call() produces when the function is given the objects themselves: the call that R records holds the values, not the names, so a data frame argument is pasted into it. The next script shows how long such an entry gets, and what max.lines = 2 does to it.

source("scenario.R")

first_overdue <- function(df) {
  stopifnot(nrow(df) > 100L)
  days <- df$return_date - df$loan_date
  which(days > loan_days)[1L] # nolint: object_usage_linter.
}

# data frame the call that traceback() has to deparse is long: lengths() counts
# the lines of each entry, deepest call first.
options(error = function() {
  stack <- as.list(.traceback(3))
  cat("lines per entry:", lengths(stack), "\n")
  short <- as.list(.traceback(3, max.lines = 2L))
  cat("with max.lines = 2:", lengths(short), "\n")
  traceback(3, max.lines = 2L)
  q(status = 0)

When traceback() does not help

It reports the stack of the last uncaught error, and only that. An error caught by try() or tryCatch() generates no traceback, and neither does a warning; the help page says that what traceback() prints is the call sequence for the last uncaught error and not necessarily for the last error. The stack ends where the error was signalled, so it cannot tell what the values were. Writing R Extensions gives three more reasons it may not point at the cause. If the innermost call is .C, .Fortran, .Call, .External or .Internal, the error came from compiled code, and as such code can evaluate R expressions the compiled call need not be the innermost one. When S4 method dispatch is involved the traceback can stop at a call such as initialize(value, ...) while the error message names a function that is not in the stack. And for infinite recursion the message evaluation nested too deeply: infinite recursion / options(expressions=)? can be hard to read at the default limit of 5000 nested expressions, so the manual suggests lowering it with options(expressions = 500) and running the example again (the script below does this). In all three cases the tools of the next sections, which stop the program while it is still running, give more.

The live stack: sys.calls() in a calling handler

A calling handler runs on top of the stack of the condition it handles, before anything is unwound, so it can read the live stack with sys.calls() (R documentation: sys.parent and its relatives). That is the one way to get a stack for a condition that a tryCatch() further out would catch, and the way to log the stack of an error without stopping the program. tryCatch(), by contrast, unwinds first, so its handler sees only the frames outside it. The script below logs the stack of the failing report and then lets the error continue to try().

source("scenario.R")

is_overdue <- function(loan_date, return_date,
                       today = shelf_today) { # nolint: object_usage_linter.
  end <- if (is.na(return_date)) today else return_date
  if (as.integer(end - loan_date) > loan_days) TRUE else FALSE # nolint: object_usage_linter, line_length_linter.
}

count_overdue <- function(rows) {
  flags <- vapply(seq_len(nrow(rows)), \(i) {
    is_overdue(rows$loan_date[i], rows$return_date[i])
  }, logical(1L))
  sum(flags)
}

# A calling handler runs on top of the stack of the error, before it unwinds, so
# sys.calls() still shows the frames that led to it. tryCatch() would have
# unwound them first.
show_stack <- function(e) {
  calls <- sys.calls()
  cat("frames on the stack:", length(calls), "\n")
  for (i in seq_along(calls)) {
    cat(i, ": ", deparse(calls[[i]])[1L], "\n", sep = "")
  }
}

  ),

)

Stopping inside the code: browser()

A call to browser() in the body of a function stops the evaluation at that point and gives you a prompt, Browse[1]>, at which any R expression is evaluated in the environment where browser() was called. It is the lowest-level tool: debug() and the breakpoints of the IDEs use the same browser, and the RStudio user guide calls it the lowest-level debugging tool (R-lang: browser; RStudio user guide: Debugging). Its signature is browser(text = "", condition = NULL, expr = TRUE, skipCalls = 0L). The first two arguments carry information for helper programs and can be read back at the prompt with browserText() and browserCondition(); expr makes the stop conditional; skipCalls is for wrappers, and tells the browser to report a location further up the stack when the call to browser() is itself nested in another debugging function (R documentation: browser).

The prompt accepts ordinary R, plus a handful of one-word commands that R interprets itself. The R Language Definition lists five of them, the help page lists them all:

Conditional breakpoints

Stopping on every iteration of a loop is useless when the interesting one is the 512th. browser(expr = <condition>) evaluates the condition and enters the prompt only when it is true. The text argument labels the stop, so that browserText() can tell several breakpoints apart.

Byte-compiled code

R compiles functions to byte code after a couple of calls (the just-in-time compiler, enabled by default since R 3.4.0, which NEWS says will not compile code that contains explicit calls to browser(), to support single stepping from that call). Inserting code without editing: trace()

trace() goes further than debug(). It builds a modified version of a function, with extra code inserted at the start, before chosen statements or on exit, and assigns it back where the original was found; untrace() restores the original. The help page calls it a generalization of debug() implemented differently. The inserted code, the tracer, can be a call to browser() or recover(), but also any expression: a cat() that prints a variable, a condition that stops only when something is wrong, an assignment that saves a value in the global environment. The R Language Definition describes the plainest use: with only a function name, trace() prints the call every time the function is evaluated (R-lang: trace/untrace). The arguments are:

what

The function to trace, as a name or a string, possibly quoted with quote(). Several functions can be traced at once with a vector of quoted names or an expression().

tracer

A function, whose name is used and which is called with no arguments, or an unevaluated expression. browser and recover are the usual function tracers.

exit

The same, evaluated when the function exits, through the on.exit mechanism. returnValue() gives the value about to be returned.

at

A numeric vector, or a list of vectors, of steps of the function body; the tracer runs just before those steps instead of on entry. It works only if the body is a { block.

print

If TRUE, the default, a descriptive line is printed before the tracer runs. Use FALSE with an expression tracer.

signature

A method signature: trace the S4 method and not the generic.

where

Where to look for the function; needed for functions that are not visible from the top level, such as methods in a namespace.

TRUE, or the name of an editor: edit the function’s body interactively, for loops and other places at cannot reach.

Breakpoints from a file: setBreakpoint() and findLineNum()

findLineNum() finds the function and the step that contain a given line of a source file, and setBreakpoint() is a wrapper that calls trace() for it, with browser as the default tracer. The file name is matched by its base name unless nameonly = FALSE, and "file.R#nn" gives the line (R documentation: findLineNum and setBreakpoint). By default they search the global environment; for code inside a package namespace or for S4 methods the envir and lastenv arguments widen the search. The RStudio user guide describes its editor breakpoints in similar terms (see below).

What trace() cannot do

The help page lists the limits. Tracing does not nest: a call to trace() replaces any earlier tracing of the same function, except for edited versions, and untrace() always restores the untraced function. The exit argument will not work if the function itself uses on.exit() without add = TRUE, because the existing call overrides the one trace() adds. Tracing a primitive works only by a special mechanism, replaces the primitive by a function of ..., gives little information, and issues a warning. The traced object is saved back where the function came from, so tracing of a function in the global environment survives in a saved workspace image and goes on in the next session, where untrace() removes it, while functions in packages are not saved with the image, so tracing of them ends with the session. The browser reached through trace() is the ordinary one. Fixes in recent releases show where the edges are: trace() of coerce works correctly since R 4.5.0, isS3stdGeneric() (used by debugcall()) has recognised an S3 generic that is being traced since R 4.0.3, and R-devel, the development version that will become R 4.7.0, makes trace() work for functions whose class attribute has more than one string, such as S7 generics and methods, and fixes a bad call that trace() could insert when tracing rematched S4 methods (R-devel NEWS; upcoming, not run here).

After the error: post-mortem debugging

browser(), debug() and trace() all need a second run of the program. When the failure is expensive to reproduce, the other approach is to arrange for the error itself to leave the frames behind and to look at them afterwards. Writing R Extensions puts the sequence in order: locate the error with traceback(), then look at a post-mortem dump with options(error = dump.frames) and debugger(), or browse the live frames with options(error = recover); and when the cause is still unclear, look at what was happening just before the error with debug() (Writing R Extensions: Debugging R code). Post-mortem debugging is good for finding out exactly what went wrong, in the words of that chapter, "but not necessarily why".

Batch jobs: dump to a file

The expression is wrapped in quote() so that it is stored in the option instead of being evaluated at once, and the function is written utils::dump.frames so that it also works in a start-up file, where utils may not be attached yet. Letting a script continue: catch.script.errors

R 4.4.0 added a documented option for the other common batch need, to carry on after an error: with options(catch.script.errors = TRUE), an error in a non-interactive script is reported and evaluation continues with the next top-level expression, instead of ending the run. The traceback has three entries because stop() is a call too, and the second error is reported without the Calls: line. The option is a switch for the whole script. Finding a warning

A warning has no stack: R signals it, shows or stores a message, and the program goes on. The message names a call, but not always the useful one: NAs introduced by coercion below is reported as coming from FUN(X[[i]], ...), the anonymous call inside vapply(), which says nothing about which caller was responsible. Writing R Extensions suggests turning a warning that is a clear precursor of a later error into an error, so that the usual tools work: options(warn = 2) does that. The warn option has four documented levels: negative ignores warnings, 0 is the default and stores them until the top-level call returns, 1 prints them as they occur and 2 or more turns every warning into an error; the options help page notes that, while sometimes useful for debugging, converting warnings into errors may trigger bugs and resource leaks that would not have been triggered otherwise, which is a reason to set it for a run and not for good. The first script has a warning inside vapply() and shows both the immediate warning and the converted one with its traceback.

# A warning whose call is not much help: it names the inner FUN, not the caller.
pages_of <- function(txt) as.integer(sub("p\\.", "", txt))

total_pages <- function(txts) {
  sum(vapply(txts, pages_of, integer(1L)), na.rm = TRUE)
}

labels <- c("320", "288 p.", "n/a")

options(warn = 2, error = function() {

  q(status = 0)
})

Without a converted warning, two other tools find the same place. tryCatch(warning = ) stops at the first warning and returns the condition, whose conditionCall() is the call that signalled it. A calling handler sees the stack and can then muffle the warning with the muffleWarning restart so the computation finishes, which is the way to inspect many warnings from one run:

pages_of <- function(txt) as.integer(sub("p\\.", "", txt))

}

total <- withCallingHandlers(
  total_pages(labels),

    calls <- sys.calls()

)

Special cases

Infinite recursion

The error evaluation nested too deeply: infinite recursion / options(expressions=)? is raised when the number of nested expressions reaches the limit set by options(expressions =), 5000 by default, and the manual’s advice is to lower it, for example to 500, and run again so that the traceback is short. R 4.2.0 made stack-overflow errors conditions that inherit from stackOverflowError. The help page lists the specific classes: CStackOverflowError for the C stack, protectStackOverflowError for the pointer protection stack, nodeStackOverflowError for the node stack of the byte-code engine and expressionStackOverflowError for the limit of nested expressions, so a handler can tell them apart (R documentation: StackOverflows). The help page also says that such errors can be caught by exiting handlers established with tryCatch(), but that calling handlers may fail because there may not be enough stack to run them, which is why the script catches the error with tryCatch().

# A function that calls itself without a base case.
runaway <- function(n) runaway(n + 1L)

# The default limit, 5000 nested expressions, takes a while to reach and fills
# the traceback; a small limit finds the problem faster. Restore it afterwards.
options(expressions = 500)
err <- tryCatch(runaway(1L), error = \(e) e)
options(expressions = 5000)

conditionMessage(err)
#> [1] "evaluation nested too deeply: infinite recursion / options(expressions=)?"
class(err)
#> [1] "expressionStackOverflowError" "stackOverflowError"
#> [3] "error"                        "condition"
# R 4.2.0 and later signal a classed condition, so the stack overflow can be
# told apart from other errors in a handler.
inherits(err, "stackOverflowError")
#> [1] TRUE

Source: R NEWS: Changes in R 4.2.0

The valid values of expressions are 25 to 500000 according to the options help page, which also warns that increasing it may cause a segfault from overflow of the C stack. The script restores the default after catching the error, and the error is of class expressionStackOverflowError first, then stackOverflowError, error and condition.

S3 methods

For an S3 generic, debug(fun) flags the generic, which does little except dispatch; the method that runs is the thing to flag. When the method is visible, debug(format.book) works. For a method that is not exported, use the triple colon (debug(stats:::predict.Arima) in the manual) or getS3method(). utils::debugcall() does the lookup for you: given a call, it sets the flag on the non-generic function, S3 method or S4 method that evaluating the call would run, based on the classes of the arguments, and undebugcall() clears it. It was added in R 3.4.0 together with the signature argument of debug(), and R 4.4.1 made debugcall(S3Generic()) work when a corresponding S4 generic version is in the methods cache. The help page notes that it uses non-standard evaluation to get the call, so a variable holding a call does not work, and that for non-standard S3 generics the generic itself is debugged. It does not run the call; the idiom eval(debugcall(summary(f))) evaluates it afterwards.

S4 methods

R FAQ 8.5, "How can I debug S4 methods?", answers in one sentence: use trace() with the argument signature= to add calls to the browser, or any other code, to the method that will be dispatched for the corresponding signature (R FAQ 8.5). Writing R Extensions says that debug() "cannot be used for S4 methods"; that text predates R 3.4.0, which added the signature argument to debug(), debugonce(), undebug() and isdebugged(). Since then debug(fun, signature = ) works, implemented with the trace machinery; later releases extended it: R 3.5.0 supports methods on any object of class genericFunction, including group generics, and R 4.5.0 accepts a string that names an S4 generic. The script defines a tiny S4 class (the methods package is attached by Rscript), traces a method and the show() method, and uses isdebugged() with a signature.

# Rscript attaches the methods package, which tracing by signature needs.
setClass("Book", slots = c(title = "character", year = "integer"))
setGeneric("age_in", function(x, ...) standardGeneric("age_in"))
#> [1] "age_in"
setMethod("age_in", "Book", function(x, ...) 2026L - x@year)
setMethod("show", "Book", function(object) {
  cat("<Book>", object@title, "\n")
})

bk <- new("Book", title = "The quiet streets", year = 1999L)
age_in(bk)
#> [1] 27

# The method that runs for a Book, not the generic, gets the tracer (R FAQ 8.5).
invisible(trace(
  "age_in",
  signature = "Book",
  tracer = quote(cat("age_in method for", class(x), "called\n")),
  print = FALSE
))
age_in(bk)
#> age_in method for Book called
#> [1] 27
untrace("age_in", signature = "Book")
age_in(bk)
#> [1] 27

# show() is an S4 generic too; autoprinting a Book calls its method.
invisible(trace(
  "show",
  signature = "Book",
  tracer = quote(cat("show method for Book\n")),
  print = FALSE
))
bk
#> show method for Book
#> <Book> The quiet streets
untrace("show", signature = "Book")

# debug() with a signature uses the trace machinery, and isdebugged() asks about
# one method rather than the generic. Pass the generic function itself, not its
# name, to undebug() when the generic lives in the global environment.
isdebugged("age_in", signature = "Book")
#> [1] FALSE
debug(age_in, signature = "Book")
isdebugged("age_in", signature = "Book")
#> [1] TRUE
isdebugged("age_in")
#> [1] FALSE
undebug(age_in, signature = "Book")
isdebugged("age_in", signature = "Book")
#> [1] FALSE

Printing and checking, the cheap tools

Not every bug needs a debugger. Output that is cheap to leave in is worth having: message() writes to the error stream, so it does not mix with a function’s printed result and can be silenced with suppressMessages(); str() and dput() show what an object really is, which is often the bug, such as a Date that is a number with a class; and on.exit() reports how a function was left, including by an error. The following script uses all of them on the shelf’s loan with the impossible dates.

source("scenario.R")

# Print debugging that costs little to leave in: message() writes to standard
# error, so it does not mix with the function's own printed output, and it can
# be silenced with suppressMessages().
late_days <- function(loan_date, return_date, verbose = FALSE) {
  days <- as.integer(return_date - loan_date)
  if (verbose) {
    message(sprintf("late_days: %s -> %s = %d days", loan_date, return_date,
                    days))
  }
  max(days - loan_days, 0L) # nolint: object_usage_linter.
}
late_days(loans$loan_date[12], loans$return_date[12], verbose = TRUE)

Debugging in an IDE

RStudio and Positron do not have a debugger of their own; they are front ends to the tools above, and everything they do can be reproduced at a plain console. This section is documented, not run: it is based on the RStudio user guide (the version 2026.10.0 Debugging chapter) and on the Ark README for Positron, both read on 2026-10-20, and the screenshots are not reproduced. The wording of buttons and menus changes between releases, so check the documentation of the release you have.

RStudio

The user guide organises debugging around the ways to enter debug mode (RStudio user guide: Debugging).

  • An editor breakpoint is set by clicking to the left of a line number, or with Shift+F9 on the line. It takes effect immediately and does not change the code: it works by injecting tracing code into the function object, which is the setBreakpoint() mechanism described above, and a function that holds a breakpoint is marked with a red dot in the Environment pane. If the function object does not exist yet, or no longer matches the editor because the file changed since source() was last called, the breakpoint is deferred and shown as a hollow red circle; in most cases source() on the file resolves it.

  • A browser() call is the other kind of breakpoint. It is part of the code, so it takes effect only when the code is sourced, rebuilt or reloaded, but it works where editor breakpoints cannot, and with an if around it gives a conditional breakpoint, such as stopping at iteration 512 of a loop.

  • debugonce() and debug() flag a function, for code with no local source file, such as debugonce(devtools::install); the guide does not recommend leaving debug() set.

  • On error: the Debug menu has an On Error setting whose values include the Error Inspector and Break in Code. RStudio does not start the debugger if none of your own code is on the stack, so that errors deep inside other packages do not open it; a Global Options check box (the guide names "Use debug error handler only when my code contains errors") turns that filter off. As discussed above, the guide’s options(error = browser()) overrides the Debug menu setting. Older articles describe two buttons of the Error Inspector, Show Traceback and Rerun with Debug; the current user guide does not document them, so they are not described here.

When code is stopped, the console prompt becomes Browse[1]>, the Environment pane shows the environment of the running function instead of the global one, with arguments that have not been evaluated shown in gray as promises, and a drop-down list shows the chain of enclosing environments. The traceback shares the space of the Environment pane; the guide says it shows the call stack and is called the traceback for symmetry with traceback(), that clicking a frame shows its variables and code without changing the active environment of the console (use recover() for that), and that internal functions are hidden unless View Internals is ticked. The guide has a section on special circumstances, and they follow from how the mechanisms work. Breakpoints that are outside any function cannot be injected into a function object, so RStudio provides debugSource(), a source() that stops at those breakpoints; it is not recursive, so a file that is itself sourced by the debugged file is not stopped in. Compiled code

The R debugger sees interpreted code only. When the failing code is in C, C++ or Fortran, Writing R Extensions covers the tools in its chapter on debugging compiled code: a crash prints "caught segfault" and a traceback of the R calls active, a core dump can be examined with gdb, R can be run under the debugger with R -d gdb --vanilla, an interrupt (Ctrl-C) while a long computation runs drops into the debugger so that where shows where the time goes, and a debugger can be attached to a running process with gdb -p pid. Compiled code loaded dynamically can have breakpoints set in it only after it is loaded, so the procedure is to start R under the debugger, load the shared object with dyn.load() or library(), send an interrupt, set the breakpoints and continue. options(CBoundsCheck = TRUE) makes .C and .Fortran check whether compiled code writes beyond the arguments it is passed (Writing R Extensions: Debugging compiled code). R FAQ 8.2 gives the short version (R FAQ 8.2). Writing compiled extensions is covered in Interfacing C, C++ and Fortran.

A debugging workflow

  1. Read the message, and note the call and the text. If the call is NULL or unhelpful, the stack is what you need.

  2. Get the stack: traceback() at the prompt, options(error = function() { traceback(3); q(status = 0) }) in a script, or options(catch.script.errors = TRUE) to see several failures in one run.

  3. If the stack names the function but not the cause, stop the program there while it is running: options(error = recover) to look at the frames after the error, or debugonce() on the function and run again to step through it.

  4. If the bad value is produced in a loop or in many calls, use a conditional stop, browser(expr = ), or a trace() with an expression tracer that prints only the bad case.

  5. If the failure is a warning, set options(warn = 2) for the run and treat it as an error.

  6. If the code runs unattended, use dump.frames(to.file = TRUE) and q(status = 1) in the error option, and debug the dump later.

  7. Fix the cause, then add the check that would have caught it earlier, with stopifnot() or an error with a class, and remove every browser(), debug() and trace() before committing: undebug(), untrace() and options(error = NULL) are the clean-ups.
