Numbers and Arithmetic

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. Everything on this page is base R, so no add-on package version applies; the scripts also use the book class and the data of the running shelf scenario, which are plain base R code, and the lintr 3.4.0 default linters were used only to check the scripts. The CRAN package bit64 is mentioned in prose and was not installed, so nothing here was run with it.

Numbers are the part of R that looks the simplest and hides the most. A bare 1 is not an integer, 0.1 + 0.2 is not 0.3, -7 %/% 2 is -4, (-8)^(1/3) is NaN, and the same double prints as 1e+05 or 100000 depending on a global option. Each of these surprises has the same cause, which is that R keeps numbers in a handful of fixed-size binary formats and then shows you a decimal rendering of them. This page goes through those formats (the 32-bit integer, the 64-bit IEEE 754 double and the complex pair of doubles), what happens at their limits, how to compare and round numbers, how integer division and remainders work, what the bitwise functions and bitstring() show about the stored bits, and how format(), formatC(), prettyNum() and sprintf() turn numbers back into text.

Every example below is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines starting with #> are what it printed. The scripts pass the default lintr linters. Errors and warnings that a script shows on purpose are caught with tryCatch() and printed as their conditionMessage(), so the text is exactly what R says. The scripts that use the library scenario of the section (books, loans, shelf_today, loan_days) start with source("scenario.R"), the file described on the section index. The operators themselves are on Operators and Precedence, which also has a section on floating-point comparisons; this page goes into the numbers behind them and does not repeat that section line by line.

class() says "numeric" for a double and "integer" for an integer, whereas mode() says "numeric" for both; the numeric help page calls it a historical anomaly that floating-point vectors have two names, double and numeric, and typeof() is the name to use when the exact storage matters (R documentation: typeof). is.numeric() is TRUE for integers and doubles (and for factors it is FALSE), and the help page adds that is.complex() and is.numeric() are never both TRUE (R documentation: complex). Most of the time you do not need to care which of the two numeric types a number has: R converts as needed, and An Introduction to R says that for most purposes the user will not be concerned whether the numbers in a vector are integers, reals or complex, because calculations are done as double precision numbers, or double precision complex numbers if the input is complex (An Introduction to R: Vector arithmetic). The exceptions are the subject of the next sections.

Integer versus double

The R Language Definition makes the first point itself: the number returned for the expression 1 is a numeric (a double), and the simplest way to get an integer is the suffix L (The R Language Definition: Constants). The suffix can qualify any number that is an integer in value, so 0x10L is 16 and 1e3L is 1000L. The scripts below check the types of literals and the usual tests, then show which common functions return integers.

Writing integer literals

The same help page that defines integer vectors says why they exist: they let data be passed to C or Fortran code that expects them, and they represent (small) whole numbers exactly and compactly. They are limited to 32 bits, which is about plus or minus two billion, whereas doubles hold much larger whole numbers exactly (R documentation: integer). The literal rules are in the language definition: the suffix L qualifies a decimal, hexadecimal or scientific constant, 1e3L is 1000L (the L qualifies 1e3, not the 3), and a sign is not part of the constant but a unary operator applied to it (The R Language Definition: Literal constants). Hexadecimal constants without the L are doubles: 0xFF is the double 255.

# A bare number is a double; the L suffix makes an integer
typeof(1)
#> [1] "double"
typeof(1L)
#> [1] "integer"
typeof(1e3)
#> [1] "double"
typeof(1e3L)
#> [1] "integer"
typeof(0x10L)
#> [1] "integer"
class(1)
#> [1] "numeric"
class(1L)
#> [1] "integer"
mode(1L)
#> [1] "numeric"
storage.mode(1L)
#> [1] "integer"

Source: The R Language Definition: Constants

If the value after the suffix is not a whole number, or does not fit, R keeps the number and warns while parsing, so the result is a double. The three parse-time warnings below are the real texts; parse() is used to show them because a warning raised by the parser appears before the code runs.

# An integer literal that does not fit becomes a double, with a parse warning
tryCatch(parse(text = "2147483648L"), warning = \(w) conditionMessage(w))
#> [1] "non-integer value 2147483648L qualified with L; using numeric value"
typeof(suppressWarnings(eval(parse(text = "2147483648L"))))
#> [1] "double"
tryCatch(parse(text = "1.5L"), warning = \(w) conditionMessage(w))
#> [1] "integer literal 1.5L contains decimal; using numeric value"
tryCatch(parse(text = "1.L"), warning = \(w) conditionMessage(w))
#> [1] "integer literal 1.L contains unnecessary decimal point"

Source: R documentation: NumericConstants

The list of accepted numeric forms is on the NumericConstants help page, including the C99 hexadecimal floating-point form (0x1.1p1), which is valid R and gives a double (R documentation: NumericConstants).

The is.integer trap and integer-valued doubles

is.integer() tests the storage type, not the value. The help page warns in capital letters that is.integer(x) does not test whether x contains whole numbers, and gives a tolerance-based is.wholenumber() function in its examples (R documentation: integer). The comparison operators convert, so 5 == 5L is TRUE, but identical(5, 5L) is FALSE because the types differ; the same trap hits any identical() test between a value computed with doubles and one read as an integer. A factor and a Date are not numeric for is.numeric(), even though they are stored as an integer and a double.

source("scenario.R")

# is.integer() tests the type, not whether the value is whole
is.integer(5)
#> [1] FALSE
is.integer(5L)
#> [1] TRUE
is.numeric(5L)
#> [1] TRUE
is.double(5L)
#> [1] FALSE
is.numeric(factor(1:2))
#> [1] FALSE
is.numeric(shelf_today)
#> [1] FALSE
5 == 5L
#> [1] TRUE
identical(5, 5L)
#> [1] FALSE

Source: R documentation: integer

The consequence for code is that you should compare numbers with == or all.equal() and keep identical() for objects whose type you control. A function that must accept "whole numbers" should test the value, as is_whole_number() does in Equality of doubles, rather than the type.

Which functions return integers

Integers come from a small set of places: the L suffix, the colon operator, seq_len() and seq_along(), length(), nchar(), nrow() and ncol(), counting functions such as which() and table(), read.csv() and read.table() columns that contain only whole numbers (the year and pages columns of books), and as.integer(). Arithmetic on integers keeps the type for +, -, *, %% and %/%, and the result of / and ^ is always a double. A single double operand makes the whole result a double. seq(1, 3) is an integer vector because seq.default() without by returns from:to when from is a whole number, while seq(1, 3, by = 1) is a double (R documentation: seq). sum() of integers is an integer when it fits and mean() is always a double.

Integer overflow

Integers are 32-bit, so there is a largest one: .Machine$integer.max, which the .Machine help page says is always 2^31 - 1, that is 2147483647 (R documentation: .Machine). Arithmetic on integers that leaves the range returns NA_integer_ and signals the warning NAs produced by integer overflow. The smallest 32-bit pattern is reserved for NA_integer_, so the usable range is symmetric: minus 2147483647 to plus 2147483647, and -.Machine$integer.max - 1L already overflows. The same sums in doubles are exact, because a double has 53 bits of significand.

# The largest integer, and what happens beyond it
.Machine$integer.max
#> [1] 2147483647
2^31 - 1
#> [1] 2147483647
.Machine$integer.max == 2147483647L
#> [1] TRUE
typeof(.Machine$integer.max)
#> [1] "integer"

Source: R documentation: .Machine

# Integer arithmetic past the limit: NA with a warning
tryCatch(.Machine$integer.max + 1L, warning = \(w) conditionMessage(w))
#> [1] "NAs produced by integer overflow"
suppressWarnings(.Machine$integer.max + 1L)
#> [1] NA
tryCatch(-.Machine$integer.max - 1L, warning = \(w) conditionMessage(w))
#> [1] "NAs produced by integer overflow"
tryCatch(100000L * 100000L, warning = \(w) conditionMessage(w))
#> [1] "NAs produced by integer overflow"
.Machine$integer.max + 1
#> [1] 2147483648
100000 * 100000
#> [1] 1e+10
typeof(100000L * 100000)
#> [1] "double"

Source: R documentation: Arithmetic

The warning does not stop the program, so NA flows on through later arithmetic, exactly like any other missing value. A script that must not continue turns warnings into errors (options(warn = 2)) or, better, avoids the situation by choosing the type: use a double for counters, sums of many values, products, timestamps in seconds and identifiers that can pass two billion, and keep integers for indexes, counts and codes that stay small.

sum, cumsum and coercion

Not every integer function overflows. Since R 3.0.2 sum() of integers accumulates in an integer of at least 64 bits, and since R 3.5.0 it returns a double when the total does not fit in an integer instead of an NA with a warning (R NEWS: Changes in R 3.0.2 and 3.5.0). The older warning about integer overflow in sum() that many web pages mention therefore no longer appears. cumsum() has no such rescue: its help page says integer overflow gives NA with a warning, and the message is integer overflow in 'cumsum'; use 'cumsum(as.numeric(.))' (R documentation: cumsum). prod() always returns a double, and cumprod() returns a double for integer input. Coercing a too large double (or a string holding one) with as.integer() returns NA with a different warning, NAs introduced by coercion to integer range, and the same happens for -2147483648, whose pattern is NA_integer_.

# sum() accumulates in 64 bits and returns a double when the total does not fit
big <- c(.Machine$integer.max, 1L)
sum(big)
#> [1] 2147483648
typeof(sum(big))
#> [1] "double"
typeof(sum(1:10))
#> [1] "integer"
mean(big)
#> [1] 1073741824
# cumsum() has no such rescue: it still overflows with a warning
tryCatch(cumsum(big), warning = \(w) conditionMessage(w))
#> [1] "integer overflow in 'cumsum'; use 'cumsum(as.numeric(.))'"
cumsum(as.numeric(big))
#> [1] 2147483647 2147483648
# prod() always returns a double
typeof(prod(1:3))
#> [1] "double"

Source: R documentation: sum

# Coercing a large double to integer
tryCatch(as.integer(3e9), warning = \(w) conditionMessage(w))
#> [1] "NAs introduced by coercion to integer range"
tryCatch(as.integer("3000000000"), warning = \(w) conditionMessage(w))
#> [1] "NAs introduced by coercion to integer range"
as.integer(2147483647)

Beyond 32-bit integers and 53-bit significands

When 2147483647 is not enough there are three standard answers. The first is to use doubles, which hold every whole number exactly up to 2^53 (about 9.0e15), the point where the spacing between neighbouring doubles becomes 2. The second is the CRAN package bit64, which provides a 64-bit integer class (integer64) stored in a vector of doubles; it is community-maintained, was not installed for this page and nothing here was run with it. The third, for numbers of any size, are the arbitrary-precision packages on CRAN, which are outside this page. Beyond 2^53 whole numbers silently lose their last digits, and the integer-valued factorials show where that begins: the double factorial(22) is still exactly 1124000727777607680000 because the odd part of 22! IEEE 754 doubles

The arithmetic of the numeric type is the double precision arithmetic of the IEC 60559 standard, better known as IEEE 754. The Arithmetic help page says that all current R platforms use it, though some details the standard leaves optional, such as the support for denormal numbers, can differ between platforms and even between calculations on one platform (R documentation: Arithmetic). A double has 64 bits:

1

11

Two consequences follow, and the rest of this section illustrates them. A number is stored exactly only if it is a whole number below 2^53 or a fraction whose denominator is a power of two (1/2, 3/8, 5/1024); every other number, 0.1 included, is rounded to the nearest of the roughly 1.8e19 doubles, and the rounding error is part of the value from then on. And the doubles are not evenly spread: the gap between neighbours is relative to the magnitude, about 2.2e-16 near 1 and 2 near 2^53. The R FAQ says it the same way: the only numbers that can be represented exactly are integers and fractions with a denominator that is a power of 2, and all other numbers are rounded to typically 53 binary digits (R FAQ 7.31: Why doesn’t R think these numbers are equal?).

Equality of doubles

The R FAQ entry 7.31 is the canonical answer to the most asked question about R numbers: two floating-point numbers are not reliably equal unless they were computed by the same algorithm, and not always even then. The FAQ example is sqrt(2)^2, which differs from 2 by 4.440892e-16, and the entry points to all.equal() with its default tolerance of .Machine$double.eps ^ 0.5 (R FAQ 7.31: Why doesn’t R think these numbers are equal?). The section on floating-point comparisons of Operators and Precedence reproduces the FAQ examples and the seq() trap; this section adds the three tools you have for the question and their return values.

  • == compares two numbers exactly (the two zeroes are equal, and a comparison with NA or NaN gives NA).

  • identical(x, y) is TRUE only if the two objects are the same in every respect, including type and attributes, and returns a single TRUE or FALSE (R documentation: identical).

  • all.equal(target, current) tests near equality and returns TRUE or a character vector that describes the differences, so it cannot be used directly as a condition: the help page says to wrap it in isTRUE(), or to use identical() where that is appropriate (R documentation: all.equal).

#> [1] FALSE
identical(sqrt(2)^2, 2)
#> [1] FALSE
all.equal(sqrt(2)^2, 2)
#> [1] TRUE
isTRUE(all.equal(sqrt(2)^2, 2))
#> [1] TRUE

How the tolerance works

The default tolerance is sqrt(.Machine$double.eps), about 1.5e-8. For numeric input, all.equal() takes the mean absolute value of target as the scale; if that scale is finite and above the tolerance, differences are expressed relative to it, and otherwise they are absolute differences (R documentation: all.equal). So all.equal(100, 101) reports a relative difference of 0.01, while all.equal(0, 1e-5) reports an absolute difference of 1e-05 because the target is 0, and all.equal(0, 1e-10) is TRUE since the absolute difference is below the tolerance. A numeric scale forces absolute comparison after dividing by it, and tolerance = 0 makes the report show the difference that the default tolerance hides.

# The tolerance is relative (default: sqrt of the machine epsilon)

#> [1] TRUE

#> [1] TRUE
all.equal(0, 1e-10)
#> [1] TRUE
all.equal(0, 1e-5)

#> [1] TRUE
all.equal(1, 1.001, tolerance = 1e-4)
#> [1] "Mean relative difference: 0.001"

#> [1] "Mean relative difference: 2.220446e-16"

Truncation to integer

as.integer() truncates toward zero, as the integer help page says, so a double that should be whole but is a hair below loses a unit. 0.29 * 100 is 28.999999999999996, which prints as 29 and converts to 28. The remedy is to round before converting, as.integer(round(x)), or to avoid the multiplication by keeping amounts as integers (see The numbers of the shelf). as.integer(2.999999) is 2 because the value is below 3 however close, and as.integer(-2.9) is -2, the same as trunc() and not as floor().

The rules that keep a program safe can be stated briefly:

  • Never test the result of floating-point arithmetic with ==, identical(), %in% or match(); compare with a tolerance (abs(x - y) < tol for vectors, isTRUE(all.equal(x, y)) for one pair of objects).

  • Keep exact quantities (money, counts, identifiers) in integers, in the smallest unit.

  • Round before converting to integer or before building a key or a label from a double.

  • Do not use all.equal() bare in if; it returns a character vector when the objects differ, and if rejects it with argument is not interpretable as logical.

  • Use .Machine$double.eps as the unit of a relative error only near 1; for a number x the gap is about x * .Machine$double.eps.

Rounding to decimals

With digits greater than 0 there is a second effect on top of the tie rule: the argument is a binary double, so the "5" you typed may be stored slightly above or below the real tie. The help page says exactly this, that 0.15 is not represented exactly, the rule applies to the represented number and not to the printed number, and round(0.15, 1) could be either 0.1 or 0.2, depending on the OS services and on representation error. Division by zero

Dividing by zero is not an error in R. For doubles it follows IEEE 754: a nonzero number divided by zero is Inf or -Inf, and zero divided by zero is NaN. Complex numbers

A complex number in R is a pair of doubles, the real part and the imaginary part, either of which can be NaN, NA or infinite (R documentation: complex). R has no single literal for a number such as 3+4i: 4i is the imaginary constant, and 3 + 4i is the sum of a double and a complex, evaluated like any other expression (a suffix L after an imaginary constant, 12iL, is a syntax error, as the language definition says). The other question people ask, why (-8)^(1/3) is not -2, is answered by the Arithmetic help page and not by the FAQ. Formatting numbers

A number has two lives: the binary value in memory and the text that shows it. Four functions turn one into the other, with different jobs. print() and auto-printing show a value in the console. format() returns a character vector in a common format, so that a column lines up. formatC() formats each number on its own with a C-style specification. sprintf() builds a string from a format that mixes text and numbers, and prettyNum() adds marks to something that is already formatted. All of them can only show what the value contains, and none changes it: formatting is the last step, after the rounding.

Printing and the digits option

Console output uses options(digits), which controls the number of significant digits to print and is a suggestion only: valid values are 1 to 22 with default 7 (R documentation: options). print(x, digits = n) sets it for one call, and format() has the same digits argument defaulting to the option. The number of decimals is then chosen so that the smallest element has that many significant digits, which is why format(c(0.001, 0.1), digits = 1) gives "0.001" "0.100": one significant digit for the small number forces three decimals on both. The print.default page adds that for digits of 16 or more the number of significant digits depends on the C library’s sprintf(), so do not rely on the digits beyond 15 being the same across platforms (R documentation: print.default).

sprintf()

sprintf(fmt, ...) is the vectorised C sprintf, with %d for integers, %f, %e and %g for doubles, %s for strings and %% for a percent sign, flags such as -, +, 0 and a space, and a width and precision (%8.2f). Fixed or scientific: options(scipen)

When R prints a double it computes the width of the fixed and of the scientific representation and uses fixed notation unless it is wider than the scientific one by more than scipen characters. The default is 0: positive values bias toward fixed notation and negative values toward scientific notation. The help page says valid values are between -9 and 9999 with relevant values for double precision in -6 to 319, and that invalid values warn and are set to a boundary (R documentation: options). Since R 4.5.0 options(scipen = NULL) and other invalid values signal an error instead of invalidating the operations that rely on a finite integer (R NEWS: Changes in R 4.5.0); the chunk shows the real text. Converting text to numbers

as.numeric() (the same function as as.double()) and as.integer() accept strings with optional blanks around them, decimal and scientific notation ("1e-3" is 0.001), hexadecimal with a 0x prefix ("0x1A" is 26), and the special strings "Inf", "-inf" and "NaN". Anything else gives NA with the warning NAs introduced by coercion: a thousands separator, a decimal comma ("1,5"), a currency sign, and even the string "NA", while the missing value NA_character_ converts silently. as.integer() of a string with a fraction truncates (as.integer("12.7") is 12), and as.numeric("TRUE") is NA although as.numeric(TRUE) is 1 (R documentation: numeric). The warning is the only signal of a bad value, so a data-cleaning script should count the new NA values, or catch the warning, as the chunk does.

The classic trap is a factor: as.numeric() of a factor returns the integer codes of the levels, not the labels, which the help page flags in a warning. Convert through the labels, as.numeric(as.character(f)), or through levels(f)[f]; R FAQ 7.10 has the same advice (R FAQ 7.10: How do I convert factors to numeric?). See Factors.
