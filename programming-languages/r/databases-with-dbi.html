Databases with DBI

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. Every database example uses DBI 1.3.0 with RSQLite 3.53.3, which bundles SQLite 3.53.3 and needs no database server. The dbplyr sections also use dplyr 1.2.1 and dbplyr 2.6.0, and print the tibble 3.3.1 data frames they return; integers beyond 32 bits come back as bit64 4.8.6 objects; lintr 3.4.0 was used only to check the scripts. The other backend packages (RPostgres, RMariaDB, odbc, duckdb) and the packages RODBC, sqldf, keyring and config are not installed here, and askpass and glue are installed but not used: all of them are named in the text, described from their own documentation, and never run. Data usually lives in a database for a reason: it is bigger than memory, or other people and programs share it. R, on the other hand, keeps everything in memory. The DBI package is the answer to how the two talk to each other, and this page is about it: one set of functions (dbConnect(), dbGetQuery(), dbExecute(), dbWriteTable() and so on) that behaves the same whether the database behind it is SQLite, PostgreSQL, MariaDB, DuckDB or anything reachable through ODBC, and about the dbplyr package, which writes the SQL for you from dplyr code.

Every example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines that start with #> are what it printed. The scripts also pass the default lintr linters. The names books, loans, shelf_today, loan_days and the book() constructor come from the running library-shelf scenario described on the section index: a script that needs them starts with source("scenario.R"), and books and loans are the data frames that every example copies into a database. Each script opens its own connection and closes it before it ends. The databases are in memory, or in a file made with tempfile() that the script deletes, and no example prints the name of a temporary file. Where a message contains quotation marks, they are the typographic quotes R prints in a UTF-8 locale.

This page is about the R side of databases. Writing SQL (selecting, joining, grouping, defining tables, transactions) is the subject of the SQL Reference, and the queries below are only as long as the R function being shown needs; the SQL transactions page explains what the transaction functions in the section on transactions below do in the database. The data frames that go in and come out are explained in Data Frames, the dates in Dates and Times, the S4 system that DBI is built on in S4 Classes and Methods, the condition system used to catch errors in Conditions and Error Handling, and the dplyr verbs that dbplyr translates in The tidyverse and dplyr.

Why talk to a database from R

R Data Import/Export gives the reasons in the first section of its chapter on relational databases (R Data Import/Export: Why use a database?). Everything R manipulates is resident in memory, and several copies of the data can exist during a function call, so data objects of more than a few hundred megabytes can make R run out of memory. R does not easily support concurrent access: if several users read and update the same data, the changes of one are not visible to the others. R can store data between sessions, but in a format that is specific to R. A relational database management system is designed to do all of these things well: fast access to selected parts of large tables, summaries and cross-tabulations computed where the data is, a more organised way to store data than a rectangular grid, and concurrent access from many clients with security constraints. The manual’s examples of the statistical use of a database are to extract a 10% sample, to cross-tabulate into a multi-dimensional table, and to extract the data group by group for separate analysis.

The pattern that follows from this is to push the work that the database is good at (filtering, joining, aggregating) into the query, and to bring only the result into R. The rest of this page is the machinery for doing that safely. For data that fit in memory and live in files, the routes are in Reading and Writing Text Data and Serialization: RDS, RData and JSON; for data that arrive over the network, in HTTP and Web APIs.

The manual’s overview of relational databases also states two points that matter for every query below (R Data Import/Export: SQL queries). The more comprehensive R interfaces generate SQL behind the scenes for common operations, but direct use of SQL is needed for complex operations in all of them. And, unlike the rows of a data frame, the rows of a table are best thought of as unordered: without an ORDER BY, the order of the result is indeterminate. A script that depends on the order of rows must say so in the query.

DBI: one interface, many backends

DBI stands for DataBase Interface. Its home page says that the package separates the connection to the database management system into a front-end and a back-end: DBI defines the interface, and packages such as RPostgres, RMariaDB, RSQLite and odbc implement it for a particular system (DBI package documentation: DBI). The interface is similar in spirit to the database interfaces of Perl, Java, Python and Microsoft ODBC: connect and disconnect, create and execute statements, extract results, handle errors, ask for metadata, and manage transactions. The R Data Import/Export manual describes the same split as a proposal for a unified front-end package with a back-end per system (R Data Import/Export: R interface packages); that proposal is now the way R talks to databases.

In R terms DBI is a set of S4 generics and a handful of virtual S4 classes. A generic such as dbGetQuery() is defined once, in DBI. Each backend package defines classes that extend DBI’s (SQLiteConnection extends DBIConnection) and writes methods for them. When you call dbGetQuery(con, sql), S4 dispatch looks at the class of con, finds the method of the backend that created it, and runs that. The diagram shows the layers, with dbplyr above DBI.

The class names in the diagram are the ones the backends' own documentation uses (for example the DBI page of dbBind() lists the methods RSQLite::dbBind("SQLiteResult"), RPostgres::dbBind("PqResult"), RMariaDB::dbBind("MariaDBResult"), odbc::dbBind("OdbcResult") and duckdb::dbBind("duckdb_result") (DBI package documentation: dbBind)). Three kinds of object take part, and every DBI backend has all three:

  • a driver (DBIDriver), made by a constructor such as RSQLite::SQLite(), that knows how to open connections;

  • a connection (DBIConnection), returned by dbConnect(), that you pass to nearly every other function and must close;

  • a result (DBIResult), returned by dbSendQuery() and dbSendStatement(), that stands for one query in progress, from which rows are fetched, and that must be cleared.

The DBI home page names RPostgres, RMariaDB, RSQLite and odbc among the backends and says that odbc is for databases that you can access via ODBC. The specification that every backend implements is the DBI specification (DBI package documentation: DBI specification); that is why the code in the rest of this page, written against SQLite, changes only in the line that creates the connection when the database changes. What does not carry over is the SQL itself, which has dialects, and a few details that the specification leaves to the backend; those are called out where they appear (the format of the parameter placeholders, the column types, the date support).

The first script asks R itself how the layers are arranged. is() lists the classes of an object from the most specific to the most general; showMethods() lists the S4 methods that exist for a generic.

# RSQLite's classes extend the base classes that DBI defines.
is(drv)

#> [1] TRUE
isVirtualClass("DBIConnection")
#> [1] TRUE

The driver and the connection each have the backend class first and the DBI class after it, and both end in DBIObject, the root of the hierarchy. dbListTables() has a method written for the backend’s own class, SQLiteConnection. dbGetQuery() is the other case: the method that showMethods() lists is the one defined for any DBIConnection, which a SQLiteConnection inherits, because the definition is the same for every backend. The DBI article on advanced usage describes what it does: dbGetQuery() works by calling dbSendQuery(), dbFetch() and dbClearResult() behind the scenes (DBI package documentation: Advanced DBI usage). Those three are what you call yourself when you want to read a result in pieces, as in the section on chunked reads below. In DBI 1.3.0 many of these generics are of the kind "nonstandardGeneric", a change its NEWS lists among the breaking changes because a package that tests the generic’s definition could notice; ordinary users do not.

Connecting and disconnecting

A database in memory

dbConnect() is the first call of every session. Its first argument is the driver object; the remaining arguments are the backend’s. For SQLite the one that matters is dbname, the file that holds the database, or the special name ":memory:" for a database that lives in RAM and disappears when the connection is closed (RSQLite package documentation: SQLite). That makes it the right database for experiments, tests and the examples on this page.

library(DBI)

con <- dbConnect(RSQLite::SQLite(), ":memory:")
con
#> <SQLiteConnection>
#>   Path: :memory:
#>   Extensions: TRUE
dbIsValid(con)
#> [1] TRUE
dbListTables(con)
#> character(0)

dbDisconnect(con)
dbIsValid(con)
#> [1] FALSE
con
#> <SQLiteConnection>
#>   DISCONNECTED

# A closed connection cannot be used again.
tryCatch(dbListTables(con), error = \(e) conditionMessage(e))
#> [1] "Invalid or closed connection"

# Close the connection even when the code in between fails.
with_shelf_db <- function(dbname, fun) {
  con <- dbConnect(RSQLite::SQLite(), dbname)
  on.exit(dbDisconnect(con), add = TRUE)
  fun(con)
}

kept <- NULL
result <- tryCatch(
  with_shelf_db(":memory:", \(con) {
    kept <<- con
    stop("something went wrong")
  }),
  error = \(e) conditionMessage(e)
)
result
#> [1] "something went wrong"
dbIsValid(kept)
#> [1] FALSE

# A connection cannot be saved: after a round trip through a file it is dead.
con <- dbConnect(RSQLite::SQLite(), ":memory:")
path <- tempfile(fileext = ".rds")
saveRDS(con, path)
restored <- readRDS(path)
dbIsValid(restored)
#> [1] FALSE
tryCatch(dbListTables(restored), error = \(e) conditionMessage(e))
#> [1] "bad_weak_ptr"
dbDisconnect(con)
unlink(path)

Source: DBI package documentation: dbConnect

The print method of a connection says what it is connected to: <SQLiteConnection>, the Path, and whether loadable Extensions are enabled (they are by default). It never prints a memory address, so a connection can be shown in a log. After dbDisconnect(), dbIsValid() is FALSE, the object prints as DISCONNECTED, and any function that needs the connection fails with Invalid or closed connection. Calling the functions on a closed connection is a programming error and not a recoverable condition, which is why the function with_shelf_db() at the end of the script opens the connection, registers the closing with on.exit() and only then runs the code it was given. The code fails with an error, the connection is closed anyway, and dbIsValid(kept) confirms it. The last block of the script shows that a connection is not a value that can be stored: after saveRDS() and readRDS() the restored object is not valid (dbIsValid() is FALSE) and using it fails with the unhelpful bad_weak_ptr, because the connection lives in memory that belongs to the session. Open a new connection in each session. add = TRUE keeps any other on.exit() handler of the function (R documentation: on.exit).

Closing is not optional. RSQLite’s documentation notes that connections are cleaned up automatically after they are deleted and the garbage collector reclaims them, but that dbDisconnect() terminates a connection early, and that it will not actually close until all open result sets have been closed (a warning says so; see the section on chunked reads). The RPostgres documentation puts it the same way: manually disconnecting is not necessary, but still recommended, and deleting the object that holds a connection disconnects it at the next garbage collection with a warning (RPostgres package documentation: Postgres). For a server database each forgotten connection is also a session the server keeps open until it times out.

Disconnecting is documented on its own page (DBI package documentation: dbDisconnect).

A database in a file

A file name as dbname makes a database that survives the session, can be opened by another R session or program, and is created if it does not exist. The next script uses a file from tempfile(), writes the books table to it, closes the connection, opens the file again, and removes it at the end. It also shows the read-only flag, and dbCanConnect(), which answers TRUE or FALSE instead of signalling an error.

source("scenario.R")
library(DBI)

path <- tempfile(fileext = ".sqlite")
file.exists(path)
#> [1] FALSE

con <- dbConnect(RSQLite::SQLite(), path)
dbWriteTable(con, "books", books, row.names = FALSE)
dbDisconnect(con)
file.exists(path)
#> [1] TRUE

# A second connection, even from another R session, sees the same data.
con <- dbConnect(RSQLite::SQLite(), path)
dbListTables(con)
#> [1] "books"
dbGetQuery(con, "SELECT COUNT(*) AS n FROM books")
#>    n
#> 1 16
dbDisconnect(con)

# SQLITE_RO opens the file read-only.
ro <- dbConnect(RSQLite::SQLite(), path, flags = RSQLite::SQLITE_RO)
tryCatch(
  dbExecute(ro, "DELETE FROM books"),
  error = \(e) conditionMessage(e)
)
#> [1] "attempt to write a readonly database"
dbDisconnect(ro)

# dbCanConnect() answers TRUE or FALSE instead of failing.
isTRUE(dbCanConnect(RSQLite::SQLite(), path))
#> [1] TRUE
missing_path <- tempfile(fileext = ".sqlite")
isTRUE(dbCanConnect(
  RSQLite::SQLite(), missing_path,
  flags = RSQLite::SQLITE_RO
))
#> [1] FALSE

unlink(path)
file.exists(path)
#> [1] FALSE

Source: RSQLite package documentation: SQLite

The arguments of dbConnect() for an SQLite driver, as documented in version 3.53.3, are these.

Argument Meaning

dbname

The database file. ":memory:" or "file::memory:" makes a temporary in-memory database; "" makes a temporary on-disk database whose file is deleted when the connection is closed.

flags

SQLITE_RWC (the default) opens read/write and creates the file if it does not exist; SQLITE_RW opens read/write and fails if the file does not exist; SQLITE_RO opens read-only.

extended_types

FALSE by default. When TRUE, columns declared DATE, TIME or DATETIME/TIMESTAMP are returned as Date, hms and POSIXct (see the section on types).

bigint

The R type for 64-bit integers: "integer64" (the default), "integer", "numeric" or "character".

loadable.extensions, default.extensions

Whether SQLite loadable extensions are enabled (TRUE by default) and whether initExtension() is called on the new connection.

synchronous

"off" (the default), "normal" or "full". The documentation calls it an advanced option: "off" is faster, at the very modest risk of database corruption if the operating system itself crashes.

cache_size, vfs

Advanced options: the number of pages SQLite keeps in memory, and the SQLite operating-system interface.

Source: RSQLite package documentation: SQLite

The read-only connection in the script gets the error text of SQLite itself, attempt to write a readonly database. dbCanConnect() is the DBI generic added in DBI 1.0.0 for checking, before a long job, that the settings work. Because a file database is shared, a second connection (or a second R process) can read it while the first one is open; what happens when two of them write at once is up to SQLite’s locking, which RSQLite documents under its own functions (its NEWS for 2.2.4 introduces sqliteSetBusyHandler() to configure what SQLite does when the database is locked), and one reason to prefer a server database when many users write.

Other databases

A server database needs more than a file name: where it is, which database on it, and who you are. The argument names differ by backend, as the references of RPostgres (dbname, host, port, user, password), RMariaDB (dbname, host, username, password), odbc (dsn, or driver, server, database, uid, pwd) and duckdb (dbdir, read_only) show. The fragment below is the shape of those calls, with every setting read from the environment (the next section explains why). It is a fragment that was only linted: the four packages are not installed here and no database server is available, so it was never run.

# Fragment, never run: RPostgres, RMariaDB, odbc and duckdb are not installed
# here, and no database server is available. The settings come from the
# environment, not from the code.
library(DBI)

connect_shelf_postgres <- function() {
  dbConnect(
    RPostgres::Postgres(),
    dbname = Sys.getenv("SHELF_DB_NAME"),
    host = Sys.getenv("SHELF_DB_HOST"),
    user = Sys.getenv("SHELF_DB_USER"),
    password = Sys.getenv("SHELF_DB_PASSWORD")
  )
}

connect_shelf_mariadb <- function() {
  dbConnect(
    RMariaDB::MariaDB(),
    dbname = Sys.getenv("SHELF_DB_NAME"),
    host = Sys.getenv("SHELF_DB_HOST"),
    username = Sys.getenv("SHELF_DB_USER"),
    password = Sys.getenv("SHELF_DB_PASSWORD")
  )
}

connect_shelf_odbc <- function() {
  dbConnect(
    odbc::odbc(),
    dsn = Sys.getenv("SHELF_DB_DSN"),
    uid = Sys.getenv("SHELF_DB_USER"),
    pwd = Sys.getenv("SHELF_DB_PASSWORD")
  )
}

connect_shelf_duckdb <- function() {
  dbConnect(duckdb::duckdb())
}

# The rest of the code does not change with the backend.
count_loans <- function(connect) {
  con <- connect()
  on.exit(dbDisconnect(con), add = TRUE)
  dbGetQuery(con, "SELECT COUNT(*) AS n FROM loans")$n
}

Source: RPostgres package documentation: Postgres

The last function, count_loans(), is the point of the fragment: it takes the function that makes the connection and does not care which database it reaches. The other documentation pages for the arguments used above are RMariaDB package documentation: dbConnect, odbc package documentation: dbConnect and duckdb package documentation: duckdb. DuckDB, like SQLite, is embedded in the R package; its dbdir argument defaults to a database kept in RAM.

Credentials stay out of the code

A password written in a script ends up in version control, in a shared project folder, in a screenshot of the editor and in the history of every machine the script was copied to. The DBI introduction makes the same point about its own example, which has a password in the code: that should be avoided for databases with secured access, and one way is to keep the credential in the system’s credential store and query it with the keyring package (DBI package documentation: Introduction to DBI). The rules for this page and for any script that connects to a real server are:

  • Read every connection setting that differs between machines (host, database name, user, password) with Sys.getenv(), never from a literal in the script. The values live in environment variables, set by the environment that runs the script (a shell profile, a deployment secret store, a CI secret) or by a .Renviron file.

  • A .Renviron file holds NAME=value lines that R turns into environment variables when it starts. R looks for it in the current directory first and then in the user’s home directory, unless the variable R_ENVIRON_USER names another file (R documentation: Startup). A project-level .Renviron holds the names of the settings, and the file must be excluded from version control (listed in .gitignore). readRenviron() loads a file into a running session. How R reads startup files is the subject of Sessions, Workspaces and Startup.

  • Some backends read the usual environment variables of their database themselves. RPostgres documents that host and port default to the PGHOST and PGPORT variables, and user and password to PGUSER and PGPASSWORD or to the matching line of the ~/.pgpass file. RMariaDB can read authentication parameters from a section of a MariaDB option file (default.file and group), and odbc can take the connection from a data source name (dsn) configured outside R and listed by odbcListDataSources(). In each case the secret is kept outside the R code.

  • For interactive use, ask for the secret when it is needed instead of storing it: the askpass package prompts for a password, and keyring reads and writes the operating system’s credential store (macOS Keychain, the Windows Credential Store, the Linux Secret Service). The config package returns the values for the current environment (development, test, production), which is useful as long as the secrets in the configuration are placeholders for environment variables. These three packages are named here from their CRAN descriptions and are not run.

  • Make the script fail early and clearly when a setting is missing, and never print the value.

Tables: writing, listing, reading and removing

The functions that treat a whole table as a data frame are the shortest way in and out of a database, and the manual presents them as convenient interfaces to read, write, test and delete tables: dbWriteTable() copies a data frame into a table, dbReadTable() copies a table into a data frame, and dbListTables(), dbListFields(), dbExistsTable() and dbRemoveTable() look after the rest (R Data Import/Export: Packages using DBI). Creating a table first

dbWriteTable() guesses the column types and writes the data in one call. Column types: from R classes to SQLite and back

Four consequences follow.

  • A logical column comes back as 0, 1 and NA; convert with as.logical(). A factor comes back as text; rebuild the factor on the R side with factor(x, levels = ...) if the level order matters (see Factors).

  • A Date is stored as a number, and converting it back is up to you: as.Date(x) on the numbers works in R 4.3.0 and later, which accepts a numeric argument without origin (R NEWS: Changes in R 4.3.0); before it, as.Date(x, origin = "1970-01-01") was required. If a stored value cannot be mapped, an NA is returned with a warning. The RSQLite reference table says how the value is read: a numeric value is a count of days (for DATE) or seconds (for the other two) since 1970-01-01, and a text value must be in ISO format (2020-01-23, 12:34:56, or both separated by a space).

dbExecute(): statements that change data

UPDATE, DELETE, INSERT and the statements that define tables return no rows. dbExecute() sends one and returns the number of rows it affected, which is the thing to check: 0 rows deleted is the usual sign of a WHERE that matches nothing. dbExecute() and dbSendStatement() are the DBI 0.5 names for work that older code did with dbGetQuery() and dbSendQuery(); RSQLite’s NEWS says new code should use them where appropriate. In the output above, UPDATE reported 16 rows, DELETE 1 row (the book without a year) and CREATE INDEX 0. Sending a SELECT through dbExecute() is not an error; it returns 0.

SQLite runs one statement per call. If the string holds two, RSQLite runs the first and warns Ignoring remaining part of query: SELECT 2 AS a. That is a property of this backend and a useful accident against stacked-statement tricks, but not a defence (see the section on parameters, and the contrast in the older tutorials section); other backends may run all the statements. The function is documented in DBI package documentation: dbExecute.

Reading a result in chunks

When a result is too big to read at once, or when only the first rows are needed, take the three steps that dbGetQuery() performs by itself, and keep control of the middle one: dbSendQuery() sends the query and returns a result object, dbFetch(res, n =) fetches up to n rows from it (all the remaining ones if n is omitted or -1), and dbClearResult() releases it. dbHasCompleted() says whether all the rows have been fetched, dbGetRowCount() how many were fetched so far, and dbColumnInfo() what the columns are. The DBI article on advanced usage gives the loop on this pattern: fetch chunk by chunk while dbHasCompleted() is false.

source("scenario.R")
library(DBI)

con <- dbConnect(RSQLite::SQLite(), ":memory:")
dbWriteTable(con, "loans", loans, row.names = FALSE)

# dbSendQuery() starts the query; dbFetch(n =) pulls rows a chunk at a time.
res <- dbSendQuery(con, "SELECT loan_id, member FROM loans ORDER BY loan_id")
dbHasCompleted(res)
#> [1] FALSE
dbColumnInfo(res)
#>      name      type
#> 1 loan_id character
#> 2  member character

sizes <- integer()
while (!dbHasCompleted(res)) {
  chunk <- dbFetch(res, n = 25)
  sizes <- c(sizes, nrow(chunk))
}
sizes
#> [1] 25 25 10
dbGetRowCount(res)
#> [1] 60
dbClearResult(res)
dbIsValid(res)
#> [1] FALSE

# Put the cleanup in on.exit() so an error in the loop still releases it.
count_in_chunks <- function(con, sql, chunk_size) {
  res <- dbSendQuery(con, sql)
  on.exit(dbClearResult(res), add = TRUE)
  total <- 0L
  while (!dbHasCompleted(res)) {
    total <- total + nrow(dbFetch(res, n = chunk_size))
  }
  total
}
count_in_chunks(con, "SELECT * FROM loans", 25L)
#> [1] 60

# A result that is never cleared makes dbDisconnect() complain.
res <- dbSendQuery(con, "SELECT * FROM loans")
tryCatch(dbDisconnect(con), warning = \(w) conditionMessage(w))
#> [1] "There are 1 result in use. The connection will be released when they are closed"
dbClearResult(res)
dbDisconnect(con)
dbIsValid(con)
#> [1] FALSE

Source: DBI package documentation: dbFetch

The 60 loans came out as chunks of 25, 25 and 10 rows, and the loop stopped without a fourth, empty fetch because dbHasCompleted() turned TRUE when the last row was read. dbSendQuery() is documented for queries that return rows: its page describes the data retrieval flow, and dbSendStatement() has the matching flow for statements that change data (DBI package documentation: dbSendQuery, DBI package documentation: dbHasCompleted, DBI package documentation: dbClearResult). A result that is never cleared holds the connection open: dbDisconnect() warns with There are 1 result in use. The connection will be released when they are closed, and clearing it is what lets the connection go. Put dbClearResult() in on.exit(), as count_in_chunks() does, so that an error halfway through the loop cannot leave it behind. Chunking limits what R holds in memory at once; the database still evaluates the query.

Parameterised queries

A query that contains a value taken from a variable has two ways to get it in. One is to build the SQL text with the value inside; the other is to leave a placeholder in the SQL and to send the value separately. The second is the rule, because it makes SQL injection impossible by construction. In the DBI documentation’s words, parameterised (or prepared) queries and statements serve two purposes besides safety: the same query can be run more than once with different values, and the database may cache intermediate information such as the execution plan (DBI package documentation: dbBind). The DBI article on advanced usage names two ways to avoid injection from user-supplied parameters, quoting and parameterised queries, and then shows parameterised queries as the way to push the substitution to the DBMS (DBI package documentation: Advanced DBI usage).

The attack, in one paragraph: a function that pastes genre into "... WHERE genre = '" ... "'" is correct for the values its author thought of, and a value that contains a quotation mark ends the string literal early and the rest of the value is read as SQL. The value comes from a form field, a file or a web request, so the person who types it decides part of the query. A parameter is sent to the database as data, after the SQL text has been parsed, so it can never become SQL. The demonstration with the real output is in the section on older tutorials, where the pattern belongs.

Bulk inserts and dbBind()

dbExecute() accepts params too, and the vectors make a bulk insert: one INSERT statement, many rows, one call, safe by the same rule. RSQLite’s NEWS describes executing the same prepared query or statement efficiently many times by passing a data-frame-like object. Transactions

A transaction groups statements so that they all take effect or none does. Without one, a failure halfway through a series of INSERT statements leaves the database with half of them. DBI offers dbWithTransaction() for the common case, and dbBegin(), dbCommit() and dbRollback() for control by hand (DBI package documentation: dbWithTransaction, DBI package documentation: transactions). The database does the work; what a transaction guarantees is explained in the SQL transactions page.

library(DBI)

con <- dbConnect(RSQLite::SQLite(), ":memory:")
dbExecute(con, "CREATE TABLE members (name TEXT NOT NULL UNIQUE)")
#> [1] 0

count_members <- function() {
  dbGetQuery(con, "SELECT COUNT(*) AS n FROM members")$n
}

# dbWithTransaction() commits when the code finishes, and returns its value.
dbWithTransaction(con, {
  dbExecute(con, "INSERT INTO members (name) VALUES ('Ana Ruiz')")
  dbExecute(con, "INSERT INTO members (name) VALUES ('Ben Okafor')")
  "committed"
})
#> [1] "committed"
count_members()
#> [1] 2

# An error rolls the whole block back and is passed on.
tryCatch(
  dbWithTransaction(con, {
    dbExecute(con, "INSERT INTO members (name) VALUES ('Dev Patel')")
    dbExecute(con, "INSERT INTO members (name) VALUES ('Ana Ruiz')")
  }),
  error = \(e) conditionMessage(e)
)
#> [1] "UNIQUE constraint failed: members.name"
count_members()
#> [1] 2

# dbBreak() leaves the block and rolls back without an error.
dbWithTransaction(con, {
  dbExecute(con, "INSERT INTO members (name) VALUES ('Eva Lindqvist')")
  dbBreak()
})
count_members()
#> [1] 2

# The same steps by hand: dbBegin(), then dbCommit() or dbRollback().
dbBegin(con)
dbExecute(con, "DELETE FROM members") # two rows deleted ...
#> [1] 2
count_members() # ... and gone, inside the transaction
#> [1] 0
dbRollback(con)
count_members()
#> [1] 2

# Transactions do not nest, and there is nothing to commit outside one.
tryCatch(
  dbWithTransaction(con, dbWithTransaction(con, 1)),
  error = \(e) conditionMessage(e)
)
#> [1] "cannot start a transaction within a transaction"
tryCatch(dbCommit(con), error = \(e) conditionMessage(e))
#> [1] "cannot commit - no transaction is active"

  • dbWithTransaction(con, code) starts a transaction, evaluates code, commits if it finishes, and returns the value of the code ("committed"). If code signals an error, it rolls back and re-throws it, so the failed insert of a duplicate name left the table unchanged (two members) and the error message was still delivered to tryCatch(). DBI 1.3.0 (2026-02-11) made it roll back also when the code is interrupted.

  • dbBreak() inside the block stops it and rolls back without an error; dbWithTransaction() then returns NULL invisibly, which is why the call printed nothing.

  • By hand, dbBegin(), the statements, and then dbCommit() to keep them or dbRollback() to discard them. The DELETE inside the transaction is visible to the connection that made it (the count was 0) and gone after the rollback (2 again). Other connections do not see the deletion until it is committed.

  • Transactions do not nest in SQLite, and the messages from the database say so: cannot start a transaction within a transaction, and cannot commit - no transaction is active when there is nothing to commit. A function that opens a transaction cannot call another that opens one; decide which of the two owns it.

  • Outside a transaction a database normally commits each statement by itself (autocommit), so statements issued without dbBegin() take effect one by one.

A rollback restores the database; it does not undo what the R code did meanwhile. A script that wrote a file or sent a message in the middle of the transaction cannot take that back.

  • collect() runs it. The result is an ordinary tibble in R, with the class tbl_df, tbl, data.frame; everything after collect() is local R (dbplyr package documentation: collect). Do the filtering, joining and aggregating before collect(), and the summarising or plotting after it. A lazy table is not a data frame: loans_db$member is an error (The $ method of <tbl_lazy> is for internal use only) that points to dplyr::pull(), which runs the query and returns one column as a vector.

  • Functions are translated, or passed through. dbplyr translates a fixed set of R functions into the SQL of the connection (for SQLite, n(), is.na(), the arithmetic and comparison operators and many more). A function it does not know is sent unchanged, which is why julianday(), an SQLite function, works in mutate(). The same rule makes grepl() fail, because SQLite has no such function: the error arrives when the query runs, wrapped by dbplyr’s Failed to collect lazy table. and ending with the database’s own words. Which R functions are translated is in the translation articles (dbplyr package documentation: Function translation). A variable from R, like loan_days in the script, is evaluated in R and its value is put in the SQL: held > 21.

  • SQL aggregates drop NULL. SQL’s AVG skips missing values whatever you ask. dbplyr says so once, as a warning (Missing values are always removed in SQL aggregation functions.), and stops when you pass na.rm = TRUE. The warning is shown once every eight hours, which is why it was captured in the script instead of being left to appear.

The last line of the script is the bridge between the two worlds: tbl(con, sql("SELECT ...")) takes any SQL as the source of a lazy table, and the verbs that follow are added on top of it. Use it for a query that is easier to write in SQL than in dplyr, or one that dbplyr cannot express (dbplyr package documentation: sql). The reverse is also true. show_query(), or in dbplyr 2.6.0 last_sql() (which returns the most recent query dbplyr generated), gives the SQL of a pipeline to read or to paste into a SQL client.

The overdue analysis, twice

The shelf scenario’s central question is which loans were overdue: a returned loan is overdue when it was held for more than loan_days (21) days. The scenario’s reference result is that 25 of the returned loans exceed 21 days. The next script puts books and loans in a database with date columns, answers the question by genre in SQL, answers it again with dbplyr verbs, checks that the two are the same, and checks both against base R on the data frames that never left R.

Two details of the data matter. The isbn of loans is 13 bare digits, and the isbn of books is sometimes hyphenated, so the join compares REPLACE(b.isbn, '-', '') with l.isbn. And the genres of books have nine spellings of six genres, so the grouping key is LOWER(TRIM(genre)). Both cleanings are done in the query, the way the data frame code of Data Frames does them in R. The tables are created with DATE columns and the dates are appended as ISO text, so SQLite’s julianday() can compute with them and, with extended_types = TRUE, R still receives Date columns.

The three results agree. The query keeps the loan period out of the SQL text (> ? with params = list(loan_days)), so the number lives in one place, in the scenario, in R. Of 53 returned loans, 25 are overdue: 8 fiction, 5 science fiction, and 3 each for classic, non-fiction and poetry, 2 for mystery, and 1 with an unknown genre. That last row is the lesson in the join. The loan L005 has a one-digit-short ISBN (978030640615), so no book matches it. An inner JOIN would have dropped the loan, and the total would have been 24 and not 25, with no error to say why. The LEFT JOIN keeps it and gives it the genre unknown, which makes the data problem visible. The last query of the script finds exactly that loan. The scenario’s other deliberate defects behave as they do in R: the loan with the impossible date 2025-02-30 has NULL dates, julianday() of NULL is NULL, the comparison is NULL, and SUM ignores it, so it counts as returned and not overdue; the loan returned before it was borrowed has a negative duration and is not overdue; the 7 unreturned loans are excluded by the WHERE (the question here is about returned loans; for the unreturned, shelf_today takes the place of the return date).

The dbplyr version builds the cleaning step as a lazy table (books_key), joins the loans to it, and ends in the same GROUP BY. sql("REPLACE(isbn, '-', '')") is a SQL fragment that dbplyr does not translate, and everything else is verbs. show_query() on overdue_db would show the nested query it generated.

Other backends in short

  • PostgreSQL (RPostgres): a server database that several people and programs share. The settings come from the environment (PGHOST and the others, or ~/.pgpass), parameters can be written $1, $2, and dbConnect() has timezone and timezone_out arguments for time zones (RPostgres package documentation: Postgres).

  • MariaDB and MySQL (RMariaDB): dbConnect() takes dbname, username, password and host, and can read a MariaDB option file. Its CRAN description says it implements a DBI-compliant interface to MariaDB and MySQL, and the legacy RMySQL package points to it for a modern MySQL client (RMariaDB package documentation: dbConnect).

  • ODBC (odbc): one package for every database with an ODBC driver, from a data source name or a driver and its settings. It is a DBI backend, so everything on this page applies (odbc package documentation: dbConnect).

  • DuckDB (duckdb): an embedded analytical database management system; like SQLite it needs no server. dbConnect(duckdb::duckdb()) keeps the data in RAM, and dbdir names a file (duckdb package documentation: duckdb).

  • Others, such as bigrquery, are listed on the DBI site.

Two newer parts of DBI are named here and not used, because they need packages that are not installed. DBI 1.2.0 (2023-12-20) added a family of Arrow generics (dbGetQueryArrow(), dbSendQueryArrow(), dbFetchArrow(), dbReadTableArrow(), dbWriteTableArrow() and others) with default implementations built on nanoarrow, and the DBI documentation labels these functions experimental (DBI package documentation: dbGetQueryArrow). DBI 1.3.0 added support for OpenTelemetry through the otel and otelsdk packages. For an Arrow-based workflow, the packages that talk Arrow directly are described at https://arrow.apache.org/docs/r/ (the arrow package is not installed here and is not run).

Pitfalls

The R FAQ has no entry about databases (a search of the FAQ finds none), so these come from the DBI and RSQLite documentation and from the examples above.

  • Building SQL by pasting values. Use params =, dbQuoteIdentifier() for names and sqlInterpolate() where text is unavoidable. See the section on older tutorials for the output of a pasted query.

  • Forgetting to disconnect, or to clear a result. Close in on.exit(); clear in on.exit(). Both produce a warning in RSQLite and a held server session elsewhere.

  • A vector in params is a loop, not a list of values. Use one placeholder per value for IN.

  • Assuming the types survive. Logical columns return as integers, factors as text and dates as numbers unless extended_types = TRUE and the column is declared DATE.

  • Assuming the order. A table has no order; add ORDER BY when the order matters, including for LIMIT and n =.

  • overwrite = TRUE on the wrong table. It replaces whatever is there.

  • Comparing text with the wrong case or blanks. 'Fiction', 'fiction' and 'Fiction ' are three different values to SQL. Clean at the source or in the query (LOWER(TRIM(x))).

  • Pulling everything and then filtering in R. dbReadTable() followed by a filter reads the whole table. Filter in the query.

  • NA and NULL in comparisons. x = NULL is never true in SQL; use IS NULL. In dbplyr, is.na() becomes IS NULL.

  • Secrets in the script. Environment variables, .Renviron, askpass or keyring; never a literal.

  • Saving a connection. A connection that went through saveRDS() and readRDS() is not valid (dbIsValid() is FALSE, and using it fails with the unhelpful bad_weak_ptr); open a new one in each session (see Serialization: RDS, RData and JSON).

  • Sharing one connection between processes. A worker of a parallel computation should open its own connection (see Parallel and Asynchronous Computing).

The first function builds the SQL by pasting genre between quotation marks, which is what the manual’s paste("select row_names, Murder from arrests", "where Rape > 30 ...") pattern becomes when one value is variable. It works for "Poetry". A value with an apostrophe breaks it (near "Brien": syntax error), which is the harmless way this fails. A value that closes the string and continues the logic (x' OR '1'='1) makes the WHERE true for every row: all 16 books came back for a genre that does not exist. That is SQL injection: the person who supplies the value rewrote the query. RSQLite stopped the third attempt, the stacked DROP TABLE, only because it runs a single statement per call and warned about the rest (Ignoring remaining part of query: ...); that is not protection, and a backend that executes every statement in the string would not have stopped it. The rewritten function with params = list(genre) returns the two poetry books for "Poetry" and nothing for the other two values, because they are only text to compare with. sprintf() has the same problem as paste() when the format has a %s; sprintf("... %d", n) with a number is safe only because %d will not accept text.
