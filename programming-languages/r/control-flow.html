Control Flow

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. This page explains how R chooses between alternatives and how it repeats work: if and else (which are expressions that return a value), the vectorised ifelse(), switch(), and the loops for, while and repeat with break and next. It also covers the habits that go with them: seq_along() and seq_len() instead of 1:length(x), and preallocating the result of a loop. Every example uses only base R, so no add-on package version needs to be stated; dplyr 1.2.1 is named in prose only, where its if_else() and case_when() are the usual tidyverse alternatives to ifelse().

Every example below is a complete script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines starting with #> are what it printed. The scripts also pass the default lintr linters; where an idiom being shown is exactly what a default linter dislikes (1:length(x), NA_character_ == "a"), the line carries a # nolint: comment so that the linter does not hide the lesson. Errors and warnings that the page wants to show are caught with tryCatch() and printed with conditionMessage(), which gives the message without the leading Error in if (...) : that the console adds, and so that the script still ends normally. The names books, loans, shelf_today, loan_days and the function is_valid_isbn13() come from the scenario.R file of the running library-shelf scenario described on the section index; the scripts that use them start with source("scenario.R"), which reads books.csv and loans.csv with read.csv(). The first page, Getting Started, shows how to install R and run a script.

Control flow is made of expressions

R is an expression language. The introduction manual says that its only command type is a function or expression that returns a result, that even an assignment is an expression, and that commands grouped in braces { ... } form a group whose value is the result of the last expression evaluated in it (An Introduction to R: Grouping, loops and conditional execution). The language definition adds that computation consists of evaluating statements one after another, that a semicolon always ends a statement while a newline may end one, and that a group of statements in braces is a block (The R Language Definition: Control structures).

Two consequences shape the rest of this page.

  • if, for, while, repeat, break, next and function are reserved words, yet they behave like functions: if returns the value of the branch it took, a loop returns NULL, and calling if as a function, as the last lines of the first script do, works. The help page for Control says that these are the basic control-flow constructs of the language and that they work much like the control statements of any Algol-like language (R documentation: Control).

  • The decisions R makes in a program are mostly vectorised rather than written as loops. A condition that is a single TRUE or FALSE selects what to run (if); a condition with one answer per element selects values (ifelse(), logical subsetting); an explicit loop is the tool for work that really is sequential.

if and else

The language definition gives the formal syntax of the conditional statement as if (statement1) statement2 else statement3: the condition is evaluated and, if it is TRUE, the first statement is evaluated, otherwise the second (The R Language Definition: if). The else part is optional, if statements can be nested through else if without any limit, and the statement returns, as its value, the value of the branch that ran. The introduction manual states the requirement on the condition: it must evaluate to a single logical value (An Introduction to R: Conditional execution). The section "The condition: what if accepts" below shows what that means in R 4.6.

if and else as an expression

Because if is an expression it can sit on the right-hand side of an assignment, as an argument, or as the last expression of a function, which is how most R functions return one of several values. When no branch runs (the condition is FALSE and there is no else) the value is NULL, and it is returned invisibly, so typing such an if at the console prints nothing. A block in braces is an expression too, and its value is that of its last expression.

# if/else is an expression: it has a value, so it can be assigned or returned.
pages <- 312L
size <- if (pages > 300L) "long" else "short"
size
#> [1] "long"
sizes <- c(short = "under 100 pages", long = "300 pages or more")
sizes[[size]]
#> [1] "300 pages or more"

# The value of the branch that ran, or an invisible NULL when no branch ran.
res <- if (pages > 1000L) "huge"
is.null(res)
#> [1] TRUE
if (pages > 1000L) "huge"
withVisible(if (pages > 1000L) "huge")
#> $value
#> NULL
#>
#> $visible
#> [1] FALSE
#>

# A chain of else if: the conditions are tested in order, first TRUE wins.
classify_length <- function(pages) {
  if (is.na(pages)) {
    "unknown"
  } else if (pages < 100L) {
    "short"
  } else if (pages < 300L) {
    "medium"
  } else {
    "long"
  }
}
vapply(c(80L, 250L, 312L, NA), classify_length, character(1L))
#> [1] "short"   "medium"  "long"    "unknown"

# The value of a block is the value of its last expression.
label <- if (pages > 300L) {
  n_words <- pages * 250L
  paste("about", n_words, "words")
} else {
  "fewer than 75000 words"
}
label
#> [1] "about 78000 words"

# if is a function: the call form shows the three arguments.
`if`(pages > 300L, "long", "short")
#> [1] "long"

Source: R documentation: Control

A few remarks on the script. In the else if chain only the first condition that is TRUE selects a branch, so the order of the conditions matters, and the NA test goes first because every later comparison with NA would be NA. The function-call form at the end of the script evaluates the same way as the keyword form, which is why code that rewrites expressions (see Language Objects and Quoting) sees if as a call with three arguments. The help page recommends, as a form of defensive programming, to always use braces around the branches (R documentation: Control). Without braces the branch is a single expression, which is fine for short one-line forms such as if (cond) "a" else "b".

The else rule at the top level

The one layout rule that surprises people from other languages is that else must be on the same line as the end of the if branch unless the whole if is inside braces. The language definition spells it out: when the if statement is not in a block, the else, if present, must appear on the same line as the end of the first branch, because otherwise the newline completes the if and yields a syntactically complete statement that is evaluated. The suggested solution is a compound statement with the else on the same line as the closing brace (The R Language Definition: if). The parser-level explanation is in the The else rule section of Syntax and Lexical Structure; the script below shows the real parse errors.

# The same text, parsed at the top level and inside braces.
show_parse <- function(...) {
  src <- paste(c(...), collapse = "\n")
  msg <- tryCatch(
    {
      parse(text = src, keep.source = FALSE)
      "parses"
    },
    error = conditionMessage
  )
  cat(msg, "\n")
}

# At the top level the first line is already a complete statement.
show_parse("if (TRUE) 1", "else 2")
#> <text>:2:1: unexpected 'else'
#> 1: if (TRUE) 1
#> 2: else
#>    ^
show_parse("if (TRUE) 1 else 2")
#> parses
show_parse("if (TRUE) {", "  1", "} else {", "  2", "}")
#> parses
show_parse("if (TRUE) {", "  1", "}", "else {", "  2", "}")
#> <text>:4:1: unexpected 'else'
#> 3: }
#> 4: else
#>    ^

# Inside braces the newline before else is discarded.
show_parse("{", "  if (TRUE) 1", "  else 2", "}")
#> parses

# A function body is a braced block, so the same layout is accepted there.
f <- function(x) {
  if (x > 0)
    "positive"
  else
    "not positive"
}
f(1)
#> [1] "positive"
f(-1)
#> [1] "not positive"

# At the top level too, a brace that is still open keeps the expression going.
y <- {
  if (FALSE) "a"
  else "b"
}
y
#> [1] "b"

The message is unexpected 'else', with the offending line and a caret that points at the start of else. The same text is accepted in three places: on one line, with } else { on the closing-brace line, and anywhere inside { ... }, including the body of a function, because inside braces the parser is in the middle of a compound expression and the newline cannot end the statement. That is why indented if/else layouts that fail when pasted at the console work in a function. It is also why the rule only bites at the top level of a script or the console, which is exactly where beginners write their first if. The robust style is the braced form with } else { on one line.

A script file adds a second wrinkle. Rscript reads the file and evaluates one expression after another, so the lines before the broken if run and print before the error. source() parses the whole file first, so nothing in it runs and the error carries the file name and line number.

# The same layout in a script file: Rscript evaluates the file expression by
# expression, source() parses the whole file first.
script <- tempfile(fileext = ".R")
writeLines(c(
  'cat("before\\n")',
  "if (TRUE) 1",
  "else 2",
  'cat("after\\n")'
), script)

out <- suppressWarnings(system2(rscript, script, stdout = TRUE, stderr = TRUE))
cat(sub(script, "script.R", out, fixed = TRUE), sep = "\n")

#> [1] 1
#> Error: unexpected 'else' in "else"
#> Execution halted

cat(sub(script, "script.R", res, fixed = TRUE), sep = "\n")
#> script.R:3:1: unexpected 'else'
#> 2: if (TRUE) 1
#> 3: else
#>    ^

# With the else on the closing-brace line the file runs from start to end.
writeLines(c(
  'cat("before\\n")',
  "if (TRUE) {",
  "  cat('then\\n')",
  "} else {",
  "  cat('else\\n')",
  "}",
  'cat("after\\n")'

#> after

The help page for Control gives the same advice: do not put a newline between } and else when typing at the keyboard or sourcing, and consider always using braces (R documentation: Control).

The condition: what if accepts

The help page for Control describes the condition as a length-one logical vector that is not NA, and says that other types are coerced to logical if possible, ignoring any class, and that conditions of length greater than one are an error (R documentation: Control). The script shows each way a condition can go wrong, with the real message. The messages belong to if and while alike, so each case is shown for both where it matters.

# What a condition may be, and what happens when it is not.
try_if <- function(expr) {
  tryCatch(
    {
      expr
      invisible("no error")
    },
    error = function(e) cat("error:", conditionMessage(e), "\n"),
    warning = function(w) cat("warning:", conditionMessage(w), "\n")
  )
}

# A condition of length greater than one is an error since R 4.2.0.
x <- c(TRUE, FALSE)
try_if(if (x) "yes")
#> error: the condition has length > 1
try_if(while (x) break)
#> error: the condition has length > 1

# NA is neither TRUE nor FALSE.
try_if(if (NA) "yes")
#> error: missing value where TRUE/FALSE needed
try_if(if (NA_integer_ > 1L) "yes")
#> error: missing value where TRUE/FALSE needed
try_if(if (NA_character_ == "a") "yes") # nolint: equals_na_linter.
#> error: missing value where TRUE/FALSE needed

# Length zero.
try_if(if (logical(0L)) "yes")
#> error: argument is of length zero
try_if(if (NULL) "yes")
#> error: argument is of length zero
try_if(if (character(0L) == "a") "yes")
#> error: argument is of length zero

# A string that is not a logical value.
try_if(if ("yes") "ok")
#> error: argument is not interpretable as logical
if ("TRUE") "string TRUE is accepted"
#> [1] "string TRUE is accepted"
if ("T") "string T is accepted"
#> [1] "string T is accepted"
if ("true") "lower-case true is accepted"
#> [1] "lower-case true is accepted"

# Numbers are coerced: zero is FALSE and every other non-NA number is TRUE.
if (0) "a" else "b"
#> [1] "b"
if (2.5) "a" else "b"
#> [1] "a"
if (-1L) "a" else "b"
#> [1] "a"

#> error: argument is not interpretable as logical

# Lists and functions are not coerced.
try_if(if (list(TRUE)) "a")

The length-zero case deserves attention because it comes from code that looks safe. A comparison such as character(0) == "a" has length zero, so if fails with argument is of length zero rather than treating the result as FALSE. In real code the usual source is a lookup that finds nothing (x$missing_field == "a", or which(...) returning integer(0)). The NA case is the same problem from missing data: the shelf books table has a missing year and two missing pages, and if (books$pages[[6]] > 300) stops with missing value where TRUE/FALSE needed.

The language definition has an older description in which only the first element of a longer condition is used and an error is raised for a type that is not logical or numeric. Neither statement matches R 4.6.1: a longer condition is an error, and a string spelled like a logical value is accepted. The help page quoted above is the current rule.

Conditions of length greater than one

Until R 4.1.x, if (c(TRUE, FALSE)) gave only a warning and used the first element. The NEWS for R 4.2.0 records the change: calling if() or while() with a condition of length greater than one now gives an error rather than a warning, and as a consequence the environment variable _R_CHECK_LENGTH_1_CONDITION_ no longer has any effect (R NEWS: Changes in R 4.2.0). The R Internals manual lists that variable among the environment variables of the checking tools and now describes it as no longer in use, because conditions of length greater than one in if or while statements are an error (R Internals: Tools). Old code that relied on the first-element behaviour now fails, usually with the first call of a function that was passed a vector; the fix is to say what was meant (any(), all(), isTRUE(), an index like x[[1]], or ifelse() when a value per element is wanted).

The same release made && and || with an operand of length greater than one give a warning, and R 4.3.0 turned it into an error: the NEWS for 4.3.0 says that it is now always an error, reported in the form 'length = 4' in coercion to 'logical(1)', and that the environment variable _R_CHECK_LENGTH_1_LOGIC2_ no longer has any effect (R NEWS: Changes in R 4.3.0).

Turning a vector or an NA into one condition

When the data really can be a vector or can contain NA, reduce it to one definite answer before the if. The helpers are any() and all() (with na.rm), isTRUE() and isFALSE() (which are never NA and never longer than one), the short-circuit operators && and ||, and an explicit length() guard. stopifnot() is the right tool when the condition is a requirement rather than a branch. The help pages for the logical operators explain that & and | work element by element and && and || take length-one operands and evaluate their right-hand side only if necessary (R documentation: Logic).

ifelse(): the vectorised conditional

ifelse(test, yes, no) is the vectorised form of if/else. The introduction manual describes it as a vectorised version of the if/else construct that returns a vector of the same length as the condition, with an element of yes where the condition is true and of no where it is false, both recycled as necessary (An Introduction to R: Conditional execution). The current help page puts it more precisely: ifelse returns a value with the same shape as test, filled with elements selected from yes or no (R documentation: ifelse). The details follow from that sentence, and the script shows each of them.

  • Missing values in test give missing values in the result.

  • yes and no are recycled when they are too short, and yes is evaluated if and only if some element of test is true (and likewise for no).

  • The result has the length and the attributes of test, including names, dim, dimnames and class, and it never takes them from yes or no.

  • The type of the result is the type of the logical vector test coerced to accommodate first the values taken from yes and then those taken from no, so it depends on the values in test, not only on the types of the branches.

  • test alone decides the length of the result, so a length-one test gives a length-one result however long yes and no are.

# ifelse() is the vectorised if/else: the result has the shape of `test`.
x <- c(6, -1, 0, NA, 3)
ifelse(x > 0, "positive", "not positive")
#> [1] "positive"     "not positive" "not positive" NA             "positive"

# A missing value in test gives a missing value in the result.
ifelse(c(TRUE, NA, FALSE), 1L, 2L)
#> [1]  1 NA  2

# yes and no are recycled when they are too short.
ifelse(c(TRUE, FALSE, TRUE, FALSE), c("a", "b"), "z")
#> [1] "a" "z" "a" "z"

# The type of the result depends on which branches were used.
str(ifelse(c(TRUE, TRUE), 1L, "none"))
#>  int [1:2] 1 1
str(ifelse(c(FALSE, FALSE), 1L, "none"))
#>  chr [1:2] "none" "none"
str(ifelse(c(TRUE, FALSE), 1L, "none"))
#>  chr [1:2] "1" "none"
str(ifelse(c(TRUE, TRUE), 1L, 2.5))
#>  int [1:2] 1 1
str(ifelse(c(FALSE, FALSE), 1L, 2.5))
#>  num [1:2] 2.5 2.5

# test alone determines the length: yes and no are not used for their length.
yes <- 1:3

#>  logi NA
str(ifelse(TRUE, yes, no))
#>  int 1
str(ifelse(FALSE, yes, no))
#>  num 3.14

# Attributes come from test (names, dim, dimnames, class), not from yes or no.
named <- c(a = 1, b = -2, c = 3)

#>      a      b      c
#>   "up" "down"   "up"

#> [1,]    1    2
#> [2,]    0    0

#> [1] 1 2 1
ifelse(f == "x", f, NA)

test <- c(first = TRUE, second = FALSE)

Three results in the script are traps that the help page warns about.

  • The type of the result depends on the data. ifelse(c(TRUE, TRUE), 1L, "none") is an integer vector, but changing one value of test gives a character vector, because only then is a string taken from no. A function that returns ifelse() can therefore return different types on different inputs.

  • The attributes come from test. A factor passed as yes loses its levels and comes back as integer codes (ifelse(f == "x", f, NA)), and a Date passed as yes comes back as a number of days.

  • The class of test is kept. With a test of class factor or Date the result would carry that class even if the values do not suit it; test is almost always a plain logical vector, so this rarely shows.

The help page works the date case through: restoring the class afterwards is one repair, and an assignment on a copy (the last lines of the script) is the version it calls more efficient and still clear. It also notes that if (test) yes else no is much more efficient than ifelse(test, yes, no) whenever test is a simple true/false result, that is, when length(test) == 1. In that case ifelse() is simply the wrong tool, and if also evaluates only the branch it uses.

ifelse() on the shelf: classifying overdue loans

A loan is overdue when it was kept more than loan_days (21) days; a loan that is still out is measured up to shelf_today. The loan log has two rows that cannot be classified: one loan has the impossible date 2025-02-30, which as.Date() turns into NA, and one was returned three days before it was made. Nested ifelse() calls express the three outcomes; assigning in order on a copy gives the same answer. The first step of the script uses ifelse() on the return date, so it meets the date pitfall itself and repairs it with as.Date(), which since R 4.3.0 no longer needs an origin for a numeric argument (R NEWS: Changes in R 4.3.0).

end_date <- as.Date(end_date)
days_out <- as.integer(end_date - loans$loan_date)

# was returned before it was made.

  is.na(days_out) | days_out < 0L, "check",

Alternatives to nested ifelse()

Deeply nested ifelse() is hard to read and evaluates every branch for the whole vector. R has simpler tools for the common shapes.

switch(): choosing among many cases

switch(EXPR, ...) evaluates EXPR and chooses one of the alternatives in .... The language definition notes that technically it is just another function, whose semantics are close to those of the control structures of other languages (The R Language Definition: switch), and the help page says that it is a primitive that evaluates only its first argument and the one alternative that is selected (R documentation: switch). It works in two distinct ways, depending on whether EXPR is a character string or a number.

  • Character selector. The string is matched exactly against the names of the alternatives, with no partial matching. The first matching name wins. If there is no match, the single unnamed alternative, if any, is the default; with no default the result is NULL, invisibly.

  • Fall-through. An alternative written with no value (novel = ,) is missing, so switch() evaluates the next non-missing alternative. The help page’s own example is switch("cc", a = 1, cc =, cd =, d = 2), which gives 2.

  • Numeric selector. The number is coerced to an integer and picks the alternative by position (names are ignored). A number below 1 or above the number of alternatives selects nothing and the result is NULL, invisibly. A numeric selector cannot have a default.

  • Visibility. The result has the visibility of the alternative that was evaluated, so switch("a", a = invisible("hidden")) prints nothing.

  • Errors. More than one unnamed (default) alternative is an error, as is an EXPR that is not of length one. A call with no alternatives gives a warning, because it is usually a coding error.

Edge cases and warnings

The corner cases are worth knowing because each one has a real message.

# Corner cases of switch().
try_sw <- function(expr) {
  tryCatch(expr, error = function(e) cat("error:", conditionMessage(e), "\n"),
           warning = function(w) cat("warning:", conditionMessage(w), "\n"))
}

# EXPR must be a length-one vector.
try_sw(switch(c("a", "b"), a = 1, b = 2))
#> error: EXPR must be a length 1 vector
try_sw(switch(character(0L), a = 1, b = 2))
#> error: EXPR must be a length 1 vector
try_sw(switch(NULL, a = 1))
#> error: EXPR must be a length 1 vector

is.null(switch(NA_character_, a = 1, 2))
#> [1] FALSE
switch(NA_character_, a = 1, "default")
#> [1] "default"

is.null(switch(NA_integer_, 1, 2))

  • EXPR must be a length 1 vector covers a vector, character(0) and NULL; switch() is not vectorised, so use vapply() or ifelse() for a vector of selectors.

  • A factor selector is treated as its integer codes, with a warning whose text recommends switch(as.character(*), ...). This is the classic bug: the first level is level 1, so switch(ff[1], A = ..., B = ...) picks the alternative by position, not by name. Convert with as.character() first, as the last line of that block does.

  • The selector and the names are compared exactly. switch("pro", program = "p", "no match") does not match, in contrast with argument matching of function calls (see Functions).

  • An NA_character_ selector matches no name and so takes the default; an NA_integer_ selector selects nothing. Neither is an error, so a missing value is silently treated as "other" unless you test for it first.

  • Always put EXPR first and name it when partial matching is possible, and give the character form a single unnamed default after the named values: the help page recommends both for clarity and compatibility.

  • match.arg() is the standard companion when the selector is an argument of a function: it checks the value against the allowed choices at the top of the function and gives a clear error (R documentation: match.arg). Its message uses curly quotes in a UTF-8 locale, as the last line of the script shows.

Loops

R has three statements for explicit looping, for, while and repeat, and two statements that control them, break and next; the language definition points out that R also provides implicit looping through tapply, apply and lapply, and that many operations, especially arithmetic ones, are vectorised, so a loop may not be needed (The R Language Definition: Looping). The value of a loop statement is always NULL, returned invisibly. All three loops take a single expression as the body, which in practice is a braced block.

for

The syntax is for (name in vector) statement, where the vector can also be a list (The R Language Definition: for). For each element the variable is set to that element and the body is evaluated. The help page for Control adds the precise rules, which the script confirms.

  • The sequence is evaluated once, at the start of the loop. Changing it afterwards does not affect the loop. If it has length zero the body is skipped.

  • The variable is assigned in turn the value of each element. Assigning to it inside the body does not affect the next iteration.

  • When the loop terminates the variable remains as a variable containing its latest value. After a loop over a sequence of length zero it is NULL. The variable lives in the environment where the loop runs, not in a new scope: this is difference 3.3.3 between R and S in the R FAQ, where the index of a for loop is local to the loop (R FAQ 3.3.3: Others).

  • The sequence is implicitly unclassed. For classed objects, the help page suggests as.list() to prepare a list to iterate over, or seq_along() to get an index vector and then extract the elements explicitly. A factor is coerced to a character vector, and the sequence can be a long vector (supported in for since R 4.0.0, see the NEWS entry in R NEWS: Changes in R 4.0.0).

source("scenario.R")

# for over a vector: the loop variable takes each element in turn.

  cat(n, "squared is", n^2, "\n")
}

seq_along() and seq_len() versus 1:length(x)

1:length(x) is the idiom of older tutorials, and the introduction manual itself uses 1:length(yc) in its worked example of for (An Introduction to R: Repetitive execution). It is correct whenever x is known to be non-empty. When x is empty it counts down: 1:0 is c(1, 0), so a loop over it runs twice, with i equal to 1 and then 0, indexing out of range and, if the body assigns, writing to the wrong element. seq_along(x) and seq_len(n) return an empty integer vector for zero length, so the loop body is skipped. They are described, together with seq(), in the seq help page (R documentation: seq).

Remember these rules from the script.

  • Use seq_along(x) to loop over the positions of a vector or list, seq_len(n) to loop n times, and seq_len(nrow(df)) for the rows of a data frame. the default seq_linter of lintr reports 1:length(x), 1:nrow(x) and seq_len(length(x)).

  • seq(x) is not a safe shortcut: with a length-one x it means 1:x, so seq(n) with n = 0 gives c(1, 0), the same trap.

  • for (day in dates) gives numbers, not dates, because the sequence is unclassed. Loop over seq_along(dates) and index with [[, or over as.list(dates).

  • for (col in df) visits the columns of a data frame, not its rows.

  • A loop over a factor visits the elements as their character labels, not as integer codes; use as.integer(f) for the codes.

while, repeat, break and next

while (cond) body tests the condition before each iteration, so the body may never run. repeat body has no condition and runs until a break (or an error, or a return() inside a function); the language definition notes that you need to be careful because of the danger of an infinite loop, and that the body of a repeat has to be a block, because you usually need two statements, the computation and the test (The R Language Definition: repeat and The R Language Definition: while). break leaves the innermost loop at once, and next abandons the rest of the current iteration and moves to the next one; both apply only to the innermost of nested loops (R documentation: Control).

# while: the condition is tested before every iteration.
copies <- 0L
while (copies < 3L) {
  copies <- copies + 1L
  cat("printed copy", copies, "\n")
}
#> printed copy 1
#> printed copy 2
#> printed copy 3
copies
#> [1] 3

# The body may never run.
n <- 10L
while (n < 5L) {
  n <- n + 1L
}
n
#> [1] 10

# repeat: an endless loop that ends only with break (or an error or return()).
attempt <- 0L
repeat {
  attempt <- attempt + 1L
  cat("attempt", attempt, "\n")
  if (attempt >= 3L) {
    break
  }
}
#> attempt 1
#> attempt 2
#> attempt 3

# next skips the rest of the body and goes to the next iteration.
for (i in 1:6) {
  if (i %% 2L == 0L) {
    next
  }
  cat(i, "")
}
#> 1 3 5
cat("\n")
#>

# break leaves only the innermost loop.
for (i in 1:3) {
  for (j in 1:3) {
    if (j == 2L) {
      break
    }
    cat("i =", i, "j =", j, "\n")
  }
}
#> i = 1 j = 1
#> i = 2 j = 1
#> i = 3 j = 1

A loop that stops at the first bad value

break, next and return

break and next are lexically tied to a loop. Used outside one, or inside a function called from a loop, they fail with no loop for break/next, jumping to top level. That is why the body of the function passed to vapply() or lapply() cannot use next: it is not a loop, it is a function. Return the value for the element instead (NA, an empty value, or a flag you filter on). return() leaves the whole function, even from inside a loop (see Functions), and a loop that is the last expression of a function makes the function return NULL invisibly. Recall() is the base function that calls the function currently running, a way to write a loop as recursion (R documentation: Recall).

# break and next are only meaningful inside a loop.
res <- tryCatch(eval(quote(break)), error = conditionMessage)
res
#> [1] "no loop for break/next, jumping to top level"
res <- tryCatch(eval(quote(next)), error = conditionMessage)
res
#> [1] "no loop for break/next, jumping to top level"

# They cannot cross a function boundary: the body of an anonymous function
# passed to a loop-like function is not a loop.
res <- tryCatch(
  vapply(1:3, function(i) {
    if (i == 2L) next
    i
  }, integer(1L)),
  error = conditionMessage
)
res
#> [1] "no loop for break/next, jumping to top level"

first_long <- function(pages, limit) {

Loop values and preallocation

A loop is run for its side effects. Because its value is always NULL, invisibly, x <- for (...) ... stores NULL, and a result has to be collected in a variable that is updated inside the loop. How it is collected decides the cost.

  • Growing with c() (out <- c(out, value)) allocates a new vector and copies all the existing elements on every iteration, so the total work grows with the square of the length.

  • Preallocating (out <- numeric(n), then out[[i]] <- value) allocates once and fills by position. The constructors numeric(n), integer(n), character(n) and logical(n) give vectors of the right type filled with 0, 0L, "" and FALSE; vector("list", n) gives a list of n NULL values, and vector(mode, n) is the general form (R documentation: vector).

  • Assigning past the end grows a vector, filling the gap with NA. Since R 3.4.0 this over-allocates by a small fraction, so building a vector by assigning to the next element is cheaper than c(), but the NEWS entry still says that preallocating is preferred (R NEWS: Changes in R 3.4.0). It also hides off-by-one bugs, as the last lines of the script show.

  • For results that are data frames or other objects, fill a list with vector("list", n) and combine once at the end with do.call(rbind, parts) (R documentation: do.call), instead of calling rbind() inside the loop.

When loops are fine

An explicit loop is not wrong in R; it is just not the first tool to reach for. The practical rule is the one the language definition hints at: prefer a vectorised operation when one exists (arithmetic, comparison, ifelse(), sum(), cumsum(), subsetting) and an apply-family function or a purrr-style map when you only need the values, and use an explicit for loop when it is the clearer way to say it:

  • the iterations depend on each other (each step uses the previous result: a running balance, a simulation, a search that stops, a convergence test);

  • the work per iteration is large and not vectorisable (reading a file, calling an API, fitting a model), so the loop overhead is negligible;

  • the loop is run for its side effects (printing, writing files, drawing plots, updating a database);

  • the clarity matters more than the speed: a short loop over a handful of items is easier to read than a clever vectorised one.

When the loop does nothing but compute one value per element, vapply() is the safer replacement: it checks the type and length of every result and returns a vector, which sapply() does not guarantee. See The apply Family and Functionals and Vectorisation and Iteration for the vectorised and functional styles in depth, and the section on preallocation above for the cost of building a result in a loop.
