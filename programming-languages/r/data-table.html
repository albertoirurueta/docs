data.table

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. This page is about the add-on package data.table, checked at version 1.18.6.1 (dated 22 August 2026 in its NEWS file). data.table extends the data frame of Data Frames with one query form, DT[i, j, by], that reads “take DT, choose the rows i, compute j, grouped by by”; with columns that are added, changed and removed in place; with keyed, rolling and non-equi joins; and with a multi-threaded file reader and writer, fread() and fwrite(). Apart from base R, the scripts on the page run only data.table, and one script that compares the three styles also runs dplyr, checked at version 1.2.1, always written dplyr:: so that the two packages are never attached together. The image used for the examples also had bit64 4.8.6, which supplies the integer64 class that fread() uses for 13-digit numbers such as ISBNs. dtplyr (1.3.3 in the image) is named in one sentence and is not run. data.table depends on nothing but R itself and the methods package that ships with it, and the vignette on importing it presents that as a reason to depend on it (data.table package documentation: Importing data.table).

Every example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines starting with #> are what it printed, messages included, in order. The scripts also pass the default lintr 3.4.0 linters, which includes the line-length limit of 80 characters. lintr’s object_usage_linter cannot see that a name inside DT[...] is a column, so it complains when such a query sits inside a function body; the small functions on this page that do that carry a # nolint: object_usage_linter. comment (or a nolint start and nolint end pair), which is the only exception, and queries at the top level of a script need nothing. The examples use the library-shelf scenario of the section: books, loans, shelf_today and loan_days come from the scenario.R file described on the section index, so a script that needs them starts with source("scenario.R") and then converts the data frames in place with setDT(). books has 16 rows and the columns title, author, isbn, year, genre and pages; loans has 60 rows and the columns loan_id, isbn, member, loan_date and return_date. The scripts that read the files directly use fread("books.csv"). Files that a script writes go to tempfile() and are deleted before the script ends. Each script is complete, so any block can be pasted and run on its own; the setup lines are repeated where a later block needs them.

The package website at https://rdatatable.gitlab.io/data.table/ documents the development version of data.table (its page header said 1.18.99 when it was read for this page), so a few details there are ahead of the installed 1.18.6.1. Where the two disagree, the page reports what the installed package did: the website’s options page, for example, lists datatable.print.class and datatable.print.keys with the default FALSE, and the installed package returns TRUE for both (see Printing and threads). Terms from other pages are used without repeating them: copy-on-modify is in Memory and Copy Semantics and Assignment, Names and Values, the evaluation of column names inside a call is the data-mask idea of Evaluation and Non-Standard Evaluation, and the same shelf analyses done with dplyr are in The tidyverse and dplyr.

What a data.table is

A data.table is a data frame: its class is c("data.table", "data.frame"), it is a list of columns of equal length, and every function that accepts a data frame accepts it. What differs is the [ method. DT[i, j, by] is a query language in the brackets (the next section), DT[2] is the second ROW (a data frame treats a single number as a column), and a data.table never has or uses row names. Printing differs too: a data.table shows row numbers followed by a colon, a line of column classes under the names (<char>, <int>), and for a long table only the first and last rows. data.table() builds a table from vectors as data.frame() does, with stringsAsFactors = FALSE and check.names = FALSE as defaults and an optional key argument (data.table package documentation: data.table).

The first script attaches the package with a plain library(data.table) call, which is the only place on the page where its start-up message is shown. data.table exports its own %notin% (added in data.table 1.15.0), and R 4.6.0 added %notin% to base R (it is listed in the R NEWS for 4.6.0), so attaching the package prints a conflict message and the data.table version is found first on the search path; both are the negation of %in%. In an interactive session library(data.table) also prints a line with the version and the number of threads in use; Rscript does not, because the .onAttach() hook of the package returns at once when interactive() is FALSE.

Real tables are usually already data frames, and data.table converts them in two ways. as.data.table() makes a copy and leaves the original alone. setDT() changes the object in place: it adds the class and the over-allocation described below, copies nothing, and returns the table invisibly, so it is called without an assignment. setDF() goes back in place. The next script converts the shelf tables, and shows keep.rownames for a data frame whose row names carry information.

suppressPackageStartupMessages(library(data.table))
source("scenario.R")

# books and loans from scenario.R are data frames.
class(books)
#> [1] "data.frame"

# as.data.table() copies; the original is untouched.
copy_dt <- as.data.table(books)
class(books)
#> [1] "data.frame"
class(copy_dt)
#> [1] "data.table" "data.frame"

# setDT() converts IN PLACE: no copy, no assignment, no result printed.
setDT(books)
setDT(loans)
class(books)
#> [1] "data.table" "data.frame"
class(loans)
#> [1] "data.table" "data.frame"

# Row names are dropped; keep.rownames = "isbn" keeps them in a column.
copies <- data.frame(copies = 2:3,
                     row.names = c("9780306406157", "9780141439518"))
as.data.table(copies)
#>    copies
#>     <int>
#> 1:      2
#> 2:      3
as.data.table(copies, keep.rownames = "isbn")
#>             isbn copies
#>           <char>  <int>
#> 1: 9780306406157      2
#> 2: 9780141439518      3

# setDF() goes back, also in place.
tmp <- copy(books[1:2, .(title, year)])
setDF(tmp)
class(tmp)
#> [1] "data.frame"
is.data.table(books)
#> [1] TRUE

The general form: DT[i, j, by]

The package documentation reads the form out loud: “take DT, subset rows by i, then compute j grouped by by”. The table lines the three arguments up with the clauses of an SQL query, and lists the arguments that refine them. Every argument of a query is optional, and the commas keep the positions: DT[, j] has no i, DT[i] has only i.

WHERE, ORDER BY, JOIN

by, keyby

GROUP BY

on, nomatch, mult, roll

Queries chain by writing another pair of brackets straight after the first: DT[...][...] runs the second query on the result of the first. That is how a result is sorted after grouping (DT[, .N, by = g][order(-N)]), and it replaces the temporary variables of base R.

i: choosing and ordering rows

i is evaluated inside the table, so the columns are variables and books[year > 2020] needs no books$. It can be a vector of row numbers (negative numbers drop rows), a logical expression, or order(...) for sorting, where a minus sign means descending. A logical NA in i is treated as FALSE, as the help page says, which differs from a data frame, where a logical NA produces a row of NA values. A logical i must be as long as the table: recycling a shorter one is an error. The operators %between%, %chin% and %like% (a regular expression, as grepl()) are shortcuts for common conditions. order() inside i is handled by data.table’s own fast sort, which sorts text in C-locale, not in the locale of the session (see the setters), and puts NA last, as base order() does.

When a variable of the calling environment has the name of a column, the column wins: after year <- 1900, books[year > 2022] still compares the column. The last lines of the script show it; the way to reach the variable is env = or .. (see Programming with data.table).

suppressPackageStartupMessages(library(data.table))
source("scenario.R")
setDT(books)

# i is evaluated inside the table: columns are variables, no books$ needed.
books[year > 2020, .(title, year)]
#>             title  year
#>            <char> <int>
#> 1:     Loud Roofs  2021
#> 2: THE LONG TABLE  2023
#> 3:    Ten Winters  2022

# Row numbers, negative numbers and logical vectors work as in a data frame.
books[-(3:16), .(title)]
#>                  title
#>                 <char>
#> 1:    The Dispossessed
#> 2: Pride and Prejudice

# NA in a logical i drops the row (year is NA in row 7).
books[year > 2020 | is.na(year), .(title, year)]
#>                    title  year
#>                   <char> <int>
#> 1:            Loud Roofs  2021
#> 2: Garden of Small Fires    NA
#> 3:        THE LONG TABLE  2023
#> 4:           Ten Winters  2022

# order() inside i sorts; - means descending. NA goes last for ascending.
books[order(-pages), .(title, pages)][1:3]
#>                  title pages
#>                 <char> <int>
#> 1: Pride and Prejudice   432
#> 2:    Notes on Gravity   410
#> 3:    The Dispossessed   387

# %between%, %chin% and %like% are shortcuts for common conditions.
books[year %between% c(2015, 2020), .(title, year)]
#>                   title  year
#>                  <char> <int>
#> 1:   the quiet streets   2019
#> 2:      Midnight Ledger  2016

j: columns, expressions and lists

j is evaluated in the scope of the table too. A bare column name returns the column as a vector, .(a, b) (an alias of list(a, b)) returns a data.table, and any other expression is evaluated on whole columns. When j returns a list, every element becomes a column, named after the argument, or V1, V2 and so on when it is unnamed. A number or a character vector of names in j selects columns and always gives a data.table back, which is the difference to df[, 2] on a data frame, where one column becomes a vector. A character vector held in a variable is looked up in the calling scope with the prefix .. (one level up, like .. in a file path), or passed to .SDcols. j can be any code, so it can also run for its side effect (a plot, a cat()), and then its value is what the code returns.

suppressPackageStartupMessages(library(data.table))
source("scenario.R")
setDT(books)

# A bare column in j comes back as a vector; .() or list() as a data.table.
books[, pages]
#>  [1] 387 432 214 198 301  NA  96 280 352 256  88 410 175 322  NA 244
books[1:3, .(pages)]
#>    pages
#>    <int>
#> 1:   387
#> 2:   432
#> 3:   214

# An expression is evaluated on the whole column. na.rm is needed for NA.
books[, mean(pages, na.rm = TRUE)]
#> [1] 268.2143
books[, .(mean_pages = mean(pages, na.rm = TRUE), n = .N)]
#>    mean_pages     n
#>         <num> <int>
#> 1:   268.2143    16

# Several results become several columns; unnamed ones are called V1, V2...
books[genre == "Poetry", .(title, nchar(title), pages * 2L)]
#>                    title    V2    V3
#>                   <char> <int> <int>
#> 1: Garden of Small Fires    21   192
#> 2:           Paper Moons    11   176

# A number in j selects a column and ALWAYS gives a data.table back.
books[1:2, 1]
#>                  title
#>                 <char>
#> 1:    The Dispossessed
#> 2: Pride and Prejudice
books[1:2, c("title", "year")]
#>                  title  year
#>                 <char> <int>
#> 1:    The Dispossessed  1974
#> 2: Pride and Prejudice  1813

by and keyby: groups

by runs j once for each group of rows that share the values of the columns (or expressions) named, and stacks the results. The groups come out in the order of their first appearance in the table; keyby sorts them and sets them as the key of the result, which is the usual choice when the result is printed. by accepts a column name, a character vector of names, a range a:c of columns, or a list of expressions in .(...), and a computed grouping column needs a name there, as decade below. i is applied before the grouping, which is how a filtered summary is written. A single unnamed value in j is called V1 in the result; .N (the size of the group) becomes N.

suppressPackageStartupMessages(library(data.table))
source("scenario.R")
setDT(books)
books[, genre := tolower(trimws(genre))]

# by groups; the groups come out in the order of first appearance.
books[, .(n = .N, pages = sum(pages, na.rm = TRUE)), by = genre]

#> 5:     non-fiction     3   527
#> 6:          poetry     2   184

Adding, changing and removing columns by reference

The := operator

:= is data.table’s assignment inside j. It adds a column, replaces a column or a part of one, or (with NULL) removes a column, in the table itself: no copy of the table is made and nothing is assigned back, so books[, age := 2026L - year] is a complete statement. There are two spellings. The LHS := RHS form takes column names on the left (a single name, or a character vector in c() or in parentheses) and a value or a list of values on the right. The functional form, := called like a function, as in `:=`(a = ..., b = ...), takes named arguments, which lets each column carry its own comment; let() is an alias for it in the help page of the package, and it is present in 1.18.6.1. With i, only the rows chosen are changed, and a new column is NA in the other rows. With by, the value is computed for each group and recycled within it. The call returns the table invisibly, so nothing is printed at the prompt (Printing after the := operator has the details), and .Last.updated holds the number of rows the last := or set() changed.

A name in parentheses, (cols) :=, means “the columns whose names are held in cols”, where a bare cols := would create a column called cols. This is also how one function is applied to many columns, (cols) := lapply(.SD, f). Since data.table 1.16.0 names(.SD) := lapply(.SD, f) updates every column of .SD (NEWS for 1.16.0). The help page states the rule for types: the right-hand side is coerced to the type of the existing column, not the other way round (unlike <- on a data frame), and a whole column given as the right-hand side replaces the column, with its new type ("plonk" syntax, as in (num_cols) := lapply(.SD, as.numeric) below). Coercing a part of a column warns, and a right-hand side whose length is neither 1 nor the number of rows is an error (both messages are in Common errors and warnings).

suppressPackageStartupMessages(library(data.table))
source("scenario.R")
setDT(books)

# := adds a column by reference: no assignment, and nothing is printed.
books[, age := 2026L - year]
books[1:3, .(title, year, age)]
#>                   title  year   age
#>                  <char> <int> <int>
#> 1:     The Dispossessed  1974    52
#> 2:  Pride and Prejudice  1813   213
#> 3:   the quiet streets   2019     7

# With i, only those rows change; a new column is NA in the others.
books[pages > 400L, size := "long"]
books[, .N, by = size]
#>      size     N
#>    <char> <int>
#> 1:   <NA>    14
#> 2:   long     2

# Several columns: names on the left, a list on the right.
books[, c("title", "genre") := .(trimws(title), tolower(trimws(genre)))]
books[3:4, .(title, genre)]
#>                title   genre
#>               <char>  <char>
#> 1: the quiet streets fiction
#> 2:        Loud Roofs fiction

Reference semantics and copy()

Because := and the set* functions change the table where it is, two names can refer to one table, and a change made through one name is seen through the other. b <- a gives a data.table a second name, as it does for every R object, and a := on b then changes the table both names refer to; a data frame, by contrast, is copied the moment it is modified. The same holds when a table is passed to a function: the function receives the table itself, so a := inside it changes the caller’s data. copy() makes a real, independent copy and is the way to protect the original. The vignette data.table package documentation: Reference semantics gives the reason: since R 3.1.0 adding a column to a data frame copies only the vector of column pointers (a shallow copy), but changing some rows of a column with df$c[i] <- value still copies the whole column, and := does neither.

suppressPackageStartupMessages(library(data.table))

# b <- a does not copy a data.table, and := changes the one object.
a <- data.table(x = 1:3)
b <- a
b[, y := x * 2L]
names(a)
#> [1] "x" "y"
address(a) == address(b)
#> [1] TRUE

# copy() makes an independent table.
d <- copy(a)
d[, z := 0L]
names(a)
#> [1] "x" "y"
names(d)
#> [1] "x" "y" "z"
address(a) == address(d)
#> [1] FALSE

# A function that uses := on its argument changes the caller's table.
add_flag <- function(tbl) {
  tbl[, flag := TRUE] # nolint: object_usage_linter.
  invisible(NULL)
}
add_flag(a)
names(a)
#> [1] "x"    "y"    "flag"

# copy() at the top of the function keeps the caller's table untouched.
with_stamp <- function(tbl) {
  tbl <- copy(tbl)
  tbl[, stamp := "2026-06-30"] # nolint: object_usage_linter.
  tbl[]
}
res <- with_stamp(a)
names(res)
#> [1] "x"     "y"     "flag"  "stamp"
names(a)
#> [1] "x"    "y"    "flag"

# The base R way, a$col <- value, makes a (shallow) copy as usual.
e <- a
e$w <- 1
names(a)
#> [1] "x"    "y"    "flag"
names(e)
#> [1] "x"    "y"    "flag" "w"

address(a) == address(b) is TRUE when two names refer to the same table; the addresses themselves are memory locations that change from run to run and are not worth printing. The last lines of the script show the base R way, e$w <- 1: the replacement function $<- works on a (shallow) copy, so a is unchanged. Base R replacement functions such as attr<- are the usual way a data.table is copied by accident, which is the subject of the self-reference warning below. The rule of thumb is to use := and the set* functions to change a data.table, copy() to keep the original, and not to rely on the copy-on-modify behaviour of a data frame. The sharing of one table by several names is the same idea as the shared environments of Scoping, Environments and Closures; Memory and Copy Semantics covers when R copies and when it does not.

set(), setnames(), setorder() and setcolorder()

Every function whose name starts with set changes its argument by reference and returns it invisibly. set(DT, i, j, value) is described in the help page as a low-overhead, loop-able version of := that cannot group: the cost of a DT[...] call is small but is paid on each iteration, and set() avoids it, which makes it the tool for updating columns in a for loop (i must be row numbers, j a column name or number). setnames() renames columns by name or position, setorder() sorts the table itself (a minus sign for descending; NA first), setcolorder() moves columns to the front (it gained before and after arguments in 1.15.0), and setattr() sets an attribute without copying. setkey(), setindex() and setDT() are covered elsewhere on the page.

Sorting in data.table, whether by setorder(), setkey(), or order() in i, always uses the C-locale: capitals sort before lower case whatever language the session is set to, and the order is the same on every machine. The help page of setorder() explains the choice and says that DT[base::order(...)] sorts by the locale of the session instead.

Over-allocation

The help page of truelength() explains why a data.table has room for more columns than it uses. Adding a column by creating a new list of column pointers (a shallow copy) "resulted in inconsistent behaviour in some circumstances", so data.table over-allocates the list of column pointers when data.table() or setDT() creates a table, so that := can add a column fully by reference. truelength() is the number of slots allocated and length() the number in use. The default is 1024 spare slots, set by options(datatable.alloccol = ). When the slots are used up, the next := has to reallocate, which takes a shallow copy; the page suggests copy() first, setalloccol() (also called alloc.col()) to reallocate in advance, or a larger option value to avoid it, and options(datatable.verbose = TRUE) reports when a shallow copy is taken. The functions are described as experimental and somewhat advanced, so the names might change.

A table that has been through saveRDS() and readRDS(), or save() and load(), comes back without its slots and without a valid self-reference. The next := or set() allocates them again, quietly, as the script shows with truelength() and the helper .selfref.ok(). The help page of .selfref.ok() says that it is for technical use; it is shown only to make the mechanism visible. Loading a table back is therefore not what triggers the warning in the next section.

suppressPackageStartupMessages(library(data.table))

# A data.table has room for more columns than it uses (over-allocation),
# which is why := can add a column without copying anything.

#> [1] 1
truelength(dt)
#> [1] 1025
getOption("datatable.alloccol")
#> [1] 1024

length(dt)
#> [1] 3
truelength(dt)
#> [1] 1025

# := and set() allocate the room again, quietly.

#> [1] 0

#> [1] 1028
.selfref.ok(back)
#> [1] TRUE
other <- readRDS(path)

#> [1] 1027

The self-reference warning

To know that a table is the one it allocated, data.table stores a pointer to the table itself in a hidden attribute, .internal.selfref. A table that R copied, or that was assembled by hand, does not pass the check. This happens when a table is built with structure() or by class<- on a data frame, when attr<- copies it, and when a package that knows nothing of data.table returns a modified copy. := still works on such a table, but it takes a shallow copy so that it can add the column, and warns that it did. In data.table 1.18.6.1 the warning begins "A shallow copy of this data.table was taken so that := can add or remove 1 columns by reference" (older releases, and many answers written for them, begin "Invalid .internal.selfref detected and fixed by taking a (shallow) copy of the data.table"). The cure is the one the message gives: build tables with setDT() or data.table(), copy with copy(), and use the set* functions in place of the base replacement functions.

suppressPackageStartupMessages(library(data.table))

class(df) <- c("data.table", "data.frame")
.selfref.ok(df)
#> [1] FALSE
res <- tryCatch(df[, y := 2L], warning = conditionMessage)

Printing after :=

At the prompt, books[, x := 1] prints nothing: inside := data.table sets a global flag, which the print method uses to know whether to print. The flag has a visible side effect: a function whose last expression is a := returns the table, and the print of that result can be swallowed. FAQ 2.23 of the package explains it and recommends a trailing [] after the last := in a function (data.table package documentation: Frequently asked questions). Keys, indices and joins

Keys and binary search

A key is a sort order that the table remembers. setkey(DT, col1, col2) sorts the table by those columns, in place and ascending (NA first), and marks them as the key (the "sorted" attribute). key() returns the key, haskey() tests for one, and setkeyv() is the version that takes a character vector. A table has at most one key, because the key is the physical order. Its purpose is speed and brevity: a subset by key value is a binary search, not a scan of the whole column, DT["x"] finds the group "x" of the first key column, and grouping by a leading part of the key is faster because the groups are already adjacent in memory (the reasons are in the help page of setkey()). setkey() always sorts in C-locale. nomatch = NULL drops the values of i that are not in the table, where the default nomatch = NA returns a row of NA for each, and mult chooses "first", "last" or (the default) "all" of several matches.

Joins with on=

x[i, on = ...] looks up the rows of i in x, and the result has one row for each row of i (for each match): in SQL terms x[i] is a right join, and i can be a data.table, a data frame, a list, or a vector. on names the columns to match: an unnamed character vector when both tables have the same names (on = "isbn", or on = .(isbn)), a named one when they differ (on = c(isbn = "code"), or on = "isbn==code"), and an inequality for a non-equi join (next section). It overrides the keys of the tables, and the help page recommends it even when the tables are keyed, because it makes the code readable. In j, a column of i that has the same name as one of x is reached with the prefix i., and one of x with x..

The same tool makes the other joins of the table below. nomatch = NULL turns a join into an inner join, the ! prefix gives the rows of x that have no match in i (an anti join), x[i, col := i.col, on = ...] is an update join that adds columns to x by reference, and by = .EACHI evaluates j once for each row of i, with .N the number of matches, which is how counts and sums over matches are written without first building the large joined table. merge() also works on data.tables, with all, all.x, all.y and by as for data frames, sort = TRUE by default and a default by taken from the shared key (or the common column names). A join that would produce more rows than nrow(x) + nrow(i) stops with an error unless allow.cartesian = TRUE, a guard against joining on a key that is not unique in both tables.

Rolling and non-equi joins

Two joins have no counterpart in merge(). A rolling join, roll = TRUE, matches each row of i to the last row of x whose value is less than or equal to it, in the last column of on; it is the tool for "the price, the fee or the status in force on this date". The other values of roll are -Inf (the next row, the opposite direction), "nearest", and a finite number that limits how far a row may be carried. rollends decides what happens before the first row and after the last: by default a forward roll continues past the last row, and a date before the first row gets NA. A non-equi join matches on >=, >, <= and < in on, which is how a value is placed in a range or a band; the operators are written in on = .(lo <= pages, hi > pages) (a column of x on the left of each operator and a column of i on the right) or as strings, on = c("lo<=pages", "hi>pages"). Joins on overlapping intervals have their own function, foverlaps() (data.table package documentation: foverlaps). Non-equi joins match a row of i to every row of x that satisfies the condition, so the result can be larger than either table.

The script gives each loan the late fee in force on its loan date from a small schedule (fees changed on 2025-07-01 and 2026-01-01), then places books in page-size bands.

Secondary indices and auto-indexing

A key reorders the table, and a table has one. A secondary index stores the sorted order of a column (a vector of row numbers) in an attribute without moving any row, and a table can have many. setindex(DT, col) creates one, indices(DT) lists them, and setindex(DT, NULL) removes them all. A subset on an indexed column, DT[col == value], DT[col %in% values] or DT[.(value), on = "col"], uses binary search through the index. Auto-indexing creates the index the first time a column is used in == or %in% in i, so that the following subsets on that column are fast. The vignette says that auto-indexing is implemented for == and %in% (and for several of them combined with &), not yet for < and >=, and that on = computes the index on the fly each time without saving it. It is on by default; options(datatable.auto.index = FALSE) turns it off, and options(datatable.use.index = FALSE) stops the use of existing indices. Changing the indexed column by reference drops the index, as the script shows, because it would no longer be correct. One consequence is that a == subset can change the table it reads by adding an attribute, which is harmless for the data but visible in attributes().

Reshaping and stacking

dcast() and melt() change the shape of a table, and the formula that dcast() takes is the one described in Formulas: rows ~ columns. dcast(DT, member ~ quarter, value.var = "N") makes one row per member and one column per quarter; when several rows fall into one cell, fun.aggregate (a function, or a list of functions) summarises them, and without it dcast() warns and counts the rows (the warning text is in Common errors and warnings). fill sets the value of empty cells, and an aggregate over no rows gives NaN for mean(), as the script shows for a member without loans in a year. Since data.table 1.18.0, dcast() is an error when fun.aggregate returns more than one value. melt() turns columns into rows: id.vars are kept, measure.vars are stacked, and variable.name and value.name name the two new columns. The helper measure() (exported since 1.16.0) melts several groups of columns at once, using the pieces of the column names, as in measure(value.name, year = as.integer, sep = "_"), which splits loans_2025 into the output column loans and the value 2025 of the column year.

Programming with data.table

A query that names its columns in the code cannot be reused for another column, and building the text of a query for eval(parse(text = ...)) is fragile. data.table offers four routes, from the vignette data.table package documentation: Programming on data.table.

  1. ..var in j (or .SDcols = var) looks up a character vector of column names in the calling scope. It selects columns; it does not substitute names into an expression.

  2. get(name) and mget(names) inside j evaluate a name or names as columns. They work, but the column name is then hidden inside a string, where tools and readers cannot see it.

  3. env = list(a = value, ...) is the safe route: the names in the list are substituted into i, j and by BEFORE the query is evaluated, as substitute2() does, so a function can take column names as arguments and build the query from them. By default a character element of length 1 becomes a name (a longer one is an error), and I() keeps an element as it is, which is how a character vector is inserted as a vector.

  4. substitute2(expr, env) shows the expression env = builds, which is how a generated query is checked. Its help page calls it an experimental, more robust and friendlier substitute().

The next script uses them in order. The function mean_by() carries the nolint comments mentioned in the introduction, because lintr cannot see that value and group are substituted.

Printing and threads

print.data.table() has arguments for the number of rows shown (nrows, default 100, and topn, default 5: a longer table shows the first and last topn rows with a --- line between), class (the line of column classes), row.names, col.names ("auto", "top" or "none"), print.keys (the key and indices above the data), trunc.cols (only the columns that fit the width) and quote. Every default is read from an option, datatable.print.nrows, datatable.print.topn, datatable.print.class, datatable.print.keys, datatable.print.rownames, datatable.print.colnames and datatable.print.trunc.cols, so a session or a profile can change it for every table (options are set in a script or in a startup file; see Sessions, Workspaces and Startup). Character cells longer than datatable.prettyprint.char characters are truncated with .... When a table of more than 20 rows is printed in full, since 1.18.0 the column classes are repeated at the bottom as the names already were (a truncated table, as in the first script below, shows its --- line instead).

Threads are controlled separately. fread(), fwrite(), forder() (the sort behind setkey() and order() in i), grouping with GForce, fifelse(), nafill() and a few other functions use OpenMP threads. The number of threads is decided when the package is loaded: 50% of the logical CPUs by default (R_DATATABLE_NUM_PROCS_PERCENT changes the percentage and R_DATATABLE_NUM_THREADS fixes the number, both read at load time), and never more than OMP_THREAD_LIMIT allows. getDTthreads() reports it, and setDTthreads(n) changes it for the session (setDTthreads(0) is all logical CPUs) and returns the previous setting. The number depends on the machine, so the script prints only a comparison with 1 and a restored value. A throttle (default 1024 rows) keeps small tasks on one thread, and data.table switches to a single thread inside a forked process (the mechanism of parallel::mclapply()), so it does not oversubscribe the CPUs of code that is already parallel. CRAN’s own checks set OMP_THREAD_LIMIT to 2, and a package must not raise it above 2. See Parallel and Asynchronous Computing for the other parallel tools.

Speed depends on the operation, the size of the data and the machine, so this page prints no timings. The data.table website links to the db-benchmark project (db-benchmark, whose page lists the timings with the syntax timed and the machine type, from 16 cores and 32 GB to 128 cores and 256 GB), and Performance, Profiling and Benchmarking shows how to measure a real case with bench. The differences that do not depend on timings are these:

  • Syntax. dplyr is a set of verbs, each doing one thing, joined with the pipe; data.table is one query form with three slots, in which the work of several verbs fits into one call. The SQL reading of DT[i, j, by] is a way to learn it.

  • Copying. dplyr verbs return a new table and leave the input alone, so a pipeline can be reasoned about step by step; := and the set* functions change the table in place, which saves a copy of a large table and makes it easy to change something the caller did not expect (see Pitfalls).

  • Joins. dplyr has join_by() for equality, inequality, rolling and overlap joins since version 1.1.0 (dplyr package documentation: join_by), so the two cover the same ground; data.table’s on = is terser, and by = .EACHI evaluates j for each row of i, which the error message for an accidental many-to-many join suggests as a way "to avoid the large allocation".

  • Files. fread(data.table = FALSE) returns a plain data frame and fwrite() writes data frames, so the two functions can be used with either package.

  • Dependencies. data.table depends on R 3.4.0 and imports only methods, which ships with R (packageDescription("data.table") in the image used here). dplyr 1.2.1 depends on R 4.1.0 and imports thirteen packages (cli, generics, glue, lifecycle, magrittr, methods, pillar, R6, rlang, tibble, tidyselect, utils and vctrs).

  • Mixing. A data.table is a data frame, so the dplyr verbs accept it, but code that mixes the two vocabularies is read by people who must know both, and a := among pipes can surprise a reader who expects a copy. Teams usually choose one for the main pipeline.

  • dtplyr. The package dtplyr (dtplyr package documentation) is a data.table back end for dplyr: its README states the goal as translating dplyr code into the equivalent data.table code. It is installed in the image used for the examples and is not run on this page.

Pitfalls

  • DT[, 2] is a data.table, not a vector. A data frame drops a single column to a vector; data.table never does. Use DT[[2]], DT[, col] or DT$col for the vector.

  • b <- a is not a copy. A := or set* call on b changes a too, and so does the same call inside a function that was given a. Use copy() when the original must stay as it is. This is the opposite of the copy-on-modify rule that the rest of R follows (Memory and Copy Semantics).

  • A column wins over a variable. In i, j and by a name is looked up among the columns first, so after year <- 1900 the query DT[year > 2022] still compares the column. Use ..var, env = or a differently named variable.

  • x[y] is a join, and the order matters. x[i, on = ] starts from the rows of i. books[loans, on = "isbn"] has 60 rows, one for each loan, and loans[books, on = "isbn"] starts from the books: a row for each loan of each book, and one row for a book that was never loaned.

  • Check how a join matched. Keys that are not unique give a many-to-many join (an error unless allow.cartesian = TRUE), types that differ give an error, and values that look alike but are not equal (trailing blanks, an ISBN with one digit missing) give NA.

  • rbindlist() binds by position unless told otherwise. use.names = "check" (the default) reports a different order with a message and binds by position. Pass use.names = TRUE.

  • fread() guesses. A column of 13-digit codes is integer64; an empty quoted string stays ""; unquoted blanks are stripped; a date column with one impossible date is a different class from one without. Fix the types with colClasses and check them with vapply(DT, \(x) class(x)[[1L]], character(1)).

  • Sorting is in C-locale. setkey(), setorder() and order() in i sort capitals before lower case in every locale. Sort by the locale of the session with DT[base::order(...)] when that is what is wanted.

  • A function that ends with := may print nothing. Add a trailing [] (see Printing after the := operator).

  • Base replacement functions copy. attr<-, class<- on a data frame and structure() produce tables that := has to repair with a warning (the self-reference warning). Use setattr(), setDT() and setnames().

  • Loops need set(). A for loop of DT[...] calls pays the cost of the bracket on every iteration; set() does not.

  • Packages that use data.table. In a package, import the symbols (import(data.table) or importFrom(data.table, :=, .N)), and declare the columns used in DT[...] to avoid the R CMD check NOTE about "no visible binding for global variable" (assign them NULL or use character names), as the importing vignette describes; see Packages, Libraries and Namespaces and Creating Packages.
