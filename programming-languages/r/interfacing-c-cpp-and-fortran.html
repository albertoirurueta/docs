Interfacing C, C++ and Fortran

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. This page compiles and runs code, so besides base R it used the GNU compilers gcc and g++ 13.3 and gfortran 13.3 with GNU make (all three are in the container image), and these add-on packages: Rcpp 1.1.2 for the C++ sections, bench 1.1.4 for one benchmark, pkgbuild 1.4.8 to ask whether build tools exist, and usethis 3.2.2, devtools 2.5.2 and roxygen2 8.1.1 to put compiled code into a copy of the shelf package; lintr 3.4.0 was used only to check the R scripts. cpp11 0.5.5 is installed and is named in one sentence, not run. RcppArmadillo, RcppParallel and inline are not installed, so what the page says about them is prose, and Rtools45 on Windows and Apple’s Command Line Tools on macOS were not available either: everything said about those toolchains comes from the manuals and is marked as not run.

R is an interpreter written in C, and it was designed from the start to be extended with compiled code: a great part of base R is C and Fortran called through the same entry points described here. This page is about the other direction, the code you write yourself. It explains how a C, C++ or Fortran function becomes a shared object that R loads (R CMD SHLIB and dyn.load()), the four interfaces that call it (.Call(), .External(), .C() and .Fortran()), how C code reads and builds R objects through the SEXP type and keeps them safe from the garbage collector (PROTECT and UNPROTECT), how routines are registered so that R can check them (R_registerRoutines() and useDynLib in NAMESPACE), what goes in src/Makevars, how Rcpp reduces the C++ boilerplate, which parts of R’s C API a package may use, and what each platform needs installed. Every example was compiled and run, and the error and warning messages are the ones R printed.

Every R example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines that start with #> are what it printed. The scripts also pass the default lintr linters. Every C, C++ and Fortran file shown is the exact file that was compiled; it was also compiled with -Wall -pedantic set in a personal Makevars file (shown below) and gave no warning; the transcripts of the build commands show the default build. The compiler command lines R prints are long and name the container’s directories and distribution, so the page shows them with the flags shortened to the ones that matter, and omits the line that names the compiler version and the operating system; where that happens the text says so. The compiled examples use small data typed into the scripts (a handful of loan durations in days, a few ISBN strings), not the CSV files of the running scenario described on the section index, because the compiled objects live in their own directory; the package examples use the shelf package of Creating Packages, copied and extended with a src/ directory, with paths shown as ~/shelf. The shared-object extension is .so on Linux and macOS and .dll on Windows, so the scripts write paste0("add", .Platform$dynlib.ext); where the page says add.so, read add.dll on Windows.

This page links to the references for the three languages that this one calls: the C Reference (and its Build and Tooling page), the C++ Reference (and its Program Structure and Compilation page, which explains extern "C"), and the Fortran Reference, whose pages Interoperability with C and Calling Fortran from C, C++ and Python were added by issue #277 and cover the Fortran side of what is shown here from R. Measuring whether compiled code is worth writing belongs to Performance, Profiling and Benchmarking; how R stores the objects that C code receives is the subject of Memory and Copy Semantics; calling Python instead is Python Interop with reticulate.

Why leave R, and when not to

Most of R’s speed already comes from compiled code. sum(), %*%, sort(), lm() and the arithmetic on vectors all end in C or Fortran that someone else wrote and tested, so the first answer to a slow script is usually a better use of those: vectorise, avoid growing objects, choose another algorithm, or use a package such as data.table that is compiled for that job. Performance, Profiling and Benchmarking shows how to measure, and Vectorisation and Iteration covers the byte-code compiler and preallocation that make plain R loops much faster than their reputation. The manual Writing R Extensions says the same: before using .Call() or .External() it advises to consider whether interpreted code is fast enough, and whether .C() is enough, because the first two give much more control and impose much greater responsibilities (Writing R Extensions: Handling R objects in C).

There are four good reasons to write compiled code anyway.

  • A loop that cannot be vectorised. Each iteration depends on the previous one (a simulation, a recursive filter, a state machine, a dynamic-programming table), so the work cannot be handed to a built-in that operates on whole vectors.

  • An existing library. A numerical routine in Fortran, a parser in C, a geometry engine in C++: wrapping it is far cheaper than porting it. The Fortran BLAS and LAPACK page describes the libraries R itself links.

  • Memory control. R copies on modification (see Memory and Copy Semantics); compiled code can fill a preallocated buffer in place.

  • A data structure R does not have. A heap, a hash table, a trie, a spatial index, kept alive between calls behind an external pointer.

The price is real. Compiled code is the one place where a mistake does not give an R error but a crash of the whole R process, or worse, a wrong answer with no message. It needs a compiler on every machine that installs the package from source, it has to be kept in step with changes of the R C API (this page’s last sections), it is harder to debug, and it makes a package harder to get onto CRAN. The rule of thumb in the R community is to profile first, change the algorithm second, and write compiled code last; the example near the end of this page puts numbers on why.

The toolchain: what R needs on each platform

R compiles C, C++ and Fortran with the compilers it was configured with, and it records the commands in etc/Makeconf inside the R installation. R CMD config prints any of those variables, and R CMD SHLIB and R CMD INSTALL read them, so the compiler is never named in your own build files. The script below asks whether R can find a working compiler (pkgbuild::has_build_tools() compiles a small C file with R CMD SHLIB, which is the real test), prints the shared-object extension of this platform, and prints the C, C++ and Fortran compiler commands R uses. On this machine the C compiler is selected with the C23 option (-std=gnu2x is gcc 13’s spelling of it) and the C++ compiler with the C++20 option, which are the defaults of R 4.5.0 and R 4.6.0 respectively; the version notes at the end of the page give the NEWS entries.

# Is there a compiler R can use? TRUE means make and a C compiler were found.
pkgbuild::has_build_tools(debug = FALSE)
#> [1] TRUE

# The shared-object extension of this platform.
.Platform$dynlib.ext
#> [1] ".so"

# What R was configured to compile with (the same as `R CMD config CC`).
r_bin <- file.path(R.home("bin"), "R")
for (variable in c("CC", "CXX", "FC")) {
  value <- system2(r_bin, c("CMD", "config", variable), stdout = TRUE)
  cat(sprintf("%s: %s\n", variable, value))
}
#> CC: gcc -std=gnu2x
#> CXX: g++ -std=gnu++20
#> FC: gfortran

Source: R documentation: system2

The help page of has_build_tools() adds that debug = TRUE prints extra information, and that on Windows a failure such as R CMD config CC returning status 127 means that Rtools is not on the PATH (pkgbuild package documentation: has_build_tools). What has to be installed differs by platform.

From C source to a loaded shared object

The smallest .Call function

A function called through .Call() takes R objects as arguments and returns one. In C, an R object of any type is a SEXP (a pointer to R’s internal node type, described in the next section), so the function takes SEXP arguments and returns a SEXP. The smallest useful function adds two numbers. Rf_asReal() coerces the first element of its argument to a C double, and Rf_ScalarReal() builds a length-one numeric vector from a double; the header Rinternals.h declares both, and R.h the rest of the common API.

#include <R.h>
#include <Rinternals.h>

SEXP add(SEXP x, SEXP y) {
  return Rf_ScalarReal(Rf_asReal(x) + Rf_asReal(y));
}

Source: Writing R Extensions: Calling .Call

R CMD SHLIB turns the source file into a shared object. It calls make with R’s own rules, so it uses the compiler, the flags and the link line recorded when R was built. The transcript shows the two commands it runs, with the flags shortened (the real lines carry the include directory of this R installation and about a dozen hardening and diagnostic flags) and without the first line it prints, which names the compiler version and the operating system.

R CMD SHLIB add.c
#> gcc -std=gnu2x -I"<R_HOME>/include" -fPIC -O2 -c add.c -o add.o
#> gcc -std=gnu2x -shared -o add.so add.o -L"<R_HOME>/lib" -lR

Source: R documentation: SHLIB

R CMD SHLIB accepts C (.c), C++ (.cc, .cpp), fixed-form Fortran (.f), free-form Fortran (.f90, .f95), Objective C and Objective C++ sources, or object files, or linker options. Two details from the manual are worth keeping in mind: make does not rebuild when only the flags changed (use --preclean), and a file named test.c next to test.f makes R CMD SHLIB test.f compile the C file instead (Writing R Extensions: Creating shared objects).

dyn.load, is.loaded and the symbol table

dyn.load() loads a shared object into the running R process, and .Call() then finds the C function by its name. The manual advises against assuming a file extension, and recommends file.path(path1, path2, paste0("mylib", .Platform$dynlib.ext)). The script loads add.so, calls the function with doubles, integers and a missing value, shows that only the first element of each argument is used (because the C code reads it with Rf_asReal()), and shows the two ways to be exact about which shared object a name belongs to: the PACKAGE argument, and a native symbol object from getNativeSymbolInfo().

# Load the shared object built by `R CMD SHLIB add.c`, then call into it.
dyn.load(paste0("add", .Platform$dynlib.ext))
is.loaded("add")
#> [1] TRUE
.Call("add", 1, 2)
#> [1] 3
.Call("add", 1L, 2L)
#> [1] 3
.Call("add", NA_real_, 2)
#> [1] NA
.Call("add", c(5, 6), c(10, 20))
#> [1] 15

# Pass PACKAGE so that the search is confined to this shared object.
add <- function(x, y) .Call("add", x, y, PACKAGE = "add")
add(0.1, 0.2) == 0.3
#> [1] FALSE
add(0.1, 0.2)
#> [1] 0.3

# The loaded objects, and the symbol as an R object.
"add" %in% names(getLoadedDLLs())
#> [1] TRUE
info <- getNativeSymbolInfo("add", PACKAGE = "add")
class(info)
#> [1] "NativeSymbolInfo"
info$name
#> [1] "add"

# Unloading is rarely needed; it lets the file be rebuilt on Windows.
invisible(dyn.unload(paste0("add", .Platform$dynlib.ext)))
is.loaded("add")
#> [1] FALSE

Source: R documentation: dyn.load

The loaded shared object is listed by getLoadedDLLs(), whose elements are named after the file without the extension. dyn.unload() removes it; the manual calls unloading unnecessary and not safe in general, but needed on some platforms (Windows) to allow the DLL to be rebuilt. Unloading a DLL and reloading a rebuilt one with the same name may not work on every platform (Writing R Extensions: dyn.load and dyn.unload). In practice, when you edit a C file during development, restart R after rebuilding, or use pkgload::load_all() (below), which handles unloading for a package.

PACKAGE matters more than it looks. A bare .Call("add", x, y) asks R to search every loaded shared object, and R’s search order is most recently loaded first; if two packages define a C function called add, the wrong one can be called, with the wrong number of arguments, and that normally crashes R. Writing R Extensions explains that PACKAGE confines the search and speeds it up, and the help page of .Call recommends it or a native symbol object for anything called often. The manual’s timing section measured the difference as small but real for functions called millions of times (Writing R Extensions: Registering native routines).

Errors from the lookup

When the name cannot be found, R says so in a message that is the same on every platform. These are the real texts, captured by tryCatch() (the container’s directory is replaced by <dir> so that the script, not the page, hides the path). The last three lines show the same failure for .C(), .Fortran() and .External(); only .Fortran() says "Fortran symbol name".

dyn.load(paste0("add", .Platform$dynlib.ext))
message_of <- function(expr) {
  tryCatch(expr, error = \(e) {
    gsub(getwd(), "<dir>", conditionMessage(e), fixed = TRUE)
  })
}

# A symbol that is not in any loaded shared object.
message_of(.Call("nope"))
#> [1] "C symbol name \"nope\" not in load table"

# A symbol searched in the wrong shared object, or in one that is not loaded.
message_of(.Call("nope", PACKAGE = "add"))
#> [1] "\"nope\" not available for .Call() for package \"add\""
message_of(.Call("add", 1, 2, PACKAGE = "nosuchdll"))
#> [1] "\"add\" not available for .Call() for package \"nosuchdll\""

# A file that does not exist (the second line is the operating system's text).
message_of(dyn.load("missing.so"))
#> [1] "unable to load shared object '<dir>/missing.so':\n  <dir>/missing.so: cannot open shared object file: No such file or directory"

# The same symbol name on the other three interfaces.
message_of(.C("nope"))
#> [1] "C symbol name \"nope\" not in load table"
message_of(.Fortran("nope"))
#> [1] "Fortran symbol name \"nope\" not in load table"
message_of(.External("nope"))
#> [1] "C symbol name \"nope\" not in load table"

Source: R documentation: .Call

The second line of the dyn.load() message is the operating system’s own text (this one is glibc’s), so it differs on macOS and Windows. All four lookup errors have the same remedy: check the spelling, check that the shared object was built from the current source and loaded, and check that the function is not static and, in C++, is declared extern "C".

Handling R objects in C

What a SEXP is

Every R object that C code touches is a SEXP, a pointer to a structure the headers call SEXPREC. Think of it as a variant type: the same pointer type refers to a numeric vector, a list, a function, an environment, a call or NULL, and TYPEOF(x) returns a code that says which. C code must therefore check the type before it uses the data, and it gets at the data through accessor functions, never by looking inside the structure (the structure is not part of the API and its layout is allowed to change). The types that package code meets most often are these.

Two types in that table deserve a remark. A CHARSXP is not an R-level object but the immutable, shared element of a character vector: R keeps one copy of each distinct string in a global cache, so C code must never modify the bytes behind CHAR(). And LISTSXP is the old Lisp-style pairlist; an R list is a VECSXP, which is why the test for an R list is Rf_isNewList() and not Rf_isList() (Writing R Extensions: Handling lists). R Internals describes all the types, including the ones that are not for packages (R Internals: SEXPs).

The Rf_ prefix and R_NO_REMAP

The functions in the manual’s examples carry an Rf_ prefix (Rf_allocVector, Rf_error, Rf_ScalarReal), and so do all the examples on this page. R’s headers also define short names for many of them (allocVector, error, length), which are macros that expand to the prefixed names, and those short names clash easily with system headers and other libraries. Defining R_NO_REMAP before any R header removes the macros and leaves only the prefixed names. The manual states the facts that matter: the prefix is optional in C code and recommended for new C code; since R 4.5.0 R_NO_REMAP is always defined when the R headers are included from C++, so C++ code must use the Rf_ names; and a package that defines it itself should guard it with #ifndef R_NO_REMAP to avoid compiler warnings about redefinition (Writing R Extensions: The R API).

The NEWS entries behind that: R 4.4.0 added the environment variable _R_CXX_USE_NO_REMAP_, which makes R CMD INSTALL (and so R CMD check) compile C++ code with -DR_NO_REMAP, and said that this was planned to become the default; R 4.5.0 made it the default and revised the manual to describe the remapped entry points (R NEWS: Changes in R 4.4.0 and 4.5.0). usethis::use_c() writes a template that starts with #define R_NO_REMAP, as the shelf example later shows. Two related switches exist for other headers: R_NO_REMAP_RMATH does the same for Rmath.h (the distribution functions), and STRICT_R_HEADERS, which removes the old S-compatibility definitions (PI, Calloc, Realloc, Free and the DOUBLE_* constants), has been the default since R 4.5.0, with R_Calloc, R_Realloc, R_Free and M_PI as the replacements.

A vector in, a vector out

The next file has three functions that show the pattern every .Call() routine follows: check or coerce the arguments, allocate the result, fill it through a pointer, copy the attributes that should survive, and return. overdue_days() requires a double vector and returns the days beyond the loan limit element by element; is_late() coerces to integers and returns a logical vector; count_late() calls is_late() and counts.

#include <R.h>
#include <Rinternals.h>

/* Days beyond the loan period, element by element; NA and NaN pass through. */
SEXP overdue_days(SEXP days, SEXP limit) {
  if (!Rf_isReal(days)) {
    Rf_error("'days' must be a double vector");
  }
  R_xlen_t n = XLENGTH(days);
  double lim = Rf_asReal(limit);
  const double *d = REAL_RO(days);
  SEXP out = PROTECT(Rf_allocVector(REALSXP, n));
  double *o = REAL(out);
  for (R_xlen_t i = 0; i < n; i++) {
    if (ISNAN(d[i])) {
      o[i] = d[i];
    } else {
      o[i] = d[i] > lim ? d[i] - lim : 0.0;
    }
  }
  SEXP nms = Rf_getAttrib(days, R_NamesSymbol);
  if (nms != R_NilValue) {
    Rf_setAttrib(out, R_NamesSymbol, nms);
  }
  UNPROTECT(1);
  return out;
}

/* TRUE when a loan is late, NA when the number of days is missing. */
SEXP is_late(SEXP days, SEXP limit) {
  SEXP d = PROTECT(Rf_coerceVector(days, INTSXP));
  int lim = Rf_asInteger(limit);
  R_xlen_t n = XLENGTH(d);
  SEXP out = PROTECT(Rf_allocVector(LGLSXP, n));
  const int *pd = INTEGER_RO(d);
  int *po = LOGICAL(out);
  for (R_xlen_t i = 0; i < n; i++) {
    po[i] = pd[i] == NA_INTEGER ? NA_LOGICAL : pd[i] > lim;
  }
  UNPROTECT(2);
  return out;
}

/* How many loans are late; missing values are not counted. */
SEXP count_late(SEXP days, SEXP limit) {
  SEXP flags = PROTECT(is_late(days, limit));
  const int *p = LOGICAL_RO(flags);
  R_xlen_t n = XLENGTH(flags);
  int total = 0;
  for (R_xlen_t i = 0; i < n; i++) {
    if (p[i] != NA_LOGICAL && p[i]) {
      total++;
    }
  }
  UNPROTECT(1);
  return Rf_ScalarInteger(total);
}

Several points in the file are worth a line each.

  • XLENGTH() and R_xlen_t are for lengths. R vectors can be longer than 2^31 - 1 elements on 64-bit platforms (the length is a signed 64-bit integer, with a practical limit of 52 bits), and LENGTH() and Rf_length() return an int that cannot hold such lengths; code that loops with an int index works until the day someone passes a very long vector (R Internals: Long vectors).

  • REAL_RO() returns a const pointer. The vector accessors have read-only variants (INTEGER_RO, LOGICAL_RO, DATAPTR_RO), and for a character vector or a list only read-only access exists, because writing straight into those would break the memory manager’s assumptions. The manual adds that these pointers are valid only for vectors of positive length: a zero-length vector has no data, so memcpy() of zero elements through such a pointer is undefined behaviour unless the length is checked first (Writing R Extensions: Vector accessor functions). top_days() below guards its copy for this reason.

  • REAL(x) is a function call, not a field access. Store the pointer in a variable before the loop, as the file does, instead of calling REAL(x)[i] on every iteration.

  • The result is allocated with Rf_allocVector(REALSXP, n). Unlike numeric(n) in R, Rf_allocVector() does not initialise the elements of an atomic vector (it only does so for lists and character vectors), so every element must be written before the object is returned.

  • The names are copied explicitly, with Rf_getAttrib() and Rf_setAttrib(). Attributes are not copied automatically; a function that should keep names, dim or class has to do it.

  • PROTECT() and UNPROTECT() bracket the lifetime of the new object; the section after next explains why.

Character vectors

A character vector is a STRSXP: a vector whose elements are CHARSXP nodes. Reading goes through STRING_ELT() and CHAR(); writing builds a CHARSXP with Rf_mkChar() (from a NUL-terminated C string), Rf_mkCharLen() (from part of a buffer) or Rf_mkCharLenCE() (with an encoding mark) and stores it with SET_STRING_ELT(). Rf_mkString() makes a whole length-one character vector from a C string, and Rf_ScalarString() from a CHARSXP. The function below keeps the first blank-delimited word of each string, passes NA through, and, because it copies the bytes of an element it did not interpret, copies the encoding mark of the original with it.

#include <string.h>
#include <R.h>
#include <Rinternals.h>

/* The first blank-delimited word of each string; NA stays NA. */
SEXP first_word(SEXP x) {
  if (!Rf_isString(x)) {
    Rf_error("'x' must be a character vector");
  }
  R_xlen_t n = XLENGTH(x);
  SEXP out = PROTECT(Rf_allocVector(STRSXP, n));
  for (R_xlen_t i = 0; i < n; i++) {
    SEXP el = STRING_ELT(x, i);
    if (el == NA_STRING) {
      SET_STRING_ELT(out, i, NA_STRING);
      continue;
    }
    const char *s = CHAR(el);
    int len = (int) strcspn(s, " \t");
    SET_STRING_ELT(out, i, Rf_mkCharLenCE(s, len, Rf_getCharCE(el)));
  }
  UNPROTECT(1);
  return out;
}

The encoding rules are the part of this that goes wrong in practice. A CHARSXP can be marked as UTF-8 or Latin-1, and the bytes behind CHAR() are in whatever encoding the mark says. When C code needs to interpret the characters, the manual recommends Rf_translateChar() (to the current locale’s encoding) or Rf_translateCharUTF8() (to UTF-8, which almost always represents the string faithfully), because both handle any input and allocate with R_alloc(); and when it only moves a string unchanged, as here, it should keep the mark with Rf_getCharCE() and Rf_mkCharLenCE() (Writing R Extensions: Character encoding issues). The help page of .C() adds a reason to prefer .Call() for text: a missing string reaches .C() code as the text "NA", which cannot be told from a real "NA".

Lists, classes and matrices

Lists, classes and dimensions are all attributes and vectors of vectors. loan_stats() below builds a named list with Rf_mkNamed() (which takes a C array of names ended by an empty string), fills its three elements with SET_VECTOR_ELT(), and sets the class attribute with Rf_classgets(). day_gaps() allocates a matrix with Rf_allocMatrix() (column-major, like R) and sets dimnames to a two-element list, reusing the names of the input for both dimensions. A data frame is a list of equal-length columns with names, row.names and class attributes; it is simplest to build the columns in C and call as.data.frame() or data.frame() in the R wrapper (Rcpp, later, does it in one expression).

#include <R.h>
#include <Rinternals.h>

/* A classed, named list: count, mean and maximum of the non-missing days. */
SEXP loan_stats(SEXP days) {
  SEXP d = PROTECT(Rf_coerceVector(days, REALSXP));
  const double *p = REAL_RO(d);
  R_xlen_t len = XLENGTH(d);
  int n = 0;
  double sum = 0.0, max = R_NegInf;
  for (R_xlen_t i = 0; i < len; i++) {
    if (ISNAN(p[i])) {
      continue;
    }
    n++;
    sum += p[i];
    if (p[i] > max) {
      max = p[i];
    }
  }
  const char *names[] = {"n", "mean", "max", ""};
  SEXP out = PROTECT(Rf_mkNamed(VECSXP, names));
  SET_VECTOR_ELT(out, 0, Rf_ScalarInteger(n));
  SET_VECTOR_ELT(out, 1, Rf_ScalarReal(n > 0 ? sum / n : NA_REAL));
  SET_VECTOR_ELT(out, 2, Rf_ScalarReal(n > 0 ? max : NA_REAL));
  SEXP cls = PROTECT(Rf_mkString("loan_stats"));
  Rf_classgets(out, cls);
  UNPROTECT(3);
  return out;
}

/* A matrix of differences x[i] - x[j], with names(x) as both dimnames. */
SEXP day_gaps(SEXP x) {
  SEXP xr = PROTECT(Rf_coerceVector(x, REALSXP));
  R_xlen_t n = XLENGTH(xr);
  const double *p = REAL_RO(xr);
  SEXP out = PROTECT(Rf_allocMatrix(REALSXP, (int) n, (int) n));
  double *o = REAL(out);
  for (R_xlen_t j = 0; j < n; j++) {
    for (R_xlen_t i = 0; i < n; i++) {
      o[i + n * j] = p[i] - p[j];
    }
  }
  SEXP nms = Rf_getAttrib(x, R_NamesSymbol);
  if (nms != R_NilValue) {
    SEXP dn = PROTECT(Rf_allocVector(VECSXP, 2));
    SET_VECTOR_ELT(dn, 0, nms);
    SET_VECTOR_ELT(dn, 1, nms);
    Rf_setAttrib(out, R_DimNamesSymbol, dn);
    UNPROTECT(1);
  }
  UNPROTECT(2);
  return out;
}

Errors, warnings, output and interrupts

C code reports problems to R with Rf_error() and Rf_warning(), which take a printf-style format and have the same effect as stop() and warning() in R code. Output goes through Rprintf() (R’s standard output, which a GUI console, sink() or a parallel worker may redirect) and REprintf() (R’s error stream), never printf() to the C library’s stdout, whose text may not appear in the console at all; writing complete lines is advised. A long loop should call R_CheckUserInterrupt() now and then, because no part of R can be interrupted while it runs compiled code otherwise.

#include <R.h>
#include <Rinternals.h>
#include <R_ext/Utils.h>

/* Stops on a negative value, warns about a missing one. */
SEXP checked_sqrt(SEXP x) {
  double v = Rf_asReal(x);
  if (ISNAN(v)) {
    Rf_warning("missing value, returning NA");
    return Rf_ScalarReal(NA_REAL);
  }
  if (v < 0) {
    Rf_error("'x' must be non-negative, not %g", v);
  }
  return Rf_ScalarReal(sqrt(v));
}

/* Prints a summary on standard output and a note on standard error. */
SEXP report(SEXP days) {
  SEXP d = PROTECT(Rf_coerceVector(days, REALSXP));
  R_xlen_t n = XLENGTH(d);
  Rprintf("%lld loans\n", (long long) n);
  REprintf("(note: written to the error stream)\n");
  UNPROTECT(1);
  return R_NilValue;
}

/* A long loop that can be interrupted from the console. */
SEXP busy(SEXP iterations) {
  double steps = Rf_asReal(iterations);
  double acc = 0.0;
  for (double i = 0; i < steps; i++) {
    if (((long long) i) % 1000000 == 0) {
      R_CheckUserInterrupt();
    }
    acc += 1.0;
  }
  return Rf_ScalarReal(acc);
}

Calling R from C

C code can call back into R. The routine below receives a function f, a vector and an environment, and applies the function to each element with Rf_lang2() (which builds the call f(arg)) and Rf_eval(). Each intermediate object is protected, and the check of the result’s type is made in C, since the function could return anything. The environment rho is passed from R as environment() because the API has no supported entry point for the current environment (the manual’s table of replacements tells packages to call environment() in R and pass the result).

#include <R.h>
#include <Rinternals.h>

/* Call the R function f on each element of x and collect the numbers. */
SEXP map_dbl(SEXP f, SEXP x, SEXP rho) {
  if (!Rf_isFunction(f)) {
    Rf_error("'f' must be a function");
  }
  SEXP xr = PROTECT(Rf_coerceVector(x, REALSXP));
  R_xlen_t n = XLENGTH(xr);
  SEXP out = PROTECT(Rf_allocVector(REALSXP, n));
  for (R_xlen_t i = 0; i < n; i++) {
    SEXP arg = PROTECT(Rf_ScalarReal(REAL(xr)[i]));
    SEXP call = PROTECT(Rf_lang2(f, arg));
    SEXP res = PROTECT(Rf_eval(call, rho));
    if (!Rf_isNumeric(res) || XLENGTH(res) != 1) {
      Rf_error("'f' must return a single number");
    }
    REAL(out)[i] = Rf_asReal(res);
    UNPROTECT(3);
  }
  UNPROTECT(2);
  return out;
}

The rules that keep a .Call routine safe

The manual’s rules for .Call() and .External() code can be written as a short list.

  • Treat the arguments as read-only. .Call() and .External() do not copy their arguments, so a vector that C code modifies in place changes every R variable that shares it. R shares freely (y <- x copies nothing, as Assignment, Names and Values shows). Copy with Rf_duplicate() (or Rf_shallow_duplicate() when only the top level changes) before modifying, and see Memory and Copy Semantics for how R decides when a copy is needed. The macros NAMED and SET_NAMED that older books use were replaced by reference counting in R 4.0.0; package code should use MAYBE_SHARED(), MAYBE_REFERENCED(), NO_REFERENCES() and MARK_NOT_MUTABLE(), which are documented in the section on named objects and copying (Writing R Extensions: Named objects and copying).

  • Check the types. A wrong guess gives a segmentation fault, not an R error. Test with TYPEOF() or Rf_isReal() and friends, or coerce with Rf_coerceVector() (which allocates, so the result is protected) or the scalar readers Rf_asReal(), Rf_asInteger() and Rf_asLogical(), which ignore all but the first element, as the add() example showed. Rf_asRboolean() (R 4.5.0) is the stricter version that errors on a length other than one. Coercion in C does not dispatch on class (a factor is just an integer), so it is usually better to coerce in the R wrapper.

  • Allocate with R and protect what you allocate (next section), and never keep a SEXP in a global C variable across calls unless it is registered with R_PreserveObject().

  • Stay on the main thread. The manual is explicit that the R API may be called only from the main thread of the R process; using it from another thread can corrupt memory.

  • Prefer the documented API. The last section of the page is about which entry points are documented.

PROTECT and UNPROTECT

Why objects need protecting

R frees the memory of objects automatically, by garbage collection, and it can run the collector whenever it allocates anything. An object that C code has just created and holds only in a local variable is invisible to the collector: nothing in R’s own data structures refers to it, so the next allocation can free it, and the pointer in the C variable then points at memory that may be reused. The result is not an error but corrupt output or a crash, often much later and somewhere else. PROTECT() puts the object on a stack that the collector treats as a root, and UNPROTECT(n) pops the last n entries. Writing R Extensions states the rule precisely: it is the object that is protected, not the pointer variable, so assigning a different object to p after PROTECT(p) leaves the new object unprotected (Writing R Extensions: Handling the effects of garbage collection).

The protect stack has rules, and the manual lists four of them for functions that cooperate.

  • Balance. PROTECT and UNPROTECT calls must balance in each function, and a function may unprotect only what it protected itself. A jump out of the function (an error, an interrupt) restores the stack automatically.

  • Callers protect arguments. The caller keeps every argument protected for the whole call, which is why .Call() routines do not protect their arguments.

  • Return values are unprotected. An object returned by a function must be protected at once by the caller, even if the callee only returned something that already existed, because it may have been duplicated.

  • Everything allocates. Assume that any API function or macro may allocate and so may trigger a collection; the code that is safe today because a function happens not to allocate can fail after a change in R.

The simplest style follows from them: SEXP x = PROTECT(Rf_allocVector(...)); on creation, one UNPROTECT(n) before every return, with n the number of objects protected in that function. The stack has a fixed size (10,000 entries by default), so a loop must not protect something new on every iteration without releasing it, and the better design is to store objects in a protected container (a list) or to unprotect them immediately after use. callback.c above does exactly that: it protects three objects inside the loop and UNPROTECT(3) at the end of each iteration. Anything allocated and handed straight to SET_VECTOR_ELT() or SET_STRING_ELT() is safe from then on, as loan_stats() shows.

Changing a protected value: PROTECT_WITH_INDEX

The rule that the object is protected, and not the pointer, means that code that replaces a protected object (by coercing, duplicating or growing it) must protect the replacement. When the old object is no longer needed, PROTECT_WITH_INDEX(s, &ipx) records the stack position and REPROTECT(s, ipx) stores a new object in that position, so the stack does not grow. total_days() below coerces an integer argument to double only if it needs to, and keeps whichever object it ends up using protected under one index.

#include <R.h>
#include <Rinternals.h>

/* Bug: one PROTECT too many, so the protect stack is one entry deeper. */
SEXP leaky(SEXP x) {
  SEXP out = PROTECT(Rf_allocVector(REALSXP, 1));
  REAL(out)[0] = Rf_asReal(x) * 2.0;
  return out;
}

/* Bug: one UNPROTECT too many, so the caller's entry is dropped. */
SEXP too_many(SEXP x) {
  SEXP out = PROTECT(Rf_allocVector(REALSXP, 1));
  REAL(out)[0] = Rf_asReal(x) * 2.0;
  UNPROTECT(2);
  return out;
}

/* Correct: the coerced copy replaces the protected value in place. */
SEXP total_days(SEXP x) {
  PROTECT_INDEX ipx;
  SEXP v = x;
  PROTECT_WITH_INDEX(v, &ipx);
  if (TYPEOF(v) != REALSXP) {
    REPROTECT(v = Rf_coerceVector(v, REALSXP), ipx);
  }
  double total = 0.0;
  const double *p = REAL_RO(v);
  for (R_xlen_t i = 0; i < XLENGTH(v); i++) {
    total += p[i];
  }
  UNPROTECT(1);
  return Rf_ScalarReal(total);
}

R_PreserveObject and the other ways to keep an object alive

PROTECT() is for the duration of one call. An object that has to survive between calls (a cache, a handle returned to R as an external pointer) is kept alive with R_PreserveObject(x) and released with R_ReleaseObject(x); the manual calls this less efficient than normal protection and to be used sparingly, because releasing it is then the author’s responsibility, usually from a finalizer. For parsers there is a multi-set interface (R_NewPreciousMSet, R_PreserveInMSet, R_ReleaseFromMSet), and the old UNPROTECT_PTR() is dangerous to mix with UNPROTECT() and is not for new code. External pointers, which wrap a C pointer in an R object with a finalizer, are the way to return a C data structure to R, and have their own section (Writing R Extensions: External pointers and weak references).

#include <R.h>
#include <Rinternals.h>
#include <R_ext/Utils.h>

/* Median of the non-missing days: scratch space from R_alloc. */
SEXP median_days(SEXP days) {
  SEXP d = PROTECT(Rf_coerceVector(days, REALSXP));
  R_xlen_t n = XLENGTH(d);
  const double *p = REAL_RO(d);
  double *buf = (double *) R_alloc((size_t) n, sizeof(double));
  R_xlen_t m = 0;
  for (R_xlen_t i = 0; i < n; i++) {
    if (!ISNAN(p[i])) {
      buf[m++] = p[i];
    }
  }
  double med = NA_REAL;
  if (m > 0) {
    R_rsort(buf, (int) m);
    med = (m % 2 == 1) ? buf[m / 2] : 0.5 * (buf[m / 2 - 1] + buf[m / 2]);
  }
  UNPROTECT(1);
  return Rf_ScalarReal(med);
}

/* The k largest values, in decreasing order: a buffer from R_Calloc. */
SEXP top_days(SEXP days, SEXP k) {
  SEXP d = PROTECT(Rf_coerceVector(days, REALSXP));
  R_xlen_t n = XLENGTH(d);
  int kk = Rf_asInteger(k);
  if (kk == NA_INTEGER || kk < 0) {
    Rf_error("'k' must be a non-negative integer");
  }
  if (kk > n) {
    kk = (int) n;
  }
  double *buf = R_Calloc((size_t) n, double);
  if (n > 0) {
    Memcpy(buf, REAL_RO(d), (size_t) n);
  }
  R_rsort(buf, (int) n);
  SEXP out = PROTECT(Rf_allocVector(REALSXP, kk));
  for (int i = 0; i < kk; i++) {
    REAL(out)[i] = buf[n - 1 - i];
  }
  R_Free(buf);
  UNPROTECT(2);
  return out;
}

The ISBN check as a .Call routine

So far every routine was found by its name, by searching the symbols of the shared object. The rest of the page uses one routine as its running example: the ISBN-13 check of the shelf package. It takes a character vector and returns a logical vector. Its rule is the one is_valid_isbn13() implements in R: keep the digits, reject an X, require exactly 13 digits, and require that the digits multiplied alternately by 1 and 3 add up to a multiple of 10. NA and the empty string are FALSE. The file has a header with the prototype, and starts with #define R_NO_REMAP, so every R function in it carries the Rf_ prefix. The constant ISBN_DIGITS has a default and can be overridden from the compiler command line, which the src/Makevars section uses.

#define R_NO_REMAP
#include <ctype.h>
#include <R.h>
#include <Rinternals.h>
#include "isbn.h"

#ifndef ISBN_DIGITS
#define ISBN_DIGITS 13
#endif

/* One string: keep the digits, reject an X, weight 1 and 3 alternately. */
static int valid_isbn(const char *s) {
  int n = 0, sum = 0;
  for (; *s != '\0'; s++) {
    if (isdigit((unsigned char) *s)) {
      if (n == ISBN_DIGITS) {
        return 0;
      }
      sum += (*s - '0') * (n % 2 == 0 ? 1 : 3);
      n++;
    } else if (*s == 'X' || *s == 'x') {
      return 0;
    }
  }
  return n == ISBN_DIGITS && sum % 10 == 0;
}

/* Vectorised: FALSE for NA, for the empty string and for a wrong check digit. */
SEXP isbn13_valid(SEXP x) {
  if (!Rf_isString(x)) {
    Rf_error("'x' must be a character vector");
  }
  R_xlen_t n = XLENGTH(x);
  SEXP out = PROTECT(Rf_allocVector(LGLSXP, n));
  int *po = LOGICAL(out);
  for (R_xlen_t i = 0; i < n; i++) {
    SEXP el = STRING_ELT(x, i);
    po[i] = el != NA_STRING && valid_isbn(CHAR(el));
  }
  UNPROTECT(1);
  return out;
}

R_registerRoutines and R_init_<name>

Registration replaces the search by a table that the shared object builds when it is loaded. When R loads foo.so, it looks for a function named R_init_foo and calls it with a DllInfo pointer; when it unloads the object, it calls R_unload_foo if there is one. The name is made from the file name without its extension, so it must be a valid part of a C identifier: the manual advises ASCII letters, digits and underscores only. The initialiser calls R_registerRoutines() with five arguments: the DllInfo, and one NULL-terminated array for each interface, in the order .C(), .Call(), .Fortran(), .External(). The array element types are R_CMethodDef, R_CallMethodDef, R_FortranMethodDef and R_ExternalMethodDef. Each entry holds the name by which R refers to the routine, a function pointer cast to DL_FUNC, and the number of arguments; .External() routines use -1 for "any number". The entries for .C() and .Fortran() may add an array of argument types (REALSXP, INTSXP, LGLSXP, STRSXP, VECSXP, SINGLESXP) that R checks on every call.

src/Makevars and the compiler flags

src/Makevars is a makefile fragment that R CMD SHLIB includes before R’s own Makeconf. It is the place for settings that the package needs, and it is not the place for settings that belong to the person or the machine that builds it. The manual lists the variables.

Variable Use

PKG_CPPFLAGS

Preprocessor options for C and C++ files: -I include paths, -D and -U definitions, -include, -pthread. Include paths belong here and not in PKG_CFLAGS or PKG_CXXFLAGS: there a platform include path can take precedence, which has caused hard-to-debug failures.

PKG_CFLAGS, PKG_CXXFLAGS, PKG_FFLAGS, PKG_FCFLAGS

Extra compiler flags for C, C++, fixed-form Fortran and free-form Fortran. PKG_FCFLAGS exists for the rare package that needs different flags for the two Fortran forms.

PKG_LIBS

Linker options: -L and -l for libraries the code uses. Macros from R’s Makeconf are available for numerical code: LAPACK_LIBS, BLAS_LIBS and FLIBS, which must appear in that order; FLIBS is added automatically when the package has Fortran sources.

CXX_STD

The C++ standard: CXX17, CXX20, CXX23 or CXX26 (not a make directive: no quotes, no trailing comment). For C there is no variable; the standard is set in SystemRequirements as USE_C17 or USE_C23 for a package that depends on R (>= 4.3.0).

OBJECTS

The list of object files to build, when the package does not want every source in src/ (for example to include files from subdirectories). If Makevars sets it, R CMD SHLIB does not.

C_VISIBILITY, CXX_VISIBILITY, F_VISIBILITY

Macros from R’s Makeconf that hold the compiler’s flag for hiding symbols; used as PKG_CFLAGS = $(C_VISIBILITY).

SHLIB_OPENMP_CFLAGS, SHLIB_OPENMP_CXXFLAGS, SHLIB_OPENMP_FFLAGS

The OpenMP flags for the compiler R was built with; see below.

Source: Writing R Extensions: Using Makevars

Why a package must not set -Wall

The manual says in so many words not to put compiler-specific diagnostic flags in a distributed Makevars: -O2, -Wall, -pedantic and every other -W flag are specific to GCC and compilers that copy its options (for Oracle’s compilers, -W flags passed arguments to compiler phases). Variables such as CPPFLAGS and CFLAGS themselves must not be set at all, because users and sites set them. R CMD check enforces this. The C++ standard: CXX_STD

R compiles package C++ code with a standard that depends on the R version, and the manual’s advice is to say which standard the code needs. The NEWS entries are: R 4.3.0 changed the default to C++17 where available (C++14 or C++11 otherwise); the manual says that from R 4.4.0 only a C++17 compiler is selected as the default; R 4.6.0 changed the default to C++20 where available, and otherwise C++17, and C++11 and C++14 are no longer supported; and packages can request C++17 if they need it. C standards, and the Fortran and OpenMP variables

For C, R 4.5.0 made the configure script choose a compiler option that selects C23 when one is available (gcc 15 defaults to C23 on its own). The effect on package code is stricter C: bool, true and false are keywords, K&R-style declarations are gone, and an empty parameter list now means no parameters, so code that relied on an unprototyped declaration can stop compiling. A package that cannot move can ask for an older standard with USE_C17 (or USE_C99, USE_C90) in SystemRequirements, and a user can force one when installing with R CMD INSTALL --use-C17; the same option exists for R CMD SHLIB, as its help shows. The __STDC_VERSION__ macro tells which standard the compiler claims (202311L for C23; some compilers used 202000L for a draft), but the manual advises testing for the feature the code needs and not the version (Writing R Extensions: C standards). The Fortran side has its own page in this section, and the Fortran Reference covers the language.

OpenMP is the usual way to use several threads inside compiled code. The compiler flag differs between compilers, so a package takes it from R: it puts $(SHLIB_OPENMP_CFLAGS) in both PKG_CFLAGS and PKG_LIBS for C code (and SHLIB_OPENMP_CXXFLAGS and SHLIB_OPENMP_FFLAGS for the other two languages, with a different recipe for Fortran), guards OpenMP-specific code with #ifdef _OPENMP, and includes the macros only when the code really uses OpenMP. Some toolchains, Apple’s clang among them, have no OpenMP support at all, and a note in the manual says that the C++ macro applies to the default C++ compiler and not necessarily to the one selected for C++17 or C++20, for which a configure check is advised. Writing -fopenmp directly into PKG_CXXFLAGS works with gcc and fails elsewhere, which is why R CMD check has a check named "checking use of SHLIB_OPENMP_*FLAGS in Makefiles" (it appears in the transcript of the earlier section). Calling the R API from threaded code is, in the manual’s words, for experts only and strongly discouraged: the R API changes internal data structures, and errors must be signalled only from the main thread. The threading model of R’s parallel packages is the subject of Parallel and Asynchronous Computing; the manual’s section is OpenMP support.

A .C routine

The convolution of two sequences, the manual’s own example, makes the routine. convolve() takes the two sequences and their lengths as pointers and fills a result array that the caller allocated, since a C function cannot return a vector through .C(); the R wrapper allocates it with double(length(a) + length(b) - 1) and names it so that $ab extracts it from the returned list. The file also registers a second name, convolve_checked, for the same function with its argument types, which is how the type check below is made.

#include <R.h>
#include <Rinternals.h>
#include <R_ext/Rdynload.h>

/* .C passes pointers to copies of the arguments and returns them as a list. */
void convolve(double *a, int *na, double *b, int *nb, double *ab) {
  int nab = *na + *nb - 1;
  for (int i = 0; i < nab; i++) {
    ab[i] = 0.0;
  }
  for (int i = 0; i < *na; i++) {
    for (int j = 0; j < *nb; j++) {
      ab[i + j] += a[i] * b[j];
    }
  }
}

static const R_CMethodDef c_methods[] = {
  {"convolve_checked", (DL_FUNC) &convolve, 5, convolve_types},
  {NULL, NULL, 0, NULL}
};

}

  • A NA, NaN or Inf in an argument is an error: NA/NaN/Inf in foreign function call (arg 1). NAOK = TRUE turns the check off, and the values then reach the C code as they are; the result 1 NA shows that NA * 1 is NA.

  • A mistake in the type is not an error at all. Passing the double 3 where the C code reads an int * makes the C code see the bit pattern of a double, whose low four bytes are zero on a little-endian machine, so na is 0 and the result is 0 0 0 0 instead of 0 1 2 3, with no message. The same mistake with a character string for a double * would read pointer values as numbers. The manual says as much: coerce every argument to the right mode before calling (as.double(), as.integer()).

  • Registering the argument types gives the check: wrong type for argument 2 in call to convolve_checked for the double, and Incorrect number of arguments (4), expecting 5 for 'convolve_checked' for the missing one, naming the routine and both counts. A mismatch between the number of types in the array and the number of arguments cannot be checked by the compiler, so count them.

Detecting writes outside an argument

A fairly common cause of crashes in .C() and .Fortran() code is writing a little beyond the end of an argument, which corrupts something else and crashes R later. options(CBoundsCheck = TRUE) (or the environment variable R_C_BOUNDS_CHECK=yes) changes how R copies the arguments: it adds 64 guard bytes at both ends of each copy and checks them on return. overrun() below has the classic off-by-one, a loop that runs to i <= *n.

/* Bug: the loop runs to i == *n, one element past the end of x. */
void overrun(double *x, int *n) {
  for (int i = 0; i <= *n; i++) {
    x[i] = 0.0;
  }
}

.Fortran: subroutines

.Fortran() calls a Fortran subroutine with the same copy-and-return protocol as .C(), and the same argument table. Three rules are specific to Fortran. All the Fortran compilers R supports map symbol names to lower case, so .Fortran("loan_totals") looks for the lower-case name, and so does registration. Arguments are passed by reference, which is what Fortran expects. And the compiler decorates the symbol (often a trailing underscore); R detects the convention when it is built, which is why the R code never writes the underscore, and why C code that calls Fortran must use the macros F77_NAME, F77_CALL and F77_SUB from R_ext/RS.h, never the underscore. The help page of .Fortran() adds that a Fortran name with an underscore in it is not valid Fortran 77, and its translation can differ between compilers, so the portable advice is to use plain lower-case names (R documentation: .Fortran).

R CMD SHLIB takes .f as fixed-form Fortran (which includes Fortran 77), passing it to the compiler that R was configured with, and .f90 or .f95 as free-form. Both go to the same compiler. The manual’s advice for modern code is to use .f90, to put a requirement in SystemRequirements (for example Fortran 2018) since the standard the compiler accepts is a property of the compiler, and, when the package has several source files that use modules, to tell make the compilation order in src/Makevars, because module files are produced by compiling and make cannot see the dependency. For a module iface used by cmi.f90 and dmi.f90 the line is cmi.o dmi.o: iface.o (Writing R Extensions: Using modern Fortran code). The compile commands for Fortran are the same two lines as for C, with gfortran for the first:

A subroutine for .Fortran

loan_totals adds up the days beyond the loan period and counts the late loans. Every argument is declared with its intent, which is how Fortran says "input" and "output", and the sizes come from the array lengths that R passes in. The -Wall -pedantic flags of the personal Makevars compile it without warnings.

! Total and count of the days beyond the loan period, for .Fortran.
subroutine loan_totals(days, n, limit, late_total, late_count)
  implicit none
  integer, intent(in) :: n
  double precision, intent(in) :: days(n), limit
  double precision, intent(out) :: late_total
  integer, intent(out) :: late_count
  integer :: i

  late_total = 0.0d0
  late_count = 0
  do i = 1, n
    if (days(i) > limit) then
      late_total = late_total + (days(i) - limit)
      late_count = late_count + 1
    end if
  end do
end subroutine loan_totals

Printing, warnings, errors and random numbers from Fortran

Fortran print and write statements to the default unit are not guaranteed to appear in the R console, may not interleave with C output, and on Windows interfere with C’s own output (the manual describes how gfortran’s initialisation changes the line endings of C’s stdout and how to undo it in R_init_<pkg>). R therefore provides subroutines that print through R’s own channels: labelpr(label, nchar) prints a label, intpr1(label, nchar, var), realpr1() and dblepr1() print a labelled scalar, and intpr(), realpr() and dblepr() print a labelled array (label, nchar, data, ndata); nchar is the length of the label, or -1 for all of it. There is no check on the type: a real passed to dblepr prints nonsense. For conditions, rexit(message) signals an error and rwarn(message) a warning (messages are cut to 255 characters), and rchkusr() is the interrupt check. fortran_io.f90 uses all of them.

! Printing, a warning and an error from Fortran through R's own routines.
subroutine summarise(days, n)
  implicit none
  integer, intent(in) :: n
  double precision, intent(in) :: days(n)
  double precision :: mean

  if (n < 1) call rexit("summarise: no loans")
  if (n == 1) call rwarn("summarise: only one loan")
  mean = sum(days) / n
  call labelpr("loan summary", 12)
  call intpr1("loans", 5, n)
  call dblepr1("mean days", 9, mean)
  call rchkusr()
end subroutine summarise

Random numbers are the other thing Fortran code must not do itself. The Fortran 90 random_number and random_seed, GNU’s rand, and the C library’s rand all keep a state that is private to the library: packages cannot initialise it safely, two packages can interfere, and the user’s set.seed() does not reach it. The manual’s rule is to use R’s generator, which a routine reaches by bracketing the draws with GetRNGstate() and PutRNGstate() and calling unif_rand() (or norm_rand(), exp_rand()), and it shows how to bind those C entry points from Fortran with iso_c_binding (Writing R Extensions: Random-number generation from Fortran). rngdemo.f90 does this without a line of C.

! Random loan lengths drawn from R's own generator (so set.seed() applies).
subroutine random_loans(n, longest, out)
  use iso_c_binding, only: c_double
  implicit none
  interface
    subroutine get_rng_state() bind(C, name = "GetRNGstate")
    end subroutine get_rng_state
    subroutine put_rng_state() bind(C, name = "PutRNGstate")
    end subroutine put_rng_state
    function unif_rand() bind(C, name = "unif_rand") result(u)
      import :: c_double
      real(c_double) :: u
    end function unif_rand
  end interface
  integer, intent(in) :: n
  double precision, intent(in) :: longest
  double precision, intent(out) :: out(n)
  integer :: i

  call get_rng_state()
  do i = 1, n
    out(i) = ceiling(longest * unif_rand())
  end do
  call put_rng_state()
end subroutine random_loans

Modern Fortran through .C and bind©

For Fortran 90 and later code the help page of .Fortran() and the manual give the same advice: the most portable way is to give the subroutine a C interface with iso_c_binding and call it with .C(). ! ISBN-13 check digit from the first twelve digits, callable through .C.
subroutine isbn_check_digit(digits, check) bind(C, name = "isbn_check_digit")
  use iso_c_binding, only: c_int
  implicit none
  integer(c_int), intent(in) :: digits(12)
  integer(c_int), intent(out) :: check
  integer :: i, total

  total = 0
  do i = 1, 12
    if (mod(i, 2) == 1) then
      total = total + digits(i)
    else
      total = total + 3 * digits(i)
    end if
  end do
  check = mod(10 - mod(total, 10), 10)
end subroutine isbn_check_digit

Registering a Fortran routine

A registered .Fortran() routine needs a prototype in C, because the registration table is C. Character strings and logicals between C and Fortran

Two kinds of argument are not portable and need a special mention, and both are covered in the manual’s section on calling C from Fortran and vice versa.

  • Character strings. A Fortran string is an array of bytes plus a hidden length argument; a C string is NUL-terminated. Since 2019 gfortran passes the hidden length at the end of the argument list as a size_t (backported to gfortran 7 and 8), and code that ignored it broke. R defines the macro USE_FC_LEN_T and the type FC_LEN_T in Rconfig.h to match: a C routine called from Fortran declares the extra FC_LEN_T msg_len argument, and C code that calls a BLAS or LAPACK routine with character arguments (such as dgemm("N", "T", ...)) appends FCONE for every character argument, with no comma. USE_FC_LEN_T became the default in R 4.3.0, and packages that call BLAS or LAPACK with character arguments fail to install without the adjustment. The alternative is to avoid the problem, by passing integer codes instead of strings or by writing the interface with iso_c_binding (Writing R Extensions: Fortran character strings).

  • Logicals. Fortran LOGICAL has no guaranteed size. In practice it is a 32-bit integer, and int * is the traditional C equivalent, but recent gfortran says int_least32_t *. The simplest design is to pass integers and convert in a Fortran wrapper (Writing R Extensions: Fortran LOGICAL).

Passing C functions to Fortran as arguments (callbacks) depends on the two compilers agreeing on the calling convention and has failed in practice; the manual’s most portable suggestion is to convert the Fortran to C. For everything about the Fortran language and about calling it from C, C++ and Python, the Fortran Reference section added by issue #277 has the pages Interoperability with C, Calling Fortran from C, C++ and Python and BLAS, LAPACK and Numerical Libraries, and the C build and tooling page explains the compilers and linkers involved.

.External: arguments as a pairlist

.External() differs from .Call() in one respect: the C function receives a single SEXP, a pairlist whose first cell holds the name of the routine and whose remaining cells are the arguments. That removes the limit of 65 arguments and gives the C code the argument names (the "tags"), which is what makes a function with ... natural to write. The walk over the list uses the Lisp-style macros: CDR(args) is the rest of the list, CAR(args) the current argument, TAG(args) its name as a symbol (or R_NilValue), and PRINTNAME() turns a symbol into a CHARSXP. CADR, CADDR, CADDDR and so on read the first few arguments by position, and SETCAR() and its relatives modify a cell. The first cell is skipped with args = CDR(args). When registering .External() routines, the argument count is -1, which tells R not to check it.

#include <R.h>
#include <Rinternals.h>

/* .External: the arguments arrive as one pairlist; the first cell is the name. */
SEXP total_days_ext(SEXP args) {
  args = CDR(args);
  double total = 0.0;
  for (; args != R_NilValue; args = CDR(args)) {
    SEXP el = CAR(args);
    if (!Rf_isNumeric(el)) {
      Rf_error("every argument must be numeric");
    }
    SEXP v = PROTECT(Rf_coerceVector(el, REALSXP));
    for (R_xlen_t i = 0; i < XLENGTH(v); i++) {
      total += REAL(v)[i];
    }
    UNPROTECT(1);
  }
  return Rf_ScalarReal(total);
}

/* The tags (argument names) of the call, "" for unnamed arguments. */
SEXP arg_names(SEXP args) {
  args = CDR(args);
  int n = Rf_length(args);
  SEXP out = PROTECT(Rf_allocVector(STRSXP, n));
  for (int i = 0; i < n; i++, args = CDR(args)) {
    if (TAG(args) == R_NilValue) {
      SET_STRING_ELT(out, i, Rf_mkChar(""));
    } else {
      SET_STRING_ELT(out, i, PRINTNAME(TAG(args)));
    }
  }
  UNPROTECT(1);
  return out;
}

C++ without Rcpp

C++ code reaches R through the same C interfaces, with three differences: the entry points need C linkage, the R headers need care, and a C++ exception must never cross the boundary. The manual’s own example is a C++ library of two classes that is made callable by writing a wrapper function inside extern "C" { } and building with R CMD SHLIB (which links with the C++ compiler because there is a C++ source file); the same page warns that C++ iostreams should not be used for output, because nothing guarantees that the text reaches the R console, and that R’s own entry points (Rprintf()) should be used instead (Writing R Extensions: Interfacing C++ code). The C++ Reference page on program structure and compilation explains extern "C" and name mangling.

The three points in practice:

  • Linkage. .Call() looks up a C symbol, but the C++ compiler mangles names. A function called from R must be declared extern "C". The header files of R can be included from C++ but not inside an extern "C" block, because they include system headers.

  • Header order and R_NO_REMAP. Include the C++ standard headers before the R headers, and use the Rf_ names, because since R 4.5.0 R_NO_REMAP is always defined for C++ (an earlier section). Several R short names (length, error) collide with identifiers in the standard library.

  • Exceptions and longjmp. Rf_error() unwinds the stack with a longjmp, which skips the destructors of C++ objects between the call and the catching R frame: a std::vector or std::string alive at that moment leaks. A C++ exception must not be allowed to propagate out of an extern "C" function into R’s C code. The safe pattern is to catch all exceptions inside the C++ code, copy the message into a plain character buffer, let every C++ object go out of scope, and only then call Rf_error(). For C++ code that must run destructors when an R error unwinds the stack, R offers R_UnwindProtect() with a continuation token (R_MakeUnwindCont() and R_ContinueUnwind()), which the manual describes as suitable for C++ stack unwinding (Writing R Extensions: Condition handling and cleanup code).

cxx_median.cpp follows the safe pattern. The vector, the sort and the exception live in an anonymous-namespace function that returns a status; the extern "C" function holds only plain C data when it calls Rf_error().

#define R_NO_REMAP
#include <algorithm>
#include <cstdio>
#include <stdexcept>
#include <vector>
#include <R.h>
#include <Rinternals.h>

namespace {

// All the C++ lives here; no exception leaves this function.
// Returns 0 on success, 1 after copying an error message into msg.
int median_impl(const double *x, R_xlen_t n, double *result, char *msg,
                std::size_t msg_size) {
  try {
    std::vector<double> v;
    for (R_xlen_t i = 0; i < n; ++i) {
      if (!ISNAN(x[i])) {
        v.push_back(x[i]);
      }
    }
    if (v.empty()) {
      throw std::invalid_argument("no non-missing values");
    }
    std::sort(v.begin(), v.end());
    std::size_t m = v.size();
    *result = m % 2 == 1 ? v[m / 2] : 0.5 * (v[m / 2 - 1] + v[m / 2]);

Rcpp: R objects as C++ classes

Rcpp (version 1.1.2 here) is a package of C++ headers and a small runtime that wraps R’s C API in classes. A numeric vector is a NumericVector, a list a List, a data frame a DataFrame, an R function a Function; conversion between R and C++ types happens at the boundary, PROTECT() is done by the object’s constructor and destructor, and a C++ exception thrown in your code becomes an R error. The project’s own site describes it as an interface that maps the key R data types to C++ data structures, says that it makes it easy to create a first example with cppFunction(), and reports that it is used by over 3000 packages on CRAN (Rcpp website). Rcpp is community-maintained software outside the R core, not a base package: the reference below is the package’s own documentation, the CRAN package page and the vignettes that come with it (among them the introduction, attributes, sugar and package vignettes cited below); the Rcpp Gallery (https://gallery.rcpp.org/) is community material with examples of a wide range of tasks, and is named here only as such.

What Rcpp removes

The .Call() routines of the earlier sections have a lot of ceremony that is the same each time: the SEXP signature, the coercion, the allocation, the PROTECT() and UNPROTECT() bookkeeping, the loop over REAL(x), the wrapper that attaches the attributes, the registration table and the R_init function, and the R function that calls .Call(). Rcpp attributes generate all of them. A C++ function whose signature uses Rcpp types and which is marked with // [[Rcpp::export]] is turned into an R function with the same name and arguments, including default values; the glue is generated into a pair of files in a package (RcppExports.cpp and RcppExports.R) or compiled on the fly by cppFunction() and sourceCpp().

sourceCpp() and a file of exports

sourceCpp("file.cpp") does the same for a file that may define many functions and helpers. It parses the file for // [[Rcpp::export]] attributes (and for RCPP_MODULE declarations), builds a shared library in a temporary directory (the build is cached, and only redone when the file changes unless rebuild = TRUE), and defines the exported functions in the calling environment. /*** R blocks in the file are R code that runs after compilation, which turns the C++ file into a self-testing script. Attributes also exist for dependencies (// [[Rcpp::depends(RcppArmadillo)]] adds the include path and flags of a package) and for plugins (// [[Rcpp::plugins(cpp17)]] requests a standard; the installed plugins include cpp11 to cpp26, openmp and unwindProtect). Its help page lists the other arguments: embeddedR, cacheDir, showOutput, verbose, dryRun and echo (Rcpp package documentation: sourceCpp). The help page also says that sourceCpp() is for one file whose only dependencies are R packages; for more files or external libraries, make a package.

loans.cpp has five exported functions. overdue_days_loop() is the C++ version of the loop of vectors.c; overdue_days_sugar() is the same job in one sugar expression; loan_stats() builds the classed list of structures.c in one expression; flag_late() takes a data frame and returns a data frame with a logical column; and mean_days() writes to Rcout, warns and stops. Nothing in the file mentions SEXP, PROTECT or .Call.

#include <Rcpp.h>
using namespace Rcpp;

// Days beyond the loan period, written as a loop; NA and NaN pass through.
// [[Rcpp::export]]
NumericVector overdue_days_loop(NumericVector days, double limit = 21) {
  R_xlen_t n = days.size();
  NumericVector out(n);
  for (R_xlen_t i = 0; i < n; ++i) {
    if (NumericVector::is_na(days[i])) {
      out[i] = days[i];
    } else {
      out[i] = days[i] > limit ? days[i] - limit : 0.0;
    }
  }
  out.attr("names") = days.attr("names");
  return out;
}

// The same result from Rcpp sugar: vectorised expressions, as in R.
// [[Rcpp::export]]
NumericVector overdue_days_sugar(NumericVector days, double limit = 21) {
  return ifelse(days > limit, days - limit, 0.0);
}

// [[Rcpp::export]]
List loan_stats(NumericVector days) {
  NumericVector seen = days[!is_na(days)];

    _["n"] = seen.size(),

    _["max"] = seen.size() > 0 ? max(seen) : NA_REAL
  );
  out.attr("class") = "loan_stats";

}

// [[Rcpp::export]]
DataFrame flag_late(DataFrame loans, double limit = 21) {
  CharacterVector member = loans["member"];
  NumericVector days = loans["days"];

  for (R_xlen_t i = 0; i < days.size(); ++i) {
    late[i] = NumericVector::is_na(days[i]) ? NA_LOGICAL : days[i] > limit;
  }
  return DataFrame::create(
    _["member"] = member, _["days"] = days, _["late"] = late
  );
}

// [[Rcpp::export]]
double mean_days(NumericVector days) {
  if (days.size() == 0) {
    stop("no loans");
  }
  if (is_true(any(is_na(days)))) {

  }

Errors, warnings and output

Rcpp::stop("no loans") throws a C++ exception, the wrapper that Rcpp generates around every exported function catches it and calls R’s error machinery, and the result is an ordinary R error whose message is the text. It is a condition of class Rcpp::exception, C++Error, error, condition, as the last line of the output of the script shows, so tryCatch(..., error = ) handles it and conditionMessage() returns no loans. A C++ exception derived from std::exception is converted the same way, with the text of what(). Rcpp::warning() signals an R warning that withCallingHandlers() can handle, and Rcout writes through R’s output, so capture.output() and sink() see it. In the script, mean_days(c(14, 35)) prints averaging 2 loans through Rcout and returns 24.5; with c(14, NA, 35) the calling handler prints caught: missing days are ignored to the message stream and muffles the warning, and the function carries on and averages the two known values; and with numeric() the error is caught. Rcpp can also use R_UnwindProtect() so that C++ destructors run when an R error unwinds the stack, and has a plugin named unwindProtect for it.

#include <Rcpp.h>
using namespace Rcpp;

// Keep the digits, reject an X, weight 1 and 3 alternately.
static bool valid_isbn(const std::string& s) {
  int n = 0, sum = 0;
  for (char c : s) {
    if (c >= '0' && c <= '9') {
      if (n == 13) {
        return false;
      }
      sum += (c - '0') * (n % 2 == 0 ? 1 : 3);
      ++n;
    } else if (c == 'X' || c == 'x') {
      return false;
    }
  }
  return n == 13 && sum % 10 == 0;
}

How much faster? A measurement

Whether any of this pays is a question of numbers. The script compares four implementations of the overdue-days function on a million simulated loan durations: an R for loop, the vectorised R expression pmax(days - limit, 0), the .Call() routine from vectors.c and a cppFunction() loop. bench::mark() checks that all four return the same result before timing them. Timings depend on the machine, the compiler flags and what else is running, so the script prints only the order of magnitude of each median relative to the fastest, as round(log10(ratio)); the exact ratios, which vary from run to run, are not shown. Performance, Profiling and Benchmarking explains how to measure with bench and microbenchmark.

# Built with `R CMD SHLIB vectors.c`. The same job four ways on a million
# simulated loan lengths: compare the ratios, not the seconds.
library(Rcpp)
dyn.load(paste0("vectors", .Platform$dynlib.ext))

set.seed(2026)
days <- round(runif(1e6, 1, 60))

overdue_r_loop <- function(days, limit = 21) {
  out <- numeric(length(days))
  for (i in seq_along(days)) {
    out[[i]] <- if (days[[i]] > limit) days[[i]] - limit else 0
  }
  out
}
overdue_r_vector <- function(days, limit = 21) pmax(days - limit, 0)
overdue_c <- function(days, limit = 21) {
  .Call("overdue_days", days, limit, PACKAGE = "vectors")
}
overdue_cpp <- cppFunction("
NumericVector overdue_cpp(NumericVector days, double limit = 21) {
  NumericVector out(days.size());
  for (R_xlen_t i = 0; i < days.size(); ++i) {
    out[i] = days[i] > limit ? days[i] - limit : 0.0;
  }
  return out;
}")

b <- bench::mark(
  r_loop = overdue_r_loop(days),
  r_vector = overdue_r_vector(days),
  c_call = overdue_c(days),
  rcpp = overdue_cpp(days),
  min_iterations = 20
)
rel <- summary(b, relative = TRUE)
data.frame(
  expression = as.character(rel$expression),
  orders_of_magnitude_slower = round(log10(rel$median / min(rel$median)))
)

The result is the useful lesson. The plain R for loop is about one order of magnitude slower than compiled code here. It is byte-compiled by the JIT (see Vectorisation and Iteration), which is why the gap is a factor of ten or twenty and not larger. The vectorised R expression, which runs in R’s own compiled code, is within a factor of about three of the .Call() routine and the Rcpp function, which is the resolution of this measurement. Compiled code won over the loop and not over the right R expression. That is the usual outcome for work that a vectorised built-in can already do, and the reason to reach for C, C++ or Fortran for a loop that cannot be vectorised, and not for one that can.

Debugging compiled code

The R debugger of Debugging sees interpreted code only: browser() and debug() stop at R lines, and a .Call() is a single step. Debugging compiled code uses the tools of the language, and the manual’s chapter on debugging collects the R-specific tricks (Writing R Extensions: Debugging compiled code).

  • A crash prints a traceback. On Unix-alikes R installs a signal handler. A segmentation fault or illegal instruction prints *** caught segfault ***, the address, the R-level traceback and a menu of possible actions. Since the process may be damaged, the manual says the only really safe choices are to abort or to exit without saving the workspace.

  • Run R under the debugger. R -d gdb --vanilla starts R under gdb; on macOS the debugger is lldb (R -d lldb), and the manual has a separate section on its hurdles there. A breakpoint cannot be set in code that is not loaded yet, so the manual’s recipe is: start R under the debugger, dyn.load() or library() the shared object, send an interrupt to return to the debugger prompt, set the breakpoints, and continue with signal 0. Build with -g -O0 (in a personal Makevars) so that the debugger can step through the source; pkgload::load_all() does so by default. gdb -p <pid> attaches to a running R, and Sys.getpid() gives the pid.

  • Look at R objects from the debugger. Rf_PrintValue(s) prints an object with R’s own printing; R_PV(s) prints only objects. From gdb, p R_PV(ab) prints the object ab (Writing R Extensions: Inspecting R objects when debugging). The R FAQ has two short entries on exactly this: how to debug dynamically loaded code and how to inspect R objects when debugging (R FAQ 8.2: How can I debug dynamically loaded code? and R FAQ 8.3: How can I inspect R objects when debugging?).

  • Catch memory errors early. gctorture(TRUE) finds missing PROTECT() calls; R -d valgrind --vanilla < script.R (and --tool=memcheck --leak-check=full) checks reads of uninitialised memory and writes outside allocated blocks, with false positives that the manual explains; and R can be built with the address sanitizer and the undefined-behaviour sanitizer, which catch the same errors and some more (Writing R Extensions: Checking memory access). options(CBoundsCheck = TRUE) is the cheap test for .C() and .Fortran() overruns, shown above. Fortran has its own array bounds checking: put gfortran’s -fbounds-check in FFLAGS in the personal Makevars while checking.

  • Rprintf and the other print debugging. Still the most used. Rprintf() and Rf_PrintValue() insert into the code; a C++ std::cout should not be used for it.

  • Profiling compiled code. The R profiler (Rprof) sees a .Call() as one line. Where time goes inside it is a question for the system profilers (perf on Linux, Instruments on macOS, Very Sleepy on Windows), which the manual’s section on profiling compiled code describes, with the caveat that it is based on user reports and may not be current (Writing R Extensions: Profiling compiled code).

On Windows the equivalent is gdb from Rtools with a debug build of R and of the package (Rcmd INSTALL --debug); the details are in the R for Windows FAQ (R for Windows FAQ 8.4: How do I debug code that I have compiled and dyn.load-ed?).

Portability rules for compiled code

The manual’s chapter on writing portable packages has a section for C and C++ code, and one for Fortran, whose rules are the difference between a package that installs everywhere and one that works on the author’s machine. The points that concern code written for this page’s interfaces:

  • Never end the process. Compiled code must not call abort() or exit(), which kill the user’s R session and its unsaved work. This includes assert(), which is active unless NDEBUG is defined; R CMD INSTALL defines it, which is why the debug flags of load_all() start with -UNDEBUG. Fortran code must not call STOP or EXIT.

  • Do not write to stdout or stderr. Use Rprintf() and REprintf(), or the Fortran print routines of R. C++ and Fortran I/O should not be used.

  • Do not use the system random number generators (rand, drand48, random, Fortran random_number, the C++11 <random> library, or third-party generators such as GSL’s). Use R’s through GetRNGstate(), unif_rand() and PutRNGstate(), so that set.seed() works and packages do not interfere.

  • Mind the sizes of types. long is 32 bits on some R platforms (64-bit Windows) and 64 on most Unix. Use int, R_xlen_t, size_t or a typedef chosen by a configure test; use intptr_t for pointers stored in integers. A Fortran integer is a C int on all R platforms; a Fortran logical is not guaranteed to be.

  • Avoid -march=native and other flags that produce code for the build machine’s CPU only, and avoid sprintf() and vsprintf(), which R CMD check reports; use snprintf().

  • Include the R headers in the right order (system headers first) and never inside extern "C".

The C API: what a package may call

R has a very large number of entry points in its executable and shared library, and most of them are not for packages. The manual divides them into three classes. The API is the set that is documented in Writing R Extensions and declared in an installed header file: packages can use it, and it is changed only after deprecation. Public entry points are declared in an installed header and exported on all platforms, but are not documented and can change without notice: they must not be used in distributed code, and their declarations will eventually be moved out of the installed headers. Private entry points are used to build R and are not declared in the installed headers at all. What R CMD check calls "non-API" is everything outside the first class.

The header files follow the same division. R.h includes the commonly used headers from R_ext/ (Arith.h, Error.h, Memory.h, Print.h, Random.h, RS.h and Utils.h); Rinternals.h declares the SEXP machinery used by .Call(); Rmath.h is R’s standalone math library; Rdynload.h (in R_ext/) is what registration needs; R_ext/Altrep.h is for packages that implement their own alternate representation of vectors, like R’s compact integer sequences; R_ext/BLAS.h and R_ext/Lapack.h declare the linear algebra routines. Headers not listed there are not part of the API, and the manual notes that Rdefines.h, an S-style macro layer, is no longer maintained (Writing R Extensions: Organization of header files).

What changed in R 4.5.0 and 4.6.0

R has been tightening the API in steps, and the NEWS files of R 4.5.0 and 4.6.0 list them. The facts that matter for a package author, in the order they happened:

  • R 4.5.0 added a section to Writing R Extensions, "Moving into C API compliance", to help authors move from non-API entry points to API ones; it will keep being updated. It made strict R headers the default, so the legacy definitions PI, Calloc, Realloc and Free are gone. It made R_NO_REMAP the default for C++. It added many functions that replace non-API ones (R_mkClosure, R_ClosureFormals, R_ClosureBody, R_ClosureEnv, R_ParentEnv, R_getVar and R_getVarEx, Rf_isDataFrame, Rf_charIsASCII and more, Rf_asRboolean). It lengthened the list of non-API entry points that R CMD check reports, and upgraded some of the NOTEs to WARNINGs, as preparation for removing the declarations and hiding the entry points where possible. A C23 compiler is selected by default where available.

  • R 4.6.0 removed declarations from the installed headers: the functions LOGICAL0, INTEGER0, REAL0, COMPLEX0 and RAW0, DATAPTR, VECTOR_PTR, Rf_isFrame (use Rf_isDataFrame), and the header R_ext/PrtUtil.h is no longer copied to the installed include directory. It marked a long list of further entry points as hidden and without declarations (ENVFLAGS, FRAME, ENCLOS, HASHTAB, IS_S4_OBJECT, LEVELS, NAMED, OBJECT, SETLENGTH, TRUELENGTH, SET_BODY and others). It upgraded to WARNINGs the check results for further non-API functions (including BODY, FORMALS, CLOENV, SET_TYPEOF, STRING_PTR, ATTRIB, SET_ATTRIB, Rf_findVarInFrame3, R_nchar and Rf_GetOption), and made the use of any non-API variable a check NOTE. And it added replacements: R_mapAttrib, R_getAttributes, R_class, R_nrow, R_ncol and a new experimental API for variable bindings.

  • R-devel (4.7.0) has no C-level entry in its NEWS section at the time of writing.

Toolchain notes that affect compliance

Two toolchain facts interact with all this. First, the default C standard is C23 on R 4.5.0 and later where the compiler supports it, which rejects implicit function declarations and K&R-style definitions, so older C code needs fixing or USE_C17; and the default C++ standard is C++20 from R 4.6.0, which has removed some library features that C++17 still has (the manual gives std::uncaught_exception as an example and warns that some compilers accept removed features in C++17 mode). Second, Rtools is versioned with R: Rtools45 serves R 4.5.0 and every later R including R-devel, so the Windows toolchain of this page is the same GCC 14.2 for R 4.5 and 4.6; the version history is in the next section. R CMD config prints the compiler settings that R will use, and a CI job that checks packages on Windows, macOS and Linux with the current release and R-devel finds toolchain differences before CRAN’s checks do. How packages are checked and submitted is the subject of Publishing to CRAN.
