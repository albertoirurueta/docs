Syntax and Lexical Structure

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. This page is about the smallest unit of R that a programmer reads and writes: the text of the language itself. It follows the parser from the characters in a file to the tokens, the expressions and the function calls that the evaluator finally runs, and it shows what R says when that text is wrong. Every example uses only base R (the base and utils packages that ship with R), so no add-on package version needs to be stated; the lintr 3.4.0 default linters were used only to check the scripts.

Every example below is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines starting with #> are what it printed. The scripts also pass the default lintr linters; where an idiom being shown is exactly what a default linter dislikes (T, x<-7, a non-snake-case name, a semicolon), the line carries a # nolint: comment so that the linter does not hide the lesson. The names books, loans and loan_days come from the running library-shelf scenario described on the section index: a script either reads books.csv with read.csv() or starts with source("scenario.R"). The first page, Getting Started, shows how to install R and run a script.

From text to value: what the parser does

The R Language Definition puts the whole mechanism in one chapter. The parser converts the textual representation of R code into an internal form, and that internal form is itself an R object that can be saved and manipulated (R-lang: Parser). Reading a program therefore has three stages, which map onto the sections of this page.

Stage What happens Where it is covered below

Lexical analysis

The characters are split into tokens: constants, identifiers, operators, brackets and separators. Whitespace and comments are discarded.

Tokens, names, reserved words, literals

Parsing

The tokens are grouped into expressions by the grammar. The result is a tree of function calls, held in an object of type expression (a vector of expressions) or call.

Expressions, newlines and blocks; the parse tree

Evaluation

The evaluator walks the tree. This is the stage that can fail with an "object not found" or "non-numeric argument" error.

Not covered here; see Lazy Evaluation and Promises

Source: The R Language Definition: The parsing process

A syntax error belongs to the second stage and is therefore found before any code runs; an evaluation error belongs to the third. The manual lists three modes of parsing. The read-eval-print loop reads input until a complete expression is available (the continuation prompt, + by default, means the parser expects the rest of an incomplete expression). Text files are parsed by parse() and, through it, by source(), which parses and checks the entire file before evaluating anything. Character strings are parsed by parse(text = ...), treating each element as a line of a file (R-lang: Modes of parsing). The first consequence is shown by the following script: the valid first line of a file does not run if a later line has a syntax error, while the console, which parses one line at a time, runs it.

# source() and parse() read the whole text before anything is evaluated, so a
# syntax error on the last line stops the first line from running.
script <- c(
  "cat(\"step one ran\\n\")",
  "step_two <- 2",
  "oops oops"
)
tryCatch(
  source(textConnection(script)),
  error = \(e) writeLines(conditionMessage(e))
)
#> textConnection(script):3:6: unexpected symbol
#> 2: step_two <- 2
#> 3: oops oops
#>         ^
exists("step_two")
#> [1] FALSE

# Parsing the lines one at a time, as the console does, runs the valid ones.
for (line in script) {
  tryCatch(
    eval(parse(text = line)),
    error = \(e) writeLines("syntax error on this line")
  )
}
#> step one ran
#> syntax error on this line
exists("step_two")
#> [1] TRUE

Source: R documentation: source

This is also why a long script that fails with "unexpected symbol" on its last line has not done any work, whereas a script that fails with "object not found" has done everything before that line. When a script misbehaves the first question is which of the two stages produced the message; the next sections describe each token class so that the message can be read.

The operator list of the manual predates a few operators. The help page ?Syntax lists the current set in precedence order, adds ::, :::, @, |>, &&, ||, ->>, <<- and the help operator ?, and warns that there are substantial precedence differences between R and S (R documentation: Syntax). The precedence table itself, and the reasons for it, are the subject of Operators and Precedence; this page only needs the fact that every one of those operators is a token that the lexer recognises.

Whitespace as a separator

Whitespace (spaces, tabs and form feeds; on Windows and in UTF-8 locales also other Unicode whitespace characters) serves to delimit tokens when there would otherwise be an ambiguity. The manual’s own example compares x<-5 and x < -5: the first is an assignment of 5 to x, the second is a comparison with minus five (R-lang: Separators). Beyond that, extra whitespace is not significant: R accepts a space before the opening parenthesis of a call or the opening bracket of an index, and indentation carries no meaning, unlike Python.

# Whitespace separates tokens only when the tokens would otherwise run together.
x <- 5
x
#> [1] 5
x < -5 # nolint: infix_spaces_linter.
#> [1] FALSE
x<-7 # nolint: infix_spaces_linter.
x
#> [1] 7

# Spaces before "(" and "[" are allowed, though unusual.
sum (1, 2) # nolint: function_left_parentheses_linter.
#> [1] 3
x [1] # nolint: brace_linter, spaces_inside_linter.
#> [1] 7

# A comment runs from "#" to the end of the line,
# unless the "#" is inside a string.
y <- 1 # This is a comment...
z <- "  #... but this is not."
z
#> [1] "  #... but this is not."

# The parser reports tokens and their kinds: getParseData() lists them.
exprs <- parse(text = "total <- price * 2L # double", keep.source = TRUE)
parse_data <- getParseData(exprs)
terminals <- parse_data[parse_data$terminal, c("token", "text")]
terminals
#>         token     text
#> 1      SYMBOL    total
#> 2 LEFT_ASSIGN       <-
#> 4      SYMBOL    price
#> 5         '*'        *
#> 7   NUM_CONST       2L
#> 9     COMMENT # double

# The "#line" directive changes the line number the parser reports.
code <- c(
  "#line 100 \"shelf.R\"",
  "a <- 1",
  "b b"
)
tryCatch(
  parse(text = code, keep.source = FALSE),
  error = \(e) writeLines(conditionMessage(e))
)
#> shelf.R:101:3: unexpected symbol
#> 100: a <- 1
#> 101: b b
#>        ^

Source: The R Language Definition: Separators

getParseData() is the window onto the lexer: it returns one row per token, with the token kind (SYMBOL, LEFT_ASSIGN, NUM_CONST, COMMENT, and so on) and its text. It needs the source to be kept, which is why the call passes keep.source = TRUE. The COMMENT row shows that comments are tokens for tooling such as styler and lintr, even though the evaluator never sees them. The options() entry keep.parse.data controls whether parse data is stored with the source (default TRUE), and keep.source defaults to interactive(), so it is TRUE in a console session and FALSE under Rscript (R documentation: options).

Comments and the #line directive

A comment starts at a # outside a quoted string and runs to the end of the line. The parser ignores it. R has no block-comment syntax, so a block is commented line by line (editors do this with one shortcut), and the first line #!/usr/bin/env Rscript of an executable script is just a comment for the parser. The roxygen2 documentation comments that start with #' are comments too: they matter only to the roxygen2 package, which reads the file as text.

The only directive the parser supports is #line. It is the same idea as the C preprocessor directive: it tells the parser that the following line is line nn of the file "filename", so that diagnostics point to the original source when a preprocessor generated the R code. Unlike C, the directive must be the first five characters of the line, the file name needs double quotes, and any text after it is a comment (R-lang: Directives). The last chunk of the script above shows it: after #line 100 "shelf.R" the error is reported at line 101 of shelf.R. It is rarely used by people, but it explains why an error message can name a file that does not exist on disk.

Source: The R Language Definition: Comments

Identifiers and syntactic names

An identifier is a sequence of letters, digits, the period and the underscore. It must not start with a digit or an underscore, nor with a period followed by a digit. What counts as a letter depends on the locale: the manual gives the C expression isalnum(c) || c == '.' || c == '_', which includes accented letters in many Western European locales, while only the ASCII digits 0-9 are digits (R-lang: Identifiers). An identifier that is also not a reserved word is a syntactic name and can be used directly in code. Names that start with a period are not listed by ls() unless all.names = TRUE.

The five meanings of "name"

The R FAQ spends an entry on the word, because the language uses it in five related senses, and only some of them are restricted to syntactic names (R FAQ 7.14: What are valid names?).

Kind of name Rule

Syntactic name

What the parser reads as a symbol: letters, numbers, . and _, starting with a letter or a dot not followed by a number. Reserved words are not syntactic names.

Object name

A string associated with an object by assignment or by assign(). Usually syntactic, but any non-empty string works when quoted (and it is always quoted in assign()).

Argument name

What appears left of = in a call such as f(trim = .5). Usually syntactic, but anything when quoted.

Element name

Identifies a piece of an object, for example a list component. After $ it must be syntactic or quoted; otherwise any string is allowed.

File name

A string for the operating system. Nothing to do with names in the language.

Source: R FAQ 7.14: What are valid names?

The practical consequence is the pair of rules that the next script exercises: a non-syntactic name is reached with backticks (or, in a few positions, with a string), and make.names() turns arbitrary text into a syntactic name.

make.names and backticks

make.names(names, unique = FALSE, allow_ = TRUE) makes syntactically valid names out of character vectors. It prepends X when the first character is not allowed, translates every invalid character to ., translates a missing value to "NA", appends a dot to names that match R keywords, and (with unique = TRUE) makes duplicates distinct through make.unique(). The allow_ argument exists only for compatibility with R before 1.9.0, when underscores were not valid in names; allow_ = FALSE is still useful when exporting names to an application that rejects underscores (R documentation: make.names). data.frame() and read.table()/read.csv() call it through their check.names = TRUE argument, which is why a column read as Loan ID is called Loan.ID and one called 1st loan becomes X1st.loan.

The preferred way to quote a non-syntactic name is the backtick; deparse() normally uses it, and under many circumstances single or double quotes can be used instead because a character constant is often converted to a name. Backticks may be essential to delimit variable names in formulae (R documentation: Quotes).

books <- read.csv("books.csv")

# make.names() repairs strings that are not syntactic names.
raw_names <- c("title", "pages in hundreds", "1st edition", "if", "_id",
               ".2way", "Author's", NA, "", "page.count", "ISBN-13")
make.names(raw_names)
#>  [1] "title"             "pages.in.hundreds" "X1st.edition"
#>  [4] "if."               "X_id"              "X.2way"
#>  [7] "Author.s"          "NA."               "X"
#> [10] "page.count"        "ISBN.13"
raw_names == make.names(raw_names)
#>  [1]  TRUE FALSE FALSE FALSE FALSE FALSE FALSE    NA FALSE  TRUE FALSE

# unique = TRUE makes the results distinct; allow_ = FALSE turns "_" into ".".
make.names(c("a and b", "a-and-b"), unique = TRUE)
#> [1] "a.and.b"   "a.and.b.1"
make.names(c("a and b", "a_and_b"), unique = TRUE, allow_ = FALSE)
#> [1] "a.and.b"   "a.and.b.1"
make.names(c("", "X"), unique = TRUE)
#> [1] "X.1" "X"

# Every reserved word gets a dot appended; non-ASCII letters survive in a
# UTF-8 locale.
make.names(c("TRUE", "NULL", "NA_integer_", "function", "Inf", "next"))
#> [1] "TRUE."        "NULL."        "NA_integer_." "function."    "Inf."
#> [6] "next."
make.names(c("café", "naïve name"))
#> [1] "café"       "naïve.name"

csv_text <- c("Loan ID,member name,1st loan,if", "L001,Ana Ruiz,2025-01-07,yes")

assign("books$title", "not a column") # nolint: object_name_linter.

#> [1] "not a column"

is_syntactic <- function(x) x == make.names(x)

#>  TRUE  TRUE  TRUE  TRUE FALSE FALSE FALSE FALSE

Source: R documentation: make.names

Four details in that output are worth remembering. First, make.names("") is "X" and not an error, and with unique = TRUE the call make.names(c("", "X"), unique = TRUE) gives "X.1" and "X" (R up to 3.0.2 gave them in the other order). Second, a reserved word in a data frame column becomes if., which is why a CSV with a column named if reads as if. and why check.names = FALSE is needed to keep it. Third, get("books$title") looks for an object literally named books$title; get() and assign() do not recognise subscripting operators or replacement functions, so x$a <- 1 and assign("x$a", 1) are different things, as are x[[1]] and get("x[[1]]"), and names(x) <- nm and assign("names(x)", nm) (R-lang: Identifiers). Fourth, make.names() leaves ... and ..1 alone, although they are reserved words: they are not valid object names, but they are valid tokens, so the function does not treat them as clashing keywords (checked on R 4.6.1). The helper is_syntactic() at the end of the script is therefore only a first approximation; quote() or parse() is the authority.

Names of functions follow the same rules. A function called overdue days can be defined and called with backticks or with a string in the function position, but the parameters of a function expression must be real names:

# "..." and "..1", "..2" are reserved words that refer to the arguments passed
# on from the calling function.
second_of <- function(...) ..2
second_of("a", "b", "c")
#> [1] "b"
count_args <- function(...) ...length()
count_args(1, 2, 3)
#> [1] 3
label_args <- function(...) ...names()
label_args(first = 1, 2, third = 3)
#> [1] "first" ""      "third"
nth_arg <- function(n, ...) ...elt(n)
nth_arg(3L, "x", "y", "z")
#> [1] "z"

# Using ..2 when there is only one argument is an error with its own message.
tryCatch(
  second_of("only one"),
  error = \(e) writeLines(conditionMessage(e))
)
#> the ... list contains fewer than 2 elements
tryCatch(
  eval(parse(text = "..1")),
  error = \(e) writeLines(conditionMessage(e))
)
#> ..1 used in an incorrect context, no ... to look in

# A function may have a non-syntactic name, but its parameters must be names.
`overdue days` <- function(loaned, returned) { # nolint: object_name_linter.
  as.numeric(returned - loaned)
}
`overdue days`(as.Date("2025-01-07"), as.Date("2025-02-01"))
#> [1] 25
"overdue days"(as.Date("2025-01-07"), as.Date("2025-02-01"))
#> [1] 25
tryCatch(
  parse(text = "function(\"x\") 1"),
  error = \(e) writeLines(conditionMessage(e))
)
#> <text>:1:10: unexpected string constant
#> 1: function("x"
#>              ^

# A call can use a quoted tag; a string and a name are equivalent there.
list("odd tag" = 1, plain = 2)
#> $`odd tag`
#> [1] 1
#>
#> $plain
#> [1] 2
#>
identical(list("a" = 1), list(a = 1))
#> [1] TRUE

Source: The R Language Definition: Function calls

The same script shows the three special tokens ..., ..1, ..2, and the functions that go with them: ...length(), ...names() (R 4.1.0) and ...elt(n). They refer to the arguments passed down from a calling function (R documentation: dots). Using ..2 when fewer than two arguments exist is an evaluation error with its own message, and ..1 outside a function with dots is another one; both are shown above. Functions describes how dots are matched.

A note on style

Because both the dot and the underscore are legal, R code comes in several naming dialects. The dot has a historical role in S3: print.book is the print method for class book, so a function whose name contains a dot may look like a method to the dispatcher. That is the reason most current style guides, and the default lintr object_name_linter, prefer snake_case for new names. Older tutorials use dotted names such as my.data.frame everywhere; both work, and base R itself has dotted names (read.csv, is.na, Sys.Date) that are not S3 methods. Names are case sensitive: Books and books are different objects (R-intro: R commands, case sensitivity, etc.).

Reserved words

The parser reserves a short list of words. They have a special meaning and cannot be used as object names (R-lang: Reserved words).

Group Words

Control flow

if, else, repeat, while, function, for, in, next, break

Constants

TRUE, FALSE, NULL, Inf, NaN

Missing values

NA, NA_integer_, NA_real_, NA_complex_, NA_character_

Dots

..., ..1, ..2, and so on

Source: R documentation: Reserved

The help page adds the important detail: reserved words outside quotes are always parsed to be references to the objects they stand for, hence they are not allowed as syntactic names, but they are allowed as non-syntactic names, for example inside backticks. The next script shows the two failure modes. The control-flow words fail in the parser, because the grammar has no rule that puts if on the left of <-. The constants parse as constants, so the failure comes from the evaluator, which says that the left-hand side of the assignment is invalid.

# Run a piece of text through the parser and evaluator; report the outcome.
outcome <- function(text) {
  tryCatch(
    {
      eval(parse(text = text))
      "no error"
    },
    error = \(e) conditionMessage(e)
  )
}

# The reserved words are recognised by the parser, so they cannot be names.
outcome("if <- 1")
#> [1] "<text>:1:4: unexpected assignment\n1: if <-\n       ^"
outcome("function <- 1")
#> [1] "<text>:1:10: unexpected assignment\n1: function <-\n             ^"
outcome("repeat <- 1")
#> [1] "<text>:1:8: unexpected assignment\n1: repeat <-\n           ^"

# TRUE, FALSE, NULL, Inf and NaN parse as constants, so the
# parser accepts the assignment but the evaluator refuses it.
outcome("TRUE <- 0")
#> [1] "invalid (do_set) left-hand side to assignment"
outcome("NULL <- 1")
#> [1] "invalid (do_set) left-hand side to assignment"
outcome("Inf <- 1")
#> [1] "invalid (do_set) left-hand side to assignment"

# Backticks turn a reserved word into an ordinary, non-syntactic name.
`if` <- "just a variable" # nolint: object_name_linter.
`if`

String literals and escapes

A string constant is delimited by a pair of single or double quotes. They are interchangeable; double quotes are preferred, and R always prints strings with double quotes, so single quotes are normally used only to delimit a string that contains double quotes (R documentation: Quotes). Escaping a character that is not in the table is an error, so "\q" is rejected when the code is parsed, and so is mixing octal or hexadecimal escapes with Unicode escapes in the same string. A NUL character cannot be part of a string: \0 is rejected. The text of ?Quotes says that a NUL escape truncates the string at that point (usually with a warning), but its own examples list both "foo\0bar" and "foo\u0000bar" as parse errors, and R 4.6.1 reports "nul character not allowed". A string may contain a literal newline, in which case the newline is part of the value. Unicode escapes can enter characters that are not in the current locale’s character set, in which case the string is stored in UTF-8. UTF-16 surrogate pairs written as \uD834\uDD1E become a single code point, and an unpaired surrogate gives a warning from the parser. As from R 4.1.0 the largest allowed \U value is \U10FFFF, the largest Unicode code point; a bigger value is an error because it cannot be represented in valid UTF-8 (R NEWS, Changes in R 4.1.0).

Expressions, statements and newlines

An R program is a sequence of expressions. An expression can be a simple one (a constant or an identifier) or a compound one built from other expressions (R-lang: Expressions). R makes no distinction between expressions and statements: an assignment, an if, a for loop and a block are all expressions with a value, and the value of a for is NULL.

Where a line ends

Newlines have a function that combines token separator and expression terminator: if an expression can end at the end of the line, the parser assumes it does; otherwise the newline is treated as whitespace (R-lang: Separators). This rule is the reason R needs no line-continuation character and no terminating semicolon. It also determines where a long expression may be broken: after something that leaves the expression unfinished. The next script lets the parser itself classify a set of cases: "complete" means the console would run it, "incomplete" means the console would show the + prompt.

# Ask the parser what the console would do with a line (or several lines):
# "complete" means it can be run, "incomplete" means the console would show
# the "+" continuation prompt (the parser reports "unexpected end of input" or
# an unfinished string), anything else is a syntax error.
classify <- function(...) {
  text <- c(...)
  tryCatch(
    {
      parse(text = text)
      "complete"
    },
    error = \(e) {
      msg <- conditionMessage(e)
      if (grepl("end of input|INCOMPLETE_STRING", msg)) {
        "incomplete"
      } else {
        "syntax error"
      }
    }
  )
}

The consequences for style are one rule and one trap. The same-line separators are the semicolon, which separates elementary expressions on one line (a <- 1; b <- 2), and the comma, which separates arguments and indices. The semicolon is legal but unusual style; lintr flags compound semicolons.

The else rule

The R Language Definition singles out one exception: inside a compound expression a newline before else is discarded, whereas at the outermost level the newline ends the if and a following else is a syntax error. The anomaly exists because R must decide whether the input is complete, incomplete or invalid as soon as RET is pressed. The final rows of the previous script show it: the same text is accepted inside braces and rejected without them. Write the else on the same line as the closing brace (} else {), which is correct everywhere. The full treatment of if, else, loops and switch() is in Control Flow.

Blocks and parentheses

A compound expression has the form { expr1 ; expr2 ; ... ; exprn }, with newlines allowed in place of the semicolons, and it is stored as a call to the function named { with the expressions as arguments. It evaluates its arguments in order and returns the value of the last one; the empty block {} is NULL (R-lang: Compound expressions). Braces do not create a scope in R: variables assigned inside a block belong to the enclosing environment, which is a major difference from C, Java and Rust (see Scoping, Environments and Closures). Ordinary parentheses group an expression and delimit argument lists, and they are recorded as a unary operator with the name ( even when precedence would make them redundant (R documentation: Paren).

Syntax errors: the messages and what they mean

When the text violates the grammar, the parser stops and reports an error whose first line has the form <source>:<line>:<column>: unexpected <token>, followed by the offending line (and the line before it) and a caret under the token where the parser gave up. Where the source is a character vector the source is <text>; for a file it is the file name. The token named is the first one that cannot continue the expression, which is often one token after the real mistake: in a b the parser accepted a as a complete expression and objected to the second symbol. Two things follow. The column points at the place where the parser could not go on, not at the cause; and an error at the very end of the input (unexpected end of input) means that something opened earlier was never closed.

The next script captures real messages with tryCatch(parse(text = ...)), so that none of them stops the script. This works because a syntax error from parse() is an ordinary R error condition (a plain simpleError). The R manual describes the interactive behaviour: if the parser finds a state incompatible with the grammar, a "Syntax Error" is flagged and it resumes at the beginning of the next input line.

# parse() reports a syntax error as an ordinary error condition, so a text
# can be checked without running it. The message has the form

check <- function(text) {
  tryCatch(
    {
      parse(text = text)
      writeLines("parsed")
    },
    error = \(e) writeLines(conditionMessage(e))
  )

The parse tree, parse() and deparse()

The manual states the central fact of the parser: parsed expressions are stored in an object that holds the parse tree, and every elementary R expression is stored in function-call form, as a list whose first element names the function and whose remaining elements are the arguments, which may in turn be expressions. All syntax elements are treated this way: the assignment x <- 1 is encoded as "<-"(x, 1) (R-lang: Internal representation).

parse() returns the parsed but unevaluated expressions as an object of type expression, a list of calls. Every call is a function call

The R Language Definition says that a function call has the form function_reference followed by a comma-separated argument list in parentheses, and that the function reference can be an identifier, a text string (handy when the name is not a valid identifier) or any expression that evaluates to a function object (R-lang: Function calls). Its examples include f(x), g(tag = value, , 5), the string form "odd name"("strange tag" = 5, y) and the call of a function expression (function(x) x^2)(5). The second example shows that an argument can be empty.

What makes R unusual is that this single form is also what every other piece of syntax turns into. The manual says it three times, in three sections:

  • operators: "the parsed form of a unary or binary operation is completely equivalent to a function call with the operator as the function name and the operands as the function arguments" (R-lang: Infix and prefix operators);

  • indexing: object[args], object[[args]] and object$tag are stored as calls to [, [[ and $ (R-lang: Index constructions);

  • compound expressions and flow control: a block is a call to {, and if, while, repeat, for, break and next are calls to functions of those names (R-lang: Flow control elements), and a function definition is a call to function with the argument list and the body (R-lang: Function definitions).

The slogan, popularised by John Chambers, is that everything that happens in R is a function call. The consequences are practical, not just philosophical, as the next script shows. Pipes, replacement functions and operators as arguments

Two syntactic forms are not calls to a function with the name that appears in the source. The native pipe |> (R 4.1.0) is a parse-time rewrite: the expression x |> f(y) becomes f(x, y) before it is evaluated, so no function named |> exists (exists("|>") is FALSE) and quote(books |> head(2L) |> nrow()) prints as nrow(head(books, 2L)). This is a difference from the magrittr pipe %>%, which is an ordinary function. The placeholder _ of R 4.2.0 is part of the same rewrite; Pipes and the Native Pipe covers it in depth.

Assignment with a function on the left, as in names(x)[2] <- "last", is expanded into nested replacement-function calls: the left side is evaluated into a temporary, the function named names<- receives the modified value as its last argument (which must be called value), and the result is assigned back. The second script writes the expansion by hand and checks that it gives an identical result (R-lang: Function calls).

They can also be redefined (inside local() the script makes + paste its operands), which is why packages such as Matrix and ggplot2 can give operators new meaning for their classes through S3 and S4 dispatch, a topic of S3 Group Generics and Operator Overloading. The special operators %name% are the user-extensible part: any function whose name starts and ends with % is an infix operator, so the %+% defined at the end of the script is an ordinary function that happens to be callable infix. The last lines of that script show the types of these functions: + is a builtin primitive, if, for and [ are special primitives that receive their arguments unevaluated, and sum is a builtin, while mean is a closure, a function written in R. Printing `if` shows .Primitive("if"), which is as far as R lets you look.

Reading code as data: a shelf example

The running scenario ends with a small use of these pieces. A check that the column names of the shelf tables are all syntactic (and so can be used with $ without backticks), and a function that takes a filter expression typed by a user as text, parses it first so that a syntax error becomes a message and not a crash, and only then evaluates it against a table.

books <- read.csv("books.csv")
source("scenario.R")

# The columns of both tables are already syntactic names.
all(names(books) == make.names(names(books)))
#> [1] TRUE
all(names(loans) == make.names(names(loans)))
#> [1] TRUE
names(loans)
#> [1] "loan_id"     "isbn"        "member"      "loan_date"   "return_date"

# A filter typed by a user is only text: parse it first, run it afterwards.
filter_titles <- function(expr_text, data) {
  expr <- tryCatch(str2lang(expr_text), error = \(e) NULL)
  if (is.null(expr)) {
    return(paste("not a valid R expression:", expr_text))
  }
  keep <- eval(expr, data, baseenv())
  data$title[which(keep)]
}
filter_titles("pages > 400", books)
#> [1] "Pride and Prejudice" "Notes on Gravity"
filter_titles("genre == 'Poetry'", books)
#> [1] "Garden of Small Fires" "Paper Moons"
filter_titles("pages >> 400", books)
#> [1] "not a valid R expression: pages >> 400"
filter_titles("genre ==", books)
#> [1] "not a valid R expression: genre =="

# loan_days is an integer constant (the literal 21L) from the scenario file.
loan_days
#> [1] 21
class(loan_days)
#> [1] "integer"

Source: R documentation: parse

The function evaluates the parsed expression with eval(expr, data, baseenv()): names are looked up in the data frame first and then in the base environment only, so the user text cannot see the caller’s variables. That is a limited safeguard, not security. Parsing text and evaluating it runs arbitrary code, and str2lang() followed by eval() of text from an untrusted source is a code-injection vector. Older tutorials use eval(parse(text = paste0("x", i))) to build variable names; lists, [[, get() and assign() do the same job without evaluating a string.
