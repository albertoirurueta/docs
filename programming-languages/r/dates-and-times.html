Dates and Times

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. This page explains how R represents calendar dates (Date), instants (POSIXct), broken-down times (POSIXlt) and intervals (difftime), how to read and write them as text, how time zones and daylight saving time change what a clock reading means, how to do arithmetic, sequences and counting by period, and how the ts class of the stats package stores regular time series. Everything is base R (the base, utils and stats packages), except one short section that runs lubridate 1.9.5 next to the base functions; the lintr 3.4.0 default linters were used only to check the scripts.

Every example below is a complete script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines starting with #> are what it printed. The scripts pass the default lintr linters. Errors and warnings that the page wants to show are caught with tryCatch() and printed with conditionMessage(), so the text is exactly what R says and the script still ends normally. The examples use the library scenario of the section: loans$loan_date, loans$return_date, shelf_today (the fixed "today", 2026-06-30) and loan_days (21) come from the scenario.R file described on the section index, and the scripts that use them start with source("scenario.R"). Two rules keep the output reproducible: the scripts never print Sys.time() or Sys.Date() (they change on every run, so only their classes are shown) and they always name the time zone they mean, either with tz = or by setting the TZ environment variable, so nothing depends on the zone of the machine that ran them. A few behaviours are decided by the operating system rather than by R (what happens inside a daylight-saving gap, what a misspelt zone name does, the number of names in the time zone database); the page says so where they appear and shows what the Linux container used for checking produced.

The classes at a glance

R has no single "date-time type". It has two classes for calendar days and instants that a vector can hold, one class that exposes the fields of a calendar time, one for the difference between two of them, and a separate class for regularly spaced numeric series. The help page DateTimeClasses states the design in one sentence: POSIXct is more convenient for including in data frames, and POSIXlt is closer to human-readable forms (R documentation: DateTimeClasses).

A date has no time of day and no zone, so it is the right type for something that happens "on 2026-06-30" wherever you are. An instant is a point on the time line, so it needs a zone only to be shown or to be built from a clock reading. Mixing the two ideas is the source of most date bugs, and the rest of the page keeps them apart: Dates first, then instants and time zones.

Dates

The help page for Dates says that dates are represented as the number of days since 1970-01-01, with negative values for earlier dates, and that they are always printed following the rules of the current Gregorian calendar even when that calendar was not yet in use (R documentation: Dates). It also says that the value is intended to be an integer but that this is not enforced, so a Date is stored as a double and a fraction of a day is kept but ignored when printing. Two consequences are on the first script: unclass() shows the number behind the class, and identical() should not be used on dates, because a date stored as an integer and the same date stored as a double are different objects (the help page warns about this; use == or all.equal()).

Numbers become dates with as.Date(x). Before R 4.3.0 this needed an origin argument; the 4.3.0 NEWS says that as.POSIXct(<numeric>) and as.POSIXlt() without an origin now work, and "So does as.Date(<numeric>)" (R NEWS: Changes in R 4.3.0). origin is still the way to read a number counted from another epoch, such as a spreadsheet serial number.

weekdays(), months(), quarters() and julian() are documented together on one help page (R documentation: weekdays). The names they return and the names that format() produces for %A and %B follow the LC_TIME locale category, so on a machine configured for another language weekdays(d) is in that language; the section Encodings, Locales and Internationalization explains the locale categories. julian(d) returns the number of days since the origin attribute, 1970-01-01 unless you pass another.

Reading dates with as.Date

as.Date() on text takes a format (the conversion codes of the table below) or, when none is given, tries the two ISO layouts in tryFormats = c("%Y-%m-%d", "%Y/%m/%d") on the first element that is not NA, and signals an error if neither matches. Three details of that rule cause most trouble, and the script shows each one:

  • The text is processed only as far as the format needs, so anything after the date is ignored: "2026-06-30abc" and "2026-06-30 23:59:59" both give 2026-06-30.

  • A text that fits the first layout is accepted whatever it was meant to say. "30/06/2026" is read with %Y/%m/%d: %Y takes 30, the month is 06, the day is 20 and the trailing 26 is ignored. The result is the date 0030-06-20, with no error and no warning. Give the format whenever the text is not an ISO date.

  • The layout is guessed from the first element that is not NA. An impossible date such as "2025-02-30" is not NA as text, but it does not parse, so a vector that starts with one fails as a whole, while the same date later in the vector is just NA. With a format, the impossible date is NA wherever it is.

The error text for a vector that matches no layout is character string is not in a standard unambiguous format. optional = TRUE returns NA instead of signalling that error (R documentation: as.Date).

# ISO layouts need no format: "%Y-%m-%d" and "%Y/%m/%d" are tried in turn.
as.Date("2026-06-30")
#> [1] "2026-06-30"
as.Date("2026/06/30")
#> [1] "2026-06-30"
as.Date("2026-6-3")
#> [1] "2026-06-03"

# Anything else needs a format.
as.Date("30/06/2026", format = "%d/%m/%Y")
#> [1] "2026-06-30"
as.Date("June 30, 2026", format = "%B %d, %Y")
#> [1] "2026-06-30"
as.Date("30 Jun 2026", format = "%d %b %Y")
#> [1] "2026-06-30"
as.Date("20260630", format = "%Y%m%d")
#> [1] "2026-06-30"
as.Date("30.06.26", format = "%d.%m.%y")
#> [1] "2026-06-30"

# Without a format a string that matches the first layout is accepted
# whatever it was meant to say: this is year 30, month 6, day 20.
wrong <- as.Date("30/06/2026")
wrong
#> [1] "30-06-20"
as.POSIXlt(wrong)$year + 1900L
#> [1] 30
as.POSIXlt(wrong)$mon + 1L
#> [1] 6
as.POSIXlt(wrong)$mday
#> [1] 20

# A string that matches neither layout is an error ...
tryCatch(as.Date("June 30, 2026"), error = \(e) conditionMessage(e))
#> [1] "character string is not in a standard unambiguous format"
# ... unless optional = TRUE asks for NA instead.
as.Date("June 30, 2026", optional = TRUE)
#> [1] NA

# Characters after the date are ignored.
as.Date("2026-06-30 23:59:59")
#> [1] "2026-06-30"
as.Date("2026-06-30abc")
#> [1] "2026-06-30"

# An impossible date is NA when the format is given ...
as.Date("2025-02-30", format = "%Y-%m-%d")
#> [1] NA
# ... but without a format all candidates fail, and that is an error.
tryCatch(as.Date("2025-02-30"), error = \(e) conditionMessage(e))
#> [1] "character string is not in a standard unambiguous format"
# The layout is guessed from the first element that is not NA, so one
# impossible date first in the vector makes the whole call fail ...
tryCatch(
  as.Date(c("2025-02-30", "2025-03-01")),
  error = \(e) conditionMessage(e)
)
#> [1] "character string is not in a standard unambiguous format"
# ... while the same date later in the vector is just NA.
as.Date(c("2025-03-01", "2025-02-30"))
#> [1] "2025-03-01" NA
# Giving the format avoids the guess.
as.Date(c("2025-02-30", "2025-03-01"), format = "%Y-%m-%d")
#> [1] NA           "2025-03-01"

Source: R documentation: as.Date

Printing the wrong-layout date gives 30-06-20 on the Linux container, without the zero padding of the year: how R prints a year below 1000 depends on the operating system (the Date help page does not promise a layout), which is one more reason to give a format. For two-digit years (%y), values 00 to 68 are read as 20xx and 69 to 99 as 19xx, the behaviour specified by the 2018 POSIX standard, as the parsing script shows.

The loans: an impossible date

The shelf scenario contains one deliberate date problem: row 20 of loans.csv has the loan date 2025-02-30, which does not exist. read.csv() returns every column as text (colClasses = "character" makes that explicit) and scenario.R converts the two date columns with as.Date(format = "%Y-%m-%d"), so the impossible date becomes NA and the rest of the column converts normally. Empty return_date fields, the seven loans still out, are NA as well. Because an NA is present, range() needs na.rm = TRUE, as do most of the summaries below. read.csv() can also convert while reading, with colClasses = c(loan_date = "Date"); it applies as.Date() to the text, so it gives the same result here. The section Reading and Writing Text Data covers colClasses in detail.

source("scenario.R")

raw$loan_date[18:22]

POSIXct and POSIXlt

An instant needs a finer unit than a day. POSIXct ("calendar time", from the C type time_t) stores the number of seconds since 1970-01-01 00:00:00 UTC as a double. POSIXlt ("local time", from the C structure struct tm) stores the same instant as a list of broken-down fields. Both inherit from the virtual class POSIXt, which lets operations such as subtraction mix them, and both may carry a tzone attribute (R documentation: DateTimeClasses). Because a POSIXct is just a number, it is fast, it sorts and subsets like a number, and it is one atomic column in a data frame. Because a POSIXlt is a list, a field such as the month is available directly.

# POSIXct: seconds since 1970-01-01 00:00:00 UTC, plus a tzone attribute.
x <- as.POSIXct("2026-06-30 09:30:00", tz = "UTC")
x
#> [1] "2026-06-30 09:30:00 UTC"
class(x)
#> [1] "POSIXct" "POSIXt"
typeof(x)
#> [1] "double"

#> [1] 1782811800
#> attr(,"tzone")
#> [1] "UTC"
as.numeric(x)
#> [1] 1782811800

# Numbers become date-times without an origin since R 4.3.0.

Until R 4.3.0 the last two fields were optional and platform dependent. The 4.3.0 NEWS says that all objects created in that version have 11 components, that zone is always set, that gmtoff is set for times in UTC and usually on platforms with C-level support, and that there are now comprehensive validity checks on the structure of a POSIXlt when converting, formatting and printing, which avoids mis-conversions of hand-crafted objects. The same entry introduced the experimental balancePOSIXlt(), which makes "ragged" objects (fields of different lengths, or out-of-range values) balanced (R NEWS: Changes in R 4.3.0). The 4.6.1 NEWS records that as.matrix(<POSIXlt>) again produces a numeric matrix, as the script shows, and that the c() and subassignment methods work correctly more often (R NEWS: Changes in R 4.6.1).

Three points about POSIXlt are easy to miss:

  • length(lt) is the number of times, not the number of fields, and lt[["min"]] is an error with the text shown on the script. Use lt$min or lt[, "min"] (the help page says single components can be extracted and replaced with [ and two indices).

  • Fields may be set to out-of-range values and normalised on conversion. Adding 40 to mday and converting with as.POSIXct() gives the date 40 days later. This is how the "one month later" calculation below is done in base R. After changing a field in a zone with daylight saving, also set isdst to -1 (unknown), as the daylight-saving script does, because a stale flag moves the result by an hour.

  • The fields wday and yday are informative: they are not used for conversion, printing or formatting.

Which one to store

Store POSIXct. The help page for DateTimeClasses says that data.frame() and the as.data.frame method convert a POSIXlt to a one-column POSIXct data frame, so that date-time objects are treated like atomic vectors. The conversion is applied by data.frame(), not by df$col <- value, which stores the list as it is and leaves the data frame with a column of a different kind. Convert explicitly with as.POSIXct() when you assign. Arithmetic and comparison on either class are done after coercion to POSIXct, so nothing is gained by keeping the list.

x <- as.POSIXct("2026-06-30 09:30:00", tz = "UTC")
times <- as.POSIXlt(c(x, x + 3600))

# data.frame() converts a POSIXlt column to POSIXct ...
df <- data.frame(id = 1:2, when = times)
class(df$when)
#> [1] "POSIXct" "POSIXt"

# ... but assigning a column does not, which keeps the list structure.
df$other <- times
class(df$other)
#> [1] "POSIXlt" "POSIXt"
str(df)
#> 'data.frame':	2 obs. of  3 variables:
#>  $ id   : int  1 2
#>  $ when : POSIXct, format: "2026-06-30 09:30:00" "2026-06-30 10:30:00"
#>  $ other: POSIXlt, format: "2026-06-30 09:30:00" "2026-06-30 10:30:00"

# Convert explicitly before storing.
df$other <- as.POSIXct(times)
class(df$other)
#> [1] "POSIXct" "POSIXt"

# Arithmetic and comparison go through POSIXct anyway.
df$when + 60
#> [1] "2026-06-30 09:31:00 UTC" "2026-06-30 10:31:00 UTC"
df$when > x

Time zones

A POSIXct is one point on the time line. A time zone is a rule that turns that point into a clock reading, and the other way round. Three different operations use the word tz, and mixing them up is the usual mistake:

Call What tz means Effect

the zone in which the text is written

chooses the instant

format(x, tz = "Europe/Madrid", usetz = TRUE)

the zone in which to show an existing instant

chooses the clock reading; the instant is unchanged

attr(x, "tzone") <- "Europe/Madrid"

the zone in which to show the object from now on

same as above, stored in the object

Source: R documentation: as.POSIXlt

The tzone attribute of a POSIXct is what print() and format() use. If it is the empty string (what you get when tz is not given), the object is shown in the current zone of the session, so the same object prints differently after TZ changes. The help page adds that c() on POSIXct objects drops tzone if they do not all have the same one, and that c() on POSIXlt objects converts them to the current zone (R documentation: DateTimeClasses).

#> [1] -7200

Notes on the script:

  • as.Date() of a date-time is documented to convert "by ignoring the time after midnight in the representation of the time in specified time zone, default UTC", so a late evening in New York is already tomorrow’s date unless tz is given (R documentation: as.Date). Going the other way, a Date converted to a date-time is midnight UTC (R documentation: Dates), and since R 4.3.0 as.POSIXlt(<Date>) and as.POSIXct(<Date>) apply a tz argument, which changes only the display: midnight UTC is 02:00 in Madrid in June.

  • Comparing times whose tzone attributes differ gives the warning shown ('tzone' attributes are inconsistent); the comparison itself is still made on the instants.

  • The names come from the IANA time zone database (the "Olson" database) installed on the system. OlsonNames() lists the ones available; the number depends on the installed version of the database and on the system, so the script tests it against a bound instead of printing it. The help page says that only the Continent/City and Etc/... forms are fully portable, that "UTC" and "GMT" are accepted on every platform, and that traditional names need care: "EST" is a zone in Canada without daylight saving, not the same as "EST5EDT" nor Australian Eastern Standard Time (R documentation: timezones).

  • An invalid name is not an error. The help page says invalid values are most commonly treated as UTC, on some platforms with a warning. On the Linux container used here there was no warning, so the safest checks are tz %in% OlsonNames() or a test with a known instant.

  • When there is a tzone, POSIXlt objects carry three values (the zone name and the standard and daylight abbreviations), which is why attr(as.POSIXlt(x, "Europe/Madrid"), "tzone") has length 3.

The TZ environment variable

With tz = "", the zone is the current one: the value of the TZ environment variable if it is set, otherwise the system zone. Sys.timezone() returns the name of the current zone; its value is operating-system specific and can be NA or an empty string, so this page prints it only after setting TZ itself. The help page says an invalid TZ makes most platforms use UTC, and recommends setting TZ before R starts (or in .Rprofile) when the system value is wrong. The 4.3.0 NEWS adds that on Windows TZ can be set to the desired Olson name to override the automatic mapping from Windows zone names (R NEWS: Changes in R 4.3.0). Sys.setenv() changes it for the running session (R documentation: Sys.setenv). The environment variables used by R in general are listed on Sessions, Workspaces and Startup.

Daylight saving time

Two kinds of clock reading cannot be turned into an instant without a rule: a reading that never happened (the clocks jumped forward) and a reading that happened twice (the clocks went back). The help page for as.POSIXlt says that what happens in such cases is operating-system specific: for the first one should expect NA, and the second could be read as either of the two instants (R documentation: as.POSIXlt). The Linux container used for this page chose these answers, which you cannot rely on elsewhere:

  • 02:30 on 2026-03-29 in Madrid, which does not exist, became 03:30 CEST; as.POSIXlt() of the same text keeps the fields 02:30 with an unknown isdst, so it prints without a zone.

  • 02:30 on 2026-10-25, which occurs twice, was read as the second one (CET).

The portable approach is to avoid constructing clock readings in the gap and to be explicit when adding "a day": the by units of seq.POSIXt() distinguish "day" from "DSTday". "day" is 24 hours and ignores changes to or from daylight saving; "DSTday" takes the same clock time each day (R documentation: seq.POSIXt). Likewise a difftime in "days" is a period of 24 hours, not a calendar day, and so takes no account of daylight saving (R documentation: difftime). The next script computes a due date for a loan taken at 18:00 on 2026-03-20, nine days before the clocks go forward in Madrid, with loans lasting loan_days.

source("scenario.R")

#> [1] "2026-04-10 19:00:00 CEST"

#> Time difference of 20.95833 days

Parsing text

strptime() is the strict reader: it returns a POSIXlt, and text that does not fit the format becomes NA in every field, with no error. The help page documents that an invalid time such as "2010-02-30 08:00" gives all components NA, that unspecified seconds, minutes and hours are zero, and that an unspecified year, month or day is the current one, with the exception that if a month is given the day of that month must be given too (R documentation: strptime). as.POSIXct(x, format = ) and as.Date(x, format = ) call it and convert the result. Without a format, as.POSIXct() tries a fixed list in turn ("%Y-%m-%d %H:%M:%OS", "%Y/%m/%d %H:%M:%OS", "%Y-%m-%d %H:%M", "%Y/%m/%d %H:%M", "%Y-%m-%d", "%Y/%m/%d") and takes the first that works for all the non-NA inputs; this is slow on long inputs, so give the format when you know it.

The same rule that ignores trailing characters has a nasty consequence here: when the longer layouts fail, the date-only layout still matches the beginning of the text, so a time that is not valid, or that has a T in front of it, silently becomes a date at midnight (the last lines of the script, and the next section). A parse failure that is visible as NA is better than one that is not, so check the results of parsing a column with anyNA() or sum(is.na()) and compare the number of NA before and after.

ISO 8601

ISO 8601 writes a day as 2026-06-30, a time as 09:30:05 and a combined moment as 2026-06-30T09:30:05+02:00 or 2026-06-30T07:30:05Z. R’s default text is the same except for a space instead of the T; the strptime help page notes that the ISO form uses no space, possibly T, to separate dates and times, and that R uses a space by default (R documentation: strptime). The output codes are %F (date), %T (time), %z (offset +hhmm, with no colon) and %G-W%V-%u for the week-based form. The week-based year can differ from the calendar year near 1 January (the ISO week 53 of 2026 contains the last days of the year and days of 2027), which is why %G and %Y are different codes.

Reading ISO text needs more care than writing it. The default layouts of as.POSIXct() have no T, so "2026-06-30T09:30:05" matches only as a date and the time is lost without any warning, as the script shows. Give a format ("%Y-%m-%dT%H:%M:%S", or "%FT%T") or tryFormats. A trailing Z is just a literal character in the format, so it does not set the zone: pass tz = "UTC" as well. A numeric offset is read with %z, which accepts +hhmm or -hhmm (values from -1400 to +1400); +02:00 with a colon does not match and the result is NA, so remove the colon first, as the script does with sub() (see Strings and Regular Expressions). The help page says %z on input makes most sense with tz = "UTC": the result is the instant converted to UTC.

ISOdate() and ISOdatetime() build a POSIXct from numeric year, month, day, hour, minute and second. ISOdate() defaults to 12:00 and to the time zone "GMT", which R treats as UTC, and an impossible combination such as 30 February gives NA (R documentation: ISOdatetime).

Fractional seconds

A POSIXct can hold fractions of a second, and a POSIXlt holds them in sec with better accuracy; the help page says that conversion between the two may not be exact but is better than a microsecond (R documentation: DateTimeClasses). Fractions are shown only when asked for:

  • %OSn in a format (n from 0 to 6) prints exactly n decimals, truncating and not rounding; %OS alone uses up to digits decimals, and only one %OS per format string is handled on output. On input, %OS reads fractions and %S does not.

  • format(x, digits = n) has the same effect, and options(digits.secs = n) sets the default of the digits argument for both print() and format(). A format that contains %OSn takes precedence over digits.

  • Since R 4.5.0 the print() method for date-times has its own digits argument, so print(x, digits = 3) shows milliseconds without changing the option; another 4.5.0 entry made format(dtime, digits = , format = ) more consistent for fractional seconds (R NEWS: Changes in R 4.5.0).

x <- as.POSIXct("2026-06-30 09:30:05.123456", tz = "UTC")

# Fractions are stored but not shown by default.
x
#> [1] "2026-06-30 09:30:05 UTC"
format(x, "%OS3")
#> [1] "05.123"
format(x, "%H:%M:%OS3")
#> [1] "09:30:05.123"
format(x, digits = 3)
#> [1] "2026-06-30 09:30:05.123"
# The print method accepts digits since R 4.5.0.
print(x, digits = 3)
#> [1] "2026-06-30 09:30:05.123 UTC"
as.POSIXlt(x)$sec
#> [1] 5.123456

# options(digits.secs) changes what print() and format() show.
old <- options(digits.secs = 3)
x
#> [1] "2026-06-30 09:30:05.123 UTC"
format(x)
#> [1] "2026-06-30 09:30:05.123"
options(old)
x
#> [1] "2026-06-30 09:30:05 UTC"

# %OSn truncates, it does not round.
y <- as.POSIXct("2026-06-30 09:30:05.9996", tz = "UTC")
format(y, "%OS3")
#> [1] "05.999"
format(y, "%OS2")
#> [1] "05.99"

# Fractional seconds can be read with %OS (but not with %S).
strptime("09:30:05.250", "%H:%M:%OS", tz = "UTC")$sec
#> [1] 5.25

The current date and time

Sys.Date() returns the current day as a Date, and Sys.time() returns the current instant as a POSIXct that on almost all systems has sub-second accuracy (R documentation: Sys.time). date() returns the current time as a character string in a fixed format (R documentation: date). Their value changes on every call, so a result that depends on them cannot be compared with a previous run, and this page does not print them. Code that needs the current time reads it once, at the edge of the program, and passes it down as an argument (the shelf scenario does the same with shelf_today). Timing code is a different job: Sys.time() differences are not the right tool for it, see Performance, Profiling and Benchmarking.

}

Arithmetic and difftime

Dates and date-times support a deliberately small set of arithmetic operations. The help page Ops.Date and the one for DateTimeClasses say that you can add or subtract a number (days for Date, seconds for POSIXct) or a difftime, that subtracting two objects gives a difftime, that comparisons work, and that adding two dates or times makes no sense (R documentation: Ops.Date). The errors for the rest, such as binary + is not defined for "Date" objects, are listed in Common errors and warnings.

The difftime class (R documentation: difftime) stores a number and the unit it is expressed in:

  • d2 - d1 on two Date values is a difftime in "days". On two POSIXct values the unit is chosen automatically: the largest of "secs", "mins", "hours" or "days" in which all the absolute differences are greater than one. "weeks" is never chosen automatically; pass units = "weeks" to difftime().

  • difftime(time1, time2, units = ) makes the unit explicit. as.numeric(dt, units = "days") returns the number in the unit you ask for and is the safe way to compare with a number, because the unit of d2 - d1 for date-times depends on the data.

  • units(dt) reads the unit and units(dt) <- "weeks" changes it, scaling the number.

  • There is no "months" or "years": they have no fixed length. The help page says to use seq.Date() or seq.POSIXt() to create intervals of months, quarters or years, and the error text for the attempt is in the errors section.

  • sum(), mean(), diff() and arithmetic with a number keep the unit. Since R 4.4.0 diff() of dates and date-times accepts a units argument, and since R 4.5.0 difftime has a summary() method and a format() option with.units (R NEWS: Changes in R 4.4.0 and 4.5.0).

The Ops.Date page says that character vectors in a comparison are converted with as.Date(), which is why a date compares with ISO text; subtracting text is an error.

Overdue loans

The shelf scenario defines a returned loan as overdue when return_date - loan_date > loan_days, and a loan still out as overdue when shelf_today - loan_date > loan_days. Both are the same expression once the missing return dates are replaced by "today". The script computes the lengths, notes the data error in row 12 (a loan returned three days before it was loaned, which shows as a negative difftime), and wraps the rule in a function that takes today as an argument so that it never reads the clock. The comparison lent > loan_days compares the number of days with the integer 21, since the unit of a Date difference is always days. The second comparison states the unit with as.numeric(lent, units = "days"), which stays correct if the same code is later used with date-times. The counts are 25 returned loans longer than 21 days, 7 loans out for longer than 21 days, and 32 together. The loan with the missing date (row 20) has no answer and stays NA, which sum(na.rm = TRUE) skips. See Missing and Special Values.

#> [1] 21 10  1 26 26 17
range(lent, na.rm = TRUE)
#> Time differences in days
#> [1] -3 37

sum(late, na.rm = TRUE)

Sequences, periods and cut

seq() on dates dispatches to seq.Date(), and on date-times to seq.POSIXt(). The by argument is a number (days for Date, seconds for POSIXct), a difftime, or a character string with one of "day", "week", "month", "quarter" or "year" (for date-times also "sec", "min", "hour" and "DSTday"), optionally preceded by a positive or negative integer and a space, or followed by s, and abbreviated to any unambiguous prefix (R documentation: seq.Date). Two of to, from and length.out (or along.with) must be given with by. R 4.5.0 made from optional when enough other arguments are supplied, and made seq(from, to) default to one day (R NEWS: Changes in R 4.5.0).

"month" first advances the month without changing the day and, if that is not a valid day, counts forward into the next month: January 31 plus a month is "February 31", which is March 3 (the seq.POSIXt help page says so and points to the examples). The script shows the rollover and two ways to avoid it: build month ends as "the day before the first of the next month", and add a month through POSIXlt fields. Base R has no month arithmetic with +: d + months(1) fails because months() extracts the month name from a date (see the error text on the script). lubridate has a period class for that; see lubridate in one paragraph.

#> [1] "2026-01-01" "2026-01-15" "2026-01-29"

cut() on dates (cut.Date) and date-times (cut.POSIXt) turns them into a factor of periods, which is how to count per week, month, quarter or year. The labels are the first day of each period; breaks can be an interval specification ("day", "week", "month", "quarter", "year", optionally preceded by an integer; for date-times also "sec", "min", "hour" and "DSTday"), a number of intervals, or a vector of cut points. Weeks start on Monday unless start.on.monday = FALSE. Unlike numeric cut(), the default is right = FALSE, so each interval includes its start. A quarter starts on 1 January, 1 April, 1 July or 1 October. Values outside the breaks and NA become NA (R documentation: cut.POSIXt). The levels cover the whole range, so a period with no observation is a level with count zero, which is what a monthly time series needs (see the time-series section). The result is a factor, so Factors applies to it, for example as.Date(cut(d, "month")) converts the labels back to dates.

as.character() and the format warning

as.character() is the function that every other function calls to turn a value into text, and R 4.3.0 changed what it does for dates and times. The NEWS entry says that as.character(<POSIXt>) now behaves more in line with the methods for atomic vectors such as numbers and is no longer influenced by options(), the same for as.character(<Date>), and gives the method arguments digits and OutDec with defaults that do not depend on options(): Use of as.character(*, format = .) now warns. (R NEWS: Changes in R 4.3.0). The consequences, all in the script:

  • as.character(x, format = "%Y") still returns the full ISO text and warns with the message as.character(td, ..) no longer obeys a 'format' argument; use format(td, ..) ?. Older code that used as.character() to format dates returns unformatted text now. The same warning appears for a Date: the warning is raised by the POSIXt method, to which the Date method passes the call. Use format(x, "%Y").

  • A second positional argument is now digits, so as.character(x, "%Y") is an error, 'digits' must be numeric, integer valued.

  • as.character() converts element by element, so a vector with a midnight and a non-midnight time has a text without a time for the first and with a time for the second, whereas format() uses one format for the whole vector. That is also how paste() converts a date-time.

  • as.character() ignores options(digits.secs); use format(x, digits = ), which obeys it (see fractional seconds).

x <- as.POSIXct("2026-06-30 09:30:00", tz = "UTC")

# as.character() gives the ISO text; it ignores options() since R 4.3.0.
as.character(x)
#> [1] "2026-06-30 09:30:00"
as.character(as.Date("2026-06-30"))
#> [1] "2026-06-30"

# Elements are converted one by one: a midnight loses its time.
midnight <- as.POSIXct("2026-06-30 00:00:00", tz = "UTC")
as.character(c(midnight, x))
#> [1] "2026-06-30"          "2026-06-30 09:30:00"
format(c(midnight, x))
#> [1] "2026-06-30 00:00:00" "2026-06-30 09:30:00"
paste("Loan at", x)
#> [1] "Loan at 2026-06-30 09:30:00"

# A format argument is not obeyed, and R warns.
tryCatch(
  as.character(x, format = "%Y"),
  warning = \(w) conditionMessage(w)
)
#> [1] "as.character(td, ..) no longer obeys a 'format' argument; use format(td, ..) ?"
withCallingHandlers(
  as.character(x, format = "%Y"),
  warning = \(w) invokeRestart("muffleWarning")
)
#> [1] "2026-06-30 09:30:00"
tryCatch(
  as.character(as.Date("2026-06-30"), format = "%d/%m/%Y"),
  warning = \(w) conditionMessage(w)
)
#> [1] "as.character(td, ..) no longer obeys a 'format' argument; use format(td, ..) ?"

# A second positional argument is digits, not format.
tryCatch(as.character(x, "%Y"), error = \(e) conditionMessage(e))
#> [1] "'digits' must be numeric, integer valued"

# format() takes the format.
format(x, "%Y")
#> [1] "2026"
format(as.Date("2026-06-30"), "%d/%m/%Y")
#> [1] "30/06/2026"

Time-series objects: ts

The ts class of the stats package represents numeric observations sampled at equally spaced points in time. The language definition describes the underlying attribute: tsp holds the parameters of a time series (start, end and frequency) and is used to handle series with periodic substructure such as monthly or quarterly data (The R Language Definition: Time series attributes). ts(data, start, frequency) creates one, where start is a single number or a pair c(unit, position) (for example c(2025, 1) is January 2025 for frequency = 12) and frequency is the number of observations per unit of time (R documentation: ts).

For the shelf, loans per month is a regular series: one count per calendar month, from January 2025 (the first loan) to May 2026 (the last), without the loan that has the impossible date (59 of the 60 loans are counted). cut(loans$loan_date, "month") gives the months from the first to the last date, including empty ones, so table() of it is exactly 17 counts in order. A series is irregular when observations are not equally spaced, and then a data frame with a Date column is the right structure, not a ts. The accessors frequency(), deltat(), start(), end(), time() and cycle() read the attribute (R documentation: time), and tsp() gets or sets all three (R documentation: tsp). Printing uses a calendar layout for frequencies 4 and 12 (quarters and months) and a plain listing otherwise; print(x, calendar = TRUE) forces the calendar layout.

window(x, start, end) extracts a time range and keeps the class (R documentation: window). It is the right way to subset a ts by time, because x[i] is a plain subset: the ts help page says that subsetting the first dimension returns a vector or matrix. Since R 4.5.0 head() and tail() have methods for ts that keep the time attributes; the 4.5.0 NEWS lists them as new head() and tail() methods for class "ts" proposed by Spencer Graves, and the examples of the ts help page use them (R NEWS: Changes in R 4.5.0). Before R 4.5.0 there was no such method, so head() applied ordinary subsetting, which drops the time attributes; older answers that say to use window() for that are only half right today.

Other operations align the time axes: lag(x, k) shifts the time base, diff(x, lag = ) takes differences (with lag = 12 for a year-on-year change of a monthly series), and arithmetic between two series is done on the common time range, with the warning non-intersecting series when there is none. aggregate(x, nfrequency = , FUN = ) changes the frequency: months to quarters or to years; periods that are not complete at the end are dropped, so 2026 does not appear in the yearly total below (R documentation: aggregate). For plotting a series, see Base Graphics and Devices. Models for time series, and the other packages for them, are covered by the CRAN task view Time Series that the ts help page points to (CRAN Task View: Time Series).

lubridate in one paragraph

lubridate 1.9.5, an add-on package from the tidyverse family, is a convenience layer over the same classes: its parsers (ymd(), dmy(), ymd_hms()) guess the separators and return ordinary Date or POSIXct objects, so the results work with every function on this page; period() and %m+% add calendar months with the end-of-month rule that base R lacks; floor_date(), ceiling_date() and round_date() round to a unit; interval() and %--% build intervals; with_tz() keeps the instant and changes the display zone (the same as format(tz = ) or setting tzone) and force_tz() keeps the clock reading and changes the instant (the same as re-parsing the text with the new tz). Nothing on this page requires it, but it shortens the common cases; attaching it masks date(), intersect(), setdiff() and union() (R prints that list when the package is attached), which is why the script calls everything with lubridate::. See The tidyverse and dplyr for the surrounding ecosystem.
