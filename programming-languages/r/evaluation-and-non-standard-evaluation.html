Evaluation and Non-Standard Evaluation

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. Everything on this page is base R (base, utils and stats) and codetools 0.2-20, the recommended package that ships with R and is behind the R CMD check notes about undefined global variables, except the section on tidy evaluation, which is run against rlang 1.3.0 and dplyr 1.2.1 and is labelled as package material wherever it appears; the lintr 3.4.0 default linters were used only to check the scripts. An R function normally receives values, but R can also hand a function the code that was typed as an argument, and let it decide where and when to run that code. That is non-standard evaluation, and it is how subset(books, pages > 300), with(), lm(pages ~ year, data = books) and the whole tidyverse let you write column names as if they were variables. This page takes the mechanism apart: eval() and the two environments it can be given, data masks, writing a subset()-like function and the mistakes it invites, the call stack, match.call(), do.call(), local(), and then tidy evaluation, explained as a layer built on substitute(), eval() and bquote() and not as a different language.

Every example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines that start with #> are what it printed, in the order it printed them. The scripts also pass the default lintr linters; a # nolint: comment marks a line where the idiom on show is what a default linter dislikes (a column name that is not defined as a variable, for instance), so the linter does not hide the lesson. A script that is cut into several blocks with text between them is one script: run its blocks in order. The names books, loans, shelf_today, loan_days and the book() constructor come from the running library-shelf scenario described on the section index: a script that needs them starts with source("scenario.R"). Where a message contains quotation marks, they are the typographic quotes R prints in a UTF-8 locale. The pieces this page builds on are explained elsewhere: promises and lazy evaluation in Lazy Evaluation and Promises, environments and frames in Scoping, Environments and Closures, argument matching in Functions, and quoting and the structure of calls in Language Objects and Quoting. The formula side of the same idea is in Formulas.

What non-standard evaluation is

Standard and non-standard evaluation

In standard evaluation a function uses the value of each argument: R wraps the argument in a promise, which holds the expression and the caller’s environment, and evaluates it in that environment the first time the function needs it (The R Language Definition: Argument evaluation), so the function sees a number, a string or a data frame. In non-standard evaluation the function looks at the expression the caller typed, through substitute() (see Lazy Evaluation and Promises, which shows that the expression lives in the promise), and then does something else with it: it prints it as a label, evaluates it in a place of its own choosing, or never evaluates it. The Language Definition introduces the building blocks in its chapter on computing on the language (The R Language Definition: Computing on the language), and eval() is described there as the means of evaluating call objects, with the environment as the part that often has to be set to something else (The R Language Definition: More on evaluation).

source("scenario.R")

# Standard evaluation: the argument is evaluated first and the function
# receives its value.
sum(c(310, 288, 96))
#> [1] 694

# Non-standard evaluation: the function receives the expression that was
# typed, and decides what to do with it.
label <- function(x) deparse1(substitute(x))
label(books$pages * 2)
#> [1] "books$pages * 2"
label(shelf_today + loan_days)
#> [1] "shelf_today + loan_days"

# Base R functions that treat an argument as an expression, not a value.
library(stats)
library("stats")
quote(pages > 300)
#> pages > 300
pages <- c(310, 288)
years <- c(2019, 2021)
names(data.frame(pages, years))
#> [1] "pages" "years"
names(data.frame(pages, years * 2))
#> [1] "pages"     "years...2"
class(pages ~ years)
#> [1] "formula"
with(books, max(pages, na.rm = TRUE))
#> [1] 432
nrow(subset(books, genre == "Poetry"))
#> [1] 2

Source: R documentation: substitute

The calls in the last block do five different things with their arguments. label() turns the expression into text and never evaluates it. library(stats) and library("stats") do the same because library() looks at its argument with substitute() and accepts either a name or a string (the argument character.only decides). data.frame(pages, years) takes the column names from the expressions of its arguments, which is why years * 2 becomes the awkward name years...2. A formula quotes both sides. And with() and subset() evaluate the expression inside the data frame, which is the subject of most of this page.

Why R has it

The motivation is that data analysis is mostly about columns, and that writing books$pages three times in an expression is noise. The rlang documentation traces data masking back to the S language, which introduced attach() for data scopes in 1988 and data-masked formulas for modelling functions in 1993; it credits Peter Dalgaard’s frametools package of 1997 as the origin of base::transform() and base::subset(), and Luke Tierney’s change that made formulas remember their environment (published in R 1.1.0) as the step that made hygienic data masking possible. with() followed in 2001 (rlang package documentation: data masking). Thomas Lumley’s note "Standard Nonstandard Evaluation Rules", cited from the ?with help page, is the closest thing to an official statement of the conventions (R Development: Standard Nonstandard Evaluation Rules). The price of the convenience is described in every one of those sources in the same terms: the function has to be told where to look, and the user can no longer tell from the call alone which names are columns and which are variables.

The three questions

Every non-standard evaluation function answers three questions, and a reader who asks them of an unfamiliar function can predict its behaviour. What does it capture, and when? Where does it evaluate what it captured: in which environment, and with which data in front of it? And what does it return, given that assignments made while evaluating usually vanish with the temporary environment? The sections that follow keep coming back to the second question, because every pitfall on this page is a case of the function and its user giving different answers to it.

eval() and its environments

The signature

eval(expr, envir = parent.frame(), enclos = if (is.list(envir) || is.pairlist(envir)) parent.frame() else baseenv()) evaluates the object expr in the environment described by envir. The help page lists what expr may be: a call, an expression vector, a name (looked up, and its binding evaluated), a promise, or any basic type such as a vector, a function or an environment, which are returned unchanged. evalq(expr, envir, enclos) is eval(quote(expr), ...); the help page adds that eval evaluates its first argument in the current scope before passing it to the evaluator, and that evalq avoids this. eval.parent(expr, n) is a shorthand for eval(expr, parent.frame(n)), and local() is evalq() with a new environment as the default (R documentation: eval, evalq, local). The Language Definition says that by default the evaluation frame is the one from which eval is called, and that very often the relevant frame is that of the parent of the current one, because an object that came out of substitute() contains variables that make sense to the caller only (The R Language Definition: More on evaluation).

# The signature: expr, envir and enclos.
args(eval)
#> function (expr, envir = parent.frame(), enclos = if (is.list(envir) ||
#>     is.pairlist(envir)) parent.frame() else baseenv())
#> NULL

# eval() evaluates what it is given in an environment.
x <- 10
eval(quote(x * 2))
#> [1] 20
eval(expression(x, x + 1, x + 2))
#> [1] 12
eval(as.name("x"))
#> [1] 10
eval(42)
#> [1] 42
eval(sum)
#> function (..., na.rm = FALSE)  .Primitive("sum")

# A call is evaluated; a string is a constant and comes back unchanged.
eval("x * 2")
#> [1] "x * 2"
eval(parse(text = "x * 2"))
#> [1] 20
eval(str2lang("x * 2"))
#> [1] 20

Source: The R Language Definition: More on evaluation

The last two evaluations in the block show a mistake that is easy to make. A string is a constant: eval("x * 2") returns the string, and only parse(text = ) or str2lang() turn text into something eval() can run (str2lang() was added in R 3.6.0 as a streamlined parse(text = , keep.source = FALSE) for a single expression, see the version notes). And eval() is an ordinary function, so its argument is evaluated before eval() sees it.

# eval() is a function, so its own argument is evaluated first. What eval()
# receives is the value of that argument, and it evaluates the value.
expr <- quote(x * 2)
eval(expr)
#> [1] 20
eval(quote(expr))
#> x * 2
eval(eval(quote(expr)))
#> [1] 20
eval(x * 2)
#> [1] 20

Source: R documentation: eval, evalq, local

eval(expr) evaluates the call stored in expr. eval(quote(expr)) evaluates the symbol expr, whose value is that call, so it returns the call itself, unevaluated; one more eval() runs it. And eval(x * 2) is not a quotation at all: R computes 20 first and eval() evaluates the constant 20. When the argument is already the value you wanted, the extra eval() is harmless; when the argument has side effects, they happen once for the argument and the result is evaluated again, which is why a function that receives its code unevaluated uses substitute() and not the value.

Calls, expression vectors and quotedness

An expression vector (see Language Objects and Quoting) is evaluated element by element and the value is the value of the last one. The Language Definition points out the subtle difference from a block: a call nested in another call is evaluated as a subexpression, while an expression object stays quoted unless it is passed directly to eval() (The R Language Definition: Evaluation of expression objects).

# An expression vector is evaluated element by element; the value is the
# value of the last one.
ex <- expression(2 + 2, 3 + 4)
length(ex)
#> [1] 2
ex[[1L]]
#> 2 + 2
eval(ex)
#> [1] 7

# A block is a single call with the same effect.
block <- quote({
  2 + 2
  3 + 4
})
eval(block)
#> [1] 7

# The difference: a call inside another call is evaluated when the outer
# call runs; an expression vector keeps its quotedness.
eval(substitute(mode(x), list(x = quote(2 + 2))))
#> [1] "numeric"
eval(substitute(mode(x), list(x = expression(2 + 2))))
#> [1] "expression"

# Printed alike, but one is a call that builds an expression vector.
e <- quote(expression(2 + 2))
ee <- expression(2 + 2)
e
#> expression(2 + 2)
ee
#> expression(2 + 2)
c(mode(e), mode(ee))
#> [1] "call"       "expression"
c(class(e), class(ee))
#> [1] "call"       "expression"

Source: The R Language Definition: Evaluation of expression objects

eval(ex) ran both elements and returned 7. Substituting a call for x gave "numeric", because the call 2 + 2 was evaluated before mode() saw it; substituting an expression vector gave "expression", because the evaluator does not evaluate an expression object recursively. The two objects e and ee print identically, which the manual calls out as a source of confusion, and class() is the way to tell them apart.

The forms of envir

envir can be an environment, which is used as it is; a list or a data frame, which is copied into a temporary environment; a pairlist, which is treated like a list; NULL, which is read as an empty list; or an integer, read as in sys.call(). The help page spells out the consequence of the copy: if the expression changes a component named in the list, the change is lost. Anything else is an error with a message of its own.

source("scenario.R")

x <- "global"
shelf_env <- new.env()
assign("x", "environment", envir = shelf_env)

# envir can be an environment, a list, a data frame, a pairlist or NULL.
eval(quote(x), shelf_env)
#> [1] "environment"
eval(quote(x), list(x = "list"))
#> [1] "list"
eval(quote(x), pairlist(x = "pairlist"))
#> [1] "pairlist"
eval(quote(x), NULL)
#> [1] "global"
eval(quote(paste(title, "-", pages)), books[2L, ])
#> [1] "Pride and Prejudice - 432"

# NULL means an empty list: look-up goes straight to enclos.
eval(quote(x), list(), shelf_env)
#> [1] "environment"

# An integer is a frame number, as in sys.call(): non-negative values count
# from the global environment, negative values count back from the current
# frame.
outer_fn <- function() {
  x <- "outer_fn" # nolint: object_usage_linter.
  inner_fn()
}
inner_fn <- function() {
  x <- "inner_fn" # nolint: object_usage_linter.
  c(
    default = eval(quote(x)),
    frame_1 = eval(quote(x), 1L),
    frame_2 = eval(quote(x), 2L),
    minus_1 = eval(quote(x), -1L),
    parent = eval(quote(x), parent.frame())
  )
}
outer_fn()
#>    default    frame_1    frame_2    minus_1     parent
#> "inner_fn" "outer_fn" "inner_fn" "inner_fn" "outer_fn"

# Anything else is an error, with these messages.
tryCatch(eval(quote(x), "shelf_env"), error = conditionMessage)
#> [1] "invalid 'envir' argument of type 'character'"
tryCatch(eval(quote(x), 1:2), error = conditionMessage)
#> [1] "numeric 'envir' arg not of length one"
tryCatch(eval(quote(x), TRUE), error = conditionMessage)
#> [1] "invalid 'envir' argument of type 'logical'"

Why parent.frame() is the usual enclosure

The expression handed to a function was written by the caller, so the variables it mentions are the caller’s. The default of enclos is parent.frame(), and a default argument is evaluated inside the function it belongs to; the sys.parent help page notes that these functions look at the call stack at the time they are evaluated, and that when they provide default values they are evaluated in the called function and count frames accordingly, naming the envir argument of eval as the example (R documentation: sys.call, sys.frame, sys.function and parent.frame). Inside eval(), then, the default parent.frame() is whoever called eval(). When a function calls eval(substitute(expr), data) without a third argument, that is the function itself, and the caller’s variables are out of reach. The help page of eval says as much in its note: when evaluating in a data frame that was passed to a function, the relevant enclosure is often the caller’s environment, so one needs eval(x, data, parent.frame()). Written as an argument of eval() in the body of the function, parent.frame() is a promise that is evaluated in the function’s frame, and so it gives the function’s caller: the right place.

source("scenario.R")

# The default of enclos is parent.frame(), evaluated inside eval(): it is the
# environment that called eval(), which in a function is the function's own
# frame, not the frame of whoever called the function.
bad_with <- function(data, expr) {
  eval(substitute(expr), data)
}
good_with <- function(data, expr) {
  eval(substitute(expr), data, parent.frame())
}

Assignments, evalq() and eval.parent()

Evaluating in a list evaluates in a copy, so assignments are lost. Evaluating in an environment changes that environment. And eval(N <- 4, env) is a classic trap: the argument is evaluated first, in the caller, so the assignment happens in the caller and eval() receives the value 4. evalq() quotes its argument, and the assignment goes where it was meant to. The Language Definition remarks that evaluating in a given environment may change it, most obviously with an assignment, and that the same is true of lists except that the original does not change because one is working on a copy.

eval.parent() is the tool for the opposite need, a function that is supposed to change a variable of its caller. It evaluates in the frame of the caller of the function that calls it, because inside it parent.frame(n + 1) counts the extra frame of eval.parent() itself, as the printed body shows.

# eval.parent(expr, n) is eval(expr, parent.frame(n)) for the function that
# calls it, which makes it the tool for a function that changes its caller.

}

  visits <- 100

}

Data masks

A data mask by hand

The word "data mask" comes from the tidyverse documentation, but the thing is the temporary environment of the previous section: an environment made from a data frame, in front of the caller’s environment, so that columns hide variables of the same name. The rlang documentation describes data masking as resting on three language features, defusing code with substitute() (or enquo()), first-class environments into which lists and data frames can be turned, and explicit evaluation with eval() (rlang package documentation: data masking). In base R the whole of with() fits in one line, which the first block prints before writing the same function by hand.

source("scenario.R")

# A data mask is an environment built from a data frame (or list) and chained

with() and within()

with(data, expr) evaluates expr in a mask made from data; the help page says the mask has the caller’s environment as its parent, and that when data is already an environment it is used with its existing parent. Assignments made inside take place in the mask, not in the workspace. within(data, expr) examines the mask after the evaluation and returns a modified copy of the data. The help page warns that this can fail for a data frame if the block creates objects that cannot be stored in a data frame, and presents within() as an alternative to transform(). Two details trip people up. New variables are appended in the reverse of the order in which they were created, because within() reads them back from the environment, and a variable removed with rm() inside the block is removed from the result.

Writing a non-standard evaluation function

The pattern

A subset()-like function has three steps: capture the expression with substitute(), evaluate it in the data with the caller as the enclosure, and use the result. The capture must come first, before the argument is touched, because substitute() only returns the expression of a promise that has not been replaced by an assignment (Lazy Evaluation and Promises shows the cases).

source("scenario.R")

# An NSE function in the style of subset(): capture, evaluate in the data,
# in the caller's environment, and use the result.
shelf_subset <- function(data, cond) {
  cond_call <- substitute(cond)
  rows <- eval(cond_call, data, parent.frame())
  data[rows & !is.na(rows), , drop = FALSE]
}
shelf_subset(books, pages > 400)[, c("title", "pages")]
#>                  title pages
#> 2  Pride and Prejudice   432
#> 12    Notes on Gravity   410

# Variables of the caller are found through parent.frame().
longer_than <- function(data, n) {
  shelf_subset(data, pages > n) # nolint: object_usage_linter.
}
nrow(longer_than(books, 300))
#> [1] 6

# The expression is not evaluated until eval() is called, and then once.
trace_cond <- function(data, cond) {
  cond_call <- substitute(cond)
  cat("evaluating:", deparse1(cond_call), "\n")
  eval(cond_call, data, parent.frame())
}
invisible(trace_cond(books, year < 1900))
#> evaluating: year < 1900

Source: R documentation: substitute

shelf_subset(books, pages > 400) found pages in the data. longer_than() calls it with an expression that mentions n, a variable of longer_than(), and it was found because shelf_subset() evaluated in parent.frame(), the frame of longer_than(). And trace_cond() shows that nothing is evaluated until eval() is called, and then once. The line data[rows & !is.na(rows), , drop = FALSE] is the same treatment of NA that subset() applies. These are the three habits that every function of this family needs. The pitfalls start when one of them is missing, or when two such functions meet.

Pitfalls

A variable named like a column. The mask comes first, so a parameter called year is invisible inside year > year, which compares the column with itself. The result is not an error but an empty data frame. The cure is a parameter name that cannot be a column name, or an explicit pronoun (see tidy evaluation below).

A column that does not exist, and a variable that does. If the name is not in the data, R continues to the enclosure. When no variable has that name the error is the clear object 'price' not found, but when the caller’s environment happens to contain a variable with the same name, the expression is silently evaluated with it: the result of publisher == "Nobody" is an empty data frame, not an error, because the global string publisher was used. The longer the workspace and the more generic the names, the more likely this is, and it is the reason scripts that rely on non-standard evaluation break when a variable is added far away.

Forwarding an argument. A function that receives a condition and passes it on to another non-standard evaluation function gives the second one the symbol cond, not the expression that the user typed. The second function evaluates cond in the data, does not find a column of that name, looks in the frame of the first function, finds a promise there, and forces it in the global environment, where pages does not exist. The user sees an error about a name they never wrote, in a function they never called.

source("scenario.R")
shelf_subset <- function(data, cond) {
  rows <- eval(substitute(cond), data, parent.frame())
  data[rows & !is.na(rows), , drop = FALSE]
}

# 1. A function argument named like a column: the column wins.
books_after <- function(data, year) {
  shelf_subset(data, year > year)
}

#> [1] 0

The standard-evaluation twin

The reliable way out of the forwarding problem is to separate the two jobs. A function that takes the expression and the environment as ordinary arguments does the work and can be called from anywhere; the non-standard function is a two-line wrapper that captures and passes on. The convention has a history: dplyr 0.3 (2014) gave every function that does non-standard evaluation a standard-evaluation version ending in an underscore, powered by the lazyeval package, and dplyr 0.7.0 (2017) replaced that approach with tidy evaluation (dplyr package documentation: NEWS); the trailing underscore is still the clearest name for a twin in plain base R. A third argument env = parent.frame() carries the environment that the caller means.

source("scenario.R")

# The standard-evaluation twin takes the expression and the environment as
# ordinary arguments, so it can be called from any other function.
shelf_subset_ <- function(data, cond_call, env = parent.frame()) {
  rows <- eval(cond_call, data, env)
  data[rows & !is.na(rows), , drop = FALSE]
}

# The non-standard function is a thin wrapper that captures once.
shelf_subset <- function(data, cond) {
  shelf_subset_(data, substitute(cond), parent.frame())
}

# Another function can forward its own argument with the same two lines.
long_books <- function(data, cond) {
  shelf_subset_(data, substitute(cond), parent.frame())
}
nrow(long_books(books, pages > 300))
#> [1] 6

# It also works with a variable that lives in the caller's caller.
count_longer <- function(min_pages) {
  nrow(long_books(books, pages > min_pages)) # nolint: object_usage_linter.
}
count_longer(350)
#> [1] 4

# And with an expression built from data: a list of conditions.
conditions <- list(quote(pages > 300), quote(year < 2000))
vapply(
  conditions,
  \(cond) nrow(shelf_subset_(books, cond)),
  integer(1L)
)
#> [1] 6 3

# do.call() passes a built expression to the NSE function itself.
min_pages <- 400
cond <- bquote(pages > .(min_pages))
cond
#> pages > 400
nrow(do.call(shelf_subset, list(books, cond)))
#> [1] 2
nrow(eval(bquote(shelf_subset(books, pages > .(min_pages)))))
#> [1] 2

Source: R documentation: do.call

long_books() forwards its own argument with the same two lines the original used, and finds min_pages in count_longer() even though the function that does the evaluation is two levels away. The twin also makes it possible to run a list of conditions, which a purely non-standard function cannot do, and do.call() or bquote() can build the call for the non-standard function when only that is available. do.call(shelf_subset, list(books, cond)) works because the call that do.call() builds contains the call object pages > 400 as an argument, and substitute() inside shelf_subset() returns it; the help page of do.call() warns that the behaviour of substitute() under do.call() is undefined and subject to change, so the pattern is fine in a script and not something a library should rest on.

Undefined globals and R CMD check

A column used as a bare name looks, to a static checker, like a reference to a variable that nobody defined. R CMD check runs codetools over the code of a package and reports no visible binding for global variable as a NOTE; lintr reports the same with its object_usage_linter, and an IDE shows a squiggle. The checker is right in general and cannot know that this function is going to be evaluated in a data mask. The declaration that tells the check which names are defined elsewhere is documented on the help page of globalVariables() (R documentation: globalVariables); the check is the work of codetools (codetools package documentation: checkUsage).

# R CMD check and lintr find the names a function uses without defining them.
long_books <- function(data, n) {
  subset(data, pages > n) # nolint: object_usage_linter.
}
codetools::checkUsage(long_books, name = "long_books", all = TRUE)
#> long_books: no visible binding for global variable ‘pages’
codetools::findGlobals(long_books)
#> [1] "{"      ">"      "pages"  "subset"

# Reading the column through `[[` or `$` is ordinary evaluation: the name is
# a string or a member, so there is nothing to report.
long_books_std <- function(data, n) {
  data[!is.na(data$pages) & data$pages > n, , drop = FALSE]
}
codetools::checkUsage(long_books_std, name = "long_books_std", all = TRUE)

# Declaring the name as a local variable silences the report, but it hides
# the problem: the value is NULL until the data mask is in place.
long_books_null <- function(data, n) {
  pages <- NULL
  subset(data, pages > n)
}
codetools::checkUsage(long_books_null, name = "long_books_null", all = TRUE)

Source: codetools package documentation: checkUsage

codetools::checkUsage() printed the report that R CMD check turns into a NOTE for long_books(): the name of the function, then no visible binding for global variable ‘pages’. There are four ways to deal with it, in order of preference. Use ordinary evaluation inside package code (data$pages or data[["pages"]], as in long_books_std()), where nothing needs declaring. In functions that must use the data mask, tell the checker the names: utils::globalVariables(c("pages", "year")) at the top level of the package, once, which the help page describes as naming objects that should be regarded as defined globally when the check is applied (a package-wide declaration, so a typo in one of those names is no longer reported anywhere). With tidy evaluation, use the .data pronoun, .data$pages, imported from rlang, which makes the reference explicit (see below). And do not assign pages <- NULL in the function body to silence the note: it works against the checker and creates a real local variable, and in long_books_null() above a misspelled column would not raise object 'pages' not found: the expression would silently see the NULL.

Strings or expressions?

A column name arrives in a function either as a bare name (mean_of(books, pages)) or as a string (mean_of(books, "pages")). Standard R code uses strings and [[, which needs no special treatment; a non-standard function converts the bare name with substitute(). Supporting both in one function looks friendly and is fragile, because the function cannot tell whether the symbol it received is the name of a column or the name of a variable that holds a string.

source("scenario.R")

# A string names a column; the standard way to use it is `[[`.
column <- "pages"
books[[column]][1:4]
#> [1] 387 432 214 198
mean(books[[column]], na.rm = TRUE)
#> [1] 268.2143

# A function that takes a column as a bare name needs a conversion.
mean_of <- function(data, col) {
  col <- substitute(col)
  mean(eval(col, data, parent.frame()), na.rm = TRUE)
}
mean_of(books, pages)
#> [1] 268.2143
mean_of(books, pages / 100)
#> [1] 2.682143

# `col` is a name or a string depends on a test that can be fooled.

  col <- substitute(col)
  if (is.character(col)) {
    col <- as.name(col)
  }
  mean(eval(col, data, parent.frame()), na.rm = TRUE)
}

Source: R documentation: parse, str2lang, str2expression

mean_of_either(books, column) returned NA with a warning, because column is a variable that holds "pages": the function treated the symbol as a column name, did not find one, and evaluated it as a variable holding a string. The two APIs should not be mixed in one argument. When a string must become an expression, str2lang() parses exactly one expression and fails with parsing result not of length one, but 2 for more, and parse(text = ) produces an expression vector. Both execute whatever the text says, so they are for text the program built itself, not for text a user typed into a form; and in nearly every other case an index with [[ does the job without evaluating anything (R FAQ 7.21: How can I turn a string into a variable? gives that advice for the variable-name case: get() or assign() at most, and preferably a list indexed by name, or substitute() with as.name() when a call has to be built; it is applied in the table at the end of this page).

Building a call instead of text

If a function must run code that varies, build the call as an object rather than as text. bquote() writes the call and splices values into it with .(), call() and as.call() assemble it from parts, and substitute() with a list fills in the names of an expression. The four calls in the block below are the same call, and a call is a list whose first element is the function.

local() and evalq()

local(expr, envir = new.env()) is evalq() in a fresh environment. The source printed below is the whole definition: eval.parent(substitute(eval(quote(expr), envir))) builds a call to eval() with the quoted expression and runs it in the caller’s frame, so the default new.env() is created there and becomes the scope of the block. The help page presents it as the way to make anonymous recursive functions and as a kind of limited namespace, since the variables defined in the environment are not visible from outside. The scoping page shows more uses (Scoping, Environments and Closures); the points that belong here are what it is made of and how it differs from a brace block.

A function created inside local() keeps the environment of the block, which is how due_date() carries grace_days with it while the workspace stays clean (that is a closure, built on purpose; see Function Factories and Higher-Order Functions). local(copies, shelf_env) and evalq(copies, shelf_env) are the same call. A { } block, on the other hand, is not a scope: the variable assigned inside it exists in the workspace afterwards. Because local() is implemented with eval(), a return() inside it ends the local() call and not the surrounding function (outer_fn() returned "after local"), and a <<- assigns in the enclosing environments of the block, where it will find the variable or create a global one (the last example created and changed a global counter). Both are reasons to prefer a small named function when the block gets long.

The call stack

Every function call creates a frame, and the frames are linked in the order of the calls. The Language Definition lists the accessors in its section on the call stack: sys.call, sys.frame, sys.nframe, sys.function, sys.parent, sys.calls, sys.frames, sys.parents, sys.on.exit, sys.status and parent.frame, and notes that making variables defined higher up the stack available is dynamic scope, which contradicts the lexical scope R normally uses; some functions, particularly those that use and manipulate model formulas, need to simulate it by directly accessing the stack (The R Language Definition: The call stack). The help page gives the numbering: the global environment is frame 0, and each function evaluation increases the stack by one. Non-negative which values are frame numbers and negative values count back from the current frame. The parent of a frame is the environment the function was called from, which is not necessarily the previous frame number and is not the environment where the function was defined.

# Each function call adds a frame. sys.call(), sys.function() and
# sys.frame() read a frame by number; parent.frame() reads the caller's.
outer_fn <- function(a) middle_fn(a + 1)
middle_fn <- function(b) inner_fn(b * 2, label = "x")
inner_fn <- function(v, label) {
  list(
    nframe = sys.nframe(),
    n_frames = length(sys.frames()),
    own_call = sys.call(),
    caller_call = sys.call(-1L),
    first_call = sys.call(1L),
    parents = sys.parents(),
    parent_number = sys.parent()
  )
}

inner_fn() ran at frame 3, with sys.parents() giving 0 1 2: each function was called from the one before. sys.call(-1L) is the call that created the caller, sys.call(1L) the call that started the whole stack, and sys.calls() the whole stack at once, which is what a traceback is made of and what withCallingHandlers() can print without unwinding (see Debugging). sys.call() returns the call as the caller wrote it: the arguments are not matched or named, so describe_call(label = "a", 1) shows the arguments in the order they were typed, which is the reason match.call() exists (next section). length(sys.frames()) is the same number as sys.nframe().

parent.frame() is not always the previous frame

parent.frame(n) is shorthand for sys.frame(sys.parent(n)), the help page says, and it follows the chain of callers, not the numbers. A function that is called by another function that was called by a third has parent.frame(2) as the environment of the third, if the chain is linear. The chain is not linear when a function is invoked through another: lapply() is a function with a frame of its own, so the caller of the function it applies is the frame of lapply(); do.call() evaluates the call in the envir you give it, so that is the parent frame in that case. And code evaluated by eval() sits deeper in the stack than the function that called eval(), because the stack holds both the call to the eval() closure and the context that the evaluator creates for the evaluation, and both print as the call to eval().

# parent.frame() is the frame of the function that called this one, which
# is not always the frame one level up the stack.
whoami <- function() parent.frame()

direct <- function() identical(whoami(), environment())
direct()
#> [1] TRUE

# Called through lapply(): the caller is lapply()'s own frame, so the
# function frame is two generations up.
via_lapply <- function() {
  me <- environment()
  lapply(1, \(i) {
    c(
      parent = identical(parent.frame(), me),
      grandparent = identical(parent.frame(2L), me)
    )
  })[[1L]]
}
via_lapply()
#>      parent grandparent
#>       FALSE        TRUE

# Called through do.call(): the caller is the environment given as envir.
via_do_call <- function() {
  me <- environment()
  elsewhere <- new.env()
  c(
    default = identical(do.call(whoami, list()), me),
    envir = identical(do.call(whoami, list(), envir = elsewhere), elsewhere)
  )
}
via_do_call()
#> default   envir
#>    TRUE    TRUE

# context of the evaluator are both on the stack, and both print as eval().
frames_inside_eval <- function() {
  c(
    plain = sys.nframe(),
    in_eval = eval(quote(sys.nframe()))
  )
}
frames_inside_eval()
#>   plain in_eval
#>       1       3
calls_inside_eval <- function() eval(quote(sys.calls()))
calls_inside_eval()
#> [[1]]
#> calls_inside_eval()
#>
#> [[2]]
#> eval(quote(sys.calls()))
#>
#> [[3]]
#> eval(quote(sys.calls()))
#>

Source: R documentation: sys.call, sys.frame, sys.function and parent.frame

In the first function whoami() returned the frame of direct() as expected. Through lapply(), parent.frame() was not the frame of via_lapply() but the frame of lapply(), and parent.frame(2L) was. Through do.call() with an envir, the parent was exactly that environment. The code in frames_inside_eval() ran at frame 3, while the function itself ran at frame 1, and sys.calls() shows the two eval() entries. This is why the help page cautions that internal functions may or may not set contexts and so may not be counted, that S3 methods can do surprising things, and that, as an effect of lazy evaluation, the stack functions look at the stack at the time they are evaluated and not at the time they are called.

The same fact explains a trap in the rule to evaluate a default in the callee. parent.frame() as a default argument is evaluated when the argument is first used, inside the function, so it counts frames from there and gives the function’s caller (a function f(env = parent.frame()) is correct). The help page advises against passing calls to the sys. functions as arguments to other functions, because they still look at the stack and count from the frame of the function evaluation they were called from. When the environment must be captured at a particular moment, capture it in a variable at the top of the function: caller <- parent.frame().

match.call(): the call with every argument named

match.call(definition = sys.function(sys.parent()), call = sys.call(sys.parent()), expand.dots = TRUE, envir = parent.frame(2L)) returns the call in which all the specified arguments are given by their full names, in the order of the formals. The Language Definition introduces it as the function to use instead of sys.call() when a function needs the call with every actual argument bound to its formal (The R Language Definition: Manipulation of function calls). The help page lists the two circumstances where it is most useful: to record the call for later reuse, as the model-fitting functions do in the call element of their result, and to pass most of the call to another function, often model.frame(), usually with expand.dots = FALSE and the ... element removed (R documentation: match.call). The envir argument, new in R 3.2.0, is where the ... of the call are retrieved from; it matters when a function passes its own dots on, as in the fifth use in the second block below.

The third call shows that partial matching happens before the call is recorded: da was expanded to days_late and the unnamed 3 became rate, which is what R would have done when running the call. With expand.dots = FALSE the extra arguments are collected into one element whose tag is ...; in R 4.6.1 this element is a pairlist (the call prints as ... = pairlist("a", note = "waived")), and the manual describes it as a pairlist, not a call to list() as in S. match.call() can match a call that was never run (match.call(shelf_fine, quote(...))), it refuses primitives, and an argument matched twice is an error with the message shown.

A matched call is a list: the first element is the function, the others are the arguments, tagged with the formal names. That is why the idioms of modelling functions work: set an element to NULL to delete an argument, assign to a tag to add or change one, replace the first element (with a name, not a string) to call another function, and evaluate the result in the parent frame, where the expressions make sense. The manual shows the start of lm() as its example.

sys.call() and the call that errors show

sys.call() is the call as typed, which makes it the right tool for messages. stop() records sys.call(-1) of its own frame, the call of the function that raised the error, and that is what conditionCall() returns and what Error in check_pages(-1) : prints; stop(call. = FALSE) omits it. A helper that signals an error on behalf of its caller can build a condition with a call of its choosing, as fail_in_caller() does with sys.call(-1L). The conditions page covers the classes and the handlers (Conditions and Error Handling); here the point is where the call comes from.

Why do.call("f", list(big_object)) reads badly

The list is turned into a call whose arguments are the values themselves, and everything that reports the call reports the values: error messages, traceback(), sys.call(), match.call() and substitute(). For a small vector the call is short. For a data frame it runs to dozens of lines, and a function given as an object instead of a name puts its whole definition in the call, which is what the traceback of an error shows. The help page warns that the behaviour of substitute() and similar functions under do.call() is undefined and subject to change.

delayedAssign() and the environment of a closure

delayedAssign(x, value, eval.env = parent.frame(1), assign.env = parent.frame(1)) creates a promise by hand: it binds x in assign.env to the expression value, which is evaluated, once, in eval.env the first time x is used (R documentation: delayedAssign). A function argument is the same object, made by the call; the page on Lazy Evaluation and Promises has the life cycle of a promise and its pitfalls, and the block below only shows the pieces that matter for non-standard evaluation: the evaluation is delayed, the expression stays visible to substitute() inside a function, and the two environments are independent.

The environments involved

In an NSE call four environments are in play, and most mistakes are a confusion between two of them. The frame of the function that does the evaluation is where its own variables live; its caller’s frame (parent.frame()) is where the user’s variables live; the closure environment (environment(f)) is where the function was created, which is where free variables of its body are found; and the data mask is a temporary environment between the other two. The scoping page treats the first three in depth (Scoping, Environments and Closures).

source("scenario.R")

# Four environments take part in every NSE call. For each, identical() says
# which one it is.
make_counter <- function() {
  count <- 0
  function() {
    count <<- count + 1 # nolint: assignment_linter.
    count
  }
}

#> [1] 1

probe <- function(data) {
  list(
    frame = environment(),
    caller = parent.frame(),
    defined_in = environment(sys.function()),
    mask = eval(quote(environment()), data, parent.frame())
  )
}
caller_fn <- function(data) {
  e <- probe(data)

    probe_frame_is_callers = identical(e$frame, environment()),
    parent_frame_is_callers = identical(e$caller, environment()),
    defined_in_global = identical(e$defined_in, globalenv()),
    mask_parent_is_callers = identical(parent.env(e$mask), environment()),
    mask_has_columns = all(names(data) %in% ls(e$mask))
  )
}

Quosures: an expression with its environment

The first difference is what is captured. substitute() returns an expression and parent.frame() returns the environment, as two separate pieces of information that the programmer has to keep together. rlang::enquo() captures both in one object, a quosure. A quosure carries an expression, which quo_get_expr() returns, and an environment, which quo_get_env() returns; it is hygienic because it evaluates in the environment it carries, and maskable because, when evaluated in a data mask, the mask comes first (rlang package documentation: What are quosures and when are they needed?). The documentation points out that quosures are inspired by the environment-tracking mechanism of formulas and that they resemble promises, with one difference: a promise is evaluated once and cached, while a quosure can be evaluated repeatedly, in different masks, which is what a grouped computation needs. The class vector c("quosure", "formula") and the printed ^ in front of the expression are the visible signs.

Forwarding with eval_tidy() and {{ }}

eval_tidy(expr, data) is eval() with a data mask that also understands quosures and the .data pronoun. A function built on it has the same forwarding problem as the base version, because enquo() captures one level up: whatever the user typed, as seen by the function that is called directly. The solution in tidy evaluation is to forward the quosure, and the embrace operator is the way to write it: {{ cond }} captures the argument cond of the current function, with the environment of the user, and injects it into the call. The rlang documentation describes it as combining enquo() and !! in one step (rlang package documentation: Embrace operator).

source("scenario.R")
library(rlang)

# The forwarding problem again, with eval_tidy(): the argument is captured
# one level up, so it is the symbol `cond` in the first function.
count_rows <- function(data, cond) {
  cond <- enquo(cond)
  sum(eval_tidy(cond, data), na.rm = TRUE)
}
count_rows(books, pages > 300)
#> [1] 6

report_rows <- function(data, cond) {
  count_rows(data, cond)
}
tryCatch(
  report_rows(books, pages > 300),
  error = conditionMessage
)
#> [1] "object 'pages' not found"

# Embracing forwards the user's expression, with the user's environment.
report_rows <- function(data, cond) {
  count_rows(data, {{ cond }})
}
report_rows(books, pages > 300)
#> [1] 6

# The expression keeps its own environment, so a variable of the user's
# function is found even though the data is looked up in the first.
count_longer <- function(min_pages) {
  report_rows(books, pages > min_pages) # nolint: object_usage_linter.
}
count_longer(350)
#> [1] 4

peek <- function(data, cond) {
  quo_get_expr(enquo(cond))
}
peek_via <- function(data, cond) {
  peek(data, {{ cond }})
}
peek_via(books, pages > 300)
#> pages > 300

The first report_rows() failed with object 'pages' not found, exactly the failure of long_books() earlier, for the same reason: count_rows() captured the symbol cond, evaluated it in the frame of report_rows() and forced the original promise in the global environment, where there is no pages. With {{ cond }} the second version worked and the quosure that reached count_rows() held the user’s expression and the user’s environment. count_longer() shows what the environment is for: min_pages is a variable of that function, the data mask is books, and the expression pages > min_pages is evaluated with both, as in the base pattern with parent.frame(), but across any number of function boundaries. The peek_via() call returns the expression typed by the user, not the symbol cond.

The .data and .env pronouns

Data masking has the ambiguity that every function on this page had: a column and a variable with the same name, with the column winning. The tidy remedy is a pair of pronouns. .data$year is the column and .env$year is the variable of the environment (the rlang documentation says that .data retrieves data-variables from the data frame and .env retrieves env-variables from the environment, so the lookup is explicit and there is no ambiguity; rlang package documentation: .data and .env pronouns). .data[[col]] reads a column whose name is in a string, and it never confuses col with a column called col: the variable inside the double brackets is always an env-variable. The opposite mistake is silent: filter(books, col > 300) compares the text "pages" with the number 300, which is true, and keeps every row without an error.

Injection: !! and !!!

Embracing covers the common case. The general mechanism underneath is injection, also called quasiquotation: changing a piece of code before R evaluates it. !!x injects the value or expression x into a defused expression, and !!!x splices a list of values or expressions as separate arguments. The rlang documentation says that !! works only in functions that take defused and data-masked arguments (including those defused with {{ }} or the en-prefixed operators like enquo()) and inside inject(), and that with base functions inject() has to be used to enable it; it also says that in tidyverse code !! is no longer a common pattern, because the .env pronoun solves the ambiguity problem more naturally and the embrace operator makes defuse-and-inject easier to learn (rlang package documentation: Injection operator). The splice operator !!! provides the same functionality as do.call(), as that page puts it, turning a list of inputs into distinct arguments (rlang package documentation: Splice operator).

The base counterparts are bquote() with .() for a value and with ..() and splice = TRUE for a list (the splicing form was added to bquote() in R 4.0.0), as.call() on a list that starts with the function, and substitute() with a list; the two families are compared at the end of this section.

The first group compares a free variable, a value injected with !! and the same value injected with bquote(): expr(pages > !!min_pages) and bquote(pages > .(min_pages)) both printed pages > 300, so the number is part of the expression and no longer depends on the environment, which is why injecting a value is a way to settle the column-versus-variable ambiguity. sym("pages") is as.name("pages"), and syms() makes a list of symbols; injecting them with !! and !!! is the string-to-column bridge. !! binds like unary minus, so !!a + b is (!!a) + b and !!a * b + 3 is (!!a) * b + 3, as the rlang NEWS says of version 0.2.0 (rlang package documentation: NEWS). Outside a function that supports injection, !! is the double negation of base R: !!TRUE is TRUE and !!c(0, 1) is FALSE TRUE, which is why a stray !! in ordinary code is a silent mistake. Dots, names and tidy selection

Dots need no special syntax: a function that passes ... to a data-masking verb passes the expressions untouched, and the verb defuses them. enquos(...) captures the dots as a list of quosures when the function needs to look at them, and the base counterpart is substitute(list(...)) or match.call(expand.dots = FALSE)$.... Names built from the data or from a variable use the := operator with glue syntax on the left: "{{ var }}_mean" := ... takes the name from the argument, and "{prefix}_pages" takes it from a variable. Selecting columns is a second mini-language, tidy selection, and it needs a different bridge for each kind of indirection: embrace an argument, wrap a character vector in all_of() (or any_of(), which ignores missing names). The dplyr article summarises this as two forms of indirection: a data-variable in a function argument is embraced, and an env-variable holding a character vector is indexed with .data[[ ]] for data masking and wrapped in all_of() for tidy selection.
