Performance, Profiling and Benchmarking

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Checked against R 4.6.1 (2026-06-24) on 2026-10-20; R 4.6.2 is scheduled for 2026-10-29. The timing and profiling tools of R itself are in base R (system.time() and proc.time() in base, Rprof() and summaryRprof() in utils, the byte-code compiler in the compiler package that ships with R), and those examples need nothing else. The comparisons use four add-on packages: bench 1.1.4, microbenchmark 1.5.0 (a community package, labelled as one), profvis 0.4.0 (with htmlwidgets 1.6.4 and pandoc 3.1.3 to save its widget) and data.table 1.18.6.1; callr 3.8.0 starts fresh R processes for two examples; one example compiles C++ through Rcpp 1.1.2 with g++ 13.3; and the lintr 3.4.0 default linters were used only to check the scripts. Making R code fast comes down to one habit: measure first. Guessing which line is slow is wrong often enough that the manuals, the package documentation and every serious guide say the same thing, and R ships the tools to do it: a stopwatch (system.time()), a sampling profiler (Rprof()), and, in packages, benchmarking and visualisation (bench::mark(), microbenchmark(), profvis()). Only after a measurement says where the time goes does it make sense to reach for the remedies on the second half of the page: vectorising, preallocating, avoiding copies, vapply(), better matrix algebra, the byte-code compiler and its JIT (default since R 3.4.0), a faster BLAS, data.table and, last, a hot loop written in C++.

Every example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines that start with #> are what it printed. The scripts also pass the default lintr linters, without any # nolint comment: the slow idioms on show (a growing vector, a loop that could be vectorised) are not ones that the default linters flag. The names books, loans, shelf_today, loan_days and the book() constructor come from the running library-shelf scenario described on the section index: a script that needs them starts with source("scenario.R"). No timing on this page is a number of seconds from the machine that ran the examples. Seconds depend on the processor, on what else is running, on the BLAS and on its threads, and a table of them would be wrong on every other computer. So a system.time() result is printed with <n> in place of each number, a bench::mark() result is shown through its relative columns (summary(b, relative = TRUE), every value divided by the smallest) rounded to a power of ten or to one digit because even the ratios move from run to run, a summaryRprof() table keeps its function names and its order but has <n> for the seconds and percentages, and wherever a number could not be made stable the script prints a comparison (TRUE when the slow version is at least a hundred times slower, for instance). The one measurement that does not vary is memory: the bytes a function allocates are the same on every run, so mem_alloc columns are printed as they are. The lines edited this way are the ones that contain <n>, and they are the only edits made to the output. Where a message contains quotation marks, they are the typographic quotes R prints in a UTF-8 locale. A path in an error message is shortened to <tmp>. The BLAS of the machine that ran the examples is an OpenBLAS build, and the page never prints the library path that extSoftVersion() and La_library() return.

The neighbouring pages cover what this page only points at. Vectorisation and Iteration explains vectorised functions, the growing-vector trap and the byte-compiler in the first place; this page measures them and goes further on the measuring side. Memory and Copy Semantics is the place for tracemem(), Rprofmem(), gc() and copy-on-modify, Parallel and Asynchronous Computing for using several cores, and Interfacing C, C++ and Fortran for the compiled code that the last section only previews. The data.table package has its own page, data.table, and matrix algebra is in Matrices and Arrays.

Measure first

The manual Writing R Extensions has a chapter called "Tidying and profiling R code" for code that is worth keeping and sharing, and the advice of its section on profiling is the whole method in two sentences: profile to find the bottlenecks, then consider replacing the slow R code, perhaps with compiled code (Writing R Extensions: Profiling R code for speed). The profvis documentation states why: intuition leads people to optimise things that are a small share of the run time, and some of the commonly held beliefs are false (that the *apply functions are inherently faster than a for loop is the example it gives). The arithmetic behind it is Amdahl’s law. If a part of the program takes a share \( p \) of the run time and is made \( s \) times faster, the whole program takes the fraction below of its old time.

\[ \frac{T_{\rm new}}{T_{\rm old}} = (1 - p) + \frac{ p }{ s } \]

A loop that takes 10% of the run time (\( p = 0.1 \)) and is made five times faster (\( s = 5 \)) leaves the program at 92% of its old time, an 8% saving, however pleased one is with the five. Measuring first tells which \( p \) is large. The working loop is the same every time: write the clearest correct code, add a test that pins its result, measure it on realistic data, profile to find the part that matters, change that part, check that the result is unchanged, and measure again. The remedies in the second half of this page are all things to try at the fourth step, never first.

Timing code

system.time and proc.time

system.time(expr) calls proc.time(), evaluates expr, calls proc.time() again and returns the difference. The result is an object of class proc_time: a numeric vector of length five holding the user and system CPU time of the R process (user.self, sys.self), the elapsed ("real", wall-clock) time (elapsed), and the user and system time of child processes that R has waited for (user.child, sys.child). Its print method folds the child times into the process times and shows three numbers, called user, system and elapsed. The help page defines the first two as the CPU time charged to the process for executing user instructions and for work done by the system on its behalf, and says that child times are not available on Windows and are NA there. The clock resolution is system specific: on Unix-alikes times are rounded down to milliseconds, and on Windows they are typically available to 10 ms (R documentation: proc.time). Two consequences follow. Anything shorter than a few milliseconds cannot be timed once with system.time(), and elapsed can be much smaller than user when a multi-threaded BLAS or other library keeps several cores busy at once.

The difference between CPU time and elapsed time is the first thing to understand about any timing. Sys.sleep() waits without computing: it costs elapsed time and no CPU time. A computation costs both. The script below shows the structure of the result, the sleeping against the computing, that the expression runs in the calling environment (so an assignment inside system.time() is visible afterwards), and the gcFirst argument, whose default TRUE runs a garbage collection just before the evaluation so that its cost is not charged to the expression that happens to trigger it.

# system.time() returns an object of class "proc_time" with five numbers.
set.seed(1)
st <- system.time(sort(runif(2e6)))
class(st)
#> [1] "proc_time"
names(st)
#> [1] "user.self"  "sys.self"   "elapsed"    "user.child" "sys.child"
length(unclass(st))
#> [1] 5

# print() combines the child times with the process times and shows three.
st
#>    user  system elapsed
#>     <n>     <n>     <n>

# Waiting costs elapsed time but no CPU time.
sleeping <- system.time(Sys.sleep(0.25))
sleeping[["elapsed"]] >= 0.25
#> [1] TRUE
sleeping[["user.self"]] < sleeping[["elapsed"]]
#> [1] TRUE

# Computing costs both.
busy <- system.time(for (i in seq_len(3e6)) i)
busy[["user.self"]] > 0
#> [1] TRUE

# The expression runs in the calling environment, so an assignment stays.
system.time(total <- sum(sort(runif(2e6))))
#>    user  system elapsed
#>     <n>     <n>     <n>
total > 0
#> [1] TRUE

# proc.time() is the clock behind it; subtracting two readings is the same.
start <- proc.time()
invisible(sort(runif(2e6)))
spent <- proc.time() - start
class(spent)
#> [1] "proc_time"
spent[["elapsed"]] >= 0
#> [1] TRUE

# Timing without the garbage collection that normally precedes it.
st2 <- system.time(sort(runif(2e6)), gcFirst = FALSE)
inherits(st2, "proc_time")
#> [1] TRUE

Source: R documentation: system.time

If the expression fails, system.time() still reports how far it got, in a message that starts with Timing stopped at: and gives the same three numbers (see the section on common errors below). It is a good tool for a first look and for a long job, because it adds no overhead and no dependency. It is a poor tool for comparing two fast expressions, which is the reason for the next two sections.

One measurement is not enough

A single timing is one sample from a noisy process. The computer is doing other things, the CPU changes its clock speed, the memory caches are warm or cold, the garbage collector runs when it happens to, and the first time anything is used it can cost more than later: a package namespace is loaded, a function is byte-compiled by the JIT (a small closure on its second call, a closure with a loop on its first; see the section on the compiler), a file is read from disk instead of the cache. The remedy is the usual one in measurement: repeat, and report a statistic that does not move with the outliers, the minimum or the median rather than the mean. The script below repeats a computation ten times and shows that the numbers differ, shows that the first load of a package costs far more than the second, and times the parts of a computation separately, because the total of a section of a script hides which of its lines is slow.

# One timing is one sample from a noisy process: repeat it and look at the
# spread.
set.seed(42)
work <- function() sort(runif(5e5))
elapsed <- replicate(10, system.time(work())[["elapsed"]])
length(elapsed)
#> [1] 10
max(elapsed) > min(elapsed)
#> [1] TRUE

# The first use of something can cost far more than the later ones: here the
# first call loads and attaches the namespace of a package, the second finds
# it already loaded.
first <- system.time(loadNamespace("data.table"))[["elapsed"]]
second <- system.time(loadNamespace("data.table"))[["elapsed"]]
first > 10 * second
#> [1] TRUE

# Timing a whole section hides which part is slow: time the parts.
parts <- c(
  generate = system.time(v <- runif(2e6))[["elapsed"]],
  sort = system.time(s <- sort(v))[["elapsed"]],
  cumulate = system.time(cs <- cumsum(s))[["elapsed"]]
)
names(parts)
#> [1] "generate" "sort"     "cumulate"
parts[["sort"]] > parts[["cumulate"]]
#> [1] TRUE

Source: R documentation: system.time

Writing the loop by hand (for (i in 1:100) system.time(...) and averaging) is what the next two tools automate, with the repeats, the warm-up, the choice of statistic, the check that the expressions agree, and, in bench, the memory.

bench::mark

bench::mark() is the benchmarking function of the bench package (version 1.1.4 here; bench package documentation: mark). It takes any number of expressions, named or not, evaluates each at least twice, once to measure the memory allocation and store the result, and then as many times as needed to fill min_time seconds, and returns a tibble with one row per expression. Its arguments, with their defaults, are these.

Argument Default Meaning

...

none

The expressions to compare. A name becomes the expression column; without one the deparsed expression is used.

min_time

0.5

The minimum number of seconds to keep running each expression. Inf runs max_iterations times instead.

iterations

NULL

If given, run each expression exactly this many times, overriding min_iterations and max_iterations.

min_iterations, max_iterations

1, 10000

Lower and upper bound on the number of timed runs.

check

TRUE

Compare the results with all.equal(); FALSE skips the check and does not store the results; a function of two arguments is called on each pair of results to decide whether they agree.

memory

capabilities("profmem")

Track allocations with utils::Rprofmem(). Memory allocated outside the R heap (malloc() or new in compiled code) is not counted.

Source: bench package documentation: mark

The columns of the result are expression (class bench_expr), min and median (bench_time), itr/sec (iterations per second), mem_alloc (bench_bytes), gc/sec, n_itr (the number of timed iterations after GC filtering), n_gc (the garbage collections over all iterations, a pseudo-measure of the pressure on the collector), total_time, and the list columns result, memory, time (the raw bench_time vector of each run) and gc. The classes print readably (1.2ms, 7.63MB) and are numeric underneath. The check argument is the feature that matters most for correctness: an optimisation that returns a different answer is a bug, and mark() stops with an error if the expressions disagree. The script below is the comparison of the previous section made properly: the days a loan is overdue, for 120000 loans, computed by a preallocated loop and by vectorised arithmetic. The relative column is rounded to the nearest power of ten because the exact ratio changes from run to run (it was between 1000 and 2000 in the runs that were made), and the script passes filter_gc = FALSE to mark() and to summary() because the loop allocates enough small objects to collect garbage in every iteration, which would otherwise make the function print a warning.

source("scenario.R")

# The shelf loans repeated 2000 times: 120000 rows.
loan_date <- rep(loans$loan_date, 2000L)
return_date <- rep(loans$return_date, 2000L)

late_loop <- function(loan_date, return_date, today, allowed) {
  out <- integer(length(loan_date))
  for (i in seq_along(loan_date)) {
    end <- return_date[[i]]
    if (is.na(end)) {
      end <- today
    }
    out[[i]] <- max(0L, as.integer(end - loan_date[[i]]) - allowed)
  }
  out
}

late_vector <- function(loan_date, return_date, today, allowed) {
  end <- return_date
  end[is.na(end)] <- today
  pmax(0L, as.integer(end - loan_date) - allowed)
}

b <- bench::mark(
  loop = late_loop(loan_date, return_date, shelf_today, loan_days),
  vector = late_vector(loan_date, return_date, shelf_today, loan_days),
  min_iterations = 10,
  filter_gc = FALSE
)

bench::press() runs mark() across a grid of parameters and binds the results into one tibble, which is how one finds out how a cost grows (bench package documentation: press). Named arguments define the grid, and the one unnamed expression, usually a braced block, runs once per row of the grid with the parameters available as variables. The script below grows a vector with c() and fills a preallocated one, for three sizes, and prints the memory column. That column shows the difference with no noise: doubling the length roughly quadruples the memory of the growing version, because every iteration allocates a new vector of the size so far, and only doubles the memory of the preallocated one. The function bench::system_time() is the single-shot counterpart, a system.time() that returns bench_time values called process (CPU) and real (elapsed).

# Growing a vector with c() against preallocating it, for three sizes.
grow <- function(n) {
  out <- c()
  for (i in seq_len(n)) {
    out <- c(out, i)
  }
  out
}

prealloc <- function(n) {
  out <- integer(n)
  for (i in seq_len(n)) {
    out[[i]] <- i
  }
  out
}

# Run both once or twice first so that the byte-code compiler's own
# allocations are not counted in the first measurement.
for (warm in 1:3) {
  grow(10L)
  prealloc(10L)
}

res <- bench::press(
  n = c(1000L, 2000L, 4000L),
  {
    bench::mark(
      grow = grow(n),
      prealloc = prealloc(n),
      min_iterations = 5,
      filter_gc = FALSE
    )
  },
  .quiet = TRUE
)

The script warms both functions up before the first measurement. microbenchmark

The microbenchmark package (version 1.5.0, whose help page names Olaf Mersmann as its author, on CRAN; microbenchmark on CRAN) is a community package that predates bench and is still widely used in older answers and tutorials. microbenchmark(..., times = 100L) evaluates each expression times times, in an order chosen by control$order ("random", the default, "inorder" or "block"), after control$warmup warm-up iterations (default 2), using the nanosecond timer of the operating system and subtracting the estimated cost of the timing calls themselves. It returns a data frame of class microbenchmark with one row per evaluation, whose summary() has the columns expr, min, lq, mean, median, uq, max and neval, and whose unit argument ("relative" among others) chooses the unit. Its differences from bench are worth knowing. The check argument defaults to NULL, which skips the check, and takes a function or one of the strings "equal", "equivalent" and "identical". There is no memory column. And its own help page says it is meant for micro-benchmarks of small pieces of code, and recommends the R profiler for hot spots in larger chunks. The script below compares vapply() over 100000 numbers with the vectorised expression, shows the check refusing expressions that disagree, and uses the control list. Its relative median is printed rounded down to a power of ten (the ratio was about 350).

library(microbenchmark)

set.seed(7)
x <- runif(1e5)

mb <- microbenchmark(
  vapply = vapply(x, \(v) v * 2 + 1, numeric(1)),
  vector = x * 2 + 1,
  times = 30L,
  check = "equal"
)
class(mb)
#> [1] "microbenchmark" "data.frame"
names(summary(mb))
#> [1] "expr"   "min"    "lq"     "mean"   "median" "uq"     "max"    "neval"

# unit = "relative" divides every statistic by the smallest median. The ratio
# changes from run to run, so print it rounded down to a power of ten.
rel <- summary(mb, unit = "relative")
rel$median <- 10^floor(log10(rel$median))
rel[c("expr", "median", "neval")]

#> 1 vapply    100    30
#> 2 vector      1    30

Choosing and reading a benchmark

The guidelines that follow are the ones that remove most wrong conclusions.

  • Compare expressions that compute the same thing, and let the tool check it: check = TRUE in bench::mark() (with a tolerance function such as \(a, b) isTRUE(all.equal(a, b)) for floating-point results), check = "equal" in microbenchmark().

  • Use data of realistic size. A trick that wins on 100 elements can lose on 100000, and the other way round; bench::press() shows the trend.

  • Look at the median or the minimum, not the mean, and at the memory as well as the time. Memory is reproducible; time is not.

  • Put the setup outside the timed expression: build the data once, before the call. Timing x <- runif(1e6); sort(x) times the random numbers too.

  • Time the code the way it will be used: as a call of a function with its arguments, not as loose statements that read globals.

  • Warm up. The first call pays for byte-compilation and lazy loading; bench::mark() and microbenchmark() run more than once, and a script that times a single call should call the function once before.

  • Do not benchmark what the optimiser can skip. An expression whose value is unused may do less work than it would in real use; assign or return the value.

  • Say what the machine was. The same comparison on another computer, another BLAS or with other programs running will give different ratios. A claim such as "ten times faster" needs "on this data, on this machine".

Profiling

Timing says how long; profiling says where. R’s profiler is a sampling profiler. Rprof() starts it, and every interval seconds it writes the current call stack, the list of the R functions that are being evaluated, one above the other, to a file. summaryRprof() reads the file and counts how many samples each function was on the stack. The approach is cheap and needs no change to the code, but it is statistical: a function that runs for less than one interval can be missed entirely, the result changes from run to run, and it is only as precise as the number of samples.

Reading a profile is a matter of asking the same three questions each time.

  • Which function has the largest total time that is not just the entry point? That is the branch of the program to look into.

  • Within it, which function has the largest self time? That is where the work is done, and what to change.

  • Is the work in R code or in compiled code? R functions such as strsplit() and gsub() are mostly compiled code behind a short R wrapper; a large self time there means the argument is large or the call is repeated, and the remedy is to call it fewer times on more data, not to rewrite it.

Three cautions apply. Profiling has a small cost of its own, and the output file can grow large for a long run at the default interval. A short profile is unreliable: a run of a few hundred milliseconds has only a few dozen samples, so repeat the work (the scripts here loop over a few hundred thousand elements for that reason) or lengthen the data. And the garbage collector runs from time to time and its time is charged to whichever function was running when it started; Writing R Extensions suggests comparing a profile taken straight after a gc() with one taken without (Writing R Extensions: Profiling R code for speed). R-admin adds a fourth, for installations that use a multi-threaded BLAS: profiling uses the SIGPROF signal, which may cause problems with threaded libraries, and the advice is to disable profiling when one is used (R Installation and Administration: Linear algebra).

CPU time or elapsed time: Rprof(event =) (R 4.4.0)

Before R 4.4.0 the profiler measured one thing: CPU time on Unix-alikes, elapsed time on Windows. R 4.4.0 added the event argument and, with it, profiling by elapsed (real, wall-clock) time on Unix (R NEWS: "Rprof() gains an event argument and support for elapsed (real) time profiling on Unix", R NEWS: Changes in R 4.4.0). The help page explains the difference. With "cpu", the default on Unix-alikes and typically the preferred event for finding performance bottlenecks, the profiler counts CPU time of the R process, so it excludes the time R spends waiting for input or for processes started by system(); it can go slower than the elapsed clock when the process often waits, and faster when concurrent threads (OpenMP, a threaded BLAS) compute. With "elapsed", the default and the only supported event on Windows, it counts the time the process is running and executing an R command, including a readline() that waits for input. The help page also says that elapsed profiling on Unix is new and considered experimental: to avoid missing a sample, R tries to use the real-time FIFO scheduling policy with the maximum priority for the internal thread that takes each sample, and if that is not allowed it falls back to the maximum priority of the current policy, which matters only when profiling a machine under high load. "default" is the platform’s choice.

The choice changes what the profile says about code that waits, and the script below is built to show it. wait_then_work() sleeps for a second and then sorts a million random numbers. Sys.sleep() stands in for a slow download or a database query. The CPU profile never sees the sleep, only the sorting (a fraction of a second of CPU in a function that takes over a second), and the elapsed profile shows Sys.sleep() as nine tenths of the time. For a program that is slow because it waits on a network, a disk or another process, the CPU profile is blind to the cause and the elapsed profile is the right one. For a computation, the CPU profile is the cleaner. The script ends with the two errors the arguments can raise, with their real messages: an unknown event is an error from match.arg(), and an interval below the platform minimum is a warning that says what was used instead.

Memory: three tools in brief

Memory use is part of speed, because allocation, copying and garbage collection are time, and the subject has its own page: Memory and Copy Semantics. In brief, there are three profiling tools. Rprof(memory.profiling = TRUE) writes the total allocation in small vectors, large vectors and cons cells at each sample and the number of calls to the internal duplicate function that copies objects, and summaryRprof(memory = "both") adds the change in memory to the timing tables; its caveat is that memory is attributed to the function running at the end of the sampling interval, and a collection can make the memory fall (Writing R Extensions: Memory statistics from Rprof). Rprofmem() is a non-sampling profiler that writes a stack trace each time a large vector is allocated (above a threshold given in bytes) or a new page of the R heap is allocated; it is what bench::mark() uses for its mem_alloc column (Writing R Extensions: Tracking memory allocations). tracemem() marks one object and prints a message whenever it is copied (Writing R Extensions: Tracing copies of an object), and gc() reports the memory in use and triggers a collection (R documentation: gc). The last two need R to have been built with memory profiling, which capabilities("profmem") (shown in the script above) answers. Writing R Extensions notes that memory profiling is difficult mainly because of garbage collection: allocation happens at well-defined times and release at whenever the collector runs.

profvis

profvis (version 0.4.0 here, profvis package documentation) draws the data of Rprof() as an interactive page. profvis(expr) runs the expression with line profiling and memory profiling on, and returns an htmlwidget of class profvis that RStudio and Positron show in a viewer and that htmlwidgets::saveWidget() writes to a self-contained HTML file. The page has the source code on top, with the time and memory attributed to each line, and a flame graph below it, where the horizontal axis is time and the vertical axis is the call stack, so the bottom block is the outermost call and every block above it is a function called by the one below; the width of a block is the time spent in it. A Data tab gives the same information as a table that expands the call stack. The documentation lists what the graph cannot show: some internal functions do not appear (<-, [ and $ among them, because they are not on the call stack, though their side effects show up as <GC> blocks), calls through an anonymous function appear as <Anonymous> unless the function is saved in a variable, white blocks are code for which profvis does not have the source (base R and packages), and nothing in C, C++ or Fortran is visible, only the R function that called it (profvis package documentation: Getting started with profvis, profvis package documentation: Frequently asked questions). Memory figures on a line are the allocation between the previous sample and this one, which may have happened on an earlier line.

The arguments of profvis() that matter are expr, the expression to profile (turned into the body of a function, so variables created inside it are not visible outside), interval (default 0.01, and values below 0.005 will probably not give accurate timings), prof_output (a file or directory in which to keep the Rprof() data; the default is a temporary file removed on exit), prof_input (the path to an Rprof() data file produced elsewhere, in which case there is no expr), timing (the event, described above), simplify (the equivalent of filter.callframes), rerun (run again until a sample is recorded, for expressions that return before the first sample), torture (garbage-collect after every so many allocations, which makes memory figures more exact) and split ("h" or "v", the orientation of the divider). Profiling code you cannot see

R’s profiler stops at the boundary of compiled code, so a function whose self time is large and whose work is in C, C++ or Fortran (a .Call() into a package, a BLAS routine) needs a different tool. Writing R Extensions devotes a section to it, with the hints "gleaned from various R users" for Linux (perf, oprofile and operf, sprof for a shared object, and Google’s gperftools), macOS and Windows, with the warning that this is highly system specific and that the chapter is based on reports that may not be current (Writing R Extensions: Profiling compiled code). For the common case, a BLAS call, perf record R -f script.R followed by perf report --sort=dso shows how the time divides between R itself, the C library, the BLAS shared object and the packages' shared objects, which is how one finds out that the time was spent in libRblas or libopenblas and not in the interpreter.

Making code faster

Profiling has named a function and a line. What follows is the list of remedies in the order that usually pays off: do less work (a better algorithm or a lookup in place of a search), use vectorised operations, avoid growing or copying, use the right container and the right function, and only then change the machinery under the code (the compiler, the BLAS, a different package, compiled code), or spread the work over cores (Parallel and Asynchronous Computing). Each remedy below is shown with a measurement, on the shelf data repeated to a size at which the difference is visible.

Vectorise

A vectorised function runs its loop in compiled code; a loop in R pays the interpreter’s cost for every element. The effect is the largest single win in everyday R, and Vectorisation and Iteration explains the functions that replace the common loops. The measurement here is of a kind that is easy to miss: a loop that looks up each loan’s book in a table. The loop calls which(keys == isbn[[i]]) for every loan, which scans the 16 keys every time and allocates a logical vector each time; titles[match(isbn, keys)] builds a hash table of the keys once and looks every loan up in it. The difference is about two orders of magnitude for 60000 loans. The relative column is printed with one significant digit (the ratio was between 100 and 125 in the runs that were made).

Preallocate, and do not grow

Growing a result one element at a time (out <- c(out, value)) allocates a new vector and copies the old one on every iteration, so the total work grows with the square of the length. The section on bench::press() showed it in memory (doubling the length quadrupled the allocation of the growing version). Vectorisation and Iteration covers the idiom in the section called "Preallocation and the growing-vector trap" and the assignment-beyond-the-end behaviour that R 3.4.0 added; the rule is numeric(n), integer(n), character(n), logical(n) or vector("list", n) before the loop, x[[i]] <- value inside it, and, when the length is unknown, a list of the pieces combined once at the end.

The same applies to data frames and is much more costly: rbind(df, row) inside a loop copies the whole data frame and checks the columns every time. The script below builds a 2000-row data frame three ways: rbind() in a loop, a list of one-row data frames combined by one do.call(rbind, parts), and the columns built as vectors and wrapped in data.frame() once. The time ratios are printed rounded down to a power of ten, and the memory ratios to the nearest. The loop allocates a thousand times the memory of the vector version, and the list version about ten times.

# Three ways to build a data frame of 2000 rows.
rows_loop <- function(n) {
  df <- data.frame(loan_id = character(), days = integer())
  for (i in seq_len(n)) {
    row <- data.frame(loan_id = sprintf("L%04d", i), days = i %% 40L)

  }
  df
}

Avoid copies

R’s functions behave as if arguments were copied (call by value), but a copy is made only when an object is modified while something else refers to it; Writing R Extensions explains the design with a package example in which the single line x$call <- x$printcall copies the whole object x, and shows that data frames are slower than matrices and that "this is an example of why" (Writing R Extensions: Profiling R code for memory use). The consequences for speed are three. Modifying an argument inside a function copies it, however large. Setting one cell of a data frame column in a loop, df$x[i] <- value, goes through $<-.data.frame and copies the column, and more, at every iteration, whereas the same assignment on a plain vector is done in place. And a function that takes a large object only to read a small piece of it costs nothing for the object. The script below measures the second and the first. For 10000 cells the data-frame version allocates ten thousand times the memory of the vector version, and the function that modifies its million-element argument allocates the 7.63 MB of a copy of it, while the function that only reads it allocates nothing. The remedy for the data frame is to do the loop on vectors and build the data frame once, or to work with a matrix or a list; the remedy for the argument is to make the modification a new, smaller object, or to accept the copy knowingly. Memory and Copy Semantics is the place for the rules (what counts as "something else refers to it", reference counting since R 4.0.0, and when R can modify in place) and for tracemem() to see a copy happen.

vapply and the apply family

A very common piece of advice is to replace loops by sapply() or lapply() because they are faster. They are not, by much: the apply functions are loops written in C that call an R function once per element, and the call is the cost. The profvis documentation says the same thing, and gives it as the example of a belief that is not true. The script below applies a small fee function to 120000 loan durations with a preallocated for loop, vapply(), sapply(), lapply() plus unlist(), and the vectorised pmax() form, and prints two comparisons (the four loops are within a factor of three of each other, and the vectorised form is more than ten times faster than the best of them; the factor was a hundred in the runs made) and the memory ratios, which are the same on every run. What the apply functions offer is not speed but clarity and safety, and vapply() is the safe one: it declares the type and length of each result, FUN.VALUE, and an element that does not conform is an error, not a surprise. sapply() guesses: it simplifies the result to a vector, a matrix or a list depending on what the function returns, and on an empty input it returns an empty list whatever the function would have returned. The script after it shows the two errors that vapply() raises, with their real messages, and the empty-input case.

Matrix algebra

Matrix operations are where R hands its work to the BLAS and LAPACK (see the next section), and the way they are written still matters, because the library is fast only for the operation it is asked to do. Three rules cover most of it. Do not form an inverse that is only going to be multiplied: solve(a, b) solves the linear system directly, and solve(a) %*% b computes the whole inverse first, which is more work and less accurate. Use crossprod(x) for t(x) %*% x and crossprod(x, y) for t(x) %*% y: it does not build the transpose, and for a single argument it computes only half of the symmetric result (R documentation: crossprod). Prefer a decomposition (qr(), chol()) when the same matrix is used for several right-hand sides, and keep the work in matrices: a data frame converted to a matrix once is faster to compute on than the data frame, as the section on copies showed. The script below solves the normal equations of a least-squares problem with 5000 rows and 500 columns written three ways, checking that they agree, and prints which is fastest, that the naive form is at least one and a half times slower, and the memory ratios. The crossprod form allocates about a seventeenth of the memory of the naive form, which is the cleanest measure of the difference.

set.seed(123)

y <- rnorm(n)

# The normal equations for a least-squares fit, written three ways.

better <- function(x, y) solve(t(x) %*% x, t(x) %*% y)

A faster BLAS

R does not implement its own dense linear algebra. The Installation and Administration manual states it at the start of the appendix on linear algebra: the routines make use of BLAS (Basic Linear Algebra Subprograms) and, for most, of LAPACK; the sources contain reference implementations in Fortran, and they can be replaced by external libraries, usually tuned for specific CPUs (R Installation and Administration: Linear algebra). %*%, crossprod(), solve(), chol(), qr(LAPACK = TRUE), eigen() and svd() end up there, and a tuned BLAS multiplies large matrices many times faster than the reference one, partly through CPU-specific code and partly through threads. It is the one speed-up on this page that needs no change to the program.

The choices, as the manual describes them, are these.

The ways to change the BLAS follow from where it is linked. If R was built with the shared BLAS (--enable-BLAS-shlib, the default on all platforms but AIX), every reference goes through libRblas, so the library can be swapped without rebuilding R or the packages: by symlinking an external shared BLAS over libRblas, or, on Debian-based systems, by building R with --with-blas and using update-alternatives; the manual points to the Debian wiki page on linear algebra libraries and says that ATLAS, MKL and OpenBLAS alternatives are available (R Installation and Administration: Shared BLAS). Binary distributions make the choice for the user: the NEWS of R 4.5.0 says Windows builds use the internal BLAS by default, the manual says some CRAN builds for macOS can be switched to Accelerate, and the Linux image used for this page runs on OpenBLAS.

The manual lists the caveats of an external BLAS, and all of them matter for a decision. The results are not identical to the reference implementation; some differences are benign, such as the signs of singular vectors, but an optimised library can be less accurate, and its LAPACK can be older. R relies on IEEE 754 behaviour, and a library that assumes a term with a zero factor is zero can break it, since x * 0 can be NaN. A multi-threaded BLAS can use more CPU time, and occasionally much more elapsed time, than a single-threaded one, notably on a busy machine and on hyper-threaded CPUs, because the threads contend for the CPU caches. BLAS and LAPACK calls inside threaded code (OpenMP sections in a package such as mgcv) may be unsafe with external libraries, whose thread-safety is not guaranteed. A threaded BLAS and the profiler disagree (the SIGPROF signal, noted in the section on profiling). And a threaded BLAS inside a process that is itself one of several parallel workers oversubscribes the machine: set OPENBLAS_NUM_THREADS=1 (or OMP_NUM_THREADS=1) in the workers, a point Parallel and Asynchronous Computing returns to. The links to the projects are OpenBLAS and FlexiBLAS; for MKL and Accelerate the manual’s sections are the reference (R Installation and Administration: Intel MKL, R Installation and Administration: Accelerate). The Fortran Reference page BLAS, LAPACK and Numerical Libraries covers the libraries from the Fortran side.

The byte-code compiler and the JIT

R evaluates functions by walking their syntax tree, or, if they are compiled, by running a compact byte-code form of them on a virtual machine. The compiler package, part of R since 2.13.0, compiles closures (cmpfun()), expressions (compile()) and files (cmpfile()), and disassemble() prints what it produced. Since R 3.4.0 a just-in-time compiler is on by default: the NEWS says that functions are compiled on first or second use and that top-level loops are compiled and then run (R NEWS: Changes in R 3.4.0); and since R 3.5.0 all packages are byte-compiled on installation by default (R NEWS: Changes in R 3.5.0). Vectorisation and Iteration has the section "Byte-compilation" with the first look at all this; this section is about checking what the compiler did and how it is controlled.

The levels of enableJIT(level) are these (the help page, R documentation: compile); the function returns the previous level, a negative argument returns the current one, and level 3 needs the compiler option optimize to be 2 or 3.

Level What is compiled

0

Nothing: the JIT is off.

1

Larger closures, before their first use.

2

Level 1, and some small closures before their second use.

3

Level 2, and in addition all top-level loops, before they are executed. The default.

Source: R documentation: compile

The level of a new R process is set by the environment variable R_ENABLE_JIT, and compilePKGS(TRUE) (or _R_COMPILE_PKGS_ set to a positive integer) makes the compiler compile packages when they are installed, but the help page says not to enable it outside installation, because it makes any serialized function be compiled, with a time and space overhead; R_COMPILE_PKGS is the variable that tells R CMD INSTALL whether to compile. A package can opt out in its DESCRIPTION with ByteCompile: no, and an installation can with R CMD INSTALL --no-byte-compile (Writing R Extensions: The DESCRIPTION file, R Installation and Administration: Byte-compilation). The compiler options are optimize (an integer from 0 to 3; the out-of-the-box default is 2), suppressAll, suppressUndefined and suppressNoSuperAssignVar, read by getCompilerOption() and set by setCompilerOptions(). Two of its details are visible in everyday use. The compiler does not compile code that contains explicit calls to browser(), so that one can single-step from there (R NEWS, 3.4.0). And the help page remarks that the "byte code" is, when R is compiled with gcc, actually threaded code rather than byte code.

How to tell what happened? Printing a compiled function ends with a <bytecode: ...> line that holds a memory address, so the script defines is_compiled(), which asks whether such a line is printed, and uses it to show the three facts about the default JIT: the functions of an installed package are compiled; a closure with a loop is compiled by its first call; a small closure by its second. It ends with cmpfun() and disassemble(), whose result is a list of the form (.Code, instructions, constants). For x + 1 the instruction sequence is GETVAR.OP (push x), LDCONST.OP (push the constant), ADD.OP and RETURN.OP, and the operands (1L, 2L, 0L) are positions in the constant pool that is the third element: x + 1, x and 1.

The effect of compilation can be measured, if the JIT is kept from compiling the function that is meant to be the interpreted one. The next script switches the JIT off with enableJIT(0L), which returns the previous level (3), defines a loop, compiles a copy of it by hand with cmpfun(), compares the two with bench::mark(), and restores the level. data.table

data.table (version 1.18.6.1 here) is a package for tables that are large or whose operations are heavy: grouping, joins, sorting and reading and writing files. It is fast because of how it works: it modifies columns by reference instead of copying, it uses its own radix sort and optimised grouping (GForce), it can build indexes and keys for binary-search joins, and parts of it (fread(), fwrite(), forder(), grouping) use OpenMP threads. data.table covers the package, including its section on printing and threads; this page shows only where it changes the measurements. The script below, run on the shelf loans repeated 10000 times (600000 rows), makes three comparisons. A grouped mean over the eight members: here tapply() is as fast as data.table (the script prints that only aggregate() is at least three times slower), which is the honest result for few groups. The same mean over 100000 groups, where tapply() and split() followed by vapply() are at least ten times slower than data.table (the factor was 20 to 35 in the runs made, printed rounded down to a power of ten). Reading a 600000-row CSV file, where fread() is more than ten times faster than read.csv() (about 16 in the runs made). The R FAQ gives the reason for the third part: read.table() reads everything as character data first and then works out what the columns are, which takes time and memory for a large data set, and giving colClasses helps substantially (R FAQ 7.28: Why is read.table() so inefficient?). fread() detects the types itself and in parallel.

Moving a hot loop to C++

When the profile points at a loop that cannot be vectorised, because each iteration depends on the previous one, and the byte-code compiler has already done what it can, the next step is to write that loop in a compiled language. Rcpp (version 1.1.2 here, Rcpp project site, Rcpp on CRAN) is the usual way for C++: Rcpp::cppFunction("code") compiles a function from a string and makes it callable from R, Rcpp::sourceCpp("file.cpp") does the same for a file whose exported functions carry a // [[Rcpp::export]] comment, and a package that contains such code lists Rcpp under LinkingTo and Imports in its DESCRIPTION. cpp11 is an alternative C++ interface to R. The compilation uses the tool chain of the machine: gcc and g++ 13.3 here, Rtools on Windows, the Xcode command line tools on macOS. The shelf example is a stock level that rises with returns, falls with loans and stays between zero and a capacity: level = min(capacity, max(0, level + change)), applied one day after another over a million days. The clamping makes it impossible to write with cumsum(), so the R version is a loop. The C++ version is the same loop on a NumericVector. The script checks that both return identical results before it compares them; the C++ function is about a hundred times faster (printed to the nearest power of ten; the ratio was between 90 and 105 in the runs made), at the price of a compiler dependency, a compilation step on every new session for cppFunction() (a package compiles once, at installation), and code in a second language to maintain. Because cppFunction() compiles the text it is given, the script’s compilation takes a few seconds on first use; it prints nothing when it succeeds.

# A loop that cannot be vectorised: each step depends on the previous one.
# The stock of a shelf rises with returns, falls with loans, and stays between
# 0 and the shelf capacity.
set.seed(2026)
change <- rpois(1e6, lambda = 3) - rpois(1e6, lambda = 3)

stock_r <- function(change, capacity) {
  out <- numeric(length(change))
  level <- 0
  for (i in seq_along(change)) {
    level <- min(capacity, max(0, level + change[[i]]))
    out[[i]] <- level
  }
  out
}

Rcpp::cppFunction("
NumericVector stock_cpp(NumericVector change, double capacity) {
  int n = change.size();
  NumericVector out(n);
  double level = 0.0;
  for (int i = 0; i < n; ++i) {
    level = std::min(capacity, std::max(0.0, level + change[i]));
    out[i] = level;
  }
  return out;
}")

identical(stock_r(change, 500), stock_cpp(change, 500))
#> [1] TRUE

A worked example: from slow to fast

The shelf analysis of the overdue rate by genre is the kind of computation this page is about, written the way the problem would first be described: for every loan, find its book, work out the days on loan, decide whether it is overdue, and then average by genre. The script runs the steps of the measurement loop on 120000 loans (the shelf loans repeated 2000 times). It defines the first version, overdue_rate_slow(), and prints its result, so that there is an answer to check against. It times one call with system.time(); the elapsed time is over a second, enough to matter, and is printed as <n>. It profiles one call with Rprof(): the top of by.total is the function itself, -.Date (about half the time) and difftime (nearly as much), so the cost is in subtracting dates one element at a time, and the which() lookup that looked suspicious in the source is not the bottleneck. It then changes two things, the title lookup (match()) and the date arithmetic (the whole loan_date and return_date columns subtracted at once), keeps the grouping, and checks with all.equal() that the answer did not change. Last it measures again with bench::mark() (iterations = 3 because one call of the slow version takes over a second): the new version is about a hundred times faster. The profile of the first version is the point: reading the source, the lookup in books inside the loop looked like the expensive part, and the profile says that most of the time is in the date subtraction, which is where a change helps most. Measuring first is cheaper than being wrong.

Pitfalls collected

Pitfall What to do

Optimising before measuring.

Profile first. The slow part is often not the one the source suggests, as the worked example shows.

Trusting one timing.

Repeat, and report the median or the minimum; use bench for anything under a second.

Comparing expressions that compute different things.

Use check = TRUE (bench) or check = "equal" (microbenchmark), and test the optimised function against the original.

Benchmarking tiny inputs.

A winner on 100 elements can lose on 100000. Use bench::press() over sizes, and large data for data-processing tasks.

Timing the setup.

Create the data outside the expression; assign nothing global inside it.

Reading the memory column of the first measurement.

Warm up first: the first call allocates for byte-compilation.

Reporting seconds.

They are specific to a machine. Report ratios and the memory, and say what the machine was.

Using sapply() for speed.

It is not faster than a loop; vapply() is as fast and checks its types. Vectorise for speed.

Growing vectors and data frames in a loop.

Preallocate, or collect pieces in a list and combine them once.

df$col[i] <- value in a loop.

Loop on a vector and put it in the data frame once; the data-frame form copied about ten thousand times the memory in the measurement above.

Profiling too short a run.

Fewer than a few dozen samples are noise; repeat the work or lengthen it.

Profiling a program that waits with the CPU event.

Use Rprof(event = "elapsed") (R 4.4.0) or profvis (which defaults to elapsed time on R 4.4.0 or later).

Expecting a line profile under Rscript.

keep.source is FALSE there. Source with keep.source = TRUE.

A multi-threaded BLAS with the profiler or with parallel workers.

Disable profiling, and set the BLAS threads to 1 in the workers.

Assuming a faster BLAS gives the same numbers.

The results differ in the last digits and in the signs of eigenvectors; use all.equal(), not identical().

Calling cmpfun() everywhere.

The JIT already compiles; measure with the JIT off if you want to see the effect.

Rewriting in C++ first.

It is the most expensive remedy. Vectorise, fix copies, then compile.
