What’s New and Migrating Older Code

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Re-checked on 2026-10-22: R 4.6.2 ("Diversified Portfolio") is at release-candidate stage and is scheduled for 2026-10-29, so nothing below is a claim about 4.6.2 itself; the section on upcoming changes only says what the R-devel NEWS lists for it. R changes slowly and on purpose: a feature is announced in NEWS, usually deprecated before it is removed, and the manuals are updated with the release. This page puts the changes of seven releases, R 4.0.0 (2020) to R 4.6.1 (2026), in one place: a table of every language or base-R change with a link to the page of this reference that explains it, a section per release with the code that shows the difference, the removals that stop an old script, the table of habits that older tutorials still teach, the changes that R-devel lists for the next releases, and the ways to follow them.

Every example is a script that was run with Rscript on R 4.6.1 with warnings printed as they happen (options(warn = 1)), and the lines that start with #> are what it printed. The scripts also pass the default lintr linters; a # nolint: comment marks a line where the idiom on show is the one a default linter dislikes. The names books, loans, shelf_today, loan_days come from the running library-shelf scenario described on the section index: a script that needs them starts with source("scenario.R"). Because only R 4.6.1 was available, a "before" line is one of three kinds. It is an older idiom that still runs on 4.6.1 and is run (the stringsAsFactors = TRUE argument, a hand-written %||%, a magrittr pipe). Or it is an older form that now fails, caught with tryCatch() so that the script exits normally and the real 4.6.1 message is shown. Or it is a statement taken from NEWS and not run. How R versions are numbered and released

R uses a major.minor.patchlevel numbering scheme, and the R FAQ says where to find the versions in use: r-release is the current release, r-patched is the current release plus bug fixes, and r-devel is the version heading for the next minor or major release, where new features are introduced (R FAQ 2.3: What is the current version of R?). The R Core release schedule is annual: a new x.y.0 release in spring, patch releases as needed, and a final patch release of the previous version shortly before the next x.y.0 (R Developer Page: release schedule). Two habits of the project explain the shape of the changes below. First, a change that can break existing code is usually announced before it happens. The sequences that appear on this page are: && and || with an operand of length greater than one gave a warning in R 4.2.0 and are an error since R 4.3.0; default.stringsAsFactors() was deprecated in 4.2.0 and is defunct since 4.3.0; is.R() was deprecated in 4.4.0 and is defunct since 4.5.0; the xfig() device was deprecated in 4.4.0 and removed in 4.5.0; and structure(NULL, ...) was deprecated in R 3.4.0 and is defunct since 4.6.0. The rule for if and while followed the same path over a longer time: a warning in the earlier releases and an error since R 4.2.0. The functions .Deprecated() and .Defunct() that signal these conditions are in Defensive Programming and Input Validation. Second, a new feature that is not settled is labelled as experimental, in NEWS or on its help page, and this page repeats that label: NEWS calls the use of _ to start an extraction chain (R 4.3.0), Tailcall() and Exec() and declare() (R 4.4.0) experimental, and the help page of use() (available since R 4.4.0) says that its functionality is still experimental. Experimental features may be changed or dropped, so a package that has to run on many R versions should not build on them.

R 4.0.0 (2020-04-24)

R 4.0.0 changed the defaults and the internals more than any later release of the series, and the NEWS opens it with the reminder that packages with compiled code needed to be reinstalled under the new version. For code written in R, five of its changes are visible every day: strings stay strings, raw string constants exist, a matrix has two classes, the default colours changed, and list2DF() is a new way to build a data frame. A sixth, reference counting, changed how R decides when to copy and is invisible from R code.

stringsAsFactors = FALSE is the default

The NEWS entry of R 4.0.0 says that R now uses a stringsAsFactors = FALSE default, "and hence by default no longer converts strings to factors" in calls to data.frame() and read.table(), and adds that a large number of packages had relied on the previous behaviour and needed updating. read.csv() is read.table() with different defaults, so it follows. The older behaviour is still one argument away, which is how the first block reproduces it: stringsAsFactors = TRUE gives the nine-level factor that every older tutorial printed. With factors, adding a value that is not a level is a warning and an NA, the error message of the old days that this change retired for most scripts. The function default.stringsAsFactors() that old code used to read the default was deprecated in R 4.2.0 and is defunct since R 4.3.0, and the last line of the block shows its real message. The page Data Frames explains the argument and Factors explains what a factor is for.

# Since R 4.0.0 strings stay strings.
books <- read.csv("books.csv")
class(books$genre)
#> [1] "character"
df <- data.frame(title = c("The Long Table", "Rivers of Glass"))
class(df$title)
#> [1] "character"

# Before R 4.0.0 the default was TRUE; the old behaviour is one argument away.
old <- read.csv("books.csv", stringsAsFactors = TRUE)
class(old$genre)
#> [1] "factor"
nlevels(old$genre)
#> [1] 9

# With factors, a value that is not a level is a warning and an NA.
tryCatch(
  {
    old$genre[1L] <- "Cookery"
    old$genre[1L]
  },
  warning = \(w) conditionMessage(w)
)
#> [1] "invalid factor level, NA generated"

# default.stringsAsFactors() was deprecated in 4.2.0 and is defunct since 4.3.0.
tryCatch(default.stringsAsFactors(), error = \(e) conditionMessage(e))
#> [1] "'default.stringsAsFactors' is defunct.\nUse '`stringsAsFactors = FALSE`' instead.\nSee help(\"Defunct\")"

Source: R NEWS: Changes in R 4.0.0

Raw string constants

R 4.0.0 added a syntax for raw character constants similar to the one of C++: r"(...)", where the dots are any character sequence that does not contain the characters )". The NEWS says it makes it easier to write strings that contain backslashes or both single and double quotes, and refers to the help page of Quotes. The brackets may also be [] or {}, a capital R works as well as a small one, and a run of dashes between the r and the opening bracket (and again before the closing quote) lengthens the delimiter, so that a string may contain )" itself; the block shows the dashes. Raw strings matter most for Windows paths and regular expressions, where every backslash otherwise has to be doubled. They are a parser feature: the value is an ordinary character vector, as the identical() calls show. The syntax is explained in Syntax and Lexical Structure and used for patterns in Strings and Regular Expressions.

# A Windows path needs every backslash doubled in an ordinary string.
path_old <- "C:\\shelf\\books.csv"
path_raw <- r"(C:\shelf\books.csv)"
identical(path_old, path_raw)
#> [1] TRUE
nchar(path_raw)
#> [1] 18

# Both kinds of quote can appear without escapes.
quote_old <- "She said \"hello\" and 'goodbye'"
quote_raw <- r"(She said "hello" and 'goodbye')"
identical(quote_old, quote_raw)
#> [1] TRUE

# Dashes between the r and the bracket make a longer delimiter, so that the
# text may contain )" itself.
r"---(a )" inside a raw string)---"
#> [1] "a )\" inside a raw string"

# Regular expressions are where raw strings pay off.
iso_old <- "^\\d{4}-\\d{2}-\\d{2}$"
iso_raw <- r"(^\d{4}-\d{2}-\d{2}$)"
identical(iso_old, iso_raw)
#> [1] TRUE
grepl(iso_raw, c("2026-06-30", "30/06/2026"))
#> [1]  TRUE FALSE

Source: R documentation: Quotes

Matrices also inherit from "array"

Since R 4.0.0 a matrix has two classes, c("matrix", "array"). The NEWS entry warns that this "invalidates code incorrectly assuming that" the class of a matrix has length one, and adds that S3 methods for class "array" are now dispatched for matrices. The classic casualty is a test such as if (class(m) == "matrix"): with a condition of length two it was a warning before R 4.2.0 and is an error since R 4.2.0, as the fourth line of output shows. The correct tests are is.matrix() for "is this a matrix" and inherits() for a class vector. The lintr linter class_equals_linter() finds the old form (see the migration section). The page Matrices and Arrays covers the class vector in detail.

m <- matrix(1:6, nrow = 2)
class(m)
#> [1] "matrix" "array"
inherits(m, "matrix")
#> [1] TRUE
is.matrix(m)
#> [1] TRUE

# Code written for R 3.x compared the whole class vector with a string.
tryCatch(
  if (class(m) == "matrix") "a matrix",
  error = \(e) conditionMessage(e)
)
#> [1] "the condition has length > 1"

# Ask the question directly instead.
if (is.matrix(m)) "a matrix"
#> [1] "a matrix"

# S3 methods for "array" are also dispatched for matrices.
describe <- function(x) UseMethod("describe")
describe.array <- function(x) "the array method"
describe.default <- function(x) "the default method"
describe(m)
#> [1] "the array method"
describe(1:3)
#> [1] "the default method"

Reference counting replaces NAMED

R 4.0.0 replaced the NAMED mechanism, with which R’s C code decided whether an object could safely be modified in place, by reference counting. The NEWS says it reduces the need for copying in some cases, should allow further optimisations, and is expected to have almost no impact on packages that use supported coding practices in their C and C++ code. For code written in R nothing changes: assignment never copies, and the copy is made when one of the two names is modified, which the block shows with the shelf’s pages column. What changed is how often R can skip the copy, and the way to observe it is tracemem(), which Memory and Copy Semantics and Assignment, Names and Values use. The header fields that hold the count are described in R Internals.

# Reference counting (R 4.0.0) is internal: what a script sees has not changed.
source("scenario.R")
pages <- books$pages
copy <- pages
copy[[1L]] <- 0L

# The copy is made at the modification; the original is untouched.
pages[[1L]]
#> [1] 387
copy[[1L]]
#> [1] 0
identical(pages[-1L], copy[-1L])
#> [1] TRUE

Source: R Internals: Rest of header

A new default palette()

The default palette() has a new set of colours that are less saturated and have better accessibility properties, according to the NEWS. The old default is kept under the name "R3", the new built-in palettes are listed by palette.pals(), and palette.colors() selects a subset of colours from any of them. Charts that use the numbers 1 to 8 as colours (col = 2) therefore changed their look in R 4.0.0 even though their code did not; code that needs the old look sets palette("R3"). The block changes the palette and sets it back, because the palette is session state. The page Base Graphics and Devices shows the colours.

# The default palette() changed in R 4.0.0; the old one is called "R3".
palette()
#> [1] "black"   "#DF536B" "#61D04F" "#2297E6" "#28E2E5" "#CD0BBC" "#F5C710"
#> [8] "gray62"
palette("R3")
palette()
#> [1] "black"   "red"     "green3"  "blue"    "cyan"    "magenta" "yellow"
#> [8] "gray"
palette("default")

# palette.pals() lists the named palettes that came with the change.
palette.pals()[1:5]
#> [1] "R3"        "R4"        "ggplot2"   "Okabe-Ito" "Accent"
palette.colors(4L, palette = "Okabe-Ito")
#> [1] "#000000" "#E69F00" "#56B4E9" "#009E73"

list2DF()

list2DF() creates a data frame from a list of variables. Unlike data.frame(), it does not check or rewrite the names: data.frame() turns the name loan date into loan.date and 2nd copy into X2nd.copy, and list2DF() keeps both as given. It also takes an nrow argument for the case of a list with no columns. The R 4.2.0 NEWS adds that it checks that its arguments have the same length instead of recycling. See Lists and Data Frames.

source("scenario.R")
cols <- list(title = trimws(books$title[1:3]), year = books$year[1:3])

# list2DF() (R 4.0.0) builds a data frame from a list of columns.
list2DF(cols)
#>                 title year
#> 1    The Dispossessed 1974
#> 2 Pride and Prejudice 1813
#> 3   the quiet streets 2019

# data.frame() checks and rewrites the names; list2DF() keeps them as given.

R 4.1.0 added two pieces of syntax that changed how R code looks: the native pipe and the function shorthand. The native pipe

The NEWS entry says that R now provides a simple native forward pipe syntax: the simple form inserts the left-hand side as the first argument of the right-hand side call. Before it, a pipe meant the magrittr package (2.0.5 here). The two look alike and differ in what they are. The magrittr %>% is an ordinary function that evaluates its right-hand side at run time and accepts a bare function name, an operator and the dot placeholder. The native pipe is a syntax transformation made by the parser: books |> head(3L) is read as head(books, 3L) and no pipe function is ever called, the right-hand side must be a call, and the placeholder is the underscore of the R 4.2.0 section below. The block runs both side by side and shows the transformation with quote() and the parse error for a right-hand side that is not a call. The magrittr lines carry a nolint comment because the linter pipe_consistency_linter() asks for one kind of pipe per file. Older code that works with magrittr keeps working; the page Pipes and the Native Pipe lists what has to change to move to the native pipe.

source("scenario.R")

R 4.2.0 (2022-04-22)

R 4.2.0 is the release that turned two sloppy habits of older code into errors: a condition of length greater than one in if and while, and a vector operand of && and || (a warning in R 4.2.0, an error since R 4.3.0). It also added the placeholder of the native pipe, made UTF-8 the native encoding on recent Windows, and added Sys.setLanguage().

if and while need a condition of length one

The NEWS of R 4.2.0 says that calling if() or while() with a condition of length greater than one gives an error rather than a warning, and that the environment variable _R_CHECK_LENGTH_1_CONDITION_, which made the check strict in R CMD check, no longer has any effect. Before, only the first element was used, which hid bugs: a whole column of the shelf’s loans was silently reduced to its first loan. The fix is to say what is meant, with any(), all() or isTRUE(), and to decide what an NA means; if (NA) is an error of its own (see Control Flow). The block shows the error for if and for while and the two usual repairs.

Tailcall() and Exec() (experimental)

R 4.4.0 added the experimental functions Tailcall() and Exec() to support recursive functions that do not grow the stack. They are experimental: the help page says they may be changed or dropped in future releases. Plain recursion in R keeps one frame per call and stops with an error (node stack overflow here, evaluation nested too deeply in other cases); Tailcall() replaces the running call with the new one when it is the last thing the function does. The accumulator must be evaluated before the call, because an unevaluated argument would be passed as a chain of promises that is forced all at once at the end. The older workaround was a loop or a trampoline. See Function Factories and Higher-Order Functions.

# Tailcall() and Exec() (R 4.4.0) are experimental.
sum_plain <- function(n, acc = 0) {
  if (n == 0) {
    return(acc)
  }
  sum_plain(n - 1, acc + n)
}
tryCatch(sum_plain(1e5), error = \(e) conditionMessage(e))
#> [1] "node stack overflow"

sum_tail <- function(n, acc = 0) {
  if (n == 0) {
    return(acc)
  }
  acc <- acc + n # evaluate the accumulator now, not as a chain of promises
  Tailcall(sum_tail, n - 1, acc)
}
sum_tail(1e5)
#> [1] 5000050000

grepv() is grep() with value = TRUE as the default: the NEWS says it is identical to grep() except for the default of value. The older idiom grep(pattern, x, value = TRUE) keeps working, so there is nothing to migrate, only a shorter spelling; all other arguments (ignore.case, invert, fixed, perl) behave as in grep(). The block uses the trimmed shelf titles. See Strings and Regular Expressions.

source("scenario.R")

tools::sha256sum()

The package tools gained sha256sum() in R 4.5.0, analogous to md5sum() and implementing the SHA-256 hashing algorithm. MD5 is still available, but a script that records a checksum to detect tampering, as opposed to accidental corruption, should use SHA-256. The block writes a six-byte file, prints both digests, and shows that the 64-character SHA-256 digest changes with the content. The names of the result are the file paths, which unname() removes here so that no path is printed. is.R() is defunct

is.R() asked whether the code was running in R rather than in S-PLUS. The R 4.4.0 NEWS deprecated it "as no other S dialect is known to be in use", and the R 4.5.0 NEWS made it defunct and removed the effect of the environment variable _R_DEPRECATED_IS_R_. The name still exists, so a guard such as exists("is.R") && is.R() is true for the first operand and fails on the second; the block shows the real message. The repair is to delete the test, since the code runs on R. The R FAQ explains the relation between R and S in R FAQ 3.3: What are the differences between R and S?, and the deprecation process is described in Defensive Programming and Input Validation.

# is.R() asked "is this R rather than S-PLUS?". It was deprecated in R 4.4.0

exists("is.R")
#> [1] TRUE
tryCatch(is.R(), error = \(e) conditionMessage(e))

#> [1] "'is.R' is defunct.\nSee help(\"Defunct\")"

A C23 compiler by default

R 4.5.0 selects a C23 compiler by default, if one is available, for compiling R and packages. The NEWS lists the compilers known to select C23 (gcc 13 to 15 and recent clang releases, among them) and the ways out: a package can ask for the previous standard with USE_C17 in SystemRequirements, or an installer with R CMD INSTALL --use-C17, and R itself can be built with --without-C23 unless the compiler defaults to C23 anyway. C23 rejects implicit function declarations and K&R-style definitions, so old C code needs fixing or the request for C17. Strict R headers are also the default in R 4.5.0, which removes the legacy macros PI, Calloc, Realloc and Free; the replacements are M_PI, R_Calloc, R_Realloc and R_Free. This is a matter for packages with compiled code and cannot be shown in a script that runs under Rscript; Interfacing C, C++ and Fortran covers it with compiled examples.

R 4.6.0 (2026-04-24)

R 4.6.0 is mostly additions: a negated membership operator, a constructor for message conditions, a bit-pattern printer, two options of existing functions, and drawing hooks for three more plot types. It also moved the default C++ standard to C++20, added a DOI to the citation of R, and made structure(NULL, ...) defunct.

%notin%

x %notin% table is the negation of x %in% table. The NEWS describes it as an idiom for !(x %in% table), "provided almost entirely for convenience and code readability" after many years of private definitions, mostly hidden in packages. Projects that define their own operator of the same name can delete the definition once they require R 4.6.0 or later. Because it is built on match(), NA is treated as a value, as with %in%. The block compares the three spellings on the shelf’s genres. See Operators and Precedence, where the membership operators are explained.

source("scenario.R")
wanted <- c("Fiction", "Poetry")
genre <- trimws(books$genre)

# Before R 4.6.0: negate %in% by hand, or define the operator in every project.
head(genre[!(genre %in% wanted)], 4L)
#> [1] "Science fiction" "Classic"         "fiction"         "Mystery"

# %notin% is the negation of %in%.
head(genre[genre %notin% wanted], 4L)
#> [1] "Science fiction" "Classic"         "fiction"         "Mystery"
identical(genre %notin% wanted, !(genre %in% wanted))
#> [1] TRUE

# Both use match(), so NA is a value like any other.
NA_character_ %notin% wanted
#> [1] TRUE
c(1, NA) %notin% c(NA, 2)
#> [1]  TRUE FALSE

messageCondition()

messageCondition() creates a structured "message" condition object, analogous to errorCondition() and warningCondition() (R 3.6.0). The extra arguments become fields of the condition and class adds classes in front of c("message", "condition"), so a handler can select on the class and read the fields, which is how progress messages that carry data are written. Before, the object was assembled by hand with structure(), as the first lines of the block do; both produce the same classes. See Conditions and Error Handling.

# Before R 4.6.0 a classed message condition was assembled by hand.
old <- structure(
  class = c("shelf_progress", "message", "condition"),
  list(message = "loan 12 of 60\n", call = NULL, done = 12L)
)

# messageCondition() builds the same object, as errorCondition() and
# warningCondition() have done since R 3.6.0. Extra fields are named arguments.
new <- messageCondition(
  "loan 12 of 60\n",
  class = "shelf_progress", done = 12L
)
class(new)
#> [1] "shelf_progress" "message"        "condition"
class(old)
#> [1] "shelf_progress" "message"        "condition"
new$done
#> [1] 12

# message() accepts a condition, and a handler can pick the class out.
withCallingHandlers(
  {
    message(new)
    "finished"
  },
  shelf_progress = \(m) {
    cat("progress:", m$done, "\n")
    invokeRestart("muffleMessage")
  }
)
#> progress: 12
#> [1] "finished"

match.arg(several.ok = "all")

match.arg() takes a new value for several.ok. A string that starts with "all" means that the argument may have more than one element and that every one of them must match choices. With several.ok = TRUE, the older option, elements that do not match are dropped without a word, which let typos through; the block shows both. The tests of valid values that people wrote by hand after several.ok = TRUE can be replaced. See Functions and Defensive Programming and Input Validation.

Moving older code to a current R

A script written for R 3.x or an early R 4.x usually runs unchanged on R 4.6.1. The changes that stop it are the ones in the table above, and the ones that change its meaning without stopping it are the new defaults (strings that stay strings, a matrix with two classes, a different is.atomic(NULL), a new palette). A practical order of work is the following.

  1. Note the R version and the package versions the code was last known to work with. A lockfile from Reproducible Environments with renv records both, and is the way to compare an old and a new run package by package.

  2. Run the script on the new R with warnings printed as they happen (options(warn = 1) in a profile, as the scripts of this reference do; Rscript prints warnings after the script otherwise). A warning is the cheapest signal: the && and || warning of R 4.2.x was the notice for the error of R 4.3.0.

  3. Search the code for the old idioms. The linters of lintr know many of them, and a few lines of R run them over a string of code, as the next block does for seven lines of "tutorial" code. The linters find class(x) == "matrix", sapply(), attach(), T and F, 1:length(x) and the magrittr pipe; they do not know is.R(), which a plain search finds. The page Style, Linting and Static Analysis explains the default set and how to enable the others.

  4. Fix what the table of removals shows, then the habits in the last table of this page.

  5. State the oldest R the code needs. A package says so in Depends, and R CMD build adds Depends: R (>= 4.1.0) itself when the code uses the native pipe or the lambda and the field is missing. The next section shows how a script checks for itself.

  6. Test on the oldest R that is supported, as well as on the newest; the community tools rig (rig on GitHub) and the Rocker project (Rocker) install and run several R versions side by side, and R-hub v2 runs R CMD check on a package in GitHub Actions (see Publishing to CRAN).

  'if (class(m) == "matrix") "a matrix"',
  "x <- sapply(1:3, function(i) i + 1)",
  "attach(books)",
  "ok <- T",
  "for (i in 1:length(x)) print(i)",
  "books %>% head()",
  "if (exists('is.R') && is.R()) 1"
)
linters <- list(

Keeping code portable across R versions

A script or a package that has to run on an older R than the one it was written on has three tools. The first is a version test: getRversion() returns an object of class numeric_version, which compares correctly with a string (getRversion() >= "4.1.0"), while comparing two version strings as text does not: "4.10.0" > "4.6.1" is FALSE. The second is a feature test, which asks for the thing the code needs and not for the release that introduced it: exists("grepv", envir = baseenv()). The third is a definition of the missing function that is made only when it is missing, so that the current R uses its own. The block shows all three with the operator of R 4.4.0. R.version.string and R.version$major and R.version$minor give the version of the running R as text.

R.version.string
#> [1] "R version 4.6.1 (2026-06-24)"
getRversion()
#> [1] ‘4.6.1’
getRversion() >= "4.1.0"
#> [1] TRUE

# Compare versions as versions, not as strings: "4.10.0" comes after "4.6.1".
"4.10.0" > "4.6.1"
#> [1] FALSE
numeric_version("4.10.0") > "4.6.1"
#> [1] TRUE
compareVersion("4.10.0", "4.6.1")
#> [1] 1

# A script that must also run on R older than 4.4.0 defines the operator only
# when base R lacks it.
if (getRversion() < "4.4.0") {
  `%||%` <- function(x, y) if (is.null(x)) y else x
}

#> [1] FALSE

A Depends: R (>= x.y.z) line only stops the installation on an older R; it does not make code written for the newer language run there. And testing on the oldest R that is supported, with a tool such as rig or the Rocker images, is the only way to find the calls that were added later.

How to keep up

R announces every change in NEWS, and there are several ways to read it.

  • The release NEWS (R NEWS) lists the changes from R 4.0.0 to the current release, newest first, in sections called Significant User-Visible Changes, New Features, Deprecated and Defunct, Bug Fixes and C-Level Facilities (the 4.6 series also has Graphics, Package Installation, Installation on a Unix-Alike, Utilities and Checking an Installation). The 3.x series has its own file (R NEWS for the 3.x series). The development NEWS (R-devel NEWS) starts with the changes of the next x.y.0 and also lists the next patch release, which is why 4.6.2 appears in it before it is out.

  • news() reads the NEWS of the installed R into a data frame with the columns Version, Date, Category, Text and HTML, which can be queried with an expression: the block below lists the entries of 4.6.1 by category and finds the entry that introduced %notin%. It reads the NEWS of the R that is running, so on an older R it does not know the newer entries. Its help page is news.

  • The R Blog (The R Blog) carries posts by members of R Core and others about internals and infrastructure. Two that bear on this page, both read for it, are "Generalizing Support for Functional OOP in R" (2024-05-17), which explains the base R generics added for S7, among them chooseOpsMethod() and nameOfClass(), and "New Tricks for the R Sweave Drivers" (2026-09-18), about the Sweave drivers whose help pages and options change in R 4.6.0 and R-devel.

  • The developer page (R Developer Page) shows the release schedule, including the dates of the beta and the release candidate of the next patch release. The announcements of releases go to the r-announce mailing list (r-announce), and r-project.org shows the current release.

  • The R FAQ explains the numbering and where the versions are: R FAQ 2.3: What is the current version of R?.
