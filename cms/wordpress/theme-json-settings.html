theme.json Settings

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

theme.json is the configuration file of a block theme. Its settings object decides what the editors offer (which colour, typography, spacing, border and layout controls appear, and which presets they list), and WordPress turns every preset into a CSS custom property and, for some presets, a utility class. Its styles object applies values to the site, elements and blocks, and is covered in theme.json Styles. This page is for theme developers: it builds the settings of the Lumen Press block theme lumen and shows, from a running site, what WordPress makes of them.

This page was written against WordPress 7.1.3 (released 2026-10-06; 7.1.4, a security release of 2026-10-28, is the version to run in production), PHP 7.4 minimum and 8.3+ recommended, theme.json version 3 and WP-CLI 2.12.0, and checked on 2026-10-28. The Gutenberg plugin (24.2.0) previews settings before they reach core; nothing on this page requires it. WordPress 7.2 is in beta and due in December 2026; theme.json stays at version 3 in it so far. Every merged value and CSS variable shown below was printed by wp eval on a fresh 7.1.3 installation with the themes of this page active, and each JSON file was validated against the published schema.

How a site owner changes these values without code is covered in Site Editor and Global Styles; font families, fontFace and the Font Library in Typography and Fonts; the styles/*.json files in Style Variations and Section Styles.

What settings are for

A block theme describes its design system once, in theme.json, instead of spreading it across add_theme_support() calls, editor stylesheets and front-end CSS:

  • Presets (palette, gradients, duotone filters, font sizes, font families, spacing sizes, aspect ratios, dimension sizes, shadows, border radius sizes): named values the editor lists in its pickers. A block that uses one stores the slug, not the value ("backgroundColor":"lumen-red", or var:preset|color|lumen-red in a style attribute), so changing the preset later restyles every block that uses it.

  • Feature switches (color.custom, typography.dropCap, spacing.padding, border.radius, position.sticky and so on): whether a control appears in the block sidebar at all. They only change the editing interface; values already saved in content keep rendering.

  • Layout values (layout.contentSize, layout.wideSize) used by the Group, Post Content and other layout blocks.

  • Responsive breakpoints (viewport, 7.1) used by responsive styles and block visibility.

  • Custom properties (custom) that become --wp--custom--* CSS variables for the theme’s own CSS and blocks.

Any of these can be set for the whole site or for one block type under settings.blocks. Settings never apply a style by themselves: a palette colour colours nothing until a style or an editor uses it.

A theme does not need to be a block theme to use theme.json. A classic theme that ships one becomes a hybrid theme: its editor gets the presets and controls, and since 6.8 it gets the Style Book and the Patterns screen under Appearance > Design (see Hybrid Themes and Migration to Block Themes).

The file: $schema and version

theme.json lives in the theme’s root folder. Two top-level keys matter before any setting:

version

The schema version. It must be present: with no version key WordPress replaces the whole file with an empty version 3 document, so every setting in it is silently ignored. Version 1 arrived in WordPress 5.8 (for classic themes and the post editor), version 2 in 5.9 with block themes, and version 3 in 6.6. 7.1 still uses version 3 (WP_Theme_JSON::LATEST_SCHEMA is 3). Older files keep working: WP_Theme_JSON_Schema::migrate() upgrades them in memory each time they are read, without changing the file.

$schema

The URL of the JSON Schema, read only by editors (VS Code, PhpStorm and others) for autocompletion, descriptions and validation. WordPress ignores it at runtime. https://schemas.wp.org/trunk/theme.json follows the Gutenberg plugin’s development branch; https://schemas.wp.org/wp/7.1/theme.json matches what WordPress 7.1 supports. Both redirect to the schemas/json/theme.json file of the Gutenberg repository. Pin the version the theme declares in Requires at least or Tested up to: the trunk schema already lists settings that 7.1 does not apply (text-shadow presets and background.backgroundClip), so an editor would offer keys that do nothing on a 7.1 site.

Other top-level keys (styles, customTemplates, templateParts, patterns, title, slug, blockTypes) are covered on the styles, templates and patterns pages.

The file validates against both the wp/7.1 and the trunk schema. Any JSON Schema draft-07 validator works; with Node.js, ajv-cli checks it in one command (the schema must first be saved locally, because ajv-cli does not follow the redirect):

curl -sL -o theme.schema.json https://schemas.wp.org/wp/7.1/theme.json
npx -y ajv-cli@5.0.0 validate --spec=draft7 --strict=false -s theme.schema.json -d wp-content/themes/lumen/theme.json
# wp-content/themes/lumen/theme.json valid

Source: ajv-cli: command-line interface for Ajv JSON Schema validator

--strict=false is needed because the schema uses descriptive keywords that Ajv’s strict mode rejects. Validation catches typos ("defaultPallete"), values of the wrong type and out-of-range numbers; it cannot tell whether a slug collides with a core preset, which is what the migration section below is about.

Global switches

appearanceTools

true turns on a set of controls that core leaves off by default for themes. In 7.1 it enables background image, size and gradient; border colour, radius, style and width; link, heading, button and caption colours; aspect ratio, height, min-height, min-width and width; sticky position; block gap, margin and padding; line height; and text columns. The list grows with releases (width and height were added in 7.0, minWidth and background gradients in 7.1), so a theme that turns it on also opts into future controls. To keep one of them off, set that switch to false next to appearanceTools, for instance "border": { "style": false }. After merging, wp_get_global_settings() reports appearanceTools as false and the individual switches as true: the flag is expanded and then cleared.

useRootPaddingAwareAlignments

With true, the root horizontal padding set in styles.spacing.padding is applied to blocks that use the has-global-padding class instead of to the whole page, and full-width children pull themselves back with negative margins. Full-width blocks then reach the screen edge while their content stays aligned with the rest of the page. It needs a padding value in styles to have any effect; Lumen uses the 40 spacing preset.

layout

contentSize is the default width of the content in constrained layouts (the Post Content block, Groups with "Inner blocks use content width"), and wideSize the width of alignwide blocks. They become --wp--style--global--content-size and --wp--style--global--wide-size. allowEditing: false hides the layout panel, and allowCustomContentAndWideSize: false (6.5) keeps the panel but hides the width inputs.

Colour

Key Effect

palette

The theme colours. Each entry has slug, name (translatable) and color. Generates --wp--preset--color--{slug} and the classes has-{slug}-color, has-{slug}-background-color and has-{slug}-border-color.

gradients

Gradient presets (gradient holds any CSS gradient). Generates --wp--preset--gradient--{slug} and has-{slug}-gradient-background.

duotone

Two-colour image filters (colors holds the shadow and the highlight). No CSS variable is printed up front: the SVG filter and its variable are output only when a block uses the preset.

defaultPalette, defaultGradients, defaultDuotone

false hides core’s 12 colours, 12 gradients and 8 duotones from the pickers. Their CSS variables are still printed, so content that already uses them keeps its colours.

custom, customGradient, customDuotone

false removes the free colour picker, the gradient editor or the custom duotone picker, so editors can only choose presets.

background, text, link, heading, button, caption

Show or hide each colour control. Link, heading, button and caption are off by default and turned on by appearanceTools.

Lumen hides core’s presets, adds six brand colours, one gradient and one duotone, and keeps custom colours for editors but not custom gradients. A palette should be checked for contrast before release: WordPress warns about low contrast in the block sidebar, but does not stop a combination such as slate text on ink (Accessibility).

Typography

fontSizes presets generate --wp--preset--font-size--{slug} and the class has-{slug}-font-size. With fluid turned on (true, or an object), each size becomes a clamp() that grows with the viewport:

  • the global fluid object sets minViewportWidth and maxViewportWidth (the range over which sizes scale; core’s defaults are 320px and 1600px) and minFontSize, below which sizes are not made fluid;

  • each preset may set "fluid": { "min": ..., "max": ... }, or "fluid": false to stay fixed; when a preset sets only size, WordPress derives a smaller minimum from it;

  • since 6.7 a single preset may opt into fluid sizing even when the global setting is off.

Lumen’s medium size becomes clamp(1rem, 1rem + ((1vw - 0.225rem) * 0.256), 1.125rem): at a 360px viewport 1vw equals 0.225rem and the size is the minimum; it reaches the maximum at 1140px. The maths, font families, fontFace with self-hosted WOFF2 files and the Font Library are covered in Typography and Fonts.

defaultFontSizes (6.6) decides what happens with core’s four sizes (small 13px, medium 20px, large 36px, x-large 42px). The rest of the typography switches show or hide controls: customFontSize, dropCap, fontStyle, fontWeight, letterSpacing, lineHeight, textAlign, textColumns, textDecoration, textIndent (7.0, which core sets to "subsequent"), textTransform and writingMode.

Spacing

Spacing presets fill the spacing slider of padding, margin and block gap controls, and generate --wp--preset--spacing--{slug}. There are two ways to declare them:

spacingScale

A generated scale: steps sizes around a mediumStep, multiplied (operator set to *) or added (+) by increment, in unit. Core’s own scale is 7 steps from 0.44rem to 5.06rem, multiplied by 1.5 around 1.5rem, with the slugs 20 to 80.

spacingSizes

An explicit list of slug, name and size. Sizes may be clamp() expressions or references to other variables, so fluid spacing is written here.

Version 3 changed how the two combine. In version 2, a theme’s spacingSizes replaced its spacingScale entirely; in version 3 they are merged: the scale generates its sizes, and spacingSizes entries are added, replacing generated sizes with the same slug. The lumen-scale test theme below shows it (5 generated steps and two explicit entries):

{
	"$schema": "https://schemas.wp.org/wp/7.1/theme.json",
	"version": 3,
	"settings": {
		"spacing": {
			"defaultSpacingSizes": false,
			"spacingScale": {
				"operator": "*",
				"increment": 1.5,
				"steps": 5,
				"mediumStep": 1.5,
				"unit": "rem"
			},
			"spacingSizes": [
				{ "slug": "gutter", "name": "Gutter", "size": "clamp(1rem, 4vw, 2.5rem)" },
				{ "slug": "50", "name": "Medium (fixed)", "size": "1.75rem" }
			]
		}
	}
}

Source: Theme Handbook: Spacing settings

theme spacingSizes: gutter, 30 (0.67rem), 40 (1rem), 50 (1.75rem), 60 (2.25rem), 70 (3.38rem)

Source: Code Reference: wp_get_global_settings()

The generated 50 (1.5rem) was replaced by the explicit one, and gutter was added in front. Lumen uses only spacingSizes and leaves spacingScale out. Turning the scale off with "steps": 0, which some themes and tutorials do, works at runtime but fails schema validation (steps has a minimum of 1); with defaultSpacingSizes set to false and no theme scale, it is unnecessary.

Other spacing keys: units (the units offered in custom inputs), customSpacingSize (false limits editors to the slider), and padding, margin and blockGap (show the controls; turned on by appearanceTools).

Dimensions, shadow, border, background and position

Key Since Effect

dimensions.aspectRatios, defaultAspectRatios

6.6

Aspect ratio presets for the Image, Cover and Featured Image blocks. Generates --wp--preset--aspect-ratio--{slug}. Lumen adds a 2/3 book-cover ratio and hides core’s seven.

dimensions.dimensionSizes

7.0

Size presets for the width, height and min-height controls. Generates --wp--preset--dimension--{slug}. Core itself defines 25%, 50%, 75% and 100% for the Button block only.

dimensions.width, height, minHeight, minWidth, aspectRatio

6.2 to 7.1

Show the corresponding controls (all turned on by appearanceTools; width and height 7.0, minWidth 7.1).

shadow.presets, defaultPresets

6.2

Box-shadow presets. Generates --wp--preset--shadow--{slug}. Core ships five (natural, deep, sharp, outlined, crisp).

border.radiusSizes

6.9

Radius presets for the border radius control. Generates --wp--preset--border-radius--{slug}. There is no default set and no defaultRadiusSizes switch.

border.color, radius, style, width

5.9

Show the border controls.

background.backgroundImage, backgroundSize, gradient

6.4, 6.5, 7.1

Show the background image, size and gradient controls. Core turns gradient on for every theme.

position.sticky, position.fixed

6.2

Show the sticky position control (Group block); fixed is accepted by the schema but no core block uses it yet.

lightbox.enabled, lightbox.allowEditing

6.4

"Expand on click" for the Image block, and whether editors may change it.

blockVisibility.allowEditing

7.1

false hides the block visibility controls (hiding a block, 6.9, and hiding it per viewport, 7.0). Blocks already hidden stay hidden. Global only.

Lumen sets lightbox under blocks.core/image rather than at the top level, because core’s own theme.json sets lightbox.allowEditing to true for core/image at block level, and a block-level value from any layer wins over a top-level value from a higher layer. A top-level "lightbox": { "allowEditing": false } therefore never reaches the Image block’s sidebar.

Viewport breakpoints (7.1)

WordPress 7.1 adds responsive styles: styles under @mobile and @tablet keys, in theme.json or saved by the editors, that apply only inside a viewport range (see theme.json Styles). settings.viewport moves the two breakpoints:

State Default media query Lumen (600px, 1024px)

@mobile

@media (width <= 480px)

@media (width <= 600px)

@tablet

@media (480px < width <= 782px)

@media (600px < width <= 1024px)

desktop (block visibility only)

@media (width > 782px)

@media (width > 1024px)

The rules, from WP_Theme_JSON::sanitize_viewport_settings():

  • values must be plain px, em or rem lengths (600px, 37.5em); calc(), vw, percentages and unitless numbers are dropped, because the values are written into media queries;

  • if only one value is valid it keeps its name and becomes a single max-width query: a mobile of 50vw with a tablet of 40rem yields only @tablet, at width <= 40rem;

  • if tablet is not larger than mobile, only mobile is kept; if neither is valid, the defaults apply;

  • viewport is global: it cannot be set under settings.blocks, and there is no @desktop style key (the default style is the desktop style).

The same breakpoints drive block visibility per viewport and the editor’s device preview. The checks above were run with wp eval against the public helper:

Custom properties

settings.custom accepts any nested object. WordPress flattens it into --wp--custom-- variables, joining levels with -- and turning camelCase into kebab-case: custom.bookCard.coverWidth becomes --wp--custom--book-card--cover-width. Values are copied as they are, so they may reference presets. Lumen keeps its line heights and the measurements of the lumen/book-card block there, so the block’s stylesheet uses var(--wp--custom--book-card--cover-width) and a style variation or child theme can change the card without touching the block.

Two cautions: camelCase conversion means bookCard and book-card produce the same variable, and numbers stay unitless (1.6), so a value meant as a length needs its unit in the JSON.

Per-block settings

Every setting except viewport and blockVisibility can be repeated under settings.blocks.<block name> to change what the editor offers for that block type only. Lumen:

  • limits the Button block to two colours (lumen-red, ink); the variables are re-declared on the button’s selector (.wp-block-button .wp-block-button__link) and the colour classes are scoped to it;

  • gives the Code block its own small size (0.8125rem) and no custom sizes; the variable is re-declared on .wp-block-code, so has-small-font-size means a different size inside code blocks only;

  • hides the drop cap for paragraphs;

  • turns the Image lightbox on and locks it.

Block settings of custom blocks work the same way (settings.blocks.lumen/book-card), and blocks can declare their own defaults in block.json supports, which form the "blocks" layer below the theme (see Attributes, Supports and InnerBlocks).

Layers: core, parent, child and user

WordPress never reads one theme.json. WP_Theme_JSON_Resolver::get_merged_data() builds the result from four origins, each overriding the previous one, and each passes through a filter first:

flowchart LR core["Core: wp-includes/theme.json"] --> fd(["wp_theme_json_data_default"]) fd --> o1["origin: default"] blocks["block.json of registered blocks"] --> fb(["wp_theme_json_data_blocks"]) fb --> o2["origin: blocks"] supports["add_theme_support() values"] --> o3 parent["Parent theme.json: lumen"] --> o3["origin: theme"] child["Child theme.json: lumen-child"] --> ft(["wp_theme_json_data_theme"]) ft --> o3 user["wp_global_styles post: Styles panel"] --> fu(["wp_theme_json_data_user"]) fu --> o4["origin: custom (user)"] o1 -- "overridden by" --> o2 o2 -- "overridden by" --> o3 o3 -- "overridden by" --> o4 o4 --> out["merged settings and styles"] out --> api["wp_get_global_settings()"] out --> css["wp_get_global_stylesheet()"] out --> ed["block editor settings"]

Inside the theme origin, theme supports (add_theme_support( 'editor-color-palette' ) and similar, mostly used by classic themes) are the lowest level, then the parent’s theme.json, then the child’s. The user origin is the wp_global_styles post of the active theme, written by the Styles panel; choosing a style variation copies that variation’s JSON into it.

Merging rules that matter in practice:

  • Objects merge key by key: a child that sets only layout.wideSize keeps the parent’s contentSize.

  • Preset lists replace each other per origin: a child’s palette replaces the parent’s whole palette, it does not add to it. To add one colour, the child repeats the parent’s list.

  • Presets are kept per origin, not flattened: wp_get_global_settings( array( 'color', 'palette' ) ) returns default, theme and custom lists, and the editor shows them as separate groups ("Default", "Theme", "Custom").

  • Block-level values stay block-level: the parent’s settings.blocks survive in the child unless the child overrides the same block and key.

  • The wp_theme_json_data_theme filter receives the child’s data when a child theme is active; the parent’s file is merged underneath afterwards.

Changing settings from PHP

A plugin can change any layer with the four filters. Each receives a WP_Theme_JSON_Data object; update_with() merges a partial theme.json array (with its version) into it. The must-use plugin below removes the free colour picker and custom font sizes on every theme, which a publisher may want so that editors stay within the brand:

<?php
/**
 * Plugin Name: Lumen theme.json guardrails
 * Description: Locks colour and font-size choices to the theme presets on every theme.
 */
add_filter(
	'wp_theme_json_data_theme',
	static function ( WP_Theme_JSON_Data $theme_json ): WP_Theme_JSON_Data {
		return $theme_json->update_with(
			array(
				'version'  => 3,
				'settings' => array(
					'color'      => array( 'custom' => false ),
					'typography' => array( 'customFontSize' => false ),
				),
			)
		);
	}
);

Source: Code Reference: wp_theme_json_data_theme

Saved as wp-content/mu-plugins/lumen-theme-json-guardrails.php, it makes wp_get_global_settings( array( 'color', 'custom' ) ) return false. A user-layer value would still win over the theme layer, but the Styles panel cannot save a setting whose control it no longer shows. Results are cached per request; code that changes settings after wp_get_global_settings() has run must call wp_clean_theme_json_cache().

What the output shows:

  • The naming pattern is --wp--preset--{type}--{slug} for presets and --wp--custom--{path} for custom values. Theme CSS and block stylesheets should reference these variables, never the raw values.

  • Hidden defaults are still printed. defaultPalette: false removes core’s colours from the pickers, not from the CSS, so old content that uses vivid-red keeps rendering.

  • Spacing 70 and 80 come from core: with defaultSpacingSizes: false the theme’s 20 to 60 win, but core’s sizes for slugs the theme does not define are still printed. The editor offers only the theme’s five.

  • Per-block presets are re-declared on the block’s selector, which is how one slug can mean two values.

  • Duotone presets do not appear: their filters are output only for blocks that use them.

The presets part contains the utility classes, such as .has-lumen-red-background-color{background-color: var(--wp--preset--color--lumen-red) !important;} and, for the Button palette, the same classes wrapped in :where(.wp-block-button .wp-block-button__link). The layout values appear as --wp--style--global--content-size: 680px and --wp--style--global--wide-size: 1140px in the styles part, and useRootPaddingAwareAlignments produces the .has-global-padding rules there.

The merged settings themselves come from wp_get_global_settings(), with an optional path and a block_name or origin context, as the scripts in the layers and migration sections show.

The site used for these results is the standard Compose stack (MariaDB 11.8 and the wordpress:cli-2.12.0-php8.4 image) from Local Development Environments, with the theme folder copied into wp-content/themes/. Settings are read from the files on every request (with a per-request cache), so an edit to theme.json shows on the next page load without reactivating the theme. On a production server with a persistent object cache, the theme.json cache is cleared when the theme is switched (switch_theme calls wp_clean_theme_json_cache()); after deploying a changed theme.json without a switch, run wp cache flush.

Security notes

  • Theme files are trusted code: whatever theme.json declares is printed into CSS without sanitizing, like the theme’s own stylesheet. Only install themes from trusted sources.

  • The user layer is not trusted. When a user without unfiltered_html saves global styles, the JSON passes through wp_filter_global_styles_post(), which removes unsafe values with WP_Theme_JSON::remove_insecure_properties() before it is stored.

  • viewport values are restricted to px, em and rem because they are interpolated into media queries; other values are discarded rather than escaped.

  • Feature switches are interface limits, not permissions. A user with edit_posts can still put any value in block markup through the code editor or the REST API; to restrict what content may contain, use capabilities, block locking and allowed_block_types_all, not theme.json.

What older books and tutorials get wrong

Older advice Current state (7.1)

Design settings are configured with add_theme_support() calls (editor-color-palette, editor-font-sizes, custom-spacing) and the Customizer; the books on classic themes and on Customizer-based design do not mention theme.json at all

theme.json is the configuration file of block and hybrid themes. Theme supports still work, as the lowest level of the theme origin, but newer controls (spacing presets, shadows, radius presets, dimension presets, viewports) exist only in theme.json.

Full site editing and its configuration date from WordPress 5.4 to 5.6

theme.json version 1 arrived in 5.8, version 2 and block themes in 5.9, version 3 in 6.6.

Site-wide design is "still maturing" and needs a commercial theme or page builder

Presets, fluid type, responsive breakpoints and per-block settings cover what builders were used for; the trade-offs are discussed in Page Builders and Commercial Themes.

Tutorials written for version 2: a theme defines small or large font sizes and they override core’s

In version 3 they are ignored until defaultFontSizes is false; the same for spacing slugs and defaultSpacingSizes.

spacingSizes replaces the generated scale

In version 3 the two are merged.

"spacingScale": { "steps": 0 } to turn the scale off

Works at runtime but fails schema validation; set defaultSpacingSizes to false and leave the scale out.

$schema pointing to trunk

Pin the schema of the oldest supported WordPress version, such as wp/7.1; trunk lists keys that 7.1 does not support.

Breakpoints in theme CSS with hard-coded media queries

7.1 has settings.viewport and @mobile/@tablet styles; custom media queries remain possible but do not move with the theme’s breakpoints.

Common errors and pitfalls

Symptom Cause and fix

No setting in theme.json has any effect

The file has no version key (the whole file is then replaced by an empty document), or it is not valid JSON (WordPress ignores it). Validate it against the schema.

Theme font sizes or spacing sizes are ignored after upgrading to version 3

The slugs collide with core’s. Set defaultFontSizes or defaultSpacingSizes to false.

Core colours still appear in the CSS after defaultPalette: false

Expected: the variables stay for existing content; only the pickers hide them.

The child theme lost colours of the parent

Preset lists replace each other; repeat the parent’s entries in the child.

Buttons keep the old brand colour in a child theme

The parent’s settings.blocks.core/button palette re-declares the variables on the button; override it in the child too.

A top-level setting does not reach one block

Core or a block’s block.json sets the same key at block level (for example the Image lightbox). Set it under settings.blocks for that block.

@mobile styles apply at the wrong width

settings.viewport uses an unsupported unit, or tablet is not larger than mobile; check wp_get_global_settings( array( 'viewport' ) ).

A setting from a tutorial is accepted by the editor’s autocompletion but does nothing

The $schema points to trunk and the key is newer than the installed WordPress; pin the schema.

A change to theme.json is not visible

The user layer overrides it (reset Styles), a persistent object cache holds the old data (wp cache flush), or a style variation chosen in Styles has its own values.
