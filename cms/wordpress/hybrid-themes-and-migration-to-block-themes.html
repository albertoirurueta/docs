Hybrid Themes and Migration to Block Themes

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A classic theme does not have to be rewritten in one go to benefit from the block editor. WordPress lets it adopt block features one at a time: a theme.json file, block-based template parts printed from PHP, block patterns, and single block templates for some routes. A theme in that middle state is usually called a hybrid theme. Adding templates/index.html finally turns it into a block theme. This page, for theme developers maintaining a classic theme and site owners planning a redesign, takes the Lumen Press theme lumen-classic through every stage, checking after each step what WordPress detects, which admin screens appear and what the front end renders.

This page was written against WordPress 7.1.3 (released 2026-10-06; 7.1.4, a security release of 2026-10-28, is the version to run in production), PHP 7.4 minimum and 8.3+ recommended, theme.json version 3 and WP-CLI 2.12.0, and checked on 2026-10-28. WordPress 7.2, in beta and due in December 2026, does not change the hybrid-theme behaviour described here so far.

Theme kinds are introduced in Themes Overview; the classic pieces replaced here are covered in Customizer API, Widgets and Sidebars and Navigation and Menus.

What a hybrid theme is

"Hybrid theme" is a community term, not a third theme type. Only one file decides: a theme with a readable templates/index.html is a block theme (wp_is_block_theme() returns true); every other theme is classic, however many block features it uses. A hybrid theme renders pages through the PHP template hierarchy, has no Site Editor, and keeps the Customizer, Menus and Widgets screens.

Each block feature that a classic theme can adopt has its own switch and arrived in its own version:

Feature Since What it gives a classic theme

theme.json in the theme root

5.8

Global settings and styles: palettes, font sizes, layout widths, CSS custom properties, editor controls. wp_theme_has_theme_json() (6.2) becomes true, and core adds block-templates support, which enables block templates (see Step 4).

block_template_part()

5.9

Prints parts/<name>.html from a PHP template. It works without any theme support.

add_theme_support( 'block-template-parts' )

6.1

Lets administrators edit those parts in the Site Editor; without it they are files only.

patterns/*.php files

6.0

Auto-registered block patterns, as in block themes.

Appearance > Patterns

6.5

The Site Editor’s Patterns screen for any classic theme (moved into the Site Editor in 6.6).

Appearance > Design

6.8

Replaces Patterns for a classic theme that declares editor-styles or ships a theme.json: the Style Book and the Patterns screen.

Appearance > Fonts

7.0

The Font Library page for every theme, classic ones included.

Learn WordPress treats each stage as a valid stopping point. Staying hybrid suits a site that depends on PHP logic in its templates or on Customizer options it cannot drop yet; a full conversion suits owners who should edit layouts without a developer, or a theme being redesigned anyway.

Step 0: the classic starting point

lumen-classic is the minimal classic theme from Themes Overview, split into header.php, index.php and footer.php as described in Classic Theme Anatomy and The Loop. header.php prints the menu with wp_nav_menu( array( 'theme_location' => 'primary' ) ) and footer.php prints the widget area with dynamic_sidebar( 'lumen-footer' ). Its functions.php holds the three things the migration has to map: a menu location, a widget area and a Customizer colour.

<?php
/**
 * Lumen Classic theme setup (the starting point of the migration).
 *
 * @package Lumen_Classic
 */

	add_theme_support( 'title-tag' );
	add_theme_support( 'post-thumbnails' );
	add_theme_support( 'html5', array( 'search-form', 'comment-form', 'comment-list', 'gallery', 'caption', 'style', 'script' ) );
	register_nav_menus( array( 'primary' => __( 'Primary menu', 'lumen-classic' ) ) );
}
add_action( 'after_setup_theme', 'lumen_classic_setup' );

function lumen_classic_widgets_init() {
	register_sidebar(
		array(
			'id'            => 'lumen-footer',
			'name'          => __( 'Footer', 'lumen-classic' ),

			'after_widget'  => '</div>',
		)
	);
}
add_action( 'widgets_init', 'lumen_classic_widgets_init' );

function lumen_classic_customize_register( $wp_customize ) {
	$wp_customize->add_setting(
		'lumen_classic_accent_color',
		array(
			'default'           => '#a3271f',
			'sanitize_callback' => 'sanitize_hex_color',
		)
	);
	$wp_customize->add_control(
		new WP_Customize_Color_Control(
			$wp_customize,
			'lumen_classic_accent_color',

				'label'   => __( 'Accent colour', 'lumen-classic' ),

add_action( 'customize_register', 'lumen_classic_customize_register' );

function lumen_classic_enqueue_assets() {

Step 1: add theme.json

A theme.json in the theme root moves design tokens out of PHP and CSS and switches on the editor’s design tools. It uses the palette and widths of the block theme lumen; defaultPalette: false hides core’s colours:

	"$schema": "https://schemas.wp.org/wp/7.1/theme.json",
	"version": 3,
	"settings": {
		"appearanceTools": true,
		"color": {
			"defaultPalette": false,
			"palette": [
				{ "slug": "paper", "name": "Paper", "color": "#fbf8f1" },
				{ "slug": "ink", "name": "Ink", "color": "#1f1d1a" },
				{ "slug": "lumen-red", "name": "Lumen red", "color": "#a3271f" }
			]
		},
		"layout": { "contentSize": "680px", "wideSize": "1140px" }
	},
	"styles": {
		"color": { "background": "var(--wp--preset--color--paper)", "text": "var(--wp--preset--color--ink)" },
		"elements": {
			"link": {
				"color": { "text": "var(--wp--preset--color--lumen-red)" }
			}

	}

The colour now has a home in theme.json, so the Customizer setting and the inline CSS go. functions.php loses lumen_classic_customize_register() and its hook, lumen_classic_enqueue_assets() keeps only the wp_enqueue_style() call, and the a { color: ... } rule leaves style.css, because styles.elements.link now produces it. Carrying the owner’s Customizer value over

The owner’s Customizer value #8a1f18 lives in the option theme_mods_lumen-classic, which nothing reads any more. Owner choices belong in the user layer of global styles, a wp_global_styles post per theme where the Site Editor also stores edited presets. A one-off script copies the value across:

<?php
/**
 * Copies the Lumen Classic accent colour from the Customizer into the user's global styles.
 * Usage: wp eval-file /scripts/migrate-customizer.php --user=admin
 */
// Theme mods are stored per theme slug, so read the classic theme's option directly.
$mods   = get_option( 'theme_mods_lumen-classic', array() );
$accent = isset( $mods['lumen_classic_accent_color'] ) ? sanitize_hex_color( $mods['lumen_classic_accent_color'] ) : '';

if ( ! $accent ) {
	WP_CLI::success( 'The accent colour was never customized; the theme.json default applies.' );
	return;
}
// The wp_global_styles post of the active theme (created if missing).
$post = WP_Theme_JSON_Resolver::get_user_data_from_wp_global_styles( wp_get_theme(), true );
$data = json_decode( $post['post_content'], true );
// Override the theme palette, as the Site Editor does when a preset colour is edited.
$palette = wp_get_global_settings( array( 'color', 'palette', 'theme' ) );
foreach ( $palette as $i => $color ) {
	if ( 'lumen-red' === $color['slug'] ) {
		$palette[ $i ]['color'] = $accent;
	}
}
$data['settings']['color']['palette']['theme'] = $palette;

wp_update_post(
	array(
		'ID'           => $post['ID'],
		'post_content' => wp_json_encode( $data ),
	)
);
WP_CLI::success( "lumen-red is now {$accent} in global styles post {$post['ID']}." );

Source: Code Reference: WP_Theme_JSON_Resolver::get_user_data_from_wp_global_styles()

Step 2: block template parts in PHP templates

The header becomes a block template part: the part file, its theme.json registration and a block_template_part() call in header.php. Adding add_theme_support( 'block-template-parts' ) to lumen_classic_setup() lets administrators edit the part in the Site Editor; without it the part renders from the file only.

parts/header.html contains the Site Title and a Navigation block. The Navigation block has no ref yet, which is deliberate (see below):

<!-- wp:group {"tagName":"header","className":"site-header","layout":{"type":"flex","justifyContent":"space-between"}} -->
<header class="wp-block-group site-header">
	<!-- wp:site-title {"level":0} /-->
	<!-- wp:navigation {"overlayMenu":"mobile"} /-->
</header>
<!-- /wp:group -->

Source: Theme Handbook: Template Parts

theme.json gains a top-level list that assigns the part to the Header area, "templateParts": [ { "name": "header", "title": "Header", "area": "header" } ].

header.php keeps the document head and replaces the hand-written header with the part. The wp-site-blocks wrapper is the class block templates use for their outer element, so block layout styles apply the same way in both:

<?php // header.php: document head, then the block template part parts/header.html. ?>
<!DOCTYPE html>
<html <?php language_attributes(); ?>>
<head>
	<meta charset="<?php bloginfo( 'charset' ); ?>">
	<meta name="viewport" content="width=device-width, initial-scale=1">
	<?php wp_head(); ?>
</head>
<body <?php body_class(); ?>>
<?php wp_body_open(); ?>
<div class="wp-site-blocks">
<?php block_template_part( 'header' ); ?>
<main id="content">

Menus become Navigation

The menu items appear although nothing was migrated by hand: a Navigation block without ref uses the fallback, which converted the classic menu in the primary location into a wp_navigation post (ID 12) on the first page view, leaving the classic menu untouched. The converted items keep the classic CSS classes (menu-item menu-item-type-post_type ...) and absolute URLs. Once the result looks right, select the menu in the editor so that the part stores {"ref":12} instead of relying on the fallback. Importing from the block’s menu, scripting the import with WP_Classic_To_Block_Menu_Converter, and turning the automatic creation off are described in Navigation and Menus. register_nav_menus() stays in functions.php until Step 5, so the classic menu can still be edited and switched back to.

Step 3: patterns replace widgets

Widget areas have no block-theme equivalent; their content becomes patterns placed in template parts. As a pattern, the Lumen Press footer text becomes translatable and versioned with the theme:

<?php
/**
 * Title: Footer imprint
 * Slug: lumen-classic/footer-imprint
 * Categories: footer

What older books get wrong or leave out

Older advice Current state (7.1)

A theme is either PHP templates with the Customizer or nothing, and block themes are left out (Pro WordPress, Ultimate WordPress Handbook)

Classic themes can adopt theme.json, block template parts and patterns one at a time. They become block themes when templates/index.html is added.

Full site editing arrived in 5.4 to 5.6 (Pro WordPress)

theme.json came in 5.8, block themes and block_template_part() in 5.9, and block-template-parts support in 6.1.

Customizer settings are output with get_theme_mod() and no sanitize_callback (Ultimate WordPress Handbook)

Every setting needs a sanitize_callback, and output is escaped. In a migration, the values move to theme.json and the user’s global styles.

Menus are managed only under Appearance > Menus, and widgets are the way to add content to sidebars and footers (Pro WordPress)

In a block theme, menus are Navigation blocks over wp_navigation posts (classic menus can be imported), and widget areas become template parts and patterns.

"Reusable blocks" (Ultimate WordPress Handbook)

Renamed synced patterns in 6.3. Patterns are available to classic themes through Appearance > Patterns (6.5) and Design (6.8).

Common errors and pitfalls

Symptom Cause and fix

The Site Editor does not appear although the theme has theme.json, parts/ and templates/

Only templates/index.html makes a block theme. Check with wp eval 'var_dump( wp_is_block_theme() );'.

block_template_part( 'header' ) prints nothing

The file is not parts/header.html, or the name passed includes .html. The function prints nothing when no part is found.

The header part cannot be edited in the Site Editor

add_theme_support( 'block-template-parts' ) is missing; without it the part comes from the file only. The part editor cannot create or delete parts, because the PHP template decides where they appear.

Colours changed in theme.json have no effect

The user layer (an earlier Customizer migration or Site Editor edit) overrides the theme. Check the theme’s wp_global_styles post, or reset the styles.

A new pattern file is not registered

The pattern list is cached until Version changes. Bump it, or set WP_DEVELOPMENT_MODE to theme on development sites.

Customize is still in the menu of the finished block theme

Something still hooks customize_register, such as leftover theme code or a plugin. Remove the theme’s Customizer code.

Import widget area offers nothing

The widget area is no longer registered or is empty. Keep register_sidebar() until the import is done.

A block template in a hybrid theme is not used

A more specific PHP template exists. For example, single-lp_book.php wins over templates/single.html. Only equal or more specific block templates replace a PHP template.

Security notes: patterns/*.php files run PHP whenever patterns are registered, so escape output (esc_html_e(), esc_url()) and never echo request data in them. Run the migration scripts with WP-CLI on a staging copy first (see Backups and Disaster Recovery), never as web-reachable files.
