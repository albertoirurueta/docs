wp-config.php Reference

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page was written against WordPress 7.1.3 (released 2026-10-06; 7.1.4, a security release of 2026-10-28, is the version to run in production) and WP-CLI 2.12.0, and checked on 2026-10-28. WordPress 7.1 requires PHP 7.4 at minimum and recommends PHP 8.3 or newer; WordPress 7.2 is in beta and due in December 2026, and none of the constants below is expected to change with it. Every default and every behaviour marked as verified was checked with wp eval against a WordPress 7.1.3 site running in the official wordpress:7.1.3-php8.4-apache image with MariaDB 11.8, using the wordpress:cli-php8.4 image (WP-CLI 2.12.0) for the commands. The output blocks are real output, with secrets replaced by placeholders.

wp-config.php is the one configuration file of a WordPress install: the database credentials, the authentication keys and the table prefix are mandatory, and everything else is an optional constant that changes a core default. Creating the file (by the browser installer, by hand from wp-config-sample.php or with wp config create) and generating the keys and salts is covered in Installation; this page is the reference for what can go into it. The examples configure the Lumen Press site used throughout this sub-section: database lumen_press, table prefix lp_, host https://lumenpress.test/.

How WordPress reads wp-config.php

Every request enters through wp-load.php (directly, or through index.php, wp-admin/admin.php, wp-cron.php and the other entry points). The order of events is what makes a constant work or not:

  1. wp-load.php sets ABSPATH and looks for wp-config.php, first in the WordPress directory, then in the directory above it, which it uses only when that parent directory does not itself contain a wp-settings.php (that is, when it is not another WordPress install).

  2. wp-config.php runs. It define()s constants, sets $table_prefix and ends with require_once ABSPATH . 'wp-settings.php';.

  3. wp-settings.php calls the functions in wp-includes/default-constants.php, which define every constant that is still undefined with its core default (WP_MEMORY_LIMIT, WP_DEBUG, EMPTY_TRASH_DAYS, the cookie names, the content and plugin paths, and so on). Some defaults depend on the database (the cookie hash and FORCE_SSL_ADMIN use the site URL), so those are defined later in the load.

Three consequences follow. A constant must be defined above the require_once line, which is why the sample file marks the place with "Add any custom values between this line and the "stop editing" line". A PHP constant cannot be redefined, so the first definition wins and a plugin cannot override a value set in wp-config.php (redefining one raises a "Constant already defined" warning and keeps the old value). And nothing in wp-config.php can call WordPress functions such as add_filter(), because they are not loaded yet; filters that tune updates, cron or HTTP belong in a must-use plugin in wp-content/mu-plugins/.

The database settings, keys and prefix that every file contains are shown, with their explanation, in Installation; the full environment-driven file used by Lumen Press is at the end of this page.

Save the file as UTF-8 without a byte order mark, with nothing before <?php. It needs no closing ?>; any byte after one is sent to the browser and causes "headers already sent" errors.

Two values in that output surprise people. WP_DEBUG_DISPLAY defaults to true: as soon as WP_DEBUG is switched on without also setting WP_DEBUG_DISPLAY to false, errors are printed into the pages. And FORCE_SSL_ADMIN is true although wp-config.php does not define it: when the site URL starts with https://, core defaults it to true.

Changing values with WP-CLI

The wp config commands edit wp-config.php as text, without loading WordPress, which makes them usable when the site is broken. They need the file to be writable by the user that runs WP-CLI ("wp-config.php is not writable" otherwise).

wp config set WP_MEMORY_LIMIT 128M              # string value, quoted in the file
wp config set DISALLOW_FILE_EDIT true --raw     # --raw writes true, not 'true'
wp config set WP_DEBUG_LOG /var/log/wordpress/lumen-debug.log
wp config get WP_MEMORY_LIMIT
wp config is-true DISALLOW_FILE_EDIT; echo "exit=$?"
wp config delete WP_DEBUG_LOG
wp config shuffle-salts
Success: Added the constant 'WP_MEMORY_LIMIT' to the 'wp-config.php' file with the value '128M'.
Success: Added the constant 'DISALLOW_FILE_EDIT' to the 'wp-config.php' file with the raw value 'true'.
Success: Added the constant 'WP_DEBUG_LOG' to the 'wp-config.php' file with the value '/var/log/wordpress/lumen-debug.log'.
128M
exit=0
Success: Deleted the constant 'WP_DEBUG_LOG' from the 'wp-config.php' file.
Success: Shuffled the salt keys.

Source: WP-CLI Commands: wp config

New constants are inserted just above the "stop editing" line. wp config list prints what the file defines (names, types and values, so it shows secrets), not the core defaults. Without --raw, true, false and numbers are written as quoted strings, and 'false' is a non-empty string, which PHP treats as true; booleans and integers always need --raw. wp config get reads the file only, so it reports "not defined in the 'wp-config.php' file" for a constant that runs with its core default; use wp eval (above) for the effective value. wp config shuffle-salts replaces each key definition with a literal string: on a file that reads the keys from environment variables (see Loading values from environment variables), it silently replaces the getenv() calls, which was confirmed on the official Docker image’s wp-config.php. Rotate the variables instead.

Database

Constant Default Meaning and notes

DB_NAME, DB_USER, DB_PASSWORD

(required)

Database name and credentials. The user needs the privileges listed in Installation; it should not be a MySQL administrative account.

DB_HOST

(required)

localhost, a host name, host:port (db.internal:3307) or a socket (localhost:/run/mysqld/mysqld.sock).

DB_CHARSET

utf8mb4 in the sample

Character set of the connection and of new tables. wp config create writes utf8 unless given --dbcharset=utf8mb4; WordPress still creates utf8mb4 tables when the server supports them. Details in Database Schema.

DB_COLLATE

''

Empty lets WordPress choose the best collation for the character set. Leave it empty unless a collation is required.

MYSQL_CLIENT_FLAGS

0

Flags passed to mysqli_real_connect(), for example MYSQLI_CLIENT_SSL for a TLS connection to a remote database.

$table_prefix (variable, not a constant)

wp_

Prefix of every table. Letters, digits and underscores only. Changing it after installation makes WordPress believe it is not installed: the tables, and the prefixed lp_user_roles option and lp_capabilities user meta keys, must be renamed too.

CUSTOM_USER_TABLE, CUSTOM_USER_META_TABLE

not defined

Share the users tables of another install. Set them before installing; a usermeta table is still created, and roles must be managed per site.

WP_ALLOW_REPAIR

not defined

Enables /wp-admin/maint/repair.php, which repairs and optimizes the tables. The page works without logging in, so remove the constant as soon as the repair is done.

DO_NOT_UPGRADE_GLOBAL_TABLES

not defined

Skips the expensive ALTER TABLE on the users and Multisite global tables during a core database upgrade; for large networks whose tables are upgraded separately.

Source: Advanced Administration Handbook: wp-config.php

WP_ALLOW_REPAIR repairs table structures; it does not reset passwords. An older book recommends it for regaining access to a locked-out account, which it cannot do; use wp user update lp_admin --user_pass=<new-password> (or the "Lost your password?" e-mail) instead, as described in Security Hardening.

Authentication keys and salts

The eight constants AUTH_KEY, SECURE_AUTH_KEY, LOGGED_IN_KEY, NONCE_KEY, AUTH_SALT, SECURE_AUTH_SALT, LOGGED_IN_SALT and NONCE_SALT sign the login cookies and nonces. They are generated once per site by the WordPress.org secret-key service or wp config shuffle-salts; their generation and what happens when one is missing are explained in Installation. Changing them logs every user out, which is the standard response to a suspected compromise. They are not encryption keys: a database dump does not depend on them, and nothing in wp-config.php is "encrypted" by WordPress. An older book suggests encrypting the values in wp-config.php; PHP must read them in clear text on every request, so the real protections are file permissions, a location outside the web root and, best, keeping the secrets out of the file altogether (environment variables or a secret manager).

Site URLs and cookies

Constant Default Meaning and notes

WP_HOME

home option

Site address (the public URL). Overrides the option without changing the database, and greys out the field in Settings > General.

WP_SITEURL

siteurl option

WordPress address (where core lives). Differs from WP_HOME only when core is in a subdirectory.

RELOCATE

not defined

When true, a visit to wp-login.php rewrites the siteurl option to the URL used to reach it. A one-off rescue tool after a move; remove it afterwards.

COOKIE_DOMAIN

''

Domain of the login cookies. Empty means the current host. Set it only to share cookies across subdomains on purpose.

COOKIEPATH, SITECOOKIEPATH, ADMIN_COOKIE_PATH, PLUGINS_COOKIE_PATH

derived from the URLs

Cookie paths. Rarely set by hand.

COOKIEHASH

md5() of the site URL

Suffix of every cookie name (wordpress_logged_in_<hash>). Changing the site URL therefore logs users out.

AUTH_COOKIE, SECURE_AUTH_COOKIE, LOGGED_IN_COOKIE, TEST_COOKIE, RECOVERY_MODE_COOKIE

wordpress_... names

Cookie names; changing them only renames the cookies, it adds no security.

Source: Advanced Administration Handbook: wp-config.php

Pinning WP_HOME and WP_SITEURL per environment is the usual way to stop a staging copy from redirecting to production after a database import; the full move procedure, with wp search-replace, is in Importing, Exporting and Migrating. The cookie flags themselves (HttpOnly, Secure) are covered in the Cookies article of the Advanced Administration Handbook.

Directories and paths

Constant Default Meaning and notes

ABSPATH

directory of wp-config.php + /

Path to core. Set by the last lines of the sample; never change it, even when wp-config.php moves one level up.

WP_CONTENT_DIR, WP_CONTENT_URL

ABSPATH . 'wp-content', siteurl/wp-content

Moves wp-content. Full path and full URL, no trailing slash. Set both.

WP_PLUGIN_DIR, WP_PLUGIN_URL

WP_CONTENT_DIR . '/plugins'

Moves the plugins directory. PLUGINDIR (relative to ABSPATH) exists only for old plugins.

WPMU_PLUGIN_DIR, WPMU_PLUGIN_URL

WP_CONTENT_DIR . '/mu-plugins'

Must-use plugins; MUPLUGINDIR is the relative legacy form.

UPLOADS

wp-content/uploads

Uploads directory relative to ABSPATH. Without the constant the Media settings decide.

WP_LANG_DIR

WP_CONTENT_DIR . '/languages'

Location of translation files.

WP_TEMP_DIR

system temp directory

Where downloads and unzips happen during updates; set it when /tmp is not writable or is too small.

WP_DEFAULT_THEME

twentytwentyfive

Theme used when installing and as the fallback when the active theme is missing.

TEMPLATEPATH, STYLESHEETPATH

from the active theme

Parent and child theme paths. Defined late; use get_template_directory() and get_stylesheet_directory().

Source: Advanced Administration Handbook: wp-config.php

There is no constant for the themes directory: a plugin can add one with register_theme_directory(). A layout that keeps core in its own directory (/wp) and wp-content beside it, as Composer-based setups do, uses the URL and content constants together: WP_SITEURL points to /wp, WP_HOME to the root, and WP_CONTENT_DIR/WP_CONTENT_URL to the content directory beside it, as described in Giving WordPress Its Own Directory.

Environment type and development mode

WP_ENVIRONMENT_TYPE (WordPress 5.5) tells core, plugins and hosts which kind of environment runs the code. The accepted values are local (added in 5.5.1), development, staging and production. wp_get_environment_type() resolves it in this order:

  1. the WP_ENVIRONMENT_TYPE environment variable, if set;

  2. the WP_ENVIRONMENT_TYPE constant, which overrides the variable;

  3. anything else, including an unknown value, becomes production.

Core itself uses it in a few places: development turns WP_DEBUG on when WP_DEBUG is not defined, and local relaxes the HTTPS requirement of application passwords. Plugins use it to disable e-mails, payment gateways or search indexing outside production. The list of types cannot be extended; a WP_ENVIRONMENT_TYPES constant was removed in 5.5.1 and now only triggers a deprecation notice. Each line below was run against a wp-config.php that does not define WP_DEBUG:

E='printf( "%s WP_DEBUG=%s\n", wp_get_environment_type(), var_export( WP_DEBUG, true ) );'
WP_ENVIRONMENT_TYPE=development wp eval "$E"
WP_ENVIRONMENT_TYPE=staging     wp eval "$E"
WP_ENVIRONMENT_TYPE=prod        wp eval "$E"     # not an accepted value
WP_ENVIRONMENT_TYPE=staging     wp --exec="define( 'WP_ENVIRONMENT_TYPE', 'local' );" eval "$E"
development WP_DEBUG=true
staging WP_DEBUG=false
production WP_DEBUG=false
local WP_DEBUG=false

Source: Code Reference: wp_get_environment_type()

WP_DEVELOPMENT_MODE (WordPress 6.3) is a separate switch for people working on code: core, plugin, theme, all, or '' (default). It does not change error output; it changes caching that gets in the way of development, for example theme stops global styles and theme.json data from being cached. wp_is_development_mode( 'theme' ) checks it, and all matches every type. A non-empty development mode also turns WP_DEBUG on when WP_DEBUG is not defined. Never set it in production.

// lumen theme development on a laptop.
define( 'WP_ENVIRONMENT_TYPE', 'local' );
define( 'WP_DEVELOPMENT_MODE', 'theme' );

Source: Make WordPress Core: Configuring development mode in 6.3

Debugging

Constant Default Meaning and notes

WP_DEBUG

false (true in development or a development mode)

Sets error_reporting( E_ALL ) and enables the two constants below. Shows deprecation notices from _deprecated_*().

WP_DEBUG_DISPLAY

true

With WP_DEBUG, true sets display_errors to 1 and false sets it to 0; null leaves the php.ini value alone. REST, Ajax, XML-RPC and installer requests never display errors.

WP_DEBUG_LOG

false

true logs to wp-content/debug.log; a path string (5.1+) logs to that file. Only acts when WP_DEBUG is true.

SCRIPT_DEBUG

false

Loads the non-minified core JavaScript and CSS.

SAVEQUERIES

not defined

Records every query with its time and caller in $wpdb->queries. Costs memory and time on every request.

CONCATENATE_SCRIPTS

true in the admin

false stops load-scripts.php from concatenating admin scripts; useful when a broken script hides others.

WP_DISABLE_FATAL_ERROR_HANDLER

not defined

Disables the fatal error handler and recovery mode (5.2), so fatal errors show as plain PHP errors.

RECOVERY_MODE_EMAIL

site admin e-mail

Address that receives the recovery-mode link after a fatal error.

Source: Advanced Administration Handbook: Debugging in WordPress

wp-content/debug.log is inside the web root, so on most servers anyone can download it, together with paths, query fragments and sometimes personal data. Site Health reports both a displayed and a publicly reachable log. In production, either keep WP_DEBUG off or log to a path outside the web root and never display:

define( 'WP_DEBUG', true );
define( 'WP_DEBUG_DISPLAY', false );
define( 'WP_DEBUG_LOG', '/var/log/wordpress/lumen-debug.log' );   // writable by the PHP user, outside the web root

Source: Advanced Administration Handbook: Debugging in WordPress

Tools, Site Health and troubleshooting procedures are on Debugging, Site Health and Troubleshooting.

Memory

WP_MEMORY_LIMIT is the PHP memory limit WordPress asks for on every request, and WP_MAX_MEMORY_LIMIT the one it asks for in heavier admin tasks (image processing, updates, imports). Core defaults are 40M on a single site, 64M on Multisite, and 256M for the maximum. Both work by calling ini_set( 'memory_limit', ... ), with three rules that explain most "the constant does nothing" reports:

  • WordPress only raises the limit. The 40M default is below the usual php.ini value, so it changes nothing.

  • If the host forbids runtime changes (memory_limit set with php_admin_value or similar), both constants fall back to the current limit and setting them has no effect; the limit must be raised in php.ini or the pool configuration.

  • A php.ini value above 256M (or -1, as WP-CLI uses) is kept as the maximum.

Measured in a web request on the wordpress:7.1.3-php8.4-apache image, whose php.ini sets 128M, first with no constants and then with WP_MEMORY_LIMIT at 256M and WP_MAX_MEMORY_LIMIT at 512M, using a throwaway probe script in the web root (delete such a file right after use):

<?php
// probe.php: memory limits before and after WordPress loads.
$before = ini_get( 'memory_limit' );
require __DIR__ . '/wp-load.php';
header( 'Content-Type: text/plain' );
printf( "php.ini memory_limit=%s, WP_MEMORY_LIMIT=%s, WP_MAX_MEMORY_LIMIT=%s, after load=%s\n",
	$before, WP_MEMORY_LIMIT, WP_MAX_MEMORY_LIMIT, ini_get( 'memory_limit' ) );
php.ini memory_limit=128M, WP_MEMORY_LIMIT=40M, WP_MAX_MEMORY_LIMIT=256M, after load=128M
php.ini memory_limit=128M, WP_MEMORY_LIMIT=256M, WP_MAX_MEMORY_LIMIT=512M, after load=256M

Source: Advanced Administration Handbook: wp-config.php

On the same site converted to Multisite, WP_MEMORY_LIMIT reported 64M. An older book gives different Multisite memory defaults; the values above come from default-constants.php in 7.1.

WP-Cron

Constant Default Meaning and notes

DISABLE_WP_CRON

not defined

true stops page loads from spawning wp-cron.php. Scheduled events then only run if a system cron job calls wp-cron.php or wp cron event run --due-now.

ALTERNATE_WP_CRON

not defined

Runs cron through a redirect instead of a loopback request, for hosts where loopbacks fail. Visitors may see a ?doing_wp_cron URL; a system cron is the better fix.

WP_CRON_LOCK_TIMEOUT

60 (seconds)

Minimum time between two cron runs.

Source: Plugin Handbook: Hooking WP-Cron Into the System Task Scheduler

Setting DISABLE_WP_CRON without adding the system job silently stops scheduled posts, update checks and the Lumen Press stock synchronisation. The cron setup is on WP-Cron and Scheduled Tasks.

Updates and file modifications

Automatic core updates

WP_AUTO_UPDATE_CORE Effect

not defined

Minor (security and maintenance) releases always. Major releases follow the "automatic updates for all new versions" setting on Dashboard > Updates, stored in the auto_update_core_major site option, which is enabled on sites installed with 5.6 or later.

'minor'

Minor releases only, whatever the Dashboard setting says.

true

All core releases, major and minor. 'beta', 'rc', 'development' and 'branch-development' also mean "all", and also opt into pre-release builds of that channel.

false

No automatic core updates, not even security releases. Site Health warns about it.

Asked whether it would update to an offered 7.1.4 (minor) and 7.2.0 (major), a fresh 7.1.3 site answered:

for v in "" "'minor'" "true" "false"; do
  [ -n "$v" ] && X="define( 'WP_AUTO_UPDATE_CORE', $v );" || X=""
  wp --exec="$X" eval 'require_once ABSPATH . "wp-admin/includes/class-wp-upgrader.php";
    printf( "%-10s 7.1.4=%s 7.2.0=%s\n",
      defined( "WP_AUTO_UPDATE_CORE" ) ? var_export( WP_AUTO_UPDATE_CORE, true ) : "(unset)",
      var_export( Core_Upgrader::should_update_to_version( "7.1.4" ), true ),
      var_export( Core_Upgrader::should_update_to_version( "7.2.0" ), true ) );'
done
(unset)    7.1.4=true 7.2.0=true
'minor'    7.1.4=true 7.2.0=false

HTTPS

FORCE_SSL_ADMIN set to true redirects wp-login.php and every admin page to HTTPS, so passwords and the authentication cookies never travel in clear text. Since the site URL decides its default, a site configured with https:// URLs already has it; defining it explicitly protects against a database import that brings an http:// URL.

FORCE_SSL_LOGIN was deprecated in WordPress 4.0, when logins and the admin were unified under FORCE_SSL_ADMIN. 7.1 still honours it (a true value calls force_ssl_admin( true )), but it should be replaced. On an http:// site with neither constant defined, then with only FORCE_SSL_LOGIN:

  var_export( FORCE_SSL_ADMIN, true ), var_export( force_ssl_admin(), true ) );'

Behind a load balancer or reverse proxy that terminates TLS, PHP sees plain HTTP and WordPress produces redirect loops or mixed content. Tell it about the original scheme, trusting the header only because the proxy always sets it:

// The proxy terminates TLS and always sets X-Forwarded-Proto.
if ( isset( $_SERVER['HTTP_X_FORWARDED_PROTO'] ) && 'https' === $_SERVER['HTTP_X_FORWARDED_PROTO'] ) {
	$_SERVER['HTTPS'] = 'on';
}

Source: Advanced Administration Handbook: HTTPS

The official Docker image ships a similar block in its wp-config.php. On a server reachable without the proxy, anyone can send the header, so restrict direct access first.

Constants that do not exist or no longer work

Several constants found in older books or old tutorials have no effect in WordPress 7.1. Defining them raises no error, which is why they survive in copied configurations. The dump at the top of this page shows WP_ADMIN_EMAIL and WP_USE_EXT_MYSQL as not defined, and a search of the 7.1.3 source finds no reference to WP_ADMIN_EMAIL at all.

Constant Status

WP_ADMIN_EMAIL

Does not exist. It is not a core constant, and nothing in core reads it. The administration e-mail is the admin_email option, changed in Settings > General (with a confirmation e-mail since 4.9) or with wp option update admin_email. One older book lists it as a configuration constant.

WP_USE_EXT_MYSQL

Obsolete. It once chose the old mysql PHP extension over mysqli. PHP 7.0 removed that extension, and WordPress 6.4 removed the remaining support from wpdb, which now always uses mysqli. One older book still recommends it.

FORCE_SSL_LOGIN

Deprecated in 4.0. Still forces HTTPS on the admin when true, but use FORCE_SSL_ADMIN.

WPLANG

Legacy (before 4.0). The site language is the WPLANG option, set in Settings > General or with wp site switch-language.

WP_ENVIRONMENT_TYPES

Removed in 5.5.1. The list of environment types is fixed; defining it only triggers a deprecation notice.

WP_ALLOW_REPAIR "to reset passwords"

The constant exists but only repairs tables (see Database).

Loading values from environment variables

A wp-config.php with literal passwords and keys cannot be committed to version control, and must be edited per server. Reading the values from environment variables makes the file identical in every environment and keeps the secrets in the platform that already manages them (Docker or Kubernetes secrets, the host’s control panel, a secret manager). Core helps in three places: WP_ENVIRONMENT_TYPE and, since 7.1, the two speculative loading defaults are read from the environment directly; everything else goes through getenv() in wp-config.php.

The Lumen Press configuration below reads every per-environment value and every secret from the environment. A NAME_FILE variable pointing to a file takes precedence, which is how Docker and Kubernetes secrets are mounted. A missing secret stops the request with a 500 and a log line, rather than letting WordPress fall back to empty credentials or database-stored salts:

<?php
// wp-config.php for Lumen Press: identical in every environment; values and secrets come from the environment.

if ( ! function_exists( 'lumen_env' ) ) {
	// An environment variable, or the contents of the file named by NAME_FILE (Docker/Kubernetes secrets).
	function lumen_env( $name, $default = null ) {
		$file = getenv( $name . '_FILE' );
		if ( false !== $file && is_readable( $file ) ) {
			return rtrim( file_get_contents( $file ), "\r\n" );
		}

		$value = getenv( $name );
		if ( false !== $value && '' !== $value ) {
			return $value;
		}

		if ( null === $default ) {
			error_log( 'wp-config.php: required environment variable ' . $name . ' is not set.' );
			http_response_code( 500 );
			exit( 1 );
		}

		return $default;
	}
}

Keeping wp-config.php outside the web root

WordPress also finds wp-config.php one directory above its own directory, as long as that directory is not another WordPress install (it must not contain wp-settings.php). With the document root at /srv/lumenpress/public and WordPress installed there, /srv/lumenpress/wp-config.php is outside what the web server serves. Nothing else changes: ABSPATH keeps its default, contrary to an older book that says it must be edited after the move. Moving the file on the official image from /var/www/html/ to /var/www/ left the site working unchanged.

/srv/lumenpress/
├── wp-config.php          # 440, owner deploy, group www-data
└── public/                # document root
    ├── index.php
    ├── wp-settings.php
    ├── wp-admin/
    ├── wp-includes/
    └── wp-content/

Source: Advanced Administration Handbook: Hardening WordPress

The Hardening page notes that the security benefit of the move is debated: a correctly configured PHP server never serves the file’s source, and the real exposure is a PHP handler failure or a backup copy (wp-config.php.bak, wp-config.php~) left in the web root, which the server will serve as text. Whatever the location, restrict the file to the owner and the web server group (chmod 440 or 400), block direct requests to it in the web server (see Web Servers: Apache and nginx), and never leave edited copies behind. With WordPress in a subdirectory of the document root (public/wp/), the "one level up" location is still inside the web root, so the two layouts do not combine; there, keep the secrets in environment variables instead.
