Comparison and Decision Guide

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Most WordPress projects make the same dozen choices, from where the site runs to whether WordPress is the right tool at all. This page collects them as decision tables. Each row links the page of this sub-section that explains the option and the official source behind it, and each table ends with the choice the Lumen Press project made. For a dated, sourced comparison of WordPress with fifteen other CMSs, see the CMS Comparison.

The guide was written against WordPress 7.1.3 (examples tested; released 2026-10-06), with PHP 7.4 minimum and 8.3+ recommended, WP-CLI 2.12.0, @wordpress/env 12.0.0, Action Scheduler 4.2.0 and WPGraphQL 2.25.0, and checked on 2026-10-28. WordPress 7.1.4, released on 2026-10-28, is the current security release and should be used in production; it changes no API. WordPress 7.2 is planned for 2026-12-08 and does not change any of the recommendations below so far. No prices are given anywhere: plans and fees change too often to be useful in a reference.

How to use this guide

Start from the decision tree, then read the matching table row and follow its link: the tables summarise trade-offs, the linked pages show configuration, code and pitfalls. Two principles run through every table:

  • Prefer what core provides. Core APIs (registered meta, the REST API, the Interactivity API, block themes) are maintained with every release and documented in the official handbooks. Ecosystem tools (page builders, WPGraphQL, Action Scheduler, field plugins) are good choices when a core API does not cover the need, but each adds a dependency that must be vetted and updated.

  • Choose the smallest thing that is enough, and keep the exit open. A custom table, a network, a headless front end or a page builder is hard to undo. Each table lists what leaving costs.

REST API or WPGraphQL

Core ships the REST API. WPGraphQL is an ecosystem plugin (version 2.25.0 at the check date, requiring WordPress 6.0 and PHP 7.4) that adds a GraphQL endpoint at /graphql; its directory listing describes it as becoming a canonical plugin. Faust.js, maintained by WP Engine, is a headless framework built on WPGraphQL.

Option Choose when Costs and limits Covered in Official source

REST API (core)

Most cases: no extra plugin, every core and many plugin features already exposed, plain GET URLs that HTTP caches and CDNs cache, custom routes with schemas and permission callbacks

Fixed response shapes: related objects need _embed or extra requests, and _fields trims nested properties of the resource itself (dotted names since 5.3) but not the objects inside _embedded

REST API: Using It, REST API: Extending It

REST API Handbook: Global Parameters

WPGraphQL (ecosystem plugin)

A headless front end that needs nested data (posts with authors, terms and meta) in one request with exactly the fields asked for, typed tooling, or Faust.js

One more plugin to vet and update; custom post types and taxonomies must opt in to the schema (show_in_graphql); queries sent by POST are not cached by HTTP caches without extra work (the WPGraphQL Smart Cache plugin)

Headless WordPress

WPGraphQL: WPGraphQL vs. WP REST API, WPGraphQL: Custom Post Types

The difference shows on a test site (WordPress 7.1.3, WPGraphQL 2.25.0, two posts by maria.editor, plain permalinks, so the REST route is passed as rest_route). The REST request asks for the post titles and the author’s name only:

curl -s 'http://lumenpress.test/?rest_route=/wp/v2/posts&per_page=2&_embed=author&_fields=id,title.rendered,_links.author,_embedded.author.name'

Source: REST API Handbook: Global Parameters

The response (1,867 bytes) contains the titles and, for each post, the whole embedded author object: id, name, url, description, link, slug, three avatar_urls and its own _links. The nested _fields entry did not trim the embedded object. The GraphQL request names exactly the fields it needs:

curl -s http://lumenpress.test/graphql \
  -H 'Content-Type: application/json' \
  -d '{"query":"{ posts(first: 2) { nodes { databaseId title author { node { name } } } } }"}'

Source: WPGraphQL: Introduction

{"data":{"posts":{"nodes":[{"databaseId":5,"title":"Spring catalogue announced","author":{"node":{"name":"maria.editor"}}},{"databaseId":4,"title":"The Glass Orchard is out","author":{"node":{"name":"maria.editor"}}}]}},"extensions":{"debug":[{"type":"DEBUG_LOGS_INACTIVE","message":"GraphQL Debug logging is not active. To see debug logs, GRAPHQL_DEBUG must be enabled."}]}}

The GraphQL response is 375 bytes, most of it the debug notice. The difference matters on list pages with many related objects, where REST needs _embed with full objects or one request per related resource; the REST URL, in turn, is a cacheable GET with no plugin. A query for users { nodes { email } } sent anonymously returned null for every email: WPGraphQL applies its own visibility rules, which must be checked for every type a plugin adds.

Lumen Press uses the REST API for its reader app: the routes it needs already exist in wp/v2 and lumen/v1, its requests are plain GET URLs that HTTP caches can store, and no additional plugin is required.

When WordPress is not the right tool

WordPress is a content management system: its strengths are editing, publishing, media, roles, themes and a large extension ecosystem. The general criteria are in When a CMS is the right tool, and when a framework is.

Situation Signs Better choice Covered in Official source

A complex application

The core is business logic, not content: bookings, billing, workflows with many states, a multi-tenant SaaS; most data does not fit posts and meta and ends up in many custom tables; the team fights the hook order and the request lifecycle more than it uses them

A web framework, with WordPress kept for the marketing site or blog if needed, the two talking over REST

An API with no editors

No one logs in to write content; the product is an API for apps or services

A backend framework; a headless CMS only if editors appear later

An online shop

Products, carts, payments, taxes and orders are the core of the site

WooCommerce, the WordPress e-commerce plugin, for a shop that also publishes content; a dedicated e-commerce platform when the shop is the whole product. Both are the subject of the E-commerce section

WordPress.org Plugin Directory

The boundary is rarely all or nothing: a Laravel application can serve the logged-in product while WordPress serves the marketing pages, and a WordPress site can call a separate service, as lumen-catalog does with its distributor API.

Lumen Press is a content business (news, pages, a book catalogue, authors, events), which is the case WordPress was built for. Its loans and stock are small enough to stay in lumen-catalog, and it sells no books on the site: each book page links to local bookshops through the hooked lumen/local-bookshop block.

Checking where an existing site stands

On an inherited site, most of the questions above can be answered from the code and the database before reading a line of the theme. The script below prints the facts the tables depend on and runs under wp eval-file:

<?php
/**
 * Prints the facts the comparison tables depend on, for the site WP-CLI is pointed at.
 * Run with: wp eval-file decision-snapshot.php
 */
global $wpdb;

$theme = wp_get_theme();
if ( wp_is_block_theme() ) {
	$theme_kind = 'block';
} elseif ( wp_theme_has_theme_json() ) {
	$theme_kind = 'classic with theme.json (hybrid)';
} else {
	$theme_kind = 'classic';
}

$namespaces = rest_get_server()->get_namespaces();

$cron_events = 0;
foreach ( _get_cron_array() as $hooks ) {
	foreach ( $hooks as $events ) {
		$cron_events += count( $events );
	}
}

$rows = array(
	'WordPress'          => get_bloginfo( 'version' ) . ' (PHP ' . PHP_VERSION . ')',
	'Environment type'   => wp_get_environment_type(),
	'Theme'              => $theme->get_stylesheet() . ': ' . $theme_kind,
	'Multisite'          => is_multisite() ? 'yes, ' . get_blog_count() . ' sites' : 'no',
	'WP-Cron trigger'    => ( defined( 'DISABLE_WP_CRON' ) && DISABLE_WP_CRON ) ? 'system scheduler (DISABLE_WP_CRON)' : 'page loads',
	'Cron events'        => $cron_events,
	'Action Scheduler'   => class_exists( 'ActionScheduler' ) ? 'loaded' : 'not loaded',
	'Object cache'       => wp_using_ext_object_cache() ? 'persistent' : 'per request only',
	'Active plugins'     => count( (array) get_option( 'active_plugins', array() ) ),
	'REST namespaces'    => implode( ', ', $namespaces ),
	'GraphQL endpoint'   => function_exists( 'graphql' ) ? 'yes' : 'no',
	'postmeta rows'      => (int) $wpdb->get_var( "SELECT COUNT(*) FROM {$wpdb->postmeta}" ),
);

foreach ( $rows as $label => $value ) {
	printf( "%-19s %s\n", $label . ':', $value );
}

Source: WP-CLI Commands: wp eval-file, Code Reference: wp_is_block_theme(), Code Reference: wp_theme_has_theme_json(), Code Reference: wp_using_ext_object_cache()

On a 7.1.3 test site after switching to the classic Twenty Twenty-One theme, activating WPGraphQL 2.25.0, setting DISABLE_WP_CRON and WP_ENVIRONMENT_TYPE with wp config set and publishing two posts:

$ wp eval-file decision-snapshot.php

Cron events:        9

Reading the output against the tables: a classic theme without theme.json is the starting point of the migration path; DISABLE_WP_CRON without a matching system cron entry means nothing runs; a large postmeta rows count with slow catalogue pages points to the custom-table criteria; and per request only on a busy site is the first item of Performance and Caching. The wp-abilities/v1 namespace is the Abilities API that core ships since 6.9 (Abilities API and MCP Adapter).

Where older books are outdated

The books this sub-section was compared with make several of these decisions for the reader, and some of the choices they present no longer hold:

  • Ultimate WordPress Handbook builds its sites around the Customizer and a GeneratePress/GenerateBlocks combination and calls full site editing "still maturing". Block themes have been the default since 5.9 and the focus of the Theme Handbook; a builder or multipurpose theme is a valid option with the trade-offs above, not a requirement.

  • Pro WordPress covers classic themes only and says core offers two-factor authentication and built-in caching and minification. Both are plugin or server features; the "existing plugin" and "where the site runs" tables are where they are chosen.

  • All-in-One For Dummies states that plugins cannot depend on other plugins. Since 6.5 the Requires Plugins header declares dependencies, which changes the "custom plugin that extends another plugin" case.

The complete list is in Where Older Books and Tutorials Are Outdated.
