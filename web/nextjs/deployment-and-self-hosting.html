Deployment & Self-Hosting

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when the facts and examples below were checked; the official documentation reports @doc-version 16.3.8), React 19.3.0 and Node.js 20.9.0 or later. It covers what is common to the App Router and the Pages Router — both are served by the same production server and deployed in the same ways — and says so where they differ. Caching matters for self-hosting, so each example states which model it uses: the previous model (the default) or Cache Components (the opt-in cacheComponents: true model). The examples were run against a scratch copy of the Bookshelf (Next.js 16.3.8, Node.js 24.16, macOS) and use the previous model. docker build and docker run could not be run for this page: the Docker CLI is installed on the machine that was used, but its daemon was not running. The standalone output that the Dockerfile produces was built and run with plain node in a clean directory laid out exactly as the image is, and every other example was built with next build, started, and queried with curl. Two things were not executed at all and are labelled where they appear: the NGINX configuration and the CI workflow files.

Deployment is where "it works on my machine" meets everything the framework did not decide for you: how many instances there are, where their caches live, which proxy sits in front, how a new release replaces an old one. The good news is that the minimum is small — a Node.js process — and the rest is a short list of knobs. This page walks through the deployment targets, the Adapters API, each self-hosting concern, multi-zones, custom servers, CI caching, and ends with a production checklist. For the build-time mechanics see Configuration, TypeScript and Environment Variables; for the cache layers themselves see Caching.

The Deployment Targets

The official "Deploying" page lists four options. Which features each supports is the first thing to decide on.

Table 1. The deployment options and what they support (Deploying page, checked 2026-10-03)
Option Feature support Choose it when

Node.js server (next build then next start)

All features.

You have a VM, a PaaS that runs Node.js, or a process manager, and want the simplest thing that supports everything.

Docker container (usually output: 'standalone')

All features.

You deploy to Kubernetes, ECS, Cloud Run, or any host that runs containers, and want one immutable image per release.

Static export (output: 'export')

Limited: no server features at runtime.

The site is fully known at build time and can be served from S3, NGINX, GitHub Pages or a CDN.

Adapter (a platform integration)

Varies. "Verified" adapters run the Next.js compatibility test suite.

You deploy to a platform that has its own build and runtime model (Vercel, and others).

The platform requirement behind the first two rows is small. The "Deploying to Platforms" guide states that to run Next.js a platform needs a Node.js server and nothing else: a single next start process handles Server Components, ISR, PPR, Cache Components, Server Actions, Proxy and after(). The only extra dependency is the sharp package for image optimization. Everything else — a CDN, edge compute, a shared cache — improves performance or multi-instance consistency but is not needed for correctness. The guide separates functional fidelity (every feature works) from performance fidelity (each feature at its best latency); a platform that reaches the first is a fully supported target.

A Node.js Server

The smallest deployment is the one the scaffold already has. Make sure package.json has the build and start scripts, build once, and start.

package.json scripts (as created by create-next-app)
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start"
  }
}
Build, then start on a chosen port (the previous caching model)
npm run build
PORT=3901 HOSTNAME=127.0.0.1 npx next start

Run on the scratch Bookshelf, this printed Next.js 16.3.8, Local: http://127.0.0.1:3901 and Ready, and curl returned the catalogue pages and the Route Handler JSON. next start takes -p/--port (the PORT variable is read too) and -H/--hostname (default 0.0.0.0). When the server sits behind a load balancer such as an AWS ALB, pass --keepAliveTimeout (milliseconds) with a value larger than the balancer’s idle timeout, otherwise Node.js may close a connection the balancer is about to reuse and the balancer reports a proxy error.

Source: Deploying: Node.js server and the next CLI reference.

Two things to keep in mind. First, next build bakes in everything that is not read at request time (see the build-versus-runtime discussion in the configuration page), so build in the same environment type you will run in. Second, next start serves a build; it never rebuilds. A new release is a new build, a new process, and (with several instances) a rollout plan, which is the version-skew section below.

Docker and output: 'standalone'

next start needs the project’s full node_modules, which is mostly build tooling. Setting output: 'standalone' changes that: during next build, Next.js uses @vercel/nft to trace which files each route and the server itself need, and copies only those, including the necessary part of node_modules, into .next/standalone. That folder runs on its own, without npm install, with a minimal server.js that replaces next start.

next.config.ts for a self-hosted deployment (standalone, deploymentId, cache handler, streaming header)
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  // A self-contained server in .next/standalone (Docker, VMs, any Node.js host)
  output: "standalone",

  // One identifier per release; every instance of that release must share it
  deploymentId: process.env.DEPLOYMENT_VERSION,

  // Share the ISR / route cache between instances (see cache-handler.js) and
  // switch the per-instance in-memory copy off
  cacheHandler: require.resolve("./cache-handler.js"),
  cacheMaxMemorySize: 0,

  // Tell NGINX not to buffer streamed responses
  async headers() {
    return [
      {
        source: "/:path*{/}?",
        headers: [{ key: "X-Accel-Buffering", value: "no" }],
      },
    ];
  },
};

export default nextConfig;

This one file is the thread of the page: each key is explained in its own section below. Built with DEPLOYMENT_VERSION=2026-10-03-a, it produced .next/standalone with server.js, package.json, a traced node_modules and the cache handler file. On the scratch app that folder was 42 MB, against 469 MB for the project’s full node_modules. The standalone folder does not contain public/ or .next/static; the docs say these should ideally be served by a CDN, but if you want the minimal server to serve them, copy them in after the build.

Build, add the static folders, and start the minimal server

Choices in that file worth understanding rather than copying:

  • Multi-stage. The dependencies stage is cached as long as package.json and the lockfile do not change, so a code change rebuilds only the builder and runner stages.

  • Non-root. The final stage drops to node; the mkdir .next && chown line gives that user a writable folder for the prerender cache, since the rest of /app is owned by root.

  • A slim image. The official example uses a -slim Node.js image. On glibc-based Linux the self-hosting guide notes that image optimization may need extra configuration to prevent excessive memory usage (a different memory allocator, see the sharp installation notes).

  • Build-time versus runtime variables. NEXT_PUBLIC_ values are inlined into the client bundle during next build, so they must be available (as build arguments) at that stage. Server-side values read inside a request-time context (after await connection() or another Request-time API) are evaluated at runtime, so a single image can be promoted from staging to production with different values.

  • Telemetry. Next.js collects anonymous telemetry; set NEXT_TELEMETRY_DISABLED=1 in the stage where you want it off.

  • Development. The Deploying page recommends npm run dev locally rather than Docker on macOS and Windows, for better performance.

The Adapters API

Adapters give platforms a public, documented hook into the build. They were introduced as an alpha in Next.js 16.0 (configured under experimental.adapterPath) and declared stable in Next.js 16.2 (released 2026-03-18), where the option moved to the top level as adapterPath. The documentation is explicit that there are no private framework hooks: Vercel’s own adapter uses the same public API as everyone else.

An adapter is a module that exports an object implementing the NextAdapter interface, which can be imported as a type from next. It has a name and two optional hooks: modifyConfig(config, context), called for any CLI command that loads the configuration, and onBuildComplete(context), called after the build with the routing tables and every build output. The configuration key takes the path to the module, and the NEXT_ADAPTER_PATH environment variable can be set instead for zero-configuration use on a platform.

my-adapter.js: a report-only adapter
/** @type {import('next').NextAdapter} */
const adapter = {
  name: "bookshelf-report-adapter",

  async onBuildComplete({ outputs, routing, buildId, nextVersion }) {
    console.log(`[adapter] Next.js ${nextVersion}, build ${buildId}`);
    console.log(`[adapter] app pages: ${outputs.appPages.length}`);
    console.log(`[adapter] app routes: ${outputs.appRoutes.length}`);
    console.log(`[adapter] prerenders: ${outputs.prerenders.length}`);
    console.log(`[adapter] static files: ${outputs.staticFiles.length}`);
    console.log(`[adapter] dynamic routes: ${routing.dynamicRoutes.length}`);
    for (const route of outputs.appRoutes) {
      console.log(`[adapter] route ${route.pathname} -> ${route.type}`);
    }
  },
};

module.exports = adapter;
Registering it in next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  adapterPath: require.resolve("./my-adapter.js"),
};

export default nextConfig;

A real adapter reads outputs (the appPages, appRoutes, pages, pagesApi, prerenders and staticFiles lists, plus an optional middleware entry) and routing (the phases: beforeMiddleware, middlewareMatchers, beforeFiles, afterFiles, dynamicRoutes, onMatch, fallback) and produces the platform’s deployment format. The reference documentation has dedicated pages for the output types, the routing information, invoking entrypoints, runtime integration with cache handlers, implementing PPR in an adapter, the @next/routing package, and a compatibility test harness for testing adapters.

Cache handlers for several instances

By default the Next.js server cache — the cache behind ISR, the Full Route Cache and the patched fetch — lives in memory (50 MB by default) and on the local disk of each instance. One long-lived instance with a persistent disk needs nothing more. With several pods, ephemeral compute, or a CDN in front, each copy diverges: a revalidation reaches only the instance that received it. The fix has two parts: a shared store, and coordination of tags.

cacheHandler (singular, stable since 14.1) points to a module whose class implements get, set, revalidateTag and resetRequestCache; cacheMaxMemorySize: 0 switches the per-instance memory copy off. The handler in this page’s configuration stores entries in a Map, which is only a proof that Next.js calls it; in production the entries belong in durable shared storage such as Redis or S3 (the Next.js repository has a Redis example).

cache-handler.js: a logging, in-process handler (replace the Map with shared storage in production)
const cache = new Map();

module.exports = class CacheHandler {
  constructor(options) {
    this.options = options;
  }

  async get(key) {
    const entry = cache.get(key);
    console.log(`[cache-handler] get ${key} -> ${entry ? "hit" : "miss"}`);
    return entry;
  }

  async set(key, data, ctx) {
    console.log(`[cache-handler] set ${key}`);
    cache.set(key, { value: data, lastModified: Date.now(), tags: ctx.tags });
  }

  async revalidateTag(tags) {
    const list = [tags].flat();
    for (const [key, entry] of cache) {
      if (entry.tags?.some((tag) => list.includes(tag))) cache.delete(key);
    }
  }

  resetRequestCache() {}
};

With this handler configured, the first request for the prerendered /en/books/2 logged get /route-cache/APP_PAGE/…​/en/books/2 → miss and then set with the same key, the response carried x-nextjs-cache: MISS and Cache-Control: s-maxage=31536000, and the next two requests logged → hit. Two lessons: the key space is Next.js’s own (/route-cache/APP_PAGE/…​), and a handler replaces the default store, so a fresh instance whose handler is empty regenerates the page on its first request, where a durable shared store keeps entries across restarts and across instances.

Calling revalidateTag() on one instance invalidates only that instance’s cache unless the handler coordinates. For App Router deployments with several instances, the guide asks you to implement refreshTags() in the handler (the cacheHandlers interface), which Next.js calls before each request so that the instance syncs tag state from the shared storage. revalidatePath is a convenience layer on top of tags. Build ID, deploymentId and version skew

Every build gets an identifier, and "the same build should be used and boot up multiple containers". If you rebuild per environment, make the ID reproducible with generateBuildId (for example the git hash); the self-hosting guide shows it returning an environment variable. Setting deploymentId replaces this: Next.js then uses a constant build ID and generateBuildId has no effect.

Version skew is what happens during a rolling deployment when a browser holding release A talks to a server running release B: JavaScript or CSS files that no longer exist, a Server Function identifier from the old build that the new server does not recognise, or prefetched navigation data in an incompatible shape. Configure deploymentId (or the NEXT_DEPLOYMENT_ID environment variable; if both are set the config value wins) and Next.js detects the mismatch and falls back to a full page reload instead of a broken client-side navigation.

Built with DEPLOYMENT_VERSION=2026-10-03-a, the Bookshelf’s HTML contained <html data-dpl-id="2026-10-03-a" …​>, every asset URL (scripts, stylesheet, fonts, the favicon) carried ?dpl=2026-10-03-a, and a request that sent the headers RSC: 1 and x-deployment-id: 2026-10-03-a came back with x-nextjs-deployment-id: 2026-10-03-a. The documented mechanism is: ?dpl= on static assets, an x-deployment-id request header on client navigations, an x-nextjs-deployment-id response header, the data-dpl-id attribute, and the deployment ID as part of the 'use cache' cache key, so a new deployment starts with clean 'use cache' entries.

Two honesty points from the reference page. Next.js does not read ?dpl= on incoming requests: the parameter busts caches, it does not route. A per-deployment value only avoids skew if requests are also routed by deployment (by your host or CDN); otherwise clients that reach an instance of another deployment during a rollout will reload rather than navigate. And a reload loses component state, so URL state and local storage persist but useState does not.

A related variable concerns Server Actions. Next.js encrypts the closed-over variables of a Server Function before sending them to the client, with a key generated per build. With several instances built separately, or an image built once but started many times, every instance must decrypt what any other encrypted, otherwise users see "Failed to find Server Action" errors. Set NEXT_SERVER_ACTIONS_ENCRYPTION_KEY at build time to a base64 value of 16, 24 or 32 bytes.

Build with a stable Server Functions key and deployment ID (the key is generated, never written down)
export NEXT_SERVER_ACTIONS_ENCRYPTION_KEY="$(openssl rand -base64 32)"
DEPLOYMENT_VERSION="$(git rev-parse --short HEAD)" npx next build

The build above succeeded. The key is embedded in the build output, so store the generated value in your secret manager and reuse it for every build of the same release line, rather than generating a fresh one per instance.

Streaming behind NGINX

The App Router streams responses (Suspense boundaries, loading.js, PPR). A proxy that buffers the whole upstream response before forwarding it defeats that: the user sees nothing until the slowest boundary resolves. NGINX honours the X-Accel-Buffering response header, so the self-hosting guide has Next.js send X-Accel-Buffering: no, which the headers() entry in the configuration above does. Querying the standalone server confirmed that the header is present (X-Accel-Buffering: no in the response to /en/books/2).

An NGINX server block for a Next.js upstream (not executed: no NGINX was available)
upstream nextjs_upstream {
  server 127.0.0.1:3000;
  keepalive 32;
}

server {
  listen 80;
  server_name books.example;

  location / {
    proxy_pass http://nextjs_upstream;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    # Streaming: Next.js sends X-Accel-Buffering: no; do not override it here
  }
}

The whole path must stream, not only NGINX: load balancers need chunked transfer encoding or HTTP/2 streaming (some cloud balancers, for example an AWS ALB in front of a Lambda integration, buffer by default), reverse proxies between the balancer and Next.js must not buffer, and with PPR streaming is required for the static shell to keep its time-to-first-byte advantage. See Streaming and Suspense for what is being streamed.

ISR, PPR and the CDN

ISR and revalidation use the same server cache as everything above, so a single next start instance supports ISR without more, and a multi-instance setup needs the shared handler and tag coordination. Cache Components (and with them PPR) "work by default" with next start and Docker; they are not a CDN-only feature. Static assets with hashed file names get Cache-Control: public, max-age=31536000, immutable, which cannot be overridden; ISR pages get s-maxage=<revalidate>, stale-while-revalidate; dynamically rendered pages get private, no-cache, no-store, max-age=0, must-revalidate. A CDN in front must respect these and the cache-key variability, or it will serve stale or mismatched variants during client navigation. To serve assets from another host, use assetPrefix. For the CDN details, Partial Prerendering support per platform, and revalidation internals, the documentation has dedicated guides on CDN caching, the PPR platform guide and how revalidation works; the pages Partial Prerendering and Cache Components and Incremental Static Regeneration explain the features themselves.

Proxy, environment variables and shutdown

Proxy (proxy.ts) works with no configuration under next start; it needs the incoming request, so it is unavailable in a static export. If you need all Node.js APIs it is documented as possible to move the logic into a layout or use redirects and rewrites in the config; Redirects, Rewrites and Proxy has the details. Environment variables are server-only by default; only NEXT_PUBLIC_ values reach the browser, inlined at build, and a server value read after a Request-time API such as connection() is evaluated at runtime. Startup code can use the register function of instrumentation.ts (Debugging, Instrumentation and Observability).

after() is fully supported under next start. When the platform stops the server it must send SIGINT or SIGTERM and wait: Next.js finishes in-flight requests and runs pending after() callbacks before exiting, and the guide recommends a drain period of 10 to 30 seconds. In Kubernetes this means terminationGracePeriodSeconds at least that long (see Health Probes and Lifecycle). On the scratch app, SIGTERM to the custom server below made the process exit; the standalone server.js also stopped on the default kill.

Multi-Zones

Multi-Zones are the documented micro-frontend approach: one domain, several independent Next.js applications ("zones"), each serving a set of paths and each built and deployed on its own. Use them when parts of a site are unrelated enough to deserve separate build times and release cycles — /blog/, /dashboard/ and "everything else", for example. Navigation inside a zone is a soft navigation; navigation across zones is a hard navigation that unloads the page, so pages that are visited together belong in the same zone.

A zone is a normal Next.js app with an assetPrefix so that its /_next/…​ assets do not collide with another zone’s: they are served under /<assetPrefix>/_next/…​. In versions older than Next.js 15 an extra rewrite was needed for those assets; since 15 it is not. Requests are then routed to the right zone by any HTTP proxy, or by the rewrites of one Next.js application (recommended for latency), or by Proxy when the decision is dynamic (for example a feature flag during a migration).

next.config.ts of the zone that owns /books (assets under /books-static) and a rewrite to another zone
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  assetPrefix: "/books-static",
  async rewrites() {
    return [
      {
        source: "/api/blog",
        destination: `${process.env.BLOG_DOMAIN}/api/books`,
      },
    ];
  },
};

export default nextConfig;

The rewrite uses a stand-in path because only one port was available for the test: the second "zone" was the same server. A real router rewrites the zone’s paths (/blog, /blog/:path+) and its asset prefix (/blog-static/:path+) to the zone’s own domain. Built with BLOG_DOMAIN=http://127.0.0.1:3901 and started with next start, curl /api/blog returned the JSON of the target route; the HTML of /en/books/1 referenced /books-static/_next/static/chunks/…​js, and one of those URLs returned HTTP 200. Three rules from the guide: URL paths must be unique to a zone (two zones serving /blog conflict); links to another zone must be plain <a> tags, not <Link>, because <Link> prefetches and soft-navigates; and Server Actions need serverActions.allowedOrigins set to the user-facing domain, because that domain serves several applications.

Source: Multi-Zones and assetPrefix. For rewrites see Redirects, Rewrites and Proxy.

Custom Servers

next start is the default server. A custom server starts the Next.js request handler from your own code, which you should do "only when the integrated router can’t meet your app requirements". Having an existing backend is not a reason by itself: you can keep it and run it next to Next.js (the Backend-for-Frontend page, Route Handlers and Backend for Frontend, shows how).

server.mjs: a custom server using only node:http
import { createServer } from "node:http";
import next from "next";

const port = Number.parseInt(process.env.PORT ?? "3000", 10);
const dev = process.env.NODE_ENV !== "production";
const app = next({ dev });
const handle = app.getRequestHandler();

await app.prepare();

const server = createServer((req, res) => {
  // Headers you own must be set BEFORE handing the request to Next.js
  res.setHeader("X-Served-By", "custom-server");
  handle(req, res);
});

server.listen(port, () => {
  console.log(`> Listening on http://localhost:${port} (${dev ? "development" : "production"})`);
});

// Next.js finishes in-flight requests and after() callbacks on these signals;
// close the HTTP server too so the process can exit.
for (const signal of ["SIGINT", "SIGTERM"]) {
  process.on(signal, () => server.close(() => process.exit(0)));
}
Change the scripts and run it
{
  "scripts": {
    "dev": "node server.mjs",
    "build": "next build",
    "start": "NODE_ENV=production node server.mjs"
  }
}

After next build, NODE_ENV=production PORT=3901 node server.mjs printed > Listening on http://localhost:3901 (production); curl -i /api/books?q=dune returned HTTP 200 with the X-Served-By: custom-server header and the JSON for Dune; a request with accept-language: es to / got the Proxy redirect to /es/ (HTTP 307); and SIGTERM ended the process. The next() function accepts conf, dev, dir, quiet, hostname, port, httpServer, turbopack (on by default) and webpack.

The caveats are the substance of this section:

  • Headers must be set before handle. Next.js begins sending the response inside handle(req, res), so by the time its promise resolves res.headersSent is already true and a later res.setHeader() is silently discarded. The docs say the same ordering applies when Next.js is wrapped in another framework: res in Express, reply.raw in Fastify. Express and Fastify were not installed in the scratch app; the example above uses only node:http, which is the form the official page shows, and the Express and Fastify points are the documentation’s.

  • Not combinable with standalone. In standalone mode the build does not trace custom server files; it outputs its own minimal server.js instead, and the two cannot be used together. A custom server therefore needs the full node_modules in its image.

  • Not compiled. The server file does not go through the Next.js Compiler or bundler, so its syntax must be valid for the Node.js version you run.

CI Build Caching

next build writes a cache to .next/cache that later builds reuse. In CI the workspace is usually fresh, so the cache is gone unless you persist it; without it you may see the "No Cache Detected" error. The guide lists configurations for many providers (CircleCI, Travis CI, GitLab CI, Netlify, AWS CodeBuild, GitHub Actions, Bitbucket Pipelines, Heroku, Azure Pipelines and Jenkins); on Vercel it is automatic.

To measure the effect, the scratch app was built twice in a row, the second time with only .next/cache kept from the first. The Turbopack compile step dropped from 1975 ms to 160 ms, and the wall-clock time of next build from 5.06 s to 3.00 s. On a small app that is seconds; on a large application it is the difference between minutes and tens of seconds.

A GitHub Actions workflow that restores node_modules cache and .next/cache (not run: it needs a GitHub runner)
name: build
on: [push]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: npm

      - name: Cache the Next.js build cache
        uses: actions/cache@v4
        with:
          path: ${{ github.workspace }}/.next/cache
          # A new cache whenever packages or source files change.
          key: ${{ runner.os }}-nextjs-${{ hashFiles('**/package-lock.json') }}-${{ hashFiles('**/*.js', '**/*.jsx', '**/*.ts', '**/*.tsx') }}
          # If only the sources changed, start from the last cache for these packages.
          restore-keys: |
            ${{ runner.os }}-nextjs-${{ hashFiles('**/package-lock.json') }}-

      - run: npm ci
      - run: npm run build

For Docker builds, the official example notes that a BuildKit cache mount on /app/.next/cache speeds up rebuilds but keeps .next/cache/fetch-cache out of the final image, so build-time fetch responses are not available at runtime; copy the cache folder into the image if you want them. See Build Cache and Multi-Stage Builds and CI/CD with GitHub Actions.
