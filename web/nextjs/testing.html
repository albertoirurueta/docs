Testing

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when the facts and examples below were checked; the official documentation reports @doc-version 16.3.8), React 19.3.0, Node.js 20.9.0 or later and TypeScript 5.1 or later. It covers the App Router and the Pages Router: the unit-test set-up is identical for both, and a short section shows what changes for getServerSideProps and pages/api. Caching only matters in one place, the instant() helper of Playwright, which exists only for the opt-in Cache Components model (cacheComponents: true); every other example is independent of the caching model, and the end-to-end tests of the Bookshelf were run against both a build of the previous model and a Cache Components build. Every example was built and run with Next.js 16.3.8, Node.js 24.16 and npm 11.13 on macOS, in a scratch copy of the Bookshelf (the catalogue of books and reviews that this section grows), against Vitest 5.0.3, Jest 30.5.2, React Testing Library 16.3.3, MSW 3.0.2, Playwright 1.63.0 and @next/playwright 16.3.8. Cypress is the one exception, explained in its own section. Each example is followed by the official page it derives from.

Next.js ships no test runner. The official documentation lists four tools — Cypress, Playwright, Vitest and Jest — and gives one set-up guide for each; this page walks through those guides, runs them against real Bookshelf code, and records what the guides do not tell you: which kinds of code each tool can reach, why server-only and next/navigation break a unit test, how an async Server Component can and cannot be tested, and why a mock library running in the test process cannot intercept what the Next.js server fetches. The testing fundamentals themselves (the test pyramid, Testing Library queries, user-event, act, MSW handlers, testing hooks) are not repeated; they are on React Testing. The browser-automation tools in depth (Selenium, Playwright and Cypress architecture, evidence capture, CI) are on E2E Testing in the Browser. The sibling pages of this section on authentication and on debugging and observability cover how to test signed-in flows and how to debug a failing test with the Node inspector.

What to Test, and With What

The official overview names five kinds of test — unit, component, integration, end-to-end and snapshot — and one constraint that shapes everything on this page: because async Server Components are new to the React ecosystem, some tools do not fully support them, so the documentation recommends end-to-end tests over unit tests for async components. The Vitest, Jest and Cypress guides each repeat the warning.

export function formatPrice(cents: number, locale = "en-US", currency = "EUR"): string {

      </h2>

}

Vitest

Vitest is a Vite-powered runner with a Jest-compatible API and native TypeScript and ESM support, which makes it the lowest-friction choice for a new Next.js project. Install it with the React plugin, jsdom and Testing Library:

Installing Vitest and Testing Library
npm install -D vitest @vitejs/plugin-react jsdom @testing-library/react @testing-library/dom \
  @testing-library/user-event @testing-library/jest-dom

Create vitest.config.mts (the .mts extension makes the file an ES module regardless of the "type" in package.json). The official page uses the vite-tsconfig-paths plugin to resolve the @/* alias. Vitest 5 runs on Vite 8, which resolves tsconfig.json paths itself, and prints a message asking you to drop the plugin; the config below uses the built-in option and was run as written.

vitest.config.mts
import { defineConfig } from "vitest/config";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  resolve: { tsconfigPaths: true },
  test: {
    environment: "jsdom",
    include: ["__tests__/vitest/**/*.test.{ts,tsx}"],
    setupFiles: ["./vitest.setup.ts"],
  },
});
vitest.setup.ts
import "@testing-library/jest-dom/vitest";
import { afterEach, vi } from "vitest";
import { cleanup } from "@testing-library/react";

// "server-only" throws when imported outside a React Server environment; neutralise it in unit tests.
vi.mock("server-only", () => ({}));

afterEach(() => cleanup());

Two lines of the set-up deserve a comment. @testing-library/jest-dom/vitest registers the DOM matchers (toBeInTheDocument, toHaveAttribute) on Vitest’s expect. And the vi.mock("server-only") line is not in the official guide but is needed as soon as a test imports a module marked with import "server-only", such as the Bookshelf’s lib/books.ts: the package throws on purpose when it is loaded outside a Server Component environment. Without the mock, the import fails with This module cannot be imported from a Client Component module. It should only be used from a Server Component.

Add the script and run the suite once (vitest without run stays in watch mode, which is the official default):

package.json scripts
{
  "scripts": {
    "test": "vitest run",
    "test:jest": "jest",
    "test:e2e": "playwright test"
  }
}

Jest with next/jest

Jest needs a transform to understand TypeScript and JSX. next/jest provides it: it configures Jest with the Next.js compiler (SWC), so no .babelrc is needed. The official page lists what the helper sets up for you:

  • a transform that uses the Next.js Compiler

  • automatic mocks for stylesheets (.css, .module.css and their Sass variants), image imports and next/font

  • loading of .env files (and their variants) into process.env

  • ignoring node_modules and .next for module resolution, and node_modules for transforms

  • loading of next.config.js for the flags that enable SWC transforms

Install Jest and the Testing Library packages, then write the config with the helper:

Installing Jest
npm install -D jest jest-environment-jsdom @testing-library/react @testing-library/dom \
  @testing-library/jest-dom @testing-library/user-event ts-node @types/jest

ts-node is what lets Jest read a jest.config.ts. The config below is the official one, with testMatch pointing at this page’s folder and the ESM-only package handling that the MSW section explains.

jest.config.ts
import type { Config } from "jest";
import nextJest from "next/jest.js";

const createJestConfig = nextJest({
  // Path to the Next.js app: loads next.config.ts and .env files into the test environment
  dir: "./",
});

const config: Config = {
  coverageProvider: "v8",
  testEnvironment: "jsdom",
  testMatch: ["<rootDir>/__tests__/jest/**/*.test.{ts,tsx}"],
  setupFilesAfterEnv: ["<rootDir>/jest.setup.ts"],
};

// ESM-only packages (msw 3 and its dependencies) must be transformed by the Next.js compiler too.
// next/jest returns an async config function, so wrap it and adjust transformIgnorePatterns.
const esmOnly = ["msw", "@msw", "@mswjs", "rettime", "cookie", "until-async", "headers-polyfill", "@open-draft"];

export default async function jestConfig() {
  const resolved = await createJestConfig(config)();
  return {
    ...resolved,
    transformIgnorePatterns: [
      `/node_modules/(?!(${esmOnly.join("|")})/)`,
      "^.+\\.module\\.(css|sass|scss)$",
    ],
  };
}
jest.setup.ts
import "@testing-library/jest-dom";

// "server-only" throws outside a React Server environment.
jest.mock("server-only", () => ({}));

The official page tells you to map the @/* alias with moduleNameMapper. With paths declared in tsconfig.json, next/jest 16.3.8 resolved the alias without it in this project, so the mapper is omitted above; add it if your aliases are not in tsconfig.json or jsconfig.json. Testing Components: Client, Synchronous Server and async Server

A Client Component is a normal React component that Testing Library renders in jsdom. What breaks the test is not React but the framework APIs it calls. A component that uses useRouter or useSearchParams from next/navigation throws invariant expected app router to be mounted when rendered outside the App Router. Mock the module and assert on the mock:

components/search-box.tsx and its test
// components/search-box.tsx
"use client";

import { useRouter, useSearchParams } from "next/navigation";

export function SearchBox() {
  const router = useRouter();
  const params = useSearchParams();
  return (
    <form
      onSubmit={(e) => {
        e.preventDefault();
        const q = new FormData(e.currentTarget).get("q");
        router.push(`/en?q=${encodeURIComponent(String(q))}`);
      }}
    >
      <input name="q" aria-label="Search" defaultValue={params?.get("q") ?? ""} />
      <button>Go</button>
    </form>
  );
}

// __tests__/vitest/search-box.test.tsx
import { expect, test, vi } from "vitest";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { SearchBox } from "@/components/search-box";

const push = vi.fn();
vi.mock("next/navigation", () => ({
  useRouter: () => ({ push }),
  useSearchParams: () => new URLSearchParams("q=dune"),
}));

test("SearchBox pushes the encoded query to the router", async () => {
  const user = userEvent.setup();
  render(<SearchBox />);
  const input = screen.getByRole("textbox", { name: "Search" });
  expect(input).toHaveValue("dune");
  await user.clear(input);
  await user.type(input, "war & peace");
  await user.click(screen.getByRole("button", { name: "Go" }));
  expect(push).toHaveBeenCalledWith("/en?q=war%20%26%20peace");
});

The params?.get with a question mark is not decoration: useSearchParams is typed as possibly null, because the same hook also serves Pages Router components. The Pages Router counterpart, useRouter from next/router, fails without a mock with NextRouter was not mounted.

A synchronous Server Component (no async, no cookies(), no await) is just a function that returns elements, so it renders in jsdom like any component: BookCard above is one. What you cannot do in a unit test is rely on the server-only machinery around it: import "server-only" modules need the mock shown earlier, and request APIs fail outside a request. In Vitest, calling cookies() from next/headers throws cookies was called outside a request scope (with a pointer to the next-dynamic-api-wrong-context message) and revalidatePath throws Invariant: static generation store missing. Both are the cue to move that code behind a function you can mock, or to test it end to end.

The Limits for async Server Components

The Bookshelf’s BookDetail is an async Server Component: it awaits the data layer and renders a Client Component (the review form). The official position is that Vitest, Jest and Cypress component tests do not support such components and that an end-to-end test should cover them. Two tests show exactly what that means.

tests/vitest/async-component.test.tsx
import { expect, test, vi } from "vitest";
import { render, screen } from "@testing-library/react";
import { BookDetail } from "@/app/[locale]/books/[id]/book-detail";

// The Client Component child talks to a Server Action: replace it, we only test the page here.
vi.mock("@/app/[locale]/actions", () => ({ submitReview: vi.fn() }));

test("async Server Component: call it as a function, then render the result", async () => {
  const ui = await BookDetail({ id: "1", label: "Send" }); // resolves to plain React elements
  render(ui);
  expect(screen.getByRole("heading", { level: 1, name: "Dune" })).toBeInTheDocument();
  expect(screen.getByRole("button", { name: "Send" })).toBeInTheDocument();
});

test("rendering the async function directly renders nothing (jsdom is a client environment)", () => {
  const messages: string[] = [];
  vi.spyOn(console, "error").mockImplementation((...args) => {
    messages.push(String(args[0]));
  });
  const { container } = render(<BookDetail id="1" label="Send" />);
  expect(container.innerHTML).toBe("");
  expect(messages.some((m) => m.includes("is an async Client Component"))).toBe(true);
  vi.restoreAllMocks();
});

  • Rendering the component directly fails. render(<BookDetail />) produces an empty container, and React logs that the component "is an async Client Component. Only Server Components can be async at the moment", followed by a warning that it suspended inside an act scope. jsdom plus Testing Library is a client renderer; it has no server renderer to resolve the promise.

  • Calling the component as a function works for a leaf. await BookDetail({ …​ }) returns the element tree, and rendering that tree is an ordinary component test. The Client Component child is rendered as a client component; its Server Action import has to be mocked, as above.

  • The workaround stops where the tree stops being plain. It resolves only the outermost component. A child that is itself async is still a promise-returning function in the tree and renders nothing; a page that awaits params or reads cookies() or headers() needs a request scope that a unit test does not have; Suspense boundaries and streaming are not exercised at all. For anything beyond a leaf, write the end-to-end test.

The rule of thumb: extract the logic of an async component into a plain function or into the data layer and unit-test that; keep the component thin, and cover it with a browser test. The same split is what makes the component easy to move between caching models, because neither 'use cache' nor <Suspense> placement shows up in the unit test.

Testing Server Actions

A Server Action is an async function in a module with "use server". In a unit test the directive is inert: you import the function and call it. What you must replace are the framework and session dependencies. The Bookshelf’s submitReview checks the session, validates the input with Zod, stores the review and revalidates the page, so the test mocks auth and revalidatePath and drives it with a FormData:

tests/vitest/server-action.test.ts
import { beforeEach, describe, expect, test, vi } from "vitest";

const auth = vi.fn();
vi.mock("@/auth", () => ({ auth: () => auth() }));
vi.mock("next/cache", () => ({ revalidatePath: vi.fn() }));

import { revalidatePath } from "next/cache";
import { submitReview } from "@/app/[locale]/actions";
import { listReviews } from "@/lib/books";

function form(fields: Record<string, string>) {
  const fd = new FormData();
  for (const [k, v] of Object.entries(fields)) fd.set(k, v);
  return fd;
}

describe("submitReview", () => {
  beforeEach(() => vi.clearAllMocks());

  test("rejects anonymous callers", async () => {
    auth.mockResolvedValue(null);
    const res = await submitReview({ ok: false }, form({ bookId: "1", rating: "5", text: "Great" }));
    expect(res).toEqual({ ok: false, error: "Sign in required" });
    expect(revalidatePath).not.toHaveBeenCalled();
  });

  test("validates input on the server", async () => {
    auth.mockResolvedValue({ user: { name: "Test User" } });
    const res = await submitReview({ ok: false }, form({ bookId: "1", rating: "9", text: "Too high" }));
    expect(res).toEqual({ ok: false, error: "Invalid input" });
  });

  test("stores the review and revalidates the page", async () => {
    auth.mockResolvedValue({ user: { name: "Test User" } });
    const res = await submitReview({ ok: false }, form({ bookId: "2", rating: "4", text: "Cyberpunk classic" }));
    expect(res).toEqual({ ok: true });
    expect(revalidatePath).toHaveBeenCalledWith("/[locale]/books/[id]", "page");
    expect((await listReviews("2")).map((r) => r.text)).toEqual(["Cyberpunk classic"]);
  });
});

Notes on the shape of the test:

  • The first test is the one that matters for security: an action is a public HTTP endpoint, so the negative cases (no session, invalid input, and in a real application the wrong owner) deserve as much attention as the happy path. The rule is explained on Server Actions and Mutations.

  • vi.mock calls are hoisted above the imports by Vitest; the auth function is defined before them only because the mock factory refers to it lazily.

  • A unit test proves the logic, not the wire format. An action posted by a real form travels as a multipart/form-data request with an action ID. The end-to-end test below submits the real form in a browser as an anonymous visitor and asserts on the visible error, which exercises the compiled action, the form binding and useActionState together. Signed-in flows (a session cookie in the browser context, saved with Playwright’s storage state) are covered on the authentication page of this section.

Testing the Proxy

Mocking the Network with MSW

Mock Service Worker intercepts requests at the network level, so the code under test keeps calling fetch and nothing in it is replaced. lib/ratings.ts calls a third-party ratings service (the base URL comes from configuration, not from user input), and the tests answer for the service:

lib/ratings.ts
export type Rating = { bookId: string; average: number; count: number };

// Calls a third-party service; the base URL comes from configuration, not from user input.
const BASE_URL = process.env.RATINGS_API_URL ?? "https://ratings.example.test";

export async function getRating(bookId: string): Promise<Rating | null> {
  const res = await fetch(`${BASE_URL}/api/ratings/${encodeURIComponent(bookId)}`);
  if (res.status === 404) return null;
  if (!res.ok) throw new Error(`ratings service failed: ${res.status}`);
  return (await res.json()) as Rating;
}
tests/vitest/ratings-msw.test.ts
import { afterAll, afterEach, beforeAll, expect, test } from "vitest";
import { http, HttpResponse } from "msw";
import { setupServer } from "msw/node";
import { getRating } from "@/lib/ratings";

const server = setupServer(
  http.get("https://ratings.example.test/api/ratings/:id", ({ params }) =>
    params.id === "1"
      ? HttpResponse.json({ bookId: "1", average: 4.5, count: 12 })
      : new HttpResponse(null, { status: 404 }),
  ),
);

beforeAll(() => server.listen({ onUnhandledFrame: "error" }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

test("returns the rating from the third-party service", async () => {
  expect(await getRating("1")).toEqual({ bookId: "1", average: 4.5, count: 12 });
});

test("returns null on 404", async () => {
  expect(await getRating("99")).toBeNull();
});

test("throws on a server error (per-test override)", async () => {
  server.use(http.get("https://ratings.example.test/api/ratings/:id", () => new HttpResponse(null, { status: 500 })));
  await expect(getRating("1")).rejects.toThrow("ratings service failed: 500");
});

test("a request without a handler fails the test instead of reaching the network", async () => {
  await expect(fetch("https://unmocked.example.test/ping")).rejects.toThrow();
});

The last test shows the reason for onUnhandledFrame: "error": a request without a handler is reported as [MSW] Error: intercepted a request without a matching request handler and rejects, so a forgotten mock cannot silently hit the real service. MSW 3 renamed the option that MSW 2 called onUnhandledRequest, because it also covers WebSocket connections; "warn" is the default.

What MSW cannot intercept

setupServer patches the network APIs of the test process. In an end-to-end test the Next.js server is a separate process (next start), and the fetch in getRating runs there, so an MSW handler in the Playwright test file never sees it. For server-side calls in an end-to-end test, point the application at a stand-in service instead. The RATINGS_API_URL variable exists for this reason, and Playwright starts a tiny fake next to the app (see the Playwright section). The same holds for a browser: to mock what the browser requests, use Playwright’s own page.route, which works in the browser context.

Asserting Instant Navigations with instant()

Next.js 16.3 added Instant Navigations: with cacheComponents and partialPrefetching enabled, a navigation can render its static shell and cached content at once while the rest streams into <Suspense> fallbacks. Whether a route really behaves that way is easy to break with an innocent change (an uncached fetch above a boundary), and nothing else in the build will tell you. The @next/playwright package exports instant(page, callback, options?), which holds back dynamic content while the callback runs, so assertions see only what a user sees the instant the navigation happens. See Partial Prerendering and Cache Components for the model.

sequenceDiagram participant T as Test participant P as Browser page participant S as Next.js server T->>P: instant(page, callback) Note over P: dynamic content is held back, like Pause on navigations T->>P: page.goto or click a Link P->>S: request S-->>P: static shell and prefetched UI only T->>P: assertions see the instant UI T->>P: callback ends, hold released like Resume S-->>P: dynamic content streams in T->>P: assertions see the final UI

The route under test is a product page with a cached product name and a request-time inventory. generateStaticParams makes the slug known at build time (so the name can be in the shell), and connection() marks the inventory as request data, so it can only appear in a <Suspense> fallback:

app/[locale]/store/[slug]/page.tsx
import { Suspense } from "react";
import Link from "next/link";
import { connection } from "next/server";

export function generateStaticParams() {
  return ["en", "es"].flatMap((locale) => ["shoes", "hats"].map((slug) => ({ locale, slug })));
}

export default function ProductPage(props: PageProps<"/[locale]/store/[slug]">) {
  return (
    <main>
      <nav>
        <Link href="/en/store/shoes" prefetch>
          Shoes
        </Link>{" "}
        <Link href="/en/store/hats" prefetch>
          Hats
        </Link>
      </nav>
      <Suspense fallback={<p>Loading product...</p>}>
        <ProductInfo params={props.params} />
      </Suspense>
      <Suspense fallback={<p>Checking availability...</p>}>
        <Inventory params={props.params} />
      </Suspense>
    </main>
  );
}

type Params = PageProps<"/[locale]/store/[slug]">["params"];

const catalogue: Record<string, string> = { shoes: "Running Shoes", hats: "Baseball Cap" };

async function ProductInfo({ params }: { params: Params }) {
  const { slug } = await params;
  const name = await getProductName(slug);
  return <h1>{name}</h1>;
}

async function getProductName(slug: string) {
  "use cache";
  return catalogue[slug] ?? "Unknown product";
}

async function Inventory({ params }: { params: Params }) {
  await connection(); // request-time data: never part of the static shell
  const { slug } = await params;
  return <p>In stock: {slug.length * 7}</p>;
}

    await expect(page.getByText("In stock: 35")).toBeVisible();
    await page.waitForLoadState("networkidle"); // let the <Link> prefetches finish
    await instant(page, async () => {
      await page.click('a[href="/en/store/hats"]');
      await page.waitForURL((url) => url.pathname === "/en/store/hats");
      await expect(page.getByRole("heading", { name: "Baseball Cap" })).toBeVisible();
      await expect(page.getByText("Checking availability...")).toBeVisible();
    });
    await expect(page.getByText("In stock: 28")).toBeVisible();
  });
});

Two entry points, two tests, because a <Suspense> boundary can cover one and not the other: an initial page load shows the static shell from the document response, and a client navigation shows the destination’s prefetched UI. Pass Playwright’s baseURL to instant() when page.goto() is the first navigation, because the helper needs the origin before it requests the document. Inside a client-navigation callback, wait for the destination URL before asserting, or a selector shared with the source page can match the wrong one.

What this run taught beyond the official example:

  • It only has teeth when the flag is on. Built without exposeTestingApiInProductionBuild, the same tests run against next start and fail at Checking availability…​: nothing is held back, the inventory streams in, and the fallback is gone. A test that only asserts what should be present (the heading) would pass in both cases, so assert the fallback or the absence of the dynamic text.

  • The route has to be instant for the test to pass. With no generateStaticParams, the name depends on params that are unknown at build time, and the initial-load test fails because the heading is not in the shell. On the client navigation, links without prefetch kept the old page on screen for the whole assertion timeout (the URL had changed, the content had not); with prefetch on the links the new product name rendered at once. The Navigation Inspector and the instant-navigation insights of the dev overlay show the same thing interactively.

  • The previous page stays in the DOM, hidden. After the click, two <h1> elements existed. Role-based locators ignore hidden elements, so getByRole("heading", { name }) is stable where locator("h1") fails strict mode, and toHaveCount(0) on text of the old page fails for the same reason.

  • Wait for the prefetches. The client-navigation test waits for networkidle before opening the scope; clicking before the prefetch finishes tests a slower path.

  • Requires Cache Components. In a project without cacheComponents the route above does not even build (use cache needs the flag), and instant as a segment export is documented for Cache Components only. The dev-time validation of instant navigations is separate: with Cache Components, every Page and Default segment is validated in development (validationLevel: 'warning'), and a segment can opt out with export const instant = false.

  • The cookie is shared across ports. The testing mode uses a next-instant-navigation-testing cookie, and cookies are scoped to the host, not the port; two projects on localhost can interfere. Clear the cookie when switching projects.

Source: Ensuring instant navigations: prevent regressions with e2e tests, instant, Next.js 16.3

Cypress End-to-End and Component Tests

Cypress runs the tests inside the browser alongside the application and offers two modes: E2E testing against a running server and component testing that mounts one component without a server. The guide’s quick start is npx create-next-app@latest --example with-cypress; the manual one is npm install -D cypress, a cypress:open script and a first npm run cypress:open, which creates cypress.config and the cypress folder.

How this section was verified. Cypress needs its own binary, which npm install downloads into a cache on first use. The current release is Cypress 16.1.1, and its binary was not available in the environment used for this page; a download was not made. The only binary in the cache was 13.17.0, so the E2E spec below was run with cypress@13.17.0 against the production build and passed, while the component spec could not be run: cypress run --component with Cypress 13.17.0 and Next.js 16.3.8 stops with TypeError: webpackModule.init is not a function from the Next.js dev-server handler of Cypress. The current Cypress documentation lists Next.js 15 and 16 as supported for component testing, so the component spec and the support file below follow the official Next.js and Cypress pages and have not been executed here.

The same limits apply as for Vitest: Cypress does not support component testing of async Server Components, and since component tests need no Next.js server, features that rely on one (such as <Image />) may not work out of the box. Cypress’s own documentation adds that a page whose props come from getServerSideProps or getStaticProps cannot get them in a component test, and recommends E2E tests for pages and component tests for individual components.

One problem did show up and is independent of the Cypress version: the project’s tsconfig.json includes every .ts file, and next build type-checks them all. With the Cypress types in the program, the global expect is Chai’s, which collides with the global expect that @types/jest declares, and the build fails with errors such as Property 'toBeInTheDocument' does not exist on type 'Assertion' in the Jest tests (and Property 'mount' does not exist in the component spec until the support file declares it). The usual layout avoids it: a cypress/tsconfig.json that loads the Cypress types, and an exclude of the Cypress files in the root config.

The Pages Router

Everything above except the App Router specifics applies unchanged: the same runners, the same next/jest helper, the same Playwright and Cypress configs. The official testing section has a separate Pages Router edition with the same four guides. What differs is the code under test, and it is simpler: getServerSideProps and getStaticProps are plain async functions, and a pages/api route is a function of a request and a response object.

pages/legacy.tsx, pages/api/ping.ts and their test
// pages/legacy.tsx
import type { GetServerSideProps } from "next";

type Props = { greeting: string };

export const getServerSideProps: GetServerSideProps<Props> = async ({ query }) => ({
  props: { greeting: `Hello ${String(query.name ?? "reader")}` },
});

export default function Legacy({ greeting }: Props) {
  return <h1>{greeting}</h1>;
}

// pages/api/ping.ts
import type { NextApiRequest, NextApiResponse } from "next";

export default function handler(req: NextApiRequest, res: NextApiResponse) {
  if (req.method !== "GET") {
    res.setHeader("Allow", "GET");
    return res.status(405).json({ error: "Method Not Allowed" });
  }
  return res.status(200).json({ pong: String(req.query.name ?? "world") });
}

// __tests__/vitest/pages-router.test.tsx
import { expect, test, vi } from "vitest";
import { render, screen } from "@testing-library/react";
import type { GetServerSidePropsContext, NextApiRequest, NextApiResponse } from "next";
import Legacy, { getServerSideProps } from "@/pages/legacy";
import handler from "@/pages/api/ping";

test("getServerSideProps is a plain async function", async () => {
  const result = await getServerSideProps({ query: { name: "Ada" } } as unknown as GetServerSidePropsContext);
  expect(result).toEqual({ props: { greeting: "Hello Ada" } });
  render(<Legacy greeting="Hello Ada" />);
  expect(screen.getByRole("heading", { name: "Hello Ada" })).toBeInTheDocument();
});

test("a Pages Router API route takes req and res objects", () => {
  const res = { status: vi.fn().mockReturnThis(), json: vi.fn(), setHeader: vi.fn() };
  handler({ method: "GET", query: { name: "Ada" } } as unknown as NextApiRequest, res as unknown as NextApiResponse);
  expect(res.status).toHaveBeenCalledWith(200);
  expect(res.json).toHaveBeenCalledWith({ pong: "Ada" });

  handler({ method: "POST", query: {} } as unknown as NextApiRequest, res as unknown as NextApiResponse);
  expect(res.setHeader).toHaveBeenCalledWith("Allow", "GET");
  expect(res.status).toHaveBeenLastCalledWith(405);
});

A Pages Router page that fetches in getServerSideProps has the same Cypress caveat as before: the data function does not run in a component test, so test the page end to end and test the data function separately, as above. A component that calls useRouter from next/router needs a mock of that module, exactly like the next/navigation mock earlier.

Where the Books Are Outdated

Both consulted books teach testing from the Pages Router era. In Real-World Next.js (Packt, 2022) the unit tests use Jest installed by hand, with a .babelrc that contains the next/babel preset so that Jest can transpile the project, and the component tests compare React Testing Library with Enzyme; Cypress is used for end-to-end and component tests. In Practical Next.js for E-Commerce (Apress, 2023) Cypress is the only tool, configured with npm run cypress and a baseUrl, and the end-to-end tests run against the development server. What to use today:

  • Jest set-up: next/jest, which configures Jest with the Next.js compiler, instead of a hand-written .babelrc with the next/babel preset.

  • Component testing: React Testing Library, with the @testing-library/jest-dom/vitest or jest-dom matchers. The current Next.js guides do not mention Enzyme at all.

  • Runner choice: Vitest is a first-class option in the official guides now; the books predate it.

  • End-to-end target: the production build (next build and next start), not the development server.

  • Playwright: absent from both books and now documented next to Cypress, with a Next.js-specific helper, instant(), from 16.3.

  • What is testable: the books test Pages Router pages whose data comes from getServerSideProps. With the App Router, async Server Components cannot be rendered by Testing Library; extract the logic, or test end to end.

  • Server Actions and Route Handlers: neither book has them; test them as plain functions plus an HTTP or browser test. The security habit that matters most, testing the negative authorisation cases, is also what the books' client-side checks missed.

  • Cypress details: the component-testing setup and the TypeScript requirement (Cypress below 13.6.3 did not support TypeScript 5 with moduleResolution: "bundler", per the Next.js page) changed after the books were written.

The requester’s books are listed in the section bibliography; no text, listing or figure of them is reproduced here.
