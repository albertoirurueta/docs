Images, Fonts & Scripts

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when the facts and examples below were checked; the official documentation reports @doc-version 16.3.8), React 19.3.0, Node.js 20.9.0 or later, TypeScript 5.1 or later and @next/third-parties 16.3.8. It covers the App Router in the main text and shows the Pages Router differences in a short section of their own. Caching matters little for these APIs: none of the four tools reads request data, so every example prerenders and behaves the same under the previous model (the default) and under Cache Components (cacheComponents: true); a dedicated section shows what was checked under both. The image optimiser has its own on-disk cache that neither model controls. Every example was built and run with Next.js 16.3.8, Node.js 24.16 and npm 11.13 on macOS (next build, next start, curl, and headless Chrome for the behaviour that only a browser shows), in a scratch copy of the Bookshelf — the catalogue of books that the rest of this section grows — and each one is followed by the official page it derives from.

Images, fonts and third-party scripts are the three kinds of resource that most often decide a page’s Largest Contentful Paint (LCP), Cumulative Layout Shift (CLS) and Interaction to Next Paint (INP). Next.js ships one built-in component for each, and each one is a thin layer over a platform feature that you could use by hand:

Table 1. The four tools and the browser feature each one wraps
Tool Import What it does for you

Image

next/image

An img element with a generated srcset, lazy loading, reserved space (no layout shift), optional blur-up placeholder and on-demand resizing and re-encoding through the /_next/image endpoint.

Font

next/font/google, next/font/local

Downloads Google Fonts at build time and serves them from your own domain, generates the @font-face rules, a size-adjusted fallback font and a preload link, so the browser makes no request to Google and the text does not jump when the font arrives.

Script

next/script

A script element with a loading strategy, de-duplication across client-side navigations and onLoad, onReady and onError callbacks.

Third-party components

@next/third-parties/google

Ready-made components for Google Tag Manager, Google Analytics, Google Maps Embed and YouTube embeds, built on next/script.

If the React side of this (components, props, events) is new, read React Getting Started first. For the general performance picture that these tools serve, see Performance: Loading Resources and React Performance; Core Web Vitals measurement, the React Compiler and bundle analysis have a page of their own in this section (Performance and Web Vitals).

next/image

next/image extends the HTML img element. A bare img has three well-known problems: it downloads the same large file on every device, it shifts the layout when it arrives because the browser does not know its size, and it loads even when it is far below the fold. The component fixes all three:

  • Size optimisation: it serves a correctly sized, modern-format image for each device (WebP by default).

  • Visual stability: it writes width and height (or absolute positioning for fill), so the browser reserves the space before the file arrives.

  • Faster page loads: it lazy-loads with the browser’s native loading="lazy" and can show a blurred placeholder.

  • Asset flexibility: it resizes on demand, including images that live on a remote server.

Source: Image Optimization

How an image request flows

The component itself only renders HTML. The optimisation happens when the browser follows the generated src and srcset URLs, which all point at the /next/image endpoint of your Next.js server (the _default loader):

sequenceDiagram autonumber participant B as Browser participant N as Next.js server participant C as Disk cache participant O as Origin of the image B->>N: GET /_next/image?url=/covers/solaris.jpg&w=256&q=75 with an Accept header N->>N: check url against localPatterns or remotePatterns, w against the size lists, q against qualities alt not allowed N-->>B: 400 Bad Request else allowed N->>C: look up this url, width, quality and output format alt cache hit C-->>N: optimised file else cache miss N->>O: fetch the source image (public folder, build output or remote host) O-->>N: original bytes N->>N: resize and re-encode (AVIF, WebP or the original format) N->>C: store, honouring minimumCacheTTL end N-->>B: 200 with Cache-Control, Vary Accept and Content-Disposition attachment end
Figure 1. A request to the built-in image optimiser

Two consequences follow. First, every allowed value is an allow-list entry: the width must be one of the configured sizes, the quality one of the configured qualities and the URL one of the configured patterns, because otherwise anyone could ask your server to resize arbitrary images at arbitrary settings. Second, optimisation needs a running Node.js server (or a platform that implements the endpoint); a static export has none, so it needs a custom loader or unoptimized — see the static export section for that case.

Source: Image component

Three kinds of source: static import, public folder, remote URL

src can be a static import, a path under public/, or an absolute URL. They differ in who knows the image size.

app/gallery/images/page.tsx (shortened to the sources)
import Image from "next/image";
import dune from "../covers/dune.jpg"; (1)

export default function Page() {
  return (
    <main className="p-6 space-y-8">
      {/* 1. Static import: width, height and blurDataURL are inferred */}
      <Image
        src={dune}
        alt="Cover of Dune"
        placeholder="blur"
        sizes="200px"
        style={{ width: 200, height: "auto" }}
      />

      {/* 2. File in public/: you supply the intrinsic size */}
      <Image src="/covers/solaris.jpg" alt="Cover of Solaris" width={200} height={300} />

      {/* 3. Remote image: width and height are mandatory */}
      <Image
        src="https://upload.wikimedia.org/wikipedia/commons/4/47/PNG_transparency_demonstration_1.png"
        alt="PNG transparency demonstration"
        width={280}
        height={210}
      />
    </main>
  );
}
1 The file lives next to the page (app/gallery/covers/dune.jpg). Importing it lets Next.js read its dimensions at build time and hash its name for long-lived caching.

Reading it:

  • A static import gives width, height and, for JPEG, PNG, WebP and AVIF files that are not animated, a blurDataURL, so placeholder="blur" works with no extra data. The file name is content-hashed (dune.2i-r4fzomd67d.jpg), so it can be cached forever.

  • A public-folder path needs width and height from you, because Next.js does not open the file at build time. Leaving them out is an error in development (Image with src "/covers/solaris.jpg" is missing required "width" property) and the page answers 500 until you fix it.

  • A remote URL also needs width and height (and blurDataURL if you want a placeholder), because the build cannot fetch the file. The host must be allowed in configuration, covered below.

  • width and height are the intrinsic size used to compute the aspect ratio. They do not set the rendered size; CSS does. If you set a CSS width, set height: auto as well, as the style in the first image does, to keep the aspect ratio.

  • The alt text is required. Use alt="" for purely decorative images.

A fourth source avoids static imports when the file name is only known at render time: a dynamic import() in a Server Component still returns width, height and blurDataURL, provided the path starts with a static prefix (the path is a template string such as ../content/blog/images/ followed by the file name). Every file under that prefix is bundled, so keep the prefix as narrow as possible.

Responsive images: fill and sizes

When the aspect ratio is not known, or the image must cover a box that CSS sizes, use fill. The image then becomes absolutely positioned and stretches to its parent, so the parent must be positioned (relative, fixed or absolute), and object-fit decides cropping.

A responsive grid of covers
<ul className="grid grid-cols-2 md:grid-cols-4 gap-4">
  {covers.map((cover) => (
    <li key={cover.id} className="relative aspect-[2/3]">
      <Image
        src={cover.src}
        alt={`Cover of ${cover.title}`}
        fill
        sizes="(min-width: 768px) 25vw, 50vw"
        className="object-cover"
      />
    </li>
  ))}
</ul>

sizes is the most commonly forgotten prop, and it matters more than any other for download size. It tells the browser how wide the image will be at each breakpoint, before layout, so that the browser can pick a candidate from the srcset. It changes what Next.js generates too:

  • Without sizes, Next.js emits a short srcset of density descriptors (1x, 2x), which suits a fixed-size image, and the browser assumes the image is as wide as the viewport (100vw).

  • With sizes, it emits a full srcset of width descriptors (256w, 384w, 640w, …​), filtered to the widths that can matter for the breakpoints you declared.

This was checked in a browser. The grid above, rendered with sizes, produced a srcset that starts at 256w and ends at 3840w. The same fill image without sizes, in a 400 pixel wide box at a 1000 pixel wide viewport, made the browser request w=1080 (about the viewport width) instead of w=256/384, and development printed:

Image with src "/covers/solaris.jpg" has "fill" but is missing "sizes" prop.
Please add it to improve page performance.

Use sizes for any image that uses fill, or that CSS makes responsive. A static import with explicit sizes="100vw" and style={{ width: "100%", height: "auto" }} is the pattern for a full-width image with a known ratio.

Formats and caching in practice

For the scratch cover, the same source and width produced three different files depending on the Accept header: AVIF 4,867 bytes, WebP 12,248 bytes and JPEG 13,397 bytes. The cover is a synthetic picture, so the ratio is not representative of photographs; what matters is that the response varies on Accept (Vary: Accept) and that each variant is cached separately. With the default formats (image/webp only), a browser that sends Accept: image/avif,image/webp still got WebP, as the table promises.

If a CDN or reverse proxy sits in front of Next.js, it must forward the Accept header and honour Vary: Accept, or every visitor gets the variant that was cached first. The Cache-Control header of an optimised image is public, max-age=<ttl>, must-revalidate, where the TTL is minimumCacheTTL or the upstream header, whichever is larger. Statically imported images are the exception: their hashed file name lets Next.js cache them as immutable.

Loaders: the built-in one, a custom one, and unoptimized

A loader is a function from { src, width, quality } to a URL. The default loader returns a /_next/image URL. You replace it when images are already served by an image CDN (Cloudinary, imgix, Cloudflare Images, Supabase and others; the documentation lists ready-made loaders for sixteen services) or when you cannot run the optimiser at all, as in a static export.

Per image, pass loader. Because a function cannot cross from a Server Component to the browser, the component that passes it must be a Client Component:

app/gallery/loader/loader.ts and cover.tsx
// loader.ts
import type { ImageLoaderProps } from "next/image";

// A pretend CDN: any function that returns a URL works.
export default function cdnLoader({ src, width, quality }: ImageLoaderProps) {
  const url = new URL(`https://images.example.com${src}`);
  url.searchParams.set("w", width.toString());
  url.searchParams.set("q", (quality || 75).toString());
  return url.href;
}

// cover.tsx
"use client";

import Image from "next/image";
import cdnLoader from "./loader";

export function CdnCover({ src, title }: { src: string; title: string }) {
  return (
    <Image loader={cdnLoader} src={src} alt={`Cover of ${title}`} width={200} height={300} sizes="200px" />
  );
}

The rendered img has src="https://images.example.com/covers/solaris.jpg?w=3840&q=75" and a srcset of the same shape for every width in deviceSizes and imageSizes: the browser talks to the CDN directly and /_next/image is not involved, so remotePatterns and qualities no longer apply to that image.

Built and run, every Image in the app (including those in Server Components) rendered images.example.com URLs. Two findings from that experiment are not in the documentation’s examples:

  • The official loaderFile example starts with "use client". With that directive in place, calling getImageProps from a Server Component (see below) failed the build with Attempted to call the default export of [project]/lib/image-loader.ts from the server, but it’s on the client. Removing the directive made Image and getImageProps both work from Server Components. Keep the directive only if the file really needs client-only code.

  • With a custom loader configured, an .svg source also went through the loader (images.example.com/next.svg?w=…​) instead of being served as-is. Pass unoptimized on SVG images, or have the loader return src unchanged for them.

Source: images in next.config.js, Image: loaderFile

To turn optimisation off, pass unoptimized on one image or set images.unoptimized: true. It is the right choice for files that gain nothing from re-encoding: images under about 1 KB, vector images (SVG) and animated GIFs. Enabling dangerouslyAllowSVG lifts that, but SVG can carry scripts, so it should come with contentDispositionType: "attachment" and a restrictive contentSecurityPolicy.

The LCP image: preload

The Largest Contentful Paint element of a page is very often an image: a hero banner or the first product photo. The browser normally discovers an img only when it parses the body, which delays it. The preload prop (added in 16) inserts a link rel="preload" as="image" into the document head, so the download starts with the HTML.

app/gallery/hero/page.tsx
import Image from "next/image";

export default function Page() {
  return (
    <main>
      <Image
        src="/covers/hero.jpg"
        alt="Spring reading list banner"
        width={1200}
        height={450}
        preload
        sizes="100vw"
        style={{ width: "100%", height: "auto" }}
      />
      <h1>Spring reading list</h1>
    </main>
  );
}

preload replaces priority (deprecated in 16). A preloaded image is also fetched eagerly: the rendered img has no loading="lazy" attribute. The prerendered HTML contains, in the head, a link rel="preload" as="image" imageSrcSet="/_next/image?url=%2Fcovers%2Fhero.jpg&w=640&q=75 640w, …​" whose imageSrcSet matches the img’s `srcset, so the browser downloads the same candidate it will later use.

When not to use preload, according to the documentation: when several images could be the LCP element depending on the viewport (a desktop and a mobile banner), when loading is set, and when fetchPriority is set. In most cases loading="eager" or fetchPriority="high" is the better tool. Development also helps you find the right image: the browser console printed Image with src "/covers/solaris.jpg" was detected as the Largest Contentful Paint (LCP). Please add the loading="eager" property if this image is above the fold. for a lazy-loaded image that turned out to be the LCP element.

getImageProps: art direction, themes and CSS backgrounds

getImageProps (stable since 14.1.0) returns the props the component would pass to its img, so you can use them elsewhere. The typical case is art direction: a wide banner for desktop and a tall one for phones, chosen by the browser through picture.

app/gallery/art/page.tsx
import { getImageProps } from "next/image";

export default function Page() {
  const common = { alt: "Spring reading list banner", sizes: "100vw" };
  const {
    props: { srcSet: desktop },
  } = getImageProps({ ...common, src: "/covers/hero.jpg", width: 1440, height: 540 });
  const {
    props: { srcSet: mobile, ...rest },
  } = getImageProps({ ...common, src: "/covers/hero-mobile.jpg", width: 750, height: 1000 });

  return (
    <picture>
      <source media="(min-width: 1000px)" srcSet={desktop} />
      <source media="(min-width: 500px)" srcSet={mobile} />
      <img {...rest} style={{ width: "100%", height: "auto" }} />
    </picture>
  );
}

The page prerendered and the HTML contains two source elements whose srcset values point at /_next/image for hero.jpg and hero-mobile.jpg. getImageProps does not call useState, which makes it lighter than the component, but for the same reason it cannot be combined with placeholder. The documentation also uses it to turn a srcset into a CSS image-set() for background images, and shows a theme-aware component that renders two Image elements and hides one with prefers-color-scheme; because both exist in the DOM, use fetchPriority="high" rather than preload or loading="eager" there.

next/font

Web fonts hurt performance in two ways: the browser cannot start downloading a font until it has parsed the CSS that declares it, and while it waits, text is either invisible or rendered in a fallback font whose different metrics make the layout jump when the real font arrives. next/font addresses both. It downloads Google Fonts at build time, serves the files from your own domain with the rest of the static assets (the browser sends no request to Google), emits the @font-face rule, preloads the files that the route needs, and generates a fallback font adjusted to the metrics of the real font so the swap barely moves the text.

Source: Font Optimization, Font module

A Google font and a local font, as CSS variables

The usage pattern is the same for both sources: call a font function at module scope, then apply the result. There are three ways to apply it (className, style, and a CSS variable); the CSS variable is the most flexible and is what Tailwind CSS v4 expects.

app/layout.tsx
import type { ReactNode } from "react";
import { Inter } from "next/font/google";
import localFont from "next/font/local";
import "./globals.css";

// A variable Google font: no `weight` is needed.
const inter = Inter({
  subsets: ["latin"],
  variable: "--font-inter", (1)
  display: "swap",
});

// A local variable font, resolved relative to this file.
const bookshelf = localFont({
  src: "./fonts/bookshelf-sans.woff2",
  weight: "100 900", (2)
  variable: "--font-bookshelf",
  display: "swap",
});

export default function RootLayout({ children }: { children: ReactNode }) {
  return (
    <html lang="en" className={`${inter.variable} ${bookshelf.variable}`}>
      <body>{children}</body>
    </html>
  );
}

  • The head contained two link rel="preload" as="font" type="font/woff2" crossorigin tags, one for the Latin subset of Inter and one for the local font.

  • The generated stylesheet had @font-face rules for Inter with font-weight:100 900 and font-display:swap, one per Unicode range (Latin, Cyrillic, Greek, Vietnamese, and so on); only the Latin file is preloaded because subsets: ["latin"].

That is the layout-shift protection, and adjustFontFallback controls it (a boolean for Google fonts, "Arial", "Times New Roman" or false for local fonts).

  • The computed font-family of the h1 was bookshelf, "bookshelf Fallback" and of the paragraph Inter, "Inter Fallback"; document.fonts listed both faces as loaded.

  • No request went to fonts.googleapis.com or fonts.gstatic.com, neither in the HTML nor from the browser.

Practical rules that follow from the options and from experiments:

  • Prefer variable fonts. One file covers all weights, so there is nothing to list and less to download. For a font that is not variable the weight is mandatory: with Pacifico and no weight, next build failed with Module not found: Can’t resolve 'next/font/google/target.css' and the useful line Missing weight for Pacifico. Available weights: 400.

  • Use an underscore for multi-word names: Roboto Mono is imported as Roboto_Mono.

  • Call each font function once. Every call creates a self-hosted instance. Export fonts from a shared module (the documentation calls it a font definitions file, for example app/fonts.ts) and import the object wherever you need it.

  • Scope decides preloading. A font used in a page is preloaded for that route only, in a layout for every route the layout wraps, in the root layout for all routes. Put a font in the root layout only when the whole site uses it.

  • Use few fonts. Each family and style is another file the client downloads.

  • Subset deliberately. subsets: ["latin"] is not a filter on what the stylesheet declares (all Unicode ranges were still declared above); it selects what is preloaded.

  • A font object offers className (a class that sets font-family, font-weight and font-style), style (an object including fontFamily) and, when variable was set, a variable class name.

next/script

Third-party scripts (analytics, consent managers, chat widgets) are the most common reason for a slow main thread and a poor INP. The Script component is an script element with a loading strategy and de-duplication. Placed in a layout, it loads once for every route in that layout and is not reloaded by client-side navigation; the documentation recommends adding third-party scripts only to the pages or layouts that need them.

The four strategies

Preloaded and fetched before any Next.js code and before hydration; executed in the order written; does not block hydration.

afterInteractive (default)

Injected on the client after some or all hydration.

Tag managers, analytics.

lazyOnload

Injected during browser idle time, after all resources are fetched.

The next example loads three local widget scripts with different strategies, plus an inline script. The widgets are tiny files in public/widgets/ that push a label into window.__order, so the real execution order can be read in the browser. The root layout holds the beforeInteractive script:

app/layout.tsx (the script part)
import Script from "next/script";

export default function RootLayout({ children }: { children: ReactNode }) {
  return (
    <html lang="en">
      <body>
        {children}
        <Script src="/widgets/consent.js" strategy="beforeInteractive" />
      </body>
    </html>
  );
}
app/gallery/scripts/layout.tsx
import type { ReactNode } from "react";
import Script from "next/script";

export default function ScriptsLayout({ children }: { children: ReactNode }) {
  return (
    <>
      <section>{children}</section>
      <Script src="/widgets/analytics.js" /> {/* afterInteractive by default */}
      <Script src="/widgets/chat.js" strategy="lazyOnload" />
      <Script id="show-banner"> {/* inline scripts need an id */}
        {`document.documentElement.dataset.banner = 'shown'`}
      </Script>
    </>
  );
}

Loaded in Chrome, window.order was ["consent (beforeInteractive)", "analytics (afterInteractive)", "chat (lazyOnload)"] and <html data-banner="shown"> had been set by the inline script. In the server HTML, the beforeInteractive script appeared as a link rel="preload" as="script" in the head plus an inline (self.next_s=self.__next_s||[]).push(["/widgets/consent.js",{}]) bootstrap call; the afterInteractive script appeared as a preload link, and the lazyOnload one had no preload link at all. The App Router therefore does not write a literal script src for beforeInteractive into the head: the Next.js runtime inserts it at the very start of hydration. (The documentation says such scripts are injected into the head of the initial HTML; the observable guarantee is the ordering relative to Next.js code.) The beforeInteractive script runs once per document load: a client-side navigation does not run it again, even one that changes a root param, because the root layout stays mounted.

Source: Script: strategy, Scripts: layout scripts, Scripts: inline scripts

Reacting to loading: onLoad, onReady and onError

Event handlers run code when the script has loaded. They are functions, so Script must be used inside a Client Component ("use client"):

  • onLoad runs once after the script has loaded. It cannot be used with beforeInteractive.

  • onReady runs after the script has loaded and again every time the component mounts (for example after a navigation back to the page). It does work with beforeInteractive, which is what the documentation recommends instead of onLoad.

  • onError runs if the script fails to load. It cannot be used with beforeInteractive either.

app/gallery/scripts/chat-button.tsx
"use client";

import { useState } from "react";
import Script from "next/script";

declare global {
  interface Window {
    ChatWidget?: { open: () => string };
  }
}

export function ChatButton() {
  const [state, setState] = useState("loading");
  return (
    <>
      <Script
        id="chat-loader"
        src="/widgets/chat.js?client"
        strategy="lazyOnload"
        onLoad={() => setState("loaded")}
        onReady={() => console.log("ready (runs again after every mount)")}
        onError={(e) => setState(`failed: ${e.message}`)}
      />
      <button disabled={state !== "loaded"} onClick={() => window.ChatWidget?.open()}>
        Chat ({state})
      </button>
    </>
  );
}

The page built, and in Chrome the button text changed from Chat (loading) to Chat (loaded) and the console printed ready (runs again after every mount). Remember that the handler is not the place to put analytics logic that has to run before the user can interact: the lazyOnload strategy fires at idle time, which can be seconds after hydration.

Extra attributes that Script does not use itself (a CSP nonce, data-* attributes) are forwarded to the final script element; the nonce is covered together with Content Security Policy in the security pages of this section. Inline scripts must have an id, or Next.js cannot track and optimise them; dangerouslySetInnerHTML works as an alternative to children.

Source: Script: onLoad, Script: onReady, Script: onError, Scripts: additional attributes

The worker strategy

strategy="worker" offloads a script to a web worker with Partytown so that the main thread stays free for your own code. It requires experimental: { nextScriptWorkers: true }, asks you to install @qwik.dev/partytown, and the documentation states that it is not stable and does not work with the App Router: it is for the pages/ directory only. It was not run for this page. Partytown has real trade-offs (scripts that need synchronous access to the DOM can misbehave), so treat it as an experiment and measure.

Third-party libraries with @next/third-parties

@next/third-parties is a package of components that wrap popular third-party embeds with sensible loading behaviour. It is documented as experimental and under active development, and it is versioned in lockstep with Next.js (16.3.8 at the time of writing). Install it next to next:

npm install @next/third-parties@latest next@latest

Cache Components and the previous model

These APIs interact with caching in only two ways, and neither depends on the cacheComponents setting:

  • Prerendering. Image, Script, a font function and the @next/third-parties components read no request data, so a page that only uses them is part of the static shell. The entire gallery was built twice, with CACHE_COMPONENTS=1 (Cache Components) and without it (previous model); in both builds all routes were ○ (Static), every route answered 200 and the browser checks for scripts and fonts gave the same results.

  • The image cache. Optimised images are stored in <distDir>/cache/images and governed by minimumCacheTTL, the upstream Cache-Control and maximumDiskCacheSize. This is independent of the Data Cache, the Full Route Cache and use cache: revalidating a path or tag does not purge an optimised image, and there is no invalidation API. Change the src (for example with a version query string allowed by localPatterns) to force a new image.

For the two models of caching themselves, see Caching and Partial Prerendering and Cache Components.

Pitfalls checklist

  • An unconfigured remote host, a disallowed quality or width, or a query string not in localPatterns: development throws or warns; production returns 400 and the browser shows a broken image.

  • A fill image without a positioned parent collapses to zero height; a fill or responsive image without sizes downloads an image as wide as the viewport.

  • Only one image per page should use preload; for several candidate LCP elements prefer fetchPriority="high".

  • A loader or onLoad/onError function on a Server Component fails to serialise: move it to a Client Component.

  • A "use client" loader file breaks getImageProps in Server Components.

  • SVG: leave it unoptimized; enabling dangerouslyAllowSVG without a CSP is a risk.

  • Do not call a font function inside a component; it must be at module scope, and call it once per font.

  • A non-variable Google font needs weight; multi-word names use underscores.

  • Third-party scripts affect INP: prefer lazyOnload, place a script in the narrowest layout, and measure.

  • @next/third-parties embeds contact third-party hosts (Google, jsDelivr, YouTube): put them behind consent and allow them in the Content Security Policy.

  • Do not put secrets in client-side script URLs or props; the IDs of GTM and GA are public, a server API key is not.
