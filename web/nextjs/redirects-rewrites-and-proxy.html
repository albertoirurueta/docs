Redirects, Rewrites & Proxy

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when the facts and examples below were checked; the official documentation reports @doc-version 16.3.8), React 19.3.0 and Node.js 20.9.0 or later. It covers the App Router, where proxy.ts, redirect() and permanentRedirect() live; the three next.config keys work the same way in both routers, and the Pages Router differences are called out where they exist. Where caching changes the outcome, the page labels the two models: the previous model (the default, cacheComponents off) and Cache Components (cacheComponents: true, opt-in). Every example was built and run with Next.js 16.3.8 and Node.js 24.16 on macOS in a scratch copy of the Bookshelf catalogue that the rest of this section grows, and the status codes and headers quoted below are the output of curl -I against next start, not paraphrases of the documentation.

Moving a request somewhere else is the oldest job of a web server, and Next.js has five different places to do it, which differ in when they run, what they can see and what status code the browser receives. The page starts with a map of the five, then the order in which they are evaluated, then each in turn, and ends with the question the official documentation itself raises: how much should the Proxy do. The files named here (next.config.ts, proxy.ts, the app folder) are described in Project Structure and Configuration, TypeScript and Environment Variables; the request flow they take part in is drawn in Introduction and Architecture.

The Five Places to Redirect or Rewrite

A redirect answers with a 3xx status and a Location header, so the browser’s address bar changes and the browser issues a second request. A rewrite serves the content of a different path while the URL in the address bar stays what the user asked for: it is a proxy behind the scenes, and no second request is made. Both can be declared in five places.

The practical rule from the official documentation is to use the first option that fits: a static list of known paths goes in redirects; a decision that needs request data but no slow work goes in the Proxy; and a decision that needs your data goes in the component or action that already has it. The three redirect* APIs and the two config keys are sections below; the decision table at the end of the page repeats the rule with the Bookshelf’s own cases.

Order of Evaluation

When a request arrives, Next.js runs the five mechanisms in a fixed order. The order matters because an earlier step can end the request before a later one sees it: a redirects entry wins over a Proxy that redirects the same path, and a Proxy redirect wins over any rewrite.

(added to the response)"] H --> RD{"2. redirects from next.config
match?"} RD -- yes --> E1["307 / 308 response, done"] RD -- no --> P{"3. proxy.ts
(if the matcher matches)"} P -- "redirect or direct Response" --> E2["Response, done"] P -- "rewrite, next()" --> BF{"4. beforeFiles rewrites"} BF --> FS{"5. Filesystem: public/, _next/static,

The same order as a list, with what each step can and cannot do:

Table 2. Evaluation order in Next.js 16.3
Step What runs Notes

1

headers from next.config.ts

Checked first. A later headers entry that sets the same key overrides an earlier one.

2

redirects from next.config.ts

Checked before the filesystem, public/ files and the Proxy.

3

proxy.ts

Runs for every request its matcher allows. It can rewrite, redirect, change headers or answer directly.

4

beforeFiles rewrites

Run after the Proxy and before any file, so they can shadow a file in public/ or a page.

5

The filesystem

public/, _next/static and non-dynamic routes.

6

afterFiles rewrites

Run only when step 5 found nothing. A plain array returned from rewrites() is treated as afterFiles.

7

Dynamic routes

For example app/[locale]/books/[id]/page.tsx.

8

fallback rewrites

The last resort, run before the 404 page. This is where an external legacy site goes.

The Bookshelf’s next.config.ts and proxy.ts were built so that the order can be observed. The path /probe is redirected by both redirects (to /from-config) and the Proxy (to /from-proxy); /probe2 is redirected by the Proxy and also has a beforeFiles rewrite; /hello.txt exists in public/ and has a beforeFiles rewrite as well.

$ curl -I localhost:3306/probe
HTTP/1.1 307 Temporary Redirect
location: /from-config

$ curl -I localhost:3306/probe2
HTTP/1.1 307 Temporary Redirect
location: /from-proxy

$ curl localhost:3306/hello.txt
{"status":"ok"}

redirects beat the Proxy on /probe; the Proxy beat the rewrite on /probe2; and the beforeFiles rewrite beat the static file on /hello.txt, because the response is the JSON of the Route Handler it points to (/api/health) and not the text in public/hello.txt. One more consequence of the order is easy to miss: the Proxy runs before the afterFiles and fallback rewrites, so a Proxy that redirects every path to a locale prefix also redirects the source path of a rewrite before the rewrite is ever consulted. In the scratch app a rewrite from /shelf/:id was shadowed that way (the response was a 307 to /en/shelf/2) until the source was written as /en/shelf/:id. Either write rewrite sources the way the Proxy leaves them, or exclude their paths from the Proxy matcher, as the legacy prefix is below.

The redirects Key

redirects is an async (or plain) function in next.config.ts that returns an array of rules. Each rule has a source pattern, a destination and either permanent or statusCode. The rules are compiled into the routing table at build time, so a change needs a new build (or a restart of next dev).

Redirect rules in the Bookshelf’s next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  async redirects() {
    return [
      // 308: the old catalogue moved for good
      { source: "/catalog", destination: "/en", permanent: true },
      // regex parameter: digits only; the id is reused in the destination
      { source: "/catalog/:id(\\d+)", destination: "/en/books/:id", permanent: true },
      // wildcard: everything below /old-blog moves, the query string is passed through
      { source: "/old-blog/:slug*", destination: "/en/blog/:slug*", permanent: false },
      // custom status code instead of permanent (never both)
      { source: "/gone-for-now", destination: "/en", statusCode: 301 },
    ];
  },
};

export default nextConfig;

The behaviours worth knowing, each confirmed with curl -I:

  • Status codes. permanent: true answers 308 and permanent: false answers 307. A 308 response also carries a Refresh: 0;url=…​ header, which the documentation says exists for old browsers (IE11). statusCode replaces permanent when a client needs 301 or 302; you cannot set both.

  • Query strings pass through. /old-blog/2024/post-1?hello=world kept hello=world on the destination.

  • Path patterns follow path-to-regexp. :slug matches one segment, :slug* zero or more, :slug+ one or more, :slug? zero or one, and :id(\\d+) restricts a parameter with a regular expression. A request for /catalog/abc did not match the digits-only rule and fell through to the Proxy (which redirected it to /en/catalog/abc). Patterns are anchored at the start of the path, and the parameters can be reused in the destination. The characters (, ), {, }, :, *, + and ? must be escaped with a double backslash when they are meant literally.

  • Always put a / before the colon. /old-blog/:slug is a pattern; old-blog:slug is a literal string and risks an infinite redirect.

  • The destination may be absolute. destination: "https://example.com/store" redirects out of the site (the /store rule in the scratch app answered 307 with that location).

has and missing: matching on more than the path

A rule can be restricted to requests that carry (or lack) a header, cookie, query parameter or host. Every has item must match and every missing item must not, in addition to the source. A value is a regular-expression-like string, and a named capture group makes the captured text available in the destination as :name.

async redirects() {
  return [
    // only when the cookie beta=off is present
    {
      source: "/beta",
      has: [{ type: "cookie", key: "beta", value: "off" }],
      destination: "/en",
      permanent: false,
    },
    // only when the header x-no-redirect is absent
    {
      source: "/store",
      missing: [{ type: "header", key: "x-no-redirect" }],
      destination: "https://example.com/store",
      permanent: false,
    },
    // named capture group in a query value, reused in the destination
    {
      source: "/search",
      has: [{ type: "query", key: "term", value: "(?<t>.+)" }],
      destination: "/en?q=:t",
      permanent: false,
    },
    // host matching
    {
      source: "/hostcheck",
      has: [{ type: "host", value: "shop.example.test" }],
      destination: "/en",
      permanent: false,
    },
  ];
},

Limits and pitfalls

  • Config redirect responses carry no headers entries (observed). Although headers is step 1 of the order, the 308 and 307 responses produced by redirects rules in the scratch app did not include the security headers that a catch-all headers rule adds to every other response, while redirects produced by the Proxy did. If a header must be on every response, set it in the Proxy as well, or at the CDN.

  • A 308 is cached for good. Browsers and search engines keep a permanent redirect; a wrong permanent: true is hard to undo. Start with permanent: false and switch once the mapping is final.

  • In the Pages Router, redirects does not apply to client-side routing. The documentation says Link and router.push do not get redirected, as they navigate without a request unless a Proxy matches the path.

  • Platform limits. The guide notes that redirects can be limited by the platform (1,024 entries on Vercel). Beyond a few hundred rules, see Redirect Maps at Scale.

  • Loops. A rule whose destination matches its own source, or a Proxy and a config rule that point at each other, produces ERR_TOO_MANY_REDIRECTS in the browser. curl -IL --max-redirs 5 finds them quickly.

The rewrites Key

rewrites has the same shape as redirects without the status code: a source and a destination, with the same path patterns and the same has/missing/basePath options. A plain array is applied after the filesystem and before dynamic routes (afterFiles); returning an object with beforeFiles, afterFiles and fallback arrays places rules at the three points of the order of evaluation.

Rewrites in the Bookshelf’s next.config.ts
async rewrites() {
  return {
    beforeFiles: [
      // checked before public/ files, so it can shadow a static file
      { source: "/hello.txt", destination: "/api/health" },
    ],
    afterFiles: [
      // checked after public/ and pages, before dynamic routes
      { source: "/api/v1/books", destination: "/api/books" },
      { source: "/en/shelf/:id", destination: "/en/books/:id" },
    ],
    fallback: [
      // checked last: only reached when nothing else matched
      { source: "/legacy/:path*", destination: "http://localhost:3399/:path*" },
    ],
  };
},

  • The URL does not change. /api/v1/books is served by /api/books, which is the usual way to keep a public URL stable while the implementation moves, and /en/shelf/2 renders the book page.   • An external destination makes Next.js a reverse proxy. The fallback rule forwarded /legacy/shop/cart to a small Node.js server on port 3399 and returned its body.   • Rewrite parameters become the query when the destination does not use them (observed with a page). The headers Key

headers adds response headers for matching paths: a source pattern, a headers array of key/value pairs and the same has, missing and basePath options. Path parameters can be used in the key and the value. When several entries match and set the same key, the last one wins.

async headers() {
  return [
    {
      source: "/:path*",
      headers: [
        { key: "X-Content-Type-Options", value: "nosniff" },
        { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
      ],
    },
    {
      // :id is captured and reused in the value
      source: "/en/books/:id",
      headers: [{ key: "X-Bookshelf-Book", value: ":id" }],
    },
    {
      // only when the preview cookie is present
      source: "/en/books/:id",
      has: [{ type: "cookie", key: "preview" }],
      headers: [{ key: "Cache-Control", value: "private, no-store" }],
    },
  ];
},

  • Static headers belong in headers; per-request values belong in the Proxy. A Content-Security-Policy with a nonce changes on every request, so it is built in the Proxy (see the content security policy guide in the references); a fixed X-Content-Type-Options needs no code at all.

Status Codes: 307, 308, 303 and the Meta Tag

Why does Next.js talk about 307 and 308 instead of the 302 and 301 that every tutorial uses? Because many browsers rewrote the request method to GET after a 301 or 302, so a POST /v1/users redirected to /v2/users could arrive as GET /v2/users. 307 and 308 say explicitly that the method (and body) must be preserved. The cost of that precision is a third code, 303, that you meet in Server Actions.

redirect() and permanentRedirect()

redirect(path) and permanentRedirect(path) come from next/navigation. They work while rendering Server and Client Components, in Route Handlers and in Server Functions (the Server Actions of the React Forms and Actions page). Both throw a special NEXT_REDIRECT error that unwinds the render, which has two consequences: the call never returns (its TypeScript return type is never, so no return is needed), and it must not sit inside a try block that swallows errors.

In a Server Action

After a mutation, the usual reply is to send the user to the page that shows the result. The action below validates the form, creates a book (a stand-in id here), revalidates the catalogue and redirects. The redirect() call is the last statement and is outside any try/catch.

app/[locale]/books/new/actions.ts
"use server";

import { redirect } from "next/navigation";
import { revalidatePath } from "next/cache";
import { isLocale, defaultLocale } from "@/lib/i18n";

export async function createBook(formData: FormData) {
  const title = String(formData.get("title") ?? "").trim();
  const requested = String(formData.get("locale") ?? "");
  const locale = isLocale(requested) ? requested : defaultLocale;
  if (!title) redirect(`/${locale}/books/new?error=title`);

  const id = "1"; // pretend we inserted a row and got its id
  revalidatePath(`/${locale}/books`);
  redirect(`/${locale}/books/${id}`); // outside any try/catch: redirect() throws
}

Pitfalls specific to redirect()

  • try/catch swallows it. redirect() throws NEXT_REDIRECT; a catch (error) that does not rethrow turns the redirect into a silent no-op. Call it after the try block, or rethrow the error in the catch.

  • Not in event handlers. onClick={() ⇒ redirect("/x")} is an error; use useRouter().push("/x"), a Link, or a Server Action.

  • Mutating GETs. A redirect after a mutation belongs to a POST (a Server Action or a mutating Route Handler); a redirect() in a Server Component that also changes data runs again on every refresh and on every prefetch.

  • revalidatePath before redirect. If the target page shows the changed data, revalidate first, as the example does; the redirect is the last statement.

  • In Route Handlers redirect() also works, as does returning NextResponse.redirect(new URL("/x", request.url)); both answer 307 unless you pass another status to the second form.

A safe ?from= parameter

The Proxy below sends anonymous visitors to /en/login?from=/en/account. When the login page later sends the user back, it must not trust from: ?from=//evil.example and ?from=https://evil.example are valid-looking values. The helper accepts only a path on the same site and was run against both attack shapes:

lib/safe-next.ts
// Accept only same-site relative paths from a ?from= parameter.
export function safeNext(from: string | null | undefined, fallback: string): string {
  if (!from) return fallback;
  // must start with a single slash; "//host" and "/\host" are protocol-relative tricks
  if (!from.startsWith("/") || from.startsWith("//") || from.startsWith("/\\")) return fallback;
  try {
    const url = new URL(from, "http://localhost"); // resolves against a dummy origin
    if (url.origin !== "http://localhost") return fallback;
    return url.pathname + url.search;
  } catch {
    return fallback;
  }
}

"//evil.example/x"     -> /en
"https://evil.example" -> /en
"/\\evil.example"      -> /en
"javascript:alert(1)"  -> /en
null                   -> /en

proxy.ts

The Proxy is a single file, proxy.ts (or .js), at the project root or in src/ next to app/ and pages/, that exports one function. Next.js calls it for every request the matcher allows, before routes are rendered. From it you can redirect, rewrite, set request or response headers and cookies, or answer with a Response of your own. Next.js 16 renamed the feature from Middleware; the functionality is the same and the reason for the new name is that "middleware" suggested Express-style middleware chains, while the feature behaves like a network boundary in front of the app.

The module must export a function named proxy or a default function. It may export a config object. It receives the NextRequest and, optionally, a NextFetchEvent whose waitUntil(promise) keeps the invocation alive for background work such as logging after the response is sent. A NextProxy type infers both parameter types.

import { NextResponse, type NextRequest } from "next/server";

export function proxy(request: NextRequest) {
  if (request.nextUrl.pathname.startsWith("/about")) {
    return NextResponse.rewrite(new URL("/about-2", request.url));
  }
}

export const config = { matcher: "/about/:path*" };

Source: Proxy and proxy.js

A few file rules: there is one Proxy per project (split the logic into modules and import them from proxy.ts); when pageExtensions is customised the file is proxy.page.ts; and the function can be async. The ƒ Proxy (Middleware) line in the next build route table confirms that the Proxy was found.

The matcher

Without a matcher, the Proxy runs on every request, including _next/static, _next/image and the files in public/. A redirect or an authentication check then blocks the CSS and JavaScript of the login page itself. Always declare a matcher, usually as a negative lookahead.

export const config = {
  matcher: ["/((?!api|_next/static|_next/image|legacy|favicon.ico|.*\\..*).*)"],
};

The pattern syntax is path-to-regexp, as in redirects:

  • a source must start with /, is anchored to the start of the path, and may use named parameters (/about/:path matches /about/a but not /about/a/c), modifiers (:path*, :path+, :path?) and a parenthesised regular expression;

  • the value is an array for several paths and must be a constant: the matcher is analysed at build time, and variables are ignored;

  • an entry can be an object with source, locale, has and missing, which adds header, cookie, query and host conditions.

The object form is how to skip prefetch requests, which would otherwise run the Proxy on every Link in the viewport. The following matcher was built and tested with curl against a Proxy that adds an x-proxy-ran header:

export const config = {
  matcher: [
    {
      source: "/((?!api|_next/static|_next/image|favicon.ico).*)",
      // skip prefetches
      missing: [
        { type: "header", key: "next-router-prefetch" },
        { type: "header", key: "purpose", value: "prefetch" },
      ],
    },
  ],
};

x-proxy-ran: /en/login

Three details from the reference page that bite in practice. First, even if a negative matcher excludes _next/data, the Proxy still runs for those routes; that is intentional, so that protecting a page also protects its data route. Second, a matcher excluding a path also excludes the Server Function calls on that path, because a Server Function is not a separate route but a POST to the route where it is used; moving a function to another route can silently drop Proxy coverage, so every Server Function checks authorisation itself. Third, the pattern api in the lookahead above also excludes /apiary, because it matches a prefix; write api/ plus a separate api$ entry if that matters.

NextRequest and NextResponse

NextRequest extends the web Request. NextResponse extends the web Response. Together they are the whole API of the Proxy.

Table 4. The parts of NextRequest and NextResponse the Proxy uses

request.nextUrl

A URL with extras: pathname (without the basePath), searchParams, basePath and buildId. clone() returns a mutable copy.

request.cookies

get, getAll, has, set, delete and clear on the incoming Cookie header.

The web Headers. Internal Flight headers (rsc, next-router-state-tree, next-router-prefetch) are stripped for RSC requests so that the HTML and RSC variants of a request are handled alike.

The Bookshelf Proxy

The scratch project’s proxy.ts combines the usual jobs: an optimistic authentication redirect, a cookie-based A/B rewrite, a locale redirect, and a request header forwarded to the app. Each part is explained after the listing.

proxy.ts
import { NextResponse, type NextRequest } from "next/server";
import { locales, defaultLocale, isLocale } from "@/lib/i18n";

function pickLocale(request: NextRequest): string {
  const preferred = request.headers.get("accept-language")?.slice(0, 2) ?? "";
  return isLocale(preferred) ? preferred : defaultLocale;
}

// Clone nextUrl (not `new URL(path, request.url)`) so basePath is re-applied.
function withPath(request: NextRequest, pathname: string, search = request.nextUrl.search) {
  const url = request.nextUrl.clone();
  url.pathname = pathname;
  url.search = search;
  return url;
}

export async function proxy(request: NextRequest) {
  const { pathname, search } = request.nextUrl;

  // Optimistic check only: the real authorisation lives in the Data Access Layer.
  const account = /^\/(en|es)\/account(\/|$)/.exec(pathname);
  if (account && !request.cookies.has("bookshelf_session")) {
    const login = withPath(request, `/${account[1]}/login`, "");
    login.searchParams.set("from", pathname + search);
    return NextResponse.redirect(login);
  }

  // A/B test: sticky bucket in a cookie, rewrite keeps the URL.
  if (/^\/(en|es)\/about$/.test(pathname)) {
    const bucket = request.cookies.get("bucket")?.value ?? (Math.random() < 0.5 ? "a" : "b");
    const response =
      bucket === "b" ? NextResponse.rewrite(withPath(request, `${pathname}-b`)) : NextResponse.next();
    if (!request.cookies.has("bucket")) {
      response.cookies.set("bucket", bucket, { path: "/", maxAge: 60 * 60 * 24 * 30, sameSite: "lax" });
    }
    return response;
  }

  // Locale redirect.
  if (!locales.some((l) => pathname === `/${l}` || pathname.startsWith(`/${l}/`))) {
    return NextResponse.redirect(withPath(request, `/${pickLocale(request)}${pathname}`));
  }

  // Pass data to the app: request headers (upstream only) + a response header for the demo.
  const requestHeaders = new Headers(request.headers);
  requestHeaders.set("x-request-id", crypto.randomUUID());
  requestHeaders.set("x-locale", pathname.split("/")[1]);
  const response = NextResponse.next({ request: { headers: requestHeaders } });
  response.headers.set("x-bookshelf-proxy", "ran");
  return response;
}

export const config = {
  matcher: ["/((?!api|_next/static|_next/image|legacy|favicon.ico|.*\\..*).*)"],
};

  • Redirect with a return path. The authentication branch builds the login URL from nextUrl and stores the original path and query in from, the pattern of the NextResponse reference. The check reads only the cookie’s presence: it is an optimistic check, which the authentication guide recommends for the Proxy because it runs on every request, prefetches included. It never proves the session is valid.

  • Cookies. request.cookies reads the incoming cookie; response.cookies.set() writes Set-Cookie on the response, here to keep a visitor in the same experiment bucket. Set path, maxAge and sameSite explicitly, and httpOnly and secure for anything sensitive; an experiment bucket is not sensitive.

  • Rewrite. NextResponse.rewrite() served /en/about-b while the URL stayed /en/about. The response carries an x-middleware-rewrite header; the name still says "middleware" in 16.3.8 and is visible to clients, so never put anything secret in a rewrite URL.

  • Forwarding data to the app. NextResponse.next({ request: { headers } }) makes the new request headers available to the page, route or action, and only to them: the client does not receive them. A Server Component read them with headers() (locale=en id=<uuid> in the scratch app). The Proxy overwrote a client-supplied x-request-id: spoofed, which is the point: overwrite or delete any header the application trusts, never merge. The docs warn that NextResponse.next({ headers }) is a different thing, it sends headers to the client and can override headers such as the Content-Type that Server Actions rely on. Prefer an allow-list when forwarding request headers, so cookies and authorization do not leak to upstream services.

  • basePath. Under basePath: "/shop", request.nextUrl.pathname has no /shop, but new URL("/en/login", request.url) does not add it back: the first version of this Proxy answered location: /en/login?from=…​ for a request to /shop/en/account, a redirect that left the base path. nextUrl.clone() keeps the base path, and the helper withPath() above produced location: /shop/en/login?from=%2Fen%2Faccount.

Answering directly

The Proxy may return a Response instead of continuing. This guards a write API that must refuse anonymous callers before any handler code runs:

import type { NextRequest } from "next/server";

// Only the Bookshelf write API; reads stay public.
export const config = { matcher: "/api/admin/:path*" };

export function proxy(request: NextRequest) {
  const token = request.headers.get("authorization");
  // Optimistic: only checks that a bearer token is present. Verify it in the handler.
  if (!token?.startsWith("Bearer ")) {
    return Response.json({ success: false, message: "authentication required" }, { status: 401 });
  }
}

Background work with waitUntil

A NextFetchEvent is the second argument. Its waitUntil() keeps the invocation alive after the response has been sent, which is where audit logging and analytics belong. In the scratch app the response to GET /api/health came back in 2 ms while the audit line was written about 300 ms later:

import { NextResponse, type NextFetchEvent, type NextRequest } from "next/server";

export function proxy(request: NextRequest, event: NextFetchEvent) {
  const started = Date.now();
  // runs after the response has been sent; must not block it
  event.waitUntil(
    new Promise<void>((resolve) =>
      setTimeout(() => {
        console.log(`AUDIT ${request.method} ${request.nextUrl.pathname} after ${Date.now() - started}ms`);
        resolve();
      }, 300),
    ),
  );
  return NextResponse.next();
}

Node.js Runtime, the Deprecated Edge middleware.ts and the Codemod

The Proxy’s headline change in Next.js 16 is the runtime. Middleware ran on the Edge runtime, a restricted environment that supports only a subset of the Node.js APIs, so some npm packages (database drivers and parts of auth libraries among them) did not work in it. What the Proxy Should and Should Not Do

The official documentation is unusually blunt: the Proxy is meant to be used as a last resort, and the rename is partly meant to discourage reaching for it. The reasons are structural: it runs on every matching request (prefetches included), before the render, in a unit that is invoked separately from your render code and, in optimised cases, deployed to a CDN.

Good uses

  • Cheap redirects that need request data: locale detection from Accept-Language, a cookie, a legacy-path map.

  • Rewrites for experiments: A/B buckets in a cookie, as above, so that cached variants do not collide.

  • Optimistic checks: is there a session cookie at all, then send the visitor to /login. It centralises the redirect and protects static routes that share data between users, such as paywalled content.

  • Headers for every response: a nonce-based Content-Security-Policy, security headers, request IDs.

  • Refusing obviously invalid requests early (the 401 above), before any rendering work.

Things to avoid

  • Authorisation as the only line of defence. The Proxy is no full session management or authorisation layer. Verify the session where the data is read (a Data Access Layer used by Server Components, Route Handlers and Server Actions), and in every Server Function: the matcher is easy to get wrong, and the documentation shows how a matcher that skips a path silently skips the Server Function calls on it. In March 2025 the Middleware of Next.js 12 to 15 could be bypassed with an internal x-middleware-subrequest header (CVE-2025-29927, fixed in 15.2.3, 14.2.25, 13.5.9 and 12.3.5); any application that relied on Middleware alone was open. Keep the application patched and do not make the Proxy the only check.

  • Slow work. Database queries, calls to remote services and anything with high latency delay every request and every prefetch. fetch options such as cache, next.revalidate and next.tags have no effect in the Proxy.

  • Shared state. Do not rely on module globals or shared modules between the Proxy and the application: they run separately, and the Proxy may run on a CDN. Pass information through headers, cookies, rewrites, redirects or the URL.

  • Large request bodies. When a Proxy exists, Next.js buffers and clones each request body (10 MB by default) so that it can be read twice; the proxyClientMaxBodySize option, which the documentation labels experimental, sets the limit.

  • Business logic. Anything that could be an ordinary function in a Route Handler, a layout or a Server Action (redirect() after reading data) should be one. The self-hosting guide even suggests moving logic that needs all of Node.js to a layout, as a Server Component, and using redirects or rewrites with has and missing for cookie and header conditions.

  • Secrets in rewrite URLs and headers. Both can be visible to the client (x-middleware-rewrite).

Redirect Maps at Scale

A site migration can leave thousands of old URLs that must forward to new ones. redirects in next.config.ts is simple and fast, but it is part of the build, the rule list is held in memory by the server, and the guide warns that a platform may cap it (1,024 entries on Vercel). Past roughly a thousand rules, or when the list changes without a deploy, the guide’s advice is a redirect map handled by the Proxy, with two design questions: where the map lives and how to look it up cheaply.

1. Creating and storing the map. A redirect map is a key-value structure from old path to destination, kept in a JSON file or a store such as Redis or a KV service:

redirects/redirects.json
{
  "/catalogue/dune": { "destination": "/en/books/1", "permanent": true },
  "/catalogue/neuromancer": { "destination": "/en/books/2", "permanent": true },
  "/summer-sale": { "destination": "/en", "permanent": false }
}

2. Cheap lookup. Reading a large map on every request is slow. The documented technique puts a Bloom filter (a compact structure that answers "definitely not present" or "possibly present") in the Proxy, so that only the paths the filter reports as present trigger the real lookup in a Route Handler. The filter is generated at build time from the map; the example uses the bloom-filters package (3.0.4 was installed):

scripts/build-bloom.mjs
import { readFileSync, writeFileSync } from "node:fs";
import { ScalableBloomFilter } from "bloom-filters";

const redirects = JSON.parse(readFileSync("redirects/redirects.json", "utf8"));
const filter = new ScalableBloomFilter(); // default options; tune the error rate for big maps
for (const source of Object.keys(redirects)) filter.add(source);
writeFileSync("redirects/bloom-filter.json", JSON.stringify(filter.saveAsJSON()));
console.log(`${Object.keys(redirects).length} redirects in the filter`);
The redirect-map branch of proxy.ts
import { ScalableBloomFilter } from "bloom-filters";
import bloomJson from "@/redirects/bloom-filter.json";

type RedirectEntry = { destination: string; permanent: boolean };
const bloom = ScalableBloomFilter.fromJSON(bloomJson as any);

// inside proxy(request):
if (bloom.has(pathname)) {
  const lookup = withPath(request, "/api/redirects", "");
  lookup.searchParams.set("pathname", pathname);
  const res = await fetch(lookup);
  if (res.ok) {
    const entry: RedirectEntry = await res.json();
    const status = entry.permanent ? 308 : 307;
    return NextResponse.redirect(withPath(request, entry.destination, ""), status);
  }
}
app/api/redirects/route.ts
import type { NextRequest } from "next/server";
import redirects from "@/redirects/redirects.json";

type RedirectEntry = { destination: string; permanent: boolean };

export function GET(request: NextRequest) {
  const pathname = request.nextUrl.searchParams.get("pathname");
  if (!pathname) return new Response("Bad Request", { status: 400 });

  const entry = (redirects as Record<string, RedirectEntry>)[pathname];
  // The Bloom filter can report false positives, so a miss is normal here.
  if (!entry) return new Response(null, { status: 404 });
  return Response.json(entry);
}

Choices made in the scratch version, and why:

  • The matcher excludes api. The Proxy calls its own Route Handler with fetch; without the exclusion the lookup request would run through the Proxy again.

  • The handler answers 404 for a miss. The Bloom filter has false positives by design, so "no such redirect" is an expected answer; the official example returns 400 for it, which makes a harmless miss look like a client error in your logs.

  • withPath() instead of request.url. The first version used new URL("/api/redirects", request.nextUrl.origin) and new URL(entry.destination, request.url). With basePath: "/shop" the lookup went to the wrong URL and redirected to a destination without /shop; building both from nextUrl.clone() fixed it (/shop/catalogue/dune answered 308 location: /shop/en/books/1).

  • Same-origin fetch is a design smell. Behind a reverse proxy, request.nextUrl.origin may not be reachable from inside the container. The Proxy runs on Node.js in 16, so it can import a data client or a bigger lookup structure and skip the extra HTTP hop; the Route Handler pattern exists mainly because earlier Middleware ran on the Edge runtime and could not do that. Measure before choosing, and keep the Bloom filter if the map file is large.

  • The map is trusted data. The destinations in the example are written by you. If editors can add rows to a database-backed map, validate each destination (a relative path or an allowed host) when the row is saved, for the same open-redirect reason as in A safe ?from= parameter.

  • Rebuild the filter when the map changes. A stale filter hides new entries (it reports "absent"), so generate it in the build and deploy the map and the filter together.

Where the Books Are Outdated

The two books this section was prepared with (Packt, 2022 and Apress, 2023) are about the Pages Router, and searching both for redirects, rewrites and middleware finds none of the mechanisms on this page: neither teaches the redirects, rewrites or headers keys of next.config.js, and neither has a middleware or Proxy file (the word "middleware" appears only for Express-style, Redux and API-route "middlewares").

  • Redirects are written as Pages Router code. The 2022 book redirects inside API Routes with res.redirect(…​) and after sign-in with the client-side useRouter hook, and describes redirecting anonymous users away on the server before the page renders. The current equivalents are NextResponse.redirect() or redirect() in a Route Handler, redirect() in a Server Action or Server Component, and a Proxy for the early, optimistic version of the same check. A client-side hook (useAuth, useSession or router.push after render) protects nothing; the check must run on the server.

  • redirectToCheckout. Both books send customers to Stripe with the client-side stripe.redirectToCheckout, which Stripe has deprecated; the current pattern is to redirect to the Checkout Session’s url (a 303 from a Server Action or Route Handler, or embedded Checkout).

  • Internationalisation by redirect. The 2023 book localises with the i18n key in next.config.js and next-i18next, which the Pages Router supports and the App Router replaced with app/[locale] segments and a locale redirect in the Proxy, as in the example above.

  • Middleware. Anything the books or older tutorials call "middleware" or _middleware.js is now proxy.ts on Node.js; middleware.ts is deprecated (16.0), and the Edge runtime is no longer the default.

  • Redirect URLs built from the request. One book uses req.headers.origin to build redirect URLs: the header is caller-controlled, so the redirect target can be forged. Use a fixed base URL from configuration, a relative path, or an allow-list.

  • Status codes. Tutorials of that era talk about 301 and 302. next.config redirects answer 307 and 308 on purpose so the request method is preserved, and a Server Action form posted without JavaScript answers 303.
