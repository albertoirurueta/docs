Data Fetching

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when the facts and examples below were checked; the official documentation reports @doc-version 16.3.8), React 19.3.0, Node.js 20.9.0 or later and TypeScript 5.1 or later. Data fetching in the App Router is plain async/await inside Server Components, so most of this page is about the App Router; the Pages Router has its own data functions (getServerSideProps, getStaticProps), which are covered in a section of their own as the legacy path. Caching changes what a fetch does, so every example says which model it uses: the previous model (the default, in which fetch responses are not cached unless you ask) or the opt-in Cache Components model (cacheComponents: true, with the 'use cache' directive). Every example was built with next build, started with next start and exercised with curl or a headless Chrome on Next.js 16.3.8 and Node.js 24.16 on macOS, in a scratch copy of the Bookshelf — the catalogue of books, authors and reviews that this section grows — talking to a stand-in for the Bookshelf API that answers after 300 ms and counts the calls it receives, so the timings and call counts quoted below are measurements, not estimates. Each example is followed by the official page it derives from.

The page answers four questions in order: where does the fetch run (server, client, or both), when does it run (at build time, at request time, or in the browser), how many times does it run (memoization, caching, preloading) and how do the requests relate (sequential or parallel). It does not re-teach React’s use API or Suspense; read React Data Fetching for the client-side fundamentals and Streaming and Suspense for the delivery mechanism. The caching pages of this section (caching, and the Server Actions and Route Handlers pages that follow it) are only mentioned here in prose.

The Big Picture: Where, When and How Often

The most important change from the Pages Router is that there is no special function to fetch data. A Server Component is an async function, it await`s whatever it needs, and Next.js renders the result. The same is true of layouts and of `generateMetadata. Data fetching happens in one of five places.

The Bookshelf Scenario and the Test Rig

The examples fetch from a Bookshelf API that this site already builds three times: with FastAPI, with NestJS and with Django. In the scratch app that API is a small Node.js process that serves /books, /books/<id>, /books/<id>/reviews, /authors/<id> and a /graphql endpoint, waits 300 ms before answering and keeps a counter per route (GET /__hits). It returns the shape that the NestJS comparison page uses, extended with an author and a price. Swapping it for a real service changes one environment variable, BOOKSHELF_API_URL.

The types and the single module that knows the API address (lib/types.ts and lib/bookshelf.ts)
// lib/types.ts
export type Book = { id: number; title: string; authorId: number; priceCents: number };
export type Author = { id: number; name: string };
export type Review = { id: number; bookId: number; rating: number; text: string };

// lib/bookshelf.ts
import "server-only";
import type { Author, Book, Review } from "@/lib/types";

// Server-only configuration: never prefix with NEXT_PUBLIC_ and never log it.
const API_URL = process.env.BOOKSHELF_API_URL ?? "http://localhost:3611";

async function get<T>(path: string): Promise<T> {
  const res = await fetch(`${API_URL}${path}`);
  if (!res.ok) throw new Error(`Bookshelf API ${path} answered ${res.status}`);
  return (await res.json()) as T;
}

// Encode every value that goes into the upstream URL (never interpolate raw input).
export const getBooks = (q = "") => get<Book[]>(`/books?q=${encodeURIComponent(q)}`);
export const getBook = (id: number) => get<Book>(`/books/${id}`);
export const getAuthor = (id: number) => get<Author>(`/authors/${id}`);
export const getReviews = (bookId: number) => get<Review[]>(`/books/${bookId}/reviews`);

Source: Fetching Data: with the fetch API and Data security: Data Access Layer

Three details of this module recur on the rest of the page. import "server-only" makes the module fail the build if a Client Component ever imports it (shown below). process.env.BOOKSHELF_API_URL is read on the server, so the address can be an internal one such as http://api:8000 inside a Docker network, and the browser never learns it. Every dynamic value is passed through encodeURIComponent or is a number; the books this section consulted build upstream URLs by interpolating whatever the visitor typed, which lets a crafted value rewrite the path and query of the upstream request.

Because the shape differs, convert it once, at the edge of the app, and let the rest of the code use one Book type. The function below turns a Django REST framework page into the Book[] that the pages use; it is a pure function, so it is also the part to unit-test.

Mapping a Django REST framework page into the app’s own type (lib/bookshelf-django.ts)
// A pure mapping layer: the rest of the app only ever sees `Book`, whichever backend answers.
import type { Book } from "@/lib/types";

type DrfPage<T> = { count: number; next: string | null; previous: string | null; results: T[] };
type DjangoBook = { id: number; title: string; author_id: number; price_cents: number };

export function fromDjangoPage(page: DrfPage<DjangoBook>): Book[] {
  return page.results.map((b) => ({
    id: b.id,
    title: b.title,
    authorId: b.author_id,
    priceCents: b.price_cents,
  }));
}

Source: Fetching Data

Called with a one-element page it printed [{"id":1,"title":"Dune","authorId":1,"priceCents":999}]. Two rules keep the integration safe. Calls from the Next.js server to the API need no CORS configuration, because CORS is a browser mechanism; only direct calls from browser code do (see CORS). And the API must authorise every request itself: anyone who can reach its port can bypass the Next.js layer, as NestJS vs Next.js explains.

Credentials are forwarded from the server. The helper below reads a cookie and sends it as a bearer token, with a timeout so a hung upstream cannot hold the render forever. A wrong or missing token gives a signed-out page instead of a crash.

Forwarding a credential to the API from the server (lib/me.ts)
import "server-only";
import { cookies } from "next/headers";

// Forward the caller's credential to the API from the server; the browser never sees the upstream URL.
export async function getMe() {
  const token = (await cookies()).get("access_token")?.value;
  if (!token) return null;
  const res = await fetch(`${process.env.BOOKSHELF_API_URL ?? "http://localhost:3611"}/me`, {
    headers: { Authorization: `Bearer ${token}` },
    signal: AbortSignal.timeout(3000), // never wait forever for a slow upstream
  });
  if (res.status === 401) return null;
  if (!res.ok) throw new Error(`Bookshelf API /me answered ${res.status}`);
  return (await res.json()) as { name: string };
}
A page that uses it (app/df/me/page.tsx)
import { getMe } from "@/lib/me";

export default async function Page() {
  const me = await getMe(); // cookies() makes this route dynamic: rendered per request
  return <p>{me ? `Hello, ${me.name}` : "Signed out"}</p>;
}

Fetching in Server Components

A Server Component is fetched into by making it async. Anything that does asynchronous I/O works: the extended fetch, an ORM, a database client, the file system or another SDK.

With the fetch API

A Server Component that fetches (app/df/books/page.tsx)
import { connection } from "next/server";
import { getBooks } from "@/lib/bookshelf";

export default async function BooksPage({ searchParams }: PageProps<"/df/books">) {
  await connection(); // render per request; fetch alone is not cached but would be prerendered
  const { q } = await searchParams;
  const books = await getBooks(typeof q === "string" ? q : "");
  return (
    <ul>
      {books.map((b) => (
        <li key={b.id}>{b.title} ({(b.priceCents / 100).toFixed(2)})</li>
      ))}
    </ul>
  );
}
Observed
curl -s "localhost:3601/df/books?q=sol"   # <ul><li>Solaris (7.99)</li></ul>

Source: Fetching Data: with the fetch API

await connection() is there on purpose, and it is the first pitfall of this page. In the previous model a fetch without a cache option is not cached, but a route that uses no request-time API is still prerendered at next build, so the fetch runs once during the build and its result is baked into the HTML. Reading searchParams, cookies(), headers() or calling connection() before the fetch makes the route dynamic, so the fetch runs per request. Without that line the same page would have printed the build-time catalogue to every visitor, and a build with the API down would have failed. Three requests to /df/books made three calls to the API: the response is not cached.

With an ORM or a database client

Server Components run only on the server, so a query and its credentials never reach the client bundle. Drizzle, Prisma, Kysely or a raw driver are all used the same way as fetch: await them. The scratch app stands in for a database with an in-memory table; the shape of the code is what matters.

A database-style data function (lib/books-db.ts)
import "server-only";
import { cache } from "react";

// Stand-in for an ORM or database client (Drizzle, Prisma, pg ...).
const rows = [
  { id: 1, title: "Dune", priceCents: 999 },
  { id: 2, title: "Neuromancer", priceCents: 899 },
];

// cache() deduplicates calls with the same arguments during ONE render pass (one request).
export const getBookRow = cache(async (id: number) => {
  console.log(`DB query for book ${id}`); // visible once per request, not once per caller
  return rows.find((r) => r.id === id) ?? null;
});

Source: Fetching Data: with an ORM or database and Reusing data with React.cache

React.cache is explained in the memoization section below. Authentication and authorisation still apply: the query runs on the server, but nothing about a Server Component checks who is asking. The data security guide recommends a Data Access Layer, a server-only module that every Server Component, Route Handler and Server Action goes through, which checks the session, returns only the fields the UI needs and is the one place that talks to the database. The Data Access Layer also answers a worry that the consulted books raise, that a front-end framework should not touch the database: the recommendation is not to avoid server-side data access but to confine it to one audited module, or to a separate back end such as the Bookshelf APIs above.

Keeping server code out of the client: server-only and tainting

Server and Client Components run in separate module graphs, but a Client Component can still import a module, and an accidental import of a data module would drag server code towards the browser. import "server-only" turns that accident into a build error. With the data module above imported from a file that starts with 'use client', the build fails:

The same guide describes an opt-in extra layer, tainting (experimental_taintObjectReference and experimental_taintUniqueValue with experimental.taint: true), which makes React refuse to serialise a marked object or value to the client. Treat it as a second line behind filtering in the Data Access Layer, not as a replacement. Also remember what crosses the boundary: props that a Server Component passes to a Client Component, and the props that getServerSideProps returns in the Pages Router, are serialised into the HTML and visible to anyone.

Under Cache Components an uncached fetch outside a Suspense boundary is an error at build time rather than a silent slowdown. A page like this:

Under Cache Components, uncached data outside Suspense fails the build
import { getReviews } from "@/lib/bookshelf";

export default async function Page() {
  const reviews = await getReviews(1); // uncached fetch outside <Suspense>
  return <p>{reviews.length}</p>;
}
The build output with cacheComponents enabled
Error: Route "/df/cc-bad": Next.js encountered uncached or runtime data during prerendering.

`fetch(...)`, `cookies()`, `headers()`, `params`, `searchParams`, or `connection()` accessed outside of `<Suspense>`
prevents the route from being prerendered, blocking the page load and leading to a slower user experience.

Ways to fix this:
  - [stream] Provide a placeholder with `<Suspense fallback={...}>` around the data access
  - [cache] For uncached data (`fetch`, database calls): cache the access with `"use cache"`
  - [block] Set `export const instant = false` to allow a blocking route

Source: blocking-prerender-dynamic

The fix is one of the three bullets. This page is the shell-plus-hole version: cache what is stable, stream what is not.

The same data fetched under Cache Components (app/df/cc/page.tsx, cacheComponents: true)
import { Suspense } from "react";
import { cacheLife } from "next/cache";
import { getBooks, getReviews } from "@/lib/bookshelf";

// Cached: becomes part of the prerendered static shell and is revalidated in the background.
async function Catalogue() {
  "use cache";
  cacheLife("minutes");
  const books = await getBooks();
  return <ul>{books.map((b) => <li key={b.id}>{b.title}</li>)}</ul>;
}

// Not cached: an uncached fetch is "dynamic" under Cache Components and must be inside <Suspense>.
async function LatestReviews() {
  const reviews = await getReviews(1);
  return <p>{reviews.length} review(s) right now</p>;
}

export default function Page() {
  return (
    <main>
      <h1>Bookshelf</h1>
      <Catalogue />
      <Suspense fallback={<p>Loading reviews...</p>}>
        <LatestReviews />
      </Suspense>
    </main>
  );
}

Errors, missing data and loading states

A rejected promise in a Server Component is caught by the nearest error.js boundary; notFound() renders the nearest not-found.js; and loading.js wraps the page in a Suspense boundary so a navigation shows a fallback at once. Throw for non-ok responses instead of rendering garbage, as lib/bookshelf.ts does, and translate a 404 from the API into notFound() where the page can tell the difference. Two behaviours deserve care. A layout that reads uncached or runtime data does not fall back to a loading.js of the same segment; it blocks navigation until it has rendered, so put the Suspense boundary closest to the slow data. And notFound() thrown below a Suspense boundary arrives after the response status was sent, so the status stays 200; the details are on Streaming and Suspense.

Source: Fetching Data: streaming and loading.js

Sequential Versus Parallel Fetching

Two requests are sequential when the second cannot start until the first has finished, and parallel when both are in flight at the same time. Some requests really depend on each other: you need the book before you know the author’s ID. The mistake is to make independent requests wait for each other by writing them as consecutive `await`s.

The waterfall

Three awaits in a row (app/df/waterfall/[id]/page.tsx)
import { connection } from "next/server";
import { getAuthor, getBook, getReviews } from "@/lib/bookshelf";

export default async function Page({ params }: PageProps<"/df/waterfall/[id]">) {
  await connection();
  const { id } = await params;
  const book = await getBook(Number(id)); // 300 ms
  const author = await getAuthor(book.authorId); // +300 ms: genuinely depends on book
  const reviews = await getReviews(book.id); // +300 ms: does NOT depend on author, an avoidable wait
  return <h1>{book.title} by {author.name} ({reviews.length} reviews)</h1>;
}

Source: Fetching Data: parallel data fetching

The reviews do not need the author, yet they wait for it. Measured: 953 ms for the whole response, and the response cannot start before that, because the page awaits everything before it returns anything.

Parallel: start early, await late

Call the functions first, without await, so every request is in flight, then await the promises where their values are needed. Promise.all is the shorter form when you need all of them at the same point.

Start the independent request first, await it last (app/df/parallel/[id]/page.tsx)
import { connection } from "next/server";
import { getAuthor, getBook, getReviews } from "@/lib/bookshelf";

export default async function Page({ params }: PageProps<"/df/parallel/[id]">) {
  await connection();
  const { id } = await params;
  // Start every request that does not depend on another one, then await late.
  const bookPromise = getBook(Number(id));
  const reviewsPromise = getReviews(Number(id));
  const book = await bookPromise;
  const author = await getAuthor(book.authorId); // runs while reviews are already in flight
  const reviews = await reviewsPromise;
  return <h1>{book.title} by {author.name} ({reviews.length} reviews)</h1>;
}

Source: Fetching Data: parallel data fetching

Measured: 611 ms, two thirds of the waterfall; the only wait left is the real dependency. Two things to know. Promise.all rejects as soon as one promise rejects, which fails the whole page; use Promise.allSettled when a failed part may be omitted. And layouts and pages of one route already render in parallel, so a layout and a page that each fetch do not wait for each other, unlike two awaits inside one component.

Streaming instead of waiting

Parallelism shortens the total; streaming lets the browser see something earlier. Await only what the first paint needs, and put the rest behind <Suspense>. Each boundary is a component that fetches for itself.

The shell waits for the book only (app/df/streamed/[id]/page.tsx)
import { Suspense } from "react";
import { connection } from "next/server";
import { getAuthor, getBook, getReviews } from "@/lib/bookshelf";

export default async function Page({ params }: PageProps<"/df/streamed/[id]">) {
  await connection();
  const { id } = await params;
  const book = await getBook(Number(id)); // the only thing the shell waits for
  return (
    <main>
      <h1>{book.title}</h1>
      <Suspense fallback={<p>Loading author...</p>}>
        <Author authorId={book.authorId} />
      </Suspense>
      <Suspense fallback={<p>Loading reviews...</p>}>
        <Reviews bookId={book.id} />
      </Suspense>
    </main>
  );
}

async function Author({ authorId }: { authorId: number }) {
  const author = await getAuthor(authorId);
  return <p>by {author.name}</p>;
}

async function Reviews({ bookId }: { bookId: number }) {
  const reviews = await getReviews(bookId);
  return <p>{reviews.length} review(s)</p>;
}

Both holes start only after the shell’s data is in, because they are children of a component that awaited the book; that is the price of keeping the code local. When the book request itself is the bottleneck, start it earlier or cache it. Bots and crawlers are an exception to streaming: Next.js waits for the data and sends the whole page to them, so search-engine output is not affected by where you put the boundaries.

Preloading

A request starts late when its component only renders after other blocking work, even though its input has been known for a while. Preloading means starting the request early without waiting for it, then reading the same request in the component that needs it. It needs one thing: the data function must deduplicate identical calls, so the second call joins the first. A fetch does that by itself (memoization, next section); a database function needs React.cache; under Cache Components a 'use cache' function does (or 'use cache: private' when it reads cookies() or headers()).

A component and its preload function, side by side (app/df/preload/[id]/item.tsx)
import { getBook } from "@/lib/bookshelf";

export const preload = (id: number) => {
  void getBook(id); // start the request, do not await it
};

export default async function Item({ id }: { id: number }) {
  const book = await getBook(id); // identical fetch call: reuses the request preload() started
  return <h1>{book.title}</h1>;
}
Calling preload before another blocking request (app/df/preload/[id]/page.tsx)
import { connection } from "next/server";
import Item, { preload } from "./item";

async function checkIsAvailable(id: number) {
  await new Promise((r) => setTimeout(r, 300)); // another blocking dependency (stock service)
  return id < 100;
}

export default async function Page({ params, searchParams }: PageProps<"/df/preload/[id]">) {
  await connection();
  const [{ id }, { early }] = await Promise.all([params, searchParams]);
  const n = Number(id);
  if (early === "1") preload(n); // the scratch page toggles this to compare the two timings
  const isAvailable = await checkIsAvailable(n);
  return isAvailable ? <Item id={n} /> : null;
}

Source: fetch: memoization

The limits of memoization are the source of most surprises.

  • It is per request. Neither fetch memoization nor React.cache shares anything between two visitors. Persistent reuse is caching, a different feature.

  • Arguments are compared by identity. React.cache compares its arguments with Object.is, so a fresh object literal on every call is a different key each time and defeats it; pass primitives (an ID) instead.

  • It needs the same call. fetch is memoized for GET requests with the same URL and options only; a POST, a different header or a different URL string is a new request.

  • It can be turned off. Passing an AbortController signal to fetch opts that call out. Two identical calls with a signal reached the API twice ({"GET /books/1":2}), while the same two calls without one reached it once.

  • It does not exist in Route Handlers. They are not part of the React component tree, so two fetch calls in a handler are two requests.

  • It is not the Data Cache. In the previous model fetch(url, { next: { revalidate: 60, tags: ["books"] } }) stores the response across requests: three requests to the page that used it made one API call ({"GET /books":1}), while three requests to the page without the option made three.

Passing Promises to Client Components with use()

Sometimes a Client Component needs data that a Server Component can start but that the page should not wait for. The Server Component creates the promise without await and passes it as a prop; the Client Component reads it with React’s use() inside a <Suspense> boundary. The request begins on the server, as early as possible, and the result streams into the page.

Start the promise on the server, do not await it (app/df/use/page.tsx)
import { Suspense } from "react";
import { connection } from "next/server";
import { getBook, getReviews } from "@/lib/bookshelf";
import Reviews from "./reviews";

export default async function Page() {
  await connection();
  const book = await getBook(1); // awaited: the title is in the first chunk
  const reviews = getReviews(book.id); // NOT awaited: a promise crosses the boundary
  return (
    <main>
      <h1>{book.title}</h1>
      <Suspense fallback={<p>Loading reviews...</p>}>
        <Reviews reviews={reviews} />
      </Suspense>
    </main>
  );
}
Read it in the Client Component (app/df/use/reviews.tsx)

import type { Review } from "@/lib/types";

  const all = use(reviews); // suspends until the server promise resolves

Rules and limits worth knowing:

  • The promise must come from a Server Component (or from a cache or library that is Suspense-compatible). A promise created while a Client Component renders is a new promise on every render, so it never settles from React’s point of view.

  • A promise from a Server Component is serialised across the boundary; the value it resolves to must itself be serialisable, which excludes functions, class instances and the like.

  • await in the Server Component when the data is needed to render the server part, and use() in the Client Component when only the client part needs it; React documents the trade-off under "resolve a promise in a Server or Client Component".

  • To share one promise with many Client Components, provide it through a context provider rather than passing it down as a prop; the SPA guide has the pattern.

  • A rejected promise is an error: put an error.js or an error boundary around it.

  • Under Cache Components the Server Component that starts the promise runs inside the shell or a Suspense hole like any other, so the same rules about request-time data apply.

Three caches that must agree

When a client library and Next.js caching are both in use, up to three layers hold related data: the Next.js server cache, the Next.js client cache of route payloads, and the library cache under its key. Each has its own freshness policy and they do not need matching durations, but the identity (key or tag) and the invalidation after a mutation must be coordinated. After a mutation, invalidate the cached server read that provided the initial data and update or invalidate the library cache: updateTag(tag) when a Server Action must make its update visible at once, revalidateTag(tag, 'max') when stale data is acceptable meanwhile, and revalidateTag(tag, { expire: 0 }) for a webhook that needs immediate expiry. An optimistic update must restore the previous browser value when the write fails. If the server read is not cached there is nothing on the server to invalidate. The mutation side is on the Server Actions page of this section (not written yet at the time of writing).

A plain effect, written correctly

Without a library, a Client Component can fetch in an effect. It is the most error-prone option, and the effect callback itself must not be async (an async callback returns a promise where React expects a cleanup function), every request needs to be cancellable, and errors and non-ok responses need handling. The version below passes all three.

Fetching in an effect with abort and error handling (app/df/effect/book-effect.tsx)
"use client";
import { useEffect, useState } from "react";
import type { Book } from "@/lib/types";

export function BookEffect({ q }: { q: string }) {
  const [books, setBooks] = useState<Book[] | null>(null);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const controller = new AbortController();
    // The effect callback itself is not async: it returns the cleanup function.
    async function load() {
      try {
        const res = await fetch(`/api/books?q=${encodeURIComponent(q)}`, { signal: controller.signal });
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        setBooks(await res.json());
      } catch (e) {
        if (e instanceof DOMException && e.name === "AbortError") return; // superseded or unmounted
        setError(e instanceof Error ? e.message : "unknown error");
      }
    }
    load();
    return () => controller.abort();
  }, [q]);

  if (error) return <p>Error: {error}</p>;
  if (!books) return <p>Loading...</p>;
  return <ul>{books.map((b) => <li key={b.id}>{b.title}</li>)}</ul>;
}

Source: React: fetching data with Effects

The server-rendered HTML contains only "Loading…​" (effects do not run on the server), and the browser then shows the three books after one request to /api/books. This is the weakest option for a page that has any other choice: the data is not in the HTML, the request starts only after the JavaScript has loaded and hydrated, and nested components that each do this form a waterfall. See Client-Side Rendering for the cost of that waterfall.

Plain fetch from a Server Component

A GraphQL query from the server with no client library
// lib/bookshelf-graphql.ts
import "server-only";

export async function graphql<T>(query: string, variables: Record<string, unknown> = {}): Promise<T> {
  const res = await fetch(process.env.BOOKSHELF_GRAPHQL_URL ?? "http://localhost:3611/graphql", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ query, variables }),
  });
  if (!res.ok) throw new Error(`GraphQL endpoint answered ${res.status}`);
  const body = (await res.json()) as { data?: T; errors?: { message: string }[] };
  if (body.errors?.length) throw new Error(body.errors[0].message); // GraphQL errors come with HTTP 200
  return body.data as T;
}

Source: Fetching Data: with the fetch API

A POST is not memoized and is not cached by default, unlike a GET; opt in with cache: 'force-cache' or 'use cache' if the query is cacheable, or use persisted queries with GET. The check of errors matters because GraphQL reports resolver errors in a 200 response.

  // Browser requests go to the BFF or to a CORS-enabled API; SSR needs an absolute URL.
  const link = new HttpLink({ uri: process.env.NEXT_PUBLIC_GRAPHQL_URL ?? "http://localhost:3611/graphql" });
  return new ApolloClient({ cache: new InMemoryCache(), link });
}

export function ApolloWrapper({ children }: React.PropsWithChildren) {
  return <ApolloNextAppProvider makeClient={makeClient}>{children}</ApolloNextAppProvider>;
}

// app/df/apollo/client-books.tsx
"use client";
import { useSuspenseQuery } from "@apollo/client/react";
import { BOOKS } from "@/lib/queries";

type Data = { books: { id: string; title: string; author: { id: string; name: string } }[] };

// app/df/apollo/page.tsx
import { Suspense } from "react";
import { connection } from "next/server";
import { PreloadQuery, query } from "@/lib/apollo";
import { BOOKS } from "@/lib/queries";
import { ClientBooks } from "./client-books";

export default async function Page() {
  await connection();
  const { data } = await query<{ books: { id: string; title: string }[] }>({ query: BOOKS });
  return (
    <main>
      <p>Server Component sees {data!.books.length} books</p>
      {/* Separate client instance: the data is seeded into the browser cache, not shared with RSC */}
      <PreloadQuery query={BOOKS}>
        <Suspense fallback={<p>Loading...</p>}>
          <ClientBooks />
        </Suspense>
      </PreloadQuery>
    </main>
  );
}

Points to remember, all from the integration’s documentation. Data fetched through PreloadQuery is client data and should not be read in Server Components; the integration deliberately uses a separate client so the two cannot mix, and RSC queries do not update in the browser while SSR/client queries can. Prefer the suspense hooks (useSuspenseQuery, useFragment) so server rendering streams; place Suspense boundaries at meaningful points; and when a query uses @defer, use PreloadQuery with useReadQuery, or the integration’s multipart links, because useSuspenseQuery only suspends until the first part arrives. Pass Next.js-specific fetch options through fetchOptions on the HttpLink or per query through context.fetchOptions (for example next: { revalidate: 60 }); that option does not work with export const dynamic = "force-static".

The Pages Router Data Functions (Legacy)

The Pages Router fetches data in functions that a page module exports, which Next.js runs on the server and whose result it hands to the page as props. They still work in Next.js 16.3 and are the right tool for an existing Pages Router application; for new work the App Router is the recommended path. A project can contain both a pages/ and an app/ directory, as the scratch app does.

getServerSideProps: per request (pages/legacy.tsx)
import type { GetServerSideProps, InferGetServerSidePropsType } from "next";

type Book = { id: number; title: string };

export const getServerSideProps = (async ({ query }) => {
  const q = typeof query.q === "string" ? query.q : "";
  const res = await fetch(`${process.env.BOOKSHELF_API_URL ?? "http://localhost:3611"}/books?q=${encodeURIComponent(q)}`);
  if (!res.ok) throw new Error(`Bookshelf API answered ${res.status}`);
  const books: Book[] = await res.json();
  return { props: { books } }; // props are serialized into the HTML (__NEXT_DATA__): nothing secret here
}) satisfies GetServerSideProps<{ books: Book[] }>;

export default function Legacy({ books }: InferGetServerSidePropsType<typeof getServerSideProps>) {
  return <ul>{books.map((b) => <li key={b.id}>{b.title}</li>)}</ul>;
}
getStaticProps with revalidation: at build time, then incrementally (pages/legacy-static.tsx)
import type { GetStaticProps, InferGetStaticPropsType } from "next";

type Book = { id: number; title: string };

export const getStaticProps = (async () => {
  const res = await fetch(`${process.env.BOOKSHELF_API_URL ?? "http://localhost:3611"}/books`);
  const books: Book[] = await res.json();
  return { props: { books }, revalidate: 60 }; // ISR: regenerate at most once a minute
}) satisfies GetStaticProps<{ books: Book[] }>;

export default function LegacyStatic({ books }: InferGetStaticPropsType<typeof getStaticProps>) {
  return <ul>{books.map((b) => <li key={b.id}>{b.title}</li>)}</ul>;
}

Pages Router behaviours to remember: getServerSideProps can only be exported from a page, so a component deeper in the tree cannot fetch for itself and data has to be passed down as props; it returns serialisable JSON that anyone can read in the HTML, so no secrets in props; a thrown error renders pages/500; you can set Cache-Control headers (for example public, s-maxage=10, stale-while-revalidate=59) from inside it to cache dynamic responses at a CDN, though getStaticProps with revalidate is usually the better fit; and during client-side navigation Next.js asks the server to run getServerSideProps. You never need an API route to feed getServerSideProps from your own page: call the database, the CMS or the back end directly from the function.

Table 10. Common data fetching mistakes
Mistake Symptom Fix

A dynamic page without a request-time API, in the previous model

Every visitor sees the data from build time; the build fails if the API is down

Read searchParams, cookies(), headers() or call connection(); or set cache: 'no-store'

Awaiting independent requests one after the other

Time to first byte is the sum of the requests

Start early and await late, or Promise.all, or stream with Suspense

Reading request data in a layout that has a loading.js sibling

Navigation blocks instead of showing the fallback

Put a <Suspense> boundary around the slow part, or fetch in the page

Importing a data module in a Client Component

Build error (with server-only) or server code in the browser bundle

import "server-only" in every data module

Passing a whole database row to a Client Component

Private fields appear in the HTML and RSC payload

Return only the fields the UI needs from the Data Access Layer

A helper in a 'use client' file called from a Server Component

"Attempted to call …​ from the server but …​ is on the client"

Keep shared helpers in a module without 'use client'

Fresh object arguments to a React.cache function

The function runs again and again

Pass primitives such as an ID

Expecting memoization in a Route Handler

The same request is made twice

Share through a function that you call once, or cache with 'use cache'

What Changed Recently

Table 11. Data fetching changes by version
Version Change

13.0 (2022)

The App Router and the extended fetch arrive; fetch is cached by default and Server Components can be async.

14

Server Actions stable; the fetch and GET Route Handler defaults are still "cached".

15.0 (2024-10-21)

fetch requests are no longer cached by default (opt in with cache: 'force-cache', or fetchCache = 'default-cache'); GET Route Handlers are no longer cached by default; params, searchParams, cookies() and headers() become asynchronous.

16.0 (2025-10-21)

Synchronous access to params, searchParams, cookies() and headers() is removed; Cache Components arrives as the opt-in successor of experimental.ppr, dynamicIO and useCache, with 'use cache', cacheLife and cacheTag stable; revalidateTag(tag, profile), updateTag and refresh are new.

16.2 (2026-03-18)

Server Function calls are logged in development.

16.3 (2026-08-03)

Instant Navigations and partial prefetching (opt-in). The 16.3 documentation carries the client-side fetching guides for SWR and TanStack Query, which seed the library from a Server Component, and the preloading section of the Fetching Data page.

Ecosystem

Apollo Client 4 with @apollo/client-integration-nextjs; TanStack Query 5.40.0+ can dehydrate pending queries; SWR 2.3.0+ accepts promises as a fallback with React 19.
