Hydration is the step that turns server-rendered HTML into a running React application: the page is already on the screen, React renders the same components again in the browser, checks that the result matches what is in the DOM, and attaches the event handlers and state. It is the reason a server-rendered page can look finished and still ignore a click, and the reason a harmless-looking new Date().toLocaleDateString() can throw away the server’s work. This is the most detailed page of the rendering chapters. It explains the mechanism first (what is in the response, what the browser does with it, why only the first load hydrates), then the order in which parts of the page hydrate, then what hydration costs and how to make it cheaper, then the long list of ways it fails with a reproduction and a fix for each, and finally the surrounding topics: Partial Prerendering, data-cache hydration, the Pages Router, and how Angular and Vue handle the same problem.

It builds on Rendering Fundamentals (the rendering spectrum), Server and Client Components (which components exist in the browser at all), Server-Side Rendering (how the HTML and the payload are produced) and Streaming and Suspense (how the response is cut into chunks). The sibling pages on client-side rendering, static site generation, incremental static regeneration and Partial Prerendering with Cache Components are written alongside this one; where they own a topic this page only names it. For the React primitives underneath, see Server Rendering, SSG and React Server Components and Code Splitting and Suspense.

What Hydration Is and Why Server HTML Needs It

Server-rendered HTML is a snapshot. The browser can paint it, search engines can read it, and links in it work as ordinary links, but nothing in it reacts to the user in the way a React component does: there are no event handlers attached to the buttons, no state behind the inputs, no effects have run. Making the snapshot live has two possible strategies:

  • Throw the HTML away and render everything again in the browser from scratch (what client-side rendering does). The user sees a blank or loading state until the JavaScript has run, and the server’s work was wasted.

  • Keep the HTML, render the same tree again in the browser without creating DOM nodes, walk the existing nodes in step with it, and adopt them: connect each React element to the node that is already there, then attach the event handlers. This is hydration, and it is what hydrateRoot does.

Hydration is therefore not a second rendering of the page for the user’s benefit. It is a reconciliation of two trees, the one React would build now and the one the server already built, with the DOM as the thing in between. That is why it has a hard requirement: the first render in the browser must produce the same output as the server render. If it does not, React cannot adopt the DOM, and it has to throw part of it away (see What React Does with a Mismatch).

Table 1. The vocabulary of this page
Term Meaning

Prerender, SSR, SSG

Producing HTML on the server, at request time (SSR) or at build time (SSG). Both produce the HTML that gets hydrated.

RSC payload

The serialized result of the Server Components, sent next to the HTML. It tells the browser what the tree is, where the Client Components go and which props they receive.

Hydration

React in the browser adopting the server-rendered DOM and attaching event handlers (hydrateRoot).

Selective hydration

Hydrating each <Suspense> boundary separately, in a priority order that follows what the user is doing, instead of the whole page in one block.

Mismatch (hydration error)

The browser’s first render differs from the server HTML. React reports it and regenerates part of the tree on the client.

Recoverable error

React’s name for an error that it handled by falling back to client rendering; reported through onRecoverableError, not thrown at the user.

Interactivity gap

The time between the first paint of the server HTML and the moment the page reacts to input: JavaScript download, parse and hydration.

Dehydrated boundary

A Suspense boundary whose HTML is in the page but which React has not hydrated yet.

How Next.js Hydrates

The Next.js documentation describes the first load of an App Router page in three inputs and one job each: the HTML is used to show a fast non-interactive preview, the RSC payload is used to reconcile the Server and Client Component trees, and the JavaScript is used to hydrate the Client Components and make the application interactive. This section opens each of the three, using the scratch Bookshelf.

What the browser does with them

When the scripts have loaded, Next.js starts React on the document with hydrateRoot. In this order:

  1. The browser has already painted the HTML. That is the first paint; the page is not interactive.

  2. The runtime reads the payload from self.__next_f and rebuilds the React element tree from it. For Server Components this is pure data: nothing runs. For each client reference, it loads the module and renders the Client Component in the browser with the props from the payload.

  3. React compares the output of that render with the existing DOM node by node. Where they agree, React adopts the node (it records that this fiber owns this DOM element) and attaches handlers. Where they disagree, you have a hydration error.

  4. Effects run (useEffect), the router takes over link clicks, and the page is interactive.

The consequence that surprises most people the first time is in step 2: a Server Component is not re-rendered during hydration, only compared. A new Date() in a Server Component evaluates once, on the server, and the browser reads the result from the payload, so it can never disagree with itself. A new Date() in a Client Component evaluates twice, once for the server HTML and once in the browser, and the two answers will rarely be equal. This is why almost every hydration bug in an App Router application lives in a Client Component, and why the cheapest fix is often to move the volatile code to a Server Component.

Document-level hydration

In the App Router the root layout renders <html> and <body>, so React hydrates the whole document, not a div#root. Two consequences are worth knowing before the catalogue. Attributes that something else adds to <html> or <body> (a theme script, a browser extension) are compared like any other attribute, so they produce a warning in development unless the element has suppressHydrationWarning (the catalogue below shows that the warning disappears with it). Extra elements are treated differently, and less uniformly than the React 19 announcement suggests. The announcement says that unexpected tags in <head> and <body> are skipped. In the scratch app (production build), an injected <style>, <link> or <script> placed in <head> or directly in <body> caused no error, but an injected <div> placed directly in <body>, or any element inside <main>, produced Minified React error 418. Count on the tolerance for stylesheets and scripts, not for visible elements.

Why Later Navigations Do Not Hydrate

Hydration happens once per document: when the browser loads the HTML of a page (a first visit, a reload, a link to another site and back, a plain <a> to a route of the app). It does not happen when you move between routes with <Link>, router.push or the back button. The Next.js router already owns the document at that point, and it navigates by fetching an RSC payload for the new route and asking React to render it into the existing tree. There is no server HTML for the new page, so there is nothing to compare and no hydration; the Client Components of the new page are rendered in the browser, for the first time, from the payload.

This was measured on the scratch app (production build) with a home page that links to /about, a prerendered route with the Client Component from above:

Two practical rules follow. Anything you measure on the first load (a hydration error, a mismatch, a flash) is a first-load problem. If a component only misbehaves after a reload, it is a hydration bug; if it only misbehaves after a client navigation, it is not, and the cause is somewhere else (state, caching, a Server Component that is not re-rendered). And the cost of hydration is paid once, which is why bundle size matters most for the landing pages of an application and much less for pages that are usually reached from inside it.

Selective and Progressive Hydration

React 18 changed hydration from "all or nothing" to "boundary by boundary". Before it, hydrate() had to render and hydrate the whole tree in one block, and it could start only when all the JavaScript of the page had loaded. A slow part, such as a heavy widget, delayed everything. With hydrateRoot and <Suspense>, each Suspense boundary is a unit that React can hydrate separately, later, or first. The React working group describes three consequences:

  • Streaming HTML: the server can send the shell now and a boundary’s HTML later.

  • Selective hydration: React does not have to wait for the slow part’s code to hydrate the rest of the page.

  • Interaction priority: React hydrates first the boundary the user is interacting with.

Hydration starts as early as possible and is done in time slices, so that the main thread can still respond; the boundaries are hydrated in tree order unless the user’s input changes the order.

The first experiment shows that a boundary does not have to wait for another one. The page has two Suspense boundaries, each with a Client Component loaded with next/dynamic so that each lives in its own JavaScript chunk (with ssr left at its default, both are server-rendered):

Experiment 2: interaction priority

The second experiment shows the order. The page has 200 sibling Suspense boundaries, each containing a Client Component whose render takes about 8 ms (a busy loop standing in for a big list, a chart or an expensive formatter), so hydrating all of them takes more than a second and a half. The test waits until hydration has started, then clicks the button of boundary number 150:

200 boundaries with an expensive render each
// components/sel/busy-item.tsx
"use client";

import { useEffect, useState } from "react";
import { mark } from "./log"; // pushes [name, performance.now()] to window.__h in the browser

function busy(ms: number) {
  const end = performance.now() + ms;
  while (performance.now() < end) {}
}

export function BusyItem({ i }: { i: number }) {
  mark(`item ${i} render`);
  busy(8); // stands in for an expensive render
  const [n, setN] = useState(0);
  useEffect(() => mark(`item ${i} hydrated`), [i]);
  return (
    <li>
      <button data-testid={`b${i}`} onClick={() => { setN(n + 1); mark(`item ${i} click handled`); }}>
        Item {i}: {n}
      </button>
    </li>
  );
}

What to take from the two experiments:

  • Wrap independent, expensive or late-arriving parts in <Suspense>. A boundary is the unit of selective hydration, of streaming, and of mismatch recovery (see What React Does with a Mismatch). loading.js creates one around a whole segment, so a route with one is already split from its layout.

  • Selective hydration helps with CPU time and with arrival order. It does not remove the need for the code. A boundary that is waiting for a chunk is dead until the chunk arrives.

  • Granularity matters. A boundary around everything gives all-or-nothing hydration again; a boundary around every button is overhead. Put boundaries where the content is independent: a review list, a recommendation strip, a chart.

  • Interaction priority applies to discrete user input. Do not design around it for correctness; design the page so that the order does not matter.

Streamed boundaries hydrate when they arrive

Everything above applied to boundaries whose HTML was in the first chunk. A boundary that suspends on the server is sent later in the same response: first as a fallback, then as a hidden element plus a tiny inline script that swaps it in place (the streaming page shows the bytes). React treats the swapped-in HTML as a new dehydrated boundary and hydrates it when its code is loaded and the main thread is free, so late content hydrates later than early content by design. The PPR measurement in Hydration under Partial Prerendering shows this with timestamps.

Source: Streaming.

<Link> Prefetching Waits for Hydration

<Link> is a Client Component. Its prefetching logic (watch the viewport, call the router’s prefetch) runs in the browser, so it cannot start before <Link> itself has been hydrated. On the first visit, that means a link in the server HTML works as a plain <a> (a click is a full page load) until hydration has reached it, and the router’s prefetch does not begin before then. The Next.js documentation lists this under "Hydration not completed" and recommends reducing the bundle size and moving logic from the client to the server.

The effect was measured on the scratch app (production build): a home page with two `<Link>`s, with the JavaScript held back by the test harness for 1.5 seconds:

The Cost of Hydration

Hydration has no network cost of its own, and that is exactly why it is easy to overlook. The data is already in the HTML; what the user pays is JavaScript: the bytes to download, the time to parse and compile them, and the time to render every Client Component again in the browser. The page looks finished and is unresponsive for that long. The three metrics that expose it are:

  • Total Blocking Time (TBT), the lab metric that sums the long tasks between first paint and the moment the main thread is idle. web.dev calls it a lab proxy for INP.

  • Interaction to Next Paint (INP), the field metric: the delay between a user’s input and the next paint. A good INP is 200 ms or less. A click during the hydration gap is the worst case.

  • Time to Interactive (TTI), the older lab metric that the books use for the same idea: when the page reliably responds.

The render cost during hydration

Bytes are only half. The second experiment of Selective and Progressive Hydration measured render cost directly: 200 Client Components that each take 8 ms to render cost about 1.6 seconds of main-thread time during hydration, split into slices, but a total all the same. A real component does not busy-wait, but a formatter, a large map, a derived list or a chart library can easily reach a few milliseconds each. The same page rendered as Server Components would cost the browser no render time at all, because the work was done on the server and the browser compared the output with the payload.

How to reduce hydration cost

The levers, in the order in which they usually pay off:

  1. Make it a Server Component. Everything that does not need state, effects, event handlers or browser APIs should stay on the server. This is the default of the App Router, so the work is in not adding "use client" out of habit.

  2. Push "use client" to the leaves. Put the directive on the search box, not on the layout that contains it. The documentation’s example is a layout with static markup and one interactive search bar: only the search bar is a Client Component.

  3. Compose instead of converting. A Client Component can receive Server Components as children or other props (variant 3 above). The state lives in the client wrapper; the content stays on the server and costs nothing to hydrate. The reverse (importing a Server Component into a Client file) is not possible, because the import would pull it into the browser bundle.

  4. Keep heavy libraries out of the client graph. Validation, markdown rendering, date and number formatting, syntax highlighting and syncing a database client belong on the server. A server-only import marks modules that must never reach the browser.

  5. Load late what is not needed at first paint. next/dynamic or React.lazy with <Suspense> split a Client Component into its own chunk, loaded only when it renders; ssr: false skips its server HTML (see The Fix Toolbox for the trade-offs of skipping it). A modal, an editor or a chart that opens on click should not be in the first bundle.

  6. Use Suspense boundaries around independent parts so that they hydrate on their own schedule (see Selective and Progressive Hydration).

  7. Measure the bundle. Next.js 16.1 added next experimental-analyze for Turbopack (still labelled experimental), and @next/bundle-analyzer remains for webpack builds only. The useReportWebVitals hook (from next/web-vitals) reports LCP, INP, CLS and the others from real users.

  8. Be careful with third parties. Analytics and tag-manager scripts run on the main thread too; the Google Tag Manager and Google Analytics components of @next/third-parties fetch their scripts after hydration by default, so the page’s own hydration is not delayed.

  9. Consider the React Compiler (reactCompiler, stable and off by default in Next.js 16) for Client Components that re-render more than they need to. It reduces update cost; it does not remove the first hydration render.

Hydration Errors

A hydration error is React reporting that the first render in the browser disagrees with the server HTML. It is the most common first-week problem with any server-rendered React application, and one of the least understood, because the message names a symptom (text did not match) and not the cause. This section explains how the report looks in development and in production, what React does with the tree afterwards, and how to read the diff. The next section is the catalogue of causes, each with a reproduction that was run and a fix that was run.

What React Does with a Mismatch

When the first client render disagrees with the HTML, React cannot adopt the server DOM below the point of difference: the DOM nodes it would attach to are not the nodes the component describes. The Next.js preventing-flash guide describes the recovery: React falls back to client rendering from the nearest error or Suspense boundary. It discards the server DOM of that boundary (or of the whole root if there is none), renders the tree again in the browser and reports the error as recoverable.

The effect is measurable, and it is not cosmetic. The experiment uses a page with two inputs, one outside and one inside a section, and a Client Component that renders Date.now() (a guaranteed mismatch). The test script holds the JavaScript back, types into both inputs while the page is still plain HTML, marks the input nodes, then lets the JavaScript load and hydrate. Three variants: no mismatch, a mismatch with no Suspense boundary, and a mismatch inside a Suspense boundary.

A page to see the blast radius of a mismatch (production build)
// app/scope/[mode]/page.tsx (Server Component, rendered per request)
import { Suspense } from "react";
import { connection } from "next/server";
import { Clock } from "@/components/bad/clock"; // "use client", renders Date.now()

function Search({ id }: { id: string }) {
  return <input data-testid={id} placeholder={id} />;
}

export default async function Page({ params }: PageProps<"/scope/[mode]">) {
  await connection();

  return (
    <main>

        <section>
          <Search id="inside" />
          {mode === "ok" ? null : <Clock />}
        </section>
      )}
    </main>
  );
}
// components/bad/clock.tsx
"use client";

The first line is the baseline: when nothing mismatches, the text the user typed before hydration is preserved, and the DOM nodes are the very same ones (hydration adopts them). The second line is the disaster: one volatile Date.now() anywhere in the page, outside any Suspense boundary, made React regenerate the whole document, and both inputs lost their text and their DOM nodes. The third is the mitigation: with a Suspense boundary around the section, the input outside kept both, and only the boundary was redone. The consequences in practice:

  • Lost input and focus. Whatever the user did before hydration inside the regenerated region is gone: typed text, focus, selection, scroll position of inner containers, an open <details>.

  • Wasted work and a flash. The HTML the server produced, and the user already saw, is replaced; images may reload and layout may shift.

  • Slower hydration. Rendering twice is the opposite of what server rendering was for.

  • Wrong handlers in the worst case. The React documentation warns that in the worst case event handlers can get attached to the wrong elements, because attribute differences are not patched.

  • A Suspense or error boundary limits the blast radius, but it is a damage limiter, not a fix. Fix the cause.

1. Invalid HTML nesting

Reproduction. HTML has rules about what can contain what: a <p> cannot contain a <div>, an <a> cannot contain another <a>, a <table> cannot have <tr> as a direct child. React does not enforce them when it renders to a string, so the server happily writes the invalid markup. The browser’s HTML parser then repairs it while building the DOM, and the DOM that results is not the tree React expects.

Three invalid nestings (Server Components; this is not a client-only problem)
// components/bad/nesting.tsx
export function Nested() {
  return (
    <p data-testid="nest">
      Book details
      <div>Dune, by Frank Herbert</div>
    </p>
  );
}

// components/bad/nesting-a.tsx
export function NestedLinks() {
  return (
    <a href="/books/1" data-testid="outer">
      Dune <a href="/authors/1">Frank Herbert</a>
    </a>
  );
}

// components/bad/table.tsx
export function Prices() {
  return (
    <table data-testid="prices">
      <tr>
        <td>Dune</td>
        <td>9.99</td>
      </tr>
    </table>
  );
}

The server sent exactly what the components describe, for example <p …​>Book details<div>Dune, by Frank Herbert</div></p>. The browser built a different DOM from it (parsed with DOMParser in Chrome):

What the parser made of the three server responses
nesting   => <p data-testid="nest">Book details</p><div>Dune, by Frank Herbert</div><p></p>
table     => <table data-testid="prices"><tbody><tr><td>Dune</td><td>9.99</td></tr></tbody></table>
nesting-a => <a href="/books/1" data-testid="outer">Dune </a><a href="/authors/1">Frank Herbert</a>

The <p> was closed early and an empty <p> appeared; a <tbody> was inserted; the outer link was closed before the inner one started. React hydrates against that repaired DOM and finds a different structure than it expected.

Real messages (development). React detects the invalid nesting before it hydrates and says so explicitly:

In HTML, <div> cannot be a descendant of <p>.
This will cause a hydration error.

In HTML, <a> cannot be a descendant of <a>.
This will cause a hydration error.

In HTML, <tr> cannot be a child of <table>. Add a <tbody>, <thead> or <tfoot> to your code to match
the DOM tree generated by the browser.
This will cause a hydration error.

and then the structural mismatch (Hydration failed because the server rendered HTML didn’t match the client; the overlay marks the offending elements with >). In production: Minified React error #418 with args[]=HTML.

Fix. Write valid HTML. The usual sources are a <div> inside a <p> (a component that renders a block element used inside a paragraph: an image wrapper, a card, a Markdown renderer), a link or button inside a link or button, a <form> inside a <form>, a list item outside a list, and tables without <tbody> produced by hand. The fixed versions:

Valid nesting
// components/fixed/nesting.tsx
export function Nested() {
  return (
    <div data-testid="nest">
      <p>Book details</p>
      <div>Dune, by Frank Herbert</div>
    </div>
  );
}

// components/fixed/table.tsx
export function Prices() {
  return (
    <table data-testid="prices">
      <tbody>
        <tr>
          <td>Dune</td>
          <td>9.99</td>
        </tr>
      </tbody>
    </table>

The nested link has no single-element fix; make the whole card a link and the author a plain <span>, or make the two links siblings. 2. typeof window in render

Reproduction. A component branches on whether it is running in the browser. The branch is the mismatch: on the server the condition is one thing, in the browser it is the other, so the two renders differ by construction.

A server/client branch in a Client Component
// components/bad/typeof-window.tsx
"use client";

export function Environment() {
  return <p data-testid="env">Rendered on the {typeof window === "undefined" ? "server" : "client"}</p>;
}

Real message (development).

Hydration failed because the server rendered text didn't match the client. As a result this tree
will be regenerated on the client. ...

  <Environment>
    <p data-testid="env">
+     client
-     server

The page ends up reading "Rendered on the client" (the browser’s version wins after the regeneration), and the production build reports error #418. The React documentation lists this exact pattern among the common causes.

Fix. The point is that the component wants different output in the browser. There are four honest ways to say so, and they are the subject of The Fix Toolbox: render the same thing first and change it after hydration (two-pass), do not server-render it (next/dynamic with ssr: false, or use(browser())), or read the browser value through useSyncExternalStore with a server snapshot. Do not branch on typeof window in render.

Source: react-hydration-error, hydrateRoot: Pitfall.

3. window, localStorage or navigator read during render

Reproduction. Reading a browser-only global in the body of a component fails earlier than a mismatch: on the server it does not exist.

A Client Component that reads localStorage while rendering
// components/bad/shelf-from-storage.tsx
"use client";

export function ShelfCount() {
  const ids: string[] = JSON.parse(localStorage.getItem("shelf") ?? "[]");
  return <p data-testid="count">{ids.length} books on your shelf</p>;
}

Real behaviour. In next dev the request returns HTTP 500 and the overlay shows Runtime Error: localStorage is not defined at the line of the component. In a production build (next start) the same route answers HTTP 500 too, the server log has the error, the response carries no HTML for the page, and the browser renders the page from the RSC payload on the client, so a user sees a working page after the JavaScript runs while a crawler that does not run JavaScript gets an error. For a prerendered route, next build fails instead: in the run, a read of window in a Client Component of a static route stopped the build with ReferenceError: window is not defined and a link to the prerender-error page. The common "fix", typeof window !== "undefined" && localStorage…​, turns the crash into case 2: the server renders the empty value, the browser the real one, and you get a text mismatch.

Fix. The component needs a value that only exists in the browser, so tell React that: use(browser()) inside a <Suspense>, next/dynamic with ssr: false, useSyncExternalStore for a store, or an effect that reads the value after hydration. All four were run on this component, and none of them produced a message:

Fix with next/dynamic and ssr: false (in a Client Component)
// components/fixed/shelf-count-no-ssr.tsx
"use client";

import dynamic from "next/dynamic";

const ShelfCount = dynamic(() => import("./shelf-count"), {
  ssr: false,
  loading: () => <p data-testid="count">Loading your shelf...</p>,
});

export function ShelfCountNoSsr() {
  return <ShelfCount />;
}
Fix with use(browser()) (React 19.3)
// components/fixed/shelf-count-browser.tsx
"use client";

import { Suspense, use } from "react";
import { browser } from "react-dom";

function Count() {
  use(browser("The shelf lives in localStorage."));
  const ids: string[] = JSON.parse(localStorage.getItem("shelf") ?? "[]");
  return <p data-testid="count">{ids.length} books on your shelf</p>;
}

export function ShelfCountBrowser() {
  return (
    <Suspense fallback={<p data-testid="count">Loading your shelf...</p>}>
      <Count />
    </Suspense>
  );
}

Both are explained, with their trade-offs, in The Fix Toolbox. Source: Lazy Loading: Skipping SSR, React: browser.

4. Date, time zone and locale in render

Reproduction. This is the case that the Next.js guide on preventing a flash before hydration is built around, and the one that is easiest to miss locally, because on a developer’s machine the server and the browser share a locale and a time zone. A server in a data centre usually runs in UTC with an en-US or C locale, and the user’s browser does not.

A Client Component that formats a date and a time
// components/bad/added-on.tsx
"use client";

export function AddedOn({ iso }: { iso: string }) {
  return (
    <p data-testid="added">
      Added on {new Date(iso).toLocaleDateString()} at {new Date(iso).toLocaleTimeString()}
    </p>
  );
}

Rendered with iso="2026-06-15T23:30:00Z". Node.js takes its default locale from the environment (LANG) and its time zone from TZ, so starting the server as TZ=UTC LANG=ja_JP.UTF-8 makes the simulation exact. The two sides, from the runs:

LANG=ja_JP.UTF-8 TZ=UTC node -e 'const d = new Date("2026-06-15T23:30:00Z"); console.log(d.toLocaleDateString(), d.toLocaleTimeString())'
# 2026/6/15 23:30:00          <- the server's text
# the browser (en-US, America/New_York): 6/15/2026 7:30:00 PM

Real message (development).

Hydration failed because the server rendered text didn't match the client. ...

  <AddedOn iso="2026-06-15...">
    <p data-testid="added">
+     6/15/2026
-     2026/6/15

Note that the date and the time are two different bugs in one line: the locale changes the order and separators, the time zone changes the hour (and, here, would change the day for a user in Madrid, where the same instant is already June 16). In production the result was error #418 with args[]=text, and the page after regeneration read Added on 6/15/2026 at 7:30:00 PM.

Fixes, from the cheapest:

  1. Render it on the server and send the result (a Server Component, or a prop formatted on the server). The browser does not re-render a Server Component, so it cannot disagree. The cost: the date is in the server’s locale and time zone for everyone. Acceptable for a fixed format (an ISO date, a date in the event’s own time zone, an explicit timeZone and locale passed to toLocaleDateString).

  2. Format with an explicit locale and time zone, the same on both sides: toLocaleDateString("en-US", { timeZone: "UTC" }). Deterministic, and again not the user’s own.

  3. Show the server value and correct it after hydration with the two-pass pattern (flash of the server value).

  4. Do not server-render it (ssr: false or use(browser())), accepting a fallback in the HTML.

  5. Correct it before the first paint with an inline script, the pattern that the Next.js guide documents. It is the only one that gives the user’s own format with neither a mismatch nor a flash, and it is covered in Preventing a Flash Before Hydration: the Inline-Script Pattern. It was built and verified with the server in ja_JP/UTC and two different browsers (en-US in New York, es-ES in Madrid), where the same instant rendered as "June 15, 2026" and "16 de junio de 2026".

Source: Preventing flash before hydration, hydrateRoot.

5. Values that change on every call: Date.now(), Math.random(), generated ids

Reproduction. Anything that returns a different value each time it is called gives the server one answer and the browser another. Two flavours were run:

A timestamp and a random id in Client Components
// components/bad/clock.tsx
"use client";

export function Clock() {

6. The viewport, the user agent and other "environment" values

Reproduction. A component adapts to the screen size, the colour scheme, the user agent, the connection state or the language, and it reads that from the browser during render, usually behind a typeof window guard to survive the server.

A layout choice read from matchMedia while rendering
// components/bad/media.tsx
"use client";

export function Layout() {
  const narrow = typeof window !== "undefined" && window.matchMedia("(max-width: 600px)").matches;
  return <p data-testid="layout">{narrow ? "compact" : "wide"} layout</p>;
}

With a 500 px wide viewport the overlay read + compact and - wide: the server cannot know the viewport, so it renders the default, and every phone gets a mismatch. On a wide desktop browser the same code worked, which is exactly why this bug is found late: it appears only on the devices that you did not test.

Fixes.

  • Use CSS. Anything that is only about layout belongs in a media query, a container query or prefers-color-scheme, not in JavaScript. The server sends one DOM and the stylesheet adapts it. This is the best fix by far, because it needs no JavaScript to hydrate.

  • If the component really needs the value in JavaScript, read it as an external store, with useSyncExternalStore, which takes a getServerSnapshot that is used on the server and during hydration, then re-renders at once with the real value:

The fix with useSyncExternalStore and a server snapshot
// components/fixed/layout-store.tsx
"use client";

import { useSyncExternalStore } from "react";

const query = "(max-width: 600px)";

function subscribe(cb: () => void) {
  const mql = window.matchMedia(query);
  mql.addEventListener("change", cb);
  return () => mql.removeEventListener("change", cb);
}

export function Layout() {
  const narrow = useSyncExternalStore(
    subscribe,
    () => window.matchMedia(query).matches, // in the browser, after hydration
    () => false,                            // on the server and while hydrating
  );
  return <p data-testid="layout">{narrow ? "compact" : "wide"} layout</p>;
}

Verified with the 500 px viewport: no overlay, and the paragraph read compact layout after hydration. Without the third argument React cannot render the component on the server at all, and says so:

8. CSS-in-JS libraries that are not configured for the App Router

What the documentation says. CSS-in-JS in the App Router needs three things: a style registry that collects the rules of a render, the useServerInsertedHTML hook (from next/navigation) to inject those rules into the stream before the content that uses them, and a Client Component that wraps the application in the registry. The CSS-in-JS guide lists the libraries that are supported in Client Components (among them styled-jsx, styled-components, @mui/material, chakra-ui, ant-design, pandacss, stylex, tss-react and vanilla-extract) and, on 2026-10-03, still lists emotion under "currently working on support". Reproduction. A library that is misconfigured fails in one of two ways, and both were reproduced.

9. A CDN, proxy or minifier that rewrites the HTML

Reproduction. Something between your server and the browser edits the HTML. The Next.js error page names the edge or CDN configurations that try to modify the HTML response, with Cloudflare’s Auto Minify as the example. HTML minifiers remove whitespace and comments. React’s server output uses an empty comment (<!-- -→) to separate two adjacent text nodes, as in Hello, <!-- -→Ada<!-- -→! You have <!-- -→3<!-- -→ books.. If the comments disappear, the browser parses Hello, Ada! You have 3 books. as one text node, and React expects four.

The experiment rewrote the response the same way (html.replace(/<!-- -→/g, "")) for a page with that paragraph:

  <Greeting>
    <p data-testid="greeting">
+     {"Hello, "}
-     Hello, Ada! You have 3 books.

In production: error #418 with args[]=text. The text is "the same" to a human, which is what makes this cause disorienting: the diff shows a single node on one side and a fragment on the other.

The same goes for any proxy that injects scripts or banners into HTML (a corporate proxy, an ad-injecting ISP), and for tools that obfuscate e-mail addresses in markup. 11. External changing data without a snapshot

Reproduction. The last bullet of the message ("External changing data without sending a snapshot of it along with the HTML") covers everything that is not props or state: a global store, a cache, a router state read from window, a data-fetching hook that has its data on the client but not on the server. If a Client Component reads such a source during render and the server and the browser do not hold the same value, they render different output. Two shapes of it:

  • A module-level variable (a singleton store, an in-memory cache). On the server it is shared by every request, which is also a data leak between users; in the browser it starts empty. Both are bugs. Create per-request instances (a QueryClient, an Apollo Client, a store created inside the component with useState) and seed them from the server.

  • A store that has real data only in the browser (localStorage, navigator.onLine, a BroadcastChannel): case 6, with useSyncExternalStore and a server snapshot.

Fix. Send the snapshot with the HTML, so that the browser starts with what the server had: pass the data as props from a Server Component, or dehydrate a client cache on the server and rehydrate it in the browser (the HydrationBoundary of TanStack Query, the Apollo integration, SWR’s fallback). That is the subject of Hydrating Data Caches: TanStack Query and Apollo, with a measured example in which the client made zero requests for the data that the server had already fetched.

Source: react-hydration-error, React: useSyncExternalStore.

Two-pass rendering

The oldest technique and the one in the Next.js error page ("Using useEffect to run on the client only"). The first render returns exactly what the server rendered, and an effect, which runs only in the browser after hydration, flips a flag and triggers a second render with the real value. The two renders are different but the first matches the server, and that is all hydration compares.

Two-pass rendering (a Client Component)
// components/fixed/added-on-two-pass.tsx
"use client";

import { useEffect, useState } from "react";

export function AddedOn({ iso }: { iso: string }) {
  const [mounted, setMounted] = useState(false);
  useEffect(() => setMounted(true), []);
  const d = new Date(iso);
  return (
    <p data-testid="added">
      Added on {mounted ? d.toLocaleDateString() : d.toISOString().slice(0, 10)}
    </p>
  );
}

Verified: no overlay, no message. The costs are explicit in the React documentation: the component renders twice, hydration is slower, and on a slow connection the JavaScript can arrive much later than the HTML, so the user sees the server value (here the ISO date) for a while and then it changes, which can feel jarring. Setting state in an effect is also something the React Compiler’s lint rule dislikes: in the scratch app react-hooks/set-state-in-effect flagged this file. Use the technique when the extra render is cheap and a visible change is acceptable. For a browser-only component, use(browser()) states the intent more directly.

use(browser()) (React 19.3)

React 19.3.0 (2026-09-09) added a first-class API for "this component only renders in the browser": the browser function from react-dom, passed to use. During server rendering the component suspends, so the nearest <Suspense> boundary’s fallback goes into the HTML. In the browser use(browser()) returns undefined and the component renders normally. The React announcement presents it as the replacement for the two older techniques (a mounted flag set in an effect, and a typeof window check).

The rules that the reference page states:

  • It must be inside a <Suspense> boundary during server rendering; without one the server render fails.

  • It must be called from a Client Component, not a Server Component.

  • browser() alone does nothing; pass its result to use. Do not throw it.

  • The optional argument is a reason (a string or a function that returns one); it becomes the cause of the error passed to the server renderer’s onBrowserBailout. A reason function is called on the server only.

  • Like other uses of use, it can be called conditionally, so a hook can opt out of server rendering depending on an argument.

  • React does not call the server renderer’s onError or hydrateRoot’s `onRecoverableError for it, so it is not a "hydration error" in your monitoring.

useSyncExternalStore with a server snapshot

For any value that lives outside React (a Web API, a global store), useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot) is the type-correct answer. getServerSnapshot is used on the server and during hydration, so the first client render equals the server render by construction, and React then re-renders at once with getSnapshot if it differs. suppressHydrationWarning, one level deep

suppressHydrationWarning on an element tells React to not report a text or attribute difference on that element and to keep what is in the DOM. It is an escape hatch for unavoidable differences (a timestamp, an attribute that an inline script or an extension sets). Three rules decide whether it is the right tool:

  • It applies to one level. It covers the element’s own attributes and its direct text; it does not apply to descendants.

  • It silences, it does not repair. React does not try to patch the mismatched text, so the server’s text stays.

  • It is not a fix for structure. If the elements differ it is not enough.

The first rule was verified. The same mismatching text rendered in a <time> inside a <p>, with the prop on the <time> and then on the <p>:

// components/fixed/clock-suppressed.tsx: right, the prop is on the element that holds the text
"use client";

export function Clock() {
  return (
    <p data-testid="clock">
      Rendered at <time suppressHydrationWarning>{Date.now()}</time>
    </p>
  );
}

// components/fixed/clock-suppressed-wrong.tsx: wrong, the mismatching text is one level deeper
"use client";

export function Clock() {
  return (
    <p data-testid="clock" suppressHydrationWarning>
      Rendered at <time>{Date.now()}</time>
    </p>
  );
}

The first produced no message. The second produced "Hydration failed because the server rendered text didn’t match the client" and the whole-page regeneration, exactly as if the prop were not there. (ESLint’s react-hooks/purity rule flags Date.now() in both files; the rule is right in general, and this example is the narrow exception that the documentation describes.)

Use it for: a live clock, an attribute set by an inline script, <html> and <body> attributes set by theme libraries and extensions. Do not use it for: values that you can make deterministic, structure differences, and anything that spreads over several elements (it hides real errors).

Other tools

  • useId for every id, for, aria-describedby and name that must match between server and browser (case 5).

  • Explicit formats. toLocaleDateString("en-US", { timeZone: "UTC" }) is deterministic; toLocaleDateString() is not. The same holds for Intl.NumberFormat currency and unit formatting.

  • Read the request on the server. await headers() (for Accept-Language) or await cookies() (for a stored theme or locale) in a Server Component gives the server the information it lacked. The price is dynamic rendering for the route, which the guide spells out: reading the cookie in the root layout opts the whole app out of static prerendering, and under Cache Components blocks every segment under the layout. A cookie read in an inline script (see the next section) keeps the page static.

  • Move it to a Server Component. The most robust fix: the browser does not re-render a Server Component, so it cannot disagree.

  • key to force a remount is not a hydration fix; a mismatch is detected before any remount.

Preventing a Flash Before Hydration: the Inline-Script Pattern

Some information exists only in the browser and matters at first paint: the user’s locale and time zone, a theme saved in localStorage, a persisted UI state such as which accordion section is open. Every technique above gives the user either a mismatch or a flash: the server’s default is visible until hydration (or later) corrects it. The pattern in the Next.js guide "How to prevent flash before hydration" removes the flash by running a tiny script synchronously while the browser parses the HTML, so the DOM is corrected before the first paint and before React exists on the page. The guide summarises the alternatives:

  • A Client Component that re-renders with client values: a hydration error.

  • Deferring to useEffect: no error, but a visible flash.

  • Rendering only on the server: no client-specific formatting at all.

Dates and formatting

The guide’s recipe, built here in a reusable form. The server renders the date with its own locale into an element, an inline script placed right after the element rewrites the text with the browser’s locale before the first paint, and suppressHydrationWarning tells React to accept the DOM as it is, because the script changed the text before React compared it. In a Client Component the markup is wrapped in <time> with a dateTime attribute, and a helper makes the script type text/javascript on the server and text/plain on the client, so that soft navigations (where scripts inserted by React do not run) fall back to the Client Component’s own render and React does not warn about script tags.

The two files (each script argument is JSON-encoded and < is escaped, so a value can break out of neither the string nor the script tag)
// components/fixed/inline-script.tsx
export function InlineScript({ html }: { html: string }) {
  return (
    <script
      type={typeof window === "undefined" ? "text/javascript" : "text/plain"}
      suppressHydrationWarning
      dangerouslySetInnerHTML={{ __html: html }}
    />
  );
}

// components/fixed/local-date.tsx
"use client";

// JSON.stringify alone does not escape "<", so a value containing </script> could close
// the inline script; escaping "<" as \u003c keeps the literal valid and the tag closed.
const js = (value: unknown) => JSON.stringify(value).replace(/</g, "\\u003c");

import { useId } from "react";
import { InlineScript } from "./inline-script";

export function LocalDate({ date, options }: { date: string; options?: Intl.DateTimeFormatOptions }) {
  const id = useId();
  return (
    <>
      <time id={id} dateTime={date} suppressHydrationWarning data-testid="local-date">
        {new Date(date).toLocaleDateString(undefined, options)}
      </time>
      <InlineScript
        html={`{var n=document.getElementById(${js(id)});if(n)n.textContent=new Date(${js(date)}).toLocaleDateString(undefined,${js(options ?? {})})}`}
      />
    </>
  );
}

Themes

A page is server-rendered with a default theme and the user has a saved preference. The same technique: read the value and set a data-theme attribute on <html> before the first paint. <html> gets suppressHydrationWarning because the script changes an attribute React rendered.

Persisted UI state

For a Client Component whose React state must match what the script put in the DOM, use a lazy state initializer that reads from the same source as the script, with a server default, so that React’s first state equals the DOM the script produced. The guide’s accordion example does this with localStorage and the <details> element. The one-liner to remember: the script and the initializer must read the same key and agree. For a value that only has to be right after hydration, useSyncExternalStore does the same job without a script (see Worked Example: the Bookshelf Book Page); the script is for the cases where the correct value must be on screen before React is there.

A content security policy needs a nonce

Inline scripts with dangerouslySetInnerHTML are blocked by a strict Content Security Policy that does not allow 'unsafe-inline'. With a nonce-based policy set in proxy.ts, Next.js adds the nonce to its own scripts automatically, but not to yours: read it from the x-nonce request header that the proxy sets and put it on the script. Because the nonce is made per request, the page must be dynamically rendered. An experiment with the policy from the CSP guide (script-src 'self' 'nonce-…​' 'strict-dynamic') and the theme script:

The root layout with a nonce (the proxy is the one from the CSP guide)

  const nonce = (await headers()).get("x-nonce") ?? undefined;
  return (
    <html lang="en" data-theme="light" suppressHydrationWarning>
      <head>
        <script nonce={nonce} dangerouslySetInnerHTML={{ __html: themeScript }} />
      </head>
      <body>{children}</body>
    </html>
  );
}

Strict Mode in development

The guide warns that in development, React’s Strict Mode remounts components once and, on that remount, resets <html>, <head> and <body> to only the attributes that JSX manages, clearing the attribute that the script set. The proposed fix is to re-apply the stored value in the component that owns the theme, in a useLayoutEffect (which runs before paint):

The safety net from the guide (a Client Component)
"use client";

import { useLayoutEffect } from "react";

export function ThemeToggle() {
  // Re-apply after React clears it on the dev remount. This is a no-op in production.
  useLayoutEffect(() => {
    const theme = localStorage.getItem("theme");
    if (theme) document.documentElement.setAttribute("data-theme", theme);
  }, []);

  function toggle() {
    const next = (localStorage.getItem("theme") ?? "light") === "dark" ? "light" : "dark";
    localStorage.setItem("theme", next);
    document.documentElement.setAttribute("data-theme", next);
  }
  return <button onClick={toggle}>Toggle theme</button>;
}

A caveat from the experiment: with Next.js 16.3.8 and React 19.3.0 the attribute was still there after hydration in next dev, both with and without this useLayoutEffect, so the remount-clears-the-attribute behaviour could not be reproduced in this setup (<html> had suppressHydrationWarning). The React 19.3 changelog says Strict Mode now double-invokes effects during hydration, matching client-rendered roots, and the Next.js guide still documents the problem, so keep the effect as a cheap safety net, but do not count it as proven for your own setup: test your theme in development with a reload.

Testing for Hydration Errors and Monitoring Them

Hydration errors have a nasty property: they depend on the difference between the server and the browser, so a developer whose machine has one locale, one time zone and a wide window never sees them. The remedies are to make the difference deliberate, to test in a way that fails on the console, and to count the errors in production.

Make server and browser differ on purpose: TZ and LANG

The Next.js guide on flash prevention says it plainly: run the dev server with TZ and LANG set differently from your browser, for example TZ=UTC LANG=ja_JP.UTF-8 next dev, because most servers run in UTC. Node.js takes the default locale of toLocaleDateString() and Intl from LANG and the time zone from TZ; that is what the experiments of this page used:

Monitoring in production

In production a hydration error is invisible to users and quiet in the console. Because React reports recoverable errors through reportError(), they arrive as window error events. Next.js lets you hook them without owning hydrateRoot: instrumentation-client.ts is a file in the project root (or in src) that runs before the application becomes interactive, and the documentation’s own example is an error listener. This one forwards hydration errors to an endpoint with navigator.sendBeacon:

Reporting recoverable hydration errors (verified in a production build)
// instrumentation-client.ts
// Runs before the application becomes interactive (Next.js 16).
// React reports recoverable errors (including hydration mismatches) with reportError(),
// which fires a window "error" event.
window.addEventListener("error", (event) => {
  const message = String(event.error?.message ?? event.message);
  // Production builds minify the text: "Minified React error #418" (text mismatch),
  // #422, #423, #425 and friends. Development builds say "Hydration failed ...".
  if (!/Minified React error #(418|419|422|423|425)|Hydration failed|hydrat/i.test(message)) return;
  navigator.sendBeacon(
    "/api/hydration-errors",
    JSON.stringify({ path: location.pathname, message: message.slice(0, 200) }),
  );
});
// app/api/hydration-errors/route.ts
export async function POST(request: Request) {
  const report = await request.json();
  console.log("hydration-error", JSON.stringify(report)); // replace with your error tracker
  return new Response(null, { status: 204 });
}

A debugging checklist

  1. Reproduce in development with TZ, LANG and a narrow viewport that differ from the server’s. Read the overlay: is it a "Recoverable Error" (text or structure) or a "Console Error" (attribute)?

  2. Read the + Client and - Server lines. Two different formats of one value are a locale or zone bug; two different numbers a volatile call; an element on one side only is nesting or an injector; one text node against a split one is a minifier.

  3. Open the component named below the diff and the source line the overlay shows. Is it a Client Component? If it is a Server Component the cause is nesting or something outside React.

  4. Check HTML validity of what it renders (a <div> in a <p>, a table without <tbody>).

  5. Search the component and what it calls for window, document, localStorage, navigator, Date, Math.random, Intl, toLocale…​ and a module-level variable.

  6. If the error disappears in a private window, it is an extension; if it only happens through the CDN or a corporate proxy, it is a rewriting layer; if only on an iPhone, it is data detection.

  7. Apply the fix of the catalogue, then confirm with the smoke test and a production build: attribute mismatches are silent there.

Hydration under Partial Prerendering

Partial Prerendering (PPR, part of the Cache Components model: cacheComponents: true) renders a static shell at build time and fills dynamic holes at request time. Hydration was designed for streaming, and PPR is streaming where the first chunk is ready in advance. The experiment uses Cache Components (a separate scratch copy of the app with cacheComponents: true; the previous model does not prerender a shell for a dynamic route). The route has a Client Component in the shell and another one inside a dynamic hole:

A page with a static shell and a dynamic hole (Cache Components)

What this shows about hydration under PPR:

  • The shell hydrates as soon as the JavaScript is there, long before the dynamic data exists. The button in the shell worked at 157 ms, 1.8 seconds before the hole’s content arrived. This is selective hydration with the slow part being the server.

  • The hole hydrates when it arrives, as a new dehydrated boundary, like any streamed boundary (Selective and Progressive Hydration). The shell is never blocked by it.

  • The shell is prerendered at build time, so it is shared by all users. Anything in the shell that differs per user, per locale or per moment is a build-time value. In the Cache Components model Next.js enforces the rule for request data: reading it outside a Suspense boundary fails the build (the "blocking route" error; the PPR page covers it, together with connection() for time and randomness). Hydration mismatches in the shell are therefore mostly about locale and zone formatting of build-time values, which the inline-script pattern also fixes.

  • A mismatch inside a hole is contained to that boundary (What React Does with a Mismatch); the shell stays hydrated. That makes a Suspense boundary around anything volatile a standard precaution.

  • Platform requirement. PPR needs a hosting platform that supports streaming HTTP responses. The PPR platform guide describes the same two-step flow: send the static shell immediately, resume rendering with the stored postponedState, and stream the rest, so that React can hydrate the deferred Suspense boundaries. Hydrating Data Caches: TanStack Query and Apollo

Everything above is about the DOM. A client data library has the same problem with its cache: if a component calls useQuery on the client and the data was already fetched on the server, the browser should start with the data, not fetch it again and render a loading state that the server HTML did not have (a mismatch for the first render, and a waterfall). The solution is dehydrate on the server, hydrate in the browser: serialize the cache into the page, and seed the browser’s cache from it before the first render.

TanStack Query: HydrationBoundary

The documented App Router pattern: a Server Component creates a QueryClient per request, prefetches, and wraps the Client Components in HydrationBoundary with the dehydrated state. HydrationBoundary is a Client Component, so the state travels in the RSC payload as props and the browser’s QueryClient is seeded when it renders. This was built and run with @tanstack/react-query 5.104.1:

The shared client factory: one QueryClient per request on the server, one per tab in the browser
// lib/get-query-client.ts
import { QueryClient, defaultShouldDehydrateQuery, environmentManager } from "@tanstack/react-query";

function makeQueryClient() {
  return new QueryClient({
    defaultOptions: {
      // With SSR, a staleTime above 0 avoids refetching immediately on the client.
      queries: { staleTime: 60 * 1000 },
      dehydrate: {
        // Also send queries that are still pending, so the stream carries the promise.
        shouldDehydrateQuery: (query) => defaultShouldDehydrateQuery(query) || query.state.status === "pending",
      },
    },
  });
}

let browserQueryClient: QueryClient | undefined;

export function getQueryClient() {
  if (environmentManager.isServer()) return makeQueryClient(); // one per request
  return (browserQueryClient ??= makeQueryClient()); // one per tab
}

Things to know:

  • The dehydrated state is public. It is inside the HTML and the payload, so whatever you prefetch reaches every visitor’s browser. Do not put secrets or data the user may not see in a prefetched query; authorize on the server before you prefetch (the data-security page of this section covers it).

  • staleTime above zero. With the default of zero the client treats the hydrated data as stale and refetches at once, which defeats the point. The guide recommends a value above 0, such as a minute.

  • One client per request on the server. A module-level QueryClient shared by every request leaks one user’s cache into another’s response; the factory above creates a new one on the server and reuses one in the browser (it must not be re-created when React suspends during the first render).

  • Pending queries. With shouldDehydrateQuery including pending queries (TanStack Query 5.40.0 and later) you can start a prefetch without await, so it does not block the Suspense boundary, and let the promise stream; use useSuspenseQuery in the client component to "use" it. The client-side rendering page of this section shows that variant in detail; the docs of 5.104.1 now call the underlying method queryClient.query(…​), while prefetchQuery, used above, still exists.

  • Non-JSON data (dates, maps) needs serializeData and deserializeData on the two sides.

  • Server Actions are for mutations, not for queryFn. The guide warns that Server Actions called from the client run serially.

Apollo Client

GraphQL clients have the same two-step flow. The existing Apollo configuration page of this documentation describes the classic mechanism (client.extract() on the server, new InMemoryCache().restore(window.APOLLO_STATE) in the browser) in Apollo Client Configuration (the section "SSR hydration"). For the App Router the maintained package is @apollo/client-integration-nextjs (0.14.5 on 2026-10-03, with @apollo/client 4): its README describes registerApolloClient, which returns getClient, query and a PreloadQuery component for Server Components, and an ApolloNextAppProvider with a makeClient function for Client Components, so that data queried on the server is transported to the browser cache with the streamed response and useSuspenseQuery in a Client Component waits for the server’s request instead of making its own. The rules are the same as for TanStack Query: a client per request on the server, no secrets in preloaded data, and the same query and variables on both sides.

SWR

SWR seeds its cache with the fallback option of SWRConfig or a fallbackData prop in the same way; see the client-side rendering page of this section for the Next.js specifics and for when fetching on the client is the right choice at all.

Worked Example: the Bookshelf Book Page

All the techniques above come together in one page of the running Bookshelf. The book page is statically generated (generateStaticParams) and shows, next to the server-rendered title and price: when the book was added to the catalogue in the reader’s locale and zone, an "Add to shelf" button and a shelf counter that read localStorage, and a "last opened" line that is browser-only. Each of the three needs a different tool, and the page produces no hydration error with the server in ja_JP and UTC and the browser in en-US or es-ES.

2. The shelf: an external store read with useSyncExternalStore
// components/bookshelf/shelf-store.ts
const KEY = "shelf";
const listeners = new Set<() => void>();

export function subscribe(listener: () => void) {
  listeners.add(listener);
  window.addEventListener("storage", listener); // other tabs
  return () => {
    listeners.delete(listener);
    window.removeEventListener("storage", listener);
  };
}

// getSnapshot must return a stable, comparable value: a string, not a new array.
export const getSnapshot = () => localStorage.getItem(KEY) ?? "[]";
// Rendered on the server and during hydration.
export const getServerSnapshot = () => "[]";

export function addToShelf(id: string) {
  const ids: string[] = JSON.parse(getSnapshot());
  if (!ids.includes(id)) localStorage.setItem(KEY, JSON.stringify([...ids, id]));
  listeners.forEach((l) => l());
}
// components/bookshelf/shelf-button.tsx
"use client";

import { useSyncExternalStore } from "react";
import { addToShelf, getServerSnapshot, getSnapshot, subscribe } from "./shelf-store";

export function ShelfButton({ bookId }: { bookId: string }) {
  const raw = useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot);
  const ids: string[] = JSON.parse(raw);
  const onShelf = ids.includes(bookId);
  return (
    <p>
      <button data-testid="shelf-btn" disabled={onShelf} onClick={() => addToShelf(bookId)}>
        {onShelf ? "On your shelf" : "Add to shelf"}
      </button>{" "}
      <span data-testid="shelf-count">{ids.length} on your shelf</span>
    </p>
  );
}

The server snapshot is the empty shelf, so the server HTML and the first client render agree on "Add to shelf" and "0 on your shelf"; React then re-renders at once with the real shelf. The page works across tabs (the storage event) and the same module can be shared by other components that show the shelf.

3. "Last opened": browser-only content with use(browser())
// components/bookshelf/last-opened.tsx
"use client";

import { Suspense, use, useEffect, useState } from "react";
import { browser } from "react-dom";

function Inner({ bookId }: { bookId: string }) {
  use(browser("Last-opened time lives in localStorage."));
  const key = `opened:${bookId}`;
  const [previous] = useState(() => localStorage.getItem(key));
  useEffect(() => localStorage.setItem(key, new Date().toISOString()), [key]);
  return (
    <p data-testid="last-opened">
      {previous ? `You last opened this book on ${new Date(previous).toLocaleString()}` : "First visit"}
    </p>
  );
}

export function LastOpened({ bookId }: { bookId: string }) {
  return (
    <Suspense fallback={<p data-testid="last-opened">&nbsp;</p>}>
      <Inner bookId={bookId} />
    </Suspense>
  );
}

Nothing about this line can exist on the server, and the server does not pretend: its HTML contains the fallback (a non-breaking space that reserves the line’s height, which avoids a layout shift) inside a boundary marked for client rendering.

What is worth taking from the comparison:

  • React’s closest analogue of "hydrate never" is the Server Component. Angular’s hydrate never still ships the component’s code to the browser (the content is just not activated); a Server Component’s code is never in the bundle. And the reverse: Angular and Vue 3.5 let you choose when each part hydrates (viewport, idle, interaction) with triggers or strategies, whereas React’s selective hydration is automatic and driven by arrival order and input; you influence it with Suspense boundaries and lazy imports, not with triggers.

  • Event replay is a real difference. In Angular, withEventReplay() closes the gap between first paint and hydration by replaying recorded events, and Vue replays the event that triggers a lazy hydration. In the Next.js experiments of this page, a click on a boundary whose code was not yet in the page was lost, and a click before any script ran was lost. Design the landing page so that the essential interaction does not depend on JavaScript (a link, a form), or make it hydrate first.

  • The mismatch policy differs. Vue patches the mismatched subtree in place; React discards and re-renders the boundary. Both ask you to treat a mismatch as a bug; React’s recovery is more expensive, which is why a Suspense boundary and an exact fix both matter.

  • Server Components change the question. In the React model the first question is not "how do I hydrate this cheaply" but "does this need to be in the browser at all".

Where the Books Are Outdated

The two reference books were consulted for the concepts they cover, and their treatment of hydration is, in short, correct for their time and incomplete for today. Nothing is reproduced from them; this is a summary of the differences.

  • Real-World Next.js (Packt, 2022, Pages Router) introduces hydration as the step that makes server-rendered pages dynamic, shows client-side rendering with useEffect (the server’s text is replaced after hydration, with a visible flash) and next/dynamic with ssr: false, and sets up Apollo Client and Redux with typeof window === "undefined" branches. Today: the App Router hydrates only Client Components; browser-only content has use(browser()) (React 19.3); a typeof window branch in render is itself a hydration bug; a module-level client on the server is shared by every request, so it has to be created per request and seeded from the server (HydrationBoundary, @apollo/client-integration-nextjs); ssr: false is allowed only in Client Components.

  • Practical Next.js for E-Commerce (Apress, 2023) meets hydration as a console warning to fix (a third-party tabs component, solved by loading it with ssr: false; a translation key whose case differed between server and client) and shows the message of React 17 and 18, which printed the two texts in one warning. Today the message is a single error with a + Client and - Server diff (React 19, and the overlay indicator from Next.js 16.2), the cause catalogue above generalises the two cases, and the third-party-component fix has a sharper tool in use(browser()) or a Suspense boundary.

  • Neither book covers selective hydration with Suspense, the RSC payload, the cost of hydration as a metric (INP replaced FID in 2024), the inline-script pattern, useSyncExternalStore with a server snapshot, useId, onRecoverableError monitoring or hydration under Partial Prerendering. They also predate React 19’s third-party-script tolerance and the Strict-Mode-on-by-default App Router.

Summary

  • Hydration reconciles the server HTML with the browser’s first render and attaches handlers. In Next.js the HTML gives the preview, the RSC payload gives the tree, and the JavaScript hydrates the Client Components. It happens once per document; client navigations render the RSC payload without hydrating.

  • The first client render must equal the server render. Server Components cannot disagree with themselves, so almost every mismatch lives in a Client Component.

  • Suspense boundaries are the unit of selective hydration, of streaming and of mismatch recovery. A mismatch regenerates from the nearest boundary (or the whole root), losing typed input; attribute mismatches are not patched and are silent in production.

  • The cost of hydration is JavaScript: download, parse, render. Server Components, composition, lazy loading and smaller dependencies reduce it; the measured example saved about 380 KiB.

  • The catalogue (nesting, typeof window, browser globals, locale and time zone, volatile values, viewport, extensions, CSS-in-JS, CDN rewriting, iOS detection, external data) has a verified fix for each. The tools are: make it deterministic, move it to the server, use CSS, useSyncExternalStore, use(browser()), ssr: false, two-pass, an inline script, and suppressHydrationWarning as a last, one-level escape hatch.

  • Test with a server whose TZ and LANG differ from the browser’s, fail the build on console errors, and count the production errors with instrumentation-client.ts.

  • Under PPR the shell hydrates early and each hole hydrates when it arrives. A client data cache needs dehydrate and HydrationBoundary (or the library’s equivalent) so that the browser starts with the server’s data.
