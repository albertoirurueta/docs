What’s Changed & Upgrading

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Next.js 16.3 (the latest release on 2026-10-03 is 16.3.8, and the official documentation reports @doc-version 16.3.8), React 19.3 and Node.js 20.9 or later, verified on 2026-10-03. It covers the App Router and the Pages Router: the change log applies to both, the code examples are App Router code unless a Pages Router difference is called out, and the caching entries label the two models, the previous model (the default, with cacheComponents off) and Cache Components (cacheComponents: true, opt-in). The upgrade commands, the codemod output, the build errors and the curl results below were produced with Next.js 16.3.8 and Node.js 24.16 on macOS in scratch projects (an older 15.5 project that was upgraded, a Create React App style single-page app, and a copy of the Bookshelf catalogue that the rest of this section grows).

Most Next.js tutorials, answers and books were written for a version that no longer exists. Two books were used while preparing this section, and they are about Next.js 12 and 13 and the Pages Router; this page is where the differences between that world and the current one are written down once, so the other pages of the section can stay focused on how things work today. It has four parts: a change log by major version, the tools that automate an upgrade, the two official migration guides for single-page apps, and the collected lists of everything in the books that is outdated or wrong. The concepts themselves are explained in depth on the pages linked from each entry, for instance Caching, Redirects, Rewrites & Proxy and Turbopack & the Compiler.

Next.js 13 and 13.4: the App Router Arrives

Next.js 13 is the version the Pages Router books stop at. It introduced the app directory in beta with layouts, React Server Components and streaming, and the App Router was declared stable in 13.4 (May 2023). The release notes list the first set of breaking changes that tutorials from 2021 and 2022 trip over:

  • the minimum React version became 18.2 and the minimum Node.js version 14.6;

  • next/image was renamed next/legacy/image and the new image component took the name next/image;

  • a next/link child can no longer be an <a> (the temporary legacyBehavior prop keeps the old form);

  • the target option of next.config.js was removed, Internet Explorer was dropped as a target, and swcMinify became true;

  • @next/font replaced the CSS font loading recipes (13.2 made it built in as next/font).

The Pages Router was not removed. Both routers coexist in one application, and the Pages Router remains supported; it is simply no longer where the new features land. The pages of this section that touch it say so where it differs.

Source: Next.js 13 and Next.js 13.4

Next.js 14: Server Actions and next export

Next.js 14 (2023-10-26) is a small upgrade guide. Its summary is four lines:

  • the minimum Node.js version moved from 16.14 to 18.17;

  • the next export command was removed in favour of output: 'export' in next.config;

  • ImageResponse moved from next/server to next/og;

  • the @next/font package was removed in favour of the built-in next/font.

Server Actions became stable, and Partial Prerendering appeared as a preview. Version 14.2 added the first staleTimes experiment for the client router cache, which Next.js 15 used to change a default (see below).

Next.js 15: Async Request APIs and Caching Off by Default

Version 15 (2024-10-21) made the two changes that break the most old code. Both are described in the version 15 upgrade guide.

Request-time APIs became asynchronous. cookies, headers, draftMode, the params prop of layout, page, route, default and the metadata image files, and the searchParams prop of page are Promises. Version 15 kept a temporary synchronous compatibility mode that logged a warning in development; Next.js 16 removed it. The reason is rendering: a Promise lets Next.js prerender everything before the first access to request data, which is what Partial Prerendering and Cache Components build on.

Version 15 and later: awaiting the request APIs
import { cookies } from 'next/headers'

// Before (13 and 14)
const cookieStore = cookies()
const token = cookieStore.get('token')

// After (15, required in 16)
const cookieStore = await cookies()
const token = cookieStore.get('token')

Source: Upgrading from 14 to 15: Async Request APIs and Next.js 15: why the APIs became asynchronous

The page-level form is the one tutorials get wrong most often, because the destructured argument is now a Promise object:

A page before and after (the output of the codemod shown in a later section)
// Before
type Props = { params: { id: string }; searchParams: { lang?: string } }

export default function Page({ params, searchParams }: Props) {
  const theme = cookies().get('theme')?.value ?? 'light'
  /* ... */
}

// After
type Props = {
  params: Promise<{ id: string }>
  searchParams: Promise<{ lang?: string }>
}

export default async function Page(props: Props) {
  const searchParams = await props.searchParams
  const params = await props.params
  const theme = (await cookies()).get('theme')?.value ?? 'light'
  /* ... */
}

Source: Upgrading from 14 to 15: params and searchParams

A synchronous Client Component page cannot await; it reads the Promise with React’s use hook instead (const params = use(props.params)). Next.js 15.5 added npx next typegen, which generates the global PageProps, LayoutProps and RouteContext helpers so that these types need not be written by hand; they are used throughout this section as PageProps<'/[locale]/books/[id]'>.

Caching defaults moved to "uncached". In versions 13 and 14 a fetch was cached by default, a GET Route Handler was cached unless it used a dynamic function, and the client router cache reused page segments for about 30 seconds. Version 15 reversed all three: fetch requests and GET handlers are not cached unless asked to be (cache: 'force-cache', export const dynamic = 'force-static'), and the client router cache no longer reuses page segments on navigation (staleTimes.dynamic is 0), although it still reuses them for back and forward navigation and for shared layouts. The full account of the layers, in both models, is on the Caching page; the shape of the change is this:

Source: Upgrading from 14 to 15: fetch requests, Route Handlers and Client Cache

Other breaking changes in 15: the minimum Node.js version became 18.18; React 19 became the minimum for the App Router (the Pages Router accepts React 18 or 19); useFormState was replaced by useActionState; next/dynamic with ssr: false is disallowed in Server Components; the runtime value experimental-edge is an error (use edge); revalidateTag and revalidatePath throw if called during render; geo and ip were removed from NextRequest; Speed Insights auto-instrumentation was removed; experimental.bundlePagesExternals became bundlePagesRouterDependencies and experimental.serverComponentsExternalPackages became serverExternalPackages. Version 15 also made next.config.ts a supported file, shipped <Form>, stabilised instrumentation.js, and improved hydration error messages. Version 15.1 added after (stable) and forbidden/unauthorized (experimental).

Source: Next.js 15 and Next.js 15.1

Next.js 16.0: Turbopack, Proxy and the End of the Compatibility Period

Version 16 (2025-10-21) is the largest cleanup since 13. Its upgrade guide is long, but the changes group into five themes.

Turbopack by default. next dev and next build use Turbopack; the --turbopack flag in package.json scripts is no longer needed. A project with a custom webpack function and no turbopack key fails next build on purpose, so that nobody ships a build that silently ignores their webpack configuration. The three ways out are --webpack to opt out, --turbopack to build anyway, or an (empty or real) turbopack key. The turbopack configuration also moved out of experimental.

Synchronous request APIs removed. The version 15 compatibility mode is gone, so code that still reads params, searchParams, cookies(), headers() or draftMode() synchronously fails to type-check and fails at runtime. In Next.js 16 the props of opengraph-image, twitter-image, icon, apple-icon and sitemap (the id) became Promises as well.

Caching APIs. revalidateTag takes a second argument, a cacheLife profile, and the single-argument form is deprecated (a TypeScript error, as above); updateTag is new, for Server Actions only, and gives read-your-writes semantics; refresh refreshes the client router from a Server Action; cacheLife and cacheTag are stable, so the unstable_ prefix and the aliased imports go away. experimental.ppr, the experimental_ppr segment export, experimental.dynamicIO and experimental.useCache were removed in favour of the top-level cacheComponents flag. Enabling cacheComponents is not a rename: it can surface build errors for uncached data outside <Suspense>, and the migration path is the Migrating to Cache Components guide. The mechanics are on the Caching and Partial Prerendering & Cache Components pages.

The three caching changes in code
// Before
import {
  unstable_cacheLife as cacheLife,
  unstable_cacheTag as cacheTag,
} from 'next/cache'
revalidateTag('posts')

// After (16): stable names, a profile on revalidateTag
import { cacheLife, cacheTag, revalidateTag } from 'next/cache'
revalidateTag('posts', 'max') // stale-while-revalidate

// For read-your-writes inside a Server Action
import { updateTag } from 'next/cache'
updateTag(`user-${userId}`)

Removals. These were deprecated earlier and are gone:

  • AMP: the amp configuration, next/amp and useAmp, and export const config = { amp: true };

  • next lint and the eslint option of next.config; next build no longer lints;

  • serverRuntimeConfig and publicRuntimeConfig (use environment variables);

  • the devIndicators options appIsrStatus, buildActivity and buildActivityPosition;

  • experimental.dynamicIO, experimental.useCache, experimental.ppr and experimental_ppr;

  • unstable_rootParams (replaced by next/root-params, which shipped in 16.3);

  • the size and First Load JS columns of the next build output, which were inaccurate with Server Components.

Behaviour changes and defaults. These do not break compilation but change output:

  • Parallel routes need default.js. Every parallel route slot needs a default.js (return null or call notFound()). In the scratch test a slot without one built successfully, and the request that did not match the slot answered 404; adding default.tsx returning null made the same request answer 200. The upgrade guide says builds fail without it, so treat the file as required (see Parallel & Intercepting Routes).

  • next/image defaults. minimumCacheTTL went from 60 seconds to 4 hours; 16 left the default imageSizes; qualities defaults to [75]; local IPs are blocked unless dangerouslyAllowLocalIP is set; maximumRedirects defaults to 3; local images with a query string need localPatterns with a search entry. next/legacy/image and images.domains are deprecated; use next/image and remotePatterns. See Images, Fonts & Scripts.

  • Dev and build directories. next dev writes to .next/dev, so dev and build can run at the same time, and a lockfile prevents two next dev or two next build processes on one project.

  • ESLint flat config. @next/eslint-plugin-next defaults to the flat config format.

  • Scroll behaviour. Next.js no longer overrides a global scroll-behavior: smooth during navigation; add data-scroll-behavior="smooth" to <html> to get the old override.

  • Navigation. The prefetch and navigation layer was rewritten (layout deduplication, incremental prefetching): more, smaller prefetch requests with no code changes.

  • next dev config load. The config file is no longer loaded by the next dev launcher, so a check such as process.argv.includes('dev') in next.config.js returns false; check NODE_ENV or the config phase instead.

  • Sass. sass-loader 16 and the modern Sass API; Turbopack does not support the legacy ~ prefix in Sass imports.

The minor releases of 16 carry no breaking change for a project already on 16.0, but several of them change behaviour by default, and several are experiments whose names changed between minors. Anyone reading a post or a prompt from one month may find the name different in the next.

A few of these renamed or moved between minors, and the names matter when following older material:

  • catchError. In 16.2 it shipped as unstable_catchError() with an unstable_retry() callback (and an unstable_retry prop for error.tsx). In 16.3 the stable names are catchError and retry, imported from next/error. The remove-unstable-prefix codemod (checked in its source) renames only unstable_cacheLife and unstable_cacheTag, so rename this one by hand.

  • next/root-params. Version 16.0 removed unstable_rootParams and promised an alternative in a minor release; that alternative is next/root-params, which arrived in 16.3. It works in Server Components (and inside use cache scopes) but not yet in Route Handlers or Server Actions.

  • Adapters. The alpha of 16.0 read experimental.adapterPath; 16.2 made adapterPath a stable top-level option.

  • Bundle analysis. next experimental-analyze (16.1) replaces @next/bundle-analyzer for Turbopack projects, and it is experimental by name and by status.

  • File-system caching. Dev caching was stable in 16.1; the build cache and memory eviction became defaults in 16.3 (see Turbopack & the Compiler).

  • Agents. The DevTools MCP is from 16.0 and get_routes from 16.1; bundled docs are from 16.2 and the AGENTS.md block that next dev maintains is from 16.3.

A safe order for an upgrade

The commands above combine into a routine that works for one major at a time. Skipping versions is possible (the 16 guide is written for 15), but each guide assumes the previous one was applied, and the two compatibility periods of Next.js (synchronous request APIs in 15, middleware in 16) are easiest to leave one at a time.

  1. Commit everything and create a branch; the codemods refuse to run on a dirty tree.

  2. Upgrade to the latest patch of the current major first (npx @next/codemod upgrade patch), so that the deprecation warnings of the current version are visible.

  3. Read the upgrade guide of the next major from top to bottom once; most steps are one paragraph.

  4. Run npx next upgrade (16.1+) or npx @next/codemod@canary upgrade latest, answer the prompts, and review the diff of package.json and the lockfile on its own.

  5. Run npx @next/codemod@latest next-async-request-api . when the project still reads request APIs synchronously, then npx next typegen and replace hand-written params types by PageProps, LayoutProps and RouteContext.

  6. Fix next.config by hand: turbopack at the top level, removed keys, images defaults, and the cacheComponents decision. Keep cacheComponents off until the rest builds.

  7. Run next build. Type errors and the validator messages shown in this page are the checklist; fix, rebuild, repeat.

  8. Run the test suite and a production-mode smoke test (next start, then curl or the end-to-end suite), because caching defaults changed silently between 14 and 15: code that relied on a cached fetch is now slower, not broken.

  9. Only then adopt the new features (Cache Components, Partial Prefetching, the React Compiler) one at a time.

The same upgrade can be handed to a coding agent: the version 16 guide ships a prompt that asks the agent to set up version-matched docs first (npx @next/codemod@canary agents-md, or the bundled docs and AGENTS.md block that Next.js 16.2 and 16.3 maintain), run the codemod, explain the plan, and verify the result with the dev tools.

Migrating from Create React App and Vite

Both official guides use the same incremental strategy: first make the existing single-page app run inside Next.js as a client-only application, unchanged, then adopt Next.js features route by route. The motivation the guides give is the usual list (a client-only app downloads all its code before it can fetch data, which causes waterfalls; Next.js adds automatic code splitting, streaming, server-side data fetching, the Proxy and the built-in optimisations). Nothing about the first step needs React Server Components. The two guides are at Create React App and Vite; Create React App is no longer maintained, so that guide is the one most older projects need.

From Create React App

The steps of the guide, applied to a small Create React App style project (a src/App.tsx with state, an image import and a REACT_APP_ variable), were:

  1. Install Next.js (npm install next@latest).

  2. Create next.config.ts with output: 'export' and distDir: 'build'.

  3. Create app/layout.tsx: the <html>, <head> and <body> of public/index.html become the root layout, and the div#root becomes <div id="root">{children}</div>.

  4. Move the title and description into the Metadata API, and drop the charset and viewport tags (Next.js adds them).

  5. Import global CSS from the layout.

  6. Create the entry page as an optional catch-all route, app/[[…​slug]]/page.tsx, with generateStaticParams returning [{ slug: [''] }].

  7. Add a client-only entrypoint, app/[[…​slug]]/client.tsx, that loads the old App with next/dynamic and ssr: false.

  8. Change image imports (they return an object; use logo.src or the Image component).

  9. Rename REACT_APP_ variables to NEXT_PUBLIC_.

  10. Update the package.json scripts and .gitignore, then clean up public/index.html, src/index.tsx, react-scripts and the reportWebVitals setup.

From Vite

The Vite guide has the same shape (steps 1 to 9) with these differences from the Create React App one:

  • next.config.mjs uses distDir: './dist';

  • tsconfig.json needs nine specific changes (remove the project reference to tsconfig.node.json, add ./dist/types/*/.ts and ./next-env.d.ts to include, the next plugin, esModuleInterop, jsx: react-jsx, allowJs, forceConsistentCasingInFileNames, incremental);

Errata and Bad Practices Not to Reproduce

The books also contain faults that are not a matter of age. They are collected here with the correct form of each, so that nobody copies them; the pages that teach the topic (data security, authentication, Route Handlers) repeat the relevant one in context. The correct forms below follow the official documentation, and the ones that could be shown as a short program were built and run in the scratch Bookshelf app with next build and next start -p 3903.

Table 8. Errata of the two books, and the correct form
# Fault Correct form

1

Secret exposed to the browser (Libby ch. 3 to 4, 7). A Sanity write token stored as NEXT_PUBLIC_SANITY_TOKEN with the build warning silenced, and the claim that .env keeps it private.

Everything prefixed NEXT_PUBLIC_ is inlined into the client JavaScript, wherever it is defined. Use an un-prefixed variable read in server-only code, rotate any token that was ever shipped, and use a read-only token or none for public reads. See Data Security & CSP.

2

Secret exposed to the browser. A Stripe secret key named NEXT_PUBLIC_STRIPE_SECRET_KEY.

Only the publishable key may use the prefix. The secret key stays in a server-only variable and a server-only module.

3

Price tampering (Libby ch. 4, 7). Checkout line_items are built from the cart posted by the client and its prices; quantities are not validated (missing in both books).

The client sends product ids and quantities only. The server looks the price up by id and validates the quantity. The Route Handler below was run.

4

Payment fulfilment (both books). The success redirect is treated as proof of payment.

The redirect proves nothing. Fulfil an order from the payment provider’s signed webhook, verified on the raw body, answered quickly and idempotent. See Route Handlers & Backend for Frontend.

5

Injection. The slug is interpolated into a GROQ query (Libby ch. 3).

Pass the slug as a query parameter of the CMS client (a GROQ query uses $slug and the client takes the value separately) instead of concatenating it into the query string, and validate it first, as in item 6.

6

Injection and open proxy (Riva ch. 4). An unvalidated path segment is interpolated into an upstream URL, and the API route forwards whatever it is given.

Validate the segment against a strict pattern, build the upstream URL from a fixed host, and look the resource up by id. Run below.

7

Auth (Riva ch. 12, Libby ch. 12). A hard-coded JWT secret and hard-coded credentials.

Secrets come from environment variables (placeholders in the repository, real values in the hosting provider); credentials come from a user store with hashed passwords, or from an identity provider.

8

Auth. No token expiry, and a cookie without secure or sameSite.

Set httpOnly, secure, sameSite and an expiry (maxAge). Run below.

9

Auth. An uncaught jwt.verify error, so a tampered cookie produces a 500.

Treat a failed verification as "not signed in": catch the error and return a 401 or a redirect to sign-in.

10

Auth. Pages protected only by client-side hooks (useAuth, useSession).

A client hook hides UI; it protects nothing. Authorise on the server, in the Server Component, Route Handler or Server Action that reads the data, and use the Proxy only as an optimistic first check. See Authentication & Authorization.

11

Auth. NEXTAUTH_SECRET omitted from the initial setup.

Auth.js v5 needs AUTH_SECRET (and AUTH_TRUST_HOST behind a proxy, or on localhost with next start), and the NextAuth v4 setup of the books needed NEXTAUTH_SECRET. Generate a random value, keep it in the environment, and set it before the first sign-in.

12

Other. useEffect(async () ⇒ …​) with no abort (Riva ch. 4).

An effect callback must be synchronous (it may return only a cleanup function). Put the async work in an inner function and abort the request in the cleanup. Built below.

13

Other. A root-run, single-stage Dockerfile without a .dockerignore that copies .env* (Riva ch. 11).

A multi-stage build, a non-root user, and a .dockerignore that excludes .env*, .git and node_modules. The deployment pages of this section show the Next.js specific parts.

14

Other. req.headers.origin used to build redirect URLs (Libby ch. 4).

The header is controlled by the caller. Build the redirect from a fixed base URL in configuration, a relative path, or an allow-list. Run below.

15

Other. The claims that generateMetadata needs TypeScript and that the App Router is unsuitable (Libby ch. 8).

Neither is true. generateMetadata works in plain JavaScript files (run below), and the App Router is the default for new Next.js applications.

Errata 3: prices read on the server by id, quantities validated (app/api/quote/route.ts)
import { z } from "zod";
import { getBook } from "@/lib/books";

// The client sends ids and quantities only; prices never come from the request.
const Cart = z.object({
  items: z.array(z.object({ id: z.string(), quantity: z.number().int().min(1).max(10) })).min(1),
});

export async function POST(request: Request) {
  const parsed = Cart.safeParse(await request.json().catch(() => null));
  if (!parsed.success) {
    return Response.json({ error: "invalid cart" }, { status: 400 });
  }
  const lines = [];
  for (const { id, quantity } of parsed.data.items) {
    const book = await getBook(id);
    if (!book) return Response.json({ error: `unknown book ${id}` }, { status: 400 });
    lines.push({ id, quantity, unitCents: book.priceCents });
  }
  const totalCents = lines.reduce((sum, l) => sum + l.unitCents * l.quantity, 0);
  return Response.json({ lines, totalCents });
}

Errata 6: a validated segment and a lookup by id (app/api/upstream/[id]/route.ts)
import { getBook } from "@/lib/books";

// Validate the segment against a strict pattern and look it up by id,
// instead of interpolating it into an upstream URL.
export async function GET(_req: Request, ctx: RouteContext<"/api/upstream/[id]">) {
  const { id } = await ctx.params;
  if (!/^\d{1,6}$/.test(id)) {
    return Response.json({ error: "bad id" }, { status: 400 });
  }
  const book = await getBook(id);
  return book ? Response.json(book) : Response.json({ error: "not found" }, { status: 404 });
}

Errata 12: a synchronous effect callback with an inner async function and an abort (app/[locale]/abort-effect/book-count.tsx)
"use client";

import { useEffect, useState } from "react";

export function BookCount() {
  const [count, setCount] = useState<number | null>(null);

  useEffect(() => {
    const controller = new AbortController();
    // The effect callback itself stays synchronous; the async work lives inside it.
    async function load() {
      try {
        const res = await fetch("/api/books", { signal: controller.signal });
        setCount((await res.json()).length);
      } catch (error) {
        if ((error as Error).name !== "AbortError") throw error;
      }
    }
    load();
    return () => controller.abort();
  }, []);

  return <p>{count === null ? "Loading…" : `${count} books`}</p>;
}

The component was compiled and type-checked by next build, and the server-rendered HTML contained Loading…; the effect itself runs only in the browser. The React side of the rule is on the Effects page.

Summary

  • The big changes by version: 13 (the App Router), 14 (Server Actions stable, next export removed), 15 (async request APIs, uncached by default, React 19), 16 (Turbopack default, proxy.ts, Cache Components, synchronous APIs and several features removed) and 16.1 to 16.3 (stable dev cache, Adapters, catchError, next/root-params, Instant Navigations opt-in).

  • npx next upgrade (16.1 and later) or npx @next/codemod@canary upgrade latest upgrades the packages and runs the recommended codemods, but not all of them: run next-async-request-api by hand, fix next.config and revalidateTag manually, and accept cache-components-instant-false only when adopting Cache Components.

  • Create React App and Vite apps move to Next.js as a client-only catch-all page with output: 'export', and then adopt features route by route.

  • cacheComponents and partialPrefetching remain opt-in in 16.3; the section teaches both caching models.

  • Thirteen areas of the books are outdated and fifteen items are errata; the tables above list each with the correct form and the page that teaches it.
