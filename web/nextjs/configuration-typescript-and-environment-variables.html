Configuration, TypeScript & Environment Variables

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when everything below was checked; the official documentation @doc-version is also 16.3.8), React 19.3.0, Node.js 20.9 or later and TypeScript 5.1 or later. It describes the App Router; the places where the Pages Router differs are called out in the text. Configuration keys do not depend on the rendering model, but a few options (cacheComponents, partialPrefetching, cacheLife) only matter under Cache Components, which is still opt-in, while the rest of the page describes behaviour that is identical under the previous caching model (the default today, with fetch and GET Route Handlers uncached); where an example needs one or the other, it says so. The page is the reference for every project-level file: next.config.ts, tsconfig.json, next-env.d.ts, eslint.config.mjs, the .env* files and the import aliases. Every example was built and run on Next.js 16.3.8 in a scratch copy of the Bookshelf application with Node.js 24, in both caching models where it matters; the output blocks are real output from those runs, and each example is followed by the official page it derives from. The folder layout around these files is covered in Project Structure.

Where Configuration Lives

A Next.js project is configured by a small, fixed set of files in the project root. Each is read by a different tool at a different moment, which is what decides whether a change needs a restart, a rebuild or nothing at all.

Table 1. The configuration surfaces of a Next.js 16 project
File Owns Read by

next.config.ts (or .js, .mjs, .mts)

Framework behaviour: routing rules, caching model, images, headers, bundler options, build output, TypeScript and build flags, experimental flags.

The Next.js CLI at next dev, next build, next start and next typegen, at start-up and again in some build sub-processes. It runs in Node.js, is not bundled and is never sent to the browser. A change needs a restart of the dev server.

tsconfig.json

TypeScript compiler options, the next editor plugin, the paths aliases for absolute imports, and which generated type files are included.

tsc, the editor and the build’s type-check step. The bundler also reads paths to resolve aliases.

next-env.d.ts

References to Next.js’s own ambient types, regenerated for you.

TypeScript only. Never edit it.

eslint.config.mjs

Lint rules, through the eslint-config-next package and the ESLint CLI.

The eslint command that you run yourself, never next build (see ESLint With the Flat Config CLI).

.env, .env.local, .env.development, .env.production, .env.test and their .local variants

Values that differ between machines and environments: URLs, feature flags, secrets, and NEXT_PUBLIC_ values that are baked into client code.

Next.js loads them into process.env before it loads next.config.ts; loadEnvConfig from @next/env does the same for other tools.

package.json

Scripts, dependencies, the engines range and the "type" field that decides whether .js files are ESM.

Node.js and the package manager.

proxy.ts, instrumentation.ts

Request interception and start-up hooks. They are code rather than configuration and have their own pages.

At request time, and once on server start.

Source: next.config.js, TypeScript, ESLint and Environment Variables

The pieces interact. next.config.ts sets typedRoutes, which makes Next.js generate types that tsconfig.json must include, which tsc and the editor then check. A .env value feeds next.config.ts through process.env because the config file runs in Node.js with the environment already loaded. The sections below follow that order.

next.config.ts

The configuration file lives in the project root (next to package.json, not inside app/ or src/). Next.js accepts four spellings: next.config.ts, next.config.js (CommonJS, with module.exports), next.config.mjs and next.config.mts. The official reference states that .cjs and .cts are not supported; in the scratch app a next.config.cjs stops next typegen and next build with "Configuring Next.js via 'next.config.cjs' is not supported. Please replace the file with 'next.config.js', 'next.config.mjs', or 'next.config.ts'". TypeScript configuration (next.config.ts) arrived in Next.js 15.0 and is what create-next-app generates. The file is a regular Node.js module that runs when the CLI starts, so it can read process.env, compute values and import other modules, but it is not processed by Turbopack, webpack or Babel: avoid JavaScript syntax your Node.js version lacks.

The smallest useful file exports an object typed with NextConfig. The Bookshelf’s version below turns on the checks and hardening that every project should have and adds one redirect, one header rule and one remote image host.

next.config.ts for the Bookshelf (previous caching model)
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  reactStrictMode: true,
  poweredByHeader: false,
  typedRoutes: true,
  images: {
    remotePatterns: [
      { protocol: "https", hostname: "covers.example.com", pathname: "/covers/**" },
    ],
  },
  async redirects() {
    return [{ source: "/catalogue", destination: "/en", permanent: true }];
  },
  async headers() {
    return [
      {
        source: "/:path*",
        headers: [
          { key: "X-Content-Type-Options", value: "nosniff" },
          { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
        ],
      },
    ];
  },
};

export default nextConfig;

A function instead of an object

The default export may also be a function (sync or async) that receives the current phase and returns the configuration. Phases are string constants exported by next/constants; the function form is how you make a setting depend on whether Next.js is running the dev server, a production build or the production server. Async functions have been supported since Next.js 12.1.

next.config.ts as an async function of the phase
import type { NextConfig } from "next";
import { PHASE_DEVELOPMENT_SERVER, PHASE_PRODUCTION_BUILD } from "next/constants";

export default async function config(phase: string): Promise<NextConfig> {
  const isDev = phase === PHASE_DEVELOPMENT_SERVER;
  console.log(`[next.config] phase=${phase}`);
  return {
    reactStrictMode: true,
    poweredByHeader: false,
    typedRoutes: true,
    // Serve static assets from a CDN only in production builds.
    assetPrefix: phase === PHASE_PRODUCTION_BUILD ? "https://cdn.example.com" : undefined,
    allowedDevOrigins: isDev ? ["bookshelf.local"] : undefined,
    env: { BUILD_LABEL: "bookshelf-2026-10" },
  };
}

Running it shows when the file is evaluated. The log line appeared three or four times during one next build, so Next.js evaluates the file more than once; a configuration function must be free of side effects. In the scratch app next build printed [next.config] phase=phase-production-build and next dev printed [next.config] phase=phase-development-server; after a production build the HTML referenced https://cdn.example.com/_next/static/chunks/…​; for every script.

Source: Configuration as a Function and assetPrefix

next/constants exports PHASE_DEVELOPMENT_SERVER, PHASE_PRODUCTION_BUILD, PHASE_PRODUCTION_SERVER, PHASE_EXPORT, PHASE_TEST, PHASE_INFO and PHASE_ANALYZE (the seven names were listed from the installed package); their values are strings such as phase-development-server. The function also receives a second argument, an object holding the defaultConfig. next typegen loads the config with the production build phase, so it needs the same environment variables as a build. In the scratch app each command printed its own phase value, and a single next build printed the phase line three times, because the configuration is evaluated in more than one process.

Native ESM, top-level await and next.config.mts

Module resolution inside next.config.ts is limited to CommonJS semantics. On Node.js 22.10 or later, Next.js detects Node’s native TypeScript support through process.features.typescript, and the file can then use native ESM, including top-level await and dynamic import(). The feature is on by default from Node.js 22.18; on 22.10 to 22.17 you start the CLI with NODE_OPTIONS=--experimental-transform-types. In a CommonJS project the documentation recommends the .mts spelling so that Node.js knows the file is ESM from the start.

next.config.mts using a dynamic import (Node.js 22.10 or later)
import type { NextConfig } from "next";

// Top-level await and dynamic import() work in next.config.mts (Node.js 22.10+).
const flags = await import("./flags.mjs").then((m) => m.default);

const nextConfig: NextConfig = {
  typedRoutes: Boolean(flags.typedRoutes),
  poweredByHeader: false,
};

export default nextConfig;

With a one-line flags.mjs (export default { typedRoutes: true };) next to it, npx next typegen and npx next build both reported Running next.config.mts and loaded the flag on Node.js 24.16. A flags.js in a project without "type": "module" also works, but Node.js prints a MODULE_TYPELESS_PACKAGE_JSON warning because it has to reparse the file; naming it .mjs avoids that.

The caching-model switch used by the Bookshelf

cacheComponents is the one option that changes how the rest of the application is rendered, which is why the scratch app drives it from an environment variable (CACHE_COMPONENTS=1) read in the configuration function. Everything else in this page works in both models. When the option is on, next build prints Cache Components enabled before the route table, and the table uses the ◐ (Partial Prerender) symbol for routes that mix a static shell with streamed dynamic content. Later pages explain the model; here you only need to know where it is switched on.

Reading the switch from the environment (excerpt of the configuration function)
export default async function bookshelfConfig(phase: string): Promise<NextConfig> {
  return {
    // CACHE_COMPONENTS=1 -> Cache Components; unset -> the previous caching model
    cacheComponents: process.env.CACHE_COMPONENTS === "1",
    typedRoutes: true,
  };
}

What Next.js does with unknown and removed keys

The configuration is validated when it loads. An unknown key does not stop the build: it prints a warning that links to https://nextjs.org/docs/messages/invalid-next-config, which is easy to miss in CI logs. A few keys that were removed in earlier majors are fatal, with a message that names the replacement. This configuration, deliberately wrong, was built on Next.js 16.3.8 to show the output.

import type { NextConfig } from "next";

const nextConfig = {
  typedRoutes: true,
  reactStrictModee: true, // typo

  publicRuntimeConfig: { apiUrl: "/api" }, // removed in 16
  eslint: { ignoreDuringBuilds: true }, // removed in 16

The Option Catalogue

The official next.config.js reference has one page per option, 72 of them at @doc-version 16.3.8 (one of them, incrementalCacheHandlerPath, documents the cacheHandler key, and turbopackIgnoreIssue documents turbopack.ignoreIssue). This catalogue lists every one of them, grouped by purpose, with its status, the version where it appeared or changed where the documentation gives one, and a link to its page. Read it as an index: the option pages carry the full detail, and most options are expanded on the later page that uses them.

Three rules decide where a key goes in NextConfig, and putting a key in the wrong object is the most common reason an option is silently ignored.

  • Top level: stable options such as basePath, images or typedRoutes.

  • Under experimental: options marked experimental, for example experimental.staleTimes. Their names and behaviour may change in a minor release. The same rule holds for several options that have long been in use, such as experimental.serverActions for its allowedOrigins and bodySizeLimit settings. The tables write the full path of these keys.

  • A key that is not in the schema at all: a warning (see above), or an error for removed flags.

The status column uses four words. Stable means a documented top-level option. Experimental means the documentation page carries the experimental banner and the key lives under experimental. Legacy or deprecated means the page says so. Removed means the key is no longer in the schema.

Routing, URLs and Output

Table 3. Options that shape URLs, routing rules and the build output
Option Status and version What it does

basePath

Stable

Serves the app under a sub-path such as /docs. Set at build time: the value is inlined into client bundles. next/link applies it automatically; a static src passed to next/image needs it added by hand.

assetPrefix

Stable

Serves /_next/ assets from a CDN origin. Combine with the phase argument so development keeps local assets. Not needed on Vercel.

trailingSlash

Stable (9.5)

Redirects /about to /about/ when true (the default is the reverse). Files with extensions and .well-known paths are exempt.

skipTrailingSlashRedirect

Stable (13.1)

Turns off the automatic trailing-slash redirects so that Proxy can decide. An advanced Proxy flag.

skipProxyUrlNormalize

Stable. Renamed in 16.0 from skipMiddlewareUrlNormalize (13.1)

Lets Proxy see the original request URL instead of the normalised one. An advanced Proxy flag.

pageExtensions

Stable

Extensions treated as page files. The default is tsx, ts, jsx, js; add md and mdx for MDX pages.

redirects

Stable (9.5; has 10.2, missing 13.3)

An array of source, destination, permanent rules; 308 when permanent, 307 otherwise. Sync or async function.

rewrites

Stable (9.5; has 10.2, missing 13.3)

Maps a request path to another destination while keeping the URL, acting as a URL proxy. Also applied to client-side navigation.

headers

Stable (9.5; has 10.2, missing 13.3)

Adds response headers for matching paths. A function returning source plus a list of key and value pairs.

output

Stable

'standalone' traces the files each page needs and writes a self-contained .next/standalone folder with a minimal server.js (used by Docker deployments). Static HTML export is the other documented mode.

distDir

Stable

Replaces the .next build folder. It must stay inside the project. Since 16, next dev writes to .next/dev so dev and build can run at the same time.

exportPathMap

Legacy, deprecated

Belonged to the removed next export command. Use generateStaticParams (App Router) or getStaticPaths (Pages Router).

appDir

Legacy. Unnecessary since 13.4

Once enabled the App Router. In 16.3.8 the key is no longer in the schema and logs Unrecognized key(s).

Rendering, Caching and Deployment

Table 4. Options for the caching model, revalidation, deployments and server behaviour
Option Status and version What it does

cacheComponents

Stable flag, opt-in (16.0)

Turns on Cache Components and the use cache directive. One flag that replaces experimental.ppr, useCache and dynamicIO. Requires the Node.js runtime.

partialPrefetching

Stable flag, opt-in (16.3)

Prefetches only the static parts of each route by default (Instant Navigations). Requires cacheComponents; without it, next dev and next build throw at config validation.

cacheLife

Stable, needs cacheComponents

Defines named cache profiles (stale, revalidate, expire, in seconds) used by the cacheLife function inside use cache.

cacheHandlers

Stable (16.0)

Custom storage for use cache and use cache: remote. use cache: private cannot be customised. Most apps never need it.

cacheHandler

Stable. Renamed from incrementalCacheHandlerPath in 14.1; image-optimisation caching in 16.2

Custom store for the server cache: ISR pages, Route Handler responses and optimised images. Not used by use cache (that is cacheHandlers, plural).

cacheMaxMemorySize

Stable

Size in bytes of the in-memory cache per server instance (50 MB by default). Set 0 to disable it, for example when a custom cacheHandler takes over.

expireTime

Stable

The stale-while-revalidate expire time (in seconds) CDNs see in the Cache-Control header of ISR pages.

experimental.staleTimes

Experimental (14.2). Default dynamic changed from 30 s to 0 s in 15.0

Overrides how long the client router cache keeps dynamic and static page segments.

staticGeneration*

Experimental

experimental.staticGenerationRetryCount, staticGenerationMaxConcurrency and staticGenerationMinPagesPerWorker tune how next build generates static pages.

experimental.prefetchInlining

Experimental. Added in 16.2, on by default since 16.3

Bundles small prefetch responses into one request. Leave it on unless you are debugging navigation or measuring request volume.

experimental.serverComponentsHmrCache

Experimental

Caches Server Component fetch responses across hot-reload refreshes in development. Set false to see fresh data on each refresh.

htmlLimitedBots

Stable (15.2)

A regular expression of user agents that receive blocking metadata instead of streamed metadata.

reactMaxHeadersLength

Stable

Maximum length of the preload headers React emits while prerendering (6000 by default, App Router only). Lower it behind proxies that truncate long headers.

deploymentId

Stable (14.1.4; was experimental.deploymentId in 13.4.10)

An identifier for version-skew protection and cache busting. Next.js adds ?dpl= to asset URLs and detects a mismatch between client and server. Wins over the NEXT_DEPLOYMENT_ID variable.

generateBuildId

Stable

Returns a stable build ID (for example a git hash) so several containers built separately serve the same build. Has no effect when deploymentId is set.

generateEtags

Stable

ETag generation for pages is on by default; set false to disable it.

outputHashSalt

Stable (16.3)

A salt mixed into content-addressed output file names, to invalidate cached assets across deployments. NEXT_HASH_SALT is concatenated with it.

supportsImmutableAssets

Stable (16.3), for adapter authors

Lets static asset URLs omit the ?dpl parameter so browsers keep them across deployments. Enabling it on a platform that does not support it breaks the deployment.

adapterPath

Stable top-level since 16.2

Path to a deployment adapter module. NEXT_ADAPTER_PATH enables zero-config use on a hosting platform.

experimental.serverActions

Stable feature since 14; options live under experimental

allowedOrigins (extra hosts allowed to invoke Server Actions behind a proxy) and bodySizeLimit (1 MB by default).

experimental.authInterrupts

Experimental

Enables the forbidden() and unauthorized() functions and their forbidden.js and unauthorized.js files.

experimental.taint

Experimental

Enables React’s experimental_taintObjectReference and experimental_taintUniqueValue, turns on the React experimental channel for the app directory, and taints process.env so it cannot be passed whole to a Client Component. Not a security boundary on its own.

experimental.proxyClientMaxBodySize

Experimental

Limit (10 MB by default) on the request body Next.js buffers so that Proxy and the handler can both read it. Accepts a number of bytes or a string such as '1mb'.

Unit-testing the routing rules

Since 15.1 the experimental next/experimental/testing/server package contains unstable_getResponseFromNextConfig, which runs only the headers, redirects and rewrites of a configuration against a request. It ignores the Proxy and file-system routes, so use it for configuration regressions rather than end-to-end routing. The test below uses the built-in Node.js test runner; the .js suffix on the import is needed only because plain Node.js ESM does not resolve extensionless subpath imports (Vitest and Jest resolve next/experimental/testing/server as written in the reference).

Testing a redirect rule without starting the server
import assert from "node:assert/strict";
import { test } from "node:test";
import { getRedirectUrl, unstable_getResponseFromNextConfig } from "next/experimental/testing/server.js";

test("/catalogue redirects permanently to /en", async () => {
  const response = await unstable_getResponseFromNextConfig({
    url: "https://bookshelf.example.com/catalogue",
    nextConfig: {
      async redirects() {
        return [{ source: "/catalogue", destination: "/en", permanent: true }];
      },
    },
  });
  assert.equal(response.status, 308);
  assert.equal(getRedirectUrl(response), "https://bookshelf.example.com/en");
});

TypeScript

TypeScript is first-class in Next.js. A project made with create-next-app is already TypeScript; to add it to an existing project, rename a file to .ts or .tsx and run next dev or next build, which installs the missing packages and writes a tsconfig.json with the recommended options. If a jsconfig.json exists, copy its paths into the new tsconfig.json and delete it. The required levels are TypeScript 5.1 or later (an async Server Component returns a Promise, which only type-checks from TypeScript 5.1.3 with @types/react 18.2.8 or later; otherwise you see "`Promise<Element>` is not a valid JSX element").

The typescript key and the build

next build fails when the project has type errors. Two keys of the typescript object adjust that: tsconfigPath selects a different file (for example tsconfig.build.json that extends the main one and relaxes a check for the production build), and ignoreBuildErrors skips the type-checking step entirely, which the reference calls dangerous unless a separate type-check runs in CI. The configured path is used by next dev, next build and next typegen; in development only tsconfig.json is watched, so restart the dev server after editing a different file.

import type { NextConfig } from "next";

PageProps, LayoutProps and RouteContext

Next.js declares three global helper types, so they need no import. Each takes the route as a string literal and derives the shape from the folder tree: PageProps<'/blog/[slug]'> gives params (a Promise, since the sync access was removed in 16) and searchParams; LayoutProps<'/dashboard'> gives children, params and one prop per parallel route slot (@modal becomes modal); RouteContext<'/users/[id]'> gives the params of a Route Handler. A PageProps for a static route has params equal to {}. They are available once types have been generated.

Environment Variables

Next.js loads .env* files into process.env before it evaluates next.config.ts, so the configuration file itself can read them. Files are plain KEY=value lines. Multi-line values are allowed inside double quotes, and a $OTHER reference is expanded from another variable (escape a literal dollar as \$). Three rules decide what code can see a variable: the load order, the NEXT_PUBLIC_ prefix, and whether the code runs at build time or per request.

Files and load order

For each variable Next.js looks, in order, in: the real process environment, .env.$(NODE_ENV).local, .env.local (skipped when NODE_ENV is test), .env.$(NODE_ENV) and .env, and stops at the first place that defines it. NODE_ENV is development for next dev and production for every other command (build, start), and test only if a test runner sets it. The files are looked up in the project root, also when you use a src/ folder.

The order is easier to follow as a decision for one variable, as the next diagram shows. The reason for the test exception is reproducibility: tests should give the same result for everyone, so .env.local, the personal overrides, is ignored when NODE_ENV is test.

NEXT_PUBLIC_ inlining versus runtime reads

Variables without a prefix exist only in the Node.js process. To make a value available to browser code, prefix it with NEXT_PUBLIC_; at next build Next.js then replaces each process.env.NEXT_PUBLIC_* expression with the literal value from the environment of the build. The consequences follow from that: the value is public, it is frozen in the bundle, and changing the variable after the build has no effect. A single Docker image promoted from staging to production therefore keeps the staging value of every NEXT_PUBLIC_ variable.

Runtime environment variables

By default variables are only available on the server, and a NEXT_PUBLIC_ variable is a build-time constant. To read a value at runtime, read it on the server during dynamic rendering (after await connection() or another request-time API such as cookies() or headers()), in a Route Handler for a client that must discover its configuration, or in code that runs at startup through the register function of instrumentation.ts. A client that needs a runtime value fetches it from an endpoint or receives it as a prop from a Server Component; the guide states that you have to set up your own API for this. That is the pattern that lets one Docker image run in several environments.

Source: Runtime Environment Variables and Instrumentation

The env key of next.config.ts

The env key in the configuration defines build-time constants that always go into the bundle; the NEXT_PUBLIC_ prefix has no effect on them. The reference marks the key as legacy since 9.4. In the experiment, env: { BUILD_LABEL: "bookshelf-2026-10" } made process.env.BUILD_LABEL appear as the literal "bookshelf-2026-10" in the client chunk. Because destructuring process.env cannot be replaced, write process.env.BUILD_LABEL in full. Prefer .env files unless you need a value computed in next.config.ts, such as a Git hash.

Source: env

Pages Router differences

The Pages Router reads .env* files with the same rules and the same NEXT_PUBLIC_ inlining. For runtime values the guide recommends getServerSideProps (or adopting the App Router incrementally); getStaticProps runs at build time, so what it reads is frozen into the generated HTML and JSON.

Secrets and the NEXT_PUBLIC_ prefix

The prefix is a publication switch, not a naming style. NEXT_PUBLIC_ is correct only for values that are safe to show every visitor: a publishable payment key, an analytics identifier, a public site URL. Credentials of any kind (API secret keys, database URLs, CMS write tokens, signing secrets such as AUTH_SECRET) must carry no prefix and must be read only in server code: Server Components, Route Handlers, Server Actions and proxy.ts. A variable that is unprefixed stays out of the client bundle by construction, which is the protection to rely on. Keeping a .env file out of git protects the repository, not the browser: the file’s contents still reach the page if the name starts with the prefix.

Concrete rules for the Bookshelf code:

  • Keep every secret unprefixed, for example STRIPE_SECRET_KEY, SANITY_API_WRITE_TOKEN or DATABASE_URL, and import the module that reads it through import "server-only" so that a Client Component importing it fails the build.

  • Use the prefix only for values you would put in HTML anyway, such as NEXT_PUBLIC_SITE_URL.

  • After a build, search the client output for the secret’s value. A secret that appears under .next/static has leaked and must be rotated.

  • Never rely on the "frozen at build time" behaviour to hide a value: build artefacts and Docker layers are readable.

  • Values that differ per environment (an API host, a feature flag) are better as unprefixed variables read at request time than as NEXT_PUBLIC_ values, which would force a rebuild per environment. When a Docker image is built once and promoted, pass genuinely public values as build arguments, because setting them on the running container does nothing.

The data-security page of this section (Data Security & CSP) covers the Data Access Layer, server-only and the taint APIs in depth.

Source: Data security guide and Environment variables

The Removed Runtime Config

Older Pages Router projects configured values with serverRuntimeConfig and publicRuntimeConfig in next.config.js and read them with getConfig() from next/config. Both keys were removed in Next.js 16.0 and the next/config module is no longer in the package (no node_modules/next/config.js in 16.3.8). The scratch build confirms it: the keys are reported under "Unrecognized key(s) in object" (see the warning block above) and are ignored. The replacement is environment variables, with the split described above.

Absolute Imports and Module Path Aliases

Next.js reads the baseUrl and paths compiler options of tsconfig.json (or jsconfig.json), so import { Button } from '@/components/button' replaces '../../../components/button'. The generated file already contains "paths": { "@/": ["./"] }. A baseUrl makes every top-level folder importable by name, and paths adds named aliases whose targets are relative to baseUrl (or to the tsconfig.json when there is none). Turbopack, webpack, the type checker and the editor plugin all use the same mapping, so there is no second place to configure; test runners do need their own alias configuration.

tsconfig.json compilerOptions with a baseUrl and an extra alias
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["./*"],
      "@ui/*": ["components/*"]
    }
  }
}

Source: Set up Absolute Imports and Module Path Aliases

A page that uses all three forms
import { dict } from "lib/i18n"; // resolved through baseUrl
import { Nav } from "@ui/nav"; // resolved through paths
import { listBooks } from "@/lib/books";

export default async function Page() {
  const books = await listBooks();
  return (
    <main>
      <Nav locale="en" genre="sf" />
      <p>{dict.en.send}</p>
      <p>{books.length} books</p>
    </main>
  );
}

This built with next build (the page appeared as /en/abs and /es/abs in the route table), and tsc --noEmit accepted it. Without paths entries that match, an import such as @/app/…​ fails with Turbopack’s "Module not found: Can’t resolve '@/app/[locale]/books/[id]/book-detail'", which is what happened when the @/ alias was left out of the first attempt; aliases are not additive between extends files, so repeat the ones you need. When a project uses a src/ folder, .env files and next.config.ts stay in the root, and the usual alias becomes "@/": ["./src/"].

Source: Set up Absolute Imports and Module Path Aliases and Glossary

create-next-app asks Would you like to customize the import alias (@/* by default)?, and with the src/ option the default alias points at src/*. A baseUrl also lets bare specifiers such as components/nav resolve from a folder: the scratch app built and passed tsc on TypeScript 5.9 with "baseUrl": "." and an import of components/nav next to one of @/components/nav. Under TypeScript 7, however, baseUrl no longer exists (error TS5102, shown in the TypeScript section), so new code should use paths only, with entries resolved relative to the tsconfig.json when there is no baseUrl.

paths-only aliases that work without baseUrl
{
  "compilerOptions": {
    "paths": {
      "@/components/*": ["./components/*"],
      "@/lib/*": ["./lib/*"]
    }
  }
}

Keep .env* next to package.json, or load them with @next/env.

Tests do not see .env.local
