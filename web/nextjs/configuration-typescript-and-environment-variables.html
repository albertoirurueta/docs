Configuration, TypeScript & Environment Variables

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when everything below was checked; the official documentation @doc-version is also 16.3.8), React 19.3.0, Node.js 20.9 or later and TypeScript 5.1 or later. It describes the App Router; the places where the Pages Router differs are called out in the text. Configuration keys do not depend on the rendering model, but a few options (cacheComponents, partialPrefetching, cacheLife) only matter under Cache Components, which is still opt-in, while the rest of the page describes behaviour that is identical under the previous caching model (the default today, with fetch and GET Route Handlers uncached); where an example needs one or the other, it says so. The page is the reference for every project-level file: next.config.ts, tsconfig.json, next-env.d.ts, eslint.config.mjs, the .env* files and the import aliases. Every example was built and run on Next.js 16.3.8 in a scratch copy of the Bookshelf application with Node.js 24, in both caching models where it matters; the output blocks are real output from those runs, and each example is followed by the official page it derives from. The folder layout around these files is covered in Project Structure.

Where Configuration Lives

A Next.js project is configured by a small, fixed set of files in the project root. Each is read by a different tool at a different moment, which is what decides whether a change needs a restart, a rebuild or nothing at all.

Table 1. The configuration surfaces of a Next.js 16 project
File Owns Read by

next.config.ts (or .js, .mjs, .mts)

Framework behaviour: routing rules, caching model, images, headers, bundler options, build output, TypeScript and build flags, experimental flags.

The Next.js CLI at next dev, next build, next start and next typegen, at start-up and again in some build sub-processes. It runs in Node.js, is not bundled and is never sent to the browser. A change needs a restart of the dev server.

tsconfig.json

TypeScript compiler options, the next editor plugin, the paths aliases for absolute imports, and which generated type files are included.

tsc, the editor and the build’s type-check step. The bundler also reads paths to resolve aliases.

next-env.d.ts

References to Next.js’s own ambient types, regenerated for you.

TypeScript only. Never edit it.

eslint.config.mjs

Lint rules, through the eslint-config-next package and the ESLint CLI.

The eslint command that you run yourself, never next build (see ESLint With the Flat Config CLI).

.env, .env.local, .env.development, .env.production, .env.test and their .local variants

Values that differ between machines and environments: URLs, feature flags, secrets, and NEXT_PUBLIC_ values that are baked into client code.

Next.js loads them into process.env before it loads next.config.ts; loadEnvConfig from @next/env does the same for other tools.

package.json

Scripts, dependencies, the engines range and the "type" field that decides whether .js files are ESM.

Node.js and the package manager.

proxy.ts, instrumentation.ts

Request interception and start-up hooks. They are code rather than configuration and have their own pages.

At request time, and once on server start.

Source: next.config.js, TypeScript, ESLint and Environment Variables

The pieces interact. next.config.ts sets typedRoutes, which makes Next.js generate types that tsconfig.json must include, which tsc and the editor then check. A .env value feeds next.config.ts through process.env because the config file runs in Node.js with the environment already loaded. The sections below follow that order.

next.config.ts

The configuration file lives in the project root (next to package.json, not inside app/ or src/). Next.js accepts four spellings: next.config.ts, next.config.js (CommonJS, with module.exports), next.config.mjs and next.config.mts. The official reference states that .cjs and .cts are not supported; in the scratch app a next.config.cjs stops next typegen and next build with "Configuring Next.js via 'next.config.cjs' is not supported. Please replace the file with 'next.config.js', 'next.config.mjs', or 'next.config.ts'". TypeScript configuration (next.config.ts) arrived in Next.js 15.0 and is what create-next-app generates. The file is a regular Node.js module that runs when the CLI starts, so it can read process.env, compute values and import other modules, but it is not processed by Turbopack, webpack or Babel: avoid JavaScript syntax your Node.js version lacks.

The smallest useful file exports an object typed with NextConfig. The Bookshelf’s version below turns on the checks and hardening that every project should have and adds one redirect, one header rule and one remote image host.

next.config.ts for the Bookshelf (previous caching model)
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  reactStrictMode: true,
  poweredByHeader: false,
  typedRoutes: true,
  images: {
    remotePatterns: [
      { protocol: "https", hostname: "covers.example.com", pathname: "/covers/**" },
    ],
  },
  async redirects() {
    return [{ source: "/catalogue", destination: "/en", permanent: true }];
  },
  async headers() {
    return [
      {
        source: "/:path*",
        headers: [
          { key: "X-Content-Type-Options", value: "nosniff" },
          { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
        ],
      },
    ];
  },
};

export default nextConfig;

Source: next.config.js

The same configuration was built and started on port 3214 of the scratch app. The route table comes from next build, and curl confirms the effect of each key: poweredByHeader: false removes the x-powered-by header, headers() adds the security headers, and redirects() answers /catalogue with a permanent redirect before the Proxy runs.

A function instead of an object

The default export may also be a function (sync or async) that receives the current phase and returns the configuration. Phases are string constants exported by next/constants; the function form is how you make a setting depend on whether Next.js is running the dev server, a production build or the production server. Async functions have been supported since Next.js 12.1.

next.config.ts as an async function of the phase
import type { NextConfig } from "next";
import { PHASE_DEVELOPMENT_SERVER, PHASE_PRODUCTION_BUILD } from "next/constants";

export default async function config(phase: string): Promise<NextConfig> {
  const isDev = phase === PHASE_DEVELOPMENT_SERVER;
  console.log(`[next.config] phase=${phase}`);
  return {
    reactStrictMode: true,
    poweredByHeader: false,
    typedRoutes: true,
    // Serve static assets from a CDN only in production builds.
    assetPrefix: phase === PHASE_PRODUCTION_BUILD ? "https://cdn.example.com" : undefined,
    allowedDevOrigins: isDev ? ["bookshelf.local"] : undefined,
    env: { BUILD_LABEL: "bookshelf-2026-10" },
  };
}

Native ESM, top-level await and next.config.mts

Module resolution inside next.config.ts is limited to CommonJS semantics. On Node.js 22.10 or later, Next.js detects Node’s native TypeScript support through process.features.typescript, and the file can then use native ESM, including top-level await and dynamic import(). The feature is on by default from Node.js 22.18; on 22.10 to 22.17 you start the CLI with NODE_OPTIONS=--experimental-transform-types. In a CommonJS project the documentation recommends the .mts spelling so that Node.js knows the file is ESM from the start.

next.config.mts using a dynamic import (Node.js 22.10 or later)
import type { NextConfig } from "next";

// Top-level await and dynamic import() work in next.config.mts (Node.js 22.10+).
const flags = await import("./flags.mjs").then((m) => m.default);

const nextConfig: NextConfig = {
  typedRoutes: Boolean(flags.typedRoutes),
  poweredByHeader: false,
};

export default nextConfig;

With a one-line flags.mjs (export default { typedRoutes: true };) next to it, npx next typegen and npx next build both reported Running next.config.mts and loaded the flag on Node.js 24.16. A flags.js in a project without "type": "module" also works, but Node.js prints a MODULE_TYPELESS_PACKAGE_JSON warning because it has to reparse the file; naming it .mjs avoids that.

The Option Catalogue

The official next.config.js reference has one page per option, 72 of them at @doc-version 16.3.8 (one of them, incrementalCacheHandlerPath, documents the cacheHandler key, and turbopackIgnoreIssue documents turbopack.ignoreIssue). This catalogue lists every one of them, grouped by purpose, with its status, the version where it appeared or changed where the documentation gives one, and a link to its page. Read it as an index: the option pages carry the full detail, and most options are expanded on the later page that uses them.

Three rules decide where a key goes in NextConfig, and putting a key in the wrong object is the most common reason an option is silently ignored.

  • Top level: stable options such as basePath, images or typedRoutes.

  • Under experimental: options marked experimental, for example experimental.staleTimes. Their names and behaviour may change in a minor release. The same rule holds for several options that have long been in use, such as experimental.serverActions for its allowedOrigins and bodySizeLimit settings. The tables write the full path of these keys.

  • A key that is not in the schema at all: a warning (see above), or an error for removed flags.

The status column uses four words. Stable means a documented top-level option. Experimental means the documentation page carries the experimental banner and the key lives under experimental. Legacy or deprecated means the page says so. Removed means the key is no longer in the schema.

Environment Variables

Next.js loads .env* files into process.env before it evaluates next.config.ts, so the configuration file itself can read them. Files are plain KEY=value lines. Multi-line values are allowed inside double quotes, and a $OTHER reference is expanded from another variable (escape a literal dollar as \$). Three rules decide what code can see a variable: the load order, the NEXT_PUBLIC_ prefix, and whether the code runs at build time or per request.

Files and load order

For each variable Next.js looks, in order, in: the real process environment, .env.$(NODE_ENV).local, .env.local (skipped when NODE_ENV is test), .env.$(NODE_ENV) and .env, and stops at the first place that defines it. NODE_ENV is development for next dev and production for every other command (build, start), and test only if a test runner sets it. The files are looked up in the project root, also when you use a src/ folder.

The order is easier to follow as a decision for one variable, as the next diagram shows. The reason for the test exception is reproducibility: tests should give the same result for everyone, so .env.local, the personal overrides, is ignored when NODE_ENV is test.

NEXT_PUBLIC_ inlining versus runtime reads

Variables without a prefix exist only in the Node.js process. To make a value available to browser code, prefix it with NEXT_PUBLIC_; at next build Next.js then replaces each process.env.NEXT_PUBLIC_* expression with the literal value from the environment of the build. The consequences follow from that: the value is public, it is frozen in the bundle, and changing the variable after the build has no effect. Runtime environment variables

By default variables are only available on the server, and a NEXT_PUBLIC_ variable is a build-time constant. Pages Router differences

Secrets and the NEXT_PUBLIC_ prefix

The prefix is a publication switch, not a naming style. NEXT_PUBLIC_ is correct only for values that are safe to show every visitor: a publishable payment key, an analytics identifier, a public site URL. Credentials of any kind (API secret keys, database URLs, CMS write tokens, signing secrets such as AUTH_SECRET) must carry no prefix and must be read only in server code: Server Components, Route Handlers, Server Actions and proxy.ts. A variable that is unprefixed stays out of the client bundle by construction, which is the protection to rely on. Keeping a .env file out of git protects the repository, not the browser: the file’s contents still reach the page if the name starts with the prefix.

Concrete rules for the Bookshelf code:

  • Keep every secret unprefixed, for example STRIPE_SECRET_KEY, SANITY_API_WRITE_TOKEN or DATABASE_URL, and import the module that reads it through import "server-only" so that a Client Component importing it fails the build.

  • Use the prefix only for values you would put in HTML anyway, such as NEXT_PUBLIC_SITE_URL.

  • After a build, search the client output for the secret’s value. A secret that appears under .next/static has leaked and must be rotated.

  • Never rely on the "frozen at build time" behaviour to hide a value: build artefacts and Docker layers are readable.

  • Values that differ per environment (an API host, a feature flag) are better as unprefixed variables read at request time than as NEXT_PUBLIC_ values, which would force a rebuild per environment. When a Docker image is built once and promoted, pass genuinely public values as build arguments, because setting them on the running container does nothing.

Next.js reads the baseUrl and paths compiler options of tsconfig.json (or jsconfig.json), so import { Button } from '@/components/button' replaces '../../../components/button'. A Client Component read an unprefixed variable: the server-rendered HTML had the real value, the browser has none.

Read it in a Server Component, Server Action or Route Handler and pass the result down.

A secret appears in the browser bundle

It was given a NEXT_PUBLIC_ prefix, or put in the env key.

Remove the prefix, rotate the secret, and keep it in server-only modules.

A server variable is frozen at build time

It was read in a prerendered route without a request-time API.

Call await connection() first (inside <Suspense> with Cache Components).

A GET Route Handler returns the build-time value

Under Cache Components a handler without a dynamic API is prerendered (○ /api/env).

Add await connection().

The build fails with "Next.js encountered uncached or runtime data during prerendering"

connection(), cookies(), params or searchParams read outside <Suspense> under Cache Components.

Wrap the reading component in <Suspense>.

Variables in .env are not found in a monorepo or src/ layout

Files are read from the project root only.

Keep .env* next to package.json, or load them with @next/env.

Tests do not see .env.local

It is not loaded when NODE_ENV is test, so tests do not depend on a developer’s machine.

Put test values in .env.test.

Where the Books Are Outdated

Real-World Next.js (Riva, Packt, 2022) targets Next.js 12 and the Pages Router, and Practical Next.js for E-Commerce (Libby, Apress, 2023) targets 13.2, when the App Router was still in beta; both of those majors are out of support.
