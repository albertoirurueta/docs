Routing Fundamentals

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when the facts and examples below were checked; the official documentation reports @doc-version 16.3.8), React 19.3.0, Node.js 20.9.0 or later and TypeScript 5.1 or later. It teaches the App Router (the app/ directory) first and puts the Pages Router (the pages/ directory) and React Router next to it. Routing itself does not depend on the caching model, but two details do: reading params or a routing hook such as usePathname() while a route is prerendered. The examples use the previous model (cacheComponents off, the default), and a section near the end shows the small changes that the opt-in Cache Components model asks for. Every example was built with Next.js 16.3.8, Node.js 24.16 and npm 11.13 in a scratch copy of the Bookshelf — the catalogue of books, authors and reviews that the rest of this section grows, and that the Django and NestJS sections also build as a back end — and run with next start plus curl and a real browser; each one is followed by the official page it derives from.

Routing answers one question: given a URL, which components does the application render? Everything else in the section hangs from the answer, because in Next.js the route is also the unit of rendering, of code splitting, of caching and of data loading. This page explains the idea from first principles, shows how a React single-page app does it by hand, and then shows how Next.js moves the same decision into the folder structure and into the server. It does not re-teach React; for components, props and state read React Getting Started; for the library-level view of client routing read React Routing. The architecture behind the request, the RSC payload and the HTML is in Introduction and Architecture, and the folder conventions that surround app/ are in Project Structure. The special files that sit next to page are explained in Layouts, Templates and Special Files; this page only traces where template, loading and error land in the tree of a URL. The dynamic segment shapes are covered in depth by Dynamic Routes and Route Groups, the Link API, prefetching and the client cache by Linking and Navigation, and the advanced route types (parallel and intercepting routes, Route Handlers) by later pages of this section.

How Routing Works in a React Single-Page App

React renders a tree of components from state. It has no notion of a URL. A single-page app (SPA) therefore adds three things on top of React, and every client-side router is a variation of them:

  1. The browser’s History API to change the address bar without asking the server for a new document.

  2. A route table that matches the current URL (location.pathname) against patterns such as /books/:id.

  3. React state that holds the current location, so that a change re-renders the matching components.

Here is the whole mechanism without any library. It is not production code (no nested routes, no scroll handling, no data loading), but it is exactly what a router does:

A router in a few lines of plain TypeScript (the same code without types ran in a browser console)
const routes: Record<string, string> = { "/": "Home", "/books": "Books" };

function match(pathname: string): string {
  const m = pathname.match(/^\/books\/([^/]+)$/); // "/books/:id"
  return m ? `Book ${m[1]}` : (routes[pathname] ?? "Not found");
}

function render() {
  console.log("render:", match(location.pathname)); // React would set state here
}

// 1. Our own navigation: change the URL, then render. No request is made.
function navigate(to: string) {
  history.pushState(null, "", to);
  render();
}

// 2. The browser's back and forward buttons: popstate fires, we render again.
window.addEventListener("popstate", render);

navigate("/books/7"); // render: Book 7
navigate("/books");   // render: Books
history.back();       // render: Book 7  (popstate)

Running this in a page returned Book 7, Books and Book 7 again after history.back(). Two details matter later. history.pushState() does not fire popstate; only the back and forward buttons do, so a router must render itself after its own pushState. And the server is out of the loop: the first visit loaded one HTML document, the app’s JavaScript bundle, and from then on every "page" is a component switch. A SPA host therefore has to answer every path with the same index.html (a "fallback"), because /books/7 is not a file, and the browser asks for it when the user reloads or opens a shared link.

Source: MDN: History API

React Router packages the three pieces. This is the same Bookshelf shape as a declarative route object with a nested layout:

React Router: the route table is data, nesting is children and Outlet
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import {
  createBrowserRouter,
  Link,
  Outlet,
  RouterProvider,
  useParams,
} from "react-router";

function BooksLayout() {
  return (
    <section>
      <nav>
        <Link to="/books/1">Dune</Link>
      </nav>
      <Outlet /> {/* the matching child route renders here */}
    </section>
  );
}

function Book() {
  const { id } = useParams(); // string | undefined
  return <h1>Book {id}</h1>;
}

const router = createBrowserRouter([
  { path: "/", element: <h1>Bookshelf</h1> },
  {
    path: "/books",
    element: <BooksLayout />,
    children: [
      { index: true, element: <h1>All books</h1> },
      { path: ":id", element: <Book /> },
    ],
  },
]);

createRoot(document.getElementById("root")!).render(
  <StrictMode>
    <RouterProvider router={router} />
  </StrictMode>,
);

This file type-checks with tsc --strict against react-router 8.4.0 (the version on npm on 2026-10-03; the older react-router-dom package, which React Routing imports from, is a separate package that re-exports the same API, at 7.18.4 on the same date). Source: React Router: Routing

A SPA router has real strengths: instant transitions once the bundle is loaded, full control in JavaScript, and a static host is enough. It also has the weaknesses that motivate a framework router:

  • Nothing is rendered until the bundle runs. The first HTML is an empty shell; the content appears after the JavaScript has downloaded, executed and (usually) fetched data. Search engines and slow devices feel it.

  • The route table is code you maintain by hand, in a place that is not obviously connected to the files that implement each screen.

  • Code splitting is opt-in. Without lazy() per route the bundle contains every screen.

  • Data loading is a separate problem, solved per library (loaders in React Router, useEffect, a query library) and usually serial: route, then component, then request.

What a Framework Router Changes

A framework router keeps the client half (History API, Link, nested layouts) and adds three decisions that a library cannot make, because it does not own the server and the build:

Table 1. A React SPA router versus the Next.js App Router
Question React SPA with a router library Next.js App Router

Where is the route table?

In code: an array of route objects or JSX <Route> elements.

In the file system: folders are URL segments, page files make them reachable. The build derives the table.

Who matches the URL first?

The browser, after the bundle has loaded.

The server, on every request. The matching route’s layouts and page render on the server as Server Components.

What does a navigation fetch?

Possibly a lazy chunk, then whatever data the component asks for.

The RSC payload of the next route (the serialised UI tree), requested with a ?_rsc= parameter, plus Client Component chunks that are not loaded yet.

What does the first visit return?

An empty HTML shell plus the bundle.

Complete HTML of the page, plus the RSC payload for hydration. See the SSR, SSG and hydration pages of this section.

Code splitting

Manual (React.lazy per route).

Automatic per route segment, and Server Components add no client JavaScript at all.

Layouts

Hand-written nesting with Outlet.

The layout file of each folder; nesting follows the folders and the layout is kept alive across navigations.

Source: Layouts and Pages and Linking and Navigating

The consequence worth internalising is that Next.js routing is server-centric with client-side navigation. The server decides what a URL renders, in every case; the client just avoids reloading the document while it asks. The rest of the page follows that idea.

File-System Routing in the App Router

Next.js uses file-system based routing: the folders and files under app/ define the routes. Two kinds of names are involved.

  • Folders define route segments. A segment is one part of the URL path between slashes, so app/books/[id] contributes the two segments books and [id].

  • Files with reserved names define the UI shown for a segment. page is the one that makes a segment reachable, layout wraps the segment and its descendants, and route (a Route Handler, covered on its own page) answers with data instead of UI.

Three consequences are easy to miss:

  • Only page and route make a segment public. Any other file in a route folder (a helper, a test, a component) is colocated safely: it can never be reached by URL, and only what page returns is sent to the client. A build with app/books/format.ts and app/books/_components/helper.ts added produced exactly the same route table as one without them. Private folders are therefore optional; they are useful to group files and to avoid clashes with future file conventions, which the project-structure page of this section discusses.

  • Route groups do not change the URL, but they do change the tree. (marketing)/about is /about. Two groups that resolve to the same URL ((marketing)/about and (shop)/about) are a build error.

  • Dynamic segments return strings (or arrays of strings). params.id is '2', never 2, and unknown params are not an error by themselves: whether /books/99 is a 404 is decided by your code (notFound()) or by dynamicParams for statically generated params.

app/books/[id]/page.tsx
import Link from "next/link";
import { notFound } from "next/navigation";
import { getBook, listBooks } from "@/lib/books";

export async function generateStaticParams() {
  return (await listBooks()).map((b) => ({ id: b.id }));
}

export default async function BookPage({ params }: PageProps<"/books/[id]">) {
  const { id } = await params;
  const book = await getBook(id);
  if (!book) notFound();
  return (
    <article>
      <h1>{book.title}</h1>
      <p>{book.author}</p>
      <Link href={`/books/${book.id}/reviews`}>Reviews</Link>
    </article>
  );
}
app/books/[id]/reviews/page.tsx
import { listBooks, listReviews } from "@/lib/books";

export async function generateStaticParams() {
  return (await listBooks()).map((b) => ({ id: b.id }));
}

export default async function ReviewsPage({
  params,

  const { id } = await params;

Two small Client Components finish the example. MountedAt is a probe, used in the navigation section below: it records the moment it was mounted. BookNav is the usual "highlight the active link" component, and the reason a layout can know which child is active even though layouts do not receive the URL.

components/mounted-at.tsx
"use client";

import { useEffect, useState } from "react";

// The effect runs once per mount: if the timestamp does not change during
// navigation, the component was kept alive (it was not remounted).
export function MountedAt({ label }: { label: string }) {
  const [at, setAt] = useState<string | null>(null);
  useEffect(() => setAt(new Date().toISOString()), []);
  return (
    <p data-testid={label}>
      {label} mounted at {at ?? "..."}
    </p>
  );
}
components/book-nav.tsx
"use client";

import Link from "next/link";
import { useSelectedLayoutSegment } from "next/navigation";

export function BookNav({ books }: { books: { id: string; title: string }[] }) {
  const active = useSelectedLayoutSegment(); // "2" on /books/2/reviews, null on /books
  return (
    <ul>
      {books.map((b) => (
        <li key={b.id}>
          <Link
            href={`/books/${b.id}`}
            aria-current={active === b.id ? "page" : undefined}
          >
            {b.title}
          </Link>
        </li>
      ))}
    </ul>
  );
}

URL to Component Tree

The diagram maps one request through the three views of the Bookshelf: the folders, the URL segments they stand for, and the component tree React renders.

The mapping has a few rules that explain every behaviour in this page:

  1. Segments are matched left to right, one per folder. /books/2/reviews matches app, books, [id] and reviews.

  2. Each segment on the path contributes at most one layout, and the last segment contributes the page. Layouts nest from the root down; each receives the next level as children. The tree for /books/2/reviews is RootLayout, containing BooksLayout, containing ReviewsPage. There is no layout in [id] or reviews, so those segments add only a param and a page.

  3. A page is a leaf. books/[id]/page.tsx is the leaf of /books/2; it is not an ancestor of /books/2/reviews, even though its folder is. The two pages are siblings below the same layout.

  4. Params flow down. params is { id: '2' } for the page and, if it declared them, for layouts below the [id] segment. A layout above a dynamic segment does not see it.

  5. Layouts do not receive the URL. A layout is shared by many URLs, so it has no searchParams and no pathname. To react to the URL from a layout, use a Client Component with usePathname(), useSelectedLayoutSegment() or useSelectedLayoutSegments(), as BookNav does.

How a URL Is Matched: Priority and Conflicts

books/new, books/[id] and books/[...rest] all accept /en/books/new. Next.js resolves such overlaps with a fixed priority and rejects at build time the ones it cannot resolve. The dynamic routes page details each segment shape; this section collects the rules and runs them against the Bookshelf.

Priority: the most specific route wins

For one URL position, a static folder beats a dynamic [param] folder, which beats a catch-all [...param] (an optional catch-all [[...param]] is a catch-all that also matches its parent’s own URL). The comparison is made on whole routes: if the more specific branch fails further down the URL, a less specific route that matches the whole URL still wins over a 404.

Partial Rendering of Shared Layouts

A soft navigation does not re-render the page: it re-renders what differs. When you go from /books/2 to /books/2/reviews, the root layout and the books layout are the same, so React keeps them: their client state, their DOM, their focus, and any scroll position inside them survive, and their server-rendered output is not requested again. Only the [id] page is replaced by the reviews page. The docs state it in one sentence: on navigation, layouts preserve state, remain interactive, and do not rerender.

Three mechanisms cooperate:

  1. Prefetching. A Link that enters the viewport prefetches its route in the background. For a static route the whole route is prefetched; for a dynamic route, down to the nearest loading file, so the shared layouts and the loading fallback are ready before the click. prefetch={false} turns it off for long lists of links. Prefetching is enabled in production only (not in next dev), and it only starts after Link has hydrated.

  2. Layout deduplication and incremental prefetching (Next.js 16). When many prefetched URLs share a layout, the layout payload is downloaded once, and only the parts not already in the client cache are requested. You may see more, smaller prefetch requests than in Next.js 15; the total transfer is lower.

  3. Streaming and loading. If the target page is dynamic, the server streams the changed part. A loading file (or a <Suspense> boundary) lets the router show a fallback immediately and keep the shared layouts interactive and the navigation interruptible.

The corollary is a design rule: put state and expensive UI in the layout, and the things that change in the page. The reverse also holds, and is the most common surprise: a layout does not re-run when the URL changes within it. Code that must run on every navigation (a page-view counter, a form that resets, a useEffect with a per-page effect) does not belong in a layout; it belongs in the page or in a template, which remounts on every navigation and has its own page in this section.

That is the Pages Router’s well-known isReady gotcha; the App Router has no equivalent, because params is passed to the page on the server. Second, the page is a Client Component by nature (it uses a Hook), while an App Router page is a Server Component by default.

Source: Pages Router: useRouter and Per-page layouts

Both routers can coexist in one project, which is how an incremental migration works: app/ and pages/ side by side, Link navigating between them (a hard navigation between the two routers). They must not define the same URL. Adding pages/about.tsx next to the Bookshelf’s app/(marketing)/about/page.tsx fails next build with:

Error: App Router and Pages Router both match path: /about
Next.js does not support having both App Router and Pages Router routes matching the same path. Please remove one of the conflicting routes.

Under Cache Components

Routing does not change with cacheComponents: true, but two reads that the previous model tolerates are rejected at build time if they are not inside <Suspense>: runtime data (params of a segment that has no generateStaticParams, searchParams, cookies(), headers()) and routing hooks such as usePathname() and useSelectedLayoutSegment(). The first build of this page’s example without the final changes failed under Cache Components with blocking-prerender-client-hook (a hook read outside <Suspense>) and blocking-prerender-dynamic (params awaited outside <Suspense>). Both are fixed in the code above: BookNav is wrapped in a Suspense boundary in the layout, and both pages declare generateStaticParams, so the params are known at build time. With those two changes the same files build in both models; with CACHE_COMPONENTS=1 the build succeeded and the route table marked the /books/[id] and /books/[id]/reviews entries ◐ Partial Prerender, next to the prerendered ○ paths for ids 1 to 3. The caching and Partial Prerendering pages of this section explain the model; the two errors are documented at blocking-prerender-client-hook and blocking-prerender-dynamic.

The probe MountedAt itself needs care: a first version computed new Date() in the useState initialiser and was rejected by Cache Components (blocking-prerender-current-time-client), because the value would be frozen at build time. Reading the clock in an effect, as above, is the fix. The Instant Navigations of Next.js 16.3 (cacheComponents plus partialPrefetching) go one step further: the per-route app shell is prefetched so that a click shows the static and cached part of the next route at once. They are opt-in in 16.3.8 and are covered in the navigation page of this section.

Pitfalls

Table 17. Common routing mistakes and their fixes
Symptom Cause Fix

A route returns 404 although the folder exists

The folder has no page (or route) file, or the file is named Page.tsx or index.tsx. Reserved names are lower-case: page, layout, route.

Add page.tsx. In the App Router index.tsx has no special meaning.

A new file next to a page suddenly shows up as a URL

It was named page, or route, or a metadata convention such as icon, by accident.

Rename it. Other names are safe to colocate; use a _private folder to be explicit.

Error: App Router and Pages Router both match path

The same URL is defined in app/ and pages/, or two route groups resolve to the same path.

Remove one definition; migrate a route at a time.

params.id is undefined, or Property 'id' does not exist on type 'Promise'

Since Next.js 15 params is a Promise; Next.js 16 removed synchronous access.

const { id } = await params; in an async function. In a Client Component, use(params).

The layout does not update when I navigate

By design: a layout is kept alive within its segment. It receives neither the URL nor new searchParams.

Read the URL in a Client Component (usePathname, useSelectedLayoutSegment), or move the code to the page or to a template.

The whole page reloads, the layout state is lost and links are not prefetched

A plain <a> was used, or navigation crossed two root layouts, or window.location was assigned.

Use Link or router.push; keep one root layout unless the groups really are different documents.

useRouter imported from next/router in app/: NextRouter was not mounted

The Pages Router’s router is not available in the App Router.

Import from next/navigation; use usePathname, useSearchParams and useParams instead of router.query. In pages/, next/compat/router is the variant that does not throw.

router.query is empty on first render (Pages Router)

Automatic static optimisation: the router is not ready until the client has hydrated.

Wait for router.isReady in an effect, or read the value in getServerSideProps or getStaticProps.

Active-link highlighting is wrong or the build says "outside of Suspense"

usePathname(), useSelectedLayoutSegment() or params read in a layout that is prerendered under Cache Components.

Wrap the Client Component in <Suspense> and give dynamic segments generateStaticParams.

Search crawlers or users see /books/99 as 200 with an empty page

notFound() was thrown inside a streamed <Suspense> boundary after the response status was already sent. A loading file in any segment above the page is such a boundary (see Checking the trace in a browser).

Decide existence outside any <Suspense> boundary (as BookPage does), or accept a 200 and add noindex. The streaming page of this section covers the details.

Many tiny prefetch requests after upgrading to 16

Layout deduplication and incremental prefetching split prefetches into smaller requests.

Expected; the total bytes are lower. Use prefetch={false} on very long lists of links.

<Link> inside <Link>, or a button wrapped in a link

Invalid HTML: it renders nested <a> or an <a> containing interactive content, which breaks keyboard and screen-reader behaviour.

Style the Link as a button, or use router.push in a `button’s handler.

Ambiguous app routes detected at build time

Two dynamic folders at the same position, such as [id] and [slug] under books.

Keep one dynamic folder per position; put the other route under a static segment (books/by-slug/[slug]).

Conflicting route and page, Catch-all must be the last part of the URL, or two groups with one path

Overlapping routes with no winner.

See the conflicts table in Conflicts: the overlaps that fail the build.

A mistyped URL returns 200 instead of 404

A catch-all ([...rest]) or a permissive dynamic segment accepts it.

Validate the params in the page and call notFound(); for a known, finite set, dynamicParams = false with generateStaticParams.

/de/books renders a page in a language the site does not have

A dynamic root segment such as [lang] accepts any value.

export const dynamicParams = false next to generateStaticParams in app/[lang]/layout.tsx turns unknown values into 404s.

A Link to /api/... or to a file causes a full page load, and the Network panel shows a wasted prefetch

The router prefetches the URL as an RSC payload, gets JSON or a file, and falls back to a browser navigation.

Use a plain <a> for Route Handlers, downloads and other non-page URLs.

The template’s state resets on some navigations but not others, or a language switch resets every sidebar

A template is keyed by its child segment; a changed layout param ([lang]) makes every layout below it new.

See Soft and hard navigation, request by request. Keep state that must survive above the segment that changes, in the URL or in storage.

Client navigations through a CDN always reload the page

The CDN strips the rsc request header or caches one response for both variants, so the router receives HTML.

Forward rsc and the router headers, and include _rsc in the cache key, as the CDN guide describes.

Summary

  • Routing is the function from URL to component tree. A SPA computes it in the browser from a route table you write; Next.js computes it on the server from the folder structure, and the client router avoids document reloads.

  • Folders are segments, page makes them public, layout wraps the segment and everything below, and anything else is colocated and private. [id], [...slug], [[...slug]] and (group) shape params and URLs.

  • The tree for a URL is root layout, nested layouts, then one page; the page is a leaf, not an ancestor of its child routes.

  • Soft navigation (Link, router.push) fetches an RSC payload and keeps shared layouts alive; hard navigation (<a>, reload, crossing root layouts) is a new document.

  • Inside a segment the files nest as layout, template, error, loading, not-found, then the page or the next segment; a folder without files (such as [id] on the way to reviews) adds only a param.

  • Matching prefers static over dynamic over catch-all over optional catch-all, on whole routes; overlaps that have no winner (two dynamic siblings, route next to page, two groups with one URL) fail the build.

  • A soft navigation sends RSC: 1 and the client’s segment tree and receives only the changed segments; layouts keep their state, a template remounts when its child segment changes, and a changed layout param remounts everything below it.

  • The Pages Router does the same by files and by _app; coexistence is allowed but URLs must not overlap. React Router, the Pages Router and the App Router agree on the shape of the tree and on match priority, and differ on where it runs.
