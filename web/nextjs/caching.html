Caching

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when the facts and examples below were checked; the official documentation reports @doc-version 16.3.8), React 19.3.0 and Node.js 20.9.0 or later. It covers the App Router, where almost all of Next.js caching lives, and the small part that belongs to the Pages Router (The Pages Router). Next.js now has two caching models and a project uses exactly one of them: the previous model (the default: nothing is cached unless you ask, with fetch options, unstable_cache and the dynamic, revalidate and fetchCache segment config) and the opt-in Cache Components model (cacheComponents: true, with the 'use cache' directives, cacheLife and cacheTag). Every section says which model it describes. Every example was built with next build, started with next start (a few with next dev) and observed with curl, a counter on the data source and, for the client cache, a headless browser, on Next.js 16.3.8 and Node.js 24.16 in a scratch copy of the Bookshelf that the rest of this section grows; each example is followed by the official page it derives from, and every number, header and log line quoted below is a real measurement from those runs.

"Caching" is not one thing in Next.js; it is a stack of independent layers, each with its own key, lifetime and way to invalidate it. Most caching bugs come from invalidating one layer and forgetting the others. Incremental Static Regeneration explains the stale-while-revalidate loop and every revalidation API in depth, and Partial Prerendering and Cache Components explains the static shell and the prerender rules. This page is the map of all the layers: where each one lives, what it stores, how it is keyed, when it expires, what clears it, and how to see what it is doing. The sibling pages on data fetching, on Server Actions and mutations, and on Route Handlers and the backend for frontend of this section use these layers from the calling side.

How the Examples Were Measured

A cache is invisible until the thing behind it is counted. The experiments of this page use a lab inside the scratch app: a stand-in for the Bookshelf API (the "origin") that counts how often it is really called and returns the count with a timestamp. Whenever a layer answers instead of the origin, the number stays the same.

The origin: a Route Handler that counts its real calls (lib/source.ts and app/api/source/route.ts)
// lib/source.ts
import "server-only";

// Stands in for a slow upstream (CMS, database, REST API): counts how often it is really hit.
const g = globalThis as unknown as { __origin?: Record<string, number> };

export function originHit(label: string) {
  g.__origin ??= {};
  const n = (g.__origin[label] = (g.__origin[label] ?? 0) + 1);
  console.log(`[origin] ${label} hit #${n}`);
  return { label, n, at: new Date().toISOString().slice(11, 23) };
}

export const ORIGIN = "http://localhost:3603/api/source";

export async function readOrigin(label: string, init?: RequestInit) {
  const res = await fetch(`${ORIGIN}?label=${encodeURIComponent(label)}`, init);
  return (await res.json()) as { label: string; n: number; at: string };
}

Request Memoization (Both Models)

The cheapest layer is the one you rarely configure. During one server render, identical GET fetch calls are memoized: the layout, the page and generateMetadata can all ask for the same URL, and the request leaves the server once. This is separate from persistent caching: the memo lives for one render pass and is gone when the response is sent. For data that does not come from fetch (an ORM, a database driver, an SDK), React’s cache function gives the same per-render deduplication. Both are shown below with two components that need the same data.

Two components, one origin call per render (app/lab/memo/page.tsx, previous model)
// app/lab/memo/page.tsx
import { cache } from "react";
import { connection } from "next/server";
import { originHit, readOrigin } from "@/lib/source";

// Not a fetch: React cache() deduplicates it for the duration of one render pass.
const countOnce = cache(async () => originHit("react-cache"));

async function Header() {
  const book = await readOrigin("memo", { cache: "no-store" }); // same URL and options ...
  const again = await countOnce();
  return <p>header: fetch n={book.n}, cache() n={again.n}</p>;
}

async function Footer() {
  const book = await readOrigin("memo", { cache: "no-store" }); // ... so this reuses the answer
  const again = await countOnce();
  return <p>footer: fetch n={book.n}, cache() n={again.n}</p>;
}

export default async function Page() {
  await connection();
  return (
    <>
      <Header />
      <Footer />
    </>
  );
}

  • Memoization applies to GET requests with the same URL and options in the same render pass. It also covers generateStaticParams, generateMetadata and generateViewport.

  • It does not apply in Route Handlers, which are not part of the React tree.

  • Passing an AbortController signal to fetch opts that call out.

  • Inside 'use cache', React.cache has its own isolated scope: a value stored by React.cache outside a cached function is not visible inside it, and calls from two separate cached functions do not share one result.

Because memoization lives for a single render, it is the layer that makes "fetch where you need it" cheap: put the data call in the component that uses it instead of passing props down.

The Previous Model

This is what runs when cacheComponents is not set. The mental model is a default of "dynamic where the code needs it, static where it can": a route is prerendered at build time unless something in it needs the request (cookies(), headers(), searchParams, an uncached fetch after one of them, connection()), and data is cached only where you say so.

fetch and the Data Cache

Next.js extends fetch so that each call on the server can set its own persistent cache and revalidation. The cache option decides whether the server-side Data Cache is used:

Option Behaviour (16.3)

none (the default, called auto no cache)

Not cached. Fetched on every request in development, once during next build if the route is prerendered, and on every request if a request-time API is used on the route.

cache: 'no-store'

Fetched on every request, even without a request-time API; the route becomes dynamic.

cache: 'force-cache'

Looked up in the Data Cache. A request matches on URL, method, headers and body. A fresh match is returned; a missing or stale match fetches again and stores the response. Only 200 responses are stored.

next: { revalidate: false | 0 | n }

Cache lifetime in seconds. false means indefinitely, 0 means do not cache, n means at most n seconds. If two calls in one route differ, the lower value wins, and a value lower than the route’s revalidate lowers the route’s interval.

next: { tags: ['books'] }

Labels for on-demand invalidation with revalidateTag. At most 128 tags of 256 characters.

Combining options that contradict each other, such as { revalidate: 3600, cache: 'no-store' }, is not allowed: both are ignored and development prints a warning. The next example reads the origin four ways in one render; the page calls connection() first so it renders per request, which lets us watch the Data Cache without a Full Route Cache in front:

unstable_cache for Everything That Is Not a fetch

Database queries, ORM calls and SDK calls do not go through fetch, so they miss the Data Cache. unstable_cache(fn, keyParts, { tags, revalidate }) wraps such a function so that its result is stored in the same Data Cache, with the same tags and the same stale-while-revalidate behaviour. The arguments and the stringified function are already part of the key; keyParts is only needed when the function reads outside variables that are not passed as arguments.

Caching a non-fetch function (app/lab/unstable/page.tsx, previous model)
// app/lab/unstable/page.tsx
import { unstable_cache } from "next/cache";
import { connection } from "next/server";
import { originHit } from "@/lib/source";

// Persists across requests (and deployments) in the data cache, like a tagged fetch.
const getBookRow = unstable_cache(
  async (id: string) => originHit(`unstable-cache:${id}`),
  ["book-row"], // key prefix; the arguments are added to the key automatically
  { tags: ["books"], revalidate: 5 },
);

export default async function Page() {
  await connection();
  const [one, two] = await Promise.all([getBookRow("1"), getBookRow("2")]);
  return <pre>{JSON.stringify({ one, two })}</pre>;
}

The two arguments make two entries. Because it shares the tag books with the tagged fetch of the previous example, one revalidateTag('books', …​) call refreshed both.

Cookies, headers and other request data cannot be read inside the wrapped function; read them outside and pass the values in. The name is historical: unstable_cache was introduced in 14.0 and, as of 16, the official docs mark it as replaced by 'use cache'. It remains the way to cache a non-fetch function in the previous model, and it is also the one that survives deployments (see fetch and unstable_cache Under Cache Components).

The Full Route Cache and the Segment Config

The Full Route Cache is the server-side store of prerendered routes: for every route that has no request-time dependency, next build stores the HTML and the RSC payload, and ISR regenerates them later (see Static Site Generation and Incremental Static Regeneration). You steer it with three route segment config exports from a page, layout or Route Handler:

Export Values and effect

dynamic

'auto' (default: cache as much as possible without blocking dynamic behaviour); 'force-dynamic' (render per request, like every fetch being { cache: 'no-store', next: { revalidate: 0 } }); 'error' (fail the build if anything is dynamic, like getStaticProps); 'force-static' (prerender and make cookies(), headers() and useSearchParams() return empty values).

revalidate

false (default, cache indefinitely), 0 (always dynamic), or a number of seconds. It must be statically analyzable (600, not 60 * 10). The lowest value across the layouts and the page of a route wins, and it does not override next.revalidate of individual fetches.

fetchCache

An advanced override of the default cache of every fetch in a segment: 'auto', 'default-cache', 'only-cache', 'force-cache', 'force-no-store', 'default-no-store', 'only-no-store'. The only- values throw when a fetch contradicts them; force- wins over only- across the segments of one route; a parent cannot use 'default-no-store' if a child uses 'auto' or a -cache value.

The Client Router Cache and staleTimes

The browser keeps its own cache of RSC payloads, so that moving between pages sends only the segments that changed and back and forward buttons are instant (Linking and Navigation shows how <Link> prefetching feeds it). Its lifetime is the one cache setting most people have never touched. In the previous model the defaults since 15 are:

  • Dynamic pages (not statically generated and not fully prefetched): staleTimes.dynamic = 0 seconds, so every click on a link requests the page again. In 14 the value was 30 seconds.

  • Static pages, or links with prefetch={true}: staleTimes.static = 5 minutes.

  • Layouts and loading boundaries are still reused, because only the segment that changes is requested.

  • Back and forward navigation restores the entry regardless, to keep scroll position and avoid layout shift.

staleTimes is the option to change them. The docs still label it experimental, so it sits under experimental in 16.3:

// next.config.ts (previous model)
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  experimental: {
    staleTimes: {
      dynamic: 30, // seconds
      static: 180,
    },
  },
}

export default nextConfig

Cache Components

This is what runs when cacheComponents: true. The default flips: everything that needs data at request time is dynamic, and you choose what to cache, at the level of a function, a component or a whole file, with the 'use cache' directive. Next.js prerenders a static shell (HTML plus RSC payload) from everything that can finish at build time, including the results of cached functions, and streams the rest behind <Suspense> boundaries (Partial Prerendering, the subject of Partial Prerendering and Cache Components). The route segment config of the previous model is replaced: a route that exports dynamic, revalidate or fetchCache fails the build (the exact message is in 'use cache': Forms, Keys and Restrictions); cacheLife and cacheTag take over the lifetime and invalidation roles.

'use cache': Forms, Keys and Restrictions

The directive caches the return value of an async function or component. It can sit at the top of a function body (function or component level), or at the top of a file, where every export becomes a cached async function (including generateMetadata and generateStaticParams, which must then be async). A page or layout file is a module like any other, so a file-level directive caches that whole segment, and a cached layout does not cache the children it renders, because slots pass through unread. A file with the directive at its top can have its exports imported into a Client Component and called there, running on the server like a Server Function; prefer calling them on the server and passing results down.

What Makes Up the Key

The entry of a cached function is stored under a key built from:

  1. the build id (or the deploymentId when one is configured, which overrides it), so a new build invalidates everything

  2. the function id, a secure hash of the function’s location and signature

  3. the serialized arguments: props of a component, parameters of a function

  4. in development only, an HMR refresh hash

A variable captured from an enclosing scope is bound as an argument automatically, so it becomes part of the key too. Different inputs mean different entries; the same inputs mean one entry shared by every user and every request.

Arguments and captured values are the key (app/lab/keys/page.tsx, Cache Components)
// app/lab/keys/page.tsx
import { Suspense } from "react";
import { cacheLife } from "next/cache";
import { readOrigin } from "@/lib/source";

async function getBook(id: string) {
  "use cache";
  cacheLife("lab"); // custom profile from next.config.ts: stale 30, revalidate 5, expire 60
  return readOrigin(`keys-book-${id}`); // the id argument is part of the cache key
}

async function Books({ searchParams }: { searchParams: Promise<{ id?: string; lang?: string }> }) {
  const { id = "1", lang = "en" } = await searchParams;

  // A value captured from the enclosing scope becomes part of the key as well.
  const getTitle = async () => {
    "use cache";
    cacheLife("lab");
    return readOrigin(`keys-title-${id}-${lang}`);
  };

  const [a, b, title] = await Promise.all([getBook(id), getBook(id), getTitle()]);
  return <pre>{JSON.stringify({ first: a, second: b, title })}</pre>;
}

export default function Page(props: PageProps<"/lab/keys">) {
  return (
    <Suspense fallback={<p>loading</p>}>
      <Books searchParams={props.searchParams} />
    </Suspense>
  );
}

Serialization

Arguments and return values must be serializable, with two different rules: arguments use the Server Components serialization (stricter), return values the Client Components one. Supported arguments are primitives, plain objects, arrays, Date, Map, Set, typed arrays and ArrayBuffer, and React elements as pass-through only; return values add JSX. Class instances, functions (except pass-through), symbols, WeakMap, WeakSet and URL instances are not supported. Pass-through means the cached function accepts a value it never reads: children, other slots and Server Actions can flow through a cached component without becoming part of its key, which keeps a cached wrapper around dynamic content valid:

  return (
    <section>
      <p>cached header: origin n={book.n} at {book.at}</p>
      {children}

}

  await connection();
  const book = await readOrigin("wrapper-live");
  return <p>live child: origin n={book.n} at {book.at}</p>;
}

  return (
    <CachedWrapper>
      <Suspense fallback={<p>loading</p>}>

cacheTag and Invalidation by Tag

cacheTag('a', 'b') labels the entry of the enclosing cached scope; a single call accepts up to 128 tags of at most 256 characters (extra or longer tags are dropped or skipped with a console warning). Tags are idempotent and case-sensitive, and may be computed from the data (cacheTag('book', data.id) after the fetch). The labels are what revalidateTag and updateTag act on. Next.js also attaches soft tags to every entry, derived from the route (N_T/layout, N_T/books/layout, N_T/books/1…​), which is how revalidatePath reaches entries through the same mechanism and what a custom cache handler receives as softTags in get().

The invalidation API is small and the difference between its members is a choice about who waits:

Call Where Behaviour

updateTag(tag)

Server Actions only

Expires the tag now: the next read waits for fresh data. Read-your-own-writes after a mutation.

revalidateTag(tag, 'max')

Server Actions and Route Handlers

Marks the tag stale; the next request is served stale content while a refresh runs. The profile ('max' = one-year window, any cacheLife profile, or { expire: seconds }) says how long stale content may still be served.

revalidateTag(tag, { expire: 0 })

Server Actions and Route Handlers

Never serves stale: the next request blocks on fresh data. The one-argument form revalidateTag(tag) is deprecated and behaves like this.

revalidatePath(path, type?)

Server Actions and Route Handlers

Invalidates the entries of a route (or a layout and below) through the soft tags.

refresh()

Server Actions only

Refreshes the client router for the current page; does not touch the server caches.

None of them can be called from a Client Component or from Proxy. A revalidation is triggered by the next request, not by the call. Revalidating by tag from a Route Handler (app/api/revalidate/route.ts, both models)
// app/api/revalidate/route.ts
import { revalidateTag } from "next/cache";
import type { NextRequest } from "next/server";

export async function POST(request: NextRequest) {
  if (request.headers.get("x-revalidate-secret") !== process.env.REVALIDATE_SECRET) {
    return Response.json({ ok: false }, { status: 401 });
  }
  const tag = request.nextUrl.searchParams.get("tag");
  if (!tag) return Response.json({ ok: false }, { status: 400 });
  const expire = request.nextUrl.searchParams.get("expire");
  revalidateTag(tag, expire === "0" ? { expire: 0 } : "max");
  return Response.json({ ok: true, tag, expire: expire === "0" ? 0 : "max" });
}

'use cache: remote' and cacheHandlers

The default 'use cache' stores entries in memory, which has limits: entries are evicted, memory is finite, and on serverless platforms each instance is short-lived with its own memory, so a runtime entry is rarely reused. 'use cache: remote' stores the output in a remote cache handler instead, shared by every instance and surviving restarts, at the price of a network lookup and storage cost. It pays off for content that is deferred to request time (read behind cookies(), headers() or searchParams inside <Suspense>) and expensive or fragile to compute: rate-limited APIs, slow databases, costly aggregations, flaky services. Avoid it when operations already take under about 50 ms, when keys are mostly unique per request (search filters, per-user ids: near-zero hit rate), or when the data changes every few seconds. Cache on the dimension with few values (category, language) and filter the rest in memory.

Nesting rules: a remote cache may sit inside a remote or a regular cache; it cannot sit inside a private one, and a private cache cannot sit inside a remote one.

The handler that stores it is configured with cacheHandlers (plural; see below for the singular one). Two names are built in: default serves 'use cache' and remote serves 'use cache: remote'; extra names can be used as 'use cache: <name>'. Without configuration both use an in-memory LRU. A handler implements five methods: get(cacheKey, softTags) (return undefined for a missing or expired entry), set(cacheKey, pendingEntry) (await the pending entry, whose value is a ReadableStream), refreshTags() (called before a request, to sync tag state in a cluster), getExpiration(tags) (the most recent revalidation timestamp for those tags, 0 for none, Infinity to check soft tags in get) and updateTags(tags, durations) (invalidate entries with those tags). A CacheEntry has value, tags, stale, timestamp, expire and revalidate. This minimal handler keeps entries in a Map and logs every call; it is not for production (a real one talks to Redis, DynamoDB or similar and must catch its own errors, since an exception thrown from refreshTags() or get() fails the request):

A logging in-memory handler (cache-handlers/remote.cjs)
// A minimal in-process "remote" handler that logs every call. A production handler
// would talk to Redis, DynamoDB or another store shared by all instances.
const cache = new Map();
const pending = new Map();
const log = (...a) => console.log("[handler:remote]", ...a);

module.exports = {
  async get(cacheKey, softTags) {
    const p = pending.get(cacheKey);
    if (p) await p;
    const entry = cache.get(cacheKey);
    log("get", cacheKey.slice(0, 40), entry ? "HIT" : "MISS", "softTags=" + softTags.length);
    if (!entry) return undefined;
    if (Date.now() > entry.timestamp + entry.revalidate * 1000) return undefined;
    // the stored stream can be read once: hand out a copy
    const [a, b] = entry.value.tee();
    entry.value = b;
    return { ...entry, value: a };
  },
  async set(cacheKey, pendingEntry) {
    let done;
    pending.set(cacheKey, new Promise((r) => (done = r)));
    try {
      const entry = await pendingEntry;
      log("set", cacheKey.slice(0, 40), "tags=" + entry.tags.join(","));
      cache.set(cacheKey, entry);
    } finally {
      done();
      pending.delete(cacheKey);
    }
  },
  async refreshTags() {},
  async getExpiration() {
    return 0;
  },
  async updateTags(tags) {
    log("updateTags", tags.join(","));
    for (const [key, entry] of cache) {
      if (entry.tags.some((t) => tags.includes(t))) cache.delete(key);
    }
  },
};

Prerendered Shells, App Shell and ISR

The layer that most users see without configuring anything is the prerendered shell: at build time Next.js renders the component tree, completes everything that can finish (cached functions whose lifetime is long enough, module imports, pure computation) and stores the result as static HTML and an RSC payload; the holes (<Suspense> boundaries around request-time work) are filled when the request arrives, by resuming the render. When the params of a dynamic route are not known at build time, the reusable, URL-independent shell is the App Shell, served instantly and upgraded in the background with the concrete params (ISR with Cache Components, 16.3). Where the shell lives, how it is resumed and how a CDN can serve it are in Partial Prerendering and Cache Components and Incremental Static Regeneration; for caching purposes remember two points. The shell is a cache like any other: its lifetime comes from the cached scopes it contains (the single hours scope of ◐ /lab/shell 1h 1d above), and updateTag/revalidateTag of a tag used in it regenerates it. And bots and crawlers are detected by user agent and get a complete document rendered at request time instead of the shell, so everything the shell used at build time must also be reachable at request time.

Source: Caching: prerendering, ISR with Cache Components

The Client Cache

With Cache Components the browser keeps the cached content of visited and prefetched routes in memory, and its freshness is the stale of the cacheLife profiles involved. The server communicates it with the x-nextjs-stale-time response header, the router enforces a minimum of 30 seconds so that prefetched links stay usable until clicked, and the lifetime applies only to time-based expiry: any Server Action that calls revalidateTag, revalidatePath, updateTag or refresh clears the whole client cache immediately. This stale is per function or per route; staleTimes of the previous model is a global setting (and updating staleTimes.static also updates the stale of the default profile). 'use cache: private' results live only here. 16.3 adds partialPrefetching, which prefetches each route’s App Shell by default and, with <Link prefetch={true}>, the cached content that depends on the link’s URL data (see Linking and Navigation).

curl shows the header; on the lab’s fully cached page (stale: 120) it was x-nextjs-stale-time: 120, on a route whose scopes use the default profile 300. A headless browser confirmed the effect: a <Link> to /lab/cached-page sent no RSC request on the click (0 requests on three clicks), because its content had already been prefetched and was fresh for 120 seconds.

Note the asymmetry of a partial prerender. The static shell is stored as a prerender, but the response of a route that also streams holes is a live, per-request response, so Next.js itself marks it non-cacheable; a CDN that wants to serve the shell from the edge must be able to resume the postponed holes (see Partial Prerendering and Cache Components). A fully prerendered route is the one a plain CDN can cache with the headers above.

What a CDN must get right, per the official CDN guide:

  • Honour s-maxage and stale-while-revalidate and cache the HTML and the RSC payload of a route together, with the same lifetime and invalidation, otherwise client navigation can show different content from a page load.

  • Respect Vary. App Router responses vary on rsc, next-router-state-tree, next-router-prefetch, next-router-segment-prefetch and, for interception routes, next-url. For CDNs that ignore Vary, Next.js adds an _rsc query parameter, a hash of those header values, that must stay in the cache key. A request with rsc: 1 but without the right _rsc value gets a 307 to the URL with the correct hash (observed), which the CDN must follow.

  • Never strip the rsc request header: the server would answer with HTML where the client router expects an RSC payload and navigation would fall back to full page loads.

  • Purge on demand revalidation. revalidateTag and revalidatePath invalidate the Next.js server cache only. The CDN keeps its copy until s-maxage ends, so call the CDN purge API for the affected URLs (both variants) right after the Next.js call.

  • Run Proxy before the CDN cache, or bypass the CDN for routes whose behaviour depends on proxy.ts decisions (see Redirects, Rewrites and Proxy).

  • Static assets under /_next/static/ are immutable and can be cached for a year; assetPrefix serves them from another origin. The official guide also describes a direction of travel: moving every cache-affecting input into the URL pathname so that Vary and _rsc are no longer needed. It is still design work in 16.3.

The stale-while-revalidate and s-maxage directives are the standard ones of HTTP caching (RFC 9111 and RFC 5861); expireTime in next.config lowers the one-year default of the second number for every ISR page of the previous model (see Incremental Static Regeneration).

The Pages Router

The Pages Router has a much shorter list of caches, none of which is controlled by cacheComponents (Cache Components, 'use cache' and the segment config belong to the App Router): a page is statically generated with getStaticProps (optionally with revalidate, which is ISR), rendered per request with getServerSideProps, or neither. The server cache behind ISR is the one that cacheHandler (singular) replaces, and res.revalidate() is the on-demand call. getServerSideProps has no cache of its own, so the only way to cache its responses is a Cache-Control header, which is set by the page and honoured by a CDN:

The two caching modes of a Pages Router page (pages/lab-pages/ssr-cached.tsx and static-isr.tsx)
// pages/lab-pages/ssr-cached.tsx
import type { GetServerSideProps } from "next";

type Props = { renderedAt: string };

export const getServerSideProps: GetServerSideProps<Props> = async ({ res }) => {
  // Fresh for 10 s at a shared cache, then stale-while-revalidate for 59 s.
  res.setHeader("Cache-Control", "public, s-maxage=10, stale-while-revalidate=59");
  return { props: { renderedAt: new Date().toISOString() } };
};

export default function Page({ renderedAt }: Props) {
  return <p>getServerSideProps rendered at {renderedAt}</p>;
}
// pages/lab-pages/static-isr.tsx
import type { GetStaticProps } from "next";

type Props = { builtAt: string };

export const getStaticProps: GetStaticProps<Props> = async () => ({
  props: { builtAt: new Date().toISOString() },
  revalidate: 5, // ISR: regenerate at most once every 5 seconds
});

export default function Page({ builtAt }: Props) {
  return <p>getStaticProps generated at {builtAt}</p>;
}

Observed: /lab-pages/ssr-cached answered with Cache-Control: public, s-maxage=10, stale-while-revalidate=59 and rendered anew on every request that reached the server (the timestamp changed between two requests); /lab-pages/static-isr answered Cache-Control: s-maxage=5, stale-while-revalidate=31535995 with x-nextjs-cache: STALE once the 5 seconds had passed and the regenerated page on the next request (the generation timestamp moved from 15:06:01 to 15:06:24 and then 15:06:30). The build table lists it as ● /lab-pages/static-isr 5s 1y under Route (pages). For getServerSideProps the official advice is to consider getStaticProps with ISR first and use the header only when the response is genuinely per-request but safe to share for seconds.

Self-Hosting, Instances and Deployments

Three facts decide how caching behaves outside a managed platform:

  • One instance, one cache. The default 'use cache' handler is an in-memory LRU per Node.js process and the server cache of ISR is a file-system cache of that machine. Several instances behind a load balancer each have their own, and a revalidation call reaches only the instance that received it. A shared cacheHandler and a shared cacheHandlers store, coordinated through updateTags() and refreshTags(), are the answer; Incremental Static Regeneration works through a multi-instance setup.

  • Serverless instances are short-lived, so runtime 'use cache' entries are rarely reused. Build-time caching works normally. Use 'use cache: remote' for the expensive ones, and measure with cacheMaxMemorySize: 0 first.

  • A deployment starts clean. The build id (or deploymentId) is part of every 'use cache' key and the Full Route Cache is rebuilt, so the first visits after a deploy recompute. Only the fetch Data Cache and unstable_cache persist. During a rolling deploy, set deploymentId so that a client of deploy A that meets a server of deploy B does a hard navigation instead of mixing payloads.

Source: Self-hosting: Caching and ISR, How revalidation works: multi-instance considerations

Debugging Caches

A cache bug always has the same shape: a value that is older, or newer, than you expect. Work from the outside in.

  1. Build output. The route table tells you what was prerendered: ○ static, ● generateStaticParams, ƒ dynamic, ◐ partial prerender, plus Revalidate and Expire columns. A route you thought was cached and shows ƒ has a request-time API or a no-store fetch somewhere below it.

  2. Response headers. curl -I shows Cache-Control (what a CDN will do), x-nextjs-cache (HIT, STALE, MISS, REVALIDATED; self-hosted only), x-nextjs-prerender and x-nextjs-stale-time (what the client will do).

  3. Count the origin. Put a counter, a log line or a timestamp on the data source, as the lab does. "Is it the Next.js cache or my own?" is answered by whether the counter moved.

  4. Verbose cache logs. NEXT_PRIVATE_DEBUG_CACHE=1 npm run start (or dev) logs every cache operation, including ISR, the file-system cache and use cache. A shortened excerpt from the log while the lab’s fully cached page was requested after its 5 second revalidate had passed:

Common Pitfalls

  • Invalidating one layer and forgetting the next. A tag call updates the server; the CDN keeps its copy until you purge it, and an open browser tab keeps its own until a Server Action clears it or the stale time passes.

  • Assuming fetch is cached. It was in 13 and 14; it is not in 15 and 16. The same page can feel fast in one version and slow in the next.

  • One cache: 'no-store' fetch deep in the tree makes the whole route dynamic in the previous model; it shows as ƒ in the build table.

  • Mixing fetchCache with per-call cache options. The measured result contradicted the docs on 16.3.8 (see above); use one mechanism.

  • unstable_cache and captured variables. Variables read from outside are not part of the key unless you pass them in the arguments or in keyParts; two different closures can then share one entry.

  • Per-user data in a shared cache. 'use cache' and 'use cache: remote' are shared by all users. The user id (or its absence) must be part of the key; with fetch, force-cache on a credentialed request stores a personal response server-wide.

  • Over-keying. A cache keyed by a search string, a price range or a user id has a near-zero hit rate and fills memory. Cache the shared slice and filter in memory, especially for 'use cache: remote'.

  • No cacheLife. The default profile (15 minutes) is applied silently and a short inner lifetime can shorten an outer one; name a profile in every 'use cache' scope.

  • Reading cookies() inside 'use cache'. It fails; read it outside and pass the value.

  • Expecting entries to survive a deploy. 'use cache' keys contain the build id; fetch and unstable_cache data survive.

  • Expecting a shared cache on serverless. The in-memory handler is per instance; use 'use cache: remote' or accept that runtime entries are rarely reused.

  • Treating x-nextjs-cache as an API. It is a diagnostic of a self-hosted server and may change.

  • Revalidation endpoints with secrets in the URL, or on GET. Use POST, a header secret or a verified signature, and never put the secret in the query string.

  • Single-argument revalidateTag(tag). Deprecated since 16; use 'max', a profile or { expire: 0 }, or updateTag in a Server Action.

  • Trusting next dev. Development does not cache pages and behaves differently for fetch; confirm with next build and next start.

  • Bots and crawlers skip the static shell and render everything at request time; data the shell used at build time must be reachable then too.

Where the Books Are Outdated

The two reference books were written for the Pages Router, before any of the App Router caches existed. Their caching material is correct for the Pages Router and incomplete for everything else:

The books say Today

Pages are cached through getStaticProps with revalidate (ISR), and a response is cached by setting Cache-Control with s-maxage and stale-while-revalidate in getServerSideProps

Still valid in the Pages Router (and shown above). In the App Router the same ideas are revalidate/cacheLife, fetch options and 'use cache', and Next.js writes the Cache-Control header itself.

There is one cache to think about: the server’s

There are up to five layers (The Layers at a Glance), and most surprises come from the client router cache, the CDN or the Data Cache.

Client libraries (an Apollo InMemoryCache, SWR, TanStack Query) are the data cache of the page

Those are client-side caches of another layer (see Client-Side Rendering). With Server Components the data layer is on the server (Data Cache, 'use cache'), and the client libraries are for data that must be fetched in the browser.

Data is fetched in getStaticProps and getServerSideProps and frozen into JSON props

Data is fetched in async Server Components, and the cache is a property of the function ('use cache', unstable_cache) or the call (fetch), not of the page type.

res.revalidate() from an API route called with a secret in the URL

Valid for the Pages Router. In the App Router use revalidateTag(tag, 'max') or updateTag from a Route Handler or Server Action, with a header secret or signature, never a secret in a URL.

Pages are static or dynamic as a whole

A route can mix static, cached and dynamic parts with Cache Components, each with its own lifetime.

Performance advice about cache policy of static assets (Lighthouse)

/_next/static/* is already public, max-age=31536000, immutable; third-party assets are outside Next.js' control.
