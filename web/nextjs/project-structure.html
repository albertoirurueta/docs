Project Structure

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Next.js 16.3 (16.3.8 was the latest release on 2026-10-03, when the facts and examples below were checked; the official documentation, @doc-version 16.3.8, was read on the same day), React 19.3.0, Node.js 20.9 or later and TypeScript 5.1 or later. It describes the App Router (the app folder) in depth and the Pages Router (the pages folder) as a comparison. The file and folder conventions are the same under Cache Components and under the previous caching model; the examples on this page were built and run with the previous model (cacheComponents off), because the scratch pages read params and cookies() directly in layouts, which Cache Components rejects at build time unless the access sits under Suspense (the caching pages cover that). Every example was built with next build and, where it matters, served with next start in a scratch project that is a reduced version of the Bookshelf used throughout this section, so the route tables and curl outputs shown here are real output, not hand-written.

The page answers three questions in order: which folders and files does Next.js give a meaning to, how do you arrange everything else without changing your URLs, and what does the finished Bookshelf project look like. Pages that go deeper on single conventions (the routing pages, the configuration and TypeScript page, the data and caching pages) are named in plain prose where they matter. The Next.js section of this site has not been linked in the navigation yet, so those pages are not cross-referenced here. For the React concepts underneath (components, Suspense, error boundaries), see the React routing page; for the same Bookshelf on the server side of a different stack, see NestJS vs Next.js.

Conventions, Not Configuration

Next.js discovers your application from the file system. A folder inside app is a route segment; a small set of reserved file names inside it gives the segment a UI, a boundary or an endpoint; everything else is yours. The official page is explicit that Next.js is unopinionated about how you organise and colocate the rest of your project, and gives you tools (colocation, private folders, route groups, src) rather than a mandatory layout.

Three rules explain almost everything that follows:

  • Folders define URL segments. Nesting folders nests segments, and a layout at any level wraps all of its child segments.

  • Only special file names do anything. A route becomes publicly reachable only when it contains a page or a route file (or a metadata route such as sitemap.ts). Any other file next to them is just a module.

  • Names in brackets or parentheses are syntax, not folder names: [id] is a dynamic segment, (group) is invisible in the URL, _folder is invisible to routing, @slot is a named slot and (.)folder intercepts a route.

Source: Project structure and organization

Top-Level Folders

Table 1. Top-level folders of a Next.js project
Folder Purpose Notes

app

The App Router: file-system routes, layouts, Server Components and Route Handlers.

The recommended router for new projects. A root layout (with <html> and <body>) is required.

pages

The Pages Router: one file per route, getStaticProps/getServerSideProps, pages/api.

Still supported; both routers can live in the same project, which is how incremental migration works.

public

Static assets served from the base URL: public/avatars/me.png is served at /avatars/me.png.

Next.js cannot safely cache these files, so it sends Cache-Control: public, max-age=0. For robots.txt, favicons and similar files use the metadata file conventions inside app instead.

src

Optional folder that holds app or pages (and usually components, lib, proxy.ts) so that application code is separated from configuration files at the root.

public, package.json, next.config., tsconfig.json and .env files stay in the project root. See the src folder below.

A freshly generated project and the final Bookshelf both contain a top-level public folder. This is the behaviour of a file in public, as served by the scratch project:

A file in public/ is served from the root, with the default caching header

The Proxy file follows the same placement rule. The Bookshelf one redirects every request that has no locale prefix; its matcher leaves API routes, _next assets and files with an extension (such as /file.svg or /favicon.ico) alone, which matters because without a matcher the Proxy runs on every request, including static files.

proxy.ts - the exported function is named proxy
import { NextResponse, type NextRequest } from "next/server";
import { locales, defaultLocale } from "@/lib/i18n";

export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl;
  if (locales.some((l) => pathname === `/${l}` || pathname.startsWith(`/${l}/`))) {
    return NextResponse.next();
  }
  return NextResponse.redirect(new URL(`/${defaultLocale}${pathname}`, request.url));
}

export const config = {
  matcher: ["/((?!api|_next|.*\\..*).*)"],
};

Source: proxy.js

The File-Convention Table

The next four tables list every file convention of the App Router, derived from the project-structure page and the File-system conventions reference of the 16.3.8 documentation. Where a file has a JavaScript and a TypeScript form, the table gives the accepted extensions.

Routing Files

Table 3. Routing files of the App Router (every one lives inside a route segment folder)
File Extensions What it does

layout

.js .jsx .tsx

Shared UI that wraps the segment and its children. Preserves state and does not re-render on navigation between child routes. The root layout (app/layout) must define <html> and <body>.

page

.js .jsx .tsx

The UI unique to a route and what makes the segment publicly accessible. Always the leaf of the route subtree; a Server Component by default. Receives params and searchParams as promises.

loading

.js .jsx .tsx

An instant loading state: Next.js wraps the segment’s page and children in a React Suspense boundary and uses this file as the fallback while content streams in.

not-found

.js .jsx .tsx

UI rendered when notFound() is thrown inside the segment; the root app/not-found also handles unmatched URLs.

global-not-found

.js .jsx .tsx

Experimental (since 15.4, behind experimental.globalNotFound). One 404 page for the whole app that bypasses rendering of any layout, so it must define its own <html> and <body>. Useful with multiple root layouts.

error

.js .jsx .tsx

A React error boundary (a Client Component) for the segment’s page and children, with a retry function. Does not catch errors of the layout or template of the same segment.

global-error

.js .jsx .tsx

Replaces the root layout when an error escapes it; must define its own <html> and <body>. Lives in the root app folder.

route

.js .ts

A Route Handler: an endpoint exporting GET, POST and the other HTTP method functions. A segment cannot have both route and page.

template

.js .jsx .tsx

Like a layout, but a new instance is mounted for each child on navigation, so state is reset and effects re-run.

default

.js .jsx .tsx

Fallback for a parallel-route slot (and the implicit children slot) when Next.js cannot recover the slot’s active state after a full page load.

forbidden

.js .jsx .tsx

UI for the forbidden() function (HTTP 403). Experimental, needs experimental.authInterrupts; introduced in 15.1.

unauthorized

.js .jsx .tsx

UI for the unauthorized() function (HTTP 401). Experimental, needs experimental.authInterrupts; introduced in Next.js 15.1.

Sources: layout.js, page.js, loading.js, not-found.js, error.js, route.js, template.js, default.js, forbidden.js, unauthorized.js

Several of these are one-file examples. The error boundary and the 401/403 files are the ones people most often get wrong, so here they are as built in the scratch project. error.tsx must be a Client Component and receives retry (stable in 16.3.0; unstable_retry in 16.2). The forbidden.tsx and unauthorized.tsx files sit in the root of app and only render once experimental.authInterrupts is on and a page calls forbidden() or unauthorized().

error.tsx, forbidden.tsx and the page that triggers it
// app/[locale]/(shop)/books/[id]/error.tsx
"use client";

export default function BookError({ retry }: { error: Error; retry: () => void }) {
  return <button onClick={() => retry()}>Try again</button>;
}

// app/forbidden.tsx
export default function Forbidden() {
  return <h1>403 - you may not see this</h1>;
}

// app/[locale]/(account)/admin/page.tsx
import { forbidden } from "next/navigation";
import { getUser } from "@/lib/dal";

export default async function AdminPage() {
  const user = await getUser();
  if (user?.id !== "admin") forbidden();
  return <h1>Admin</h1>;
}
next.config.ts - the flag that enables forbidden() and unauthorized()
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  experimental: { authInterrupts: true },
};

export default nextConfig;

Component Hierarchy

The components defined in special files are rendered in a fixed hierarchy, from the outside in: layout.js, then template.js, then error.js (a React error boundary), then loading.js (a React Suspense boundary), then not-found.js (a React error boundary for the "not found" UI) and finally page.js or a nested layout.js. In nested routes the components of a segment are nested inside the components of its parent segment.

flowchart TB subgraph L["layout.js - persists across navigations"] subgraph T["template.js - new instance for each navigation"] subgraph E["error.js - React error boundary"] subgraph S["loading.js - Suspense boundary"] subgraph N["not-found.js - boundary for notFound()"] P["page.js, or the nested layout.js of the child segment"] end end end end end

Two consequences follow from the nesting, and both are easy to get wrong:

  • error.js sits inside the layout and template of its own segment, so it cannot catch their errors. An error in the root layout needs global-error.js, which replaces the root layout while active.

  • loading.js wraps the page and children but not the layout, so it never shows while the layout itself is slow; a slow layout therefore blocks the segment’s loading UI.

To see the order in the rendered output, the scratch project has a segment app/[locale]/(shop)/demo that contains all of layout, template, error, loading and page, with a data-file attribute on each wrapper. The page calls connection() so it is rendered at request time and the fallback is streamed first:

The demo segment: one file per convention (error.tsx is a Client Component boundary and leaves no DOM)
// layout.tsx
export default function Layout({ children }: LayoutProps<"/[locale]/demo">) {
  return <div data-file="layout">{children}</div>;
}

// template.tsx
export default function Template({ children }: { children: React.ReactNode }) {
  return <div data-file="template">{children}</div>;
}

// loading.tsx
export default function Loading() {
  return <p data-file="loading">loading...</p>;
}

// page.tsx
import { connection } from "next/server";

export default async function Page() {
  await connection(); // request-time rendering, so loading.tsx is streamed first
  await new Promise((r) => setTimeout(r, 200));
  return <p data-file="page">page</p>;
}

<div hidden id="S:0">...</div>
<div hidden id="S:1"><p data-file="page">page</p></div>

The streamed <div hidden> chunks hold the page content that React swaps into the fallback’s place, which is the loading UI doing its job. The full hierarchy for a nested route repeats the box, with the child segment’s layout.js taking the place of page.js at each level until the leaf page.js.

Colocation

Because only page and route files make a segment public, and only their returned content is sent to the client, project files can be safely colocated inside route segments without becoming routable. The decision tree is short:

flowchart TD F["File inside app/"] --> Q1{"Inside a _private folder?"} Q1 -->|yes| NR1["Never routable, nor its subfolders"] Q1 -->|no| Q2{"File name is page, route or a metadata route?"} Q2 -->|no| NR2["Plain module - not routable, can be imported"] Q2 -->|yes| Q3{"Another page or route at the same URL?"} Q3 -->|yes| ERR["Build error: conflicting paths"] Q3 -->|no| R["Public route"]

The Bookshelf book page keeps a helper and a test next to page.tsx:

A segment with colocated files
app/[locale]/(shop)/books/[id]/
├── page.tsx           # routable: exports the page
├── format-title.ts    # colocated helper, imported by page.tsx
├── page.test.tsx      # colocated test
├── error.tsx
├── loading.tsx
└── opengraph-image.tsx
Colocated helper (format-title.ts) used by page.tsx
// A colocated helper: sits next to page.tsx but is not routable
export const formatTitle = (t: string) => t.toUpperCase();
Only the page is reachable; colocated files are 404
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3203/en/books/1
200
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3203/en/books/1/format-title
404
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3203/en/books/1/page.test
404
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3203/en/books/1/page
404

The two rules that look like the opposite of colocation are conflicts. A segment with both a page and a route, and two route groups that resolve to the same URL, fail the build instead of picking a winner (messages from the scratch builds):

Build errors for conflicting routes
Error: Conflicting route and page at /: route at /(shop)/route and page at /(shop)/page

Error: You cannot have two parallel pages that resolve to the same path. Please check /(account)/books and /(shop).

Colocation is optional. You can also keep project files outside app, in top-level folders such as components and lib (the strategy the final Bookshelf layout uses), or put top-level folders inside app, or split files by feature under the route segments that use them; see Organisation strategies.

Private Folders

A folder prefixed with an underscore, folderName, is a private implementation detail: it and every subfolder are opted out of routing. Colocation already makes private folders unnecessary for safety, but they help to separate UI logic from routing logic, to organise internal files consistently, to sort and group files in editors and to avoid clashes with future Next.js file conventions. The _Bookshelf uses _components next to the pages that use the components. To prove the opt-out, the scratch project also has a page.tsx inside a private _internal folder:

A page.tsx inside a private folder, and the %5F escape for a real underscore segment
app/[locale]/(shop)/
├── _components/book-card.tsx   # imported by page.tsx
├── _internal/page.tsx          # a page, but inside a private folder
└── %5Fstatus/page.tsx          # URL segment that starts with an underscore
A private folder is invisible to routing; %5F produces an underscore URL

404
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3203/en/internal
404
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3203/en/_status

Route Groups

A route group is a folder wrapped in parentheses, (folderName). It exists for organisation and is not part of the URL. Typical uses are to organise routes by site section, intent or team, to share a layout between a subset of routes of the same segment level, and to create multiple root layouts. In the Bookshelf, (shop) and (account) share the [locale] segment and the URL space, yet have different layouts: the account layout requires a session and the shop layout does not.

app/[locale]/(account)/layout.tsx - a layout that applies to the account routes only
import { requireUser } from "@/lib/dal";
import { SiteHeader } from "@/components/ui/site-header";

export default async function AccountLayout({
  children,
  params,
}: LayoutProps<"/[locale]">) {
  const { locale } = await params;
  await requireUser(locale);
  return (
    <>
      <SiteHeader locale={locale} />
      {children}
    </>
  );
}

Everything the group does is invisible in the URL and in the route table:

Folders and the URLs they produce
app/[locale]/(shop)/page.tsx                  /en
app/[locale]/(shop)/books/[id]/page.tsx       /en/books/1
app/[locale]/(account)/my-reviews/page.tsx    /en/my-reviews
app/[locale]/(account)/admin/page.tsx         /en/admin

The documentation shows three further uses of groups. To opt only some routes into a layout, move them into a group with its own layout.js. To give one page a loading skeleton without affecting its siblings, put loading.tsx and the page inside a group such as (overview). And to partition an app into sections with completely different UI, create multiple root layouts.

Multiple Root Layouts

To create multiple root layouts, remove the top-level layout.js and add a layout.js with <html> and <body> inside each route group. This was built in a second scratch project (a (shop) and an (account) group, no app/layout.tsx):

Two root layouts, one per route group
// app/(shop)/layout.tsx
export default function ShopRootLayout({ children }: LayoutProps<"/">) {
  return (
    <html lang="en">
      <body className="shop">{children}</body>
    </html>
  );
}

// app/(account)/layout.tsx
export default function AccountRootLayout({ children }: LayoutProps<"/">) {
  return (
    <html lang="en">
      <body className="account">{children}</body>
    </html>
  );
}
Each route gets the body of its own root layout
$ for u in / /books /my-reviews; do echo $u; curl -s localhost:3203$u | grep -o '<body[^>]*>'; done
/
<body class="shop">
/books
<body class="shop">
/my-reviews
<body class="account">

The caveats from the Route Groups reference are real constraints, not style advice. Navigating between routes that use different root layouts triggers a full page load instead of a client-side navigation. Routes in different groups must not resolve to the same URL (the second build error above). And if you use multiple root layouts with no top-level layout.js, the home route / has to be defined inside one of the groups.

A root layout can also sit under a dynamic segment. The Bookshelf does this: its root layout is app/[locale]/layout.tsx, there is no app/layout.tsx, and the dynamic segments before the root layout are root parameters, which any Server Component can read with next/root-params.

app/[locale]/layout.tsx - the root layout of the Bookshelf, under a dynamic segment
import { notFound } from "next/navigation";
import { locales, isLocale } from "@/lib/i18n";

export function generateStaticParams() {
  return locales.map((locale) => ({ locale }));
}

export default async function RootLayout({
  children,
  modal,
  params,
}: LayoutProps<"/[locale]">) {
  const { locale } = await params;
  if (!isLocale(locale)) notFound();
  return (
    <html lang={locale}>
      <body>
        {children}
        {modal}
      </body>
    </html>
  );
}

The src Folder

Application code can live in an optional src folder, which separates it from the configuration files at the root. Move app (or pages) to src/app (or src/pages). The reference lists what has to stay put and what must follow:

  • public, package.json, next.config., tsconfig.json and .env files stay in the project root.

  • src/app or src/pages is ignored if app or pages exists in the root.

  • The Proxy (proxy.ts) goes inside src; so do instrumentation.ts and instrumentation-client.ts.

  • You will probably also move components and lib into src.

  • If a @/* path alias exists, update its target in tsconfig.json so that it includes src/.

  • If a tailwind.config.js file is used, add the /src prefix to its content paths.

The scratch Bookshelf was converted in a copy, moving app, components, lib, proxy.ts, instrumentation.ts and instrumentation-client.ts under src/ and pointing the alias at ./src/*. The build produced the identical route table, and the server printed the same register() line:

tsconfig.json when everything lives in src
{
  "compilerOptions": {
    "paths": {
      "@/*": ["./src/*"]
    }
  }
}

Module Path Aliases

Next.js has built-in support for the paths and baseUrl options of tsconfig.json and jsconfig.json, so imports read @/components/button instead of ../../../components/button. create-next-app offers an import alias (default @/), and with --yes it is set up for you. The configuration that the scratch project uses, and that the generator writes, maps @/ to the project root with paths alone:

tsconfig.json - the default alias
{
  "compilerOptions": {
    "plugins": [{ "name": "next" }],
    "paths": {
      "@/*": ["./*"]
    }
  }
}
Using the alias from any depth
import { SiteHeader } from "@/components/ui/site-header";
import { getUser } from "@/lib/dal";

The reference also documents baseUrl (absolute imports relative to a folder) and several aliases whose targets are relative to baseUrl. This was built in the src copy: with baseUrl set to src/, a second alias and a bare absolute import both resolved, and the build passed.

tsconfig.json - baseUrl plus several aliases
{
  "compilerOptions": {
    "baseUrl": "src/",
    "paths": {
      "@/*": ["./*"],
      "@ui/*": ["components/ui/*"]
    }
  }
}
Imports that resolve with that configuration
import { SiteHeader } from "@ui/site-header"; // alias
import { requireUser } from "lib/dal";        // absolute import from baseUrl (src/)

Aliases are a TypeScript and bundler feature: they exist at compile time only, so they work in app, pages, proxy.ts and route files alike. The TypeScript plugin, typedRoutes and the PageProps, LayoutProps and RouteContext helpers are covered on the configuration and TypeScript page of this section.

Organisation Strategies

The official examples are a high-level overview of common strategies; the stated takeaway is to choose one that works for you and your team and to be consistent. components and lib are placeholders with no framework meaning; your project might use ui, utils, hooks or styles.

Table 7. Common strategies for project files
Strategy Layout Good when

Store project files outside app

Shared code in folders at the project root; app contains only routing files.

You want routing and implementation fully separate (the final Bookshelf layout).

Store project files in top-level folders inside app

Shared code in folders in the root of app.

You want everything under one folder.

Split project files by feature or route

Globally shared code in the root app folder, route-specific code in the segments that use it.

Features are owned by different people or move independently (colocation and private folders).

Whichever you pick, the rest of the structure is the same: private folders keep helpers away from the router, route groups divide the URL space into sections without changing it, and aliases make deep imports readable.

The data access layer and the Server Actions are the two files with an architectural role; both are plain modules that only Server Components and actions import. lib/dal.ts reads the session cookie through cookies() and is the single place that decides who the user is (the scratch version only checks that a cookie exists; the authentication page replaces it with a real session check):

lib/dal.ts - a server-only module
import "server-only";
import { cache } from "react";
import { cookies } from "next/headers";
import { redirect } from "next/navigation";

// Data Access Layer: the only place that reads the session
export const getUser = cache(async () => {
  const jar = await cookies();
  const id = jar.get("session")?.value;
  return id ? { id } : null;
});

export async function requireUser(locale: string) {
  const user = await getUser();
  if (!user) redirect(`/${locale}/sign-in`);
  return user;
}
lib/actions/reviews.ts - a file of Server Actions
"use server";

import { revalidatePath } from "next/cache";
import { getUser } from "@/lib/dal";

export async function addReview(formData: FormData) {
  const user = await getUser();
  if (!user) throw new Error("Not signed in");
  const bookId = String(formData.get("bookId"));
  const text = String(formData.get("text")).slice(0, 500);
  console.log("review", user.id, bookId, text.length);
  revalidatePath(`/[locale]/books/${bookId}`, "page");
}
