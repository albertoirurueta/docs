Dynamic Routes & Route Groups

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when the facts and examples below were checked; the official documentation reports @doc-version 16.3.8), React 19.3.0, Node.js 20.9.0 or later and TypeScript 5.1 or later. It covers the App Router in depth and compares it with the Pages Router in one section. Wherever caching changes the behaviour of a dynamic route, the page names the model it is describing: the previous model (the default, in which generateStaticParams and dynamicParams decide what is prerendered) or Cache Components (cacheComponents: true, still opt-in, in which params are runtime data unless you supply samples). Every example was built and run with Next.js 16.3.8, Node.js 24.16 and npm 11.13 on macOS in a scratch copy of the Bookshelf — the catalogue of books, authors and reviews that this section grows — and each one is followed by the official page it derives from.

A static route like /about is one folder and one URL. A bookshop needs /en/books/3, /en/shelf/fiction/sci-fi and a documentation tree of unknown depth, and it cannot create a folder for each of them. A dynamic segment is a folder whose name is a placeholder: Next.js matches it against any value in that position and hands the value to your code as a param. This page covers the three placeholder shapes, the three ways to read the value, how to type it, how to prerender the values you know about, and the two folder conventions — route groups and private folders — that let you organise the tree without adding a URL segment. It assumes the folder basics of Project Structure and the rendering vocabulary of Introduction and Architecture.

The Three Dynamic Segment Shapes

A dynamic segment is created by wrapping a folder name in square brackets. The name inside the brackets is the key of the param. Next.js passes the captured values as the params prop to layout, page, route and the generateMetadata function of the segment and everything below it. The official documentation calls them dynamic segments, and also path params, route params or URL params.

Table 2. The three shapes and what each one matches
Folder Matches Example URL and params params type

app/blog/[slug]/page.tsx

exactly one segment

/blog/a gives { slug: 'a' }

{ slug: string }

app/shop/[...slug]/page.tsx

one or more segments (a catch-all)

/shop/a/b/c gives { slug: ['a', 'b', 'c'] }; /shop does not match

{ slug: string[] }

app/shop/[[...slug]]/page.tsx

zero or more segments (an optional catch-all)

/shop gives { slug: undefined }; /shop/a/b gives { slug: ['a', 'b'] }

{ slug?: string[] }

app/[categoryId]/[itemId]/page.tsx

two dynamic segments

/books/42 gives { categoryId: 'books', itemId: '42' }

{ categoryId: string, itemId: string }

The difference between the last two catch-all shapes is a single question: should the route without the parameter exist? A catch-all [...slug] needs at least one segment. An optional catch-all [[...slug]] also answers the bare path, which makes it the right shape for a documentation tree where /docs is the index and /docs/a/b is a deep page, with a single page.tsx for both.

One Segment: [id]

The Bookshelf book page is the canonical [slug]-style route. The segment is called id because the data layer looks books up by id, but the shape is identical to the official [slug] example:

app/[locale]/(shop)/books/[id]/page.tsx
import { notFound } from "next/navigation";
import { getBook } from "@/lib/books";

export default async function Page({ params }: PageProps<"/[locale]/books/[id]">) {
  const { id } = await params;
  const book = await getBook(id);
  if (!book) notFound();
  return (
    <article>
      <h2>{book.title}</h2>
      <p>by {book.author}</p>
    </article>
  );
}

PageProps<'/[locale]/books/[id]'> is a globally available type helper (the next sections explain it). The segment [locale] above is also a param, so the page receives { locale, id }, not just { id }: a route’s params holds every dynamic segment from the root to the page.

Several Segments: Static Beats Dynamic

A static folder next to a dynamic one wins for its own URL. The Bookshelf has books/new/page.tsx beside books/[id]/page.tsx:

Static segments win over dynamic ones (production server, port 3303)
$ curl -s localhost:3303/en/books/new | grep -o '<h2>[^<]*'
<h2>Add a book (static segment wins over [id])
$ curl -s localhost:3303/en/books/2 | grep -o '<title>[^<]*'
<title>Neuromancer - Bookshelf

So /en/books/new is the form page and is never captured as id = 'new'. In the same experiment a sibling catch-all books/[...all] lost to [id] for /en/books/2 and won for /en/books/2/extra: a static folder beats a dynamic one, which beats a catch-all, so you can add specific pages next to a general route without restructuring it.

Catch-all: […​path]

The Bookshelf shelf is a hierarchy of unknown depth (fiction/sci-fi, non-fiction/science, and so on). A catch-all route captures it as an array:

app/[locale]/(shop)/shelf catch-all path page
export default async function Page({ params }: PageProps<"/[locale]/shelf/[...path]">) {
  const { path } = await params; // string[]
  return (
    <p data-segments={path.length}>
      Shelf: {path.map((s) => decodeURIComponent(s)).join(" > ")}
    </p>
  );
}
Results (production server)
$ curl -s localhost:3303/en/shelf/fiction/sci-fi | grep -o 'data-segments="[0-9]*">Shelf:.*</p>'
data-segments="2">Shelf: <!-- -->fiction &gt; sci-fi</p>
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:3303/en/shelf
404

/en/shelf is a 404 because a plain catch-all needs at least one segment. The decodeURIComponent call is deliberate: in Next.js 16.3.8 the values are handed over percent-encoded (see Pitfalls and Errors).

Optional Catch-all: [[…​slug]]

For the Bookshelf documentation, one file serves /en/docs and every deeper page:

app/[locale]/(marketing)/docs optional catch-all slug page
export default async function Page({ params }: PageProps<"/[locale]/docs/[[...slug]]">) {
  const { slug } = await params; // string[] | undefined
  return <p data-slug={slug ? slug.join("/") : "index"}>Docs: {slug?.join("/") ?? "home"}</p>;
}
Results (production server)
$ curl -s localhost:3303/en/docs | grep -o '<p data-slug[^>]*>'
<p data-slug="index">
$ curl -s localhost:3303/en/docs/a/b | grep -o '<p data-slug[^>]*>'
<p data-slug="a/b">

An optional catch-all claims the bare path, so a sibling docs/page.tsx would resolve to the same route. Next.js refuses it at build time:

("/[locale]/docs" and "/[*]/docs/[[...slug]]").

Delete the extra page.tsx and branch on slug === undefined instead.

Reading Params: await, use() and useParams

In the App Router, params is a Promise. The reason is performance: the value is runtime data in routes that are not fully known at build time, and a Promise lets Next.js start rendering the static parts of the tree before the value resolves. There are five places to read a param, and the right one depends on the kind of component.

flowchart TD q{"Where do you read the param?"} q -- "async Server Component:
page, layout, route, generateMetadata" --> a["const { id } = await params"] q -- "synchronous Server Component" --> b["pass the params Promise to a child
and await it there, inside Suspense"] q -- "Client Component page or layout" --> c["const { id } = use(params)"] q -- "Client Component deeper in the tree" --> d["const params = useParams()"] q -- "root segment, any Server Component
or shared server code" --> e["await locale() from next/root-params"]
Table 3. Which tool reads params where
Where How Notes

Async Server Component (page, layout, route, generateMetadata, image files)

const { id } = await params

The default. params carries every dynamic segment from the root down to this file.

Synchronous Server Component

Pass params (the Promise) as a prop and await it in a child; or call use(params)

React’s use API reads a Promise during render. Under Cache Components, keep the read inside <Suspense>.

Client Component page or layout

const { id } = use(params)

The Promise arrives as a prop and use unwraps it. A Client Component cannot be async.

Any Client Component in the tree

Returns an object of the active params (empty object when the route has none). No prop drilling.

Root parameters anywhere on the server

await locale() from next/root-params

Server Components only; see Root Parameters and next/root-params.

In Server Components: await

The book page above is the case: an async component, await params, destructure. The same holds for layouts and for generateMetadata, which also receives params as a Promise:

generateMetadata receives the same params Promise as the page
import type { Metadata } from "next";
import { getBook } from "@/lib/books";

export async function generateMetadata({
  params,
}: PageProps<"/[locale]/books/[id]">): Promise<Metadata> {
  const { id } = await params;
  const book = await getBook(id);
  return { title: book ? `${book.title} - Bookshelf` : "Book not found" };
}

Route Handlers get their params through a second argument typed with RouteContext:

app/api/books/[id]/route.ts

export async function GET(_request: Request, { params }: RouteContext<"/api/books/[id]">) {
  const { id } = await params;
  const book = await getBook(id);
  if (!book) return Response.json({ error: "Book not found" }, { status: 404 });
  return Response.json(book);
}

In Client Component Pages: use()

A Client Component page receives the same Promise. React’s use API unwraps it; because a Client Component cannot be async, await is not available. The Bookshelf reviews page is a Client Component, for instance because it will hold interactive state:

app/[locale]/(shop)/books/[id]/reviews/page.tsx (previous model)
"use client";

import { use } from "react";

export default function ReviewsPage({
  params,
}: {
  params: Promise<{ locale: string; id: string }>;
}) {
  const { id } = use(params);
  return <h2>Reviews of book {id}</h2>;
}
Result (production server)
$ curl -s localhost:3303/es/books/1/reviews | grep -o '<h2>[^<]*<!-- -->[^<]*'
<h2>Reviews of book <!-- -->1

In the Client Tree: useParams

use(params) only works where the Promise was passed down as a prop. A breadcrumb inside the layout needs the same values without receiving a prop, which is what the useParams hook is for. It is a Client Component hook that returns the params of the current URL:

app/[locale]/(shop)/books/[id]/crumbs.tsx
"use client";

import { useParams } from "next/navigation";

export function Crumbs() {
  const params = useParams<{ locale: string; id: string }>();
  return (
    <nav>
      {params.locale} / books / {params.id}
    </nav>
  );
}
Result (production server): the hook is also rendered on the server for the first HTML
$ curl -s localhost:3303/es/books/1/reviews | grep -o '<nav>.*</nav>'
<nav>es<!-- --> / books / <!-- -->1</nav>

useParams returns an object whose keys are the active dynamic segments; each value is a string, or an array of string for catch-all segments; a route with no dynamic segments gives {}. In the Pages Router the same hook returns null on the first render until the router is ready (it was introduced in 13.3.0).

Source: useParams

With Cache Components: runtime params need Suspense

Under the previous model, awaiting params anywhere is fine. With cacheComponents: true the rule changes, and the rule depends on whether generateStaticParams covers the route. Without it, the param values are unknown while prerendering, so reading them is runtime data and must sit inside a <Suspense> boundary or the build fails. The documented pattern is to pass the Promise down and await it in a child:

app/[locale]/(marketing)/docs optional catch-all slug page (Cache Components)
import { Suspense } from "react";

export default function Page({ params }: PageProps<"/[locale]/docs/[[...slug]]">) {
  return (
    <Suspense fallback={<p>Loading...</p>}>
      <Docs params={params} />
    </Suspense>
  );
}

async function Docs({ params }: { params: PageProps<"/[locale]/docs/[[...slug]]">["params"] }) {
  const { slug } = await params; // string[] | undefined
  return <p data-slug={slug ? slug.join("/") : "index"}>Docs: {slug?.join("/") ?? "home"}</p>;
}

Without the Suspense boundary the same build stops with this error (verified on 16.3.8):

next build with cacheComponents: true and the Suspense boundary removed
Error: Route "/[locale]/docs/[[...slug]]": Next.js encountered uncached or runtime data during prerendering.
`fetch(...)`, `cookies()`, `headers()`, `params`, `searchParams`, or `connection()` accessed outside of `<Suspense>`
prevents the route from being prerendered ...
Learn more: https://nextjs.org/docs/messages/blocking-prerender-dynamic

useParams follows the same rule: when every param of the route is known at build time (a static route, or one covered by generateStaticParams) it needs no boundary; for params not covered it suspends, and the call site needs <Suspense> or the build fails with blocking-prerender-client-hook. In a layout, do not await params at the top level: that blocks the layout from being prerendered. Pass the Promise to the component that needs it instead.

Source: Dynamic Segments: With Cache Components, blocking-prerender-dynamic, blocking-prerender-client-hook

Typing Params

Route params values are typed string, string[] or undefined because the actual value is whatever a visitor types in the address bar. The table lists the TypeScript shape for each folder:

Table 4. params types by route shape
Route params type

app/blog/[slug]/page.tsx

{ slug: string }

app/shop/[...slug]/page.tsx

{ slug: string[] }

app/shop/[[...slug]]/page.tsx

{ slug?: string[] }

app/[categoryId]/[itemId]/page.tsx

{ categoryId: string, itemId: string }

You can write those by hand (params: Promise<{ slug: string }>), but the idiomatic way is to let Next.js derive them from the folder tree. PageProps, LayoutProps and RouteContext are globally available helpers, generated by next dev, next build or next typegen (the command was introduced in 15.5). They take the route literal, give autocomplete and strict keys, and they know the Promise shape, so a typo or a leftover synchronous access fails the type check:

  const { slug } = await props.params;
  const sync = props.params.id;
  return <p>{slug}{sync}</p>;
}

A URL path is text, and nothing in a folder name such as [id] says "number", so Next.js never converts: id is '1', never 1. The contract also runs the other way. Returning numbers from generateStaticParams passes the TypeScript step and then stops the build:

Narrowing Params: One Parsing Module for Every Route

A param is typed string, but most have a much smaller set of valid values. The documented approach is runtime validation with an assertion function: invalid values go to notFound(), and the rest of the code works with the narrower type. This is also the security rule for the whole page: a param is user input. Validation scattered over pages drifts, so the Bookshelf keeps the rules in one server module that pages, layouts, generateMetadata and Route Handlers call before touching data. The root layout calls assertLocale, so /fr/…​ is a 404 before any page runs; the book page calls parseId (a zod schema such as z.string().regex(…​) works just as well):

lib/params.ts
import { notFound } from "next/navigation";
import { type Locale, isLocale } from "@/lib/i18n";

// A route param is always a string: narrow it once, at the edge of the route.
export function assertLocale(value: string): asserts value is Locale {
  if (!isLocale(value)) notFound();
}

// "3" -> 3. Anything else ("abc", "1e3", "-1", "", "99999999999") -> notFound().
export function parseId(value: string): number {
  if (!/^[0-9]{1,9}$/.test(value)) notFound();
  return Number(value);
}

// Page params arrive percent-encoded: decode each segment once, then validate.
export function decodeSegments(segments: string[]): string[] {
  try {
    return segments.map((s) => decodeURIComponent(s));
  } catch {
    notFound(); // a malformed escape
  }
}

Source: Dynamic Segments: TypeScript, PageProps helper, notFound

Why a pattern and not Number(id)? Number('1e3') is 1000, Number('') is 0 and parseInt('1abc', 10) is 1: each turns a junk URL into a real book page and a separate cache entry. The nine-digit cap stays below Number.MAX_SAFE_INTEGER. Spellings the pattern does accept, such as 01, are sent to the canonical URL with permanentRedirect (308), so search engines and the ISR cache see one URL per book. Narrowing works because notFound() and permanentRedirect() throw and are typed never.

Check per-page params (id, slug) in the page, not a layout: a layout does not re-run on a soft navigation between its children. And give generateMetadata the same guard, or it can build a <title> from an invalid value.

Never interpolate a raw param into a query string, a file path or a command: a slug captured into an fs path allows .. tricks (see Special Characters in Segments: Encoding and Decoding), and a slug concatenated into a GROQ or SQL query allows injection. The consulted e-commerce book, for instance, interpolates the slug into a CMS query; the correct form passes it as a query parameter.

The same generated types also check the other direction: with typedRoutes: true, a link such as /${locale}/book/${id} (a typo for books) fails the TypeScript step of next build with TS2322, while /${locale}/books/${id} passes. Prefer template literals for links to dynamic routes; a concatenated string is not checked and needs an as Route cast. The option is covered in Configuration, TypeScript and Environment Variables.

Special Characters in Segments: Encoding and Decoding

The browser (or curl) percent-encodes what a URL cannot carry: a space becomes %20, é the UTF-8 bytes %C3%A9, and a slash inside a value must be sent as %2F. The router splits the path on real / characters before anything is decoded, so %2F never creates a segment. What your code then receives depends on where it runs. The shelf page prints the raw param and the result of decodeSegments:

  const { slug } = await params; // string[]
  return (
    <pre>
      raw={JSON.stringify(slug)} decoded={JSON.stringify(decodeSegments(slug))}
    </pre>
  );
}

Previous Model: Subsets, dynamicParams and Request-time Rendering

What happens for a value that generateStaticParams did not return is controlled by the dynamicParams route segment config (it replaces the fallback: true | false | 'blocking' option of the Pages Router’s getStaticPaths):

  • true (the default): the page is rendered on demand the first time and the result is cached.

  • false: the page answers 404 for every value not returned by generateStaticParams.

The Bookshelf book page prerenders ids 1 and 2. With the default dynamicParams = true, id 3 renders on demand, and the second request is already a cache hit. Setting dynamicParams = false makes id 3 a 404:

// It is not allowed when cacheComponents is on.

Cache Components: Samples, Not Lists

With cacheComponents: true the contract of generateStaticParams changes. It supplies samples: param values used at build time to run the route and validate that it accesses runtime data correctly. The rules, all verified on 16.3.8:

  • generateStaticParams must return at least one param. An empty array is a build error (empty-generate-static-params), because with no sample Next.js cannot check that the route does not read cookies(), headers() or searchParams incorrectly.

  • dynamicParams is not available: exporting it fails the build, whatever its value.

  • Values returned by generateStaticParams are prerendered into complete static HTML. Other values are runtime params: the static shell is sent, then the param-dependent content streams in, and pages rendered this way are saved after a successful first request.

  • Build-time validation covers only the code paths the samples execute. A branch reached by other values (for example slug.startsWith('private-') reading cookies()) is validated on the first request instead, so wrap such branches in <Suspense>.

Per-group Layouts and Opting Out of a Layout

A route inherits every layout on its folder path, and there is no "skip the parent layout" switch. A route group is how you give a layout to some siblings without inventing a URL segment. In the URL map, (shop) holds the shop navigation, (account) the account navigation (in the full Bookshelf it also runs the session check of the Data Access Layer), and (marketing) a plain wrapper. (checkout) has no layout: to remove checkout from the shop chrome you do not configure checkout, you move it next to (shop) instead of inside it. The probe confirms it: /en/checkout returns 200 with no data-group="shop" element.

The same move scopes loading.tsx, error.tsx and not-found.tsx to one route. Groups are only needed at the same level: books/new/page.tsx never sees books/[id]/layout.tsx, because it is not below that folder.

Shared Root Layout or Multiple Root Layouts: the Cost

To measure the "full page load" caveat, a second variant deleted app/[locale]/layout.tsx and gave each group a layout with <html> and <body> (and the locale generateStaticParams). The same browser script ran against both builds; the navigation entry is performance.getEntriesByType('navigation')[0].name, which changes only when the browser loads a new document:

The same navigation in the two variants (production server, Chromium)
One shared root layout ([locale]/layout.tsx)
  /en/books/2 -> /en/my-reviews   marker=alive      navigation entry /en/books/1      (soft)

One root layout per group ((shop) and (account) render <html>)
  /en/books/1 -> /en/books/2      marker=alive      navigation entry /en/books/1      (soft: same root)
  /en/books/2 -> /en/my-reviews   marker=undefined  navigation entry /en/my-reviews   (hard: new document)

Crossing root layouts discarded the JavaScript state, the React tree and the router cache, like a plain <a href>.

So keep one root layout for areas users move between all the time (the Bookshelf’s catalogue, account and checkout), and reserve one root layout per group for areas they rarely cross, such as a public site and an admin console that needs a different <html>, theme or analytics. With several roots, a root parameter missing from some of them is typed string | undefined by next/root-params. The file-level rules are in Layouts, Templates and Special Files.

Private Folders

A folder whose name starts with an underscore, _folderName, is a private folder: the routing system ignores it and every subfolder. The Bookshelf keeps shared UI next to the routes that use it in app/[locale]/_components/:

app/[locale]/_components/book-card.tsx, imported by the catalogue page
import Link from "next/link";
import type { Book } from "@/lib/books";

export function BookCard({ book, locale }: { book: Book; locale: string }) {
  return (
    <li>
      <Link href={`/${locale}/books/${book.id}`}>{book.title}</Link> - {book.author}
    </li>
  );
}

Files in app/ are safely colocated by default (only page and route files create URLs), so a private folder is not required for colocation. It is useful to separate UI code from routing code, to organise internal files consistently, to sort and group files in editors, and to avoid clashes with future Next.js file conventions. To make a URL segment that really starts with an underscore, write the folder with %5F, the URL-encoded underscore: %5FfolderName. A private folder never appears in the build route table.

Source: Private folders; the Project Structure page compares the three organisation strategies.

Root Parameters and next/root-params

The dynamic segments that sit above the root layout are root parameters. The Bookshelf’s [locale] is one, because its root layout is app/[locale]/layout.tsx. Normally a deeply nested component gets a param only if every ancestor passes the params prop down. The next/root-params module (shipped in 16.3) removes that: it exports one async getter per root parameter, named after the folder, and any Server Component or server-side utility can import it:

app/[locale]/layout.tsx: the root layout reads the locale with a getter
import { notFound } from "next/navigation";
import { locale } from "next/root-params";
import { locales, isLocale } from "@/lib/i18n";

export function generateStaticParams() {
  return locales.map((locale) => ({ locale }));
}

export default async function RootLayout({ children }: LayoutProps<"/[locale]">) {
  const current = await locale();
  if (!current || !isLocale(current)) notFound();
  return (
    <html lang={current}>
      <body>{children}</body>
    </html>
  );
}
The book page reads the same value without any prop drilling
import { locale as rootLocale } from "next/root-params";

// ... inside the async Page component:
const loc = await rootLocale(); // "en" or "es"
// <p>by {book.author} (locale: {loc})</p>
Result (production server)
$ curl -s localhost:3303/en/books/3 | grep -o '<p>by.*</p>'
<p>by <!-- -->Stanislaw Lem<!-- --> (locale: <!-- -->en<!-- -->)</p>

The getter returns a Promise: string for [id], string[] for [...path] and string[] | undefined for [[...path]]. When an app has several root layouts, a getter is typed for all of them, so a parameter missing from some roots is string | undefined. The types are generated by next dev, next build or next typegen, like the PageProps helpers (.next/types/root-params.d.ts declares locale(): Promise<string> for the Bookshelf).

Pages Router: Dynamic Routes

The Pages Router uses the same bracket convention on files or folders under pages/, with a different API around it. The value is not a prop: it lives in the query object of useRouter() and in the params of the data functions. The experiments for this section built the same Bookshelf book in a pages/ project:

pages/books/[id].tsx: getStaticPaths, getStaticProps and useRouter().query
import type { GetStaticPaths, GetStaticProps } from "next";
import { useRouter } from "next/router";
import { getBook, type Book } from "@/lib/books";

export const getStaticPaths = (async () => {
  return {
    paths: [{ params: { id: "1" } }, { params: { id: "2" } }],
    fallback: "blocking", // false | true | "blocking"
  };
}) satisfies GetStaticPaths;

export const getStaticProps = (async ({ params }) => {
  const book = await getBook(String(params?.id));
  if (!book) return { notFound: true };
  return { props: { book }, revalidate: 60 };
}) satisfies GetStaticProps<{ book: Book }>;

export default function BookPage({ book }: { book: Book }) {
  const router = useRouter();
  // router.query.id is a string | string[] | undefined
  return (
    <article>
      <h1>{book.title}</h1>
      <p>by {book.author} (id from router.query: {String(router.query.id)})</p>
    </article>
  );
}

The catch-all and optional catch-all work the same way: pages/shelf/[...path].tsx and pages/docs/[[...slug]].tsx, with params.path / params.slug in the data functions.

Two typing and timing differences matter:

  • Types. In getServerSideProps and getStaticProps, params values are string | string[] | undefined (ParsedUrlQuery), even for a plain [id]; the App Router types a plain segment as string. Code that declares a string[] | null prop must normalise, as the experiment’s getServerSideProps does with typeof slug === "string" ? [slug] : (slug ?? null).

  • Timing. On a page that is statically optimised (no data function), router.query is an empty object during prerendering, and is filled after hydration. The experiment’s pages/shelf/[...path].tsx rendered ready=false path=- in the HTML. Read router.query only when router.isReady is true (in an effect), and prefer the data functions on the server.

Params, Query and Encoding in the Pages Router

In the Pages Router the route params and the query string arrive in one object. The URL map app also had a pages/legacy/[id].tsx whose getServerSideProps returned ctx.params and ctx.query as props, and which rendered them next to useRouter().query; a sibling pages/legacy/[...slug].tsx rendered its ctx.params:

    curl -s "localhost:3712$u" | grep -o '<pre>.*</pre>'; done

Four behaviours differ from the App Router:

  • The route param wins over a query parameter of the same name. /legacy/1?id=2 gives query.id === '1', and the ?id=2 is lost. In the App Router params and searchParams are separate props and never collide.

  • Values are decoded: 'café', '100%', and b%2Fc as one segment 'b/c', where an App Router page receives 'caf%C3%A9' (see Special Characters in Segments: Encoding and Decoding). Check before porting a decodeURIComponent call between the routers.

  • State is not reset when only the param changes. /legacy/1 to /legacy/2 renders the same component, so React keeps its state; the documented fixes are a key on Component in pages/_app.tsx or an effect keyed on router.query.id. In the App Router a layout under [id] remounts per id on its own.

  • The next/navigation hooks become nullable when both routers are present. With a pages/ directory, Next.js adds /// <reference types="next/navigation-types/compat/navigation" /> to next-env.d.ts, which types useParams, usePathname, useSearchParams and the segment hooks as possibly null. The URL map’s segments.tsx then failed with error TS18047: 'all' is possibly 'null'; handle the null in shared components.
