Dynamic Routes & Route Groups

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when the facts and examples below were checked; the official documentation reports @doc-version 16.3.8), React 19.3.0, Node.js 20.9.0 or later and TypeScript 5.1 or later. It covers the App Router in depth and compares it with the Pages Router in one section. Wherever caching changes the behaviour of a dynamic route, the page names the model it is describing: the previous model (the default, in which generateStaticParams and dynamicParams decide what is prerendered) or Cache Components (cacheComponents: true, still opt-in, in which params are runtime data unless you supply samples). Every example was built and run with Next.js 16.3.8, Node.js 24.16 and npm 11.13 on macOS in a scratch copy of the Bookshelf — the catalogue of books, authors and reviews that this section grows — and each one is followed by the official page it derives from.

A static route like /about is one folder and one URL. A bookshop needs /en/books/3, /en/shelf/fiction/sci-fi and a documentation tree of unknown depth, and it cannot create a folder for each of them. A dynamic segment is a folder whose name is a placeholder: Next.js matches it against any value in that position and hands the value to your code as a param. This page covers the three placeholder shapes, the three ways to read the value, how to type it, how to prerender the values you know about, and the two folder conventions — route groups and private folders — that let you organise the tree without adding a URL segment. It assumes the folder basics of Project Structure and the rendering vocabulary of Introduction and Architecture.

The Three Dynamic Segment Shapes

A dynamic segment is created by wrapping a folder name in square brackets. The name inside the brackets is the key of the param. Next.js passes the captured values as the params prop to layout, page, route and the generateMetadata function of the segment and everything below it. The official documentation calls them dynamic segments, and also path params, route params or URL params.

Table 2. The three shapes and what each one matches
Folder Matches Example URL and params params type

app/blog/[slug]/page.tsx

exactly one segment

/blog/a gives { slug: 'a' }

{ slug: string }

app/shop/[...slug]/page.tsx

one or more segments (a catch-all)

/shop/a/b/c gives { slug: ['a', 'b', 'c'] }; /shop does not match

{ slug: string[] }

app/shop/[[...slug]]/page.tsx

zero or more segments (an optional catch-all)

/shop gives { slug: undefined }; /shop/a/b gives { slug: ['a', 'b'] }

{ slug?: string[] }

app/[categoryId]/[itemId]/page.tsx

two dynamic segments

/books/42 gives { categoryId: 'books', itemId: '42' }

{ categoryId: string, itemId: string }

The difference between the last two catch-all shapes is a single question: should the route without the parameter exist? A catch-all [...slug] needs at least one segment. An optional catch-all [[...slug]] also answers the bare path, which makes it the right shape for a documentation tree where /docs is the index and /docs/a/b is a deep page, with a single page.tsx for both.

One Segment: [id]

The Bookshelf book page is the canonical [slug]-style route. The segment is called id because the data layer looks books up by id, but the shape is identical to the official [slug] example:

app/[locale]/(shop)/books/[id]/page.tsx
import { notFound } from "next/navigation";
import { getBook } from "@/lib/books";

export default async function Page({ params }: PageProps<"/[locale]/books/[id]">) {
  const { id } = await params;
  const book = await getBook(id);
  if (!book) notFound();
  return (
    <article>
      <h2>{book.title}</h2>
      <p>by {book.author}</p>
    </article>
  );
}

PageProps<'/[locale]/books/[id]'> is a globally available type helper (the next sections explain it). The segment [locale] above is also a param, so the page receives { locale, id }, not just { id }: a route’s params holds every dynamic segment from the root to the page.

With Cache Components: runtime params need Suspense

Under the previous model, awaiting params anywhere is fine. With cacheComponents: true the rule changes, and the rule depends on whether generateStaticParams covers the route. Without it, the param values are unknown while prerendering, so reading them is runtime data and must sit inside a <Suspense> boundary or the build fails. The documented pattern is to pass the Promise down and await it in a child:

app/[locale]/(marketing)/docs optional catch-all slug page (Cache Components)
import { Suspense } from "react";

export default function Page({ params }: PageProps<"/[locale]/docs/[[...slug]]">) {
  return (
    <Suspense fallback={<p>Loading...</p>}>
      <Docs params={params} />
    </Suspense>
  );
}

async function Docs({ params }: { params: PageProps<"/[locale]/docs/[[...slug]]">["params"] }) {
  const { slug } = await params; // string[] | undefined
  return <p data-slug={slug ? slug.join("/") : "index"}>Docs: {slug?.join("/") ?? "home"}</p>;
}

Narrowing Params: One Parsing Module for Every Route

A param is typed string, but most have a much smaller set of valid values. The documented approach is runtime validation with an assertion function: invalid values go to notFound(), and the rest of the code works with the narrower type. This is also the security rule for the whole page: a param is user input. Validation scattered over pages drifts, so the Bookshelf keeps the rules in one server module that pages, layouts, generateMetadata and Route Handlers call before touching data. The root layout calls assertLocale, so /fr/…​ is a 404 before any page runs; the book page calls parseId (a zod schema such as z.string().regex(…​) works just as well):

lib/params.ts
import { notFound } from "next/navigation";
import { type Locale, isLocale } from "@/lib/i18n";

// A route param is always a string: narrow it once, at the edge of the route.
export function assertLocale(value: string): asserts value is Locale {
  if (!isLocale(value)) notFound();
}

// "3" -> 3. Anything else ("abc", "1e3", "-1", "", "99999999999") -> notFound().
export function parseId(value: string): number {
  if (!/^[0-9]{1,9}$/.test(value)) notFound();
  return Number(value);
}

// Page params arrive percent-encoded: decode each segment once, then validate.
export function decodeSegments(segments: string[]): string[] {
  try {
    return segments.map((s) => decodeURIComponent(s));
  } catch {
    notFound(); // a malformed escape
  }
}

Source: Dynamic Segments: TypeScript, PageProps helper, notFound

Why a pattern and not Number(id)? Number('1e3') is 1000, Number('') is 0 and parseInt('1abc', 10) is 1: each turns a junk URL into a real book page and a separate cache entry. The nine-digit cap stays below Number.MAX_SAFE_INTEGER. Spellings the pattern does accept, such as 01, are sent to the canonical URL with permanentRedirect (308), so search engines and the ISR cache see one URL per book. Narrowing works because notFound() and permanentRedirect() throw and are typed never.

Check per-page params (id, slug) in the page, not a layout: a layout does not re-run on a soft navigation between its children. And give generateMetadata the same guard, or it can build a <title> from an invalid value.

Never interpolate a raw param into a query string, a file path or a command: a slug captured into an fs path allows .. tricks (see Special Characters in Segments: Encoding and Decoding), and a slug concatenated into a GROQ or SQL query allows injection. The consulted e-commerce book, for instance, interpolates the slug into a CMS query; the correct form passes it as a query parameter.

The same generated types also check the other direction: with typedRoutes: true, a link such as /${locale}/book/${id} (a typo for books) fails the TypeScript step of next build with TS2322, while /${locale}/books/${id} passes. Prefer template literals for links to dynamic routes; a concatenated string is not checked and needs an as Route cast. The option is covered in Configuration, TypeScript and Environment Variables.

  • Decode once, in pages. Decoding twice corrupts values containing %; Route Handlers and the Pages Router already decode.

Multiple Segments: Top Down or Bottom Up

You can generate params for segments above the current file, never below. Two approaches work. Bottom up: the leaf page returns every combination at once. Top down: the parent layout returns its own segment and the child’s generateStaticParams runs once per parent value, receiving what the parent generated:

Top down: the parent generates [author], the child [title]
// app/[locale]/(shop)/authors/[author]/layout.tsx
export function generateStaticParams() {
  return [{ author: "herbert" }, { author: "gibson" }];
}

export default function AuthorLayout({ children }: LayoutProps<"/[locale]/authors/[author]">) {
  return <div>{children}</div>;
}

// app/[locale]/(shop)/authors/[author]/[title]/page.tsx
const titles: Record<string, string[]> = {
  herbert: ["dune", "children-of-dune"],
  gibson: ["neuromancer"],
};

export function generateStaticParams({ params }: { params: { author: string } }) {
  return (titles[params.author] ?? []).map((title) => ({ title }));
}

The build table above lists /en/authors/herbert/dune, /en/authors/herbert/children-of-dune and /en/authors/gibson/neuromancer (and the three es twins). Inside a nested generateStaticParams a root parameter can also be read directly with its next/root-params getter instead of destructuring it from params.

Previous Model: Subsets, dynamicParams and Request-time Rendering

What happens for a value that generateStaticParams did not return is controlled by the dynamicParams route segment config (it replaces the fallback: true | false | 'blocking' option of the Pages Router’s getStaticPaths):

  • true (the default): the page is rendered on demand the first time and the result is cached.

  • false: the page answers 404 for every value not returned by generateStaticParams.

The Bookshelf book page prerenders ids 1 and 2. With the default dynamicParams = true, id 3 renders on demand, and the second request is already a cache hit. Setting dynamicParams = false makes id 3 a 404:

app/[locale]/(shop)/books/[id]/page.tsx: only the ids from generateStaticParams exist
// Previous model only: false turns every id outside generateStaticParams into a 404.
// It is not allowed when cacheComponents is on.
export const dynamicParams = false;

Cache Components: Samples, Not Lists

With cacheComponents: true the contract of generateStaticParams changes. It supplies samples: param values used at build time to run the route and validate that it accesses runtime data correctly. The rules, all verified on 16.3.8:

  • generateStaticParams must return at least one param. An empty array is a build error (empty-generate-static-params), because with no sample Next.js cannot check that the route does not read cookies(), headers() or searchParams incorrectly.

  • dynamicParams is not available: exporting it fails the build, whatever its value.

  • Values returned by generateStaticParams are prerendered into complete static HTML. Other values are runtime params: the static shell is sent, then the param-dependent content streams in, and pages rendered this way are saved after a successful first request.

  • Build-time validation covers only the code paths the samples execute. A branch reached by other values (for example slug.startsWith('private-') reading cookies()) is validated on the first request instead, so wrap such branches in <Suspense>.

Per-group Layouts and Opting Out of a Layout

A route inherits every layout on its folder path, and there is no "skip the parent layout" switch. A route group is how you give a layout to some siblings without inventing a URL segment. In the URL map, (shop) holds the shop navigation, (account) the account navigation (in the full Bookshelf it also runs the session check of the Data Access Layer), and (marketing) a plain wrapper. (checkout) has no layout: to remove checkout from the shop chrome you do not configure checkout, you move it next to (shop) instead of inside it. The probe confirms it: /en/checkout returns 200 with no data-group="shop" element.

The same move scopes loading.tsx, error.tsx and not-found.tsx to one route. Groups are only needed at the same level: books/new/page.tsx never sees books/[id]/layout.tsx, because it is not below that folder.

Private Folders

A folder whose name starts with an underscore, _folderName, is a private folder: the routing system ignores it and every subfolder. The Bookshelf keeps shared UI next to the routes that use it in app/[locale]/_components/:

app/[locale]/_components/book-card.tsx, imported by the catalogue page

Files in app/ are safely colocated by default (only page and route files create URLs), so a private folder is not required for colocation. Root Parameters and next/root-params

The dynamic segments that sit above the root layout are root parameters. The Bookshelf’s [locale] is one, because its root layout is app/[locale]/layout.tsx. Normally a deeply nested component gets a param only if every ancestor passes the params prop down. The next/root-params module (shipped in 16.3) removes that: it exports one async getter per root parameter, named after the folder, and any Server Component or server-side utility can import it:

app/[locale]/layout.tsx: the root layout reads the locale with a getter
import { notFound } from "next/navigation";
import { locale } from "next/root-params";
import { locales, isLocale } from "@/lib/i18n";

export function generateStaticParams() {
  return locales.map((locale) => ({ locale }));
}

export default async function RootLayout({ children }: LayoutProps<"/[locale]">) {
  const current = await locale();
  if (!current || !isLocale(current)) notFound();
  return (
    <html lang={current}>
      <body>{children}</body>
    </html>
  );
}

// <p>by {book.author} (locale: {loc})</p>

<pre>catch-all params={"slug":["a","b/c"]}</pre>

Four behaviours differ from the App Router:

  • The route param wins over a query parameter of the same name. /legacy/1?id=2 gives query.id === '1', and the ?id=2 is lost. In the App Router params and searchParams are separate props and never collide.

  • Values are decoded: 'café', '100%', and b%2Fc as one segment 'b/c', where an App Router page receives 'caf%C3%A9' (see Special Characters in Segments: Encoding and Decoding). Check before porting a decodeURIComponent call between the routers.

  • State is not reset when only the param changes. /legacy/1 to /legacy/2 renders the same component, so React keeps its state; the documented fixes are a key on Component in pages/_app.tsx or an effect keyed on router.query.id. In the App Router a layout under [id] remounts per id on its own.

  • The next/navigation hooks become nullable when both routers are present. With a pages/ directory, Next.js adds /// <reference types="next/navigation-types/compat/navigation" /> to next-env.d.ts, which types useParams, usePathname, useSearchParams and the segment hooks as possibly null. The URL map’s segments.tsx then failed with error TS18047: 'all' is possibly 'null'; handle the null in shared components.

13.4

App Router stable. generateStaticParams replaces getStaticPaths; dynamicParams replaces fallback.

Use them for new routes. See the previous section for the Pages Router equivalents.

13.3.0

useParams introduced for Client Components in next/navigation.

Use it for params deep in the client tree.

15

params becomes a Promise. Synchronous access still works temporarily, for compatibility; codemod next-async-request-api migrates.
