This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when the facts and examples below were checked; the official documentation reports @doc-version 16.3.8), React 19.3.0, Node.js 20.9.0 or later and TypeScript 5.1 or later. It covers the App Router in depth, which is where the official authentication guides live, and the Pages Router where its code differs (Auth.js in getServerSideProps, and the pitfalls of using it there). Caching changes how a session may be read, so each example says which of the two models it uses: the previous model (the default, in which nothing is cached unless you ask) or the opt-in Cache Components model (cacheComponents: true), which has a section of its own. Every example was built with next build and run with next start and curl, or with a headless browser, on Next.js 16.3.8, Node.js 24.16 and macOS, in scratch copies of the Bookshelf catalogue that the rest of this section grows. No real account of any provider was used: the Auth.js, Better Auth and custom examples ran end to end against a local data source, and the Auth0 and Clerk examples were built or type-checked only, which each of them says. Every example is followed by the official page it derives from.

The page answers one question: where does each check live, and what does a request that skips the user interface reach? The short answer is that the session is established once, read through one server-only function, and verified again next to the data every time something is read or changed. The Proxy, the layouts and the client components only improve the user experience. If OAuth 2.0 and OpenID Connect are new, read the protocol background first, in OAuth 2.0 and OpenID Connect; this page links to the relevant chapters instead of repeating them.

Authentication, Session Management and Authorization

The official guide splits the topic into three concepts, and the rest of this page follows the same split:

Table 1. The three concerns of the official authentication guide
Concern Question it answers Typical Next.js building blocks

Authentication

Is this user who they say they are?

A form posting to a Server Action, an OAuth or OIDC redirect, a magic link, a passkey. Handled by a library or by your code.

Session management

How does the next request prove it is the same user?

A signed or encrypted cookie read with cookies() (a stateless session), or an opaque id in a cookie that points to a database row (a database session).

Authorization

What may this user read or change?

Checks in the Data Access Layer, Server Components, Server Actions and Route Handlers; optimistic redirects in Proxy; forbidden() and unauthorized().

Authentication proves identity once; authorization is asked on every read and write. Next.js has several entry points to the same data (page requests, client navigations, Server Actions, Route Handlers, fetch from a script), and each entry point has to ask the question for itself.

The Sign-In and Authorization Flow

The sequence below follows one login and two later requests. The first request shows the layers working together; the second shows the case that decides whether the application is secure: a request that carries a valid-looking cookie whose owner has lost a privilege.

sequenceDiagram participant B as Browser participant P as Proxy (optimistic) participant S as Server Action / Server Component participant D as Data Access Layer participant DB as Data source B->>S: POST login form (email, password) S->>S: validate with Zod S->>DB: find user, compare password hash DB-->>S: user row S-->>B: 303 to /dashboard + Set-Cookie (HttpOnly, SameSite, Max-Age) B->>P: GET /dashboard + cookie P->>P: verify signature only (no database) P-->>S: next() S->>D: verifySession() D->>D: decrypt cookie D->>DB: re-read the user (role, still exists?) DB-->>D: current user row D-->>S: userId, role S-->>B: 200 HTML (or 403 / 401 UI) Note over B,DB: Later, the admin role is removed in the database B->>P: GET /admin + same cookie P-->>S: next() (signature still valid) S->>D: verifySession() D->>DB: re-read the user DB-->>D: role is now "user" D-->>S: role "user" S-->>B: forbidden() renders the 403 page
Figure 1. Sign-in, optimistic check in Proxy and authoritative check in the Data Access Layer

The Proxy cannot know that the role changed, because it deliberately does not touch the database. The Data Access Layer can. That asymmetry is the reason for the two kinds of check described in Optimistic Checks in Proxy and The Data Access Layer.

Table 2. Where each kind of check runs
Place Kind of check What it is good for

Proxy (proxy.ts)

Optimistic: cookie only

Cheap pre-filtering and redirects for the whole site, and protecting static routes that share data between users.

Data Access Layer (verifySession)

Authoritative: cookie plus data source

The single place every read goes through. Called from pages, leaf components, Server Actions and Route Handlers.

Server Component or page

Authoritative, through the DAL

Role-based rendering, redirect(), forbidden(), unauthorized().

Server Action

Authoritative, through the DAL

Every action is a public POST endpoint; it authorises itself.

Route Handler

Authoritative, through the DAL

Returns 401 or 403 as a response, because there is no page to redirect to.

Layout

Not a security boundary

Shell data such as the user’s name. Does not re-render on navigation (see Why a Layout Alone Is Not Enough).

Client Component

Not a security boundary

Showing or hiding UI. Receives only the data the server chose to pass.

Source: Authentication, Data Security.

Session Management

A session keeps the authenticated state across requests. The official guide names two families and recommends a session library (iron-session or jose) over hand-written cryptography; the examples below use jose because it is what the guide’s own samples use and it runs in both the Node.js and the Edge runtimes.

The official guide describes the trade-off as simple versus secure; the practical summary is that stateless sessions are enough for many applications provided the Data Access Layer re-reads the user, and that database sessions pay for revocation, device lists and "last seen" features.

Stateless Sessions with a Signed Cookie

A stateless session needs a secret, a pair of functions to sign and verify the payload, and a cookie set on the server. Generate the secret once, keep it in the environment, and never commit it:

openssl rand -base64 32      # a 32-byte random secret; paste it into .env.local
# .env.local (never committed)
# SESSION_SECRET=<the generated value>

Reference it as process.env.SESSION_SECRET. The module below is marked server-only so that importing it from a Client Component fails the build instead of leaking the secret into a bundle (see Configuration, TypeScript and Environment Variables). It fixes four faults that the requester books' login examples share (listed in Where the Books Are Outdated): the secret comes from the environment, the token expires, a tampered cookie yields undefined instead of an uncaught exception, and the cookie is HttpOnly, SameSite and (in production) Secure.

lib/session.ts
import "server-only";
import { SignJWT, jwtVerify } from "jose";
import { cookies } from "next/headers";
import type { SessionPayload } from "@/lib/definitions";

const encodedKey = new TextEncoder().encode(process.env.SESSION_SECRET);
export const COOKIE_NAME = "session";

export async function encrypt(payload: SessionPayload) {
  return new SignJWT({ ...payload })
    .setProtectedHeader({ alg: "HS256" })
    .setIssuedAt()
    .setExpirationTime("7d")
    .sign(encodedKey);
}

export async function decrypt(session: string | undefined = "") {
  try {
    const { payload } = await jwtVerify(session, encodedKey, { algorithms: ["HS256"] });
    return payload as unknown as SessionPayload;
  } catch {
    return undefined; // tampered, expired or missing: never throw to the user
  }
}

export async function createSession(userId: string, role: SessionPayload["role"]) {
  const expiresAt = new Date(Date.now() + 7 * 24 * 60 * 60 * 1000);
  const session = await encrypt({ userId, role, expiresAt });
  const cookieStore = await cookies();
  cookieStore.set(COOKIE_NAME, session, {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    expires: expiresAt,
    sameSite: "lax",
    path: "/",
  });
}

export async function deleteSession() {
  (await cookies()).delete(COOKIE_NAME);
}

Option Why

httpOnly: true

JavaScript on the page cannot read the cookie, which limits what an XSS bug can steal.

secure: true

Sent over HTTPS only. The example enables it when NODE_ENV is production, because a browser may refuse a Secure cookie on plain HTTP in development.

sameSite: "lax"

Not sent on cross-site sub-requests such as a form posted from another site; part of the defence against CSRF (see CORS for the cross-origin side).

A session without an expiry never ends. The signed token carries its own expiry as well (setExpirationTime), so a copied cookie stops working on time.

Sent with every request to the site.

Cookies must be set on the server. Setting them in the browser lets client code tamper with them, and the session cookie should not be readable from the client in the first place. The payload should hold the minimum (a user id and a role hint), never an email, a phone number or anything sensitive: a signed token is readable by whoever holds it.

The Login Server Action

The login form posts to a Server Action. The action validates the fields with Zod and returns early on failure (so the user database is not queried with garbage), checks the password against a salted hash, answers the same message for an unknown user and a wrong password (so the form cannot be used to discover which emails are registered), creates the session and redirects. redirect() throws, so it comes last and outside any try/catch.

app/actions/auth.ts
"use server";

import * as z from "zod";
import { redirect } from "next/navigation";
import { LoginSchema, type FormState } from "@/lib/definitions";
import { createSession, deleteSession } from "@/lib/session";
import { findUserByEmail, verifyPassword } from "@/lib/users";

export async function login(state: FormState, formData: FormData): Promise<FormState> {
  const parsed = LoginSchema.safeParse({
    email: formData.get("email"),
    password: formData.get("password"),
  });
  if (!parsed.success) {
    return { errors: z.flattenError(parsed.error).fieldErrors };
  }

  const user = await findUserByEmail(parsed.data.email);
  // Same message for "no such user" and "wrong password"
  if (!user || !verifyPassword(parsed.data.password, user.passwordHash)) {
    return { message: "Invalid email or password." };
  }

  await createSession(user.id, user.role);
  redirect("/dashboard");
}

export async function logout() {
  await deleteSession();
  redirect("/login");
}

import "server-only";
import { randomBytes, scryptSync, timingSafeEqual } from "node:crypto";
import type { Role } from "@/lib/definitions";

export type UserRow = {
  id: string;
  name: string;
  email: string;
  role: Role;
  passwordHash: string;
};

function hashPassword(password: string): string {
  const salt = randomBytes(16);
  return `${salt.toString("hex")}:${scryptSync(password, salt, 32).toString("hex")}`;
}

export function verifyPassword(password: string, stored: string): boolean {
  const [salt, hash] = stored.split(":");
  const candidate = scryptSync(password, Buffer.from(salt, "hex"), 32);
  return timingSafeEqual(candidate, Buffer.from(hash, "hex"));
}

// Stands in for a database table. Seeded from an env var, never a literal.
const seed = process.env.SEED_PASSWORD ?? "";
const table: UserRow[] = [
  { id: "u1", name: "Ada", email: "ada@example.com", role: "admin", passwordHash: hashPassword(seed) },
  { id: "u2", name: "Bob", email: "bob@example.com", role: "user", passwordHash: hashPassword(seed) },
];

  return table.find((u) => u.email === email);
}
export async function findUserById(id: string) {
  return table.find((u) => u.id === id);
}
export async function demoteToUser(id: string) {
  const u = table.find((x) => x.id === id);

Database Sessions

With a database session the cookie holds only an opaque id (signed, so the server can reject forgeries cheaply) and the state lives in a table. The module below keeps the "table" in memory so that it runs anywhere; replace the Map with your database. The guide notes that keeping the cookie and the row in sync also lets Proxy do an optimistic check on the cookie.

lib/db-session.ts
import "server-only";
import { randomUUID } from "node:crypto";
import { cookies } from "next/headers";
import { SignJWT, jwtVerify } from "jose";

const key = new TextEncoder().encode(process.env.SESSION_SECRET);
const COOKIE = "sid";

type SessionRow = { id: string; userId: string; expiresAt: number };
const sessions = new Map<string, SessionRow>(); // stands in for a "sessions" table

export async function createDbSession(userId: string) {
  const expiresAt = Date.now() + 7 * 24 * 60 * 60 * 1000;
  const row: SessionRow = { id: randomUUID(), userId, expiresAt };
  sessions.set(row.id, row); // 1. persist the session

  const sealed = await new SignJWT({ sid: row.id }) // 2. the cookie only carries the id
    .setProtectedHeader({ alg: "HS256" })
    .setExpirationTime("7d")
    .sign(key);
  (await cookies()).set(COOKIE, sealed, {
    httpOnly: true,
    secure: process.env.NODE_ENV === "production",
    sameSite: "lax",
    expires: expiresAt,
    path: "/",
  });
}

export async function readDbSession() {
  const sealed = (await cookies()).get(COOKIE)?.value;
  if (!sealed) return null;
  try {
    const { payload } = await jwtVerify(sealed, key, { algorithms: ["HS256"] });
    const row = sessions.get(String(payload.sid));
    if (!row || row.expiresAt < Date.now()) return null; // revoked or expired
    return row;
  } catch {
    return null;
  }
}

// "Sign out everywhere": impossible with a pure stateless cookie.
export function revokeAllSessions(userId: string) {
  for (const [id, row] of sessions) if (row.userId === userId) sessions.delete(id);
}

Where the Session Is Read: Three Layers

Authorization has three layers, each with a different cost and a different promise. The next three sections build them in order, using the stateless session above.

  • Proxy sees every request before routing, runs once per navigation and prefetch, and should only read the cookie.

  • The Data Access Layer is the single server-only function that reads the session and the user, and everything that touches data calls it.

  • The call site (page, leaf component, Server Action, Route Handler) decides what to do with the answer: render, redirect, 401, 403.

Optimistic Checks in Proxy

Proxy (proxy.ts, the Next.js 16 name for middleware.ts) runs before every matched request, including prefetches, so it is the natural place for cheap redirects: send signed-out visitors away from /dashboard, send signed-in visitors away from /login. The official guide limits it to optimistic checks, reading the session from the cookie and avoiding database calls, because a database round trip on every navigation and prefetch is slow. In Next.js 16 Proxy runs on the Node.js runtime, so check that your auth and session libraries support it. The full Proxy reference, matcher and evaluation order are in Redirects, Rewrites and Proxy.

proxy.ts
import { NextResponse, type NextRequest } from "next/server";
import { COOKIE_NAME, decrypt } from "@/lib/session";

const protectedRoutes = ["/dashboard", "/admin"];

export default async function proxy(req: NextRequest) {
  const path = req.nextUrl.pathname;
  const isProtected = protectedRoutes.some((r) => path === r || path.startsWith(`${r}/`));

  // Optimistic: only verify the signature, never hit the database here
  const session = await decrypt(req.cookies.get(COOKIE_NAME)?.value);

  if (isProtected && !session?.userId) {
    return NextResponse.redirect(new URL("/login", req.nextUrl));
  }
  if (path === "/login" && session?.userId) {
    return NextResponse.redirect(new URL("/dashboard", req.nextUrl));
  }
  return NextResponse.next();
}

export const config = {
  matcher: ["/((?!api|_next/static|_next/image|.*\\.png$).*)"],
};

A static page is built once, so a verifySession() call in it would run at build time, not per request; the optimistic check in Proxy is what keeps unauthenticated visitors away from it.

The Data Access Layer

The guide recommends a Data Access Layer (DAL): one module that centralises data requests and authorization logic. It exports a verifySession() function that every other function calls first. Three details matter:

  • It is marked server-only, so a Client Component cannot import it.

  • It wraps the function in React cache, so calling it from a layout, a page and a leaf component in the same render runs the check once.

  • It is authoritative: after decrypting the cookie it re-reads the user from the data source, so a cookie that says admin cannot outlive the database row that says user.

lib/dal.ts
import "server-only";
import { cache } from "react";
import { cookies } from "next/headers";
import { redirect } from "next/navigation";
import { COOKIE_NAME, decrypt } from "@/lib/session";
import { findUserById } from "@/lib/users";

// Authoritative check: verify the signed cookie, then re-read the user
// from the data source so a stale cookie cannot keep old privileges.
export const verifySession = cache(async () => {
  const cookie = (await cookies()).get(COOKIE_NAME)?.value;
  const session = await decrypt(cookie);
  if (!session?.userId) redirect("/login");

  const user = await findUserById(session.userId);
  if (!user) redirect("/login");
  return { isAuth: true as const, userId: user.id, role: user.role };
});

// Data Transfer Object: return only what the UI may see.
export const getUser = cache(async () => {
  const session = await verifySession();
  const user = await findUserById(session.userId);
  return user && { id: user.id, name: user.name, role: user.role };
});

Why a Layout Alone Is Not Enough

The official guide is explicit: be cautious about checks in layouts. A layout does not re-render on navigation because of Partial Rendering, so a check that lives only there does not run on every route change, and a layout does not control whether the rest of the route renders. Route segments and parallel route slots are rendered by the router; a layout that hides or swaps them does not stop them from running or from appearing in the RSC payload. A common single-page-app pattern, returning null from a layout when the user is not authorized, is therefore not recommended: Next.js has several entry points, and it does not stop nested segments or Server Actions from being reached. The guidance is to check close to the data source or to the component that is conditionally rendered. A layout may fetch the user for the navigation bar, but the check belongs in the getUser() of the DAL, so that it runs wherever the function is called. See Layouts, Templates and Special Files for the rendering behaviour behind this.

The following is the anti-pattern, a members-only section whose only check is in its layout, with a Server Action next to it that trusts the layout:

Server Actions

The guide says to treat Server Actions with the same security considerations as public-facing API endpoints. The mechanics (action IDs, closure encryption, allowedOrigins, input validation) are in Server Actions and Mutations; the authorization rule is the one the safe action above follows: call the DAL first, take only references from the client (an id), re-read the row, and compare its owner with the session. Returning early when the role is wrong (return null) is acceptable in the official sample; calling forbidden() (below) is clearer for callers that render the result.

Rules and limits from the reference pages:

  • forbidden() cannot be called in the root layout.

  • They work by throwing. return forbidden() is unnecessary (the return type is never), and a try/catch around the call swallows the interrupt so no UI renders; use unstable_rethrow to let it through.

  • Call them in the render path: a component, or a function a component awaits. A call in an un-awaited promise throws where nothing catches it (development logs NEXT_HTTP_ERROR_FALLBACK;403 as an unhandled rejection).

  • Status codes depend on streaming. If the check runs inside a <Suspense> boundary, the response has begun as 200 and the status cannot change; the interrupt UI still renders in place. To get a real 403 the check must run before the response streams. Under Cache Components every dynamic route streams a static shell first, so the official page says to run that check in Proxy instead (see Authentication with Cache Components).

The Configuration, the Route Handler and Proxy

auth.ts
import NextAuth, { type DefaultSession } from "next-auth";
import GitHub from "next-auth/providers/github";
import Credentials from "next-auth/providers/credentials";
import "next-auth/jwt"; // makes the declare module below an augmentation
import { findUserByEmail, verifyPassword, type Role } from "@/lib/users";

declare module "next-auth" {
  interface Session {
    user: { id: string; role: Role } & DefaultSession["user"];
  }
  interface User {
    role?: Role;
  }
}
declare module "next-auth/jwt" {
  interface JWT {
    uid?: string;
    role?: Role;
  }
}

export const { handlers, auth, signIn, signOut } = NextAuth({
  providers: [
    // Reads AUTH_GITHUB_ID and AUTH_GITHUB_SECRET from the environment
    GitHub,
    Credentials({
      credentials: { email: {}, password: {} },
      authorize: async (credentials) => {
        const user = await findUserByEmail(String(credentials?.email ?? ""));
        if (!user || !verifyPassword(String(credentials?.password ?? ""), user.passwordHash)) {
          return null; // Auth.js turns this into a CredentialsSignin error
        }
        return { id: user.id, name: user.name, email: user.email, role: user.role };
      },
    }),
  ],
  session: { strategy: "jwt", maxAge: 60 * 60 * 24 * 7 },
  pages: { signIn: "/login" },
  callbacks: {
    // Runs in Proxy when auth is exported as proxy: an optimistic check
    authorized({ auth, request: { nextUrl } }) {
      const protectedPath = ["/dashboard", "/admin"].some((p) => nextUrl.pathname.startsWith(p));
      return protectedPath ? !!auth?.user : true;
    },
    jwt({ token, user }) {
      if (user) {
        token.uid = user.id;
        token.role = user.role ?? "user";
      }
      return token;
    },
    session({ session, token }) {
      session.user.id = token.uid ?? "";
      session.user.role = token.role ?? "user";
      return session;
    },
  },
});

What each piece does:

  • NextAuth({ providers, …​ }) returns handlers, auth, signIn and signOut. The route handler mounts handlers under /api/auth/* (sign-in, callback, session, CSRF and providers endpoints).

  • GitHub is passed without options: the client id and secret come from AUTH_GITHUB_ID and AUTH_GITHUB_SECRET. The callback URL to register in GitHub is https://<your-host>/api/auth/callback/github.

  • The Credentials provider forwards a login form to your authorize function; returning null makes Auth.js fail the sign-in with CredentialsSignin. It does not persist anything by default. The Auth.js page presents it for external authentication mechanisms and traditional username and password flows; prefer an OAuth, passkey or email provider where you can, and see Authentication Methods, 2FA and Passwordless.

  • session.strategy: "jwt" is the default when no database adapter is configured: a JWT in an HttpOnly cookie. With an adapter the default becomes "database", where the cookie holds a session id. The jwt and session callbacks copy the user id and role into the token and then into the session, which the declare module blocks type. The import "next-auth/jwt" line makes the second block an augmentation; without it TypeScript reports that the module cannot be found.

  • export { auth as proxy } from "@/auth" makes Proxy run auth() on every matched request, which also keeps the session alive by refreshing its expiry. The authorized callback decides what an unauthenticated request may reach: returning false redirects to the sign-in page. It is an optimistic check, with the same limits as any Proxy check.

  • On Next.js 14 and 15 the same file is middleware.ts and the export is export { auth as middleware }.

  • A database adapter that cannot run on the Edge needs the configuration split in two (an auth.config.ts without the adapter, used by Proxy or middleware, and the full auth.ts). Whether the split is still needed on the Node.js Proxy of Next.js 16 depends on the adapter; the scratch build above ran the full file in Proxy, without an adapter.

Authentication with Cache Components

With cacheComponents: true the rules for reading a session change, because a session read is a request-time read and a request-time read cannot be part of the static shell. The official companion guide (updated 2026-08-25) gives the pattern; this section reproduces its steps with the Bookshelf’s own session module and runs them. The caching background is in Partial Prerendering and Cache Components and Caching. The examples below were built with CACHE_COMPONENTS=1 (the scratch next.config.ts reads that variable for the flag; in a real project the flag is simply cacheComponents: true).

Step 1: Read the Current User in a Private Cache

A plain use cache function cannot call cookies(), and neither can use cache: remote; the session helper reads the cookie deep inside its own code and compares an expiry with the current time, so there is nothing to lift out and pass in. use cache: private exists for this case: it may read cookies(), headers() and searchParams, keeps the result in the browser only, and never caches it on the server. redirect() throws to interrupt rendering, so it is not cached; only a resolved user is.

lib/auth.ts
import "server-only";
import { cookies } from "next/headers";
import { redirect } from "next/navigation";
import { COOKIE_NAME, decrypt } from "@/lib/session";
import { findUserById } from "@/lib/users";

export type CurrentUser = { id: string; name: string; role: "admin" | "user" };

// Reads cookies(), so it must be "use cache: private": the result may be
// kept in the browser's cache, never on the server.
export async function getCurrentUser(): Promise<CurrentUser> {
  "use cache: private";
  const session = await decrypt((await cookies()).get(COOKIE_NAME)?.value);
  if (!session?.userId) redirect("/login");
  const user = await findUserById(session.userId);
  if (!user) redirect("/login");
  return { id: user.id, name: user.name, role: user.role };
}

A component that reads the session must sit behind a <Suspense> boundary; reading cookies() outside one is a build error with Cache Components. A real 403 needs the check to run before streaming, and under Cache Components the official forbidden() page says to do that check in Proxy. Proxy can only see the cookie, so a Proxy that returns 403 for the /admin prefix must rely on the role hint in the signed cookie (an optimistic check) while the Data Access Layer keeps the authoritative one; or accept the 200 plus the interrupt UI, which is usually fine for a page the user is shown rather than an API. A Route Handler is unaffected: it returns a real 401 or 403.

Step 3: Share the User with Client Components

Read the session once and hand it to both Server and Client Components inside the same boundary. A Server Component can call getCurrentUser() directly; for a Client Component, create the promise in the Server Component inside the Suspense boundary (not at the top of a layout), pass it through a context provider, and unwrap it with React’s use() behind its own <Suspense>. Expose only a narrow { id, name }, not the raw session, and use taintUniqueValue for sensitive fields. The official guide lists a UserProvider and a useUser() hook for this; the pattern is the one in Server and Client Components (passing a promise as a prop).

Step 4: Cache Data Derived From the Session

Once you have the user, cache what you fetch for them in one of two ways. Passing the user id into a plain use cache function keeps the result on the server, keyed by the id (which becomes part of the cache key) and invalidatable with a tag. Reading inside a use cache: private scope keeps it in the browser only, which matters when requirements forbid storing certain data on the server even briefly.

lib/notes.ts
import "server-only";
import { cacheLife, cacheTag } from "next/cache";
import { getCurrentUser } from "@/lib/auth";

const notes = new Map<string, string[]>();
export let reads = 0; // counts real "database" reads (scratch only)

export async function saveNote(userId: string, note: string) {
  notes.set(userId, [...(notes.get(userId) ?? []), note]);
}

// Exported: resolves the user first, so a caller cannot pick another id.
export async function getNotes() {
  const user = await getCurrentUser();
  return getNotesByUserId(user.id);
}

// Not exported on purpose. The user id becomes part of the cache key.
async function getNotesByUserId(userId: string) {
  "use cache";
  cacheTag(`notes:${userId}`);
  cacheLife("minutes");
  reads++;
  console.log(`db read for ${userId} (#${reads})`);
  return notes.get(userId) ?? [];
}

Keep getNotesByUserId unexported, so that no caller can ask for another user’s notes with a different id; resolving the user inside the exported getter is what makes that safe. Cache keys and cacheTag values are stored in plain text, so key and tag on a stable identifier such as the user id, never on a token, a password or a raw email.

Step 5: Update Session-Derived Data

A Server Action that changes the data calls updateTag with the same tag, and re-reads the session itself so that it authorises itself rather than trusting the client:

app/actions/notes.ts
"use server";

import { updateTag } from "next/cache";
import { redirect } from "next/navigation";
import { COOKIE_NAME, decrypt } from "@/lib/session";
import { cookies } from "next/headers";
import { saveNote } from "@/lib/notes";

export async function addNote(formData: FormData) {
  // Re-read the session: the action authorises itself.
  const session = await decrypt((await cookies()).get(COOKIE_NAME)?.value);
  if (!session?.userId) redirect("/login");

  const note = String(formData.get("note") ?? "").trim();
  if (note) {
    await saveNote(session.userId, note);
    updateTag(`notes:${session.userId}`);
  }
}

The server log counted "database" reads. Ada’s dashboard, requested twice, and Bob’s, requested once, produced two reads (one per user id); after Ada added a note through the action, her entry was invalidated and read again, Bob’s was not, and Bob did not see Ada’s note. An anonymous POST of the same action was answered 307 and wrote nothing.

Step 6: Make Authenticated Navigations Instant

A use cache: private scope uses the default cache profile (a five-minute stale) unless you set one, and a route that reads the session yields a per-session App Shell that is prefetched and cached per session, so navigations to it are already instant. Two things keep it that way: if you tune the lifetime with cacheLife, keep stale at 30 seconds or more (below that the scope drops out of prefetching), and a route that also depends on a params or searchParams value needs <Link prefetch={true}> on the links that point to it, together with Partial Prefetching (the partialPrefetching flag, or prefetch = "partial" on the segment). Each such link costs one server invocation, so a sidebar of many links should not all use it. The behaviour of prefetching is described in Linking and Navigation.

An existing application that enables Cache Components gets every session-reading route flagged by instant-navigation validation. The guide’s migration advice is to set export const instant = false on the page or layout so it keeps blocking on the server, and then adopt the patterns one route at a time.

Pitfalls

  • Authorizing in the client only. See Where the Books Are Outdated: hiding UI protects nothing; the endpoint must check.

  • Checking only in a layout or only in Proxy. See Why a Layout Alone Is Not Enough and Optimistic Checks in Proxy.

  • Trusting the role in the cookie. Re-read the user in the DAL; the cookie is a hint.

  • redirect() inside try/catch. redirect(), notFound(), forbidden() and unauthorized() work by throwing; catching the error cancels them. Call them last, outside try, or rethrow with unstable_rethrow.

  • Reading cookies() outside <Suspense> under Cache Components. It is a build error; push the read into a component behind a boundary. Reading cookies() inside a plain use cache function throws; use use cache: private.

  • Secrets in cache keys, tags, logs or client props. Arguments and tags are plain text; pass ids.

  • A wrong status code under streaming. A check inside <Suspense> yields 200 with the interrupt UI (see Authentication with Cache Components).

  • Forgetting AUTH_TRUST_HOST behind a proxy or on localhost with next start. Auth.js answers UntrustedHost.

  • secure: true in local development. A Secure cookie may be refused over plain HTTP; enable it in production.

  • Unauthenticated GET prefetches that have side effects. Proxy and pages run on prefetches; a link to a login route should not write a transaction cookie (the Auth0 SDK special-cases the default prefetch for this reason).

  • Sessions in the URL. Never put tokens in query strings; use cookies set on the server.

  • No expiry, no rotation. Give the cookie and the token an expiry; rotate SESSION_SECRET and AUTH_SECRET when a copy might have leaked (which invalidates existing sessions, a trade-off to plan for).

  • Testing only the happy path. A useful HTTP test includes the negative cases: no cookie, a tampered cookie, a valid cookie for a user without the role, and an action posted without a session. The sibling page on testing and the end-to-end chapter End-to-End Testing in Real Browsers show how to log in once and reuse the state; the OAuth side is in Testing and Debugging OAuth.
