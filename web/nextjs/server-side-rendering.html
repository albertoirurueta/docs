Server-Side Rendering

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when the facts and examples below were checked; the official documentation reports @doc-version 16.3.8), React 19.3.0 and Node.js 20.9.0 or later. It covers the App Router in depth and the Pages Router (getServerSideProps) side by side, because the two routers solve the same problem with very different machinery. Caching matters here, so every example says which model it uses: the previous model (the default: nothing is cached unless you ask) or Cache Components (the opt-in cacheComponents: true model, in which everything is dynamic unless you cache it and a static shell is prerendered). Every example was built with next build and served with next start (Node.js 24.16, macOS) in a scratch copy of the Bookshelf — the catalogue of books, authors and reviews that this section grows — and the results quoted below are what curl returned.

Server-side rendering (SSR) means that the HTML of a page is produced on the server for each request, after the request has arrived, so the output can depend on who is asking and on what the data is right now. This page explains how Next.js decides that a route needs it, what the server sends back, how the response is streamed, and what it costs. It builds on Routing Fundamentals and Layouts, Templates and Special Files; the rendering spectrum (SSR next to SSG, ISR, PPR and CSR) is compared on the Rendering Fundamentals page, and Server Components, streaming and Suspense have their own pages (Server and Client Components, Streaming and Suspense), which are only summarised here. For the React ideas underneath, see Server Rendering, SSG and React Server Components.

What SSR Is and Why You Use It

By default Next.js renders a route once, ahead of time, and serves the result as many times as it is asked for. That is prerendering, and it is the default for any component that does not use a Request-time API. SSR is the opposite decision: render when the request arrives. The official glossary calls it dynamic rendering (also "runtime rendering"): "when a component is rendered at request time rather than build time", which happens when it uses a Request-time API or, in the previous model, uncached data.

Table 1. The vocabulary, mapped to what you will see in the documentation
Term Meaning Where it appears

Server-side rendering (SSR)

HTML is generated on the server for each request.

Everyday name; the Pages Router docs title it "Server-side Rendering" and say it is also referred to as "Dynamic Rendering".

Dynamic rendering

An App Router route (or the dynamic part of one) is rendered at request time.

App Router glossary; the build route table marks it ƒ (Dynamic) or ◐ (Partial Prerender).

Prerendering

HTML and RSC payload produced at build time, or in the background on revalidation.

Default for components that read no request data; the opposite of SSR.

Request-time APIs

Functions and props that read request-specific data and therefore opt the component into dynamic rendering.

cookies(), headers(), searchParams, draftMode(), and in practice connection().

Server Component

A component that runs only on the server, can be async, and ships no JavaScript to the browser.

The unit that does the rendering in the App Router.

Source: Next.js glossary and Pages Router: Server-side Rendering

Use SSR when the output depends on information that exists only when the request arrives or that changes faster than you can rebuild:

  • Per-user content: a shelf, a cart or an account page that reads a session cookie.

  • Per-request context: the Accept-Language or geolocation headers, the query string of a search page, an Authorization header.

  • Data that must be fresh on every view: stock levels, prices, a live score.

Prefer prerendering when the same HTML is right for everyone; it is cheaper, can be served from a CDN and has no server work on the hot path. The practical modern answer is rarely "SSR for the whole page": put the personalised or fast-changing part under a <Suspense> boundary so the rest of the page can be served immediately (see the Streaming and Suspense page).

The Request-time APIs and Why They Are Async

In Next.js 14 cookies(), headers() and draftMode() returned their values synchronously, and params and searchParams were plain objects. In Next.js 15 they became promises (cookies, headers and draftMode are async functions; params and searchParams are Promise props), and in Next.js 16 the temporary synchronous access was removed. The reason is architectural: a promise lets the renderer start work that does not need the request (the layout, the static markup, a cached query) and only wait where the request is actually needed. A synchronous cookies() call would have forced the whole route to wait for the request before rendering anything. The same mechanism is what lets Cache Components prerender a static shell and stream the dynamic holes.

Table 3. The Request-time APIs and how to read them in a Server Component

Read-only; the standard Web Headers object.

await connection()

Source: cookies, headers, page: searchParams, draftMode, connection and io

connection() and io() exist for output that varies without reading any request data. Without them, a page that calls new Date() is rendered once at build time and the timestamp is frozen into the HTML.

A page that must differ on every request (previous model)
// app/ssr/clock/page.tsx
import { connection } from "next/server";

export default async function ClockPage() {
  await connection(); // prerendering stops here; the next lines run per request
  const now = new Date().toISOString();
  const token = Math.random().toString(36).slice(2, 8);
  return (
    <p>
      Rendered at {now} (render id {token})
    </p>
  );
}

Two requests a few milliseconds apart returned different timestamps and render ids, and the route is ƒ in the build table. Source: connection

Worked Example: the Bookshelf "My Shelf" Page

The Bookshelf keeps each reader’s shelf (the books they saved) in a shelf cookie, a comma separated list of book ids. The "My shelf" page must show that reader’s books, in the reader’s language, sorted by a query parameter. All three inputs exist only per request, so the page is server-rendered. The catalogue comes from lib/books.ts (marked server-only, from the earlier pages).

app/ssr/shelf/page.tsx (previous model)
import { cookies, headers } from "next/headers";
import { listBooks } from "@/lib/books";

export default async function ShelfPage({ searchParams }: PageProps<"/ssr/shelf">) {
  const { sort } = await searchParams; // Request-time API (async since 15)
  const jar = await cookies(); // Request-time API
  const hdrs = await headers(); // Request-time API

  const language = hdrs.get("accept-language")?.slice(0, 2) ?? "en";
  const ids = (jar.get("shelf")?.value ?? "").split(",").filter(Boolean);
  const books = (await listBooks()).filter((b) => ids.includes(b.id));
  if (sort === "title") books.sort((a, b) => a.title.localeCompare(b.title));

  return (
    <main lang={language}>
      <h1>My shelf ({books.length})</h1>
      <ul>
        {books.map((b) => (
          <li key={b.id}>{b.title}</li>
        ))}
      </ul>
    </main>
  );
}

PageProps<"/ssr/shelf"> is the globally available typed helper that Next.js generates for the route (its searchParams is Promise<Record<string, string | string[] | undefined>>). Source: page and cookies

Run against next start:

Without the cookie the same URL returned My shelf (0). Two things are worth reading in that response. First, Next.js itself sets Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate on a dynamically rendered page, so no shared cache will keep one reader’s shelf for another. Second, the Vary header lists the request headers that distinguish an HTML request from an RSC request for the same URL, which matters when a CDN sits in front.

Dynamic Rendering in Both Caching Models

The same page needs a different shape when cacheComponents: true is on. The previous model renders the whole route per request as soon as one component reads request data. Cache Components inverts the default: everything is dynamic unless cached, Next.js prerenders a static shell, and it insists that request data is read inside a <Suspense> boundary so that the shell can be sent without waiting for it.

Here is the same shelf under Cache Components. The page itself is synchronous and renders the heading as part of the static shell; the data-reading component sits under <Suspense>, and it receives the searchParams promise without awaiting it.

app/ssr/shelf/page.tsx (Cache Components)
import { Suspense } from "react";
import { cookies, headers } from "next/headers";
import { listBooks } from "@/lib/books";

export default function ShelfPage({ searchParams }: PageProps<"/ssr/shelf">) {
  return (
    <main>
      <h1>My shelf</h1> {/* part of the static shell */}
      <Suspense fallback={<p>Loading your shelf...</p>}>
        <Shelf searchParams={searchParams} />
      </Suspense>
    </main>
  );
}

async function Shelf({ searchParams }: { searchParams: PageProps<"/ssr/shelf">["searchParams"] }) {
  const { sort } = await searchParams; // runtime data: only this subtree is dynamic
  const jar = await cookies();
  const language = (await headers()).get("accept-language")?.slice(0, 2) ?? "en";
  const ids = (jar.get("shelf")?.value ?? "").split(",").filter(Boolean);
  const books = (await listBooks()).filter((b) => ids.includes(b.id));
  if (sort === "title") books.sort((a, b) => a.title.localeCompare(b.title));
  return (
    <ul lang={language}>
      {books.map((b) => (
        <li key={b.id}>{b.title}</li>
      ))}
    </ul>
  );
}

Source: Caching and cacheComponents

If you read the request data outside <Suspense>, the build stops. Removing the boundary from the after() example below produced exactly this message:

The Cache Components build error
Error: Route "/ssr/after": Next.js encountered uncached or runtime data during prerendering.
`fetch(...)`, `cookies()`, `headers()`, `params`, `searchParams`, or `connection()` accessed outside of `<Suspense>` prevents the route from being prerendered, blocking the page load and leading to a slower user experience.
Ways to fix this:
  - [stream] Provide a placeholder with `<Suspense fallback={...}>` around the data access
  - [cache] For uncached data (`fetch`, database calls): cache the access with `"use cache"` (does not apply to `connection()`)
  - [block] Set `export const instant = false` to allow a blocking route
Learn more: https://nextjs.org/docs/messages/blocking-prerender-dynamic

The Response: HTML plus the RSC Payload

A server-rendered App Router response is one document that contains two encodings of the same render. React renders the Server Component tree on the server into the RSC payload (a compact, line-based description of the React tree: elements, text, and references to Client Components with their chunk files). From that, React renders the HTML, and Next.js appends the payload to the document in <script> tags that call self.__next_f.push(…​). The browser paints the HTML immediately, then React downloads the Client Component code, reads the inline payload and hydrates the page, attaching event handlers to the existing markup instead of rebuilding it.

Client Components are server-rendered too

A 'use client' component is not skipped on the server. On the first load the server renders it to HTML like everything else (that is the "SSR" in "SSR and hydrate"), and the browser then hydrates it. Only on later navigations is it rendered purely on the client. The shelf can hand a server-read value to a Client Component as a serialisable prop:

A Client Component whose first render happens on the server
// app/ssr/client/page.tsx (Server Component)
import { cookies } from "next/headers";
import { Counter } from "./counter";

export default async function Page() {
  const jar = await cookies();
  return <Counter initial={Number(jar.get("count")?.value ?? 0)} />;
}

// app/ssr/client/counter.tsx
"use client";

import { useState } from "react";

export function Counter({ initial }: { initial: number }) {
  const [count, setCount] = useState(initial);
  return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}

With cookie: count=5 the HTML already contained <button>Count: <!-- -→5<!-- -→</button> before any JavaScript ran. Because the same component runs on the server and then again during hydration, its first render must produce the same markup in both places; branching on typeof window or on Date.now() during render makes the two differ and causes a hydration mismatch (see the pitfalls). Source: Server and Client Components and hydrateRoot

React’s Streaming APIs, and Node Streams in 16.3

Underneath, Next.js uses React’s server rendering functions, which stream: React emits the HTML for everything that is ready, leaves a placeholder for each suspended <Suspense> boundary, and sends the missing HTML later together with a tiny inline script that swaps it in. React ships two entry points for this:

  • renderToPipeableStream(reactNode, options) for Node.js, which returns { pipe, abort } and calls onShellReady, onAllReady, onShellError and onError as the render progresses.

  • renderToReadableStream(reactNode, options) for runtimes with Web Streams (Edge, Deno, Bun), which returns a promise of a ReadableStream.

You do not call either one in an App Router application; Next.js does. They matter because they explain the behaviour you observe: a shell that arrives first, chunks that arrive later, and a status code that cannot change after the first byte. This script (outside Next.js, using only react and react-dom/server) makes it visible by rendering a page whose Reviews component suspends for 200 ms:

Both APIs, side by side (run with node streams.mjs)
import { Writable } from "node:stream";
import { createElement as h, Suspense } from "react";
import { renderToPipeableStream, renderToReadableStream } from "react-dom/server";

// A component that suspends for 200 ms, like a Server Component awaiting data.
function makeApp() {
  let state = "new";
  let value;
  const promise = new Promise((r) => setTimeout(r, 200)).then(() => {
    state = "done";
    value = "3 reviews";
  });
  function Reviews() {
    if (state !== "done") throw promise;
    return h("p", null, value);
  }
  return h(
    "main",
    null,
    h("h1", null, "Dune"),

The status code is only honest when it is decided before streaming starts. Cache-Control on dynamic pages. Next.js sends Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate for a dynamically rendered page, which is the safe default. You can override it with the headers() config, and the override wins; verified:

Overriding Cache-Control for an anonymous, non-personalised path
// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  async headers() {
    return [
      {
        source: "/ssr/books/:id",
        headers: [{ key: "Cache-Control", value: "public, s-maxage=10, stale-while-revalidate=59" }],
      },
    ];
  },
};

export default nextConfig;

/ssr/books/1 then answered Cache-Control: public, s-maxage=10, stale-while-revalidate=59, while /ssr/shelf kept the private default. Only do this for output that is identical for every visitor; never for a page that reads cookies. For pages that are really "the same HTML for everyone, refreshed often", prefer prerendering with revalidation (see the Static Site Generation and Incremental Static Regeneration pages) over hand-written s-maxage. Source: headers

Work After the Response: after()

Logging, analytics and cache warming should not delay the HTML. after() from next/server schedules a callback that runs after the response (or prerender) has finished. It is stable since 15.1 (unstable_after in 15.0 RC), works in Server Components (including generateMetadata), Server Functions, Route Handlers and Proxy, and runs even if the response failed, or notFound() or redirect() was called. It is not a Request-time API: calling it does not make a route dynamic.

The one rule that catches people: in a Server Component, request data cannot be read inside the callback (Next.js must know which part of the tree reads request data), so read it first and let the callback close over the values.

after() in a page (previous model)
import { after } from "next/server";
import { headers } from "next/headers";

export default async function AfterPage() {
  // Read request data BEFORE after(): Request-time APIs are not allowed inside its callback here.
  const userAgent = (await headers()).get("user-agent") ?? "unknown";
  const started = Date.now();

  after(() => {
    // Runs after the response has been sent; does not delay it.
    console.log(`[after] page rendered for ${userAgent} in ${Date.now() - started} ms`);
  });

  return <p>Thanks for visiting</p>;
}

curl -A curl-test /ssr/after returned 200 and the server log then printed [after] page rendered for curl-test in 1 ms. Under Cache Components the headers() read moves into a component under <Suspense> (otherwise the build fails with the error shown earlier):

after() under Cache Components
import { Suspense } from "react";
import { after } from "next/server";
import { headers } from "next/headers";

export default function AfterPage() {
  return (
    <Suspense fallback={<p>...</p>}>
      <Visit />
    </Suspense>
  );
}

async function Visit() {
  const userAgent = (await headers()).get("user-agent") ?? "unknown"; // read before after()
  after(() => {
    console.log(`[after] visit by ${userAgent}`);
  });
  return <p>Thanks for visiting</p>;
}

The log printed [after] visit by cc-test. The callback runs for the platform’s default or configured maximum duration (maxDuration route segment config); on a self-hosted Node.js server, shut down with SIGINT or SIGTERM and give the process a drain period so pending after() work finishes. after is not available with a static export. Source: after and Self-hosting: after

Draft Mode

Draft Mode lets an editor see unpublished content on routes that are otherwise prerendered. A Route Handler enables it and a page reads it:

Enabling and reading Draft Mode
// app/ssr/draft/enable/route.ts
import { draftMode } from "next/headers";

export async function GET() {
  const draft = await draftMode();
  draft.enable(); // sets the __prerender_bypass cookie

}

// app/ssr/draft/page.tsx
import { draftMode } from "next/headers";

The Pages Router: getServerSideProps Side by Side

In the Pages Router a page opts into SSR by exporting an async function named getServerSideProps. Next.js calls it on the server for every request, passes its returned props to the page component, renders the page to HTML, and serialises the props into a NEXT_DATA JSON block so the browser can hydrate. The page below is the Pages Router version of the shelf, in pages/legacy/shelf.tsx (the Bookshelf scratch app had no pages/ directory, so one was added; the two routers coexist in one project as long as no URL is claimed by both).

pages/legacy/shelf.tsx (Pages Router)
import type { GetServerSideProps, InferGetServerSidePropsType } from "next";

type Props = { titles: string[]; language: string };

const catalogue: Record<string, string> = { "1": "Dune", "2": "Neuromancer", "3": "Solaris" };

export const getServerSideProps = (async ({ req, query }) => {
  const ids = (req.cookies.shelf ?? "").split(",").filter(Boolean); // cookies are parsed for you
  const language = req.headers["accept-language"]?.slice(0, 2) ?? "en";
  const titles = ids.map((id) => catalogue[id]).filter(Boolean);
  if (query.sort === "title") titles.sort();
  return { props: { titles, language } };
}) satisfies GetServerSideProps<Props>;

export default function Page({ titles, language }: InferGetServerSidePropsType<typeof getServerSideProps>) {
  return (
    <main lang={language}>
      <h1>My shelf ({titles.length})</h1>
      <ul>
        {titles.map((t) => (
          <li key={t}>{t}</li>
        ))}
      </ul>
    </main>
  );
}

curl -si -H 'cookie: shelf=3,1' '/legacy/shelf?sort=title' returned 200, the same private Cache-Control, and <main lang="en"><h1>My shelf (2)</h1><ul><li>Dune</li><li>Solaris</li></ul></main>. Source: getServerSideProps

SSR Cost and Scaling

SSR moves rendering from build time to request time, so the cost scales with traffic instead of with deployments. Three effects matter.

  • Latency on the critical path. The browser waits for the server to render before it receives the first byte of HTML (time to first byte, TTFB). A slow query in an un-boundaried page delays everything. Streaming shortens this: the shell leaves as soon as it is ready.

  • CPU and memory per request. Rendering React, serialising the RSC payload and running your data layer is CPU work on a Node.js process. Throughput is bounded by cores, and a slow dependency holds a request open and ties up memory.

  • Hosting requirements. A static export needs only a file server; SSR needs a running Node.js server (or an adapter for a platform that provides one), and after() and streaming need the platform to support them.

Table 9. Levers for making SSR cheaper
Lever How it helps

Prerender what you can

A route (or the shell of one) that reads no request data costs no server work per request. With Cache Components the shell is static and only the holes render.

Cache the data, not the page

"use cache"/cacheLife (Cache Components) or fetch caching and unstable_cache (previous model) avoid repeating the same query for different users.

Push request-time access down the tree

Read cookies() or searchParams in the smallest component, under <Suspense>, so the rest is static or streams early.

Avoid waterfalls

Start independent fetches together (Promise.all) instead of awaiting one after another, otherwise latency is the sum.

Use a CDN for public SSR

Only for output identical for every visitor, with an explicit s-maxage and stale-while-revalidate; prerendering with revalidation is usually simpler.

Move non-essential work to after()

Logging and analytics stop contributing to response time.

Scale out, and keep instances stateless

Run several Node.js processes or containers behind a load balancer; do not keep per-user state in process memory; share the cache handler if you run several instances.

Make sure streaming survives the proxy

Disable buffering in nginx (X-Accel-Buffering: no) and use a load balancer that passes chunked responses; otherwise the user waits for the full render and the TTFB advantage disappears.

Upgrade

16.3 moves App Router SSR to native Node.js streams, which the team measured at up to about 22 percent more requests handled under load.

Source: Self-hosting: streaming and Suspense, Caching and Next.js 16.3

No number on this page should be read as a capacity plan. Measure your own routes (a load test against next start with realistic data and cookies) before deciding between "SSR the page", "stream the page" and "prerender the page".

An extra network hop, a second render and an extra cold path.

Assuming new Date() runs per request

Starting next start with a different cacheComponents setting than the build
