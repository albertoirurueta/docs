Introduction & Architecture

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Next.js 16.3 (16.3.8 was the latest release on 2026-10-03, when every fact and example below was checked, and the official documentation reported @doc-version 16.3.8), React 19.3, Node.js 20.9 or later and TypeScript 5.1 or later. It describes the App Router (the app/ directory) as the primary model and compares it throughout with the Pages Router (the pages/ directory). Where caching matters it names the previous model (the defaults of Next.js 15 and 16 with cacheComponents off) and the Cache Components model (cacheComponents: true), because Cache Components is still opt-in. The examples were built and run on Next.js 16.3.8 with Node.js 24 in a scratch project; each one is followed by the official page it derives from. The rest of the section builds Bookshelf — a catalogue of books, authors and reviews, the same scenario used in the FastAPI, NestJS and Django sections of this site — one concept at a time.

What a React Framework Adds to React

React is a library for describing user interfaces as a tree of components. It deliberately stops there: it has no router, no way to get a page to the browser before its JavaScript has run, no build pipeline and no opinion about where data comes from. The React documentation says so in its page on building a React app from scratch: after you pick a build tool you still have to assemble routing, data fetching, code splitting and performance work yourself. It therefore recommends starting with a framework, and lists Next.js (App Router) first among the full-stack frameworks that "take advantage of React’s architecture".

The official documentation defines Next.js as "a React framework for building full-stack web applications": you write components with React, and Next.js supplies the features and optimizations around them and configures the bundler and compiler for you.

Source: Next.js documentation home

The smallest possible App Router application is a root layout and one page. Both are Server Components by default: they run on the server, and only their rendered output reaches the browser.

// app/layout.tsx
import type { Metadata } from "next";

export const metadata: Metadata = { title: "Bookshelf" };

export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  );
}
// app/page.tsx
import Link from "next/link";
import { listBooks } from "@/lib/books";
import { LikeButton } from "./books/like-button";

export default async function Home() {
  const books = await listBooks(); // runs on the server; never shipped to the browser
  return (
    <main>
      <h1>Bookshelf</h1>
      <p>{books.length} books on the shelf.</p>
      <LikeButton />
      <Link href="/books">Browse the catalogue</Link>
    </main>
  );
}

Source: Layouts and Pages

The page import`s a Client Component, which is the only part that needs JavaScript in the browser. It opts in with the ’use client' directive.

// app/books/like-button.tsx

import { useState } from "react";

  const [likes, setLikes] = useState(0);
  return <button onClick={() => setLikes(likes + 1)}>Likes: {likes}</button>;
}

Two things in these examples are React features rather than Next.js features: Server Components and Suspense. The React documentation says so, and adds that adopting them at the framework level takes bundler integration, which is why a framework is the supported way to use them. Next.js is maintained by Vercel and runs on any host that supports Node.js or Docker, and it can also produce a static export that needs no server.

For the React concepts used here — components, props, Hooks, Suspense and Actions — see the React Reference on this site. The React server rendering page covers the underlying react-dom/server APIs that Next.js drives for you.

App Router and Pages Router

Next.js has two routers, and the official documentation describes them in one sentence each: the App Router is "the newer router that supports new React features like Server Components", and the Pages Router is "the original router, still supported and being improved". Both ship in the same next package, and one project can use both.

The two routers answer the same questions with different primitives. The Pages Router decides server or static rendering with a function exported from the page file, and the page component receives props from it.

// pages/catalogue.tsx  (Pages Router)
import type { GetServerSideProps } from "next";
import { listBooks, type Book } from "@/lib/books-data";

type Props = { books: Book[] };

export const getServerSideProps: GetServerSideProps<Props> = async ({
  query,
}) => {
  const q = typeof query.q === "string" ? query.q : "";
  return { props: { books: await listBooks(q) } };
};

export default function Catalogue({ books }: Props) {
  return (
    <ul>
      {books.map((b) => (
        <li key={b.id}>
          {b.title} by {b.author}
        </li>
      ))}
    </ul>
  );
}

Source: getServerSideProps (Pages Router)

The App Router version is an async Server Component that reads the same data directly. Since Next.js 15 the searchParams prop is a Promise and must be awaited; reading it makes the route dynamic, and it is wrapped in <Suspense> so the page also builds under Cache Components (more on that in Rendering Philosophy).

// app/books/page.tsx  (App Router)
import { Suspense } from "react";
import { listBooks } from "@/lib/books";

async function Results({
  searchParams,
}: {
  searchParams: Promise<{ q?: string }>;
}) {
  const { q } = await searchParams;
  const books = await listBooks(q);
  return (
    <ul>
      {books.map((b) => (
        <li key={b.id}>
          {b.title} by {b.author}
        </li>
      ))}
    </ul>
  );
}

export default function BooksPage({
  searchParams,
}: {
  searchParams: Promise<{ q?: string }>;
}) {
  return (
    <main>
      <h1>Catalogue</h1>
      <Suspense fallback={<p>Loading books...</p>}>
        <Results searchParams={searchParams} />
      </Suspense>
    </main>
  );
}

Source: page.js

Which router should you choose?

The decision rarely requires deliberation:

  • New project: App Router. create-next-app marks the App Router as "(recommended)" in its prompts and includes it in its recommended defaults, and every feature added in the last several major versions — Server Components, Cache Components, Server Functions, proxy.ts integration, Instant Navigations — targets it.

  • Existing Pages Router application that works: keep it, and adopt the App Router when a feature justifies it. The Pages Router is described by the official documentation as "still supported and being improved", and Next.js 16 still ships it. There is no deadline in the support policy forcing a migration.

  • Existing application that needs Server Components, nested layouts that keep their state, streaming or Server Functions: migrate page by page.

Incremental adoption

The official migration guide says the app directory "is intentionally designed to work simultaneously with the pages directory to allow for incremental page-by-page migration". The steps are: update to Next.js 13.4 or later, create app/, add a root layout (which replaces _app and _document), then move pages one at a time, migrating next/head to the Metadata API, routing hooks to next/navigation, and data functions to Server Components. The scratch project above is exactly such a hybrid: app/ serves /books and pages/ serves /catalogue, and the build lists them in two tables.

Three rules govern the coexistence:

  • A URL can belong to only one router. If both an app/books/page.tsx and a pages/books/index.tsx exist, the build fails:

    Error: App Router and Pages Router both match path: /books
Next.js does not support having both App Router and Pages Router routes matching the same path.
Please remove one of the conflicting routes.

  • Moving between routes served by different routers is a hard navigation, and automatic prefetching with next/link does not cross routers.

  • Components that must work in both routers can import useRouter from next/compat/router, which does not throw when the Pages Router is not mounted and returns null instead, until the migration is finished.

Source: Migrating from Pages to the App Router

The same next package serves both routers, so the codemods and next upgrade described under Release Cadence and Support Policy work on hybrid projects.

The Compiler Pipeline: SWC and Turbopack

Two Rust components turn your source files into what the server and the browser run.

  • SWC, the Next.js Compiler, transforms individual files: it strips TypeScript types, compiles JSX, handles the 'use client' and 'use server' directives, applies the options under compiler in next.config.ts and minifies the production output. It replaced Babel for individual files and Terser for minification and has been enabled by default since Next.js 12.

  • Turbopack, an incremental bundler, joins the transformed modules into chunks. It keeps one unified graph for every output environment (server and client) instead of stitching the results of separate compilers, bundles in development as well (rather than serving native ES modules), caches results down to the function level and persists them to disk (file-system caching was stable for next dev in 16.1), and only bundles what the dev server is asked for. It is the default bundler for next dev and next build since Next.js 16.

Source: Turbopack

The --webpack flag is the way to keep a project that still has a custom webpack configuration working: since Next.js 16, next dev and next build use Turbopack by default, and next build fails if it finds a custom webpack configuration unless you choose a bundler explicitly with --turbopack or --webpack. Platforms without native Turbopack bindings (for example FreeBSD) fall back to WebAssembly bindings that do not support Turbopack and need --webpack. Turbopack picks up an existing Babel configuration file automatically (new in 16); SWC still does Next.js’s internal transforms, whereas the webpack bundler disables SWC when a Babel configuration file is present.

SWC options live under the compiler key. This configuration removes console.* calls from application code in production builds but keeps console.error; it was loaded by the scratch project’s build without warnings.

// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  compiler: {
    // Strip console.* calls from application code, except console.error.
    removeConsole: { exclude: ["error"] },
  },
};

export default nextConfig;

Source: Next.js Compiler

The transform works on statements. In a client component with console.log("ping-debug-marker") and console.error("ping-error-marker") as plain statements, searching the client chunks in .next/static after a build on 16.3.8 found both markers without the option, and only the console.error marker with removeConsole. A console.log written as the shorthand body of an arrow function survived the same build, so do not rely on the transform to strip every possible call.

Other built-in transforms in the same page cover styled-components, Emotion, Relay, Jest (next/jest), removing React properties and legacy decorators. The SWC minifier became the default in Next.js 13 and, from 15, cannot be customised. The React Compiler is a separate, opt-in transform (reactCompiler: true, a top-level option since 16, which also needs babel-plugin-react-compiler); Next.js applies it only to files that contain JSX or Hooks, and builds can be slower because it runs through a Babel plugin. The 16.3 release also lists a Rust-based React Compiler as experimental (turbopackRustReactCompiler). The build writes its results to .next/: server code under .next/server and browser chunks under .next/static.

Source: reactCompiler

The two bundlers are both supported by the Pages Router and the App Router. The configuration page of this section (configuration, TypeScript and environment variables) covers the turbopack options in detail.

Server, Client and Edge Runtimes

An App Router page is not "a server file" or "a client file": the same source tree runs in several places, and knowing which place matters for every API you call.

Table 4. Where each kind of code runs
Code Where it runs Notes

Server Components (default)

On the Node.js server, at build time for static output and at request time for dynamic output.

Their rendered result is serialized into the RSC payload; their code is not sent to the browser.

Client Components ('use client')

Prerendered to HTML on the server, then hydrated in the browser; they re-run in the browser.

They are the only components that can use state, effects and browser APIs.

Route Handlers (route.ts) and Pages Router API routes

Node.js server, per request.

Web Request/Response API in the App Router.

Server Functions ('use server')

Node.js server, called from the client as POST requests to the route where they are used.

Always verify authentication and authorization inside the function.

Proxy (proxy.ts)

Node.js runtime, before routing, for every matching request.

The runtime segment option is not available in Proxy; setting it throws an error.

Edge Runtime

A restricted Web-API runtime. Deprecated.

export const runtime = 'edge' still works but warns; the Node.js runtime is the default.

Source: Edge Runtime and proxy.js

Next.js documents two server runtimes: the Node.js runtime (the default, used to render the application) and the Edge Runtime, a smaller set of Web APIs. In Next.js 16 the Edge Runtime is deprecated: the runtime route segment option accepts 'nodejs' (default) and 'edge' (deprecated), the build prints a warning when a route exports runtime = 'edge', and the documented fix is to delete the export. The Edge Runtime does not support all Node.js APIs and does not support Incremental Static Regeneration. Proxy itself moved to the Node.js runtime in 16 (Node.js Middleware had been stable since 15.5), so the old reason to reach for the edge — running Middleware close to the user — is now a hosting decision rather than a Next.js runtime choice.

// app/edge-demo/route.ts  (deprecated; shown only to reproduce the warning)
export const runtime = "edge";

export function GET() {
  return new Response("hi");
}
⚠ The Edge Runtime is deprecated. You can use the "nodejs" runtime instead. Learn more: https://nextjs.org/docs/messages/edge-runtime-deprecated
⚠ Using edge runtime on a page currently disables static generation for that page

Source: runtime

The official pages are not fully consistent here. The Edge Runtime reference still says the Edge Runtime is "used in Proxy", while the Proxy reference says Proxy defaults to the Node.js runtime and rejects the runtime option. Follow the Proxy page, which matches the 16.0 release. Everything that runs "at the edge" in front of a self-hosted application is therefore a CDN or platform feature, not a separate Next.js runtime.

Source: Edge Runtime

The client side of the boundary is protected from server-only code. A module that must never reach the browser (it holds database credentials, for example) imports the server-only package; importing it from a Client Component fails the build instead of leaking the code.

One Request, End to End

The figure shows what happens to a request in a self-hosted application. A CDN (or any cache in front of Next.js) can answer prerendered HTML and static assets itself. Everything else reaches the Proxy, then the Next.js server, which matches a route and renders it with React.

The Proxy is ordinary code. This one, from the scratch project, adds a header so that the effect is visible with curl:

// proxy.ts (project root, next to app/ and pages/)
import { NextResponse, type NextRequest } from "next/server";

export function proxy(request: NextRequest) {
  const response = NextResponse.next();
  response.headers.set("x-bookshelf-path", request.nextUrl.pathname);
  return response;
}

export const config = { matcher: ["/((?!_next).*)"] };

Source: proxy.js

The first visit to a page returns HTML. In it, the Server Components have already been rendered into markup (the <main> element below) and the same result is repeated inside self.__next_f.push(…​) scripts as the React Server Component (RSC) payload. The payload also contains a reference to the Client Component’s chunk ("$Ld" points at the LikeButton entry), which tells the browser what to hydrate.

$ curl -si localhost:3201/ | head -4
HTTP/1.1 200 OK
x-bookshelf-path: /
Vary: rsc, next-router-state-tree, next-router-prefetch, next-router-segment-prefetch, Accept-Encoding
x-nextjs-cache: HIT

$ curl -s localhost:3201/ | grep -o '<main>.*</main>'
<main><h1>Bookshelf</h1><p>3<!-- --> books on the shelf.</p><button>Likes: <!-- -->0</button><a href="/books">Browse the catalogue</a></main>

The payload lines that matter, decoded from those scripts:

d:I[81706,["/_next/static/chunks/3fntmmi971322.js","/_next/static/chunks/0t-ncsnp7ysxs.js"],"LikeButton"]
4:["$","main",null,{"children":[["$","h1",null,{"children":"Bookshelf"}],["$","p",null,{"children":[3," books on the shelf."]}],["$","$Ld",null,{}],["$","$Le",null,{"href":"/books","children":"Browse the catalogue"}]]}]

The x-bookshelf-path header is present even though / is prerendered and served from the cache (x-nextjs-cache: HIT), which shows that the Proxy runs ahead of the cache lookup. The Vary header lists the request headers that select between the HTML and the RSC payload, and the Cache-Control: s-maxage=31536000 header that Next.js sets on a static page is what lets a CDN keep it; on-demand revalidation does not purge a CDN by itself.

Source: CDN Caching

When the user then clicks a link, the browser does not request a document. It asks for the payload alone, using the RSC: 1 request header, and React reconciles it with the tree already on screen. Requesting the payload by hand (the first response is a redirect to a URL with a cache-busting _rsc query parameter, so curl needs -L):

$ curl -sL -i -H 'RSC: 1' 'http://localhost:3201/books?q=sol' | grep -i -E '^HTTP|content-type'
HTTP/1.1 307 Temporary Redirect
HTTP/1.1 200 OK
Content-Type: text/x-component

$ curl -sL -H 'RSC: 1' 'http://localhost:3201/books?q=sol' | grep Solaris
5:["$","ul",null,{"children":[["$","li","2",{"children":["Solaris"," by ","Stanislaw Lem"]}]]}]

Source: Server and Client Components

The documentation defines the RSC payload as "a compact, serialized representation of the rendered React Server Components tree", used by the client to update the DOM, and summarizes the first load in three steps: HTML for a fast non-interactive preview, the RSC payload to reconcile the Client and Server Component trees, and JavaScript to hydrate the Client Components. Hydration is React attaching event handlers to server-rendered HTML; see hydrateRoot. The Pages Router follows a similar flow without RSC payloads: it sends HTML plus the page’s props as JSON (NEXT_DATA) and hydrates the whole page. Server Components themselves are specified by React: Server Components.

Rendering Philosophy

Most web frameworks draw the line between static and dynamic at the route: a page is either prerendered at build time or rendered per request. The official Rendering Philosophy guide states that Next.js draws it at the component: "the boundary between static and dynamic is at the component level, not the route level". One page can have a static shell that loads instantly and dynamic sections that stream in when they resolve, a cached function can live inside a dynamic route, and a static page can be updated without a redeploy. Partial Prerendering, Cache Components (the 'use cache' directive) and on-demand revalidation are described as expressions of this model rather than as separate features.

Table 5. Where frameworks draw the static and dynamic boundary
Boundary How it works Trade-off

Build-time prerendering

Every page is generated at build time and served from a CDN or file server; dynamic content is fetched on the client after load.

Simplest to deploy; every content change needs a rebuild and redeploy.

Route-level

Each route is static or dynamic. Static files go to a CDN, dynamic routes to a server.

Easy to reason about, but all-or-nothing per route: one live element makes the whole page dynamic or forces a client fetch.

Component-level (Next.js)

Static and dynamic content share one streaming response; cached functions revalidate independently.

Moves complexity from application code into the hosting platform.

Source: Rendering Philosophy

The guide lists the infrastructure consequences of that choice: streaming (so a static shell and dynamic parts can share a response), cache coordination across instances (because revalidateTag() and revalidatePath() can invalidate any cached content), consistency between the HTML and the RSC payload when they are regenerated, and, for the best Partial Prerendering performance, a platform that can store the static shell separately and resume dynamic rendering. A single Node.js process handles every feature correctly; additional infrastructure improves performance. The documentation calls the first level functional fidelity and the second performance fidelity.

Both caching models are in use today, and the same page behaves differently under each. This Server Component reads a cookie, which makes it request-time data, but only a small part of the page depends on it:

// app/shelf/page.tsx
import { Suspense } from "react";
import { cookies } from "next/headers";

async function Greeting() {
  const name = (await cookies()).get("reader")?.value ?? "guest";
  return <p>Welcome back, {name}.</p>;
}

export default function Shelf() {
  return (
    <main>
      <h1>My shelf</h1>
      <Suspense fallback={<p>Loading your profile...</p>}>
        <Greeting />
      </Suspense>
    </main>
  );
}

Source: cookies

Previous model (cacheComponents unset or false): the route is dynamic as a whole. It is rendered per request, and the build marks it ƒ.

Cache Components (cacheComponents: true in next.config.ts): the build prerenders the shell, up to the Suspense boundary, and streams the rest per request. The build marks it ◐ (Partial Prerender).

// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  cacheComponents: true,
};

export default nextConfig;
$ CACHE_COMPONENTS=1 npx next build        # Cache Components
Route (app)
┌ ○ /
├ ○ /_not-found
├ ƒ /api/books
├ ◐ /books
└ ◐ /shelf
...
◐  (Partial Prerender)  prerendered as static HTML with dynamic server-streamed content

$ npx next build                           # previous model
Route (app)
┌ ○ /
├ ○ /_not-found
├ ƒ /api/books
├ ƒ /books
└ ƒ /shelf

Source: Caching

The scratch project switches the setting with an environment variable read in next.config.ts; the config page of this section shows the plain form. Under Cache Components the response shows the split: the shell is sent immediately with a fallback, and x-nextjs-postponed: 1 marks a prerendered response whose remaining work resumes per request.

$ curl -s -H 'Cookie: reader=ana' localhost:3201/shelf | grep -o '<main>.*</main>'
<main><h1>My shelf</h1><!--$?--><template id="B:0"></template><p>Loading your profile...</p><!--/$--></main>

The same project, built as Cache Components, refuses a page that reads request data outside a Suspense boundary. Before the Suspense wrapper was added to /books, the build failed with:

Error: Route "/books": Next.js encountered uncached or runtime data during prerendering.

`fetch(...)`, `cookies()`, `headers()`, `params`, `searchParams`, or `connection()` accessed outside of
`<Suspense>` prevents the route from being prerendered, blocking the page load and leading to a slower user
experience.

Ways to fix this:
  - [stream] Provide a placeholder with `<Suspense fallback={...}>` around the data access
  - [cache] For uncached data (`fetch`, database calls): cache the access with `"use cache"` ...
  - [block] Set `export const instant = false` to allow a blocking route

Learn more: https://nextjs.org/docs/messages/blocking-prerender-dynamic

Source: blocking-prerender-dynamic

cacheComponents and partialPrefetching are opt-in in Next.js 16.3; the release notes state that these behaviours "will become the default in a future major version", which is why this section teaches both models and labels every example. The caching and rendering pages go through 'use cache', cacheLife, cacheTag and updateTag.

Next.js ships continuously. New builds are published to the canary channel daily; they are tested internally before being promoted to a stable release, and the documentation does not recommend serving production traffic from canary. On 2026-10-03 the npm dist-tags were:

  ...

Source: Next.js Support Policy

The cadence has three levels:

  • One major version a year, in October: 14 on 2023-10-26, 15 on 2024-10-21, 16 on 2025-10-21.

  • Several minor releases per major: the 16 line has had 16.0 (2025-10-21), 16.1 (2025-12-18), 16.2 (2026-03-18) and 16.3 (2026-08-03), a few months apart, each with a blog post of new features.

  • Frequent patch releases, including security releases (July, August and September 2026 each had one; 16.3.8 on 2026-09-30 was a security release).

The support policy gives each major version a long-term support (LTS) life cycle.

Four notes on reading the table.

  • Remix. The name has moved. React Router’s site describes v7 as the next major version of Remix after v2, and its framework mode continues that React framework. The remix.run site today presents a different, web-API-based toolkit, so when a book or article says "Remix", check which of the two it means.

  • Gatsby. The official site and documentation are online, but the last stable npm release (5.16.1) dates from 2026-02-10. "Maintenance mode" is an inference from that release cadence, not an official statement; weigh it against your own risk tolerance.

  • Vite. A plain Vite SPA is a legitimate choice, not a strawman: Vite is also the build tool behind React Router framework mode and one of the two behind TanStack Start (the other is Rsbuild).

  • Other UI libraries. Nuxt, SvelteKit and Angular SSR solve the same problems with the same vocabulary (SSR, prerendering, hydration), so the concepts of this section transfer.

Choosing Vite for a single-page app does not exclude Next.js: Next.js can be configured to produce the same output. With output: 'export', next build writes a folder of static files. A page that renders only on the client behaves as in any Vite SPA:

// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  output: "export",
};

export default nextConfig;
// app/page.tsx
"use client";

import { useEffect, useState } from "react";

export default function Page() {
  const [books, setBooks] = useState<string[]>([]);
  useEffect(() => {
    fetch("https://api.example.com/books")
      .then((r) => r.json())
      .then((data: { title: string }[]) => setBooks(data.map((b) => b.title)))
      .catch(() => setBooks([]));
  }, []);
  return <ul>{books.map((t) => <li key={t}>{t}</li>)}</ul>;
}

┌ ○ /
└ ○ /_not-found

$ ls out
404.html  _next  _not-found  _not-found.html  index.html  index.txt  ...

Source: Static Exports and SPAs

A static export has no server, so features that need one — the Proxy (the Proxy documentation lists "Static export" as not supported), Route Handlers that read the request, and Server Functions — are unavailable. The advantage of starting in Next.js is that the application can grow server features later without a rewrite; the official guide for moving a Vite application, How to migrate from Vite to Next.js, lists the problems that motivate the move: slow first load, no automatic code splitting, client-server request waterfalls and no per-route loading states. The react.dev note on full-stack frameworks makes the same point from the other side: frameworks do not require a server, and let you "opt-in to using server features on individual routes without rewriting your app".

How the SSR, CSR, SSG and hydration of Next.js relate to the lower-level React APIs, and how Next.js sits in a layered backend and front end architecture, are covered in Layering backend and frontend.

Where the Books Are Outdated

Two books on this topic are in the section’s bibliography: Real-World Next.js (Packt, 2022), which targets Next.js 12 and the Pages Router, and Practical Next.js for E-Commerce (Apress, 2023), which targets Next.js 13.2 and the Pages Router and explicitly skips the App Router. They are good for concepts, and their Next.js versions are no longer supported. Where they touch the material on this page, the current practice differs as follows. On any discrepancy, the official documentation wins.

Table 9. Introduction and architecture topics: the books versus Next.js 16.3
Topic Outdated in the books, current approach

Router

Only the Pages Router is taught. The App Router has been stable since 13.4 and is the default for new projects; the Pages Router remains supported for existing applications.

Compiler and bundler

Custom .babelrc and webpack configuration in next.config.js to extend the build. SWC replaced Babel in 12, and Turbopack is the default for dev and build in 16; a Babel file is picked up automatically, and a custom webpack function now needs --webpack.

Rendering vocabulary

getServerSideProps and getStaticProps as the definition of SSR and SSG. The same outcomes now come from async Server Components, generateStaticParams, caching and revalidation APIs, and a single page can mix them (see the rendering philosophy above).

Request APIs

Synchronous params, query and cookies() usage. Since 15 these are Promises, and synchronous access was removed in 16.

Middleware

middleware.ts, and the idea of running it on a separate edge runtime. 16 renames it proxy.ts, runs it on Node.js, and deprecates the Edge Runtime.

Runtime requirements

Node.js 14 or 16 and React 17 or 18. Next.js 16 requires Node.js 20.9 or later and TypeScript 5.1 or later; the App Router uses the React canary built into Next.js (React 19 features), while the Pages Router uses the React in your package.json.

Support

Versions 12 and 13 are described as current. Both are now unsupported; 16 is Active LTS and 15 is Maintenance LTS.

Comparison with Gatsby, Razzle, Nuxt and Angular Universal

Razzle and Angular Universal are no longer the reference points. Angular’s server rendering is now @angular/ssr and Gatsby’s last npm release is from February 2026; the comparison table above is current.

Common Pitfalls

Table 10. Pitfalls on the architecture level and their fixes
Symptom Cause Fix

Build error "App Router and Pages Router both match path"

app/ and pages/ define the same URL.

Delete or rename one of the two routes.

Build error "Next.js encountered uncached or runtime data during prerendering" under Cache Components

params, searchParams, cookies(), headers(), connection() or an uncached fetch runs outside a Suspense boundary.

Wrap the access in <Suspense>, cache it with 'use cache', or opt the route out with export const instant = false. See blocking-prerender-dynamic.

Build error "You’re importing a module that depends on server-only"

A Client Component, or a Pages Router file, imports a module that imports server-only.

Keep the server-only module out of the client import graph; pass data as props or call a Server Function.

Warning "The Edge Runtime is deprecated"

A route exports runtime = 'edge'.

Remove the export; Node.js is the default. See edge-runtime-deprecated.

middleware.ts still works but is flagged in the build output or docs

Middleware is deprecated in 16.

Run the middleware-to-proxy codemod. See middleware-to-proxy.

next build fails with a custom webpack configuration

Turbopack is the default in 16.

Run next build --webpack, or migrate the customization to Turbopack options.

Full page reload when moving between /catalogue and /books

The two routes belong to different routers, so the navigation is a hard one and is not prefetched.

Finish migrating the related routes, or accept the reload during the transition.

A page reading searchParams is not static

Reading request data opts a route into dynamic rendering (previous model) or into streaming (Cache Components).

Expected; move the dynamic part under Suspense and keep the rest static.
