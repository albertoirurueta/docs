What a React Framework Adds to React

React is a library for describing user interfaces as a tree of components. It deliberately stops there: it has no router, no way to get a page to the browser before its JavaScript has run, no build pipeline and no opinion about where data comes from. The React documentation says so in its page on building a React app from scratch: after you pick a build tool you still have to assemble routing, data fetching, code splitting and performance work yourself. It therefore recommends starting with a framework, and lists Next.js (App Router) first among the full-stack frameworks that "take advantage of React’s architecture".

The official documentation defines Next.js as "a React framework for building full-stack web applications": you write components with React, and Next.js supplies the features and optimizations around them and configures the bundler and compiler for you.

Source: Next.js documentation home

Table 1. What React provides and what Next.js adds
Concern React alone Next.js adds

Routing

Nothing; you bring a router library.

File-system routing: folders and special files (page, layout, route) under app/ or files under pages/ define URLs, nested layouts and dynamic segments.

Rendering location

Client-side rendering by default; react-dom/server is a low-level API.

Server Components rendered on the server, HTML prerendered at build time or per request, streaming with Suspense, and hydration of Client Components.

Data fetching

Components fetch in effects, or you adopt a data library.

async Server Components that read data where it lives, Route Handlers (route.ts) for JSON APIs, Server Functions for mutations, and a caching layer.

Code splitting

Manual lazy and dynamic imports.

Automatic per route, plus a server/client split: Server Components ship no component JavaScript to the browser.

Build and compile

You choose and configure a bundler and compiler.

A Rust compiler (SWC) and bundler (Turbopack) preconfigured for TypeScript, JSX, CSS, code splitting and production minification.

Asset optimization

None.

next/image, next/font, next/script, and prefetching of linked routes.

Request pipeline

None.

A Proxy (proxy.ts) that runs before routing, redirects/rewrites/headers in next.config.ts, and environment-variable handling.

Deployment

Static files from any host.

A Node.js server (next start), Docker, a static export, or an adapter for a hosting platform.

The smallest possible App Router application is a root layout and one page. Both are Server Components by default: they run on the server, and only their rendered output reaches the browser.

// app/layout.tsx
import type { Metadata } from "next";

export const metadata: Metadata = { title: "Bookshelf" };

export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  );
}
// app/page.tsx
import Link from "next/link";
import { listBooks } from "@/lib/books";
import { LikeButton } from "./books/like-button";

export default async function Home() {
  const books = await listBooks(); // runs on the server; never shipped to the browser
  return (
    <main>
      <h1>Bookshelf</h1>
      <p>{books.length} books on the shelf.</p>
      <LikeButton />
      <Link href="/books">Browse the catalogue</Link>
    </main>
  );
}

import { useState } from "react";

}

Two things in these examples are React features rather than Next.js features: Server Components and Suspense. The React documentation says so, and adds that adopting them at the framework level takes bundler integration, which is why a framework is the supported way to use them. Next.js is maintained by Vercel and runs on any host that supports Node.js or Docker, and it can also produce a static export that needs no server.

For the React concepts used here — components, props, Hooks, Suspense and Actions — see the React Reference on this site. The React server rendering page covers the underlying react-dom/server APIs that Next.js drives for you.

App Router and Pages Router

Next.js has two routers, and the official documentation describes them in one sentence each: the App Router is "the newer router that supports new React features like Server Components", and the Pages Router is "the original router, still supported and being improved". Both ship in the same next package, and one project can use both.

Table 2. The two routers side by side
Aspect App Router (app/) Pages Router (pages/)

Introduced and status

Introduced in Next.js 13, marked stable in 13.4 (May 2023). The recommended router for new work.

The original router (Next.js 1 to 12 only had this one). Still supported and maintained.

Component model

React Server Components by default; Client Components opt in with 'use client'.

Which router should you choose?

The decision rarely requires deliberation:

  • New project: App Router. create-next-app marks the App Router as "(recommended)" in its prompts and includes it in its recommended defaults, and every feature added in the last several major versions — Server Components, Cache Components, Server Functions, proxy.ts integration, Instant Navigations — targets it.

  • Existing Pages Router application that works: keep it, and adopt the App Router when a feature justifies it. The Pages Router is described by the official documentation as "still supported and being improved", and Next.js 16 still ships it. There is no deadline in the support policy forcing a migration.

  • Existing application that needs Server Components, nested layouts that keep their state, streaming or Server Functions: migrate page by page.

Incremental adoption

The official migration guide says the app directory "is intentionally designed to work simultaneously with the pages directory to allow for incremental page-by-page migration". The steps are: update to Next.js 13.4 or later, create app/, add a root layout (which replaces _app and _document), then move pages one at a time, migrating next/head to the Metadata API, routing hooks to next/navigation, and data functions to Server Components. The scratch project above is exactly such a hybrid: app/ serves /books and pages/ serves /catalogue, and the build lists them in two tables.

Three rules govern the coexistence:

  • A URL can belong to only one router. If both an app/books/page.tsx and a pages/books/index.tsx exist, the build fails:

    Error: App Router and Pages Router both match path: /books
Next.js does not support having both App Router and Pages Router routes matching the same path.
Please remove one of the conflicting routes.

  • Moving between routes served by different routers is a hard navigation, and automatic prefetching with next/link does not cross routers.

  • Components that must work in both routers can import useRouter from next/compat/router, which does not throw when the Pages Router is not mounted and returns null instead, until the migration is finished.

The Compiler Pipeline: SWC and Turbopack

Two Rust components turn your source files into what the server and the browser run.

  • SWC, the Next.js Compiler, transforms individual files: it strips TypeScript types, compiles JSX, handles the 'use client' and 'use server' directives, applies the options under compiler in next.config.ts and minifies the production output. It replaced Babel for individual files and Terser for minification and has been enabled by default since Next.js 12.

  • Turbopack, an incremental bundler, joins the transformed modules into chunks. It keeps one unified graph for every output environment (server and client) instead of stitching the results of separate compilers, bundles in development as well (rather than serving native ES modules), caches results down to the function level and persists them to disk (file-system caching was stable for next dev in 16.1), and only bundles what the dev server is asked for. It is the default bundler for next dev and next build since Next.js 16.

// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  compiler: {
    // Strip console.* calls from application code, except console.error.
    removeConsole: { exclude: ["error"] },
  },
};

export default nextConfig;

Source: Next.js Compiler

The transform works on statements. Rendering Philosophy

Most web frameworks draw the line between static and dynamic at the route: a page is either prerendered at build time or rendered per request. The official Rendering Philosophy guide states that Next.js draws it at the component: "the boundary between static and dynamic is at the component level, not the route level". One page can have a static shell that loads instantly and dynamic sections that stream in when they resolve, a cached function can live inside a dynamic route, and a static page can be updated without a redeploy. Partial Prerendering, Cache Components (the 'use cache' directive) and on-demand revalidation are described as expressions of this model rather than as separate features.

Table 5. Where frameworks draw the static and dynamic boundary
Boundary How it works Trade-off

Build-time prerendering

Every page is generated at build time and served from a CDN or file server; dynamic content is fetched on the client after load.

Simplest to deploy; every content change needs a rebuild and redeploy.

Route-level

Each route is static or dynamic. Static files go to a CDN, dynamic routes to a server.

Easy to reason about, but all-or-nothing per route: one live element makes the whole page dynamic or forces a client fetch.

Component-level (Next.js)

Static and dynamic content share one streaming response; cached functions revalidate independently.

Moves complexity from application code into the hosting platform.

Source: Rendering Philosophy

The guide lists the infrastructure consequences of that choice: streaming (so a static shell and dynamic parts can share a response), cache coordination across instances (because revalidateTag() and revalidatePath() can invalidate any cached content), consistency between the HTML and the RSC payload when they are regenerated, and, for the best Partial Prerendering performance, a platform that can store the static shell separately and resume dynamic rendering. A single Node.js process handles every feature correctly; additional infrastructure improves performance. The documentation calls the first level functional fidelity and the second performance fidelity.

Both caching models are in use today, and the same page behaves differently under each. This Server Component reads a cookie, which makes it request-time data, but only a small part of the page depends on it:

      <h1>My shelf</h1>

Your team writes Vue, not React.

Your organization standardizes on Angular and TypeScript with dependency injection.

Four notes on reading the table.

  • Remix. The name has moved. React Router’s site describes v7 as the next major version of Remix after v2, and its framework mode continues that React framework. The remix.run site today presents a different, web-API-based toolkit, so when a book or article says "Remix", check which of the two it means.

  • Gatsby. The official site and documentation are online, but the last stable npm release (5.16.1) dates from 2026-02-10. "Maintenance mode" is an inference from that release cadence, not an official statement; weigh it against your own risk tolerance.

  • Vite. A plain Vite SPA is a legitimate choice, not a strawman: Vite is also the build tool behind React Router framework mode and one of the two behind TanStack Start (the other is Rsbuild).

  • Other UI libraries. Nuxt, SvelteKit and Angular SSR solve the same problems with the same vocabulary (SSR, prerendering, hydration), so the concepts of this section transfer.

Choosing Vite for a single-page app does not exclude Next.js: Next.js can be configured to produce the same output. With output: 'export', next build writes a folder of static files. A page that renders only on the client behaves as in any Vite SPA:

// next.config.ts
import type { NextConfig } from "next";

const nextConfig: NextConfig = {
  output: "export",
};

export default nextConfig;
// app/page.tsx
"use client";

import { useEffect, useState } from "react";

export default function Page() {
  const [books, setBooks] = useState<string[]>([]);
  useEffect(() => {
    fetch("https://api.example.com/books")
      .then((r) => r.json())
      .then((data: { title: string }[]) => setBooks(data.map((b) => b.title)))
      .catch(() => setBooks([]));
  }, []);
  return <ul>{books.map((t) => <li key={t}>{t}</li>)}</ul>;
}

Source: Static Exports and SPAs

A static export has no server, so features that need one — the Proxy (the Proxy documentation lists "Static export" as not supported), Route Handlers that read the request, and Server Functions — are unavailable. The advantage of starting in Next.js is that the application can grow server features later without a rewrite; the official guide for moving a Vite application, How to migrate from Vite to Next.js, lists the problems that motivate the move: slow first load, no automatic code splitting, client-server request waterfalls and no per-route loading states. The react.dev note on full-stack frameworks makes the same point from the other side: frameworks do not require a server, and let you "opt-in to using server features on individual routes without rewriting your app".

How the SSR, CSR, SSG and hydration of Next.js relate to the lower-level React APIs, and how Next.js sits in a layered backend and front end architecture, are covered in Layering backend and frontend.

Where the Books Are Outdated

Two books on this topic are in the section’s bibliography: Real-World Next.js (Packt, 2022), which targets Next.js 12 and the Pages Router, and Practical Next.js for E-Commerce (Apress, 2023), which targets Next.js 13.2 and the Pages Router and explicitly skips the App Router. They are good for concepts, and their Next.js versions are no longer supported. Where they touch the material on this page, the current practice differs as follows. On any discrepancy, the official documentation wins.

Table 9. Introduction and architecture topics: the books versus Next.js 16.3
Topic Outdated in the books, current approach

Router

Only the Pages Router is taught. The App Router has been stable since 13.4 and is the default for new projects; the Pages Router remains supported for existing applications.

Compiler and bundler

Custom .babelrc and webpack configuration in next.config.js to extend the build. SWC replaced Babel in 12, and Turbopack is the default for dev and build in 16; a Babel file is picked up automatically, and a custom webpack function now needs --webpack.

Rendering vocabulary

getServerSideProps and getStaticProps as the definition of SSR and SSG. The same outcomes now come from async Server Components, generateStaticParams, caching and revalidation APIs, and a single page can mix them (see the rendering philosophy above).

Request APIs

Synchronous params, query and cookies() usage. Since 15 these are Promises, and synchronous access was removed in 16.

Middleware

middleware.ts, and the idea of running it on a separate edge runtime. 16 renames it proxy.ts, runs it on Node.js, and deprecates the Edge Runtime.

Runtime requirements

Node.js 14 or 16 and React 17 or 18. Next.js 16 requires Node.js 20.9 or later and TypeScript 5.1 or later; the App Router uses the React canary built into Next.js (React 19 features), while the Pages Router uses the React in your package.json.

Support

Versions 12 and 13 are described as current. Both are now unsupported; 16 is Active LTS and 15 is Maintenance LTS.

Razzle and Angular Universal are no longer the reference points. Angular’s server rendering is now @angular/ssr and Gatsby’s last npm release is from February 2026; the comparison table above is current.

Common Pitfalls

Table 10. Pitfalls on the architecture level and their fixes
Symptom Cause Fix

Build error "App Router and Pages Router both match path"

app/ and pages/ define the same URL.

Delete or rename one of the two routes.

Build error "Next.js encountered uncached or runtime data during prerendering" under Cache Components

params, searchParams, cookies(), headers(), connection() or an uncached fetch runs outside a Suspense boundary.

Wrap the access in <Suspense>, cache it with 'use cache', or opt the route out with export const instant = false. See blocking-prerender-dynamic.

Build error "You’re importing a module that depends on server-only"

A Client Component, or a Pages Router file, imports a module that imports server-only.

Keep the server-only module out of the client import graph; pass data as props or call a Server Function.

Warning "The Edge Runtime is deprecated"

A route exports runtime = 'edge'.

Remove the export; Node.js is the default. See edge-runtime-deprecated.

middleware.ts still works but is flagged in the build output or docs

Middleware is deprecated in 16.

Run the middleware-to-proxy codemod. See middleware-to-proxy.

next build fails with a custom webpack configuration

Turbopack is the default in 16.

Run next build --webpack, or migrate the customization to Turbopack options.

Full page reload when moving between /catalogue and /books

The two routes belong to different routers, so the navigation is a hard one and is not prefetched.

Finish migrating the related routes, or accept the reload during the transition.

A page reading searchParams is not static

Reading request data opts a route into dynamic rendering (previous model) or into streaming (Cache Components).

Expected; move the dynamic part under Suspense and keep the rest static.
