Getting Started

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when the facts and examples below were checked; the official documentation reports @doc-version 16.3.8), React 19.3.0, Node.js 20.9.0 or later and TypeScript 5.1 or later. It covers the App Router, which is what create-next-app generates, and it shows the Pages Router equivalent wherever the setup differs. Caching is only touched where it changes the first pages you write: the examples use the previous model (the default, in which nothing is cached unless you ask), and one section shows the same page under the opt-in Cache Components model (cacheComponents: true). Every example was built and run with Next.js 16.3.8, Node.js 24.16 and npm 11.13 on macOS, in a scratch copy of the Bookshelf — the catalogue of books, authors and reviews that the rest of this section grows, and that the Django and NestJS sections also build as a back end — and each one is followed by the official page it derives from.

The page starts at an empty folder and ends with a running, type-checked, linted and production-built application, a working dev loop, and a map of the official getting-started sequence. It does not re-teach React; if components, props and state are new, read React Getting Started first, and Server Rendering, SSG and React Server Components for the ideas behind the rendering modes that Next.js automates.

System Requirements

Next.js is a Node.js program: the dev server, the build and next start all run on it. The requirements below are the ones on the official installation page for 16.3.8.

Table 1. System requirements for Next.js 16.3
Requirement Value Notes

Node.js

20.9.0 or later

This is also the engines range of the next package. Node.js 18 stopped being supported in Next.js 16.

Operating systems

macOS, Windows (including WSL) and Linux

Turbopack ships native bindings for macOS (x64, ARM64), Windows (x64, ARM64) and Linux glibc and musl (x64, ARM64). Elsewhere (FreeBSD, OpenBSD) Next.js falls back to WebAssembly bindings, which do not support Turbopack, and you must pass --webpack.

Browsers

Chrome 111+, Edge 111+, Firefox 111+, Safari 16.4+

Modern browsers need no configuration. Polyfills and browser targets are described in the official browser-support page.

TypeScript

5.1.0 or later (optional)

Next.js 16.3 can also use TypeScript 7 for the type check in next build. The scaffold pins typescript to ^5.

React

react and react-dom 19

The App Router bundles its own React canary, which contains the stable React 19 features plus newer ones; you still declare react and react-dom in package.json. The Pages Router uses the version in your package.json, and React 18 still works there.

Package manager

npm, pnpm, Yarn or Bun

create-next-app accepts --use-npm, --use-pnpm, --use-yarn and --use-bun.

Check the Node.js version before anything else; most "it does not start" reports in a new project are an old Node.js.

Creating a Project with create-next-app

The quickest start is create-next-app, which writes the folder layout, installs the dependencies and configures TypeScript, the linter, the CSS toolchain, the import alias and the agent guidance file. --yes skips every prompt and uses your saved preferences or the defaults.

Quick start: the recommended defaults without prompts
npx create-next-app@latest bookshelf --yes
cd bookshelf
npm run dev

Source: Installation: quick start

Run without arguments, the CLI asks interactively. The first prompt names the project; the second chooses between the recommended defaults, your previous settings, or a customised set. The prompts below are the ones documented for Next.js 16.3.8.

The ESLint setup is a flat config that extends the Next.js rule sets. Since Next.js 16 the linter is run by its own CLI (eslint), not by next lint.

Source: ESLint

Three details of the scaffold matter later. First, .gitignore contains .env*, so environment files are not committed by default (the official environment-variables guide warns that you almost never want to commit them). Second, next-env.d.ts is listed in .gitignore, because Next.js regenerates it. Third, the starter layout.tsx loads the Geist fonts through next/font/google; the font files are fetched when the project is built, so the first build needs network access (self-hosting the font files is covered with fonts in the official sequence listed below).

The generated --api template is a good minimal Route Handler. The second handler reads a dynamic segment, and since Next.js 15 params is a Promise that must be awaited.

The route handlers generated by --api
// app/route.ts
import { NextResponse } from "next/server";

export async function GET() {
  return NextResponse.json({ message: "Hello world!" });
}
// app/[slug]/route.ts
import { NextRequest, NextResponse } from "next/server";

export async function GET(
  request: NextRequest,
  { params }: { params: Promise<{ slug: string }> },
) {
  const { slug } = await params;
  return NextResponse.json({ message: `Hello ${slug}!` });
}

The AGENTS.md and CLAUDE.md files

Since 16.2, create-next-app includes AGENTS.md by default (--no-agents-md opts out), together with a one-line CLAUDE.md containing @AGENTS.md. The file does not teach anything itself: it tells a coding agent to read the documentation that ships inside the next package, in node_modules/next/dist/docs/, which always matches the installed version, instead of relying on training data. A human reader gets the same benefit, because those files are the official docs as Markdown.

The block that next dev and create-next-app maintain in AGENTS.md
<!-- BEGIN:nextjs-agent-rules -->

# This is NOT the Next.js you know

This version has breaking changes — APIs, conventions, and file structure may all differ from your training data. Read the relevant guide in `node_modules/next/dist/docs/` (resolved from this file's directory; in monorepos the `next` package may not be visible from the repo root) before writing any code. Heed deprecation notices.

This block is written and re-added by `next dev` — verify at `node_modules/next/dist/server/lib/generate-agent-files.js`. Removing it from a diff only re-creates the uncommitted change; committing it with your work keeps the tree clean.

<!-- END:nextjs-agent-rules -->

Source: AI coding agents

From 16.3, next dev also writes and maintains this block in existing projects when it detects an AI coding agent in the environment (it was observed in the manual-installation run below, where the log printed that it had generated AGENTS.md and CLAUDE.md). Content you write outside the BEGIN and END markers is preserved. To opt out of the automatic generation, set agentRules to false:

Opting out of the managed agent files
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  agentRules: false,
}

export default nextConfig

Source: AI coding agents: opting out

On 16.2 the docs are bundled but the file is not auto-generated; on 16.1 and earlier the docs are not bundled and the legacy npx @next/codemod@canary agents-md command downloads a version-matched copy into .next-docs/.

Manual Installation

Nothing in Next.js requires create-next-app: it is a convenience. A project is three packages, three scripts and two files. This sequence was run from an empty folder, with the file contents exactly as shown.

Manual installation: packages and scripts

npm init -y
npm i next@latest react@latest react-dom@latest
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start",
    "lint": "eslint",
    "lint:fix": "eslint --fix"
  }

Source: Installation: manual installation

The app directory needs one file, the root layout, which must render the <html> and <body> tags; the home page is optional but nothing would be served at / without it.

The smallest App Router application: app/layout.tsx and app/page.tsx
// app/layout.tsx
export default function RootLayout({
  children,
}: {
  children: React.ReactNode
}) {
  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  )
}
// app/page.tsx
export default function Page() {
  return <h1>Hello, Next.js!</h1>
}

Two things differ from the scaffolded project. The auto-installed typescript is the newest release (7.0.2 on the checked date), whereas the scaffold pins ^5; both passed next build here. And the generated tsconfig.json has "strict": false; set it to true for a new project, or you give up most of what TypeScript offers.

A real pitfall of this route: on npm 11.13, npm init -y writes "type": "commonjs" into package.json. Turbopack then refuses ES-module syntax in the .tsx files (JSX compiles to an import) and every request returns HTTP 500.

The error caused by "type": "commonjs" in package.json
⨯ ./app/layout.tsx
Error: Specified module format (CommonJs) is not matching the module format of the source code (EcmaScript Modules)
The CommonJs module format was specified in the package.json that is affecting this source file ...
 GET / 500 in 988ms

The fix is to delete the "type" line (or set it to "module"); after removing it the same files returned HTTP 200. create-next-app never writes the field.

The Commands: dev, build and start

The next binary is the whole toolchain. Three commands make the lifecycle; the others are helpers.

Table 4. The next CLI commands in 16.3
Command Purpose

next dev

Development server with Hot Module Replacement, error reporting and on-demand compilation. Output goes to .next/dev, so next dev and next build can run at the same time.

next build

Optimised production build; prints the route table. Since 16 it no longer runs the linter, and no longer prints bundle sizes.

next start

Starts the production server. The application must have been compiled with next build first.

next info

Prints operating system, Node.js, package manager and package versions for bug reports (--verbose for more).

next typegen

Generates the route types (PageProps, LayoutProps, typed routes) and next-env.d.ts without a build, for next typegen && tsc --noEmit in CI.

next upgrade

Upgrades Next.js (and its docs) to the latest version; available from 16.1.

next telemetry

Enables or disables the anonymous telemetry (--enable, --disable).

next experimental-analyze

Turbopack bundle analyzer, labelled experimental. --output writes static files to .next/diagnostics/analyze.

Source: next CLI

Running next without a command is an alias for next dev. That has a nasty consequence for a removed command: in Next.js 16.3.8 next lint does not exist any more, and the CLI treats lint as the project directory of next dev:

A removed command is read as a directory
$ npx next lint
Invalid project directory provided, no such directory: /path/to/bookshelf/lint

Use the lint script (eslint) instead. A project that still has next lint in its scripts can be migrated with npx @next/codemod@canary next-lint-to-eslint-cli ..

Source: Installation: set up linting and Upgrading to version 16

next dev

Starting and requesting the development server (assembled from real runs, with the network address replaced)
$ npm run dev
> bookshelf@0.1.0 dev
> next dev

▲ Next.js 16.3.8 (Turbopack)
- Local:         http://localhost:3000
- Network:       http://192.168.1.20:3000
✓ Ready in 98ms
✓ Running next.config.ts took 13ms

The first request compiles the route on demand (Turbopack bundles lazily, only what the server is asked for), later ones are served in milliseconds, and each saved edit prints Compiled in …​. The request lines split the time into framework (next.js) and your code (application-code).

Table 5. The options of next dev that you use most
Option Effect

-p, --port <port> or PORT=4000

The port (default 3000). PORT cannot be set in a .env file, because the HTTP server starts before environment files are loaded. With npm run, pass flags after --: npm run dev — -p 4000.

-H, --hostname <hostname>

The hostname to bind (default 0.0.0.0, so it is reachable from other devices on the network).

--turbopack, --webpack

Turbopack is the default; --webpack selects webpack. --turbo is an alias of --turbopack.

--inspect

Attaches the Node.js debugger to the process that runs your code (16.1). --inspect-brk and --inspect-wait must go through NODE_OPTIONS.

--experimental-https

HTTPS with a self-signed certificate generated for localhost, for webhooks and authentication callbacks. Use --experimental-https-key, --experimental-https-cert and --experimental-https-ca to bring your own.

[directory]

A project directory other than the current one.

The First Page and Layout, Step by Step

The starter page is replaced by pages that belong to the Bookshelf. Everything below was written into the scaffolded project and then type-checked (tsc --noEmit), linted (eslint), built (next build) and served (next start). Routing is explained in depth later in this section; here the goal is only to see the file conventions at work.

Next.js routes by file system: folders inside app define URL segments, and special files inside them define the UI of that segment. A page.tsx makes a segment publicly reachable; a layout.tsx wraps its page and every nested segment, keeps its state and does not re-render on navigation between those children.

The root layout

app/layout.tsx: the root layout with metadata and navigation
import type { Metadata } from 'next'
import Link from 'next/link'
import './globals.css'

  title: { default: 'Bookshelf', template: '%s | Bookshelf' },
  description: 'A small catalogue of books, authors and reviews.',
}

export default function RootLayout({
  children,
}: {
  children: React.ReactNode
}) {
  return (
    <html lang="en">
      <body>
        <header>
          <nav>
            <Link href="/">Home</Link> <Link href="/books">Books</Link>
          </nav>
        </header>
        <main>{children}</main>
      </body>
    </html>
  )
}

Source: layout.js: root layout

The rules of the root layout, from the official reference:

  • It is required, lives at the top of app, and must define <html> and <body>.

  • Do not write <head> tags such as <title> and <meta> by hand; export metadata (or generateMetadata) and Next.js streams and de-duplicates the head elements. The title.template above turns a page title Books into Books | Bookshelf.

  • There can be several root layouts: any layout with no layout.js above it is a root layout, for example with the route groups app/(shop)/layout.js and app/(marketing)/layout.js. Navigating between different root layouts is a full page load, not a client-side navigation.

  • The root layout may sit under a dynamic segment such as app/[lang]/layout.js (internationalisation); that segment then becomes a root parameter.

  • A layout cannot read the request object. It is cached on the client between navigations and does not re-render, so use cookies() and headers() in Server Components and Functions instead, not in the layout’s props.

app/books/[id]/page.tsx: a dynamic segment, prerendered with generateStaticParams
import { notFound } from 'next/navigation'
import { books, getBook } from '@/lib/books'

export function generateStaticParams() {
  return books.map((book) => ({ id: book.id }))
}

export default async function BookPage(props: PageProps<'/books/[id]'>) {
  const { id } = await props.params
  const book = getBook(id)
  if (!book) notFound()

  return (
    <article>
      <h1>{book.title}</h1>
      <p>by {book.author}</p>
    </article>
  )
}

Source: Layouts and pages, page.js and Link

Points worth noticing in these four files:

  • Link is the primary navigation component. It extends <a> with prefetching and client-side transitions, so clicking Books swaps the page without a full reload while the layout stays mounted.

  • The module path alias @/lib/books comes from the paths entry written by create-next-app; getBook and books are imported from the project root, not through ../../../.

  • PageProps<'/books/[id]'> is a globally available helper type. It is generated into .next/types (and .next/dev/types) by next dev, next build or next typegen, so no import is needed, and it types params from the route string. Static routes resolve params to an empty object.

  • params is a Promise and must be awaited. Next.js 15 made the request APIs asynchronous (with a temporary synchronous compatibility layer), and Next.js 16 removed the synchronous access. A page that reads params.id directly is a leftover of the older model.

  • generateStaticParams returns the segment values to prerender at build time, which is why the route table shows /books/1, /books/2 and /books/3 as ●. A value outside the list is rendered on demand; notFound() renders the not-found UI and the response status is 404 (verified: /books/99 returns 404 under the previous model).

  • A page that is not a Client Component is a Server Component by default: it runs on the server (at build time here, because everything it needs is known), its code never reaches the browser, and the browser receives HTML plus the RSC payload used for later navigations.

Search parameters make a page dynamic

A Server Component page reads the query string through the searchParams prop, which is also a Promise. Reading it needs the incoming request, so the route stops being prerendered and is rendered on every request (the ƒ in the route table).

app/search/page.tsx: server-rendered search, previous model
import { books } from '@/lib/books'

export default async function SearchPage(props: PageProps<'/search'>) {
  const { q } = await props.searchParams
  const term = (Array.isArray(q) ? q[0] : q)?.toLowerCase() ?? ''
  const hits = books.filter((book) => book.title.toLowerCase().includes(term))

  return (
    <>
      <h1>Search</h1>
      <ul>
        {hits.map((book) => (
          <li key={book.id}>{book.title}</li>
        ))}
      </ul>
    </>
  )
}

Use the searchParams prop when the parameters decide which data to load (filtering, pagination); use the client hook useSearchParams when they only affect the client, for a list that was already loaded.

The same page under Cache Components

With cacheComponents: true the model is reversed: the build prerenders as much as it can into a static shell, and anything that needs the request must be inside a <Suspense> boundary, or the build fails. The page above, built unchanged with the option on, stops the build:

Build error with cacheComponents and an un-suspended searchParams
Error: Route "/search": Next.js encountered uncached or runtime data during prerendering.

`fetch(...)`, `cookies()`, `headers()`, `params`, `searchParams`, or `connection()` accessed outside of `<Suspense>`
prevents the route from being prerendered, blocking the page load and leading to a slower user experience.

Ways to fix this:
  - [stream] Provide a placeholder with `<Suspense fallback={...}>` around the data access
  - [cache] For uncached data (`fetch`, database calls): cache the access with `"use cache"` ...
  - [block] Set `export const instant = false` to allow a blocking route

Learn more: https://nextjs.org/docs/messages/blocking-prerender-dynamic

The error page blocking-prerender-dynamic documents the fix: stream the dynamic part behind a fallback. Under Cache Components the route becomes partially prerendered (◐): the heading and the fallback are in the shell, the results stream in.

  cacheComponents: true,

export default nextConfig

Fast Refresh

Fast Refresh is a React feature integrated into Next.js that applies your edits in the browser within about a second while keeping temporary client-side state. It has been on by default since Next.js 9.4 and needs no configuration. Its behaviour depends on what the edited file exports:

  • A file that exports only React components is re-evaluated alone and its components re-render; styles, rendering logic, handlers and effects are all editable.

  • A file that also exports non-component values (a constant, a helper) is re-run together with the files that import it.

  • A file imported by something outside the React tree makes Fast Refresh fall back to a full reload.

Error resilience is part of the design. A syntax error shows an overlay; fixing it and saving removes the overlay with no reload and with no loss of state. A runtime error inside a component shows a contextual overlay; state is kept if the error did not occur while rendering, and React remounts the application with the new code if it did. Error boundaries retry on the next edit, so one around a section can stop a render error from resetting the whole page.

The behaviour was checked in a browser against the LikeButton above on a running next dev: the button was clicked twice (Like (2)), the label in the source was changed to Favourite, and after the save the button read Favourite (2) — the new code was live and the state survived.

-  return <button onClick={() => setLikes(likes + 1)}>Like ({likes})</button>
+  return <button onClick={() => setLikes(likes + 1)}>Favourite ({likes})</button>

When state is reset on every edit, one of these limitations applies, and each has a fix:

Table 7. Why Fast Refresh may reset state
Cause What to do

The file is a class component (only function components and Hooks keep state)

Convert to a function component.

The file exports something that is not a component next to the component

Move the constant or helper to its own file.

The file exports the result of a higher-order component such as HOC(Wrapped) and the result is a class

Use a function component.

An anonymous default export, such as export default () ⇒ <div />

Name the component. The name-default-component codemod does this for a large code base.

An import whose case does not match the file name (./header against ./Header)

Fix the case; both fast and full refresh fail on it.

Two tools help. Add the comment // @refresh reset anywhere in a file to make Fast Refresh remount that file’s components on every edit, which is handy for an animation that only runs on mount. And remember that hooks with dependency arrays (useEffect, useMemo, useCallback) always re-run during Fast Refresh, ignoring their dependencies; code that tolerates an occasional extra effect run is better code anyway, and React Strict Mode enforces it.

Cross-origin dev access

Next.js blocks cross-origin requests to dev-only assets and endpoints. localhost, its subdomains and the hostname the server was started with are allowed; opening the app through another hostname (a tunnel, a custom domain, a different machine) needs an allowedDevOrigins entry containing only the hostname, without scheme or port. Without it the browser’s requests to those dev-only assets and endpoints are blocked.

next.config.ts: allowing a development tunnel
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  allowedDevOrigins: ['*.tunnel.example.com'],
}

export default nextConfig

Symptom Cause Fix

Every request returns 500 with "Specified module format (CommonJs) is not matching"

package.json contains "type": "commonjs" (written by npm init -y on npm 11.13)

Remove the field, or set it to "module".

next lint prints "Invalid project directory provided"

The command was removed in 16; next treats the word as the project directory

Use the eslint script; migrate with the next-lint-to-eslint-cli codemod.

next build fails after adding a webpack function to next.config

Turbopack is the default and the version 16 upgrade guide says a custom webpack config fails the build

Remove the customisation, or run next build --webpack and next dev --webpack.

Error: listen EADDRINUSE: address already in use :::3000

Another process owns the port

PORT=3001 npm run dev or npm run dev — -p 3001. PORT in .env is ignored.

The page loads through a tunnel or custom host but dev features do not work

The origin is not allowed in development

Add the hostname to allowedDevOrigins.

await is missing on params or searchParams and the page fails or warns

Since 15 they are Promises; 16 removed synchronous access

const { id } = await props.params, or use PageProps for the types.

The build fails with "uncached or runtime data during prerendering"

cacheComponents is on and request data is read outside <Suspense>

Move the read into a child under <Suspense>, cache it with 'use cache', or opt out of the shell with export const instant = false.

A missing book returns HTTP 200 instead of 404

notFound() was thrown inside a streamed <Suspense> boundary after the response had started

Call it before streaming begins, or add a noindex robots tag; the status cannot change after the headers are sent.

The first next build fails offline

The scaffold’s layout downloads Geist from Google Fonts

Allow the network, or self-host the font with next/font/local.

A change does not show after next start

next start serves the last build

Run next build again; use next dev while editing.

.env values are committed

The .env* ignore rule was removed

Keep .env* in .gitignore; only variables prefixed NEXT_PUBLIC_ are bundled into browser code.

Source: Upgrading to version 16, Environment variables and blocking-prerender-dynamic

Where the Books Are Outdated

The two books consulted for this section — Real-World Next.js (Michele Riva, Packt, 2022) and Practical Next.js for E-Commerce (Alex Libby, Apress, 2023) — target the Pages Router on Next.js 12 and 13.2, with React 17 and 18. Their first chapters are the setup and project-layout chapters, which is where the differences from today are largest. They are good for the concepts and wrong for the commands.
