Pages Router

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Next.js 16.3.8 (the latest release on 2026-10-03, when the facts and examples below were checked; the official documentation reports @doc-version 16.3.8), React 19.3.0 and Node.js 20.9.0 or later. It covers the Pages Router in full, because a very large number of production applications, and both requester-provided books this section consulted, are written with it, and the App Router only where it matters for migration: what replaces each Pages Router file and function, and how the two routers run side by side while you move. Caching matters here too, so the page says which model applies: the Pages Router has its own, much smaller set of caches that cacheComponents does not change (the previous model from the App Router’s point of view), and Cache Components only enters the picture for the routes you move into app. Every example was built with next build and served with next start (Node.js 24.16, macOS) in a scratch copy of the Bookshelf — the catalogue of books this section grows — and the results quoted below are what curl returned.

The Pages Router is not deprecated or removed: it ships in Next.js 16.3 with its own documentation tree (the index is at https://nextjs.org/docs/pages/llms.txt), and the 16.x line is the one under Active LTS in the support policy. The next package still accepts React 18 as well as React 19 in its peer range, which is one of the reasons a codebase can stay on pages while it upgrades other things. What it does not get is the new work: Server Components, Server Actions, Cache Components and Instant Navigations are App Router features. Read this page if you maintain a Pages Router app, if you have to read one (the books do), or if you are planning to leave it. The routing, rendering and caching ideas are explained from the App Router side on Routing Fundamentals, Server-Side Rendering, Static Site Generation and Incremental Static Regeneration, each of which also has a Pages Router comparison that this page consolidates.

The Pages Router at a Glance

In the Pages Router every file in pages/ that exports a React component is a route, every file in pages/api/ is a server-only endpoint, and a handful of reserved files (_app, _document, _error, 404, 500) customise how pages are initialised, wrapped in HTML and shown when something goes wrong. Data is not fetched by components: it is fetched by an exported data function next to the page, which runs on the server and hands its result to the component as props. The page component itself is a normal React component that is rendered on the server (for the first HTML) and again in the browser (hydration), which is why, in the App Router’s vocabulary, every Pages Router component is a Client Component.

The pages Directory and File-System Routing

The Pages Router maps files to URLs. The conventions are the ones the App Router later kept in spirit but not in file names (there is no page.tsx here: the file is the page).

A specific route wins over a dynamic one, and a dynamic one over a catch-all (the official dynamic routes page lists the exact precedence). One practical limit is worth remembering: every file under pages/ that matches the configured page extensions is a route, so you do not colocate components or tests there the way the App Router lets you colocate files next to page.tsx; keep them in a components/ folder (as the examples do) or restrict the extensions with pageExtensions in next.config.ts.

The dynamic route and its helpers are the best illustration of how the Pages Router splits a route in two: the component renders, and the data functions decide what to render and when. The [id] page used throughout this page is shown in full in the data functions section; the dynamic-routes mechanics (parameters, precedence, catch-alls) are explained, with the App Router syntax, on Dynamic Routes and Route Groups.

_app: Wrapping Every Page

pages/_app.tsx overrides the App component Next.js uses to initialise every page. It receives Component (the active page; it changes on every client-side navigation) and pageProps (the props the page’s data function returned, or an empty object). It is the place to render a layout that persists across navigations, to inject shared data, and to import global CSS — in the Pages Router a global stylesheet may only be imported here. Providers for React Context, a Redux store or an authentication session wrap Component in this file; that is the pattern both books use, and it is also why a Pages Router app is hard to make lean: whatever _app imports is bundled into every page.

pages/_app.tsx: a per-page layout through the getLayout pattern (verified: build and curl)
import "@/styles/globals.css";
import type { ReactElement, ReactNode } from "react";
import type { NextPage } from "next";
import type { AppProps } from "next/app";
import Layout from "@/components/Layout";

export type NextPageWithLayout<P = {}, IP = P> = NextPage<P, IP> & {
  getLayout?: (page: ReactElement) => ReactNode;
};

type AppPropsWithLayout = AppProps & { Component: NextPageWithLayout };

export default function MyApp({ Component, pageProps }: AppPropsWithLayout) {
  const getLayout = Component.getLayout ?? ((page) => <Layout>{page}</Layout>);
  return getLayout(<Component {...pageProps} />);
}

Source: Pages Router: Custom App and Pages Router: Pages and Layouts

A page opts into a different layout by setting Page.getLayout, which _app calls (the official pages-and-layouts page calls this the per-page layouts pattern). Component.getLayout is the single piece of layout machinery of the Pages Router; it is replaced by native nested layouts in the App Router, as the migration section shows. Three caveats from the official page matter in practice:

  • App does not support getStaticProps or getServerSideProps. Data that every page needs has to be fetched by each page, or you reach for getInitialProps on App.

  • getInitialProps on App is documented as a pattern the Next.js team does not recommend: it disables Automatic Static Optimization for every page that has no getStaticProps, and the page points to incremental adoption of the App Router instead.

  • If you add pages/_app while the dev server is running and it did not exist before, restart the server.

_document: The HTML Skeleton

pages/_document.tsx customises the <html> and <body> that wrap every page. It is rendered only on the server, so event handlers such as onClick do not work in it, and the components it uses (Html, Head, Main and NextScript, all imported from next/document) are all required for the page to render correctly.

pages/_document.tsx: the document with a language and a site-wide meta tag (verified)
import { Html, Head, Main, NextScript } from "next/document";

export default function Document() {
  return (
    <Html lang="en">
      <Head>
        <meta name="application-name" content="Bookshelf" />
      </Head>
      <body>
        <Main />
        <NextScript />
      </body>
    </Html>
  );
}

Source: Pages Router: Custom Document

curl of any page returned <html lang="en"> and the application-name meta tag in <head>. The caveats are the reverse of `_app’s:

  • The Head from next/document is not next/head. Use it only for tags shared by every page; use next/head in pages and components for the rest (titles, per-page meta). The next section of this page covers next/head.

  • React components outside <Main /> are not initialised in the browser, so do not put application logic or custom CSS such as styled-jsx there; use a layout in _app for shared UI.

  • Document does not support getStaticProps or getServerSideProps.

  • A getInitialProps on a class Document is used for libraries that need to customise renderPage (CSS-in-JS server rendering). It is not called on client-side transitions, the official page again does not recommend it, and if you do use it you must check that ctx.req is defined before assuming the page was rendered per request, because it is undefined for prerendered pages.

next/head renders elements into the document head from inside any component, which is how the Pages Router handles titles and meta tags. Two details from the official page and from our run: elements must be direct children of Head (or wrapped in at most one level of fragment or array) or they are not picked up on client-side navigations, and the <title> should receive one string. In the scratch app <title>{book.title} - Bookshelf</title>, whose children React sees as an array, produced an empty <title></title> in the server HTML, while the template literal form <title>{${book.title} - Bookshelf`}</title>` produced <title data-next-head="">Dune - Bookshelf</title>. In the App Router next/head is replaced by the Metadata API (see the migration table).

Source: Pages Router: Head

_error, 404 and 500

The Pages Router has three levels of error pages, all in pages/:

  • 404.tsx is the page shown when no route matches (and when a data function returns notFound: true). It is generated statically at build time, so it costs nothing per hit; Next.js provides a default 404 if you add none.

  • 500.tsx is the page shown when a server-side error occurs. It is also generated statically.

  • _error.tsx is the advanced hook. 500 errors are handled by the Error component on both the server and the client, and _error overrides it. It is only used in production: in development you get the error overlay with the call stack instead.

pages/404.tsx, pages/500.tsx and pages/_error.tsx (verified)
// pages/404.tsx
export default function Custom404() {
  return <h1>404 - Page Not Found</h1>;
}

// pages/500.tsx
export default function Custom500() {
  return <h1>500 - Server-side error occurred</h1>;
}

// pages/_error.tsx
import type { NextPageContext } from "next";

function Error({ statusCode }: { statusCode?: number }) {
  return (
    <p>{statusCode ? `An error ${statusCode} occurred on server` : "An error occurred on client"}</p>
  );
}

Error.getInitialProps = ({ res, err }: NextPageContext) => {
  const statusCode = res ? res.statusCode : err ? err.statusCode : 404;
  return { statusCode };
};

export default Error;

Source: Pages Router: Custom Errors

After next build and next start, curl -i /nope returned 404 with the body 404 - Page Not Found (the generated .next/server/pages/404.html contains it). A getServerSideProps that throws, on a temporary /boom page, returned 500 with 500 - Server-side error occurred and logged the stack trace on the server. Because 404.tsx and 500.tsx are rendered inside your custom _app, your global styles and theme apply to them, unlike the built-in pages, which follow the operating system’s colour scheme.

To show the built-in error page from a page (for example when an upstream API fails) import Error from next/error and render it with a statusCode; the component also accepts a title. If you define your own _error, import that one instead. _error, like _app, is a reserved pathname: /_error rendered directly returns 404 (our curl /_error did), and _error does not support the data functions.

Source: Pages Router: Custom Errors

API Routes

Any file in pages/api/ is mapped to /api/* and treated as an endpoint instead of a page. API routes are server-only bundles: they add nothing to the client bundle. The handler receives a Node.js req (http.IncomingMessage, extended with req.cookies, req.query and req.body, the body parsed by content-type) and a res (http.ServerResponse, extended with res.status(code), res.json(body), res.send(body), res.redirect([status,] path) and res.revalidate(urlPath)). This is the Node.js-style API that the books use; it is not the Web Request/Response API of App Router Route Handlers.

pages/api/books/index.ts: one handler, several HTTP methods (verified)
import type { NextApiRequest, NextApiResponse } from "next";
import { addBook, listBooks, type Book } from "@/lib/books";

type Data = Book[] | Book | { error: string };

export default async function handler(req: NextApiRequest, res: NextApiResponse<Data>) {
  switch (req.method) {
    case "GET": {
      const q = typeof req.query.q === "string" ? req.query.q : "";
      return res.status(200).json(await listBooks(q));
    }
    case "POST": {
      const { title, author } = req.body ?? {};
      if (typeof title !== "string" || typeof author !== "string" || !title || !author) {
        return res.status(400).json({ error: "title and author are required" });
      }
      return res.status(201).json(await addBook({ title, author }));
    }
    default:
      res.setHeader("Allow", ["GET", "POST"]);
      return res.status(405).json({ error: `Method ${req.method} Not Allowed` });
  }
}

Source: Pages Router: API Routes

The behaviour to remember about API routes:

  • They are same-origin only by default: no CORS headers are sent. To allow other origins wrap the handler with CORS helpers (the official page links an example).

  • They cannot be used with a static export (output: 'export'); Route Handlers in the App Router can, for GET.

  • They are affected by pageExtensions.

  • req.body is typed any in NextApiRequest because a client may send anything. Validate the shape at runtime, as the example does (a schema library such as Zod is the usual tool). Never trust the body for prices or permissions: the handler is public.

  • Dynamic API routes ([id].ts), catch-all ([…​slug].ts) and optional catch-all ([[…​slug]].ts) follow the same rules as pages, and predefined routes win over dynamic ones.

  • An API route can stream a response; the official page has a section on it.

  • The migration guide notes that if you used API routes only to call an external API from the client, Server Components can fetch it securely instead.

res.revalidate is the Pages Router’s on-demand ISR trigger and must be protected, because anyone who can call it can make your server regenerate pages. The example reads the token from the environment (the value shown is a placeholder):

pages/api/revalidate.ts: on-demand revalidation behind a shared secret (verified)
import type { NextApiRequest, NextApiResponse } from "next";

export default async function handler(req: NextApiRequest, res: NextApiResponse) {
  if (req.method !== "POST") return res.status(405).end();
  if (req.headers["x-revalidate-token"] !== process.env.REVALIDATE_TOKEN) {
    return res.status(401).json({ message: "Invalid token" });
  }
  try {
    await res.revalidate("/books/1");
    return res.json({ revalidated: true });
  } catch {
    return res.status(500).send("Error revalidating");
  }
}

Source: Pages Router: Incremental Static Regeneration

Calling it with and without the token (REVALIDATE_TOKEN is set in the server’s environment)

$ curl -i -X POST -H "x-revalidate-token: $REVALIDATE_TOKEN" http://localhost:3902/api/revalidate

GET on the same route returned 405. The App Router replacement is revalidatePath or revalidateTag called from a Route Handler or a Server Action, covered on Incremental Static Regeneration and Route Handlers and Backend for Frontend.

next/router

The Pages Router has two ways to navigate: the Link component from next/link (declarative, prefetches in production) and the router from next/router (programmatic). useRouter() is a React Hook, so it cannot be used in class components; withRouter is the class-component alternative, and a function component can wrap a class.

Table 3. The router object returned by useRouter from next/router
Field Meaning

pathname

The route file’s path after /pages, for example /books/[id]; excludes basePath, locale and the trailing slash.

query

The query string and the dynamic route parameters as an object. Empty during prerendering when the page does not use server-side rendering.

asPath

The path as shown in the browser, including the search params; excludes basePath and locale.

isReady

Whether the router fields are updated on the client. Use it inside effects, not to render different HTML on the server.

isFallback

Whether the current page is shown in getStaticPaths fallback mode.

isPreview

Whether the application is in preview mode.

basePath, locale, locales, defaultLocale, domainLocales

The configured base path and i18n values, if enabled.

The methods are router.push(url, as, options) (adds a history entry), router.replace (same parameters, no new entry), router.prefetch (production only; Next.js does not prefetch in development), router.back, router.reload (a full reload), router.beforePopState(cb) to intercept popstate events, and router.events. url can be a string or a URL object ({ pathname: "/books", query: { q } }), and the options include shallow to change the URL without re-running the data functions. External URLs do not need the router: use window.location. The router fires routeChangeStart, routeChangeComplete, routeChangeError, beforeHistoryChange, hashChangeStart and hashChangeComplete; each callback receives the URL and an object with shallow.

components/SearchBox.tsx: programmatic navigation and router events (built; the SSR output was checked, the click handling was not run in a browser)
import { useEffect, useState, type FormEvent } from "react";
import { useRouter } from "next/router";

export default function SearchBox() {
  const router = useRouter();
  const [q, setQ] = useState("");

  useEffect(() => {
    const done = (url: string) => console.log("navigated to", url);
    router.events.on("routeChangeComplete", done);
    return () => router.events.off("routeChangeComplete", done);
  }, [router.events]);

  function onSubmit(e: FormEvent) {
    e.preventDefault();
    router.push({ pathname: "/books", query: q ? { q } : {} });
  }

  return (
    <form onSubmit={onSubmit}>
      <input value={q} onChange={(e) => setQ(e.target.value)} placeholder="Search books" />
      <button type="submit">Search</button>
    </form>
  );
}

Source: Pages Router: useRouter

Subscribe to events in an effect and unsubscribe in its cleanup, as shown; _app is a convenient place for global handlers because it is not unmounted on navigation. When a navigation to the same page with a different parameter must reset component state, either update the state in an effect or give the component a key so React remounts it.

Two version-specific facts matter when the two routers coexist. useRouter from next/router is not supported in the app directory (it can keep being used in pages); the App Router has its own useRouter from next/navigation that does not return pathname or query, which are replaced by usePathname, useSearchParams and useParams. And next/compat/router exports a useRouter that returns null instead of throwing when the Pages Router is not mounted, which lets one component run in both routers during a migration. For linking details see Linking and Navigation.

getStaticProps and getStaticPaths

getStaticProps generates the page at build time (static site generation); for a dynamic route it is paired with getStaticPaths, which lists the paths to build and what to do with the rest through fallback. getStaticProps returns props, and optionally revalidate (seconds after which the page is regenerated in the background: ISR), notFound (serve the 404 page) or redirect. getStaticPaths returns paths (an array of params objects whose keys match the route’s brackets; an array for a catch-all) and fallback.

pages/books/[id].tsx: static generation, a fallback and ISR in one page (verified)
import type { GetStaticPaths, GetStaticProps, InferGetStaticPropsType } from "next";
import Head from "next/head";
import { useRouter } from "next/router";
import { getBook, listBooks, type Book } from "@/lib/books";

export const getStaticPaths = (async () => {
  const books = await listBooks();
  return {
    // build only the first two books; the rest are generated on first request
    paths: books.slice(0, 2).map((b) => ({ params: { id: b.id } })),
    fallback: "blocking",
  };
}) satisfies GetStaticPaths;

export const getStaticProps = (async ({ params }) => {
  const book = await getBook(params!.id as string);
  if (!book) return { notFound: true, revalidate: 60 };
  return { props: { book }, revalidate: 60 };
}) satisfies GetStaticProps<{ book: Book }, { id: string }>;

export default function BookPage({ book }: InferGetStaticPropsType<typeof getStaticProps>) {
  const router = useRouter();
  if (router.isFallback) return <p>Loading...</p>;
  return (

  );
}

getServerSideProps

getServerSideProps runs on every request and returns props, notFound or redirect. The context carries req and res (the Node.js objects, with req.cookies), query, params, resolvedUrl (the normalised URL, with the _next/data prefix removed for client transitions), draftMode, and the locale values if i18n is enabled. Use it when a page depends on the request (a cookie, a header, a query string) or on data that must be current.

pages/books/index.tsx: a server-rendered search page with its own caching header (verified)
import type { GetServerSideProps, InferGetServerSidePropsType } from "next";
import Link from "next/link";
import SearchBox from "@/components/SearchBox";
import { listBooks, type Book } from "@/lib/books";

export const getServerSideProps = (async ({ query, res }) => {
  const q = typeof query.q === "string" ? query.q : "";
  res.setHeader("Cache-Control", "public, s-maxage=10, stale-while-revalidate=59");
  return { props: { q, books: await listBooks(q) } };
}) satisfies GetServerSideProps<{ q: string; books: Book[] }>;

export default function Books({ q, books }: InferGetServerSidePropsType<typeof getServerSideProps>) {
  return (
    <main>
      <h1>Books{q ? ` matching "${q}"` : ""}</h1>
      <SearchBox />
      <ul>
        {books.map((b) => (
          <li key={b.id}>
            <Link href={`/books/${b.id}`}>{b.title}</Link> by {b.author}
          </li>
        ))}
      </ul>
    </main>
  );
}

getInitialProps

getInitialProps is an async function attached to the page component as a property. It is a legacy API: the official page recommends getStaticProps or getServerSideProps instead. It runs on the server for the initial load and again in the browser on client-side navigations, so it must not use server-only modules and what it returns is serialised, plain objects only. Its context has pathname, query, asPath, req, res and err; req and res exist only on the server. It can only be used in top-level pages/ files, not in nested components, and a page that has it is never statically optimised.

pages/legacy.tsx: getInitialProps and the server/client split (verified)
import type { NextPageContext } from "next";

type Props = { runtime: string; path: string };

export default function Legacy({ runtime, path }: Props) {
  return (
    <main>
      <h1>Legacy page</h1>
      <p>Rendered on the {runtime} for {path}</p>
    </main>
  );
}

Legacy.getInitialProps = async (ctx: NextPageContext): Promise<Props> => {
  return { runtime: ctx.req ? "server" : "client", path: ctx.asPath ?? ctx.pathname };
};

Automatic Static Optimization

Next.js decides on its own that a page is static when it has no blocking data requirement, which it infers from the absence of getServerSideProps and getInitialProps. That page is prerendered to HTML at build time without you writing a data function; it is still hydrated and fully interactive. The home page of the scratch app (pages/index.tsx, a page with next/head and useRouter but no data function) is shown as ○ in the route table, and next build wrote .next/server/pages/index.html. The official page’s example makes the rule visible: pages/about.js is emitted as .next/server/pages/about.html while adding getServerSideProps turns it into JavaScript (about.js) that renders per request.

The consequences of a static page that you must plan for:

  • The router’s query object is empty during prerendering, because there is no query to provide at build time. After hydration Next.js triggers a second render with the real values, when the page is a dynamic route, has query values in the URL, or when rewrites are configured. Use router.isReady to tell whether query is complete.

  • Dynamic route parameters of a page that uses getStaticProps are always in query.

  • Avoid asPath in the render tree until isReady is true: a statically optimised page only knows asPath on the client, so using it can cause a hydration mismatch.

  • A custom App with getInitialProps turns the optimisation off for all pages without getStaticProps. A custom Document with getInitialProps means you must check ctx.req as described above.

What the home page does with the query (verified: curl "http://localhost:3902/?name=Ada")
import Head from "next/head";
import { useRouter } from "next/router";

export default function Home() {
  const router = useRouter();
  return (
    <main>
      <Head>
        <title>Bookshelf</title>
      </Head>
      <h1>Bookshelf</h1>
      <p>Greeting for: {router.isReady ? (router.query.name ?? "reader") : "reader"}</p>
    </main>
  );
}

Source: Pages Router: Automatic Static Optimization

The server response for /?name=Ada contained Greeting for: reader and an empty "query":{} in NEXT_DATA: the HTML is the prerendered one, and Ada appears only after hydration. That is the whole point of the optimisation (the file is served from a CDN without running anything) and the whole source of the "flash of default content" on query-driven pages; when the first render must depend on the query, use getServerSideProps instead. The hydration side of this is explained on Hydration and the client-rendered half on Client-Side Rendering.

Caching: Previous Model and Cache Components

The Pages Router has a short list of caches, none of which cacheComponents changes: the build output of static and getStaticProps pages, the ISR cache (visible through x-nextjs-cache), the Cache-Control headers that you set (and that Next.js sets on ISR responses, as in the output above). Everything else is request-time. To check that, the Pages Router scratch app was built with CACHE_COMPONENTS=1 (which sets cacheComponents: true) and with it unset: the route table was identical in both modes.

Cache Components starts to matter per route that you move. In the migrated copy of the app (below) the new app/books route reads searchParams. With the previous model it built and served as ƒ. With Cache Components the same page failed next build with Route "/books": Next.js encountered uncached or runtime data during prerendering and the message blocking-prerender-dynamic; the fix is to read searchParams inside a component wrapped in Suspense, as the Partial Prerendering and Cache Components and Caching pages explain. So an application can turn cacheComponents on while it still has pages routes, provided the routes already in app follow the new rules. The mapping of getStaticProps and revalidate to caching APIs depends on the model you target; the table below names both.

Incremental Migration to the App Router

The App Router was designed to work alongside the Pages Router: the app directory and the pages directory can both be present, and routes can be moved one at a time. The official migration guide recommends splitting the change into small steps, because moving to the App Router may be the first time you meet Server Components, Suspense and the new data model at once. Before the steps, remember what the two routers share and what they do not:

  • A route must exist in only one place: with app/dup/page.tsx and pages/dup/index.tsx both present, next build failed with App Router and Pages Router both match path: /dup.

  • app/layout.tsx does not wrap pages/ routes, and _app and _document do *not wrap app/* routes. Styles imported in the root layout do not apply to pages; keep _app/_document until the last page has moved. In our migrated copy curl of the app route returned no <nav> (the navigation lives in _app’s layout), while the `pages route still had it.

  • Navigating between a route in app and one in pages is a hard navigation (a full page load), and next/link prefetching does not cross routers. The official guide links to Vercel guidance on optimising these.

  • In a mixed app, an unmatched URL or a notFound() from the Pages Router rendered the App Router’s not-found page, not pages/404.tsx. Without app/not-found.tsx Next.js showed its default "This page could not be found."; with a app/not-found.tsx it showed that file’s content, for both /nope and the pages route /books/99. Add the App Router not-found file on day one of a migration.

The Steps

Step 1: update. The guide’s baseline for the App Router is Next.js 13.4; today you start from 16.3, which brings the Node.js 20.9 requirement, async request APIs and the other changes tabulated below. Upgrade the Pages Router app first, run it, then add app.

Step 2: create app/ and a root layout. A root layout is mandatory, defines <html> and <body> and replaces _app and _document over time. Context providers from _app must become a Client Component imported into the layout.

  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  );
}

Source: Migrating from the Pages Router to the App Router

Step 3: the getLayout pattern becomes nested layouts, and next/head becomes metadata. A Page.getLayout function is replaced by a layout.tsx in the route’s folder; interactive parts of the old layout component stay in a Client Component and move into the Server Component layout piece by piece. <Head><title> becomes export const metadata or generateMetadata (see Metadata and SEO).

Step 4: migrate one page. Pages in app are Server Components by default, unlike pages, where every page is a Client Component. The guide’s safest route is two sub-steps: move the default-exported page component into a Client Component ('use client'; it is still prerendered to HTML on the first load, like in pages), then add a page.tsx that imports it, and fetch the data in the Server Component instead of in a data function. components/SearchBox.tsx: a Client Component using only next/navigation (verified in both routers)
"use client";

import { useState, type FormEvent } from "react";
import { useRouter, useSearchParams } from "next/navigation";

export default function SearchBox() {
  const router = useRouter();
  const searchParams = useSearchParams();
  const [q, setQ] = useState(searchParams?.get("q") ?? "");

  function onSubmit(e: FormEvent) {
    e.preventDefault();
    router.push(q ? `/books?q=${encodeURIComponent(q)}` : "/books");
  }

  return (
    <form onSubmit={onSubmit}>
      <input value={q} onChange={(e) => setQ(e.target.value)} placeholder="Search books" />
      <button type="submit">Search</button>
    </form>
  );
}

Pitfalls

  • Secrets in props. Everything returned from a data function is serialised into NEXT_DATA; return only what the component needs. Server-only modules imported in a page can end up in the client bundle if they are used in the component, and a package that imports server-only fails the Pages Router build with a message that it is used in the Pages Router.

  • Unprotected revalidation and API routes. res.revalidate and pages/api/* are public endpoints: validate method, token and body, and check authorisation in the handler.

  • The query is empty on static pages. Read it only after router.isReady; if the first render must depend on it, use getServerSideProps.

  • A getInitialProps in _app. It silently turns static optimisation off for the whole site.

  • <title> with several children. It produced an empty title in our run; use one string.

  • Mixed routers. Layouts and global CSS do not cross; the not-found page is the App Router’s; navigations between the routers are hard navigations; the same URL in both is a build error.

  • next/router in app. It is not supported there; use next/navigation or next/compat/router.

  • Moving a route under Cache Components without Suspense. blocking-prerender-dynamic, as shown above.
