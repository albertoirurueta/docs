The admin is the part of Django that turns your models into a ready-made back office: a change list with search, filters and bulk actions, a change form with validation, an audit trail, and a permission system. This page covers how it is wired in, how to register models, every ModelAdmin option and hook that matters, how the display and action decorators work, inlines, custom filters, admin permissions, and what to watch out for. It builds the staff side of the Bookshelf application (the catalog app developed across this section). Customising the site itself (a custom AdminSite, extra views, template overrides, JavaScript, securing the URL) is the subject of Admin Customization.

Where the admin sits in the request and response cycle

The admin is an ordinary Django app (django.contrib.admin) that exposes one URLconf, admin.site.urls, which you mount wherever you like (the project template uses admin/). There is no special server: a request to /admin/…​ travels through the same middleware stack as any other URL (see Middleware and The Request/Response Cycle), is matched by the URL resolver, and reaches a view that happens to be a method of AdminSite or ModelAdmin.

sequenceDiagram participant B as Browser participant M as Middleware (session, auth, messages, CSRF) participant S as AdminSite.admin_view participant A as ModelAdmin view participant F as ModelForm and formsets participant D as Database B->>M: GET or POST /admin/catalog/book/ M->>S: request with request.user and messages S->>S: has_permission? (active and staff) alt not staff S-->>B: 302 to /admin/login/?next=... else staff S->>A: changelist_view / add_view / change_view A->>A: has_*_permission(request, obj) A->>F: build form, validate, save_model, save_formset F->>D: SELECT, INSERT, UPDATE, DELETE A-->>B: TemplateResponse, or redirect with a flash message end

Three facts follow from that picture and explain most admin behaviour.

  • Every admin view is wrapped by AdminSite.admin_view(). The wrapper checks AdminSite.has_permission() (the user must be active and is_staff), sends anonymous users to the admin login page with a next parameter, applies never_cache and csrf_protect. Views you add yourself must be wrapped the same way (covered in Admin Customization).

  • The admin needs three middleware classes and four context processors. SessionMiddleware, AuthenticationMiddleware and MessageMiddleware must be in MIDDLEWARE; the request, auth and messages context processors must be configured on a DjangoTemplates backend. System checks admin.E401 to admin.E410 verify all of this, so manage.py check tells you what is missing.

  • Authorisation happens inside the admin view, per request. After admin_view lets a staff user in, each ModelAdmin view asks has_view_permission(), has_add_permission(), has_change_permission() or has_delete_permission(), and answers 403 when the answer is no. This is where the rules of Permissions in the admin plug in.

A model appears in the admin only after it is registered. Django imports the admin module of every installed app at start-up (autodiscover(), called by AdminConfig.ready()), so the convention is a catalog/admin.py that registers the app’s models.

The change list: list_display and its five kinds of value

list_display sets the columns. Without it the list shows one column, the object’s __str__. Each element can be:

  1. The name of a model field (a ForeignKey shows the related object’s __str__; a BooleanField shows a yes/no/unknown icon).

  2. A related field with the double-underscore notation, such as author__country (Django 5.1; before that the only way was a callable).

  3. A callable that accepts the model instance.

  4. A string naming a ModelAdmin method that accepts the instance.

  5. A string naming a model attribute or method with no required argument.

Django resolves an element in that order (a model field wins over a ModelAdmin attribute of the same name). ManyToManyField is not supported directly because it would run one query per row; write a method that does the work once (for example from an annotation) instead.

The decorator @admin.display (Django 3.2) configures how a callable behaves as a column or a read-only field.

Argument Effect

description

The column header, or the label of a read-only field. Defaults to the name with underscores replaced by spaces.

ordering

The field (or lookup, or query expression, or "-field" for descending) the column sorts by. Without it a callable column is not sortable.

boolean

True shows the yes/no/unknown icon for a callable that returns True, False or None. Since 5.0 it also works on properties, and since 6.1 the icon is used for boolean fields on related models.

empty_value

What to show when the value is None, an empty string or an empty iterable; overrides ModelAdmin.empty_value_display for that column.

Output of a callable is HTML-escaped. To emit markup, build it with format_html() (which escapes the arguments) and never with string formatting plus mark_safe(): the values come from user input. A property can be a column too, but @property must be the outer decorator and @admin.display the inner one.

list_select_related and the N+1 problem

A column that follows a foreign key (author here) runs one extra query per row unless the related row is fetched with the list. list_select_related controls that: a list or tuple of field names is passed to select_related(), an empty tuple disables it, and get_list_select_related(request) makes it dynamic. Two changes matter on 6.1: when the option is False (the default) the change list now selects only the foreign keys named in list_display instead of all of them, and setting the option to True (or returning True from the method) is deprecated, so name the fields. In the scratch project with 30 books, the change list ran 11 queries both with the default and with list_select_related = ["author"], and 36 with list_select_related = [], which is the N+1 problem in one number. ModelAdmin ignores the option if the changelist queryset already called select_related().

Filters, facets, search and date drill-down

list_filter adds the right-hand sidebar. A plain field name gives the filter that matches the field type (BooleanField, CharField with choices, DateField, DateTimeField, IntegerField, ForeignKey, ManyToManyField), lookups across relations work, and a tuple (field, FilterClass) picks a filter explicitly. Custom list filters shows how to write your own. get_list_filter(request) makes the list dynamic.

Facets (Django 5.0) show the number of rows behind each filter choice, updating as filters are applied. show_facets takes a ShowFacets value: ALLOW (the default: counts appear when the user toggles them on, which adds _facets to the query string), ALWAYS (as in BookAdmin) and NEVER. Each filter costs extra queries, which matters on big tables: the 30-book change list ran 11 queries with ALLOW and 35 with ALWAYS.

search_fields adds the search box. Terms are split on spaces (a quoted phrase stays together); every term must match at least one field, and the default lookup is icontains. A field name can carry any lookup (isbn__exact, price__exact) and can follow relations (author__name). The old one-character prefixes still work: ^ for istartswith, = for iexact, @ for the search lookup. search_help_text (4.0) shows a hint below the box, and get_search_fields() and get_search_results() customise it. On 6.1 a term that is not valid for a field with an explicit lookup, such as hello for price__exact, is skipped for that field instead of raising an error; on 5.2 drop non-text lookups from search_fields or override get_search_results().

date_hierarchy names a DateField or DateTimeField (it may follow a relation, author__pub_date) and adds drill-down links above the list. With USE_TZ = True it relies on QuerySet.datetimes(), so the current time zone matters.

Custom list filters

SimpleListFilter is the base class for a filter that is not a field. It needs a title (the sidebar heading) and a parameter_name (the query-string key), a lookups(request, model_admin) method that returns (value, label) pairs (the filter is hidden when lookups() returns nothing), and a queryset(request, queryset) method that applies self.value(). Both methods receive the request, so a filter can depend on the user, and lookups() receives the model_admin, so it can offer only choices that match existing rows.

A rating-band filter based on the annotated average (catalog/admin.py)
class RatingBandFilter(admin.SimpleListFilter):
    title = "rating"
    parameter_name = "rating_band"

    def _bands(self, queryset):
        # Relies on the avg_rating annotation added by BookAdmin.get_queryset().
        return {
            "top": ("4 or better", queryset.filter(avg_rating__gte=4)),
            "mixed": ("below 4", queryset.filter(avg_rating__lt=4)),
            "none": ("no reviews yet", queryset.filter(avg_rating__isnull=True)),
        }

    def lookups(self, request, model_admin):
        # Only offer the bands that match at least one visible book.
        queryset = model_admin.get_queryset(request)
        return [
            (key, label)
            for key, (label, rows) in self._bands(queryset).items()
            if rows.exists()
        ]

    def queryset(self, request, queryset):
        if self.value() in ("top", "mixed", "none"):
            return self._bands(queryset)[self.value()][1]
        return queryset

The built-in field filters need to be opted into with a (field, FilterClass) pair. BookAdmin uses two of them:

The change form: fields, layout and widgets

When neither fields nor fieldsets is set, the form shows every editable non-AutoField field in model order, followed by the readonly_fields. Use:

  • fields for simple layouts: a subset or different order; wrap names in a tuple to put them on one line ([("price", "isbn")]). exclude removes fields from the generated form. When a ModelForm and the ModelAdmin both define exclude, the admin’s wins.

  • fieldsets for sections: a list of (title, options) pairs, where options has fields (required), classes (collapse for an initially collapsed section) and description. Fieldset descriptions are not HTML-escaped, so escape user-controlled text with django.utils.html.escape(). The wide class was removed in 6.1 because the new layout made it obsolete. TabularInline supports only the fields key of a fieldset.

  • readonly_fields for values that are shown but not edited: model fields, model methods and ModelAdmin methods (decorated with @admin.display). Read-only fields are excluded from the form, are added last when fields is not set, and are ignored when fields or fieldsets is set and does not list them.

  • prepopulated_fields maps a slug field to its sources and fills it with JavaScript while the object is new. It does not accept DateTimeField, ForeignKey, OneToOneField or ManyToManyField, and it never rewrites a saved slug, so URLs do not change.

  • autocomplete_fields replaces the <select> of a ForeignKey or ManyToManyField with a Select2 box that loads options as you type. The related model’s admin must define search_fields, and the user needs the view or change permission on the related model, otherwise the autocomplete URL answers 403. The related admin’s get_ordering() and get_paginator() shape the results (system checks admin.E039 and admin.E040 catch the missing pieces).

  • raw_id_fields shows a plain input for the primary key plus a lookup popup, the cheapest widget for a table with millions of rows. It needs the related model registered on the same site to show the lookup.

  • radio_fields renders a ForeignKey or a field with choices as radio buttons (admin.VERTICAL or admin.HORIZONTAL); filter_horizontal and filter_vertical give a many-to-many field the two-box chooser.

  • formfield_overrides maps a field class (not a string) to extra form-field arguments, such as a widget for every TextField. It cannot change the widget of a relation field that is in raw_id_fields, radio_fields or autocomplete_fields.

  • form swaps in your own ModelForm for custom validation. Omit Meta.model (the admin supplies it), or set Meta.fields = []; Meta.fields is ignored anyway because the admin has its own way to choose fields.

  • save_as replaces "Save and add another" with "Save as new"; save_as_continue=False sends the user to the list afterwards. save_on_top repeats the save buttons above the form.

  • view_on_site controls the "View on site" link: True (the default) uses get_absolute_url(), False hides it, and a callable that takes the object returns any URL.

  • delete_confirmation_max_display (new in 6.1) truncates the list on the delete-confirmation page, a display-only limit that is useful when deleting one object cascades to thousands.

  • The add_form_template, change_form_template, change_list_template, delete_confirmation_template, delete_selected_confirmation_template, object_history_template and popup_response_template attributes point at alternative templates; the techniques are in Admin Customization.

Inlines

An inline edits rows of a related model on the parent’s page. TabularInline (a table, compact) and StackedInline (a block per row) differ only in the template. Both are InlineModelAdmin subclasses, so most ModelAdmin options (fields, fieldsets, readonly_fields, raw_id_fields, autocomplete_fields, prepopulated_fields, ordering, formfield_overrides, form, the formfield_for_* hooks and the permission methods) work in them.

Option Effect

model

Required: the model of the inline.

fk_name

The foreign key to the parent. Required only when the model has more than one foreign key to the same parent.

formset

A BaseInlineFormSet subclass for custom formset logic; inlines are model formsets.

form

A ModelForm for custom validation. Be careful with validation that depends on the parent: the parent may have failed validation.

extra, max_num, min_num

Extra empty forms (default 3), the maximum and the minimum number of forms. get_extra(), get_max_num() and get_min_num() make them dynamic. JavaScript adds an "Add another" link until max_num is reached.

can_delete

Whether rows can be deleted from the inline (default True).

show_change_link

Adds a link to the row’s own change form (default False).

classes, template

Extra CSS classes (collapse collapses the inline) and an alternative template.

verbose_name, verbose_name_plural

Override the model’s names; the plural defaults to the singular plus s.

has_add_permission(request, obj), has_change_permission(), has_delete_permission()

Per-inline permissions; obj is the parent object (or None when the parent is being added).

Points to remember when writing inlines.

  • Inlines do not go through save_model(). The parent form is saved by save_model(), the inline rows by save_formset(); stamp inline objects there, as AuthorAdmin.save_formset() does. When formset.save(commit=False) is used, deleted objects are in formset.deleted_objects and must be deleted by hand.

  • The "extra" forms are ignored when the inline has no add permission. The ReviewInline test posts an extra review form and asserts that nothing is created.

  • Several foreign keys to one parent need fk_name. Without it the system check fails with admin.E202 ("has no ForeignKey to…​" or "has more than one ForeignKey to…​").

  • Many-to-many fields can be edited as inlines on the through table. The example below edits a genre’s books with an inline on Book.genres.through (and, on the other side of the relation, would exclude the genres field of BookAdmin so the field does not appear twice). Because the admin sees only a model with two foreign keys, the m2m_changed signal is not sent when rows are added or removed this way.

  • A model with an intermediary through model has no widget by default; an inline on the intermediary model (with extra = 1, for example) is the way to edit its extra columns.

  • Generic relations use GenericTabularInline or GenericStackedInline from django.contrib.contenttypes.admin.

  • get_inline_instances() must return instances of the classes listed in inlines. Otherwise adding related objects answers "Bad Request".

Actions

An action is a function called with the admin, the request and the queryset of the rows selected on the change list. Django ships "Delete selected objects"; the actions option adds yours. Write the function (or a ModelAdmin method) with the @admin.action decorator (Django 3.2), which sets the attributes the admin reads.

Argument Effect

description

The label in the drop-down. It supports %(verbose_name)s and %(verbose_name_plural)s placeholders. Defaults to the function name with underscores replaced by spaces.

permissions

A list of permission names; the action is offered only if the user passes at least one check. "add", "change", "delete" and "view" map to the has_<name>_permission() methods; any other name needs a has_<name>_permission(self, request) method you write.

description_plural (6.1)

The label used in the change list; defaults to description. Useful when the same action also appears on the change form.

location (6.1)

Where the action is available: ActionLocation.CHANGE_LIST (the default), ActionLocation.CHANGE_FORM, or a list of both. On the change form, unsaved edits are lost when an action runs.

Key rules from the documentation:

  • Actions are listed by name in actions: a string names a ModelAdmin method, a function reference names a function. actions = None disables every action for that admin, including the site-wide ones.

  • An action returns None (the user returns to the list), or an HttpResponse: a file download, or a redirect to an intermediate view that receives the selected ids. The built-in delete action does the latter for confirmation.

  • Report what happened with self.message_user(), and handle foreseeable errors there instead of letting them become a 500.

  • queryset.update() is the fast way to change many rows, but it does not call save() and sends no pre_save or post_save signals. Iterate and call save() when those matter.

  • The delete selected action calls QuerySet.delete(), which does not call each model’s delete() method. Override delete_queryset() or write your own action when you need that.

  • The admin does not check object-level permissions for the selected rows. If it matters, check self.has_change_permission(request, obj=obj) inside the action.

Permissions in the admin

Authorisation in the admin has four layers, from the coarsest to the finest. A staff member passes every layer that applies, and superusers pass all of them.

  1. Entry: AdminSite.has_permission(request) requires is_active and is_staff. A non-staff user is redirected to the login page; an anonymous user too. This check cannot be bypassed by a model permission.

  2. Model permissions. Each model gets add, change, delete and (since Django 2.1) view permissions when migrate runs (catalog.view_book and so on), plus any in Meta.permissions (the catalog.publish_book of the Bookshelf). They are assigned to users or to groups. A user with only the view permission can open the change list and a read-only change form; the change permission implies the ability to view. The index page lists only the models for which the user has at least one permission, and a staff user without any permission on a model gets 403.

  3. Rules in code: has_view_permission(request, obj=None), has_add_permission(request), has_change_permission(request, obj=None) and has_delete_permission(request, obj=None). They default to the model permissions and are the place for business rules (for example, published books cannot be deleted). When obj is None the question is "in general", for the list and the "add" button. has_module_permission(request) only hides the app on the index; it does not protect the views behind it.

  4. Which rows: get_queryset(request) restricts what a user sees and edits (a queryset filtered by owner, for example). It is the only layer that is about rows rather than about operations.

The BookAdmin shows three rules: the custom publish permission (used by the actions and to make status read-only for everyone else), the rule that a published book cannot be deleted (it must be withdrawn first), and the copy-not-mutate pattern for get_readonly_fields().

Things the admin does not do for you.

  • Object-level permissions are not visibility filters. has_view_permission(request, obj) stops someone opening one object, but the object can still appear in the change list, in related-field choices, in autocomplete results and in the "recent actions" panel. Restrict those by customising the querysets (get_queryset(), formfield_for_foreignkey()).

  • list_editable, actions and inlines have their own paths. A field made editable in the list can be changed by anyone with the change permission, so a "publish" rule must not rely on a field being editable in the form only (the example removes status from list_editable and makes it read-only without the permission).

  • Action permissions are checked per model, not per selected object. The built-in "delete selected" action does ask has_delete_permission(request, obj) for the selected objects (the test shows the "Cannot delete" page), but a custom action must call has_change_permission(request, obj=obj) itself.

  • The user must have a permission on the related model for autocomplete. A staff user with view_book but not view_author gets 403 from the author autocomplete.

  • Superusers pass every model-permission check (has_perm() is always true for them), but code you add in has_*_permission() still applies to them: the "published books cannot be deleted" rule blocks superusers too, as the "delete selected" test shows. Keep superuser accounts few, and use groups for everyone else.

  • The "view" permission was added in 2.1. A custom permission whose codename looks like view_<model> accidentally grants view access to the list and detail pages since then.

Row scoping is usually done with a proxy model: the proxy has its own admin page and its own four permissions (catalog.view_mybook, catalog.change_mybook, …​), and its admin filters the queryset by the current user. The MyBookAdmin shown with the CSV helper above does it in four lines. An object outside the queryset is not found, so the admin answers with the redirect it uses for a missing object (the user never learns whether it exists).

Groups are the natural way to assign permissions to roles: an "Editors" group with view_book and change_book, a "Publishers" group that adds publish_book. The tests create users with exactly the permissions they need, which is also the best way to document and verify your policy.

The audit trail: LogEntry

Every add, change and delete done through the admin writes a LogEntry (django.contrib.admin.models.LogEntry: action_time, user, content_type, object_id, object_repr, action_flag, change_message). The "History" link of an object lists them (paginated since 4.1) and the admin index shows the "Recent actions" of the user. A site can filter the log shown on its index by overriding AdminSite.get_log_entries() (5.0). The log is written only by admin views: changes made in a shell, a management command or a public view leave no entry, and a custom action that uses queryset.update() writes no entries unless it creates them itself.

Sync and async

The admin is synchronous. ModelAdmin and AdminSite methods, the formsets and the templates are all blocking code, and there is no async variant of any hook. That is fine under ASGI: Django runs a synchronous view in a worker thread and the admin works unchanged. Two practical consequences:

  • Write hooks as ordinary def methods; the admin calls them synchronously. If an action must call async code, wrap the call with asgiref.sync.async_to_sync, as the Django async documentation describes, and keep it short: the admin request holds a worker thread while it waits.

  • A server that only speaks ASGI does not serve static files. Under uvicorn the admin pages rendered (the change list answered 200) but the admin CSS and JavaScript were a 404, whereas runserver serves them. In production serve the static files with WhiteNoise, the web server or a CDN (see Static Files & Front-end Assets).

Pitfalls

Symptom Cause Fix

The change list is slow and runs one query per row

A ForeignKey column or a callable that touches a relation, without select_related().

Name the fields in list_select_related, or annotate in get_queryset(); never use True (deprecated in 6.1).

The change list is slow with many filters

Facet counts run extra queries (24 more with six filters in the scratch project), and "full result count" is a second COUNT(*).

show_facets = admin.ShowFacets.NEVER (or the default ALLOW) and show_full_result_count = False.

Search is slow

icontains on unindexed columns, or a leading wildcard that no index can use.

Search fewer fields, use ^/istartswith on indexed columns, or override get_search_results() with full-text search (PostgreSQL SearchVector) or an external engine.

UnorderedObjectListWarning for a model with Meta.ordering

annotate() with an aggregate drops Meta.ordering from the query.

Set ordering on the ModelAdmin, as AuthorAdmin does.

A custom column is not sortable

Callables are not database fields.

@admin.display(ordering="field") (or an annotation, as average_rating does).

readonly_fields entry does not show

fields or fieldsets is set and does not list it.

Add the name to fields or fieldsets.

Added fields pile up request after request

A get_*() hook mutates the list returned by super().

Build a copy: [*super().get_readonly_fields(request, obj)].

save_model() seems to ignore a veto

save_model() and delete_model() are not validation hooks; they must still save and delete.

Validate in the form (clean()), or raise ValidationError there.

added_by is empty for objects created through an inline

Inlines are saved by save_formset(), not by save_model().

Override save_formset() as the author page does.

Bulk status change leaves updated_at or signals untouched

queryset.update() does not call save() and sends no signals.

Loop and save(update_fields=[…​]), or update the timestamp explicitly.

"Delete selected" does not run my delete() method

It uses QuerySet.delete().

Override delete_queryset(), or replace the action.

A user sees objects they should not in lists and dropdowns

Object-level has_view_permission() is not a visibility filter.

Scope get_queryset() and formfield_for_foreignkey().

403 on an autocomplete field

The user has no view or change permission on the related model.

Grant view_<related>, or drop the field from autocomplete_fields.

400 "Bad Request" when filtering by a query parameter

lookup_allowed() rejects lookups that are not local fields or list_filter paths.

List the field in list_filter, or override lookup_allowed() for that one lookup.

AlreadyRegistered at start-up

The model is registered twice, often because another app already registers it (User, Group).

admin.site.unregister(Model) first.

Markup in a column shows as text

The callable output is escaped.

Return format_html(); never mark_safe() on user input.

Admin pages unstyled in production

Static files are not served by an ASGI or WSGI server.

collectstatic plus WhiteNoise, a web server or a CDN.

An error when a non-numeric term is searched on 5.2

A price__exact-style lookup in search_fields receives text that is not a number; 6.1 skips such terms.

On 5.2 override get_search_results(), or search text fields only.

Operational advice from the documentation and from practice: the admin is a tool for trusted staff, not a front end. It is a model-centric interface, and the more of your business process you force through its hooks the more you fight it. When users need a task-oriented screen, write a view instead and keep the admin for curation. See Admin Customization for the reasoning and for securing the site.

Where the books are outdated

The four books this section cross-checks were written for Django 1.11 to 2.1, and their admin chapters show their age in four places. The first is syntax: columns are configured by setting attributes on functions (short_description, admin_order_field, boolean) instead of @admin.display, and actions the same way instead of @admin.action. Both forms still work, but the decorators (3.2) are the documented ones and are the only way to configure a property column. The second is permissions: Django 1.11 and 2.0 predate the view permission (2.1), so advice that treats "can see in the admin" and "can change" as the same thing no longer holds; a read-only auditor group is a one-permission change today. The third is features that did not exist: list_display through related__field (5.1), facets (5.0), AdminSite.get_model_admin() (5.0), the 6.1 action locations and ActionLocation, and the fact that allow_tags (removed in 2.0) is gone, so markup in a column must go through format_html(). The fourth is hardening: the books' guidance to build custom admin pages with staff_member_required still works, but AdminSite.admin_view() (shown in Admin Customization) is the supported wrapper because it also adds never_cache and CSRF protection, and a chapter that marks user-supplied Markdown safe with mark_safe() is an XSS bug, not a pattern. What the books got right and still holds: the admin is for trusted staff and not an end-user UI, list_display, list_filter, search_fields, prepopulated_fields, raw_id_fields, date_hierarchy, inlines, admin actions and the get_urls() plus admin_view() pair for internal dashboards are all current.
