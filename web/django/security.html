Security

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Django 6.1 (6.1.1, released 2026-09-02; 6.1.2 is a security release scheduled for 2026-10-06), Python 3.12-3.14 and PostgreSQL 15 or newer, all checked on 2026-10-03; where the 5.2 LTS (5.2.17) behaves differently the text says so. Every example was built and run on that stack in a scratch project (SQLite, the Django test client, the runserver development server and curl, and django-cors-headers 4.9.0); none needs PostgreSQL or Redis. Django ships with defences against the common web attacks, but most of them only work if the project keeps the middleware enabled, uses the template and ORM APIs as designed and sets a handful of deployment settings; this page explains each protection, where it sits in the request/response cycle, which setting controls it, how it fails, and how to test it in the Bookshelf application (the catalog app built across this section). It ends with the deployment checklist (check --deploy) and with Django’s own security policy, because keeping the framework patched is a security control too.

Where each protection runs in the request cycle

Almost every built-in protection is a middleware, so the order of MIDDLEWARE is part of the security configuration (see Middleware for the onion model and The Request/Response Cycle for the full path). The diagram follows a request into the Bookshelf and back out, with the stack shown in The middleware list, with the third-party CORS layer placed before CommonMiddleware (config/settings.py).

flowchart TD R["HTTP request"] --> S1["SecurityMiddleware: HTTPS redirect"] S1 --> SE["SessionMiddleware"] SE --> CO["CorsMiddleware (third party): preflight answer"] CO --> CM["CommonMiddleware: get_host() checks ALLOWED_HOSTS"] CM --> CS["CsrfViewMiddleware.process_view: token and Origin check"] CS --> AU["AuthenticationMiddleware"] AU --> V["View: form validation, ORM parameters, template escaping"] V --> X["XFrameOptionsMiddleware: X-Frame-Options"] X --> CS2["CsrfViewMiddleware: set csrftoken cookie"] CS2 --> CO2["CorsMiddleware: Access-Control-* headers"] CO2 --> S2["SecurityMiddleware: HSTS, nosniff, Referrer-Policy, COOP"] S2 --> RESP["HTTP response"]

HTTPS redirect (SECURE_SSL_REDIRECT)

SecurityMiddleware, on the way in

Answers 301 to the https:// URL without calling the rest of the stack.

DisallowedHost is raised and Django answers 400, logging to django.security.DisallowedHost.

403 through CSRF_FAILURE_VIEW, logged to django.security.csrf; the view never runs.

When the view first reads request.body or request.POST

SuspiciousOperation subclass, turned into a 400.

Auto-escaping, parameterised queries, form validation

Inside the view, in the template engine, the ORM and the forms

Escaped output, bound parameters, is_valid() returning False.

X-Frame-Options

XFrameOptionsMiddleware, on the way out

Not applicable: it only adds the header when the response lacks one.

HSTS, nosniff, Referrer-Policy, Cross-Origin-Opener-Policy

SecurityMiddleware, on the way out

Not applicable: each header is added only if the response lacks it.

Two consequences follow from that layout. First, a response produced by a layer above another (a CORS preflight, an HTTPS redirect) never reaches the layers below it, so those layers' protections do not apply to it, and the layers above can only add headers to what comes back. Second, protections that live in the front-end web server (HTTPS redirect, size limits, Host validation, security headers) also cover the requests Django never sees, such as static files and media, which is why the documentation recommends doing them there when you can and treating Django’s versions as the fallback.

The Bookshelf security setup used on this page

The examples share one small project. The key is read from the environment and never committed; DJANGO_SECRET_KEY can be generated once with python -c "from django.core.management.utils import get_random_secret_key as g; print(g())".

The settings that every example relies on (config/settings.py, excerpt)
# The key never lives in source control: it is read from the environment.
SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]
DEBUG = os.environ.get("DJANGO_DEBUG", "0") == "1"
ALLOWED_HOSTS = os.environ.get("DJANGO_ALLOWED_HOSTS", "localhost,127.0.0.1").split(",")

Always sanitize user input

The golden rule of the security overview is that user-controlled data is never trusted. Django’s tool for that is the forms framework: declare the shape of valid data once, call is_valid(), and use only cleaned_data. Anything that arrives in request.GET, request.POST, request.body, request.FILES, cookies, headers, the URL and even data from web services or the database that a user once supplied is input. Cross-site scripting (XSS)

In an XSS attack, script written by an attacker runs in another user’s browser with that user’s privileges: it can read the page, send requests as the user and read anything not marked HttpOnly. The script reaches the victim either stored (a review body saved in the database and shown to every reader) or reflected (a crafted link whose query string is echoed by the page). In Django the primary defence is automatic escaping in the template engine, and the common ways to lose it are mark_safe(), the safe filter, autoescape off, HTML stored in the database and unquoted attributes.

Auto-escaping

The Django template language escapes <, >, ', " and & in every variable it renders, so attacker-supplied markup is shown as text. The protection is for HTML output; if you render something else (JSON, JavaScript, CSV, a plain-text email) with the template engine, the characters that need escaping are different and auto-escaping is not enough. The template side of escaping is covered on Templates and Custom Template Tags and Filters (the is_safe and needs_autoescape flags of custom filters).

The escape hatches and how to use them safely

mark_safe(), the safe filter and {% autoescape off %} all tell Django "this string is already safe". They are promises, not filters: nothing is checked. A safe string built by interpolating user input is exactly the bug the template engine exists to prevent. format_html() is the correct way to build a small HTML fragment in Python: the format string is trusted, every argument is escaped with conditional_escape() first, and only the final result is marked safe. format_html_join() does the same for a list of fragments (since 5.2 it also accepts an iterable of mappings that become keyword arguments), conditional_escape() avoids double escaping, and escape() is the plain function for text going into HTML.

        from django.utils.html import escape
        from django.utils.safestring import mark_safe

Defence in depth: HttpOnly cookies and a Content Security Policy

Two settings reduce what an XSS bug can do. SESSION_COOKIE_HTTPONLY is True by default, which hides the session cookie from JavaScript. A Content Security Policy tells the browser which sources of script, style and frames are allowed, so injected inline script is blocked even when escaping failed; it is built into Django since 6.0 and described on Content Security Policy. Neither replaces escaping, and the documentation warns against excluding paths from the policy because a hole on one page can be used to attack the protected ones (same-origin policy).

Cross-site request forgery (CSRF)

A CSRF attack makes a logged-in user’s browser send a request the user did not intend, for example a hidden form on an attacker’s page that posts to /reviews/new/; the browser attaches the session cookie automatically, so the site cannot tell the request from a real one. Django’s defence has three parts: safe methods must be side-effect free, unsafe methods must carry a secret that the attacker’s page cannot read, and the Origin (or, on HTTPS, Referer) header must come from a trusted origin.

How the protection works

  • A random secret is stored in the csrftoken cookie (or in the session, with CSRF_USE_SESSIONS). The middleware sets it whenever get_token() is called, for example by the {% csrf_token %} tag, and the secret changes every time a user logs in.

  • The {% csrf_token %} tag renders a hidden csrfmiddlewaretoken field. To defeat BREACH attacks the field is the secret scrambled with a new random mask on every call, so its value differs on every response.

  • For every request whose method is not GET, HEAD, OPTIONS or TRACE, CsrfViewMiddleware.process_view requires the cookie and either the csrfmiddlewaretoken form field or the X-CSRFToken header (named by CSRF_HEADER_NAME, whose default is 'HTTP_X_CSRFTOKEN'); a missing or wrong token gives a 403.

  • If the browser sent an Origin header it must match the request’s own origin or CSRF_TRUSTED_ORIGINS. For a secure (HTTPS) request without Origin, the Referer must match the host or a trusted origin. Both checks close the cross-subdomain and man-in-the-middle holes of a cookie-only scheme.

The protection is not linked to a session by default, which is deliberate: it also works for anonymous submissions. Rejected requests are logged as warnings to the django.security.csrf logger.

Decorators for the edge cases

Decorator Use

csrf_exempt

Opts a view out of the middleware’s check. Reserve it for endpoints called by servers, not browsers, and authenticate them another way (the webhook view above verifies an HMAC signature with hmac.compare_digest).

csrf_protect

Applies the middleware’s check to one view. Use it as belt and braces when the middleware might be removed, and in reusable apps (the contrib apps do), and below cache_page so the cached response keeps the cookie and Vary: Cookie.

requires_csrf_token

Makes the tag work in a view where process_view did not run (404 and 500 handlers) without ever rejecting a request.

ensure_csrf_cookie

Forces the cookie to be sent from a view that renders no form.

Combining them follows one rule: csrf_exempt followed by requires_csrf_token (innermost) gives an unprotected view that can still render a token. Since Django 5.0 all four decorators also wrap async def views, which AsyncCsrfTests above checks: an async view protected by csrf_protect rejects a token-less post with 403.

Limitations and pitfalls

  • Any subdomain can set cookies for the whole domain, so a subdomain controlled by an untrusted party can defeat CSRF protection (and enables session fixation); do not give untrusted users subdomains.

  • CSRF protection assumes there is no XSS on the site, valid Host headers and HTTPS with HSTS, because it cannot defend against man-in-the-middle attacks.

  • Referrer-Policy: no-referrer (or a no-referrer meta tag) removes the header that strict Referer checking needs on HTTPS, so every unsafe request starts failing; use rel="noreferrer" on third-party links instead.

  • The first request after a login can fail with a CSRF error from a page loaded before the login, because the secret is rotated at login (back button, a second tab); reload the page.

  • Posting an arbitrary cookie and token pair is not a vulnerability by design, since only a man-in-the-middle could plant the cookie.

  • Django REST framework’s SessionAuthentication enforces CSRF itself, and Django Ninja’s cookie-based authentication classes check it by default, while header-token authentication does not need it; see the API pages of this section.

SQL injection

SQL injection happens when user input becomes part of the SQL text instead of a value, letting the attacker change the query. Querysets are protected because the query is built with parameterisation: the SQL text and the parameters travel separately and the driver escapes the parameters. The risk returns with the raw-SQL features and with a few places where the client chooses a field name rather than a value.

API Rule

filter(), exclude(), get(), Q, F

Safe for values. Never expand a client-supplied dictionary into keyword arguments (filter(**request.GET.dict())): the key is a lookup path, so a client could filter on authorpasswordstartswith and learn hashes one character at a time.

order_by(), values(), only()

Safe for values but the field name comes from the client: map it through an allow-list, otherwise clients can sort by (and so infer) related or sensitive fields.

Manager.raw()

Put values in the params argument and use %s placeholders without quotes; dictionary params use %(name)s and are not supported by SQLite.

connection.cursor().execute()

Same: execute(sql, [params]); never format the SQL with % or f-strings.

QuerySet.extra() and RawSQL

Full control over the SQL, so insecure with unsanitised input; the documentation says to use them sparingly, and the security team treats unsanitised use as the developer’s bug. Prefer expressions and annotations.

Keyword arguments of database functions and aggregates

Some are passed to the SQL; treat them as code, not data.
Safe queries and the client-chosen names allow-listed (excerpt of catalog/views.py)
SORTABLE = {"title": "book", "rating": "rating"}
FILTERABLE = {"book__icontains", "rating__gte"}


def search(request):
    term = request.GET.get("q", "")
    # ORM: the value travels as a bound parameter, never inside the SQL text.
    reviews = Review.objects.filter(book__icontains=term)

    # Never pass a client-chosen field name straight to order_by() or filter():
    # map it through an allow-list.
    sort = SORTABLE.get(request.GET.get("sort", ""), "book")
    reviews = reviews.order_by(sort)

    extra = {k: v for k, v in request.GET.items() if k in FILTERABLE}
    reviews = reviews.filter(**extra)
    return JsonResponse({"books": [r.book for r in reviews]})


def search_raw(request):
    term = request.GET.get("q", "")
    # Raw SQL is fine when the value goes through `params`.
    reviews = Review.objects.raw(
        "SELECT * FROM catalog_review WHERE book = %s", [term]
    )
    return JsonResponse({"books": [r.book for r in reviews]})

Clickjacking

In a clickjacking attack a malicious page loads your site in a transparent iframe and lines up a button of yours under a button of its own, so the user’s click performs an action on your site. Browsers honour the X-Frame-Options response header: DENY forbids framing, SAMEORIGIN allows only your own pages to frame it. XFrameOptionsMiddleware adds it to every response that does not already carry one, and it is in the startproject template. The default value comes from X_FRAME_OPTIONS, which defaults to 'DENY'.

Three decorators change the header per view and override the middleware: xframe_options_deny, xframe_options_sameorigin and xframe_options_exempt (which tells the middleware not to add the header, for widgets that other sites must frame). If a form inside a frame must post, or a session cookie must be sent from inside it, you may also need to loosen CSRF_COOKIE_SAMESITE or SESSION_COOKIE_SAMESITE. The decorators wrap async views since 5.0. The header only protects in modern browsers; the Content Security Policy frame-ancestors directive is its modern complement.

@xframe_options_sameorigin

HTTPS, HSTS and security headers with SecurityMiddleware

Without HTTPS an attacker on the network can read credentials and session cookies and alter responses. Any site that lets users log in should enforce HTTPS site-wide (the same session cookie travels over HTTP and HTTPS, so protecting only the login or admin pages is not enough). django.middleware.security.SecurityMiddleware does the Django-side part and should be the first entry of MIDDLEWARE; it is both a request and a response layer (see Where each protection runs in the request cycle). Rolling HSTS out safely

HSTS applies to the whole domain, not just the URL that carried the header, and browsers will not let users click through an expired or self-signed certificate once it is cached. Start with SECURE_HSTS_SECONDS = 3600, confirm that every asset and every subdomain you included works over HTTPS, then raise the value (31536000, one year, is common); add includeSubDomains and preload last, because preloading is hard to undo.

Behind a reverse proxy

When TLS ends at a proxy, Django sees plain HTTP: request.is_secure() is False, SECURE_SSL_REDIRECT redirects forever and HSTS is never sent. SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https") tells Django which header to believe (written as in request.META; since 4.1 a comma-separated list is accepted and the leftmost value is used). It is only safe if all of these are true: the app is behind a proxy, the proxy removes that header from every incoming request (including comma-separated forms) and sets it only for requests that arrived over HTTPS. If any is not true, leave the setting None; an attacker who can send the header can make Django treat plain HTTP as secure, which weakens CSRF checks. The test test_proxy_header shows both states: with the header and no setting the redirect still happens, with the setting it does not.

USE_X_FORWARDED_HOST (default False) makes Django prefer X-Forwarded-Host over Host, and USE_X_FORWARDED_PORT does the same for the port; enable them only behind a proxy that sets them, and the host is then still validated against ALLOWED_HOSTS.

Host header validation and ALLOWED_HOSTS

Django builds absolute URLs (password-reset links, redirects, request.build_absolute_uri()) from the Host header. The header is client-controlled, so a forged value can poison links in emails, caches and CSRF checks. Even a web server that looks like it validates the header often does not (a request can match a default virtual host and still carry a fake Host), so Django validates it itself in HttpRequest.get_host() against ALLOWED_HOSTS, and a mismatch is a SuspiciousOperation that Django turns into a 400 and logs to django.security.DisallowedHost.

Entry Matches

'www.bookshelf.example'

That exact host, case-insensitively, ignoring the port.

'.bookshelf.example'

The apex bookshelf.example and every subdomain.

'*'

Anything; you are then responsible for validating the header yourself, in a middleware placed first.

[] with DEBUG = True

Validated against ['.localhost', '127.0.0.1', '[::1]'].

[] with DEBUG = False

Every request fails with 400; Django does not work without a value.

A trailing dot in the header (some browsers send it) is stripped before matching. The setting is also checked when running tests, which is why the test client uses testserver (added automatically by the test runner, and the reason the @override_settings(ALLOWED_HOSTS=[…​]) test below sends its own Host). Code that reads request.META["HTTP_HOST"] directly bypasses the validation: always call request.get_host().

User-uploaded files

Uploads are the largest attack surface of many sites: denial of service by size, code execution if the web server interprets the file, stored XSS if the browser renders it as HTML, path traversal through the file name. Django’s upload machinery (see File Uploads and Storage) helps, but the security overview is candid that no framework-level check can prove arbitrary content is safe.

Limit size and count

  • Limit the request body size in the web server (Apache LimitRequestBody, nginx client_max_body_size), because Django’s own limits are checked late: under ASGI the whole request may be spooled to disk before any size validation runs.

  • DATA_UPLOAD_MAX_MEMORY_SIZE (default 2.5 MB) caps the request body excluding file uploads, raising RequestDataTooBig when request.body or request.POST is read; form submissions containing files are not limited by it. DATA_UPLOAD_MAX_NUMBER_FIELDS (default 1000) caps parameters, and DATA_UPLOAD_MAX_NUMBER_FILES (default 100) caps files in a multipart request. FILE_UPLOAD_MAX_MEMORY_SIZE (default 2.5 MB) is the size above which an upload streams to a temporary file; it is not a limit.

  • Validate the size of each file in a validator too (see validate_cover_size below).

Tightened limits for the Bookshelf (config/settings.py, excerpt)
DATA_UPLOAD_MAX_MEMORY_SIZE = 1_000_000  # bytes of non-file request body
DATA_UPLOAD_MAX_NUMBER_FIELDS = 500
DATA_UPLOAD_MAX_NUMBER_FILES = 10
FILE_UPLOAD_MAX_MEMORY_SIZE = 1_000_000  # larger uploads are streamed to disk

Validate extension and content, and never trust the name

FileExtensionValidator checks the extension, ImageField makes Pillow verify the bytes are an image, and the model or form should also check the size. A random stored name, built from uuid4, removes both path-traversal and name-collision attacks and keeps client-chosen characters out of URLs and headers; Django’s storage also refuses paths that escape the storage root with SuspiciousFileOperation.

Serve uploads defensively

  • Never serve media from the Django project’s own origin if you can avoid it. Serving it from a distinct top-level or second-level domain (usercontent-example.com, not usercontent.example.com) keeps the browser’s same-origin policy between uploaded content and your application, so a rendered polyglot cannot read your cookies or call your API.

  • Make sure the web server never interprets uploads (the Apache mod_php case): a .php file in MEDIA_ROOT must be downloaded or refused, never executed.

  • Keep SECURE_CONTENT_TYPE_NOSNIFF on (it is the default) so the browser trusts the Content-Type; configure the same header in the front server if it serves MEDIA_URL directly.

  • Restrict the allowed extensions and configure the web server to serve only those.

  • For files that need authorisation, stream them through a view with FileResponse(…​, as_attachment=True), which sends Content-Disposition: attachment so the browser saves the file instead of rendering it.

  • FILE_UPLOAD_PERMISSIONS defaults to 0o644 and FILE_UPLOAD_DIRECTORY_PERMISSIONS to None (operating-system dependent); set them deliberately on shared hosts.

A defensive download view (excerpt of catalog/views.py)

Mass assignment

Mass assignment happens when a form or serializer binds every field a client sends to a model, so a reader can set featured=on, is_staff=on or author=1 simply by adding a parameter. In Django the cause is almost always a ModelForm whose Meta uses fields = "all" or exclude, and a Django REST framework serializer with fields = "all". The fix is an explicit allow-list of fields, and server-side assignment of everything the user must not choose.

The safe form (catalog/forms.py)
from django import forms

from .models import Review


class ReviewForm(forms.ModelForm):
    class Meta:
        model = Review
        # An explicit allow-list: `featured` and `author` can never be set
        # by a request, whatever extra POST fields an attacker adds.
        fields = ["book", "rating", "body"]

    def clean_rating(self):
        rating = self.cleaned_data["rating"]
        if not 1 <= rating <= 5:
            raise forms.ValidationError("Rating must be between 1 and 5.")
        return rating

The review_create view above saves with commit=False and sets review.author = request.user itself.

Mass assignment tests (catalog/tests.py)
class MassAssignmentTests(TestCase):
    def test_extra_fields_are_ignored(self):
        form = ReviewForm({"book": "Dune", "rating": 5, "featured": "on", "author": 1})
        self.assertTrue(form.is_valid())
        self.assertEqual(set(form.cleaned_data), {"book", "rating", "body"})
        self.assertFalse(form.instance.featured)

    def test_all_fields_would_expose_them(self):
        from django import forms

        class BadForm(forms.ModelForm):
            class Meta:
                model = Review
                fields = "__all__"

exclude is a deny-list, so a field added to the model next year is silently exposed; fields is an allow-list, so it is not. Django (since 1.8) refuses a ModelForm that sets neither, which is why fields = "all" has to be spelled out and is easy to find in a review. For APIs the same rule applies: list the serializer fields, mark server-owned fields read-only, and use different serializers for create and for staff; a viewset that returns every customer’s orders because nothing scopes its queryset is the same class of bug at the row level (see Permissions and Authorization and Model Forms and Formsets). Do not expose sequential primary keys for resources that need to stay private; authorise every object access, or use a non-guessable identifier in addition.

Open redirects and other input-driven requests

A login or logout view that redirects to a next parameter without checking it lets an attacker send users to a look-alike site from a link on your domain. django.utils.http.url_has_allowed_host_and_scheme(url, allowed_hosts, require_https=False) returns True only for relative URLs and absolute ones whose host is in allowed_hosts; it also rejects javascript: and protocol-relative //host URLs. Django’s own LoginView and LogoutView use it; use it in every view that redirects to client-supplied data. Pass require_https=request.is_secure() so a secure page cannot be redirected to plain HTTP. The function is named in the 3.0 release notes (where it replaced the private is_safe_url()) but is not listed in the utilities reference, so the signature and behaviour described here were checked against the 6.1.1 source and the test below rather than a reference page; treat it as a stable helper that the framework itself relies on.

A safe redirect (excerpt of catalog/views.py) and its test
def login_redirect(request):
    target = request.GET.get("next", "")
    if not url_has_allowed_host_and_scheme(
        url=target,
        allowed_hosts={request.get_host()},
        require_https=request.is_secure(),
    ):
        target = "/"
    return redirect(target)

Secrets, DEBUG and error pages

  • SECRET_KEY signs sessions (unless a cache-backed store is used), password-reset tokens, messages and signed cookies; a leaked key can lead to privilege escalation and remote code execution. It must be long, random, unique per environment and out of source control: read it from an environment variable or a file outside the repository, generate it with django.core.management.utils.get_random_secret_key(), and never reuse the django-insecure- value startproject writes.

  • SECRET_KEY_FALLBACKS (since 4.1) lets you rotate: set the new key as SECRET_KEY, keep the old one in the fallback list while old sessions and tokens age out, then remove it, because every verification that does not match the current key costs an extra signature check. check --deploy validates the fallbacks too (security.W025).

  • DEBUG must be False in production: the debug page leaks source excerpts, local variables, settings and installed libraries. Mark sensitive values with sensitive_variables and sensitive_post_parameters so they are hidden from error reports.

  • The database password and cache credentials are as sensitive as the key; keep the database and cache servers reachable only from the application servers (firewall), because cache servers often have weak authentication.

  • Custom 400.html, 403.html, 404.html and 500.html templates replace the default error pages.

  • Django does not throttle login attempts. Put a rate limit in the web server, use a third-party throttling or lockout app, and see Authentication and Passwords for the password side.

  • Keep the Python code outside the web server’s document root, and read the OWASP Top Ten for the issues the framework cannot solve for you (broken access control above all).

CORS with django-cors-headers

The browser’s same-origin policy stops a page on one origin from reading responses from another. Cross-Origin Resource Sharing (CORS) is the opt-in: the API answers with Access-Control-Allow-Origin and related headers. Django has no built-in CORS support; the community package django-cors-headers (4.9.0, PyPI classifiers up to Django 6.0, installed and run here with 6.1.1) is the usual choice. The protocol, the preflight and the common mistakes are explained on CORS; this section covers only the Django configuration.

$ python -m pip install django-cors-headers

Add "corsheaders" to INSTALLED_APPS and corsheaders.middleware.CorsMiddleware to MIDDLEWARE as high as possible, and in particular before any middleware that can generate responses, such as CommonMiddleware (and WhiteNoise’s middleware, if you use it), otherwise redirects and error responses lack the headers. The middleware answers preflight (OPTIONS with Access-Control-Request-Method) requests itself, so they never reach the view or CSRF middleware, and adds Vary: Origin to enabled responses.

CORS and CSRF solve different problems. CORS only controls which origins' scripts may read responses; it does not stop a cross-site form post, which the browser sends anyway. A cross-origin AJAX client that authenticates with the session cookie therefore needs all of: the origin in CORS_ALLOWED_ORIGINS, CORS_ALLOW_CREDENTIALS = True, the same origin in CSRF_TRUSTED_ORIGINS (with its scheme), an appropriate SameSite cookie setting and the X-CSRFToken header; the test_trusted_origin_is_accepted test above exercises the CSRF half. The middleware is both sync and async capable.

Logging security events

Security failures are logged to dedicated loggers: django.security.csrf for CSRF rejections and one django.security.<ExceptionName> logger per SuspiciousOperation subtype (DisallowedHost, RequestDataTooBig, TooManyFields, SuspiciousFileOperation, and so on). A SuspiciousOperation that ends in a 400 is logged to the security logger only, not to django.request. By default these events reach the django logger, which mails ADMINS when DEBUG is False; route them to your log pipeline and alert on spikes instead, and silence a noisy one with a NullHandler and propagate: False for that single logger name.

Sending the security loggers to a handler (config/settings.py, excerpt)
LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,
    "handlers": {"console": {"class": "logging.StreamHandler"}},
    "loggers": {
        "django.security": {"handlers": ["console"], "level": "WARNING"},
    },
}

The tests above use assertLogs("django.security.csrf"), assertLogs("django.security.DisallowedHost") and assertLogs("django.security.RequestDataTooBig") to assert that the events are emitted. Do not log secrets: request bodies, tokens and cookies must stay out of log records, and the include_html option of AdminEmailHandler sends full tracebacks with settings, so enable it only for trusted recipients.

Sync and async notes

  • Every middleware discussed here (SecurityMiddleware, CsrfViewMiddleware, XFrameOptionsMiddleware, CorsMiddleware) works in both a synchronous and an asynchronous stack; mixing a sync-only third-party middleware into an ASGI project forces a thread hop for the rest of the chain (see Middleware).

  • csrf_exempt, csrf_protect, ensure_csrf_cookie, requires_csrf_token and the xframe_options_* decorators can wrap async def views since 5.0; the AsyncCsrfTests test exercises one. login_required and its relatives gained the same support in 5.1.

  • Under ASGI the entire request body may be spooled to disk before DATA_UPLOAD_MAX_MEMORY_SIZE or any file validation is applied, so request-size limits belong in front of Django (the ASGI server or proxy) too.

  • The SQL-injection rules are the same in async code: the asynchronous queryset methods (aget(), acreate() and async for over a queryset) use the same parameterised queries, and calling the synchronous ORM from an async def view is a separate bug (it raises SynchronousOnlyOperation).

  • request.get_host() and ALLOWED_HOSTS behave the same on ASGI.

Django’s security policy and release process

Django treats security as a first-class release type, and an application inherits that only if it upgrades.

Reporting a vulnerability

Report suspected vulnerabilities privately to security@djangoproject.com (an optional PGP key is published), not on the public ticket tracker. You should get an acknowledgement within 3 working days, analysis can take weeks, and reports aim to be resolved within 90 days, faster for high-severity confirmed issues. Be mindful of volunteer time: send a brief description, a minimal working proof of concept, the Django and Python versions, and optionally a patch; leave out CVSS scores and long background, and wait for triage before sending more reports. The policy also states what is not a valid report:

  • failures to sanitise user input (the send_mail() and extra() examples above);

  • issues that only occur on an end-of-life Python or dependency, or only on runserver;

  • proof of concepts that need request headers or URLs over 8 KB, a request body over 2.5 MB, or DTL template content over 100 KB, because production servers and defaults already limit them;

  • code that calls private or undocumented functions directly, or needs uncommon or insecure management-command options;

  • unverified AI-generated reports: tools used must be disclosed and the issue must be real and reproducible, otherwise the report is closed.

Supported versions and severity

Security fixes go to the main development branch, to the two most recent release series and to any LTS. As of 2026-10-03 that means 6.1 (mainstream support until April 2027, extended to December 2027), 6.0 (until April 2027) and the 5.2 LTS (extended until April 2028). Severity follows the attack type: high for remote code execution and SQL injection, moderate for XSS, CSRF and broken authentication, low for denial of service, sensitive data exposure, broken session management, unvalidated redirects and issues needing an uncommon configuration, and the team may adjust a level (a default-configuration, unauthenticated denial of service can be raised to moderate).

How a release is announced, and what to do

About a week before disclosure, Django announces the date, time and severity on the django-announce list (subscribe to it, it is the notice for everyone, without the details); distributors get the details privately. On the day, the patch is applied, new releases are published on PyPI and the website, and the issue is described on the Django weblog and the django-announce and oss-security lists. The practical rules for a project are therefore:

  • subscribe to django-announce and watch the release schedule;

  • pin Django to a supported minor series and take every patch release immediately, because patch releases contain only fixes (the 6.1.2 release notes page already lists one low and three moderate security issues for 2026-10-06);

  • stay on a supported series: older releases are not investigated and receive no patches;

  • upgrade dependencies too (Pillow, the database driver, the ASGI server, DRF); security releases sometimes fix popular third-party packages;

  • keep a short incident plan: who can rotate SECRET_KEY (with SECRET_KEY_FALLBACKS), revoke sessions and redeploy.

Source: Django’s security policies, Archive of security issues, Django’s release process, Supported versions

Pitfalls checklist

  • mark_safe() on an f-string, .format() result or % result. Use format_html().

  • Unquoted attribute values in templates.

  • csrf_exempt for convenience. It disables protection for that view; webhooks need a signature check instead.

  • Posting a form to an external URL with {% csrf_token %} inside. The token leaks.

  • Forgetting ensure_csrf_cookie on a page that uses AJAX but renders no form.

  • Cache decorators above csrf_protect. The cached response has no cookie or Vary.

  • fields = "all" or exclude in a ModelForm or serializer.

  • Client-chosen field names in order_by(), filter(**params) or values().

  • SQL built with f-strings or %. Pass params.

  • ALLOWED_HOSTS = [""]* without your own validation, or reading request.META["HTTP_HOST"].

  • SECURE_PROXY_SSL_HEADER without a proxy that strips the header. It lets attackers fake HTTPS.

  • Enabling HSTS with a long age, includeSubDomains and preload before every subdomain is HTTPS-only.

  • Trusting ImageField or the extension as proof that a file is harmless; serve uploads as attachments or from another domain.

  • Referrer policy no-referrer breaking CSRF on HTTPS.

  • Running check --deploy against the development settings, or ignoring warnings without a comment.

  • DEBUG = True, a committed SECRET_KEY or a django-insecure- key in production.

  • CORS with credentials*, or using CORS as if it protected against CSRF.

  • Staying on an unsupported Django series.

Where the books are outdated

The books that informed this section were written for Django releases between 1.11 and 5.x; the security advice in them is mostly sound, but several specifics have moved on.

  • Settings that no longer exist. SECURE_BROWSER_XSS_FILTER and the X-XSS-Protection header (removed in 4.0, because browsers ignore the header) and CSRF_COOKIE_HTTPONLY as a protection (the documentation now says it gives little practical benefit) appear in older checklists.

  • Third-party packages that became core. django-secure is core since 1.8 (SecurityMiddleware), and django-csp is superseded by the built-in Content Security Policy in 6.0; see the CSP page before adding a package.

  • Renamed helpers. is_safe_url() is url_has_allowed_host_and_scheme() since 3.0, and url(), ugettext and force_text snippets in older examples no longer import.

  • Defaults changed. SECURE_CONTENT_TYPE_NOSNIFF is on by default (3.0), SECURE_REFERRER_POLICY defaults to 'same-origin' (3.1), Cross-Origin-Opener-Policy is sent by default (4.0) and CSRF_TRUSTED_ORIGINS needs schemes (4.0); older text that lists them as optional extras or without schemes is out of date.

  • Logout over GET. Older examples link to a logout URL; since 5.0 LogoutView accepts only POST, which closes a CSRF hole (a logout triggered by an image tag).

  • Key rotation. Older text recommends replacing SECRET_KEY and invalidating every session; SECRET_KEY_FALLBACKS (4.1) allows a graceful rotation.

  • Examples that are themselves vulnerable. Some textbook examples fetch a user-supplied URL server-side (SSRF), build HTML from Markdown with mark_safe() and no sanitising, assign innerHTML from API data, expose a viewset whose queryset is not filtered by owner, or use fields = "all"; none of those patterns should be copied.
