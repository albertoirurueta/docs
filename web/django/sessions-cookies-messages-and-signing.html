Sessions, Cookies, Messages & Signing

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Django 6.1 (6.1.1, released 2026-09-02; 6.1.2 is scheduled for 2026-10-06), Python 3.12-3.14 and PostgreSQL 15 or newer, checked on 2026-10-03; where Django 5.2 LTS (5.2.17) behaves differently the text says so. Every listing was run in a scratch project on Python 3.13.16 and Django 6.1.1 with SQLite: manage.py check, a suite of 57 tests (manage.py test), a curl session against runserver and the shell snippets all passed, and the output shown is the real output. Nothing on this page needs PostgreSQL or Redis to run; the cache-based session backends are shown with the local-memory cache in the tests, and the text says where a production deployment would use Redis or Memcached instead.

HTTP is stateless: each request arrives without memory of the previous one. Django gives you four layered tools to bridge that gap. A cookie is a small name/value pair the browser sends back with every request. A signed value is a string that carries a cryptographic signature, so tampering is detected even when the value travels through an untrusted place such as a cookie or a URL. A session is a per-visitor dictionary that lives on the server (or, with one backend, inside a signed cookie) and is found again through a session id cookie. The messages framework is a one-shot notification queue ("flash messages") built on top of cookies or sessions. This page covers all four, in that order from the lowest layer up, and finishes with a working session-based cart for the Bookshelf catalogue that grows across this section. The settings file that switches these features on is covered on Settings & Configuration, the models in the examples on Models & Fields, and the queries used to read them on Making Queries.

Cookies

A cookie is created by a Set-Cookie response header and returned by the browser in a Cookie request header (RFC 6265). Django exposes the incoming ones as the dictionary request.COOKIES (string values only) and the outgoing ones through three methods of HttpResponse.

Reading, setting and deleting cookies

def theme(request):
    current = request.COOKIES.get("theme", "light")           # read: plain dict of strings
    response = JsonResponse({"theme": current})
    response.set_cookie(
        "theme",
        "dark",
        max_age=60 * 60 * 24 * 30,   # seconds, or a timedelta; None = until the browser closes
        samesite="Lax",              # "Strict", "Lax" or the string "None"
        secure=True,                 # only over HTTPS
        httponly=False,              # JavaScript may read a preference cookie; never for credentials
    )
    return response


def forget_theme(request):
    response = HttpResponse("ok")
    response.delete_cookie("theme")  # path/domain must match what set_cookie used
    return response

Signed cookies

When you do need a cookie the user must not be able to edit (a display name, a "has accepted terms" marker, a small piece of state) Django can sign it. set_signed_cookie() and HttpRequest.get_signed_cookie() wrap the signing API from Cryptographic signing and add the cookie name to the signature, so a value signed for one cookie cannot be replayed as another:

catalog/views.py (signed cookie)
from datetime import timedelta

from django.http import HttpResponse, JsonResponse


def welcome(request):
    name = request.get_signed_cookie(
        "display_name", default=None, salt="catalog.display-name", max_age=3600
    )
    response = JsonResponse({"display_name": name})
    if "name" in request.GET:
        response.set_signed_cookie(
            "display_name",
            request.GET["name"],
            salt="catalog.display-name",
            max_age=timedelta(hours=1),
            httponly=True,
            samesite="Lax",
        )
    return response


def forget(request):
    response = HttpResponse("forgotten")
    response.delete_cookie("display_name", samesite="Lax")
    return response

Source: Django: HttpRequest.get_signed_cookie()

The behaviour, verified with curl against runserver:

$ curl -si -c jar.txt "http://127.0.0.1:18926/welcome/?name=Ana" | grep -i set-cookie
Set-Cookie: display_name=Ana:1xCmoe:CblyCzAWyf2H57LnH_Lwho66ETSaYpMBXsHMBy5P4II; expires=Sat, 03 Oct 2026 00:37:24 GMT; HttpOnly; Max-Age=3600; Path=/; SameSite=Lax
$ curl -s -b jar.txt http://127.0.0.1:18926/welcome/
{"display_name": "Ana"}
$ curl -s -b "display_name=Mallory:abc" http://127.0.0.1:18926/welcome/
{"display_name": null}

Notice that the value Ana is plainly visible: signed is not encrypted. The signature (1xCmoe is the base62 timestamp, the rest the HMAC) only guarantees that the value was produced by your site and has not been altered. Four details are worth knowing:

  • get_signed_cookie(key, default=RAISE_ERROR, salt='', max_age=None) raises KeyError if the cookie is missing and BadSignature (or its subclass SignatureExpired) if it was tampered with or is older than max_age seconds; passing a default suppresses both the missing-cookie error and the signature errors. max_age is checked against the timestamp inside the signature, not against the cookie’s Max-Age attribute, which the client controls.

  • salt puts the cookie into its own signature namespace, and you must pass the same salt when reading. The test suite asserts that reading with a different salt raises BadSignature.

  • Signed cookies are not revocable. A stolen, still valid cookie works until it expires; there is no server-side record to delete. Keep the max_age short and keep authorisation decisions out of them.

  • The salt derivation changed in Django 6.1. Until the security fix recorded in the 6.1 documentation as "changed in 5.2.15", two different (cookie name, salt) pairs that concatenate to the same string ("ab" + "c" and "a" + "bc") shared one signature namespace, so a cookie signed in one place could be replayed in the other. The cookie name and salt length are now part of the derived salt. Per the 6.1 documentation, older versions accept cookies signed the old way by default, and in 6.1 the transitional setting SIGNED_COOKIE_LEGACY_SALT_FALLBACK defaults to False and is deprecated, to be removed in Django 2028. Set it to True temporarily if you must accept cookies issued by an older deployment during a rollout. A test in the scratch project forged a cookie with the old derivation and confirmed it is rejected by default and accepted when the setting is True.

The shape of the cookie also depends on SIGNING_BACKEND, whose default is django.core.signing.TimestampSigner.

Cryptographic signing

Everything above rests on django.core.signing. It is useful by itself whenever data has to travel through a channel the user controls: "reset your password" links, hidden form fields, one-time download URLs, email confirmation tokens, the share link of a reading list.

Signer: sign and verify a string

>>> from django.core.signing import Signer, BadSignature
>>> signer = Signer()
>>> value = signer.sign("My string")
>>> value
'My string:6qWbEDv3EZfyZwEz1zb6cAIxgvYENsKX0xFxk4C-A9g'
>>> signer.unsign(value)
'My string'
>>> signer.unsign(signer.sign(2.5))      # non-strings are forced to str
'2.5'
>>> try:
...     signer.unsign(value + "m")
... except BadSignature as exc:
...     print("BadSignature:", exc)
BadSignature: Signature "6qWbEDv3EZfyZwEz1zb6cAIxgvYENsKX0xFxk4C-A9gm" does not match

Source: Django: Cryptographic signing - low-level API

The signature is appended after a separator (a colon by default) and is computed with HMAC from SECRET_KEY. The signature values above will differ on every project because the key differs. The constructor in 6.1 is keyword-only:

Signer(*, key=None, sep=':', salt=None, algorithm=None, fallback_keys=None)

  • key overrides SECRET_KEY for this signer.

  • sep must not be in the URL-safe base64 alphabet (letters, digits, hyphen, underscore).

  • algorithm is any hashlib algorithm and defaults to 'sha256'.

  • fallback_keys is a list of extra keys used only to verify (default SECRET_KEY_FALLBACKS, see Rotating SECRET_KEY: SECRET_KEY_FALLBACKS).

Positional arguments (Signer("key")) were deprecated in Django 4.2 and removed in 5.1; the scratch tests confirm a TypeError today, so older tutorials that call Signer("my-key") need the key= keyword. The default algorithm moved from SHA-1 to SHA-256 in Django 3.1; support for the old SHA-1 signatures was removed in 4.0.

The salt: one namespace per purpose

>>> Signer().sign("My string")
'My string:6qWbEDv3EZfyZwEz1zb6cAIxgvYENsKX0xFxk4C-A9g'
>>> Signer(salt="extra").sign("My string")
'My string:HnM9ss2LRRcApLAcECoK80VVJ_xnuDbtF1d4zwkvXWo'

Source: Django: Cryptographic signing - the salt argument

Different salts give different signatures for the same text, so a token minted for one feature cannot be fed to another. The salt is not a secret; it is a namespace. Use a constant per purpose, such as "catalog.share-wishlist" or "accounts.email-confirm", and never reuse the default.

TimestampSigner: expiring values

TimestampSigner appends a signed timestamp, and unsign(value, max_age=…​) raises SignatureExpired (a subclass of BadSignature) when the value is too old. max_age is an integer number of seconds or a timedelta:

>>> from datetime import timedelta
>>> from django.core.signing import TimestampSigner, SignatureExpired
>>> ts = TimestampSigner()
>>> t = ts.sign("hello")
>>> t
'hello:1xCmoE:1dUrRBnqlumSA9OTiICKVeFwX5lfOK24SoojSj94OnI'
>>> try:                                   # two seconds later
...     ts.unsign(t, max_age=1)
... except SignatureExpired as exc:
...     print("SignatureExpired:", exc)
SignatureExpired: Signature age 2.465151071548462 > 1 seconds
>>> ts.unsign(t, max_age=timedelta(seconds=20))
'hello'

Signing lists and dictionaries: sign_object, dumps, loads

Signer.sign_object() and unsign_object() (added in Django 3.2) serialise a list, tuple or dictionary to JSON, base64-encode it and sign it. TimestampSigner has the same two methods and adds max_age. The module-level shortcuts signing.dumps() and signing.loads() are TimestampSigner(salt='django.core.signing').sign_object()/unsign_object() with sensible defaults:

>>> signer = Signer()
>>> o = signer.sign_object({"message": "Hello!"})
>>> o
'eyJtZXNzYWdlIjoiSGVsbG8hIn0:psTPcr1zqrhc8TdYPva_xbpU5gKleZyr7Wbhcbmv2q4'
>>> signer.unsign_object(o)
{'message': 'Hello!'}

>>> from django.core import signing
>>> d = signing.dumps({"books": [1, 2]}, salt="catalog.share-wishlist", compress=True)
>>> d
'eyJib29rcyI6WzEsMl19:1xCmoG:Uk4TxxdnW60N4e-rmrhT5MzbCNpZptu8RJMp4eGDe08'
>>> signing.loads(d, salt="catalog.share-wishlist", max_age=3600)
{'books': [1, 2]}
>>> signing.loads(signing.dumps(("a", "b", "c")))     # JSON has no tuples
['a', 'b', 'c']
>>> signing.loads(d)                                   # wrong salt
Traceback (most recent call last):
...
django.core.signing.BadSignature: Signature "Uk4TxxdnW60N4e-rmrhT5MzbCNpZptu8RJMp4eGDe08" does not match

Source: Django: Cryptographic signing - complex data structures

dumps(obj, key=None, salt='django.core.signing', serializer=JSONSerializer, compress=False) returns a URL-safe string; compress=True only compresses when that makes the result shorter, which is why the small payload above looks unchanged. loads(string, key=None, salt=…​, serializer=JSONSerializer, max_age=None, fallback_keys=None) is the inverse and raises BadSignature on failure. Because JSON is the serialisation format, a stolen SECRET_KEY lets an attacker forge signed values but not run code, which is the difference from the pickle-based signing the old books describe. The serializer argument exists, so do not pass a pickle-based one.

Example: a signed, expiring share link

The Bookshelf lets a reader share a reading list as a URL. No database table is needed: the list of book ids is the token.

catalog/views.py (signed share link)
from datetime import timedelta

from django.core import signing
from django.core.signing import BadSignature, SignatureExpired
from django.http import Http404, HttpResponse, JsonResponse

from catalog.models import Book

SHARE_SALT = "catalog.share-wishlist"


def make_share_token(book_ids):
    return signing.dumps({"books": list(book_ids)}, salt=SHARE_SALT, compress=True)


def shared_list(request, token):
    try:
        payload = signing.loads(token, salt=SHARE_SALT, max_age=timedelta(days=2))
    except SignatureExpired:
        return HttpResponse("This link has expired.", status=410)
    except BadSignature:
        raise Http404("Invalid link")
    books = Book.objects.filter(pk__in=payload["books"], is_published=True)
    return JsonResponse({"titles": [b.title for b in books]})

Source: Django: Cryptographic signing - low-level API

SignatureExpired must be caught before BadSignature because it is the subclass. The URL pattern is path("shared/<str:token>/", views.shared_list, name="shared-list"); a token is a str containing a colon, which the default str converter accepts. A test in the scratch project builds a token, fetches it (200, titles returned), appends a character to it (404) and patches the clock three days forward (410). The payload is readable by anyone holding the link, so put ids in it, not private data; and because the link grants access to whatever the ids point to, still filter on the server (here is_published=True).

Rotating SECRET_KEY: SECRET_KEY_FALLBACKS

Everything signed is tied to SECRET_KEY: sessions on the signed_cookies backend, password-reset tokens, signed cookies, dumps(). Changing the key logs everyone out and invalidates every outstanding link, unless you rotate it: since Django 4.1 the SECRET_KEY_FALLBACKS setting lists previous keys that are still accepted for verification (never for signing):

# settings.py after a rotation
SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]                 # the new key signs everything from now on
SECRET_KEY_FALLBACKS = [os.environ["DJANGO_SECRET_KEY_OLD"]]  # the previous key still verifies

Source: Django: Settings - SECRET_KEY_FALLBACKS

Procedure: set the new key, put the old value first in the fallback list, deploy, and remove the old value once the oldest thing signed with it (the longest SESSION_COOKIE_AGE, the longest token lifetime) has expired. Every fallback key adds a verification attempt to each check that does not match an earlier key, so do not accumulate them. A test verified the contract: a value signed with the old key verifies under the new SECRET_KEY, and a fresh signature is different from the old one. The fallback list is not honoured by every third-party signing library, only by Django’s own signing and the features built on it.

What changed recently in signing

  • 3.1: SHA-256 replaces SHA-1 as the default; the transitional DEFAULT_HASHING_ALGORITHM setting existed for the upgrade and was removed in 4.0.

  • 3.2: sign_object()/unsign_object().

  • 4.1: SECRET_KEY_FALLBACKS; set_cookie() accepts a timedelta for max_age.

  • 5.1: positional arguments to Signer/TimestampSigner removed.

  • 6.1: unambiguous salts for signed cookies, SIGNED_COOKIE_LEGACY_SALT_FALLBACK (default False, deprecated). The default algorithm of django.core.signing.base64_hmac() and django.utils.crypto.salted_hmac() is deprecated too: pass an explicit algorithm if you call them directly.

Sessions

The session framework stores arbitrary per-visitor data on the server and sends the browser only an identifier. It is implemented by SessionMiddleware, which loads the session lazily when the view first touches request.session and saves it in the response phase.

sequenceDiagram participant B as Browser participant SM as SessionMiddleware participant V as View participant ST as Session store B->>SM: GET /cart/ (Cookie: sessionid=abc) SM->>V: request.session (lazy, not loaded yet) V->>ST: first access loads "abc" ST-->>V: data as a dict V->>V: request.session["cart"] = ... V-->>SM: response SM->>ST: save if modified (or SESSION_SAVE_EVERY_REQUEST) SM-->>B: Set-Cookie: sessionid=abc (only if created or modified)

Three consequences follow from the diagram. The store is only touched if the view reads or writes the session. The cookie is only sent if the session was created or modified (or SESSION_SAVE_EVERY_REQUEST is on), so a visitor who never gets session data never gets a cookie; a test asserts that a view that does not touch the session returns no sessionid. And the session is not saved when the response status is 500.

Enabling sessions

django-admin startproject already enables everything: SessionMiddleware in MIDDLEWARE and django.contrib.sessions in INSTALLED_APPS (needed for the db and cached_db backends only). The order matters: AuthenticationMiddleware and MessageMiddleware need the session, so SessionMiddleware must come before them. A site that never needs sessions can remove both lines and save a little overhead, but django.contrib.auth and the admin need them.

Rules of thumb from the reference

  • Use plain strings as keys. Keys beginning with an underscore are reserved by Django (_auth_user_id, _messages and others).

  • Never replace request.session with another object and never set attributes on it; use it like a dictionary.

  • Store only what the serializer can round-trip (below). Store references (ids), not model instances.

  • Session data is not a cache for computed results: it is loaded for every request that touches it and rewritten when it changes.

When the session is saved: the modified gotcha

Django saves the session only if it believes it changed, which means a key was assigned or deleted on the session object. Mutating a value that is itself mutable does not count:

request.session["foo"] = "bar"           # modified
del request.session["foo"]               # modified
request.session["foo"] = {}              # modified
request.session["foo"]["bar"] = "baz"    # NOT modified: this changes the inner dict, not the session

request.session.modified = True          # tell Django explicitly

Source: Django: Sessions - when sessions are saved

The scratch project reproduces it with two views that change prefs["theme"] in place. The one that sets request.session.modified = True persists the change; the one that does not changes nothing, silently:

catalog/views.py (the modified flag)
def prefs(request):
    prefs = request.session.setdefault("prefs", {"theme": "light"})
    if "theme" in request.GET:
        prefs["theme"] = request.GET["theme"]
        request.session.modified = True      # in-place change of a nested value
    return JsonResponse(prefs)


def nested_no_flag(request):                  # the bug: nested change, no flag
    prefs = request.session.setdefault("prefs", {"theme": "light"})
    prefs["theme"] = request.GET.get("theme", "dark")
    return JsonResponse(prefs)

Source: Django: Sessions - when sessions are saved

The test asserts that after GET /prefs-bad/?theme=dark the stored value is still "light", and that after GET /prefs/?theme=dark it is "dark". (A freshly created {"theme": "light"} is persisted by setdefault, which does assign.) Two settings change the policy: SESSION_SAVE_EVERY_REQUEST = True writes on every request and resends the cookie every time, which also slides the expiry forward (at the price of a write per request); the default False writes only when modified, and an empty session is never created.

What can go into a session

Session data is serialized with SESSION_SERIALIZER, whose only included value in 6.1 is django.contrib.sessions.serializers.JSONSerializer. JSON restricts you in two ways that surprise people coming from older tutorials:

  • Only JSON types. datetime and Decimal fail: session["price"] = Decimal("12.50") raises TypeError: Object of type Decimal is not JSON serializable at save time (a test asserts this). Convert (str(price), an epoch integer) or, better, store an id and read the real value from the database.

  • String keys only. JSON object keys are strings, so session[0] = "bar" becomes session["0"] after the next request, and session[0] raises KeyError (also asserted by a test). That is why the cart below uses str(book.pk) as the key.

PickleSerializer was deprecated in Django 4.1 and removed in 5.0 because a leaked secret key could turn the signed-cookie backend into remote code execution; the books' advice to switch to pickle to store arbitrary objects therefore no longer works. If you really need richer types, write a serializer class with dumps(self, obj) and loads(self, data) and point SESSION_SERIALIZER at it, and prefer converting the values yourself instead.

Session backends

SESSION_ENGINE chooses where session data lives. There are five included engines:

Engine (django.contrib.sessions.backends.<name>) Data lives in Strengths Weaknesses

db (default)

The django_session table (the Session model).

Durable, shared by all processes, no extra service, queryable.

A database read per request that touches the session and a write when it changes.

cached_db

Database and cache, written through to both.

Fast reads from the cache with durable fallback to the database; survives cache eviction.

Still writes to the database; needs a cache configured.

cache

Only the cache.

Fastest; no table to clean.

Eviction or a cache restart logs users out; only for Memcached or Redis; never local-memory in production.

file

Files in SESSION_FILE_PATH (default the system temporary directory).

No database.

Slow on busy servers, not shared across hosts without shared storage, files accumulate.

signed_cookies

The browser, inside a signed cookie.

No server-side storage at all.

Readable by the client, size limited to roughly 4 KB, no revocation or freshness guarantee.

All five were exercised in the scratch project with the same round trip (two requests to the async visits view, which must answer {"visits": 2}), using override_settings(SESSION_ENGINE=…​). The cache-based ones used the local-memory cache for the test only.

Database-backed sessions

The default. Add django.contrib.sessions to INSTALLED_APPS and run migrate to create the django_session table (session_key, session_data, expire_date). Every request that touches the session issues one SELECT, plus an UPDATE or INSERT if it changed. It is the right default until a profile shows sessions as a bottleneck.

Cache-based sessions: cached_db and cache

Cache-based sessions use the cache named by SESSION_CACHE_ALIAS (default 'default'). A production configuration with Redis (not run in the scratch project, which had no Redis server) looks like:

# production settings (Redis required)
CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.redis.RedisCache",   # Django 4.0+
        "LOCATION": "redis://127.0.0.1:6379/1",
    }
}
SESSION_ENGINE = "django.contrib.sessions.backends.cached_db"
SESSION_CACHE_ALIAS = "default"

Source: Django: Sessions - cached sessions

  • cached_db is a write-through cache: a write goes to the database first and then to the cache; a failing cache write is logged on the sessions logger (Django 5.1) instead of failing the request. Reads come from the cache and fall back to the database when the entry was evicted. Use it when you need both speed and durability, and keep django.contrib.sessions installed.

  • cache stores sessions only in the cache. Eviction (cache full, restart) means lost sessions and logged-out users, so it is only reasonable with a cache configured for persistence. The documentation advises cached_db unless you are sure about that persistence. Do not use the local-memory backend for sessions: it is not shared between processes and loses data on restart, which breaks any multi-worker deployment.

  • Django’s built-in Redis cache backend arrived in 4.0 and PyMemcacheCache in 3.2 (MemcachedCache was removed in 4.1); the third-party packages the books recommend for Redis are no longer required for basic use.

File-based sessions

SESSION_ENGINE = "django.contrib.sessions.backends.file" writes one file per session below SESSION_FILE_PATH (the system temporary directory when unset). Make sure the web server user can read and write that directory. It is acceptable for a single small server and a poor fit for containers (the directory is not shared and vanishes with the container).

Cookie-based sessions

With SESSION_ENGINE = "django.contrib.sessions.backends.signed_cookies" the whole dictionary is serialised, signed with SECRET_KEY and stored in the sessionid cookie. No table, no cache, no cleanup, and it works on any number of servers without shared storage. The cost is a set of properties you must accept consciously:

  • Readable. The payload is base64-encoded JSON. A scratch test decodes the cookie of the visits view and reads {"visits": 2} straight out of it. Never store anything the client should not see.

  • Tamper-evident, not tamper-proof against loss. Altering any character makes the session invalid: the test replaces the last two characters of the cookie and the next request starts a new session ({"visits": 1}). A cookie larger than the browser limit (about 4096 bytes) is dropped by the browser and the session is lost, even though Django compresses it.

  • No freshness, no logout. The signature cannot tell the latest cookie from an older one, and logout() cannot revoke a copy somebody else holds: a stolen cookie works until SESSION_COOKIE_AGE runs out. Replay attacks are possible on anything that must be "used once".

  • Bigger cookies on every request, which costs bandwidth.

  • A leaked SECRET_KEY lets an attacker create valid sessions for any user. (With a pickle serializer it used to mean remote code execution, which is why pickle is gone.)

Keep SESSION_COOKIE_HTTPONLY at True. Use this backend for tiny, low-value state in a stateless deployment, not for authentication of a high-value application.

A custom database-backed engine

To query sessions by something other than the key (for example "log this user out everywhere"), extend the database engine with your own model. Session security

  • Fixation. An attacker who can plant a known session id in your browser can later use it. django.contrib.auth.login() calls cycle_key() so the key changes at login; if you build your own login flow, call request.session.cycle_key() yourself. logout() calls flush(), which removes the data and the cookie.

  • Subdomains. A sibling subdomain may set cookies for the whole parent domain, which makes fixation possible if you do not control all subdomains. Likewise, a SESSION_COOKIE_DOMAIN of "example.com" sends the session cookie to every subdomain. Leave it None unless you need it and trust every subdomain.

  • No session ids in URLs. Django is cookie-only, by design: putting ids in URLs (as PHP can) exposes them through the Referer header.

  • Production flags. SESSION_COOKIE_SECURE = True, SESSION_COOKIE_HTTPONLY = True (default), SESSION_COOKIE_SAMESITE = "Lax" (default) and HTTPS everywhere; the CSRF cookie has its own settings.

  • Concurrent invalidation. Since 3.2, SessionMiddleware raises SessionInterrupted (a BadRequest subclass) instead of SuspiciousOperation when the session was destroyed by a concurrent request, so it surfaces as a 400 rather than a security log entry.

A session-based cart, corrected

Session carts are a classic first exercise: a shopper adds books before logging in, so the data cannot live in an order row yet. Tutorials and books in this area tend to share a handful of bugs, all of which the Bookshelf cart avoids on purpose.

Pitfall The cart below

Prices stored in the session next to the quantity (stale prices, a place to tamper with, and Decimal is not JSON)

The session stores only {"<book id>": quantity}; titles and prices are read from the database on every display.

Adding to the cart with a GET link

@require_POST plus {% csrf_token %}; a GET returns 405 (tested), and a POST without a token returns 403 (tested with enforce_csrf_checks=True).

Ids of deleted or unpublished books left in the session forever

Cart.prune() removes them each time the cart page renders (tested).

Quantity not bounded (negative, huge, above stock)

Clamped to 1..stock and to a per-line maximum of 10; a non-numeric value falls back to 1.

Integer keys, which JSON turns into strings

String keys everywhere.

Nested-dict edits that are never saved

The dictionary is reassigned to the session in _save(), which marks it modified.
catalog/cart.py
from decimal import Decimal

from catalog.models import Book

CART_SESSION_KEY = "cart"
MAX_PER_LINE = 10


class Cart:
    """A shopping cart kept in request.session.

    The session holds only {"<book id>": <quantity>}: JSON-friendly, small and
    free of prices. Titles and prices are always read from the database.
    """

    def __init__(self, request):
        self.session = request.session
        self._lines = self.session.get(CART_SESSION_KEY, {})

    def _save(self):
        # Assigning a new dict marks the session as modified.
        self.session[CART_SESSION_KEY] = self._lines

    def add(self, book, quantity=1, *, replace=False):
        key = str(book.pk)
        current = 0 if replace else self._lines.get(key, 0)
        new_quantity = min(current + quantity, MAX_PER_LINE, book.stock)
        if new_quantity <= 0:
            self._lines.pop(key, None)
        else:
            self._lines[key] = new_quantity
        self._save()

    def remove(self, book):
        if self._lines.pop(str(book.pk), None) is not None:
            self._save()

    def clear(self):
        self.session.pop(CART_SESSION_KEY, None)
        self._lines = {}

    def prune(self):
        """Drop ids whose book was deleted or unpublished since it was added."""
        live = set(
            Book.objects.filter(pk__in=[int(k) for k in self._lines], is_published=True)
            .values_list("pk", flat=True)
        )
        stale = [key for key in self._lines if int(key) not in live]
        for key in stale:
            del self._lines[key]
        if stale:
            self._save()

    def __len__(self):
        return sum(self._lines.values())

    def __iter__(self):
        books = Book.objects.filter(pk__in=[int(k) for k in self._lines], is_published=True)
        for book in books.select_related("author"):
            quantity = self._lines[str(book.pk)]
            yield {
                "book": book,
                "quantity": quantity,
                "line_total": book.price * quantity,
            }

    def total(self):
        return sum((line["line_total"] for line in self), Decimal("0.00"))

Source: Django: Sessions - using sessions in views

A few design notes. _lines is the same dictionary object that came out of the session; mutating it and then assigning it back is what makes Django save it. clear() is what an order-placement view calls after the order exists (inside the same transaction, see Transactions, Raw SQL & Multiple Databases). len(cart) is the number of items, not lines. A real shop would also lock stock when ordering and snapshot the price into the order line at that moment, because the price shown in the cart may legitimately change before checkout.

The messages framework

The messages framework is for one-time notifications ("flash messages") that outlive exactly one redirect: a view adds a message and redirects; the next page renders and consumes it. It works for anonymous and authenticated users.

Enabling messages

Everything is on in a startproject project: django.contrib.messages in INSTALLED_APPS, MessageMiddleware after SessionMiddleware in MIDDLEWARE, and the context processor django.contrib.messages.context_processors.messages in the TEMPLATES option context_processors. The context processor provides two template variables: messages (the queue) and DEFAULT_MESSAGE_LEVELS (a mapping of level names to integers). The default storage uses sessions, which is why the session middleware must be listed first. Remove all three entries only if you really never need messages; the admin and the auth views use them.

Storage backends

cookie.CookieStorage

Adding messages

from django.contrib import messages


def flash_levels(request):
    messages.debug(request, "debug message")                       # dropped unless MESSAGE_LEVEL <= DEBUG
    messages.info(request, "info message")
    messages.success(request, "success message")
    messages.warning(request, "warning message", extra_tags="sticky")
    messages.error(request, "error message")
    messages.add_message(request, 50, "critical message")          # custom level
    return redirect("messages-json")

Source: Django: Messages - adding a message

add_message(request, level, message, extra_tags='', fail_silently=False) is the general form and debug, info, success, warning and error are shortcuts. extra_tags are placed before the level tag: the warning above has the tag string "sticky warning". All of them accept fail_silently=True, which suppresses the MessageFailure raised when the framework is disabled; a test shows messages.info(HttpRequest(), "boom") raising MessageFailure and the same call with fail_silently=True passing. Only that failure is hidden, not other errors.

The minimum level can also be changed within one request: messages.set_level(request, messages.WARNING) and back with messages.set_level(request, None); messages.get_level(request) reads the current value. A test runs a view that does this and confirms level_was == 30, level_now == 20, and that only the warning was recorded.

Keeping messages for another request

Messages are marked for clearing when the storage is iterated and removed when the response is processed. To keep them available for the next request, set storage.used = False after iterating:

def keep_messages(request):
    storage = messages.get_messages(request)
    seen = [str(m) for m in storage]
    storage.used = False  # keep them for the next request
    return JsonResponse({"seen": seen})

Messages and async views

The messages API has no a-prefixed variants. Adding a message from an async def view works anyway: the storage collects messages in memory and MessageMiddleware stores them when the response passes through the (sync-capable) middleware chain. The scratch project adds messages.success(request, "added from an async view") in an async view and confirms the message is delivered on the next request through AsyncClient. Do not rely on this for anything that reads the session inside the view; use the async session API for that.

Caveats

  • Parallel requests. Messages ride on cookies or sessions, so when the same browser fires several requests at once, a message created by one may be delivered to another tab or, in some cases, not at all. It is normally not a problem for post/redirect/get flows.

  • Cookie size. The cookie backends cap data at about 2 KB; do not put long text in messages.

  • Rendering HTML in messages. Message text is escaped by the template like any variable. Use mark_safe or format_html only for fixed markup, never to wrap user input.

  • Admin. ModelAdmin.message_user() uses messages.INFO by default. Since Django 6.0 the DEBUG and INFO levels have their own icons and CSS in the admin instead of looking like SUCCESS; pass level=messages.SUCCESS to keep the old look.

Pitfalls checklist

  • Editing a mutable value inside the session without request.session.modified = True (or reassigning the key).

  • Putting Decimal, datetime or model instances into the session; non-string keys; relying on pickle.

  • Using cache sessions on a cache that evicts, or the local-memory cache with several workers.

  • Forgetting clearsessions; the db/file stores grow without bound.

  • A hard-coded or random-per-restart SECRET_KEY (all sessions and signed values die with a restart) and no rotation plan.

  • Treating a signed cookie, a signed token or a cookie-backed session as secret: it is readable.

  • Leaving SESSION_COOKIE_SECURE/CSRF_COOKIE_SECURE off in production; manage.py check --deploy warns about both.

  • State-changing GET links (add to cart, logout); use POST and CSRF.

  • Cart and session data that reference ids which no longer exist.

  • Not iterating messages in the template, so the same message appears again on the next page.

  • Catching BadSignature before SignatureExpired; the more general class swallows the specific one.
