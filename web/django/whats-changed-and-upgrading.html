Supported versions and the release policy

Django ships a feature release roughly every eight months and patch releases as needed; every third feature release (x.2) is a long-term support (LTS) release that receives security and data-loss fixes for about three years. A feature deprecated in one release keeps working, with a warning, for at least two feature releases and is then removed. The mechanics of this policy, and why it gives you a predictable upgrade path, are explained in Introduction & Architecture: release policy and its deprecation policy; this section only records the state on 2026-10-03.

Calendar versioning from Django 2028

Following DEP 20, adopted in Django 6.1, the releases previously planned as 7.0 and 7.1 are called Django 2028 and Django 2029. From 2028 a feature release ships every January and is named after its year; 6.2 is the last release under the old numbering and support scheme, and from Django 2028 on every release is supported for three years. The deprecation warning classes are renamed to the calendar version in which the feature disappears: what 6.0 and 6.1 deprecate is announced by RemovedInDjango2028Warning (formerly RemovedInDjango70Warning).

The rename has a timing detail worth knowing: Django 6.1.1 (2026-09-02) still defines only RemovedInDjango70Warning. The rename was committed to the 6.1 stable branch on 2026-09-03 and keeps RemovedInDjango70Warning as an alias, so it reaches users with the next 6.1 patch release. Code that filters warnings should therefore match on the parent class (PendingDeprecationWarning or DeprecationWarning) rather than on either name, as the pytest configuration in Turning deprecation warnings on does.

$ python -c "from django.utils import deprecation as d; print([n for n in dir(d) if n.startswith('Removed')])"
['RemovedAfterNextVersionWarning', 'RemovedInDjango70Warning', 'RemovedInNextVersionWarning']

One model, ten releases

The quickest way to feel how much the model layer moved since the books is to write one Bookshelf model with a feature from almost every release. Each comment names the release that introduced the line; none of it existed in Django 2.1.

catalog/models.py
from decimal import Decimal

from django.db import models
from django.db.models import F, Q
from django.db.models.functions import Lower, Now


class Book(models.Model):
    class Format(models.TextChoices):  # 3.0: enumeration types for choices
        HARDCOVER = "HC", "Hardcover"
        EBOOK = "EB", "E-book"

    title = models.CharField(max_length=200)
    format = models.CharField(max_length=2, choices=Format, default=Format.HARDCOVER)  # 5.0: no .choices
    metadata = models.JSONField(default=dict, blank=True)  # 3.1: JSONField on every backend
    pages = models.PositiveIntegerField()
    added = models.DateTimeField(db_default=Now())  # 5.0: database-computed default
    price = models.DecimalField(max_digits=8, decimal_places=2)
    price_with_vat = models.GeneratedField(  # 5.0: generated column
        expression=F("price") * Decimal("1.21"),
        output_field=models.DecimalField(max_digits=10, decimal_places=2),
        db_persist=True,
    )

    class Meta:
        indexes = [models.Index(Lower("title"), name="book_title_ci_idx")]  # 3.2: functional index
        constraints = [
            models.UniqueConstraint(Lower("title"), name="book_title_ci_unique"),  # 4.0: functional unique
            models.CheckConstraint(condition=Q(pages__gt=0), name="book_pages_positive"),  # 5.1: condition=
        ]

    def __str__(self):
        return self.title


class Review(models.Model):  # id is a BigAutoField: DEFAULT_AUTO_FIELD defaults to it since 6.0
    book = models.ForeignKey(Book, on_delete=models.DB_CASCADE)  # 6.1: database-level ON DELETE
    stars = models.PositiveSmallIntegerField()


class ShelfEntry(models.Model):  # 5.2: composite primary key
    pk = models.CompositePrimaryKey("shelf", "position")
    shelf = models.CharField(max_length=50)
    position = models.PositiveIntegerField()
    book = models.ForeignKey(Book, on_delete=models.DB_CASCADE)

Source: Model field reference, Constraints reference and ForeignKey.on_delete

Two details came out of running it. GeneratedField expressions are computed by the database with its own arithmetic: on SQLite F("price") * 121 / 100 returned 12.00 for a price of 10.00 because the division was done on integers, while F("price") * Decimal("1.21") returns 12.10. And db_comment (4.2) was left out on purpose: SQLite cannot store column comments, so manage.py check reports fields.W163 there; on PostgreSQL it is a one-word addition.

The test exercises every comment above and passes under -W error, which turns any deprecation warning into a failure:

catalog/tests.py
from decimal import Decimal

from django.core.exceptions import ValidationError
from django.test import TestCase

from .models import Book, Review, ShelfEntry


class TimelineFeatureTests(TestCase):
    def test_features_from_3_0_to_6_1(self):
        book = Book.objects.create(title="Dune", pages=412, price=Decimal("10.00"))

The deprecation timeline

The official deprecation timeline is organised by the release in which things are removed, newest first, and each block points to the release notes "of two versions prior" where the deprecation was announced. On 2026-10-03 its blocks are 2028, 6.1, 6.0, 5.1, 5.0, 4.1, 4.0, 3.1, 3.0 and older. There are no 4.2, 5.2 or 6.2 blocks: an LTS release removes nothing. Features deprecated in an x.0 or x.1 release are removed in (x+1).0, and features deprecated in the x.2 LTS are removed in (x+1).1 — which is why 5.2 deprecations disappear in 6.1. Upgrading Django

Upgrading regularly keeps the project on a version that still receives security fixes, brings new features and bug fixes, and keeps each individual upgrade small. The official how-to describes the same loop for every hop; the diagram condenses it.

flowchart TD A[Read the release notes of every feature release up to the target] --> B[Read the deprecation timeline for those releases] B --> C[On the current version run the tests with python -Wa and fix every warning] C --> D[Check that each dependency supports the next feature release] D --> E[Install the latest patch of the next feature release in a fresh environment] E --> F[Run django-upgrade, the full test suite with warnings on, check and makemigrations --check] F --> G{All green?} G -- no --> C G -- yes --> H[Deploy, then clear the cache] H --> I{Target reached?} I -- no --> D I -- yes --> J[Turn warnings into errors in CI]

The steps in detail

  1. Read. Read the release notes of every feature release after the one you run, up to and including the target, paying most attention to the "Backwards incompatible changes" sections, and look the same releases up in the deprecation timeline. The Release by release: 3.0 to 6.1 above is the short version.

  2. Resolve warnings first. On the version you run today, run the test suite with python -Wa manage.py test and fix every RemovedInDjango…​Warning that comes from your own code. A warning fixed now is a crash avoided after the upgrade.

  3. Go one feature release at a time. Upgrading 4.2 to 6.1 means 4.2 → 5.0 → 5.1 → 5.2 → 6.0 → 6.1, each on its latest patch release, rather than all the changes at once. The same incremental approach is recommended between LTS releases: LTS to LTS is a sequence of hops, not one jump. Python moves too: 6.0 needs Python 3.12, so a project on 3.10 or 3.11 upgrades Python while it is on 5.2.

  4. Upgrade the dependencies. Most Django-related packages publish a release for each new Django version; if one has not yet, you may have to wait or contribute the fix. PyPI classifiers often lag behind: on 2026-10-03 Channels 4.3.2, drf-spectacular, WhiteNoise and django-tasks still listed Django 6.0 as their newest classifier, while DRF 3.18.1, Django Ninja 1.7.1, django-debug-toolbar 8.0.0 and django-allauth already listed 6.1. A missing classifier is a reason to run the tests, not proof of incompatibility.

  5. Install in a fresh environment. For a major upgrade create a new virtual environment, then python -m pip install -U "Django>=6.1,<6.2" (or bump the pin in pyproject.toml and uv lock --upgrade-package django).

  6. Test. Run the whole suite with warnings visible, plus manage.py check (and check --deploy with production settings) and manage.py makemigrations --check --dry-run, which fails if the upgrade changed a model state, as the DEFAULT_AUTO_FIELD change in 6.0 does for projects that never set it.

  7. Deploy and clear the cache. Objects pickled into the cache by one Django version are not guaranteed to unpickle in another (cached HttpResponse objects from cache_page() were a past example), so clear the cache after deploying.

Source: How to upgrade Django to a newer version

django-upgrade: rewriting old code automatically

django-upgrade, by Django contributor Adam Johnson and listed under "upgrade utilities" on the official community ecosystem page, is a command-line tool that rewrites Python files so they stop using deprecated APIs, and in a few cases adopts the newer syntax. It enables every fixer up to and including the --target-version you give it; without the option it reads the minimum Django version from project.dependencies in pyproject.toml (falling back to 2.2). It does not recurse into directories, so you hand it the file list, and it exits with status 1 when it changed something so a CI job or pre-commit run stops for review.

What it left for you

Reading the diff is part of the job; four things in it need a human:

  • request.is_ajax() is untouched. There is no fixer, because the right replacement depends on intent. The 3.1 release notes give the exact equivalent, request.headers.get("x-requested-with") == "XMLHttpRequest", or request.accepts("application/json") if the code really cares about the Accept header. Note that accepts() returns True when the client sends no Accept header at all (the test client sends none), so a test that expected HTML got JSON when the scratch run first tried it.

  • [-\w]+ stays a regex. Only regexes that exactly match a path converter ([0-9]+, [-a-zA-Z0-9_]+, [^/]+, .+, the UUID pattern) are converted, so the slug route became re_path(). \w matches non-Latin letters and Django’s slug converter does not, so changing it to <slug:slug> is a behaviour change you decide on. Where a route was converted, the view now receives an int instead of a str; test those views.

  • Model changes need migrations. The null_boolean_field and index_together fixers change model state. Run makemigrations: for index_together it generates a RenameIndex operation that keeps the existing index. Keep makemigrations --check in CI so a forgotten migration fails the build.

  • Formatting is not its job. The admin rewrite left three blank lines at the end of the file; run your formatter after it.

Pitfalls

  • Jumping several releases at once. Each removal is announced by a warning in the two releases before it; skipping releases skips the warnings, and the first sign is an ImportError or TypeError at start-up, as in A hop through 5.2 → 6.0 → 6.1, for real.

  • Running the tests without warnings. Django’s warnings are invisible by default; a green suite under a plain manage.py test says nothing about the next release. Use -Wa locally and warnings-as-errors in CI.

  • Letting 6.0 change your primary keys. A project that never set DEFAULT_AUTO_FIELD gets migrations altering every implicit id to bigint. Pin AutoField first, then migrate deliberately if you want big integers.

  • Trusting classifiers in either direction. A package without a 6.1 classifier may work (Channels 4.3.2 did); one with it may still emit deprecation warnings. The test suite decides.

  • Forgetting migrations after automatic fixes. null_boolean_field and index_together change model state; makemigrations --check in CI catches the forgotten migration.

  • Accepting every rewrite blindly. django-upgrade turns str URL arguments into int when a regex becomes <int:pk> and leaves intent-dependent code (is_ajax()) alone; review the diff and run the tests.

  • Matching warning classes by name. RemovedInDjango70Warning becomes RemovedInDjango2028Warning during the 6.1 series; filter on DeprecationWarning/PendingDeprecationWarning instead.

  • Keeping the old cache. Pickled objects are not guaranteed to survive a version change; clear the cache after the deploy.

  • Copying a book’s settings file. Several of its settings no longer exist (MIDDLEWARE_CLASSES, USE_L10N, the storage settings), others are insecure as printed (Errata and practices not to copy).
