Internationalization & Translation

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Django 6.1 (6.1.1, released 2026-09-02; 6.1.2 is scheduled for 2026-10-06), Python 3.12-3.14 and PostgreSQL 15 or newer, checked on 2026-10-03; where Django 5.2 LTS (5.2.17) behaves differently the text says so. Every listing was run in a scratch project on Python 3.13.16 and Django 6.1.1 with SQLite: manage.py check, a suite of 34 tests (manage.py test) and a curl session against runserver all passed, and the output shown is the real output. One limit applies: the GNU gettext tools (xgettext, msguniq, msgfmt) are not installed on the machine that produced this page, so makemessages and compilemessages could not be executed. Their real failure message is shown, the .po files in the scratch project were written by hand in exactly the format makemessages produces, and a 60-line Python stand-in compiled them to .mo for the tests. Nothing here needs PostgreSQL or Redis. The two third-party model-translation packages (django-modeltranslation, django-parler) were not installed in the scratch project; their sections are written from the packages' own documentation and say so.

A site that serves one language still benefits from marking its strings, because the same marks later drive translation, the admin, form errors and validation messages. This page covers the whole chain in the order a project meets it: the vocabulary and the settings, marking strings in Python and in templates, extracting and compiling message files, how Django discovers catalogues and picks a language per request, translated URLs, the language switcher, JavaScript, translating database content, and testing. Number, date and time formatting (the "l10n" half) and time zones are on Localization & Time Zones; this page only touches them where they change what a translated page prints. The settings machinery is on Settings & Configuration, the middleware chain on Middleware, the URL layer on URLs & Routing, and the template language on Templates.

The settings that matter

Vocabulary and the end-to-end flow

Django’s documentation separates two words that people use interchangeably. Internationalization (i18n) is preparing the software for translation, usually done by developers. Localization (l10n) is writing the translations and local formats, usually done by translators. A few more terms recur through the page:

Term Meaning

Locale name

A language, or a language plus country, written ll or ll_CC with an underscore: it, de_AT, pt_BR, sr_Latn. This is the form of the directory names under locale/.

Language code

The same idea written with a dash, as browsers send it in the Accept-Language header: it, de-at, pt-br. This is the form used in LANGUAGE_CODE, in LANGUAGES and in URL prefixes. to_locale("pt-br") gives pt_BR.

Message file

A plain-text .po file for one language: the source strings (msgid) and their translations (msgstr).

Compiled catalogue

The binary .mo file produced from a .po by msgfmt; this is what Django loads at run time.

Domain

django for Python and template strings, djangojs for JavaScript strings. The split keeps the JavaScript catalogue small.

Translation string

Any literal marked so that tools can find it and Django can translate it.

A translatable project moves through five steps. Developers mark strings in code and templates, makemessages extracts them into a .po file per language, translators fill in the msgstr values, compilemessages compiles each .po into a .mo, and at run time Django activates one language per request and looks every marked string up in the merged catalogue.

flowchart LR A[Mark strings in Python and templates] --> B[makemessages] B --> C[locale/nl/LC_MESSAGES/django.po] C --> D[Translator fills in msgstr] D --> E[compilemessages] E --> F[django.mo] F --> G[LocaleMiddleware activates a language] G --> H[gettext looks the string up]

Two warnings from the official overview are worth repeating. The setting that turns all of this on or off is called USE_I18N, although it controls translation, not formatting (formatting is always localized since Django 5.0 removed USE_L10N). And Django assumes that the original strings in the source are written in English; a non-English base language works but has limits, covered in A non-English base language.

The Bookshelf pieces used on this page

Every example belongs to the app catalog of the Bookshelf project that grows across this section. The scratch project here offers three languages: English (the source language), Dutch (nl, two plural forms) and Polish (pl, three plural forms, used to show why ngettext exists). A Genre model carries a hand-written Dutch name to illustrate content translation later.

Marking strings in Python

Import gettext and, by convention, alias it to _:

catalog/views.py (excerpt)
from django.http import HttpResponse
from django.utils.translation import gettext as _


def greeting(request, name):
    # Translators: %(name)s is the reader's first name.
    return HttpResponse(_("Hello, %(name)s!") % {"name": name})

Source: Django: Translation — Standard translation

Run against the scratch project, curl shows the English literal and the Dutch translation (the Dutch page lives at a Dutch URL, see Translated URLs: i18n_patterns):

$ curl -s http://127.0.0.1:51731/en/hello/Eva/
Hello, Eva!
$ curl -s http://127.0.0.1:51731/nl/hallo/Eva/
Hallo, Eva!

Rules that follow from how extraction and lookup work:

  • Only functions with a single string argument may be aliased to _: gettext and gettext_lazy. The others (ngettext, pgettext, …​) must be imported by name because xgettext (the extractor) is configured with their argument layout.

  • Django deliberately does not install () into the builtins as the standard library’s gettext.install() would. The underscore means "the previous result" in the interactive shell and in doctests, and a global would also hide the question of whether this file wants the eager or the lazy variant.

  • Computed values and variables translate but cannot be extracted. (" ".join(words)) or (sentence) work at run time, yet makemessages never sees the literal, so it never reaches a .po file. Keep the literal visible.

  • Use named placeholders, not positional ones, once there is more than one. _("Today is %(month)s %(day)s.") % {…} lets a translator reorder the words (Spanish: "Hoy es 26 de noviembre."); %s %s does not.

  • Never use an f-string. _(f"Welcome {name}") interpolates before gettext is called, so the lookup key is the finished sentence and no translation can ever match. Use _("Welcome %(name)s") % {"name": name} or _("Welcome {name}").format(name=name).

  • Literal percent signs. A string such as "10% interest" is mis-detected as a Python format string and the compile step then fails with "number of format specifications …​ does not match". Write "10%% interest" or add the comment # xgettext:no-python-format above the call.

  • Comments for translators. A comment that begins with the keyword Translators on the line above the call is copied into the .po file as #. Translators: …. The same works in templates (see Marking strings in templates).

Plurals: ngettext

English has two plural forms; Polish has three, Arabic six, Japanese one. Django therefore never asks you to decide which form to use: you give the singular, the plural and the number, and the catalogue’s Plural-Forms rule picks.

catalog/views.py (excerpt)
from django.utils.translation import ngettext

from .models import Book


def shelf_summary():
    count = Book.objects.count()
    return ngettext(
        "There is %(count)d book on the shelf.",
        "There are %(count)d books on the shelf.",
        count,
    ) % {"count": count}

Source: Django: Translation — Pluralization

The Polish catalogue in the scratch project declares nplurals=3 with the standard Polish rule, and the test below passes 1, 2, 5 and 22 to the same call:

catalog/tests.py (excerpt)
def test_plural_forms(self):
    def msg(n):
        return ngettext(
            "There is %(count)d book on the shelf.",
            "There are %(count)d books on the shelf.",
            n,
        ) % {"count": n}

    with translation.override("pl"):
        assert [msg(n) for n in (1, 2, 5, 22)] == [
            "Na półce jest 1 książka.",
            "Na półce są 2 książki.",
            "Na półce jest 5 książek.",
            "Na półce są 22 książki.",
        ]

Source: Django: Translation — Pluralization

Three pitfalls the official page spells out:

  • Do not roll your own singular-or-plural logic. Choosing verbose_name or verbose_name_plural with if count == 1 is wrong for every language whose rule is not "one versus many". Put the model’s verbose_name inside both sentences instead.

  • Use the same placeholder names in the singular and the plural literal. A singular using %(name)s and a plural using %(plural_name)s makes compilemessages fail with "a format specification for argument 'name', as in 'msgstr[0]', doesn’t exist in 'msgid'".

  • With the lazy variants the count is not known at definition time. ngettext_lazy accepts a key name as its third argument and looks the number up in the dictionary used for the later % interpolation:

catalog/forms.py (illustrative)
from django import forms
from django.core.exceptions import ValidationError
from django.utils.translation import ngettext_lazy


class CartForm(forms.Form):
    too_many = ngettext_lazy(
        "You may only borrow %(num)d book at a time.",
        "You may only borrow %(num)d books at a time.",
        "num",
    )

    def clean(self):
        if self.cleaned_data.get("books", 0) > 3:
            raise ValidationError(self.too_many % {"num": 3})

Source: Django: Translation — Lazy translations and plural

If a lazy plural string contains exactly one unnamed placeholder you can interpolate the number directly: message % number.

Contextual markers: pgettext and npgettext

The English word May is a month and a verb; many languages use two different words. pgettext(context, message) (and npgettext(context, singular, plural, number) when it also pluralizes) adds a context string that becomes a msgctxt line, so the same msgid can have one translation per context.

catalog/views.py (excerpt)
from django.utils.translation import pgettext

month = pgettext("month name", "May")
verb = pgettext("verb", "May")

Source: Django: Translation — Contextual markers

catalog/locale/nl/LC_MESSAGES/django.po (excerpt)
msgctxt "month name"
msgid "May"
msgstr "mei"

msgctxt "verb"
msgid "May"
msgstr "mogen"

With the Dutch catalogue active, the home page prints mei / mogen / mei for pgettext("month name", …), pgettext("verb", …) and the template tag {% translate "May" context "month name" %} respectively.

Marking without translating: gettext_noop

gettext_noop marks a string for extraction but returns it unchanged. Use it for constants that must stay in the source language because they travel through other systems (a status stored in a database, a value in an API) and that you translate at the last moment, when they are shown.

catalog/views.py (excerpt)
from django.utils.translation import gettext as _
from django.utils.translation import gettext_noop

STATUS_LABELS = {
    "draft": gettext_noop("Draft"),
    "live": gettext_noop("Published"),
}

shown = [_(label) for label in STATUS_LABELS.values()]  # translate here, not at import

Source: Django: Translation — Marking strings as no-op

Under the Dutch catalogue STATUS_LABELS["live"] is still "Published" while shown becomes Concept, Online gezet (the project-level catalogue overrides the app’s, see How Django discovers catalogues).

Lazy translation: translating late

gettext("x") translates now, in whichever language is active now. Code that runs when a module is imported runs before any request exists, so it would freeze the translation of whatever language happened to be active, or none. The *_lazy functions return a proxy object that stores the literal and translates when it is finally used as a string, typically while a template renders.

Use the lazy variants wherever the value is evaluated at import time:

  • model field verbose_name and help_text, relation verbose_name, and Meta.verbose_name/verbose_name_plural (always give explicit lowercase names rather than relying on Django’s English-only guess from the class name)

  • form field labels, help texts and error messages

  • LANGUAGES names and URL patterns

  • the description argument of @admin.display and @admin.action

  • module-level constants

catalog/models.py (excerpt)
from django.db import models
from django.utils.translation import gettext_lazy as _
from django.utils.translation import pgettext_lazy


class Genre(models.Model):
    code = models.SlugField(unique=True)
    name_en = models.CharField(_("name (English)"), max_length=100)
    name_nl = models.CharField(_("name (Dutch)"), max_length=100, blank=True)

    class Meta:
        verbose_name = _("genre")
        verbose_name_plural = _("genres")

    def __str__(self):
        return self.name_en


class Book(models.Model):
    title = models.CharField(_("title"), max_length=200)
    genre = models.ForeignKey(
        Genre,
        on_delete=models.PROTECT,
        related_name="books",
        verbose_name=_("genre"),
    )
    price = models.DecimalField(
        _("price"),
        max_digits=6,
        decimal_places=2,
        help_text=pgettext_lazy("help text for Book.price", "Price in euros."),
    )

    class Meta:
        verbose_name = _("book")
        verbose_name_plural = _("books")
        ordering = ["title"]

    def __str__(self):
        return self.title

Source: Django: Translation — Lazy translation

The behaviour the test suite checks:

with translation.override("nl"):
    assert str(Book._meta.verbose_name_plural) == "boeken"
    assert str(Book._meta.get_field("price").help_text) == "Prijs in euro."

Things to know when you hold a lazy object:

  • It behaves like a str in Django code, but arbitrary Python (the requests library, json.dumps, a database driver) may not accept it. Convert with str(value) at the boundary, and only there, because str() freezes the current language.

  • str.format() does not work when the format string or an argument is lazy. Use django.utils.text.format_lazy, which creates another lazy object that formats only when finally rendered:

catalog/views.py (excerpt)
from django.utils.text import format_lazy
from django.utils.translation import gettext_lazy

TAGLINE = format_lazy(
    "{name}: {slogan}",
    name=gettext_lazy("Bookshelf"),
    slogan=gettext_lazy("read more"),
)

Source: Django: Translation — Formatting strings: format_lazy()

With Dutch active, str(TAGLINE) is Boekenplank: lees meer; with English active it is Bookshelf: read more.

  • To delay your own function, wrap it with django.utils.functional.lazy(function, str); then to_lower_lazy(_("My STRING!")) stays lazy.

  • Lazy and non-lazy are not interchangeable. Calling the eager gettext in a model field would translate once, at import, into whatever language is active then. Calling a lazy one in a view is harmless but pointless.

Marking strings in templates

Template translation has its own two tags and its own syntax. Every template that uses them must contain {% load i18n %} near the top, including templates that extend a base template that already loaded it, because load is per template.

{% translate %}

{% translate %} translates a constant string (single or double quotes) or the value of a variable. Internally it is a gettext call. When you pass a variable, the tag first resolves it and then looks the resulting string up in the catalogue; it cannot mix variables inside a literal (use blocktranslate for that).

Table 2. Options of the translate tag

Message files: makemessages and compilemessages

The GNU gettext prerequisite

makemessages shells out to xgettext, msguniq and msgmerge, and compilemessages to msgfmt. The official minimum is gettext 0.19 (raised from 0.15 in Django 5.2). Install the package called gettext with your system’s package manager; on Windows download a precompiled gettext build and make sure xgettext --version works at a command prompt. JavaScript template strings additionally need gettext 0.21 or newer.

On the machine used to verify this page no gettext tools are installed. The official page still says that without gettext makemessages "will create empty files"; with Django 6.1.1 the commands instead stop with an explicit error:

Extracting strings: makemessages

Run it from the project root (the directory containing manage.py) or from an app’s root:

$ django-admin makemessages -l nl        # create or update locale/nl/LC_MESSAGES/django.po
$ django-admin makemessages -a           # update every existing language

The anatomy of a .po file

The scratch project’s Dutch file shows the whole format. After makemessages -l nl the entries have empty msgstr values and a #: location comment; the translator fills them in.

msgid ""
msgstr ""
"Project-Id-Version: bookshelf\n"
"Language: nl\n"
"MIME-Version: 1.0\n"
"Content-Type: text/plain; charset=UTF-8\n"
"Content-Transfer-Encoding: 8bit\n"
"Plural-Forms: nplurals=2; plural=(n != 1);\n"

msgid "Welcome to the Bookshelf."
msgstr "Welkom bij de Boekenplank."

msgid "There is %(count)d book on the shelf."
msgid_plural "There are %(count)d books on the shelf."
msgstr[0] "Er staat %(count)d boek op de plank."
msgstr[1] "Er staan %(count)d boeken op de plank."

msgid "about/"
msgstr "over/"

msgid "hello/<str:name>/"
msgstr "hallo/<str:name>/"

Source: Django: Translation — Message files

  • msgid is the source text and must not be edited; msgstr is the translation. A long string is written as an empty first line followed by quoted pieces that are concatenated, so mind the trailing spaces inside each piece.

  • The header’s Plural-Forms line defines how many msgstr[n] there are and how a number picks one. Translation editors fill it in; Django only reads it.

  • The file must be UTF-8 without a byte-order mark. A text editor that adds a BOM breaks loading.

  • fuzzy entries (a guess msgmerge made from a similar string) are skipped by compilemessages unless you pass --use-fuzzy. Review and remove the flag rather than shipping fuzzy text.

  • #. Translators: … lines are the comments you wrote for translators; #: path:line lines are generated locations.

  • URL patterns are translated like any other string: the msgid is the whole pattern text, hello/<str:name>/, converter included. Translate the words and keep <str:name> exactly.

How Django discovers catalogues

At first use Django builds one in-memory catalogue per language by merging every .mo it finds, in this order of precedence:

  1. The directories in LOCALE_PATHS, first entry first.

  2. The locale/ directory of each app in INSTALLED_APPS, first app first.

  3. Django’s own django/conf/locale/ (107 locale directories in 6.1.1), the fallback.

All three use the same layout: <language>/LC_MESSAGES/django.(po|mo), with the directory named by locale name (pt_BR). Untranslated strings of a territorial variant (pt_BR) fall back to the generic language (pt).

This is how a project overrides a wording Django or a third-party app ships: put the same msgid in a project-level locale/ listed in LOCALE_PATHS. The scratch project does it on purpose. The app catalogue says Published is Gepubliceerd; the project catalogue says Online gezet, and the project wins:

msgid "Published"
msgstr "Online gezet"

Catalogues are built lazily and cached per process. In development runserver watches the .mo files in LOCALE_PATHS and in each non-Django app’s locale/ directory and clears the translation caches when one changes (the reloader module is django.utils.translation.reloader in the source), so a recompile shows up on the next request. In production each worker process keeps the catalogue it loaded, so restart or reload the workers after deploying new .mo files. Since Django 3.1 the reloader no longer reacts to changes inside Django’s own built-in translation files.

A non-English base language

Django assumes English source strings. If you write the source strings in another language you can, but: gettext offers only two plural forms for the original messages, so you must also provide a translation for the base language when its plural rule differs from English; and a visitor using an English variant, when an English translation is missing, gets the original strings, not the project’s LANGUAGE_CODE. For example, an English user visiting a site whose LANGUAGE_CODE is Spanish and whose source strings are Russian sees Russian. Most teams keep English sources and add en only if they need to polish wording.

Choosing the language per request: LocaleMiddleware

With no middleware, LANGUAGE_CODE decides the language for every visitor: "static" translation. To let each visitor have their own, add django.middleware.locale.LocaleMiddleware. It reads the request, picks a language, activates it for the current thread or task, and exposes it as request.LANGUAGE_CODE.

Where it sits in the request cycle

Middleware order matters, and the official guidance has three rules:

  1. Put it in the first few entries.

  2. It must come after SessionMiddleware (the locale logic may read session-backed data) and before CommonMiddleware (because CommonMiddleware needs an activated language to resolve the requested URL, and with i18n_patterns the URL depends on the active language).

  3. If you use the cache middleware, put LocaleMiddleware after it.

The detection algorithm

For each request the middleware tries these sources in order and stops at the first that yields a usable language:

  1. The language prefix in the URL path, but only if the root URLconf uses i18n_patterns (see Translated URLs: i18n_patterns).

  2. The language cookie, whose name is LANGUAGE_COOKIE_NAME (default django_language).

  3. The Accept-Language header that the browser sends. Django tries each language in the header, in priority order, until one has available translations.

  4. LANGUAGE_CODE, the global fallback.

Rules that apply at every step:

  • Preferences are expected as language codes with a dash (pt-br).

  • If the base language exists but the sublanguage does not, the base language is used: de-at selects de.

  • Only languages listed in LANGUAGES can be selected, whether the preference comes from the URL, the cookie or the header. Restrict LANGUAGES to the languages you really ship; otherwise a visitor whose header says fr is served in French and every string you never translated stays English in the middle of Django’s own French messages.

  • A language in LANGUAGES must also have a catalogue Django can load (check_for_language); a code that is listed but has no .mo anywhere is skipped.

The scratch project’s tests walk through the order. The URL prefix beats the cookie and the header; the cookie beats the header (a cookie for a language outside LANGUAGES is ignored); an unprefixed URL with only a header is redirected:

What the middleware does to the response

On the way out LocaleMiddleware does three things that matter for caches and clients:

  • Sets Content-Language to the active language if the view did not set one.

  • Adds Accept-Language to the Vary header, unless the URL carried a language prefix (the URL already distinguishes the variants). In the curl output above, the prefixed /nl/language/ response has no Vary: Accept-Language, while an unprefixed response does.

  • For a 404 on an unprefixed path, when i18n_patterns is in use with prefix_default_language=True, it tries the same path with the language prefix and, if that path resolves (also trying to append a slash when APPEND_SLASH is on), redirects there. The redirect carries Vary: Accept-Language, Cookie so shared caches do not serve one visitor’s redirect to another. The redirect class is the attribute response_redirect_class (default HttpResponseRedirect); subclass the middleware to issue permanent redirects instead.

Inside a view, the active language is request.LANGUAGE_CODE (dynamic translation) or settings.LANGUAGE_CODE (static). Prefer django.utils.translation.get_language(), which also works in code that does not receive the request.

Pitfalls

  • Position is not optional. Placing LocaleMiddleware after CommonMiddleware makes URL resolution happen before a language is active; i18n_patterns URLs and APPEND_SLASH redirects then use the wrong language.

  • The 404 redirect only works when the same path exists under the prefix. With translated URL segments, the unprefixed path /about/ is not redirected when the Dutch route is /nl/over/: the scratch project returned 404 for /about/ with the Dutch cookie set, because /nl/about/ is not a valid path. See Translated URLs: i18n_patterns.

  • Remember the middleware is the only thing that activates a language. A view that is reached without it (a management command, a task, a signal handler) runs in whichever language is active on that thread, which after a test client request may be left over from the previous request. See Testing translated code.

  • Caches must vary on the language. A response that depends on the language and is cached without that key leaks one language to all. The middleware adds Vary: Accept-Language for unprefixed URLs; cache_page and the per-site cache middleware honour Vary, and a CDN must be configured to as well. Prefixed URLs make caching simpler: each language has its own URL.

  • set_language and LANGUAGES are checked separately. The view accepts any code for which a catalogue exists (check_for_language), but the middleware later ignores a cookie whose code is not in LANGUAGES, so a hand-crafted POST for a language you do not offer sets a cookie that does nothing.

Translated URLs: i18n_patterns

Two independent mechanisms exist. i18n_patterns adds the active language as a prefix to every route inside it, so LocaleMiddleware can read the language from the URL. gettext_lazy around a pattern string translates the path segments themselves. Both require LocaleMiddleware, because both need an active language per request.

    path("language/", views.language_info, name="language"),
]

Source: Django: Translation — Translating URL patterns

With the Dutch catalogue, reverse("catalog:about") returns /nl/over/ and /nl/about/ is a 404, while the same name under English returns /en/about/. Remember that:

  • The msgid is the whole pattern string, including converters: hello/<str:name>/ becomes hallo/<str:name>/; a translation that changes or drops the converter breaks the route.

  • Translate URLs only inside i18n_patterns. A carelessly translated segment outside it can collide with an untranslated pattern.

  • Name your routes and always reverse them. Hard-coded paths do not follow the language.

  • Link to another language’s version with the language tag. {% language code %}{% url 'catalog:about' %}{% endlanguage %} (shown in Switching the language inside a template: {% language %}) builds the link in that language, because a plain url tag always uses the current one.

  • Switch the current URL programmatically with translate_url. django.urls.translate_url(url, lang_code) returns the same page in another language (or the URL unchanged if it cannot); the set_language view uses it to rewrite next. It resolves the URL under the currently active language, so with Dutch active translate_url("/nl/over/", "en") is /en/about/, while with English active the same call returns /nl/over/ unchanged (checked in the test suite).

The language switcher: set_language

Django ships a view, django.views.i18n.set_language, that stores the choice in the language cookie and redirects. Include the URLconf django.conf.urls.i18n outside i18n_patterns, which mounts it at setlang/:

path("i18n/", include("django.conf.urls.i18n")),   # /i18n/setlang/

Source: Django: Translation — The set_language redirect view

The view expects a POST with a language field and an optional next field (a GET or POST parameter). It:

  1. checks language with check_for_language and, if good, sets the cookie named by LANGUAGE_COOKIE_NAME with the other LANGUAGE_COOKIE_* attributes;

  2. validates next with url_has_allowed_host_and_scheme (same host, safe scheme); an unsafe or missing next falls back to the Referer, then to /, for requests that accept HTML; a client that does not accept HTML and sent no next gets 204 No Content;

  3. rewrites next into the new language with translate_url, so a visitor on /en/about/ who chooses Dutch lands on /nl/over/;

  4. never changes state on a GET: a GET only redirects.

Setting the language yourself

When the preference comes from elsewhere (a user profile, a single-sign-on claim), activate it for the request and persist it in the cookie so the next request finds it. activate affects only the current thread or task:

catalog/views.py (excerpt)
from django.conf import settings
from django.http import HttpResponse, HttpResponseBadRequest
from django.utils import translation
from django.utils.translation import gettext as _
from django.views.decorators.http import require_POST


@require_POST
def remember_language(request):
    """Persist a preference that came from somewhere other than the language form."""
    code = request.POST.get("language", "")
    if not translation.check_for_language(code):
        return HttpResponseBadRequest("Unsupported language")
    with translation.override(code):
        response = HttpResponse(_("Welcome to the Bookshelf."))
    response.set_cookie(
        settings.LANGUAGE_COOKIE_NAME,
        code,
        max_age=settings.LANGUAGE_COOKIE_AGE,
        samesite=settings.LANGUAGE_COOKIE_SAMESITE,
    )
    return response

Translating outside views and templates

The translation functions are not tied to the request. A background task, a management command, a signal handler or an e-mail builder can pick any language that has a catalogue. Management commands, tasks and mail

Since Django 2.1 management commands run with the language that is active, no longer with translations deactivated. If a command must write untranslated text (for example into the database), decorate the work with @no_translations; otherwise pick a language with override. The same applies to anything that runs outside a request: a Celery or django.tasks worker, a cron-driven script, a signal receiver. Wrap the rendering of a user-facing message in override(<that user’s language>).

catalog/management/commands/welcome.py
from django.core.management.base import BaseCommand, no_translations
from django.utils import translation
from django.utils.translation import gettext as _


class Command(BaseCommand):
    help = "Print the welcome line in one or all languages."

    def add_arguments(self, parser):
        parser.add_argument("--lang", default=None)
        parser.add_argument("--raw", action="store_true", help="Run with translations deactivated.")

    def handle(self, *args, **options):
        if options["raw"]:
            return self.handle_raw()
        lang = options["lang"]
        if lang:
            with translation.override(lang):
                self.stdout.write(_("Welcome to the Bookshelf."))
        else:
            self.stdout.write(_("Welcome to the Bookshelf.") + " [" + str(translation.get_language()) + "]")

    @no_translations
    def handle_raw(self):
        self.stdout.write(_("Welcome to the Bookshelf.") + " [" + str(translation.get_language()) + "]")

Synchronous and asynchronous code

The active translation is stored in an asgiref.local.Local (see trans_real.py in the Django source), which is thread-local under WSGI and task-local under ASGI. Consequences:

  • Under WSGI each worker thread has one active language at a time; LocaleMiddleware sets it at the start of every request, so sequential requests on one thread never see each other’s language, but code that runs between requests (a signal, a test) sees whatever the last request left.

  • Under ASGI, concurrent requests on one event loop each have their own language even though they interleave. LocaleMiddleware is async-capable, so the chain stays asynchronous; await points inside a view do not change the language.

  • The translation functions themselves are plain synchronous functions (no I/O after the catalogue is loaded), so call them directly from async def views; there is no agettext.

  • The first use of a language loads its .mo files from disk. In a latency-sensitive async deployment warm the catalogue at start-up (for example translation.activate("nl") in an AppConfig.ready() for each language, then deactivate()) rather than paying for it in the first request.

The async view and the test that proves it: fifteen requests in three languages run concurrently, each view sleeps 50 ms (so the requests interleave) and each still answers in its own language.

Caching the catalogue

Both views rebuild the catalogue from .mo files on every request. The output is constant between deployments, so cache it on the server, on the client, or build it at deploy time. Server-side with cache_page and a key prefix that changes when translations change; client-side with a conditional-GET decorator (or ConditionalGetMiddleware ETags):

from django.conf.urls.i18n import i18n_patterns
from django.urls import path
from django.utils import timezone
from django.views.decorators.cache import cache_page
from django.views.decorators.http import last_modified
from django.views.i18n import JavaScriptCatalog

# The value must change when the translations change; a deploy id is a good source.
CATALOG_VERSION = "2026-10-03-1"

last_modified_date = timezone.now()  # changes on every restart of the application server

    path(
        "jsi18n/",
        cache_page(86400, key_prefix=f"jsi18n-{CATALOG_VERSION}")(

        name="javascript-catalog",

    ),
)

Testing translated code

  • Use translation.override (or activate plus cleanup) in tests. A request made with the test client leaves its language active on the thread. The scratch project showed it: a test class that ran after the middleware tests found nl active and failed an assert str(lazy) == "Welcome to the Bookshelf." until its setUp activated en and a cleanup deactivated it.

  • Pass the header with headers=. self.client.get("/", headers={"accept-language": "nl"}); the async client accepts the same form. The older HTTP_ACCEPT_LANGUAGE="nl" spelling still works.

  • Test URLs both ways: reverse under override, resolve of the translated path, and a 404 for the untranslated one.

  • Compile before testing. Without .mo files every assertion on translated text fails; in CI run compilemessages before the tests (or ship the .mo files).

Pitfalls checklist

Pitfall What to do

Strings that never show up in the .po file

Keep the literal inside the call (_("text")), not in a variable; use gettext_noop for constants, and the djangojs domain for .js files.

The sentence is built with an f-string or by concatenation

Use one translatable sentence with named placeholders; word order differs per language.

Eager gettext at import time

Use gettext_lazy in models, forms, settings and URL patterns; wrap in str() only at the boundary.

Plurals decided with if count == 1

Use ngettext; keep the same placeholder names in both forms.

Wrong middleware position

LocaleMiddleware after SessionMiddleware and before CommonMiddleware; after the cache middleware if you use one.

Translated text that changes after a deploy but not after a compile

Compile .mo in the build, restart workers, and keep .mo out of version control but .po in.

LANGUAGES lists languages without catalogues

Restrict it to what you ship, and keep the list in sync with the locale/ directories.

Language leaks between requests in tests or scripts

Use override, deactivate in cleanup, and activate explicitly in management commands and workers.

Caching pages that differ by language

Rely on the Vary header, or put the language in the URL with i18n_patterns.

JavaScript shows English

The catalogue view must be inside i18n_patterns if the URLconf uses them, and djangojs .mo files must exist.

URLs translated outside i18n_patterns

Only translate path segments inside the prefixed block, to avoid collisions.

.po file saved with a BOM or a non-UTF-8 encoding

UTF-8 without BOM only.

% in a message flagged as Python format

Write %% or add # xgettext:no-python-format.

Language chosen through a GET link

set_language is POST-only on purpose (a GET never changes state); use the form with CSRF.

Performance and deployment notes

  • USE_I18N = False lets Django skip loading the translation machinery; only do it for sites that will never translate, because gettext then returns its argument and LocaleMiddleware has nothing to select. (With False, i18n_patterns also returns its patterns without a prefix.)

  • The catalogue of a language is loaded on first use and then kept in memory for the life of the process; the cost is a one-off file read per language and per worker.

  • Compile messages in the image build, restart workers after a deploy, and cache the JavaScript catalogue (see Caching the catalogue).

  • Behind a CDN, either put the language in the URL or make sure the CDN varies on Accept-Language and on the language cookie; otherwise the first visitor’s language is served to everybody.

  • The Content-Language header and the lang attribute on <html> help search engines and assistive technology; for SEO also publish hreflang alternates (the language template tag makes the per-language URLs easy to build).

Where the books are outdated

The four books consulted for this section date from Django 1.11 to 5.x. For internationalization, watch for these things when you follow an older tutorial (the listings above show the current form of each):

gettext, gettext_lazy, ngettext, gettext_noop; the u-prefixed names were deprecated in 3.0 and removed in 4.0.

3.0 / 4.0

{% trans %}, {% blocktrans %}

{% translate %}, {% blocktranslate %} (the old names still work).

3.1

javascript_catalog() and json_catalog() function views

The class-based JavaScriptCatalog and JSONCatalog views.

long gone

The language cookie (LANGUAGE_COOKIE_NAME) set by set_language.

path() and re_path(); url() was removed in 4.0.

Always give explicit lazy verbose_name and verbose_name_plural.

What changed recently

Version Change that touches translation

3.0

LANGUAGE_COOKIE_HTTPONLY, LANGUAGE_COOKIE_SAMESITE, LANGUAGE_COOKIE_SECURE; compilemessages --ignore; LocaleMiddleware stops reading the language from the session; ugettext* deprecated; Feed.language for syndication; new languages (Uzbek).

3.1

translate and blocktranslate tags introduced; LANGUAGE_COOKIE_SAMESITE accepts 'None'; the reloader stops watching Django’s built-in translation files; more languages.

3.2

makemessages no longer processes invalid locales that contain hyphens; the cache key no longer includes the language when USE_I18N is off and localization is on.

4.0

ugettext* removed; set_language no longer stores the language in the session; Malay translations.

4.1

i18n_patterns supports languages with both scripts and regions; makemessages does not rewrite up-to-date .po files.

4.2

makemessages accepts locales with private sub-tags; blocktranslate asvar output is marked safe; Sitemap.get_languages_for_item(); the test clients accept a headers argument (used above for Accept-Language).

5.0

USE_L10N removed (formatting is always localized); Uyghur added.

5.2 (LTS)

Minimum gettext raised from 0.15 to 0.19.

6.0

Haitian Creole added; no other change to the translation workflow.

6.1

BLANK_CHOICE_LABEL: the default "blank" option in form choice lists is now a more accessible, translatable label (the transitional USE_BLANK_CHOICE_DASH setting restores the old dash).

Nothing about the gettext workflow itself changed in 6.0 or 6.1: the code on this page is the same on 5.2 LTS and on 6.1, apart from the minimum gettext version. For the long view, i18n_patterns, LocaleMiddleware and JavaScriptCatalog have been stable for years.
