Django REST Framework

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Django 6.1 (6.1.1 on PyPI, released 2026-09-02; 6.1.2 is scheduled for 2026-10-06), Python 3.12-3.14 and PostgreSQL 15 or newer, and against Django REST framework (DRF) 3.18.1 (released 2026-09-07, the first line to declare Django 6.1 support; it supports Django 5.2, 6.0 and 6.1 and Python 3.10 or newer), all checked on 2026-10-03. The companion packages are django-filter 26.1 (2026-07-11, classified for Django 6.1), drf-spectacular 0.30.0 (2026-07-06) and djangorestframework-simplejwt 5.5.1 (2025-07-21); the last two only declare Django up to 6.0 and 5.2 respectively, but both were installed and exercised against Django 6.1.1 for this page. On a Django 5.2 LTS project the same DRF release applies unchanged. Every listing was run in a scratch project on Python 3.13 with SQLite: manage.py check (also under -W error) passes, manage.py spectacular --validate --fail-on-warn produces a valid schema for each API version, a suite of 17 APITestCase tests passes, and every curl session shown was captured against runserver.

Django on its own can answer with JSON (JsonResponse, see Responses, Streaming, CSV & PDF), but a real API needs much more: turning model instances into JSON and validating JSON back into model instances, content negotiation, authentication schemes that do not rely on cookies, per-object permissions, rate limits, pagination, filtering, versioning, machine-readable documentation and a test client that speaks JSON. DRF supplies all of these as small, replaceable classes layered on top of Django’s own views, so that everything else on this site — the ORM, authentication, the permission system, settings, middleware — keeps working. In the Bookshelf application that grows across this section the running example is a versioned API for books, authors and reviews: anyone may read published books, staff curate the catalogue, signed-in readers post one review per book, and only a review’s author may change it.

Where DRF sits in the request cycle

DRF does not replace Django’s request handling; it plugs in at the view layer. A request still passes through the middleware stack and the URL resolver described in The Request/Response Cycle, and then reaches a DRF view, which is an ordinary Django view produced by APIView.as_view(). Inside that view DRF runs its own pipeline. APIView.dispatch() first wraps Django’s HttpRequest in a DRF Request (adding request.data, request.query_params, lazy request.user/request.auth), then initial() runs, in this order: content negotiation (which renderer will produce the response), version determination (request.version), authentication, permission checks and throttle checks. Only then is the handler (get(), post(), or the ViewSet action such as list() or create()) called. Any APIException raised on the way — by a permission, a throttle, a serializer or your own code — is turned by the exception handler into a JSON error response, and finalize_response() renders the Response with the negotiated renderer.

Three consequences follow from this position. First, APIView.as_view() wraps the view in csrf_exempt, so Django’s CsrfViewMiddleware does not reject the request; instead SessionAuthentication performs the CSRF check itself, and only for requests it authenticates from the session cookie (token and JWT requests are not subject to CSRF because browsers do not attach those credentials automatically). Second, authentication is lazy and happens inside the view, which is why Django 5.1’s LoginRequiredMiddleware cannot see DRF’s authentication result: since DRF 3.16 every DRF view is opted out of that middleware, and access control for APIs belongs in permission classes. Third, the version, the user and the throttle state are all available to get_queryset(), get_serializer_class() and get_permissions(), which is what makes the per-version and per-user behaviour on this page possible.

catalog/models.py
from django.conf import settings
from django.core.validators import MaxValueValidator, MinValueValidator
from django.db import models


class Author(models.Model):
    name = models.CharField(max_length=200)
    slug = models.SlugField(max_length=200, unique=True)
    born = models.DateField(null=True, blank=True)

    class Meta:
        ordering = ["name"]

    def __str__(self):
        return self.name


class Book(models.Model):
    class Status(models.TextChoices):
        DRAFT = "draft", "Draft"
        PUBLISHED = "published", "Published"

    title = models.CharField(max_length=300)
    author = models.ForeignKey(Author, on_delete=models.PROTECT, related_name="books")
    isbn = models.CharField("ISBN", max_length=17, unique=True)
    status = models.CharField(max_length=20, choices=Status, default=Status.DRAFT)
    price = models.DecimalField(max_digits=8, decimal_places=2)
    published_on = models.DateField(null=True, blank=True)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        ordering = ["title"]

    def __str__(self):
        return self.title


class Review(models.Model):
    book = models.ForeignKey(Book, on_delete=models.CASCADE, related_name="reviews")
    user = models.ForeignKey(
        settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name="reviews"
    )
    rating = models.PositiveSmallIntegerField(
        validators=[MinValueValidator(1), MaxValueValidator(5)]
    )
    text = models.TextField(blank=True)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        ordering = ["-created_at"]
        constraints = [
            models.UniqueConstraint(
                fields=["book", "user"], name="one_review_per_user_and_book"
            )
        ]

Serializers

A serializer does two jobs. Serializing turns a model instance (or any object) into primitive Python data — dicts, lists, strings, numbers — that a renderer then turns into JSON. Deserializing takes untrusted input (request.data), validates it field by field and as a whole, and produces validated_data that save() turns into a created or updated instance. It plays the role a ModelForm plays for HTML (see Model Forms & Formsets), with the same rule: list the fields explicitly.

ModelSerializer and inspecting what it generates

ModelSerializer derives fields, validators and a default create()/update() from the model. Meta.fields is the allow-list of what is read and written; Meta.read_only_fields and Meta.extra_kwargs adjust generated fields without redeclaring them. Calling repr() on a serializer shows exactly which fields it generated, which is the first thing to check when a field behaves unexpectedly.

The serializers module for the running example follows. It shows the common field tools in one place: a nested read-only representation of the author together with a write-only primary key (source="author") so clients send an id but receive an object; a HyperlinkedIdentityField that renders each book’s URL (versioning-aware, see Versioning); read_only_fields so that clients cannot set status (publishing has its own endpoint); an extra_kwargs entry that adds a minimum price without redeclaring the field; and a v2 subclass that adds an annotated average_rating.

catalog/api/serializers.py
from django.db import transaction
from rest_framework import serializers

from catalog.models import Author, Book, Review


class AuthorSerializer(serializers.ModelSerializer):
    books_count = serializers.IntegerField(read_only=True)

    class Meta:
        model = Author
        fields = ["id", "name", "slug", "born", "books_count"]


class AuthorSummarySerializer(serializers.ModelSerializer):
    class Meta:
        model = Author
        fields = ["id", "name", "slug"]


class BookSerializer(serializers.ModelSerializer):
    # nested, read-only representation of the author...
    author = AuthorSummarySerializer(read_only=True)
    # ...and a write-only primary key for creating/updating
    author_id = serializers.PrimaryKeyRelatedField(
        source="author", queryset=Author.objects.all(), write_only=True
    )
    url = serializers.HyperlinkedIdentityField(view_name="book-detail")

    class Meta:
        model = Book
        fields = [
            "id", "url", "title", "isbn", "status", "price",
            "published_on", "author", "author_id",
        ]
        read_only_fields = ["status"]
        extra_kwargs = {"price": {"min_value": 0}}

    def validate_isbn(self, value):
        digits = value.replace("-", "")
        if len(digits) != 13 or not digits.isdigit():
            raise serializers.ValidationError("Enter a 13-digit ISBN.")
        return digits

    def validate(self, attrs):
        published_on = attrs.get("published_on")
        author = attrs.get("author") or getattr(self.instance, "author", None)
        if published_on and author and author.born and published_on < author.born:
            raise serializers.ValidationError(
                {"published_on": "A book cannot be published before its author was born."}
            )
        return attrs


class BookV2Serializer(BookSerializer):
    average_rating = serializers.FloatField(read_only=True)

    class Meta(BookSerializer.Meta):
        fields = BookSerializer.Meta.fields + ["average_rating"]


class ReviewSerializer(serializers.ModelSerializer):
    user = serializers.ReadOnlyField(source="user.username")

    class Meta:
        model = Review
        fields = ["id", "book", "user", "rating", "text", "created_at"]
        read_only_fields = ["book", "created_at"]


class BookInlineSerializer(serializers.ModelSerializer):
    class Meta:
        model = Book
        fields = ["title", "isbn", "price"]


class AuthorWithBooksSerializer(serializers.ModelSerializer):
    """Writable nested serializer: create an author together with their books."""

    books = BookInlineSerializer(many=True)

    class Meta:
        model = Author
        fields = ["id", "name", "slug", "books"]

    def create(self, validated_data):
        books_data = validated_data.pop("books")
        with transaction.atomic():
            author = Author.objects.create(**validated_data)
            Book.objects.bulk_create(
                Book(author=author, **data) for data in books_data
            )
        return author

Validation: fields, objects and validators

is_valid() runs validation in a fixed order: each field converts and checks its own value (type, max_length, min_value, choices), then the field’s validators, then a validate_<field_name>(self, value) method if the serializer defines one, and finally validate(self, attrs) with all values together. Field-level methods return the (possibly normalised) value — validate_isbn() above strips hyphens — and object-level validate() returns the whole attrs dict. Raise serializers.ValidationError with a string for a field error, or with a dict to attach the error to a specific field from validate(); a plain string from validate() lands under non_field_errors.

is_valid(raise_exception=True) raises instead of returning False, and DRF’s exception handler turns that into a 400 response whose body is serializer.errors. Object-level validation only runs once every field is valid, so the two error bodies below come from two separate requests:

Django’s full_clean() is not called by ModelSerializer.save(); the model’s field validators are copied onto the serializer fields, but a model clean() method is not run. Put API-relevant rules in the serializer (or in a function both the serializer and the model call).

Unique constraints and read-only fields

ModelSerializer turns unique=True into a UniqueValidator and a UniqueConstraint over several fields into a UniqueTogetherValidator — but only when every field in the constraint is writable on the serializer. In the running example book and user are read-only (the view supplies them), so DRF generates no validator for one_review_per_user_and_book, and a second review from the same user would reach the database and fail with an IntegrityError (a 500). The DRF validators guide offers two fixes: make the field a HiddenField with a default such as CurrentUserDefault() so it takes part in validation, or check explicitly in the view or serializer. The running example checks in the reviews action and returns a 400; the database constraint stays as the last line of defence.

Saving, partial updates and extra data

serializer.save() calls create(validated_data) when the serializer was built without an instance and update(instance, validated_data) when it was built with one. Keyword arguments to save() are merged into validated_data, which is how the view attaches data the client must not choose: serializer.save(book=book, user=request.user). partial=True (used automatically by PATCH in the generic views) makes every field optional so a client can send only what changes; PUT without partial requires every writable field.

Nested serializers

Nesting a serializer as a field gives a nested JSON object (or, with many=True, a list). Read-only nesting, like author in BookSerializer, needs nothing else. Writable nesting does: DRF refuses to guess how to save related objects, so a serializer with a writable nested field must implement create() (and update() if it supports updates) itself. AuthorWithBooksSerializer creates an author and their books in one request, inside transaction.atomic() so that a failure leaves nothing half-written (see Transactions, Raw SQL & Multiple Databases).

Creating an author with nested books
curl -s -X POST http://127.0.0.1:8000/api/v1/authors/bulk/ \
     -H "Authorization: Bearer $ACCESS" -H "Content-Type: application/json" \
     -d '{"name": "Octavia E. Butler", "slug": "butler",
          "books": [{"title": "Kindred", "isbn": "9780807083697", "price": "15.00"}]}'

Errors inside a many=True serializer changed format in DRF 3.18.0: they are now a dictionary keyed by the index of each invalid item, and valid items are omitted. Before 3.18 the errors were a list with an empty dict for every valid item. Requests, responses and APIView

APIView is DRF’s base class-based view. It looks like Django’s View (one method per HTTP verb, see Class-Based Views) but its handlers receive a DRF Request and return a DRF Response:

  • request.data holds the parsed body for any method and any configured parser (JSON, form data, multipart), unlike request.POST, which only handles form data on POST. request.query_params is a clearer name for request.GET. request.user and request.auth come from the authentication classes (request.auth is the token object or None).

  • Response(data, status=…​) takes unrendered Python data; the renderer chosen by content negotiation renders it. With the defaults a browser asking for text/html gets the browsable API and other clients get JSON; ?format=json forces a renderer.

  • Handlers raise DRF exceptions — ValidationError (400), NotAuthenticated (401), PermissionDenied (403), NotFound (404), MethodNotAllowed (405), Throttled (429) — and Django’s own Http404 and PermissionDenied are translated too. Use the constants in rest_framework.status instead of bare numbers.

The statistics endpoint needs no model serializer, so a plain APIView is the right tool. The extend_schema decorator only describes the response for the OpenAPI schema (see OpenAPI schemas with drf-spectacular); the view works without it.

The rules that keep generic views correct:

  • Override get_queryset(), never mutate queryset. The class attribute is evaluated once and cached across requests; get_queryset() runs per request and can use self.request.user and self.request.version. It is also the place for select_related(), prefetch_related() and annotate() (the books_count above), which the generic views guide calls out for avoiding N+1 queries.

  • Hooks instead of rewriting actions. perform_create(serializer), perform_update(serializer) and perform_destroy(instance) are the places to call serializer.save(owner=self.request.user), enqueue a task after commit, or write an audit entry.

  • get_object() applies object permissions. It looks the object up by lookup_field (pk by default, slug above) within get_queryset(), raises 404 if absent, and calls check_object_permissions(). A custom action that loads an object any other way skips those checks.

  • Combining permission classes. IsAdminUser | ReadOnly composes permissions with Python’s bitwise operators (&, |, ~), the same technique the permissions guide uses to rebuild IsAuthenticatedOrReadOnly. Setting permission_classes on a view replaces the default list from settings; it does not add to it.

ViewSets and routers

A ViewSet groups the handlers for one resource in a single class, named after actions rather than HTTP methods: list(), create(), retrieve(), update(), partial_update() and destroy(). A router then generates the URL patterns and maps methods to actions (GET on the collection is list, POST is create, GET on an item is retrieve, and so on). The classes available:

Class Provides

ViewSet

No actions and no queryset handling: write list(), retrieve()…​ yourself (an APIView with action routing).

GenericViewSet

GenericAPIView behaviour, no actions; add the mixins you need (the ReviewViewSet below has retrieve, update and destroy, but no list or create).

ReadOnlyModelViewSet

list() and retrieve().

ModelViewSet

All six actions.

Inside a ViewSet self.action names the current action, which is how one class can choose a serializer, a queryset, permissions or throttles per action. The BookViewSet below is the centre of the API: public reads of published books (staff also see drafts), staff-only writes, a different serializer and an annotated queryset for v2, and two extra actions.

catalog/api/views.py - the book ViewSet
class BookViewSet(viewsets.ModelViewSet):
    filterset_class = BookFilter
    search_fields = ["title", "author__name", "=isbn"]
    ordering_fields = ["title", "price", "published_on"]
    ordering = ["title"]

    def get_queryset(self):
        qs = Book.objects.select_related("author")
        if self.request.version == "v2":
            qs = qs.annotate(average_rating=Avg("reviews__rating"))
        user = self.request.user
        if not (user.is_authenticated and user.is_staff):
            qs = qs.filter(status=Book.Status.PUBLISHED)
        return qs

    def get_serializer_class(self):
        if self.action == "reviews":
            return ReviewSerializer
        if self.request.version == "v2":
            return BookV2Serializer
        return BookSerializer

    def get_permissions(self):
        if self.action in {"create", "update", "partial_update", "destroy", "publish"}:
            return [permissions.IsAdminUser()]
        return super().get_permissions()

    def get_throttles(self):
        if self.action == "reviews" and self.request.method == "POST":
            self.throttle_scope = "reviews"
        return super().get_throttles()

    @action(detail=True, methods=["post"])
    def publish(self, request, pk=None, version=None):
        book = self.get_object()
        book.status = Book.Status.PUBLISHED
        book.save(update_fields=["status"])
        return Response({"status": book.status})

    @action(detail=True, methods=["get", "post"])
    def reviews(self, request, pk=None, version=None):
        book = self.get_object()
        if request.method == "GET":
            page = self.paginate_queryset(book.reviews.select_related("user"))
            serializer = self.get_serializer(page, many=True)
            return self.get_paginated_response(serializer.data)
        if book.reviews.filter(user=request.user).exists():
            raise ValidationError({"detail": "You have already reviewed this book."})
        serializer = self.get_serializer(data=request.data)
        serializer.is_valid(raise_exception=True)
        serializer.save(book=book, user=request.user)
        return Response(serializer.data, status=status.HTTP_201_CREATED)

Extra actions with @action

Not every operation is CRUD. @action marks a ViewSet method as routable; the router adds a URL for it and names it <basename>-<url_name>. Its arguments:

Argument Meaning

detail

Required. True for an item route (books/<pk>/publish/), False for a collection route (books/recent/).

methods

HTTP methods, default ["get"]; http.HTTPMethod members are accepted too (documented since 3.15).

Override the URL segment (default: the method name, underscores kept) and the route name (default: the method name with underscores turned into dashes).

Two traps showed up while building this example. First, keyword arguments to @action only change the view’s attributes; if the ViewSet overrides get_serializer_class() or get_permissions() without consulting them, they are silently ignored. The first version of reviews passed serializer_class=ReviewSerializer while get_serializer_class() returned the book serializer unconditionally, so posting a review failed with "title: This field is required". The fix is to branch on self.action (as above) or to call super() for actions you do not handle. Second, an action that loads its object must use self.get_object(), which applies get_queryset() (drafts are invisible to the public) and the object-level permissions; Book.objects.get(pk=pk) would bypass both.

Older code uses @detail_route and @list_route. Authentication: session, token and JWT

Authentication answers "who is calling"; it does not refuse anything by itself. DRF tries each class in DEFAULT_AUTHENTICATION_CLASSES (or the view’s authentication_classes) in order; the first that recognises credentials sets request.user and request.auth, and if none does, request.user is an AnonymousUser. Invalid credentials (a bad token, an expired JWT) produce an immediate 401 instead of falling through. Permission classes then decide what the identified user may do (see Permissions, including object-level). The three schemes on this page:

Scheme Credential Good for Watch out for

SessionAuthentication

Django’s session cookie, from a normal login.

A JavaScript front end served from the same site, and the browsable API.

CSRF: unsafe methods need the X-CSRFToken header. Cross-site use needs CORS and cookie settings.

TokenAuthentication

Authorization: Token <key>; one random key per user in the authtoken_token table.

Simple server-to-server clients and scripts.

Keys do not expire and are stored in plain text; one key per user, shared by all their devices.

JWTAuthentication (djangorestframework-simplejwt)

Mobile and single-page apps on other origins, and services that verify tokens without a database lookup.

401 or 403: why the order of the classes matters

An unauthenticated request that is refused should get 401 with a WWW-Authenticate header telling the client how to authenticate; an authenticated request that is refused gets 403. DRF can only send one WWW-Authenticate header, so it uses the first authentication class: SessionAuthentication has no such header, so with it first anonymous clients receive 403. The running example lists JWTAuthentication first, so anonymous writes get a proper 401 (the first test suite run of this page failed on exactly this assertion with session listed first).

Session authentication and CSRF

With SessionAuthentication, users log in through Django’s normal login (see Authentication); path("api-auth/", include("rest_framework.urls")) adds login and logout views for the browsable API (logout is a POST since DRF 3.15). JWT with djangorestframework-simplejwt

DRF has no built-in JWT support; the DRF authentication guide points to third-party packages, and djangorestframework-simplejwt is the common choice. A client posts its username and password to TokenObtainPairView and receives an access token (sent on every request) and a refresh token (sent only to TokenRefreshView to get a new access token). The tokens are signed JWTs, by default HS256 with Django’s SECRET_KEY, so the server verifies them without a database query. The protocol background — claims, signatures, why access tokens are short-lived and how refresh-token rotation detects theft — is covered in JWT and JOSE and Access and Refresh Tokens.

 "messages": [{"token_class": "AccessToken", "token_type": "access", "message": "Token is invalid"}]}

Source: Simple JWT: Blacklist app and Simple JWT: Token types

Store tokens carefully on the client: an access token in JavaScript memory and a refresh token in an HttpOnly cookie or the platform’s secure storage are the usual compromise. If the front end is same-site, session authentication avoids token storage problems entirely. For "log in with Google" or a full OAuth 2.0 authorisation server, DRF’s guide lists django-oauth-toolkit and similar packages; the flows themselves are explained in OAuth.

Permissions, including object-level

Permissions run after authentication and before throttling and the handler. Each permission class has two hooks: has_permission(request, view), checked for every request in initial(), and has_object_permission(request, view, obj), checked only when the view calls get_object() (or check_object_permissions() explicitly). A request must satisfy every class in the list. A refusal raises NotAuthenticated (401 or 403, see 401 or 403: why the order of the classes matters) for anonymous users and PermissionDenied (403) otherwise.

Object permissions have two documented limitations that matter for security. They are not applied to list responses — the generic views do not call has_object_permission() for each row, for performance — and they are not applied on create, because there is no object yet. So "users may only see their own records" must be enforced in get_queryset(), which is what MyReviewsViewSet does: it never returns other users' reviews, and a request for someone else’s review id gets a 404 rather than revealing that it exists. Restrictions on creation belong in the serializer or in perform_create().

This is precisely the mistake in one of the books (Marani, ch. 6): a customer-facing ModelViewSet whose queryset was Order.objects.all(), guarded only by a permission class, so every authenticated customer could list everyone’s orders. The correction is the pattern above: scope get_queryset() to request.user (and keep object-level checks for writes). The swagger_fake_view guard is for drf-spectacular, which calls get_queryset() without a real user while generating the schema (see OpenAPI schemas with drf-spectacular).

Throttling

Throttles limit how often a client may call the API; they run after permissions. Each throttle class computes a cache key for the request (the user id, or the client IP for anonymous requests), keeps the timestamps of recent requests in Django’s cache and raises Throttled (HTTP 429, with a Retry-After header) once the rate is exceeded. Rates are written as "<number>/<period>", where only the first letter of the period counts (s, m, h, d).

Class Throttles by

AnonRateThrottle

Client IP, for unauthenticated requests only; rate key anon.

UserRateThrottle

User id (IP for anonymous users); rate key user.

ScopedRateThrottle

User id or IP, per throttle_scope named on the view; rate key = the scope name. Views without a throttle_scope are not throttled by it.

The running example combines all three: modest global anon/user rates, a reviews scope of 20 per day for posting reviews (set dynamically in BookViewSet.get_throttles() so that reading reviews is not limited), and a lookups scope for the ISBN lookup (set with the @throttle_scope decorator). Exceeding a rate looks like this:

{"detail": "Request was throttled. Expected available in 60 seconds."}

Source: Django REST framework: Throttling

Things to know before relying on throttles:

  • They are not a security boundary. The built-in implementations are open to race conditions under concurrency and the guide says so; use them for fair use and cost control, and put hard limits (login brute force, abusive IPs) in the proxy or a dedicated tool.

  • The cache must be shared. The default LocMemCache is per process, so with several Gunicorn workers each worker counts separately. Use Redis or Memcached in production (see Caching), or set a custom throttle’s cache attribute to another alias.

  • Client IPs behind a proxy. Throttles use X-Forwarded-For when present, which a client can forge. Set NUM_PROXIES to the number of trusted proxies in front of the application so DRF picks the right address.

  • Testing. Rates are copied into SimpleRateThrottle.THROTTLE_RATES when DRF is imported, so override_settings(REST_FRAMEWORK=…​) does not change them; patch the dictionary instead, and clear the cache between tests, as in this test from the suite:

Pagination

Generic list views and ViewSets paginate automatically when DEFAULT_PAGINATION_CLASS and PAGE_SIZE are set (or a view sets pagination_class). Custom actions must call self.paginate_queryset() and self.get_paginated_response() themselves, as the reviews action does. DRF ships three styles:

PageNumberPagination

?page=2; optional page_size_query_param with max_page_size.

Numbered pages and a total count are wanted.

LimitOffsetPagination

?limit=20&offset=40; max_limit.

Clients want arbitrary windows (spreadsheets, exports).

CursorPagination

An opaque ?cursor=…​; requires a stable, unique ordering.

Filtering, search and ordering

Filter backends narrow the queryset from query parameters; they run in filter_queryset(), after get_queryset(), so they can never widen what a user is allowed to see. Three backends cover most needs, and all are enabled globally in the running example through DEFAULT_FILTER_BACKENDS:

  • django_filters.rest_framework.DjangoFilterBackend (from django-filter) for exact and range filters on fields: filterset_fields = ["status", "author"] for simple equality, or a FilterSet class in filterset_class for lookups such as gte/lte, renamed parameters and validation of the values;

  • rest_framework.filters.SearchFilter for ?search=…​ across search_fields, where a prefix picks the lookup: none for icontains, ^ for istartswith, = for iexact, $ for iregex and @ for PostgreSQL full-text search. DRF 3.18 added UnaccentedSearchFilter, which wraps the lookups in PostgreSQL’s unaccent (so "Jeremy" matches "Jérémy");

  • rest_framework.filters.OrderingFilter for ?ordering=price or ?ordering=-price, restricted to ordering_fields, with the view’s ordering as the default.

import django_filters

from catalog.models import Book

    published_after = django_filters.DateFilter(
        field_name="published_on", lookup_expr="gte"

        model = Book

Versioning

An API that has clients outside your repository cannot change shape freely. DRF’s versioning determines a version per request — before authentication, see Where DRF sits in the request cycle — and stores it in request.version; your code branches on it. The schemes differ only in where the client puts the version:

Scheme Client sends Notes

URLPathVersioning

/api/v1/books/

URL kwarg version; visible, cache-friendly, easy to route at the proxy.

NamespaceVersioning

/api/v1/books/

The same URLs, but the version comes from the URL namespace of an include().

AcceptHeaderVersioning

Accept: application/json; version=1.0

Clean URLs; harder to try in a browser.

HostNameVersioning

v1.api.example.com

Needs DNS and TLS per version.

QueryParameterVersioning

/api/books/?version=v1

Easy, but easy to forget.

The running example uses URLPathVersioning with ALLOWED_VERSIONS = ["v1", "v2"] and DEFAULT_VERSION = "v1". The URL pattern only accepts those two versions, so /api/v3/books/ is a plain 404 (with an open <str:version> converter DRF would reject the unknown version with its own 404 error instead). Version 2 adds an average_rating field: get_serializer_class() returns BookV2Serializer and get_queryset() adds the Avg("reviews__rating") annotation only when request.version == "v2", so v1 clients pay nothing for it.

OpenAPI schemas with drf-spectacular

An OpenAPI 3 document describes every path, parameter, request body, response and security scheme; Swagger UI and Redoc render it as interactive documentation, and code generators turn it into typed clients. DRF’s own rest_framework.schemas.openapi generator is deprecated: the DRF schemas guide says it will be moved out and retired, and recommends drf-spectacular as the full replacement. The even older CoreAPI-based schemas, which Django 2-era books use, were superseded by OpenAPI in DRF 3.10 and removed in DRF 3.17. drf-spectacular introspects serializers, views, filters, pagination, authentication and versioning, and lets you fill the gaps with decorators.

Setup is three pieces, all shown earlier: "drf_spectacular" in INSTALLED_APPS, "DEFAULT_SCHEMA_CLASS": "drf_spectacular.openapi.AutoSchema" in REST_FRAMEWORK plus a SPECTACULAR_SETTINGS dictionary (title, description, version, and SERVE_INCLUDE_SCHEMA: False to keep the schema endpoint out of the schema), and the URL patterns for SpectacularAPIView (the YAML or JSON document) and SpectacularSwaggerView (the UI; SpectacularRedocView is the alternative). Because the API is versioned by URL path, the schema views are mounted inside the versioned prefix: /api/v1/schema/ describes v1 and /api/v2/schema/ describes v2 (including average_rating), each with its own /docs/ page.

Introspection works well for generic views and ViewSets, because they declare their serializer. It needs help where the code decides at runtime, and the generator prints a warning or error for each such place. The running example needed three fixes, all shown in the listings above:

  • CatalogStatsView is a plain APIView without a serializer, so drf-spectacular could not guess its response ("unable to guess serializer"); @extend_schema(responses=inline_serializer(…​)) describes it. Sync and async

DRF 3.18 is synchronous: APIView.dispatch(), authentication, permissions, throttles, serializers and the generic views are all plain functions, and there is no async def handler support. Declaring one does not work — Django sees an async method and treats the view as async, but DRF’s synchronous dispatch never awaits the handler and fails with "Expected a Response, HttpResponse or StreamingHttpResponse to be returned from the view, but received a `<class 'coroutine'>`" (reproduced for this page with DRF 3.18.1).

Under an ASGI server (Uvicorn, Daphne, Granian) that is not a problem for correctness: Django runs synchronous views in a thread, exactly as it runs any sync view, so DRF works unchanged and can be served alongside async Django views and Channels consumers. The cost is a thread per in-flight request and the context switch, as explained in Async Support. If an endpoint must be truly async — many concurrent slow calls to other services, long polling — the options are a native async Django view for that endpoint, Django Ninja (async endpoints with Pydantic schemas), or the third-party adrf package, which the DRF docs list and which adds async APIView/ViewSet variants. For streaming events to browsers see Channels & WebSockets.

Source: Django: Async views and adrf

Inside DRF code the usual sync rules apply, which also means the classic async pitfalls of the books — synchronous ORM calls on the event loop — cannot happen in a DRF view. Background work triggered by an API call (emails, thumbnails) belongs in a task enqueued after commit; see Tasks Framework.

DRF or Django Ninja?

DRF is the mature, batteries-included choice: class-based views, a large ecosystem (filters, auth packages, drf-spectacular), the browsable API and a decade of documentation, at the cost of being synchronous and somewhat verbose. Django Ninja builds endpoints from type-annotated functions and Pydantic schemas, produces OpenAPI natively and supports async endpoints, in the style of FastAPI; it suits new, typed, API-first projects. Both sit on the same Django models, auth and settings, and can coexist in one project under different URL prefixes. Django Ninja compares them in detail, and FastAPI: Introduction and Architecture covers the FastAPI side.

Pitfalls checklist

  • fields = "all" or exclude on a serializer: new model columns become writable and visible. List fields.

  • A queryset attribute without user scoping on endpoints that return per-user data: object permissions do not filter lists. Override get_queryset().

  • get_serializer_class()/get_permissions() overrides that ignore @action(serializer_class=…​, permission_classes=…​).

  • Custom actions that fetch objects with Model.objects.get() instead of self.get_object(), skipping queryset filtering and object permissions.

  • SessionAuthentication listed first: anonymous clients get 403 without WWW-Authenticate. List the token or JWT class first if non-browser clients matter.

  • Unique constraints over read-only fields: no validator is generated, and duplicates surface as IntegrityError.

  • Missing select_related()/prefetch_related() for nested serializers: N+1 queries on every list page.

  • No pagination on a list endpoint: one request can read the whole table.

  • Throttling with LocMemCache behind several workers, or without NUM_PROXIES behind a proxy.

  • Long-lived bearer credentials: DRF tokens never expire; JWT access tokens cannot be revoked. Keep access tokens short, rotate refresh tokens, and serve everything over HTTPS.

  • Model clean() logic that the API silently skips: serializers do not call full_clean().

  • override_settings(REST_FRAMEWORK=…​) in tests for values DRF caches at import time (throttle rates).

  • Undocumented or drifting schema: generate it in CI with --validate --fail-on-warn.

  • async def handlers on DRF views: not supported in DRF 3.18.
