What GeoDjango is

GeoDjango is not a separate package: it is django.contrib.gis, installed with Django. It adds, in layers:

  • Model fields for the OGC Simple Features geometry types and for rasters, with a spatial index by default.

  • ORM extensions: spatial lookups such as intersects and dwithin, geographic database functions such as Distance and Transform, and GIS aggregates such as Extent and Union.

class MeetupQuerySet(models.QuerySet):

        return (

Choosing an SRID: degrees, projections and geography

The SRID decides how coordinates are read, and therefore what a "distance" means. WGS 84 (4326) stores longitude and latitude, which are angles; one degree is not a fixed number of metres, so a distance between two WGS 84 points is either in degrees (the planar answer) or needs a calculation on the sphere or spheroid. The documentation’s advice has three branches:

  1. Projected system for a region (a metric SRID such as a UTM zone or a national grid): coordinates are in metres or feet, planar distance is exact enough and fast, indexes are used. Only valid inside the region it was designed for.

  2. Geographic system with distance functions (4326 with geometry columns): Django asks PostGIS for ST_DistanceSphere or ST_DistanceSpheroid. Correct, but the spatial index on traditional geometry fields cannot be used, so the distance is computed for every row.

  3. geography=True (PostGIS, forces 4326): distance and measurement operations on a geography column automatically use great circle arc calculations and return linear units, and the index is used. The price is that only a subset of lookups works on geography: besides the distance lookups only bboverlaps, coveredby, covers and intersects.

When you need a geography column in a lookup or aggregate that does not support it, cast it to a geometry in the query:

Cast a geography column to geometry for one query
from django.contrib.gis.db.models import PointField
from django.db.models.functions import Cast

Meetup.objects.annotate(geom=Cast("venue", PointField())).filter(geom__within=polygon)

The compiled SQL contains ("places_meetup"."venue")::geometry(POINT,4326) AS "geom" and WHERE ST_Within"places_meetup"."venue")::geometry(POINT,4326), ST_GeomFromEWKB(<ewkb>. When you save a geometry whose SRID differs from the field’s, Django wraps it in ST_Transform(…​, field_srid) for you (see Creating and saving models with geometry fields). The PostGIS documentation has a section on when to use geography versus geometry; spatialreference.org lists SRIDs.

django.contrib.gis.geos wraps the GEOS C library. Every geometry is a GEOSGeometry; the constructor takes WKT, HEX, WKB (as a memoryview) or GeoJSON, and the type-specific classes (Point, LineString, LinearRing, Polygon and the multi types) take coordinates. All accept an srid keyword.

Creating geometries (executed)

Operating on geometries

Geometries are "Pythonic": coordinates can be indexed, iterated, changed and appended like lists, and they support set-like operators (| union, & intersection, - difference, ^ symmetric difference). Binary predicates return booleans, constructive operations return new geometries:

Predicates, constructive operations, validity (executed)
poly = Polygon(((0, 0), (0, 50), (50, 50), (50, 0), (0, 0)), srid=4326)
poly.area, poly.centroid.wkt, poly.extent
# (2500.0, 'POINT (25 25)', (0.0, 0.0, 50.0, 50.0))
poly.contains(Point(10, 10)), Point(10, 10).within(poly)
# (True, True)
poly.buffer(1).geom_type
# 'Polygon'

bowtie = Polygon(((0, 0), (2, 2), (2, 0), (0, 2), (0, 0)))
bowtie.valid, bowtie.valid_reason
# (False, 'Self-intersection[1 1]')
bowtie.make_valid().wkt
# 'MULTIPOLYGON (((0 2, 1 1, 0 0, 0 2)), ((2 0, 1 1, 2 2, 2 0)))'

The reference also covers intersects, covers, crosses, disjoint, overlaps, touches, relate_pattern, difference, union, simplify, interpolate, project, distance, normalize and the properties coords, wkt, wkb, hex, ewkt, geojson, json, extent, centroid, envelope and prepared. A PreparedGeometry (the prepared property) speeds up repeated contains, intersects or covers tests against one geometry; it behaved as documented in a quick check.

Two comparisons deserve a warning because they trip everyone once. The == operator is equals_exact(), not spatial equality: the same line drawn in the opposite direction is equals() but not ==.

Spatial lookups

Lookups are the spatial equivalent of __icontains: they filter on a geometry or raster field and are available on any manager method (filter(), exclude(), get()). Normal lookups can be chained with spatial ones.

Spatial lookups (SQL compiled against the PostGIS backend)
from django.contrib.gis.geos import Point, Polygon
from places.models import Bookshop, Region

madrid = Point(-3.7038, 40.4168, srid=4326)
area = Polygon(((-3.75, 40.38), (-3.75, 40.45), (-3.65, 40.45), (-3.65, 40.38), (-3.75, 40.38)), srid=4326)

Region.objects.filter(boundary__contains=madrid)
# WHERE ST_Contains("places_region"."boundary", ST_GeomFromEWKB(<ewkb>))

Region.objects.filter(boundary__intersects="POINT(-3.7 40.4)")        # WKT is accepted
# WHERE ST_Intersects("places_region"."boundary", ST_GeomFromEWKB(<ewkb>))

Bookshop.objects.filter(location__within=area)
# WHERE ST_Within("places_bookshop"."location", ST_GeomFromEWKB(<ewkb>))

Region.objects.filter(boundary__bbcontains=madrid)                   # bounding boxes only
# WHERE "places_region"."boundary" ~ ST_GeomFromEWKB(<ewkb>)

Region.objects.filter(boundary__relate=(madrid, "T*T***FF*"))         # DE-9IM pattern for "contains"

(In the real SQL the pattern is a quoted parameter; the stubbed str(queryset.query) shows it bare, and Django documents that this string is not necessarily valid SQL.) Choosing between them is mostly about boundaries and cost. contains and within are the strict pair; covers and coveredby treat a point on the boundary as inside, which is what most people mean and, on PostGIS, can be what a geography column supports (contains is not available on geography). intersects is the general-purpose "touches in any way" test and the one to reach for first. bbcontains and the other bounding-box lookups are the cheap pre-filters. Observed in compiled SQL: geom_type="MULTIPOLYGON" becomes GeometryType(col) = 'MULTIPOLYGON', isvalid=False becomes NOT ST_IsValid(col), num_dimensions=2 becomes ST_NDims(col) = 2.

One trap: exact on PostGIS compares bounding boxes, so Region.objects.filter(boundary=geom) can match a region whose shape differs but whose box is the same. Use equals when you mean the shapes are the same.

Raster lookups

On PostGIS lookups work on rasters on either side, and geometry and raster inputs can be mixed. A band index goes in the left-hand side with the double underscore or in the right-hand side as a tuple: Elevation.objects.filter(rastcontains=geom), rast1contains=geom, rastcontains=(rst, 1). Each lookup has native (N), bilateral (B) or geometry-conversion © raster support, listed in the compatibility table; where the operator does not accept rasters natively Django converts the raster to a polygon with ST_Polygon, which you must keep in mind when interpreting results. Raster lookups were not run here. They were also the subject of a security fix: see Security: the 2026 fixes and what to validate.

Distance queries

Distance lookups take a tuple: the geometry (or raster) to measure from, and the distance, as a number in the field’s units, a Distance object, or a query expression. The five lookups are distance_lt, distance_lte, distance_gt, distance_gte and dwithin (not on MariaDB and MySQL). Distance objects may be in any unit; Django converts to the field’s units.

Distance lookups on a geography column (SQL compiled)
from django.contrib.gis.measure import D
from places.models import Bookshop, Meetup

Meetup.objects.filter(venue__distance_lte=(madrid, D(km=5)))
# WHERE ST_Distance("places_meetup"."venue", ST_GeogFromWKB(<ewkb>)) <= 5000.0

Meetup.objects.filter(venue__dwithin=(madrid, D(km=5)))
# WHERE ST_DWithin("places_meetup"."venue", ST_GeomFromEWKB(<ewkb>), 5000.0)

On the geometry column Bookshop.location (WGS 84) the same intent has two spellings, depending on whether you want an exact distance or an indexed one:

Distance lookups on a WGS 84 geometry column
# Exact, but computed per row and unable to use the spatial index: ST_DistanceSphere
Bookshop.objects.filter(location__distance_lte=(madrid, D(km=2)))

# The 'spheroid' option uses ST_DistanceSpheroid (not on dwithin); the number is in the field's units
Bookshop.objects.filter(location__distance_lte=(madrid, 0.01, "spheroid"))
# WHERE ST_DistanceSpheroid("places_bookshop"."location", ST_GeomFromEWKB(<ewkb>),
#       SPHEROID["WGS 84",6378137.0,298.257223563]) <= 0.01

dwithin is the indexed one, with a catch that was observed and matches the reference: you can only provide Distance objects if the targeted geometries are in a projected system. On a geographic geometry field the lookup refuses a Distance object:

dwithin with a Distance on a geographic geometry field (observed)
Bookshop.objects.filter(location__dwithin=(madrid, D(km=2)))
# ValueError: Only numeric values of degree units are allowed on geographic DWithin queries.

So for dwithin use a projected SRID (delivery_area__dwithin=(point_3857, D(m=500)) compiled to ST_DWithin("places_bookshop"."delivery_area", ST_GeomFromEWKB(<ewkb>), 500.0)), a geography=True field as in the first example, or a number of degrees. With a Distance and a distance lookup on a projected field whose geometry comes in another SRID, Django also transforms the input: ST_Distance(col, ST_Transform(ST_GeomFromEWKB(<ewkb>), 3857)) ⇐ 2000.0.

Distances as annotations and nearest neighbours

To get the distance as a value rather than a filter, annotate with the Distance function; the result is a Distance measure object, so row.distance.km and row.distance.mi are available. On PostGIS a WGS 84 geometry column makes Django pick ST_DistanceSphere (observed), a geography column uses plain ST_Distance, which is already in metres. GeometryDistance is the PostGIS-only function for nearest-neighbour search: used in order_by() it is index-assisted.

Annotating and ordering by distance (SQL compiled)
from django.contrib.gis.db.models.functions import Distance, GeometryDistance

Bookshop.objects.annotate(distance=Distance("location", madrid)).order_by("distance")[:5]
# SELECT ..., ST_DistanceSphere("places_bookshop"."location", ST_GeomFromEWKB(<ewkb>)) AS "distance" ...
#   ORDER BY 3 ASC LIMIT 5

Bookshop.objects.order_by(GeometryDistance("location", madrid))[:3]
# ORDER BY ("places_bookshop"."location" <-> ST_GeomFromEWKB(<ewkb>)) ASC LIMIT 3

The <→ operator behind GeometryDistance is a planar distance in the geometry’s units (degrees on 4326), which is right for ranking and wrong for display; use Distance for the number you show. The <→ ordering is the fast way to answer "the three closest shops" on a large table. The near() manager method in The models used on this page combines a geography dwithin filter with a Distance annotation and compiled to one ST_DWithin and one ST_Distance.

Aggregates

The GIS aggregates (Collect, Extent, Extent3D, MakeLine, Union) live in django.contrib.gis.db.models and since Django 5.0 accept the filter argument. Union dissolves boundaries and is processor-intensive on big querysets; Collect just rolls geometries into a collection or multi geometry and can be several orders of magnitude faster. Extent returns a 4-tuple (lower-left and upper-right corner); MakeLine builds a LineString from points.

Aggregates grouped by region (SQL compiled)

Region.objects.values("name").annotate(u=Union("boundary"))
# ST_Union("places_region"."boundary") AS "u"

CourierRoute.objects.values("name").annotate(l=MakeLine("path"))
# ST_MakeLine("places_courierroute"."path") AS "l"

A complete endpoint for the Bookshelf map. It validates what a client sends, caps the radius, and returns application/geo+json. The queryset is the near() method from The models used on this page:

places/views.py
from django.contrib.gis.geos import Point
from django.core.serializers import serialize
from django.http import HttpResponse, HttpResponseBadRequest

from .models import Meetup


def nearby_meetups(request):
    try:
        lon = float(request.GET["lon"])
        lat = float(request.GET["lat"])
        km = min(float(request.GET.get("km", "5")), 50.0)
        point = Point(lon, lat, srid=4326)  # validated: Point() rejects non-numbers
    except (KeyError, ValueError):
        return HttpResponseBadRequest("lon and lat are required numbers")
    meetups = Meetup.objects.near(point, km)[:20]
    body = serialize("geojson", meetups, geometry_field="venue", fields=["title"])
    return HttpResponse(body, content_type="application/geo+json")

Sync, async and threads

The GeoDjango reference describes no async-specific API: the ORM’s async methods (aget(), acreate(), async for over a queryset) are the way to reach spatial fields from async code, and GEOS and GDAL calls are plain synchronous, CPU-bound functions that block the event loop for as long as they run. In an async view run heavy geometry work with sync_to_async or a worker (see Tasks Framework for background work). The Deploying GeoDjango page adds a warning that deserves attention: GDAL is not thread safe at this time, so it recommends not using threads when deploying; for example set threads to 1 in a mod_wsgi daemon and raise the number of processes instead. Apply the same reasoning to any threaded server configuration.

Security: the 2026 fixes and what to validate

GeoDjango turns user-supplied text into parsers, file handles and SQL fragments, and 2026 produced five advisories in it (all listed in the security archive). Read them as a checklist of what can go wrong:

2026-02-03 (6.0.2, with 5.2 and 4.2 patches)

CVE-2026-1207, severity high: SQL injection through raster lookups on PostGIS

Untrusted data used as a band index (rast<band>contains) was injected into SQL. Validate band indexes as integers.

2026-07-07 (6.0.7, with the 6.1 and 5.2 patches)

What to take from it:

  • Never pass raw user strings, paths or dictionaries into a spatial lookup. Parse and validate the input first, build a GEOSGeometry, and pass that. The fix makes the dangerous inputs fail (observed in 6.1.1: a dict raised a SuspiciousOperation subclass and "/etc/passwd" raised ValueError: String input unrecognized as WKT EWKT, and HEXEWKB). If a trusted piece of code really needs to use a path or dictionary raster in a lookup, wrap it explicitly in GDALRaster(…​); the documentation says that explicit wrapping signals that the value is trusted.

  • Assignments to model fields were not changed. Elevation(rast={…​}) opens a new raster and a string path is fetched, so those fields must never receive request data without your own validation. The GeometryField form field rejects raster values when validating geometry input; for raster input you write the validation.

  • Treat the admin as an entry point. lookup_allowed() lets staff filter the changelist by lookup, so a vulnerable spatial field was reachable by any staff user who can view the model.

  • Limit the drivers GDAL may use where you can (the documentation links GDAL’s own security considerations for defence in depth), and keep coordinates numeric and finite.

  • Keep Django patched. The SQL injection fix landed in 6.0.2, the over-read in 6.0.7 and the other two in 6.0.8 and the matching 6.1 and 5.2 releases; the 5.2 LTS receives them too. The Django 6.1.2 release notes page (dated 2026-10-06, not yet on PyPI when this page was written) also lists "one data loss issue in 4.0": network rasters were deleted by GeoDjango when closed. If you open remote rasters with GDALRaster and close them, wait for 6.1.2 or the matching 5.2 patch release before relying on it, and do not point GDALRaster at a network resource you cannot afford to lose.

Pitfalls checklist

  • Point(x, y) is longitude then latitude; lat, lon pairs pasted from a map site are swapped.

  • A distance in degrees is not a distance in metres. Use geography=True, a projected SRID, or the Distance function and read .m/.km.

  • dwithin with a D(…​) on a geographic geometry field raises ValueError; use a geography or projected field, or degrees.

  • == on geometries is equals_exact(); use equals() for spatial equality. exact on PostGIS compares bounding boxes.

  • A plain Polygon cannot be assigned to a MultiPolygonField (TypeError); LayerMapping converts, assignment does not.

  • ogrinspect on GeoJSON writes max_length=0 for strings; fix the generated model.

  • Form widgets submit coordinates in map_srid (3857); a longitude/latitude GeoJSON without a CRS is misread.

  • Do not use the Union aggregate on a whole table: filter first, or use Collect.

  • Geography columns support only a subset of lookups; Cast to geometry when you need another one.

  • Create GEOS objects inside functions, not at module level.

  • GDAL is not thread safe: keep threads at 1 per process, scale with processes.

  • Never feed request strings, paths or dictionaries to spatial lookups or raster fields.

  • inspectdb and the map widgets only work with django.contrib.gis in INSTALLED_APPS.

  • Without GEOS_LIBRARY_PATH/GDAL_LIBRARY_PATH set to the full library file, "library not found" is the first error you will see; on Linux install binutils too.

  • Spatial test databases need a user that may create them (and the extension, so possibly a superuser).
