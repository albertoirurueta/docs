GeoDjango

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Django 6.1 (6.1.1, released 2026-09-02; 6.1.2 is scheduled for 2026-10-06), Python 3.12-3.14 and PostgreSQL 15 or newer with the PostGIS 3.2-3.6 extension, all checked on 2026-10-03; where the 5.2 LTS (5.2.17) behaves differently the text says so. GeoDjango is the part of Django that lives in django.contrib.gis: model fields for points, lines, polygons and rasters, a spatial lookup and function layer on top of the ORM, Python wrappers for the GEOS and GDAL libraries, form widgets and an admin that edit geometries on a map, and a few import and serialization tools. No PostgreSQL or PostGIS server was available while writing, so nothing on this page that needs a spatial database was executed against one; the GEOS and GDAL parts were executed for real, and the database-facing examples were compiled to SQL with the genuine PostGIS backend classes. The section What was run, and what was not lists, example by example, what was run and what was not. In the Bookshelf application that grows across this section, GeoDjango locates bookshops and book-club meetups, answers "which meetups are within five kilometres of me", measures courier routes and lets the staff drag a shop’s pin on a map in the admin.

What GeoDjango is

GeoDjango is not a separate package: it is django.contrib.gis, installed with Django. It adds, in layers:

  • Model fields for the OGC Simple Features geometry types and for rasters, with a spatial index by default.

  • ORM extensions: spatial lookups such as intersects and dwithin, geographic database functions such as Distance and Transform, and GIS aggregates such as Extent and Union.

  • Python interfaces to GEOS (django.contrib.gis.geos, geometry operations without a database) and GDAL (django.contrib.gis.gdal, reading vector and raster data), plus measurement objects (django.contrib.gis.measure).

  • Forms and admin: map widgets built on OpenLayers and GISModelAdmin.

  • Tools: LayerMapping, the ogrinspect command, a GeoJSON serializer, geographic feeds and KML sitemaps, GeoIP2.

The GEOS and GDAL interfaces work without a database or a settings module (the documentation says they can be used independently of Django), which is how most of the examples on this page were run. Geometries are lazy: when a model instance is loaded the column is kept in a textual form and the GEOSGeometry object is created the first time you access the attribute, which is why shop.location gives you a rich object with wkt, geojson, contains() and dozens of other members.

Installing on PostgreSQL with PostGIS

Installation has four parts: the geospatial libraries, PostGIS in the database server, the database adapter, and Django’s own settings.

The geospatial libraries

GeoDjango locates libgeos_c and libgdal with ctypes.util.find_library(). On Debian and Ubuntu the documentation suggests this one-liner for the libraries and for the binutils that find_library() needs on Linux:

Debian and Ubuntu (documented command)
sudo apt-get install binutils libproj-dev gdal-bin

Source: Installing geospatial libraries

On macOS the documentation lists Postgres.app (the easiest: a PostgreSQL server that already includes PostGIS, plus gdal from Homebrew), Homebrew (brew install postgresql postgis gdal), Fink and MacPorts. On Windows it uses the EnterpriseDB PostgreSQL installer with the PostGIS add-on from Stack Builder and the OSGeo4W installer for GDAL, then sets GDAL_DATA and PROJ_LIB and the PATH. The Python adapter is psycopg (psycopg 3 or psycopg2).

If Django cannot find a library it raises ImportError/ImproperlyConfigured naming the library and telling you to set GEOS_LIBRARY_PATH or GDAL_LIBRARY_PATH. Both settings take the full path of the C shared library; for GEOS it is libgeos_c, not libgeos. That is exactly what the scratch project of this page did, because its libraries came from Python wheels:

config/settings.py (library paths from the environment)
import os

# Only needed when the libraries are not where find_library() looks.
if "GEOS_LIBRARY_PATH" in os.environ:
    GEOS_LIBRARY_PATH = os.environ["GEOS_LIBRARY_PATH"]
if "GDAL_LIBRARY_PATH" in os.environ:
    GDAL_LIBRARY_PATH = os.environ["GDAL_LIBRARY_PATH"]

Source: Installing geospatial libraries, troubleshooting

PostGIS

PostGIS adds geographic object support to PostgreSQL. Install the server package for your platform together with its PostGIS package (on Debian and Ubuntu the documentation names postgresql-x, postgresql-x-postgis-3 and postgresql-server-dev-x, with x the PostgreSQL major version). For a development database a container that already contains both is the quickest route. The postgis/postgis image exists on the registry with tags that pair a PostgreSQL and a PostGIS version, for example 17-3.5; the password is read from your shell instead of being written down:

A throwaway PostGIS database (not run here)
export POSTGRES_PASSWORD="$(python -c 'import secrets; print(secrets.token_urlsafe(16))')"
docker run --name bookshelf-db -e POSTGRES_PASSWORD -e POSTGRES_DB=bookshelf \
    -p 127.0.0.1:5432:5432 -d postgis/postgis:17-3.5

Source: Installing PostGIS. The image is documented at postgis/postgis on Docker Hub.

The extension must exist in the database. Django can create it for you: the PostGIS backend’s prepare_database() checks pg_extension and issues CREATE EXTENSION IF NOT EXISTS postgis when migrate runs (read in the 6.1.1 source), and the documentation says the database user must be a superuser for that. The alternative that keeps the step in version control, and lets a non-superuser deployment pipeline run it as a privileged step, is a migration operation:

places/migrations/0001_initial.py (first operation)
from django.contrib.postgres.operations import CreateExtension
from django.db import migrations


class Migration(migrations.Migration):
    initial = True
    dependencies = []

    operations = [
        CreateExtension("postgis"),
        # CreateModel operations follow
    ]

Source: Creating a spatial database

Two optional extensions: postgis_raster (needed for RasterField, activated with the same CreateExtension operation or CREATE EXTENSION postgis_raster;) and postgis_topology, which GeoDjango does not use. CreateExtension is described on PostgreSQL & Database Backends.

SpatiaLite, MySQL and Oracle in one paragraph

For SQLite, install SpatiaLite 4.3+ (on Debian-based systems libsqlite3-mod-spatialite; with Homebrew brew install spatialite-tools and brew install gdal), make sure SQLite was built with the R*Tree module, use the django.contrib.gis.db.backends.spatialite engine and, when Django cannot find the extension, set SPATIALITE_LIBRARY_PATH to the mod_spatialite library (the documented Homebrew value is /opt/homebrew/lib/mod_spatialite.dylib). SpatiaLite is fine for a prototype or a single-user tool; it cannot do distance calculations between geometries in a geographic coordinate system the way PostGIS can, and rasters are PostGIS-only. MySQL and Oracle need only GEOS and GDAL on the Python side.

The models used on this page

places/models.py
from django.contrib.gis.db import models
from django.contrib.gis.db.models.functions import Distance
from django.contrib.gis.measure import D


class Bookshop(models.Model):
    name = models.CharField(max_length=100)
    # WGS 84 (SRID 4326) is the default; a spatial (GiST) index is created by default.
    location = models.PointField()
    # A projected, metric SRID for the delivery area (Web Mercator here).
    delivery_area = models.PolygonField(srid=3857, null=True, blank=True)

    def __str__(self):
        return self.name


class MeetupQuerySet(models.QuerySet):
    def near(self, point, km):
        """Meetups within ``km`` kilometres of ``point``, nearest first."""
        return (
            self.filter(venue__dwithin=(point, D(km=km)))
            .annotate(distance=Distance("venue", point))
            .order_by("distance")
        )


class Meetup(models.Model):
    objects = MeetupQuerySet.as_manager()
    title = models.CharField(max_length=100)
    # geography=True: a "geography" column; distances are in metres on a sphere.
    venue = models.PointField(geography=True)

    def __str__(self):
        return self.title


class CourierRoute(models.Model):
    name = models.CharField(max_length=100)
    path = models.LineStringField()


class Region(models.Model):
    name = models.CharField(max_length=100)
    boundary = models.MultiPolygonField()

Note the import: from django.contrib.gis.db import models re-exports everything in django.db.models and adds the spatial fields, so one import is enough for a model that mixes both. See Managers & Custom QuerySets for the as_manager() pattern.

Choose the most general type your data needs: a MultiPolygonField is the safe choice for administrative areas because countries have islands. Field options

All spatial fields accept the usual field options plus:

Option Meaning

srid

The spatial reference system identifier. Default 4326 (WGS 84, units are degrees of longitude and latitude). -1 disables automatic SRID transformation on save: the assigned geometry’s SRID is set to -1 and any explicit SRID is discarded.

spatial_index

Default True. Creates a spatial index, usually a variant of an R-tree (GiST on PostGIS). This is not db_index: spatial indexes are created differently from B-tree indexes.

dim

Coordinate dimension, default 2; 3 is supported on PostGIS and SpatiaLite only. The map widgets do not support 3D, so Django falls back to a Textarea for such fields (observed on a PointField(dim=3)).

geography

True creates a geography column instead of geometry. PostGIS only; forces SRID 4326.

max_geom_collections

Geometry fields only. Forwarded to the form field; bounds how many geometry collections may be nested or contained in submitted WKT or WKB. Default 198. Added by the August 2026 security fix (see Security: the 2026 fixes and what to validate).

Choosing an SRID: degrees, projections and geography

The SRID decides how coordinates are read, and therefore what a "distance" means. WGS 84 (4326) stores longitude and latitude, which are angles; one degree is not a fixed number of metres, so a distance between two WGS 84 points is either in degrees (the planar answer) or needs a calculation on the sphere or spheroid. The documentation’s advice has three branches:

  1. Projected system for a region (a metric SRID such as a UTM zone or a national grid): coordinates are in metres or feet, planar distance is exact enough and fast, indexes are used. Only valid inside the region it was designed for.

  2. Geographic system with distance functions (4326 with geometry columns): Django asks PostGIS for ST_DistanceSphere or ST_DistanceSpheroid. Correct, but the spatial index on traditional geometry fields cannot be used, so the distance is computed for every row.

  3. geography=True (PostGIS, forces 4326): distance and measurement operations on a geography column automatically use great circle arc calculations and return linear units, and the index is used. The price is that only a subset of lookups works on geography: besides the distance lookups only bboverlaps, coveredby, covers and intersects.

When you need a geography column in a lookup or aggregate that does not support it, cast it to a geometry in the query:

Cast a geography column to geometry for one query
from django.contrib.gis.db.models import PointField
from django.db.models.functions import Cast

Meetup.objects.annotate(geom=Cast("venue", PointField())).filter(geom__within=polygon)

The compiled SQL contains ("places_meetup"."venue")::geometry(POINT,4326) AS "geom" and WHERE ST_Within"places_meetup"."venue")::geometry(POINT,4326), ST_GeomFromEWKB(<ewkb>. When you save a geometry whose SRID differs from the field’s, Django wraps it in ST_Transform(…​, field_srid) for you (see Creating and saving models with geometry fields). The PostGIS documentation has a section on when to use geography versus geometry; spatialreference.org lists SRIDs.

Operating on geometries

Geometries are "Pythonic": coordinates can be indexed, iterated, changed and appended like lists, and they support set-like operators (| union, & intersection, - difference, ^ symmetric difference). Binary predicates return booleans, constructive operations return new geometries:

Spatial lookups

Lookups are the spatial equivalent of __icontains: they filter on a geometry or raster field and are available on any manager method (filter(), exclude(), get()). Normal lookups can be chained with spatial ones.

Spatial lookups (SQL compiled against the PostGIS backend)
from django.contrib.gis.geos import Point, Polygon
from places.models import Bookshop, Region

madrid = Point(-3.7038, 40.4168, srid=4326)
area = Polygon(((-3.75, 40.38), (-3.75, 40.45), (-3.65, 40.45), (-3.65, 40.38), (-3.75, 40.38)), srid=4326)

Region.objects.filter(boundary__contains=madrid)
# WHERE ST_Contains("places_region"."boundary", ST_GeomFromEWKB(<ewkb>))

Region.objects.filter(boundary__intersects="POINT(-3.7 40.4)")        # WKT is accepted
# WHERE ST_Intersects("places_region"."boundary", ST_GeomFromEWKB(<ewkb>))

Bookshop.objects.filter(location__within=area)
# WHERE ST_Within("places_bookshop"."location", ST_GeomFromEWKB(<ewkb>))

Region.objects.filter(boundary__bbcontains=madrid)                   # bounding boxes only
# WHERE "places_region"."boundary" ~ ST_GeomFromEWKB(<ewkb>)

Region.objects.filter(boundary__relate=(madrid, "T*T***FF*"))         # DE-9IM pattern for "contains"
# WHERE ST_Relate("places_region"."boundary", ST_GeomFromEWKB(<ewkb>), 'T*T***FF*')

Source: Spatial lookups

(In the real SQL the pattern is a quoted parameter; the stubbed str(queryset.query) shows it bare, and Django documents that this string is not necessarily valid SQL.) Choosing between them is mostly about boundaries and cost. contains and within are the strict pair; covers and coveredby treat a point on the boundary as inside, which is what most people mean and, on PostGIS, can be what a geography column supports (contains is not available on geography). intersects is the general-purpose "touches in any way" test and the one to reach for first. bbcontains and the other bounding-box lookups are the cheap pre-filters. Observed in compiled SQL: geom_type="MULTIPOLYGON" becomes GeometryType(col) = 'MULTIPOLYGON', isvalid=False becomes NOT ST_IsValid(col), num_dimensions=2 becomes ST_NDims(col) = 2.

One trap: exact on PostGIS compares bounding boxes, so Region.objects.filter(boundary=geom) can match a region whose shape differs but whose box is the same. Use equals when you mean the shapes are the same.

Distance queries

Distance lookups take a tuple: the geometry (or raster) to measure from, and the distance, as a number in the field’s units, a Distance object, or a query expression. The five lookups are distance_lt, distance_lte, distance_gt, distance_gte and dwithin (not on MariaDB and MySQL). Distance objects may be in any unit; Django converts to the field’s units.

Distance lookups on a geography column (SQL compiled)
from django.contrib.gis.measure import D
from places.models import Bookshop, Meetup

Meetup.objects.filter(venue__distance_lte=(madrid, D(km=5)))
# WHERE ST_Distance("places_meetup"."venue", ST_GeogFromWKB(<ewkb>)) <= 5000.0

Meetup.objects.filter(venue__dwithin=(madrid, D(km=5)))
# WHERE ST_DWithin("places_meetup"."venue", ST_GeomFromEWKB(<ewkb>), 5000.0)

On the geometry column Bookshop.location (WGS 84) the same intent has two spellings, depending on whether you want an exact distance or an indexed one:

Distance lookups on a WGS 84 geometry column
# Exact, but computed per row and unable to use the spatial index: ST_DistanceSphere
Bookshop.objects.filter(location__distance_lte=(madrid, D(km=2)))

# The 'spheroid' option uses ST_DistanceSpheroid (not on dwithin); the number is in the field's units
Bookshop.objects.filter(location__distance_lte=(madrid, 0.01, "spheroid"))
# WHERE ST_DistanceSpheroid("places_bookshop"."location", ST_GeomFromEWKB(<ewkb>),
#       SPHEROID["WGS 84",6378137.0,298.257223563]) <= 0.01

dwithin is the indexed one, with a catch that was observed and matches the reference: you can only provide Distance objects if the targeted geometries are in a projected system. On a geographic geometry field the lookup refuses a Distance object:

dwithin with a Distance on a geographic geometry field (observed)
Bookshop.objects.filter(location__dwithin=(madrid, D(km=2)))
# ValueError: Only numeric values of degree units are allowed on geographic DWithin queries.

So for dwithin use a projected SRID (delivery_area__dwithin=(point_3857, D(m=500)) compiled to ST_DWithin("places_bookshop"."delivery_area", ST_GeomFromEWKB(<ewkb>), 500.0)), a geography=True field as in the first example, or a number of degrees. With a Distance and a distance lookup on a projected field whose geometry comes in another SRID, Django also transforms the input: ST_Distance(col, ST_Transform(ST_GeomFromEWKB(<ewkb>), 3857)) ⇐ 2000.0.

Distances as annotations and nearest neighbours

To get the distance as a value rather than a filter, annotate with the Distance function; the result is a Distance measure object, so row.distance.km and row.distance.mi are available. On PostGIS a WGS 84 geometry column makes Django pick ST_DistanceSphere (observed), a geography column uses plain ST_Distance, which is already in metres. GeometryDistance is the PostGIS-only function for nearest-neighbour search: used in order_by() it is index-assisted.

Annotating and ordering by distance (SQL compiled)
from django.contrib.gis.db.models.functions import Distance, GeometryDistance

Bookshop.objects.annotate(distance=Distance("location", madrid)).order_by("distance")[:5]
# SELECT ..., ST_DistanceSphere("places_bookshop"."location", ST_GeomFromEWKB(<ewkb>)) AS "distance" ...
#   ORDER BY 3 ASC LIMIT 5

Bookshop.objects.order_by(GeometryDistance("location", madrid))[:3]
# ORDER BY ("places_bookshop"."location" <-> ST_GeomFromEWKB(<ewkb>)) ASC LIMIT 3

The <→ operator behind GeometryDistance is a planar distance in the geometry’s units (degrees on 4326), which is right for ranking and wrong for display; use Distance for the number you show. The <→ ordering is the fast way to answer "the three closest shops" on a large table. The near() manager method in The models used on this page combines a geography dwithin filter with a Distance annotation and compiled to one ST_DWithin and one ST_Distance.

Aggregates

The GIS aggregates (Collect, Extent, Extent3D, MakeLine, Union) live in django.contrib.gis.db.models and since Django 5.0 accept the filter argument. Union dissolves boundaries and is processor-intensive on big querysets; Collect just rolls geometries into a collection or multi geometry and can be several orders of magnitude faster. The GIS admin

Registering a model with geometry fields in the ordinary admin already gives you a map: ModelAdmin uses the model field’s default form field, which uses OpenLayersWidget (observed on the scratch project). For an OpenStreetMap layer with street detail use GISModelAdmin from django.contrib.gis.admin. It has two attributes: gis_widget, the widget class for GeometryField (default OSMWidget), and gis_widget_kwargs, the keyword arguments passed to it (default empty).

from .models import Bookshop, Region


@admin.register(Bookshop)
class BookshopAdmin(admin.GISModelAdmin):
    list_display = ["name"]
    gis_widget_kwargs = {
        "attrs": {
            "default_lon": -3.7038,
            "default_lat": 40.4168,
            "default_zoom": 12,

Serving geometries to a map: the GeoJSON serializer

Browsers draw GeoJSON. django.core.serializers.serialize("geojson", queryset, …​) produces a FeatureCollection from model instances. Besides the options of the json serializer it takes geometry_field (needed when a model has several geometry fields; default is the first), id_field (default the primary key), srid (default 4326) and fields (limits properties). It is output only: there is no deserializer, so loaddata cannot reload it.

Serializing (executed, unsaved instances)
from django.core.serializers import serialize
from places.models import Bookshop

shop = Bookshop(pk=1, name="Libros", location=madrid)
serialize("geojson", [shop], geometry_field="location", fields=["name"])
# {"type": "FeatureCollection", "features": [{"type": "Feature", "id": 1, "properties": {"name": "Libros"},
#  "geometry": {"type": "Point", "coordinates": [-3.7038, 40.4168]}}]}

serialize("geojson", [shop], geometry_field="location", srid=3857, id_field="name", fields=["name"])
# "id": "Libros", ... "coordinates": [-412305.1300001266, 4926696.669635533]

A complete endpoint for the Bookshelf map. It validates what a client sends, caps the radius, and returns application/geo+json. The queryset is the near() method from The models used on this page:

places/views.py
from django.contrib.gis.geos import Point
from django.core.serializers import serialize
from django.http import HttpResponse, HttpResponseBadRequest

from .models import Meetup


def nearby_meetups(request):
    try:
        lon = float(request.GET["lon"])
        lat = float(request.GET["lat"])
        km = min(float(request.GET.get("km", "5")), 50.0)
        point = Point(lon, lat, srid=4326)  # validated: Point() rejects non-numbers
    except (KeyError, ValueError):
        return HttpResponseBadRequest("lon and lat are required numbers")
    meetups = Meetup.objects.near(point, km)[:20]
    body = serialize("geojson", meetups, geometry_field="venue", fields=["title"])
    return HttpResponse(body, content_type="application/geo+json")

Feeds, sitemaps and GeoIP

Three smaller tools complete the picture; none was run. django.contrib.gis.feeds.Feed is a syndication feed whose geometry() and item_geometry() methods embed locations in RSS or Atom using the GeoRSSFeed, GeoAtom1Feed (Simple GeoRSS) or W3CGeoFeed classes (the W3C Geo format supports only points). Tests that touch spatial lookups need a spatial database. With PostGIS, Django creates the test database and the extension; if your spatial database template was created like in the instructions, the user only needs the ability to create databases, otherwise a superuser:

Test database user (documented commands)
createuser --createdb -R -S <user_name>
# or, from a superuser psql session:
#   ALTER ROLE <user_name> CREATEDB NOSUPERUSER NOCREATEROLE;

The optional POSTGIS_VERSION = (X, Y, Z) setting tells GeoDjango the PostGIS version and saves the version query at start-up; together with the stubs described in What was run, and what was not it let the scratch project run check and makemigrations without a server. Anything that needs no rows, such as geometry arithmetic, form validation, widget configuration and SQL shape, can be tested with SimpleTestCase and no database at all, which is what the 21 tests in the scratch project do:

places/tests.py (adapted excerpt; the full module of 21 tests passed)
import re

from django.contrib.gis.geos import GEOSGeometry, LineString, Point
from django.contrib.gis.measure import D
from django.test import SimpleTestCase

from .models import Meetup

MADRID = Point(-3.7038, 40.4168, srid=4326)


def sql(queryset):
    """The SQL Django would send, with the binary geometry literal elided."""
    return re.sub(r"E'(?:[^'\\]|\\.)*'::bytea", "<ewkb>", str(queryset.query))


class GeometryTests(SimpleTestCase):
    def test_equality_is_not_spatial_equality(self):
        ls1, ls2 = LineString((0, 0), (1, 1)), LineString((1, 1), (0, 0))
        self.assertTrue(ls1.equals(ls2))
        self.assertFalse(ls1 == ls2)

    def test_nested_collection_limit(self):
        deep = "GEOMETRYCOLLECTION(" * 300 + "POINT(0 0)" + ")" * 300
        with self.assertRaises(ValueError):
            GEOSGeometry(deep)


class NearbyTests(SimpleTestCase):
    def test_queryset_sql(self):
        text = sql(Meetup.objects.near(MADRID, 3))
        self.assertIn("ST_DWithin(", text)
        self.assertIn("ST_Distance(", text)

    def test_dwithin_with_distance_on_geographic_geometry_is_rejected(self):
        from .models import Bookshop

        with self.assertRaisesMessage(ValueError, "Only numeric values of degree units"):
            str(Bookshop.objects.filter(location__dwithin=(MADRID, D(km=2))).query)

Anything that returns rows must be a TestCase against a real PostGIS (marked or tagged so it is skipped where PostGIS is absent). Sync, async and threads

The GeoDjango reference describes no async-specific API: the ORM’s async methods (aget(), acreate(), async for over a queryset) are the way to reach spatial fields from async code, and GEOS and GDAL calls are plain synchronous, CPU-bound functions that block the event loop for as long as they run. In an async view run heavy geometry work with sync_to_async or a worker (see Tasks Framework for background work). The Deploying GeoDjango page adds a warning that deserves attention: GDAL is not thread safe at this time, so it recommends not using threads when deploying; for example set threads to 1 in a mod_wsgi daemon and raise the number of processes instead. Apply the same reasoning to any threaded server configuration.

Security: the 2026 fixes and what to validate

GeoDjango turns user-supplied text into parsers, file handles and SQL fragments, and 2026 produced five advisories in it (all listed in the security archive). Read them as a checklist of what can go wrong:

Fixed Issue What changed

2026-02-03 (6.0.2, with 5.2 and 4.2 patches)

CVE-2026-1207, severity high: SQL injection through raster lookups on PostGIS

Untrusted data used as a band index (rast<band>contains) was injected into SQL. Validate band indexes as integers.

2026-07-07 (6.0.7, with the 6.1 and 5.2 patches)

CVE-2026-53877, severity low: heap buffer over-read in GDALRaster

Building a GDALRaster from a bytes raster could over-read about 32 bytes of the buffer (information disclosure or a crash). Only rasters in GDAL’s virtual filesystem were affected.

2026-08-04 (6.0.8, with the 6.1 and 5.2 patches)

CVE-2026-15307, severity high: server-side file write and request forgery via spatial lookups

Spatial lookups used to pass str and dict values to GDALRaster; depending on the driver that could write a file (in some cases leading to remote code execution) or send a network request. The admin changelist made it reachable by staff with view permission on any model with a spatial field. Lookups now reject dict, pathlib.Path and any str that is not valid GEOS input. This is backward incompatible.

2026-08-04 (6.0.8, with the 6.1 and 5.2 patches)

CVE-2026-15830, severity moderate: denial of service through nested geometry collections

Deeply nested GEOMETRYCOLLECTION input crashed GEOS with a segmentation fault. A maximum of 198 collections is enforced (nesting depth for WKT, total count for WKB); configure it with the new max_geom_collections argument on GEOSGeometry, the form field and the model field. GeoJSON is not affected, because GDAL parses it.

Source: Archive of security issues and the release notes 6.0.2, 6.0.7 and 6.0.8

What to take from it:

  • Never pass raw user strings, paths or dictionaries into a spatial lookup. Parse and validate the input first, build a GEOSGeometry, and pass that. The fix makes the dangerous inputs fail (observed in 6.1.1: a dict raised a SuspiciousOperation subclass and "/etc/passwd" raised ValueError: String input unrecognized as WKT EWKT, and HEXEWKB). If a trusted piece of code really needs to use a path or dictionary raster in a lookup, wrap it explicitly in GDALRaster(…​); the documentation says that explicit wrapping signals that the value is trusted.

  • Assignments to model fields were not changed. Elevation(rast={…​}) opens a new raster and a string path is fetched, so those fields must never receive request data without your own validation. The GeometryField form field rejects raster values when validating geometry input; for raster input you write the validation.

  • Treat the admin as an entry point. lookup_allowed() lets staff filter the changelist by lookup, so a vulnerable spatial field was reachable by any staff user who can view the model.

  • Limit the drivers GDAL may use where you can (the documentation links GDAL’s own security considerations for defence in depth), and keep coordinates numeric and finite.

  • Keep Django patched. The SQL injection fix landed in 6.0.2, the over-read in 6.0.7 and the other two in 6.0.8 and the matching 6.1 and 5.2 releases; the 5.2 LTS receives them too. The Django 6.1.2 release notes page (dated 2026-10-06, not yet on PyPI when this page was written) also lists "one data loss issue in 4.0": network rasters were deleted by GeoDjango when closed. If you open remote rasters with GDALRaster and close them, wait for 6.1.2 or the matching 5.2 patch release before relying on it, and do not point GDALRaster at a network resource you cannot afford to lose.

Source: GDAL API, security considerations and Django 6.1.2 release notes

Pitfalls checklist

  • Point(x, y) is longitude then latitude; lat, lon pairs pasted from a map site are swapped.

  • A distance in degrees is not a distance in metres. Use geography=True, a projected SRID, or the Distance function and read .m/.km.

  • dwithin with a D(…​) on a geographic geometry field raises ValueError; use a geography or projected field, or degrees.

  • == on geometries is equals_exact(); use equals() for spatial equality. exact on PostGIS compares bounding boxes.

  • A plain Polygon cannot be assigned to a MultiPolygonField (TypeError); LayerMapping converts, assignment does not.

  • ogrinspect on GeoJSON writes max_length=0 for strings; fix the generated model.

  • Form widgets submit coordinates in map_srid (3857); a longitude/latitude GeoJSON without a CRS is misread.

  • Do not use the Union aggregate on a whole table: filter first, or use Collect.

  • Geography columns support only a subset of lookups; Cast to geometry when you need another one.

  • Create GEOS objects inside functions, not at module level.

  • GDAL is not thread safe: keep threads at 1 per process, scale with processes.

  • Never feed request strings, paths or dictionaries to spatial lookups or raster fields.

  • inspectdb and the map widgets only work with django.contrib.gis in INSTALLED_APPS.

  • Without GEOS_LIBRARY_PATH/GDAL_LIBRARY_PATH set to the full library file, "library not found" is the first error you will see; on Linux install binutils too.

  • Spatial test databases need a user that may create them (and the extension, so possibly a superuser).
