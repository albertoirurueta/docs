A URLconf is the table of contents of a Django site: a Python module whose urlpatterns list maps URL paths to views, and, because the same table can be read backwards, it is also the only place that knows what a URL looks like. This page covers both directions. Going forward it explains path() and re_path(), the converters that turn text from the URL into Python values, include() and the application and instance namespaces that make URLs from different apps coexist, and the error handlers that answer when nothing matches. Going backward it explains reverse(), reverse_lazy(), get_absolute_url() and the {% url %} template tag, so that no URL is ever typed twice. It closes with the checks Django runs on your URLconf, per-request URLconfs, translated URLs and a step-by-step migration from the long-removed url() function that most older tutorials still use. The views that the patterns point at are covered on the pages about function-based views, class-based views and generic views; where the URLconf sits in the whole request is on the request/response cycle page; the project layout that holds config/urls.py and catalog/urls.py is on Project Structure & Apps; and the first path() you ever write is on Getting Started.

Where the URLconf sits in the request/response cycle

Routing is the step between the middleware chain and the view. When the handler (WSGI or ASGI) receives a request it builds an HttpRequest, runs it down through the middleware listed in MIDDLEWARE, and only then, inside the innermost layer, resolves the path. Django’s documentation lists the algorithm exactly:

  1. Django picks the root URLconf module. Normally this is the ROOT_URLCONF setting, but if the HttpRequest has a urlconf attribute (set by a middleware that ran earlier) its value is used instead.

  2. Django imports that module and reads its urlpatterns variable, a sequence of path() and/or re_path() instances (and include() results).

  3. It runs through the patterns in order and stops at the first one that matches request.path_info, the path without the host, the query string or any script prefix.

  4. It imports and calls the view with the HttpRequest as the first argument, plus the captured values as keyword arguments (or positional arguments, if the pattern used unnamed regular-expression groups), overridden by the optional kwargs dictionary of the pattern.

  5. If no pattern matches, or any exception is raised on the way, Django calls an error-handling view.

Four consequences follow from this picture and come back in the sections below:

  • The URL is matched on the path alone. The query string, the domain and the HTTP method play no part (GET /books/ and POST /books/ reach the same view); the view or a decorator decides what to do with the method.

  • request.resolver_match exists only after resolution. It is available in views, in process_view() and later hooks, and in template contexts, but not in the "before the view" part of a middleware’s call, which runs first.

  • The resolver is built once. get_resolver() is cached per URLconf module, and the regular expressions of the patterns are compiled the first time they are needed, so routing cost per request is a sequential scan of compiled patterns, not an import.

  • Resolution is synchronous and CPU-only. The ASGI handler calls it directly in the event loop; it does no I/O, so an async view is routed exactly like a sync one (see Sync and async notes).

The Bookshelf URL design used on this page

Every example belongs to the Bookshelf catalogue, an app named catalog in a project named config. The model is small, because what matters here is the URL design. get_absolute_url() is the canonical way to give a model instance an address and it already uses reverse() (explained in reverse() and reverse_lazy()):

catalog/models.py
from django.db import models
from django.urls import reverse


class Book(models.Model):
    title = models.CharField(max_length=200)
    slug = models.SlugField(unique=True)
    isbn = models.CharField(max_length=13, unique=True)

    def __str__(self):
        return self.title

    def get_absolute_url(self):
        return reverse("catalog:book-detail", kwargs={"slug": self.slug})

path(): routes, kwargs and name

path(route, view, kwargs=None, name=None) returns one element of urlpatterns.

  • route is a string (or a gettext_lazy() string, see Translated and language-prefixed URLs) containing the pattern. Angle brackets capture a part of the URL and pass it to the view as a keyword argument (<slug:slug>); the part before the colon is the converter, which limits what matches and what Python type the view receives. Without a converter the capture is str and matches any non-empty text except /.

  • view is a function, the result of View.as_view() for class-based views, or an include(). Passing the class itself (a frequent slip: views.BookCreate instead of views.BookCreate.as_view()) is caught by the system check urls.E009.

  • kwargs is a dictionary of extra keyword arguments added to every call (Extra options and default arguments).

  • name makes the pattern reversible (Naming URL patterns).

Some rules are easy to miss and cause real bugs:

  • No leading slash. Every URL has one, so you write books/, never /books/ (system check urls.W002).

  • Order matters: the first match wins. In catalog/urls.py books/new/ comes before books/<slug:slug>/; swap them and the create page becomes a book with the slug new, which get_object_or_404 turns into a 404. Put specific literals before generic captures.

  • Trailing slashes are part of the pattern. books/ does not match /books (Trailing slashes and APPEND_SLASH). Pick a convention (Django’s is a trailing slash on pages, none on file-like URLs such as sitemap.xml or robots.txt) and keep to it.

  • The method, the query string and the host are not matched. https://example.com/books/?page=3 is looked up as books/.

  • Patterns are matched against path_info. Behind a proxy that mounts the project under a prefix, the prefix is the script prefix and is not part of the route (The script prefix and mounting under a sub-path).

Converters have two jobs and one rule. They match (the regex), they convert (to_python() for the URL to the view, to_url() for reverse()), and ValueError raised from either one means "this pattern does not apply": an incoming URL falls through to the next pattern and finally to a 404, and a reverse lookup raises NoReverseMatch unless another pattern with the same name fits. Raising ValueError from to_url() has been supported since Django 3.1.

Custom converters

A converter is a plain class with a regex string attribute and the two methods. The Bookshelf registers two: a four-digit year, taken from the official documentation’s own example, and an ISBN-13 whose check digit is validated, so a mistyped ISBN is a 404 at routing time instead of a failed lookup inside the view:

catalog/converters.py
class FourDigitYearConverter:
    regex = "[0-9]{4}"

    def to_python(self, value):
        return int(value)

    def to_url(self, value):
        return "%04d" % value


class Isbn13Converter:
    """Matches 13 digits and rejects numbers whose check digit is wrong."""

    regex = "[0-9]{13}"

    @staticmethod
    def _valid(digits: str) -> bool:
        total = sum(int(d) * (1 if i % 2 == 0 else 3) for i, d in enumerate(digits[:12]))
        return (10 - total % 10) % 10 == int(digits[12])

    def to_python(self, value):
        if not self._valid(value):
            raise ValueError(value)  # no match: Django tries the next pattern, then 404
        return value

    def to_url(self, value):
        value = str(value)
        if len(value) != 13 or not value.isdigit() or not self._valid(value):
            raise ValueError(value)  # reverse() raises NoReverseMatch
        return value

register_converter(converter, type_name) takes the class (not an instance; Django instantiates it) and the name used inside angle brackets. Call it at import time of a URLconf module, as catalog/urls.py does above, so the name exists before any pattern uses it. Two details matter on Django 6.1:

  • Registering a name twice, or a name that is a built-in (int, str, …​), raises ValueError("Converter 'yyyy' is already registered."). Overriding converters was deprecated in Django 5.1 and became an error in 6.0; a test below pins this behaviour.

  • The regex is spliced into the pattern’s regular expression, so it must not contain capturing groups. Use (?:…​) if you need grouping.

Pitfalls specific to converters:

  • int accepts leading zeros and has no upper bound. /page/007/ resolves to the same view as /page/7/, and reverse() always gives /page/7/. Two URLs for one page is a duplicate-content problem for search engines; if it matters, use a stricter custom converter ([1-9][0-9]*).

  • slug is ASCII only. If your slugs contain accented characters, use str with a model lookup, or a custom converter with the regex you need.

  • Converters match text, not existence. <int:pk> matches /books/999999/ even if there is no such book; the 404 comes from the view (get_object_or_404), not the router.

re_path(): regular expressions

re_path(route, view, kwargs=None, name=None) is path() with a regular expression for the route, compatible with Python’s re module. It is the direct successor of the old url() (Migrating from url() to path() and re_path()). Use it when no combination of converters expresses what you need: optional segments, several alternatives in one pattern, matching a fixed number of digits without writing a converter, or legacy URLs that must keep working character for character.

  • Write the route as a raw string (r"…​") so that sequences like \d need no doubled backslash.

  • If the route ends in $, the whole of path_info must match (re.fullmatch() is used); otherwise the pattern matches a prefix, which is how include() prefixes work with re_path().

  • Named groups (?P<name>…​) become keyword arguments; unnamed groups (…​) become positional arguments. Mixing both styles in one pattern is a bug waiting to happen: when both appear, the unnamed groups are ignored.

  • All values arrive as strings. There is no type conversion with re_path(). Switching a pattern between path() and re_path() changes the type of the view’s arguments, so adapt the view.

  • Use non-capturing groups (?:…​) for structure that the view does not need. Nested capturing groups pass the outer and the inner match to the view and, worse, force you to reverse with a piece of URL.

Extra options and default arguments

There are three ways to give a view values that are not in the URL, and each is visible in catalog/urls.py:

  • The kwargs dictionary (third positional argument of path()): path("about/", views.echo, {"template": "about"}, name="about") calls echo(request, template="about"). If a captured name and a dictionary key collide, the dictionary wins. The syndication framework uses this technique to hand options to its feed views.

  • Defaults on the view: page/ and page/<int:num>/ both point at views.page, whose signature is def page(request, num=1). The first pattern captures nothing, so the view’s default applies. Give the two patterns distinct names (page-first, page) or reverse them by argument count; Django also matches names by the number and names of the arguments you pass.

  • include() with extra options: path("blog/", include("inner"), {"blog_id": 3}) passes blog_id=3 to every pattern of the included module, whether or not the view accepts it. Use it only when you control all the views in the module.

include(): composing URLconfs

include() mounts another set of patterns under a prefix. Django chops off the part of the URL matched so far and hands the rest to the included patterns, so catalog/urls.py never needs to know whether it lives at /, /shop/ or /outlet/. The signatures are:

  • include(module, namespace=None): a dotted path to a URLconf module (or the module object itself). The application namespace is taken from the module’s app_name.

  • include(pattern_list): any iterable of path()/re_path() instances, for small inline groups.

  • include((pattern_list, app_namespace), namespace=None): a 2-tuple that carries the application namespace with the list.

Typical uses, taken from the official guide and from config/urls.py above:

from django.urls import include, path

from credit import views as credit_views

extra_patterns = [
    path("reports/", credit_views.report),
    path("reports/<int:id>/", credit_views.report),
    path("charge/", credit_views.charge),
]

urlpatterns = [
    path("help/", include("apps.help.urls")),         # a module, by dotted path
    path("credit/", include(extra_patterns)),         # an inline list
    # one prefix, many suffixes: state the common part once
    path(
        "<page_slug>-<page_id>/",
        include([path("history/", views.history), path("edit/", views.edit)]),
    ),
]

Rules for include():

  • Captured parameters flow down. path("<username>/blog/", include("foo.urls.blog")) passes username to every view of foo/urls/blog.py.

  • Never end the prefix route of an include() with $. The rest of the URL must still be matched by the included patterns, so a $ makes everything below it unreachable; system check urls.W001 warns about it (System checks for the URLconf).

  • A trailing slash on the prefix is conventional. include("catalog.urls") under path("shop", …​) would give /shopbooks/.

  • include() order is match order. path("", include("catalog.urls")) in config/urls.py is last on purpose: an empty prefix matches every URL, so anything placed after it that it can match is shadowed.

  • i18n_patterns() cannot be used inside an included URLconf, only in the root one (Translated and language-prefixed URLs).

  • Mount a project’s URLs in one place. Keep the include list in config/urls.py short and let each app own its patterns; this is the same boundary as the app boundary described on Project Structure & Apps.

include() also validates its arguments. Asking for an instance namespace without an application namespace is an error, which the scratch project reproduced as:

ImproperlyConfigured: Specifying a namespace in include() without providing an app_name is not supported. Set the app_name attribute in the
included module, or pass a 2-tuple containing the list of patterns and app_name instead.

Naming URL patterns

Reversing needs names. Any string is allowed (it is not a Python identifier), but follow these rules:

  • Give every pattern that you link to a name, and name patterns after what they are, not where they are: book-detail, book-create, not books-slug-view.

  • Avoid names that other apps might use. If two apps both call a pattern comment, reverse("comment") finds whichever is last in the project’s urlpatterns. Prefix with the app (catalog-comment) or, better, use a namespace (Application and instance namespaces).

  • Do not put a colon in a name. The colon is the namespace separator (system check urls.W003).

  • Reuse a name deliberately to override a view. Django’s own LoginView is found by reverse("login"); if you name your own login route login and include it after django.contrib.auth.urls, reverse() finds yours.

  • The same name can serve several patterns if they differ in their arguments. reverse() matches the name, the number of positional arguments or the names of the keyword arguments, and any converter that raises ValueError in to_url().

Application and instance namespaces

Namespaces let different apps (or several copies of one app) use the same URL names without clashing. A namespace has two parts, and both are strings:

  • Application namespace: the name of the app being deployed. Every instance of an app shares it. It comes from app_name in the included module or from the 2-tuple form of include(). Django’s admin has the application namespace admin.

  • Instance namespace: identifies one deployment of the app. It must be unique across the project. By default it equals the application namespace, which makes that instance the default instance; pass namespace="shop" to include() to give it another name.

A namespaced name is written app:name, and namespaces nest: api:v1:book-list is the pattern book-list in the namespace v1, itself inside api. The Bookshelf uses all of it. catalog/urls.py sets app_name = "catalog"; config/urls.py includes the module three times (instances shop, outlet, and the default instance catalog at the root), and api_urls.py includes api_v1_urls.py, each with its own app_name.

When Django reverses catalog:book-list it follows the documented strategy, which is worth knowing by heart because it explains most "why did the link go to the wrong place" surprises:

flowchart TD start(["reverse of app:name"]) --> appns{"app matches an
application namespace?"} appns -->|"no"| inst["Look up app as an instance namespace directly"] appns -->|"yes: a list of instances"| cur{"current_app given
or request.current_app set?"} cur -->|"yes"| use1["Use that instance, if it is one of the list"] cur -->|"no"| def{"An instance whose namespace
equals the application namespace?"} def -->|"yes"| use2["Use the default instance"] def -->|"no"| use3["Use the last deployed instance"] inst --> done(["Resolve the name inside the instance"]) use1 --> done use2 --> done use3 --> done

Applied to the Bookshelf’s config/urls.py, the observed behaviour is:

  • reverse("shop:book-list") and reverse("outlet:book-list") always go to that instance: /shop/ and /outlet/.

  • reverse("catalog:book-list") with no current instance goes to the default instance (instance namespace catalog): /. With only the shop and outlet includes (no default instance), the same call returns /outlet/, the last deployed instance (checked with a throw-away URLconf), which is the surprise that bites people who add a second instance later; current_app="shop" there returns /shop/.

  • reverse("catalog:book-list", current_app="outlet") goes to /outlet/. The current_app hint is how a page rendered inside the outlet instance keeps its links inside it.

  • The {% url %} tag takes the namespace of the currently resolved view (request.resolver_match.namespace) as the current app, unless you set request.current_app (The {% url %} template tag). In a class-based view, pass current_app=self.request.resolver_match.namespace to reverse() yourself.

Pitfalls:

  • Duplicate instance namespaces. Two include() calls with the same namespace make one of them unreachable by name; system check urls.W005 warns ("URL namespace …​ isn’t unique").

  • A namespace without an app_name is an ImproperlyConfigured error since Django 2.0 (see above).

  • Reversing a namespaced view by its callable does not work: reverse(views.archive) only reverses non-namespaced patterns. Always reverse by name.

  • Do not hardcode instance names in reusable code. A reusable app should reverse its own names through its application namespace and let the project decide how many instances to deploy (that is what AdminSite instances do).

reverse() and reverse_lazy()

reverse(viewname, urlconf=None, args=None, kwargs=None, current_app=None, , query=None, fragment=None) returns the absolute *path (no scheme or host) for a URL pattern name. It is the Python-code counterpart of the {% url %} tag, and the reason a URL is written exactly once, in the URLconf.

  • viewname is a pattern name ("catalog:book-detail") or, discouraged, a callable view object from the URLconf. A view built with as_view() can be reversed by object only if the same object is used in the URLconf, and namespaced views cannot be reversed by object.

  • args or kwargs, never both: passing both raises ValueError.

  • current_app is the hint described in Application and instance namespaces.

  • urlconf names a different URLconf module to reverse against (default: the root URLconf of the current thread, which is request.urlconf if a middleware set one).

  • query (Django 5.2 and later, keyword-only) is added to the returned URL after a ?. It accepts a QueryDict (for example request.GET) or anything urllib.parse.urlencode() accepts: a dict, or a list of pairs for repeated keys. Values are encoded for you.

  • fragment (5.2 and later) is appended after #, without encoding.

  • The result is already URL-quoted. Do not run it through urllib.parse.quote() again.

  • If nothing matches, NoReverseMatch is raised. Its message lists every pattern that was tried.

reverse_lazy()

reverse_lazy() has the same signature but evaluates when the value is first used. It is needed whenever the URL is required before the URLconf can be loaded, which is typically at import time of a module that the URLconf itself imports:

  • the success_url attribute of a generic class-based view (a class body runs at import);

  • the login_url argument of a decorator such as permission_required;

  • a default value in a function signature.

BookCreate in catalog/views.py shows the first case, and the test test_create_view_uses_reverse_lazy_success_url above posts a form and follows the redirect. Calling plain reverse() in that class body would try to import config.urls while catalog.views is still being imported, a circular import. Inside a method, which runs per request, use reverse(); the lazy version only adds a proxy.

resolve() and ResolverMatch

resolve(path, urlconf=None) does what the dispatcher does: it turns a path into a ResolverMatch, or raises Resolver404 (a subclass of Http404) when nothing matches. Use it in tests, in middleware that needs to know which view will run, and in tools. A ResolverMatch carries:

Attribute Meaning

func

The view callable (for a class-based view, the function returned by as_view(), which has a view_class attribute).

args, kwargs

The positional and keyword arguments the view will receive. kwargs is captured_kwargs plus extra_kwargs.

captured_kwargs, extra_kwargs

The values captured from the URL, and the values added by the kwargs dictionary of path()/include().

url_name

The name of the matched pattern.

route

The route of the matching pattern, for example shop/published/<yyyy:year>/.

app_name, app_names

The application namespace (and its components: foo:bar gives ['foo', 'bar']).

namespace, namespaces

The instance namespace and its components.

view_name

The name including the namespace, e.g. shop:by-year, or the dotted path of the view if the pattern has no name.

tried

The patterns tried before the match; useful in debugging.

A ResolverMatch unpacks as the triple (func, args, kwargs); the session in the reverse demo above printed one:

ResolverMatch(func=catalog.views.echo, args=(), kwargs={'year': 2024}, url_name='by-year', app_names=['catalog'], namespaces=['shop'], route='shop/published/<yyyy:year>/', captured_kwargs={'year': 2024})

During a request the same object is request.resolver_match; the echo view uses it to print view_name, route and the namespaces (see the curl output earlier on this page). It is how logging, analytics and CSS "active link" helpers know which route is running (request.resolver_match.url_name) without parsing the path.

The {% url %} template tag

In templates, {% url %} is reverse(): the first argument is the pattern name (a quoted literal or a context variable) and the rest are the arguments, positional or keyword but never mixed. Special characters in the result are encoded with iri_to_uri().

<h1>Books</h1>
<ul>
{% for book in books %}
  <li><a href="{{ book.get_absolute_url }}">{{ book.title }}</a>
      (<a href="{% url 'catalog:by-isbn' isbn=book.isbn %}">ISBN</a>)</li>
{% empty %}
  <li>No books yet.</li>
{% endfor %}
</ul>

<p>Archive: <a href="{% url 'catalog:by-year' 2024 %}">2024</a></p>

{% if optional_url %}<a href="{{ optional_url }}">never rendered</a>{% else %}no optional page{% endif %}
<p>Next: <a href="{% url 'catalog:book-list' %}{% querystring page=2 %}">page 2</a></p>

  • {% url 'catalog:by-isbn' isbn=book.isbn %} uses keyword syntax; {% url 'catalog:by-year' 2024 %} uses positional syntax.

  • {% url 'catalog:missing-page' as optional_url %} stores the URL in a variable instead of printing it and, unlike the plain form, does not raise NoReverseMatch when the name does not exist; the variable is empty and {% if %} handles it. The variable is scoped to the enclosing {% block %}. This is how a reusable template links to an optional page.

  • A missing name without as var raises NoReverseMatch and the page becomes a 500 (a debug page with DEBUG = True). That is the intended fail-fast behaviour for a link you expect to exist.

  • The tag has no query or fragment argument. Append a query string with {% querystring %} (Django 5.1 and later), as in the last line of the template, or write ?q={{ term|urlencode }} by hand.

  • Always quote the name. {% url book-detail book.slug %} without quotes looks up a context variable named book-detail, which is a syntax or NoReverseMatch error at best and silently wrong at worst.

  • The namespace of the current view is used as the current app, so a template served by the shop instance links to /shop/, as the test test_url_tag_follows_the_current_instance verifies. It needs django.template.context_processors.request or a RequestContext (render() provides one). To override the choice, set request.current_app in the view before rendering.

  • For links to model instances prefer {{ book.get_absolute_url }}: the model, not each template, then decides what a book’s address is.

Error handlers: handler400, handler403, handler404 and handler500

When no pattern matches, or a view raises, Django calls one of four error views. The defaults live in django.views.defaults and render 400.html, 403.html, 404.html and 500.html from the top of your template tree if you provide them (they are used when DEBUG is False; the 404 template receives request_path and exception, the 403 template receives exception, and the 400 and 500 templates receive no exception text on purpose, so that nothing is disclosed). Override a handler by assigning a callable or a dotted path to a module-level variable of the root URLconf; setting it in any other URLconf has no effect.

Variable Raised by Signature

handler400

SuspiciousOperation and its subclasses (bad host header, malformed multipart upload…​)

view(request, exception), returns HttpResponseBadRequest

handler403

PermissionDenied

view(request, exception), returns HttpResponseForbidden

handler404

Http404, including the Resolver404 of an unmatched URL

view(request, exception), returns HttpResponseNotFound

handler500

Any other exception raised by a view

view(request), no exception argument; returns HttpResponseServerError

Since Django 2.0, custom 400, 403 and 404 views that do not accept the exception argument are no longer supported (and the default handlers became callables instead of dotted paths); system checks urls.E007 and urls.E008 verify, at startup, that each custom handler can be imported and takes the right number of arguments. The Bookshelf’s handlers answer in JSON, which is what an API wants; an HTML site would render() a template instead:

catalog/error_views.py
from django.http import JsonResponse


def not_found(request, exception):
    # For an unmatched URL the exception is a Resolver404 whose first argument is a dict
    # ({"tried": [...], "path": ...}) describing your whole URLconf: never echo str(exception).
    message = exception.args[0] if exception.args and isinstance(exception.args[0], str) else ""
    return JsonResponse({"error": "not found", "path": request.path, "detail": message}, status=404)


def permission_denied(request, exception):
    return JsonResponse({"error": "forbidden"}, status=403)


def bad_request(request, exception):
    return JsonResponse({"error": "bad request"}, status=400)


def server_error(request):  # no `exception` argument: Django calls handler500(request)
    return JsonResponse({"error": "server error"}, status=500)

  • Never echo str(exception) for a URL that did not match. Choosing the URLconf per request

request.urlconf, when set by middleware, replaces ROOT_URLCONF for that request, and setting it to None returns to the default. This is how a single Django process serves several hostnames with different routes (an api. subdomain, a "club" site, a staff site) without running several projects. HostUrlconfMiddleware serves config/urls_api_host.py for hosts that start with api.:

catalog/middleware.py
class HostUrlconfMiddleware:
    """Serve a different URLconf for api.* hosts by setting request.urlconf."""

    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        host = request.get_host().split(":")[0]
        if host.startswith("api."):
            request.urlconf = "config.urls_api_host"
        return self.get_response(request)

Trailing slashes and APPEND_SLASH

CommonMiddleware implements the APPEND_SLASH setting (default True): if a request path does not end in /, does not match any pattern, but would match once a slash is appended, the middleware answers with a permanent redirect (301) to the slash form. The test test_first_match_wins_and_trailing_slash and the real server agree:

$ curl -si 'localhost:8822/about'
HTTP/1.1 301 Moved Permanently
Location: /about/

Things to know:

  • A POST cannot be redirected without losing its body. With DEBUG = True, an unslashed POST, PUT, PATCH or DELETE that would need the redirect raises a RuntimeError explaining the problem, so that you notice in development. In production it silently becomes a 301 and the data is lost; point forms at the slashed URL (generate it with {% url %}).

  • Opt a view out with @no_append_slash from django.views.decorators.common (added in Django 3.2), for URLs that are intentionally slash-less, such as file-like endpoints.

  • The redirect only fires when the slash form exists. /nope stays a 404, not a redirect to /nope/.

  • Set APPEND_SLASH = False for an API whose clients must get a clean 404 for the wrong spelling.

  • Case counts. /Books/ does not match books/. Django does not normalise case; add a redirect or lower-case at the proxy if you need tolerance.

URLconfs that Django and other packages give you

Several pieces ship URLs that you include(); each has an app_name or a fixed set of names that other code expects:

  • The admin: path("admin/", admin.site.urls) (namespace admin; reverse("admin:index"), reverse("admin:app_list", kwargs={"app_label": "auth"})).   • Authentication: path("accounts/", include("django.contrib.auth.urls")) adds login, logout, password_change and the password reset URLs under unnamespaced names (login, logout…​), which is why LOGIN_URL = "login" works. LogoutView accepts only POST since Django 5.0, so a logout link must be a small form.

  • Static and media files in development: static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT) from django.conf.urls.static returns a pattern that serves files when DEBUG is true, and an empty list otherwise (and for prefixes that include a host). It is a development convenience, never a production file server (see the static-files and file-upload pages). STATIC_URL/MEDIA_URL must end with a slash (system check urls.E006).

  • Third-party and debug tools: django-debug-toolbar adds path("debug/", include("debug_toolbar.urls")); REST frameworks give you routers that generate a URLconf from a viewset; admin sites for different audiences are separate AdminSite instances, which is the instance-namespace feature at work.

Translated and language-prefixed URLs

i18n_patterns(urls, prefix_default_language=True) from django.conf.urls.i18n prepends the active language code to the patterns it wraps (/en/books/, /es/books/), reverse() and {% url %} produce the URL in the active language, and routes may be marked translatable with gettext_lazy() (path(_("books/"), …​)). It needs LocaleMiddleware, can only be used in the *root URLconf (using it in an included one raises ImproperlyConfigured), and prefix_default_language=False keeps existing URLs unprefixed for the default language. Translating a segment needs a message catalogue, which is the subject of the internationalization page; the test below checks the prefixing without one, and the unprefixed /books/ is redirected by the middleware:

config/urls_i18n.py
from django.conf.urls.i18n import i18n_patterns
from django.urls import path
from django.utils.translation import gettext_lazy as _

from catalog import views

urlpatterns = i18n_patterns(
    path(_("books/"), views.echo, name="books"),  # translated route: needs a catalogue to differ per language
    prefix_default_language=True,
)

The script prefix and mounting under a sub-path

If a proxy serves the project under a path such as /bookshelf/, the WSGI server passes that prefix as SCRIPT_NAME, Django stores it with set_script_prefix(), and reverse(), {% url %} and redirects add it automatically, while patterns keep matching path_info without it. FORCE_SCRIPT_NAME sets it explicitly. get_script_prefix() returns it (it is "/" when the project is at the root) and, as the documentation warns, it cannot be used outside a request/response cycle because it relies on values initialised then. The test test_reverse_honours_the_script_prefix above proves that reverse() adds /bookshelf/ when the prefix is set. Never concatenate the prefix by hand: use reverse() so that the same code works at / and under a sub-path.

from django.core.management.base import BaseCommand
from django.urls import URLPattern, URLResolver, get_resolver


def walk(patterns, prefix="", namespace=""):
    for entry in patterns:
        route = prefix + str(entry.pattern)
        if isinstance(entry, URLResolver):
            ns = f"{namespace}{entry.namespace}:" if entry.namespace else namespace
            yield from walk(entry.url_patterns, route, ns)
        elif isinstance(entry, URLPattern):
            yield route, f"{namespace}{entry.name}" if entry.name else "-", entry.lookup_str


class Command(BaseCommand):
    help = "Print every route of the root URLconf as: route, namespaced name, view."

    def handle(self, *args, **options):
        for route, name, view in walk(get_resolver().url_patterns):
            self.stdout.write(f"{route:<42} {name:<22} {view}")

Migrating from url() to path() and re_path()

Before Django 2.0 there was one routing function, django.conf.urls.url(), which took a regular expression. Django 2.0 added path() (readable routes with converters) and re_path() (the same regular-expression behaviour as url()), made include importable from django.urls, and Django 3.1 deprecated url(); it was removed in Django 4.0. On Django 6.1 the import fails:

ImportError: cannot import name 'url' from 'django.conf.urls'

(This is also asserted by the test test_old_url_import_is_gone.) The migration has two levels, and you can stop at the first one:

  1. Mechanical: rename url( to re_path( and import it from django.urls. The regular expressions stay, so the same URLs match and the view still receives strings. This is safe and enough to run on a current Django.

  2. Idiomatic: convert the patterns that a converter expresses well to path(), and adapt the views for the new argument types.

Typical conversions:

Old New Notes

url(r"^$", v, name="home")

path("", v, name="home")

No ^, no $, no leading slash.

url(r"^books/(?P<pk>[0-9]+)/$", v)

path("books/<int:pk>/", v)

pk is now an int; /books/007/ still matches.

url(r"^tag/(?P<slug>[-\w]+)/$", v)

path("tag/<slug:slug>/", v)

slug is ASCII only; \w also matches Unicode letters.

url(r"^archive/(?P<year>[0-9]{4})/$", v)

re_path(r"^archive/(?P<year>[0-9]{4})/$", v) or a yyyy converter

<int:year> would accept any number of digits.

url(r"^blog/", include("blog.urls", namespace="blog", app_name="blog"))

path("blog/", include("blog.urls", namespace="blog")) plus app_name = "blog" in blog/urls.py

The app_name argument of include() was removed in 2.0.

url(r"^admin/", include(admin.site.urls))

path("admin/", admin.site.urls)

The 3-tuple form of include() was removed in 2.0.

url(r"^files/(?P<path>.*)$", v)

path("files/<path:path>", v)

The path converter requires at least one character.

The type change is the real risk: a view that did int(year) keeps working with an int, but one that did year.zfill(4) or compared with a string breaks. The tests below show both syntaxes side by side in one URLconf and prove that they do not accept exactly the same URLs.

config/urls_migration.py
from django.urls import include, path, re_path

from catalog import views

urlpatterns = [
    # Before (Django 1.x-3.x):  url(r"^archive/(?P<year>[0-9]{4})/$", views.echo)
    # Step 1, mechanical: same regex, same string arguments (works on Django 2.0+).
    re_path(r"^old/(?P<year>[0-9]{4})/$", views.echo),
    # Step 2, idiomatic: path() with a converter; the view now receives an int.
    path("new/<int:year>/", views.echo),
    # Before: url(r"^blog/", include("blog.urls", namespace="blog", app_name="blog"))
    # After: the application namespace lives in blog/urls.py as `app_name`; include() takes `namespace` only.
    path("blog/", include("catalog.urls", namespace="blog")),
]

Sync and async notes

  • Routing is sync and trivial. resolve() is a plain function that scans compiled regular expressions; the ASGI handler calls it directly (self.resolve_request(request)) from the event loop without a thread hop, and converters, reverse(), reverse_lazy() and resolve() are ordinary synchronous, I/O-free functions that are safe to call from async code.

  • The view’s sync or async nature does not affect the pattern. path("ping/", views.ping) works for async def ping(request) and the test test_async_view_is_routed_like_any_other uses AsyncClient against it. A sync view reached through ASGI runs in a thread via sync_to_async; an async view under WSGI is run to completion on a private event loop. The async page of this section explains when each is worthwhile.

  • Keep converters and to_python() free of I/O. A converter that queries the database would run inside the event loop on ASGI, blocking it (and, in sync mode, would run for every non-matching pattern it is tried against). Validate formats in converters and look up rows in the view.

  • reverse() in a coroutine is fine. The only trap is reverse_lazy() proxies stored in module state: they evaluate on first use, in whichever thread uses them first, which is harmless because the URLconf import is thread-safe.

Pitfalls checklist

  • Hardcoded URLs. <a href="/books/{{ book.slug }}/"> and redirect("/books/") break when a prefix changes. Use {% url %}, get_absolute_url() and reverse().

  • reverse() at import time (class attributes, default arguments, module constants) causes circular imports; use reverse_lazy().

  • A missing app_name is the cause of “'catalog' is not a registered namespace” (NoReverseMatch). Set app_name in the included module or use the 2-tuple form.

  • Passing the class, not as_view(), to path(); caught by urls.E009.

  • Specific routes after generic ones, so books/new/ becomes a slug lookup; put literals first.

  • $ on an include() prefix (urls.W001) and a leading / in a route (urls.W002).

  • Forgetting the trailing slash in a form action, so a POST hits APPEND_SLASH; reverse the URL instead.

  • Mixing named and unnamed groups in re_path(); the unnamed ones disappear.

  • Optional named groups pass nothing when absent; give the view a default.

  • Reversing a top-level |; restructure the pattern or add separate patterns for each alternative.

  • Same include() module mounted twice with the same instance namespace (urls.W005); or relied on "last deployed instance" without a default instance.

  • handler404 seems ignored, because DEBUG = True shows the technical 404 page; or because the handler was set in a URLconf other than the root one.

  • Echoing str(exception) in a 404 handler leaks the list of patterns tried.

  • Heavy work in handler500. Return something static.

  • Registering a converter name twice (for example by reloading a URLconf module in a test) raises ValueError since Django 6.0.

  • int leading zeros and unbounded size give duplicate URLs; use a stricter custom converter.

  • Routing on the query string is impossible; the URLconf never sees it. Branch in the view.

  • Different behaviour per HTTP method belongs in the view (or require_http_methods), not in extra patterns: the URLconf ignores the method.

Where the books are outdated

The four reference books were written for Django 1.11 to 5; their URL chapters are right about the ideas (namespaces, named patterns, reverse() instead of hardcoded URLs) and wrong about several spellings:

  • url(). Older code and the Django 1.11 and 2 era books use from django.conf.urls import url with ^…​$ regular expressions. url() was deprecated in 3.1 and removed in 4.0. Use path() and re_path() (added in 2.0), see Migrating from url() to path() and re_path().

  • include() arguments. include("app.urls", namespace="x", app_name="x") and the 3-tuple include(admin.site.urls) were removed in 2.0; the application namespace is app_name in the module (or the 2-tuple), and admin.site.urls goes straight into path().

  • django.core.urlresolvers. Removed in 2.0; import reverse, reverse_lazy, resolve and NoReverseMatch from django.urls.

  • Pre-1.10 idioms such as patterns("", …​), string view names and reversing by dotted path, still visible in old snippets, were removed in 1.10.

  • Everything is a string in the URL regexes of those books. With path() and converters the view receives an int, UUID or custom type, so code such as int(pk) is redundant (harmless) and pk.isdigit() raises AttributeError.

  • Logout links. Books that link to /accounts/logout/ with a GET produce a 405 on Django 5.0 and later, because LogoutView is POST-only.

  • Error handlers. A custom def handler404(request) (or 400 or 403) without the exception argument fails: the argument has been required since Django 2.0, and urls.E007 reports the mismatch at startup. Only handler500 takes just the request.

  • Query strings for redirects are built by hand with urlencode in older code; reverse(query=…​, fragment=…​) does it since 5.2.
