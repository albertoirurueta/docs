Making a logging call

Python’s standard logging module is the only logging API Django uses and the only one you need to call. The convention is one logger per module, named after the module, created at import time:

Logging from a view (catalog/views.py)
import logging

from django.http import Http404, HttpResponse

logger = logging.getLogger(__name__)  # "catalog.views"


def book_detail(request, pk):
    if pk > 100:
        logger.warning("Book %s not found (asked by %s)", pk, request.GET.get("who", "anonymous"))
        raise Http404
    logger.info("Showing book", extra={"book_id": pk})
    return HttpResponse(f"book {pk}")

Source: Make a basic logging call

Four habits make that code worth having:

  • Pass arguments, do not format. logger.warning("Book %s not found", pk) formats the message only when a handler actually emits the record; an f-string pays the formatting cost even for records that are thrown away, and it makes every message unique, which defeats grouping in a log search or an error tracker.

  • Pick the level for the reader. Python’s levels are DEBUG (low-level diagnostics), INFO (normal events), WARNING (something unexpected but handled), ERROR (an operation failed) and CRITICAL (the process cannot continue). A logger discards records below its level; a handler discards records below its own.

  • Use logger.exception() inside except blocks. It logs at ERROR and attaches the traceback; logger.error(…​, exc_info=True) is the same thing. Log the failure once where it is handled, not at every layer it passes through.

  • Never call the logger in settings.py. Django applies LOGGING as part of django.setup(), after the settings module is read, so records emitted while settings are loading are handled by whatever Python defaults exist at that moment. Try logging from a view, a management command or an AppConfig.ready().

Every record emitted by that logger flows through a small, fixed pipeline. Understanding it is the key to every configuration in this page.

flowchart LR call["logger.warning(...)
creates a LogRecord"] --> lvl{"record level >=
logger level?"} lvl -- no --> drop1["discarded"] lvl -- yes --> lf["logger filters"] lf --> h["each handler on this logger
(level check, handler filters)"] h --> fmt["formatter renders the record as text"] fmt --> dest["stream, file, socket,
email, queue"] lf --> prop{"propagate?"} prop -- "yes" --> parent["parent logger's handlers
(not its level or filters)"] prop -- "no" --> stop["stop here"]

A logger is a named bucket; names are dotted, so catalog.views is a child of catalog, which is a child of the root logger. A handler decides what happens to a record (write it, send it); a filter vetoes or edits records on a logger or a handler; a formatter turns a LogRecord into the final text. The detail that surprises people: when a record propagates to a parent, the parent’s handlers see it, but the parent’s level is not consulted, only the levels of its handlers.

What Django does by default

Django ships a complete logging configuration, available as django.utils.log.DEFAULT_LOGGING, and merges your LOGGING into it (when you keep disable_existing_loggers set to False). Its behaviour is:

Condition Result

DEBUG is True

The django logger sends records of INFO and above (except django.server) to the console handler.

DEBUG is False

The django logger sends ERROR and CRITICAL records (except django.server) to AdminEmailHandler, which emails ADMINS.

Always

django.server (the runserver request line) logs INFO and above to the console and does not propagate.

Everything else

Python’s own defaults: WARNING and above from any other logger go to standard error through the last-resort handler.

Configuring logging with LOGGING

LOGGING is a dictionary in the logging.config.dictConfig() schema. Django passes it to LOGGING_CONFIG (by default logging.config.dictConfig) while setting up. The four sections are the four parts of the model: formatters, filters, handlers and loggers, plus an optional root logger.

The request id comes from Structured logging; the django.server lines show [-] because the object attached to those records is a socket, not a Django request. The redaction filter masked the address in both the message and the logged query string. The mechanics worth knowing:

  • The "()" key names a factory (a class or a function by dotted path); the remaining keys of that dictionary are passed to it as keyword arguments. Without "()", a filter or formatter dictionary uses the standard class and a handler dictionary needs "class".

  • "style": "{" chooses str.format() placeholders in a formatter; the default style is %. Pick one and use it everywhere.

  • "propagate": False on django stops Django records at that logger. Leave it out (default True) when you want them to reach a root handler too, and remember that propagation hands the record to the parents' handlers without re-checking their levels.

  • Levels live on loggers and on handlers. The console handler above has no level, so it prints everything its loggers let through; mail_admins only accepts ERROR and above.

  • The disable_existing_loggers pitfall. If the key is missing, dictConfig treats it as True and silently disables every logger that already exists and is not named in the dictionary: they still exist but discard everything, without propagating. The scratch project proved it: a module logger created before the call reported disabled as True after a configuration without the key, and False after the configuration above. Always write "disable_existing_loggers": False.

Handlers, filters and formatters

The Python handlers you will actually use

Django adds one handler (AdminEmailHandler, below) to Python’s own. For the rest:

  • logging.StreamHandler writes to sys.stderr (or a stream you give it): the right default for containers and platforms, see Running it in production.

  • logging.FileHandler writes to a file; logging.handlers.WatchedFileHandler, RotatingFileHandler and TimedRotatingFileHandler reopen or rotate the file. Prefer WatchedFileHandler when logrotate does the rotating, and never use FileHandler with a path the application user cannot write to.

  • logging.handlers.SysLogHandler, HTTPHandler, SocketHandler and SMTPHandler ship records to a collector; each does network I/O inside the logging call, which matters in async code (Sync, async and blocking handlers).

  • logging.NullHandler discards.

  • logging.handlers.QueueHandler hands records to another thread so slow handlers do not block the request (since Python 3.12 it can be configured from dictConfig, see Sync, async and blocking handlers).

Source: logging.handlers and Configure a handler

Django’s three filters

  • django.utils.log.RequireDebugFalse and RequireDebugTrue pass records only when settings.DEBUG is False (respectively True); the default mail_admins handler uses the first so that development errors are never emailed.

  • django.utils.log.CallbackFilter(callback) calls a function on each record and drops the record when the function returns False. The documentation’s example keeps UnreadablePostError (a client that cancelled an upload) out of the admin emails:

Structured logging

A line such as Book 700 not found is for a person reading a terminal. Log aggregators (Loki, Elasticsearch, CloudWatch, Datadog, any ELK-style stack) are better served by one JSON object per line with stable field names: they can then filter by request_id, book_id or level without regular expressions. Python’s standard library already contains everything needed; three pieces cooperate.

1. A formatter that emits JSON. Attributes passed with extra={…​} become attributes of the LogRecord, so the formatter can copy every non-standard attribute into the payload:

A JSON formatter (catalog/log.py)
import json
import logging

# Attributes every LogRecord has; anything else came from extra={...}
# (django.request adds status_code and the request object, which we skip).
_STANDARD = set(logging.makeLogRecord({}).__dict__) | {"message", "asctime", "request_id", "request"}


class JsonFormatter(logging.Formatter):
    """One JSON object per line, ready for a log shipper."""

    def format(self, record):
        payload = {
            "time": self.formatTime(record, "%Y-%m-%dT%H:%M:%S%z"),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
            "request_id": getattr(record, "request_id", "-"),
        }
        payload.update({k: v for k, v in record.__dict__.items() if k not in _STANDARD})
        if record.exc_info:
            payload["exception"] = self.formatException(record.exc_info)
        return json.dumps(payload, default=str)

Source: Implementing structured logging (Python Logging Cookbook)

2. A request id on every record. A contextvars.ContextVar carries a value for the duration of one request, in threads and in async tasks alike. A middleware sets it (the full pattern is on Middleware; this version also stores the id on the request) and a filter copies it onto every record:

Request id middleware and filter (catalog/middleware.py and catalog/log.py)
# catalog/log.py
import contextvars
import logging

request_id_var = contextvars.ContextVar("request_id", default="-")


class RequestIdFilter(logging.Filter):
    """Stamp every record with the id of the request being served."""

    def filter(self, record):
        request_id = request_id_var.get()
        if request_id == "-":
            # django.request 4xx records are emitted after the middleware chain
            # has unwound, so fall back to the request attached to the record.
            request = getattr(record, "request", None)
            request_id = getattr(request, "request_id", "-")
        record.request_id = request_id
        return True


# catalog/middleware.py
import uuid

from .log import request_id_var


class RequestIdMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        request_id = request.headers.get("X-Request-ID") or uuid.uuid4().hex[:12]
        request.request_id = request_id
        token = request_id_var.set(request_id)
        try:
            response = self.get_response(request)
        finally:
            request_id_var.reset(token)
        response["X-Request-ID"] = request_id
        return response

Source: contextvars and Middleware

Two things were learned by running it. The first version of the filter only read the context variable, and the django.request 404 line had request_id - while the 500 line had the real id: Django logs a 4xx response from BaseHandler.get_response() after the middleware chain returned, so the variable had been reset. Records from django.request carry the request object as record.request, so the fallback above recovers the id. The second: the same code served by uvicorn (ASGI) produced a correct id on both the view’s own record and the django.request record, because context variables follow the request through async code.

3. Fields through extra. Running the project with LOG_JSON=1 under uvicorn printed:

Do not use reserved attribute names in extra (message, asctime or any LogRecord field such as name, args, msg): the logging module raises KeyError instead of overwriting them.

Third-party packages build on the same mechanism when you want more than a hand-written formatter: python-json-logger (a JSON Formatter), structlog (processors, bound loggers and context binding) and django-structlog (request middleware for structlog). They were not run for this page; the standard-library recipe above is enough for most projects and keeps the LOGGING dictionary as the single source of truth.

Redacting your own messages

Django’s error reports have their own sensitive-data filtering (Filtering sensitive data out of reports), but nothing filters the text you pass to a logger. A filter that edits the record before it reaches the handler is the last line of defence, not a substitute for not logging secrets in the first place:

A redaction filter (catalog/log.py)
import logging
import re


class RedactFilter(logging.Filter):
    """Mask e-mail addresses and bearer tokens in your own log messages."""

    PATTERNS = [
        (re.compile(r"[\w.+-]+@[\w-]+\.[\w.-]+"), "<email>"),
        (re.compile(r"(?i)bearer\s+\S+"), "Bearer <token>"),
    ]

    def filter(self, record):
        message = record.getMessage()
        for pattern, replacement in self.PATTERNS:
            message = pattern.sub(replacement, message)
        record.msg, record.args = message, None
        return True

Sync, async and blocking handlers

A logging call is synchronous: logger.info() returns after every handler has emitted the record. A StreamHandler writing to stdout is fast enough to ignore, but a FileHandler on a slow disk, an SMTPHandler or a SocketHandler blocks the thread, and in an async def view that thread is the event loop, so every other request on that worker waits. The AdminEmailHandler is in the same position: it sends mail synchronously, which Django accepts because it only runs on errors.

The standard cure is QueueHandler: the logging call puts the record on a queue and returns; a QueueListener thread feeds the slow handlers. Since Python 3.12 dictConfig can build both, and the same configuration is verified here:

A queued handler in dictConfig (Python 3.12+)
import logging
import logging.config

logging.config.dictConfig({
    "version": 1,
    "disable_existing_loggers": False,
    "handlers": {
        "slow": {"class": "logging.StreamHandler"},  # stands for a file, socket or SMTP handler
        "queued": {
            "class": "logging.handlers.QueueHandler",
            "handlers": ["slow"],
            "respect_handler_level": True,
        },
    },
    "loggers": {"catalog": {"handlers": ["queued"], "level": "INFO", "propagate": False}},
})
logging.getHandlerByName("queued").listener.start()  # dictConfig creates the listener but does not start it

Source: Configuring QueueHandler and QueueListener

The comment on the last line is the part the documentation page makes easy to miss and the scratch test confirmed: without the start() call the listener’s thread does not exist and records are queued but never delivered. Start the listener once per process (for example in AppConfig.ready() or in the module that calls dictConfig) and call listener.stop() at shutdown. Django’s own handlers (AdminEmailHandler) can sit behind the queue by listing them under "handlers".

Context variables, the request-id mechanism of Structured logging, work in async views and in sync views served from asgiref’s thread pool alike; that is why `ContextVar rather than threading.local is the right tool.

Error reporting

When DEBUG is False the browser shows a bland 500 page and Django reports the error by other means. The default channels are an email to ADMINS for every server error and an email to MANAGERS for broken links; third-party trackers take over from there.

Server errors by email: ADMINS and AdminEmailHandler

When DEBUG is False and AdminEmailHandler is configured (the default logging does it), Django emails the people in ADMINS whenever the code raises an unhandled exception that ends as a response with status 500 or more. The email contains a description of the error, the full traceback and details of the request. It is sent through the logging framework, so everything above about handlers, filters and levels applies to it.

Details that decide whether the mail arrives:

  • ADMINS is a list of address strings. Before Django 6.0 it required (name, address) tuples whose name was never used; the tuple form is deprecated since 6.0. To include a display name, write the address as '"Name" <address>', as above.

  • The sender is SERVER_EMAIL, which defaults to root@localhost; many providers reject that address, so set it.

  • The mail itself needs a working mail configuration. Until 6.1 that meant EMAIL_HOST, EMAIL_HOST_USER, EMAIL_HOST_PASSWORD and friends. Since 6.1 it is the MAILERS setting (see below).

  • The subject carries the prefix EMAIL_SUBJECT_PREFIX and says EXTERNAL IP or INTERNAL IP depending on whether the client address is in INTERNAL_IPS.

Broken links: BrokenLinkEmailsMiddleware, MANAGERS and IGNORABLE_404_URLS

Django can also email MANAGERS about broken links (404 responses) when DEBUG is False and MIDDLEWARE contains django.middleware.common.BrokenLinkEmailsMiddleware. It mails only when the request has a referer and the referer is not the requested URL itself, because 404s without a referer are mostly people typing URLs or bots. Put it toward the top of MIDDLEWARE, before middleware that intercepts 404s such as LocaleMiddleware or FlatpageFallbackMiddleware. IGNORABLE_404_URLS is a list of compiled regular expressions for URLs not worth reporting; the documentation’s example excludes the usual crawler requests:

Ignoring conventional 404s (settings fragment)

The limits of email

Email reporting is pragmatic and fragile: one broken dependency can produce thousands of identical messages a minute and trip the mail provider’s rate limits; there is no grouping, no counts, no resolved state; and the report may contain personal data that travels unencrypted. The Django documentation says as much and points to third-party services. A reasonable setup keeps the ADMINS mail for small sites and for a last-resort channel (set include_html to False), and uses a tracker (Sentry) for everything else.

Filtering sensitive data out of reports

By default an error report holds the traceback, every frame’s local variables, the request attributes (including POST data and cookies, with some filtering) and the Django settings. The documentation puts it bluntly: filtering sensitive data is a hard problem, it is nearly impossible to guarantee that nothing leaks, so reports must be available only to trusted team members and not sent unencrypted over the internet. The tools below reduce the risk; they do not remove it.

@sensitive_variables and @sensitive_post_parameters

sensitive_variables(*variables) marks local variables of a function (a view or any other callable) whose values must be replaced by stars in reports; with no arguments it hides every local variable of the function. sensitive_post_parameters(*parameters) marks POST parameters of a view the same way, and with no arguments hides all of them. The built-in authentication views (login, password reset confirm, password change, and the user admin’s add and password change views) hide every POST parameter without you asking. Since Django 5.0 both decorators work on async def functions.

Hiding card data (catalog/views.py)
from django.views.decorators.debug import sensitive_post_parameters, sensitive_variables


class PaymentError(Exception):
    pass


@sensitive_variables("card_number", "gateway_token")
def _charge(request):
    card_number = request.POST["card_number"]
    gateway_token = request.POST["gateway_token"]
    order_note = request.POST["note"]
    raise PaymentError(f"gateway refused order ({order_note})")


@sensitive_post_parameters("card_number", "gateway_token")
def checkout(request):
    return _charge(request)


@sensitive_variables("card_number")
async def _acharge(request):
    card_number = request.POST["card_number"]
    raise PaymentError("async gateway refused")


@sensitive_post_parameters("card_number")
async def acheckout(request):
    return await _acharge(request)


def plain_checkout(request):
    # Deliberately undecorated, to show what leaks.
    card_number = request.POST["card_number"]
    raise PaymentError("no filtering")

Two rules from the documentation: when the sensitive variable is also a function argument and the function has other decorators, @sensitive_variables must be the outermost decorator, or the argument is exposed as it passes through the others; and the decorators only annotate (the function or the request), the actual replacement is done by the reporter filter, so they have no effect on anything that does not use it, such as your own logger.error("…​", request.POST) calls.

A site-wide filter: SafeExceptionReporterFilter

The filter that does the replacement is django.views.debug.SafeExceptionReporterFilter. To apply rules to the whole site, subclass it and name the class in DEFAULT_EXCEPTION_REPORTER_FILTER. The attributes and methods the documentation lists as overridable are: cleansed_substitute (the replacement text, by default), hidden_settings (a compiled regular expression matching setting names and request.META keys to hide), is_active(request) (by default the filter is active when DEBUG is False), get_post_parameters(request) and get_traceback_frame_variables(request, tb_frame). The default hidden_settings is API|AUTH|TOKEN|KEY|SECRET|PASS|SIGNATURE|HTTP_COOKIE, case-insensitive; note that a setting called SENTRY_DSN or DATABASE_URL matches none of it.

A custom filter and reporter (catalog/reporting.py)
import re

from django.views.debug import ExceptionReporter, SafeExceptionReporterFilter


class BookshelfReporterFilter(SafeExceptionReporterFilter):
    cleansed_substitute = "[redacted]"
    # Extend the built-in pattern (API|AUTH|TOKEN|KEY|SECRET|PASS|SIGNATURE|HTTP_COOKIE).
    hidden_settings = re.compile(
        SafeExceptionReporterFilter.hidden_settings.pattern + r"|DSN|DATABASE_URL",
        flags=re.IGNORECASE,
    )
    hidden_post = re.compile(r"card|iban|ssn", flags=re.IGNORECASE)

    def is_active(self, request):
        # Filter even when DEBUG is True (the default only filters when it is False).
        return True

    def get_post_parameters(self, request):
        params = super().get_post_parameters(request)
        return {
            name: self.cleansed_substitute if self.hidden_post.search(name) else value
            for name, value in params.items()
        }


class BookshelfExceptionReporter(ExceptionReporter):
    def get_traceback_data(self):
        data = super().get_traceback_data()
        data["sys_path"] = []  # nobody needs the server's import path in an e-mail
        return data

A second test passed reporter_class="catalog.reporting.BookshelfExceptionReporter" to AdminEmailHandler and the email body contained Python Path: []. Three things to keep in mind:

  • ExceptionReporter (the class named in DEFAULT_EXCEPTION_REPORTER) compiles and formats the report; its main extension point is get_traceback_data(), and it uses the filter when preparing the data. It also has html_template_path, text_template_path, get_traceback_html() and get_traceback_text().

  • The default filter instance is cached on first use. A test that swaps DEFAULT_EXCEPTION_REPORTER_FILTER with override_settings has no effect until django.views.debug.get_default_exception_reporter_filter.cache_clear() is called (the scratch test did so, and registered the same call as cleanup). That function is an internal detail, not a documented API, so keep the test helper in one place.

  • You can choose per request: set request.exception_reporter_filter or request.exception_reporter_class inside a view to an instance of your class, for example only for authenticated users.

Subclasses must inherit from SafeExceptionReporterFilter (Django 3.1 made that mandatory for custom filters).

Rules of thumb

  • Mark every view that receives a credential, card number, token or national id with @sensitive_post_parameters, and every helper that holds one in a local with @sensitive_variables.

  • Name settings so they match hidden_settings, or widen the pattern; a DSN, a connection URL and a webhook URL are secrets too.

  • Keep include_html off, send error email only to people allowed to see production data, and prefer a tracker you control over email.

  • Do not log request bodies, headers such as Authorization and Cookie, or model instances with personal fields; use the redaction filter of Redacting your own messages as a backstop only.

  • Remember what is outside the filter: your own logger calls, the request object attached to django.request records (so a custom handler or an error tracker can see it), and the database contents behind a record id.

Sentry

Sentry is an error-tracking service (hosted or self-hosted) that groups the same exception into one issue, counts occurrences, tracks releases and keeps the context of each event. The setup below follows the Sentry SDK documentation, and Django needs no code change beyond initialising it. The package is sentry-sdk (2.71.0, 2026-09-28, requires Python 3.6 or newer); installing it with pip install sentry-sdk is enough. The Django integration is enabled automatically when Django is installed; adding DjangoIntegration() to integrations is only needed to set its options.

Initialising Sentry from the environment (catalog/sentry_setup.py)
import logging
import os

import sentry_sdk
from sentry_sdk.integrations.django import DjangoIntegration
from sentry_sdk.integrations.logging import LoggingIntegration

SENSITIVE_HEADERS = {"authorization", "cookie", "x-session-token"}


def scrub_event(event, hint):
    """Last line of defence: runs on every error event before it leaves the process."""
    headers = event.get("request", {}).get("headers", {})
    for name in list(headers):
        if name.lower() in SENSITIVE_HEADERS:
            headers[name] = "[scrubbed]"
    return event


def init_sentry(**overrides):
    dsn = os.environ.get("SENTRY_DSN")
    if not dsn:
        return  # local development and CI: Sentry stays off
    options = dict(
        dsn=dsn,
        environment=os.environ.get("APP_ENV", "production"),
        release=os.environ.get("GIT_SHA"),
        send_default_pii=False,  # the default; stated for the reader
        traces_sample_rate=0.05,
        integrations=[
            DjangoIntegration(),
            LoggingIntegration(level=logging.INFO, event_level=logging.ERROR),
        ],
        before_send=scrub_event,
    )
    options.update(overrides)
    sentry_sdk.init(**options)

Call init_sentry() at the end of settings.py, as early as possible in the process lifecycle, so that exceptions raised while Django starts are captured too.

What was verified against the scratch project, with a local transport function standing in for the network (the DSN was a generated placeholder pointing at an unresolvable host, so no event left the machine):

  • An unhandled exception in a view reached the transport as one error event with the configured release and environment and the URL path as transaction name. The event for a 500 was reported once, not once by Django’s signal and once by the django.request log record.

  • logging.getLogger("catalog.payments").error(…​) produced a second event (the LoggingIntegration default turns ERROR records into events and INFO and above into breadcrumbs, which is what event_level and level state explicitly above), while an INFO record added nothing but a breadcrumb.

  • With send_default_pii=False and a request served by runserver, the event had the request URL, method and headers but no user data. Both the SDK’s own scrubbing (the Authorization and Cookie headers arrived as [Filtered]) and the before_send function (a custom X-Session-Token header arrived as [scrubbed]) worked.

  • With the Django test client the request section of the event was empty: the SDK collects request data in its WSGI/ASGI wrapper, which the test client bypasses. Test Sentry behaviour with a real server process or by calling scrub_event directly.

The decisions behind each option:

  • DSN from the environment, off when missing. The DSN identifies the project and is accepted by anyone who has it, so treat it as configuration that does not belong in the repository, and make development and CI run without it.

  • send_default_pii=False. Leave it off unless you have decided what to do about personal data; turning it on attaches user id, email, username and cookies when django.contrib.auth is installed.

  • before_send is the hook for rules the SDK does not know: drop events (return None), redact fields, add tags.

  • release and environment let Sentry attribute an error to a deployment and separate staging from production; a git commit hash is a good release.

  • traces_sample_rate is performance tracing, independent of error capture; sample, do not set it to 1.0 in production.

  • The hostname. Events include the server name, which may be internal infrastructure naming; set server_name or scrub it when that matters.

Sentry does not replace logging: keep structured logs for the narrative of a request and use the tracker for failures that a person must act on. If you use another tracker, the structure is the same (initialise early, from the environment, with a scrubbing hook); the Django-side contract is only the logging framework, the got_request_exception signal and middleware.

Testing logs and error reports

  • self.assertLogs(logger, level) is a context manager that fails if nothing was logged at that level and exposes cm.records and cm.output; self.assertNoLogs(logger, level) asserts the opposite. Both come from unittest. They replace the logger’s handlers and stop propagation inside the block (see the trap under Server errors by email: ADMINS and AdminEmailHandler).

  • The test runner swaps the email backend for the in-memory one, so mail.outbox holds error and broken-link emails; with Client(raise_request_exception=False) a view exception becomes a 500 response and the email is sent, instead of the exception propagating into the test.

  • logging.disable(logging.CRITICAL) in a setUp (with logging.disable(logging.NOTSET) in cleanup) silences log noise from tests that deliberately hit errors.

  • Do not initialise Sentry in the test settings; test your before_send function as a plain function.

  • A configuration that fails to import (a typo in "()") is found by manage.py check or any test run, because LOGGING is applied at set-up; run one of them in CI.

Running it in production

  • Log to the standard streams. In Docker, Kubernetes and most platforms the platform collects what the process prints. A StreamHandler to stderr (or stdout) is the right production handler, and rotation, retention and shipping are the platform’s job (the twelve-factor "logs as event streams" rule).

  • The server’s own logs. Gunicorn writes its access log only when told to: --access-logfile - sends it to stdout, --error-logfile - sends the error log to stderr, --capture-output redirects the application’s stdout and stderr into the error log, and --log-level sets the level; --log-config-json and --log-config load a full configuration. Uvicorn has --log-level, --access-log / --no-access-log and --log-config. Both servers use their own loggers, not django.server.

  • One configuration, many processes. Every worker process runs django.setup() and therefore applies LOGGING; a QueueListener thread exists per process.

  • Set levels per environment through variables (DJANGO_LOG_LEVEL, LOG_JSON) as above, and keep DEBUG off; django.db.backends logging only works with DEBUG=True, so in production use the database’s own slow-query log.

  • Do not log to a file in a container unless a volume and a rotation strategy exist; a file inside an ephemeral container disappears with it.

  • Check the checklist. manage.py check --deploy does not inspect LOGGING, so review it with the other items of the deployment checklist (see Security and Settings & Configuration).

Pitfalls

  • Forgetting "disable_existing_loggers": False silences every logger that is created before dictConfig runs.

  • Expecting INFO lines from your own code in production without a handler or a level for the catalog logger.

  • Putting log calls or dictConfig before the settings they depend on in settings.py.

  • Using f-strings in log calls (cost and grouping) and logging secrets in a message that no Django filter can see.

  • Attaching AdminEmailHandler to a logger that logs every request: one outage floods the mailbox.

  • Using a filter on a parent logger to filter records of its children (filters on a logger do not apply to records that propagate to it from children; attach to the handler instead).

  • Wrapping a request in assertLogs and wondering why the admin email is not sent.

  • Sending the debug page by email (include_html) and treating the report as safe because one view was decorated.

  • Trusting hidden_settings for names that do not match its pattern (SENTRY_DSN, DATABASE_URL, webhook URLs).

  • Letting a slow handler (SMTP, remote syslog, a slow disk) run on the event loop without a QueueHandler.

  • Enabling Sentry’s send_default_pii without a policy for personal data.

Where the books are outdated

The four reference books cover Django 1.11 to 4 and their logging advice is good where it is about habits: use levels, log exceptions with logger.exception, put logging in every module, keep secrets out of logs and reports. Several details have moved on:

  • Configuration style. Older examples build LOGGING with %-style formats and no explicit disable_existing_loggers; the current documentation recommends setting it to False, and the { style is as supported as %.

  • The default configuration. A description of a single "mail admins when DEBUG is False`" rule predates the `django.server logger, which always logs the development server’s request lines to the console; copying a config that assumes the old defaults can give duplicate lines.

  • Email settings. Chapters on error emails configure EMAIL_HOST, EMAIL_HOST_USER, EMAIL_HOST_PASSWORD and EMAIL_BACKEND. Since Django 6.1 the current way is MAILERS, and those settings are deprecated until Django 2028; ADMINS as (name, address) tuples (shown in every older book) has been deprecated since 6.0.

  • Sensitive data. Older sections show sensitive_variables and sensitive_post_parameters on sync functions only; both have worked on async def since 5.0. The default hidden_settings pattern matches more names than in the 2.x era (SIGNATURE, HTTP_COOKIE, and since 5.2 AUTH), and since 3.1 cleansed_substitute and hidden_settings are documented attributes of the filter class, so custom filters no longer need to reimplement the cleansing method.

  • Python itself. Pre-3.12 text cannot configure QueueHandler through dictConfig; the logging.getHandlerByName() accessor used in this page is also new in 3.12.

  • Third-party logging. Text that recommends Raven (the original Sentry client) is out of date: Sentry’s current Python client is sentry-sdk, whose Django integration is automatic.

  • Debugging by print. Chapters that debug with print() and the development server’s console should use a logger, which works under every deployment style.
