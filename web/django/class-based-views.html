Class-Based Views

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Django 6.1 (6.1.1 on PyPI; 6.1.2 is scheduled for 2026-10-06), Python 3.12-3.14 and PostgreSQL 15+, checked on 2026-10-03; where Django 5.2 LTS behaves differently the text says so. Every listing below was run in a scratch project on Python 3.13.16 and Django 6.1.1 with SQLite: manage.py check, 43 tests (manage.py test), curl sessions against runserver (WSGI) and against Uvicorn (ASGI), and the shell examples all passed, and the output shown is the real output. None of the code needs anything but SQLite.

A class-based view (CBV) is a Python class that answers an HTTP request with one method per HTTP verb instead of one function with an if request.method == …​ ladder. Django does not call the class: the URL resolver needs a callable that takes a request, so as_view() builds one. Everything else on this page follows from that one trick: the per-request instance, the setup() and dispatch() hooks, configuration through class attributes and as_view() keyword arguments, decorators that need an adapter, mixins that depend on the method resolution order, and async handlers that are detected from the class. This page covers the base classes in django.views and django.views.generic.base (View, TemplateView, RedirectView) and the mixin machinery they are built from. The model-aware generic views (ListView, DetailView, FormView, CreateView, UpdateView, DeleteView and the date-based views) are built on the same machinery and get their own page, Generic Views. The function-based alternative is on Function-Based Views & Shortcuts, and the pipeline around every view is on Request/Response Cycle and Middleware. For the models used below see Models & Fields; for the Python side of multiple inheritance see Advanced OOP & Design and, for decorators, Decorators & Metaclasses.

What a class-based view is

The contract Django has with every view is the same, class-based or not: a callable that receives an HttpRequest (plus whatever the URL pattern captured) and returns an HttpResponse, or raises an exception that Django turns into one. A CBV keeps that contract and wraps it. The callable that goes into the URLconf is the function returned by Class.as_view(); on every request that function builds a fresh instance of your class, hands it the request, and lets dispatch() pick the method that matches the HTTP verb.

The diagram is the whole mechanism of django.views.generic.base.View; the rest of the page fills in each box. Three consequences are worth holding on to before the details:

  • There is one instance per request. Instance attributes you set in setup(), dispatch() or a handler disappear with the request, so they are safe. Class attributes, and the values you pass to as_view(), are created once when the URLconf is imported and are shared by every request the process serves.

  • The handler methods are ordinary methods. get(), post() and the rest receive request as an argument and return a response exactly like a function view; they can also read self.request, self.args and self.kwargs. Shortcuts such as render() and redirect() and response classes such as TemplateResponse work unchanged inside a CBV.

  • Anything that wraps a view sees the function, not the class. Middleware, decorators in the URLconf and the resolver all receive the function from as_view(). It carries two attributes, view_class and view_initkwargs, for code that needs the class back.

View: one method per HTTP verb

django.views.View (importable from django.views and django.views.generic) is the parent of every class-based view. It implements exactly four things: dispatch by HTTP method, a 405 response for methods you did not write, a default OPTIONS answer, and sanity checking in as_view(). A view is a subclass with methods named after the verbs it supports, written in lowercase.

catalog/views_basic.py: the smallest useful view
from django.http import HttpResponse
from django.views import View


class GreetingView(View):
    greeting = "Good day"

    def get(self, request, *args, **kwargs):
        name = kwargs.get("name", "reader")
        return HttpResponse(f"{self.greeting}, {name}!")

    def post(self, request, *args, **kwargs):
        return HttpResponse("Message received", status=201)
catalog/urls.py: the same class mounted twice with different configuration
from django.urls import path

from . import views_basic

urlpatterns = [
    path("greet/", views_basic.GreetingView.as_view(), name="greet"),
    path("greet/<str:name>/", views_basic.GreetingView.as_view(greeting="Welcome"), name="greet-named"),
]

Four behaviours are worth knowing exactly:

  • HEAD is GET without a body. setup() assigns self.head = self.get when the class defines get() but no head(). Define head() yourself only when you can answer cheaper than running the whole get().

  • OPTIONS is built in. View.options() returns an empty 200 response whose Allow header lists every handler the instance has (GET, POST, HEAD, OPTIONS above; HEAD appears because setup() created it). CORS preflights are a different matter and are normally answered by middleware before the view runs; see CORS.

  • An unsupported verb is a 405, not an error. http_method_not_allowed() returns HttpResponseNotAllowed with the same Allow list, an empty body, and writes a warning to the django.request logger (Method Not Allowed (DELETE): /greet/ on the console).

  • Handlers receive the URL’s captures. Named groups arrive as keyword arguments (kwargs["name"]), unnamed groups as positional arguments, and both are also kept on self.args and self.kwargs. Declare *args, **kwargs on handlers you intend to subclass so a future URL change does not break them.

http_method_names: the allow-list

View.http_method_names is the complete list of verbs that may reach a handler. The default is ["get", "post", "put", "patch", "delete", "head", "options", "trace"]. dispatch() lowercases request.method and refuses anything that is not in the list, even when a method of that name exists on the class. That makes the attribute a cheap way to forbid verbs for a whole family of views, and it is also the reason an unusual verb (WebDAV’s PROPFIND, say) is a 405 until you add its lowercase name to the list and write a method for it. Removing "options" does not remove the method, it only makes the verb a 405; and trace should stay off unless you know why you need it.

The TimedView below is the base for the next two sections. It narrows http_method_names, assigns per-request state in setup() and decorates every response in dispatch():

catalog/views_basic.py: a base class that restricts verbs and adds headers to every response
import time
import uuid

from django.http import JsonResponse
from django.views import View

from .models import Book


class TimedView(View):
    """Cross-cutting behaviour in setup() and dispatch(); subclasses add handlers."""

    http_method_names = ["get", "post", "head", "options"]  # no PUT/PATCH/DELETE/TRACE

    def setup(self, request, *args, **kwargs):
        super().setup(request, *args, **kwargs)  # sets self.request, self.args, self.kwargs
        self.request_id = request.headers.get("X-Request-ID") or uuid.uuid4().hex
        self.started = time.perf_counter()

    def dispatch(self, request, *args, **kwargs):
        response = super().dispatch(request, *args, **kwargs)
        response["X-Request-ID"] = self.request_id
        response["X-Elapsed-Ms"] = f"{(time.perf_counter() - self.started) * 1000:.1f}"
        return response


class BookCountView(TimedView):
    def get(self, request, *args, **kwargs):
        return JsonResponse({"books": Book.objects.filter(is_published=True).count()})

as_view(): configuration, validation and per-request instances

as_view(*initkwargs) is a class method (decorated classonlymethod, so it cannot be called on an instance) that returns the view function. What it does at *import time, when the URLconf is loaded, and what that function does at request time are different things, and mixing them up is the source of most CBV bugs.

At import time as_view() validates the keyword arguments you passed and builds the function:

  • a keyword that is the name of an HTTP method (as_view(get=…​)) is a TypeError;

  • a keyword that is not already an attribute of the class (as_view(colour="red")) is a TypeError, which catches typos in the URLconf the moment the server starts;

  • the function gets view_class, view_initkwargs, the class’s docstring, and a copy of everything in cls.dispatch.dict, which is how decorators that set an attribute on the function (csrf_exempt sets csrf_exempt = True) keep working when you decorate dispatch();

  • when every HTTP handler on the class is async def, the function is marked as a coroutine function (see Async class-based views).

At request time the function runs the sequence in the diagram: self = cls(initkwargs) (View.init simply does setattr for each keyword), self.setup(request, *args, kwargs), a check that setup() really set self.request, and finally return self.dispatch(request, *args, **kwargs).

Two configuration styles result, and they combine: subclass and override attributes (class MorningGreeting(GreetingView): greeting = "Morning") or pass attributes to as_view() in the URLconf, as the second path() above did. Use as_view() keywords for deployment-specific variations of one class (a different template_name at two URLs) and subclasses when the variation deserves a name, tests, or added methods.

Class state is shared, instance state is not

Because as_view() runs once while the instance is created for every request, a mutable class attribute is one object shared by all requests of the process, across threads. The classic mistake looks harmless:

catalog/views_basic.py: a shared list versus per-request state
from django.http import HttpResponse
from django.views import View


class SharedStateView(View):
    seen = []  # BUG: one list shared by every request served by this process

    def get(self, request, *args, **kwargs):
        self.seen.append(request.path)
        return HttpResponse(f"{len(self.seen)} requests seen")


class PerRequestStateView(View):
    def setup(self, request, *args, **kwargs):
        super().setup(request, *args, **kwargs)
        self.seen = []  # a fresh list on a fresh instance, for every request

    def get(self, request, *args, **kwargs):
        self.seen.append(request.path)
        return HttpResponse(f"{len(self.seen)} requests seen")
Three requests to each view (a running dev server answers 1, 2, 3 for the first and 1, 1, 1 for the second)
$ curl -s localhost:8723/shared/ localhost:8723/shared/ localhost:8723/shared/
1 requests seen2 requests seen3 requests seen
$ curl -s localhost:8723/per-request/ localhost:8723/per-request/ localhost:8723/per-request/
1 requests seen1 requests seen1 requests seen

SharedStateView leaks one request’s data into the next and is a data race under a threaded server. The same applies to values passed through as_view(): as_view(items=[]) creates one list when the URLconf is imported. Initialise mutable state in setup() (or init, which receives the as_view() keywords) and keep anything that must outlive a request in the database, the cache or a module-level object designed for concurrency.

setup() and dispatch(): the two hooks

setup(request, args, **kwargs) initialises per-request attributes: it sets self.request, self.args and self.kwargs and creates the head alias. It runs before dispatch(), so everything there can rely on those attributes, including dispatch() overrides and mixins. Override setup() to compute values every handler needs (a request ID, the parsed tenant, a service object) and *always call super().setup(…​) first. Forgetting it is caught immediately, because as_view() checks for self.request afterwards:

catalog/views_basic.py: a setup() that forgot super()
import time

from django.http import HttpResponse
from django.views import View


class ForgetfulView(View):
    def setup(self, request, *args, **kwargs):
        self.started = time.perf_counter()  # forgot super().setup(...)

    def get(self, request, *args, **kwargs):
        return HttpResponse("never reached")
>>> Client().get("/forgetful/")
AttributeError: ForgetfulView instance has no 'request' attribute. Did you override setup() and forget to call super()?

dispatch(request, *args, kwargs) is "the view part of the view". Its default body is four lines: lowercase the method, check it against http_method_names, look the handler up with getattr(self, method, self.http_method_not_allowed), and call it. Override it for behaviour that is the same for every verb: authentication and permission checks (that is exactly what LoginRequiredMixin does), logging, response headers (as TimedView did), tenant resolution, or rejecting a request before any handler runs. Three rules keep an override correct: call super().dispatch(request, *args, kwargs) so the verb routing still happens; return the response (or a modified one) rather than discarding it; and do not assume self.request differs from the request argument, they are the same object.

dispatch() is also where a view’s decorators are applied (next sections), and where the sync/async distinction bites: an async def handler makes super().dispatch() return a coroutine, so an overriding dispatch() that post-processes the response must itself be async def and await it.

Source: View.setup() and View.dispatch()

Where a CBV sits relative to CSRF and middleware

dispatch() runs inside the view, which is after the middleware’s process_view() hooks. For unsafe methods, CsrfViewMiddleware therefore answers before http_method_not_allowed() ever gets a chance: a bare curl -X DELETE localhost:8723/greet/ returns 403 Forbidden (no CSRF token), not 405, while the test client, which skips CSRF checks by default, shows the 405. Both behaviours are correct and the order matters when you debug a "wrong status code": 403 from the CSRF middleware is reported before the 405 from the view. The full pipeline is covered on Request/Response Cycle.

TemplateView: render a template with the URL’s captures

TemplateView is View plus two mixins, TemplateResponseMixin (which knows how to render) and ContextMixin (which knows how to build the context). Its MRO, printed above, is TemplateView > TemplateResponseMixin > ContextMixin > View. Its only handler is get(), which is three lines: build the context from the URL’s keyword arguments with get_context_data(**kwargs), then render_to_response(context). That makes it the right base for any page that shows a template and nothing else: a home page, an "about" page, a documentation page, the page that hosts a client-side app.

from django.views.generic import TemplateView

from .models import Book


class HomeView(TemplateView):
    template_name = "catalog/home.html"
    extra_context = {"site_name": "Bookshelf"}

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context["latest_books"] = Book.objects.filter(is_published=True).order_by("-id")[:3]
        return context

What goes into the context, in order, is: the URL’s named captures (kwargs), the view itself under the key view (set by ContextMixin with setdefault, so a URL capture named view would win), then everything in extra_context. extra_context is a class attribute (also accepted by as_view()) holding a dictionary of constants; it is evaluated once at import time, so never put a QuerySet or a "current time" in it. Anything per-request, such as the three latest books above, belongs in get_context_data(), and the override must call super().get_context_data(**kwargs) first and return the dictionary, which is what lets mixins cooperate (see the MRO section).

Choosing the template and the response

TemplateResponseMixin exposes four attributes and two methods:

The template to render. Required unless get_template_names() is overridden, otherwise ImproperlyConfigured is raised.

Returns a list of candidate names; the first one that exists is used. Override it to pick a template from request or URL data.

template_engine

Name of a configured template engine (the NAME of an entry in TEMPLATES); None tries all engines in order.

The response type, TemplateResponse by default. Replace it with a subclass to change rendering or headers.

class PageView(TemplateView):

    def get_template_names(self):
        return [f"catalog/pages/{self.kwargs['slug']}.html", "catalog/pages/default.html"]


class RobotsView(TemplateView):
    template_name = "catalog/robots.txt"
    content_type = "text/plain"

RedirectView: redirect on any method

RedirectView is a View whose every handler (get, head, post, options, delete, put, patch) calls the same redirecting get(). Pointing a URL at it replaces a function view that only returns redirect(…​), and it is the usual tool for moved pages, short links and canonical-URL redirects. It has five attributes, all settable on the class or through as_view():

Attribute Default Meaning

url

None

The target as a string. Dictionary-style % formatting is applied with the URL’s named captures ("/books/%(pk)s/"), and it is always applied, so a literal percent sign must be written %%. None (with no pattern_name) makes the view answer 410 Gone.

pattern_name

None

A URL name to reverse(), using the same positional and keyword arguments the request captured. Ignored when url is set.

permanent

False

True answers 301 instead of 302. Browsers and search engines cache a 301, so use it only for moves you will never undo.

query_string

False

True appends the request’s query string to the target (with & if the target already has one).

preserve_request

False

New in Django 6.1. True keeps the HTTP method and body across the redirect: 307 instead of 302, or 308 instead of 301 when permanent is True.

from django.views.generic import RedirectView

    path("legacy/<int:pk>/", RedirectView.as_view(url="/books/%(pk)s/", permanent=True)),
    path("docs/", RedirectView.as_view(url="https://docs.djangoproject.com/en/6.1/")),
    path("retired/", RedirectView.as_view(url=None), name="retired"),

Why preserve_request exists. With a 301 or 302, browsers may (and for POST historically do) replay the redirected request as a GET and drop the body, which silently breaks a form or API client posting to a moved endpoint. 307 and 308 forbid that change. Before 6.1 you had to subclass RedirectView and build the 307 or 308 response yourself. The response classes HttpResponseRedirect and HttpResponsePermanentRedirect also take a preserve_request argument (documented with the request and response objects), and RedirectView passes its attribute to them. On Django 5.2 LTS keep the subclass.

get_redirect_url(): computed targets

get_redirect_url(*args, **kwargs) is the one method worth overriding. It receives the URL’s captures, must return a URL string or None (410), and the default implementation is the logic of the table above, so calling super().get_redirect_url(…​) after your own work reuses url, pattern_name and query_string. Two patterns come up constantly: side effects before the redirect (a counter, a log line) and computing the target.

catalog/views_redirect.py: count a visit, then redirect by pattern name
from django.db.models import F
from django.shortcuts import get_object_or_404
from django.views.generic import RedirectView

from .models import Book


class BookShortLinkView(RedirectView):
    """/b/<isbn>/ counts a visit, then redirects to the book's detail URL."""

    permanent = False
    query_string = True
    pattern_name = "book-detail"

    def get_redirect_url(self, *args, **kwargs):
        book = get_object_or_404(Book, isbn=kwargs["isbn"])
        Book.objects.filter(pk=book.pk).update(visits=F("visits") + 1)
        return super().get_redirect_url(pk=book.pk)

Location: /books/2/?ref=mail

The counter uses F("visits") + 1 inside update(), so the increment is one atomic SQL statement instead of a read-modify-write race; see Making Queries. Counting on a redirect that crawlers and prefetchers follow also counts them, so it is a statistic, not a billing record.

Never redirect to an unchecked user-supplied URL. A view that sends the browser to whatever ?next= says is an open redirect that phishing links abuse. Django’s own LoginView and set_language() validate the next parameter for you, so reuse them where they fit; the helper they use internally is not part of the documented public API (the 3.0 and 4.2 release notes call it private), so do not build on it. For your own redirects the dependable rule is to accept a name, not a URL: map a small set of allowed keys to URL names and reverse() the result.

    def get_redirect_url(self, *args, **kwargs):

Decorating class-based views

Function decorators expect a function that takes request first. A CBV is not that, and its methods take self first, so there are two places to decorate and one adapter.

In the URLconf you decorate the function that as_view() returns. This applies the decorator to that one URL only, and it is the simplest way to protect a built-in view you do not subclass:

from django.contrib.auth.decorators import login_required, permission_required
from django.views.generic import TemplateView

urlpatterns = [
    path("about/", login_required(TemplateView.as_view(template_name="secret.html"))),
    path("vote/", permission_required("polls.can_vote")(VoteView.as_view())),
]

On the class you decorate dispatch(), so that every URL that uses the class gets the behaviour. method_decorator() turns a function decorator into a method decorator by supplying the missing self. It can wrap the method directly or, more compactly, be applied to the class with the name of the method; it also accepts a list or tuple of decorators, applied in the order given (the first one in the list sees the request first):

catalog/views_decorated.py: class-level decorators, in both spellings

catalog/views_decorated.py: a webhook exempt from CSRF, authenticated by a shared secret instead
import hmac
import os

from django.http import HttpResponse, HttpResponseForbidden
from django.utils.decorators import method_decorator
from django.views import View
from django.views.decorators.csrf import csrf_exempt


@method_decorator(csrf_exempt, name="dispatch")
class StockWebhookView(View):
    """Server-to-server callback: no browser, so no CSRF cookie; authenticated by a shared secret instead."""

    def post(self, request, *args, **kwargs):
        secret = os.environ.get("STOCK_WEBHOOK_SECRET", "")
        supplied = request.headers.get("X-Webhook-Secret", "")
        if not secret or not hmac.compare_digest(secret, supplied):
            return HttpResponseForbidden()
        return HttpResponse(status=204)


class FormPostView(View):
    """Same POST handler, but still protected by CsrfViewMiddleware."""

    def post(self, request, *args, **kwargs):
        return HttpResponse(status=204)

Four details trip people up:

  • method_decorator passes args and *kwargs through, so the decorated method must accept the arguments dispatch() receives; a method with a narrower signature raises TypeError.

  • Decorate dispatch(), not get(), to cover every verb; decorate a single handler (@method_decorator(cache_page(60), name="get")) to cover only that verb.

  • A list passed to method_decorator() is applied in order; stacking several @method_decorator lines applies the bottom one first, as with ordinary stacked decorators.

  • method_decorator() wraps asynchronous methods too since Django 5.2, but decorating dispatch() of a view with async handlers requires an async def dispatch() (see the async section).

For access control the classic alternative to decorators is a mixin: LoginRequiredMixin, PermissionRequiredMixin and UserPassesTestMixin from django.contrib.auth.mixins override dispatch() and call handle_no_permission() on failure, which redirects anonymous users to the login URL and raises PermissionDenied (a 403) for signed-in ones. They are configured with attributes (login_url, permission_required, raise_exception, redirect_field_name) rather than decorator arguments, and the result is equivalent to method_decorator(login_required, name="dispatch"). If every page except a few needs a login, Django 5.1 added LoginRequiredMiddleware with a login_not_required() decorator for the exceptions; note the middleware reads login_url from the login_required() decorator but not from LoginRequiredMixin.

Mixins and the method resolution order

A mixin is a small class that adds one capability and is not meant to stand alone; a CBV combines it with a base view by multiple inheritance. Django’s own views are built exactly this way, which is why TemplateView is little more than View plus two mixins. To predict what a combination does you need one Python rule, the method resolution order (MRO): when self.method() is called, Python searches the classes of type(self).mro from left to right and runs the first definition it finds, and super() means "the next class after this one in that list", not "my parent". The list is computed by C3 linearisation: each class precedes its bases, and the left-to-right order of the bases in the class statement is preserved. Every Django view has View near the end and object last; listing the bases is therefore the way you choose the order in which the hooks run.

The arrows are the MRO printed earlier in the shell session for StaffDashboardView. Reading it is the debugging technique for every "why did my override not run" question: print MyView.mro, then find the first class that defines the method.

Four rules make mixins work.

  1. Mixins go to the left of the view class. class V(MyMixin, TemplateView). The base view’s dispatch() does not call super().dispatch(); it routes to a handler and stops. A mixin placed after it in the bases is behind that wall and its dispatch() is never called (the broken example below).

  2. Every override calls super(). A dispatch() or get_context_data() that forgets super() silently disables everything to its right in the MRO.

  3. Mixins stay small and independent. A mixin that uses attributes defined by another class (self.object, self.request.user) documents the dependency or checks for it; a mixin with init arguments is almost always a design smell, because as_view() configures views by attributes.

  4. Only one parent may be a view. Of the bases, only one class should derive from View; the rest are mixins. Combining two generic views (say ListView with ProcessFormView) mixes two get() implementations and rarely works.

A response-format mixin

Rendering is the part of a CBV most worth swapping, and the template pipeline gives you a clean seam: render_to_response(). A mixin adds render_to_json_response(), and the concrete view decides which renderer to call. One gotcha deserves the comment in the code: the context always contains view, the view instance, which JsonResponse cannot serialise:

catalog/views_mixins.py: one mixin, two output formats from the same view
from django.http import JsonResponse
from django.views.generic import TemplateView


class JSONResponseMixin:
    """Renders the template context as JSON instead of HTML."""

    def render_to_json_response(self, context, **response_kwargs):
        return JsonResponse(self.get_data(context), **response_kwargs)

    def get_data(self, context):
        # ContextMixin puts the view itself under "view": not JSON-serializable.
        return {key: value for key, value in context.items() if key != "view"}


class NegotiatedPageView(JSONResponseMixin, TemplateView):
    template_name = "catalog/pages/default.html"
    extra_context = {"title": "Opening hours"}

    def render_to_response(self, context, **response_kwargs):
        if self.request.GET.get("format") == "json":
            return self.render_to_json_response(context, **response_kwargs)
        return super().render_to_response(context, **response_kwargs)

Dispatch mixins: order is behaviour

Cross-cutting rules are the best use of dispatch() mixins. Order decides which one acts first: the leftmost mixin’s dispatch() runs first and passes the call along with super(). Here auditing is leftmost, so even refused requests are logged; reversing the first two would log only requests that pass the staff check. CurrentYearMixin shows the cooperative get_context_data() pattern: take what the next class in the MRO produced, add to it, return it.

SingleObjectMixin with a plain View

The object-lookup half of DetailView is SingleObjectMixin: model or queryset, get_queryset(), and get_object(), which reads the pk or slug URL captures (pk_url_kwarg, slug_url_kwarg) and answers 404 through Http404 when nothing matches. Combining list and single-object mixins

Sometimes one page needs a list that hangs off a single object: the books of one author, paginated. ListView provides pagination; SingleObjectMixin finds the author. Two views, one URL

A page that shows an object and also accepts a form posted to the same URL is the classic temptation to mix DetailView with FormMixin, which works only with considerable care. Where as_view() sits in the request cycle

A request reaches your class only after the middleware chain and the URL resolver. The resolver matches the path and returns the function from as_view(); the handler then runs the process_view() hooks of every middleware with that function and the captured arguments, and only then calls the function. That is why decorators and middleware cannot see your class directly, but can recover it from view_class:

catalog/middleware.py: a middleware that records which class served the request (installed first in MIDDLEWARE)
class ViewClassHeaderMiddleware:
    """Shows where as_view() sits in the request cycle: process_view() receives
    the function that as_view() returned and can read its view_class."""

    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        response = self.get_response(request)
        label = getattr(request, "view_label", None)
        if label:
            response["X-View"] = label
        return response

    def process_view(self, request, view_func, view_args, view_kwargs):
        view_class = getattr(view_func, "view_class", None)
        if view_class is not None:
            request.view_label = f"{view_class.__module__}.{view_class.__qualname__}"
        else:
            request.view_label = f"{view_func.__module__}.{view_func.__name__}"
        return None  # None means: carry on to the view

The X-View header in the curl output earlier (catalog.views_basic.GreetingView) comes from this middleware. Functions have no view_class, so the same middleware labels a function view with its dotted name. The same attribute is on resolve("/greet/").func, which is how tools such as the debug toolbar and test helpers identify the view class. After the view returns, a TemplateResponse is rendered, process_template_response() and the response-phase middleware run in reverse order, and the response goes out; an exception raised anywhere in your methods is passed to process_exception() and then turned into a 404, 403, 400 or 500 response by the exception handlers described on Request/Response Cycle and Middleware.

The middleware above is a plain synchronous class. Under ASGI, with async views, Django adapts a sync-only middleware by running it in a thread, which has a measurable cost; middleware that declares async_capable avoids it. For a project that is mostly synchronous none of this matters.

Async class-based views

Django has run async views since 3.1; since 4.1 a View subclass may define async def handlers. There is no special base class: you write async def get(…​) instead of def get(…​). as_view() checks the handlers (everything in http_method_names except options) and, when they are coroutine functions, marks the function it returns as a coroutine function, so Django’s handler awaits it on ASGI instead of running it in a thread. View.options() and http_method_not_allowed() detect the same condition and wrap their responses in a coroutine, so OPTIONS and 405 work in async views without code from you (the test suite checks both).

catalog/views_async.py: native async handlers, concurrent queries, async iteration, and a sync function bridged explicitly
import asyncio
import time

from asgiref.sync import sync_to_async
from django.http import JsonResponse
from django.views import View

from .models import Author, Book


class AsyncStatsView(View):
    async def get(self, request, *args, **kwargs):
        books, authors = await asyncio.gather(Book.objects.acount(), Author.objects.acount())
        return JsonResponse({"books": books, "authors": authors})


class AsyncTitlesView(View):
    async def get(self, request, *args, **kwargs):
        titles = [book.title async for book in Book.objects.order_by("title")]
        return JsonResponse({"titles": titles})

    async def post(self, request, *args, **kwargs):
        # A plain sync function (here a stand-in for a blocking library) is bridged explicitly.
        created = await sync_to_async(self._create_sync)(request.POST.get("title", "Untitled"))
        return JsonResponse({"created": created}, status=201)

    def _create_sync(self, title):
        author, _ = Author.objects.get_or_create(name="Anonymous")
        book = Book.objects.create(title=title, isbn=f"x{time.time_ns()}"[:13], author=author, price=0)
        return book.title

Inside the handlers, use the a-prefixed ORM methods (acount(), aget(), acreate()), async for over a QuerySet, and await sync_to_async(function)() for anything that is still synchronous-only. Calling a synchronous ORM method directly from an async handler raises SynchronousOnlyOperation; see Async Support and Making Queries for the async ORM.

What async buys you, and where it does not apply

  • Under ASGI an async handler does not hold a thread while it waits for I/O, so one process can serve hundreds of slow connections and can run several awaits concurrently (asyncio.gather above).

  • Under WSGI (runserver, Gunicorn sync workers) Django runs each async view in a one-off event loop. The code still works, and concurrent awaits inside one request still overlap, but you get none of the connection-scaling benefit and pay a small adaptation cost per request. The same AsyncStatsView answered correctly from runserver during testing.

  • A request is still the unit of work. Async is for waiting on networks and databases; CPU-bound work blocks the event loop under ASGI exactly as it blocks a thread under WSGI.

  • Transactions and persistent connections are the limits. Transactions do not work across await in async mode, so wrap transactional code in a synchronous function and call it through sync_to_async(); see Transactions, Raw SQL & Multiple Databases. Deployment and server choices are on Deployment.

The all-or-nothing rule

as_view() refuses a class whose handlers are a mixture of sync and async, because one function cannot be both. The check runs when the URLconf is imported, so the project fails at startup rather than on a request:

catalog/views_async.py
from django.http import HttpResponse
from django.views import View
from django.views.generic import CreateView

from .models import Book


class MixedView(View):
    """All handlers must be sync or all async; Django refuses a mixture."""

    def get(self, request, *args, **kwargs):
        return HttpResponse("sync")

    async def post(self, request, *args, **kwargs):
        return HttpResponse("async")


class AsyncCreateAttempt(CreateView):
    """CreateView ships sync get() and post(); an async get() makes the handlers a mixture."""

    model = Book
    fields = ["title"]

    async def get(self, request, *args, **kwargs):
        return HttpResponse("async get")
>>> MixedView.as_view()
django.core.exceptions.ImproperlyConfigured: MixedView HTTP handlers must either be all sync or all async.
>>> AsyncCreateAttempt.as_view()
django.core.exceptions.ImproperlyConfigured: AsyncCreateAttempt HTTP handlers must either be all sync or all async.

The second case is the practical consequence for the built-in generic views: their handlers (get(), post(), put()) are ordinary def methods, so declaring one handler async produces a mixture, and there is no async variant of ListView or CreateView. Make a view async by building it from View (and the context and template mixins if you want them) and writing every handler yourself. ListView with only an async get() does pass the check, but then nothing of `ListView’s own logic is awaitable, so it saves nothing.

Async dispatch(), decorators and mixins

An override of dispatch() that post-processes the response must be async def and await the call to super().dispatch(…​), because with async handlers that call returns a coroutine, not a response:

import time

from django.http import HttpResponse
from django.utils.decorators import method_decorator
from django.views.decorators.cache import never_cache


class AsyncTimedMixin:
    """An async-aware dispatch(): it must be async def and await the handler."""

    async def dispatch(self, request, *args, **kwargs):
        started = time.perf_counter()
        response = await super().dispatch(request, *args, **kwargs)
        response["X-Elapsed-Ms"] = f"{(time.perf_counter() - started) * 1000:.1f}"
        return response


class TimedAsyncStatsView(AsyncTimedMixin, AsyncStatsView):
    pass


class AwaitedDispatchView(View):
    @method_decorator(never_cache)
    async def dispatch(self, *args, **kwargs):
        return await super().dispatch(*args, **kwargs)

    async def get(self, request, *args, **kwargs):
        return HttpResponse("ok")

from django.contrib.auth.mixins import LoginRequiredMixin
from django.contrib.auth.views import redirect_to_login
from django.http import HttpResponse
from django.views import View


class SyncMixinOnAsyncView(LoginRequiredMixin, View):
    """BUG: LoginRequiredMixin.dispatch() is a plain def; its redirect cannot be awaited."""

    async def get(self, request, *args, **kwargs):
        return HttpResponse("members only")


class AsyncLoginRequiredMixin:
    async def dispatch(self, request, *args, **kwargs):
        user = await request.auser()
        if not user.is_authenticated:
            return redirect_to_login(request.get_full_path())
        return await super().dispatch(request, *args, **kwargs)


class MembersAsyncView(AsyncLoginRequiredMixin, View):
    async def get(self, request, *args, **kwargs):
        user = await request.auser()
        return HttpResponse(f"members only, {user.get_username()}")

Testing class-based views

Test a CBV at three levels, cheapest first. Calling as_view()(request) with a RequestFactory request runs setup(), dispatch() and the handler with no URLconf, middleware, session or database unless the view needs them; use it for unit tests of one view’s branches and of get_context_data(). The test client goes through the whole stack and is right for routing, middleware and templates. AsyncRequestFactory and AsyncClient are the async equivalents (the test method must itself be async def).

Function-based or class-based?

Neither replaces the other; the Django documentation says so in its first paragraph on class-based views. They are two ways to write the same contract, and a project normally contains both. What differs is how each style handles reuse, branching and readability:

A working rule, in the spirit of the advice in Two Scoops of Django and equally valid for Django 6.1: use the simplest view that is clear. A generic CBV for the standard CRUD pages, a TemplateView for static pages, a function view for one-off logic, webhooks and anything with branching that would need three overridden hooks in a class, and a plain View when you want verb separation without generic machinery. Keep views thin whichever style you choose: validation in forms, queries in managers and QuerySets (see Managers & Custom QuerySets), business rules in service functions, so that the view only translates between HTTP and those layers. Mixins are for behaviour that really is shared; two mixins with overlapping hooks are usually a sign that a function or a service object would be simpler. For JSON APIs prefer Django REST framework’s own class-based views or Django Ninja functions over bending the template views of this page.

Pitfalls checklist

  • Mutable class attributes are shared by all requests; assign them in setup().

  • as_view() arguments are evaluated once, at import time, including extra_context; per-request values go in get_context_data().

  • Forgetting super() in setup(), dispatch() or get_context_data() silently disables the rest of the MRO (or fails loudly for setup()).

  • A mixin to the right of the view class never runs, and access mixins then fail open. Test as an anonymous user.

  • A raw URL in RedirectView.get_redirect_url() from user input is an open redirect; accept keys and reverse() names.

  • csrf_exempt removes a protection; use it only on machine-to-machine endpoints that authenticate some other way.

  • CSRF answers before the 405: unsafe verbs without a token are 403 in a browser or curl, 405 in the test client.

  • context contains view; strip it before serialising the context.

  • Sync and async handlers cannot be mixed, and sync dispatch mixins (including LoginRequiredMixin) break async views for the cases where they return a response.

  • An async dispatch() must await the call to super().dispatch().

  • Heavy hierarchies are hard to read: if you need the MRO diagram to explain a view, simplify it.
