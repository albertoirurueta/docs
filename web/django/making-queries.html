Making Queries

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Django 6.1 (6.1.1 on PyPI; 6.1.2 is scheduled for 2026-10-06), Python 3.12-3.14 and PostgreSQL 15+, checked on 2026-10-03; where Django 5.2 LTS behaves differently the text says so. The listings were run in a scratch project on Python 3.13.16 and Django 6.1.1 with SQLite: manage.py check, four tests (manage.py test), a curl session against runserver and every shell example below passed, and the output shown is the real output. Examples that depend on a PostgreSQL feature say so; none of the code needs anything but SQLite.

The ORM is the part of Django that turns Python method calls into SQL. Its central object is the QuerySet: a lazy, chainable, cached description of a query. This page shows how to build one, when it actually reaches the database, how to filter across relationships, how to express "compare this column with that column" (F) and "this or that" (Q), how to create, update and delete rows singly and in bulk, how to shape results (values, alias, exists, contains) and how to teach the ORM new lookups. Defining the fields and relations being queried is covered on Models & Fields and Relationships; aggregation, subqueries and database functions are on Aggregation, Expressions & Functions; reusable query methods are on Managers & Custom QuerySets; and avoiding the N+1 query problem is the subject of Query Optimization & Fetch Modes. For the SQL side of finding slow queries, see Diagnosing slow queries.

Every example queries the same three small models of the Bookshelf catalogue, plus Genre for a many-to-many relation. The Meta.ordering on Book matters later (default ordering interacts with first(), union() and slicing):

QuerySets and laziness

A manager (Book.objects) is the entry point; calling all(), filter() and the other query methods on it returns a QuerySet. A QuerySet is a Python object that holds a query description, not rows. Three rules explain almost every ORM surprise:

  1. Building is free. filter(), exclude(), order_by(), annotate(), values(), slicing and the other "returns a new QuerySet" methods never touch the database.

  2. Chaining never mutates. Each of those methods returns a new QuerySet; the original is unchanged and can be reused as a base for other queries.

  3. Evaluation runs the query once and caches the rows. The first time you iterate, call len(), list(), bool() or repr(), index with a step, or pickle a QuerySet, Django executes the SQL and stores the instances in the QuerySet’s result cache; reusing that same object costs no query.

from catalog.models import Book

with CaptureQueriesContext(connection) as ctx:

The details that matter in practice:

  • Slicing. qs[2:5] on an unevaluated QuerySet adds LIMIT 3 OFFSET 2 and returns another QuerySet. A step (qs[::2]) forces evaluation and returns a list. Negative indices are not supported (ValueError: Negative indexing is not supported.), and a sliced QuerySet cannot be filtered further (TypeError: Cannot filter a query once a slice has been taken.) or deleted.

  • str(qs.query) prints the SQL that would run (parameters inlined, for reading only). Do not execute it. For the SQL a block actually executed, wrap it in CaptureQueriesContext, as the listings here do, or use the Debug Toolbar.

  • The cache belongs to the object. Book.objects.filter(…​) called twice builds two QuerySets and runs two queries. Keep the QuerySet in a variable if you will iterate it twice, and pass it to the template rather than a list copy.

  • Which methods use the cache. len(), iteration, bool() and list() evaluate and cache. count() on a QuerySet that is already loaded returns the length of the cache; on a fresh one it runs SELECT COUNT(*). exists() and contains() use the cache when they can and otherwise ask the database for one row.

  • if qs: is a hidden SELECT *. Truthiness evaluates the whole QuerySet. Use qs.exists() when you only need to know if there is a row, qs.count() when you only need the number, and len(qs) only when you will iterate afterwards.

  • iterator() streams rows in chunks and bypasses the cache; it is the tool for very large results (see below).

Where a query runs in the request/response cycle

A QuerySet is evaluated where it is first consumed, which is not always where it was written. A view that returns Book.objects.all() in the template context queries when the template loop starts, after the view has returned; a QuerySet stored at module level is shared by every request and its result cache would be reused forever, so build QuerySets inside the view (or call .all() on a stored one, which returns a fresh copy). The database connection is per thread and managed by Django: opened lazily on the first query of a request and closed at the end of the request unless CONN_MAX_AGE keeps it open (CONN_HEALTH_CHECKS can validate a persistent connection before reuse). With ATOMIC_REQUESTS = True the whole view runs in one transaction, which is covered on Transactions, Raw SQL & Multiple Databases. The complete view and tests at the end of this page show the cycle in action.

Retrieving objects: all, filter, exclude and get

Method Behaviour

all()

A QuerySet for every row (a copy; evaluation is still lazy).

filter(**lookups)

Rows matching all the keyword conditions (joined with AND). Arguments can also be Q objects (below).

exclude(**lookups)

Rows that do not match the combined conditions (NOT (a AND b)).

get(**lookups)

Exactly one object, as an instance, not a QuerySet. Raises Model.DoesNotExist for zero rows and Model.MultipleObjectsReturned for more than one (both subclass ObjectDoesNotExist / MultipleObjectsReturned).

first() / last()

The first or last object by ordering (falling back to the primary key when the QuerySet is unordered), or None. Since 6.1 they no longer add a primary-key ordering when you cleared the ordering with a bare order_by().

earliest(field) / latest(field)

The object with the smallest or largest value of a field; raises DoesNotExist when there are no rows.

order_by(*fields) / reverse()

Ordering; a leading - is descending; F("x").desc(nulls_last=True) controls NULL placement.

distinct()

SELECT DISTINCT; needed when a join on a multi-valued relation repeats rows.

none()

An always-empty QuerySet that never queries; useful for permission filters.

in_bulk(id_list, field_name="pk")

A dict mapping the field value to the instance, in one query. 6.1 allows chaining it after values() / values_list().

Field lookups

A lookup is the suffix that says how to compare a field. title="x" is shorthand for titleexact="x". The full form is fieldlookup=value, optionally with transforms in between (publishedyear__gte=1990 is the year transform followed by the gte lookup).

Lookup Meaning

exact, iexact

Equality; iexact is case-insensitive. exact=None is IS NULL.

contains, icontains

Substring (LIKE '%x%'), case-sensitive or not. On SQLite LIKE is case-insensitive for ASCII text, so contains behaves like icontains there; PostgreSQL honours the difference.

startswith, istartswith, endswith, iendswith

Prefix and suffix matches.

in

Membership in a list, tuple or another QuerySet (which becomes a subquery).

gt, gte, lt, lte

Comparisons.

range

BETWEEN low AND high (inclusive); works for numbers, dates and datetimes.

isnull

True or False only; non-boolean right-hand values, which were never documented, stopped being accepted in Django 4.0.

regex, iregex

Regular-expression match, using the database’s regex dialect.

date, year, iso_year, month, day, week, week_day, iso_week_day, quarter, time, hour, minute, second

Date and time component transforms that can be followed by another lookup (publishedyearlt=1965). Datetime fields follow the current time zone when USE_TZ is true.

Spanning relationships

Double underscores also walk relationships, forwards (authorname), backwards (bookstitle, using related_name or, by default, the model name in lowercase; set related_query_name to change the query name independently) and through many-to-many tables (genres__name). Django adds the `JOIN`s itself. See Relationships for how the relations are declared.

Following relationships in filters (ex/e4_relations.py)
from django.db import connection
from django.test.utils import CaptureQueriesContext
from catalog.models import Author, Book, Genre, Review

def names(qs, attr="title"):
    return sorted(getattr(o, attr) for o in qs)

# forward: follow the ForeignKey with double underscores
print(names(Book.objects.filter(author__name__startswith="Stan")))
# backward: related_name="books" is also the default query name
print(names(Author.objects.filter(books__price__gt=12), "name"))
# many-to-many in both directions
print(names(Book.objects.filter(genres__name="Fantasy")), names(Genre.objects.filter(books__title="Kindred"), "name"))
# across two hops, and to a model without a reverse name (reviews -> reviewer)
print(names(Book.objects.filter(reviews__reviewer__username="ana")))
# isnull across a reverse relation = "has no rows"
print(names(Book.objects.filter(reviews__isnull=True)))
print(names(Author.objects.filter(books__isnull=True), "name"))

# multi-valued relations: one filter() call = one related row must satisfy ALL conditions
one_call = Book.objects.filter(reviews__rating=5, reviews__body="Dense but rewarding")
# chained filter() calls = conditions may be satisfied by DIFFERENT related rows
chained = Book.objects.filter(reviews__rating=5).filter(reviews__body="Dense but rewarding")
print("one call:", names(one_call), "| chained:", names(chained))
print(chained.query.__str__().count("JOIN"), "joins when chained;", one_call.query.__str__().count("JOIN"), "when in one call")

# exclude() on a multi-valued relation is a subquery, and does NOT behave like filter() negated
print(names(Book.objects.exclude(reviews__rating=5, reviews__body="Brilliant")))

# duplicates: a join on a multi-valued relation can repeat the parent row
print(Book.objects.filter(reviews__rating__gte=3).count(), Book.objects.filter(reviews__rating__gte=3).distinct().count())

Three behaviours in this output decide whether a query is correct:

  • One filter() call versus a chain. With a multi-valued relation (reverse foreign key, many-to-many), conditions in a single filter() call must be satisfied by the same related row, while conditions in chained filter() calls may be satisfied by different related rows. Here no single review is both a 5 and "Dense but rewarding", but The Dispossessed has one review with rating 5 and another with that text, so the chain matches it. The SQL differs accordingly (the chain adds a second JOIN).

  • exclude() does not mirror filter(). On a multi-valued relation exclude(reviewsrating=5, reviewsbody="Brilliant") removes books that have a review matching both conditions; Django builds it with a subquery, and the result here removes only The Dispossessed, whereas exclude(a).exclude(b) would remove every book with a 5 or a "Brilliant" review.

  • Joins repeat rows. Filtering on reviewsratinggte=3 joins Book to Review, so a book with two matching reviews appears twice (4 rows versus 3 with distinct()). Use distinct(), or filter with a subquery (pk__in= or Exists()) when the duplicates matter.

The related manager (author.books, book.reviews, book.genres) is a manager scoped to one object: le_guin.books.filter(price__lt=10) is a normal QuerySet. Every attribute traversal from an instance (book.author) is a separate query when the object was not loaded with the relation: the last loop above issues nine queries for eight books. That is the N+1 problem; the cures (select_related, prefetch_related and the Django 6.1 fetch modes) are on Query Optimization & Fetch Modes.

F expressions: referring to columns

An F("field") object refers to the value of a column inside the database instead of a Python value that was read earlier. It has three jobs: comparing two columns of one row, computing a new value from the current one, and ordering or annotating by an expression. Because the arithmetic happens in SQL, an F() update is atomic with respect to other writers and avoids the lost-update race of "read, add one in Python, save".

Q objects: AND, OR, NOT and XOR

Keyword arguments to filter() are always AND`ed. A `Q() object wraps the same keyword conditions so they can be combined with & (and), | (or), ~ (not) and, since Django 4.1, ^ (exclusive or: true when an odd number of the operands is true). get_or_create and update_or_create

get_or_create(defaults=None, kwargs) looks the row up with get(kwargs); if it does not exist it creates it from kwargs plus defaults and returns (object, created). update_or_create() does the same but, when the row exists, applies defaults as updates (via save()), and returns (object, created). Both are not single SQL statements: Django wraps them in a transaction (a savepoint when already inside one), and relies on a unique constraint to resolve races.

  • In views build the lookup from validated input only; a get_or_create on request.POST data is a write triggered by user input and needs the same CSRF and validation care as any form handler.

create(**kwargs) / save()

One INSERT or UPDATE; runs save() overrides, pre_save/post_save signals and field auto_now handling.

The upsert is the headline: bulk_create(…​, update_conflicts=True, unique_fields=[…​], update_fields=[…​]) compiles to INSERT …​ ON CONFLICT (isbn) DO UPDATE SET …​, so a nightly price import is one statement for any number of rows, instead of a get_or_create per row. The facts to keep in mind:

  • Added in Django 4.1 (confirmed in the 4.1 release notes: "QuerySet.bulk_create() now supports updating fields when a row insertion fails uniqueness constraints"), supported on MariaDB, MySQL, PostgreSQL and SQLite 3.24+; the 6.1 baseline is SQLite 3.37, so it is available everywhere Django 6.1 runs, except Oracle.

  • unique_fields is required on PostgreSQL and SQLite (the conflict target) and ignored on MySQL/MariaDB, which choose the target themselves; update_fields is the list of columns to overwrite. Give both on every backend so the code is portable.

  • Primary keys. With update_conflicts=True Django 5.0 and later sets the primary key on every instance when the database supports it (the [True, True] line); ignore_conflicts=True never sets primary keys (the duplicate instance shows None). Before 5.0 the keys were missing for upserts, and on SQLite bulk_create only returned primary keys from 4.0 (SQLite 3.35+).

  • ignore_conflicts swallows more than duplicates on MySQL and MariaDB (invalid values, non-nullable violations become warnings); the official page carries that warning.

  • Signals and validation are skipped. No save(), no pre_save/post_save, no model full_clean(); validate before inserting.

  • Batching. SQLite and Oracle limit the number of query parameters, so Django splits large inserts; set batch_size explicitly for very large lists (and to bound memory in bulk_update, which builds all WHEN clauses before running anything).

  • update() returns rows matched (which can be more than the rows whose value actually changed). Use the return value to detect "nothing to update" for compare-and-set logic: filter(pk=…​, stock__gt=F("reserved")).update(reserved=F("reserved") + 1) == 1, shown in reserve_copy() below.

  • save(update_fields=[…​]) writes only the named columns (the last line prints the unchanged pages), which also narrows the window for lost updates between concurrent edits of different fields.

  • delete() collects related objects in Python to honour on_delete and signals, unless the relation and the database allow a fast path; Django 6.1’s DB_CASCADE, DB_SET_NULL and DB_SET_DEFAULT options move that work into the database (see Relationships).   • Combined queries are restricted. After union(), intersection() or difference() only count(), order_by(), values(), values_list() and slicing are allowed (the NotSupportedError above); every part must select compatible columns.

Custom lookups and transforms

When no built-in lookup says what you mean, register your own. A Lookup subclass (lookup_name, as_sql()) adds a comparison such as ne; a Transform subclass (function, an output_field) adds a step that can be chained with further lookups, such as pagesabs__lt. Register them on a field class with Field.register_lookup() (a decorator form exists), import the module from AppConfig.ready() so registration happens at startup, and remember that the lookup’s as_sql() returns the SQL fragment and its parameters, never user data interpolated into the string.

catalog/lookups.py
from django.db.models import CharField, Field, IntegerField, Lookup, Transform
from django.db.models.functions import Lower


@Field.register_lookup
class NotEqual(Lookup):
    """title__ne="x"  ->  title <> 'x'"""

    lookup_name = "ne"

    def as_sql(self, compiler, connection):
        lhs, lhs_params = self.process_lhs(compiler, connection)
        rhs, rhs_params = self.process_rhs(compiler, connection)
        return f"{lhs} <> {rhs}", (*lhs_params, *rhs_params)


@IntegerField.register_lookup
class AbsoluteValue(Transform):
    """pages__abs  ->  ABS(pages)"""

    lookup_name = "abs"
    function = "ABS"

    @property
    def output_field(self):
        return IntegerField()


# Lower is a Transform that Django ships but does not register on any field
CharField.register_lookup(Lower)

  • Register early. A lookup is only known after its module is imported; importing it in ready() guarantees it exists before any query is built. Import errors there fail at startup, which is the point.

  • Lookup versus Transform. A Transform takes one expression and returns a new one (ABS(pages)), so it can be followed by a lookup or another transform; a Lookup takes a left and right side and returns a boolean condition, so it ends the chain. Django’s database functions can be registered as transforms too (FloatField.register_lookup(Abs) in the official database-functions reference); the listing registers Lower on CharField to enable titlelowerstartswith (it is not registered by default).

  • Per-field registration (Django 4.2). Book._meta.get_field("title").register_lookup(ShortTitle) registers a lookup on a single field instance; other fields of the same class do not see it (the FieldError for Author.name). Earlier versions could only register on field classes.

  • prepare_rhs. By default the right-hand value is converted with the left field’s get_prep_value(): on a CharField the integer 7 would become the string '7' and SQLite would compare a number with text and match every row. Set prepare_rhs = False (as ShortTitle does) or override get_prep_lookup() when the right-hand side has a different type.

  • Database-specific SQL. Define as_postgresql(), as_mysql(), as_oracle() or as_sqlite() next to as_sql() to emit different SQL per vendor; Django picks the method matching connection.vendor.

  • bilateral = True on a Transform applies it to both sides (a case-insensitive comparison via UPPER on both the column and the value).

  • PostgreSQL extras. django.contrib.postgres registers its own lookups (unaccent, trigram_similar, full-text search); see PostgreSQL & Database Backends.

The Bookshelf search: queries, view, tests and curl

The pieces combine into a small search endpoint. The function builds one composable QuerySet from optional filters, select_related("author") loads the author in the same query, the view paginates and returns JSON, and the tests pin both behaviour and query counts with assertNumQueries.

catalog/queries.py
from decimal import Decimal

from django.db.models import F, Q

from .models import Book


def search_books(*, text: str = "", country: str = "", max_price: Decimal | None = None, in_stock: bool = False):
    """Build one composable QuerySet from optional filters; nothing runs until it is evaluated."""
    q = Q(is_published=True)
    if text:
        q &= Q(title__icontains=text) | Q(author__name__icontains=text)
    if country:
        q &= Q(author__country=country)
    if max_price is not None:
        q &= Q(price__lte=max_price)
    if in_stock:
        q &= Q(stock__gt=F("reserved"))
    return Book.objects.filter(q).select_related("author")


def reserve_copy(book_id: int) -> bool:
    """Atomic compare-and-set: succeeds only while an unreserved copy is left."""
    updated = Book.objects.filter(pk=book_id, stock__gt=F("reserved")).update(reserved=F("reserved") + 1)
    return updated == 1


def import_prices(rows: list[dict]) -> None:
    """Upsert (INSERT ... ON CONFLICT DO UPDATE) keyed on the unique ISBN."""
    Book.objects.bulk_create(
        [Book(**row) for row in rows],
        update_conflicts=True,
        unique_fields=["isbn"],
        update_fields=["price", "stock"],
    )

def book_search(request):
    try:
        max_price = Decimal(request.GET["max_price"]) if "max_price" in request.GET else None
    except InvalidOperation:
        return JsonResponse({"error": "max_price must be a number"}, status=400)

        country=request.GET.get("country", ""),
        max_price=max_price,

    return JsonResponse({
        "count": page.paginator.count,
        "results": [{"title": b.title, "author": b.author.name, "price": str(b.price)} for b in page],
    })

Sync and async behaviour

Since Django 4.1 every QuerySet method that hits the database has an a-prefixed coroutine (aget, acreate, acount, aexists, afirst, aupdate, adelete, abulk_create, aget_or_create, aiterator, …​) and a QuerySet can be consumed with async for. Django 4.2 added Model.asave(), adelete() and arefresh_from_db() and the async related-manager methods (aadd, aclear, aremove, aset); 5.0 added aprefetch_related_objects(), prefetching with aiterator() and create_defaults for aupdate_or_create(). Methods that only build a QuerySet (filter, exclude, order_by, …​) are plain synchronous calls in both worlds.

  • The async API still uses a thread. The ORM drivers are synchronous; a-methods run the sync code in a thread pool (sync_to_async), so they keep the event loop responsive but do not make the database faster. Transactions are not supported across await points: transaction.atomic() cannot wrap async code, so put the atomic part in a sync function and call it with sync_to_async.

  • Lazy attribute access is blocked. book.author on an unloaded relation, list(qs) or if qs: inside a coroutine raise SynchronousOnlyOperation; load relations up front with select_related() or prefetch_related(), or await them.

  • Connections. The ORM calls run in worker threads and each thread has its own database connection; see Async Support for how persistent connections and async code interact.

  • Sync views under ASGI still work: Django runs them in a thread. Choose async views only when the view awaits other I/O (HTTP calls, channels) besides the ORM.

Where the books are outdated

Books written for Django 1.11 to 3.x describe the ORM correctly in outline (QuerySets, lookups, F/Q, get_or_create, values), but several parts have moved on:

  • Missing features. They predate QuerySet.alias() (3.2), QuerySet.contains() (4.0), Q XOR (4.1), bulk_create upserts (4.1), create_defaults (5.0), per-field register_lookup (4.2), the async ORM (4.1/4.2), QuerySet.totally_ordered and fetch modes (6.1); pre-4.1 code typically reaches for raw SQL, extra() or a get_or_create loop where these now exist. The official documentation calls extra() a last resort that is expected to be deprecated.

  • Boolean checks. Old advice to write if qs.count() > 0 or if len(qs) is superseded by exists() (and contains() for a given instance).

  • NullBooleanField was removed in 4.0 (use BooleanField(null=True)), and non-boolean values for isnull are no longer accepted (4.0); django.utils.six and Python 2 idioms (iteritems, unicode) are gone.

  • bulk_update() returns the number of updated rows since 4.0; bulk_create() sets primary keys on SQLite since 4.0 and on upserts since 5.0.

  • Defaults. Primary keys are BigAutoField by default since 6.0, so the ids printed in older listings (AutoField) differ in the migrations they generate.

  • assertQuerysetEqual is assertQuerySetEqual (4.2; old name removed in 5.1) and no longer calls repr() on strings.

  • Shell and Python. Interactive examples that import models by hand predate the shell auto-imports of 5.2; code based on pytz or timezone-naive datetimes predates zoneinfo (4.0) and the USE_TZ = True default (5.0).
