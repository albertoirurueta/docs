PostgreSQL & Database Backends

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Django 6.1 (6.1.1, released 2026-09-02; 6.1.2 is scheduled for 2026-10-06), Python 3.12-3.14 and PostgreSQL 15 or newer, with psycopg 3.3.6, all checked on 2026-10-03; where the 5.2 LTS (5.2.17) behaves differently the text says so. No PostgreSQL server was available while writing, so nothing on this page was run against one: the PostgreSQL examples were validated by manage.py check, by makemigrations, by sqlmigrate and by compiling the queries to SQL with the real PostgreSQL backend and its field, index, constraint and function classes, with the server round-trips stubbed out, and the portable SQLite code was executed and tested. The section What was run, and what was not lists, example by example, what was executed and what was not. Choosing PostgreSQL is the most common decision a Django project makes about its database, and the reason is not only quality: django.contrib.postgres exposes PostgreSQL’s arrays, ranges, hstore, exclusion constraints, GIN/GiST indexes and full-text search as ordinary fields, lookups and expressions. In the Bookshelf application that grows across this section, PostgreSQL stores the catalogue, tags books with arrays, prevents two book-club meetings from overlapping in a room with an exclusion constraint and powers the catalogue search with a stored, weighted full-text vector. This page covers the backend notes for every officially supported database, then django.contrib.postgres (fields, indexes, constraints, migration operations, aggregates), then search (full-text and trigram), and ends with pitfalls, what is outdated in older books and what changed recently.

Connections: lifetime, health checks and pools

Django opens a connection the first time a request needs one and, by default, closes it at the end of the request (CONN_MAX_AGE = 0). settings.py configures this per alias; the full table of DATABASES keys is in Settings & Configuration. What matters for the backend choice:

  • CONN_MAX_AGE set to a positive number of seconds (or None for unlimited) keeps one connection per thread alive between requests. Django closes an over-age or broken connection at the start or end of a request. Your database must allow at least as many connections as you have worker threads. The development server creates a thread per request, so persistence does nothing there.

  • CONN_HEALTH_CHECKS = True checks a reused connection once per request, and only if the request touches the database. It prevents errors after the server closed an idle connection or restarted.

  • Under ASGI, persistent connections should be disabled. The async ORM methods run the queries in a thread, so a long lifetime per thread does not help; use the backend’s pool (or an external pooler) and size it to the number of queries you want in flight.

  • PostgreSQL pools (5.1, psycopg only): set "pool" in OPTIONS to True (the ConnectionPool defaults) or to a dictionary of ConnectionPool options. This needs psycopg[pool], and CONN_MAX_AGE must be 0; connection lifetime is the max_lifetime pool option. Django keeps one pool per database alias per process, and closing a Django connection returns it to the pool. Unless you pass a check callable, CONN_HEALTH_CHECKS decides whether connections are checked on checkout.

  • Oracle pools (5.2): "pool": True or a dictionary for the driver’s create_pool().

# config/settings_pg.py -- needs a PostgreSQL server and psycopg[pool]
import os

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ.get("POSTGRES_DB", "bookshelf"),
        "USER": os.environ.get("POSTGRES_USER", "bookshelf"),

The import was executed (it printed 4 for IsolationLevel.SERIALIZABLE); the options were not applied to a server. Further PostgreSQL facts from the notes:

  • Fewer round-trips per connection. Django needs client_encoding set to UTF8, the isolation level (read committed by default) and timezone (UTC when USE_TZ is True). If the role already has those values, Django skips the SET statements for each new connection; set them with ALTER ROLE or in postgresql.conf.

  • varchar and text get two indexes with db_index=True. Django adds a second index with the like operator class (varchar_pattern_ops/text_pattern_ops), needed for LIKE-based lookups such as contains and startswith. The sqlmigrate output of a unique=True CharField shows it (pgdemo_room_name…​_like).

  • Server-side cursors and poolers. QuerySet.iterator() opens a server-side cursor, and PostgreSQL assumes only the first 10% of a cursor query will be fetched (cursor_tuple_fraction). Behind a transaction-pooling pooler such as PgBouncer, set DISABLE_SERVER_SIDE_CURSORS = True for that alias, or wrap the iteration in atomic().

  • Identity columns and explicit primary keys. Auto-incrementing keys are identity columns fed by a sequence. Creating a row with an explicit pk does not advance the sequence, so a later insert can raise IntegrityError: duplicate key value violates unique constraint. After loading data with explicit keys, run manage.py sqlsequencereset <app> and execute the output.

  • Extensions such as hstore, pg_trgm or btree_gist are enabled through migration operations, see Migration operations: extensions, collations, concurrent indexes.

  • Tests. TEST["TEMPLATE"] names the template database the test database is created from; the notes also describe speeding the test run with non-durable settings on a throwaway server, which is dangerous on anything you care about.

MySQL and MariaDB notes

MariaDB uses the MySQL backend (ENGINE = "django.db.backends.mysql"), so the notes apply to both. They were not executed here; they are the documentation’s, grouped by what goes wrong:

Topic What to know

Storage engine

Use InnoDB (transactions, foreign keys). MyISAM does not enforce foreign keys and does not support transactions; savepoint methods raise database errors on it. Django does not choose an engine when creating tables, so set the server default.

Character set

Create the database with CHARACTER SET utf8mb4. Columns of type VARCHAR with unique=True are limited to 255 characters (CharField, SlugField); a TextField cannot be unique=True because MySQL needs a key length.

Collation

The default utf8mb4_0900_ai_ci compares strings case-insensitively, so "Fred" and "freD" collide on a unique column. Use db_collation per column or a case-sensitive collation (utf8mb4_0900_as_cs). Model formsets validate unique fields case-sensitively, so the database can still raise IntegrityError at save().

sql_mode

Keep strict mode (STRICT_TRANS_TABLES or STRICT_ALL_TABLES) so truncation raises instead of losing data; set it with 'init_command': "SET sql_mode='STRICT_TRANS_TABLES'" in OPTIONS.

Isolation level

Django works best with, and defaults to, read committed; MySQL’s own default repeatable read can make get_or_create() raise IntegrityError for an object that a following get() cannot see. Set OPTIONS["isolation_level"] to 'read committed', 'repeatable read', 'serializable' or 'read uncommitted' (or None for the server’s setting).

Time zones and fractions

Load the time zone tables with mysql_tzinfo_to_sql once per server to use time-zone support. Fractional seconds need DATETIME(6) columns; Django does not upgrade existing columns (use RunSQL in a migration). A legacy database with TIMESTAMP columns needs USE_TZ = False to avoid corrupting values.

Row locking

SKIP LOCKED and NOWAIT work on both; OF is MySQL-only; NO KEY is not supported on either, and unsupported options raise NotSupportedError. Filter select_for_update() on indexed or unique columns, or MySQL locks the whole table for the transaction.

Type coercion

Querying a string column with an integer makes MySQL coerce every row to an integer (so WHERE col = 0 matches 'abc'). Django casts string-field values to strings; if you write custom fields, RawSQL, extra() or raw(), do the same.

Table names

MySQL can alter the case of table names under some conditions; keep db_table lowercase.

SQLite notes

SQLite is the zero-configuration backend (the standard-library driver, 3.37.0 or newer) and the one every example in this section can fall back to. The differences that surprise people:

  • Substring and case matching. contains and iexact match case-insensitively for substrings, but exact matches on strings with non-ASCII characters are case-sensitive even with iexact.

  • Decimals are floats. DecimalField is stored as REAL, so decimal arithmetic is not exact.

  • "database is locked". Too much write concurrency. Shorten transactions, raise OPTIONS["timeout"] (which only waits longer) or move to another backend.

  • Transaction mode. OPTIONS["transaction_mode"] accepts DEFERRED (default), IMMEDIATE and EXCLUSIVE (5.1); IMMEDIATE waits for the lock up to the timeout. ATOMIC_REQUESTS is discouraged with it.

  • Pragmas. OPTIONS["init_command"] runs statements at connection time (5.1).

  • No row locking. select_for_update() is accepted but has no effect.

  • Mutating a table while iterating. Rows changed inside an iterator() loop may appear zero or two times.

  • JSON. JSONField needs the JSON1 extension, enabled by default from SQLite 3.38; otherwise fields.E180.

Oracle notes

Oracle 19c or newer with oracledb 2.3.0 or newer. Nothing here was executed (no server, no driver). The points that shape a project:

  • Privileges. migrate needs CREATE TABLE, CREATE SEQUENCE, CREATE PROCEDURE and CREATE TRIGGER. Running a test suite needs additional user and tablespace privileges (CREATE USER, ALTER USER, DROP USER, CREATE TABLESPACE, DROP TABLESPACE and the WITH ADMIN OPTION variants), all included in the DBA role, which is appropriate on a private developer database only. The backend also uses SYS.DBMS_LOB and SYS.DBMS_RANDOM.

  • Connecting. With a service name (or a tnsnames.ora entry) leave HOST and PORT empty; with a SID fill in both. A full DSN or Easy Connect string can go into NAME when HOST and PORT are empty ("NAME": "localhost:1521/orclpdb1").

  • Pool (5.2). "OPTIONS": {"pool": True}, or a dictionary of create_pool() parameters such as min and max.

  • INSERT …​ RETURNING INTO. The backend uses it to read generated keys; disable with "use_returning_into": False in OPTIONS for unusual setups such as remote tables or views with INSTEAD OF triggers.

  • Names. Identifiers are limited to 30 characters (truncated with an MD5 suffix) and upper-cased; a quoted db_table such as '"name_left_in_lowercase"' avoids both. Do not name a field date, timestamp, number or float.

  • NULL and empty strings. Oracle treats them identically, so the backend ignores an explicit null=False on fields that allow '' and reads NULL back as ''.

  • TextField is an NCLOB. It cannot be a primary key, be indexed or appear in SELECT DISTINCT; combine defer() with distinct() as a workaround.

Source: Django: Oracle notes

Subclassing a backend, and third-party backends

To change one behaviour of a built-in backend (a feature flag, an operation) you subclass it: a package with a base.py that defines a DatabaseWrapper subclass, then ENGINE set to the package. This is also the pattern the third-party backends use.

# mydbengine/base.py
from django.db.backends.postgresql import base, features


class DatabaseFeatures(features.DatabaseFeatures):
    def allows_group_by_selected_pks_on_model(self, model):
        return True


class DatabaseWrapper(base.DatabaseWrapper):
    features_class = DatabaseFeatures
DATABASES = {"default": {"ENGINE": "mydbengine", "NAME": "bookshelf"}}

Source: Django: Subclassing the built-in database backends

Executed: with that setting Django resolved the engine, connection.features came from mydbengine.base and connection.vendor was still postgresql. Keep such subclasses small; each Django release can change the feature flags and operation methods you override.

Writing code that survives two backends

The cleanest policy is to test on the database you deploy to (Testing on PostgreSQL). When a project must run on SQLite as well (a tutorial, a laptop without Docker), isolate the PostgreSQL-only code behind connection.vendor, which is "postgresql", "mysql", "sqlite" or "oracle":

# portable/search.py
from django.db import connections
from django.db.models import Q, QuerySet


def search_books(qs: QuerySet, term: str, using: str = "default") -> QuerySet:
    """Full-text search on PostgreSQL, a plain substring match everywhere else."""
    if connections[using].vendor == "postgresql":
        from django.contrib.postgres.search import SearchQuery, SearchRank, SearchVector

        vector = SearchVector("title", weight="A") + SearchVector("summary", weight="B")
        query = SearchQuery(term, search_type="websearch")
        return (
            qs.annotate(search=vector, rank=SearchRank(vector, query))
            .filter(search=query)  # the @@ match, not a rank threshold
            .order_by("-rank")
        )
    return qs.filter(Q(title__icontains=term) | Q(summary__icontains=term))

from django.db import connection
from django.test import TestCase

from .models import Book

Migration operations: extensions, collations, concurrent indexes

django.contrib.postgres.operations provides the operations that make migrations PostgreSQL-aware. Their position in the request cycle is "deployment": they run during migrate, never while serving a request.

Extensions

ExclusionConstraint

An exclusion constraint generalises a unique constraint to any commutative operator: "no two rows may satisfy this operator on these expressions at the same time". PostgreSQL implements it with an index (GiST by default). The classic use is preventing overlapping bookings, and it is the only reliable way to do that: checking overlap in Python before saving has a race between two concurrent requests.

ExclusionConstraint(*, name, expressions, index_type=None, condition=None, deferrable=None, include=None, violation_error_code=None, violation_error_message=None):

  • expressions: an iterable of (expression_or_field_name, operator) pairs; use RangeOperators instead of raw operator strings. For ("room", RangeOperators.EQUAL) on a scalar column you need the btree_gist extension (BtreeGistExtension()).

  • index_type: GiST (default), Hash (6.1) or SPGiST, case-insensitive.

  • condition: a Q restricting the constraint to a subset of rows (condition=Q(cancelled=False)), with the same database restrictions as a partial index.

  • deferrable: Deferrable.DEFERRED or Deferrable.IMMEDIATE; a deferred constraint is enforced at the end of the transaction, with a performance penalty.

  • include: non-key columns for index-only scans (GiST and SP-GiST).

  • violation_error_code (5.0) and violation_error_message: used when model validation raises ValidationError.

  • OpClass() can set a custom operator class for any expression.

A violation raises IntegrityError at save time, and exclusion constraints are also checked by model validation (full_clean(), ModelForm). The model and DDL are the Booking model and the CREATE TABLE …​ EXCLUDE USING GIST in the earlier listings. Full-text search

PostgreSQL’s full-text search compares a tsvector (a document reduced to normalised lexemes, stemmed and without stop words) with a tsquery. Django exposes both through django.contrib.postgres.search. It is "inside your database", so it combines with relational filters and needs no extra service; it is less powerful than a dedicated engine (Elasticsearch, Solr), which you would feed through a translation layer. See the database reference for those engines and PostgreSQL pgvector for semantic search in the same database.

The search lookup and SearchVector

The simplest search is a lookup on one column, which builds a to_tsvector from the column and a plainto_tsquery from the term, both in the database’s default configuration (needs django.contrib.postgres in INSTALLED_APPS):

from django.contrib.postgres.search import SearchVector

Book.objects.filter(summary__search="cheese")

Book.objects.annotate(search=SearchVector("title", "summary")).filter(search="django")
WHERE to_tsvector(COALESCE("pgdemo_book"."summary", '')) @@ (plainto_tsquery('cheese'))
WHERE to_tsvector(COALESCE("title", '') || ' ' || COALESCE("summary", '')) @@ (plainto_tsquery('django'))

Source: Django: The search lookup

Compiled only. SearchVector(*expressions, config=None, weight=None) takes field names or expressions, concatenates several arguments with a space, and vectors can be added (SearchVector("a") + SearchVector("b")). The relation-spanning form (SearchVector("body_text", "blog__tagline")) works too.

SearchQuery, user input and Lexeme

SearchQuery(value, config=None, search_type="plain") turns text into a tsquery. The search_type values:

search_type Meaning

plain (default)

The terms are separate keywords, all of which must match (after stemming).

phrase

The terms form one phrase, in order.

raw

A tsquery with operators you write, for example "'tomato' & ('red' | 'green')".

websearch

Web-search syntax (quoted phrases, - for exclusion, OR); requires PostgreSQL 11 or newer, so always available now.

Queries combine with &, | and ~. Passing raw user input to the raw type lets a user inject operators; plain and websearch are the safe choices for a search box. Since 6.0, Lexeme(value, output_field=None, *, invert=False, prefix=False, weight=None) makes operators safe with untrusted strings: each lexeme is escaped, and lexemes combine with &, | and ~, with prefix matching and weights.

from django.contrib.postgres.search import Lexeme, SearchQuery

Book.objects.filter(search_vector=SearchQuery("django -flask", search_type="websearch", config="english"))
Book.objects.filter(search_vector=SearchQuery(Lexeme("django") & ~Lexeme("flask"), config="english"))
WHERE "pgdemo_book"."search_vector" @@ (websearch_to_tsquery('english'::regconfig, 'django -flask'))
WHERE "pgdemo_book"."search_vector" @@ (to_tsquery('english'::regconfig, ('django' & !'flask')))

Source: Django: SearchQuery

Compiled only. Lexeme exists from 6.0; on a 5.2 LTS project use plain/websearch and do not build raw queries from user input.

Ranking and headlines

SearchRank(vector, query, weights=None, normalization=None, cover_density=False) scores how well a vector matches: it considers frequency, proximity and the weight of the field in which the term appears. normalization is a bit mask (combine with Value(2).bitor(Value(4))); cover_density=True takes the proximity of terms into account. Weights A, B, C, D default to 1.0, 0.4, 0.2, 0.1; pass weights=[d, c, b, a] to change them. SearchHeadline(expression, query, config=None, start_sel=None, stop_sel=None, max_words=None, min_words=None, short_word=None, highlight_all=None, max_fragments=None, fragment_delimiter=None) returns the text with the matched terms wrapped; the defaults are PostgreSQL’s (<b>, </b>). The result of SearchHeadline is an HTML-looking string built from user-controlled text: if you set start_sel and stop_sel to markup, escape the surrounding text yourself before marking it safe in a template.

from django.contrib.postgres.search import SearchHeadline, SearchQuery, SearchRank
from django.db.models import F, Value

query = SearchQuery("django orm", config="english")
results = (
    Book.objects.filter(search_vector=query)
    .annotate(
        rank=SearchRank(F("search_vector"), query, normalization=Value(2).bitor(Value(4))),
        headline=SearchHeadline("summary", query, config="english", start_sel="<mark>", stop_sel="</mark>"),
    )
    .order_by("-rank")
    .defer("search_vector")
)

                   <options string carrying StartSel and StopSel>) AS "headline"
FROM "pgdemo_book"
WHERE "pgdemo_book"."search_vector" @@ (plainto_tsquery('english'::regconfig, 'django orm'))
ORDER BY 9 DESC

Configurations and weights

config on SearchVector, SearchQuery and SearchHeadline chooses the language parser and dictionaries (config="english"); it can also be an expression such as F("blog__language") so each row is processed in its own language. Vector and query must use the same configuration to match as expected. Weights are set per vector before combining:

vector = SearchVector("title", weight="A", config="english") + SearchVector("summary", weight="B", config="english")
rank = SearchRank(vector, SearchQuery("cheese", config="english"), weights=[0.2, 0.4, 0.6, 0.8])

A stored vector with GeneratedField

Computing to_tsvector for every row on every query is fine for a few hundred rows. The documentation recommends, once you search more than that, either a functional GinIndex(SearchVector(…​)) (the example in PostgreSQL index types; every query must then use the same expression) or a stored column. The stored column is a SearchVectorField. Older code keeps it populated with a trigger; since 5.0 a GeneratedField lets PostgreSQL maintain it, with no trigger and no signal to forget. That is the search_vector field in the models above; the generated DDL is

"search_vector" tsvector GENERATED ALWAYS AS ((setweight(to_tsvector('english'::regconfig, COALESCE("title", '')), 'A')
    || setweight(to_tsvector('english'::regconfig, COALESCE("summary", '')), 'B'))) STORED
CREATE INDEX "book_search_vector_idx" ON "pgdemo_book" USING gin ("search_vector");

Source: Django: Using GeneratedField

The migration was generated and its SQL printed here; the column was not created on a server. What to know:

  • The column is read-only. Do not assign to it; it is recomputed when title or summary change, including through QuerySet.update() and bulk_update().

  • The configuration is part of the generation expression (config="english" above), so one column serves one language; use several columns, or the per-query config expressions described earlier, for several languages.

  • Since 6.0 Django refreshes generated values from the database after save() on PostgreSQL (through RETURNING), so book.search_vector is current right after saving.

  • Adding a generated column to a large existing table rewrites it; plan the migration like any other table rewrite (see Migrations).

  • Since 6.1 GeneratedField supports virtual columns (db_persist=False) on PostgreSQL 18+. A column that a GIN index covers has to be stored, so this page uses db_persist=True; check PostgreSQL’s documentation for the index support of virtual generated columns before choosing otherwise.

  • Searching against the stored column is just Book.objects.filter(search_vector=query), as in the previous examples; the older Book.objects.update(search_vector=SearchVector("body_text")) pattern is for trigger-maintained columns only.

Trigram similarity and unaccent

A trigram is a group of three consecutive characters; two strings are similar when they share many. Trigrams find "Middlesborough" when the row says "Middlesbrough" and suit short strings (names, titles) where users type something close. They need the pg_trgm extension (TrigramExtension() in a migration), and unaccent needs its own (UnaccentExtension()).

Tool Use

name__trigram_similar="…​"

Lookup (%): similarity above the current threshold. On CharField and TextField.

trigram_word_similar (4.0), trigram_strict_word_similar (4.2)

The greatest number of shared trigrams with any substring of the field; the strict variant forces word boundaries.

TrigramSimilarity(expression, string)

Annotation with the similarity (0 to 1) for ordering and thresholds.

TrigramWordSimilarity(string, expression), TrigramStrictWordSimilarity

Word variants; note that the string comes first.

TrigramDistance, TrigramWordDistance, TrigramStrictWordDistance

The complement, for order_by("distance").

nameunaccenticontains="…​"

Accent-insensitive lookup, chainable with other lookups; it generally forces a full table scan.

Sync and async

All of the fields, lookups and expressions above are ordinary query building blocks, so they work with the async ORM (await Book.objects.filter(…​).acount(), async for) exactly as they do synchronously; the compiled SQL is identical, as the portable test showed on SQLite. What differs is the connection model: each async ORM call runs in a thread with the connection of its request, concurrent requests in one process share the connection pool, persistent connections (CONN_MAX_AGE) should be disabled, and transactions do not yet work in async mode. So for an ASGI deployment of Bookshelf: psycopg 3 with "pool" in OPTIONS, CONN_MAX_AGE = 0, a pool sized to the in-flight queries you want, and transactional code kept in a synchronous function called with sync_to_async(). See Introduction & Architecture for where the database sits in the request cycle.

Pitfalls checklist

  • Forgetting the app or the extension. django.contrib.postgres in INSTALLED_APPS for lookups; the extension in a migration for the type or operator class (type "hstore" does not exist, operator class "gin_trgm_ops" does not exist). The extension operation must run before the first thing that needs it.

  • default=[] and default={}. Mutable defaults shared between instances; use list and dict.

  • Typos in hstore lookups become key lookups silently.

  • unaccent and icontains can force full scans; measure before relying on them.

  • A GIN or GiST index that the query cannot use. Plain db_index=True is a B-tree; functional indexes must match the query’s expression; confirm with explain().

  • Checking overlap in Python. Racy; use ExclusionConstraint. And remember it needs btree_gist for scalar columns.

  • CREATE INDEX CONCURRENTLY in an atomic migration fails; set atomic = False and keep the operation alone.

  • AddConstraintNotValid and ValidateConstraint in one migration defeats the purpose.

  • pool without psycopg[pool], with CONN_MAX_AGE other than 0, or with psycopg2.

  • Persistent connections under ASGI, and connections left open by threads or scripts outside the request cycle.

  • Transaction-pooling poolers and iterator(): disable server-side cursors.

  • Explicit primary keys in fixtures or imports without sqlsequencereset afterwards.

  • Searching with different configurations for vector and query, or with raw queries built from user input.

  • Trusting SQLite in tests for PostgreSQL-only features: the code that passes there is the fallback branch, not the feature.

  • StringAgg, ArrayAgg(ordering=…​) and the bit aggregates from django.contrib.postgres.aggregates in new code: deprecated or removed (see below).
