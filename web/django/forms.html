Where a form sits in the request cycle

A form is not part of the framework’s request pipeline: nothing in the URL resolver or the middleware knows about Form. Forms are ordinary Python objects that a view creates, feeds with the request’s data and hands to a template. What the framework does around them is the part that matters: the CSRF middleware inspects the submission before your view starts, the request body is parsed lazily when first read, and the CSRF cookie is attached to the response when a template asked for the token.

sequenceDiagram participant B as Browser participant M as CsrfViewMiddleware participant V as View participant F as Form participant T as Template B->>M: POST /catalog/suggest/ with csrfmiddlewaretoken M->>M: compare cookie secret and posted token (reads request.POST) M->>V: request (view runs only if the token is valid) V->>F: BookSuggestionForm(request.POST) V->>F: is_valid() runs full_clean() alt valid V-->>B: 302 redirect to the success page else invalid V->>T: render with the bound form T-->>B: 200 with errors and submitted values end

In order, for one submission:

  1. The server (WSGI or ASGI) builds the HttpRequest. The body is not parsed yet.

  2. Middleware runs top-down. CsrfViewMiddleware.process_view() is the first code that reads request.POST for a POST without the X-CSRFToken header: it needs the csrfmiddlewaretoken field, so the whole form-encoded or multipart body (files included) is parsed here, before the view and before any form exists. A failed check ends the request with a 403 and your view never runs.

  3. The URL resolver picks the view.

  4. The view decides bound or unbound from the HTTP method, builds the form, calls is_valid() (which triggers full_clean() once and caches the result) and chooses the response.

  5. If the template calls {% csrf_token %}, get_token() marks the request so that process_response() adds the csrftoken cookie and a Vary: Cookie header. That is also why a page containing a form is not safely cacheable by a shared cache.

  6. The browser follows the redirect with a fresh GET (or re-renders the page, for an invalid form).

The middleware chain is explained in Middleware and the whole pipeline in The Request/Response Cycle.

What the browser sends: HTML forms, GET and POST

An HTML <form> has an action (the URL, by default the current page), a method and fields with a name. The browser sends the names and values of the controls it submits, encoded as one of three content types:

  • application/x-www-form-urlencoded (the default) for text fields; Django exposes it as request.POST for POST requests and as request.GET for the query string.

  • multipart/form-data, required when the form contains a file input (enctype="multipart/form-data"); text parts appear in request.POST, file parts in request.FILES.

  • text/plain, which is for debugging and which Django does not parse.

A control that is not submitted is simply absent: an unchecked checkbox, an unselected radio group and a disabled control send nothing. That one rule explains several details below (BooleanField(required=False), disabled=True, value_omitted_from_data()).

The choice of method is a design decision, not a style one. GET is for requests that can be repeated, bookmarked, cached and prefetched without harm: a search, a filter, a pagination link. POST is for requests that change state on the server: suggest a book, upload a file, log in. Django enforces that distinction in two places: the CSRF protection applies to every method that is not GET, HEAD, OPTIONS or TRACE, and the request.POST dictionary is empty for a GET. Do not change state in a GET handler; the books' habit of a "delete" or "add to basket" link that works through GET is wrong because a prefetching browser, a crawler or an image tag on another site can trigger it.

Only form-encoded and multipart bodies fill request.POST. A JSON body, as sent by fetch() with Content-Type: application/json, leaves request.POST empty and has to be parsed by hand (or by Django REST framework or Django Ninja); a Form bound to it would report every field as missing.

A form is a class whose class attributes that are Field instances become its fields, in declaration order. What the run shows, and what to remember:

  • An unbound form is never valid and has no errors. is_valid() is is_bound and not errors. Rendering an unbound form shows initial values and no error messages, which is what you want for the first GET.

  • An empty dict is bound. BookSuggestionForm({}) reports three "required" errors. The common mistake is to write if request.POST: to detect a submission: an empty POST (a form whose controls were all unchecked checkboxes) is falsy and would be treated as a GET. Test request.method == "POST" instead.

  • cleaned_data holds Python values, not strings. pages is an int, published a date, notify_me a bool. This conversion is the reason to validate through a form rather than read request.POST yourself.

  • After a failed is_valid(), cleaned_data contains only the fields that passed. Never read a key that may be missing; use it only after is_valid() returned True (or in clean() with .get()).

  • Initial values are for display only. genre has initial=Genre.FICTION and is absent from changed_data when the submission equals it, but initial is not a fallback: submit genre="" and the field is "required", not "fiction". Initial data can also come from the constructor (initial={"genre": "science"}, which wins over the field’s initial); callables are evaluated each time an unbound form is displayed.

  • changed_data and has_changed() compare submitted data with the initial values. The model formset machinery uses them to skip untouched extra forms; empty_permitted=True lets a form whose data did not change validate as empty.

  • Every field is validated every time. The validation cycle runs once, on the first access to errors, cleaned_data or is_valid(), and the result is cached on the instance; mutating form.data afterwards has no effect.

Two constructor arguments change how the same form object is used in one page. prefix="shelf" renames every control to shelf-name, shelf-capacity, and so makes it possible to put two forms of the same class in one <form> tag or page; the prefix must be passed when reading the data back. auto_id controls the id attributes ("id_%s" by default, False to omit them), and the label suffix and ordering options (label_suffix, field_order, order_fields()) work as their names say.

Fields: validation and conversion

A Field converts and validates one submitted value. Its clean(value) runs to_python() (convert), validate() (field rules, such as "required") and run_validators() (the field’s own and any you pass in validators), and raises ValidationError or returns the cleaned value. You can call it directly, which is the quickest way to learn what a field does: forms.EmailField().clean("not an address") raises ValidationError: ['Enter a valid email address.'].

Three of these deserve a closer look because they are misused constantly.

ChoiceField and its siblings. The choices come from the model-field vocabulary since 5.0, so a TextChoices class can be passed directly (choices=Genre) and no .choices property is needed. A ChoiceField always returns a string; for numbers use TypedChoiceField. Both reject any submitted value that is not among the choices, which is a security property (a tampered <select> cannot smuggle a value in) as well as a validation rule. The ModelChoiceField blank label changed in 6.1: the default blank label of choice fields moved from "---------" to "- Select an option -", defined as django.db.models.fields.BLANK_CHOICE_LABEL, and the transitional setting USE_BLANK_CHOICE_DASH brings the old dash back while it lasts (it is deprecated).

BooleanField. forms.BooleanField() is required by default, so a form with an optional checkbox must say required=False; otherwise every submission without the box ticked fails with "This field is required", which is correct for an "accept the terms" box and wrong for a preference. The cleaned value is a real bool.

DecimalField and DateField. Why each part is the way it is:

  • Three outcomes, one view. GET shows an empty form; an invalid POST shows the same template with the bound form (the user’s input and the errors); a valid POST does its work and redirects. The else branch builds the unbound form, so there is exactly one render() call for both display cases.

  • Redirect after a successful POST (Post/Redirect/Get). If the success page were rendered by the POST itself, a browser refresh would resubmit the form (the "resend form data?" dialog) and create the suggestion twice. A 302 to a GET URL makes refresh harmless and the success page bookmarkable. Use redirect() or HttpResponseRedirect with a named URL through reverse(); never hard-code paths. A 303 See Other is the status that says "fetch this with GET" most precisely; Django’s default 302 is treated as a 303 by every browser for a POST.

  • An invalid form returns status 200. Django’s convention is to re-render with 200, not 400 or 422; browsers show it either way, but many tools treat a 4xx page as a failure. JavaScript clients that need a machine-readable signal use a JSON response, as suggest_api below does with 422.

  • The message survives the redirect. messages.success() stores the text in the session or a cookie, and the next page’s template shows and clears it; see Sessions, Cookies, Messages & Signing.

  • novalidate is a choice. It turns off the browser’s own checks so you see Django’s messages while developing; leave it off in production if you want the browser’s early feedback. Browser checks are a convenience: the server always validates, because a client can send anything.

  • {{ form }} renders the whole form. Since 5.0 it uses the <div>-based template; Rendering a form in a template shows the other ways.

  • Side effects go after is_valid(). Do the work (save, enqueue, send) only with cleaned_data, never with request.POST. Work that must not run if a transaction rolls back belongs in transaction.on_commit(), see Transactions, Raw SQL & Multiple Databases.

The shortcuts and decorators around this pattern (require_POST, require_http_methods, redirect()) are covered in Function-Based Views & Shortcuts, in particular its section on redirects.

CSRF protection and {% csrf_token %}

Cross-site request forgery makes a logged-in person’s browser send a request they did not intend: a hidden form on another site that POSTs to /catalog/suggest/ rides on the session cookie the browser attaches automatically. Django’s defence is the synchroniser token pattern implemented by CsrfViewMiddleware, which is in the default MIDDLEWARE list:

  1. A random secret is stored in the csrftoken cookie (changed at login).

  2. The {% csrf_token %} tag renders <input type="hidden" name="csrfmiddlewaretoken" value="…​">. The value is the secret masked with a fresh random mask on every render (so the HTML differs each time, as a defence against BREACH-style compression attacks).

  3. For every request whose method is not GET, HEAD, OPTIONS or TRACE the middleware requires the cookie and a matching token, from the csrfmiddlewaretoken form field or from the X-CSRFToken header (CSRF_HEADER_NAME).

  4. It also checks the Origin header against the current host and CSRF_TRUSTED_ORIGINS, and, for HTTPS requests with no Origin, the Referer strictly. On failure the response is a 403, produced by the CSRF_FAILURE_VIEW (django.views.csrf.csrf_failure by default) and logged on the django.security.csrf logger.

An attacker’s page can make the browser send the cookie but cannot read it (same-origin policy), so it cannot produce the matching token. The protection assumes HTTPS with HSTS, validated Host headers and no XSS: an XSS hole already gives the attacker everything CSRF would.

Using the tag

<form method="post">
  {% csrf_token %}
  ...
</form>

Rules, from the how-to and the reference:

  • Put {% csrf_token %} inside every <form method="post"> that targets an internal URL.

  • Never put it in a form whose action is an external site: the token would be leaked to that site.

  • The template must be rendered with a RequestContext, which render(), the generic views and the contrib apps already do. If you build the response with Template.render(Context(…​)) and no request, the tag renders nothing and the POST fails with 403.

  • GET forms need no token, and adding one only leaks it into URLs, logs and referrers.

  • In the Jinja2 backend the equivalent is {{ csrf_input }}, which Django adds to the context.

  • The token makes a page Vary: Cookie and sets a cookie, so it interacts with caching; the how-to explains the cache_page/ensure_csrf_cookie combinations (see Security for the whole security picture).

The Client(enforce_csrf_checks=True) tests below prove the rejection and the acceptance paths; the default test client does not enforce CSRF, so an ordinary test with client.post() passes even if the template forgot the tag, and only the curl session (or a test that reads the token from the rendered page and posts it back) proves the template is right.

CSRF settings and decorators

Item Notes

CSRF_COOKIE_NAME, CSRF_COOKIE_AGE, CSRF_COOKIE_DOMAIN, CSRF_COOKIE_PATH

Cookie name (csrftoken), lifetime (one year), and scope. A domain such as .example.com allows cross-subdomain posts.

CSRF_COOKIE_SECURE, CSRF_COOKIE_HTTPONLY, CSRF_COOKIE_SAMESITE

Secure flag (set it with HTTPS), HttpOnly (breaks reading the cookie from JavaScript), SameSite ("Lax" by default).

CSRF_USE_SESSIONS

Store the secret in the session instead of a cookie.

CSRF_HEADER_NAME

The request.META key of the header, "HTTP_X_CSRFTOKEN" by default (the header is X-CSRFToken).

CSRF_TRUSTED_ORIGINS

Origins allowed to post cross-origin or behind a reverse proxy; each entry must include the scheme (https://app.example.com), required since 4.0.

CSRF_FAILURE_VIEW

A function view(request, reason="") that renders the 403 page; use it for a friendly message.

@csrf_protect

Enforces the check on one view; use it only if the middleware is removed, and then on both the view that renders the token and the one that receives the POST.

@csrf_exempt

Turns the check off for a view. Legitimate for a webhook that authenticates in some other way (a signature); never a fix for "my form gives 403".

@requires_csrf_token

Makes {% csrf_token %} work without enforcing the check.

@ensure_csrf_cookie

Forces the cookie to be sent by a view that has no {% csrf_token %}.

What to know about file fields:

  • FileField cleans to an UploadedFile (InMemoryUploadedFile below 2.5 MB, TemporaryUploadedFile above, controlled by FILE_UPLOAD_MAX_MEMORY_SIZE) with name, size, content_type and read()/chunks(). The name is the client’s, reduced to a base name; it is still client data, which is why the view stores it through default_storage and not through open(os.path.join(…​)). The test of the view posts ../../evil.txt and checks that the stored name is excerpts/evil…​ inside MEDIA_ROOT.

  • The validators in the example run in order. Extension and size are cheap and happen before any heavy work. They are not a security check: the extension and content_type are client claims, so serving uploaded files safely is a separate topic (File Uploads & Storage, including multiple files, upload handlers, storage backends and private files).

  • ImageField needs Pillow and opens the image to verify it (invalid_image for a corrupt or fake file), attaching the Pillow object as .image on the cleaned file. Pillow closes the file descriptor after verifying, so non-pixel attributes (width, height, format) remain readable but pixel methods require re-opening the file. Passing validation proves that Pillow can parse the file, not that it is harmless.

  • max_length limits the file name, not the size; allow_empty_file=True accepts a zero-byte file (the default rejects it with the empty code). There is no built-in size limit on the field: use a validator (as above), DATA_UPLOAD_MAX_MEMORY_SIZE (2.5 MB, counts everything in the body except file parts), DATA_UPLOAD_MAX_NUMBER_FILES (100) and DATA_UPLOAD_MAX_NUMBER_FIELDS (1000), and a limit at the reverse proxy.

  • Widgets. ClearableFileInput is the default; when the form has an initial file (an edit form) it shows the current file and a "Clear" checkbox for optional fields. FileInput is the plain control. Neither accepts multiple unless the widget class sets allow_multiple_selected = True (the fix for CVE-2023-31047 in 4.2.1, 4.1.9 and 3.2.19), and a field that validates every file needs a custom FileField subclass as well.

  • Request-cycle position. Because CsrfViewMiddleware reads request.POST for the token, the multipart body (and so the upload) is parsed in the middleware, before the view. The consequence: upload handlers cannot be swapped inside the view on the same request unless the view is exempt from the middleware’s parse and protected by csrf_protect inside, which is described in the file-uploads topic guide.

Sync and async

Forms have no asynchronous API: is_valid(), full_clean(), clean() and every clean_<field>() hook are plain synchronous methods, and there is no ais_valid(). That is harmless in an async def view as long as validation is pure Python, and a bug when it touches the database:

  • A form made of ordinary fields (CharField, ChoiceField, FileField with validators that read bytes) can be validated directly inside an async view; the work is CPU-bound and short. request.POST can also be read in an async view, because the ASGI handler has already buffered the body.

  • ModelChoiceField, ModelMultipleChoiceField, unique checks in a ModelForm, and any clean_<field> hook that runs a query evaluate a queryset in the synchronous API. Called from the event loop, Django raises SynchronousOnlyOperation. Run the whole validation in a thread with sync_to_async() (or asyncio.to_thread()).

Pitfalls

  • Detecting a submission with if request.POST. An empty POST is falsy; use request.method == "POST".

  • Forgetting request.FILES or enctype. The file is silently absent; the field says "This field is required".

  • @csrf_exempt to cure a 403. It removes the protection. Add {% csrf_token %}, render with a request, or fix CSRF_TRUSTED_ORIGINS.

  • {% csrf_token %} in a form with an external action. It leaks the token to that site.

  • Rendering the success page from the POST. Refresh resubmits; redirect (Post/Redirect/Get).

  • Changing state in a GET view. CSRF does not protect GET; browsers prefetch and crawlers follow links.

  • Reading request.POST[…​] instead of cleaned_data. You skip validation, conversion and normalisation.

  • Reading cleaned_data after a failed is_valid(). Keys of failed fields are missing.

  • BooleanField without required=False. The checkbox becomes mandatory.

  • Believing initial is a default. It is only for display; a missing value fails "required".

  • Treating HiddenInput or readonly as trusted. Use disabled=True and validate on the server; a hidden control is user input.

  • Passing request.POST to a form behind a JSON API. A JSON body leaves request.POST empty.

  • Mutating the class-level fields at request time. Change self.fields in __init__.

  • Dynamic choices computed at import time. choices=[…​ for x in Model.objects.all()] in the class body runs a query at import time and freezes the list; pass a callable, use a ModelChoiceField, or set the choices in __init__.

  • Mixing a validation concern into the template. Show form.errors, non_field_errors and each field’s errors, or users will not see why the page came back.

  • fields = "all" and exclude in model forms. Mass assignment: always list the fields explicitly (see Model Forms & Formsets).

  • Trusting the browser’s required and maxlength. They are hints; every rule must also exist on the server.

  • Validating a ModelChoiceField form in an async view without sync_to_async(). SynchronousOnlyOperation.

Where the books are outdated

The four reference books target Django 1.11 to 2.1 (2017-2018); the concepts they teach for forms are still right (declare fields, bind, validate, redirect), but a good deal of the surrounding code has moved on:

  • Manual field-by-field rendering loops. Hand-written {% for field in form %} blocks printing the label, the errors and the widget, and {{ form.as_table }} wrapped in <table>, were the norm. Forms render through templates since 4.0, as_div arrived in 4.1 and became the default for {{ form }} in 5.0, and as_field_group (5.0) renders one field with its label, help text and errors in one call.

  • Hand-written CSRF exemption for AJAX. Books that add a CsrfExemptMixin or @csrf_exempt to make a JavaScript POST work are wrong; the documented answer is the X-CSRFToken header (JavaScript and fetch).

  • CSRF_TRUSTED_ORIGINS without a scheme. Entries must include https:// since 4.0; the old bare host names make the system check fail.

  • ugettext/ugettext_lazy for labels and error messages. Removed in 4.0; use gettext_lazy.

  • url() in form action reverse examples. django.conf.urls.url() was removed in 4.0; use path()/re_path().

  • assertFormError(response, "form", "field", message). The signature was deprecated in 4.1 and removed in 5.0; pass the form (response.context["form"]).

  • attrs={"multiple": True} on file inputs. Raises ValueError since 4.2.1 (4.1.9, 3.2.19); see File fields.

  • URLField defaulting to http. The default scheme for a value typed without one changed to https in 6.0 (the assume_scheme argument came in 5.0, and the FORMS_URLFIELD_ASSUME_HTTPS transitional setting is gone).

  • ModelChoiceField blank label ---------. It is - Select an option - in 6.1.

  • Choices as a hand-built list of tuples only. ChoiceField also accepts an enumeration, a mapping or a callable (5.0), which is much tidier with TextChoices (3.0).

  • render_to_response() (removed 3.0) and request.REQUEST (long gone) in form views; use render() and request.POST or request.GET.

  • django.shortcuts.render_to_response and ModelForm without Meta.fields. The latter has raised ImproperlyConfigured since 1.8; the books' habit of fields = "all" still works and is a security flaw (mass assignment).

  • jQuery date pickers and Bootstrap 3/4 markup. Today <input type="date"> (via DateInput(attrs={"type": "date"})) and the framework of your choice (see the crispy-forms discussion in the rendering page) replace them.

What changed recently

Version Change

4.0

Forms (and formsets and error lists) render through the template engine; CSRF_TRUSTED_ORIGINS entries need a scheme; django.conf.urls.url() removed; DeleteView uses FormMixin (a form can confirm deletion).

4.1

as_div() and div.html; FORM_RENDERER classes get form_template_name; legend_tag() and use_fieldset; new assertFormError() signature that takes a form; DATA_UPLOAD_MAX_NUMBER_FILES (4.1.7).

4.2

ModelForm accepts Meta.formfield_callback; the multiple-file widget guard (4.2.1).

5.0

{{ form }} renders as <div> by default; field groups (as_field_group()); aria-describedby and aria-invalid on fields; URLField(assume_scheme=…​); ChoiceField.choices accepts enumerations, mappings and callables; old assertFormError() signature removed; the transitional div renderers deprecated.

5.1

The form fieldset gets an aria-describedby that points at its help text; {% querystring %} for GET forms and pagination.

5.2

bound_field_class (form and field level) replaces the custom-get_bound_field() workaround; ColorInput, SearchInput, TelInput; the aria_describedby property on BoundField; error lists get an id through field_id; Script assets in form media.

6.0

URLField assumes https; the transitional DjangoDivFormRenderer/Jinja2DivFormRenderer removed.

6.1

FilePathField.set_choices(); BLANK_CHOICE_LABEL and the new default blank label (USE_BLANK_CHOICE_DASH brings back the old one, deprecated); Stylesheet assets in form media; RedirectView.preserve_request (307/308 redirects that keep method and body).
