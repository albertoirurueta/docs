Query Optimization & Fetch Modes

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Django 6.1 (6.1.1, released 2026-09-02; 6.1.2 is scheduled for 2026-10-06) on Python 3.12 to 3.14, with PostgreSQL 15 or later as the production database and the 5.2 LTS differences noted where they matter, and was checked on 2026-10-03. The examples ran on Django 6.1.1 and Python 3.13 with SQLite in a throw-away project containing the Bookshelf catalogue models of this section (Author, Genre, Book, Review); 29 tests pass, the pages were rendered through runserver and curl, and the Debug Toolbar settings passed manage.py check and served its panels. There was no PostgreSQL server in that project, so the connection-pool and PostgreSQL-specific parts are only configuration that passed manage.py check; each of them says so where it appears.

An ORM makes it easy to write code that is correct and slow: every attribute access that crosses a relationship can silently become a query. The cure is a habit rather than a trick: measure the queries a page issues, fetch related data in bulk instead of one row at a time, load only the columns you need, and keep the number of statements per request constant instead of proportional to the data. This page covers the N+1 problem and the two classic tools against it (select_related and prefetch_related), the fetch modes added in Django 6.1 that fix most N+1 patterns automatically or forbid them outright, deferring columns, streaming large result sets, reading query plans with explain(), hooking every statement with database instrumentation, connection persistence and pooling, and the Django Debug Toolbar. For the vendor-neutral workflow that takes you from "this feels slow" to a confirmed root cause, see Diagnosing and Fixing Slow Queries.

The N+1 problem

A query is lazy and so are related objects: book.author does not exist on the instance until you touch it, and then Django runs a query to fetch it. Looping over N books and printing each author therefore costs one query for the list plus one query per book, which is where "N+1" comes from. With 12 books that is 13 queries; with 12,000 it is 12,001, each with its own round trip to the database.

The examples that follow use these models.

# catalog/models.py
from django.db import models


class Author(models.Model):
    name = models.CharField(max_length=200)

    def __str__(self) -> str:
        return self.name


class Genre(models.Model):
    name = models.CharField(max_length=100, unique=True)

    def __str__(self) -> str:
        return self.name


class Book(models.Model):
    title = models.CharField(max_length=300)
    author = models.ForeignKey(Author, on_delete=models.CASCADE, related_name="books")
    genres = models.ManyToManyField(Genre, related_name="books", blank=True)
    summary = models.TextField(blank=True)
    published = models.DateField(null=True, blank=True)

    class Meta:
        ordering = ["title"]

    def __str__(self) -> str:
        return self.title


class Review(models.Model):
    book = models.ForeignKey(Book, on_delete=models.CASCADE, related_name="reviews")
    rating = models.PositiveSmallIntegerField()
    body = models.TextField(blank=True)

    def __str__(self) -> str:
        return f"{self.book_id}: {self.rating}"

from .models import Book


def books_with_authors():
    # N+1: every book.author access below costs one query.
    return [(book.title, book.author.name) for book in Book.objects.all()]

Where this sits in the request cycle

Queries are issued wherever a QuerySet is evaluated or a lazy attribute is accessed, and that is often not the view. A view that returns a Book queryset to a template can trigger N+1 inside the template when it writes {{ book.author.name }}, because the template engine calls attributes for you and its syntax hides the cost. So the budget has to be enforced where the data is consumed: in the view that builds the context, in serializers when you use Django REST Framework, and in tests. The usual place to fix a query problem is the view (or a manager method it calls) that builds the QuerySet, not the template that consumes it. A QuerySet is only evaluated when you iterate it, slice it with a step, call len(), list(), bool() or repr() on it, or call a method such as get() or count(); see Making Queries.

Django also caches in two places and understanding both avoids unnecessary work. A QuerySet caches its results once evaluated, so iterating the same variable twice costs one query. And attributes on model instances are cached: after entry.blog is fetched once, the next entry.blog is free, while callable attributes such as entry.authors.all() run a query every time. The template system calls callables automatically, so be careful reading template code, and for your own expensive properties use functools.cached_property.

Source: Database access optimization.

select_related: one JOIN for single-valued relations

select_related() follows foreign-key and one-to-one relationships and fetches the related row in the same SQL statement, using a JOIN. It works for forward relationships and for the reverse side of a OneToOneField, but not for many-valued relations (reverse foreign keys and many-to-many), which cannot be flattened into one row per object. It is the right default for "the author of each book".

# catalog/services.py
def books_with_authors_joined():
    books = Book.objects.select_related("author")
    return [(book.title, book.author.name) for book in books]
# catalog/tests.py (excerpt)
def test_select_related(self):
    with self.assertNumQueries(1):
        books_with_authors_joined()

Source: QuerySet.select_related().

The behaviour you need to know:

  • Chain relationships with the double-underscore syntax, for example select_related("book__author") for a Review queryset, to join several levels in one statement.

  • Calling select_related() with no arguments follows every non-null foreign key; avoid it, because the join list then grows silently as the model grows, and it is deprecated since Django 6.1. Name the fields.

  • Several calls add to the list of relations, and select_related(None) clears it. A foreign key with null=True is followed with a LEFT OUTER JOIN, so rows without a related object are still returned.

  • It combines with only() and defer(), for example select_related("author").only("title", "author__name"), to also trim the joined columns.

  • The result is one wide row per book, so it is a poor fit when a parent repeats thousands of times with large columns; measure.

Since Django 6.1, select_related() also matters for fetch modes: a relation that was joined is already loaded, so no fetch happens for it whatever the mode (see Fetch modes (Django 6.1)).

prefetch_related and Prefetch: one extra query per relation

prefetch_related() handles the relations select_related() cannot: many-to-many, reverse foreign keys, and generic relations. It runs one additional query per lookup, using WHERE id IN (…​) with the primary keys of the first query’s results, and then joins the rows to their parents in Python. Two queries instead of N+1, regardless of N.

# catalog/services.py
def books_with_reviews_prefetched():
    books = Book.objects.select_related("author").prefetch_related("genres", "reviews")
    return [
        (book.title, [g.name for g in book.genres.all()], [r.rating for r in book.reviews.all()])
        for book in books
    ]
# catalog/tests.py (excerpt)

Customising a prefetch with Prefetch objects

A Prefetch(lookup, queryset=None, to_attr=None) object lets you control the query behind a lookup, for example to filter or order the related rows, to select_related further objects, or to store the result in a separate attribute so that the plain relation manager stays untouched.

# catalog/services.py
from django.db import models

from .models import Book, Review


def best_reviews_per_book():
    best = Review.objects.filter(rating__gte=4).order_by("-rating")
    return Book.objects.prefetch_related(
        models.Prefetch("reviews", queryset=best, to_attr="best_reviews")
    )
# catalog/tests.py (excerpt)

Pitfalls of prefetching

  • Filtering a prefetched relation discards the cache. book.reviews.filter(rating__gte=4) builds a new query and ignores what was prefetched, so a loop over prefetched books that calls .filter() or .order_by() on the relation is N+1 again (.all() and a plain .count() reuse the prefetched rows). Do the filtering in the Prefetch queryset, or in Python over .all(). In the scratch project three prefetched books plus a .filter(…​).count() per book cost three extra queries, five in total.

  • Prefetching does not help single-object lookups. For a single instance the join in select_related is cheaper; prefetch pays off when several parents share each query.

  • Large IN lists. The second query lists every parent id. On SQLite and Oracle the number of terms in an IN clause is limited; with iterator() pass a chunk_size small enough for that limit (see Streaming large results with iterator()).

  • Related-object access uses the base manager. When Django follows a relation it uses the model’s base manager rather than the default manager, so custom filtering in a default manager does not apply to prefetched objects. Keep this in mind when you put select_related or prefetch_related in a manager (see Managers & Custom QuerySets).

  • Choose by shape. Use select_related for forward foreign keys and one-to-one (a join), prefetch_related for the many side. Two many-valued joins in one statement would multiply the rows, which is why Django fetches those relations with separate queries instead.

Fetch modes (Django 6.1)

Django 6.1 added fetch modes: a per-QuerySet setting that decides what happens when you touch a field that was not loaded by the original query. Before 6.1 the only behaviour was "fetch it for this one instance", which is what produces N+1; now you can choose to fetch it for the whole batch, or to forbid the fetch. The mode applies to ForeignKey fields, OneToOneField fields and their reverse accessors, fields deferred with defer() or only(), and generic relations. It does not change the queries of related managers such as author.books.all(); the mode is merely copied onto the objects those managers fetch. A fetch mode is set with QuerySet.fetch_mode(); the three modes live in django.db.models.fetch_modes and are re-exported from django.db.models, so the convention is from django.db import models and models.FETCH_PEERS.

Forbidding lazy loading with FETCH_RAISE

FETCH_RAISE turns an accidental query into an error, which is what you want in a performance-critical view, a serializer or a test: if a relation is touched that you did not load explicitly, the code fails immediately instead of degrading quietly. Relations you did load, with select_related or prefetch_related, still work.

from django.core.exceptions import FieldFetchBlocked
from django.db import models

book = Book.objects.fetch_mode(models.FETCH_RAISE).first()
try:
    book.author
except FieldFetchBlocked as exc:
    print(exc)  # Fetching of Book.author blocked.

# Loaded explicitly, so allowed:
book = Book.objects.fetch_mode(models.FETCH_RAISE).select_related("author").first()
print(book.author.name)

Source: Fetch modes.

Fetch modes spread along the object tree

Django copies the fetch mode of an instance to the related objects it fetches, so the mode applies to a whole tree of relationships, not just the top-level model. If a book is loaded with FETCH_PEERS, the author object fetched through book.author carries FETCH_PEERS too, and so on down the chain. The copy is also made by related managers, although the mode does not change the queries that those managers themselves run.

book = Book.objects.fetch_mode(models.FETCH_PEERS).first()
assert book.author._state.fetch_mode is models.FETCH_PEERS

author = Author.objects.fetch_mode(models.FETCH_PEERS).first()
list(author.books.all())  # a normal single query; the manager ignores the mode

Source: Fetch modes.

Making a fetch mode the default for a model

The mode is set per QuerySet, so to apply it to every query of a model, override get_queryset() in a custom manager. The official guidance says to prefer FETCH_PEERS over select_related/prefetch_related when it is hard to predict which fields will be accessed, and to use select_related/prefetch_related when FETCH_PEERS is not appropriate or not efficient enough.

from django.db import models


class BookManager(models.Manager):
    def get_queryset(self):
        return super().get_queryset().fetch_mode(models.FETCH_PEERS)


class Book(models.Model):
    title = models.CharField(max_length=300)
    author = models.ForeignKey("Author", on_delete=models.CASCADE)

    objects = BookManager()

Sync and async behaviour of lazy fetches

A lazy foreign-key access performs a synchronous query, so doing it from async code raises SynchronousOnlyOperation; in the scratch project book.author inside an async def after await Book.objects.afirst() was blocked. Loading fewer columns: only, defer and values

Columns have a cost too: large TextField values, JSON documents and computed columns are transferred and converted into Python objects whether you use them or not.

  • only("title", "author") loads just the named fields (plus the primary key) and defers everything else.

  • defer("summary") loads everything except the named fields.

  • values() and values_list() skip model instances altogether and return dictionaries or tuples, useful for read-only listings and for feeding templates or JSON output.

books = list(Book.objects.only("title"))      # 1 query, no summary/published/author_id
for book in books:
    book.summary                               # deferred: 1 extra query per book

rows = Book.objects.values_list("title", "author__name")   # one JOIN, no model instances
print(Book.objects.defer("summary").first().get_deferred_fields())   # {'summary'}

Source: QuerySet.only(), QuerySet.defer() and QuerySet.values().

The official guide warns that accessing a deferred field makes a separate query, so deferring a column you end up needing is a pessimisation: only defer large text data or fields expensive to convert, and profile first. The database must read most non-text data from disk for a row whatever columns you ask for, so deferring many small columns rarely pays. With FETCH_PEERS a deferred field is loaded for the whole batch on first access, which softens (but does not remove) the penalty of a mistake.

Streaming large results with iterator()

A QuerySet caches every row it has loaded, which is what makes a second iteration free but also means that a million-row export holds a million objects. iterator(chunk_size=None) evaluates the query and returns a generator without any QuerySet-level caching, so memory stays flat when each object is processed once. The asynchronous twin is aiterator().

for review in Review.objects.filter(rating__gte=4).iterator(chunk_size=2000):
    total += review.rating

Points to remember:

  • Since Django 4.1, iterator() supports prefetch_related() as long as chunk_size is given; before 4.1 no prefetching happened at all. The prefetch queries then run once per chunk, as the test above shows. Without chunk_size, current Django raises ValueError ("chunk_size must be provided when using QuerySet.iterator() after prefetch_related()", observed on 6.1.1).

  • When no prefetching is involved, omitting chunk_size uses an implicit default of 2000.

  • On PostgreSQL and Oracle, iterator() uses server-side cursors that stream from the database; chunk_size is then the number of rows cached by the driver. MySQL cannot stream, so the driver loads the whole result set anyway. On SQLite results come in batches via fetchmany(), but be careful writing to the table being iterated.

  • Behind a transaction-pooling proxy such as PgBouncer, server-side cursors fail because a later transaction may be served by a different connection; set DISABLE_SERVER_SIDE_CURSORS to True for that database.

  • Calling iterator() on an already evaluated QuerySet runs the query again.

Database instrumentation

connection.execute_wrapper(wrapper) returns a context manager that installs a wrapper around every query execution on the current thread’s connection, then removes it. Wrappers resemble middleware: each receives execute (the next callable), sql, params, many (whether it is executemany()) and context (a dictionary with the connection and cursor), and must call execute(sql, params, many, context) and return its result. They can count, time, log or block queries, and they only live inside the with block, so they are specific to one flow.

# catalog/querylog.py
import time
from contextlib import contextmanager

from django.db import connection


class QueryLogger:
    """Database wrapper that records every statement and its duration."""

    def __init__(self) -> None:
        self.queries: list[dict] = []

    def __call__(self, execute, sql, params, many, context):
        entry = {"sql": sql, "params": params, "many": many}
        start = time.monotonic()
        try:
            result = execute(sql, params, many, context)
        except Exception as exc:
            entry["status"] = "error"
            entry["exception"] = exc
            raise
        else:
            entry["status"] = "ok"
            return result
        finally:
            entry["duration"] = time.monotonic() - start
            self.queries.append(entry)


def blocker(execute, sql, params, many, context):
    alias = context["connection"].alias
    raise RuntimeError(f"Access to database '{alias}' blocked here")


@contextmanager
def log_queries():
    logger = QueryLogger()
    with connection.execute_wrapper(logger):
        yield logger

Connection management

Opening a database connection is slow, much more so over TLS or to a remote server, so how connections live matters as much as how many statements run.

Persistent connections: CONN_MAX_AGE and CONN_HEALTH_CHECKS

By default Django closes the connection at the end of every request (CONN_MAX_AGE = 0). A positive number of seconds keeps it open for reuse by later requests handled by the same thread, and None keeps it forever. At the start and end of each request Django closes connections that have reached their maximum age or that are unusable. Setting CONN_HEALTH_CHECKS to True (Django 4.1) makes Django verify a persistent connection before reusing it, once per request and only when the request accesses the database, which avoids errors after the server closed an idle connection or restarted.

# settings.py (excerpt)
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": "bookshelf",
        "CONN_MAX_AGE": 60,          # keep a connection for up to 60 seconds
        "CONN_HEALTH_CHECKS": True,  # Django 4.1+: validate before reuse
    }
}

Source: Persistent database connections and CONN_MAX_AGE.

The caveats from the official page matter. Each thread keeps its own connection, so the database must allow at least as many connections as you have worker threads. The development server creates a new thread for every request, which negates persistence, so do not enable it in development. When you change connection parameters such as the isolation level or time zone, persistent connections keep the change across requests unless you reset it. And in a long-running process outside the request cycle (a script, a worker, a thread of your own) a connection stays open until you close it, and django.db.close_old_connections() closes the old or unusable ones. Most importantly, the documentation states that persistent connections should be disabled under ASGI: use the database backend’s own pooling instead.

PostgreSQL connection pools (Django 5.1)

Since Django 5.1 the PostgreSQL backend can use a connection pool provided by psycopg_pool. Pools reuse connections across threads, and Django keeps a separate pool per database alias in each process; closing a Django connection returns it to the pool. Pooling requires psycopg 3 with the pool extra (pip install "psycopg[pool]"). Enable it with the "pool" key in OPTIONS, either True for the defaults or a dictionary of ConnectionPool arguments. CONN_MAX_AGE must be 0 when a pool is enabled; control lifetime with the pool’s max_lifetime option instead. Unless you pass a check callback in the pool options, CONN_HEALTH_CHECKS decides whether connections are checked as they are taken from the pool.

# config/settings_pg.py
import os

from .settings import *  # noqa: F401,F403

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": os.environ.get("DB_NAME", "bookshelf"),
        "USER": os.environ.get("DB_USER", "bookshelf"),
        "PASSWORD": os.environ["DB_PASSWORD"],
        "HOST": os.environ.get("DB_HOST", "localhost"),
        "PORT": os.environ.get("DB_PORT", "5432"),
        "CONN_MAX_AGE": 0,           # must stay 0 with a pool
        "CONN_HEALTH_CHECKS": True,  # validate connections taken from the pool
        "OPTIONS": {
            "pool": {"min_size": 2, "max_size": 10, "timeout": 10},
        },
    }
}

Source: Connection pool and Django 5.1 release notes.

This settings module passed python manage.py check --settings=config.settings_pg in the scratch project, which does not open a connection; the pool itself was not exercised, because there was no PostgreSQL server and psycopg_pool was not installed there. Treat the pool sizes as starting values to tune against max_connections on the server and the number of worker processes: with p processes each holding a pool of up to max_size connections, the database sees up to p * max_size connections. The password is read from the environment and never written in the settings file.

Django Debug Toolbar

The Django Debug Toolbar is a third-party package (8.0.0 on PyPI on 2026-10-03, classified for Django 5.2, 6.0 and 6.1) that adds a side panel to HTML pages in development. Its SQL panel lists every query of the request with its time, flags duplicate and similar queries (the signature of N+1), shows the stack trace that issued each query, and lets you run EXPLAIN on a statement. Its other panels cover timing, templates, cache calls, signals and settings. Install it as a development dependency only.

pip install django-debug-toolbar
# config/settings_dev.py
from .settings import *  # noqa: F401,F403

INSTALLED_APPS += ["debug_toolbar"]
MIDDLEWARE.insert(0, "debug_toolbar.middleware.DebugToolbarMiddleware")
INTERNAL_IPS = ["127.0.0.1"]
# config/urls.py
from django.conf import settings
from django.contrib import admin
from django.urls import include, path

from catalog.views import book_list

urlpatterns = [
    path("admin/", admin.site.urls),
    path("books/", book_list, name="book-list"),
]

if settings.DEBUG and "debug_toolbar" in settings.INSTALLED_APPS:
    urlpatterns += [path("__debug__/", include("debug_toolbar.urls"))]

Source: Debug Toolbar installation and Debug Toolbar panels.

With this configuration check passes, and a request to /books/ returned a page containing the toolbar’s djDebug markup and the /debug/ panel endpoints; the toolbar only appears when DEBUG is True, the request comes from an address in INTERNAL_IPS, and the response is HTML. Pitfalls: put the middleware as early as possible but after any middleware that encodes the response (such as GZipMiddleware), never enable the toolbar in production, and remember that it measures a single request, so use assertNumQueries to keep what it taught you from regressing. The older toolbar recipes that registered the URL with url(r'^debug/', include(debug_toolbar.urls)) and listed the middleware in MIDDLEWARE_CLASSES no longer work: url() was removed in Django 4.0 and MIDDLEWARE_CLASSES in Django 2.0.

Where the books are outdated

The four books this section consults were written for Django 1.11 to 5.x and predate several of the tools on this page, so check what they tell you against the current documentation.

  • Fetch modes do not exist in them: they describe select_related and prefetch_related as the only remedies for N+1, and treat lazy loading as unavoidable and unobservable. In Django 6.1 you can batch it (FETCH_PEERS) or forbid it (FETCH_RAISE).

  • Older books rely on connection.queries and the Debug Toolbar to count queries. Both still work, but assertNumQueries, CaptureQueriesContext and connection.execute_wrapper() let you enforce a budget in tests and in production code.

  • Debug Toolbar setup in older books uses MIDDLEWARE_CLASSES (removed in Django 2.0) and the url() helper (removed in Django 4.0); current setup is the MIDDLEWARE list and path() with include("debug_toolbar.urls") as shown above.

  • Connection handling: CONN_MAX_AGE is described without CONN_HEALTH_CHECKS (4.1), without pools (5.1) and without the ASGI warning. Driver advice also moved on: psycopg 3 is supported since Django 4.2 and is the recommended driver.

  • Large exports that use iterator() in older books cannot combine it with prefetch_related(); since Django 4.1 they can, with chunk_size.

  • Composite indexes: index_together, used for composite indexes in older books, was removed in Django 5.1; use Meta.indexes (see Constraints, Indexes & Composite Keys).

Pitfalls checklist

  • Count queries in tests with assertNumQueries for every list page; a loop over related objects that "works" locally with five rows is the usual N+1.

  • The template engine hides queries: {{ book.author.name }} inside a loop is a query per row unless the view loaded the author.

  • Calling .filter() or .order_by() on a prefetched relation throws the prefetch away; .all() and .count() reuse it.

  • only()/defer() followed by access to a deferred field is slower than loading everything; defer big columns, not small ones.

  • select_related() without arguments follows every non-null foreign key and is deprecated since Django 6.1; name the fields.

  • FETCH_PEERS is a safety net, not a plan: it costs one query per relation touched; select_related costs none extra.

  • iterator() after prefetch_related() raises ValueError unless you pass chunk_size; it also bypasses the result cache, so repeated use repeats the query; behind PgBouncer in transaction mode disable server-side cursors.

  • Under ASGI keep CONN_MAX_AGE at 0, because persistent connections are not reused safely there; combining CONN_MAX_AGE above 0 with OPTIONS["pool"] raises ImproperlyConfigured.

  • explain(analyze=True) runs the statement; never point it at data you cannot afford to modify.

  • Never leave the Debug Toolbar, DEBUG = True or query logging of params on in production.
