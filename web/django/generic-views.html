The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Django 6.1 (6.1.1 on PyPI; 6.1.2 is scheduled for 2026-10-06), Python 3.12-3.14 and PostgreSQL 15+, checked on 2026-10-03; where Django 5.2 LTS behaves differently the text says so. Nothing on this page needs PostgreSQL or Redis: the listings were run in a scratch project on Python 3.13.16 and Django 6.1.1 with SQLite. manage.py check is clean, the 38 tests shown in Running the examples pass (manage.py test catalog), a curl session against runserver returned the responses shown, and the shell scripts printed the output quoted below.

Generic views are the ready-made class-based views in django.views.generic: they implement the handful of patterns that account for most pages of a database-backed site — show a list of objects, show one object, show a form, create, change or delete an object, and browse objects by date. You configure them with class attributes and customise them by overriding small methods, and they are built from small mixins that you can recombine. The base machinery (View, as_view(), dispatch(), setup(), TemplateView, how the method resolution order works) belongs to Class-Based Views, the page before this one; this page assumes it and concentrates on what the generic views add. Models and fields are covered on Models & Fields, filtering and ordering on Making Queries, and avoiding the N+1 problem in list templates on Query Optimization & Fetch Modes. Forms, templates, authentication and testing have their own pages later in the section; here they appear only as far as the views need them.

The Bookshelf catalog app used on this page

Every example belongs to one small app, catalog, of the running Bookshelf scenario: authors, books and reader reviews. The app is registered in INSTALLED_APPS, its URLs are included under catalog/ in the project’s urls.py (path("catalog/", include("catalog.urls"))), and the project keeps Django’s defaults for everything else (SQLite, the messages and session middleware, LOGIN_URL = "/accounts/login/"). The models are deliberately small, but three details matter later:

  • Book.Meta.ordering is set, because paginating an unordered QuerySet gives unstable pages (see Pagination).

  • Book.published is a DateField, not a DateTimeField, which is what the date-based views want (see Date-based views).

  • Review belongs to a user (reviewer) and has a UniqueConstraint, which is what makes it the right model for queryset scoping to request.user (see Scoping querysets to request.user).

from django.conf import settings
from django.core.validators import MaxValueValidator, MinValueValidator
from django.db import models
from django.urls import reverse


class Author(models.Model):
    name = models.CharField(max_length=200)
    slug = models.SlugField(unique=True)

    def __str__(self):
        return self.name

    def get_absolute_url(self):
        return reverse("catalog:author-books", kwargs={"slug": self.slug})


class Book(models.Model):
    title = models.CharField(max_length=200)
    slug = models.SlugField(unique=True)
    isbn = models.CharField(max_length=13, unique=True)
    author = models.ForeignKey(Author, on_delete=models.PROTECT, related_name="books")
    price = models.DecimalField(max_digits=6, decimal_places=2)
    published = models.DateField()
    is_published = models.BooleanField(default=True)
    views = models.PositiveIntegerField(default=0)

    class Meta:
        ordering = ["-published", "title"]

    def __str__(self):
        return self.title

    def get_absolute_url(self):
        return reverse("catalog:book-detail", kwargs={"slug": self.slug})


class Review(models.Model):
    book = models.ForeignKey(Book, on_delete=models.CASCADE, related_name="reviews")
    reviewer = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE)
    rating = models.PositiveSmallIntegerField(
        validators=[MinValueValidator(1), MaxValueValidator(5)]
    )
    body = models.TextField(blank=True)
    created = models.DateTimeField(auto_now_add=True)

    class Meta:
        ordering = ["-created"]
        constraints = [
            models.UniqueConstraint(
                fields=["book", "reviewer"], name="one_review_per_reader_and_book"
            )
        ]

    def __str__(self):
        return f"{self.book} ({self.rating}/5)"

    def get_absolute_url(self):
        return reverse("catalog:book-detail", kwargs={"slug": self.book.slug})

Each model has a get_absolute_url(). The editing views use it to find where to redirect after a successful save, so defining it once on the model saves a success_url per view.

The forms are one plain form (SuggestionForm, for FormView), one ModelForm that receives the book and the reviewer so it can reject a second review of the same book as an ordinary form error (ReviewForm), and a one-checkbox form that makes DeleteView ask for confirmation (ConfirmDeleteForm):

from django import forms
from django.core.exceptions import ValidationError
from django.core.mail import send_mail

from .models import Review


class SuggestionForm(forms.Form):
    title = forms.CharField(max_length=200)
    author_name = forms.CharField(max_length=200)
    reason = forms.CharField(widget=forms.Textarea, required=False)

    def send_email(self, suggested_by):
        send_mail(
            subject=f"Book suggestion: {self.cleaned_data['title']}",
            message=(
                f"{suggested_by} suggests {self.cleaned_data['title']} "
                f"by {self.cleaned_data['author_name']}.\n\n"
                f"{self.cleaned_data['reason']}"
            ),
            from_email=None,  # DEFAULT_FROM_EMAIL
            recipient_list=["curators@example.com"],
        )


class ReviewForm(forms.ModelForm):
    class Meta:
        model = Review
        fields = ["rating", "body"]
        widgets = {"body": forms.Textarea(attrs={"rows": 4})}

    def __init__(self, *args, book, reviewer, **kwargs):
        super().__init__(*args, **kwargs)
        self.book = book
        self.reviewer = reviewer

    def clean(self):
        cleaned_data = super().clean()
        duplicates = Review.objects.filter(
            book=self.book, reviewer=self.reviewer
        ).exclude(pk=self.instance.pk)
        if duplicates.exists():
            raise ValidationError("You have already reviewed this book.")
        return cleaned_data


class ConfirmDeleteForm(forms.Form):

Four consequences follow from this picture and explain most generic-view questions:

  • A view instance lives for one request. as_view() returns a function that builds a fresh instance each time, so assigning to self inside a method (self.author = …​, self.object = …​) is safe and is the idiomatic way to pass data between hooks. Class attributes, by contrast, are shared by every request and every thread; never mutate them (see the queryset warning in Single-object mixins: SingleObjectMixin and SingleObjectTemplateResponseMixin).

  • setup() runs before dispatch(). Since Django 2.2 View.setup() stores request, args and kwargs on the instance (and makes head an alias of get). A mixin that needs per-request attributes can override setup() and be sure they exist in every handler. Raising Http404 there happens before an access mixin’s dispatch() check, which is why this page looks things up lazily instead (see the book property in Editing views: FormView, CreateView, UpdateView and DeleteView).

  • The response is a TemplateResponse. render_to_response() does not render the template; it returns a response that is rendered later, after the view has returned. Middleware with process_template_response() can still change template_name or context_data of a generic view’s response. That is also why a QuerySet used in the template is evaluated after the view returns.

  • Access mixins run in dispatch(). LoginRequiredMixin, PermissionRequiredMixin and UserPassesTestMixin override dispatch(); for an anonymous user the handler, get_queryset() and get_object() never run (the tests in Scoping querysets to request.user assert exactly that).

    """Return a subclass that records the order in which the named hooks run."""
    namespace = {}

            def hook(self, *args, **kwargs):
                calls.append(name)
                return getattr(super(subclass, self), name)(*args, **kwargs)
            return hook
        namespace[name] = make(name)
    subclass = type("Traced" + view_class.__name__, (view_class,), namespace)
    return subclass

class BookListView(ListView):
    queryset = PUBLISHED  # a class attribute: get_queryset() clones it for every request
    paginate_by = 3
    context_object_name = "books"  # in addition to the default object_list

    def get_queryset(self):
        queryset = super().get_queryset()
        q = self.request.GET.get("q", "").strip()
        if q:

        return queryset

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context["q"] = self.request.GET.get("q", "").strip()
        return context

DetailView, lookups and "extra work"

DetailView fetches one object. It reads the pk keyword argument of the URL pattern, or, when that is absent, the slug keyword argument, and looks it up in get_queryset(); if neither argument is in the URLconf it raises an AttributeError that says so (see Pitfalls and the error messages they produce), and if no row matches it raises Http404. The names are configurable (pk_url_kwarg, slug_url_kwarg, slug_field), so a route such as books/<slug:slug>/ needs no code at all:

catalog/views.py — BookDetailView
class BookDetailView(DetailView):
    queryset = PUBLISHED.prefetch_related("reviews__reviewer")
    # DetailView looks the object up by the URL keyword argument "slug"
    # (slug_url_kwarg) against the model field "slug" (slug_field).

    def get_object(self, queryset=None):
        book = super().get_object(queryset)
        # "extra work": an atomic counter update that is safe under concurrency
        Book.objects.filter(pk=book.pk).update(views=F("views") + 1)
        return book

        context = super().get_context_data(**kwargs)
        context["average_rating"] = self.object.reviews.aggregate(
            average=Avg("rating")
        )["average"]
        return context

Pagination

Setting paginate_by turns on pagination: ListView wraps the queryset in a Paginator, selects the page named by the page query-string parameter (or a page keyword argument in the URLconf, as in path("objects/page<int:page>/", …​)) and adds paginator, page_obj and is_paginated to the context. Pages are numbered from 1, ?page=last is accepted as a shortcut for the final page, and any other value that is not a valid page number (abc, 0, a page past the end) is a 404 — not a 500, and not silently page 1. The options are plain attributes, so as_view() can set them without a subclass:

The pagination links in pagination.html use the {% querystring %} template tag (new in Django 5.1) to build ?page=2 while keeping every other query parameter — here the q of the search form — instead of hand-assembling a URL and forgetting one. Three pitfalls specific to pagination:

  • Order the queryset. Paginating an unordered queryset can show the same row on two pages and skip another, because SQL does not promise any order without ORDER BY. Django warns about it: paginating Author.objects.all() (no Meta.ordering) printed UnorderedObjectListWarning: Pagination may yield inconsistent results with an unordered object_list: <class 'catalog.models.Author'> QuerySet. The Book model has a Meta.ordering, so BookListView does not warn; UnorderedWarningTests in Running the examples proves the warning for an unordered queryset.

  • Let the client choose the page size only within limits. get_paginate_by() is the hook; the mixin below clamps whatever ?per_page= says so that ?per_page=100000 cannot make one request load the whole table.

  • paginate_by counts objects, not queries. A page of 3 books with the template reading book.author.name would still run a query per row without the select_related("author") in PUBLISHED; see Query Optimization & Fetch Modes.

catalog/views.py — PerPageMixin
class PerPageMixin:
    """Let the client pick the page size with ?per_page=, within sane limits."""

    max_per_page = 50

    def get_paginate_by(self, queryset):
        try:
            requested = int(self.request.GET.get("per_page", self.paginate_by))
        except (TypeError, ValueError):
            requested = self.paginate_by
        return max(1, min(requested, self.max_per_page))

  • success_url uses reverse_lazy() because the attribute is evaluated when the module is imported, before the URLconf is loaded; reverse() there would fail. Alternatively override get_success_url(), which runs per request and can use reverse().

CreateView and UpdateView: model forms

CreateView and UpdateView build a ModelForm for you. The class is chosen like this: if form_class is set it is used; otherwise fields is required and Django generates a form for the model found from model, from the object returned by get_object() or from queryset. The two ways are mutually exclusive:

class BookCreateView(PermissionRequiredMixin, CreateView):
    permission_required = "catalog.add_book"
    model = Book
    fields = ["title", "slug", "isbn", "author", "price", "published", "is_published"]

  • fields is required when Django generates the form. A model form view without fields (and without form_class) raises ImproperlyConfigured — the same as writing a ModelForm without Meta.fields. List the fields explicitly; never use fields = "all", because the day someone adds an is_staff-like column to the model it becomes writable from the browser (mass assignment).

  • fields together with form_class is an error (ImproperlyConfigured) since Django 1.8; before that fields was silently ignored, which is how stale tutorials ended up with forms that did not match their fields list.

  • form_class still needs model: the documentation says to specify it even when the form_class is a ModelForm that already knows its model.

  • The redirect: with no success_url, ModelFormMixin.get_success_url() calls get_absolute_url() on the saved object (Book.get_absolute_url() here), and raises ImproperlyConfigured if neither exists. A success_url string may contain {field} placeholders that are filled with str.format() from the saved object’s attributes: "/catalog/authors/{slug}/?new=1" redirects to /catalog/authors/cy-poet/?new=1. (Django 1.8 introduced the {} syntax; the old %(field)s form was deprecated then and removed in 1.10, so tutorials that still show it are very old.) Only plain attributes (slug, author_id) are available, not related objects.

  • Templates: both views use <app>/<model>_form.html; set template_name_suffix (for example "_update_form") or template_name for a separate template.

  • self.object is None while a CreateView shows its form and is set to the saved instance in form_valid(); an UpdateView sets it in get() and post() before building the form.

Setting the owner in form_valid() and get_form_kwargs()

Fields that the user must not choose — the author of a review, the book it is about — are not on the form; the view fills them in before the object is saved. The official idiom is to assign to form.instance in form_valid() and then call super(), which saves:

catalog/views.py — ReviewCreateView and JsonableResponseMixin
class JsonableResponseMixin:
    """Add JSON support to an object-based form view such as CreateView."""

    def wants_json(self):
        preferred = self.request.get_preferred_type(["text/html", "application/json"])
        return preferred == "application/json"

    def form_invalid(self, form):
        response = super().form_invalid(form)
        if self.wants_json():
            return JsonResponse(form.errors, status=400)
        return response

    def form_valid(self, form):
        response = super().form_valid(form)  # saves the object, sets self.object
        if self.wants_json():
            return JsonResponse({"pk": self.object.pk}, status=201)
        return response


class ReviewCreateView(
    LoginRequiredMixin, JsonableResponseMixin, SuccessMessageMixin, CreateView
):
    model = Review
    form_class = ReviewForm

    @cached_property
    def book(self):
        return get_object_or_404(PUBLISHED, slug=self.kwargs["slug"])

    def get_form_kwargs(self):
        kwargs = super().get_form_kwargs()
        kwargs.update(book=self.book, reviewer=self.request.user)
        return kwargs

    def form_valid(self, form):
        # ModelFormMixin.form_valid() saves form.instance, so fill in the fields that
        # are not on the form first. Never put them in `fields` and trust the browser.
        form.instance.book = self.book
        form.instance.reviewer = self.request.user
        return super().form_valid(form)

    def get_success_message(self, cleaned_data):
        return f"Your review of {self.book.title} was saved."

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context["book"] = self.book
        return context

Reading the class from the top:

  • The base-class order is deliberate. LoginRequiredMixin must be leftmost so its dispatch() runs first; JsonableResponseMixin and SuccessMessageMixin wrap form_valid()/form_invalid() and so must precede CreateView, whose versions they extend with super().

  • book is a cached_property, not a lookup in setup(). It runs on first use — in get_form_kwargs() or form_valid() — which is after the login check, and only once per request even though several hooks read it. A Http404 for an unknown slug therefore cannot leak whether a book exists to anonymous visitors, and no query runs for them at all.

  • get_form_kwargs() hands book and reviewer to ReviewForm, whose clean() turns a second review of the same book into an ordinary non-field error instead of an IntegrityError and a 500. (The UniqueConstraint is the backstop. A constraint on fields that are not on the form is not checked by ModelForm validation, because validate_unique() and validate_constraints() skip excluded fields; that is why the check is in clean().) Passing request.user to the form this way, rather than reaching into request from the form, keeps the form testable.

  • form_valid() assigns form.instance.book and form.instance.reviewer, so a hostile browser cannot choose them: even a posted reviewer=2 is ignored because it is not in fields (the test_posted_reviewer_field_is_ignored test below posts it).

  • form_valid() assigns to form.instance and then calls super().form_valid(form), which saves once and redirects. Do not call form.save() yourself and then super().form_valid(form): the base class saves a second time (an extra UPDATE and a second round of save signals). If you want full control, use self.object = form.save(commit=False), set the fields, call self.object.save() and form.save_m2m() (needed for many-to-many fields when commit=False), and return your own redirect without calling super().form_valid().

  • SuccessMessageMixin queues a flash message after a valid form. Its success_message is formatted with % and the form’s cleaned_data, so a literal percent sign in the message would raise; for text that uses the saved object, override get_success_message(), as above.

  • get_context_data() adds book so the template can say what is being reviewed.

JsonableResponseMixin is the documented "same form, two clients" pattern. Scoping querysets to request.user

The commonest security bug in a generic edit view is not a missing login check; it is that the object is looked up by a primary key from the URL and any logged-in user may pass any key. /catalog/my-reviews/17/edit/ then edits review 17 whoever wrote it — an insecure direct object reference. The generic views give a one-line cure, because every one of them finds its objects through get_queryset(): restrict that, and the list, the detail lookup, the update form and the delete confirmation are all restricted in one place.

How it works:

  • OwnReviewsMixin extends LoginRequiredMixin, so a single base class gives both rules, and its get_queryset() calls super().get_queryset() before adding .filter(reviewer=self.request.user). Because the generic view’s own get_queryset() is next in the MRO (the mixin is listed first), the model or queryset attribute still applies.

  • get_object() runs get_queryset().get(pk=…​); for another user’s review that is DoesNotExist, which the generic view turns into Http404. The other user’s review is not found, not "forbidden": a 403 would confirm that review 17 exists.

  • The list view reuses the mixin and only adds select_related("book__author"), so the template can print book titles without one query per row.

  • An anonymous request never reaches get_queryset(): LoginRequiredMixin.dispatch() redirects first, so self.request.user is a real user inside every handler and the filter never receives an AnonymousUser. That only holds when the access mixin is the leftmost base class.

  • ReviewUpdateView uses the same ReviewForm as the create view and passes the book of the existing review through get_form_kwargs(). self.object is already loaded when get_form_kwargs() runs for an UpdateView.

  • ReviewDeleteView combines the scoping mixin with SuccessMessageMixin and a confirmation form; its success_url uses reverse_lazy() for the same import-time reason as before.

The access-control mixins

The scoping mixin builds on the access mixins of django.contrib.auth.mixins, which exist since Django 1.9. They all derive from AccessMixin, so they share the same attributes, and each overrides dispatch().

Mixin Behaviour

LoginRequiredMixin

Anonymous users are redirected to the login page (or get a 403 when raise_exception = True). It does not check is_active; the default authentication backends already reject inactive users. It must be the leftmost base class.

PermissionRequiredMixin

Set permission_required to one "app_label.codename" string or an iterable (all are required). Override get_permission_required() or has_permission() for custom logic. Anonymous users are redirected to login; authenticated users without the permission get a 403.

UserPassesTestMixin

Override test_func() (or get_test_func()) to return a boolean. It cannot be stacked: two UserPassesTestMixin subclasses in one MRO do not combine, because the first test_func() does not call the second.

AccessMixin

The base: login_url (get_login_url(), falls back to settings.LOGIN_URL), redirect_field_name ("next"; None omits it), raise_exception (default False), permission_denied_message and handle_no_permission(), which you can override to change how denial is answered.

An authenticated user who fails a permission or test check always gets a 403, never a redirect to login (that would loop for a user who is already logged in). For an object-level rule that is not "the owner" — an editor may change reviews of their section, say — a UserPassesTestMixin.test_func() that reads self.get_object() works but fetches the object twice; overriding get_queryset() to include the allowed rows is usually simpler and safer, because it protects every handler at once.

Two newer facts. Django 5.1 added LoginRequiredMiddleware, which makes every view require login unless it is decorated with login_not_required() (the authentication page covers both). The mixin is still the right tool when the rule is per view or needs permission_required; the middleware is a safety net so that a new view cannot be public by mistake. And permissions are cached on the user object, which is why the test above reloads the user after adding a permission.

Pitfalls of access control in class-based views

  • Order of the bases. class V(CreateView, LoginRequiredMixin) puts the access check after the generic view’s dispatch(); the check never runs. Mixins on the left, the generic view on the right.

  • A hand-written check before the mixin. Overriding dispatch() in your view, or adding a mixin whose dispatch() reads request.user.profile, to the left of LoginRequiredMixin means your code runs for anonymous users first and crashes with an AttributeError on AnonymousUser. Any extra mixin that uses request.user must come after LoginRequiredMixin.

  • Filtering after the fact. get_object() then if obj.reviewer != request.user: raise PermissionDenied is correct but only for that one handler, and leaks existence with a 403. Filter the queryset.

  • DELETE skips the form. DeletionMixin.delete() is still a handler of DeleteView: an HTTP DELETE request deletes the object without validating ConfirmDeleteForm (and without the success message), because only the POST handler runs the form. The scoping still holds, since delete() also calls get_object() (the test_http_delete_skips_the_confirmation_form_but_not_the_scoping test pins both facts down). If the confirmation form is a real business rule, not just UX, restrict http_method_names to ["get", "post", "head", "options"].

  • Guessable keys. Sequential primary keys let anyone enumerate objects that are meant to be reachable only by whoever has the link. query_pk_and_slug = True makes get_object() match both the primary key and the slug (the script above shows a mismatched slug giving a 404), and a non-sequential slug or UUID key hides the rest. This is a mitigation, not authorization: scoping the queryset is.

  • CSRF. All the state-changing views use POST and the templates contain {% csrf_token %}. A "delete" link that is a plain <a href> to a URL that deletes on GET is a CSRF hole; DeleteView does not delete on GET.

Pitfalls that cost people an afternoon:

  • The default month format is %b, the abbreviated month name (aug, as strptime() reads it), so a URL /2024/05/ is a 404 until you set month_format = "%m". The URLconf then captures it with <int:month> or <str:month>. Never use the format characters of the now template tag here; these attributes use strftime() characters.

  • ISO weeks need the ISO year. week_format = "%V" is supported (since Django 3.2), but a %V week is only meaningful with the ISO year %G: the default year_format = "%Y" makes the view raise ValueError: ISO week directive '%V' is incompatible with the year directive '%Y'. Use the ISO year '%G' instead. — an unhandled error, a 500 page. That is why BookWeekArchiveView sets both; test_iso_week_format_needs_the_iso_year_format asserts the error and test_year_month_day_week the working configuration. Week numbers printed with the date filter’s W character are not always equal to strftime()’s `%W, so do not build URLs from them (the manual says the same).

  • Time zones. If date_field is a DateTimeField and USE_TZ is on, "the day" means the day in the current time zone; with per-user time zones the same URL can show different objects for different users. Use a DateField (as Book.published is) when the date is a calendar date, not an instant.

  • Each next_ and previous_* value costs a query* when allow_empty = False, because Django looks for the next period that has objects.

  • The archive views fetch everything for the period. MonthArchiveView has no pagination by default; add paginate_by for a busy period.

  • The order of date_list is fixed (years newest first on the index, months and days oldest first); iterate it with {% for d in date_list reversed %} for the other direction.

The views are built from mixins — YearMixin, MonthMixin, DayMixin, WeekMixin, DateMixin and BaseDateListView — documented in Mixin reference. Their get_year(), get_month() and get_day() methods try, in order, the year/month/day attribute, the URL argument of the same name and the query-string parameter, and raise Http404 if none is usable. A route without a year argument therefore still works with ?year=2024 in the query string, and an invalid date such as 2024-02-31 is a 404, not a 500 (the test_invalid_date_is_404 test).

Sync and async behaviour

The generic views are written as ordinary synchronous Python, and that is the right default: the ORM calls in get_queryset(), get_object(), form_valid() and the paginator are synchronous, and so are the form and template layers. What that means in practice depends on the server:

  • Under WSGI (Gunicorn’s default workers, runserver without ASGI) everything is sync and nothing special happens.

  • Under ASGI (Uvicorn, Daphne, Granian; runserver with Daphne), Django runs a sync view in a worker thread (sync_to_async() with thread-sensitive mode) so it does not block the event loop. A generic view therefore works unchanged, with a small thread-hop cost per request. The check BookListView.view_is_async is False; for an async handler it is True.

  • Template rendering is always sync work, even for an async view: render_to_response() returns a lazy TemplateResponse, and the handler renders it in a thread afterwards. That is why the async list view below can still use a template that touches the ORM — but a template that reads a not-yet-evaluated QuerySet does that query synchronously.

An async generic view is a generic view whose handler is async def. Since the view base class (View) supports async handlers (Django 3.1), you override get() in a display view and use the async ORM (async for, aget(), acount(); Django 4.1) and the async shortcuts (aget_object_or_404() and aget_list_or_404(), Django 5.0):

catalog/views.py — async display views
class AsyncBookListView(ListView):
    queryset = PUBLISHED
    context_object_name = "books"
    template_name = "catalog/book_list.html"

    async def get(self, request, *args, **kwargs):
        # Evaluate the queryset asynchronously; template rendering is done later by the
        # handler (in a worker thread), so the template can still touch the ORM.
        self.object_list = [book async for book in self.get_queryset()]
        return self.render_to_response(self.get_context_data())


class AsyncBookDetailView(DetailView):
    queryset = PUBLISHED

    async def get(self, request, *args, **kwargs):
        self.object = await aget_object_or_404(self.get_queryset(), slug=kwargs["slug"])
        return self.render_to_response(self.get_context_data(object=self.object))

The rules, each backed by something that ran:

  • All handlers of one class must be sync or all async. View.view_is_async inspects the handlers. ListView and DetailView only define get() (plus options(), which adapts), so overriding get() as async def is allowed. CreateView, UpdateView, FormView and DeleteView define post(), put() or delete() as sync methods, so an async get() on them fails when as_view() is called: ImproperlyConfigured: Mixed HTTP handlers must either be all sync or all async. (the last test of AsyncViewTests asserts it). To make an editing view async you would override every handler, which gives up almost everything the generic view does; for editing, keep the sync view.

  • Do not touch the ORM synchronously in an async handler. Evaluating a QuerySet (list(qs), iteration, get_object(), paginate_queryset()) inside async def raises SynchronousOnlyOperation. AsyncBookListView evaluates the queryset with async for and sets self.object_list to a list, and get_context_data() then does no queries. ListView pagination is sync-only; Django 6.0 added AsyncPaginator and AsyncPage, but the generic views do not use them, so an async list that paginates has to call the async paginator itself. Which to choose? Keep the generic views sync, and reach for an async handler only when the page waits on slow I/O that can run concurrently — several outbound HTTP calls in one get(), say. The rest of the checklist, from the earlier sections:

Pitfall Remedy

Mutating the class-level queryset (for example appending a filter in place)

Use get_queryset(), which clones; add filters on the clone.

self.object or an attribute set on self in one request appears in another

It cannot: the view instance is per request. Class attributes are shared, so keep mutable defaults (lists, dicts, QuerySets) out of them or copy them.

Overriding get_context_data() without super()

The object_list, paginator, form and view entries vanish. Always context = super().get_context_data(**kwargs).

Filtering in the template or in get_context_data() instead of get_queryset()

The template filter still serves hidden rows to anyone with the URL, and pagination counts the wrong total. Filter the queryset.

fields = "all" or exclude on a CreateView/UpdateView

A new model column becomes browser-writable. List fields explicitly, or use a ModelForm with an explicit Meta.fields.

Setting form.instance.owner after super().form_valid()

By then the object is saved without it (an IntegrityError for a required field). Assign before calling super().

Returning nothing from form_valid()

The view must return an HttpResponse; return super().form_valid(form) or your own redirect.

success_url = reverse("name") at class level

Fails at import (the URLconf is not loaded yet). reverse_lazy(), or override get_success_url().

Placeholders in success_url that name related objects

Only attributes of the saved object are available ({slug}, {author_id}), not {author.slug}. Override get_success_url() for anything else.

DeleteView without a way to leave GET harmless

It already does: a GET only renders the confirmation. Do not link "delete" to a URL that deletes on GET.

Custom deletion logic in a delete() override

Since Django 4.0 the POST path goes through form_valid(). Move the logic there or into a helper that both call.

LoginRequiredMixin not leftmost, or an extra dispatch() that uses request.user before it

Put access mixins first; anything touching request.user after them.

Using UserPassesTestMixin twice

Combine the tests into one test_func().

paginate_by on an unordered queryset

Set ordering or Meta.ordering; otherwise pages are unstable and Django warns.

month_format, week_format, allow_future, allow_empty left at their defaults

%b months, Sunday-based %U weeks, future items hidden and empty periods a 404. Check the date-view options table.

An async get() on a view with sync post()

ImproperlyConfigured; keep editing views sync.

self.request.user in an async handler

SynchronousOnlyOperation; await self.request.auser().

Using request.accepts("text/html") to branch between HTML and JSON

It is true for / and for a missing header. Prefer request.get_preferred_type([…​]) (Django 5.2).

Choosing between generic views, function views and your own class

Use a generic view when the page is one of the shapes in the first table and the differences from the default are a queryset, a template, a form class or a couple of hooks. Use a function-based view (see Function-Based Views & Shortcuts) when the logic is a short sequence that does not fit the shape — an endpoint that calls three services, a webhook receiver — or when reading the generic view’s hooks would take longer than writing twenty lines. Use a plain View subclass, or View plus a mixin from this page (as BookJsonListView does), when you want the object lifecycle (setup(), dispatch(), method routing) but not templates or forms.

Practical rules that keep generic views maintainable:

  • Keep the inheritance shallow: at most one generic view and a few small mixins that do one thing each, with LoginRequiredMixin first and the generic view last.

  • Put the rules in the places the framework already calls: query restrictions in get_queryset(), ownership in form_valid(), extra form arguments in get_form_kwargs(), validation in the form. A view whose post() re-implements form handling has stopped being a generic view.

  • Keep business logic out of the view: call a model method, a manager method or a service function from form_valid() so that the same code can serve an admin action, a management command or a Celery task.

  • Write one test per view that checks the status, the template or redirect, the context or the database effect, and the denial cases.

  • Django REST Framework has its own generics module (ListAPIView, ListCreateAPIView and so on) that follows the same idea for JSON APIs; it is a separate library and has its own page later in this section. The Django generic views here render HTML.

Where the books are outdated

The four books that informed this section were written against Django 1.11 to 2.1. For generic views the concepts survived; the details that changed are the ones that bite when you copy a listing:

  • Everything about class-based generic views dates from Django 1.3 (2011). If an old tutorial mentions the function-based generic views (direct_to_template, object_list and others in modules such as django.views.generic.list_detail), those were deprecated in 1.3 and are long gone; the class-based views here are the only generic views.

  • url() in the URLconf of an older listing no longer exists (removed in 4.0); write path() or re_path() and the <int:pk> converters shown in the URLconf above.

  • DeleteView logic. Books that customise deletion by overriding delete() describe the pre-4.0 flow. Since 4.0, POST goes through form_valid() and a form, so the logic belongs there and SuccessMessageMixin finally works.

  • Success URL placeholders in older code use %(slug)s; the {slug} syntax arrived in 1.8 and the old one was removed in 1.10.

  • fields. Old code relies on a CreateView without fields, which generated a form with every field; that is an ImproperlyConfigured error today (see the output above), and fields = "all" is a security anti-pattern, not a convenience. Specifying fields and form_class together has been an error since 1.8.

  • Permissions in views. Books that predate 1.9 wrap dispatch() in @method_decorator(login_required); use LoginRequiredMixin and PermissionRequiredMixin (added in 1.9) leftmost in the class. A book listing that puts a check in dispatch() before the mixin runs it for anonymous users first, which is a bug in the book, not a technique.

  • request.user.is_authenticated() as a method call was a property from 1.10 and the call form was removed in 2.0; the mixins hide it, but hand-written checks in old code still show it.

  • Tests that pass for the wrong reason. A test that POSTs a delete and only asserts status_code == 200 (a 200 means the confirmation page was shown, not that anything was deleted), or that never checks the row afterwards, proves nothing. The tests on this page re-read the database after every write.

  • Template and helper names (render_to_response, ugettext, {% load staticfiles %}) in old view code were removed in 3.0 and 4.0; use render()/TemplateResponse, gettext and {% load static %}.

  • Books show GET links that change state (a "delete" or "add to basket" link). Those are CSRF holes; the generic editing views use POST with {% csrf_token %}.
