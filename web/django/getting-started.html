Install Django

Django is a pure Python package with two small hard dependencies (asgiref and sqlparse). Everything else (a database driver, an image library, Redis) is optional and only needed for the feature that uses it. The installation guide lists three sources: an official release from PyPI (the right choice for nearly everyone), the package your operating system distributes (usually old), and the development branch (only for people who want to help test it).

The Python version matrix

Each Django release supports a window of Python versions, and only the latest micro release of each Python series is officially supported:

Django Python versions

4.2 LTS

3.8, 3.9, 3.10, 3.11, 3.12 (added in 4.2.8). Security support ended in April 2026.

5.0

3.10, 3.11, 3.12

5.1

3.10, 3.11, 3.12, 3.13 (added in 5.1.3)

5.2 LTS

3.10, 3.11, 3.12, 3.13, 3.14 (added in 5.2.8). Extended support until April 2028.

Source: FAQ: Installation, Django 6.1 release notes

The practical rule is that Django 6.0 and later need Python 3.12 or newer, so an old system Python cannot install them. This is easy to trip over: with the Python 3.9 that ships with some operating systems, pip looks at the package index, sees that none of the newer releases declares support for its interpreter and fails with a message that looks like a typo in the package name:

$ python3.9 -m pip install "Django>=6.1,<6.2"
ERROR: Could not find a version that satisfies the requirement Django<6.2,>=6.1 (from versions: 1.1.3, ..., 4.2.30)
ERROR: No matching distribution found for Django<6.2,>=6.1

Source: FAQ: Installation

The list of versions in that error stops at 4.2.30, which is the newest release whose metadata accepts Python 3.9 (the output above was captured on 2026-10-03). The fix is a newer interpreter, not a different command. If you must stay on an older Python for a while, pin the Django series it supports (Django 4.2 for Python 3.9) and read the matching documentation version through the version switcher on docs.djangoproject.com. The FAQ also gives the rule behind the table: Django supports a Python version up to and including the first LTS release whose security support ends after that Python version’s own security support ends. Python 3.10 and 3.11 were last supported by the Django 5.2.x series.

Create a project directory and a virtual environment

Give every project its own virtual environment, so its packages never collide with another project’s or with the system. The tool-agnostic mechanics (what a virtual environment is, requirements.txt, lock files) are covered in the Python Reference, in Virtual Environments & Packaging, and are not repeated here. Two routes work equally well.

With uv, a fast project manager that creates the environment, installs Django and records exact versions in uv.lock:

uv init bookshelf --bare --python 3.13
cd bookshelf
uv add "django>=6.1,<6.2"
uv run python -m django --version

Source: Quick install guide

uv init --bare writes only a pyproject.toml. uv add creates .venv (you never activate it), adds the dependency to pyproject.toml and locks the resolved versions. This was run on 2026-10-03 and installed asgiref==3.12.1, django==6.1.1 and sqlparse==0.6.0; uv run python -m django --version printed 6.1.1. Prefix every later command with uv run (for example uv run python manage.py runserver) or activate .venv yourself.

With the standard library and pip:

mkdir bookshelf && cd bookshelf
python3.13 -m venv .venv
source .venv/bin/activate          # Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install "Django>=6.1,<6.2"
python -m django --version
pip freeze                         # asgiref, Django, sqlparse

Source: How to install Django

Quote the requirement: without quotes the shell treats > and < as redirections. Pinning the series (>=6.1,<6.2) means you receive security and bug-fix releases (6.1.2 and later) without a surprise jump to the next feature release. After the install, django-admin is on the path of the environment, and python -m django is an equivalent spelling that always uses the interpreter you are running, which is handy when two environments are installed.

Verify from Python itself, as the installation guide does:

>>> import django
>>> print(django.get_version())
6.1.1
>>> django.VERSION
(6, 1, 1, 'final', 0)

Source: Quick install guide

Databases and the web server you do not need yet

Django ships with a development server and uses SQLite, which is part of Python, so nothing else has to be installed for this page. For production the installation guide recommends PostgreSQL (officially supported: PostgreSQL, MariaDB, MySQL, Oracle and SQLite). Django 6.1 requires PostgreSQL 15 or newer, MySQL 8.4 or newer, MariaDB 10.11 or newer and SQLite 3.37 or newer, and a PostgreSQL project installs psycopg (psycopg 3 has been supported since Django 4.2). Production servers (Gunicorn, Uvicorn, Daphne, Granian) are the subject of the deployment pages; nothing on this page needs them. Windows users can follow the official How to install Django on Windows for the interpreter and path setup.

Source: How to install Django, Databases

Create a Project With startproject

A project is the configuration of one Django site: settings, the root URL table and the entry points for web servers. It is generated, not written by hand:

django-admin startproject mysite djangotutorial
cd djangotutorial

Source: Writing your first Django app, part 1

The signature is django-admin startproject name [directory]. With both arguments (as above) the directory djangotutorial is the project directory and mysite is the Python package inside it. With only a name, both the directory and the package are called mysite, which produces the familiar mysite/mysite nesting. With . as the directory, the project is generated in the current directory, which is the usual choice inside an already created repository:

The reloader watches Python files and restarts the process on change (it prints Watching for file changes with StatReloader). Where the development server sits in the request cycle: it is a small multithreaded WSGI server. It builds a WSGI environ for each HTTP request and calls the object named by the WSGI_APPLICATION setting (mysite.wsgi.application), exactly like Gunicorn would, so everything described under "The request cycle" below runs identically. It has not been security audited and is not meant for production. For asynchronous code it still works: an async def view runs under it (Django adapts it to the synchronous request path), but only an ASGI server runs async views natively. The Request Cycle in One Picture

Everything you will write in this page plugs into one path. A request enters through the WSGI or ASGI entry point (wsgi.py or asgi.py), passes down through the middleware listed in MIDDLEWARE, is routed by the root URLconf named by ROOT_URLCONF, reaches a view, and the response travels back up through the same middleware. The view reads or writes models (the ORM) and renders a template. That is the whole loop, and it is the reason a typical change touches the same four places in the same order: the model (data), the view (logic), the URLconf (address) and the template (presentation).

# polls/models.py
import datetime

from django.contrib import admin
from django.db import models
from django.utils import timezone


class Question(models.Model):
    question_text = models.CharField(max_length=200)
    pub_date = models.DateTimeField("date published")

The rule to remember is the three-step loop for every model change: edit models.py, run makemigrations to write a migration file, run migrate to apply it. The @admin.display decorator on the method (since Django 3.2; it replaces the older short_description and boolean function attributes) configures how the admin shows it and is used in step 6.

Notes that matter:

  • Template location and namespacing. The default TEMPLATES setting uses the DjangoTemplates backend with APP_DIRS: True, so Django looks in a templates/ directory inside every installed app. The file is polls/templates/polls/index.html and is referred to as polls/index.html. The doubled polls/ is deliberate: Django returns the first template whose name matches, so unnamespaced templates from two apps would shadow each other.

  • render(request, template_name, context) loads the template, renders it with the context (a dictionary) and returns an HttpResponse. Passing request is what makes context processors (such as request, auth and messages) available. It replaces the older two-step loader.get_template(…​) plus HttpResponse(…​), and the render_to_response() that Django 3.0 removed.

  • get_object_or_404() raises Http404 when no row matches; get_list_or_404() does the same for an empty list. The helper lives in django.shortcuts on purpose: the model layer must not know about HTTP.

  • {% url 'polls:detail' question.id %} reverses a URL from its name, so the link survives a change to the pattern. The app_name = "polls" line creates the polls: namespace so two apps can both have a detail view. Hard-coded paths such as /polls/{{ question.id }}/ (the tutorial’s first draft) break as soon as the mount point moves.

  • Template variables use dot lookup: dictionary key, then attribute, then list index; question.choice_set.all calls the method.

  • The tutorial’s templates are intentionally fragments. Real projects should use complete HTML documents (see the pitfall about the debug toolbar below).

from django.db.models import F
from django.http import HttpResponseRedirect
from django.shortcuts import get_object_or_404, render
from django.urls import reverse

from .models import Choice, Question


def vote(request, question_id):
    question = get_object_or_404(Question, pk=question_id)
    try:
        selected_choice = question.choice_set.get(pk=request.POST["choice"])
    except (KeyError, Choice.DoesNotExist):
        # Redisplay the question voting form.
        return render(
            request,
            "polls/detail.html",
            {
                "question": question,
                "error_message": "You didn't select a choice.",
            },
        )
    else:
        selected_choice.votes = F("votes") + 1
        selected_choice.save()
        # Always redirect after a successful POST so a refresh does not vote twice.
        return HttpResponseRedirect(reverse("polls:results", args=(question.id,)))

The vote is counted with F("votes") + 1, which makes the database perform the increment, so two simultaneous voters cannot overwrite each other’s update (a read-modify-write in Python would lose one). Static files (CSS, JavaScript, images) live in static/ directories next to templates and are namespaced the same way: polls/static/polls/style.css. The {% load static %} tag and {% static %} generate the URL from STATIC_URL:

{# top of polls/templates/polls/index.html #}
{% load static %}
<link rel="stylesheet" href="{% static 'polls/style.css' %}">

Source: Writing your first Django app, part 6

Under runserver with DEBUG = True, django.contrib.staticfiles serves them from the app directories (the curl check returned HTTP 200, Content-Type: text/css). In production there is no such magic: collectstatic gathers files into STATIC_ROOT and a web server or WhiteNoise serves them, which the Static & Media Files page covers. Old books write {% load staticfiles %} or {% load admin_static %}; those tag libraries were removed in Django 3.0, use {% load static %}.

Step 9: the admin (tutorial parts 2 and 7)

Create an administrator and register the models:

python manage.py createsuperuser

Source: Writing your first Django app, part 2

createsuperuser prompts for a username, an optional email address and a password (twice); never script a real password into a command line or a repository. Then customise the admin as in part 7:

# polls/admin.py
from django.contrib import admin

from .models import Choice, Question


class ChoiceInline(admin.TabularInline):
    model = Choice
    extra = 3


class QuestionAdmin(admin.ModelAdmin):
    fieldsets = [
        (None, {"fields": ["question_text"]}),
        ("Date information", {"fields": ["pub_date"], "classes": ["collapse"]}),
    ]
    inlines = [ChoiceInline]
    list_display = ["question_text", "pub_date", "was_published_recently"]
    list_filter = ["pub_date"]
    search_fields = ["question_text"]


admin.site.register(Question, QuestionAdmin)

Source: Writing your first Django app, part 7

Visit /admin/, log in and you get create, change, delete and history screens for questions, with Choice rows edited inline on the question page (TabularInline is the compact layout, StackedInline the roomy one), a change list with the columns of list_display, a date filter and a search box. Two ModelAdmin facts help to read the code: list_display entries may be methods of the model (here with the @admin.display decorator from step 2), and fieldsets controls grouping, the collapse class hides a group behind a toggle. The admin is a page of its own in this section.

Sync and Async Notes

Everything above is synchronous: a WSGI server calls your view in a worker thread, the ORM blocks that thread while it waits for the database, and that is a perfectly good default. Since Django 3.1 views and middleware may be async def, and the ORM has asynchronous methods (aget, acount, async for over a queryset) since 4.1. An async view runs natively under ASGI (asgi.py, served by Uvicorn, Daphne or Granian); under WSGI, including runserver, Django adapts it to the synchronous path so it works but gains no concurrency. This view was added to the polls app and answered correctly under both servers:

# polls/views.py
from django.http import JsonResponse

from .models import Question


async def ping(request):
    count = await Question.objects.acount()
    return JsonResponse({"questions": count})
# polls/urls.py (add to urlpatterns)
path("ping/", views.ping, name="ping"),

Source: Asynchronous support

$ python -m uvicorn mysite.asgi:application --port 8000
$ curl -si http://127.0.0.1:8000/polls/ping/
HTTP/1.1 200 OK
...
{"questions": 1}

Source: How to deploy with ASGI

Do not mix blocking calls (a plain ORM query, requests, time.sleep) into an async def view: Django raises SynchronousOnlyOperation for ORM access from an async context, and other blocking calls stall the whole event loop. Prefer plain def views unless you need concurrency, WebSockets or server-sent events. These topics have dedicated pages.

Pitfalls Checklist

  • Wrong interpreter. Django 6.0 and later need Python 3.12 or newer. An older Python makes pip report "No matching distribution".

  • Installing into the system Python. Use a virtual environment per project and run python -m django --version to see which Django you actually get.

  • Forgetting to register the app. Models in an app that is not in INSTALLED_APPS are not migrated; makemigrations polls then answers "No installed app with label 'polls'" (seen while preparing this page).

  • Skipping include() or putting /polls/ twice in the browser URL: the root URLconf strips the matched prefix.

  • Editing models without migrating. Run makemigrations and migrate; commit the migration files.

  • Un-namespaced templates and static files shadowing each other across apps.

  • Changing data over GET or omitting {% csrf_token %} in a POST form (the request fails with 403).

  • Treating runserver as production. It is neither hardened nor tuned; deploy behind Gunicorn or an ASGI server.

  • Leaving the generated SECRET_KEY, DEBUG = True and an empty ALLOWED_HOSTS in deployed settings. Run check --deploy.

  • Reading a stale tutorial. See the next section.

Where the Books Are Outdated

Introductory books and blog posts written between Django 1.11 and Django 3 remain useful for the ideas (the project/app split, the model-view-template flow, forms, the admin) but several commands and imports no longer work on Django 6.1. Check these first when a sample fails:

  • Python and installation. Books that install with virtualenv, pipenv or easy_install and a Python 2 or early Python 3 interpreter do not match the 3.12 to 3.14 window. The installation steps in this page (venv or uv, a pinned series) are the current ones.

  • URL routing. The regular-expression url() function from django.conf.urls was removed in Django 4.0. Use path() (added in 2.0) or re_path(). Likewise django.core.urlresolvers was removed in 2.0 in favour of django.urls.

  • Registering apps. default_app_config in init.py is obsolete (automatic discovery since 3.2), and the AppConfig is referred to by "polls" or "polls.apps.PollsConfig".

  • Settings. MIDDLEWARE_CLASSES was replaced by MIDDLEWARE in 2.0; the template tag libraries staticfiles and admin_static were removed in 3.0; USE_L10N was removed in 5.0; DEFAULT_AUTO_FIELD is no longer in generated projects since 6.0; and DEFAULT_FILE_STORAGE/STATICFILES_STORAGE were replaced by STORAGES (4.2) and removed in 5.1.

  • Tests. assertQuerysetEqual is assertQuerySetEqual since 4.2 (old name removed in 5.1).

  • Admin. Method attributes such as short_description and boolean are replaced by the @admin.display decorator (3.2).

  • Layout. Older books place the project in a directory named after itself (mysite/mysite) and show manage.py commands without the shell auto-imports; both remain valid but the destination argument and the shell imports make the modern flow shorter.

  • Async. ASGI (3.0), async views (3.1), the async ORM (4.1) and async authentication (5.0) postdate nearly every book; none of them is required to follow this page.

Source: Django Deprecation Timeline

What Changed Recently

  • Django 6.1 (2026-08-05). Python 3.12 to 3.14; PostgreSQL 15 or newer. New: model field fetch modes, database-level delete options for ForeignKey.on_delete (DB_CASCADE, DB_SET_NULL, DB_SET_DEFAULT), and the MAILERS setting, which is generated in new projects (it will replace EMAIL_BACKEND and the other EMAIL_* settings in Django 2028, and the old settings and get_connection() already emit deprecation warnings). Calendar versioning (DEP 20): the releases planned as 7.0 and 7.1 are now Django 2028 and 2029; the matching rename of the deprecation warning classes (RemovedInDjango70Warning to RemovedInDjango2028Warning, old name kept as an alias) was announced in 6.1 and ships in a 6.1 patch after 6.1.1. Management commands enable suggest_on_error on Python 3.14, so typos in subcommand names get a suggestion.

  • Django 6.0. DEFAULT_AUTO_FIELD defaults to BigAutoField and is no longer generated; startproject and startapp create a missing destination directory; the shell auto-imports settings and other common utilities; template partials, the django.tasks framework and built-in Content Security Policy support arrive (each has its own page).

  • Django 5.2 LTS. The shell automatically imports models from installed apps; Python 3.14 added in 5.2.8.

  • Release rhythm. 5.2 is the long-term-support release until April 2028; 6.2 LTS is planned for April 2027. For learning, use the newest release; for a long-lived project, plan upgrades through the LTS releases and run your tests with python -W error::DeprecationWarning (or -Wall) so deprecations surface early.
