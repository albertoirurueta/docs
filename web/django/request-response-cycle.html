Request/Response Cycle

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Django 6.1 (6.1.1 on PyPI; 6.1.2 is scheduled for 2026-10-06), Python 3.12-3.14 and PostgreSQL 15+, checked on 2026-10-03; where Django 5.2 LTS behaves differently the text says so. The listings were run in a scratch project on Python 3.13.16 and Django 6.1.1 with SQLite: manage.py check, 32 tests (manage.py test), curl sessions against runserver, Uvicorn and Gunicorn, and the stand-alone scripts below all passed, and the output shown is the real output. Nothing on this page needs PostgreSQL or Redis.

Every Django site, however large, is a function from an HTTP request to an HTTP response. Understanding the path a request takes through the framework explains most of the questions people ask in practice: why a middleware sees a response it did not create, why request.user is missing in one place, why a 404 page looks different with DEBUG = True, why a view that forgets return fails with a ValueError, or why an async view is slower under one server than another. This page follows one request from the socket to the view and back, in order, and describes every object it meets on the way: the handler, the middleware chain, the URL resolver, the view, the deferred template renderer, the error views, and the HttpRequest, QueryDict and HttpResponse classes. The Bookshelf scenario (the catalog app) supplies the examples.

Each layer has a page of its own for the details this page only summarises: Middleware for writing and ordering middleware, Function-Based Views & Shortcuts for the views themselves, and Introduction & Architecture for the MTV architecture this cycle implements. URL patterns (path(), converters, namespaces, reverse()), class-based and generic views, file uploads, and streaming, CSV and PDF responses each have their own pages in this section; here they appear only at the point where the cycle reaches them. Readers coming from FastAPI will find the same ideas under different names on FastAPI: Request Object & Content Type and FastAPI: Status Codes & Error Handling.

The cycle at a glance

In words, for one ordinary GET under WSGI:

  1. The server (Gunicorn, runserver, uWSGI, mod_wsgi; or Uvicorn, Daphne, Granian, Hypercorn under ASGI) accepts the connection, parses the HTTP request and calls the application object that config/wsgi.py or config/asgi.py exposes.

  2. The handler (WSGIHandler or ASGIHandler) sends the request_started signal, builds an HttpRequest from the server’s environ (WSGI) or scope and body (ASGI), and passes it to get_response().

  3. get_response() calls the outermost middleware. Each middleware’s __call__() runs its "before" code, then calls get_response to hand the request to the next layer.

  4. The innermost layer (Django’s own, not yours) resolves the URL: it matches request.path_info against the urlpatterns of ROOT_URLCONF (or of request.urlconf if a middleware set one) and stores the result in request.resolver_match.

  5. Every middleware’s process_view() hook runs, top-down. Any of them may answer on its own.

  6. The view runs with the request plus the URL’s captured arguments, and returns a response object.

  7. If the response has a render() method (a TemplateResponse), every process_template_response() hook runs, bottom-up, and then the template is rendered.

  8. The response travels back out through each middleware’s "after" code, bottom-up.

  9. The handler turns the response into a status line, headers (including Set-Cookie) and a body for the server, which sends them and calls response.close(); closing sends request_finished.

Whenever something raises along the way, Django turns the exception into a response and the cycle continues from step 8, as the red panel in the figure shows. The sections below take the steps in order.

The server and the handler

Django does not listen on a socket. A server does, and it speaks to Django through one of two Python standards: WSGI (a synchronous callable application(environ, start_response)) or ASGI (an asynchronous callable application(scope, receive, send)). startproject generates config/wsgi.py and config/asgi.py, each of which exposes a module-level application; Introduction & Architecture compares the two interfaces and lists the servers. What matters here is what the callable behind application does, because it is the first piece of Django code that touches the request. get_wsgi_application() and get_asgi_application() call django.setup() and return an instance of django.core.handlers.wsgi.WSGIHandler or django.core.handlers.asgi.ASGIHandler. Django documents the two functions, not the classes, as the public interface, so build on them in production code. The classes are used directly below only to make the cycle visible.

WSGIHandler

WSGIHandler.__call__(environ, start_response) does five things, in this order (read in Django 6.1.1’s django/core/handlers/wsgi.py):

  1. It records the script prefix (SCRIPT_NAME, or FORCE_SCRIPT_NAME) so that reverse() and {% url %} produce paths that work when Django is mounted below /.

  2. It sends the request_started signal with the handler class as sender and the environ dictionary.

  3. It builds a WSGIRequest (an HttpRequest subclass) from the environ.

  4. It calls get_response(request), which runs the middleware chain, the view and everything in between, and always returns a response object.

  5. It calls start_response() with the status line and the headers (the response’s headers plus one Set-Cookie per cookie) and returns the response, which is an iterable of byte strings. When the server provides wsgi.file_wrapper, a FileResponse is handed to it so the server can use sendfile-style transfers.

The handler can be called without a server, which is the clearest way to see that a WSGI application is "just a function":

catalog/tests.py (HandlerTests, WSGI half)
from wsgiref.util import setup_testing_defaults

from django.core.handlers.wsgi import WSGIHandler
from django.test import SimpleTestCase


class HandlerTests(SimpleTestCase):
    def test_wsgi_handler_speaks_wsgi(self):
        environ = {}
        setup_testing_defaults(environ)
        environ.update(PATH_INFO="/hello/", REQUEST_METHOD="GET", HTTP_HOST="localhost")
        seen = {}

        def start_response(status, headers):
            seen["status"], seen["headers"] = status, dict(headers)

        body = b"".join(WSGIHandler()(environ, start_response))
        self.assertEqual(seen["status"], "200 OK")
        self.assertEqual(seen["headers"]["Content-Type"], "text/plain")
        self.assertEqual(body, b"Hello from Bookshelf")

setup_testing_defaults() from the standard library’s wsgiref fills in the environ keys a real server would provide. WSGIHandler() loads the middleware chain once, in its constructor; a production server creates it once per worker process (the module-level application), never per request.

Source: Django: How to deploy with WSGI

ASGIHandler

ASGIHandler.__call__(scope, receive, send) has the same job with different mechanics:

  • It serves only http scopes. A websocket scope raises ValueError; WebSockets belong to Channels, which routes the websocket scope to consumers and hands http to Django (see the Channels page of this section).

  • It reads the whole request body before the view runs: read_body() collects http.request messages into a SpooledTemporaryFile (in memory up to FILE_UPLOAD_MAX_MEMORY_SIZE, which is 2.5 MiB by default, then on disk) and wraps it as the request’s body stream. A slow upload therefore never occupies the view, but it also means the view cannot start processing a body while it is still arriving.

  • It sends request_started with await signals.request_started.asend(…​) (asynchronous signal dispatch exists since Django 5.0) and builds an ASGIRequest.

  • ASGIRequest fills META from the scope: header names containing an underscore are dropped (the same anti-spoofing rule as runserver), repeated headers are joined with commas and repeated Cookie headers with "; ". If the request cannot even be built (an undecodable query string gives a plain 400, an oversized body a plain-text 413), the handler answers directly and no middleware runs.

  • While the view runs it listens for the http.disconnect message. If the client goes away first, the view’s task is cancelled and an asyncio.CancelledError is raised inside it, so an async view can clean up (supported since Django 5.0).

  • It sends the response in chunks of up to 64 KiB (ASGIHandler.chunk_size) as http.response.start and http.response.body messages; for a StreamingHttpResponse it sends each chunk of the iterator as it is produced.

A hand-written ASGI "server" shows the message flow. The receive callable must behave like a real server’s: deliver the body, and then block until the client disconnects (a version that returns a second http.request message makes Django raise an AssertionError, because the protocol forbids it):

catalog/tests.py (HandlerTests, ASGI half)
import asyncio

from django.core.handlers.asgi import ASGIHandler


class HandlerTests(SimpleTestCase):  # the same class as above
    async def test_asgi_handler_speaks_asgi(self):
        scope = {
            "type": "http",
            "asgi": {"version": "3.0"},
            "http_version": "1.1",
            "method": "GET",
            "path": "/hello/",
            "raw_path": b"/hello/",
            "query_string": b"",
            "headers": [(b"host", b"localhost")],
            "server": ("localhost", 8000),
            "client": ("127.0.0.1", 50000),
            "scheme": "http",
        }
        sent = []
        messages = [{"type": "http.request", "body": b"", "more_body": False}]

        async def receive():
            if messages:
                return messages.pop(0)
            await asyncio.Event().wait()  # like a real server: block until disconnect

        async def send(message):
            sent.append(message)

        await ASGIHandler()(scope, receive, send)
        self.assertEqual(sent[0]["type"], "http.response.start")
        self.assertEqual(sent[0]["status"], 200)
        self.assertEqual(sent[1]["body"], b"Hello from Bookshelf")

What differs inside the cycle

Everything after the handler is shared code in django.core.handlers.base.BaseHandler, but the handler’s mode decides whether each step runs natively or through an adapter (see Sync and async through the cycle):

WSGI ASGI

Request class

WSGIRequest, reading environ.

ASGIRequest, reading scope and a spooled body file.

Body handling

The server streams the body; Django reads it lazily when request.body, request.POST or request.read() is used.

Django buffers the body before calling the middleware (a 2.5 MiB threshold decides memory versus disk).

Client disconnects

Not visible to the view; the server simply fails to write.

Cancels the view’s task with asyncio.CancelledError (5.0+).

request_started / request_finished

Sent with send(), before the request object is built.

Sent with asend() (5.0+) after the body has been read; receivers may be sync or async.

StreamingHttpResponse content

Must be a synchronous iterator.

Should be an asynchronous iterator (4.2+); a sync iterator is consumed fully, with a warning.

Multiple Cookie headers (HTTP/2)

Handled by the server.

Supported since 6.0.

Middleware chain

Built with is_async=False.

Built with is_async=True; sync-only middleware is wrapped.

Source: Django: StreamingHttpResponse objects and Django 5.0 release notes

Signals around a request

Three signals in django.core.signals frame the cycle:

Signal When it is sent

request_started

By the handler, before the HttpRequest is built. Arguments: sender (the handler class) and environ (WSGI) or scope (ASGI).

request_finished

When the response has been delivered and response.close() runs. Arguments: sender (the handler class).

got_request_exception

Whenever an exception reaches Django’s exception-to-response conversion and will become a 500 (and when an error view itself fails). Arguments: sender (always None) and request.

Django itself listens: the database layer connects reset_queries and close_old_connections to request_started and close_old_connections to request_finished, which is how CONN_MAX_AGE is enforced, and the URL machinery resets the thread’s URLconf (set_urlconf(None)) on request_finished. The test below connects two receivers and records the order around a hand-driven WSGI call:

catalog/tests.py (HandlerTests, signals)
from django.core import signals


class HandlerTests(SimpleTestCase):  # the same class again
    def test_signals_around_one_request(self):
        events = []

        def started(sender, **kwargs):
            events.append(("request_started", sender.__name__))

        def finished(sender, **kwargs):
            events.append(("request_finished", sender.__name__))

        environ = {}
        setup_testing_defaults(environ)
        environ.update(PATH_INFO="/hello/", HTTP_HOST="localhost")
        signals.request_started.connect(started)
        signals.request_finished.connect(finished)
        try:
            result = WSGIHandler()(environ, lambda status, headers: None)
            events.append(("response returned to the server", ""))
            result.close()  # the WSGI server calls close() when it has sent the body
        finally:
            signals.request_started.disconnect(started)
            signals.request_finished.disconnect(finished)
        self.assertEqual(
            events,
            [
                ("request_started", "WSGIHandler"),
                ("response returned to the server", ""),
                ("request_finished", "WSGIHandler"),
            ],
        )

Two practical consequences follow. First, request_finished fires when the server closes the response, which for a streaming response is after the last chunk, not when the view returns. Second, the official signals reference names the sender class WsgiHandler; the real class is WSGIHandler, which is what the receiver above printed.

Source: Django: request_started, request_finished and got_request_exception

The middleware chain

Middleware is the first and the last code your project runs for a request. Django builds the chain once, when the handler is created: BaseHandler.load_middleware() walks settings.MIDDLEWARE in reverse, calls each middleware factory with a get_response callable (the layer that was just built, starting from the handler’s own _get_response), and wraps every layer in an exception-to-response converter. The outermost layer ends up in the handler’s _middleware_chain, and get_response(request) simply calls it. A factory is any callable that takes get_response and returns a callable that takes a request and returns a response, either a function or a class with __init__(get_response) and __call__(request). Because the chain is built once, __init__() (or the body of a function factory) runs once per process, not per request.

Phase Order and rule

Request ("before" code)

MIDDLEWARE order, top-down: each __call__() runs its code, then calls get_response.

process_view(request, view_func, view_args, view_kwargs)

MIDDLEWARE order, top-down, after URL resolution, just before the view. Return None to continue or a response to skip the view.

View

Called with the request and the URL’s arguments.

process_template_response(request, response)

Reverse order (innermost first), only if the response has a render() method. Must return a response with render().

process_exception(request, exception)

Reverse order (innermost first), only for exceptions raised by the view or by render(). Return None to pass the exception on or a response to stop.

Response ("after" code)

Reverse order, bottom-up: the same layers that saw the request see the response.

The three process_* hooks are optional extras on a class-based middleware; they are what the figure at the top of this page draws inside the chain. Writing each kind of middleware, the full list of built-in classes and their ordering rules are on the Middleware page; this page uses just enough middleware to show the cycle.

The default stack

startproject generates this MIDDLEWARE; each entry has a role in the cycle:

Middleware What it does in the cycle

SecurityMiddleware

Optional HTTPS redirect (before the view), security headers such as HSTS and X-Content-Type-Options (on the way out).

SessionMiddleware

Attaches request.session lazily on the way in; saves it and sets the session cookie on the way out.

CommonMiddleware

Rejects DISALLOWED_USER_AGENTS, optional PREPEND_WWW; on the way out turns a 404 into a redirect when APPEND_SLASH is true and the same path with a trailing slash resolves, and sets Content-Length on non-streaming responses.

CsrfViewMiddleware

In process_view(): rejects unsafe-method requests without a valid CSRF token with a 403 before the view runs; sets the CSRF cookie on the way out.

AuthenticationMiddleware

Attaches request.user (a lazy object) and request.auser(). Needs the session, so it comes after SessionMiddleware.

MessageMiddleware

Attaches request._messages; stores pending messages in the session or a cookie on the way out.

XFrameOptionsMiddleware

Adds X-Frame-Options on the way out.

The order is not decoration: AuthenticationMiddleware reads the session, so moving it above SessionMiddleware breaks it, and a middleware that wants to wrap everything (timing, request IDs, logging) goes first, while one that needs request.user goes after AuthenticationMiddleware.

Source: Django: Middleware reference and Django: Activating middleware

Watching the chain work

A middleware that records every hook it receives makes the order visible. Because two instances of one class cannot be given different arguments (Django instantiates with only get_response), the example uses two subclasses that differ in their name:

catalog/middleware.py (tracing middleware)
from django.http import HttpResponse

TRACE: list[str] = []


class TraceMiddleware:
    """Records every hook Django calls, in order."""

    name = "trace"

    def __init__(self, get_response):
        self.get_response = get_response  # called once, at server start-up

    def __call__(self, request):
        TRACE.append(f"{self.name}: before get_response")
        response = self.get_response(request)
        TRACE.append(f"{self.name}: after get_response -> {response.status_code}")
        return response

    def process_view(self, request, view_func, view_args, view_kwargs):
        TRACE.append(f"{self.name}: process_view({view_func.__name__})")
        return None  # None means "carry on"

    def process_template_response(self, request, response):
        TRACE.append(f"{self.name}: process_template_response")
        return response

    def process_exception(self, request, exception):
        TRACE.append(f"{self.name}: process_exception({type(exception).__name__})")
        return None


class OuterTrace(TraceMiddleware):
    name = "outer"


class InnerTrace(TraceMiddleware):
    name = "inner"

TRACE is a module-level list only because the example is a demonstration; real middleware must not keep per-request state in module or instance attributes, because one instance serves every request of the process, concurrently. A small script drives the test client through a chain of just those two classes and prints the trace (the test client builds the same handler chain, with DEBUG = False so the error views are the production ones):

--- 404 raised by URL resolution: GET /nowhere/ -> 404
    outer: before get_response
    inner: before get_response
    inner: after get_response -> 404
    outer: after get_response -> 404

Four facts the trace proves, each of which surprises someone:

  • Both layers' "before" code runs before any process_view(): the view hooks belong to the innermost step, after URL resolution, not to each layer’s own turn.

  • process_view() runs top-down, but process_exception() (and process_template_response()) run bottom-up.

  • The response of a failing view, a 500 here, is an ordinary response when it passes the "after" code of each layer. Neither layer needed a try/except.

  • A URL that matches no pattern never reaches process_view() or process_exception(): resolution raises Resolver404 before either step, and the converter turns it into a 404 response (see URL resolution). A Http404 raised inside a view is different: it passes through process_exception() like any other exception, as the next test shows.

Short-circuiting and rescuing

A layer may answer without calling get_response. Nothing inside it, the view included, ever sees the request, but the response still travels back out through the layers above it. The next middleware returns 503 for requests carrying a maintenance header, and the RescueMiddleware shows a process_exception() that returns a response for one exception type; both live in catalog/middleware.py beside the tracing classes:

catalog/middleware.py (short-circuit and rescue)
class MaintenanceGate:
    """Short-circuits: answers 503 without ever calling get_response."""

    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        if request.headers.get("X-Maintenance") == "on":
            TRACE.append("gate: short-circuit 503")
            return HttpResponse("Back soon", status=503, headers={"Retry-After": "120"})
        return self.get_response(request)


class RescueMiddleware(TraceMiddleware):
    """process_exception that turns one exception type into a response."""

    name = "rescue"

    def process_exception(self, request, exception):
        super().process_exception(request, exception)
        if isinstance(exception, LookupError):
            return HttpResponse("rescued: " + str(exception), status=422)
        return None

Exceptions are converted between layers

Each layer is wrapped by convert_exception_to_response(). When a view or a middleware raises, the wrapper turns the exception into a response before the next layer up sees anything. Every middleware therefore always gets a response back from get_response, and never needs its own try/except around it. The official documentation puts it this way: even if the very next middleware raises Http404, your middleware will receive a response with status_code 404. Two corollaries:

  • process_exception() is not a general error hook. It sees only exceptions raised by the view or by a TemplateResponse’s `render(); an exception raised by another middleware is converted straight to a response.

  • Setting DEBUG_PROPAGATE_EXCEPTIONS to True stops the conversion of exceptions that would become a 500: they propagate out of the handler to the server (the test test_debug_propagate_exceptions_skips_the_500_page below shows it). It is a debugging aid for servers that have their own error pages, not a production switch. The official text says it skips "this conversion", but in Django 6.1.1 the 4xx conversions (Http404, PermissionDenied, BadRequest, SuspiciousOperation) still happen.

The full set of conversions is the subject of Exceptions and error views.

Middleware in sync and async mode

A middleware declares which modes it supports with the class or function attributes sync_capable (default True) and async_capable (default False). When the handler builds the chain it compares each layer’s mode with the mode of the layer below it and, if they differ, wraps the callable with asgiref’s `sync_to_async() or async_to_sync(). The adaptation costs a thread hop, which is why a single synchronous third-party middleware makes an ASGI deployment slower than it should be. A function middleware that supports both modes uses the sync_and_async_middleware decorator and checks the mode of get_response once, at start-up:

catalog/middleware.py (a middleware for both modes)
from inspect import iscoroutinefunction

from django.utils.decorators import sync_and_async_middleware


@sync_and_async_middleware
def timing_middleware(get_response):
    """Function middleware that adapts to whichever mode it is given."""
    import time

    if iscoroutinefunction(get_response):

        async def middleware(request):
            start = time.perf_counter()
            response = await get_response(request)
            response.headers["X-Elapsed-ms"] = f"{(time.perf_counter() - start) * 1000:.1f}"
            return response

    else:

        def middleware(request):
            start = time.perf_counter()
            response = get_response(request)
            response.headers["X-Elapsed-ms"] = f"{(time.perf_counter() - start) * 1000:.1f}"
            return response

    return middleware

URL resolution

At the centre of the chain, BaseHandler.resolve_request() decides which view will run:

  1. If the request has a urlconf attribute (set by a middleware), that module is the root URLconf; otherwise ROOT_URLCONF is used. set_urlconf() records the choice for the current thread (so reverse() and {% url %} agree with it), and request_finished resets it.

  2. The resolver matches request.path_info (the path without the script prefix, and without the query string) against each entry of urlpatterns, in order, and stops at the first match. include() hands the rest of the path to a nested list.

  3. The result is a ResolverMatch, stored in request.resolver_match and unpacked into the view, its positional arguments and its keyword arguments.

  4. If nothing matches, Resolver404 (a subclass of Http404) is raised.

The ResolverMatch object is what a view or a template gets when it asks "which route am I?":

Attribute Meaning

func

The view callable; for a class-based view, the function returned by as_view() (which has a view_class attribute).

args, kwargs

The arguments that will be passed to the view: positional groups, or named parts. kwargs also contains any extra dictionary given to path().

captured_kwargs, extra_kwargs

The two halves of kwargs: values captured from the URL, and the extra dictionary from path(…​, kwargs={…​}).

url_name, route

The pattern’s name= and its route string, for example books/<int:pk>/inspect/.

app_name, app_names, namespace, namespaces

The application and instance namespaces, joined with : or as lists.

view_name

The namespaced name used with reverse(), such as catalog:book-detail, or the dotted path of the view when there is no name=.

tried

The patterns tried before a match was found or the list was exhausted (useful in debugging).

resolve("/path/") returns the same object without a request, and reverse() goes the other way. The test below resolves a path, checks every attribute that matters, and goes through the whole stack with the test client:

Switching the URLconf per request

Because the handler looks for request.urlconf before resolving, a middleware can route different hosts to different URL trees; setting it to None returns to ROOT_URLCONF. This is how multi-tenant or api. subdomain setups are built without a second project:

catalog/middleware.py (HostUrlconfMiddleware)
class HostUrlconfMiddleware:
    """Serve a different URLconf for api.* hosts (sets request.urlconf)."""

    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        if request.get_host().split(":")[0].startswith("api."):
            request.urlconf = "catalog.api_urls"
        return self.get_response(request)

Calling the view

With a ResolverMatch in hand, _get_response() runs the process_view() hooks and then calls the view:

response = view(request, *args, **kwargs)

args are the unnamed groups of a re_path() pattern (used only when the pattern has no named groups); kwargs are the named parts, such as pk, overridden by the optional kwargs dictionary given to path(). A view may be a function, the callable returned by View.as_view(), or any callable that takes a request; the sections of this page after this one use plain functions, and Function-Based Views & Shortcuts covers the conveniences around them. Before the call the handler does two more things.

Transactions. If ATOMIC_REQUESTS is True for a database alias in DATABASES, the view is wrapped in transaction.atomic(using=alias), unless the view is decorated with @transaction.non_atomic_requests. That wrapping is only possible for synchronous views: with an async def view the handler raises RuntimeError: You cannot use ATOMIC_REQUESTS with async views. The wrapping covers the view only, not the middleware around it and not template rendering (the transaction commits when the view returns, before a TemplateResponse renders).

Async views. A view that is a coroutine function is run through async_to_sync() in WSGI mode and awaited natively in ASGI mode; a synchronous view in ASGI mode runs in a thread (sync_to_async(thread_sensitive=True)). Both are described in Sync and async through the cycle.

The contract. A view must return an HttpResponse (or a subclass, or an object with the same interface such as StreamingHttpResponse or TemplateResponse). Two mistakes are caught by the handler with a clear message:

catalog/views.py (two view mistakes)

    pass  # forgot the return statement


def forgot_await(request):
    return async_hello(request)  # a coroutine object, never awaited

The HttpRequest object

The handler builds one HttpRequest per request (a WSGIRequest or an ASGIRequest) and every layer after it receives the same object. Treat its attributes as read-only unless the reference says otherwise; middleware may add attributes. The attributes fall in three groups.

method

The HTTP method, always uppercase. Test it with request.method == "POST", never with if request.POST: (a POST can have an empty body).

http or https. Under a TLS-terminating proxy it is correct only if SECURE_PROXY_SSL_HEADER is configured.

The path including or excluding the script prefix (SCRIPT_NAME). URL resolution and most code should use path_info; use path when building links.

Uploaded files, only for a POST whose form uses enctype="multipart/form-data".

A dictionary of cookie names to string values.

Reading the body

request.POST is filled only for application/x-www-form-urlencoded and multipart/form-data bodies. JSON, XML and any other format arrive in request.body and must be parsed by the view. import json

from django.core.exceptions import BadRequest
from django.http import HttpResponseNotAllowed, JsonResponse


def attributes(request):
    """Show request.body, request.POST and the file-like interface."""
    if request.method != "POST":

    return JsonResponse({"form": request.POST.dict()})

Content negotiation: accepts() and get_preferred_type()

Browsers, curl and API clients tell the server which representations they can handle in the Accept header. Two request methods read it:

  • request.accepts("application/json") returns True if the header matches that type (since 3.1). Most browsers send Accept: / by default, in which case accepts() is True for every type, so it answers "may I send this?", not "which is best?".

  • request.get_preferred_type(["text/html", "application/json"]) returns the best of the candidates according to the header’s q weights and parameters, or None if none is acceptable (since 5.2). With / it returns the first candidate, so list your default first.

The negotiate view answers HTML, JSON or 406 Not Acceptable. Because the response now depends on a request header, it declares that with Vary: Accept (the vary_on_headers decorator adds it) so that caches keep one entry per representation:

catalog/views.py (negotiate)
from http import HTTPStatus

from django.http import HttpResponse, JsonResponse
from django.views.decorators.vary import vary_on_headers


@vary_on_headers("Accept")
def negotiate(request):
    best = request.get_preferred_type(["text/html", "application/json"])
    if best is None:
        return HttpResponse(status=HTTPStatus.NOT_ACCEPTABLE)
    if best == "application/json":
        return JsonResponse({"books": ["Dune", "Emma"]})
    return HttpResponse("<ul><li>Dune</li><li>Emma</li></ul>")

The HttpResponse object

Unlike the request, the response is your responsibility: a view builds it and returns it. django.http.HttpResponse is the workhorse; it holds the body and the headers in memory, which also lets middleware read and change them.

HttpResponse(content=b"", content_type=None, status=200, reason=None, charset=None, headers=None)

The body as bytes, and as a decoded string (text was added in 5.2).

The status; the reason phrase follows status_code unless set explicitly.

Cookie helpers, described below.

Cookies

Cookies are response state, not request state: the server sets them in Set-Cookie headers and the browser returns them in Cookie. set_cookie(key, value="", max_age=None, expires=None, path="/", domain=None, secure=False, httponly=False, samesite=None) takes max_age as seconds or a timedelta (a timedelta is accepted since 4.1) and computes expires for you. Use secure=True so the cookie is sent only over HTTPS, httponly=True so JavaScript cannot read it, and samesite="Lax" or "Strict" as defence in depth against cross-site requests (not a replacement for CSRF protection; samesite="None" is the explicit "send always" form). delete_cookie(key, path="/", domain=None, samesite=None) must repeat the path and domain used to set the cookie. Browsers guarantee about 4096 bytes per cookie; Django does not warn if you exceed it. set_signed_cookie(key, value, salt="", …​) adds a signature, and request.get_signed_cookie(key, salt=…​) verifies it: the signature protects against tampering, but the value is still readable by the client, so never put secrets in it.

Streaming and file responses in the cycle

StreamingHttpResponse and its subclass FileResponse send their body in pieces instead of building it in memory. They change the cycle in four ways: they have no content (middleware must test response.streaming and wrap streaming_content instead of reading it; wrappers must match the iterator type, which response.is_async reveals); middleware that needs the whole body, such as CommonMiddleware’s `Content-Length or ConditionalGetMiddleware’s `ETag, skips them; request_finished fires only when the server has sent the last chunk; and under WSGI a streaming response ties up a worker for its whole duration. Under ASGI the iterator should be asynchronous (supported since 4.2); a synchronous one is consumed completely, with a warning, which defeats streaming. If a client disconnects mid-stream under ASGI, Django cancels the coroutine, and you may catch asyncio.CancelledError to release resources (re-raise it afterwards). Building such responses in practice (CSV exports, PDFs, server-sent events) belongs to the Responses, Streaming, CSV & PDF page of this section.

Custom error views

handler400, handler403, handler404 and handler500 are plain module-level variables in the root URLconf (setting them in an included URLconf has no effect). Each holds a callable or its dotted path. handler404, handler403 and handler400 receive (request, exception), and handler500 receives only (request). The default 404.html, 500.html, 403.html and 400.html templates (top level of the template tree) are what the built-in views render; a custom view replaces them when you need to vary the output, here by the Accept header so API clients get JSON and browsers get HTML:

from django.http import HttpResponse, JsonResponse

    if request.accepts("application/json") and not request.accepts("text/html"):
        return JsonResponse({"error": "not_found", "path": request.path}, status=404)
    return HttpResponse("<h1>Sorry, nothing here</h1>", status=404)


def server_error(request):
    return HttpResponse("<h1>Something broke on our side</h1>", status=500)

Sync and async through the cycle

One chain serves both modes, and Django adapts whatever does not match. Reading django/core/handlers/base.py (6.1.1) gives the rules:

Practical consequences:

  • A single synchronous middleware in the stack makes every request pay a thread hop under ASGI, hence the advice to check the django.request DEBUG log as shown earlier. The bundled middleware supports both modes.

  • Do not call blocking code in an async def view. The ORM’s synchronous methods are async-unsafe: Django raises SynchronousOnlyOperation instead of risking corruption, so use the a-prefixed ORM methods or sync_to_async().

  • request.user is a lazy object that touches the database; in an async view use await request.auser() (5.0+).

  • With a purely synchronous codebase there is no need to switch to ASGI; async pays off when requests spend their time waiting (external APIs, streaming, long polling, WebSockets) and many must be open at once.

Common pitfalls, collected from the sections above:

  • Using request.POST to detect a form submission instead of request.method == "POST".

  • Reading request.body after the form parser, or request.POST in a middleware, and then wondering why uploads or later reads fail.

  • Forgetting that process_exception() does not see Http404 raised by URL resolution or errors raised by other middleware.

  • Keeping per-request state on self in a middleware; one instance serves all requests concurrently.

  • Expecting RequestFactory to run middleware or URL resolution (it runs neither), or the test client to enforce CSRF (it does not unless asked).

  • Testing error pages with DEBUG = True: the technical pages replace your handlers. The test runner sets DEBUG = False for you; runserver does not.

  • Trusting X-Forwarded-* headers without USE_X_FORWARDED_HOST, SECURE_PROXY_SSL_HEADER and a proxy that overwrites them, so request.scheme, get_host() and build_absolute_uri() are wrong behind TLS termination.

  • A view that returns nothing, or returns an un-awaited coroutine: both fail with a ValueError naming the view.

  • Using ATOMIC_REQUESTS = True together with async views.

  • Forgetting that a POST to a URL without the trailing slash cannot be redirected by APPEND_SLASH without losing the body.

Where the books are outdated

The books listed in the section bibliography were written for Django 1.11 to 3.x and describe the same cycle, but several APIs on the way have changed. When following a book, translate these:

  • Old-style middleware. MIDDLEWARE_CLASSES with process_request() and process_response() methods was replaced by MIDDLEWARE and get_response callables in Django 1.10; support for the old setting was removed in 2.0. Old middleware classes can be adapted with django.utils.deprecation.MiddlewareMixin, whose __init__() requires the get_response argument since 4.0, but new code should use the factory pattern shown above. The old semantics also differ: under MIDDLEWARE every layer that saw the request sees the response and a failing layer cannot skip the others.

  • request.is_ajax(). Deprecated in 3.1 and removed in 4.0, because it relied on a non-standard header. Use request.headers, request.accepts() (3.1) or get_preferred_type() (5.2).

  • request.REQUEST. Gone since 1.9; use request.GET or request.POST explicitly.

  • url() and django.core.urlresolvers. django.conf.urls.url() was removed in 4.0 (use path() or re_path()); django.core.urlresolvers was removed in 2.0 (use django.urls).

  • render_to_response(). Removed in 3.0; use render() or TemplateResponse.

  • HttpResponse(mimetype=…​). The mimetype argument is long gone (1.7); the argument is content_type.

  • Headers. Books set response["Header"] or read request.META["HTTP_X"]. Both still work, but response.headers (3.2) and request.headers (2.2) are the supported, case-insensitive interfaces.

  • WSGI only. Books describe a synchronous, WSGI-only framework. ASGI arrived in 3.0, async views and middleware in 3.1, the async ORM in 4.1, async streaming responses in 4.2, and client-disconnect handling in 5.0; the Channels-only advice for anything long-lived is dated, though Channels remains right for WebSockets.

  • Error handlers. The current signatures are handler404(request, exception), handler403(request, exception), handler400(request, exception) and handler500(request); older code that defines handler404(request) must accept the extra exception argument.

  • Signed cookies. Examples that use the signing module or set_signed_cookie() are correct in outline, but the salt derivation changed in 6.1 and the compatibility switch is deprecated.
