Channels & WebSockets

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Django 6.1 (6.1.1 on PyPI, released 2026-09-02; 6.1.2 is scheduled for 2026-10-06), Python 3.12-3.14, Channels 4.3.2 (2025-11-20), channels_redis 4.3.0 (2025-07-22) and Daphne 4.2.3 (2026-07-21), all checked on 2026-10-03. Channels 4.3.2 lists Django 6.0 as its newest confirmed version and has no Django 6.1 classifier yet; it installed and ran under Django 6.1.1 in the scratch project used for this page, and it also supports the 5.2 LTS (official since Channels 4.2.1), so nothing below changes between 5.2 and 6.1. Every listing was run in that scratch project on Python 3.13 and Django 6.1.1 with SQLite: manage.py check (also under -W error) passes, the 23 tests shown or described pass with Django’s test runner, and the same asgi.py was served by Daphne 4.2.3 (and, for one echo message, by Uvicorn) and exercised with a real WebSocket client, curl and Node’s built-in WebSocket. No Redis server was available: every test uses InMemoryChannelLayer, and the channels_redis configuration was only instantiated (no connection was opened), so the Redis behaviour described here comes from the Channels and channels_redis documentation and source, not from a run.

Plain Django answers one HTTP request with one response and forgets the connection. Some features need the opposite: a chat room, a live "new review" feed, a progress bar, a dashboard that updates by itself — a connection that stays open for minutes or hours and carries messages in both directions. Django itself deliberately does not speak WebSocket: its ASGI handler refuses everything except HTTP (it raises ValueError: Django can only handle ASGI/HTTP connections). Channels is the official Django project that fills that gap. It adds routing by connection type, consumers (the long-lived counterpart of a view), a channel layer that lets one consumer talk to others, and authentication, sessions and origin checks that reuse Django’s own. This page covers all of it, using the Bookshelf application that grows across this section: a per-book discussion room, a staff notification stream and a live review feed.

Where Channels sits in the request cycle

A normal request travels through the middleware chain to a view and back (the whole path is in The Request/Response Cycle). A WebSocket does not: the protocol server (Daphne, Uvicorn, …​) accepts the TCP connection, reads the HTTP upgrade request, and calls your ASGI application once for the whole connection. ASGI describes that call as application(scope, receive, send): a scope dict (what this connection is: its type, path, headers, query_string, client, subprotocols, …​) and two awaitables to receive events from the client and send events back. For a WebSocket the events are websocket.connect, websocket.receive, websocket.disconnect (from the client) and websocket.accept, websocket.send, websocket.close (from you). One scope is one connection, and one consumer instance serves it for its entire life — which is why a consumer can keep per-connection state on self, and why Django’s per-request middleware does not run: Channels brings its own middleware (sessions, authentication, origin checks) that works on the scope.

Plain HTTP can use the same door. With the router in asgi.py: ProtocolTypeRouter, URLRouter and as_asgi() the "http" entry sends ordinary requests to Django’s own ASGI handler (so views, middleware and templates are unchanged) and can send a few paths to Channels consumers, such as a server-sent-events stream.

Installing and configuring Channels

Install Channels with the Daphne extra, plus the Redis channel layer for production:

python -m pip install -U 'channels[daphne]' channels-redis

The daphne extra pulls in daphne>=4.0.0. Daphne is optional since Channels 4: without the extra you install any other ASGI server yourself (Other ASGI servers). channels_redis is a separate package with its own releases. Then three settings:

# config/settings.py (excerpt)
INSTALLED_APPS = [
    "daphne",  # must come before django.contrib.staticfiles
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "channels",  # optional: only needed for the runworker command
    "catalog",
]

ALLOWED_HOSTS = ["localhost", "127.0.0.1"]  # also drives AllowedHostsOriginValidator

ASGI_APPLICATION = "config.asgi.application"

CHANNEL_LAYERS = {
    "default": {"BACKEND": "channels.layers.InMemoryChannelLayer"},
}

  • "daphne" in INSTALLED_APPS replaces runserver with an ASGI version (so manage.py runserver serves WebSockets in development). It must precede django.contrib.staticfiles; otherwise the check framework fails with daphne.E001: Daphne must be listed before django.contrib.staticfiles in INSTALLED_APPS (reproduced on 2026-10-03). Any other app that replaces runserver (the documentation names whitenoise.runserver_nostatic) conflicts for the same reason: keep daphne at the top.

  • "channels" in INSTALLED_APPS is optional in Channels 4: it only registers the runworker command (Background workers). Channels 2 required it for runserver; that role moved to Daphne.

  • ASGI_APPLICATION is the dotted path of the root application. The daphne command and other ASGI servers take the module path on their command line and ignore it, but Daphne’s runserver and runworker read it: without it runserver stops with CommandError: You have not set ASGI_APPLICATION, which is needed to run the server.

  • CHANNEL_LAYERS is optional. Leave it unset (or {}) if you only need independent WebSockets; consumers then have no channel_layer, and a groups attribute raises InvalidChannelLayerError on connect (Channel layers and groups).

  • ALLOWED_HOSTS is Django’s own setting; AllowedHostsOriginValidator reuses it (Origin validation).

Production values (the Redis host, a sharing key) come from the environment, never from the repository; the switch is shown in [redis-config].

asgi.py: ProtocolTypeRouter, URLRouter and as_asgi()

startproject already wrote config/asgi.py; Channels asks you to extend it, not replace the Django part. The root object is a router — itself an ASGI application — that looks at scope["type"] and hands the connection to the right sub-application.

# config/asgi.py
"""ASGI entry point: HTTP goes to Django, WebSockets go to Channels."""

import os

from django.core.asgi import get_asgi_application

os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings")

# Initialise Django (and the app registry) before importing anything that
# touches models: consumers, auth middleware and the routing module.
django_asgi_app = get_asgi_application()

from channels.auth import AuthMiddlewareStack  # noqa: E402
from channels.routing import ProtocolTypeRouter, URLRouter  # noqa: E402
from channels.security.websocket import AllowedHostsOriginValidator  # noqa: E402
from django.urls import re_path  # noqa: E402

from catalog import routing  # noqa: E402
from catalog.middleware import TicketAuthMiddleware  # noqa: E402

application = ProtocolTypeRouter(
    {
        # long-lived HTTP endpoints first, everything else falls through to Django
        "http": URLRouter(
            [
                *routing.http_urlpatterns,
                re_path(r"", django_asgi_app),
            ]
        ),
        "websocket": AllowedHostsOriginValidator(
            AuthMiddlewareStack(
                TicketAuthMiddleware(URLRouter(routing.websocket_urlpatterns))
            )
        ),
    }
)

Source: Routing and How to deploy with ASGI

Four details in that file are not decoration.

  • get_asgi_application() runs first. It calls django.setup(), which populates the app registry. Anything that imports a model (consumers, AuthMiddlewareStack, the routing module) must be imported after it, which is why those imports sit below the call with noqa: E402. Importing them earlier fails with AppRegistryNotReady: Apps aren’t loaded yet. (or, when the settings module is not even set, the ImproperlyConfigured error the Channels troubleshooting page quotes); that page shows the same ordering.

  • The "http" key is explicit. In Channels 2 an unrouted HTTP request went to a bundled handler; since Channels 4.0 you must route it yourself, normally to get_asgi_application(). Without the key, HTTP requests are refused with ValueError: No application configured for scope type 'http'.

  • as_asgi() is the consumer’s as_view(). A consumer class is not itself an ASGI callable you can route to. Consumer.as_asgi(*initkwargs) returns one that builds a *new consumer instance for every scope (every connection), passing initkwargs to the constructor, exactly like View.as_view() does per request.

  • The "websocket" stack is wrapped inside-out: origin check first (so a hostile page never reaches your code), then cookies, session and user, then your own middleware, then URL routing. Origin validation and Authentication and sessions explain each layer.

URLRouter

URLRouter takes a list of django.urls.path() or re_path() entries (not url(), which Django 4.0 removed), matched against scope["path"] the way the URL dispatcher matches a request (see URLs & Routing). Captured values arrive in the scope:

# catalog/routing.py
from django.urls import path

from . import consumers

websocket_urlpatterns = [
    path("ws/echo/", consumers.EchoConsumer.as_asgi()),
    path("ws/books/<int:book_id>/discussion/", consumers.DiscussionConsumer.as_asgi()),
    path("ws/notifications/", consumers.NotificationConsumer.as_asgi()),
]

http_urlpatterns = [
    path("feed/reviews/", consumers.ReviewFeedConsumer.as_asgi()),
]

Inside the consumer, self.scope["url_route"]["kwargs"]["book_id"] is an int thanks to the <int:book_id> converter; args holds positional groups from re_path. Notes from the documentation and the source:

  • Named and unnamed regex groups cannot be mixed: positional groups are discarded as soon as a named one matches.

  • include() is not supported: use nested URLRouter instances. Nesting URLRouter`s under `path() routes while wrapping the inner router in extra middleware is a documented gotcha (Channels issue 1428); put the middleware around the outermost router instead.

  • URLRouter matches the path only, not the query string and not the method. The HTTP router in asgi.py lists the long-lived paths first and uses re_path(r"", django_asgi_app) as a match-everything last entry, the pattern the documentation recommends for splitting HTTP between consumers and Django.

  • No match is a server error, not a 404. The outermost URLRouter raises ValueError: No route found for path …​; on a WebSocket the handshake fails with HTTP 500 and the traceback goes to the server log (observed with Daphne). Add a catch-all consumer that closes the socket if you want a quiet refusal.

  • When the server sets a root_path (a Django app mounted under a prefix), the outermost URLRouter strips it before matching (fixed in Channels 4.1).

ProtocolTypeRouter and ChannelNameRouter

ProtocolTypeRouter maps scope["type"] to an application: "http", "websocket" and, for workers, "channel" (Background workers). A scope type with no entry raises ValueError. ChannelNameRouter is the third router: it dispatches channel-type scopes by scope["channel"] and exists only for background workers. All three are plain classes you could write yourself; the documentation recommends a ProtocolTypeRouter as the root, with protocol-specific routing below it.

Routers work on the scope, not on events: you choose one consumer for the whole connection, and cannot spread one connection’s events over several consumers.

Source: ProtocolTypeRouter, URLRouter and ChannelNameRouter

Consumers

A consumer is the unit of application code in Channels: the long-lived cousin of a view. It is a class whose instance serves exactly one connection, from the first event to the last, and whose methods are called when events happen — you never write an event loop. Channels ships two base classes and a family of ready-made WebSocket and HTTP consumers built on them.

The model: events, handler names and the scope

Both base classes (channels.consumer.SyncConsumer and channels.consumer.AsyncConsumer) work the same way. Every event is a dict with a "type"; Channels replaces each . in the type with _ and calls the method of that name. A websocket.connect event calls websocket_connect(event), a channel-layer event of type chat.join calls chat_join. Besides self.send(event) (to the client or server) the instance gets:

Attribute Meaning

self.scope

The connection’s scope dict: type, path, query_string, headers (raw byte pairs), subprotocols, client, plus whatever middleware and routers added: url_route, cookies, session, user.

self.channel_layer

The channel layer for channel_layer_alias (default "default"), or None when CHANNEL_LAYERS is empty.

self.channel_name

A unique name for this connection’s mailbox on the layer, generated when the consumer starts.

The raw flavours are the "hello world" of the model. They also show the part the generic consumers do for you: after websocket.disconnect the consumer must raise channels.exceptions.StopConsumer, or the server waits for the application to exit (Daphne’s --application-close-timeout, 10 seconds by default) and then kills it with a warning.

# catalog/lowlevel.py
from channels.consumer import AsyncConsumer, SyncConsumer
from channels.exceptions import StopConsumer


class SyncEcho(SyncConsumer):
    """Raw ASGI events, handled in a thread-pool thread."""

    def websocket_connect(self, event):
        self.send({"type": "websocket.accept"})

    def websocket_receive(self, event):
        self.send({"type": "websocket.send", "text": event["text"]})

    def websocket_disconnect(self, event):
        raise StopConsumer()  # tell the server the application is finished


class AsyncEcho(AsyncConsumer):
    """The same thing with coroutines: every handler and self.send is async."""

    async def websocket_connect(self, event):
        await self.send({"type": "websocket.accept"})

    async def websocket_receive(self, event):
        await self.send({"type": "websocket.send", "text": event["text"]})

    async def websocket_disconnect(self, event):
        raise StopConsumer()

Source: Consumers: basic layout and Closing consumers

A handler name with no method is an error, not a silent ignore: a typo in a group event type ("chat.mesage") raises ValueError: No handler for message type chat.mesage inside the consumer, which ends the connection. The same applies to an event type that starts with an underscore (ValueError: Malformed type in message (leading underscore)). Prefix your own types (discussion., notify) so they cannot collide with the protocol’s (websocket., http.).

Sync or async?

The two classes differ in where your code runs:

  • AsyncConsumer: every handler is a coroutine and runs on the event loop. A blocking call (a synchronous ORM query, requests.get(), time.sleep()) stalls every connection served by that process. Inside, use await and async-native libraries, the async ORM (aget(), acreate(), aexists(), async for) or database_sync_to_async (Database access from consumers).

  • SyncConsumer: Channels runs the whole handler in a thread-pool thread (using database_sync_to_async, so database connections are closed afterwards) and bridges self.send back to the loop. You may call the ORM and any blocking code freely; the cost is one thread per concurrently running handler, and one database connection per thread.

The Channels documentation still recommends sync consumers by default and async ones where you know async will help. The async ORM (Django 4.1, extended in 4.2; the Channels documentation reflects it since 4.2.0) makes the async side far more practical than when that advice was written. A workable rule: use async for connections that mostly wait and forward (chat, feeds, presence, SSE), and sync for handlers that are mainly ORM-heavy business logic or call blocking libraries. Never mix: all handlers of one consumer must be the same kind, including channel-layer event handlers.

The general async/sync boundary in Django (sync_to_async, async_to_sync, SynchronousOnlyOperation) is covered in Async Support and, for the language side, in Concurrency and Async.

Generic WebSocket consumers

Like Django’s generic views, Channels ships consumers that wrap the verbose ASGI events. All live in channels.generic.websocket:

Class What it adds

WebsocketConsumer

Synchronous. connect(), receive(text_data=None, bytes_data=None), disconnect(code); helpers accept(), send(), close().

AsyncWebsocketConsumer

The same methods, all async def (await self.accept(), await self.send(…​), await self.close()).

JsonWebsocketConsumer

Synchronous. receive_json(content, **kwargs) gets the decoded object; send_json(content, close=False) encodes it; override the encode_json / decode_json classmethods to change the format.

AsyncJsonWebsocketConsumer

Async variant; note that encode_json and decode_json are coroutine functions here.

The pieces you will use constantly:

  • connect() runs when the browser asks to open the socket. The default accepts every connection (so EchoConsumer.connect below is only there to be explicit). Call self.accept() to accept, self.accept("subprotocol") to choose one of the scope["subprotocols"] the client offered, self.accept(headers=[…​]) (Channels 4.1) to add response headers, or self.close() to refuse. You can raise channels.exceptions.AcceptConnection or DenyConnection from anywhere inside connect (reusable authentication or rate-limit helpers) instead of calling them.

  • receive() gets either text_data or bytes_data per frame, never both; the JSON consumers only accept text and raise ValueError on a binary frame (and on an empty text frame, because the check is if text_data:).

  • send(text_data=None, bytes_data=None, close=False) sends one frame; it raises ValueError unless you pass exactly one kind. close=True (or a code) closes after sending. self.close(code=None, reason=None) closes from the server.

  • disconnect(code) runs when the socket closes for any reason. It may not run on a crash, a power loss or a killed process, so do not rely on it for correctness; the layer’s group_expiry is the safety net for group membership.

  • groups, a class attribute: names of groups to join on connect and leave on disconnect automatically (on both the sync and async consumers). It is static, so it suits "everyone gets this" streams; per-user or per-book groups are managed by hand, as below.

# catalog/consumers.py (excerpt)
class EchoConsumer(WebsocketConsumer):
    """Smallest useful consumer: accept, echo text back."""

    def connect(self):
        self.accept()

    def receive(self, text_data=None, bytes_data=None):
        if text_data is not None:
            self.send(text_data=text_data)

    def disconnect(self, code):
        pass

An async JSON consumer: the discussion room

Now a real one. Readers of a book join a room; every message is validated, saved with the async ORM and broadcast to everyone in the room. The room is a group named after the book, so the consumer needs no knowledge of the other connections.

# catalog/consumers.py (excerpt)
class DiscussionConsumer(AsyncJsonWebsocketConsumer):
    """One group per book; everyone on the page sees every message."""

    MAX_LENGTH = 500

    async def connect(self):
        self.book_id = self.scope["url_route"]["kwargs"]["book_id"]
        self.user = self.scope["user"]
        self.group_name = f"book-{self.book_id}"

        if not self.user.is_authenticated:
            await self.close(code=4401)  # application-defined: "log in first"
            return
        if not await Book.objects.filter(pk=self.book_id).aexists():
            await self.close(code=4404)
            return

        await self.channel_layer.group_add(self.group_name, self.channel_name)
        await self.accept()

    async def disconnect(self, code):
        # connect() may have closed before joining; group_discard is harmless then
        if hasattr(self, "group_name"):
            await self.channel_layer.group_discard(self.group_name, self.channel_name)

    async def receive_json(self, content, **kwargs):
        text = str(content.get("text", "")).strip()
        if not text or len(text) > self.MAX_LENGTH:
            await self.send_json({"error": "text must be 1-500 characters"})
            return
        message = await DiscussionMessage.objects.acreate(
            book_id=self.book_id, author=self.user, text=text
        )
        await self.channel_layer.group_send(
            self.group_name,
            {
                "type": "discussion.message",  # -> discussion_message()
                "id": message.pk,
                "author": self.user.get_username(),
                "text": text,
            },
        )

    async def discussion_message(self, event):
        await self.send_json(
            {"id": event["id"], "author": event["author"], "text": event["text"]}
        )

Walk through the choices, because each one answers a pitfall:

  • connect reads the book id from scope["url_route"] and the user from scope["user"] (Authentication and sessions). Unauthenticated users and unknown books are refused before group_add, so nothing leaks to a stranger. disconnect still runs when connect refused, hence the hasattr guard.

  • The message "type": "discussion.message" is the event sent through the layer: Channels will call discussion_message(self, event) on every consumer in the group, including the sender. That last method turns the event into the frame the browser sees. What travels on the layer and what travels on the socket are two separate formats, and keeping them separate lets you change one without the other.

  • receive_json validates the payload itself. The browser can send anything, so check types and sizes, answer mistakes on the same socket, and never trust a user id or a book id inside the payload when the scope already tells you.

  • The database write uses DiscussionMessage.objects.acreate(…​): a coroutine, safe on the event loop. The event carries the saved row’s id, so every client can de-duplicate.

  • Closing before accepting makes the server answer the upgrade with HTTP 403 (the handshake is refused). The numeric code (4401 and 4404 here are application-defined; RFC 6455 reserves 4000-4999 for private use) is visible to the test communicator but not to a browser, which sees only a failed connection. If the client must tell "log in" from "not found", accept first and close afterwards with the code, which does arrive in the browser’s CloseEvent.

HTTP consumers and server-sent events

channels.generic.http.AsyncHttpConsumer turns an HTTP request into a coroutine you control. Implement handle(self, body) (the whole request body as bytes), then answer with send_response(status, body, headers=…​) or, for streaming, send_headers(status=200, headers=…​) followed by send_body(bytes, more_body=True) calls and a final send_body(bytes). Headers may be a list of byte pairs or a dict, and the server only starts sending after the first send_body. Override disconnect() for cleanup; it also runs on an unclean disconnect.

A server-sent-events feed has to stay open and react to events from the channel layer, which needs one non-obvious step. AsyncHttpConsumer.http_request calls handle() and then raises StopConsumer as soon as handle() returns, ending the consumer. Group events are dispatched one at a time, after the current handler returns, so a feed written as a handle() that sends headers and returns never receives its group events (reproduced with Channels 4.3.2: the consumer was already finished a moment after the first body chunk). The long-poll example in the Channels documentation has that shape; do not copy it for a stream fed by the layer. Override http_request instead and return from it without stopping:

# catalog/consumers.py (excerpt)
class ReviewFeedConsumer(AsyncHttpConsumer):
    """Server-sent events: an HTTP response that stays open and is fed by group events.

    AsyncHttpConsumer.http_request() raises StopConsumer as soon as handle()
    returns, which would end the consumer before any group event arrives. An
    event-driven stream therefore overrides http_request() and returns from it
    without stopping; the consumer then lives until http_disconnect().
    """

    GROUP = "reviews"

    async def http_request(self, message):
        if message.get("more_body"):
            return  # a GET has no body; ignore any further chunks
        await self.channel_layer.group_add(self.GROUP, self.channel_name)
        await self.send_headers(
            headers=[
                (b"Cache-Control", b"no-cache"),
                (b"Content-Type", b"text/event-stream"),
            ]
        )
        # Headers only go out with the first body event; more_body keeps it open.
        await self.send_body(b": connected\n\n", more_body=True)

    async def review_posted(self, event):
        payload = json.dumps({"book": event["book"], "stars": event["stars"]})
        await self.send_body(f"data: {payload}\n\n".encode(), more_body=True)

    async def http_disconnect(self, message):
        await self.channel_layer.group_discard(self.GROUP, self.channel_name)
        await super().http_disconnect(message)

Channel layers and groups

Consumers handle their own connection. To reach another connection — the other readers in a room, one user’s other tabs, a browser whose consumer lives in a different process — they send events through a channel layer: a small message bus with named mailboxes. A layer offers two addressing modes:

  • a channel: one mailbox. Every consumer creates one when it starts (its channel_name); sending to it reaches that single connection. The name is only valid for the lifetime of the connection.

  • a group: a named broadcast list of channels. group_add(group, channel) subscribes a channel, group_discard removes it, group_send(group, event) delivers a copy of the event to every member. A group can neither be listed nor counted: it is a pure broadcast. If you need "who is in the room", keep that data yourself.

The interface is async-only (await layer.send(…​)). Synchronous code wraps each call in async_to_sync. A layer is optional: leave CHANNEL_LAYERS unset and consumers simply have no channel_layer.

Choosing and configuring a layer

Channels bundles channels.layers.InMemoryChannelLayer; the maintained production layers are in the channels_redis package (the documentation calls it the only official, Django-maintained layer supported for production).

Backend Use it for

channels.layers.InMemoryChannelLayer

Tests and a single-process development server. Each process has its own layer, so nothing crosses processes: with two Daphne workers, two browsers can sit in the same "room" and never see each other. Do not use it in production.

channels_redis.core.RedisChannelLayer

Production. The original layer: channels and groups implemented over Redis lists, sorted sets and a Lua script; supports sharding over several Redis hosts, message expiry, capacities and optional encryption.

channels_redis.pubsub.RedisPubSubChannelLayer

Production, newer, built on Redis Pub/Sub. Its README labels it Beta, meaning it may change incompatibly. It can drop messages while the connection to Redis is partitioned; it offers on_disconnect / on_reconnect events so a consumer can re-sync.

The API in four calls

Call Meaning

get_channel_layer(alias="default")

The configured layer (from channels.layers), for use outside consumers; inside a consumer it is self.channel_layer.

await layer.send(channel, event)

Deliver event (a dict with a "type") to one channel. Raises channels.exceptions.ChannelFull when the channel is at capacity.

await layer.group_add(group, channel) / group_discard(group, channel)

Subscribe / unsubscribe a channel to a group.

await layer.group_send(group, event)

Deliver event to every channel in the group. Members whose channel is full are skipped without an error.

await layer.new_channel() / receive(channel) / flush()

Used by consumers and tests: create a channel name, wait for its next event, empty the layer.

Names are validated: channels and groups accept ASCII letters, digits, hyphen, underscore and period only (the documentation lists hyphens and periods; the source also allows underscores), fewer than 100 characters. "book:1", "new books" and a 100-character name raise TypeError, which is why the groups above are book-1 and user-7. Channels 4.2.1 also warns about long group names.

What you send should be a high-level event, not a frame: {"type": "discussion.message", "id": …​, "text": …​}, which each consumer turns into its own socket output. Ids and small values beat whole serialised model instances: the receiving consumer can check permissions and load fresh data.

Delivery guarantees and limits

A channel layer is a low-latency, best-effort bus, not a queue with promises.

  • At most once. A message is delivered to a channel at most once; if the consumer is gone or too slow it is lost. There is no acknowledgement, retry or dead-letter. Anything that must not be lost belongs in the database first, with the event only a hint to refresh (that is why DiscussionConsumer saves the message and then broadcasts it).

  • Messages expire after expiry seconds (60 by default), and a channel holds at most capacity messages (100). A full channel makes send raise ChannelFull, and group_send skips the receiver.

  • No history. A client that reconnects sees nothing from before. Give clients a way to re-sync: an HTTP endpoint for the latest messages, or an id they send on reconnect.

  • Serialisation differs between layers. The in-memory layer deep-copies the dict, so almost anything passes; the Redis layers serialise with msgpack (or JSON) and tuples come back as lists and a datetime raises TypeError (both checked with channels_redis.serializers). Tests on the in-memory layer therefore cannot prove an event is Redis-safe: send only strings, numbers, booleans, None, lists and dicts of those.

  • Group membership expires after group_expiry from the moment of group_add (see the options table), and disconnect() may never run: do not treat a group as proof that a client is connected.

  • Redis is a single point of failure unless you run Sentinel or a managed service; while it is unreachable, layer calls fail and the errors surface in your consumers and views. For Redis operations see Redis replication, Sentinel and Cluster and Redis security; for the Pub/Sub primitive underneath the Pub/Sub layer see Redis streams and Pub/Sub.

Authentication and sessions

A WebSocket starts life as an HTTP GET with an Upgrade header, so the browser sends the same cookies it sends to your views, including the session cookie. Channels reuses Django’s session and authentication machinery on that handshake; it does not run Django’s MIDDLEWARE (that list belongs to the HTTP handler behind get_asgi_application()), so anything a WebSocket consumer needs must come from ASGI middleware wrapped around the router.

AuthMiddlewareStack

AuthMiddlewareStack(inner) is a shortcut for three middlewares, outermost first:

Middleware Puts into the scope

channels.sessions.CookieMiddleware

scope["cookies"], parsed from the cookie header.

channels.sessions.SessionMiddleware

scope["session"], a lazy session object built from SESSION_ENGINE and the cookie named by SESSION_COOKIE_NAME. SessionMiddlewareStack is the first two without authentication.

channels.auth.AuthMiddleware

scope["user"], the logged-in user or an AnonymousUser, looked up with the backend path stored in the session.

scope["user"] is a UserLazyObject, but AuthMiddleware resolves it (through database_sync_to_async, in a thread) before your consumer is called, so reading self.scope["user"] in an async consumer does not touch the database on the event loop. The user is read-only: Channels never writes it back. In the discussion consumer (Consumers) connect() refuses anonymous users with close code 4401 and the tests check both cases.

Two details catch people out:

  • Sessions are not saved automatically in WebSocket consumers. HTTP consumers save a modified session when they send the response; a WebSocket consumer must call scope["session"].save() (or await scope["session"].asave() in async code) itself, or other connections and views never see the change.

  • channels.auth.login(scope, user) and logout(scope) exist (async functions; wrap them in async_to_sync from a sync consumer), and need the same explicit save(). Most sites never need them: users log in through the normal HTTP login view (see Authentication) and the socket simply inherits that session.

Long-lived connections outlive logouts

The scope is built once, at the handshake. A socket opened at 09:00 still carries the 09:00 session at 17:00, even if the user clicked "log out" in another tab at noon. The documentation suggests calling channels.auth.get_user(scope) periodically, and it does re-read the user row (so a deactivated user or a changed password is noticed), but it checks the session object already loaded into the scope: in the scratch project it still returned alice after the session had been deleted by a logout. To notice a logout, read the session again from the store before privileged actions:

# catalog/auth_checks.py
from importlib import import_module

from channels.auth import get_user
from channels.generic.websocket import AsyncJsonWebsocketConsumer
from django.conf import settings

SessionStore = import_module(settings.SESSION_ENGINE).SessionStore


async def fresh_user(scope):
    """Re-read the session from the store: was the user logged out elsewhere?

    scope["session"] was loaded once, when the socket opened; get_user(scope)
    re-checks the user row and the password hash, but not a session that a
    logout in another tab has since deleted.
    """
    store = SessionStore(scope["session"].session_key)
    return await get_user({"session": store})


class WhoAmIConsumer(AsyncJsonWebsocketConsumer):
    async def connect(self):
        if self.scope["user"].is_authenticated:
            await self.accept()
        else:
            await self.close(code=4401)

    async def receive_json(self, content, **kwargs):
        cached = await get_user(self.scope)
        current = await fresh_user(self.scope)
        if not current.is_authenticated:
            await self.close(code=4401)  # session gone: stop serving this socket

Clients that cannot send cookies

A browser on your own domain sends the session cookie automatically; nothing else is needed. A mobile app or a script usually has an API token instead, and the browser WebSocket API cannot set an Authorization header. Marani’s book solves this by putting the long-lived API token in the URL query string and looking it up with a synchronous ORM call inside the async middleware; both are mistakes. URLs end up in proxy and server access logs, browser history and monitoring tools, so a token placed there is a leaked credential, and a blocking query in async middleware stalls the event loop for every connection on that process.

The scratch project uses a narrower pattern instead: an authenticated HTTP endpoint hands out a ticket — a value signed with Django’s signing module, salted for this one purpose and valid for 30 seconds, i.e. only long enough to open the socket — and a small middleware turns it into scope["user"]:

# catalog/middleware.py
from channels.db import database_sync_to_async
from channels.middleware import BaseMiddleware
from django.contrib.auth import get_user_model
from django.contrib.auth.models import AnonymousUser
from django.core import signing
from urllib.parse import parse_qs

TICKET_SALT = "catalog.ws-ticket"
TICKET_MAX_AGE = 30  # seconds: a ticket is only needed to open the socket


def issue_ticket(user):
    """Called from a normal HTTP view for a logged-in user."""
    return signing.dumps({"uid": user.pk}, salt=TICKET_SALT)


@database_sync_to_async
def _user_for_ticket(ticket):
    try:
        data = signing.loads(ticket, salt=TICKET_SALT, max_age=TICKET_MAX_AGE)
    except signing.BadSignature:  # includes SignatureExpired
        return AnonymousUser()
    User = get_user_model()
    return User.objects.filter(pk=data["uid"], is_active=True).first() or AnonymousUser()


class TicketAuthMiddleware(BaseMiddleware):
    """Authenticate clients that cannot send cookies (mobile apps, scripts)."""

    async def __call__(self, scope, receive, send):
        scope = dict(scope)  # never mutate the caller's scope
        user = scope.get("user")
        if user is None or not user.is_authenticated:
            query = parse_qs(scope.get("query_string", b"").decode())
            ticket = (query.get("ticket") or [""])[0]
            if ticket:
                scope["user"] = await _user_for_ticket(ticket)
        return await super().__call__(scope, receive, send)

Source: Custom authentication and Cryptographic signing: timestamped values

What makes it safe enough:

  • Not the credential itself. The ticket cannot call the API, cannot be refreshed, expires after TICKET_MAX_AGE seconds and is bound to its salt, so a ticket copied from a log afterwards is useless. If even a 30-second replay window is too much, store a random nonce in the cache when issuing and delete it on first use.

  • No blocking call on the event loop. signing.loads() is CPU-only, and the user lookup is a database_sync_to_async function (Database access from consumers).

  • query_string is bytes. The ASGI scope carries the raw query string as bytes; it is decoded before parse_qs. Comparing it, or values sliced from it, with str never matches (the book’s bug), and the short illustrative middleware in the Channels documentation, which passes the whole raw query string to int(), only works when the query string is nothing but a number.

  • A fresh scope. scope = dict(scope) copies before writing, the same thing AuthMiddleware does, so the outer middleware’s dictionary is never mutated.

  • Placement. It runs inside AuthMiddlewareStack and only fills in a user when the cookie produced none. Forged and expired tickets give an AnonymousUser, and the consumer’s own check closes with 4401.

BaseMiddleware is the Channels 3+ middleware shape: a single async callable call(scope, receive, send). The Channels 2 two-step "instance per scope, then `call`" style no longer works (Migrating from Channels 2 to Channels 4).

Origin validation

Cookies make WebSockets vulnerable to cross-site WebSocket hijacking: any page on the internet can run new WebSocket("wss://bookshelf.example/ws/…​"), and the browser attaches your user’s cookies. Django’s CSRF protection does not apply — it is HTTP middleware, and the handshake carries no CSRF token. What the browser does send, and a hostile page cannot forge, is the Origin header. Channels checks it with two ASGI middlewares from channels.security.websocket:

Middleware Allows

OriginValidator(app, allowed_origins)

Origins matching the list: a bare domain ("bookshelf.example"), a leading-dot pattern for subdomains (".bookshelf.example"), or a full scheme://host[:port] origin (port optional but recommended). "*" allows any origin, including none.

AllowedHostsOriginValidator(app)

OriginValidator built from Django’s ALLOWED_HOSTS, so the list lives in one place. With DEBUG = True and an empty ALLOWED_HOSTS it allows localhost, 127.0.0.1 and [::1], as Django does for the Host header.

Rejected connections are closed before accept(), which protocol servers turn into an HTTP 403 on the handshake. Against Daphne in the scratch project, a foreign Origin, a missing Origin and an anonymous user were each refused with HTTP 403 (WSREJECT in Daphne’s log), while the same page with Origin: http://localhost:8760 connected.

Rules that follow from how the validator works:

  • Wrap outermost. Put the validator around AuthMiddlewareStack, as config/asgi.py does, so a hostile page is turned away before a session is even loaded.

  • A missing Origin is refused unless "*" is allowed. Browsers always send one; scripts and mobile clients may have to set it explicitly (the Node and Python clients used for this page did).

  • ALLOWED_HOSTS is read when the stack is built, i.e. when asgi.py is imported, not per connection. A test that overrides the setting must build its own stack (test_validator_reads_allowed_hosts_when_it_is_built in Testing consumers).

  • It is not authorisation. Origin checks stop other sites' pages; they do nothing against a malicious client that sets any Origin it likes. Authenticate in connect() and authorise every message.

Database access from consumers

The ORM’s query execution is synchronous. What that means for a consumer depends on its flavour:

Consumer How to query

Sync (WebsocketConsumer, JsonWebsocketConsumer, SyncConsumer)

Call the ORM normally. Every handler already runs in a worker thread, and Channels closes stale connections around each one, as Django does around a request.

Async (AsyncWebsocketConsumer, AsyncJsonWebsocketConsumer, AsyncConsumer, AsyncHttpConsumer)

Use the async ORM (aget(), acreate(), aexists(), acount(), async for) or wrap a sync function with channels.db.database_sync_to_async. A plain Book.objects.get() on the event loop raises SynchronousOnlyOperation — Django’s guard against blocking every other connection on the process.

The discussion consumer uses the async ORM directly (aexists() and acreate()). Anything more involved — a values() query with slicing and joins, code shared with sync views, a transaction — is clearer as a plain sync function run by database_sync_to_async:

# catalog/queries.py
from channels.db import aclose_old_connections, database_sync_to_async

from .models import DiscussionMessage


@database_sync_to_async
def recent_messages(book_id, limit=20):
    """Plain synchronous ORM code, run in a thread and cleaned up afterwards."""
    rows = (
        DiscussionMessage.objects.filter(book_id=book_id)
        .order_by("-created")
        .values("id", "author__username", "text")[:limit]
    )
    return list(reversed(rows))  # evaluate inside the thread, oldest first


async def history_for(book_id):
    """Call from a long-lived async consumer that may have been idle for a while."""
    await aclose_old_connections()  # drop connections the database may have closed
    return await recent_messages(book_id)

Source: database_sync_to_async and aclose_old_connections

test_queries calls history_for() from an async def test and gets both rows back, oldest first. The points worth remembering:

  • database_sync_to_async is asgiref.sync.sync_to_async plus connection cleanup. Before and after the wrapped function it closes connections that are past CONN_MAX_AGE or broken, so a thread never reuses a dead connection. Plain sync_to_async does not; prefer the Channels version for ORM code inside consumers.

  • Evaluate inside the thread. A QuerySet is lazy: returning it unevaluated from the wrapped function moves the actual query back to the event loop, where it fails. list(…​), .first(), .count() or a values() slice turned into a list keep the query in the thread.

  • Long-lived async consumers need aclose_old_connections(). Since Channels 4.2 async consumers close old connections when a connection starts, when it ends and whenever a message arrives from the client. Group events from the channel layer and timers do not trigger this, so a consumer woken by group_send after an hour of silence may hold a connection the database server already dropped. Call await aclose_old_connections() before the first query in a while, as history_for() does.

  • Count the threads. Sync consumers and database_sync_to_async share one thread pool; each thread can hold a database connection. The pool size follows min(32, os.cpu_count() + 4) and can be capped with the ASGI_THREADS environment variable. Many open WebSockets on sync consumers can exhaust PostgreSQL’s max_connections; async consumers only borrow a thread for the query.

  • Transactions stay synchronous. transaction.atomic() cannot span await calls; put the whole transaction in one database_sync_to_async function (see Transactions, Raw SQL and Multiple Databases).

Marani’s consumers call the synchronous ORM straight from async def handlers. On Channels 2 and Django 2.x nothing stopped that; it blocked the event loop for every connection on the server. Since Django 3.0 the same line raises SynchronousOnlyOperation, and since Django 4.1 the async ORM makes most wrappers unnecessary. The wider picture — async views, sync_to_async, thread_sensitive, async-safe and async-unsafe APIs — is in Async Support.

Three habits keep the tests fast and isolated:

  • Use InMemoryChannelLayer in tests (the scratch settings already do; a production project overrides CHANNEL_LAYERS in its test settings). It needs no Redis, but its groups and queues live in the process, so flush it after each test:

    # catalog/tests/base.py
from asgiref.sync import async_to_sync
from channels.layers import get_channel_layer
from django.test import TestCase


class LayerTestCase(TestCase):
    """Start every test with an empty in-memory channel layer."""

    def tearDown(self):
        async_to_sync(get_channel_layer().flush)()

  • Inject the user to unit-test a consumer, drive asgi.py to test the stack. A communicator’s scope is a plain dictionary; setting communicator.scope["user"] before connect() skips cookies and sessions, which keeps consumer tests about the consumer. Separate tests run the real application with real cookies, origins and tickets.

  • Assert silence explicitly. receive_nothing() (default timeout 0.1 s) is how you prove that a message did not reach another group, and receive_output() raises asyncio.TimeoutError (after 1 s by default) instead of hanging when something you expected never arrives.

A few pitfalls the scratch tests ran into:

  • Disconnect what you connect. A communicator left open keeps its consumer task alive; the next test may receive its group messages. Every test above ends with await communicator.disconnect() (or never got past a refused connect()).

  • Module-level stacks capture settings. AllowedHostsOriginValidator reads ALLOWED_HOSTS when it is built, so @override_settings(ALLOWED_HOSTS=…​) has no effect on the imported application; build the stack inside the test.

  • Channels 4.3 changed ApplicationCommunicator. When the application has already finished, sending input now returns its result instead of timing out later; tests that relied on a timeout must now assert the CancelledError.

  • The database and the event loop. Data created in setUpTestData is visible to the consumer, which runs in the same test transaction; Django’s TestCase handles that for async def tests.

The Bookshelf discussion room, end to end

Put together, one message travels like this through the files above:

  1. The book page loads discussion.js, which opens ws(s)://<host>/ws/books/<id>/discussion/; the browser sends the session cookie and its Origin.

  2. ProtocolTypeRouter sees scope["type"] == "websocket"; AllowedHostsOriginValidator checks the origin against ALLOWED_HOSTS; AuthMiddlewareStack loads the session and the user; TicketAuthMiddleware leaves them alone; URLRouter matches the path and puts book_id into scope["url_route"].

  3. DiscussionConsumer.as_asgi() builds a consumer for this connection. connect() refuses anonymous users (4401) and unknown books (4404), joins the group book-<id> and accepts.

  4. The user sends {"text": "…​"}. receive_json() validates it, stores it with acreate() and calls group_send("book-<id>", {"type": "discussion.message", …​}).

  5. The channel layer (Redis in production) delivers the event to every channel in the group, on any server process. In each consumer discussion_message() runs and send_json() writes the frame to that browser, which appends it with textContent.

  6. A closed tab triggers disconnect(), which leaves the group.

Where the books are outdated

Marani’s Practical Django 2 and Channels 2 (Apress, 2019) is the only one of the section’s books that builds a Channels application, and its chapters 8-10 predate everything in the table above. Beyond the API changes, five patterns from it should not be copied:

  • Synchronous ORM calls inside async consumers. They block every connection on the process; current Django refuses them outright. Use the async ORM or database_sync_to_async (Database access from consumers).

  • The API token in the WebSocket URL. A long-lived credential in a query string ends up in logs and histories. Use the session cookie for browsers and a short-lived, single-purpose ticket for other clients (Clients that cannot send cookies).

  • Presence by polling Redis with KEYS. KEYS scans the whole keyspace and blocks Redis while it runs, so polling it for "who is online" degrades every other client of that server. Track presence explicitly instead: add and remove members in connect()/disconnect() in a structure you can read directly (a Redis set or a database table with a last-seen timestamp that heartbeats refresh), and broadcast changes through a group.

  • Connections that are never closed. Long-lived consumers keep database connections across idle hours; current Channels closes them around client messages and provides aclose_old_connections() for the rest (Database access from consumers).

  • Treating scope["query_string"] as text. It is bytes; decode it before parsing (Clients that cannot send cookies).

What still holds from the book is the architecture: consumers per connection, groups for fan-out, a Redis layer between processes, and testing with communicators.

What changed recently

  • Channels 4.3.2 (2025-11-20) confirmed Django 6.0 and Python 3.14 and added a types extra for the types-channels stubs. It has no Django 6.1 classifier yet (checked 2026-10-03); it worked unchanged with Django 6.1.1 in the scratch project.

  • Channels 4.3.0 (2025-07-28) raised the minimums to Python 3.9 and asgiref 3.9, fixed ChannelsLiveServerTestCase on Django 5.2 and changed ApplicationCommunicator to return the result of an application that has already finished.

  • Channels 4.2.1 (2025-03-29) added official Django 5.2 LTS and Python 3.13 support, and warns about over-long group names.

  • Channels 4.2.0 (2024-11-15) brought the async-ORM-aware documentation, aclose_old_connections() and automatic connection closing in async consumers, plus Django 5.1 support.

  • Channels 4.1.0 (2024-04-03) made Django 4.2 the minimum and added the headers argument of accept() and reason on close.

  • channels_redis 4.3.0 (2025-07-22) added Python 3.13, dropped 3.8 and requires Channels 4.2.2+.

  • Daphne 4.2.3 (2026-07-21) is the current server release.

  • Django has meanwhile grown its own async story (async views in 3.1, the async ORM in 4.1, async sessions and auth in 5.x, the Tasks framework in 6.0), so Channels is now needed only for WebSockets, channel layers and other non-HTTP protocols; a one-way live feed can also be an async streaming view (see Async Support).
