In the Bookshelf application that grows across this section, uploads are the cover image of a book, a public excerpt and a private manuscript. A file upload crosses more trust boundaries than any other request: the bytes, the file name and the declared type all come from the client, they are parsed by Django before your view runs, they are stored somewhere that someone must later serve, and what you serve can be executed by a browser. This page follows that path from the request to the storage backend and back to the browser.

The path of an upload

A browser sends the form as multipart/form-data: one request body made of parts, each with its own headers, some of them files. Django does not hand your view the raw body. When the view (or CSRF middleware, or a form) first touches request.POST or request.FILES, Django’s multipart parser walks the body, feeds file parts to the configured upload handlers, and builds one UploadedFile per file. Your code then passes that object to a form, a model field or a storage, and the storage decides where the bytes finally go.

Two consequences shape the rest of the page. First, the body is parsed before your view body runs whenever CsrfViewMiddleware is enabled, so anything that must happen early (changing the upload handlers, rejecting oversized bodies) has to happen in the web server or at view setup. Second, the model never contains the file: it contains a path that the storage can resolve, so moving to another storage is a configuration change plus a data copy, not a schema change.

from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent

MEDIA_URL = "media/"                    # public URL prefix (relative: prefixed with SCRIPT_NAME)
MEDIA_ROOT = BASE_DIR / "media"         # where FileSystemStorage writes
PRIVATE_ROOT = BASE_DIR / "private"     # never exposed by a URL

STORAGES = {
    "default": {"BACKEND": "django.core.files.storage.FileSystemStorage"},
    "staticfiles": {"BACKEND": "django.contrib.staticfiles.storage.StaticFilesStorage"},
    "private": {
        "BACKEND": "django.core.files.storage.FileSystemStorage",
        "OPTIONS": {"location": PRIVATE_ROOT},
    },
}

DATA_UPLOAD_MAX_MEMORY_SIZE = 2_621_440   # request body excluding files; the default
DATA_UPLOAD_MAX_NUMBER_FILES = 20         # default is 100

FILE_UPLOAD_DIRECTORY_PERMISSIONS = 0o755

Receiving a file: request.FILES

request.FILES is a dictionary-like object with one key per file input, filled only when three conditions hold: the request method is POST, at least one file was actually posted, and the <form> carries enctype="multipart/form-data". Forget the enctype and the browser sends only the file name as an ordinary field; request.FILES is empty and the form reports "This field is required", which is the most common upload bug.

<form method="post" enctype="multipart/form-data">
  {% csrf_token %}
  {{ form.as_div }}
  <button type="submit">Upload</button>
</form>

A plain form and view

The smallest working example is a form with a forms.FileField and a view that binds request.FILES to it. The form constructor takes two dictionaries, data and files: leaving out request.FILES is the classic second bug, and again the symptom is "required".

# catalog/forms.py
from django import forms


class UploadFileForm(forms.Form):
    title = forms.CharField(max_length=50)
    file = forms.FileField()
# catalog/views.py
from django.core.files.storage import default_storage
from django.http import JsonResponse
from django.shortcuts import render

from .forms import UploadFileForm


def save_upload(uploaded):
    """Store an UploadedFile through the default storage, chunk by chunk."""
    return default_storage.save(f"inbox/{uploaded.name}", uploaded)


def upload_file(request):
    if request.method == "POST":
        form = UploadFileForm(request.POST, request.FILES)   # both dictionaries
        if form.is_valid():
            name = save_upload(request.FILES["file"])
            return JsonResponse({"saved_as": name})
        return JsonResponse(form.errors, status=400)
    return render(request, "catalog/upload.html", {"form": UploadFileForm()})

Two details of save_upload are deliberate. The upload is passed to default_storage.save() instead of being copied with open(name, "wb") as older tutorials show: the storage iterates the file with chunks(), so a 2 GB upload never sits in memory, and the storage chooses a free name instead of overwriting. And the client’s file name is not used as a path: Django’s storage runs it through get_valid_name() and rejects .. segments. A multipart part named ../../etc/passwd was stored as inbox/passwd, and a second upload named notes.txt became inbox/notes_MVRyPkO.txt (an underscore plus seven random characters, produced by get_alternative_name()). The name Django returns from save() is the only name you may rely on, and the client name is still data to display, not to trust.

The UploadedFile object

Each value in request.FILES is an UploadedFile (or one of its subclasses): a wrapper over the received bytes.

Member Meaning

name

The file name sent by the client, already stripped of directory components. Display it, do not build paths from it.

size

Size in bytes after the upload was received. Reliable for limits, because Django counted the bytes itself.

content_type

The Content-Type header of the part. Client-controlled; "trust but verify". For an ImageField, Django replaces it with the type Pillow detected, or None.

content_type_extra, charset

Extra parameters of the header, and the charset for text/* parts. Same trust level.

Reads everything into memory. Fine for small, size-checked files; use chunks() for anything else.

Generator of byte chunks (64 KB by default). The default way to copy an upload.

A ModelForm with a file field

When the destination is a model, a ModelForm does the binding, the validation and the storage in one step: form.save() saves the file to the location given by the field’s upload_to, then saves the row. Several files in one field

HTML allows <input type="file" multiple>, but forms.FileField validates one file. For years the docs showed a shortcut that validated only the last file, which became CVE-2023-31047 and was fixed in 4.2.1 (and 4.1.9, 3.2.19): since then ClearableFileInput and FileInput raise ValueError if you set the multiple attribute, unless the widget class sets allow_multiple_selected = True. A field that validates every file has to subclass FileField as well:

# catalog/forms.py
from django import forms


class MultipleFileInput(forms.ClearableFileInput):
    allow_multiple_selected = True


class MultipleFileField(forms.FileField):
    def __init__(self, *args, **kwargs):
        kwargs.setdefault("widget", MultipleFileInput())
        super().__init__(*args, **kwargs)

    def clean(self, data, initial=None):
        single_file_clean = super().clean
        if isinstance(data, (list, tuple)):
            return [single_file_clean(d, initial) for d in data]
        return [single_file_clean(data, initial)]

Where the bytes live: upload handlers

The multipart parser does not store anything itself. It asks a chain of upload handlers, taken from FILE_UPLOAD_HANDLERS, which of them wants each file, and the first handler that returns an UploadedFile wins. The default list is

FILE_UPLOAD_HANDLERS = [
    "django.core.files.uploadhandler.MemoryFileUploadHandler",
    "django.core.files.uploadhandler.TemporaryFileUploadHandler",
]

Source: Django: FILE_UPLOAD_HANDLERS

and gives Django’s default behaviour: small uploads live in memory (InMemoryUploadedFile), large ones are streamed to a temporary file (TemporaryUploadedFile) as they arrive.

Writing a custom handler

Subclass FileUploadHandler when you need behaviour that cannot be done after the fact: enforcing a quota while the bytes arrive, computing a checksum on the fly, driving a progress bar, or sending data straight to another store without a local copy. The hooks are called in this order for every request.

Hook When and what

handle_raw_input(input_data, META, content_length, boundary, encoding)

Optional. Called before parsing; return None to continue, or a (POST, FILES) tuple to take over parsing completely. It runs outside the parser’s error handling, so do not raise StopUpload here (the exception becomes a 500).

new_file(field_name, file_name, content_type, content_length, charset, content_type_extra)

Optional. A new file part starts. May raise StopFutureHandlers so later handlers ignore this file. Call super().new_file() to store the arguments on the handler.

receive_data_chunk(raw_data, start)

Required. Gets each chunk (chunk_size bytes, 64 KB by default; the smallest value among handlers wins). Return the data to pass it on, return None to swallow it, raise StopUpload to abort the upload or SkipFile to skip this file.

file_complete(file_size)

Required. The file ended. Return an UploadedFile to finish, or None to let a later handler do it.

upload_complete()

Optional. All files are done.

upload_interrupted()

Optional, added in 3.2. The connection dropped mid-upload; release what you hold.

Source: Django: Writing custom upload handlers

The handler below counts bytes and aborts as soon as the budget is exhausted. It stores nothing, so the default handlers after it still build the UploadedFile: it is a filter in front of them.

# catalog/handlers.py
from django.core.files.uploadhandler import FileUploadHandler, StopUpload


class MaxUploadSizeHandler(FileUploadHandler):
    """Abort the whole upload as soon as it exceeds ``limit`` bytes."""

    def __init__(self, request=None, limit=5 * 1024 * 1024):
        super().__init__(request)
        self.limit = limit
        self.received = 0

    def receive_data_chunk(self, raw_data, start):
        self.received += len(raw_data)
        if self.received > self.limit:
            raise StopUpload(connection_reset=True)   # do not read the rest of the body
        return raw_data                               # feed the next handler in the chain

    def file_complete(self, file_size):
        return None                                   # a later handler builds the UploadedFile

Source: Django: FileUploadHandler.receive_data_chunk()

StopUpload(connection_reset=True) makes Django stop reading the body at once, which the browser shows as a connection reset; the default StopUpload() consumes the rest of the body first and then halts, which is friendlier to the client and costs bandwidth. In both cases request.FILES stays empty, so the form reports the field as required: if you want a specific message, record the abort on the handler or on the request and test for it in the view.

Changing handlers for one view

FILE_UPLOAD_HANDLERS applies everywhere; a single view can change request.upload_handlers instead. Two rules from the official guide matter: do it before anything reads request.POST or request.FILES (changing the list afterwards raises an error), and note that CsrfViewMiddleware reads request.POST, so the view must be csrf_exempt to get a chance to modify the list, and the code that really processes the request must be wrapped in csrf_protect. The handlers then start receiving file data before the CSRF check has run, which is an exposure you accept consciously. For a class-based view the equivalent is to exempt dispatch and protect the method:

# catalog/views.py
from django.utils.decorators import method_decorator
from django.views import View
from django.views.decorators.csrf import csrf_exempt, csrf_protect


@method_decorator(csrf_exempt, name="dispatch")
class QuotaUploadView(View):
    """Per-request handler: must be installed before request.POST/FILES is read."""

    def setup(self, request, *args, **kwargs):
        request.upload_handlers.insert(0, MaxUploadSizeHandler(request, limit=64 * 1024))
        super().setup(request, *args, **kwargs)

    @method_decorator(csrf_protect)
    def post(self, request, *args, **kwargs):
        form = UploadFileForm(request.POST, request.FILES)
        if not form.is_valid():
            return JsonResponse(form.errors, status=400)
        return JsonResponse({"saved_as": save_upload(request.FILES["file"])})

Limits belong in front of Django too

Django’s settings bound memory and field counts; they do not bound the body. The security guide says so plainly: limit upload size in the web server (Apache’s LimitRequestBody, Nginx’s client_max_body_size, the proxy of your platform) and do not rely solely on DATA_UPLOAD_MAX_MEMORY_SIZE or FILE_UPLOAD_MAX_MEMORY_SIZE. Under ASGI the entire request may be spooled to disk before Django enforces its own limits, so a missing proxy limit becomes a disk-filling attack. The MaxUploadSizeHandler above is useful for per-view quotas, but it runs after the proxy has already accepted the bytes.

FileField and ImageField

FileField and ImageField store a name in a varchar column (100 characters by default, set max_length for longer paths) and nothing else: the bytes live in a storage, and the database holds a path relative to that storage’s root. That is why the files are not in your database backups and why dumpdata only dumps names (see Fixtures, Serialization & Initial Data). The general field catalogue is in Models & Fields; this section covers what is specific to files.

Option Meaning

upload_to

A string or Path appended to the storage location (may contain strftime() codes such as uploads/%Y/%m/), or a callable (instance, filename) returning a Unix-style relative path. The result is passed to Storage.save().

storage

A storage object, or a callable returning one (3.1). Defaults to default_storage.

max_length

Length of the stored path, including upload_to. A longer generated name fails; the storage truncates when it can.

ImageField.width_field, height_field

Names of model fields that receive the image dimensions each time an image is set. Queryable, unlike the properties.

primary_key

Not supported on FileField.

Source: Django: FileField and ImageField

ImageField needs Pillow (pip install pillow), validates that the upload really is an image Pillow can open, and adds width and height. The Bookshelf Book model uses three file fields with three different needs: an image with validators and a generated path, a public attachment partitioned by date, and a private file on its own storage.

# catalog/models.py
import uuid
from pathlib import PurePath

from django.core.files.storage import storages
from django.db import models

from .validators import MaxFileSize, validate_cover_extension, validate_image_content


def cover_path(instance, filename):
    """Never trust the client file name: keep only a normalised extension."""
    ext = PurePath(filename).suffix.lower()
    return f"covers/{instance.pk or 'new'}/{uuid.uuid4().hex}{ext}"


def private_storage():
    """Callable storage: migrations store a reference to this function, not a path."""
    return storages["private"]


class Book(models.Model):
    title = models.CharField(max_length=200)
    cover = models.ImageField(
        upload_to=cover_path,
        width_field="cover_width",
        height_field="cover_height",
        blank=True,
        validators=[validate_cover_extension, validate_image_content, MaxFileSize(2 * 1024 * 1024)],
    )
    cover_width = models.PositiveIntegerField(null=True, blank=True, editable=False)
    cover_height = models.PositiveIntegerField(null=True, blank=True, editable=False)
    excerpt = models.FileField(upload_to="excerpts/%Y/%m/", blank=True)
    manuscript = models.FileField(storage=private_storage, upload_to="manuscripts/", blank=True)

    def __str__(self):
        return self.title

Source: Django: FileField and Django: Using a callable

A few details of upload_to deserve attention:

  • A callable receives the instance before it is saved. instance.pk is usually None for a new object (the example falls back to new), and a primary key assigned by the database cannot be used. A UUID primary key or a generated token solves it; so does a random component, as here.

  • The directory is not a security boundary. Whatever the callable returns is combined with the storage location after Storage.generate_filename() validated it, so a returned ../.. is rejected, but a user name or title interpolated into the path creates directories you did not plan for (and, on a case-insensitive file system, collisions).

  • strftime() codes are filled at save time. With excerpts/%Y/%m/ an excerpt saved on 2026-10-02 went to excerpts/2026/10/excerpt.txt; the date partitions keep any single directory from growing without bound.

The FieldFile behind the attribute

Reading book.cover does not give you a string or a Python file object but a FieldFile, a proxy that offers the File API (see The File API: File, ContentFile, ImageFile) and delegates to the field’s storage. Its extras are save(name, content, save=True) and delete(save=True), plus the name, path, size and url properties, which call the corresponding storage methods.

book = Book.objects.create(title="Dune")
book.excerpt.save("excerpt.txt", ContentFile("héllo"), save=True)
print(book.excerpt.name)    # excerpts/2026/10/excerpt.txt
print(book.excerpt.size)    # 6     (bytes, not characters)
print(book.excerpt.url)     # /media/excerpts/2026/10/excerpt.txt
print(book.excerpt.path)    # /tmp/media-5f1h1nrm/excerpts/2026/10/excerpt.txt   (FileSystemStorage only)

with book.excerpt.open("rb") as fh:
    assert fh.read().decode() == "héllo"

book.excerpt.delete(save=True)       # removes the file and clears the field
assert not book.excerpt              # an empty FieldFile is falsy
book.refresh_from_db()
assert book.excerpt.name == ""

Source: Django: FileField and FieldFile

Points that bite in practice:

  • save() and delete() also save the model by default. Pass save=False when you are about to call instance.save() yourself, or you write the row twice.

  • The on-disk name is not final until the model has been saved. The storage may rename the file to avoid a collision, so read name after save(), never before.

  • path exists only for local storage. On S3 or any remote backend FieldFile.path raises NotImplementedError; use open() and url and keep your code storage-neutral.

  • Deleting the row does not delete the file, and neither does replacing it (see Housekeeping: orphaned files).

  • Dimensions are updated at assignment, not after FieldFile.save(). Since 5.1 ImageField.update_dimension_fields(force=True) is no longer called after the image is saved to storage (so a storage that resizes the image cannot desynchronise the stored dimensions). In the scratch project, after book.cover.save(…​) the in-memory book.cover_width was None while book.cover.width was 8 and, after refresh_from_db(), cover_width was 8 as well; assigning book.cover = ContentFile(data, name="d.png") and saving filled it at once. Prefer assignment or a ModelForm, or refresh the instance.

  • An image read from FieldFile is closed. The official guide notes that Image.open(car.photo) raises ValueError: seek of closed file because dimensions are cached but the file is not open; call book.cover.open() first, or use the context manager as in the listing below.

from PIL import Image

with book.cover.open("rb") as fh:
    with Image.open(fh) as image:
        print(image.size, image.format)      # (10, 20) PNG

Storage objects in migrations

A migration records the field’s arguments, including storage. A storage is the object that understands a particular place for files. Writing a custom storage

Write a storage class when no existing backend fits: a proprietary object store, an encrypted directory, a content-addressed store. The recipe from the official how-to has five steps: subclass django.core.files.storage.Storage; make the class instantiable without arguments (read defaults from django.conf.settings); implement _open() and _save(); override path() only if the storage is local; and make the class deconstructible so migrations can serialise it, usually with django.utils.deconstruct.deconstructible. The class below is complete and runnable: a non-persistent storage that keeps bytes in a dictionary. It is a teaching tool, not a production backend (state is per process and lost on restart), but it shows every moving part, including the no-argument constructor that falls back to a setting.

# catalog/storage.py
from datetime import datetime, timezone
from io import BytesIO

from django.conf import settings
from django.core.files.base import File
from django.core.files.storage import Storage
from django.utils.deconstruct import deconstructible


@deconstructible
class DictStorage(Storage):
    """A tiny, non-persistent storage that keeps bytes in a dict (demo only)."""

    def __init__(self, base_url=None):
        # Django must be able to instantiate us with no arguments: fall back to settings.
        self.base_url = base_url or getattr(settings, "DICT_STORAGE_URL", "/dict-files/")
        self._files = {}

    def _open(self, name, mode="rb"):
        try:
            return File(BytesIO(self._files[name][0]), name=name)
        except KeyError:
            raise FileNotFoundError(name) from None

    def _save(self, name, content):
        self._files[name] = (content.read(), datetime.now(timezone.utc))
        return name                                   # the name actually used

    def exists(self, name):
        return name in self._files

    def delete(self, name):
        self._files.pop(name, None)

    def size(self, name):
        return len(self._files[name][0])

    def url(self, name):
        return self.base_url + name

    def listdir(self, path):
        prefix = path.rstrip("/") + "/" if path else ""
        dirs, files = set(), []
        for n in self._files:
            if n.startswith(prefix):
                head, _, tail = n[len(prefix):].partition("/")
                (dirs.add(head) if tail else files.append(head))
        return sorted(dirs), sorted(files)

    def get_modified_time(self, name):
        return self._files[name][1]

Overriding a hook changes the policy without rewriting the backend. A content-addressed variant stores each upload under a name derived from the SHA-256 of its bytes, so identical uploads are stored once and the client’s name is irrelevant. It overrides save() (the public entry point) to compute the name, and get_available_name() so that an existing name is reused instead of renamed:

import hashlib

from django.core.files.base import ContentFile


@deconstructible
class ContentAddressedStorage(DictStorage):
    def get_available_name(self, name, max_length=None):
        return name                       # same content, same name: nothing to avoid

    def save(self, name, content, max_length=None):
        data = content.read()
        digest = hashlib.sha256(data).hexdigest()
        ext = name.rsplit(".", 1)[-1].lower() if "." in name else "bin"
        return super().save(f"{digest[:2]}/{digest}.{ext}", ContentFile(data), max_length)

Notes for production:

  • Latency is part of the API. exists(), size() and listdir() are network calls. Rendering a list of 50 books that touches cover.size makes 50 requests; store the size in a column, or avoid calling it in loops. cover.url does not call the network (it signs locally).

  • Signed URLs expire. With querystring_auth=True every page render yields different URLs, which defeats HTTP caching of the page; a CDN with a custom domain and public, immutable objects (content-hashed names) caches well.

  • Static files can use the same package by pointing the staticfiles alias at an S3 storage, but then collectstatic uploads to the bucket; most sites serve static files from WhiteNoise or a CDN instead.

  • Configuration is per alias. Two buckets (public media, private exports) are two aliases with different options.

  • Prefer the S3 transport settings you understand. addressing_style, signature_version, client_config and transfer_config exist for gevent compatibility, proxies and older regions; the package documents each.

Private files

Some files must be visible only to some users: manuscripts, invoices, exports. Give them a storage whose files are not under any public prefix (the private alias), keep their URLs out of templates, and serve them through a view that checks permission first and streams with FileResponse:

# catalog/views.py
from django.http import FileResponse, Http404, HttpResponseForbidden
from django.shortcuts import get_object_or_404


def manuscript(request, pk):
    """Serve a private file only to staff; the storage has no public URL."""
    if not request.user.is_staff:
        return HttpResponseForbidden("staff only")
    book = get_object_or_404(Book, pk=pk)
    if not book.manuscript:
        raise Http404
    response = FileResponse(book.manuscript.open("rb"), as_attachment=True, filename=f"book-{book.pk}.pdf")
    response["X-Content-Type-Options"] = "nosniff"
    return response

Validating uploads safely

Everything about an upload except its bytes is chosen by the sender: the name, the declared type, the extension, the announced length. The security guide is blunt about the consequence: Django’s image handling lets an HTML file be uploaded as an image if it starts with a valid PNG header followed by markup, because Pillow’s verification accepts it, and "no bulletproof technical solution exists at the framework level to safely validate all user uploaded file content". Safety comes from layers, each assuming the previous one failed.

Proxy limit

Bounds the body size before Django sees it (Limits belong in front of Django too). DATA_UPLOAD_MAX_* bound memory and counts, not bytes.

Extension allow-list

FileExtensionValidator(["jpg", "jpeg", "png", "webp"]). Never a deny-list, never based on the content type.

Size

Checked on the received file (value.size), not on Content-Length.

Content check

Decode the bytes (Pillow verify()), check the decoded format against an allow-list and bound the pixel count.

Server-side name

Generate the storage name; keep at most a normalised extension (cover_path above).

Safe serving

Another registrable domain, X-Content-Type-Options: nosniff, attachment disposition for non-images, no script execution.

Antivirus and processing

For documents, scan asynchronously and re-encode images (a re-saved image drops embedded payloads).

The validators are ordinary callables raising ValidationError, so they work on a model field, on a form field and in the admin alike. Django’s own ImageField also runs the Pillow check and FileExtensionValidator with the extensions Pillow knows, so ours narrow and add to it:

# catalog/validators.py
from django.core.exceptions import ValidationError
from django.core.validators import FileExtensionValidator
from django.utils.deconstruct import deconstructible
from PIL import Image, UnidentifiedImageError

ALLOWED_IMAGE_TYPES = {"JPEG": "image/jpeg", "PNG": "image/png", "WEBP": "image/webp"}

validate_cover_extension = FileExtensionValidator(["jpg", "jpeg", "png", "webp"])


@deconstructible
class MaxFileSize:
    """Reject files larger than ``limit`` bytes (checked after parsing)."""

    def __init__(self, limit):
        self.limit = limit

    def __call__(self, value):
        if value.size > self.limit:
            raise ValidationError(
                "File too large (%(size)d bytes, limit %(limit)d).",
                code="file_too_large",
                params={"size": value.size, "limit": self.limit},
            )

    def __eq__(self, other):
        return isinstance(other, MaxFileSize) and self.limit == other.limit


def validate_image_content(value):
    """Decode the bytes: the extension and Content-Type are only hints."""
    position = value.tell() if hasattr(value, "tell") else 0
    try:
        value.seek(0)
        with Image.open(value) as image:
            image.verify()                      # structural check; does not decode every pixel
            if image.format not in ALLOWED_IMAGE_TYPES:
                raise ValidationError(
                    "Unsupported image format %(format)s.",
                    code="bad_image_format",
                    params={"format": image.format},
                )
            if image.width * image.height > 25_000_000:
                raise ValidationError("Image dimensions too large.", code="image_too_big")
    except (UnidentifiedImageError, OSError, SyntaxError) as exc:
        raise ValidationError("Not a valid image.", code="invalid_image") from exc
    finally:
        value.seek(position)

That is why the serving layer has the last word.

Serving untrusted files safely

The official recommendations, in order of strength:

  1. Serve uploads from a distinct top-level or second-level domain (for example usercontent-example.com for a site on example.com; a subdomain such as usercontent.example.com is not sufficient), so the same-origin policy blocks cookie theft and script access even if a file executes.

  2. Allow only expected extensions and configure the server to serve only those.

  3. Disable script execution on the media location (mod_php, CGI, SSI).

  4. Send X-Content-Type-Options: nosniff and a restrictive Content-Security-Policy (Django 6.0 added built-in CSP support for pages it renders; for static media the web server must send the header, as in the Nginx fragment above).

  5. Use Content-Disposition: attachment for anything that is not meant to be rendered inline.

  6. Avoid SVG uploads from untrusted users unless you sanitise them: an SVG is an XML document that can contain script, and it renders inline in a browser. Pillow does not read SVG at all, so the checks above reject it; accepting it means a separate sanitiser and a download-only disposition.

  7. Re-encode images you display (open with Pillow, resize or convert, save as a new file) when you can afford it; that also strips metadata such as GPS coordinates and any appended payload.

Other traps seen in uploads: filenames with Unicode normalisation tricks or reserved Windows names (the server-side name removes them), huge images that exhaust memory on decode ("decompression bombs": Pillow warns above its pixel limit; the validator above rejects above 25 million pixels), zip files that expand enormously, and CSV or spreadsheet uploads with formulas that a spreadsheet executes when opened (prefix cells that begin with =, +, - or @ when you export them back).

Housekeeping: orphaned files

The database and the storage are two systems with no transaction between them, and Django deliberately does not synchronise them. The reference says it explicitly: when a model is deleted, related files are not deleted, and neither are files replaced by a new upload. In the scratch project, deleting a Book left its excerpt in storage, and uploading a second cover over the first left the first on disk (the prune_covers command reported it as an orphan after the curl session). Two defences exist and are usually combined.

Delete after commit. A post_delete receiver removes the files, but only after the surrounding transaction commits, so a rollback does not lose files for rows that still exist. The storage and the name are bound in default arguments because the instance is gone by the time the callback runs. See Transactions, Raw SQL & Multiple Databases for on_commit.

# catalog/signals.py
from django.db import transaction
from django.db.models.signals import post_delete
from django.dispatch import receiver

from .models import Book

FILE_FIELDS = ("cover", "excerpt", "manuscript")


@receiver(post_delete, sender=Book)
def delete_book_files(sender, instance, **kwargs):
    """Remove stored files only after the surrounding transaction commits."""
    for name in FILE_FIELDS:
        fieldfile = getattr(instance, name)
        if fieldfile:
            # bind the storage and name now; the instance is gone by commit time
            storage, path = fieldfile.storage, fieldfile.name
            transaction.on_commit(lambda s=storage, p=path: s.delete(p))
# catalog/apps.py
from django.apps import AppConfig


class CatalogConfig(AppConfig):
    name = "catalog"

    def ready(self):
        from . import signals  # noqa: F401

A receiver does not cover everything: it cannot see a file that was replaced by a new upload, rows removed by database-level cascades (such as DB_CASCADE, new in 6.1), or a crash between the two steps. Add a periodic sweep as a custom management command (see Management Commands & Shell) that compares what the storage holds with what the database references, using only the Storage API so it works on S3 as well:

# catalog/management/commands/prune_covers.py
from django.core.files.storage import default_storage
from django.core.management.base import BaseCommand

from catalog.models import Book


def walk(storage, root=""):
    """Yield every file name below ``root`` using only the Storage API."""
    try:
        dirs, files = storage.listdir(root)
    except FileNotFoundError:      # FileSystemStorage raises this for a missing directory
        return
    for name in files:
        yield f"{root}/{name}" if root else name
    for d in dirs:
        yield from walk(storage, f"{root}/{d}" if root else d)


class Command(BaseCommand):
    help = "Delete files under covers/ that no Book references (dry run by default)."

    def add_arguments(self, parser):
        parser.add_argument("--delete", action="store_true")

    def handle(self, *args, **options):
        referenced = set(Book.objects.exclude(cover="").values_list("cover", flat=True))
        orphans = [n for n in walk(default_storage, "covers") if n not in referenced]
        for name in orphans:
            self.stdout.write(("deleting " if options["delete"] else "orphan ") + name)
            if options["delete"]:
                default_storage.delete(name)
        self.stdout.write(self.style.SUCCESS(f"{len(orphans)} orphan file(s)"))

Source: Django: Writing custom django-admin commands

The first version of this command crashed with FileNotFoundError on a fresh install, because FileSystemStorage.listdir() raises it when the directory does not exist yet (the try above is the fix). In a test with one referenced cover and one stray file, prune_covers printed orphan covers/stray.png and 1 orphan file(s), and --delete removed only the stray file. Run it as a dry run first, on a schedule, and keep object versioning or a lifecycle rule on S3 buckets so an over-eager sweep is recoverable. On S3, listing a prefix with millions of keys is slow and billed; the same job is usually better done from the provider’s inventory reports.

Sync and async

The storage API and the File API are synchronous. Under ASGI nothing changes functionally, but every storage call inside an async def view blocks the event loop for the duration of the disk or network access, which on S3 can be hundreds of milliseconds. Wrap the calls with sync_to_async() or asyncio.to_thread(); the examples run in the scratch project:

import asyncio

from asgiref.sync import sync_to_async
from django.core.files.base import ContentFile
from django.core.files.storage import default_storage


async def go():
    name = await sync_to_async(default_storage.save)("async.txt", ContentFile(b"z"))
    data = await asyncio.to_thread(lambda: default_storage.open(name).read())
    return name, data

print(asyncio.run(go()))     # ('async.txt', b'z')

Source: Django: Asynchronous support and File storage API

Notes: model methods have asynchronous variants (asave(), adelete(), arefresh_from_db()), but FieldFile.save() and FieldFile.delete() have none, so they follow the same wrapping rule; form validation (which reads and decodes the upload) is synchronous and CPU-bound, so validate large images in a worker, not in the event loop; and on ASGI the request body may be spooled to disk before your view starts, which is why the proxy limit is more important, not less. django-storages backends are synchronous because boto3 is.

Where the books are outdated

Older tutorials and the books written for Django 1.11 to 3.x (see the bibliography on the index page of this section) teach a workflow that still runs but contains traps or removed names:

  • DEFAULT_FILE_STORAGE and STATICFILES_STORAGE. Both were removed in 5.1, as was get_storage_class(). Use STORAGES (4.2). A project upgraded from 4.1 with these settings simply loses its custom storage, silently falling back to the local disk, until the setting is moved.

  • Copying with open(path, "wb"). Older examples build a path from uploaded.name and write it by hand. Use default_storage.save() or a model field; name is client data.

  • A FileField alone as the validation. Books show FileField followed by trust in the content type or the extension. The security guide, and the polyglot behaviour above, say that is not enough.

  • ImageField as a security check. It proves that Pillow can open the file, nothing more.

  • MEDIA_ROOT served by Django in production. The static() helper works only with DEBUG = True and the guide marks it unsuitable for production.

  • A multiple-file widget with attrs={"multiple": True}. It stopped working in 4.2.1 (and 4.1.9, 3.2.19) with a ValueError, because it validated only the last file; use allow_multiple_selected and a field that cleans every file.

  • No limit on the number of files. DATA_UPLOAD_MAX_NUMBER_FILES exists since 4.1.7 (also 4.0.10, 3.2.18), default 100.

  • FILE_UPLOAD_PERMISSIONS = None behaviour. Before 3.0 uploaded files had different modes depending on their size; the default is now an explicit 0o644.

  • Storage code that assumed path(). Anything that uses FieldFile.path breaks on S3; use open() and url.

  • Calling FileSystemStorage.save() with os.path arguments. Since 3.1 it accepts pathlib.Path, and upload_to accepts Path since 3.0; new code needs no os.path.join.

Checklist of pitfalls

  • Forgetting enctype="multipart/form-data" or request.FILES in the form constructor: "This field is required".

  • Using the client’s file name as a path or as the stored name; always take the name save() returns.

  • Reading a whole upload with read() instead of chunks().

  • Trusting content_type, the extension or ImageField alone; no proxy size limit; serving uploads from the application’s own origin without nosniff.

  • Accepting multiple on a plain FileField, which validates one file.

  • Overriding STORAGES without the staticfiles alias, or leaving removed DEFAULT_FILE_STORAGE settings behind.

  • FileSystemStorage private storage whose inherited base_url produces public-looking but dead URLs.

  • A storage instance on a field: the migration freezes its constructor arguments; use a callable.

  • FieldFile.save()/delete() saving the model twice, and dimension fields stale after FieldFile.save() (5.1).

  • Assuming files vanish with their rows: use on_commit receivers and a periodic sweep.

  • Calling storage methods in loops over remote storages, or from async def without sync_to_async().

  • Changing request.upload_handlers after request.POST was read, or forgetting csrf_protect on the processing method.

  • Raising StopUpload in handle_raw_input(): it runs outside the parser’s error handling and becomes a 500.

  • Real S3 behaviour not exercised by a local simulator: credentials, ACLs, CORS and CDN signing need a staging bucket.
