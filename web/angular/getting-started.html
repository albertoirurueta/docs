Getting Started with Angular

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Angular is a batteries-included, TypeScript-first framework for building single-page web applications. It ships its own component model, routing, forms, HTTP client, testing tools, and a command-line interface, so a new project is productive without assembling a stack of separate libraries.

What Angular is

Angular is a framework, not just a view library. A view library (such as React) renders components and leaves routing, forms, HTTP, and build tooling to the ecosystem; Angular provides all of those as first-party, versioned packages that upgrade together.

  • TypeScript-first. Components, services, templates, and configuration are all type-checked, including expressions inside templates.

  • Single-page application (SPA) model. The browser loads one HTML shell and one JavaScript bundle; the Angular router then swaps views client-side and (optionally) lazy-loads more code on demand, so navigation does not trigger a full page reload.

  • Reactive rendering. You describe the view as a function of state. When state changes — a signal is updated, an event fires, an HTTP response arrives — Angular re-runs change detection and updates only the DOM nodes whose bound values changed.

import { Component, signal } from '@angular/core';

@Component({
  selector: 'app-greeting',
  template: `<h1>Hello, {{ name() }}</h1>`,
})
export class Greeting {
  readonly name = signal('Angular');
}

See What is Angular? and Essentials for the guided introduction.

When Angular is the right choice

Choosing a framework is a trade of flexibility against consistency. Angular sits at the consistency end:

What you get What it costs

One official answer for routing, forms, HTTP, testing, internationalisation, and the build, versioned together and upgraded with ng update.

A larger vocabulary to learn before the first feature ships: dependency injection, templates, signals and RxJS, decorators.

Strict TypeScript everywhere, including inside templates, so refactors surface errors at compile time.

Build-time compilation of templates (AOT) means an extra compile step and framework-specific error messages.

A predictable project layout and a CLI that generates code in that layout, which keeps large teams and long-lived codebases uniform.

Opinionated conventions: you adopt Angular’s structure rather than assembling your own.

A published release cadence and long-term-support windows, which suits applications maintained for many years.

A major upgrade roughly every six months to keep up with.

A view library such as React, or a lighter framework such as Vue or Svelte, is a fair choice when you want to pick every piece yourself, ship a small widget, or embed in a page that already has a stack. Angular pays off for large, multi-team, long-lived applications where uniformity matters more than freedom of choice.

The Angular CLI workspace

The Angular CLI scaffolds, serves, builds, and tests the app. Create a workspace with either command:

npm create @angular@latest my-app
# or, with the CLI installed globally (npm i -g @angular/cli):
ng new my-app

The generated workspace has a predictable layout:

my-app/
  angular.json          # workspace + build/serve/test target configuration
  package.json
  tsconfig.json         # base TypeScript config (strict type checking is the TypeScript 6 default)
  public/               # static files copied as-is into the build (favicon, images)
  src/
    main.ts             # entry point: calls bootstrapApplication(App, appConfig)
    index.html          # the single HTML shell
    styles.css          # global styles (styles.scss when created with --style=scss)
    app/
      app.ts            # root standalone component
      app.config.ts     # ApplicationConfig: the provider list
      app.routes.ts     # Routes array

Day-to-day CLI commands:

ng serve                 # dev server with hot reload at http://localhost:4200
ng build                 # production bundle into dist/
ng test                  # run unit tests
ng generate component ui/button   # scaffold a component (alias: ng g c)
ng add @angular/material          # install + configure a package
ng update                         # migrate dependencies to a newer Angular

ng generate (alias ng g) is the CLI’s code generator. Each schematic creates the file in the right folder, with a colocated spec file, using the conventions the rest of this section assumes:

Command Generates

ng g component books/book-list

a standalone component class, template, stylesheet, and spec in src/app/books/

ng g service books/book-store

a service class (an @Service() in the current release, or an @Injectable with --injectable) and its spec

ng g directive ui/highlight / ng g pipe ui/shorten

an attribute directive or a pure pipe

ng g guard auth / ng g resolver book / ng g interceptor error

a functional route guard, route resolver, or HTTP interceptor

ng g interface books/book / ng g enum books/genre / ng g class books/cart

a plain TypeScript type or class

ng g environments

the src/environments/ files and the fileReplacements entry in angular.json

ng g config vitest (or karma, browserslist)

the otherwise built-in configuration file, so you can customise it

Generated components use OnPush change detection unless you pass --change-detection=Eager, and --inline-template / --inline-style keep a small component in one file. Run any schematic with --dry-run to preview the files it would write.

See Installation for prerequisites (a current Node.js LTS) and the CLI overview for every command and flag.

Bootstrapping without a root NgModule

Modern Angular applications start from a standalone root component and a plain configuration object — there is no root NgModule. main.ts calls bootstrapApplication:

// main.ts
import { bootstrapApplication } from '@angular/platform-browser';
import { App } from './app/app';
import { appConfig } from './app/app.config';

bootstrapApplication(App, appConfig)
  .catch((err) => console.error(err));
// app.config.ts
import { ApplicationConfig, provideBrowserGlobalErrorListeners } from '@angular/core';
import { provideRouter } from '@angular/router';
import { provideHttpClient } from '@angular/common/http';
import { routes } from './app.routes';

export const appConfig: ApplicationConfig = {
  providers: [
    provideBrowserGlobalErrorListeners(),
    provideRouter(routes),
    provideHttpClient(),
  ],
};

The generated app.config.ts contains no change-detection provider at all: a workspace created by the current CLI has no zone.js polyfill, and an application without Zone.js runs zoneless by default (see Lifecycle and change detection). Add provideZoneChangeDetection() (plus the zone.js polyfill) only if you need to opt back into Zone.js. The provideZonelessChangeDetection() function from earlier releases is still exported and still valid.

Each capability is added through a provide* function in the providers array instead of by importing a feature NgModule. Libraries expose provideRouter, provideHttpClient, provideClientHydration, and so on. See Dependency injection and bootstrapApplication.

From index.html to the first render

ng build and ng serve compile the templates ahead of time and emit a bundle whose entry point is main.ts. What happens when the browser loads that bundle is the same for every application:

sequenceDiagram participant B as Browser participant M as main.ts participant A as bootstrapApplication participant I as Root injector participant R as Root component B->>B: parse index.html, find the app-root element B->>M: run the bundle M->>A: bootstrapApplication(App, appConfig) A->>I: create the platform and the root EnvironmentInjector from appConfig.providers I->>I: run environment initializers, then await app initializers A->>R: create App and match it to the app-root element R->>R: first change detection renders the template Note over B,R: later, a signal change or an event schedules the next change detection

Two consequences matter in practice. First, everything in appConfig.providers is created lazily, but provideAppInitializer() callbacks run before the root component exists, so slow work there delays the first paint. Second, the root component’s selector (app-root in the generated project) must match an element in index.html; nothing else in the HTML shell is rendered by Angular.

A first feature, end to end

The rest of this section builds on one small application, BookShelf, a catalogue of books. This is the whole first slice: a typed model, a service that owns the state in signals, a component that renders it, and a test.

// src/app/books/book.ts
export interface Book {
  id: string;
  title: string;
  author: string;
  price: number;
  rating: number;
}
// src/app/books/book-store.ts
import { Injectable, computed, signal } from '@angular/core';
import { Book } from './book';

@Injectable({ providedIn: 'root' })
export class BookStore {
  private readonly _books = signal<Book[]>([
    { id: 'b1', title: 'Learning Angular', author: 'A. Bampakos', price: 39, rating: 5 },
    { id: 'b2', title: 'Pro Angular', author: 'A. Freeman', price: 45, rating: 4 },
    { id: 'b3', title: 'Modern Angular', author: 'A. Vardanyan', price: 42, rating: 4 },
  ]);

  readonly books = this._books.asReadonly();
  readonly count = computed(() => this._books().length);
  readonly total = computed(() => this._books().reduce((sum, b) => sum + b.price, 0));

  remove(id: string): void {
    this._books.update((list) => list.filter((b) => b.id !== id));
  }
}
// src/app/books/book-list.ts
import { Component, inject } from '@angular/core';
import { CurrencyPipe } from '@angular/common';
import { BookStore } from './book-store';

@Component({
  selector: 'app-book-list',
  imports: [CurrencyPipe],
  template: `
    <h2>Books ({{ store.count() }})</h2>
    <ul>
      @for (book of store.books(); track book.id) {
        <li>
          {{ book.title }} - {{ book.price | currency: 'EUR' }}
          <button type="button" (click)="store.remove(book.id)">Remove</button>
        </li>
      } @empty {
        <li>No books yet.</li>
      }
    </ul>
    <p>Total: {{ store.total() | currency: 'EUR' }}</p>
  `,
})
export class BookList {
  protected readonly store = inject(BookStore);
}
// src/app/app.ts
import { Component } from '@angular/core';
import { BookList } from './books/book-list';

@Component({
  selector: 'app-root',
  imports: [BookList],
  template: `
    <h1>BookShelf</h1>
    <app-book-list />
  `,
})
export class App {}

Nothing here subscribes, unsubscribes, or calls a change-detection method. BookList reads signals in its template, so Angular knows which bindings depend on count(), books(), and total(), and re-renders only those when remove() updates the list. The test drives the real component tree and asserts on the rendered DOM:

// src/app/books/book-list.spec.ts
import { TestBed } from '@angular/core/testing';
import { App } from '../app';

describe('BookShelf', () => {
  it('renders the list and reacts to removals', async () => {
    const fixture = TestBed.createComponent(App);
    await fixture.whenStable();
    const el = fixture.nativeElement as HTMLElement;
    expect(el.querySelectorAll('li').length).toBe(3);
    expect(el.textContent).toContain('Total: €126.00');

    el.querySelector('button')!.click();
    await fixture.whenStable();
    expect(el.querySelector('h2')?.textContent).toBe('Books (2)');
  });
});

ng test runs this with Vitest in a jsdom environment (the CLI’s default test runner), and ng build produces the optimised bundle. Both compile the templates with the same strict checker, so a typo such as store.totl() fails the build and the test run rather than failing in the browser. Modern baseline: what’s current

Examples throughout this section assume a current major release, where the following are the default or recommended approach:

  • Standalone by default — components, directives, and pipes declare their own imports; NgModule is legacy. See Components and importing dependencies.

  • OnPush by default — a component is checked only when a signal it reads changes, one of its inputs changes, or an event fires inside it; changeDetection: ChangeDetectionStrategy.Eager opts a component back into checking on every pass (the old Default strategy, now deprecated under that name). See Components.

  • Signals for reactive state — signal(), computed(), effect(). See Signals and the signals guide.

  • Built-in control flow — @if, @for, @switch in templates instead of the legacy structural directives. See Control flow and @defer and control flow.

  • @defer blocks — declarative lazy loading of template sections. See deferrable views.

  • Zoneless change detection — the default for a new application: no Zone.js dependency, and change detection is scheduled from signals and events. See Lifecycle and change detection and zoneless.

  • SSR with hydration — @angular/ssr renders on the server and the client reuses that DOM. See Production and performance and server-side rendering.

Angular ships a major release roughly every six months, with an active-support window followed by long-term support (LTS). Read the update guide to migrate between versions and the release schedule for support windows and the deprecation policy.

Tooling

Angular DevTools is a browser extension (Chrome and Firefox) that adds a component-tree inspector, a signal/property viewer, and a change-detection profiler. Install it and open the Angular tab in the browser developer tools. See Angular DevTools.

The Angular Language Service powers editor features for templates: autocompletion, go-to-definition, type-aware diagnostics, and hover information for bindings written in HTML files or inline template strings. It runs in VS Code (the official Angular Language Service extension), WebStorm, and any editor with a TypeScript plugin host. See Angular Language Service.

Editor setup is minimal: enable the Angular Language Service extension, turn on format-on-save (Prettier handles both TypeScript and templates), and keep the workspace tsconfig.json strict settings that ng new generates. VS Code with the language service is the most common setup and needs no further configuration.
