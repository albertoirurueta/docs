Lifecycle and Change Detection

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A component moves through a fixed sequence of lifecycle hooks from creation to destruction, and Angular keeps the DOM in sync with component state through change detection. Modern signal-based code needs fewer hooks, but understanding both is essential for performance work.

Lifecycle hooks

Implement the matching interface (OnInit, OnDestroy, …​) and Angular calls the method at the right time.

Hook When it runs

ngOnChanges(changes)

Before ngOnInit and again whenever a bound input changes — decorator @Input() properties and signal input() properties alike. changes maps each changed input to its previousValue, currentValue, and firstChange. New code usually reacts with computed() / effect() instead and has no need for the hook.

ngOnInit()

Once, after the first ngOnChanges — inputs are set. Do initialisation here.

ngDoCheck()

Every change-detection run. Custom dirty-checking only; keep it cheap.

ngAfterContentInit()

Once, after projected content (<ng-content>) is initialised.

ngAfterContentChecked()

After every check of projected content.

ngAfterViewInit()

Once, after the component’s own view and child views exist — view queries are resolved.

ngAfterViewChecked()

After every check of the component’s view.

ngOnDestroy()

Just before Angular destroys the component. Unsubscribe, clear timers.

 
import { Component, OnInit, OnDestroy, inject } from '@angular/core';

@Component({ selector: 'app-clock', template: '{{ now }}' })
export class Clock implements OnInit, OnDestroy {
  now = '';
  private id?: ReturnType<typeof setInterval>;

  constructor() {
    // DI and field setup only -- inputs are NOT available yet.
  }

  ngOnInit(): void {
    this.id = setInterval(() => (this.now = new Date().toLocaleTimeString()), 1000);
  }

  ngOnDestroy(): void {
    clearInterval(this.id);
  }
}

constructor vs. ngOnInit: the constructor runs at class instantiation, before Angular sets inputs or resolves queries — use it only for inject() and simple field initialisation. Put anything that reads inputs or starts work in ngOnInit. See Component lifecycle.

The hooks in practice

The table above is easier to trust once you have watched it happen. The component below logs every hook, an effect(), an afterNextRender() callback, and a DestroyRef callback. A parent renders it with @if, changes one bound input, and finally removes it.

import {
  AfterContentChecked, AfterContentInit, AfterViewChecked, AfterViewInit, Component, DestroyRef, DoCheck,
  Input, OnChanges, OnDestroy, OnInit, SimpleChanges, afterNextRender, effect, inject, input, signal,
} from '@angular/core';

export const log: string[] = [];

@Component({ selector: 'app-book-title', template: '<ng-content />{{ title }}' })
export class BookTitle
  implements OnChanges, OnInit, DoCheck, AfterContentInit, AfterContentChecked, AfterViewInit, AfterViewChecked, OnDestroy {
  @Input() title = '';
  readonly subtitle = input('');

  constructor() {
    log.push('constructor');
    effect(() => log.push(`effect(subtitle=${this.subtitle()})`));
    afterNextRender(() => log.push('afterNextRender'));
    inject(DestroyRef).onDestroy(() => log.push('DestroyRef.onDestroy'));
  }
  ngOnChanges(c: SimpleChanges) { log.push(`ngOnChanges(${Object.keys(c).join(',')})`); }
  ngOnInit() { log.push('ngOnInit'); }
  ngDoCheck() { log.push('ngDoCheck'); }
  ngAfterContentInit() { log.push('ngAfterContentInit'); }
  ngAfterContentChecked() { log.push('ngAfterContentChecked'); }
  ngAfterViewInit() { log.push('ngAfterViewInit'); }
  ngAfterViewChecked() { log.push('ngAfterViewChecked'); }
  ngOnDestroy() { log.push('ngOnDestroy'); }
}

@Component({
  imports: [BookTitle],
  template: `@if (show()) { <app-book-title [title]="t()" [subtitle]="'a classic'" /> }`,
})
export class Host {
  readonly show = signal(true);
  readonly t = signal('Dune');
}

Creating the host, then calling t.set('Emma'), then show.set(false) — awaiting fixture.whenStable() after each step in a test — produced this log:

Three things are worth reading off it. First, the "init" hooks (ngOnInit, ngAfterContentInit, ngAfterViewInit) fire exactly once, while ngDoCheck and the two Checked hooks fire on every pass that reaches the component. Second, the effect() created in the constructor does not run in the constructor: it is scheduled and runs during change detection, here after ngDoCheck and before the content hooks, and it did not run again when only title changed because it does not read it. Third, afterNextRender fires last, after Angular has written the DOM, and never on the server.

Where should this code go?

I need to …​ Put it in

inject services, initialise fields

the constructor or a field initializer with inject()

fetch data, start a timer or a subscription once inputs are known

ngOnInit (or a resource() driven by input signals)

derive a value from inputs

computed() — no hook at all

react to a changing value with a side effect

effect()

compare the previous and the new value of an input

ngOnChanges, or linkedSignal() with the previous-state form

measure or touch the real DOM (size, focus, a chart library)

afterNextRender / afterEveryRender — browser only

release a listener, timer or subscription

DestroyRef.onDestroy() or takeUntilDestroyed()

Reading a viewChild() signal needs no hook either: it is undefined until the view exists and then updates by itself, so use it from a computed() or an effect() rather than from ngAfterViewInit.

Cleanup: DestroyRef and render callbacks

DestroyRef.onDestroy(fn) registers teardown without implementing OnDestroy, and takeUntilDestroyed() (from @angular/core/rxjs-interop) completes an observable when the injection context is destroyed — the cleanest way to end a subscription.

import { Component, DestroyRef, inject } from '@angular/core';
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';
import { interval } from 'rxjs';

@Component({ selector: 'app-ticker', template: '{{ tick }}' })
export class Ticker {
  tick = 0;
  private readonly destroyRef = inject(DestroyRef);

  constructor() {
    interval(1000)
      .pipe(takeUntilDestroyed())          // auto-unsubscribe on destroy
      .subscribe(() => (this.tick++));

    this.destroyRef.onDestroy(() => console.log('ticker gone'));
  }
}

afterNextRender(fn) runs a callback once after the next render, and afterEveryRender(fn) (named afterRender in earlier releases) after every render — both browser-only, for measuring or manipulating the real DOM after Angular has written to it. See afterNextRender.

How change detection works

Change detection is Angular checking each component’s template bindings and updating the DOM where a bound value changed. It runs top-down from the root component.

  • Zone.js (the traditional model) monkey-patches async APIs — addEventListener, setTimeout, fetch, promises — and tells Angular to run change detection after each such task completes. It is the reason a click handler that mutates a field "just updates the view".

  • ChangeDetectionStrategy.Eager checks a component on every pass; ChangeDetectionStrategy.OnPush checks it only when: an input binding changes (a new reference, for objects), an event fires inside it, a signal it reads in its template changes, an async pipe in its template emits, or ChangeDetectorRef.markForCheck() is called. From Angular 22 OnPush is the default for every component that does not set changeDetection, and Eager is the explicit opt-out; in earlier releases the always-check strategy was called Default and was the default (Default still compiles in 22 as a deprecated alias of Eager). OnPush everywhere is the main lever for large-app performance.

  • ChangeDetectorRef gives manual control: markForCheck() schedules this component (and its ancestors) to be checked next pass; detach() removes it from the tree entirely; detectChanges() runs a synchronous check of it now; reattach() reverses detach().

  • Signals integrate directly: when a signal read in a template changes, Angular marks exactly that component dirty — no markForCheck needed, and it works the same under OnPush.

  • Zoneless change detection (provideZonelessChangeDetection(), stable since v20) drops Zone.js entirely, and workspaces generated by the current CLI start that way: ng new produces no zone.js polyfill and no change-detection provider, because zoneless is the default. Angular then schedules a check only from explicit signals: signal writes, async pipe emissions, markForCheck(), and template event bindings. In an existing app, remove zone.js from polyfills and prefer signals for all reactive state; to keep the zone-based model in a new one, add provideZoneChangeDetection() and the zone.js polyfill back.

// main.ts -- opt into zoneless
import { bootstrapApplication } from '@angular/platform-browser';
import { provideZonelessChangeDetection } from '@angular/core';
import { App } from './app/app';

bootstrapApplication(App, {
  providers: [provideZonelessChangeDetection()],
});
import { ChangeDetectionStrategy, Component, input } from '@angular/core';

@Component({
  selector: 'app-row',
  changeDetection: ChangeDetectionStrategy.OnPush,   // the default from Angular 22; explicit in earlier releases
  template: '{{ label() }}',
})
export class Row {
  readonly label = input.required<string>();   // signal input -> marks Row dirty on change
}

References: Runtime performance and Zoneless.

OnPush in practice: mutation versus a new reference

OnPush compares input references. The component below reads a decorator input, so it only re-renders when the parent passes a different object:

@Component({
  selector: 'app-row',
  changeDetection: ChangeDetectionStrategy.OnPush,
  template: '{{ book.title }}',
})
export class Row {
  @Input() book!: { id: number; title: string };
  readonly cdr = inject(ChangeDetectorRef);
}

Run against a fixture, the three ways of changing the data behave like this:

const fixture = TestBed.createComponent(Row);
const book = { id: 1, title: 'Dune' };
fixture.componentRef.setInput('book', book);
await fixture.whenStable();                      // renders "Dune"

book.title = 'Emma';                             // 1. mutate in place
await fixture.whenStable();                      //    still renders "Dune"

fixture.componentInstance.cdr.markForCheck();    // 2. mark the view dirty by hand
await fixture.whenStable();                      //    renders "Emma"

fixture.componentRef.setInput('book', { ...book, title: 'Persuasion' });  // 3. new reference
await fixture.whenStable();                      //    renders "Persuasion"

The robust fix is not markForCheck() but immutable updates ({ ...book, title }) or signals: a signal read in the template marks exactly that view dirty on its own, with no reference comparison involved.

ExpressionChangedAfterItHasBeenChecked (NG0100)

In development mode Angular runs a second, read-only pass after each check and compares every binding with the value it just rendered. If a hook or a getter changed a value between the two passes, the build throws NG0100. The classic cause is changing parent-visible state inside ngAfterViewInit, which runs after the view was already checked:

@Component({ selector: 'app-bad', changeDetection: ChangeDetectionStrategy.Eager, template: '{{ title }}' })
export class Bad implements AfterViewInit {
  title = 'before';
  ngAfterViewInit() { this.title = 'after'; }   // NG0100: Previous value: 'before'. Current value: 'after'
}

Keep such state in a signal and set it where Angular expects it: afterNextRender(() => this.title.set('after')) (or an effect, or simply an earlier hook). The signal write schedules a clean second pass instead of contradicting the first one.
