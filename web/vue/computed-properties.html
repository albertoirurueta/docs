Computed Properties

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A computed property is a reactive value derived from other reactive state. You give computed() a getter; it returns a ref whose .value is the getter’s result, recomputed only when a dependency changes. This page follows Computed Properties and the computed() API entry.

The basics

<script setup>
import { ref, computed } from 'vue'

const first = ref('Ada')
const last = ref('Lovelace')

const fullName = computed(() => `${first.value} ${last.value}`)
</script>

<template>
  <p>{{ fullName }}</p>   <!-- auto-unwrapped, like any ref -->
</template>

In the template fullName behaves like the other refs. In script you read fullName.value.

Caching vs. a method

A computed property caches. Its getter re-runs only when one of the reactive values it read last time changes; any number of reads in between return the stored result. A method, by contrast, runs on every re-render, because the template has no way to know whether its result would differ.

<script setup>
import { ref, computed } from 'vue'

const list = ref([1, 2, 3, 4, 5, 6])

// cached: recomputed only when `list` changes
const evens = computed(() => list.value.filter((n) => n % 2 === 0))

// not cached: runs on every render that calls it
function evensNow() {
  return list.value.filter((n) => n % 2 === 0)
}
</script>

For an expensive derivation — filtering a large array, formatting dates, walking a tree — the cache is the whole point. computed also does not recompute when an unrelated piece of state triggers the re-render.

When a method is the right choice

Use a method (or a plain function) instead of computed when:

  • the result takes arguments — formatPrice(item) in a v-for; a computed takes none;

  • you want it to run every time on purpose, e.g. Date.now() or Math.random(), which have no reactive dependency to cache against;

  • it performs an action rather than producing a value — see Reactivity Fundamentals and watch for side effects.

Writable computed

Pass an object with get and set to make a computed assignable. The setter runs when code writes .value, and typically writes back to the underlying refs.

<script setup>
import { ref, computed } from 'vue'

const first = ref('Ada')
const last = ref('Lovelace')

const fullName = computed({
  get() {
    return `${first.value} ${last.value}`
  },
  set(value) {
    [first.value, last.value] = value.split(' ')
  },
})

fullName.value = 'Grace Hopper'   // runs set(); first -> 'Grace', last -> 'Hopper'
</script>

Keep getters pure

A getter must only compute and return. Do not mutate other reactive state, perform async requests, or touch the DOM inside it — those make the value unpredictable and can loop. Put effects in watch or watchEffect. It is also fine to return a fresh object or array from a getter; since 3.4 Vue compares the getter’s result and skips downstream updates when it is deeply unchanged from the previous run, so a stable value does not cause needless re-renders.

computed vs. watch

Both react to state, but they answer different questions:

Use computed when Use watch / watchEffect when

you need a value that is a pure function of other state

you need a side effect — fetch data, write to localStorage, start a timer — in response to a change

the template or other logic reads the result

nothing reads a result; you are reacting, not deriving

Reaching for watch to copy one ref into another is almost always a computed in disguise. See Reactivity Fundamentals for watch.

How the cache decides to recompute

A computed ref is both a subscriber and a source. While its getter runs it subscribes to every reactive value it reads; other effects (a component render, a watch) that read the computed subscribe to it in turn. When a source changes, the computed is only marked dirty — the getter does not run yet. The getter runs lazily, the next time somebody reads .value, and only if one of its sources really changed since the last run.

sequenceDiagram participant S as ref (source) participant C as computed participant R as render effect R->>C: read .value C->>S: getter reads the source (dependency tracked) C-->>R: value, cached S->>C: source written (computed marked dirty) C->>R: notify subscribers R->>C: re-render reads .value again C->>S: getter re-runs, tracks again C-->>R: new value (unchanged value stops further updates)

This laziness and the cache are observable. The first script below counts how often the getter runs:

import { ref, computed } from 'vue'

const todos = ref([{ done: true }, { done: false }, { done: false }])
const other = ref(0)
let runs = 0

const remaining = computed(() => {
  runs++
  return todos.value.filter((t) => !t.done).length
})

console.log(remaining.value, remaining.value, runs) // 2 2 1   -- second read is cached
other.value++                                        // unrelated state
console.log(remaining.value, runs)                   // 2 1     -- still cached
todos.value[0].done = false                          // a dependency changes
console.log(remaining.value, runs)                   // 3 2     -- recomputed once

Running it prints 2 2 1, 2 1 and 3 2, as the comments say. Note that other.value++ did not even mark the computed dirty, because the getter never read other.

Worked example: a filtered and sorted todo view

Real views usually chain several derivations. Splitting them into separate computed properties means each step caches independently: toggling the sort direction re-sorts, but does not re-filter.

<script setup>
import { ref, computed } from 'vue'

const todos = ref([
  { id: 1, text: 'write docs', done: false },
  { id: 2, text: 'ship release', done: true },
  { id: 3, text: 'answer mail', done: false }
])
const filter = ref('open') // 'all' | 'open' | 'done'
const sortAsc = ref(true)

// step 1: filter
const filtered = computed(() =>
  todos.value.filter((t) =>
    filter.value === 'all' ? true : filter.value === 'done' ? t.done : !t.done
  )
)

// step 2: sort a copy of step 1 -- re-runs only when `filtered` or `sortAsc` changes
const visible = computed(() => {
  const copy = [...filtered.value]
  copy.sort((a, b) => a.text.localeCompare(b.text))
  return sortAsc.value ? copy : copy.reverse()
})

const summary = computed(() => `${visible.value.length} of ${todos.value.length} shown`)
</script>

<template>
  <button @click="sortAsc = !sortAsc">Sort {{ sortAsc ? 'Z-A' : 'A-Z' }}</button>
  <ul>
    <li v-for="t in visible" :key="t.id">{{ t.text }}</li>
  </ul>
  <p>{{ summary }}</p>
</template>

The open todos render as answer mail, write docs, the summary reads 2 of 3 shown, and one click on the button reverses the order. The sort works on a copy ([...filtered.value]) because Array.prototype.sort mutates in place, and a getter must not change the state it reads.

Reading the previous value

Since Vue 3.4 the getter receives the value it returned last time as its first argument. That is useful for values that should only move forward or ignore some inputs:

import { ref, computed } from 'vue'

const count = ref(2)

// Vue 3.4+: the getter receives the previous value as its first argument
const alwaysSmall = computed((previous) => {
  if (count.value <= 3) return count.value
  return previous ?? 0
})

console.log(alwaysSmall.value) // 2
count.value = 3
console.log(alwaysSmall.value) // 3
count.value = 4
console.log(alwaysSmall.value) // 3  -- kept the previous value
count.value = 1
console.log(alwaysSmall.value) // 1

A computed whose getter returns the same value as before (compared with Object.is) does not notify its subscribers, so downstream effects and renders are skipped. Returning the previous value, as above, is the way to get that behaviour for objects as well.

Computed in a component versus outside one

computed() called during setup is tied to the component: Vue stops its subscriptions when the component unmounts. Called anywhere else — a module, a store, a test — the computed lives as long as its sources do. In a long-lived module that holds a computed over short-lived data, create it inside an effectScope() so you can dispose of it together with its siblings; Composables shows the pattern.

Debugging a computed

For development, computed() accepts onTrack and onTrigger hooks as a second (or, with the object form, extra) argument. onTrack fires when a dependency is collected; onTrigger fires when a dependency change schedules the recompute. Both receive a DebuggerEvent you can log or debugger-break on.

import { computed } from 'vue'

const total = computed(
  () => items.value.reduce((sum, i) => sum + i.price, 0),
  {
    onTrack(e) {
      // e.target, e.type, e.key -- which dependency was read
      console.log('tracked', e)
    },
    onTrigger(e) {
      // e.oldValue, e.newValue -- what changed
      debugger
    },
  },
)

These hooks are stripped from production builds. The advanced debugging APIs are listed under computed() and Reactivity Fundamentals.
