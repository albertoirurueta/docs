Template Refs

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A template ref is a direct handle to a DOM element or child component instance that the template rendered — for focus management, measuring, driving an animation, or wiring up a non-Vue library. Reach for one only when props and events cannot express what you need. The reference is Template Refs and useTemplateRef().

useTemplateRef

Since 3.5, useTemplateRef('name') returns a ref whose value is the element or component carrying the matching ref="name" attribute.

<script setup>
import { useTemplateRef, onMounted } from 'vue'

const input = useTemplateRef('search')

onMounted(() => {
  input.value.focus()
})
</script>

<template>
  <input ref="search">
</template>

The string must match the ref attribute. The attribute may itself be bound (:ref="dynamicName"), and useTemplateRef handles that.

The classic pattern

Before 3.5 — and still valid — you declare a ref whose variable name equals the ref attribute value:

<script setup>
import { ref, onMounted } from 'vue'

const input = ref(null)   // matches ref="input"

onMounted(() => input.value.focus())
</script>

<template>
  <input ref="input">
</template>

useTemplateRef is preferred in new code: it separates the variable name from the attribute string and is easier to type.

Timing

flowchart LR s["setup() runs
ref is null"] --> m["mount: element created
ref = element"] m --> om["onMounted
ref is safe to use"] om --> rm["v-if turns false
or unmount
ref = null"] rm -->|"v-if true again"| m

The ref is null until the component mounts and is populated by the time onMounted runs. If the element is later removed (an enclosing v-if turns false) the ref returns to null. Never read the ref synchronously during setup — the DOM does not exist yet. To act on the first assignment with a watcher, use flush: 'post' (see Watchers):

watch(input, (el) => {
  if (el) el.focus()
}, { flush: 'post' })

Refs inside v-for

Put ref on an element inside v-for and the ref holds an array of those elements, populated after mount. The array order is not guaranteed to match the source array.

<script setup>
import { ref, useTemplateRef } from 'vue'

const list = ref([1, 2, 3])
const items = useTemplateRef('items')   // array of <li> after mount
</script>

<template>
  <ul>
    <li v-for="n in list" :key="n" ref="items">{{ n }}</li>
  </ul>
</template>

Function refs

Bind :ref to a function instead of a string. Vue calls it on mount with the element and on unmount with null — handy for storing handles in a Map. See Function Refs.

<script setup>
import { ref } from 'vue'
const cells = ref(new Map())
</script>

<template>
  <div
    v-for="row in rows"
    :key="row.id"
    :ref="(el) => { if (el) cells.set(row.id, el) }" />
</template>

An inline arrow is a new function on every render, so the ref detaches and re-attaches each update; use a stable method reference if that matters.

Refs on a component

A ref on a child gives you the child’s instance. A <script setup> child is closed by default — the parent sees nothing unless the child calls defineExpose(). See Ref on Component.

<!-- Child.vue -->
<script setup>
import { ref } from 'vue'

const count = ref(0)
function reset() { count.value = 0 }

defineExpose({ count, reset })
</script>
<!-- Parent.vue -->
<script setup>
import { useTemplateRef, onMounted } from 'vue'
import Child from './Child.vue'

const child = useTemplateRef('child')

onMounted(() => {
  child.value.reset()
  console.log(child.value.count)   // exposed refs are unwrapped
})
</script>

<template>
  <Child ref="child" />
</template>

Components authored with the Options API or a plain setup() return are exposed by default; <script setup> components are not.

A ref, or props and events?

A template ref is imperative and couples the parent to the child’s internals. Prefer the declarative interface first:

  • Data going in → props.

  • Data or notifications coming out → emitted events (Component Events and v-model).

  • Two-way on a form-like child → v-model / defineModel().

Keep refs for genuinely imperative actions with no state to model: focus, scroll, play and pause, measuring text, kicking off an animation, or handing an element to a charting library.

Worked example: a task composer that manages focus

The running example is a task list. Its input box shows what refs are for: imperative behaviour with no state to model. TaskComposer focuses its input when it appears and again after each submission, and exposes a focus() method so a parent can pull focus back to it:

<!-- src/components/TaskComposer.vue -->
<script setup lang="ts">
import { ref, useTemplateRef, onMounted } from 'vue'

const emit = defineEmits<{ add: [title: string] }>()
const title = ref('')
const input = useTemplateRef<HTMLInputElement>('title-input')

function submit() {
  if (!title.value.trim()) return
  emit('add', title.value.trim())
  title.value = ''
  input.value?.focus()          // the element exists, so the ref is set
}

onMounted(() => input.value?.focus())

defineExpose({ focus: () => input.value?.focus() })
</script>

<template>
  <form @submit.prevent="submit">
    <input ref="title-input" v-model="title" aria-label="New task">
    <button>Add</button>
  </form>
</template>

Two details matter here. The typed argument of useTemplateRef<HTMLInputElement> makes input.value an HTMLInputElement | null, so the optional chain is required by the type checker as well as by the mount timing. And the exposed focus function, not the element, is the component’s public surface: the parent never learns that an <input> exists.

A test needs the component attached to the document, because document.activeElement only reports elements that are in it:

import { it, expect } from 'vitest'
import { mount } from '@vue/test-utils'
import TaskComposer from '@/components/TaskComposer.vue'

it('focuses on mount, again after submit, and exposes focus()', async () => {
  const wrapper = mount(TaskComposer, { attachTo: document.body })
  const input = wrapper.get('input').element as HTMLInputElement
  expect(document.activeElement).toBe(input)

  input.blur()
  await wrapper.get('input').setValue('Write docs')
  await wrapper.get('form').trigger('submit')
  expect(wrapper.emitted('add')).toEqual([['Write docs']])
  expect(document.activeElement).toBe(input)

  input.blur()
  ;(wrapper.vm as unknown as { focus(): void }).focus()   // the exposed method
  expect(document.activeElement).toBe(input)
  wrapper.unmount()
})

Scrolling a new row into view

A function ref stores one element per task, keyed by id, which a plain v-for array cannot do reliably because its order is not guaranteed. A flush: 'post' watcher then runs after the new row has been rendered:

<!-- src/components/TaskScroller.vue -->
<script setup lang="ts">
import { ref, useTemplateRef, watch } from 'vue'
import TaskComposer from './TaskComposer.vue'

const tasks = ref([{ id: 1, title: 'first' }])
const rows = new Map<number, HTMLElement>()
const composer = useTemplateRef<InstanceType<typeof TaskComposer>>('composer')

function setRow(id: number, el: unknown) {
  if (el) rows.set(id, el as HTMLElement)
  else rows.delete(id)              // Vue calls the function with null on unmount
}

function add(title: string) {
  tasks.value.push({ id: tasks.value.length + 1, title })
}

watch(() => tasks.value.length, () => {
  const last = tasks.value[tasks.value.length - 1]
  rows.get(last.id)?.scrollIntoView({ block: 'end' })
}, { flush: 'post' })
</script>

<template>
  <TaskComposer ref="composer" @add="add" />
  <ul>
    <li v-for="t in tasks" :key="t.id" :ref="(el) => setRow(t.id, el)">{{ t.title }}</li>
  </ul>
</template>

rows is a plain Map, not a ref: nothing renders from it, so there is no reason to make it reactive. Without flush: 'post' the callback would run before the DOM patch and rows.get(last.id) would still be undefined. InstanceType<typeof TaskComposer> types the component ref, including the members passed to defineExpose, so composer.value?.focus() is checked by vue-tsc.

jsdom does not implement layout, so scrollIntoView is absent there; a test replaces it with a spy on Element.prototype and asserts it was called on the right element.

Pitfalls

  • Reading a ref in setup or in the template of the first render. It is null; use onMounted, a flush: 'post' watcher, or optional chaining.

  • Refs inside v-if and v-for. They come and go with the element; never cache the element in another variable.

  • One ref per element. An element carries a single ref attribute; a function ref can store the element in several places if you need that.

  • Ref names with hyphens. ref="title-input" works with useTemplateRef('title-input'); the classic variable-name pattern cannot match such a name, one more reason to prefer useTemplateRef.

  • Changing a child’s state through its ref. If the parent writes to child.value.count, the data flow becomes invisible; expose a method with a clear name instead, or use props.
