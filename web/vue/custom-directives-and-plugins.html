Custom Directives and Plugins

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Custom directives and plugins are Vue’s two extension points for logic that is not a component. A directive packages low-level DOM access you attach to an element with a v- attribute; a plugin is an object that installs app-wide features — components, directives, global properties, injected values — through a single app.use() call.

Custom directives

A directive is an object of lifecycle hooks that each receive the raw element. Inside <script setup>, any camelCase binding named vSomething is usable as v-something in that component’s template:

<script setup>
// registers v-focus for this component only
const vFocus = {
  mounted: (el) => el.focus()
}
</script>

<template>
  <input v-focus />
</template>

Use a directive when you genuinely need direct DOM manipulation that a binding or component cannot express — managing focus, integrating a non-Vue widget, custom scroll behaviour. See Custom Directives.

The hook set

Every hook is optional and receives (el, binding, vnode, prevVnode):

Hook Called

created

before the element’s attributes and event listeners are applied

beforeMount

before the element is inserted into the DOM

mounted

after the element and its parent component are mounted

beforeUpdate

before the containing component re-renders

updated

after the component and its children have updated

beforeUnmount

before the element is unmounted

unmounted

after the element has been removed

The list and each hook’s timing are in Directive Hooks.

Function shorthand

When the behaviour is the same on mounted and updated, pass a function instead of an object — it is registered as both hooks:

app.directive('color', (el, binding) => {
  el.style.color = binding.value   // runs on mounted AND updated
})

The binding object

The second argument carries the parsed template usage. For v-pin:right.far="offset":

Property Value

binding.value

the current value of the expression — here whatever offset holds

binding.oldValue

the previous value; available in beforeUpdate and updated only

binding.arg

"right" — can be dynamic, e.g. v-pin:[side]

binding.modifiers

an object of flags — here { far: true }

binding.instance

the component instance that is using the directive

 
app.directive('pin', (el, binding) => {
  el.style.position = 'fixed'
  const side = binding.arg || 'top'
  const offset = binding.modifiers.far ? '64px' : '16px'
  el.style[side] = offset
})
// <span v-pin:right.far="true">pinned</span>

Local vs. global registration

Global registration — app.directive('focus', { ... }) in main.js — makes the directive available everywhere but invisible at the point of use. Prefer local registration: the vFocus object in <script setup>, or the directives option in an Options-API component:

// Options API -- local registration (contrast form)
export default {
  directives: {
    focus: { mounted: (el) => el.focus() }
  }
}

Directives on components

Discouraged. On a component with a single root node the directive applies to that root, like a fallthrough attribute; on a component with multiple root nodes it is ignored and Vue emits a warning. Prefer a prop or a wrapper element. See Usage on Components.

Plugins

A plugin is any object exposing an install(app, options) method (or a plain function used as that method). app.use(plugin, options) invokes it once and ignores repeat calls for the same plugin. Inside install you have the full application API — register components and directives, add global properties, or provide injectable values:

// plugins/i18n.js
export default {
  install(app, options) {
    const dict = options.messages ?? {}
    const translate = (key) => dict[key] ?? key

    // 1. a global property -- usable as $t in every template
    app.config.globalProperties.$t = translate

    // 2. an injectable value -- for inject('i18n') in <script setup>
    app.provide('i18n', { t: translate })

    // 3. ship a component and a directive with the plugin
    app.component('I18nText', {
      props: ['k'],
      setup: (props) => () => translate(props.k)
    })
    app.directive('t', (el, binding) => {
      el.textContent = translate(binding.value)
    })
  }
}
// main.js
import { createApp } from 'vue'
import App from './App.vue'
import i18n from './plugins/i18n.js'

createApp(App)
  .use(i18n, { messages: { hello: 'Hola', bye: 'Adios' } })
  .mount('#app')

Consume the provided value in a component:

<script setup>
import { inject } from 'vue'
const i18n = inject('i18n')
</script>

<template>
  <h1>{{ i18n.t('hello') }}</h1>
  <p v-t="'bye'"></p>
</template>

The install contract and app.use are documented in Plugins; providing values app-wide is app.provide; and to give $t a type on ComponentCustomProperties, see Augmenting Global Properties.

A toast plugin

A second, smaller example — a plugin that mounts its own host element and exposes an imperative push:

// plugins/toast.js
import { createApp, reactive } from 'vue'
import ToastHost from './ToastHost.vue'

export default {
  install(app) {
    const state = reactive({ items: [] })
    const push = (text) => state.items.push({ id: Date.now(), text })

    const mountPoint = document.createElement('div')
    document.body.appendChild(mountPoint)
    createApp(ToastHost, { state }).mount(mountPoint)

    app.provide('toast', { push })
    app.config.globalProperties.$toast = push
  }
}

Every mainstream Vue library follows this shape — app.use(pinia), app.use(router), app.use(i18n). See Routing for the router’s own app.use(router) call.

When the directive hooks run

Directive hooks are tied to the lifecycle of the element, not of a component, and they run while Vue creates, patches and removes it. Cleanup you register in mounted belongs in beforeUnmount (or unmounted), because Vue does not undo anything a directive attached to the DOM or to document.

flowchart TD A["created: before attributes and listeners are applied"] --> B["beforeMount: before insertion"] B --> C["mounted: element is in the DOM"] C --> D{"component re-renders?"} D -->|"yes"| E["beforeUpdate"] E --> F["updated: children also updated"] F --> D D -->|"element removed"| G["beforeUnmount: element still attached"] G --> H["unmounted: element removed"]

Worked example: a click-outside directive for the todo menu

Closing a menu when the user clicks elsewhere needs a listener on document, which a component template cannot express. That is a typical directive. The listener is registered in mounted, kept up to date in updated (an inline arrow function in the template is a new function on every render), and removed in beforeUnmount. Registration is deferred by one task with setTimeout: the click that opens the menu is still bubbling towards document when Vue renders the menu, and a listener added at that moment would see the very same click as an outside click and close the menu immediately. The timer is cleared on unmount in case the element disappears before it fires.

// directives/vClickOutside.js -- calls the bound function when a click lands outside the element
const states = new WeakMap()

export const vClickOutside = {
  mounted(el, binding) {
    const state = {
      callback: binding.value,
      listener(event) {
        if (!el.contains(event.target)) state.callback(event)
      }
    }
    // Wait one task: the click that rendered this element is still bubbling towards `document`
    // and would otherwise be treated as an outside click and close the menu at once.
    const timer = setTimeout(() => document.addEventListener('click', state.listener))
    state.stop = () => {
      clearTimeout(timer)
      document.removeEventListener('click', state.listener)
    }
    states.set(el, state)
  },
  // the inline arrow in the template is a new function on every render: keep the latest one
  updated(el, binding) {
    states.get(el).callback = binding.value
  },
  beforeUnmount(el) {
    states.get(el).stop()
    states.delete(el)
  }
}
<script setup>
import { ref } from 'vue'
import { vClickOutside } from './directives/vClickOutside.js'

const open = ref(false)
</script>

<template>
  <div>
    <button class="toggle" @click="open = !open">Menu</button>
    <ul v-if="open" v-click-outside="() => (open = false)" class="menu">
      <li>Clear completed</li>
      <li>Export</li>
    </ul>
  </div>
</template>

In a jsdom test the menu opens on the toggle click (after one task has passed), stays open when the menu itself is clicked, and closes when document.body is clicked. The per-element state lives in a WeakMap rather than on the element, so the directive never adds properties to DOM nodes and cannot leak: when the element is garbage collected its state goes with it.

A subtle point is that the toggle button is outside the menu. Clicking the button while the menu is open runs the toggle handler (closing the menu) and also the document listener (closing it again), which is harmless here because both set the same value; for a directive that must tell the two apart, compare event.target against the trigger element as well.

Worked example: a plugin with configuration, a directive and an injection key

The earlier i18n plugin used a string key. A plugin that is meant for reuse should export a unique Symbol key so that two plugins cannot collide, and should merge caller options over defaults:

// plugins/todoDefaults.js
export const defaultsKey = Symbol('todoDefaults')

export default {
  install(app, options = {}) {
    const defaults = { filter: 'all', storageKey: 'todos', ...options }

    // 1. injectable configuration
    app.provide(defaultsKey, defaults)

    // 2. a directive shipped with the plugin
    app.directive('autofocus', { mounted: (el) => el.focus() })

    // 3. a global property for templates
    app.config.globalProperties.$todoDefaults = defaults
  }
}
<script setup>
import { inject } from 'vue'
import { defaultsKey } from './plugins/todoDefaults.js'

const defaults = inject(defaultsKey)
</script>

<template>
  <input v-autofocus />
  <p>{{ defaults.storageKey }} / {{ $todoDefaults.filter }}</p>
</template>

Installing it with app.use(todoDefaults, { filter: 'open' }) and mounting renders todos / open, and the input receives focus. Calling app.use a second time with the same plugin and different options changes nothing: Vue logs "Plugin has already been applied to target app" and ignores the call, so options must be given at the first installation.

sequenceDiagram participant M as main.js participant A as app instance participant P as plugin install M->>A: createApp(App) M->>A: app.use(plugin, options) A->>P: install(app, options) P->>A: provide, directive, component, globalProperties M->>A: app.mount('#app') Note over M,A: registrations made after mount are not applied to the already-rendered tree

Choosing the right extension point

Need Mechanism

Reusable stateful logic, with or without lifecycle hooks

Composable

Direct access to a DOM element (focus, measurement, third-party widget, document listeners)

Custom directive

Reusable markup with props, slots and events

Component

App-wide registration and configuration, installed once

Plugin

Intercepting every component of the app, such as a global error or warning handler

app.config options (errorHandler, warnHandler)

Mixins: legacy only

Before the Composition API, a mixin shared option fragments between components:

// legacy pattern -- avoid in new code
export const paginationMixin = {
  data: () => ({ page: 1 }),
  methods: { next() { this.page++ } }
}

export default {
  mixins: [paginationMixin]
}

Merged options hide where page and next came from, two mixins can silently collide on a name, and a mixin takes no arguments. The Vue documentation now points to composables for stateful reuse, custom directives for DOM logic, and plugins for app-level installation — see Composables vs. Mixins.
