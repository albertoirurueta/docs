Conditional and List Rendering

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Two directive families control what a template produces: v-if / v-show decide whether an element renders, and v-for repeats one. They follow Conditional Rendering and List Rendering.

v-if, v-else, v-else-if

v-if renders its element only when the expression is truthy. v-else-if and v-else chain from it and must sit on the immediately following sibling element.

<template>
  <p v-if="status === 'loading'">Loading...</p>
  <p v-else-if="status === 'error'">Something went wrong.</p>
  <ul v-else>
    <li v-for="item in items" :key="item.id">{{ item.label }}</li>
  </ul>
</template>

When v-if is false the element and its component children are not created; toggling it later mounts and unmounts them, running lifecycle hooks each time.

v-if on <template>

To toggle several elements as a unit without adding a wrapper, put v-if on a <template> tag. It renders its children only, no extra DOM node:

<template>
  <template v-if="showDetails">
    <h2>Details</h2>
    <p>{{ description }}</p>
  </template>
</template>

v-else / v-else-if also work on <template>.

v-if vs. v-show

v-show always renders the element and toggles its CSS display property. It has no <template> form and no v-else partner.

Use v-show when the thing flips often; use v-if when the condition rarely changes or the branch is expensive and usually absent.

v-for

v-for iterates a data source. Always pair it with a :key.

Arrays — the item, then an optional index:

<template>
  <li v-for="(user, index) in users" :key="user.id">
    {{ index }}. {{ user.name }}
  </li>
</template>

Objects — value, then optional key, then optional index, in Object.keys() order:

<template>
  <li v-for="(value, key) in settings" :key="key">{{ key }}: {{ value }}</li>
</template>

A range — an integer n iterates 1..n:

<template>
  <span v-for="n in 5" :key="n">{{ n }}</span>   <!-- 1 2 3 4 5 -->
</template>

On <template> — repeat a group with no wrapper element:

<template>
  <template v-for="item in items" :key="item.id">
    <dt>{{ item.term }}</dt>
    <dd>{{ item.definition }}</dd>
  </template>
</template>

You can iterate an array-returning computed property to render a filtered or sorted view without mutating the source.

The key requirement

Give every v-for a :key bound to a stable, unique identifier for each item — a database id, not the array index. The key lets Vue match nodes across re-renders so it moves and reuses DOM and component state correctly instead of patching in place. An index key breaks as soon as the list is reordered, filtered, or has items inserted, and it corrupts component state and transitions. Put :key on the <template> tag when v-for is on it.

Array updates: mutate or replace

Vue detects change on a reactive array in both directions:

  • Mutation methods — push, pop, shift, unshift, splice, sort, reverse — trigger updates in place.

  • Replacement — filter, map, slice, concat return a new array; assign it back (list.value = list.value.filter(...)) and Vue re-renders, reusing DOM where keys match.

Both are fine. Index and length writes (arr[99] = x, arr.length = 0) are also tracked in Vue 3 — see Reactivity Fundamentals for the reactivity caveats. To show a derived order without touching the original, return a copy from a computed: [...list.value].sort(...).

v-for with a component

v-for on a component still needs a :key, and data does not flow into the component automatically — pass it as props:

<template>
  <TodoItem
    v-for="todo in todos"
    :key="todo.id"
    :todo="todo"
    @remove="removeTodo(todo.id)"
  />
</template>

Do not put v-if and v-for on the same element

It is discouraged, and the precedence is a trap: v-if has higher priority than v-for, so the condition runs before the loop variable exists, and v-if="todo.done" throws or misbehaves.

Fix it by moving one out:

<template>
  <!-- filter in a computed, then loop -->
  <li v-for="todo in pendingTodos" :key="todo.id">{{ todo.name }}</li>

  <!-- or wrap the loop in a conditional <template> -->
  <template v-if="todos.length">
    <li v-for="todo in todos" :key="todo.id">{{ todo.name }}</li>
  </template>
</template>
const pendingTodos = computed(() => todos.value.filter((t) => !t.done))

Choosing between the conditional directives

The four ways of hiding something differ in what they cost and what they leave behind. This decision tree summarises the rules from the sections above:

flowchart TD Start["Element depends on a condition"] --> Q1{"Does it need to exist in the DOM while hidden?"} Q1 -->|"no, and it is rarely shown"| IF["v-if: not created while false"] Q1 -->|"yes, toggled often or must keep state"| Q2{"Is the subtree expensive and mostly hidden?"} Q2 -->|"yes"| IF Q2 -->|"no"| SHOW["v-show: stays mounted, CSS display toggles"] IF --> Q3{"Must hidden state survive being hidden?"} Q3 -->|"yes"| KA["Wrap in KeepAlive"] Q3 -->|"no"| Done["Plain v-if"]

v-show keeps a component’s state because the component never unmounts; v-if plus <KeepAlive> gets the same effect while still skipping the render cost of the hidden branch.

Worked example: a filterable todo board

A list view usually has three visual states — no data at all, data that the current filter hides, and rows to show — and v-if / v-else-if / v-else express them as one chain. The rows themselves come from a computed property, so the template stays declarative.

<script setup>
import { ref, computed } from 'vue'

const todos = ref([
  { id: 1, text: 'write docs', done: false },
  { id: 2, text: 'ship release', done: true },
  { id: 3, text: 'answer mail', done: false }
])
const filter = ref('open')

const visible = computed(() => {
  if (filter.value === 'all') return todos.value
  return todos.value.filter((t) => (filter.value === 'done') === t.done)
})
</script>

<template>
  <nav>
    <button v-for="f in ['all', 'open', 'done']" :key="f" :disabled="filter === f" @click="filter = f">
      {{ f }}
    </button>
  </nav>

  <p v-if="todos.length === 0">Nothing to do yet.</p>
  <p v-else-if="visible.length === 0">No {{ filter }} todos.</p>
  <ul v-else>
    <li v-for="todo in visible" :key="todo.id">{{ todo.text }}</li>
  </ul>
</template>

With the sample data the open filter renders two rows, and clicking done swaps them for one. Neither the filter buttons nor the empty-state messages need any imperative code. The buttons are themselves a v-for over a literal array, which is fine because the literal is created once per render and f is a stable key.

Seeing why keys matter

The key advice above is easy to dismiss until the list holds uncontrolled DOM state, such as text the user has typed into an input that is not bound with v-model. The component below can key its rows either by index or by id, and renders an <input> in every row:

<script setup>
import { ref } from 'vue'

defineProps({ byIndex: Boolean })

const items = ref([
  { id: 'a', label: 'Alpha' },
  { id: 'b', label: 'Beta' },
  { id: 'c', label: 'Gamma' }
])
</script>

<template>
  <!-- each row holds uncontrolled DOM state: whatever the user typed in the input -->
  <div v-for="(item, i) in items" :key="byIndex ? i : item.id">
    {{ item.label }} <input />
  </div>
  <button @click="items.shift()">Remove first</button>
</template>

Type typed-in-alpha-row into the Alpha row and then click Remove first. The result depends on the key:

Key Rows after removal Where the typed text ends up

item.id

Beta, Gamma

Gone, with the Alpha row it belonged to.

index

Beta, Gamma

Still in the first row — now labelled Beta.

With index keys Vue sees "the first <div> still exists, only its label changed" and reuses the element, typed text included; with id keys it sees that the element keyed a disappeared and removes exactly that one. The same mismatch affects component state, focus and CSS transitions, which is why a stable id is the rule. Running the component in a test (typing into the first input, removing the first item and reading each row’s input value) shows Beta carrying the leftover text under the index key and an empty Beta row under the id key.

Iterating iterables, and what v-for does not do

v-for works on anything iterable, not only arrays: a Map, a Set or a generator can be iterated directly (v-for="[key, value] in map"). It does not filter or sort; those belong in a computed property. It also creates its loop variables as plain template locals, so reassigning one inside an event handler (@click="todo = null") only changes the local, not the array.

For long lists the cost is in the number of rendered nodes, not in v-for. The techniques for lists with thousands of rows — virtual scrolling, shallowRef for large immutable data, v-memo — are in Performance and Deployment.
