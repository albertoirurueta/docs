Variables

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A Sass variable stores a value under a name so it can be written once and reused everywhere. Variables are resolved entirely at compile time: by the time the browser sees the stylesheet, every reference has been replaced by the literal value it held.

Declaring and using variables

A declaration is a name prefixed with $, a colon, and a value:

$primary: #3f51b5;
$font-stack: "Inter", "Helvetica Neue", sans-serif;
$gutter: 16px;
$max-content-width: 72ch;

body {
  font-family: $font-stack;
  color: $primary;
  max-width: $max-content-width;
  padding: $gutter;
}

Compiles to:

body {
  font-family: "Inter", "Helvetica Neue", sans-serif;
  color: #3f51b5;
  max-width: 72ch;
  padding: 16px;
}

Any Sass value may be stored: numbers (with or without units), strings, colors, booleans, null, lists, and maps (see Lists & Maps). Hyphens and underscores are interchangeable in variable names, so $line-height and $line_height refer to the same variable.

Variables can be used anywhere a value is expected, including inside other variable declarations and in interpolation for places that aren’t value positions:

$base: 8px;
$gutter: $base * 2;      // arithmetic -- see the Operators page
$breakpoint-md: 768px;

@media (min-width: $breakpoint-md) {
  .grid { gap: $gutter; }
}

$side: left;
.callout {
  border-#{$side}: 3px solid $primary;   // interpolation: builds the property name
}

Interpolation (#{...}) is required whenever the variable’s value must become part of a selector, a property name, or a string rather than a whole value on its own.

Data types

A variable can hold any of Sass’s value types. The meta.type-of() function reports which one a value is, which is handy when debugging a stylesheet that produces the wrong output:

@use "sass:meta";

$samples: (
  number: 16px,
  string: "Inter",
  bare: sans-serif,
  color: #3f51b5,
  bool: true,
  nothing: null,
  list: (1px 2px 3px),
  map: (a: 1),
);

@each $label, $v in $samples {
  .type-#{$label}::after { content: "#{meta.type-of($v)}"; }
}

Compiling it gives one rule per sample, shown here condensed:

.type-number::after  { content: "number"; }
.type-string::after  { content: "string"; }
.type-bare::after    { content: "string"; }
.type-color::after   { content: "color"; }
.type-bool::after    { content: "bool"; }
.type-nothing::after { content: "null"; }
.type-list::after    { content: "list"; }
.type-map::after     { content: "map"; }

Two details matter in practice. A quoted and an unquoted string ("Inter" and sans-serif) are both of type string; the quotes only affect how the value is written out. And null is a real value: a property whose value is null is omitted from the output entirely, which is what makes optional arguments in mixins possible.

Scope

A variable declared at the top level of a stylesheet is global — visible to the rest of that file and, via @use, to files that load it. A variable declared inside a block (a style rule, mixin, function, or control directive) is local: it exists only until that block ends.

$colour: red;         // global

.alpha {
  $colour: blue;      // local -- shadows the global inside .alpha only
  color: $colour;     // blue
}

.beta {
  color: $colour;     // red -- the global was never modified
}

Assigning to an existing name inside a block creates a new local variable that shadows the global; it does not reassign it. To deliberately reach out and change the global from inside a block, add the !global flag:

$theme: light;

@mixin activate-dark-theme {
  $theme: dark !global;   // reassigns the global variable
}

.page {
  @include activate-dark-theme;
}

.footer::after {
  content: "#{$theme}";   // "dark"
}

!global should only be used on a variable that already exists at the global level. Using it to create a new global still works today, but the compiler reports a new-global deprecation warning and Dart Sass 2.0.0 will make it an error — declare the variable at the top level first ($new: null;). In practice !global is best avoided — action-at-a-distance mutation makes stylesheets hard to reason about, and configuring a module with @use ... with (see Partials & Modules) or passing arguments to a mixin is almost always the clearer alternative.

Control-flow blocks are a deliberate exception to the shadowing rule: @if, @each, @for, and @while bodies assign to a variable declared at the same level as the control-flow rule, which is what makes accumulator patterns work.

$total: 0;
@each $w in 10px, 20px, 30px {
  $total: $total + $w;   // updates the outer $total, no !global needed
}
// $total is now 60px

"Same level" is the part to remember. A loop inside a style rule does not reach a variable declared at the top of the stylesheet; it creates a fresh local one, and the global keeps its old value. Declare the accumulator in the same block as the loop:

$i: 0;

.broken { @for $n from 1 through 3 { $i: $i + $n; } width: $i * 1px; }   // width: 0px
.works  { $i: 0; @for $n from 1 through 3 { $i: $i + $n; } width: $i * 1px; }   // width: 6px

Both rules were checked with the compiler: .broken emits width: 0px and .works emits width: 6px.

The lookup that decides which variable a name refers to walks outward from the current block:

flowchart TB A["Reference to $x
inside a nested block"] --> B{"$x declared in
this block?"} B -- yes --> R1["Use the local value"] B -- no --> C{"Declared in an
enclosing block?"} C -- yes --> R2["Use that value"] C -- no --> D{"Declared at the
stylesheet top level
or in a @use'd module?"} D -- yes --> R3["Use the global value"] D -- no --> R4["Error: undefined variable"]

Whether a name exists in a given scope can be asked at compile time with meta.variable-exists() (current scope and enclosing ones) and meta.global-variable-exists() (top level only):

@use "sass:meta";

$g: 1;

@mixin probe {
  $local: 2;
  a: meta.variable-exists(local);          // true
  b: meta.global-variable-exists(g);       // true
  c: meta.global-variable-exists(local);   // false
}

.x { @include probe; d: meta.variable-exists(local); }   // d: false

Compiling gives a: true; b: true; c: false inside .x, and d: false — the mixin’s $local is gone once the mixin has finished.

Default values with !default

The !default flag assigns a value only if the variable is currently undefined or null. This is the mechanism that makes a Sass library configurable: the library declares its knobs with !default, and a consumer overrides whichever ones it cares about.

// _theme.scss  (the library)
$primary:      #3f51b5 !default;
$radius:       4px      !default;
$font-stack:   sans-serif !default;

.button {
  background: $primary;
  border-radius: $radius;
  font-family: $font-stack;
}

A consumer configures it at load time:

// main.scss
@use "theme" with (
  $primary: #e91e63,
  $radius: 12px
);
// $font-stack keeps its !default value of sans-serif

!default only looks at whether the variable is undefined or null. It does not treat false or 0 as "unset", so a consumer that deliberately sets $flag: false or $gap: 0 keeps that value:

$a: null;   $a: 1    !default;   // a is 1  (null counts as unset)
$b: false;  $b: true !default;   // b stays false
$c: 0;      $c: 5    !default;   // c stays 0

Without !default, the library’s assignment would unconditionally clobber whatever the consumer supplied. The rule of thumb is simple: every variable in a file intended to be loaded by others should carry !default.

Sass variables vs. CSS custom properties

The two look similar and solve overlapping problems, but they run at completely different times, and the distinction matters:

Sass variable ($name) CSS custom property (--name)

Resolved

At compile time

At runtime, by the browser

Present in output CSS

No — substituted away

Yes — shipped and live in the cascade

Changeable at runtime

No

Yes (via JavaScript, media queries, a class on an ancestor)

Cascades / inherits

No — lexical scope only

Yes — follows the DOM

Usable in Sass arithmetic

Yes

Not directly (the value is opaque to the compiler)

Use a Sass variable for values fixed at build time — a spacing scale, a breakpoint used in a @media query, anything you want to do arithmetic on. Use a CSS custom property for values that must change in the browser, such as a runtime-switchable theme. They combine well: a Sass variable can define a custom property.

$primary: #3f51b5;

:root {
  --primary: #{$primary};       // interpolation is required here
}

[data-theme="dark"] {
  --primary: #7986cb;           // switched at runtime, no recompile
}

.button { background: var(--primary); }

Note the interpolation: writing --primary: $primary; would emit the literal text $primary, because custom property values are parsed as opaque tokens rather than Sass expressions.

Interpolation in depth

#{...} evaluates an expression and splices the result into the surrounding text as an unquoted string. It is the only way to put a variable somewhere that is not a value: a selector, a property name, a media query, or the inside of a quoted string.

$name: "primary";
$prop: margin;
$side: left;
$w: 10px;

.btn-#{$name} {
  #{$prop}-#{$side}: $w;
  background-image: url("/img/#{$name}.png");
}

@media (min-width: #{$w * 10}) { .x { y: z; } }

.s {
  content: "#{$name}";           // a quoted string stays quoted
  plain: #{$name};               // spliced unquoted: primary
  font: #{12px}/#{1.5} serif;    // keeps the slash literal
}
.btn-primary {
  margin-left: 10px;
  background-image: url("/img/primary.png");
}

@media (min-width: 100px) {
  .x {
    y: z;
  }
}
.s {
  content: "primary";
  plain: primary;
  font: 12px/1.5 serif;
}

Because the result is an unquoted string, an interpolated number can no longer take part in arithmetic. Interpolate at the last moment, and keep the real numbers in variables.

Variables across modules

A variable that a module exposes is read as module.$name. If the module declared it with !default it can also be assigned from outside, either at load time with with, or afterwards with a plain assignment on the namespaced name:

// _lib.scss
$primary: red;

// main.scss
@use "lib";

.a { color: lib.$primary; }   // red
lib.$primary: green;
.b { color: lib.$primary; }   // green -- the module's own variable was updated

Names beginning with - or _ are private and cannot be read from another file. Prefer with for configuration; reassigning a module’s variable from outside is order-dependent in the same way !global is.

Worked example: a design-token module

The pieces above combine into the usual way to publish a configurable set of design tokens: variables with !default as the knobs, a map for the palette, and a loop that turns the Sass values into CSS custom properties so the browser can still switch them at runtime.

// _tokens.scss
@use "sass:map";

$spacing-unit: 4px !default;
$colors: (
  primary: #3f51b5,
  danger: #e53935,
) !default;
$prefix: null !default;

:root {
  @each $name, $value in $colors {
    --#{$prefix}color-#{$name}: #{$value};
  }
  @for $i from 1 through 4 {
    --#{$prefix}space-#{$i}: #{$spacing-unit * $i};
  }
}

.card {
  padding: var(--#{$prefix}space-2);
  border-left: 4px solid var(--#{$prefix}color-primary);

  &:hover { border-left-color: map.get($colors, danger); }
}

Loaded with no configuration, @use "tokens"; produces:

:root {
  --color-primary: #3f51b5;
  --color-danger: #e53935;
  --space-1: 4px;
  --space-2: 8px;
  --space-3: 12px;
  --space-4: 16px;
}

.card {
  padding: var(--space-2);
  border-left: 4px solid var(--color-primary);
}
.card:hover {
  border-left-color: #e53935;
}

A consumer overrides the knobs, including the whole palette map, and every output value follows:

@use "tokens" with (
  $spacing-unit: 8px,
  $prefix: "acme-",
  $colors: (primary: #009688, danger: #d81b60)
);
:root {
  --acme-color-primary: #009688;
  --acme-color-danger: #d81b60;
  --acme-space-1: 8px;
  --acme-space-2: 16px;
  --acme-space-3: 24px;
  --acme-space-4: 32px;
}

.card {
  padding: var(--acme-space-2);
  border-left: 4px solid var(--acme-color-primary);
}
.card:hover {
  border-left-color: #d81b60;
}

Notice that $prefix defaults to null: interpolating null produces an empty string, so the unconfigured names come out as --color-primary with no stray text. The hover rule reads the palette with map.get() because the value is needed at compile time, while the rest of the stylesheet refers to the runtime var(--...) properties.

For the CSS side of this, see CSS custom properties and media queries.
