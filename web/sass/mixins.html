Mixins

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A mixin is a named, reusable group of CSS declarations (and optionally whole rules) that can be dropped into any selector. Mixins are the main tool for eliminating repetition in a stylesheet.

Defining and including

@mixin defines; @include uses.

@mixin visually-hidden {
  position: absolute;
  width: 1px;
  height: 1px;
  margin: -1px;
  padding: 0;
  overflow: hidden;
  clip: rect(0 0 0 0);
  white-space: nowrap;
  border: 0;
}

.skip-link:not(:focus) {
  @include visually-hidden;
}
.skip-link:not(:focus) {
  position: absolute;
  width: 1px;
  height: 1px;
  margin: -1px;
  padding: 0;
  overflow: hidden;
  clip: rect(0 0 0 0);
  white-space: nowrap;
  border: 0;
}

Mixin names, like variable names, treat hyphens and underscores as equivalent. A mixin taking no arguments may be included with or without empty parentheses (@include visually-hidden; or @include visually-hidden();).

A mixin may contain complete rules, not just declarations — including nested selectors and media queries:

@mixin card-surface {
  background: white;
  border-radius: 8px;
  box-shadow: 0 1px 3px rgb(0 0 0 / 0.2);

  &:hover { box-shadow: 0 4px 12px rgb(0 0 0 / 0.25); }

  @media (prefers-color-scheme: dark) {
    background: #1e1e1e;
  }
}

Arguments

Arguments make a mixin parameterised. They are declared as variables in parentheses and are in scope for the mixin’s body:

@mixin square($size, $colour) {
  width: $size;
  height: $size;
  background: $colour;
}

.avatar { @include square(48px, #3f51b5); }
.thumb  { @include square(96px, #e91e63); }

Named arguments

Arguments can be passed by name instead of position. This makes a long call self-documenting and lets you skip over defaults you don’t want to change:

@mixin button($bg, $fg: white, $radius: 4px, $padding: 8px 16px) {
  background: $bg;
  color: $fg;
  border-radius: $radius;
  padding: $padding;
  border: 0;
}

.btn-primary { @include button(#3f51b5); }
.btn-pill    { @include button(#e91e63, $radius: 999px); }
.btn-ghost   { @include button($bg: transparent, $fg: #3f51b5); }

Named arguments must come after any positional ones. Because they are matched by name, renaming a mixin’s parameter is a breaking change for its callers.

Default values

A default is an expression, evaluated when the mixin is called, and it may refer to earlier parameters of the same mixin:

@mixin inset($top, $right: $top, $bottom: $top, $left: $right) {
  top: $top;
  right: $right;
  bottom: $bottom;
  left: $left;
}

.overlay { @include inset(0); }          // all four sides 0
.panel   { @include inset(8px, 16px); }  // 8/16/8/16

Missing and unknown arguments

An argument without a default is required. Leaving it out is a compile-time error that names both the declaration and the call that failed:

@mixin square($size, $colour) { width: $size; background: $colour; }
.a { @include square(10px); }
Error: Missing argument $colour.
  ╷
1 │ @mixin square($size, $colour) { width: $size; background: $colour; }
  │        ━━━━━━━━━━━━━━━━━━━━━━ declaration
2 │ .a { @include square(10px); }
  │      ^^^^^^^^^^^^^^^^^^^^^ invocation
  ╵

Passing a name the mixin does not declare (@include square(10px, red, $color: red)) is an error too — No parameter named $color — so a typo in a named argument is caught instead of being silently ignored.

Arbitrary arguments

A trailing parameter written $name... collects every remaining argument into a list — Sass’s variadic form. This is how a mixin wraps a CSS property that itself takes a variable number of comma-separated values:

@mixin shadows($shadows...) {
  box-shadow: $shadows;
}

.card {
  @include shadows(0 1px 2px rgb(0 0 0 / 0.1), 0 4px 12px rgb(0 0 0 / 0.15));
}

If named arguments are passed to a variadic mixin, they are collected into a map accessible via meta.keywords():

@use "sass:meta";

@mixin custom-properties($args...) {
  @each $name, $value in meta.keywords($args) {
    --#{$name}: #{$value};
  }
}

:root {
  @include custom-properties($primary: #3f51b5, $radius: 4px);
}
:root {
  --primary: #3f51b5;
  --radius: 4px;
}

The same ... syntax works at the call site, spreading a list or map into individual arguments:

$brand-shadow: (0 1px 2px rgb(0 0 0 / 0.1), 0 4px 12px rgb(0 0 0 / 0.15));
.card { @include shadows($brand-shadow...); }

$btn-config: (bg: #3f51b5, radius: 999px);
.btn { @include button($btn-config...); }   // map keys become named arguments

Content blocks with @content

@content marks the place where a block passed by the caller is injected. This turns a mixin into a wrapper — the caller supplies the styles, the mixin supplies the context they go in.

The canonical use is a media-query helper:

@use "sass:map";

$breakpoints: (
  sm: 576px,
  md: 768px,
  lg: 992px,
  xl: 1200px
);

@mixin respond-to($name) {
  $width: map.get($breakpoints, $name);

  @if $width == null {
    @error "Unknown breakpoint `#{$name}`. Expected one of: #{map.keys($breakpoints)}.";
  }

  @media (min-width: $width) {
    @content;
  }
}

.sidebar {
  width: 100%;

  @include respond-to(md) {
    width: 280px;
    float: left;
  }

  @include respond-to(lg) {
    width: 320px;
  }
}
.sidebar { width: 100%; }
@media (min-width: 768px) {
  .sidebar { width: 280px; float: left; }
}
@media (min-width: 992px) {
  .sidebar { width: 320px; }
}

A mixin may use @content more than once, emitting the block in several places, and a mixin with no block passed simply produces nothing where @content appears.

Passing arguments to a content block

@content(...) passes values out to the block, which receives them with using ($var):

@use "sass:map";

$themes: (
  light: (bg: #ffffff, fg: #212121),
  dark:  (bg: #121212, fg: #eeeeee)
);

@mixin each-theme {
  @each $name, $colours in $themes {
    [data-theme="#{$name}"] & {
      @content($colours);
    }
  }
}

.panel {
  @include each-theme using ($c) {
    background: map.get($c, bg);
    color: map.get($c, fg);
  }
}
[data-theme=light] .panel { background: #ffffff; color: #212121; }
[data-theme=dark] .panel { background: #121212; color: #eeeeee; }

Note that a content block is evaluated in the lexical scope where it was written, not inside the mixin. It can therefore see the caller’s variables, but not the mixin’s local ones — which is exactly why using exists.

How a content block is evaluated

The block is written by the caller but runs where the mixin says. Sass evaluates it in the scope where it was written, then splices the result into the mixin’s output at the @content position:

flowchart LR A["Caller writes
@include respond-to(md) { width: 280px }"] --> B["Mixin body runs
with its own arguments and locals"] B --> C["Reaches @content"] C --> D["Caller's block is evaluated
in the caller's scope"] D --> E["Result is emitted
inside the mixin's wrapper"]

This is easy to see with two variables of the same name, one in the caller and one in the mixin:

$tone: red;

@mixin wrap {
  $tone: blue;
  .w { @content; }
}

.x {
  $tone: green;
  @include wrap { color: $tone; }
}
.x .w {
  color: green;
}

The block saw the caller’s $tone (green), not the mixin’s blue and not the global red. A mixin may use @content several times, and a mixin called without a block simply emits nothing at that point:

@mixin twice { @content; @content; }

.y { @include twice { a: b; } }   // .y { a: b; a: b; }
.z { @include twice; }            // emits no rule at all

Higher-order mixins

Mixins are not values, but the sass:meta module can look one up by name and apply it later. That makes a mixin that accepts other mixins possible:

@use "sass:meta";

@mixin rounded($r: 4px) { border-radius: $r; }
@mixin bordered($w: 1px) { border: $w solid currentColor; }

@mixin apply-all($mixins...) {
  @each $m in $mixins {
    @include meta.apply($m);
  }
}

.chip {
  @include apply-all(meta.get-mixin("rounded"), meta.get-mixin("bordered"));
  exists: meta.mixin-exists("rounded");   // true
  missing: meta.mixin-exists("nope");     // false
}
.chip {
  border-radius: 4px;
  border: 1px solid currentColor;
  exists: true;
  missing: false;
}

meta.get-mixin() takes the mixin’s name as a string, meta.apply() includes it (extra arguments and a content block may follow), and meta.mixin-exists() guards against a missing name. Reach for this only when mixin choice is genuinely data-driven; a plain @include is clearer in almost every other case.

Worked example: a button system

The pieces combine into a typical component library. A map describes the variants; one mixin generates a variant; a second mixin encapsulates the interactive states and hands each state to the caller through @content(...) and using:

@use "sass:map";

$variants: (
  primary: (base: #3f51b5, hover: #32408f),
  danger:  (base: #e53935, hover: #c62828),
);

@mixin interactive-states {
  &:hover:not(:disabled) { @content(hover); }
  &:focus-visible        { @content(focus); }
  &:disabled             { opacity: 0.5; cursor: not-allowed; }
}

@mixin button-variant($name, $colours) {
  .btn--#{$name} {
    background: map.get($colours, base);
    color: white;

    @include interactive-states using ($state) {
      @if $state == hover {
        background: map.get($colours, hover);
      } @else {
        outline: 2px solid map.get($colours, base);
        outline-offset: 2px;
      }
    }
  }
}

@each $name, $colours in $variants {
  @include button-variant($name, $colours);
}
.btn--primary {
  background: #3f51b5;
  color: white;
}
.btn--primary:hover:not(:disabled) {
  background: #32408f;
}
.btn--primary:focus-visible {
  outline: 2px solid #3f51b5;
  outline-offset: 2px;
}
.btn--primary:disabled {
  opacity: 0.5;
  cursor: not-allowed;
}

.btn--danger {
  background: #e53935;
  color: white;
}
.btn--danger:hover:not(:disabled) {
  background: #c62828;
}
.btn--danger:focus-visible {
  outline: 2px solid #e53935;
  outline-offset: 2px;
}
.btn--danger:disabled {
  opacity: 0.5;
  cursor: not-allowed;
}

Adding a third variant is one more entry in $variants; changing what every button does on focus is one edit inside the @include interactive-states block. The :disabled rule lives in the mixin because it is the same for every variant, while the hover and focus styling is supplied by the caller because it depends on the colour.

Mixins vs. functions vs. @extend

  • A mixin emits declarations. Reach for it when you want to inject styles.

  • A function returns a single value and emits nothing — see Functions.

  • @extend merges selectors instead of duplicating declarations — see Selector Inheritance for the trade-off between the two.

The practical difference between a mixin and @extend: a mixin copies its declarations into every caller, so ten callers produce ten copies (which gzip compresses well, and which keeps the cascade predictable), whereas @extend produces one rule with ten selectors on it. The same clearfix written both ways, compiled for two callers each:

@mixin clearfix {
  &::after { content: ""; display: table; clear: both; }
}
.a { @include clearfix; }
.b { @include clearfix; }

%clearfix {
  &::after { content: ""; display: table; clear: both; }
}
.c { @extend %clearfix; }
.d { @extend %clearfix; }
.a::after {
  content: "";
  display: table;
  clear: both;
}

.b::after {
  content: "";
  display: table;
  clear: both;
}

.d::after, .c::after {
  content: "";
  display: table;
  clear: both;
}

Mixins also differ from plain CSS classes. A class such as .clearfix is applied in the HTML, so the markup carries the styling decision and the rule exists once; a mixin is applied in the stylesheet, so the HTML stays semantic and the declarations are repeated in the output. Use a mixin when the styling belongs to the component, and a class when it is a utility that markup authors should be able to opt in to.
