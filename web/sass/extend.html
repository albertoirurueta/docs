Selector Inheritance (@extend)

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

@extend tells Sass that one selector should inherit another’s styles. Rather than copying the declarations, Sass rewrites the selector list of the inherited rule so it also matches the extending selector.

Basic usage

.message {
  padding: 12px 16px;
  border: 1px solid;
  border-radius: 4px;
}

.message--success {
  @extend .message;
  border-color: #43a047;
  color: #1b5e20;
}

.message--error {
  @extend .message;
  border-color: #e53935;
  color: #b71c1c;
}
.message, .message--success, .message--error {
  padding: 12px 16px;
  border: 1px solid;
  border-radius: 4px;
}

.message--success { border-color: #43a047; color: #1b5e20; }
.message--error   { border-color: #e53935; color: #b71c1c; }

The shared declarations appear once, with all three selectors attached. This is the defining property of @extend and the reason people reach for it: minimal output, no duplication.

Note what this means in the HTML: class="message--success" alone is now enough, because the compiled CSS matches it directly. There is no need to also write class="message message--success".

@extend also propagates through every rule the target appears in, including nested and compound selectors:

.message { padding: 12px; }
.panel .message { margin: 8px; }
.message:hover { opacity: 0.9; }

.alert { @extend .message; }
.message, .alert { padding: 12px; }
.panel .message, .panel .alert { margin: 8px; }
.message:hover, .alert:hover { opacity: 0.9; }

That reach is the power and the main hazard of @extend — one @extend can rewrite many rules across the whole stylesheet, including ones written in a completely different file.

How @extend works behind the scenes

Sass does not copy declarations when it sees @extend. It records the request, finishes reading the stylesheet, and then rewrites selectors. For every rule whose selector contains the target, it adds the extender beside that selector, keeping whatever context surrounded it:

flowchart TD A["Evaluate the stylesheet
collect every @extend as a pair:
extender, target"] --> B["Walk all emitted rules"] B --> C{"Does this rule's selector
contain a target?"} C -- no --> D["Leave the rule unchanged"] C -- yes --> E["Add the extender to the selector list
copying the surrounding context"] E --> F["Rule stays where the target was written"] D --> G["Emit CSS"] F --> G

A placeholder with several rules shows what "copying the surrounding context" means. Three components extend %btn, which appears bare, under two ancestors and with a pseudo-class:

%btn { padding: 8px; }
.nav %btn { margin: 0; }
.form %btn { margin: 4px; }
%btn:hover { opacity: 0.9; }

.a { @extend %btn; }
.b { @extend %btn; }
.c { @extend %btn; }
.c, .b, .a {
  padding: 8px;
}

.nav .c, .nav .b, .nav .a {
  margin: 0;
}

.form .c, .form .b, .form .a {
  margin: 4px;
}

.c:hover, .b:hover, .a:hover {
  opacity: 0.9;
}

Each extender was added to all four rules, so three components times four rules gave twelve selectors, and the declarations are still written only once per rule. The extenders appear in reverse order of declaration; Sass makes no promise about that order, so never write CSS that depends on it.

Extension is scoped to the modules a file loads

With the module system, an @extend only affects stylesheets that the extending file loads, directly or transitively. A file cannot reach into a module it knows nothing about, which removes much of the "action at a distance" that made @extend risky in the @import era. Given a _lib.scss whose .base rule sets padding, an unrelated _unrelated.scss whose .base rule sets a margin, and a button module that loads only lib:

// _button.scss
@use "lib";
.button { @extend .base; }
// main.scss
@use "unrelated";
@use "button";

only the lib rule is extended:

.base {
  margin: 0;
}

.base, .button {
  padding: 4px;
}

If the extending file does not load the module that defines the target at all, the target is "not found" and compilation fails with The target selector was not found, plus a hint to add !optional.

Placeholder selectors

A placeholder selector starts with %. It behaves like a class for extension purposes but is never emitted to the output on its own:

%message-base {
  padding: 12px 16px;
  border: 1px solid;
  border-radius: 4px;
}

.message--success {
  @extend %message-base;
  border-color: #43a047;
}

.message--error {
  @extend %message-base;
  border-color: #e53935;
}
.message--success, .message--error {
  padding: 12px 16px;
  border: 1px solid;
  border-radius: 4px;
}

.message--success { border-color: #43a047; }
.message--error   { border-color: #e53935; }

No %message-base rule is emitted, and no .message class is left in the CSS that nothing uses.

Placeholders are the recommended @extend target. Extending a real class emits that class whether or not any markup uses it, and couples your rule to a selector that someone may later restyle or delete. A placeholder exists purely as an extension point, which makes the intent explicit. A placeholder that is never extended produces no output at all, so unused ones cost nothing.

Which to use. Default to a mixin. The output-size argument that historically favoured @extend is largely neutralised by gzip/brotli, which compress repeated declaration blocks extremely well, while mixins remain local, predictable, and parameterisable. Reach for @extend (always against a %placeholder) when several selectors genuinely represent the same thing semantically and you want them to share one rule — and when the set of extenders is small and lives in the same file or module.

Measuring the difference

The size argument is easy to check. Twenty icon classes share six declarations and each adds a background image. Written once with @extend %icon and once with @include icon, the compiled output (compressed) measures:

Version Raw bytes Gzip level 9

@extend %icon

1394

381

@include icon

3359

321

The extended version is less than half the size before compression, but after gzip the mixin version is the smaller of the two, because repeated blocks are exactly what the compressor removes best. The extend version also produces one rule with twenty comma-separated selectors, which is harder to read in devtools. The numbers shift with the input, but the conclusion holds: output size alone is rarely a reason to choose @extend.

The source for the comparison, for the @extend form:

$icons: (add, remove, edit, delete, search, home, user, star, mail, phone, lock, cog, bell,
         calendar, camera, cloud, download, upload, flag, heart);

%icon {
  display: inline-block;
  width: 1em;
  height: 1em;
  background-repeat: no-repeat;
  background-size: contain;
  vertical-align: middle;
}

@each $name in $icons {
  .icon-#{$name} {
    @extend %icon;
    background-image: url("icons/#{$name}.svg");
  }
}

For the mixin form, replace %icon with @mixin icon and @extend %icon; with @include icon;.

Caveats

Media queries

A rule can only extend a selector defined in the same media context. Sass cannot merge selectors across @media boundaries, because the resulting rule would have to apply in both contexts at once.

%wide-only { float: left; }

@media (min-width: 768px) {
  .sidebar {
    @extend %wide-only;   // ERROR: You may not @extend selectors across media queries.
  }
}

The fix is a mixin, which has no such restriction:

@mixin wide-only { float: left; }

@media (min-width: 768px) {
  .sidebar { @include wide-only; }
}

This limitation alone rules @extend out of most responsive component code.

Selector bloat

Because @extend rewrites every rule the target appears in, extending a selector that is itself widely used (or that is itself the product of other extends) can multiply selectors combinatorially. A rule ending up with hundreds of comma-separated selectors is a known failure mode, and it can make the compiled CSS larger than the mixin version it was meant to shrink.

Extending inside a loop is the fastest way to get there:

// Dangerous: every generated class joins the same rule's selector list
@each $name in a, b, c, d, e {
  .icon-#{$name} { @extend %icon-base; }
}

Source order and specificity surprises

The merged rule appears where the target was defined, not where the @extend was written. If you extend something defined early in the stylesheet, the inherited declarations land early too — and can be overridden by rules you expected them to beat. See Selectors & specificity for how the cascade resolves this.

A concrete case: a .muted helper is written between a placeholder and the component that extends it.

%message { color: #212121; }
.muted { color: #9e9e9e; }
.message--note { @extend %message; }
.message--note {
  color: #212121;
}

.muted {
  color: #9e9e9e;
}

On class="message--note muted" the later .muted rule wins, and the element is grey. The same stylesheet written with @mixin message and @include message places the declaration where .message--note is written, after .muted, so the note wins and stays dark. Same selectors, same specificity, opposite result, purely because of where the merged rule landed.

Extending compound selectors

Only a simple selector can be extended. @extend .a.b or @extend .parent .child is an error:

.a.b { color: red; }
.c { @extend .a.b; }   // ERROR: compound selectors may no longer be extended

Extend the individual pieces instead, or use a mixin. Selecting an element that has several classes is covered in Elements with multiple classes.

The allowed alternative is to extend each simple selector separately:

.a { color: red; }
.b { font-weight: bold; }
.c { @extend .a; @extend .b; }

This compiles to .a, .c { color: red; } and .b, .c { font-weight: bold; }: .c is styled as if the element carried both classes. Because @extend treats .c as matching .a and .b, it also extends any rule written for the compound .a.b in the same compilation (its selector becomes .a.b, .c). The difference from the forbidden @extend .a.b is the reverse direction: .c also picks up every rule for .a alone and for .b alone, not only the rules that require both classes.

!optional

Extending a selector that does not exist is an error. !optional downgrades that to silence, which is useful in a library where a hook may or may not be defined:

.button { @extend %theme-hook !optional; }

Use it sparingly — it also silences the genuine typo case.

@extend and &

@extend composes with nesting, but read the result carefully: inside a nested block, the extending selector is the full compiled selector, so the merge happens against that, not against the innermost fragment.

%focus-ring { outline: 2px solid #3f51b5; }

.form {
  input {
    &:focus-visible { @extend %focus-ring; }   // extends as ".form input:focus-visible"
  }
}

Related: selector.extend()

The same rewriting is available as a function in the sass:selector module, which is how a mixin can compute what an @extend would produce without performing it (see Built-in Modules). selector.extend(".a .b", ".b", ".c") returns .a .b, .a .c, while selector.replace() with the same arguments returns just .a .c, replacing rather than adding.
