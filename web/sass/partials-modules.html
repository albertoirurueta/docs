Partials and Modules (@use / @forward)

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Splitting a stylesheet across many files is what makes a large Sass codebase manageable. Sass’s module system — @use and @forward — controls how those files load each other, what names they expose, and how they are configured. It replaces the older @import rule, which is deprecated.

Partials

A partial is a Sass file whose name begins with an underscore: _variables.scss, _buttons.scss. The underscore tells the compiler "this file is not a stylesheet in its own right — do not compile it to a standalone .css file". It exists only to be loaded by other files.

scss/
├── main.scss           ← compiled to main.css
├── _variables.scss     ← partial, not compiled on its own
├── _mixins.scss        ← partial
└── components/
    ├── _button.scss
    └── _card.scss

When loading a partial, the leading underscore and the file extension are both omitted:

@use "variables";              // loads _variables.scss
@use "components/button";      // loads components/_button.scss

Without the underscore, running sass scss/:css/ would emit a variables.css, mixins.css, and so on alongside the one file you actually wanted — which is the entire reason the convention exists.

@use

@use loads another stylesheet as a module, making its variables, mixins, and functions available.

// _colors.scss
$primary: #3f51b5;
$danger:  #e53935;

@mixin text-on-primary { color: white; }
// main.scss
@use "colors";

.button {
  background: colors.$primary;
  @include colors.text-on-primary;
}

Three properties of @use matter, and all three are improvements over @import:

  1. Members are namespaced. By default the namespace is the file’s basename without underscore or extension (colors), and members are reached as colors.$primary. Nothing leaks into the global namespace, so two modules can both define $primary without colliding.

  2. Each module is loaded exactly once, no matter how many files @use it. @import re-evaluated the file every time, duplicating its CSS output.

  3. @use must appear at the top of the file, before any rules other than @charset and other @use/ @forward lines. This makes the dependency graph statically analysable.

Choosing a namespace with as

@use "components/button" as btn;     // btn.$height
@use "very/long/path/typography" as t;

Loading without a namespace: as *

as * drops the namespace and dumps the module’s members into the current scope:

@use "colors" as *;

.button { background: $primary; }    // no prefix needed

Convenient, but it reintroduces exactly the collision risk namespaces were designed to prevent. Reserve it for a single project-wide token file, and prefer explicit namespaces everywhere else.

Private members

A member whose name starts with - or _ is private to its module: usable inside the file that defines it, invisible to anything that loads it with @use.

// _colors.scss
@use "sass:color";

$-internal-seed: #123456;      // private
$primary: color.adjust($-internal-seed, $lightness: 40%);   // fine here

Configuring a module with with

A module’s !default variables (see Variables) are its configuration surface. A loader overrides them at load time with with:

// _theme.scss
$primary: #3f51b5 !default;
$radius:  4px     !default;
$font:    sans-serif !default;

.button {
  background: $primary;
  border-radius: $radius;
  font-family: $font;
}
// main.scss
@use "theme" with (
  $primary: #e91e63,
  $radius: 12px
);

Constraints worth remembering:

  • Only variables declared with !default can be configured; anything else is an error.

  • A module can be configured only once, and only by the first file that loads it. If two files both write @use "theme" with (...), compilation fails.

  • Configuration is applied before the module’s own body runs, so the module’s rules see the new values.

@forward

@forward makes another module’s members visible to files that load this one, without using them here. It is how a library exposes a single entry point that aggregates many internal partials.

// _index.scss  -- the public face of the library
@forward "colors";
@forward "typography";
@forward "spacing";
// main.scss
@use "theme";                  // loads theme/_index.scss

.button {
  background: theme.$primary;      // defined in theme/_colors.scss
  font-family: theme.$font-stack;  // defined in theme/_typography.scss
}

A directory containing an _index.scss (or _index.sass) can be loaded by directory name alone — @use "theme" finds theme/_index.scss automatically.

@forward does not make the members usable in the forwarding file itself. To both re-export and use them, write both rules — Sass loads the module only once regardless:

@forward "colors";
@use "colors";

.debug { outline: 1px solid colors.$danger; }

show and hide

@forward "colors" show $primary, $danger, text-on-primary;   // only these
@forward "internals" hide $-scratch, reset-everything;        // all but these

show is the safer default for a public library API: it makes the exposed surface explicit, so adding a member internally does not silently widen the API.

Prefixing with as

@forward "..." as prefix-* prepends a prefix to every forwarded member’s name — useful for keeping an aggregated namespace readable while still exposing everything through one entry point:

// _index.scss
@forward "colors"     as color-*;
@forward "typography" as type-*;
@use "theme";

.button {
  background:  theme.$color-primary;   // was $primary in _colors.scss
  font-family: theme.$type-font-stack; // was $font-stack in _typography.scss
}

Two details trip people up. First, when as and show/hide appear together, show and hide name the members after the prefix has been added, so @forward "tokens" as ds-* hide ds-space hides the function, while hide space hides nothing (the compiler does not complain, and ds-space() stays visible). Second, the clauses must appear in the order as, then show/hide, then with.

A forwarded module’s configuration can also be set or re-exposed. @forward ... with (... !default) forwards the module while supplying a new default that the eventual consumer may still override:

// theme-entry.scss
@forward "abstracts/tokens" show $primary, $radius, space
  with ($primary: #009688 !default, $radius: 2px !default);
// consumer.scss
@use "theme-entry" with ($radius: 10px);

.x {
  c: theme-entry.$primary;     // #009688 -- the forwarded default
  r: theme-entry.$radius;      // 10px    -- the consumer's override
  s: theme-entry.space(2);     // 16px
}
.x {
  c: #009688;
  r: 10px;
  s: 16px;
}

A theme that sits between a library and an application is built exactly like this: it changes some defaults, leaves the others configurable, and hides everything it does not want to make public.

A worked module graph

Putting it together — an entry stylesheet that applies @use to two component partials, one of which applies @forward to a shared token partial:

flowchart TD MAIN["main.scss
(compiled → main.css)"] IDX["theme/_index.scss"] COL["theme/_colors.scss"] TYP["theme/_typography.scss"] BTN["components/_button.scss"] MAIN -- "@use 'theme'" --> IDX MAIN -- "@use 'components/button'" --> BTN IDX -- "@forward 'colors'" --> COL IDX -- "@forward 'typography'" --> TYP BTN -- "@use '../theme'" --> IDX classDef entry fill:#3f51b5,stroke:#1a237e,color:#fff classDef agg fill:#7986cb,stroke:#3f51b5,color:#fff class MAIN entry class IDX agg

theme/_index.scss is loaded by both main.scss and components/_button.scss, but it is evaluated exactly once, and theme/_colors.scss reaches main.scss only through the @forward chain.

Worked example: a layered project with configuration

A typical project keeps design tokens and helpers in an abstracts folder, global rules in base, and one partial per component. Only main.scss is compiled:

scss/
├── main.scss
├── abstracts/
│   ├── _index.scss        ← @forward "tokens"; @forward "mixins";
│   ├── _tokens.scss
│   └── _mixins.scss
├── base/
│   └── _reset.scss
└── components/
    ├── _card.scss
    └── _button.scss

The tokens expose configurable defaults, one private helper map and a public function:

// abstracts/_tokens.scss
@use "sass:map";

$primary: #3f51b5 !default;
$radius: 4px !default;
$spacing: 8px !default;
$-scale: (1: 1, 2: 2, 4: 4);   // private to this file

@function space($step) {
  @return $spacing * map.get($-scale, $step);
}
// abstracts/_mixins.scss
@use "tokens";

@mixin card-surface {
  padding: tokens.space(2);
  border-radius: tokens.$radius;
  background: white;
}
// abstracts/_index.scss
@forward "tokens";
@forward "mixins";

Each component loads the folder through its index file, under a short namespace:

// components/_card.scss
@use "../abstracts" as a;

.card {
  @include a.card-surface;
  border-left: 4px solid a.$primary;
  margin-bottom: a.space(4);
}
// components/_button.scss
@use "../abstracts" as a;

.button {
  background: a.$primary;
  border-radius: a.$radius;
  padding: a.space(1) a.space(2);
}

The entry point is where the project configures the tokens, once, before anything else loads them:

// main.scss
@use "abstracts" with ($primary: #e91e63, $radius: 8px);
@use "base/reset";
@use "components/card";
@use "components/button";

.hero { color: abstracts.$primary; margin: abstracts.space(4); }

Compiled with sass scss/main.scss:

*, *::before, *::after {
  box-sizing: border-box;
}

body {
  margin: 0;
}

.card {
  padding: 16px;
  border-radius: 8px;
  background: white;
  border-left: 4px solid #e91e63;
  margin-bottom: 32px;
}

.button {
  background: #e91e63;
  border-radius: 8px;
  padding: 8px 16px;
}

.hero {
  color: #e91e63;
  margin: 32px;
}

The configuration reached every file: _card.scss and _button.scss never mention #e91e63, yet they use it, because all of them share the single evaluation of abstracts that main.scss configured. The output order follows the order of the @use rules, and each module’s CSS appears once.

flowchart TD MAIN["main.scss"] -- "@use with config" --> ABS["abstracts/_index.scss"] ABS -- "@forward" --> TOK["_tokens.scss"] ABS -- "@forward" --> MIX["_mixins.scss"] MIX -- "@use" --> TOK MAIN -- "@use" --> RES["base/_reset.scss"] MAIN -- "@use" --> CARD["components/_card.scss"] MAIN -- "@use" --> BTN["components/_button.scss"] CARD -- "@use" --> ABS BTN -- "@use" --> ABS

Configure first, or not at all

Configuration is accepted only by the first @use of a module. If an earlier file already loaded it, even indirectly, a later with is rejected. Swapping two lines of the entry point is enough to trigger it:

@use "components/card";                    // loads abstracts, unconfigured
@use "abstracts" with ($primary: red);     // too late
Error: This module was already loaded, so it can't be configured using "with".
  ┌──> bad.scss
2 │ @use "abstracts" with ($primary: red);
  │ ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ new load
  ╵
  ┌──> components/_card.scss
1 │ @use "../abstracts" as a;
  │ ━━━━━━━━━━━━━━━━━━━━━━━━ original load
  ╵

The robust pattern is therefore the one above: the entry point configures first, and components only @use modules without with. When several entry points need different configurations, give each its own copy of the configuring @use line, or build a small theme module with @forward ... with as shown earlier.

The private member is enforced too. Reading abstracts.$-scale from main.scss fails with Private members can't be accessed from outside their modules.

Load paths and loading CSS at runtime

A bare @use "lib" is resolved relative to the file first, then against each load path given on the command line:

sass --load-path=vendor scss/main.scss

With vendor/lib/_index.scss present, @use "lib" finds it. The JavaScript API has the equivalent loadPaths option. Package managers add a third route: with the Node package importer enabled (--pkg-importer=node on the command line), a pkg: URL such as @use "pkg:bootstrap" is resolved through node_modules, so no load path is needed.

When the module to load is chosen by a variable, or must be emitted inside a selector, use meta.load-css(). It includes a module’s CSS where it is called, and it accepts a configuration map in $with:

@use "sass:meta";

.dark-mode {
  @include meta.load-css("components/button", $with: ());
}
.dark-mode .button {
  background: #3f51b5;
  border-radius: 4px;
  padding: 8px 16px;
}

Unlike @use, meta.load-css() exposes no members and may appear anywhere, including inside a rule; the loaded CSS is nested under the surrounding selector. It is the tool for scoping a third-party stylesheet under a class or a theme wrapper.

@import is deprecated

Sass’s original @import rule is deprecated and slated for removal from Dart Sass. Prefer @use/@forward in all new code.

@import (deprecated) @use / @forward

Everything is global — collisions are silent and order-dependent

Members are namespaced per module

The same file loaded twice is evaluated twice, duplicating CSS

Each module is evaluated exactly once

Can appear anywhere, including nested in a rule

Must appear at the top of the file

No notion of private members

-/_ prefix marks a member private

Configured only by assigning globals before importing

Configured explicitly with @use ... with (...)

 
// old
@import "variables";
@import "mixins";
.button { background: $primary; @include button-base; }

// new
@use "variables" as v;
@use "mixins" as m;
.button { background: v.$primary; @include m.button-base; }

Note that CSS also has its own @import, which is unrelated and not deprecated. Sass passes a plain CSS @import through untouched when the URL is absolute, ends in .css, or is written as url(...) — so @import url("https://fonts.googleapis.com/...") still works as expected.

The official sass-migrator tool automates the conversion:

npm install -g sass-migrator
sass-migrator module --migrate-deps scss/main.scss
