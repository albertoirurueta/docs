Selenium Grid

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Selenium Grid runs WebDriver sessions on browsers that live somewhere else: on another machine, in a container, or in a fleet of containers that scale with the load. The test code stays the same except for one line: instead of starting a local ChromeDriver, it creates a RemoteWebDriver that points at the Grid, and the Grid decides which Node has a free slot for the requested browser. This page is written for Selenium 4.51.0 (released 9 October 2026, the latest release on 25 October 2026) and the selenium/* Docker images at the same version, and it was checked on 25 October 2026. The examples were run against the Bookshelf application with Java 17 and JUnit 5.14.4, and with Python 3.13 and pytest 9.1, against real Grids: the Selenium Server jar on the host (Standalone) and Docker containers started with Docker Compose (Standalone, Hub and Nodes, fully distributed, Dynamic Grid, and a video recorder). The Helm chart with KEDA, an external Redis or PostgreSQL session map, tracing with Jaeger and the custom Node were not run, for the reasons given in their sections.

How to create a driver, the options of each browser and Selenium Manager are explained in Drivers, Browsers & Options; the first test is in Getting Started. The general question of covering several browsers is discussed in Cross-Browser Testing, and wiring a Grid into a pipeline in Running in CI/CD. Playwright can also borrow a browser from a Grid; that is covered in Playwright Advanced Topics.

When to use a Grid

A Grid pays off when the number of browser sessions you want at the same time is larger than one machine can serve, or when the machine that runs the tests is not the machine that can run the browser. The Selenium documentation lists the cases: run tests in parallel against different browser types, browser versions and operating systems, and shorten the time a suite needs. The arithmetic is simple:

Number of tests * average test time / number of Nodes = total execution time

   15 *  45 s /  1 = 11 min 15 s   (no Grid)
   15 *  45 s /  5 =  2 min 15 s   (Grid with 5 Nodes)
   15 *  45 s / 15 =        45 s   (Grid with 15 Nodes)
  100 * 120 s / 15 = 13 min 20 s   (over 3 hours without a Grid)

Source: Selenium — When to Use Grid

The formula assumes the tests are independent (see Test Design & Page Objects) and that the Grid has as many free slots as there are tests; the queue in front of the Distributor (explained below) absorbs the difference when it does not. A Grid is not always the answer:

  • One machine with enough CPU and memory can already run several local drivers in parallel. Start there: a Grid adds a network hop to every command, one more thing to operate and a security surface.

  • A Grid does not make a test faster, it makes more tests run at the same time. A slow test stays slow.

  • Browsers that exist only on specific hardware (Safari on macOS, the legacy Internet Explorer mode of Edge on Windows) need a Node on that hardware; a Linux container cannot provide them.

  • If you do not want to operate infrastructure, a cloud grid (BrowserStack, Sauce Labs, TestMu AI and similar) speaks the same WebDriver protocol, so the RemoteWebDriver code on this page works against them with a different URL and vendor capabilities. See Cross-Browser Testing for those services.

The three roles

Grid 4 is composed of six components (listed in the next section) that can be started together or separately. Selenium Server, a single jar (selenium-server-4.51.0.jar, attached to every GitHub release), exposes them as sub-commands (standalone, hub, node, distributor, router, sessions, sessionqueue, event-bus). You choose how many of them to run in each process:

Role What runs in the process Use it for

Standalone

All the components and a Node in a single process, on a single machine. Listens on http://localhost:4444.

Developing or debugging with RemoteWebDriver locally, a quick suite before pushing, a Grid in a CI job (GitHub Actions, Jenkins). It is also what the selenium/standalone-* Docker images run.

Hub and Node

The Hub runs the Router, Distributor, Session Map, New Session Queue and Event Bus. Each Node is a separate process, usually on a separate machine, that registers with the Hub.

The most common setup: machines with different operating systems and browser versions behind one URL, capacity that can be added or removed without stopping the Grid.

Distributed

Every component in its own process, ideally on its own machine.

Large Grids (the documentation puts "large" at 60 to 100 Nodes with a Hub, more than 100 with the distributed role), or when a component must be scaled or restarted on its own, for example with an external session map.

Source: Selenium — Getting started with Selenium Grid

Standalone

Standalone needs Java 11 or newer, a browser, and either its driver on the PATH or the --selenium-manager true flag so the Node asks Selenium Manager to download it:

Hub and Node

Start the Hub, then one or more Nodes. On the same machine the defaults are enough:

java -jar selenium-server-4.51.0.jar hub
java -jar selenium-server-4.51.0.jar node
java -jar selenium-server-4.51.0.jar node --port 5555    # a second Node would use another port, such as 6666

Source: Selenium — Getting started with Selenium Grid

On different machines a Node registers by publishing a message to the Hub’s Event Bus and then letting the Hub call it back over HTTP, so the Hub machine must expose the Event Bus ports (4442 and 4443 by default) and the Node must expose its own port. If the Hub uses default ports, the --hub flag is the short form; otherwise name the Event Bus ports explicitly:

java -jar selenium-server-4.51.0.jar node --hub http://<hub-ip>:4444

# a Hub with non-default ports ...
java -jar selenium-server-4.51.0.jar hub --publish-events tcp://<hub-ip>:8886 --subscribe-events tcp://<hub-ip>:8887 --port 8888
# ... and the Node that registers with it
java -jar selenium-server-4.51.0.jar node --publish-events tcp://<hub-ip>:8886 --subscribe-events tcp://<hub-ip>:8887

Source: Selenium — Getting started with Selenium Grid

Fully distributed

In the distributed role the start order follows the dependencies between the components: Event Bus and Session Map first, then the New Session Queue, the Distributor, the Router and finally the Nodes. The default ports are 4442, 4443 and 5557 for the Event Bus, 5559 for the queue, 5556 for the Session Map, 5553 for the Distributor, 4444 for the Router and 5555 for a Node.

java -jar selenium-server-4.51.0.jar event-bus --publish-events tcp://<event-bus-ip>:4442 --subscribe-events tcp://<event-bus-ip>:4443 --port 5557
java -jar selenium-server-4.51.0.jar sessionqueue --port 5559
java -jar selenium-server-4.51.0.jar sessions --publish-events tcp://<event-bus-ip>:4442 --subscribe-events tcp://<event-bus-ip>:4443 --port 5556
java -jar selenium-server-4.51.0.jar distributor --publish-events tcp://<event-bus-ip>:4442 --subscribe-events tcp://<event-bus-ip>:4443 \
  --sessions http://<sessions-ip>:5556 --sessionqueue http://<new-session-queue-ip>:5559 --port 5553 --bind-bus false
java -jar selenium-server-4.51.0.jar router --sessions http://<sessions-ip>:5556 --distributor http://<distributor-ip>:5553 \
  --sessionqueue http://<new-session-queue-ip>:5559 --port 4444
java -jar selenium-server-4.51.0.jar node --publish-events tcp://<event-bus-ip>:4442 --subscribe-events tcp://<event-bus-ip>:4443

Source: Selenium — Getting started with Selenium Grid

--bind-bus false on the Distributor means "connect to the Event Bus, do not start one": in a Hub the Event Bus is bound by the Hub itself. These commands were not run on the host as separate processes (they would need five local ports for each test run); the same topology, with the same components, was run with the official Docker images and is shown in the docker-selenium section.

Components and architecture

The figure shows who talks to whom when a test creates a session and when it sends later commands.

Component Responsibility

Router

The front door of the Grid, and the only component that may be reachable from outside (the documentation strongly advises against exposing even that to the wider internet). A new session request is forwarded to the New Session Queue; a request for an existing session is sent to the Node found in the Session Map. It forwards each request to the component best able to handle it, so the other components are not loaded for nothing.

New Session Queue

Holds new session requests in first-in, first-out order. It has a request timeout (--session-request-timeout, 300 seconds by default) and a check period (--session-request-timeout-period, 10 seconds). Requests that wait longer than the timeout are rejected and removed. The Router waits on the queue for the answer.

Distributor

Does two jobs. It registers Nodes and tracks their capabilities in the Grid Model, and it polls the New Session Queue, finds a matching free slot on a Node, creates the session there and stores the session id and Node in the Session Map. If every matching slot is busy it returns the request to the queue.

Session Map

A data store from session id to the Node that runs the session. The Router asks it for the owner of every command to an existing session. In-memory by default; Redis and JDBC (SQL) implementations exist (see the external datastore section).

Node

Owns a machine’s slots. A Node only executes the commands it receives; it does not decide anything else. By default it registers every driver it finds on the PATH, creating one slot per CPU for Chromium-based browsers and Firefox and a single slot for Safari. It can also start each session in a Docker container or relay commands to another WebDriver endpoint. A Node can be on a different operating system from the rest of the Grid.

Event Bus

The message channel between Nodes, Distributor, New Session Queue and Session Map. Most internal communication uses events instead of HTTP calls. In the distributed role it is the first component to start. The default implementation is ZeroMQ.

Source: Selenium — Selenium Grid Components

Two concepts from the architecture page appear in every configuration: a slot is the place where one session can run, and every slot has a stereotype, the minimal set of capabilities a new session request must match before the Distributor sends it to that slot (for example {"browserName": "firefox"}). The Grid Model is the Distributor’s own picture of the Grid; it is used instead of asking every Node, which is fast but can briefly lag reality, for example just after the Distributor starts.

Synchronous and asynchronous calls

The Grid uses two mechanisms. Synchronous JSON-over-HTTP calls are used when the action is synchronous (most WebDriver commands) or when missing the answer would be a problem. Asynchronous events on the Event Bus are used to broadcast information to anyone who is interested or when losing a message does not matter. Events are more decoupled from their listeners than HTTP calls are.

Node registration and the status object

A Node emits a heartbeat event periodically (60 seconds by default, --heartbeat-period). When the Distributor sees one it calls the Node’s /status endpoint over HTTP and, from that, builds the Grid Model. It uses the same endpoint to check the Node on a schedule (--healthcheck-interval, 120 seconds by default), and the Node keeps sending heartbeats so a Distributor that was restarted catches up. Nodes the Distributor has not heard from for a while are purged (--purge-nodes-interval, 30 seconds). The Node status is a JSON object with these fields:

Field Type Meaning

availability

string

up, draining or down. draining means no new sessions are sent; when the last session closes the Node exits or restarts.

externalUrl

string

The URI the other components use to reach the Node.

lastSessionCreated

integer

Epoch time of the last session started here. When everything else is equal the Distributor prefers the Node idle the longest.

maxSessionCount

integer

How many sessions may run at once before the Node counts as full.

nodeId

string

A UUID for this instance of the Node.

osInfo

object

arch, name and version; used by the Grid UI and GraphQL.

slots

array

The slot objects: id, lastStarted (ISO 8601), stereotype and, while busy, the session (capabilities, startTime, stereotype, uri).

version

string

The Node’s version, which matches the Selenium version.

Source: Selenium — Grid architecture

A Node can have more slots than it can run at once: a Node with maxSessionCount 10 and three browsers has 10 slots for each of them, and the cap applies to the total.

Slot selection

The Distributor chooses among the Nodes that match with a slot selector. The default, DefaultSlotSelector, picks the Node that has been free the longest, which spreads sessions evenly. GreedySlotSelector does the opposite and fills one Node before using another, which suits autoscaled environments where idle Nodes should disappear. Select it with --slot-selector (the environment variable SE_DISTRIBUTOR_SLOT_SELECTOR in the Docker images). --slot-matcher replaces the code that decides whether a Node can serve a request, and --reject-unsupported-caps true makes the Distributor fail a request at once if no Node could ever serve it (useful when Nodes are not created on demand, and the behaviour seen in this page’s Chrome-only Standalone).

Source: docker-selenium — Fully distributed mode

Grid sizes and sizing a Node

Creating sessions concurrently depends on the CPUs of the machine that runs the Distributor: with 4 CPUs it can create up to 4 sessions at the same time (--newsession-threadpool-size, which defaults to the number of processors times three, tunes it). A Node’s default --max-sessions is the number of CPUs, with the exception of Safari, which is always one; the documentation suggests budgeting about one CPU and 1 GB of memory for each browser session and measuring from there. --override-max-sessions true allows a higher value than the CPU count, at the risk of an unstable Node. Prefer many small Nodes over one big one: a failing Node then affects fewer sessions, and containers make that cheap.

Size Setup (rough guidance from the documentation)

Small

Standalone, or Hub and Node with 5 or fewer Nodes.

Middle

Hub and Node with between 6 and 60 Nodes.

Large

Hub and Node with between 60 and 100 Nodes, or the distributed role with more than 100 Nodes.

Source: Selenium — Getting started with Selenium Grid

Securing a Grid

A Grid executes browsers on behalf of whoever can reach it, so an exposed one lets third parties browse your internal applications, read files the browser can reach and run custom binaries. The official page says to protect it with firewall permissions. The built-in options are:

  • Do not publish the Grid port to the internet. Put it on a private network or behind a reverse proxy, and use --sub-path if the proxy serves it under a path.

  • Router basic authentication (username and password in the [router] TOML section, or --username and --password). The Grid UI and the new session request then need the credentials. In Java, pass them in the client configuration; in other bindings put them in the URL.

  • A shared registration secret (--registration-secret) so only Nodes that know it can register or be drained or removed through the management endpoints.

  • HTTPS with --https-certificate and --https-private-key; java -jar selenium-server-4.51.0.jar info security prints the details.

[router]
username = "admin"
password = "myStrongPassword"

ClientConfig clientConfig = ClientConfig.defaultConfig()
    .baseUrl(new URL("http://localhost:4444"))
    .authenticateAs(new UsernameAndPassword("admin", "myStrongPassword"));
HttpCommandExecutor executor = new HttpCommandExecutor(clientConfig);
RemoteWebDriver driver = new RemoteWebDriver(executor, new ChromeOptions());

Real credentials belong in the environment or a secret store, not in a committed file. This example was not run: the Grids used for the other examples had no authentication.

Configuration

Every component takes the same three kinds of input, which are merged: command-line flags, one or more TOML (or JSON) files passed with --config, and, in the Docker images, environment variables that the start-up scripts translate into flags (for example SE_NODE_MAX_SESSIONS for --max-sessions). The Selenium team recommends TOML files because they can be read and version-controlled, and flags for the few values that change per environment. The documentation warns that its option tables can lag the code, so when in doubt ask the jar itself:

java -jar selenium-server-4.51.0.jar info config        # how configuration works
java -jar selenium-server-4.51.0.jar info security      # HTTPS, registration secret
java -jar selenium-server-4.51.0.jar info sessionmap    # external session map set-up
java -jar selenium-server-4.51.0.jar info tracing       # OpenTelemetry and Jaeger
java -jar selenium-server-4.51.0.jar --config-help      # every command and its options
java -jar selenium-server-4.51.0.jar standalone --help  # options of one component

Source: Selenium — Configuration help

Observability

Selenium Server is instrumented with OpenTelemetry. Every request is traced from start to end; a trace is made of timed spans, a span has attributes, and most spans carry two kinds of events: a normal event that records a unit of work and its success, and an error event with the exception information. Tracing is on by default (--tracing true) and works in every role. Traces are exported in two ways: to the console at FINE level (the default log level is INFO, so raise it with --log-level FINE) and to a tracing backend such as Jaeger, whose setup java -jar selenium-server-4.51.0.jar info tracing prints.

java -jar selenium-server-4.51.0.jar standalone --log-level FINE

Source: Selenium — Observability in Selenium Grid

Events can also be logged as structured JSON (--structured-logs true; pretty-printing is off). Every event record has the event time in epoch nanoseconds, the trace id and span id, the span kind, the event name and the event attributes (such as http.status_code, http.handler_class, http.url, http.method, session.id); an error event adds exception.type, exception.message and exception.stacktrace. Tracing must stay enabled for event logging even if you never export traces. The official page shows a sample record for a DELETE /session/<id> and one for an exception from a misconfigured JDBC session map. Neither this logging nor Jaeger were run for this page (no Jaeger container was started); the standard logging lines quoted earlier are real.

Customising a Node

To add set-up before a session and clean-up after it (or any other decoration), write a class that extends org.openqa.selenium.grid.node.Node, give it a static factory public static Node create(Config config), and pass its fully qualified name with --node-implementation. The usual pattern is a wrapper: create the default LocalNode with LocalNodeFactory.create(config) inside your factory and delegate every method to it, adding behaviour around the calls. The documentation’s sample, DecoratedLoggingNode, prints a line before and after each operation (newSession, executeWebDriverCommand, getSession, uploadFile, downloadFile, stop, isSessionOwner, isSupporting, getStatus, drain, isReady and the rest). The core of it is:

public class DecoratedLoggingNode extends Node {
  private Node node;

  protected DecoratedLoggingNode(Tracer tracer, NodeId nodeId, URI uri, Secret registrationSecret, Duration sessionTimeout) {
    super(tracer, nodeId, uri, registrationSecret, sessionTimeout);
  }

  public static Node create(Config config) {
    LoggingOptions loggingOptions = new LoggingOptions(config);
    BaseServerOptions serverOptions = new BaseServerOptions(config);
    URI uri = serverOptions.getExternalUri();
    SecretOptions secretOptions = new SecretOptions(config);
    NodeOptions nodeOptions = new NodeOptions(config);
    Duration sessionTimeout = nodeOptions.getSessionTimeout();

    Node node = LocalNodeFactory.create(config);   // the real Node that does the work
    DecoratedLoggingNode wrapper = new DecoratedLoggingNode(loggingOptions.getTracer(), node.getId(), uri,
        secretOptions.getRegistrationSecret(), sessionTimeout);
    wrapper.node = node;
    return wrapper;
  }

  @Override
  public Either<WebDriverException, CreateSessionResponse> newSession(CreateSessionRequest sessionRequest) {
    return perform(() -> node.newSession(sessionRequest), "newSession");
  }

  // ... every other abstract method of Node delegates the same way
}

Source: Selenium — Customizing a Node

Package it in one of two ways. As an uber jar (use the Maven Shade plugin rather than the Assembly plugin, which does not merge the META-INF/services files properly), started with java -jar custom_node-server.jar node --node-implementation org.seleniumhq.samples.DecoratedLoggingNode. Or as a regular jar added to the stock server: java -jar selenium-server-4.51.0.jar --ext custom_node-1.0-SNAPSHOT.jar node --node-implementation org.seleniumhq.samples.DecoratedLoggingNode. The project needs the org.seleniumhq.selenium:selenium-grid dependency. The documentation also points to a second implementation, org.openqa.selenium.grid.node.k8s.OneShotNode, that shuts itself down after one session; it is not in any pre-built Maven artifact, so it has to be built from the source. This section was not run: the interfaces of Node are an internal API of Selenium Server that can change between releases, so the sample must be compiled against the same version as the server that loads it.

Watching a session: noVNC and VNC

The browser images run the browser in a virtual display and serve it two ways: a VNC server on port 5900 and a browser-based noVNC client on port 7900 (--no-vnc-port, SE_NO_VNC_PORT). Publish the port you need and open http://localhost:7900/?autoconnect=1&resize=scale&password=secret while a test is running; secret is the default VNC password, and SE_VNC_NO_PASSWORD=1 removes it (used in the Compose file above, for a local Grid only) while SE_VNC_PASSWORD sets another. The Grid UI links a running session to the same view. The Node reports se:vncEnabled and se:noVncPort in the slot stereotype, which is visible in the /status output. With several Nodes on one host, map each container to a different host port. For the Compose file above, the noVNC pages answered HTTP 200 on 7960 (Standalone), 7961 (Chrome Node) and 7962 (Firefox Node). Viewing needs a person, so the picture itself was not inspected. The noVNC view is a debugging tool: it shows the real browser, headed, so a test that is flaky only in the Grid can be watched while it runs. Headless browsers have no display to show, and video recording does not support them.

Recording video

A recording needs a second container, selenium/video, in front of every browser container (one to one, so five Nodes need five recorders). It watches the browser’s virtual display with ffmpeg and writes MP4 files to /videos, so mount a host directory there. Expect about one CPU for each recorder and one for each browser. The Compose service above is the recommended wiring: DISPLAY_CONTAINER_NAME names the Node container whose display is recorded, SE_NODE_GRID_URL lets the recorder ask the Hub which session is active, and SE_VIDEO_FILE_NAME=auto names each file from the se:name capability of the session plus the session id.

The file names show it working: the tests set se:name to paginationShowsSixBooksPerPage [chrome] and the recorder produced paginationShowsSixBooksPerPage_chrome_18d3c45fc014cd072d0d339950f2538f.mp4 (spaces become underscores, characters outside letters, digits, hyphen and underscore are removed, and the name is cut to 255 characters; SE_VIDEO_FILE_NAME_TRIM_REGEX changes the pattern and SE_VIDEO_FILE_NAME_SUFFIX=false drops the session id). The files started with the standard MP4 ftyp header and were 64 KB and 175 KB for sessions of a second or two.

Not every session was recorded in this run, and that is worth knowing before relying on video:

  • The Chrome Node had two slots, and the recorder films one display. When two Chrome sessions ran at the same time (the parallel JUnit run) only one produced a file. For video, run one session per recorded Node (SE_NODE_MAX_SESSIONS=1).

  • Of two sequential runs of two Chrome tests each lasting a second or two, only one test in each run produced a file. The recorder polls for sessions (SE_VIDEO_POLL_INTERVAL, default 1 second here) when it is not in event-driven mode, so very short sessions can be missed. Real tests take longer, but a smoke test that finishes in under a second may not be filmed.

By default the recorder films every session (SE_RECORD_VIDEO is true in the video image). A test can decide for itself with the se:recordVideo capability, which wins over the variable for that session: set SE_RECORD_VIDEO=false and opt in per test, or leave it on and send false for the sessions that do not need a video. The capability also works in event-driven mode, where the recorder subscribes to the Event Bus instead of polling. Videos can be uploaded (SE_VIDEO_UPLOAD_ENABLED) or kept only for failed sessions, which the repository documents; neither was tried here.

Three details cost time and are not obvious from the documentation:

  • The configuration file has to be mounted at /opt/selenium/docker.toml, not at config.toml, together with SE_NODE_DOCKER_CONFIG_FILENAME=docker.toml. When it was mounted as config.toml, the image ignored it and used a generated default file, which on this host named the image tags 4.48.0-20260905, and the server failed to start with "no matching manifest for linux/arm64 in the manifest list entries" because that tag has no arm64 image.

  • An assets directory must be mounted at /opt/selenium/assets. Without it every session failed with "Assets path must be set" and the client saw a session-not-created error.

  • The browser containers need the same host.docker.internal mapping as other containers, which host-config-keys with ExtraHosts passes down; give the standalone container itself an extra_hosts entry on Linux.

Mounting the Docker socket gives the container full control of the host’s Docker daemon: use a Dynamic Grid only in a trusted environment.

Helm chart and KEDA autoscaling

For Kubernetes the project offers a Helm chart that deploys the Grid (and, optionally, scales it). Add the repository and install:

Source: docker-selenium — Helm chart README

Autoscaling uses KEDA with its selenium-grid scaler, which reads the number of pending and running sessions from the Grid’s GraphQL endpoint and scales browser Node Deployments or Jobs up and down. Enable it with autoscaling.enabled (the chart then installs KEDA) or autoscaling.enableWithExistingKEDA (use a KEDA you already have). autoscaling.scalingType selects between deployment (a ScaledObject: long-running Nodes scaled by replica count, with a terminationGracePeriodSeconds of 3600 seconds by default so running tests finish) and job (a ScaledJob: one short-lived Node for each session, which is a close cousin of a Dynamic Grid). The trigger metadata browserVersion and platformName should be set explicitly for correct scaling when the Grid mixes autoscaled and fixed Nodes, and the client request should use the same values. The chart can also deploy an external scaler that the Selenium project maintains separately from KEDA’s built-in one. The Distributor works hard during mass scale-up, so the chart sets the new-session thread pool (SE_NEW_SESSION_THREAD_POOL_SIZE, behind --newsession-threadpool-size) from the number of node types and the maximum replica count.

Java and JUnit 5

The first example is a parameterised JUnit 5 test class that runs the same test on Chrome and on Firefox. Two details matter for parallel runs: the driver of each test lives in a ThreadLocal, so concurrent tests in the same JVM never share a session, and the application URL is the address of Bookshelf as the browser sees it (host.docker.internal), while the Grid URL is the address as the test sees it. Both come from system properties so a pipeline can override them.

package demo;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

import java.net.URI;
import java.time.Duration;
import java.util.Locale;
import org.junit.jupiter.api.AfterEach;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;
import org.openqa.selenium.By;
import org.openqa.selenium.Capabilities;
import org.openqa.selenium.MutableCapabilities;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeOptions;
import org.openqa.selenium.firefox.FirefoxOptions;
import org.openqa.selenium.remote.RemoteWebDriver;
import org.openqa.selenium.support.ui.ExpectedConditions;
import org.openqa.selenium.support.ui.WebDriverWait;

class GridCrossBrowserTest {
  // Where the tests talk to the Grid, and where the *browser* finds the application.
  static final String GRID_URL = System.getProperty("grid.url", "http://localhost:4602");
  static final String APP_URL = System.getProperty("app.url", "http://host.docker.internal:3916");

  private final ThreadLocal<RemoteWebDriver> driver = new ThreadLocal<>();

  static MutableCapabilities optionsFor(String browser) {
    return switch (browser) {
      case "chrome" -> new ChromeOptions();
      case "firefox" -> new FirefoxOptions();
      default -> throw new IllegalArgumentException(browser);
    };
  }

  RemoteWebDriver start(String browser, String testName) throws Exception {
    MutableCapabilities options = optionsFor(browser);
    options.setCapability("se:name", testName + " [" + browser + "]"); // shown in the Grid UI
    RemoteWebDriver d = new RemoteWebDriver(URI.create(GRID_URL).toURL(), options);
    driver.set(d);
    return d;
  }

  @AfterEach
  void stop() {
    RemoteWebDriver d = driver.get();
    if (d != null) {
      d.quit();
      driver.remove();
    }
  }

  @ParameterizedTest(name = "search on {0}")
  @ValueSource(strings = {"chrome", "firefox"})
  void searchFindsBook(String browser) throws Exception {
    WebDriver d = start(browser, "searchFindsBook");
    d.get(APP_URL + "/books");
    d.findElement(By.cssSelector("[data-testid=search-input]")).sendKeys("quiet");
    d.findElement(By.cssSelector("[data-testid=search-submit]")).click();
    new WebDriverWait(d, Duration.ofSeconds(10)).until(ExpectedConditions.textToBePresentInElementLocated(
        By.cssSelector("[data-testid=result-count]"), "1 book found"));
    assertEquals(1, d.findElements(By.cssSelector("[data-testid=book-card]")).size());

    // Which browser did the Grid really give us?
    Capabilities actual = driver.get().getCapabilities();
    assertEquals(browser, actual.getBrowserName().toLowerCase(Locale.ROOT));
    System.out.printf("%s ran on %s %s (%s) in session %s%n", Thread.currentThread().getName(),
        actual.getBrowserName(), actual.getBrowserVersion(), actual.getPlatformName(),
        driver.get().getSessionId());
  }

  @ParameterizedTest(name = "pagination on {0}")
  @ValueSource(strings = {"chrome", "firefox"})
  void paginationShowsSixBooksPerPage(String browser) throws Exception {
    WebDriver d = start(browser, "paginationShowsSixBooksPerPage");
    d.get(APP_URL + "/books");
    assertEquals(6, d.findElements(By.cssSelector("[data-testid=book-card]")).size());
    d.findElement(By.cssSelector("[data-testid=page-next]")).click();
    new WebDriverWait(d, Duration.ofSeconds(10)).until(ExpectedConditions.textToBePresentInElementLocated(
        By.cssSelector("[data-testid=page-indicator]"), "2"));
    assertTrue(d.getCurrentUrl().contains("page=2"), d.getCurrentUrl());
  }
}

What happens when the Grid is full

A Grid with fewer free slots than requests does not fail them: it queues them (up to the request timeout). This script opens two Chrome sessions on the Hub’s Chrome Node, asks for a third in a thread, and uses GraphQL to look at the queue. The third session is served as soon as one of the others quits:

import json
import threading
import time
import urllib.request

from selenium import webdriver

GRID = "http://localhost:4602"


def grid_numbers():
    request = urllib.request.Request(
        f"{GRID}/graphql",
        data=json.dumps({"query": "{ grid { sessionCount, sessionQueueSize } }"}).encode(),
        headers={"Content-Type": "application/json"})
    return json.load(urllib.request.urlopen(request))["data"]["grid"]


# The Chrome Node has two slots: two sessions fill it, the third has to wait in the queue.
first, second = (webdriver.Remote(GRID, options=webdriver.ChromeOptions()) for _ in range(2))
result = {}


def third():
    started = time.time()
    result["driver"] = webdriver.Remote(GRID, options=webdriver.ChromeOptions())
    result["waited"] = time.time() - started


thread = threading.Thread(target=third)
thread.start()
time.sleep(3)
print("while queued:", grid_numbers())
first.quit()                      # frees a slot, the queued request is served
thread.join()
print(f"third waited {result['waited']:.1f}s")
print("after:", grid_numbers())
second.quit()
result["driver"].quit()

The practical consequence is that parallelism in the test runner can safely be higher than the number of slots, at the price of the waiting time that shows up as a long session start; and that the client’s HTTP timeout, not just the Grid’s --session-request-timeout, can end a wait. Capabilities that talk to the Grid

Capabilities with the se: prefix are for Grid and docker-selenium; the Grid ignores unknown ones for matching.

Capability Effect

se:name

A test name shown instead of the session id in the Grid UI and used for the video file name when SE_VIDEO_FILE_NAME=auto.

se:recordVideo

Record or skip the session in the docker-selenium recorder, overriding SE_RECORD_VIDEO.

se:downloadsEnabled

Ask the Node to keep the files the session downloads so the client can list, fetch and delete them (options.setEnableDownloads(true) in Java). Needs --enable-managed-downloads on the Node.

se:vncEnabled, se:noVncPort

Reported by Nodes that expose VNC.

Any se: or vendor-prefixed capability

Metadata, visible in the session information and through GraphQL.

Source: Selenium — Getting started with Selenium Grid

Uploads and downloads cross the network when the browser is remote. An upload from a RemoteWebDriver needs a file detector so that sendKeys with a local path sends the file to the Node (Java has none by default, so call setFileDetector(new LocalFileDetector()); some other bindings include a basic one by default). A download is kept on the Node, so request it with se:downloadsEnabled and fetch it through HasDownloads in Java (getDownloadableFiles, downloadFile, deleteDownloadableFiles) or the /session/<id>/se/files endpoint of the Grid. Neither was run: the Bookshelf application has no upload or download feature.

WebDriver BiDi and CDP also flow through the Grid as web sockets: the Router opens a TCP tunnel (--tcp-tunnel) so the client connects to the Node. See WebDriver BiDi for what to do with them. If a firewall, proxy or ingress does not carry web sockets, disable them with --enable-cdp false and --enable-bidi false.

Pitfalls

  • localhost in the browser means the browser’s machine. Give containers host.docker.internal (with host-gateway on Linux) or a name on the Docker network; never the URL that works from your IDE.

  • A request for a browser the Grid does not have fails at once with "No nodes support the capabilities in the request", as the Firefox cases against the Chrome Standalone showed. --reject-unsupported-caps is the documented switch for this behaviour on Grids that create Nodes on demand.

  • totalSlots is not capacity. Read maxSession for how many sessions can run at once.

  • Release the session in a finally, @AfterEach or fixture finalizer. A session that is never quit keeps its slot until --session-timeout (300 seconds by default) expires.

  • The Grid in a container must be told its own external address when clients cannot reach the container IP (SE_NODE_GRID_URL, --external-url, --grid-url), and Node containers need SE_EVENT_BUS_HOST and both Event Bus ports.

  • Keep the Grid and the bindings on the same version where you can. Pin the images to a tag and update them together with the bindings, so a new se: capability or protocol change is available on both sides.

  • On Apple silicon the images run as linux/arm64. Some default tags that ship inside images may have no arm64 build, as the Dynamic Grid section shows.

  • Keep a Grid private. See the security section.
