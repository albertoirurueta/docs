Selenium: Locating & Interacting

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Selenium WebDriver drives a real browser through the W3C WebDriver protocol: you ask the driver for a reference to a page element, then tell the browser to do something with it, or you send the browser itself a command such as "go back", "accept this dialog" or "print this page". This page covers both halves of that vocabulary: how to find things (locators, finders, relative locators, the shadow DOM) and how to act on them and on the browser (element interactions, select lists, the Actions API, navigation, alerts, cookies, frames, windows and tabs, the virtual authenticator and PDF printing). It was written against Selenium 4.51.0 (released 9 October 2026) and checked on 25 October 2026. The Java examples use Java 17 and JUnit 5.14.4; the Python examples use pytest with Selenium 4.51.0 and Python 3.13. All of them were run against the Bookshelf application with Chrome 155 driven headless through Selenium Manager, and a subset of the Python suite also ran against Firefox in a docker-selenium container (the differences are listed near the end). The C#, Ruby and JavaScript snippets show where the official documentation differs between languages; they were not run, because this work only executed the Java and Python bindings.

Waiting for things to be ready, which is what makes any of this reliable, is the subject of Waits & Expected Conditions; starting browsers and setting their options is covered in Drivers, Browsers & Options, and installing and the first script in Getting Started. How to organise the locators of a page into page objects is in Test Design & Page Objects. For the same ideas in the other tools, see Playwright: Locators, Actions & Auto-waiting and Cypress: Queries, Assertions & Custom Commands.

Locating elements

A locator is a way to identify one or more elements on the page; it is the argument you give to findElement / find_element. Selenium supports eight traditional strategies, all built on the By class (Java, C#, Ruby and JavaScript spell it By.id(...), By.Id(...), {id: ...} and By.id(...); Python uses By.ID constants):

Strategy Matches Java / Python

id

The element whose id attribute equals the value.

By.id("q") / By.ID, "q"

name

Elements whose name attribute equals the value.

By.name("q") / By.NAME, "q"

class name

Elements whose class attribute contains the value. A compound class name ("a b") is not permitted; use a CSS selector for that.

By.className("card") / By.CLASS_NAME, "card"

tag name

Elements with that tag.

By.tagName("h1") / By.TAG_NAME, "h1"

link text

Anchor elements whose visible text matches the value exactly.

By.linkText("Catalogue") / By.LINK_TEXT, "Catalogue"

partial link text

Anchor elements whose visible text contains the value; with several matches findElement returns the first.

By.partialLinkText("Sign") / By.PARTIAL_LINK_TEXT, "Sign"

CSS selector

Anything a CSS selector can express: attributes, structure, pseudo-classes.

By.cssSelector("[data-testid=book-author]") / By.CSS_SELECTOR, "[data-testid=book-author]"

XPath

A path through the document tree, absolute or relative; also the only strategy that can match on text of any element or climb to a parent.

By.xpath("//li[@data-testid='book-card']//h3") / By.XPATH, "//li[@data-testid='book-card']//h3"

The id, name, class name and tag name strategies are, in the WebDriver protocol, shortcuts that the driver turns into CSS selectors, so the CSS selector and XPath strategies are the two that carry real expressive power. All eight run against Bookshelf’s catalogue page like this:

@Test
void eightStrategies() {
  driver.get(BASE_URL + "/books?q=quiet");
  assertEquals("quiet", driver.findElement(By.id("q")).getDomProperty("value"));
  assertEquals("search", driver.findElement(By.name("q")).getDomAttribute("type"));
  assertEquals("1", driver.findElement(By.className("card")).getDomAttribute("data-book-id"));
  assertTrue(driver.findElement(By.linkText("Catalogue")).getDomProperty("href").endsWith("/books"));
  assertEquals("Sign in", driver.findElement(By.partialLinkText("Sign")).getText());
  assertEquals("Catalogue", driver.findElement(By.tagName("h1")).getText());
  assertEquals("The Quiet Compiler",
      driver.findElement(By.xpath("//li[@data-testid='book-card']//h3")).getText());
  assertEquals("Mara Velde", driver.findElement(By.cssSelector("[data-testid=book-author]")).getText());
}

Choosing a locator

Locators are the part of a Selenium suite that breaks most often, so choose them with the page’s contract in mind rather than its current markup. A practical order, which matches the guidance of the other tools:

  1. A dedicated test attribute, such as Bookshelf’s data-testid, through a CSS selector: [data-testid=search-submit]. Selenium has no built-in test-id locator (Playwright has getByTestId), so wrap the selector once in a helper or a page object.

  2. An id or name that is part of the page’s behaviour (form fields, anchors targeted by labels): stable, fast and unambiguous when unique. Ids are only unique by convention, so a page with duplicate ids returns the first match.

  3. Link text or partial link text for navigation links whose wording is part of the user-facing contract. They break on any copy change or translation, and only match a elements.

  4. CSS selectors on structure (.card > a) when no attribute exists. Prefer short selectors tied to meaningful ancestors over long chains copied from the browser’s developer tools.

  5. XPath when you need what CSS cannot do: matching by text (//button[normalize-space()='Search']), selecting a parent or ancestor, or position-based logic. Avoid absolute paths (/html/body/div[2]/...), which break on any layout change.

  6. Relative locators (below) when an element is hard to describe but easy to place next to one that is not.

Selenium has no role- or label-based locators like Playwright’s getByRole and getByLabel. The accessibility information is available after the fact (getAriaRole() and getAccessibleName(), in the element-information section), and the XPath-with-label pattern //label[text()='Username']/following-sibling::input is the usual workaround.

ByChained and ByAll (Java)

The Java support package has two composite locators. ByChained applies several locators in sequence, each searching inside the previous result, so one findElement replaces a parent lookup followed by a child lookup. ByAll returns elements that match any of the locators, in document order, so one findElements finds, for example, the username and password fields together:

import org.openqa.selenium.support.pagefactory.ByAll;
import org.openqa.selenium.support.pagefactory.ByChained;

@Test
void chainedAndAllLocators() {
  driver.get(BASE_URL + "/books");
  WebElement title = driver.findElement(new ByChained(By.cssSelector("[data-testid=book-list]"), By.tagName("h3")));
  assertFalse(title.getText().isEmpty());
  driver.get(BASE_URL + "/signin");
  List<WebElement> fields = driver.findElements(new ByAll(By.id("username"), By.id("password")));
  assertEquals(2, fields.size());
}

The Python bindings have no equivalent classes (a search in the 4.51.0 package finds none); chain find_element calls on the parent element, or use a combined CSS selector, instead.

Relative locators

Relative locators (called friendly locators in Selenium 3 documentation) describe an element by where it is relative to another one. Selenium asks the browser for the position and size of the candidate elements and picks those that satisfy the spatial relationship. They are useful when an element has no good attribute but its neighbour does:

Method (Java / Python) Meaning

above / above

The element’s bottom edge is above the reference element’s top edge.

below / below

The element is below the reference.

toLeftOf / to_left_of

The element is left of the reference.

toRightOf / to_right_of

The element is right of the reference.

near / near

The element is at most 50 pixels from the reference by default; Java accepts a different distance as a second argument.

The reference can be a locator or a previously located element; the starting point is the tag, or any other locator, that filters the candidates (with(By.tagName("input"))). Calls chain, which combines constraints (below the email field and right of the cancel button). They run on Bookshelf’s sign-in form:

import static org.openqa.selenium.support.locators.RelativeLocator.with;

@Test
void relativeLocators() {
  driver.get(BASE_URL + "/signin");
  WebElement above = driver.findElement(with(By.tagName("input")).above(By.id("password")));
  WebElement below = driver.findElement(with(By.tagName("input")).below(By.id("username")));
  WebElement near = driver.findElement(with(By.tagName("input")).near(By.cssSelector("label[for=username]")));
  assertEquals("username", above.getDomAttribute("id"));
  assertEquals("password", below.getDomAttribute("id"));
  assertEquals("username", near.getDomAttribute("id"));
  WebElement button = driver.findElement(with(By.tagName("button")).below(below).toLeftOf(By.id("theme-toggle")));
  assertEquals("Sign in", button.getText());
}

Relative locators are computed from the rendered geometry, so they depend on viewport size and layout: a responsive design that stacks a row of buttons vertically at phone width changes what toLeftOf means. Use them as a fallback, check them at the viewport your tests actually run in, and prefer near only when the relative positions vary.

Finding elements

find_element and find_elements

findElement returns a reference to the first matching element in document order and throws NoSuchElementException when nothing matches. findElements returns a list of every match and an empty list when there are none, which makes it the idiomatic existence check. A reference is a handle to an element in the browser’s current document; if the page replaces that element (a re-render, a navigation) the handle becomes stale and any use throws StaleElementReferenceException, so look the element up again rather than caching it across page changes.

Scoping a search

WebDriver, WebElement and ShadowRoot all implement the SearchContext interface, so a search can start from any of them. A lookup from an element searches only its descendants; use it to find a field inside the right card when the page repeats the same markup, instead of building one long locator:

@Test
void findersScopingAndActiveElement() {
  driver.get(BASE_URL + "/books");
  List<WebElement> cards = driver.findElements(By.cssSelector("[data-testid=book-card]"));
  assertEquals(6, cards.size());
  assertFalse(cards.get(0).findElement(By.tagName("h3")).getText().isEmpty());
  assertTrue(driver.findElements(By.id("does-not-exist")).isEmpty());
  assertThrows(NoSuchElementException.class, () -> driver.findElement(By.id("does-not-exist")));
  driver.findElement(By.id("q")).click();
  assertEquals("q", driver.switchTo().activeElement().getDomAttribute("id"));
}

The shadow DOM

A shadow DOM is an encapsulated DOM tree hidden inside an element (a shadow host): ordinary locators on the document do not see into it. Selenium can reach an open shadow root with getShadowRoot() (Java) or shadow_root (Python), which returns a SearchContext you can search from. Inside a shadow root use CSS selectors: when tried with Python on Chrome 155, By.ID and CSS selectors worked, while an XPath and a tag-name lookup failed with invalid argument: invalid locator. A lookup stays inside that one root and does not cross into nested shadow roots (a selector for an element two roots down raised NoSuchElementException), so nested components are searched one root at a time. The examples use an open shadow root; closed roots were not tested.

@Test
void shadowDom() {
  driver.get(dataUrl("""
      <div id=host></div><script>
      const r = document.getElementById('host').attachShadow({mode: 'open'});
      r.innerHTML = '<button id=inner class=pill>Inside</button><input name=q>';
      </script>"""));
  SearchContext root = driver.findElement(By.id("host")).getShadowRoot();
  assertEquals("Inside", root.findElement(By.cssSelector("#inner")).getText());
  assertEquals(2, root.findElements(By.cssSelector("button, input")).size());
  // since 4.50 relative locators also work from a shadow root
  WebElement input = root.findElement(with(By.tagName("input")).near(By.id("inner")));
  assertEquals("q", input.getDomAttribute("name"));
}

Interacting with elements

The high-level element commands are click, sendKeys / send_keys, clear and submit, plus the Select helper covered below. They are designed to emulate a user’s experience, and unlike the Actions API they try to make the action possible first:

  • If the element is outside the viewport, Selenium scrolls it into view (aligning the bottom of the element with the bottom of the viewport) before acting. If that fails, or the element is not displayed for another reason, the command throws.

  • Selenium decides whether an element is displayed by running a JavaScript atom that checks for things that would keep it from being visible (display: none, zero size, hidden by an ancestor and so on). The W3C specification mentions the concept but does not define it, which is why isDisplayed() is an approximation.

  • If the centre of the element is covered by another element, click throws ElementClickInterceptedException. A sticky header, a cookie banner or an overlay still animating away are the usual culprits; wait for the covering element to go (an explicit condition, see Waits & Expected Conditions) rather than forcing the click with JavaScript, which would hide the bug a real user would hit.

click clicks the centre of the element. sendKeys types the keys into a keyboard-interactable element, typically a text input or an element with contenteditable; otherwise it throws. The key constants (Keys.ENTER, Keys.TAB, Keys.CONTROL and so on) can be sent too. clear resets the content of an editable element. submit was a separate endpoint in Selenium 3; in Selenium 4 it works by running a script, so the documentation recommends clicking the page’s submit button instead. The test below exercises all four on a small page:

@Test
void informationAndInteractions() {

The Actions API

The element commands above are high-level. The Actions API is the low-level interface: it sends virtualised device input to the browser, exactly as the W3C specification describes it. Selenium provides three kinds of input source: a key input for keyboards, a pointer input for a mouse, a pen or a touch device, and a wheel input for a scroll wheel (added in Selenium 4.2). You build a chain of actions assigned to those inputs and run them with perform(); the browser executes them in order. Each pointer movement and wheel scroll can take a duration, and pause adds a plain wait between actions.

You rarely need the raw building blocks: the Actions class (Java) and ActionChains (Python) combine them into convenience methods for the common gestures, as shown below. Two things to remember:

  • The driver remembers the state of every input device for the whole session. A key that was pressed and not released stays pressed, and the pointer stays wherever the last action left it, even if you create a new Actions object. There is a special method to release everything: ((RemoteWebDriver) driver).resetInputState() in Java, ActionChains(driver).reset_actions() in Python. In a suite with a fresh browser per test this rarely matters, but with a shared driver call it between tests.

  • Actions do not scroll for you, unlike click and sendKeys. Moving the pointer to an element that is outside the viewport fails, and the wheel input exists precisely to scroll first.

All the Actions examples share one fixture page: an input, a target div, a draggable box and a drop zone, with a log that records the events the browser delivered, and a tall div so the page can scroll.

Keyboard actions

A keyboard can do exactly two things: press a key down and release a pressed key. Regular characters are keys; the non-character keys (Shift, Control, Enter, arrows) have unicode values that Selenium exposes as the Keys class (the constants differ by language, and the full list is in each binding’s API documentation). sendKeys in the Actions API is a convenience that combines keyDown and keyUp for typing several characters in the middle of other actions; given an element, it first moves to or focuses that element. The example types text, then holds Shift for a capital letter, then does select-all and cut with the platform’s shortcut key (Command on macOS, Control elsewhere):

Scroll wheel actions

Because Actions does not scroll by itself, the wheel input provides four ways to scroll:

  • Scroll to an element (scrollToElement / scroll_to_element): scrolls so that the bottom of the element is at the bottom of the viewport, whether the element was above or below. If the element is already inside the viewport nothing happens. The most common case.

  • Scroll by an amount (scrollByAmount(dx, dy) / scroll_by_amount(dx, dy)): positive values go right and down, negative left and up.

  • Scroll from an origin (scrollFromOrigin / scroll_from_origin), which takes a scroll origin and a delta. The origin is either the viewport (an offset from its upper-left corner) or an element (an offset from its centre). Use it to scroll only part of the page, for example a nested scrollable container or an iframe. If the element is out of view it is first scrolled to the bottom of the viewport, and if the resulting origin falls outside the viewport the command errors.

Scrolling is asynchronous in a browser with smooth scrolling, so assert on the final scroll position with a wait, not immediately:

@Test
void wheel() {
  driver.get(dataUrl(PAGE));

  new Actions(driver).scrollFromOrigin(ScrollOrigin.fromViewport(10, 10), 0, -200).perform();
  wait.until(d -> scrollY() == 300);
  new Actions(driver).scrollToElement(driver.findElement(By.id("tall"))).perform();
}

Frames and iframes

Frames (a deprecated way of building layouts from several documents) and iframes (a document embedded from the same or another origin) are separate browsing contexts. Selenium only sees the elements of the top-level document until you switch into the frame, so looking for a button that lives in an iframe fails with NoSuchElementException even though you can see it. There are three ways to switch:

  • By element (the most flexible): find the iframe element with any locator and pass it to switchTo().frame(element).

  • By name or id: switchTo().frame("inner-name"); if the value is not unique, the first match wins.

  • By index: switchTo().frame(1), the position among the frames of the current document (zero-based).

To leave, switchTo().defaultContent() returns to the top-level document and switchTo().parentFrame() goes up one level. The tests use two iframes created from srcdoc attributes:

@Test
void frames() {
  driver.get(dataUrl("""
      <h1 id=top>Top</h1><iframe id=inner name=inner-name srcdoc="<button id=b onclick=&quot;this.textContent='clicked'&quot;>Inside</button>"></iframe>
      <iframe srcdoc="<p id=second>Second</p>"></iframe>"""));
  assertThrows(NoSuchElementException.class, () -> driver.findElement(By.id("b")));
  driver.switchTo().frame(driver.findElement(By.id("inner")));   // by element
  driver.findElement(By.id("b")).click();
  assertEquals("clicked", driver.findElement(By.id("b")).getText());
  driver.switchTo().defaultContent();
  driver.switchTo().frame("inner-name");                         // by name or id
  driver.switchTo().parentFrame();
  driver.switchTo().frame(1);                                    // by index
  assertEquals("Second", driver.findElement(By.id("second")).getText());
  driver.switchTo().defaultContent();
  assertEquals("Top", driver.findElement(By.id("top")).getText());
}

Windows and tabs

WebDriver makes no distinction between windows and tabs. If a site opens a new one, you work with it through its window handle, a string that identifies it for the session. getWindowHandle() returns the handle of the current one and getWindowHandles() the handles of all of them (in the order they were opened, though you should not depend on it for anything but the first). Opening a window with a link or window.open focuses it on screen, but WebDriver does not know which window the operating system considers active, so you must switch to it:

@Test
void windowsAndTabs() {
  driver.get(BASE_URL + "/books");
  String original = driver.getWindowHandle();
  assertEquals(1, driver.getWindowHandles().size());
  ((JavascriptExecutor) driver).executeScript("window.open(arguments[0], '_blank')", BASE_URL + "/signin");
  waitFor().until(ExpectedConditions.numberOfWindowsToBe(2));
  for (String handle : driver.getWindowHandles()) {
    if (!handle.equals(original)) {
      driver.switchTo().window(handle);
    }
  }
  waitFor().until(ExpectedConditions.urlContains("/signin"));
  driver.close();
  driver.switchTo().window(original);   // forgetting this raises NoSuchWindowException
  assertTrue(driver.getCurrentUrl().endsWith("/books"));
  driver.switchTo().newWindow(WindowType.TAB);   // created and focused in one call
  driver.get(BASE_URL + "/");
  assertEquals(2, driver.getWindowHandles().size());
  driver.close();
  driver.switchTo().window(original);
  driver.switchTo().newWindow(WindowType.WINDOW);
  driver.close();
  driver.switchTo().window(original);
}

Virtual authenticator

Web Authentication (WebAuthn) lets users sign in without passwords using public-key credentials held by an authenticator, which can be a hardware key or software in the device. The virtual authenticator emulates one for testing, so a test can register and use a passkey without touching a real device or answering a biometric prompt. In Selenium you create it from VirtualAuthenticatorOptions and add it to the driver; credentials then live in that authenticator, and you can list, add and remove them. Support is a Chromium feature through the DevTools WebAuthn domain; Firefox and Safari do not currently document it. The properties you can set:

Option Meaning

protocol

CTAP2 or U2F. U2F authenticators cannot hold resident (discoverable) credentials.

transport

BLE, INTERNAL, NFC or USB, the transport the authenticator pretends to use.

hasResidentKey

Whether the authenticator supports resident (discoverable) credentials.

hasUserVerification

Whether it supports user verification such as a PIN or biometric.

isUserConsenting

Whether it simulates the user consenting to the operation.

isUserVerified

Whether user verification succeeds or fails; flip it with setUserVerified on the authenticator to test the failure path.

The authenticator exposes these methods: addCredential and addResidentCredential forms (Credential.createResidentCredential and createNonResidentCredential build credentials from an id, relying-party id, a PKCS#8-encoded private key, a user handle for resident ones and a signature counter), getCredentials, removeCredential(id), removeAllCredentials, setUserVerified(boolean), and finally removing the authenticator itself. The test registers a passkey on Bookshelf’s origin (localhost counts as a secure context, so WebAuthn is available), reads the credential back from the authenticator, removes it, adds it again, and uses it to authenticate:

@Test
void virtualAuthenticator() {
  driver.get(BASE_URL + "/");   // localhost is a secure context, so WebAuthn is available
  VirtualAuthenticatorOptions options = new VirtualAuthenticatorOptions()
      .setProtocol(VirtualAuthenticatorOptions.Protocol.CTAP2)
      .setHasResidentKey(true)
      .setHasUserVerification(true)
      .setIsUserVerified(true);
  VirtualAuthenticator authenticator = ((HasVirtualAuthenticator) driver).addVirtualAuthenticator(options);
  Object result = ((JavascriptExecutor) driver).executeAsyncScript("""
      const done = arguments[arguments.length - 1];
      navigator.credentials.create({publicKey: {
        rp: {name: 'Bookshelf'}, user: {id: new Uint8Array([1]), name: 'reader', displayName: 'Reader'},
        challenge: new Uint8Array([1, 2, 3]), pubKeyCredParams: [{type: 'public-key', alg: -7}],
        authenticatorSelection: {residentKey: 'required', userVerification: 'required'}}})
        .then(c => done(c.id), e => done('error: ' + e.name));""");
  assertFalse(result.toString().startsWith("error"));
  List<Credential> credentials = authenticator.getCredentials();
  assertEquals(1, credentials.size());
  assertTrue(credentials.get(0).isResidentCredential());
  Credential stored = credentials.get(0);
  authenticator.removeAllCredentials();
  assertTrue(authenticator.getCredentials().isEmpty());
  authenticator.addCredential(stored);   // a Credential read from the authenticator can be added back

      navigator.credentials.get({publicKey: {challenge: new Uint8Array([4, 5, 6]), userVerification: 'required'}})

  authenticator.setUserVerified(false);   // simulate a failed biometric check

Pitfalls checklist

  • Stale elements. Any action that rebuilds the DOM invalidates references; re-find after navigation, filters, tab switches and Single Page Application re-renders.

  • Click intercepted. An overlay is covering the target; wait for it, do not click through with JavaScript.

  • Implicit waits and findElements. A list lookup that should be empty can burn the whole implicit wait; see Waits & Expected Conditions.

  • Frame state. After switchTo().frame(...) every lookup runs inside it until you leave; reset with defaultContent() in teardown.

  • Window state. After close() switch back; an unclosed extra window leaks into later tests unless quit() runs.

  • Prompt state. A popup you did not handle makes the next command fail; handle it or choose an unhandled-prompt behaviour.

  • Action state. Pressed keys and pointer position persist for the session; call resetInputState() / reset_actions() if a test may leave them dirty.

  • Colour and CSS strings. Normalise through Color before comparing, and never compare computed font or colour strings across browsers.

  • Headless differences. Headless Chrome (--headless=new) shares the real Chrome engine, so locators and interactions behave the same as headed mode, but window size, fonts and popup behaviour can differ; print-to-PDF and some viewport-dependent relative locators are the likeliest to change.

  • Parallel tests. Give each test its own driver; a WebDriver instance is not thread-safe, and the ThreadGuard wrapper (see Waits & Expected Conditions) makes misuse fail loudly.

What changed recently

  • Selenium 4.51 (9 October 2026): the Java client bindings dropped the Guava dependency, so ExpectedCondition no longer implements Guava’s Function; until(d -> ...) lambdas still work. The release also updates the CDP versions (v153 to v155) and adds the BiDi code generator.

  • Selenium 4.50: relative locators can start from an element or a shadow root (the Java example above), and the removed deprecated HTTP client methods may affect custom client factories.

  • October 2026 documentation: runnable shadow DOM finder examples for all bindings (8 October) and tested C# and Kotlin alert examples (20 October). The alert page notes that recent drivers dismiss beforeunload prompts automatically.

  • Selenium 4.5: creating a Select for a disabled select element throws.

  • Selenium 4.2: the wheel input and its scroll actions arrived in the Actions API.

  • Selenium 4.0 and the 4.x line: the W3C-only protocol, getDomAttribute / getDomProperty, switchTo().newWindow, the print command and the virtual authenticator replaced or extended Selenium 3 behaviour; Selenium 3 style capability objects and the JSON Wire Protocol commands are legacy (see Selenium IDE & Legacy).
