Playwright Locators, Actions & Auto-Waiting

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Locators and actions are the two APIs a Playwright test touches on almost every line. A locator describes how to find an element at any moment; an action such as click() or fill() resolves that locator, waits until the element is ready, and only then acts. Together they replace explicit waits in the vast majority of tests. This page covers every built-in locator, the ways to narrow and combine them, the checks Playwright performs before each action (auto-waiting), the input actions, and the page-level features tests need around them: frames, dialogs, downloads, popups, events, evaluating JavaScript, handles and navigations.

The baseline is Playwright 1.64.1 for Node.js (the current release on 25 October 2026); the Python, Java and .NET bindings expose the same locator and action API and were verified at 1.63 and later (see Playwright with Python, Java & .NET). Every example on this page is real test code that was run against the Bookshelf demo application on 25 October 2026, in Chromium and WebKit with Playwright 1.64.1, unless the text says otherwise. The Bookshelf routes, data-testid conventions and credentials are described on that page; passwords are read from BOOKSHELF_READER_PASSWORD and never written in a test. Bookshelf has no iframes, dialogs, downloads or popups, so the examples for those features are served by the test itself: a small serveLab() helper registers a page.route() that answers /lab/<name> with an HTML document (and page.setContent() is used for small snippets), which gives the page a real origin without changing the application. The helper is shown once in The examples on this page.

The model: locators, actionability, retries

A Locator is not an element. It is a recipe (a selector plus the frame it lives in) that Playwright evaluates every time you use it. This has three consequences that the rest of the page builds on:

  • Always up to date. If the page re-renders between two actions, the second action finds the new element. A locator never goes stale, which is the key difference from ElementHandle (see Evaluating JavaScript and handles).

  • Lazy. Creating a locator does not query the page and does not fail when nothing matches. Failure happens when you act on it, and then only after the timeout.

  • Strict. Acting on a locator that matches more than one element is an error (see Strictness and picking by position), while counting or asserting on several elements is fine.

When you call an action, Playwright runs this loop until it succeeds or the action timeout expires: resolve the locator, check the element against the list of actionability checks for that action, scroll it into view if needed, perform the action, and retry from the top if the element detached or a check failed. Web-first assertions such as expect(locator).toBeVisible() use the same retry model; they are covered in Playwright Assertions.

All methods that create a locator exist on Page, Locator, Frame and FrameLocator, so you chain them to narrow the search from the top of the page down to one element.

Built-in locators

Playwright recommends choosing locators in the order a user perceives the page: by role first, then by label, text and the other user-facing attributes, and by test id when there is no accessible handle. CSS and XPath are the last resort.

Non-interactive content: paragraphs, spans, list items, messages.

page.getByLabel(text, { exact })

page.getByPlaceholder(text, { exact })

getByRole

getByRole() reflects how assistive technology sees the page. It uses the W3C rules for implicit roles (a <button> is a button, an <h3> is a heading of level 3), ARIA attributes and the accessible-name computation, so the same locator also gives early feedback on accessibility problems (it does not replace an audit; see Accessibility Testing). Pass the accessible name whenever several elements share a role.

test('getByRole with name, level and exact', async ({ page }) => {
  await expect(page.getByRole('heading', { name: 'Catalogue', level: 1 })).toBeVisible();
  // The name is a case-insensitive substring unless exact is set. The link's name
  // comes from its content: the cover image alt text and the heading.
  await expect(page.getByRole('link', { name: 'quiet compiler' })).toHaveCount(1);
  await expect(page.getByRole('link', { name: 'The Quiet Compiler', exact: true })).toHaveCount(0);
  await expect(page.getByRole('searchbox', { name: 'Search books' })).toBeVisible();
  await expect(page.getByRole('navigation', { name: 'Pagination' })).toBeVisible();
  // Regular expressions work for the name too.
  await expect(page.getByRole('heading', { name: /^Small Systems/, level: 3 })).toHaveCount(1);
});

Two details in that test are worth remembering. The accessible name of a link is built from its content, so the Bookshelf link that wraps a cover image and a heading is found by the substring quiet compiler (the test expects exactly one such link on the catalogue page). And the sign-in error paragraph is role="alert" but carries the hidden attribute until a failure happens, so it only matches with includeHidden: true.

getByText, getByLabel, getByAltText, getByTestId

getByText() matches by the text content: a string is a case-insensitive substring match, exact: true makes it case-sensitive and whole-string, and a RegExp matches as written. Whitespace is always normalised (runs collapse to one space, line breaks become spaces, leading and trailing whitespace is ignored), even with exact. Prefer it for non-interactive elements and use roles for buttons and links. getByLabel() finds the control associated with a label (including aria-label and aria-labelledby), and getByAltText() and getByTitle() match the attributes of the same name. All of them accept exact.

test('getByText, getByLabel, getByAltText, getByTestId', async ({ page }) => {
  await expect(page.getByText('24 books found')).toBeVisible();
  await expect(page.getByText(/^\d+ books found$/)).toBeVisible();
  await expect(page.getByText('Mara Velde', { exact: true })).toHaveCount(1);
  await expect(page.getByLabel('Search books')).toBeVisible();
  await expect(page.getByAltText('Cover of Salt and Signal')).toBeVisible();
  await expect(page.getByAltText('Cover of', { exact: false })).toHaveCount(6);
  await expect(page.getByTestId('book-card')).toHaveCount(6);
  await expect(page.getByTestId(/^page-/)).toHaveCount(3);
  // aria-label is an accessible name, so getByLabel finds it as well.
  await expect(page.getByLabel('Toggle theme')).toHaveText('Theme');
});

test('getByPlaceholder, getByTitle and a custom test id attribute on a lab page', async ({ page }) => {
  await page.setContent(`
    <input type="email" placeholder="name@example.com">
    <span title="Issues count">25 issues</span>

  await page.getByPlaceholder('name@example.com').fill('reader@example.com');
  await expect(page.getByPlaceholder('name@example.com')).toHaveValue('reader@example.com');
  await expect(page.getByTitle('Issues count')).toHaveText('25 issues');

  const { selectors } = await import('@playwright/test');
  selectors.setTestIdAttribute('data-pw');

  } finally {
    selectors.setTestIdAttribute('data-testid');
  }
});

Test ids and testIdAttribute

getByTestId() is the most stable locator because a test id survives changes to text, structure and role. The price is that it is not user-facing: a button with the right test id passes even when its label is wrong, so use it when role, label and text are not enough. By default it matches data-testid. If your application uses another attribute, set testIdAttribute in the configuration so the whole suite follows:

// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  use: {
    testIdAttribute: 'data-pw',
  },
});

Source: Playwright: Set a custom test id attribute

The Bookshelf configuration states testIdAttribute: 'data-testid' explicitly, as in the project layout page. The attribute can also be changed in code with selectors.setTestIdAttribute(), which the test above does for the duration of one check. A RegExp is accepted by getByTestId() as well (getByTestId(/^page-/) in the earlier example matched the three pager elements). The older selector shorthands id=, data-testid=, data-test-id= and data-test= still work in page.locator(), but getByTestId() is preferred.

Filtering locators

locator.filter() narrows an existing locator. Its options combine, and several filter() calls can be chained.

Option Keeps the elements that…​ Added in

hasText

contain the text (string: case-insensitive substring; RegExp as written) somewhere inside, including descendants.

Original API

hasNotText

do not contain the text.

1.33

has

contain an element matching the inner locator.

Original API

hasNot

do not contain an element matching the inner locator.

1.33

visible

are visible (true) or invisible (false).

1.51

The inner locator of has and hasNot is relative: it is queried starting from each element matched by the outer locator, not from the document root, and it must live in the same frame (it cannot contain a FrameLocator). A filter such as has: page.getByRole('list').getByText('Product 2') therefore never matches when the outer locator is a list item, because the list is outside the item.

test('filter by text, hasNotText, has and hasNot', async ({ page }) => {
  const cards = page.getByTestId('book-card');
  const fiction = cards.filter({ hasText: 'Fiction' });
  await expect(fiction).toHaveCount(2);
  await expect(cards.filter({ hasNotText: 'Fiction' })).toHaveCount(4);
  await expect(cards.filter({ hasText: /\$9\.99/ })).toHaveCount(2);

  const withTechnologyTitle = cards.filter({
    has: page.getByRole('heading', { name: 'The Quiet Compiler' }),
  });
  await expect(withTechnologyTitle).toHaveCount(1);
  await expect(cards.filter({ hasNot: page.getByRole('heading', { name: 'The Quiet Compiler' }) })).toHaveCount(5);

  // Chained filters narrow the match step by step.
  const card = cards
    .filter({ hasText: 'Fiction' })
    .filter({ has: page.getByRole('link', { name: 'Salt and Signal' }) });
  await expect(card.getByTestId('book-author')).toHaveText('Ines Okafor');
});

Chaining, and, or, visible and within

Chaining (page.getByTestId('book-card').getByRole('link')) searches inside each match of the previous locator and is the everyday way to scope a query to a card, a row or a form.

  • locator.and(other) keeps the elements that match both locators: getByRole('button').and(getByTitle('Subscribe')).

  • locator.or(other) matches either alternative, or both. Use it to wait for one of two outcomes (a button or a security dialog). When both are present the combined locator resolves to two elements, so add .first() before acting on it, or the strictness rule throws.

  • locator.visible() (new in 1.63) matches only visible elements. It replaces the :visible CSS pseudo-class and the filter({ visible: true }) form for the common case; use filter({ visible: false }) to select the invisible ones. Visibility is evaluated each time the locator is used, not when visible() is called.

  • locator.within(parent) (new in 1.64) reads in the natural order, "this button, within that dialog": saveButton.within(dialog). Relative methods such as nth() and first() are resolved separately inside each parent, so getByRole('cell').nth(2).within(getByRole('row')) is the third cell of every row, which is how a table column is addressed.

test('and, or, visible and within', async ({ page }) => {
  // and: both conditions must hold for the same element.
  const searchButton = page.getByRole('button').and(page.getByTestId('search-submit'));
  await expect(searchButton).toHaveText('Search');

  // or: either alternative; both may match, so strict mode needs first() when both are present.
  const next = page.getByTestId('page-next');
  const prev = page.getByTestId('page-prev');
  await expect(next.or(prev)).toHaveCount(2);
  await expect(next.or(prev).first()).toBeVisible();

  // visible: the signed-out page has an error paragraph that is hidden, then shown after a failed sign-in.
  await page.goto('/signin');
  const errors = page.getByTestId('signin-error');
  await expect(errors.visible()).toHaveCount(0);
  await page.getByLabel('Username').fill('reader');
  await page.getByLabel('Password').fill('wrong-password');
  await page.getByRole('button', { name: 'Sign in' }).click();
  await expect(errors.visible()).toHaveText('Invalid username or password');
  await expect(page.getByTestId('signin-error').filter({ visible: true })).toHaveCount(1);

  // within (1.64): "this author paragraph, within that card".
  await page.goto('/books');
  const secondCard = page.getByTestId('book-card').nth(1);
  const authorInSecondCard = page.getByTestId('book-author').within(secondCard);
  await expect(authorInSecondCard).toHaveText('Ilan Brooks');
  // Relative locators resolve inside each parent: the first author of every card.
  const firstParagraphOfEveryCard = page.locator('p').first().within(page.getByTestId('book-card'));
  await expect(firstParagraphOfEveryCard).toHaveCount(6);
});

CSS, XPath and the legacy selector engines

page.locator(selector) accepts a selector string. Playwright detects CSS and XPath automatically: a string starting with // or .. is XPath, anything else is CSS, and the prefixes css= and xpath= make the choice explicit. Both are tied to the DOM structure, so long chains such as #tsf > div:nth-child(2) > div.A8SBwf > ... break whenever the markup changes. Use them for what has no user-facing handle.

Playwright augments CSS in two ways. CSS selectors pierce open shadow roots, and a set of custom pseudo-classes is available:

Pseudo-class or engine Meaning

:has-text("x")

The element contains the text somewhere inside (case-insensitive, trimmed substring). Combine it with a tag or class, otherwise it also matches <body>.

:text("x")

The smallest element containing the text (case-insensitive substring).

:text-is("x")

The smallest element with exactly that text (case-sensitive, whole string after trimming).

:text-matches("re", "i")

The smallest element whose text matches the regular expression. Backslashes need doubling inside a CSS string, and doubling again inside a JavaScript string.

:has(selector), :is(a, b)

Standard relational and list pseudo-classes. A comma-separated list also matches any alternative.

:visible

Only visible elements. Prefer locator.visible().

:nth-match(selector, n)

The n-th match (one-based) of the selector across the whole page, not among siblings. Also useful with waitFor() to wait for a number of elements.

:right-of(), :left-of(), :above(), :below(), :near()

Layout selectors based on the bounding box, with an optional maximum distance. Deprecated and not recommended; matches can change with a one-pixel layout shift.

nth=0, nth=-1

Zero-based index selector, used as locator('button').locator('nth=-1').

xpath=...

XPath, equivalent to Document.evaluate. Pipe unions (a|b) work. XPath does not pierce shadow roots.

text=Log in, text="Log in", text=/Log\s*in/i

Legacy text engine. Use getByText() instead.

id=, data-testid=, data-test-id=, data-test=

Legacy attribute shorthands. Use getByTestId() instead.

selector1 >> selector2

Legacy chaining. Use chained locators instead. A leading * on a part (*css=article >> text=Hello) captures that intermediate element, for which filter({ has }) is the replacement.

 
test('CSS, XPath and legacy selector engines', async ({ page }) => {
  await page.goto('/books');
  await expect(page.locator('css=li.card')).toHaveCount(6);
  await expect(page.locator('li.card')).toHaveCount(6);
  await expect(page.locator('//li[@data-book-id="2"]')).toHaveCount(1);
  await expect(page.locator('xpath=//li[@data-book-id="2"]//h3')).toHaveText('Rivers of Static');
  await expect(page.locator('li.card:has-text("Fiction")')).toHaveCount(2);
  await expect(page.locator('li.card:has(a[href="/books/5"])')).toHaveCount(1);
  await expect(page.locator(':nth-match(li.card, 3)')).toHaveAttribute('data-book-id', '3');
  await expect(page.locator('li.card').locator('nth=-1')).toHaveAttribute('data-book-id', '6');
  await expect(page.locator('li.card >> text=Salt and Signal')).toHaveCount(1);
  await expect(page.locator('data-testid=search-input')).toHaveCount(1);
  await expect(page.locator('id=q')).toHaveCount(1);
  // Parent of a child: prefer filter({ has }), fall back to xpath=..
  const parentByFilter = page.getByTestId('book-card').filter({ has: page.getByText('Rivers of Static') });
  const parentByXpath = page.getByText('Rivers of Static').locator('xpath=../..');
  await expect(parentByFilter).toHaveAttribute('data-book-id', '2');
  await expect(parentByXpath).toHaveAttribute('data-book-id', '2');
});

test('Playwright CSS extensions: text pseudo-classes, :visible and layout selectors', async ({ page }) => {
  await page.goto('/signin');

Two retargeting rules from the same guide are worth knowing. To reach the parent of an element, filter({ has }) is better than xpath=.., as the parent test above shows. And an action aimed at a label is retargeted to its control: click(), fill(), inputValue(), selectText(), setInputFiles() and selectOption() on the label’s text act on the associated input, while an assertion such as toHaveText() still reads the label itself.

Shadow DOM

All locators pierce open shadow roots by default, so a locator for text inside a web component is written as if the shadow root were not there. Two exceptions: XPath does not pierce shadow roots, and closed-mode shadow roots are not supported.

test('shadow DOM is pierced by default', async ({ page }) => {
  await page.setContent(`
    <x-details>
      <div>Title</div>
    </x-details>
    <script>
      const host = document.querySelector('x-details');
      const root = host.attachShadow({ mode: 'open' });
      root.innerHTML = '<div id="inner-details"><button data-testid="inner-button">Details</button></div>';
    </script>
  `);
  await expect(page.getByText('Details')).toBeVisible();
  await expect(page.getByRole('button', { name: 'Details' })).toHaveCount(1);
  await expect(page.getByTestId('inner-button')).toBeVisible();
  await expect(page.locator('#inner-details')).toHaveCount(1);
  await expect(page.locator('x-details', { hasText: 'Details' })).toHaveCount(1);
  // XPath does not pierce shadow roots.
  await expect(page.locator('//div[@id="inner-details"]')).toHaveCount(0);
});

Source: Playwright: Locate in Shadow DOM

Playwright 1.64 added an includeShadow option to page.content() so the serialised HTML contains the shadow content too (see What changed recently).

Aria refs: page.getByRef()

A page snapshot in the ai mode annotates every node with a short reference such as [ref=e12], and Playwright 1.64’s page.getByRef('e12') resolves that reference back to a locator. This is the mechanism behind tools that let a language model read a page snapshot and then act on one element of it (see Playwright MCP & CLI). The ai mode also includes the content of iframes. Forcing, trial runs and dispatching events

  • force: true skips the non-essential checks (visibility is still needed to compute the click point; "receives events" is skipped). In the overlay test above the forced click is dispatched at the point where the overlay is the hit target, so the button’s own handler does not run: force can hide a real bug where the element is covered.

  • trial: true performs the checks and skips the action, which is a way to wait until an element is ready without touching it. Modifier keys are still pressed.

  • locator.dispatchEvent('click') fires the DOM event on the element itself with no checks at all. It tests the handler, not the user experience.

Overlays that appear at unpredictable times

Timeouts

In the test runner the action timeout is 0 (no limit) unless actionTimeout is set in use, so an action is bound by the test timeout (30 s by default); each web-first assertion is bound by the expect timeout (5 s by default). Individual calls accept timeout, and since 1.62 most calls and assertions accept signal (an AbortSignal) to cancel them. Action What it does and its main options

fill(value)

Same as fill('').

dblclick(), tap()

Same checks and similar options. tap() needs a context with hasTouch: true.

hover()

Moves the pointer over the element, for menus and tooltips.

For input[type=checkbox], input[type=radio] and [role=checkbox]. They verify the final state and throw if the click did not produce it.

Focus and blur the element, for pages that react to focus.

Frames

A page has a main frame and optionally child frames from <iframe> elements. Locators on the page do not look inside iframes, so go through page.frameLocator(selector), which returns a FrameLocator that offers the same getBy* methods. A frame locator is as lazy as a locator: it waits for the iframe to exist and load when you act. Its counterpart locator.contentFrame() turns a locator for an <iframe> into a FrameLocator, and frameLocator.owner() goes the other way. Use the Frame object (page.frame({ name }), page.frame({ url }), page.frames(), frame.parentFrame()) when you need frame-level APIs such as frame.waitForLoadState(). Dialogs

alert(), confirm(), prompt() and beforeunload dialogs block the page until handled. By default Playwright dismisses them automatically (a confirm() returns false). To control them, register a dialog listener before the action that triggers the dialog and make it accept or dismiss: a listener that only logs the message leaves the dialog open and the triggering action hangs. Useful members of the Dialog object are type(), message(), defaultValue(), accept(promptText) and dismiss(). Use page.once() for one-off handling.

test('dialogs: accept, dismiss, prompt and the default behaviour', async ({ page }) => {
  await serveLab(page, {
    'dialogs.html': `
      <button onclick="document.getElementById('out').textContent = 'alert closed'; alert('Saved!')">Alert</button>
      <button onclick="document.getElementById('out').textContent = String(confirm('Delete this review?'))">Confirm</button>
      <button onclick="document.getElementById('out').textContent = String(prompt('Your name?', 'anonymous'))">Prompt</button>
      <p id="out"></p>`,
  });
  await page.goto('/lab/dialogs.html');

  // No listener: dialogs are dismissed automatically, so confirm() returns false.
  await page.getByRole('button', { name: 'Confirm' }).click();
  await expect(page.locator('#out')).toHaveText('false');

  // Accept a confirm and inspect it. once() removes the listener after the first dialog.
  const messages: string[] = [];
  page.once('dialog', async (dialog) => {
    messages.push(`${dialog.type()}: ${dialog.message()}`);
    await dialog.accept();
  });
  await page.getByRole('button', { name: 'Confirm' }).click();
  await expect(page.locator('#out')).toHaveText('true');
  expect(messages).toEqual(['confirm: Delete this review?']);

  // A prompt takes the answer as the argument of accept(); defaultValue() is the pre-filled text.
  page.once('dialog', (dialog) => {
    expect(dialog.defaultValue()).toBe('anonymous');
    return dialog.accept('Reader');
  });
  await page.getByRole('button', { name: 'Prompt' }).click();
  await expect(page.locator('#out')).toHaveText('Reader');

  // A permanent listener that dismisses everything; the alert is simply closed.
  const handler = (dialog: import('@playwright/test').Dialog) => dialog.dismiss();
  page.on('dialog', handler);
  await page.getByRole('button', { name: 'Alert' }).click();
  await expect(page.locator('#out')).toHaveText('alert closed');
  page.off('dialog', handler);
});

Downloads

Every attachment downloaded by the page emits a download event. Files are kept in a temporary folder and deleted when the browser context that produced them closes, so save the ones you need with download.saveAs(path). As with dialogs and popups, start waiting for the event before the click that causes it and await the promise afterwards.

Download member Meaning

suggestedFilename()

Filename the browser would propose (from Content-Disposition or the download attribute).

url()

URL of the download.

saveAs(path)

Copies the file once the download finished.

path()

Path of the file in the temporary folder (waits until it finishes).

createReadStream()

Readable stream with the content.

failure()

null on success, otherwise the error string.

cancel(), delete()

Cancel a running download; remove the temporary file.

 
test('downloads: waitForEvent, saveAs and the Download object', async ({ page }, testInfo) => {
  await serveLab(page, {
    // The page builds a file in memory and offers it through a link with the download attribute.
    'download.html': `<a id="dl" download="books.csv">Download file</a>
      <script>
        const blob = new Blob(['id,title\\n1,The Quiet Compiler\\n'], { type: 'text/csv' });
        document.getElementById('dl').href = URL.createObjectURL(blob);
      </script>`,
  });
  await page.goto('/lab/download.html');

  // Start waiting before the click that triggers the download. Note: no await on the promise.
  const downloadPromise = page.waitForEvent('download');
  await page.getByText('Download file').click();
  const download = await downloadPromise;

  expect(download.suggestedFilename()).toBe('books.csv');
  expect(download.url()).toMatch(/^blob:/);
  expect(await download.failure()).toBeNull();
  const target = testInfo.outputPath('books.csv');
  await download.saveAs(target);
  expect(readFileSync(target, 'utf8')).toBe('id,title\n1,The Quiet Compiler\n');
});

Pages, tabs and popups

A BrowserContext holds any number of Page objects (tabs and popup windows). They share cookies, storage and context-level settings such as routes, viewport and locale, and each behaves as the active page, so there is no need to bring a page to the front. context.pages() lists them, and context.newPage() creates one. To catch a page that a click opens, wait for the page event of the context (all new pages, including target="_blank" links) or for the popup event of the opener page (popups opened by that page, in addition to the context event). In both cases register the wait before the click. popup.opener() returns the opener.

test('popups and new tabs: waitForEvent popup, context page event', async ({ page, context }) => {
  // Routes registered on the context apply to every page it opens, popups included.
  await serveLab(context, {
    'opener.html': `<a href="/lab/child.html" target="_blank">open new tab</a>
                     <button onclick="window.open('/lab/child.html', 'child', 'popup,width=400,height=300')">open the popup</button>`,
    'child.html': `<title>Child page</title><button>Close me</button>`,
  });
  await page.goto('/lab/opener.html');

  // A link with target=_blank is a new page in the context, and a popup of the opener.
  const pagePromise = context.waitForEvent('page');
  await page.getByText('open new tab').click();
  const newPage = await pagePromise;
  await newPage.waitForLoadState();
  await expect(newPage).toHaveTitle('Child page');
  expect(context.pages()).toHaveLength(2);
  await newPage.close();

  // window.open: the popup event is specific to the opener page.
  const popupPromise = page.waitForEvent('popup');
  await page.getByText('open the popup').click();
  const popup = await popupPromise;
  await expect(popup.getByRole('button', { name: 'Close me' })).toBeVisible();
  await expect(popup).toHaveTitle('Child page');
  expect(await popup.opener()).toBe(page);
});

If the action that opens the page is unknown, use context.on('page', ...) or page.on('popup', ...) as a listener and call await page.waitForLoadState() before using the page. Events

Playwright emits events for requests, responses, console messages, dialogs, downloads, file choosers, new pages, workers and more. There are two patterns. Waiting (page.waitForEvent(), page.waitForRequest(), page.waitForResponse(), page.waitForURL(), page.waitForLoadState()) blocks until the event happens and returns it, and listening (page.on(), page.once(), page.off()) handles events that arrive at unknown times. The rule for waiting is always the same: create the promise first, trigger the action, then await the promise. Awaiting after the action can miss an event that already happened. Handling events with a listener forks the control flow, so the test can end before the handler finishes; prefer waiting when the order matters.

test('events: waitForEvent, on, once, off, waitForRequest and waitForResponse', async ({ page }) => {
  const requests: string[] = [];
  const onRequest = (request: import('@playwright/test').Request) => requests.push(request.url());
  page.on('request', onRequest);

  const coverRequest = page.waitForRequest('**/covers/1.svg');
  await page.goto('/books');
  expect((await coverRequest).url()).toMatch(/\/covers\/1\.svg$/);
  page.off('request', onRequest);
  const seen = requests.length;
  expect(seen).toBeGreaterThan(2);

  const responsePromise = page.waitForResponse((r) => r.url().includes('/api/books') && r.status() === 200);
  await page.evaluate(() => fetch('/api/books?q=quiet'));
  const response = await responsePromise;
  expect((await response.json()).total).toBe(1);

  // After off() the listener no longer collects anything.
  await page.goto('/books?page=2');
  expect(requests).toHaveLength(seen);

  // Console messages are an event too.
  const consolePromise = page.waitForEvent('console', (m) => m.text() === 'hello from the page');
  await page.evaluate(() => console.log('hello from the page'));
  expect((await consolePromise).type()).toBe('log');
});

Evaluating JavaScript and handles

page.evaluate(fn, arg) runs a function in the page and returns the result (serialised, with promises awaited). The test runs in Node.js and the function runs in the browser, in different processes, so variables are not shared: pass them as the single optional argument, which can be a serialisable value or a mix of values and handles. Browser globals (window, document) are available inside the function. locator.evaluate(fn, arg) receives the resolved element as the first parameter, locator.evaluateAll(fn) receives an array of all matches, and frame.evaluate() runs in a frame. page.addInitScript() (and context.addInitScript()) run a script before any page script on every navigation, which is the place to install mocks such as a fixed Math.random.

A handle is a reference, living in the Node.js process, to an object that lives in the browser. JSHandle references any JavaScript object and is created with page.evaluateHandle(); ElementHandle (a subclass) references a DOM element. Handles can be passed back into evaluate() and are released with dispose() (they also stay alive until the page navigates). Playwright discourages ElementHandle because it points at one particular element: if the page re-renders, the handle refers to a stale node, unlike a locator. Use it only for extensive DOM traversal on a static page, and create it with page.waitForSelector() so it waits for the element.

test('evaluate, evaluateHandle and handles', async ({ page }) => {
  await page.goto('/books');

  // Return values are serialised; browser globals are available inside the function.
  expect(await page.evaluate(() => document.location.pathname)).toBe('/books');
  const status = await page.evaluate(async () => (await fetch('/api/books')).status);
  expect(status).toBe(200);

  // Variables from the test must be passed as the argument.
  const data = { q: 'signal' };
  const total = await page.evaluate(async (args) => (await (await fetch('/api/books?q=' + args.q)).json()).total, data);
  expect(total).toBe(1);
  await expect(page.evaluate(() => (data as any).q)).rejects.toThrow(/ReferenceError/);

  // A locator evaluates against the element it resolves to.
  const cardIds = await page.getByTestId('book-card').evaluateAll((cards) => cards.map((c) => (c as HTMLElement).dataset.bookId));
  expect(cardIds).toEqual(['1', '2', '3', '4', '5', '6']);
  expect(await page.getByTestId('book-title').first().evaluate((el, suffix) => el.textContent + suffix, '!')).toBe('The Quiet Compiler!');

  // JSHandle: a reference to an object that stays in the page.
  const myArrayHandle = await page.evaluateHandle(() => {
    (window as any).myArray = [1];
    return (window as any).myArray as number[];
  });
  expect(await page.evaluate((a) => a.length, myArrayHandle)).toBe(1);
  await page.evaluate((arg) => arg.myArray.push(arg.newElement), { myArray: myArrayHandle, newElement: 2 });
  expect(await myArrayHandle.jsonValue()).toEqual([1, 2]);
  expect(await myArrayHandle.evaluate((a) => a.length)).toBe(2);
  await myArrayHandle.dispose();

  // ElementHandle: discouraged, and it points at one specific element.
  const handle = await page.waitForSelector('[data-testid=search-submit]');
  expect(await handle.getAttribute('type')).toBe('submit');
  expect((await handle.boundingBox())!.width).toBeGreaterThan(20);
  await handle.dispose();

  // Init scripts run before any page script, on every navigation.
  await page.addInitScript((value) => {
    Math.random = () => value;
  }, 0.42);
  await page.reload();
  expect(await page.evaluate(() => Math.random())).toBe(0.42);
});

Navigations

page.goto(url, options) opens a URL and, by default, waits for the load event. waitUntil chooses the milestone: 'load' (default), 'domcontentloaded', 'networkidle' (discouraged) or 'commit' (response headers received and navigation committed). goto() returns the main-resource Response (or null), and an HTTP error status such as 404 is a normal response, not an exception; only network-level failures throw. Relative URLs are resolved against baseURL.

After an action that navigates, such as clicking a link or submitting a form, use page.waitForURL(urlOrPattern) when the click can trigger several navigations (redirects, then a client-side route) and you want the final one. Assertions such as await expect(page).toHaveURL(...) retry too. page.goBack() and page.goForward() walk the history, and page.reload() reloads. The lifecycle of a navigation is: it starts when the URL changes or a link is clicked, it commits when the response headers are parsed (page.url() updates), then the document is parsed (domcontentloaded) and its resources load (load).

test('navigations: goto, waitUntil, waitForURL, back and forward', async ({ page }) => {
  const response = await page.goto('/books', { waitUntil: 'domcontentloaded' });
  expect(response!.status()).toBe(200);

  // Clicking a link starts a navigation; waitForURL waits for the final URL.
  await page.getByRole('link', { name: 'Next' }).click();
  await page.waitForURL('**/books?page=2');
  await expect(page.getByTestId('page-indicator')).toHaveText('Page 2 of 4');

  // Several navigations after one click: sign in goes to /account.
  await page.goto('/signin?next=/account');
  await page.getByLabel('Username').fill('reader');
  await page.getByLabel('Password').fill(process.env.BOOKSHELF_READER_PASSWORD ?? 'reader-local-only');
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.waitForURL(/\/account$/);

  // History navigation.
  await page.goto('/books');
  await page.getByRole('link', { name: 'Next' }).click();
  await page.waitForURL('**/books?page=2');
  await page.goBack();
  await expect(page).toHaveURL(/\/books$/);
  await page.goForward();
  await expect(page).toHaveURL(/page=2$/);

  // A 404 is a response, not an exception.
  const missing = await page.goto('/books/9999');
  expect(missing!.status()).toBe(404);

  // Lifecycle: load fires after domcontentloaded.
  const order: string[] = [];
  page.on('domcontentloaded', () => order.push('domcontentloaded'));
  page.on('load', () => order.push('load'));
  await page.goto('/books');
  await page.waitForLoadState('load');
  expect(order).toEqual(['domcontentloaded', 'load']);
});

Two behaviours from the navigation guide matter in practice:

  • Hydration. Playwright acts the moment it sees an element. On a server-rendered page whose scripts are not attached yet a click can be ignored or typed text can be wiped by the later hydration. Fix the application (enable the control only once it is interactive) rather than adding sleeps; you can reproduce the problem by emulating Slow 3G in DevTools and reloading.

  • Back/forward cache. Playwright disables the BFCache in all browsers. Even if you enable it, restoring a page from the BFCache with goBack() is not supported: no lifecycle events fire, so the Page object loses synchronisation and later interactions time out.

Headless, headed, local and CI

Locators and actions behave the same in headless and headed runs and in every browser; the differences come from timing and rendering. Headless is the default for npx playwright test; add --headed to watch a run, or --ui and the trace viewer to inspect each action (see Debugging, Tracing & Codegen). Slow CI machines make animations, network and rendering slower, which is where missing waits show: because every action waits on its own checks, a test that passes locally and fails in CI usually has an assertion on something that never becomes true there, not a missing sleep. Dialogs, downloads and popups are all handled by listeners, so they work identically headless. Keep the action and expect timeouts generous on CI instead of adding fixed waits, and read Running in CI/CD for retries and traces. Features that need a display, such as the print dialog UI, are not available headless, which is why the print example replaces window.print.

Common pitfalls

  • Not waiting for the promise before the click. waitForEvent('download'), 'popup', 'filechooser' and waitForResponse() must be created before the action and awaited after it.

  • A dialog listener that does not call accept() or dismiss(). The page stays blocked and the action hangs.

  • Using waitForTimeout() to let the page settle. Wait for an element, URL or response instead.

  • Reading a value once and asserting on it. expect(await locator.textContent()).toBe(...) does not retry; use await expect(locator).toHaveText(...).

  • Forgetting await. A locator method without await returns a promise; the test continues while the action runs.

  • Locator or assertion over several elements. Fix the locator before reaching for first().

  • Text locators that match too much. getByText('Sign in') matches a heading and a button; use getByRole() for interactive elements, or exact.

  • Backslashes in CSS text pseudo-classes. :text-matches("sign\\s*in") needs the backslash doubled for CSS and doubled again in a JavaScript string, as the lab test shows.

  • Sharing server state between workers. Bookshelf’s reset endpoint clears every session, so the examples run with one worker; a real suite isolates state per test instead (see Parallelism, Sharding & Retries).

// lab.ts
import type { BrowserContext, Page } from '@playwright/test';

/** Serves small HTML documents under /lab/<name> of the Bookshelf origin, without touching the server. */
export async function serveLab(target: Page | BrowserContext, pages: Record<string, string | { body: string; headers?: Record<string, string>; contentType?: string }>) {
  await target.route('**/lab/**', async (route) => {
    const name = new URL(route.request().url()).pathname.replace('/lab/', '');
    const entry = pages[name];
    if (entry === undefined) return route.fulfill({ status: 404, body: 'not in the lab' });
    const { body, headers, contentType } = typeof entry === 'string' ? { body: entry, headers: undefined, contentType: undefined } : entry;
    await route.fulfill({ status: 200, contentType: contentType ?? 'text/html', headers, body });
  });
}
