Playwright Configuration, Fixtures & Projects

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Almost everything that makes a Playwright Test suite behave the way it does is decided in three places: the configuration file, which says how and where tests run; fixtures, which give each test the environment it needs; and projects, which run the same tests in several configurations. This page covers all three, plus the supporting machinery around them: timeouts, the webServer option that starts the application, global setup and teardown, annotations, tags and locks, parameterized tests and TypeScript. It describes Playwright 1.64.1 for Node.js (the Python, Java and .NET bindings were exercised at 1.63; see Playwright for Python, Java & .NET) and was checked on 25 October 2026. Every example below was run against the Bookshelf application with Chromium, the mobile emulation of a Pixel 7 and, where stated, WebKit. The complete test project used for this page has 71 tests in its main configuration (66 pass, five are skipped on purpose; the WebKit project adds 28 more) plus four small configurations for the webServer, global setup, timeout and parallel-run examples.

The page assumes you can already write and run a test (see Getting Started) and use locators and assertions (Locators, Actions & Auto-Waiting and Assertions).

The configuration file

Playwright Test looks for playwright.config.ts (or .js, .mjs, .cts, .mts) in the directory you run the command from; npx playwright test --config path/to/config.ts (short form -c) chooses another one. The file default-exports the result of defineConfig(), which only adds type checking and completion. Relative paths such as testDir: './tests' are resolved against the config file’s own directory.

There are two kinds of options, and mixing them up is the commonest configuration mistake:

  • Test runner options are top-level properties of the config: testDir, timeout, retries, workers, reporter, projects, webServer, globalSetup and so on. They describe how the runner schedules and reports tests.

  • Browser and context options live in the use section: baseURL, locale, trace, viewport and so on. They configure the browser, the browser context and the page that every test receives. They can be overridden per project, per file and per test, which the runner options (mostly) cannot.

The configuration used for the examples on this page reads the base URL from BASE_URL, like every other test project in this section, and declares two timeouts, a set of use options, a setup project with a teardown project, and several projects. Each part is explained in the sections that follow.

import { defineConfig, devices } from '@playwright/test';
import type { BookshelfOptions } from './fixtures';

export default defineConfig<BookshelfOptions>({
  testDir: './tests',
  outputDir: './test-results',

  // Runner options are top-level.
  fullyParallel: true,
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 2 : 0,
  workers: process.env.CI ? 2 : undefined,
  reporter: [['list']],

  // Timeouts.
  timeout: 20_000,
  expect: { timeout: 5_000 },
  globalTimeout: 10 * 60_000,

  // Browser, context and recording options.
  use: {
    baseURL: process.env.BASE_URL ?? 'http://localhost:3914',
    testIdAttribute: 'data-testid',
    actionTimeout: 5_000,
    navigationTimeout: 10_000,
    locale: 'en-GB',
    timezoneId: 'Europe/Madrid',
    colorScheme: 'light',
    extraHTTPHeaders: { 'X-Test-Run': 'docs' },
    ignoreHTTPSErrors: true,
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: 'off',
    launchOptions: { slowMo: 0 },
  },

  projects: [
    // Setup project, with a teardown project that runs after every dependent project.
    { name: 'setup', testMatch: /global\.setup\.ts/, teardown: 'cleanup' },
    { name: 'cleanup', testMatch: /global\.teardown\.ts/ },

    {
      name: 'desktop',
      use: { ...devices['Desktop Chrome'] },
      dependencies: ['setup'],
      testIgnore: /(parameterized|locks)\.spec\.ts/,
    },
    {
      name: 'mobile',
      use: { ...devices['Pixel 7'] },
      dependencies: ['setup'],
      testIgnore: /(parameterized|locks)\.spec\.ts/,
    },
    // Tests that replace the shared data run last and serialise themselves with a lock.
    {
      name: 'shared-data',
      use: { ...devices['Desktop Chrome'] },
      dependencies: ['desktop', 'mobile'],
      testMatch: /locks\.spec\.ts/,
    },
    // Parameterized projects: the same specs with different option fixture values.
    {
      name: 'fiction-shelf',
      use: { ...devices['Desktop Chrome'], searchTerm: 'Fiction' },
      dependencies: ['setup'],
      testMatch: /parameterized\.spec\.ts/,
    },
    {
      name: 'nature-shelf',
      use: { ...devices['Desktop Chrome'], searchTerm: 'Nature' },
      dependencies: ['setup'],
      testMatch: /parameterized\.spec\.ts/,
    },
    // Configured but not run by a plain "npx playwright test" (1.64).
    {
      name: 'webkit',
      use: { ...devices['Desktop Safari'] },
      dependencies: ['setup'],
      testIgnore: /(parameterized|locks)\.spec\.ts/,
      default: false,
    },
  ],
});

Test runner options

Option Effect

testDir

Directory searched for test files. Relative to the config file.

testMatch, testIgnore

Glob patterns or regular expressions that select or exclude test files. The default testMatch is **/*.@(spec|test).?(c|m)[jt]s?(x), which is why global.setup.ts above is not picked up by a plain project. Both options can also be set per project.

outputDir

Where traces, screenshots, videos and attachments of a run are written. Defaults to test-results. Playwright clears the folder at the start of each run, so do not keep hand-written files in it.

timeout, expect

Per-test timeout and the expect() options, including the assertion timeout. See Timeouts.

globalTimeout

Maximum time for the whole run. When it is reached Playwright stops, and the reporters still write their reports.

fullyParallel

Run every test of every file in parallel. Without it, tests in one file run in order in one worker. See Parallelism, Sharding & Retries.

workers

Maximum number of worker processes, or a percentage of the logical CPU cores such as '50%'.

retries

Number of retries for a failed test. Tests that pass on a retry are reported as flaky.

retryStrategy

When retries run: 'immediate' (default) or 'isolated', which runs all retries at the end in a single worker to minimize interference with the rest of the run (added in 1.62).

forbidOnly

Fail the run if a test.only was committed. Set it to !!process.env.CI so a focused test cannot silently skip the rest of the suite on CI.

reporter

One or more reporters, with options: [['list'], ['html', { open: 'never' }]].

grep, grepInvert

Run only tests whose title (including tags) matches or does not match a regular expression. The same options exist per project.

globalSetup, globalTeardown

Files that run once before and after the whole run. See Global setup and teardown.

projects

The list of projects. See Projects.

webServer

Start one or more servers before the tests. See The webServer option.

tsconfig

A single tsconfig file used when loading tests and reporters. See TypeScript.

Filtering with testMatch and testIgnore is how the example above keeps parameterized.spec.ts and locks.spec.ts away from the browser projects that should not run them. Both options accept an array, and patterns are matched against the absolute path, so '**/smoke/**' and /.*smoke.spec.ts/ both work.

Use options

The use section holds everything a test needs to know about its browser. Playwright creates one browser per worker and one fresh browser context per test; the options below are applied to that context and to the page opened in it, so every test starts from a known, isolated state. The most important ones, grouped as in the official reference:

With retries: 2, a test that fails once and then passes keeps the first run’s trace under retain-on-failure, the first run’s and the retry’s trace under on and retain-on-failure-and-retries, and only the retry’s trace under on-first-retry. Setting options at four levels

The same option can be set globally, per project, per file or describe block with test.use(), and per test through test.use() in a nested block. The closest scope wins. This is the first spec file of the project; each describe block overrides a different option, and the last block shows how to put an option back to the configuration’s value.

import { test, expect } from '../fixtures';

test('config-level use options reach the page', async ({ page, baseURL }) => {
  await page.goto('/');
  expect(baseURL).toBe(process.env.BASE_URL);
  expect(await page.evaluate(() => navigator.language)).toBe('en-GB');
  expect(await page.evaluate(() => Intl.DateTimeFormat().resolvedOptions().timeZone)).toBe('Europe/Madrid');
  expect(await page.evaluate(() => matchMedia('(prefers-color-scheme: dark)').matches)).toBe(false);
});

test('testIdAttribute makes getByTestId read data-testid', async ({ page }) => {
  await page.goto('/');
  await expect(page.getByTestId('site-header')).toBeVisible();
});

test('extraHTTPHeaders are sent with every request', async ({ page }) => {
  const [request] = await Promise.all([
    page.waitForRequest('**/books'),
    page.goto('/books'),
  ]);
  expect((await request.allHeaders())['x-test-run']).toBe('docs');
});

test.describe('French locale for one describe block', () => {
  test.use({ locale: 'fr-FR', timezoneId: 'America/Mexico_City' });

  test('locale and time zone are overridden', async ({ page }) => {
    await page.goto('/');
    expect(await page.evaluate(() => navigator.language)).toBe('fr-FR');
    expect(await page.evaluate(() => Intl.DateTimeFormat().resolvedOptions().timeZone)).toBe('America/Mexico_City');
  });
});

test.describe('dark colour scheme', () => {
  test.use({ colorScheme: 'dark' });

  test('Bookshelf follows prefers-color-scheme', async ({ page }) => {
    await page.goto('/');
    expect(await page.evaluate(() => matchMedia('(prefers-color-scheme: dark)').matches)).toBe(true);
    const background = await page.evaluate(() => getComputedStyle(document.body).backgroundColor);
    expect(background).toBe('rgb(17, 24, 39)');
  });
});

test.describe('explicit viewport', () => {
  test.use({ viewport: { width: 800, height: 600 } });

  test('the file-level viewport wins over the project', async ({ page }) => {
    await page.goto('/');
    expect(await page.evaluate(() => [innerWidth, innerHeight])).toEqual([800, 600]);
  });
});

test.describe('reset an option to the config value', () => {
  test.use({ baseURL: 'http://localhost:1/never-used' });

  test.describe('nested', () => {
    test.use({ baseURL: undefined });

    test('baseURL is back to the config value', async ({ page }) => {
      await page.goto('/');
      expect(new URL(page.url()).port).toBe(new URL(process.env.BASE_URL!).port);
    });
  });
});

test('browser fixtures inherit the use options', async ({ browser }) => {
  const context = await browser.newContext();
  const page = await context.newPage();
  await page.goto(process.env.BASE_URL!);
  expect(await page.evaluate(() => navigator.language)).toBe('en-GB');
  await context.close();
});

Three details are easy to miss. First, test.use({ baseURL: undefined }) restores the value from the configuration rather than removing it; to remove the option completely, use the long form baseURL: [async ({}, use) => use(undefined), { scope: 'test' }]. Second, test.use() at the top of a file applies to the whole file, inside test.describe() only to that block, and it cannot be called inside a test. Third, because device descriptors such as devices['Pixel 7'] set viewport, userAgent, isMobile and hasTouch together, spreading a descriptor after your own viewport overrides it; put your overrides last.

The rules that matter most:

  • The test timeout covers the test function, the setup of the fixtures it uses and the beforeEach hooks. A separate timeout of the same value is shared by fixture teardown and afterEach hooks after the test ends. beforeAll and afterAll hooks get their own, which does not share time with any test.

  • The expect timeout is unrelated to the test timeout: a failing expect(locator).toHaveText() polls for 5 s and then fails, even if the test has 25 s left. Do not raise it globally to hide a slow application; raise it on the one assertion that needs it.

  • Action and navigation timeouts default to no limit, so a stuck action is stopped only by the test timeout. Setting actionTimeout to a few seconds produces an error that names the action, rather than a bare "test timeout exceeded".

  • test.slow() triples the test timeout and is also an annotation (see Annotations and tags); it can be conditional, test.slow(browserName === 'webkit', 'WebKit is slower on CI').

  • A slow fixture, typically a worker-scoped one that boots a service, should get its own timeout so the per-test limit can stay small.

import { test, expect } from '../fixtures';

test('test.slow() triples the timeout', async ({ page }) => {
  test.slow();
  expect(test.info().timeout).toBe(60_000);
  await page.goto('/');
});

test('test.setTimeout() sets an explicit timeout', async ({ page }) => {
  test.setTimeout(45_000);
  expect(test.info().timeout).toBe(45_000);
  await page.goto('/');
});

test('an assertion can have its own timeout', async ({ page }) => {
  await page.goto('/books');
  const assertion = expect(page.getByTestId('empty-state')).toBeVisible({ timeout: 500 });
  await expect(assertion).rejects.toThrow(/Timeout: 500ms/);
});

test('actionTimeout from the config limits a single action', async ({ page }) => {
  await page.goto('/');
  await expect(page.getByRole('button', { name: 'Does not exist' }).click()).rejects.toThrow(/Timeout 5000ms exceeded/);
});

test('a per-call timeout overrides actionTimeout', async ({ page }) => {
  await page.goto('/');
  await expect(page.getByRole('button', { name: 'Does not exist' }).click({ timeout: 700 })).rejects.toThrow(/Timeout 700ms exceeded/);
});

The webServer option

Most browser tests need the application to be running. The webServer option starts it before the first test and stops it after the last, so npx playwright test works on a clean checkout and in CI without a separate script. Playwright starts the process, waits until the application is ready, runs the tests and then terminates the process.

Property Meaning

command

Shell command that starts the server, for example node server.js or npm run start.

cwd

Working directory of the process. Defaults to the directory of the config file.

env

Environment variables for the command. Defaults to process.env plus PLAYWRIGHT_TEST=1.

url

URL that must answer with a 2xx, 3xx, 400, 401, 402 or 403 status before tests start; redirects are followed. Use either url or port.

port

Deprecated in favor of url. Waits for the port to accept connections and passes it as the baseURL.

wait

Regular expressions to look for in stdout or stderr before the server counts as started. Named capture groups become upper-case environment variables, so (?<bookshelf_port>\d+) becomes BOOKSHELF_PORT. If both url and wait are given, the server is ready when either condition is met.

timeout

How long to wait for start-up, in milliseconds. Default 60 000.

reuseExistingServer

true uses a server that already answers on the url or port; false fails if something is already there. The common setting is !process.env.CI: reuse your own dev server locally, always start a fresh one on CI.

stdout, stderr

'pipe' shows the server’s output in the test output (default for stderr), 'ignore' hides it (default for stdout).

name

Prefix of the server’s log lines. Defaults to [WebServer].

gracefulShutdown

By default the process group is killed with SIGKILL. { signal: 'SIGTERM', timeout: 500 } sends SIGTERM first and kills only if the process is still alive after the timeout. Ignored on Windows. A Docker container needs SIGTERM.

ignoreHTTPSErrors

Ignore certificate errors when polling the url.

Practical points:

  • DEBUG=pw:webserver npx playwright test prints every readiness poll and the server’s stdout, which is the quickest way to see why a server "never starts". A common cause is a url that returns 404 or 5xx; point it at a route that answers, such as a health or session endpoint, not at an authenticated page.

  • Tests can use relative URLs when use.baseURL is set. When webServer is an array, Playwright cannot guess which entry is the base, so set baseURL explicitly.

  • The wait capture is the way to cope with servers that choose their own port. It becomes visible in the config’s environment only after the server starts, so read it in the test or in a fixture, not at the top of the config file. The reference example for this feature writes the option as baseUrl; the actual option name is baseURL.

  • Start several processes with an array: webServer: [{ command: 'npm run start', url: 'http://localhost:3000', name: 'Frontend' }, { command: 'npm run backend', url: 'http://localhost:3333', name: 'Backend' }].

  • reuseExistingServer: true is convenient and also dangerous: a stale server from yesterday makes tests pass against old code. Keep it for local development and turn it off on CI.

  • The main configuration on this page does not use webServer at all and reads BASE_URL: start the application yourself (or in CI, before the job) and skip the option, which is the right choice when the application is deployed elsewhere, built by another job, or shared with other tools.

Fixtures

A fixture is something a test asks for by name and Playwright sets up for it: a page, a logged-in user, a page object, a database connection. Tests receive fixtures through the first argument, a destructured object, and Playwright creates only those that the test (or the fixtures it depends on) mentions. Compared with beforeEach/afterEach hooks, fixtures keep set-up and tear-down in one place, are reusable between files, are created on demand, can depend on each other, and need no describe wrapper to share an environment, so tests can be grouped by meaning instead of by set-up.

Creating fixtures with test.extend

base.extend() returns a new test object that has everything the base had plus your fixtures. A fixture is an async function that receives the fixtures it depends on, an object, then calls use() with the value the test will receive. The code before use() is set-up, the code after it is tear-down, and it runs even when the test fails. The project’s fixtures.ts defines one of each kind, described under the file.

export const test = base.extend<BookshelfOptions & TestFixtures, WorkerFixtures>({
  // An option fixture: the default is used when no project or test.use() overrides it.
  role: ['anonymous', { option: true }],
  searchTerm: ['', { option: true }],

  // An automatic, boxed fixture: set up for every test even when the test does not list it,
  // and hidden from the step list of reports.
  serverErrors: [async ({ page }, use, testInfo) => {

      if (response.status() >= 500) failures++;

    await use(() => failures);
    testInfo.annotations.push({ type: 'server-errors', description: String(failures) });

  appPage: async ({ page, role }, use) => {

  • Test-scoped fixtures (the default) are created for each test and torn down after it. appPage signs in through the API with page.request, which shares cookies with the page, so a test starts already signed in without clicking through the form. It depends on the role option, so a test or a project chooses who is signed in.

  • Worker-scoped fixtures are created once per worker process and shared by every test the worker runs, and torn down when the worker shuts down. Declare them with the second generic parameter and { scope: 'worker' }. They are the place for expensive, read-only resources: a started service, a seeded account per worker (use workerInfo.workerIndex to make names unique), a compiled asset. A worker fixture cannot depend on test-scoped fixtures such as page or request, which is why catalogue creates its own API client with playwright.request.newContext() and reads BASE_URL from the environment. It gets a separate timeout equal to the test timeout, adjustable as shown.

  • Automatic fixtures use { auto: true }. They are set up for every test (or every worker) even when the test does not list them. pageErrors records uncaught page exceptions and fails the test during tear-down, and serverErrors counts 5xx responses. Automatic fixtures are also the way to write a beforeEach/afterEach or beforeAll/afterAll that applies to every file: declare it with auto: true (and scope: 'worker' for the beforeAll equivalent) in the shared test object, and import that object in all specs.

  • Option fixtures use { option: true }. They have a default and are meant to be overridden in the config or with test.use(), which makes configuration declarative and type-safe. Pass the option types to defineConfig<Options>() so the config checks them, as playwright.config.ts does. If the value of an option is an array, wrap it: test.use({ persons: [[{ name: 'Alice' }], { scope: 'test' }] }).

  • Overriding a built-in fixture: a fixture with the same name replaces (or wraps) the original and can depend on it. page: async ({ baseURL, page }, use) => { await page.goto(baseURL); await use(page); } makes every test start on the home page. Overriding storageState this way supplies cookies computed at run time. Overriding changes the fixture for every test that uses that test object, so keep a differently named fixture (like appPage) when only some tests want the new behavior.

  • Names start with a letter or underscore and contain only letters, digits and underscores.

Execution order

Each fixture’s set-up runs before the test or hook that needs it, and its tear-down runs when nothing needs it any more. The rules:

  1. When fixture A depends on fixture B, B is set up before A and torn down after A.

  2. Non-automatic fixtures are lazy: they are created only when a test or hook needs them, so an unused fixture is never set up.

  3. Test-scoped fixtures are torn down after each test; worker-scoped ones when the worker process shuts down.

  4. Automatic worker fixtures are set up before anything else in the worker, automatic test fixtures before beforeEach hooks and the test itself.

For a worker with a beforeAll, a first test that only uses page and a second that uses a test fixture depending on a worker fixture, the order is: browser (needed by an automatic worker fixture), the automatic worker fixture, beforeAll; then for each test the automatic test fixture, page, beforeEach, the test, afterEach, and the teardown in reverse; the worker fixture is created lazily before the second test but torn down only at the end, after afterAll.

Tags are labels that start with @. Add them in the details object, { tag: '@smoke' } or an array of tags, on a test or on a test.describe() (inherited by every test inside), or write the tag in the title. Annotations with a type attach more than a label: { annotation: { type: 'issue', description: 'https://example.com/tickets/42' } }, one or an array, on a test or a group. The HTML report shows them all except those whose type starts with an underscore, and custom reporters receive them. A test can also add one at run time with test.info().annotations.push(...).

Test locks

Parallel tests are fast until two of them touch the same thing that cannot be shared: an external service, a global account setting, a single shared record. A lock is a named mutex declared on tests. Tests that hold the same lock name never run at the same time, across files, workers and projects, while every other test keeps running in parallel. Locks arrived in 1.63; in 1.64 test.describe.configure({ lock }) adds locks to a whole file or group.

import { test, expect } from '@playwright/test';

// Each of these tests replaces the shared Bookshelf data, so they must not run at the same time,
// even though fullyParallel is on and they could be scheduled in different workers.
// The file runs in its own project, after the others, with the plain test object.
test('seed one book', { lock: 'bookshelf-data' }, async ({ request, page }) => {
  await request.post('/api/test/seed', { data: { books: [{ title: 'Only Book', author: 'Test Author' }], reviews: [] } });
  await page.goto('/books');
  await expect(page.getByTestId('book-card')).toHaveCount(1);
});

test('seed two books', { lock: ['bookshelf-data'] }, async ({ request, page }) => {
  await request.post('/api/test/seed', {
    data: { books: [{ title: 'First', author: 'A' }, { title: 'Second', author: 'B' }], reviews: [] },
  });
  await page.goto('/books');
  await expect(page.getByTestId('book-card')).toHaveCount(2);
});

test.describe('whole group under a lock', () => {
  test.describe.configure({ lock: 'bookshelf-data' });

  test('empty catalogue', async ({ request, page }) => {
    await request.post('/api/test/seed', { data: { books: [], reviews: [] } });
    await page.goto('/books');
    await expect(page.getByTestId('empty-state')).toBeVisible();
  });
});

Source: Playwright: Parallelism

A test can hold several locks ({ lock: ['database', 'external-api'] }) and only starts when it can acquire all of them. Playwright acquires the locks before the test starts and releases them when it ends. Repeated calls to describe.configure({ lock }) add to, rather than replace, the locks already declared. In the default and serial modes, all tests in a file run together in order, so a lock declared on any one of them is held for the whole file.

Locks serialize; they do not isolate. They do not stop an unrelated test from reading the data that a locked test is changing. That is why this project runs locks.spec.ts in its own project (shared-data), which depends on the browser projects and therefore starts after them: Bookshelf’s /api/test/reset and /api/test/seed endpoints replace the shared data and, in the case of reset, clear every session, and an unrelated test in another worker could otherwise lose its login in the middle of a run. The first version of this project reset the data in an automatic fixture before every test and failed intermittently for exactly that reason, with six workers running. Per-test isolation is better solved by giving every test its own data (see Authentication & Isolation) and keeping locks for the few resources that truly are singletons. The lock tests were run with 4 workers and --repeat-each 5 (15 executions of the three tests):

Parameterized tests

Playwright runs in Node.js, so parameterizing is plain JavaScript. There are three levels.

Test level: generate tests from data with a loop. Each title must be unique. Put hooks outside the loop to run them once, or inside a test.describe() in the loop to run them for every row.

import { test, expect } from '../fixtures';

// Test-level parameterization: one test per row.
const searches = [
  { query: 'quiet', title: 'The Quiet Compiler' },
  { query: 'clouds', title: 'A Field Guide to Clouds' },
  { query: 'static', title: 'Rivers of Static' },
];

for (const { query, title } of searches) {
  test(`search for "${query}" finds ${title}`, async ({ page }) => {
    await page.goto(`/books?q=${query}`);
    await expect(page.getByRole('heading', { name: title })).toBeVisible();
  });
}

// Project-level parameterization: the option fixture searchTerm is set per project.
test('the shelf project searches its own term', async ({ page, request, searchTerm }) => {
  const expected = (await (await request.get(`/api/books?q=${searchTerm}`)).json()).total;
  await page.goto('/books');
  await page.getByTestId('search-input').fill(searchTerm);
  await page.getByTestId('search-input').press('Enter');
  await expect(page.getByTestId('result-count')).toHaveText(`${expected} books found`);
});

// Environment variables select the account: the password never appears in the test.
test('sign in with credentials from the environment', async ({ page }) => {
  await page.goto('/signin');
  await page.getByLabel('Username').fill(process.env.BOOKSHELF_USER ?? 'reader');
  await page.getByLabel('Password').fill(process.env.BOOKSHELF_READER_PASSWORD ?? 'reader-local-only');
  await page.getByTestId('signin-submit').click();
  await expect(page.getByTestId('account-heading')).toContainText(process.env.BOOKSHELF_USER ?? 'reader');
});

Environment level: environment variables select the target and carry secrets, which keeps them out of source control. The last test above reads BOOKSHELF_READER_PASSWORD; the config reads BASE_URL. Run BOOKSHELF_USER=admin BOOKSHELF_READER_PASSWORD=... npx playwright test to change them for one run. TypeScript

Playwright Test runs TypeScript without a build step: it transforms each file as it is loaded. It does not type-check, so a test with a type error still runs. Run the compiler next to it, in CI before the tests (npx tsc -p tsconfig.json --noEmit) and locally in watch mode (-w). The project of this page type-checks cleanly:

$ npx tsc -p ex-configuration/tsconfig.json
$ echo $?
0

Source: Playwright: TypeScript

Playwright reads the tsconfig.json closest to each file it loads (going up the directory tree, jsconfig.json too), so a tests/tsconfig.json can have test-specific settings. It honors only these compiler options: allowJs, baseUrl, paths, jsx, jsxFactory, jsxFragmentFactory, jsxImportSource, references and extends. Options such as target or strict only matter to your own tsc run. To use one file for everything, pass --tsconfig=tsconfig.test.json on the command line or set tsconfig in the config; the config option applies to test files and reporters but not to the config file or the files it imports.

Path mapping works in the specs. This project maps @helpers/* to helpers/* in its tsconfig.json, and fixtures.ts imports @helpers/credentials; the 66 tests resolved the import at run time:

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "preserve",
    "moduleResolution": "bundler",
    "strict": true,
    "noEmit": true,
    "skipLibCheck": true,
    "types": ["node"],
    "paths": {
      "@helpers/*": ["./helpers/*"]
    }
  },
  "include": ["**/*.ts"]
}

Source: Playwright: TypeScript

TypeScript 7, the version installed in the test project, removed baseUrl. Mappings then need an explicit ./ prefix ("@helpers/*": ["./helpers/*"]) and no baseUrl, and the old node (node10) moduleResolution is gone as well, so use bundler, node16 or nodenext. Playwright still lists baseUrl as a supported option, which matters for projects that stay on TypeScript 5 or 6 where it exists. Playwright compiles .tsx and .jsx files according to the jsx family of options and, since 1.64, uses the automatic runtime from react/jsx-runtime when jsx is unspecified, preserve or react-native.

If you use a very recent language feature that Playwright’s transformer does not handle, compile the tests yourself: a tests/tsconfig.json with an outDir such as ../tests-out, a pretest script of tsc --incremental -p tests/tsconfig.json, and playwright test -c tests-out as the test script.
