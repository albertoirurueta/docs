RequestBuilder, JSON & XML

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against GWT 2.13.1 (released 2026-06-19), gwt-maven-plugin 1.3.0 (net.ltgt.gwt.maven), JDK 21 running the compiler with -sourceLevel 17, the Jakarta Servlet 6 server of the Bookshelf scenario run by Jetty 12.1.10, Chrome 155 as the browser, and the gwt-user 2.13.1 sources, checked on 2026-10-09. Almost everything here is client code: RequestBuilder, the JSON and XML readers and JsonpRequestBuilder are Java compiled to JavaScript, and under the hood they drive the browser’s XMLHttpRequest, JSON and DOMParser objects. The server appears as ordinary servlets that return JSON, JSONP, XML or an event stream, and the build needs only a few <inherits> lines in the module XML. Nothing is shared between client and server in this style; the contract between them is a text format, which is exactly why it is useful when the back end is not Java, and exactly why it needs more care than GWT-RPC. Every output block on this page was produced by a lab module compiled with the 2.13.1 compiler, served from a private copy of the Bookshelf scenario by Jetty on port 8933 (a second origin on port 8943 played the part of "another site"), and driven in headless Chrome, which posted its log back to the server; the curl outputs came from the same server, and the AutoBean details marked as probes from a small JVM program using the 2.13.1 jars. Messages are quoted as they were printed; where a statement comes from the Developer Guide or the 2.13.1 source only, the text says so.

GWT-RPC (see the GWT-RPC page) is the Java-to-Java answer to "how do I call the server". This page covers the other half of the Developer Guide chapter on server communication: the HTTP client classes, with JSON and XML as the data formats, plus the cross-site tricks around them. Use it when the server is not a GWT-RPC servlet: a REST API written in any language, a third-party service, a legacy endpoint, a file or feed that is only a URL.

A first request

The Bookshelf catalogue is published by a servlet as JSON at /api/books?start=0&length=2. This is the complete request, with the response read in the callback.

RequestBuilder builder = new RequestBuilder(RequestBuilder.GET, BASE + "api/books?start=0&length=2");
builder.setHeader("Accept", "application/json");
builder.setTimeoutMillis(5000);
try {
  builder.sendRequest(null, new RequestCallback() {
    @Override
    public void onResponseReceived(Request request, Response response) {
      log("GET status=" + response.getStatusCode() + " text=" + response.getStatusText()
          + " type=" + response.getHeader("Content-Type"));
      String body = response.getText();
      // parse body: see "Reading JSON"
    }

    @Override
    public void onError(Request request, Throwable exception) {
      log("onError " + exception.getClass().getName() + ": " + exception.getMessage());
    }
  });
} catch (RequestException e) {
  log("sendRequest threw " + e.getClass().getName() + ": " + e.getMessage());
}

Measured output of the callback:

GET status=200 text=OK type=application/json;charset=utf-8

Source: GWT Developer Guide — Server communication: Making HTTP requests

Three things in that example are easy to get wrong, and the rest of this section is about them.

  • The call returns at once. The code after sendRequest runs before the response arrives, and GWT offers no synchronous variant (the Developer Guide explains that a synchronous call would freeze the single browser thread).

  • onResponseReceived is called for every response the browser produces, including 404 and 500. onError is not "the call failed"; it is "the timeout expired" (and, as shown below, almost nothing else).

  • getText() returns a String. Choosing and running a parser is your job.

Methods

GET, POST, PUT, DELETE and HEAD are constants of RequestBuilder. The release notes of 2.0.1 list the fix "RequestBuilder restricted to GET and POST", so the older statement that only those two work is obsolete. For a method without a constant, such as PATCH, the class has a second constructor that takes the method as a String, but it is protected: write a small subclass of RequestBuilder and call super("PATCH", url). The 2.13.1 source documents the constructor but the Developer Guide does not mention it, and the lab did not exercise it, so check your server’s handling of the method in a test before relying on it.

Pass the request body to sendRequest(String requestData, RequestCallback callback), or call setRequestData(String) and setCallback(RequestCallback) and then send(); sendRequest does not remember the data or callback it was given, while send() uses the stored ones. A body is a String: serialise JSON or XML yourself, and see below for the encoders.

Building the URL

RequestBuilder takes a URL that is already encoded. The URL class has the encoders: URL.encode(String) for a whole URL (it leaves the reserved characters of URL syntax alone), URL.encodeQueryString(String) for the value of a query parameter, and URL.encodePathSegment(String) for a path segment. UrlBuilder assembles a URL from parts and encodes each one.

String url = BASE + "api/books?author=" + URL.encodeQueryString(author) + "&start=" + start;

Concatenating user input into a URL without encoding it is the client-side half of query injection (an & in the author name adds a parameter). The server must still validate every parameter, because anyone can send any URL to it without your client.

Source: GWT Developer Guide — Server communication: Making HTTP requests

Headers

setHeader(name, value) sets one request header and replaces an earlier value of the same name; both arguments must be non-empty. There is one trap in the source of setHeaders: if you set no header at all, GWT adds Content-Type: text/plain; charset=utf-8; if you set at least one header, it adds nothing, and the browser chooses the content type from the body, which for a String is text/plain;charset=UTF-8. So a POST with a JSON body needs Content-Type: application/json set explicitly the moment you add any other header, such as a CSRF token. The lab made this visible: with only the token header set, the Bookshelf servlet, which insists on JSON, answered 415 and said what it had seen (full listing in the CSRF section below).

POST token but no Content-Type -> 415 Unsupported Media Type ; server says: application/json required, got text/plain;charset=utf-8

The browser keeps some headers for itself (the "forbidden request-header" list of the Fetch standard: Host, Content-Length, Cookie, Origin and others), so do not expect setHeader to control them. Custom headers on a cross-origin request turn it into a preflighted request, as measured in the CORS section.

Timeouts

setTimeoutMillis(int) sets a timer; 0 (the default) means no timeout, and a negative value throws IllegalArgumentException("Timeouts cannot be negative"). When the timer fires, GWT aborts the XMLHttpRequest and calls onError with a RequestTimeoutException, whose message and getters are:

timeout onError com.google.gwt.http.client.RequestTimeoutException: A request timeout has expired after 300 ms

(The lab asked the server to wait 1500 ms with a 300 ms timeout.) The request is aborted in the browser, but the server may keep working on it; a non-idempotent request that timed out may still have been applied, so do not blindly repeat it. RequestTimeoutException.getRequest() and getTimeoutMillis() give the details.

Status codes are not errors

The lab asked for a 404 and a 500. Both arrived in onResponseReceived:

404 reached onResponseReceived status=404 text=Not Found
500 reached onResponseReceived status=500 content-type=text/html;charset=iso-8859-1

Notice the second line: the error body of a servlet container is HTML, not your JSON. Check getStatusCode() (and ideally the Content-Type) before parsing, as the wrapper in the worked example does. Response has SC_* constants for the usual codes, so write Response.SC_OK rather than 200, and remember that success is the whole 2xx range (a 201 Created or 204 No Content is not SC_OK).

Status 0: "no response"

When the browser produces no HTTP response at all (the server is down, DNS fails, the connection is reset, or a cross-origin request is blocked), the XMLHttpRequest still reaches its DONE state with status 0 and an empty statusText. GWT delivers that to onResponseReceived, not to onError, with an empty body. This is the single most surprising behaviour of the class, and the Developer Guide’s comment in the sample (the onError branch is "could be timeout, SOP violation, etc.") does not match it. Measured with a request to another origin that sends no CORS headers:

cross-origin onResponseReceived status=0 text='' body.length=0

So the success test in a real application is "status in 200..299", and status 0 is a distinct, user-visible case: "cannot reach the server or the request was blocked". The browser console says which, but the page cannot read it: for security reasons JavaScript is deliberately not told why a cross-origin request failed.

Failing before the request starts

sendRequest can throw instead of calling back. RequestException covers failures to start; the subclass RequestPermissionException is thrown when XMLHttpRequest.open itself fails, which is what a URL that the browser cannot parse does:

malformed url -> com.google.gwt.http.client.RequestPermissionException: The URL http://[bad is invalid or violates the same-origin security restriction

The message mentions the same-origin policy because GWT cannot tell the cases apart. Handle both channels: a catch around sendRequest and the two callback methods.

Cancelling

sendRequest returns a Request. isPending() is true while the browser is working on it; cancel() clears the state-change handler, aborts the XMLHttpRequest and stops the timeout timer, without calling either callback. Use it when the user navigates away from the screen that asked, or to drop a stale search. Measured: the lab started a request that the server would answer after 500 ms, cancelled it, and waited 900 ms.

cancel: pending before=true
cancel: pending after=false
cancel: 900 ms later no callback was invoked

The server may still process a cancelled request, so cancelling is a client-side courtesy and not a way to undo a state-changing call.

User, password and credentials

setUser(String) and setPassword(String) pass HTTP basic credentials to XMLHttpRequest.open; putting a password in client code means every visitor can read it, so they are only useful with credentials typed by the user at run time. Cookies of the same origin are always sent. For a cross-origin request, setIncludeCredentials(true) sets withCredentials so that the browser also sends cookies and accepts Set-Cookie; it needs the server’s Access-Control-Allow-Credentials: true and a specific (not *) Access-Control-Allow-Origin. (The 2.5.1 release notes call this method withCredentials(); the method in 2.13.1 is setIncludeCredentials.)

A wrapper that treats non-2xx as failure

Most applications wrap RequestBuilder once, so that callers see one AsyncCallback like the one GWT-RPC uses and never touch status codes. This is the Bookshelf wrapper; it keeps the "status 0" case distinct and lets parse errors reach the same onFailure.

public final class JsonClient {
  public interface Parser<T> {
    T parse(String text);
  }

  private static final int TIMEOUT_MILLIS = 10_000;

  private JsonClient() {}

  public static <T> Request get(String url, Parser<T> parser, AsyncCallback<T> callback) {
    RequestBuilder builder = new RequestBuilder(RequestBuilder.GET, url);
    builder.setHeader("Accept", "application/json");
    builder.setTimeoutMillis(TIMEOUT_MILLIS);
    try {
      return builder.sendRequest(null, new RequestCallback() {
        @Override
        public void onResponseReceived(Request request, Response response) {
          int status = response.getStatusCode();
          if (status == 0) {
            callback.onFailure(new HttpStatusException(0, "No response: network error, CORS or aborted"));
          } else if (status < 200 || status >= 300) {
            callback.onFailure(new HttpStatusException(status, status + " " + response.getStatusText()));
          } else {
            T value;
            try {
              value = parser.parse(response.getText());
            } catch (RuntimeException e) {
              callback.onFailure(e); // malformed body
              return;
            }
            callback.onSuccess(value);
          }
        }

        @Override
        public void onError(Request request, Throwable exception) {
          callback.onFailure(exception); // timeout
        }
      });
    } catch (RequestException e) {
      callback.onFailure(e); // could not even start
      return null;
    }
  }
}

Measured with Parser being text -> (BookPageDto) NativeJson.parse(text):

JsonClient 404 -> HttpStatusException: 404 Not Found
JsonClient cross-origin -> HttpStatusException: No response: network error, CORS or aborted network=true
JsonClient bad body -> JavaScriptException: (SyntaxError) : Unexpected end of JSON input

The callback.onSuccess call is outside the try on purpose: an exception thrown by the caller’s success code must not be reported as a parse failure. Exceptions that escape a callback are not caught by RequestBuilder: the browser event handler is wrapped with GWT’s $entry (visible in the XMLHttpRequest source), so they reach the handler installed with GWT.setUncaughtExceptionHandler.

Overlay types: the legacy typed view

An overlay type is a Java class that extends JavaScriptObject and whose methods are JSNI one-liners reading properties of the JavaScript object underneath. It is what the Retrieving JSON tutorial teaches, and the JSNI & Overlay Types page describes the rules in detail: a protected no-argument constructor, final methods, no instance fields.

public class BookJso extends JavaScriptObject {
  protected BookJso() {}

  public final native String getTitle() /*-{ return this.title; }-*/;

  public final native int getYear() /*-{ return this.year; }-*/;
}

public class BookPageJso extends JavaScriptObject {
  protected BookPageJso() {}

  public final native int getTotal() /*-{ return this.total; }-*/;

  public final native JsArray<BookJso> getBooks() /*-{ return this.books; }-*/;
}
BookPageJso jso = JsonUtils.safeEval(body);
log("safeEval overlay total=" + jso.getTotal() + " first=" + jso.getBooks().get(0).getTitle());
safeEval overlay total=25 first=The Pragmatic Programmer

The compiler turns the getters into direct property reads (the overlay’s methods can be inlined, as the tutorial notes), so there is no per-object copy and no parser in the output beyond JSON.parse. JsArray<T>, JsArrayString, JsArrayInteger, JsArrayNumber and JsArrayBoolean wrap arrays. The drawbacks are the reason the tutorials' style is now legacy: it relies on JSNI, which the JsInterop page replaces; it is a GWT-only mechanism rather than part of the portable JsInterop specification; and nothing checks that the JSON really has a title.

JsInterop native types and JSON.parse

In new code, bind the JSON shape with a native JsInterop type. A native type has no implementation in Java: the compiler emits plain property accesses, so a DTO costs nothing at run time, and the JSON object itself is bound the same way.

@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "JSON")
public final class NativeJson {
  private NativeJson() {}

  public static native <T> T parse(String text);

  public static native String stringify(Object value);
}

@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "Object")
public class BookDto {
  public double id;
  public String title;
  public String author;
  public int year;
  public int copies;
}

@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "Object")
public class BookPageDto {
  public int total;
  public BookDto[] books;
}
BookPageDto dto = NativeJson.parse(body);
log("JSON.parse dto total=" + dto.total + " year0=" + dto.books[0].year + " author0=" + dto.books[0].author);
log("JSON.stringify(dto.books[0]) = " + NativeJson.stringify(dto.books[0]));
JSON.parse dto total=25 year0=1999 author0=Andrew Hunt
JSON.stringify(dto.books[0]) = {"id":1,"title":"The Pragmatic Programmer","author":"Andrew Hunt","year":1999,"copies":0}

Elemental2 ships the same binding (elemental2.core.Global.JSON, covered with fetch on the DOM & Elemental2 page), so a project that already depends on it can write Global.JSON.parse(text) and skip the hand-written NativeJson. Writing the three-line binding avoids a dependency for one function.

Three properties of this approach decide how you use it.

  • There is no validation. NativeJson.parse gives back whatever the server sent, cast to your type unchecked. A missing field is JavaScript undefined: a missing object field reads as null in Java, but a missing primitive does not read as 0. Measured with NativeJson.parse("{}") as a BookDto:

    missing primitives: year=undefined (== 0 ? false) title==null ? true id=undefined

    Validate the fields you depend on (Js.isTruthy, Js.isUndefined of jsinterop-base, or a range check) before using them in arithmetic.

  • Numbers are doubles. JavaScript has one number type, the double, and a GWT long is an emulated type rather than a JavaScript number, so declare ids as double (as BookDto.id is) or carry them as strings.

  • The text must be JSON. JSON.parse rejects anything else. A syntax error surfaces as a JavaScriptException whose message is the browser’s: (SyntaxError) : Unexpected end of JSON input.

JSONP

JSON with Padding is a workaround for the same-origin policy that predates CORS. The browser may load a <script> from any origin, so instead of XMLHttpRequest the client adds <script src="https://other.example/data?callback=handler">. The server answers with executable JavaScript, handler({...});, and the browser runs it, which calls the function the client registered. The Cross-site Requests tutorial (T Xsite) and the JSON and Mashups article (A JSON mash-ups) both build on it.

The server side of JSONP

The server must wrap the JSON in a call to a function whose name comes from the request. That name is attacker-controlled text that you write into a script, so it is a code-injection point. The lab servlet accepts only a dotted identifier, prefixes the body with /**/ (a common hardening against content-sniffing abuse of JSONP endpoints), and sets X-Content-Type-Options: nosniff.

public class BooksJsonpServlet extends HttpServlet {
  private static final Pattern CALLBACK = Pattern.compile("[A-Za-z_$][A-Za-z0-9_$.]{0,63}");

  @Override
  protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
    String callback = req.getParameter("callback");
    if (callback == null || !CALLBACK.matcher(callback).matches()) {
      resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "invalid callback");
      return;
    }
    Book first = CatalogRepository.INSTANCE.page(0, 1).getBooks().get(0);
    String json = "{\"id\":" + first.getId() + ",\"title\":" + BooksRestServlet.quote(first.getTitle()) + "}";
    resp.setContentType("text/javascript");
    resp.setCharacterEncoding(StandardCharsets.UTF_8.name());
    resp.setHeader("X-Content-Type-Options", "nosniff");
    resp.getWriter().write("/**/" + callback + "(" + json + ");");
  }

State-changing requests: CSRF/XSRF

A request that changes data must prove that the page that sent it is your page. Cross-site request forgery (CSRF, called XSRF in the GWT documents) makes the victim’s browser send a request with the victim’s cookies from a hostile site; the server cannot tell it from a genuine one unless something an attacker cannot know or set travels with it. GWT-RPC has built-in protection in RpcToken and XsrfProtectedService, described on the GWT-RPC page and on the XSRF, RPC & Server Security page; for RequestBuilder and REST endpoints you apply the same idea by hand.

The defences, in the order to apply them:

  1. Do not change state on GET (nor on HEAD), and make the other methods the only way in.

  2. Send a token in a custom header that the server compares with a per-session secret. A custom header cannot be set by a cross-site form or <script>, and for a cross-origin XMLHttpRequest it triggers a preflight that only an origin you allowed can pass.

  3. Require Content-Type: application/json on JSON endpoints; a cross-site HTML form can only send application/x-www-form-urlencoded, multipart/form-data or text/plain.

  4. Use SameSite cookies (Lax or Strict) for the session cookie, as defence in depth.

  5. Authorise on the server for every call. A token proves the origin of a request, not the user’s right to make it.

How the token reaches the client matters. Give it to the page in the dynamic host page (the server renders the HTML, so it can write the token into a <meta> tag), or have the page fetch it once from an endpoint that only the same origin can read. Never put it in a URL, and never hard-code one in the source of the module. The lab uses the first way; the host page is produced by a servlet and the token is a random value stored in the session:

The servlet compares the header with the session token in constant time, checks the content type, and only then reads the body:

public class BooksWriteServlet extends HttpServlet {
  @Override
  protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws IOException {
    String sent = req.getHeader("X-CSRF-Token");
    String expected = tokenFor(req.getSession(true));
    boolean ok = sent != null && MessageDigest.isEqual(
        sent.getBytes(StandardCharsets.UTF_8), expected.getBytes(StandardCharsets.UTF_8));
    if (!ok) {
      resp.sendError(HttpServletResponse.SC_FORBIDDEN, "missing or invalid CSRF token");
      return;
    }
    String type = req.getContentType();
    if (type == null || !type.toLowerCase().startsWith("application/json")) {
      resp.sendError(HttpServletResponse.SC_UNSUPPORTED_MEDIA_TYPE, "application/json required, got " + type);
      return;
    }
    String body = new String(req.getInputStream().readAllBytes(), StandardCharsets.UTF_8);
    // validate the JSON, authorise the user, then change the data
    resp.setStatus(HttpServletResponse.SC_CREATED);
    resp.setContentType("application/json");
    resp.getWriter().write("{\"saved\":true,\"bytes\":" + body.length() + "}");
  }
}

Security notes

  • The response is untrusted input. Parse with JSON.parse-based readers (safeEval, parseStrict, NativeJson.parse), never with eval; validate fields before use; display text with setText, not setHTML; use SafeHtml for markup.

  • Third-party scripts are your code. JSONP, and any ScriptInjector call, give the other site full control of your page. Prefer CORS or a proxy that returns only data.

  • State-changing calls need a token and a content type. The header-token pattern above, with SameSite cookies and server-side authorisation on every call. Tokens come from the server at run time; none belongs in source code or in a URL.

  • Cross-origin is the server’s decision. Allow specific origins, never * with credentials, and answer the preflight only for the headers and methods you want.

  • Do not send secrets in the URL. Query strings are logged by servers and proxies and stored in browser history; use headers or the body, over HTTPS.

  • Server-side validation is the only validation. Anything the client checks can be bypassed with curl; the lab’s servlets validate the callback name, the content type and the token themselves.

  • Do not return private data in a JSONP or GET JSON endpoint that cookies alone protect. See the hijacking discussion in the JSONP section.

  • Errors may expose internals. The 500 page measured above is a container HTML page; configure error pages so that stack traces are not sent to the browser.

onResponseReceived status=0 text='' body.length=0 for a call that "worked in curl" (lab)

No response: server down, DNS, TLS, or a cross-origin response without CORS headers or with a failed preflight

Open the browser console for the real reason; configure CORS on the server; treat status 0 as a distinct failure

com.google.gwt.http.client.RequestPermissionException: The URL http://[bad is invalid or violates the same-origin security restriction thrown by sendRequest (lab)

A URL that XMLHttpRequest.open rejects

Encode and validate the URL; catch RequestException around sendRequest

com.google.gwt.http.client.RequestTimeoutException: A request timeout has expired after 300 ms in onError (lab)

setTimeoutMillis(300) and a slow server

Raise the timeout or fix the server; do not repeat a non-idempotent request blindly

415 Unsupported Media Type and application/json required, got text/plain;charset=utf-8 (lab)

A header was set, so GWT did not add its default Content-Type, and the browser sent text/plain for the string body

Always set Content-Type: application/json; charset=utf-8 yourself on JSON bodies

403 Forbidden with missing or invalid CSRF token (lab)

The request has no token header, or a token from another session

Read the token from the dynamic host page and send it in a custom header

com.google.gwt.jsonp.client.TimeoutException: Timeout while calling http://localhost:8933/api/books.js (lab)

A JSONP request that the server refused (here 400 invalid callback) or that returned something other than a callback call

Check the server log; set a short setTimeout; JSONP gives no status

parsererror elements=1 and no exception after XMLParser.parse of malformed XML in Chrome (lab)

The 2.13.1 implementation only recognises the Mozilla parse-error namespace

Look for a parsererror element in the result

"id":"99" where the server expects a number (lab: AutoBeanCodex.encode output)

AutoBeanCodex writes a long as a JSON string

Use int, double or String in the interface, or accept strings on the server

java.lang.IllegalArgumentException: jsonTitle when calling a setter (probe, JVM)

@AutoBean.PropertyName is on the getter only; it is asymmetric

Annotate the getter and the setter

parseLenient ran attacker script: pwned=true (lab)

The eval-based parser executed an expression inside the "JSON"

Use parseStrict; remove JSONParser.parse and unsafeEval

A write that was cancelled or timed out was applied anyway (source)

Request.cancel() and the timeout abort the XMLHttpRequest in the browser; the server may already have processed the request

Make writes idempotent; send a request id the server can de-duplicate

Where older material is outdated

  • The Developer Guide’s JSON page describes JsonUtils.safeEval as a method that "evals" its input and shows only the overlay and JSONParser styles. In the 2.13.1 source safeEval is JSON.parse. The page does not mention parseStrict or the native-type style.

  • JSONParser.parse is @Deprecated; the guide and the 2007 book use it as the normal reader, and the book itself notes that it evaluates the text instead of parsing it. Use parseStrict.

  • The Developer Guide’s RequestBuilder example says onError handles "SOP violation": in the browser it is onResponseReceived with status 0 (measured above).

  • The XML page says XMLParser.parse throws DOMException for malformed input; in Chrome it returns a document with a parsererror element (measured above).

  • The tutorials use javax.servlet, Servlet 2.3 DTDs, Eclipse wizards, the removed Jetty-based development mode server and Google Data feeds. The structure is right and the code needs the changes in the table above.

  • The 2007 book (chapters 12 and 13) teaches RequestBuilder with only GET and POST, XMLParser, FormPanel and a JSON search component that parses with the eval-based JSONParser.parse, backed by a third-party search service and server proxies in Java, Perl and Ruby. Its explanation of the HTTP methods and of the proxy idea still holds; the parser, the GET/POST limit (lifted in GWT 2.0.1) and the example service do not. File uploads with FormPanel are covered on the widgets page and, for the server half, on the server integration page of this section.

  • The 2.5.1 release notes name a RequestBuilder.withCredentials() method; the method is setIncludeCredentials(boolean).

What changed recently

  • 2.0.1. RequestBuilder accepts methods other than GET and POST (release notes).

  • 2.5.1. RequestBuilder gained the credentials option for CORS (listed as withCredentials(), now setIncludeCredentials).

  • JSON. JSONParser.parse is deprecated in favour of parseStrict; JsonUtils.safeEval is JSON.parse in 2.13.1.

  • 2.13.x. The release notes fetched on 2026-10-08 list no change to com.google.gwt.http, json, jsonp or xml. These packages in 2.13.1 are what the 2010 documents describe, apart from the points above.

  • Beyond 2.13. The roadmap fetched on 2026-10-08 names no replacement for them; for new code, the browser’s own fetch through Elemental2 or one of the libraries on the REST & JSON Libraries page are the options when you do not want RequestBuilder.
