Cell Widgets

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against GWT 2.13.1 (2026-06-19), gwt-maven-plugin 1.3.0 (net.ltgt.gwt.maven), JDK 21 running the compiler with -sourceLevel 17, and the Jakarta Servlet 6 server of the Bookshelf scenario, checked on 2026-10-08. Cell widgets are client knowledge: they are classes of gwt-user (the com.google.gwt.user.User module inherits them) that the GWT compiler turns into JavaScript together with your code. The data they show is usually shared with the server (the Book and BookPage classes travel over GWT-RPC), the server side of paging and sorting is a few lines of plain Java, and the build needs nothing beyond what any GWT module already has (see Project Structure & Modules). Every example on this page was compiled with the 2.13.1 compiler and loaded in headless Chrome; the Bookshelf catalogue also ran against the Jetty 12 backend of the scratch application, and the HTML, the request payloads and the messages quoted below are what the browser and the compiler printed.

Cell widgets are the GWT answer to the question "how do I show a thousand rows without a thousand widgets?". An ordinary widget (a Label, a Button, a row of a FlexTable) is a Java object with a DOM element, event handlers and a place in the widget hierarchy, so a table of 1,000 rows by 5 columns is 5,000 objects that have to be created, attached and eventually detached. A cell widget (CellList, CellTable, DataGrid, CellTree, CellBrowser) keeps one HTML string per page of data instead: it asks a small, stateless cell to render each value into that string, assigns the whole string to the browser with innerHTML, and lets the cell look at events afterwards. The same handful of cell objects serve every row, which is the flyweight pattern the official guide names.

What a cell widget is

Four ideas explain almost everything on this page.

  • A cell renders a value into SafeHtml. Cell<C> has a render(Context, C, SafeHtmlBuilder) method that appends HTML for one value. It does not create DOM nodes. A cell for a String is a few lines; a cell for a whole Book can be a <div> with an image and two lines of text.

  • A cell is a flyweight. One TextCell object renders the title of row 1 and of row 10,000, and it receives the browser events of all those rows. It must not keep per-row state in its fields; the Context argument tells it which row and column it is working for.

  • A cell widget shows a page of rows. Cell widgets are always paged: a widget has a visible range (a start index and a length), it renders only those rows, and it announces range changes. The page size defaults to 25 for CellList, 15 for CellTable and 50 for DataGrid. "No paging" simply means a page size as big as the data.

  • Data arrives through a data provider. The widget does not own the data. A data provider is told which range the widget wants and pushes rows back with updateRowData. When the data changes, the provider pushes again and the widget re-renders the affected rows.

CellPanel, in spite of its name, is not a cell widget: it is a base class of table-based panels such as HorizontalPanel (the official guide makes the same remark). The Grid and FlexTable panels that the 2007 book teaches hold ordinary widgets in table cells and are covered with the other panels (see the Panels & Layout and Widgets pages).

Choose a cell widget when the data set is large or changes often, when the columns map to data fields, when you need paging, sorting or selection, or when you want the table to stay cheap on a phone. Choose a plain widget (or UiBinder) for a small, form-like layout where each part is a different component. A cell widget can still contain interactive parts: buttons, check boxes, text inputs and drop-downs are all built-in cells.

The cells that take input (EditTextCell, TextInputCell, CheckboxCell, SelectionCell, DatePickerCell) extend AbstractEditableCell, which adds view data: a map from the row key to what the user typed but has not saved. That is the second reason a ProvidesKey matters (see below): with the default key (the row object itself) a re-fetched row looks like a new row and the pending edit is lost. ValueUpdater and FieldUpdater

A cell tells the outside world about a user action through a ValueUpdater<C>: its single method update(C newValue) is called with the new value (the text typed, the box state, the selected option; for a button, the same value again as a "something happened" signal). A cell widget with no columns, such as CellList, takes the updater directly with setValueUpdater. A table column wraps it: Column.setFieldUpdater(FieldUpdater<T, C>) provides update(int index, T row, C value), which is what you almost always want, because it knows the row.

An updater does not re-render anything. It is a notification. The code in it must change the model and then ask for the affected row to be drawn again, as the pitfalls table below shows with a measurement.

CellTable

CellTable<T> renders a page of rows of type T as an HTML <table>; each column shows one aspect of the row. A Column<T, C> has to implement getValue(T row), and a Cell<C> (given to its constructor) renders that value. TextColumn<T> is the shortcut for a text column (Cell<String> is a TextCell), and IdentityColumn<T> passes the row itself to the cell, which is what a CompositeCell or an "actions" cell needs.

What the experiment also showed:

  • The CheckboxCell(true, false) combined with createCheckboxManager() made a click on a check box select a row (the row got the selected style and the box was checked), while a click on any other cell of the row only moved the keyboard focus. Column and cell styling

Column.setCellStyleNames("name") sets a style for every cell of a column, and Column.getCellStyleNames(Cell.Context, T row) can return a style per cell, as the Bookshelf catalogue does for books with no copies left. AbstractCellTable.setRowStyles(RowStyles<T>) takes an object with getStyleNames(T row, int rowIndex) for the whole row. setColumnWidth(Column, double, Unit) and setColumnWidth(Column, String) control widths, Column.setHorizontalAlignment(...) and setVerticalAlignment(...) the alignment, and addColumnStyleName(int, String) a style on a <col>.

The widths need a fixed layout to be reliable. By default the columns grow to fit the contents of their cells, which looks jumpy when the content changes with paging; table.setWidth("100%", true) switches to the fixed table layout and lets you give the columns percentages (which should add up to 100%), pixels, or a mix: a narrow pixel column for a check box and percentages for the rest. The official guide adds that with table.setWidth("auto", true) a column without a width is invisible, because its width defaults to 0.

The look of the widget itself comes from its Resources bundle. CellTable.Resources defines cellTableStyle() (a CellTable.Style CssResource whose default stylesheet is CellTable.css) and the images for the header and footer backgrounds, the loading indicator and the sort arrows; CellTable.BasicResources is the variant for the GWT standard style theme and uses CellTableBasic.css. To restyle it, extend CellTable.Resources, re-declare cellTableStyle() with @Source({CellTable.Style.DEFAULT_CSS, "mytable.gss"}) and pass an instance to a constructor such as CellTable(int pageSize, Resources resources); the CSS and GSS directives are the subject of the Styling: CSS & GSS page.

Sorting

A cell table does not sort anything by itself; it provides the user interface and an event, and you decide where the sort happens.

  1. column.setSortable(true) makes the column header clickable (role="button") and shows an arrow once it is the sort column.

  2. A click on the header pushes the column onto the table’s ColumnSortList and fires a ColumnSortEvent.

  3. Handlers registered with table.addColumnSortHandler(...) react.

Two handlers ship with GWT, one for each kind of data provider.

CellTree and CellBrowser

A tree cell widget shows hierarchical data without a widget per node. The widgets know nothing about your hierarchy; a TreeViewModel answers two questions:

  1. <T> NodeInfo<?> getNodeInfo(T value): "the children of this value are provided by this data provider, rendered by this cell, selected through this selection model".

  2. boolean isLeaf(Object value): "this value cannot be opened".

The tree asks getNodeInfo(rootValue) for the first level, where rootValue is the object you pass to the constructor and the tree never displays (null is accepted), and calls it again with the value of each node that the user opens. NodeInfo<T> is an interface with a cell, a key provider, a selection model, a value updater and the setDataDisplay/unsetDataDisplay that attach a list to the node; TreeViewModel.DefaultNodeInfo<T> implements it from a data provider and a cell (and optionally a selection model and a value updater), which covers nearly every case.

A catalogue tree: authors, then the books of an author (CatalogTreeModel.java)
public class CatalogTreeModel implements TreeViewModel {
  private final List<Book> books;
  private final SingleSelectionModel<Book> bookSelection = new SingleSelectionModel<>(b -> b.getId());

  public CatalogTreeModel(List<Book> books) {
    this.books = books;
  }

  @Override
  public <T> NodeInfo<?> getNodeInfo(T value) {
    if (value == null) {                         // the hidden root: its children are the authors
      ListDataProvider<String> authors = new ListDataProvider<>();
      authors.getList().addAll(new TreeSet<>(authorNames()));
      return new DefaultNodeInfo<>(authors, new TextCell());
    }
    String author = (String) value;              // an author node: its children are the books
    ListDataProvider<Book> byAuthor = new ListDataProvider<>(b -> b.getId());
    for (Book b : books) {
      if (b.getAuthor().equals(author)) {
        byAuthor.getList().add(b);
      }
    }
    return new DefaultNodeInfo<>(byAuthor, new AbstractCell<Book>() {
      @Override
      public void render(Context context, Book book, SafeHtmlBuilder sb) {
        if (book != null) {
          sb.appendEscaped(book.getTitle());
        }
      }
    }, bookSelection, null);
  }

  @Override
  public boolean isLeaf(Object value) {
    return value instanceof Book;
  }
}

A tree node’s children are a data display like any other, so a node can use an AsyncDataProvider: getNodeInfo returns a DefaultNodeInfo over a provider that fetches the children of the opened node from the server. Because getNodeInfo is called each time a node is opened, create the provider inside it (as above) or cache it, but do not share one provider between two nodes.

Data providers, ranges and pagers

HasData, HasRows and Range

A cell widget exposes its paging state through HasRows: getVisibleRange(), setVisibleRange(int start, int length), getRowCount(), isRowCountExact(), setRowCount(int) and setRowCount(int, boolean), plus handlers for RangeChangeEvent and RowCountChangeEvent. HasData<T> adds setRowData(int start, List<? extends T>), getVisibleItem(int), getVisibleItems() and setSelectionModel. A Range is the pair start index, length (new Range(0, 10)), a plain serializable value class, so it can also be an argument of an RPC method.

The row count is separate from the rows: a widget can show rows 10 to 19 and still know that there are 25 in all. The count can be exact or an estimate: when a count is not exact, the pager shows "of over N" and lets the user keep going while data keeps arriving, which suits a stream or a server that cannot count cheaply.

ListDataProvider

ListDataProvider<T> is a provider whose data is a java.util.List in the browser. getList() returns a wrapper of the list: every change made through it (add, set, remove, clear, sort) is noticed and pushed to the displays, at the end of the current event loop, so several changes cost one refresh. flush() pushes immediately, refresh() re-sends every row, and setList(List) replaces the underlying list. The page size of the display decides which rows of the list are shown, so a list of 200 items and a CellList of 25 produce eight pages without further code.

The wrapper cannot see changes inside the items: the Javadoc says so, and the lab measured it with a CellList showing one Book.

AsyncDataProvider

AsyncDataProvider<T> is for data that lives on a server or is expensive to produce. It is deliberately small: you subclass it and implement a single method.

protected abstract void onRangeChanged(HasData<T> display)

GWT calls that method whenever a display needs a different range: the moment the display is added with addDataDisplay (the display’s current visible range is "initialised" right away, which is why adding the display is the signal to load the first page), when the user pages, when the page size changes, and after a sort when AsyncHandler clears the data. The method’s job is to read display.getVisibleRange(), start the request and, when the answer comes, call two methods that AsyncDataProvider makes public:

  • updateRowCount(int count, boolean exact) tells all displays how many rows exist.

  • updateRowData(int start, List<T> values) gives them the rows that start at index start.

The provider does not hold on to the data: it forwards to each display only the rows that fall inside that display’s visible range (an empty list that starts at the page start is delivered too) and ignores the rest, so a late answer for an old range does not put foreign rows on the page. The only state it keeps is the last row count it was told, which it passes to a display that is added later.

Out-of-order answers

Two requests can be in flight at once (the user pages twice, or sorts while a page is loading), and the network does not promise to answer them in order. The provider cannot know which answer is newer, so the code that owns the request does: the Bookshelf presenter below numbers each request and drops a response that is not the latest, and a JVM unit test delays the first answer and checks that the late one is ignored.

ProvidesKey

Custom cells

The built-in cells cover forms and tables; a custom cell is how a book, an author or a rating gets its own look without a widget per row. The recipe has four steps, and every step is a decision the guide spells out.

  1. Extend AbstractCell<C>, with C the type of value the cell shows. The constructor lists the events the cell wants: super("click", "keydown").

  2. Implement render(Context, C, SafeHtmlBuilder). Check for null, escape anything that came from a user, and append HTML.

  3. Override onBrowserEvent(...) if the cell reacts to events, and onEnterKeyDown(...) for the keyboard.

  4. Report changes by calling the ValueUpdater that is passed in (it can be null).

Rendering safely: SafeHtmlBuilder and SafeHtmlTemplates

The HTML a cell appends is assigned to the page without any further escaping, so the cell is where cross-site scripting is prevented or allowed. SafeHtmlBuilder supports the safe habit: appendEscaped(String) turns < and & into entities, appendHtmlConstant(String) is for literals written by the developer (never for data) and append(SafeHtml) adds something already known to be safe (the SafeHtml & XSS page covers the type system behind it). The lab fed the title <script>alert(1)</script> Tricks to a cell that used appendEscaped, and the browser received <script>alert(1)</script> Tricks, displayed as text.

For anything with attributes, string concatenation quickly gets unreadable and unsafe, so GWT generates the code from a template: an interface that extends SafeHtmlTemplates, with one method per fragment and the HTML in an annotation. The type of each parameter says how it is escaped: a String is escaped as text or as an attribute value, a SafeHtml is inserted as is, SafeStyles goes in a style attribute and SafeUri in a href or src.

The lab’s CopiesBadgeCell shows the number of copies of a book as a small badge; clicking it (or pressing Enter on it) asks to borrow a copy.

A custom cell with a template and events (CopiesBadgeCell.java)
public class CopiesBadgeCell extends AbstractCell<Integer> {

  interface Templates extends SafeHtmlTemplates {
    @SafeHtmlTemplates.Template("<span class=\"{0}\" title=\"{1}\">{2}</span>")
    SafeHtml badge(String styleName, String tooltip, String text);
  }

  private static final Templates TEMPLATES = GWT.create(Templates.class);

  public CopiesBadgeCell() {
    super("click", "keydown");               // the events this cell wants to receive
  }

  @Override
  public void render(Context context, Integer copies, SafeHtmlBuilder sb) {
    if (copies == null) {
      return;                                // widgets pass null for filler cells
    }
    String style = copies == 0 ? "bk-badge bk-out" : "bk-badge";
    String text = copies == 0 ? "none left" : copies + " left";
    sb.append(TEMPLATES.badge(style, "Row " + context.getIndex(), text));
  }

  @Override
  public void onBrowserEvent(Context context, Element parent, Integer copies, NativeEvent event,
      ValueUpdater<Integer> updater) {
    super.onBrowserEvent(context, parent, copies, event, updater);   // Enter -> onEnterKeyDown
    if ("click".equals(event.getType())
        && parent.getFirstChildElement().isOrHasChild(Element.as(event.getEventTarget()))) {
      borrow(copies, updater);
    }
  }

  @Override
  protected void onEnterKeyDown(Context context, Element parent, Integer copies, NativeEvent event,
      ValueUpdater<Integer> updater) {
    borrow(copies, updater);
  }

  private void borrow(Integer copies, ValueUpdater<Integer> updater) {
    if (copies != null && copies > 0 && updater != null) {
      updater.update(copies - 1);
    }
  }
}

Source: GWT — Developer Guide: Custom Cells

The pieces to notice:

  • GWT.create(Templates.class) is deferred binding (see Deferred Binding & Generators): the compiler generates the implementation and checks the template while it compiles, so a typo in a placeholder is a build error and not a runtime surprise. The messages are in the pitfalls table.

  • The title attribute is a String parameter, so a book title with a quote in it cannot break out of the attribute.

  • parent in onBrowserEvent is the element that contains the cell’s HTML, not the outermost element the cell wrote (a TextCell writes no element at all). parent.getFirstChildElement().isOrHasChild(target) is the guide’s test for "the click really hit what I rendered".

  • super.onBrowserEvent(...) is called first because AbstractCell is what turns a keydown with the Enter key into a call of onEnterKeyDown. The cell must list "keydown" among its events for that to happen.

Combining cells: CompositeCell and HasCell

One table cell can hold several cells. CompositeCell<C> takes a List<HasCell<C, ?>>; each HasCell<C, X> names a Cell<X>, how to get its value X from the cell’s value C and an optional FieldUpdater<C, X>. Each part is rendered in a <span> of its own, and the composite hands every event to the part that rendered the target. The loan table above ends with an "Actions" column built this way (rendered <span>#3</span><span><button …>Renew</button></span>): a TextCell that shows the loan number and an ActionCell whose Delegate extends the due date. IdentityColumn<T> is the column to use with it, because the composite’s value is the whole row.

IconCellDecorator<C> wraps one cell and puts an ImageResource in front of it (the constructor can also set the vertical alignment); it is the lightweight way to add an icon to a built-in cell without writing a new one.

Rules of thumb

  • Cells are shared: a field of the cell holds configuration (a format, a style name), never the row being rendered.

  • Escape everything that came from outside, including titles, author names, file names and data that comes from the server. Use appendEscaped, a String template parameter, or a SafeHtmlRenderer; do not build markup by string concatenation and do not use appendHtmlConstant on data.

  • Return early on null.

  • Keep a cell’s HTML small; it is generated for every visible row, on every redraw.

  • Make interactive parts reachable by keyboard: a <button> is focusable, a <span> with a click handler is not; add tabindex and handle Enter, as ClickableTextCell does, or use a button.

/** Sorts on a whitelisted field only; an unknown field falls back to id order. */
public BookPage page(int start, int length, String sortField, boolean ascending) {
  List<Book> all = new ArrayList<>(books.values());
  Comparator<Book> order = comparatorFor(sortField);
  if (order != null) {
    all.sort(ascending ? order : order.reversed());
  }
  int from = Math.max(0, Math.min(start, all.size()));
  int to = Math.max(from, Math.min(all.size(), from + Math.max(0, length)));
  return new BookPage(all.subList(from, to), all.size());
}

private static Comparator<Book> comparatorFor(String field) {
  if (field == null) {
    return null;
  }
  switch (field) {
    case "title":  return Comparator.comparing(Book::getTitle).thenComparing(Book::getId);
    case "author": return Comparator.comparing(Book::getAuthor).thenComparing(Book::getId);
    case "year":   return Comparator.comparingInt(Book::getYear).thenComparing(Book::getId);
    case "copies": return Comparator.comparingInt(Book::getCopies).thenComparing(Book::getId);
    default:       return null;
  }
}

Source: GWT — Developer Guide: Communicating with a Server

The tie-break by id makes the order total: without it, two rows with the same author could swap places between two requests, and a row would appear on two pages or on none. In a real application the sort would be a database ORDER BY with the same whitelist, and start and length a LIMIT and OFFSET (or, better for large tables, a keyset condition).

The presenter

The presenter is plain Java: it has no GWT.create call, so a JVM unit test runs it with a fake service. It numbers the requests and ignores the answer of a request that is no longer the latest (the out-of-order problem described with the provider).

CatalogPresenter.java
public class CatalogPresenter {
  private final CatalogServiceAsync service;
  private final CatalogDisplay display;
  private int latestRequest;

  public CatalogPresenter(CatalogServiceAsync service, CatalogDisplay display) {
    this.service = service;
    this.display = display;
  }

  public void load(int start, int length, String sortField, boolean ascending) {
    final int request = ++latestRequest;
    service.getBooks(start, length, sortField, ascending, new AsyncCallback<BookPage>() {
      @Override
      public void onSuccess(BookPage page) {
        if (request == latestRequest) {   // a newer range or sort order was requested meanwhile
          display.showRows(start, page.getBooks(), page.getTotal());
        }
      }

      @Override
      public void onFailure(Throwable caught) {
        if (request == latestRequest) {
          display.showError(caught.getMessage());
        }
      }
    });
  }
}

The view

The view owns the DataGrid and the AsyncDataProvider; its onRangeChanged is the only place that knows about sorting. The key provider (Book::getId) is given to the grid.

CatalogView.java (the data flow, abridged)
public class CatalogView extends Composite implements CatalogDisplay {
  public interface Listener {
    void onRange(int start, int length, String sortField, boolean ascending);
    void onOpen(Book book);
  }

  private final DataGrid<Book> grid = new DataGrid<>(10, Book::getId);
  private final Map<Column<Book, ?>, String> sortFields = new HashMap<>();
  private final AsyncDataProvider<Book> provider;

  public CatalogView(Listener listener) {
    provider = new AsyncDataProvider<Book>() {
      @Override
      protected void onRangeChanged(HasData<Book> display) {
        Range range = display.getVisibleRange();
        ColumnSortList sorts = grid.getColumnSortList();
        String field = null;
        boolean ascending = true;
        if (sorts.size() > 0) {
          field = sortFields.get(sorts.get(0).getColumn());
          ascending = sorts.get(0).isAscending();
        }
        listener.onRange(range.getStart(), range.getLength(), field, ascending);
      }
    };

    addSortable(titleColumn, msg.title(), "title");
    addSortable(authorColumn, msg.author(), "author");
    addSortable(copiesColumn, msg.copiesHeader(), "copies");   // copiesColumn also styles books with no copies
    grid.addColumn(openColumn);                                // a ButtonCell column with a FieldUpdater

    // Sorting clears the data and fires a RangeChangeEvent, so onRangeChanged runs again.
    grid.addColumnSortHandler(new ColumnSortEvent.AsyncHandler(grid));

    SimplePager pager = new SimplePager();
    pager.setDisplay(grid);
    …                                                          // DockLayoutPanel: pager south, grid center
  }

  private void addSortable(Column<Book, ?> column, String header, String sortField) {
    column.setSortable(true);
    sortFields.put(column, sortField);
    grid.addColumn(column, header);
  }

  /** Starts the data flow. Call it once the presenter exists: this triggers the first range request. */
  public void connect() { provider.addDataDisplay(grid); }

  @Override
  public void showRows(int start, List<Book> rows, int total) {
    provider.updateRowCount(total, true);
    provider.updateRowData(start, rows);
  }
}

Three details are easy to get wrong and were all exercised:

  • connect() is separate from the constructor. addDataDisplay calls onRangeChanged at once. In an earlier version of the view the display was added in the constructor, before the activity had created the presenter; the first range request hit a null listener, the exception was thrown inside Activity.start, the widget was never attached, and nothing was shown, silently, because the uncaught-exception handler only logged. The activity now creates the view, then the presenter, shows the view and then calls connect().

  • The sort field comes from the column, through a map filled in addSortable, so adding a sortable column is one line and the provider never learns column positions.

  • Sorting keeps the page. AsyncHandler reuses the current range, so sorting on page 2 asks for rows 10 to 19 of the sorted list. If the user expects to go back to the top, call grid.setVisibleRange(0, grid.getPageSize()) (or pager.firstPage()) in a sort handler of your own.

Accessibility and keyboard use

The cell widgets bring some of the accessibility work, and leave the rest to the cells. What the lab’s markup showed: sortable table headers have role="button" and tabindex="-1"; the SimplePager buttons are <img> elements with role="button", an aria-label ("First page", "Previous page", "Next page", "Fast forward") and aria-disabled; CellTree sets role="tree" and gives each node role="treeitem" with aria-level, aria-setsize, aria-posinset, aria-expanded and aria-selected; the focused row or cell has tabindex="0". The pager labels come from SimplePager.ImageButtonsConstants, a Constants interface, so they are translated with the module’s locale.

What to do in your own cells: use a real <button> or <input> for actions (they are focusable and announced), give an icon-only control an aria-label in the template, handle Enter and not only the click, and keep KeyboardSelectionPolicy at ENABLED or BOUND_TO_SELECTION rather than DISABLED unless another way to reach the rows exists. A table also needs an accessible name; give the widget’s element an aria-label or aria-labelledby yourself. The ARIA roles and states API of GWT (com.google.gwt.aria.client.Roles) and the rest of the guidance are on the Accessibility & ARIA page.

What changed since the older material

  • The book predates cell widgets. The 2007 first edition (GWT 1.3 and 1.4) builds tables from Grid and FlexTable panels with widgets in the cells and listener interfaces for events, as did every GWT application until 2010. Cell widgets arrived with the first 2.1 milestone (19 May 2010; 2.1.0 final 27 October 2010), announced together with an application framework for large business applications. None of the cell classes in this page is in the book.

  • DataGrid is a 2.4.0 feature (7 September 2011): a scrolling table with a fixed header and footer.

  • CellTableBuilder, custom headers and footers, and UiBinder rendering of cells (the UiRenderer of this page) came with the 2.5.0 release candidates (27 June 2012; 2.5.0 final 25 October 2012).

  • Selection by event manager. DefaultSelectionEventManager and its factories are how current code chooses what selects. The 2.5.0 release notes list AbstractCellTable.doSelection(Event,Object,int,int), AbstractHasData.onUpdateSelection() and CellList.doSelection(Event, Object, int) among the removed methods, so code from the 2.1 and 2.2 era that overrides them does not compile any more. The same notes record that the LEFT and RIGHT placement of the text in SimplePager was fixed, which may swap it for applications that had worked around the bug.

  • Deprecated or stale API in the guide’s examples. CheckboxCell(boolean isSelectBox) is deprecated in favour of the two-argument constructor. The guide says ActionCell acts on mouseUp; in 2.13.1 it consumes click and keydown. The sort examples refer to a Tester.Contact type that exists only in the file they were copied from. The table of contents of the cell widget guide links to #cellbrowser, an anchor the page does not define, and the guide’s AsyncDataProvider example pushes rows with cellList.setRowData instead of updateRowData on the provider.

  • Showcase link. The guide’s demo link uses http://samples.gwtproject.org/samples/Showcase/Showcase.html#!CwCellSampler; the same page over https is listed in the references.

  • J2CL. Cell widgets ship in gwt-user. Among the org.gwtproject.* libraries that are published for J2CL (all still 1.0.0 release candidates when checked on 2026-10-08) there is no gwt-user-style module that contains them, so a cell-widget application is a GWT application today (see J2CL & the Future).
