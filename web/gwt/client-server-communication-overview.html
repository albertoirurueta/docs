Client–Server Communication

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against GWT 2.13.1 (2026-06-19), gwt-maven-plugin 1.3.0, a JDK 21 toolchain with -sourceLevel 17 and the Jakarta Servlet 6 server of the Bookshelf scenario, and was checked on 2026-10-09. It is an overview and a decision guide, so it touches all four kinds of code of a GWT application: client code (compiled to JavaScript, where every call starts), shared code (the types that cross the wire when GWT-RPC is used), server code (servlets, filters, event streams) and build settings (which module to inherit and which artifact to add). The output blocks were produced by compiling the examples with the 2.13.1 compiler and running them in headless Chrome 155 against Jetty 12.1.10 (the Bookshelf server) and a small scripted server that serves JSON, JSONP, server-sent events and a WebSocket; where a statement comes only from the Developer Guide, the 2.13.1 source or a registry page, the text says so.

A GWT application is a program that runs in the browser, so everything it knows about the outside world arrives over HTTP (or a protocol that starts as HTTP). The compiler gives you no network layer of its own: it gives you several, built on the same browser primitives, and they differ in who defines the message format, how much Java type information crosses the wire, which origins they may talk to and how much they cost in code size. This page names the options, shows when each one fits, explains the one rule they all share (the browser never blocks, so every answer comes back through a callback or a promise) and the one wall they all meet (the same-origin policy).

The rest of the section goes deeper: the architecture page explains where the client, shared and server code live, and the section’s pages GWT-RPC, RequestBuilder, JSON & XML, REST & JSON Libraries, RequestFactory & AutoBeans and Server Integration & Deployment treat each option in full, with XSRF, RPC & Server Security and SafeHtml & XSS on protecting the calls.

The options at a glance

Table 1. The seven ways to reach a server from GWT 2.13.1
Style What travels What you write Cross-origin

GWT-RPC

A POST with the content type text/x-gwt-rpc; the body is a compact, GWT-specific text format that carries Java objects

A RemoteService interface, an Async twin, a servlet that extends RemoteServiceServlet and shared Serializable types

Always preflighted by the browser, because the content type and the X-GWT-Permutation header are not CORS-safelisted

RequestBuilder with JSON or XML

Any text: JSON, XML, form data, plain text

An HTTP request in Java, a parser for the answer (JSONParser, XMLParser, overlay types, JsInterop)

Subject to the same-origin policy (it is XMLHttpRequest underneath); works with CORS

JSONP

A <script> element whose source is a GET URL; the server wraps JSON in a call to a function the client names

JsonpRequestBuilder, an overlay type or a JsInterop type for the result

Works across origins without CORS, at the price of running the server’s reply as code

RequestFactory

JSON (application/json; charset=utf-8) describing changes to proxies of server entities

RequestFactory, RequestContext, EntityProxy and ValueProxy interfaces, @ProxyFor and @Service bindings, a servlet

Preflighted, for the same reason as RPC

REST libraries

JSON over plain HTTP verbs, designed by you or by an existing API

An annotated Java interface (DominoKit domino-rest, RestyGWT) or hand-written code

Subject to the same-origin policy; works with CORS

Elemental2 fetch

Whatever the Fetch API can send, typically JSON

DomGlobal.fetch(...) and Promise chains, in Java

Subject to the same-origin policy; works with CORS

WebSocket and server-sent events

A long-lived connection: messages in both directions (WebSocket) or events from the server (EventSource)

Elemental2 WebSocket or EventSource, plus a server endpoint of your choice

WebSocket is not subject to CORS, so the server must check the Origin header itself; a cross-origin EventSource is CORS-checked (withCredentials for cookies)

The Developer Guide groups them in two families: the GWT RPC framework, which "transparently" calls Java servlets, and the HTTP client classes, which build and send custom requests. Everything else in the table is either one of those two with more convenience around it (RequestFactory, the REST libraries) or the browser’s own API reached through Elemental2. The Guide also states that GWT does not limit you to one mechanism or one server-side language: it is "RPC agnostic", and a GWT client can talk to a server written in any language that speaks HTTP.

Choosing a style

The deciding questions are about the server and about who else uses the API, not about the browser.

Asynchronous programming

GWT offers no blocking network call. The FAQ (GWT FAQ — Server) states why: browsers run JavaScript on a single thread, so a blocking call to XMLHttpRequest would also block the user interface and make the page appear to freeze, and the workarounds that exist are not available in every browser. Every style in this page is therefore asynchronous: the method that starts the call returns at once, and the result is delivered later, when the event loop is free, to code that you registered.

The Developer Guide adds the practical consequences. The code that follows the call runs while the round trip is still in progress. Code inside onSuccess is written next to the call but runs only after the calling code has returned to the JavaScript event loop and the answer has arrived. A server that is slow or unreachable cannot hang the application, and several calls can be in flight at once, so the time they take overlaps instead of adding up.

The callback contract

GWT-RPC and JSONP use the same interface from com.google.gwt.user.client.rpc (the AsyncCallback interface lives there even when no RPC is involved):

public interface AsyncCallback<T> {
  void onFailure(Throwable caught);
  void onSuccess(T result);
}

Exactly one of the two methods is called, once, for a call that completes. RequestBuilder uses a different pair, RequestCallback.onResponseReceived(Request, Response) and onError(Request, Throwable), and Elemental2 uses Promise.then(onFulfilled, onRejected). The three shapes mean the same thing, and they differ in one way that matters: what counts as a failure.

Table 3. What each style reports as a failure

RequestCallback

Only a request that could not be sent or timed out (onError). A response with any HTTP status, including 404 and 500, goes to onResponseReceived, and so does a request the browser blocked: see the pitfalls table

Four things to read in this output.

  • Line 2 is printed before any response: the call returned immediately, and the rest of the method ran while both requests were in flight.

  • The answer of the second request arrived first (50 ms against 400 ms). Responses are not delivered in the order in which requests were sent, so a screen that reloads on every keystroke or page change can show old data over new data unless the callback ignores stale answers.

  • An exception thrown inside a callback does not reach the code that started the call, because that code has long finished. It reaches the handler registered with GWT.setUncaughtExceptionHandler, which here printed the IllegalStateException.

  • A RequestBuilder timeout set with setTimeoutMillis calls onError with a RequestTimeoutException, and no "slow answered" line appeared even though the scripted server replied to that request after 1500 ms: the late answer is not delivered.

Handling the in-between state

An asynchronous call has a state that a blocking call never had: started, not finished. A screen has to say what it shows during that time, and what happens if the user acts again. Two patterns cover most of the Bookshelf catalogue.

The first is a request counter that makes the callback ignore answers to requests that are no longer the latest one:

CatalogLoader.java: ignore stale answers
private int requestCounter;

public void load(int start, int length) {
  final int mine = ++requestCounter;
  DomGlobal.document.title = "Loading...";
  catalog.getBooks(start, length, new AsyncCallback<BookPage>() {
    @Override
    public void onFailure(Throwable caught) {
      if (mine == requestCounter) {
        DomGlobal.document.title = "Could not load the catalogue";
      }
    }

    @Override
    public void onSuccess(BookPage page) {
      if (mine != requestCounter) {
        return; // a newer request has been sent; this answer is stale
      }
      DomGlobal.document.title = page.getBooks().size() + " of " + page.getTotal();
    }
  });
}

The second is a join: start independent calls together and continue when all of them have succeeded, which is faster than chaining them. GWT has no Future, and the Elemental2 Promise.all is awkward with Java generics (see the DOM and Elemental2 page for its pitfall), so a small typed helper is enough:

Join2.java: continue when two parallel calls have both succeeded
public static final class Join2<A, B> {
  private A a;
  private B b;
  private boolean haveA, haveB, failed;
  private final AsyncCallback<Void> done;

  public Join2(AsyncCallback<Void> done) { this.done = done; }

  public AsyncCallback<A> first() {
    return new AsyncCallback<A>() {
      @Override public void onFailure(Throwable t) { fail(t); }
      @Override public void onSuccess(A result) { a = result; haveA = true; maybeDone(); }
    };
  }

  public AsyncCallback<B> second() {
    return new AsyncCallback<B>() {
      @Override public void onFailure(Throwable t) { fail(t); }
      @Override public void onSuccess(B result) { b = result; haveB = true; maybeDone(); }
    };
  }

  public A a() { return a; }
  public B b() { return b; }

  private void fail(Throwable t) {
    if (!failed) { failed = true; done.onFailure(t); }
  }

  private void maybeDone() {
    if (haveA && haveB && !failed) { done.onSuccess(null); }
  }
}

// Usage: the page of books and the first book are requested together.
Join2<BookPage, Book> join = new Join2<>(new AsyncCallback<Void>() {
  @Override public void onFailure(Throwable t) { DomGlobal.console.log("one of the calls failed: " + t); }
  @Override public void onSuccess(Void ignored) { DomGlobal.console.log("both arrived"); }
});
catalog.getBooks(0, 10, join.first());
catalog.getBook(7L, join.second());

Both classes were compiled by the 2.13.1 compiler as part of a probe module. A callback that touches a widget must also guard against the widget having been removed while the call was in flight (compare isAttached()), and a screen that can be left should cancel its Request (Request.cancel()) when it goes.

Current browsers allow more connections per host and HTTP/2 multiplexes requests on one connection, so the amount of parallelism you get depends on the browser and the protocol: measure it instead of designing around the number two.

GWT-RPC

GWT-RPC maps a Java interface to a servlet. The client sees an Async twin of the interface whose methods take a callback, GWT generates the proxy with deferred binding, and the server side extends RemoteServiceServlet (the com.google.gwt.user.server.rpc.jakarta package for Jakarta Servlet 5 and later, shipped in gwt-servlet-jakarta; the javax variant is in gwt-servlet). The Bookshelf catalogue service is declared like this:

CatalogService.java and CatalogServiceAsync.java (shared)
@RemoteServiceRelativePath("catalog")
public interface CatalogService extends XsrfProtectedService {
  BookPage getBooks(int start, int length);
  Book getBook(long id) throws BookNotFoundException;
  Book saveBook(Book book) throws BookNotFoundException;
}

public interface CatalogServiceAsync {
  void getBooks(int start, int length, AsyncCallback<BookPage> callback);
  void getBook(long id, AsyncCallback<Book> callback);
  void saveBook(Book book, AsyncCallback<Book> callback);
}

Source: GWT Developer Guide — Creating services

The User module already inherits the RPC module (com.google.gwt.user.RemoteService), so a client that inherits com.google.gwt.user.User needs nothing else. The request is a POST with Content-Type: text/x-gwt-rpc; charset=utf-8, and the client also sends X-GWT-Permutation and X-GWT-Module-Base headers (the names are constants of RpcRequestBuilder). RemoteServiceServlet refuses a request whose content type is not text/x-gwt-rpc and, unless you override checkPermutationStrongName, a request without the permutation header, which is also a first line of defence against cross-site request forgery. Run against the Bookshelf server, the refusals look like this:

RPC calls that change data must be protected against cross-site request forgery, which the Bookshelf service does by extending XsrfProtectedService; the XSRF, RPC & Server Security page explains the token flow.

RequestBuilder with JSON or XML

RequestBuilder is the building block of every other HTTP style in the GWT library: it wraps XMLHttpRequest. Its module, com.google.gwt.http.HTTP, is inherited by User; JSON support (com.google.gwt.json.JSON) and JSONP support (com.google.gwt.jsonp.Jsonp) are separate modules, and neither is in User. A request is a method and a URL (encoded with URL.encode or its siblings), optional headers, a timeout and a callback:

Probe.java: RequestBuilder against the Bookshelf JSON endpoint

rb.setTimeoutMillis(5000);

  rb.sendRequest(null, new RequestCallback() {
    @Override public void onError(Request request, Throwable exception) {
      log("RequestBuilder onError: " + exception);
    }
    @Override public void onResponseReceived(Request request, Response response) {
      log("RequestBuilder onResponseReceived: status=" + response.getStatusCode()

JSONP

Browsers refuse to let a script read the answer of a cross-origin XHR, but they do run a <script> element loaded from any origin. JSONP exploits that: the client names a callback function in the URL, and the server answers with JavaScript that calls it with the data. JsonpRequestBuilder (module com.google.gwt.jsonp.Jsonp) generates the function name and sends the name in the callback parameter, which you can change with setCallbackParam; the default timeout is 10 seconds (setTimeout).

Probe.java: JSONP
JsonpRequestBuilder jsonp = new JsonpRequestBuilder();
jsonp.setTimeout(3000);
jsonp.requestObject(api + "/jsonp?x=1", new AsyncCallback<JavaScriptObject>() {
  @Override public void onFailure(Throwable caught) { log("JSONP onFailure: " + caught); }
  @Override public void onSuccess(JavaScriptObject result) { log("JSONP onSuccess: " + new JSONObject(result)); }
});

Output in headless Chrome 155, with the page on port 9931 and the endpoint on port 8931, which sends no CORS header at all:

JSONP onSuccess: {"total":25}

It worked where RequestBuilder and fetch were blocked (next section), and that is its danger. The reply is executed as JavaScript in your page with your page’s privileges: a provider that is compromised, or that is wrong about escaping, runs code in the Bookshelf session. JSONP can only issue GET requests, cannot send headers, and cannot tell a 404 from a network failure; the same call against a server that had no such path (a 404) produced:

JSONP onFailure: com.google.gwt.jsonp.client.TimeoutException: Timeout while calling http://localhost:8931/jsonp?x=1

Use it only when the provider is trusted and offers nothing else. The old "JavaScript hijacking" weakness of JSON over GET (CVE-2007-2378) is a related design issue, and the XSRF, RPC & Server Security page covers it.

RequestFactory

RequestFactory is the Developer Guide’s data-oriented alternative to RPC: the client works with proxy interfaces (EntityProxy, ValueProxy) through a RequestContext, only the changes of a modified object travel to the server, and the server side is bound to your domain classes with @ProxyFor, @Service and optional Locator classes. The Maven coordinates changed when GWT moved to Maven Central: the artifacts are requestfactory-client, requestfactory-server, requestfactory-server-jakarta and requestfactory-apt under the group org.gwtproject.web.bindery, all at 2.13.1 (2026-06-19) on Maven Central on 2026-10-09, and the 2.13.1 BOM manages the requestfactory dependency. Server push: WebSocket, server-sent events and polling

A request/response style cannot tell the browser that something happened. There are three answers, and none of them is GWT-RPC (the RPC protocol is request/response and its format is not a message stream):

  • Polling: ask again every few seconds with a Timer. It is the most compatible and the most wasteful option, and the simplest to secure, because every poll is an ordinary authenticated request.

  • Server-sent events (SSE): one HTTP response that stays open and carries text/event-stream events; the browser’s EventSource reconnects by itself. One direction only, plain HTTP GET, subject to CORS like fetch (the withCredentials field of EventSource sends cookies cross-origin).

  • WebSocket: a full-duplex channel started by an HTTP upgrade. Messages are strings or binary, so the format (usually JSON) is yours.

Elemental2 provides EventSource and WebSocket (module elemental2.dom.Dom); GWT-RPC serialisation is not involved:

The same-origin policy and CORS

The browser lets a script read a response only if it comes from the same origin as the page: the same scheme, host and port. The GWT FAQ (GWT FAQ — Server) states it plainly, and also states that this is not a GWT problem: it applies to any Ajax framework. It affects GWT in three places: the host page and the compiled scripts, the calls the application makes, and development (the code server on one port, the application server on another). Cross-Origin Resource Sharing is the server’s way of opting specific other origins in; the site’s CORS page explains the headers and the preflight protocol, and this section shows how each GWT style meets them.

Avoiding CORS, or answering it correctly

The first choice is not to cross origins at all. The Developer Guide’s deployment section already shows the pattern: serve the static files from one server and configure it to proxy only the servlet paths to the application server (it uses Apache HTTPD with ProxyPass and ProxyPassReverse), so that the browser sees a single origin. The same idea works with any reverse proxy, with Spring Boot serving the compiled module and the API from one application, and in development with the proxy of your build tool or code server. No header has to be configured, and cookies stay first-party.

When the API must be on another origin, answer CORS on the server, with an explicit list of allowed origins and never a reflected Origin header. Jetty 12 ships a CrossOriginHandler (module cross-origin), Tomcat a CorsFilter (org.apache.catalina.filters.CorsFilter), and Spring has its own configuration; a filter of a few lines is enough for the Bookshelf servlets and shows the moving parts:

AllowListCorsFilter.java: CORS for an allow-list of origins (server)
public class AllowListCorsFilter implements Filter {
  private Set<String> allowed = Set.of();

  @Override
  public void init(FilterConfig config) {
    String origins = config.getInitParameter("allowedOrigins");
    if (origins != null && !origins.isBlank()) {
      allowed = Set.of(origins.split("\\s*,\\s*"));
    }
  }

  @Override
  public void doFilter(ServletRequest req, ServletResponse resp, FilterChain chain)
      throws IOException, ServletException {
    HttpServletRequest request = (HttpServletRequest) req;
    HttpServletResponse response = (HttpServletResponse) resp;
    String origin = request.getHeader("Origin");
    if (origin != null) {
      response.addHeader("Vary", "Origin");
      if (allowed.contains(origin)) {
        response.setHeader("Access-Control-Allow-Origin", origin);
        response.setHeader("Access-Control-Allow-Credentials", "true");
        boolean preflight = "OPTIONS".equals(request.getMethod())
            && request.getHeader("Access-Control-Request-Method") != null;
        if (preflight) {
          response.setHeader("Access-Control-Allow-Methods", "GET, POST");
          response.setHeader("Access-Control-Allow-Headers",
              "Content-Type, X-GWT-Permutation, X-GWT-Module-Base, X-Bookshelf-Client");
          response.setHeader("Access-Control-Max-Age", "600");
          response.setStatus(HttpServletResponse.SC_NO_CONTENT);
          return;
        }
      }
    }
    chain.doFilter(req, resp);
  }
}

RequestBuilder.setIncludeCredentials sets withCredentials on the underlying request. With credentials, the server must answer with the exact origin (the wildcard is not accepted) and Access-Control-Allow-Credentials: true. The last output line shows a detail that surprises people: the server did send X-Content-Type-Options: nosniff, yet response.getHeader("X-Content-Type-Options") returned null, because a cross-origin script can read only the CORS-safelisted response headers unless the server lists others in Access-Control-Expose-Headers.

Two things CORS does not do. It does not authenticate anyone: any non-browser client ignores it, so the authorisation checks stay on the server, for every call, whatever the origin (the CORS page of this site makes the same point). And it does not replace protection against cross-site request forgery for cookie-authenticated calls; the XSRF, RPC & Server Security page covers the token flow that the Bookshelf RPC service uses.

The book consulted for this section (Hanson and Tacy, 2007, GWT 1.3/1.4) predates most of what this page uses: it builds RPC clients with ServiceDefTarget.setServiceEntryPoint and GWT.getModuleBaseURL() where today a @RemoteServiceRelativePath annotation does the job, it uses Java 1.4 collections and @gwt.typeArgs comments where today generics are used, it loads JSON with JSONParser.parse, which relied on eval, where parseStrict is the safe call, it relies on server push by blocking in servlets where EventSource and WebSocket exist, and its example services (Google and Yahoo search endpoints) no longer exist. The concepts it teaches are still valid: calls must be asynchronous, the same-origin policy decides what the client may reach, and the client must treat every answer as untrusted input.
