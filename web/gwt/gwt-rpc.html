GWT-RPC

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against GWT 2.13.1 (released 2026-06-19), gwt-maven-plugin 1.3.0 (net.ltgt.gwt.maven), JDK 21 running the compiler and the server with -sourceLevel 17, the Jakarta Servlet 6 server (Jetty 12.1.10, EE 10) of the Bookshelf scenario and the gwt-user and gwt-servlet-jakarta 2.13.1 jars and sources, checked on 2026-10-09. GWT-RPC spans three kinds of code at once. The shared interfaces and data classes are compiled twice, once by GWT to JavaScript and once by javac to bytecode. The client part is the generated proxy, the AsyncCallback objects and the code of the calling presenter, all compiled to JavaScript. The server part is a servlet that decodes the request, calls your Java method and encodes the result. The build has to deploy one extra artifact, the serialisation policy file that the compiler writes next to the JavaScript. Every output block on this page was produced by running the examples in a private copy of the Bookshelf scenario: a lab module compiled with the 2.13.1 compiler, served by Jetty 12 on port 8932 and driven by headless Chrome 155 through the DevTools protocol, probe modules compiled with the 2.13.1 compiler for the generator messages, curl against the servlet for the wire format, and plain JUnit tests on JDK 21 for the presenter. Where a statement comes only from the Developer Guide, the Javadoc or the 2.13.1 source, the text says so.

GWT-RPC is a remote procedure call mechanism between a GWT client and a Java servlet that is built into the toolkit. You write a Java interface, a servlet that implements it and a callback, and GWT generates the code that turns method arguments and results into a text payload, sends it over XMLHttpRequest and turns the answer back into Java objects. The Developer Guide is explicit about what it is not: the service is not a SOAP or REST web service, it is not meant to be a public API for other clients, and it does not replace a Jakarta EE back end. It is "getting from the client to the server" for the application that shipped the client, and the rest of this page follows from that. Other ways to talk to a server (JSON, XML, REST libraries, RequestFactory) are compared on the communication overview page (Client-Server Communication).

The life of one call

The diagram follows getBooks(0, 10) of the Bookshelf catalogue from the presenter to the callback. The names of the checks are the real ones of the 2.13.1 sources.

sequenceDiagram participant P as Presenter participant X as CatalogService_Proxy participant S as RemoteServiceServlet participant L as Policy file (.gwt.rpc) participant I as CatalogServiceImpl P->>X: getBooks(0, 10, callback) X->>X: serialise the arguments (type serializer) X->>S: POST text/x-gwt-rpc + X-GWT-Permutation + X-GWT-Module-Base S->>S: checkPermutationStrongName (header present?) S->>L: load policy by strong name (cached per module base and name) S->>S: RPC.decodeRequest (interface, method, signatures, types) S->>I: onAfterRequestDeserialized, then invoke getBooks I-->>S: BookPage, or a declared exception S->>S: encode //OK[...] or //EX[...] against the policy S-->>X: 200 application/json, optionally gzip X->>X: parse (JSON.parse from RPC version 8, eval before) X-->>P: callback.onSuccess(BookPage) or callback.onFailure(caught)

Three things in the diagram explain most of the pitfalls later on. First, nothing is sent until the browser’s event loop is free again: the call returns immediately and the callback runs later (see Asynchronous calls). Second, the server decides what may be deserialised from the policy file, not from the class path, which is why a missing policy file breaks every call (see Serialisation policy files). Third, an error can happen at four different places (the proxy, the transport, the servlet, the callback), and each place reports through a different exception (see Exceptions: everything that can reach onFailure).

Defining the Bookshelf CatalogService

The running scenario of this section is the Bookshelf (books, authors, reviews, loans) as a three-module GWT application: bookshelf-shared, bookshelf-client and bookshelf-server (see Project structure and modules). The service lives in the shared module because both sides compile it.

bookshelf-shared: the synchronous service interface
package com.example.bookshelf.shared;

import com.google.gwt.user.client.rpc.RemoteService;
import com.google.gwt.user.client.rpc.RemoteServiceRelativePath;

/** GWT-RPC service. Mapped to the module base URL plus "catalog". */
@RemoteServiceRelativePath("catalog")
public interface CatalogService extends RemoteService {
  BookPage getBooks(int start, int length);

  Book getBook(long id) throws BookNotFoundException;

  Book saveBook(Book book) throws BookNotFoundException, AccessDeniedException;

  int lend(long id) throws BookNotFoundException;

  java.util.ArrayList<Review> reviews(long bookId) throws BookNotFoundException;

  java.util.HashMap<Format, Integer> copiesByFormat();

  int revision();
}
bookshelf-shared: the asynchronous interface
package com.example.bookshelf.shared;

import com.google.gwt.http.client.Request;
import com.google.gwt.http.client.RequestBuilder;
import com.google.gwt.user.client.rpc.AsyncCallback;

public interface CatalogServiceAsync {
  void getBooks(int start, int length, AsyncCallback<BookPage> callback);

  Request getBook(long id, AsyncCallback<Book> callback);

  RequestBuilder saveBook(Book book, AsyncCallback<Book> callback);

  void lend(long id, AsyncCallback<Integer> callback);

  void reviews(long bookId, AsyncCallback<java.util.ArrayList<Review>> callback);

  void copiesByFormat(AsyncCallback<java.util.HashMap<Format, Integer>> callback);

  void revision(AsyncCallback<Integer> callback);
}

The rules that the generator enforces, all from ServiceInterfaceProxyGenerator:

  • The Async interface has the same package and simple name plus Async: com.example.bookshelf.shared.CatalogServiceAsync for com.example.bookshelf.shared.CatalogService.

  • Each synchronous method has one asynchronous method with the same name and the same parameters plus a last AsyncCallback<R> parameter, where R is the return type boxed (Integer for int, Void for void).

  • The asynchronous return type is void, com.google.gwt.http.client.Request or com.google.gwt.http.client.RequestBuilder. A Request lets the caller ask isPending() and cancel(). A RequestBuilder means that the call is prepared but not sent until the caller invokes send(), so the caller can still change headers or the timeout.

  • A synchronous method may declare checked exceptions; they travel back as the exceptions of onFailure (see Exceptions: everything that can reach onFailure).

  • @RemoteServiceRelativePath is a runtime-retained annotation on the synchronous interface. Its value is resolved against GWT.getModuleBaseURL(). Without the annotation the service has no URL until ServiceDefTarget.setServiceEntryPoint(String) is called.

When the generator cannot find the Async interface, or a method is missing, the compile fails with messages that print the interface it expected. The two cases below were reproduced with probe interfaces named P7 and P8:

Checking the synchronous interface 'com.example.probe.client.Services.P7' against its asynchronous version 'com.example.probe.client.Services.P7Async'

   A valid definition for the asynchronous version of interface 'com.example.probe.client.Services.P7' would be:

public interface P7Async {
	void hello(java.lang.String name, com.google.gwt.user.client.rpc.AsyncCallback<java.lang.String> arg2);

bookshelf-server: the jakarta implementation (excerpt)
package com.example.bookshelf.server;

import com.google.gwt.user.server.rpc.RPCRequest;
import com.google.gwt.user.server.rpc.jakarta.RemoteServiceServlet;
import jakarta.servlet.http.HttpServletRequest;
// other imports omitted

public class CatalogServiceImpl extends RemoteServiceServlet implements CatalogService {
  /** Called after the request was decoded and before the service method runs: a place for audit logging. */
  @Override
  protected void onAfterRequestDeserialized(RPCRequest rpcRequest) {
    log("rpc " + rpcRequest.getMethod().getName() + " with " + rpcRequest.getParameters().length + " parameter(s)");
  }

  @Override
  public BookPage getBooks(int start, int length) {
    if (start < 0 || length < 0) {
      throw new IllegalArgumentException("start and length must be >= 0");
    }
    return CatalogRepository.INSTANCE.page(start, Math.min(length, 100));
  }

  @Override
  public Book getBook(long id) throws BookNotFoundException {
    return CatalogRepository.INSTANCE.get(id);
  }

  @Override
  public Book saveBook(Book book) throws BookNotFoundException, AccessDeniedException {
    // Authorisation is a server-side decision: never trust a flag sent by the browser.
    if (getThreadLocalRequest().getUserPrincipal() == null) {
      throw new AccessDeniedException();
    }
    if (book.getTitle() == null || book.getTitle().isBlank() || book.getTitle().length() > 200) {
      throw new IllegalArgumentException("Invalid title");
    }
    return CatalogRepository.INSTANCE.save(book);
  }
  // lend, reviews, copiesByFormat and revision omitted
}

Source: GWT — Server communication: implementing services

This excerpt is the plain, unprotected form used to introduce the servlet API. Because saveBook changes state, the deployed Bookshelf service extends the jakarta XsrfProtectedServiceServlet instead, and its onAfterRequestDeserialized override calls super.onAfterRequestDeserialized(rpcRequest) first so the token check still runs (see XSRF protection).

getBooks caps the page size at 100 (Math.min(length, 100)) because the length comes from the browser. Treat every argument as hostile input and validate it again on the server; the client-side checks of the user interface are a convenience only.

Mapping the servlet to a URL

The URL of a service is the module base URL plus the value of @RemoteServiceRelativePath. The module base URL is the directory that contains the module’s *.nocache.js file, with the context path in front: with rename-to="bookshelf" and a web application deployed at the root, GWT.getModuleBaseURL() is http://localhost:8932/bookshelf/ and the servlet is mapped to /bookshelf/catalog.

bookshelf-server: WEB-INF/web.xml
<?xml version="1.0" encoding="UTF-8"?>
<web-app xmlns="https://jakarta.ee/xml/ns/jakartaee" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-app_5_0.xsd"
  version="5.0">

  <servlet>
    <servlet-name>catalogServlet</servlet-name>
    <servlet-class>com.example.bookshelf.server.CatalogServiceImpl</servlet-class>
  </servlet>
  <servlet-mapping>
    <servlet-name>catalogServlet</servlet-name>
    <url-pattern>/bookshelf/catalog</url-pattern>
  </servlet-mapping>
</web-app>

The annotation-based alternative needs no web.xml entry. It was run in Jetty 12 EE 10 and gave the same lab results as the web.xml mapping:

@WebServlet(name = "catalogServlet", urlPatterns = "/bookshelf/catalog")
public class CatalogServiceImpl extends RemoteServiceServlet implements CatalogService {
  // ...
}

Source: GWT — Server communication: testing services during development

Three details of the mapping decide whether calls arrive:

  • The part of the pattern before the last segment must equal the module base path. If the module is renamed with rename-to, the renamed value is used; either way the segment must be the directory inside the WAR where the module’s files are served.

  • The servlet only handles POST. A GET of the same URL answers 405 Method Not Allowed, because AbstractRemoteServiceServlet.doPost is the only handler (doPost is final).

  • The servlet must be in the same web application as the module’s files: it loads the policy file with ServletContext.getResourceAsStream, and the module path must start with the context path (see Serialisation policy files).

A servlet around a plain service class

RemoteServiceServlet has a second constructor, RemoteServiceServlet(Object delegate), for a service implementation that is not itself a servlet. That makes the logic a plain class that can be unit-tested, reused, or created by a dependency-injection container.

/** Plain class: it does not extend a servlet. */
public class PingLogic implements NoPathService {
  @Override
  public String ping() {
    return "pong";
  }
}

/** Wraps a service implementation that is not itself a servlet. */
@WebServlet(name = "pingServlet", urlPatterns = "/bookshelf/ping")
public class PingServlet extends RemoteServiceServlet {
  public PingServlet() {
    super(new PingLogic());
  }
}

NoPathService is a service interface without @RemoteServiceRelativePath, so the client sets the URL explicitly (see ServiceDefTarget and RpcRequestBuilder). The call returned //OK[1,["pong"],0,7] in the lab. In a Spring application the same constructor lets a @Service bean become the delegate of a servlet registered through a ServletRegistrationBean (the registration itself belongs to Server integration and deployment and is not repeated here).

What the servlet does for you, and the hooks it offers

The base classes implement a fixed pipeline. Each step has a protected method you can override; most applications override only the first two rows.

Table 3. The extension points of RemoteServiceServlet and AbstractRemoteServiceServlet
Method Use and default

onBeforeRequestDeserialized(String) and onAfterResponseSerialized(String)

getThreadLocalRequest() and getThreadLocalResponse()

The current HttpServletRequest and HttpServletResponse, for the session, the principal and headers. Valid only on the request thread.

getRequestModuleBasePath() and getPermutationStrongName()

Throws SecurityException ("Blocked request without GWT permutation header (XSRF attack?)") if the permutation header is missing. May be overridden to a no-op for non-GWT clients.

Public so that they can be tested without HTTP. Override to route the call to a framework component.

Every response also carries Content-Type: application/json;charset=utf-8 and Content-Disposition: attachment.

Calling the service from the client

The client side of a call always has the same three steps: create the proxy with GWT.create(), write the callback, make the call.

CatalogServiceAsync catalog = GWT.create(CatalogService.class); // the cast is implicit: the proxy implements the Async interface

catalog.getBooks(0, 10, new AsyncCallback<BookPage>() {
  @Override
  public void onSuccess(BookPage page) {
    display.showRows(0, page.getBooks(), page.getTotal());
  }

  @Override
  public void onFailure(Throwable caught) {
    display.showError("The catalogue could not be loaded.");
  }
});

Source: GWT — Server communication: actually making a call

The assignment from GWT.create(CatalogService.class) to the Async type compiles without a cast because GWT.create is generic; older code and the Developer Guide write (CatalogServiceAsync) GWT.create(...). The proxy can be created once and shared by every presenter; it holds no per-call state except the optional RPC token and the request builder. In the Bookshelf the ClientFactory creates it and the facade below wraps it.

Asynchronous calls

Every call returns before the server has answered. The code after the call runs first, then the browser returns to its event loop, and only when the response arrives is onSuccess or onFailure invoked. GWT offers no synchronous variant, because a synchronous XMLHttpRequest would freeze the single JavaScript thread of the page.

The consequences for the code you write are practical:

  • A field that the callback sets is not yet set on the line after the call. Move the follow-up work into the callback, or into a method the callback calls.

  • Two calls started one after the other may complete in either order. If the order matters, start the second call from the first one’s callback (see [chaining]).

  • If the user can trigger a call twice (a double click on a button), disable the control until the callback ran, or use Request.cancel() on the earlier call.

  • If the widget that owns the callback has been removed from the page when the answer arrives, the callback still runs. Check a flag or the attached state before touching the DOM.

The Developer Guide adds a claim that most browsers allow only two simultaneous connections. That figure comes from an older generation of browsers and HTTP/1.0 era limits; do not design around it, and measure on the target browsers instead.

The same-origin policy

A GWT-RPC call is an XMLHttpRequest like any other, so it obeys the browser’s same-origin policy. By default the entry point is the module base URL plus the relative path, which is on the same origin as the page, and nothing needs configuring. This is the reason the Bookshelf serves the host page, the compiled module and the servlet from one web application. The GWT FAQ states that the policy limits every form of server call, GWT-RPC included, and recommends either serving the application and its services from one server or putting a reverse proxy in front of both. Pointing setServiceEntryPoint at another origin is possible only if that server answers the CORS preflight (see ServiceDefTarget and RpcRequestBuilder and CORS), and the cross-site loading topic of the bootstrap (see Linkers and bootstrap) is a separate question: it concerns where the module’s JavaScript files are loaded from, not where the calls go.

A facade, callback chaining and plain Java presenters

Calling the proxy directly from every presenter spreads the plumbing. A small facade that wraps the proxy gives presenters one place to configure the request builder and the error handling, and lets them pass lambdas instead of anonymous AsyncCallback classes.

/** Facade: the only class that knows the RPC proxy. */
public class CatalogGateway {
  private final CatalogServiceAsync service = GWT.create(CatalogService.class);

  public CatalogGateway(int timeoutMillis) {
    ((ServiceDefTarget) service).setRpcRequestBuilder(new BookshelfRpcRequestBuilder(timeoutMillis));
  }

  public CatalogServiceAsync raw() {
    return service;
  }

  static <T> AsyncCallback<T> callback(Consumer<T> onSuccess, Consumer<Throwable> onFailure) {
    return new AsyncCallback<T>() {
      @Override
      public void onSuccess(T result) {
        onSuccess.accept(result);
      }

      @Override
      public void onFailure(Throwable caught) {
        onFailure.accept(caught);
      }
    };
  }

  public void books(int start, int length, Consumer<BookPage> ok, Consumer<Throwable> failed) {
    service.getBooks(start, length, callback(ok, failed));
  }

  public void book(long id, Consumer<Book> ok, Consumer<Throwable> failed) {
    service.getBook(id, callback(ok, failed));
  }

  /** Callback chaining: the second call starts from the first call's result. */
  public void firstBookOfPage(int start, Consumer<Book> ok, Consumer<Throwable> failed) {
    books(start, 5, page -> {
      if (page.getBooks().isEmpty()) {
        failed.accept(new IllegalStateException("empty page"));
      } else {
        book(page.getBooks().get(0).getId(), ok, failed);
      }
    }, failed);
  }
}

Polling and emulated server push

GWT-RPC is request and response: the server cannot call the browser. The classic workaround is polling with a Timer. The poller below asks for the catalogue’s revision number every few hundred milliseconds and reports a change:

public class RevisionPoller {
  private final CatalogServiceAsync service;
  private final IntConsumer onChange;
  private int last = -1;
  private boolean waiting;
  private final Timer timer = new Timer() {
    @Override
    public void run() {
      if (waiting) {
        return; // never stack requests when the server is slow
      }
      waiting = true;
      service.revision(new AsyncCallback<Integer>() {
        @Override
        public void onSuccess(Integer revision) {
          waiting = false;
          if (last >= 0 && revision != last) {
            onChange.accept(revision);
          }
          last = revision;
        }

        @Override
        public void onFailure(Throwable caught) {
          waiting = false; // keep polling; a real application would back off
        }
      });
    }
  };

  public RevisionPoller(CatalogServiceAsync service, IntConsumer onChange) {
    this.service = service;
    this.onChange = onChange;
  }

  public void start(int periodMillis) { timer.scheduleRepeating(periodMillis); }

  public void stop() { timer.cancel(); }
}

Tokens Meaning

Number of parameters.

Two protocol versions and what the client does with them

The server writes version 7 by default. The system property gwt.rpc.version (read by RPC.getRpcVersion() on every response) can raise it to 8. The client reader accepts versions 5 to 8; for versions before 8 it evaluates the payload with the JavaScript eval, for version 8 it parses it with JsonUtils.safeEval, which in 2.13.1 calls JSON.parse.

That difference is invisible until the page has a Content Security Policy without 'unsafe-eval'. With script-src 'self' 'unsafe-inline' and the default version 7, every call of the lab failed in the browser:

The 'unsafe-inline' in that policy was needed by the GWT bootstrap of the lab. Serialisable types

GWT’s idea of "serialisable" is its own, smaller than Java’s. It is decided at compile time from the types in the service interface, and enforced at run time by the policy file. A type may appear in a service method (as a parameter, a return type, a declared exception, or reachable from any of them through its fields) when at least one of the following holds, which is the list of the Developer Guide checked against the generator:

  • It is a primitive, String, Date (and the java.sql subclasses, which the policy lists), or a primitive wrapper.

  • It is an enum. Only the ordinal travels; the fields of the constants are not sent, and an enum cannot have a custom field serializer.

  • It is an array of serialisable types.

  • It is a user-defined class that is assignable to IsSerializable or java.io.Serializable (directly or through a superclass), whose non-final, non-transient instance fields are themselves serialisable, and that has a no-argument constructor of any visibility (or no constructor at all).

  • It has at least one serialisable subclass (the compiler then includes the subclasses it can see).

  • It has a custom field serializer (see Custom field serializers).

java.io.Serializable has been accepted since GWT 1.4, as the Developer Guide’s FAQ explains, on the condition that the policy file is deployed. IsSerializable, which older material requires, is still accepted and is equivalent.

How the servlet finds the policy

RemoteServiceServlet.getSerializationPolicy runs once per module base URL and strong name and caches the result:

  1. It strips the context path from the module base path and opens <module path><strong name>.gwt.rpc with ServletContext.getResourceAsStream. The module path must be inside the servlet’s own web application.

  2. If the file is not found, and the system property gwt.codeserver.port is set, it downloads the policy from the Super Dev Mode code server (see Policies in Super Dev Mode).

  3. If nothing is found, it logs a warning and falls back to the legacy 1.3.3 policy, which accepts only IsSerializable types.

Policies in Super Dev Mode

In development the Java server and the code server are separate processes. Two mechanisms exist, and the lab ran both.

The first one copies the policies. When the Maven plugin is configured with a launcherDir (the modular-webapp archetype does this), the code server copies each policy file next to the bootstrap script in that directory, and the Jetty profile env-dev adds that directory to its resource bases (see the archetype’s bookshelf-server/pom.xml). A comment in LauncherDir.java explains the purpose: the copies let the RemoteServiceServlet subclass find the policies in the module directory. In the lab the first page load compiled the module on demand and the calls worked.

The second one downloads them. Start the servlet container with -Dgwt.codeserver.port=9932 (the code server’s port) and RemoteServiceServlet.getCodeServerPolicyUrl returns http://localhost:<port>/policies/<strong name>.gwt.rpc. With the copies deleted, the first call logged:

Custom field serializers

A custom field serializer (CFS) replaces the automatic, reflection-based serialisation of one class with code you write. Use one when the class has no no-argument constructor (an immutable value type), when a more compact wire representation is worth the code, for a Java record, for a type from a library that you cannot change, and, as the next sections show, for your own exception classes on Java 17 and later. Most of the JRE collection classes in GWT have one, as do Date, the wrapper types and StackTraceElement.

The rules, from the Developer Guide and checked against CustomFieldSerializerValidator:

  • The class is named after the class it serialises with the suffix _CustomFieldSerializer and sits in the same package (Isbn_CustomFieldSerializer next to Isbn). Types of the JRE can be served from com.google.gwt.user.client.rpc.core.<package>.

  • It must be visible to the GWT compiler (in the source path), because the generated client code calls it. A serialiser in a server-only package is never used by the browser.

  • The compiler requires public static methods: void serialize(SerializationStreamWriter, T), void deserialize(SerializationStreamReader, T), and T instantiate(SerializationStreamReader) when the type is not default-instantiable.

  • The server prefers an instance: a CFS that also extends CustomFieldSerializer<T> and overrides serializeInstance, deserializeInstance, and (for custom instantiation) hasCustomInstantiateInstance returning true plus instantiateInstance. Every JRE serialiser of GWT does both and delegates the instance methods to the static ones.

  • The compiler rejects enums with a serializer: "Enumerated types cannot have custom field serializers."

The Developer Guide only says that a CFS should extend CustomFieldSerializer. A class that does that but has no static methods does not compile. The first version of the Bookshelf’s Isbn_CustomFieldSerializer had only the instance methods, and the compiler answered:

Records

A record needs the same treatment, because its components are final fields and it has no default constructor. The compiler accepts records in shared source (the Bookshelf compiles at -sourceLevel 17), but RPC fails without a serializer (see the probe table above).

public record Review(long bookId, int stars, String comment) implements Serializable {}

public final class Review_CustomFieldSerializer extends CustomFieldSerializer<Review> {
  public static void deserialize(SerializationStreamReader reader, Review instance) { }

  public static Review instantiate(SerializationStreamReader reader) throws SerializationException {
    return new Review(reader.readLong(), reader.readInt(), reader.readString());
  }

  public static void serialize(SerializationStreamWriter writer, Review instance) throws SerializationException {
    writer.writeLong(instance.bookId());
    writer.writeInt(instance.stars());
    writer.writeString(instance.comment());
  }
  // the four instance methods delegate to the static ones, as in Isbn_CustomFieldSerializer
}

A type-checked server-side serializer

A server must deserialise whatever bytes a browser sends, before the service method can reject them. That makes deserialisers a target for denial-of-service payloads (very large or deeply nested values). Since GWT 2.4 a CFS can have a server-only twin, <Name>_ServerCustomFieldSerializer extends ServerCustomFieldSerializer<T>, whose methods receive the expected generic parameter types and are supposed to read nested objects with the type-checking readObject overloads. The built-in HashMap_ServerCustomFieldSerializer is the reference.

The lookup of the name replaces the first occurrence of the text client in the fully-qualified class name with server. com.example.bookshelf.shared.Isbn has no client in it, so its twin must be named com.example.bookshelf.shared.Isbn_ServerCustomFieldSerializer, in the same package as the shared class. That is possible without GWT seeing it: put the class in the server module (a split package on the class path), where the GWT source path never reaches.

bookshelf-server: src/main/java/com/example/bookshelf/shared/Isbn_ServerCustomFieldSerializer.java (excerpt)
package com.example.bookshelf.shared; // the shared package, but in the server module

public final class Isbn_ServerCustomFieldSerializer extends ServerCustomFieldSerializer<Isbn> {
  @Override
  public boolean hasCustomInstantiateInstance() {
    return true;
  }

  @Override
  public Isbn instantiateInstance(ServerSerializationStreamReader reader, Type[] expectedParameterTypes,
      DequeMap<TypeVariable<?>, Type> resolvedTypes) throws SerializationException {
    return Isbn.of(reader.readString());
  }

  @Override
  public void deserializeInstance(ServerSerializationStreamReader reader, Isbn instance,
      Type[] expectedParameterTypes, DequeMap<TypeVariable<?>, Type> resolvedTypes) { }

  @Override
  public void deserializeInstance(SerializationStreamReader reader, Isbn instance) { }

  @Override
  public void serializeInstance(SerializationStreamWriter writer, Isbn instance) throws SerializationException {
    writer.writeString(instance.value());
  }
}

With a temporary System.out.println in instantiateInstance, the container log showed the twin used when the saveBook request (which carries a Book with an ISBN) arrived. Isbn holds only a string, so there is nothing to type-check here; the example shows where the class goes. A twin that reads collections or other objects must pass the expected type to readObject, as the built-in ones do; getting that wrong is what leaves the server exposed. The unit that does the type check for the normal path is ServerSerializationStreamReader, which throws SerializedTypeViolationException when a value is not of the expected type (see the table of exceptions).

Java 17 and later: exceptions that cannot be serialised

GWT-RPC serialises an exception through reflection, like any other class, and every exception inherits the private fields of java.lang.Throwable. Since JDK 17 the module system denies reflective access to the private fields of java.base classes from unnamed modules unless the JVM is started with --add-opens. The consequence is a failure that is easy to hit and hard to diagnose. This is open upstream as gwtproject/gwt issue 9793 ("Serialization fails with Unable to make field private java.lang.String java.lang.Throwable.detailMessage accessible", opened on 2023-01-09 against GWT 2.10.0 on Java 17, still open when this page was checked on 2026-10-09, with three comments and no fix).

1. Open the package for the servlet container’s JVM. The option that GWT’s own exceptions need:

# any container started by a script or an executable JAR
java --add-opens java.base/java.lang=ALL-UNNAMED -jar bookshelf.jar

With the option, the same getBook(999) call returned the exception, with the type, the id and the message written by reflection:

The option has to reach the JVM that hosts the servlet container: MAVEN_OPTS for the Maven Jetty plugin was the form that was run. Tomcat reads CATALINA_OPTS, and an application server has its own JVM option file; those forms were not run. Note that the module is java.base, package java.lang, target ALL-UNNAMED: the exceptions of a library (java.util, for example) would need their own package.

2. Give each of your own exceptions a custom field serializer. A CFS replaces the reflective walk over the class and its superclasses, so the private fields of Throwable are never touched. The serializer of BookNotFoundException writes the id and the constructor rebuilds the message:

public final class BookNotFoundException_CustomFieldSerializer
    extends CustomFieldSerializer<BookNotFoundException> {
  public static void deserialize(SerializationStreamReader reader, BookNotFoundException instance) {
    // Nothing left to read: instantiate() consumed the id.
  }

  public static BookNotFoundException instantiate(SerializationStreamReader reader) throws SerializationException {
    return new BookNotFoundException(reader.readLong());
  }

  public static void serialize(SerializationStreamWriter writer, BookNotFoundException instance)
      throws SerializationException {

JPA, JDO and DTOs: the 2.10.1 and 2.11 change

Persistence frameworks "enhance" entity classes on the server with extra fields (for example the state of a lazy proxy). Before 2.10.1, GWT-RPC had a feature for that case: a class annotated with javax.jdo.annotations.PersistenceCapable(detachable=true) or javax.persistence.Entity, or named in the rpc.enhancedClasses property, was an enhanced class. The server serialised the fields that the client did not know with Java serialisation into one Base64 string, sent it to the browser as an opaque blob, and deserialised it again when the browser sent the object back. That is a Java deserialisation of data controlled by the client, which is a known class of remote-code-execution vulnerabilities. Issue gwtproject/gwt#9709 ("Java Deserialization vulnerability in GWT-RPC") reported it. The maintainers' note at the top of the issue lists the mitigation that follows and two follow-up issues, signing the payloads (#9880) and not serialising such classes at all (#9881), which were still waiting for contributors when the note was written.

The 2.11.0 release (2024-01-09) disabled it by default and added a warning when it is in use, and 2.10.1 (2024-01-09) backported the change. The Developer Guide still has a section "Serializing Enhanced Classes" written for GWT 2.0 that does not mention this, so read it as history.

Use data transfer objects

The recommendation of the Developer Guide’s neighbour article, "Using GWT with Hibernate" (2009), still stands and is stronger now: do not send entities. Entities carry lazy collections and proxies (accessing one raises LazyInitializationException or fails to serialise), reference whole graphs, carry columns the browser must never see, and bind the wire format to the database schema. The article compares three strategies: hand-written DTOs and copy methods, the Dozer mapper, and the Gilead library that replaces proxies automatically. This page did not evaluate Dozer or Gilead; the article’s own conclusion is that DTOs are the simple, predictable approach and cost the copy code. (Its sample DTO also holds an account password; do not copy that. A DTO is a list of what the screen needs, and a password hash is never on it.)

The Bookshelf keeps the entity out of the shared module and maps it with a function that lists the fields the browser may see:

bookshelf-server: a JPA entity that never reaches the wire, and its mapper
/** Server-only persistence entity: never appears in a RemoteService signature. */
@Entity
public class BookEntity {
  @Id
  @GeneratedValue
  private Long id;

  @Column(nullable = false)
  private String title;

  private String author;
  private int year;
  private int copies;

  @OneToMany(mappedBy = "book", fetch = FetchType.LAZY)
  private List<LoanEntity> loans = new ArrayList<>();
  // getters omitted
}

/** Copies exactly the fields the browser needs, and nothing that is lazy or confidential. */
public final class BookMapper {
  private BookMapper() {}

  public static Book toDto(BookEntity entity) {
    return new Book(entity.getId(), entity.getTitle(), entity.getAuthor(), entity.getYear(), entity.getCopies());
  }
}

The classes compiled against jakarta.persistence-api 3.1.0 with javac --release 21; they were not run against a database. Do the mapping inside the transaction (before lazy associations close), return a new ArrayList<Book>, and keep LoanEntity.memberEmail and its like out of every DTO. For many entities a mapping generator is less error-prone than hand-written copies; the server side of this is on Lombok and MapStruct, and the persistence side on Spring Data JPA and Hibernate.

Security of the RPC channel

GWT-RPC exposes your Java methods to the network. The checklist below is the minimum; the section’s security pages (SafeHtml and XSS and XSRF, RPC and server security) treat the topics in depth.

  • Authorise every method on the server. The browser can call any method of the service interface with any argument, whether or not a button exists for it. The Bookshelf’s saveBook checks getThreadLocalRequest().getUserPrincipal() and throws the declared AccessDeniedException; in the lab, without a principal, the call ended with //EX[1,["com.example.bookshelf.shared.AccessDeniedException/35684112"],0,7]. With Spring Security or the container’s security constraints, authorise by role per method (see Spring Security). Never accept an "isAdmin" flag or a user id from a parameter as proof.

  • Validate every argument again. The page size cap of getBooks and the title check of saveBook are examples. Bean Validation constraints on the shared DTO are the natural place (see Validation).

  • Protect state-changing calls against XSRF with the token mechanism below.

  • Use HTTPS and set the session cookie attributes your container supports (Secure, HttpOnly, SameSite). RPC carries session cookies like any other request.

  • Never put credentials in method parameters. The Developer Guide’s example emptyMyInbox(String username, String password) is an illustration of the call syntax and a bad design; authenticate through the container or the framework and identify the user from the session.

  • Keep secrets and personal data out of DTOs, because every field of a serialised class leaves the server. The transient keyword and a dedicated DTO are both guards.

  • Treat the policy file as part of the build artefact, deploy it with the module it belongs to, and do not enable gwt.codeserver.port or gwt.enhancedClasses.enabled in production.

  • Do not trust the response either if it can come from another origin: a client that follows a cross-origin entry point evaluates (version 7) or parses (version 8) what that server sends.

  • Set a CSP that fits GWT’s payload (see the section on the wire and Linkers and bootstrap).

GWT-RPC has some built-in defences that are easy to over-rate. The response begins with //OK or //EX, so a <script src="..."> include of the URL sees a comment and a cross-site script cannot read the data this way (CVE-2007-2378, "JavaScript hijacking", concerns JSON that is exchanged without any protection scheme). The X-GWT-Permutation header is a custom header, so a plain cross-site <form> cannot set it. The servlet answers only POST. Content-Disposition: attachment is set on every response. None of these identifies the caller, and a request replayed by curl passes all of them.

XSRF protection

The token mechanism of GWT 2.3 and later binds each protected call to the user’s session. A service interface extends XsrfProtectedService instead of RemoteService (or a method carries @XsrfProtect; @NoXsrfProtect exempts one), the implementation extends XsrfProtectedServiceServlet (the jakarta package in the Bookshelf), and a second servlet, XsrfTokenServiceServlet, hands out tokens. The default implementation derives the token from the session cookie (the Developer Guide describes an MD5 hash of the cookie value, stateless, which works because an attacker cannot read the cookie), and the gwt.xsrf.session_cookie_name context parameter names that cookie for the token servlet and for every protected servlet. A session must exist before the first token request, which the scratch application ensured with a small filter that calls getSession(true). Method-level annotations override interface-level ones.

<context-param>
  <param-name>gwt.xsrf.session_cookie_name</param-name>
  <param-value>JSESSIONID</param-value>
</context-param>

<servlet>
  <servlet-name>xsrfServlet</servlet-name>
  <servlet-class>com.google.gwt.user.server.rpc.jakarta.XsrfTokenServiceServlet</servlet-class>
</servlet>
<servlet-mapping>
  <servlet-name>xsrfServlet</servlet-name>
  <url-pattern>/bookshelf/xsrf</url-pattern>
</servlet-mapping>

The client fetches a token first and attaches it to the protected proxy through HasRpcToken:

XsrfTokenServiceAsync xsrf = GWT.create(XsrfTokenService.class);
((ServiceDefTarget) xsrf).setServiceEntryPoint(GWT.getModuleBaseURL() + "xsrf");
xsrf.getNewXsrfToken(new AsyncCallback<XsrfToken>() {
  @Override
  public void onSuccess(XsrfToken token) {
    ((HasRpcToken) catalog).setRpcToken(token);   // every later call carries it
    onReady.run();
  }

  @Override
  public void onFailure(Throwable caught) {
    GWT.log("Cannot get an XSRF token", caught);
  }
});

In the scratch Bookshelf (the same Jetty setup as the lab, checked when the project was built for this section) the token request and the protected call answered 200, and a call without a token answered with the exception of the protocol:

//EX[2,1,["com.google.gwt.user.client.rpc.RpcTokenException/2345075298","Invalid RPC token (XSRF token missing)"],0,7]

That response reaches the browser only when the JVM can serialise exceptions (see Java 17 and later: exceptions that cannot be serialised); otherwise it is the generic 500. AbstractXsrfProtectedServiceServlet validates the token inside onAfterRequestDeserialized, so an override of that hook in a protected servlet must call super.onAfterRequestDeserialized(rpcRequest) or the check disappears. The full treatment, with RpcTokenExceptionHandler and token renewal, is on the XSRF, RPC and server security page.

A servlet is shared between requests

One servlet instance serves all requests concurrently. getThreadLocalRequest() and getThreadLocalResponse() are thread-locals and are valid only on the request thread. Keep per-request state in local variables, make shared fields thread-safe (the lab’s in-memory repository uses a ConcurrentSkipListMap and an AtomicInteger), and do not hand the request object to another thread.

Where older material is outdated

The Developer Guide and the tutorial still teach the right architecture, with details from the Ant era. Several statements have been overtaken:

  • Direct-Eval RPC. The Server Communication page still has a section on it, while the 2.10.0 release notes say deRPC was removed. The page itself calls the feature a failed experiment and discourages its use.

  • The sample callback. The raw AsyncCallback of "Actually making a call" does not compile (see the pitfalls). Its emptyMyInbox(username, password) also sends credentials as arguments, which is a design to avoid.

  • Printing caught.getMessage(). The Developer Guide’s asynchronous example shows the message of the exception to the user. For a StatusCodeException that is the status, the status text and the whole response body.

  • Serializing enhanced classes. The section describes the GWT 2.0 support for JPA and JDO classes. Since 2.10.1 and 2.11.0 the feature is off by default and the servlet refuses the service (see JPA, JDO and DTOs: the 2.10.1 and 2.11 change).

  • gwt-servlet.jar in war/WEB-INF/lib, webAppCreator, ant war and the embedded Jetty of development mode. Today the server classes come from org.gwtproject:gwt-servlet or gwt-servlet-jakarta with Maven; the 2.13.0 release notes say the development mode server now serves only static files, so you run your own container; webAppCreator is deprecated since 2.11.

  • Two connections per browser. The advice about parallel calls assumes an old limit.

  • Exceptions in the tutorials. DelistedException and any similar declared exception need the measures of Java 17 and later: exceptions that cannot be serialised on a current JDK.

The 2007 book "GWT in Action" (Hanson and Tacy, Manning, first edition, GWT 1.3 and 1.4) devotes two chapters to the same ground: the asynchronous model and the service types, then the client architecture around them (a facade, callback chaining, polling, custom field serializers). The concepts all still hold, and this page’s facade, chaining, poller and serializers are their modern form. The details differ:

  • It requires the IsSerializable marker; java.io.Serializable has been accepted since GWT 1.4.

  • It declares collection element types with a Javadoc annotation (@gwt.typeArgs); generics replaced it in GWT 1.5, and the compiler now warns about raw collections.

  • It sets the URL with ServiceDefTarget.setServiceEntryPoint and GWT.getModuleBaseURL(); @RemoteServiceRelativePath replaced that, although the setter still exists.

  • Its examples use Java 1.4 syntax, the javax.servlet API, hosted mode and servlets that block to emulate server push.

  • The security topics of this page (policy files, XSRF tokens, CSP, deserialisation of enhanced classes, Java 17) did not exist or were not covered.

What changed recently

  • 2.10.0 (2022-06-09): the rpc.XserializeFinalFields property turns on experimental final-field serialisation; LinkedHashSet may be serialised without a policy; deRPC is removed.

  • 2.10.1 and 2.11.0 (both 2024-01-09): JPA/JDO enhanced classes are not serialisable by default, with a compile warning; 2.11.0 adds the Jakarta artifacts gwt-servlet-jakarta (and requestfactory-server-jakarta) and makes the custom field serializers of GWT ready for Java 17.

  • 2.12.0 (2024-10-29): fixes for Content Security Policy issues in linkers, development mode and, according to the notes, workarounds for GWT-RPC payloads (see the wire section).

  • 2.13.0 (2026-02-11) and 2.13.1 (2026-06-19): the release notes list no RPC-specific change. The development mode server serves only static files (2.13.0), which matters when a tutorial assumes the embedded Jetty.

  • Open: gwtproject/gwt issue 9793 (exceptions on Java 17 and later) was still open on 2026-10-09.
