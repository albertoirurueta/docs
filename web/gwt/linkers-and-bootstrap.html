Linkers & Bootstrap

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against GWT 2.13.1 (2026-06-19), gwt-maven-plugin 1.3.0 and the Jakarta Servlet 6 stack of the modular-webapp archetype, checked on 2026-10-09. The compiler ran on JDK 21 with -sourceLevel 17. It is build and tooling knowledge with a runtime half: the linkers run inside the compiler on the developer machine or in CI, and the script they write, <module>.nocache.js, runs in the browser before any of your client code. Nothing on this page is compiled from your Java source except the tiny entry points of the lab modules. Every command, file listing, console message and DOM dump below comes from a private copy of the Bookshelf scenario of this section, extended with the lab modules printed on the page. They were compiled with com.google.gwt.dev.Compiler of 2.13.1 and loaded in headless Chrome 155 from two static Python servers (one acting as the host page’s origin, one as a CDN). Only Chrome was run: Firefox and Safari were not, and the Content Security Policy results in particular are Chrome results. The 32-character content hashes that name the permutation files are shown as GECKO_HASH and SAFARI_HASH, and the nonces are placeholders (NONCE_PLACEHOLDER).

The compiler turns Java into JavaScript, but a browser cannot simply load "the" JavaScript of a GWT application, because there are several versions of it (one per permutation) and the right one depends on the browser and the locale. The linker is the stage of the compiler that decides how the compiled code is packaged and how it finds its way into the page. It writes the small bootstrap script that you put in your host page, it names and places the permutation files, and it writes the side files (policy files, symbol maps, reports). Most applications never think about it, because the default linker does the right thing. You need this page when you load a module from a CDN, put two modules on one page, tighten the Content Security Policy, produce a single file, or add a build step that must see every output file.

Where linkers sit in the build

The linker stage comes last in the compile: the compiler parses the Java, resolves deferred binding, compiles one JavaScript program per permutation (see Compiler and compilation), and then hands everything to the linkers. The Developer Guide describes the subsystem like this: each output file is an artifact, and the linkers decide each file’s name, location and content. The files are classified by EmittedArtifact.Visibility:

Table 1. Kinds of linker output
Visibility Meaning Where it lands with -war, -deploy, -extra

Public

Files meant to be downloaded by browsers: the bootstrap, the permutation files, images and CSS of the public path.

The module directory under -war

Source

Files served only during development: Java source and source maps for the browser debugger (the Developer Guide’s description).

Not part of a production module directory

Deploy

Files the application server needs but browsers must not get, such as the GWT-RPC serialization policy manifest and the symbol maps.

-deploy; the Maven plugin puts them in target/gwt/deploy (a WEB-INF/deploy directory appears under -war too when you run the compiler as in the lab)

Private

Optional reports about the compile, such as the compile report.

-extra

Linkers belong to three categories, and the module XML names them:

  • A primary linker is the main one and writes the bootstrap. Only one primary linker runs per compile: adding a second primary linker with <add-linker> replaces the first.

  • Pre-linkers run before the primary linker, post-linkers run after it. Both categories are additive.

  • The category is declared on the linker class with @LinkerOrder(Order.PRE), @LinkerOrder(Order.PRIMARY) or @LinkerOrder(Order.POST).

A linker has a short name that is defined once with <define-linker name="..." class="..."/> and switched on with <add-linker name="..."/>. The Core module of 2.13.1 (inherited by User, so by every application) defines the standard ones and activates the default set:

The linker lines of Core.gwt.xml in 2.13.1
<define-linker name="sso" class="com.google.gwt.core.linker.SingleScriptLinker" />
<define-linker name="std" class="com.google.gwt.core.linker.IFrameLinker" />
<inherits name="com.google.gwt.core.XSLinker" />              <!-- defines "xs" -->
<inherits name="com.google.gwt.core.CrossSiteIframeLinker" /> <!-- defines "xsiframe" and "direct_install" -->

<!-- std and xs linkers are deprecated and will emit a warning, which can be turned off -->
<define-configuration-property name="iframe.linker.suppressDeprecationWarning" is-multi-valued="false" />
<set-configuration-property name="iframe.linker.suppressDeprecationWarning" value="false" />

<define-linker name="soycReport" class="com.google.gwt.core.linker.SoycReportLinker" />
<define-linker name="symbolMaps" class="com.google.gwt.core.linker.SymbolMapsLinker" />

<add-linker name="xsiframe" />
<add-linker name="soycReport" />
<add-linker name="symbolMaps" />

Source: GWT 2.13.1 source — Core.gwt.xml, GWT — Linkers: introduction

That is the whole reason a plain module has the xsiframe linker: no line in your module asks for it. The names xsiframe, direct_install, sso, std and xs are the available primary linkers, and the Developer Guide lists them in exactly that way.

The order in which linkers run

Running the lab module with -logLevel DEBUG shows the order in which 2.13.1 invokes the linkers for one permutation. The extra Precache manifest line is the custom linker of Custom linkers:

Linker invocation order (compiler log, trimmed)
   Invoking Linker RPC policy file manifest
   Invoking Linker Cross-Site-Iframe
   Invoking Linker Precache manifest
   Invoking Linker RPC log linker
   Invoking Linker Export CompilationResult symbol maps
   Invoking Linker Emit compile report artifacts

The first line is a pre-linker, the second is the primary linker, and the rest are post-linkers. The same six lines are repeated for every permutation and once more for the final link after all permutations are compiled. The Developer Guide says post-linkers run "in reverse lexical order of their name". The 2.13.1 source and this log say otherwise: StandardLinkerContext collects the post-linkers in the order in which their add-linker elements were processed and then reverses that list ("Get all the post-linkers IN REVERSE ORDER"), and the Javadoc of Linker says the exact order is determined by the order of the add-linker tags. A linker added last (here precacheManifest, added by the module that inherits it) therefore runs first among the post-linkers. That matters when one post-linker reads the output of another: write the dependency into the order of your inherits and add-linker lines, and look at the DEBUG log to confirm it.

Source: GWT 2.13.1 source — StandardLinkerContext.java, Javadoc — Linker

The bootstrap sequence

The file you reference from the host page, bookshelf/bookshelf.nocache.js, is the selection script. It is written by the primary linker from a template (CrossSiteIframeTemplate.js for the default linker) into which the linker splices a set of helper scripts: the permutation lookup, the property providers, the base-URL computation and the install code. Its job is small and specific: work out which compiled script this browser needs, load it into an isolated place in the page, and call onModuleLoad.

sequenceDiagram autonumber participant B as Browser participant H as Host page participant N as bookshelf.nocache.js participant F as Hidden iframe participant S as Server or CDN B->>H: parse the host page H->>S: GET bookshelf.nocache.js (revalidated, never cached long) S-->>N: selection script N->>N: sendStats bootstrap begin, processMetas (gwt:property, gwt:onLoadErrorFn) N->>N: computeScriptBase (baseUrl meta, own script src, base element, page URL) N->>N: run property providers (locale, user.agent) and pick the strong name N->>H: add link elements for the module stylesheets alt installCode is true (default, obfuscated output) N->>S: GET STRONGNAME.cache.js through a script element in head S-->>N: module.onScriptDownloaded with an array of strings N->>F: wait for body, create the iframe, install each string as script text else installCode is false (direct_install, PRETTY, DETAILED) N->>F: wait for body, create the iframe, add a script element with src F->>S: GET STRONGNAME.cache.js end F->>F: evaluate the module, then gwtOnLoad F->>H: run every entry point (onModuleLoad)

The numbers in the diagram correspond to what the template does, in this order (the helper names are the function names visible in a -style PRETTY build of bookshelf.nocache.js):

Table 2. What the selection script does, in order
Step Function in the script What it does

1

sendStats('bootstrap', 'begin')

Reports the first startup event to window.__gwtStatsEvent, if the page defined one (see Watching the sequence: __gwtStatsEvent).

2

processMetas()

Reads the meta tags of the host page: gwt:property, gwt:onPropertyErrorFn and gwt:onLoadErrorFn. A meta name that carries another module’s prefix (other::gwt:property) is skipped, and this module’s prefix (bookshelf::) is removed first.

3

computeScriptBase()

Finds the module base URL (the directory that holds the nocache.js), in this order: a baseUrl entry from a gwt:property meta tag, the src of the script element whose URL contains <module>.nocache.js, the last base element, and as a last resort the directory of the page URL. 4

getCompiledCodeFilename()

Runs the property providers, looks the values up in the permutation map that the linker embedded, and returns the file name STRONGNAME.cache.js relative to the module base. A strong name may carry a :N suffix, which the script splits into the file name and a "soft permutation" number.

5

the Super Dev Mode hook

If the page is served over http: or file: and sessionStorage holds a Super Dev Mode URL for this module, the script loads that URL instead and stops (see The Super Dev Mode hook).

6

Adds one link rel="stylesheet" element to the head for every <stylesheet src="..."/> of the module, unless another module on the page already added the same URL.

7

Loads the compiled code, the part that depends on installCode: the next section.

The host page the sequence assumes

A host page is any HTML that has a script element pointing at the nocache.js. The selection script waits for document.body before it creates the iframe, so the tag may sit in the head. Three details of the template are worth knowing:

  • The iframe gets the module name as its id (scriptFrame.id = 'bookshelf'). Do not give another element that id.

  • The iframe is positioned off screen (left: -1000px) and not hidden with display: none, because the comment in installLocationIframe.js says some browsers do not run code in a display: none frame.

  • The page should be in standards mode (<!doctype html>): the script reads compatMode to decide whether the frame it creates gets a doctype.

The meta tags and the module base URL

The host page can configure the bootstrap with three meta names. They are all read by processMetas(), they all accept a module prefix, and the values are used exactly as the source shows.

The Super Dev Mode hook

The default linker also emits the hook that makes Super Dev Mode work with the same host page. When the page protocol is http: or file: and sessionStorage has an entry named __gwtDevModeHook:<module>, the script validates the stored URL against a whitelist and loads it instead of the compiled code. The default whitelist, from CrossSiteIframeLinker, is http://(localhost|127\.0\.0\.1)(:\d+)?/.*; anything else is ignored and logged as Ignoring non-whitelisted Dev Mode URL: .... Three configuration properties control the hook: devModeRedirectEnabled (default true), devModeUrlWhitelistRegexp and the protocol rule, which a custom linker can change by overriding getJsDevModeRedirectHookPermitted. The Javadoc of the protocol hook recommends refusing the redirect on https and on host names that end users visit; see Development mode and debugging for the Super Dev Mode workflow and its security notes. The query parameter ?gwt.codesvr= belongs to the classic Dev Mode and makes the script load <module>.devmode.js instead of a permutation; the classic plugin-based mode is legacy.

xsiframe: the default

xsiframe (class CrossSiteIframeLinker, description "Cross-Site-Iframe") "uses an iframe to hold the code and a script tag to download the code". Because the code is fetched with a script element and never with XMLHttpRequest, the module directory can be on another origin (see Cross-site loading), and because the compiled code lives in its own iframe the module’s globals do not collide with the page’s or with another module’s, and code-split fragments can be installed into the same frame later.

The comment in installScriptEarlyDownload.js describes the mechanism: the download starts immediately, and the contents are installed into the iframe once the document body is ready. The consequence that matters today is the second half of the table: inline script text is not allowed by a strict Content Security Policy. That is why direct_install exists.

Two further properties of xsiframe are worth knowing. First, it does not support <script src="..."/> elements in a *.gwt.xml file, because it has no place to put them in the host page: the compile fails unless you set xsiframe.failIfScriptTag to FALSE (see Pitfalls). Second, it uses the ScriptTagLoadingStrategy for code splitting, because CrossSiteIframeLinker.gwt.xml switches the AsyncFragmentLoader.LoadingStrategy with <when-linker-added name="xsiframe"/>; the default strategy of every other linker, XhrLoadingStrategy, downloads fragments with XMLHttpRequest. The <when-linker-added> condition was added in 2.9.0, according to the release notes.

direct_install

direct_install (class DirectInstallLinker) "adds a script tag directly to the iframe rather than downloading the JavaScript code as a list of strings"; its Javadoc says it is "exactly like CrossSiteIframeLinker except that it defaults to `installCode=false`". You turn it on with one line in the module:

Switching to direct_install in the module XML
<add-linker name="direct_install" />

Because the primary linker is replaced, the other linkers (the policy manifest, symbol maps and so on) still run. The 2.5.1 release notes introduced the linker with the remark that applications built with it "should work in a page where inline scripts are forbidden", which was written for Chrome extensions and is exactly the Content Security Policy case. The lab confirms it for 2.13.1, with one exception (code splitting) that is the subject of Content Security Policy.

The price of the src install is visible in the cross-site section: the script element carries crossOrigin='' when the page has a host name, and so a module directory on another origin needs an Access-Control-Allow-Origin header.

Cross-site loading

The book’s chapter on the bootstrap describes a separate "cross-site" loader, nocache-xs.js, for modules hosted on a different site from the host page. With the default linker there is no second file: the ordinary nocache.js is cross-site capable, and the host page just uses an absolute URL. The module base is computed from the script element’s src, so every other file (permutations, fragments, policy files, stylesheets) is requested from the same remote directory.

Two more things cross sites with the module and are not solved by the linker. And a script loaded from another origin runs with the full authority of the host page that includes it, so load a module only from an origin you trust as much as your own server.

The unprefixed gwt:property sets English for every module that does not have its own tag, and loans::gwt:property overrides it for the loans module only. Removing the prefixed tag and setting the first one to Spanish gave locale=es in both. Source: GWT 2.13.1 source — processMetas.js

The things that make this work and the things to watch:

  • The registry. Every module adds an entry to the page-wide window.__gwt_activeModules object with moduleName, moduleBase, bindings and canRedirect; Super Dev Mode reads it, and so can your monitoring.

  • Names must differ. The module function (window.shelf, window.loans) and the iframe id are derived from the module name. Give every module on a page a different rename-to short name, and never reuse the name as an element id.

  • Stylesheets are deduplicated. loadExternalStylesheets() records each URL in window.__gwt_stylesLoaded and adds a link element only once, so two modules that inherit the same theme share one CSS file.

  • Code is not shared. Each module is compiled as a separate program with its own copy of every library class it uses. Measured with the lab modules, a Counter permutation (it uses the Button widget) is about 35.8 KB, a Badge permutation about 10.7 KB, and one module that inherits both is about 36.0 KB, instead of about 46.4 KB for the two scripts. With a real widget library the duplication is in the hundreds of kilobytes.

  • State is not shared. Static fields live in each module’s own iframe. If the modules must talk to each other, use the page: a JsInterop export (see JsInterop) or DOM events.

  • Properties are per module. A locale that one module supports may be rejected by another; the gwt:onPropertyErrorFn meta tag, which also accepts the module prefix, is the hook.

The alternative to several modules is one module with several entry points (<entry-point> elements, or an entry point that decides by looking at the page) and, for the code that is rarely needed, code splitting with GWT.runAsync, which Code splitting covers. Choose several modules when the pieces are owned by different teams or released at different times; choose one when they share code.

Dynamic host pages

The host page does not have to be a static file. The Developer Guide article on dynamic host pages shows a servlet that writes the page, and the reason is practical: the server can decide per request whether to include the nocache.js tag at all (only for a logged-in user, for instance), and it can put initial data into the page so that the module does not need a first RPC. The article’s steps for a static host page also describe the bootstrap of its time, which included an MD5-named .cache.html file; with the default linker the file is .cache.js.

A servlet host page that keeps the bootstrap tag and passes data as inert JSON

     .append("<meta name=\"gwt:property\" content=\"locale=en\">")

Source: GWT — Article: Dynamic Host Page (servlet as host page)

This snippet was not compiled or run (the nonce mechanics were measured with static host pages, see Content Security Policy), and it leaves out the data block on purpose. The article puts the user’s e-mail address into a second script element by string concatenation, which is a script-injection hole for any value that contains </script>; the server integration page has the corrected version (an inert application/json data block with escaping) and the client side that reads it with setText. Custom linkers

When the standard output is not enough, you write your own linker. The reasons are mostly build-side: listing the output files for a service worker or an offline cache, adding a file such as a version stamp or a hash manifest, stripping files that must not be deployed, pre-compressing, or changing how the bootstrap works. The Developer Guide gives the recipe in four sentences, and the Javadoc of Linker fills in the rest:

  1. Extend com.google.gwt.core.ext.Linker or, usually, com.google.gwt.core.ext.linker.AbstractLinker, which adds the emitString, emitBytes and emitInputStream helpers.

  2. Annotate the class with @LinkerOrder(Order.PRE | PRIMARY | POST).

  3. Annotate it with @Shardable. Non-shardable linkers are deprecated according to the Javadoc, and a shardable linker implements link(logger, context, artifacts, onePermutation), which is called once per compiled permutation (with onePermutation true) and once more after all of them (with onePermutation false, and only the artifacts that are @Transferable).

  4. Register it with <define-linker name="short_name" class="fully.qualified.Class"/> and switch it on with <add-linker name="short_name"/>. The name must be a valid Java identifier. A second define-linker with the same name redefines the linker.

Source: GWT — Linkers: Custom linkers, GWT 2.13.1 source — Linker.java, Javadoc — AbstractLinker

A precache manifest linker

The Bookshelf wants an offline shell, and a service worker needs the list of files to precache. The module directory contains hashed permutation files, so the list changes with every build and must be generated. This linker is a post-linker that waits for the final link, collects every public file, and writes <module>.precache.json:

PrecacheManifestLinker.java: a post-linker that lists the public files
package com.example.bookshelf.linker;

import com.google.gwt.core.ext.LinkerContext;
import com.google.gwt.core.ext.TreeLogger;
import com.google.gwt.core.ext.UnableToCompleteException;
import com.google.gwt.core.ext.linker.AbstractLinker;
import com.google.gwt.core.ext.linker.ArtifactSet;
import com.google.gwt.core.ext.linker.EmittedArtifact;
import com.google.gwt.core.ext.linker.EmittedArtifact.Visibility;
import com.google.gwt.core.ext.linker.LinkerOrder;
import com.google.gwt.core.ext.linker.LinkerOrder.Order;
import com.google.gwt.core.ext.linker.Shardable;

import java.io.IOException;
import java.io.InputStream;
import java.util.TreeMap;

/** Post-linker that lists the public files of a module so a service worker can precache them. */
@LinkerOrder(Order.POST)
@Shardable
public class PrecacheManifestLinker extends AbstractLinker {
  @Override
  public String getDescription() {
    return "Precache manifest";
  }

  @Override
  public ArtifactSet link(TreeLogger logger, LinkerContext context, ArtifactSet artifacts,
      boolean onePermutation) throws UnableToCompleteException {
    ArtifactSet result = new ArtifactSet(artifacts);
    if (onePermutation) {
      // Per-permutation call: the nocache.js bootstrap does not exist yet.
      return result;
    }

    TreeMap<String, Long> files = new TreeMap<>();
    for (EmittedArtifact artifact : artifacts.find(EmittedArtifact.class)) {
      if (artifact.getVisibility() == Visibility.Public) {
        files.put(artifact.getPartialPath(), sizeOf(logger, artifact));
      }
    }

    StringBuilder json = new StringBuilder("{\n  \"module\": \"")
        .append(context.getModuleName()).append("\",\n  \"files\": [\n");
    String separator = "";
    for (var entry : files.entrySet()) {
      json.append(separator).append("    {\"path\": \"").append(entry.getKey())
          .append("\", \"bytes\": ").append(entry.getValue()).append('}');
      separator = ",\n";
    }
    json.append("\n  ]\n}\n");

    result.add(emitString(logger, json.toString(), context.getModuleName() + ".precache.json"));
    return result;
  }

  private static long sizeOf(TreeLogger logger, EmittedArtifact artifact)
      throws UnableToCompleteException {
    try (InputStream in = artifact.getContents(logger)) {
      return in.readAllBytes().length;
    } catch (IOException e) {
      logger.log(TreeLogger.ERROR, "Cannot read " + artifact.getPartialPath(), e);
      throw new UnableToCompleteException();
    }
  }
}

The linker class is not client code. It must not be inside a <source path> of any module (the compiler would try to translate it), it needs gwt-dev on its compile classpath, and it must be on the classpath of the compiler when the module is built. In a Maven project the simplest layout is a separate *-linker module (or a library jar) that the gwt-app module depends on; the lab compiled the class with javac --release 17 against gwt-dev and put the output directory on the compiler classpath. The registration lives in a small module that applications inherit:

PrecacheManifest.gwt.xml: define and add the linker
<module>
  <define-linker name="precacheManifest" class="com.example.bookshelf.linker.PrecacheManifestLinker" />
  <add-linker name="precacheManifest" />
</module>

The application module then only needs <inherits name="com.example.bookshelf.linkers.PrecacheManifest"/>. Compiled with the Badge module, the module directory gained badge.precache.json:

What the run shows, and what a real implementation must handle:

  • The file is a public artifact, so it is written next to the nocache.js; paths are relative to the module directory.

  • The list contains files a browser does not need (badge.devmode.js, compilation-mappings.txt) and not the files of other kinds (code-split fragments appear under deferredjs/ in a module that has split points). A production linker should filter by name, and should fail the build on a surprise, not skip it silently.

  • The service worker itself is not generated here. It must be served from a path that covers the pages it controls (usually the application root, not the module directory), and the nocache.js must never be precached, because the point of its name is that it is always revalidated: precache it only with a "network first" strategy, or exclude it and cache the hashed files only. GWT 2.13.1 has no application-cache linker; that mechanism was removed from browsers, and a service worker with a generated manifest is the replacement.

  • The linker runs inside the compile, so it can read the artifacts' real bytes (as here) to compute sizes or integrity hashes. Do not put secrets or build-machine paths into a public artifact.

Content Security Policy

A Content Security Policy (CSP) tells the browser which scripts it may run. The GWT bootstrap is a good test of a policy, because it creates scripts at run time in two ways (a script element with src, and a script element with inline text) and it does so in an iframe that inherits the page’s policy. The SafeHtml and XSS page measured policies against a lab module and found that script-src 'self' is enough to start it; the GWT-RPC page recorded a run in which the same policy stopped a module with an inline-script message. Both are right, and this page explains why: they were compiled with different output styles. The SafeHtml lab was compiled with -style PRETTY, for which installCode is false. The RPC lab used the default obfuscated output, for which installCode is true and the bootstrap installs the code as inline script text.

The lab ran the same Badge module in headless Chrome 155 under five header policies and several builds. A pass means that the module started (the title became started:badge and the entry point wrote into the page).

The two failures have different causes, and both follow from the sequence earlier on this page:

  • Inline text. The default installScript sets script.text, which is an inline script from the browser’s point of view. The only ways to allow it are unsafe-inline, a hash of every string (impossible, the code changes with every build), or a nonce combined with strict-dynamic. Switching to direct_install removes the problem at the source.

  • The script element GWT creates. The permutation file is requested by a script element that the bootstrap creates (in the host page’s head, or inside the iframe), and that element has no nonce. A nonce-only policy therefore blocks it, even though the host page’s own nocache.js tag has the nonce. strict-dynamic says: scripts created by a trusted (nonced) script are trusted too, which is the shape of a GWT bootstrap. This is also why the "nonce alone" row fails for every build except sso, which has no second script to load.

The sso row is the most CSP-friendly output, and xs and std are the worst: both of them rely on inline script in the frame, so even the strict-dynamic policy did not start them.

A policy for the Bookshelf

The measurements give a policy the Bookshelf can use with its split admin area, its XSRF-protected RPC and the default linker, where the server writes the nonce into the host page as in the dynamic host page example:

A header for a Bookshelf host page with a nonce
Content-Security-Policy:
  script-src 'nonce-NONCE_PLACEHOLDER' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data:;
  frame-ancestors 'self'

  • The nonce goes on the nocache.js tag and on any inline script of the host page, is generated per response from a secure random generator, and is never a constant in a file.

  • style-src 'unsafe-inline' is the SafeHtml page’s measured need: StyleInjector and CssResource.ensureInjected() write inline style elements and the module XML’s <stylesheet> adds a link element from the module base.

  • RPC payloads in protocol version 7 are evaluated with eval and need 'unsafe-eval'; protocol version 8 (-Dgwt.rpc.version=8 on the server) uses JSON.parse and does not. The GWT-RPC page has the measured case.

  • default-src was left out. Set it only after you have listed what the application loads, as the SafeHtml page shows.

Run on the real Bookshelf module (the XSRF call failed because no server was running), the direct_install build put its shell into the page under script-src 'self' and under the nonce policy, and the obfuscated default build did so under the nonce policy and not under script-src 'self'. The admin area’s fragment was not opened in that run; the split-point result above is from the single-split-point lab module.

The sibling GWT-specific CSP facts, already measured on the SafeHtml page, are not repeated here: the gwt.cspCompatModeEnabled binding property (default false) that makes widgets avoid javascript: targets, StyleInjector having no nonce support, and the 2.12.0 release note "Fix CSP issues in linkers and dev mode".

Worked example: the Bookshelf’s bootstrap

Putting the page together for the Bookshelf:

  1. Linker. Keep the default xsiframe while the policy allows unsafe-inline or a nonce with strict-dynamic. If the security team requires a policy without unsafe-inline and without strict-dynamic, switch the application module to direct_install, and note that the split admin area then cannot load (see the code splitting table above).

  2. Host page. Serve it from a servlet (the dynamic host page above) so it can carry a per-response nonce and the locale meta tag from the user’s profile, and serve it with a short cache time.

  3. Files. Cache bookshelf.nocache.js with revalidation and the hashed files for a long time; the server integration page has the header table. Precompress with the Precompress module if the server uses static .gz files.

  4. Offline. Add the precache manifest linker and a service worker that precaches the hashed files only.

  5. Observability. Define __gwtStatsEvent in the host page to report the startup events, and a timeout that reports a module that never reached moduleStartup:end, because gwt:onLoadErrorFn does not fire for a failed download of the default build.

  6. Second module. If the Bookshelf’s reading list is embedded in a portal as a separate module, give it its own rename-to, a prefixed gwt:property tag, and its own nonce-carrying script tag.
