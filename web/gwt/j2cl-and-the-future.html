J2CL & the Future

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against GWT 2.13.1 (released 2026-06-19), gwt-maven-plugin 1.3.0 (net.ltgt.gwt.maven), JDK 21 running the compiler with -sourceLevel 17, the J2CL repository release v20260402 (2026-04-02) and j2cl-maven-plugin 0.22.0 (2023-11-13), checked on 2026-10-09. It concerns shared code (Java that is compiled by javac, by the GWT compiler and by J2CL), client code (the part that each of the two compilers turns into JavaScript) and build/tooling (Maven, Bazel, the module XML). Every build, error message, size and browser result in the worked example was produced by running the Bookshelf scenario on this page: one shared module, one application built by gwt-maven-plugin 1.3.0 with GWT 2.13.1 and one built by j2cl-maven-plugin 0.22.0, both loaded in headless Chrome. Statements about projects that were not run (the J2CL Bazel workflow, J2Wasm, the watch goal) come from the project documentation and say so.

GWT 2.13.1 is the toolkit you can ship with today. J2CL is a second, different Java-to-JavaScript compiler from Google, and the org.gwtproject libraries are the part of GWT that was rewritten to run on both. This page explains how the three relate, what is and is not available, and how to keep the code you write today portable.

Two compilers, one language

The GWT compiler and J2CL solve the same problem, running Java in the browser, with different designs.

J2CL’s own README describes it as a transpiler from Java to Closure style JavaScript, tightly integrated with the Closure Compiler and built with Bazel. It is the technology behind several large Google applications (the README names Gmail, Inbox, Docs, Slides and Calendar) and says it is used in production inside Google. The same README also says that the workflow for open-source users is not finalised, that Windows is not supported outside WSL, and in its disclaimer section that the project is an alpha developer preview and not an official Google product. Its Wasm backend is described as working but still work in progress.

The practical consequence is that the two compilers do not replace one another feature by feature. A GWT application that uses widgets, UiBinder, GWT-RPC, ClientBundle, i18n Messages and GWT.create cannot be handed to J2CL; the code that CAN be moved is the plain Java underneath it (model, validation, state machines, event bus, parsing) and the libraries that were rewritten to be independent of gwt-user.

Where J2CL differs from GWT in the language

The J2CL documentation lists the places where Java semantics are deliberately different. They matter when shared code runs on both compilers, because the same method can behave differently.

Isbn.java: JsInterop type, shared logic and one server-only method
package com.example.bookshelf.core.shared;

import java.io.File;
import jsinterop.annotations.JsMethod;
import jsinterop.annotations.JsType;

@JsType(namespace = "bookshelf", name = "Isbn")
public final class Isbn {

  private Isbn() {}

  @JsMethod
  public static String normalize(String raw) {
    return raw.replace("-", "").replace(" ", "");
  }

  @JsMethod
  public static boolean isValid(String raw) {
    String digits = normalize(raw);
    if (digits.length() != 13) {
      return false;
    }
    int sum = 0;
    for (int i = 0; i < 13; i++) {
      char c = digits.charAt(i);
      if (c < '0' || c > '9') {
        return false;
      }
      sum += (c - '0') * (i % 2 == 0 ? 1 : 3);
    }
    return sum % 10 == 0;
  }

  /** Server-only: java.io.File is not part of either emulation. */
  @GwtIncompatible("java.io.File is not emulated")
  public static String coverFileName(String raw) {
    return new File("covers", normalize(raw) + ".jpg").getPath();
  }
}

GwtIncompatible is a six-line annotation declared in the same package (@Retention(CLASS), targets type, method, field and constructor, one String value()): both tools look at its simple name only, so there is no dependency on GWT to import.

BookAddedEvent.java and Catalog.java: shared model on the ported event bus
public class BookAddedEvent extends Event<BookAddedEvent.Handler> {

  public interface Handler {
    void onBookAdded(BookAddedEvent event);
  }

  public static final Type<Handler> TYPE = new Type<>();

  private final String title;

  public BookAddedEvent(String title) {
    this.title = title;
  }

  public String getTitle() {
    return title;
  }

  @Override
  public Type<Handler> getAssociatedType() {
    return TYPE;
  }

  @Override
  protected void dispatch(Handler handler) {
    handler.onBookAdded(this);
  }
}

public class Catalog {

  private final EventBus bus = new SimpleEventBus();
  private final List<String> titles = new ArrayList<>();

  public EventBus events() {
    return bus;
  }

  public boolean add(String title, String isbn) {
    if (!Isbn.isValid(isbn)) {
      return false;
    }
    titles.add(title);
    bus.fireEvent(new BookAddedEvent(title));
    return true;
  }

  public int size() {
    return titles.size();
  }
}

The j2cl-maven-plugin

The Maven plugin is the way to build J2CL code without Bazel. It is a community project by Vertispan, not part of the GWT SDK or of Google’s J2CL repository.

What the Readme documents (not all of it exercised here):

  • Per-library builds with a cache. Each dependency is hashed together with its dependencies and the plugin version, stripped of @GwtIncompatible members, run through annotation processors, transpiled and cached; only changed libraries are rebuilt. The cache lives in target by default and can be moved to a shared directory with the gwt3.cache.dir property.

  • mvn j2cl:clean removes cache entries, -Dartifact=<artifactId> limits it to one artifact and -Dartifact=* empties the cache directory.

  • Dependency rewriting. By default the plugin replaces the jsinterop-base coordinates with com.vertispan.jsinterop:base, which the build log confirmed (Removing dependency com.google.jsinterop:base:jar:1.0.1:compile, replacing with com.vertispan.jsinterop:base:jar:1.0.1-1).

  • Compilation levels. ADVANCED_OPTIMIZATIONS for production (the sample archetype writes ADVANCED, which worked), SIMPLE_OPTIMIZATIONS, WHITESPACE_ONLY, BUNDLE (concatenation only) and BUNDLE_JAR (one bundle per classpath entry, loaded in order).

  • Dev mode. The watch goal recompiles the changed libraries of a whole reactor, so it is meant to be run from the parent project. It was not run for this page.

The test goal runs JUnit tests compiled to JavaScript (the archetype’s test runs under HtmlUnit); the Readme claims the plugin is the only way to build general J2CL projects outside Bazel. The GWT counterpart of such tests is covered in Testing GWT Applications.

Gradle, Bazel and the rest

The community GWT Gradle plugins mentioned in Build Tools: Maven & Gradle build GWT 2 applications; none of them was checked for J2CL. Google’s own J2CL workflow is Bazel (its getting-started page uses Bazelisk and bazel build/bazel run on the helloworld sample, and says the output of that sample is a single optimised line of JavaScript). The Bazel path was not run for this page. For a Java team that already builds with Maven, the plugin is the lower-friction route; the plugin bundles the older J2CL build v20230718-1, so features added since (the J2CL README mentions Wasm) are reached through Bazel; whether the plugin exposes them was not checked.

Moving a GWT code base toward J2CL

A realistic migration is incremental and always keeps the GWT build green:

  • Isolate the portable core. Move models, validation, formatting and domain events into a module that depends on no gwt-user type, as bookshelf-core does. Compile it with javac and JUnit first.

  • Replace JSNI with JsInterop. The pages JSNI & Overlay Types and JsInterop describe the mapping; JsInterop works in both compilers.

  • Replace GWT.create and generators in the core with factories or annotation processors (see Deferred Binding & Generators).

  • Swap gwt-user classes for ported ones where a module exists and is acceptable to depend on at release-candidate quality (gwt-event, gwt-core, gwt-dom, gwt-safehtml, gwt-editor), or for Elemental2.

  • Add the second build (J2CL) in CI and keep it as a canary. Anything that breaks it shows which GWT assumption crept into the core.

  • Leave the UI and the transport alone. Widgets, UiBinder, cell widgets, ClientBundle, i18n and GWT-RPC have no J2CL-ready counterpart in org.gwtproject.

Mapping of the old coordinates and packages, with the other changes between GWT versions, is collected in What’s Changed & Migration, in particular the recipes for coordinates and packages, Jakarta, JSNI and Elemental. A catalogue of the libraries around GWT, including alternatives for the pieces that were not ported, is in Ecosystem & Libraries, and IDE support for GWT and J2CL projects in Tooling & IDE Support.

The roadmap

The GWT roadmap page is short and says the following (checked on 2026-10-09):

  • planning happens in GitHub milestones; the milestones are the place to look, because priorities change;

Outdated material in older books and posts

Books written for GWT 1.x and 2.0 to 2.5 predate J2CL, which Google began in 2015, and the org.gwtproject modules, so they cannot be used to decide anything about either. Their chapters on events, DOM access, RPC and widgets describe the com.google.gwt packages, which remain valid for GWT 2.13.1; what changed is that the same code is no longer the only option for non-UI libraries.
