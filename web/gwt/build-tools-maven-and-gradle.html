Build Tools: Maven & Gradle

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against GWT 2.13.1 (2026-06-19), gwt-maven-plugin 1.3.0 (2026-05-31), Maven 3.9.16, source level 17 and Jakarta Servlet 6.0 (the values the modular-webapp archetype 2026.6.22 generates), as of 2026-10-08. Every Maven command and every console output shown was run on that stack with JDK 21 (the same build also passes on JDK 26), except the Jetty command of the multi-module section, which was run on the scratch application earlier in the work on this section, and the CI workflow fragment. It is build and tooling material: nothing here is compiled to JavaScript, but the POM decides which of your sources are, which artifacts reach the server, and how the compiler is invoked. The compiler flags themselves belong to the Compiler & Compilation page, the module XML to Project Structure & Modules, and the run loop to Development Mode & Debugging; this page covers the build around them.

Maven and Gradle themselves, independent of GWT, are covered in JVM Build Tools: Ant, Maven & Gradle.

What the build has to do

A GWT application is three kinds of code that the Java tooling normally mixes together, and the build exists to keep them apart:

  • client code is compiled twice: once by javac (so the IDE and unit tests work) and once by the GWT compiler into JavaScript. The GWT compiler needs the Java sources of everything the client uses, not just class files;

  • shared code (DTOs, RPC interfaces) is compiled by javac for the server and, with its sources, by the GWT compiler for the client;

  • server code is ordinary Java for a servlet container and must never contain client-only classes, nor the other way round.

packaging gwt-app"] shared --> server["bookshelf-server

The running scenario of this section, the Bookshelf, is exactly this shape: bookshelf-shared, bookshelf-client and bookshelf-server as generated by the net.ltgt.gwt.archetypes:modular-webapp archetype, plus a small bookshelf-widgets library module added on this page to show a gwt-lib. The sources a GWT compile reads come from the module XML <source> paths, so the build must make the sources of dependencies available on the compiler classpath. gwt-maven-plugin does this with two packagings (gwt-lib and gwt-app) and a set of goals, described next.

The org.gwtproject BOM and the GWT artifacts

Since 2.10.0 GWT publishes under the Maven groupId org.gwtproject (release notes 2.10.0); the former com.google.gwt coordinates stop at version 2.10.0. The bill of materials org.gwtproject:gwt:2.13.1 is a pom-type artifact that manages the versions of every GWT artifact, so that your POM states the GWT version exactly once:

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.gwtproject</groupId>
      <artifactId>gwt</artifactId>
      <version>2.13.1</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
    <dependency>
      <groupId>jakarta.servlet</groupId>
      <artifactId>jakarta.servlet-api</artifactId>
      <version>6.0.0</version>
    </dependency>
  </dependencies>
</dependencyManagement>

Two consequences matter in practice:

  • gwt-user brings javax.servlet-api 3.1.0 even when your server is Jakarta. Keep the real server API (jakarta.servlet:jakarta.servlet-api, provided) in the server module, use gwt-servlet-jakarta there, and never put gwt-user on the server classpath of a deployed WAR: it duplicates gwt-servlet.

  • gwt-dev is large (a complete Jetty and HtmlUnit). A gwt-app module can declare it at the default scope because the gwt-app WAR contains only the compiler output, but a library should declare it provided, otherwise every consumer inherits it.

gwt-maven-plugin

The Maven integration used by the archetypes, by the GWT project’s own samples (moved to Maven in 2.13.0) and by this section is net.ltgt.gwt.maven:gwt-maven-plugin, written by Thomas Broyer. Its design goals are stated on its site: it is independent of the GWT version (it passes explicit argument lists to GWT instead of modelling every flag), it understands multi-module projects, and it adds two packagings and two artifact types. It is tested against the latest two stable GWT versions and the latest snapshot.

<plugin>
  <groupId>net.ltgt.gwt.maven</groupId>
  <artifactId>gwt-maven-plugin</artifactId>
  <version>1.3.0</version>
  <extensions>true</extensions>
  <configuration>
    <moduleName>com.example.bookshelf.App</moduleName>
    <moduleShortName>bookshelf</moduleShortName>
    <sourceLevel>17</sourceLevel>
    <failOnError>true</failOnError>
  </configuration>
</plugin>

Source: gwt-maven-plugin — Basic usage

<extensions>true</extensions> is what makes the gwt-app and gwt-lib packagings (and artifact types) known to Maven; without it Maven answers Unknown packaging: gwt-app. The usage page still shows BOM 2.13.0 while the plugin 1.3.0 is the latest release; use the BOM version you actually run. failOnError makes the compile fail when sources have errors instead of producing a partial result, and the generated POMs of both the archetype and webAppCreator set it. sourceLevel is explained under the compile goal.

The two artifact types

The same two names are also dependency types. They describe what the artifact contains, and therefore how a consumer may use it.

Table 4. The gwt-lib and gwt-app artifacts
Type Content How to depend on it

gwt-lib

A JAR with both compiled classes and their sources: the generated module descriptor (<slashified moduleName>.gwt.xml), META-INF/gwt/mainModule (optional), **/*.java, **/*.class and other resources such as *.gss, *.png and *.ui.xml.

<type>jar</type> or <type>gwt-lib</type>.

gwt-app

A WAR holding only the compiler output: <moduleShortName>/<moduleShortName>.nocache.js and the other files under <moduleShortName>/. No WEB-INF/web.xml, no classes, no libraries.

<type>war</type> or <type>gwt-app</type>. With war the maven-war-plugin overlays the content into the resulting WAR automatically.

gwt:codeserver and gwt:devmode are aggregator goals that require dependency resolution at compile+runtime scope and first execute the process-classes phase of the modules they run; the other goals resolve compile (compile), runtime (generate-module) or test (test) dependencies.

A few behaviours deserve a real transcript. Compilation is skipped when the output is up to date: running the same build a second time took 0.9 seconds in total (the first one took 17 seconds, six permutations):

$ mvn -B package -DskipTests -pl bookshelf-client -am
[INFO] --- gwt:1.3.0:compile (default-compile) @ bookshelf-client ---
[INFO] Compilation output seems uptodate. GWT compilation skipped.
[INFO] --- gwt:1.3.0:package-app (default-package-app) @ bookshelf-client ---
[INFO] BUILD SUCCESS
[INFO] Total time:  0.946 s

Source: gwt-maven-plugin — gwt:compile forceCompilation

With -Dgwt.skipCompilation=true the goal only logs GWT compilation is skipped and the application WAR is built without compiler output. With the properties of the table you steer a single run from the command line, here a draft compile with readable output and two workers, forced because the output was already up to date:

mvn -B package -DskipTests -pl bookshelf-client -am \
    -Dgwt.draftCompile=true -Dgwt.style=PRETTY -Dgwt.localWorkers=2 -Dgwt.forceCompilation=true

Source: gwt-maven-plugin — gwt:compile draftCompile

That run finished in 11.3 seconds for the whole reactor, against 18.7 seconds for the first full build (a draft compile also turns the -Xnamespace default to PACKAGE, hence the new warnings Namespace option is not compatible with CodeSplitter, turning it off, which can be ignored).

Which sourceLevel is used is the most frequent surprise. The property it reads is maven.compiler.source, and maven-compiler-plugin projects that only set maven.compiler.release (the modern way) leave it empty. Both generated POMs therefore set <sourceLevel> explicitly: the archetype uses 17 together with <release>17</release> on the compiler plugin, and the webAppCreator Maven template uses maven.compiler.release 11 with a comment explaining that the compiler of 2.12.0 and later needs level 11 or above. The Compiler -help text and the Developer Guide are right that the command-line compiler’s own default is 1.8 (the default argument registered in ToolBase), so Java 12 to 17 syntax needs an explicit -sourceLevel 17, and auto resolves to the level of the running JVM. The plugin’s <sourceLevel> is therefore not the compiler’s default but whatever maven.compiler.source holds; setting the level explicitly avoids depending on either (details on the Compiler & Compilation page).

Further compiler flags go in compilerArgs. The Bookshelf enables the generation of JsInterop exports this way:

<configuration>
  <moduleName>com.example.bookshelf.App</moduleName>
  <moduleShortName>bookshelf</moduleShortName>
  <compilerArgs>
    <arg>-generateJsInteropExports</arg>
  </compilerArgs>
</configuration>

Source: gwt-maven-plugin — gwt:compile compilerArgs

The code server and DevMode goals

gwt:codeserver is the Maven way to run Super Dev Mode. It is an aggregator goal, so its configuration belongs in the root POM, and it gathers the gwt-app modules of the reactor by itself. The plugin documentation lists its differences from gwt:compile:

  • the applications and all reactor modules depended on with <type>gwt-lib</type> or <classifier>sources</classifier> have their source roots used as they are, so edits are seen immediately (a resource directory with filtering or relocation behaves differently);

  • the dependency scope for the classpath is runtime by default rather than compile, configurable with classpathScope;

  • since GWT 2.7 you should set launcherDir, a folder your web server or servlet container reads static resources from, so that the *.nocache.js written by the code server is loadable and the browser’s "recompile on reload" works;

  • because the goal triggers process-classes in all modules, restrict the reactor with -pl and add -am, or set projects (-Dgwt.projects=) in a profile;

  • because the code server takes different arguments from the compiler, arguments needed by both are defined twice, in compilerArgs and in codeserverArgs.

Module generation goals

gwt:generate-module is what lets a Maven project avoid maintaining <inherits> lines by hand. It reads the template (src/main/module.gwt.xml by default) and writes the real descriptor to the class output, in the package of moduleName. The description in the descriptor is precise:

  • META-INF/gwt/mainModule files from the project’s direct dependencies (not transitive) produce <inherits> directives, inserted at the very beginning of the generated module, before any <inherits> of the template;

  • if moduleShortName is given, it overwrites any rename-to of the template;

  • unless the template contains a <source> or <super-source> element, the lines <source path="client"/>, <source path="shared"/> and <super-source path="super"/> are appended at the end.

Super-source goals

gwt:add-super-sources adds src/main/super (parameter superSourceDirectory) to the resources, and gwt:add-test-super-sources adds src/test/super (testSuperSourceDirectory). GWT requires super-sources to live in a subdirectory of the module; with relocateSuperSource (respectively relocateTestSuperSource) set to true the plugin relocates the directory’s content into a super subfolder of the module named by moduleName, and the <super-source path="super"/> line from the generation rules above then makes the sources visible. Both parameters default to false. The two goals are bound to initialize; the Bookshelf has no super-sources, which the build reports as skip non existing resourceDirectory .../src/main/super.

<configuration>
  <moduleName>com.example.bookshelf.widgets.Widgets</moduleName>
  <superSourceDirectory>src/main/super</superSourceDirectory>
  <relocateSuperSource>true</relocateSuperSource>
</configuration>

Multi-module builds

The three-module split is not decoration: it is how the plugin keeps the three code kinds apart. The Bookshelf reactor, in the order Maven resolves it from the dependencies, is bookshelf-widgets (gwt-lib), bookshelf-shared (jar), bookshelf-client (gwt-app) and bookshelf-server (war). The relationships to set up are:

<!-- bookshelf-client/pom.xml -->
<packaging>gwt-app</packaging>
<dependencies>
  <dependency>
    <groupId>${project.groupId}</groupId>
    <artifactId>bookshelf-shared</artifactId>
    <version>${project.version}</version>
  </dependency>
  <dependency>
    <groupId>${project.groupId}</groupId>
    <artifactId>bookshelf-shared</artifactId>
    <version>${project.version}</version>
    <classifier>sources</classifier>
  </dependency>
  <dependency>
    <groupId>${project.groupId}</groupId>
    <artifactId>bookshelf-widgets</artifactId>
    <version>${project.version}</version>
  </dependency>
  <dependency>
    <groupId>org.gwtproject</groupId>
    <artifactId>gwt-user</artifactId>
  </dependency>
  <dependency>
    <groupId>org.gwtproject</groupId>
    <artifactId>gwt-dev</artifactId>
  </dependency>
</dependencies>

Source: gwt-maven-plugin — Artifact Handlers

The shared module needs a sources classifier JAR (the client module lists it as a second dependency) because the compiler reads Java source; the maven-source-plugin execution jar-no-fork bound to package in the root pluginManagement produces it. A gwt-lib needs none of that because its JAR already contains sources, which is why a pure client library should be a gwt-lib and a library shared with the server should stay a plain JAR with sources.

The server module depends on the client’s WAR (<type>war</type>, runtime scope) and the maven-war-plugin overlays it:

<!-- bookshelf-server/pom.xml, profile env-prod (active by default) -->
<dependency>
  <groupId>${project.groupId}</groupId>
  <artifactId>bookshelf-client</artifactId>
  <version>${project.version}</version>
  <type>war</type>
  <scope>runtime</scope>
</dependency>

Source: gwt-maven-plugin — gwt-app artifact

The archetype wraps that dependency in a profile pair. env-prod is active by default and adds the client WAR; env-dev is activated by -Denv=dev (or -Penv-dev, as the archetype README says) and instead points the Jetty plugin at the launcherDir written by the code server, so the server can be started without compiling the application. The comment in the generated POM explains the odd shape: Maven forces an explicit env-prod profile to be able to exclude the dependency in env-dev. The effect, measured on the Bookshelf, was that the server WAR built with -Denv=dev contained no nocache.js (0 matches), while the default build contained one:

# Development: the code server runs in one terminal, the server in another
mvn gwt:codeserver -pl bookshelf-client -am
mvn -Denv=dev -pl bookshelf-server -am org.eclipse.jetty.ee10:jetty-ee10-maven-plugin:12.1.10:run

# Production: compiles the client and overlays it
mvn clean package

Source: tbroyer/gwt-maven-archetypes — modular-webapp

The reactor options to remember are -pl (select projects), -am (also make the projects they depend on), -amd (also make the projects depending on them) and -rf (resume from). The first command above works because -pl bookshelf-client -am selects the client, the shared module and the library, and because the aggregator goal runs once at the root. In a shell, use plain project names, as noted before.

Skipping GWT work in CI profiles

Compiling GWT is the slowest step of a CI job (17 seconds for the small Bookshelf, minutes for a real application), and most jobs do not need it: a server-only test run, a lint job, or a documentation job. Because the plugin parameters are bound to properties, a profile can switch work off without editing any plugin configuration.

<profiles>
  <profile>
    <id>no-gwt</id>
    <properties>
      <gwt.skipCompilation>true</gwt.skipCompilation>
      <skipTests>true</skipTests>
    </properties>
  </profile>
  <profile>
    <id>ci-fast</id>
    <build>
      <pluginManagement>
        <plugins>
          <plugin>
            <groupId>net.ltgt.gwt.maven</groupId>
            <artifactId>gwt-maven-plugin</artifactId>
            <configuration>
              <draftCompile>true</draftCompile>
              <style>PRETTY</style>
              <localWorkers>2</localWorkers>
            </configuration>
          </plugin>
        </plugins>
      </pluginManagement>
    </build>
  </profile>
</profiles>

Source: Apache Maven — Introduction to Build Profiles

Run with -Pno-gwt the whole reactor built in 3.4 seconds, all four modules SUCCESS, with the log lines GWT compilation is skipped for the client and Tests are skipped. for each module. That is the right profile for a job that only needs to know that the Java sources compile. The ci-fast profile keeps the compile but cuts its cost; it is suitable for pull-request builds that run the browser tests, while the release build runs without it so that the shipped JavaScript is optimised and obfuscated. Guidelines that follow from the descriptor:

  • Prefer properties for toggles (gwt.skipCompilation, gwt.draftCompile, gwt.style, gwt.localWorkers) and profiles for presets. The plugin has few properties by design because it passes arguments to GWT explicitly; the migration page of the plugin suggests presets in profiles and the attribute combine.children="append" to extend an existing compilerArgs list from a profile.

  • gwt.localWorkers accepts a number or a number with C: -Dgwt.localWorkers=0.5C uses half the cores, useful on shared CI runners.

  • Do not set skipCompilation for the build that produces the artifact you deploy: a gwt-app WAR built that way is valid but empty of JavaScript, and the server WAR overlays it without complaint.

  • The plugin decides that a compile can be skipped by checking that the output *.nocache.js exists and that the POM, sources and dependencies have not changed (the documented behaviour of forceCompilation). For a release build, pass -Dgwt.forceCompilation=true so that a stale target/ directory restored from a CI cache can never ship.

  • GWT tooling needs Java 11 or newer to run (the 2.13.0 notes say that 2.13 is probably the last release whose compiler and dev tools run on Java 11), so pin the CI JDK to a version your GWT release supports and set sourceLevel explicitly.

# GitHub Actions job (fragment): server tests on every push, full GWT build only on the main branch
- uses: actions/setup-java@v4
  with:
    distribution: temurin
    java-version: 21
    cache: maven
- run: mvn -B -Pno-gwt verify
- run: mvn -B clean verify
  if: github.ref == 'refs/heads/main'

Source: gwt-maven-plugin — gwt:compile skipCompilation

The Maven commands of the fragment were run as shown; the workflow file itself was not executed.

Packaging reusable GWT libraries as JARs

A library that other GWT projects will inherit must ship its sources, because the consumer’s compiler translates them. The module descriptor and any public resources must be on the classpath next to them. Doing this by hand means placing src/main/java in the resources (or building a second JAR with the maven-source-plugin and a sources classifier, as the shared module does) and writing the .gwt.xml correctly. The plugin automates the first variant, which is why a gwt-lib is the recommended packaging for client-only libraries:

  1. set <packaging>gwt-lib</packaging>;

  2. set <moduleName> to the fully qualified module the library exposes;

  3. keep a src/main/module.gwt.xml template with the <inherits> of the other GWT libraries and the <source> paths if they are not the defaults (the plugin appends client, shared and super source paths when the template has none);

  4. declare gwt-user normally and gwt-dev as provided;

  5. install or deploy it: the consumer depends on it with the usual <dependency> (the type defaults to jar, which is accepted).

The consumer needs no <inherits> line when it uses gwt:generate-module, because META-INF/gwt/mainModule from the direct dependency generates it, and it needs one if the module template is hand-written and generation is skipped. A library that is not a gwt-lib but publishes a sources classifier is consumed as in the Bookshelf’s bookshelf-shared: both the binary and the sources dependency, and <inherits> of the module (or the mainModule mechanism when the producer uses gwt:generate-module-metadata).

What goes wrong is nearly always one of two things, both visible as compiler errors: the sources are not on the classpath (No source code is available for type com.example.bookshelf.shared.Book; did you forget to inherit a required module?), or the module is not inherited. The next pitfall table collects them. The module XML itself (the <source>, <public> and <inherits> elements and the standard module hierarchy) is explained on the Project Structure & Modules page; the official reference is the Developer Guide chapter on modules.

Source: GWT — Organizing Projects: Modules, units of configuration

A practical migration order that keeps the project building at every step:

  1. Replace the plugin coordinates and set <extensions>true</extensions>; keep the module descriptor where it is by setting skipModule to true (the lowest-risk route) and move to src/main/module.gwt.xml later.

  2. Import the org.gwtproject:gwt BOM and declare gwt-user and gwt-dev; remove the version properties of the old plugin that selected the GWT version.

  3. Move the old <configuration> entries into moduleName, moduleShortName, sourceLevel, style, draftCompile, jvmArgs and compilerArgs.

  4. Replace gwt:run-codeserver by gwt:codeserver at the root of a multi-module build, with launcherDir.

  5. Replace gwt:source-jar and gwt:resources by the gwt-lib packaging for client libraries.

  6. Split the server out into its own module and overlay the gwt-app WAR on it.

  7. Delete the use of gwt:i18n, gwt:css, gwt:generateAsync, gwt:mergewebxml and write what they generated.

I did not run either Gradle plugin, so nothing about their task behaviour or compatibility with the Bookshelf is claimed beyond what the READMEs say. If you choose Gradle, the equivalent of the multi-module layout above is a client project that applies the GWT plugin, a shared project that exposes its sources to the client, and a server project; check how the plugin you pick makes the sources of the shared project available to the compiler, since that is the part Maven solves with the sources classifier and gwt-lib. Maven remains the build documented and exercised throughout this section, because gwt-maven-plugin, the archetypes and the GWT project’s own samples are Maven.

The command-line creator tools

Before archetypes, the GWT SDK shipped command-line generators. They are history, and the official pages that still describe them have not kept up.

webAppCreator is a script in the SDK that runs com.google.gwt.user.tools.WebAppCreator from gwt-user. Its documented parameters are -[no]overwriteFiles, -[no]ignoreExistingFiles, -templates (default sample,ant,eclipse,readme), -out, -junit, the deprecated -[no]maven and -[no]ant, and the module name. The 2.11.0 release notes list the tool as deprecated. The class itself prints this on every run (real output on 2.13.1):

java -cp gwt-user-2.13.1.jar:gwt-dev-2.13.1.jar com.google.gwt.user.tools.WebAppCreator \
     -out foo -templates maven,sample,readme com.example.foo.Foo

Source: GWT — Command Line Tools: webAppCreator

WebAppCreator is deprecated - please refer to https://www.gwtproject.org/gettingstarted.html for other ways to create a new application with GWT, including with Maven archetypes. These encourage better separation of classpaths, and do not need IDE-specific setup.
Generating from templates: [maven, readme, _sample-test, sample]

What it generates is a single-module war project, the opposite of the layout recommended above. Its pom.xml (2.13.1) still pins gwt-maven-plugin 1.2.0, runs the compile and test goals, sets maven.compiler.release to 11 and sourceLevel to 11, writes the classes into WEB-INF/classes and disables Surefire in favour of gwt:test. It passes -compileReport and -XcompilerMetrics in compilerArgs (see Compile Reports & Optimization); the latter is accepted by the compiler but is not listed in the compiler’s -help output. The official Getting Started page (gettingstarted.html) still tells you to unpack gwt-2.10.0.zip, requires Java 1.8 and Apache Ant, and uses the default Ant template with ant devmode and ant build, so it is stale; the same is true of the Compile & Debug chapter, which launches DevMode through ant devmode. The deprecation, not those pages, is current. Use the archetype instead:

mvn archetype:generate \
    -DarchetypeGroupId=net.ltgt.gwt.archetypes -DarchetypeArtifactId=modular-webapp -DarchetypeVersion=2026.6.22 \
    -DgroupId=com.example.bookshelf -DartifactId=bookshelf -Dmodule-short-name=bookshelf

Source: tbroyer/gwt-maven-archetypes

i18nCreator (com.google.gwt.i18n.tools.I18NCreator) generates a properties file and a script that regenerates the Java interface (a Constants, ConstantsWithLookup or Messages subinterface) when the properties change. It is not deprecated in the source and still runs. Real output for a Messages interface:

$ java -cp gwt-user-2.13.1.jar:gwt-dev-2.13.1.jar com.google.gwt.i18n.tools.I18NCreator \
       -createMessages com.example.foo.client.FooMessages
Created file src/com/example/foo/client/FooMessages.properties
Created file FooMessages-i18n

Source: GWT — Command Line Tools: i18nCreator

The generated script calls com.google.gwt.i18n.tools.I18NSync with the classpath of the machine where it was generated, which makes it non-portable. The Internationalization page recommends writing the Messages interface first and the properties files from it, which is the direction Maven builds prefer.

Tools the first book taught

GWT in Action by Hanson and Tacy (Manning, 2007) was written for GWT 1.x and shows a toolchain that no longer exists in GWT 2.13.1: the projectCreator and applicationCreator scripts (an Eclipse-oriented pair run in that order), junitCreator, i18nCreator and the shell and compile scripts generated beside the application, which started the hosted browser and the old com.google.gwt.dev.GWTCompiler. In the source of 2.13.1:

Pitfalls

Table 15. Build problems and fixes
Symptom or message Cause Fix

Unknown packaging: gwt-app (and Unknown packaging: gwt-lib), reported as The build could not read 2 projects

The plugin is declared without <extensions>true</extensions>.

Add the extensions flag to the plugin declaration (in pluginManagement or build/plugins).

No source code is available for type com.example.bookshelf.shared.Book; did you forget to inherit a required module?

The module is not inherited, or the dependency has no sources JAR on the compiler classpath (for instance, running mvn test before the sources classifier JAR is packaged).

Declare both the binary and the sources classifier dependency, add <inherits>, and run mvn verify or install.

gwt:test prints nothing and reports no tests

includes is not configured for the goal in this setup.

Add <includes> with **/*Test.java or pass -Dtest=....

No tests matching pattern "..." were executed!

-Dtest is applied to every module of the reactor.

Add -Dsurefire.failIfNoSpecifiedTests=false.

Could not find the selected project in the reactor: *-client

A wildcard in -pl (Maven 4 only).

Use -pl bookshelf-client.

Unable to find '.../Widgets.gwt.xml' on your classpath

A module descriptor was never generated (for instance skipModule is true without a hand-written file) or the library is not on the classpath.

Remove skipModule, or put the descriptor where the module name says.

GWT compile is skipped and the application is empty

gwt.skipCompilation is set (a CI profile that leaked into the release build).

Build the artifact with -Dgwt.forceCompilation=true and no skip profile.

The compile uses a different Java level from javac

maven.compiler.source is empty because only maven.compiler.release is set.

Set <sourceLevel> in the plugin configuration.

Ignoring incompatible plugin version 4.0.0-beta-... (maven-install-plugin, maven-deploy-plugin)

Maven 3.9 skipping newer plugin betas that need Maven 4.

Harmless noise; pin versions in pluginManagement to silence it.

GWT-RPC call fails with InaccessibleObjectException for java.lang.Throwable.detailMessage on Java 17 or later

Server-side exception serialisation needs reflection into java.lang; upstream issue gwtproject/gwt#9793.

Start the servlet container JVM with --add-opens java.base/java.lang=ALL-UNNAMED (the Maven Jetty plugin: MAVEN_OPTS).

Recent changes and where the books are outdated

  • 2.10.0: the groupId becomes org.gwtproject; the BOM org.gwtproject:gwt carries the managed versions.

  • 2.11.0: Jakarta artifacts (gwt-servlet-jakarta, requestfactory-server-jakarta); webAppCreator deprecated.

  • 2.12.0: minimum Java 11 for the tools; Java 12 to 17 language levels (hence sourceLevel 17 in the archetype); the ApplicationCreator and ProjectCreator main classes removed.

  • 2.13.0: the samples of the GWT repository moved to Maven; DevMode serves only static files by default; the notes say that 2.13 is probably the last release whose compiler and dev tools run on Java 11.

  • Plugin 1.3.0 (2026-05-31) and the archetype 2026.6.22 target 2.13.x; the archetype pins jetty-ee10-maven-plugin 12.1.10 for the server.

  • Gradle: still no official plugin; two maintained community plugins, one archived.

  • The 2007 book (first edition) describes Ant, projectCreator/applicationCreator, the hosted browser and the GWTCompiler class: none of that exists. The second edition of the book (2013) has a Manning page that resolves but was not consulted for this page. The Google-hosted Getting Started and Compile & Debug pages also still describe the Ant flow of GWT 2.10.
