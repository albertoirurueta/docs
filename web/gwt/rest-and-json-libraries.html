REST & JSON Libraries

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against GWT 2.13.1 (2026-06-19), gwt-maven-plugin 1.3.0, Elemental2 1.3.2, a JDK 21 toolchain with -sourceLevel 17, the Jakarta Servlet 6 stack of the modular-webapp archetype and Spring Boot 4.1.1 (Spring Framework 7.0.9, Spring Security 7.1.1, Tomcat 11.0.24), and was checked on 2026-10-09. Every output block was produced with the Bookshelf scenario of this section: a probe module compiled to JavaScript for each library, a Spring Boot application serving the REST API and the compiled files, and headless Chrome 155 loading the page and reporting the log. It covers client code (the REST and JSON code that is compiled to JavaScript), shared code (the DTO classes the client libraries need), server code (the Spring Boot REST backend and a proxy to a third-party service) and build settings (the Maven coordinates, annotation processors and module inherits each library needs).

GWT-RPC is the way GWT calls a Java servlet with Java objects. Many applications talk to something else: a REST API that other clients also use, a service written in another language, or a public JSON API. For that, the Developer Guide says the application is free to integrate "other RPC mechanisms, such as JSON using the GWT supplied RequestBuilder class, JSNI methods or a third party library". This page is about the third-party and browser-native options, and about the server side of the same conversation.

Reading the table:

  • Pick by the maintenance signal you need. domino-rest and domino-jackson published releases within the last three months of the check date; Elemental2 published a release candidate (1.4.0-RC1) in July 2026, while its latest stable release, 1.3.2, is thirteen months old. RestyGWT, AutoREST and gwt-jackson did not publish a release in the last two years, but all three still compiled and ran against GWT 2.13.1 in the probes below, which is not a promise that they will with the next GWT release.

  • A library that works today still needs an owner. If you adopt one of the three quiet projects, plan to fork or replace it: the annotation processors and generators of those projects run inside the GWT compiler or javac, and a future JDK or GWT release can break them without anyone to fix them.

  • GWT itself documents none of them. The Developer Guide names RequestBuilder, JSNI and "a third party library"; it never names RestyGWT, AutoREST, gwt-jackson or DominoKit. The Ecosystem & Libraries page lists the wider library landscape.

The Bookshelf REST API (Spring Boot)

Every client probe below talks to the same server: a Spring Boot application with a Bookshelf controller. This is the server half of the conversation; the Spring side is documented in depth in REST APIs with Spring MVC and WebFlux (controllers, Bean Validation, ProblemDetail, CORS), and the authentication side in Spring Security. The earlier pages of this section used a read-only servlet at /api/books; the controller below serves the same URL with the full set of verbs.

The payload is a DTO, never a JPA entity: the record fixes the JSON shape that the browser depends on, and a change to the database mapping cannot leak into the contract by accident.

public record BookDto(
    Long id,
    @NotBlank @Size(max = 120) String title,
    @NotBlank @Size(max = 80) String author,
    @Min(1450) @Max(2100) int year,
    @Min(0) int copies) {
}

public record BookPageDto(int total, List<BookDto> books) {
}

@RestController
@RequestMapping("/api/books")
public class BookController {
  private final BookStore store;

  public BookController(BookStore store) {
    this.store = store;
  }

  @GetMapping
  public BookPageDto list(@RequestParam(defaultValue = "0") int start,
                          @RequestParam(defaultValue = "10") int length) {
    return new BookPageDto(store.total(), store.slice(start, Math.min(length, 100)));
  }

  @GetMapping("/{id}")
  public BookDto get(@PathVariable long id) {
    return store.find(id).orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND, "No book " + id));
  }

  @PostMapping
  public ResponseEntity<BookDto> create(@Valid @RequestBody BookDto body) {
    BookDto saved = store.add(body);
    return ResponseEntity.created(URI.create("/api/books/" + saved.id())).body(saved);
  }

  @PutMapping("/{id}")
  public BookDto update(@PathVariable long id, @Valid @RequestBody BookDto body) {
    return store.replace(id, body)
        .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND, "No book " + id));
  }

  @DeleteMapping("/{id}")
  @ResponseStatus(HttpStatus.NO_CONTENT)
  public void delete(@PathVariable long id) {
    if (!store.remove(id)) {
      throw new ResponseStatusException(HttpStatus.NOT_FOUND, "No book " + id);
    }
  }
}

Source: Spring Boot — Spring MVC: error handling, Spring Framework — Error responses

BookStore is an in-memory map in the probe, standing in for the repository of a real application. The configuration needs three lines, one of which turns Spring errors into RFC 9457 problem documents:

server.port=8934
spring.mvc.problemdetails.enabled=true
spring.security.user.name=librarian
spring.security.user.password=${BOOKSHELF_PASSWORD}
spring.security.user.roles=LIBRARIAN

Source: Spring Boot — Spring MVC: error handling

The password comes from the environment (the probes were run with the placeholder value PASSWORD_PLACEHOLDER); never commit a real one, and use a user store or an identity provider in a real application.

Security: authorisation and CSRF

Reading is public, writing needs the LIBRARIAN role, and the browser proves it is the same application with a double-submit cookie:

@Configuration
public class SecurityConfig {

  @Bean
  SecurityFilterChain api(HttpSecurity http) throws Exception {
    http
        .csrf(csrf -> csrf.spa())
        .authorizeHttpRequests(auth -> auth
            .requestMatchers(HttpMethod.GET, "/api/**", "/", "/*.html", "/restdemo/**").permitAll()
            .requestMatchers("/api/**").hasRole("LIBRARIAN")
            .anyRequest().denyAll())
        .httpBasic(Customizer.withDefaults());
    return http.build();
  }
}

Source: Spring Security — CSRF: Single-Page Applications

csrf.spa() (present in Spring Security 7.1.1 and shown on the Spring Security CSRF page) configures a cookie repository that is not HttpOnly, so the page can read it: the server writes a cookie named XSRF-TOKEN and expects its value back in a request header named X-XSRF-TOKEN. httpBasic is used here only because it keeps the probe small; a real application uses a form login, OAuth 2.0 or OpenID Connect, as the Spring Security page explains. The authorisation rule is on the server: hiding a button in the GWT client does not protect anything, because the client code is public.

Without the header, with the same credentials, the answer is not 403:

HTTP/1.1 401

Content-Length: 0

CsrfFilter runs before BasicAuthenticationFilter, so the request is still anonymous when the token check fails, and the authentication entry point answers with 401 instead of the access-denied handler’s 403 (the Spring debug log said Invalid CSRF token found for http://localhost:8934/api/books/4). A client must therefore treat both 401 and 403 on a write as "not allowed or token missing" and fetch a fresh token with a GET before retrying once. When the same check runs for a request that needs no authentication, as in the headless-browser probe of the Elemental2 section below, the answer is 403 with an empty body.

A body that fails validation returns a problem document, but Spring Boot 4.1.1 does not list the offending fields in it by default:

HTTP/1.1 400
Content-Type: application/problem+json

{"detail":"Invalid request content.","instance":"/api/books","status":400,"title":"Bad Request"}

and an unknown id gives the 404 of the contract:

HTTP/1.1 404
Content-Type: application/problem+json

{"detail":"No book 99","instance":"/api/books/99","status":404,"title":"Not Found"}

The spring side of CORS is described in REST APIs: cross-origin requests and the concepts in What is CORS?. The probes avoid CORS entirely by serving the compiled GWT files and the API from the same origin, which is also what the Server Integration & Deployment page recommends: no Access-Control-Allow-Origin header, no preflight request, and a session cookie that never leaves the site.

Elemental2 fetch

Elemental2 is Google’s set of Java type definitions for the browser APIs, generated from the JavaScript externs (see DOM and Elemental2 for the types, DomGlobal, Promise and a first fetch example). For REST it gives you DomGlobal.fetch, Response, Headers, RequestInit, AbortSignal and Promise, and nothing else: the library has no JSON-to-object mapper, so the shape of a response is a JsInterop native type that costs no code. This is the smallest dependency set of all the options, and the right choice for a handful of calls.

The data shapes

A native type with name = "Object" is "a plain JavaScript object with these properties"; no class is generated and no copying happens. The @JsOverlay factory is the only code, and it is inlined:

@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "Object")
public class BookJson {
  public double id;
  public String title;
  public String author;
  public int year;
  public int copies;

  @JsOverlay
  public static BookJson create(String title, String author, int year, int copies) {
    BookJson book = new BookJson();
    book.title = title;
    book.author = author;
    book.year = year;
    book.copies = copies;
    return book;
  }
}

@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "Object")
public class BookPageJson {
  public int total;
  public JsArray<BookJson> books;
}

Source: GWT — Coding Basics: JsInterop

The id is a double because a JavaScript number is a double: a long field in a native type is not a safe way to read a number from JSON, and ids above 2^53 lose precision whatever the Java type is. If the server uses 64-bit ids that large, send them as strings. JsInterop is described on the JsInterop page.

A small fetch wrapper

Hand-written calls repeat the same four decisions: the headers, the CSRF token, the deadline and what an error status means. Put them in one class:

public final class Rest {
  static final String XSRF_COOKIE = "XSRF-TOKEN";
  static final String XSRF_HEADER = "X-XSRF-TOKEN";
  static final double DEFAULT_TIMEOUT_MS = 5000;

  public static Promise<Response> send(String method, String url, Object body, double timeoutMs) {
    RequestInit init = RequestInit.create();
    init.setMethod(method);
    init.setCredentials("same-origin");
    init.setSignal(AbortSignal.timeout(timeoutMs));

    Headers headers = new Headers();
    headers.set("Accept", "application/json");
    if (body != null) {
      headers.set("Content-Type", "application/json");
      init.setBody(Global.JSON.stringify(body));
    }
    if (!isSafe(method)) {
      String token = Cookies.getCookie(XSRF_COOKIE);
      if (token != null) {
        headers.set(XSRF_HEADER, token);
      }
    }
    init.setHeaders(headers);

    return DomGlobal.fetch(url, init).then(res -> res.ok ? Promise.resolve(res) : failed(res));
  }

  public static <T> Promise<T> json(String method, String url, Object body) {
    return send(method, url, body, DEFAULT_TIMEOUT_MS)
        .then(res -> res.status == 204 ? Promise.resolve((Object) null) : res.json())
        .then(value -> Promise.resolve(Js.<T>uncheckedCast(value)));
  }

  static boolean isSafe(String method) {
    return "GET".equals(method) || "HEAD".equals(method) || "OPTIONS".equals(method);
  }

  private static Promise<Response> failed(Response res) {
    return res.text().then(text -> {
      String detail = res.status + " " + res.statusText;
      if (text != null && text.startsWith("{")) {
        JsPropertyMap<Object> problem = Js.asPropertyMap(Global.JSON.parse(text));
        Object d = problem.get("detail");
        if (d != null) {
          detail = res.status + " " + d;
        }
      }
      return Promise.reject(new HttpException(res.status, detail));
    });
  }
}

Source: MDN — AbortSignal.timeout(), MDN — Request.credentials, GWT Javadoc — Cookies

What each decision is, and why:

  • setSignal(AbortSignal.timeout(ms)). fetch has no timeout of its own. AbortSignal.timeout aborts the request after the delay and rejects the promise with a TimeoutError (reproduced below with a delay of 0). Without it a hung server leaves the screen waiting for ever.

  • setCredentials("same-origin"). It is the default, written out so the intent is reviewable: the session cookie goes to the page’s own origin and to no other.

  • Cookies.getCookie is the GWT class (com.google.gwt.user.client.Cookies); Elemental2 has no cookie API beyond the document.cookie string. The wrapper sends the token on every method except GET, HEAD and OPTIONS, the "safe" methods of RFC 9110.

  • An error status resolves the promise. fetch rejects only for network failures and aborts. The wrapper turns a response with ok == false into a rejection of its own type, HttpException, which carries the status and the detail of the problem document.

  • The Java exception is the rejection value. Promise.reject(new HttpException(...)) rejects with the Java object, so a later handler can test error instanceof HttpException. I did not test a throw inside a callback; the explicit reject is the form that was tested.

HttpException is a plain RuntimeException with an int status.

Typed calls

public final class BooksClient {
  private static final String BASE = "/api/books";

  public static Promise<BookPageJson> list(int start, int length) {
    return Rest.json("GET", BASE + "?start=" + start + "&length=" + length, null);
  }

  public static Promise<BookJson> get(long id) {
    return Rest.json("GET", BASE + "/" + id, null);
  }

  public static Promise<BookJson> create(BookJson draft) {
    return Rest.json("POST", BASE, draft);
  }

  public static Promise<BookJson> update(long id, BookJson book) {
    return Rest.json("PUT", BASE + "/" + id, book);
  }

  public static Promise<Object> delete(long id) {
    return Rest.json("DELETE", BASE + "/" + id, null);
  }
}

Source: MDN — Using the Fetch API

Path segments that come from users must be encoded with Global.encodeURIComponent (and query values with URLSearchParams, see the DOM & Elemental2 page); the ids above are numbers, so the strings need no encoding.

Running a whole conversation

The entry point chains the calls. The first lines show the shape; the other steps (update, delete, an invalid book, an unknown id, a write without a token, a timeout, an HTML page parsed as JSON, a cross-origin call) follow the same pattern:

BooksClient.list(0, 2)
    .then(page -> {
      log("list         : total=" + page.total + " returned=" + page.books.length);
      for (int i = 0; i < page.books.length; i++) {
        BookJson b = page.books.getAt(i);
        log("  book       : #" + (long) b.id + " " + b.title + " (" + b.year + ")");
      }
      return BooksClient.get(2);
    })
    .then(book -> {
      log("get(2)       : " + book.title + " by " + book.author);
      log("xsrf cookie  : " + (Cookies.getCookie(Rest.XSRF_COOKIE) != null ? "present" : "missing"));
      return BooksClient.create(BookJson.create("Dune", "Frank Herbert", 1965, 2));
    })
    .then(created -> {
      log("create       : id=" + (long) created.id + " " + created.title);
      created.copies = 5;

Adapting a Promise to an AsyncCallback

Presenters written for the GWT-RPC style (see the MVP page, Activities and Places) keep working if the client returns an AsyncCallback. An adapter is five lines:

public static <T> void call(Promise<T> promise, AsyncCallback<T> callback) {
  promise.then(
      value -> {
        callback.onSuccess(value);
        return null;
      },
      error -> {
        callback.onFailure(error instanceof Throwable ? (Throwable) error : new RuntimeException(String.valueOf(error)));
        return null;
      });
}

Source: GWT Javadoc — AsyncCallback

The two-argument then is deliberate: an exception thrown by onSuccess is not routed to onFailure, so a bug in the presenter is not reported as a network error. This is also the shape of the bridge to the RequestBuilder style (see RequestBuilder, JSON & XML): a RequestCallback becomes a Promise in the same way.

Mapping JSON without a library

There are three ways to turn a response into Java without a mapper, in order of cost:

Table 4. JSON mapping without a library
Way When Limits

Native JsInterop type (BookJson) read from Response.json()

the usual choice; zero code per property

no validation: a missing field is undefined; long and Date are not supported by JSON itself

JsPropertyMap (Js.asPropertyMap)

a payload whose shape you do not control, or a map of unknown keys

every access is a string key and an Object

JsonUtils and JSONParser (GWT’s own classes)

old code, and the JSONValue tree model

described on the RequestBuilder, JSON & XML page

A library mapper (next sections) gains real Java objects with getters, setters, collections and annotations, and loses the zero-code property: every DTO has a generated serializer and deserializer in the compiled output.

DTOs, the service and the call

A DTO is a plain class annotated @JSONMapper; a service is an interface annotated @RequestFactory with Jakarta REST annotations:

@JSONMapper
public class BookDto {
  public Long id;
  public String title;
  public String author;
  public int year;
  public int copies;
}

@JSONMapper
public class BookPageDto {
  public int total;
  public List<BookDto> books;
}

@RequestFactory(serviceRoot = "/api")
public interface BooksService {

  @GET
  @Path("books")
  BookPageDto list(@QueryParam("start") int start, @QueryParam("length") int length);

  @GET
  @Path("books/{id}")
  BookDto get(@PathParam("id") long id);

  @POST
  @Path("books")
  BookDto create(@RequestBody BookDto draft);
}

The annotation types come from jakarta.ws.rs (GET, POST, Path, PathParam, QueryParam) and from org.dominokit.rest.shared.request.service.annotations (RequestFactory, RequestBody), and JSONMapper from org.dominokit.jackson.annotation. javac runs the processor during mvn compile and writes, for this probe, seven files to target/generated-sources/annotations: BooksServiceFactory, and for each DTO a BookDto_MapperImpl, a BookDtoBeanJsonSerializerImpl and a BookDtoBeanJsonDeserializerImpl (the same three for the page). The generated factory has one method per interface method, returning a ServerRequest<RequestType, ResponseType>:

public ServerRequest<Void, BookPageDto> list(int start, int length) {
  BooksService_list instance = new BooksService_list();
  ParameterSetter.setParameter(instance, "start", () -> start, "Query");
  ParameterSetter.setParameter(instance, "length", () -> length, "Query");
  // ... meta parameters for GET and the path "books"
  return instance;
}

and the call reads like a promise chain: onSuccess, onFailed, then send().

DominoRestConfig.initDefaults() must run before the first request. The interceptor copies the CSRF cookie into the header, using the RequestInterceptor interface that the library documents with a token example:

public class XsrfInterceptor implements RequestInterceptor {
  @Override
  public void interceptRequest(ServerRequest request, ContextWait<ServerRequest> contextWait) {
    String token = Cookies.getCookie("XSRF-TOKEN");
    if (token != null) {
      request.setHeader("X-XSRF-TOKEN", token);
    }
    contextWait.complete(request);
  }
}

Source: GitHub — DominoKit/domino-rest

ContextWait is org.dominokit.domino.api.shared.extension.ContextAggregator.ContextWait (from domino-aggregator-shared, a transitive dependency). The request metadata in this version has the Java method name but not the HTTP verb (RequestMeta has getMethodName, not getMethod), so this interceptor adds the header to every request. That is harmless on a same-origin GET and the server ignores it, but it must never be used to send the token to another origin.

AutoREST

AutoREST (com.intendia.gwt.autorest) generates a model from a JAX-RS interface whose methods return RxJava 2 types: Single<T> for one JSON object, Observable<T> for a JSON array, Completable for no body. It does not map JSON itself: the GWT module’s RequestResourceBuilder uses XMLHttpRequest and JSON.parse and returns whatever object the parse produced, so DTOs are JsInterop native types, like the Elemental2 probe above. The same interface can be implemented by a JAX-RS server, which is the idea of the project: one definition, a client generated for GWT, the JVM or Android. That does not apply to a Spring MVC server, whose controllers do not use JAX-RS annotations.

Calling third-party JSON services through a server-side proxy

A page cannot call just any JSON API from the browser: the same-origin policy blocks a response from another origin unless that origin sends CORS headers (What is CORS? explains the mechanism). The old workaround, JSONP, runs the response as a script and is described with its risks on the RequestBuilder, JSON & XML page. The safe and still standard answer is a server-side proxy: the browser calls your own origin, and your server calls the third party. This is also a security boundary: API keys for the third party live on the server and never in the compiled JavaScript, and the server decides what comes back.

sequenceDiagram participant B as GWT client participant S as Bookshelf server participant C as Third-party catalogue B->>S: GET /api/isbn/9780132350884 (same origin) Note over S: validates the ISBN, builds the URL itself S->>C: GET /isbn/9780132350884.json (timeouts) C-->>S: JSON with many fields S-->>B: JSON with title and number_of_pages only

A Bookshelf screen can fill a book form from an ISBN. The controller below is the proxy. The browser sends the ISBN; the server builds the upstream URL, calls it with Spring’s RestClient, and returns only the fields the screen needs:

@RestController
public class IsbnProxyController {
  private final RestClient catalogue;

  public IsbnProxyController(RestClient.Builder builder, @Value("${bookshelf.isbn-service}") String baseUrl) {
    this.catalogue = builder.baseUrl(baseUrl).build();
  }

  public record IsbnBook(String title, Integer number_of_pages) {
  }

  @GetMapping("/api/isbn/{isbn}")
  public IsbnBook lookup(@PathVariable @Pattern(regexp = "[0-9]{13}") String isbn) {
    try {
      return catalogue.get().uri("/isbn/{isbn}.json", isbn).retrieve().body(IsbnBook.class);
    } catch (HttpClientErrorException.NotFound e) {
      throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Unknown ISBN");
    } catch (RestClientException e) {
      throw new ResponseStatusException(HttpStatus.BAD_GATEWAY, "Catalogue unavailable");
    }
  }
}

The rules that make a proxy safe:

Table 5. Rules for a server-side proxy
Rule Why

The client sends an identifier, never a URL

A proxy that fetches whatever URL the browser sends is a server-side request forgery (SSRF) endpoint into your internal network. The controller above builds the URL from a fixed base and a validated ISBN

Validate the identifier strictly

The @Pattern accepts exactly thirteen digits; the abc request never reaches the upstream call

Set connect and read timeouts

A slow third party must not hold your request threads; the two properties above bound the call

Return a DTO of your own, not the upstream body

Upstream fields can change or contain data you do not want to pass on. The response above has two fields of the upstream’s many

Map upstream failures to 502 or 404

The browser must not see upstream stack traces, headers or internal host names

Authenticate and rate-limit the endpoint

It spends your quota with the third party. Apply the same authentication and CSRF rules as the rest of the API

Cache where the terms of the service allow it

It saves quota and latency; keep the cache on the server

The client side of the proxy is one more Rest.json("GET", "/api/isbn/" + isbn, null) with a native type for the two fields. The XSRF, RPC & Server Security page covers XSRF, the same-origin policy and JSON hijacking in more depth than this page.

Security notes

Table 6. Security rules for REST clients in GWT
Risk Rule

Cross-site request forgery

Send the XSRF token header on every state-changing call (POST, PUT, PATCH, DELETE), as in Rest.send, the XsrfInterceptor and the RestyGWT dispatcher above. GWT-RPC has its own token mechanism, described on the XSRF, RPC & Server Security page. Keep SameSite on the session cookie

Authorisation in the client

All checks are on the server. The client code is public and can be edited in the developer tools

Untrusted JSON in the DOM

Put response text in the page with setText, setInnerText or textContent, never setHTML or innerHTML with concatenated data. For rich text use SafeHtml (see SafeHtml & XSS)

Unvalidated JSON shapes

A native JsInterop type is a promise, not a check: a missing property is undefined. Validate fields before using them in URLs, DOM or logic

Unsafe parsers

Use Response.json(), JSON.parse or a mapper. Never eval a response, and avoid JSONP for anything that matters

Entity leakage

Serve DTOs; do not return JPA entities, which can expose columns, lazy relations and internal ids

Secrets in the client

API keys for third-party services stay on the server (proxy section); the compiled JavaScript is readable by every visitor

Token in a URL

Put tokens in headers, not in query strings that end up in logs and the Referer header

Error details

Return problem documents with a stable detail and no stack traces; log the details on the server

Unbounded results

Cap length on the server, as the controller does, and paginate

Where older material is outdated

  • JSON and the proxy in GWT in Action. The book (2007, GWT 1.3 and 1.4) devotes its chapter 13 to JSON: the JSON format, the JSONParser and JSONValue classes, and a servlet that proxies a third-party search API for the page. The idea of a server-side proxy is unchanged and is the section above. What changed is everything around it: the server code there uses Apache Commons HttpClient, whose project page says it is end of life and was replaced by Apache HttpComponents; the third-party API it targets is not used here; and GWT now has JsonUtils.safeEval, JSONParser.parseStrict, JsInterop native types and Elemental2 fetch, so a hand-written parse of every value is rarely needed.

  • "A third party library". The Developer Guide still says the application can use JSON with RequestBuilder, JSNI "or a third party library" and does not name any. JSNI is the legacy route (see JSNI and overlay types); native types replace it.

  • XSRF in the Developer Guide. The guide’s XSRF protection is built for GWT-RPC (RpcToken, XsrfProtectedService). For a REST API the mechanism is the one in your server framework (here Spring Security), and the client’s job is to send the token header.

  • RestyGWT’s own home page. It still offers 2.2.0 as the latest download; the latest release on Maven Central is 2.2.7 (2020-05-17). The annotations are the javax.ws.rs ones (javax.ws.rs-api 2.0.1 and its sources on the class path), not the jakarta.ws.rs ones that domino-rest uses.

  • domino-jackson badge. The README says release 1.0.0-RC3; Central has 1.0.6.

What changed recently

  • 2025-09-15. Elemental2 1.3.2, the version used for the fetch probe, is the latest stable release; 1.4.0-RC1 followed on 2026-07-07.

  • 2025-12-30. domino-rest 2.0.0, after release candidates in 2024 (RC1 on 2024-01-14, RC2 on 2024-11-06). 2.0.1 followed on 2026-07-29 and 2.0.2 on 2026-09-24.

  • 2026-07-27. domino-jackson 1.0.6, following 1.0.5 on 2024-11-06.

  • 2023-11-22 to 2023-11-24. AutoREST 0.10 and 0.11, the first releases since 0.9 in 2018.

  • 2026-06-19. GWT 2.13.1, the compiler used here; Jakarta servlet artifacts (gwt-servlet-jakarta) were added in 2.11.0, which is how the Bookshelf server module serves RPC next to the REST API.

  • Spring Boot 4. Uses Jackson 3 (tools.jackson, version 3.1.5 in the probe) for JSON, RestClient for the proxy call, and needs spring-boot-starter-restclient for the auto-configured RestClient.Builder. The annotations that Jackson 3 still reads come from the 2.x annotation artifact (2.21 in the probe).
