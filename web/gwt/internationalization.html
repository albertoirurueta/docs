Internationalization

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against GWT 2.13.1 (2026-06-19), gwt-maven-plugin 1.3.0 (net.ltgt.gwt.maven), JDK 21 running the compiler with -sourceLevel 17, the Jakarta Servlet 6 server of the Bookshelf scenario and the org.gwtproject:gwt BOM, checked on 2026-10-09. Internationalization is mostly client and build knowledge: the interfaces and formatters live in the com.google.gwt.i18n packages, the translations are properties files and annotations that the GWT compiler turns into Java classes during deferred binding, and the choice of language is made in the browser by the bootstrap script. The server takes part only through the host page (it can write a meta tag, set a cookie or print a JavaScript object) and through whatever it uses for its own messages. Every listing on this page was compiled by the 2.13.1 compiler and run: a probe module com.example.i18n.Probe with the locales en, es and ar was loaded in headless Chrome 155 and inspected through its DOM, the Bookshelf additions ran as GWTTestCase classes in HtmlUnit, and the compiler messages and outputs are quoted as they were printed.

GWT does almost all locale work at compile time: a locale is a value of a compile-time property, every supported locale is compiled into its own JavaScript file, and the browser downloads only the one that matches. That makes translations type-safe (a missing argument is a compile error), makes unused messages disappear from the output and makes lookups as fast as a string literal, but it also means that adding a language is a rebuild, not a data change. The page walks through the whole model: the techniques and when to pick each, how a locale is declared, found and inherited, Constants and Messages with plural and select forms, the dynamic Dictionary alternative, locale-sensitive classes and resources, number, date and currency formatting, bidirectional text, the command-line tools and properties-file encoding, and a complete English and Spanish Bookshelf with plural review counts.

The model: one locale, one permutation

In GWT locale is a client property, exactly like user.agent. A client property can have any number of values, but all of them must be known when the compiler runs, because the compiler produces one optimized JavaScript program (a permutation) for every combination of property values. The bootstrap script <module>.nocache.js evaluates the properties in the browser, maps them to one permutation and loads that *.cache.js file only. The generators that write the Constants and Messages classes are deferred-binding generators, described on the deferred binding page. The Bookshelf declares two locales and the default two user.agent values, so the compiler printed Compiling 4 permutations and wrote this mapping (file compilation-mappings.txt):

Two consequences shape everything below.

  • Locales multiply permutations. Every locale you add multiplies the number of compiles and the build time (see the compiler page for the cost of permutations), so list only the languages you really translate and use runtime locales (see [runtime-locales]) for country variants.

  • The locale of a running page is fixed. There is no setLocale call; the page changes language by reloading with a different query parameter, cookie or meta value (see [switching]), after which the module restarts.

Choosing a technique

GWT offers several ways to internationalize, and a real application mixes them. The Developer Guide starts with a decision list; this table puts it in one place, with the cost of each approach from the guide and the probe.

Typed values loaded from properties: String, String[], int, float, double, boolean and Map. Labels, menu texts, configuration such as a page size.

The rest of the Developer Guide advice reduces to four rules of thumb:

  • writing code from scratch: start with Messages for text and Constants for typed values;

  • you have existing properties files: let I18NSync (see [tools]) generate the interfaces from them;

  • you add GWT to a page that already has a localization system on the server: use Dictionary;

  • you only want properties files delivered to the client regardless of language: use Constants with no locale-specific files.

Setting up a module

A module that uses internationalization inherits the I18N module. com.google.gwt.user.User already inherits it (the probe compiled without the explicit line), so the inherits element is optional but harmless and makes the dependency visible. Locales are added with extend-property; the only locale that exists without any declaration is the literal value default.

<module>
  <inherits name="com.google.gwt.user.User" />
  <inherits name="com.google.gwt.i18n.I18N" />

  <!-- 1. the full list of supported locales -->
  <extend-property name="locale" values="en,es" />
  <!-- 2. remove the 'default' locale permutation -->
  <set-property name="locale" value="en,es" />
  <!-- 3. use English wherever no locale is requested or matched -->
  <set-property-fallback name="locale" value="en" />
</module>

Source: GWT Developer Guide — i18n Locale: The Default Locale

The three lines are the recipe from the Developer Guide and they are what the Bookshelf module uses:

  1. extend-property adds the values. values takes a comma-separated list, so one element can add several locales.

  2. set-property with the same list restricts the permutations to the listed values, which removes the default permutation.

  3. set-property-fallback names the real language that answers when the requested locale is unknown (?locale=zz) or absent.

Why bother? The default locale has no language, so the Developer Guide warns that "many things will produce surprising results" in it: only a small set of currencies is supported and no plural forms at all. The same gap shows up as a compiler warning about an unknown plural form (see the plural forms section and the pitfalls table). The probe module with three locales and the three-line recipe printed Compiling 6 permutations (3 locales x 2 user agents); leaving default in would have added two more.

Encoding

The Java properties format is ISO-8859-1 by default, but GWT reads these files as UTF-8, so accented and non-Latin characters can be written directly and native2ascii is no longer needed. Three places must agree:

  1. the properties files are saved as UTF-8 (set the encoding in the IDE, and project.build.sourceEncoding to UTF-8 in the parent POM, as the Bookshelf does, so resource copying does not re-encode them);

  2. the Java sources are UTF-8 for the same reason (the compiler plugin takes the same property);

  3. the host page declares <meta charset="utf-8"> in its head and is served as UTF-8, otherwise correctly compiled text appears garbled.

The probe checked what happens when this goes wrong. A Spanish file saved as ISO-8859-1 compiled without an error or a warning and displayed the replacement character: appName=Estanter�a. Unicode escapes also work, as in any Java properties file: Estanter\u00eda in the file displayed Estantería. The Developer Guide tutorial still writes Ä and ü HTML entities in its German properties files from the time when UTF-8 was not available; with UTF-8 files and a UTF-8 host page, write the characters themselves, because an entity in a String message that goes through setText would be shown literally.

Points worth knowing:

Messages

Messages is the interface for text with parameters. Each method returns a String (or SafeHtml, see [safehtml-messages]), its parameters match the {0}, {1} placeholders of the message, and the compiler checks that the message uses exactly the arguments the method declares. The message syntax follows java.text.MessageFormat with GWT extensions (the choice format type is not supported; plural and select forms replace it), and the compiler removes what it can: unused methods vanish and the localized strings are inlined.

# ErrorMessages.properties

  String permissionDenied(int errorCode, String username);

Usually the default text goes into the source with @DefaultMessage, and properties files add the other languages. The Bookshelf’s catalogue line is the smallest realistic message:

Quoting rules

MessageFormat quoting is the first thing that bites. A single quote starts a quoted section, so the apostrophe in an English default is written twice, and text that must not be treated as a placeholder is quoted:

@DefaultMessage("It''s {0} and ''{0}''")
String apostrophe(String x);      // "It's x and 'x'"

@DefaultMessage("Saved \"{0}\"")
String saved(String title);       // Java string escapes for double quotes are ordinary Java

Source: GWT Developer Guide — i18n Messages: Overview

A single apostrophe is not silently swallowed as it is in plain MessageFormat: the 2.13.1 generator refuses it with [ERROR] Error parsing 'It's {0}'. The official tutorial states the same rule ("replace them with two consecutive single quotes in the properties files").

Plural forms

Most languages change the word for a counted thing with the count, and the rules differ: English separates 1 from the rest, French uses the singular for 0 and 1, Arabic has five special forms besides the default, and some languages have no plural at all. GWT ships plural rules for hundreds of languages and applies them to the parameter marked @PluralCount.

The Bookshelf shows review counts under each title. The default (English) text sits in the annotations:

@DefaultMessage("{0,number} reviews")
@AlternateMessage({"=0", "No reviews yet", "one", "{0,number} review"})
@Description("Number of reader reviews of a book, shown under its title")
String reviews(@PluralCount int count);

@DefaultMessage is the text for every count that has no entry (the English plural), "one" is the singular and "=0" is an exact value that wins over the rules: it is nicer to say "No reviews yet" than "0 reviews". Other languages put their forms in the properties file with a bracket syntax that GWT invented because properties files have no plural support:

# AppMessages_es.properties
reviews={0,number} reseñas
reviews[\=0]=Aún no hay reseñas
reviews[one]={0,number} reseña

"=N" forms (exact values), @Offset and list formatting handle the cases where grammar rules are not enough. Both are demonstrated by a message that shows who liked a book; the offset subtracts the two names that are shown before the plural rule decides between "and one other" and "and N others":

SafeHtml messages

When a message contains markup and its result goes into an HTML context (the content of an HTML or InlineHTML widget), declare the method with the return type com.google.gwt.safehtml.shared.SafeHtml. The generator then HTML-escapes every String argument before substitution and leaves SafeHtml arguments alone, which is how cross-site scripting through message parameters is prevented:

@DefaultMessage("A <strong>{0} error</strong> has occurred: {1}.")
SafeHtml errorHtml(String error, SafeHtml details);

SafeHtml html = msgs.errorHtml("<404>", SafeHtmlUtils.fromSafeConstant("<em>missing</em>"));
errorBar.setHTML(html);          // html.asString():
// A <strong>&lt;404&gt; error</strong> has occurred: <em>missing</em>.

Source: GWT Developer Guide — i18n Messages: SafeHtml Messages

Rules of the 2.13.1 generator, observed in the probe:

  • a method with a SafeHtml argument must return SafeHtml; a String result is refused with [ERROR] Message methods with SafeHtml arguments can only have SafeHtml return type;

  • the Developer Guide says that a parameter inside a tag, such as <span class="{0}">, is not allowed. The 2.13.1 generator accepted it and wrote <span class="a&quot; onclick=&quot;alert(1)">tag</span> for the argument a" onclick="alert(1), so the value was escaped rather than rejected. Do not rely on that: put dynamic values in text positions and choose attribute values from a fixed set;

  • translators may change the markup in the properties file (the Spanish errorHtml entry keeps the <strong> tag), so review translations of SafeHtml messages like code. The SafeHtml & XSS page describes how to build SafeHtml values.

For user-supplied data that is not markup, never concatenate it into HTML; use setText or a SafeHtml message.

Dynamic strings: Dictionary

com.google.gwt.i18n.client.Dictionary reads strings that the host page defines as a JavaScript object. It ignores the locale property completely: the server renders the right strings into the page, and the same compiled application works with any set of translations that exists on the server. It is meant for adding a GWT module to an application that already has a server-side localization system.

<!doctype html>
<html>
  <head>
    <meta charset="utf-8">
    <script>
      var bookshelfStrings = { title: "Bookshelf", greeting: "Hello" };   // printed by the server, in the user's language
    </script>
  </head>
  <body>
    <script src="bookshelf/bookshelf.nocache.js"></script>
  </body>
</html>
Dictionary dict = Dictionary.getDictionary("bookshelfStrings");
Window.setTitle(dict.get("title"));            // "Bookshelf"
Set<String> keys = dict.keySet();              // [greeting, title]
Collection<String> values = dict.values();

Source: Javadoc — Dictionary

The probe produced the two failure messages (both are `java.util.MissingResourceException`s):

  • an unknown key: Cannot find 'nope' in Dictionary bookshelfStrings;

  • an unknown object: 'noSuchDict' is not a JavaScript object and cannot be used as a Dictionary.

Everything is looked up at run time: there is no type checking, keys cannot be validated by the compiler, the compiler cannot remove unused values and the code is larger and slower than static internationalization. In return, adding a language does not need a rebuild. Security notes: the server must emit the object as proper JavaScript (escape quotes, </script> and line separators, or print the strings through a JSON encoder), and the application must treat dictionary values as plain text (setText, a Label) unless the server guarantees they are safe HTML.

Writing the locale from the host page

A server-rendered host page can choose the locale itself, for instance from the user’s profile or from the Accept-Language header, and print it as the meta tag:

<!doctype html>
<html>
  <head>
    <meta charset="utf-8">
    <title>Bookshelf</title>
    <meta name="gwt:property" content="locale=es">
    <script src="bookshelf/bookshelf.nocache.js"></script>
  </head>
  <body>
    <noscript>Bookshelf needs JavaScript.</noscript>
  </body>

A meta or cookie value is plain text that the visitor controls, so the server should validate it against the list of supported locales before printing it into the page (and never print it unescaped). If the module is embedded in an existing page that decides the locale in some other way, write a property provider in the module XML: a JavaScript fragment that returns the value. Runtime locales

Sometimes the translations are the same but country-specific details differ: one Spanish translation for all of Latin America, yet Argentinian pesos and Mexican number separators. <extend-configuration-property name="runtime.locales" value="es_MX" />

Switching language at run time

A language selector therefore stores a choice and reloads the page. The Bookshelf’s LocaleSwitcher builds its items from LocaleInfo, writes the choice into the cookie named by locale.cookie and reloads; the cookie is read by the bootstrap script on the next load:

public class LocaleSwitcher extends ListBox {
  public LocaleSwitcher() {
    String current = LocaleInfo.getCurrentLocale().getLocaleName();
    for (String name : LocaleInfo.getAvailableLocaleNames()) {
      if ("default".equals(name)) {
        continue;
      }
      addItem(LocaleInfo.getLocaleNativeDisplayName(name), name);
      if (name.equals(current)) {
        setSelectedIndex(getItemCount() - 1);
      }
    }
    addChangeHandler(event -> {
      String cookie = LocaleInfo.getLocaleCookieName();
      Date expires = new Date(System.currentTimeMillis() + 365L * 24 * 60 * 60 * 1000);
      Cookies.setCookie(cookie, getSelectedValue(), expires, null, "/", false);
      Window.Location.reload();
    });
  }
}

A GWTTestCase in the en permutation confirmed the items en=English and es=español, the selected item en and the cookie name bookshelf_locale. The sequence in the browser is:

sequenceDiagram participant U as User participant S as LocaleSwitcher participant B as Browser participant N as nocache.js U->>S: picks Español S->>B: Cookies.setCookie(bookshelf_locale, es) S->>B: Window.Location.reload() B->>N: loads the host page again N->>N: query string, then cookie finds es N->>B: loads the es permutation B->>U: Bookshelf in Spanish

The cookie is not HttpOnly (the page script writes it), so any script in the page can change it; treat it as a preference, never as authorization. Do not store anything secret in it. Also pass false as the secure flag only on plain HTTP development servers; in production serve the site over HTTPS and set the flag to true. The alternative that needs no cookie is a link with ?locale=es (the UrlBuilder from Window.Location.createUrlBuilder() replaces the parameter and keeps the rest), which is also shareable and bookmarkable.

Numbers, dates and currencies

GWT does not emulate java.text.DecimalFormat, java.text.DateFormat or java.util.Currency. It offers NumberFormat, DateTimeFormat, CurrencyList and CurrencyData in com.google.gwt.i18n.client, whose big difference from the JRE is that the locale-specific logic is selected by deferred binding, so only the code for the compiled locale is in each permutation. The data comes from the Unicode CLDR. The 2.9.0 release notes (2020-05-13) record "Updates CLDR to version 34" as the latest update; later releases do not mention a new CLDR version, so expect names and patterns of that vintage and use the browser’s Intl object through JsInterop when you need newer data. The Bookshelf scenario binds Intl.NumberFormat with a few lines (see the JsInterop page).

Bidirectional text

Arabic, Hebrew, Persian and Urdu are written right to left (RTL), and a mix of RTL and left-to-right (LTR) text in one paragraph needs care. GWT has three layers:

  • Locale awareness: LocaleInfo.getCurrentLocale().isRTL() is true for the compiled locale ar (and false for en and es); LocaleInfo.hasAnyRTL() tells whether any compiled locale is RTL. BidiPolicy.isBidiEnabled() is true when at least one compiled locale is RTL, and widgets consult it; the module property gwt.forceBidi (default false) can force it on.

  • Direction of elements and widgets: HasDirection.Direction is the enum RTL, LTR, DEFAULT (inherit). com.google.gwt.i18n.client.BidiUtils reads and writes the dir property of a DOM element with getDirectionOnElement and setDirectionOnElement. Label implements HasDirection and HasDirectionalText, so it has setDirection, getDirection, getTextDirection and setText(String, Direction).

  • Direction estimation: for text of unknown direction, setDirectionEstimator(true) on a widget makes it guess from the content (WordCountDirectionEstimator and FirstStrongDirectionEstimator are in com.google.gwt.i18n.shared), and BidiFormatter wraps strings in span or Unicode marks so that, for example, an English title inside an Arabic sentence does not reorder the punctuation.

// Direction of the whole page follows the locale
Direction dir = LocaleInfo.getCurrentLocale().isRTL() ? Direction.RTL : Direction.LTR;
BidiUtils.setDirectionOnElement(Document.get().getBody(), dir);

// A label that works out its own direction from its text
Label title = new Label("שלום עולם");
title.setDirectionEstimator(true);                 // getTextDirection() is RTL

// Force a direction
Label latin = new Label("Hello");
latin.setDirection(Direction.RTL);

Source: Javadoc — BidiUtils and Javadoc — HasDirection

The probe printed body dir=rtl for ?locale=ar and body dir=ltr for en, and the Hebrew label reported RTL from getTextDirection() and BidiUtils.getDirectionOnElement. Styles and graphics follow the direction too: CssResource flips left and right properties for RTL locales unless a rule is marked as not flippable (GSS has @noflip, see Styling: CSS & GSS), and @ImageOptions(flipRtl = true) on an ImageResource mirrors arrows and disclosure icons. LocaleInfo.isRTL() is the decision point for all of them.

  @DefaultMessage("Catalogue")
  String catalogue();

  @DefaultMessage("{0,number} reviews")
  @AlternateMessage({"=0", "No reviews yet", "one", "{0,number} review"})

}

Pitfalls

The messages below were printed by the 2.13.1 compiler for the probe module with one deliberately broken change per row, or by the JavaScript the compiler produced. Compiler errors of the generator are normally followed by a second, generic line that is the real failure of the build: [ERROR] Line 48: Failed to resolve 'com.example.i18n.client.BookMessages' via deferred binding, because the GWT.create could not complete. Search the log for the first [ERROR] above it.

Symptom (message as printed) Cause Fix

[WARN] Plural form 'one' unknown in com.google.gwt.i18n.client.impl.plurals.DefaultRule: ignoring, then 1 reviews at run time (test: expected: <1 review>, actual: <1 reviews>)

The English plural forms are in the annotations only. Without _en.properties the English class is generated with the language-less rule, which has no one.

Add AppMessages_en.properties (even with only a comment). Remove the default locale from the module.

[ERROR] Argument 2 beyond range of arguments: {0} de {1} ({2})

A translation uses more placeholders than the method has parameters.

Fix the translation or add the parameter.

[ERROR] Required argument 1 not present: {0} de autor

A translation omits a parameter that the method declares.

Add the placeholder, or mark the parameter @Optional.

[ERROR] No resource found for key 'reviews.header' followed by a MissingResourceException stack trace

A method has no @DefaultMessage (or default value annotation) and the properties files do not define its key.

Add the default annotation or the key to the suffix-less file.

[ERROR] diez could not be parsed as a number.

A Constants property is not a valid int, float or double.

Correct the value in the properties file.

[ERROR] Error parsing 'It's {0}'

A single apostrophe in a message.

Write It''s {0}.

[ERROR] reviews: PluralCount parameter must be int, short, array, or List

@PluralCount on a double or another type.

Use int, short, an array or a List.

[ERROR] Message methods with SafeHtml arguments can only have SafeHtml return type

A Messages method takes a SafeHtml parameter and returns String.

Return SafeHtml.

[WARN] Plural form 'few' unknown in com.google.gwt.i18n.client.impl.plurals.DefaultRule_es: ignoring

A translation uses a plural form the language’s rule does not have.

Use only the forms of that language (see the Plural Forms section).

[WARN] In locale 'ar', required plural forms are missing: [few, none, many, two]

A locale has no translation for a message with plural forms.

Add the forms to the _ar file, or drop the locale.

java.util.MissingResourceException: Cannot find constant 'poetry'; expecting a method name

ConstantsWithLookup.getString with a name that is not an accessor.

Check the name, or catch the exception for data-driven keys.

Cannot find 'nope' in Dictionary bookshelfStrings and 'noSuchDict' is not a JavaScript object and cannot be used as a Dictionary

A key that the host page object lacks, or a missing/typo’d host variable.

Define the object before the bootstrap script and validate keys.

Uncaught Error: java.lang.NumberFormatException: 1.234,5 (console, in the en permutation)

NumberFormat.parse with separators of another locale.

Parse with the user’s locale, catch NumberFormatException, and exchange numbers with the server as plain double/ISO text.

No message at all; Spanish shows English

The _es.properties file is in another package than the interface, or its suffix is wrong (it must be Interface_es.properties in the same package).

Move it; the matching is silent.

No message at all; Estanter�a

The properties file is saved as ISO-8859-1 but read as UTF-8.

Save as UTF-8, or use \u00ed escapes; keep project.build.sourceEncoding at UTF-8.

A String[] with a comma in a value has one element too many (Historia\, política gave four elements, not three)

The Developer Guide shows a single backslash, but the properties loader consumes one, so the value reaches GWT as a bare comma.

Write two backslashes in the file: Historia\\, política.

?locale=es-ES shows English

The query value uses a hyphen; GWT locales use underscores.

?locale=es_ES. The browser-language source converts the hyphen for you; a query parameter is not converted.

?locale=es_AR shows the number and currency formats of es (euro, not peso)

es_AR is not compiled, so the suffix is stripped to es.

Declare runtime.locales for country-specific number, currency and date data (see the runtime locales section), or compile the locale.

?locale=zz ignores the cookie

The first source with a value wins, even if it matches nothing.

Validate the value in the page that links to the application.

Arabic numbers in an Arabic-locale page whose server expects 1234.5

ar formats digits as Arabic-Indic.

NumberFormat.setForcedLatinDigits(true) for formatting, and send numbers to the server as double or ISO text.

Recent changes and the outdated material

Table 20. What changed since the older material
Version Change

2.9.0 (2020-05-13)

CLDR data updated to version 34, the latest CLDR update in the release notes.

2.10 to 2.13.1

No internationalization entry in the release notes; the generator, the formatters and the locale provider described on this page are those of the 2.13.1 tag.

2.13.1 source

The individual DateTimeFormat getters (getShortDateFormat() and the like) are @Deprecated in favour of getFormat(PredefinedFormat), @PluralText is deprecated in favour of @AlternateMessage, and MessageCatalogFormat is deprecated in favour of MessageCatalogFactory.

  • The Manning book (Hanson and Tacy, 2007, GWT 1.3 and 1.4) covers Constants and the locale property in its third chapter and Constants, ConstantsWithLookup, Messages, Localizable and Dictionary in its fifteenth. Its techniques still exist and work the same way, but there are no annotations (the book keeps every default in a properties file), no plural or select forms, no SafeHtml messages, no runtime locales, no locale.cookie, no LocaleInfo-based switching and no UiBinder i18n. Its project tooling (applicationCreator, Eclipse .launch files, -i18n scripts with GWTCompiler) is gone: use Maven and I18NSync from the classpath.

  • The official pages. The Developer Guide describes @Generate(String[] formatFQCN, ...) where the element is format; it shows a single-backslash comma escape that does not survive the properties loader (use \\,); it prints formatting examples (1,2345.6789, 1.2345E4, Dec 18, 2007) that no longer match what the formatters print; its tutorial uses HTML entities in properties files; and some UiBinder i18n samples use the ui: prefix on attributes and the older placeholder names. The compiled code on this page is the reference.

  • Packages. com.google.gwt.i18n.shared contains the types that are safe to use on the server and in shared code (DateTimeFormat, Localizable, BidiFormatter, the direction estimators, GwtLocale), while com.google.gwt.i18n.client is client-only. The org.gwtproject.* modules offer J2CL-ready replacements for parts of this API; see J2CL & the Future.

The same idea in other stacks

Every web stack externalizes text into per-language resources, selects a locale per request or per user, and formats numbers and dates by locale; GWT’s twist is that all of it is resolved at compile time.

  • Thymeleaf internationalization: message expressions, where the texts come from and how the locale is resolved, the server-rendered counterpart of Messages and the locale property.

  • ASP.NET Core globalization and localization: IStringLocalizer, .resx conventions and the request-localization culture providers, comparable to the query string, cookie and browser-language sources of the GWT locale provider.

  • Next.js internationalization: locale routing strategies, dictionaries per locale in server components and next-intl, the JavaScript-framework counterpart.
