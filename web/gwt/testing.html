This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against GWT 2.13.1 (2026-06-19), gwt-maven-plugin 1.3.0, JDK 21 with -sourceLevel 17, the HtmlUnit 2.55.0 and Jetty 9.4.58 that the GWT BOM manages for the test runner, and the Jakarta Servlet 6 stack of the modular-webapp archetype, checked on 2026-10-09. It is about build and tooling (how the tests are compiled and run), about client code that is tested after compilation to JavaScript, and about shared and server code that is tested as plain Java. Every command and every output block below was produced in a private copy of the Bookshelf scratch application of this section: a bookshelf-shared, a bookshelf-client and a bookshelf-server module, 19 JUnit tests and 2 Playwright tests.

A GWT application has three kinds of code and each needs a different kind of test. Most of the code is plain Java that never touches the browser, and it should be tested on the JVM in milliseconds. The code that calls GWT.create, uses JSNI or JsInterop, or builds widgets only works after the GWT compiler has processed it, and GWTTestCase exists for that. The whole application, deployed and driven through a browser, is the job of an end-to-end tool.

The Bookshelf test layout

The module bookshelf-client is compiled by the GWT compiler from the packages named by its <source> elements (client and shared). Everything in those packages is translated to JavaScript when a test module is compiled, including test classes that live there. That decides where each kind of test goes:

  client/BookshelfGwtTest.java          GWTTestCase  (inside the module source path, must be)
  client/CatalogAsyncGwtTest.java       GWTTestCase  (asynchronous tests)
  client/SpanishMessagesGwtTest.java    GWTTestCase  (a second test module)
  client/rpc/PingService.java           test-only RPC interface and its Async twin (client code)
  testserver/PingServiceImpl.java       test-only servlet (server code: outside the source path)
  suite/AllGwtTests.java                GWTTestSuite (JUnit-only class: outside the source path)
  unit/CatalogPresenterTest.java        plain JUnit (outside the source path)

bookshelf-server/src/test/java/.../server/   CatalogRepositoryTest, CatalogServiceImplTest

GWTTestCase classes must be on the module source path, because the compiler has to see their source. Plain JUnit classes, suites and servlets must be outside it. Section Pitfalls shows what happens when they are not. The rule is the same one the page about Activities and Places used for its navigation tests.

GWTTestCase

com.google.gwt.junit.client.GWTTestCase extends JUnit’s junit.framework.TestCase, so it is a JUnit 3 style class: the test methods are the public void methods whose names start with test, and annotations such as @Test are not used. It runs under the JUnit 4 provider that gwt:test selects. Under the same fully qualified name there is a second, translatable class (in the translatable source tree), which is what actually runs in the browser. The JVM-side class only starts the machinery and carries the result back.

A first test

A GWTTestCase subclass has one obligation: getModuleName() returns the name of a module whose source path contains the test class. The Bookshelf test module inherits the application module and pins what the permutations would otherwise multiply:

AppTest.gwt.xml
<?xml version="1.0" encoding="UTF-8"?>
<module rename-to="apptest">
  <inherits name="com.example.bookshelf.App" />
  <!-- One locale and one user agent keep the test compile to a single permutation -->
  <set-property name="locale" value="en" />
  <set-property name="user.agent" value="gecko1_8" />
  <!-- Mapped on the embedded Jetty 9 test server, relative to the module base URL -->
  <servlet path="/ping" class="com.example.bookshelf.testserver.PingServiceImpl" />
</module>

public class BookshelfGwtTest extends GWTTestCase {
  @Override
  public String getModuleName() { return "com.example.bookshelf.AppTest"; }

  public void testPluralMessages() {
    assertEquals("en", LocaleInfo.getCurrentLocale().getLocaleName());
    AppMessages msg = GWT.create(AppMessages.class);   // deferred binding runs in the test
    assertEquals("No copies", msg.copies(0));
    assertEquals("1 copy", msg.copies(1));
    assertEquals("3 copies", msg.copies(3));
  }

  public void testPlaceTokens() {
    AppPlaceHistoryMapper mapper = GWT.create(AppPlaceHistoryMapper.class);
    assertEquals("book:7", mapper.getToken(new BookPlace(7)));
    assertEquals(7L, ((BookPlace) mapper.getPlace("book:7")).getId());
  }

What happens during a run

sequenceDiagram participant M as gwt:test (forked JVM) participant S as JUnitShell participant J as Embedded Jetty 9 participant B as HtmlUnit browser participant R as GWTRunner (in the page) M->>S: GWTTestCase.run() calls JUnitShell.runTest() S->>S: compile synthetic module AppTest.JUnit S->>J: start the web server, serve junit.html and the module servlets S->>B: launch the run style on the module URL B->>J: load the compiled JavaScript R->>J: RPC asks for the next block of tests J-->>R: test class and method names R->>R: new test instance, gwtSetUp, test method, gwtTearDown R->>J: RPC reports the result or the exception S-->>M: TestResult passed, failed or errored

com.google.gwt.junit.JUnitShell is a subclass of the Dev Mode launcher. It builds a synthetic module named <module>.JUnit (here com.example.bookshelf.AppTest.JUnit) that inherits your test module and adds the JUnit runtime, compiles it, starts an embedded Jetty and launches the run style, which decides which browser loads the page. The page’s GWTRunner then pulls test blocks from the server over GWT-RPC, runs them and reports back. The JUnit module the synthetic module inherits turns on jre.debugMode and emulated stack traces, which is why failure traces in the reports show Java class and method names. The page-plus-server design is also why a test can fail with TimeoutException: The browser did not contact the server within 60000ms. (nothing loaded the page) and why the test module can declare <servlet> elements.

Module names and pure Java mode

  • One module name per test class is the key to speed: every distinct module costs one GWT compile. Put tests that need the same configuration in the same module and the same suite (see GWTTestSuite and one module per test class).

  • getModuleName() may return null. The test then runs as a plain JUnit test on the JVM ("pure Java mode"), isPureJava() returns true, and gwtSetUp/gwtTearDown still run. setForcePureJava(true) has the same effect.

  • The module needs the permutations pinned, or the test fails with an AssertionError (section Pitfalls). Two ways: a test module with <set-property> as above, or arguments on the command line (next sections).

gwtSetUp and gwtTearDown

setUp() and tearDown() are final in GWTTestCase. Override gwtSetUp() and gwtTearDown() instead; both are protected and run once per test method, inside the browser. The page of RootPanel is shared by all test methods of a module run, so a test that attaches widgets should clean up:

@Override
protected void gwtTearDown() {
  RootPanel.get().clear();
}

Asynchronous tests

A test method that returns ends the test, and GWT code cannot block. A test of a Timer (see Delayed Logic & Scheduler), an RPC call or an event therefore calls delayTestFinish(int) with a timeout, returns, and calls finishTest() from the callback. Three things can happen during the delay: finishTest() is called (success), an exception escapes from an event handler (error with that exception), or the delay expires (error with a TimeoutException). delayTestFinish and finishTest are protected final methods of GWTTestCase; calling delayTestFinish again resets the timeout, which is how events are chained.

The Bookshelf tests one Timer and one real GWT-RPC round trip against a test servlet. The servlet extends the javax flavour of RemoteServiceServlet because the embedded test server is Jetty 9 (javax.servlet); the Jakarta flavour is for the application server, not for the module <servlet> element.

Production mode, development mode and strictness

The official Testing page says that tests run in development mode by default and that -prod selects production mode. In 2.13.1 the shell’s developmentMode field is initialised to false, -devMode is the flag that turns it on, and -prod and -web are its negated aliases. Plain JUnit tests for presenters and other client logic

The cheapest test of GWT client code is no GWT test. The testing methodologies article puts it plainly: standard JUnit test cases run orders of magnitude faster than GWTTestCase, and a presenter that talks to its view through an interface needs no widget at all. The conditions are the ones from the Model-View-Presenter pattern (see Activities and Places):

  • the presenter receives the service interface and the view interface through its constructor,

  • it never calls GWT.create, new Label() or any JSNI/JsInterop method, so the JVM never needs the compiler,

  • the views are interfaces, so a fake or a mock stands in.

The Bookshelf CatalogPresenter is written that way (its class comment says "Plain Java: no GWT.create()"):

CatalogPresenterTest.java (fakes written by hand, no mocking library)
package com.example.bookshelf.unit;   // outside the module source path

public class CatalogPresenterTest {
  static class FakeService implements CatalogServiceAsync {
    boolean fail;

    @Override
    public void getBooks(int start, int length, AsyncCallback<BookPage> cb) {
      if (fail) {
        cb.onFailure(new RuntimeException("boom"));
      } else {
        cb.onSuccess(new BookPage(List.of(new Book(1, "T", "A", 2000, 1)), 42));
      }
    }
    // getBook and saveBook are empty
  }

  static class FakeDisplay implements CatalogDisplay {
    int total = -1;
    int start = -1;
    String error;

    @Override
    public void showRows(int start, List<Book> rows, int total) { this.start = start; this.total = total; }

    @Override
    public void showError(String message) { error = message; }
  }

  @Test
  public void loadPushesRowsToTheDisplay() {
    FakeDisplay d = new FakeDisplay();
    new CatalogPresenter(new FakeService(), d).load(10, 10);
    assertEquals(10, d.start);
    assertEquals(42, d.total);
    assertNull(d.error);
  }

  @Test
  public void failureIsReported() {
    FakeService s = new FakeService();
    s.fail = true;
    FakeDisplay d = new FakeDisplay();
    new CatalogPresenter(s, d).load(0, 10);
    assertEquals("boom", d.error);
  }
}

In production mode the code runs as JavaScript, so there is no bytecode to measure. In -devMode the bytecode runs, but it is loaded by GWT’s own class loader, which the agent does not instrument; the same run reported 0 for CatalogView and the places, and added JSNI errors such as Member 'stringTable' in JSNI reference '@com.google.gwt.user.client.rpc.impl.ClientSerializationStreamReader::stringTable' could not be found; expect subsequent failures to the log (the tests still passed). That is one more reason to keep logic out of the views, and the number for the client module must be read as "coverage of the presenters", not of the module. The GWTTestCase layer is judged by what it asserts, not by a percentage.

End-to-end tests with Playwright

The top of the pyramid drives a real browser against the deployed application, so it also covers the host page, the linker output, the servlet, the session and navigation. The page about E2E testing in real browsers compares Selenium, Playwright and Cypress and covers installation, headless runs, evidence capture and CI; this section only adds what is specific to a GWT application. A separate site-wide issue (#258) tracks Playwright, Cypress and Selenium coverage.

Start the application as in production (the Bookshelf runs from the Jetty plugin on port 9954 in these examples), then run a Playwright Test spec:

mvn -B verify -DskipTests
mvn -B org.eclipse.jetty.ee10:jetty-ee10-maven-plugin:12.1.10:run -pl bookshelf-server -Djetty.http.port=9954 &
npx playwright test
tests/catalogue.spec.js
const { test, expect } = require('@playwright/test');

test('the catalogue lists the first page of books', async ({ page }) => {
  await page.goto('/');
  await expect(page.getByText('1-10 of 25')).toBeVisible();
  await expect(page.getByRole('row', { name: /^Effective Java Joshua Bloch/ })).toBeVisible();
});

test('opening a book changes the history token', async ({ page }) => {
  await page.goto('/');
  await page.getByRole('row', { name: /^Effective Java Joshua Bloch/ }).getByRole('button', { name: 'Open' }).click();
  await expect(page).toHaveURL(/#book:/);
});

The playwright.config.js only sets use.baseURL to the server URL. This run used @playwright/test 1.64.0 and, because the browser revision it expects was not installed, an executablePath in launchOptions pointing to an already cached headless Chromium; a normal setup runs npx playwright install chromium once. Playwright for Java (Maven artifact com.microsoft.playwright:playwright, 1.63.0 on Central) has the same locators and suits teams that want the E2E tests next to the server tests; the choice does not change anything on the GWT side.

What is specific to GWT:

  • Wait for the application, not for the page. The host page loads bookshelf.nocache.js, which loads the permutation, which creates the widgets, then the catalogue is fetched over RPC. page.goto returns long before. The auto-waiting assertions (toBeVisible on the text 1-10 of 25) wait for the rendered result; sleeps are not needed.

  • Locate by role and text, never by class names. The generated CSS class names of an obfuscated GWT application (CFEWP3D-b-a in the Bookshelf’s compiled DataGrid) change with every compile. The DataGrid rows expose role="row" and the buttons their text, which is what the spec uses.

  • Make the data selectors unambiguous. The Bookshelf seeds 25 books, so Effective Java appears twice (Effective Java (copy 2)), and the first draft of the spec failed with a strict mode violation (section Pitfalls).

  • History tokens are part of the contract. toHaveURL(/#book:/) tests that the place changed, which is the observable effect of the activity and place wiring (see History and navigation).

  • Security features run for real here. The XSRF cookie and token, the Content-Security-Policy header and the session filter are only exercised end to end; a failing journey after a security change is the expected signal, not a flaky test. Do not disable XSRF protection to make the test pass.

Where older material is outdated

  • The Testing page says the tests run in development mode unless -prod is given. In 2.13.1 production mode is the default (above). The same page, its tutorial and the Eclipse launch files assume webAppCreator with -junit, which generated FooTest-dev.launch and FooTest-prod.launch files and an Ant build.xml; a Maven project does not use them.

  • @DoNotRunWith(Platform.HtmlUnit), shown in the HtmlUnit page and the release notes of 2.0, does not exist: the enum holds HtmlUnitBug, HtmlUnitLayout, HtmlUnitUnknown, Devel and Prod.

  • The HtmlUnit page names Firefox 38 emulation and the FF38,IE11 argument. The names are FF, Chrome, IE and Edge.

  • The Coverage page (EMMA, EclEmma, a patched emma.jar, ant devmode) is obsolete for Maven builds; use JaCoCo on the plain JUnit layer.

  • The Remote Testing page (Selenium RC servers, the Firefox profile with the GWT Developer Plugin, RemoteWeb) describes mechanisms that are removed (RemoteWeb, the plug-in) or deprecated (Selenium).

  • The book chapter on testing and deploying (JUnit basics, GWTTestCase and getModuleName, asynchronous tests with delayTestFinish/finishTest) was written for JUnit 3, GWT 1.x and the hosted-mode browser. The core API it teaches is unchanged; the run configuration, the browsers and the hosted mode are not. Its chapter parts on organising the compiled output and installing RPC servlets in a servlet container are covered, for 2.13, on the page about server integration and deployment.

Recent changes

  • 2.13.0 added -strict to the test arguments (the release notes say it helps to find compile issues in GWT libraries) and deprecated RunStyleSelenium for removal (issue #10222, opened 2025-12-10 and closed).

  • 2.10.0 updated the test runner to HtmlUnit 2.55.0 and Jetty 9.4.44 (the 2.13.1 BOM pins Jetty 9.4.58), which brought Promise support to unit tests.

  • 2.8.0 (RC1) deprecated classic Dev Mode and kept -devMode for tests as a temporary switch.

  • 2.14 (milestone, open): issue #10038, enable -strict for user tests, so a stricter default is possible later.
