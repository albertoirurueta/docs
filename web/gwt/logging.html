Logging

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against GWT 2.13.1 (2026-06-19), gwt-maven-plugin 1.3.0 and the Jakarta Servlet 6 stack of the modular-webapp archetype, with a JDK 21 toolchain and -sourceLevel 17, and was checked on 2026-10-09. Every output block was produced with the Bookshelf scenario of this section: a three-module application compiled to JavaScript, served by Jetty 12 (EE 10) and loaded in headless Chrome 155. It covers client code (the logging emulation that is compiled to JavaScript), shared code (a class that logs on both sides), server code (the remote logging servlet and the stack trace deobfuscator) and build settings (the properties and the compiler flag that decide what is left in the output).

Logging in a browser has an unusual constraint: the log lives in the user’s machine, in a console you cannot see. GWT therefore splits the problem in three. A compile-time switch decides how much logging exists at all, a set of handlers decides where a record goes on the client (console, popup, your own widget), and a remote handler can send records to the server, where the obfuscated stack trace is turned back into Java class and method names.

The logging emulation

GWT emulates a subset of java.util.logging, so the logging code has the same syntax as server code and can be shared. The classes live in the JRE emulation (see JRE emulation and shared code); what is output is decided by the logging modules described below.

Level

Source: GWT — JRE Emulation Reference: java.util.logging, GWT source — emulated Logger.java

What is not there matters, because it is a compile error and not a silent difference. The emulated Logger has no parameterised overloads (log(Level, String, Object) and log(Level, String, Object[])), no logp, logrb, entering, exiting, throwing, no Filter, no resource bundles and no getAnonymousLogger; there is no FileHandler, ConsoleHandler or SocketHandler, and no logging.properties (LogManager cannot read a configuration). The reproduced error messages are in the pitfalls table at the end of the page. Logger names form a tree exactly as on the server: Foo.Bar and Foo.Baz are children of Foo, and a name without a dot has the root logger (the empty name) as parent.

Adding logging to a module

The shortest recipe is the one in the Developer Guide: inherit the logging module and create a logger.

<!-- in the .gwt.xml file -->
<inherits name="com.google.gwt.logging.Logging"/>
private static final Logger LOG = Logger.getLogger(LoanDesk.class.getName());
...
LOG.log(Level.SEVERE, "Cannot renew book " + bookId, e);

Source: GWT — Logging: Super Simple Recipe for Adding Logging

The logging module is not part of com.google.gwt.user.User; the Bookshelf module lists it explicitly. What inheriting it changes is easy to misjudge, because the emulation is always compiled in, so code that uses Logger builds either way. The Developer Guide warns that logging still works without the module, because the emulation is always present, but that you then get no default handlers and no way to configure the root logger. That is the intended setup for a library: it logs through java.util.logging and lets the application that includes it decide whether anything is shown.

Console logging without the logging module

The properties behind the module are defined in Core.gwt.xml, so a module that does not inherit Logging can still turn on plain console output with one property. It is the cheapest option: it adds essentially no code.

<!-- the Logging module is not inherited -->
<set-property name="jre.logging.logLevel" value="INFO"/>

Compiled this way (the same sources, -setProperty jre.logging.logLevel=INFO) the production file was 247,179 bytes against 247,181 for the build without logging, and the browser console showed the records without timestamp or logger name, as written by the emulation’s internal SimpleConsoleLogHandler (excerpt):

Bookshelf starting
Cannot renew book 7
Exception: java.lang.IllegalStateException: Loan limit reached for book 7
Error: java.lang.IllegalStateException: Loan limit reached for book 7
    at W0.Xe [as Kb] (bookshelf-0.js:1779:162)

Source: GWT source (2.13.1) — Core.gwt.xml

The values of jre.logging.logLevel are OFF, SEVERE, WARNING, INFO and ALL, and the comment in Core.gwt.xml describes them: OFF compiles out all logging, the other values keep the framework and compile out the basic calls (fine(), info() and so on) below the level. It also notes that logger.log(Level.INFO, "foo") will not compile out, which the size measurements below confirm.

All of the configuration is done with deferred-binding properties, so each choice is a compile-time decision that produces different JavaScript (with -setProperty or <set-property> fixing one value, a single permutation results). Handlers and formatters

Handlers are attached to the root logger by LogConfiguration, an entry point that the logging module registers. Its onModuleLoad sets setUseParentHandlers(false) on the root logger, sets its level (from the logLevel URL parameter or from gwt.logging.logLevel) and adds one handler per enabled property, skipping any that the property turned into a NullLogHandler. A disabled handler is therefore not just silent but absent from the output. The replacement happens where LogConfiguration creates the handler through GWT.create, so a handler that you build with new is not affected by these properties.

Two formatters ship with GWT. TextLogFormatter writes the record date (Date.toString()), the logger name, a line break, LEVEL: message and, when asked, the stack trace; HtmlLogFormatter colours the record by level (red for SEVERE, orange for WARNING, green for INFO, blue for CONFIG, purple for the fine levels) and escapes <, > and tabs in the text. Both extend an internal FormatterImpl; the Developer Guide names them HTMLFormatter and TextFormatter, but the classes are HtmlLogFormatter and TextLogFormatter.

The popup is invasive, as the Developer Guide says: the run with gwt.logging.hasWidgetsHandler=ENABLED put a <div class="gwt-PopupPanel" style="left: 0px; top: 0px; position: absolute; ..."> over the application, and added about 11 KB to the JavaScript (see the size table). For a real application the Developer Guide recommends sending records to a panel you own.

A log area in your own page

HasWidgetsLogHandler takes any HasWidgets that accepts several add calls. The Bookshelf attaches one to the root logger when the page is opened with ?logpanel=1:

if (Window.Location.getParameter("logpanel") != null) {
  FlowPanel panel = new FlowPanel();
  RootPanel.get().add(panel);
  Logger.getLogger("").addHandler(new HasWidgetsLogHandler(panel));
}

Source: GWT — Logging: Different Types of Handlers

The serialised page then contained one coloured span with a code element per record, for example INFO: UNGUARDED-AUDIT 756 7 and SEVERE: Cannot renew book 7 followed by the stack trace with line breaks. Because the handler is created with new, it works whatever gwt.logging.hasWidgetsHandler says, but the logging itself must be enabled: in a gwt.logging.enabled=FALSE build the panel stayed empty. The widget is an HTML widget filled with formatter output, so if you write your own sink use setText or SafeHtml (see SafeHtml & XSS) for the record message.

Writing a handler

A handler extends java.util.logging.Handler and implements publish, flush and close. The custom handler in the remote section is a complete example; the points to remember are to honour isLoggable(record) (the handler level defaults to ALL), to set a Formatter if you format, and never to log from inside publish through a logger that the same handler receives. RemoteLogHandlerBase, the base class of SimpleRemoteLogHandler, shows the guard that GWT itself uses: it keeps a list of excluded logger names (WireActivityLogger) so that the failure of the transport is never sent through the same transport.

Shared code and the server

GWT emulates the API, but client and server are two separate logging worlds. The client has a root logger and a logger tree of its own, compiled into the JavaScript; the server uses the JVM’s java.util.logging (or whatever framework you bridge it to). A class in the shared module logs to whichever tree is active where it executes, and the Developer Guide advises against adding or changing handlers in shared code because the configuration code cannot behave the same on both sides.

The Bookshelf has a shared class that is used on both sides:

package com.example.bookshelf.shared;

import java.util.logging.Level;
import java.util.logging.Logger;

public final class LateFee {
  private static final Logger LOG = Logger.getLogger(LateFee.class.getName());

  private LateFee() {}

  public static long cents(int daysLate) {
    long cents = Math.min(daysLate, 30) * 25L;
    LOG.log(Level.INFO, "late fee for " + daysLate + " days is " + cents + " cents");
    return cents;
  }
}

Source: GWT — Logging: Client vs. Server-side Logging

The catalogue service on the server calls LateFee.cents(3), and so does the entry point in the browser. The two outputs differ in format and destination:

# Jetty console (server root logger, JDK SimpleFormatter)
Oct 09, 2026 1:28:25 AM com.example.bookshelf.shared.LateFee cents
INFO: late fee for 3 days is 75 cents

# browser console (client root logger, TextLogFormatter)
Fri Oct 09 01:28:31 GMT+200 2026 com.example.bookshelf.shared.LateFee
INFO: late fee for 3 days is 75 cents

Source: GWT — Logging: Client vs. Server-side Logging

The shared code uses string concatenation rather than {0} placeholders because the emulation has no parameterised log methods, and the JDK Logger would accept both. Use the Supplier forms (LOG.fine(() -> expensive())) when building the message is costly.

On the server nothing GWT-specific is needed: pick the framework the rest of the application uses. The remote logging code logs through java.util.logging, so with SLF4J and Logback the usual step is the jul-to-slf4j bridge, which routes JDK records to SLF4J once SLF4JBridgeHandler.install() has been called at startup (the SLF4J documentation also warns that bridging has a translation cost for disabled levels). The book of 2007 recommends Log4J for the server, which is still a valid choice; what changed is that the same API is now available in the browser.

Uncaught exceptions

The LogConfiguration entry point also installs an uncaught exception handler if none is set yet. When logging is enabled, an exception that nobody catches is logged at SEVERE with the exception message and stack trace:

// in the Bookshelf entry point, behind ?boom=1: nobody catches this
Scheduler.get().scheduleDeferred(() -> {
  throw new IllegalStateException("Unexpected failure in a scheduled command");
});

Source: GWT source (2.13.1) — LogConfiguration.java

# gwt.logging.enabled=TRUE
Fri Oct 09 01:29:14 GMT+200 2026 com.google.gwt.logging.client.LogConfiguration
SEVERE: Unexpected failure in a scheduled command

# gwt.logging.enabled=FALSE
Uncaught java.lang.IllegalStateException: Unexpected failure in a scheduled command

An application that calls GWT.setUncaughtExceptionHandler itself takes the place of that handler. One that only calls GWT.log, as the first version of the Bookshelf entry point did, reports nothing in production, because GWT.log is removed from production output; log through a Logger instead.

Remote logging

Records written in the browser are lost unless something sends them to the server. GWT ships a handler that does it with GWT-RPC, and the pieces to do it with anything else.

sequenceDiagram participant App as Browser (obfuscated JavaScript) participant H as SimpleRemoteLogHandler participant S as RemoteLoggingServiceImpl participant D as StackTraceDeobfuscator participant L as Server logger (java.util.logging) App->>H: Logger.log(SEVERE, message, thrown) H->>S: POST /bookshelf/remote_logging (GWT-RPC, header X-GWT-Permutation) S->>D: deobfuscateStackTrace(thrown, strongName) D->>D: read symbolMaps/strongName.symbolMap D-->>S: Java class, method, line S->>L: Logger.getLogger(name).log(record) S-->>H: null when logged, else an error text

SimpleRemoteLogHandler and the servlet

Enabling the handler is one property. The client then creates RemoteLoggingService, whose relative path is remote_logging, so the module base URL (/bookshelf/ for the Bookshelf, from rename-to) decides where it posts. The server needs a servlet mapped at that URL. In 2.13.1 the servlet exists in two packages: com.google.gwt.logging.server.RemoteLoggingServiceImpl for javax.servlet (artifact gwt-servlet) and com.google.gwt.logging.server.jakarta.RemoteLoggingServiceImpl (artifact gwt-servlet-jakarta, available since GWT 2.11) for Jakarta Servlet. Both extend RemoteServiceServlet and have two setters: setLoggerNameOverride(String) and setSymbolMapsDirectory(String). The Bookshelf subclass reads the directory from a system property:

package com.example.bookshelf.server;

import com.google.gwt.logging.server.jakarta.RemoteLoggingServiceImpl;
import jakarta.servlet.ServletException;

public class BookshelfRemoteLoggingServlet extends RemoteLoggingServiceImpl {
  @Override
  public void init() throws ServletException {
    super.init();
    String dir = System.getProperty("bookshelf.symbolMaps");
    if (dir != null && !dir.isBlank()) {
      setSymbolMapsDirectory(dir);
    }
  }
}
<servlet>
  <servlet-name>remoteLogging</servlet-name>
  <servlet-class>com.example.bookshelf.server.BookshelfRemoteLoggingServlet</servlet-class>
</servlet>
<servlet-mapping>
  <servlet-name>remoteLogging</servlet-name>
  <url-pattern>/bookshelf/remote_logging</url-pattern>

The record arrives in the server’s own logger tree, under the name of the client logger (or the override), through RemoteLoggingServiceUtil.logOnServer. The stack trace is in Java names because the servlet was told where the symbol maps are, which is the subject of the next section.

Some behaviour that the sources and the runs establish:

  • No batching, no back-off. The Developer Guide calls it "the simplest possible way": one RPC call per record, with no retry. Every record that a handler accepts is a request, so do not enable it at ALL.

  • The handler has its own level, ALL by default. Restrict what is sent with setLevel on the handler instance of the root logger. In a TRUE build with this code in the entry point, the browser console showed INFO records and the server received only the SEVERE ones:

    for (Handler handler : Logger.getLogger("").getHandlers()) {
  if (handler instanceof SimpleRemoteLogHandler) {
    handler.setLevel(Level.WARNING);   // WARNING and SEVERE are sent
  }
}

    Source: GWT — Logging: Remote Logging

  • Failures stay out of the loop. The handler’s callback logs failures to the logger WireActivityLogger, which RemoteLogHandlerBase excludes. On failure the client logged SEVERE: Remote logging failed: followed by the exception (against a server that did not know the URL, the exception was com.google.gwt.user.client.rpc.StatusCodeException: 501 Unsupported method ('POST')). When the servlet cannot process a record it answers with the string Remote logging failed, check stack trace for details., logs Remote logging failed with the cause at SEVERE, and the client then logs Remote logging failed: with that text.

  • No Java 17 flag is needed for this direction. The record is deserialised on the server; the run needed no --add-opens (the pitfall about serialising exceptions on the server side belongs to GWT-RPC).

  • The RPC proxy is part of the output only when the handler is. With gwt.logging.simpleRemoteHandler disabled (or logging FALSE) the remote_logging string and the service proxy are absent from the JavaScript (see the size table).

A JSON endpoint instead of GWT-RPC

GWT-RPC needs the serialisation policy files and a servlet that extends RemoteServiceServlet. A project that already talks JSON, or that wants the log endpoint on another service, can use the helper classes that the logging module provides: JsonLogRecordClientUtil (client) turns a LogRecord into JSON, and the JSON overload of RemoteLoggingServiceUtil.logOnServer (server) reads it back and logs it; its parameters are the JSON text, the strong name, a StackTraceDeobfuscator and a logger name override. The handler below sends only SEVERE records with RequestBuilder (see RequestBuilder, JSON & XML). It sends the permutation strong name in the same header that GWT-RPC uses, and it stays silent on failure.

public class JsonLogHandler extends Handler {
  private final String url;

  public JsonLogHandler(String url) {
    this.url = url;
    setLevel(Level.SEVERE);
  }

  @Override
  public void publish(LogRecord record) {
    if (!isLoggable(record)) {
      return;
    }
    RequestBuilder request = new RequestBuilder(RequestBuilder.POST, url);
    request.setHeader("Content-Type", "application/json; charset=utf-8");
    request.setHeader(RpcRequestBuilder.STRONG_NAME_HEADER, GWT.getPermutationStrongName());
    try {
      request.sendRequest(JsonLogRecordClientUtil.logRecordAsJson(record), new RequestCallback() {
        @Override public void onResponseReceived(Request request, Response response) { }
        @Override public void onError(Request request, Throwable exception) { }
      });
    } catch (RequestException e) {
      // a broken log channel must not break the application
    }
  }

  @Override public void flush() { }
  @Override public void close() { }
}

Source: GWT Javadoc — JsonLogRecordClientUtil

The matching servlet checks the size before it parses anything, takes the strong name from the header and delegates to the GWT utility, with the deobfuscator built from the same directory as before:

public class JsonLogServlet extends HttpServlet {
  private static final int MAX_BODY = 16 * 1024;
  private StackTraceDeobfuscator deobfuscator;   // com.google.gwt.core.server

  @Override
  public void init() {
    String dir = System.getProperty("bookshelf.symbolMaps");
    if (dir != null && !dir.isBlank()) {
      deobfuscator = StackTraceDeobfuscator.fromFileSystem(dir);
    }
  }

  @Override
  protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws IOException {
    byte[] body = req.getInputStream().readNBytes(MAX_BODY + 1);
    if (body.length > MAX_BODY) {
      resp.sendError(HttpServletResponse.SC_REQUEST_ENTITY_TOO_LARGE);
      return;
    }
    String strongName = req.getHeader("X-GWT-Permutation");
    try {
      RemoteLoggingServiceUtil.logOnServer(
          new String(body, StandardCharsets.UTF_8), strongName, deobfuscator, "client");
      resp.setStatus(HttpServletResponse.SC_NO_CONTENT);
    } catch (RemoteLoggingException e) {
      resp.sendError(HttpServletResponse.SC_BAD_REQUEST);
    }
  }
}

Source: GWT Javadoc — RemoteLoggingServiceUtil

Stack-trace deobfuscation

A production build renames methods and classes, so the stack trace of an exception in the browser names functions such as cf and qf (GWT prints a frame as at Unknown.cf(bookshelf-0.js)); a trace that a user sends you is not readable as it is. The compiler therefore writes a symbol map for each permutation, and the server uses it to translate the frames back.

How traces are produced: compiler.stackMode

The compiler flags and properties in general are covered on Compiler & Compilation, and the symbol map files on Linkers & Bootstrap.

The property compiler.stackMode (StackTrace.gwt.xml) decides what a Throwable carries. It defaults to native: the stack comes from the browser’s own error object. The legacy property compiler.emulatedStack set to true selects emulated, and strip removes the information. Measured on the same TRUE build:

The server side

com.google.gwt.core.server.StackTraceDeobfuscator (moved there from the logging package in 2.6.0; the old com.google.gwt.logging.server.StackTraceDeobfuscator is a deprecated subclass) reads the symbol maps. Its factories open them from a directory (fromFileSystem(String)), the classpath (fromResource(String)) or a URL (fromUrl(URL)), and setLazyLoad(true) caches only the symbols that were asked for and discards the rest of the map, which its Javadoc describes as a large memory saving at the price of occasional extra disk reads. The method deobfuscateStackTrace takes a Throwable and the strong name and rewrites the stack trace of the exception and of its causes.

The strong name travels with the request. GWT-RPC clients send it in the header X-GWT-Permutation (RpcRequestBuilder.STRONG_NAME_HEADER), and the server reads it with getPermutationStrongName() in RemoteServiceServlet. In your own code the client side is GWT.getPermutationStrongName(). The servlet shown above passes the header value to the deobfuscator; RemoteLoggingServiceImpl does it for you once setSymbolMapsDirectory has been called.

Three details of the output are worth knowing. The line numbers are those of the method declarations (checkLimit was declared on line 23 of the file at that time, tryRenew on line 12, onModuleLoad on line 26): without source-map information the symbol map only knows where a method starts. The first frames are the constructors of the exception classes (Throwable, Exception, RuntimeException, IllegalStateException) because the stack is captured where the exception is created. A server given a directory that does not contain the strong name of the running build did not complain: the trace simply stayed obfuscated. The source explains it: when the symbol map is missing or unreadable, the deobfuscator swallows the IOException and returns empty data for the symbols.

That last point is the operational rule. The symbol maps must match the deployed .cache.js names exactly, so archive the deploy directory of every release together with it (clients still run old permutations from caches for a long time), and rebuild nothing between the build that is deployed and the build whose maps you keep.

What the numbers say:

  • FALSE is the build that carries no logging machinery. The handlers, the LogConfiguration implementations other than the null one, the popup and the RPC proxy of the remote handler are replaced by deferred binding and disappear (compare 245,633 bytes with 272,691). It is even a little smaller than not inheriting the module.

  • SEVERE, WARNING and TRUE cost the same. The level only changes constants; the code of the handlers is the part that weighs. The remote handler alone adds about 15 KB (272,691 against 257,207), the popup about 11 KB.

  • The message of a disabled call is not removed. In every build above, including FALSE, the compiled file still contained the strings UNGUARDED-AUDIT, INFO-METHOD, FINE-METHOD and SEVERE-METHOD. The calls became if(!flag){return} checks against fields that the Logger class sets in its static initialiser (the compiled initialiser of the FALSE build sets one flag to true and four to false), and the compiler does not fold them. The comment in Core.gwt.xml (a call such as logger.log(Level.INFO, "foo") will not compile out) and the Developer Guide, which says that other logging-related code you write is not guaranteed to compile out, agree.

  • LogConfiguration.loggingIsEnabled() is a runtime check too. The guarded literal GUARDED-AUDIT was also present in the FALSE output, behind a call of the form SJ()&&... where the function returned false. The guard does what it promises at runtime: the expression inside the block, here Window.getClientWidth() plus a string concatenation, is not evaluated, while the argument of an unguarded LOG.log(Level.INFO, "..." + Window.getClientWidth()) is built before the call and then discarded. The Developer Guide example uses the same pattern for a message that is expensive to compute.

if (LogConfiguration.loggingIsEnabled(Level.FINE)) {
  LOG.fine(describe(book));       // describe(...) runs only when FINE records are possible
}

Source: GWT — Logging: Making All Logging Code Compile Out

The Developer Guide adds that code which compiles out in production is still present in Development Mode, and that the same condition hides it there too. For loggingIsEnabled(Level) the answer in a SEVERE build is true only for SEVERE, in a WARNING build for levels from WARNING up, in a TRUE build for every level and in a FALSE build always false.

Worked example: the Bookshelf renewal path

The following pieces make the whole flow of this page run in the Bookshelf, in this order:

  1. bookshelf-client inherits com.google.gwt.logging.Logging and enables gwt.logging.simpleRemoteHandler; the default gwt.logging.enabled is SEVERE, so a production page creates only SEVERE records and sends them to the server.

  2. LoanDesk (the class that renews a loan) logs a SEVERE record with the exception when a renewal is refused. Its FINE calls produce no output in production and appear in Super Dev Mode.

  3. LateFee in bookshelf-shared logs on both sides with the same code.

  4. bookshelf-server maps BookshelfRemoteLoggingServlet at /bookshelf/remote_logging and starts with -Dbookshelf.symbolMaps=... pointing at the deploy directory of the deployed build.

  5. The profile quiet-logs produces the build without any of it, for a deployment that must not log.

public final class LoanDesk {
  private static final Logger LOG = Logger.getLogger(LoanDesk.class.getName());

  public static boolean tryRenew(long bookId) {
    LOG.fine("Renewing book " + bookId);
    try {
      checkLimit(bookId);
      return true;
    } catch (IllegalStateException e) {
      LOG.log(Level.SEVERE, "Cannot renew book " + bookId, e);
      return false;
    }
  }

  private static void checkLimit(long bookId) {
    if (bookId > 0) {
      throw new IllegalStateException("Loan limit reached for book " + bookId);
    }
  }
}

Security notes

  • Client log input is attacker input. Anyone can post to the remote logging endpoint, with any text in the record and any logger name. A record posted to the JSON servlet with the message hello followed by a line break and INFO: forged line appeared in the Jetty console as two lines, the second looking like a record of its own. Treat the messages as untrusted: escape or neutralise line breaks before they reach a text log (log forging, CWE-117), cap the body size as the JSON servlet above does, rate-limit by session or address, authenticate the endpoint when the application has users, and use setLoggerNameOverride so that browser records go to one named logger (and to an appender with its own retention) instead of choosing their own.

  • Do not log secrets. The browser console is readable by the user and by extensions, GWT.log and logger output end up in server logs through the remote handler, and a record can carry an exception message or a whole request. Never log tokens, passwords, session ids or personal data; log identifiers.

  • RemoteLoggingServiceImpl extends RemoteServiceServlet, not the XSRF-protected servlet. A record has no side effect beyond a log line, so rate limiting is the usual defence, but protect the endpoint properly if records raise alerts.

  • Symbol maps are internal. They reveal class names, method names and source paths. Keep them in the deploy directory and out of the public folder (see the pitfall table).

  • The logLevel parameter is user input. In any build that keeps logging, a visitor can change the level of the page they are looking at, and a value that Level.parse rejects stops the application at startup (see the pitfalls). It cannot affect other users. A FALSE build ignores the parameter.

  • HTML sinks. HasWidgetsLogHandler renders formatter output in an HTML widget; it escapes < and > in the message but is a display aid, not a sanitiser. Custom log views should use setText.

Where older material is outdated

  • Client logging in the book. GWT in Action (chapter 3, "Implementing application logging") tells the reader that the only built-in client-side logging in web mode is Window.alert, with GWT.log for hosted mode, and recommends Log4J for the server. Both statements describe GWT 1.x. Since 2.1.0 the client has the java.util.logging emulation, and since 2.5 the output can be compiled out by level. GWT.log is removed from production output (no occurrence of a GWT.log string was left in the compiled Bookshelf) and prints to the browser console in Super Dev Mode, where the old hosted-mode window no longer exists.

  • Wrapping a JavaScript logger. The book suggests wrapping a library such as Log4JavaScript with JSNI. That is now unnecessary; if you want a custom sink, write a Handler.

  • Default handlers in the Developer Guide. The guide says that the popup and system handlers are attached by default. Since 2.7.0 the default is SEVERE and above on the browser console, and the popup and system handlers are off. Its names HTMLFormatter and TextFormatter are HtmlLogFormatter and TextLogFormatter, and it says that DevelopmentModeLogHandler output is seen in the "DevMode window", which no longer exists in Super Dev Mode.

  • The sample. The guide links the LogExample sources at a fixed commit of the repository. The samples folder of the 2.13.1 tag has no logexample, so use the pages and sources cited here.

  • Guaranteed compile-out. The guide says code behind LogConfiguration.loggingIsEnabled() is guaranteed to be removed. In 2.13.1 the check stays in the output and returns false; the saving is the work that the check prevents at runtime.

What changed recently

The cross-section view of releases is on What’s Changed & Migration.

  • 2.1.0 (milestone 1). The java.util.logging emulation was added to GWT.

  • 2.5.0. "Added option to compile out logging calls below SEVERE and WARN"; the gwt.logging.enabled values SEVERE and WARNING come from this release.

  • 2.5.1 and 2.6.0. The deobfuscator got a constructor option to conserve server memory (later setLazyLoad) and moved to com.google.gwt.core.server.

  • 2.7.0. New defaults: records at SEVERE and above go to the browser console; PopupLogHandler and SystemLogHandler are no longer enabled by default; FirebugLogHandler and NullLoggingPopup were removed.

  • 2.8.0. "Improved logging and stack traces for superdev mode", in the release notes' words.

  • 2.11.0. Jakarta artifacts for GWT-RPC: com.google.gwt.logging.server.jakarta.RemoteLoggingServiceImpl in gwt-servlet-jakarta.

The properties and defaults described here are those of the 2.13.1 sources. The Developer Guide page does not reflect the defaults that 2.7.0 introduced, which is why the page and the behaviour disagree in the places listed above.
