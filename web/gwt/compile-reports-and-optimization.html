Compile Reports & Optimization

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against GWT 2.13.1 (2026-06-19), gwt-maven-plugin 1.3.0, JDK 21 with -sourceLevel 17 and the Jakarta Servlet 6 stack of the modular-webapp archetype, checked on 2026-10-09. It is build and tooling knowledge with one client part: the compile report and the JFR events are produced by the compiler on the developer or CI machine, while the lightweight metrics are JavaScript events emitted by the compiled client code in the visitor’s browser. Every number and output block below was produced on the Bookshelf scenario of this section (three locales, two user agents, one DataGrid and one GWT.runAsync split point) with a private copy of the scratch application. The application grew a little during the section, so the absolute sizes differ from those on the compiler page; compare figures only inside one table.

Measure first

Optimising without numbers usually shrinks the wrong thing. GWT gives three different instruments, and each answers a different question:

About 2 to 3 seconds more and several MB of files per permutation

The compile report

Producing it

-compileReport ("Compile a report that tells the Story of Your Compile", default off) collects, for every permutation, the size contributed by each package and class and how the code is distributed over fragments, and writes a set of static HTML pages. The gwt-maven-plugin compile goal has no compileReport parameter, so pass the flag through compilerArgs. With the plugin the extras directory is target/extras, and the report ends up in target/extras/<module>/soycReport/compile-report/.

<plugin>
  <groupId>net.ltgt.gwt.maven</groupId>
  <artifactId>gwt-maven-plugin</artifactId>
  <configuration>
    <moduleName>com.example.bookshelf.App</moduleName>
    <moduleShortName>bookshelf</moduleShortName>
    <compilerArgs>
      <arg>-generateJsInteropExports</arg>
      <arg>-compileReport</arg>
    </compilerArgs>
  </configuration>
</plugin>

Source: GWT — Compile Report: Usage, gwt-maven-plugin — gwt:compile

The run printed the location of the extras, and the report is not part of the war:

[INFO]    Compilation succeeded -- 12,164s
[INFO] Linking into .../bookshelf-client/target/bookshelf-client-1.0-SNAPSHOT/bookshelf; Writing extras to .../bookshelf-client/target/extras/bookshelf

With the command-line compiler the same flag works with -extra dir. The flags related to the report are:

Flag Effect Status

-compileReport

Standard report. -nocompileReport is the negative form.

Documented; -soyc is an older alias found in the source

-XsoycDetailed

Adds detailedStories<n>.xml.gz, which link Java snippets to JavaScript snippets (257,758 bytes for one permutation here). The Developer Guide says it is most useful when investigating specific snippets.

Experimental, not listed by the -help output

-XcompilerMetrics

Adds compilerMetrics.xml (669,650 bytes here) and the "Compiler Metrics" pages: build times of the module analysis, precompile and compile phases and the lists of source files, types and unreferenced types.

Experimental, not listed by the -help output

The -XsoycDetailed flag is a size-for-time trade: the documentation says it is "at the expense of compile time". In this application the difference was within the noise of the machine. Two more switches (-XenableJsonSoyc and -XdisableSoycHtml) exist in the 2.13.1 source as undocumented experimental flags and were not run here.

Why is this class in the initial download?

The dependency pages answer "I expected this to be left out". The Developer Guide describes the procedure: from the overview open the permutation, follow the "Report" link under "Initial download size", open the package and then the class; the page shows a chain of calls back to the entry point. The same information is in dependencies<n>.xml.gz, where every method lists its called by entries. Following the first caller at every step for the sort-icon initializer of the grid gave:

DataGrid_Resources_en_InlineClientBundleGenerator$dataGridSortAscendingInitializer::$clinit
  <- AbstractHeaderOrFooterBuilder::AbstractHeaderOrFooterBuilder
  <- DefaultHeaderOrFooterBuilder::DefaultHeaderOrFooterBuilder
  <- AbstractCellTable::$init
  <- AbstractCellTable::AbstractCellTable
  <- DataGrid::DataGrid

The DataGrid constructor is the link to break: create the grid inside a split point and the whole chain, including the generated client bundle, leaves the initial download. The "Split point status" and "Leftover status" pages explain the opposite case, an item that is only in the leftover fragment because two split points need it (each page offers a "See why it’s not exclusive to s.p. #n" link). The mechanics of exclusive and leftover fragments belong to Code Splitting.

Source: GWT — Compile Report: Features, GWT — Compile Report: Use cases

Comparing permutations and keeping the report private

The overview lists every permutation, so differences between user agents or locales can be compared one by one. The four use cases named by the Developer Guide are reducing the whole download, the initial fragment, specific fragments and comparing permutations.

The report contains class names, method names and, with -XsoycDetailed, JavaScript snippets mapped to Java. Keep it out of the public site. With the Maven plugin the extras folder is outside the war (a search of the war found no soyc or symbol-map file), and the same holds for -extra of the command-line compiler as long as that directory is not inside -war. Never point -extra at the web root.

Class metadata: -XnoclassMetadata

By default GWT keeps metadata so that Class.getName() and getSimpleName() work (-X[no]classMetadata, default on). Turning it off saved 119,370 bytes over the six files. The price is visible at run time. A line that logs App.class.getName() + " / " + App.class.getSimpleName() printed, in a headless Chrome:

com.example.bookshelf.client.App / App         (default)
Class$17 / Class$17                            (with -XnoclassMetadata)

So do not use the flag in an application that logs, serializes or switches on class names. In the source the disabled mode names a class "Class$" plus an id.

Source: GWT — Command Line Tools, GWT source — Class.java

Runtime checks: jre.checks.*

The JRE emulation contains checks that Java programs get from the JVM. They are controlled by properties defined in Preconditions.gwt.xml: jre.checks.checkLevel (NORMAL, the default, OPTIMIZED or MINIMAL) and the four finer switches jre.checks.bounds, jre.checks.api, jre.checks.numeric and jre.checks.type, each AUTO (follow the level), ENABLED or DISABLED. In InternalPreconditions the bounds, API and numeric checks are on only at NORMAL, and the type check at OPTIMIZED or higher. Set the level in the module or on the command line:

<!-- bookshelf-client/src/main/module.gwt.xml, release build only -->
<set-property name="jre.checks.checkLevel" value="MINIMAL" />
# same effect from the compiler arguments of a profile
-setProperty jre.checks.checkLevel=MINIMAL

Source: GWT source — Preconditions.gwt.xml

The property is a deferred-binding property, so it does not add permutations when it has one value. The trade-off is correctness: with the checks gone an out-of-range list.get(10) or a failed cast is no longer reported the way Java reports it. Measure the gain first (2.3 % here) and try OPTIMIZED before MINIMAL. The old -XcheckCasts flag is deprecated in favour of jre.checks.checkLevel, as the -help text says.

Avoiding heavy JRE classes

The report’s jre group is the cost of Java library classes that you pull in. A single call chain using BigDecimal to compute a late fee, new BigDecimal("0.25").multiply(BigDecimal.valueOf(days)).setScale(2, RoundingMode.HALF_UP), made one permutation grow from 265,852 to 290,470 bytes (+24,618, +9.3 %); the report named java.math as 21,220 bytes (8.1 %). Computing the fee in whole cents with int removes all of it:

// shared: Bookshelf late fee in cents, no java.math needed
public static int lateFeeCents(int daysLate) {
  return 25 * Math.max(0, daysLate);
}

Other classes with the same effect are listed on the JRE emulation page; see JRE Emulation & Shared Code. Prefer plain int, double and String in shared code, and check the report’s jre list after adding a library.

Source: GWT — Compile Report: Package and code type breakdown

Other levers

  • Optimisation level. Keep the default -optimize 9. Level 5 was already as large as 9 here (+0.2 %) and level 0 more than doubled the output.

  • Widgets. com.google.gwt.user.cellview.client was 15.6 % of the Bookshelf. A plain table in the first screen and the DataGrid in a lazily loaded area is a real saving.

  • Locales. Every locale adds a permutation (more build output, not more bytes per visitor); see Internationalization.

  • Split points. Code that the first screen does not need belongs behind GWT.runAsync; the compile report is the tool that proves it left the initial fragment.

  • Compression. The .cache.js of 265,852 bytes compressed to about 89,500 bytes with gzip -9, a 66 % reduction without touching code. See Server Integration & Deployment.

  • Output style. OBFUSCATED is the default; PRETTY was 2.75 times larger.

Fewer permutations

The cheapest saving is to compile fewer permutations while developing. Fixing the properties reduced six permutations to one:

mvn -B package -pl bookshelf-client -am -DskipTests -Dgwt.draftCompile=true
# or, with compilerArgs in a dev profile:
#   -setProperty locale=en  -setProperty user.agent=safari

Source: GWT — Compiling and Debugging, gwt-maven-plugin — gwt:compile

The Maven user properties gwt.draftCompile, gwt.optimize and gwt.localWorkers exist on the compile goal.

-localWorkers is not just threads

-localWorkers count is the number of workers that compile permutations. The 2.13.1 source shows what a worker is: ThreadedPermutationWorkerFactory creates in-process threads, but caps them at the system property gwt.jjs.maxThreads, whose default is 1. Every further worker is launched by ExternalPermutationWorkerFactory as a separate JVM that inherits the JVM arguments of the compiler (-Xmx and -D options) unless gwt.jjs.javaArgs overrides them. Consequences:

  • with no -localWorkers the six permutations were compiled one after the other by "In-process PermutationWorker 0", as the JFR events show;

  • -localWorkers N needs memory for N compiler JVMs, not for one;

  • timing gains depend on the free cores, and on the loaded machine used here the runs with 1, 3 and 6 workers (9.8 to 13.5 seconds) were not distinguishable from the default.

-incremental and -validateOnly

-incremental compiles faster by reusing data from the previous compile, but it works on one permutation only:

[ERROR] Current binding properties are expanding to more than one permutation but per-file compilation requires that each compile operate on only one permutation.

Combine it with -setProperty values that fix every property, as the code server does. The flag is meant for development; the compiler page lists its other restrictions. -validateOnly -failOnError checks the sources without producing output and is the cheapest first step of a pull-request build.

Runtime performance: lightweight metrics

The collector and its events

The lightweight metrics system is a global JavaScript function, __gwtStatsEvent, that the compiled code and the bootstrap call with an event object. If the host page does not define it, nothing is reported (the compiled code checks for it before building an event). The event is a plain object with these fields:

Field Meaning

moduleName

The GWT module that emitted the event, so several modules on one page can be told apart

subSystem

The component: startup, rpc, runAsync, or your own name

evtGroup

A group of related events that follow a serial order; for RPC it is the request number

millis

Timestamp in milliseconds

type

The step, for example selectingPermutation

Some events carry more: sessionId, method (the RPC proxy and method), fragment and size (fragment downloads) and bytes (RPC payloads). The collector must return true or false to say whether it recorded the event, and it has to be defined before the bootstrap script runs.

Source: GWT — Lightweight Metrics: How it works

A collector for the Bookshelf host page

The Developer Guide’s example writes each event into the page with innerHTML. A collector should never render event fields as HTML (custom events can carry any string), so this one stores text only and prints it with textContent:

<!doctype html>
<html>
  <head>
    <meta charset="UTF-8">
    <title>Bookshelf (metrics)</title>
    <meta name="gwt:property" content="locale=en">
    <script>
      // Must run before bookshelf.nocache.js
      window.__gwtStatsEvent = function (e) {
        window.__t0 = window.__t0 || e.millis;
        var line = (e.millis - window.__t0) + ' ms | ' + e.moduleName + ' | ' + e.subSystem
            + ' | ' + e.evtGroup + ' | ' + e.type
            + (e.method ? ' | ' + e.method : '')
            + (e.fragment !== undefined ? ' | fragment=' + e.fragment : '');
        (window.__lines = window.__lines || []).push(line);
        return true;
      };
      window.addEventListener('load', function () {
        setTimeout(function () {
          var pre = document.createElement('pre');
          pre.textContent = window.__lines.join('\n');
          document.body.appendChild(pre);
        }, 3000);
      });
    </script>
    <script src="bookshelf/bookshelf.nocache.js"></script>
  </head>
  <body></body>
</html>

Source: GWT — Lightweight Metrics: Global collector function

Your own events with JsInterop

The Developer Guide extends the system with a JSNI method. In 2.13 a native JsInterop binding does the same without JSNI, and JsPackage.GLOBAL reached the host page’s __gwtStatsEvent (the compiled code runs inside the xsiframe iframe, and the call still arrived):

@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "Object")
public class StatsEvent {
  public String moduleName;
  public String subSystem;
  public String evtGroup;
  public double millis;
  public String type;
}

public final class Stats {
  private Stats() {
  }

  @JsProperty(namespace = JsPackage.GLOBAL, name = "__gwtStatsEvent")
  private static native Object collector();

  @JsMethod(namespace = JsPackage.GLOBAL, name = "__gwtStatsEvent")
  private static native boolean send(StatsEvent event);

  public static void log(String subSystem, String evtGroup, String type) {
    if (collector() == null) {
      return; // no collector on the host page: cost is one check
    }
    StatsEvent e = new StatsEvent();
    e.moduleName = GWT.getModuleName();
    e.subSystem = subSystem;
    e.evtGroup = evtGroup;
    e.millis = Duration.currentTimeMillis();
    e.type = type;
    send(e);
  }
}

// App.onModuleLoad
Stats.log("bookshelf", "shell", "begin");
ClientFactory factory = new ClientFactory();
// ... build the shell ...
Stats.log("bookshelf", "shell", "end");

Source: GWT — Lightweight Metrics: Extending the system

The shell begin and shell end lines in the output above come from this code. Several modules on one page report to the same collector with their own moduleName, which allows comparing them (the "multiple modules" section of the guide).

Using the data in production

  • Events contain module names, RPC method names, timings and fragment numbers, not RPC payloads. Do not add user data to custom events.

  • The collector is an inline <script>; with a strict Content-Security-Policy put it in a file or give it a nonce.

  • To send field data to a server, batch the lines and use navigator.sendBeacon from the collector; do not issue a request per event.

  • The Developer Guide mentions a Debug Panel for GWT built on this system; it was not tried here.

JFR events of the compiler (2.13)

The 2.13.0 release notes say: "JFR events added to replace SpeedTracer, support observability into compiler steps, permutation and fragment counts, and output size". The Optimizing page of the Developer Guide still recommends Speed Tracer, which is outdated. These are Java Flight Recorder events in the compiler JVM, not browser data; use the browser’s own developer tools for run-time profiling, with source maps from Super Dev Mode & Debugging. The 2.13.1 release added the GWT version and commit to the output, so recordings can be compared across releases.

Recording

The events are ordinary jdk.jfr.Event subclasses in the GWT category with @StackTrace(false). They are written when a recording is running in the compiler JVM. With Maven the compiler is a forked JVM, so pass the option in jvmArgs:

<configuration>
  <jvmArgs>
    <arg>-XX:StartFlightRecording:filename=${project.build.directory}/gwt-compile.jfr,settings=default</arg>
  </jvmArgs>
</configuration>
mvn -B package -pl bookshelf-client -am -DskipTests
$JAVA_HOME/bin/jfr summary bookshelf-client/target/gwt-compile.jfr
$JAVA_HOME/bin/jfr print --events gwt.compiler.js.Fragment bookshelf-client/target/gwt-compile.jfr

Source: GWT — Release Notes 2.13.0, GWT source — util/log/perf

The fragment events tie the two tools together. For permutation 0 the recording has fragment 0 with jsBytes = 259606 and fragment 1 with jsBytes = 658; the compile report of the same permutation reported an initial download of 259,606 bytes and a split point of 658.

Nested tasks overlap, so the figures do not add up. Two conclusions followed: the time before the permutations (parsing and type resolution) is as large as the optimisation, and generators are almost free here, so trimming UiBinder templates would not shorten this build while fewer permutations would.

The gwt.jjs.dumpAst system property, which the release notes say was tweaked in 2.13.0, dumps the Java and JavaScript AST between passes to a file; gwt.jjs.dumpAst.filter restricts the output to source files and line ranges. It is a compiler-developer tool and is only mentioned for completeness.

Recent changes and outdated material

  • 2.13.0. JFR events replace Speed Tracer for compiler observability; 2.13.1 adds the GWT version and commit to them.

  • Optimizing page. The Developer Guide page still points to Speed Tracer and uses innerHTML in its metrics sample; both are outdated.

  • JSNI. The extension example of the lightweight metrics page uses JSNI; JsInterop does it without JSNI.

  • The book. The first edition of GWT in Action predates GWT 2 and does not cover compile reports, lightweight metrics or JFR.
