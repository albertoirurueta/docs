JsInterop

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against GWT 2.13.1 (2026-06-19), gwt-maven-plugin 1.3.0 (net.ltgt.gwt.maven), JDK 21 running the compiler with -sourceLevel 17, jsinterop-annotations 2.0.0 (the version the GWT BOM pins), jsinterop-base 1.2.0 and Elemental2 1.3.2, and the Jakarta Servlet 6 server of the Bookshelf scenario, checked on 2026-10-08. JsInterop is client knowledge: the annotations are read by the GWT compiler while it translates client and shared Java to JavaScript, and they decide what the generated JavaScript looks like at the boundary with the browser, with third-party scripts and with the host page. The build side is one compiler flag and one module inheritance, both covered below; there is nothing to do on the server. Every example on this page was compiled with the 2.13.1 compiler (from the command line and through mvn package with the gwt-app packaging), loaded in headless Chrome and exercised from JavaScript; the outputs and compiler messages are quoted as they were printed.

JsInterop is the modern way for Java and JavaScript to talk to each other in GWT. It replaced hand-written JavaScript inside Java comments (JSNI, covered in JSNI & Overlay Types) with annotations on ordinary Java declarations: a Java type that stands for something JavaScript already provides is a native type, and a Java type that JavaScript is meant to call is an exported type. The Elemental2 browser bindings (see DOM & Elemental2), jsinterop-base and parts of GWT’s emulated java.util classes are written with these annotations, so the rules on this page are the rules of the whole ecosystem.

  • Java calls JavaScript. You write a Java declaration with the shape of the JavaScript API, mark it @JsType(isNative = true), and the compiler emits a direct access to the JavaScript name. There is no wrapper object and no glue code: new NumberFormatJs("de-DE") compiles to new $wnd.Intl.NumberFormat("de-DE").

  • JavaScript calls Java. You mark a Java type or member as exported and (in GWT) compile with -generateJsInteropExports; the compiler then makes the member reachable under a stable, non-obfuscated JavaScript name such as bookshelf.Api.formatCopies.

  • Callbacks cross both ways through @JsFunction interfaces: a Java lambda becomes a real JavaScript function, and a JavaScript function becomes a Java interface instance.

Setting up

JsInterop needs three things in a Maven build: the annotations jar (already on the classpath), the compiler flag for exports (only if JavaScript calls Java), and optionally the helper libraries.

The org.gwtproject:gwt BOM manages jsinterop-annotations (2.0.0 in the 2.13.1 BOM), and gwt-user brings it in transitively, so the annotations need no dependency of their own. mvn dependency:tree on the module above printed com.google.jsinterop:jsinterop-annotations:jar:2.0.0:compile under gwt-user, com.google.jsinterop:base:jar:1.2.0:compile with org.jspecify:jspecify:jar:0.3.0:compile, and the three Elemental2 jars (elemental2-dom, elemental2-core and elemental2-promise, all 1.3.2). Maven Central also lists jsinterop-annotations 2.1.0 (2023-07-18); jsinterop-base 1.2.0 itself declares 2.0.2, and the BOM-managed 2.0.0 won the resolution without any problem.

Each library that has GWT-specific source needs a <inherits> line in the module XML, because GWT compiles from source, not from bytecode.

Module XML of the lab (src/main/module.gwt.xml)
<?xml version="1.0" encoding="UTF-8"?>
<module>
  <inherits name="com.google.gwt.user.User"/>
  <inherits name="elemental2.dom.Dom"/>
  <inherits name="elemental2.promise.Promise"/>
  <inherits name="jsinterop.base.Base"/>
  <source path="client"/>
  <entry-point class="com.example.lab.client.Lab"/>
</module>

Source: jsinterop-base — README

The annotations themselves need no <inherits>; jsinterop.base.Base is the module named in the jsinterop-base README, and the two Elemental2 modules above come from the .gwt.xml files in the 1.3.2 jars (elemental2/dom/Dom.gwt.xml, elemental2/promise/Promise.gwt.xml, which itself inherits jsinterop.base.Base).

The exports flag goes to the production compiler and to Super Dev Mode, and the Maven plugin has a separate argument list for each of them (see Build Tools: Maven & Gradle for the plugin). The flag is described among the compiler flags in Compiler & Compilation, and Super Dev Mode in Development Mode & Debugging.

The three "no effect" rows deserve a concrete picture. A probe module compiled @JsNullable, @JsNonNull, @JsAsync and an @JsEnum enum without any error. The only output was two warnings about the enum, [unusable-by-js] Type of parameter 'c' in 'String Probe.color(Probe.Color)' is not usable by but exposed to JavaScript. and the matching return-type warning, and in the browser the value returned by probe.Probe.green() was a plain Java enum object whose own keys were ["name_0","ordinal_0"]. Write these annotations only for code that must also compile with J2CL, and do not expect them to change what GWT generates.

The attribute defaults and the rules that the compiler checks are summarised here; each rule is quoted in the pitfalls table with the exact message.

  • Namespace and name of an exported type. The default namespace is the Java package (the compiler’s own message about two exports clashing names 'com.example.bad2.client.TwoCtors'), and the default name is the simple class name. JsPackage.GLOBAL as the namespace of a native type means "a global".

  • Members. A public member of a @JsType is exported with its Java name unless @JsMethod, @JsProperty or @JsIgnore says otherwise. The Developer Guide says the annotation exposes the public non-static members; on 2.13.1 the public static members of bookshelf.Api (VERSION, formatCopies, sum) were exported too.

  • Not transitive. @JsType on a class does not make the types in its signatures exportable; each needs its own annotation, or JavaScript receives opaque objects (the [unusable-by-js] warning below).

  • Unknown shapes. A native type may use the name "?" (unknown) or "*" (any): jsinterop-base names its Any type "*" and Elemental2’s union helper types use "?". The Developer Guide describes "?" for a JavaScript API that has no well-defined type, and the 2.8.1 release notes added both names.

Calling JavaScript from Java: native types

A native type is a Java class or interface with the shape of a JavaScript API. The compiler never generates its implementation; it generates calls to the JavaScript name. The rules are those of the Developer Guide and the checker in the compiler: constructors are empty, methods are native (or @JsOverlay), fields have no initializer and are not final, and a native class extends only native classes.

A first binding: Intl.NumberFormat

The Bookshelf shows the number of copies per book and the price in the reader’s locale. The browser already has a locale-aware formatter, Intl.NumberFormat, so there is nothing to ship: the binding is a facade. This is the class that the Bookshelf scratch application contains.

The Bookshelf’s binding for Intl.NumberFormat (bookshelf-client)
package com.example.bookshelf.client.interop;

import jsinterop.annotations.JsType;

/** Binding for the browser's {@code Intl.NumberFormat}; native types need no JavaScript glue. */
@JsType(isNative = true, namespace = "Intl", name = "NumberFormat")
public class NumberFormatJs {
  public NumberFormatJs(String locale) {}

  public native String format(double value);
}

Source: MDN — Intl.NumberFormat

  • namespace = "Intl" and name = "NumberFormat" are the JavaScript name; the Java class is called NumberFormatJs only to avoid a clash with GWT’s own com.google.gwt.i18n.client.NumberFormat.

  • The constructor body is empty, as the compiler requires; the arguments are passed straight through.

  • format(double) is native: there is no Java body, and the call compiles to .format(n) on the JavaScript object.

Compiled with -style PRETTY, a method that used the class produced this JavaScript (the whole facade disappears):

Generated JavaScript for new NumberFormatJs(locale).format(n)
return (new $wnd.Intl.NumberFormat(locale)).format(n);

$wnd is the window that hosts the page, not the iframe in which the compiled module runs. Native types with JsPackage.GLOBAL (or a namespace such as Intl) are resolved through $wnd, which is why a library loaded by an ordinary <script> tag of the host page is visible to them.

Options objects: a native type that is a plain object

JavaScript APIs take "options bags". A native type named Object in the global namespace is the idiom for them: it adds no behaviour, only typed property names.

A typed options bag with a @JsOverlay factory (FormatOptions.java)
package com.example.lab.client.intl;

import jsinterop.annotations.JsOverlay;
import jsinterop.annotations.JsPackage;
import jsinterop.annotations.JsType;

/** Options bag for {@code Intl.NumberFormat}: a plain JavaScript object, never a Java object. */
@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "Object")
public class FormatOptions {
  public String style;
  public String currency;
  public int maximumFractionDigits;

  @JsOverlay
  public static FormatOptions currency(String code) {
    FormatOptions o = new FormatOptions();
    o.style = "currency";
    o.currency = code;
    return o;
  }
}

Two details matter here. First, the fields are public and not initialised, so only the properties that Java sets exist on the JavaScript object: the compiler printed (o = new $wnd.Object , o.style = 'currency' , o.currency = 'EUR' , o), and no maximumFractionDigits property was created. Second, @JsOverlay lets the facade carry a final helper (the factory) that is plain Java and is inlined at each call site; JavaScript never sees it. A second constructor taking the options object is a second declaration of the same native constructor.

Using the facade
NumberFormatJs eur = new NumberFormatJs("es-ES", FormatOptions.currency("EUR"));
String text = eur.format(1234.5);   // "1234,50", a no-break space and the euro sign in headless Chrome

Source: MDN — Intl.NumberFormat

In headless Chrome the call printed 1234,50 € for es-ES (Spanish formatting does not group four-digit numbers) and 1.234,5 for de-DE through the exported bookshelf.Api.formatCopies. The actual strings are the browser’s: they depend on its ICU data, so tests should not hard-code them.

Properties, methods and static members

JavaScript properties are not methods. Java has no way to say "this getter reads a property", so JsInterop uses an annotation on the accessor. The lab binds a small legacy script that defines a constructor Shelf with a read-only count accessor property, a label data property, a put method and a static kind property.

The legacy script (host page)
function Shelf(name) { this.name = name; this._items = []; this.label = name; }
Shelf.kind = "legacy";
Object.defineProperty(Shelf.prototype, "count", { get: function () { return this._items.length; } });
Shelf.prototype.put = function (t) { this._items.push(t); return this; };
The binding (Shelf.java)
package com.example.lab.client.shelf;

import jsinterop.annotations.JsMethod;
import jsinterop.annotations.JsOverlay;
import jsinterop.annotations.JsPackage;
import jsinterop.annotations.JsProperty;
import jsinterop.annotations.JsType;

/** Binding for a hypothetical legacy script: function Shelf(name) { ... }. */
@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "Shelf")
public class Shelf {
  @JsProperty(name = "kind")
  public static native String getKind();

  public Shelf(String name) {}

  @JsProperty
  public native int getCount();

  @JsProperty(name = "label")
  public native String getLabel();

  @JsProperty(name = "label")
  public native void setLabel(String label);

  @JsMethod(name = "put")
  public native Shelf add(String title);

  @JsOverlay
  public final Shelf addAll(String... titles) {
    for (String t : titles) {
      add(t);
    }
    return this;
  }
}
Using it, and what the browser printed
Shelf shelf = new Shelf("Fiction");
shelf.addAll("Dune", "Emma").setLabel("Shelf A");
String summary = shelf.getLabel() + ":" + shelf.getCount() + ":" + Shelf.getKind();
// summary is "Shelf A:2:legacy"

  • @JsProperty on getCount() makes the call shelf.getCount() read shelf.count; the name is derived from the JavaBean convention (getCount is property count), and @JsProperty(name = "label") gives the getter and setter an explicit name.

  • A static property accessor is allowed only on a native type, which is why getKind() reads Shelf.kind; the compiler rejects it elsewhere (Static property accessor '%s' can only be native.).

  • @JsMethod(name = "put") binds the Java method add to the JavaScript put; without it Java add would look for shelf.add.

  • addAll(String...) is a @JsOverlay method, so it exists only in Java and expands into put calls; the generated JavaScript contained no addAll.

  • A native interface describes a structural type whose implementers are plain JavaScript objects; because there is no runtime marker to test, the compiler forbids instanceof against it.

Source: GWT — JsInterop: importing a type from an external JavaScript script

Globals, duck typing and JSON

A global function or object needs no class of its own to be wrapped. The Developer Guide’s example binds JSON, whose members are static; the same class serves the lab’s JSON examples.

A global object as a native class (JsonNative.java)
package com.example.lab.client;

import jsinterop.annotations.JsPackage;
import jsinterop.annotations.JsType;

@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "JSON")
public class JsonNative {
  public static native Object parse(String text);

  public static native String stringify(Object value);
}

Source: GWT — JsInterop: importing a type

For structures that have no constructor to name (an object returned by JSON.parse, a configuration literal), the options-bag idiom above works, and jsinterop-base (see [jsinterop-base]) offers JsPropertyMap for the dynamic case. A data transfer object that mirrors a JSON document is therefore a native type named Object:

A JSON-shaped DTO as a native type (BookDto.java)
package com.example.lab.client.exported;

import jsinterop.annotations.JsPackage;
import jsinterop.annotations.JsType;

/** A JSON-shaped DTO: native type means "a plain JavaScript object with these properties". */
@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "Object")
public class BookDto {
  public String title;
  public int copies;
}

Source: GWT — JsInterop: importing a type

JSON.stringify of such an object printed {"title":"Dune","copies":3}. JSON.stringify of an ordinary (non-@JsType) Java object holding the same values printed {}, because the fields of a GWT-compiled Java object are not JSON-visible properties; if JavaScript, or a library such as a chart or a store, must read the fields, the object must be a native DTO or an exported type.

Callbacks: @JsFunction

A JavaScript function that is passed as an argument is a Java functional interface annotated with @JsFunction. Because the annotation implies "this is a function value", GWT turns a Java lambda that implements the interface into a real JavaScript function.

A callback type (nested in ChartOptions.java)
package com.example.lab.client.chart;

import jsinterop.annotations.JsFunction;
import jsinterop.annotations.JsPackage;
import jsinterop.annotations.JsType;

@JsType(isNative = true, namespace = JsPackage.GLOBAL, name = "Object")
public class ChartOptions {
  /** A JavaScript callback: the browser calls it, Java supplies it as a lambda. */
  @JsFunction
  public interface ClickHandler {
    void onClick(Object event, ChartElement[] elements);
  }

  public ClickHandler onClick;
}

Source: GWT — JsInterop: consuming a JavaScript function with a callback argument

A @JsFunction interface cannot extend another interface, cannot declare members other than @JsOverlay ones, and cannot be implemented by a class that is also a @JsType; each rule has a compiler message in the pitfalls table. An instanceof or cast against a @JsFunction is, per its Javadoc, a JavaScript typeof test for a function. The direction of the call decides which side owns the function: a lambda passed to a native API (options.onClick = ...) is a Java-implemented function called by JavaScript, and the parameter of an exported method typed with a @JsFunction interface (Api.subscribe(Listener)) is a JavaScript function that Java calls.

Worked example: a chart library for the Bookshelf

The Bookshelf’s admin area shows how many loans were made each month. Chart.js draws a bar chart from a configuration object: new Chart(canvas, config), a data object with labels and datasets, a chart.update() after the data is changed, chart.destroy() when the canvas is thrown away, and an onClick option that is called with the event, the active elements and the chart. That is the surface the lab binds; it is documented on the Chart.js site (links below).

The lab does not download or run Chart.js. It runs a short stand-in script with the same constructor, update, destroy and onClick surface, which records its calls; what is exercised is the binding, and a real Chart.js build would be loaded by the same <script> tag. The binding is five native types and one widget.

The constructor and the lifecycle methods (ChartJs.java)
package com.example.lab.client.chart;

import com.google.gwt.dom.client.CanvasElement;
import jsinterop.annotations.JsPackage;
import jsinterop.annotations.JsType;

/** Binding for a Chart.js-style constructor: {@code new Chart(canvas, config)}. */

Exporting Java to JavaScript

Sometimes the caller is not Java: a legacy script on the Bookshelf host page, a Selenium test, a browser extension or a hand-written widget wants to open a book or format a number with the application’s own code. Details worth knowing:

  • The patterns are Java regular expressions, not the package wildcards that the 2.8.1 release notes describe. The class RegexFilter compiles each argument with java.util.regex.Pattern; the .* suffix in the examples above is a regular expression, and the dots in a package name are best escaped.   • Without a filter, everything is exported. In the PRETTY output of the lab, next to bookshelf.Api, the compiler registered java.lang.String, java.util.List and other JRE emulation types (for example _.copyOf = copyOf; under provide('java.util.List')), because GWT’s own emulated classes carry JsInterop annotations.   • Exports cost bytes and defeat pruning. The measurement in Compiler & Compilation shows a growth from 244,639 to 263,127 bytes of the main file when the flag was on in the Bookshelf.

  • Code server. In Super Dev Mode the flag must reach gwt:codeserver (codeserverArgs), as described under [setup]; the CodeServer class accepts it and its compiled output then contained the exports.

  • The flag is a build choice, not part of the code. The same annotated classes compiled without it simply have no JavaScript entry point; the Java callers are unaffected.

Promises and callbacks

GWT has two callback styles, and the browser has a third.

  • AsyncCallback<T> is the GWT-RPC interface with onFailure(Throwable) and onSuccess(T). It is a normal Java interface, not a JavaScript function.

  • @JsFunction interfaces are JavaScript functions seen from Java, as shown above.

  • Promises are the JavaScript Promise object, which the browser returns from fetch, from Response.json() and from many web APIs. Elemental2 provides elemental2.promise.Promise<T> and IThenable<T> as native types; their methods are then, catch_ (bound to JavaScript’s catch with @JsMethod(name = "catch")), finally_, and the static all, race, resolve and reject.

@JsAsync, the annotation for async functions, has no effect in GWT 2.13.1 (see the annotation table), so a GWT method returns a Promise explicitly instead of declaring async.

Consuming a Promise: fetch

fetch and the JSON it returns (Net.java)
package com.example.lab.client;

import com.google.gwt.user.client.rpc.AsyncCallback;
import elemental2.dom.DomGlobal;
import elemental2.promise.Promise;
import java.util.function.Consumer;
import jsinterop.base.Any;
import jsinterop.base.Js;
import jsinterop.base.JsPropertyMap;

/** Promise-based code next to GWT's callback style. */
public final class Net {
  private Net() {}

  /** fetch() returns a Promise; the chain below never blocks. */
  public static Promise<String> firstTitle(String url) {
    return DomGlobal.fetch(url)
        .then(response -> {
          if (!response.ok) {
            return Promise.reject("HTTP " + response.status);
          }
          return response.json();
        })
        .then(json -> {
          JsPropertyMap<Object> page = Js.asPropertyMap(json);
          Any[] books = page.getAsAny("books").asArray();
          return Promise.resolve(books[0].asPropertyMap().getAsAny("title").asString());
        });
  }

  /** Adapter: expose a callback-style call as a Promise. */
  public static <T> Promise<T> toPromise(Consumer<AsyncCallback<T>> call) {
    return new Promise<>((resolve, reject) ->
        call.accept(new AsyncCallback<T>() {
          @Override
          public void onFailure(Throwable caught) {
            reject.onInvoke(caught.getMessage());
          }

          @Override
          public void onSuccess(T result) {
            resolve.onInvoke(result);
          }
        }));
  }

  /** Adapter the other way: consume a Promise through an AsyncCallback. */
  public static <T> void fromPromise(Promise<T> promise, AsyncCallback<T> callback) {
    promise.then(value -> {
      callback.onSuccess(value);
      return null;
    }, error -> {
      callback.onFailure(new RuntimeException(String.valueOf(error)));
      return null;
    });
  }
}

Source: MDN — fetch()

The lab served a one-book JSON file and called these methods:

  • Net.firstTitle("books.json") resolved to Dune, reading books[0].title through JsPropertyMap and Any.

  • Net.firstTitle("missing.json") rejected with HTTP 404, the string passed to Promise.reject.

  • Net.<String>toPromise(cb -> cb.onSuccess("rpc-ok")) turned a callback-style call into a Promise that resolved to rpc-ok.

  • Net.fromPromise(promise, callback) did the reverse: for the failed fetch it called onFailure with a RuntimeException whose message was HTTP 404.

Three observations about the code:

  • The lambdas passed to then are @JsFunction lambdas, and the generic types (Promise<String>, IThenable<...>) are erased as usual; the Java compiler infers the chain.

  • A promise rejection value can be anything. The adapter converts it with String.valueOf(error); a production adapter should inspect it (for a fetch failure it is a TypeError, for a rejected Response the code above builds the message itself).

  • The callbacks run later, on the browser’s event loop; the GWT code is single-threaded and needs no synchronisation, but a user can navigate away before the Promise settles, so check that the presenter is still attached.

The Developer Guide’s tutorial menu still lists "GWT & Polymer", a six-page tutorial that builds a to-do application with Polymer Web Components through the vaadin-gwt-polymer-elements library. It belongs to the early JsInterop period and should be read as history:

  • It targets the experimental JsInterop of GWT 2.7: its project page tells you to set <jsInteropMode>JS</jsInteropMode> in the old org.codehaus.mojo:gwt-maven-plugin and explains that JsInterop had to be enabled explicitly in 2.7.0. The 2.8.0 (RC1) release notes list the removal of that legacy JsInterop, and the 2.8.0 (Beta1) notes say JsInterop had graduated from experimental, so the flag and the setting no longer exist.

  • It creates the project with the SDK’s webAppCreator command and an old pom.xml fix-up, where this section uses the modular-webapp Maven archetype.

  • The library it uses, com.vaadin.polymer:vaadin-gwt-polymer-elements, has its last Maven Central release (1.9.3.1) dated 2017-09-17; the GitHub repository has moved from vaadin to manolo/gwt-polymer-elements and its last push was 2018-10-23. It wraps Polymer 1.x elements.

  • The Polymer project itself states in its README that LitElement is the successor of PolymerElement and recommends considering it for new projects.

The tutorial still shows the technique that did not age: web components are DOM elements with properties, so they are native Java types, and a code generator (gwt-api-generator) can produce those bindings from the elements' metadata. For a new application use the pattern shown in the section above, or Elemental2’s DOM types.

J2CL compatibility

J2CL is Google’s Java-to-JavaScript transpiler. It is a separate product from GWT, and the J2CL README says the GWT 3 effort evolved into an SDK for libraries and enterprise tooling on top of it. The point for a GWT 2.13 application is not to switch, but to write the boundary code (the annotations and the helper libraries on this page) so that it stays portable: GWT 2.9.0 made the compiler accept jsinterop-base, Elemental2 and jsinterop-annotations 2.0.0, which the release notes call compatibility across these tools with J2CL, except for @JsAsync and @JsEnum.

The Bookshelf, end to end

In the section’s running scenario, JsInterop appears in three places, each one a pattern from this page.

  • Number formatting (native type). NumberFormatJs formats the number of copies in the reader’s locale (see Internationalization); the exported bookshelf.Api.formatCopies makes the same function reachable from the host page.

  • Opening a book from outside GWT (exported type). bookshelf.Api.open(id) calls the PlaceController (see MVP, Activities & Places), so a legacy script, a link on another page of the site or a test can navigate the application without reaching into its internals. The install(ClientFactory) hook is Java-only (@JsIgnore).

  • The admin chart (native type, callback, widget). LoanChart wraps the chart library, calls destroy() when detached, and routes onClick back into the presenter.

The pieces fit the earlier pages: the presenters stay in plain Java and know nothing about JavaScript, the native types are in one interop package, and the host page decides which scripts load. Security rules from the other pages still apply across the boundary. A value that came from JavaScript is untrusted input like any other: bookshelf.Api.open(id) must check that the id is a valid number (an int parameter would not, as the table above shows), the server must authorise every operation behind it, and text from a script that is shown on the page goes through setText or SafeHtml (see SafeHtml & XSS), never setHTML with concatenated input.

What changed since the older material

  • JSNI chapter. The 2007 book (GWT 1.3 and 1.4) treats JavaScript interop as JSNI: handwritten JavaScript in /*-{ ... }-*/ comments, $wnd and $doc, JavaScriptObject wrappers and hand-built exports, including loading and wrapping third-party libraries. That material still compiles, but JsInterop (stable since 2.8.0, October 2016) replaced it, and the whole JsInterop vocabulary on this page postdates the book by years.

  • Experimental flag. The -XjsInteropMode flag of the 2.7 line and the <jsInteropMode> plugin setting no longer exist.

  • Annotations jar. The annotations moved to their own artifact com.google.jsinterop:jsinterop-annotations (2.8.0 notes); GWT 2.9.0 aligned with jsinterop-base 1.0.0, Elemental2 1.0.0 and jsinterop-annotations 2.0.0.

  • Export filters. -includeJsInteropExports and -excludeJsInteropExports came in 2.8.1; their notes describe wildcards, and the 2.13.1 implementation uses regular expressions.

  • Overlay on default methods. Since 2.8.0 @JsOverlay may be used on Java 8 default methods (as jsinterop-base does), and @JsOptional was added in the same line.

  • Stale links. The Developer Guide’s annotation Javadoc link and the DevGuideJsInterop.html name used elsewhere both return 404; the working page is DevGuideCodingBasicsJsInterop.html.
