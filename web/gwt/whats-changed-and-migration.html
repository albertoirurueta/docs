What’s Changed & Migration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against GWT 2.13.1 (2026-06-19), gwt-maven-plugin 1.3.0 (2026-05-31), JDK 21 with -sourceLevel 17 and Jakarta Servlet 6.0 (the stack the modular-webapp archetype 2026.6.22 generates), as of 2026-10-09; the release dates are those of the official release notes. It is about everything that moved: the language and tooling jumps from GWT 1.x to 2.x, what each 2.x release changed, how to migrate an existing project (build and server code: Maven coordinates, servlets, plugin; client code compiled to JavaScript: JSNI, Elemental, CSS), and where older books, tutorials and even some official pages no longer match the toolkit. It is the page to open when you inherit an application written for GWT 1.x to 2.8, when a tutorial or the 2007 first edition of GWT in Action tells you something that does not compile, and when you have to decide the order of an upgrade. Each topic page of this section has its own "outdated" and "recent changes" notes; this page collects them in one place.

The 2.x line on one page

timeline title GWT milestones that change how applications are written 2009 : 2.0 in-browser development mode, UiBinder, ClientBundle, code splitting, HtmlUnit tests 2010 : 2.1 cell widgets, RequestFactory, Activities and Places 2012 : 2.5 Super Dev Mode experimental, Elemental experimental, ARIA library 2014 : 2.7 Super Dev Mode is the default, GSS and JsInterop experimental 2016 : 2.8 Java 8 syntax, JsInterop and GSS graduate 2020 : 2.9 Elemental2 and jsinterop-base compatible, Elemental deprecated 2022 : 2.10 org.gwtproject coordinates, IE 8 to 10 dropped, Java 17 tested 2024 : 2.11 Jakarta artifacts : 2.12 Java 12 to 17 language features 2026 : 2.13 static-only DevMode server, JFR events : 2.13.1 bug fixes

The long gaps are real: after 2.8.2 (2017-10-19) the project shipped 2.9.0 in 2020, 2.10.0 in 2022 and 2.11.0 in 2024, and 2.13.1 on 2026-06-19 is the newest release. The open milestone list of the GitHub repository and the roadmap name the direction: bring Java language features and the JRE emulation up to Java 21, and explore some J2CL-only JsInterop features in the GWT compiler. There is no GWT 3 release (J2CL & the Future).

From GWT 1.x to 2.x

The first edition of the book this section is compared with describes GWT 1.3 and 1.4 (2007) and Java 1.4 client code. Moving from that world to GWT 2 is less one upgrade than five: the language level, the event model, the development loop, the resources and the UI toolkit.

Source: GWT — Release notes (1.5.0, 2.0.0 RC1, 2.1.0 M1, 2.5.0 RC1, 2.7.0 RC1, 2.8.0)

Three consequences of that table deserve a sentence each, because they are what breaks an old code base first.

  • The 2.0 notes introduce the terms "development mode" and "production mode" for what 1.x called hosted mode and web mode. Command lines changed with them: -web became -prod, -portHosted became -codeServerPort, and junitCreator disappeared into webAppCreator -junit. webAppCreator is itself deprecated since 2.11.0 (see Getting Started).

  • Deferred binding and the module XML survived the jump unchanged in spirit: a 1.x module descriptor with <inherits>, <source>, <entry-point>, <servlet> still parses, but its user.agent assumptions do not (see the browser matrix below).

  • Server code is Java, not GWT. A 1.x servlet that extends RemoteServiceServlet still works if its javax.servlet container still exists; on a Jakarta container it needs the recipe below.

Behaviour changes that compile but behave differently

These are the changes that no compiler error will report. Two are in the 2.13.0 notes under "Breaking Changes"; the others are consequences of defaults that moved.

Table 4. Silent changes and how to check your code
Change What it means for your code Check

String.split emulation follows Java 8 semantics for empty entries (2.13.0)

Code that split on a delimiter and relied on the old emulated handling of empty leading or trailing entries can return a different array

Search for split( in client and shared code; shared code now matches the JVM behaviour

Collectors.toMap throws when a value is null (2.13.0)

The emulation matches the JVM (though not its Javadoc); a map built from nullable values fails at run time in the browser

Search for toMap(; filter nulls or use a merge-friendly collector

AccessControlException emulation removed (2.13.0)

A class that catches or throws it in shared code stops compiling for the client

Keep it behind a server-only class or @GwtIncompatible

Source level (2.12.0 and 2.13.x)

The command-line compiler’s -sourceLevel defaults to 1.8, so Java 12 to 17 syntax in a Java 17 code base is rejected unless the build passes -sourceLevel 17. auto resolves to the level of the running JVM

The archetype sets <sourceLevel>17</sourceLevel> in gwt-maven-plugin (the plugin’s own default comes from maven.compiler.source); set it in any hand-written build

-failOnError (alias -strict since 2.13.0)

Without it the compiler can hide JSNI and overlay errors behind "Ignored N units with compilation errors in first pass"; the archetype turns it on

Make sure failOnError is true in CI

DevMode as application server (2.13.0)

The embedded Jetty 9 launcher is no longer the default and is "due to be removed". A project that relied on gwt:devmode serving its servlets must split the server out or supply a ServletContainerLauncher

Run the server (Jetty or Spring Boot) separately and use gwt:codeserver

JPA/JDO enhanced classes over GWT-RPC (2.10.1 and 2.11.0)

Entities that were enhanced by an ORM are no longer serializable by default; a warning explains it (the -Dgwt.enhancedClasses.enabled=true switch restores the old behaviour at your own risk)

Send plain DTOs instead

Source: GWT — Release notes (2.13.0, 2.12.0, 2.11.0)

Migration recipes

Migrate in this order; every step leaves the project buildable, and the order puts the build first because every later step needs the 2.13 tools.

com.google.gwt to org.gwtproject

The repository metadata confirms the cut: com.google.gwt:gwt-user and gwt-servlet have 2.10.0 as latest and release version (last updated 2022-06-23), and asking for a newer version under the old groupId fails like this:

Could not find artifact com.google.gwt:gwt-user:jar:2.13.1

The POM of that version does not exist in the old group on Maven Central (the request answers 404). The edit that fixes it is a groupId change plus a BOM:

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.gwtproject</groupId>
      <artifactId>gwt</artifactId>
      <version>2.13.1</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <dependency>
    <groupId>org.gwtproject</groupId>
    <artifactId>gwt-user</artifactId> <!-- version from the BOM -->
  </dependency>
  <dependency>
    <groupId>org.gwtproject</groupId>
    <artifactId>gwt-dev</artifactId>
  </dependency>
</dependencies>

Source: GWT — Release notes (2.10.0: Maven groupId)

If a library you depend on still declares com.google.gwt:gwt-user 2.10.0 transitively, import the new BOM first so Maven resolves a single version, and exclude the old coordinates.

javax to jakarta

A servlet container that implements Jakarta Servlet 5 or later (Tomcat 10+, Jetty 11+, Spring Boot 3+) has no javax.servlet classes, so GWT’s server classes that extend javax.servlet.http.HttpServlet cannot load. GWT 2.11.0 added Jakarta variants; the client side is untouched.

com.google.gwt.user.client.rpc.RemoteService, AsyncCallback, @RemoteServiceRelativePath, XsrfProtectedService, XsrfToken, XsrfTokenService (client and shared code)

com.google.gwt.user.server.rpc.RemoteServiceServlet becomes com.google.gwt.user.server.rpc.jakarta.RemoteServiceServlet

Your DTOs and your service interfaces

XsrfProtectedServiceServlet and XsrfTokenServiceServlet become the classes of the same names in com.google.gwt.user.server.rpc.jakarta

The module XML

com.google.gwt.logging.server.RemoteLoggingServiceImpl becomes the class in com.google.gwt.logging.server.jakarta

*.gwt.xml, the host page

RequestFactory: com.google.web.bindery.requestfactory.server.RequestFactoryServlet becomes the class in com.google.web.bindery.requestfactory.server.jakarta, from org.gwtproject.web.bindery:requestfactory-server-jakarta

servlet-api provided by the container

the dependency org.gwtproject:gwt-servlet-jakarta (runtime), jakarta.servlet:jakarta.servlet-api 6.0.0 (provided) and the web.xml namespace https://jakarta.ee/xml/ns/jakartaee

Source: GWT — Release notes (2.11.0: Jakarta artifacts)

The mismatch is easy to recognise because the compiler cannot even read the old servlet class against Jakarta Servlet 6. Compiling a servlet that still extends the javax base class with gwt-user 2.13.1 and jakarta.servlet-api 6.0.0 on the class path printed (JDK 21):

src/com/example/bookshelf/server/LegacyCatalogServlet.java:3: error: cannot access HttpServlet
public class LegacyCatalogServlet extends RemoteServiceServlet {
                                          ^
  class file for javax.servlet.http.HttpServlet not found
src/com/example/bookshelf/server/LegacyCatalogServlet.java:3: error: cannot access ServletException
public class LegacyCatalogServlet extends RemoteServiceServlet {
       ^
  class file for javax.servlet.ServletException not found
2 errors

Changing the import to the jakarta package, with gwt-servlet-jakarta on the class path, compiled cleanly. The reverse mistake (a Jakarta servlet class deployed to a javax container) fails when the container loads the class. Keep one flavour per deployment.

// Before: javax container
import com.google.gwt.user.server.rpc.XsrfProtectedServiceServlet;

// After: Jakarta container (Tomcat 10+, Jetty 11+, Spring Boot 3+)
import com.google.gwt.user.server.rpc.jakarta.XsrfProtectedServiceServlet;

Source: GWT — Release notes (2.11.0)

Two related facts move with this recipe. The validation annotations follow the same split: a javax.validation constraint on a DTO is silently ignored by a Jakarta Bean Validation server and vice versa (see Validation). And on JDK 17 and later every reflectively serialized exception fails over GWT-RPC unless the container JVM is started with --add-opens java.base/java.lang=ALL-UNNAMED or the class has a custom field serializer (upstream issue gwtproject/gwt#9793; see GWT-RPC).

The Codehaus plugin to the net.ltgt plugin

JSNI to JsInterop

JSNI (/*-{ ... }-*/ bodies of native methods and JavaScriptObject overlays) still compiles in 2.13.1, but JsInterop (stable since 2.8.0, compatible with J2CL since 2.9.0) replaces it for new code and is the only style that carries over to J2CL. The mapping, verified by compiling both versions, is in JSNI & Overlay Types and JsInterop; the short version:

CSS to GSS

Legacy CssResource syntax (@def, @eval, @sprite, @if user.agent) has been deprecated since 2.8.0, but it is still the default in 2.13.1: CssResource.enableGss is false, CssResource.conversionMode is off and CssResource.gssDefaultInUiBinder is false. Automatic conversion is a bridge that the compiler says "will be removed in the next version of GWT".

The sequence that worked on the Bookshelf (details, converter output and every combination of the three properties are in Styling: CSS & GSS):

  1. Turn on CssResource.enableGss and set CssResource.conversionMode to strict, so remaining .css files are converted in memory.

  2. Convert a folder with com.google.gwt.resources.converter.Css2Gss (its class path needs gwt-dev as well as gwt-user), review the .gss it wrote, fix what it dropped (comments, CSS hacks).

  3. Keep @Source("book.css") as it is: with enableGss true the compiler prefers a .gss file of the same base name.

  4. When no .css file is referenced, delete them, remove conversionMode and set gssDefaultInUiBinder to true.

<!-- bookshelf App.gwt.xml: the bridge configuration -->
<set-configuration-property name="CssResource.enableGss" value="true" />
<set-configuration-property name="CssResource.conversionMode" value="strict" />
<!-- the end state: enableGss true, gssDefaultInUiBinder true, no conversionMode -->

Source: GWT — GSS Migration Guide

There is no GssResource type in 2.13.1: GSS is a syntax of CssResource selected by the property (the generator is GssResourceGenerator). DataGrid, CellTable and the other widgets that embed legacy CSS need strict conversion or gssDefaultInUiBinder once enableGss is true.

Step 2: the servlet

package com.example.bookshelf.server;

import com.example.bookshelf.shared.Book;
import com.example.bookshelf.shared.BookNotFoundException;
import com.example.bookshelf.shared.BookPage;
import com.example.bookshelf.shared.CatalogService;
import com.google.gwt.user.server.rpc.jakarta.XsrfProtectedServiceServlet;

public class CatalogServiceImpl extends XsrfProtectedServiceServlet implements CatalogService {
  @Override
  public BookPage getBooks(int start, int length) {
    return CatalogRepository.INSTANCE.page(start, Math.min(length, 100));
  }

  @Override
  public Book saveBook(Book book) throws BookNotFoundException {
    if (book.getTitle() == null || book.getTitle().isBlank() || book.getTitle().length() > 200) {
      throw new IllegalArgumentException("Invalid title");
    }
    return CatalogRepository.INSTANCE.save(book);
  }

  // getBook(long id) omitted
}

The import is the only difference from the javax version; the server also validates its input, because nothing the browser sends can be trusted. web.xml moves to the https://jakarta.ee/xml/ns/jakartaee namespace (version 5.0), declares gwt.xsrf.session_cookie_name and maps XsrfTokenServiceServlet (the jakarta class) next to the service servlet.

Step 3: the JSNI method

// before: JSNI in a widget, legacy but still compiles in 2.13.1
// private static native String format(String locale, double n) /*-{ ... }-*/;
// ("..." is the native body that called the browser's Intl.NumberFormat)
// after: a native JsInterop type, no JavaScript text
package com.example.bookshelf.client.interop;

import jsinterop.annotations.JsType;

@JsType(isNative = true, namespace = "Intl", name = "NumberFormat")
public class NumberFormatJs {
  public NumberFormatJs(String locale) {}

  public native String format(double value);
}

Used as new NumberFormatJs("es").format(1234.5). Exporting the same logic to the host page is one more annotation, and needs the compiler flag:

@JsType(namespace = "bookshelf", name = "Api")
public final class ExportedApi {
  private ExportedApi() {}

  @JsMethod
  public static String formatCopies(String locale, double n) { return new NumberFormatJs(locale).format(n); }
}

In the browser bookshelf.Api.formatCopies('es', 1234.5) returned "1234,5" (no grouping separator for four digits with the es locale). Without -generateJsInteropExports in both compilerArgs and codeserverArgs the call fails with ReferenceError: bookshelf is not defined.

A migration checklist

  1. Pin the toolchain: JDK 21 (the tools need Java 11 or later), Maven 3.9, GWT 2.13.1, gwt-maven-plugin 1.3.0.

  2. Replace the plugin and the groupId, import the org.gwtproject:gwt BOM and delete explicit GWT versions.

  3. Set sourceLevel to 17 and failOnError to true, and fix the new errors one at a time.

  4. Switch servlets to jakarta if the container requires it, and set --add-opens java.base/java.lang=ALL-UNNAMED for exception serialization on Java 17 and later.

  5. Run Super Dev Mode with gwt:codeserver from the root POM; run the server separately.

  6. Replace listener interfaces, ImageBundle, DeferredCommand and DOM.* calls with their current forms; the compiler’s deprecation warnings list them.

  7. Convert CSS to GSS folder by folder with strict conversion as the bridge.

  8. Convert JSNI to JsInterop, Elemental to Elemental2; add the export flag to both compilerArgs and codeserverArgs.

  9. Review String.split, Collectors.toMap and AccessControlException uses for the 2.13.0 changes.

  10. Review security: user data as text, SafeHtml for markup, XSRF protection, a CSP that matches the chosen linker and output style.

  11. Run mvn verify and a manual Super Dev Mode session before moving on to J2CL-oriented clean-ups.
