Message Design and Serialization

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A WebSocket gives you an ordered stream of frames and nothing else: no message names, no request/response pairing, no retry safety, no versioning and no schema. Everything that makes the stream a protocol is yours to design, and a mistake here is paid for in every client you ever ship, because old mobile builds and cached browser tabs keep talking your first design for years. This page designs one complete protocol, Chatterbox v1, and then uses it as the contract that every WebSocket server page of this section implements, so that one browser client can talk to every stack.

It was written against Node.js 24.21 (type stripping on by default, the global WebSocket client stable since 22.4.0), ws 8.22.0, Zod 4.6.7, Ajv 8.20.0, @msgpack/msgpack 3.1.3, protobufjs 8.8.1 and TypeScript 7.0.2. The standards behind it are JSON in RFC 8259 (STD 90) with the I-JSON profile of RFC 7493, the WebSocket protocol in RFC 6455 and UUIDs (including UUIDv7) in RFC 9562. Everything was checked on 2026-10-24, and every project listing on this page (the schema, server, client and scripts) was run and type-checked.

Who uses what. The chat scenario (Chatterbox) uses the whole protocol: acknowledged messages, idempotent retries, per-room ordering, history, presence, typing and receipts. The videoconference scenario (Huddle) reuses the envelope, acknowledgements and error model for its signalling messages (offers, answers and candidates, see Signaling and Perfect Negotiation), because signalling is also request/response over one socket. The game scenario (Pixel Arena) uses the same ideas but a binary encoding for its high-rate state, as measured in Choosing an encoding and used in Multiplayer Game Architecture.

Envelopes and versioning

Every frame carries a small, fixed envelope with routing and bookkeeping fields, and a type-specific payload. The envelope is the part you can never change, so keep it small and boring. Chatterbox uses six fields, which have been enough for chat, signalling and presence:

Field Type Meaning

v

integer

Protocol major version, always 1 in this specification. A server that receives another value answers with the error unsupported_version and closes the socket with code 4426.

type

string

One of the twelve types: hello, join, leave, message, edit, react, typing, receipt, presence, history, ack and error. It selects the payload schema.

id

string

Generated by the client for every client-to-server envelope (a UUIDv7 or a ULID, 26 to 36 characters). Server-originated envelopes carry a server-generated id made of the prefix s_ and a ULID. The id of a message is the id of that message forever: edits, reactions and receipts refer to it.

room

string or null

A room name matching [a-z0-9-]{1,64}. Direct messages use dm-<userA>-<userB> with the two user ids sorted. It is null for hello, for client presence and for acks and errors that are not tied to a room.

ts

integer

Server time in Unix epoch milliseconds, set by the server on every outbound envelope. A client-supplied ts is ignored (clients send 0).

payload

object

The type-specific body. Use {} when there is nothing to say; it is never null.

A second field lives inside the payload of message, edit and react broadcasts: seq, a per-room, strictly increasing integer assigned by the server. It is the ordering key (see Ordering).

Four design decisions are worth copying even if you never use Chatterbox:

  • A type discriminator and a payload object, rather than flat fields. A receiver can route on type without understanding the payload, log the envelope without logging user text, and apply one validation schema per type. Flat messages with a mix of optional fields cannot be validated this strictly.

  • Names that never change meaning. A field can be added (receivers ignore unknown fields, so adding an optional field is compatible within v1) but never renamed, retyped or repurposed. Removing one needs a new major version.

  • Integers for time, strings for ids. Epoch milliseconds are smaller than ISO 8601 strings and cannot be mis-parsed; ids and any 64-bit quantity are strings, because JSON numbers are IEEE 754 doubles in JavaScript and silently lose integer precision above 2^53 (RFC 7493 says to send such values as strings).

  • null for "explicitly nothing", absent for "unknown or unchanged". replyTo: null means "not a reply"; a missing replyTo is invalid for a new message. Never use the text "null" or an empty string as a sentinel.

Version negotiation

Chatterbox negotiates the version twice, on purpose. The WebSocket handshake carries the subprotocol token chatterbox.v1 in Sec-WebSocket-Protocol (RFC 6455, section 1.9). The browser lists the versions it supports in preference order, the server picks one and echoes it, and a server that supports none returns the handshake without a subprotocol (browsers then fail the connection). The v field in every envelope repeats the decision for the benefit of logs, replayed history and proxies that see frames without the handshake.

// browser: offer v2 first, fall back to v1; the server answers with exactly one of them
const ws = new WebSocket("wss://chat.example.test/ws", ["chatterbox.v2", "chatterbox.v1"]);
ws.onopen = () => console.log("negotiated", ws.protocol); // "chatterbox.v1" or "chatterbox.v2"

Source: MDN: WebSocket constructor, the protocols argument

The rules that keep a protocol evolvable are short:

  • Additive changes stay in v1. New optional payload fields, new error codes and new optional behaviour are fine because receivers ignore what they do not know. A new type is not additive, because an old receiver answers bad_request; gate new types behind a hello capability or a new version.

  • Breaking changes get a new major version and a new subprotocol token. Run both versions side by side until the old clients are gone, and measure that with the client string in hello.

  • Never infer the version from the payload shape. Always read v.

  • Servers advertise limits in hello (heartbeatMs, maxFrameBytes) so they can change without a client release.

Request/response correlation

WebSocket frames have no built-in reply mechanism. Chatterbox adds one with the envelope id:

  1. The client generates a fresh id and sends the request.

  2. The server answers with exactly one ack or one error whose payload field ref equals that id.

  3. The client keeps a map from pending ids to promises, resolves the promise on the matching ack and rejects it on the matching error, and starts a 10 second ack timeout when it sends.

Everything else is a push: broadcasts such as another user’s message or typing, which no one asked for and which carry no ref. Two types are deliberately fire-and-forget because losing one is harmless and an ack per keystroke would double the traffic: typing and receipt (receipts are cumulative, so the next one supersedes a lost one). The hello request is answered by the hello reply, whose payload also contains ref.

The ack is not a delivery receipt to other users. It means only "the server accepted and stored this envelope, and assigned seq`". Delivery and read state travel as `receipt frames (see Presence, Typing and Receipts).

The next subsections give each type’s payload, one complete example frame and the server behaviour. Every example below is validated against the Zod schemas of The Zod schema module by the conformance script, so they cannot drift from the code.

hello

Direction: client to server as the first frame, and server to client as the reply. The server must receive hello within 5 seconds of the socket opening, else it closes with code 4408.

Client payload:

Field Type Meaning

token

string, optional

A one-time ticket minted by an authenticated HTTP call. Omitted when the connection is authenticated by a cookie.

client

string

Client name and version such as web/1.4, for logs and version statistics.

resume

object, optional

{ "sessionId": string, "rooms": { "<room>": <lastSeq> } }: the session to continue and the last seq the client has seen per room.

 
{
  "v": 1, "type": "hello", "id": "01JAB3W6A1B2C3D4E5F6G7H8J9", "room": null, "ts": 0,
  "payload": {
    "token": "ticket-change-me",
    "client": "web/1.4",
    "resume": { "sessionId": "sess_01JAB3V0000000000000000000", "rooms": {"general":41} }
  }
}

Source: RFC 8259, section 4: Objects

Server payload (the reply):

Field Type Meaning

ref

string

The id of the client hello.

userId, name

string

The authenticated identity.

sessionId

string

Pass it back in resume after a reconnect.

heartbeatMs

integer

Heartbeat interval, 20000 by default.

maxFrameBytes

integer

Largest client frame the server accepts, 16384.

resumed

boolean

true when the old session was found and missed events are about to be replayed.

rooms

array of strings

Rooms the session is currently a member of.

 
{
  "v": 1, "type": "hello", "id": "s_01JAB3W7QA0000000000000000", "room": null, "ts": 1761300000000,
  "payload": {
    "ref": "01JAB3W6A1B2C3D4E5F6G7H8J9",
    "userId": "alice",
    "name": "Alice",
    "sessionId": "sess_01JAB3V0000000000000000000",
    "heartbeatMs": 20000,
    "maxFrameBytes": 16384,
    "resumed": true,
    "rooms": ["general"]
  }
}

Source: RFC 8259, section 5: Arrays

Server behaviour: validate the ticket (one-time, expires after 30 seconds, an invalid or replayed ticket gets unauthorized and close 4401), create or resume the session, reply, and when resuming replay the message, edit and react envelopes with seq greater than the client’s lastSeq for each room it names. Any frame other than hello before the handshake completes is answered with unauthorized and close 4401; a second hello gets conflict.

join

Direction: client to server. Payload { "since": <seq or null> }. The ack result is { "members": [{ "userId", "name", "status" }], "lastSeq": integer }. The server creates the room if it does not exist, adds the user, acks, replays envelopes newer than since when it is not null, and broadcasts the user’s presence to the other members. Direct message rooms (dm- prefix) are open only to the two users named in the room, otherwise the answer is forbidden. Joining a room you are already in is allowed and has no further effect.

{
  "v": 1, "type": "join", "id": "01JAB3W6B1B2C3D4E5F6G7H8J9", "room": "general", "ts": 0,
  "payload": { "since": 41 }
}

Source: RFC 8259, section 3: Values

leave

Direction: client to server. Payload {}, ack result {}. Leaving a room you are not in answers not_found.

{
  "v": 1, "type": "leave", "id": "01JAB3W6C1B2C3D4E5F6G7H8J9", "room": "general", "ts": 0,
  "payload": {  }
}

Source: RFC 8259, section 4: Objects

message

Direction: client to server to post, and server to client to broadcast to every member of the room including the sender. The envelope id is the client’s id and stays the message id forever.

Client payload:

Field Type Meaning

text

string

1 to 4000 UTF-16 code units (the JavaScript length).

replyTo

string or null

The id of the message this one answers, which must exist in the same room.

attachments

array

0 to 5 objects { "url": https URL, "name": string, "mime": string, "size": integer }. Files are uploaded over HTTP first; the protocol carries only references.

 
{

    "text": "Hello, Chatterbox",
    "replyTo": null,
    "attachments": [
      {
        "url": "https://chat.example.test/files/menu.pdf",
        "name": "menu.pdf",
        "mime": "application/pdf",
        "size": 48213

    ]
  }
}

{
  "v": 1, "type": "message", "id": "01JAB3W7Q8Z4N5R6T7V8X9Y0ZA", "room": "general", "ts": 1761300000000,

    "from": { "userId": "alice", "name": "Alice" },

Server behaviour: the sender must be a member (else forbidden); a replyTo that is not a message of this room is not_found; the server assigns the next seq, stores the message, answers the sender with an ack carrying seq, and broadcasts. A duplicate id returns the original ack with dup: true and does nothing else (see Idempotency).

edit

Direction: client to server { "target": messageId, "text": string }; server to client broadcast { "target", "text", "seq", "editedAt" }. Only the author may edit (forbidden otherwise), the target must exist (not_found), and the edit consumes a new seq so that every client applies edits in the same order.

{
  "v": 1, "type": "edit", "id": "01JAB3WAE1B2C3D4E5F6G7H8J9", "room": "general", "ts": 0,
  "payload": { "target": "01JAB3W7Q8Z4N5R6T7V8X9Y0ZA", "text": "Hello, Chatterbox!" }
}

Source: RFC 8259, section 4: Objects

{
  "v": 1, "type": "edit", "id": "s_01JAB3W7QB0000000000000000", "room": "general", "ts": 1761300005000,
  "payload": {
    "target": "01JAB3W7Q8Z4N5R6T7V8X9Y0ZA",
    "text": "Hello, Chatterbox!",
    "seq": 43,
    "editedAt": 1761300005000
  }
}

Source: RFC 8259, section 6: Numbers

react

Direction: client to server { "target": messageId, "emoji": string, "op": "add" or "remove" }, where emoji is exactly one grapheme cluster; server to client broadcast { "target", "emoji", "op", "from": { "userId" }, "seq" }. Adding a reaction the user already added is conflict; removing one that is not there is not_found.

{
  "v": 1, "type": "react", "id": "01JAB3WAF1B2C3D4E5F6G7H8J9", "room": "general", "ts": 0,
  "payload": { "target": "01JAB3W7Q8Z4N5R6T7V8X9Y0ZA", "emoji": "👍", "op": "add" }
}

Source: MDN: Intl.Segmenter (counting graphemes)

{
  "v": 1, "type": "react", "id": "s_01JAB3W7QC0000000000000000", "room": "general", "ts": 1761300006000,
  "payload": {
    "target": "01JAB3W7Q8Z4N5R6T7V8X9Y0ZA",
    "emoji": "👍",
    "op": "add",
    "from": { "userId": "bob" },
    "seq": 44
  }
}

Source: RFC 8259, section 7: Strings

typing

Direction: client to server { "state": "start" or "stop" }, fire-and-forget, throttled by the client to one frame per 3 seconds; server to the other members { "userId", "state" }. Receivers expire a start after 5 seconds, so a lost stop never leaves an indicator stuck.

{
  "v": 1, "type": "typing", "id": "01JAB3WAG1B2C3D4E5F6G7H8J9", "room": "general", "ts": 0,
  "payload": { "state": "start" }
}

Source: RFC 8259, section 4: Objects

{
  "v": 1, "type": "typing", "id": "s_01JAB3W7QD0000000000000000", "room": "general", "ts": 1761300007000,
  "payload": { "userId": "bob", "state": "start" }
}

Source: RFC 8259, section 3: Values

receipt

Direction: client to server { "kind": "delivered" or "read", "upTo": seq }, fire-and-forget and cumulative (everything up to and including upTo); server to the other members { "userId", "kind", "upTo" }. An upTo beyond the room’s last seq is bad_request.

{
  "v": 1, "type": "receipt", "id": "01JAB3WAH1B2C3D4E5F6G7H8J9", "room": "general", "ts": 0,
  "payload": { "kind": "read", "upTo": 44 }
}

Source: RFC 8259, section 6: Numbers

{
  "v": 1, "type": "receipt", "id": "s_01JAB3W7QE0000000000000000", "room": "general", "ts": 1761300008000,
  "payload": { "userId": "bob", "kind": "read", "upTo": 44 }
}

Source: RFC 8259, section 4: Objects

presence

Direction: client to server { "status": "online" or "away" } with room set to null; server to room members { "userId", "name", "status": "online", "away" or "offline" }. This frame doubles as the application heartbeat: the client re-sends its current status every heartbeatMs, the server acks it, and the client measures the round trip. The server broadcasts only changes. A user becomes offline for everyone 15 seconds after their last connection closes.

{
  "v": 1, "type": "presence", "id": "01JAB3WAJ1B2C3D4E5F6G7H8J9", "room": null, "ts": 0,
  "payload": { "status": "away" }
}

Source: RFC 6455, section 5.5.2: Ping (protocol-level heartbeat)

{
  "v": 1, "type": "presence", "id": "s_01JAB3W7QF0000000000000000", "room": "general", "ts": 1761300009000,
  "payload": { "userId": "alice", "name": "Alice", "status": "away" }
}

Source: RFC 8259, section 7: Strings

history

Direction: client to server { "before": seq or null, "limit": 1 to 100 } (default 50). before is exclusive and null means "newest". The answer is an ack whose result is { "messages": [message envelopes, ascending seq], "hasMore": boolean, "next": seq or null }. Page back by sending next as the next before. Because edits and reactions consume sequence numbers too, the message seq values on a page have gaps; that is normal.

{
  "v": 1, "type": "history", "id": "01JAB3WAK1B2C3D4E5F6G7H8J9", "room": "general", "ts": 0,
  "payload": { "before": 42, "limit": 2 }
}

Source: RFC 8259, section 5: Arrays

The ack that answers it:

{
  "v": 1, "type": "ack", "id": "s_01JAB3W7QJ0000000000000000", "room": "general", "ts": 1761300013000,
  "payload": {
    "ref": "01JAB3WAK1B2C3D4E5F6G7H8J9",
    "ok": true,
    "seq": null,
    "dup": false,
    "result": {
      "messages": [
        {
          "v": 1,
          "type": "message",
          "id": "01JAB3W9D2F6G8H0J1K3M5N7P9",

          "ts": 1761299940000,

            "from": { "userId": "bob", "name": "Bob" },
            "text": "Morning!",
            "replyTo": null,
            "attachments": [],
            "seq": 40,
            "edited": false
          }
        }
      ],
      "hasMore": true,
      "next": 40
    }
  }
}

Source: RFC 8259, section 4: Objects

ack and error

Both are server-to-client only. They are described next, together with the error-code table.

Acknowledgements, errors and the code table

ack payload: { "ref": id, "ok": true, "seq": integer or null, "dup": boolean, "result": object }. It is sent for every client envelope except typing, receipt and hello. seq is the assigned sequence for message, edit and react, and null otherwise. dup is true when the id was already processed. result is type specific: empty for a message, the member list for join, the page for history.

{
  "v": 1, "type": "ack", "id": "s_01JAB3W7QG0000000000000000", "room": "general", "ts": 1761300000000,
  "payload": { "ref": "01JAB3W7Q8Z4N5R6T7V8X9Y0ZA", "ok": true, "seq": 42, "dup": false, "result": {} }
}

Source: RFC 8259, section 4: Objects

error payload: { "ref": id or null, "code": string, "message": string, "retryable": boolean }. ref is null when the frame was unparseable or the failure is not tied to a request. The message is for logs and developers, never for users: show localised text chosen by code. Exactly one of ack or error answers each acked request.

{
  "v": 1, "type": "error", "id": "s_01JAB3W7QK0000000000000000", "room": "general", "ts": 1761300014000,
  "payload": {
    "ref": "01JAB3WAE1B2C3D4E5F6G7H8J9",
    "code": "forbidden",
    "message": "only the author can edit a message",
    "retryable": false
  }
}

Source: RFC 8259, section 3: Values

Idempotency

Networks lose acknowledgements. When an ack is lost the client cannot tell "the server never saw my message" from "the server saw it and I never heard back", and the only safe client policy is to retry. The only safe server policy is to make the retry harmless. That is what an idempotency key does: the same operation, identified by the same key, has the same effect no matter how often it is delivered. The envelope id is that key. The same idea protects HTTP payments (Stripe’s Idempotency-Key header, and the IETF HTTP API working group’s draft of the same name, which is still an Internet-Draft).

The Chatterbox rules:

  1. The server keeps a table from (userId, id) to the original ack for at least 24 hours and for at least the last 1000 ids per user.

  2. A repeated id gets that stored ack again with dup: true. No new seq is assigned, nothing is stored and nothing is re-broadcast.

  3. Only acks are remembered. An error is not cached, so a retry after rate_limited or internal is processed afresh (and a deterministic error such as forbidden simply repeats).

  4. The rate limiter runs before deduplication, so a retry storm is still limited.

  5. The client retries unacknowledged envelopes after a reconnect, with the same ids, in their original order, and after an ack timeout of 10 seconds on a live connection.

  6. The client never reuses an id for a different operation, and never regenerates the id on retry.

The reference server of this page implements the table in a few lines (see reply() and the early return in onFrame() in the listing), and the client scenario proves the behaviour three ways: an immediate resend, a resend after a dropped socket, and no second broadcast to the other member.

The same mechanism gives exactly-once effect out of at-least-once delivery. It does not give exactly-once delivery, which does not exist; it makes duplicate delivery invisible. Keys that expire need a deployment story: if your retention is 24 hours, a client that retries after two days may create a duplicate, so client queues must also expire.

Ordering

TCP, and therefore a single WebSocket, delivers frames in order. Order breaks when you add anything else: several sockets per user (a phone and a laptop), a server cluster where two nodes broadcast the same room, a reconnect that replays history while new events arrive, or optimistic UI that renders a local echo before the ack. Wall-clock timestamps cannot fix it, because clocks disagree and two events in the same millisecond have no order.

Per-room sequence numbers

Chatterbox gives each room one counter, assigned by the server when it accepts a message, edit or react. Rules:

  • seq is a strictly increasing integer starting at 1; there is exactly one writer per room, which is what makes it cheap and gapless in a single process. In a cluster, route all writes for a room to one owner (consistent hashing) or allocate the sequence in a shared store such as a Redis INCR (see Scaling WebSockets).

  • Clients render by seq, not by arrival time or ts. An optimistic local echo is shown in a "sending" state at the bottom and re-sorted when the ack arrives.

  • A client tracks lastSeq per room. A jump (it holds 41 and receives 44) means a gap. It fills the gap with a history request or with join and since, and never invents the missing envelopes.

  • The cursor for reconnects, history and receipts is always a seq, never a timestamp.

Lamport timestamps as background

A single seq per room is the right tool when one server owns the room. Peer-to-peer and multi-writer designs (data channels between browsers, offline-first editing, replicated stores) cannot assume one writer, and use logical clocks instead. Leslie Lamport’s 1978 paper defined the simplest one: every process keeps a counter, increments it before it sends, stamps the message, and on receipt sets its counter to the maximum of its own and the stamp, plus one. The result is a partial order consistent with causality: if event A could have influenced event B, then A’s stamp is smaller. The converse does not hold (a smaller stamp does not prove causality), so concurrent events are ordered arbitrarily, and adding the process id as a tiebreaker gives every participant the same total order. Vector clocks go one step further and can detect concurrency, at the price of one counter per participant.

Chatterbox does not need Lamport clocks, because the server is the single sequencer, but the idea explains why seq works and when you must graduate from it:

/** A Lamport clock: a counter that never goes backwards and jumps ahead of anything it has seen. */
export class LamportClock {
  private time = 0;
  /** Call before sending: advances the clock and returns the timestamp to attach. */
  tick(): number { return ++this.time; }
  /** Call on receive: move past the sender's timestamp so causality is preserved. */
  observe(remote: number): number { this.time = Math.max(this.time, remote) + 1; return this.time; }
}

// Alice writes, Bob answers after reading it, Carol writes without having seen either.
const alice = new LamportClock(), bob = new LamportClock(), carol = new LamportClock();
const a1 = alice.tick();          // 1: "Shall we ship?"
bob.observe(a1);                  // Bob's clock becomes 2
const b1 = bob.tick();            // 3: "Yes" (a reply: causally after a1)
const c1 = carol.tick();          // 1: concurrent with a1, unrelated to the other two
console.log({ a1, b1, c1 });
if (!(a1 < b1)) throw new Error("a reply must carry a larger Lamport timestamp than its cause");
// Equal or unordered stamps are concurrent: break ties with (timestamp, userId) to get one total order everyone agrees on.
const order = [{ t: a1, u: "alice" }, { t: b1, u: "bob" }, { t: c1, u: "carol" }]
  .sort((x, y) => x.t - y.t || x.u.localeCompare(y.u)).map((e) => `${e.t}:${e.u}`);

Heartbeat, resume, rate limits, size limits and close codes

Heartbeat. There are two layers and Chatterbox uses both. The server sends a WebSocket protocol ping frame every heartbeatMs (20 seconds); browsers answer with a pong automatically and JavaScript cannot see either. The client sends a presence envelope every heartbeatMs, which the server acks, so the page can measure round-trip time and notice a half-open connection that the operating system has not yet reported. Either side closes with code 4408 after 2 x heartbeatMs of silence. The interval must be shorter than every idle timeout on the path (an AWS Application Load Balancer defaults to 60 seconds); the full lifecycle is in Connection Lifecycle, Heartbeats and Reconnection.

Resume. After a drop the client reconnects on a new socket and sends hello with resume: { sessionId, rooms: { room: lastSeq } }. If the session is still held (the server keeps it for 120 seconds) the reply has resumed: true and the server replays the missed message, edit and react envelopes with their original seq. If not, the reply has resumed: false and the client re-joins each room with since set to its lastSeq. Either way the client then resends its unacknowledged envelopes, and idempotency makes that safe.

Rate limits. 20 envelopes per second per connection with a burst of 40 (a token bucket). Beyond it the server answers rate_limited (retryable); ten of those within ten seconds close the socket with code 4429.

Size limits. 16384 bytes per client frame; larger frames get too_large and close 4413 (the transport guard may close with the standard code 1009 first). Text is 4000 code units and attachments are limited to five references. Frames the server sends may be larger, because a history page is not a client frame, but the server keeps them under 262144 bytes by returning fewer messages and hasMore: true.

Close codes. Browsers may send only 1000 and codes from 3000 to 4999, so application codes live in the 4xxx range; 1005, 1006 and 1015 are reserved and never sent on the wire (1006 is what JavaScript reports for an abnormal drop).

Choosing an encoding

JSON is the default for a reason: every language parses it, browsers have JSON.parse built in, and a frame can be read in the browser’s network panel, in a log file and in a bug report. Its costs are size (every field name is repeated in every frame, and numbers are decimal text), parse time, and a data model of strings, doubles, booleans, null, arrays and objects, with no bytes, no 64-bit integers, no dates and no undefined, NaN or Infinity. How to read the table:

  • For small frames the field names are most of the bytes. A 17-character message is 230 bytes of JSON of which only 17 are the text; MessagePack saves a quarter, Protocol Buffers and the hand-packed layout save about two thirds.

  • The advantage shrinks as the text grows: at 349 characters MessagePack saves only 10 percent, because text dominates. Chat is text, so for Chatterbox the gain is real but modest.

  • Compression closes much of the gap. After deflate, JSON on a history page is as small as MessagePack and Protocol Buffers, because the repeated field names compress away. If your server already runs permessage-deflate, the remaining win of a binary format is parse speed and the small frames (typing, acks, presence), which are the ones that compression helps least because they are too short to build up a dictionary.

  • Compression has a price: per-connection memory for the compression context, and a length oracle if secrets and attacker-controlled text share a context (a CRIME or BREACH style attack). See Security.

  • Size budget. Treat bytes as a budget per feature, not a general goal. Chatterbox: 16 KiB per client frame is generous (a 4000-character message in JSON is about 4.2 KB with its envelope) and keeps one slow message from monopolising the connection; typing and receipts must stay under 150 bytes because they are frequent; one history page should stay under 100 KiB so it parses in one frame budget. Pixel Arena: 20 snapshots per second to 8 players means any per-snapshot overhead is multiplied 160 times per second, which is why its snapshots are hand-packed (see Latency Compensation).

function ulidBytes(id: string): Uint8Array {
  const body = id.replace(/^s_/, "");
  let n = 0n;
  for (const ch of body) n = (n << 5n) | BigInt(CROCKFORD.indexOf(ch));
  const out = new Uint8Array(16);
  for (let i = 15; i >= 0; i--) { out[i] = Number(n & 0xffn); n >>= 8n; }
  return out;
}

Which to pick. Use JSON for control-plane traffic such as Chatterbox, and for anything a human will ever need to read. Switch to MessagePack when profiling shows JSON parsing or bandwidth on mobile as a real cost and you want no schema tooling. Choose Protocol Buffers when many languages share the contract and you want generated types and enforced evolution rules. Hand-pack only the hot data path, as a game does, and keep the control plane in JSON on the same socket (a text frame for the envelope, a binary frame for state). Optional: an edit could be expressed as a JSON Merge Patch (RFC 7396) of the message object, which is compact for large documents, but for a chat message replacing the whole text is simpler, and merge patch cannot express "set to null" distinctly from "remove".

Schema validation on both ends

The WebSocket gives you bytes from a stranger. JSON.parse returns any, so TypeScript types alone prove nothing at the boundary: a cast tells the compiler to stop checking, and the first malformed frame surfaces as an exception deep inside a handler. Validate at the edge, once, and let the rest of the code trust the types.

Server side (hostile input). Parse inside try, check v, validate the envelope and the payload for the declared type, and answer a failure with bad_request carrying the ref when it can be recovered. Reject, do not repair. Unknown fields are ignored (and stripped, so they cannot leak into your storage), strings and arrays have maximum lengths, numbers are integers within a range, and ids and rooms are matched against a regular expression with no nested quantifiers. A size check before JSON.parse stops memory exhaustion: the 16384-byte limit is applied on the raw text first.

Client side (a server you do not fully control). The same schemas, run over every inbound frame. A server bug, a proxy that mangles a frame, an old cached client talking to a new server, or a compromised server must not be able to inject a value that the UI then trusts. The reference server also validates its own outbound frames in sendRaw(), so a server bug throws in tests rather than reaching a client.

Zod 4 expresses the protocol as data: one object schema per type, a discriminated union on type so a failure points at one branch, and z.infer giving the TypeScript types for free. Two notes: z.int() rejects fractions and unsafe integers, and z.toJSONSchema() exports the same schema as JSON Schema (draft 2020-12) so that non-TypeScript clients and tools such as Ajv can enforce the contract. The conversion cannot express JavaScript refinements, such as the grapheme-count check on emoji, so the JSON Schema is the looser of the two: keep Zod authoritative where it exists, and use the JSON Schema to generate documentation, client validators in other languages and API tooling.

/** Parse one inbound text frame. Never throws: callers answer failures with a bad_request error. */
export function parseClientFrame(text: string):
  | { ok: true; frame: ClientFrameT }
  | { ok: false; code: "bad_request" | "unsupported_version"; message: string; ref: string | null } {
  let raw: unknown;
  try {
    raw = JSON.parse(text);
  } catch {
    return { ok: false, code: "bad_request", message: "frame is not valid JSON", ref: null };
  }
  const obj = typeof raw === "object" && raw !== null ? (raw as Record<string, unknown>) : {};
  const ref = typeof obj.id === "string" && ClientId.safeParse(obj.id).success ? obj.id : null;
  if (obj.v !== PROTOCOL_VERSION) {
    return { ok: false, code: "unsupported_version", message: `unsupported protocol version ${String(obj.v)}`, ref };
  }
  const parsed = ClientFrame.safeParse(raw);
  if (!parsed.success) {
    const issue = parsed.error.issues[0];
    return { ok: false, code: "bad_request", message: `${issue.path.join(".") || "frame"}: ${issue.message}`, ref };
  }
  return { ok: true, frame: parsed.data };
}

console.log(`\nGenerated JSON Schema: ${(clientSchema.oneOf ?? clientSchema.anyOf)?.length} client variants, ${(serverSchema.oneOf ?? serverSchema.anyOf)?.length} server variants`);

import { randomBytes } from "node:crypto";

const CROCKFORD = "0123456789ABCDEFGHJKMNPQRSTVWXYZ";

/** 26-character ULID: 48-bit millisecond timestamp followed by 80 random bits. */
export function ulid(now: number = Date.now()): string {
  let time = "";
  let t = now;
  for (let i = 0; i < 10; i++) {
    time = CROCKFORD[t % 32] + time;
    t = Math.floor(t / 32);
  }
  const rnd = randomBytes(10);
  let bits = 0n;
  for (const byte of rnd) bits = (bits << 8n) | BigInt(byte);
  let tail = "";
  for (let i = 0; i < 16; i++) {
    tail = CROCKFORD[Number(bits & 31n)] + tail;
    bits >>= 5n;
  }
  return time + tail;
}

export const clientId = (): string => ulid();

const ack24h = 24 * 60 * 60 * 1000;

export function startServer(opts: Options = {}) {
  const o = {
    port: 18080,
    allowedOrigins: ["https://chat.example.test"],
    heartbeatMs: 20000,
    helloTimeoutMs: 5000,
    presenceGraceMs: 15000,
    sessionKeepMs: 120000,
    maxOutboundBytes: 262144,
    ...opts,
  };
  const tickets = new Map<string, { userId: string; expires: number }>(); // one-time tickets
  const users = new Map<string, Member>(); // userId -> identity
  const sessions = new Map<string, Session>(); // sessionId -> session
  const byUser = new Map<string, Session>(); // userId -> live or detached session
  const rooms = new Map<string, Room>();
  const conns = new Set<Conn>();

  // ------------------------------------------------------------ http: login stand-in and upgrade
  const http: Server = createServer((req, res) => {
    const url = new URL(req.url ?? "/", "http://localhost");
    if (req.method === "POST" && url.pathname === "/ticket") {
      // Stand-in for "the login system": a real server mints this behind the session cookie.
      const userId = (url.searchParams.get("user") ?? "").toLowerCase();
      if (!/^[a-z0-9]{1,32}$/.test(userId)) { res.writeHead(400).end(); return; }
      res.writeHead(200, { "content-type": "application/json" }).end(JSON.stringify({ ticket: issueTicket(userId) }));
      return;
    }
    res.writeHead(404).end();
  });
  const wss = new WebSocketServer({
    noServer: true,
    maxPayload: 65536, // transport guard; the 16384-byte protocol limit is enforced below with close code 4413
    handleProtocols: (protocols) => (protocols.has(SUBPROTOCOL) ? SUBPROTOCOL : false),
  });
  http.on("upgrade", (req: IncomingMessage, socket, head) => {
    const origin = req.headers.origin; // browsers always send it; non-browser clients may omit it
    if (origin !== undefined && !o.allowedOrigins.includes(origin)) {
      socket.write("HTTP/1.1 403 Forbidden\r\nConnection: close\r\n\r\n");
      socket.destroy();
      return;
    }
    wss.handleUpgrade(req, socket, head, (ws) => onConnection(ws));
  });

  function issueTicket(userId: string): string {
    const t = `tk_${ulid()}`;
    tickets.set(t, { userId, expires: Date.now() + 30000 });
    return t;
  }

  // ------------------------------------------------------------ sending
  const sendRaw = (ws: WebSocket, env: Envelope): void => {
    const check = ServerFrame.safeParse(env); // validate outbound too: a server bug must not reach the wire
    if (!check.success) throw new Error(`invalid outbound frame: ${check.error.issues[0].message}`);
    if (ws.readyState === WebSocket.OPEN) ws.send(JSON.stringify(env));
  };
  const envelope = (type: string, room: string | null, payload: Envelope, id = serverId()): Envelope =>
    ({ v: PROTOCOL_VERSION, type, id, room, ts: Date.now(), payload });
  const sendToSession = (s: Session, env: Envelope): void => s.conns.forEach((c) => sendRaw(c.ws, env));
  const sendError = (c: Conn, ref: string | null, code: ErrorCode, message: string, room: string | null = null): void =>
    sendRaw(c.ws, envelope("error", room, { ref, code, message, retryable: ERROR_CODES[code].retryable }));
  const closeWith = (c: Conn, code: number, reason: string): void => {
    c.ws.close(code, reason);
    setTimeout(() => c.ws.terminate(), 1000).unref(); // do not wait for a dead peer to answer the close frame
  };
  const broadcast = (room: Room, env: Envelope, except?: string): void => {
    for (const userId of room.members) {
      if (userId === except) continue;
      const s = byUser.get(userId);
      if (s) sendToSession(s, env);
    }
  };
  const roomOf = (name: string): Room => {
    let r = rooms.get(name);
    if (!r) rooms.set(name, (r = { name, seq: 0, members: new Set(), log: [], messages: new Map(), reactions: new Map() }));
    return r;
  };
  const who = (userId: string): Member => users.get(userId)!;

  // ------------------------------------------------------------ connection lifecycle
  function onConnection(ws: WebSocket): void {
    const c: Conn = { ws, session: null, lastSeen: Date.now(), tokens: 40, refilledAt: Date.now(), limited: [] };
    conns.add(c);
    c.helloTimer = setTimeout(() => { if (!c.session) closeWith(c, 4408, "hello timeout"); }, o.helloTimeoutMs);
    ws.on("pong", () => { c.lastSeen = Date.now(); });
    ws.on("message", (data, isBinary) => {
      c.lastSeen = Date.now();
      if (isBinary) return closeWith(c, 4400, "binary frames are not part of chatterbox.v1");
      const text = data.toString("utf8");
      if (Buffer.byteLength(text) > MAX_FRAME_BYTES) {
        sendError(c, null, "too_large", `frames are limited to ${MAX_FRAME_BYTES} bytes`);
        return closeWith(c, 4413, "frame too large");
      }
      onFrame(c, text);
    });
    ws.on("close", () => onClose(c));
    ws.on("error", () => {});
  }

  function onClose(c: Conn): void {
    conns.delete(c);
    clearTimeout(c.helloTimer);
    const s = c.session;
    if (!s) return;
    s.conns.delete(c);
    if (s.conns.size > 0) return;
    s.detachedAt = Date.now();
    // After the grace period without a reconnect the user becomes offline for everyone in their rooms.
    s.offlineTimer = setTimeout(() => { if (s.conns.size === 0) setStatus(s, "offline"); }, o.presenceGraceMs);
    setTimeout(() => {
      if (s.conns.size === 0 && s.detachedAt && Date.now() - s.detachedAt >= o.sessionKeepMs) {
        sessions.delete(s.id);
        if (byUser.get(s.userId) === s) byUser.delete(s.userId);
      }
    }, o.sessionKeepMs + 50).unref();
  }

  function setStatus(s: Session, status: Session["status"]): void {
    if (s.status === status) return;
    s.status = status;
    for (const name of s.rooms) {
      const r = rooms.get(name)!;
      broadcast(r, envelope("presence", name, { userId: s.userId, name: who(s.userId).name, status }), s.userId);
    }
  }

  // ------------------------------------------------------------ rate limit: 20 envelopes/s, burst 40
  function allow(c: Conn): boolean {
    const now = Date.now();
    c.tokens = Math.min(40, c.tokens + ((now - c.refilledAt) / 1000) * 20);
    c.refilledAt = now;
    if (c.tokens >= 1) { c.tokens -= 1; return true; }
    c.limited = c.limited.filter((t) => now - t < 10000).concat(now);
    return false;
  }

  // ------------------------------------------------------------ frame dispatch
  function onFrame(c: Conn, text: string): void {
    if (!allow(c)) {
      sendError(c, null, "rate_limited", "slow down: 20 envelopes per second, burst 40");
      if (c.limited.length >= 10) closeWith(c, 4429, "rate limited");
      return;
    }
    const parsed = parseClientFrame(text);
    if (!parsed.ok) {
      sendError(c, parsed.ref, parsed.code, parsed.message);
      if (parsed.code === "unsupported_version") closeWith(c, 4426, "unsupported version");
      return;
    }
    const f = parsed.frame;
    if (f.type === "hello") return onHello(c, f);
    const s = c.session;
    if (!s) {
      sendError(c, f.id, "unauthorized", "send hello first");
      return closeWith(c, 4401, "hello required");
    }
    // Idempotency: a repeated id gets the ORIGINAL ack again, with dup:true, and has no other effect.
    const prior = s.acks.get(f.id);
    if (prior) {
      sendRaw(c.ws, envelope("ack", prior.room, { ...prior.payload, dup: true }));
      return;
    }
    try {
      handlers[f.type](c, s, f as never);
    } catch (e) {
      console.error(e);
      sendError(c, f.id, "internal", "unexpected server error", f.room);
    }
  }

  function reply(c: Conn, s: Session, f: ClientFrameT, seq: number | null, result: Envelope = {}): void {
    const payload = { ref: f.id, ok: true, seq, dup: false, result };
    s.acks.set(f.id, { payload, room: f.room, at: Date.now() });
    if (s.acks.size > 1000) { // keep at least the last 1000 ids, drop anything older than 24 hours
      for (const [id, a] of s.acks) { if (s.acks.size <= 1000 || Date.now() - a.at < ack24h) break; s.acks.delete(id); }
    }
    sendRaw(c.ws, envelope("ack", f.room, payload));
  }

  function onHello(c: Conn, f: Extract<ClientFrameT, { type: "hello" }>): void {
    if (c.session) return sendError(c, f.id, "conflict", "hello already completed");
    const token = f.payload.token ?? ""; // this reference server accepts tickets only, not cookies
    const ticket = tickets.get(token);
    tickets.delete(token); // one-time
    if (!ticket || ticket.expires < Date.now()) {
      sendError(c, f.id, "unauthorized", "invalid or expired ticket");
      return closeWith(c, 4401, "unauthorized");
    }
    clearTimeout(c.helloTimer);
    const userId = ticket.userId;
    users.set(userId, { userId, name: userId[0].toUpperCase() + userId.slice(1) });
    const resume = f.payload.resume;
    let session = resume && sessions.get(resume.sessionId);
    let resumed = false;
    if (session && session.userId === userId && Date.now() - (session.detachedAt ?? Date.now()) < o.sessionKeepMs) {
      resumed = true;
      clearTimeout(session.offlineTimer);
      session.detachedAt = null;
    } else {
      session = { id: `sess_${ulid()}`, userId, rooms: new Set(), status: "online", conns: new Set(), detachedAt: null, acks: new Map() };
      sessions.set(session.id, session);
      byUser.set(userId, session);
    }
    session.conns.add(c);
    c.session = session;
    sendRaw(c.ws, envelope("hello", null, {
      ref: f.id, userId, name: who(userId).name, sessionId: session.id, heartbeatMs: o.heartbeatMs,
      maxFrameBytes: MAX_FRAME_BYTES, resumed, rooms: [...session.rooms],
    }));
    if (resumed) {
      for (const [name, last] of Object.entries(resume!.rooms)) if (session.rooms.has(name)) replay(c, rooms.get(name)!, last);
      setStatus(session, "online");
    }
  }

  const replay = (c: Conn, room: Room, after: number): void => {
    for (const env of room.log) if (env.payload.seq > after) sendRaw(c.ws, env);
  };

  // ------------------------------------------------------------ per-type handlers
  type H<T extends ClientFrameT["type"]> = (c: Conn, s: Session, f: Extract<ClientFrameT, { type: T }>) => void;
  const member = (c: Conn, s: Session, f: ClientFrameT): Room | null => {
    const r = f.room ? rooms.get(f.room) : undefined;
    if (!r || !r.members.has(s.userId)) { sendError(c, f.id, "forbidden", "join the room first", f.room); return null; }
    return r;
  };
  const dmAllowed = (room: string, userId: string): boolean => !room.startsWith("dm-") || room.split("-").slice(1).includes(userId);

  const handlers: { [K in ClientFrameT["type"]]: H<K> } = {
    hello: () => {},
    join(c, s, f) {
      if (!dmAllowed(f.room, s.userId)) return sendError(c, f.id, "forbidden", "not your direct-message room", f.room);
      const r = roomOf(f.room);
      const wasMember = r.members.has(s.userId);
      r.members.add(s.userId);
      s.rooms.add(r.name);
      const members = [...r.members].map((id) => ({ userId: id, name: who(id).name, status: byUser.get(id)?.status ?? "offline" }));
      reply(c, s, f, null, { members, lastSeq: r.seq });
      if (f.payload.since !== null) replay(c, r, f.payload.since);
      if (!wasMember) broadcast(r, envelope("presence", r.name, { userId: s.userId, name: who(s.userId).name, status: s.status }), s.userId);
    },
    leave(c, s, f) {
      const r = rooms.get(f.room);
      if (!r || !r.members.delete(s.userId)) return sendError(c, f.id, "not_found", "not a member of that room", f.room);
      s.rooms.delete(r.name);
      reply(c, s, f, null);
    },
    message(c, s, f) {
      const r = member(c, s, f); if (!r) return;
      const { text, replyTo, attachments } = f.payload;
      if (replyTo && !r.messages.has(replyTo)) return sendError(c, f.id, "not_found", "replyTo does not exist in this room", r.name);
      if (r.messages.has(f.id)) return sendError(c, f.id, "conflict", "message id already used", r.name);
      const seq = ++r.seq;
      const env = envelope("message", r.name, {
        from: { userId: s.userId, name: who(s.userId).name }, text, replyTo, attachments, seq, edited: false,
      }, f.id); // the message id IS the client's envelope id
      r.messages.set(f.id, env);
      r.log.push(env);
      reply(c, s, f, seq);
      broadcast(r, env);
    },
    edit(c, s, f) {
      const r = member(c, s, f); if (!r) return;
      const target = r.messages.get(f.payload.target);
      if (!target) return sendError(c, f.id, "not_found", "no such message", r.name);
      if (target.payload.from.userId !== s.userId) return sendError(c, f.id, "forbidden", "only the author can edit a message", r.name);
      const seq = ++r.seq;
      const editedAt = Date.now();
      target.payload.text = f.payload.text;
      target.payload.edited = true;
      const env = envelope("edit", r.name, { target: f.payload.target, text: f.payload.text, seq, editedAt });
      r.log.push(env);
      reply(c, s, f, seq);
      broadcast(r, env);
    },
    react(c, s, f) {
      const r = member(c, s, f); if (!r) return;
      const { target, emoji, op } = f.payload;
      if (!r.messages.has(target)) return sendError(c, f.id, "not_found", "no such message", r.name);
      const set = r.reactions.get(target) ?? new Set<string>();
      const key = `${s.userId}|${emoji}`;
      if (op === "add" && set.has(key)) return sendError(c, f.id, "conflict", "reaction already added", r.name);
      if (op === "remove" && !set.has(key)) return sendError(c, f.id, "not_found", "reaction not present", r.name);
      op === "add" ? set.add(key) : set.delete(key);
      r.reactions.set(target, set);
      const seq = ++r.seq;
      const env = envelope("react", r.name, { target, emoji, op, from: { userId: s.userId }, seq });
      r.log.push(env);
      reply(c, s, f, seq);
      broadcast(r, env);
    },
    typing(c, s, f) { // fire-and-forget: no ack, only an error when the sender is not a member
      const r = member(c, s, f); if (!r) return;
      broadcast(r, envelope("typing", r.name, { userId: s.userId, state: f.payload.state }), s.userId);
    },
    receipt(c, s, f) { // fire-and-forget and cumulative
      const r = member(c, s, f); if (!r) return;
      if (f.payload.upTo > r.seq) return sendError(c, f.id, "bad_request", "upTo is beyond the last seq", r.name);
      broadcast(r, envelope("receipt", r.name, { userId: s.userId, kind: f.payload.kind, upTo: f.payload.upTo }), s.userId);
    },
    presence(c, s, f) { // doubles as the application heartbeat; the ack lets the client measure RTT
      reply(c, s, f, null);
      setStatus(s, f.payload.status);
    },
    history(c, s, f) {
      const r = member(c, s, f); if (!r) return;
      const { before, limit } = f.payload;
      const all = [...r.messages.values()].filter((m) => before === null || m.payload.seq < before);
      let page = all.slice(-limit);
      const size = (p: Envelope[]) => Buffer.byteLength(JSON.stringify(p));
      while (page.length > 1 && size(page) > o.maxOutboundBytes - 1024) page = page.slice(1); // keep the newest messages that fit
      const hasMore = page.length < all.length;
      reply(c, s, f, null, { messages: page, hasMore, next: hasMore ? page[0].payload.seq : null });
    },
  };

  // ------------------------------------------------------------ heartbeat: ping every heartbeatMs, close after 2x silence
  const timer = setInterval(() => {
    const now = Date.now();
    for (const c of conns) {
      if (now - c.lastSeen > 2 * o.heartbeatMs) { closeWith(c, 4408, "heartbeat timeout"); continue; }
      if (c.ws.readyState === WebSocket.OPEN) c.ws.ping();
    }
  }, Math.max(10, o.heartbeatMs / 2));
  timer.unref();

  return new Promise<{ port: number; issueTicket: typeof issueTicket; close: (code?: number) => Promise<void> }>((resolve) => {
    http.listen(o.port, "127.0.0.1", () => {
      const port = (http.address() as { port: number }).port;
      resolve({
        port,
        issueTicket,
        close: (code = 4503) => new Promise((done) => {
          clearInterval(timer);
          for (const c of conns) c.ws.close(code, "server restarting");
          setTimeout(() => { for (const c of conns) c.ws.terminate(); http.close(() => done()); http.closeAllConnections(); }, 100);
        }),
      });
    });
  });
}

Points worth noticing in the listing:

  • The Origin check happens in the upgrade handler, before handleUpgrade. Browsers apply no same-origin policy to WebSocket handshakes and attach cookies, so a page on any site can open a socket to your server as the logged-in user (Cross-Site WebSocket Hijacking) unless the server compares Origin with an allow-list. Requests without an Origin (not a browser) are admitted here because they must still present a one-time ticket in hello.

  • Authentication is in the first frame, not the URL. The browser WebSocket constructor cannot set headers. A one-time ticket in the first message never lands in access logs or Referer headers the way a query-string token does, expires in 30 seconds and cannot be replayed; the 5-second hello deadline keeps unauthenticated sockets cheap.

  • reply() is the idempotency table, and the early return at the top of onFrame() is the deduplication.

  • sendRaw() validates outbound frames with the same Zod schema the client uses.

  • closeWith() terminates after 1 second, because a peer that never answers the close frame would otherwise hold the socket for the library’s close timeout.

The client and the scenario script

The client class below validates inbound frames, correlates acks with promises, keeps unacknowledged envelopes in order, resends them with the same ids after a reconnect, and resumes with lastSeq per room. It uses the global WebSocket of Node 22 and later, which is the same API a browser has, so the class runs in a page unchanged apart from the ticket fetch. The scenario at the bottom exercises everything and prints PASS or FAIL for 21 checks, including the duplicate-id retry three ways.

import { fileURLToPath } from "node:url";
import { ServerFrame, SUBPROTOCOL, type ServerFrameT } from "./chatterbox-schema.ts";
import { clientId } from "./ids.ts";

type Listener = (frame: ServerFrameT) => void;
interface Pending { frame: Record<string, unknown>; resolve: (f: ServerFrameT) => void; timer?: ReturnType<typeof setTimeout> }

/** Minimal Chatterbox client: validates every inbound frame, correlates acks and retries with the same id. */
export class ChatterboxClient {
  ws: WebSocket | null = null;
  sessionId: string | null = null;
  lastSeq: Record<string, number> = {};
  readonly pending = new Map<string, Pending>(); // insertion order = original send order
  readonly sent = new Map<string, Record<string, unknown>>(); // every request frame, kept so tests can replay it
  readonly seen: ServerFrameT[] = [];
  private listeners = new Set<Listener>();
  private base: string;
  private userId: string;
  private ackTimeoutMs: number;
  constructor(base: string, userId: string, ackTimeoutMs = 10000) {
    this.base = base;
    this.userId = userId;
    this.ackTimeoutMs = ackTimeoutMs;
  }

  on(l: Listener): () => void { this.listeners.add(l); return () => this.listeners.delete(l); }
  waitFor(pred: (f: ServerFrameT) => boolean, ms = 3000): Promise<ServerFrameT> {
    return new Promise((resolve, reject) => {
      const t = setTimeout(() => { off(); reject(new Error("waitFor timed out")); }, ms);
      const off = this.on((f) => { if (pred(f)) { clearTimeout(t); off(); resolve(f); } });
    });
  }

  async connect(): Promise<ServerFrameT & { type: "hello" }> {
    const res = await fetch(`http://${this.base}/ticket?user=${this.userId}`, { method: "POST" });
    const { ticket } = (await res.json()) as { ticket: string };
    const ws = new WebSocket(`ws://${this.base}/`, SUBPROTOCOL); // browser-compatible global client, Node >= 22
    this.ws = ws;
    ws.onmessage = (ev) => this.onMessage(String(ev.data));
    await new Promise<void>((ok, bad) => { ws.onopen = () => ok(); ws.onerror = () => bad(new Error("connect failed")); });
    const resume = this.sessionId ? { sessionId: this.sessionId, rooms: this.lastSeq } : undefined;
    const hello = this.waitFor((f) => f.type === "hello");
    this.write({ v: 1, type: "hello", id: clientId(), room: null, ts: 0, payload: { token: ticket, client: "node/1.0", ...(resume && { resume }) } });
    const h = (await hello) as ServerFrameT & { type: "hello" };
    this.sessionId = h.payload.sessionId;
    for (const p of this.pending.values()) this.write(p.frame); // retry unacked envelopes, same ids, original order
    return h;
  }

  /** Send an envelope that expects an ack or an error and resolve with whichever arrives. */
  request(type: string, room: string | null, payload: Record<string, unknown>, id = clientId()): Promise<ServerFrameT> {
    const frame = { v: 1, type, id, room, ts: 0, payload };
    this.sent.set(id, frame);
    return new Promise((resolve) => {
      const p: Pending = { frame, resolve };
      this.pending.set(id, p);
      p.timer = setTimeout(() => { if (this.ws?.readyState === WebSocket.OPEN) this.write(frame); }, this.ackTimeoutMs);
      if (this.ws?.readyState === WebSocket.OPEN) this.write(frame);
    });
  }
  /** Fire-and-forget envelopes (typing, receipt). */
  notify(type: string, room: string, payload: Record<string, unknown>): void {
    this.write({ v: 1, type, id: clientId(), room, ts: 0, payload });
  }
  /** Re-send a frame that was already sent, byte for byte, as a lost-ack retry would. */
  resend(id: string): void { this.write(this.sent.get(id)!); }

  private write(frame: Record<string, unknown>): void { this.ws?.send(JSON.stringify(frame)); }

  private onMessage(text: string): void {
    const parsed = ServerFrame.safeParse(JSON.parse(text));
    if (!parsed.success) { console.error("dropping invalid server frame:", parsed.error.issues[0]); return; }
    const f = parsed.data;
    this.seen.push(f);
    if (f.type === "message" || f.type === "edit" || f.type === "react") {
      this.lastSeq[f.room] = Math.max(this.lastSeq[f.room] ?? 0, f.payload.seq);
    }
    if (f.type === "ack" || f.type === "error") {
      const ref = f.payload.ref;
      const p = ref && this.pending.get(ref);
      if (p && (f.type === "ack" || !f.payload.retryable)) {
        clearTimeout(p.timer);
        this.pending.delete(ref);
        p.resolve(f);
      }
    }
    this.listeners.forEach((l) => l(f));
  }

  close(): void { this.ws?.close(1000, "bye"); }
  drop(): void { this.ws?.close(1000, "simulated network loss"); }
}

Security considerations

  • Treat every frame as hostile input. Check the byte length before parsing, validate the envelope and payload with a schema, and cap strings, arrays, and depth. Deeply nested JSON and huge arrays are cheap to send and costly to parse. JSON.parse itself is safe with a __proto__ key (it creates an ordinary own property), but merging parsed objects into others with a recursive merge helper can pollute prototypes: copy only the fields the schema returned.

  • Authorise on every frame, not once at connect. Membership, message authorship and DM ownership are checked per request (see member() and dmAllowed()), because permissions change while sockets stay open (see Authentication and Authorization).

  • Never trust from, userId or ts sent by a client. The server derives identity from the session and stamps time itself; the broadcast from comes from the session, never from the payload.

  • Escape on render. text is user content. Insert it with textContent, never innerHTML, and never interpolate it into markup, a URL or a log line without encoding. Attachments are https URLs only, validated by the schema, and should be loaded from a separate origin with a content-security policy.

  • Limit everything that scales with the attacker: frame size, frame rate, rooms per user, members per room, history page size, pending resend queue. The protocol advertises the first three so the client can behave.

  • Do not log payloads or tickets. Log type, id, room, size and outcome. Tickets in the first frame stay out of access logs, which is their point.

  • Idempotency tables are state an attacker can fill. Bound them per user (this server keeps the last 1000 ids at least) and expire them.

  • Compression and secrets. If you enable permessage-deflate, do not put secrets in frames that also contain attacker text; see Security.

Common errors and pitfalls

  • Regenerating the id on retry. The retry then creates a second message. Generate the id once, store it with the queued envelope.

  • Treating the ack as delivery. It means "stored". A user who sees a double tick because of an ack is misled.

  • Assuming ack and broadcast arrive in a fixed order. The sender may see its own broadcast before the ack. Match by id.

  • Ordering by ts or arrival time. Use seq.

  • Using an unbounded seq in a 32-bit field. The hand-packed layout above holds 4.29 billion messages per room; a busy public room can exceed that. Choose the width on purpose.

  • JSON.stringify surprises. undefined fields vanish, NaN and Infinity become null, Date becomes an ISO string, BigInt throws, and a Map becomes {}. Build frames from plain objects and validate them before sending too.

  • Large integers as numbers. Ids above 2^53 corrupt silently in JavaScript. Send them as strings.

  • Mixed text and binary without a plan. Decide per connection, and set binaryType to arraybuffer in browsers.

  • Message and field names that leak the implementation. postgres_row_id in a payload is a protocol you cannot change.

  • Errors without ref. A client that cannot correlate a failure to a request can only guess; always include the id when it could be parsed.

  • Ignoring retryable. Retrying a forbidden forever, or never retrying a rate_limited.

  • Replaying a mutation on a new connection without the same id. The most common cause of double-posted messages after a flaky mobile network.

  • One giant union with no discriminator. Validation errors then list every branch and are useless.

  • Forgetting the other direction. Servers validate clients, but clients must validate servers too; the second is where version skew shows up first.

Version and specification notes

  • JSON is specified by RFC 8259 (December 2017, Internet Standard 90), which obsoletes RFC 7159 and requires UTF-8 for JSON exchanged between systems. RFC 7493 (the I-JSON profile) adds the interoperability rules this page leans on: unique member names, numbers that fit an IEEE double, and strings for anything larger. RFC 7396 (JSON Merge Patch) is the optional alternative to full-replacement edits.

  • UUIDv7 is time-ordered and was standardised in RFC 9562 (May 2024), which obsoletes RFC 4122. ULID is a community specification with the same time-ordered idea in a 26-character Crockford base32 string.

  • MessagePack is a community specification (versioned by its spec document, with the timestamp extension type defined in it); @msgpack/msgpack 3.1.3 is the current JavaScript implementation.

  • Protocol Buffers: proto3 is the schema syntax used here; the encoding rules (varints, tags, wire types) are stable and documented separately, and the field-number reuse rule is the one rule that cannot be broken.

  • Zod 4 (2025) added the built-in z.toJSONSchema() and the top-level z.int() and z.url() forms that this page uses; Zod 3 code uses z.number().int() and z.string().url().

  • Node.js: native TypeScript type stripping is on by default in Node 24 (and 22.18 and later); the global WebSocket client is stable since 22.4.0; there is still no built-in server, so servers use ws or another library.

  • The Chatterbox protocol itself is versioned by v and the chatterbox.v1 subprotocol; this page is its single definition, and the stack pages must not change its semantics.
