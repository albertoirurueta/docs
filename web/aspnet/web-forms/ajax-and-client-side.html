AJAX and Client-Side Integration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Web Forms predates the modern fetch/JSON client-side world, and its own "ASP.NET AJAX" layer (UpdatePanel and friends) is best understood as partial-page postback dressed up to look asynchronous — genuinely useful for retrofitting existing postback-based pages, but not a substitute for a real client-side JSON API when building something new.

ScriptManager and ScriptManagerProxy

Exactly one ScriptManager per page (or per content page via master page) is required for any AJAX functionality below to work; nested content pages that need to register additional scripts use ScriptManagerProxy instead of a second ScriptManager:

<%-- Site.master --%>
<asp:ScriptManager ID="ScriptManager1" runat="server" EnablePartialRendering="true" />
<%-- Default.aspx, which uses Site.master --%>
<asp:ScriptManagerProxy ID="ScriptManagerProxy1" runat="server">
    <Scripts>
        <asp:ScriptReference Path="~/Scripts/page-specific.js" />
    </Scripts>
</asp:ScriptManagerProxy>

UpdatePanel, UpdateProgress, and Timer

UpdatePanel wraps a region of a page so that a postback originating inside it (or targeted at it via a Trigger) refreshes only that region’s HTML, without a full-page navigation:

<asp:UpdatePanel ID="ResultsPanel" runat="server">
    <ContentTemplate>
        <asp:Label ID="ResultsLabel" runat="server" />
        <asp:Button ID="RefreshButton" runat="server" Text="Refresh" OnClick="RefreshButton_Click" />
    </ContentTemplate>
</asp:UpdatePanel>

<asp:UpdateProgress ID="Progress1" runat="server" AssociatedUpdatePanelID="ResultsPanel">
    <ProgressTemplate><span>Loading...</span></ProgressTemplate>
</asp:UpdateProgress>

<asp:Timer ID="AutoRefreshTimer" runat="server" Interval="30000" OnTick="AutoRefreshTimer_Tick" />

UpdateProgress shows/hides its template automatically around an in-flight async postback for the panel it is associated with; Timer raises a periodic async postback (OnTick) without any user action, commonly paired with an UpdatePanel for polling-style auto-refresh.

UpdateMode/Triggers and the real cost of partial rendering

By default (UpdateMode="Always") an UpdatePanel refreshes on any postback anywhere on the page, not just ones that originated inside it — often not what is wanted, and a common source of unnecessary re-render work. UpdateMode="Conditional" combined with explicit <Triggers> scopes updates to specific controls/events:

<asp:UpdatePanel ID="ResultsPanel" runat="server" UpdateMode="Conditional">
    <ContentTemplate>...</ContentTemplate>
    <Triggers>
        <asp:AsyncPostBackTrigger ControlID="SearchButton" EventName="Click" />
        <asp:PostBackTrigger ControlID="ExportButton" /> <%-- forces a FULL postback, e.g. for a file download --%>
    </Triggers>
</asp:UpdatePanel>

The critical point Esposito’s Programming Microsoft ASP.NET 4 makes explicit and that is easy to miss: an UpdatePanel postback is not a lightweight AJAX call. The entire page life cycle still runs server-side — full ViewState load/save, every control’s Load/PreRender, the works — only the response is trimmed down to the changed panel(s)' HTML (via a client-side script that patches the DOM) instead of a full-page document. UpdatePanel reduces bandwidth and avoids a visible full-page reload; it does essentially nothing for server-side CPU cost per request.

The ASP.NET AJAX client library and the AJAX Control Toolkit (historic)

Sys.*/Sys.Net.* (the MicrosoftAjax.js/MicrosoftAjaxWebForms.js scripts ScriptManager injects automatically) is the original client-side runtime UpdatePanel and the unobtrusive validators depend on. The AJAX Control Toolkit was a large community/Microsoft-maintained library of additional UpdatePanel-style controls (CalendarExtender, AutoCompleteExtender, ModalPopupExtender, …​) built on top of it — still functional (community-maintained on GitHub) but effectively historic; no new project should adopt it, and an existing dependency on it is a signal that any client-side interactivity work is better done with plain JavaScript/jQuery against a JSON endpoint instead of another extender.

Page methods and script services

Page methods are static methods on a page’s code-behind, marked [WebMethod], callable directly from client script via a generated proxy, without the overhead of a full postback or UpdatePanel:

public partial class Search : System.Web.UI.Page
{
    [System.Web.Services.WebMethod]
    public static List<string> FindMatches(string query)
    {
        return _searchService.Find(query); // static: no access to Page/Session/ViewState
    }
}
PageMethods.FindMatches(document.getElementById('QueryBox').value, function (results) {
    // onSuccess callback; results is the JSON-deserialized List<string>
    renderResults(results);
});

Page methods must be static (no implicit Page/control access) and require <asp:ScriptManager EnablePageMethods="true">. A script service is the same idea generalized to a standalone .asmx (below) marked [ScriptService], callable from any page that references it via ScriptManager, rather than being tied to one specific page.

ASMX web services and WCF from script

.asmx ASMX web services are the original SOAP/XML web-service technology from ASP.NET 1.x, still functional under Web Forms and callable from client script when decorated [ScriptService]:

[System.Web.Services.WebService(Namespace = "http://example.com/")]
[System.Web.Script.Services.ScriptService]
public class Catalog : System.Web.Services.WebService
{
    [System.Web.Services.WebMethod]
    public Product[] GetProducts(int categoryId) => _repository.ByCategory(categoryId);
}

WCF services can also be exposed to script via System.ServiceModel.Activation.WebScriptServiceHostFactory and an .svc endpoint configured for JSON, offering roughly the same client-callable shape as a script-enabled ASMX service but built on the newer (for the Web Forms era) WCF service model. Both predate ASP.NET Web API and are the two REST/JSON-from-script options native to System.Web.

Using jQuery and plain fetch/XHR against .ashx handlers instead

For anything beyond the simplest partial-postback scenario, calling a .ashx generic handler directly with fetch or jQuery’s $.ajax sidesteps the page life cycle entirely and is both simpler to reason about and considerably cheaper server-side than an UpdatePanel:

fetch('/Handlers/Search.ashx?q=' + encodeURIComponent(query))
    .then(r => r.json())
    .then(results => renderResults(results));
// Handlers/Search.ashx.cs
public class Search : IHttpHandler
{
    public bool IsReusable => true;
    public void ProcessRequest(HttpContext context)
    {
        var results = _searchService.Find(context.Request.QueryString["q"]);
        context.Response.ContentType = "application/json";
        context.Response.Write(new JavaScriptSerializer().Serialize(results));
    }
}

This is the pattern most maintained Web Forms applications converge on for anything genuinely interactive, since it has none of the full-life-cycle cost of an UpdatePanel and none of the SOAP-era ceremony of ASMX/WCF.

ClientIDMode

Web Forms historically mangled a control’s rendered id attribute with its full naming-container path (ctl00_MainContent_SearchBox), which made writing plain CSS/JavaScript selectors against server controls awkward. ClientIDMode (4.0+) controls this:

Value Behavior

AutoID

The historic behavior — fully qualified, container-prefixed ID (ctl00_MainContent_SearchBox).

Static

The control’s own ID, unqualified (SearchBox) — the developer is responsible for avoiding collisions if the control repeats.

Predictable

Used for data-bound repeating controls; concatenates the naming container’s ID with the data item’s index/key in a predictable, shorter pattern than AutoID.

Inherit (default at the control level)

Use whatever the parent/page specifies.

 
<%@ Page ClientIDMode="Static" ... %>

Setting ClientIDMode="Static" page- or application-wide (<pages clientIDMode="Static" /> in web.config) is the common choice in any Web Forms page written to be driven by hand-authored jQuery/CSS, since it makes $('#SearchBox') reliable again.

See ASP.NET AJAX UpdatePanel Control Overview and ClientIDMode and the ASP.NET 4 Control ID Algorithm.

What an UpdatePanel request really looks like on the wire

An asynchronous postback is an ordinary form POST made with XMLHttpRequest. The ScriptManager marks it with the X-MicrosoftAjax: Delta=true header, the server runs the complete page life cycle, and the response is not HTML but a pipe-delimited list of the panels that changed plus the new ViewState and validation values. The client script splices each panel’s HTML into the DOM:

sequenceDiagram participant B as Browser (PageRequestManager) participant S as ScriptManager (server) participant P as Page life cycle B->>S: POST same URL, header X-MicrosoftAjax = Delta=true, full form incl. __VIEWSTATE S->>P: PreInit .. Load .. events .. PreRender P->>P: UpdatePanels that need refreshing render their HTML P-->>S: rendered panels S-->>B: text/plain delta: length|type|id|content| entries (updatePanel, hiddenField, ...) B->>B: replace the panels' innerHTML, update hidden fields B->>B: raise endRequest

Because the panel’s DOM nodes are replaced, anything attached to them from script is lost after each refresh: event handlers bound with jQuery to a button inside the panel, a date-picker widget on a textbox, a focused field. The client library therefore exposes events for re-attaching them, and a server-side registration API that works inside partial updates.

Worked example: a search box with an UpdatePanel, and its hardening

The order desk needs a product search that refreshes only the result list. The markup uses a conditional panel with an explicit trigger, a progress indicator, and a client-side hook for status and errors:

<asp:ScriptManager ID="ScriptManager1" runat="server"
    OnAsyncPostBackError="ScriptManager1_AsyncPostBackError" AsyncPostBackTimeout="30" />

<asp:TextBox ID="SearchBox" runat="server" />
<asp:Button ID="SearchButton" runat="server" Text="Search" OnClick="SearchButton_Click" />
<span id="status"></span>

<asp:UpdatePanel ID="ResultsPanel" runat="server" UpdateMode="Conditional">
    <ContentTemplate>
        <asp:Repeater ID="ResultsRepeater" runat="server">
            <ItemTemplate><div><%#: Eval("Name") %> -- <%#: Eval("Price", "{0:C}") %></div></ItemTemplate>
        </asp:Repeater>
        <asp:Label ID="NoResultsLabel" runat="server" Visible="false" Text="No products match." />
    </ContentTemplate>
    <Triggers>
        <asp:AsyncPostBackTrigger ControlID="SearchButton" EventName="Click" />
    </Triggers>
</asp:UpdatePanel>

<script type="text/javascript">
    var prm = Sys.WebForms.PageRequestManager.getInstance();

    prm.add_beginRequest(function () {
        document.getElementById('status').textContent = 'Searching...';
    });

    prm.add_endRequest(function (sender, args) {
        var error = args.get_error();
        if (error) {
            document.getElementById('status').textContent = 'The search failed. Please try again.';
            args.set_errorHandled(true); // suppress the default alert() box
        } else {
            document.getElementById('status').textContent = '';
        }
    });
</script>
using System;
using System.Linq;
using System.Web.UI;
using WebFormsApp.Services;

protected void SearchButton_Click(object sender, EventArgs e)
{
    string term = SearchBox.Text.Trim();
    var matches = ProductCatalog.All()
        .Where(p => p.Name.IndexOf(term, StringComparison.OrdinalIgnoreCase) >= 0)
        .ToList();

    ResultsRepeater.DataSource = matches;
    ResultsRepeater.DataBind();
    NoResultsLabel.Visible = matches.Count == 0;

    // ClientScript.Register... is ignored in a partial update; ScriptManager is not.
    ScriptManager.RegisterStartupScript(ResultsPanel, GetType(), "focusResults",
        "document.getElementById('" + SearchBox.ClientID + "').select();", true);
}

protected void ScriptManager1_AsyncPostBackError(object sender, AsyncPostBackErrorEventArgs e)
{
    // Runs when any async postback throws; the message is what the client's endRequest sees as get_error().
    ScriptManager1.AsyncPostBackErrorMessage = "The server could not complete the request.";
}

The pieces to take from it. UpdateMode="Conditional" with one AsyncPostBackTrigger keeps unrelated postbacks on the page from re-rendering the results. ClientScript.RegisterStartupScript writes into the full-page HTML and is therefore silently skipped during a partial update, while ScriptManager.RegisterStartupScript(control, ...) adds the script to the delta, tied to the panel that is being updated. By default an unhandled server exception in an async postback shows the exception message in a JavaScript alert, which can leak internals; setting AsyncPostBackErrorMessage (and handling endRequest as above) replaces it with a generic message. Re-attaching script behavior after each refresh belongs in the same add_endRequest handler, or in a pageLoad function, which ScriptManager calls after every partial update as well as at first load.

Worked example: a JSON order endpoint called with fetch

For anything beyond refreshing a region, a plain handler returning JSON is simpler and cheaper than a panel. The following endpoint accepts an order line, validates it, and answers with a status code and JSON in every case:

// Handlers/OrderApi.ashx.cs
using System;
using System.IO;
using System.Web;
using System.Web.Script.Serialization;
using WebFormsApp.Services;

namespace WebFormsApp.Handlers
{
    public class OrderApi : IHttpHandler
    {
        public class OrderRequest
        {
            public int ProductId { get; set; }
            public int Quantity { get; set; }
        }

        public bool IsReusable { get { return true; } }

        public void ProcessRequest(HttpContext context)
        {
            if (context.Request.HttpMethod != "POST")
            {
                Fail(context, 405, "POST required.");
                return;
            }

            // A cross-site form cannot add a custom header, so this blocks forged POSTs from other origins.
            if (context.Request.Headers["X-Requested-With"] != "fetch")
            {
                Fail(context, 403, "Missing X-Requested-With header.");
                return;
            }

            var serializer = new JavaScriptSerializer();
            OrderRequest request;
            try
            {
                using (var reader = new StreamReader(context.Request.InputStream))
                {
                    request = serializer.Deserialize<OrderRequest>(reader.ReadToEnd());
                }
            }
            catch (ArgumentException)
            {
                Fail(context, 400, "Malformed JSON.");
                return;
            }
            catch (InvalidOperationException)
            {
                Fail(context, 400, "Unexpected JSON shape.");
                return;
            }

            if (request == null || request.Quantity < 1 || request.Quantity > 100)
            {
                Fail(context, 400, "Quantity must be between 1 and 100.");
                return;
            }

            Product product = ProductCatalog.Find(request.ProductId);
            if (product == null)
            {
                Fail(context, 404, "Unknown product.");
                return;
            }

            context.Response.StatusCode = 201;
            context.Response.ContentType = "application/json";
            context.Response.Write(serializer.Serialize(new { total = request.Quantity * product.Price }));
        }

        private static void Fail(HttpContext context, int status, string message)
        {
            context.Response.StatusCode = status;
            context.Response.ContentType = "application/json";
            context.Response.Write(new JavaScriptSerializer().Serialize(new { error = message }));
        }
    }
}
async function placeOrder(productId, quantity) {
    const response = await fetch('/Handlers/OrderApi.ashx', {
        method: 'POST',
        credentials: 'same-origin',
        headers: { 'Content-Type': 'application/json', 'X-Requested-With': 'fetch' },
        body: JSON.stringify({ productId: productId, quantity: quantity })
    });

    const body = await response.json();
    if (!response.ok) {
        throw new Error(body.error); // 400, 403, 404 and 405 all carry { error: "..." }
    }

    return body; // { total: 99.8 }
}

placeOrder(1, 2)
    .then(function (result) { console.log('Order total: ' + result.total); })
    .catch(function (err) { console.error('Order failed: ' + err.message); });

The call crosses no ViewState, runs no page life cycle, and reports failure through the HTTP status that fetch exposes as response.ok, which is what makes it easy to test with a plain HTTP client as well as from a browser. It also needs the authorization the page-based version got for free: an .ashx under a folder that <authorization> protects is protected like a page, but a handler outside any protected path is public, so place handlers deliberately and check context.User.Identity.IsAuthenticated for any endpoint that changes data.

Stable IDs inside repeating controls

ClientIDMode="Static" is right for single controls, but inside a repeater or grid it would produce duplicate DOM IDs. The Predictable mode with a row suffix generates readable and unique IDs instead:

<asp:GridView ID="ProductsGrid" runat="server" AutoGenerateColumns="false"
    ClientIDMode="Predictable" ClientIDRowSuffix="Id" DataKeyNames="Id" DataSourceID="ProductsObjectSource">
    <Columns>
        <asp:TemplateField>
            <ItemTemplate>
                <asp:Button ID="BuyButton" runat="server" Text="Buy" CommandName="Buy" />
            </ItemTemplate>
        </asp:TemplateField>
    </Columns>
</asp:GridView>

The button of the row whose Id is 3 renders as ProductsGrid_BuyButton_3, so a script can address one row’s button with document.getElementById('ProductsGrid_BuyButton_3') and the ID survives a re-sort or a page change, which a positional suffix (_0, _1) does not.
