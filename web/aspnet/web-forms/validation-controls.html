Validation Controls

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Web Forms validation controls declaratively bind a rule to an input control and run that rule both in the browser (via injected JavaScript) and again on the server (because client-side checks can always be bypassed), without hand-writing either half.

The built-in validator controls

Control Checks

RequiredFieldValidator

The associated control has a non-empty, non-InitialValue value.

RangeValidator

The value falls between MinimumValue and MaximumValue for a given Type (Integer, Double, Date, Currency, String).

CompareValidator

Compares against a fixed value, another control’s value (ControlToCompare), or just checks a type conversion (Operator="DataTypeCheck").

RegularExpressionValidator

The value matches a ValidationExpression regular expression.

CustomValidator

Arbitrary logic via a server ServerValidate event and/or a client ClientValidationFunction.

ValidationSummary

Aggregates every failed validator’s ErrorMessage on the page (or one group) into a single list or message box.

 
<asp:TextBox ID="EmailBox" runat="server" />
<asp:RequiredFieldValidator ID="EmailRequired" runat="server"
    ControlToValidate="EmailBox" ErrorMessage="Email is required." Display="Dynamic" />
<asp:RegularExpressionValidator ID="EmailFormat" runat="server"
    ControlToValidate="EmailBox" ErrorMessage="Enter a valid email address."
    ValidationExpression="^[^@\s]+@[^@\s]+\.[^@\s]+$" Display="Dynamic" />

<asp:TextBox ID="AgeBox" runat="server" />
<asp:RangeValidator ID="AgeRange" runat="server" ControlToValidate="AgeBox"
    Type="Integer" MinimumValue="0" MaximumValue="120" ErrorMessage="Age must be 0-120." />

<asp:TextBox ID="PasswordBox" runat="server" TextMode="Password" />
<asp:TextBox ID="ConfirmBox" runat="server" TextMode="Password" />
<asp:CompareValidator ID="PasswordsMatch" runat="server"
    ControlToValidate="ConfirmBox" ControlToCompare="PasswordBox"
    ErrorMessage="Passwords do not match." />

<asp:ValidationSummary ID="Summary" runat="server" HeaderText="Please fix the following:" />

CustomValidator covers anything the built-in validators cannot express, such as a rule needing a database lookup:

<asp:CustomValidator ID="UsernameAvailable" runat="server"
    ControlToValidate="UsernameBox" OnServerValidate="UsernameAvailable_ServerValidate"
    ErrorMessage="That username is already taken." />
protected void UsernameAvailable_ServerValidate(object source, ServerValidateEventArgs args)
{
    args.IsValid = !_userRepository.UsernameExists(args.Value);
}

See ASP.NET Validation Controls Overview and How to: Perform Validation for a Custom Server Control.

ValidationGroup

A page with multiple independent forms (e.g. a login box and a newsletter sign-up box on the same page) uses ValidationGroup to scope which validators fire for which submit button, so submitting one form does not trigger validation errors from the other:

<asp:TextBox ID="LoginUserBox" runat="server" ValidationGroup="Login" />
<asp:RequiredFieldValidator runat="server" ControlToValidate="LoginUserBox"
    ValidationGroup="Login" ErrorMessage="Username required." />
<asp:Button ID="LoginButton" runat="server" Text="Log in" ValidationGroup="Login" />

<asp:TextBox ID="NewsletterEmailBox" runat="server" ValidationGroup="Newsletter" />
<asp:RequiredFieldValidator runat="server" ControlToValidate="NewsletterEmailBox"
    ValidationGroup="Newsletter" ErrorMessage="Email required." />
<asp:Button ID="SubscribeButton" runat="server" Text="Subscribe" ValidationGroup="Newsletter" />

Page.IsValid and Validate()

Server-side code must always check Page.IsValid before acting on submitted data — client-side validation is a UX convenience, not a security boundary, and can be bypassed entirely (disabled JavaScript, a hand-crafted POST):

protected void SaveButton_Click(object sender, EventArgs e)
{
    if (!Page.IsValid)
    {
        return; // validators already populated their error messages; nothing else to do
    }
    _customerService.Save(EmailBox.Text, int.Parse(AgeBox.Text));
}

Page.IsValid reflects the last call to Page.Validate(), which ASP.NET calls automatically for any control whose CausesValidation is true (the default for Button/LinkButton/ImageButton) when it causes a postback. Calling Page.Validate("GroupName") explicitly (rather than relying on automatic validation) is needed when validating a specific group outside the normal button-click flow.

Server/client duality

Each validator renders both the markup ASP.NET needs to evaluate it server-side and, when the MS_AJAX_.../WebResource.axd-served client validation script is present (automatic unless explicitly disabled), a matching client-side check that runs on submit and toggles the control’s visibility/CSS class without a round trip. The server-side check always re-runs regardless of what the client already reported — this is why removing or working around the client script never bypasses server enforcement, only the instant feedback.

Unobtrusive validation (4.5) and its jQuery dependency

Starting with ASP.NET 4.5, ValidationSettings:UnobtrusiveValidationMode (in web.config, or Page.UnobtrusiveValidationMode) switches client-side validation from inline onsubmit/onclick script blocks to data-val-* HTML5 attributes read by a small unobtrusive-validation script, which in turn depends on jQuery being present on the page:

<appSettings>
  <add key="ValidationSettings:UnobtrusiveValidationMode" value="WebForms" />
</appSettings>
<!-- rendered output changes shape but not semantics -->
<input name="EmailBox" type="text" data-val="true"
       data-val-required="Email is required."
       data-val-regex="Enter a valid email address."
       data-val-regex-pattern="^[^@\s]+@[^@\s]+\.[^@\s]+$" />

This mode requires jQuery (and the WebForms.js/MicrosoftAjaxWebForms.js unobtrusive-validation shim) to be referenced on the page — a ScriptManager typically pulls these in automatically (see AJAX and Client-Side Integration); without jQuery loaded, client-side validation silently does not run (server-side validation is unaffected either way).

CausesValidation

Any control that submits the page can opt out of triggering validation with CausesValidation="false" — essential for "Cancel" buttons, which should post back (to abandon edits and navigate away) without being blocked by unrelated validators on the same form:

<asp:Button ID="CancelButton" runat="server" Text="Cancel"
    CausesValidation="false" OnClick="CancelButton_Click" />

Where validation runs: the full flow

Client validation, the postback, and Page.IsValid are three separate steps, and the second and third happen even when the first succeeded. The following diagram follows one click of the order form’s Add button:

flowchart TD A["User clicks a button with CausesValidation = true"] --> B{"Client script present\nand EnableClientScript = true?"} B -- yes --> C["Browser evaluates each validator\nin the button's ValidationGroup"] C --> D{"All valid?"} D -- no --> E["Show messages and the ValidationSummary,\nSetFocusOnError moves the cursor; no request is sent"] D -- yes --> F["__doPostBack / form submit"] B -- no --> F F --> G["Server: Load, then Page.Validate(group)\nrun for the button that caused the postback"] G --> H["Each validator's EvaluateIsValid / ServerValidate runs"] H --> I{"Page.IsValid?"} I -- no --> J["Handler returns early;\npage re-renders with the same messages"] I -- yes --> K["Handler does the work"]

Two details follow from the flow. The server always re-validates, so a tampered request that skips the client script reaches the handler with Page.IsValid false, not with bad data. And validation runs before the click handler but after Page_Load: Page_Load cannot use Page.IsValid (reading it before Validate has run throws an HttpException), while the click handler can.

Worked example: the order-entry form

The following fragment combines five rules on the order form from Getting Started: a required quantity, a numeric range, a rule that items ship in cartons of five (a CustomValidator with matching client and server code), a delivery date that cannot precede the order date (a CompareValidator between two controls), and a summary tied to one validation group:

<asp:ValidationSummary ID="OrderSummary" runat="server" ValidationGroup="Order"
    HeaderText="Please fix the following:" DisplayMode="BulletList" />

<asp:TextBox ID="QuantityBox" runat="server" />
<asp:RequiredFieldValidator ID="QuantityRequired" runat="server" ControlToValidate="QuantityBox"
    ValidationGroup="Order" ErrorMessage="Quantity is required." Text="*" Display="Dynamic"
    SetFocusOnError="true" />
<asp:RangeValidator ID="QuantityRange" runat="server" ControlToValidate="QuantityBox"
    ValidationGroup="Order" Type="Integer" MinimumValue="1" MaximumValue="500"
    ErrorMessage="Quantity must be between 1 and 500." Text="*" Display="Dynamic" />
<asp:CustomValidator ID="CartonRule" runat="server" ControlToValidate="QuantityBox"
    ValidationGroup="Order" ErrorMessage="Items ship in cartons of 5." Text="*" Display="Dynamic"
    ClientValidationFunction="validateCarton" OnServerValidate="CartonRule_ServerValidate" />

<asp:TextBox ID="OrderDateBox" runat="server" TextMode="Date" />
<asp:TextBox ID="DeliveryDateBox" runat="server" TextMode="Date" />
<asp:CompareValidator ID="DeliveryAfterOrder" runat="server" ControlToValidate="DeliveryDateBox"
    ControlToCompare="OrderDateBox" Operator="GreaterThanEqual" Type="Date"
    ValidationGroup="Order" ErrorMessage="Delivery cannot be before the order date." Text="*" />

<asp:Button ID="PlaceOrderButton" runat="server" Text="Place order" ValidationGroup="Order"
    OnClick="PlaceOrderButton_Click" />

<script type="text/javascript">
    function validateCarton(source, args) {
        var quantity = parseInt(args.Value, 10);
        args.IsValid = !isNaN(quantity) && quantity % 5 === 0;
    }
</script>
protected void CartonRule_ServerValidate(object source, ServerValidateEventArgs args)
{
    int quantity;
    args.IsValid = int.TryParse(args.Value, out quantity) && quantity % 5 == 0;
}

protected void PlaceOrderButton_Click(object sender, EventArgs e)
{
    if (!Page.IsValid)
    {
        return;
    }

    // Only reached when every validator in the "Order" group passed.
    var order = new Order
    {
        CustomerName = User.Identity.Name,
        Total = int.Parse(QuantityBox.Text) * 10m
    };
    _orderRepository.Save(order);
}

Notes on how the pieces interact. Text="*" is shown next to the field while ErrorMessage goes to the summary, so the form stays compact. Display="Dynamic" collapses the space of a validator that is not failing. CustomValidator and the other validators (except RequiredFieldValidator) treat an empty value as valid, which is why the quantity box also needs the RequiredFieldValidator; set ValidateEmptyText="true" on a CustomValidator when it must also judge empty input. The Order and OrderRepository types in the handler are those of Architecture and Testing. CompareValidator with Type="Date" parses both boxes with the current culture; the ISO yyyy-MM-dd text that TextMode="Date" posts is accepted by the client and server parsers in the common cultures, but a form shipped to several locales should be tested with each of them, or compare the values in a CustomValidator instead.

Reporting server-only errors in the summary

Some failures are only discovered inside the handler — a duplicate order number found by the database, a payment gateway refusal — after every validator has already passed. Adding a validator that is already invalid puts such an error into the same ValidationSummary and Page.IsValid machinery, instead of inventing a second error label:

using System.Web;
using System.Web.UI;
using System.Web.UI.WebControls;

public static class ValidationExtensions
{
    public static void AddError(this Page page, string message, string validationGroup = "")
    {
        page.Validators.Add(new CustomValidator
        {
            IsValid = false,
            // ValidationSummary writes ErrorMessage as HTML, so never pass unencoded user input.
            ErrorMessage = HttpUtility.HtmlEncode(message),
            ValidationGroup = validationGroup
        });
    }
}
try
{
    _orderRepository.Save(order);
}
catch (DuplicateOrderException ex)
{
    this.AddError("Order " + ex.OrderNumber + " already exists.", "Order");
}

(DuplicateOrderException stands for whatever exception the repository layer throws for that case.)

Writing a validator control

When a rule is reused in many forms, a custom validator is cleaner than repeating a CustomValidator with two handlers. A server-only validator derives from BaseValidator and overrides EvaluateIsValid:

using System.Web.UI.WebControls;

namespace WebFormsApp.Controls
{
    public class MultipleOfValidator : BaseValidator
    {
        public int Multiple
        {
            get { return (int)(ViewState["Multiple"] ?? 1); }
            set { ViewState["Multiple"] = value; }
        }

        protected override bool ControlPropertiesValid()
        {
            return Multiple > 0 && base.ControlPropertiesValid();
        }

        protected override bool EvaluateIsValid()
        {
            string text = GetControlValidationValue(ControlToValidate);
            int value;
            return int.TryParse(text, out value) && value % Multiple == 0;
        }
    }
}
<%@ Register TagPrefix="cc" Namespace="WebFormsApp.Controls" Assembly="WebFormsApp" %>
<cc:MultipleOfValidator ID="CartonRule" runat="server" ControlToValidate="QuantityBox"
    Multiple="5" ErrorMessage="Items ship in cartons of 5." />

BaseValidator supplies ControlToValidate, ErrorMessage, Display, IsValid and the group handling; the class above is server-only, so to give it instant client feedback it also has to register a script in OnPreRender and set the evaluationfunction expando attribute on the rendered span, which is the contract the built-in validators follow. When that client half is not needed, the server-only version is complete.
