Getting Started with ASP.NET Web Forms

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page orients a developer inside an ASP.NET Web Forms codebase: how the project is organized, how a page is put together, and how a request becomes rendered HTML before the page life cycle itself (covered next) takes over.

Web Site Project vs. Web Application Project

Visual Studio has offered two different project models for Web Forms since .NET Framework 2.0, and both are still current on .NET Framework 4.8.1:

Web Site Project (WSP) Web Application Project (WAP)

No .csproj; the folder on disk is the project.

Standard MSBuild .csproj; explicit file list.

Each page compiles individually, on first request or with aspnet_compiler.

The whole project compiles into one assembly before deployment.

Easy to edit a single page directly on a production server.

Cannot edit a single file in place without a full rebuild/redeploy.

Weak refactoring support; partial classes are inferred at compile time.

Full Visual Studio refactoring, since code-behind partial classes are explicit compiled members.

Good fit for simple sites maintained by many small edits.

Good fit for team development with source control, unit tests, and CI builds.

New Web Forms development (to the extent there is any) should use the Web Application Project model — it is the one that behaves like every other MSBuild-based .NET project and is what the rest of this section assumes. See Web Application Projects versus Web Site Projects for the full comparison.

<!-- WebFormsApp.csproj (Web Application Project, .NET Framework 4.8.1) -->
<Project ToolsVersion="15.0" xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
  <PropertyGroup>
    <TargetFrameworkVersion>v4.8.1</TargetFrameworkVersion>
    <ProjectTypeGuids>{349c5851-65df-11da-9384-00065b846f21};{FAE04EC0-301F-11D3-BF4B-00C04F79EFBC}</ProjectTypeGuids>
    <UseIISExpress>true</UseIISExpress>
  </PropertyGroup>
  <ItemGroup>
    <Reference Include="System.Web" />
    <Reference Include="System.Web.Extensions" />
  </ItemGroup>
</Project>

The {349c5851-...} project-type GUID marks this as an ASP.NET Web Application in the solution; it is what tells Visual Studio to compile the whole site into one assembly and enable the WAP-specific tooling.

.aspx / .aspx.cs anatomy

A Web Forms page is two files working together: the .aspx markup file and its code-behind class.

<%-- Default.aspx --%>
<%@ Page Title="Home" Language="C#" AutoEventWireup="true"
    CodeBehind="Default.aspx.cs" Inherits="WebFormsApp.Default" %>

<!DOCTYPE html>
<html>
<head runat="server">
    <title><%: Page.Title %></title>
</head>
<body>
    <form id="form1" runat="server">
        <div>
            <asp:Label ID="GreetingLabel" runat="server" Text="Hello" />
            <asp:Button ID="SayHiButton" runat="server" Text="Say hi"
                OnClick="SayHiButton_Click" />
        </div>
    </form>
</body>
</html>
// Default.aspx.cs
namespace WebFormsApp
{
    public partial class Default : System.Web.UI.Page
    {
        protected void Page_Load(object sender, EventArgs e)
        {
            if (!IsPostBack)
            {
                GreetingLabel.Text = "Hello, first visit!";
            }
        }

        protected void SayHiButton_Click(object sender, EventArgs e)
        {
            GreetingLabel.Text = "Hello, " + DateTime.Now.ToLongTimeString();
        }
    }
}

The code-behind class is partial; Visual Studio generates a second partial class, Default.aspx.designer.cs, containing a protected field per runat="server" control (GreetingLabel, SayHiButton above) so they can be referenced by name from code-behind without manual declarations. Every .aspx page ultimately derives from System.Web.UI.Page, itself a System.Web.UI.Control — the base of the control-tree model covered in Server Controls.

Code-behind vs. inline code

Inline code — <% ... %> render blocks and <%= ... %> / <%: ... %> expressions directly in the .aspx markup — still works and predates code-behind:

<p>Server time: <%: DateTime.Now.ToString("T") %></p>
<% for (int i = 0; i < 3; i++) { %>
    <li>Item <%: i %></li>
<% } %>

<%: expr %> (added in ASP.NET 4) HTML-encodes the result automatically; the older <%= expr %> does not and is an XSS risk against untrusted data. Prefer <%: %> (or Server.HtmlEncode) whenever the value did not come from a trusted, already-encoded source. Code-behind is preferred for anything beyond trivial formatting: it gets full IntelliSense, step debugging, and unit-testable methods, none of which apply cleanly to inline code blocks embedded in markup.

The @Page, @Control, @Register, and @Import directives

<%@ Page Language="C#" AutoEventWireup="true" CodeBehind="Default.aspx.cs"
    Inherits="WebFormsApp.Default" MasterPageFile="~/Site.master"
    EnableViewState="true" %>

<%@ Import Namespace="System.Text" %>

<%@ Register TagPrefix="uc" TagName="Greeting" Src="~/Controls/Greeting.ascx" %>
<%@ Register TagPrefix="cc" Namespace="WebFormsApp.Controls" Assembly="WebFormsApp" %>

<uc:Greeting ID="Greeting1" runat="server" />

  • @Page — one per .aspx file; declares the language, the code-behind link, the base class, the master page, and page-level defaults such as EnableViewState and ValidateRequest.

  • @Control — the @Page equivalent for a .ascx user control (see User and Custom Controls).

  • @Import — brings a namespace into scope for inline code, equivalent to a C# using.

  • @Register — makes a user control (Src=) or a compiled custom-control assembly (Namespace=/Assembly=) available under a markup tag prefix.

See ASP.NET Web Forms Page Syntax for the full directive and syntax reference.

The App_* special folders

ASP.NET reserves several top-level folder names and compiles or serves their contents specially:

Folder Purpose

App_Code

Classes compiled automatically into a dynamic assembly, referenceable from any page without an explicit project reference — helper classes, typed DataSet classes, .wsdl/.xsd-generated proxies.

App_Data

Application data files — .mdf SQL Server Express databases, XML files — excluded from being served directly over HTTP by default IIS/ASP.NET configuration.

App_Themes

Skin files (.skin) and theme CSS/images, one subfolder per theme; see Master Pages, Themes, and Localization.

App_GlobalResources

.resx resource files available application-wide via <%$ Resources: %> and strongly typed Resources.* classes.

App_LocalResources

Per-page .resx files (Default.aspx.resx, Default.aspx.fr.resx, …​) scoped to one page or user control, used for implicit meta:resourcekey localization.

App_Browsers

.browser files extending ASP.NET’s browser-capabilities detection (Request.Browser) for non-standard clients.

AutoEventWireup

AutoEventWireup="true" (the WAP template default) lets ASP.NET bind well-known page-lifecycle event handler methods — Page_Load, Page_Init, Page_PreRender, and so on — purely by method name, with no explicit += subscription required. Setting it to "false" requires wiring events explicitly, typically by overriding OnLoad/OnInit or subscribing in the constructor:

// Equivalent to AutoEventWireup picking up Page_Load automatically:
public partial class Default : System.Web.UI.Page
{
    public Default()
    {
        Load += Page_Load; // explicit wiring, needed when AutoEventWireup="false"
    }

    private void Page_Load(object sender, EventArgs e) { /* ... */ }
}

Explicit wiring is marginally faster (it skips a reflection-based lookup on the first page hit per type) and is required if a base class also defines a Page_Load-named method that should not be auto-bound; almost all Web Forms code leaves AutoEventWireup="true" and relies on the naming convention.

Visual Studio designer and tooling

Visual Studio’s Web Forms Designer offers a WYSIWYG/Split/Source view over .aspx markup, drag-and-drop from the Toolbox (which inserts <asp:Control runat="server" .../> markup and a matching designer field), and the Properties window bound to whichever control is selected. IntelliSense works over both markup (tag/attribute completion for registered controls) and code-behind. Debugging a Web Forms page is ordinary .NET debugging — set a breakpoint in Page_Load or an event handler, run under IIS Express, and step through exactly as in any other .NET Framework project; the debugger has no special awareness of the page life cycle beyond what a normal call stack shows.

Targeting .NET Framework 4.8.1

NET Framework 4.8.1 is an in-place update to 4.8 (Windows 11-specific ARM64 and WIC improvements; no new

Web Forms features) and is the effective ceiling for TargetFrameworkVersion in any Web Forms project today. There is no reason to target an older 4.x version for new work — 4.8.1 is fully backward compatible with code written against 4.0 through 4.8, and picking it gets the latest available runtime and JIT fixes with no source changes required. See the ASP.NET Web Forms documentation on Microsoft Learn and .NET Framework versions and dependencies for compatibility details.

From request to rendered page: what the compiler does with an .aspx file

An .aspx file is never interpreted line by line. The first time a URL is requested (or at deployment time when the site is precompiled, see HTTP Pipeline, Handlers, and Configuration), ASP.NET parses the directives and markup, turns every runat="server" element into a node of a control tree description, emits a C# (or VB) class that derives from the code-behind class, and compiles it. The generated class lives in the ASP namespace; its BuildControlTree method is what instantiates Label, TextBox, and Button objects and adds them to the page, and its Render method is what writes the literal markup between them. That is why the code-behind class must be partial for the designer fields and, in a Web Site Project, why a syntax error in one .aspx surfaces as a compile error only when that page is first requested.

flowchart TD A["Browser requests /Orders/NewOrder.aspx"] --> B["IIS hands the .aspx extension to ASP.NET: PageHandlerFactory is the handler"] B --> C{"Compiled assembly for this page\nexists and is newer than the file?"} C -- yes --> F C -- no --> D["Parser reads @Page directive and markup,\nbuilds a description of the control tree"] D --> E["Code generator emits class ASP.orders_neworder_aspx\nderived from WebFormsApp.Orders.NewOrder;\ncompiler writes it to Temporary ASP.NET Files"] E --> F["Instantiate the page class\nand run the page life cycle"] F --> G["Render: HTML response to the browser"] H["Edit the .aspx, change web.config,\nor recycle the app pool"] -.invalidates.-> C

Two practical consequences follow. A change to web.config or to anything in bin restarts the application domain and discards every cached page, so the next request to each page pays the compilation cost again (the reason production sites are precompiled or warmed up after a deployment). And an unhandled compile error is reported with the generated source line, not the .aspx line, which is the first thing to know when reading a "Compilation Error" page.

Worked example: the order-entry page used throughout this section

The remaining pages of this section build on one small application, WebFormsApp: a catalog of products and an order-entry page on top of it. This is the foundation. First the model, kept in an ordinary class file (Services/ProductCatalog.cs) so that nothing in it depends on System.Web:

// Services/ProductCatalog.cs
using System.Collections.Generic;
using System.Linq;

namespace WebFormsApp.Services
{
    public sealed class Product
    {
        public int Id { get; set; }
        public string Name { get; set; }
        public decimal Price { get; set; }
    }

    public static class ProductCatalog
    {
        private static readonly Product[] Items =
        {
            new Product { Id = 1, Name = "Keyboard", Price = 49.90m },
            new Product { Id = 2, Name = "Monitor", Price = 219.00m },
            new Product { Id = 3, Name = "Webcam", Price = 79.50m },
        };

        public static IReadOnlyList<Product> All() => Items;

        public static Product Find(int id) => Items.FirstOrDefault(p => p.Id == id);
    }
}

Then the page, Orders/NewOrder.aspx, with its code-behind:

<%-- Orders/NewOrder.aspx --%>
<%@ Page Title="New order" Language="C#" AutoEventWireup="true"
    CodeBehind="NewOrder.aspx.cs" Inherits="WebFormsApp.Orders.NewOrder" %>

<!DOCTYPE html>
<html>
<head runat="server">
    <title><%: Page.Title %></title>
</head>
<body>
    <form id="form1" runat="server">
        <h1><asp:Label ID="SiteNameLabel" runat="server" Text="<%$ AppSettings:SiteName %>" /></h1>
        <asp:DropDownList ID="ProductList" runat="server" />
        <asp:TextBox ID="QuantityBox" runat="server" Text="1" />
        <asp:RequiredFieldValidator ID="QuantityRequired" runat="server"
            ControlToValidate="QuantityBox" ErrorMessage="Quantity is required." Display="Dynamic" />
        <asp:RangeValidator ID="QuantityRange" runat="server" ControlToValidate="QuantityBox"
            Type="Integer" MinimumValue="1" MaximumValue="100"
            ErrorMessage="Enter a quantity between 1 and 100." Display="Dynamic" />
        <asp:Button ID="AddButton" runat="server" Text="Add to order" OnClick="AddButton_Click" />
        <asp:Label ID="TotalLabel" runat="server" />
    </form>
</body>
</html>
// Orders/NewOrder.aspx.cs
using System;
using System.Web.UI;
using WebFormsApp.Services;

namespace WebFormsApp.Orders
{
    public partial class NewOrder : Page
    {
        protected void Page_Load(object sender, EventArgs e)
        {
            if (IsPostBack)
            {
                return; // the list items come back from ViewState
            }

            ProductList.DataSource = ProductCatalog.All();
            ProductList.DataTextField = "Name";
            ProductList.DataValueField = "Id";
            ProductList.DataBind();
        }

        protected void AddButton_Click(object sender, EventArgs e)
        {
            if (!IsValid)
            {
                return;
            }

            Product product = ProductCatalog.Find(int.Parse(ProductList.SelectedValue));
            int quantity = int.Parse(QuantityBox.Text);
            TotalLabel.Text = string.Format("{0} x {1} = {2:C}", quantity, product.Name, quantity * product.Price);
        }
    }
}

The designer file that Visual Studio regenerates every time the markup changes is the bridge between the two halves; it contains nothing but one field per named server control, which is what lets ProductList and TotalLabel be used in the code-behind without being declared there:

// Orders/NewOrder.aspx.designer.cs (generated -- never edit by hand)
namespace WebFormsApp.Orders
{
    public partial class NewOrder
    {
        protected global::System.Web.UI.HtmlControls.HtmlForm form1;
        protected global::System.Web.UI.WebControls.Label SiteNameLabel;
        protected global::System.Web.UI.WebControls.DropDownList ProductList;
        protected global::System.Web.UI.WebControls.TextBox QuantityBox;
        protected global::System.Web.UI.WebControls.RequiredFieldValidator QuantityRequired;
        protected global::System.Web.UI.WebControls.RangeValidator QuantityRange;
        protected global::System.Web.UI.WebControls.Button AddButton;
        protected global::System.Web.UI.WebControls.Label TotalLabel;
    }
}

The markup reads its heading text (SiteNameLabel) from configuration through an expression builder. Expression builders (<%$ ... %>) are resolved once when the control is created, which makes them the right tool for settings that belong in web.config rather than in a compiled string:

<configuration>
  <appSettings>
    <add key="SiteName" value="Order Desk" />
  </appSettings>
  <connectionStrings>
    <add name="CatalogDb" providerName="System.Data.SqlClient"
         connectionString="Data Source=.\SQLEXPRESS;Initial Catalog=Catalog;Integrated Security=true" />
  </connectionStrings>
  <system.web>
    <compilation debug="false" targetFramework="4.8" />
    <httpRuntime targetFramework="4.8" />
  </system.web>
</configuration>

The two targetFramework attributes opt the application in to the 4.5+ behaviors (unobtrusive validation, request-validation changes, the async pipeline) that the later pages assume; an application that omits httpRuntime/@targetFramework silently runs with 4.0 behavior even on a 4.8 server, a frequent cause of "it works on the new site but not the migrated one" reports.

The syntax blocks at a glance

Every <% ... %> form has a different meaning, and mixing them up is a common source of both bugs and XSS holes:

Syntax Meaning

<%@ ... %>

Directive: configures the parser and compiler (Page, Control, Master, Register, Import, OutputCache, Reference). Evaluated at compile time, never at request time.

<% statements %>

A render block: arbitrary C# statements run during Render, writing output with the surrounding markup.

<%= expression %>

Writes the expression’s string value without encoding.

<%: expression %>

Writes the expression’s string value HTML-encoded (ASP.NET 4 and later).

<%# expression %>

A data-binding expression, evaluated only when DataBind() runs on the containing control.

<%$ Prefix: value %>

An expression builder (ConnectionStrings, AppSettings, Resources, or a custom one), evaluated when the control is created. Valid only as the value of a server-control attribute, never as free text.

<%-- comment --%>

A server-side comment: unlike an HTML comment it is never sent to the browser.

The data-binding form is covered in Data Binding and Data Controls, and the HTML-encoding forms in Security.

See the ASP.NET Web Forms documentation and the ASP.NET 4 documentation archive for the page code model and expression syntax references.
