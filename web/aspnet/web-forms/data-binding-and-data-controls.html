Data Binding and Data Controls

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Data binding is Web Forms' declarative link between a data source and a repeating or detail UI, and it is the area where the framework’s "close to configuration, not code" promise is most visible — and where the binding-order pitfall covered at the end of this page is most commonly hit.

Data-binding expressions

<asp:Repeater ID="ProductsRepeater" runat="server">
    <ItemTemplate>
        <li>
            <%# Eval("Name") %> -- <%# Eval("Price", "{0:C}") %>
            <%-- Bind() is required (not Eval()) wherever the control writes the value back, e.g. FormView edit mode --%>
            <asp:TextBox runat="server" Text='<%# Bind("Quantity") %>' />
        </li>
    </ItemTemplate>
</asp:Repeater>

<asp:Repeater ID="CatalogRepeater" runat="server">
    <ItemTemplate>
        <%-- XPath() reads from an XmlDataSource-bound XPathNavigator item instead of a property bag --%>
        <span><%# XPath("@name") %></span>
    </ItemTemplate>
</asp:Repeater>

Eval is one-way (data → control); Bind is two-way and only valid inside a control that supports updating (a FormView/DetailsView edit template, or paired with a data source control’s Update command); XPath is the XML-specific sibling of Eval, valid when the bound item is an XmlDataSource node. All three only evaluate when DataBind() actually runs on the containing control — they are not live bindings.

Data source controls

Data source controls are the declarative, no-code-behind way to wire a data-bound control to data:

Control Backs onto

SqlDataSource

A raw ADO.NET connection/command — SQL text or stored procedure, parameterized.

ObjectDataSource

An arbitrary business/data-access class following a method-name convention (SelectMethod, UpdateMethod, …​).

LinqDataSource

A LINQ to SQL DataContext.

EntityDataSource

An Entity Framework (EF6-era, ObjectContext/DbContext) model.

XmlDataSource

An XML document/file, queryable via XPath.

SiteMapDataSource

The site’s Web.sitemap hierarchy (see Master Pages, Themes, and Localization).

 
<asp:SqlDataSource ID="ProductsSource" runat="server"
    ConnectionString="<%$ ConnectionStrings:CatalogDb %>"
    SelectCommand="SELECT Id, Name, Price FROM Products WHERE CategoryId = @CategoryId"
    UpdateCommand="UPDATE Products SET Name=@Name, Price=@Price WHERE Id=@Id AND RowVersion=@original_RowVersion"
    ConflictDetection="CompareAllValues" OldValuesParameterFormatString="original_{0}">
    <SelectParameters>
        <asp:QueryStringParameter Name="CategoryId" QueryStringField="cat" Type="Int32" />
    </SelectParameters>
</asp:SqlDataSource>

<asp:ObjectDataSource ID="ProductsObjectSource" runat="server"
    TypeName="WebFormsApp.Data.ProductRepository"
    SelectMethod="GetByCategory" UpdateMethod="Update" InsertMethod="Insert" DeleteMethod="Delete" />

SqlDataSource embedding SQL directly in markup is functional but tightly couples presentation to persistence and is the pattern most Web Forms teams eventually replace with ObjectDataSource over a repository, or with model binding against a plain method.

Data-bound controls

Control Shape

GridView

Tabular, one row per record, built-in paging/sorting/editing/deleting via declarative fields.

DetailsView

A single record, field-per-row, with built-in paging between records and insert/edit/delete.

FormView

A single record, fully templated (no default rendering) — the templated counterpart to DetailsView.

Repeater

Fully templated, minimal built-in behavior — no default styling, paging, or editing; the most "just render this" of the group.

DataList

Templated, like Repeater, but supports a repeating flow/table layout (RepeatColumns, RepeatDirection) and basic edit-mode templates.

ListView / DataPager

Templated like Repeater/DataList but with full built-in paging (via a separate DataPager), sorting, insert/edit/delete — effectively the flexibility of GridView without its fixed tabular rendering.

 
<asp:GridView ID="ProductsGrid" runat="server" DataSourceID="ProductsSource"
    AutoGenerateColumns="false" DataKeyNames="Id"
    AllowPaging="true" PageSize="20" AllowSorting="true"
    OnRowEditing="ProductsGrid_RowEditing">
    <Columns>
        <asp:BoundField DataField="Name" HeaderText="Name" SortExpression="Name" />
        <asp:TemplateField HeaderText="Price">
            <ItemTemplate><%# Eval("Price", "{0:C}") %></ItemTemplate>
            <EditItemTemplate><asp:TextBox runat="server" Text='<%# Bind("Price") %>' /></EditItemTemplate>
        </asp:TemplateField>
        <asp:CommandField ShowEditButton="true" ShowDeleteButton="true" />
    </Columns>
</asp:GridView>

TemplateField (used for Price above) is how any column beyond simple text — a formatted value, a nested control, conditional markup — is expressed; BoundField covers the plain-text case with less markup.

Paging, sorting, editing, inserting, deleting

GridView/DetailsView/ListView implement these against the capabilities of the bound IDataSource: paging re-queries (SelectCommand/SelectMethod) with new offset/size parameters, sorting appends an ORDER BY (SQL) or reflection-based sort (Object/Linq data sources), and edit/insert/delete map directly onto the data source’s UpdateCommand/InsertMethod/DeleteCommand. With a SqlDataSource/ObjectDataSource wired up, none of this requires code-behind at all beyond handling result/exception events for user feedback:

protected void ProductsSource_Updated(object sender, SqlDataSourceStatusEventArgs e)
{
    if (e.Exception != null)
    {
        e.ExceptionHandled = true;
        StatusLabel.Text = "Save failed: " + e.Exception.Message;
    }
}

Optimistic concurrency (ConflictDetection)

SqlDataSource/ObjectDataSource support optimistic concurrency via ConflictDetection="CompareAllValues" (compare every original column against current database state before applying the update, as in the SqlDataSource example above) or "OverwriteChanges" (last write wins, the default). CompareAllValues requires the data-bound control to keep the original row values around (via OldValuesParameterFormatString and, for GridView, DataKeyNames plus the row’s originally bound values) to compare against at update time, surfacing a conflict as a failed UpdateCommand/zero-rows-affected rather than a thrown ADO.NET concurrency exception.

Nested data-bound controls and the binding-order pitfall

Nesting one data-bound control inside another’s ItemTemplate (a Repeater of categories, each containing a nested Repeater of products) is common, but the outer control’s items — and therefore the inner controls — are only created once the outer control’s DataBind()/ItemDataBound has run. The classic mistake is calling .DataBind() on the inner control too early (e.g. in Page_Load, before the outer control has even created it) or forgetting to bind it at all inside ItemDataBound:

protected void CategoriesRepeater_ItemDataBound(object sender, RepeaterItemEventArgs e)
{
    if (e.Item.ItemType != ListItemType.Item && e.Item.ItemType != ListItemType.AlternatingItem)
    {
        return;
    }

    var category = (Category)e.Item.DataItem;
    var innerRepeater = (Repeater)e.Item.FindControl("ProductsRepeater");
    innerRepeater.DataSource = category.Products;
    innerRepeater.DataBind(); // must happen here -- the inner control does not exist before this fires
}

The general rule: bind the innermost control from within the outer control’s ItemDataBound (or the equivalent RowDataBound for GridView), never from Page_Load, because the inner control instance is created fresh on every outer-row bind and does not persist identity the way a page-level control does.

See ASP.NET Data-Bound Controls and GridView Web Server Control Overview.

DataSource vs. DataSourceID: who calls DataBind()

A data-bound control can be fed in two mutually exclusive ways, and the choice decides who is responsible for binding at the right moment:

  • DataSource plus an explicit DataBind() call (imperative binding): the page binds when it wants to, usually inside if (!IsPostBack), and must rebind after every operation that changes the data.

  • DataSourceID pointing at a data source control (declarative binding): the control binds itself during PreRender (and again whenever a command such as edit, sort, or page change invalidates its data), so no DataBind() call is written at all. Setting both properties throws.

Declarative binding is why the grid in the example below needs no Page_Load at all, and also why a data source control’s Selecting and Selected events, not Page_Load, are the place to hook query parameters or errors.

sequenceDiagram participant G as GridView participant V as DataSourceView (ObjectDataSource) participant R as ProductRepository Note over G: PreRender: DataSourceID set and data not yet bound G->>V: Select(arguments: sort expression, start row, max rows) V->>V: raise Selecting V->>R: GetPage(sortExpression, startRowIndex, maximumRows) R-->>V: rows for the current page only V->>V: raise Selected V-->>G: rows G->>G: for each row: RowCreated, then RowDataBound G->>G: DataBound once for the whole control

Worked example: a paged, sortable, editable product grid

The following example needs no code-behind beyond a repository class. The repository exposes the three methods ObjectDataSource looks for when paging is delegated to the data layer: a select method taking the sort expression and the paging window, a count method, and an update method:

// Data/ProductRepository.cs
using System.Collections.Generic;
using System.Linq;
using WebFormsApp.Services;

namespace WebFormsApp.Data
{
    public class ProductRepository
    {
        public IEnumerable<Product> GetPage(string sortExpression, int startRowIndex, int maximumRows)
        {
            IEnumerable<Product> query = ProductCatalog.All();

            switch (sortExpression)
            {
                case "Name DESC":
                    query = query.OrderByDescending(p => p.Name);
                    break;
                case "Price":
                    query = query.OrderBy(p => p.Price);
                    break;
                case "Price DESC":
                    query = query.OrderByDescending(p => p.Price);
                    break;
                default:
                    query = query.OrderBy(p => p.Name);
                    break;
            }

            return query.Skip(startRowIndex).Take(maximumRows).ToList();
        }

        public int GetCount()
        {
            return ProductCatalog.All().Count;
        }

        public void Update(int id, string name, decimal price)
        {
            Product product = ProductCatalog.Find(id);
            if (product != null)
            {
                product.Name = name;
                product.Price = price;
            }
        }
    }
}
<asp:ObjectDataSource ID="ProductsObjectSource" runat="server"
    TypeName="WebFormsApp.Data.ProductRepository"
    SelectMethod="GetPage" SelectCountMethod="GetCount" EnablePaging="true"
    SortParameterName="sortExpression" UpdateMethod="Update" />

<asp:GridView ID="ProductsGrid" runat="server" DataSourceID="ProductsObjectSource"
    DataKeyNames="Id" AutoGenerateColumns="false"
    AllowPaging="true" PageSize="2" AllowSorting="true"
    OnRowDataBound="ProductsGrid_RowDataBound">
    <Columns>
        <asp:BoundField DataField="Id" HeaderText="Id" ReadOnly="true" />
        <asp:BoundField DataField="Name" HeaderText="Name" SortExpression="Name" />
        <asp:BoundField DataField="Price" HeaderText="Price" SortExpression="Price"
            DataFormatString="{0:C}" />
        <asp:CommandField ShowEditButton="true" />
    </Columns>
</asp:GridView>
protected void ProductsGrid_RowDataBound(object sender, GridViewRowEventArgs e)
{
    if (e.Row.RowType != DataControlRowType.DataRow)
    {
        return; // header, footer and pager rows have no data item
    }

    var product = (Product)e.Row.DataItem;
    if (product.Price > 200m)
    {
        e.Row.CssClass = "premium";
    }
}

How the pieces fit: the grid asks the data source for one page (startRowIndex and maximumRows are the default names ObjectDataSource fills from the pager), the count method lets the grid draw page numbers without loading every row, and SortParameterName hands the SortExpression of the clicked header (Price, then Price DESC on the second click) to the select method. Edit mode is generated entirely by the grid: pressing Edit raises RowEditing and sets EditIndex, Update collects the key (Id) and the edited cells and calls Update(id, name, price) by name matching between parameters and field names, and then rebinds.

sequenceDiagram participant U as Browser participant G as GridView participant D as ObjectDataSource participant R as ProductRepository U->>G: click Edit (row 1) G->>G: RowEditing, EditIndex = 1, rebind with textboxes U->>G: click Update G->>G: RowUpdating (can cancel), collect keys and new values G->>D: Update(Id = 2, Name, Price) D->>R: Update(id, name, price) R-->>D: done D->>D: Updated event (exception handling point) G->>G: RowUpdated, EditIndex = -1, rebind

Paging in the data layer, as above, is what makes a grid usable on a large table. With a SqlDataSource in its default DataSet mode the control loads all matching rows on every request and the grid shows a slice of them, so for large result sets either set DataSourceMode="DataReader" (no sorting or paging then) or move to an ObjectDataSource with a count method as shown.

Worked example: ListView with a DataPager

When a grid’s fixed table layout is too rigid, ListView hands the markup to the page author: a LayoutTemplate containing a placeholder, an ItemTemplate repeated for each row, and an optional DataPager for paging:

<asp:ListView ID="ProductsList" runat="server" DataSourceID="ProductsObjectSource"
    DataKeyNames="Id" ItemPlaceholderID="itemPlaceholder">
    <LayoutTemplate>
        <ul class="products">
            <li runat="server" id="itemPlaceholder" />
        </ul>
        <asp:DataPager ID="Pager" runat="server" PageSize="2">
            <Fields>
                <asp:NumericPagerField ButtonCount="5" />
            </Fields>
        </asp:DataPager>
    </LayoutTemplate>
    <ItemTemplate>
        <li><%# Eval("Name") %> -- <%# Eval("Price", "{0:C}") %></li>
    </ItemTemplate>
    <EmptyDataTemplate>
        <p>No products found.</p>
    </EmptyDataTemplate>
</asp:ListView>

Two details cause most ListView bugs. The placeholder element must carry runat="server" and the ID named by ItemPlaceholderID, because the control replaces exactly that element with the rendered items; and a DataPager inside the LayoutTemplate finds its ListView by naming-container walk, so it needs no PagedControlID, while a pager placed outside the control needs one. With an ObjectDataSource, the DataPager supplies the same startRowIndex/maximumRows arguments as the grid’s pager, so the count method keeps working.

Master/detail with a FormView

Selecting a row in a grid to edit a single record elsewhere on the page is a data-source-to-data-source link, and ControlParameter expresses it declaratively:

<asp:ObjectDataSource ID="ProductDetailSource" runat="server"
    TypeName="WebFormsApp.Services.ProductCatalog" SelectMethod="Find">
    <SelectParameters>
        <asp:ControlParameter Name="id" ControlID="ProductsGrid" PropertyName="SelectedValue" Type="Int32" />
    </SelectParameters>
</asp:ObjectDataSource>

<asp:FormView ID="ProductForm" runat="server" DataSourceID="ProductDetailSource" DefaultMode="ReadOnly">
    <ItemTemplate>
        <h3><%# Eval("Name") %></h3>
        <p>Price: <%# Eval("Price", "{0:C}") %></p>
    </ItemTemplate>
</asp:FormView>

With ShowSelectButton="true" added to the grid’s CommandField, clicking Select updates ProductsGrid.SelectedValue (the Id, because of DataKeyNames), the detail source sees the new parameter value on its next select, and the FormView rebinds — all without a line of code-behind. The parameter has no default, so before the first selection the select is cancelled (CancelSelectOnNullParameter is true by default) and the FormView shows nothing; provide an EmptyDataTemplate or a DefaultValue on the parameter to cover that state. Note that the price column above deliberately omits ApplyFormatInEditMode: an edit box filled with $219.00 cannot be converted back to a decimal by the data source, so currency formatting belongs in read-only cells.
