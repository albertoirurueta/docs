Deployment

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Deployment is dotnet publish plus a host that runs the output. See Host and deploy ASP.NET Core.

dotnet publish

dotnet publish -c Release -o ./publish                 # framework-dependent (needs .NET runtime on host)
dotnet publish -c Release -r linux-x64 --self-contained # bundles the runtime, RID-specific

# size / startup options
dotnet publish -c Release -r linux-x64 -p:PublishTrimmed=true -p:PublishReadyToRun=true
dotnet publish -c Release -r linux-x64 -p:PublishAot=true      # Native AOT (Minimal APIs)

dotnet publish -c Release /t:PublishContainer               # build an OCI image, no Dockerfile
<PropertyGroup>
  <PublishReadyToRun>true</PublishReadyToRun>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>

Publish profiles (Properties/PublishProfiles/*.pubxml) capture a target’s settings for repeatable publishes. See .NET application deployment. Every deployment mode of dotnet publish (framework-dependent, self-contained, single-file, trimmed, ReadyToRun, Native AOT) is compared in Publish and Deployment Models, and building an image without a Dockerfile with /t:PublishContainer in Container Images.

IIS (Windows)

The ASP.NET Core Module forwards requests from IIS to the app. Publishing a Web SDK project emits a web.config that configures it. Use the in-process hosting model (default) unless you need out-of-process. Create an app pool with "No Managed Code". See Host ASP.NET Core on Windows with IIS.

Linux

Run Kestrel as a service behind Nginx (TLS termination + reverse proxy):

# /etc/systemd/system/shop.service
[Service]
WorkingDirectory=/var/www/shop
ExecStart=/usr/bin/dotnet /var/www/shop/Shop.Web.dll
Restart=always
Environment=ASPNETCORE_ENVIRONMENT=Production
User=www-data
server {
    listen 443 ssl;
    server_name shop.example.com;
    location / {
        proxy_pass         http://127.0.0.1:5000;
        proxy_set_header   Host $host;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
    }
}

AddWindowsService() / AddSystemd() integrate lifetime and logging with the service manager. See Host on Linux with Nginx.

Containers

FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish Shop.Web/Shop.Web.csproj -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled AS final
WORKDIR /app
COPY --from=build /app .
USER $APP_UID
ENV ASPNETCORE_HTTP_PORTS=8080
EXPOSE 8080
ENTRYPOINT ["dotnet", "Shop.Web.dll"]

Chiseled / distroless runtime images are small and have no shell; run as non-root ($APP_UID). Deploy to Azure App Service, Azure Container Apps, Kubernetes, or AWS (ECS/App Runner). See Host ASP.NET Core in Docker containers. For the Azure-side deployment mechanics of these two targets — environments, revisions, and ingress for Container Apps, or plans, deployment slots, and scaling for App Service — see Container Apps and App Service and Azure Functions. For the AWS side, see ECS and Fargate and Choosing a Compute Service.

Behind a proxy or load balancer

builder.Services.Configure<ForwardedHeadersOptions>(o =>
{
    o.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;
    o.KnownNetworks.Clear();
    o.KnownProxies.Clear();                 // then add the actual proxy IPs/ranges
});
app.UseForwardedHeaders();
app.UsePathBase("/shop");                   // if hosted under a sub-path

See Configure ASP.NET Core to work with proxy servers and load balancers.

Production config, secrets, and CI/CD

  • Configuration from environment variables / Key Vault / managed identity; no secrets in the image or repo.

  • Expose readiness/liveness endpoints for the orchestrator’s probes (see Observability).

  • A web farm must share the Data Protection key ring and set the same application name (see Security hardening).

# .github/workflows/deploy.yml
name: deploy
on: { push: { branches: [main] } }
jobs:
  build-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-dotnet@v4
        with: { dotnet-version: '10.0.x' }
      - run: dotnet test --configuration Release
      - run: dotnet publish Shop.Web -c Release -o publish
      - uses: azure/webapps-deploy@v3
        with: { app-name: shop-prod, package: publish }

Deep dive: a rolling update of the Orders API without dropped requests

A rolling update replaces instances one at a time. Requests are dropped when an old instance is killed with calls in flight, or when a new instance is sent traffic before it is ready. Both are controlled by the app and the orchestrator together.

sequenceDiagram participant LB as Load balancer participant Old as Instance v1 participant New as Instance v2 participant O as Orchestrator O->>New: start container New->>New: apply configuration, warm up O->>New: readiness probe New-->>O: 503 until ready, then 200 O->>LB: add v2 to the pool O->>Old: SIGTERM O->>LB: remove v1 from the pool Old->>Old: stop accepting, drain in-flight requests Old-->>O: exit 0 within the termination grace period

Readiness, liveness and a warm-up gate

A liveness probe says "restart me"; a readiness probe says "send me traffic". Keep them separate: liveness must not check the database, or a database outage restarts every healthy instance.

builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddDbContextCheck<AppDbContext>("orders-db", tags: ["ready"]);   // Microsoft.Extensions.Diagnostics.HealthChecks.EntityFrameworkCore

var app = builder.Build();
app.MapHealthChecks("/health/live", new HealthCheckOptions { Predicate = r => r.Tags.Contains("live") });
app.MapHealthChecks("/health/ready", new HealthCheckOptions { Predicate = r => r.Tags.Contains("ready") });
# Kubernetes container spec fragment
livenessProbe:
  httpGet: { path: /health/live, port: 8080 }
readinessProbe:
  httpGet: { path: /health/ready, port: 8080 }
  periodSeconds: 5
terminationGracePeriodSeconds: 40

Graceful shutdown

On SIGTERM the host stops accepting new connections and waits for in-flight requests and hosted services to finish, up to HostOptions.ShutdownTimeout (30 seconds by default since .NET 6). The orchestrator’s grace period must be longer than that, or the process is killed with SIGKILL mid-request:

builder.Services.Configure<HostOptions>(o => o.ShutdownTimeout = TimeSpan.FromSeconds(30));

app.Lifetime.ApplicationStopping.Register(() =>
    app.Logger.LogInformation("Draining: no new requests, finishing in-flight work"));

Long-running work should observe the CancellationToken of the request (HttpContext.RequestAborted) or of the hosted service, so that shutdown can complete inside the timeout.

Database changes: expand, then contract

During a rolling update, v1 and v2 run against the same database at once, so a migration must work for both. Split a breaking change in two releases:

  1. Expand — release N adds the new column as nullable (or a new table) and the code writes both old and new shapes.

  2. Backfill — a one-off job copies old data into the new shape.

  3. Contract — release N+1 reads only the new shape; a later migration drops the old column once no v(N-1) instance is running.

Apply the expand migration from the pipeline (dotnet ef migrations script --idempotent) before the rollout starts, so no instance has to race to migrate at startup.
