Web API Controllers

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Controller-based Web APIs give you conventions, filters, and the [ApiController] behaviors on top of routing and model binding. Choose them over Minimal APIs for large APIs that benefit from shared base classes, action filters, or an existing MVC codebase.

ControllerBase + [ApiController]

[ApiController]
[Route("api/[controller]")]
public sealed class OrdersController(IOrderService orders) : ControllerBase
{
    [HttpGet("{id:int}")]
    public async Task<ActionResult<OrderDto>> Get(int id)
    {
        var order = await orders.FindAsync(id);
        return order is null ? NotFound() : Ok(order.ToDto());
    }

    [HttpPost]
    public async Task<ActionResult<OrderDto>> Create(CreateOrderDto dto)
    {
        var created = await orders.CreateAsync(dto);
        return CreatedAtAction(nameof(Get), new { id = created.Id }, created.ToDto());
    }
}

[ApiController] enables automatic 400 responses for invalid ModelState, binding-source inference (complex types from the body, simple types from the route/query), and ProblemDetails for error status codes. See Create web APIs with ASP.NET Core.

Action return types

Return type Use

ActionResult<T>

Return either T (200) or a result helper (NotFound(), BadRequest()).

IActionResult

When only status/results matter, no typed body.

Results<Ok<T>, NotFound, ...>

Typed union; documents every response for OpenAPI (same as Minimal APIs).

T / IEnumerable<T>

Plain object, serialized with 200.

Status helpers: Ok, Created / CreatedAtAction, NoContent, NotFound, BadRequest, Conflict, UnprocessableEntity, Problem, ValidationProblem. See Controller action return types.

Content negotiation and System.Text.Json options

The framework picks an output formatter from the Accept header (JSON by default). Configure System.Text.Json:

builder.Services.AddControllers(o => o.ReturnHttpNotAcceptable = true)  // 406 instead of ignoring Accept
    .AddJsonOptions(o =>
    {
        o.JsonSerializerOptions.PropertyNamingPolicy = JsonNamingPolicy.CamelCase;
        o.JsonSerializerOptions.Converters.Add(new JsonStringEnumConverter());
        o.JsonSerializerOptions.DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull;
    })
    .AddXmlSerializerFormatters();

AddJsonOptions configures the MVC formatters. (ConfigureHttpJsonOptions is the equivalent for Minimal APIs and does not affect controllers.)

Use [Produces("application/json")] / [Consumes("application/json")] to constrain a controller, and the System.Text.Json source generator (JsonSerializerContext) for trimming/AOT and speed. Write a custom TextOutputFormatter for formats like CSV. See Format response data.

ProblemDetails error responses

Return RFC 9457 ProblemDetails / ValidationProblemDetails for machine-readable errors:

builder.Services.AddProblemDetails(o => o.CustomizeProblemDetails = ctx =>
    ctx.ProblemDetails.Extensions["traceId"] = ctx.HttpContext.TraceIdentifier);

// in an action
return Problem(title: "Payment declined", statusCode: StatusCodes.Status402PaymentRequired);

Map exceptions to problem responses centrally with IExceptionHandler — see Error Handling, Logging, and Observability and Handle errors in ASP.NET Core web APIs.

DTOs and API contracts

Expose request/response DTOs, not EF Core entities: it decouples the wire contract from the schema, prevents over-posting, and keeps navigation properties out of responses.

public sealed record OrderDto(int Id, string Customer, decimal Total, string Status);
public static class OrderMappings
{
    public static OrderDto ToDto(this Order o) => new(o.Id, o.Customer.Name, o.Total, o.Status.ToString());
}

See Data Access with EF Core for the entities these DTOs are mapped from.

CORS

builder.Services.AddCors(o => o.AddPolicy("spa", p =>
    p.WithOrigins("https://app.example.com").AllowAnyHeader().AllowAnyMethod()));
app.UseCors("spa");

See What is CORS?.

JsonPatch

Add the Microsoft.AspNetCore.JsonPatch.SystemTextJson package (.NET 10, System.Text.Json based), accept a JsonPatchDocument<T> body and call patch.ApplyTo(model); the legacy path is the Microsoft.AspNetCore.Mvc.NewtonsoftJson package with AddControllers().AddNewtonsoftJson(). See JsonPatch in ASP.NET Core web API.

Minimal APIs vs. controllers

Choose When

Minimal APIs

New, small-to-medium JSON APIs; least ceremony; fastest startup and best Native-AOT support.

Controllers

Large APIs that benefit from shared base-class logic, [ApiController] conventions, action filters (see Filters and the MVC Pipeline), or that already exist as an MVC codebase.

Both share the same routing, model binding, and hosting — the choice is about ergonomics for the app’s size and team, not capability. .http files in the project let you send requests straight from the editor for manual testing. See Choose between controller-based APIs and Minimal APIs.

Deep dive: lost updates, ETag and If-Match

Two clerks open the same order, one marks it Shipped, the other (still looking at the old state) marks it Cancelled. A plain PUT lets the second write silently overwrite the first: a lost update. HTTP has a built-in answer, optimistic concurrency with validators. The server sends an ETag identifying the version it returned; the client echoes it in If-Match when it writes; the server applies the write only if the version still matches, and otherwise answers 412 Precondition Failed.

sequenceDiagram participant A as Clerk A participant B as Clerk B participant S as OrdersController A->>S: GET /api/orders/7 S-->>A: 200 + ETag v1 B->>S: GET /api/orders/7 S-->>B: 200 + ETag v1 A->>S: PUT status Shipped, If-Match v1 S-->>A: 200 + ETag v2 B->>S: PUT status Cancelled, If-Match v1 S-->>B: 412 Precondition Failed Note over B: reloads, sees Shipped, decides again

Storing the version

EF Core can maintain the version for you with a row-version column that the database changes on every update:

public sealed class Order
{
    public int Id { get; set; }
    public string Status { get; set; } = "Placed";

    [Timestamp] public byte[] RowVersion { get; set; } = [];     // SQL Server rowversion; checked in UPDATE ... WHERE
}

public enum UpdateOutcome { Updated, NotFound, VersionMismatch }

public sealed class OrderService(ShopDbContext db)
{
    public async Task<(UpdateOutcome Outcome, Order? Order)> SetStatusAsync(
        int id, string status, byte[] expectedVersion, CancellationToken ct)
    {
        var order = await db.Orders.FindAsync([id], ct);
        if (order is null) return (UpdateOutcome.NotFound, null);

        db.Entry(order).Property(o => o.RowVersion).OriginalValue = expectedVersion;   // compare against the client's copy
        order.Status = status;

        try
        {
            await db.SaveChangesAsync(ct);
            return (UpdateOutcome.Updated, order);
        }
        catch (DbUpdateConcurrencyException)
        {
            return (UpdateOutcome.VersionMismatch, null);          // zero rows matched the version
        }
    }
}

Setting OriginalValue is what makes EF Core add the version to the UPDATE ... WHERE clause. Without it, EF Core compares against the version it just loaded, which always matches, and the protection silently disappears.

The controller

[ApiController]
[Route("api/orders")]
public sealed class OrderStatusController(OrderService orders) : ControllerBase
{
    [HttpGet("{id:int}")]
    public async Task<ActionResult<OrderStatusDto>> Get(int id, [FromServices] ShopDbContext db)
    {
        var order = await db.Orders.AsNoTracking().FirstOrDefaultAsync(o => o.Id == id);
        if (order is null) return NotFound();

        Response.Headers.ETag = $"\"{Convert.ToBase64String(order.RowVersion)}\"";   // strong validator, quoted
        return new OrderStatusDto(order.Id, order.Status);
    }

    [HttpPut("{id:int}/status")]
    public async Task<ActionResult<OrderStatusDto>> SetStatus(
        int id, SetStatusDto dto, [FromHeader(Name = "If-Match")] string? ifMatch, CancellationToken ct)
    {
        if (string.IsNullOrWhiteSpace(ifMatch))
            return Problem(title: "If-Match header is required.", statusCode: StatusCodes.Status428PreconditionRequired);

        var version = new byte[8];                                  // SQL Server rowversion is 8 bytes
        if (!Convert.TryFromBase64String(ifMatch.Trim('"'), version, out var written) || written != 8)
            return Problem(title: "Malformed If-Match value.", statusCode: StatusCodes.Status400BadRequest);

        var (outcome, order) = await orders.SetStatusAsync(id, dto.Status, version, ct);

        switch (outcome)
        {
            case UpdateOutcome.NotFound:
                return NotFound();
            case UpdateOutcome.VersionMismatch:
                return Problem(title: "The order changed since you loaded it.",
                               statusCode: StatusCodes.Status412PreconditionFailed);
            default:
                Response.Headers.ETag = $"\"{Convert.ToBase64String(order!.RowVersion)}\"";
                return new OrderStatusDto(order.Id, order.Status);
        }
    }
}

public sealed record OrderStatusDto(int Id, string Status);
public sealed record SetStatusDto([property: Required] string Status);

Three status codes carry the protocol: 428 Precondition Required when the client did not send If-Match at all (so a careless client cannot opt out of the protection), 412 Precondition Failed when the version is stale, and 200 with the new ETag on success so the client can keep editing without reloading. Both error cases use ProblemDetails (see the section above) so clients handle them like any other API error.

Testing the conflict

A controller test alone cannot prove the SQL, so test the conflict through the pipeline with a real relational provider (see the SQLite fixture in Testing):

[Fact]
public async Task Second_writer_with_a_stale_etag_gets_412()
{
    var client = factory.CreateClient();
    var first = await client.GetAsync("/api/orders/7");
    var staleEtag = first.Headers.ETag!.ToString();

    using var winner = new HttpRequestMessage(HttpMethod.Put, "/api/orders/7/status")
        { Content = JsonContent.Create(new { status = "Shipped" }) };
    winner.Headers.TryAddWithoutValidation("If-Match", staleEtag);
    Assert.Equal(HttpStatusCode.OK, (await client.SendAsync(winner)).StatusCode);

    using var loser = new HttpRequestMessage(HttpMethod.Put, "/api/orders/7/status")
        { Content = JsonContent.Create(new { status = "Cancelled" }) };
    loser.Headers.TryAddWithoutValidation("If-Match", staleEtag);          // same, now stale, version
    Assert.Equal(HttpStatusCode.PreconditionFailed, (await client.SendAsync(loser)).StatusCode);
}

The same mechanism works for GET caching: send If-None-Match with the stored ETag and answer 304 when it is unchanged. The SQLite provider has no rowversion type, so a SQLite-backed test needs a manually maintained version column (for example a Guid regenerated on each save, marked with [ConcurrencyCheck]); keep the contract the same and only the storage differs.
