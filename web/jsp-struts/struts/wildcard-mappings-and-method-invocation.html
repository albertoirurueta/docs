Wildcard Mappings & Method Invocation

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Struts 7.4.0 (released 2026-10-02) running on Apache Tomcat 11.0.26, Jakarta Servlet 6.1 and Java 21, with the configuration read against the Struts 6.0 DTD (why 6.0). Everything was verified on 2026-10-08: the facts against the Struts Core Developer Guide, the Getting Started tutorial, the security guide and the 7.4.0 source, and every example by building it into a Maven WAR with struts2-bom 7.4.0 and calling it with curl on a scratch Tomcat 11.0.26. The outputs shown are the outputs of those runs. A wildcard mapping lets one <action> element stand for many URLs, and the placeholder {1} carries the part of the URL that the wildcard matched into the method name, the class name, the results and the parameters. That power is also the page’s main hazard, because a mapping that turns request text into a method name decides which Java methods a stranger can call. The running scenario is the Bookshelf of the previous pages, now with a BookCrudAction that can list, create, edit and delete books, and a maintenance method called purge that must never be reachable from a URL.

Why Wildcards Exist

A conventional mapping names one URL, one class and one method. The Bookshelf with four operations needs four elements that differ only in a method name. A wildcard mapping states the pattern once.

Table 1. The same URL space with four hard-coded mappings and with one wildcard mapping
Approach Configuration Cost

One mapping per URL

createBook, editBook, deleteBook and the list each need their own <action> with method="create", method="edit" and so on

Grows with every new method; easy to forget one; each is explicit and safe

One wildcard mapping

<action name="*Book" method="{1}"> serves createBook, editBook, deleteBook and plain Book

Constant size; every method name that matches the pattern becomes a URL, so the allowed set must be restricted

One regular-expression mapping

<action name="/{type}/content/{title}"> serves any two-segment URL and fills two fields

Needs a different pattern matcher for the whole application; clean URLs without an extension

Wildcard mappings come from Struts 1 and its predecessors (see Struts 1 (Classic) & Migration). The Struts 1 mailreader example that the Core Developer Guide still quotes maps /edit* to Edit{1}Action. In Struts 1 the same need was met with DispatchAction, an action class whose request parameter named the method to call, and with LookupDispatchAction, which looked the method up from a button label. Struts 2 offers three replacements, in the order the framework prefers them: the method attribute with a wildcard, strict method invocation with an allowed list, and, deprecated in practice, dynamic method invocation with the bang character. See the Struts 1 part of the history page for where those ideas came from.

How a URL Is Matched

The StrutsPrepareAndExecuteFilter of the servlet filter chain hands the request to the ActionMapper. The default mapper splits the path into a namespace and an action name, removes the extension (action or none, because struts.action.extension is action,, in 7.4.0, so /crud/createBook and /crud/createBook.action are the same request) and, only when dynamic method invocation is on, splits the name at a bang. The configuration then looks the name up inside the namespace. The order of that lookup is the part that people get wrong.

flowchart TD req["GET /crud/createBook.action"] --> map["ActionMapper: namespace /crud, name createBook, extension action"] map --> dmi{"DMI on and name contains a bang?"} dmi -->|"yes"| split["name book, method create from the URL"] dmi -->|"no"| exact{"Exact action name in the namespace?"} split --> exact exact -->|"yes: no wildcard matching at all"| cfg["ActionConfig as written"] exact -->|"no"| wild["Try wildcard patterns in declared order, first match wins"] wild -->|"none matches"| nf["404: There is no Action mapped"] wild -->|"match"| sub["Copy the config and replace each placeholder with the matched text"] sub --> allowed{"Is the resulting method allowed?"} allowed -->|"no"| nf allowed -->|"yes"| proxy["ActionProxy: interceptors, then the method, then the result"] cfg --> proxy

The diagram is the whole rule: a name that has no wildcard is found first and is never compared with the patterns.

The Pattern Tokens

A pattern is an action name that contains a special token. A name without a token is a literal and is matched by plain lookup.

Table 3. Tokens of the default wildcard matcher (class WildcardHelper, 7.4.0)
Token Matches Example

*

Zero or more characters except the slash

docs/* matches docs/readme but not docs/a/b

**

Zero or more characters including the slash

all/** matches all/a/b and fills {1} with a/b

\x

The backslash escapes the next character, so \* is a literal asterisk

An action name with an asterisk cannot be requested anyway: struts.allowed.action.names accepts only letters, digits and the characters ., _, !, /, -

{N} in an attribute

The text matched by the N-th wildcard, N from 1 to 9

method="{1}"

{0} in an attribute

The whole matched request path

generic mapping, {0} printed generic mapping, anything for /order/anything

Two properties of the matching are easy to forget. First, a wildcard is not greedy: it matches up to the first occurrence of the text that follows it. Second, the loose-match rule: when the pattern ends in a wildcard that follows a literal character, such as Book_*, the pattern is also tried without those last two characters, so Book matches Book_* with an empty {1}. That rule exists to support the old *!* form with an optional part, and it is what lets the Bookshelf call Book and Book_create through one mapping.

The Bookshelf Wildcard Mapping

The scratch application has this action class. execute lists, create, edit and delete are the operations, and purge is the maintenance method that no URL may reach. Setters that carry @StrutsParameter are the only ones that request parameters may fill (the page Parameter Injection and @StrutsParameter covers that annotation); the class below has none that matter yet.

The Bookshelf action: four operations and one method that must stay private to the application
package org.example.bookshelf;

import org.apache.struts2.ActionSupport;

public class BookCrudAction extends ActionSupport {
    private String message = "unset";

    @Override
    public String execute() {
        if ("unset".equals(message)) {
            message = "list";
        }
        return SUCCESS;
    }

    public String create() { message = "create"; return SUCCESS; }
    public String edit()   { message = "edit";   return SUCCESS; }
    public String delete() { message = "delete"; return SUCCESS; }

    /** Maintenance method that was never meant to be reachable from a URL. */
    public String purge()  { message = "purge: every book deleted"; return SUCCESS; }

    public String getMessage() { return message; }
    public void setMessage(String message) { this.message = message; }
}

Source: Struts Core Developer Guide — Action Configuration, Action Methods

The view prints the message field, so the examples below show which method ran. It also prints four fields (type, title, author and id) that are empty in most requests; the outputs on this page keep only the interesting part of the line.

/WEB-INF/views/book.jsp: print the name of the method that ran
<%@ page contentType="text/plain; charset=UTF-8" %><%@ taglib prefix="s" uri="/struts-tags" %>method=<s:property value="message"/> type=<s:property value="type"/> title=<s:property value="title"/> author=<s:property value="author"/> id=<s:property value="id"/>

Source: Struts Tag Developers Guide — property

One wildcard mapping that serves the list, create, edit and delete URLs
<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE struts PUBLIC
        "-//Apache Software Foundation//DTD Struts Configuration 6.0//EN"
        "https://struts.apache.org/dtds/struts-6.0.dtd">
<struts>
    <package name="crud" extends="struts-default" namespace="/crud">
        <action name="*Book" class="org.example.bookshelf.BookCrudAction" method="{1}">
            <result>/WEB-INF/views/book.jsp</result>
            <allowed-methods>create,edit,delete</allowed-methods>
        </action>
    </package>
</struts>
Calling the mapping (output of the scratch run on Tomcat 11.0.26, trimmed to the method= part)
$ curl -s http://localhost:18080/g8wild/crud/createBook.action
method=create
$ curl -s http://localhost:18080/g8wild/crud/editBook.action
method=edit
$ curl -s http://localhost:18080/g8wild/crud/deleteBook.action
method=delete
$ curl -s http://localhost:18080/g8wild/crud/Book
method=list
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18080/g8wild/crud/purgeBook.action
404

Source: Struts Getting Started — Wildcard Method Selection

The last request shows the point of the allowed list. purgeBook matches the pattern, the placeholder would turn into purge, and the framework refuses because purge is neither the method attribute of a literal mapping nor on any allowed list. The response is the ordinary "no action" 404, with the text There is no Action mapped for namespace [/crud] and action name [purgeBook].

The URL /crud/Book has nothing in front of Book, so {1} is empty. An empty method becomes execute, and execute is on the default allowed list (see Where the Allowed List Comes From), which is why the plain Book URL lists the books.

Where {1} Can Be Used

The substitution is done by ActionConfigMatcher.convert on a copy of the matched configuration. In 7.4.0 it replaces the placeholders in the following places and in no others.

method attribute of <action>

method="{1}"

Chooses the Java method; checked against the allowed methods

class attribute of <action>

Chooses the action class; see A Class Chosen by a Wildcard and the OGNL Allowlist for the allowlist consequence

name of a <result>, and the result type

A result can be a whole redirect target. The mapping below sends /go/toabout to the action about of the /pages namespace.

{1} inside a redirectAction result
<package name="go" extends="struts-default" namespace="/go">
    <action name="to*">
        <result type="redirectAction">
            <param name="namespace">/pages</param>
            <param name="actionName">{1}</param>
        </result>
    </action>
</package>
The redirect answered by the scratch app
$ curl -s -i http://localhost:18080/g8wild/go/toabout | grep -i "HTTP/\|location"
HTTP/1.1 302
Location: /g8wild/pages/about.action

Source: Struts Core Developer Guide — Wildcard Mappings

A mapping with no class at all, the last of these placeholder uses, is the catch-all that serves static-looking pages by name. The framework fills in ActionSupport as the default class, and the result location is built from the matched name.

A catch-all that maps /pages/about to /WEB-INF/views/about.jsp
<package name="pages" extends="struts-default" namespace="/pages">
    <action name="*">
        <result>/WEB-INF/views/{1}.jsp</result>
    </action>
</package>
Output of the scratch run
$ curl -s http://localhost:18080/g8wild/pages/about
page about rendered
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18080/g8wild/pages/secret
404

Source: Struts Core Developer Guide — Action Configuration, Action Default

A single * cannot contain a slash, so /pages/../x cannot be built from the name, and the views stay under WEB-INF. A ** in the same position would remove that protection, so do not use it in a result location. The catch-all belongs at the end of the configuration of its namespace, as the documentation says, because anything declared after it that it also matches is never reached (see Which Pattern Wins).

Once a wildcard mapping exists, the framework treats the expanded name as an action of its own. The Core Developer Guide says that such a "virtual" mapping can have its own validations, message resources and type converters, just as a hand-written mapping can.

Which Pattern Wins

An exact name always beats a pattern, and a request that matches an exact name never reaches the wildcard matcher. Among several patterns that match, the order of declaration decides, and here the official documentation and the framework disagree.

Table 5. What the sources say about patterns that overlap
Source Statement

Core Developer Guide, Wildcard Mappings

"If more than one pattern matches the last one wins, so less specific patterns must appear before more specific ones"

AbstractMatcher, 7.4.0 source

"Patterns will be matched in the order they were added. The first match wins, so more specific patterns should be defined before less specific patterns"; the loop stops at the first match

The scratch run

The first declared pattern that matches wins, so the guide’s sentence is wrong for 7.4.0

Two packages with the same two patterns in opposite orders show it.

The generic pattern first, then the specific one (namespace /order), and the reverse (namespace /order2)
<package name="order" extends="struts-default" namespace="/order">
    <action name="*" class="org.example.bookshelf.BookCrudAction">
        <param name="message">generic mapping, {0}</param>
        <result>/WEB-INF/views/book.jsp</result>
    </action>
    <action name="book*" class="org.example.bookshelf.BookCrudAction">
        <param name="message">book* mapping, {1}</param>
        <result>/WEB-INF/views/book.jsp</result>
    </action>
    <action name="bookshelf" class="org.example.bookshelf.BookCrudAction">
        <param name="message">exact mapping</param>
        <result>/WEB-INF/views/book.jsp</result>
    </action>
</package>
<package name="order2" extends="struts-default" namespace="/order2">
    <action name="book*" class="org.example.bookshelf.BookCrudAction">
        <param name="message">book* mapping, {1}</param>
        <result>/WEB-INF/views/book.jsp</result>
    </action>
    <action name="*" class="org.example.bookshelf.BookCrudAction">
        <param name="message">generic mapping, {0}</param>
        <result>/WEB-INF/views/book.jsp</result>
    </action>
</package>
Output of the scratch run
$ curl -s http://localhost:18080/g8wild/order/bookcase
method=generic mapping, bookcase
$ curl -s http://localhost:18080/g8wild/order/bookshelf
method=exact mapping
$ curl -s http://localhost:18080/g8wild/order2/bookcase

$ curl -s http://localhost:18080/g8wild/order2/anything

Source: Struts Core Developer Guide — Wildcard Mappings

So the rule to apply is the one in the framework’s own javadoc: write the specific pattern first and the catch-all last. Physical order is a property of XML; the Convention plugin has no such order, because annotated classes are found by scanning. Since Struts 7.3.0 the names of annotated wildcard actions are sorted most specific first before they are registered (WW-3784), with these keys in order: fewer ** tokens, fewer wildcard tokens (a *, a ** run or a {var} group), more literal characters, then alphabetical order as a tie-breaker. Struts 7.3.0 applied the ** key third and 7.4.0 moves it to the first place, so a/*/* is registered before a/** (WW-5743). XML mappings are unaffected and keep their declared order.

Non-Greedy Matching and Several Wildcards

A wildcard stops at the first occurrence of what follows it.

A mapping that works for ListAccounts and fails for ListSponsors, and two wildcards in one name
<package name="star" extends="struts-default" namespace="/star">
    <action name="docs/*" class="org.example.bookshelf.BookCrudAction">
        <param name="message">docs/* got {1}</param>
        <result>/WEB-INF/views/book.jsp</result>
    </action>
    <action name="all/**" class="org.example.bookshelf.BookCrudAction">
        <param name="message">all/** got {1}</param>
        <result>/WEB-INF/views/book.jsp</result>
    </action>
    <action name="List*s" class="org.example.bookshelf.BookCrudAction">
        <param name="message">List*s got {1}</param>
        <result>/WEB-INF/views/book.jsp</result>
    </action>
    <action name="two/*/*" class="org.example.bookshelf.BookCrudAction">
        <param name="message">two got {1} and {2}</param>
        <result>/WEB-INF/views/book.jsp</result>
    </action>
</package>
Output of the scratch run (slashes in action names need the constants of Slashes in Action Names)
$ curl -s http://localhost:18080/g8wild/star/docs/readme
method=docs/* got readme
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18080/g8wild/star/docs/a/b
404
$ curl -s http://localhost:18080/g8wild/star/all/a/b
method=all/** got a/b
$ curl -s http://localhost:18080/g8wild/star/ListAccounts

$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18080/g8wild/star/ListSponsors

$ curl -s http://localhost:18080/g8wild/star/two/a/b

Source: Struts Core Developer Guide — Wildcard Mappings, non-greedy matching

ListSponsors fails for the reason the guide gives: the pattern List*s stops at the first s, so {1} becomes Spon and the configuration that results is ListSpons, which does not exist. Where a name can legitimately contain the following letter, use the regular-expression matcher of Regular-Expression Patterns.

Prefix and Postfix Styles

The Core Developer Guide shows two naming styles for wildcard methods: the method as a prefix of the action name (*Book, so createBook) and the method as a postfix after an underscore (Book_*, so Book_create). The postfix style reads like a URL with a verb and is the one the loose-match rule was written for.

The postfix style
<package name="postfix" extends="struts-default" namespace="/postfix">
    <action name="Book_*" class="org.example.bookshelf.BookCrudAction" method="{1}">
        <result>/WEB-INF/views/book.jsp</result>
        <allowed-methods>create,edit</allowed-methods>
    </action>
</package>
Output of the scratch run
$ curl -s http://localhost:18080/g8wild/postfix/Book_create
method=create
$ curl -s http://localhost:18080/g8wild/postfix/Book
method=list
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18080/g8wild/postfix/Book_purge
404

Source: Struts Core Developer Guide — Action Configuration, Wildcard Method

Slashes in Action Names

By default an action name has no slash: /admin/book/42 is read as namespace /admin/book, name 42. The Core Developer Guide’s section "Parameters after the action name" shows how to keep the rest of the path in the name. Two constants are needed.

The two constants that make book/* and all/** possible
<constant name="struts.enable.SlashesInActionNames" value="true"/>
<constant name="struts.mapper.alwaysSelectFullNamespace" value="false"/>

The second constant matters because struts.mapper.alwaysSelectFullNamespace is true in the 7.4.0 default.properties (a change of the 6 to 7 line). With it set to true the mapper takes the whole path before the last slash as the namespace and never looks for a shorter namespace that has a longer action name.

The same URLs with and without the constants (output of the scratch runs g8wild and g8wildns)
$ curl -s http://localhost:18080/g8wild/admin/book/42
method=book/42 id=42
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18080/g8wildns/admin/book/42
404
$ curl -s http://localhost:18080/g8wildns/admin/book/42 | grep -o "There is no Action[^.]*"
There is no Action mapped for namespace [/admin] and action name [42] associated with context path [/g8wildns]
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:18080/g8wild/admin/book/42/x
404

Source: Struts Core Developer Guide — Wildcard Mappings, Parameters after the action name

The constant struts.enable.SlashesInActionNames changes the whole application, not one package. The Core Developer Guide links the side effects to WW-1383, and the validation-file naming for names with slashes is covered on the page Validation. The related constant struts.allowed.action.names holds the regular expression that an action name must match; the default is [a-zA-Z0-9._!/\-]*, and a name that does not match is answered with the default action.

Strict Method Invocation

Strict method invocation (SMI) is the rule that decides which Java methods a request may run. It replaces the older "strict DMI" and applies to every way of selecting a method: a method attribute with placeholders, a bang URL and a method: parameter. The check is made by ActionConfig.isAllowedMethod: a method is allowed when it is the method written in the mapping, when it equals execute for a mapping without a method, or when it is on the allowed list of the action.

The four results teach different things.

  • bare/createBook is refused: with no list, create is not allowed, because the package declares no <allowed-methods> and create is not on the default list.

  • bare/deleteBook works with no entry anywhere, because delete is on the global list that struts-default declares. A method called delete is allowed by default in every package that extends struts-default.

The DTD Order of allowed-methods

The DTD declares the content of <action> as ((param|result|interceptor-ref|exception-mapping)*,allowed-methods?). The element <allowed-methods> must therefore come last. An application whose element is first does not start. Tomcat reports the failure of the filter, with the cause below, and every request then answers 404.

Dynamic Method Invocation

Dynamic method invocation (DMI) lets the caller name the method in the URL. The bang form book!create.action runs the book mapping with the method create. The parameter form sends a request parameter whose name starts with method:, as in book.action?method:create=x, and the value is ignored. Struts uses the second form for buttons: <s:submit method="create"/> renders as name="method:create".

The Core Developer Guide explains why the framework does not like it. The code scans the action name for a bang and then tricks the framework into calling another method while the configuration is that of execute, including its validation. The framework "believes" it is running execute. The wildcard method feature is implemented differently: the framework behaves as if the mapping Category!create had been written in the file, so the virtual mapping has its own validations, messages and type converters. For that reason the guide says wildcard method selection is preferred. A DMI request also reaches a method that no mapping mentions, and the security guide recommends disabling DMI to avoid XSS in the automatically generated error pages that contain the action name.

false by default. The action: prefix, as in name="action:other", is ignored until it is true; action:name!method additionally needs DMI

Four properties of this matcher are not in the guide, and the scratch runs showed them.

  • A {title} with no regular expression matches any text including slashes, so /fiction/content/a/b gives the title a/b. Add a regular expression such as {title:[^/]+} where that is wrong.

  • The * and ** tokens do not exist in this mode. The matcher treats a name with no { as a literal, so every wildcard mapping of the earlier sections would stop working if struts.patternMatcher were switched on its own.

  • A pattern whose regular expression contains braces, such as {year:[0-9]{4}}, stops the application from starting. The matcher ends the expression at the first closing brace, builds the regular expression year/([0-9](.*?) and Tomcat reports PatternSyntaxException: Unclosed group. Write [0-9]+ or \d+, or repeat the class.

  • Only one pattern matcher exists per application. A project that needs wildcards in some packages and regular expressions in others needs a custom PatternMatcher, as the guide says.

Path Values and Parameter Binding

A value that the pattern extracts reaches the action in one of two ways, and the two ways have different security rules.

  1. As <param> elements. A {1} in <param name="id"> is a static parameter of the mapping. The staticParams interceptor sets it before the parameters interceptor runs and it does not need @StrutsParameter.

  2. As named values ({type} in the regex matcher, {id} in a namespace). In 7.4.0 these are appended to the static parameters of the mapping (struts.matcher.appendNamedParameters is true), so they also bind without an annotation.

Both ways are different from a query-string parameter, which binds only through a setter annotated with @StrutsParameter. The scratch app proves the difference and a consequence.

A class with an unannotated setter, mapped by a path variable
public class UnannotatedBookAction extends ActionSupport {
    private String type;
    public String getType() { return type; }
    public void setType(String type) { this.type = type; }
    public String getMessage() { return "type=" + type; }
}

A Class Chosen by a Wildcard and the OGNL Allowlist

A wildcard can build the class name, as in class="org.example.bookshelf.Edit{1}Action", and the default configuration comment of Struts 7 still suggests <action name="*/*" method="{2}" class="actions.{1}">. In Struts 7 that mapping fails by default. The OGNL allowlist (struts.allowlist.enable is on by default from 7.0) allows the classes that the configuration names, and a class that appears only through a placeholder is not named anywhere. The framework calls execute() through OGNL and the call is blocked.

The /admin/editAuthor request in the default scratch app, where EditAuthorAction is reached only through {1}

$ curl -s http://localhost:18080/g8wild/admin/editAuthor | grep -o "NoSuchMethodException[^<]*"

The failure shows as an HTTP 500 and a NoSuchMethodException for a method that exists. An application that logs at WARN level also shows a warning from SecurityMemberAccess that names the blocked class and recommends struts.allowlist.classes or struts.allowlist.packageNames, which is the clue to read. The better design avoids the problem: a mapping whose class comes from request text means that the request chooses which Java class to run, so allowlist a small package of such classes and keep other classes out of it.

Wildcards in the Convention Plugin

The Convention plugin (see Convention Plugin & Annotations) builds mappings from annotations. A wildcard name in @Action is a wildcard mapping like any other, and the plugin’s registration order has no relation to the source order of the classes. That was a bug until 7.3.0: a broad pattern registered before a narrower one that it also matches could shadow it, in an order that differed between JVMs (WW-3784). The sort rule of Which Pattern Wins is the fix, and 7.4.0 corrects the position of the ** key (WW-5743).

Version Change

2.5

7.3.0

Annotated wildcard actions are sorted most specific first before registration (WW-3784)

7.4.0

The path-spanning ** key moves to the first place of that sort (WW-5743); Struts 7.4.0 released 2026-10-02; struts.enable.DynamicMethodInvocation remains false
