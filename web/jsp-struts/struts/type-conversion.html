Type Conversion

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Apache Struts 7.4.0 (released 2026-10-02) running on Apache Tomcat 11.0.26 and Java 21, the combination on which every example was built, deployed and requested; the facts were checked on 2026-10-08 and 2026-10-10 against the Core Developer Guide pages on https://struts.apache.org/core-developers/, the 7.4.0 Javadoc, the source files tagged STRUTS_7_4_0 and the classes inside the 7.4.0 struts2-core jar (javap). HTTP carries text and nothing else: a form field named pages arrives as the string "12", a date arrives as whatever the user typed, a checkbox arrives as "on" or not at all. Type conversion is the part of Struts that turns those strings into the int, BigDecimal, Date, enum, List or domain object that the action property declares, and turns the property back into a string when a form or a result renders it. Most of the time it is invisible; this page is about the moments when it is not: which formats are accepted, how the request locale changes them, how to teach Struts a new type, how collections and maps of beans are filled from indexed parameter names, and what happens, and what the visitor sees, when a value cannot be converted. The running scenario is the Bookshelf catalogue of this part: a book has a page count, a publication date, a list price, an ISBN and a shelf code. The related pages of this section are ValueStack, ActionContext & OGNL, Parameter Injection and @StrutsParameter, Validation, Localization and i18n and ModelDriven, Preparable & CRUD.

Where Conversion Happens

Conversion is not an interceptor. It is a service that the OGNL layer calls whenever it assigns a value to a property whose type differs from the type of the value. The params interceptor reads the request parameters (the interceptor stack page lists where it sits in defaultStack), asks the value stack to set each one on the action, and the value stack asks the converter to produce a value of the right type. When the converter cannot, it does not throw to the caller: it records the failure in a map called conversionErrors of the ActionContext and moves on to the next parameter. A later interceptor, conversionError, converts those records into field errors, and workflow decides, from the presence of field errors, that the input result must render. The same machinery runs in the other direction when a tag such as <s:textfield name="listPrice"/> reads the property back: the value is converted to a string for the page.

Reading the output line by line shows the rules:

  • A single value goes to a scalar; several values with the same name go to an array or a collection (tags, ratings, keywords), and each element is converted individually.

  • A String is never split: keywords=x,y is one element, x,y. Splitting on commas is the job of the page, not of the framework.

  • char takes the first character of the string (ABC becomes A), and an empty string leaves the default.

  • Numbers keep their precision: BigInteger and BigDecimal have no 64-bit limit, and listPrice=1234.50 keeps the trailing zero.

  • An enum is matched by constant name and is case sensitive: format=HARDCOVER works, format=hardcover is a conversion error (observed).

  • The list for keywords is an XWorkList, a framework ArrayList subclass that supports the auto-growth of indexed names described in Collections and Maps.

  • A Date is parsed with the formats listed in Dates, and a LocalDate with the ISO form only.

Booleans, Checkboxes and Blank Values

Boolean conversion is Boolean.valueOf of the string: only the text true, in any letter case, is true (observed with Struts 7.4.0, where the converter’s doConvertToBoolean does exactly that). Everything else, including the on that browsers send for a checkbox without a value attribute, is false and is not an error:

available=on        -> available = false (Boolean)     fieldErrors = {}
featured=yes        -> featured = false (Boolean)
featured=1          -> featured = false (Boolean)
available=TRUE      -> available = true (Boolean)
available=true&available=false  -> available = true   (the first value of a repeated name wins for a scalar)
featured=           -> featured = false (Boolean)      (an empty string is not null for a Boolean)

Source: Core Developer Guide — Type Conversion, Built in Type Conversion Support

The consequence for forms is the classic checkbox problem: an unchecked checkbox sends nothing, so the property is never touched and keeps its previous (possibly true) value. The checkbox interceptor of defaultStack handles it: a hidden companion field named __checkbox_featured sets the property to false when the checkbox itself is absent. With the companion field present and the checkbox absent, the observed result is featured = false; with both present and set to true, featured = true. The <s:checkbox> tag renders the companion field for you; the tags page of this section covers it.

Numbers and the Request Locale

NumberConverter converts with java.text.NumberFormat for the locale of the request: the locale chosen by the i18n interceptor (from request_locale, the session or the browser’s Accept-Language). That makes the decimal and grouping separators locale dependent, in two different ways for two kinds of target:

Three things to remember. A decimal comma typed by a visitor whose locale is en-US is not an error: it is dropped as a grouping separator and 1,5 becomes fifteen. The primitive int and long go through the plain DefaultTypeConverter (no grouping), whereas the wrapper types and BigDecimal use NumberFormat. And the locale is the one the framework resolved, which is why a form and its action must agree on how the locale is chosen (the page Localization and i18n covers the i18n interceptor). For prices the safest design is a BigDecimal property, an explicit NumberFormat-aware validation rule, and the same locale for rendering and parsing.

Two behaviours deserve a warning. And the result of a numeric short date depends on the locale of the request, as the same value 02/10/2026 is 2 October for a visitor on en-GB and 10 February for en-US (the SHORT pattern decides which field is the month). For forms that matter, define one format and use it for input and output: a text key struts.date.format in the global resource bundle puts that format first, or a custom converter (see below) owns the format completely.

The java.time types are handled separately: LocalDateTime, LocalDate and LocalTime are parsed with ISO_LOCAL_DATE_TIME, ISO_LOCAL_DATE and ISO_LOCAL_TIME (preceded by the global format when one is defined), and OffsetDateTime with ISO_OFFSET_DATE_TIME. That is why added=2026-10-02 works and added=02/10/2026 fails with a conversion error (observed). The guide does not mention java.time at all.

Arrays, Collections and String Properties

For an array or a collection property the converter converts each submitted value to the element type and builds the container: an array of the property’s type, a HashSet for Set, a TreeSet for SortedSet and an XWorkList (a framework ArrayList subclass) for List and Collection (read from CollectionConverter in the 7.4.0 source). When the element type cannot be determined the guide says elements are treated as String. The Set<String> genres of CollectionAction collapses duplicates:

genres=a  genres=b  genres=a   ->   genres = [a, b]
ratings=1  ratings=x           ->   ratings stays null; fieldErrors = {ratings=[...]}   (one bad element rejects the array)

Source: Core Developer Guide — Type Conversion, Built in Type Conversion Support

A property of type String receives the raw parameter; an Object or Number property that already holds a compatible value is left alone. The framework also converts to Class (by Class.forName) and to Calendar; both are rarely useful for request input and Class conversion from request text is a reason to keep the allowlist of the OGNL layer switched on (the page Security Hardening covers it).

Parameter Names, OGNL and Null Property Handling

The guide gives the central rule in one sentence: there is no need to capture form values in intermediate strings and primitives; name the inputs with OGNL expressions and the framework reads and writes the properties of the objects they address, converting on the way. person.name means getPerson().setName(...). The consequences, each verified on the Bookshelf:

  • The target of a dotted name is created when it is null. On NullAction the property review is declared Review review; (never assigned), and review.text=hi produces a Review (the framework calls the no-argument constructor and setReview), then sets the text. A setReview method must exist, and so must the getter used for the lookup.

  • An object that already exists is never replaced. ready is initialised in the field declaration and ready.stars=4 sets a property on the existing instance.

  • An interface cannot be created. rating is declared as Rateable (an interface) and is null, so rating.stars=3 is silently discarded.

public class NullAction extends ActionSupport {
    private Review review;                    // class with a public no-arg constructor
    private Rateable rating;                  // interface
    private Review ready = new Review();      // already created

    @StrutsParameter(depth = 1) public Review getReview() { return review; }
    public void setReview(Review v) { review = v; }
    @StrutsParameter(depth = 1) public Rateable getRating() { return rating; }
    public void setRating(Rateable v) { rating = v; }
    @StrutsParameter(depth = 1) public Review getReady() { return ready; }
    public void setReady(Review v) { ready = v; }
    // report() and execute() omitted
}

The guide spells out the rules: a property declared exactly as Collection or List gets an ArrayList, a Map gets a HashMap, and a bean with a no-argument constructor is built through the ObjectFactory. Null creation is switched on only while the params interceptor runs (the context key CREATE_NULL_OBJECTS), so reading review in an action method does not create one. The @StrutsParameter(depth = 1) on the getters is what permits the request to reach one level below review: the depth rules belong to the page Parameter Injection and @StrutsParameter. A conversion error inside the nested object is reported with the full dotted name, review.stars (observed: review.stars=x gives the field error review.stars).

The guide recommends creating the target objects in the constructor or in a prepare() method when they should not be built on demand, and notes that the framework "will not instantiate an object if an instance already exists". It also gives the naming advice for lists and maps: use index notation (people[0].name, friends['patrick'].name), and for a multiple select box name the element people.name so that the framework creates one Person per selected item.

Creating a Custom Type Converter

When the built-in rules are not right, or the target is a type Struts has never heard of, an application writes a converter. The guide’s recipe is to extend org.apache.struts2.util.StrutsTypeConverter: two methods, one for each direction. The Bookshelf has an Isbn value type (a thirteen digit string with a canonical hyphenated form):

public class Isbn {
    private final String digits;
    public Isbn(String digits) { this.digits = digits; }
    public String getDigits() { return digits; }
    @Override public String toString() { return "Isbn[" + digits + "]"; }
}

public class IsbnConverter extends StrutsTypeConverter {

    @Override
    public Object convertFromString(Map context, String[] values, Class toClass) {
        String text = values[0].replace("-", "").trim();
        if (text.length() != 13 || !text.chars().allMatch(Character::isDigit)) {
            throw new TypeConversionException("not an ISBN-13: " + values[0]);
        }
        return new Isbn(text);
    }

    @Override
    public String convertToString(Map context, Object o) {
        String d = ((Isbn) o).getDigits();
        return d.substring(0, 3) + "-" + d.substring(3, 4) + "-" + d.substring(4, 6) + "-"
                + d.substring(6, 12) + "-" + d.substring(12);
    }
}

Source: Core Developer Guide — Type Conversion, Creating a Type Converter

Source: Struts Javadoc — StrutsTypeConverter

The points of the contract:

  • convertFromString(Map context, String[] values, Class toClass) receives all the submitted values of the parameter as an array (a repeated name gives several), and toClass is the declared type of the property. A converter that serves one type usually reads values[0].

  • convertToString(Map context, Object o) is called when a tag or a result needs the property as text, for example <s:property value="isbn"/> or the value of a text field. Without it, the text of an Isbn would be its toString().

  • StrutsTypeConverter extends DefaultTypeConverter, which implements the TypeConverter interface of the framework. The base class also offers the hook performFallbackConversion, which the guide describes as a fall-back for when the conversion of the converter fails; by default it delegates to the superclass conversion. A converter that does not need the two-way contract can implement TypeConverter directly, or extend DefaultTypeConverter and override convertValue, and signal "not my type" with TypeConverter.NO_CONVERSION_POSSIBLE.

  • To report a bad value, throw TypeConversionException (or, as the guide puts it, XWorkException). The message is for the log, not for the visitor: the visitor sees the text of the xwork.default.invalid.fieldvalue key (see Conversion Errors).

  • The context map is the OGNL context; DefaultTypeConverter offers the protected method getLocale(context), which returns the locale of the current ActionContext (and falls back to the configured locale provider), so a converter can follow the request locale like the built-in ones.

  • The converter should be stateless and thread safe, because the framework may reuse one instance for every request.

The same converter on a model that contains a second kind of value, a page range 10-20, shows the pattern for a value that spans several fields of the target:

public record PageRange(int from, int to) {
    public int getFrom() { return from; }
    public int getTo() { return to; }
    @Override public String toString() { return from + "-" + to; }
}

public class PageRangeConverter extends StrutsTypeConverter {
    @Override
    public Object convertFromString(Map context, String[] values, Class toClass) {
        String[] parts = values[0].split("-");
        try {
            if (parts.length != 2) {
                throw new TypeConversionException("expected from-to");
            }
            return new PageRange(Integer.parseInt(parts[0].trim()), Integer.parseInt(parts[1].trim()));
        } catch (NumberFormatException e) {
            throw new TypeConversionException(e.getMessage());
        }
    }

    @Override
    public String convertToString(Map context, Object o) { return o.toString(); }
}

Collections and Maps

A form often edits several objects at once: the three books of a wish list, a table of notes keyed by book id. Struts supports this through the index notation of OGNL names and through the Element_, Key_, KeyProperty_ and CreateIfNull_ rules of a -conversion.properties file. The ObjectTypeDeterminer reads those rules (the default implementation is DefaultObjectTypeDeterminer; a custom one can be registered), and where the property is declared with generics the determiner reads the type argument.

The guide’s caveat applies to a Set: equals and hashCode of the element must not rest only on the id, or two new elements, both with a null id, collapse into one.

An index is an invitation to allocate memory, so the growth is limited. The constant struts.ognl.autoGrowthCollectionLimit (it replaced the deprecated xwork.autoGrowCollectionLimit) caps the highest index an indexed name can create. The limit exists to prevent a denial of service by a parameter named books[2000000000].title. A form that really needs more rows raises it in struts.xml: <constant name="struts.ognl.autoGrowthCollectionLimit" value="1024"/>. Note that going over the limit is silent: the data is lost without a conversion error or a log line at the default level, so an unexpectedly empty list is worth checking against this limit.

What Does Not Convert

  • A map whose key cannot be converted does not report an error: notes[x]=bad with Map<Long,String> leaves notes empty (observed; compare books[0].pages=zz, which is reported).

  • An array of beans does not grow: picks[1].title=P on a pre-sized Book[3] left every element null (observed with @StrutsParameter(depth = 2) on the getter). Use a List<Book> for repeated beans.

  • The elements of a raw List are String when no Element_ rule is present (the guide: "it is assumed to be a String").

  • A property declared with a custom interface cannot be instantiated (the rating example above); initialise the field or create the object in a prepare() method.

  • Generics lost to erasure break conversion in abstract hierarchies. The guide’s example is Measurement<T extends Enum> with a setter setUnits(T): the signature after erasure is setUnits(java.lang.Enum), the framework tries to instantiate Enum and fails with IllegalArgumentException: java.lang.Enum is not an enum type. The fix is to work around the erasure with a property of the concrete type. The guide’s example was not run here; the rule it states (that the converter sees only the erased parameter type) is the one the numbers above follow.

Three details of the annotations, taken from the Struts 7.3.0 changes and the guide:

  • Key derivation. Until 7.3.0 the rule prefix was added automatically only for annotations on methods; a class-level @Conversion(conversions = ...) had to write key = "CreateIfNull_users". Conversion Errors

A conversion error does not stop a request; it leaves a trail. This section follows that trail from the converter to the form, with the Bookshelf’s EditAction behind a form of four fields.

The conversionErrors Map and the conversionError Interceptor

Each failed conversion is stored in the map conversionErrors of the ActionContext, keyed by the property name, with the rejected value and the target class. Nothing is reported yet. The interceptor conversionError (class StrutsConversionErrorInterceptor in struts-default.xml, a subclass of ConversionErrorInterceptor) reads the map after params has run and, for each entry, if the action is ValidationAware:

  • adds a field error with the text of the key xwork.default.invalid.fieldvalue (the default text of 7.4.0 is Invalid field value for field "{0}".) or the per-field override invalid.fieldvalue.<field>;

  • remembers the original value, so that any later read of the property from a tag returns what the visitor typed, not the value in the action (abc stays abc, not 0);

  • does nothing for a value that is null, the empty string or an array holding only the empty string, which is the variant that the Struts subclass adds so that an empty text field is not reported as an error.

The interceptor has no parameters of its own, extends MethodFilterInterceptor (so includeMethods and excludeMethods work) and is part of basicStack, defaultStack and paramsPrepareParamsStack. After it, validation can add more errors, and workflow returns input if there are any.

With both the interceptor and the validator the field gets two messages: the generic one from conversionError and the validator’s own. The Struts constant struts.validators.skipValidatorsOnConversionError (default false in 7.4.0; the Version Notes of 7.3.0 list the ticket WW-2934, "conversion error should short-circuit all validators") skips the other validators of a field that failed to convert, to avoid a second message of a "required" or "range" rule for a value that never became a number; as the comment of default.properties says, the field’s own conversion validator still runs. What a Conversion Error Does Without an input Result

Because workflow returns input when there are field errors, a mapping without an input result (or with the action’s execution still reachable) fails in the way the page Exception Handling and Global Results shows: with a global java.lang.Exception mapping the failure to find the input result is swallowed into the polite error page with HTTP 200, which is a confusing way to learn that an id=abc was typed. Map input for every action that receives request parameters (see Exception Handling and Global Results).

Inconsistencies in the Official Documentation

Collected while running the examples against 7.4.0; none changes behaviour, but each can mislead:

  • The Type Conversion page says dates use "the SHORT format for the Locale"; DateConverter tries eight formats and java.time types use ISO formats (see Dates).

  • The page says a blank string "cannot be set on a BigDecimal or BigInteger"; in 7.4.0 a blank string gives null without an error (observed).

  • The Null Property Handling section refers to com.opensymphony.xwork2.interceptor.ParametersInterceptor; the class is org.apache.struts2.interceptor.parameter.ParametersInterceptor in 7.x. The same section also says "set it by calling setUsers() and then finally called getUsers().setName()" for the person example (the setter is setPerson).

  • The Advanced Example listing uses <stextfield name="beanList(%{bean.id}).name" /> (the tag prefix is missing a colon) and id="bean" on s:iterator (the retired attribute; var is current).

  • The TypeConversion Annotation page’s last example writes property = "java.util.Date"; the 7.4.0 annotation has no attribute property (its attributes are key, type, rule, converter, converterClass and value, per javap), and the page’s parameter table lists key and value but describes value only for KEY_PROPERTY.

  • The parameter table of the TypeConversion Annotation page marks converter as "DEPRECATED: either this or value" while the Javadoc of the annotation in the 7.4.0 jar carries defaults for every attribute (key and converter and value are the empty string, converterClass is XWorkBasicConverter); the example converterClass = String.class for an ELEMENT rule shows that the attribute doubles as the element class.

  • The Conversion Annotation page’s example (public setDate(Date date)) has a setter without a return type, which does not compile.

  • The page title of the guide page for annotations in older navigation, conversion-annotations, no longer exists (the address returns 404); the pages are conversion-annotation and type-conversion-annotation.

Summary

  • Conversion is a service of the OGNL layer: params sets properties by name, the converter turns text into the declared type, and failures are recorded in conversionErrors, not thrown.

  • The built-in converters are locale aware for numbers and dates; booleans are Boolean.valueOf; blank input is a non-error for most targets; the date format list is broader than the guide says.

  • Custom converters extend StrutsTypeConverter and throw TypeConversionException; they are registered per action (Action-conversion.properties), per bean (Class-conversion.properties) or per type for the whole application (struts-conversion.properties), or with @Conversion and @TypeConversion.

  • Collections and maps are filled from index notation; Element_, Key_, KeyProperty_ and CreateIfNull_ describe what the generics cannot; the () notation addresses an element by key; growth is limited by struts.ognl.autoGrowthCollectionLimit.

  • The conversionError interceptor turns the recorded failures into field errors with xwork.default.invalid.fieldvalue or invalid.fieldvalue.<field>, and keeps the text the visitor typed; workflow returns input.

  • The failure modes that lose data silently (comma as grouping, a date prefix, the growth limit, an excluded interceptor) are the ones to test for in a real form.
