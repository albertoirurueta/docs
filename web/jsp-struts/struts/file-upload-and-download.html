File Upload and Download

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Struts 7.4.0 (released 2026-10-02) running on Apache Tomcat 11.0.26 and Java 21, the combination on which every example was built, deployed and requested with curl on 2026-10-08 and again on 2026-10-10. The facts were checked against the struts-default.xml, default.properties and struts-messages.properties files inside the 7.4.0 struts2-core jar, the Javadoc of the classes involved and the Core Developer Guide pages on https://struts.apache.org/core-developers/. File upload is the feature of Struts with the worst security history: the bulletins S2-066 and S2-067 (CVE-2023-50164 and CVE-2024-53677), both remote code execution through path traversal in the upload parameters, are the reason the old fileUpload interceptor was replaced in 6.4 by actionFileUpload and removed from the distribution in 7.0. The running scenario is the Bookshelf, a catalogue of books exposed as Struts actions. This page lets a librarian upload a cover image for a book (uploadCover), limits what may be uploaded, stores the bytes outside the web application under a generated name, serves the cover back with the stream result (cover) and exports the catalogue as a CSV file (export). The neighbouring pages are the value stack, parameter injection, validation and localization.

Upload and Download in One Page

Uploading and downloading are the two directions of the same problem: bytes that do not fit in a text parameter cross the boundary between the browser and the action. They use different parts of the framework.

The action implements UploadedFilesAware, the interface through which the interceptor hands the files over. The action reads the first file, checks the first bytes of the content (a PNG starts with the eight bytes 89 50 4E 47 0D 0A 1A 0A, a JPEG with FF D8 FF), and only then stores it.

package org.example.bookshelf;

import java.io.IOException;
import java.io.InputStream;
import java.nio.file.Path;
import java.util.List;
import org.apache.struts2.ActionSupport;
import org.apache.struts2.action.UploadedFilesAware;
import org.apache.struts2.dispatcher.multipart.UploadedFile;
import org.apache.struts2.inject.Inject;
import org.apache.struts2.interceptor.parameter.StrutsParameter;

public class CoverUploadAction extends ActionSupport implements UploadedFilesAware {
    private String dir = System.getProperty("java.io.tmpdir") + "/g9upload-covers";
    private long bookId = 1;
    private List<UploadedFile> files = List.of();
    private CoverStore.Cover saved;

    @Inject(value = "bookshelf.covers.dir", required = false)
    public void setDir(String dir) { this.dir = dir; }

    @StrutsParameter
    public void setBookId(long bookId) { this.bookId = bookId; }

    public long getBookId() { return bookId; }

    public CoverStore.Cover getSaved() { return saved; }

    public List<CoverStore.Cover> getCovers() { return CoverStore.all(); }

    @Override
    public void withUploadedFiles(List<UploadedFile> uploadedFiles) {
        this.files = uploadedFiles;
    }

    public String form() { return INPUT; }

    @Override
    public String execute() throws IOException {
        if (files.isEmpty()) {
            addActionError("Choose a cover image first.");
            return INPUT;
        }
        UploadedFile f = files.get(0);
        try (InputStream in = f.getInputStream()) {
            byte[] head = in.readNBytes(8);
            if (!looksLikeImage(head)) {
                addActionError("The content of " + f.getInputName() + " is not a PNG or JPEG image.");
                return INPUT;
            }
        }
        String ext = f.getContentType().equals("image/png") ? ".png" : ".jpg";
        try (InputStream in = f.getInputStream()) {
            saved = CoverStore.save(Path.of(dir), bookId, f.getOriginalName(), f.getContentType(), in, ext);
        }
        return SUCCESS;
    }

    private static boolean looksLikeImage(byte[] h) {
        boolean png = h.length >= 8 && (h[0] & 0xFF) == 0x89 && h[1] == 'P' && h[2] == 'N' && h[3] == 'G';
        boolean jpg = h.length >= 3 && (h[0] & 0xFF) == 0xFF && (h[1] & 0xFF) == 0xD8 && (h[2] & 0xFF) == 0xFF;
        return png || jpg;
    }
}

What the Form and the Request Must Look Like

The parser acts only on a request that is a POST and whose Content-Type matches struts.multipart.validationRegex, by default ^multipart/form-data(?:\s*;\s*boundary=...)?... (a multipart/form-data media type with an optional boundary and charset). Anything else is an ordinary request and the file parts never arrive. The classic mistake is a form without enctype: the browser then sends only the file name as a text field.

curl -s -d "bookId=1&cover=dune.png" http://localhost:18080/g9upload/uploadCover | grep -A1 errorMessage
<ul class="errorMessage">
  <li><span>Choose a cover image first.</span></li></ul>

The action sees no file at all (an empty list, not an error from Struts), so the application has to handle the empty case; the action above does it with an action error. Struts disables the whole mechanism with <constant name="struts.multipart.enabled" value="false"/>, after which it ignores the Content-Type header and treats every request as ordinary (documented, not run here).

UploadedFilesAware and UploadedFile

org.apache.struts2.action.UploadedFilesAware is the Struts 6.4 and later way to receive uploads. It has one method, withUploadedFiles(List<UploadedFile>), called by the interceptor once per request with every accepted file part. The interceptor sets the files through this callback, not through setters named after the form field, which is the design change that removed the attack surface of S2-066 and S2-067 (see The Security History). The list contains one entry for each file part, whatever its field name, so an action that expects one file reads get(0) after checking isEmpty().

public class MultiUploadAction extends ActionSupport implements UploadedFilesAware {
    private final List<String> report = new ArrayList<>();

    @Override
    public void withUploadedFiles(List<UploadedFile> uploadedFiles) {
        for (UploadedFile f : uploadedFiles) {
            report.add(f.getInputName() + "|" + f.getOriginalName() + "|" + f.getContentType() + "|" + f.length() + "|" + f.isMissing());
        }
    }

    public List<String> getReport() { return report; }

    @Override
    public String execute() { return SUCCESS; }
}

Reading the content: stream first, file only when needed

Since 7.3.0 a small upload (below the parser’s disk-spill threshold, around 8 KB according to the official page) is kept in memory and its temporary file is written lazily, only when something asks for a java.io.File. Uploads that the interceptor rejects by size, type or extension therefore never touch the file system. The consequence for code is to read with getInputStream() and to avoid getContent() and getAbsolutePath() unless a library really needs a file:

public void withUploadedFiles(List<UploadedFile> uploadedFiles) {
    for (UploadedFile file : uploadedFiles) {
        try (InputStream in = file.getInputStream()) {
            // process the bytes; no temporary file is created for small uploads
        } catch (IOException e) {
            // handle
        }
    }
}

Several files: one name or several names

Several s:file fields with the same name (upload) produce several entries in the one list, which is what the official multiple-upload example uses. Fields with different names also end in the same list, and getInputName() tells them apart. In the old fileUpload style the two choices needed three setters per file or three arrays; with the new callback there is no such multiplication.

The actionFileUpload Interceptor

org.apache.struts2.interceptor.ActionFileUploadInterceptor is registered under the name actionFileUpload and is available since Struts 6.4.0 as the replacement for fileUpload. It is based on MultiPartRequestWrapper, which the framework applies to every request that carries a file, and, for an action that implements UploadedFilesAware, it passes the files through the callback. It adds field errors when the action implements ValidationAware (every ActionSupport does).

Where it sits in the stacks

struts-default.xml of 7.4.0 registers the interceptor and puts it in three stacks. In defaultStack it is the 11th of 24 interceptors, before params (17th) and validation; in paramsPrepareParamsStack it sits after modelDriven and before staticParams and the second params; and actionFileUploadStack is a two-entry stack, the interceptor followed by basicStack.

Per-request rules with expressions

Since 7.2.0 the three parameters allowedTypes, allowedExtensions and maximumSize accept ${...} expressions that are evaluated against the value stack at the time of the upload (the interceptor implements WithLazyParams). The policy can therefore depend on the action: here ebooks may be PDFs up to 400000 bytes and every other upload is a PNG of at most 100 bytes.

/** Upload policy chosen per request: ebooks may be PDF up to 400 000 bytes, everything else PNG up to 100 bytes. */
public class PolicyUploadAction extends MultiUploadAction {
    private String kind;

    @StrutsParameter
    public void setKind(String kind) { this.kind = kind; }

    public String getAllowedContentTypes() { return "ebook".equals(kind) ? "application/pdf" : "image/png"; }

    public Long getMaxFileSize() { return "ebook".equals(kind) ? 400000L : 100L; }

    public String getKind() { return kind; }
}
<action name="uploadPolicy" class="org.example.bookshelf.PolicyUploadAction">
    <interceptor-ref name="basicStack"/>
    <interceptor-ref name="actionFileUpload">
        <param name="allowedTypes">${allowedContentTypes}</param>
        <param name="maximumSize">${maxFileSize}</param>
    </interceptor-ref>
    <result>/WEB-INF/views/many.jsp</result>
    <result name="input">/WEB-INF/views/many.jsp</result>
</action>

The order of basicStack and actionFileUpload matters, and the official page does not say so. The kind parameter is copied to the action by params, which is inside basicStack. What the limits cannot do

The limits are about bytes and counts, not about the server in front of Struts. The servlet container has its own limits (Tomcat’s maxPostSize and maxParameterCount of the connector, maxSwallowSize for aborted uploads, and the @MultipartConfig limits of servlets that are not Struts), and a reverse proxy has its own body size limit (for example client_max_body_size of nginx). A limit that the proxy imposes shows up as a proxy error page, not as a Struts message. The Struts limits remain necessary because they are the last line of defence when the front layers are misconfigured or bypassed.

Storing Uploads Safely

An uploaded file is first written by the parser to a temporary location (the parts below the disk-spill threshold stay in memory since 7.3.0). The official page asks the action to process or move the file, because the temporary file does not outlive the request, and warns that a server security policy may forbid writing outside the temporary directory and the directories of the web application. The advice of this page for where to move it is the opposite of the habit of older tutorials, which saved into a folder of the web application:

  • Save outside the web application root (and outside any directory that the container serves). A file stored under the web root can be requested directly, and a file whose name ends in .jsp or .jspx will be compiled and run by Jasper. This is the mechanism behind the upload-to-RCE incidents, and the Tomcat bulletins CVE-2024-50379 and CVE-2024-56337 (a time-of-check time-of-use race in JSP compilation, exploitable when an uploaded file is treated as a JSP on a case-insensitive file system) show that even an extension filter on the Tomcat side is not a substitute for storing the bytes elsewhere.

  • Generate the stored name (a UUID plus an extension picked from a fixed table), and never use getOriginalName() or getContentType() as part of a path. Keep the original name as data, for the download header or a label, after sanitising it.

  • Resolve the target and check that it is below the intended directory (normalize() then startsWith()), which protects against a name that contains .. or an absolute path.

  • Authorise the upload and the download: who may attach a cover to which book is application logic that the file interceptors know nothing about.

  • Limit the total storage per user and the number of files, and delete the temporary file when the work is finished (UploadedFile.delete()).

  • Serve user uploads through an action (the stream result below) rather than by mapping a folder to a URL, so that the content type and the disposition are chosen by the application, not guessed from the file name.

The store of the Bookshelf follows these rules. It keeps the covers in a directory that is not part of the WAR, saves under a generated name, and refuses a target outside the directory:

public final class CoverStore {
    public record Cover(String id, long bookId, String originalName, String contentType, long size, Path path) {
        public String getId() { return id; }
        public long getBookId() { return bookId; }
        public String getOriginalName() { return originalName; }
        public String getContentType() { return contentType; }
        public long getSize() { return size; }
    }

    private static final Map<String, Cover> COVERS = new ConcurrentHashMap<>();

    public static Cover save(Path dir, long bookId, String originalName, String contentType, InputStream in, String ext) throws IOException {
        Files.createDirectories(dir);
        String id = UUID.randomUUID().toString();
        Path target = dir.resolve(id + ext).normalize();
        if (!target.startsWith(dir.normalize())) {
            throw new IOException("Refusing to write outside " + dir);
        }
        Files.copy(in, target, StandardCopyOption.REPLACE_EXISTING);
        Cover cover = new Cover(id, bookId, originalName, contentType, Files.size(target), target);
        COVERS.put(id, cover);
        return cover;
    }

    public static Cover find(String id) { return id == null ? null : COVERS.get(id); }

    public static List<Cover> all() { return new ArrayList<>(COVERS.values()); }
}

The in-memory map stands in for a database table in the scratch application; a real application keeps the metadata in the database and the path or object key next to it. Three things in the mapping are deliberate. The disposition attachment makes the browser save the file instead of rendering it, which is the safe default for user uploads (an uploaded HTML or SVG file shown inline runs in the application’s origin). The same action with a filter, export?author=Gibson, returns only the header line and the Neuromancer row (observed). The points worth reading in this output:

  • contentCharSet adds ;charset=UTF-8 to the content type, and the bytes really are UTF-8 (getBytes(UTF_8)); the length is the number of bytes, not of characters (178 bytes for 4 rows, because the accented letter takes two).

  • The leading U+FEFF is a byte order mark (the three bytes EF BB BF). Excel needs it to recognise UTF-8 in a CSV file; other readers show it as a stray character, so add it only when the consumers are spreadsheet users.

  • Every cell is quoted and an embedded double quote is doubled (""), which also protects the comma in Les Misérables, vol. 1; the line separator is the CRLF that RFC 4180 specifies.

  • A cell that begins with =, +, -, @, a tab or a carriage return is prefixed with a single quote. Without that, a book titled =HYPERLINK("http://example.org") becomes a formula when the file is opened in a spreadsheet (CSV injection or formula injection). Escaping for CSV does not prevent it, the prefix does.

The Bookshelf End to End: a Cover for a Book

The pieces above combine into one flow of the Bookshelf. A librarian opens covers, uploads dune.png for book 7, and the page lists it; a reader follows the link to cover?id=...; the librarian exports the catalogue.

# 1. the form
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:18080/g9upload/covers
# 2. a valid upload
curl -s -F bookId=7 -F "cover=@dune.png;type=image/png" http://localhost:18080/g9upload/uploadCover | grep saved
# 3. a rejected upload (a PDF)
curl -s -F "cover=@x.pdf;type=application/pdf" http://localhost:18080/g9upload/uploadCover | grep -c errorMessage
# 4. the download
curl -s -D - -o /dev/null "http://localhost:18080/g9upload/cover?id=06607f3c-4cbf-41b4-a318-7c1632a07a75" | grep -i disposition
# 5. the catalogue as CSV
curl -s http://localhost:18080/g9upload/export

The five steps answered 200 with the form, the line Saved 06607f3c-... (69 bytes, image/png) as dune.png, the two field errors for the PDF (extension and content type), the header Content-Disposition: attachment;filename="cover-7.png" and the CSV shown above. The matrix of what the interceptors decide for each input is the table of Allowed Types and Extensions; the limits are the table of Limits: Two Layers.

In a real application the same flow has three more parts. The identifier comes from a database and the download action checks that the current user may read the cover; the upload action is reachable only after authentication and, because it changes state, is protected by the token interceptor (the topic of the double-submit page of this section); and the front proxy and the container have body limits equal to or slightly above the Struts ones.

Notes on the Official Documentation

While this page was written the official pages were found to disagree with Struts 7.4.0 in several places; each is recorded so that the reader is not surprised.

  • The Action File Upload page still says com.opensymphony.xwork2.ValidationAware and javax.servlet.context.tempdir in prose that was written before the 7.0 repackaging and the Jakarta namespace move; the classes are in org.apache.struts2 and the attribute is jakarta.servlet.context.tempdir.

  • The legacy File Upload page still shows @StrutsParameter setters for the old File properties, although there is no fileUpload interceptor in 7.4.0; the code compiles and does nothing.

  • The Stream Result page shows com.opensymphony.xwork2.Action and private getters, and says that allowCaching sets no-cahce headers (observed: no-cache).

  • The text of struts.messages.error.file.too.large contains "allowed mx size", and the whole-request message does not report the request’s size although the properties text promises it (observed).

  • The Security Guide has no section on file uploads; the guidance on this page (store outside the web root, generated names, content checks) comes from the Core Developer Guide, the bulletins and the observations above.
