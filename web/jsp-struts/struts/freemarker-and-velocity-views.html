FreeMarker & Velocity Views

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Struts 7.4.0 (released 2026-10-02) running on Apache Tomcat 11.0.26 (Jakarta Servlet 6.1, Jakarta Pages 4.0) with Java 21, FreeMarker 2.3.35 (the library struts2-core 7.4.0 depends on) and, for the Velocity half, struts2-velocity-plugin 7.4.0 with Velocity Engine 2.4.1. Everything was verified on 2026-10-08 and re-run on 2026-10-10: the facts against the Struts documentation and the 7.4.0 sources and jars, and every example by building it into a Maven WAR with the struts2-bom, deploying it on Tomcat 11.0.26 and calling each URL with curl; the outputs shown are what that run produced (session ids and blank lines are left out). JSP is not the only way to turn an action into a page. Struts ships a second view technology in its core, FreeMarker, which the framework itself uses to render every UI tag, and a third one, Velocity, as a plugin. A FreeMarker or Velocity view is a plain text file that is rendered by a result type, reads the same action and value stack as a JSP and needs no servlet container support for JSP, so it can be packaged in a jar, tested without a container and edited without a translation step. The running scenario is the Bookshelf catalogue: the same book data is rendered through JSP-free views, the Struts tags are used from both engines, a layout is built from macros, and each engine is configured for production.

Why Use a Template View Instead of JSP

All three technologies end in the same place, a Result that writes text to the response. The differences are in how the text is produced and where it can be loaded from.

The FreeMarker documentation of Struts gives the reason for choosing it: the engine reports errors well, has built-in internationalization and offers powerful macro libraries, and it suits cases where the action result may have to be loaded from outside a servlet container, for example a plug-in jar that carries the whole action class and its view. The same page notes that Velocity is also supported. The rest of this page treats FreeMarker first because every Struts form tag is already a FreeMarker template, then Velocity.

The FreeMarker Result

struts-default.xml registers the freemarker result type (class org.apache.struts2.views.freemarker.FreemarkerResult), so nothing is added to the build: FreeMarker is a dependency of struts2-core. The result element takes the template path as its default parameter.

A FreeMarker view for the Bookshelf catalogue (action and template)
<action name="hello" class="org.example.bookshelf.BookViewAction">
    <result type="freemarker">/WEB-INF/views/hello.ftl</result>
</action>
<html>
<head><title>Hello</title></head>
<body>
<h1>Hello, ${title}</h1>
<p>${book.title} by ${book.author}</p>
<p>id=${book.id} price=${book.price} id-c=${book.id?c}</p>
</body>
</html>
The response for /hello (the book title is Dune <b>& more</b> and its id is 1234)
<html>
<head><title>Hello</title></head>
<body>
<h1>Hello, Dune</h1>
<p>Dune &lt;b&gt;&amp; more&lt;/b&gt; by Frank Herbert</p>
<p>id=1,234 price=1,234.5 id-c=1234</p>
</body>
</html>

Source: Apache Struts — FreeMarker, Getting Started

Three things in the output matter before anything else is learned. ${title} is not a field access: FreeMarker asked the value stack for title and the stack called getTitle() on the action (see The Data Model). The markup in the book title was escaped, because auto-escaping is on (Auto-Escaping). And the number 1234 was printed as 1,234, because FreeMarker formats numbers for the locale unless told otherwise (Numbers, Dates and Locales). The Data Model

Everything a template can read is the data model, a hash FreeMarker consults by name. In Struts it is a ScopesHashModel, built for each request by FreemarkerManager. Its own entries are the names below, and a name that is not found there is looked up in the value stack and in the places behind it. Variable Resolution

A plain name such as title is resolved in this order, first match wins (ScopesHashModel.get): the entries of the data model above, the value stack, the action context, the request attributes, the session attributes, then the application attributes. That ordering is the reason ${book.title} needs no # prefix as <s:property value="#request.x"/> does in a JSP, and also the reason a request attribute named like an action property is hidden by the property.

The same values reached through the s tag macros (OGNL-tag) use OGNL and the hash #request, while FreeMarker reads the hash models Request and Session. Mixing the two works, but choose one style per template. Note that filter-on-action only prints x because the action’s setFilter carries @StrutsParameter; the request parameter itself is always readable as Parameters.filter whether or not the action accepts it.

Auto-Escaping

Struts 7.4.0 configures FreeMarker with the HTML output format and the "enable if default" auto-escaping policy (see the FreemarkerManager.createConfiguration source), so every ${...} interpolation in a template is HTML-escaped. This is the biggest difference from the JSP model, where plain EL output is not escaped. FreeMarker has three ways to leave the escaping out, and the Struts property tag has its own switch.

auto=${book.title}
noesc=<#noautoesc>${book.title}</#noautoesc>
no_esc=${book.title?no_esc}
prop=<@s.property value="book.title"/>
prop-noesc=<@s.property value="book.title" escapeHtml="false"/>
fmt=${.output_format} ${.auto_esc?c}
json=${book.title?json_string}
The output of /escape for a title Dune <b>& more</b>
auto=Dune &lt;b&gt;&amp; more&lt;/b&gt;
noesc=Dune <b>& more</b>
no_esc=Dune <b>& more</b>
prop=Dune &lt;b&gt;&amp; more&lt;/b&gt;
prop-noesc=Dune <b>& more</b>
fmt=HTML true
json=Dune &lt;b&gt;&amp; more&lt;\/b&gt;

Source: Apache FreeMarker — Auto-escaping, Disabling auto-escaping

Source: Apache FreeMarker — noautoesc

The old way of escaping, the ?html built-in, is a template error under auto-escaping. A template written for Struts 2.3 or 2.5 stops at the first request:

<p>${book.title?html}</p>
The result of /legacy
HTTP/1.1 500
Using ?html (legacy escaping) is not allowed when auto-escaping is on with a markup output format (HTML), to avoid double-escaping mistakes.

Source: Apache FreeMarker — html built-in

The fix is to delete the built-in and let the engine escape. ?no_esc and <#noautoesc> are for markup that was already made safe, such as the output of another tag; they are the FreeMarker equivalent of cross-site scripting holes when applied to user input. The escaping format is HTML, so ${...} inside a <script> block is escaped as HTML, not as JavaScript; for a JavaScript or JSON context use ?json_string (shown above, the / was escaped too) or build the JSON in Java.

Numbers, Dates and Locales

FreeMarker formats numbers and dates with its own rules, driven by the locale of the request. This is a different mechanism from the Struts type conversion that the property tag applies, and the Struts documentation warns about it: ${...} evaluates a FreeMarker expression and converts the result with FreeMarker’s formatting, while the property tag evaluates an OGNL expression and converts the result to a string with the Struts conversion rules.

ftl-number=${book.price}
ftl-date=${book.published?string("yyyy-MM-dd")}
ftl-id=${book.id}
tag-price=<@s.property value="book.price"/>
tag-id=<@s.property value="book.id"/>
The output for the default locale, with ?request_locale=de, and with an Accept-Language: de header
$ curl "http://localhost:18080/g10ftlvel/convert"
ftl-number=1,234.5
ftl-date=1970-01-01
ftl-id=1,234
tag-price=1234.5
tag-id=1234

$ curl "http://localhost:18080/g10ftlvel/convert?request_locale=de"
ftl-number=1.234,5
ftl-date=1970-01-01
ftl-id=1.234
tag-price=1234,5
tag-id=1234

Source: Apache Struts — FreeMarker, Type Conversion and Locales

The request_locale parameter is the one the i18n interceptor reads, so the action locale and the FreeMarker locale move together (the header gave the same output as the parameter). The three practical rules follow from the output: use ?c for identifiers, years and anything that is not a quantity (${book.id?c} printed 1234, ${book.id} printed 1,234); format dates with ?string(pattern) or ?date, ?time and ?datetime; and use <@s.property> when the Struts converters configured for the action must decide. A java.util.Date of unknown kind cannot be printed without one of those:

<p>${book.published?string("yyyy-MM-dd")}</p>
<p>${book.published}</p>
The result of /datetype
<p>1970-01-01</p>
<p>Can't convert the date-like value to string because it isn't known if it's a date (no time part), time or date-time value.
...
Tip: Use ?date, ?time, or ?datetime to tell FreeMarker the exact type.

Source: Apache FreeMarker — string built-in for dates

Source: Apache FreeMarker — c built-in for numbers

A default locale for the engine can be fixed in freemarker.properties (locale=en_US, see freemarker.properties); the request locale still wins when the i18n interceptor sets one. Messages from resource bundles are read through the action: ${action.getText("book.heading", [title])} and <@s.text name="book.heading"><@s.param value="title"/></@s.text> both printed Catalogue of Dune for a bundle entry book.heading=Catalogue of {0} in BookViewAction.properties.

Source: Apache Struts — FreeMarker, Type Conversion and Locales

Struts Tags as FreeMarker Macros

Every generic and UI tag of Struts is available as a FreeMarker macro under the prefix s, with the syntax <@s.tag ...>...</@s.tag>. The s prefix is in the data model (see the table above), so no assign or taglib declaration is needed. A form that is written in JSP as <s:form>, <s:textfield> and <s:submit> is written in FTL by changing the prefix delimiters:

<@s.form action="hello" method="get" theme="simple">
    <@s.textfield name="title" placeholder="Title" cssClass="wide"/>
    <@s.select name="shelf" list="books" listKey="id" listValue="title"/>
    <@s.submit value="Search"/>
</@s.form>
The response for /form
<form id="hello" name="hello" action="/g10ftlvel/hello.action" method="get"><input type="text" name="title" value="Dune" id="hello_title" class="wide" placeholder="Title"/><select name="shelf" id="hello_shelf">
    <option value="1">Dune</option>
    <option value="2">Neuromancer</option>
</select>

<input type="submit" value="Search" id="hello_0"/>
</form>

Source: Apache Struts — FreeMarker Tags

The same tag set that the tags and form-tags pages of this section describe is therefore usable from FreeMarker; those pages are written for JSP, and this one only covers what differs.

Attributes and Expressions

A FreeMarker tag call takes attributes in two forms, and they are evaluated differently. A quoted string is handed to the tag as a string, and the tag evaluates it as OGNL for the attributes it declares (value="title", list="books", test="title == 'Dune'", value="%{#request.wishlist}"), converting the result to the attribute’s type. An unquoted value is a FreeMarker expression, evaluated by FreeMarker before the tag sees it; FTL lists, hashes and numbers pass through as objects. The next examples show where the two meet.

<@s.select theme="simple" name="r1" list="{1, 2, 3}"/>
<@s.select theme="simple" name="r2" list=[1, 2, 3]/>
<@s.select theme="simple" name="r3" list={"A":"Alpha","B":"Beta"}/>
<@s.textfield theme="simple" name="a" size="20" cols=5/>
The response for /tags2 (the r1 and r2 options are identical, and r3 has two options)
<select name="r1" id="r1">
    <option value="1">1</option>
    <option value="2">2</option>
    <option value="3">3</option>
</select>
<select name="r2" id="r2">
    <option value="1">1</option>
    <option value="2">2</option>
    <option value="3">3</option>
</select>
<select name="r3" id="r3">
    <option value="A">Alpha</option>
    <option value="B">Beta</option>
</select>
<input type="text" name="a" size="20" value="" id="a" cols="5"/>

Source: Apache Struts — FreeMarker Tags, Attribute Types

The documentation example list="%{1, 2, 3}" rendered an empty select on 7.4.0; use the OGNL form list="{1, 2, 3}" (no %) or an FTL sequence. Where the tag needs a number (size, rows, cols), both size="20" and cols=5 worked in the native macros; the "must be a number" rule that the Struts docs state applies to the JSP tag library bridge.

Inline attributes also replace the param tag for the tags that take parameters. The query-string builder url shows the four forms and a trap in the first:

A: <@s.url value="hello" filter="%{title}" personId="%{book.id}"/>
B: <@s.url value="hello" filter=title personId=book.id?c/>
C: <@s.url value="hello"><@s.param name="filter" value="title"/><@s.param name="personId" value="book.id"/></@s.url>
D: <@s.url var="u" value="hello"><@s.param name="filter" value="title"/><@s.param name="personId" value="book.id"/></@s.url>${u} / ${u?no_esc}
The output of /tags2 for these lines (the session id that the first response carries is ;jsessionid=... after hello and is left out)
A: hello?filter=%25%7Btitle%7D&amp;personId=%25%7Bbook.id%7D
B: hello?filter=Dune&amp;personId=1234
C: hello?filter=Dune&amp;personId=1234
D: hello?filter=Dune&amp;amp;personId=1234 / hello?filter=Dune&amp;personId=1234

Source: Apache Struts — FreeMarker Tags, Attributes and Parameters

Line A is the example from the documentation, and in 7.4.0 the %{...} is not evaluated for an inline parameter: the literal text is URL-encoded into the query string. Line B passes an FTL expression, which works; line C is the param tag, which evaluates OGNL; line D stores the URL in a variable, and printing the variable with ${u} escapes the already escaped ampersand a second time (&amp;), so use ?no_esc there or print the URL by leaving var out (A to C print it directly).

Control Flow: FreeMarker Directives or Struts Tags

The Struts control tags (iterator, if, else, set, property) exist as macros, but FreeMarker has its own directives that are faster and need no OGNL, and the performance-tuning guide of Struts recommends using the FreeMarker equivalent instead of the JSP tags. The two are interchangeable for the Bookshelf catalogue:

<ul>
<#list books as b>
  <li>${b?counter}. ${b.title} (${b.price})</li>
</#list>
</ul>
<ul>
<@s.iterator value="books" status="st">
  <li>${st.count}. <@s.property value="title"/> (<@s.property value="price"/>)</li>
</@s.iterator>
</ul>
<@s.if test="title == 'Dune'">it is Dune</@s.if><@s.else>another book</@s.else>
The response for /iter
<ul>
  <li>1. Dune (9.99)</li>
  <li>2. Neuromancer (7.5)</li>
</ul>
<ul>
  <li>1. Dune (9.99)</li>
  <li>2. Neuromancer (7.5)</li>
</ul>
it is Dune

Source: Apache Struts — Performance Tuning, Use the FreeMarker equivalent

Inside <@s.iterator> the current element is on top of the value stack, so <@s.property value="title"/> (OGNL) and ${title} (the FreeMarker lookup of the stack) both read the book’s title; inside <#list> only the loop variable b is the book and ${title} would read the action’s title. That difference is the most common source of wrong output when a JSP is converted.

Since Struts 7.0 the tag templates read attributes where earlier versions read parameters, as the FreeMarker Tags page notes. A template error is a first-class feature of FreeMarker and Struts changes what it does. Configuring FreeMarker

Struts reads FreeMarker configuration from four places: constants in struts.xml or struts.properties, a freemarker.properties file on the classpath, init parameters in web.xml (the TemplatePath and freemarker.incompatible_improvements ones), and a replacement FreemarkerManager. The defaults that matter come from FreemarkerManager.createConfiguration in 7.4.0: HTML output format with auto-escaping, HTML_DEBUG error handling, localised template lookup off, and TemplateClassResolver.SAFER_RESOLVER for the ?new built-in.

freemarker.properties

A freemarker.properties file on the classpath (typically src/main/resources) holds any setting that the FreeMarker Configuration understands. Struts reads it once, when the engine is created, and applies each key with Configuration.setSetting.

template_exception_handler=rethrow
default_encoding=UTF-8
locale=en_US

Where Templates Are Loaded From

FreemarkerManager.createTemplateLoader builds a MultiTemplateLoader. It searches, in this order: a directory or classpath location given as the TemplatePath context parameter (prefix file:// or class://), then the web application, then the classpath. That order is why an application can override a template that ships inside the Struts jar: the copy in the web application wins.

<context-param>
    <param-name>TemplatePath</param-name>
    <param-value>file:///var/lib/bookshelf/templates</param-value>
</context-param>

The override appeared only after the application was redeployed: FreeMarker’s MultiTemplateLoader remembers which loader found a template last and asks it first, so a file added later to a loader that was not consulted is not noticed until the engine restarts. Add overrides before the first request, or restart. The Struts documentation notes that the template path is not relative to the application root.

The Object Wrapper

FreeMarker wraps Java objects with an object wrapper. Struts uses StrutsBeanWrapper, which extends the BeansWrapper but changes maps. FreeMarker normally supports either friendly map built-ins (?keys, ?values) with String keys only, or no built-ins and any key type; the Struts wrapper gives both. The Bookshelf stock map in the layout example is printed key by key with ${stock[k]} and stock?keys. If the special behaviour causes trouble, the constant struts.freemarker.wrapper.altMap set to false restores the standard wrapper.

Escaping References

Velocity does not escape. Its engine ships an event handler that does, EscapeHtmlReference, and it is enabled in velocity.properties on the classpath; the match property is a regular expression that selects the references to escape, so a handler matching /.*/ escapes everything.

event_handler.reference_insertion.class = org.apache.velocity.app.event.implement.EscapeHtmlReference
event_handler.escape.html.match = /\$book.*/
$book.title is now escaped and $title (which does not match) is not

Use /.*/ unless a reference is known to hold safe markup; a Velocity template without a handler is the Velocity equivalent of <#noautoesc> everywhere.

Velocity Tools and the Toolbox Trap

Velocity Tools are the reusable helpers (EscapeTool, NumberTool, DateTool) that the earlier generation of Struts and Velocity integrations loaded in a toolbox. The plugin supports a toolbox through struts.velocity.toolboxlocation, with the optional jars struts2-velocity-tools-view-jakarta and velocity-tools-generic 3.1 on the classpath (neither is brought in by the plugin, since both are optional dependencies). The location is read from the classpath, and the configuration is validated: an application-scoped tool in a request toolbox is rejected.

<tools>
  <toolbox scope="request">
    <tool key="shelf" class="org.example.bookshelf.ShelfTool"/>
  </toolbox>
</tools>
shelf=$shelf.label('Dune')
title=$title
stack=$stack
The output of /vm/macros with struts.velocity.toolboxlocation set to tools.xml

The tool works, and the value stack is gone: $title and $stack are printed as written, and a Struts directive such as #stextfield fails with NullPointerException: Cannot invoke "org.apache.struts2.util.ValueStack.getContext()" because "stack" is null. The cause is in StrutsVelocityManager.createContext: when a toolbox is configured the context comes only from VelocityTools.createContext, a ToolContext with the default (request) toolbox, and the Struts context is never built. A toolbox therefore turns the integration into plain Velocity. Use struts.velocity.contexts (above) for helpers; put a Velocity Tools toolbox into a context class if a tool is needed. Where the Books and Docs Are Outdated

The two Struts books consulted for concept coverage describe the technology in its first generation and are not reproduced here.

Table 7. Material about FreeMarker and Velocity views that no longer matches Struts 7.4
Material Struts 7.4

Struts in Action (Struts 1), the Velocity chapter: Velocity templates instead of JSP through the VelocityViewServlet and the VelocityStruts tools

Struts 2 and later do not use the servlet. The velocity result and the #s... directives replace it, the plugin is struts2-velocity-plugin, and a toolbox (struts.velocity.toolboxlocation) replaces the context in 7.4.0. The VelocityViewServlet still exists in the Jakarta fork of Velocity Tools and renders plain templates

Struts 2 in Action: tags are FreeMarker templates; the FreeMarker examples use ${title?html} or no escaping at all

Auto-escaping is on in 7.4.0 and ?html is an error. The themes and the form-tag templates are FreeMarker; the theme override is a template with the same path

Struts docs: req, res and ognl in a FreeMarker view; attributes.myParameter for a request parameter; application as the ServletContext

request, response, Parameters.myParameter and Application/application attribute maps; req, res, ognl and attributes are not in the data model

Struts docs: update delay "60 s", foo="checked: %{bar}" evaluated, list="%{1, 2, 3}", personId="%{personId}" in s:url

None of these behaved as documented in the verification run (see the examples above)

Struts docs: the Velocity Properties page lists action-default.vm, tigris-macros.vm, myapp.vm and refers to struts-default.vm

No such files in the 7.4.0 jars; the core jar has a struts.vm with legacy macros that use $req and $res, which the 7.4.0 context does not define

Both books also describe the earlier Struts 2 and Struts 1 generations of the JSP tag libraries and the Struts 1 tags. The Struts 1 page of this section, Struts 1 (Classic) & Migration, covers the correspondence, and the migration material tells which of the old packages and classes are gone. The Velocity examples in the books should be treated as design ideas, not as configuration.

Putting It Together for the Bookshelf

A Bookshelf application that uses FreeMarker for every page needs, in the build, only struts2-core. It sets template_exception_handler=rethrow in freemarker.properties, keeps auto-escaping, formats identifiers with ?c, builds pages from an imported layout macro, writes forms with the s macros (using FTL expressions for inline attributes) and overrides a tag template in template/xhtml/ when a field needs a hint. A Velocity page is added only when an existing set of templates has to be reused, with the escape handler enabled and the toolbox left alone. JSP remains the choice when a page needs a JSP-only tag library, since the FreeMarker bridge is broken on Pages 4.0.
