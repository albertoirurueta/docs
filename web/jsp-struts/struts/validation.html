Validation

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Struts 7.4.0 (released 2026-10-02) running on Apache Tomcat 11.0.26 and Java 21, the combination that every example was built, deployed and requested on; the facts were checked on 2026-10-08 against the struts2-core 7.4.0 jar (class lists, validators/default.xml, default.properties, the DTDs), its Javadoc and the Core Developer Guide pages on https://struts.apache.org/core-developers/. Validation in Struts is not one feature but a small pipeline: the params interceptor copies request values onto the action, the conversionError interceptor remembers the values that could not be converted, the validation interceptor runs the checks (a validate() method on the action, XML rules, annotations) and records every failure as a field error or an action error on the action, and the workflow interceptor looks at those errors and, if there is one, answers with the input result before the action method runs. Everything is driven by configuration, and each piece is replaceable: this page follows the pipeline in order, goes through every validator that ships with the framework, and then covers the parts that surprise people (the order in which validators run, what short-circuiting really skips, how the files for a class and for an alias are combined, why a ModelDriven form shows no error beside its field, and why a field that failed conversion collects two messages). The running scenario is the Bookshelf, a catalogue of books exposed as Struts actions; here it is a form that adds a title, and every output quoted below was produced by requests to that form’s actions. Related pages of this section: ValueStack, ActionContext & OGNL, Parameter Injection and @StrutsParameter, Type Conversion, Bean Validation Plugin, Localization and i18n, ModelDriven, Preparable & CRUD and UI & Form Tags.

The Validation Pipeline

Validation needs two interceptors, and both are already in the default stack. The validation interceptor (class org.apache.struts2.interceptor.validation.AnnotationValidationInterceptor, a subclass of org.apache.struts2.validator.ValidationInterceptor) does the checking and creates the errors. It does not change the course of the request. The workflow interceptor (org.apache.struts2.interceptor.DefaultWorkflowInterceptor) is the one that acts: it returns the input result when the action has an action error, a field error or a conversion error. The Core Developer Guide states the dependency plainly: both interceptors belong to the default stack, and a stack that leaves either out does not validate. It also warns about the consequence of a missing input result.

flowchart TD R["Request for the action"] --> P["params: request values copied onto the action"] P --> C["conversionError: values that failed conversion are remembered as field errors"] C --> X{"Method named in excludeMethods or marked with SkipValidation?"} X -- "yes, validation is skipped" --> A X -- "no" --> M["validateMethodName() or validateDoMethodName(), if the action has one"] M --> V["validate(), unless alwaysInvokeValidate is false"] V --> D["XML files and annotations: plain validators, then field validators"] D --> W{"workflow: any action error, field error or conversion error?"} W -- "yes" --> I["input result, or the name chosen by ValidationWorkflowAware, ValidationErrorAware or InputConfig"] W -- "no" --> A["The action method runs, then the result"]

The same interceptors also run on the way back out of the stack, but they do nothing there: all the work is done before the action. The practical consequences are three. Validation never sees a value the params interceptor did not set (a setter without @StrutsParameter leaves the property at its default and the validator checks that default). Validation cannot protect an action whose mapping uses a stack without validation and workflow. And the action method does not run when validation fails, so a null that the validator rejected can never reach execute().

Turning Validation On

The default stack has validation turned on. struts-default.xml binds the names to the classes and the defaultStack gives both interceptors the same exclusion list; the stack called validationWorkflowStack (basicStack, then validation and workflow, with no exclusion) is the smallest stack that validates:

<interceptor name="validation"
             class="org.apache.struts2.interceptor.validation.AnnotationValidationInterceptor"/>
<interceptor name="workflow" class="org.apache.struts2.interceptor.DefaultWorkflowInterceptor"/>
<!-- inside defaultStack: -->
<interceptor-ref name="validation">
    <param name="excludeMethods">input,back,cancel,browse</param>
</interceptor-ref>
<interceptor-ref name="workflow">
    <param name="excludeMethods">input,back,cancel,browse</param>
</interceptor-ref>

Source: Apache Struts — Validation, Turning on Validation

A stack of your own must list both interceptors, in that order, after the interceptors that set the values (params, modelDriven, prepare in a paramsPrepareParamsStack). A stack with validation and no workflow records the errors and then runs the action anyway; a stack with workflow and no validation has nothing to look at.

Programmatic Validation: validate() and Its Relatives

The simplest validation is Java code in the action. ActionSupport (see the Actions page) implements two interfaces for it: org.apache.struts2.Validateable, whose method validate() the validation interceptor calls, and org.apache.struts2.interceptor.ValidationAware (the org.apache.struts2.interceptor interface, not the com.opensymphony.xwork2 one that older pages name), which stores the errors. The methods an action uses are:

Method Effect

addFieldError(String field, String message)

Adds a message for one input field; the view shows it next to that field and the workflow interceptor treats it as an error

addActionError(String message)

Adds a message that belongs to the action as a whole, not to one field

addActionMessage(String message)

Adds an informational message; it is not an error and does not trigger input

hasErrors(), hasFieldErrors(), hasActionErrors()

True when any error, any field error or any action error exists

getFieldErrors(), getActionErrors(); clearErrors() of ActionSupport

Read the map and the collection; empty both (clearErrors() is a method of ActionSupport, not of the interface)

Source: Apache Struts — Getting Started, Form Validation

Besides validate(), the interceptor looks for a method named after the action method. The Default Workflow Interceptor page states the rule: if the class has validateMethodName() it is called; otherwise, if it has validateDoMethodName(), that is called; and either way validate() runs afterwards while alwaysInvokeValidate is true. The first letter of the method name is capitalised (save gives validateSave). The Bookshelf action below has three entry points, one with each kind of method, and one that is excluded from validation with @SkipValidation:

ProgrammaticAction: validate(), validateSave(), validateDoUpdate() and @SkipValidation
public class ProgrammaticAction extends TracedAction {
    private String title;
    private int pages;

    @Override
    public void validate() {
        called.append("validate() ");
        if (title == null || title.isBlank()) {
            addFieldError("title", "Title is required");
        }
    }

    public void validateSave() {
        called.append("validateSave() ");
        if (pages <= 0) {
            addFieldError("pages", "Pages must be positive");
        }
    }

    public void validateDoUpdate() {
        called.append("validateDoUpdate() ");
    }

    public String save() {
        called.append("save() ");
        return SUCCESS;
    }

    public String update() {
        called.append("update() ");
        return SUCCESS;
    }

    @SkipValidation
    public String list() {
        called.append("list() ");
        return SUCCESS;
    }

    public String getTitle() { return title; }
    @StrutsParameter public void setTitle(String title) { this.title = title; }
    public int getPages() { return pages; }
    @StrutsParameter public void setPages(int pages) { this.pages = pages; }
}

The Workflow Interceptor and the input Result

workflow returns the name input whenever the action has any action error, field error or conversion error. The mapping must therefore have a result called input. When it has not, Struts does not run the action and does not show the errors; it answers with an error page:

HTTP/1.1 404
No result defined for action org.example.bookshelf.ProgrammaticAction and result input

That is the output of programmatic-noinput, a mapping of save with only a success result, on Struts 7.4.0 (also the message of the no-input mapping of AddBookAction). The Basic Validation tutorial gives the same warning in its fourth step. The missing result is a ConfigurationException that the dispatcher turns into an HTTP 404, as the Exception Handling page explains.

Source: Apache Struts — Basic Validation, Step 4

Source: Apache Struts — Validation

The name of the result can be changed in four ways, from the broadest to the narrowest:

  1. The stack parameter workflow.inputResultName, for every action that uses the stack (the mapping custom-workflow above answered with the result invalid).

  2. The interface org.apache.struts2.interceptor.ValidationWorkflowAware, whose only method, getInputResultName(), lets the action choose the name for its own errors.

  3. The interface org.apache.struts2.interceptor.ValidationErrorAware, whose method actionErrorOccurred(String currentResultName) is called with the name input and may return another one; it is the hook for an action that wants to log or to react to the failure.

  4. The annotation @InputConfig(resultName = "form") on one action method (or methodName to call another method of the action instead of returning a result).

WorkflowAwareAction and ErrorAwareAction
public class WorkflowAwareAction extends TracedAction implements ValidationWorkflowAware {
    private String title;

    @Override
    public void validate() {
        if (title == null || title.isBlank()) {
            addFieldError("title", "Title is required");
        }
    }

    @Override
    public String getInputResultName() {
        return "edit-form";
    }

    public String getTitle() { return title; }
    @StrutsParameter public void setTitle(String title) { this.title = title; }
}

public class ErrorAwareAction extends TracedAction implements ValidationErrorAware {
    private String title;

    @Override
    public void validate() {
        if (title == null || title.isBlank()) {
            addFieldError("title", "Title is required");
        }
    }

    @Override
    public String actionErrorOccurred(String currentResultName) {
        called.append("actionErrorOccurred(" + currentResultName + ") ");
        return "retry";
    }

    public String getTitle() { return title; }
    @StrutsParameter public void setTitle(String title) { this.title = title; }
}

The Bookshelf rules for the "add a title" form are in one file. It has a plain validator (a rule that looks at several fields), then one field per property. It is long on purpose: it uses every built-in validator once, and each validator is explained in the next section.

AddBookAction-validation.xml (header left out)
<validators>

    <validator type="expression">
        <param name="expression"><![CDATA[pages == null || pages >= 10 || title == null || title.length() <= 20]]></param>
        <message>A short book needs a short title</message>
    </validator>

    <field name="title">
        <field-validator type="requiredstring" short-circuit="true">
            <message>Title is required</message>
        </field-validator>
        <field-validator type="stringlength">
            <param name="minLength">2</param>
            <param name="maxLength">40</param>
            <message>Title must have ${minLength} to ${maxLength} characters</message>
        </field-validator>
    </field>

    <field name="isbn">
        <field-validator type="requiredstring" short-circuit="true">
            <message>ISBN is required</message>
        </field-validator>
        <field-validator type="regex">
            <param name="regex"><![CDATA[\d{3}-\d{10}]]></param>
            <message>ISBN must look like 978-0441172719</message>
        </field-validator>
        <field-validator type="isbn">
            <param name="allowHyphens">true</param>
            <message>ISBN checksum is wrong</message>
        </field-validator>
    </field>

            <message>Pages is required</message>
        </field-validator>

            <param name="maxExpression">${maxPages}</param>

        </field-validator>
    </field>

Field and Non-Field Validators, Order and Short-Circuiting

The Validation page names two "flavours". A plain validator (expression is the standard one) checks the action as a whole. It has no field name, and its failure is an action error. A field validator checks one property, and its failure is a field error. The flavour is a property of the validator class (the framework looks at whether it implements org.apache.struts2.validator.FieldValidator); the XML only says which syntax to use:

Syntax Use

<field name="x"><field-validator type="...">

Field validators only; the field name is inherited, and the DTD does not allow a plain validator inside field

<validator type="...">

Both kinds; a field validator written here needs <param name="fieldName">x</param>

The guide recommends the field syntax for every field validator because it groups all the rules of a property.

Messages: Text, Keys and Parameters

Every validator or field validator has exactly one message element. Its body is the default text; its optional key attribute names a key in the action’s resource bundles, looked up with getText() of the action (so the message follows the locale of the request when the action implements LocaleAware, as ActionSupport does). When the validator fails, the validator itself is pushed on the value stack and the text is scanned for ${...} sections, which are replaced with the value of the OGNL expression between the braces. That is why ${min} and ${max} in an int message print the validator’s own parameters, while ${pages} prints the action’s property, as in the Bookshelf message "Pages must be between 10 and 800, got 0".

Source: Apache Struts — Validation, Localizing and Parameterizing Messages

A second form adds param children to the message and uses the MessageFormat placeholders of the properties file: the names of the params do not matter, their order does, and each is an OGNL expression evaluated against the value stack. Custom Validators

A validator is a class with a validate(Object action) method that adds an error when the check fails. Pick the base class that fits: ValidatorSupport for a plain validator, FieldValidatorSupport for a validator of one field (it supplies getFieldName(), getFieldValue(...) and the error methods), RangeValidatorSupport for ranges, and RepopulateConversionErrorFieldValidatorSupport for validators that repopulate the field after a conversion error. In Struts 7 they are in org.apache.struts2.validator.validators; the Validation page still lists the com.opensymphony.xwork2.validator.validators names. The Bookshelf validates the ISBN-13 check digit:

IsbnValidator: a field validator
public class IsbnValidator extends FieldValidatorSupport {
    private boolean allowHyphens = true;

    public void setAllowHyphens(boolean allowHyphens) {
        this.allowHyphens = allowHyphens;
    }

    @Override
    public void validate(Object object) throws ValidationException {
        String fieldName = getFieldName();
        Object value = getFieldValue(fieldName, object);
        if (value == null || value.toString().isBlank()) {
            return; // an empty value is the job of the required validators
        }
        String digits = allowHyphens ? value.toString().replace("-", "") : value.toString();
        if (!isValidIsbn13(digits)) {
            addFieldError(fieldName, object);
        }
    }

    static boolean isValidIsbn13(String digits) {
        if (digits.length() != 13 || !digits.chars().allMatch(Character::isDigit)) {
            return false;
        }
        int sum = 0;
        for (int i = 0; i < 13; i++) {
            sum += (digits.charAt(i) - '0') * (i % 2 == 0 ? 1 : 3);
        }
        return sum % 10 == 0;
    }
}

Generated JavaScript validation (deprecated)

<s:form validate="true"> in the xhtml and css_xhtml themes generates JavaScript from the same validation files. It supports only a subset of the validators (required, requiredstring, stringlength, regex, email, url, int, double), not the visitor validator, and needs the action name and namespace to be resolvable. It is deprecated since Struts 7.4.0 (WW-5694) and is announced for removal in Struts 8.0.0 (WW-5696); new code should use the HTML5 constraints or the AJAX validation below.

AJAX validation

The third mechanism sends the form to the server on each onblur event and shows the errors without a page reload. The server side is the jsonValidation interceptor and a JSON result of the JSON plugin (see JSON Plugin & AJAX); the client side is the application’s own script. The whole stack, including the visitor validators and validate(), runs, so every rule that works on submit works in the browser. The guide notes that the former Dojo client of the framework is gone.

Notes on the Official Documentation

Reading the official pages against the 7.4.0 jar showed inconsistencies that a reader will meet; they are listed so that a mismatch is not mistaken for a mistake in the example code.

  • The Validation page’s "Writing custom validators" list and the Default Workflow Interceptor page still name classes in com.opensymphony.xwork2; in 7.4.0 they are in org.apache.struts2.validator.validators and org.apache.struts2.

  • The "Bundled Validators" list and the annotation index omit long and creditcard (with no page) and the annotations @CreditCardValidator, @LongRangeFieldValidator, @ShortRangeFieldValidator and @ConditionalVisitorFieldValidator.

  • The regex validator page lists the parameter as regexp; the class has setRegex and every example uses regex.

  • The Form Validation Using XML tutorial spells the parameter fieldname; the other pages spell it fieldName. Both work.

  • The Validation page says alwaysInvokeValidate is an option of validation; on the Default Workflow Interceptor page it is mentioned in the workflow text, but the 7.4.0 jar has the setter only on the validation interceptor.

  • The section on slashes in action names does not mention struts.mapper.alwaysSelectFullNamespace, without which the mapping is not found.

  • The Validation page says a short-circuited plain validator stops the field validators; verified within one file, but across files the class file’s validators run first.
