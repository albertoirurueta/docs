UI & Form Tags

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Struts 7.4.0 (released 2026-10-02) running on Apache Tomcat 11.0.26 and Java 21, the combination that every example was built, deployed and requested on; the facts were checked on 2026-10-08 and 2026-10-10 against the Tag Developers Guide on https://struts.apache.org/tag-developers/, the Getting Started tutorial on form tags, the Core Developer Guide pages on the checkbox and multiselect interceptors, the 7.4.0 struts2-core jar (struts-tags.tld, the FreeMarker templates under template/, default.properties) and the 7.4.0 struts2-javatemplates-plugin. The UI tags are the half of the Struts tag library that writes HTML: unlike a generic tag, which prints a value, a UI tag hands its attributes to a template, and the template writes the markup, the label, the error rows and the surrounding table or div. This page walks the form tags one by one, with their attributes and the HTML each one produced. The running scenario is the Bookshelf, a catalogue of books exposed as Struts actions; here it is an edit form for one title (title, ISBN, price, publication date, genre, format, tags, stock flag, summary). The generic and control tags, the themes and the template language are the subjects of other pages of this section (Tags Overview & Generic Tags, Themes & Templates, FreeMarker & Velocity Views). The pages on Actions, Type Conversion, Validation, Localization and i18n and Double-Submit Tokens & Wait Pages are linked where they help.

What the UI Tags Do

The Tag Developers Guide describes UI tags as the tags "focused on using data" from the action or the data tags and "displaying data in rich and reusable HTML"; all of them are driven by templates and themes. A JSP page that says <s:textfield name="book.title"/> makes the framework do the following:

  1. read the attribute values (evaluating OGNL where an attribute is an expression);

  2. derive what the attributes leave out: the id from the form and the name, the value from the property named by name, the label from the key, the error list from the action’s field errors;

  3. pick a template (template/<theme>/text.ftl for a textfield) and render it with the attributes in a hash;

  4. write the result to the page.

The same work is done by every tag of the table below, which groups the 7.4.0 UI tags by what they render. The tag library descriptor of the jar (/struts-tags, tlib-version 6.0, short name s) declares them next to the generic tags; all of them accept the common attributes described later.

The Bookshelf Used on This Page

All examples below are classes, views and mappings of one WAR, g10uitags.war, deployed under the context path /g10uitags on Tomcat 11.0.26 (the Struts BOM struts2-bom 7.4.0, struts2-core, Servlet API 6.1 and JSP API 4.0 as provided, one StrutsPrepareAndExecuteFilter mapped to /*; see Getting Started with Struts 2). Every "Observed" block is the literal response of a request to that WAR, shortened only where it says so. The model is a Book bean with the properties the form needs, and one action class serves every view:

public class CatalogAction extends ActionSupport {
    private Book book = new Book();   // title, isbn, price, publishedOn, genre, format, tags, inStock, summary
    private String note;

    public CatalogAction() {          // the "Dune" record that the form starts from
        book.setTitle("Dune");
        book.setIsbn("9780441172719");
        book.setGenre("sf");
        book.getTags().add("classic");
        book.setSummary("Spice & sand");
    }

    @StrutsParameter(depth = 2)       // lets the params interceptor fill book.title, book.tags[0], ...
    public Book getBook() { return book; }

    public String getNote() { return note; }
    @StrutsParameter
    public void setNote(String note) { this.note = note; }

    public Map<String, String> getGenreMap() { /* sf -> "Science fiction", fantasy, crime */ }
    public List<String> getTagChoices() { return List.of("classic", "new", "signed", "rare"); }

    @Override
    public void validate() {
        if (book.getTitle() == null || book.getTitle().isBlank()) {
            addFieldError("book.title", "Title is required");
        }
        if (book.getIsbn() != null && !book.getIsbn().matches("\\d{13}")) {
            addFieldError("book.isbn", "ISBN needs 13 digits");
        }
    }

    public String save() { return SUCCESS; }
}

Source: Apache Struts — Getting Started, Processing Form Input In The Action Class

Source: Apache Struts — StrutsParameter Annotation, Usage

The mapping uses one wildcard so that a view called edit.jsp is shown by page-edit and posted to save-edit, and the OGNL allowlist is opened for the model package, the setting that the value stack page of this section explains (without it the tags cannot read book.title, and the textfield stays empty):

<struts>
    <constant name="struts.allowlist.packageNames" value="org.example.bookshelf"/>
    <package name="default" extends="struts-default" namespace="/">
        <action name="page-*" class="org.example.bookshelf.CatalogAction">
            <result>/WEB-INF/views/{1}.jsp</result>
            <result name="input">/WEB-INF/views/{1}.jsp</result>
        </action>
        <action name="save-*" class="org.example.bookshelf.CatalogAction" method="save">
            <result name="input">/WEB-INF/views/{1}.jsp</result>
            <result>/WEB-INF/views/saved.jsp</result>
        </action>
    </package>
</struts>

The Round Trip of a Form

A form tag is one half of a conversation; the other half is the interceptor stack. The tags write field names that the params interceptor later reads back, hidden helper fields that the checkbox and multiselect interceptors read, and they read the field errors that the workflow interceptor leaves in the action when it returns input.

flowchart LR A["page-edit: action runs, JSP renders s:form and the field tags"] --> B["Browser shows the form (names, values, hidden helper fields)"] B --> C["POST save-edit"] C --> D["checkbox and multiselect interceptors add false and empty lists for missing controls"] D --> E["params interceptor: book.title, book.tags and so on, with type conversion"] E --> F["validation interceptor: validate() and -validation.xml add field errors"] F --> G{"errors or conversion errors?"} G -- "yes: workflow returns input" --> H["same JSP again: tags read fieldErrors and the submitted values"] G -- "no" --> I["save() runs, success result"] H --> B

Source: Apache Struts — Checkbox Interceptor, How it works

Source: Apache Struts — Multiselect Interceptor

Four consequences follow and are used below. A tag needs a name that is a path the params interceptor can set. The value shown after a failed round trip is the submitted text, not the converted property, when the conversion failed (the type conversion page of this section describes the mechanism). The error rows come from the action, so a view rendered by an action other than the one that validated (for example the page that just shows an empty form) has none. And the helper fields work only when the matching interceptor is in the stack, which defaultStack of 7.4.0 guarantees (checkbox is the twelfth, datetime the thirteenth and multiselect the fourteenth of its interceptors, all ahead of params, the seventeenth, as listed on the interceptors page).

The s:form Tag

s:form renders the form element and gives every tag inside it three things: the form’s id (the prefix of the ids of the fields), the theme (the xhtml theme opens a table that the fields fill with rows), and a place for the form-wide defaults of the label position and the tooltips. The Tag Developers Guide calls it a different kind of tag from the others: the "behavior of the form tag is different from the elements enclosed within it".

How the action URL is built

The Form Tag page gives the order of the decision. With no action attribute the current request decides the URL. With an action that is an alias in the configuration the framework asks the configuration for it (in the given or the current namespace) and builds the URL with the action extension. With an action that is not an alias in that namespace the value is used as a URL, "separating the namespace from it". The results of seven forms, each in a view rendered by the action page-misc on a first request that had no session cookie, make the rule concrete:

<s:form><s:textfield name="a"/></s:form>
<s:form action="save-misc"><s:textfield name="a"/></s:form>
<s:form action="save-misc" namespace="/admin"><s:textfield name="a"/></s:form>
<s:form action="nope/save-misc"><s:textfield name="a"/></s:form>
<s:form action="/save-misc.action?x=1"><s:textfield name="a"/></s:form>
<s:form action="save-misc" includeContext="false" namespace="/"><s:textfield name="a"/></s:form>
<s:form action="http://example.com/x"><s:textfield name="a"/></s:form>

Observed (the form start tags, with <sid> standing for the 32-character session id):

<form id="page_misc" name="page_misc" action="/g10uitags/page-misc.action;jsessionid=<sid>" method="post">
<form id="save_misc" name="save_misc" action="/g10uitags/save-misc.action;jsessionid=<sid>" method="post">
<form id="save_misc_jsessionid_<sid>" name="save_misc_jsessionid_<sid>" action="save-misc;jsessionid=<sid>" method="post">
<form id="save_misc_jsessionid_<sid>" name="save_misc_jsessionid_<sid>" action="nope/save-misc;jsessionid=<sid>" method="post">
<form id="save_misc" name="save_misc" action="/g10uitags/save-misc.action;jsessionid=<sid>?x=1" method="post">
<form id="save_misc" name="save_misc" action="/save-misc.action" method="post">
<form id="x" name="x" action="http://example.com/x" method="post">

Source: Apache Struts — Form Tag, Description

Four lessons come out of the seven lines. The action name is the whole address: there is no /g10uitags/ anywhere to write by hand, and a typo or a wrong namespace (third and fourth forms) does not fail; the tag falls back to the literal text, which becomes a relative URL, and the page works until it is served from a different path. Second, the ;jsessionid=... part exists only on the first response, before the browser has returned the session cookie, because the tag encodes the URL; once the cookie is known the URL is clean. A third consequence of the same fallback is visible in the id of the third and fourth forms: the id and name are derived from the text of the URL, so the session id ended up inside the id (save_misc_jsessionid_<sid>) and the ids of all fields in the form carry it too. Fourth, includeContext="false" drops the context path (/save-misc.action), which is right only for an application deployed as the root context; for any other path it posts to a different web application.

Attributes the form passes through

Any attribute that the tag library does not declare is a dynamic attribute and is written to the element. The HTML5 data-* and aria-* attributes, placeholder, required and autofocus therefore work on every tag of the library. The view below also uses focusElement, which takes the id that the tag generated for the field (<formId>_<fieldName> with dots turned into underscores), and s:head for the StrutsUtils script that runs the focus code:

<s:form action="save-formattrs" namespace="/" method="get" enctype="multipart/form-data" acceptcharset="UTF-8"
        target="_blank" cssClass="stacked" cssStyle="width:20em" onsubmit="return true;" id="bookForm"
        includeContext="false" theme="simple" data-test="42" aria-label="Edit">
    <s:textfield name="book.title" tabindex="2" accesskey="t" title="Book title" placeholder="Title here"
                 required="true" data-x="y" autofocus="true"/>
</s:form>

Observed:

<form id="bookForm" name="bookForm" onsubmit="return true;" action="/save-formattrs.action" target="_blank" method="get"
      enctype="multipart/form-data" class="stacked" style="width:20em" accept-charset="UTF-8" data-test="42"
      aria-label="Edit">
<input type="text" name="book.title" value="Dune" tabindex="2" id="bookForm_book_title" title="Book title" accesskey="t"
       data-x="y" placeholder="Title here" autofocus="true" required="true"/>
</form>

Source: Apache Struts — Form Tag, Attributes

The element also shows that required="true" on a tag is a plain HTML attribute (the browser enforces it), not the Struts notion of a required field: the label star of the xhtml theme needs requiredLabel="true", and the Core Developer Guide stresses that the two are unrelated. Lower-case spellings of the layout attributes from Struts 2.0-era documents (labelposition, requiredposition) are not recognised: they too become dynamic attributes and appear on the element (observed on <s:form labelposition="top">, which printed labelposition="top" on the form tag while the fields kept the default left layout); the attributes are labelPosition and requiredPosition.

Source: Apache Struts — Client Side Validation, requiredLabel is unrelated to the required attribute

The name and value relationship

The Tag Developers Guide explains the central rule: name is both the request parameter that the control submits and the property that fills it. <s:textfield name="book.title"/> therefore calls getBook().getTitle() for the value and, on submit, the params interceptor calls getBook().setTitle(...). The value attribute is optional; a template that needs the value reads attributes.nameValue, because the key value is not what it contains. Writing both is not wrong, but the explicit value="%{...}" hides the property, and after a failed submit the tag still shows the submitted text for a field that has a conversion error (next sections).

Generated ids

The Guide says "all form tags automatically assign an ID to the control": a form’s id is the action name and a control’s id is the form’s name joined to the field name. The Bookshelf views above show it: the form save_edit and the field book.title give save_edit_book_title. Labels point to that id with for, so a label click focuses the field. Two fields with the same name in one form get the same id (the view of the next sections that repeats book.genre has duplicates), which is invalid HTML; pass id explicitly when a name repeats.

Label position and inheritance

labelPosition on the form is propagated to every field in it and a field’s own attribute wins (the Guide marks this "Since 2.3.17"). A form with labelPosition="top" whose first field asks for a star on the left and a different separator, and whose second field overrides the position, rendered these rows in the xhtml theme:

<s:form action="save-lp" labelPosition="top">
    <s:textfield name="book.title" label="Title" requiredLabel="true" requiredPosition="left" labelSeparator=" -"/>
    <s:textfield name="book.isbn" label="ISBN" labelPosition="left"/>
</s:form>

Observed (the table rows):

<tr>
    <td class="tdLabelTop" colspan="2"><label for="save_lp_book_title" class="label"><span class="required">*</span>Title -</label></td>
</tr>
<tr>
    <td class="tdInput"><input type="text" name="book.title" value="Dune" id="save_lp_book_title"/></td>
</tr>
<tr>
    <td class="tdLabel"><label for="save_lp_book_isbn" class="label">ISBN:</label></td>
    <td class="tdInput"><input type="text" name="book.isbn" value="9780441172719" id="save_lp_book_isbn"/></td>
</tr>

Source: Apache Struts — Form Tags, Form labelposition propagation

The star came from requiredLabel="true" requiredPosition="left", and labelSeparator=" -" replaced the colon; the first field took the form’s top position (own row for the label) and the second one its own left. Without requiredLabel no star is drawn, even for a field that a validator requires: the Guide’s "Required Attribute" section says the required attribute defaults to true "only if you have client-side validation enabled, and a validator is associated with that particular field"; a form with validate="true" and a requiredstring validator for the field printed Title: without a star in the Bookshelf (the label became errorLabel after a failed submit, and nothing else changed).

Source: Apache Struts — Form Tags, Required Attribute

Validation in the Browser

Server-side errors are shown by the tags as described above. Two features try to catch an error before the request.

Generated JavaScript (deprecated)

s:form validate="true" in an xhtml or css_xhtml form includes /static/xhtml/validation.js and generates a function validateForm_<id> that is called from onsubmit. The page of the Core Developer Guide on client side validation marks it "deprecated since Struts 7.4.0 (WW-5694), removed in Struts 8.0.0 (WW-5696)" and the templates carry the same comment. It understands only the validators required, requiredstring, stringlength, regex, email, url, int and double. On the Bookshelf, a CatalogAction-clientform-validation.xml file with requiredstring for book.title and stringlength for book.isbn produced, in the page that the action clientform rendered after an invalid post, rules like these:

// field name: book.title
// validator name: requiredstring
if (form.elements['book.title']) {
    field = form.elements['book.title'];
    var error = "Title is required (client)";
    var fieldValue = getFieldValue(field);
    if (continueValidation && fieldValue !== null && (fieldValue === "" || fieldValue.replace(/^\s+|\s+$/g,"").length === 0)) {
        addError(field, error);
        errors = true;
    }
}

Source: Apache Struts — Client Side Validation, Pure JavaScript Client Side Validation (deprecated)

In the same experiment a plain page-client view, rendered by an action that has no validation file (the form’s action pointed at save-client, which had one), produced the function with no rules at all, and so did the view client2.jsp whose form pointed at clientform but was rendered by page-client2; the rules appeared only when the page was rendered by the action that owns the validators (here clientform, by a post that failed validation). The Guide says the code is generated "from the same validation configuration used server-side"; in 7.4.0 the validators are those of the current action. Together with the removal announced for 8.0, a new project should not use it.

HTML5 constraints

The replacement is the html5 theme with struts.ui.html5.constraints=true, which derives required, minlength, maxlength, pattern, min and max from the action’s validators. The validation page of this section has the mapping table and the worked example, so only the pointer is repeated here: the browser enforces the attributes, the server validation still runs, and requiredLabel is a different thing (a star on the label; it never makes a field required).

Notes on the Official Documentation

Reading the official pages against the 7.4.0 jar showed inconsistencies that a reader will meet; they are listed so that a mismatch is not mistaken for a mistake in the example code.

  • The Getting Started "Form Tags" tutorial, the Checkbox Interceptor page and the Hidden Field Prefix section of the Checkbox Tag page say the checkbox tag writes the hidden __checkbox_... field by itself; in 7.4.0 it does so only with submitUnchecked="true" (the attribute’s own row says so and gives the constant "since Struts 6.1.1").

  • The Form Tags page says the framework "bundles three themes"; the 7.4.0 jar has four (html5 since 7.2.0), and the html5 Theme page lists "Validation and error reporting" as a feature although its controlheader and controlfooter templates are empty.

  • The Form Tags page lists the general attribute as tabIndex; the tag library descriptor declares tabindex (a camel-case tabIndex is not a declared attribute).

  • The Form Tag page, and the descriptor of s:form, still say validate is "only useful with theme xhtml/ajax"; there is no ajax theme, and the page’s own "Validation" section says the attribute is deprecated since 7.4.0.

  • The Form Tags page’s tooltip examples 3 to 5 open their comments with <-- instead of <!--.

  • The Select Tag page warns that a map key of another type than the value does not match ('1' against '01' or "1"); on 7.4.0 all seven combinations tried selected the option.

  • The Fielderror Tag page’s last example repeats <s:fielderror fieldName="field1" /> twice.

  • The Datetextfield Tag page and the descriptor say "Render an HTML input fields with the date time" and give no example, while the 7.4.0 templates print "works only with the JavaTemplates Plugin!" and the plugin page asks for struts.ui.theme set to simple.

  • The Getting Started "Form Tags" page shows a radio id save_personBean_gendernot sure: ids built from list keys keep the spaces.

  • The Submit Tag description still calls it a tag "to provide asynchronous form submissions" and warns about Internet Explorer 6; the Reset Tag descriptor lists image as a valid type although the tag page lists two types.
