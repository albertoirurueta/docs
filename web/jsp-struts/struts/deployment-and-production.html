Deployment & Production

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Struts 7.4.0 (released 2026-10-02) on Apache Tomcat 11.0.26 and Java 21; everything was checked on 2026-10-08 and 2026-10-10 against the Core Developer Guide pages Performance Tuning, Static Content, Application Servers, OGNL Cache Configuration and Reloading Configuration, the default.properties and StrutsConstants of the 7.4.0 struts2-core jar, the Tomcat 11 documentation and the example and archetype resources named at the end. Every Struts and Tomcat example was built into a Maven WAR (g12prod.war and a family of smaller scratch WARs) and exercised with curl on Tomcat 11.0.26, on a private Tomcat instance with its own CATALINA_BASE so that its server.xml could be changed; the same WAR was also started on the Jetty 12.1.14 Maven plugin and deployed to GlassFish 8.0.5. The Docker daemon and a Kubernetes cluster were not available for this page, so the Docker and Kubernetes files are shown as the part that is specific to a Struts WAR and are labelled as not run; the Kubernetes manifest was only parsed. A Struts application is an ordinary WAR. "Going to production" therefore means three things: switching off what exists only to help the developer, letting the right component serve each kind of request (static files by the container or a proxy, actions by Struts), and applying the usual container hardening. The running scenario is the Bookshelf, a catalogue of books exposed as Struts actions; here it is built once as a production WAR and smoke-tested the way a deployment pipeline would. The pages on testing, debugging and logging, security hardening, security headers and security bulletins cover the neighbouring topics.

Who Handles Which Request

In production a request passes through more components than on a developer’s laptop, and the useful question for most problems is which of them answers. The figure shows the path of the Bookshelf WAR of this page.

flowchart LR C["Browser"] --> P["Reverse proxy or load balancer: TLS, compression, caching"] P -->|"X-Forwarded-Proto and X-Forwarded-For"| T["Tomcat connector: optional gzip"] subgraph app["Tomcat: the Bookshelf web application"] V["Host valves: RemoteIpValve, ErrorReportValve"] --> E["ExpiresFilter for /static and /assets"] E --> S["StrutsPrepareAndExecuteFilter"] S -->|"action found"| A["Action, then JSP"] S -->|"excludePattern or no action mapping"| D["Container default servlet and HealthServlet"] end T --> V A --> R["HTML response"] D --> R2["Static file, health answer or error page"]

The proxy and the connector are the only components that can see the original scheme and client address, which is why the valve at the start of the Tomcat pipeline restores them (see Behind a Reverse Proxy). The filter mapped to /* sees every request that reaches the web application and decides in two steps: if the URL starts with the static content path and Struts serves static content, it answers itself; otherwise it asks the action mapper for an action. A request with no action falls through to the next filter and, finally, to a servlet; that is how assets/app.css is served by Tomcat’s default servlet in the verification below, and also why an extensionless servlet URL needs the exclusion of Health Checks and Startup Failure.

Static Content

Struts can serve static files itself. The Core Developer Guide describes the arrangement: the constant struts.ui.staticContentPath (default /static) names a path prefix, the StaticContentLoader (default DefaultStaticContentLoader) answers requests under it from the classpath, and the same path serves the files that the xhtml and css_xhtml themes need (s:head emits links to them). The Bookshelf shows the default arrangement first.

A request that Struts serves itself (defaults, headers as observed)
$ curl -s -D - -o /dev/null http://localhost:18081/g12deploy/static/utils.js
HTTP/1.1 200
Expires: Sun, 11 Oct 2026 11:05:50 GMT
Retry-After: Sun, 11 Oct 2026 11:05:50 GMT
Cache-Control: public
Last-Modified: Sat, 10 Oct 2026 11:05:45 GMT
Content-Type: text/javascript

Struts adds Cache-Control: public and an Expires one day ahead, the browser-cache behaviour that struts.serve.static.browserCache=true stands for; the Retry-After header with the same date is sent too and means nothing for a 200. With struts.serve.static.browserCache=false the answer carries Cache-Control: no-cache, Pragma: no-cache and Expires: -1 instead, which is useful while the static files of a plugin change. Both forms are verified on 7.4.0.

Changing or Disabling the Path

Two constants move or switch off the arrangement. Moving the path is a one-line constant; the old path then answers 404 and the new one 200 (observed).

struts.ui.staticContentPath
<constant name="struts.ui.staticContentPath" value="/assets-struts"/>

Source: Core Developer Guide — Static Content, Default path

Disabling it is the production choice when the container, a CDN or a proxy serves the files.

struts.serve.static
<constant name="struts.serve.static" value="false"/>

Source: Core Developer Guide — Static Content, Disabling static content

With the constant false a request for /static/utils.js answers 404 (observed), but the tags do not know that: s:head still writes the links, so a page that uses the xhtml theme and s:head needs the files to exist somewhere. The Core Developer Guide says so ("make sure the JavaScript and CSS files shipped inside the core jar are extracted to your web application directory"). Extraction is a build step. The files are not under static/ in the jar; they are under org/apache/struts2/static/ and, for the theme stylesheets, template/<theme>/styles.css, and the loader maps them to the URLs below, so the copy has to reproduce the URLs.

Extracting the static files of the Struts 7.4.0 jar into the web application (run once, commit the result or run in the build)
J=$HOME/.m2/repository/org/apache/struts/struts2-core/7.4.0/struts2-core-7.4.0.jar
mkdir -p tmp && (cd tmp && unzip -q "$J" "org/apache/struts2/static/*" \
    "template/xhtml/styles.css" "template/css_xhtml/styles.css")
D=src/main/webapp/static
mkdir -p $D/xhtml $D/css_xhtml
cp tmp/org/apache/struts2/static/* $D/
cp tmp/template/xhtml/styles.css $D/xhtml/
cp tmp/template/css_xhtml/styles.css $D/css_xhtml/
rm -rf tmp

Source: Core Developer Guide — Static Content, Default Content Loader

After this copy and with struts.serve.static set to false, the page produced by s:head linked /g12prod/static/xhtml/styles.css and /g12prod/static/utils.js, and Tomcat’s default servlet answered both with 200 and, through the ExpiresFilter of The Bookshelf Production WAR, Cache-Control: max-age=604800 and an Expires seven days ahead (observed). The application’s own files under assets/ get the same headers.

Headers of the static files in the production WAR (observed)
$ curl -s -D - -o /dev/null http://localhost:18081/g12prod/static/utils.js
HTTP/1.1 200
Cache-Control: max-age=604800
Expires: Sat, 17 Oct 2026 11:26:41 GMT
Content-Type: text/javascript;charset=ISO-8859-1

The charset=ISO-8859-1 on a JavaScript file comes from Tomcat’s default servlet and its file-encoding default, not from Struts; a proxy or an explicit <mime-mapping> and fileEncoding setting changes it, and it is harmless for the ASCII-only files of the jar. A seven-day lifetime is safe for files whose names change when the content changes (a build hash, a version directory) and a risk for app.css under a fixed name: a long max-age means returning visitors keep the old file, so production builds either fingerprint the name or use a short lifetime with validation (ETag, Last-Modified), which Tomcat’s default servlet sends for files on disk.

Keeping Requests Away from Struts

Files and servlets of the application itself are not served by the Struts loader. They pass through the Struts filter, which tries to map the URL to an action and, finding none, lets the request continue. The mapping step is where a surprise sits: the 7.4.0 default struts.action.extension is action,,, so an extensionless URL is a candidate action name. A file with an extension (/assets/app.css) passes; an extensionless servlet URL (/health) does not.

A servlet at an extensionless URL is swallowed by the Struts filter (observed)
$ curl -s -i http://localhost:18081/g12deploy/health | head -1
HTTP/1.1 404
$ curl -s http://localhost:18081/g12deploy/health | grep -o "There is no Action mapped[^.]*"
There is no Action mapped for namespace [&#47;] and action name [health] associated with context path [&#47;g12deploy]

The remedy is the exclude pattern: a comma-separated list of regular expressions matched against the request URI, which makes the filter pass matching requests untouched.

struts.action.excludePattern
<constant name="struts.action.excludePattern" value="/health,/assets/.*"/>

With it /health answered 200 UP and /assets/app.css 200 (observed). Since Struts 6.1.0 a separator other than the comma can be chosen with struts.action.excludePattern.separator when a pattern itself needs a comma. The expressions are Java regular expressions, matched with the whole URI including the context path, so write them with care and prefer a narrow pattern to .*.

WebJars

Since Struts 7.3.0 the same pipeline serves WebJars, the client-side libraries (Bootstrap, jQuery) packaged as JARs under META-INF/resources/webjars/<name>/<version>/. The core jar bundles webjars-locator-lite, and the webjar tag writes the URL. The Bookshelf added org.webjars:bootstrap:5.3.8 and one tag.

A WebJar stylesheet in the page
<link rel="stylesheet" href="<s:webjar path="bootstrap/css/bootstrap.min.css"/>">
The page and the files it links (observed)
$ curl -s http://localhost:18081/g12wj/books | grep -o 'href="[^"]*bootstrap[^"]*"'
href="/g12wj/static/webjars/bootstrap/5.3.8/css/bootstrap.min.css"
$ curl -s -o /dev/null -w "%{http_code}\n" .../static/webjars/bootstrap/5.3.8/css/bootstrap.min.css
200
$ curl -s -o /dev/null -w "%{http_code}\n" .../static/webjars/bootstrap/css/bootstrap.min.css
200

Several details follow from the run. The tag writes the versioned URL, although the page describes version-less requests; both forms are served. WebJars ride the static pipeline, so they need struts.serve.static to be true: with false both URLs answered 404, and a WebJar application that disables Struts static serving must let the container serve the jar’s META-INF/resources itself (the Servlet specification makes a container serve it for jars in WEB-INF/lib, under the path /webjars/...; that route was not run here). struts.webjars.allowlist restricts the names: with jquery as the allowlist the Bootstrap URL answered 404 and the tag wrote an empty href. Path traversal (.. and its encoded form) answered 404. The constants are struts.webjars.enabled (default true) and struts.webjars.allowlist (default empty, meaning every WebJar on the classpath).

Source: Core Developer Guide — Static Content, WebJars support

Source: Tag Developer Guide — webjar Tag

The theme side of static content (s:head, the stylesheet of each theme, overriding templates) is in Themes and Templates. For a high-traffic site the guide’s advice is the same as for any web application: move the files to a separate server or a CDN and let a cache layer in front of Tomcat serve them, which is what struts.serve.static=false makes possible.

HTTP Caching of Dynamic Pages

The tip "use the correct HTTP headers" is about dynamic HTML. Struts adds no Cache-Control to an action’s response (the production request matrix below shows none on /books), so the response carries no caching directive at all. A page that shows personal data must say Cache-Control: no-store, and a public catalogue page can be cached for a short time. Sessions, I18nInterceptor and the Interceptor Stack

Struts itself does not create a session unless something asks. Two things ask without being noticed. A JSP creates a session by default (page directive session="true"), so the production books.jsp says session="false". And the i18n interceptor, which is part of the default stack, stores the locale chosen with request_locale in the session. The Bookshelf shows it.

Which requests create a session (observed; the session id is replaced by a placeholder)
$ curl -s -D - -o /dev/null http://localhost:18081/g12deploy/books | grep -i set-cookie
$ curl -s -D - -o /dev/null "http://localhost:18081/g12deploy/books?request_locale=es" | grep -i set-cookie
Set-Cookie: JSESSIONID=<id>; Path=/g12deploy; HttpOnly

The first request has no cookie (the page has session="false" and nothing else touches the session); the second has one. In this run only the request with request_locale created a session; an application that wants stateless, cache-friendly pages never sends the parameter or removes the interceptor from the stack (A Leaner Stack Has a Price shows the price). Sessions matter for scaling: each one is memory in the container and, in a cluster, state that the load balancer has to keep together or the container has to replicate; replicated session attributes must be Serializable (a servlet-container rule that this page did not run), so keep action objects out of the session and put in it only the user and a few small values. The sibling topic page, Action Chaining, Sessions and Scopes, covers what is legitimate to keep there, and Localization and i18n the interceptor.

A Leaner Stack Has a Price

The defaultStack of 7.4.0 has 24 interceptors, and the tip to use a smaller one is easy to follow with a stack that the framework already defines: validationWorkflowStack is basicStack plus validation and workflow. The Bookshelf action was switched to it with one line.

Using validationWorkflowStack for one action
<action name="books" class="org.example.bookshelf.BookAction">
    <interceptor-ref name="validationWorkflowStack"/>
    <result>/WEB-INF/views/books.jsp</result>
</action>
Same request, default stack against validationWorkflowStack (observed)
$ curl -s -D - -o /dev/null "http://localhost:18081/g12deploy/books?request_locale=es"
# defaultStack: Set-Cookie JSESSIONID, Vary: Sec-Fetch-*, Cross-Origin-Embedder-Policy-Report-Only: require-corp,
#               Cross-Origin-Opener-Policy: same-origin
# validationWorkflowStack: no cookie, none of those headers

The saving is real (no session, fewer interceptors) and so is the loss. The coop, coep and fetchMetadata interceptors of the 7.4.0 default stack write the Cross-Origin headers and the Vary header of the Sec-Fetch family and implement a resource isolation policy based on the fetch metadata, and the csp interceptor belongs to the same family; the debugging interceptor is what answers ?debug= in development. A stack that omits them is a stack without those protections. The security headers page of this section explains each one; the rule here is that "do not use interceptors you do not need" now includes security interceptors, and that a custom stack should be built by copying defaultStack and deleting named entries, not by starting from basicStack. Logging

Log level is the tip with the largest effect. Struts and FreeMarker log a great deal at debug. On the Bookshelf, with org.apache.struts2 and freemarker at debug, one warm request to /books wrote 267 lines to standard output; with no log4j2.xml and with warn it wrote none. A production log4j2.xml therefore sets the two loggers to warn, the root to info and writes to the console, which is where Tomcat, Docker and Kubernetes collect logs.

src/main/resources/log4j2.xml
<?xml version="1.0" encoding="UTF-8"?>
<Configuration status="WARN">
  <Appenders>
    <Console name="Console" target="SYSTEM_OUT">
      <PatternLayout pattern="%d{ISO8601} %-5level %logger{1} - %msg%n"/>
    </Console>
  </Appenders>
  <Loggers>
    <Logger name="org.apache.struts2" level="warn"/>
    <Logger name="freemarker" level="warn"/>
    <Root level="info">
      <AppenderRef ref="Console"/>
    </Root>
  </Loggers>
</Configuration>

Context Paths, ROOT.war and Parallel Deployment

Tomcat derives the context path from the file name of the WAR. A WAR named g12deploy.war is served under /g12deploy, a WAR named ROOT.war at /, and a name with ## before a version string deploys several versions of the same path side by side, so that a new version can take new sessions while the old one drains. All three were run on the private instance.

The three naming forms (observed)
$ cp g12deploy.war base/webapps/ROOT.war
$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:18081/books
200
$ curl -s http://localhost:18081/books | grep -o 'action="[^"]*"'
action="/books.action"
$ cp g12deploy.war 'base/webapps/g12pd##001.war' && cp g12deploy.war 'base/webapps/g12pd##002.war'
$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:18081/g12pd/books
200

With ROOT.war the form action is /books.action, because Struts builds links from the context path, which is empty; no URL in the application may hard-code the old prefix. In a parallel deployment Tomcat sends a request without a session to the latest version and a request with a session to the version that owns it (the rule of the Tomcat documentation); the two WARs are separate web applications with their own Struts configuration and caches. Remove the older version after its sessions have ended, and remember that anything with state outside the web application (a database schema, a shared cache) must work with both versions at once, which is the real constraint of a rolling upgrade.

Behind a Reverse Proxy

A production Struts application is nearly always behind a proxy or load balancer that terminates TLS. The container then sees plain HTTP from the proxy, and Struts, which builds absolute URLs from the request, would write http:// links. The s:url tag with forceAddSchemeHostAndPort shows the effect, and RemoteIpValve the fix; the proxy has to send X-Forwarded-Proto and the host.

An absolute URL without and with the proxy headers (observed, a host name invented for the test)
$ curl -s http://localhost:18081/g12deploy/books | grep abs
<p id="abs">http://localhost:18081/g12deploy/books.action</p>
$ curl -s -H 'X-Forwarded-Proto: https' -H 'Host: books.example.test' http://localhost:18081/g12deploy/books | grep abs
<p id="abs">https://books.example.test/g12deploy/books.action</p>

The default internalProxies of the valve match loopback and private addresses, which is why the test from the same machine was trusted; in production the valve’s internalProxies must list exactly the proxies, so that clients cannot send their own X-Forwarded-For and become someone else’s address in the access log. The constants struts.url.http.port and struts.url.https.port exist for the port Struts writes into absolute URLs when the valve cannot be used (they were not run here). Other proxy duties are the proxy’s own: TLS, HTTP/2, the large-upload limit (the struts.multipart.maxSize family of the file upload limits must agree with the proxy’s body size limit), timeouts and buffering of long-running actions.

Health Checks and Startup Failure

Container platforms ask the application whether it is alive and ready. The cheapest probe is a servlet that answers a constant. It must bypass Struts (the previous section on Keeping Requests Away from Struts), and it must not touch the database, or the whole fleet is restarted when the database is slow.

src/main/java/org/example/bookshelf/HealthServlet.java
package org.example.bookshelf;

import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;

@WebServlet("/health")
public class HealthServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        resp.setContentType("text/plain");
        resp.getWriter().print("UP");
    }
}

Source: Jakarta Servlet 6.1 Javadoc — WebServlet

A servlet that always answers 200 is useful for exactly one reason that the bogus-cache run proved: when the Struts filter fails to initialise (a bad constant, a malformed struts.xml, a missing class), Tomcat does not start the context at all, and the health servlet, the static files and every action answer 404 together.

A failed Struts filter takes the whole context down (observed)
$ curl -s -o /dev/null -w "books %{http_code}\n" http://localhost:18081/g12deploy/books
books 404
$ curl -s -o /dev/null -w "health %{http_code}\n" http://localhost:18081/g12deploy/health

$ grep -a SEVERE base/logs/catalina.out | tail -2
SEVERE ... StandardContext.startInternal One or more Filters failed to start. Full details will be found in the appropriate container log file
SEVERE ... StandardContext.startInternal Context [/g12deploy] startup failed due to previous errors

A readiness probe on /health therefore catches a configuration error (the pod never becomes ready and the rollout stops) without the application having to say so. The probe path /health answers 200 only when the Struts filter started, as shown above, and the readiness probe’s five-second period lets a bad rollout stop early. The image name is a placeholder; nothing in it is a credential. Inconsistencies in the Official Documentation

Several statements of the official pages do not match 7.4.0. The first three are measured on the Bookshelf, the rest were read from the pages and the jar.

  • The Performance Tuning page gives the FreeMarker template_update_delay default as 500 ms; the measured default is 5 s, and the unit of the Struts constant is seconds.

  • The page and default.properties say whitespace stripping is disabled in devMode; FreemarkerManager has no such check and a devMode run was still stripped.

  • The OGNL cache page documents expressionCacheLRUMode and beanInfoCacheLRUMode, which 7.4.0 ignores, and does not list expressionCacheType, beanInfoCacheType or the localized-text and proxy caches.

  • The Static Content page says Struts serves content "from the classpath" under /static; the files in the jar are under org/apache/struts2/static and template/<theme>/, so "extract to the web application directory" is not a plain unzip.

  • DefaultStaticContentLoader sends a Retry-After header with the Expires date on a 200 response.

  • The WebJar section describes version-less URLs; the webjar tag writes the versioned URL, and the feature needs struts.serve.static=true.

  • The Performance Tuning page still names the Ajax theme (Dojo), the Calendar tag and struts.freemarker.templatesCache; none exists in 7.4.0.

  • Application Servers lists servers from the 2000s and Wildfly 10.x, links only some of them, and does not name Tomcat 10.1 or 11, Jetty 12 or GlassFish 8.

  • The struts-examples repository is on 7.3.0 and Jetty 11 although 7.4.0 was released on 2026-10-02.

  • GlassFish 8.0.5 reports X-Powered-By: JSP/3.0 on a JSP response, although it implements Pages 4.0.

Summary

A Struts 7.4 WAR is production-ready by default and the work is in what surrounds it. Keep devMode and the reload switches off and check with ?debug=xml; let the container or a proxy serve static files (struts.serve.static=false, the jar’s files extracted, ExpiresFilter or proxy caching) and send servlets and health endpoints around Struts with struts.action.excludePattern; leave the OGNL caches at wtlfu and give FreeMarker a long update delay; keep logging at warn for Struts and FreeMarker; create sessions only on purpose and do not trade the security-header interceptors for speed; harden Tomcat with a Host-level ErrorReportValve, error pages, RemoteIpValve and cookie flags; deploy the same WAR to Tomcat 11, Jetty 12.1 or GlassFish 8; and expose a /health servlet for probes, remembering that a failed Struts filter takes the whole context down with a 404. Docker and Kubernetes add a start-up command, probes and memory limits around that WAR and are covered by their own pages. Take learning code from struts-examples and the showcase, versions from the BOM, and never from a 6.0.0 archetype.
