JSON Plugin & AJAX

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Struts 7.4.0 (released 2026-10-02) and its struts2-json-plugin 7.4.0, running on Apache Tomcat 11.0.26 and Java 21, the combination every example was built, deployed and requested on; the facts were checked on 2026-10-08 against the JSON plugin page, the Core Developer Guide AJAX page, the Tag Developer Guide AJAX pages, the Javadoc, the plugin jar (struts-plugin.xml and javap on its classes) and its source jar. The plugin does two jobs. As a result type (json) it writes an action, or one part of it, as a JSON document; as an interceptor (json) it reads a JSON request body and fills the action from it. Together they turn a Struts action into the endpoint of a JavaScript client, which is what AJAX meant for Struts from the beginning: the request is an ordinary request, only the response (or the body) is not a page. The running scenario is the Bookshelf catalogue exposed as a JSON API under /api, and the client side uses fetch and htmx because the Dojo, jQuery and YUI tag plugins that older material teaches no longer exist for Struts 7. The neighbouring pages are the REST plugin, security hardening and testing.

The Bookshelf JSON API Used on This Page

All examples are classes and mappings of one WAR, g11json.war, deployed under the context path /g11json on Tomcat 11.0.26. It is the Struts Bookshelf of Getting Started (the struts2-bom 7.4.0 and struts2-core) with one more dependency and one more package:

<dependency>
    <groupId>org.apache.struts</groupId>
    <artifactId>struts2-json-plugin</artifactId>
</dependency>

Source: JSON Plugin — Installation

The version comes from the BOM. Copying the jar into WEB-INF/lib is all the plugin needs: it has no other files to add. The domain classes are small. Book is a bean with id, title, author, subtitle, genre (an enum with a label), published (a Date) and an internalNote that must never reach the client; BookStore keeps three books in memory (Dune, Neuromancer and The Hobbit); BookRecord is a Java record used to show the 7.3 record support. The actions that matter are named where they appear.

Source: JSON Plugin — Deserialization limits

The json interceptor is not part of defaultStack and no action uses it unless a mapping says so. That is deliberate: a JSON request body is only read for the actions that opt in, which keeps ordinary form actions unaffected. The result type, by contrast, is available to every package that extends json-default, and a package can list several parents (extends="struts-default,json-default"), which is how one package serves both pages and JSON (see Results and Result Types, which also lists the json result next to the other plugin results).

The Round Trip: Request, Interceptor, Action, Result

sequenceDiagram participant C as fetch or curl participant F as Struts filter participant J as json interceptor participant S as defaultStack participant A as AddBookAction participant R as json result C->>F: POST /api/add-all (Content-Type application/json) F->>J: invoke J->>J: read the body, check limits, filter and authorize keys J->>A: populate the action from the JSON object J->>S: invoke the rest of the stack S->>A: params, validation, workflow A-->>R: execute returns success R-->>C: 200 application/json (serialized action or root)

The interceptor acts only when the request Content-Type equals the configured jsonContentType (application/json by default) or jsonRpcContentType (application/json-rpc, for SMD). Any other content type, for example a form post or a GET, passes through untouched, which the scratch run confirmed: a form post to add-all filled note from the form fields and ignored the JSON machinery. The result then serializes whatever the mapping selects. The two halves are independent: an action can read JSON and answer with a page, or read a form and answer with JSON.

Source: JSON Plugin — Accepting JSON

The json Result

The smallest JSON endpoint is an action and a json result without parameters. The mapping needs a package that extends json-default:

<package name="api" extends="json-default" namespace="/api">
    <action name="all-default" class="org.example.bookshelf.DefaultJsonAction">
        <result type="json"/>
    </action>
</package>

Source: JSON Plugin — Write the mapping for the action

DefaultJsonAction extends ActionSupport and has two getters, getBooks() and getCount(). The response contains exactly those two properties:

$ curl -s http://localhost:18080/g11json/api/all-default
{"books":[{"author":"Frank Herbert","genre":"SCIENCE_FICTION","id":1,"publishedOn":"1965-08-01","subtitle":null,"title":"Dune"}, ... ],"count":3}

Three things are visible. Property names are sorted alphabetically. A null is written as null. And none of the getters that ActionSupport brings (getActionErrors(), getLocale(), getTexts() and so on) were serialized, because by default the writer looks only at the getters declared on the root object’s own class and ignores those of its base classes; the ignoreHierarchy parameter, covered below, changes that. Serialization is by getters: the plugin page says a field without a getter and a transient field are not serialized, and @JSON(serialize = false) removes a getter from the output.

Source: JSON Plugin — Example

The response headers of such a result are the ones of any Struts response (the stack adds Vary: Sec-Fetch-*, Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy-Report-Only, see the page on interceptors) plus Content-Type: application/json;charset=UTF-8 and a Content-Length. The headers other than those two are left out of the transcripts below.

Choosing the Root

A whole action is rarely what an API wants to return. The root parameter is an OGNL expression that names the object to serialize, evaluated against the value stack (see the Value Stack and OGNL):

public class BooksAction extends ActionSupport {
    private String q;
    private int id;
    private List<Book> books;
    private Book book;

    @Override
    public String execute() {
        books = BookStore.all().stream()
                .filter(b -> q == null || b.getTitle().toLowerCase().contains(q.toLowerCase()))
                .collect(Collectors.toList());
        return SUCCESS;
    }

    public String show() {
        book = BookStore.find(id);
        return book == null ? "missing" : SUCCESS;
    }

    public List<Book> getBooks() { return books; }
    public Book getBook() { return book; }
    public String getQ() { return q; }

    @StrutsParameter
    public void setQ(String q) { this.q = q; }

    @StrutsParameter
    public void setId(int id) { this.id = id; }
}
<action name="books" class="org.example.bookshelf.BooksAction">
    <result type="json">
        <param name="root">books</param>
    </result>
</action>
<action name="book" class="org.example.bookshelf.BooksAction" method="show">
    <result type="json">
        <param name="root">book</param>
    </result>
    <result name="missing" type="json">
        <param name="statusCode">404</param>
        <param name="root">q</param>
    </result>
</action>

Source: JSON Plugin — Root Object

The two setters carry @StrutsParameter because the q and id request parameters are bound by the params interceptor, which accepts only annotated setters in Struts 7 (see Parameter Injection and @StrutsParameter).

$ curl -s 'http://localhost:18080/g11json/api/books?q=hobbit'
[{"author":"J. R. R. Tolkien","genre":"FANTASY","id":3,"publishedOn":"1937-09-21","subtitle":null,"title":"The Hobbit"}]

$ curl -s 'http://localhost:18080/g11json/api/book?id=2'
{"author":"William Gibson","genre":"SCIENCE_FICTION","id":2,"publishedOn":"1984-07-01","subtitle":null,"title":"Neuromancer"}

$ curl -si 'http://localhost:18080/g11json/api/book?id=99' | head -1
HTTP/1.1 404

$ curl -s 'http://localhost:18080/g11json/api/book?id=99'
null

A root that is a list serializes as a JSON array, so the response is [...], not an object. The statusCode parameter sets the HTTP status of the response (here 404 for a missing book) while the body is still written by the result; the example uses the not-set q as the root, which is why the body is null. A real API would return a small error object as the root of that result. The related errorCode parameter calls sendError instead and so hands the response to the servlet container, which writes its own HTML error page: in the scratch run an action with errorCode 503 answered Content-Type: text/html;charset=ISO-8859-1 and the Tomcat status page, not JSON. Use statusCode for JSON APIs.

Source: JSON Plugin — Status and Error code

Including and Excluding Properties

excludeProperties and includeProperties take comma-separated regular expressions matched against the path of each property. For a root that is a list, the path of the title of the first element is [0].title, so the expressions below carry the index and the property name:

<action name="books-excl" class="org.example.bookshelf.BooksAction">
    <result type="json">
        <param name="root">books</param>
        <param name="excludeProperties">\[\d+\]\.genre,\[\d+\]\.subtitle</param>
    </result>
</action>
<action name="books-incl" class="org.example.bookshelf.BooksAction">
    <result type="json">
        <param name="root">books</param>
        <param name="includeProperties">\[\d+\]\.id,\[\d+\]\.title</param>
    </result>
</action>
$ curl -s http://localhost:18080/g11json/api/books-excl
[{"author":"Frank Herbert","id":1,"publishedOn":"1965-08-01","title":"Dune"}, ... ]

$ curl -s http://localhost:18080/g11json/api/books-incl
[{"id":1,"title":"Dune"},{"id":2,"title":"Neuromancer"},{"id":3,"title":"The Hobbit"}]

Source: JSON Plugin — Excluding properties

Source: JSON Plugin — Including properties

In this and the following transcripts an ellipsis marks output shortened for the page.

The page states that exclude expressions win when both are present: an include expression is not applied once an exclude expression matched first. Both parameters exist on the result and on the interceptor; on the interceptor they shape the output of SMD calls, and (see the input filtering section below) they can also be made to gate the keys of an incoming body. Excluding is the safer default for secrets (a password, a national identification number) only if the list is complete; an include list is an allow-list and survives new getters being added later.

Annotating the Bean: @JSON

The @JSON annotation (org.apache.struts2.json.annotations.JSON) customizes one property. It has four members: name (the key to use), serialize (default true), deserialize (default true) and format (a date pattern, default yyyy-MM-dd'T'HH:mm:ss). Book uses all but deserialize:

public class Book {
    private Date published;
    private String internalNote = "reviewed by Ana";

    @JSON(name = "publishedOn", format = "yyyy-MM-dd")
    public Date getPublished() { return published; }

    @StrutsParameter
    @JSON(name = "publishedOn", format = "yyyy-MM-dd")
    public void setPublished(Date published) { this.published = published; }

    @JSON(serialize = false, deserialize = false)
    public String getInternalNote() { return internalNote; }
    // ... the other properties are plain getters and setters
}

Source: JSON Plugin — Customizing Serialization and Deserialization

published appears in every response above as "publishedOn":"1965-08-01" and internalNote never appears. The plugin page’s table says name applies to serialization only, and the scratch run confirms it: a request body that uses the key publishedOn leaves published unset, while the key published (the bean property name) is read, parsed with the same format, and written back as publishedOn (shown in the next section). The asymmetry catches clients that echo a response back as a request body.

Nulls, Enums, Records and Optional

By default a property with value null is written as null. Setting excludeNullProperties to true drops it:

<action name="books-nonull" class="org.example.bookshelf.BooksAction">
    <result type="json">
        <param name="root">books</param>
        <param name="excludeNullProperties">true</param>
    </result>
</action>

Source: JSON Plugin — Excluding properties with null values

The subtitle key, present as null in books, is gone from the output of books-nonull. An enum is written as its name() ("genre":"FANTASY"); enumAsBean writes it as an object with all its properties plus a _name entry:

<result type="json">
    <param name="root">books</param>
    <param name="enumAsBean">true</param>
    <param name="includeProperties">\[\d+\]\.title,\[\d+\]\.genre.*</param>
</result>
$ curl -s http://localhost:18080/g11json/api/books-enum-bean
[{"genre":{"label":"Science fiction","_name":"SCIENCE_FICTION"},"title":"Dune"}, ... ,{"genre":{"label":"Fantasy","_name":"FANTASY"},"title":"The Hobbit"}]

Source: JSON Plugin — Enumerations

Since Struts 7.3.0 a Java record is serialized by its components, so a record no longer needs a bean wrapper, and java.util.Optional is written as its content or as null when empty. @JSON and @JSONFieldBridge can sit on a record component:

public record BookRecord(int id, String title, @JSON(name = "writer") String author, Optional<String> subtitle) {
}
$ curl -s http://localhost:18080/g11json/api/records
[{"id":1,"title":"Dune","writer":"Frank Herbert","subtitle":null},{"id":2,"title":"Neuromancer","writer":"William Gibson","subtitle":"Sprawl trilogy, book 1"}]

$ curl -s http://localhost:18080/g11json/api/records-nonull
[{"id":1,"title":"Dune","writer":"Frank Herbert"},{"id":2,"title":"Neuromancer","writer":"William Gibson","subtitle":"Sprawl trilogy, book 1"}]

Source: JSON Plugin — Java records and Optional

The empty Optional is null and is therefore removed by excludeNullProperties, as the second request shows. A @JSONFieldBridge converts a value to a string with a class implementing FieldBridge (and optionally ParameterizedBridge to receive @JSONParameter values). The Bookshelf bridge writes the Genre enum as its label with a prefix passed in the annotation:

public class LabelBridge implements FieldBridge, ParameterizedBridge {
    private String prefix = "";

    @Override
    public void setParameterValues(Map<String, String> parameters) {
        prefix = parameters.getOrDefault("prefix", "");
    }

    @Override
    public String objectToString(Object object) {
        return object == null ? null : prefix + ((Genre) object).getLabel();
    }
}

public class ShelfAction extends ActionSupport {
    @JSON(name = "shelfGenre")
    @JSONFieldBridge(impl = LabelBridge.class, params = @JSONParameter(name = "prefix", value = "Genre: "))
    public Genre getGenre() {
        return Genre.FANTASY;
    }
}
$ curl -s http://localhost:18080/g11json/api/shelf
{"shelfGenre":"Genre: Fantasy"}

Source: Javadoc — JSONFieldBridge

Base Classes and ignoreHierarchy

The default of ignoreHierarchy is true: only the getters of the root object’s own class are serialized. Setting it to false serializes the getters of every superclass up to Object, and for an action that extends ActionSupport that means all the framework getters:

<action name="hier" class="org.example.bookshelf.HierAction">
    <result type="json">
        <param name="ignoreHierarchy">false</param>
    </result>
</action>
$ curl -s http://localhost:18080/g11json/api/hier
{"actionErrors":[],"actionMessages":[],"fieldErrors":{},"greeting":"hello","locale":"en_US","texts":null}

$ curl -s http://localhost:18080/g11json/api/hier-default
{"greeting":"hello"}

Source: JSON Plugin — Base Classes

HierAction has a single getter, getGreeting(). The first response adds the locale, the (empty) error and message collections and a texts entry, all inherited from ActionSupport; that is the reason the default is true. Leave it alone and name the root.

JSONP is a pre-CORS device for reading JSON from another origin through a <script> element, and it hands the page to whoever controls the callback name; do not enable it for an authenticated endpoint. The two deprecated cousins, a wrapWithComments wrapper and the prefix option that writes {}&&, are documented with the warning that comment wrapping can turn safe JSON into dangerous text (the example is a string containing */ followed by script), so use wrapPrefix if a hijacking-defence prefix is wanted at all.

Accepting JSON: the json Interceptor

An action receives a JSON body when its stack contains the json interceptor. The interceptor reads the request body (application/json), parses it into maps, lists and primitives, filters the keys, and then sets the properties of the action by reflection on its setters. Place it before defaultStack (or use the stack that suits the action):

public class AddBookAction extends JsonSupport {
    private Book book;
    private String note;
    private List<String> tags = new ArrayList<>();
    private String secret = "untouched";

    @Override
    public String execute() {
        if (book != null) {
            BookStore.add(book);
        }
        return SUCCESS;
    }

    @StrutsParameter(depth = 1)
    public Book getBook() { return book; }

    @StrutsParameter(depth = 1)
    public void setBook(Book book) { this.book = book; }

    public String getNote() { return note; }

    @StrutsParameter
    public void setNote(String note) { this.note = note; }

    @StrutsParameter(depth = 1)
    public List<String> getTags() { return tags; }

    @StrutsParameter(depth = 1)
    public void setTags(List<String> tags) { this.tags = tags; }

    public String getSecret() { return secret; }
    public void setSecret(String secret) { this.secret = secret; }
}
<action name="add-all" class="org.example.bookshelf.AddBookAction">
    <interceptor-ref name="json"/>
    <interceptor-ref name="defaultStack"/>
    <result type="json"/>
</action>
$ curl -s -X POST -H 'Content-Type: application/json' -d '{"book":{"title":"Hyperion","author":"Dan Simmons","genre":"SCIENCE_FICTION","published":"1989-05-26","internalNote":"changed"},"tags":["classic","space-opera"],"secret":"pwned","note":"first"}' http://localhost:18080/g11json/api/add-all
{"book":{"author":"Dan Simmons","genre":"SCIENCE_FICTION","id":4,"publishedOn":"1989-05-26","subtitle":null,"title":"Hyperion"},"note":"first","secret":"untouched","tags":["classic","space-opera"]}

Source: JSON Plugin — Accepting JSON

Source: JSON Plugin — Parameter authorization

The response shows the rules at work. book was populated, including the nested genre (a string converted to the enum) and published (parsed with the @JSON format), tags was filled with the list, and note was set. secret has a public setter but no @StrutsParameter, so it stayed untouched although the body asked for pwned: the interceptor applies the same annotation rule as the params interceptor to every key of the JSON tree, before anything is set (a rejected key is dropped and logged, not an error). The plugin page says the annotation is enforced per property during deserialization, so unauthorized fields are never set on the target object.

Two details of that rule are not spelled out in the page and cost time:

  • A nested key such as book.title has depth one. For depth greater than zero the authorizer reads the annotation from the getter, and the intermediate node book (depth zero) is checked against the setter. In the scratch run an action with @StrutsParameter(depth = 1) on the setter only produced an empty Book (the node book passed, its children did not), and with the annotation on the getter only the whole book was dropped. Annotating both, as above, works.

  • The classes of the nested objects are not asked for annotations when the root is the action: a variant of the WAR whose Book has no @StrutsParameter at all still populated book through add-all.

The internalNote key of the body above was also ignored, but that is the effect of @JSON(deserialize = false) on the bean, as the plugin page’s table describes; it does not appear in any response to prove it, so the table rather than the run is the source for that statement.

A Root for the Incoming Object

The interceptor’s root parameter has the opposite meaning to the result’s: it names the object to populate, so the body can be a bare object instead of an object with one key per property. The object must exist before the interceptor runs; a null root fails with Invalid root expression:

public class AddRootAction extends ActionSupport {
    private final Book book = new Book();

    @Override
    public String execute() {
        BookStore.add(book);
        return SUCCESS;
    }

    public Book getBook() { return book; }
}
<action name="add-root" class="org.example.bookshelf.AddRootAction">
    <interceptor-ref name="json">
        <param name="root">book</param>
    </interceptor-ref>
    <interceptor-ref name="defaultStack"/>
    <result type="json">
        <param name="root">book</param>
    </result>
</action>
$ curl -s -X POST -H 'Content-Type: application/json' -d '{"title":"Foundation","author":"Isaac Asimov","published":"1951-06-01"}' http://localhost:18080/g11json/api/add-root
{"author":"Isaac Asimov","genre":null,"id":5,"publishedOn":"1951-06-01","subtitle":null,"title":"Foundation"}

Source: JSON Plugin — Root Object

The first attempt with an action whose book field was not initialized answered 500 with the message Invalid root expression: 'book'. Because the root is the Book itself, the authorization check runs against the setters of Book, which is why Book carries @StrutsParameter on its setters in the Bookshelf code (the published setter above shows one); in the variant of the WAR without those annotations the same request answered 200 with a book whose title and author were null. The page also states that a body that is a JSON array needs a root on the interceptor, because the array has to land in a property; an array body without a root is rejected (the scratch run answered 500 with Unable to deserialize JSON object from request).

Which Values Are Accepted

The plugin page lists what populates: primitives, Date, List, Map, primitive arrays, other classes and arrays of them; objects inside lists and maps arrive as Map, whole numbers as Long, decimals as Double and arrays as List. Since Struts 7.3.0 the keys of the body are filtered with the same acceptability controls as ordinary request parameters, using the dotted and indexed paths (address.city, items[0].name): the framework-wide excluded and accepted name patterns, a maximum path length (paramNameMaxLength, 100 by default), the ParameterNameAware and ParameterValueAware callbacks, and @StrutsParameter. Limits on the Body

Five limits protect the parser: elements per array or object (struts.json.maxElements, 10000), nesting depth (maxDepth, 64), total input length (maxLength, 2 MB), the length of one string value (maxStringLength, 256 KB) and the length of an object key (maxKeyLength, 512). Each can be set as a constant or as a parameter of one interceptor. Since Struts 6.11.0 and 7.3.0 the input length is counted while the body is read, in fixed-size chunks, instead of line by line, so the way a client splits the payload into lines no longer matters.

<constant name="struts.json.maxLength" value="1048576"/>
<interceptor-ref name="json">
    <param name="maxLength">100</param>
</interceptor-ref>

The security bulletins of 2026 make the limits more than a tuning knob: S2-072 (CVE-2026-73633) describes a JSON request body read into memory without a bound, so the configured length limit did not reduce exposure; it was fixed in 7.3.0 and 6.11.0 (see the security section below).

Errors in a JSON API

Without any configuration, a malformed body is a server error with the container’s HTML page: the body {"book": made the interceptor throw JSONException ("Input string is not well formed JSON") and Tomcat answered 500 with an HTML report. JSON Validation: jsonValidation and jsonActionRedirect

The jsonValidation interceptor turns the field errors of the action into a JSON document so that a form can validate through AJAX without a page reload (the plugin lists "JSON Ajax Validation" as a feature). It acts when the request carries struts.enableJSONValidation=true, answers 400 with the errors when there are any, and with struts.validateOnly=true stops before the action runs. The sample stack jsonValidationWorkflowStack of the plugin wires it between validation and workflow:

public class ValidatedAction extends ActionSupport {
    private String title;
    private String author;

    @Override
    public String execute() { return SUCCESS; }

    @StrutsParameter
    public void setTitle(String title) { this.title = title; }
    public String getTitle() { return title; }

    @StrutsParameter
    public void setAuthor(String author) { this.author = author; }
    public String getAuthor() { return author; }

    @Override
    public void validate() {
        if (title == null || title.isBlank()) {
            addFieldError("title", "Title is required");
        }
        if (author == null || author.isBlank()) {
            addFieldError("author", "Author is required");
        }
    }
}

    <interceptor-ref name="jsonValidationWorkflowStack"/>
    <result type="json">
        <param name="includeProperties">title,author</param>
    </result>
</action>

Customizing the Serializer: JSONWriter and JSONReader

The writer and reader are Struts beans. The default struts implementations are registered with scope="prototype", and struts.json.writer and struts.json.reader select the implementation by bean name, so a custom one is a class, a bean declaration and a constant (the plugin page names the interface org.apache.struts2.json.JSONWriter and a Flexjson-based sample in the json-customize project of the struts-examples repository). The Bookshelf variant wraps every response in an envelope by extending the built-in writer:

public class EnvelopeJSONWriter extends StrutsJSONWriter {
    @Override
    public String write(Object object, Collection<Pattern> excludeProperties,
                        Collection<Pattern> includeProperties, boolean excludeNullProperties) throws JSONException {
        return "{\"data\":" + super.write(object, excludeProperties, includeProperties, excludeNullProperties) + "}";
    }
}

    <constant name="struts.json.writer" value="envelope"/>

The same page records that the struts.json.writer and struts.json.reader overrides were ignored in 7.2.x (WW-5641, fixed in 7.3.0), so a workaround carried from that release can be removed.

SMD and JSON-RPC

The plugin can also expose action methods to a script. A Simple Method Definition (SMD) is a JSON description of the remote methods; a client that understands it generates a proxy, and each call is a JSON-RPC request. It was built for the Dojo toolkit and needs two things, both required together: enableSMD on the interceptor and on the result, and the @SMDMethod annotation on each method that may be called (a security measure: only annotated methods are reachable). The package of the annotation in 7.4.0 is org.apache.struts2.json.annotations:

public class SmdAction extends ActionSupport {
    public String smd() { return SUCCESS; }

    @SMDMethod
    public Book rename(Book book, int number) {
        book.setTitle(book.getTitle() + " #" + number);
        return book;
    }
}
<action name="smd" class="org.example.bookshelf.SmdAction" method="smd">
    <interceptor-ref name="json">
        <param name="enableSMD">true</param>
    </interceptor-ref>
    <result type="json">
        <param name="enableSMD">true</param>
    </result>
</action>
$ curl -s http://localhost:18080/g11json/api/smd
{"methods":[{"name":"rename","parameters":[{"name":"p0"},{"name":"p1"}]}],"objectName":null,"serviceType":"JSON-RPC","serviceUrl":"\/g11json\/api\/smd","version":".1"}

$ curl -s -X POST -H 'Content-Type: application/json-rpc' -d '{"id":1,"method":"rename","params":[{"title":"Dune"},2]}' http://localhost:18080/g11json/api/smd
{"debug":null,"error":null,"id":"1","result":{"author":null,"genre":null,"id":0,"publishedOn":null,"subtitle":null,"title":"Dune #2"}}

Source: JSON Plugin — JSON RPC

A GET returns the SMD (the smd method only exists to give the result something to serialize) and a POST with the application/json-rpc content type invokes the method. Parameters are positional (p0, p1) unless @SMDMethodParameter names them. If the action could be a proxy (for instance when AOP interceptors wrap it), annotations on its methods are not inherited; the result parameter ignoreInterfaces and the interceptor parameter ignoreSMDMethodInterfaces, both set to false, make the plugin inspect interfaces and superclasses at a performance cost.

Source: JSON Plugin — Proxied objects

SMD is the weakest part of the plugin for a 2026 application. The documentation’s client is dojo.rpc.JsonService, and Dojo has not been part of Struts since 2.5; nothing else generates a client from an SMD document with any frequency; and the feature is the one surface of the plugin that a security bulletin touched (S2-071, below). A new API is better served by plain JSON endpoints, as in the earlier sections, or by the REST plugin of this section.

AJAX Without Dojo: fetch and htmx

AJAX needs nothing from Struts. The Core Developer Guide says the point: an Ajax request is an ordinary request, the framework cannot tell it was sent by a script, and the Ajax response is simply a portion of a page, a fragment, a script or JSON. In Struts 7 the work of the old tag libraries is done by two plain mechanisms. The first is an action that returns JSON, called from fetch. The page below is ajax.html of the scratch WAR, served from the web root:

The fragment goes to a library such as htmx, which swaps it into the page by attributes alone:

public class HtmlFragmentAction extends ActionSupport {
    private String q = "";

    public InputStream getInputStream() {
        StringBuilder sb = new StringBuilder("<ul>");
        for (Book b : BookStore.all()) {
            if (b.getTitle() != null && b.getTitle().toLowerCase().contains(q.toLowerCase())) {
                sb.append("<li>").append(escape(b.getTitle())).append("</li>");
            }
        }
        sb.append("</ul>");
        return new ByteArrayInputStream(sb.toString().getBytes(StandardCharsets.UTF_8));
    }

    @StrutsParameter
    public void setQ(String q) { this.q = q == null ? "" : q; }

    @Override
    public String execute() { return SUCCESS; }

    private static String escape(String s) {
        return s.replace("&", "&amp;").replace("<", "&lt;").replace(">", "&gt;").replace("\"", "&quot;");
    }
}

Same-Origin Calls, Cross-Origin Calls and CSRF

A script on the same origin as the application sends cookies and needs nothing special. The default stack of Struts 7.4.0 includes the fetchMetadata interceptor (see the page on interceptors), which inspects the Sec-Fetch-* headers that browsers attach. With curl setting those headers by hand the scratch run showed: a cross-site GET with Sec-Fetch-Mode: cors answered 200, a same-origin one 200, and a cross-site POST with a JSON body and Sec-Fetch-Mode: cors answered 404 (the interceptor’s bad-request-style result has no mapping, see the pitfalls of the interceptors page). That is an additional layer and not a substitute for a CSRF defence: a JSON endpoint authenticated by a cookie is still subject to cross-site request forgery. Setting Content-Type: application/json on a cross-origin fetch forces a preflight, which does protect an endpoint that never accepts form content types, but an action that also accepts a form post (every action does) is open to a plain <form> post. Use tokens (see Double-Submit Tokens), SameSite cookies and CORS rules on the container or reverse proxy. A cross-origin call also needs CORS headers from the server, which Struts does not add; the page on CORS explains the mechanism.

The Old AJAX Material: Dojo, the Ajax Theme and Tag Plugins

The Core Developer Guide AJAX page, the Tag Developer Guide’s "Ajax Tags" and "Ajax and JavaScript Recipes" pages and the second edition of the Manning book all describe a generation of Ajax support that is gone:

  • The Dojo plugin (the sx tag library, <%@ taglib prefix="sx" uri="/struts-dojo-tags" %>) was a theme in 2.0, a bundled plugin in 2.1 to 2.3.x and "not part of the Struts2 distribution anymore" since 2.5. The Ajax Tags page itself begins with the warning that the Ajax template (Dojo plugin) is deprecated and will not be supported. None of its tags (sx:a, sx:autocompleter, sx:bind, sx:datetimepicker, sx:div, sx:head, sx:submit, sx:tabbedpanel, sx:textarea, sx:tree, sx:treenode) exist for Struts 7.

  • The ajax theme of the UI tags was removed with it. The 7.4.0 struts2-core jar contains the simple, xhtml, css_xhtml and html5 templates only (see the page on themes and templates).

  • The jQuery, YUI, Ajax Parts, GWT and Ajax File Upload plugins listed on the AJAX page are third-party or retired. The struts2-bom 7.4.0 contains no plugin of that kind: the Ajax-related artifacts that still exist are struts2-json-plugin and struts2-rest-plugin.

  • s:datetimepicker (the Dojo widget) has no direct successor: the nearest tag is s:datetextfield, whose limits are described in UI and Form Tags, and a plain HTML <input type="date"> covers most needs.

The recipes page is still worth reading for what it taught: request triggers and targets (bind), update of a region (div with href and reloadTopics), an indicator during the request, error handling with a message, and an autocompleter that loads its options from an action. The recipe’s JSON autocompleter in particular used the json result with root set to a map (<param name="root">options</param>), which is the same mapping as the books action above with another root.

The lesson common to the three is the lifetime of the reader and writer objects, and the 7.3.0 design (fresh reader and writer per request, prototype beans) is what a custom writer must preserve. Inconsistencies in the Official Documentation

Several details of the official pages disagree with the 7.4.0 jar or with themselves. They are listed so that a reader who meets them is not misled.

  • The plugin page’s examples import com.opensymphony.xwork2.Action and ActionSupport, and its SMD example imports com.googlecode.jsonplugin.annotations.SMDMethod; in 7.4.0 these are org.apache.struts2.ActionSupport, org.apache.struts2.Action and org.apache.struts2.json.annotations.SMDMethod.

  • The plugin page’s JSON-RPC client example uses the dojo.rpc.JsonService toolkit, which Struts no longer ships.

  • The "Parameter authorization" paragraph says to annotate the action properties that may be populated. For a nested bean both accessors need the annotation in 7.4.0 (see above); the page does not say so.

  • The @JSON table says name is not used for deserialization, which agrees with the run, but the sample action returns a property with @JSON(name = "newName") and the page’s text calls it "custom name", which readers take to be symmetric.

  • The jsonActionRedirect Javadoc speaks of a "JS/AJAX context" and the result switches to JSON only when the request parameter struts.enableJSONValidation=true is present; the response then declares a charset of ISO-8859-1.

  • The Core Developer Guide AJAX page names the standard Struts 2 tag library as containing "several Ajax JSP tags", which is no longer true, and its Stream result example imports java.io.StringBufferInputStream while the code uses ByteArrayInputStream (a missing import, since StringBufferInputStream is deprecated).

  • The AJAX page lists a jQuery plugin, an Ajax Parts taglib, a YUI plugin and a GWT plugin as Struts plugins; none of them is in the 7.4.0 BOM.

Summary

The JSON plugin makes JSON a first-class result and body format: map the action in a package that extends json-default, name the root, shape the output with includeProperties, excludeProperties, excludeNullProperties and the @JSON annotation, and use statusCode for a JSON error. To accept JSON, put the json interceptor before defaultStack, annotate every property that may be set (both accessors of a nested bean), bound the body with maxLength and the other limits, and map the exceptions of the interceptor to a JSON 400 with the exception interceptor in front. Use jsonValidation for AJAX validation, a prototype-scoped JSONWriter for custom output, and leave SMD alone. For the client, use fetch for JSON and a stream result for HTML fragments with htmx, and treat the Dojo, jQuery and YUI material as history. Keep CSRF defences, because JSON endpoints are reached by cookies like any other action.
