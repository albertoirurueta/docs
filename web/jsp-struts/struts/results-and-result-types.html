Results & Result Types

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Struts 7.4.0 (released 2026-10-02), running on Apache Tomcat 11.0.26 (Jakarta Servlet 6.1, Jakarta Pages 4.0) with Java 21. Everything was verified on 2026-10-08: the facts against the Struts documentation, the struts-default.xml, default.properties and struts-plugin.xml files inside the 7.4.0 jars and the 7.4.0 sources of org.apache.struts2.result, and every example by building it into a Maven WAR with the struts2-bom and deploying it on Tomcat 11.0.26, where each URL was called with curl; the outputs shown are the outputs that run produced (headers that do not matter and blank lines are left out). An action decides what happened; a result decides what the browser receives. Struts keeps the two apart on purpose: the action returns a short code such as success or input, and the configuration maps that code to a result type that renders a JSP, redirects, streams a file, writes JSON or sets a status line. The running scenario is the Bookshelf catalogue: the page grows from one JSP result to a configuration that redirects after a POST, exports a CSV file, answers a health check and serves JSON, with every example run against Struts 7.4.0.

What a Result Is

Once the action method (and the interceptors around it) has finished, the framework needs to produce the response. It asks the action invocation for a Result and calls its execute method. In Struts 7 the contract is the interface org.apache.struts2.result.Result (before 7.0 it was com.opensymphony.xwork2.Result; the package rename is part of the 6 to 7 migration) with exactly one method, execute(ActionInvocation). Almost every built-in result extends StrutsResultSupport, which adds the location property, the parse and encode switches and the evaluation of ${...} expressions against the value stack. What the action method returns decides how the framework reaches a Result:

Table 1. What an action method may return and what the framework does with it (7.4.0 DefaultActionInvocation)
Return value Effect

A String result code

Looked up by name in the action’s result configurations; the matching result element names the result type and its parameters

null or none

No result is looked up or run; the action is expected to have written the response itself (or nothing is needed)

A Result object (any type)

That object is used directly and no configuration is consulted; the framework injects its dependencies (container.inject)

A Callable

Treated as an asynchronous action: the framework suspends the invocation, runs the callable and processes its outcome as one of the above

Source: Apache Struts — Result Configuration, Returning Result Objects

The result is the last step before the response, but it is not the very last thing that happens. PreResultListener objects registered during the action or by an interceptor run first and may still change the result code (see Listeners Around the Result), and interceptors get control back after the result has run, so an interceptor that wraps invoke() sees a response that already exists.

The diagram shows why a typo in a result name is a runtime problem and not a startup problem: the framework cannot know which codes an action method will return, so the lookup happens per request. The rest of the page follows the diagram from the left: the configuration (Result Configuration), the shared parameters, and then each result type.

Result Configuration

A result element has two jobs: it gives a logical name (the code the action returns) and it names a result type with its parameters. Every part of the element has a default, so the common case is very short.

The same result written with fewer and fewer defaults (all four behave identically)
<result name="success" type="dispatcher">
    <param name="location">/WEB-INF/views/books.jsp</param>
</result>

<result>
    <param name="location">/WEB-INF/views/books.jsp</param>
</result>

<result>/WEB-INF/views/books.jsp</result>

<result name="success" type="dispatcher">/WEB-INF/views/books.jsp</result>

Source: Apache Struts — Result Configuration, Result Elements

Three defaults make the short forms possible, and each one can be changed:

  • Default name. A result without a name is named success.

  • Default type. A result without a type uses the result type registered with default="true". In struts-default.xml that is dispatcher; a package can register its own default with <result-type name="..." class="..." default="true"/>, and a child package inherits it from its parent unless it sets another.

  • Default parameter. Each result type declares which parameter receives the element’s text. For dispatcher, freemarker, velocity, redirect, plainText and postback it is location; for redirectAction and chain it is actionName; for stream it is inputName; for xslt it is stylesheetLocation; httpheader has none. So <result type="chain">books</result> and <result type="chain"><param name="actionName">books</param></result> are the same.

Result Codes

The code an action returns is a plain String. ActionSupport (and the Action interface in org.apache.struts2.action) define five constants, and applications are free to invent more.

Table 4. Predefined result codes (org.apache.struts2.action.Action)
Constant Value Typical meaning

SUCCESS

success

The action did its job; show the normal view. This is also the default result name

INPUT

input

The input was not acceptable; show the form again. The workflow interceptor returns it when the validation interceptor recorded field or action errors (validate() in the Bookshelf add action)

ERROR

error

Something failed; show an error view

LOGIN

login

The caller must authenticate first; usually a global result

NONE

none

Skip result processing: the action already wrote the response. Returning null has the same effect

Source: Apache Struts — Result Configuration

The book Struts 2 in Action shows @Result(name="SUCCESS") in an annotation example; the constant’s value is lower case success, so that spelling never matches the code the action returns.

Several Results for One Action: the Bookshelf add Action

The add action validates its input in validate() and returns input when the title is empty. One result serves two codes (error, input, a list with a comma, supported since Struts 2.5), and the code that is not named explicitly is success, which redirects. The redirect result is explained in Redirect, Redirect Action and Post/Redirect/Get.

The add action: the form is shown again on error or input, otherwise the browser is redirected
<action name="add" class="org.example.bookshelf.AddBookAction">
    <result name="error, input">/WEB-INF/views/add.jsp</result>
    <result type="redirectAction">
        <param name="actionName">books</param>
        <param name="added">${newId}</param>
        <param name="anchor">book-${newId}</param>
    </result>
</action>
The action class behind it
public class AddBookAction extends ActionSupport {
    private String title;
    private String author;
    private int newId;

    public String getTitle() { return title; }

    @StrutsParameter
    public void setTitle(String title) { this.title = title; }

    public String getAuthor() { return author; }

    @StrutsParameter
    public void setAuthor(String author) { this.author = author; }

    public int getNewId() { return newId; }

    @Override
    public void validate() {
        if (title == null || title.isBlank()) {
            addFieldError("title", "Title is required");
        }
    }

    @Override
    public String execute() {
        newId = BookStore.add(title, author == null ? "" : author).getId();
        return SUCCESS;
    }
}

The * "Other" Result and Duplicate Names

A result named * is selected only when no result with the exact returned name exists. The documentation stresses that it is not a wildcard pattern, only a fallback name, and that an unrecognised result name is usually a programming error that should be fixed rather than hidden. Without any match the request fails.

An action that returns weird, with and without a * result
<action name="weird" class="org.example.bookshelf.WeirdAction">
    <result name="other">/WEB-INF/views/books.jsp</result>
</action>

<action name="weird-star" class="org.example.bookshelf.WeirdAction">
    <result name="other">/WEB-INF/views/books.jsp</result>
    <result name="*" type="httpheader">
        <param name="error">422</param>
    </result>
</action>
$ curl -i http://localhost:18080/g8res/weird
HTTP/1.1 404
...
Message: No result defined for action org.example.bookshelf.WeirdAction and result weird

$ curl -i http://localhost:18080/g8res/weird-star
HTTP/1.1 422

Source: Apache Struts — Result Configuration, the '*' Other Result

The first request is logged by the dispatcher at WARN ("Could not find action or result") and answered with a 404, because the ConfigurationException is handled like a missing action. The same 404 appears when a result points at a template that does not exist; the container, not Struts, reports it (JSP file [/WEB-INF/views/nope.jsp] not found on Tomcat 11). Two result elements with the same name in one action do not raise an error either: in the run, the later success replaced the earlier one, so a copy-and-paste duplicate silently wins.

Global Results

Results that many actions share (a login redirect, a generic error page) are declared once per package in global-results. The framework looks for a local result in the action first and checks the global results only if no local match exists, so an action can override a global result by declaring one with the same name. Global results of a parent package are inherited by child packages.

A shared login result and the action that uses it (the guard is reduced to a constant here)
<global-results>
    <result name="login" type="redirectAction">login-form</result>
    <result name="error">/WEB-INF/views/error.jsp</result>
</global-results>

<action name="secret" class="org.example.bookshelf.SecretAction"/>
$ curl -i http://localhost:18080/g8res/secret
HTTP/1.1 302
Location: /g8res/login-form.action

Source: Apache Struts — Result Configuration, Global Results

SecretAction.execute() returns LOGIN and has no result of its own; the package’s login global result answers. Exception mappings use the same lookup (an exception is converted into a result code), which is why global results and global exception mappings are normally written together; that is the subject of the Exception Handling and Global Results page of this section.

Dynamic Results

The text of a result element and of its parameters may contain ${expression}, which is evaluated against the value stack when the result runs, so the action can compute the destination. In the Bookshelf the add result above builds an anchor (book-${newId}) and a query parameter (added=${newId}) from the id the action generated, and a wizard decides at runtime where to go next.

A result whose target is computed by the action
<action name="wizard" class="org.example.bookshelf.WizardAction">
    <result name="next" type="redirectAction">${nextAction}</result>
</action>
public class WizardAction extends ActionSupport {
    private int step = 1;

    public int getStep() { return step; }

    @StrutsParameter
    public void setStep(int step) { this.step = step; }

    /** Computed from server-side state only, never from a request parameter. */
    public String getNextAction() { return step >= 2 ? "books" : "wizard-done"; }

    @Override
    public String execute() { return "next"; }
}
$ curl -i 'http://localhost:18080/g8res/wizard?step=2'
HTTP/1.1 302
Location: /g8res/books.action

$ curl -i 'http://localhost:18080/g8res/wizard?step=1'
HTTP/1.1 302
Location: /g8res/wizard-done.action

Source: Apache Struts — Result Configuration, Dynamic Results

Which expressions are allowed, and why ${nextAction} above is safe while ${target} taken from the request is not, is the subject of Security: Dynamic Values and the Allowlist.

Returning a Result Object

An action method may return a Result instead of a code, which skips the configuration altogether. This is useful when the destination is built in code, and it is also how the functional PlainResult (see The Plain Result) works. The ServletActionRedirectResult constructors take the action name, an optional namespace, method and anchor.

An action method that returns a ready Result; no result element is needed
public class ShortcutAction {
    public Result go() {
        return new ServletActionRedirectResult("books");
    }
}
<action name="shortcut" class="org.example.bookshelf.ShortcutAction" method="go"/>
$ curl -i http://localhost:18080/g8res/shortcut
HTTP/1.1 302
Location: /g8res/books.action

Source: Apache Struts — Result Configuration, Returning Result Objects

NONE: the Action Wrote the Response Itself

Returning none (or null) skips the result lookup. The action must then have completed the response, typically through the servlet response. Everything the result types below do for you (content type, character set, flushing) becomes the action’s job.

An action that writes directly and returns NONE
public class RawAction extends ActionSupport {
    @Override
    public String execute() throws IOException {
        var response = ServletActionContext.getResponse();
        response.setContentType("text/plain;charset=UTF-8");
        response.getWriter().write("written by the action; no result runs");
        return NONE;
    }
}
$ curl -i http://localhost:18080/g8res/raw
HTTP/1.1 200
Content-Type: text/plain;charset=UTF-8

written by the action; no result runs

Source: Apache Struts — Result Configuration, predefined result names

For anything beyond a one-liner prefer a result type (stream, plain, json): they keep the action testable and the response handling in one place.

The Dispatcher Result: Forward to a View

dispatcher is the default type and the one almost every action ends with. It hands the request to a web resource, usually a JSP, through the servlet RequestDispatcher, so the target sees the same request and response objects and the action is still on the value stack (the JSP’s s:property tags read it). The documentation lists three ways the result can run, and the 7.4.0 source confirms the order of the checks:

  1. If a JSP PageContext is available (the result runs inside a page, for example from the action tag), the page context’s include is called.

  2. Otherwise, if the response is not committed and the request is not already an include, forward is called. A forward lets the page set the content type and status, and it records struts.view_uri and struts.request_uri as request attributes.

  3. In every other case include is called.

Table 6. Parameters of the dispatcher result
Parameter Default Effect

location

none

The resource to dispatch to. Start it with / so it is resolved from the web application root

parse

true

Evaluate ${...} in the location; set false to take it literally

Source: Apache Struts — Dispatcher Result

Redirect, Redirect Action and Post/Redirect/Get

A dispatcher result answers the current request. If that request was a POST, the browser’s address bar still shows the POST URL, and pressing reload sends the form again. The remedy, known as Post/Redirect/Get, is to answer a successful POST with a redirect, so the browser issues a GET to a different URL. Struts has two result types for it: redirect sends the browser to a URL, and redirectAction sends it to an action by name, asking the configured ActionMapper for the URL.

sequenceDiagram participant B as Browser participant F as Struts filter participant A as AddBookAction B->>F: POST /add (title, author) F->>A: validate(), execute() A-->>F: success (newId = 3) F-->>B: 302 Location books.action?added=3 at book-3 B->>F: GET /books.action?added=3 F-->>B: 200 books.jsp (a reload only repeats this GET)

A redirect is a new request, so the action instance, its field errors and its messages are gone by the time the next action runs. Its parameters are actionName (the default parameter), namespace, method and skipActions (a comma-separated list of action names that must not be chained to).

Three details of the example are worth stating. The getter returns a new stream on each call; the result asks the action for the stream once, but returning a fresh object keeps the action reusable if it is ever called twice. The Plain Result: Writing the Response from Java

Since Struts 6.0.0 an action method may return a PlainResult, a functional interface with one method that receives a ResponseBuilder. No result element is needed. The builder collects the body, headers and cookies; the default content type is text/plain; charset=UTF-8, and helper methods switch it to HTML or JSON. The result refuses to write when the response is already committed (a StrutsException) unless the implementation overrides ignoreCommitted().

                .write("{\"status\":\"UP\",\"books\":" + BookStore.all().size() + ",\"dispatcherReady\":" + ready + "}");

Report and Chart Results

The jasper and jasperReport7 results turn an action into a PDF, CSV or other report from a compiled .jasper file. Their common parameters are location (the compiled report), dataSource (an expression for a list on the value stack), format (PDF when none is given), contentDisposition, documentName, reportParameters, exportParameters, parse, and connection for a JDBC connection. Since 7.4.0 dataSource is optional: when neither it nor connection is set the report is filled from report parameters alone, which allows non-JDBC query executors to be driven through reportParameters. The JasperReports 7 plugin no longer brings the jasperreports library transitively in 7.4.0; the application declares it (and jasperreports-pdf for PDF). The JFreeChart plugin’s chart result streams a JFreeChart property of the action as an image, with width and height parameters. These three need libraries and compiled report files that are outside the scratch application, so no examples of them are shown here; the configuration is the same result element as for any other type, and the plugin pages give the full parameter lists and examples. Writing a Custom Result

A result type is any class that implements org.apache.struts2.result.Result. Extending StrutsResultSupport is almost always easier, because the base class provides the location property, the parse and encode switches and the evaluation of ${...}; the subclass implements only doExecute(String finalLocation, ActionInvocation invocation). The framework creates the result for each request, sets the param values through setters and injects its own beans into @Inject methods. Registering takes one line in a package’s result-types, after which the type name is available to every action of that package and of the packages that extend it.

A label result that writes its location, with the expressions already evaluated, as one line of text
public class LabelResult extends StrutsResultSupport {
    @Override
    protected void doExecute(String finalLocation, ActionInvocation invocation) throws IOException {
        var response = invocation.getInvocationContext().getServletResponse();
        response.setContentType("text/plain;charset=UTF-8");
        response.getWriter().write(finalLocation);
    }
}
<result-types>
    <result-type name="label" class="org.example.bookshelf.LabelResult"/>
</result-types>

<action name="label" class="org.example.bookshelf.BookCardAction">
    <result type="label">${book.title} -- ${book.author}</result>
</action>
$ curl -s 'http://localhost:18080/g8res/label?id=2'
Neuromancer -- William Gibson

Limiting the Parameters a Result Accepts

A result takes every param of its element, including ones a careless configuration supplied. A result type that should accept only some of them implements ParamNameAwareResult; the StrutsResultBuilder asks acceptableParameterName(name, value) before setting each parameter and skips the ones for which it answers false. The documentation’s example spells the method acceptableParamName, which is not the name in 7.4.0 (see the errata below): an implementation with that name does not satisfy the interface.

A result type that accepts only location
public class RestrictedLabelResult extends LabelResult implements ParamNameAwareResult {
    @Override
    public boolean acceptableParameterName(String name, String value) {
        return "location".equals(name);
    }
}

Listeners Around the Result

Two small interfaces let code observe or influence the result phase without being a result.

A PreResultListener runs after the action (and the interceptors above it) has produced a result code and before the result is looked up. An action or an interceptor registers it on the ActionInvocation; beforeResult(invocation, resultCode) may inspect or modify the response, the action or even the result code. The documentation shows the registration from an action and from an interceptor (AbstractInterceptor.intercept); the Custom Interceptors page of this section builds on the second form.

An action that registers a PreResultListener which adds a header carrying the result code
public class ListenerAction extends ActionSupport {
    @Override
    public String execute() {
        ActionContext.getContext().getActionInvocation().addPreResultListener((invocation, resultCode) ->
                invocation.getInvocationContext().getServletResponse().setHeader("X-Result-Code", resultCode));
        return SUCCESS;
    }
}

Content-Disposition: inline
Content-Type: text/plain;charset=ISO-8859-1

It is registered statically with Dispatcher.addDispatcherListener, so the registration must happen before the filter initialises: a ServletContextListener runs before filters, and the example sets a servlet context attribute that the health action above reports.

Security: Dynamic Values and the Allowlist

Results are where request data meets the response, and three rules keep that meeting safe.

Expressions in results are evaluated, so their inputs must be trusted. A ${...} in a result is evaluated against the value stack, the same mechanism that powers tags. The expressions in the examples above refer to properties the action computes (${newId}, ${nextAction}, ${fileName}). A property filled from a request parameter and then used as the whole target of a redirect is an open redirect: the visitor chooses where the browser goes. The run shows both forms.

A redirect target taken from the request, and the allowlist version
<action name="unsafe-go" class="org.example.bookshelf.GoAction">
    <result type="redirect">${target}</result>
</action>

<action name="go" class="org.example.bookshelf.GoAction">
    <result type="redirect">${destination}</result>
</action>
public class GoAction extends ActionSupport {
    private static final Map<String, String> DESTINATIONS = Map.of(
            "catalogue", "/books",
            "export", "/export");

    private String target;

    public String getTarget() { return target; }

    @StrutsParameter
    public void setTarget(String target) { this.target = target; }

    /** Allow-list: the request chooses a key, never a URL. */
    public String getDestination() { return DESTINATIONS.getOrDefault(target, "/books"); }
}

Only parameters the action opted into can be set, and only allowlisted classes can be reached. Struts 7 enables both struts.parameters.requireAnnotations (a request parameter may set only a property whose setter or getter carries @StrutsParameter) and struts.allowlist.enable (OGNL expressions may reach only the minimal set of classes the application needs); both are new defaults of 7.0. The 6.x to 7.x migration guide says most applications need no configuration, but those that use POJOs or DTOs for parameter injection and template rendering must allow their classes or packages with struts.allowlist.packageNames or struts.allowlist.classes. The Bookshelf Book class was not allowlisted until the constant in the shared package named its package, and the log said so:

The allowlist does not apply to FreeMarker, which reads the property through its own object wrapper: in the run the same book.title printed in book-card.ftl while the OGNL expression in the label result printed nothing. That asymmetry is why a result that works in one engine can fail in another.

The stream result evaluates inputName only when it passes the accepted-patterns check, and a configuration that takes the name from a request value would let a visitor choose any stream property; keep inputName, like location, a constant. The same constants (struts.excludedClasses, struts.excludedPackageNames, and the accepted patterns) that protect parameters protect these expressions; the Security Hardening page of this section lists them.

Summary

A result is the second half of an action: the action returns a code, result elements map codes to types, and the type turns the code into a response. Most result elements need only a location because the name, the type and the parameter all have defaults. dispatcher forwards to a JSP under WEB-INF, redirectAction ends a POST with a redirect, stream sends files, httpheader sends statuses, PlainResult writes strings from Java, and the plugin packages add JSON, XSLT, Tiles, Velocity and reports. Treat every expression in a result as code that runs on the server: compute it in the action, never take it from the request, and let the allowlist stay on.
