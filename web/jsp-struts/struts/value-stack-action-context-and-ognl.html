ValueStack, ActionContext & OGNL

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Struts 7.4.0 (released 2026-10-02) with OGNL 3.4.12, running on Apache Tomcat 11.0.26 and Java 21; the facts were checked on 2026-10-08 against the 7.4.0 sources and default.properties, the Javadoc of ValueStack and ActionContext and the Tag and Core Developer Guides on https://struts.apache.org/, and every example was built into a WAR, deployed on Tomcat 11 and requested. Nearly everything an action does for a view happens through two objects that the framework creates for each request: the ActionContext, a map of everything that belongs to the request (session, parameters, locale, the servlet objects and more), and the ValueStack, a stack of objects (the action first of all) that is the root of every OGNL expression. The tags write <s:property value="title"/>, OGNL looks title up on the stack from the top down, and <s:property value="#session.user"/> leaves the stack and reads a key of the context map. The running scenario is the Bookshelf, a catalogue of books exposed as Struts actions; this page uses it to print the stack and the context map, to push objects onto both, to evaluate expressions of every kind and to watch the 7.x security settings refuse the ones they must refuse. Related pages of this section: Parameter Injection and @StrutsParameter, Type Conversion, Tags Overview & Generic Tags, Security Hardening and Testing.

The Big Picture

Four words are used for what happens when a view needs a value, and they are easy to confuse:

Term What it is

ActionContext

org.apache.struts2.ActionContext: a thread-local holder around one Map<String, Object> (the context map). It is the place where everything belonging to the current request is reachable: session map, application map, request parameters, locale, the action name, the ActionInvocation, the servlet request, response and context, the ValueStack itself

ValueStack

org.apache.struts2.util.ValueStack (the implementation is org.apache.struts2.ognl.OgnlValueStack): a stack of objects, seen by OGNL as one single object. The action is pushed on it, so are the model of a ModelDriven action, the element of an s:iterator loop and whatever s:push or s:bean adds. It is the OGNL root

OGNL context

The OgnlContext that OGNL evaluates against. Struts makes the ActionContext map this context (the value stack even keeps a reference to it as getContext()), so "the context map", "the ActionContext map" and "the OGNL context" are the same map

OGNL

The Object-Graph Navigation Language, a library (OGNL 3.4.12 inside Struts 7.4.0) that evaluates expression strings such as books[0].title or #session.user against a root object and a context map

Source: Tag Developer Guide — OGNL, Context

The Tag Developer Guide states the relation in one sentence: the framework sets the OGNL context to be the ActionContext and the ValueStack to be the OGNL root object, and along with the stack it places other objects in the context (application, session, request, parameters, attr and the current action). Because OGNL treats the root specially (properties of the root need no marker) and everything else in the context needs a #, the rule for every expression in a Struts view follows directly: a bare name is looked up on the value stack, a name with a # in front is looked up in the context map.

The diagram uses the real objects of one request to the example action of this page: the stack holds the model (a Book, pushed by the modelDriven interceptor), the action and the DefaultTextProvider that every new stack starts with, and the map holds the session, request, application and parameter views next to the stack. Both halves are created by the framework for each request (the creation step is part of the request lifecycle described in Architecture and Request Lifecycle) and discarded with it; nothing is shared between two requests, which is why an action needs no thread safety of its own.

The names also tell where to look when something fails: a null from title is a stack problem (no getter, wrong object on top, access refused by the security rules), a null from #session.user is a context-map problem (a different key, an object put into the wrong scope). The rest of the page follows the same split: the context first, then the stack, then the language that joins them.

ActionContext

What It Is

The Javadoc of ActionContext calls it the context in which an action is executed: each context is a container of the objects an action needs for execution, like the session, parameters and locale. It is thread local, which means that the values stored in it are unique per thread; the benefit stated by the Javadoc is that nobody has to worry about a user specific action context and nobody has to make actions thread safe. ActionContext.getContext() returns the context bound to the current thread, and getContextMap() returns the underlying map, which is the same map that OGNL sees as its context.

Reaching the Scopes From an Action

Three ways exist to read or write the session, request and application from Java, and the Core Developer Guide ranks them (the servlet-level objects behind these maps are described in Servlet Fundamentals, Sessions, and the action classes that receive them in Actions). The recommended one is the Aware interfaces of org.apache.struts2.action: the framework, through the servletConfig interceptor of defaultStack, calls the single method of each interface that an action implements, and the action stores what it is given. The guide says that using ActionContext directly for this is a bad practice and should be avoided, with the *Aware interfaces as the alternative; ServletActionContext (static helpers for the request, response, servlet context, page context, action mapping and the stack of a request) is the third way and ties the action to the servlet API in the same way as ServletRequestAware.

AwareAction.java, session, application and request through the Aware interfaces
public class AwareAction extends ActionSupport
        implements SessionAware, ApplicationAware, ServletRequestAware {
    private Map<String, Object> session;
    private Map<String, Object> application;
    private HttpServletRequest request;
    private String report;

    @Override public void withSession(Map<String, Object> session) { this.session = session; }
    @Override public void withApplication(Map<String, Object> application) { this.application = application; }
    @Override public void withServletRequest(HttpServletRequest request) { this.request = request; }

    @Override
    public String execute() {
        session.put("lastShelf", "scifi");
        application.put("shelfCount", 3);
        request.setAttribute("requestId", 7);
        report = "session=" + session.get("lastShelf") + " application=" + application.get("shelfCount")
                + " request=" + request.getAttribute("requestId")
                + " sameMapAsContext=" + (session == ActionContext.getContext().getSession());
        return SUCCESS;
    }

    public String getReport() { return report; }
}

ActionContext Outside a Request

The 7.4.0 API creates and binds a context with static factories, which is what makes unit tests without a servlet container possible: ActionContext.of(map) (or of()) creates a context around a map, the with... methods fill it, bind() attaches it to the current thread and clear() removes it.

ActionContextDemo.java, a context bound by hand and invisible from other threads
Map<String, Object> session = new HashMap<>();

System.out.println("before bind: " + ActionContext.getContext());
ActionContext.of(new HashMap<>()).withSession(session).withLocale(Locale.FRANCE).bind();

Thread other = new Thread(() -> System.out.println("other thread: " + ActionContext.getContext()));
other.start();
other.join();

ValueStack

What Is on the Stack and When

The interceptors that fill the stack (modelDriven, params, servletConfig) are described on Interceptors. The Javadoc describes the value stack as a structure that allows multiple beans to be pushed in and dynamic expressions to be evaluated against it; when an expression is evaluated, the stack is searched from the latest object pushed in to the earliest, looking for a bean with a getter or setter for the given property, or a method of the given name. Seeing the Stack

The root of the stack is a CompoundRoot, a list that ValueStack.getRoot() returns, so printing its elements shows what a view can reach. This action property lists the class of every element from the top; it is used by all the stack experiments below.

ShelfAction.java, the classes on the stack from the top
public String getStackReport() {
    ValueStack stack = ActionContext.getContext().getValueStack();
    StringBuilder sb = new StringBuilder("size=").append(stack.size());
    for (int i = 0; i < stack.getRoot().size(); i++) {
        sb.append("\n[").append(i).append("] ").append(stack.getRoot().get(i).getClass().getName());
    }
    return sb.toString();
}

The ValueStack API

Member Role

Object peek(), Object pop(), void push(Object), int size()

The stack operations; peek() is the top, which is what the OGNL name top returns

CompoundRoot getRoot()

The list behind the stack, index 0 being the top

Map<String, Object> getContext() and ActionContext getActionContext()

The OGNL context map and the context that wraps it

void set(String key, Object value)

Puts value under key in a map that is itself pushed on the stack, so findValue(key) and a plain name in a view find it. Repeated calls reuse the map while it is still on top

Object findValue(String expr) and the overloads with a Class type and a boolean throwExceptionOnFailure

Evaluates the expression against the stack; the Class overload converts the result with the type converters; returns null when the lookup fails, unless the boolean asks for an exception

String findString(String expr) (and with the boolean)

The same, converted to a String

void setValue(String expr, Object value), setValue(String, Object, boolean), setParameter(String, Object)

Sets the property that the expression names; setParameter is the variant meant for request values and, unlike setValue, does not allow eval (chained) expressions

setDefaultType(Class), setExprOverrides(Map), getExprOverrides()

A default type to convert to when no type is given, and an override map whose entries take precedence in find operations

VALUE_STACK, REPORT_ERRORS_ON_NO_PROP

Constants: the context key of the stack and the flag for "report property errors"

Source: Struts Javadoc — ValueStack, method detail

The members were listed from the 7.4.0 class with javap and match the Javadoc. Two details of OgnlValueStack matter in practice. A failed lookup is swallowed: findValue logs and returns null instead of throwing, unless the caller asked for exceptions (struts.devMode and struts.ognl.logMissingProperties control how loudly). And when the stack lookup returns null or fails, the implementation tries the context map under the same name, which is the "fallback to context" discussed in the OGNL and security sections.

An Interceptor That Writes to the Stack

An interceptor reaches both objects through the ActionInvocation: getStack() for the stack and getInvocationContext() for the ActionContext. This one puts a banner text on the stack and a flag in the session before the action runs.

BannerInterceptor.java and its mapping
public class BannerInterceptor extends AbstractInterceptor {

OGNL

What It Is and What Struts Adds

OGNL, the Object-Graph Navigation Language, is an expression language for getting and setting properties of Java objects. It is a separate open source library (the project lives at https://github.com/orphan-oss/ognl, and Struts 7.4.0 pins version 3.4.12); Struts uses it in four places that you meet daily: the tags (value, test, list and %{...} attributes), the params interceptor (a request parameter name such as book.title is an OGNL expression that is set on the stack), the validators and the result configuration (${...} in a result parameter is OGNL as well, see Results and Result Types). The Tag Developer Guide gives the minimum the framework adds to plain OGNL, and everything in this section is built on it:

  • the value stack is the root object, and a property lookup searches the stack from the top (see the previous section);

  • the ActionContext map is the OGNL context, so #name reads a key of it;

  • a handful of named objects (#action, #parameters, #request, #session, #application, #attr) are placed in the context;

  • tag attributes may contain %{...} to force evaluation (the next two sections).

The OGNL language itself (operators, literals, projection, selection, lambdas, instanceof, new, the @class@member static syntax) is documented by the OGNL project in its Language Guide; this page covers what Struts 7.4.0 lets through.

Forced Evaluation and Its Dangers

The notation %{expression} tells a tag to evaluate the text inside it as OGNL when the attribute is a String. It is very powerful, and the Security Guide says why it is dangerous: used with wrong data it can lead to remote code execution, so incoming data must never be used as the input of a forced expression evaluation. The danger has two forms.

Building expression text from request data. The text inside %{...}, in a value or test attribute and in a message passed to getText is code. Reading a request value inside an expression is harmless: label="%{filter}" evaluates the name filter and prints whatever the property holds. The dangerous shape is the opposite one, where the text of the expression itself comes from the request: a tag attribute assembled from request text before the tag sees it, or an action that hands a user-supplied string to ValueStack.findValue(...) (the scratch probe action of this page does exactly that, to demonstrate the issue, and must never be written in an application).

Double evaluation. Historically the evaluated result of a %{...} attribute could itself contain %{...} that the framework evaluated again, so a request parameter holding an expression ended up executed. The bulletins S2-001 (a remote code exploit on form validation error) and S2-029 (forced double OGNL evaluation on raw user input in tag attributes) are examples of that class, and S2-045 (CVE-2017-5638, the Jakarta Multipart parser) showed that even the text of an error message generated while handling a request can end up evaluated. The 7.0 migration guide still names "double evaluations in the past" as the case that the allowlist was introduced for. The observed behaviour of 7.4.0 is that a result is not evaluated again; the test is easy to run: the request /g9valuestack/shelf?filter=%25%7B1%2B1%7D (the parameter filter holding the text %{1+1}) went through the lines that print it:

The guide names the getText(...) methods of the TextProvider (for instance ActionSupport.getText(String)), which evaluate expressions embedded in the key or default text. All three returned the evaluated result, confirming the warning: an action that passes a request parameter to getText as the key or the default text hands the sender an OGNL evaluator. The rule that the guide states, and that applies to every API on this page, is to treat the text of an expression as code: it comes from your pages and your configuration, never from the request. Request data belongs in the value positions (s:property of a property, a {0} parameter of a message), and the allowlist and the other restrictions of the next section are the second line of defence, not the first.

Java Records in OGNL

Java records are the case where the pages of this section once disagreed, so this is the single place that states the rule; the other pages link here. Two independent mechanisms decide whether a record component is printed, and both were re-checked on Tomcat 11.0.26 with Struts 7.4.0 and OGNL 3.4.12.

  1. A qualified path reads a record component. When the expression names the object first (isbn.code, first.title, #b.title, top.title) or calls the accessor (isbn.code(), title()), OGNL calls the component accessor title(); no getTitle() is needed. The allowlist still applies: a record outside the action’s own package must be listed in struts.allowlist.packageNames (or struts.allowlist.classes), otherwise the value is empty and SecurityMemberAccess logs is not allowlisted. Inside an s:iterator body the element’s class is added to a per-thread allowlist for the length of the iteration (threadAllowlist.allowClassHierarchy(...) in IteratorComponent), so top.title, #b.title and title() on the current element worked even with no allowlist entry.

  2. An unqualified name does not find a record component. A bare name such as title is resolved by searching the stack from the top (see ValueStack), and that search asks each object whether it has a JavaBean getter (OgnlRuntime.hasGetProperty in CompoundRootAccessor). A record’s title() is not a getter, so the record on top of the stack is skipped: <s:property value="title"/> inside s:iterator printed nothing, with or without the allowlist. The search then continues downwards, which is worse than an empty value: inside the loop the bare isbn.code printed the action’s own isbn instead of the current book’s.

So, for a view that iterates over records, either qualify every name (top.title, or a var and #b.title) or give the record JavaBean getters (public String getTitle() { return title; }), which makes the bare name work again; with a getter the unqualified title printed the value in the same test. A JavaBean model, as the Bookshelf of this page uses, avoids the question. JSP EL is a separate engine: ${b.title} reads records through RecordELResolver in EL 6.0.

The Expression Cache and "Compilation"

OGNL parses every expression string into a syntax tree before it can evaluate it, and parsing is the expensive part of repeated evaluations. Struts keeps the parsed trees in an expression cache (OgnlUtil, backed by a cache from ExpressionCacheFactory) and caches the parsed BeanInfo of classes in a second cache. The Core Developer Guide page on the OGNL caches lists the settings; the 7.4.0 values come from default.properties and StrutsConstants:

The effect is easy to see by reading the cache size from the container, which the scratch probe action did through ActionContext.getContext().getInstance(OgnlUtil.class).expressionCacheSize(). Evaluating the expressions 10+1, 10+1, 10+1, 10+2, 10+3, 10+3 and books.size+100 one request after the other printed the sizes 59, 59, 59, 60, 61, 61 and 62: a new string adds one entry, a repeated string adds none. With struts.ognl.enableExpressionCache set to false the size stayed 0 for every request. The sizes are relative: the cache already held 58 entries parsed by the framework and the JSP in earlier requests. Two consequences follow. A tag attribute that is the same on every request costs one parse for the whole lifetime of the application, while an expression whose text changes with each request (built from request data, the pattern the previous sections forbid) fills the cache with entries that are never used again; this is the performance reason, besides the security reason, to keep expression text constant. And the cache keeps the tree, not a Java class: nothing is compiled to bytecode.

The Tag Developer Guide has a page called "OGNL Expression Compilation" that suggests otherwise, and it is worth reading for what it is. It is an integrator’s guide to the OGNL 2.7 bytecode enhancement API (Ognl.compileExpression, OgnlExpressionCompiler, ExpressionAccessor, Javassist) written around the Tapestry 4 integration (HiveMindExpressionCompiler, ExpressionBinding, a pool of OgnlContext objects) and says of itself that it is not meant for general user reference. It refers to the OpenSymphony JIRA and to a snapshot repository at an address from that time. Struts does not use that API: a search of the 7.4.0 struts2-core classes finds no reference to compileExpression, setCompiler or ExpressionAccessor, and OgnlUtil.compile(String) only parses the expression (through the OGNL Guard), checks that it is not an eval chain and returns the parsed tree, caching it like every other expression. "Compilation" in a Struts context therefore means "parsing and caching the tree", and the page matters to Struts users only if they write their own OGNL integration, in which case they should read the OGNL project’s current documentation instead.

Summary

  • The ActionContext is a thread-local map with everything of the request; the ValueStack is a stack of objects held in it as the OGNL root, with the action on it and, depending on the page, a model, an iterated element, a pushed object or a set map.

  • A plain name searches the stack from the top; [n] cuts the stack; top is the top; #name reads the context map (#session, #request, #application, #parameters, #attr, #action and your variables); %{...} forces evaluation in a String attribute; ${...} is JSP EL and cannot go in a Struts tag attribute.

  • OGNL gives properties, indexes, projection {x}, selection {? ...}, {^ ...}, {$ ...}, literal lists and maps, in and not in, operators and instance methods; Struts 7.4.0 lets through only what the allowlist, the exclusion lists and the static rules permit, and refuses silently with a WARN line in the log.

  • Keep expression text under your control: request data goes into values, never into expression text, getText keys or evaluated defaults.

  • Use the property forms of collections, expose constants as getters, allowlist your model packages, and turn off the context fallback and the stack lookup from EL when the application does not need them.
