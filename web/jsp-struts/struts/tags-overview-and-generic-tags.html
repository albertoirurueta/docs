Tags Overview & Generic Tags

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Apache Struts 7.4.0 (released 2026-10-02) running on Apache Tomcat 11.0.26 and Java 21 with Jakarta Pages 4.0 and Servlet 6.1; the facts were checked on 2026-10-08 against the 7.4.0 struts2-core jar (its struts-tags.tld, the tag and component classes and default.properties) and the Tag Developer Guide, and every example on it was built into a WAR, deployed on Tomcat 11 and requested. The Struts tag library is the part of the framework that a JSP page talks to: a view does not call the action, it writes <s:property value="filter"/> and the tag looks the name up on the value stack, formats the result and writes it, escaped. The library has 53 tags in the 7.4.0 descriptor, 27 generic tags (control flow, data access, URLs, assets) and 26 UI tags (form controls and their layout); this page is about the generic ones and about the rules that every tag attribute obeys, the UI and form tags and the themes that render them are the topic of the pages UI & Form Tags and Themes & Templates. The running scenario is the Bookshelf, a catalogue of books exposed as Struts actions: the page reads its list of books, loops over them, builds links to other actions, formats prices and dates and links the CSS and JavaScript of the page, and every output shown is real. The related pages of this section are linked where they help: FreeMarker & Velocity Views, Tiles & Page Layouts, Security Hardening, JSON Plugin & AJAX and Testing.

The Big Picture

A Struts tag is a normal JSP tag handler (a classic tag, see Custom Tags: Classic Handlers) with one extra step. The handler class lives in org.apache.struts2.views.jsp (PropertyTag, IteratorTag, URLTag and so on), receives each attribute as a String through its setters and hands them to a component in org.apache.struts2.components (Property, IteratorComponent, URL and so on). The component holds the logic: it evaluates the attributes against the value stack (which the framework put in the request before the JSP ran, see Architecture and Request Lifecycle), pushes and pops objects on the stack, and writes to the page. The same components serve the FreeMarker and Velocity tags, which is why the Tag Developer Guide says the library is decoupled from the view technology: <s:property .../> in a JSP and <@s.property .../> in a FreeMarker template call the same Property component.

Tag Syntax: How Attributes Are Evaluated

The Tag Syntax page boils the whole subject down to three rules, and every surprise with a Struts tag is one of them being applied:

  1. All String attribute types are parsed for the %{ ... } notation; text outside the notation is literal.

  2. All non-String attribute types (a boolean, an int, a List or a Collection, an Object) are not parsed for the notation but evaluated directly as an OGNL expression.

  3. The exception to rule 2: if a non-String attribute does use the %{ } notation, the notation is ignored as redundant and its content is evaluated, so %{true} and true mean the same.

Source: Tag Developer Guide — Tag Syntax, Reading a property

flowchart TD A["Attribute value as written in the page"] --> B{"Is the tag property a String?"} B -->|"yes"| C["Parse for percent-brace expressions"] C --> D["Text outside the braces stays literal, text inside is evaluated as OGNL"] B -->|"no: boolean, int, List, Object"| E["Evaluate the whole value as an OGNL expression"] E --> F{"Was it written with the percent-brace notation?"} F -->|"yes"| G["Strip the notation, evaluate the content"] F -->|"no"| H["Evaluate as written"] D --> R["Result goes to the component"] G --> R H --> R

String Attributes

The experiment that shows rule 1 uses s:textfield with theme="simple", which renders just the <input> element and no table row (themes belong to the page on themes and templates). The same action property filter (value all) is written five ways, and the HTML of each is quoted:

<s:textfield name="filter" theme="simple"/>
<s:textfield name="filter" value="filter" theme="simple"/>
<s:textfield name="filter" value="%{filter}" theme="simple"/>
<s:textfield name="filter" value="%{getText('book.heading')}" theme="simple"/>
<s:textfield name="filter" value="%{filter} and %{count}" theme="simple"/>
<input type="text" name="filter" value="all" id="filter"/>
<input type="text" name="filter" value="filter" id="filter"/>
<input type="text" name="filter" value="all" id="filter"/>
<input type="text" name="filter" value="Books on the shelf" id="filter"/>
<input type="text" name="filter" value="all and 4" id="filter"/>

The first line gets its value without a value attribute at all, because name tells the tag which property to read (and to write back on submission). The second prints the literal text filter: value of a form tag is a String attribute, so filter is a literal, not a property name. The third reads the property with the notation. The fourth calls a method of the action (getText is inherited from ActionSupport) and the fifth mixes literal text with two expressions, which is what the notation is for.

The most common use of the same rule is a label that comes from a message bundle or contains data:

<s:textfield name="filter" label="%{#request.requestId}" theme="xhtml"/>

<s:textfield name="filter" label="%{getText('book.heading')}" theme="xhtml"/>
<s:textfield name="filter" label="Cart item No. %{count} note" theme="xhtml"/>

The Text tag page of the Tag Developer Guide shows exactly that form, label="getText('person.lastName')", as the way to use i18n in an attribute; on Struts 7.4.0 it prints the call, and the working form needs %{...} around it.

Rule 2 is the reason that test=count  3 works without any notation on s:if, and that multiple="true" on a select is a boolean. The Tag Syntax page gives four spellings of the same boolean; the example WAR renders them with a s:select (the multi-select attribute multiple is a boolean), and the HTML shows that the first two are multiple selects and the last two follow the action property allowMulti, which is false:

The list attribute of the same tag is a non-String attribute too: list="genres" is the OGNL expression genres, the Map of the action. Because it is easy to forget which attributes are Strings, the notation is harmless on the non-String ones, and most Struts code writes %{...} everywhere an expression is meant; the official examples of the generic tags, though, write test="#rowstatus.odd == true" and value="users" without it, and so does this page.

The Alt Syntax, History Only

The page named Alt Syntax in the Tag Developer Guide is now a history page, and it is the reason that older books and blog posts look different. Before WebWork 2.1.4 every attribute was evaluated as an OGNL expression, so a literal needed single quotes; the altSyntax option made only %{...} evaluate. It was on by default from WebWork 2.2 and a struts.xml constant and a per-request flag could switch it off. Struts 2.6 removed both (WW-3877), so the %{...} notation is the only syntax. The guide’s own before-and-after example is the clearest summary:

<%-- old syntax, expression everywhere --%>
<s:textfield label="'Cart item No.' + #rowstatus.index + ' note'"
             name="'cart.items[' + #rowstatus.index + '].note'"
             value="note" />

<%-- today: literal text, %{...} marks the expressions --%>
<s:textfield label="Cart item No. %{#rowstatus.index} note"
             name="cart.items[%{#rowstatus.index}].note"
             value="%{note}" />

Source: Tag Developer Guide — Alt Syntax, History

A page copied from an old example in which value="note" was supposed to read the property note prints the literal text note on Struts 7.4.0 (the third line of the experiment above), and a ${...} of the same era is JSP EL, which a Struts attribute does not accept.

Property Names That Cannot Be Used

The Tag Syntax page lists seven property names as disallowed: parameters, application, session, struts, request, servletRequest and servletResponse; its example, <s:iterator value="parameters"/> on an action with a getParameters() getter, "will not work". On Tomcat 11.0.26 with Struts 7.4.0 an action with String[] getParameters() was read normally:

D1 [<s:iterator value="parameters"><s:property/>,</s:iterator>]
D2 [<s:iterator value="getParameters()"><s:property/>,</s:iterator>]
D1 [x,y,]
D2 [x,y,]

Source: Tag Developer Guide — Tag Syntax, Disallowed property names

The bare name resolves on the stack, the action is on the stack, so its property wins. The names are still a poor choice: they are the names of the context map’s own objects, and #parameters, #session and #request with a # mean something else on the same page; the rule to keep is not to give an action a property that has the name of a context object.

The Characters of OGNL: the One-Character Trap

A quirk of OGNL deserves its own paragraph because it is the oldest question about the if tag (the guide’s FAQ has it). In OGNL a single-quoted literal of one character is a char, not a String. Comparing the string a of the action to the literal 'a' is therefore false:

<s:if test="one == 'a'">one is a</s:if><s:else>one is not a</s:else>
<s:if test='one == "a"'>one is a</s:if><s:else>one is not a</s:else>
<s:if test="one.length == 1">len</s:if>
<s:if test="one in {'a'}">in</s:if>
one is not a
one is a
len
(nothing)

Source: Tag Developer Guide — Struts Tags, FAQs (the one-char string question)

The cure given by the FAQ is to flip the quotes: double quotes inside single quotes make a String. The same applies to every test or value with a one-character literal; a literal of two or more characters is a String and needs no care.

Expressions Outside Tag Attributes

JSP EL and OGNL live side by side on a page and do not read the same objects: ${...} is evaluated by the JSP container and works in template text and in the attributes of JSP or JSTL tags, while OGNL works only in Struts tag attributes. The Tag Syntax page lists the forms: ${user.username} reads a JavaBean in a standard context (JSTL, FreeMarker or Velocity), <s:textfield name="username"/> reads a property on the stack, and #{'a':'b'} is a literal map. How ${filter} reaches the value stack (the request wrapper that falls back to the stack), why <s:property value="${x}"/> fails and what changes with escaping is the subject of the value stack page; the section on JSTL below shows the combinations that work.

Escaping the Body of a Tag

Since Struts 2.6 and the FreeMarker version that enables auto-escaping by default, the guide says to stop using ?html in custom tags and FreeMarker pages. For the tags whose body is markup the library offers escapeHtmlBody: it exists on a, submit and component, and the global constant struts.ui.escapeHtmlBody sets it for all three, with the attribute taking precedence over the constant. bean instantiates a class that conforms to the JavaBeans specification, sets properties through nested param tags and pushes the bean on the stack for the body; with var it is also stored in the context, for later use. The class needs a public no-argument constructor and setters for the parameters, and, as for every object that OGNL touches, its package must be allowlisted: with a helper class in a package that was not (org.example.other.Helper), the tag created the object but its param setter and its getter were refused (is not allowlisted in the log) and the properties printed nothing. The attributes are name (required, the class name) and var.

BE3 [<s:bean name="org.example.bookshelf.model.Reader" var="r2"><s:param name="name" value="%{filter}"/></s:bean><s:property value="#r2.name"/>]
BE1 [Ana/Lima] [Ana] []
BE3 [all]

Source: Tag Developer Guide — bean tag, Examples

Inside the body the bean is on top of the stack (name and city read its properties); outside, the stack is popped (the third value of BE1 is empty) and the var is the way back (#reader.name). The bean tag is a view-side object factory and it creates objects in the view that no action tests; use it for a helper such as a formatter or a counter, not for domain objects. A class that cannot be loaded is a silent failure: with name="org.example.bookshelf.NoSuch" the log had a ClassNotFoundException, the tag wrote nothing, and every expression after it on the page, even <s:property value="filter"/>, printed nothing (page bd), because the failed bean was left on the stack. A page that suddenly goes blank after a bean tag has a mistyped class name.

The param tag parameterises the tag that contains it: bean, include, url, a, text, action, append, merge and component are the tags that read it. It has name, value and suppressEmptyParameters. The guide stresses a difference between the two ways to give a value, which is rule 1 versus rule 2 in a new place:

<s:param name="color">blue</s:param>       <%-- (A) body: the text "blue", a java.lang.String --%>
<s:param name="color" value="blue"/>       <%-- (B) attribute: the OGNL expression "blue", an Object --%>

Source: Tag Developer Guide — param tag, Description (WW-808)

The second form is the one that catches people out. value is an expression, blue is not a property, so the value is null; to pass the text it must be a literal, value="'blue'", or the body form. On the example page:

PA3 [<s:bean name="org.example.bookshelf.model.Reader" var="r5"><s:param name="city" value="Lima"/></s:bean><s:property value="#r5.city"/>]
    [<s:bean name="org.example.bookshelf.model.Reader" var="r6"><s:param name="city" value="'Lima'"/></s:bean><s:property value="#r6.city"/>]
    [<s:bean name="org.example.bookshelf.model.Reader" var="r7"><s:param name="city" value="%{'Lima'}"/></s:bean><s:property value="#r7.city"/>]
PA3 [] [Lima] [Lima]

The empty first value is null from the unquoted Lima. The same mistake appears in the FAQ of the guide about locale links (<s:param name="request_locale" value="en" />), where the quotes are missing. suppressEmptyParameters leaves an empty parameter out of the URL, see the url tag below.

action

action executes an action from within a view, and optionally renders its result in place: a way to compose a page from the output of several actions (a "portlet" of the shelf’s statistics on every page). Nested param tags give parameters to the action.

Three behaviours of this tag differ from what the guide’s text implies:

  • The guide and its FAQ say that a method other than execute is selected with the "bang" syntax, <s:action name="actionTagAction!specialMethod" executeResult="true"/>. In Struts 7.4.0 dynamic method invocation is off (struts.enable.DynamicMethodInvocation=false in default.properties), and stats!featured did not call featured() (the note attribute stayed empty, AC3); a mapping with method="featured" (the stats-featured action of the example) is the form that works (AC8). Wildcard mappings with {1} give the same effect for many methods; the page Wildcard Mappings & Method Invocation has the details.

  • An exception thrown by the inner action does not stop the page by default: with rethrowException left at false the tag logs the error and goes on (AC5, the boom action: the variable was set and the page continued). With rethrowException="true" the exception propagates out of the tag, the page stops where it is (the browser received the text before the tag with status 200 and the container then reported that sendError() could not be called on a committed response).

  • An inner action runs the full interceptor stack, including validation and the workflow interceptor, which is why the FAQ says that an action tag whose action has validation errors does not execute its method; the default stack excludes input from validation, so !input is the documented way around it.

Source: Tag Developer Guide — Struts Tags, FAQs (the action tag questions)

The action tag is a convenience with a cost: it executes a whole request cycle inside the page, so a page with ten of them runs ten action stacks. For a reusable fragment of a page a JSP include or a tag file is lighter (see the include tag below, and the Part I page Tag Files & Layouts).

  • action produces the context path, the action name and the extension (.action); value with a leading slash is context-relative and without it is left as written (UR1, logo.png). A value that starts with a scheme (http://example.org/p) is used as is.

  • The parameters are encoded (a space is +) and, by default, the & between parameters is written as &, correct inside an HTML attribute (UR3).   • includeParams is the cause of the question of the FAQ, "why are request parameters appended to our hyperlinks": it copies the parameters of the current request into the generated URL. compress (since Struts 7.2.0) removes the whitespace between the tags of its body while keeping the content, to reduce the size of generated HTML. It is enabled globally by struts.tag.compress.enabled (default true) and is switched off automatically in development mode so that the output stays readable; force="true" overrides that. The body size is limited by struts.tag.compress.maxSize (default 10485760, 10 MB, content above it is skipped without compression) and the log lines show at most struts.tag.compress.log.maxLength (200) characters of the body, so sensitive text is not written to the log.

<s:compress>
   <div>
      <p>Compressed    text</p>
      <span>between tags</span>
   </div>
   <pre>
     keep   this
   </pre>
</s:compress>
<s:compress force="true"><ul>
   <li>one</li>
   <li>two</li>
</ul></s:compress>
<div><p>Compressed    text</p><span>between tags</span></div><pre>
     keep   this
   </pre>
<ul><li>one</li><li>two</li></ul>

Source: Tag Developer Guide — compress tag, Examples

Whitespace between tags is removed and whitespace inside text and inside <pre> is kept, so the tag does not change what a browser renders. In the devMode build the first block was left alone and the second, with force="true", was compressed. The documentation lists the safeguards: bodies above the size limit are left as they are, the regular expressions have a ReDoS guard with a hard 50 MB limit and the log text is truncated. The saving is small for pages that are served compressed by the container or a proxy; the tag is for pages generated with much indentation.

Inconsistencies in the Official Documentation

Collected while verifying this page against the 7.4.0 jar, default.properties and the running examples; none of them changes behaviour, but each can mislead:

  • The Tag Reference page lists 26 generic tags; the 7.4.0 TLD has 27: number (class NumberTag, component org.apache.struts2.components.Number) has no reference page, and tag-developers/number-tag.html answers 404.

  • The Tag Syntax page says the property names parameters, session, request, application, struts, servletRequest and servletResponse are disallowed and that <s:iterator value="parameters"/> "will not work"; an action with getParameters() was read normally on Struts 7.4.0 (page syntax, D1).

  • The Text tag page shows <s:textfield name="lastName" label="getText('person.lastName')"/> as the way to localise a label; without the %{...} notation the attribute is the literal text getText('person.lastName').

  • The Text tag and i18n tag pages read a pushed bundle with <s:property value="text('aaa.bbb.ccc')"/>; on 7.4.0 text('...') printed nothing and only s:text reads the bundle of s:i18n.

  • The URL tag page says that the includeParams constant defaults to none since 2.1.3 (as default.properties does), and the FAQ "Why are request parameters appended to our hyperlinks" says the default is GET; the FAQ’s repair, <s:param name="request_locale" value="en" />, passes null because en is an expression, not a string.

  • The Action tag page and its FAQ select a method with name!method, which requires dynamic method invocation; the constant defaults to false and stats!featured did nothing on 7.4.0.

  • The Include tag page says no value stack is created for the included page, so s:property cannot read the parameters; the request’s value stack is visible in the included JSP (the parameters are still only request parameters).

  • default.properties comments the global constant as escapeHtmlTag (“<s:a ... escapeHtmlTag="true">”); the attribute of the tag is escapeHtmlBody.

  • The iterator page documents status as a Boolean attribute (it takes a name, and the docs' own examples write status="rowstatus"), its var description as the name "used to reference the value pushed into the Value Stack (scope: action)", and its example of the <s:iterator var="counter" begin="1" end="5"> comments as if counter held the number (it prints the loop number only through top).

  • The Push tag examples spell the tag s:propery (missing letter) and close it with </push>; the Iterator tag example has the same unclosed </push> and the action tag example ends a span that was never opened. The a tag page’s usage example calls errorText and preInvokeJS, attributes that are not in the 7.4.0 TLD (they belonged to the removed Ajax tags) and uses ${id} inside a Struts attribute.

  • The append tag page’s example of <s:param value="%{myList1}"/> does not say that an empty list in the sequence ends the append.

  • The Generator tag page’s "Example 4" is titled "generate an iterator with comparator attribute" and uses converter.

  • The Text tag page links to java.sun.com pages for Java 1.4.2 for MessageFormat and DecimalFormat.

Summary

  • The Struts tags are classic JSP tag handlers over shared components; the TLD is in struts2-core (uri="/struts-tags", 53 tags: 27 generic, 26 UI) and no attribute accepts a JSP expression.

  • Attributes obey three rules: a String attribute is literal text with %{...} expressions embedded, a non-String attribute is itself an expression, and %{} around a non-String attribute is redundant. The pre-2.2 syntax with 'literal' everywhere is gone since 2.6.

  • A bare name is read from the value stack, #name from the context map; OGNL’s one-character literal is a char, and the JDK collection methods are blocked, so use books.size, books.empty, books[0].

  • The control tags: if (a real boolean test), iterator (var, status with index, count, first, last, odd, even, begin/end/step), append, merge, generator, sort and subset for iterators.

  • The data tags: property (escapes HTML by default), set and its scopes, push, bean and param, action, text and i18n, date, number, include, url and a (including includeParams, escapeAmp and the encoding of parameters) and debug.

  • script, link (CSP nonce), webjar (since 7.3.0) and compress (since 7.2.0) are the asset tags.

  • JSTL and EL work beside the tags: ${filter} reads the stack through the request wrapper; escape EL output with c:out; read a JSTL variable from OGNL with #attr.name.
