Localization and i18n

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Apache Struts 7.4.0 (released 2026-10-02) running on Apache Tomcat 11.0.26 and Java 21, the combination that every example was built, deployed and requested on; the facts were checked on 2026-10-08 and 2026-10-10 against the Core Developer Guide pages on https://struts.apache.org/core-developers/, the Tag Developer Guide, the 7.4.0 struts2-core jar (default.properties, struts-default.xml, javap of TextProvider and ActionSupport) and the 7.4.0 source of StrutsLocalizedTextProvider. Struts has one mechanism for every piece of text that is not hard-coded in a page: property files that live next to the Java classes, a lookup that walks the class hierarchy, the model, the package tree and the global bundles, and a locale that the i18n interceptor puts into the action context on each request. The same machinery produces form labels, validation and type conversion messages, the output of s:text and, through MessageFormat, the localized dates and numbers of the views. The running scenario is the Bookshelf, a catalogue of books exposed as Struts actions; this page uses it to print the seven levels of the bundle search, to switch the page between English, German, Spanish and French with request_locale, to format a price and a publication date for each locale and to measure what happens with a locale that nobody supports. The neighbouring pages are linked where they help: value stack and OGNL, type conversion, validation and the form tags, besides the chapters on actions, interceptors and configuration.

Where Struts Needs Localized Text

The Core Developer Guide lists three places where the framework internationalizes: the UI tags, the messages and errors of the ValidationAware interface (field errors, action errors, action messages), and the action classes that extend ActionSupport, through getText(). All three use the same lookup, LocalizedTextProvider.findText(...), and the same locale, the one stored in the ActionContext. A page therefore never asks for a locale; it asks the action (or the s:text tag) for a key and receives the text for whichever locale the request was given.

Resource Bundles in Two Minutes

A resource bundle is a family of Java ResourceBundle files that share a base name. In Struts they are plain .properties files on the class path (src/main/resources in a Maven project), one key=value per line:

# LocaleAction.properties (the base bundle, used when no locale file matches)
book.title=Books
accent=café
format.money={0,number,currency}
format.date={0,date,MM/dd/yyyy}

# LocaleAction_de.properties
book.title=Bücher
accent=Käse über
format.money={0,number,#,##0.00} €
format.date={0,date,dd.MM.yyyy}

Source: Java 21 Javadoc — PropertyResourceBundle

Struts does not read the files itself; it asks java.util.ResourceBundle.getBundle(name, locale, classLoader) for the bundle, so the rules of the JDK apply:

  • The file name is the base name, an underscore and the locale suffix: LocaleAction_de.properties (language), LocaleAction_de_AT.properties (language and country). For a request in de_AT the JDK tries _de_AT, _de and the base file, in that order, and each file only needs the keys that differ from the more general one.

  • If no file exists for the requested language, the JDK falls back to the JVM default locale before the base file. On the test machine (en_US) a request for zz therefore ends in LocaleAction.properties; on a server whose default locale is German it would end in LocaleAction_de.properties. Setting -Duser.language on the server, or shipping a base file in the application’s main language, makes the result predictable.

  • Since Java 9 a .properties bundle is read as UTF-8 and, only if the bytes are not valid UTF-8, again as ISO-8859-1. The Bookshelf shows both: LocaleAction_de.properties is saved as UTF-8 (Bücher) and LocaleAction_fr.properties as ISO-8859-1 (the byte 0xE9 for é), and both printed correctly on Java 21. The books of the section tell the reader to write é escapes or to run native2ascii; neither is needed any more, but mixing encodings in one project is an invitation to a file that is silently read as Latin-1, so keep every file in UTF-8.

  • A property file that is not found is not an error: Struts caches the miss and moves on to the next level.

Source: Java 21 Javadoc — ResourceBundle.getBundle(String, Locale)

The Package Tree

Step 5 walks up the directory structure of the class. The Core Developer Guide draws it with com/acme/package.properties and com/acme/actions/package.properties: if FooAction.properties does not define the key, com/acme/actions/ is searched, then com/acme/, then com/, and so on up to the root of the class path. Placing the labels that several actions share (the field names of a form that is submitted to a create and to an update action) in the package file removes the duplicates that the "one bundle per action" rule produces; the message-resource tutorial of the Getting Started guide does exactly that with a greeting key in org/apache/struts/package.properties.

Source: Getting Started — Message Resource Files, Package Level Properties

The Key Hierarchy (Step 6)

The Core Developer Guide calls step 6 "search up the i18n message key hierarchy itself" and does not explain it. The code does this: when a dotted key such as book.heading was not found, Struts treats the part before the first dot as a property of the action (getBook()), takes the property’s type, and runs the whole lookup again for the rest of the key (heading) with that type as the starting class. The Bookshelf’s BookAction has a Book getBook() property, and Book.properties has the key heading:

public class BookAction extends ActionSupport {
    private final Book book = new Book();

    public Book getBook() {
        return book;
    }
}
# org/example/bookshelf/Book.properties

getText        = <s:property value="getText('book.heading')"/>

Observed (GET /g9i18n/child): both lines print Heading found in Book.properties through the property book. In the action plain, which has no book property, the same two lines print the key book.heading. This is why the key attribute of a form field named person.firstName can be labelled from Person.properties, the class of the nested bean, with no label entry in the action’s own file; it is also why the getText of an unknown dotted key costs a reflective look at the first segment. The order page above has a related line: getText('key.hier.sub.deep') printed the key itself although key.hier exists, because only the first segment is peeled off and the tail is then looked up in the type of that property; a longer key is not shortened from the right.

Actions Without a Class

An <action> with no class attribute (a pure forward, <action name="plain"> in the Bookshelf) is instantiated from the package’s default class reference. In 7.4.0 the default-class-ref of struts-default.xml is org.apache.struts2.ActionSupport, so for such an action step 3 reaches ActionSupport.properties, which the Core Developer Guide puts in org/apache/struts2/. The scratch app has org/apache/struts2/ActionSupport.properties with one key, common.save, and both the class-less plain action and BookAction print it:

The same trick is the Struts 7 replacement for the single application.properties of Struts 1: one ActionSupport.properties holds the texts that every action of the application shares (button captions, "required" markers), as long as the actions extend ActionSupport. Putting a package-wide file at the top of the package tree, or a global bundle, is the alternative that does not depend on the base class.

Global Bundles and the Framework’s Own Texts

A global bundle is one that is searched last, for every action, regardless of the class or package. It is declared with the constant struts.custom.i18n.resources, a comma separated list of base names (not file names, no extension, the package written with dots or slashes):

<constant name="struts.custom.i18n.resources" value="global"/>
<!-- several bundles: -->
<constant name="struts.custom.i18n.resources" value="global,org.example.bookshelf.errors"/>

The same constant can be written in struts.properties (struts.custom.i18n.resources=global). Bundles are looked up with the request locale, so global_de.properties next to global.properties works exactly as for any other bundle. The Bookshelf’s global.properties carries shop.name=Bookshelf, the contact text and key.hier, the key that the order table above showed being overridden by ShelfAction.properties.

The framework registers two bundles of its own after the custom ones: org/apache/struts2/struts-messages (token, upload and development-mode messages, struts.messages.*, with translations for da, de, en, pl and pt) and org/apache/struts2/xwork-messages (xwork.default.invalid.fieldvalue=Invalid field value for field "{0}"., the text of every conversion error that nothing more specific overrides, and the "no action mapped" messages). A key of the same name in your global bundle comes first, which is how an application replaces struts.messages.invalid.token or xwork.default.invalid.fieldvalue with its own wording.

What the output proves, line by line:

  • s:text and getText give the same text; s:text is the idiom inside a page and getText is the only way to fill a tag attribute (<s:textfield label="%{getText('person.lastName')}"/>), because a tag cannot be nested inside a tag attribute. The tag reference says exactly this.

  • The positional parameters {0}, {1} are filled from the s:param children, from the list of the OGNL expression {reader, count} or from the Java array. A Number argument is formatted for the request locale, so the integer 1234 prints 1,234; the same value passed as a String (the Java example, String.valueOf(getCount())) prints 1234 because a string is not a number to MessageFormat.

  • quote and quote.args.bad lose their apostrophe: the text is run through java.text.MessageFormat, where a single quote starts a quoted section. It's a book printed Its a book even with no arguments, and It's book number {0} printed Its book number {0} because everything after the quote is literal, including the placeholder. The message must be written It''s book number {0} (two single quotes), which is the single most common i18n bug of a new Struts project and is the reason the s:date pattern of the Spanish bundle below needs doubled quotes.

  • %{title} inside a message is evaluated as OGNL against the value stack (Title: Dune), and the ${reader} of a JSP EL expression is evaluated too (Reader: Ana). The default text provider evaluates a message after reading it from the bundle, which makes a bundle a place where an expression can run. Text that comes from users must never be put in a bundle or passed through a mechanism that evaluates it (see the security section below and the bulletins that involve forced evaluation).

  • A message is not HTML-escaped: <b>bold</b> was written to the page as markup. The s:text tag has the attributes escapeHtml, escapeXml, escapeJavaScript and escapeCsv (all false by default); escapeHtml="true" printed the entities. Escaping depends on where the text is used, so apply it in the view and leave the bundle plain.

  • A missing key never throws. s:text and getText(key) both print the key itself ([no.such.key]), which is how an untranslated screen looks in production; getText(key, defaultValue) and the body of s:text supply a default that is used instead; hasKey(key) answers false without side effects, so a template can choose between a translation and a fallback.

  • var="h" stores the text in the action scope of the value stack and prints nothing, as the tag reference says.

  • s:i18n name="org.example.bookshelf.Titled" pushes another bundle on the value stack, and the s:text inside it read ib from Titled.properties (the interface file, because the bundle named by the tag is searched first). The last line is a trap: getText('ib') inside s:i18n still asks the action and printed the key, while text('ib') returned nothing; the bundle named by the tag was reachable only through s:text. The tag reference’s example uses text('aaa.bbb.ccc') inside the tag; on 7.4.0 with s:property that call printed an empty string.

The i18n Interceptor and the Request Locale

The bundles are chosen by locale, and the locale of the request is decided by the i18n interceptor, which is in the defaultStack of Struts 7.4.0 (fifth after exception, alias, servletConfig and httpMethod; see Interceptors). The interceptor puts a Locale into the ActionContext on every request; the UI tags, the validators, the conversion error messages and getText all read it from there. The order of its decisions, in the words of the Core Developer Guide: a request parameter that names a locale wins and is remembered; otherwise the stored locale is used; if there is none the browser’s locale is used. On top of that, the interceptor removes its own parameters so that nothing is ever set on the action.

The mode decides which request parameter the interceptor listens to: the cookie mode needs request_cookie_locale, the request mode needs request_only_locale, only the session mode listens to request_locale, and the accept_language mode ignored request_locale in the experiment. A language selector (a few links or a select) must therefore use the parameter name that belongs to the configured storage, which the Core Developer Guide does not state in one place.

The supportedLocale list is documented as the filter for Accept-Language: with the value es,de the Bookshelf’s locale-accept action printed de for de-DE,de;q=0.9, and fr (not in the list) still printed fr, so a locale outside the list was not replaced by a default on 7.4.0. The documentation only says the interceptor "will try to match" the supported locales. An application that must restrict the choice has to do it itself, for example with the constants of the section on caches below or a small custom interceptor placed after i18n.

Number Formats in Forms and Round Trips

The Core Developer Guide warns about an input field that shows a number: a field filled with the Java default format is wrong in a non-English locale, and it is worse when the user submits it, because type conversion is locale aware. The Bookshelf has a form on price.jsp backed by PriceAction, a Double price property with @StrutsParameter on the setter (see the parameter injection page for why 7.x needs it), and the message format.number={0,number,#,##0.0##}:

public class PriceAction extends ActionSupport {
    private Double price = 1234.5;

    public Double getPrice() { return price; }

    @StrutsParameter
    public void setPrice(Double price) { this.price = price; }

    @Override
    public void validate() {
        if (price != null && price < 0) {
            addFieldError("price", getText("price.negative"));
        }
    }

    @Override
    public String execute() { return SUCCESS; }
}
raw           = <s:property value="price"/>
formatted     = <s:property value="getText('format.number', {price})"/>
getFormatted  = <s:property value="getFormatted('format.number', 'price')"/>
errors        = <s:property value="fieldErrors"/>
...
<s:textfield key="price" value="%{getFormatted('format.number','price')}" theme="simple"/>

Observed with ?request_locale=de: raw = 1234,5, formatted = 1.234,5, getFormatted = 1.234,5, and the input value 1.234,5. Posting price=1.234,5 under de parsed back to 1234.5. Three facts follow:

  • s:property value="price" already prints 1234,5: Struts converts a Double to a String with the locale of the request, so the "raw" value is not the value of Double.toString. A hidden field that carries a number to a different system must be formatted explicitly.

  • getText('format.number', {price}) and the tag form formatting the same value use the same pattern; getFormatted(key, expression), added to ActionSupport for this purpose, is the variant the guide recommends for input fields because it supports conversion errors: with price=abc posted (a conversion error) the field was re-displayed with the rejected text abc instead of a formatted default.

  • A pattern with grouping (#,##0.0##) is a data-entry trap, because the comma is a group separator in one locale and the decimal separator in another. The input 1,234.5 under en_US parsed as 1234.5 and 1.234,5 under de parsed as 1234.5. Print the same format that you accept (hence getFormatted) and state the expected format in a hint.

When struts.locale is unset, the locale derived from Accept-Language is checked against the JVM’s available locales; an unavailable one falls back to the default locale. The i18n interceptor already checks its own request_locale

A Custom TextProvider

The text provider is an extension point. LocalizedTextProvider is the lookup service (the findText and findResourceBundle methods listed by javap), TextProvider is the view of it that an action sees, and TextProviderFactory creates the TextProvider for a class (StrutsTextProviderFactory by default), which is why the Core Developer Guide says both interfaces must be implemented to change where messages come from (a database, a CMS, a remote service). A custom implementation is registered with <bean> elements and selected with the constants struts.localizedTextProvider and struts.textProviderFactory. The shipped implementations are StrutsLocalizedTextProvider (the hierarchy walk described above), GlobalLocalizedTextProvider (the global-only provider), CompositeTextProvider, DefaultTextProvider and TextProviderSupport, all in org.apache.struts2.text. The text-provider application of the struts-examples repository shows a small implementation.

Worked Example: A Bookshelf Page in Four Languages

Putting the pieces together, the following is the order in which a request to GET /locale?request_locale=de is processed in the Bookshelf, with the files that contribute:

  1. The Servlet container hands the request to StrutsPrepareAndExecuteFilter, which creates the ActionContext with the locale from struts.locale or Accept-Language.

  2. The i18n interceptor finds request_locale=de, validates it, writes de to the session under WW_TRANS_I18N_LOCALE, replaces the locale of the ActionContext and removes the parameter.

  3. LocaleAction runs and returns success, and locale.jsp is rendered with the action on the value stack.

  4. <s:text name="book.title"/> asks findText(LocaleAction.class, "book.title", de): step 1 finds LocaleAction_de.properties, so the answer is Bücher.

  5. <s:text name="format.money"> reads the pattern {0,number,#,##0.00} € from the same file and MessageFormat renders 1.234,50 €.

  6. <s:date name="published"/> reads struts.date.format (dd.MM.yyyy) and prints 01.08.1965.

  7. The next request in the session has no parameter; the interceptor reads the session value and the page is again German.

The three bundles that matter for the page are LocaleAction.properties (English and fallback), _de and _es; a fourth language costs one file, and a language that has only some keys falls back, key by key, to the base file because the JDK combines the candidate bundles (LocaleAction_fr.properties has no format.money and the page printed the English pattern with the French number rules and the ¤ sign: partial files should be completed or the missing keys inherit the base language).

Struts Messages Versus JSTL fmt

A Struts page that is rendered by JSP can also use the JSTL formatting library (fmt:message, fmt:formatDate), which has its own locale and bundle model: it reads the locale from the jakarta.servlet.jsp.jstl.fmt.locale configuration setting or the Accept-Language header, not from the ActionContext, and it finds bundles by basename rather than through the class-based search of getText. A request_locale change made by the i18n interceptor is therefore not seen by fmt:message unless the same locale is also passed to it with fmt:setLocale. The safe rule is to use one mechanism per page: s:text and getText for texts that belong to an action, and the JSTL library, described on the JSTL i18n & Messages page, only in plain JSP pages that are not served by an action.

Inconsistencies in the Official Documentation

Collected while verifying this page against the 7.4.0 jar and source; none of them changes behaviour, but each can mislead:

  • The Localization page says the default action class defined by default-class-ref is com.opensymphony.xwork2.ActionSupport; in 7.4.0 struts-default.xml names org.apache.struts2.ActionSupport, which is the class whose .properties file is meant.

  • The Localization page says step 6 is to "search up the i18n message key hierarchy itself" without saying that this is a child-property lookup in the type of the first key segment.

  • The I18n Interceptor page says a request to foo.action?request_locale=en_US stores the locale; its parameter table names request_cookie_locale and request_only_locale, but the page does not say that the cookie and request storage modes react only to their own parameter (observed: request_locale did nothing in either).

  • The Text tag page uses text('aaa.bbb.ccc') inside s:i18n with s:property; on 7.4.0 the call returned an empty string, and s:text is what reads the pushed bundle.

  • The Text tag page’s example label="getText('person.lastName')" shows no %{...}; without it the attribute is a literal string, not an expression.

  • The Formatting Dates and Numbers page sends the reader to "Sun’s Java API docs" and the Text tag page links to java.sun.com pages for Java 1.4.2; the current documentation is the MessageFormat Javadoc of the JDK in use.

  • The Localization page’s Struts 1 comparison says the ActionSupport.properties shortcut works "if all your actions subclass XWork2’s ActionSupport"; in 7.x the class is org.apache.struts2.ActionSupport and XWork2 no longer exists as a package.

Summary

  • Texts live in .properties files next to the classes: the action, its interfaces, its base classes, the model, the package.properties of every package up the tree, the child-property type and the global bundles, searched in that order until the first match.

  • getText, s:text, s:i18n and the key attribute all use that lookup; a missing key prints the key, a default argument or the tag body replaces it, and the text is formatted with MessageFormat (so a single quote must be doubled) and evaluated for %{...}.

  • The i18n interceptor chooses the locale: request_locale stores it in the session, request_cookie_locale in a cookie, request_only_locale for one request, and accept_language follows the browser; each storage mode listens to its own parameter.

  • Dates and numbers are MessageFormat patterns in the bundles; s:date reads struts.date.format, forms use getFormatted, and conversion errors are invalid.fieldvalue.<property> messages in the same bundles.

  • The locale comes from the client: keep Struts at 7.4.0, keep the caches bounded, and set struts.locale.validateRequestLocale or a fixed struts.locale on public sites.
