Security Bulletins

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Apache Struts 7.4.0 (released 2026-10-02) running on Apache Tomcat 11.0.26 and Java 21. The bulletin list of the Struts wiki, every bulletin cited here, the announcement pages announce-2026.html, announce-2025.html, announce-2024.html, announce-2023.html, announce-2018.html and announce-2017.html, the End-of-Life page and the security guide were fetched and read on 2026-10-10 (the bulletin list ends at S2-078, published on 2026-10-05), and every CVE id shown was looked up on the CVE record service behind cve.org and, for the recent ones, on NVD before it was written down. The page is the history of how Struts was attacked: the bulletins are the project’s own advisories, one wiki page per vulnerability with the affected versions, the fixed versions, the reporter, the CVE id, a description, a solution, a statement about backward compatibility and a workaround. Reading them as a series shows that a handful of design decisions (OGNL evaluated on text that came from the request, parameters bound without a filter, prefixes in parameter names that choose an action, a multipart parser that handles untrusted headers, plugins that deserialize request bodies, and resources that grow with the input) produced almost every serious entry, and that each of those decisions has a visible countermeasure in Struts 7.4.0. The running scenario is the Bookshelf: the page asks, for a Bookshelf built on an old Struts release, which bulletins applied, and ends with an audit of the Bookshelf built on 7.4.0 that fails the build on a vulnerable version and probes the classic attack shapes against the running application. The related pages of this section are Security Hardening, Security Headers, Debugging, Dev Mode and Logging, Testing, Deployment and Production and Struts 1 Classic and Migration.

How a Bulletin Reads

The wiki page Security Bulletins is an index; each entry is a child page named S2-nnn (S2 for Struts 2, a number in the order of publication). Every bulletin has the same fields, and knowing them makes the pages quick to read.

Field What it tells you

Summary

A one-line statement of the weakness

Who should read this

Who is concerned (all Struts 2 developers, or only users of a plugin or a feature)

Impact of vulnerability

The class of damage: remote code execution, denial of service, disclosure of data, data integrity, bypass of a configured limit

Maximum security rating

Critical, Important, Moderate or Low (see the scale below)

Recommendation

The version to upgrade to, sometimes with a configuration alternative

Affected Software

The version ranges, including the branches that are end-of-life

Reporter

Who found it

CVE Identifier

The CVE id, empty for some old bulletins and for configuration advice such as S2-043

Problem, Solution, Backward compatibility, Workaround

The mechanism, the fix, the compatibility cost of the fix and a mitigation when an upgrade is not possible

Source: Apache Struts Security Bulletin — S2-066

The index page defines the four ratings, and the definition is about exploitability, not about the size of the damage.

Rating Meaning in the Struts scale

Critical

Could be exploited by a remote attacker to execute arbitrary code automatically, by worms or scanners, even when developers followed the security advice

Important

Could compromise data or availability; includes easy remote code execution that exists because the developer treated user input as trusted

Moderate

Significant mitigation exists: an unlikely configuration, a rarely used feature, or an authenticated attacker

Low

Believed extremely hard to exploit, or minimal consequences

Source: Apache Struts Security Bulletins (rating scale)

Three reading habits follow from the fields. First, read the affected ranges against the exact version in the application, because several bulletins exclude the patched maintenance releases of an older branch (S2-029 and S2-032 list "except 2.3.20.3 and 2.3.24.3"). Second, read the "Non-affected" and "Note" sentences: S2-067 says that applications not using FileUploadInterceptor are safe, S2-075 says that applications using the default action mapper, the restful2 mapper or the REST plugin are not affected, and S2-072 says that releases which do not bundle the JSON plugin are not affected. Third, read the workaround as a statement of what the weakness depends on: S2-068 offers a size-limited temporary folder or disabling upload, which shows that the leak needs the upload feature to be on.

How the CVE Ids on This Page Were Checked

The wiki pages are written by the project, but the project’s own announcement pages carry ids that look unusual for the 2026 entries (for example CVE-2026-73631 or CVE-2026-104711), so the ids were not copied from the announcements. Each id was fetched from the CVE record service (the JSON API behind cve.org) and the state, the publication date and the title were compared with the bulletin; NVD was queried for a sample of the same ids and returned a record for each. The result is that every id in the tables below resolves to a PUBLISHED record whose title matches the bulletin. The records of the 2026 bulletins were published on 2026-08-14 and 2026-08-15 (S2-070 to S2-074) and on 2026-10-05 (S2-075 to S2-078); the record of S2-069, CVE-2025-68493, was published on 2026-01-11. Where a bulletin has no id (S2-001, S2-007, S2-043) the page says so instead of guessing, and where the bulletin says "Related to CVE-2017-7525" (S2-055) the id is cited as the related Jackson record, not as a Struts id.

Seven Families of Weakness

The seventy-eight bulletins are not seventy-eight different ideas. Grouped by mechanism they fall into a small number of families, and the family is what the Bookshelf author should remember, because the next bulletin will belong to one of them.

Family Bulletins (examples) Countermeasure in Struts 7.4.0 and in your code

OGNL evaluated on request data through parameter names

S2-003, S2-005, S2-009, S2-020, S2-021

ParametersInterceptor with excludeParams patterns, the OGNL allowlist and member access restrictions, and since 6.4 the @StrutsParameter annotation that makes every bound property opt-in (see Parameter Injection and @StrutsParameter)

OGNL evaluated on request data through values (conversion errors, tags, localization)

S2-007, S2-029, S2-036, S2-053, S2-059, S2-061, S2-062

%{...} only on trusted expressions; the 7.4.0 probe below shows no second evaluation of a request value in the attributes tried, Struts tags instead of raw EL, struts.ognl.expressionMaxLength

Method and action selection by request syntax

S2-016, S2-017, S2-019, S2-032, S2-033, S2-057

Dynamic Method Invocation off (struts.enable.DynamicMethodInvocation=false), the action: and redirect: prefixes off, strict method invocation, a namespace on every package (see Wildcard Mappings & Method Invocation)

Multipart and upload handling

S2-045, S2-046, S2-060, S2-063 to S2-068

The actionFileUpload interceptor with UploadedFilesAware, limits in struts.multipart.*, uploads stored outside the web application (see File Upload and Download)

Plugins that parse or deserialize bodies

S2-052, S2-054, S2-055, S2-056, S2-070 to S2-072, S2-077

Plugin limits (struts.json.maxLength, struts.rest.content.maxLength), no XStream handler registered by default (see JSON Plugin & AJAX and REST Plugin)

Resources that grow with the input

S2-011, S2-034, S2-041, S2-044, S2-047, S2-050, S2-063, S2-064, S2-065, S2-068, S2-073, S2-074, S2-076

Bounded reads, bounded caches, bounded decimal rendering; a fixed locale where the application is not multilingual (S2-074)

Shared state and operational exposure

S2-043, S2-069, S2-070, S2-071, S2-078

No Config Browser plugin in production, no shared formatter state, a modern XML parser setup (the XWork XXE of S2-069)

Source: Struts Security Guide — Strict Method Invocation

Source: Struts Security Guide — Defining and annotating your Action parameters

Source: Struts Security Guide — Do not use incoming, untrusted user input in forced expression evaluation

Reading Order: What to Do When a New Bulletin Appears

A bulletin is useful only if it is compared with the application. The decision is small enough to draw: find the version, read the ranges and the conditions, and then either upgrade or apply the workaround.

flowchart TD A["New S2 bulletin or announcement"] --> B["Which Struts version does the WAR contain?"] B --> C{"Version inside the Affected Software ranges?"} C -- "no" --> D["Record the check and the date"] C -- "yes" --> E{"Feature or plugin from the Problem section in use?"} E -- "no" --> D E -- "yes" --> F{"Fixed release available on the same branch?"} F -- "yes" --> G["Upgrade the struts2-bom, rebuild, run the tests"] F -- "no, EOL branch" --> H["Plan migration to 6.x or 7.x now"] H --> I["Apply the Workaround section in the meantime"] G --> J["Redeploy and probe the old attack shape"] I --> J J --> D

The two boxes on the right are the reason the End-of-Life section further down matters: on an end-of-life branch the "fixed release" box is always empty.

S2-057 is the bulletin that shows how configuration and code combine: no line of the application was wrong in isolation. The bulletin’s own advice (and the verified 7.4.0 defaults in this page’s audit) is that every package declares its namespace and that the defaults for method invocation stay off. The 7.x line changed the default of struts.mapper.alwaysSelectFullNamespace to true as part of the 6 to 7 migration, which makes the namespace discipline more important, not less.

The upload bulletins, S2-066 and S2-067, deserve their own paragraph because they changed the framework. S2-066 was fixed by patch releases (2.5.33 and 6.3.0.2), but for S2-067 the bulletin’s only solution is a new mechanism, because it concerns the mixing of setters for uploaded files with setters for normal fields, and it says the change is not backward compatible. The fix was a new mechanism in 6.4 (actionFileUpload, with UploadedFilesAware and UploadedFile) and the removal of the old interceptor in 7.0, so an application that upgrades the version number only finds that its upload code compiles and silently receives nothing. The upload page of this section shows the new mechanism with verified examples.

Five observations come out of these nine entries.

  • A regression can hide in one release. S2-070 and S2-071 affect Struts 7.2.1 and nothing else; the bulletin’s recommendation is 7.3.0. A release number is therefore part of the audit, not only "7.x".

  • Bounded reads are the new baseline. S2-072, S2-073 and S2-077 are the same defect in three places (the JSON plugin, the CSP report endpoint, the REST plugin). Both plugin pages of this section (JSON Plugin and Ajax and REST Plugin) describe the limit constants (struts.json.maxLength and struts.rest.content.maxLength) and the fixed 7.4.0 behaviour.

  • Input that selects a cache key is an input. S2-074 is the localization version of the same idea: the locale of the request chooses the key of a cache, so an attacker chooses the number of entries. The localization page of this section covers the fixed locale. See Localization and i18n.

  • The allowlist did its job. S2-075 is a remote code execution class bug that the bulletin rates Moderate, because a Struts 7 application with the default OGNL allowlist is not affected. The rating is a statement about the mitigation, and the mitigation is a default that the Bookshelf must not switch off.

  • Type conversion renders too. S2-076 shows that the combination of a numeric conversion and a rendered value can amplify a request; see Type Conversion for the conversion side.

Why Struts 2.5 and Older Must Be Upgraded

Worked Example: A Build That Refuses a Vulnerable Struts

The cheapest control is a Maven Enforcer rule that fails the build when any Struts artifact on the classpath is older than the release that closed the latest bulletins. The Bookshelf pom pins one version with the struts2-bom (so every plugin follows it) and adds the bannedDependencies rule below. The rule uses the version range syntax (,7.4.0), which means "anything below 7.4.0".

<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-enforcer-plugin</artifactId>
    <version>3.5.0</version>
    <executions>
        <execution>
            <id>no-vulnerable-struts</id>
            <phase>validate</phase>
            <goals><goal>enforce</goal></goals>
            <configuration>
                <rules>
                    <bannedDependencies>
                        <excludes>
                            <exclude>org.apache.struts:*:(,7.4.0)</exclude>
                        </excludes>
                        <message>Struts below 7.4.0 has published security bulletins (S2-075 to S2-078); upgrade the struts2-bom.</message>
                    </bannedDependencies>
                </rules>
            </configuration>
        </execution>
    </executions>
</plugin>

Source: Apache Maven Enforcer — Banned Dependencies

With the property struts.version set to 7.3.0 (the Bookshelf pom reads the version of the BOM from it), the build stops in the validate phase, before any code is compiled, and the output names the artifact and the rule.

$ mvn -B -q validate -Dstruts.version=7.3.0
[ERROR] Rule 0: org.apache.maven.enforcer.rules.dependency.BannedDependencies failed with message:
[ERROR] Struts below 7.4.0 has published security bulletins (S2-075 to S2-078); upgrade the struts2-bom.
[ERROR] org.example:bookshelf-struts:war:1.0.0-SNAPSHOT
[ERROR]    org.apache.struts:struts2-core:jar:7.3.0 <--- banned via the exclude/include list

With the default 7.4.0 the same command prints Rule 0: ...BannedDependencies passed and BUILD SUCCESS; both runs were made on 2026-10-10 with Maven and JDK 21. The rule is a floor, not a scanner: it knows nothing about bulletins that are published after the date it was written, so the floor has to be raised by a person when a new bulletin names a higher fixed version. A dependency checker in the continuous integration pipeline covers the transitive libraries that the bulletins do not name (the Jackson case of S2-055 is the example).

Source: Apache Struts Security Bulletin — S2-055

Worked Example: Probing the Classic Attack Shapes on 7.4.0

The second half of the audit asks whether the shapes of the historical attacks still do anything on 7.4.0. The Bookshelf action books has one parameter, filter, declared with @StrutsParameter, and the JSP forced.jsp echoes it in four ways. All probes use harmless arithmetic (7*7 would print 49 if it were evaluated) against the scratch application.

public class BookAction extends ActionSupport {
    private String filter;

    public String getFilter() { return filter; }

    @StrutsParameter
    public void setFilter(String filter) { this.filter = filter; }

    public List<String> getTitles() { return List.of("Dune", "Neuromancer"); }
}

<p id="a">[<s:property value="filter"/>]</p>
<p id="b">[<s:property value="%{filter}"/>]</p>
<s:textfield name="q" id="%{filter}" value="x"/>

Expression in a parameter value (S2-007, S2-029 family)

The page prints Filter: %{7*7} literally (200); the value is data

The conclusion is limited on purpose. A clean probe proves that one shape no longer works in one configuration; it does not prove that the application is secure, and the bulletins S2-075 to S2-078 show that the dangerous settings are the ones that were switched off, such as the OGNL allowlist (S2-075 says Struts 7 is affected only when the allowlist is disabled). The hardening page of this section lists the settings that must stay at their defaults.

Following the Announcements

The project publishes security news through four channels, and a team should subscribe to at least the first.

Channel What it carries

announcements@struts.apache.org

The announcements mailing list named on the project’s mailing list page, with the subscribe address announcements-subscribe@struts.apache.org (and an unsubscribe address of the same pattern); the Announcements pages below are the web copy of what it announces

The Announcements pages (announce-2026.html and the earlier years)

One entry per release and per bulletin, with an anchor of the form a20261005-s2075; each entry names the bulletin, the CVE id and the fixed versions

The Security Bulletins index on the wiki

The index of the S2 pages, the authoritative list of bulletins

security@struts.apache.org

The private address for reporting a vulnerability (never for ordinary bugs, which go to the issue tracker); the project asks reporters to read the security guideline first

Source: Apache Struts — Mailing Lists

Source: Apache Struts — Reporting New Security Issues with Apache Struts

Two practical rules. A bulletin appears on the wiki and in the announcements together, so a delay of days between an announcement and the Bookshelf’s upgrade is a window in which the bulletin is public and the application is not patched; the reporting page says that the project takes an active stance against security problems and denial of service attacks and that it cannot promise workarounds for generic problems such as a client streaming a lot of data; its stated philosophy is to avoid attacks that make the server consume resources in a non-linear relationship to the size of the input, which is the kind of fix the 2026 bulletins describe. Second, a release announcement without a bulletin can still be a security release: the announcement of 7.4.0 and 6.12.0 came three days before the bulletins S2-075 to S2-078 were published, and an application that waited for the bulletin gained nothing.

Beyond the Struts Bulletins

Struts runs inside a container, and the container publishes its own security pages. The Tomcat CVEs that touch JSP and the default servlet (CVE-2024-50379 and CVE-2024-56337 for uploads treated as JSP on case-insensitive file systems, CVE-2024-52318 for the XSS in generated JSPs from unreleased pooled tags, CVE-2025-24813 for the partial PUT, CVE-2017-12617 for a JSP upload by PUT and CVE-2020-1938 "Ghostcat" for AJP) are described with their fixed versions in Security, which also lists the verified table of the container side. The Struts 1 record CVE-2014-0114 belongs to the Struts 1 page of this section. The Jackson record CVE-2017-7525 is the one S2-055 points at, and the general rule it teaches is that a Struts bulletin may be a library bulletin with a Struts version number on it.

Pitfalls

Pitfall Why it hurts What to do

Reading only the "Fixed" column

Several bulletins list branches as affected that have no fix (EOL), and a patch release may exist for another branch only

Read the Affected Software ranges against the exact version in the WAR, then the Recommendation

Treating the rating as the severity of the damage

The scale is about exploitability: S2-075 is a code execution class bug rated Moderate because the default allowlist blocks it

Read the Problem and the "not affected" notes, and keep the defaults that provide the mitigation

Upgrading to "latest 7.x" without the release number

S2-070 and S2-071 affect 7.2.1 only

Pin the struts2-bom to the fixed version named by the newest bulletin

Trusting an old fix to be complete

S2-005 after S2-003, S2-061 after S2-059 and S2-062 after S2-061 show that the first fix is sometimes incomplete

Follow the chain of "similar to" bulletins and take the last fixed version

Keeping the old upload mechanism after upgrading

S2-067 says that keeping the old mechanism keeps the application vulnerable; in 7.x the interceptor is removed and the old code silently receives nothing

Migrate to actionFileUpload and UploadedFilesAware

Copying a CVE id from an announcement without opening the record

Ids differ from habits (the 2026 ids are long) and transcription errors create wrong claims

Look up each id on the CVE record service or NVD and compare the title with the bulletin

Staying on 2.5.x with a commercial extension and no plan

The extension is a bridge for a migration, and the project does not endorse it

Schedule the 6.x or 7.x migration and treat the extension as temporary

Switching off the OGNL allowlist to make an old expression work

S2-075 depends on the allowlist being disabled for Struts 7

Add the package to struts.allowlist.packageNames instead

Leaving Config Browser or devMode in production

S2-043 (Low) says that using the Config Browser plugin in production is itself the problem; the security guide says to restrict it and to disable devMode

Remove the plugin from the production WAR and keep struts.devMode=false

Never raising the Enforcer floor

A floor written in 2026 knows nothing about the next bulletin

Update the rule whenever a bulletin names a higher fixed version, and keep a dated note

Source: Struts Security Guide — Restrict access to the Config Browser Plugin

Where the Books and Old Tutorials Are Outdated

Struts 2 in Action (2008, Struts 2.0) and the Struts 1 book Struts in Action (2002) predate almost every bulletin on this page, so the model they teach is the one the bulletins replaced. The statements below describe what that model was and what the bulletins and the 7.4.0 defaults say today.

  • Parameters are bound to every setter that the request names. The 2.0 model relies on the interceptor to filter dangerous names; the bulletins S2-003, S2-005, S2-009, S2-020 and S2-021 are that filter being bypassed or extended. Struts 6.4 and 7 made binding opt-in with the @StrutsParameter annotation (see the parameter injection page of this section).

  • Dynamic Method Invocation and the !, method:, action: and redirect: syntax are normal. S2-016, S2-019, S2-032 and S2-033 turned them into attack surface; DMI is off by default (S2-019) and the 7.4.0 probe above shows the prefixes ignored.

  • %{...} can be used freely in any tag attribute. S2-029, S2-059, S2-061 and S2-062 are the history of why forced evaluation of request data is dangerous; the security guide’s rule is the up-to-date version.

  • The fileUpload interceptor with File, xxxContentType and xxxFileName setters. S2-066 and S2-067 ended it; the 7.x equivalent is the actionFileUpload interceptor.

  • Struts 1 is a supported choice. It has been end-of-life since 5 April 2013, and CVE-2014-0114 names Struts 1.x through 1.3.10; the Struts 1 book is for reading legacy code, not for starting projects.

  • The version of the example is the version to use. The Struts 2.0 and 2.1 versions of that era are inside the affected ranges of S2-003 (2.0.0 to 2.1.8.1) and of every later bulletin that begins at 2.0.0.

  • Security is a chapter, not a build step. A build that fails on a vulnerable dependency, like the Enforcer rule above, is a modern habit that the books do not show.
