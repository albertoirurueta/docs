The reference material consulted while preparing these pages is listed in the section bibliography.

Security in a JSP application is mostly one habit and a handful of settings. The habit is to treat every value that came from outside as text that must be encoded for the place where it is written. The settings keep the pages out of reach of direct requests, remove the dangerous features of the container and make the session and the cookie harder to steal or abuse. The running scenario is the Bookshelf, the small catalogue of books of this section: a search page, a review form, a cover upload and an admin area. Where Untrusted Text Comes From

A JSP page has more inputs than the request parameters it reads. The expression language reads all of them with the same syntax, which is what makes the habit necessary.

Three rules cover almost every defect on this page. Encode on output, for the context in which the value is written, as late as possible. Never turn text into code: no expression, no OGNL (on the Struts side), no script or SQL is built from input. Keep the application away from the places where the container serves files directly. The sections below apply the rules one context at a time.

Cross-Site Scripting and the Expression Language

The expression language writes the value it computes to the response as it is. An expression in template text, ${param.q}, does not escape anything, and neither does an expression in a tag attribute whose handler prints the value unescaped. The search page of the Bookshelf (see the Getting Started page) shows the four ways of writing the same parameter that the page set offers:

search.jsp: the same value, four ways
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="fn" uri="jakarta.tags.functions" %>
<%@ taglib prefix="e" uri="owasp.encoder.jakarta" %>
<p id="raw">Results for: ${param.q}</p>
<p id="cout">Results for: <c:out value="${param.q}"/></p>
<p id="fn">Results for: ${fn:escapeXml(param.q)}</p>
<p id="enc">Results for: <e:forHtml value="${param.q}"/></p>

Requested with q=<b>x</b>&"' (the parameter encoded for the URL), the page answered:

<p id="raw">Results for: <b>x</b>&"'</p>
<p id="cout">Results for: &lt;b&gt;x&lt;/b&gt;&amp;&#034;&#039;</p>
<p id="fn">Results for: &lt;b&gt;x&lt;/b&gt;&amp;&#034;&#039;</p>
<p id="enc">Results for: &lt;b&gt;x&lt;/b&gt;&amp;&#34;&#39;</p>

The first line is a cross-site scripting hole: the markup in the parameter became markup in the page, and a script element would have run. The other three are correct for HTML text and for a quoted HTML attribute. c:out and fn:escapeXml replace exactly the five characters <, >, &, " and ' (by <, >, &, " and '), which is the whole of their job: they are an HTML-body encoder, not a universal one. The OWASP encoder writes numeric references for the quotes (", '), which are the same characters. The details of c:out (the default attribute, escapeXml taking any text as false except "true", reader values) are on the JSTL core page and those of fn:escapeXml on the JSTL functions page; the one fact to take away is that the default of c:out is the safe one, and that only a literal escapeXml="false" on text the page’s own authors control may switch it off.

Which of the four to use is a style choice. c:out is the idiom that reviewers recognise and that a search for "an ${...} that is not inside a tag" finds. ${fn:escapeXml(x)} is convenient inside an attribute value that contains other text. The encoder tags and functions (the next section) are the only ones that also cover the other contexts, so a page that uses them for the other contexts may use them for HTML text as well, to have a single vocabulary.

Source: Jakarta Standard Tag Library 3.0 — 4.2 c:out

Source: Jakarta Standard Tag Library 3.0 — 15.5 fn:escapeXml

Source: OWASP — XSS Prevention Cheat Sheet, Output Encoding for HTML Contexts

The unescaped ${b.title} of the first Bookshelf page of this section (an expression in template text) is the same hole as ${param.q} as soon as a title comes from a form or an import: an expression is only as safe as the text it prints. Encoding for the Context

HTML text is one context. The same value needs a different encoding when it lands in a quoted attribute, in a JavaScript string, in a URL or in CSS, and no single function is right for all of them. The diagram is the decision the page author makes for every dynamic value.

The JavaScript Context

c:out is wrong inside a script block, and the run shows how. With q set to \';alert(1)// (a backslash, a quote and a script fragment) the page produced:

<script nonce="...">
  var query = '\\\x27;ale\x72\x74(1)\/\/';
  var broken = '\&#039;;alert(1)//';
</script>

The first line, from e:forJavaScript, is a harmless string. The second, from c:out, is not safe in JavaScript: an HTML entity means nothing inside a script element, so the value is the text &#039; and the backslash that the attacker supplied escapes the closing quote of the literal, which breaks the page’s script and, in a page with a second injection point, lets the attacker take over the statement. Two more observations from the run. The 1.5.0 encoder writes \x escapes for the letters of the word "script" (c, i, p, r, s, t in either case) as well as for the characters that need it, so alert became ale\x72\x74: the output is valid and equal to the input, only verbose, and it exists so that a value can never spell the end of the script element. And the rule is not "encode, then everything is allowed": the safest design keeps data out of script text altogether. Put the value in a data-* attribute (a quoted HTML attribute, encoded by c:out) and read it with element.dataset, or put a JSON document in a <script type="application/json"> block written with e:forJson (a tag of the library) and parse it. A Content-Security-Policy that forbids inline scripts (see below) then protects the page even if a value is missed.

Source: OWASP — XSS Prevention Cheat Sheet, Output Encoding for JavaScript Contexts

Quoted Attributes, Unquoted Attributes and Whole URLs

An attribute value must be quoted. The HTML attribute encoders are written for a quoted value; the OWASP library has a separate forHtmlUnquotedAttribute because an unquoted value ends at the first space, and a page that leaves out the quotes needs it. The better rule is to quote every attribute and never to use the unquoted form.

The other half of a link is the scheme. A value in href or src that is encoded correctly can still be an attack, because javascript: is a valid URL. The run, with site=javascript:alert(1):

<a id="badsite" href="<c:out value="${param.site}"/>">site</a>
<c:choose>
  <c:when test="${fn:startsWith(param.site, 'https://')}">
    <a id="site" href="<c:out value="${param.site}"/>">site</a>
  </c:when>
  <c:otherwise><span id="site">no link</span></c:otherwise>
</c:choose>
<a id="badsite" href="javascript:alert(1)">site</a>
<span id="site">no link</span>

and with site=https://example.org/?a=1&b="x the second branch printed <a id="site" href="https://example.org/?a=1&amp;b=&#034;x">. The first anchor shows that escaping does not neutralise a scheme; the c:choose shows the allow list (an HTTPS prefix test, case-sensitive, so compare on a lower-cased copy if HTTP in capitals must pass), and that c:out still encodes the value that passed. A value that is a path of the application belongs in c:url instead, which also adds the context path.

Stored Cross-Site Scripting: the Review Page

A value that is stored and shown later is the same defect, with a longer path and a larger audience. The review page prints the book and the text of every review with c:out:

reviews.jsp: reviews written by one user and read by all
<ul>
<c:forEach var="r" items="${reviews}">
  <li><c:out value="${r.book}"/>: <c:out value="${r.text}"/></li>
</c:forEach>
</ul>

A review posted with the text <script>alert(1)</script> was listed as:

<li>Dune: &lt;script&gt;alert(1)&lt;/script&gt;</li>

The encoding happens on output, in the page that knows the context, not on input in the servlet: a value escaped when it is saved is double-encoded the next time it passes through a c:out, and wrong for any other consumer of the same data, such as a JSON endpoint or a PDF. Input validation (a length limit, a character set, a format) is a separate defence that reduces what can be stored. A page that must show formatted user text (reviews with bold and links) cannot use an encoder, because it would show the tags; it needs an HTML sanitizer with an allow list of elements and attributes, run when the text is saved or displayed, and the Content-Security-Policy below as a second line.

Source: OWASP — XSS Prevention Cheat Sheet, HTML Sanitization

Content-Security-Policy and Header Defences

A policy that the browser enforces limits what an injected script can do and, with a nonce, forbids inline scripts that the server did not mark. The Bookshelf sets one for every response with a filter and passes the nonce to the pages through a request attribute:

CspFilter.java: a policy with a per-request nonce
@WebFilter("/*")
public class CspFilter implements Filter {
    private static final SecureRandom RANDOM = new SecureRandom();

    @Override
    public void doFilter(ServletRequest req, ServletResponse resp, FilterChain chain)
            throws IOException, ServletException {
        byte[] bytes = new byte[16];
        RANDOM.nextBytes(bytes);
        String nonce = Base64.getEncoder().encodeToString(bytes);
        req.setAttribute("cspNonce", nonce);
        ((HttpServletResponse) resp).setHeader("Content-Security-Policy",
                "default-src 'self'; script-src 'nonce-" + nonce + "'; object-src 'none'; "
                + "base-uri 'none'; frame-ancestors 'none'");
        chain.doFilter(req, resp);
    }
}

Every script block of a page then carries the nonce, <script nonce="${cspNonce}">, and the response had:

Content-Security-Policy: default-src 'self'; script-src 'nonce-xbVYu1qbsWZOTNUEpa1RBg=='; object-src 'none'; base-uri 'none'; frame-ancestors 'none'
<script nonce="xbVYu1qbsWZOTNUEpa1RBg==">

The nonce is base 64 text from a secure random generator, so printing it without encoding is safe; it must be fresh for every response, because a nonce that repeats is a password that is published. The policy is a defence in depth, never a replacement for encoding.

Tomcat ships a filter for three more headers. Adding it to web.xml is two elements, and no code:

web.xml: Tomcat’s HTTP header security filter
<filter>
    <filter-name>httpHeaderSecurity</filter-name>
    <filter-class>org.apache.catalina.filters.HttpHeaderSecurityFilter</filter-class>
    <async-supported>true</async-supported>
</filter>
<filter-mapping>
    <filter-name>httpHeaderSecurity</filter-name>
    <url-pattern>/*</url-pattern>
</filter-mapping>

and a response of the Bookshelf then carried X-Frame-Options: DENY and X-Content-Type-Options: nosniff. The filter documentation names three protections: HSTS (added only to responses for HTTPS requests), click-jacking protection and content-type sniffing protection; the policy header above is not among them, which is why the application sets it itself. The filter is Tomcat-specific, so a WAR that must run on other containers sets the same headers in a filter of its own.

Source: OWASP — Content Security Policy Cheat Sheet, Defense Against XSS

Source: Apache Tomcat 11 — HTTP Header Security Filter

Expression Language Injection

Encoding protects the output. The second family of defects is about input that becomes code. An expression is a small program: since EL 2.2 it can call methods, and with EL 3.0 the classes of java.lang are imported by default. When text from a request is handed to something that evaluates it as an expression, the attacker writes the program. A value that is only printed is never evaluated again: with q set to ${1+1}, the search page printed ${1+1} (the raw, c:out and fn:escapeXml lines above), because ${param.q} is evaluated once, and its result is a string, not source text.

The defect needs a component that takes a string and parses it. The Bookshelf contains one on purpose, a custom tag that a careless author wrote to "let templates carry expressions":

EvalTag.java: unsafe on purpose, never write this
public class EvalTag extends SimpleTagSupport {
    private String expr;
    public void setExpr(String expr) { this.expr = expr; }

    @Override
    public void doTag() throws JspException, IOException {
        PageContext pc = (PageContext) getJspContext();
        ELContext el = pc.getELContext();
        ExpressionFactory factory = ExpressionFactory.newInstance();
        Object value = factory.createValueExpression(el, expr, Object.class).getValue(el);
        pc.getOut().print(value);
    }
}

Used as <bs:eval expr="${param.q}"/>, the page evaluated the value of the parameter a second time ("double evaluation"). The requests and the responses of the run:

Replacing availableProcessors() with a method that starts a process is the end of the story, which is why the OWASP page on expression language injection rates the impact as high. The same pattern exists in the wild in tag libraries that evaluate a message or a label: that page describes the spring:message tag of Spring versions before 3.0.6, which resolved expressions twice, and states that the pattern must be avoided. The defences:

  • Never pass request text to createValueExpression, ELProcessor.eval or any "evaluate this string" API. If a feature needs user-defined formulas, parse them with a purpose-built, restricted grammar.

  • Do not build an expression from input: ${param.x} as an operand is safe, a string concatenated into "${" + x + "}" is not.

  • Do not let a message, a label or a tag attribute that comes from a database be evaluated. Messages are text for MessageFormat, not for the expression language.

  • Use a static isELIgnored or deferred-syntax-allowed-as-literal only for what they are meant for (compatibility with old pages), not as an injection defence: an attacker’s text reaches the evaluator by a path that has nothing to do with the page’s own template text.

  • Keep tag handlers pure. A handler that reads getJspContext().getELContext() to do its own evaluation is the place where the problem lives; the container already evaluates every attribute of every tag.

The EL configuration and the evaluator API are on the EL configuration and ELProcessor page; the Spring tags and the Struts OGNL equivalent are on the Spring MVC with JSP and ValueStack, ActionContext & OGNL pages of this section, and on the Struts side the same defect has had a long list of severe CVEs.

Scripting Elements Switched Off

A scriptlet is Java code in the page, in the thread of the request, with the full power of the web application. The first defence is to forbid it. One property group in web.xml turns every <% %>, <%! %> and <%= %> of the web application into a translation error:

web.xml: no scripting anywhere
<jsp-config>
    <jsp-property-group>
        <url-pattern>*.jsp</url-pattern>
        <scripting-invalid>true</scripting-invalid>
    </jsp-property-group>
</jsp-config>

A page legacy.jsp that contained <% out.println("scriptlet"); %> failed on the first request with a 500 response (the error valve of the Bookshelf prints no report, see below) and the log said:

org.apache.jasper.JasperException: /WEB-INF/views/legacy.jsp (line: [2], column: [2]) Scripting elements ( <%!, <jsp:declaration, <%=, <jsp:expression, <%, <jsp:scriptlet ) are disallowed here.

The error is a feature: a pull request that adds a scriptlet fails in the first test that renders the page. The property groups, their url-pattern rules and the stricter ScriptFreeTLV validator are described on the configuration page and the scripting elements page, which also shows how to migrate a page away from scriptlets.

Scriptlets are also where the classic server-side vulnerabilities of old JSP books live. Every Page Starts a Session

A JSP takes part in the session by default (session="true" is the default of the page directive), so an anonymous visitor who only reads the search page receives a session cookie. The response header of the Bookshelf’s search page had:

This is a performance and a privacy concern, not a flaw by itself, but it matters for security in two ways: a session id is issued before the user logs in (so the id must change at login, below), and a page that does not need a session should say so with <%@ page session="false" %>. Session Cookies and Fixation

Four lines of web.xml and one Context attribute harden the session cookie. The first three are the servlet specification’s cookie-config; the last is Tomcat’s:

web.xml: the cookie of the session
<session-config>
    <session-timeout>30</session-timeout>
    <cookie-config>
        <http-only>true</http-only>
        <secure>true</secure>
    </cookie-config>
    <tracking-mode>COOKIE</tracking-mode>
</session-config>
META-INF/context.xml: SameSite for every cookie of this web application
<Context>
    <CookieProcessor className="org.apache.tomcat.util.http.Rfc6265CookieProcessor" sameSiteCookies="strict"/>
</Context>

With both in the WAR the cookie of the response above has Secure; HttpOnly; SameSite=Strict. HttpOnly hides it from scripts, so an XSS cannot read the id (it can still act as the user, which is why XSS must not be allowed in the first place); Secure keeps it off plain HTTP; SameSite=Strict keeps it off cross-site requests; and the COOKIE tracking mode prevents the ;jsessionid= suffix on URLs. The Bookshelf scratch application runs on plain HTTP; curl still returned the Secure cookie from its jar for localhost, but a browser on a non-TLS host that is not local does not send it back. SameSite=Strict also means that a link from another site arrives without the cookie, so a user who follows an e-mail link to a logged-in page sees the login page once; Lax allows the cookie on top-level navigations and is the usual compromise. The servlet fundamentals page lists the cookie attributes that the specification itself defines, among them the generic attribute element of cookie-config (the specification’s way of setting SameSite), and the Tomcat-specific CookieProcessor is the alternative that also covers the cookies the application creates itself.

Session fixation is the attack where an attacker obtains a session id and gets the victim to use it, so that the victim’s login authenticates the attacker’s session. The defence is to change the id at the moment of login:

RotateServlet.java: a new id after authentication
@WebServlet("/session/rotate")
public class RotateServlet extends HttpServlet {
    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        HttpSession session = req.getSession();
        String before = session.getId();
        String after = req.changeSessionId();
        resp.setContentType("text/plain;charset=UTF-8");
        resp.getWriter().println("changed: " + !before.equals(after));
    }
}

curl -X POST with the session cookie answered changed: true and the cookie in the jar had a new value. The attributes of the session (the cart, the token) survive the change; only the id differs. Tomcat’s authenticators change the id when a user logs in (the changeSessionIdOnAuthentication option of the authenticator valves, documented with the Tomcat valves); an application that authenticates in its own servlet must call changeSessionId itself.

Cross-Site Request Forgery

A browser attaches the cookie of a site to every request to that site, including a request that a page of another site triggers. A form on a hostile page that posts to the Bookshelf’s review URL would be authenticated as the visitor. The defences, in the order a servlet application should adopt them:

  1. State changes only through POST (or PUT and DELETE), never GET: a link or an image tag can make a GET.

  2. A synchroniser token: a random value stored in the session, written into every form as a hidden field and compared on the server with the submitted one.

  3. SameSite cookies (above), which stop the cookie on cross-site POSTs.

  4. Optionally a check of the Origin or Referer header and Fetch Metadata headers, as a second line.

ReviewServlet.java: create the token on GET and compare in constant time on POST
@Override
protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
    HttpSession session = req.getSession();
    String token = (String) session.getAttribute("csrf");
    if (token == null) {
        byte[] bytes = new byte[32];
        RANDOM.nextBytes(bytes);
        token = Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
        session.setAttribute("csrf", token);
    }
    req.setAttribute("reviews", reviews);
    req.getRequestDispatcher("/WEB-INF/views/reviews.jsp").forward(req, resp);
}

@Override
protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
    HttpSession session = req.getSession(false);
    String expected = session == null ? null : (String) session.getAttribute("csrf");
    String actual = req.getParameter("csrf");
    if (expected == null || actual == null
            || !MessageDigest.isEqual(expected.getBytes(StandardCharsets.UTF_8),
                    actual.getBytes(StandardCharsets.UTF_8))) {
        resp.sendError(HttpServletResponse.SC_FORBIDDEN, "Invalid CSRF token");
        return;
    }
    reviews.add(new Review(req.getParameter("book"), req.getParameter("text")));
    resp.sendRedirect(req.getContextPath() + "/reviews");
}
reviews.jsp: the hidden field
<form method="post" action="${pageContext.request.contextPath}/reviews">
  <input type="hidden" name="csrf" value="<c:out value="${sessionScope.csrf}"/>">
  <input type="text" name="book">
  <input type="text" name="text">
  <button type="submit">Add review</button>
</form>

The redirect after the post is the post/redirect/get pattern, which also prevents a duplicate on reload. The token is 43 characters of URL-safe base 64 for 32 random bytes; MessageDigest.isEqual compares in time that does not depend on how many leading characters match. A JSP page that renders a form must write the token (a tag file that every form uses is the way to not forget it), and a page that is served from a cache must not contain a token. Tomcat also ships a CsrfPreventionFilter that adds tokens to URLs and checks them, and Spring Security and Struts have their own mechanisms; the principle is the same.

File Uploads: Never Into the Web Application

A cover upload is a way for a stranger to put a file on the server, and the CVE list below is mostly the story of what happens when that file ends up where the container can execute or overwrite it. Four rules:

  1. Store outside the web application. An uploaded file in the public tree is a candidate for being executed or served with the wrong content type; one under WEB-INF is not served, but is still inside the deployment, which can be replaced.

  2. Choose the name yourself. A generated name (a UUID) and an extension picked by the server from the validated content type; never the name the client sent, which can contain .. or a path.

  3. Allow-list the type and limit the size. The container enforces the limits that @MultipartConfig declares.

  4. Serve it back through a servlet that sets Content-Type and X-Content-Type-Options: nosniff, not by a static link.

CoverServlet.java: the Bookshelf’s cover upload
@WebServlet("/covers")
@MultipartConfig(maxFileSize = 1_048_576, maxRequestSize = 1_100_000)
public class CoverServlet extends HttpServlet {
    private static final Set<String> ALLOWED = Set.of("image/png", "image/jpeg");
    private final Path storage = Path.of(System.getProperty("java.io.tmpdir"), "bookshelf-covers");

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        Part part = req.getPart("cover");
        if (part == null || !ALLOWED.contains(part.getContentType())) {
            resp.sendError(HttpServletResponse.SC_UNSUPPORTED_MEDIA_TYPE, "Only PNG or JPEG covers");
            return;
        }
        String extension = part.getContentType().equals("image/png") ? ".png" : ".jpg";
        Files.createDirectories(storage);
        Path target = storage.resolve(UUID.randomUUID() + extension);
        try (InputStream in = part.getInputStream()) {
            Files.copy(in, target, StandardCopyOption.REPLACE_EXISTING);
        }
        resp.setContentType("text/plain;charset=UTF-8");
        resp.getWriter().println("stored " + target.getFileName() + " outside the web root");
    }
}

The run, with curl -F: a PNG file answered stored ca1be081-....png outside the web root; a file with the content type application/x-jsp answered 415; a 2 MB file with the type image/png answered 413 (over the 1 MB limit). The content type is a claim of the client, so a production application also checks the file signature (the first bytes) and, for images, decodes and re-encodes the image, which destroys most polyglot files. The file-upload cheat sheet has the full list, and the multipart API is on the Servlet fundamentals page.

Authentication and Authorisation

An application that authenticates in its own servlet, with a table of users and a hand-made "logged in" flag in the session, as the books of the early 2000s did, owns every defect that comes with it: unhashed passwords, a missing session change, no lock-out and a check that some page forgets. The platform’s alternatives are, in the order of preference for a new application, Jakarta Security or Spring Security (see the Spring Security page), or at least the container’s declarative security: a security-constraint names URLs and roles, a login-config the mechanism, and the realm of the server holds the users.

web.xml: the admin area needs a role
<security-constraint>
    <web-resource-collection>
        <web-resource-name>Bookshelf administration</web-resource-name>
        <url-pattern>/admin/*</url-pattern>
    </web-resource-collection>
    <auth-constraint>
        <role-name>bookshelf-admin</role-name>
    </auth-constraint>
</security-constraint>
<login-config>
    <auth-method>BASIC</auth-method>
    <realm-name>Bookshelf</realm-name>
</login-config>
<security-role>
    <role-name>bookshelf-admin</role-name>
</security-role>

An anonymous request for /admin/index.html answered 401 with WWW-Authenticate: Basic realm="Bookshelf", charset=UTF-8. The run did not log in: the shared server has no user for the role and the page never contains a password. The facts to know are those of the Tomcat guide. BASIC and FORM send the user name and the password in clear text, so they are for HTTPS only (combine the constraint with CONFIDENTIAL). The realms do not lock accounts by default, and the MemoryRealm and the UserDatabaseRealm are not for large or changing installations. FORM login is a page of the application that posts to j_security_check. A hashed password store, a per-user salt, and a real identity provider are the production answer. Hand-made login code in a filter (HttpSession attribute user) is still seen; where it exists it must at least call changeSessionId at login, throw the session away at logout and compare secrets in constant time.

The HttpServletRequest methods isUserInRole, getUserPrincipal and getRemoteUser read the container’s identity, so a page can hide a link with ${pageContext.request.isUserInRole('bookshelf-admin')} (hiding a link is cosmetic, the constraint is the enforcement).

Injection Into Queries and Redirects

The output encoders above protect the browser. Two more places take request text and hand it to something that gives it meaning: the database and the Location header. The Bookshelf search of this page reads q from the request and the catalogue page of the MVC with Servlets & JSP page passes it to a repository. If the repository builds the SQL by concatenation, a q of zzz%' OR title LIKE '% closes the string and adds a condition that is always true. With a bound parameter the same text is only a string to look for. The listing is the pair of methods that a scratch run exercised against an in-memory H2 database with two books (Dune and Emma).

Concatenated query versus bound parameter, and a redirect target that stays inside the application
static List<String> concatenated(Connection c, String q) throws SQLException {
    List<String> out = new ArrayList<>();
    try (Statement st = c.createStatement();
         ResultSet rs = st.executeQuery("SELECT title FROM book WHERE title LIKE '%" + q + "%'")) {
        while (rs.next()) out.add(rs.getString(1));
    }
    return out;
}

static List<String> bound(Connection c, String q) throws SQLException {
    List<String> out = new ArrayList<>();
    try (PreparedStatement ps = c.prepareStatement("SELECT title FROM book WHERE title LIKE ?")) {
        ps.setString(1, "%" + q + "%");
        try (ResultSet rs = ps.executeQuery()) {
            while (rs.next()) out.add(rs.getString(1));
        }
    }
    return out;
}

static String safeTarget(String contextPath, String next) {
    if (next == null || !next.startsWith("/") || next.startsWith("//") || next.contains("\\")) {
        return contextPath + "/books";
    }
    try {
        URI u = URI.create(next);
        if (u.getScheme() != null || u.getHost() != null) return contextPath + "/books";
    } catch (IllegalArgumentException e) {
        return contextPath + "/books";
    }
    return contextPath + next;
}

The concatenated query returned every book, including the ones that the search should not have matched; the bound query returned none. A value can be bound, but a column name or a sort direction cannot, which is why the BookService of the MVC page maps the sort parameter through a fixed map and never pastes it into the SQL. The sql:query tags of the JSTL SQL and XML page bind with sql:param, but a query in a view is the wrong place for any of this.
