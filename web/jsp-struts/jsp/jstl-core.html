JSTL Core

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Standard Tag Library 3.0 (API jakarta.servlet.jsp.jstl:jakarta.servlet.jsp.jstl-api 3.0.2, implementation org.glassfish.web:jakarta.servlet.jsp.jstl 3.0.1, the latest release of both), which is part of Jakarta EE 10 and 11, together with Jakarta Pages 4.0, Jakarta Expression Language 6.0 and Jakarta Servlet 6.1, running on Apache Tomcat 11.0.26 and Java 21. Everything was verified on 2026-10-08: the rules against chapters 1 to 5 of the Tags 3.0 specification and the tag documentation (tagdocs) of the core library, and every example by building it into a Maven WAR (context path /g5jstlcore) and running it on Tomcat 11.0.26 with curl; the outputs and error messages shown are the ones that run produced. The Standard Tag Library is the set of tags that page authors use instead of scriptlets: it prints and escapes values, creates and removes scoped variables, makes decisions and catches errors, and (on the pages of this section that follow this one) loops, builds URLs, imports resources, localises and formats text, calls string functions and, in two legacy libraries, queries databases and processes XML. This page covers the whole library at the level of concepts, the five URIs and the conventions every tag obeys, and then the part of the core library that is neither iteration nor URLs: c:out, c:set, c:remove, c:catch, c:if and c:choose. The running scenario is the Bookshelf, a small catalogue of books; the page ends with a book-detail page that uses every tag described here, then the pitfalls, what changed from JSTL 1.0 to 3.0 and where the books in the section bibliography are out of date. Writing ${...} itself, the implicit objects and the operators are on the expression language basics page and the operators and type coercion page of this section; the iteration, URL, internationalisation, formatting, function, SQL and XML tags have a page each.

What the Standard Tag Library Is

A JSP page that wants to show a list, hide a block for guests or format a price needs logic, and the first generation of JSP put that logic in Java scriptlets. The Standard Tag Library (JSTL, "Jakarta Tags" since Jakarta EE 9) is the answer the platform standardised: a few dozen tags and functions with fixed names, attributes and behaviour, available in every container, so that the template stays markup and the logic is expressed with the expression language. The specification states the goal as helping page authors who are not fluent in a programming language, and lists what it offers: general-purpose actions that complement the expression language (display a value, set and remove scoped attributes, catch exceptions), control-flow actions (conditionals and iterators), tag library validators that can forbid scripting, and standard actions and EL functions for URLs, text formatting, internationalisation, SQL, XML and string handling.

It is a specification with several implementations of the same tag handlers, not a Tomcat feature. The API artifact holds the few Java types an application may touch (Config, ConditionalTagSupport, LoopTagSupport, LoopTag, LoopTagStatus, Result, LocalizationContext and the validators); the implementation artifact holds the tag handlers and the TLD files that map a URI to them. Neither is in the JSP container: Tomcat 11.0.26 has no JSTL jar in its lib directory, so the web application packages both, which is the setup the getting started page of this section builds. Eclipse GlassFish and the other full Jakarta EE servers ship their own.

The Bookshelf Used on This Page

The examples need data in scope and a few beans to modify. A ServletContextListener puts the catalogue into application scope, and a filter mapped to *.jsp gives every request a fresh ReaderProfile, an empty map and a StringReader. The pages themselves are plain JSPs in the root of the WAR so that curl can reach them; in the real application of the section they live under WEB-INF/views behind a servlet.

Every plain-text page starts with <%@ page contentType="text/plain;charset=UTF-8" trimDirectiveWhitespaces="true" %>, which leaves out most blank lines but has a side effect worth knowing: trimDirectiveWhitespaces also removes template text that is only white space, so a single space between two ${...} expressions or two tags disappears (${a} ${b} prints ab). The examples therefore separate values with a visible character such as a bar. A name such as nothing that is not defined anywhere evaluates to null.

How a Tag Is Translated, Validated and Run

A tag is not interpreted at request time by looking up its name. The page is translated once, and the translation is where most of the work and most of the errors are:

flowchart LR subgraph T["Translation: once per page change"] d["taglib directive: prefix and URI"] --> r["URI resolved to a TLD in a jar, META-INF/c.tld"] r --> v["attributes checked against the TLD: required, request-time, static"] v --> l["tag library validator JstlCoreTLV checks the page as a whole"] l --> g["Java source calls the tag handler classes"] end subgraph R["Request: every time"] h["handler gets the PageContext and the attributes"] --> e["EL in attributes evaluated"] e --> w["output written to the JspWriter, scoped variables set"] end g --> h

What each step means in practice, in the order Tomcat applies it:

  • The taglib directive binds a prefix to a URI. A URI that no TLD declares is a translation error (the message above). The container finds the TLD in META-INF/*.tld of any jar under WEB-INF/lib; that is the implicit mapping, and no web.xml entry is needed since JSP 2.0.

  • The TLD (for example c.tld, tlib-version 3.0, short-name c) lists every tag with its handler class (org.apache.taglibs.standard.tag.rt.core.OutTag for c:out), its body content type and its attributes with required and rtexprvalue flags. The specification’s "Dynamic" column and the tag documentation’s "Request-time" column are the rtexprvalue flag.

  • Attribute checks happen at translation time: an unknown attribute, a missing required attribute, or an expression in an attribute that does not accept one is an error before anything runs.

  • The validator (org.apache.taglibs.standard.tlv.JstlCoreTLV for the core library) looks at the page as a whole, which is how rules such as the one that requires c:otherwise to be the last child of c:choose can be reported at translation time.

  • The handler runs for every request. It evaluates the EL in its attributes, reads and writes scoped attributes through the PageContext and writes to the current JspWriter.

The tag library specification summarises the error policy in one sentence: syntax errors and constraints on static attributes are reported at translation time, constraints on dynamic attributes at request time. The tags also try to avoid exceptions where a page author could not reasonably handle them: a null where a collection is expected means "do nothing", and a null where a fixed set of values is expected means "use the default". When an exception is raised it is a JspException or a subclass (usually JspTagException), with the original error as its root cause if the tag caught one in its body.

Expressions in Attributes

Almost every attribute of a JSTL tag accepts an expression, written with the syntax of the expression language page. Three things from the specification’s chapter 3 decide how the value reaches the tag.

  • Mixed text and expressions. An attribute may contain several ${...} expressions mixed with literal text; the result is a String.

  • Coercion to the attribute type. The tag declares a type (boolean for test, int for begin, Object for value) and the EL converts to it with the rules of the type-coercion section of the EL specification. null becomes 0 for a number and false for a boolean.

  • Defaults instead of errors. The EL turns many failures into type-correct defaults (a missing property is null, a null operand of + is 0) so that a page degrades instead of throwing.

Scoped Variables: var, scope and Visibility

Every JSTL tag that produces a value exposes it the same way: as a scoped variable, a JSP scoped attribute (an attribute of the PageContext, the request, the session or the application, see the implicit objects and scopes page). No tag creates a Java scripting variable, which is what makes the library usable on pages with scripting disabled. The conventions are fixed by chapter 2 of the specification and are the same in every library.

Table 4. The naming and scoping conventions of the specification
Convention Rule

var

the attribute that names the main exported variable (c:set, c:if, c:catch, c:forEach, fmt:formatDate, …​). It is deliberately not called id, to stress that only a scoped variable, not a scripting variable, is exposed

scope

page, request, session or application, with the meaning of jsp:useBean; the default is page. session is allowed only when the page takes part in a session

varStatus, varReader, …​

secondary variables of a tag are var plus a suffix; c:forEach has var for the item and varStatus for the loop status

static var and scope

both attributes take only literal values (no ${...}), which helps tools and is an error otherwise (previous section)

nested variables

visible only inside the tag body, stored in page scope and removed at the end of the tag; a nested variable has no scope attribute (the var and varStatus of c:forEach)

at-end variables

visible after the tag, with the lifetime of their scope; this is the default (c:set, c:if, fmt:formatNumber, …​)

configuration variables

scoped variables named by the specification that tune the behaviour of a library (locale, bundle, time zone, data source); next section

Some tags read their settings from outside the tag: the formatting locale, the resource bundle, the time zone, the default SQL data source. Observations that are not in the specification’s text but follow from how the tag is built:

c:choose, c:when and c:otherwise: Mutually Exclusive Branches

c:choose is the if / else if / else and switch of the library. It has no attributes of its own; its body holds one or more c:when (each with a test) and at most one c:otherwise, in that order, with only white space between them. The first c:when whose test is true is processed, all others are skipped, and c:otherwise runs only when no c:when did.

flowchart TD start["c:choose entered"] --> w1{"test of the first c:when true?"} w1 -- yes --> b1["process body of first c:when"] w1 -- no --> w2{"test of the next c:when true?"} w2 -- yes --> b2["process body of that c:when"] w2 -- no --> more{"more c:when tags?"} more -- yes --> w2 more -- no --> o{"c:otherwise present?"} o -- yes --> bo["process body of c:otherwise"] o -- no --> none["nothing is written"] b1 --> done["leave c:choose, the other bodies are skipped"] b2 --> done bo --> done none --> done

The semantic difference from several c:if tags is the point of the tag: a c:if always processes its body when its test is true, so two true c:if tags both print, whereas two true c:when tags print only the first one’s body. c:when and c:otherwise are only valid as direct children of c:choose, which is also why a custom conditional tag of an application should expose its result as a variable that a c:when can test (ConditionalTagSupport is the base class the API offers for that).

The tests of later branches are still evaluated

Only the bodies are skipped. The test of a c:when is an attribute, and the container evaluates an attribute expression before it calls the tag, so every c:when of a c:choose has its test evaluated even after an earlier branch matched. A test with a side effect runs, and a test that throws aborts the page although its branch could never have won.

The page below uses every tag of this page. Notes on the page:

  • c:catch as input validation. The only exception the page expects is NumberFormatException from param.id + 0; it turns a bad id into a message and a normal HTTP 200 for the page, where an uncaught exception would be a 500. The better design is a controller servlet that validates the id and answers 400 or 404; the catch keeps the example on one page.

  • c:set for derived values (book, copies, age) so that the expressions are written once and the template reads as a description. The values stay in page scope; nothing leaks to request or session.

  • c:if with var computes canLoan once; the form and any other part of the page that needs it reuse the name.

  • Every user-controlled string goes through c:out: the reader name, the id echoed in the error, the flash message. The numbers (book.year, age) are numbers and need no escaping, so the plain ${book.year} is fine.

  • The flash message is the standard use of c:remove: put a message in the session, show it, remove it with an explicit scope so that nothing else is cleared.

  • State change is a POST with a validated id and a redirect afterwards. The production version also carries a CSRF token, which the servlet fundamentals page demonstrates with a filter.

  • The action uses pageContext.request.contextPath, which is correct for the context path but does not add session rewriting; the URL page of this section covers c:url, which does both.

Security Notes

  • ${...} does not escape; c:out and fn:escapeXml do. Every value that can contain text typed by a user, including a book title read from a database or a request header, belongs in c:out unless it is deliberately markup. Use it in HTML text and in quoted attributes; use an encoder for the other contexts (above).

  • Never switch escaping off with data. escapeXml takes any text, and everything except the word "true" disables it, including a typo, an empty attribute and a null expression. Write escapeXml="false" only on a literal, for text your own code produced, and consider whether it should be a tag file instead.

  • Treat target and property of c:set as code. property must be a literal; a value from the request must be validated and converted before it is stored. target must be an object that the page is allowed to modify: a request or session attribute of the current user, never a shared application-scoped bean or map (a c:set on an application Map changes it for every user and is not thread safe).

  • Do not build an expression from input. A tag attribute such as value="${param.expr}" is safe, because the value is an operand, but passing request text to an API that evaluates it as an expression is EL injection; the library has no such tag, and the spring:eval tag that has is described on the Spring MVC with JSP page of this section.

  • Tags do not make a page safe from scripting. Use the scriptfree validator (or the scripting-invalid property group) to make sure a page that was converted to JSTL stays free of scriptlets; on Tomcat 11.0.26 a page with jakarta.tags.scriptfree declared and one scriptlet fails to translate with Validation error messages from TagLibraryValidator for [scriptfree] …​: JSP page contains 1 scriptlet.

  • JSPs stay under WEB-INF. The examples of this page sit in the context root only so that curl reaches them; a JSP in the public tree can be requested with parameters nobody expected.

  • Keep the jars current. JSTL 3.0.1 has had no release since 2023 and the Tomcat releases carry the security fixes of the container; an application should still follow the Tomcat security pages, for example CVE-2024-52318, "Incorrect JSP tag recycling leads to XSS", fixed in Tomcat 11.0.1 and 10.1.33: it concerns the way the container reuses tag handler instances, which every tag of this library depends on.
