Spring MVC with JSP

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Spring Framework 7.0.9 and Spring Boot 4.1.1, which sit on the Jakarta EE 11 baseline (Servlet 6.1, so Tomcat 11 or Jetty 12.1), together with Jakarta Pages 4.0, Jakarta Expression Language 6.0, Jakarta Tags 3.0 (API 3.0.2, implementation 3.0.1), Hibernate Validator 9.1.4.Final and Java 21. Everything was verified on 2026-10-08: the rules against the Spring Framework reference chapter "JSP and JSTL", the Javadoc of the classes named here, the tag library descriptors spring.tld and spring-form.tld read from the spring-webmvc 7.0.9 jar and the Spring Boot reference, and every example by building it into a Maven WAR (context paths /g7spring, /g7springbean and /g7springboot) and running it on Apache Tomcat 11.0.26 with curl; the outputs and error messages shown are the ones those runs produced. Spring MVC does not render a page itself: a controller returns a view name, a view resolver turns it into a view object, and for JSP the view forwards the request to the JSP container, which is the same RequestDispatcher.forward that a hand-written Model 2 servlet uses (see the servlet fundamentals page). What Spring adds is the controller side (data binding, validation, message sources, URL mapping), a view resolver that finds the page, and two tag libraries that read what the framework put in the request. This page covers that glue: registering the resolver, the JSTL bridge, every tag of the spring: and form: libraries, HTTP method conversion, and Spring Boot’s rules for JSP, which are narrower than the Spring Framework’s. The running scenario is the Bookshelf catalogue, here in a Spring MVC variant of the book list and the book form of the pages before this one. The page ends with a worked example, a pitfalls table, what changed in Spring 6 and 7 and where the books in the section bibliography are out of date. The framework-neutral Model 2 pattern (a servlet controller, JSP views under WEB-INF) is written on the MVC with Servlets & JSP page of this section, the form, validation and session mechanics of plain servlets on the Forms, Validation & Sessions page, the output-escaping contexts on the Security page and the Jasper settings on the Jasper Configuration & Precompilation page; none of them is repeated here.

Status and Where It Runs

JSP is supported by Spring MVC and will keep being supported, but it is not the view technology the Spring team recommends: the Spring Boot reference says "If possible, JSPs should be avoided" and lists FreeMarker, Groovy templates, Thymeleaf and Mustache as the engines it auto-configures. The reasons are in Boot’s JSP Limitations (executable jars cannot serve JSPs, a custom error.jsp does not replace the default error view, the source directory must be the standard one) and are covered in the Spring Boot section below. Where an application already has JSPs, or where a container such as Tomcat is the deployment target anyway, Spring MVC with JSP is a complete and current combination.

The property maven.compiler.parameters passes -parameters to javac. Spring MVC reads controller parameter names from the bytecode, and without that flag a method such as delete(@PathVariable long id) fails at the first request (the pitfalls table shows the message). The Spring Boot parent POM sets the flag itself, which is why the Boot variant below does not need the property.

A form-backing object has to be a JavaBean with a default constructor and setters, because the form tags read and the data binder writes properties by name. The immutable record used for the read-only pages earlier in this section is therefore kept for display and a mutable bean is used for the form.

How a Request Reaches a JSP

sequenceDiagram participant B as Browser participant T as Tomcat connector and filters participant D as DispatcherServlet participant C as BookController participant R as InternalResourceViewResolver participant V as JstlView participant J as Jasper JspServlet B->>T: GET /g7spring/books T->>D: doFilter chain then service D->>C: handler method with Model C-->>D: view name books and model attributes D->>R: resolveViewName books, locale R-->>D: JstlView for /WEB-INF/views/books.jsp D->>V: render model, request, response V->>V: copy model to request attributes, expose locale and MessageSource to JSTL V->>J: RequestDispatcher.forward to /WEB-INF/views/books.jsp J-->>B: HTML written by the compiled page
Figure 1. A Spring MVC request that ends in a JSP: the controller returns a name, the resolver builds the view, the view forwards

The steps are the ones the Spring reference describes for any view technology; only the last three are specific to JSP. JstlView copies the model into request attributes (so ${books} finds the list the controller added) and, before the forward, stores the current Locale and Spring’s MessageSource where JSTL’s fmt: tags look for them. The forward goes through RequestDispatcher, which is why a JSP under WEB-INF is reachable by the controller and not by the browser: a request for /g7spring/WEB-INF/views/books.jsp returns 404 (observed). The container’s own JSP servlet then runs the translation, compilation and request phases described on the lifecycle and translation page, with the request and session scopes of the implicit objects and scopes page.

Participant Role for JSP

DispatcherServlet

The front controller, mapped to / by the initializer below; it is a servlet, so every filter of the filter chain runs before it

Handler (@Controller)

Returns the logical view name and fills the Model; never names a .jsp file

ViewResolver

Maps a logical name to a view; InternalResourceViewResolver prepends the prefix and appends the suffix and always succeeds, which makes it the last resolver in any chain

InternalResourceView / JstlView

Exposes the model as request attributes and forwards to the resource

Jasper

Compiles and runs the page; it knows nothing about Spring

Source: InternalResourceViewResolver Javadoc

View Resolvers

The Spring reference says: "When developing with JSPs, you typically declare an InternalResourceViewResolver bean", that it can dispatch to any servlet resource "but in particular for JSPs", and that "as a best practice, we strongly encourage placing your JSP files in a directory under the WEB-INF directory so there can be no direct access by clients."

registry.jsp()

In the Java configuration the resolver is registered through the ViewResolverRegistry that WebMvcConfigurer hands to configureViewResolvers. The no-argument form registers a JSP resolver with the default view name prefix /WEB-INF/ and the default suffix .jsp; the two-argument form sets both.

WebConfiguration.java
package org.example.bookshelf;

import org.springframework.context.MessageSource;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.support.ResourceBundleMessageSource;
import org.springframework.web.servlet.config.annotation.EnableWebMvc;
import org.springframework.web.servlet.config.annotation.ViewResolverRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
@EnableWebMvc
@ComponentScan("org.example.bookshelf")
public class WebConfiguration implements WebMvcConfigurer {

    @Override
    public void configureViewResolvers(ViewResolverRegistry registry) {
        registry.jsp("/WEB-INF/views/", ".jsp");
    }

    @Bean
    public MessageSource messageSource() {
        ResourceBundleMessageSource source = new ResourceBundleMessageSource();
        source.setBasename("messages");
        source.setDefaultEncoding("UTF-8");
        return source;
    }
}

Source: ViewResolverRegistry.jsp(String, String)

With the shorter registry.jsp() the books page would be looked up at /WEB-INF/books.jsp. The Bookshelf keeps its views in WEB-INF/views, so the first run with the no-argument call produced exactly the failure the defaults predict:

HTTP/1.1 404
JSP file [/WEB-INF/books.jsp] not found

Source: ViewResolverRegistry.jsp()

Calling jsp() more than once registers one resolver per call. Because an InternalResourceViewResolver cannot tell whether a JSP exists without forwarding to it, several JSP resolvers only make sense together with the viewNames property, which says which view names each one handles (for example admin/* under one prefix and everything else under another). The Spring reference chains resolvers with Ordered, and the Javadoc repeats the rule that the internal resource resolver must be last.

Source: Spring Framework — View Resolution

InternalResourceViewResolver as a bean

The registry is shorthand. Declaring the bean yourself gives access to every property of the resolver, such as viewClass, requestContextAttribute and viewNames. The variant below was built as a second WAR with registry.jsp(...) removed.

The same resolver declared as a bean
@Bean
public InternalResourceViewResolver jspViewResolver() {
    InternalResourceViewResolver resolver = new InternalResourceViewResolver();
    resolver.setViewClass(JstlView.class);
    resolver.setPrefix("/WEB-INF/views/");
    resolver.setSuffix(".jsp");
    resolver.setRequestContextAttribute("requestContext");
    return resolver;
}

Source: InternalResourceViewResolver Javadoc

With requestContextAttribute set, every JSP can read a Spring RequestContext; a line ctx=${requestContext.contextPath} locale=${requestContext.locale} in the page printed ctx=/g7springbean locale=en_US. The context object also exposes the message source and the bind status, which the tags below use internally.

The view class for every resolved name

The redirect: and forward: prefixes are handled by the resolver base class, not by the prefix and suffix: a controller that returns redirect:/books produces an HTTP redirect (the Bookshelf’s create and delete methods do, and curl showed 302 with Location: /g7spring/books), and forward:/other forwards to another path inside the application. A view name that starts with either prefix never reaches the JSP folder.

The XML form

The reference still shows the XML namespace form, <mvc:view-resolvers><mvc:jsp/></mvc:view-resolvers> inside a beans element. Spring Framework 7.0 deprecated the whole mvc: XML namespace in favour of the Java configuration: "There are no plans yet for removing it completely, but XML configuration will not be updated to follow the Java configuration model", while the generic bean namespace is not deprecated. New code uses WebMvcConfigurer; the XML form only matters for old applications.

Source: Spring Framework 7.0 Release Notes

Starting the application without web.xml

On Servlet 3.0 and later containers the Spring SpringServletContainerInitializer finds every WebApplicationInitializer, so a class is enough to register the dispatcher servlet and filters; the WAR has no deployment descriptor. This initializer also registers the filter of the HTTP method conversion section.

BookshelfInitializer.java
package org.example.bookshelf;

import jakarta.servlet.Filter;

import org.springframework.web.filter.HiddenHttpMethodFilter;
import org.springframework.web.servlet.support.AbstractAnnotationConfigDispatcherServletInitializer;

public class BookshelfInitializer extends AbstractAnnotationConfigDispatcherServletInitializer {

    @Override
    protected Class<?>[] getRootConfigClasses() {
        return null;
    }

    @Override
    protected Class<?>[] getServletConfigClasses() {
        return new Class<?>[] { WebConfiguration.class };
    }

    @Override
    protected String[] getServletMappings() {
        return new String[] { "/" };
    }

    @Override
    protected Filter[] getServletFilters() {
        return new Filter[] { new HiddenHttpMethodFilter() };
    }
}

Source: Spring Framework — Context Hierarchy and Servlet Container Config

The mapping / makes the dispatcher the default servlet of the application. Tomcat’s own JSP servlet is mapped to *.jsp and *.jspx in the container’s conf/web.xml, and those more specific mappings still win, so a JSP that is requested directly (which only works outside WEB-INF) is served by Jasper, not by Spring. That is one more reason for the WEB-INF rule.

JSP versus JSTL: JstlView

The Spring reference puts it in one sentence: when using the JSP Standard Tag Library you must use a special view class, JstlView, "as JSTL needs some preparation before things such as the I18N features can work". Two things make that preparation unnoticeable in practice: InternalResourceViewResolver selects JstlView by itself when the JSTL API is on the classpath (the Javadoc: "The default is InternalResourceView, or JstlView if the JSTL API is present"), and the bridge uses the same MessageSource as the Spring tags. The page tags.jsp printed the same text through both libraries:

<%@ taglib prefix="fmt" uri="jakarta.tags.fmt" %>
<%@ taglib prefix="spring" uri="http://www.springframework.org/tags" %>

<p>spring:message : <spring:message code="books.title"/></p>
<p>fmt:message    : <fmt:message key="books.title"/></p>
spring:message : Bookshelf catalogue
fmt:message    : Bookshelf catalogue

With Accept-Language: es and a messages_es.properties containing books.title=Catálogo de la Librería both lines printed Catálogo de la Librería, and the count line Showing {0} books became Mostrando 2 libros. No fmt:setBundle and no jakarta.servlet.jsp.jstl.fmt.localizationContext context parameter were involved: the view exposed Spring’s message source and locale to JSTL. The locale itself is chosen by Spring’s LocaleResolver (the Accept-Language header by default), not by the JSTL rules of the JSTL i18n and messages page; an application that mixes fmt:setLocale with Spring’s resolver sees two sources of truth, so one of them should be chosen.

The spring: Tag Library

The library is declared with its URI; the descriptor spring.tld (library version 4.0, short name spring) is inside spring-webmvc-7.0.9.jar, so no taglib mapping in web.xml and no extra dependency are needed.

<%@ taglib prefix="spring" uri="http://www.springframework.org/tags" %>

spring:message, spring:argument and the message codes

The tag resolves code through the application’s MessageSource for the locale chosen by the LocaleResolver. Arguments for the {0} placeholders come from the arguments attribute (several values separated by argumentSeparator, a comma by default) or from nested spring:argument tags; text is used when the code does not exist, and var stores the result instead of printing it. Observed on Tomcat 11.0.26:

<p>missing code   : <spring:message code="no.such.code" text="(default text)"/></p>
<p>with var       : <spring:message var="count" code="book.count" arguments="${books.size()}"/>${count}</p>
<spring:message var="m" code="book.count"><spring:argument value="${book.id}"/></spring:message>
message with argument tag: ${m}
missing code   : (default text)
with var       : Showing 2 books
message with argument tag: Showing 1 books

Source: Spring Framework — tags package description

A code with no message in any bundle and no text fails the page: <spring:message code="zzz.missing"/> produced a JspTagException with the message No message found under code 'zzz.missing' for locale 'en_US'. as the root cause of the JasperException; a default text is the usual protection for codes that are still being written.

spring:url and spring:param

spring:url prepends the context path to a context-relative value (so the page does not hard-code /g7spring), expands {id} templates from spring:param and URL-encodes the values; extra parameters become the query string. The tag is the Spring counterpart of the c:url tag of the URLs, imports and redirects page, with URI-template support.

<p>url relative   : <spring:url value="/books/new"/></p>
<p>url with param : <spring:url value="/books"><spring:param name="q" value="Don Quixote & co"/></spring:url></p>
<p>url template   : <spring:url value="/books/{id}"><spring:param name="id" value="${book.id}"/></spring:url></p>
url relative   : /g7spring/books/new
url with param : /g7spring/books?q=Don%20Quixote%20%26%20co
url template   : /g7spring/books/1

Source: Spring Framework — tags package description

On the very first request of a browser that has no session cookie yet, Tomcat’s URL rewriting appends the session id to every URL that goes through response.encodeURL, and spring:url is one of them: the first response contained /g7spring/books/1;jsessionid= followed by the session id, the second request (with the cookie) did not. The JSTL c:url tag encodes URLs through the same encodeURL call. The cure is a tracking-mode of COOKIE in web.xml or in ServletContext.setSessionTrackingModes; the Boot property server.servlet.session.tracking-modes configures only the embedded server and had no effect in the deployed WAR (;jsessionid was still present).

spring:eval

spring:eval evaluates a SpEL expression against the "standard JSP evaluation context consisting of implicit variables and scoped attributes" (Javadoc), so that book.title.toUpperCase() reads the request attribute book and calls a method.

<p>eval title     : <spring:eval expression="book.title.toUpperCase()"/></p>
<p>eval static    : <spring:eval expression="T(java.lang.Math).max(1,2)"/></p>
eval title     : DON QUIXOTE
eval static    : 2

Source: EvalTag Javadoc

SpEL is a full expression language: it calls methods and constructors, and T(...) reaches any class on the class path. That is the whole of the injection caveat. The expression attribute accepts a runtime expression, so an author can write <spring:eval expression="${param.expr}"/>, which first evaluates the JSP expression ${param.expr} and then evaluates the resulting string as SpEL: a double evaluation. A request to /g7spring/books/tags?expr=T(java.lang.Math).abs(-5) printed 5; the demonstration used a harmless method, but the same request line could name any class and any method the application can load. An empty expr produced the message 'expressionString' must not be null or blank as the root cause of a JasperException. The rule is the one of every expression language: never build an expression from request data, and never pass untrusted text as the expression attribute. The general EL-injection discussion, the OWASP guidance and the Tomcat settings that limit EL belong to the Security page of this section.

The same kind of double evaluation existed in the Spring tags themselves: CVE-2011-2730 (verified as published on cve.org on 2026-10-08) covers Spring Framework before 2.5.6.SEC03, 2.5.7.SR023 and 3.x before 3.0.6, where a container with EL support evaluated the attributes of spring:message, spring:bind, spring:nestedPath, spring:hasBindErrors, spring:theme and spring:transform twice, which let an attacker obtain sensitive information. The vulnerability was fixed long ago and does not affect Spring 7; it is the history behind the warning.

The defaults of the generic tags (spring:message, spring:eval, spring:url, spring:bind) are therefore no escaping, exactly like ${...} on a JSP, unless something turns it on: the attribute on the tag, spring:htmlEscape for the rest of the page (which overrides a defaultHtmlEscape context parameter in web.xml, as the descriptor says) or that context parameter for the whole application. The form tags are different: form:input rendered a title typed as "><script>alert(1)</script> as value=""><script>alert(1)</script>" (observed), because they always escape bound values. The safe habit is the one of plain JSP pages: print data with c:out or ${fn:escapeXml(x)} (see the JSTL core page), and put the defaultHtmlEscape context parameter on, so that a forgotten attribute does not turn a message into markup. spring:escapeBody escapes a block of body text, and javaScriptEscape is for text inside a script string, not a replacement for a JavaScript-context encoder.

form:form, the command object and modelAttribute

form:form renders the form element and "puts the command object in the PageContext so that the command object can be accessed by inner tags". Without a modelAttribute it looks for a model attribute called command; naming the attribute (the reference calls that "definitely a best practice") binds the form to a model attribute of that name. The controller that shows the empty form and the one that handles the submission:

BookController.java
package org.example.bookshelf;

import jakarta.validation.Valid;

import java.util.List;

import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.validation.BindingResult;
import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;

@Controller
@RequestMapping("/books")
public class BookController {

    private final BookRepository repository;

    public BookController(BookRepository repository) {
        this.repository = repository;
    }

    @ModelAttribute("genres")
    public List<String> genres() {
        return List.of("NOVEL", "HORROR", "POETRY");
    }

    @GetMapping
    public String list(Model model) {
        model.addAttribute("books", repository.findAll());
        return "books";
    }

    @GetMapping("/new")
    public String newBook(Model model) {
        model.addAttribute("book", new Book());
        return "book-form";
    }

    @PostMapping
    public String create(@Valid @ModelAttribute("book") Book book, BindingResult result) {
        if (result.hasErrors()) {
            return "book-form";
        }
        repository.save(book);
        return "redirect:/books";
    }

    @DeleteMapping("/{id}")
    public String delete(@PathVariable long id) {
        repository.delete(id);
        return "redirect:/books";
    }
}

Source: Spring Framework — The form tag

The BindingResult parameter must directly follow the @Valid object; without it Spring would throw MethodArgumentNotValidException and the user would see an error page instead of the form with its messages. Returning "book-form" (not a redirect) keeps the model and the binding result in the request, which is exactly what the form tags read. The genres list reaches every view of the controller as a request attribute through @ModelAttribute.

The checkbox and its marker field

HTML does not send an unchecked checkbox, so Spring follows its own convention: for each checkbox the tag also renders a hidden field whose name is the checkbox’s name prefixed by an underscore. The reference says this tells Spring that "the checkbox was visible in the form, and I want my object to which the form data binds to reflect the state of the checkbox, no matter what". Without the marker, un-ticking available would not change the bean.

<input id="available1" name="available" type="checkbox" value="true" checked="checked"/><input type="hidden" name="_available" value="on"/>

Source: Spring Framework — The checkbox tag

The marker value is on in Spring 7.0.9; the reference’s listing shows 1. A client that posts the form by hand (a test script, curl) must include _available=on for the unchecked case, otherwise the field keeps whatever the bean already had: the first POST of this page’s run, without the marker, left available at its default true. The single checkbox works in the three approaches the reference lists (a Boolean property, a collection or array property, any other type compared with value) and always generates the same HTML. form:checkboxes and form:radiobuttons take items as an array, a list or a map (the key is the value and the map value the label); for objects, itemValue and itemLabel name the bean properties.

select, option and options

form:select path="genre" items="${genres}" renders the select with the bound value marked selected="selected"; nesting form:option value="-" label="--Please Select" and form:options items="${countries}" itemValue="code" itemLabel="name" gives a display-only default entry above the data-driven options and produces the same HTML. A map in items uses the keys as values and the map values as labels, and itemValue/itemLabel then apply to the key and the value of the entry. A property bound as an array or collection renders multiple="true" on the select automatically.

form:errors

form:errors renders field errors in a span (the element attribute changes the tag, delimiter separates several messages with <br/> by default). path="*" shows all errors, a field name shows that field’s, and an omitted path shows only the object-level errors:

<form:errors path="*" cssClass="errorBox"/>
<form:errors path="title"/>

Other tags: password, hidden, textarea

form:password renders type="password" and, by default, does not print the bound value; showPassword="true" prints it, which is almost never wanted and which the pitfalls table lists. form:hidden renders a bound hidden field (an unbound hidden value is a plain HTML input). form:textarea takes rows and cols. All three escape the bound value.

HTTP Method Conversion

Browsers submit only GET and POST. For a REST-style URL such as DELETE /books/1 the reference describes the workaround: use JavaScript, or post with the real method as an additional parameter in a hidden field. Spring’s HiddenHttpMethodFilter reads that parameter (named _method by default; the methodParam property of the filter changes it) and wraps the request so that getMethod() returns the real method. The Javadoc is precise about the limits: only PUT, DELETE and PATCH are accepted, and for a multipart POST the filter must run after the multipart processing because it reads a body parameter. The filter is a plain servlet filter, so it works in front of any framework, not just Spring MVC.

The form tag cooperates: <form:form method="delete"> renders a POST form with the hidden field, and the page books.jsp used it for the delete button of every book:

Spring Boot and JSP

Spring Boot supports JSP with narrower promises than Spring Framework, and the Boot reference says so twice. In the section on template engines: Spring MVC "supports a variety of templating technologies, including Thymeleaf, FreeMarker, and JSPs", Boot auto-configures FreeMarker, Groovy, Thymeleaf and Mustache, and "If possible, JSPs should be avoided. There are several known limitations when using them with embedded servlet containers." In the section on embedded servlet containers, under JSP Limitations, the reference lists the facts:

  • with Jetty and Tomcat, JSP "should work if you use war packaging"; an executable war works with java -jar and is also deployable to any standard container;

  • "JSPs are not supported when using an executable jar";

  • a custom error.jsp does not override the default view for error handling, and the reference’s advice is to use custom error pages instead;

  • when the application is started by mvn spring-boot:run or gradle bootRun with a source directory other than the standard src/main/webapp, the environment variable WAR_SOURCE_DIRECTORY tells Boot where the JSPs are.

Source: Spring Boot — JSP Limitations

The consequence is that a Boot application with JSP is a WAR project. Three steps from Boot’s traditional-deployment guide make a WAR that deploys to an external Tomcat and also runs with java -jar: a SpringBootServletInitializer subclass, war packaging, and the embedded container marked provided.

The generic Spring tags do not escape by default, unlike the form tags

What Changed Recently

  • Spring Framework 7.0 and Boot 4.0/4.1: the baseline is Jakarta EE 11 with Servlet 6.1, so Tomcat 11.0 or Jetty 12.1 are the supported containers for a WAR; the release notes say that "applications should be deployed on recent Servlet containers like Tomcat 11+ and Jetty 12.1+". Undertow support was removed because it lacks Servlet 6.1. A Spring 7 WAR is therefore not a target for Tomcat 10.1.

  • The XML namespace mvc: is deprecated in Spring 7.0 in favour of the Java configuration; registry.jsp() is the current form.

  • The spring-form.tld of 7.0.9 has no commandName attribute on form:form; the model attribute is modelAttribute, which the reference chapter uses throughout. Pages that still use commandName must be updated.

  • Themes: the 7.0.9 spring.tld has no spring:theme tag (CVE-2011-2730 above named it in 2011), so a page that used it needs another mechanism, such as a CSS file chosen by the page.

  • spring-jcl removed: logging uses Apache Commons Logging 1.3.0 directly; transparent for a JSP application.

  • JSTL: the API moved to jakarta.servlet.jsp.jstl:jakarta.servlet.jsp.jstl-api 3.0.2 and the taglib URIs to jakarta.tags.*. Pages that still declare http://java.sun.com/jsp/jstl/core (valid in the Spring reference’s own old samples) must change them.

  • Boot: the Boot 4.1.1 build of this page uses spring-boot-starter-webmvc and spring-boot-starter-tomcat (with provided scope for the WAR); check the starter names when moving a project from Boot 3.

  • Jakarta Validation: jakarta.validation.constraints.*, Hibernate Validator 9.1.4.Final; the javax.validation imports of old samples no longer compile.

Source: Spring Framework 7.0 Release Notes

The javax.* to jakarta.* namespace move itself (Servlet 5, Spring 6) is described on the Spring Boot getting started page, and the whole picture of what changed in Jakarta EE and in Struts is on the What’s Changed & Migration page of this section.

Where the Books Are Outdated

None of the four books in the section bibliography teaches Spring MVC with JSP: they were written for the Servlet and JSP containers of 2001 to 2008 and for Struts as the application framework. What they say that conflicts with a Spring MVC application today:

  • Web Development with JavaServer Pages (2001) shows the page-centric and servlet-centric architectures with a hand-written front controller and scriptlets or beans in the page. Spring’s DispatcherServlet is that front controller, the model is a Model and request attributes, and the page contains no Java; the book’s helper classes, jsp:useBean and jsp:getProperty pages are replaced by EL and by the binding tags.

  • JSTL in Action (2002) uses the JSTL 1.0 URIs (http://java.sun.com/jstl/core), the _rt libraries and the fmt tags with a bundle chosen by fmt:setBundle or a context parameter. With Spring the bundle is the MessageSource, exposed by JstlView; the URIs are jakarta.tags.* and no _rt library exists.

  • Struts in Action (2002) and Struts 2 in Action (2008) use their own html: or s: tags to bind a form to an ActionForm or an action. The form: library is Spring’s equivalent, bound to a @ModelAttribute bean with Bean Validation; chapter 9 of the second book, on Spring and JPA, wires Struts actions with Spring 2 XML, ContextLoaderListener and OpenEntityManagerInViewFilter, none of which is the way to render a JSP with Spring MVC today. The Struts-side integration (the Spring plugin) is written on the Spring Integration page of the Struts part.

  • All four books' deployment descriptors are web.xml documents; a Spring MVC WAR in 2026 has none (the WebApplicationInitializer) or generates the equivalent (SpringBootServletInitializer).

When to Choose What

Situation Choice

Existing JSP application, adding Spring for controllers, validation and messages

Spring MVC with registry.jsp(...) and the spring:/form: tags, as on this page; Tomcat 11 WAR

New application that needs a JSP-like view and deploys to a standard servlet container

Still possible, but a template engine (Thymeleaf) avoids the JSP limitations and tests more easily

New Spring Boot application, executable jar

Not JSP: use Thymeleaf, FreeMarker or Mustache; JSPs are not supported in an executable jar

Spring Boot application that must keep its JSPs

war packaging with SpringBootServletInitializer, tomcat-embed-jasper and the provided Tomcat starter

Pure REST backend

No view technology; see the REST APIs page
