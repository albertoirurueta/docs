EL Lambdas, Collections & Streams

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Expression Language 6.0 (API jakarta.el:jakarta.el-api 6.0.1), the version used by Jakarta Pages 4.0 on Tomcat 11.0.26, with Jakarta Standard Tag Library 3.0 and Jakarta Servlet 6.1, on Java 21. Everything was verified on 2026-10-08: the syntax and the semantics against sections 1.20 and 2 of the EL 6.0 specification and the Javadoc, and every example by building it into a Maven WAR and running it on Tomcat 11.0.26 with curl; the outputs shown are the outputs that run produced. Since Expression Language 3.0 (JSR 341, Java EE 7) the language has three features that older JSP material does not know: lambda expressions (an anonymous function written inline), collection literals (a set, a list or a map written inline) and stream operations (filter, map, sorted, reduce and nineteen more, applied to a collection through a pipeline of method calls). Together they let a view answer questions such as "which books under ten euros, cheapest first" or "how many authors are on this shelf" without a scriptlet, without a helper bean and without a tag loop. They also make it easier than ever to put business logic in a view, so the page spends as much time on when not to use them as on how. The running scenario is the Bookshelf, a small catalogue of books: a servlet puts a list of Book records in the request and forwards to a view under WEB-INF, and each example below is a view of that one application. The operators these examples use (lt, ge, and and the conditional operator) are explained on the Operators and Type Coercion page, and the Java equivalents of the same ideas are on the lambdas and method references, streams and collectors and Optional pages.

The Bookshelf Used on This Page

All the examples are views of one WAR, deployed as g4ellambda.war under the context path /g4ellambda, built with the Maven dependencies of the section’s example application (jakarta.servlet-api 6.1.0, jakarta.servlet.jsp-api 4.0.0 and jakarta.el-api 6.0.1 as provided, and the JSTL API 3.0.2 with the GlassFish implementation 3.0.1). A servlet mapped to /view/* puts the catalogue in the request and forwards to /WEB-INF/views/<name>.jsp. The Book record has seven components, because the stream examples need a category, a price and a list of tags to work on.

Book, the record the views read (a record is a bean for EL 6.0 through RecordELResolver)
package org.example.bookshelf;

import java.util.List;

public record Book(long id, String title, String author, int year, String category, double price, List<String> tags) {
}

Source: Jakarta Expression Language 6.0 — RecordELResolver

Catalogue, a bean with two methods that take a lambda (the Java side of the examples in the lambda section)
package org.example.bookshelf;

import jakarta.el.LambdaExpression;
import java.util.List;
import java.util.function.Predicate;

public class Catalogue {
    private final List<Book> books;

    public Catalogue(List<Book> books) {
        this.books = books;
    }

    public List<Book> getBooks() {
        return books;
    }

    /** Receives the lambda as a LambdaExpression and invokes it itself. */
    public List<Book> where(LambdaExpression predicate) {
        return books.stream()
                .filter(b -> Boolean.TRUE.equals(predicate.invoke(b)))
                .toList();
    }

    /** Receives the lambda coerced to a functional interface (EL 5.0 and later). */
    public List<Book> select(Predicate<Book> predicate) {
        return books.stream().filter(predicate).toList();
    }
}

Where These Features Live

The three features are defined in two places of the Expression Language specification, and the split explains several behaviours that surprise people.

Table 1. Where each feature is specified and how it is implemented
Feature Specification How it is implemented

Lambda expression

EL 6.0 section 1.20

part of the language grammar: the parser builds a LambdaExpression object (jakarta.el.LambdaExpression, part of the API) which behaves like a function; invoke evaluates its body

Set, list and map literals

EL 6.0 sections 2.2.1 to 2.2.3

part of the language grammar: evaluated to a java.util.Set, java.util.List or java.util.Map at the moment the expression is evaluated

Stream operations

EL 6.0 sections 2.3.5 to 2.3.26

not part of the language: ordinary method calls on the object stream() returns. The specification says explicitly that the Stream and Optional classes are not part of the API and that the operations can be extended or replaced with customised ELResolver objects

Assignment and sequence (=, ;)

EL 6.0 sections 1.13 and 1.14

part of the language grammar; used below to give a lambda a name

Calling a lambda from Java

EL 6.0 sections 1.25.8 and the LambdaExpression Javadoc

a lambda passed to a Java method is either received as a LambdaExpression or coerced to a functional interface (since EL 5.0)

Source: Jakarta Expression Language 6.0 — 1.20 Lambda Expressions

Source: Jakarta Expression Language 6.0 — 2.1 Overview

In Tomcat 11.0.26 (observed) the stream classes are org.apache.el.stream.Stream and org.apache.el.stream.Optional, and the only resolver involved is the one that answers stream() on a collection or an array (StreamELResolverImpl); every other call on the stream, such as filter(...) or toList(), is an ordinary method call that the BeanELResolver makes on that Stream object. Other containers carry their own implementation (GlassFish uses Expressly, Maven coordinates org.glassfish.expressly:expressly 6.0.0), so the printed class names and the handling of the cases the specification calls "undefined" can differ; the tables and examples on this page are the specified behaviour, and every row marked "observed" is Tomcat’s.

Lambda Expressions

A lambda expression is a ValueExpression with parameters. The syntax is the Java syntax with one difference: the body is not a block or a statement but an EL expression, so there is no return and no { }.

Table 2. Forms of a lambda expression
Form Example Notes

One parameter

x->x+1 or (x)->x+1

the parentheses are optional if and only if there is exactly one parameter

Several parameters

(x,y)->x+y

parentheses and commas required; x,y->x+y is a parse error (observed)

No parameter

()->64

an empty pair of parentheses

Nested

x->y->x+y

a lambda whose body is a lambda; called as f(1)(2)

Method reference

not supported

Block body or return

not supported

the body is a single expression; use the conditional operator ?: and the sequence operator ; for more

Calling a Lambda: Immediately, by Name, or from Java

A lambda can be invoked at once by following it with an argument list, it can be given a name with the assignment operator and invoked through that name, or it can be passed as an argument to a method that invokes it. The assignment form is written name = lambda; name(args): the semicolon operator evaluates its left side, discards the value and returns the right side, and the assignment stores the lambda in a variable. On a JSP page the variable is a page-scope attribute, so it is visible to everything later on the same page (see the scope pitfall below).

x-lambda-basics.jsp: five ways to call or hold a lambda

one parameter:     ${(x->x*2)(21)}
no parameters:     ${(()->64)()}
assigned:          ${add = (x,y)->x+y; add(3,4)}
reads a bean:      ${(b->b.price lt 9)(books[0])}
as a value:        ${(x->x).getClass().name}
Output
immediate:         7
one parameter:     42
no parameters:     64
assigned:          7
reads a bean:      false
as a value:        jakarta.el.LambdaExpression

Source: Jakarta Expression Language 6.0 — 1.13 Assignment Operator

The last line shows what a lambda is at run time: an instance of jakarta.el.LambdaExpression, an ordinary object that can be stored, passed around and invoked. The line "reads a bean" calls a lambda with a Book; a record works as a bean because the RecordELResolver is part of the default resolver chain since EL 6.0.

Recursion, Currying and Functions That Return Functions

Because a lambda is an object and the name it is assigned to is an ordinary variable, the lambda body can refer to its own name (recursion), can return another lambda (currying), and can take a lambda as a parameter (higher-order functions). The specification’s own examples are the factorial and the curried addition.

x-lambda-recursion.jsp: recursion, currying, composition and a function that builds comparators
factorial:    ${fact = n -> n==0 ? 1 : n*fact(n-1); fact(5)}
curried:      ${add = x->y->x+y; add(10)(5)}
composed:     ${inc = x->x+1; inc(inc(1))}
higher order: ${by = f->(p,q)->f(p).compareTo(f(q)); books.stream().sorted(by(b->b.title)).map(b->b.title).toList()}
Output
factorial:    120
curried:      15
composed:     3
higher order: [Cosmos, Dune, Emma, Neuromancer, Pale Blue Dot, The Selfish Gene]

Source: Jakarta Expression Language 6.0 — 1.20 Lambda Expressions

The last line is the specification’s comparing idea (section 2.3.9) made usable: by takes a function f and returns a comparator, so sorted(by(b->b.title)) sorts by title. The inner lambda (p,q)->... still sees f after by has returned, which is why the specification says that the scope of an outer lambda parameter extends to cover the inner body.

Scope, Hiding and Argument Counts

The scope of a lambda parameter is the lambda body. A parameter hides an EL variable or an attribute of the same name and the parameters of enclosing lambdas of the same name. The reverse is a trap: assigning with = creates a page-scope attribute that outlives the expression.

${x = 5; (x->x+1)(10)}
x is still ${x}
${(x->x)(7)}
extra arguments: ${((x)->x)(1,2,3)}
nested: ${[1,2,3].stream().map(a->[a, [10,20].stream().map(b->a*b).toList()]).toList()}
Output
11
x is still 5
7
extra arguments: 1
nested: [[1, [10, 20]], [2, [20, 40]], [3, [30, 60]]]

Source: Jakarta Expression Language 6.0 — 1.20 Lambda Expressions

Line one assigns x = 5 (which creates a page-scope attribute) and then calls a lambda whose own parameter is also called x; the parameter wins inside the lambda and the result is 11. Line two shows that the attribute x is still 5 afterwards, which is why a name assigned in one expression can silently change the meaning of a later one, and why assigned lambdas should get names that nothing else on the page uses. The "extra arguments" line shows a rule of the specification: the number of arguments must be equal to or more than the number of parameters and any extra arguments are ignored. Too few is an error, and so is a second argument list on a lambda that does not return a lambda.

Lambdas Passed to Java Methods

A lambda becomes useful to Java code when it is an argument of a method call. There are two ways for the receiving method to accept it. If the parameter type is jakarta.el.LambdaExpression, the method receives the lambda itself and calls invoke(Object...); this is how the where method of Catalogue above works. Since EL 5.0 (specification section 1.25.8) the lambda can also be coerced to a functional interface, so a method that takes a java.util.function.Predicate or a java.util.Comparator can be called with a lambda and the container produces the interface implementation. The specification says a type counts as a functional interface only if it carries @FunctionalInterface; Tomcat 11.0.26 (observed) also accepts an interface with a single abstract method that does not carry the annotation, so do not rely on the difference.

x-lambda-java.jsp: a lambda as an argument of a bean method, and of methods of java.util.List
where: ${catalogue.where(b->b.year lt 1970).stream().map(b->b.title).toList()}
select: ${catalogue.select(b->b.category == 'science').stream().map(b->b.title).toList()}
removeIf: ${list = [3,1,2]; list.removeIf(n->n gt 1); list}
sort: ${list = [3,1,2]; list.sort((a,b)->a.compareTo(b)); list}
Output
where: [Dune, Emma]
select: [The Selfish Gene, Cosmos, Pale Blue Dot]
removeIf: [1]
sort: [1, 2, 3]

Source: Jakarta Expression Language 6.0 — 1.25.8 Coerce A to functional interface method invocation

where receives a LambdaExpression, select receives a Predicate<Book>, and removeIf and sort are methods of the list that EL calls with a lambda coerced to Predicate and Comparator. These two last calls mutate the list literal, which is legal (see the next section) but is the opposite of what a view should do to a model object. On the list words, which is immutable (List.of), words.sort(...) throws UnsupportedOperationException (observed).

A trap sits in the coerced comparator. The comparator must return an int, and EL arithmetic on integers produces a Long: list.sort((a,b)->a-b) fails with ClassCastException: class java.lang.Long cannot be cast to class java.lang.Integer (observed). Call a.compareTo(b), which returns an Integer, as the listing does. The stream operations are lenient about this (their comparator result is coerced with the EL rules), which is why the arithmetic-difference style works with sorted, but it has its own trap, described under sorting.

Four details of that output matter in practice.

  • A set is a HashSet (observed), so its iteration order is whatever the hash codes give; {1,1,2} has two elements because a set drops duplicates. Do not rely on the order of a set literal; sort it through a stream if the order is part of the output.

  • The braces of a literal collide with the braces that delimit the expression, so a set or map literal at the start of an expression is written ${{1,2,3}}: the outer pair is the EL delimiter and the inner pair is the literal.

  • A map literal supports both access forms of a map: m["two"] and m.two. Keys are expressions, so {1:"x"}[1] uses a number as a key.

  • The literals are mutable ArrayList, HashSet and HashMap objects (observed: l = [1,2]; l.add(3); l is [1, 2, 3]), so a lambda can change them, but they are also fresh objects on every evaluation, so a change does not survive the expression unless the literal was assigned to a name.

A literal also works wherever EL is accepted, including tag attributes, which makes the items attribute of c:forEach easy to feed without a bean:

x-literals-use.jsp (contentType text/html): a list and a map literal as the items of c:forEach
<c:forEach var="t" items="${['alpha','beta','gamma']}">[${t}]</c:forEach>
<c:forEach var="e" items="${{'a':1,'b':2}.entrySet()}">${e.key}=${e.value};</c:forEach>
Output
[alpha][beta][gamma]
a=1;b=2;

The map iterates as Map.Entry objects, so e.key and e.value read each entry. A literal can also be passed to a function such as fn:length, and combined with the empty operator (empty [] is true).

Streams and Pipelines

The collection operations are method calls on a stream of the collection’s elements. The model is the Java 8 model with a smaller scope: a pipeline has a source, zero or more intermediate operations (each returns another stream) and exactly one terminal operation (it does not return a stream). Nothing runs until the terminal operation starts.

Getting a Stream

stream() is available on any java.util.Collection and on a Java array. A Map has no stream(); its collection views (entrySet(), values(), keySet()) do. The listing runs stream() on a list, a primitive array, a String array, the paramValues implicit object (an array of strings per parameter name), a list literal, a set literal and the three views of a map literal. The view is requested as /g4ellambda/view/x-sources?tag=a&tag=b.

{"a":1}.stream() fails with MethodNotFoundException: Method not found: class java.util.HashMap.stream() (observed). A stream of numbers made from a Java primitive array (sizes above) has Object elements as far as EL is concerned: EL deals with objects and does not track generic types, and there are no IntStream or mapToInt.

The Rules of a Pipeline

The specification imposes five rules that the container does not enforce:

  • the operations must not modify the source collection, and the source must not be modified externally while the pipeline runs;

  • the behaviour is undefined if the collection contains null elements, so remove them first with a filter;

  • a stream that has already started cannot be used in another pipeline;

  • any null argument raises a NullPointerException;

  • the operations are specified on Object, and generic types do not exist at run time.

Source: Jakarta Expression Language 6.0 — 2.3.1 Streams and Pipelines

Laziness and Order of Evaluation

Intermediate operations are lazy: filter does not build a filtered collection, it passes on one element at a time. The one exception named by the specification is sorted, which must see all elements before it can yield the first. The listing makes the order visible with peek, which calls a function on each element as it flows past; the function appends to the request attribute sink, a list the servlet prepared. (Mutating a model object from a view is only acceptable in a demonstration.)

x-lazy.jsp: elements flow one by one through the pipeline
${[1,2,3,4,5].stream().peek(i->sink.add('before '.concat(i))).filter(i-> i%2 == 0).peek(i->sink.add('after '.concat(i))).toList()}
${sink}
Output
[2, 4]
[before 1, before 2, after 2, before 3, before 4, after 4, before 5]

Source: Jakarta Expression Language 6.0 — 2.3.11 peek

The trace shows each element going through the first peek, then the filter, and the even ones through the second peek, before the next element starts. No intermediate collection is built. A limit after the filter ends the work early; the peek before it then sees only the elements that were needed (verified separately: with limit(2) over [1..6] filtered to values above 1, only the elements 1, 2 and 3 were visited).

A Stream Cannot Be Reused

A stream is a one-shot view. The specification calls a second use undefined; Tomcat does not complain, it quietly returns the answer for an exhausted stream.

x-reuse.jsp: the same stream counted twice, and two fresh streams
${s = books.stream(); s.count() + s.count()}
${books.stream().count() + books.stream().count()}
Output
6
12

Source: Jakarta Expression Language 6.0 — 2.3.1 Streams and Pipelines

The first line is 6 where 12 is expected, because the second count() runs on a consumed stream. The fix is to call stream() again for every pipeline, as on the second line, or to keep the result list (toList()) and not the stream.

sorted, limit and substream

sorted() uses the natural order and needs Comparable elements; sorted(comparator) takes a lambda of two arguments. The specification warns that an element type that does not implement Comparable makes the no-argument form undefined; Tomcat throws ELException caused by ClassCastException: class org.example.bookshelf.Book cannot be cast to class java.lang.Comparable (observed), and a null element gives an ELException caused by a NullPointerException. limit(n) keeps the first n elements. substream(start) and substream(start, end) skip the first start elements and then take the rest or the elements up to end exclusive; it is the EL name for skip, and with limit it is how paging is written.

Reading the output: "by length" is the specification’s own example of a comparator that falls back to alphabetical order for words of equal length; "by price" sorts ascending by Double.compareTo and keeps the three cheapest; the three limit calls show zero giving an empty list, a count larger than the stream giving everything and a negative count giving an empty list; "out of range" shows a start beyond the end giving an empty list and a negative start skipping nothing; "a page" is page two of a page size of two (elements at positions 2 and 3).

Two traps are specific to comparators.

  1. A comparator built with subtraction truncates decimals. The comparator result is coerced to an int, so with prices 1.5, 1.2 and 1.0 the differences are 0.3 and 0.2, which become 0 and the list is returned unsorted (observed: [1.5,1.2,1.0].stream().sorted((a,b)->a-b).toList() prints [1.5, 1.2, 1.0]). Use a.compareTo(b) for decimals; the subtraction form is safe only for integers, as in the by-year line above.

  2. A one-parameter lambda is not a comparator. The specification’s own examples for sorted and limit pass p->p.unitPrice (a key extractor in the style of Java’s Comparator.comparing), which EL does not have. On Tomcat the call does not fail: the lambda is called with two arguments, the extra one is ignored and the returned price is read as a comparison result, so the order is arbitrary (observed: books.stream().sorted(p->p.price).limit(1).map(b->b.title).toList() printed [Dune], the first book in the catalogue, not the cheapest). Write the comparator with two parameters, or build comparing as in the recursion section.

peek

peek passes every element on unchanged and calls a function on each, as the laziness listing showed. The specification describes its purpose as debugging. In a JSP there is no print function (the specification’s example assumes one; the call print(i) fails with Function [:print] not found, observed), so the listings call sink.add instead; in a real page, prefer no side effect at all.

The page stays readable because each pipeline fits on a line and does one job. When a view needs more than that, say two nested pipelines per row and a third for a total, the grouping belongs in the controller or in a bean method that returns the report rows; the view then iterates a list of rows and nothing else. What Changed Recently

Table 9. Changes that touch lambdas, literals and streams
Version Change

EL 3.0 (JSR 341, Java EE 7)

the first version that was an independent specification; introduced lambda expressions, collection construction and the stream operations of this page, together with the assignment, semicolon and string concatenation operators and static field and method access. Before it, EL 2.2 had method calls (JSP 2.2) but no inline functions

EL 4.0 (Jakarta EE 9)

the namespace changes from javax.el to jakarta.el; a lambda written for EL 3.0 still works after the package rename

EL 5.0 (Jakarta EE 10)

a LambdaExpression can be coerced to a functional interface method invocation (the spec’s change item #45, section 1.25.8), so a lambda can be passed where a Predicate or Comparator is expected; array coercion; BeanELResolver considers default methods; generics throughout the API; minimum Java 11

EL 6.0 (Jakarta EE 11)

minimum Java 17; the java.beans dependency becomes optional; length property for arrays (so words.stream().toArray().length works); RecordELResolver enabled by default (so a record is a bean inside a lambda); opt-in OptionalELResolver; SecurityManager references removed. The stream operations and lambda syntax are unchanged

EL 6.1 (Jakarta EE 12, under development)

the plan on the specification page lists an Elvis operator and + to merge collections among the language enhancements, plus pluggable caching and a performance optimisation for scoped attributes in cooperation with Pages 4.1; no removals planned; minimum Java 17. These are plans, not released behaviour; Tomcat 12 is not released

Where the Books Are Outdated

None of the books in this section knows these features. Web Development with JavaServer Pages (2nd edition, 2002) is written for JSP 1.2, which has no expression language at all, and JSTL in Action (2003) teaches the JSTL 1.0 expression language, which was a small language of property access, comparison, arithmetic and empty, available only inside JSTL tag attributes. Both the lambdas and the streams of this page arrived eleven years later.
