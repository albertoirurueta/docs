Expression Language Basics

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Expression Language 6.0, Jakarta Pages 4.0 (chapter 2, "Expression Language"), Jakarta Standard Tag Library 3.0 (chapter 3, "Expression Language Overview") and Jakarta Servlet 6.1, running on Apache Tomcat 11.0.26 and Java 21. Everything was verified on 2026-10-08: the facts against the three specifications and the Javadoc, and every example by building it into a Maven WAR and running it on Tomcat 11.0.26 with curl; the outputs and error messages shown are the ones that run produced. The Expression Language (EL) is the small language that lives between the ${ and } of a JSP page. It reads data that a servlet or a tag left in a scope, walks into beans, maps, lists and arrays, compares and calculates, and turns the result into text. Since JSP 2.0 it is the normal way to read data in a view, and scriptlets are legacy. It is also the part of JSP most often misused: an unknown name prints nothing instead of failing, a missing property fails with a stack trace, #{} is not an alias for ${}, and nothing in it escapes HTML. This page is the foundation for the other Expression Language pages of this section: it covers the two delimiters, where an expression may appear, how data is reached, what happens when it is missing, and how the container decides which object answers a lookup. Operators and type coercion, lambdas and streams, static access, records and Optional, and standalone use with ELProcessor each have their own page. The running scenario is the Bookshelf, a small catalogue of books; the scopes and implicit objects that EL reads are explained on the Implicit Objects & Scopes page, and the servlet that fills them on the Servlet Fundamentals page.

What the Expression Language Is

EL is an independent specification (Jakarta Expression Language 6.0, part of Jakarta EE 11) that Jakarta Pages, Jakarta Tags (JSTL), Jakarta Faces and Jakarta Servlet applications all embed. The specification describes it as a language for the presentation layer: a simple syntax restricted to the evaluation of expressions, variables and nested properties, relational, logical, arithmetic, conditional and empty operators, functions implemented as static methods, and lenient semantics in which defaults and conversions keep errors away from the reader of the page. Around the language it defines a pluggable API (ELResolver, ELContext, ExpressionFactory, ValueExpression, MethodExpression) that the container implements. Status: current and stable, shipped with Tomcat 11.0.26 and Jakarta EE 11; the 6.1 version is in development (milestone 6.1.0-M2).

Jakarta Pages adds three things on top of the language. It defines where an expression may be written (template text and attribute values, chapter 2 of the Pages specification), which objects are visible to it (the implicit objects and the four scopes), and which resolvers answer a lookup (section 2.10). It also keeps three switches in the configuration (isELIgnored, errorOnELNotFound, deferredSyntaxAllowedAsLiteral), which the Configuration and Property Groups page describes.

Two Delimiters: Immediate and Deferred Evaluation

An EL expression is written between ${ and } or between #{ and }. The language itself parses and evaluates both in exactly the same way; the difference is a convention of the technology that embeds the language. In the Jakarta EE web tier ${expr} means immediate evaluation and #{expr} means deferred evaluation:

  • an immediate expression is compiled when the page is compiled and executed when the page runs, once, at the place where it is written, and the result is what the attribute or the text receives;

  • a deferred expression is parsed but not run: the tag handler receives the expression object (jakarta.el.ValueExpression or jakarta.el.MethodExpression) and decides when, and how often, to evaluate it. Jakarta Faces is the classic user, because a form field needs the expression both to read the value now and to write it later.

JSP template text only ever uses the immediate form. The deferred form belongs to tag attributes, and the specification states the rules as a table. The number of places is small, but each of them fails differently, so the rules are worth seeing run.

Immediate Reads Now, Deferred Reads Later

The table says when an expression is evaluated, not what that means. The next tag shows it. It receives the same request attribute twice, once as a dynamic attribute written with ${} and once as a deferred attribute written with #{}, and between the two it changes the attribute.

WEB-INF/tags/lazy.tag, changes the attribute and then prints both attributes
<%@ tag body-content="empty" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ attribute name="value" required="true" deferredValue="true" rtexprvalue="false" deferredValueType="java.lang.String" %>
<%@ attribute name="now" required="true" %>
<c:set var="when" value="after" scope="request"/>
deferred=[${value}] immediate=[${now}]
lazy.jsp, taglib directives left out
<c:set var="when" value="before" scope="request"/>
<x:lazy value="#{when}" now="${when}"/>
Output
deferred=[after] immediate=[before]

The immediate expression was evaluated when the page passed the attribute, so it holds the value from before the tag ran. The deferred expression was evaluated by the tag, at the moment the tag file used ${value}, so it sees the value after the change. In a tag file the deferred attribute is consumed as ${value} (Tomcat evaluates it there); a Java tag handler receives the ValueExpression itself and calls getValue with its ELContext, which is how Faces components and any custom tag that wants late binding work.

What the Page Author Must Remember About Mixing

  • A composite expression mixing the two delimiters in one attribute value is illegal. Tomcat reports Cannot use both ${} and #{} EL expressions in the same attribute value for def="${book.title} #{book.year}" (observed). The specification gives the reason: a developer must not believe that the delimiter chooses when each part is evaluated.

  • A nested expression such as ${books[${param.i}].title} is illegal. Tomcat reports Failed to parse the expression [${books[${param.i}].title}] (observed). The index needs no inner expression: ${books[param.i].title}.

  • A deferred attribute that is also dynamic needs care. A tag-file attribute written with deferredValue="true" and the default rtexprvalue (true) is handled by Tomcat 11.0.26 as a deferred attribute only: #{...} works, while ${...} and a plain literal fail at run time with ClassCastException: class java.lang.String cannot be cast to class jakarta.el.ValueExpression (observed). Section 2.3.5 of the specification describes such an attribute as accepting all three, with a setter of type Object, so write rtexprvalue="false" (as above) unless a Java tag handler needs both.

Writing a Literal #{ or ${

Since JSP 2.1 the character sequence #{ is reserved. A page that merely contains it in template text is not a page that prints it: it is a translation error, and ${ in a page that was written before JSP 2.0 is evaluated. Three ways out exist, in order of preference: escape it, quote it, or switch the interpretation off.

hashesc.jsp, escaping the two delimiters
escaped: \#{book.title} and \${book.title}
dollar-quoted: ${'${'}book.title}
Output
escaped: #{book.title} and ${book.title}
dollar-quoted: ${book.title}
hashlit.jsp, a page that allows #{ as plain text (the page directive is shown)
<%@ page contentType="text/plain;charset=UTF-8" deferredSyntaxAllowedAsLiteral="true" %>
literal hash: #{not evaluated} and ${book.title}
Output
literal hash: #{not evaluated} and Dune
ignored.jsp, a page that switches EL off altogether
<%@ page contentType="text/plain;charset=UTF-8" isELIgnored="true" %>
ignored: ${book.title} #{book.title}
Output
ignored: ${book.title} #{book.title}

The quoting form ${'${'}book.title} comes from the language specification (a string literal inside an expression); the backslash form \${ and \#{ is the escape that the specification also defines for literal text, and it is the one to use in a page. The language specification adds that other technologies embedding EL may not integrate literal expressions at all, and that JSP then defines its own escaping; the three lines above are what Tomcat 11.0.26 does. A template-text #{...} that is not escaped fails with the message already quoted, for example for Title: #{book.title} in a page (observed):

org.apache.jasper.JasperException: /WEB-INF/views/el/dtext.jsp (line: [4], column: [9]) #{...} is not allowed in template text

Which form to use is a question of how much of the page is affected. A single literal uses the backslash. A page full of text from another template language (a JavaScript template literal, for instance, see below) is a candidate for deferredSyntaxAllowedAsLiteral or for isELIgnored, and a whole directory of old pages is a candidate for the jsp-property-group elements of the same names. Both switches, their defaults and the page-versus-group precedence are on the Configuration and Property Groups page, and the Expression Language Configuration page of this section covers the deferred syntax further.

EL in Template Text

Anywhere that plain text is allowed in a page, in the body of a standard or custom action or outside any action, ${expr} is evaluated by the container when the response is rendered. The result is converted to a String by the EL coercion rules and inserted into the current output, with the same semantics as a Java expression (section 2.2 of the Pages specification). Only ${} is allowed here. An expression may appear several times in a text, and an attribute value may mix text and expressions: the specification calls this a composite expression. The parts are evaluated from left to right, each converted to a String, and concatenated with the text between them.

template.jsp, the same data in template text, in a composite attribute and escaped
template text : ${book.title} by ${book.author} (${book.year})
composite     : <c:out value="Price of ${book.title} is ${book.year}"/>
attribute     : <c:out value="${book.title}"/>
escaped       : \${book.title} | ${'${'}book.title}
quotes        : ${'it\'s'} | ${"say \"hi\""} | ${'say "hi"'}
Output
template text : Dune by Frank Herbert (1965)
composite     : Price of Dune is 1965
attribute     : Dune
escaped       : ${book.title} | ${book.title}
quotes        : it's | say "hi" | say "hi"

Source: Jakarta Expression Language 6.0 — 1.2.3 Composite expressions

Source: Jakarta Expression Language 6.0 — 1.3 Literals

The fifth line shows the rules for string literals, which are the same as in the language specification. A string is enclosed in single or double quotes; the backslash must be escaped as \\; the enclosing quote must be escaped, and the other quote may be; and no other escape sequence exists, so \n is not a newline in EL. There are literals for true, false, integers, floating-point numbers, strings and null.

A few more consequences of being evaluated as a String are worth knowing, and the next view shows them.

nonstr.jsp, expressions that are not text
object (toString) : ${book}
number            : ${book.year + 1}
missing parameter : ${param.start + 10}
boolean           : ${book.year gt 1900 and not empty book.title}
Output
object (toString) : Book[id=1, title=Dune, author=Frank Herbert, year=1965]
number            : 1966
missing parameter : 10
boolean           : true

Source: Jakarta Expression Language 6.0 — 1.2.1.1 Eval-expressions as value expressions

An object is printed through its toString, which for the record Book shows every component. A number is printed without any formatting (no grouping, no locale); output that needs formatting goes through the JSTL fmt library. A parameter that is not present is null, and null in arithmetic is 0, which is why ${param.start + 10} printed 10. The operators and the coercion rules are on the Operators and Type Coercion page of this section.

Template Text That Is Not Really Template Text

The container does not know what language the surrounding text is written in. Three places catch pages out, and one view shows all of them.

comments.jsp, three kinds of comment or script around EL
<%-- JSP comment: ${book.title} never reaches the client --%>
<!-- HTML comment: ${book.title} is evaluated and sent -->
<script>
const evaluated = `Hello ${book.title}`;
const kept = `Hello \${name}`;
</script>
Output
<!-- HTML comment: Dune is evaluated and sent -->
<script>
const evaluated = `Hello Dune`;
const kept = `Hello ${name}`;
</script>

A JSP comment disappears at translation time, so nothing inside it is evaluated and nothing is sent. An HTML comment is ordinary template text: the expression is evaluated, and its value is sent to every visitor, including data the page author thought was hidden. And a JavaScript template literal uses the same ${...} as EL, so the container tries to evaluate it: the first literal was filled in with the book title on the server, and the second needed the backslash to reach the browser untouched. A page with much client-side script is better served by moving the script to a static file.

Source: Jakarta Pages 4.0 — 2.2 Expressions and Template Text

<%-- raw.tag --%>

<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<jsp:doBody var="body" scope="page"/>
body=[<c:out value="${body}"/>]

<%-- tagdep.jsp --%>
<x:raw>Title: ${book.title}</x:raw>
Output

EL in Attribute Values

Any attribute of a standard or custom action that accepts a run-time expression value accepts an EL expression. The value is parsed by ExpressionFactory.createValueExpression with the expected type from the TLD, evaluated immediately, coerced to that type and handed to the tag. The JSTL specification shows the typical uses: a condition in c:if, text that mixes literals and expressions in c:out, and numeric attributes such as begin and end in c:forEach that receive an Integer or even a request parameter.

jstl.jsp, EL in the attributes of three JSTL tags (the taglib directive is left out)
<c:if test="${book.year lt 1970}">${book.title} is a classic | </c:if><c:forEach var="b" items="${books}" begin="${param.start}" end="${param.start + 1}">${b.title}; </c:forEach>| <c:out value="${reader.address.city}" default="no address on file"/>
Output of curl "http://localhost:18080/g4elbasics/view/jstl?start=1"
Dune is a classic | Neuromancer; Solaris; | no address on file

Three things happened. The condition was a boolean expression, and lt is the word form of < that avoids entity references in XML syntax. begin="${param.start}" received the string 1 from the request and the tag received an int: the container coerced the value to the attribute’s type, and ${param.start + 10} earlier showed the same rule for arithmetic. And c:out supplied its own default when its expression evaluated to null, because reader has no address. A request parameter is user input, so start=abc would fail with ELException: Cannot convert [abc] of type [class java.lang.String] to [int] (observed; see the pitfalls).

The chain handles a request for an identifier, and the language adds three things around it (section 1.5.1). Watching the Chain Work

A resolver registered with JspApplicationContext.addELResolver sits second in the chain, behind the implicit objects, so it is asked for everything the implicit objects do not answer. The next resolver exploits that. It logs only for requests that carry a request attribute named trace, which the example servlet sets for the views whose name starts with trace, so every other page is unaffected. It resolves nothing, so every lookup continues down the chain, and it records each question it hears in the container log. Because it reports the base type and the property, the log lists the lookups in the order the chain receives them.

public class TraceResolver extends ELResolver {
    private final ServletContext ctx;

    public TraceResolver(ServletContext ctx) { this.ctx = ctx; }

    @Override
    public Object getValue(ELContext context, Object base, Object property) {
        JspContext jc = (JspContext) context.getContext(JspContext.class);
        if (jc instanceof PageContext pc && pc.getRequest().getAttribute("trace") != null) {
            ctx.log("ELTRACE base=" + (base == null ? "null" : base.getClass().getSimpleName())
                    + " property=" + property);
        }
        return null;   // propertyResolved is not set: the next resolver is asked
    }

    @Override public Class<?> getType(ELContext c, Object base, Object p) { return null; }
    @Override public void setValue(ELContext c, Object base, Object p, Object v) { }
    @Override public boolean isReadOnly(ELContext c, Object base, Object p) { return true; }
    @Override public Class<?> getCommonPropertyType(ELContext c, Object base) { return null; }
}

The Bookshelf Worked Example: A Search Page

The Bookshelf gets a search page. It reads the search term, a list of tags, the preferred language and a theme cookie from the request, reads the shelf name from web.xml, filters a list and builds a link per hit. It uses almost every part of this page: implicit objects, the dot and the bracket, a composite expression, a conditional, empty, defaults, and output escaping. It declares session="false" because nothing here needs a session, and it reads a single index (books[param.first]) to show where user input becomes an error.

search.jsp, the whole page
<%@ page contentType="text/html;charset=UTF-8" session="false" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="fn" uri="jakarta.tags.functions" %>
<h1>${initParam.shelfName}</h1>
<c:choose>
  <c:when test="${empty param.q}"><p>Type a title to search.</p></c:when>
  <c:otherwise>
    <p>Results for <b><c:out value="${param.q}"/></b> (${fn:length(books)} books on the shelf)</p>
    <ul>
    <c:forEach var="b" items="${books}">
      <c:if test="${fn:containsIgnoreCase(b.title, param.q)}">
        <c:url var="link" value="/view/search"><c:param name="q" value="${b.title}"/></c:url>
        <li class="${b.year lt 1970 ? 'classic' : 'modern'}">
          <a href="${fn:escapeXml(link)}"><c:out value="${b.title}"/></a>
          by <c:out value="${b.author}"/> (${b.year})
        </li>
      </c:if>
    </c:forEach>
    </ul>
  </c:otherwise>
</c:choose>
<p>Tags: <c:forEach var="t" items="${paramValues.tag}" varStatus="s"><c:out value="${t}"/>${s.last ? '' : ', '}</c:forEach>
 | Language: <c:out value="${header['accept-language']}" default="none"/>
 | Theme: <c:out value="${cookie.theme.value}" default="light"/>
 | Page size: <c:out value="${param.size}" default="10"/> | First: <c:out value="${books[param.first].title}"/></p>

What the run shows. Every parameter, header and cookie is read with the implicit objects and has a default where it is optional: c:out supplies none, light and 10, and empty param.q chooses the branch without a null check. The class attribute used a conditional on the number year and a literal, so it needed no escaping, while every param, header, cookie and book field that is text went through c:out or fn:escapeXml; the hostile search term was printed as <script> and found no book. The link was built by c:url with c:param, so the title is URL-encoded and the context path is added, and the whole URL is then escaped as an attribute value. ${b.year lt 1970} and the word form lt in the condition is also the one to use in a JSP document in XML syntax, where < is not allowed in attribute values. And the last request shows the limit of EL’s leniency: first=x is not a number, so the [] operator cannot coerce it, and the whole page fails with HTTP 500 and a NumberFormatException. A value like this has to be validated by the servlet before the page runs, which is why a form handler belongs in a controller (the Servlet Fundamentals page). The page does not have jsp:useBean or a scriptlet anywhere, and all the data came from the servlet.

Inconsistencies Found in the Official Text

Three small errors in the official material are worth knowing when the text and the container disagree.

  • Section 2.3.4 of the Pages 4.0 specification points to "section 1.23, Type Conversion" of the EL 6.0 specification. In EL 6.0 type conversion is section 1.25, and 1.23 is java.util.Optional.

  • Section 2.10 of the Pages specification calls the static-field resolver jakarta.el.StaticFieldResolver. The class in the 6.0 Javadoc, and in Tomcat, is jakarta.el.StaticFieldELResolver.

  • The Expression Language specification, section 1.2.2, shows #{'#{'}exprB} as a way to write a literal #{. That is a composite expression of the language, but in a JSP page #{'#{'}book.title} in template text fails at translation with #{...} is not allowed in template text (observed); the escape that works is \#{.
