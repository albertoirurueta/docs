EL Operators & Type Coercion

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Expression Language 6.0 (Jakarta EE 11), Jakarta Pages 4.0, Jakarta Standard Tag Library 3.0 and Jakarta Servlet 6.1, running on Apache Tomcat 11.0.26 and Java 21 (EL 6.0 needs Java 17 or later). Everything was verified on 2026-10-08: the rules against sections 1.7 to 1.17 and section 1.25 of the Expression Language 6.0 specification and against section 2.8 and 2.9 of the Pages 4.0 specification, and every example by building it into a Maven WAR (context path /g4elops) and running it on Tomcat 11.0.26 with curl; the outputs and error messages shown are the ones that run produced. An Expression Language expression is small, but it is not simple: ${a + b} is numeric addition and never string concatenation, ${a == b} calls equals after a round of type conversions, a comparison with a missing value is quietly false, and a page can fail with an HTTP 500 because a request parameter was not a number. All of that is decided by two sets of rules in the EL specification: one per operator (sections 1.7 to 1.16) and one for converting a value to the type an operator or an attribute expects (section 1.25). This page lists both, operator by operator, with the Bookshelf (a small catalogue of books) as the running scenario, and ends with the pitfalls, what changed from JSP 2.0 to EL 6.0 and where the books in the section bibliography are out of date. The syntax of ${...} and #{...}, the implicit objects and the property access operators . and [] are on the Expression Language Basics page of this section; the lambda operator ->, collection literals and streams, static access, records and Optional, and ELProcessor have a page of their own each (Lambdas, Collections and Streams, Static Access, Records and Optional and Configuration and ELProcessor).

The Bookshelf Used on This Page

The examples need data in scope and nothing else, so a ServletContextListener puts a handful of values into application scope when the web application starts. The Book record is the one used in the rest of the section. Records are read as beans by the EL since version 6.0, so ${dune.title} works without getters.

Arithmetic Operators

The operators are +, -, *, / (or div), % (or mod) and the unary minus. They work on integers (BigInteger and Long) and on floating-point numbers (BigDecimal and Double); every other numeric type, and a String, is converted first. The specification picks the working type for +, - and * from the operands:

flowchart TD start["A and B evaluated"] --> nn{"Both null?"} nn -- yes --> zero["Result is the Long 0"] nn -- no --> bd{"Either operand a BigDecimal?"} bd -- yes --> rbd["Both become BigDecimal"] bd -- no --> fl{"Either a Float, a Double, or a String containing . e or E?"} fl -- yes --> bi1{"Either a BigInteger?"} bi1 -- yes --> rbd bi1 -- no --> rdb["Both become Double"] fl -- no --> bi2{"Either a BigInteger?"} bi2 -- yes --> rbi["Both become BigInteger"] bi2 -- no --> rlg["Both become Long"]

Reading the output against the rules:

  • Integer division does not exist. / is Double division unless a BigDecimal or BigInteger is involved, so ${7 / 2} is 3.5 and even ${8 div 2} prints 4.0. There is no operator for the whole-number quotient; round the result with fmt:formatNumber (maximum fraction digits 0, which rounds half to even) or move the arithmetic into the controller.

  • The money rule. price is a BigDecimal with two decimals, so every operation stays exact and keeps scale 2 for +, - and * (37.50, 13.50); the division is rounded half up to the scale of the left operand (4.17). A Double never enters a BigDecimal calculation unless it is a literal such as 0.1: see the pitfalls.

  • A Float is widened to a Double, which exposes the binary representation: 0.1f * 3 prints 0.30000000447034836. Prefer Double or BigDecimal in model classes that a page multiplies.

  • Long arithmetic wraps silently. 9223372036854775807 + 1 is -9223372036854775808. Use a BigInteger (the big value) when overflow is possible; ${big + 1} is exact.

  • Division by zero is not an error for Double: 1 / 0 is Infinity and 0 / 0 is NaN. A Long or BigInteger remainder by zero is an error (see the next example).

  • Null counts as zero, and a String is parsed ('12' + 1 is 13, '2.5' + 1 is 3.5), including the empty String, which is 0 (${'' + 1} is 1).

Two lessons are in this output. First, the third line is the commonest mistake of everybody who comes from Java or JavaScript: + never concatenates. The operands of 'Dune' + ' (1965)' are parsed as numbers, and the parse fails. The concatenation operator is += (next section). Second, a number-conversion failure surfaces as a raw NumberFormatException from Long.valueOf and not as an ELException, while a Boolean operand is rejected with an ELException; handlers that map exceptions to pages must be ready for both. Whatever the type, the page never renders partially in this case: the container answers 500 (or the configured error page, see the error handling page).

String Concatenation: +=

${A += B} converts both operands to String and returns the concatenation. It exists because + is arithmetic only. A null operand becomes the empty String and an enum becomes its name(), so there is no NullPointerException and no "null" text, as there would be in Java.

Points the output makes concrete:

  • Numbers compare as numbers whatever their type: 1 eq 1.0, copies == 3.0 (an Integer against a Double) and count == 7 (a Long against an Integer literal) are true. A String that is compared with a number is converted to a number ('1' eq 1, ${'10' lt 9} is false because 10 is not less than 9).

  • Two Strings compare lexically, not numerically: '10' lt '9' is true. The comparison is also case sensitive and based on String.compareTo, so 'Zebra' lt 'apple' is true (upper case sorts first). To sort or filter book titles in a locale-aware way, do it in Java.

  • Null makes every ordering comparison false, with one exception: nothing le nothing is true because the two operands are the same (null) and the operator allows equality (step 1 comes before the null test). nothing == 0 and nothing == '' are false (null is never equal to a non-null value), and blank == null is false: the empty String is not null.

  • A String is compared with an enum by constant name (status == 'AVAILABLE'), a Boolean with the text 'true' or 'false', and any Comparable, such as LocalDate, with another of its kind (loan.due lt today).

  • Equality of unrelated objects falls back to equals: books[0] == dune is true because the list holds the same record. A record has value-based equals, so two Book records with the same components are equal as well.

price is 12.50 (scale 2). == calls BigDecimal.equals, which is false for 12.50 and 12.5, so ${price == 12.50} is false too: the literal 12.50 is a Double that is converted to BigDecimal as 12.5. To test a BigDecimal for equality in a page, use price le x and price ge x, or a Double-free string (price eq '12.50' has the same scale), or do the comparison in Java. The last two lines show the same trap in arithmetic: a numeric literal such as 0.1 is a Double, and converting it to a BigDecimal exposes the binary expansion of 0.1; the quoted '0.1' is converted to a BigDecimal from its text and stays exact.

Assignment and the Semicolon

EL 3.0 added two operators that change state, both designed for the stand-alone ELProcessor and for lambdas, and both available in a page.

  • ${A = B} evaluates B and writes it to the writable reference A, and the whole expression returns the value written. It is right associative: ${a = b = 5} is a = (b = 5). A that cannot be written throws PropertyNotWritableException.

  • ${A ; B} evaluates A, discards the value, then evaluates and returns B. It is the C comma operator, so it chains assignments: ${x = 5; y = x * 2; x + y}.

What a bare name means to = is decided by the resolvers. Type Coercion

Every expression is evaluated in the context of an expected type: an operator expects numbers, a Boolean or a String; a tag attribute expects the type in its TLD; a method call expects the parameter type. The result of the sub-expression rarely matches, so section 1.25 defines how a value X becomes a type Y. The first step is to find a custom converter: an ELResolver can implement convertToType, and the resolvers in the chain are asked in order. Only when no resolver converts does the default conversion run.

Notes on the page. param.page + 0 is the idiom for "this parameter, as a number": it turns the text "2" into the Long 2 so that page - 1 and page + 1 do arithmetic and the links print the numbers 1 and 3. An absent or empty parameter is covered by empty param.page, but a parameter that is not a number (?page=abc) still ends in NumberFormatException: For input string: "abc" and an HTTP 500: validate numeric input in a servlet or filter, or in a tag that catches the error (c:catch), before the page reads it. The third response is the other trap: ?page=3 is a valid number past the end of the data, and the page announces "Showing 5 to 3 of 3" with an empty list. The operators cannot clamp the value without a Math.min, so compute the page range in the controller and hand the view the numbers. The titles are printed through c:out; the ${book.year} in text is a number and needs no escaping, which is not true of ${param.q} or of any text typed by a user.

Security Notes

  • EL does not escape. The result of an expression in template text is written as is, so ${param.q} is an XSS vector. Use c:out (which escapes <, >, &, ' and " by default) or fn:escapeXml; operators do not change this, and the conditional ${empty param.q ? 'all' : param.q} is as unsafe as the parameter it returns.

  • A request value is an operand, never code. ${param.page + 1} cannot make the container run the user’s text as an expression. EL injection needs the text to be evaluated, for example by building an expression string from input and passing it to ExpressionFactory.createValueExpression or ELProcessor.eval; never do that. The syntax and escaping page of this section covers the template-text case, and the Security page covers the rest.

  • = and ; are statements. Pages that contain them modify scoped attributes (see the typo example). Keep them out of templates, and prefer c:set for the assignments that do belong in a page.

  • Numeric input fails with 500. An unvalidated param.n + 1 is a denial-of-service nuisance and fills the error log; map NumberFormatException and ELException to an error page.
