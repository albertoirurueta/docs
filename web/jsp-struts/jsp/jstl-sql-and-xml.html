Why they are discouraged

The sentence that opens chapter 10 of the specification is the whole argument: it is generally preferred to have database operations handled in the business logic of an MVC application, but there are situations where a page author needs them within the page: prototyping and testing, small and simple applications, lack of developer resources. Choosing the Data Source

Every SQL tag that talks to a database needs a javax.sql.DataSource, and the same algorithm finds it for sql:query, sql:update and sql:transaction. The specification (10.2) gives the steps, and the diagram follows them.

flowchart TD start["sql:query, sql:update or sql:transaction runs"] --> tx{"query or update nested in sql:transaction?"} tx -->|"yes"| parent["Use the connection of the parent transaction"] tx -->|"no"| attr{"dataSource attribute set?"} attr -->|"yes"| val["Use its value"] attr -->|"no"| cfg{"Configuration variable jakarta.servlet.jsp.jstl.sql.dataSource found by Config.find?"} cfg -->|"yes"| val cfg -->|"no"| err1["JspException: dataSource is null"] val --> kind{"Type of the value?"} kind -->|"javax.sql.DataSource object"| conn["getConnection()"] kind -->|"String"| jndi{"Lookup of java:comp/env/ plus the string succeeds?"} jndi -->|"yes"| conn jndi -->|"no"| dm["Read the string as url, driver, user, password and use DriverManager"] dm -->|"fails"| err2["JspException: Unable to get connection"] dm -->|"works"| conn

Case 5 is the pitfall: sql:setDataSource without var replaces the configuration variable for the page scope, so every later tag of the page that has no dataSource attribute uses the new database, whatever web.xml says. A JNDI name that is not bound is not reported as "name not found": the algorithm falls through to the JDBC parameter string, and the error is the one from DriverManager. The helper tags are also scoped by scope: a sql:setDataSource with scope="application" in a page changes the data source of every page that runs afterwards (verified: after one request to such a page, an unrelated page that has no dataSource attribute failed with the other database’s "Table not found"; the application had to be redeployed), which is another reason to configure it once, in web.xml or in Java.

Two rules close the section. First, the parameter string and the four JDBC attributes put a user name and a password into a page: use them only on a laptop with a throwaway database and a placeholder account, and never commit a real password into a JSP, a web.xml or a context.xml that is under version control. Second, a JDBC driver in WEB-INF/lib of a web application is registered with DriverManager and not unregistered by the container on undeploy: Tomcat logs a warning that the application "registered the JDBC driver [org.h2.Driver] but failed to unregister it" when the scratch WAR is redeployed, and the Tomcat JNDI how-to has a section on the service provider mechanism and memory leaks that recommends putting the driver in the server’s lib directory for container-managed pools.

Paging with startRow and maxRows

The two attributes are, in the words of the specification, a "poor man’s way" of paging: maxRows protects against runaway queries and startRow skips the pages already shown. Without an ORDER BY the order is not guaranteed, so a page can repeat or skip a row between requests. limitedByMaxRows tells the page whether a "next" link makes sense.

    SELECT id, title FROM book ORDER BY id
</sql:query>

    <c:forEach var="row" items="${books.rows}"><li><c:out value="${row.title}"/></li></c:forEach>
</ol>
<c:if test="${books.limitedByMaxRows}"><a href="?page=${page + 1}">next</a></c:if>

Doing It Properly: Replacing the SQL Tags

The replacement for sql:* is the structure the specification recommends: the page prints, a servlet (or a service behind it) queries. The Bookshelf servlet BooksServlet gets the container’s data source through @Resource, runs a prepared statement, puts a list of records in the request and forwards to a page that has no SQL.

BooksServlet.java
@WebServlet("/books-mvc")
public class BooksServlet extends HttpServlet {

    @Resource(name = "jdbc/bookshelf")
    private DataSource dataSource;

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        String author = req.getParameter("author");
        String like = "%" + (author == null ? "" : author) + "%";
        List<Book> books = new ArrayList<>();
        try (Connection connection = dataSource.getConnection();
             PreparedStatement statement = connection.prepareStatement(
                     "SELECT id, title, author, published_year FROM book WHERE author LIKE ? ORDER BY id")) {
            statement.setString(1, like);
            try (ResultSet rs = statement.executeQuery()) {
                while (rs.next()) {
                    books.add(new Book(rs.getLong("id"), rs.getString("title"), rs.getString("author"),
                            rs.getInt("published_year")));
                }
            }
        } catch (SQLException e) {
            throw new ServletException("Cannot read the books", e);
        }
        req.setAttribute("books", books);
        req.getRequestDispatcher("/WEB-INF/views/books-mvc.jsp").forward(req, resp);
    }
}

Filtering large documents

The filter attribute exists for performance: a DOM-like tree of a large document is expensive, so a filter can drop what the page does not need before the tree is built. The specification’s example prunes non-European customers. The Bookshelf filter drops every book whose year attribute is older than a threshold; it is an ordinary XMLFilterImpl that skips the subtree, and the page creates it with jsp:useBean (no scriptlet).

YearFilter.java
public class YearFilter extends XMLFilterImpl {
    private int minYear = 1960;
    private int skipDepth;

    public void setMinYear(int minYear) {
        this.minYear = minYear;
    }

    @Override
    public void startElement(String uri, String local, String qName, Attributes atts) throws SAXException {
        if (skipDepth > 0) {
            skipDepth++;
            return;
        }
        if ("book".equals(qName) && Integer.parseInt(atts.getValue("year")) < minYear) {
            skipDepth = 1;
            return;
        }
        super.startElement(uri, local, qName, atts);
    }

    @Override
    public void endElement(String uri, String local, String qName) throws SAXException {
        if (skipDepth > 0) {
            skipDepth--;
            return;
        }
        super.endElement(uri, local, qName);
    }

    @Override
    public void characters(char[] ch, int start, int length) throws SAXException {
        if (skipDepth == 0) {
            super.characters(ch, start, length);
        }
    }
}

The entity attack is the one that makes XML tags in a page worth a security review: the restriction is a default of the implementation, not a promise of the specification (the chapter only says x:parse does not validate), and a container or a different implementation on the class path may behave otherwise. A project that keeps these tags runs the check above once per implementation upgrade.

Forbidding the Libraries: PermittedTaglibsTLV

The best defence for a team that wants nothing of this page in its code is to forbid the libraries. The specification’s chapter 14 provides two tag library validators for that. jakarta.servlet.jsp.jstl.tlv.PermittedTaglibsTLV lists the tag libraries a page may import, and ScriptFreeTLV forbids scripting elements. A validator is attached to a tag library descriptor; every page that imports that library is then checked at translation time. The TLD below allows the core, formatting and functions libraries and (a requirement of the TLV) itself, and nothing else.

Worked Example: Importing the Catalog File into the Database

The two libraries meet in a one-off administrative task of the Bookshelf: load catalog.xml into the book table in one transaction. It is a prototype page, exactly what these tags are meant for, and it shows the libraries working together: x:forEach inside sql:transaction, XPath results turned into typed parameters with x:set, and a count at the end. Each book is stored with an offset of 100 on its id so that it does not collide with the rows of setup.jsp.

xml-import-db.jsp
<%@ page contentType="text/plain;charset=UTF-8" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="sql" uri="jakarta.tags.sql" %>
<%@ taglib prefix="x" uri="jakarta.tags.xml" %>
<x:parse var="catalog"><c:import url="/WEB-INF/data/catalog.xml"/></x:parse>
<sql:transaction>
    <sql:update>DELETE FROM shelf WHERE book_id > 100</sql:update>
    <sql:update>DELETE FROM book WHERE id > 100</sql:update>
    <x:forEach select="$catalog/catalog/book" var="b">
        <x:set var="id" select="number($b/@id) + 100"/>
        <x:set var="title" select="string($b/title)"/>
        <x:set var="author" select="string($b/author)"/>
        <x:set var="year" select="number($b/@year)"/>
        <sql:update var="n">
            INSERT INTO book (id, title, author, published_year, added_on) VALUES (?, ?, ?, ?, CURRENT_DATE)
            <sql:param value="${id}"/>
            <sql:param value="${title}"/>
            <sql:param value="${author}"/>
            <sql:param value="${year}"/>
        </sql:update>
imported ${title}: ${n} row
    </x:forEach>
</sql:transaction>
<sql:query var="r">SELECT COUNT(*) AS n FROM book WHERE id > 100</sql:query>
rows now: ${r.rows[0].n}

The number() results are Double objects (id 101.0), which sql:param bound to a BIGINT and an INT without complaint on H2; the string() results are String objects for the text columns, which is the combination the specification documents. The page ran twice with the same result because the first statements clear the previous load. As a design it has every smell listed at the beginning of this page (a write that a GET can trigger, a file and a database in a view, no authentication), and in a real project it becomes a servlet or a batch job that uses JAXB or StAX and a repository.
