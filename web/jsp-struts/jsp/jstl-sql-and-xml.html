JSTL SQL & XML (Legacy)

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Standard Tag Library 3.0 (API jakarta.servlet.jsp.jstl:jakarta.servlet.jsp.jstl-api 3.0.2, implementation org.glassfish.web:jakarta.servlet.jsp.jstl 3.0.1, the latest release of both), Jakarta Pages 4.0, Jakarta Expression Language 6.0 and Jakarta Servlet 6.1, running on Apache Tomcat 11.0.26 with Java 21. Everything was verified on 2026-10-08: the rules against chapters 10 to 13 of the Tags 3.0 specification (and chapter 14 for the tag library validators), the tag documentation (tagdocs) and the API Javadoc, and every example by building it into a Maven WAR (context path /g5jstlsqlxml) with an in-memory H2 2.5.252 database, deploying it on Tomcat 11.0.26 and calling it with curl; the outputs and error messages shown are the ones that run produced (blank lines produced by templates are left out). The two libraries are the part of JSTL that the Jakarta EE Tutorial calls archived: a subset of Jakarta Tags has been archived in favor of Jakarta XML Binding, Jakarta Faces and Jakarta Persistence. They still exist in the specification and in the implementation, they still work on Tomcat 11, and the specification itself says that database work belongs in the business logic of an MVC application and that DriverManager access is "for prototyping purposes only". This page documents every tag with an example, shows the safe way to use each one, and says plainly when to stop using them. The running scenario is the Bookshelf catalogue: the book and shelf tables on the SQL side, and a catalog.xml file and a feed of new books on the XML side. The core tags used in the examples (c:forEach, c:out, c:catch, c:import, c:set) have a page each in this section, written together with this one; the expression language is on the expression language basics page.

What the Two Libraries Are and Why They Are Discouraged

The Standard Tag Library has five libraries. Three of them (core, formatting and functions) are the everyday tools of a page author; the other two reach outside the view layer. The table lists them as the specification and the tag library descriptors of the implementation define them.

The old Sun URIs http://java.sun.com/jsp/jstl/sql and http://java.sun.com/jsp/jstl/xml are still accepted by the 3.0.1 implementation on Tomcat 11 (a page that declares them runs; checked), but the URIs of JSTL 3.0 are the jakarta.tags.* ones, and only those are used on this page. The JSTL 1.0 URIs http://java.sun.com/jstl/sql and the _rt twin libraries of the older books are another matter, covered in Where the Books Are Outdated.

Why they are discouraged

The sentence that opens chapter 10 of the specification is the whole argument: it is generally preferred to have database operations handled in the business logic of an MVC application, but there are situations where a page author needs them within the page: prototyping and testing, small and simple applications, lack of developer resources. Nothing in the libraries is wrong for those cases, and nothing in them scales beyond them.

Table 2. Why sql:* and x:* stay at the prototype end of a project
Concern What happens What to do instead

Layering

SQL (or XPath and XSLT) lives in the view, so the view is coupled to table and column names, cannot be unit tested without a container and cannot be reused by a REST endpoint or a batch job

Query in a servlet or a service, put the result in a request attribute, let the page only print it (see Doing It Properly: Replacing the SQL Tags)

Connection management

sql:setDataSource with url, driver, user and password uses DriverManager; the specification says it should not be used other than for prototyping because it provides no connection management

A javax.sql.DataSource from the container (JNDI) or from the application, with a pool

Injection

A statement built with ${...} inside the body of sql:query is plain string concatenation (shown in sql:param and sql:dateParam: Injection-Safe Values); the safe form needs a ? marker and a nested sql:param for every value

Parameters always; better, no SQL in pages

Transactions

sql:transaction is a JDBC Connection transaction; its behaviour is undefined inside a larger JTA user transaction, and a rollback cannot be forced from SQL

A transaction owned by a service

Error handling and leaks

Every failure becomes a JspException whose message contains the SQL statement, which must not reach a visitor

Catch and log in Java, show a reference number (see the error handling page)

XML parsing

Whole documents become trees in memory inside a page, with parser security that depends on the implementation (see XML Security: XXE, XSLT, XPath Injection and Escaping)

Testing and tooling

XPath and SQL errors surface at run time as JspException messages with a page line number

Plain Java classes with real tests

A throwaway setup.jsp creates and fills the two tables (a book and the number of copies on each of two shelves). It already uses most of the tags described below, which is why it comes first: DDL through sql:update, a transaction around several statements, parameters for every value and sql:dateParam for a date. Choosing the Data Source

Every SQL tag that talks to a database needs a javax.sql.DataSource, and the same algorithm finds it for sql:query, sql:update and sql:transaction. The specification (10.2) gives the steps, and the diagram follows them.

flowchart TD start["sql:query, sql:update or sql:transaction runs"] --> tx{"query or update nested in sql:transaction?"} tx -->|"yes"| parent["Use the connection of the parent transaction"] tx -->|"no"| attr{"dataSource attribute set?"} attr -->|"yes"| val["Use its value"] attr -->|"no"| cfg{"Configuration variable jakarta.servlet.jsp.jstl.sql.dataSource found by Config.find?"} cfg -->|"yes"| val cfg -->|"no"| err1["JspException: dataSource is null"] val --> kind{"Type of the value?"} kind -->|"javax.sql.DataSource object"| conn["getConnection()"] kind -->|"String"| jndi{"Lookup of java:comp/env/ plus the string succeeds?"} jndi -->|"yes"| conn jndi -->|"no"| dm["Read the string as url, driver, user, password and use DriverManager"] dm -->|"fails"| err2["JspException: Unable to get connection"] dm -->|"works"| conn

The value can therefore be given in five ways. The page datasource.jsp uses all of them in turn against the same database.

Form Where it is written Notes

Configuration variable

Used when a tag has no dataSource attribute; the page needs no JDBC knowledge. A String here is read like the attribute below

Attribute with a DataSource object

Needs a servlet, a listener or sql:setDataSource var to put the object in a scope

Attribute with a JNDI relative path

Attribute with the JDBC parameter string

Stores a DataSource (or the string) in var, or sets the configuration variable when there is no var; the four attributes are a simpler spelling of the parameter string

<%@ taglib prefix="sql" uri="jakarta.tags.sql" %>

<sql:setDataSource var="proto" url="jdbc:h2:mem:bookshelf;DB_CLOSE_DELAY=-1" driver="org.h2.Driver" user="sa" password=""/>

A: ${a.rows[0].n} (setDataSource var)
<%-- 2. the "url,driver,user,password" string form --%>
<sql:query var="b" dataSource="jdbc:h2:mem:bookshelf;DB_CLOSE_DELAY=-1,org.h2.Driver,sa,">SELECT COUNT(*) AS n FROM book</sql:query>
B: ${b.rows[0].n} (parameter string)
<%-- 3. a JNDI relative path, java:comp/env/ is prepended --%>
<sql:query var="c1" dataSource="jdbc/bookshelf">SELECT COUNT(*) AS n FROM book</sql:query>

<%-- 6. missing JNDI name and no configuration --%>

The output shows what each form does, including the surprising last two cases (line 5 is another empty in-memory database, and line 6 shows the message for a name that is neither a JNDI resource nor a JDBC string):

A: 5 (setDataSource var)
B: 5 (parameter string)
C: 5 (JNDI relative path)
D: 5 (web.xml context-param)
E: Table "BOOK" not found (this database is empty); SQL statement:
SELECT COUNT(*) AS n FROM book [42104-252]
F: Unable to get connection, DataSource invalid: "java.sql.SQLException: No suitable driver found for jdbc/missing"

Case 5 is the pitfall: sql:setDataSource without var replaces the configuration variable for the page scope, so every later tag of the page that has no dataSource attribute uses the new database, whatever web.xml says. A JNDI name that is not bound is not reported as "name not found": the algorithm falls through to the JDBC parameter string, and the error is the one from DriverManager. The helper tags are also scoped by scope: a sql:setDataSource with scope="application" in a page changes the data source of every page that runs afterwards (verified: after one request to such a page, an unrelated page that has no dataSource attribute failed with the other database’s "Table not found"; the application had to be redeployed), which is another reason to configure it once, in web.xml or in Java.

Two rules close the section. First, the parameter string and the four JDBC attributes put a user name and a password into a page: use them only on a laptop with a throwaway database and a placeholder account, and never commit a real password into a JSP, a web.xml or a context.xml that is under version control. Second, a JDBC driver in WEB-INF/lib of a web application is registered with DriverManager and not unregistered by the container on undeploy: Tomcat logs a warning that the application "registered the JDBC driver [org.h2.Driver] but failed to unregister it" when the scratch WAR is redeployed, and the Tomcat JNDI how-to has a section on the service provider mechanism and memory leaks that recommends putting the driver in the server’s lib directory for container-managed pools.

sql:query: Reading Rows

sql:query runs a SELECT and stores a jakarta.servlet.jsp.jstl.sql.Result in var. It has three syntaxes, which differ only in where the statement and the parameters come from.

The statement; alternatively it is the body of the tag

dataSource

DataSource or String (yes)

int (yes)

Largest number of rows kept; -1 or absent means no limit; must be at least -1. Beats the configuration variable jakarta.servlet.jsp.jstl.sql.maxRows (Config.SQL_MAX_ROWS)

Paging with startRow and maxRows

The two attributes are, in the words of the specification, a "poor man’s way" of paging: maxRows protects against runaway queries and startRow skips the pages already shown. Without an ORDER BY the order is not guaranteed, so a page can repeat or skip a row between requests. limitedByMaxRows tells the page whether a "next" link makes sense.

    SELECT id, title FROM book ORDER BY id
</sql:query>

    <c:forEach var="row" items="${books.rows}"><li><c:out value="${row.title}"/></li></c:forEach>
</ol>
<c:if test="${books.limitedByMaxRows}"><a href="?page=${page + 1}">next</a></c:if>

Doing It Properly: Replacing the SQL Tags

The replacement for sql:* is the structure the specification recommends: the page prints, a servlet (or a service behind it) queries. The Bookshelf servlet BooksServlet gets the container’s data source through @Resource, runs a prepared statement, puts a list of records in the request and forwards to a page that has no SQL.

BooksServlet.java
@WebServlet("/books-mvc")
public class BooksServlet extends HttpServlet {

    @Resource(name = "jdbc/bookshelf")
    private DataSource dataSource;

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        String author = req.getParameter("author");
        String like = "%" + (author == null ? "" : author) + "%";
        List<Book> books = new ArrayList<>();
        try (Connection connection = dataSource.getConnection();
             PreparedStatement statement = connection.prepareStatement(
                     "SELECT id, title, author, published_year FROM book WHERE author LIKE ? ORDER BY id")) {
            statement.setString(1, like);
            try (ResultSet rs = statement.executeQuery()) {
                while (rs.next()) {
                    books.add(new Book(rs.getLong("id"), rs.getString("title"), rs.getString("author"),
                            rs.getInt("published_year")));
                }
            }
        } catch (SQLException e) {
            throw new ServletException("Cannot read the books", e);
        }
        req.setAttribute("books", books);
        req.getRequestDispatcher("/WEB-INF/views/books-mvc.jsp").forward(req, resp);
    }
}

Filtering large documents

The filter attribute exists for performance: a DOM-like tree of a large document is expensive, so a filter can drop what the page does not need before the tree is built. The specification’s example prunes non-European customers. The Bookshelf filter drops every book whose year attribute is older than a threshold; it is an ordinary XMLFilterImpl that skips the subtree, and the page creates it with jsp:useBean (no scriptlet).

YearFilter.java
public class YearFilter extends XMLFilterImpl {
    private int minYear = 1960;
    private int skipDepth;

    public void setMinYear(int minYear) {
        this.minYear = minYear;
    }

    @Override
    public void startElement(String uri, String local, String qName, Attributes atts) throws SAXException {
        if (skipDepth > 0) {
            skipDepth++;
            return;
        }
        if ("book".equals(qName) && Integer.parseInt(atts.getValue("year")) < minYear) {
            skipDepth = 1;
            return;
        }
        super.startElement(uri, local, qName, atts);
    }

    @Override
    public void endElement(String uri, String local, String qName) throws SAXException {
        if (skipDepth > 0) {
            skipDepth--;
            return;
        }
        super.endElement(uri, local, qName);
    }

    @Override
    public void characters(char[] ch, int start, int length) throws SAXException {
        if (skipDepth == 0) {
            super.characters(ch, start, length);
        }
    }
}

Worked Example: Importing the Catalog File into the Database

The two libraries meet in a one-off administrative task of the Bookshelf: load catalog.xml into the book table in one transaction. It is a prototype page, exactly what these tags are meant for, and it shows the libraries working together: x:forEach inside sql:transaction, XPath results turned into typed parameters with x:set, and a count at the end. Each book is stored with an offset of 100 on its id so that it does not collide with the rows of setup.jsp.

xml-import-db.jsp
<%@ page contentType="text/plain;charset=UTF-8" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="sql" uri="jakarta.tags.sql" %>
<%@ taglib prefix="x" uri="jakarta.tags.xml" %>
<x:parse var="catalog"><c:import url="/WEB-INF/data/catalog.xml"/></x:parse>
<sql:transaction>
    <sql:update>DELETE FROM shelf WHERE book_id > 100</sql:update>
    <sql:update>DELETE FROM book WHERE id > 100</sql:update>
    <x:forEach select="$catalog/catalog/book" var="b">
        <x:set var="id" select="number($b/@id) + 100"/>
        <x:set var="title" select="string($b/title)"/>
        <x:set var="author" select="string($b/author)"/>
        <x:set var="year" select="number($b/@year)"/>
        <sql:update var="n">
            INSERT INTO book (id, title, author, published_year, added_on) VALUES (?, ?, ?, ?, CURRENT_DATE)
            <sql:param value="${id}"/>
            <sql:param value="${title}"/>
            <sql:param value="${author}"/>
            <sql:param value="${year}"/>
        </sql:update>
imported ${title}: ${n} row
    </x:forEach>
</sql:transaction>
<sql:query var="r">SELECT COUNT(*) AS n FROM book WHERE id > 100</sql:query>
rows now: ${r.rows[0].n}

The number() results are Double objects (id 101.0), which sql:param bound to a BIGINT and an INT without complaint on H2; the string() results are String objects for the text columns, which is the combination the specification documents. The page ran twice with the same result because the first statements clear the previous load. As a design it has every smell listed at the beginning of this page (a write that a GET can trigger, a file and a database in a view, no authentication), and in a real project it becomes a servlet or a batch job that uses JAXB or StAX and a repository.

The specification examples carry old habits too. The chapter 10 sample jdbc:mysql://localhost/,org.gjt.mm.mysql.Driver uses a driver class of the year 2000, <x:if select="$customer/[location='UK']"> is not valid XPath, the syntax of x:forEach in 12.6 has a stray > after select, and the two example TLDs of chapter 14 do not parse. They are listed with the other inconsistencies found in this section. What the specification is right about, and the books agree: these tags are for a prototype, a small internal tool or a stop-gap, and the day the page needs a second consumer, a test, a pool setting or a security review, the query moves to Java.
