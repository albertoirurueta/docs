Standard Actions & JavaBeans

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Jakarta Pages 4.0 (chapter 5, "Standard Actions", and sections 1.14 and 1.8 for the rules they depend on), with Jakarta Expression Language 6.0, Jakarta Tags 3.0 and Jakarta Servlet 6.1, running on Apache Tomcat 11.0.26 and Java 21. Everything was verified on 2026-10-08: the facts against the Pages 4.0 specification, the Javadoc of java.beans and the Tomcat 11 documentation, and every example by building it into a Maven WAR and requesting it with curl on Tomcat 11.0.26; the outputs and error messages shown are the ones that run produced, and rows marked "observed" were reproduced. A standard action is an XML-style element with the prefix jsp that every Pages container understands without a taglib directive. Thirteen of them exist in Pages 4.0 (a fourteenth, jsp:plugin, was removed). The three that give the page a model are jsp:useBean, jsp:setProperty and jsp:getProperty; they date from JSP 0.92 and they are the reason the JavaBeans conventions appear in a web guide at all. The others compose pages (jsp:include, jsp:forward, jsp:param), generate markup (jsp:element, jsp:attribute, jsp:body, jsp:text, jsp:output) or belong to tag files (jsp:invoke, jsp:doBody). The running scenario is the Bookshelf of this section: a bean describes a book, a form fills it, a fragment renders it.

The bean tags are legacy in the sense that new code reads and writes beans with EL and JSTL, and forms are bound by a controller. They still matter for three reasons. They are in every JSP written before 2005, which is what most maintenance work meets. They are the simplest demonstration of the page-to-bean contract that Struts, Spring MVC and Jakarta Faces all re-implement. And jsp:include, jsp:forward, jsp:param, jsp:element, jsp:attribute, jsp:body and jsp:text are not legacy at all: they are the supported way to compose pages without a tag library.

A translation error results when the jsp prefix is used for an element that is not a standard action; Tomcat 11.0.26 reports Invalid standard action for jsp:plugin, which Pages 4.0 removed (observed).

Three attribute-handling rules apply to every action, and explain several error messages later on this page.

  • Attribute values given as plain strings are converted to the attribute’s declared type (section 1.14.2.1, table JSP.1-11). JavaBeans Conventions

A JavaBean is, for the purposes of Pages, an ordinary Java class that follows a few naming rules so that tools (and Jasper) can discover its properties without being told about them. The rules come from the JavaBeans specification and are implemented by java.beans.Introspector; Jasper introspects the bean class for every jsp:setProperty and jsp:getProperty, and EL’s BeanELResolver uses the same machinery for ${book.title}.

Table 2. The conventions that decide whether jsp:setProperty and jsp:getProperty can see a property
Convention Rule Consequence if broken

Public no-argument constructor

jsp:useBean with class instantiates with it

The value for the useBean class attribute [...] is invalid at translation time (observed)

Property from accessors

getX() and setX(T) define a property x; the type is the getter’s return and the setter’s parameter

Without the setter the property is read-only; without the getter it cannot be read with jsp:getProperty

Boolean property

isX() returning primitive boolean (and optionally getX())

A getter Boolean isX() returning the wrapper type is not a getter: Cannot find a method to read property [featured] (observed)

Property name decapitalization

Introspector.decapitalize: getTitle() gives title, but getISBN() gives ISBN and getURL() gives URL because the first two letters are capitals

property="isbn" fails with Cannot find any information on property [isbn]; the name must be ISBN (observed)

Indexed property

An array-valued getX()/setX(T[]), optionally with getX(int)/setX(int, T)

Introspector reports it as indexed (observed); jsp:setProperty needs an array value

Serializable

Implement java.io.Serializable for beans stored in a session

A distributable application fails to replicate the session otherwise

HttpSessionBindingListener

valueBound and valueUnbound are called when the bean is put into or removed from a session

Useful for releasing resources; see the example below

BeanInfo

A class named XBeanInfo next to X overrides introspection

Properties it does not list are invisible to jsp:setProperty and to EL (observed)

PropertyEditor

A registered editor converts a String to the property type with setAsText

Used by jsp:setProperty for types that are not primitives, wrappers or String

Records

A record’s accessors (title()) are not getters

jsp:getProperty fails: Cannot find any information on property [title]; EL 6.0 reads records (observed, see the example below)

Source: Java SE 21 — java.beans.Introspector

Source: Java SE 21 — java.beans.BeanInfo

The Bookshelf bean used by every example on this page is a plain class with the conventions above: a no-argument constructor, ordinary accessors, a boolean isAvailable(), an indexed tags property, Serializable, and a session binding listener that records its own lifecycle. The featured flag exists so that a later example can show why property="*" is dangerous. The Titled interface exists so that jsp:useBean can name a type that cannot be instantiated.

The Bookshelf book bean (src/main/java/org/example/bookshelf/BookBean.java)

import jakarta.servlet.http.HttpSessionBindingListener;
import java.io.Serializable;
import java.util.ArrayList;
import java.util.List;

public class BookBean implements Titled, Serializable, HttpSessionBindingListener {
    private static final long serialVersionUID = 1L;
    public static final List<String> EVENTS = new ArrayList<>();   // demo only

    private long id;
    private String title = "";
    private String author = "";
    private int year;
    private boolean available;
    private String[] tags = new String[0];
    private boolean featured;

    public BookBean() {                       // required by jsp:useBean class="..."
    }

    public long getId() { return id; }
    public void setId(long id) { this.id = id; }

    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }

    public void setAuthor(String author) { this.author = author; }

    public void setTags(String[] tags) { this.tags = tags; }

    public boolean isFeatured() { return featured; }             // must not come from a form
    public void setFeatured(boolean featured) { this.featured = featured; }

    @Override
    public void valueBound(HttpSessionBindingEvent event) { EVENTS.add("bound " + event.getName()); }

    @Override
    public void valueUnbound(HttpSessionBindingEvent event) { EVENTS.add("unbound " + event.getName()); }
}

jsp:useBean

jsp:useBean associates a Java object that lives in a scope with a name, creating the object first if it does not exist. It is the action that "introduces" a bean to the page: jsp:setProperty and jsp:getProperty are only valid for names introduced this way (or by a custom action that declares a variable of that name). In a scripting page it also declares a Java local variable of the same name; in a scriptless page or context only the EL variable exists.

Table 3. The attributes of jsp:useBean (Pages 4.0 table JSP.5-1)
Attribute Meaning Rules

id

The name of the object in its scope, and the scripting variable name

Required. Unique within the translation unit: a duplicate id is a fatal translation error (observed). Case sensitive and a legal Java variable name

scope

page (default), request, session or application

Anything else is a translation error: Illegal value of 'scope' attribute: [pagee] (observed)

class

Fully qualified class to instantiate when the object is not found

Must be non-abstract with a public no-argument constructor

type

The type of the scripting variable and the type the object must have

A superclass, an interface, or the class itself; a ClassCastException results otherwise (observed)

beanName

A name for java.beans.Beans.instantiate: a class name or a serialized resource a/b/c.ser

Accepts a request-time value. Used with type; class and beanName together are a translation error (observed)

At least one of type and class must be present, and class with beanName is not valid. When type and class are both present, class must be assignable to type; Jasper compiles the generated servlet with that assumption, so the mismatch becomes a Java compile error (Unable to compile class for JSP, observed).

<%@ page contentType="text/html; charset=UTF-8" pageEncoding="UTF-8" %>
<jsp:useBean id="book" class="org.example.bookshelf.BookBean" scope="request"/>

Why the Wildcard Form Is a Security Risk

property="*" lets the request decide which properties are set. Anyone who can send a request can send featured=true, id=1 or any other property name the bean happens to expose, whether or not the form shows a field for it. That is the same defect that OWASP calls mass assignment (and that Struts 7 counters by requiring the @StrutsParameter annotation on every settable property by default). A bean used with * therefore has to contain only properties that are safe to set from outside, or the page has to list its properties one at a time. The worked example later on this page uses the explicit form.

A conversion error is the second risk. A parameter such as year=abc is not validated: the exception propagates and the page fails with HTTP 500 (observed).

jsp:forward

jsp:forward dispatches the current request to another resource in the same application and ends the current page: nothing after the action is executed. It is RequestDispatcher.forward from inside a page, with the same effects on the request path attributes. If the page output is buffered, the buffer is cleared before the forward. If the buffer was already flushed, or if an unbuffered page had written anything, the forward cannot work: the specification demands an IllegalStateException.

jsp:forward accepts the same jsp:param children as jsp:include, with the same ordering rules, and a single attribute page, which accepts a request-time value (and has the same path-selection risk as in jsp:include).

<jsp:forward page="/WEB-INF/fragments/card.jsp"/>

Tomcat 11.0.26 did not throw the IllegalStateException of the specification: the JSP writer’s clear() raised java.io.IOException: Error: Attempt to clear a buffer that's already been flushed, the error-page mechanism could not run because the response was committed (too late for an error page in the log), and the client received an HTTP 200 with an empty body (observed). The practical rule is the one from the servlet fundamentals page: decide to forward before writing anything, which also means before any <% out.flush() %> and before a full buffer.

A forward is invisible to the browser (the URL does not change) and is only appropriate when the destination is part of the same logical request; after a state change use a redirect (see Includes, Forwards & Page Composition).

jsp:param Rules in Brief

jsp:param has two mandatory attributes, name and value, and the value may be a request-time expression. It is valid only inside jsp:include, jsp:forward (and the removed jsp:params); anywhere else the page is rejected: The jsp:param action must not be used outside the jsp:include or jsp:forward elements (observed). Names and values are written unencoded by the page author; the container encodes them with the request’s character encoding when it has to build a query string, which is why a value containing an ampersand needs no manual escaping. New parameters take precedence over existing ones of the same name and are visible only during the included or forwarded call.

Source: Jakarta Pages 4.0 — 5.6 jsp:param

Generating Markup: jsp:element, jsp:attribute, jsp:body, jsp:text and jsp:output

jsp:element creates an element whose name is only known at request time, jsp:attribute gives it attributes (and, as shown above, can also give attributes to other actions), jsp:body gives it content, and jsp:text writes template text verbatim.

Table 11. Attributes of jsp:attribute (Pages 4.0 table JSP.5-6)
Attribute Meaning

name

Required. With jsp:element, the attribute name in the generated element; otherwise it must match an attribute of the enclosing action, as declared in the TLD or as specified. May be a QName. A translation error results if the value is also given as an XML attribute

trim

true (default) removes leading and trailing whitespace of the body, at translation time only; whitespace produced by an action in the body is never trimmed

omit

With jsp:element only: when true, the attribute is left out of the generated element. Ignored elsewhere. Default false

jsp:body takes no attributes and is required whenever jsp:attribute children are present. If jsp:attribute children are present and there is no (or an empty) jsp:body, the action has an empty body.

jsp:element has one mandatory attribute, name, which must be an XML attribute (not a jsp:attribute) because jsp:attribute has a special meaning inside jsp:element. The name may be a request-time value.

jsp:text

jsp:text encloses template data and has no attributes. Its body is passed through to the output unchanged, without the whitespace removal that applies elsewhere, and it may contain EL, but no nested actions or scripting elements. Inside a JSP document the body must also be well-formed XML, so a literal < or & has to be escaped or put into a CDATA section.

<%-- text2.jsp --%>
<%@ page contentType="text/html; charset=UTF-8" pageEncoding="UTF-8" %>

Observed output

[<b>not bold</b> 2]

jsp:output

jsp:output can be used only in JSP documents and in tag files in XML syntax, where it controls the XML declaration and the DOCTYPE of the generated output. Pages 4.0 defines four properties, all affecting the prolog: omit-xml-declaration (yes, no, true, false; the default is yes for a document that has a jsp:root element), doctype-root-element, doctype-system and doctype-public. A DOCTYPE is generated only if doctype-system is present, and doctype-root-element must then be present; doctype-public needs doctype-system. In a standard-syntax page the action is a translation error: <jsp:output> must not be used in standard syntax (observed).

demo/doc.jspx, a JSP document with jsp:output and the bean tags
<?xml version="1.0" encoding="UTF-8"?>
<html xmlns:jsp="http://java.sun.com/JSP/Page" xmlns:c="jakarta.tags.core">
  <jsp:output doctype-root-element="html" doctype-system="about:legacy-compat" omit-xml-declaration="true"/>
  <jsp:directive.page contentType="text/html; charset=UTF-8"/>
  <body>
    <h1><jsp:text>Bookshelf</jsp:text></h1>
    <jsp:useBean id="book" class="org.example.bookshelf.BookBean"/>
    <jsp:setProperty name="book" property="title" value="Dune"/>
    <p>${book.title} <jsp:getProperty name="book" property="title"/></p>
  </body>
</html>
Observed output
<!DOCTYPE html SYSTEM "about:legacy-compat">
<html><body><h1>Bookshelf</h1><p>Dune Dune</p></body></html>

The identifier http://java.sun.com/JSP/Page is the namespace name of the standard actions in XML syntax. It is an identifier, not an address, and Pages 4.0 still uses it in its own examples. JSP documents are covered in JSP Documents (XML Syntax).

jsp:invoke and jsp:doBody (Tag Files)

jsp:invoke and jsp:doBody are valid only inside tag files, and a translation error results if they are used in a page. jsp:invoke fragment="name" invokes a fragment attribute (declared with fragment="true"); jsp:doBody evaluates the body passed to the tag. Both write to the current output by default; var (a String) or varReader (a java.io.Reader, resettable) captures the output in a scoped variable, and scope (default page) says which scope, valid only with var or varReader. A session scope throws IllegalStateException when the calling page has no session. The action has no body. This example is only a pointer; the full treatment is on the tag file pages of this section.

WEB-INF/tags/panel.tag
<%@ tag body-content="scriptless" %>
<%@ attribute name="header" fragment="true" %>
<%@ attribute name="title" required="true" %>
<section><h2>${title}</h2>
<header><jsp:invoke fragment="header"/></header>
<jsp:doBody var="inner" scope="page"/>
<div>[${inner}]</div>
<jsp:doBody/>
</section>
demo/tagfile.jsp
<%@ page contentType="text/html; charset=UTF-8" pageEncoding="UTF-8" %>
<%@ taglib prefix="t" tagdir="/WEB-INF/tags" %>
<t:panel title="Books">
  <jsp:attribute name="header">Header: ${1 + 2}</jsp:attribute>
  <jsp:body>Dune</jsp:body>
</t:panel>
Observed output
<section><h2>Books</h2>
<header>Header: 3</header>
<div>[Dune]</div>
Dune
</section>

Here jsp:attribute supplies the fragment attribute header, jsp:body supplies the body, jsp:invoke writes the fragment, and jsp:doBody is used twice: once captured into inner and once written directly.

jsp:plugin Is Gone

jsp:plugin (with jsp:params and jsp:fallback) generated the object or embed markup that loaded an applet or a bean into the browser’s Java plug-in. Applets no longer run in browsers, and the action was deprecated in Pages 3.1 and removed in 4.0 ("Remove the deprecated jsp:plugin action and related actions"). A page that uses it no longer compiles (observed):

demo/plugin.jsp
<%@ page contentType="text/html; charset=UTF-8" pageEncoding="UTF-8" %>
<jsp:plugin type="applet" code="Foo.class" width="1" height="1"><jsp:fallback>no</jsp:fallback></jsp:plugin>
curl output on Tomcat 11.0.26
org.apache.jasper.JasperException: /demo/plugin.jsp (line: [2], column: [5]) Invalid standard action

There is no replacement for an applet. A page that rendered one needs a rewrite to ordinary HTML and JavaScript, or a server-side equivalent.

The Bookshelf Worked Example: A Book Card from a Form

The Bookshelf needs a "preview" page that shows a book typed into a form. The legacy shape binds with property="*" and prints with jsp:getProperty. The shape below keeps the standard actions but removes the two dangers: it lists the three properties the form may set, and it prints through c:out. A fragment renders the card; it receives its bean through the request scope and a heading level through jsp:param.

demo/worked.jsp, bean creation, explicit properties and an include
<%@ page contentType="text/html; charset=UTF-8" pageEncoding="UTF-8" %>
<jsp:useBean id="book" class="org.example.bookshelf.BookBean" scope="request"/>
<%-- only the three properties the form is allowed to set, never property="*" --%>
<jsp:setProperty name="book" property="title"/>
<jsp:setProperty name="book" property="author"/>
<jsp:setProperty name="book" property="year"/>
<!DOCTYPE html>
<html lang="en">
<body>
<jsp:include page="/WEB-INF/fragments/book-card.jsp">
  <jsp:param name="level" value="2"/>
</jsp:include>
</body>
</html>
WEB-INF/fragments/book-card.jsp, a fragment that names the bean by type and renders it
<%@ page contentType="text/html; charset=UTF-8" pageEncoding="UTF-8" trimDirectiveWhitespaces="true" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<jsp:useBean id="book" type="org.example.bookshelf.BookBean" scope="request"/>
<article>
  <jsp:element name="h${param.level}">
    <jsp:attribute name="class">title</jsp:attribute>
    <jsp:body><c:out value="${book.title}"/></jsp:body>
  </jsp:element>
  <p>by <c:out value="${book.author}"/> (${book.year})</p>
</article>
Observed: an attempt to set featured and a markup-injection title
$ curl -s "http://localhost:18080/g3actions/demo/worked.jsp?title=Dune&author=Frank%20Herbert&year=1965&featured=true&level=1"
<!DOCTYPE html>
<html lang="en">
<body>
<article>
  <h2 class="title">Dune</h2><p>by Frank Herbert (1965)</p>
</article>

</body>
</html>

$ curl -s -G "http://localhost:18080/g3actions/demo/worked.jsp" --data-urlencode 'title=<script>x</script>' -d author=A -d year=1
...
  <h2 class="title">&lt;script&gt;x&lt;/script&gt;</h2><p>by A (1)</p>
...

What the run shows: the level=1 the client sent was overridden by the page’s own jsp:param (the heading is an h2), featured=true was ignored because the page never names that property, the title was escaped by c:out, and the fragment found the bean through jsp:useBean type because the request scope is shared by an included page. The year is printed with plain EL: a number needs no escaping. A form that must reject year=abc still needs a controller, because jsp:setProperty throws.
