JSTL Iteration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Standard Tag Library (also called Jakarta Tags) 3.0, whose API is jakarta.servlet.jsp.jstl:jakarta.servlet.jsp.jstl-api 3.0.2 with the GlassFish implementation org.glassfish.web:jakarta.servlet.jsp.jstl 3.0.1, running under Jakarta Pages 4.0, Jakarta Expression Language 6.0 and Jakarta Servlet 6.1 on Apache Tomcat 11.0.26 and Java 21. Everything was verified on 2026-10-08: the rules against chapter 6 ("Iterator Actions") and appendix B of the Tags 3.0 specification, the tag reference and the LoopTagStatus Javadoc, and every example by building it into a Maven WAR (context path /g5jstliteration) and requesting it with curl on Tomcat 11.0.26; the outputs and error messages shown are the ones that run produced. Iteration is the job that made the tag libraries worth having: before them a page that listed rows needed a for loop in a scriptlet, a cast of the attribute to its real type and braces that opened in one scriptlet and closed in another. Two tags replace all of that. c:forEach repeats its body over an array, a collection, a map, an iterator, an enumeration or a count, and c:forTokens repeats it over the pieces of a string. Both can hand the body a status object that knows which round is running, which is the raw material of row numbers, zebra stripes, "first" and "last" styling, comma-separated lists and page links. The running scenario is the Bookshelf, a small catalogue of books: a servlet puts the books in the request and forwards to a view under WEB-INF. The tags that sit next to c:forEach in nearly every loop, c:out, c:if and c:choose, are covered with the rest of the core library on the JSTL Core page of this section; the Expression Language operators the examples use are on the EL operators and type coercion page, and the ${...} syntax itself is on Expression Language basics.

The Bookshelf Used on This Page

All the examples are views of one WAR, deployed as g5jstliteration.war under the context path /g5jstliteration. Its Maven dependencies are the ones of the section’s example application: jakarta.servlet-api 6.1.0, jakarta.servlet.jsp-api 4.0.0 and jakarta.el-api 6.0.1 as provided, and the JSTL API 3.0.2 with the GlassFish implementation 3.0.1 as ordinary compile-scope dependencies, because Tomcat does not ship JSTL. A servlet mapped to /view/* puts the catalogue and a few other collections in the request and forwards to /WEB-INF/views/<name>.jsp. Every JSP listing below omits the page directive and the taglib directive that start each file (<%@ taglib prefix="c" uri="jakarta.tags.core" %>). The Iteration Tags

Iteration lives in the core library, jakarta.tags.core, conventionally with the prefix c. The library has two iteration tags, and a third one in the XML library that belongs to the legacy part of JSTL.

Table 1. The iteration tags of Jakarta Tags 3.0
Tag What it repeats the body over Where to read more

c:forEach

an array, a collection, a map, an iterator, an enumeration, a comma separated string, or a range of integers

this page

c:forTokens

the tokens of a string, split with a set of delimiter characters

this page

x:forEach

the nodes an XPath expression selects in an XML document

the JSTL SQL and XML page (legacy)

Source: Jakarta Standard Tag Library 3.0 — 6 Iterator Actions: core tag library

Both core tags share their range attributes (begin, end, step), their var and varStatus attributes and their status object. The specification describes c:forEach as the base iteration action and says other iteration actions, c:forTokens and x:forEach among them, exist for "specific, specialized functionality". The flow below is what the tag does on every request; the sections that follow take its steps one at a time.

flowchart TD start["<c:forEach> starts"] --> hasItems{"items attribute present?"} hasItems -- yes --> pick["Pick the iterator by type: array, Collection, Map entries, Iterator, Enumeration, String of commas"] hasItems -- no --> count["Count from begin to end (both required), the item is an Integer"] pick --> range["Skip to begin, stop after end, take every step-th item"] count --> round range --> round["Each round: set var and varStatus in page scope, run the body"] round --> more{"More items?"} more -- yes --> round more -- no --> clean["Remove var and varStatus from page scope"]

Source: Jakarta Standard Tag Library 3.0 — c:forEach

c:forEach: the Attributes

c:forEach has two syntaxes, one that walks a collection and one that counts. They share every attribute except items.

<%-- Syntax 1: iterate over a collection --%>
<c:forEach [var="varName"] items="collection" [varStatus="varStatusName"] [begin="begin"] [end="end"] [step="step"]>
    body content
</c:forEach>

<%-- Syntax 2: iterate a fixed number of times --%>
<c:forEach [var="varName"] [varStatus="varStatusName"] begin="begin" end="end" [step="step"]>
    body content
</c:forEach>

Source: Jakarta Standard Tag Library 3.0 — c:forEach

Table 2. The attributes of c:forEach (the Dyn column of the specification is the "accepts an expression" column)
Attribute Type Expression allowed Meaning

items

any supported collection type

yes

the collection to walk; with it the tag uses syntax 1, without it syntax 2. A null value is an empty collection and nothing is iterated

var

String

no, a literal name

the page-scope variable that holds the current item; its visibility is "nested", that is, the body only. Optional

no, a literal name

the page-scope variable that holds the LoopTagStatus of the current round; also nested. Optional

int

yes

with items: the index of the first item to process (the first item has index 0). Without items: the first value of the counter. Must be 0 or more

Source: Jakarta Tags 3.0 tag reference — c:forEach

The tag reference lists begin, end and step as int and items as a jakarta.el.ValueExpression; the specification adds the constraints, which the container enforces at request time (see the pitfalls table for the exact exceptions). Three consequences are worth keeping in mind. First, var and varStatus are names, not expressions: writing var="${name}" is a translation error (observed: "attribute [var] does not accept any expressions"). Second, both are optional, so a loop that only needs to repeat its body (c:forEach begin="1" end="3" printing a star) can omit them. Third, an attribute that is an expression is coerced to int by the Expression Language rules, so a request parameter such as ${param.page} works without parsing, as long as it holds a number.

Maps: the Item Is an Entry

A map is walked through its entrySet(), so the loop variable is a Map.Entry and the page reads its two properties, key and value. The order is the order of the map, which the tag does not change: a HashMap has no promised order, a LinkedHashMap keeps insertion order and a TreeMap sorts by key. The three maps below hold the same four entries.

maps.jsp
HashMap:       <c:forEach var="e" items="${stockHash}" varStatus="s">${e.key}=${e.value}<c:if test="${!s.last}">, </c:if></c:forEach>
LinkedHashMap: <c:forEach var="e" items="${stockLinked}" varStatus="s">${e.key}=${e.value}<c:if test="${!s.last}">, </c:if></c:forEach>
TreeMap:       <c:forEach var="e" items="${stockTree}" varStatus="s">${e.key}=${e.value}<c:if test="${!s.last}">, </c:if></c:forEach>
item class:    <c:forEach var="e" items="${stockLinked}" end="0">${e.getClass().name}</c:forEach>

Source: Jakarta Standard Tag Library 3.0 — 6.1.2 Map

HashMap:       fiction=3, science=3, history=2, poetry=0
LinkedHashMap: science=3, fiction=3, poetry=0, history=2
TreeMap:       fiction=3, history=2, poetry=0, science=3
item class:    java.util.LinkedHashMap$Entry

The HashMap order is neither the insertion order nor the sorted order, and it can differ between Java versions, so a page that shows a map to people should be given a LinkedHashMap or a TreeMap by the servlet. The same output shows that the item is the real Map.Entry of the map, not a copy: begin, end and step count entries, and an entry whose value is a list (the byCategory map of the nested example below) can be iterated again with a second c:forEach.

Iterator and Enumeration: Use Once

An Iterator or an Enumeration cannot be rewound. The specification says so in one sentence, "must be used with caution", and the next view shows what it means: the second loop over the same Iterator finds it used up and prints nothing, without an error.

iterator.jsp
first loop:  <c:forEach var="b" items="${books2}" varStatus="s">${b.id}<c:if test="${!s.last}">, </c:if></c:forEach>
second loop: <c:forEach var="b" items="${books2}" varStatus="s">${b.id}<c:if test="${!s.last}">, </c:if></c:forEach>(nothing, the Iterator is used up)

Source: Jakarta Standard Tag Library 3.0 — 6.1.1 Collections of Objects to Iterate Over

first loop:  1, 2, 3, 4, 5, 6
second loop: (nothing, the Iterator is used up)

The practical rule is to put a List or another Collection in the request, not an Iterator. The one place an Iterator is natural is a very large result that must not be held in memory; even there, one loop per request is the limit, and an included fragment that loops again over the same attribute prints nothing. Note that varStatus still reports last correctly on an Iterator and an Enumeration (the separators above are right): the tag looks ahead.

Types That Are Not Supported

Anything outside the table raises a JspTagException at request time. These three were observed on Tomcat 11.0.26, and all raise the same message, Don't know how to iterate over supplied "items" in <forEach>.

items value What it is Fix

${books.get(0)}

a single Book, not a collection

loop over a collection, or do not loop

${books.stream()}

a java.util.stream.Stream

end the pipeline with toList() in the servlet or in EL (see the alternatives section)

${5}

a number

Source: Jakarta Standard Tag Library 3.0 — 6.1.1 Collections of Objects to Iterate Over

The same section explains one absence on purpose: a java.sql.ResultSet is not supported. The SQL tags use their own jakarta.servlet.jsp.jstl.sql.Result object, and ResultSupport.toResult(resultSet) converts a result set into one; a modern application does not hand a ResultSet to a page at all but maps rows to beans or records in the servlet or a service. The SQL tags are on the JSTL SQL and XML page of this section.

A String as items (Deprecated)

When items is a String, c:forEach splits it at commas. The specification marks this deprecated and gives the reason in a footnote: the proper way to process strings of tokens is c:forTokens, or the split and join functions. It still works in the 3.0.1 implementation.

string with forEach: <c:forEach var="t" items="${csv}" varStatus="s">[${t}]</c:forEach>

Source: Jakarta Standard Tag Library 3.0 — B.2 Changed between 2.0 and JSR-52, note on strings

string with forEach: [Dune][Emma][Cosmos]

Use c:forTokens for this, which can split at any characters and not only commas (see the section on c:forTokens).

Counting Without a Collection

Leave out items and c:forEach becomes a counted loop: begin and end are both required and the current value is an Integer. The range is inclusive at both ends, which is the opposite of a Java for (int i = 1; i < 5; i++).

range.jsp (first lines)
counted 1..5:   <c:forEach var="i" begin="1" end="5">${i} </c:forEach>
counted step:   <c:forEach var="i" begin="0" end="10" step="5">${i} </c:forEach>
item class:     <c:forEach var="i" begin="1" end="1">${i.getClass().name}</c:forEach>

Source: Jakarta Standard Tag Library 3.0 — 6.1.4 Range Attributes

counted 1..5:   1 2 3 4 5
counted step:   0 5 10
item class:     java.lang.Integer

A counted loop is the right tool for page numbers (begin="1" end="${pages}"), for a fixed number of empty form rows and for the stars of a rating. It is the wrong tool for walking a list by index (books[i]), because the collection can do that itself.

Taking Part of a Collection: begin, end and step

With items, the range attributes select a slice of the collection without copying it. begin and end are indexes into the collection, counted from 0, and end is included; step keeps every step-th item of the slice, starting with the first one. The output shows the four things that trip people. The two rounds are the indexes 2 and 4, so index and count differ (index is for "which item of the list", count is for "which row of the output"). last is true on the index 4 round even though end is 5, because the next step would be index 6. begin, end and step are null when the attributes were not given, and null prints as an empty string, so a page that needs a default writes ${empty s.end ? 'none' : s.end}. Finally, the object is an instance of an internal class of the implementation: depend on the interface and its properties, not on that class.

The status variable is a convenience, not a requirement: the loop does not pay for it unless varStatus is present, and nothing in LoopTagStatus can be changed from the page. The interface is the same one that custom loop tags expose, as the section on tag collaboration explains.

A Worked Example: the Bookshelf Catalogue

Most pages use c:forEach for exactly one job, a table. The catalogue below shows the pieces together: an empty-state branch with c:choose, a table whose row classes come from varStatus (zebra stripes through count, and the first and last rows marked for the style sheet), values escaped with c:out, and a second loop that builds a comma-separated list with last deciding where the separators go.

catalogue.jsp, an HTML view
<c:choose>
  <c:when test="${empty books}">
    <p>The shelf is empty.</p>
  </c:when>
  <c:otherwise>
    <table>
      <tr><th>#</th><th>Title</th><th>Author</th></tr>
      <c:forEach var="b" items="${books}" varStatus="s">
        <tr class="${s.count % 2 == 0 ? 'even' : 'odd'}${s.first ? ' first' : ''}${s.last ? ' last' : ''}">
          <td>${s.count}</td>
          <td><c:out value="${b.title}"/></td>
          <td><c:out value="${b.author}"/></td>
        </tr>
      </c:forEach>
    </table>
    <p>${books.size()} books by
      <c:forEach var="a" items="${books}" varStatus="s"><c:out value="${a.author}"/><c:if test="${!s.last}">, </c:if></c:forEach>
    </p>
  </c:otherwise>

Paging

A catalogue of six books fits on a page; a catalogue of six thousand does not. The two designs below differ in where the slice is taken, and the difference decides whether the application scales.

Paging in the View With begin and end

The view receives the whole list and uses begin and end to show one page of it. The page number and size come from request parameters, and the page links are a counted loop.

paging.jsp, an HTML view that pages an in-memory list

</c:forEach>
</ul>

The page is short, but it is fragile in three ways, all observed. A page or size that is not a number ends in a jakarta.el.ELException (Cannot convert [x] of type [class java.lang.String] to [int]), because the parameters feed begin and end directly. A page beyond the last, ?page=9, gives an empty list with the heading "Page 9 of 2". And the servlet had to load every book to show four of them, which is fine for an in-memory list and a disaster for a table with a million rows. The Math.ceil call uses the EL 3.0 rule that the classes of java.lang are imported by default; it needs no tag.

Paging in the Servlet, the View Only Loops

The design that scales takes the slice before the view: the servlet validates the page and size, asks the data source (a SQL LIMIT/OFFSET, a Spring Data Pageable, a subList) for one page, and puts only that page in the request. The view then has no begin or end at all, because the list is already the page.

PagedServlet, validating the parameters and taking the slice (the data and imports omitted)
@WebServlet("/paged")
public class PagedServlet extends HttpServlet {
    private static final int MAX_SIZE = 50;

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        List<Book> all = /* the six books */;
        int size = clamp(parse(req.getParameter("size"), 4), 1, MAX_SIZE);
        int pages = Math.max(1, (all.size() + size - 1) / size);
        int page = clamp(parse(req.getParameter("page"), 1), 1, pages);
        int from = (page - 1) * size;
        req.setAttribute("books", all.subList(from, Math.min(from + size, all.size())));
        req.setAttribute("from", from);
        req.setAttribute("page", page);
        req.setAttribute("pages", pages);
        req.setAttribute("size", size);
        req.getRequestDispatcher("/WEB-INF/views/paged.jsp").forward(req, resp);
    }

    private static int parse(String value, int fallback) {
        try {
            return Integer.parseInt(value);
        } catch (NumberFormatException e) {
            return fallback;
        }
    }

    private static int clamp(int value, int min, int max) {
        return Math.max(min, Math.min(max, value));
    }
}

c:forTokens

c:forTokens splits a string and repeats its body once per token. It has the same begin, end, step, var and varStatus attributes as c:forEach, with two more that matter: items is the string, and delims is the set of delimiter characters.

Table 6. The attributes of c:forTokens that differ from c:forEach
Attribute Required Meaning

items

yes

the string to split. A null value iterates zero times

delims

yes

the characters that separate tokens; every character in the string is a delimiter on its own. A null value makes the whole items a single token

Source: Jakarta Standard Tag Library 3.0 — c:forTokens

The tokens come from a java.util.StringTokenizer built with items and delims, as the specification states. Two properties follow from that. delims is a set of characters, not a separator string, so delims=", " splits at a comma and at a space and not at the two characters together. And a token is "a maximal sequence of consecutive characters that are not delimiters": two delimiters in a row do not produce an empty token between them. The empty field in scifi, classic;cyberpunk,,romance disappears, and so does the space after the first comma, because the space is a delimiter too.

simple:         <c:forTokens var="t" items="a,b,c" delims=",">[${t}]</c:forTokens>
two delimiters: <c:forTokens var="t" items="${tags}" delims=",; ">[${t}]</c:forTokens>
range:          <c:forTokens var="t" items="${tags}" delims=",; " begin="1" end="2">[${t}]</c:forTokens>
step:           <c:forTokens var="t" items="${tags}" delims=",; " step="2">[${t}]</c:forTokens>
null delims:    <c:forTokens var="t" items="${tags}" delims="${nothing}">[${t}]</c:forTokens>
null items:     <c:forTokens var="t" items="${nothing}" delims=",">[${t}]</c:forTokens>(nothing)

Nested Loops and the Scope of var

A loop inside a loop is the normal way to show grouped data. The servlet builds a Map<String, List<Book>>; the outer loop walks the entries and the inner loop walks each entry’s list. Each loop has its own varStatus, which is how a heading can say "1. fiction" and the rows below it "1.1", "1.2" and so on.

${outer.count}. ${entry.key} (${entry.value.size()} books)
<c:forEach var="b" items="${entry.value}" varStatus="inner">
   ${outer.count}.${inner.count}: ${b.title} (${b.price})
</c:forEach>

The specification adds a warning that matters for names. The nested variable always goes in page scope, and a variable with the same name in another scope may or may not be affected, depending on the container, which is why page authors should avoid the same name in different scopes. inside: 1,2

The loop used the name b while a page-scope b already existed, and when the loop ended the page-scope variable was gone: it was not restored to "outer value". The request-scope b was untouched. samevar.jsp

The inner loop overwrote x and, when it finished, removed it, so the outer x is empty after the inner loop although the outer loop is still running. Choose distinct names for every loop in a view, including the varStatus names, and a var name that no other attribute uses.

Deferred Expressions in items

The specification has a section for items written as a deferred expression, #{customer.children}. The reason is Jakarta Faces: a component such as h:inputText inside the loop needs the iteration variable as a deferred value with the right index, and the tag can only provide that when it sees the original expression. The specification also notes that the number of items must be the same when Faces builds the component tree and when the loop runs. In a plain JSP page there is no such component, and an immediate ${books} is what to write. For the record, items="#{books}" is accepted by the 3.0.1 implementation on Tomcat 11.0.26 and prints the same six books (observed: 123456 for ${b.id}), so a deferred items does not fail in a JSP page, but it gains nothing there.

Source: Jakarta Standard Tag Library 3.0 — 6.1.6 Deferred Values

Tag Collaboration and Custom Loop Tags

c:forEach implements jakarta.servlet.jsp.jstl.core.LoopTag, and its status object is the LoopTagStatus described above. This is what the specification calls tag collaboration: a custom tag in the body of the loop can find the loop with TagSupport.findAncestorWithClass(this, LoopTag.class) and ask it for the current item (getCurrent()) or the status (getLoopStatus()) without the page author passing anything. The specification’s example is a pair of tags, acme:odd and acme:even, that print their body only on odd or even rounds, replacing a c:choose on ${status.count % 2 == 0}. The same interface lets a developer write a new iteration tag that collaborates in the same way: the base class LoopTagSupport does the bookkeeping of begin, end, step, var and varStatus, and the subclass only supplies the items (prepare(), hasNext() and next()). The LoopTag Javadoc warns not to confuse the interface with the Pages interface jakarta.servlet.jsp.tagext.IterationTag; they are different things. How to write a tag that uses either one is the subject of the classic and SimpleTag custom tag pages of this section.

Source: Jakarta Standard Tag Library 3.0 — 6.1.5 Tag Collaboration

Security and Performance

Two things go wrong with loops in views, and both have the same cause: letting the request decide how much work the page does.

  • Request-controlled limits. In c:forEach begin="1" end="${param.n}" the loop count is whatever the visitor sends. The counted form (no items) has no collection to stop it: ?n=100000 printed 100,000 stars (a body of 100,002 bytes with the line breaks) in a single request on Tomcat 11.0.26, and a larger value costs proportionally more time and bandwidth. Validate and clamp the number in the servlet, as PagedServlet does with MAX_SIZE, and do not feed a raw parameter to end.

  • Unescaped output. The Expression Language writes a value as it is. ${b.title} in an HTML page breaks the markup for a title such as Fish & Chips and runs script for a title that contains a tag. Inside a loop, which repeats the mistake for every row, use c:out (which escapes <, >, &, ' and " by default) or the escaping the application standardises on. The worked example does this for every title and author.

  • Work in the view. A loop that calls a method per item, a lazy association per item or a query per item is the N+1-queries problem in its worst place, because the view hides it. Load what the page needs in the servlet or a service and hand it over as plain beans or records.

  • Memory. c:forEach over a 100,000-element list is just 100,000 iterations of the body, but the list has to exist first. Page before the view (see paging in the servlet) instead of paging inside it.
