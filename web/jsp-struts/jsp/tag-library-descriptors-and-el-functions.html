Tag Library Descriptors & EL Functions

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Pages 4.0 (chapter 7 "Tag Extensions", section 2.11 "Functions" and section 3.2 "Taglib Map"), Jakarta Standard Tag Library 3.0 (chapter 14 "Tag Library Validators"; API jakarta.servlet.jsp.jstl:jakarta.servlet.jsp.jstl-api 3.0.2, implementation org.glassfish.web:jakarta.servlet.jsp.jstl 3.0.1), Jakarta Expression Language 6.0 and Jakarta Servlet 6.1, running on Apache Tomcat 11.0.26 and Java 21. Everything was verified on 2026-10-08: the rules against the Pages 4.0 specification and the TLD XML Schema web-jsptaglibrary_4_0.xsd, and every example by building it into a Maven WAR (context path /g6tld, with the tag handlers split between the WAR and a small tag-library JAR) and running it on Tomcat 11.0.26 with curl; the outputs and error messages shown are the ones that run produced. A Tag Library Descriptor is the contract between a tag library and the JSP container: an XML file that names the library (its URI and preferred prefix), lists the tags with their handler classes, attributes, body types and variables, lists the EL functions with the static methods that implement them, and optionally names a validator and listeners. The container reads it at translation time, long before any request, and uses it to check every use of the library; page authors and tools read the same file. The running scenario is the Bookshelf, a small catalogue of books; the library bs below has a rating tag, a newest tag and a handful of functions. Writing the handler classes themselves is covered by the two custom-tags pages of this section (simple tag handlers and classic tag handlers) and tag files by Tag Files & Layouts; this page covers what surrounds them: the descriptor, its discovery, its packaging and its validation.

What a Tag Library Descriptor Is and Who Reads It

A tag library is a collection of actions (and, since JSP 2.0, EL functions) made available to a page by a taglib directive that names the library by a URI and chooses a prefix. The URI is only an identifier: it "may be any valid URI as long as it can be used to uniquely identify the semantics of the tag library", and it is not downloaded. The descriptor is the XML document that stands behind it. It has the file extension .tld, and the specification gives it five consumers.

Table 1. Who uses the descriptor and for what
Reader What it takes from the descriptor

The JSP container, at translation time

The URI to descriptor mapping, the handler class of every tag, the attributes (names, required, request-time or not, type), the body type, the scripting variables, the function signatures, the validator and the listeners. It enforces "all constraints described in the TLD" before it generates any Java: a page that breaks them is not compiled

The JSP container, at start-up

The listener elements: the container instantiates and registers the listeners of every descriptor it finds, before the application starts

Page authors

The URI, the suggested prefix (short-name), the descriptions and examples

Authoring tools and IDEs

Everything above plus the tool-only taglib-extension, tag-extension and function-extension elements, which "must not affect the behavior of a container"

Other tag libraries and frameworks

The same file, read without loading a single class, because the descriptor "can be read by tools without instantiating objects or loader classes"

Source: Jakarta Pages 4.0 — 7.3 The Tag Library Descriptor

Three pieces cooperate. The taglib directive in the page gives a URI and a prefix; the descriptor says what the library contains; and the Java classes (tag handlers, functions, a validator, TagExtraInfo classes, listeners) do the work. The classes fall in two groups with different lifetimes: those instantiated at translation time (TagLibraryValidator, TagExtraInfo) and those instantiated at request time (tag handlers). Both must be reachable from WEB-INF/classes or a JAR in WEB-INF/lib, and the translation-time class loader sees the same classes as the request-time one.

Source: Jakarta Pages 4.0 — 7.2.2 Location of Java Classes

The Schema and the Skeleton of a Descriptor

Since JSP 2.0 the descriptor is described by an XML Schema. For Jakarta Pages 4.0 it is https://jakarta.ee/xml/ns/jakartaee/web-jsptaglibrary_4_0.xsd, in the namespace https://jakarta.ee/xml/ns/jakartaee; the version attribute of the root taglib element is required and fixed to 4.0 in that schema (the 3.0 and 3.1 schemas exist next to it and fix 3.0 and 3.1). The root element is a sequence, in this order: the description group (description, display-name, icon), tlib-version, short-name, uri, validator, listener, tag, tag-file, function and taglib-extension.

Table 2. The children of taglib in web-jsptaglibrary_4_0.xsd
Element Meaning

description, display-name, icon

Human and tool information; all optional

tlib-version

Required. The version of the library itself as a dewey decimal (1.0), not the JSP version

short-name

Required. A mnemonic name that tools use as the preferred prefix; "do not use white space, and do not start with digits or underscore"

uri

Optional. The public URI that identifies the library; it is what the implicit map of the container is built from (see below), and "leave it empty if it does not apply"

validator

Optional, at most one. A TagLibraryValidator class with initialisation parameters

listener

Zero or more. Servlet event listener classes shipped with the library

tag

Zero or more. A tag implemented by a Java handler class

tag-file

Zero or more. A tag implemented by a tag file, located by path

function

Zero or more. An EL function implemented by a public static method

taglib-extension

Zero or more. Tool-only extension elements

The names of tag and tag-file elements share one namespace (the schema declares name unique across both), and function names are unique among functions. A minimal descriptor, the head of the Bookshelf library, looks like this.

WEB-INF/tlds/bookshelf.tld, the header
<?xml version="1.0" encoding="UTF-8"?>
<taglib xmlns="https://jakarta.ee/xml/ns/jakartaee"
        xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
        xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-jsptaglibrary_4_0.xsd"
        version="4.0">
    <description>Bookshelf tags and EL functions.</description>
    <display-name>Bookshelf</display-name>
    <tlib-version>1.0</tlib-version>
    <short-name>bs</short-name>

Source: Jakarta Pages 4.0 — 7.3.1 Identifying Tag Library Descriptors

Tomcat 11.0.26 did not reject a descriptor that breaks the schema. A descriptor in the old namespace http://java.sun.com/xml/ns/javaee with version="2.1" and an element the schema does not know (jsp-version) was read without a message and its function ran (the page t-oldns of the verification WAR printed A). That is convenient for old libraries and unhelpful for new ones: a misspelt element is not reported, it is simply ignored, so a tag library author should check the descriptor against the schema in the build. The XML Schema and the XML text are also the contract for tools, which are stricter than Tomcat.

The tag Element

A tag element describes one action that is implemented by a Java class. The 4.0 schema fixes the order of its children: the description group, name, tag-class, tei-class, body-content, variable, attribute, dynamic-attributes, example and tag-extension.

Table 3. The children of tag
Element Meaning

name

The action name used after the prefix: rating in bs:rating. An NMTOKEN, unique in the library

tag-class

Required. The class that implements jakarta.servlet.jsp.tagext.JspTag: a SimpleTag or a classic Tag

tei-class

Optional. A TagExtraInfo subclass consulted at translation time for scripting variables and extra validation; "if this is not given, the class is not consulted"

body-content

Required, no default since JSP 2.0. empty, scriptless, tagdependent or JSP; see below

variable

Zero or more. Scripting-variable information stated directly in the descriptor

attribute

Zero or more. The attributes the tag accepts

dynamic-attributes

true if the handler also accepts attributes with names the descriptor does not list; the handler must implement jakarta.servlet.jsp.tagext.DynamicAttributes

example

An informal example for tools
Table 4. The four body-content values
Value The body of the tag

empty

Must be empty; the container rejects any body (and <bs:rating value="3">text</bs:rating> fails to translate)

scriptless

May contain template text, EL and action elements, but no scripting elements. "A reasonable default for simple tag handlers" when the tag can have a body

JSP

May contain any JSP syntax including scriptlets. Only classic tag handlers can use it

tagdependent

Is not interpreted as JSP at all: its text is passed to the handler uninterpreted (an embedded query language, for instance)

The next listing is the handler class of the rating tag. It is a plain SimpleTagSupport subclass; its properties are the attribute names, so the container calls setValue and setMax before doTag.

bookshelf/RatingTag.java
public class RatingTag extends SimpleTagSupport {
    private int value;
    private int max = 5;

    public void setValue(int value) { this.value = value; }
    public void setMax(int max) { this.max = max; }

    @Override
    public void doTag() throws JspException, IOException {
        if (value < 0 || value > max) {
            throw new JspTagException("rating " + value + " is outside 0.." + max);
        }
        getJspContext().getOut().write("★".repeat(value) + "☆".repeat(max - value));
    }
}

Attributes: required, rtexprvalue, type, fragment and Deferred Values

Each attribute child describes one attribute. The schema fixes the order: description, name, required, then either the group rtexprvalue, type and one of deferred-value or deferred-method, or the single element fragment.

Table 5. The children of attribute
Element Meaning

name

The attribute name, a Java identifier; it must match a setter of the handler (value needs setValue)

required

true or false; the default is false

rtexprvalue

Whether the value may be computed at request time: a scriptlet expression or, as the specification puts it in section 1.14.1, an EL expression ${...} or #{...}. The default is false: the value is a constant fixed at translation time

type

The Java type of the value; java.lang.Object if omitted, and int, boolean and the other primitives are legal (the container converts string constants and EL results)

fragment

true if the attribute is a jakarta.servlet.jsp.tagext.JspFragment: dynamic content the handler can evaluate as often as it needs; it is mutually exclusive with rtexprvalue, type and the deferred elements, and since a fragment attribute is always translated as a fragment it cannot hold a scriptlet expression

deferred-value

The value is passed to the handler as a jakarta.el.ValueExpression, evaluated by the handler (the optional type child is the type it will be coerced to; Object by default). #{...} expressions are the usual form

deferred-method

The value is passed as a jakarta.el.MethodExpression; the optional method-signature child gives its signature (void method() by default)

Section 1.14.1 states the rule that makes rtexprvalue matter: "by default, except in tag files, all attributes have page translation-time semantics. Attempting to specify a scriptlet expression or EL expression as the value for an attribute that (by default or otherwise) has page translation time semantics is illegal, and will result in a fatal translation error."

Scripting Variables and the variable Element

A tag can create a variable for the page. A SimpleTag does it by calling getJspContext().setAttribute(name, value, scope); the descriptor can additionally declare the variable so that scripting elements after the tag see it as a Java local variable. The variable element has the children description, then one of name-given (a constant name) or name-from-attribute (the name of an attribute whose translation-time value is the name of the variable), then variable-class (java.lang.String by default), declare (true by default) and scope, one of NESTED (the default, visible between the start and end tags), AT_BEGIN or AT_END (visible after the end tag).

The handler of the newest tag
public class NewestTag extends SimpleTagSupport {
    private Collection<Book> books;
    private String var;

    public void setBooks(Collection<Book> books) { this.books = books; }
    public void setVar(String var) { this.var = var; }

    @Override
    public void doTag() throws JspException, IOException {
        Book newest = books.stream().max(Comparator.comparingInt(Book::year)).orElse(null);
        getJspContext().setAttribute(var, newest, PageContext.PAGE_SCOPE);
    }
}

Since JSP 2.0 pages should read such variables with EL, and the scriptlet form is on the Scripting Elements (Legacy) page.

TagExtraInfo: Variables and Translation-Time Checks in Java

When the variable’s name or type depends on more than a constant or an attribute value, or when the tag needs a check that a descriptor cannot express, the descriptor names a TagExtraInfo class in tei-class. The container calls getVariableInfo(TagData) to learn the variables (each a VariableInfo with a name, a class name, a declare flag and a scope constant NESTED, AT_BEGIN or AT_END) and validate(TagData) to run extra checks; TagData gives the attribute values that are known at translation time (getAttributeString("var")) and getId() identifies the action. The schema says that a tag with variable children must not have a TagExtraInfo class that returns variables: use one mechanism or the other. Section 7.4.1.3 adds that since JSP 2.0 validate is the preferred method, the older isValid still works, and implementing both is not recommended.

bookshelf/NewestInfo.java
public class NewestInfo extends TagExtraInfo {

    @Override
    public VariableInfo[] getVariableInfo(TagData data) {
        return new VariableInfo[] {
            new VariableInfo(data.getAttributeString("var"), "bookshelf.Book", true, VariableInfo.AT_END)
        };
    }

    @Override
    public ValidationMessage[] validate(TagData data) {
        String var = data.getAttributeString("var");
        if (var == null || !Character.isJavaIdentifierStart(var.charAt(0))) {
            return new ValidationMessage[] {
                new ValidationMessage(data.getId(), "var must be a Java identifier, not [" + var + "]")
            };
        }
        return null;
    }
}

Dynamic Attributes and tag-file Elements

Two more children of the tag library complete the list of ways to define an action.

A tag that mimics an HTML element cannot know in advance which attributes a page author will pass. Setting <dynamic-attributes>true</dynamic-attributes> in the tag element, and implementing DynamicAttributes in the handler, makes the container hand every attribute that is not declared to setDynamicAttribute(uri, localName, value). The bookshelf-ui JAR has a badge tag that copies the extra attributes into a span.

bookshelf/ui/BadgeTag.java, in the bookshelf-ui JAR
public class BadgeTag extends SimpleTagSupport implements DynamicAttributes {
    private final Map<String, Object> extra = new LinkedHashMap<>();
    private String kind = "info";

    public void setKind(String kind) { this.kind = kind; }

    @Override
    public void setDynamicAttribute(String uri, String localName, Object value) {
        extra.put(localName, value);
    }

    @Override
    public void doTag() throws JspException, IOException {
        StringWriter body = new StringWriter();
        if (getJspBody() != null) {
            getJspBody().invoke(body);
        }
        StringBuilder html = new StringBuilder("<span class=\"badge badge-").append(kind).append('"');
        extra.forEach((k, v) -> html.append(' ').append(k).append("=\"").append(v).append('"'));
        html.append('>').append(body).append("</span>");
        getJspContext().getOut().write(html.toString());
    }
}

Functions and EL 6.0 Method Calls

Functions predate the features that now replace many of them. Since EL 2.2 a page can call a method on an object (${book.title.toUpperCase()}), since EL 3.0 it can import a class and call its static methods (${Math.max(a, b)} after an import, see the static access page), and EL 6.0 keeps both. A function declared in a descriptor still has three advantages: it is bound and checked at translation time; it hides which class implements it, so a page author does not need to know or import the class; and it is the only way to offer a library of helpers to pages that run with EL method calls and class imports restricted by configuration (see the EL configuration page). Where the helper belongs to a domain class, a method on that class called from EL is simpler than a function.

How Tomcat Scans and How to Speed It Up

Tomcat finds the descriptors in JARs by scanning the JARs that its JAR scanner is configured to visit (those in WEB-INF/lib first of all) for META-INF/*.tld. Scanning hundreds of JARs that do not contain tag libraries is slow, and Tomcat tells you so with an INFO message logged by org.apache.jasper.servlet.TldScanner: "At least one JAR was scanned for TLDs yet contained no TLDs. Enable debug logging for this logger for a complete list of JARs that were scanned but no TLDs were found in them. Skipping unneeded JARs during scanning can improve startup time and JSP compilation time." The remedy is the Jar Scan Filter of the Context: the tldSkip and tldScan attributes are comma-separated file-name patterns (* and ? wildcards, case-sensitive), defaultTldScan says what happens to JARs that match neither, and the defaults come from the tomcat.util.scan.StandardJarScanFilter.jarsToSkip and jarsToScan properties of conf/catalina.properties. The consequence cuts both ways: a library JAR whose name matches a skip pattern is never scanned and its URI is unresolved, and a JAR that should be scanned but is skipped looks exactly like a missing library.

TagLibraryValidator

A TagLibraryValidator looks at the whole page, through its XML view: the page converted to the XML form that the specification defines for JSP documents (see the JSP documents page). The descriptor names the class and its initialisation parameters; the container instantiates it, calls setInitParameters(Map) with the init-param values and then validate(prefix, uri, PageData) once for every page that imports the library. PageData.getInputStream() is the XML view, and every element in it carries a jsp:id attribute (namespace http://java.sun.com/JSP/Page) that the container assigns, so that a message can point at an element. The method returns null for a valid page or an array of ValidationMessage(id, message) objects.

The Bookshelf validator rejects rating actions whose literal value exceeds a limit the descriptor configures. It reads the XML view with a namespace-aware SAX parser, with DOCTYPE declarations disallowed and secure processing on (the input is generated by the container, but a validator is a parser and should be configured like one).

bookshelf/RatingRangeTLV.java
public class RatingRangeTLV extends TagLibraryValidator {

    private static final String JSP_NS = "http://java.sun.com/JSP/Page";

    @Override
    public ValidationMessage[] validate(String prefix, String uri, PageData page) {
        int allowed = Integer.parseInt(String.valueOf(getInitParameters().getOrDefault("maxAllowed", "5")));
        List<ValidationMessage> problems = new ArrayList<>();
        try (InputStream xml = page.getInputStream()) {
            SAXParserFactory factory = SAXParserFactory.newInstance();
            factory.setNamespaceAware(true);
            factory.setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true);
            factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
            factory.newSAXParser().parse(xml, new DefaultHandler() {
                @Override
                public void startElement(String ns, String local, String qName, Attributes atts) {
                    if (!uri.equals(ns) || !"rating".equals(local)) {
                        return;
                    }
                    String value = atts.getValue("value");
                    if (value != null && value.matches("\\d+") && Integer.parseInt(value) > allowed) {
                        problems.add(new ValidationMessage(atts.getValue(JSP_NS, "id"),
                                "<" + prefix + ":rating> value " + value
                                        + " is above the allowed maximum " + allowed));
                    }
                }
            });
        } catch (Exception e) {
            return new ValidationMessage[] {new ValidationMessage(null, "cannot read the XML view: " + e)};
        }
        return problems.isEmpty() ? null : problems.toArray(new ValidationMessage[0]);
    }
}

The Standard Tag Library implementation JAR already contains two such descriptors, META-INF/scriptfree.tld (URI jakarta.tags.scriptfree, all four parameters false, so even top-level expressions are rejected) and META-INF/permittedTaglibs.tld (URI jakarta.tags.permittedTaglibs). A page that imports the validator library and jakarta.tags.fmt fails with taglib p (https://example.org/jsp/permitted) allows only the following taglibs to be imported: [https://example.org/jsp/bookshelf, https://example.org/jsp/permitted, jakarta.tags.core], and a page that imports only jakarta.tags.core and the validator library printed ok. The validator library’s own URI has to be in the list: a page that imports it has imported it.

Two limits matter. These validators are policy for page authors: they stop a careless scriptlet, not a malicious one (a page that a hostile author controls does not need to import the library at all; the control that holds is to forbid scripting by configuration, scripting-invalid in a property group, or by not letting such authors write JSPs, as the configuration page explains). And they see the page through the XML view, so they check what the page says and not what the EL expressions in it will do. jsp-config is also the natural place to require the validator, as the next listing shows.

A property group whose include-prelude file carries the taglib directive imports the validator library into every page the group matches, so the page author cannot forget it. The verification WAR matched one page with an exact pattern:

    <url-pattern>/WEB-INF/views/pg-bad.jsp</url-pattern>
    <include-prelude>/WEB-INF/prelude-scriptfree.jspf</include-prelude>
</jsp-property-group>
<%@ taglib prefix="sf" uri="https://example.org/jsp/scriptfree" %>

Listeners in a Descriptor

A tag library can ship Servlet event listeners. The listener element holds a listener-class, and the container, which is "required to locate all TLD files, read their listener elements, and treat the event listeners as extensions of those listed in web.xml", instantiates and registers them before the application starts. The order among them is undefined, and resource injection works in them as it does in tag handlers. The Bookshelf listener leaves a marker in the application scope.

bookshelf/TldListener.java
public class TldListener implements ServletContextListener {
    @Override
    public void contextInitialized(ServletContextEvent event) {
        event.getServletContext().setAttribute("bookshelfTldListener", "started by the tag library");
    }
}
WEB-INF/tlds/bookshelf.tld, the listener element (after validator, before the first tag)
<listener>
    <listener-class>bookshelf.TldListener</listener-class>
</listener>

The page functions.jsp ends with <p>listener: ${applicationScope.bookshelfTldListener}</p> and printed <p>listener: started by the tag library</p>: the listener ran with no entry in web.xml and no annotation. That is useful for a library that needs to initialise itself (a cache, a bundle, a registry), and a supply-chain consideration for everybody else: any JAR dropped in WEB-INF/lib with a descriptor and a listener element runs code at start-up, without being named anywhere in the application’s own configuration. Review a library’s descriptors as well as its classes.

Source: Jakarta Pages 4.0 — 7.1.9 Event Listeners

Tool Extensions

The descriptor has three extension points, taglib-extension on the library, tag-extension on a tag or tag file and function-extension on a function, for information that only tools use (the specification’s example is a fictitious company that attaches sound files to tags). The contract protects portability: "JSP containers must not alter their behavior based on the content, the presence, or the absence of a particular Tag or Tag Library Extension Element", and a library whose extension element says mustUnderstand="true" is invalid, so "any attempt to use an invalid tag library must produce a translation error". An extension is declared by importing an XML namespace into the descriptor; nothing about it reaches a running page.

Source: Jakarta Pages 4.0 — 7.3.10 Tag and Tag Library Extension Elements

Customising a Library at Deployment

Section 7.5.3 admits that there is "no convenient place in web.xml" for the settings of a tag library (the specification’s example is a database login) and suggests that a library author put them "in a well-known location at some resource in the WEB-INF/ portion of the Web Application" and read them with ServletContext.getResource. That advice is from the JSP 1.x era and predates context-param conventions, @Resource injection and the container’s own configuration. Today a library reads context parameters or JNDI entries (the Standard Tag Library does it with its jakarta.servlet.jsp.jstl.* context parameters, see the internationalisation page), and never stores credentials in a descriptor, in web.xml or in the WAR: they come from the environment or from the container.

Source: Jakarta Pages 4.0 — 7.5.3 Customizing a Tag Library

In practice, moving a library from Java EE to Jakarta EE touches three things: the Java imports in handlers, validators and TagExtraInfo classes (javax.servlet.jsp becomes jakarta.servlet.jsp), the descriptor namespace and schema location if the descriptor uses the old ones (Tomcat 11.0.26 accepted a 2.1 descriptor in the old namespace, so the change is for tools and for tidiness), and, for libraries compiled against BodyTag.EVAL_BODY_TAG, the recompilation against EVAL_BODY_BUFFERED. The URIs of the Standard Tag Library moved from http://java.sun.com/jsp/jstl/* to jakarta.tags.*; on Tomcat 11.0.26 with JSTL 3.0.1 the old http://java.sun.com/jsp/jstl/core URI still resolved (legacy-uri printed OK in the verification WAR), because the JSTL JAR still ships the old descriptors. They are identifiers, not links.

Where the Books Are Outdated

  • Web Development with JavaServer Pages (2nd edition, 2001) teaches classic tag handlers and the JSP 1.2 descriptor: a DTD document type declaration, tlibversion, jspversion, shortname, tagclass, bodycontent, and a taglib map directly under web-app in a Servlet 2.3 web.xml. The element names of the 1.2 DTD (tagclass, bodycontent, tlibversion) are read by Tomcat 11.0.26 (a 1.2 descriptor with <tagclass> worked in the verification WAR), but they are the old form; current descriptors use tag-class, body-content and tlib-version, the Jakarta namespace and a schema, and the taglib map belongs in jsp-config. Its rtexprvalue and TagExtraInfo material still applies. Its default of JSP for bodycontent no longer exists.

  • The same book’s chapter on validating tag libraries is current in its mechanics (TagLibraryValidator, PageData, ValidationMessage, jsp:id, descriptors packaged under META-INF) and outdated in its package names: the validator classes live in jakarta.servlet.jsp.tagext now.

  • JSTL in Action (2002) describes JSTL 1.0 and its _rt twin libraries (c_rt, fmt_rt, …​), which exist so that the tags can take Java expressions; since JSP 2.0 the EL works in every request-time attribute and the twins are gone from jakarta.tags.*. It shows custom tags that evaluate EL manually with Jakarta Taglibs' ExpressionEvaluatorManager; today a handler declares the attribute type and the container converts. Its ScriptFreeTLV and PermittedTaglibsTLV chapter is still accurate for the classes; the package is jakarta.servlet.jsp.jstl.tlv and the URIs of its examples are jakarta.tags.*.

  • Both books install libraries with descriptors in WEB-INF and entries in web.xml; since JSP 1.2 the uri element and the implicit map make the entry unnecessary, and the JAR is simply dropped in WEB-INF/lib.

  • Neither book covers tag-file, dynamic-attributes, fragment attributes or EL functions (JSP 2.0 and later), and they predate the deprecation of scripting, so they use scripting variables and variable elements where today’s pages use EL.

  • Tutorials that still write <%@ taglib uri="/WEB-INF/tlds/foo.tld" prefix="foo" %> are using the fallback path rule of section 7.3.6. It works, but a stable uri is the form to use.

Official Documentation Inconsistencies

The specifications' own examples and statements need attention; the discrepancies were found by comparing them with the schema and by running them.

  • Chapter 14 of the Tags 3.0 specification shows descriptors with <jsp-version>2.0</jsp.version> (the end tag does not match the start tag, so the document is not well formed), <short-name>jstl taglibs only</scriptfree> (again a mismatched end tag, and a short name with white space, which the schema forbids), and an element jsp-version that does not exist in the 3.0 or 4.0 schema. Copying them verbatim gives a parse error; the version="3.0" attribute of the root is what states the JSP version. Tomcat ignores an unknown jsp-version element in a well-formed descriptor.

  • The same chapter lists the classes as jakarta.servlet.jsp.jstl.tlv.ScriptFree and ...PermittedTaglibs in the overview and as ScriptFreeTLV and PermittedTaglibsTLV in the examples. The classes are ScriptFreeTLV and PermittedTaglibsTLV.

  • Section 7.3.1 of the Pages 4.0 specification still gives the schema as http://java.sun.com/xml/ns/j2ee/web-jsptaglibrary_2_1.xsd, and section 7.3.10’s example uses the javaee namespace and version="2.1"; the schema of Pages 4.0 is https://jakarta.ee/xml/ns/jakartaee/web-jsptaglibrary_4_0.xsd.

  • Section 7.2.3 says "it is a fatal translation error for a URI attribute value to resolve to two different TLD resource paths". Two .tld files in WEB-INF/tlds with the same uri were accepted by Tomcat 11.0.26 without a message, and the second one won. The order of the search is "implementation-specific and should not be relied on", so the winner is not a feature.

  • Section 2.11.2 says a function method that is not public static is a translation-time error. Tomcat 11.0.26 reported it at request time (see "How a Function Call Is Resolved").

  • The XML Schema comment for the rtexprvalue element speaks of "scriptlet expressions"; the same property controls EL expressions as well (section 1.14.1).
