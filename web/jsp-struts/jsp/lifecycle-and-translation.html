JSP Lifecycle and Translation

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Jakarta Pages 4.0 (Jakarta EE 11), together with Jakarta Servlet 6.1, Jakarta Expression Language 6.0 and Jakarta Standard Tag Library 3.0, as implemented by Apache Tomcat 11.0.26 (the Jasper engine) on Java 21. Everything was verified on 2026-10-08: the facts against the Pages 4.0 specification, the HttpJspPage and JspPage Javadoc and the Tomcat 11 Jasper documentation, and every example by building it into a Maven WAR (g3lifecycle.war) and running it on Tomcat 11.0.26 with curl; the outputs, generated sources and log lines shown are the ones that run produced. A JSP page is not interpreted. The container translates it into the source of a Java servlet class, compiles that class, loads it, creates one instance and calls it from many threads, and this page follows that path step by step: the two phases the specification defines, the three methods of the page contract, the generated servlet read straight from the work/ directory, the threading model that follows from a single instance, how and when the class is rebuilt, how errors are mapped back to JSP lines, how the response is buffered, and how to translate pages ahead of time. The running scenario is the Bookshelf, a small catalogue of books, here reduced to the pages that make the lifecycle visible.

A JSP Page Is a Servlet in Waiting: Two Phases

The specification describes the life of a page as two phases. In the translation phase the container validates the page (and the tag files and tag libraries it uses) and determines the JSP page implementation class that corresponds to it. In the execution phase the container manages one or more instances of that class in response to requests and other events. The specification allows translation at any moment between the deployment of the page and the processing of the first client request, and deliberately leaves the choice open as a quality-of-service decision of the container. Tomcat translates lazily, on the first request, unless the page is declared with load-on-startup (shown below), and rebuilds the class when the source changes.

The Contract: JspPage, HttpJspPage and the Three Methods

Chapter 11 of the specification defines the contract between a JSP container and the class that implements a page. It corresponds to the Servlet interface, extended by two interfaces in jakarta.servlet.jsp: JspPage (generic) and HttpJspPage (the HTTP form every page uses). Of the three methods of the contract, only two can be written by the page author.

Table 2. How the JSP container processes a page (specification Table JSP.11-1 with the observed Tomcat behaviour)
Method Who writes it Contract and observed behaviour

void jspInit()

Optional, in a declaration (<%! ... %>)

Called once when the page is initialised; every method of the servlet, including getServletConfig, is already usable. In Tomcat HttpJspBase.init(ServletConfig) calls jspInit() first, then the generated _jspInit()

void jspDestroy()

Optional, in a declaration

Called before the page is destroyed, at a time when no request is being serviced. HttpJspBase.destroy() calls jspDestroy(), then _jspDestroy()

void _jspService(HttpServletRequest, HttpServletResponse)

Never: generated by the container

The body of the page; invoked on every request. HttpJspBase.service(...) calls it. The Javadoc says the page author must never define it

Three details of that table matter in practice:

  • init, destroy and service are not available for redefinition. The JspPage Javadoc tells a page to redefine init() and destroy() from Servlet, but Tomcat’s HttpJspBase declares init, destroy and service as final (verified with javap), so only jspInit and jspDestroy can be overridden in a declaration. This is an inconsistency in the Javadoc, recorded in the section’s errata.

  • The page is its own servlet. getServletConfig().getServletName() returns jsp for a page reached by its path (it is served by Tomcat’s default jsp servlet), and the name given in web.xml when the page is declared as a servlet with <jsp-file> (shown below). info in the page directive becomes the return value of getServletInfo().

  • Names of the form jsp_* and jspx_*, with or without a leading underscore and in any combination of upper and lower case, are reserved by the specification (section 9.1.2). A declaration must not define such a name: the generated class already uses them for its own fields and methods.

By default the generated class extends a container-specific base class (org.apache.jasper.runtime.HttpJspBase in Tomcat), which implements HttpJspPage. The extends attribute of the page directive replaces that superclass; the author then guarantees that the replacement supports the contract. Almost nobody needs it, and it is covered with the other attributes on the Directives page of this section.

One Instance, Many Threads

The generated class is a servlet and the container creates a single instance of it (specification section 2.2 of the Servlet specification: one instance per declaration unless the application is distributable), so every request to lifecycle.jsp runs _jspService on that same object, on a different thread. The consequences follow directly from the translation table above:

  • Variables declared in a scriptlet are locals of _jspService: each thread has its own copy. They are safe.

  • Fields declared in a <%! %> declaration are fields of the shared instance. They are shared mutable state, as in any servlet, and need the same care (synchronized, atomic types, or no mutation after jspInit).

  • The implicit objects request, response, out, session and pageContext are locals as well; application and config are locals initialised from the shared servlet context and configuration.

  • The page-scope attributes belong to a PageContext created for the request and released at its end, not to the instance.

The example above increments hits inside synchronized (this). Forty parallel requests against it (twenty at a time, with xargs -P 20) leave the counter exactly where it should be, on one instance:

curl -s http://localhost:18080/g3lifecycle/lifecycle.jsp | grep instance=

(hits=43 is the two earlier requests plus the forty parallel ones plus this last one.)

The old escape hatch for a page that was not thread safe, <%@ page isThreadSafe="false" %>, made the container serialise requests with the SingleThreadModel interface. That interface was deprecated for years and was removed in Servlet 6.0, and the attribute was deprecated in Pages 3.1 and removed in Pages 4.0. On Tomcat 11 it is a translation error:

org.apache.jasper.JasperException: /threadsafe.jsp (line: [1], column: [2]) [Page directive] has invalid attribute: [isThreadSafe]

The replacement is design, not configuration: keep state out of instance fields, or protect it.

When a Page Is Translated: First Request, Startup and Servlet Declarations

By default Tomcat translates a page on the first request that reaches it (the first hit pays for translation and compilation; the instance created then serves all the others). A page can be moved to deployment time by declaring it as a servlet with <jsp-file> and <load-on-startup>, which also lets web.xml give it a name, initialisation parameters and its own URL mapping.

A page declared as a servlet, translated when the application starts (WEB-INF/web.xml)
<servlet>
    <servlet-name>bookshelf-warmup</servlet-name>
    <jsp-file>/WEB-INF/views/warmup.jsp</jsp-file>
    <init-param>
        <param-name>greeting</param-name>
        <param-value>Hello from web.xml</param-value>
    </init-param>
    <load-on-startup>1</load-on-startup>
</servlet>
<servlet-mapping>
    <servlet-name>bookshelf-warmup</servlet-name>
    <url-pattern>/warmup</url-pattern>
</servlet-mapping>
<%@ page contentType="text/plain; charset=UTF-8" %>
name=<%= getServletConfig().getServletName() %> greeting=<%= getServletConfig().getInitParameter("greeting") %>
curl -s http://localhost:18080/g3lifecycle/warmup
name=bookshelf-warmup greeting=Hello from web.xml

The generated file for warmup.jsp carries the header Generated at: 2026-10-08 11:02:36 UTC, the moment the application was deployed, while lifecycle_jsp.java, which was only requested later, carries 11:02:40: translation happened at deployment for the first and at request time for the second. Pages under WEB-INF (as here) cannot be requested directly by a client; only the mapping /warmup reaches this one, which is the right place for views. Two other things to know about the container’s page management:

  • A page that is not used does not have to stay loaded: Tomcat’s jspIdleTimeout (seconds, default -1, never) unloads idle pages and maxLoadedJsps (default -1, unlimited) keeps only the most recently used ones; unloading destroys the instance, so jspDestroy runs, and a later request creates a new instance and calls jspInit again.

  • Which files are treated as pages (the *.jsp and *.jspx mappings of Tomcat’s default jsp servlet, and jsp-property-group patterns) belongs to the Configuration and Property Groups page of this section.

Recompilation: What Changes a Class and When Tomcat Notices

In development mode (the Jasper parameter development, default true) Tomcat checks a page for changes when it is requested, but not more often than modificationTestInterval seconds (default 4); a value of 0 checks on every access. When the source, or a file the page depends on, is newer than the compiled class, the page is translated and compiled again, the old instance is destroyed (jspDestroy) and a new instance of the new class is created (jspInit). The experiment below changes hello.jsp on disk, five seconds after the previous request:

<%@ page contentType="text/plain; charset=UTF-8" %>
Hello version one
curl -s http://localhost:18080/g3lifecycle/hello.jsp
# edit hello.jsp in the exploded web application: "version one" becomes "version two"
curl -s http://localhost:18080/g3lifecycle/hello.jsp
Hello version one
Hello version two

The generated hello_jsp.java was rewritten (out.write("Hello version two\n")) and its Generated at header moved. Editing lifecycle.jsp the same way produced the log pair that shows what recompilation does to a page’s state: the old instance reported jspDestroy after 43 hits, the new instance reported jspInit, instance 157172844, and the counter on the page started again at hits=1. A page that keeps data in an instance field therefore loses it whenever the page is edited, a second reason (after concurrency) to keep state out of declarations.

Dependencies are tracked too. composed.jsp includes footer.jspf with the static include directive, and the footer is listed in _jspx_dependants. Editing only the footer (after the interval) made the next request to composed.jsp show footer version two: the including page was translated again, because a static include is part of its translation unit. Editing only hello.jsp, which composed.jsp includes with jsp:include, did not recompile composed.jsp at all; hello.jsp was rebuilt on its own the next time it was served.

Translation Errors Versus Request-Time Errors, and Line Mapping with SMAP

Because translation and compilation happen on the first request, a mistake in a page is not reported at deployment but to the first client. The two kinds of failure look different, and both are mapped back to lines of the page.

A translation or compilation error is a JasperException with the heading Unable to compile class for JSP:

A page with a Java error in a scriptlet (broken.jsp)
<%@ page contentType="text/html; charset=UTF-8" %>
<html>
<body>
<% int total = ; %>
</body>
</html>
HTTP Status 500 – Internal Server Error
org.apache.jasper.JasperException: Unable to compile class for JSP:
An error occurred at line: [4] in the jsp file: [/broken.jsp]
Syntax error on token ";", delete this token
1: <%@ page contentType="text/html; charset=UTF-8" %>
2: <html>
3: <body>
4: <% int total = ; %>
5: </body>
6: </html>

The message shows the JSP line and a few lines of context (displaySourceFragment, default true), not the generated Java. A request-time error is an exception thrown while _jspService runs. Here the page dereferences a request parameter that is absent:

A page that fails at request time (runtimefail.jsp)
<%@ page contentType="text/html; charset=UTF-8" %>
<html>
<body>
<h1>Bookshelf</h1>
<%
    String title = request.getParameter("title");
%>
<p>Title length: <%= title.length() %></p>
</body>
</html>
org.apache.jasper.JasperException: An exception occurred processing [/runtimefail.jsp] at line [8]
5: <%
6:     String title = request.getParameter("title");
7: %>
8: <p>Title length: <%= title.length() %></p>
9: </body>
10: </html>
Root Cause: java.lang.NullPointerException: Cannot invoke "String.length()" because "title" is null
        org.apache.jsp.runtimefail_jsp._jspService(runtimefail_jsp.java:130)

Jasper says line 8 of the JSP, but the stack frame in the cause says line 130 of the generated Java. The two numbers are related by the SMAP, the line table that the Jakarta Debugging Support for Other Languages specification defines and that the Pages specification requires of every container (section 11.5): the class file gets a SourceDebugExtension attribute, with a stratum named JSP, mapping lines of the page to lines of the generated class. Tomcat uses it to turn the Java line into the page line in the message, and IDE debuggers use it to step through the page rather than the generated servlet. javap -v shows the table of runtimefail_jsp.class:

SourceDebugExtension:
  SMAP
  runtimefail_jsp.java
  JSP
  *S JSP
  *F
  + 0 runtimefail.jsp
  runtimefail.jsp
  *L
  1,7:121
  7:128
  8:129,3
  9,3:132
  *E

Each *L line reads "input lines a,b map to output starting at line n`": JSP line 8 is output lines 129 to 131, and the failing statement is at 130. The same table is why a debugger breakpoint on line 8 of a JSP works, and why a stack trace of the page in the server log needs the cause section, not the first frames. With `suppressSmap=true Tomcat leaves the table out, and the message falls back to Java line numbers. In development, keep mappedfile on and read the .java in work/ when a page misbehaves in a way the message cannot explain.

Output Buffering: JspWriter, buffer, autoFlush and Commit

The implicit object out is a jakarta.servlet.jsp.JspWriter, a buffered writer that sits between the generated code and the servlet response. Headers are not sent until the response is committed, which happens when the buffer is flushed or, with autoFlush="true", fills up. Until then the page can still change the status, set headers, redirect or call sendError; after that those calls no longer work, exactly as for any servlet. Two attributes of the page directive control it, and a third affects whether the page touches the session at all.

Table 7. Page attributes that decide how a page’s output is buffered (specification section 1.10.1)

none (unbuffered, output goes straight to the response writer) or a size such as 16kb; the kb suffix is mandatory, or translation fails. out.getBufferSize() returns it

autoFlush

true

true flushes the buffer when it fills; false raises an exception on overflow. autoFlush="false" with buffer="none" is a translation error

session

true

If true the page gets the session object, and Tomcat creates the session (and sends a JSESSIONID cookie) the first time a page that does not say otherwise is requested; session="false" makes the session variable unavailable

The Servlet response buffer, which is the layer below JspWriter, is discussed in the Servlet Fundamentals page.

Precompilation: The jsp_precompile Request and Build-Time Translation

The specification gives containers a precompilation protocol (section 11.4). Request parameter names beginning with jsp are reserved; a request to a page with the parameter jsp_precompile is a precompilation request that must not be delivered to the page itself. The parameter may have no value, true or false; true or no value is a suggestion to translate and compile the page, which the container may ignore. Any other value is an error (HTTP 500). Tomcat honours the suggestion and returns an empty 200:

curl -s -w '%{http_code} len=%{size_download}\n' "http://localhost:18080/g3lifecycle/hello.jsp?jsp_precompile=true"
curl -s -o /dev/null -w '%{http_code}\n' "http://localhost:18080/g3lifecycle/hello.jsp?jsp_precompile=foo"
200 len=0
500

After the first call, hello_jsp.java and hello_jsp.class exist in work/ although the page body never ran; the second call produced jakarta.servlet.ServletException: Cannot have precompilation request parameter [jsp_precompile] set to [foo], as the specification requires. This is a way to warm up a deployed application page by page, with a script that requests each page with the parameter. A better one for production is to translate and compile every page during the build (JspC, the Ant <jasper> task, the Jetty JspC Maven plugin) and package the result, which removes the first-request delay and the need for a compiler on the server; the specification describes this in section 1.1.9 and in Appendix A, and the tooling is the subject of the Jasper configuration and precompilation page of this section. Precompilation does not work with every feature (the HowTo points out that jsp-property-group can make it impractical), which is why the production settings above still matter.

Which Engine Does This: Jasper, WaSP and Portability

The lifecycle above is the specification’s; the generated source is Tomcat’s. Tomcat and Jetty implement Pages with Apache Jasper (Jetty names its JSP module apache-jsp), and GlassFish with Eclipse WaSP (eclipse-ee4j/wasp), which uses the Expressly EL implementation. The three produce differently shaped classes, so a page, a tag or a framework must not depend on the class name, the package, the superclass or the helper methods seen above; the supported seams are the HttpJspPage contract, the tag APIs, PageContext and the SMAP. File locations differ too: the work/ directory path shown here is Tomcat’s, so check the container’s own documentation for where it keeps generated sources.
