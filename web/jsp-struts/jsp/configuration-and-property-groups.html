Configuration and Property Groups

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Pages 4.0 (chapter 3, "JSP Configuration"), Jakarta Servlet 6.1 (deployment descriptor, web fragments and ServletContext.getJspConfigDescriptor) and Jakarta Standard Tag Library 3.0 (section 2.8, "Configuration Data"), running on Apache Tomcat 11.0.26 and Java 21. Everything was verified on 2026-10-08: the facts against the specifications, the jsp_4_0.xsd schema and the Javadoc, and every example by building it into a Maven WAR and running it on Tomcat 11.0.26 with curl; the outputs and error messages shown are the ones that run produced. Most of what a JSP page can say about itself, with the page directive, can also be said once for a whole directory or file extension in web.xml: the page encoding, the content type, whether scripting is allowed, whether EL is evaluated, a header and a footer to include in every page. That is the job of the jsp-config element. The running scenario is the Bookshelf, a small catalogue of books whose JSP pages start in a flat directory and are then split into an admin/ area, a legacy/ area and a strict/ area, each with its own settings.

Where JSP Configuration Lives

A web application can carry general JSP configuration in its deployment descriptor, WEB-INF/web.xml, in a single jsp-config element (a child of web-app) with two kinds of children: taglib elements, which map a tag-library URI to a tag library descriptor, and jsp-property-group elements, which attach properties to a set of files. The same element can appear in a web-fragment.xml inside a library JAR; the Servlet specification says that jsp-property-group elements from fragments are additive, and recommends that fragments use path patterns, not extension patterns, together with a subdirectory named after the fragment, so a fragment’s group cannot capture the application’s own JSP files.

The configuration is part of the container contract, not of the JSP engine. Since Servlet 3.0 the servlet container reads jsp-config from web.xml and every fragment and makes it available through ServletContext.getJspConfigDescriptor(); the JSP engine (Jasper in Tomcat, WaSP in GlassFish, Jetty’s Apache JSP) asks the container instead of re-parsing the descriptor. The returned JspConfigDescriptor is read-only: it has getTaglibs() and getJspPropertyGroups() and no setters, so there is no programmatic way to add a property group. Configuration is declarative, in the descriptor.

The element order inside jsp-property-group is fixed by the schema (jsp_4_0.xsd): the description group, one or more url-pattern, then el-ignored, error-on-el-not-found, page-encoding, scripting-invalid, is-xml, include-prelude, include-coda, deferred-syntax-allowed-as-literal, trim-directive-whitespaces, default-content-type, buffer and error-on-undeclared-namespace. Tomcat 11.0.26 does not validate web.xml by default and accepted a group with el-ignored placed before url-pattern (verified), but a validating tool, an IDE or another container may not, so keep the schema order.

The Bookshelf assembles one jsp-config element in the sections that follow. This servlet reads it back and prints it, which is also the quickest way to check what the container really parsed.

A servlet that prints the JSP configuration the container read from web.xml
@WebServlet("/jspconfig")
public class ConfigServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        resp.setContentType("text/plain;charset=UTF-8");
        JspConfigDescriptor cfg = getServletContext().getJspConfigDescriptor();
        for (TaglibDescriptor t : cfg.getTaglibs()) {
            resp.getWriter().printf("taglib %s -> %s%n", t.getTaglibURI(), t.getTaglibLocation());
        }
        for (JspPropertyGroupDescriptor g : cfg.getJspPropertyGroups()) {
            resp.getWriter().printf("group %s elIgnored=%s scriptingInvalid=%s isXml=%s prelude=%s coda=%s%n",
                    g.getUrlPatterns(), g.getElIgnored(), g.getScriptingInvalid(), g.getIsXml(),
                    g.getIncludePreludes(), g.getIncludeCodas());
        }
    }
}

The Taglib Map

A taglib directive names a tag library by URI: <%@ taglib prefix="c" uri="jakarta.tags.core" %>. The container turns that URI into a TLD resource path through the taglib map, a table from URI to a resource path inside the web application. The map is built from several sources, listed here from highest to lowest precedence as the Pages specification states them (section 7.3.2):

Order Source of map entries

1

The tag libraries that are part of the Jakarta EE platform, when the container is platform-compliant: the Jakarta Tags (JSTL) libraries and the Jakarta Faces libraries

2

The explicit taglib elements in web.xml, the subject of this section

3

Implicit entries deduced from the <uri> of every .tld file under WEB-INF and inside the JARs of WEB-INF/lib (TLDs in JARs under META-INF)

4

Implicit entries known to the container itself

Entries 3 and 4 are why you almost never write a taglib element today: a TLD that declares <uri> is found automatically, and so is every library inside a JAR. The explicit map still has two uses. It is the only way to give a tag library a URI that its TLD does not declare, for example an alias or an application-internal name, and it is the way to point a URI at one specific TLD when several candidates exist.

A taglib element has exactly two children. taglib-uri is the URI to be used in taglib directives; it may be an absolute URI or a relative one, and the specification forbids two entries with the same taglib-uri. taglib-location is the context-relative location of the TLD file (or of a JAR with META-INF/taglib.tld).

The Bookshelf keeps a TLD with one EL function and gives it the application-internal name urn:bookshelf:text.

The taglib map entry in web.xml
<jsp-config>
  <taglib>

    <taglib-location>/WEB-INF/tlds/bookshelf.tld</taglib-location>

Property Groups: What They Are

A JSP property group is a collection of properties that apply to a set of files that represent JSP pages. A group is a jsp-property-group element with one or more url-pattern children (which files) and any number of property elements (which settings). Four points of the specification define how groups behave.

  • A group makes its files JSP files. There is an implicit property: every resource that matches a group’s url-pattern is a JSP file, whatever its extension. That is how a file such as cover.svg or page.htm is compiled by the JSP engine instead of being served as a static file (both observed below).

  • Most properties apply to a translation unit. A translation unit is the requested JSP file together with every file it includes through the include directive. The exceptions are page-encoding and is-xml, which apply to each file separately, because an included file may be stored in a different encoding or be an XML document.

  • Groups never affect tag files. A tag file (.tag, .tagx) ignores every jsp-property-group; its settings come from the tag directive in the file.

  • Page-level settings override groups. Where the same property exists as an attribute of the page directive, the attribute in the page wins, except for the conflicts that are translation errors (an encoding named twice with different values, shown below).

Besides these properties a group carries url-pattern and the optional description, display-name and icon of the schema’s description group, which have no effect on the page. The page directive attributes themselves are described on Directives; here only their relation to the groups matters.

URL Patterns, Precedence and Which Group Applies

A group applies to the resources that match any of its url-pattern values. The patterns use the same syntax as the Servlet specification’s chapter 12 (URL mapping), with one difference: they are bound at translation time, against the path of the JSP file, not at request time against the request URL. Three forms are used in practice.

Form Example Matches

Extension

*.jsp, *.jspf, *.svg

Every file with that extension, anywhere in the application

Path prefix

/admin/*, /WEB-INF/views/*

Every file below that directory, at any depth

Exact

/admin/report.jsp

That one file

Mixing a wildcard in the middle of a path is not a valid pattern. Tomcat 11.0.26 refused to start a web application whose group used /buf/*.jsp, with java.lang.IllegalArgumentException: Invalid <url-pattern> [/buf/*.jsp] in servlet mapping in the log; the application then answered 404. To cover the JSP files of one directory, use /buf/*.

Several groups, and the servlet mappings, can all match one file. The Pages specification (section 3.3) says:

  • If a resource matches a servlet-mapping pattern and a group pattern, the most specific pattern applies, with the rules of the Servlet specification: an exact match beats a longest path prefix, which beats an extension.

  • If the patterns are identical, the group wins over the servlet-mapping.

  • If at least one group holds the most specific matching pattern, the resource is a JSP file, and the properties of that group apply.

  • In addition, once the resource is a JSP file, every include-prelude and include-coda of every matching group applies, in the order the groups appear in web.xml.

The wording "the properties of that group apply" suggests that the other matching groups are ignored. Tomcat 11.0.26 does not do that for the ordinary properties: it decides each property separately, taking it from the most specific matching group that declares it. A less specific group’s value therefore still applies when the more specific group is silent about it. The experiments below make the difference visible, and they are the behaviour of Tomcat; a container that follows the sentence literally would give the outcome the specification describes. Declaring in the most specific group every property that matters removes the difference.

Deactivating EL: el-ignored

The sequence ${expr} was not reserved before JSP 2.0, and #{expr} was not reserved before JSP 2.1, so an old page can contain such text with no intention of calling the expression language. The el-ignored property passes both sequences through verbatim for the matching files. The default depends on the version of the descriptor: a web.xml in Servlet 2.3 or earlier format ignores EL (backward compatibility), a Servlet 2.4 or later one evaluates it. Since the Bookshelf descriptor is version="6.1", EL is on, and a group is needed only for the pages that must stay as they are.

The page can override the group with <%@ page isELIgnored="false" %>. Tag files have no default: they always evaluate EL unless the tag directive says isELIgnored="true". The specification states the whole truth table:

Disabling EL is a compatibility tool, not a security control. If the goal is to stop an injected ${...} from being evaluated, remember that the sequence in the source of a page is the author’s, and that EL never re-evaluates request data it prints. The risk of EL is in expressions built from user input, which Security discusses.

Disabling Scripting: scripting-invalid

scripting-invalid set to true makes scriptlets, declarations and expressions a translation error for the matching files. Scripting is on by default. JSP 2.0 introduced the element as an easier replacement for the older practice of enforcing the rule with a tag-library validator (ScriptFreeTLV in the Jakarta Tags TLDs). It is the single most useful hardening switch in the descriptor (Scripting Elements (Legacy) shows what to write instead): a project that has moved to EL and tags can turn scripting off for every page and stop a scriptlet from ever re-entering the code base.

The admin area has no scripting and two more includes
<jsp-property-group>
  <url-pattern>/admin/*</url-pattern>
  <scripting-invalid>true</scripting-invalid>
  <include-prelude>/WEB-INF/jspf/prelude2.jspf</include-prelude>
  <include-coda>/WEB-INF/jspf/coda2.jspf</include-coda>
</jsp-property-group>

<p>count: <%= 1 + 2 %></p>

The error is raised at translation time, so the page fails on the first request (or at precompilation), never in the middle of a response. The setting applies to the whole translation unit, which means that a scriptlet inside a file included with the include directive is rejected too. A tag file is not affected by the group and keeps whatever scripting its own directives allow.

Unknown Identifiers: error-on-el-not-found

By default an EL expression that names an identifier nobody defined resolves to null, and the output is an empty string. That hides typos: ${owner} for a misspelt request attribute looks like an empty field, not a bug. Jakarta Pages 3.1 added an option to raise jakarta.el.PropertyNotFoundException instead. The group element error-on-el-not-found sets it for matching pages; the page directive attribute errorOnELNotFound and the tag directive attribute of the same name override it. Tag files have no group default: they return null unless their own directive says true.

Page Encoding: page-encoding

page-encoding sets the pageEncoding of the files of a group: the character set in which the source files are stored, so the container decodes them correctly. Its valid values are those of the pageEncoding attribute. It matters only for pages in standard syntax; a JSP document in XML syntax takes its encoding from the XML declaration or a byte-order mark. Without any statement the page is read as ISO-8859-1, which is why a UTF-8 file with a non-ASCII title can show mojibake when nothing configures the encoding.

It is a translation-time error to name different encodings in the pageEncoding attribute of a page and in a group that matches the page, and also to name different encodings in the XML declaration of a document and in a matching group. Naming the same encoding twice is legal. A group should therefore be the single place that declares the encoding, and a page that needs a different one must sit in a different group.

One place for the source encoding
<jsp-property-group>
  <url-pattern>*.jsp</url-pattern>
  <page-encoding>UTF-8</page-encoding>
</jsp-property-group>

The response encoding, the request encoding and the byte-order-mark detection algorithm are separate subjects. All of them are covered on Character Encoding, together with default-content-type (below).

Implicit Includes: include-prelude and include-coda

include-prelude and include-coda name context-relative files that the container includes, as if with the include directive, at the start and at the end of every JSP page of the group. They are the configuration equivalent of "every page begins with the same taglib directives and ends with the same footer", and the standard way to remove that boilerplate. Both elements can repeat inside one group, in which case the files are included in the order written.

When more than one group matches a page, the preludes of all of them are included, in the order in which the groups appear in web.xml; the codas likewise, in order. The specification points out that this is unlike the other properties, where a single group’s pattern is selected. A prelude or coda follows the rules of a statically included JSP segment: start and end tags must be in the same file, so a prelude cannot open an HTML element that only the coda closes if that element is built from a JSP tag. The conventional extension for such fragments is .jspf, and the files belong under WEB-INF so they cannot be requested directly.

Two groups that both match /admin/report.jsp, in this order
<jsp-property-group>
  <url-pattern>*.jsp</url-pattern>
  <include-prelude>/WEB-INF/jspf/prelude1.jspf</include-prelude>
  <include-coda>/WEB-INF/jspf/coda1.jspf</include-coda>
</jsp-property-group>
<jsp-property-group>
  <url-pattern>/admin/*</url-pattern>
  <include-prelude>/WEB-INF/jspf/prelude2.jspf</include-prelude>
  <include-coda>/WEB-INF/jspf/coda2.jspf</include-coda>

JSP Documents: is-xml

is-xml marks the files of a group as JSP documents: XML-syntax pages that must be well-formed XML. The default extension .jspx (and .tagx for tag files) already means "document". The element exists for two reverse cases, both shown in the specification: setting is-xml to false for *.jspx to treat those files as ordinary pages, and setting it to true for another extension, such as *.svg, so that a generator of XML output is written as a document. Like page-encoding, it applies per file and not per translation unit. The syntax of documents (jsp:root, jsp:output, namespaces) is the subject of JSP Documents (XML Syntax); here only the switch matters.

Deferred Syntax as Literal: deferred-syntax-allowed-as-literal

From JSP 2.1 the sequence #{ is reserved for deferred EL expressions, so a page that uses it in template text, for example a placeholder such as #{title} meant for a client-side template, fails to translate. The related compatibility rule (spec 3.4) is that #{expr} as the value of a tag attribute is evaluated only when the TLD declares jsp-version 2.1 or later; in a TLD that declares an older version it is a string literal.

Removing Whitespace: trim-directive-whitespaces

Whitespace in template text is preserved, so every taglib directive, every c:set and every blank line between actions adds a line break to the response. trim-directive-whitespaces (default false), or the page attribute trimDirectiveWhitespaces, removes template text that consists only of whitespace. Text that contains anything else is kept exactly. It has no effect on JSP documents. In the specification’s example, two taglib lines followed by Hello World! produce two blank lines without the setting and none with it; in Tomcat 11.0.26 that exact case already printed no blank lines in the test application, so the visible effect is shown below with actions in the page.

Content Type and Buffer: default-content-type and buffer

default-content-type supplies the response content type of the group’s pages when the page has no contentType attribute. Its values are those of the contentType attribute, including the charset. Without it, and without any contentType, Tomcat 11.0.26 answered text/html;charset=UTF-8 in the test application (observed with no group at all); the Pages specification still names ISO-8859-1 as the fallback character encoding for page decoding. Stating the value in a group makes the answer independent of the container’s default, which matters for portability.

buffer sets the buffering of the page’s out writer for the group: the same values as the buffer attribute of the page directive, none or a size in kilobytes such as 32kb. The default is container-specific; Tomcat’s is 8 KB (observed 8192). A larger buffer lets a page set headers, cookies or an error status after producing a lot of output, because nothing is committed until the buffer fills; none makes every write go straight to the response and is rarely what you want.

JSTL Configuration Settings and Context Parameters

The configuration of the standard tag library is a different mechanism from jsp-config, but it lives in the same descriptor and is often needed together, so it is part of this page. Jakarta Tags 3.0 (section 2.8) defines configuration settings: values that change how the actions behave and that can be set in two ways. Application-wide, as a context-param in web.xml whose name is the setting’s name and whose value is a string. For one scope, as a configuration variable stored in the page, request, session or application scope, with the class jakarta.servlet.jsp.jstl.core.Config. A configuration variable overrides the context parameter for as long as its scope lasts. The class hides the real attribute name, so that a variable set in the request scope does not collide with a same-named variable in the session; use Config, never setAttribute, to set them. The actions that read these settings are described on JSTL i18n & Messages and JSTL Formatting.

        req.getRequestDispatcher("/WEB-INF/views/tz.jsp").forward(req, resp);
    }
}
