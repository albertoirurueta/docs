EL Static Access, Records & Optional

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Jakarta Expression Language 6.0 (jakarta.el:jakarta.el-api 6.0.1), Jakarta Pages 4.0, Jakarta Standard Tag Library 3.0 and Jakarta Servlet 6.1, on Java 21 and Tomcat 11.0.26, the container whose Jasper and EL implementation ran every example. Everything was verified on 2026-10-08: the facts against the EL 6.0 and Pages 4.0 specifications and the EL Javadoc, and every example by building it into a Maven WAR and requesting it with curl; the outputs and error messages shown are the ones that run produced. Besides properties of beans, maps and lists, EL can reach four more kinds of thing: the static members of a class (${Integer.MAX_VALUE}, ${Math.max(3, 7)}), the constants of an enum, the length of an array, and the components of a Java record, and it can see through a java.util.Optional if the page or application asks for it. Three of these are ordinary parts of every page, one is off unless you switch it on, and each has an access rule that surprises people the first time it silently prints nothing. The running scenario is the Bookshelf, a small catalogue of books; the same Book is a record with an enum status and an optional ISBN.

The Bookshelf Used on This Page

The examples below are views of one WAR, deployed as g4elstatic.war under the context path /g4elstatic. A servlet (ViewServlet, mapped to /view/*) puts a Book, a second Book without an ISBN, a list of both, an array of their titles and an Optional<Book> into the request and forwards to /WEB-INF/views/<name>.jsp for a fixed list of view names. The model is a record Book with an Author record and a Status enum, plus a final class Shelf that holds constants and static helpers. Where These Features Sit in the Resolver Chain

Every EL expression in a page is evaluated through one jakarta.el.CompositeELResolver that the container builds. Pages 4.0 section 2.10 lists its components in order (the Implicit Objects and Scopes page shows the same chain from the scope side), and the three features of this page are three of the entries. The expression ${Shelf.MAX_LOANS} is resolved by the import resolver (to a class), then by StaticFieldELResolver (to the field); ${book.title} is resolved by RecordELResolver before the generic BeanELResolver ever sees it; and ${book.isbn.value} can only work if somebody added OptionalELResolver to the part of the chain that is reserved for application resolvers.

Static Fields and Methods

The syntax is classname.member, where classname is the simple class name without its package: ${Boolean.TRUE}, ${Integer.MAX_VALUE}, ${Math.max(3, 7)}. The specification attaches four security restrictions: only public static fields and methods can be referenced, they must be in an accessible (exported) module, static fields cannot be modified, and, except for java.lang, a class has to be imported before its static members can be named.

Default Imports and the page Directive

The EL on its own imports java.lang.* only. The specification lets a technology that uses EL add more, and Pages does: the import attribute of the page directive (see the Directives page) describes "the types that are available to the scripting and EL environments", and the container implicitly imports java.lang.*, jakarta.servlet.*, jakarta.servlet.jsp.* and jakarta.servlet.http.*. That the EL environment has the same defaults as the scripting environment was clarified in Pages 3.1. A page can add more with import, as it does for Shelf above, and can import a whole package or a single class.

The import handler is the object ELContext.getImportHandler() returns, and PageContext.getELContext() gives a page its ELContext.         JspFactory.getDefaultFactory()
                .getJspApplicationContext(event.getServletContext())
                .addELContextListener(ece -> {
                    ImportHandler imports = ece.getELContext().getImportHandler();

What java.lang Gives a Page, and Why That Matters

The default imports are a convenience for page authors and a hazard for everything else. java.lang contains Runtime, System, Thread and ProcessBuilder, and the Pages packages contain Cookie, so an expression that an attacker can choose is not limited to reading the Bookshelf. Three rules follow from the output.

  • Concrete classes only. Cookie is a class, so its constructor and .name work. HttpServletResponse and HttpServletRequest are interfaces and PageContext is an abstract class, so ${HttpServletResponse.SC_NOT_FOUND} and ${PageContext.REQUEST_SCOPE} print an empty string even though the packages are on the default import list. Naming such a class in a page import, or in importStatic, does not help: it raises the ELException quoted in the table above. To use HttpServletResponse.SC_NOT_FOUND in a page, put the number in a constant of your own class or write the literal.

  • Never the package-qualified name. The qualified name is not parsed as a class: jakarta is looked up as an attribute, found nowhere, and the whole expression is null.

  • Empty is not an error. An unimported class and an interface constant both evaluate to null, because NotFoundELResolver always resolves, and a null prints as nothing. The errorOnELNotFound setting changes that for a bare identifier in development; see the Expression Language Configuration page of this section.

Enums

An enum constant is a public static field, so ${RoundingMode.FLOOR} and ${Status.AVAILABLE} use the static syntax above and need the same import. The specification adds a second route for values that are already enum instances: an enum is compared with a string, and the string is coerced to the enum type with Enum.valueOf, so ${mySuit == 'Spade'} is true when mySuit is the Spade constant. Everything else about an enum is ordinary Java: its getters are properties (${status.label} calls getLabel()), its methods are callable (name(), ordinal()), and its static methods values() and valueOf(String) are static methods of the imported enum class.

Records

A Java record has no getters. Its accessors are methods named after its components (title(), not getTitle()), so a resolver that only looks for getX and isX, which is what BeanELResolver does, cannot read it. EL 6.0 adds RecordELResolver for exactly this case. It handles any base object that is a java.lang.Record, accepts any non-null property, coerces it to a string with toString() and uses that string to find the accessor method of the component with the same name. It is always read-only. Because EL 6.0 enables it by default and Pages 4.0 lists it right before BeanELResolver, a record works as a bean on Tomcat 11 with no configuration: ${book.title} calls title().

Switching the Resolver On

OptionalELResolver is a normal ELResolver, so it is registered the way any application resolver is: through the JspApplicationContext of the web application, which Pages 4.0 section 2.10 places right after the implicit objects in the chain. The natural place is a ServletContextListener; the one below reads a context parameter so the same code ran as the plain WAR (false) and the Optional-enabled WAR (true).

OptionalSupport.java and the context parameter in web.xml
@WebListener
public class OptionalSupport implements ServletContextListener {

    @Override
    public void contextInitialized(ServletContextEvent event) {
        ServletContext context = event.getServletContext();
        if (Boolean.parseBoolean(context.getInitParameter("optionalEL"))) {
            JspFactory.getDefaultFactory().getJspApplicationContext(context).addELResolver(new OptionalELResolver());
        }
    }
}

The registration is application-wide and happens once, at start-up. After it the chain looks through every java.util.Optional in every page of the application: this is a global change of semantics that cannot be limited to one page, so every page that calls .isPresent() or .orElse(...) breaks (below). The Javadoc defines the behaviour precisely: for an Optional base, an empty Optional resolves every property to null; a populated one resolves the property on its content, by calling the whole resolver chain with the content as the base; with a null property the content itself is the value; method calls are forwarded to the content, and an empty Optional answers null to every method call; and coercion to a type is done on the content, or on null when empty.

What to Do With Optional in a Page

The pattern that works with and without the resolver, and that does not tie the pages to a global switch, is to unwrap in the servlet or in the view model. Put the nullable value in the request (book.isbn().orElse(null)), or add a component of a plain type to the view record, and let the page use the ordinary EL null handling, empty, c:if and c:out default. Reach for the resolver only in an application that has chosen to model its optional properties as Optional and to read them with property syntax everywhere, so that no page calls an Optional method. In that case register it once, in a listener, and never mix the two styles, as the table above shows why.
