JSTL Formatting

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Standard Tag Library 3.0 (specification chapter 9, "Formatting Actions"), Jakarta Pages 4.0, Jakarta Expression Language 6.0 and Jakarta Servlet 6.1 (Jakarta EE 11), with the Tags API jakarta.servlet.jsp.jstl:jakarta.servlet.jsp.jstl-api 3.0.2 and its implementation org.glassfish.web:jakarta.servlet.jsp.jstl 3.0.1, running on Apache Tomcat 11.0.26 and Java 21 (21.0.x, with its CLDR locale data). Everything was verified on 2026-10-08: the rules against the specification, the tag documentation and the Java SE 21 API documentation, and every example by building it into a Maven WAR and running it on Tomcat 11.0.26 with curl and a small script; the outputs shown are the outputs of those runs. The formatting actions turn numbers, currencies, percentages, dates and times into text and back, in the conventions of a locale and in the time zone of a user. They are the part of JSTL that has changed least since 2003 and the part where the Java platform underneath has changed the most, so most surprises come from the locale data, from the patterns of DecimalFormat and SimpleDateFormat, and from the rules that choose the locale and the time zone, not from the tags. The page explains those rules first, then each tag, then the problem that Tags 3.0 still cannot format java.time values and the current workarounds. The running scenario is the Bookshelf, whose books now have a price, a rating and a publication date. Message bundles and fmt:message are the other half of the fmt library and are covered by the JSTL i18n & Messages page of this section; this page only uses the part of them that influences formatting.

The Formatting Actions at a Glance

The fmt library is the Jakarta Tags library whose URI is jakarta.tags.fmt (conventionally the prefix fmt). Its actions fall in two groups: the i18n actions (fmt:setLocale, fmt:bundle, fmt:setBundle, fmt:message, fmt:param and fmt:requestEncoding, covered by the character encoding page) and the formatting actions below. The two groups share one locale mechanism, which is why this page keeps referring to the other one. The library is current: Tags 3.0 is the version of Jakarta EE 10 and 11, and nothing in the Jakarta EE 12 plan removes it.

Table 1. The formatting actions of Jakarta Tags 3.0 (specification sections 9.5 to 9.10)
Action What it does Result

fmt:formatNumber

Formats a number, a currency amount or a percentage in the conventions of a locale, or with a DecimalFormat pattern

Text, written to the page or stored in var as a String

fmt:parseNumber

Parses the text of a number, currency or percentage into a java.lang.Number

A Long or a Double, stored in var or written with toString()

fmt:formatDate

Formats a java.util.Date as a date, a time or both, with predefined styles or a SimpleDateFormat pattern

Text, written to the page or stored in var as a String

fmt:parseDate

Parses the text of a date and time into a java.util.Date; non-lenient

A Date, stored in var or written with toString()

fmt:timeZone

Sets the time zone for the formatting and parsing actions in its body

The body’s output, unchanged

fmt:setTimeZone

Stores a time zone in a scoped variable, or as the default time zone of a scope

Nothing is written

Source: Jakarta Standard Tag Library 3.0 — 9. Formatting Actions

Every action is usable without a body except fmt:timeZone, and formatNumber, parseNumber and parseDate accept their value as the trimmed body instead of the value attribute (examples below). The type, pattern, var and scope attributes work the same way across the actions, and scope without var is a translation-time error. The actions format with java.text classes (DecimalFormat, SimpleDateFormat, DateFormat), so everything the Java SE documentation says about those classes, including how locale data is chosen, applies to the output.

The taglib directive is the one that every page of this section uses, with the jakarta.tags.* URI. The old http://java.sun.com/jsp/jstl/fmt URI is not a link to anything any more (the Tags 3.0 release page says only that the old URIs may still be used as identifiers), and the specification and every tool of the Jakarta era use the new one.

<%@ taglib prefix="fmt" uri="jakarta.tags.fmt" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>

Source: Jakarta Standard Tag Library 3.0 — tag documentation

The Bookshelf Used on This Page

All the examples are files of one Maven WAR, g5jstlformatting.war, deployed under the context path /g5jstlformatting on Tomcat 11.0.26. Its dependencies are those of the Getting Started page of this section (provided Servlet, Pages and EL APIs, plus the Jakarta Tags API and its implementation, which Tomcat does not include). One servlet puts a Book record and a list holding it in the request, plus a fixed now so that every output is repeatable, and forwards to /WEB-INF/views/<name>.jsp (the views live under WEB-INF, as everywhere in this section).

The data the pages format: a record, one book and a fixed instant
public record Book(long id, String title, String author, BigDecimal price, double rating,
                   Date publishedAt, LocalDate released) { }

Book book = new Book(1, "Cien años de soledad", "Gabriel García Márquez",
        new BigDecimal("1234.5"), 0.875,
        Date.from(LocalDate.of(1967, 5, 30).atStartOfDay(ZoneOffset.UTC).toInstant()),
        LocalDate.of(1967, 5, 30));
req.setAttribute("book", book);
req.setAttribute("books", List.of(book));
req.setAttribute("now", Date.from(Instant.parse("2026-10-08T14:30:00Z")));

The price is deliberately a BigDecimal (money is never a double), the rating is a double between 0 and 1 so that it can be shown as a percentage, and the publication date is stored as the instant of midnight UTC, as many databases and importers do. The released field holds the same day as a LocalDate, to show what the tags cannot yet do with it. Unless a section says otherwise, web.xml contains two context parameters, the default time zone and the fallback locale, which are explained in the configuration section:

<context-param>
  <param-name>jakarta.servlet.jsp.jstl.fmt.timeZone</param-name>
  <param-value>Europe/Madrid</param-value>
</context-param>
<context-param>
  <param-name>jakarta.servlet.jsp.jstl.fmt.fallbackLocale</param-name>
  <param-value>es_ES</param-value>
</context-param>

Source: Jakarta Standard Tag Library 3.0 — 9.11 Configuration Settings

A word on reading the outputs. Java 21 uses the Unicode CLDR locale data, and CLDR separates numbers from their symbols with no-break characters: U+00A0 (no-break space) before € or % in Spanish and German, and U+202F (narrow no-break space) as the thousands separator in French and before AM and PM in English times. They look like spaces, they are not spaces, and the output blocks below show them as ordinary spaces. A comparison or a parse that types a normal space fails, which is a pitfall in its own right (see the pitfalls table).

Which Locale and Time Zone an Action Uses

Before the tags themselves, the two rules that explain most of the output. An action never "has" a locale; it finds one every time it runs, following the algorithm of specification section 9.2 and 9.3.

flowchart TD A["formatting action runs"] --> B{"inside fmt:bundle whose bundle has a locale?"} B -- yes --> U["use that locale"] B -- no --> C{"localizationContext setting with a locale?"} C -- yes --> U C -- no --> D["preferred locales: the fmt.locale setting (fmt:setLocale), else the Accept-Language locales"] D --> E{"does an available locale match one of them?"} E -- yes --> U E -- no --> F{"does the fallbackLocale setting match?"} F -- yes --> U F -- no --> G["no locale: formatNumber and formatDate print the value with toString, parseNumber and parseDate throw JspException"]

The steps in the diagram, in order:

  1. A formatting action nested in fmt:bundle takes the locale of that bundle’s localization context.

  2. Otherwise the jakarta.servlet.jsp.jstl.fmt.localizationContext setting, if it holds a bundle with a locale, supplies the locale.

  3. Otherwise the action establishes a locale. The preferred locales are those of fmt:setLocale or the jakarta.servlet.jsp.jstl.fmt.locale setting when one exists (the "application-based" locale, which wins) and the locales of the Accept-Language header, in order, otherwise (the "browser-based" locale).

  4. Each preferred locale is looked up among the locales that Java reports as available for that action (NumberFormat.getAvailableLocales() for the number actions, DateFormat.getAvailableLocales() for the date actions). A lookup tries language, country and variant, then language and country, then the language alone when the available locale has no country.

  5. If no preferred locale matches, the jakarta.servlet.jsp.jstl.fmt.fallbackLocale setting is looked up the same way.

  6. If nothing matches, the specification leaves the corrective action to the tag: the format actions print the value with Number.toString() or Date.toString(), and the parse actions throw a JspException that names the value.

Source: Jakarta Standard Tag Library 3.0 — 9.2 Formatting Locale

Source: Jakarta Standard Tag Library 3.0 — 9.3.3 Formatting Locale Lookup Algorithm

The last step is not theoretical. These are the same page, the same tags and the same data, requested with three different headers, on a JVM whose default locale is es_ES and with no fallbackLocale configured:

$ curl -s http://localhost:18080/g5jstlformatting/shelf?v=locales
request locales: en_US
1234.5 | Thu Oct 08 16:30:00 CEST 2026
$ curl -s -H 'Accept-Language: en-US' http://localhost:18080/g5jstlformatting/shelf?v=locales
request locales: en_US
$1,234.50 | October 8, 2026
$ curl -s -H 'Accept-Language: xx-XX' http://localhost:18080/g5jstlformatting/shelf?v=locales
request locales: xx_XX
1234.5 | Thu Oct 08 16:30:00 CEST 2026

The first request has no Accept-Language header, so the tags see no preferred locale (the Servlet API’s request.getLocale() still answers en_US there, which is why ${pageContext.request.locale} is a poor proxy for what the tags will do) and print the raw values. The third has a header that names a locale Java does not know. Browsers always send the header, curl, health checks, tests and many API clients do not, and that is why a "formatting" page can look correct in the browser and print 1234.5 in a script. The fix is to configure a fallbackLocale, or to call fmt:setLocale from the page or from a filter. With the context parameter above the same two requests print 1.234,50 € and 8 de octubre de 2026.

A locale that is available but incomplete is the other trap. Accept-Language: sw (Swahili, language only) matches the available locale sw, which has no country and therefore no currency, so the currency format prints the generic currency sign ¤ (observed: ¤ 1,234.50). A fallback locale should therefore name a country too: es_ES printed 1.234,50 €, while the language-only es printed 1.234,50 ¤ in the same test.

Source: Jakarta Standard Tag Library 3.0 — 9.3 Establishing a Formatting Locale

Source: Jakarta Standard Tag Library 3.0 — 8.11.2 Fallback Locale

The time zone has a shorter chain, used by fmt:formatDate and by fmt:parseDate for text that carries no zone of its own:

flowchart LR A["fmt:formatDate or fmt:parseDate"] --> B{"timeZone attribute?"} B -- yes --> Z["use it"] B -- no --> C{"inside fmt:timeZone?"} C -- yes --> Z C -- no --> D{"fmt.timeZone setting (fmt:setTimeZone or context parameter)?"} D -- yes --> Z D -- no --> E["the time zone of the container: the JVM default"] E --> Z

Source: Jakarta Standard Tag Library 3.0 — 9.4 Time Zone

The locale and the time zone are independent: a Spanish user can see Tokyo time, and a Japanese user can see Madrid time. The browser tells the server nothing about the time zone, so unless the application records it (a profile setting, a cookie set by JavaScript, an offset sent with a form) the container’s zone is what every user sees. The number and currency formatting does not depend on the time zone.

fmt:formatNumber

fmt:formatNumber formats a number according to the formatting locale (type) or to a custom pattern (pattern), and fine-tunes the result with the digit and grouping attributes.

Types and locales

The same three tags, run once per locale with fmt:setLocale (the c:forTokens loop only keeps the page short):

<c:forTokens items="en_US,es_ES,de_DE,fr_FR,fr_CH,ja_JP" delims="," var="l">
  <fmt:setLocale value="${l}"/>
  ${l}: <fmt:formatNumber value="${book.price}" type="currency"/>
      | <fmt:formatNumber value="${book.price}"/>
      | <fmt:formatNumber value="${book.rating}" type="percent"/>
</c:forTokens>
Rendered output (U+00A0 and U+202F shown as spaces; the price is 1234.5 and the rating 0.875)
en_US: $1,234.50 | 1,234.5 | 88%
es_ES: 1.234,50 € | 1.234,5 | 88 %
de_DE: 1.234,50 € | 1.234,5 | 88 %
fr_FR: 1 234,50 € | 1 234,5 | 88 %
fr_CH: 1 234.50 CHF | 1 234,5 | 88%
ja_JP: ￥1,234 | 1,234.5 | 88%

Source: Jakarta Standard Tag Library 3.0 — 9.1.1 Formatting Numbers, Currencies, and Percentages

Several things are visible in six lines. The decimal and grouping separators, the position of the currency sign and the space before % are all the locale’s; the page never says where a symbol goes. The currency comes from the locale (Swiss francs for fr_CH, yen for ja_JP), not from the data: a fmt:formatNumber of a price does not know what currency the price is in, it knows the currency of the reader’s country. ja_JP prints 1,234 without cents because the yen has no minor unit, so the .5 was rounded away (half-even, see below). A shop that sells in one currency to readers of many must pass the currency of the data, as in the next section. Finally, the specification’s own example for fr_CH (SFr. 9'876'543.21) predates the CLDR data and Java 21 prints something else: examples in books and in the specification show what the platform printed when they were written.

Patterns, digits and the currency of the data

The attribute list in one page, each line a different attribute (the locale is en_US, the price 1234.5):

<fmt:setLocale value="en_US"/>
[<fmt:formatNumber value="${book.price}" pattern="#,##0.00"/>]
[<fmt:formatNumber value="12.3" pattern=".000"/>]
[<fmt:formatNumber value="123456.7891" pattern="#,#00.0#"/>]
[<fmt:formatNumber value="${book.price}" type="currency" currencyCode="EUR"/>]
[<fmt:formatNumber value="${book.price}" type="currency" currencySymbol="EUR "/>]

[<fmt:formatNumber value="${book.price}" groupingUsed="false"/>]
[<fmt:formatNumber value="7" minIntegerDigits="3"/>]
[<fmt:formatNumber value="${book.rating}" type="percent" minFractionDigits="1"/>]
[<fmt:formatNumber value="3" minFractionDigits="2"/>]

Source: Jakarta Standard Tag Library 3.0 — 9.7 fmt:formatNumber

The lines show the rules of the specification at work. pattern replaces the locale’s pattern but not its symbols (lines 1 to 3, the second and third are the specification’s own examples and print the values it states). currencyCode="EUR" changes the symbol to the euro sign while the layout stays that of en_US; currencySymbol prints any text; with both, the code wins (line 6). groupingUsed="false" removes the separators, which is how to print a number that another program will read. A body can replace value, and is trimmed (line 11), which is useful when the number is the result of another tag. A type of percent multiplies by 100, but pattern wins over type, so line 12 does not multiply: it is a plain 0.0 pattern, and mixing the two is almost always a mistake. A null or empty value prints nothing at all and removes var, which is why an empty cell in a table is not an error and also why a typo in a variable name (${missing}) produces an empty cell instead of a failure.

The pattern language is the one of java.text.DecimalFormat:

Source: Java SE 21 — DecimalFormat, Patterns

Three consequences of that class are worth knowing. The rounding mode is HALF_EVEN ("banker’s rounding"): with maxFractionDigits="0", 2.5 prints 2 and 3.5 prints 4, and the rating 0.875 printed as 88% above is 87.5 rounded to the even neighbour. Money is therefore formatted from BigDecimal values that were already rounded deliberately by the application; the page is not the place to decide how a price rounds. The maxIntegerDigits attribute does not round, it truncates the high-order digits: 1234567.891 with maxIntegerDigits="3" and maxFractionDigits="1" printed 567.9 (observed), a way to print a plausible and wrong number. And currencyCode only changes the symbol and the code; it does not move the decimal places to those of the currency, so ja_JP with currencyCode="EUR" printed €1,234 (the layout keeps the yen’s zero decimals) while en_US printed €1,234.50. If a page shows amounts in a currency that is not the reader’s, set minFractionDigits and maxFractionDigits too.

Source: Java SE 21 — RoundingMode

Source: Jakarta Standard Tag Library 3.0 — 9.7 fmt:formatNumber

Storing the result with var

With var the action writes nothing and stores a String. This is how to use a formatted amount inside an attribute or in another tag (such as the fmt:message argument of the i18n page) without printing it first:

<fmt:formatNumber value="${book.price}" type="currency" var="label" scope="request"/>
<span title="${label}">${label}</span>   <%-- label is a java.lang.String --%>
Rendered output, en_US
<span title="$1,234.50">$1,234.50</span>

Source: Jakarta Standard Tag Library 3.0 — 9.7 fmt:formatNumber

The result is text made of digits, the locale’s symbols and no markup, so it needs no escaping by itself, but the symbols are data from the platform and the page that prints ${label} inside an attribute is still printing a value. When the number is something a user typed (a "price" field echoed back), print the original string with c:out, or parse it first and format the parsed number, never the raw text inside a value attribute that is later reflected in HTML.

Parsing is where the conventions are strictest, because the same text means different numbers in different locales:

<fmt:setLocale value="en_US"/>
<fmt:parseNumber value="1.234,56" parseLocale="es_ES" var="a"/>      a=${a} ${a.getClass().simpleName}
<fmt:parseNumber value="1,234.56" parseLocale="en_US" var="b"/>      b=${b} ${b.getClass().simpleName}
<fmt:parseNumber value="1,234.56" parseLocale="en_US" integerOnly="true" var="c"/>   c=${c} ${c.getClass().simpleName}
<fmt:parseNumber value="${pctEs}" type="percent" parseLocale="es_ES" var="d"/>   d=${d}
<fmt:parseNumber value="$1,234.50" type="currency" parseLocale="en_US" var="e"/> e=${e}
<fmt:parseNumber value="42" var="f"/>   f=${f} ${f.getClass().simpleName}
<fmt:parseNumber var="i">  7.5 </fmt:parseNumber>   i=${i}
<fmt:parseNumber value="1234.5" parseLocale="en_US"/>
Rendered output
a=1234.56 Double
b=1234.56 Double
c=1234 Long
d=0.875
e=1234.5
f=42 Long
i=7.5
1234.5

Source: Jakarta Standard Tag Library 3.0 — 9.1.1 Formatting Numbers, Currencies, and Percentages

The percent text of line 4 is 87,5 % with a no-break space (U+00A0) before the sign, which is what es_ES prints on Java 21 and therefore what the parser expects; the servlet put that string in the request attribute pctEs for the test. The result is the fraction 0.875, not 87.5: a percent is divided by 100 on the way in, as it was multiplied on the way out. The last line shows that without var the number goes to the page through Number.toString(), which is not locale-aware.

The parser is lenient at the end and strict at the start

DecimalFormat.parse reads the longest prefix that is a number and ignores whatever follows. The tag inherits that. Each of the following is silently wrong, not an error:

<fmt:parseNumber value="12abc" parseLocale="en_US" var="h"/>                  h=${h}
<fmt:parseNumber value="1.234,56" parseLocale="en_US" var="k"/>               k=${k}
<fmt:parseNumber value="1 234,5" pattern="#,##0.#" parseLocale="fr_FR" var="g"/>   g=${g}
Rendered output
h=12
k=1.234
g=1

The second line reads a Spanish number with an English parser: the parse stops at the comma and returns 1.234, a thousand times too small and with no message. The third types an ordinary space where French uses the narrow no-break space, and the parse stops at it and returns 1. Text that cannot start a number does fail:

The message is the specification’s required one (it must include the string being parsed, with the parser’s exception as root cause); the < is in the implementation’s message text itself (it was added to avoid HTML injection in error pages), so it prints as entities when ${err.message} is written to a page without escaping. The exception is a jakarta.servlet.jsp.JspException wrapping a java.text.ParseException; the error handling page of this section explains how an error page or a c:catch receives it. A parseLocale that is absent when the page has no formatting locale throws too, with In <parseNumber>, a parse locale can not be established (observed with a request without Accept-Language and no fallback). An empty value is not an error: it removes var (if var held an older value, the older value is gone), so "empty input" and "invalid input" can be told apart with empty var.

Two rules follow for a form. Do not parse user input in the view: a form field is untrusted, the conversion belongs in the controller (or in a validator) where a failure can produce a message next to the field and a 400 or a re-display, and the view then formats the parsed value. And give the user the same convention the parser expects (a fmt:formatNumber of the current value in the same locale), or use <input type="number">, which always submits a dot as the decimal separator whatever the locale of the browser.

A number for a machine is not a number for a person

The value of an <input type="number"> must use a dot and no grouping. Formatting it with fmt:formatNumber in a locale that uses a comma produces a value the browser rejects:

Dates Without java.time: the Missing Support and the Workarounds

The value attribute of fmt:formatDate is typed java.util.Date, and Tags 3.0 knows nothing about java.time. A LocalDate, LocalDateTime, Instant or ZonedDateTime is rejected before the tag runs. A String is rejected too, because there is no editor that turns text into a Date:

<c:catch var="e1"><fmt:formatDate value="${book.released}" dateStyle="long"/></c:catch>
${e1.getClass().name}: ${e1.message}
<c:catch var="e2"><fmt:formatDate value="1967-05-30" dateStyle="long"/></c:catch>
${e2.getClass().name}: ${e2.message}
Rendered output
jakarta.el.ELException: Cannot convert [1967-05-30] of type [class java.time.LocalDate] to [class java.util.Date]
org.apache.jasper.JasperException: Unable to convert string [1967-05-30] to class [java.util.Date] for attribute [value]: [Property Editor not registered with the PropertyEditorManager]

Source: Jakarta Standard Tag Library 3.0 — 9.9 fmt:formatDate

The first error is the Expression Language’s attempt to coerce the attribute to the declared type; the second comes from the Jasper compiler for a literal that must become a Date. This is the single most common complaint about the library in modern projects, and the Jakarta Tags project has recorded it: issue 247, "Support java.time API in fmt:parseDate and fmt:formatDate", is the one feature planned for Tags 3.1 (Jakarta EE 12), which also raises the minimum Java to 21. Tags 3.1 is under development and available only as milestone builds, so a production page today needs one of these four workarounds, from the most to the least recommended:

<%@ page import="java.time.format.DateTimeFormatter, java.time.ZoneOffset, java.util.Date" %>
<fmt:setLocale value="en_US"/>
1: ${book.released}
2: ${book.released.format(DateTimeFormatter.ISO_LOCAL_DATE)}
3: ${DateTimeFormatter.ofPattern("d MMMM uuuu").withLocale(pageContext.request.locale).format(book.released)}
4: <fmt:formatDate value="${Date.from(book.released.atStartOfDay(ZoneOffset.UTC).toInstant())}" dateStyle="long" timeZone="UTC"/>
Rendered output
1: 1967-05-30
2: 1967-05-30
3: 30 May 1967
4: May 30, 1967

Source: Jakarta Standard Tag Library 3.1 (under development)

Source: Java SE 21 — DateTimeFormatter

Source: Jakarta Tags issue 247 — Support java.time API in fmt:parseDate and fmt:formatDate

The workarounds, in prose:

  1. Convert in the controller or in a view model. The servlet or the controller puts a java.util.Date (or a String already formatted for the reader) in the request next to the java.time value; the view stays plain. This is the simplest and the safest, because the zone decision is made once, in Java, where it can be tested.

  2. Print the ISO form, line 1 and 2. The toString() of a LocalDate is the ISO 8601 date, which is right for machine-readable output (<time datetime="${book.released}">, a value attribute of <input type="date">) and for no one else.

  3. Format with DateTimeFormatter from EL, line 3. A page directive’s import makes the class (and the static constants of the class, such as ISO_LOCAL_DATE) known to the Expression Language, which then calls instance and static methods. Note the pitfall in the example: pageContext.request.locale is the first locale of Accept-Language, which is not the locale fmt:setLocale chose, so the line and the fmt tags of the same page can disagree about the language. The class used must be public and not abstract: ZoneId.of(...) fails with The class [java.time.ZoneId] must be public, in an exported package, non-abstract and not an interface (observed), which is why the example uses the final class ZoneOffset.

  4. Convert to Date in the page, line 4, with a zone that you decide (UTC for a calendar date) and timeZone set to the same zone. It works and is the one to avoid, since the conversion lives in the view where the zone rule is easy to forget.

A custom EL function or a tag file wrapping DateTimeFormatter is the clean way to reuse workaround 3; both are covered by the SimpleTag and TLDs and EL functions pages of this section. Until Tags 3.1 is final and the container ships it, none of this code needs to change when it arrives.

Security and Correctness

The formatting tags do not write markup, so they are not an XSS vector by themselves: a number or a date formats to digits, the symbols of the locale data and spaces. The security issues are around them:

  • The value of fmt:formatNumber and fmt:parseNumber can be user text. A string that is not a number fails with a JspException, which on a default Tomcat error page prints the message with the offending text; configure an error page and do not print err.message for requests that come from users.

  • A pattern is code for the formatter. A pattern taken from a request parameter lets a user crash the page (the IllegalArgumentException above) and choose how much of a number is shown. Patterns come from a fixed list.

  • A time zone or locale from a request parameter is harmless to the tags (they fall back), but it changes the output, so it must not be part of a cache key unless it was validated.

  • Convert and validate user input in the controller (see the parsing section) so that a ParseException becomes a message next to the field, and use an error page for the rest (see the error handling page).

What Changed Recently

The tags did not change between Tags 1.1 and 3.0 in a way that affects their behaviour. What changed is the namespace of the library and, above all, the platform below it.

Table 12. Changes that affect formatting
Version Change Effect for page authors

JSTL 1.1 (JSP 2.0, 2003)

New URIs (http://java.sun.com/jsp/jstl/fmt), the container evaluates EL in attributes, the _rt twin libraries disappear

Pages written for JSTL 1.0 need the new taglib URI and no longer use fmt_rt

Java 9 (JEP 252)

CLDR locale data becomes the default instead of the older JRE data

Separators, currency sign positions and date styles of many locales differ from older outputs

Tags 3.0 (Jakarta EE 10)

The URI becomes jakarta.tags.fmt; the packages and the configuration variables move to jakarta.servlet.jsp.jstl.*; Java 11 minimum; the old java.sun.com URIs still work as identifiers

javax code and web.xml parameters with the old names need renaming; the tags behave as before

Java 20 (CLDR 42)

A narrow no-break space (U+202F) before AM and PM in English times

Text compared with, or parsed from, a time style written before Java 20 stops matching

Tags 3.0.1 (2023-01-19)

The implementation org.glassfish.web:jakarta.servlet.jsp.jstl 3.0.1 is still the latest final

Nothing to upgrade; pin 3.0.1 with the 3.0.2 API

Tags 3.1 (Jakarta EE 12, in progress)

fmt:formatDate and fmt:parseDate to support java.time; Java 21 minimum; no removals planned

Milestones only today; do not rely on them in production

Where the Books Are Outdated

JSTL in Action (Manning, 2003, listed in the section bibliography) teaches JSTL 1.0 on JSP 1.2, and its chapters on formatting and internationalization are the origin of the vocabulary of this page (number and date formatting, parsing, time zones, locales). The concepts survived; the platform around them did not.
