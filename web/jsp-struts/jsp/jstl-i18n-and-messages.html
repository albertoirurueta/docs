JSTL i18n & Messages

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against the Jakarta Standard Tag Library (Jakarta Tags) 3.0, chapter 8 "Internationalization (i18n) Actions" and the configuration data of chapter 2, together with Jakarta Pages 4.0, Jakarta Expression Language 6.0 and Jakarta Servlet 6.1 (Jakarta EE 11), as implemented by Apache Tomcat 11.0.26 on Java 21 with the Tags implementation org.glassfish.web:jakarta.servlet.jsp.jstl 3.0.1 and the API jakarta.servlet.jsp.jstl:jakarta.servlet.jsp.jstl-api 3.0.2. Everything was verified on 2026-10-08: the rules against the specification and the Javadoc, and every example by building it into a Maven WAR and running it on Tomcat 11.0.26 with curl; the outputs shown are the outputs of those runs. The fmt: library is the part of JSTL that lets a page keep its words out of its markup: labels, messages and sentences live in resource bundles, one per language, and the page asks for them by key. This page covers the actions that choose a language and fetch text (fmt:setLocale, fmt:bundle, fmt:setBundle, fmt:message, fmt:param, fmt:requestEncoding), the algorithm that picks a bundle for a visitor, and the configuration settings that steer it. Numbers, currencies, dates and time zones use the same locale machinery but belong to the JSTL Formatting page of this section. The running scenario is the Bookshelf, now in English and Spanish.

Status: Archived Tutorial, Current Library

The fmt: library is not deprecated and not removed: Tags 3.0 is the current version of the specification, it ships in Jakarta EE 10 and 11, and its implementation is the same one Tomcat, Jetty and GlassFish applications load today. What is archived is the teaching material. The Jakarta EE Tutorial moved its Jakarta Pages and Jakarta Tags chapters to an "Archived" area, and its remaining chapter on internationalization, "Internationalizing and Localizing Web Applications", is written around Jakarta Faces (faces-config.xml, f:loadBundle) and was last updated for Jakarta EE 9.1; the only JSTL content in it is one sentence saying that a component can set the locale with fmt:setLocale. The last complete official tutorial for the JSP flavour, the Java EE 5 Tutorial, uses javax.* names. The consequence is that the specification chapter and the Javadoc of jakarta.servlet.jsp.jstl.fmt are the primary sources, and they are what this page follows.

Locale, Bundle, Basename and Key

The specification builds the library on four ideas, all taken from java.util.

  • A locale is a language, optionally with a country and a variant. The language is the lower-case two-letter ISO-639 code (es, fr), the country the upper-case two-letter ISO-3166 code (ES, CA). The semantics are those of java.util.Locale, so the legacy codes apply: he, yi and id are reported as iw, ji and in by Locale unless the JVM property java.locale.useOldISOCodes says otherwise.

  • A resource bundle holds locale-specific objects, here strings, each associated with a key.

  • A basename identifies a family of bundles that translate the same keys. The bundle for a locale is the basename plus a suffix: Messages is the root bundle, Messages_es the Spanish one, Messages_es_ES the Spanish of Spain.

  • A localization context is the pair the actions actually work with: a resource bundle and the locale for which it was found. It is the Java class jakarta.servlet.jsp.jstl.fmt.LocalizationContext.

The specification names two ways of internationalizing a page. The first is one page per locale with a controller servlet that dispatches to the right one, which suits pages where most of the content differs. The second isolates the locale-sensitive text in bundles and fetches it with the fmt: actions, which suits everything else and is what the rest of this page is about. The two combine: a controller can pick a page variant per locale and each variant still uses bundles for its labels.

The Bookshelf Used on This Page

All the examples are files of one Maven WAR, g5jstli18n.war, deployed under the context path /g5jstli18n on Tomcat 11.0.26 (plus one variant that differs only in web.xml, named where it appears). The WAR has the dependencies of the Getting Started page of this section: provided Servlet, Pages and EL APIs, plus the Jakarta Tags API 3.0.2 and its implementation 3.0.1. One servlet, DataServlet, mapped to /data/*, puts a list of Book records in the request and forwards to /WEB-INF/e/<name>.jsp, so /data/basic runs /WEB-INF/e/basic.jsp. Every request below was made with curl and an explicit Accept-Language header, because that header is what a browser uses to say which languages its user reads; the header is set with -H 'Accept-Language: es'.

The bundles are plain .properties files in src/main/resources/org/example/bookshelf/i18n/. They are saved as UTF-8 and contain the accented characters directly; Java 9 and later read them as UTF-8 (see the pitfalls section).

The servlet that feeds every page
@WebServlet("/data/*")
public class DataServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        List<Book> books = List.of(
                new Book(1, "Dune", "Frank Herbert", 1965),

Declaring the Library

The i18n actions live in the fmt library with the URI jakarta.tags.fmt (Tags 3.0 renamed the URIs from http://java.sun.com/jsp/jstl/ to jakarta.tags.). The prefix fmt is a convention, not a rule.

<%@ taglib prefix="fmt" uri="jakarta.tags.fmt" %>

Source: Jakarta Standard Tag Library 3.0 — Appendix B.1, Changes

The old URIs still work with the 3.0.1 implementation because the jar keeps the older TLD files (fmt-1_0.tld, fmt-1_0-rt.tld, fmt-1_1.tld, fmt.tld): uri="http://java.sun.com/jsp/jstl/fmt" and the JSTL 1.0 URI uri="http://java.sun.com/jstl/fmt" both rendered the Bookshelf title on Tomcat 11.0.26. The URI of the JSF-era namespace, http://xmlns.jcp.org/jsp/jstl/fmt, is not one of them and fails with JasperException: The absolute uri: [http://xmlns.jcp.org/jsp/jstl/fmt] cannot be resolved in either web.xml or the jar files deployed with this application. New code should use jakarta.tags.fmt.

The First Message: fmt:setBundle and fmt:message

The smallest internationalized page names a bundle once and then asks for keys. fmt:setBundle without a var makes the bundle the default localization context of the page, and fmt:message reads its key from that default.

A page whose text comes from bundles, basic.jsp
<%@ page contentType="text/html; charset=UTF-8" pageEncoding="UTF-8" %>
<%@ taglib prefix="c" uri="jakarta.tags.core" %>
<%@ taglib prefix="fmt" uri="jakarta.tags.fmt" %>
<fmt:setBundle basename="org.example.bookshelf.i18n.Messages"/>
<h1><fmt:message key="shelf.title"/></h1>
<p><fmt:message key="shelf.count"><fmt:param value="${books.size()}"/></fmt:message></p>
<ul>
<c:forEach var="b" items="${books}">
  <li><c:out value="${b.title}"/></li>
</c:forEach>
</ul>

With Accept-Language: es the page answers with the Spanish bundle, and with no Accept-Language header at all it answers with the root bundle:

<!-- curl -H 'Accept-Language: es' /g5jstli18n/data/basic -->
<h1>Mi estantería</h1>
<p>Tienes 3 libros en la estantería</p>

<!-- curl /g5jstli18n/data/basic -->
<h1>My Bookshelf</h1>
<p>You have 3 books on the shelf</p>

The response headers are part of the result. For the Spanish request Tomcat answered Content-Language: es and Content-Type: text/html;charset=UTF-8; for a request with Accept-Language: en-GB it answered Content-Language: en-GB; for a request without the header there was no Content-Language at all. The actions set the response locale as a side effect, which is the subject of the response section below.

The book titles are printed with c:out, never as a bare ${b.title}, because a title is data and not a message: bundles hold the application’s own text, and the data around it still has to be escaped (the security section shows why fmt:message is not an escaping tag).

fmt:message and fmt:param Reference

fmt:message looks a key up in the bundle of the localization context it determines and writes the text to the current JspWriter, or stores it in a scoped variable when var is given. It has three syntaxes: the key in an attribute and no body, the key in an attribute with fmt:param children, and the key as the (trimmed) body, optionally followed by fmt:param children.

Parameters and MessageFormat

A message that contains variables is a java.text.MessageFormat pattern, and fmt:param supplies the arguments in the order of the tags. The specification states the mechanism exactly: with one or more fmt:param tags the message is passed to MessageFormat.applyPattern() and the values are collected in an Object[] for format(), with the MessageFormat locale set to the locale of the localization context (or, when the context has no locale, to the formatting locale of the page, or finally to the JVM default). Without any fmt:param the message is left untouched and MessageFormat is not used at all. That second rule explains several outputs below.

Parameters in a message, the number, the plural and the date cases, params.jsp
<fmt:setBundle basename="org.example.bookshelf.i18n.Messages"/>
<c:set var="b" value="${books[0]}"/>
<p><fmt:message key="shelf.summary"><fmt:param value="${b.title}"/><fmt:param value="${b.author}"/><fmt:param value="${b.year}"/></fmt:message></p>
<p><fmt:message key="shelf.summary.year"><fmt:param value="${b.title}"/><fmt:param value="${b.author}"/><fmt:param value="${b.year}"/></fmt:message></p>
<p><fmt:message key="shelf.copies"><fmt:param value="${0}"/><fmt:param value="${b.title}"/></fmt:message></p>
<p><fmt:message key="shelf.copies"><fmt:param value="${1}"/><fmt:param value="${b.title}"/></fmt:message></p>
<p><fmt:message key="shelf.copies"><fmt:param value="${1234}"/><fmt:param value="${b.title}"/></fmt:message></p>
<p><fmt:message key="shelf.count"><fmt:param><fmt:formatNumber value="${12345}"/></fmt:param></fmt:message></p>
<jsp:useBean id="now" class="java.util.Date"/>
<p><fmt:message key="shelf.due"><fmt:param value="${now}"/></fmt:message></p>

with these extra keys in Messages.properties (the Spanish file has the same keys translated):

shelf.copies=There {0,choice,0#are no copies|1#is one copy|1<are {0,number,integer} copies} of {1}
shelf.due=Due on {0,date,long}
Output with Accept-Language: en and with Accept-Language: es

<p>There are no copies of Dune</p>
<p>There is one copy of Dune</p>
<p>There are 1,234 copies of Dune</p>

<p>Hay una copia de Dune</p>

<p>Vence el 8 de octubre de 2026</p>

Four lessons are visible in this output.

  • A number argument is formatted by MessageFormat with the grouping of the locale. The year 1965 printed as 1,965 in English and 1.965 in Spanish. The pattern {2,number,#} (a DecimalFormat pattern without grouping) prints 1965 in both. A year, an id or a postal code is not a quantity and needs that pattern, or a String argument.

  • The choice format gives plural forms (0#...|1#...|1<...), and the number inside it can use its own sub-format ({0,number,integer} printed 1,234). Spanish shows that the plural words are the translator’s business: the Spanish line reads awkwardly (Hay ninguna copia, where a translator would write No hay ninguna copia), which is the argument for putting the whole sentence, not a fragment, in the bundle and letting the translator own it. Plural rules of languages with more than two forms are beyond choice; ICU4J’s MessageFormat is the usual answer when they are needed.

  • A date argument can be given a style ({0,date,long}) and is then localized by the same locale: October 8, 2026 against 8 de octubre de 2026.

  • fmt:param accepts a body, so another action can compute the argument. fmt:formatNumber inside the fmt:param printed 12,345 and 12.345, using the same formatting locale as the message.

Source: Jakarta Standard Tag Library 3.0 — 8.8 fmt:message, parametric replacement

Source: Java SE 21 API — MessageFormat, Patterns and Their Interpretation

The apostrophe trap

MessageFormat uses the single quote to quote text, so an apostrophe in a message that is formatted has to be doubled, and an apostrophe in a message that is not formatted must not be. Because fmt:message calls MessageFormat only when there are fmt:param children, the same text needs different spelling in the two cases. The bundle for this example adds three keys:

shelf.apostrophe.plain=Don't panic
shelf.apostrophe.param=Don''t panic about {0}
shelf.apostrophe.broken=Don't panic about {0}
The three spellings with and without parameters, apostrophe.jsp and apos2.jsp
<p>1: <fmt:message key="shelf.apostrophe.plain"/></p>
<p>2: <fmt:message key="shelf.apostrophe.param"><fmt:param value="Dune"/></fmt:message></p>
<p>3: <fmt:message key="shelf.apostrophe.broken"><fmt:param value="Dune"/></fmt:message></p>
<p>4: <fmt:message key="shelf.apostrophe.broken"/></p>
<p>5: <fmt:message key="shelf.apostrophe.param"/></p>
<p>1: Don't panic</p>
<p>2: Don't panic about Dune</p>
<p>3: Dont panic about {0}</p>
<p>4: Don't panic about {0}</p>
<p>5: Don''t panic about {0}</p>

Line 3 is the failure: the single quote started a quoted section, so the apostrophe vanished and {0} was printed literally. Line 5 is the mirror image: the doubled apostrophe shows doubled when the message is not formatted. The rule that works is to double the apostrophe in every message that is ever used with a fmt:param, and to keep a message either always with parameters or never. A message whose parameter count may be zero should be given a dummy parameter or should be rewritten, because the same bundle line cannot satisfy both spellings.

Source: Java SE 21 API — MessageFormat, quoting with single quotes

Bundles and the Localization Context

An i18n action needs a localization context, and the specification fixes where it comes from. The first rule that applies wins.

Table 5. How fmt:message finds its localization context (Tags 3.0, section 8.2)
Order Source Example

1

The bundle attribute of fmt:message, a LocalizationContext object

<fmt:message key="x" bundle="${msgs}"/>

2

The innermost enclosing fmt:bundle

<fmt:bundle basename="..."> ... </fmt:bundle>

3

The default localization context, the configuration setting jakarta.servlet.jsp.jstl.fmt.localizationContext, set by fmt:setBundle without var, by a scoped configuration variable or by a context-param

<fmt:setBundle basename="..."/> earlier in the page

If the default setting is a LocalizationContext, its bundle is used as it is. If it is a String, the action builds its own context with that string as the basename, using the lookup algorithm of the next section.

flowchart TD msg["fmt:message key"] --> a{"bundle attribute present?"} a -- yes --> ctx1["use that LocalizationContext"] a -- no --> b{"inside a fmt:bundle?"} b -- yes --> ctx2["use the context of the innermost fmt:bundle"] b -- no --> c{"default localizationContext configured?"} c -- "LocalizationContext object" --> ctx3["use it as it is"] c -- "String basename" --> ctx4["build a context from the basename with the lookup algorithm"] c -- "nothing" --> none["no bundle: output is ???key???"] ctx1 --> out["look the key up, apply MessageFormat if fmt:param children exist"] ctx2 --> out ctx3 --> out ctx4 --> out

fmt:bundle and its prefix

fmt:bundle creates a localization context for its body: every fmt:message nested inside it, at any depth of markup, uses it (unless the message has its own bundle attribute). The prefix attribute is prepended to the key of every nested fmt:message, which saves typing for long, dotted keys. The body of fmt:bundle is processed normally and written to the page.

fmt:setBundle: a variable or the default

fmt:setBundle with a var stores a LocalizationContext that other tags can pass in their bundle attribute. This is the way to use two bundles on one page, for instance the application’s messages and a separate bundle of error texts, without nesting fmt:bundle blocks. Without var, the context becomes the page’s default (or, with scope="session" or scope="application", the default of a wider scope).

The two uses of fmt:setBundle
<%-- 1. as a variable, used explicitly --%>
<fmt:setBundle basename="org.example.bookshelf.i18n.Errors" var="errors"/>
<fmt:message key="book.notFound" bundle="${errors}"/>

<%-- 2. as the default of the page, session or application --%>
<fmt:setBundle basename="org.example.bookshelf.i18n.Messages" scope="application"/>

Choosing the Locale

The locale that picks the bundle (and, for the formatting actions, the number and date style) comes from one of two places, and the specification gives the first priority.

  • Application-based. The configuration setting jakarta.servlet.jsp.jstl.fmt.locale (the constant Config.FMT_LOCALE) holds a locale chosen by the application. It is set by fmt:setLocale, by Config.set from Java code, or by a context-param of the same name. It is the right choice when the user picks a language in the interface, or when the language is stored in the user’s profile.

  • Browser-based. If the setting is absent, the actions call ServletRequest.getLocales(), the ordered list built from the Accept-Language header, and try the locales in that order.

Either way an ordered list of preferred locales is fed to the bundle algorithm. One detail of the implementation matters in tests: the Util.getRequestLocales of the 3.0.1 implementation returns the locales of the request only when the request has an Accept-Language header. Without the header the list is empty, even though request.getLocales() alone would return the server’s default locale (it printed en_US in the test). A curl without the header therefore behaves like a visitor whose browser expresses no preference, and falls to the fallback locale or the root bundle.

A language switcher with an allowlist and Config

A language selector should not be a request parameter read by the tag. The pattern that scales is a servlet that validates the choice and stores it in the session with the Config class, after which every page of the session uses it. Config.set(session, Config.FMT_LOCALE, locale) is the Java equivalent of fmt:setLocale scope="session".

A servlet that validates and stores the locale, LanguageServlet
@WebServlet("/language")
public class LanguageServlet extends HttpServlet {
    private static final Set<String> SUPPORTED = Set.of("en", "es");

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        String tag = req.getParameter("lang");
        if (tag != null && SUPPORTED.contains(tag)) {
            Config.set(req.getSession(), Config.FMT_LOCALE, Locale.forLanguageTag(tag));
        }
        resp.sendRedirect(req.getContextPath() + "/data/shelf");
    }
}

The Bundle Lookup and Fallback Algorithm

Given a basename and the ordered preferred locales, the specification defines the resource bundle for a localization context in two parts.

The lookup of one locale uses ResourceBundle.getBundle(basename, locale) but only its first level: the candidates are basename_language_country_variant, basename_language_country and basename_language. The JDK’s later steps (the JVM default locale, then the root bundle) are explicitly removed so that other locales can be considered first.

The determination of the bundle then runs these steps and stops at the first success:

  1. For each preferred locale, in order, do the lookup. The first match wins and the context stores that locale and bundle.

  2. If none matched, do the lookup for the locale in the jakarta.servlet.jsp.jstl.fmt.fallbackLocale setting.

  3. If still nothing, load the root bundle (basename alone). If it exists it is used and the context has no locale.

  4. Otherwise the context has neither bundle nor locale and the action must take corrective action (fmt:message prints ???key???).

flowchart TD start["preferred locales, in order"] --> loop{"next preferred locale"} loop -- "lookup finds basename_lang[_country[_variant]]" --> done["use it: context = bundle and that locale"] loop -- "none left" --> fb{"fallbackLocale set and found?"} fb -- yes --> done2["use it: context = bundle and the fallback locale"] fb -- no --> root{"root bundle basename exists?"} root -- yes --> done3["use the root bundle: context has no locale"] root -- no --> none["context without a bundle: fmt:message prints ???key???"]

Two consequences are stated in the specification and are easy to get wrong.

  • A language match beats an exact match further down the list. With the browser preferences en then fr_CA and the bundles Messages_en and Messages_fr_CA, the bundle used is Messages_en, because the lookup for en succeeds before fr_CA is tried.

  • A bundle for a language and country (Resources_fr_CA) should be backed by one for the language alone (Resources_fr). A visitor whose browser asks only for fr finds nothing in Resources_fr_CA: the lookup for the locale fr does not look at fr_CA.

The Response Locale and the Request Charset

The i18n actions have a side effect that the specification spells out: an action that establishes a localization context sets the locale of the response by calling ServletResponse.setLocale() with the context’s locale (unless the context has no locale). fmt:setLocale always does it; fmt:bundle, fmt:setBundle, a fmt:message that establishes a context and the formatting actions that choose a formatting locale do it too. The results of the tests above show it in the Content-Language header: es for Spanish, en-GB for Accept-Language: en-GB.

The Servlet rule behind it is that setLocale also sets the response character encoding when no encoding has been set explicitly by setContentType with a charset or by setCharacterEncoding; on a stock Tomcat 11 the two response-character-encoding elements of conf/web.xml already say UTF-8, and the pages above also declare charset=UTF-8, so the charset stayed UTF-8 in every response. Two conditions apply in general: setLocale must run before the writer is obtained, which is why the page needs a large enough buffer, and an explicit charset always wins over the locale’s. How a locale maps to a charset, and what to declare so that the result never depends on the container, is on the Character Encoding page.

After setting the response locale, an action stores the charset of the response in the scoped variable jakarta.servlet.jsp.jstl.fmt.request.charset in session scope, if a session exists and is valid. That variable exists for the next action.

Source: Jakarta Standard Tag Library 3.0 — 8.4 Response Encoding

Security: fmt:message Does Not Escape

Neither fmt:message nor fmt:param escape their output. The text of the bundle is trusted (the application’s own), but a parameter that comes from the request or the database is not, and it is written into the page as markup. A message with the visitor’s input as a parameter is therefore a cross-site scripting hole unless the parameter is escaped.

Three ways to pass a request value as a parameter, escape.jsp with ?t=<script>alert(1)</script>
<%@ taglib prefix="fn" uri="jakarta.tags.functions" %>
<p>1: <fmt:message key="shelf.summary"><fmt:param value="${param.t}"/><fmt:param value="x"/><fmt:param value="y"/></fmt:message></p>
<p>2: <fmt:message key="shelf.summary"><fmt:param value="${fn:escapeXml(param.t)}"/><fmt:param value="x"/><fmt:param value="y"/></fmt:message></p>
<p>3: <fmt:message key="shelf.summary"><fmt:param><c:out value="${param.t}"/></fmt:param><fmt:param value="x"/><fmt:param value="y"/></fmt:message></p>
<p>4: <fmt:message key="${param.k}"/></p>
<p>1: <script>alert(1)</script> was written by x in y</p>
<p>2: &lt;script&gt;alert(1)&lt;/script&gt; was written by x in y</p>
<p>3: &lt;script&gt;alert(1)&lt;/script&gt; was written by x in y</p>
<p>4: Search</p>

Line 1 is the vulnerability. Lines 2 and 3 fix it, with fn:escapeXml (a function, available since JSTL 1.1) or with a c:out in the fmt:param body. The rule to apply uniformly is to escape every parameter that is not a constant, and to escape the whole message when the bundle itself contains no markup and the message is used as an attribute value or text. If a translated message legitimately contains markup, such as a link, keep that markup in the bundle and escape only the parameters.

Line 4 is a different problem: the key came from the request, so a visitor can read any message of the bundle (form.search was returned), which can reveal internal or unreleased text. Keys should be literals or come from the application, never from a request parameter. The same applies to the basename of fmt:bundle and to a locale taken from a parameter (see the table of fmt:setLocale).

Bundle files are application resources. They should live inside the classpath (WEB-INF/classes or a library), not in a directory served by the container, and translations received from third parties are reviewed like code, because a translation can contain markup and the tag does not escape it.

The Same Idea in Spring and Struts

fmt:message is not the only way to reach a bundle from a JSP. Spring MVC resolves the locale with a LocaleResolver (accept-header, cookie or session, plus an interceptor that reads a request parameter) and reads messages with a MessageSource; its JSP tag library offers spring:message for the same job as fmt:message, and the two libraries can coexist on a page. In Struts the bundles are resolved by the framework with a different search order, and the Localization and i18n page of the Struts part describes it. The point for a JSP author is that the concept (locale chosen per request, text by key, parameters by position) is the same in all of them, while the bundle search algorithm and the way a locale is selected are specific to each.

What Changed Recently

The i18n actions are stable: chapter 8 of Tags 3.0 describes the same actions as JSTL 1.0. What changed is around them.

Table 15. Changes that affect the i18n actions
Version Change Effect for JSP authors

Jakarta Tags 2.0 (Jakarta EE 9)

The packages moved from javax.servlet.jsp.jstl to jakarta.servlet.jsp.jstl

Imports of LocaleSupport, Config and LocalizationContext change; the library and fmt: actions are the same

Jakarta Tags 3.0 (Jakarta EE 10, Java 11)

Tag URIs renamed to jakarta.tags.*, JPMS module info added, dependency on XML Binding removed from the API

uri="jakarta.tags.fmt"; the older URIs still resolve in the 3.0.1 implementation (observed)

Java 9 (JEP 226)

PropertyResourceBundle reads .properties files as UTF-8, falling back to ISO-8859-1

Bundles can contain accented characters directly; native2ascii and ñ escapes are no longer necessary

Tomcat 10.1 and 11

conf/web.xml sets request and response character encoding to UTF-8

UTF-8 forms work without fmt:requestEncoding; a Latin-1 form posted without a charset now gets HTTP 400 (observed)

Jakarta EE 11 (Pages 4.0, Servlet 6.1)

Tags stays at 3.0

Nothing changes in fmt: usage

Jakarta Tags 3.1 (Jakarta EE 12, under development)

The Jakarta site lists the specification as under development; Tags 3.1.0-M2 is the milestone API on Maven Central

Per the section’s baseline, java.time support in the formatting actions is planned; the i18n actions are not announced to change. Treat it as in progress, not as a feature to rely on

Where the Books Are Outdated

JSTL in Action (Manning, 2002, JSTL 1.0 on JSP 1.2) devotes a chapter to formatting and internationalization, and its chapters on configuration and on control and performance touch the topic again. It is listed in the section bibliography. The concepts it teaches (locale, bundle, basename, the localization context, fmt:message with parameters, the fallback locale, fmt:requestEncoding, the Config settings) are the same today; the platform around them is not.
