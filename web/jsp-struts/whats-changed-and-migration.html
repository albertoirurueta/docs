What’s Changed & Migration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page was verified on 2026-10-10 against Jakarta Pages 4.0, Jakarta Expression Language 6.0, Jakarta Standard Tag Library (Jakarta Tags) 3.0, Jakarta Servlet 6.1, Apache Tomcat 11.0.26, Apache Struts 7.4.0 (released 2026-10-02) and 6.12.0, Java 21, Spring Framework 7.0.9 and Spring Boot 4.1.1. It is the section’s collection point: it says what changed between the platform of the four reference books (Servlet 2.3 and 2.4, JSP 1.2 and 2.0, JSTL 1.0, Struts 1 and Struts 2.0, Tomcat 4 to 6, the javax namespace) and the platform the rest of the section teaches, and how to move an old application across the gap. The running scenario is the Bookshelf: a catalogue of books with a list page, an "add a book" form and a lend action. Here it is first an application of the javax era (a servlet, a filter, a tag handler, a tag library descriptor and a JSP using JSTL 1.2), which is converted three ways, and then a Struts application that crosses the 2.3, 2.5, 6 and 7 borders one change at a time. Every example that runs was built into a WAR and deployed on Tomcat 11.0.26 with Java 21 and requested with curl; the "before" snippets that cannot run on a current container (Servlet 2.3, Struts 2.3) are marked as such. The repository’s Bookshop legacy-migration scenario (a Struts 1 and JSP monolith moved to a modern stack) is linked in Modernisation Paths; the Faces-based path is covered by the JSF (JavaServer Faces) section. Pages of this section that explain the topics summarised below are linked from the tables, and the books themselves appear only in the bibliography and in the "where the books are outdated" parts, never as a source of text.

The Version Map

The platform moved in generations. Each generation changed the Java package of the APIs, the version of the descriptor and, for the later ones, the minimum Java version, and a book written for one generation describes the others only by accident. The timeline puts the specification generations, Tomcat and Struts on one axis; the dates are the dates of the JCP records, the Jakarta specification pages and the Struts announcements that Introduction and History lists with their sources.

From javax to jakarta, with the Tomcat Migration Tool

Jakarta Servlet 5.0 "is only a change of namespaces", in the words of the specification’s compatibility appendix, and migrating a Servlet 4.0 project to 5.0 or later "requires the replacement of the namespace javax.* with jakarta.*`". Pages 3.0 lists the same move first among its changes (`javax.servlet.jsp to jakarta.servlet.jsp), Jakarta Tags 3.0 says that applications using the Java EE package "will need to change this to the Jakarta EE package", and the Tomcat migration guide calls it "a significant breaking change between Tomcat 9.0.x and Tomcat 10.0.x". The Introduction and History page has the table of renamed packages; this page shows what happens to a real WAR.

The Bookshelf as a javax WAR

The WAR was built for this page with Java 17, javax.servlet-api 4.0.1 and javax.servlet.jsp-api 2.3.3 as provided dependencies and JSTL 1.2 (javax.servlet:jstl) in WEB-INF/lib. It has a servlet registered with @WebServlet, a filter declared in web.xml, a SimpleTag handler with its tag library descriptor, and a JSP that uses JSTL through the java.sun.com library URIs.

The servlet and the filter of the javax era
// BooksServlet.java
import javax.servlet.annotation.WebServlet;
import javax.servlet.http.HttpServlet;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;

@WebServlet("/books")
public class BooksServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        req.setAttribute("books", Arrays.asList(
                new Book(1, "Dune", "Frank Herbert", 1965),
                new Book(2, "Neuromancer", "William Gibson", 1984)));
        req.getRequestDispatcher("/WEB-INF/views/books.jsp").forward(req, resp);
    }
}

// AuditFilter.java
public class AuditFilter implements javax.servlet.Filter {
    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) throws IOException, ServletException {
        ((HttpServletResponse) res).setHeader("X-Bookshelf-Audit", "javax");
        chain.doFilter(req, res);
    }
}

What Happens Without Migration

Dropped into the webapps directory of Tomcat 11.0.26 as it is, the WAR does not start. The filter named in web.xml extends an interface that the container no longer has, so the context fails, and every URL of it answers 404:

$ curl -s -o /dev/null -w "GET /bookshelf-javax/books -> %{http_code}\n" http://localhost:18180/bookshelf-javax/books
GET /bookshelf-javax/books -> 404

SEVERE [Catalina-utility-2] org.apache.catalina.core.StandardContext.filterStart Exception starting filter [audit]
	java.lang.NoClassDefFoundError: javax/servlet/Filter
	Caused by: java.lang.ClassNotFoundException: javax.servlet.Filter

A servlet that is registered only by annotation fails more quietly: the annotation scan looks for jakarta.servlet.annotation.WebServlet, finds nothing, and the application deploys cleanly and answers 404 without a message. The failing "before" case of that variant, with its two servlets, is on the Introduction and History page.

Conversion at Deployment: legacyAppBase

The first remedy needs no tool of your own. Each Tomcat host has a legacyAppBase directory, webapps-javaee by default, and the Host documentation says that Java EE applications placed there "will be converted to Jakarta EE using the Apache Tomcat Migration Tool for Jakarta EE", with the result placed in the appBase. On 11.0.26 the default works without any configuration: the instance used for this page has no legacyAppBase attribute in server.xml, and copying bookshelf-javax.war into the empty webapps-javaee directory produced, a few seconds later, a converted application in webapps that answered normally:

Conversion Ahead of Time: the Migration Tool

The Tomcat migration guide recommends the same tool ahead of time "to benefit from faster deployment time and more precise conversion configuration options". Tomcat 11.0.26 bundles version 1.0.12 as lib/jakartaee-migration-1.0.12-shaded.jar behind bin/migrate.sh; the current release on Maven Central at the time of writing is 1.0.13 (published as a shaded jar, with a bin distribution next to it), and the download page of the Apache Tomcat site lists the same 1.0.13. Tomcat 11 starts a web.xml of any version it can parse, and for pages the descriptor version has one documented effect on the language: the Pages specification says that the default mode for JSP pages in an application delivered with a Servlet 2.3 or earlier descriptor is to ignore EL, "for backward compatibility". Two things changed from the books' point of view. In JSP 1.2 there was no EL at all, and in a JSTL 1.0 tag the EL lived inside the library and ended at the attribute, which is why the books' claim that EL does not work in template text is true only of that pair; since JSP 2.0 ${...} works anywhere in the page, as the ignored-EL table above shows for the one case (an old descriptor) where it still does not. The EL pitfalls of an upgrade are mostly in the table the earlier pages collected, and the three that bite first are these:

  • ${bean.class.name} stopped parsing (shown above); write ${bean.getClass().getName()}.

  • A record is read by its component name (${isbn.code}), and on Tomcat 11 a bean-style getter on a record is not reachable as a property.

@StrutsParameter, OGNL and the Allowlist

The 6 to 7 guide calls the next group "stronger security", and it is where an application that compiles after the repackaging still misbehaves, because nothing fails: a value is silently not bound or a property silently prints nothing. Three Struts 7.4.0 defaults, read from default.properties, decide it: struts.parameters.requireAnnotations is true, struts.allowlist.enable is true, and struts.ognl.allowStaticFieldAccess is false.

Modernisation Paths

A migration does not have to end at "the same application on a newer platform". Three destinations are realistic for a Bookshelf-sized JSP or Struts application, and the choice is the one the repository’s architecture pages already describe for a legacy monolith.

  • Stay on JSP and Struts, current versions. The cheapest path when the application is stable: the steps of this page, in order, then keep the Struts line current. It is the right answer for an internal application that changes little.

  • Struts or JSP to Spring MVC with Thymeleaf (or another template engine), one screen at a time. The strangler-fig path. The Spring MVC page of this section, Spring MVC with JSP, shows the first step (new controllers that still render JSP views, in a WAR), and the Thymeleaf section carries the destination: Thymeleaf: Introduction and Architecture and Thymeleaf: What’s Changed and Migration. The comparison of the web UI options for Spring Boot is Web UI Frameworks, and the javax.* to jakarta.* switch of Spring Boot 3 is in Spring Boot: Getting Started.

  • Faces. A component-based move is a different programming model; it is covered by the JSF: Migrating to Jakarta Faces page and the rest of the JSF (JavaServer Faces) section, and is not described here.

The repository’s Bookshop scenario, a Struts 1 and JSP monolith moved to a modern stack, is the longer story of the first two paths with its phases, risks and decisions, in Migration Path: Legacy to Modern Stack, with the general view of migration strategies in Migration Overview; the Struts 1 specifics (a dual request processor, the concept map) are on Struts 1 (Classic) and Migration.

Pitfalls

Pitfall Symptom Remedy

A javax WAR dropped into Tomcat 10.1 or 11

A filter or listener in web.xml stops the context (NoClassDefFoundError: javax/servlet/Filter, every URL 404); a servlet registered only by annotation deploys silently and answers 404

Convert at the source, with the migration tool ahead of time, or through webapps-javaee; read the log, not the HTTP status (What Happens Without Migration)

Trusting the converted WAR to be modern

The descriptors still name Java EE 8 (xmlns.jcp.org, version="4.0", the 2.1 TLD schema) and the JSTL URIs are unchanged

Plan the source-level migration anyway; the next javax import mixes two namespaces in one application (Conversion Ahead of Time: the Migration Tool)

Converting only the application’s own jars

The tool also converts the jars bundled in WEB-INF/lib, but not libraries installed in Tomcat’s lib directory or other shared locations

Keep libraries in the WAR, or convert the shared jars with the same tool before installing them

JasperException for an old page on the first request

isThreadSafe or jsp:plugin fails at translation, not at startup

Precompile with JspC in the build to find every old page at once (Jasper Configuration and Precompilation)

${bean.class.name} or ${exception.class.name}

Failed to parse the expression

${bean.getClass().getName()}

Expecting EL to work under an old descriptor

${...} printed literally in every page of a WAR whose web.xml is a Servlet 2.3 DTD

Move the descriptor to the schema of the version in use, or set el-ignored to false in a property group

Old JSTL URIs left in place

Nothing fails today (the 3.0.1 jar still resolves them), so they survive into the next library change; xmlns.jcp.org URIs fail immediately

Replace with jakarta.tags.* while the diff is small

fileUpload or timer interceptor references

The whole application fails to start; every URL of the context is 404 and the only trace is Unable to find interceptor class referenced by ref-name in the log

Replace fileUpload with actionFileUpload and drop timer; test the startup, not only a request

Unannotated setters after the move to 7

Parameters silently not bound, no error on the page

Add @StrutsParameter after reviewing each setter; use the transition mode of 7.4.0 while you do it

Plain POJOs on a page after the move to 7

<s:property> prints nothing and the log has a warning about a class that is "not allowlisted"

Add the model package to struts.allowlist.packageNames; do not turn the allowlist off

Old constant names

Silently ignored (struts.xwork.chaining.copyMessages)

Use the 6.0 names from the constants table

action!method links and buttons

404 There is no Action mapped for namespace [/] and action name [books!lend]

Map the method as its own action, or use wildcard method selection with <allowed-methods> placed after the results

A new servlet next to Struts at an extensionless URL

Struts answers 404 for the URL before the servlet is reached

struts.action.extension set to action, or struts.action.excludePattern; update the legacy links

Copying a class from the official Struts documentation

package com.opensymphony.xwork2 does not exist, or a javax.validation import that does not resolve

Take the org.apache.struts2 and jakarta names of Packages, Aware Interfaces and Actions; the documentation page is stale, not the framework

Upgrade Checklist

The checklist is the order that the sections above follow, and each step names what proves it. It assumes the target of this section, Tomcat 11 with Java 21 and Struts 7.4, and takes a legacy javax JSP application with Struts 2.3 as the longest case; a JSP-only application skips the Struts steps.

Before touching the code

  1. Inventory the application: container and Java versions, web.xml version, JSP and JSTL libraries and their URIs, Struts version and plugins, and every third-party jar that still imports javax.*.

  2. Run the tests, and record the answer of ten real URLs with curl; they are the regression suite for everything below.

  3. If the aim is only to run on Tomcat 11 first, convert with the migration tool (webapps-javaee or the command line), run the ten URLs, and stop here for the first release.

Platform and JSP

  1. Change javax.servlet, javax.servlet.jsp and javax.el imports to jakarta.*, the dependencies to jakarta.servlet-api 6.1.0, jakarta.servlet.jsp-api 4.0.0 and jakarta.el-api 6.0.1 (provided), and JSTL to the 3.0 API and the 3.0.1 implementation (Conversion at the Source).

  2. Move web.xml to the 6.1 schema and every TLD to the 4.0 schema; keep version and namespace in step.

  3. Replace the removed Servlet and Pages API (SingleThreadModel, HttpUtils, getValue and friends, EVAL_BODY_TAG, getRootCause, the jakarta.servlet.jsp.el classes) with the replacements of Jakarta Servlet: What Changed and What Was Removed.

  4. Delete isThreadSafe and jsp:plugin; replace .class.name in EL; replace the JSTL URIs with jakarta.tags.*.

  5. Precompile all JSPs with JspC in the build, so translation errors surface at build time.

Struts, in the order of the guides

  1. Move to 2.5.33, then 6.12.0, then 7.4.0, running the ten URLs after each step: filter class and DTD (2.5), tag attributes and the removed s:div (2.5), constants, the Aware interfaces and static method access (6), jakarta, org.apache.struts2, @StrutsParameter, the allowlist, actionFileUpload and the removed plugins (7).

  2. Start the application and read the log from the top: a Struts filter that fails to initialise leaves a running context and a 404 for every URL.

  3. Review every @StrutsParameter you added, every struts.allowlist.* entry, and every place where a DMI link was replaced.

  4. Update the version of every plugin to the one of the core, and set the struts2-bom so that no plugin version is hard-coded.

After

  1. Replace the old descriptor namespaces and URIs that the tool or Tomcat tolerated.

  2. Run the security checks of the section (Security Hardening, Security) and read the security bulletins of the line you are on (Security Bulletins).

  3. Decide what the application is: maintained on JSP and Struts, or on its way to Spring MVC and Thymeleaf (Modernisation Paths), and write the decision next to the version numbers.
