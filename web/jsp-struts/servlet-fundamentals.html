Servlet Fundamentals

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Servlet 6.1 (Jakarta EE 11), the specification that Apache Tomcat 11.0.26 implements together with Jakarta Pages 4.0, Jakarta Expression Language 6.0 and Jakarta Standard Tag Library 3.0, on Java 21 (the specifications need Java 17 or later). Everything was verified on 2026-10-08: the facts against the Servlet 6.1 specification, its Javadoc and the Tomcat 11.0 documentation, and every example by building it into a Maven WAR and running it on Tomcat 11.0.26 with curl; the outputs shown are the outputs that run produced. Servlets are the layer underneath both halves of this section. A JSP is translated into a servlet (JSP Lifecycle and Translation), and Struts 7 is a filter plus a set of servlet-API calls, so the vocabulary on this page (request, response, scope, filter, dispatcher, mapping, error page) is the vocabulary the rest of the section uses. The running scenario is the Bookshelf, a small catalogue of books that grows from a servlet that lists three titles into an application with sessions, cookies, filters, listeners, error pages and a cover-image upload.

What a Servlet Is and Where It Runs

A servlet is a Java class that a servlet container (Tomcat, Jetty, GlassFish, WildFly and others) instantiates, calls and destroys, in order to turn a request into a response. The specification defines the contract between container and application: the Servlet interface, the request and response objects, the application-wide ServletContext, the packaging of a web application as a WAR, and the deployment descriptor web.xml. Almost every Java web technology sits on top of that contract. A JSP page is compiled into an HttpJspPage servlet, Struts 2 installs a servlet filter, Spring MVC is a single DispatcherServlet, and the Jakarta Faces runtime is the FacesServlet.

The container does the work that is the same for every application: it listens on a socket, parses HTTP, selects the web application and the servlet from the URL, manages threads, tracks sessions, applies filters, handles errors and cleans up. The application supplies only the code that is different.

The HTTP Contract Behind a Servlet

Servlets implement a thin layer over HTTP, so a few protocol facts decide how every servlet is written. HTTP is a request/response protocol: the client sends a request line, headers and optionally a body, and the server answers with a status line, headers and a body. It is stateless: nothing in the protocol links two requests, which is why the servlet API adds sessions on top. The raw exchange for a form POST to the example’s /search servlet is:

curl -sv -d 'title=Dune&tag=sf' http://localhost:18080/g2-servlet/search -o /dev/null
> POST /g2-servlet/search HTTP/1.1
> Host: localhost:18080
> Accept: */*
> Content-Length: 17
> Content-Type: application/x-www-form-urlencoded
>
< HTTP/1.1 200
< Content-Type: text/plain;charset=UTF-8
< Content-Length: 302

The Servlet Lifecycle and the Threading Model

The container manages every servlet through a fixed lifecycle expressed by three methods of the Servlet interface. HttpServlet and GenericServlet implement it, so an application normally overrides init() (the no-argument convenience), a doXxx method and destroy().

Table 4. The servlet lifecycle (specification chapter 2)
Phase Container call What the application should know

Load and instantiate

the class is loaded and a public no-argument constructor runs

At startup or lazily on the first request. loadOnStartup (or <load-on-startup>) asks for startup; a non-negative value means "at deployment, lowest numbers first"

Initialize

init(ServletConfig) exactly once

Read init parameters, open expensive resources. If it throws ServletException or UnavailableException, the servlet is not put in service, destroy() is not called, and the container may try a fresh instance later

Serve

service(request, response) for every request, possibly on many threads at once

HttpServlet.service dispatches to doGet, doPost, and the other doXxx methods; a servlet may legitimately handle no request at all

Destroy

destroy() once, after all requests have left service

Release resources. It runs at undeploy or shutdown, or when an UnavailableException marks the servlet permanently unavailable

The rule that shapes every design is in section 2.2 of the specification: unless the application is marked distributable, the container uses one instance per servlet declaration. Every request that reaches that declaration runs on a different thread but calls the same object. Fields of a servlet are therefore shared mutable state, exactly as if they were static.

A servlet with one shared counter, read-only configuration and a destroy hook
@WebServlet(urlPatterns = "/lifecycle", loadOnStartup = 1,
        initParams = @WebInitParam(name = "greeting", value = "Hello from init"))
public class LifecycleServlet extends HttpServlet {

    private final AtomicInteger hits = new AtomicInteger(); // shared by every request thread
    private String greeting;                                 // written once in init, read-only afterwards

    @Override
    public void init() throws ServletException {
        greeting = getInitParameter("greeting");
        EventLog.of(getServletContext()).add("LifecycleServlet.init, instance " + System.identityHashCode(this));
    }

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        resp.setContentType("text/plain;charset=UTF-8");
        resp.getWriter().printf("%s%ninstance=%d hits=%d thread=%s%n", greeting,
                System.identityHashCode(this), hits.incrementAndGet(), Thread.currentThread().getName());
    }

    @Override
    public void destroy() {
        getServletContext().log("LifecycleServlet.destroy after " + hits.get() + " hits");
    }
}

The shared counter is an AtomicInteger, and greeting is written once in init before any request thread can see the servlet, so both are safe. HttpServlet, HTTP Methods and Method Handling

HttpServlet.service reads the HTTP method and calls the matching method. A servlet overrides only the methods it supports, and the base class answers the rest.

Table 6. The doXxx methods of HttpServlet
Method Behaviour

Safe, idempotent retrieval. Override getLastModified to enable conditional GET (If-Modified-Since) handling

doPost

Form submissions and state changes; the usual target of a Post/Redirect/Get flow

doPut, doDelete, doPatch

Servlet 6.0 added PATCH support to the specification; the container routes them to the corresponding method if you override it

Requests: Parameters, Headers, Paths and Attributes

An HttpServletRequest gives the servlet read access to everything the client sent and a small writable map of attributes. The accessors fall into five groups.

Table 7. The main request accessors
Group Methods and rules

Request line

getMethod(), getRequestURI() (the raw path, still percent-encoded, without the query), getRequestURL() (scheme, host, port and path), getQueryString(), getProtocol(), getScheme(), isSecure()

Path elements

getContextPath(), getServletPath(), getPathInfo(). The request URI is always context path plus servlet path plus path info (plus path parameters such as ;jsessionid), see the mapping section

Parameters

getParameter(name), getParameterValues(name), getParameterMap(), getParameterNames(). They merge the query string and, for a form POST with application/x-www-form-urlencoded, the body. Multipart text fields are also parameters when the servlet has @MultipartConfig

Headers

getHeader(name) (first value, name is case-insensitive), getHeaders(name) (all values), getHeaderNames(), getIntHeader, getDateHeader; getLocale() and getLocales() parse Accept-Language; getContentType(), getContentLength(), getCharacterEncoding()

Body and connection

getReader() or getInputStream() (one of them, never both), getRemoteAddr(), getServerName(), getServerPort(), and the 6.0 identifiers getRequestId(), getProtocolRequestId() and getServletConnection()

Attributes

setAttribute, getAttribute, removeAttribute: per-request storage used to pass the model from a controller servlet to a view

The one rule about parameters that surprises people is ordering. Parameters are parsed on the first call to any parameter method, and a form body can be consumed only once. If a servlet or filter reads the body with getReader() or getInputStream() first, the container has nothing left to parse and getParameter returns null for form fields. In Servlet 6.1 a failure during parsing (a malformed body, an exceeded limit) makes the parameter methods throw a runtime exception, so a filter that touches parameters must be prepared to catch it (specification change log, issue 431).

The next servlet prints what the container exposes for a request. It is mapped to /search and, as the filter section will show, runs behind a request wrapper that trims whitespace around every parameter value.

Reading parameters, headers and locale
@WebServlet("/search")
public class SearchServlet extends HttpServlet {

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        handle(req, resp);
    }

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        handle(req, resp);
    }

    private void handle(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        resp.setContentType("text/plain");           // the charset comes from web.xml (UTF-8)
        PrintWriter out = resp.getWriter();
        out.println("method=" + req.getMethod() + " query=" + req.getQueryString());
        out.println("request encoding=" + req.getCharacterEncoding() + " type=" + req.getContentType());
        out.println("title=" + req.getParameter("title"));
        out.println("tag=" + Arrays.toString(req.getParameterValues("tag")));
        Map<String, String[]> sorted = new TreeMap<>(req.getParameterMap());
        sorted.forEach((k, v) -> out.println("  param " + k + " -> " + Arrays.toString(v)));
        out.println("Accept-Language=" + req.getHeader("Accept-Language"));
        out.println("locale=" + req.getLocale() + " locales=" + Collections.list(req.getLocales()));
        out.println("Accept (all values)=" + Collections.list(req.getHeaders("Accept")));
        out.println("User-Agent present=" + (req.getHeader("User-Agent") != null));
        out.println("response encoding=" + resp.getCharacterEncoding() + " locale=" + resp.getLocale()
                + " (" + Locale.getDefault() + " default)");
    }
}

Reading Headers: Content Negotiation in a Controller

Headers drive content negotiation. The BookServlet of the example serves the same catalogue as HTML or JSON depending on the Accept header, and sets Vary: Accept so that a shared cache keeps the two representations apart.

BookServlet.doGet: one URL, two representations, path info for the id
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        Catalogue catalogue = Catalogue.of(getServletContext());
        String info = req.getPathInfo();                      // null for /books, "/2" for /books/2

        if (info == null || info.equals("/")) {
            req.setAttribute("books", catalogue.all());
            req.setAttribute("csrf", csrfToken(req.getSession()));
            if (wantsJson(req)) {
                resp.setContentType("application/json");
                resp.setHeader("Vary", "Accept");
                resp.getWriter().write(toJson(catalogue));
                return;
            }
            resp.setHeader("Vary", "Accept");
            req.getRequestDispatcher("/WEB-INF/views/books.jsp").forward(req, resp);
            return;
        }

        long id;
        try {
            id = Long.parseLong(info.substring(1));
        } catch (NumberFormatException e) {
            resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "Book ids are numbers");
            return;
        }
        Optional<Book> book = catalogue.find(id);
        if (book.isEmpty()) {
            resp.sendError(HttpServletResponse.SC_NOT_FOUND);
            return;
        }
        req.setAttribute("book", book.get());
        req.getRequestDispatcher("/WEB-INF/views/book.jsp").forward(req, resp);
    }

Character Encoding

Encoding is the most common reason for garbled accented characters in a servlet application, and the specification’s defaults are older than the web.

Table 8. The encoding rules of Servlet 6.1 (sections 3.13 and 5.6)
Situation Rule

Request body, application/x-www-form-urlencoded, no charset in Content-Type

The container must decode with US-ASCII and treat %nn values as ISO-8859-1; getCharacterEncoding() returns null to show the charset is unknown

Any other request body without charset

ISO-8859-1, unless the application or container configured something else

Configure the request encoding

<request-character-encoding> in web.xml, ServletContext.setRequestCharacterEncoding at startup, or request.setCharacterEncoding before any parameter is read or any input consumed; calling it afterwards has no effect

Response with no encoding set

ISO-8859-1 for the writer

Configure the response encoding

<response-character-encoding>, ServletContext.setResponseCharacterEncoding, response.setCharacterEncoding, a charset in setContentType, or setLocale with a locale-encoding mapping. Calls after getWriter() or after commit are ignored

URL path and query string

Decoded as UTF-8 per section 12.1; containers may offer a vendor option (Tomcat’s connector has URIEncoding)

The container may buffer output. Committing a response, and what a late change does
@WebServlet("/buffer")
public class BufferServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        resp.setContentType("text/plain;charset=UTF-8");
        resp.setBufferSize(16 * 1024);                       // a hint: the container may give more, never less
        PrintWriter out = resp.getWriter();
        out.println("bufferSize>=16384: " + (resp.getBufferSize() >= 16 * 1024));
        switch (String.valueOf(req.getParameter("mode"))) {
            case "reset" -> {
                out.println("draft that will be discarded");
                resp.resetBuffer();                            // clears the body, keeps status and headers
                out.println("final body, committed=" + resp.isCommitted());
            }
            case "late-header" -> {
                out.println("first line");
                resp.flushBuffer();                            // commits: status line and headers are on the wire
                resp.setHeader("X-Too-Late", "1");             // silently ignored
                resp.setStatus(500);                           // silently ignored
                out.println("committed=" + resp.isCommitted());
            }
            case "late-error" -> {
                out.println("first line");
                resp.flushBuffer();
                try {
                    resp.sendError(500, "too late");
                } catch (IllegalStateException e) {
                    out.println("sendError after commit -> IllegalStateException");
                }
                try {
                    resp.resetBuffer();
                } catch (IllegalStateException e) {
                    out.println("resetBuffer after commit -> IllegalStateException");
                }
            }
            case "late-session" -> {
                out.println("first line");
                resp.flushBuffer();
                try {
                    req.getSession();                              // would need a Set-Cookie header
                    out.println("session created, id from cookie=" + req.isRequestedSessionIdFromCookie());
                } catch (IllegalStateException e) {
                    out.println("getSession after commit -> IllegalStateException");
                }
            }
            default -> out.println("modes: reset, late-header, late-error, late-session");
        }
    }
}

@WebServlet("/redirects")
public class RedirectServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        String target = req.getContextPath() + "/books";
        switch (String.valueOf(req.getParameter("mode"))) {
            case "default" -> resp.sendRedirect(target);                                     // 302
            case "relative" -> resp.sendRedirect("books");                                   // relative to this request URI
            case "303" -> resp.sendRedirect(target, HttpServletResponse.SC_SEE_OTHER);       // 6.1: choose the status
            case "308" -> resp.sendRedirect(target, HttpServletResponse.SC_PERMANENT_REDIRECT); // 6.1 constant for 308
            case "keep-body" -> {
                resp.setContentType("text/plain;charset=UTF-8");
                resp.getWriter().print("my own redirect body");
                resp.sendRedirect(target, HttpServletResponse.SC_TEMPORARY_REDIRECT, false);  // 6.1: do not clear the buffer
            }
            case "bad" -> resp.sendRedirect("http://[bad host");                             // not a valid URL
            default -> resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "unknown mode");
        }
    }
}

Sessions

HTTP is stateless, so the container associates requests of one client through a session id. The HttpSession interface hides the mechanism. Cookies are the mechanism every container must support, URL rewriting is the fallback, and an SSL session id is a third, rarely used option.

The session lifecycle is: created lazily by request.getSession() (or getSession(true)); looked up without creating by getSession(false), which returns null when there is none; replaced on privilege change with changeSessionId(); ended by invalidate() or by the idle timeout. A session is new until the client has returned the cookie, so the first request is the only one on which isNew() is true, and a servlet must work when the client never joins the session.

Timeouts have two scales: ServletContext.setSessionTimeout and <session-timeout> use minutes, while HttpSession.setMaxInactiveInterval uses seconds, and a zero or negative value means the session never expires.

Objects stored in a session follow a few rules that come from the container, not from the language. They should be small and Serializable (the container may persist or replicate the session; Tomcat’s standard manager preserves sessions across restarts when its pathname attribute is set), thread-safe or guarded, because the same session can serve two requests at once, and well-behaved JavaBeans (public no-argument constructor, getXxx/isXxx/setXxx accessors) when a JSP is going to read them through EL. An object that needs to know when it joins or leaves a session implements HttpSessionBindingListener, as Cart does; one that holds non-serializable resources implements HttpSessionActivationListener to drop and re-acquire them around passivation. The bean conventions themselves are covered by Standard Actions & JavaBeans.

A cookie is a name and value that the server asks the client to store and return.         String theme = req.getParameter("theme");
        if (theme != null) {
            if (!THEMES.contains(theme)) {                     // never copy raw input into a cookie value
                resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "unknown theme");
                return;
            }
            Cookie cookie = new Cookie("theme", theme);
            cookie.setPath(req.getContextPath().isEmpty() ? "/" : req.getContextPath());
            cookie.setMaxAge(30 * 24 * 60 * 60);                // seconds; -1 = browser session, 0 = delete
            cookie.setHttpOnly(true);
            cookie.setSecure(req.isSecure());                   // Secure only makes sense over HTTPS
            cookie.setAttribute("SameSite", "Lax");              // Servlet 6.0: generic cookie attributes
            if ("1".equals(req.getParameter("partitioned"))) {
                cookie.setAttribute("Partitioned", "");          // attribute without a value
            }
            resp.addCookie(cookie);
            resp.getWriter().println("theme cookie set to " + theme);
        } else if ("1".equals(req.getParameter("clear"))) {
            Cookie cookie = new Cookie("theme", "");
            cookie.setPath(req.getContextPath().isEmpty() ? "/" : req.getContextPath());
            cookie.setMaxAge(0);                               // same name and path, or the browser keeps the old one
            resp.addCookie(cookie);
            resp.getWriter().println("theme cookie cleared");
        } else {
            Cookie[] cookies = req.getCookies();               // null when the request has no Cookie header
            String current = "none";
            if (cookies != null) {
                for (Cookie c : cookies) {
                    if (c.getName().equals("theme")) {
                        current = c.getValue();
                    }
                }
            }
            resp.getWriter().println("theme=" + current + " (browsers send only name and value back)");
        }
    }
}

Filters, Wrappers and the Filter Chain

A filter is an object that intercepts requests to a servlet, a JSP or a static file, and responses on the way back. It can inspect or reject the request, wrap the request or response to change what later components see, and post-process the response. Authentication, logging, compression, character-encoding fixes, CORS headers and page layout (SiteMesh) are all filters, and so is the Struts 2 entry point, StrutsPrepareAndExecuteFilter (see Architecture & Request Lifecycle).

Table 16. The Filter contract
Member Rule

init(FilterConfig)

Called once per declaration before the first request; FilterConfig gives init parameters and the ServletContext. Throwing UnavailableException marks the filter unusable

doFilter(request, response, chain)

Called for every matching request, on the same thread as the servlet. Calls chain.doFilter(request, response) to continue, with the originals or with wrappers, or does not call it to block the request and write the response itself

destroy()

Called once when the filter is removed from service

One instance per <filter> declaration, shared by all threads, like a servlet. Declaring the same class twice creates two instances

Declaring and Ordering Filters

A filter is declared with @WebFilter or a <filter> element, and attached with <filter-mapping> to URL patterns or servlet names. The order of the chain is defined by the specification (section 6.2.4): first all <url-pattern> mappings that match the request, in the order they appear in web.xml, then all <servlet-name> mappings that match, in the order they appear. The last filter calls the servlet. The order of filters declared only by annotations is unspecified, so a chain whose order matters needs web.xml (or programmatic registration, where isMatchAfter controls the position).

The Bookshelf declares three instances of one timing filter, all with <async-supported>, in this order: a mapping by servlet name (written first), then outer and inner for /*:

A pass-through filter: code before and after chain.doFilter
public class TimingFilter implements Filter {
    private ServletContext ctx;
    private String label;

    @Override
    public void init(FilterConfig config) {
        ctx = config.getServletContext();
        label = config.getInitParameter("label");
    }

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest req = (HttpServletRequest) request;
        boolean trace = req.getHeader("X-Trace") != null;
        long start = System.nanoTime();
        if (trace) {
            EventLog.of(ctx).add(label + " before " + req.getDispatcherType() + " " + req.getRequestURI());
        }
        try {
            chain.doFilter(request, response);               // everything after this line runs on the way back
        } finally {
            if (trace) {
                EventLog.of(ctx).add(label + " after (" + (System.nanoTime() - start) / 1000 + " us)");
            }
        }
    }
}

Wrapping the Request

HttpServletRequestWrapper and HttpServletResponseWrapper implement the decorator pattern: a filter creates a subclass that overrides a few methods, passes the wrapper to chain.doFilter, and every servlet, JSP and later filter sees the modified behaviour without being aware of it. The container must pass the wrapper itself (or a wrapper of it) on to the next component (section 6.2.2).

The TrimFilter below wraps the request so that every parameter value reaches the servlet already trimmed. A wrapper must override all the accessors that expose the same data (getParameter, getParameterValues, getParameterMap, and getParameterNames uses the unchanged keys), or code that uses the one you forgot sees the raw value.

A request wrapper that trims parameters
public class TrimFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        chain.doFilter(new TrimmedRequest((HttpServletRequest) request), response);
    }

    static final class TrimmedRequest extends HttpServletRequestWrapper {
        TrimmedRequest(HttpServletRequest request) {
            super(request);
        }

        @Override
        public String getParameter(String name) {
            String value = super.getParameter(name);
            return value == null ? null : value.strip();
        }

        @Override
        public String[] getParameterValues(String name) {
            String[] values = super.getParameterValues(name);
            return values == null ? null : Arrays.stream(values).map(String::strip).toArray(String[]::new);
        }

        @Override
        public Map<String, String[]> getParameterMap() {   // override all accessors, or the filter has holes
            return super.getParameterMap().entrySet().stream().collect(Collectors.toMap(
                    Map.Entry::getKey, e -> Arrays.stream(e.getValue()).map(String::strip).toArray(String[]::new)));
        }
    }
}

Wrapping the Response and Why FORWARD Matters

A response wrapper captures the output of the rest of the chain so the filter can change it before it reaches the client: compress it, rewrite links, decorate it with a layout. The FooterFilter buffers a page in a CharArrayWriter and appends an HTML comment after the content of every text/html response:

A response wrapper that appends a footer to HTML
public class FooterFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        CapturingResponse wrapper = new CapturingResponse((HttpServletResponse) response);
        chain.doFilter(request, wrapper);
        String type = wrapper.getContentType();
        if (wrapper.captured() != null && type != null && type.startsWith("text/html")) {
            String html = wrapper.captured().toString();
            response.getWriter().write(html);
            response.getWriter().write("<!-- rendered by Bookshelf -->\n");
        } else if (wrapper.captured() != null) {
            response.getWriter().write(wrapper.captured().toString());
        }
    }

    static final class CapturingResponse extends HttpServletResponseWrapper {
        private CharArrayWriter buffer;
        private PrintWriter writer;

        CapturingResponse(HttpServletResponse response) {
            super(response);
        }

        @Override
        public PrintWriter getWriter() {
            if (writer == null) {
                buffer = new CharArrayWriter();
                writer = new PrintWriter(buffer);
            }
            return writer;
        }

        CharArrayWriter captured() {
            if (writer != null) {
                writer.flush();
            }
            return buffer;
        }
    }
}

A filter that does not call chain.doFilter ends the request. The AdminFilter protects /admin/* and the LoginServlet shows the safe login sequence (validate, rotate the session id, store the identity, redirect):

A filter that blocks anonymous requests
@WebFilter("/admin/*")
public class AdminFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest req = (HttpServletRequest) request;
        HttpServletResponse resp = (HttpServletResponse) response;
        HttpSession session = req.getSession(false);
        if (session == null || session.getAttribute("user") == null) {

Pluggability: Fragments and ServletContainerInitializer

Frameworks plug into a web application without touching web.xml. A library JAR in WEB-INF/lib can carry a META-INF/web-fragment.xml that contributes servlets, filters and listeners (ordered with <ordering> or the application’s <absolute-ordering>), static resources under META-INF/resources, and a ServletContainerInitializer registered in META-INF/services/jakarta.servlet.ServletContainerInitializer. The container calls onStartup(Set<Class<?>>, ServletContext) before any listener, passing every class that matches the @HandlesTypes annotation of the initializer. This is how Spring’s SpringServletContainerInitializer, Jasper and Jakarta Faces start themselves, and why a JAR on the classpath can change the behaviour of an application.

The example has a tiny initializer, registered through the services file, that records which filters the container found:

A ServletContainerInitializer that reports the Filter classes it was handed
@HandlesTypes(Filter.class)
public class ScanInitializer implements ServletContainerInitializer {
    @Override
    public void onStartup(Set<Class<?>> classes, ServletContext ctx) {
        List<String> names = classes == null ? List.of()
                : classes.stream().map(Class::getSimpleName).sorted().toList();
        ctx.setAttribute("filtersFound", names);
    }
}

RequestDispatcher: Forward, Include and Named Dispatch

A RequestDispatcher hands the current request to another resource inside the same container: a servlet, a JSP, a static file. It is the mechanism behind the Model 2 pattern (built out in MVC with Servlets & JSP): a controller servlet prepares the model as request attributes and forwards to a JSP that renders it (the BookServlet of this page does so). It comes from request.getRequestDispatcher(path) (the path may be relative to the current servlet), ServletContext.getRequestDispatcher(path) (must start with /) or ServletContext.getNamedDispatcher(name) (a servlet name from web.xml or @WebServlet(name=...)). A path can carry a query string, and the container merges the new parameters with the original ones, the new values first.

URL Mapping Rules

The container maps a request to a servlet in two steps. It first picks the web application with the longest context path that matches the start of the URL. Within the application it removes the context path and any path parameters (such as ;jsessionid=...), decodes the rest as UTF-8, and applies these rules in order, stopping at the first match:

Step Pattern form Rule

1

exact: a string such as /map/exact

The whole path equals the pattern

2

path prefix: /map/*

The longest prefix match, one directory at a time; the pattern matches /map, /map/ and everything below it

3

The last segment ends in .report

4

default: /

Error Pages

When a servlet calls sendError or lets an exception escape, the container renders an error response. The <error-page> element replaces the container’s default report with an application resource (the JSP side, with the errorPage attribute and isErrorPage, is in Error Handling; Struts maps exceptions to results instead, see Exception Handling and Global Results):

<error-page>

The matching rules (section 10.9.2) are:

  1. sendError(status): an <error-code> entry for that status.

  2. An exception that escapes: the <exception-type> entry whose class is the closest in the class hierarchy.

  3. If none matches and the exception is a ServletException, a second pass with getRootCause().

  4. Otherwise the default entry, an <error-page> without code and type.

  5. Otherwise the container’s own page, with status 500 for uncaught exceptions.

The error page is invoked by an ERROR dispatch that always uses the HTTP method GET, whatever the original method was, with the request path and attributes set as for a forward. Servlet 6.1 added jakarta.servlet.error.method for the original method and jakarta.servlet.error.query_string.

The outputs teach five things. The POST that failed was handled as GET with the original method in error.method. The servlet_name identifies the component that failed, including default for a missing resource. For an escaped runtime exception that matched the default entry, Tomcat 11 supplied the exception attribute but left exception_type null and the message empty, so an error page should read error.exception. A ServletException wrapping a SQLException reached the /errors/database page through the second, root-cause pass; the status was 500 in both. And when the response was already committed (committed), no error page can run: the client got the partial page and a truncated chunked body (curl exits with 18), which is the visible symptom of an exception after a flush.

When the same web.xml also declared <exception-type>java.lang.Throwable</exception-type>, the result for wrapped changed. That entry matches every exception at the first pass, so the wrapped case never reached /errors/database and produced /errors/generic with exception_type=class java.sql.SQLException: the root-cause pass is skipped whenever a broad type is declared. A catch-all belongs in the entry without code and type.

The error page mechanism does not apply to exceptions thrown inside a RequestDispatcher call or to errors that the calling filter handles itself, so a filter or servlet that dispatches gets the chance to deal with the error first. The error response is also the place to avoid leaking information: Tomcat’s default report shows the exception and the server version unless ErrorReportValve is configured (showReport, showServerInfo), so applications supply their own page and never print stack traces to users.

@WebServlet("/upload")
@MultipartConfig(location = "", fileSizeThreshold = 8 * 1024, maxFileSize = 64 * 1024, maxRequestSize = 128 * 1024)
public class UploadServlet extends HttpServlet {

    private static final Set<String> TYPES = Set.of("image/png", "image/jpeg");

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws ServletException, IOException {
        resp.setContentType("text/plain;charset=UTF-8");
        String contentType = req.getContentType();
        if (contentType == null || !contentType.toLowerCase().startsWith("multipart/form-data")) {
            resp.sendError(HttpServletResponse.SC_UNSUPPORTED_MEDIA_TYPE, "multipart/form-data expected");
            return;
        }
        Part cover;
        String title;
        try {
            title = req.getParameter("title");               // text fields arrive as ordinary parameters
            cover = req.getPart("cover");
        } catch (IllegalStateException e) {                  // size limits exceeded
            resp.setStatus(HttpServletResponse.SC_REQUEST_ENTITY_TOO_LARGE);
            resp.getWriter().println("upload rejected: too large");
            return;
        }
        if (cover == null || cover.getSize() == 0 || !TYPES.contains(cover.getContentType())) {
            resp.sendError(HttpServletResponse.SC_UNSUPPORTED_MEDIA_TYPE, "send a PNG or JPEG in the cover part");
            return;
        }
        String submitted = cover.getSubmittedFileName();     // the client's name: display only, never a file path
        String display = submitted == null ? "" : Paths.get(submitted.replace('\\', '/')).getFileName().toString();
        File dir = (File) getServletContext().getAttribute("jakarta.servlet.context.tempdir");
        Path target = dir.toPath().resolve(UUID.randomUUID() + ".png");     // the server picks the stored name
        try (InputStream in = cover.getInputStream()) {
            Files.copy(in, target);
        }
        resp.getWriter().println("title=" + title + " cover=" + display + " type=" + cover.getContentType()
                + " bytes=" + cover.getSize() + " stored=" + Files.exists(target));
        Files.delete(target);
    }
}

Asynchronous Processing in Brief

A servlet that waits for a slow resource (a remote service, a queue) can release the container thread instead of blocking it. It calls startAsync(), returns, and later completes the response from another thread with AsyncContext.complete() or re-dispatches with AsyncContext.dispatch. Both the servlet and every filter in its path must declare asyncSupported (annotation attribute or <async-supported>), or startAsync throws IllegalStateException. The example’s three timing filters declare it in web.xml.

Releasing the container thread while a slow task runs
@WebServlet(urlPatterns = "/async", asyncSupported = true)
public class AsyncServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        String requestThread = Thread.currentThread().getName();
        AsyncContext async = req.startAsync();               // the container thread is released when doGet returns
        async.setTimeout(5_000);
        async.start(() -> {
            try {
                Thread.sleep(200);                            // stands in for a slow remote call
                resp.setContentType("text/plain;charset=UTF-8");
                resp.getWriter().println("request thread=" + requestThread + ", worker thread="
                        + Thread.currentThread().getName());
            } catch (IOException | InterruptedException e) {
                Thread.currentThread().interrupt();
            } finally {
                async.complete();                             // always complete, or the request hangs until timeout
            }
        });
    }
}
curl -s http://localhost:18080/g2-servlet/async
request thread=http-nio-18080-exec-37, worker thread=http-nio-18080-exec-30

The request thread and the worker thread are different threads of the container’s pool. The finally block that calls complete() is not optional: a response that is neither completed nor dispatched stays open until the timeout. Non-blocking I/O (ReadListener, WriteListener), HTTP trailers and protocol upgrade (WebSocket) build on the same machinery and are outside this page; HTTP/2 server push, available through newPushBuilder(), is deprecated in 6.1 and optional for containers. For new applications with high concurrency on Java 21, virtual threads and plain blocking servlets are an alternative worth measuring before reaching for the async API.

    protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        HttpSession session = req.getSession(false);
        String expected = session == null ? null : (String) session.getAttribute("csrf");
        String actual = req.getParameter("csrf");
        if (expected == null || actual == null
                || !MessageDigest.isEqual(expected.getBytes(), actual.getBytes())) {
            resp.sendError(HttpServletResponse.SC_FORBIDDEN, "Missing or invalid CSRF token");
            return;
        }
        String title = req.getParameter("title");
        String author = req.getParameter("author");
        int year;
        try {
            year = Integer.parseInt(req.getParameter("year"));
        } catch (NumberFormatException e) {
            year = -1;
        }
        if (title == null || title.isBlank() || author == null || author.isBlank() || year < 1450) {
            resp.sendError(HttpServletResponse.SC_BAD_REQUEST, "title, author and a year >= 1450 are required");
            return;
        }
        Book created = Catalogue.of(getServletContext()).add(title.strip(), author.strip(), year);
        // Post/Redirect/Get: 303 tells the client to follow with a GET, so a refresh never re-posts the form.
        resp.sendRedirect(req.getContextPath() + "/books/" + created.id(), HttpServletResponse.SC_SEE_OTHER);
    }
