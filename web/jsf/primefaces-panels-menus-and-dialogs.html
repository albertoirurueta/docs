PrimeFaces Panels, Menus and Dialogs

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against PrimeFaces 16.0.0 (released 2026-09-04) on Jakarta Faces 4.1 (API jakarta.faces-api 4.1.2, Jakarta EE 11), with Eclipse Mojarra 4.1.17 and Apache MyFaces Core 4.1.4, Tomcat 11.0.26 with Weld 6.0.4.Final (Tomcat and Weld; other servers are on the Jakarta EE servers page) and Java 17 or later (the examples were compiled with --release 21). PrimeFaces 16 dropped JavaServer Faces and Java EE (javax.*) support: its baseline is Jakarta Faces 4.0 and newer, so everything below also applies to Faces 4.0. The previous line, PrimeFaces 15.0.x, still has the same components with the differences listed in What Changed per Version. Every example was deployed as an exploded Bookshelf WAR, once on Mojarra and once on MyFaces, and driven in headless Chrome 155 (clicks, Ajax requests counted, results read back from the DOM) on 2026-10-08. A claim that was not run is marked as such. The component and attribute names were checked against the tag library descriptor inside primefaces-16.0.0.jar (176 tags) and against the PrimeFaces 16 documentation, and the Java API against the classes in the jar.

The components of this page are the layout and interaction part of PrimeFaces: containers that group other components (panel, accordion, tab view, toolbar), menus that navigate or run actions, and overlays that interrupt the user (dialogs, confirmations, a blocking mask) or run behind the scenes (poll). The input components, p:ajax, validation, p:growl and p:messages belong to the PrimeFaces Ajax and forms page of this section; the data components (p:dataTable, trees, p:schedule) to the PrimeFaces data components page. They are named here without repeating them, and the examples use a p:dataTable and a p:growl only as scenery. The PrimeFaces setup, themes and icons are on the PrimeFaces getting started page. Plain Faces behaviour that this page relies on is on the Ajax page and the search expressions page.

What These Components Have in Common

Before the individual components, five facts explain almost every surprise in this family. All were observed.

They are Faces components with a JavaScript widget. Each component renders its markup and a script that creates a client object, a widget (PrimeFaces.cw("Panel","detailsPanel",{...}) in the page source). The widget is registered under the component’s widgetVar, which is generated (widget_f_details) unless you set it, and is reached from script with PF('detailsPanel'). That is how PF('editDialog').show() and PF('importPoll').stop() work. A widgetVar is a name in a global table, so give it a name that is unique in the page and does not equal the id of any element: the id of an element becomes a property of window, and a widget variable of the same name is a recipe for confusion (the examples use ids such as details with the widget variable detailsPanel).

The namespace is primefaces. PrimeFaces 16 declares the tag library as xmlns:p="primefaces" (the Faces 4.0 URN style) and keeps the older http://primefaces.org/ui working. Both are used in the wild; this section uses the short one.

Ajax defaults to process="@all". A p:commandButton, a p:menuitem or a p:poll without process posted jakarta.faces.partial.execute=@all in every request below, unlike f:ajax, whose default is @this (see execute and render). Row buttons that only need the row should say process="@this", otherwise every other input of the page is decoded, converted and validated for a click on one row.

update is resolved from the source component’s naming container. A p:accordionPanel with value/var, a p:dataTable, a ui:repeat and a p:tabView are naming containers. An update="msgs" written inside one of them looks for msgs inside it and, on both implementations in the Development project stage, failed the whole page with an error page:

Cannot find component for expressions "msgs" referenced from "f:acc".

The fix is an absolute id from the view root, update=":f:msgs", which is what the examples below do. The rules are the ones of the search expressions page; PrimeFaces components resolve them strictly, so a wrong id is an error on the first render, not a silently ignored update.

Ajax actions need a form. A p:poll or a menu item with an action sends its request with a form’s fields and the view state. With no h:form in the page at all, the requests of a poll and of a p:menuitem were posted every second without jakarta.faces.ViewState, the listener never ran, and the server logged nothing. When another form existed elsewhere in the page, PrimeFaces used it (the request carried that form’s name) and the listener ran. Rely on neither: put actions in a form, and keep a page with menus and polls to one form or to forms that each own their actions.

p:panel

p:panel is the basic grouping box: an optional header and footer, a content area, and three built-in header features, toggling (collapse), closing and an options menu. All three are switched on by attributes and facets:

Attribute or facet Meaning

header, footer and facets header, footer

Texts, or markup in the facets. When an attribute and the facet of the same name are both given, the facet wins (PrimeFaces documentation).

toggleable, toggleSpeed (default 500 ms), toggleOrientation (vertical or horizontal), toggleableHeader

A toggle icon in the title bar, or the whole title bar when toggleableHeader is true.

collapsed

The initial state of a toggleable panel; also where the server state is kept (below).

closable, closeSpeed, visible

A close icon; visible="false" renders the panel hidden.

facet options

A gear icon in the title bar that opens the p:menu placed in the facet.

facet actions

Your own icons in the title bar (the PrimeFaces documentation shows h:commandLink with the ui-panel-titlebar-icon classes).

multiViewState

Keeps the state across views of the same session (default false); not exercised here.

renderEmptyFacets

Renders the facets even if their children are not rendered (default false).

Two Ajax events exist, toggle and close, handled with p:ajax. The listener of toggle receives a org.primefaces.event.ToggleEvent (getVisibility() is Visibility.VISIBLE or HIDDEN), the listener of close a org.primefaces.event.CloseEvent.

panel.xhtml — a toggleable, closable panel with a footer and an options menu
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core"
      xmlns:ui="jakarta.faces.facelets"
      xmlns:p="primefaces">
<ui:composition template="/WEB-INF/templates/layout.xhtml">
  <ui:define name="title">Details panel</ui:define>
  <ui:define name="content">
    <h:form id="f">
      <p:growl id="msgs"/>
      <p:panel id="details" header="Book details" widgetVar="detailsPanel"
               toggleable="true" closable="true" toggleSpeed="200"
               collapsed="#{panelsBean.detailsCollapsed}" visible="#{panelsBean.detailsVisible}">
        <p:ajax event="toggle" listener="#{panelsBean.onToggle}" update="msgs"/>
        <p:ajax event="close" listener="#{panelsBean.onClose}" update="msgs"/>
        <h:outputText value="Dune, Frank Herbert, 1965"/>
        <f:facet name="footer">
          <h:outputText value="Showing 1 of 3 books"/>
        </f:facet>
        <f:facet name="options">
          <p:menu>
            <p:menuitem value="All books" outcome="/accordion.xhtml"/>
          </p:menu>
        </f:facet>
      </p:panel>
    </h:form>
  </ui:define>
</ui:composition>
</html>
PanelsBean.java — remembers the panel and tab state on the server
package org.example.bookshelf.web;

import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.FacesContext;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;
import org.primefaces.event.CloseEvent;
import org.primefaces.event.TabChangeEvent;
import org.primefaces.event.TabCloseEvent;
import org.primefaces.event.TabEvent;
import org.primefaces.event.ToggleEvent;
import org.primefaces.model.Visibility;

@Named
@ViewScoped
public class PanelsBean implements Serializable {

    @Inject
    private transient BookService books;

    private boolean detailsVisible = true;
    private boolean detailsCollapsed;
    private int activeTab;

    public List<Book> getBooks() {
        return books.findAll();
    }

    /** Remember the state on the server, so that a re-render shows the panel as the user left it. */
    public void onToggle(ToggleEvent event) {
        detailsCollapsed = event.getVisibility() == Visibility.HIDDEN;
        info("Panel " + (detailsCollapsed ? "collapsed" : "expanded"));
    }

    public void onClose(CloseEvent event) {
        detailsVisible = false;
        info("Panel closed");
    }

    public void onTabChange(TabChangeEvent<?> event) {
        info("Tab: " + event.getTab().getTitle());
    }

    public void onTabClose(TabCloseEvent<?> event) {
        info("Closed tab: " + event.getTab().getTitle());
    }

    /** Called through tabController: tabs may be opened, but not closed. */
    public boolean isTabActionAllowed(TabEvent<?> event) {
        return !(event instanceof TabCloseEvent);
    }

    private void info(String text) {
        FacesContext.getCurrentInstance().addMessage(null, new FacesMessage(FacesMessage.SEVERITY_INFO, text, null));
    }

    public boolean isDetailsVisible() { return detailsVisible; }
    public void setDetailsVisible(boolean detailsVisible) { this.detailsVisible = detailsVisible; }
    public boolean isDetailsCollapsed() { return detailsCollapsed; }
    public void setDetailsCollapsed(boolean detailsCollapsed) { this.detailsCollapsed = detailsCollapsed; }
    public int getActiveTab() { return activeTab; }
    public void setActiveTab(int activeTab) { this.activeTab = activeTab; }
}

Source: PrimeFaces 16 documentation: Panel

What the headless run showed, identical on Mojarra and MyFaces:

  • Clicking the toggle icon sent jakarta.faces.behavior.event=toggle with the hidden field f:details_collapsed=true; the content area was hidden and the listener ran. The state travels in two hidden inputs of the form, details_collapsed and details_visible, which are part of every later post of that form.

  • The toggle listener ran in the Apply Request Values phase (getCurrentPhaseId() printed APPLY_REQUEST_VALUES), the close listener in Invoke Application, like the tab and poll listeners below. A toggle listener therefore runs before the submitted values are converted or validated and must not rely on the model being updated. See the phases.

  • Because collapsed and visible are bound to properties of the view-scoped bean and the listeners store the new values there, a re-render of the whole form (update="@form" from a refresh button, tried on an earlier version of this page) kept the panel closed. Without the bean the server only knows what the hidden fields post; the example stores the state so that a redisplay agrees with it.

  • Closing is only a client hide plus an event. Reloading the page shows the panel again unless the server remembers the choice (here detailsVisible is lost with the view scope, which is the correct lifetime for a view preference; a preference that must survive needs your own storage).

Other grouping containers exist in the 16.0.0 library and are used the same way (their names are tags of the library; they were not exercised for this page): p:fieldset (a bordered group with a legend, optionally toggleable), p:card, p:scrollPanel, p:overlayPanel (a pop-up anchored to a component), p:sidebar, p:splitter, p:panelGrid, p:outputPanel and p:inplace.

p:accordionPanel

p:accordionPanel stacks p:tab children vertically; one tab is open at a time unless multiple="true". p:tab is the same child component as in the tab view: title (or a title facet), disabled, closable and key (a unique key that the accordion’s active accepts instead of an index since 16, see What Changed per Version). The attributes you will actually use:

Attribute Meaning

active

Open tab index or indexes, or keys (since 16; none or -1 collapses all, all opens all). activeIndex is the deprecated predecessor.

multiple

Several tabs open at once.

dynamic, cache

Only the active tab’s content is rendered, the others are loaded by Ajax when first activated; cache="false" loads again each time.

value, var, varStatus

Iterate: one p:tab is repeated for every element, like ui:repeat.

tabController

A method expression boolean method(TabEvent) that the server runs to allow or refuse a tab change or close.

onTabChange, onTabShow, onTabClose

Client-side callbacks; onTabChange runs before a tab is shown.

toggleSpeed, scrollIntoView, multiViewState

Animation speed, scrolling the active tab into view (start, center, end, nearest), state across views.

The Ajax events are tabChange (a TabChangeEvent) and tabClose (a TabCloseEvent); both carry getTab(), the Tab component.

accordion.xhtml — one tab per book, with a server-side veto
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core"
      xmlns:ui="jakarta.faces.facelets"
      xmlns:p="primefaces">
<ui:composition template="/WEB-INF/templates/layout.xhtml">
  <ui:define name="title">Accordion</ui:define>
  <ui:define name="content">
    <h:form id="f">
      <p:growl id="msgs"/>
      <p:accordionPanel id="books" value="#{panelsBean.books}" var="book"
                        multiple="false" tabController="#{panelsBean.isTabActionAllowed}">
        <p:ajax event="tabChange" listener="#{panelsBean.onTabChange}" update=":f:msgs"/>
        <p:tab title="#{book.title}">
          <h:outputText value="#{book.author} (#{book.year})"/>
        </p:tab>
      </p:accordionPanel>
    </h:form>
  </ui:define>
</ui:composition>
</html>

Source: PrimeFaces 16 documentation: AccordionPanel

Observed, on both implementations: clicking the second header sent one request (jakarta.faces.behavior.event=tabChange with a posted ..._tabindex field of 1), the listener ran in Invoke Application and the second header became the active one. To test the veto, isTabActionAllowed was changed to return false: the tab stayed closed in the browser, but the tabChange listener still ran, before the controller (LISTENER then CONTROLLER TabChangeEvent in the log). A listener that changes anything must therefore check the same rule itself; the controller only decides what the client is allowed to show. (The PrimeFaces documentation shows the controller as void; the method returns a boolean.) Three more points from the documentation, all consistent with the run:

  • A single tab cannot be updated by Ajax. Update the whole accordion, or a container inside the tab (the documentation warns about this for the tab view as well).

  • A tabChange listener must not update the accordion or a parent of it. The component is then broken after the re-render (documented, not reproduced here); update the messages component or an element inside a tab instead, as in the example.

  • active="none" renders everything collapsed and lets the renderer skip evaluating tab keys.

p:tabView

p:tabView is the horizontal sibling: tab headers in a row, one panel visible. It shares p:tab, value/var, dynamic/cache, tabindex, multiViewState and the callbacks with the accordion, and adds:

Attribute Meaning

activeIndex

The open tab, a value expression is written when the tab changes (below).

orientation

top (default), left, right, bottom.

effect, effectDuration

A jQuery UI effect and its speed (slow, normal, fast).

scrollable

Keeps the headers on one line with navigation buttons instead of wrapping them.

focusOnError, focusOnLastActiveTab

After a validation failure, activate the tab that contains the first error; remember the last active tab.

touchable

Touch support (global default or primefaces.TOUCHABLE).

facet actions

Extra icons next to the tab headers.

A p:tab with closable="true" shows a close icon and fires tabClose.

tabs.xhtml — lazy tabs with a closable tab
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core"
      xmlns:ui="jakarta.faces.facelets"
      xmlns:p="primefaces">
<ui:composition template="/WEB-INF/templates/layout.xhtml">
  <ui:define name="title">Tabs</ui:define>
  <ui:define name="content">
    <h:form id="f">

      <p:tabView id="tabs" dynamic="true" cache="true" activeIndex="#{panelsBean.activeTab}">
        <p:ajax event="tabChange" listener="#{panelsBean.onTabChange}" update=":f:msgs"/>
        <p:ajax event="tabClose" listener="#{panelsBean.onTabClose}" update=":f:msgs"/>
        <p:tab title="Details">
          <h:outputText value="Dune, Frank Herbert, 1965"/>
        </p:tab>
        <p:tab title="Reviews">
          <h:outputText value="#{panelsBean.books.size()} books on the shelf"/>
        </p:tab>
        <p:tab title="Covers" closable="true">

        </p:tab>
      </p:tabView>
    </h:form>
  </ui:define>
</ui:composition>
</html>

Source: PrimeFaces 16 documentation: TabView

Observed on both implementations: with dynamic="true" the content of the second tab was not in the initial page; clicking the header sent a tabChange request with f:tabs_contentLoad=true and the tab view appeared in the render list (jakarta.faces.partial.render=f:msgs f:tabs), after which the text was there. Going back to the first tab and to the second again sent two more tabChange events without contentLoad, because the contents are cached (cache defaults to true). The listener saw activeTab=1 in the bean, so activeIndex is written to the bound property before the listener runs. Clicking the close icon of Covers removed the header and fired tabClose (Closed tab: Covers); like a closed panel, the tab is back when the page is requested again, so keep the decision on the server (a rendered condition on a bean flag) when it matters. A dynamic tab is a good place for something expensive, and the tab view is the right fit for a book page with Details, Reviews and Covers. An expensive tab belongs to a view-scoped bean; the view scope explains how much a view keeps.

p:toolbar

p:toolbar is a bar for commands: two placeholders, left and right, defined either with facets of those names or with p:toolbarGroup children (align="left" is the default, or right). Any content may go in a group.

The groups were rendered as ui-toolbar-group-left and ui-toolbar-group-right and the text read New book | Refresh | Export. Menus: One Item Model, Many Presentations

All PrimeFaces menus are built from the same pieces. p:menuitem is one entry, p:submenu groups entries (and, in a menubar, nests), p:divider separates them. The menu components differ in how they present and where they sit.

p:menuitem: Action, Outcome or URL

A p:menuitem has three kinds of target, and which one applies is decided by the attribute you set. The PrimeFaces documentation says that url is the key: if it is set, the item is a plain link, so do not set it for an item that runs a command.

Attributes Behaviour

action (and actionListener), update, process

An Ajax request (the default), like a p:commandButton. ajax="false" makes it a normal form POST (the example’s Rebuild index item). immediate, oncomplete, onstart, partialSubmit, resetValues work as on the command components.

outcome, includeViewParams, fragment

A GET navigation resolved with the navigation handler, like h:link (see navigation); the item rendered a plain link to the target view. Safe for bookmarkable targets.

url or href, target

A plain link to any address; target="_blank" opened it in a new tab. The links of the example were https://primefaces.github.io/primefaces/16_0_0/ with _blank and /bookshelf/accordion.xhtml.

icon, iconPos, badge, value, title, ariaLabel

Presentation. escape (default true) controls whether the label is HTML-escaped; see Security Notes for This Family. The tag declares value for the label; several samples in the PrimeFaces documentation write label, which is not an attribute of the 16.0.0 tag.

disabled, rendered

Hide or grey the item (never an authorization, Security Notes for This Family).

The item is also what the p:confirm behaviour, p:confirmDialog, p:confirmPopup and p:confirm, attaches to, and the item you give to a steps or breadcrumb component.

p:menubar

A horizontal navigation bar: p:submenu children that open drop-downs, plus p:menuitem children as root items. Submenus nest for deeper levels. The facets start and end take a logo or a button. autoDisplay (default true) opens the first level on hover, toggleEvent (hover or click), showDelay and hideDelay tune the timing.

p:dialog is an overlay window that is not visible until you show it. The two ways to show it are the client API and a server-side script; the examples use the first:

BookDialogBean.java — load on the server, save, tell the client it worked
package org.example.bookshelf.web;

import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.FacesContext;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;
import org.primefaces.PrimeFaces;

@Named
@ViewScoped
public class BookDialogBean implements Serializable {

    @Inject
    private transient BookService books;

    private long id;
    private String title;
    private String author;
    private int year;

    public List<Book> getBooks() {
        return books.findAll();
    }

    /** Called from a row button: reads the book on the server, never trusting client-sent values. */
    public void edit(long bookId) {
        Book book = books.findById(bookId).orElseThrow();
        this.id = book.id();
        this.title = book.title();
        this.author = book.author();
        this.year = book.year();
    }

    public void save() {
        books.save(new Book(id, title, author, year));
        info("Saved " + title);
        PrimeFaces.current().ajax().addCallbackParam("saved", true);
    }

    public void delete(long bookId) {
        Book book = books.findById(bookId).orElseThrow();
        books.delete(bookId);
        info("Deleted " + book.title());
    }

    public void deleteAll() {
        books.deleteAll();
        info("Deleted every book");
    }

    private void info(String text) {
        FacesContext.getCurrentInstance().addMessage(null, new FacesMessage(FacesMessage.SEVERITY_INFO, text, null));
    }

    public long getId() { return id; }
    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
    public String getAuthor() { return author; }
    public void setAuthor(String author) { this.author = author; }
    public int getYear() { return year; }
    public void setYear(int year) { this.year = year; }
}

How it fits together, as run:

  1. The row button runs edit(book.id) with process="@this", copies the book’s fields from the server-side service into the view-scoped bean (it does not use a field posted by the browser) and updates :editForm so the inputs show the book; oncomplete then shows the dialog. The id of the dialog’s form is absolute because the dialog is outside the first form.

  2. Save submits editForm. With an empty title the request ran Process Validations, the message Title: Validation Error: Value is required. appeared in the dialog’s p:messages, the dialog stayed open and save did not run.

  3. With a valid title save() ran and PrimeFaces.current().ajax().addCallbackParam("saved", true) put a value in the response. The oncomplete script read it from the args object (args.saved) and hid the dialog; the table (:list:books) and the growl were updated in the same response, and the first-row text read the new title. args is how a server decision reaches script, and it avoids closing a dialog whose validation failed (the &amp;&amp; in the file is the XML escape of &&).

The dialog was a child of the body (parentElement.tagName == BODY) because of appendTo="@(body)". That is deliberate and has a consequence: the dialog’s content is no longer inside the form that declared it in the page source, so give it its own h:form, as above. The PrimeFaces documentation names two reasons for appendTo: nested dialogs and a dialog inside a clipping container (a tab view, an accordion). p:confirmDialog, p:confirmPopup and p:confirm

A confirmation replaces the browser’s window.confirm with a styled dialog (p:confirmDialog) or a small overlay anchored to the button (p:confirmPopup). Each has two modes.

Local mode: a p:confirmDialog with a widgetVar, header, message (or a message facet) and severity (alert, the default, or info), whose buttons you write, shown by PF('deleteAllDialog').show(). It is a dialog with a message, and the p:dialog advice applies.

Global mode: one p:confirmDialog global="true" (or p:confirmPopup global="true") per page, and a p:confirm child behaviour in each button that needs it. The behaviour holds the header, message, icon and, for the popup, type="popup"; its attributes yesButtonLabel, noButtonLabel and the icon and class variants (yesButtonIcon, noButtonClass) override the dialog’s buttons; disabled switches it off and escape (default true) controls HTML escaping of the message. The buttons that answer the question carry style classes: ui-confirmdialog-yes and ui-confirmdialog-no for the dialog, ui-confirm-popup-yes and ui-confirm-popup-no for the popup. p:confirm can be put in a p:commandButton, p:commandLink or p:menuitem.

The Dialog Framework

The dialogs above are declared in the page. The dialog framework is the programmatic alternative: the server decides at run time to open a view in a dialog. The page of the dialog is an ordinary Faces view that is loaded into an iframe inside a dialog that PrimeFaces creates; the dialog is destroyed when the view closes it. It is the right tool for a reusable picker or editor that has its own page, its own bean and its own validation. The entry point is PrimeFaces.current().dialog() (since 7 the replacement of the RequestContext of older code; see What Changed per Version), whose methods in 16.0.0 are:

Method Purpose

openDynamic(String outcome)

Open the view that the navigation outcome names, with defaults.

openDynamic(String outcome, DialogFrameworkOptions options, Map<String, List<String>> params)

With options (a builder) and request parameters for the dialog’s view. An overload takes a Map<String, Object> of options instead.

closeDynamic(Object data)

Called by the view in the dialog: close it and pass data (an object, or null) back.

showMessageDynamic(FacesMessage), showMessageDynamic(FacesMessage, boolean)

Show a message in a small dialog without a view of your own.

The PrimeFaces 16 documentation calls the last method showMessageInDialog; the 16.0.0 jar has showMessageDynamic and no showMessageInDialog (verified with javap). The documentation sample is out of date; use showMessageDynamic.

Without them nothing happened when the button was pressed: the request was answered, no dialog appeared, and the log was silent. With them it worked on Mojarra and on MyFaces.

package org.example.bookshelf.web;

import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.Serializable;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;
import org.primefaces.PrimeFaces;

/** Backs the view that is shown inside the dialog (df-edit.xhtml). */
@Named
@ViewScoped
public class BookEditorBean implements Serializable {

    @Inject
    private transient BookService books;

    private long id;
    private String title;
    private String author;
    private int year;
    private boolean found;

    public void load() {
        books.findById(id).ifPresent(b -> {
            this.title = b.title();
            this.author = b.author();
            this.year = b.year();
            this.found = true;
        });
    }

    public void save() {
        Book saved = books.save(new Book(id, title, author, year));
        PrimeFaces.current().dialog().closeDynamic(saved);
    }

    public void cancel() {
        PrimeFaces.current().dialog().closeDynamic(null);
    }

    public long getId() { return id; }
    public void setId(long id) { this.id = id; }
    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
    public String getAuthor() { return author; }
    public void setAuthor(String author) { this.author = author; }
    public int getYear() { return year; }
    public void setYear(int year) { this.year = year; }
    public boolean isFound() { return found; }
}

Source: PrimeFaces 16 documentation: Dialog Framework

What happened, in order, on both implementations:

  1. The button posted an Ajax request (execute=f:...:edit because of process="@this"); the response told the client to open a dialog.

  2. The browser requested /bookshelf/df-edit.xhtml?id=2&pfdlgcid=<uuid> from inside the iframe. The pfdlgcid parameter ties the dialog to the request that opened it; the dialog title was the <title> of the view (Edit book). The view is a completely separate Faces view: it has its own view state and its own view-scoped beans, which the PrimeFaces documentation also states.

  3. In the dialog, Save was an Ajax post to df-edit.xhtml?pfdlgcid=...; closeDynamic(saved) made the dialog close.

  4. The host button’s dialogReturn behaviour then fired a second Ajax request to the host page (a ..._pfdlgcid= parameter), with jakarta.faces.behavior.event=dialogReturn; the listener onReturn(SelectEvent<Book>) received the saved book through getObject(), and the growl and the Last edited text were updated. Cancel (closeDynamic(null), immediate="true" so no validation blocks it) delivered a null object, which onReturn shows as cancelled.

  5. showMessageDynamic(new FacesMessage(...)) opened a small dialog with the summary and the detail text (Index rebuilt | It took 0 ms.).

Options. DialogFrameworkOptions.builder() has a method for each of these: modal (default false), draggable (true), resizable (true), closable (true), closeOnEscape (false), minimizable, maximizable, width, height (both auto), contentWidth (640), contentHeight, minWidth, minHeight, includeViewParams (false), headerElement, widgetVar, appendTo, dynamic, showEffect, hideEffect, position, fitViewport, responsive, focus, onShow, onHide, blockScroll, styleClass, iframeStyleClass, resizeObserver and resizeObserverCenter. The method names are those of the DialogFrameworkOptions.Builder class in the 16.0.0 jar, the defaults come from the documentation table. The documentation cautions that contentWidth="auto" and "100%" do not work well because the content is in an iframe; give a pixel width. modal(true) was used in the example.

Passing data. Parameters go to the dialog view as request parameters (the third argument; the example’s id, read by f:viewParam), which is the better choice: it is a bookmarkable, validated, string-typed input, and the view loads what it needs itself. The documentation also shows passing an object through the flash, with a DialogKeepFlashPhaseListener to keep it for the dialog’s request (the listener is registered by the jar, as seen above); the flash holds a value only for the next request and a large object belongs in the session or a service instead (see the flash page). Data comes back through closeDynamic(data) and the host’s dialogReturn behaviour; the object is available as SelectEvent#getObject().

The dialog view is a normal URL. GET /bookshelf/df-edit.xhtml?id=2 without pfdlgcid returned the edit page, the same form, with 200. Whoever can request the view can use it outside the dialog. Authorise in the view (a f:viewAction guard or the called service) exactly as for any other page, and never assume that the dialog is only reachable from the host. Calls to the dialog API in a non-Ajax request are ignored (documentation), so the opening buttons are Ajax buttons, as above.

p:blockUI

p:blockUI puts a translucent mask (optionally with content, such as a loading message) over a target while an Ajax request is running. block is a search expression for the target(s), trigger the id(s) of the component(s) whose requests show it (comma separated); with that wiring the mask appears at the start of the trigger’s Ajax request and disappears when it completes. blocked="true" blocks from the start, delay waits before showing, animate can be turned off, and the widget has show(), hide() and isBlocking().

p:poll

p:poll sends an Ajax request at an interval from the page, runs the listener (a method expression) and updates the components named in update. The interval is in seconds by default (interval="2"; intervalType="millisecond" changes the unit). autoStart="false" waits for PF('importPoll').start(); stop="#{...}" ends polling when the expression becomes true; stop() is the client call. onactivated and ondeactivated are client callbacks that may veto, async stops the requests from queueing, global decides whether p:ajaxStatus reacts, and process, partialSubmit, form behave as on any PrimeFaces Ajax source.

ImportStatusBean.java — the job, its checks and a slow action
package org.example.bookshelf.web;

import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.FacesContext;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Named;
import java.io.Serializable;

/** Stands in for a long-running catalogue import: every poll "checks" it, the third check finds it finished. */
@Named
@ViewScoped
public class ImportStatusBean implements Serializable {

    private int checks;
    private boolean done;

    public void check() {
        checks++;
        if (checks >= 3) {
            done = true;
        }
    }

    /** A slow action: the reason for p:blockUI. */
    public void reindex() throws InterruptedException {
        Thread.sleep(1200);
        FacesContext.getCurrentInstance().addMessage(null,
                new FacesMessage(FacesMessage.SEVERITY_INFO, "Re-index finished", null));
    }

    public int getChecks() { return checks; }
    public boolean isDone() { return done; }
}

Source: PrimeFaces 16 documentation: Poll

Observed on both implementations: one request per second (execute=@all, render=f:status), the text going Checks: 1, Checks: 2, Checks: 3, finished: true, and exactly three requests in total: once the listener set done, the stop expression was true in the response and the client stopped (the poll is not in the update list; the stop worked anyway). The listener ran in Invoke Application.

Polling has costs and limits. Every poll is a full Faces request with a lifecycle and, with server-side state saving, a view state lookup; a view-scoped bean stays in use, and the requests count as session activity (not measured here). Use a long interval, stop as soon as the condition is met, keep the listener to a cheap read, and prefer server push for events that should reach the page the moment they happen: the f:websocket of the push page, which replaced the removed p:push. A p:poll is the right tool when the state is only visible by asking.

Security Notes for This Family

Security is part of correctness for these components, because most of them take strings from data and show them in other people’s browsers.

Escape what you show. Titles and labels are escaped by default (see cross-site scripting and the escape attribute). A hostile string <img src=x onerror=...>T was put in p:panel header, p:tab title (tab view and accordion), a p:submenu label, a p:menuitem value, a breadcrumb item, a steps item, the p:dialog header, the p:confirm header and message, a growl message and the text inside a p:blockUI; on Mojarra none of them created an img element. The one place where it did was p:menuitem escape="false", which ran the script (the counter of the handler was 1). escape="false" on a label that contains user data is an XSS bug; if markup is needed, build it from your own fixed strings or sanitise it. p:confirm has an escape attribute too (default true) with the same rule.

A hidden or disabled menu is not an authorization. rendered="false" and disabled="true" on items only change what a browser is told. The action method, the outcome target and the dialog view must each check the user’s role or the ownership of the data, for example with the role checks of the security page or an @RolesAllowed-style check in the service, and the menu model of Menus from a MenuModel may hide what the user cannot use for convenience only. The same holds for p:steps: a step is not reached because the step is clickable.

A client confirmation is not a protection. See p:confirmDialog, p:confirmPopup and p:confirm.

A dialog view is a URL. See A Launcher and a Dialog View. It is also a view in its own right for CSRF: its Ajax posts carry their own view state, and the protected-view rules of the CSRF section apply to it.

Do not trust the state the client posts. The details_collapsed and details_visible hidden fields, the active tab, the selected rows: all come from the browser. Use them for presentation, not for decisions. The edit dialog of this page therefore reads the book from the service by id on the server and the save action writes only the fields of the form, never a client-supplied identity (an editor still has to check that the user may edit book id, which this scratch application does not model).

Content Security Policy. With primefaces.CSP set to true (see the CSP section) the header was Content-Security-Policy: script-src 'self' 'nonce-...';, and the edit dialog (oncomplete and args), the confirmations, the dialog framework and the panel and tab Ajax behaviours all worked unchanged on Mojarra. Plain Faces command components are the part that does not work everywhere under this policy (see the CSP section: an h:commandButton with f:ajax did not update on Mojarra); use PrimeFaces components in such a page. Keep your own oncomplete and onclick to widget calls and args, as in the examples, and move real logic to a script file loaded with h:outputScript.

Mojarra Versus MyFaces

PrimeFaces components are the same code on both implementations; the Faces implementation supplies the lifecycle, state saving and Ajax runtime. Every scenario of this page (panel toggle and close, accordion and tab view events and veto, dynamic and cached tabs, the declarative and model menus, context menu, breadcrumb, steps, dialog with validation and args, global and local confirmations, blockUI, poll with stop, the dialog framework round trip) gave the same results on Mojarra 4.1.17 and MyFaces 4.1.4. The differences seen were cosmetic: generated ids (j_idt11 on Mojarra, j_id_h on MyFaces) and the string form of PhaseId (INVOKE_APPLICATION 5 against INVOKE_APPLICATION(5)). Only Mojarra was used for the hostile-string test, the Content Security Policy run, the dynamic dialog and the form-less poll described above. For the comparison of the two Faces implementations in general see Versions and Implementations.

Where the Books Are Outdated

The PrimeFaces books of the 2013-2015 era (PrimeFaces Cookbook, second edition, for PrimeFaces 5.1/5.2 on JSF 2.2) cover these components in their layout, menus and advanced chapters. Their Ajax and component ideas still hold; the following do not:

  • The request context. They call the Ajax helper methods (callback parameters, executing script, the dialog framework) through RequestContext; today everything goes through PrimeFaces.current() (current().ajax().addCallbackParam(...), current().dialog(), current().executeScript(...)). I did not check the older method names of the dialog framework against the books, only the 16.0.0 ones above.

  • Themes and icons. The ThemeRoller themes and the jQuery UI icon classes (ui-icon-...) of their examples are replaced by the PrimeFaces themes and PrimeIcons (pi pi-...); the migration guide says legacy ThemeRoller themes are unsupported since 15 and do not render correctly. Some structural class names (ui-icon inside the panel header) remain.

  • Removed or renamed components and attributes. p:separator is gone, the p:menubar delay attribute was renamed, activeIndex of the accordion is deprecated, and the menu model is built with builders rather than constructors and addElement.

  • The old JSF base. Their pages use the java.sun.com or xmlns.jcp.org namespaces, javax.faces and @ManagedBean backing beans, none of which exist in Faces 4 (and PrimeFaces 16 no longer supports JSF 2.x); the examples above use CDI @Named, jakarta.* and the jakarta.faces.* URNs.

  • Push. The book’s p:push/Atmosphere approach to live updates was removed; poll is still available, and push is f:websocket or OmniFaces o:socket.

Pitfalls

Pitfall What to do

update="msgs" from inside an accordion, table or repeat fails the page

Use an absolute id (:form:msgs) or a search expression that resolves from the naming container; see What These Components Have in Common.

A button or menu item without process posts @all

Say process="@this" (or the ids you need) for row actions.

A dialog’s inputs are submitted with the wrong form, or nothing happens

With appendTo, the dialog leaves its form in the DOM; give the dialog’s content its own h:form.

A dialog closes although validation failed

Do not hide it from onclick; hide it in oncomplete after testing args, as in p:dialog.

p:ajax event="tabChange" updates the tab view or accordion itself

Update the messages or an inner container; the component breaks when it or a parent is replaced (documented).

The tab controller refuses a tab and the tabChange listener still changes data

The listener ran first in the test; make the listener apply the same rule.

A closed panel or tab comes back after a reload

Store the decision (a bean property, or a rendered flag) if it must survive.

Nothing happens in the dialog framework

Register the three handlers in faces-config.xml (Registration); there is no log message otherwise.

showMessageInDialog does not compile

The 16 API is showMessageDynamic.

The dialog view works as a stand-alone page for anyone

It is a URL: guard it like one (A Launcher and a Dialog View).

escape="false" on a menu label

XSS if any part of the text is user data; leave it at the default.

A poll or menu action does nothing, silently

No form around it; put it in an h:form (What These Components Have in Common).

p:poll runs forever or on a hidden tab

Bind stop to a state the listener sets, or stop it from script when the user leaves.

widgetVar the same as a component id

Choose a distinct, unique name; PF('name') looks the widget up by it.

A menu item with both url and action

url wins and the item is a link; use one of them.
