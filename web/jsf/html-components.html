Standard HTML Components

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Faces 4.1 (API jakarta.faces-api 4.1.2, part of Jakarta EE 11, Java SE 17 or later), with Eclipse Mojarra 4.1.17 and Apache MyFaces Core 4.1.4. Faces 4.0 (Jakarta EE 10) behaves the same for everything below except where What Changed Between Versions says otherwise. The code and the HTML shown were run for real: the pages were deployed in a scratch Bookshelf WAR on Apache Tomcat 11.0.26 with Weld 6.0.4.Final (Java 21, English locale, project stage Development), requested with curl, and the markup quoted is what came back, with session ids removed (checked on 2026-10-08). Every statement about the tags is taken from the Jakarta Faces 4.1 VDL documentation, the specification and the Jakarta EE Tutorial, and each example below is followed by the page it derives from.

The standard HTML tag library is the set of tags in the jakarta.faces.html namespace, conventionally bound to the prefix h. Each tag creates one component in the view’s component tree and attaches the renderer that writes the HTML; the components are explained in the architecture page. The h tags are the vocabulary of every Faces page, and the component libraries covered later in this section (PrimeFaces, OmniFaces) build on them. The f namespace (jakarta.faces.core) tags that appear next to them, such as f:selectItems and f:param, belong to the core tag library, covered on the core tags page; the ones needed here are explained where they are used.

How an HTML Component Tag Works

A tag such as <h:inputText id="reviewer" value="#{reviewBean.reviewer}"/> does four things:

  1. While the view is built, Facelets creates a HtmlInputText component, copies the tag’s attributes into it (as values or as value expressions) and adds it to the parent in the component tree.

  2. While the request is decoded, the component’s renderer reads the request parameter named after the component’s client id and stores it as the component’s submitted value.

  3. The submitted value is converted, validated and, if valid, written to the bean property the value expression points at.

  4. While the response is rendered, the renderer writes the HTML element for the component’s current value.

The tag name therefore selects a component class and a renderer. Tags that look alike can share the behaviour and differ only in the renderer: h:selectOneMenu, h:selectOneListbox and h:selectOneRadio are three tags over the UISelectOne model with three renderers (Menu, Listbox and Radio). Attributes Shared by Most Tags

Most h tags accept the same families of attributes. The VDL documentation lists them per tag; this is what they mean and where they act in the request.

Attribute Meaning

id

Names the component inside its naming container. Without one, Faces generates an id (j_idt5 on Mojarra, j_id_8 on MyFaces). Give an id to anything that other code refers to: a label, a message, an Ajax render list, a script, a test. The tutorial notes that id is the one attribute that does not take a deferred #{} expression.

rendered

A boolean expression. When it is false the component produces no markup and is skipped when the submitted form is decoded and processed (lifecycle position). It is evaluated on every request, so it must give the same answer on the postback as when the page was rendered.

binding

Stores the component instance in a bean property. See the pitfalls of binding before using it.

value

For output components the value to display; for input components the model value that is read for display and written when the input is valid. A value expression that is writable is required on an input.

converter, converterMessage

Converts between the string in the request and the Java type of the model value (converters page).

required, requiredMessage, validator, validatorMessage

Validation of the submitted value (validators page, Bean Validation).

immediate

Moves conversion, validation and, for a command, the action to the Apply Request Values phase. See the lifecycle page for what it skips.

label

A human name for an input; it replaces the client id at the start of the validation and conversion messages (messages).

disabled, readonly

Rendered as the HTML attributes. On the server, a disabled or read-only input is skipped when decoding, so a request that is forged to send a value for it is ignored (lifecycle position).

style, styleClass, title, lang, dir, role, tabindex, accesskey

Pass-through attributes. styleClass becomes the HTML class. role was added to the pass-through set in 2.2.

onclick, onchange, onfocus, onblur, onkeyup and the other DOM event attributes

Pass-through JavaScript. They are plain browser events, not Faces events; Ajax behaviours are attached with f:ajax (Ajax page).

Any other attribute can be added to an h tag as an HTML5 pass-through attribute with the jakarta.faces.passthrough namespace; this is covered on the HTML5-friendly markup page. Only autocomplete="off" is written by the renderer for the attribute autocomplete: the VDL says any other value renders nothing, and both implementations confirmed it (autocomplete="name" on h:inputText produced no attribute, autocomplete="off" did).

Source: Jakarta EE Tutorial: Common Component Tag Attributes and Jakarta Faces 4.1 VDL: h:inputText

Forms: h:form

Every input and every command component must sit inside an h:form. The form is the unit of submission: only the components in the submitted form are decoded, converted, validated and updated, which is why a page often has several small forms.

<h:form id="review">
  ...
</h:form>

The renderer wrote this for the form above:

<form id="review" name="review" method="post" action="/bookshelf/inputs.xhtml"
      enctype="application/x-www-form-urlencoded">
<input type="hidden" name="review" value="review" />
...
<input type="hidden" name="jakarta.faces.ViewState" id="j_id1:jakarta.faces.ViewState:0"
       value="..." autocomplete="one-time-code" />
</form>

Three things matter in that markup:

  • method is always post; Faces forms are postbacks to the same view (action is the view’s own URL).

  • The hidden field named after the form id tells Faces, while decoding, which form was submitted. MyFaces uses a different convention: it writes <input type="hidden" name="review_SUBMIT" value="1" />. A script that builds a POST by hand has to use the right one.

  • jakarta.faces.ViewState carries the identifier (server-side state saving) or the serialised state (client-side state saving) of the view; without it the postback fails with a ViewExpiredException. With server-side state saving its unguessable value can also act as a defence against cross-site request forgery, under the conditions the security page of this section spells out (this page did not test it). It is written once in every form.

The attributes of h:form: prependId (whether the form’s id is part of the client ids of its children, true by default), enctype (multipart/form-data for file uploads), target, accept, acceptcharset, lang, dir, style, styleClass, title, rendered, binding, role and the DOM events onsubmit and onreset, besides those in the common table.

Rules to remember:

  • Forms cannot be nested. Browsers do not support a form inside a form, and Faces gives no way around it. Use sibling forms.

  • A command outside a form renders but does nothing useful. In project stage Development Mojarra adds an informational message to the page: "The form component needs to have a UIForm in its ancestry. Suggestion: enclose the necessary components within `<h:form>`". MyFaces rendered the button silently.

  • h:inputFile needs enctype="multipart/form-data" on its form. Without it Mojarra rendered a development-stage message ("File upload component requires a form with an enctype of multipart/form-data") and the form stayed application/x-www-form-urlencoded. The file upload page of this section covers the rest.

  • One huge form versus several small ones. Everything in the submitted form is processed, so a validation failure in an unrelated field of the same form blocks the action. Split independent areas, or use f:ajax execute to limit the fields (Ajax page).

Source: Jakarta Faces 4.1 VDL: h:form and Jakarta EE Tutorial: Adding Components to a Page Using HTML Tag Library Tags

            new Book(3, "SPQR", "Mary Beard", Genre.HISTORY),

        return List.of(new SelectItem("PAPERBACK", "Paperback"),
                new SelectItem("HARDCOVER", "Hardcover"),
                new SelectItem("EBOOK", "E-book", "Digital edition", true));
    }

    public record GenreGroup(String label, List<Book> books) {
    }

    public List<GenreGroup> getGenreGroups() {
        return java.util.Arrays.stream(Genre.values())
                .map(g -> new GenreGroup(g.getLabel(), books.stream().filter(b -> b.genre() == g).toList()))
                .toList();
    }

    public SelectItemGroup[] getGroupedBooks() {
        List<SelectItemGroup> groups = new ArrayList<>();
        for (Genre g : Genre.values()) {
            List<SelectItem> items = new ArrayList<>();
            for (Book b : books) {
                if (b.genre() == g) {
                    items.add(new SelectItem(b.id(), b.title()));
                }
            }
            groups.add(new SelectItemGroup(g.getLabel(), "", false, items.toArray(new SelectItem[0])));
        }
        return groups.toArray(new SelectItemGroup[0]);
    }

    public Book find(long id) {
        return books.stream().filter(b -> b.id() == id).findFirst().orElse(null);
    }
}

Text Input Components

The four text inputs map to the HTML form controls one to one. They are all UIInput components, so they all share value, converter, required, validator, immediate, valueChangeListener and the message attributes.

  • h:inputText renders <input type="text">. Attributes: maxlength, size, readonly, disabled, alt, autocomplete, accesskey and tabindex, and since 4.0 type. The type attribute (default text) lets the one tag render an HTML5 input such as email, url, number, date or tel without pass-through attributes; the VDL adds that for a type that already has a more specific component (hidden, password, checkbox, radio, file, submit, image, reset, button), the renderer warns in development stage and the more specific component is preferred. The HTML5 page covers the topic.

  • h:inputSecret renders <input type="password">. By default it never writes its value back to the page: the field came back with value="" after a postback that had submitted a password. redisplay="true" changes that and should not be used for a real password, since the value would be in the HTML.

  • h:inputTextarea renders <textarea>; rows and cols size it.

  • h:inputHidden renders <input type="hidden">. The value is written to the page and the browser sends it back, so anyone can change it. Never treat a hidden field as trusted: it is for state that can be re-checked on the server.

  • h:inputFile renders <input type="file"> and submits a jakarta.servlet.http.Part. multiple (to submit a Collection of parts) and accept were added in 4.0. The file upload page of this section covers it.

Points the output makes visible:

  • The for of each label became the client id of its input (review:reviewer), resolved from the plain id the page used. That is what makes clicking the label focus the field, and what screen readers use.

  • autocomplete="name" did not appear on the first input.

  • The empty h:message cells are <td></td>: with no message to show and no id, h:message wrote nothing at all.

What happens on a postback:

  1. Apply Request Values. Each input’s renderer reads review:reviewer and the others from the request. An input whose parameter is absent from the request is left alone (the run posted a form without the field and required did not fire); one that arrives empty stores "".

  2. Process Validations. An empty reviewer fails required and the page redisplays with the message "Please enter your name". Without requiredMessage the text is the standard "Validation Error: Value is required.", prefixed by the label or, when there is no label, by the client id.

  3. Update Model Values. Valid values are written to the bean. The run posted a name and an empty comment and the bean received comment='', an empty string, not null. Setting the context parameter jakarta.faces.INTERPRET_EMPTY_STRING_SUBMITTED_VALUES_AS_NULL to true in web.xml makes the same post leave the property null (confirmed on Mojarra). According to the specification text, the standard converters already return null for an empty string (read, not run here).

  4. Invoke Application. save runs submit().

Defining the options

<h:selectOneMenu id="format" value="#{reviewBean.format}">
  <f:selectItem itemLabel="-- choose --" itemValue="" noSelectionOption="true"/>
  <f:selectItems value="#{catalogueBean.formats}"/>
</h:selectOneMenu>

f:selectItem takes itemValue (what is submitted and converted), itemLabel (what the user sees), itemDescription, itemDisabled, itemEscaped (default true) and noSelectionOption. f:selectItems takes a value that is an array, a Collection or a Map:

  • a collection or array of jakarta.faces.model.SelectItem objects (the form used for getFormats() above), or of SelectItemGroup objects (see Grouped options: f:selectItemGroup and f:selectItemGroups);

  • a collection or array of any objects, in which case var, itemValue and itemLabel say how to read each one:

    <f:selectItems value="#{catalogueBean.books}" var="b" itemValue="#{b.id}"
               itemLabel="#{b.title} (#{b.author})"/>

    itemDisabled, itemDescription and itemLabelEscaped take expressions on var too, and noSelectionValue marks the element that stands for "no selection";

  • a Map, whose keys are the labels and whose values are the item values. A LinkedHashMap keeps the order; the run rendered Paperback and Hardcover as labels over the values PAPERBACK and HARDCOVER.

An enum needs no converter: the run submitted FICTION and the property of type Genre received Genre.FICTION, because Faces applies the enum converter implicitly. Long and the other wrapper types also convert implicitly. Any other class needs a converter, as shown in Selecting objects, and the "Value is not valid" error.

The itemDisabled item is drawn but cannot be chosen: new SelectItem("EBOOK", "E-book", "Digital edition", true) rendered <option value="EBOOK" disabled="disabled">E-book</option>. The description was not written to the HTML.

The no-selection option

A menu shows its first option when the value is empty, so a prompt such as "-- choose --" has to be an item with an empty value. Marking it noSelectionOption="true" (on f:selectItem) or noSelectionValue (on f:selectItems) tells Faces the item stands for "nothing", and with required="true" a user who leaves it selected fails validation. The run confirmed it: a required menu left on its prompt came back with "Edition: Validation Error: Value is required." (the text before the colon is the label).

<h:selectOneMenu id="edition" label="Edition" required="true" value="#{reviewBean.format}">
  <f:selectItem itemLabel="-- choose --" itemValue="" noSelectionOption="true"/>
  <f:selectItems value="#{catalogueBean.formats}"/>
</h:selectOneMenu>

hideNoSelectionOption="true" removes the prompt once a value is selected. On Mojarra, after a post with HARDCOVER, the menu came back with the three formats and without the "-- choose --" option. This was not checked on MyFaces.

Selecting objects, and the "Value is not valid" error

Faces compares what the browser sent with the options that were rendered. Two errors follow from that.

The submitted value must be one of the options. A value that is not in the list (a forged request, or a list that changed between render and postback) fails with "pick:book: Validation Error: Value is not valid" (the run posted a book id that was not offered). Rebuild the list identically on the postback: a @RequestScoped or @ViewScoped bean that recomputes the options must produce the same set, and a list that depends on request state must be rebuilt from state that survives (view scope).

Item values that are not simple types need a converter. The Bookshelf menu below uses the Book objects themselves as item values, with no converter:

<h:selectOneMenu id="objmenu" value="#{reviewBean.book}">
  <f:selectItems value="#{catalogueBean.books}" var="b" itemValue="#{b}" itemLabel="#{b.title}"/>
</h:selectOneMenu>

The renderer used toString() for the option values (Book[id=1, title=Dune, ...]) and the postback failed with "Conversion Error setting value 'Book[id=1, …​]' for 'null Converter'.". A converter that maps the book to its id and back repairs it. A managed converter, registered for the class and able to inject the catalogue, is the shortest form (converters page):

@FacesConverter(forClass = Book.class, managed = true)
@ApplicationScoped
public class BookConverter implements Converter<Book> {

    @Inject
    private CatalogueBean catalogue;

    @Override
    public Book getAsObject(FacesContext context, UIComponent component, String value) {
        if (value == null || value.isBlank()) {
            return null;
        }
        try {
            return catalogue.find(Long.parseLong(value));
        } catch (NumberFormatException e) {
            throw new ConverterException(e);
        }
    }

    @Override
    public String getAsString(FacesContext context, UIComponent component, Book value) {
        return value == null ? "" : String.valueOf(value.id());
    }
}

With it the same menu rendered <option value="1">Dune</option> and a post of 3 set the property to the SPQR book. The alternative that needs no converter is to submit the id (itemValue="#{b.id}", a Long) and look the book up in the action, as the list box above does.

Labels are escaped. itemLabel and itemLabelEscaped (and itemEscaped on f:selectItem) default to true. Setting them to false made the label <b>bold</b> render as real bold markup in the run, which is only safe for labels written by the page author and never for text a user can influence.

h:outputText

Writes the value as text. The text is escaped by default: with note = "<b>bold</b> & more",

<h:outputText id="n1" value="#{reviewBean.note}"/>

The <span> exists only when the tag has an id, a style or another attribute that needs an element; without any of them the renderer writes just the text (the run printed no id for <h:outputText value="no id"/>). escape="false" writes the value as markup. It must never be used for text that comes from a user, a database field they can edit or a request parameter, because that is cross-site scripting; escape the value or render it with the default. h:graphicImage

Renders <img>. There are two ways to give the source:

  • name and library refer to a resource: a file under resources/ (here resources/img/cover.png), served through the Faces resource handler with caching and versioning. <h:graphicImage name="cover.png" library="img"/> rendered src="/bookshelf/jakarta.faces.resource/cover.png.xhtml?ln=img" on both implementations.

  • url (or its alias value) is a context-relative URL. <h:graphicImage url="/images/cover.png"/> rendered src="/bookshelf/images/cover.png": a path starting with / is prefixed with the context path.

Always give alt (empty for a purely decorative image). width, height, longdesc, usemap and ismap pass through. The resource handling page of this section explains libraries, versions and locales.

h:outputScript, h:outputStylesheet, h:head and h:body

h:outputStylesheet name="app.css" library="css" rendered <link rel="stylesheet" href="...?ln=css" /> inside the page head; h:outputScript renders a <script src> and accepts target="head" or target="body". A script that is written twice with the same name and library was rendered once. These two tags need h:head and h:body rather than the plain HTML elements, because the renderers of h:head and h:body are where resources targeted at the head and the body are written (the Facelets page explains it in the h:head and h:body section). Faces also needs its faces.js library for Ajax and for h:commandLink; Mojarra wrote the <script> for it inline, just before the first command link of the form.

h:doctype renders a document type declaration at the position it is written, for views that do not use an HTML5 <!DOCTYPE html>. <h:doctype rootElement="html" public="-//W3C//DTD HTML 4.01//EN" system="http://www.w3.org/TR/html4/strict.dtd"/> rendered the matching declaration in the run; rootElement is required (without it Mojarra wrote <!DOCTYPE null> and MyFaces <!DOCTYPE >). Ordinary Facelets pages simply start with <!DOCTYPE html>, as in the examples above.

Since Faces 4.1 the VDL lists an id attribute on h:head and h:body (the component identifier, unique within the closest naming container). The documentation adds that the attribute is rendered only when the current doctype is an HTML5 doctype, so <h:body id="page"> yields <body id="page"> on a <!DOCTYPE html> page and no id on an older doctype. This rendering rule is quoted from the VDL; it was not run on either implementation.

h:commandButton and h:commandLink

Both fire an ActionEvent when activated. action is either a method expression whose result is the navigation outcome (#{reviewBean.submit} returned null, so the same view was redisplayed) or a literal outcome string. actionListener runs before the action and cannot change the navigation; immediate="true" moves both to the Apply Request Values phase and skips conversion and validation of the other inputs, which is right for a "Cancel" button and wrong almost everywhere else (lifecycle page).

h:commandButton takes type (submit by default, button, reset) and image. With image the element is <input type="image"> and the value is not shown: image="/images/cover.png" rendered type="image" and src="/bookshelf/images/cover.png". type="reset" clears the browser form without contacting the server, as does a type="button" with its own onclick; neither triggers an action. The specification says a reset is ignored on decode.

h:commandLink has no HTML equivalent of its own: it renders an anchor whose onclick submits the surrounding form with JavaScript that Faces provides (mojarra.cljs on Mojarra, myfaces.oam.submitForm on MyFaces) and adds faces.js. It therefore requires JavaScript and does not work in a new tab, and f:param children become extra request parameters of the post (from=link above). Prefer a button for destructive actions and a link for navigation.

h:button and h:link

These two are the outcome-target components. They have no action; they use outcome and the navigation rules to compute a URL at render time, and the user’s click is a plain GET. Attributes: outcome, includeViewParams (add the current view parameters to the URL), fragment (the #anchor), f:param children (query parameters), disabled, disableClientWindow, and for h:button an image, for h:link the anchor attributes such as rel and target. The page on navigation covers outcomes and the page on view parameters covers includeViewParams.

Because the URL exists in the HTML, h:link supports "open in new tab", bookmarking and crawling, and it needs no postback or view state. When the outcome cannot be resolved Faces disables the control rather than render a broken URL: <h:link outcome="nonexistent"/> became a <span> with the text "gone: This link is disabled because a navigation case could not be matched." and an h:button was rendered disabled, with the same message, and a development-stage message "Unable to find matching navigation case from view ID '/more.xhtml' for outcome 'nonexistent'" was added. (These messages appear in Development stage only.)

A GET must not change state. A link such as ?delete=42 that deletes on request is exposed to prefetching, crawlers and cross-site request forgery; changes belong to a POST command component with view state.

h:commandScript

h:commandScript (2.3) declares a JavaScript function that, when called, sends an Ajax request (execute, render, resetValues, onevent, onerror and action work as on f:ajax). name is required; autorun="true" calls the function when the page loads.

<h:form id="up">
  <h:commandScript id="cs" name="refreshFeed" execute="@form" render="out" action="#{reviewBean.submit}"/>
  <h:outputText id="out" value="x"/>
</h:form>

The footer comes before the body in the markup, as the HTML table model requires. Two cautions:

  • h:panelGrid is for tabular arrangements, such as a label/input form. Whole-page layout belongs to CSS (grid or flexbox); a panelGrid of panelGrid`s produces nested tables that are hard to style and to read with a screen reader. `h:panelGrid cannot span cells: every child occupies exactly one cell, so a component that needs a wider cell must be wrapped, and several components that must share one cell go in an h:panelGroup.

  • Count the children. A columns="2" grid fills two cells per row from the children that are rendered, so a child with rendered="false" does not leave a gap: with children A, B (not rendered), C and D the run put A and C on the first row and D alone on the second, which shifts every following cell. An h:message that has nothing to show still occupies its cell (<td></td>), which is why the review form keeps its columns aligned. MyFaces padded the short last row with an empty <td>; Mojarra did not.

h:panelGroup groups components so that they count as one child, and optionally renders a container. With layout="block" it is a <div>, otherwise a <span>, and in both cases only when it has an id, a style or a class. In the run <h:panelGroup id="blk" layout="block" styleClass="box">inside</h:panelGroup> gave <div id="blk" class="box">inside</div>, a group with an id and no layout gave <span id="inl">inline</span>, and a group with neither an id nor a style produced no element, only its children. It is also the standard way to give an Ajax render target to a block of components that may or may not be rendered: if the container is conditional, there is no element in the page to update.

h:dataTable and h:column produce a table over a collection and are covered on the data tables and iteration page of this section.

(The list item had both the summary and the detail because the tag asked for both.) Validation and conversion failures are associated with their component, so a per-field h:message shows them. The text of a failure starts with the component’s label or, when it has none, its client id:

<span id="f:m" class="err" title="f:name: Validation Error: Value is required.">	f:name: Validation Error: Value is required.</span>

Replace the standard texts with requiredMessage, converterMessage and validatorMessage on the input, or per language with a message bundle (messages and internationalisation page).

Two behaviours help with Ajax:

  • A message component with no messages still renders its element when it has an id: h:messages id="msgs" wrote <div id="f:msgs"></div> (or a <table>, with layout="table") and h:message id="m" wrote <span id="f:m"></span>. That empty container is what an f:ajax render="msgs" replaces, and it is why a message component needs an id to take part in partial rendering. A message tag with no id and no content wrote nothing.

  • In project stage Development, a message that no h:message or h:messages displayed is not lost: Mojarra added a <ul id="jakarta_faces_developmentstage_messages"> to the end of the page, MyFaces a <div> with the same id. It is how you find out that a validation error was raised for a component that has no message tag.

The id you write is only the last segment of the id that reaches the browser. The client id is built from the ids of all the naming containers above the component, joined with the separator character, which is : by default. h:form, h:dataTable, ui:repeat and composite components are naming containers (the architecture page explains how client ids are built). What it shows:

  • A component without an id gets a generated one, j_idt5. Mojarra used it only as the name of the input and did not write an HTML id for it; MyFaces wrote id="search:j_id_8" too. It is not stable: adding a component earlier in the page renumbers the later ones. In the scratch app the submit button was pick:j_idt21 and became pick:j_idt25 after two menus with their f:selectItem and f:selectItems children were added above it, so a test or script that hard-coded the generated id broke. Any component you refer to must have an explicit id. MyFaces generates j_id_8 instead.

  • prependId="false" removes the form’s id from its children (q2). The risk is duplicates: two forms with the same child id then collide. Do not use it with several forms on a page.

  • Inside a repeating component the client id includes the row index (dt:tbl:0:title), and a ui:repeat adds its own generated id segment (rep:j_idt7:0:t) when it has no id; give it one.

  • The name attribute of an input is its client id, which is what the decode reads.

  • #{component.clientId} is available in the attribute of a tag and gives the id of the component the attribute belongs to, the stable way to hand an id to JavaScript.

The separator is configurable. The context parameter jakarta.faces.SEPARATOR_CHAR set to - made the same page render search-q and search-g, which avoids escaping in CSS selectors (the colon of a client id must be written #search\:q in a CSS selector, while document.getElementById('search:q') needs no escaping). The parameter is global, so everything that builds ids by hand or tests that match them must agree; a component library can break when the separator changes. The default is the safe choice.

Rules of thumb:

  • Reference components by search expression (@form, @this, absolute ids starting with :, relative ids) from render and execute, and avoid string-concatenating client ids in Java. The page on search expressions describes them.

  • Use CSS classes, not #id selectors, for styling.

  • In tests, give the elements data-testid pass-through attributes (HTML5 page) or `id`s, and match with a stable selector instead of the generated id.

Where the Components Act in the Request Processing Lifecycle

Phase What the standard HTML components do

Restore View

On the first request the component tree is built from the Facelets view; on a postback it is rebuilt and the view state is restored. Every tag of this page becomes a component here.

Apply Request Values

Every component that is rendered, enabled and not read-only calls decode. An input reads the parameter named after its client id and stores the string as its submitted value. A command button looks for its client id (or .x and .y for an image) and queues an ActionEvent. h:selectBooleanCheckbox turns a missing parameter into false. An immediate input or command acts here.

Process Validations

The submitted strings are converted, then validated: required, the validators, and for the select components the check that the value is one of the offered options. Messages are added here, and an error moves the request straight to Render Response.

Update Model Values

Valid values are written to the beans.

Invoke Application

Action listeners and actions of h:commandButton, h:commandLink and h:commandScript run; the outcome picks the next view.

Render Response

Renderers encode the HTML; h:message shows the messages; for h:button and h:link the target URL is computed.

Two server-side rules follow from this and were checked on both implementations. A request that sends a value for a component that is disabled, readonly or has rendered="false" is ignored for that component: the bean kept its old value when the run posted outer:a=hacked, outer:b=hacked and outer:c=hacked for a disabled, a read-only and a non-rendered input. This protects the data that the page hides or locks, but only as far as the attribute is not itself computed from forgeable state; and it is not authorisation: a user who can reach the action can call it, whatever the page shows. Check permissions in the bean or with Jakarta Security (security page), not with rendered.

See the lifecycle page for the six phases in full, Apply Request Values and the immediate attribute.

Common Pitfalls

  • Inputs or commands outside an h:form. They render but do not submit. Mojarra’s development-stage message names the cause; MyFaces may say nothing.

  • Nested forms. Not supported by HTML; use sibling forms.

  • A required field that is skipped by the button you want. The button validates the whole form. Put the "Cancel" button in its own form, or in the same form with immediate="true" only after reading the lifecycle page.

  • Missing label. Messages start with a client id such as pick:reqmenu, which means nothing to the user.

  • escape="false" and itemLabelEscaped="false" with user text. Cross-site scripting. Escape, or sanitise on the way in and render with the default.

  • Select lists that change between request and postback. Fails with "Value is not valid". Build the list from state that does not change within the view, and make equals() of object values consistent with the converter.

  • Objects as item values without a converter. "Conversion Error setting value …​ for 'null Converter'". Register a converter for the class, or submit the id.

  • Relying on generated ids (j_idt21). Give an explicit id to anything you refer to.

  • Business logic in getters bound to value. A getter runs several times per request for each component, in both rendering and decoding; the lifecycle page explains why. Compute in an action or @PostConstruct and return a field.

  • Hidden fields as a security measure. The browser can send anything; recheck server-side.

  • A state-changing h:link or h:button. GET must not change state.

  • h:commandLink for plain navigation. It requires JavaScript, is not crawlable and cannot open in a new tab. Use h:link.

  • binding on a bean that outlives the request. Components are not thread-safe or serialisable in the way scoped beans expect (architecture page).

  • Too much in one h:panelGrid. A table per field row is hard to style; consider CSS grid on a div with h:panelGroup layout="block" children.

What Changed Between Versions

Version Change for the standard HTML tags

1.x

The tags were used from JSP pages through tag handlers, with the namespaces http://java.sun.com/jsf/html and http://java.sun.com/jsf/core.

2.0

Facelets becomes the standard view technology. The VDL documentation marks h:button, h:link, h:outputScript, h:outputStylesheet and the name and library attributes of h:graphicImage as added in 2.0.

2.1

The VDL documentation marks h:doctype as added in 2.1.

2.2

h:inputFile; the role attribute; HTML5 pass-through attributes and elements (the jakarta.faces.passthrough namespace).

2.3

h:commandScript; the group attribute of h:selectOneRadio (standalone radio buttons); styleClass on h:column; disabled on h:button.

3.0

The namespaces become jakarta.faces.*; the tag behaviour is unchanged.

4.0

Namespace URNs jakarta.faces.html, jakarta.faces.core, jakarta.faces.facelets replace the http://xmlns.jcp.org/jsf/* and http://java.sun.com/jsf/* URIs (old ones are planned for removal in 5.0). New: type on h:inputText, multiple and accept on h:inputFile, f:selectItemGroup and f:selectItemGroups, layout="list" for h:selectOneRadio and h:selectManyCheckbox.

4.1

rowStatePreserved and the id attribute of h:head and h:body are added to the VDL documentation (the 4.1 VDL says the id of those two tags "is only rendered when the current doctype is a HTML5 doctype"). No new h tag.

5.0 (milestones)

Not released. Planned work is listed on the versions page; none of it is assumed here. The specification page lists a placeholder attribute for h:inputText and h:inputTextarea (issue 2025) and oninput-style HTML5 events for UIInput (issue 1507) as planned; neither exists in 4.1, so use a pass-through attribute for them today (HTML5 page).

Where the Books Are Outdated

The standard component library is the part of the books that has aged best, because the tags are stable. Still:

  • JavaServer Faces 2.0: The Complete Reference (Burns and Schalk), which has a full reference of the standard components and chapters on selection and output components, was written for Faces 2.0. It does not have the type attribute of h:inputText, layout="list", f:selectItemGroups, the group attribute of h:selectOneRadio, multiple and accept on h:inputFile, h:commandScript, the jakarta.faces.* namespace URNs, or the jakarta. package names (its Java uses javax.faces). Its tag reference is still a useful guide to the older attributes.

  • The books that predate Faces 2.0 (the Mann and the Dudney books) show JSP pages with <%@ taglib uri="http://java.sun.com/jsf/html" %>, the f:view wrapper and h:outputText for every piece of text. JSP views were removed in 4.0, and on Facelets expressions work in template text. The component model behind the tags is the same, which is the reason to keep those books for background.

  • Recipes in the JSF 2.0 Cookbook and similar books that add file upload, rich tables or selection widgets with Tomahawk (t:), Trinidad or RichFaces components target libraries that no longer exist; with the standard tags, use h:inputFile, layout="list" and CSS, and for richer widgets the PrimeFaces components (PrimeFaces pages, other libraries).

  • The PrimeFaces Cookbook shows p: components that stand in for the standard ones (p:inputText, p:selectOneMenu, p:commandButton); the standard tags remain the base, and PrimeFaces 16 builds on them.

Use the books for the explanation of the component model and the way the tags are meant to be combined, and the VDL documentation and this page for the attribute lists and rendered HTML of Faces 4.1.
