Jakarta Faces on Spring Boot with JoinFaces

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Faces 4.1, JoinFaces 6.1.1 (2026-09-04) on Spring Boot 4.1.1 and Spring Framework 7.0.9, Java 17 or later (the examples compile with java.version 21 and were run on JDK 26), PrimeFaces 16.0.0 and OmniFaces 5.5.5. The versions JoinFaces itself selects are older than the newest releases of the libraries it integrates, and the page says which is which: the JoinFaces 6.1.1 starters pin Mojarra 4.1.12, MyFaces 4.1.3, Weld 6.0.4.Final, OmniFaces 5.5.1 and PrimeFaces 15.0.17, and Spring Boot 4.1.1 brings Tomcat 11.0.24. Everything below was run on 2026-10-08 with a scratch Bookshelf application built on Maven; behaviour that was not run is marked as such. Faces 4.0 differences are noted where they matter.

Spring Boot does not support Faces out of the box: it has no FacesServlet registration, no web.xml, and an embedded servlet container that is started before any Faces initialiser would run. JoinFaces is the community project that closes the gap. Its starters pull the Faces implementation, the CDI container Mojarra needs and, optionally, PrimeFaces or OmniFaces; its auto-configuration registers the FacesServlet, runs the servlet container initialisers that a full server would run, maps Spring Boot properties to Faces context parameters, and teaches Spring about the Faces scopes. The existing page Server-Side Web UI Frameworks introduces JoinFaces next to Thymeleaf and Vaadin and calls it a legacy choice; this page goes much deeper, and the last sections explain when the other choices are the better ones.

How JoinFaces Fits Together

Three containers coexist in a JoinFaces application, and most surprises come from forgetting that.

  • Spring creates and wires every bean you write: the EL resolver org.springframework.web.jsf.el.SpringBeanFacesELResolver, registered by a META-INF/faces-config.xml that ships inside joinfaces-autoconfigure, lets #{catalogueBean.books} resolve a Spring bean.

  • Weld (or OpenWebBeans) is present because Mojarra 4.1 refuses to start without CDI (on Tomcat without a CDI container it fails with a ClassNotFoundException for ELAwareBeanManager; Tomcat and Weld covers that setup) and because OmniFaces and PrimeFaces use CDI. In a Boot application it is a library for the framework, not the container of your beans.

  • The embedded servlet container (Tomcat 11.0.24 with Spring Boot 4.1.1) hosts the FacesServlet that JoinFaces registers through Boot’s ServletRegistrationBean mechanism, plus Spring Security’s filter chain when it is present.

flowchart LR B[Browser] --> T[Embedded Tomcat] T --> S[Servlet filters: Spring Security, open EntityManager in view] S --> F[FacesServlet registered by JoinFaces] F --> L[Faces lifecycle: six phases] L --> E[EL: SpringBeanFacesELResolver] E --> P[Spring beans with request, session or view scope] P --> R[Services and Spring Data repositories] W[Weld: CDI for Mojarra and OmniFaces] -.-> L

Faces features that need no CDI bean of your own (the lifecycle, Facelets, f:ajax, converters registered by id, resource handling) behave as on any other runtime and are documented in the other pages of this section; this page covers only what changes when the container is Spring.

package org.example.bookshelf.model;

import java.io.Serializable;

public record Book(long id, String title, String author, String isbn) implements Serializable {
}
package org.example.bookshelf.service;

import java.util.List;
import org.example.bookshelf.model.Book;
import org.springframework.stereotype.Service;

@Service
public class BookService {

    private final List<Book> books = List.of(
            new Book(1, "Dune", "Frank Herbert", "9780441172719"),
            new Book(2, "Neuromancer", "William Gibson", "9780441569595"),
            new Book(3, "Solaris", "Stanislaw Lem", "9780156027601"));

    public List<Book> findAll() {
        return books;
    }
}
package org.example.bookshelf.web;

import jakarta.faces.view.ViewScoped;
import java.io.Serializable;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;
import org.springframework.stereotype.Component;

@Component("catalogueBean")
@ViewScoped
public class CatalogueBean implements Serializable {

    private final BookService bookService;
    private int clicks;

    public CatalogueBean(BookService bookService) {
        this.bookService = bookService;
    }

    public List<Book> getBooks() {
        return bookService.findAll();
    }

    public void click() {
        clicks++;
    }

    public int getClicks() {
        return clicks;
    }
}

Two things are different from a Jakarta EE server. The bean is a Spring @Component with an explicit name (the name EL uses), and its constructor takes a Spring bean: constructor injection works because Spring, not CDI, instantiates it. The @ViewScoped annotation is the Faces one (jakarta.faces.view.ViewScoped), and JoinFaces maps it to a Spring scope (see Scopes: Spring and CDI Annotations on Spring Beans). A view bean is held in the view map and must be Serializable (see the serialisation advice in Scopes); its Spring collaborators are not serialisable state, so test the configuration you deploy if view state is ever serialised (client state saving, a clustered session).

The view sits under META-INF/resources of the classpath, which Tomcat serves like a web root. That is why src/main/resources and not src/main/webapp is the location in a JAR application. Templates and includes go under META-INF/resources/WEB-INF:

The layout template stays unreachable by URL, and a client view uses it

Mappings and the Welcome Page

JoinFaces registers one servlet named FacesServlet with the mappings /faces/*, *.jsf, *.faces and *.xhtml (property joinfaces.faces-servlet.url-mappings). In the run, /index.xhtml, /index.jsf, /index.faces and /faces/index.xhtml all rendered the same view. That convenience has a security cost described in Spring Security: Filters, URL Rules and Facelet Tags: every alias is a separate URL for the same page.

GET / answered 404. Spring Boot’s welcome-page handling belongs to Spring MVC, which is not present, so Tomcat looks for a welcome file and finds none that maps to a Faces view. The fix is a welcome file registered on the Tomcat context:

WelcomePage.java: make / show index.xhtml (Spring Boot 4 package names)
package org.example.bookshelf;

import org.springframework.boot.tomcat.servlet.TomcatServletWebServerFactory;
import org.springframework.boot.web.server.WebServerFactoryCustomizer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class WelcomePage {

    @Bean
    WebServerFactoryCustomizer<TomcatServletWebServerFactory> welcomeFile() {
        return factory -> factory.addContextCustomizers(context -> context.addWelcomeFile("index.xhtml"));
    }
}

With it, GET / answered 200. Setting joinfaces.faces.automatic-extensionless-mapping=true made GET /index answer 200 as well (it answered 404 before); the Faces side of that setting is the extensionless mapping described in Project Setup.

Newer Library Versions Than the Starters Pin

The versions in the table are what the 6.1.1 starters and BOM carry, which lags the libraries' newest releases. To move one forward:

  • Mojarra and OmniFaces have a plain management entry. Declaring the artifact in your own dependencyManagement, before the imported platform BOM, was enough: org.glassfish:jakarta.faces 4.1.17 and org.omnifaces:omnifaces 5.5.5 replaced 4.1.12 and 5.5.1, and the log said Initializing Mojarra 4.1.17. MyFaces is declared the same way in its starter (myfaces-api and myfaces-impl); an override was not run for it.

The joinfaces.jsf.* Names Are Silently Ignored

The appendix of the JoinFaces 6.1.1 reference lists joinfaces.jsf.project-stage, joinfaces.jsf.facelets-refresh-period and the rest under the prefix joinfaces.jsf.*, while the prose of the same document uses joinfaces.faces.*. The configuration metadata inside joinfaces-autoconfigure-6.1.1.jar settles it: the joinfaces.jsf.* entries are marked deprecated at level error with the replacement joinfaces.faces.*, and 28 properties are in that state. Starting the application with --joinfaces.jsf.project-stage=development produced Production: the property was ignored and the start-up log said nothing. The same value under joinfaces.faces.project-stage gave Development. An IDE that reads the metadata flags the old name; a command line or an environment variable does not. Treat any snippet or blog post that uses joinfaces.jsf. as written for an older JoinFaces. The joinfaces.mojarra.*, joinfaces.myfaces.*, joinfaces.primefaces.* and joinfaces.omnifaces.* names were not renamed.

The Default Project Stage

With no property the stage was Production, which is the Faces default but differs from what many tutorials assume for a development run (see Configuration and Project Stages). Set the development stage in a Spring profile (application-dev.properties) and never in the base file.

Secrets

Two JoinFaces properties carry secrets. Both must come from the environment or a secret store, never from a committed application.properties:

  • joinfaces.primefaces.secret has the metadata default primefaces. With nothing configured, the running application reported primefaces.SECRET equal to the string primefaces, a publicly known value. PrimeFaces uses it to encrypt the value expressions that streamed content (charts, images) exposes in URLs. With joinfaces.primefaces.secret=${PRIMEFACES_SECRET} the parameter was set to the environment value.

  • joinfaces.myfaces.secret (and mac-secret) initialise the key that encrypts and signs client-side view state. They are needed on every node of a cluster when joinfaces.faces.state-saving-method=client; the state-saving page explains the key format (client-state keys).

What the numbers and the log lines show:

  • Every one of the eleven beans was created by Spring. The probe inspected the creating stack: org.springframework.beans, never org.jboss.weld. A class annotated @Named is picked up by Spring’s component scan (Spring supports jakarta.inject.Named as a stereotype), and the CDI scope annotation is then interpreted by JoinFaces as a Spring scope. The @Named @SessionScoped bean behaved like a Spring session bean and was destroyed with the session. Weld is installed for the framework only.

  • @ViewScoped works on a Spring component. A new view (a GET) creates a new instance, postbacks to the same view reuse it (instance 1 in both POST columns, the view of the first GET), and a click counter stored in it accumulated across postbacks (three clicks in a row gave clicks 3 on the Bookshelf page). A different session got a new instance (3).

  • Destruction. Request-scoped beans were destroyed at the end of each request. After a navigation to a different view (an action returning other), the view-scoped beans of the old view were destroyed; after invalidateSession() the session-scoped and the view-scoped beans were destroyed. The singleton and the @ClientWindowScoped bean were created at start-up and never destroyed.

  • @ClientWindowScoped is not mapped. The annotation is accepted, nothing complains, and the bean is an ordinary singleton shared by every user and every browser window: instance 1 in every column, created at start-up, even from a second session. This is the most dangerous row of the table, because the Faces annotation suggests per-window isolation. Do not use it on Spring beans; keep window-scoped state in a @ViewScoped bean or use a real CDI bean (see Multi-Window Support).

  • @FlowScoped and @Dependent are not in the documented mapping, and flows were not run on JoinFaces for this page. Treat Faces Flows as unsupported on Spring beans unless you test them. The @ConversationScoped mapping to the HTTP session means a Spring bean with that annotation never has a conversation that can begin or end.

Choosing the Annotation

For new code use the Spring annotations and the Faces @ViewScoped; they are the supported surface of the reference, and a reader from a Spring background understands them. @Named/CDI scopes work through the same mapping, which is convenient while moving a class from a Jakarta EE server (compare Backing Beans and CDI), but they hide the fact that the bean is not a CDI bean: observers, interceptors, @Produces methods and @Inject of CDI-only types do not apply to it. The rules of the Scopes page still hold on top: no request data in a session bean, a view bean must be serialisable, and a view-scoped bean holds only what that view needs. The probe numbers above are the proof for the view-scope lifetime; the serialisation rules for client state saving are in the limits of view scope.

Spring Beans in Faces Artefacts

Spring beans are reachable from EL, so anything that accepts a value expression accepts a Spring bean. Converters and validators have two registration forms, and only one of them works with Spring injection.

A validator and a converter written as Spring components, referenced by EL
package org.example.bookshelf.web;

import jakarta.faces.application.FacesMessage;
import jakarta.faces.component.UIComponent;
import jakarta.faces.context.FacesContext;
import jakarta.faces.validator.ValidatorException;
import org.example.bookshelf.service.BookService;
import org.springframework.stereotype.Component;

@Component("isbnValidator")
public class IsbnValidator {

    private final BookService bookService;

    public IsbnValidator(BookService bookService) {
        this.bookService = bookService;
    }

    public void validate(FacesContext context, UIComponent component, Object value) {
        String isbn = String.valueOf(value);
        boolean known = bookService.findAll().stream().anyMatch(b -> b.isbn().equals(isbn));
        if (!known) {
            throw new ValidatorException(
                    new FacesMessage(FacesMessage.SEVERITY_ERROR, "Unknown ISBN", "Unknown ISBN " + isbn));
        }
    }
}
package org.example.bookshelf.web;

import jakarta.faces.component.UIComponent;
import jakarta.faces.context.FacesContext;
import jakarta.faces.convert.Converter;
import java.util.Locale;
import org.example.bookshelf.service.BookService;
import org.springframework.stereotype.Component;

@Component("titleConverter")
public class TitleConverter implements Converter<String> {

    private final BookService bookService;

    public TitleConverter(BookService bookService) {
        this.bookService = bookService;
    }

    @Override
    public String getAsObject(FacesContext context, UIComponent component, String value) {
        return value == null ? null : value.trim();
    }

    @Override
    public String getAsString(FacesContext context, UIComponent component, String value) {
        return value == null ? "" : value.toUpperCase(Locale.ROOT) + " of " + bookService.findAll().size();
    }
}

  <h:inputText id="title" value="#{isbnForm.title}" converter="#{titleConverter}"/>

Posting the form with an unknown ISBN produced the message Unknown ISBN from the validator, which called the injected service; a known ISBN passed, and the converter’s getAsString (which also uses the injected BookService) rendered DUNE of 3. The validator attribute takes a method expression, and the converter attribute of h:inputText accepts a value expression that evaluates to a Converter instance; both are normal Faces rules (see Converters and Validators). The cost is that the bean is a singleton shared by every request, so it must be thread-safe and stateless.

What does not work:

  • @FacesConverter(value = "bookConverter", managed = true) with @Inject BookService. The managed converter or validator form lets Faces create the instance through CDI. Under JoinFaces the request that used it failed with jakarta.faces.FacesException: @FacesConverter("bookConverter", managed=true) on …BookConverter could not be resolved by CDI. Weld does not register the classes of the application (see the next point), so the converter cannot be created through CDI. Register converters and validators as Spring components and reference them by EL, as above.

  • Expecting CDI to manage your classes. A @Named @RequestScoped class with an @Inject BookService field received the Spring singleton (the BookService instance printed by Spring and the one printed through the @Named bean had the same identity), because Spring processes @Inject itself. Adding META-INF/beans.xml (with bean-discovery-mode="annotated" or "all") did not change that: in the executable JAR Weld logged WELD-000119: Not generating any bean definitions from BOOT-INF.classes.org.example.bookshelf… for the application classes and registered none of them. CDI-only features on your classes (observers, producers, interceptors, decorators) would therefore not be discovered; that was not run. There is one container for them, and it is Spring.

  • @FacesConverter("id") without managed. Faces instantiates the class itself, so constructor injection is impossible.

The Spring @Autowired/constructor injection that works everywhere else in Boot is the rule here. The CDI injection of Faces artefacts documented in Backing Beans and CDI (@Inject FacesContext and the other producers) was not run on JoinFaces for this page; call FacesContext.getCurrentInstance() in a Spring bean instead, as the invalidate action of the probe application did.

import java.io.Serializable;
import org.springframework.stereotype.Component;

@Component("reviewBean")
@ViewScoped
public class ReviewBean implements Serializable {

    @NotBlank
    @Size(min = 10, max = 200)

    private String saved = "none";

    public String getComment() { return comment; }
    public void setComment(String comment) { this.comment = comment; }
    public String getSaved() { return saved; }

    public void save() {
        saved = comment;
        FacesContext.getCurrentInstance().addMessage(null, new FacesMessage("Saved"));
    }
}

Security on JoinFaces is Spring Security’s: the filter chain protects the URLs, the login form is a plain form that posts to the filter, and CSRF protection is Spring’s token. package org.example.bookshelf.security;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/jakarta.faces.resource/**", "/login.xhtml", "/index.xhtml").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .formLogin(form -> form
                .loginPage("/login.xhtml")
                .loginProcessingUrl("/login")
                .defaultSuccessUrl("/index.xhtml")
                .failureUrl("/login.xhtml?error"))
            .logout(logout -> logout
                .logoutUrl("/logout")
                .logoutSuccessUrl("/login.xhtml?logout"));
        return http.build();
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }

    // Demonstration only: a real application loads users from a database or an identity provider
    @Bean
    UserDetailsService users(PasswordEncoder encoder,
                             @Value("${bookshelf.users.reader.password}") String readerPassword,
                             @Value("${bookshelf.users.admin.password}") String adminPassword) {
        return new InMemoryUserDetailsManager(
                User.withUsername("reader").password(encoder.encode(readerPassword)).roles("USER").build(),
                User.withUsername("admin").password(encoder.encode(adminPassword)).roles("USER", "ADMIN").build());
    }
}

sec:isAllowed(url, method), isAnonymous, isAuthenticated, isFullyAuthenticated

EL functions for URL access and the authentication state

Run with two users (the passwords supplied as environment variables):

  • An anonymous request to /index.xhtml showed Please sign in; /admin/panel.xhtml answered 302 to /login.xhtml.

  • After login as reader, the page showed user=reader, the reader block and Welcome back, and sec:areAnyGranted('ROLE_ADMIN') and sec:isAllowed(...) were false; after login as admin the admin block, the url= block and both functions were true.

  • A Faces form post with the _csrf hidden field answered 200 and ran the action; the same post through f:ajax also worked (the field is part of the submitted form); a post from a form without the field answered 403. The Faces view state does not replace the Spring token, and the Spring token does not replace the view state: both are sent. Add the hidden field to every form (a Facelets tag file or a template makes that a one-line include).

Pitfall 1: POST /login Returns 404 Without a Default Servlet

The first run of this configuration answered 404 to POST /login, although the filter chain was healthy (a GET /admin/panel.xhtml was redirected to /login.xhtml). A servlet container looks up the servlet first and runs filters only when a servlet matched. A JoinFaces application has no Spring MVC DispatcherServlet and Spring Boot does not register Tomcat’s default servlet, so /login and /logout match nothing: the filter that would handle them never runs. Either register the default servlet,

server.servlet.register-default-servlet=true

Source: JoinFaces reference documentation and Spring Boot: Common Application Properties.

(with it, the login answered 302 to /index.xhtml), add Spring MVC to the project, or use a processing URL that the FacesServlet maps (for example one ending in .xhtml; not run). The same applies to the logout URL.

Pitfall 2: The /faces/* Alias Bypasses the URL Rules

The rule /admin/** protected /admin/panel.xhtml, /admin/panel.jsf and /admin/panel.faces: a reader got 403 on all three. But the same view through the prefix mapping, /faces/admin/panel.xhtml, answered 200 and rendered the admin panel to the reader: the path does not start with /admin/, and the only thing between the user and the page was anyRequest().authenticated(). Two defences, use both:

  • Restrict the Faces servlet to the mapping you use. With joinfaces.faces-servlet.url-mappings=*.xhtml, the same request to /faces/admin/panel.xhtml answered 404, and /admin/panel.xhtml answered 403 for the reader.

  • Add a rule for every prefix you keep (/faces/admin/** next to /admin/**), and protect the data in the method layer (@PreAuthorize on the service that the page calls) so a missed alias cannot expose it.

The same reasoning applies to the extensionless mapping of OmniFaces FacesViews and of joinfaces.faces.automatic-extensionless-mapping: each new way to reach a view is a new URL that a rule can miss. Test the matrix of aliases for every protected view.

Sessions and Cookies

The embedded Tomcat accepts the session id in a cookie and, by default, in the URL. In the first response of a new browser, the form of index.xhtml rendered action="/index.xhtml;jsessionid=…", and the PrimeFaces resource URLs carried the id as well (Faces encodes URLs through the ExternalContext). A session id in a URL is exposed through logs, referrers and copy-pasted links. Restrict it to the cookie, and set the cookie attributes with the normal Spring Boot properties:

server.servlet.session.tracking-modes=cookie
server.servlet.session.cookie.same-site=lax
server.servlet.session.cookie.secure=true

With these properties the response carried Set-Cookie: JSESSIONID=…; Path=/; Secure; HttpOnly; SameSite=Lax and no jsessionid appeared in the page. HttpOnly was on by default. Secure makes the browser refuse the cookie over plain HTTP, so use it with HTTPS (or a profile for local development). The security page lists the other cookie, session fixation and header concerns (cookie attributes). JoinFaces also auto-configures a SpringSessionFixFilter (org.joinfaces.session); what it fixes was not investigated for this page.

The Development Loop and Tests

mvn spring-boot:run serves the views from target/classes/META-INF/resources, so a copy of an edited .xhtml into target/classes (your IDE or mvn process-resources does that) is visible without a restart if Facelets re-checks it. With only joinfaces.faces.project-stage=development, an edit made to target/classes/META-INF/resources/index.xhtml was not visible within three seconds; with joinfaces.faces.facelets-refresh-period=1 as well, the edit appeared in the next request (the same behaviour the Mojarra notes in Project Setup describe). Run with:

mvn spring-boot:run \
  -Dspring-boot.run.arguments="--joinfaces.faces.project-stage=development --joinfaces.faces.facelets-refresh-period=1"

Spring Boot DevTools' restart class loader was not run with JoinFaces. A packaged JAR cannot be edited; the refresh period matters only for exploded runs.

An integration test starts the real server on a random port and fetches the page; it exercises the Faces servlet, the Spring context, Weld and the view in one go:

CataloguePageTest.java

import static org.assertj.core.api.Assertions.assertThat;

import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.web.server.LocalServerPort;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class CataloguePageTest {

    @LocalServerPort
    int port;

    @Test
    void catalogueListsBooks() throws Exception {
        HttpResponse<String> response = HttpClient.newHttpClient().send(
                HttpRequest.newBuilder(URI.create("http://localhost:" + port + "/index.xhtml")).build(),

Arquillian containers target Jakarta EE servers; the Spring test support above is the natural integration test here. Unit tests of beans, converters and validators are plain JUnit 5 and Mockito tests as everywhere (Spring Boot unit and integration testing).

When to Choose Thymeleaf or Vaadin Instead

JoinFaces makes Faces possible in a Spring Boot codebase; it does not make it the default. The comparison below uses what this page measured and what the neighbouring pages say.

Question JoinFaces (Faces) Thymeleaf Vaadin

What is the programming model?

Component tree and view state on the server; Facelets XHTML; Ajax through f:ajax or PrimeFaces

Server-rendered templates over Spring MVC; stateless requests; htmx or Alpine.js for interactivity

Java UI components on the server with a client engine; session state per UI

What does Spring Boot support?

Third-party integration (JoinFaces): own scope mapping, own properties, versions that lag the libraries by weeks to months

First-class auto-configuration (spring-boot-starter-thymeleaf)

Official Vaadin Spring add-on; Boot-aligned releases

What does it cost to reach the same URL safely?

Servlet aliases, a default servlet for the Spring Security filter, and a CSRF field in every form (Spring Security: Filters, URL Rules and Facelet Tags)

Spring MVC and Spring Security as documented

Router and Spring Security as documented

Where is Faces the right answer?

An existing Faces or PrimeFaces application moving to Spring Boot, a team already fluent in Faces, component-rich internal back-offices

New content sites, SEO-sensitive pages, small CRUD

Rich internal applications written entirely in Java by a team that does not want HTML templates

Prefer Thymeleaf or Vaadin for new Spring Boot work; the Server-Side Web UI Frameworks page has the full decision table, the Thymeleaf Reference and the Vaadin Spring Boot integration page cover the alternatives, and the introduction of this section compares all three (framework comparison). Use JoinFaces when the Faces investment already exists, when a Jakarta EE server is not an option, or when the Spring ecosystem (Data, Security, Actuator, configuration) is the reason for the move. Do not choose it because it hides the Faces runtime behind a starter: the scopes, security aliases and library versions above are exactly the places where the hidden machinery shows.

Mojarra Versus MyFaces on JoinFaces

  • CDI. The Mojarra starter depends on the CDI starter and so on Weld; Mojarra 4.1 does not start without CDI. MyFaces started without Weld, and the Spring scopes worked the same. Add Weld only when a library requires it.

  • Version pins. The 6.1.1 starters pin Mojarra 4.1.12 and MyFaces 4.1.3; the newest releases are Mojarra 4.1.17 and MyFaces 4.1.4. Mojarra 4.1.17 was substituted successfully with a management entry (Starters, BOMs and Version Overrides).

  • Property sets. joinfaces.mojarra.* and joinfaces.myfaces.* expose the parameters of each implementation. Client-side state is where they differ in practice: Mojarra encrypts by default and takes joinfaces.mojarra.client-state-timeout (seconds); MyFaces needs joinfaces.myfaces.secret and has joinfaces.myfaces.client-view-state-timeout (minutes). The MyFaces run with joinfaces.faces.state-saving-method=client and secret=${MYFACES_SECRET} rendered the page and processed three postbacks.

  • Bean Validation. MyFaces logs that Bean Validation support is disabled when no provider is present; add the Boot validation starter for either implementation.

  • Everything else (lifecycle, rendering, Ajax, scope behaviour in the table of Scopes: Spring and CDI Annotations on Spring Beans) was identical in the runs; the general differences are in Mojarra versus MyFaces.

What Changed

  • JoinFaces 6.1.1 (2026-09-04) on Spring Boot 4.1.1. The version used on this page. The properties moved from joinfaces.jsf.* to joinfaces.faces.*, and the old names are deprecated at level error in the metadata (28 of them), which in a run means ignored.

  • Spring Boot 4. Package names of the embedded-container API moved: TomcatServletWebServerFactory is now in org.springframework.boot.tomcat.servlet (used by the welcome-page class above), while SpringBootServletInitializer stays in org.springframework.boot.web.servlet.support. Spring Framework 7 still contains SpringBeanFacesELResolver, which JoinFaces registers.

  • Faces 4.0 to 4.1. The starters in this JoinFaces release are the Faces 4.1 line (Mojarra 4.1.x, MyFaces 4.1.x), so features that need 4.1 are available; Faces 5.0 is still a milestone and nothing here describes it.

  • Not covered by the reference or this run. Native image support (the library contains AOT hint registrars; a native build was not run), the OpenWebBeans starter, Jetty and Undertow containers, Tobago, f:websocket / @Push on Spring beans (the property joinfaces.faces.websocket-endpoint-port exists for a differing port; push was not run) and Faces Flows.

Where the Books Are Outdated

  • Anghel Leonard’s JSF 2.0 Cookbook (2010) integrates Spring 2.5 with JSF 2.0 through Spring’s DelegatingVariableResolver. That mechanism ended long ago: the variable resolvers were removed from Faces in 4.0 (EL resolvers replaced them), and the managed-bean XML that such recipes combine it with is gone too. Today JoinFaces registers a SpringBeanFacesELResolver and Spring annotations declare the beans; the "Spring beans in EL" recipe is now a dependency and a few properties.

  • The older books never show an embedded container, @SpringBootApplication, the view scope or Boot properties: they assume a WAR in a container with web.xml for every setting. Where they say "set this context parameter", the JoinFaces form is a joinfaces.* property or server.servlet.context-parameters.*.

  • The Mann and Dudney books integrate Faces with Struts 1, which reached end of life in 2013; Spring MVC, Spring Security and Spring Boot are the current equivalent surroundings, and a Boot migration of a Struts application goes through Faces (or a different UI technology) and not through that integration.

  • The PrimeFaces books of Çalışkan and Varaksin, and Jonna, assume a hand-edited web.xml and a manual JAR; the starters replace both, and several parameters they name moved (the PrimeFaces pages list them).

  • Burns and Schalk predate Spring Boot and Jakarta EE namespaces; every javax.faces import in an old Spring-and-Faces tutorial must be jakarta.faces for JoinFaces 6.

Pitfalls

  • @ClientWindowScoped on a Spring bean. Accepted and ignored: the bean is a singleton shared by everyone (Scopes: Spring and CDI Annotations on Spring Beans).

  • joinfaces.jsf.* properties. Silently ignored by 6.1.1; use joinfaces.faces.* (Configuration Properties).

  • Secrets in property files. joinfaces.primefaces.secret defaults to a public value, and the MyFaces secrets must be set explicitly; read them from the environment.

  • Production stage by default. The stage was Production with no property; set Development per profile.

  • @FacesConverter(managed = true) or CDI injection of Spring beans. Fails; register Spring components and reference them from EL (Spring Beans in Faces Artefacts).

  • A beans.xml and CDI-only features. Weld does not register the application classes of an executable JAR (WELD-000119); observers, producers and interceptors written for CDI would not be found (Spring Beans in Faces Artefacts; not run).

  • POST /login returning 404. No default servlet, so the Spring Security filter never sees the request (Spring Security: Filters, URL Rules and Facelet Tags).

  • Authorisation rules that miss /faces/*. Restrict the servlet mappings and test every alias.

  • Missing CSRF token in Faces forms. The Spring token is separate from the view state; Ajax posts need it too.

  • Session ids in URLs. Set server.servlet.session.tracking-modes=cookie.

  • No welcome page. GET / is 404 until index.xhtml is registered as a welcome file.

  • Library versions assumed from the JoinFaces version. The starters pin older Mojarra, MyFaces, OmniFaces and PrimeFaces (and the PrimeFaces jakarta classifier needs exclusions to override).

  • Open EntityManager in view left on. Hides N+1 queries behind the rendering of a page; see Open Session in View.

  • Not marking the bean serialisable. A @ViewScoped bean is held in the view map; keep it Serializable and test the configuration you deploy (client state saving, a replicated session) with its Spring collaborators.
