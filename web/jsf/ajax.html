Ajax

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Faces 4.1 (API jakarta.faces-api 4.1.2, part of Jakarta EE 11), Eclipse Mojarra 4.1.17 and Apache MyFaces Core 4.1.4, with Java 17 or later. The change lists of the 4.1 and 4.0 specifications contain a single Ajax entry (an improvement of f:ajax inside composite components in 4.0) and no 4.1 entry, so the text also describes Faces 4.0 (nothing was run on 4.0); the earlier releases are in What Changed. The examples were compiled and deployed in a scratch Bookshelf WAR on Apache Tomcat 11.0.26 with Weld 6.0.4.Final, once with Mojarra and once with MyFaces. The server side was driven with curl, and the JavaScript side with a real browser (headless Google Chrome controlled through the DevTools protocol), so the request parameters, the partial responses, the event and error payloads and the timings come from those runs (checked on 2026-10-08). The places where the two implementations disagree are collected in Mojarra and MyFaces.

Ajax is how a Faces page changes part of itself without a full page load. Faces does it without any hand-written JavaScript or response format on the application’s side: a behaviour attached to a component (f:ajax) makes the browser send the form with a marker header, the server runs the usual lifecycle on only the components that the page named, and it answers with an XML document, the partial response, that tells the browser which pieces of markup to replace. Everything the framework does here is specified (chapters 13 and 14 of the specification, the JavaScript documentation and the PartialViewContext API), which is why the same page works on every implementation and with every component library.

The Ajax Model

An Ajax request in Faces is not a different kind of request. It is a normal postback of the page’s form, with three differences:

  • It is sent by faces.ajax.request (the JavaScript function in the faces.js resource) as an asynchronous POST, with the request header Faces-Request: partial/ajax and the request parameter jakarta.faces.partial.ajax=true. The URL is the action of the form.

  • It names which components take part in the execute half of the lifecycle (jakarta.faces.partial.execute) and which are re-rendered (jakarta.faces.partial.render). Both are lists of client ids, or one of the keywords @all and @none.

  • The response is not a page. It is a text/xml document of update, insert, delete, attributes, eval, redirect and error operations that faces.ajax.response applies to the DOM.

There are three ways to start such a request from a view, and all three end in faces.ajax.request:

Entry point What it is Use it when

f:ajax

A tag that attaches an AjaxBehavior to a component, or to every component inside it.

A component should send a request on one of its own events. This is the normal case.

faces.ajax.request(source, event, options)

The JavaScript API, called from any script or event attribute.

The request is triggered by something that is not a Faces component event, or the options are computed.

h:commandScript

A component that renders a named JavaScript function which, when called, sends the request.

A script (a timer, a callback of a third-party widget, the load event) needs to call a server method.

The server side is jakarta.faces.context.PartialViewContext. The tutorial says it captures the state of an Ajax request (which components are executed, which are rendered), and that its processPartial(PhaseId) method does the partial tree traversal in each phase. A request is partial when PartialViewContext.isPartialRequest() is true; it is an Ajax request when isAjaxRequest() is true, which the API documentation defines as the presence of the Faces-Request header with the value partial/ajax. The same documentation says that isPartialRequest() is also true for the header value partial/process, a partial processing request that is not Ajax; this page deals with partial/ajax.

Source: Jakarta EE Tutorial: Using Ajax with Facelets and Jakarta Faces 4.1 specification, 13. Ajax Integration

A First Example: Live Search in Bookshelf

The catalogue of Bookshelf gets a search box that filters the list while the user types, without a page load. The page below is shown without the site template. The f:ajax inside the h:inputText sends a request 300 milliseconds after the last key-up, runs the bean’s search listener, and re-renders the result list and the counter.

src/main/webapp/search.xhtml
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core"
      xmlns:ui="jakarta.faces.facelets">
<h:head>
  <title>Search the catalogue</title>
</h:head>
<h:body>
  <h:form id="search">
    <h:inputText id="q" value="#{searchBean.query}">
      <f:ajax event="keyup" delay="300" listener="#{searchBean.search}" render="results count"/>
    </h:inputText>
    <h:outputText id="count" value="#{searchBean.searches} searches"/>
    <h:panelGroup id="results" layout="block">
      <ui:repeat value="#{searchBean.results}" var="b">
        <div class="book">#{b.title} by #{b.author}</div>
      </ui:repeat>
    </h:panelGroup>
  </h:form>
</h:body>
</html>
src/main/java/org/example/bookshelf/web/SearchBean.java
package org.example.bookshelf.web;

import jakarta.faces.event.AjaxBehaviorEvent;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;

@Named
@ViewScoped
public class SearchBean implements Serializable {

    @Inject
    private BookService books;

    private String query = "";
    private List<Book> results;
    private int searches;

    public void search(AjaxBehaviorEvent event) {
        searches++;
        results = books.search(query);
    }

    public List<Book> getResults() {
        return results != null ? results : books.findAll();
    }

    public int getSearches() { return searches; }
    public String getQuery() { return query; }
    public void setQuery(String query) { this.query = query; }
}

Typing Dune, Gibson and Le Guin into the field in a browser changed the counter to 1 searches, 2 searches and 3 searches and the list to the matching books, on both implementations. The counter keeps growing because the bean is @ViewScoped: the same instance serves every Ajax request of the view, which is the scope an Ajax-driven page almost always wants. A @RequestScoped bean would be created again for every request; that is fine for a listener whose result is rendered in the same request, as in the review preview below, and wrong for state that must survive until the next request.

A Throwaway Bean for the Small Examples

The short examples further down (groups, resetValues, h:commandScript, the listener traces and the programmatic behaviour) share one view-scoped bean, jsBean, so that each page stays a few lines. It is scaffolding for the experiments, not a Bookshelf class:

package org.example.bookshelf.web;

import jakarta.faces.context.FacesContext;
import jakarta.faces.event.AjaxBehaviorEvent;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.List;

@Named
@ViewScoped
public class JsBean implements Serializable {

    @Inject
    private FacesContext faces;

    private String name = "start";
    private String last = "";
    private boolean flag;
    private boolean visible;

    public void refresh() {
        last = "refreshed:" + name + ":" + faces.getExternalContext().getRequestParameterMap().get("tag");

    public String go() { return "js?faces-redirect=true"; }

    public List<String> getIds() { return List.of("a", "b"); }

    public void setName(String name) { this.name = name; }
    public String getLast() { return last; }
    public boolean isFlag() { return flag; }
    public void setFlag(boolean flag) { this.flag = flag; }
    public boolean isVisible() { return visible; }
}

One Request from Keystroke to DOM Update

The numbered steps of the diagram are the ones to keep in mind when something does not update.

sequenceDiagram autonumber actor U as User participant B as Browser with faces.js participant S as FacesServlet participant L as Lifecycle and component tree participant M as SearchBean U->>B: types in the search field B->>B: delay 300 ms, keep only the last call, queue the request B->>S: POST /search.xhtml with Faces-Request partial/ajax Note over B,S: parameters partial.execute, partial.render, source, behavior.event, ViewState and the executed fields S->>L: Restore View, PartialViewContext lists execute and render ids L->>L: Apply Request Values, Process Validations, Update Model Values for the execute ids only L->>M: Invoke Application, AjaxBehaviorEvent reaches search() M-->>L: query applied, results computed L->>L: Render Response for the render ids only L-->>B: text/xml partial-response with update elements and the new ViewState B->>B: events complete and success, faces.ajax.response replaces the DOM elements B-->>U: the list and the counter change, the rest of the page is untouched

The request that the browser actually sent for the live search (decoded, from a request filter in the scratch application; Mojarra 4.1.17):

Content-Type: application/x-www-form-urlencoded;charset=UTF-8

search                          = search
search:q                        = Dune
jakarta.faces.ViewState         = ...
jakarta.faces.partial.ajax      = true

jakarta.faces.source            = search:q
jakarta.faces.partial.execute   = search:q

and the answer (Mojarra; the markup inside each CDATA section is the normal rendering of that component):

<?xml version='1.0' encoding='UTF-8'?>
<partial-response><changes>
  <update id="search:count"><![CDATA[<span id="search:count">1 searches</span>]]></update>
  <update id="search:results"><![CDATA[<div id="search:results">
        <div class="book">Dune by Frank Herbert</div>
        <div class="book">Dune Messiah by Frank Herbert</div></div>]]></update>
  <update id="j_id1:jakarta.faces.ViewState:0"><![CDATA[8277362929392712006:9149938755704541982]]></update>
</changes></partial-response>

Three details of the capture are worth knowing. The render list named results first, but the update for count comes first: components are rendered in the order of the component tree, not in the order of the list (on both implementations). The ViewState update is always last and keeps the form’s view state current, so the next request carries a valid one. And the browser sent only the field that was executed: Mojarra 4.1.17 posts just the controls named in execute (plus the form marker), while MyFaces 4.1.4 posts every field of the form and the hidden formId_SUBMIT marker. Both are valid, because only executed components are decoded.

The f:ajax Tag

f:ajax registers an AjaxBehavior on one component, or on every ClientBehaviorHolder component inside it (see Grouping Components). The tag library is jakarta.faces.core. The attributes, as the VDL documentation lists them:

Attribute Value Meaning

execute

space-separated search expressions, or an expression that evaluates to a Collection<String>

The components that take part in Apply Request Values, Process Validations and Update Model Values. Default @this.

render

same

The components rendered in Render Response. Default @none.

event

a string or an expression

The client event that sends the request. A DOM event name without the on prefix (click, keyup, blur), or action for command components and valueChange for input components. If omitted, the component’s default is used.

listener

a method expression

Called once with an AjaxBehaviorEvent when the behaviour event is broadcast. See The listener and the AjaxBehaviorEvent.

onevent

the name of a JavaScript function

Called at the begin, complete and success stages of the request. See Events on the Client: onevent and addOnEvent.

onerror

the name of a JavaScript function

Called when the request or the response fails. See Ajax Error Handling.

delay

milliseconds, or the literal none

If less than this much time passes between two calls, only the last is sent. See delay, Queueing and disabled.

resetValues

a boolean

Resets the inputs named in render before rendering. See resetValues.

disabled

a boolean

true keeps the behaviour from being rendered. Default false.

immediate

a boolean

true broadcasts the behaviour event in Apply Request Values instead of Invoke Application. See The listener and the AjaxBehaviorEvent.

The execute and render attributes accept search expressions, so the keywords and the relative and absolute client ids are described together in execute and render.

Source: Jakarta Faces 4.1 VDL: f:ajax and Jakarta EE Tutorial: Attributes of the f:ajax Tag

The event Attribute and the Default Events

f:ajax with no event uses the default of the component it is nested in: action for an ActionSource such as a button or a link, valueChange for an EditableValueHolder such as an input (the tutorial). The names are logical, and each component maps them to a DOM event. What the two implementations rendered for the standard components:

onchange

h:selectBooleanCheckbox

h:selectOneRadio, h:selectManyCheckbox (each item)

Only the browser’s own events are possible beyond the logical ones, and each component accepts a fixed list. getEventNames() of ClientBehaviorHolder returns it. An unsupported name fails when the view is built, not when the user acts: with event="onkeyup" on an h:inputText, Mojarra answered with a 500 whose title read 'onkeyup' is not a supported event for HtmlInputText and listed blur, change, click, dblclick, focus, keydown, keypress, keyup, mousedown, mousemove, mouseout, mouseover, mouseup, select, valueChange, and MyFaces answered 500 with it is not a valid eventName defined for this component. The on prefix is the usual mistake.

The standard components that implement ClientBehaviorHolder (the API documentation lists them) include the input, select and command components, h:form, h:body, h:outputLabel, h:outputLink, h:link, h:button, h:graphicImage, h:panelGrid, h:panelGroup, h:dataTable, h:inputFile and UIWebsocket (the component behind f:websocket, which accepts a nested f:ajax). h:outputText is not one; to make a piece of text clickable, wrap it in an h:panelGroup with event="click":

<h:panelGroup id="rating" layout="block">
  <f:ajax event="click" render="details"/>
  <h:outputText value="#{book.title}"/>
</h:panelGroup>

execute and render

execute answers "which components does the server process?", render answers "which components does the server send back?". They are independent: a request can execute one input and render a different panel, execute a whole form and render nothing, or execute nothing and render a clock.

Keywords

The specification defines four keywords for both attributes. They are resolved in the browser: the handler that the server renders still contains the keyword, and faces.ajax.request replaces it with client ids before it sends the request.

Keyword Meaning

@this

The component that triggered the request (the source). Default of execute.

@form

The form that encloses the source.

@all

The whole view. For render the response is one update of jakarta.faces.ViewRoot that replaces the document.

@none

Nothing. Default of render; the jakarta.faces.partial.render parameter is then not sent at all.

The search expression framework of Faces 2.3 adds more (@parent, @namingcontainer, @next, @previous, @child(n), @id(...), custom keywords), and the page on search expressions covers all of them and SearchExpressionHandler. The VDL documentation of f:ajax says the values are search expressions, so any of them is valid here.

Two things happen between the tag and the wire. At render time the tag handler resolves relative and absolute ids to client ids: in the review form, render="@form :messages" was rendered as mojarra.ab(this,event,'action','@form','@form messages') and myfaces.ab(this,event,'action','@form','@form messages',{}), so :messages (absolute, from the view root) became the client id messages of a component outside the form. And when the user clicks, faces.ajax.request resolves the keywords: a button with execute="@form" in a form with the id f sent jakarta.faces.partial.execute=f:boom f on Mojarra and f f:boom on MyFaces, the source’s id and the form’s id. So the source is part of the execute list even when the page names other components (Mojarra sent f:btn f:name for execute: 'f:name', MyFaces f:name f:btn).

That last fact matters for tests written by hand. A request posted with curl whose partial.execute omits the source button was processed by Mojarra without ever invoking the button’s f:ajax listener (the phase trace showed exec=[f:title] and no listener call), while MyFaces invoked it anyway. A raw request that sends the keyword itself (jakarta.faces.partial.execute=@form) fared no better: neither implementation expanded it on the server, so Mojarra processed nothing at all (no setter ran, no message, no error) and MyFaces ran the button’s action without the inputs (the action failed on the null rating). Copy what the browser sends.

Review Preview: Execute Several Inputs, Render the Preview

The review form of Bookshelf shows a preview as the user fills in the rating. The rating input executes both inputs (they belong together), runs the listener and re-renders the preview and the two field messages. A final button submits the whole form and renders the messages that live outside it.

src/main/webapp/review.xhtml
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core">
<h:head>
  <title>Review a book</title>
</h:head>
<h:body>
  <h:messages id="messages" globalOnly="true"/>
  <h:form id="review">
    <h:inputText id="reviewer" value="#{reviewBean.reviewer}" required="true"/>
    <h:message id="reviewerMsg" for="reviewer"/>

    <h:inputText id="rating" value="#{reviewBean.rating}" required="true">
      <f:validateLongRange minimum="1" maximum="5"/>
      <f:ajax event="change" execute="reviewer rating" listener="#{reviewBean.preview}"
              render="summary reviewerMsg ratingMsg"/>
    </h:inputText>
    <h:message id="ratingMsg" for="rating"/>

    <h:outputText id="summary" value="#{reviewBean.summary}"/>

    <h:commandButton id="send" value="Send" action="#{reviewBean.submit}">
      <f:ajax execute="@form" render="@form :messages"/>
    </h:commandButton>
  </h:form>
</h:body>
</html>
src/main/java/org/example/bookshelf/web/ReviewBean.java
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.FacesContext;
import jakarta.faces.event.AjaxBehaviorEvent;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import org.example.bookshelf.service.ReviewService;

@Named
@RequestScoped
public class ReviewBean {

    @Inject
    private FacesContext faces;
    @Inject
    private ReviewService reviews;

    private String reviewer;
    private Integer rating;
    private String summary = "";

    public void preview(AjaxBehaviorEvent event) {
        summary = reviewer + " gives " + rating + " stars";
    }

    public void submit() {
        int number = reviews.save(reviewer, rating);
        faces.addMessage(null, new FacesMessage(FacesMessage.SEVERITY_INFO, "Review " + number + " saved", null));
        summary = "";
    }

    public void failing() {
        throw new IllegalStateException("The review service is down");
    }

    public String getReviewer() { return reviewer; }
    public void setReviewer(String reviewer) { this.reviewer = reviewer; }
    public Integer getRating() { return rating; }
    public void setRating(Integer rating) { this.rating = rating; }
    public String getSummary() { return summary; }
}

A change request with reviewer=Ann and rating=4 answered with an update for review:summary containing Ann gives 4 stars and empty updates for the two messages; the phase listener trace showed the request going through all six phases with ajax=true, exec=[review:reviewer, review:rating] and render=[review:summary, review:reviewerMsg, review:ratingMsg]. With rating=9 the response carried the range message in review:ratingMsg, an empty review:summary, and the listener was not called (see The listener and the AjaxBehaviorEvent). The Send button re-renders @form and the absolute :messages, which is why the saved-message appears even though the h:messages component is not inside the form. If :messages were left out of render, the message would be added to the FacesContext of that request, never sent to the browser and lost with the request, which is the most common "my Ajax action does nothing" report.

Source: Jakarta EE Tutorial: Using the execute Attribute and Jakarta EE Tutorial: Receiving an Ajax Response

Ids from an Expression

Both attributes accept a value expression that evaluates to a Collection<String>, for ids that are decided at run time. With a bean method getIds() returning List.of("a", "b"), the markup

<h:inputText id="a" value="#{jsBean.name}">
  <f:ajax event="blur" execute="#{jsBean.ids}" render="#{jsBean.ids}"/>
</h:inputText>
<h:outputText id="b" value="#{jsBean.name}"/>

was rendered with the handler onblur="mojarra.ab(this,event,'blur','f:a f:b','f:a f:b')" (and the MyFaces equivalent): the collection was evaluated and resolved to client ids when the page was rendered. The expression is therefore evaluated during Render Response of the page that contains the tag, not when the user acts. A literal value is split on spaces.

Source: Jakarta Faces 4.1 VDL: f:ajax and Jakarta EE Tutorial: Using the f:ajax Tag

What Can Be Rendered

A component can be updated only if its element exists in the page. The browser replaces the contents of the element whose id matches the update. A component with rendered="false" produces no element, and a later request cannot add it:

<h:form id="f">
  <h:commandButton id="show" value="Show" action="#{jsBean.toggle}">
    <f:ajax render="ghost wrapper"/>
  </h:commandButton>
  <h:outputText id="ghost" value="ghost-text" rendered="#{jsBean.visible}"/>
  <h:panelGroup id="wrapper" layout="block">
    <h:outputText id="inner" value="inner-text" rendered="#{jsBean.visible}"/>
  </h:panelGroup>
</h:form>

Rendering ghost, whose element was absent at the first render, failed on Mojarra with the client error malformedXML and the description During update: f:ghost not found, and the updates after it in the response were not applied (the wrapper stayed empty). MyFaces skipped the unknown element silently and rendered wrapper with its inner text. The portable form is the second one: always render an element that is always in the page (wrapper) and let the conditional content live inside it. The same holds for tables and repeated rows; render the table, not a row that may not exist.

A rendered condition is evaluated on every request, so a component can switch from hidden to visible within the wrapper. Do not render h:head, h:body and the form element casually either: @all is the supported way to replace the document.

The listener and the AjaxBehaviorEvent

The listener attribute is a method expression with the signature public void processAjaxBehavior(AjaxBehaviorEvent event), the method of jakarta.faces.event.AjaxBehaviorListener; it may throw AbortProcessingException to stop lifecycle processing. The tutorial says it is called once, in Invoke Application. The event is queued during Apply Request Values (the behaviour’s renderer decodes it) and broadcast later, so the listener follows the same rules as an action method: it runs only if the executed components converted and validated without error and the model has been updated.

The immediate attribute changes only the broadcast phase. A trace of the two variants, with a listener that logs the current phase and the bean property bound to the executed input:

The Partial Lifecycle

The lifecycle page describes the six phases and how the partial lifecycle visits fewer components. Here is the same request with a trace, using a phase listener that prints the PartialViewContext ids (the review preview, Mojarra 4.1.17; the MyFaces trace has the same phases):

  • Restore View. The view state posted in jakarta.faces.ViewState is used to restore the component tree, and the PartialViewContext reads the execute and render lists from the request. FacesContext.isPostback() is true.

  • Apply Request Values. Only the execute ids and their descendants decode. The behaviour renderer checks jakarta.faces.behavior.event and jakarta.faces.source and queues the AjaxBehaviorEvent. (immediate="true" broadcasts it here.)

  • Process Validations. The same components convert and validate. A failure calls renderResponse() and skips phases 4 and 5.

  • Update Model Values. Only the executed components write their model; SET reviewer=Ann and SET rating=4 are the setters. The fields that were not executed were not touched, which is the point of narrowing execute.

  • Invoke Application. The listener runs here, and the action of an executed command component, and so does navigation.

  • Render Response. The render ids are encoded into update elements. If the lifecycle calls responseComplete() earlier (a redirect, a file download), there is no render phase.

UIViewRoot takes the decision between full and partial processing in its processDecodes, processValidators and processUpdates and encodeChildren: they call PartialViewContext.processPartial when isPartialRequest() is true, for rendering when isAjaxRequest() is true. A custom phase listener or system event listener sees the same phases and the same ids; one trap is that getExecuteIds() and getRenderIds() cannot be read before the view has been restored: calling them in beforePhase of Restore View threw a NullPointerException (root is null) in Mojarra 4.1.17.

resetValues

A component that took part in a request keeps state in the component tree: the local value of an input that converted and validated successfully stays set until the model is updated, and the model is updated only if the whole request is valid. So a second request that re-renders such an input shows the typed value, not the model’s. The resetValues attribute exists for this case. It makes the server call UIViewRoot.resetValues(context, clientIds) on the render ids, which calls EditableValueHolder.resetValue() on each input: the submitted value, the local value and the valid flag are cleared and the model value is shown again.

The test page has a valid year and an invalid copies (range 1 to 10), a Check button that executes both and re-renders them, and two Cancel buttons that execute only themselves and re-render the inputs, one with resetValues="true":

The Request Queue

The specification requires every Ajax request to go through a client-side queue so that requests are sent in the order they were initiated: the oldest waiting request is sent next; when it completes (success or error) it leaves the queue, and the next one is sent. The page below has three buttons whose listener sleeps 400 milliseconds on the server and records which button called it; onevent records when the client saw each stage (times are milliseconds since the first click):

src/main/webapp/queue.xhtml
<h:form id="f">
  <h:commandButton id="a" value="A">
    <f:attribute name="label" value="A"/>
    <f:ajax listener="#{slowBean.work}" render="log" onevent="ev"/>
  </h:commandButton>
  <h:commandButton id="b" value="B">
    <f:attribute name="label" value="B"/>
    <f:ajax listener="#{slowBean.work}" render="log" onevent="ev"/>
  </h:commandButton>
  <h:outputText id="log" value="#{slowBean.log}"/>
</h:form>
<pre id="out"></pre>

  const t0 = Date.now();
  function ev(d) {
    document.getElementById('out').textContent += (Date.now() - t0) + 'ms ' + d.source.id + ' ' + d.status + '\n';

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.faces.event.AjaxBehaviorEvent;
import jakarta.inject.Named;
import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;

@Named
@ApplicationScoped
public class SlowBean {

    private final List<String> log = new CopyOnWriteArrayList<>();

    public void work(AjaxBehaviorEvent event) throws InterruptedException {
        String who = String.valueOf(event.getComponent().getAttributes().get("label"));
        Thread.sleep(400);
        log.add(who);
    }

    public String getLog() { return String.join(",", log); }
}

The begin event of a queued request fires when it leaves the queue and is sent, not when the user clicked, and the three requests ran strictly one after the other, in order, on the server as well. The consequence is useful and dangerous: a double click on a submit button sends two requests (the second after the first finished), so the action runs twice. The queue guarantees order, not idempotence: make the action idempotent, hide or disable the trigger in the begin handler (Events on the Client: onevent and addOnEvent), or use delay.

delay

delay="500" (or {delay: 500} in the JavaScript API) discards a request if another call to faces.ajax.request arrives within that many milliseconds; only the last call is sent. This debounces keystrokes. Three clicks on a button with delay="500" produced one request, whose begin came about 500 ms after the first click:

503ms f:c begin
916ms f:c complete
917ms f:c success       (Mojarra; MyFaces: 507 / 928 / 932)

Source: Jakarta Faces 4.1 VDL: f:ajax

The literal none, or no delay, turns it off. The live search of the first example uses it so that fast typing sends one request per pause rather than one per key.

disabled

disabled="true" (or an expression) keeps the behaviour from being rendered. It is the tag-level switch for "Ajax only in some cases": a component whose f:ajax is disabled is rendered without the handler. A disabled f:ajax inside a group had different effects on the two implementations; see Grouping Components.

faces.ajax.request

faces.ajax.request(source, event, options) sends the request:

  • source is the DOM element that triggers it, or its id. The request is sent from that element’s form (and fails if there is none or if the jakarta.faces.ViewState field is missing).

  • event is the DOM event (optional; its type is sent as jakarta.faces.partial.event).

  • options is an object with execute, render (space-delimited client ids, or the keywords), onevent, onerror (functions), params (an object of extra request parameters), delay and resetValues.

The default execute is @this, the default render is @none. The request is always a POST to the form’s action URL (or to the hidden jakarta.faces.encodedURL field’s value, if present); the header is Faces-Request: partial/ajax; the parameters sent are jakarta.faces.ViewState, jakarta.faces.partial.ajax=true, jakarta.faces.source and, when the view uses the client window, jakarta.faces.ClientWindow; plus the execute and render lists, resetValues, and the extra parameters. The JavaScript documentation adds that a form with enctype="multipart/form-data" is sent through a hidden inline frame instead of XMLHttpRequest with the same parameters, and that the begin, complete and success events are emulated for it (this was not run on this scratch application).

Partial View Traversal

How does the server process only the components in the execute list and write only those in the render list? The specification calls it partial view traversal (section 13.4) and deliberately does not prescribe a strategy: it requires only that UIViewRoot.processDecodes, processValidators and processUpdates call PartialViewContext.processPartial(PhaseId) when the request is a partial one, and that the encoding of an Ajax request goes through the same method. processPartial works on the client ids in getExecuteIds() (for the three execute phases) and getRenderIds() (for Render Response); both collections are filled from the request parameters jakarta.faces.partial.execute and jakarta.faces.partial.render, which faces.js fills with the client ids that the search expressions resolved to (see execute and render). The API for such a walk is UIComponent.visitTree: it takes a VisitContext that carries the ids and a set of VisitHint values, and a callback that is called for every component the visit reaches, which is how a partial phase can run on selected components only. The hints are: VisitHint.EXECUTE_LIFECYCLE says that the visit is part of the execution of a lifecycle phase, SKIP_UNRENDERED visits only the rendered subtrees, SKIP_ITERATION asks components that normally visit their children several times (the iterating ones, such as UIData) to visit them once, and SKIP_TRANSIENT visits only non-transient subtrees. The VisitContext used for a partial request is an implementation class (PartialVisitContext in Mojarra’s com.sun.faces.component.visit and in MyFaces' org.apache.myfaces.component.visit, not part of the API); application code obtains one from VisitContext.createVisitContext(FacesContext, Collection<String> ids, Set<VisitHint> hints) and never names it.

The two shortcuts skip the id-based visit. @all in execute makes isExecuteAll() true and in render makes isRenderAll() true: the first runs the normal full-tree phases and the second renders the whole view, as the update of a single element jakarta.faces.ViewRoot in the response. @none contributes no id, so the visit has nothing to reach; with execute="@none" not even the f:ajax listener ran on Mojarra.

The probe below replays a request’s render ids through the same API an implementation uses. The listener builds a VisitContext from getRenderIds() and visits the view, collecting what a render of those ids would reach:

src/main/java/org/example/bookshelf/web/TraversalBean.java
@Named
@RequestScoped
public class TraversalBean {

    private String found = "";

    public void inspect(AjaxBehaviorEvent event) {
        FacesContext context = FacesContext.getCurrentInstance();
        PartialViewContext pvc = context.getPartialViewContext();
        List<String> visited = new ArrayList<>();
        if (!pvc.getRenderIds().isEmpty()) {
            VisitContext visit = VisitContext.createVisitContext(
                    context, pvc.getRenderIds(), EnumSet.of(VisitHint.SKIP_UNRENDERED));
            context.getViewRoot().visitTree(visit, (ctx, component) -> {
                visited.add(component.getClientId(ctx.getFacesContext()) + ":" + component.getClass().getSimpleName());
                return VisitResult.ACCEPT;
            });
        }
        found = "executeAll=" + pvc.isExecuteAll() + " renderAll=" + pvc.isRenderAll()
                + " execute=" + pvc.getExecuteIds() + " render=" + pvc.getRenderIds() + " visited=" + visited;
    }

    public String getFound() {
        return found;
    }
}

A PartialViewContext for Every Request

To do the same for every Ajax request, decorate the factory: PartialViewContextFactory and PartialViewContextWrapper are the extension points (registered in faces-config.xml). The wrapper below always adds the messages component to the render list, so a page cannot forget it:

src/main/java/org/example/bookshelf/web/MessagesPartialViewContextFactory.java
package org.example.bookshelf.web;

import jakarta.faces.context.FacesContext;
import jakarta.faces.context.PartialViewContext;
import jakarta.faces.context.PartialViewContextFactory;
import jakarta.faces.context.PartialViewContextWrapper;
import jakarta.faces.event.PhaseId;

public class MessagesPartialViewContextFactory extends PartialViewContextFactory {

    public MessagesPartialViewContextFactory(PartialViewContextFactory wrapped) {
        super(wrapped);
    }

    @Override
    public PartialViewContext getPartialViewContext(FacesContext context) {
        return new MessagesPartialViewContext(getWrapped().getPartialViewContext(context));
    }

    static class MessagesPartialViewContext extends PartialViewContextWrapper {

        MessagesPartialViewContext(PartialViewContext wrapped) {
            super(wrapped);
        }

        @Override
        public void processPartial(PhaseId phaseId) {
            if (phaseId == PhaseId.RENDER_RESPONSE && isAjaxRequest() && !isRenderAll()) {
                getRenderIds().add("messages");
            }
            super.processPartial(phaseId);
        }
    }
}

A Behaviour Added in Java

f:ajax is a tag handler around AjaxBehavior. Code can attach the same behaviour, using the id AjaxBehavior.BEHAVIOR_ID and ClientBehaviorHolder.addClientBehavior. A system event listener does it when a component enters the view, and the guard keeps a postback (when the event is published again) from adding it twice:

src/main/java/org/example/bookshelf/web/AjaxAttacher.java
package org.example.bookshelf.web;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.faces.component.UIComponent;
import jakarta.faces.component.behavior.AjaxBehavior;
import jakarta.faces.component.behavior.ClientBehaviorHolder;
import jakarta.faces.context.FacesContext;
import jakarta.faces.event.ComponentSystemEvent;
import jakarta.inject.Named;
import java.util.List;

@Named
@ApplicationScoped
public class AjaxAttacher {

    public void attach(ComponentSystemEvent event) {
        UIComponent component = event.getComponent();
        if (component instanceof ClientBehaviorHolder holder && !holder.getClientBehaviors().containsKey("keyup")) {
            FacesContext context = FacesContext.getCurrentInstance();
            AjaxBehavior ajax = (AjaxBehavior) context.getApplication().createBehavior(AjaxBehavior.BEHAVIOR_ID);
            ajax.setExecute(List.of("@this"));
            ajax.setRender(List.of("echo"));
            ajax.setDelay("200");
            holder.addClientBehavior("keyup", ajax);
        }
    }
}

Ajax Error Handling

Errors reach the page through the error callbacks, and they come in four kinds. The tutorial and the specification list the values of status in the data object:

Status Meaning

httpError

The HTTP status is missing or outside 200 to 299.

serverError

The response contains an error element (an exception on the server).

malformedXML

The response does not follow the format, or an update cannot be applied (the missing element of What Can Be Rendered).

emptyResponse

The server sent nothing.

The data object has everything of the event payload and, in addition, description, errorName and errorMessage. The onerror attribute of f:ajax and the onerror option name a function for one request; faces.ajax.addOnError registers one for all. The lessons, in order of importance:

  • Do not show the server’s message to the user. On MyFaces 4.1.4 the Production stage still put the exception text in the response, and exception text is information about the application’s internals. Show your own text (as the example above does), log on the server, and, if the container’s default is not acceptable, install an Ajax ExceptionHandler (the exception handling page covers ExceptionHandler, ExceptionHandlerFactory and the OmniFaces FullAjaxExceptionHandler that renders an error page for Ajax requests).

  • An expired view is the error you must handle. The session timed out, or the server restarted, and the user clicks. The response is an ordinary 200 with an error element, so the page has to react; the error handler above reloads the page.

  • Development shows an alert. The specification says that in the Development stage the client signals the error with a JavaScript alert; Mojarra did, MyFaces 4.1.4 did not. In Production there is no alert on either: register an onerror handler, or the user sees nothing.

Security Notes

An Ajax request is a postback; the protections of postbacks apply and must not be bypassed for convenience.

  • The view state in jakarta.faces.ViewState is sent with every request, and its check on the server is what keeps a forged request from another site from being processed. Do not disable view state or CSRF protection to make an Ajax call work. The Faces-Request header is no protection by itself: the API documentation defines isAjaxRequest() through that header, so a script that sets it passes, but only with a valid view state of the user’s session (a bogus one failed with an error element).

  • A request executes only the components named in execute, and the server decodes only those. The hidden effect is useful: a forged value for an input that was not executed is ignored. A forged value for an input that was executed is converted and validated like any other.

  • Render only what you mean to. Everything in a render list is sent to the browser. Do not render components that contain data the user must not see just because they are in the same panel.

  • Scripts built for getEvalScripts(), for onevent handlers and for h:commandScript parameters must not concatenate user input. The values in params are request parameters and arrive as strings; validate them like any request parameter.

  • Output of user-supplied text through h:outputText is escaped in updates exactly as in full pages. escape="false" on such content is cross-site scripting in Ajax updates too.

  • Business logic belongs in beans and services, not in the JavaScript that calls them: authorize in the server method.

Source: Jakarta Faces 4.1 specification, 13. Ajax Integration and Jakarta Faces 4.1 API: PartialViewContext

Mojarra and MyFaces

Same on both: the request format (Faces-Request, partial.execute, partial.render, behavior.event, source, ViewState), the partial lifecycle and phase order, the immediate behaviour, delay, the queue, resetValues, PartialViewContext and its factory, the events (begin, complete, success) and the payload keys of an ordinary event, h:commandScript calls with parameters, programmatic AjaxBehavior, the redirect and @all responses. Differences found in the scratch application:

  • Request body: Mojarra posts only the executed controls; MyFaces posts the whole form and the hidden formId_SUBMIT.

  • Order of the executed ids: source first on Mojarra, source last on MyFaces.

  • Raw requests (for example with curl): Mojarra ignores the source button unless it is in partial.execute; MyFaces invokes it anyway. The keyword @form sent in a raw request is not expanded by either of them.

  • Default DOM event of checkboxes and radios: onclick on Mojarra, onchange on MyFaces (The event Attribute and the Default Events).

  • A listener without parameters: works on Mojarra, MethodNotFoundException on MyFaces.

  • A render target with rendered="false": Mojarra answers malformedXML and stops applying updates; MyFaces skips it.

  • Nesting f:ajax in a group: one handler versus two for the same event, and the effect of a nested disabled (Grouping Components).

  • An AjaxBehavior added in Java: faces.js is added by MyFaces and not by Mojarra (Getting faces.js onto the Page).

  • h:commandScript: underscore escaping in the name on MyFaces; isTrusted=true with autorun on Mojarra; namespace reservation on MyFaces.

  • Errors: wrapped exception names, the Production message, the status of a server error, the development alert, and the error for an invalid view state (Ajax Error Handling).

  • Response shape: the id on partial-response (MyFaces), the position of eval, the view state element id and value format.

  • getExecuteIds() before the view is restored: a NullPointerException on Mojarra 4.1.17 (the MyFaces behaviour was not run).

  • The specversion and implversion values of faces.js are implementation-defined (Mojarra 40100 and 17, MyFaces 400000 and 0 in the test); do not branch on them.

Where the Books Are Outdated

The books of the section’s bibliography that cover Ajax are of two generations. Burns and Schalk, and Leonard, describe Faces 2.0, where Ajax first became part of the specification; Jacobi and Fallows predate it.

  • Hand-written Ajax. Jacobi and Fallows build Ajax into components with their own XMLHttpRequest code, script resources and response formats, and Leonard shows ajax4jsf and Dynamic Faces. All of it is replaced by f:ajax, the standard queue, the standard partial response and ResourceHandler (Faces 2.0). The lasting idea is the one they teach: components that update parts of a page by asking the server for markup. The code to write today is none.

  • Old names. Burns and Schalk show the script jsf.js in the library javax.faces and the request parameters javax.faces.partial.*, and Leonard calls jsf.ajax.request. Today they are faces.js, faces.ajax.request, the library jakarta.faces and jakarta.faces.partial.*. Copying such examples fails twice: the script is missing (404 for jsf.js on both implementations) and the names no longer exist.

  • Newer features are missing. The books are older than delay and resetValues (2.2), h:commandScript, PartialViewContext.getEvalScripts(), search expressions (@next, @parent, @id(...)) and f:websocket (2.3), so none of them appears; delay, Queueing and disabled, resetValues, h:commandScript and Ajax from Java: PartialViewContext and AjaxBehavior cover them.

  • Libraries. ajax4jsf, Dynamic Faces and RichFaces have ended. PrimeFaces p:ajax and OmniFaces cover what they added; the pages on PrimeFaces Ajax and on OmniFaces describe them, and the RequestContext of the PrimeFaces books is PrimeFaces.current() today.

Common Mistakes

  • The message never appears. The h:messages or h:message is not in render. Add it, or use a PartialViewContext decoration for the whole application (A PartialViewContext for Every Request).

  • The model does not change. The input is not in execute. @this is the default and it executes only the trigger.

  • The action works in curl and not in the browser, or the reverse. A raw request must contain the source in partial.execute; copy the request from the browser’s network tab or from a request filter.

  • The target does not update. The element is absent from the page (rendered="false", a row that does not exist). Render a wrapper that is always present.

  • A script in the head says faces is not defined. List faces.js first with h:outputScript, put the script in a resource after it, or in the body.

  • A value reappears after a failed validation. The local value of a valid sibling stayed in the component tree; use resetValues="true" and list the inputs.

  • The listener should run for invalid input and does not. Validation failure skips Invoke Application. Do not use immediate to get around it; read the lifecycle page.

  • A double click runs the action twice. The queue serialises requests, it does not drop them. Make the action idempotent, or hide the trigger while the request is pending.

  • A listener works on one implementation only. A listener without the AjaxBehaviorEvent parameter fails on MyFaces.

  • A nested f:ajax sends two requests. A second f:ajax for the same event inside a group stacks on MyFaces 4.1.4.

  • escape="false" on rendered user text. It writes the text into the DOM unescaped.

  • Error handling shows the server’s text. Show a fixed message; log the rest. MyFaces 4.1.4 puts the full exception text in the response even in Production.

  • The page expires and nothing happens. Handle ViewExpiredException in addOnError and reload.

  • f:ajax on a non-existing event name. The 500 appears when the view is built. Names are keyup, change, click, action, valueChange; not onkeyup.
