JSF (JavaServer Faces)

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This section is written against Jakarta Faces 4.1 (Jakarta EE 11, API artifact jakarta.faces-api 4.1.2, Java SE 17 or later) and its two implementations, Eclipse Mojarra 4.1.17 and Apache MyFaces Core 4.1.4, with Java 21 for the examples. Where a library or runtime is used, the pages target PrimeFaces 16.0.0, PrimeFaces Extensions 16.0.0, OmniFaces 5.5.5, Apache Tomcat 11.0.26 with Weld 6.0.4, WildFly 41.0.1, GlassFish 8.0.5, Payara 7.2026.9, Open Liberty 26.0.0.10, Apache TomEE 10.2.0, JoinFaces 6.1.1 on Spring Boot 4.1.1 and myfaces-quarkus 4.1.4. All versions were verified on 2026-10-08 against Maven Central and the project sites. Jakarta Faces 4.0 (Jakarta EE 10) is still widely deployed, so the pages say where it behaves differently. Jakarta Faces 5.0 (Jakarta EE 12) is under development; its latest API milestone is 5.0.0-M9 (2026-09-18), and the pages describe it as upcoming, never as current behaviour. Versions & Implementations has the full version matrix.

What Jakarta Faces is

Jakarta Faces, called JavaServer Faces (JSF) in the Java EE era and Jakarta Server Faces in its first Jakarta EE releases (2.3 and 3.0), is the component-based, server-side MVC web framework of Jakarta EE. Instead of writing request handlers that return HTML, you declare a page as a tree of UI components, and the framework keeps that tree on the server between requests:

  • Facelets XHTML views declare the page. At run time they build a server-side component tree of inputs, outputs, tables and buttons, each with a renderer that writes its HTML.

  • A six-phase request processing lifecycle restores the tree on a postback, decodes the submitted values, converts and validates them, copies them into CDI backing beans through the Expression Language, calls the action method and renders the response.

  • On top of that the framework provides navigation, Ajax with partial rendering, view, flow and client-window scopes, state saving, resource handling, composite components, templating, internationalization and WebSocket push.

  • A rich ecosystem sits on top of the standard: PrimeFaces (more than a hundred components and themes), PrimeFaces Extensions, OmniFaces (utilities that fill gaps in the standard) and smaller libraries.

Faces runs on any Jakarta EE Web Profile server (GlassFish, WildFly, Payara, Open Liberty, TomEE), on a plain servlet container with a CDI implementation (Tomcat or Jetty with Weld), inside Spring Boot through JoinFaces and on Quarkus through the MyFaces extension. Its closest relative outside Java is ASP.NET Web Forms, which shares the component tree, the postback and the view state.

This section is for developers who:

  • maintain or extend an existing JSF or Jakarta Faces application, often one written for JSF 2.x with javax.*, JSP or @ManagedBean, and need the current idioms and a migration path

  • build component-rich internal or back-office applications on a Jakarta EE estate and want PrimeFaces or OmniFaces used well

  • learned JSF from the classic books (2004 to 2015) and need to know what still holds and what has been removed

  • are choosing between Faces, Vaadin, Thymeleaf with Spring MVC or a single-page application, and want the trade-offs

  4. Events, navigation, beans and scopes: listeners, outcomes and redirects, bookmarkable pages, CDI beans, scopes, the flash and Faces Flows.

  5. Ajax, push and components: f:ajax, search expressions, WebSocket push, composite and custom components, tag files and client behaviours.

  6. Resources, configuration, advanced topics and security: resources and contracts, context parameters and project stages, state saving, exceptions, extension points, multiple windows, performance and security.

Running example

Every example builds one small original application, Bookshelf, in the same domain as the Django, Python FastAPI, NestJS and Thymeleaf sections, so the stacks can be compared page by page. Here it is a Maven WAR with packages org.example.bookshelf.model, service and web, and it grows page by page into:

  • a public catalogue of books and authors with Facelets templates, search, sorting and a lazy-loaded data table

  • book details reached by bookmarkable URLs with f:viewParam and f:viewAction

  • a review form with converters, validators and Bean Validation, submitted with Ajax

  • a multi-step "borrow request" wizard implemented as a Faces Flow

  • cover-image uploads with h:inputFile

  • English and Spanish message bundles with a locale switcher

  • a "new review" live feed with f:websocket and @Push

  • a reusable "star rating" composite component and a small custom component

  • form-based login with Jakarta Security and role-based views

  • a PrimeFaces variant of the catalogue (data table, dialog framework, export) and OmniFaces utilities

  • the same WAR running on WildFly or GlassFish, on Tomcat with Weld, on Spring Boot through JoinFaces and on Quarkus

The eight books below were consulted for concept coverage, narrative and structure only.
