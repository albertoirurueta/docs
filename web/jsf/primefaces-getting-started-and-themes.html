PrimeFaces: Getting Started, Configuration and Themes

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against PrimeFaces 16.0.0 (published 2026-09-04; 15.0.18 is the previous line), Jakarta Faces 4.1 (API jakarta.faces-api 4.1.2), Eclipse Mojarra 4.1.17 and Apache MyFaces Core 4.1.4, with Java 17 or later for the application. PrimeFaces itself needs only a Java 11 runtime (its class files are version 55, checked in the 16.0.0 jar) and a Faces 4.0 or newer implementation: version 16 removed the last javax.* support. Faces 4.0 behaves like 4.1 for everything on this page. The versions were checked on 2026-10-08.

Everything marked as observed was run in a scratch Bookshelf WAR on Apache Tomcat 11.0.26 (embedded) with Weld 6.0.4.Final, once with Mojarra 4.1.17 and once with MyFaces 4.1.4; the hello-world page and the theme switch were also run on Mojarra 4.0.26. Computed styles, fonts and widths were read with headless Chrome 155. Servers other than Tomcat (WildFly, GlassFish, Payara, Open Liberty, TomEE) were not run for this page. Statements that rest only on the PrimeFaces documentation or on the 16.0.0 source are said so. Data tables, Ajax and forms, dialogs, file upload and charts have their own pages in this section; here they appear only where a setting of this page changes them.

What PrimeFaces Adds to Faces

PrimeFaces is a component library for Faces: tags in the p: namespace (176 tags in the 16.0.0 tag library, from p:accordionPanel to p:wizard), a theme system, a JavaScript layer built on jQuery that every component talks to, and a set of replacements for parts of the standard machinery. What the 16.0.0 jar registers on its own (read from its META-INF/faces-config.xml and web-fragment.xml) is the reason a page with no explicit setup already behaves differently:

Registration Effect

Renderers for jakarta.faces.Head and jakarta.faces.Body

h:head and h:body are rendered by PrimeFaces: they inject the theme, the icon font, the component styles and scripts, the locale script and the client settings (The Head: What PrimeFaces Writes and in Which Order). A page without h:head receives none of it.

PrimeResourceHandler (resource handler)

Wraps resource handling: PrimeFaces resource URLs carry the parameter v=16.0.0 (observed on the ln=primefaces URLs and absent on the application’s own ln=css URLs; The Context Parameters, HIDE_RESOURCE_VERSION), and the streamed content of components such as p:graphicImage is served through it.

PrimeFacesContextFactory, PrimePartialViewContextFactory

PrimeFaces’s own faces-context and partial-view-context factories, installed through the standard <factory> elements.

Phase listeners AutoUpdatePhaseListener, CspPhaseListener, DialogKeepFlashPhaseListener

Named after p:autoUpdate, the Content Security Policy support and the flash handling of the dialog framework.

Validators for the ids jakarta.faces.Length, jakarta.faces.LongRange, jakarta.faces.DoubleRange, jakarta.faces.RegularExpression, and twenty converters

Classes in org.primefaces.validate and org.primefaces.convert registered under the standard ids, so once the jar is on the class path every f:validateLength or standard converter of the application is served by a PrimeFaces class. Client-side validation is on the the PrimeFaces Ajax, forms and validation page of this section.

PrimeServletContextListener, UploadedFileCleanerListener, <distributable/>, font MIME mappings (ttf, woff, woff2, eot, svg)

Declared in the jar’s web-fragment.xml, so a servlet container needs no web.xml entry for them.

Source: PrimeFaces 16 documentation: Dependencies and PrimeFaces 16.0.0 source: HeadRenderer

The PrimeFaces jar also contains a beans.xml with bean-discovery-mode="all", so a CDI container scans it. On a servlet container that has no Bean Validation or Jakarta Persistence API on the class path, Weld 6.0.4 logged 36 WELD-000119 lines at INFO level ("Not generating any bean definitions from org.primefaces... because of underlying class loading error: Type jakarta.validation... not found"). The application worked; the lines only mean that the optional PrimeFaces features that need those APIs are off (The Dependency and the Optional Libraries).

The Head: What PrimeFaces Writes and in Which Order

The h:head of a PrimeFaces application is rendered by org.primefaces.renderkit.HeadRenderer, which replaces the standard renderer of the type jakarta.faces.Head. Its class comment states the intended order: the first facet, the theme style sheet, the PrimeIcons style sheet, the middle facet, the registered resources, the client validation scripts, the locale script, the PrimeFaces.settings script, the initialisation scripts, the content of the h:head element and the last facet. The three facets are PrimeFaces additions to h:head; the standard element knows no facets.

Reading the response shows how that works in practice, because it differs in one detail from the comment. In the output the theme and the icon style sheet come with the registered resources and not before the middle facet, so markup in the middle facet arrives before theme.css. The probe page puts one plain link and one h:outputStylesheet into each facet and into the head:

order-css.xhtml — a probe for the order of style sheets
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:f="jakarta.faces.core"
      xmlns:h="jakarta.faces.html"
      xmlns:p="primefaces">
<h:head>
  <f:facet name="first">
    <link rel="stylesheet" href="#{resource['css:link-first.css']}"/>
    <h:outputStylesheet library="css" name="res-first.css"/>
  </f:facet>
  <title>Resource order</title>
  <h:outputStylesheet library="css" name="res-body.css"/>
  <link rel="stylesheet" href="#{resource['css:link-body.css']}"/>
  <f:facet name="middle">

What follows from it:

  • A plain element in the first, middle or last facet or directly in h:head is written where the order above puts it. An h:outputStylesheet is a resource component: wherever it is written (in a facet too) it joins the list of registered resources and is written there. A facet therefore does not move a resource component. On Mojarra the four resource components arrived in the order body, last, first, middle; on MyFaces in the order they were declared. The probe page differs only by that. Do not rely on the relative order of resources declared in different facets.

  • The application’s h:outputStylesheet resources arrived before components.css (the likely reason is that the PrimeFaces component that pulls components.css in sits in the body and is processed after the head; the order itself was observed). At equal specificity components.css and the theme therefore win over a style sheet declared with h:outputStylesheet.

  • The plain link elements in h:head or in the last facet arrived after the PrimeFaces style sheets and the scripts, so their rules win. The expression #{resource['css:link-last.css']} (library css, name link-last.css) produces the right URL for a resource library; see resource identifiers.

  • h:outputScript is different. In a separate run (both implementations) a script written in the first facet was written in that facet, ahead of theme.css, and scripts written in h:head and in the last facet came after the PrimeFaces scripts, in the places of the plain elements.

The selector has two classes, so it beats the theme’s .ui-button rule whatever the order of the files. In headless Chrome the button computed to rgb(111, 66, 193), the accent colour, and not to the Saga Blue rgb(33, 150, 243).

A page without h:head gets nothing. The renderers are attached to the standard tags. A page that uses the plain HTML elements <head> and <body> rendered the PrimeFaces component markup but no link and no script of PrimeFaces on Mojarra and on MyFaces: no theme, no icons, no widgets. Use h:head and h:body in every template and view that holds PrimeFaces components. Faces keeps one renderer per type, so a second library that registers its own jakarta.faces.Head renderer would replace the PrimeFaces one; that case was not tested, so check such a combination in a test.

Moving the scripts to the end of the body. primefaces.MOVE_SCRIPTS_TO_BOTTOM set to true removed every script element from the head and wrote all of them, the PrimeFaces resources, the settings script and the initialisation scripts included, at the end of the body (observed on the hello page: six script elements in the head and two inline widget scripts in the body without the parameter; none in the head and six at the end of the body with it, five resource scripts and one inline script; both widgets of the page were created in all three modes). The value defer additionally gave each resource script a defer="defer" attribute and merged the initialisation scripts into one DOMContentLoaded handler that removes its own element. The page paints before the scripts run, which is the performance advantage the PrimeFaces performance page names (see the PrimeFaces part of the performance page). Test inline scripts of your own that call PrimeFaces or jQuery, because they now run before the library is loaded.

Where the Setup Sits in the Request Processing Lifecycle

The setup features of this page touch the lifecycle (the six phases) in few places, and knowing which ones explains the theme behaviour above:

Moment What happens

Application start

The context parameters are read; PostConstructApplicationEvent and PreDestroyApplicationEvent listeners of the jar (PostConstructApplicationEventListener, PreDestroyApplicationEventListener) are registered in its faces-config.xml. A changed parameter needs a restart: every test of this page restarted the application after changing one. Only the expression in primefaces.THEME is evaluated again on each request.

Restore View to Process Validations

Nothing of this page. A theme chooser is an ordinary input: the value is converted and validated like any other (a posted theme that is not in the menu stopped here with a validation error).

Update Model Values

PrimeThemeBean.setName runs, so the new theme is already in the bean when the next phase starts.

Invoke Application

PrimeThemeBean.apply runs and returns the outcome with faces-redirect=true; the lifecycle ends with a redirect and no Render Response.

Render Response

Everything else. HeadRenderer.encodeBegin evaluates primefaces.THEME and writes the head resources, the locale script and the settings (the settings gain projectStage:'Development' when the project stage is not Production, observed for Development); encodeEnd writes the last facet. The three phase listeners that PrimeFaces registers (AutoUpdatePhaseListener, CspPhaseListener, DialogKeepFlashPhaseListener) are all registered for the Render Response phase (source).

Source: PrimeFaces 16.0.0 source: HeadRenderer and Jakarta Faces 4.1 specification, 2.2 Standard Request Processing Lifecycle Phases

The Context Parameters

PrimeFaces needs no configuration ("configuration by exception"). Everything that can be configured is a context-param in web.xml named primefaces.NAME. Themes

A PrimeFaces theme is a resource library named primefaces-<name> that holds one file, theme.css. HeadRenderer takes the value of primefaces.THEME (default saga-blue), evaluates it as a value expression, and writes a link to theme.css in the library primefaces- plus that value. The theme is a style sheet for the ui-* classes that components.css and the renderers use, and it defines the colours, the fonts and the CSS custom properties (--surface-a, --primary-color, --text-color and others) of the page.

A theme per user

Because HeadRenderer evaluates the parameter as an expression on every request, the theme can come from a bean. The Bookshelf keeps the choice in a session-scoped bean (a user preference, not page state) and persists nothing else; a real application would store it in the user’s profile or in a preference cookie (cookie attributes).

PrimeThemeBean.java
package org.example.bookshelf.web;

import jakarta.enterprise.context.SessionScoped;
import jakarta.faces.context.FacesContext;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.List;
import java.util.Set;

/** Holds the PrimeFaces theme chosen by the current user. */
@Named
@SessionScoped
public class PrimeThemeBean implements Serializable {

    private static final Set<String> ALLOWED = Set.of("saga-blue", "vela-blue", "arya-blue", "luna-green");

    private String name = "saga-blue";

    public List<String> getChoices() {
        return ALLOWED.stream().sorted().toList();
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        if (ALLOWED.contains(name)) {
            this.name = name;
        }
    }

    /** Redirects to the current view so that the next response is built with the new theme only. */
    public String apply() {
        String viewId = FacesContext.getCurrentInstance().getViewRoot().getViewId();
        return viewId + "?faces-redirect=true";
    }
}

Responsive Layout: ui-fluid, Grid CSS, PrimeFlex and panelGrid

The PrimeFaces documentation names three ingredients of a responsive page: the page layout (menu, header, content, footer, which is plain HTML and CSS of the application), a grid framework that places the content, and components that adapt to their container. PrimeFaces gives the last two a vocabulary.

Fluid components

Form components have a fixed width by default. Putting them in a container with the class ui-fluid makes them take the full width of the container, which is what a grid cell needs (p:selectOneMenu has autoWidth, whose default auto since 13.0.0 notices a parent ui-fluid and skips its own width calculation). Complex components such as p:dialog, charts, the carousel and the pick list have a responsive attribute that makes them react to the screen size (documentation, not run). Touch features (swipe on the tab view, long press for the context menu) are on by default and primefaces.TOUCHABLE switches them off globally.

Security Settings of the Setup

The setup decisions of this page have security consequences that the later PrimeFaces pages build on:

  • Content Security Policy. primefaces.CSP switches PrimeFaces to nonce-stamped scripts and registered handlers instead of inline code. The security page ran it (p:commandButton worked on Mojarra and MyFaces) and explains the limitations (Content Security Policy). Moving the scripts to the bottom (The Head: What PrimeFaces Writes and in Which Order) does not replace it.

  • Rich text is untrusted markup. p:textEditor refuses to render without the OWASP sanitizer unless secure="false" is set (The Dependency and the Optional Libraries). Leave secure at its default for anything another user will read. The component documentation states the sanitizer is there "to prevent XSS".

  • The theme name is a resource name. A theme taken from a request parameter, a cookie or a profile reaches HeadRenderer as a library name. Validate it against a fixed list as PrimeThemeBean does (A theme per user) and store only the name.

  • Version disclosure. v=16.0.0 in every PrimeFaces URL tells an attacker the exact library version. HIDE_RESOURCE_VERSION removes it (The Context Parameters); keep the library patched either way.

  • Cookies. COOKIES_SAME_SITE (Strict by default) covers the cookies PrimeFaces' JavaScript writes. The session cookie and the cookies of the Faces implementation have their own settings, described on the security page.

  • Keys and credentials. PUBLIC_CAPTCHA_KEY and PRIVATE_CAPTCHA_KEY are context-param values in the documentation’s examples. The private key is a secret: keep it out of the repository and of web.xml in version control, and give it to the server through its own deployment configuration. This page has no example key on purpose.

  • Uploads. p:fileUpload has limits and validators of its own; the upload and download page sets the posture (size limits, content sniffing, file name sanitising) that the PrimeFaces files page reuses (upload limits, validating the content).

  • View state. Components are ordinary Faces components, so the rule of the security page applies: view state protects against cross-site request forgery only with server-side state saving (cross-site request forgery).

Where the Books Are Outdated

PrimeFaces Cookbook, Second Edition (Çalışkan and Varaksin, Packt, 2015; PrimeFaces 5.1 and 5.2 on JSF 2.2) is the book behind this page: its first chapters cover setup, internationalisation and resource ordering, theming, icons, and panels and layouts. Its approach to organising a PrimeFaces application is still sound; the details are not.

  • The platform. The book is written for javax.faces on JSF 2.2; PrimeFaces 14.0.0 removed Faces 2.x support and 16.0.0 removed javax.* altogether. Every namespace, import and server setup needs the Jakarta Faces 4.0 or later form. The p: namespace http://primefaces.org/ui still works and primefaces is the short form.

  • Resource files. The 5.x scripts were collected in primefaces.js; since 6.0 they are core.js and components.js (plus jQuery), and in 16 the head renderer includes them, not an explicit tag or include. Nothing has to be added by hand; a custom @ResourceDependency that names primefaces.js has to change.

  • Themes. The book teaches ThemeRoller-style themes, the theme switcher component and Maven artifacts for extra themes. In PrimeFaces 16 ThemeRoller themes do not render (15.0.0), p:themeSwitcher does not exist (11.0.0), and the extra themes are Saga, Vela, Arya, Aura, Bootstrap, Material, Luna and Nova in the single primefaces-themes jar. The setting is still primefaces.THEME, but the names are different. Custom themes are built from SCSS or extended with CSS, as in A custom theme.

  • Icons. Font Awesome came with the jar in the book’s era; it was removed in 11.0.0. PrimeIcons (pi pi-*) is the default and Font Awesome is added as a WebJar with the -jsf style sheet (Icons: PrimeIcons and Font Awesome).

  • Grid CSS. The book’s layout recipes use the Grid CSS of its day (ui-grid, ui-grid-row, ui-grid-col-N). The classes still ship in 16.0.0, but Grid CSS was deprecated in 10.0.0 in favour of PrimeFlex, which is a separate WebJar with its own class names (grid, col-12 md:col-6), and p:panelGrid has the flex layout for it (Responsive Layout: ui-fluid, Grid CSS, PrimeFlex and panelGrid).

  • Resource ordering. The book’s advice on the order of style sheets and scripts rests on the head rendering of PrimeFaces 5. The facets first, middle and last of h:head still exist, but they order plain markup, not h:outputStylesheet components, and the order differs between Mojarra and MyFaces for the latter (The Head: What PrimeFaces Writes and in Which Order).

  • Internationalisation. The mechanism (bundles for the components, client-side locale scripts) is the same idea, but client-side localisation is on by default since 14.0.0 and the languages and keys are different (Localisation).

Other books touch this page too. Learning PrimeFaces Extensions Development (Jonna, 2014) sets up a PrimeFaces Extensions 1.2.1 project against PrimeFaces 4.0; the PrimeFaces Extensions page of this section covers the present setup. JSF 2.0 Cookbook (Leonard, 2010) was written for PrimeFaces 2.0 alongside RichFaces and Tomahawk; nothing of its PrimeFaces setup applies. None of the book content is reproduced here.

Common Mistakes

  • Plain <head> and <body> in a template. No theme, no icons, no widgets; the components are rendered as bare markup (The Head: What PrimeFaces Writes and in Which Order). Use h:head and h:body.

  • A typo in primefaces.THEME, or a theme name from primefaces-themes without the jar. An unstyled page and, on Mojarra, a RES_NOT_FOUND link; there is no error. Check the link in the page source after changing the theme (Choosing a theme).

  • Re-rendering the view after the user changes the theme. The old theme link is written as well, and it wins. Redirect to a fresh view (A theme per user).

  • Putting a user-chosen string into primefaces.THEME. It becomes a library name. Allow a fixed list.

  • Overriding PrimeFaces CSS with an h:outputStylesheet. It arrives before components.css. Use a plain link with #{resource[...]} in the last facet and select with more specificity than the theme (The Head: What PrimeFaces Writes and in Which Order).

  • Depending on facets to order h:outputStylesheet components. Facets order plain markup only, and the two implementations disagree about resource components (The Head: What PrimeFaces Writes and in Which Order).

  • Hello world without the sanitizer. The official p:textEditor page answers HTTP 500 until owasp-java-html-sanitizer is on the class path; the cure is the dependency, not secure="false".

  • Font Awesome with the plain style sheet, or with the WebJar 7.3.0. The icons render as empty boxes because the font is not found. Use the *-jsf.css file and check that the version you choose still has it (Icons: PrimeIcons and Font Awesome).

  • Trusting the documentation’s configuration table for CLIENT_SIDE_LOCALISATION. The table says false; the default is true (The Context Parameters).

  • Relying on saga, arya and vela short names. They still work in 16.0.0 but were announced for removal; use the -blue names.

  • Mixing PrimeFlex and Grid CSS in one form without meaning to. p:panelGrid defaults to Grid CSS even when primefaces.FLEX is true; the attribute layout="flex" and the PrimeFlex style sheet go together.

  • Reading PrimeFaces.settings as if it were configuration. It is generated on every page from the context parameters; change web.xml.

  • A WELD-000119 flood taken for a failure. The INFO lines on a servlet container without Bean Validation or Persistence (What PrimeFaces Adds to Faces) mean that optional features are off.

  • Different PrimeFaces and primefaces-themes versions. They are released together; keep the same number in the POM.

  • Hard-coded keys. No captcha key, API key or private value in web.xml, a bean or a page (Security Settings of the Setup).
