Migrating to Jakarta Faces

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Much of the Faces code in production was written for JSF 2.x on Java EE 7 or 8, and some of it for JSF 1.x with JSP views. None of it compiles or even starts on a Jakarta EE 10 or 11 runtime without changes, and some of the changes do not fail at all: they are silently ignored and the application misbehaves. This page is the field guide for that move. It follows one small application, the Bookshelf catalogue written the way a JSF 2.3 project of 2018 would write it, through every change needed to run it on Jakarta Faces 4.1, and it records what each tool does and what it leaves for you.

The page is written against Jakarta Faces 4.1 (API jakarta.faces-api 4.1.2, Jakarta EE 11, Java 17 or later), Eclipse Mojarra 4.1.17 and Apache MyFaces Core 4.1.4, with PrimeFaces 16.0.0 and OmniFaces 5.5.5 where libraries are involved. Faces 4.0 (Jakarta EE 10, Java 11 or later) is named where it differs. Faces 5.0 (Jakarta EE 12) is still a milestone (5.0.0-M9 is the latest on 2026-10-08), so everything said about it is "upcoming". Every experiment was run on 2026-10-08: the application was built with Maven 3.9.16 for Java 21 (maven.compiler.release 21), deployed to an embedded Apache Tomcat 11.0.26 with Weld 6.0.4.Final on JDK 26, and queried with curl and a small script that posts Ajax requests. Every runtime test was repeated on Mojarra and on MyFaces. A claim that was not run is labelled "documented" or "not run".

Two other pages hold the pieces this page does not repeat. The Versions and Implementations page has the version matrix, the Java baselines and the per-release feature lists, and the Backing Beans and CDI page explains the CDI model that replaces managed beans in detail. This page is about the move: the order of the steps, the tools, the symptoms of each missed step, and the replacements.

The Route: Which Releases to Cross

A Faces application does not jump between "JSF" and "Jakarta Faces". It crosses up to four releases, each of which broke something different. The list below is the order in which the breaks happened, and it is also the order in which a careful migration removes them.

Table 1. What each release broke, and the minimum Java it needs
Faces release Platform Java SE What breaks when you cross it

2.3

Java EE 8

8

Nothing. It is the best place to start: Facelets, CDI and javax still work together, and @ManagedBean is deprecated but present.

3.0

Jakarta EE 9 (9.1 for Java 11)

8

Everything named javax.faces, javax.servlet, javax.el, javax.enterprise, javax.inject becomes jakarta.*. No other change: the specification says only that the namespace changed and that this is a breaking change.

4.0

Jakarta EE 10

11

JSP support, @ManagedBean and the javax.faces.bean scopes, MethodBinding, ValueBinding and the jakarta.faces.el package, the CURRENT_COMPONENT constants, the deprecated StateManager methods and ResourceResolver are removed. The XML namespaces move to the jakarta.faces.* URNs, and jsf.js becomes faces.js.

4.1

Jakarta EE 11

17

Nothing is removed that Faces 4.0 still had. More API is deprecated for removal (full state saving, ActionSource2, the custom-scope events, cc:extension) and the UIComponent.bindings field is gone. Java 17 is required.

5.0 (upcoming)

Jakarta EE 12 (planned)

21

Planned: removal of everything deprecated for removal since 4.0, of the old namespaces, and API modernisation. Not released.

Source: Faces 4.1 specification, B.3: Changes between 3.0 and 2.3, B.2: Changes between 4.0 and 3.0 and B.1: Changes between 4.1 and 4.0

The practical consequence is a staged route. Stage 1 is done while everything is still javax, because it needs no rename and can be tested on the platform you already run. Stages 2 to 4 are mechanical or nearly so, and the fewer problems you carry into each stage, the easier it is to tell a rename error from a design problem.

The stages are advice, not a rule of the platform. The code can jump from 2.3 straight to 4.1 in one commit, and the Bookshelf below does exactly that in its later sections. The staging is about where you get feedback: stage 1 can be verified on the old server, and each later stage fails in a recognisable way (see What Happens If You Only Upgrade the Runtime).

The Legacy Bookshelf

The application to migrate is the Bookshelf catalogue as a JSF 2.3 project would have built it: a WAR for Java EE 8, javax everywhere, two library dependencies, a managed bean with an injected service, an old-style variable resolver, a phase listener, an Ajax button written with the old script name, a JSP page next to the Facelets pages, and the old namespaces. It compiles against javax:javaee-web-api:8.0.1 and builds a WAR; no Java EE 8 server was used in these experiments, because the subject is the move, not the old runtime. It is deliberately dense in legacy idioms, one of each kind this page treats, so that every step has something to change. The bean filters inside its getter, so the filter runs every time the table asks for its value. That is one of the habits of the period that the section’s best practices reject, and the migration removes it in Managed Beans to CDI. The old expression API and the old resolver live in two small classes:

QueryReader.java and LegacyVariableResolver.java (legacy)
package org.example.bookshelf.web;

import javax.faces.context.FacesContext;
import javax.faces.el.MethodBinding;
import javax.faces.el.ValueBinding;

/** Uses the Faces 1.x expression API that Faces 4.0 removed. */
public class QueryReader {

    public static String currentQuery() {
        FacesContext ctx = FacesContext.getCurrentInstance();
        ValueBinding vb = ctx.getApplication().createValueBinding("#{catalogue.query}");
        return (String) vb.getValue(ctx);
    }

    public static void runSearch() {
        FacesContext ctx = FacesContext.getCurrentInstance();
        MethodBinding mb = ctx.getApplication().createMethodBinding("#{catalogue.search}", new Class<?>[0]);
        mb.invoke(ctx, new Object[0]);
    }
}
package org.example.bookshelf.web;

import javax.faces.context.FacesContext;
import javax.faces.el.EvaluationException;
import javax.faces.el.VariableResolver;

/** A Faces 1.1 style resolver; Faces 1.2 deprecated it and Faces 4.0 removed it. */
public class LegacyVariableResolver extends VariableResolver {

    private final VariableResolver parent;

    public LegacyVariableResolver(VariableResolver parent) {
        this.parent = parent;
    }

    @Override
    public Object resolveVariable(FacesContext context, String name) throws EvaluationException {
        if ("appName".equals(name)) {
            return "Bookshelf";
        }
        return parent.resolveVariable(context, name);
    }
}

javax to jakarta (Faces 3.0, Jakarta EE 9)

The first and widest change is the one the specification states in a single sentence: the namespace changed from javax.faces to jakarta.faces, and that is a breaking change. Jakarta EE 9 applied the same rename to every Jakarta EE API, so the change reaches far beyond Faces: Servlet, Expression Language, CDI, Bean Validation, Persistence and the rest of the platform moved with it. Jakarta EE 9 was only the rename, with no new behaviour (the BalusC article on Faces 4.0 describes Faces 3.0 as the same specification and implementation as 2.3 with javax replaced by jakarta), which is why a Faces 3.0 application is the safest intermediate stop.

Two Java rules decide whether a global search-and-replace is safe. The first is that not every javax package moved: the packages that Java SE itself provides (javax.naming, javax.sql, javax.crypto, javax.net, javax.security.auth, javax.xml.parsers, javax.annotation.processing) keep their names. A blanket s/javax/jakarta/ breaks the build in exactly those places. The second is that the rename does not tell you whether the target exists: javax.faces.bean and javax.faces.el become jakarta.faces.bean and jakarta.faces.el, names that Faces 4.0 removed (Removed and Deprecated APIs).

The script below renames only the packages and names that moved. It was run on a copy of the legacy sources to which a class with javax.naming, javax.sql, javax.annotation.PostConstruct and javax.annotation.processing imports had been added.

javax2jakarta.sh: rename what moved, keep what Java SE owns
#!/bin/sh
# javax2jakarta.sh [project-directory]
cd "${1:-.}" || exit 1
find src -type f \( -name '*.java' -o -name '*.xhtml' -o -name '*.xml' -o -name '*.properties' -o -name '*.js' \) -print0 |
  xargs -0 sed -i.bak -E \
    -e 's/javax\.(faces|servlet|el|enterprise|inject|validation|persistence|ejb|websocket|interceptor|transaction|xml\.bind)([."])/jakarta.\1\2/g' \
    -e 's/javax\.security\.enterprise/jakarta.security.enterprise/g' \
    -e 's/javax\.annotation\.(PostConstruct|PreDestroy|Resource|Resources|Priority|Generated|security)/jakarta.annotation.\1/g'
find src -name '*.bak' -delete

After it ran, 19 lines contained jakarta. and three javax lines were left: the javax.annotation.processing, javax.naming and javax.sql imports, which is correct. The inventory of Take an Inventory First then read 0, 2, 2, 0, 1, 1, 2, 1, 1, 1, 3: the packages and the parameters were done, and the work that a rename cannot do (managed beans, the old expression API, the resolver, the namespaces, the JSP view, jsf.js, the descriptor namespaces) was still listed.

JSP to Facelets

JSP was deprecated in Faces 2.0, when Facelets became the standard view declaration language, and removed in Faces 4.0, together with the JSP tag classes of the jakarta.faces.webapp package. The BalusC article states the reason: JSP writes template text to the response as soon as it meets it, while Faces needs it postponed to Render Response, which forced the f:verbatim workaround and an "everything must be a component" habit. The tools of Tools: Eclipse Transformer and OpenRewrite do not convert a JSP view; the OpenRewrite run left legacy.jsp byte for byte as it was.

The conversion is a short list of mechanical rules plus one design decision per page:

Not needed. Use <f:view locale="..."> only when you need its attributes.

Delete it. Template text is part of the tree in the right order. The tag is gone.

<!-- --> (sent to the browser) or ui:remove (not sent)

  • A request for /legacy.jsp when a view /legacy.xhtml existed rendered that view on Mojarra and on MyFaces (PrimeFaces.settings in the page showed viewId:'/legacy.xhtml'). The JSP file itself, with its <%@ taglib %> lines, was never read.

Managed Beans to CDI

Faces 4.0 removed the native managed bean facility: @ManagedBean, the scopes in javax.faces.bean, @ManagedProperty in that package and the <managed-bean> element. The mapping of every piece, with the CDI form of each, is in the Backing Beans and CDI page and its worked migration. What follows is what the Bookshelf run adds: what the recipe gets wrong, and what a managed bean silently did that a CDI bean does not.

The result for BookService: @Named, an application scope, and an explicit start-up observer
package org.example.bookshelf.service;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.enterprise.context.Initialized;
import jakarta.enterprise.event.Observes;
import jakarta.inject.Named;
import java.util.List;
import java.util.logging.Logger;
import org.example.bookshelf.model.Book;

@Named
@ApplicationScoped
public class BookService {

    private static final Logger LOG = Logger.getLogger(BookService.class.getName());

    private final List<Book> books = List.of(
            new Book("Dune", "Frank Herbert"),
            new Book("Neuromancer", "William Gibson"),
            new Book("Snow Crash", "Neal Stephenson"));

    /** Replaces eager = true of the old managed bean: runs when the application scope starts. */
    void start(@Observes @Initialized(ApplicationScoped.class) Object event) {
        LOG.info("catalogue holds " + books.size() + " books");
    }

    public List<Book> findAll() {
        return books;
    }
}

Source: Jakarta EE Tutorial: Managed Beans in Jakarta Faces Technology and OpenRewrite: Substitute removed Faces Managed Beans

Three details of this class are migration decisions, not typing:

  • @Named without a name is bookService, the same rule @ManagedBean used, so the expressions of the views need no change. The recipe wrote the name out (@Named("bookService")); both forms resolve.

  • eager = true has no automatic equivalent. The recipe dropped the attribute without a trace. A CDI application-scoped bean is created on its first use. The observer above runs when the application scope is initialised: on Mojarra 4.1.17 with Weld 6.0.4.Final on Tomcat 11 the log line appeared at start-up, before the first request. Do this only for a bean whose start-up has a side effect you need (loading a cache, validating configuration); most services do not need it.

  • The class is not Serializable and does not need to be. An application-scoped bean is never passivated. The view-scoped bean below is a different matter.

CatalogueBean: @Inject instead of @ManagedProperty, and the filter out of the getter
package org.example.bookshelf.web;

import jakarta.annotation.PostConstruct;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.List;
import java.util.Locale;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;

@Named("catalogue")
@ViewScoped
public class CatalogueBean implements Serializable {

    @Inject
    private BookService service;

    private String query = "";
    private List<Book> books = List.of();

    @PostConstruct
    void init() {
        books = service.findAll();
    }

    public String getQuery() {
        return query;
    }

    public void setQuery(String query) {
        this.query = query;
    }

    public List<Book> getBooks() {
        return books;
    }

    public void search() {
        String needle = query.toLowerCase(Locale.ROOT);
        books = service.findAll().stream()
                .filter(b -> b.getTitle().toLowerCase(Locale.ROOT).contains(needle))
                .toList();
    }
}

Source: Jakarta Faces 4.1 API: ManagedProperty and ViewScoped

The bean differs from the recipe’s output in three ways that matter:

  • @Inject replaces the field annotation and the setter. The recipe kept @ManagedProperty(value = "#{bookService}") with only its import changed. The annotation still exists in 4.1, in jakarta.faces.annotation, with a different meaning: it is a CDI qualifier that evaluates an EL expression, and it injects nothing unless it is combined with @Inject. A bean that kept it compiled, started, and answered the first request with a NullPointerException (What Happens If You Only Upgrade the Runtime). Grep for ManagedProperty after every automated run; the only legitimate uses are @Inject @ManagedProperty("#{param.id}") for an EL value, as shown on the backing beans page.

  • The filter runs once per action, not once per render. The legacy getBooks() filtered the service’s list inside the getter, so the work ran every time the table asked for its value, and in a real application that call would have been a database query. The migration is a good moment to remove the habit: the filter moved into search(), and the getter returns a field. The view-scoped bean keeps the result between the postbacks of the same view. The change is behaviour-preserving for the page: Mojarra and MyFaces returned the same rows for DUNE (case-insensitive), snow and neuro, for the f:ajax button and for the PrimeFaces button.

  • toLowerCase(Locale.ROOT). Case-insensitive comparison with the default locale gives wrong answers in a few locales (the Turkish dotted and dotless i). It is not a Faces change; it is the kind of defect an old code base carries and a review during a migration finds.

Two descriptor facts complete the bean story:

  • beans.xml from the Java EE 8 era was accepted. The unchanged file (xmlns.jcp.org namespace, version="2.0", bean-discovery-mode="all") deployed and worked with Weld 6.0.4.Final on Tomcat 11. It is still worth replacing: in discovery mode all every class of the archive is a bean candidate, which is how a converter or a helper ends up injectable by accident. The Jakarta EE 11 form is shown in Descriptors, Parameters and the Build.

  • Without any beans.xml, Weld on Tomcat discovered nothing. The page rendered, and the table had no books (#{catalogue.books} resolved to nothing) and the log had no error, which is the same silent failure as the unresolved settings managed bean. CDI’s implicit bean archive rule lets a full application server discover annotated beans in an archive without beans.xml (not run on a server here); on Tomcat with Weld the descriptor is required (see Project Setup).

The <managed-bean> entry named settings in faces-config.xml has no replacement worth writing: it declared a session-scoped copy of CatalogueBean, nothing in the views used it, and it was removed. If yours is used, the replacement is a class with the right scope annotation and a @Named name. Session scope for page state is the first habit to leave behind, with @ViewScoped as the usual successor (Scopes).

The Expression API and the Resolver, Rewritten

Two classes of the legacy Bookshelf used the removed expression API. The recipe changed their imports and left the calls. The migrated QueryReader evaluates a value expression through the Application and builds a method expression through the ExpressionFactory:

QueryReader.java after the migration
package org.example.bookshelf.web;

import jakarta.el.ExpressionFactory;
import jakarta.el.MethodExpression;
import jakarta.faces.context.FacesContext;

/** Reads a value and calls a method through the Expression Language API of Jakarta Faces 4. */
public class QueryReader {

    public static String currentQuery() {
        FacesContext ctx = FacesContext.getCurrentInstance();
        return ctx.getApplication().evaluateExpressionGet(ctx, "#{catalogue.query}", String.class);
    }

    public static void runSearch() {
        FacesContext ctx = FacesContext.getCurrentInstance();
        ExpressionFactory factory = ctx.getApplication().getExpressionFactory();
        MethodExpression search = factory.createMethodExpression(
                ctx.getELContext(), "#{catalogue.search}", void.class, new Class<?>[0]);
        search.invoke(ctx.getELContext(), new Object[0]);
    }
}

Source: Jakarta Faces 4.1 API: Application (evaluateExpressionGet, getExpressionFactory)

The Faces 1.1 VariableResolver becomes an ELResolver, which is a different contract: three methods that read, type and write a property of a base object, and one that tells whether a name is read-only. A resolver for a top-level name such as appName answers only when base is null and marks the property resolved.

AppNameResolver.java replaces LegacyVariableResolver
package org.example.bookshelf.web;

import jakarta.el.ELContext;
import jakarta.el.ELResolver;

/** The EL resolver that replaces the Faces 1.1 variable resolver: it supplies the name appName. */
public class AppNameResolver extends ELResolver {

    private static final String NAME = "appName";

    @Override
    public Object getValue(ELContext context, Object base, Object property) {
        if (base == null && NAME.equals(property)) {
            context.setPropertyResolved(true);
            return "Bookshelf";
        }
        return null;
    }

    @Override
    public Class<?> getType(ELContext context, Object base, Object property) {
        if (base == null && NAME.equals(property)) {
            context.setPropertyResolved(true);
            return String.class;
        }
        return null;
    }

    @Override
    public void setValue(ELContext context, Object base, Object property, Object value) {
        // read-only: isReadOnly() answers true, so Faces never calls this for appName
    }

    @Override
    public boolean isReadOnly(ELContext context, Object base, Object property) {
        if (base == null && NAME.equals(property)) {
            context.setPropertyResolved(true);
            return true;
        }
        return false;
    }

    @Override
    public Class<?> getCommonPropertyType(ELContext context, Object base) {
        return base == null ? String.class : null;
    }
}

In faces-config.xml the <variable-resolver> entry becomes <el-resolver>. The old entry did not fail, and #{appName} printed an empty string (What Happens If You Only Upgrade the Runtime); with the new one legacy.xhtml printed Bookshelf on both implementations.

<application>
  <resource-bundle>
    <base-name>org.example.bookshelf.messages</base-name>
    <var>msg</var>
  </resource-bundle>
  <el-resolver>org.example.bookshelf.web.AppNameResolver</el-resolver>
</application>

Source: Faces 4.1 specification, B.2.1 and the ELResolver section of Extending Faces

A resolver registered with <el-resolver> is one for the whole application. If the only need is "a value reachable by name", a CDI bean with @Named and a @Produces method does the same without a resolver (Producers); the resolver is the right tool when the answer depends on the base object or on the name itself.

Three consequences for the plan:

  • The classifier is a transition tool, not a design. A project on Java EE 8 uses the plain artifact up to 15.x; a project on Jakarta EE uses the same version with <classifier>jakarta</classifier>; at 16.0.0 the classifier disappears, and a build that still asks for it cannot resolve the artifact. The OpenRewrite recipe added the classifier and pinned 14.0.x, which is a correct step on the way and a wrong end.

  • Go one major at a time. Each guide lists what was deleted and what was deprecated "for the next release". Deleting is where code breaks, so read the guide of every major you cross, grep your XHTML and Java for the names it lists, and build and test between steps. A jump from 11 to 16 skips the deprecation notices that tell you what to change first. The PrimeFaces pages cover the current components; the migration guides cover the old names.

  • Not every major breaks your pages. The legacy p:commandButton of the Bookshelf, written for PrimeFaces 11, worked unchanged on 16.0.0 (an Ajax click filtered the table on both implementations). What broke it was the namespace, not the library API.

The PrimeFaces 16 documentation page on dependencies still lists the Faces runtimes "2.3, 3.0, 4.0" while the 16.0.0 migration guide says Faces 2.x and javax.* support were removed and the baseline is Faces 4.0; the jar agrees with the guide (all its classes use jakarta.faces). Struts 1 to Faces

The older books treat Struts 1 integration and conversion to Faces as a main subject: Mann’s book integrates the two frameworks, and the book of Dudney and colleagues has a chapter on converting a Struts application. That material is historical. The Apache Struts project has declared Struts 1 end of life (its announcement counts the Struts 2 releases as of April 2013); the last Struts 1 release was 1.3.10 in December 2008, and the announcement says that there is no drop-in replacement for it. (Struts 1, its migration and JSP in general are covered in the Struts 1 (Classic) & Migration page of the JSP & Struts section.)

One technical fact makes the old integration advice unusable on a current platform: struts-core 1.3.10, the newest release on Maven Central, refers to javax/servlet/http/HttpServlet in its ActionServlet, so it does not run on a Servlet 5 or newer container such as Tomcat 10 or later. Struts 1 and Faces 4 cannot share a WAR on a Jakarta EE 9 or newer server unless the Struts jars are transformed (the Eclipse Transformer of Eclipse Transformer: Names in Binaries, up to Jakarta EE 9 could do it; not run). The practical plan for a Struts 1 application is therefore to convert it screen by screen while it still runs on its old platform, as stage 1 of the route, or to run old and new applications as two deployments behind a reverse proxy that routes by URL.

The concepts map one to one in most places, and this is the table to use when converting. It is the author’s mapping from the two frameworks' concepts; no Struts 1 application was converted for this page.

Proving the Migration: A Smoke Test

The most dangerous failures of this page are the silent ones, so the end of the migration needs a test that fails on them. The script below makes one check for each: books listed (the bean was injected), the project stage (the parameter was read), no missing script resource, no jsf. left in the page, faces.js served, the EL resolver working, and an Ajax search that filters the table. It needs only curl and a running application, and it works on any server and on both implementations.

smoke.sh: one check per silent failure
#!/bin/sh
# smoke.sh http://localhost:8080/bookshelf
BASE=${1:?base url}
JAR=$(mktemp)
fail=0
check() { if [ "$2" = "ok" ]; then echo "ok    $1"; else echo "FAIL  $1"; fail=1; fi; }

page=$(curl -s -c "$JAR" -b "$JAR" "$BASE/index.xhtml")
echo "$page" | grep -q 'Dune' && check "bean injected, books listed" ok || check "bean injected, books listed" no
echo "$page" | grep -q 'stage=Development' && check "jakarta.faces.PROJECT_STAGE read" ok || check "jakarta.faces.PROJECT_STAGE read" no
echo "$page" | grep -q 'RES_NOT_FOUND' && check "no missing script resource" no || check "no missing script resource" ok
echo "$page" | grep -q 'jsf\.' && check "no jsf.* left in the page" no || check "no jsf.* left in the page" ok
[ "$(curl -s -o /dev/null -w '%{http_code}' "$BASE/jakarta.faces.resource/faces.js.xhtml?ln=jakarta.faces")" = 200 ] \
  && check "faces.js served" ok || check "faces.js served" no
curl -s "$BASE/legacy.xhtml" | grep -q 'Bookshelf' && check "EL resolver supplies appName" ok || check "EL resolver supplies appName" no

state=$(echo "$page" | sed -n 's/.*name="jakarta.faces.ViewState"[^>]*value="\([^"]*\)".*/\1/p' | head -1)
answer=$(curl -s -c "$JAR" -b "$JAR" -H 'Faces-Request: partial/ajax' \
  --data-urlencode 'searchForm=searchForm' --data-urlencode 'searchForm_SUBMIT=1' \
  --data-urlencode 'searchForm:query=snow' --data-urlencode "jakarta.faces.ViewState=$state" \
  --data-urlencode 'jakarta.faces.source=searchForm:search' --data-urlencode 'jakarta.faces.partial.ajax=true' \
  --data-urlencode 'jakarta.faces.partial.execute=searchForm' --data-urlencode 'jakarta.faces.partial.render=results' \
  --data-urlencode 'jakarta.faces.behavior.event=action' --data-urlencode 'searchForm:search=' \
  "$BASE/index.xhtml")
echo "$answer" | grep -q 'Snow Crash' && ! echo "$answer" | grep -q 'Dune' \
  && check "Ajax search filters the table" ok || check "Ajax search filters the table" no
rm -f "$JAR"
exit $fail

Against the migrated Bookshelf the script printed ok seven times and exited with 0 on Mojarra 4.1.17 and on MyFaces 4.1.4. Against the state with the five leftovers of What Happens If You Only Upgrade the Runtime it exited with 1: four of the seven checks failed (the page itself answered 500, so the first two checks failed together). The line searchForm_SUBMIT=1 is needed by MyFaces only; Mojarra ignores it. Add the script to the build pipeline; it is the cheapest regression test the migration can leave behind. The Security and testing pages hold the browser-level tests.

Preparing for Faces 5.0

Faces 5.0 is not released. The specification page marks it as under development with Java SE 21 as the minimum, and the latest milestone of the API is 5.0.0-M9 (2026-09-18). What the final release contains can still change, so this section describes a method and the milestone’s data, not a promise.

The direction is stated on the versions page: the removal of everything deprecated for removal since 4.0, of the old XML namespaces, of composite:extension and of the custom scope events, plus a modernisation of the API with generics and enums. That makes the preparation concrete, because the things to avoid are already marked:

  1. Compile with -Xlint:removal against 4.1. Every [removal] warning is something 5.0 plans to delete. A class using @FacesConfig(version = ...), the JSF_SCRIPT_* constants and ViewHandler.DEFAULT_SUFFIX gave five warnings against 4.1.2.

  2. Compile against the milestone in a separate step. The same class gave five errors against 5.0.0-M9 (cannot find symbol version(), Version, JSF_SCRIPT_LIBRARY_NAME, JSF_SCRIPT_RESOURCE_NAME, DEFAULT_SUFFIX). The migrated Bookshelf compiled against it with no warning and no error.

  3. Replace the old namespaces now. They still work in 4.1 (XML Namespaces: java.sun.com and xmlns.jcp.org to the URNs (Faces 4.0)) and are planned to go in 5.0.

  4. Check the libraries. Whether PrimeFaces 16, OmniFaces 5 and your own extensions run on a 5.0 milestone was not run here.

# once: get the milestone API and the compile classpath of the project

Reading the milestone API jar against the 4.1.2 jar shows the direction in detail. In 5.0.0-M9 these public API elements are absent (present and deprecated for removal in 4.1.2):

  • FacesConfig.version() and FacesConfig.Version;

  • ResourceHandler.JSF_SCRIPT_LIBRARY_NAME and JSF_SCRIPT_RESOURCE_NAME;

  • ViewHandler.DEFAULT_SUFFIX and DEFAULT_SUFFIX_PARAM_NAME;

  • StateManager.PARTIAL_STATE_SAVING_PARAM_NAME and FULL_STATE_SAVING_VIEW_IDS_PARAM_NAME;

Note also that the class files of 5.0.0-M9 are Java 17 class files (version 61) although the specification page asks for Java SE 21.

Mojarra vs MyFaces During a Migration

The two implementations agreed on almost everything above, and the differences are mostly in what they say, not in what they do:

  • Both ignored the old context parameters, the <managed-bean> and <variable-resolver> entries and an unannotated @ManagedProperty; both accepted the old namespaces and the old descriptor versions; both failed the same way when a library or a class still used javax (Mojarra with NoClassDefFoundError for the class it was loading, MyFaces with Class javax.faces.webapp.FacesServlet not found and a failed StartupServletContextListener).

  • Missing script resource: Mojarra renders <script src="RES_NOT_FOUND"> and logs nothing; MyFaces renders nothing and logs a warning with the resource and library names.

  • A request mapped to a missing view (*.jsp with no .xhtml sibling): Mojarra answered 404, MyFaces 500 with InvalidFileException.

  • Startup noise: on an embedded Tomcat without Jasper, MyFaces 4.1.4 logs SEVERE: Class org.apache.jasper.servlet.JspServlet not found while starting, after looking up the JSP servlet class. It is harmless here (JSP support is gone) and is not the reason the application fails when it fails; the actual cause is further down the log.

  • Hand-built Ajax posts: MyFaces needs the hidden form_SUBMIT=1 field in a request that you assemble by hand, as the smoke test does; Mojarra ignores it.

  • Generated markup: the Ajax button’s onclick is mojarra.ab(...) on Mojarra and myfaces.ab(...) inside faces.util.chain on MyFaces. Tests must not depend on either.

The general comparison is in Versions and Implementations.

  • HTML Components: the component reference is the part that aged best; missing type on h:inputText, layout="list", f:selectItemGroups, h:commandScript; Tomahawk and RichFaces tags; p: components standing in for standard ones.

  • Core Tags: javax and the 1.x namespace, f:view, f:verbatim and f:subview of JSP, managed beans with f:setPropertyActionListener, SelectItem lists, MethodBinding; no f:event, f:metadata, f:selectItemGroups or f:resetValues.

  • Data Tables and Iteration: JSP and javax, @ManagedBean tables, ArrayDataModel and friends without CollectionDataModel, sorting and paging through RichFaces, Tomahawk or Trinidad, ui:repeat with jsfc, binding with getRowData(), no Ajax.

  • File Upload and Download: upload recipes on Tomahawk and RichFaces components or a Commons FileUpload filter; their newest releases are from 2012 and 2016 and predate jakarta.faces; the era’s recipes lack content-type sniffing, generated file names and CSV formula escaping.

  • Converters: javax.faces.convert.Converter and ids, registration in XML, java.util.Date instead of java.time, converters with parameters via managed beans, entity converters that serialise or call a static DAO, hand-written refresh; no UUIDConverter.

  • Validators: javax names and ids, static lookups instead of injection, JSP tag handlers, MethodBinding, hand-written regular-expression and required validators, cross-field validation through other-component lookup or Tomahawk, hand-written client-side checks.

  • Bean Validation: Bean Validation 1.0 and javax.validation versus 3.1, no f:validateWholeBean, @ManagedBean and <validator> registrations, recipes relying on ended libraries, PrimeFaces client-side validation as an addition.

  • Messages and Internationalisation: javax.faces.Messages and its keys, f:loadBundle and managed beans for text, session-scoped locale switchers, native2ascii escapes, RequestContext.

  • Events and Listeners: no system events in the 1.x books, immediate and renderResponse() tricks for dependent drop-downs, MethodBinding listeners, @ManagedBean listener beans, javax.faces.event.

  • Navigation: rules for everything, .jsp view ids, every link a postback, <view-param>, NavigationHandler subclasses and MethodBinding, no Post/Redirect/Get by default, javax names, Struts-style navigation.

  • View Parameters and View Actions: no f:viewAction (a preRenderView listener instead), legacy beans and namespaces, pretty URLs from PrettyFaces, errors answered as 200, hand-built redirects.

  • Flash and Post/Redirect/Get: JSF 1.x books predate the flash and used a <redirect/> case, parameters or a session bean; the 2.0 books use javax and @ManagedBean.

  • Backing Beans and CDI: beans in faces-config.xml (1.x), @ManagedBean and @ManagedProperty with setters (2.x), Spring and EJB integration through resolvers or JNDI, static FacesContext.getCurrentInstance() everywhere, session beans as the default.

  • Scopes: @ManagedBean and the javax.faces.bean scopes, only three scopes, Seam 2 conversations, "session scope is fine for a form", javax.faces.bean.ViewScoped, the Tutorial’s "Allowable Connections" table.

  • Faces Flows: no flows at all; session beans, Seam 2 conversations, faces-config.xml navigation rules and @ManagedBean for wizards.

  • Multi-Window Support: nothing knows that tabs exist; state in session beans; hand-made tokens and window.name scripts; javax names for the 2.2 client window; session-scoped wizard beans.

  • Ajax: hand-written Ajax, Weblets and ajax4jsf; jsf.js, jsf.ajax.request and javax.faces.partial.*; older than delay, resetValues, h:commandScript and search expressions; the libraries ended.

  • Search Expressions: the PrimeFaces Cookbook treats process and update as a library feature; the core specification owns the facility since 2.3 and the older books show only four keywords.

  • WebSocket Push: no framework push before 2.3 (polling, XMLHttpRequest, libraries); PrimeFaces Push on Atmosphere was removed in 7.0; use f:websocket or o:socket.

  • Composite Components: javax packages, the java.sun.com/jsf/composite namespace, @ManagedBean; Facelets Essentials predates composites; the Composite design pattern of Dudney is a different thing; JSP tag handler components are gone.

  • Tag Files and Tag Libraries: Facelets 1.x taglib DTD and registration parameters, com.sun.facelets handlers, JSP tag handlers with TLDs, "composition components", the Tutorial’s validator-class element.

  • Custom Components and Renderers: JSP tag handlers and TLDs, javax, hand-written saveState and restoreState, XML registration, Weblets and Ajax by hand, XUL and HTC render kits; the design-patterns chapters stay accurate.

  • Client Behaviors: nothing before 2.0 knew behaviors (renderers, scripts and libraries did the job); javax; the XUL and HTC kits; PrimeFaces books describe libraries that moved on.

  • Resource Handling: Weblets as the answer for JAR resources (configuration file, weblet:// URLs, a view handler and a phase listener) and its standard replacements; library="javax.faces" with jsf.js; the old ResourceHandlerWrapper constructor rule.

  • Resource Library Contracts: contracts did not exist (2.2); templates chosen by literal path; skinning through render kits and library skins; PrimeFaces theme switchers are a separate mechanism.

  • Configuration and Project Stages: javax.faces.* parameter names (ignored silently), <managed-bean>, the JSP-era mapping and suffix, DTDs and old schemas, facelets.* parameters, Mojarra 1.x and 2.x parameters, standalone Facelets development mode, secrets in configuration.

  • Extending Faces: javax registration and namespace, VariableResolver, PropertyResolver, MethodBinding, ValueBinding and ResourceResolver, standalone Facelets view handlers, implementing whole interfaces instead of *Wrapper classes, Weblets, beans from the managed-bean facility.

  • Exception Handling: javax names, the no-argument wrapper constructor, navigating from a handler during Render Response (invalid since 2.3), no mention of per-implementation behaviour, library mechanisms of PrimeFaces 3 to 5, error pages that explain the failure.

  • State Saving and Stateless Views: the removed StateManager API, a readable client state shown as normal, "everything is saved", client state as a casual switch, JSP-era advice, hand-written component state, Seam-era workarounds, no stateless views, session memory as free.

  • Security: container-managed authentication per server (realms, j_security_check), the JSF Security project, Acegi and Seam 2; silent on protected views, SameSite, CSP, Sec-Fetch-* headers, modern password storage and OpenID Connect; listings that store clear-text passwords are historical.

  • Performance: harsher state-size warnings from full tree saving, STATE_SAVING_METHOD as the lever, ajax4jsf and Weblets, JSFUnit-era load testing, PrimeFaces 5 lazy models, partial submit and cache; none covers CDI @ViewScoped, OmniFaces 5, MyFaces view pooling or Production-stage defaults.

  • PrimeFaces: Getting Started and Themes: javax.faces on JSF 2.2, primefaces.js, ThemeRoller and the theme switcher, Font Awesome in the jar, Grid CSS, the head-resource ordering, client-side localisation.

  • PrimeFaces: Ajax, Forms and Validation: RequestContext, p:calendar, the client-side validation framework of its day, p:push, autoUpdate, p:watermark and the mobile components, namespaces.

  • PrimeFaces: Data Components: selection attributes, the old lazy load signature, sortBy and SortOrder, java.util.Date schedule models, iText 2 and POI 3.7 exporters, ui-icon classes, the raw tree-node constructors.

  • PrimeFaces: Panels, Menus and Dialogs: RequestContext for the dialog framework, ThemeRoller themes and jQuery UI icons, removed or renamed components and attributes, the old JSF base, p:push.

  • PrimeFaces: Files, Media, Charts and Drag and Drop: fileUploadListener and the upload limits on the component, Commons FileUpload, DefaultStreamedContent constructors, JCrop and the Flash camera, jqPlot charts, map set-up, drag and drop.

  • PrimeFaces Extensions: Extensions 1.2.1 and the old namespace, components that are gone or renamed, reworked components, the utility functions, security of rich-text input, a single downloadable release.

  • OmniFaces: none of the books covers OmniFaces 4 or 5; helper code around FacesContext, per-entity converters, @ManagedProperty parameters, hand-written exception and resource handlers, pretty URLs, PrimeFaces Push, cross-field validators, ended libraries, javax imports.

  • Other Component Libraries: the Cookbook’s recipes target RichFaces 3.3, PrimeFaces 2.0, Tomahawk, Trinidad, Seam 2 and Spring 2.5; render-kit chapters cover the rich-component frameworks of the JSF 1.x era; none mentions BootsFaces, Tobago or AdminFaces.

  • Jakarta EE Servers: Sun Java System Application Server, JBoss AS 4 to 7, WebLogic and Tomcat with sun-web.xml and jboss-web.xml, implementation JARs copied into the WAR, managed beans declared in faces-config.xml, Ant and hot deploy by copying files, no containers.

  • Tomcat and Weld: the 2004 and 2010 books list the JSF API and implementation JARs, jstl.jar, standard.jar and Commons JARs to copy into WEB-INF/lib or Tomcat’s shared directory, on Tomcat 5 or 6 and Servlet 2.5; no step for a CDI container (the managed-bean facility did the work), JSP as the view technology, deployment by copying files.

  • Spring Boot with JoinFaces: the Spring 2.5 DelegatingVariableResolver integration of Leonard’s cookbook, WAR-and-web.xml assumptions in place of properties, Struts 1 integration, hand-edited web.xml and manual JARs in the PrimeFaces books, and javax.faces imports in old Spring-and-Faces tutorials.

  • Quarkus: every book predates Quarkus; WAR deployment and *.jsf mappings, managed-bean entries, Spring, Seam and Hibernate recipes that assume a run-time scanning container, Development in web.xml, redeploy and JRebel hot deployment, no native or container-first packaging, PrimeFaces 4 and 5 theme jars.

  • Persistence and Services: Seam 2 conversations and entity homes, Spring 2.5 DelegatingVariableResolver (deprecated in Spring 3.2), Hibernate 3-era session filters and hbm.xml, @ManagedProperty injection, EJB 2.x entity beans, extended persistence contexts as view state.

  • Testing: JSFUnit and Faces Console, the container as the only place to test a bean, JMeter view-state extraction with the javax field name; still valid is the advice to keep converter and validator logic free of runtime Faces classes. None of the books covers Selenium, Arquillian or browser tests of PrimeFaces components.

  • Deployment and Clustering: Tomcat 5 and Servlet 2.5 containers, Ant builds, client state as the answer to clusters (true only with fixed keys, encryption and a home for view-scoped beans), the non-serialisable saved view of JSF 1.1, javax.faces.PROJECT_STAGE copied from samples, and no containers, proxies or probes.

  • Best Practices: the books teach much that holds (separate view from model, keep beans small, validate on the server, redirect after a post), but their examples use JSP, Facelets 1.x, javax.faces, @ManagedBean and session beans; they rely on hand-written Ajax and libraries without a Jakarta Faces release; they show the removed state-saving API; their security material rests on the container and on ended projects; and none covers flows, the CDI view scope, stateless views, WebSocket push, JoinFaces or Quarkus.

Common Mistakes

  • Renaming only the imports. The javax.faces string also lives in parameters, XML, messages, ids, request parameters and resources, and a missed one fails without an error (javax to jakarta (Faces 3.0, Jakarta EE 9), What Happens If You Only Upgrade the Runtime).

  • Blind s/javax/jakarta/. It breaks javax.naming, javax.sql, javax.crypto and javax.annotation.processing, which Java SE still owns, and it produces jakarta.faces.bean and jakarta.faces.el, which do not exist in 4.x.

  • Trusting a green build from an automated tool. OpenRewrite reported success on a project that did not compile, and on JDK 26 skipped the most important class with a warning. Count the changed files and compile.

  • Keeping @ManagedProperty without @Inject. It compiles, it deploys and it fails on the first request with a null service.

  • Leaving the old descriptor entries. <managed-bean>, <variable-resolver> and the javax.faces.* parameters are ignored without a message; the stage falls back to Production.

  • Changing jsf.js in Java and XHTML but not in the JavaScript files, or the other way round. Search all three.

  • Jumping several PrimeFaces majors at once. The deprecations that told you what to change were in the releases you skipped (PrimeFaces).

  • Using the jakarta classifier on PrimeFaces 16. The artifact has none.

  • Assuming the artifact name tells the namespace. org.glassfish:jakarta.faces:2.3.21 is javax (Faces Implementations and Servers).

  • Mixing javax and jakarta jars in one WAR. A library that was not migrated fails at startup, in its own listener, before Faces is reached (What Happens If You Only Upgrade the Runtime).

  • Shipping with the Development stage because the migrated web.xml came from a development copy. Set Production for deployments (Project Stages).

  • Letting the temporary *.jsp mapping stay. Old URLs keep working and hide which page is served (JSP to Facelets).

  • Migrating without a test that fails on the silent errors. The smoke test of Proving the Migration: A Smoke Test is a start.

  • Copying a book’s example and "fixing" it by trial. Start from the current page of this section, not the book.
