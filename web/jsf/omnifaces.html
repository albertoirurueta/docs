OmniFaces

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against OmniFaces 5.5.5 (released on 2026-10-06; the 5.x line requires Java 17, Jakarta Faces 4.1, Jakarta EL 6.0, Servlet 6.1 and CDI 4.1), Jakarta Faces 4.1 (API jakarta.faces-api 4.1.2, part of Jakarta EE 11), Eclipse Mojarra 4.1.17 and Apache MyFaces Core 4.1.4 with Java 17 or later, and PrimeFaces 16.0.0 where the two libraries meet. OmniFaces 4.7.15 is the release for Faces 4.0 and 3.0; where its behaviour differs, What Changed per Version says so. The examples were compiled and deployed in a scratch Bookshelf WAR on Apache Tomcat 11.0.26 with Weld 6.0.4.Final, once with Mojarra and once with MyFaces, and driven with scripted HTTP requests and a headless Chrome; every result quoted below as observed comes from those runs (checked on 2026-10-08). Features that were read in the documentation and not run say so. Faces 5.0 is still a milestone release; OmniFaces 5.4 and later declare that they are compatible with it (What Changed per Version), and nothing here describes Faces 5.0 as current behaviour.

What OmniFaces Is, and What It Is Not

Every Faces project grows the same helper classes. One fetches a request parameter without navigating FacesContext.getCurrentInstance().getExternalContext().getRequestParameterMap(); one adds a FacesMessage in one line; one turns a byte[] into an image; one registers a filter to compress the response. OmniFaces is that collection, maintained as a library: a utility library for standard Faces. Its own description is that it focuses on utilities that ease everyday tasks with the standard Faces API, and that it does not and will not contain visual components such as rich tables or look and feels. It works with any component library; the OmniFaces showcase application is itself built with PrimeFaces.

That scope separates it from PrimeFaces (see the PrimeFaces pages of this section, which start with the setup and continue with Ajax and forms, data components and PrimeFaces Extensions), which is a UI library: PrimeFaces gives you a data table and a dialog, OmniFaces gives you the missing @Param annotation, the validator that compares two fields, a handler that makes an Ajax failure show your error page, and a few output components (o:cache, o:tree, o:highlight) that render no widget markup of their own.

OmniFaces is organised by the kind of artefact it adds. The table lists the packages under org.omnifaces and the sections of this page that cover them; the showcase groups its examples the same way.

Three design choices explain how the library behaves. First, it is a WAR library: it is a web fragment with CDI extensions and Faces configuration that it registers by itself, and the jar belongs in WEB-INF/lib of each web application (Installing OmniFaces). Second, it keeps its own dependencies to a minimum: Bean Validation is optional, and the library bundles its own JSON encoder, XML helpers and cache. Third, it prefers the standard to the proprietary where the standard has caught up. Several ideas that OmniFaces offered first reached Faces itself: f:importConstants and f:websocket (both in Faces 2.3; o:socket of OmniFaces 2.3 came first), CDI injection into converters and validators (Faces 2.3, and managed=true in 4.0), and a CDI replacement for @ManagedProperty (jakarta.faces.annotation.ManagedProperty, covered on the backing beans page), which injects a value by EL expression and coerces it by the EL rules but, unlike @Param (@Param, @Cookie and @ContextParam: Injecting Request Data), has no Faces converter, validator or message. The OmniFaces documentation says so on the page of the feature concerned, and this page does the same: for every feature it states whether the standard now covers the case and when to reach for OmniFaces anyway.

The 4.x and 3.x lines receive the bugfixes of 5.x but no new features. The 5.5.5 and 4.7.15 releases are dated the same day and carry the same fixes. A Faces 4.0 server (Jakarta EE 10) therefore stays on 4.7.15 until it moves to Jakarta EE 11, and a Faces 4.1 server uses 5.5.5. The one optional dependency worth knowing is Bean Validation (version 3.1 for 5.x), needed only for o:validateBean and FacesLabelMessageInterpolator.

Three rules about where the jar goes, from the project documentation:

  • Only in WEB-INF/lib of the WAR. Placed in an EAR lib directory or in the server’s own library directory, the webapp cannot find the Faces and CDI annotated classes inside the jar, and fails at deployment or at run time.

  • Never twice. A second copy of the jar makes CDI report ambiguous dependencies at deployment.

  • Servlet container. On Tomcat (Tomcat and Weld) the jar works with Weld and either Faces implementation (all examples of this page ran that way); a server such as WildFly or GlassFish needs nothing else (Jakarta EE servers). On Spring Boot the JoinFaces starter omnifaces-spring-boot-starter pulls in the Faces and Weld starters and maps joinfaces.omnifaces.* properties to the org.omnifaces.* context parameters. On Quarkus the Quarkiverse extension quarkus-omnifaces exists. The Spring Boot with JoinFaces and Quarkus pages of this section cover those setups.

On start-up the library logs one line that confirms it was found (INFO: Using OmniFaces version 5.5.5 in the scratch runs, from ApplicationInitializer).

The XML namespace

OmniFaces 5 declares every tag and every EL function under one URN namespace:

The namespace declarations
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core"
      xmlns:o="omnifaces"
      xmlns:sec="omnifaces.security">

Source: OmniFaces: XML namespaces

The history matters when you read older code. OmniFaces 1.x to 4.x declared the tags with xmlns:o="http://omnifaces.org/ui" and the EL functions with a second prefix, xmlns:of="http://omnifaces.org/functions", so that the books and blog posts you find call the functions as #{of:abbreviate(...)}. In 5.0 both were merged into xmlns:o="omnifaces", and the functions are called as #{o:abbreviate(...)}. The security tags (sec:) are new in 5.0 and use xmlns:sec="omnifaces.security". The migration is three steps: change the o namespace, rename of: calls to o:, remove the of declaration. The old URL namespaces still work in 5.5.5 (a page declaring xmlns:o="http://omnifaces.org/ui" and xmlns:of="http://omnifaces.org/functions" rendered #{of:abbreviate('The quick brown fox', 10)} as The quick... on both implementations, with no warning in the log), but the taglibs that provide them state that they are deprecated and will be removed in 6.x. New code uses the URN namespace.

What registers itself

OmniFaces needs no entry in web.xml or faces-config.xml for most of its features: the jar ships a faces-config.xml that is ordered after all other configuration files, a web-fragment.xml marked <distributable/>, a beans.xml, four CDI extensions and one ServletContainerInitializer. Where OmniFaces Sits in the Request Processing Lifecycle

The utilities that need a lifecycle position hook into the six phases (see the lifecycle page) as the diagram shows. The positions come from the Javadoc and from the source of the 5.5.5 sources jar; the sections below repeat them where they change behaviour.

flowchart LR A[Restore View] --> B[Apply Request Values] --> C[Process Validations] --> D[Update Model Values] --> E[Invoke Application] --> F[Render Response] A1["@Eager(viewId) beans created after the phase; o:enableRestorableView rebuilds an expired view"] -.-> A B1["o:inputHidden converts and updates here; o:viewParam, o:hashParam, o:scriptParam"] -.-> B C1["o:validateEqual and the other multi-field validators when the tree walk reaches them; o:validateBean class level, before and after the phase; o:skipValidators"] -.-> C D1["o:validateBean with method validateActual runs after the phase"] -.-> D E1["o:viewAction evaluates its if attribute here; @RateLimit runs on the action method; Ajax.update and Ajax.oncomplete"] -.-> E F1["o:cache, o:highlight, o:messages, o:graphicImage URLs; CombinedResourceHandler; the handle of FullAjaxExceptionHandler after every phase"] -.-> F

Anything that reads a request parameter, @Param among them, runs when the bean that holds it is created, which is a different moment from all of the above: the first time a view or a class refers to the bean. @Param, @Cookie and @ContextParam: Injecting Request Data shows what that costs.

The Utility Classes: Faces, FacesLocal and Friends

org.omnifaces.util.Faces is the class most people meet first. It is a set of static shortcuts that "flatten" the hierarchy of objects that you reach from FacesContext, plus a number of helpers that remove multi-line boilerplate: Faces.getRequestParameter(name) instead of the chain through the external context, Faces.redirect(...) that prepends the context path and URL-encodes its parameters, Faces.sendFile(...) that streams a download, Faces.getLocale() that never returns null. FacesLocal has the same methods with the FacesContext as first argument; use it in code that calls many of them, to look up the thread-local context once. A bean that uses them

The bean reads parameters and settings, adds messages, redirects with encoded parameters and sends a file. It is the UtilsBean of the scratch application:

UtilsBean.java
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Named;
import java.nio.charset.StandardCharsets;
import java.util.List;
import org.omnifaces.util.Faces;
import org.omnifaces.util.Messages;

@Named
@RequestScoped
public class UtilsBean {

    public String getQuery() {
        // null when absent, no Map lookup and no null checks on the chain
        return Faces.getRequestParameter("q");
    }

    public Integer getPage() {
        // typed access: converts with the Faces converter for Integer, null when absent or invalid
        return Faces.getRequestParameter("page", Integer.class);
    }

    public String getBaseUrl() {
        return Faces.getRequestBaseURL();
    }

    public String getViewId() {
        return Faces.getViewId();
    }

    public String getStage() {
        return Faces.getProjectStage().toString();
    }

    public String getMapping() {
        return Faces.getMapping();
    }

    public List<String> getLocales() {
        return Faces.getSupportedLocales().stream().map(Object::toString).toList();
    }

    public java.time.LocalDate getStart() { return java.time.LocalDate.of(2020, 1, 15); }
    public java.time.LocalDate getEnd() { return java.time.LocalDate.of(2026, 10, 8); }

    public void greet() {
        Messages.addGlobalInfo("Welcome back, {0}!", "reader");
    }

    public void problem() {
        Messages.addError("form:title", "The title {0} is already on the shelf", "Dune");
        Messages.addGlobalWarn("Your changes were not saved");
    }

    public void builder() {
        Messages.create("Review saved").detail("Thank you, {0}", "reader").add();
    }

    public String flashAndRedirect() {
        Messages.addFlashGlobalInfo("Book {0} added", 42);
        return "utils?faces-redirect=true";
    }

    public void redirectWithParams() {
        // parameters are URL-encoded by Faces.redirect
        Faces.redirect("utils.xhtml?q=%s&page=%d", "war & peace", 2);
    }

    public void download() {
        Faces.sendFile("hello.txt".getBytes(StandardCharsets.UTF_8), "hello.txt", true);
    }

    public void downloadNamed() {
        String name = Faces.getRequestParameter("name");
        Faces.sendFile("x".getBytes(StandardCharsets.UTF_8), name, true);
    }
}

What the runs showed, on Mojarra and on MyFaces alike:

  • utils.xhtml?q=dune rendered q=dune; page was empty because Faces.getRequestParameter("page", Integer.class) returns null for an absent parameter, and ?page=3 gave 3. The base URL was http://localhost:8570/bookshelf/, the view id /utils.xhtml, the stage Production and the mapping .xhtml.

  • Faces.getSupportedLocales() returned [en, es] only after the application declared <locale-config> with a default locale en and a supported locale es; without it the list was empty on both implementations, so do not rely on the Javadoc’s remark that the default locale comes first before you configure the locales (see the messages page).

  • Faces.redirect("utils.xhtml?q=%s&page=%d", "war & peace", 2) sent the browser to utils.xhtml?q=war+%26+peace&page=2: the format arguments are URL-encoded, the format string is not, and the context path was added for a relative path. Encode the arguments of a redirect with this method; do not concatenate user input into the path.

  • Faces.sendFile(bytes, name, true) answered Content-Disposition: attachment;filename="hello.txt"; filename*=UTF-8''hello.txt with the content type derived from the file name. The file name goes through percent-encoding: a name with a quote, a backslash or a CR-LF pair (a"b.txt, ..\..\x.txt, a<CR><LF>X-Evil: 1.txt) came out as a%22b.txt, ..%5C..%5Cx.txt and a%0D%0AX-Evil%3A%201.txt in both parameters, so header injection is prevented. The encoding is not a path sanitiser, though: the name still contains the separators, which a browser removes when it saves the file. Build the name from your own data, never from the request, and apply the checks of the download section (including the CSV formula escaping) before you send anything the user typed.

The faces EL object

The FacesELResolver (since 2.6) exposes the parameterless get... and is... methods of Faces that return a String or a boolean as properties of an implicit object #{faces}. The Faces 4.1 specification has no such object, so this is an OmniFaces feature and works only with OmniFaces in the application. Observed on both implementations: #{faces.development} (false in Production), #{faces.requestBaseURL}, #{faces.requestContextPath} (/bookshelf), #{faces.ajaxRequest} and #{faces.serverInfo} (Apache Tomcat/11.0.26) resolved, while #{faces.contextPath} and #{faces.projectStage} failed on both (Mojarra’s message: #{faces.contextPath} does not exist), because there is no getter of that name that returns a string or a boolean. The Javadoc of importFunctions itself prefers #{faces.development} or #{request.contextPath} to calling the function form.

Source: OmniFaces 5.5.5 API: FacesELResolver

The @messages search keyword

Faces 4.0 lets a library add search keywords (see the search expressions page). OmniFaces registers one, @messages (since 3.1), which resolves to all h:message and h:messages components in the current form. It solves the chore of listing the message ids in every render attribute of a long form:

kw.xhtml (the relevant part)

The Messages Utility and o:messages

Adding a message by hand takes a client id, a severity, a summary and a detail, and a MessageFormat call if there are arguments. Messages reduces each case to one line. The summary is formatted with MessageFormat and the given arguments by default, so {0} is a placeholder (a literal quote or brace in the text has the usual MessageFormat rules).

The ways to add a message

The Ajax Utility

Standard Ajax decides what is re-rendered in the view: the render attribute of f:ajax lists the ids (see the Ajax page). When the bean knows better, org.omnifaces.util.Ajax adds to the list from Java, runs a script when the response has been processed, and passes data to that script. import java.io.Serializable;
import java.util.Map;

@ViewScoped

    private int other;

@Param, @Cookie and @ContextParam: Injecting Request Data

A bookmarkable page (see the view parameters page) usually declares f:viewParam in f:metadata, adds a f:viewAction or a preRenderView listener to load the data, and puts the loaded value into the bean in a method the framework calls at a particular phase. @Param collapses this: the request parameter is injected into the bean’s field, converted and validated, and is available in @PostConstruct.

When the messages appear

A @Param field is injected when the bean is created, and in a request scoped bean that is the first time the page refers to it. Messages added at that moment land in the queue only if the component that displays them has not rendered yet. In param.xhtml the h:messages is after the expressions that touch the bean, so the messages showed. Move it to the top and they do not: the scratch page param-first.xhtml, identical but with the messages first, rendered an empty ul id="msgs" for ?id=abc on Mojarra. Two ways to fix it, and a third that does not work:

  • Put the messages component after the first use of the bean. Cheap, and a trap for the next person who tidies the page.

  • Make the bean eager for the view with @Eager(viewId = "/param-first.xhtml") (@Eager and @Startup): it is created after the Restore View phase, before rendering, and the message appeared above the list on both implementations.

  • @Eager(requestURI = ...) does not work here: the bean is then created before the FacesServlet runs, there is no FacesContext, and the injection fails with NullPointerException: Cannot invoke "FacesContext.getApplication()" because "context" is null in ParamProducer; the Javadoc of @Eager states that the FacesContext is not available in that case, and OmniFaces logs Could not instantiate eager request scoped beans for request ....

A related difference to f:viewParam: @Param runs at bean creation, which can be in any phase, including Render Response. A conversion error in a f:viewParam, by contrast, stops the lifecycle at Process Validations for the view, and invokes f:viewAction only if everything passed. When you need the "validate everything first, then act" semantics, use o:viewParam with o:viewAction (View Parameters Done Right: o:viewParam, o:viewAction and Friends).

Path parameters

@Param(pathIndex = 0) reads the first segment after the page name (/book/978-0441013593 mapped to book.xhtml), which needs a prefix-mapped FacesServlet or FacesViews with MultiViews. The scratch run of that is in FacesViews: Extensionless URLs, MultiViews and Dynamic Routes. Path parameters are as untrusted as query parameters; in the run, /books/abc/reviews injected the string abc into a pathName field without complaint, so add a converter or a validator wherever the value is not free text.

What changed

@Param has existed since OmniFaces 1.6; multi-valued parameters came in 2.4, path parameters in 2.5, globalMessage in 4.5 and pathName in 5.5. Between 3.6 and 5.3 a @Param field also worked without @Inject; since 5.4 that is deprecated, a warning is logged at deployment for each such field, and it will be removed, so put @Inject next to every @Param. The standard alternative for a single string is @Inject @ManagedProperty("#{param.id}") (the backing beans page), which has none of the conversion, validation and message features above.

OmniFaces @ViewScoped and @RateLimit

The OmniFaces view scope

org.omnifaces.cdi.ViewScoped is an alternative to jakarta.faces.view.ViewScoped with a stricter lifecycle: the bean is destroyed (and its @PreDestroy called) when the browser unloads the page, by a navigator.sendBeacon or keepalive fetch call, and not only when the session expires or the view map is evicted. The unload can be cancelled by a leave confirmation. It also physically removes the view state of the view from the implementation’s store, which reduces the risk of ViewExpiredException on the other views of the user. Its extra element, saveInViewState, stores the whole bean in the view state (client state saving only, and the Javadoc cautions against it). The standard scope, its limits and the comparison are in the scopes page; what this page adds is a measurement.

The scratch run navigated headless Chrome from a page that used one bean of each kind to another page:

@RateLimit

@RateLimit (since 5.0) limits how often a method of a CDI bean may run per client, using a sliding window. It is an interceptor binding; the default client identifier is the client’s IP address.

package org.example.bookshelf.web;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Named;
import org.omnifaces.cdi.RateLimit;

@Named
@ApplicationScoped
public class ReviewApi {
    private int saved;

    /** At most 2 calls per client address and 60 seconds. */
    @RateLimit(maxRequestsPerTimeWindow = 2, timeWindowInSeconds = 60, maxRetries = 0)
    public String submit() {
        saved++;
        return null;
    }

    public int getSaved() { return saved; }
}

Source: OmniFaces 5.5.5 API: RateLimit and OmniFaces showcase: RateLimit

Four posts of the form through a button bound to reviewApi.submit: the first two ran (saved=1, saved=2), the third and fourth answered HTTP 500 and the log recorded RateLimitExceededException: Rate limit exceeded for client ID '0:0:0:0:0:0:0:1' (the IPv6 loopback address of the test client). That is the default: the interceptor throws, and the exception handling of your application decides what the user sees (a mapping for the exception in error-page or a handler, see the error pages section). The element maxRetries waits and retries instead of failing at once.

The default client id can be forged. Faces.getRemoteAddr(), which @RateLimit uses, takes the first address of the Forwarded, X-Forwarded-For or X-Real-IP request header when one is present, and the request address only when none is. With the limit above exhausted, five more posts from the same machine, each with a different X-Forwarded-For: 10.0.0.n header, all succeeded (saved=3 to saved=7). A rate limit keyed on the default can therefore be bypassed by any client that can send a header. Either run the application behind a proxy that overwrites those headers (and reaches the application only through it), or set clientId explicitly to something the client cannot choose: the authenticated user name or the session id.

Behind the limit, the same caution applies to Servlets.getRemoteAddr wherever else you use it for logging or access decisions.

What the table shows is what the o: tags are for:

  • o:viewParam has a stateless mode. The standard parameter converts, validates and updates the model on every postback, so a required parameter that the form does not carry makes the postback fail (the MyFaces cell above) and a view scoped bean is overwritten. o:viewParam keeps the submitted value in the component and skips conversion, validation and the model update after the first request. Choose a view scoped bean to hold the value, as above: with a request scoped bean the postback finds nothing in the model (the same button bound to load() found id null and failed with a NullPointerException).

  • An absent parameter. The Javadoc says that Faces 2.3 repaired the standard tag, and that the OmniFaces fix now matters only when jakarta.faces.INTERPRET_EMPTY_STRING_SUBMITTED_VALUES_AS_NULL is true. On 4.1 the standard page in the run reported its required error normally; the stateless mode is the remaining reason.

  • o:viewParam also gives a default label (its name), accepts a default value for an absent parameter, and does not turn a null model value into an empty parameter in generated links (includeViewParams).

  • o:viewAction evaluates if late. The standard action evaluates if in Apply Request Values, before the view parameter has reached the model, so if="#{viewParamBean.id ne null}" saw null on the GET and the book was never loaded (loads=0 above). o:viewAction evaluates it in Invoke Application, after conversion, validation and the model update. With immediate="true" it behaves like the standard one. Its message attribute adds a flash warning if the action redirects.

  • o:viewParamValidationFailed decides what a failure means. In f:metadata it applies when any view parameter failed; nested in one view parameter it applies to that one only and takes precedence. With sendError="400" it sends an HTTP status (and a page from <error-page> if you declared one); with sendRedirect="login.xhtml" it redirects with the message as a global flash error. message overrides the text. It works with any conversion or validation, Bean Validation included. A redirect always has the status of the redirect; to answer another status, use sendError and an error-page.

Behind the tags, a page that is reached by path instead of query parameters (/book/123) uses o:pathParam and @Param(pathIndex) with FacesViews (FacesViews: Extensionless URLs, MultiViews and Dynamic Routes). Three more input components belong to the same family and were only read, not run: o:hashParam (the fragment after #, kept in sync with a model value by window.onhashchange and every Ajax response), o:scriptParam (the result of a JavaScript expression that the client evaluates and sends, for the time zone offset or the screen width) and o:componentIdParam (renders only the components named by a GET parameter, for mashups). All three put client-controlled data in the model; validate it like any request parameter.

Choosing. A single lookup of a record by id is a good fit for @Param (@Param, @Cookie and @ContextParam: Injecting Request Data). A page that must reject a bad or absent parameter before anything runs, and that posts back, is a good fit for the OmniFaces tags above.

Validators: o:validateBean and the Multi-Field Family

Bean Validation (see the Bean Validation page) validates one property at a time during Process Validations, because that is how Faces works: a model is updated only after all inputs are valid. Two needs fall outside: switching validation off for one button, and validating a constraint that spans several properties of one object. o:validateBean serves both, and the o:validateXxx components do the same for plain inputs without a bean.

o:validateBean: per component and per class

Per component, it is disabled and validationGroups on a command or an input, where the standard f:validateBean offers one setting for a whole form or request:

ValidPeriodValidator.java, tolerant of missing dates (the constraint reports them)
package org.example.bookshelf.validation;

import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;
import org.example.bookshelf.model.BorrowRequest;

public class ValidPeriodValidator implements ConstraintValidator<ValidPeriod, BorrowRequest> {

    @Override
    public boolean isValid(BorrowRequest request, ConstraintValidatorContext context) {
        if (request.getFrom() == null || request.getTo() == null) {
            return true; // the @NotNull constraints of the same group report missing dates
        }
        return request.getFrom().isBefore(request.getTo());
    }
}

The mechanism matters because it has consequences. Faces updates the model only when all inputs are valid, so to validate the object OmniFaces first makes a copy of the bean, sets the submitted values on the copy and validates there; if the validation passes, the original is updated. The copy is made with the first strategy that works: Cloneable, Serializable (as BorrowRequest is), a copy constructor, or a new instance; the copier attribute names another one. Where copying is impossible, method="validateActual" updates the model and validates after Update Model Values, with the disadvantages the Javadoc lists: the invalid values stay in the model and the action runs anyway, so it must check FacesContext.isValidationFailed(). The tag collects the values before Process Validations and checks the constraints after it.

Where the message goes is controlled by showMessageFor: @form (the default, on the form’s client id), @all, @global, a list of client ids, or @violating, which puts each violation on the input whose property it concerns and falls back to the form. messageFormat (3.12) overrides the site-wide jakarta.faces.validator.BeanValidator.MESSAGE format for this tag; its {0} is the message and {1} the labels. Give the inputs labels (o:outputLabel, The o: Tags, Component by Component) so that the messages of the individual properties name the field.

Four rules from the Javadoc decide whether they behave:

  • Placement is the priority. The validators validate when the tree walk reaches them. A validator placed after all its inputs runs after their own converters and validators, and is skipped if one of them failed. A validator placed before them runs first and, if it fails, their own converters and validators do not run. Placing it between the inputs is discouraged because only the preceding inputs are converted. Put it at one end.

  • It always runs in Process Validations, cannot be made immediate, and is skipped entirely when an immediate="true" command calls renderResponse().

  • A disabled, read-only or non-rendered input contributes its model value, so the validator can compare against existing data.

  • disabled takes an EL expression that is evaluated per request. The Javadoc example is disabled="#{param.validationDisabled}". Do not copy that: a condition the client controls is a switch for the client to turn your validation off. Use a server-side condition.

o:requiredCheckboxValidator fixes a different bug: a required="true" on h:selectBooleanCheckbox never fails, because an unticked box is coerced to false, not to null. Nested in the checkbox, with a requiredMessage, it fails when the box is not ticked. The run showed Tick to accept for the unticked box. The standard tags and the standard approach to cross-field validation (a postValidate listener, f:validateWholeBean) are in the validators page; the OmniFaces family is the no-Java version of the first.

Behind both: org.omnifaces.util.Validators runs Bean Validation programmatically (validateBean(bean, groups), resolveViolatedProperty) when a service has to validate by hand.

What this teaches about SelectItemsConverter and toString():

  • The toString() is the wire format. Every option’s value in the HTML source is the string form of the entity, here all five fields of the record, visible to anyone who views the page source. A toString() that contains sensitive data (a price paid, a note, a personal field) leaks it into the page. Either write a toString() that holds only the id (Book[id=2], the pattern the Javadoc recommends) or subclass the converter and override getAsString (the Javadoc shows it), or use the index converter, which exposes nothing.

  • It must be unique and stable. Two different entities with the same string would be confused, and an entity whose string changes between the render and the postback (a field edited in between) no longer matches.

  • It needs the same list on the postback. The converter looks the string up in the items of the component, which are evaluated again on the postback. A list that is not the same on both requests (a request scoped bean with a changing query) breaks the match; the index variant is the more fragile to a list that changes.

  • equals() and hashCode() of the entity must still be right for Faces to select the right option on render.

An ImplicitNumberConverter limit on user input. The scratch run showed that the converter fails on input that the other converters accept. When the submitted text lacks the symbol, the converter builds the string with Matcher.replaceAll using the submitted value as the replacement; a submitted $1 (for a field with currencySymbol="€" or for a percent field) ended in HTTP 500 on both implementations, with IndexOutOfBoundsException: No group 1 in the log. The percent case worked on both. Treat the currency mode as unverified on MyFaces, and write your own converter, or validate the text first, when a currency field is public. This is an observation on 5.5.5, not documented behaviour; test it again on the version you use.

o:outputLabel, o:highlight and o:messages: feedback that names the field

o:outputLabel is an h:outputLabel that sets its own value as the label of the input in for, so the validation message names the field the user saw. In the run, with an empty title the message read Book title: Validation Error: Value is required., taken from the label text, and not from a generated id. o:highlight adds an error style class to every invalid input and its label and focuses the first invalid one; one per page, ideally in the master template. The markup it produced for the failed title was a script, OmniFaces.Highlight.apply(["form:title"], 'error', true);, and you write the CSS (input.error {...}); styleClass and focus configure it. The class is removed again when the user starts to use the field. o:messages is in The Messages Utility and o:messages.

o:skipValidators and o:ignoreValidationFailed: buttons that do not need a valid form

Both are tag handlers that go inside a command (or an Ajax-capable component) and change how a failure is treated. o:skipValidators skips validation entirely for that action: converters still run and the model is still updated. o:ignoreValidationFailed lets the action run even though validation failed (inside an o:form; with Ajax, the form must be in the execute list), updating only the inputs that passed. In the run, with the required title empty and author set:

  • the ordinary button redisplayed the form with Book title: Validation Error: Value is required. and did not run the action;

  • the button with o:skipValidators ran its action (log=skip) and showed no message;

  • the button with o:ignoreValidationFailed ran its action (log=ignore(null/Ada): title still null, author updated) and still showed the message.

Use them for "add a row", "save as draft" and "cancel" buttons. Compare the standard answer, immediate="true", and its consequences in the lifecycle page; these tags do not skip the Update Model Values phase the way immediate does. The validators of a skipped action are skipped: an action that processes the model must validate it by itself.

o:enableRestorableView: an expired view that can be rebuilt

An expired view makes a postback fail with ViewExpiredException (see the state saving page and the exception handling page). <o:enableRestorableView/> in f:metadata makes OmniFaces rebuild the view from scratch when the state is missing and the request is a postback. The view comes back exactly as it was on the first GET, so changes made since then (conditionally rendered parts, a view scoped value) are lost: the page must work with a request scoped bean. Two pages differed in the run only by this tag, and posted the form with a view state that the server had never issued:

  • the page with the tag answered HTTP 200 and ran the action, on Mojarra and on MyFaces;

  • the page without it answered HTTP 500 (the unhandled ViewExpiredException) on both.

The Javadoc suggests <f:view transient="true"> instead where it fits, because it keeps no state at all (stateless views). Rebuilding an expired view also means that a request that carries a forged or stale state is accepted as a fresh view; that is the whole point, and it limits the use to pages where a replayed form is harmless. Do not put it on a page that performs a state-changing action protected only by the view state (the CSRF section).

o:cache: caching a rendered fragment

o:cache stores the rendered markup of its children and serves it without evaluating the beans behind it, for time seconds. The default scope is session (one copy per user); scope="application" shares one copy among all users. The key defaults to the view id plus the client id of the component (the Javadoc warns that a client id can change when the view changes dynamically, so set key yourself in that case); reset drops the entry and disabled switches the component off; o:cacheValue caches a single value like c:set. Capacity and lifetime defaults come from the context parameters org.omnifaces.CACHE_SETTING_SESSION_MAX_CAPACITY, org.omnifaces.CACHE_SETTING_SESSION_TTL, org.omnifaces.CACHE_SETTING_APPLICATION_MAX_CAPACITY and org.omnifaces.CACHE_SETTING_APPLICATION_TTL, and the implementation from org.omnifaces.CACHE_PROVIDER.

The scratch page cached.xhtml has three caches around request-driven content: one with scope="application", one with the default scope, one around a form. A bean printed the request parameter u:

  • Alice requested ?u=alice and the application cache stored user=alice. Bob, a different client with a different session, requested ?u=bob and was served user=alice by the application cache and user=bob by the session cache. This is the leak: whatever the first visitor caused to be rendered, every later visitor gets.

  • The counter result: the first fragment evaluation printed a number from a bean counter and the second request of the same session served the same number (the bean was not asked again), on Mojarra and on MyFaces.

  • The cached form broke. On the second request Mojarra served the form with the literal text ~com.sun.faces.saveStateFieldMarker~ where the view state field belongs, and MyFaces served the jakarta.faces.ViewState field of the first request, again on every hit. Neither form can be posted back successfully.

The rules that follow: a fragment that depends on the user (a name, a price list, a menu by role, a token) must never be cached in application scope; keep the default session scope for per-user fragments, and for application scope cache only content that is identical for all users and does not change between requests. Never put a form, or anything that contains view state or a CSRF token, inside o:cache.

Three of the functions are for security-sensitive places, and one is a trap:

o:graphicImage and @GraphicImageBean

The standard h:graphicImage shows a file served as a Faces resource. An image from a database (a book cover) needs a servlet. o:graphicImage accepts a byte[] or an InputStream in its value, and the library serves it through a resource URL, without a servlet. A bean whose methods return the image bytes is marked @GraphicImageBean, a stereotype that makes it a named application scoped bean (the annotation implies @Named and @ApplicationScoped).

CoverBean.java
package org.example.bookshelf.web;

import java.awt.Color;
import java.awt.Graphics2D;
import java.awt.image.BufferedImage;
import java.io.ByteArrayOutputStream;
import java.io.IOException;
import java.io.UncheckedIOException;
import javax.imageio.ImageIO;
import org.omnifaces.cdi.GraphicImageBean;

/** A GraphicImageBean exposes its methods to o:graphicImage as images, with no servlet. */
@GraphicImageBean
public class CoverBean {
    public byte[] cover(long id) {
        System.setProperty("java.awt.headless", "true");
        BufferedImage image = new BufferedImage(60, 90, BufferedImage.TYPE_INT_RGB);
        Graphics2D g = image.createGraphics();
        g.setColor(new Color((int) (id * 60) % 255, 90, 160));
        g.fillRect(0, 0, 60, 90);
        g.dispose();
        ByteArrayOutputStream out = new ByteArrayOutputStream();
        try {
            ImageIO.write(image, "png", out);
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
        return out.toByteArray();
    }
}

An unknown bean or method in the URL (OtherBean_secret.png.xhtml) answered 404, and so did a non-numeric argument for a long parameter.

The security consequence. The Javadoc states that @GraphicImageBean "basically enables endusers to invoke any public method returning a byte[] or InputStream on the bean by just a HTTP GET request." The scratch run fetched ...CoverBean_cover.png.xhtml?ln=omnifaces.graphic&v=0&p=3 with no session cookie and received the image, and any p that the method accepts can be requested. That makes every public image method of the bean a public, guessable URL. Rules that follow:

  • Put only methods on the bean that are meant to be public, and give a private image its own check: authenticate and authorise inside the method (the caller, from an injected SecurityContext or the request), or serve it through a protected servlet instead. This part was not run; the point is that nothing in the URL carries a session.

  • Never return a file path, a name or any other user-supplied string from such a method as a way to choose a file; a method that opens a file from its argument turns the URL into a file reader.

  • Choose identifiers that cannot be guessed where the images are confidential, and set the lastModified or a version so that a changed cover is not cached for a week.

Before @GraphicImageBean (OmniFaces 2.5) the bean could be any @Named @ApplicationScoped bean; the Javadoc explains that after a server restart the images stop working until a Faces page has referenced the method once, because of exactly the security restriction above.

Three security notes:

  • The CDN handler does not validate the URL (Javadoc). It is a context parameter, so only the deployer controls it; but a URL taken from user-editable configuration turns your pages into a script injection point. Pin versions in the URL, and prefer self-hosting or a CDN with Subresource Integrity (the resources have no integrity here) for scripts.

  • The crossorigin="anonymous" attribute makes the request cookie-less, which is what you want for a CDN; the Javadoc shows overriding it per resource with a passthrough attribute (a:crossorigin="use-credentials") only when the CDN needs the cookies.

  • The versioned handler is a cache buster, not a security control: it makes a changed resource visible at once. Its version can be an EL expression such as #{environmentInfo.version}, so deployments change it without editing the pages.

Filters and security. FacesViews reaches a view in two ways: by wrapping the request and continuing the chain (the MultiViews /search/dune/2 case) or by forwarding (dynamic routes and the redirects). A forward bypasses the filters that are mapped for the default REQUEST dispatcher. The scratch run mapped a @WebFilter("/*") that set a header:

  • by default the header was present for /search/dune/2 and absent for /books/1/reviews (a dynamic route), /books/1, and the redirects;

  • with org.omnifaces.FACES_VIEWS_FILTER_AFTER_DECLARED_FILTERS set to true, the header was present on all of them.

This is the documented behaviour (the Javadoc says the FacesViews filter is first in the chain by default), and the consequence is the point: an authentication or authorisation filter, a CSRF filter or a security-headers filter that is mapped as usual can be skipped on part of the application. Either set the parameter, or protect by security-constraint (which the container applies before any of this, 403 above), or declare the filter for FORWARD too. Check every protection you rely on with a request to a dynamic route. Also keep in mind that the constraint pattern must match the URL as FacesViews serves it: /admin/panel.xhtml does not constrain /admin/panel (the pitfall of the security page); use /admin/*.

FileServlet: Serving Files From Outside the WAR

Uploads and media belong outside the web application, and the default servlet cannot serve them. org.omnifaces.servlet.FileServlet is an abstract servlet that does the work properly: ETag, If-None-Match, If-Modified-Since, Range and If-Range (needed by media players to seek and by downloads to resume). You override getFile(request):

MediaFileServlet.java
package org.example.bookshelf.web;

import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServletRequest;
import java.io.File;
import java.io.IOException;
import java.nio.file.Path;
import org.omnifaces.servlet.FileServlet;

/** Serves files below one folder, with Range and ETag support, and refuses anything outside it. */
@WebServlet("/media/*")
public class MediaFileServlet extends FileServlet {
    private static final long serialVersionUID = 1L;

    private Path folder;

    @Override
    public void init() {
        // A real application reads this from configuration, not from code.
        folder = Path.of(System.getProperty("bookshelf.media", "media-data")).toAbsolutePath().normalize();
    }

    @Override
    protected File getFile(HttpServletRequest request) {
        String pathInfo = request.getPathInfo();

        if (pathInfo == null || pathInfo.isEmpty() || "/".equals(pathInfo)) {
            throw new IllegalArgumentException(); // answered with HTTP 400
        }

        Path file = folder.resolve(pathInfo.substring(1)).normalize();

        if (!file.startsWith(folder)) {
            throw new IllegalArgumentException(); // outside the folder: HTTP 400
        }

        return file.toFile();
    }
}

Source: OmniFaces 5.5.5 API: FileServlet and OmniFaces showcase: FileServlet

The run, on Mojarra: /media/readme.txt answered 200 text/plain; a missing file 404; /media/ 400 (the IllegalArgumentException); /media/..%2f..%2fetc/passwd 400 from Tomcat before the servlet; a request with Range: bytes=0-99 for a 20,000-byte file answered 206 with Accept-Ranges: bytes. The default response also carried Cache-Control: public,max-age=2592000,must-revalidate (30 days, public) and Content-Disposition: inline.

Two changes follow for anything that is not a public cover image. The servlet serves exactly the file you return and does no confinement of its own, and the Javadoc example builds new File(folder, pathInfo); the class above resolves, normalises and checks the prefix, which is the minimum (also resolve symbolic links with toRealPath() if the folder may contain any; not run). And a response that is public for 30 days may be stored by shared caches, so override getExpireTime and the headers for files that only some users may see, and authorise inside getFile (return null for 404, throw IllegalArgumentException for 400). Also override isAttachment and getContentType for user-supplied files, so that an uploaded HTML or SVG file is delivered as a download or with a safe content type and not as active content of your origin (the upload validation section).

Where the Books Are Outdated

None of the eight books that this section consulted covers OmniFaces 4 or 5: the newest of them, the second edition of the PrimeFaces cookbook, dates from May 2015, and the others from 2004 to 2014. They solve by hand, or by other libraries, problems that OmniFaces now solves, and some of what they teach is no longer possible or no longer safe. Taking the topics that the books treat and that this page covers:

  • Helper code around FacesContext. The books that work with FacesContext and ExternalContext directly (Mann on the context objects, the JSF 2.0 reference of Burns and Schalk, Leonard’s recipes) leave the reader to write the shortcuts for parameters, messages, redirects and file downloads in every project. Faces, Messages, Servlets and Ajax are those shortcuts, maintained, with Ajax-aware redirects (The Utility Classes: Faces, FacesLocal and Friends).

  • Selecting objects and converters. The converter chapters (Leonard on standard and custom converters, Burns and Schalk) write one converter per entity, which usually queries the database on every postback. SelectItemsConverter needs none (Converters).

  • Request parameters. Books written for JSF 2.x inject a parameter with @ManagedProperty from javax.faces.bean, which was removed in Faces 4.0. @Param (@Param, @Cookie and @ContextParam: Injecting Request Data) is the replacement, with conversion, validation and messages the old annotation never had.

  • Custom handlers. The extension chapters (Burns and Schalk on PhaseListener, ExceptionHandler, ViewHandler and factories; Leonard on custom resource handlers and the JSF 2.0 ExceptionHandler; Jonna on Ajax error handling and resource optimisation) end in code you write yourself. The finished versions are FullAjaxExceptionHandler, CombinedResourceHandler, VersionedResourceHandler and CDNResourceHandler (Exception Handlers, Resource Handlers and Renderers).

  • Pretty and bookmarkable URLs. Leonard’s view parameter and pretty URL recipes, and the PrettyFaces library, belong to JSF 2.0; FacesViews and the extensionless mapping of Faces 4.0 serve the need today (FacesViews: Extensionless URLs, MultiViews and Dynamic Routes, View Parameters Done Right: o:viewParam, o:viewAction and Friends).

  • Push. PrimeFaces Push on Atmosphere (Çalışkan and Varaksin) was removed in PrimeFaces 7.0; the answers are o:socket and f:websocket (Push: o:socket, o:sse and o:notification).

  • Cross-field validation. The validation chapters (Leonard on cross-field validation, Burns and Schalk, Dudney and others) write a custom validator for "password equals confirmation"; o:validateEqual, the rest of the family and class-level o:validateBean replace them (Validators: o:validateBean and the Multi-Field Family).

  • Libraries that ended. RichFaces, Tomahawk, Trinidad, Seam 2 and PrettyFaces appear in Leonard’s recipes and in Burns and Schalk; they ended, and PrimeFaces with OmniFaces and the standard features is the maintained route.

  • Everything before Faces 2.3 and Jakarta. javax.faces.* imports, http://java.sun.com/jsf/* namespaces and JSP views in all of them; OmniFaces 4 and 5 use jakarta.* and, from 5.0, one URN namespace (Installing OmniFaces).

Common Mistakes

Security first, then correctness.

  • Trusting Faces.getRemoteAddr() or the default of @RateLimit. Both take the client address from the Forwarded, X-Forwarded-For or X-Real-IP header when present; a client that sends a different one each time defeats the limit (OmniFaces @ViewScoped and @RateLimit). Behind a proxy that overwrites the header, fine; otherwise give clientId.

  • Public image methods in a @GraphicImageBean. Every public method that returns byte[] or InputStream is a public GET URL with a guessable parameter (o:graphicImage and @GraphicImageBean).

  • o:cache with scope="application" for anything user-specific, or around a form (The o: Tags, Component by Component).

  • o:enableRestorableView on a page whose action changes data with only the view state as protection (The o: Tags, Component by Component).

  • Filters that FacesViews skips. Security filters mapped only for REQUEST do not run for dynamic routes and redirects unless FACES_VIEWS_FILTER_AFTER_DECLARED_FILTERS is set (FacesViews: Extensionless URLs, MultiViews and Dynamic Routes).

  • FileServlet without confinement, and with the default public 30-day cache (FileServlet: Serving Files From Outside the WAR); Faces.sendFile with a user-chosen name (The Utility Classes: Faces, FacesLocal and Friends).

  • Conditions the client controls. disabled="#{param.x}" on a validator, a CDN URL in user-editable configuration, a path or channel name from a request (Validators: o:validateBean and the Multi-Field Family, Resource Handlers and Renderers, Push: o:socket, o:sse and o:notification).

  • escape="false" on o:messages and o:printStackTrace on a page a user can see (The Messages Utility and o:messages, The o: EL Functions (formerly of:)).

  • A toString() that holds more than an id under SelectItemsConverter: all of it goes into the page source (Converters).

  • Parameters that arrive unchecked. @Param path segments, @Cookie values, o:scriptParam and o:hashParam are client data; validate them (@Param, @Cookie and @ContextParam: Injecting Request Data).

  • A @Param message that never shows because the bean was created after the messages component rendered; use @Eager(viewId = ...), not requestURI, which fails without a FacesContext (@Param, @Cookie and @ContextParam: Injecting Request Data).

  • Mixing up the two @ViewScoped annotations and the two @Startup annotations: jakarta.faces.view.ViewScoped against org.omnifaces.cdi.ViewScoped, jakarta.ejb.Startup against org.omnifaces.cdi.Startup (@Eager and @Startup).

  • The jar in the wrong place or twice (Installing OmniFaces); old namespaces that disappear in 6.x (Installing OmniFaces); @Param without @Inject that is deprecated since 5.4 (@Param, @Cookie and @ContextParam: Injecting Request Data).

  • o:socket and o:sse in one view on Mojarra (Push: o:socket, o:sse and o:notification); o:implicitNumberConverter for public currency input (Converters).

  • Placing a multi-field validator between its inputs (Validators: o:validateBean and the Multi-Field Family).

  • Treating sec:authorize as access control. It hides links; the constraint must exist on the server (The sec: Tags (Jakarta Security)).
