Performance

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Faces 4.1 (API jakarta.faces-api 4.1.2, part of Jakarta EE 11) with Eclipse Mojarra 4.1.17 and Apache MyFaces Core 4.1.4, Java 17 or later (the examples were compiled with --release 21), PrimeFaces 16.0.0, OmniFaces 5.5.5 and Apache JMeter 5.6.3 (the current release on the JMeter download page on 2026-10-08). Faces 4.0 is expected to behave the same for everything below (only 4.1 was run), except where What Changed in Which Version says otherwise. The examples were deployed as an exploded Bookshelf WAR on Apache Tomcat 11.0.26 with Weld 6.0.4.Final, once with Mojarra and once with MyFaces, and driven with scripted HTTP requests and, for Ajax, a headless Chrome (all observed on 2026-10-08). The project stage was Production unless a section says otherwise. Sizes and counts quoted below are exact for that setup. Timings are not: they come from a single-threaded loop on the loopback interface against pages of a few hundred components, so they only show a direction. For numbers you can quote, load test your own application as described in Load Testing with JMeter. Claims taken from an implementation’s documentation and not run are marked as such. Faces 5.0 is still a milestone release at the time of writing and nothing here describes it as current behaviour.

Performance work on a Faces application is mostly about doing less. Faces is a stateful framework: every request restores a component tree, runs it through the six lifecycle phases, renders it and saves its state again. The costs therefore scale with the size of the tree, with the amount of state that has to be saved, with how often your own code is called while that happens and with how many bytes travel to the browser. Each section below takes one of these, shows how to see it, and gives the cheapest fix. The first rule comes before all of them: measure before you change anything, because the usual bottleneck is not Faces but the database query behind a getter (the PrimeFaces documentation says the same about its own components).

Run in Production Stage

The cheapest speed-up is a context parameter (the stages are described on the configuration page). In the Development project stage Faces re-checks every view file on every request so that you can edit a page and reload, shows detailed error pages. None of that belongs on a server that real users use.

Production-ready context parameters (web.xml)
<context-param>
    <param-name>jakarta.faces.PROJECT_STAGE</param-name>
    <param-value>Production</param-value>
</context-param>
<context-param>
    <param-name>jakarta.faces.FACELETS_REFRESH_PERIOD</param-name>
    <param-value>-1</param-value>
</context-param>
<context-param>
    <param-name>jakarta.faces.FACELETS_SKIP_COMMENTS</param-name>
    <param-value>true</param-value>
</context-param>

Source: Jakarta Faces 4.1 specification, 11.1.3 Application Configuration Parameters and Mojarra 4.1 context parameters

  • jakarta.faces.PROJECT_STAGE takes Development, UnitTest, SystemTest or Production. Mojarra’s reference lists Production as the value used when the parameter is absent, and the Jakarta EE Tutorial shows the parameter being set in web.xml.

  • jakarta.faces.FACELETS_REFRESH_PERIOD is the number of seconds between two checks of a view file on disk. The declared default is 0, which means "check on every request". Mojarra’s reference says the runtime itself applies -1 (never check) when the stage is Production and the parameter is not set; the MyFaces reference gives the default as "0, -1 in Production". Setting -1 explicitly makes the intent visible and does not depend on the stage.

  • jakarta.faces.FACELETS_SKIP_COMMENTS drops XML comments (<!-- ... -->) while compiling the view, so they are not sent to the browser. With the parameter off, every comment in a template is delivered to every visitor. See the Facelets page.

  • jakarta.faces.FACELETS_BUFFER_SIZE is the number of bytes the response is buffered with while a view is rendered (default 1024, -1 leaves the response’s own buffer alone). A larger buffer flushes less often and, as the Mojarra reference puts it, makes sure an error cannot arrive after the response was partly sent; the price is memory per concurrent request.

  • Mojarra only: com.sun.faces.disableIdUniquenessCheck (false, true or auto) skips the walk that verifies that every component id in a naming container is unique. auto skips it in the Production stage. MyFaces has a similar switch, org.apache.myfaces.CHECK_ID_PRODUCTION_MODE (true, auto, false; auto checks only components that do not wrap markup). Both are documented by the implementations; the effect was not measured here.

A last measurement for the case you are weighing up. The same three Bookshelf pages (300 components, a 300-row ui:repeat and 300 rows of plain markup, all described in Component Tree Size) were requested 500 times in a loop in each stage. On the loopback interface and with server state, the Development stage was between about 1.2 and 4 times slower than Production on both implementations, and the gap was the largest on MyFaces. The ratio depends on page size and on the file system; the lesson is only that the stage matters.

Source: Mojarra 4.1 context parameters, Apache MyFaces Core 4.1 configuration

Component Tree Size

Every Faces tag that has a component behind it (h:outputText, h:inputText, h:panelGroup, f:facet children and so on) becomes a UIComponent in the tree for as long as the view lives. The tree is built when the page is first requested and rebuilt, in part, on each postback; every component takes part in every lifecycle phase it is not skipped for, costs memory in the saved state (see State Saving: Partial, Full, Server, Client) and produces markup. Two pages that look the same in the browser can differ by an order of magnitude in tree size.

The Bookshelf scratch app has three pages that print 300 labelled text boxes. They use one binding (#{bulkEditBean.title}) so only the structure differs:

tree-forEach.xhtml: c:forEach builds 300 times two components
<h:form id="f">
  <c:forEach begin="1" end="300" var="i">
    <h:outputText value="Row #{i}"/> <h:inputText value="#{bulkEditBean.title}"/><br/>
  </c:forEach>
  <h:commandButton id="go" value="Save" action="#{bulkEditBean.save}"/>
</h:form>
tree-repeat.xhtml: ui:repeat keeps one template, repeated at render time
<h:form id="f">
  <ui:repeat value="#{bulkEditBean.rows}" var="row">
    <h:outputText value="#{row}"/> <h:inputText value="#{bulkEditBean.title}"/><br/>
  </ui:repeat>
  <h:commandButton id="go" value="Save" action="#{bulkEditBean.save}"/>
</h:form>
tree-html.xhtml: plain markup inside the same ui:repeat
<h:form id="f">
  <ui:repeat value="#{bulkEditBean.rows}" var="row">
    #{row} <input type="text" name="x"/><br/>
  </ui:repeat>
  <h:commandButton id="go" value="Save" action="#{bulkEditBean.save}"/>
</h:form>

The HTML sizes are with server state (where the state field is 32 to 41 characters on both implementations, a lookup key). Three observations. The tree-html page is the smallest and was the quickest in every timing loop on both implementations, because it creates only the form, the button and the ui:repeat. The tree-forEach page was the slowest in all but one of the loops and is the one JSTL tags are blamed for: c:forEach runs while the view is built, so it creates all those components (see the JSTL page for the correctness side of that choice). And the client state sizes cross over between the implementations: the page with 300 real components has a small state on Mojarra and a large one on MyFaces, while the ui:repeat page is the reverse. I did not investigate why; the practical lesson is to measure the state of your own pages with the implementation you deploy.

What shrinks a tree:

  • Iterate with a template, not with a loop of components. ui:repeat and h:dataTable hold one set of child components and re-run it per row (see the comparison). A table with rows="25" renders 25 rows, whatever the size of the list behind it.

  • Use markup where you need no component. Static HTML, EL in template text and passthrough elements add nothing to the tree. The PrimeFaces documentation advises plain EL in the page instead of h:outputText when you need neither converters nor the output tag’s other features, and a plain div instead of p:outputPanel. A plain div that Ajax has to update can be made addressable with a passthrough attribute (<div faces:id="...">); see the HTML5 friendly markup page. Keep h:outputText where you want its features: the page on EL in template text explains what escaping you get.

  • Do not build what the user cannot see. A rendered="false" component is still built and still saved, but it is skipped by decode, validation, model update and encoding. The scratch run confirmed the decode part on both implementations: a forged value posted for an input inside a rendered="false" group never reached the setter. Content that is rarely shown (tabs, dialogs, details) is better loaded on demand; see PrimeFaces: Lazy Loading, Caching and Settings for dynamic="true".

  • Split the page. Several small views joined by navigation or Ajax (render targets) cost less than one view carrying every widget the application has.

  • Keep a whole view stateless if it has no postback state to keep (State Saving: Partial, Full, Server, Client).

Getter Cost

Faces evaluates an expression every time it needs its value: a rendered attribute is read in several phases, the value of a table is read per phase and a getter used in three places on the page is called three times or more. The page that calls #{bean.books} therefore calls getBooks() several times per request. Putting a database query, a web-service call or any other expensive work into such a getter is the best-known Faces performance mistake. The request processing page lists the phases; the data tables page observed that a table’s value is read three times before the action runs and once more to render on a postback.

The following pair of beans and views shows it. The service counts every call to catalogue(...) as a query, and a second counter counts getter calls:

QueryInGetterBean (the anti-pattern)
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;
import org.example.bookshelf.service.HitCounter;

/** The anti-pattern: the getter queries every time Faces or the page calls it. */
@Named
@RequestScoped
public class QueryInGetterBean {

    @Inject
    BookService service;
    @Inject
    HitCounter hits;

    private String filter = "";

    public List<Book> getBooks() {
        hits.hit("getter.queryInGetter");
        return service.catalogue(5);
    }

    public boolean isNoBooks() {
        return getBooks().isEmpty();
    }

    public String getFilter() {
        return filter;
    }

    public void setFilter(String filter) {
        this.filter = filter;
    }

    public String search() {
        return null;
    }
}
LoadOnceBean (the fix)
package org.example.bookshelf.web;

import jakarta.annotation.PostConstruct;
import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;
import org.example.bookshelf.service.HitCounter;

/** The fix: load once per request, expose the field. */
@Named
@RequestScoped
public class LoadOnceBean {

    @Inject
    BookService service;
    @Inject
    HitCounter hits;

    private List<Book> books;
    private String filter = "";

    @PostConstruct
    void load() {
        books = service.catalogue(5);
    }

    public List<Book> getBooks() {
        hits.hit("getter.loadOnce");
        return books;
    }

    public boolean isNoBooks() {
        return books.isEmpty();
    }

    public String getFilter() {
        return filter;
    }

    public void setFilter(String filter) {
        this.filter = filter;
    }

    public String search() {
        return null;
    }
}

Notice what the table says about the design too: even the good bean’s getter is called six to nine times on a postback. That is fine because it only returns a field.

The rules that follow:

  • A getter returns a field or a cheap derived value, nothing else. No query, no remote call, no object construction, no logging that matters.

  • Load in a place that runs once. A request-scoped bean’s @PostConstruct (as above, created at the first expression that touches the bean, see the backing beans page), an f:viewAction or an action method are such places. For data that must survive a postback without a second query, keep it in a view-scoped bean and mind its size (View Scope Size).

  • Do not return a new collection or a new DataModel per call. A table asks for its value several times per request, so a new object each time re-queries each time (the data tables page shows the stale-list bug this also causes).

  • Do not hide the cost behind a boolean. The isNoBooks() method above looks cheap and is not, because it calls the expensive getter. rendered expressions are evaluated more often than anything else.

  • Avoid computation in EL, too. The PrimeFaces documentation recommends moving inline conditions out of expressions into the bean: it is faster and easier to read. Expression syntax is on the expression language page.

  • Cache data used several times in one view in a request-scoped bean, as above. Avoid abusing session and view scopes for it (View Scope Size).

View Scope Size

A @ViewScoped bean (jakarta.faces.view.ViewScoped) lives as long as the view does and is kept in the session, in the view map of a saved view. Two things follow. Everything the bean references is held in the session for the lifetime of the view, for every open view, for every user. And the bean has to be Serializable because the container may passivate the session (the scopes page lists the passivation rules).

The commonest mistake is to keep a whole result set in the bean to avoid re-querying. The scratch bean below holds 5000 search results twice, once as entities and once as ids, and measures both with Java serialisation, which is a fair proxy for what a clustered session would have to replicate:

ResultsBean
package org.example.bookshelf.web;

import jakarta.annotation.PostConstruct;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.ByteArrayOutputStream;
import java.io.IOException;
import java.io.ObjectOutputStream;
import java.io.Serializable;
import java.util.ArrayList;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;

/** Two ways of keeping 5000 search results in view scope; the sizes are measured by Java serialisation. */
@Named
@ViewScoped
public class ResultsBean implements Serializable {

    @Inject
    transient BookService service;

    private List<Book> entities;
    private List<Long> ids;
    private String sizes = "";

    @PostConstruct
    void init() {
        entities = service.catalogue(5000);
        ids = service.ids(5000);
    }

    public String measure() throws IOException {
        sizes = "entities=" + size(new ArrayList<>(entities)) + " bytes, ids=" + size(new ArrayList<>(ids)) + " bytes";
        return null;
    }

    private static int size(Object value) throws IOException {
        ByteArrayOutputStream bytes = new ByteArrayOutputStream();
        try (ObjectOutputStream out = new ObjectOutputStream(bytes)) {
            out.writeObject(value);
        }
        return bytes.size();
    }

    public String getSizes() {
        return sizes;
    }
}

Source: Jakarta Faces 4.1 API: ViewScoped

On both implementations the same figures came back: the 5000 Book records serialise to 211,107 bytes, the 5000 ids to 70,122 bytes. Both ways are far from free (the entities are roughly 42 bytes per record, the ids roughly 14), and a view scope that holds them is paid for once for every view the user has open. The advice follows:

  • Keep ids and filters, not results. Store what is needed to repeat the query (search text, page number, sort column) and fetch the page again, or store the one selected entity’s id. A LazyDataModel (PrimeFaces: Lazy Loading, Caching and Settings) or a page-by-page DataModel loads only what the table shows.

  • Keep large read-only data out of the scope altogether. Application-scoped caches, or the request scope, are the place for data that does not belong to one view.

  • Mark what must not be saved as transient (as the scratch bean does for the injected service).

  • Know when a view bean dies. The scopes page shows that a view bean is destroyed on a navigation that builds a new view, when its view is evicted and when the session ends; a view left by a plain faces-redirect=true or a new GET is not destroyed at that moment.

  • Know the limits that bound the total. The session can hold only so many saved views and view maps. Mojarra keeps the last 15 logical views with 15 views each (com.sun.faces.numberOfLogicalViews, com.sun.faces.numberOfViewsInSession) and destroys the least recently used of 25 view maps (com.sun.faces.numberOfActiveViewMaps, default 25). MyFaces keeps 20 views (org.apache.myfaces.NUMBER_OF_VIEWS_IN_SESSION), and an evicted view takes its beans with it. The scopes page observed that a postback to an evicted view ends in ViewExpiredException, so lowering these numbers saves memory and costs users who keep many tabs open. The same page has the details.

State Saving: Partial, Full, Server, Client

Faces must restore the tree on a postback. It does so from saved view state, kept either on the server (the default, and what the jakarta.faces.ViewState hidden field then holds is a short key) or in the page itself (client state: the whole state encoded in the field). The setting is jakarta.faces.STATE_SAVING_METHOD, with the values server and client; the mechanism, the keys of client state and the cluster consequences are on the state saving page.

Partial state saving (PSS, since Faces 2.0, jakarta.faces.PARTIAL_STATE_SAVING, default true) saves only what differs from the initial state, which Facelets can rebuild by running the page again. It is the reason a restored view needs a build step at all. Disabling it (full state saving, or FSS) saves the whole tree.

Scope Ajax Requests with Execute and Render

f:ajax has two lists. execute names the components that are decoded, validated and written to the model in the request; render names the components that are encoded into the response. The common performance mistakes are execute="@form" where one input matters and render="@form" (or a distant, large container) where one text has changed: the first runs conversion, validation and every setter in the form, the second re-encodes and re-sends every component in it.

The PrimeFaces documentation says the global setting reduces network traffic; primefaces.SUBMIT was confirmed to be read by PrimeFaces 16.0.0 (its configuration class reads it), but the traffic reduction itself was not measured here.

Rules for Ajax:

  • Execute the least you can, usually @this. Then the rest of the form is neither validated nor written. This also stops an unrelated validation failure from blocking the request (see the Ajax page).

  • Render the smallest container that contains the change, with an id, instead of @form or @all. A table’s single cell or a message component is usually enough.

  • Give the page stable container ids so that a narrow render can name them. Search expressions (Search Expressions) such as @parent and @child(0) keep the targets short.

  • Group related actions on one Ajax request instead of firing several, and consider delay for per-keystroke events (the Ajax page covers delay and f:ajax disabled).

  • Prefer Ajax over a full postback for small interactions, as the PrimeFaces documentation advises, once the scoping above is right: an Ajax request that executes and renders the whole form is not cheaper than a postback.

  • Maintainability counts too: the PrimeFaces documentation itself warns to weigh readability against the last bit of speed when scoping process and update.

MyFaces: EL Caching, View Pooling and Other Switches

MyFaces has several optimisations of its own. All of them are MyFaces-only context parameters, so they do nothing (and change no behaviour) on Mojarra; keep that in mind when a team runs different servers in development and in production.

Caching EL expressions. Each time a view is built, the Facelets compiler creates the value and method expressions of the page again. org.apache.myfaces.CACHE_EL_EXPRESSIONS lets MyFaces reuse them. The valid values, from the MyFaces documentation:

View pooling. Instead of rebuilding a view for every request, MyFaces keeps a pool of views for reuse: after rendering, the view is reset to its initial state (this relies on the partial-state-saving mechanism) and parked, and the next request for the same view id, locale, render kit and contracts takes it from the pool and, for a view that has dynamic parts, refreshes only those. The MyFaces documentation reports, from tests with its demo application, about 25% less transient memory, about 9% more throughput for non-Ajax requests and 9% to 30% or more for Ajax requests depending on the tree size. Those figures are the project’s, not mine, and the documentation itself recommends the pool only where performance is a critical concern and only for the busiest views.

        <parameter>
            <name>org.apache.myfaces.VIEW_POOL_MAX_POOL_SIZE</name>
            <value>5</value>
        </parameter>
    </view-pool-mapping>
</faces-config-extension>

PrimeFaces: Lazy Loading, Caching and Settings

PrimeFaces gives one performance advice before any other: the bottlenecks are almost always in the back end and in database queries. Its toolbox follows from that.

Lazy loading of data. A p:dataTable with a plain List value holds every row in memory on every request. Binding a LazyDataModel makes the table ask for one page at a time (the PrimeFaces data components page has the full lazy model). The PrimeFaces data table documentation states the difference: regular Ajax pagination renders one page but still needs all the data in memory, a lazy table also loads only the page into memory. The model implements count and load; the table calls load on every paging, sorting or filtering. It also advises against keeping the model in a long-lived scope such as @ViewScoped (large sessions and serialisation) and shows a request-scoped bean. The example below adapts the data tables page’s BookService (its find and count methods) and was run on Mojarra with PrimeFaces 16.0.0:

CatalogueLazyModel
package org.example.bookshelf.web;

import java.util.List;
import java.util.Map;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;
import org.primefaces.model.FilterMeta;
import org.primefaces.model.LazyDataModel;
import org.primefaces.model.SortMeta;
import org.primefaces.model.SortOrder;

/** Loads one page per request from the service; nothing but the current rows is held in memory. */
public class CatalogueLazyModel extends LazyDataModel<Book> {

    private final transient BookService service;

    public CatalogueLazyModel(BookService service) {
        this.service = service;
    }

    @Override
    public int count(Map<String, FilterMeta> filterBy) {
        return service.count();
    }

    @Override
    public List<Book> load(int first, int pageSize, Map<String, SortMeta> sortBy, Map<String, FilterMeta> filterBy) {
        String field = "title";
        boolean ascending = true;
        if (!sortBy.isEmpty()) {
            SortMeta sort = sortBy.values().iterator().next();
            field = sort.getField();
            ascending = sort.getOrder() != SortOrder.DESCENDING;
        }
        return service.find(first, pageSize, field, ascending);
    }

    @Override
    public String getRowKey(Book book) {
        return String.valueOf(book.id());
    }
}

Cached output is the same for every user and every request until you clear the region, so use it only for fragments that do not depend on the user, the locale or the request, and never for anything security-relevant. The default provider has no expiry or size bound (reasoning from its description as a map; the Ehcache providers add them).

Two more PrimeFaces parameters touch the page weight. primefaces.CLIENT_SIDE_LOCALISATION is true by default in PrimeFaces 16 (the configuration table of the documentation still says false; the 14.0.0 migration guide says it became the default), which makes the pages add a script locales/locale-<language>.js for the locale of the view (observed for a Spanish request); set it to false only if the application loads or needs no client-side locale. primefaces.HIDE_RESOURCE_VERSION (false by default) drops v=16.0.0 from the URLs of PrimeFaces resources; it does not make them faster, and it removes the version that cache busting relies on (see versioning), so prefer the version in the URL unless you are hiding the library version (the parameter table, where both defaults were observed). The patterns, summarised: define process and update precisely; use plain HTML instead of Faces tags where you need no component; keep logic out of getters, EL and long-lived beans; cache data used several times in a view in a request-scoped bean; set required on inputs whose label should show the required marker instead of making p:outputLabel look the constraint up (the page says the default of indicateRequired is auto and then looks up Bean Validation constraints); and mark views you do not post back as stateless. Load Testing with JMeter

Nothing above replaces a load test. It is the only way to see how your application behaves with concurrent users, with the JIT warmed up, with real think time and with the garbage collector. Apache JMeter is the usual tool. This section covers what is specific to Faces; building plans, thread group sizing, properties and running from Maven is on the existing Performance Testing with Apache JMeter page (for Spring Boot, but the JMeter part is the same). A separate load testing page for the Java frameworks is planned in issue #260 (prose only here); the testing page has a short load-testing note, and the deployment page covers monitoring.

What makes a Faces plan different: every request carries state. A GET returns a page with a jakarta.faces.ViewState hidden field; the POST that follows must send it back or the server answers with a ViewExpiredException. So the plan has three kinds of element beyond the plain HTTP samplers:

  • An HTTP Cookie Manager, so that each virtual user keeps its session cookie. Server-side view state lives in that session.

  • A Regular Expression Extractor as a child of the GET sampler, which reads the view state out of the response body and stores it in a JMeter variable.

  • In the POST sampler, a parameter whose value is that variable, with URL encode ticked. The JMeter manual says to select it when you are unsure, and a client state value is base64 text, which contains plus, slash and equals characters.

For Ajax, the request is the same form post with these additions, as observed above for f:ajax:

  • A HTTP Header Manager entry Faces-Request: partial/ajax. Without it Mojarra 4.1.17 answered the Ajax post with the whole HTML page (text/html) rather than a partial response, while MyFaces answered with the partial response either way. Assertions make a load test meaningful: a Response Assertion on the response code, and on the text of the response (the partial response element for Ajax, a fixed text of your page for GETs, and a check that the text of your ViewExpiredException error page is absent). A test that counts only HTTP 200 will happily count error pages. See the exception handling page for how such errors are shown.

What to look at when you run it (from the JMeter best-practices page and the behaviour described above):

  • Run in CLI mode (jmeter -n -t test.jmx -l test.jtl), with as few listeners as possible and not the View Results Tree during the load, as the JMeter best-practices page advises. Keep it for debugging the script.

  • Run the application in the Production stage (Run in Production Stage), with the settings you intend to ship.

  • Give every virtual user its own session and enough think time (a timer such as the Uniform Random Timer, or the Gaussian Random Timer), and run long enough for the session count to reach a steady state: server state accumulates per session up to the limits in View Scope Size and State Saving: Partial, Full, Server, Client, and heap and garbage collection only show their cost over minutes.

  • Watch for ViewExpiredException: a user who opens more views than numberOfViewsInSession (or its MyFaces counterpart) allows loses the oldest one. A script that opens many views per virtual user without navigating away reproduces that.

  • The HTTP Request sampler can fetch embedded resources (stylesheets, scripts, images) with a concurrent pool; decide deliberately whether the test includes them, and measure the static files separately if a CDN will serve them.

  • Change one thing at a time (a context parameter, a getter, the Ajax render list) and compare the same plan before and after, on the same machine.

What Changed in Which Version

  • 2.0: partial state saving, Facelets as the standard view technology, the ResourceHandler (and with it cacheable, combinable resources), the PROJECT_STAGE parameter and FACELETS_REFRESH_PERIOD. MyFaces 2.0.8 and 2.1.2 introduced EL expression caching, and alwaysRecompile arrived in 2.1.12 (from the MyFaces documentation).

  • 2.2: stateless views (<f:view transient="true">) and jakarta.faces.SERIALIZE_SERVER_STATE (then in the javax namespace).

  • 2.3.x / 4.0.x: Mojarra added numberOfActiveViewMaps (2.3.18), refreshTransientBuildOnPSS (4.0.19) and restoreBuildTimeDecisions (4.0.23), according to its reference.

  • 4.0: the jakarta namespace and faces.js instead of jsf.js; the parameters that older material spells javax.faces.* are jakarta.faces.* from here on.

  • 4.1: full state saving is deprecated; Mojarra and MyFaces log a warning when PARTIAL_STATE_SAVING is set to false.

  • 5.0 (upcoming): the milestone releases remove deprecated APIs; this page was not checked against them. The PrimeFaces performance page mentions that a MyFaces parameter is renamed in 5.0 (USE_LAMBDA_METAFACTORY to USE_LAMBDAS_OVER_REFLECTION).

Where the Books Are Outdated

The JSF 1.x books in the bibliography (the Mann and Jacobi and Fallows titles) describe a framework in which every view saved its complete component tree; partial state saving arrived only in 2.0, which is why their warnings about page size and session size are harsher than today’s. Their tuning advice about STATE_SAVING_METHOD is still the right lever, but it now applies to a much smaller state, and full state saving is deprecated. The component-library chapters of those books (ajax4jsf, Weblets, hand-written XMLHttpRequest code) are replaced by f:ajax and the ResourceHandler, which is also where caching and combining now live.

JSF 2.0 Cookbook (2010) has recipes for testing and load-testing JSF applications and for serving resources through custom resource handlers. The advice to load test and to serve images, CSS and JavaScript as Faces resources still holds; the tools and the javax.faces code do not, and the cache headers and parameters in Resource Caching and Compression are the current form. The PrimeFaces Cookbook, Second Edition (2015, PrimeFaces 5.x) shows lazy data tables, partial submit and the cache component. Those recipes still exist in PrimeFaces 16, but LazyDataModel changed (the 16 documentation shows count and load with Map<String, SortMeta> and Map<String, FilterMeta> arguments, and builders for lambdas and JPA), partial submit is now a global primefaces.SUBMIT setting, and the cache component has a default provider and Ehcache 2 and 3 providers. Check the PrimeFaces version before copying its code. None of the books covers CDI @ViewScoped, OmniFaces 5, MyFaces view pooling or Production-stage defaults.

Pitfalls

  • Tuning without measuring. Change one setting, keep a baseline and repeat the load test. The loopback timings on this page are directions, not benchmarks.

  • Development stage in production. The per-request file checks and consistency walks are real costs; the project stage is the first thing to check.

  • Queries in getters and rendered expressions. Up to 13 queries per request on a page with five rows (see Getter Cost).

  • Entities in view scope. Memory per open view, per user (View Scope Size).

  • execute="@form" and render="@form" as a habit. Large payloads and unrelated validation failures (Scope Ajax Requests with Execute and Render).

  • Turning off partial state saving. It is deprecated and the state grew by a factor of about 1.7 to 38 in the runs above.

  • Disabling client state encryption or integrity checks to look at the state. A debugging switch is not a tuning option.

  • Copying compressViewState=false from a tuning guide with server state: it has no effect there (State Saving: Partial, Full, Server, Client).

  • Combining scripts without target="head". They are silently left alone (Combining Resources with OmniFaces CombinedResourceHandler).

  • Expecting CombinedResourceHandler to catch everything. Hard-coded <link> and <script> elements and renderer resources are not combined.

  • MyFaces view pooling without alwaysRecompile. The pool is disabled and the log says so; custom components that cannot reset themselves misbehave in a pooled view.

  • Caching a view with a view state in the browser. Use cache headers that forbid it, as with CacheControlFilter.

  • Load tests that count HTTP 200 only. A ViewExpiredException error page returns 200 on many setups; assert on content.

  • A JMeter Ajax sampler without the Faces-Request header. Mojarra then renders the full page.

  • Putting user-specific content inside p:cache. The fragment is shared by everyone.
