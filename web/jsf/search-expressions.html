Search Expressions

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Jakarta Faces 4.1 (API jakarta.faces-api 4.1.2, part of Jakarta EE 11) with Eclipse Mojarra 4.1.17 and Apache MyFaces Core 4.1.4, Jakarta Servlet 6.1 and Java 17 or later (the examples were compiled with --release 21), and, for the section on PrimeFaces, PrimeFaces 16.0.0. Search expressions were added in Faces 2.3 (the package is jakarta.faces.component.search since the move from javax to jakarta), and the specification’s change log mentions the facility only for 2.3 (and, indirectly, an Ajax change for composites in 4.0), so everything below also applies to Faces 4.0, but only 4.1 was run. Every view and class in this page was deployed as an exploded Bookshelf WAR on Tomcat 11.0.26 with Weld 6.0.4.Final, once with Mojarra and once with MyFaces (a third pair of runs added the PrimeFaces 16.0.0 jar). The Ajax behaviour was observed by loading each page in jsdom 30.1.2 with the faces.js that each implementation ships, clicking the button and reading the request that script sent and the partial response it received; the results of the SearchExpressionHandler calls were read from a Faces view that calls the handler. All of it was observed on 2026-10-08. Whatever was not run is marked as such.

When a page says render="results" or execute="@form" it uses a search expression: a string that names a component relative to the component that carries the attribute. Faces 2.3 turned what used to be a pile of per-library conventions into one specified facility with an extension point, and every standard attribute that points at another component goes through it. This page explains the grammar, the keywords, where in the request processing lifecycle an expression is resolved (which decides what it can see), what the two implementations do with the cases the specification leaves open, and how to add keywords and decorate the engine.

What a Search Expression Is

The API documentation of SearchExpressionHandler defines it: a search expression is either an identifier (matched exactly against the id property of a component), a keyword such as @this or @form, or a series of such identifiers and keywords linked by the naming container separator character, which is the colon unless jakarta.faces.SEPARATOR_CHAR says otherwise. A leading separator makes the expression absolute: the search starts at the view root. Without it the search starts at the source, the component that carries the attribute. Several expressions in one attribute are separated by spaces (and, on MyFaces, by commas; see execute and render in f:ajax).

Ids, Client Ids and Naming Containers

Two names are in play. The component id is the id you write; it has to be unique only inside the closest naming container (h:form, h:dataTable, ui:repeat, a composite component, f:subview). The client id is what the browser sees: the ids of the enclosing naming containers and the component id joined with the separator, plus the row index inside an iterating component (search:title, shelf:books:1:status). The pages on the architecture and on the HTML components work through how client ids are built; what matters here is how the two names are used:

  • A search expression written with component ids is relative to the naming container of the source. Inside <h:form id="search"> the expression title means the component search:title.

  • An expression that starts with the separator is absolute and is written with ids from the root: :search:title is the same component from anywhere in the view, and a component outside every form is :results.

  • The client ids that come out are what travel in the Ajax request. Search expressions exist so that nobody has to concatenate them by hand.

  • The separator is configurable. With the context parameter jakarta.faces.SEPARATOR_CHAR set to _ the same views rendered search_author and a relative id and an absolute expression starting with _ (_search_author) resolved to it on both implementations. Code must call UINamingContainer.getSeparatorChar(FacesContext) rather than hard-code the colon.

The specification calls the separator out in 3.2.2 (NamingContainer) and defines findComponent in 3.1.8; the latter is the ancestor of the whole facility.

Source: Jakarta Faces 4.1 specification, 3.2.2 NamingContainer and Jakarta Faces 4.1 API: UINamingContainer

The Resolution Algorithm

The handler splits an expression at the separator into commands and resolves them from left to right. The API documentation states the algorithm:

  1. If the expression starts with the separator, the base is the view root and the separator is dropped; otherwise the base is the source component.

  2. The first command is resolved starting at the base. A command that starts with @ is a keyword and is given to the keyword resolvers. Any other command is an id.

  3. Every further command is resolved starting at the component the previous command produced.

  4. A leaf keyword (@all and @none among the built-in ones) cannot be followed by anything. Both implementations throw a FacesException for @none:@form and @all:@form, and isValidExpression returns false for them.

For an id the rules of UIComponent.findComponent apply: the lookup starts at the closest naming container of the base (the base itself when it is one), and in an expression of several identifiers every identifier before the last must name a naming container. filters:isbn, with filters a plain h:panelGroup, throws an IllegalArgumentException on both implementations.

What the specification leaves open is what happens when findComponent finds nothing, and the two implementations differ. Mojarra falls back to a client-id lookup from the view root, so an id such as results (a component that is not in the form) or a full client id such as catalogue:title still resolves. MyFaces walks up through the enclosing naming containers. Both therefore accept results from inside a form, which is why render="results" works in practice even though the component lives outside the form; but they disagree about absolute client ids that contain a row index (Inside Tables and ui:repeat). The Keywords

The API documentation of SearchKeywordResolver lists the twelve keywords every implementation must support:

Keyword Meaning (from the API documentation, with what was observed)

@this

The base component: the component that carries the attribute (for a behavior, the component the behavior is attached to). In f:ajax execute this is the default.

@form

The closest ancestor form.

@all

All components in the view. A leaf. In f:ajax it is sent as @all, and the partial response updates the pseudo id jakarta.faces.ViewRoot.

@none

No component. A leaf. It is the default of render.

@parent

The parent of the base component.

@namingcontainer

The closest ancestor naming container.

@composite

The composite component the base belongs to. Outside a composite both implementations throw a NullPointerException in the handler (programmatic probe) and the page that renders such an f:ajax fails with HTTP 500.

@next, @previous

The component after or before the base among the children of the parent. They are siblings of the base, whatever type they are: a neighbouring h:outputText counts.

@child(n)

The n-th child of the base, counting from 0. When the base has fewer children the handler throws a FacesException ("has fewer children"); an n that is not a number is not recognised as the keyword at all.

@id(id)

The components with that id (an id, not a client id), found by visiting the tree below the base. See Chaining and the @id Keyword.

@root

The UIViewRoot. Meant as the start of a chain; see Chaining and the @id Keyword.

The Jakarta EE Tutorial, as of this writing, lists only four keywords for f:ajax (@all, @form, @none, @this); the specification and the API documentation have the twelve above, and the VDL for f:ajax points to SearchKeywordResolver for "the complete list of keywords".

Chaining and the @id Keyword

Chaining makes the keywords composable: @form:@child(0) is the first child of the form, @parent:isbn is the sibling named isbn reached through the parent, @composite:label is the component label inside the composite. Each step starts where the previous one ended. Five rules and pitfalls decide whether a chain works:

  • @id(x) starts at the base and looks below it. From a button it finds nothing, because a button has no children. The intuitive render="@id(results)" therefore fails: on Mojarra the unresolved token is sent to the browser as it is and the server ignores it silently (execute and render stayed @id(author) and nothing was processed); on MyFaces the page that contains the f:ajax fails to render with a ComponentNotFoundException (HTTP 500). Anchor it: @form:@id(author) or @root:@id(results) worked on both implementations (the second is in the view above).

  • The @id keyword delivers every match unless told to stop. @form:@id(note) in a test view with a repeated row returned the client ids of all three rows when called programmatically. f:ajax asks for a single component, and both implementations then used only the first row (search:rows:0:note).

  • MyFaces 4.1.4 recognises @id(x) only when the id has three or more characters. The source of IdSearchKeywordResolver tests that the command is longer than six characters (id() counts), so @id(box) works and @id(b) does not; I observed @root:@id(b) failing and @root:@id(box) resolving on MyFaces while both worked on Mojarra.

  • @root is for chains. As execute it made the server recurse until a StackOverflowError on both implementations; as render Mojarra answered with IllegalStateException: CDATA tags may not nest and MyFaces with an error response. Write @all instead of a lone @root.

  • Leaf keywords end the chain. Called on the handler, @all:@form and @none:@form throw a FacesException (message "It’s not valid to place a keyword or id after a leaf keyword" on Mojarra, "Expression cannot have keywords or ids at the right side" on MyFaces). In f:ajax, which resolves with RESOLVE_CLIENT_SIDE, the expression is treated as a pass-through keyword expression and sent on unresolved, and the request then rendered nothing: the mistake is silent on both.

When an Expression Is Resolved

This is the part that decides what an expression can express. For f:ajax the expressions are resolved while the page is rendered, not while the Ajax request is processed:

  1. During Render Response of the page that contains the f:ajax (the initial GET, a postback, or a partial response that re-renders the component), the renderer of the behavior calls the handler for every token of execute and render. Mojarra asks resolveClientId once per token; MyFaces asks resolveClientIds once per attribute. The handler returns client ids, the renderer writes them into the JavaScript call (myfaces.ab(this,event,'action','search:title search:author','results',{})), and keywords that the browser can handle itself (@all, @none, @form, and, on Mojarra only, @this) are written as they are.

  2. The Ajax request therefore carries client ids. During Apply Request Values and the later phases the PartialViewContext hands those ids to the lifecycle (getExecuteIds(), getRenderIds()); the handler is not asked again. A PhaseListener logged executeIds=[search:byId, search:title, search:author] and renderIds=[results] for the byId button, and a wrapper like the one in Decorating the Handler that logged every call to the handler logged them all before Apply Request Values and none between there and the end of the request.

  3. h:outputLabel and h:message resolve their for while they are rendered, in Render Response, in the same request that made the validation messages.

  4. A handler call from your own code resolves at the moment you make it (The SearchExpressionHandler API).

Four consequences follow, and every one of them was observed:

  • The tree that matters is the tree of the page that rendered the script. A component that is not in the tree at that moment cannot be resolved by keyword.

  • State of the postback is invisible to f:ajax expressions. A keyword such as @invalid (Custom Keywords) works in h:message for, because that attribute is resolved after validation, but in render= it would be resolved before the user has typed anything.

  • Resolution happens once per rendering of the script, not once per click. A component that a partial response re-renders gets its script resolved again: when the refresh button of the rows view below re-rendered the list, the status expressions of the three borrow buttons were resolved again while the response was rendered (Mojarra log).

  • In a PhaseListener or a bean, PartialViewContext.getRenderIds() is a list of client ids, never an expression. Use the handler if you want to resolve one.

Where this sits in the lifecycle is the Render Response phase described in the page on the request processing lifecycle (see Render Response and the partial lifecycle); execution of the ids is the job of the other phases of the partial lifecycle.

execute and render in f:ajax

The attributes are the main user of the facility; the page on Ajax covers the tag, the events and the partial lifecycle, and this section covers only the expressions in it.

  • execute defaults to @this and render to @none. The tags the keywords select take part in Apply Request Values, Process Validations, Update Model Values and Invoke Application of the Ajax request (execute) or are encoded into the partial response (render).

  • The value is either a literal of expressions separated by white space, or an EL expression that evaluates to a Collection<String> (the fromBean button above). The tokens of a literal are trimmed; extra spaces are harmless (author isbn and ` +@this + ` gave the same ids).

  • Separate expressions with spaces. f:ajax execute="author,isbn" was split by MyFaces (search:author search:isbn) but Mojarra sent the single token author,isbn, which matched nothing, so neither component was processed and no error was reported. The API documentation says that comma and space are the separator characters of the handler (getExpressionSeperatorChars, spelled as in the API), and a literal that f:ajax hands to Mojarra’s handler one token at a time never reaches that splitting.

  • Unresolvable expressions fail loudly on MyFaces and silently on Mojarra. For render="nosuch" MyFaces throws ComponentNotFoundException: Cannot find component for expression "nosuch" referenced from "search:go" while rendering the page (HTTP 500). Mojarra catches the exception, sends the token on as it is, and the browser later finds no element with that id. In development you want to know; the wrapper in Decorating the Handler logs each case on both.

  • faces.js adds the source component to execute (the requests above show search:go next to the ids) unless the value is @none or @all: with execute="@none" the request carried no jakarta.faces.partial.execute at all.

ExpressionProbe.java — resolving from the clicked button
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.faces.component.UIComponent;
import jakarta.faces.component.search.SearchExpressionContext;
import jakarta.faces.component.search.SearchExpressionHandler;
import jakarta.faces.component.search.SearchExpressionHint;
import jakarta.faces.context.FacesContext;
import jakarta.faces.event.ActionEvent;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.util.ArrayList;
import java.util.EnumSet;
import java.util.List;
import java.util.Set;

/** Resolves a search expression from the clicked button, with the programmatic API. */
@Named
@RequestScoped
public class ExpressionProbe {
    @Inject
    FacesContext context;

    private String expression = "";
    private boolean ignoreNoResult;
    private boolean clientSide;
    private boolean skipVirtual;
    private boolean single;
    private final List<String> lines = new ArrayList<>();

    public void resolve(ActionEvent event) {
        UIComponent source = event.getComponent();
        SearchExpressionHandler handler = context.getApplication().getSearchExpressionHandler();
        Set<SearchExpressionHint> hints = EnumSet.noneOf(SearchExpressionHint.class);
        if (ignoreNoResult) hints.add(SearchExpressionHint.IGNORE_NO_RESULT);
        if (clientSide) hints.add(SearchExpressionHint.RESOLVE_CLIENT_SIDE);
        if (skipVirtual) hints.add(SearchExpressionHint.SKIP_VIRTUAL_COMPONENTS);
        if (single) hints.add(SearchExpressionHint.RESOLVE_SINGLE_COMPONENT);
        SearchExpressionContext sec = SearchExpressionContext.createSearchExpressionContext(context, source, hints, null);
        try {
            lines.add("valid=" + handler.isValidExpression(sec, expression)
                    + " passthrough=" + handler.isPassthroughExpression(sec, expression));
        } catch (RuntimeException e) {
            lines.add("valid/passthrough threw " + e.getClass().getSimpleName() + ": " + e.getMessage());
        }
        try {
            lines.add("clientIds=" + handler.resolveClientIds(sec, expression));
        } catch (RuntimeException e) {
            lines.add("clientIds threw " + e.getClass().getSimpleName() + ": " + e.getMessage());
        }
        try {
            List<String> found = new ArrayList<>();
            handler.resolveComponents(sec, expression, (ctx, c) -> found.add(c.getClass().getSimpleName() + "#" + c.getId()));
            lines.add("components=" + found);
        } catch (RuntimeException e) {
            lines.add("components threw " + e.getClass().getSimpleName() + ": " + e.getMessage());
        }
        System.out.println("PROBE " + expression + " hints=" + hints + " -> " + lines);
    }

    public String getExpression() { return expression; }
    public void setExpression(String expression) { this.expression = expression; }
    public boolean isIgnoreNoResult() { return ignoreNoResult; }
    public void setIgnoreNoResult(boolean v) { this.ignoreNoResult = v; }
    public boolean isClientSide() { return clientSide; }
    public void setClientSide(boolean v) { this.clientSide = v; }
    public boolean isSkipVirtual() { return skipVirtual; }
    public void setSkipVirtual(boolean v) { this.skipVirtual = v; }
    public boolean isSingle() { return single; }
    public void setSingle(boolean v) { this.single = v; }
    public List<String> getLines() { return lines; }
}

Custom Keywords

A keyword is a SearchKeywordResolver: isResolverForKeyword says whether the instance is responsible, resolve calls SearchKeywordContext.invokeContextCallback for each component it finds and setKeywordResolved(true), and isLeaf and isPassthrough (default false) describe the keyword. Two facts decide whether a resolver works:

  • The keyword string does not contain the @. The handler strips the prefix before it asks the resolvers, so @invalid arrives as invalid and @child(0) as child(0). A resolver that compares with "@invalid" matches nothing, on both implementations; isValidExpression then reports false. The API documentation does not say this; the built-in resolvers (for example "this".equals(keyword) in Mojarra) show it, and the failure was observed.

  • What the keyword can see. It runs when the expression is resolved (When an Expression Is Resolved): at page render for f:ajax, so it must depend on the tree, not on the request. In h:message for it runs after validation.

InvalidKeywordResolver.java — @invalid, the inputs whose validation failed (registered in faces-config.xml)
package org.example.bookshelf.search;

import jakarta.faces.component.UIComponent;
import jakarta.faces.component.UIInput;
import jakarta.faces.component.search.SearchExpressionContext;
import jakarta.faces.component.search.SearchKeywordContext;
import jakarta.faces.component.search.SearchKeywordResolver;
import jakarta.faces.component.visit.VisitContext;
import jakarta.faces.component.visit.VisitResult;
import jakarta.faces.context.FacesContext;

/** Resolves {@code @invalid} to every input of the view whose validation failed in this request. */
public class InvalidKeywordResolver extends SearchKeywordResolver {

    @Override
    public boolean isResolverForKeyword(SearchExpressionContext context, String keyword) {
        return "invalid".equals(keyword);
    }

    @Override
    public void resolve(SearchKeywordContext context, UIComponent current, String keyword) {
        FacesContext facesContext = context.getSearchExpressionContext().getFacesContext();
        facesContext.getViewRoot().visitTree(VisitContext.createVisitContext(facesContext), (visit, component) -> {
            if (component instanceof UIInput input && !input.isValid()) {
                context.invokeContextCallback(input);
            }
            return VisitResult.ACCEPT;
        });
        context.setKeywordResolved(true);
    }
}

Decorating the Handler

The handler itself is replaceable. A class that extends SearchExpressionHandlerWrapper and has a constructor that takes the handler it wraps can be named in the search-expression-handler element (above); two wrappers registered in different configuration files were both active in the runs. The example below logs each expression that matched nothing and then lets the default behaviour continue: it makes the silent Mojarra case visible.

DiagnosticSearchExpressionHandler.java
package org.example.bookshelf.search;

import jakarta.faces.component.search.ComponentNotFoundException;
import jakarta.faces.component.search.SearchExpressionContext;
import jakarta.faces.component.search.SearchExpressionHandler;
import jakarta.faces.component.search.SearchExpressionHandlerWrapper;
import java.util.List;
import java.util.logging.Level;
import java.util.logging.Logger;

/** Logs every expression that cannot be resolved, then lets the default behaviour go on. */
public class DiagnosticSearchExpressionHandler extends SearchExpressionHandlerWrapper {

    private static final Logger LOG = Logger.getLogger(DiagnosticSearchExpressionHandler.class.getName());

    public DiagnosticSearchExpressionHandler(SearchExpressionHandler wrapped) {
        super(wrapped);
    }

    @Override
    public String resolveClientId(SearchExpressionContext context, String expression) {
        try {
            return super.resolveClientId(context, expression);
        } catch (ComponentNotFoundException e) {
            report(context, expression);
            throw e;
        }
    }

    @Override
    public List<String> resolveClientIds(SearchExpressionContext context, String expressions) {
        try {
            return super.resolveClientIds(context, expressions);
        } catch (ComponentNotFoundException e) {
            report(context, expressions);
            throw e;
        }
    }

    private void report(SearchExpressionContext context, String expression) {
        LOG.log(Level.WARNING, "Search expression \"{0}\" matched nothing, source component \"{1}\"",
                new Object[] {expression, context.getSource().getId()});
    }
}

The wrapper overrides resolveClientId because Mojarra’s f:ajax renderer calls that one, and resolveClientIds because MyFaces' calls that one; override the methods your callers use. PrimeFaces Search Expressions

PrimeFaces 16 builds on the facility: its documentation calls it the Search Expression Framework and says that PrimeFaces enhances the Faces search expressions with its own keywords. process, update, trigger and similar attributes of PrimeFaces components take them. The jar ships its own keyword resolvers (the package org.primefaces.expression has classes for @(selector), @row, @form, the observer and @widgetVar), and PrimeFaces resolves its attributes by calling the handler (the stack trace of a failure ran through SearchExpressionUtils into resolveClientIds). The keywords from the PrimeFaces documentation, 16.0.0:

Keyword Meaning

@this, @all, @form, @none, @namingcontainer, @parent, @composite, @child(n), @previous, @next, @root, @id(id)

The Faces keywords as above.

@row(n)

The n-th row of a data table; the last resolved component must be a UIData.

@widgetVar(name)

The component with that widgetVar.

@(selector)

PrimeFaces Selectors (PFS): a jQuery selector evaluated in the browser.

@obs(event)

Targets an event, as described in the Event/Observer pattern of the PrimeFaces documentation (not exercised here).

Chaining works as in Faces (@form:@parent, @composite:mybuttonid), and the documentation adds that the framework applies wherever one component references another, not only to partial processing and updates. The Bookshelf view below uses a selector, a widget variable, a chain and a row:

Where the Books Are Outdated

PrimeFaces Cookbook, Second Edition (Çalışkan and Varaksin, 2015) treats process, update and its own search expressions in its first chapters, for PrimeFaces 5.x on JSF 2.2. When it was written the PrimeFaces framework was a library feature; since Faces 2.3 the core specification owns the facility and PrimeFaces extends it, so the same expressions now work in f:ajax and in the standard components (labels, messages) too. Its widget and selector keywords remain PrimeFaces specific, and PrimeFaces 16 documents more keywords than a book of that age can show (@row, @obs, @widgetVar, chaining). JavaServer Faces 2.0: The Complete Reference (Burns and Schalk, 2010) and the JSF 2.0 Cookbook (Leonard, 2010) were published before Faces 2.3, so they cannot describe the standard keywords beyond the four of f:ajax, chaining, the handler or custom keywords, and their code uses javax.faces. The Jakarta EE Tutorial itself still lists four keywords. Everything above was checked on 4.1.

Pitfalls

  • Writing @id(x) from a button without an anchor (@form:@id(x), @root:@id(x)); it works on neither implementation for its own reason (Chaining and the @id Keyword).

  • Using @root alone as execute or render (Chaining and the @id Keyword): use @all.

  • Separating expressions with commas: Mojarra does not split them (execute and render in f:ajax).

  • Relying on Mojarra’s silence: a typo in render is not an error there; add the wrapper of Decorating the Handler or test on both implementations.

  • Rendering a ui:repeat, a naming container or a composite by its id: none of them writes an element (Inside Tables and ui:repeat, Inside Composite Components).

  • Absolute ids with row indexes (Inside Tables and ui:repeat).

  • A keyword resolver that tests "@name" instead of "name" (Custom Keywords).

  • A custom keyword that reads the state of the postback in f:ajax; it is resolved at render of the page (When an Expression Is Resolved).

  • A keyword that yields several components in f:ajax: all of them on MyFaces, the first on Mojarra.

  • Wrapping the handler or registering a keyword after the first request: Application.addSearchKeywordResolver throws IllegalStateException.
