Configuration and Project Stages

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Jakarta Faces 4.1 (API jakarta.faces-api 4.1.2, part of Jakarta EE 11), Eclipse Mojarra 4.1.17 and Apache MyFaces Core 4.1.4, with Java 17 or later. Faces 4.0 (Jakarta EE 10, Java 11 or later) has the same configuration model; the differences are collected in What Changed and nothing here was run on 4.0. The examples were compiled and deployed in a scratch Bookshelf WAR on Apache Tomcat 11.0.26 with Weld 6.0.4.Final, once with Mojarra and once with MyFaces, and driven with curl: every status code, HTML fragment, log line and "what happened" statement below comes from those runs (checked on 2026-10-08). A parameter described without such a statement is described from the specification, the API documentation or the Mojarra and MyFaces parameter references only, and the page says so. Faces 5.0 is still a milestone release (5.0.0-M9 on 2026-09-18) and nothing here describes it as current behaviour.

The page is the reference for how a Faces application is configured and how that configuration behaves. The Project Setup page shows how to put a first web.xml and faces-config.xml into a project; this page goes through every standard context parameter, the ProjectStage and its real effects, the faces-config.xml document, the relation between annotations and XML, the loading and ordering of several configuration files, and the parameters that only Mojarra or only MyFaces understand. Faces is configured from a handful of places, and most configuration mistakes come from not knowing which of them wins.

Where Faces Reads Its Configuration

Five mechanisms feed the configuration of a Faces application. They are independent and they overlap on purpose, so that a library can configure itself, an application can override the library, and an operations team can change a setting without rebuilding the WAR.

The sequence at startup is the same on both implementations. The container merges the descriptors, Faces decides whether it has anything to do, collects the configuration resources, sorts them, combines the annotation metadata with them, and publishes PostConstructApplicationEvent when it is finished. All of this happens before the first request is processed, which is why configuration errors are deployment errors, not request errors.

Two details of the diagram deserve a sentence. The FacesServlet is mapped for you when you do not map it yourself and one of these is true: WEB-INF/faces-config.xml exists, a META-INF/faces-config.xml or *.faces-config.xml file exists in a JAR, jakarta.faces.CONFIG_FILES is declared, or the container initializer found a class with a Faces annotation (the API documentation of FacesServlet lists the annotations); the section on Extensionless Mapping and the FacesServlet Mappings shows what that automatic mapping covers. And the Mojarra reference adds a case for applications with no web.xml and no faces-config.xml at all (a Spring Boot application that registers everything programmatically): com.sun.faces.forceLoadConfiguration starts the configuration even though none of the usual triggers is present.

Startup and Shutdown

Startup ends with an event and shutdown starts with one. At startup the specification (11.3.2) has the runtime publish PostConstructApplicationEvent immediately after all configuration resources have been processed, flows and resource library contracts included; the events page lists it as an application system event. A parsing error in a configuration resource is fatal to startup and the container does not make the application available. At shutdown (11.3.4) the runtime must make sure that FacesContext.getCurrentInstance() returns successfully while the application is going down (the API documentation of FacesContext says that getApplication() is valid during startup and shutdown), then publish PreDestroyApplicationEvent, and finally call FactoryFinder.releaseFactories(). So PreDestroyApplicationEvent is the hook for releasing what an application-wide extension holds (a thread pool, a cache, a connection), and by the time the factories are released nothing of Faces may be used any more.

A listener that releases resources at shutdown, registered in faces-config.xml
package org.example.bookshelf.config;

import jakarta.faces.context.FacesContext;
import jakarta.faces.event.AbortProcessingException;
import jakarta.faces.event.SystemEvent;
import jakarta.faces.event.SystemEventListener;
import java.util.logging.Logger;

/** Runs when the web application stops: close what the application opened at startup. */
public class ShutdownHook implements SystemEventListener {

    private static final Logger LOG = Logger.getLogger(ShutdownHook.class.getName());

    @Override
    public void processEvent(SystemEvent event) throws AbortProcessingException {
        FacesContext ctx = FacesContext.getCurrentInstance();
        String line = "shutdown: FacesContext present = " + (ctx != null)
                + ", project stage = " + (ctx == null ? "?" : ctx.getApplication().getProjectStage());
        LOG.info(line);
        System.err.println(line);
        // close the catalogue cache, stop the import scheduler ...
    }

    @Override
    public boolean isListenerForSource(Object source) {

Context Parameters

A context parameter is a name and a string value that the servlet container exposes through the ServletContext. Faces reads them once, at startup, so changing one needs a redeploy or restart. (The Facelets refresh period is no exception: it sets how often the view files are checked, and is itself read at startup.)

How Values Are Read

The values are strings and each parameter has its own rule. The specification states the rules of the boolean ones the same way for most of them: the runtime calls toLowerCase().equals("true") on the string, so true, TRUE and True enable the parameter, and anything else (yes, 1, on) leaves it off. jakarta.faces.STATE_SAVING_METHOD is compared ignoring case, jakarta.faces.PROJECT_STAGE is not: it has to be the exact name of a constant. The lists are separated by different characters depending on the parameter (semicolon for the Facelets libraries, decorators and view mappings, comma for CONFIG_FILES and FULL_STATE_SAVING_VIEW_IDS, a space for RESOURCE_EXCLUDES and FACELETS_SUFFIX); the tables below say which. A mistyped parameter name is not an error: it is simply never read, and the application runs with the default. In the scratch run jakarta.faces.PROJECT_STAG, a made-up com.sun.faces.numberOfLogicalViewz and the old javax.faces.PROJECT_STAGE were all ignored on both implementations, without a log line, while the correct jakarta.faces.PROJECT_STAGE next to them set Development. Both implementations can print what they read, which is the quickest way to find a typo (the sections on Mojarra Parameters and MyFaces Parameters show how).

Facelets Parameters in Practice

The refresh period and the comment switch are demonstrated on the Project Setup page, where the combination with the project stage is tabulated. The other Facelets parameters change how a view id is mapped to a file or what the compiler does, and they have traps.

FACELETS_SUFFIX

A request for /books.xhtml becomes the view id /books.xhtml, and the Facelets compiler reads the physical file books.xhtml. jakarta.faces.FACELETS_SUFFIX changes the file suffix that is looked for: it is a space-separated list of extensions, each starting with a dot; the first physical file that matches one of them becomes the file behind the view id. A project that keeps its views in .facelet files while the URLs stay .xhtml configures it like this:

Views stored as .facelet files
<context-param>
  <param-name>jakarta.faces.FACELETS_SUFFIX</param-name>
  <param-value>.facelet .xhtml</param-value>
</context-param>

Source: Jakarta Faces 4.1 API: ViewHandler, FACELETS_SUFFIX_PARAM_NAME

The Bookshelf scratch application had suffix.facelet and index.xhtml in its web root, the FacesServlet mapped to *.xhtml only, and the two implementations answered like this:

Two lessons follow. First, a list of suffixes is not portable: with both .facelet and .xhtml in the list, Mojarra found suffix.facelet for the request /suffix.xhtml and MyFaces answered 404 (it did not substitute the suffix because the request already ended with one of the listed ones), while with the single value .facelet both implementations served the page. The single value is the safe choice, and it means every view file must use it.

Second, and worse: the file suffix.facelet was answered with status 200 and its raw Facelets source on a direct request, in every variant, because the container serves a file nobody maps as static content. The source of a page, with its EL expressions, bean names and comments, was readable by anyone. A suffix other than .xhtml therefore needs a constraint that blocks direct access:

Blocking direct access to alternative view files
<security-constraint>
  <web-resource-collection>
    <web-resource-name>Facelets sources</web-resource-name>
    <url-pattern>*.facelet</url-pattern>
  </web-resource-collection>
  <auth-constraint/>
</security-constraint>

With this constraint the direct request answered 403 on both implementations, and the view requested as /index.xhtml still rendered. (The constraint has an empty auth-constraint, which in the Servlet specification means no role may access the resource.) Views under WEB-INF need no constraint, because the container never serves that directory; that is the reason templates are kept in WEB-INF/templates in the Bookshelf layout.

Source: Jakarta Servlet 6.1 specification, security constraints and Jakarta Faces 4.1 API: FacesServlet, security considerations

FACELETS_VIEW_MAPPINGS

jakarta.faces.FACELETS_VIEW_MAPPINGS declares that some resources are Facelets views whatever their extension. Each entry of the semicolon-separated list is a file extension written as *.xhtml or a prefix starting with a slash and ending in *, as in /user/*. A legacy application with views called *.html that maps the FacesServlet to *.html too would write:

Treating .html files as Facelets views
<context-param>
  <param-name>jakarta.faces.FACELETS_VIEW_MAPPINGS</param-name>
  <param-value>*.html</param-value>
</context-param>
<servlet-mapping>
  <servlet-name>facesServlet</servlet-name>
  <url-pattern>*.xhtml</url-pattern>
  <url-pattern>*.html</url-pattern>
</servlet-mapping>

In the scratch run a file legacy.html with Facelets content was served by MyFaces with this parameter alone (status 200, the EL expression evaluated) and answered 404 on Mojarra. Adding jakarta.faces.FACELETS_SUFFIX with the value .html made both implementations serve it, with or without the view mappings parameter. So FACELETS_SUFFIX is the parameter that decides which file is read; FACELETS_VIEW_MAPPINGS decides which view ids count as Facelets, and Mojarra needs the first even when the second is set.

Source: Jakarta Faces 4.1 API: ViewHandler, FACELETS_VIEW_MAPPINGS_PARAM_NAME

FACELETS_DECORATORS

A TagDecorator sees each tag while a view is compiled and may replace it. The classes are named in the semicolon-separated parameter, need a public no-argument constructor, and are created when the first request for a Facelets view reaches the ViewHandler. A decorator that only observes returns null:

A TagDecorator that logs every command button as the view is compiled
package org.example.bookshelf.config;

import jakarta.faces.view.facelets.Tag;
import jakarta.faces.view.facelets.TagDecorator;
import java.util.logging.Logger;

public class CompileLogDecorator implements TagDecorator {

    private static final Logger LOG = Logger.getLogger(CompileLogDecorator.class.getName());

    public CompileLogDecorator() {
        LOG.info("decorator created");
    }

    @Override
    public Tag decorate(Tag tag) {
        if ("commandButton".equals(tag.getLocalName())) {
            LOG.info("compiling " + tag.getQName() + " at " + tag.getLocation());
        }
        return null;
    }
}
<context-param>
  <param-name>jakarta.faces.FACELETS_DECORATORS</param-name>
  <param-value>org.example.bookshelf.config.CompileLogDecorator</param-value>
</context-param>

On the first request for index.xhtml both implementations logged decorator created once and then compiling h:commandButton at /index.xhtml @6,90 (Mojarra) or ... at /index.xhtml at line 6 and column 90 (MyFaces). Because the compiled view is cached, the decorator runs again only when the refresh period causes a recompilation. A decorator that returns a different Tag rewrites the view before it is built; the tag libraries and templates documented elsewhere in this section are the usual way to change markup, and a decorator is the tool for a rewrite that has to touch every view.

The time zone of f:convertDateTime

f:convertDateTime formats with GMT unless a timeZone attribute is given, a surprise for every application not running in London. jakarta.faces.DATETIMECONVERTER_DEFAULT_TIMEZONE_IS_SYSTEM_TIMEZONE switches the default to the JVM’s zone:

Making the JVM time zone the default of every date converter
<context-param>
  <param-name>jakarta.faces.DATETIMECONVERTER_DEFAULT_TIMEZONE_IS_SYSTEM_TIMEZONE</param-name>
  <param-value>true</param-value>
</context-param>
<h:outputText value="#{dateBean.published}">
  <f:convertDateTime pattern="yyyy-MM-dd HH:mm z"/>
</h:outputText>
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Named;
import java.time.Instant;
import java.util.Date;

@Named
@RequestScoped
public class DateBean {
    public Date getPublished() { return Date.from(Instant.parse("2026-07-01T12:00:00Z")); }
}

For a date of 2026-07-01 at 12:00 UTC and a JVM started with -Duser.timezone=Europe/Madrid, the page printed 2026-07-01 12:00 GMT without the parameter and 2026-07-01 14:00 CEST with it, on both implementations. The converter is applied on output in the Render Response phase and on input in Process Validations, so a value typed in a form is parsed in the same zone it was displayed in. Prefer an explicit timeZone attribute when the zone is part of the business rule rather than of the server.

Required fields that are missing from the request

required="true" is checked when the input is decoded and validated, and only for the parameters that are present in the request. A request that leaves the parameter out entirely is not an empty submission: the component has nothing submitted and, by default, is not validated. A browser always sends the field of a text input, even empty, so the problem is invisible in the browser and shows up in a scripted or malicious request.

A form with a required field
<h:form id="f">
  <h:inputText id="title" value="#{reqBean.title}" required="true"/>
  <h:message for="title"/>
  <h:inputText id="note" value="#{reqBean.note}"/>
  <h:commandButton id="b" value="save" action="#{reqBean.save}"/>
</h:form>
The bean behind the form
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Named;

@Named
@RequestScoped
public class ReqBean {
    private String title;
    private String note;
    private String last = "none";
    public String getTitle() { return title; }
    public void setTitle(String t) { this.title = t; }
    public String getNote() { return note; }
    public void setNote(String n) { this.note = n; }
    public String save() { last = "saved title=[" + title + "] note=[" + note + "]"; return null; }
    public String getLast() { return last; }
}

A POST that carried f:b and f:note but not f:title called the action with title=null on both implementations, and no message was added; a POST with f:title= (present but empty) produced "Validation Error: Value is required." With the parameter jakarta.faces.ALWAYS_PERFORM_VALIDATION_WHEN_REQUIRED_IS_TRUE set to true the first request was rejected as well, with the same message, and the action did not run.

Validating required inputs even when their parameter is missing
<context-param>
  <param-name>jakarta.faces.ALWAYS_PERFORM_VALIDATION_WHEN_REQUIRED_IS_TRUE</param-name>
  <param-value>true</param-value>
</context-param>

Treat the parameter as a hardening setting for any application where an action depends on a required value: the server must not rely on the browser to send the fields. It costs one validation call per required input and changes no markup.

Source: Jakarta Faces 4.1 API: UIInput, ALWAYS_PERFORM_VALIDATION_WHEN_REQUIRED_IS_TRUE and Jakarta Faces 4.1 specification, 11.1.3

The Client Id Separator

jakarta.faces.SEPARATOR_CHAR changes the character between the segments of a client id (f:title becomes f_title). Only the first character of the value is used. It exists for style sheets and scripts that cannot cope with the colon, and it has a price: every id with that character in it, every search expression and every piece of JavaScript written with the old character stops working. In the scratch run a form f with the input in and the button b rendered the ids f_in and f_b on both implementations, and the view state field j_id1_jakarta.faces.ViewState_0 (Mojarra) and j_id__v_0_jakarta.faces.ViewState_1 (MyFaces). The Search Expressions page lists the places that must stay in step: the update and render attributes, @form:id style absolute expressions, and CSS selectors that escape the colon.

Underscore instead of colon in client ids
<context-param>
  <param-name>jakarta.faces.SEPARATOR_CHAR</param-name>
  <param-value>_</param-value>
</context-param>

State Saving Parameters

jakarta.faces.STATE_SAVING_METHOD decides where the view state lives, and it is the most visible parameter in the page source. The state saving page covers the mechanism, the limits of the server variant, the protection of the client variant and the Mojarra and MyFaces parameters around it; here only the configuration is shown.

Switching to client state saving
<context-param>
  <param-name>jakarta.faces.STATE_SAVING_METHOD</param-name>
  <param-value>client</param-value>
</context-param>

The hidden field jakarta.faces.ViewState of a trivial page held 40 characters on Mojarra and 32 on MyFaces with the default server method (an identifier of a state kept in the session), and 704 and 128 characters respectively with client (the state itself, protected by the implementation). The size grows with the component tree on every response and every postback, and the state leaves the server, so it must be protected: both implementations encrypt it and attach a message authentication code by default, and the parameters that turn that off (com.sun.faces.disableClientStateEncryption, org.apache.myfaces.USE_ENCRYPTION) must never be set in production.

What each implementation does with them is its own business, and the scratch measurements below show that UnitTest and SystemTest mean almost nothing in practice: the practical choice is between Development and everything else.

How the Stage Is Determined

Application.getProjectStage() computes the stage the first time it is called and keeps it. The algorithm in the API documentation looks for a JNDI environment entry first and for the context parameter second, and falls back to Production when the value cannot be used.

The JNDI name is the constant ProjectStage.PROJECT_STAGE_JNDI_NAME, which holds java:comp/env/faces/ProjectStage (not jakarta.faces.PROJECT_STAGE, which is the name of the context parameter). Two ways to define it were run on Tomcat with the JNDI naming enabled, each time with the context parameter set to Production, and in each case both implementations reported Development: the JNDI entry won. In web.xml:

The stage as a JNDI environment entry in web.xml
<env-entry>
  <env-entry-name>faces/ProjectStage</env-entry-name>
  <env-entry-type>java.lang.String</env-entry-type>
  <env-entry-value>Development</env-entry-value>
</env-entry>

and in the Tomcat META-INF/context.xml of the application, which is the variant an operations team controls without touching the WAR:

The stage as a Tomcat environment entry
<Context>
  <Environment name="faces/ProjectStage" value="Development" type="java.lang.String" override="false"/>
</Context>

A value that is not exactly one of the four names is not an error. Mojarra logged INFO: Unable to discern ProjectStage for value Staging. and MyFaces WARNING: Wrong value in context init parameter 'jakarta.faces.PROJECT_STAGE' (='Staging'), using default value 'Production'; both then ran as Production. The lower-case development was refused in the same way, because the value goes through ProjectStage.valueOf(). The Jakarta EE Tutorial says custom stages can be added; that cannot work with a Java enum, and in both implementations a custom name means Production plus a log line. The mistake to avoid is a typo in the one value that should enable diagnostics (or, worse, a typo that is meant to disable them): the application starts without complaint and runs in Production.

faces-config.xml

faces-config.xml is the application configuration resource: an XML document in the Jakarta EE namespace that registers objects with the Application and the factories, and that carries the settings that have no annotation. The same format is used by the WEB-INF/faces-config.xml of the application, by the META-INF/faces-config.xml of every library and by the extra files named in jakarta.faces.CONFIG_FILES.

The Document

A Faces 4.1 document starts with this declaration, which the specification requires:

The faces-config.xml root element for Faces 4.1
<?xml version="1.0" encoding="UTF-8"?>
<faces-config xmlns="https://jakarta.ee/xml/ns/jakartaee"
              xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
              xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-facesconfig_4_1.xsd"

Source: Jakarta Faces 4.1 specification, 11.3.5 Application Configuration Resource Format and web-facesconfig_4_1.xsd

The schema of 4.1 defines the root as a choice of its children, repeated, so the elements can appear in any order and the ordering of the schema never causes a validation error. The root has three attributes: version (4.1), id, and metadata-complete, which stops annotation scanning when it is true in WEB-INF/faces-config.xml (see Annotations or XML). The Project Setup page shows the namespaces and version numbers of all the earlier releases; a document that names an older schema is still read by 4.1 runtimes, but only a 4.1 document can use the elements added since. A <managed-bean> element in a 4.1 document does not validate against the schema, and both runtimes ignored it silently in the scratch run: the managed bean facility is gone, and CDI replaces it (the Backing Beans and CDI page).

Annotations or XML

Every registration that has an annotation can be written either way, and the specification fixes the winner when the two disagree: an entry in an application configuration resource takes precedence over an annotation. The annotated classes are found by scanning, and the scan can be restricted or switched off.

What Is Scanned

The specification (11.4.1) says that all classes in WEB-INF/classes are scanned, that the classes of a JAR in WEB-INF/lib are scanned only if the JAR contains a META-INF/faces-config.xml (or a file ending in .faces-config.xml, even empty), and that a metadata-complete="true" in WEB-INF/faces-config.xml turns the scan off for everything except the implementation’s own classes. The containers' initializer is told which annotations to look for (the list is in the API documentation of FacesServlet); that is also what triggers the automatic mapping of the servlet. A library that wants its annotated classes found therefore ships a META-INF/faces-config.xml, even an empty one. Mojarra scanned a library JAR without it in the scratch runs of earlier pages and MyFaces did not, so the file is what makes the library portable.

Two parameters restrict the scan and shorten the startup of an application with a large class path:

Restricting the annotation scan
<!-- Mojarra: package names for WEB-INF/classes, or jar:name:packages -->
<context-param>
  <param-name>com.sun.faces.annotationScanPackages</param-name>
  <param-value>org.example.bookshelf.convert org.example.bookshelf.web</param-value>
</context-param>

<!-- MyFaces: comma separated packages -->
<context-param>
  <param-name>org.apache.myfaces.annotation.SCAN_PACKAGES</param-name>
  <param-value>org.example.bookshelf.convert,org.example.bookshelf.web</param-value>
</context-param>

In the scratch run, restricting the scan to org.example.bookshelf.config (a package without the @FacesConverter class) made the page that uses the converter fail with status 500 on both implementations, and restricting it to the package that contains the converter made the page work. The mistake it invites is silent: a class in a package that is not listed is never registered, and the first error is at the first use of the id.

Replacing a Standard Converter

The same replacement works on the identifiers that Faces itself registers, as long as the new class is a subclass of the standard one. The standard integer converter has the id jakarta.faces.Integer; a subclass that accepts an underscore as a digit separator and an XML entry that replaces it:

Which to Use

Prefer the annotation where one exists: the registration sits next to the class and cannot drift from it. Use XML when the registration must be changeable without recompiling (a library default the application overrides), when the same class is registered under two ids, when the item has no annotation (locales, bundles, navigation rules, phase listeners, factories, protected-views, ordering), or when the annotation scan is too expensive and metadata-complete="true" is set so that everything is listed explicitly. A project can mix the two freely; the rule above settles every conflict.

Ordering of Configuration Files

When two files register something that can only have one value, or something that wraps what was registered before, the order in which they are read decides the result. The classpath order is not a contract: it depends on the container and the build. The specification therefore defines how files declare their order. The rules (11.3.8) are borrowed from the Servlet specification’s ordering of web fragments.

The Rules

  • A file may have a top-level <name>. Only named files take part in ordering.

  • A library file may have an <ordering> with at most one <before> and one <after>; each contains the names of other files and may contain <others/>, the set of all other files.

  • <before><others/></before> moves the file to the beginning of the list, <after><others/></after> to the end; several files that say so are in unspecified order among themselves.

  • The application’s own WEB-INF/faces-config.xml is always read last, and it alone may contain an <absolute-ordering>: a list of <name> elements, optionally with one <others/>, that fixes the order of all the library files. A library file not named and without <others/> in an absolute ordering is ignored (its configuration is not read at all).

  • An <ordering> in WEB-INF/faces-config.xml or an <absolute-ordering> in a library is ignored, with a log message.

  • A cycle is an error that must fail the deployment, and so must two files with the same name.

The specification’s example
<!-- library A -->
<faces-config ...>
  <name>A</name>
  <ordering><after><name>B</name></after></ordering>
  <lifecycle><phase-listener>lib.PL_A</phase-listener></lifecycle>
</faces-config>

<!-- library B: no ordering -->
<faces-config ...>
  <name>B</name>
  <lifecycle><phase-listener>lib.PL_B</phase-listener></lifecycle>
</faces-config>

<!-- library C -->
<faces-config ...>
  <name>C</name>
  <ordering><before><others/></before></ordering>
  <lifecycle><phase-listener>lib.PL_C</phase-listener></lifecycle>
</faces-config>

<!-- WEB-INF/faces-config.xml: name "my", no ordering -->

What Ordering Changes

Ordering decides two things. The first is the order of decoratable artifacts: a ViewHandler, NavigationHandler, ActionListener, factory or other class named in <application> or <factory> wraps the one registered before it, so the file read last is the outermost wrapper. The second is every registration that has an id: a later file replaces an earlier one, as the converter table of Annotations or XML shows. For phase listeners, the order of the list is also the order of the calls: in both runs beforePhase was called for the listeners in list order (C, B, D, A, my on Mojarra) and afterPhase in reverse order (my, A, D, B, C), so the first listener registered is the outermost one. The Events and Listeners page describes how listeners registered in faces-config.xml relate to those of a view.

The key parameters are the one place where a configuration file tempts a programmer into a security mistake. A key must be the same on every node of a cluster and must not sit in the version control system of the project. Extensionless Mapping and the FacesServlet Mappings

Which URLs reach the FacesServlet is configuration too. The Project Setup page covers the three mapping styles of web.xml (extension, prefix and exact); this section covers the parts that depend on parameters: the mapping Faces adds when you declare none, the Faces 4.0 extensionless mapping, and what each setting does to the URLs the application generates.

The Automatic Mapping

When the servlet is not mapped in web.xml or web-fragment.xml and Faces detects that the application uses it (the triggers of the diagram at the start of this page), the implementation maps it to four patterns: /faces/*, *.jsf, *.faces and *.xhtml. jakarta.faces.DISABLE_FACESSERVLET_TO_XHTML removes the last of them. A mapping that you declare yourself replaces all four.

AUTOMATIC_EXTENSIONLESS_MAPPING

With jakarta.faces.AUTOMATIC_EXTENSIONLESS_MAPPING set to true, the implementation scans the web application at startup and adds a mapping for the extensionless variant of every view it finds (/index for /index.xhtml). Mojarra’s reference warns that the scan walks the whole web root and registers a mapping per view, so the startup cost grows with the number of views.

Automatic extensionless mapping
<context-param>
  <param-name>jakarta.faces.AUTOMATIC_EXTENSIONLESS_MAPPING</param-name>
  <param-value>true</param-value>
</context-param>

Source: Jakarta Faces 4.1 API: FacesServlet, AUTOMATIC_EXTENSIONLESS_MAPPING_PARAM_NAME

The exact alternative, which the Jakarta EE Tutorial describes, lists the views yourself and costs nothing at startup:

Exact mappings for two views
<servlet-mapping>
  <servlet-name>facesServlet</servlet-name>
  <url-pattern>*.xhtml</url-pattern>
  <url-pattern>/index</url-pattern>
  <url-pattern>/other</url-pattern>
</servlet-mapping>

The table has three consequences.

  • A declared mapping replaces the automatic ones. With *.xhtml declared, /faces/index.xhtml and /index.jsf stop working, even though the extensionless parameter is on.   • DISABLE_FACESSERVLET_TO_XHTML without a mapping of your own serves the views as text. /index.xhtml answered 200 with the literal stage=#{configInfoBean.stage} of the source on both implementations, and /faces/index.xhtml still rendered: an attacker reads every view’s source, including the EL expressions and the structure of the application, by dropping the prefix. Where the Books Are Outdated

The books consulted for this section describe Faces 1.0 to 2.2. The faces-config.xml reference of Burns and Schalk and the configuration chapter of Dudney and colleagues are the ones that touch this page, and the configuration they teach has changed in these ways:

  • javax.faces. parameter names.* Every parameter of the books has a jakarta.faces. name since 3.0, and the old names are ignored without a message (verified: javax.faces.PROJECT_STAGE had no effect on either implementation).

  • <managed-bean>, <managed-property> and <referenced-bean> in faces-config.xml. The first two are gone from the schema and from the runtime, and a <managed-bean> element is ignored; <referenced-bean> remains in the schema only as a note for tools. Beans are CDI beans.

  • The Pages-era configuration. JSP views, DEFAULT_SUFFIX and a FacesServlet mapped to *.jsp or *.jsf for JSP pages belong to the past; the default mapping and suffix are .xhtml and the Pages suffix is deprecated for removal.

  • DTD and old schemas. The Faces 1.0 and 1.1 DOCTYPE with web-facesconfig_1_x.dtd and the schemas of 1.2 to 2.3 name namespaces that the 4.1 documents do not use; the Project Setup page tabulates them.

  • The Facelets 1.x parameters. The standalone Facelets book configures the library through its own facelets.* context parameters and a com.sun.facelets view handler. Facelets is part of Faces since 2.0, and the jakarta.faces.FACELETS_* parameters of this page replace them.

  • Implementation parameters. The Reference Implementation parameters of older books and articles come from Mojarra 1.x and 2.x. Check every name against CONTEXT-PARAMS.md: a name that is not there (for example com.sun.faces.expressionFactory) is not a 4.1 parameter, and an unknown name is ignored without a message.

  • Project stages and development mode. Standalone Facelets had a development setting of its own. The ProjectStage of Faces 2.0 replaces it, and its effects are the ones of Project Stages, fewer than a reader may assume.

  • Secrets in configuration. Nothing in Faces configuration needs a literal secret: take keys and passwords from the environment or the server, as shown for the MyFaces key, and keep placeholders in the files under version control.

Source: Jakarta EE Tutorial: Configuring Jakarta Faces Applications (the tutorial documents Jakarta EE 10; its managed-bean pages and the schema 3.0 shown in it are outdated for Faces 4.1)

Common Mistakes

  • Leaving Development in web.xml of a release. The error page, the unhandled-message list and the refresh checks reach production. Make Production the default of the build and select Development with a profile, or take the stage from JNDI.

  • Believing UnitTest and SystemTest do something. On MyFaces they equal Production; on Mojarra they differ in one rendering detail.

  • Believing ui:debug is switched off in production. It is not; guard it with the stage, once, in the master template.

  • Enabling ERROR_HANDLING (MyFaces) or the Development stage on a public server to find a problem. Stack traces, bean state and the component tree go to the client.

  • Mistyping a parameter name. Nothing complains; print the parameters at startup and look.

  • Trusting required for server-side rules. A request that omits the field skips validation unless ALWAYS_PERFORM_VALIDATION_WHEN_REQUIRED_IS_TRUE is set; validate on the server whatever the browser sends.

  • A view suffix other than .xhtml without a constraint. The raw Facelets source is served by the container.

  • DISABLE_FACESSERVLET_TO_XHTML without a mapping of your own. The .xhtml views are then served as plain text.

  • Absolute ordering without <others/> on Mojarra 4.1.17. The application does not start.

  • Relying on classpath order. The order of unordered files is whatever the container lists; use <ordering>.

  • Relying on CONFIG_FILES to replace the META-INF search. Neither implementation skipped it.

  • Duplicate <name> values. The deployment is not refused, and one of the files may be shadowed.

  • Restricting the annotation scan too far. A converter in a package that is not listed fails at first use, not at startup.

  • Real secrets in web.xml or faces-config.xml. Keys, passwords and database URLs belong in the environment or the server; the files in version control carry placeholders.

  • Changing a descriptor and expecting a reload. Only the view files are re-read; every parameter is read at startup.
