PrimeFaces: Ajax, Forms and Validation

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against Jakarta Faces 4.1 (API jakarta.faces-api 4.1.2, part of Jakarta EE 11), PrimeFaces 16.0.0 (the previous line is 15.0.x), Eclipse Mojarra 4.1.17 and Apache MyFaces Core 4.1.4, with Java 17 or later. The PrimeFaces 16 migration guide says that its baseline is Jakarta Faces 4.0 and newer (all javax.* support was removed), so the text also holds for Faces 4.0 as far as the PrimeFaces documentation goes; nothing was run on 4.0. The examples were compiled with --release 21 and deployed in a scratch Bookshelf WAR on Apache Tomcat 11.0.26 with Weld 6.0.4.Final and Hibernate Validator 9.1.4.Final, once with Mojarra and once with MyFaces. The browser side was driven with a real browser (headless Google Chrome controlled through the DevTools protocol) and the server side with raw HTTP posts, so the request parameters, the partial responses, the JavaScript results and the validation outcomes below come from those runs (checked on 2026-10-08). The places where the two implementations disagree are collected in Mojarra and MyFaces.

Standard Ajax (f:ajax, the faces.ajax API and the partial lifecycle) is on the Ajax page; this page does not repeat it. It covers what PrimeFaces adds around it for forms: its own Ajax behaviour and commands, the process and update model, the client callbacks, the input components of the Bookshelf review form, the message components, and the PrimeFaces client-side validation framework. The data tables, panels and dialogs, files and charts, the PrimeFaces Extensions and OmniFaces have their own pages in this section (data components, panels, menus and dialogs, files, media, charts and drag and drop, PrimeFaces Extensions and OmniFaces). The PrimeFaces set-up (dependency, themes, icons, the context parameters in general) is on the page about getting started with PrimeFaces. Testing pages that use these components in a real browser is the subject of the testing page; the application-wide server settings (view state in a cluster) are on the deployment page.

The PrimeFaces Ajax Model

PrimeFaces does not replace the Faces Ajax protocol; it sends it with its own client. A p:ajax behaviour, a p:commandButton and a p:remoteCommand all end in the same call, PrimeFaces.ajax.Request.handle(cfg), which the page emits as the shorthand PrimeFaces.ab({...}). On the server the request is an ordinary Faces postback with the parameters of the standard protocol. This is a request that the browser sent for the preview example of this page (typing one character into a p:inputText that carries a p:ajax), decoded and with the view state shortened:

POST /bookshelf/preview.xhtml
Faces-Request: partial/ajax
X-Requested-With: XMLHttpRequest

jakarta.faces.partial.ajax=true
jakarta.faces.source=draft:title
jakarta.faces.partial.execute=draft:title
jakarta.faces.partial.render=draft:preview+draft:keystrokes
jakarta.faces.behavior.event=keyup
jakarta.faces.partial.event=keyup
draft=draft
draft:title=D
jakarta.faces.ViewState=...

What is different from f:ajax is the client and a few server conventions:

  • Own client, based on jQuery. PrimeFaces ships jquery.js, core.js and components.js and does not use faces.js. On the scratch pages that contain no f:ajax, the global faces object was undefined and the requests still worked. If a page mixes both, each request goes through the client of the tag that created it; the Ajax page covers the standard one.

  • Identifiers are resolved while the page is rendered. The attributes process and update accept search expressions (Search Expressions in PrimeFaces). PrimeFaces resolves them to client ids when it renders the button or the behaviour, and the browser sends the result: u:"draft:preview,draft:keystrokes" in the generated onkeyup handler became jakarta.faces.partial.render=draft:preview+draft:keystrokes in the request. An expression that matches nothing is therefore an error when the page that contains it is rendered, not when the button is clicked (An Unknown Id Fails the Page).

  • Extra parameters. PrimeFaces adds its own parameters when an option is set, for example primefaces.ignoreautoupdate=true (p:autoUpdate and Event Observers), and answers with a standard partial response that may carry extension elements with the callback arguments (Client Callbacks and Callback Arguments) and with scripts (PrimeFaces.current()).

  • Components that are not Ajax commands send their own requests. p:autoComplete posts review:book_query=Du with itself as source, execute and render target (p:autoComplete).

The documentation of PrimeFaces says that its Ajax framework is built on the standard server-side APIs with no custom view root, state manager, view handler, servlet filter or phase listener. The META-INF/faces-config.xml inside primefaces-16.0.0.jar does register a number of standard extension points, and they matter when you debug:

Registered by the jar Effect

PrimePartialViewContextFactory and PrimeFacesContextFactory

They wrap the partial view context and the Faces context of every request. The callback arguments and the scripts of PrimeFaces.current() come back in the partial response as extension elements.

Phase listeners AutoUpdatePhaseListener, CspPhaseListener and DialogKeepFlashPhaseListener

p:autoUpdate (p:autoUpdate and Event Observers), the Content Security Policy support (the primefaces.CSP parameter; see the security page) and the dialog framework, which is covered on the page about panels, menus and dialogs.

PrimeResourceHandler and a system event listener MetadataTransformerExecutor (on PreRenderComponentEvent)

The resource handling of the PrimeFaces resources, and the Bean Validation metadata transformation of Bean Validation Metadata on the Components.

A client-behaviour renderer for org.primefaces.component.AjaxBehaviorRenderer

The renderer behind p:ajax.

Renderers for jakarta.faces.Head and jakarta.faces.Body

Resource ordering and the optional moving of scripts to the end of the body (primefaces.MOVE_SCRIPTS_TO_BOTTOM).

Converters for the standard ids and types (jakarta.faces.Integer, Long, Double, Float, Short, Byte, Character, Boolean, DateTime, Number, BigInteger, BigDecimal) and validators jakarta.faces.Length, LongRange, DoubleRange, RegularExpression

PrimeFaces replaces the standard ones with subclasses that also implement the client-side validation interfaces (Client-Side Validation (CSV)).

The exception handler and the matching EL resolver of PrimeFaces are not registered by the jar; the application opts in (Ajax Errors: p:ajaxExceptionHandler and the PrimeFaces ExceptionHandler).

Where It Sits in the Lifecycle

A PrimeFaces Ajax request runs the usual Faces lifecycle, limited to the components named in process (the partial processing of the lifecycle page) and followed by a partial rendering of the components named in update. The PrimeFaces documentation describes it the same way: process means executing Apply Request Values, Process Validations, Update Model Values and Invoke Application only on the named components. The scratch listener reported its phase through FacesContext.getCurrentPhaseId(): INVOKE_APPLICATION 5 for a normal p:ajax and APPLY_REQUEST_VALUES 2 with immediate="true" (Mojarra writes the phase with a space and MyFaces with parentheses).

The p:ajax Behaviour

p:ajax is a client behaviour for any component that implements ClientBehaviorHolder, standard or PrimeFaces (see the client behaviours page). The PrimeFaces documentation calls it an extension of f:ajax. The attributes of the tag in PrimeFaces 16.0.0, from its tag library, are:

A method expression. It may take an AjaxBehaviorEvent or no parameter; both worked on Mojarra and on MyFaces in the scratch application.

What to execute. Default for p:ajax: the component itself (@this). Observed: p:"draft:title" in the handler.

update

What to render. Default: nothing.

immediate

The listener runs in Apply Request Values instead of Invoke Application (measured: Listener and Phase), before the conversion and validation of the processed components.

delay

Milliseconds to wait; if another request is started within that time only the most recent is sent.

async

When true, the request is not queued behind the running ones.

timeout

Milliseconds after which the request is abandoned; 0 (the default) is no timeout.

global

resetValues

Reset the local values of the input components that are updated (resetValues and Cancel Buttons).

process and update

Both attributes take a list of search expressions separated by commas or spaces. They have the same meaning as execute and render of f:ajax (the Ajax page explains them), written as the PrimeFaces documentation does:

  • an identifier relative to the naming container of the component: update="display" when both are in the same form;

  • an absolute client id starting with the separator character: update=":form2:display", for a target in another form; the prependId="false" setting of a form has no effect on how this works;

  • a keyword (Search Expressions in PrimeFaces) or a PrimeFaces selector.

The naming containers are the standard ones (h:form, composite components, h:dataTable) plus, in PrimeFaces, the tab view, accordion panel, data table, data grid, data list, carousel, galleria, ring, sheet and sub table. A target inside a container that the expression does not reach is the "cannot find component" error (An Unknown Id Fails the Page).

@Named
@ViewScoped

    private String log = "";

    public void check() {
        boolean valid = isbn != null && isbn.matches("\\d{13}");
        PrimeFaces pf = PrimeFaces.current();
        pf.ajax().addCallbackParam("valid", valid);
        pf.ajax().addCallbackParam("checkedAt", LocalTime.now().withNano(0).toString());
        pf.ajax().addCallbackParam("info", new IsbnInfo(String.valueOf(isbn), isbn == null ? 0 : isbn.length()));
        if (!valid) {
            pf.executeScript("console.warn('isbn rejected')");

        pf.focus("f:isbn");
        pf.scrollTo("f:log");
        log = "ajax=" + pf.isAjaxRequest() + " faces=" + pf.isFacesRequest();

Delay, Queue, Timeout and Global Status

  • delay. Typing Dune with delay="200" sent one request; without it the key-ups of a fast typist send several.

  • async. By default Ajax requests are queued, one at a time, in the order in which they were started. async="true" skips the queue for that request. The Ajax page covers the standard queue; the PrimeFaces queue can be emptied from JavaScript with PrimeFaces.ajax.Queue.abortAll() (documentation).

  • timeout. A request that has not answered within the given milliseconds is abandoned with onerror(xhr, "timeout", "timeout") (measured). The browser abandons the request; nothing tells the server to stop the action.

  • disableOnAjax on a command disables that button while its request runs, so one user cannot start the same action twice from the same button. It does not queue anything else.

  • global. p:ajaxStatus is the global indicator of Ajax requests. It shows the facets default, start, success, error and complete, or runs the callbacks onstart, onsuccess, onerror and oncomplete; it also reacts to f:ajax requests. global="false" on a command or behaviour makes it a silent request. If a complete facet is defined, the success and error facets are never seen (the documentation says so). Do not update the status component itself.

src/main/java/org/example/bookshelf/web/CatalogueBookConverter.java
package org.example.bookshelf.web;

import jakarta.enterprise.context.Dependent;
import jakarta.faces.component.UIComponent;
import jakarta.faces.context.FacesContext;
import jakarta.faces.convert.Converter;
import jakarta.faces.convert.ConverterException;
import jakarta.faces.convert.FacesConverter;
import jakarta.inject.Inject;

import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;

@Dependent
@FacesConverter(value = "bookshelf.catalogueBook", managed = true)
public class CatalogueBookConverter implements Converter<Book> {

    @Inject
    private BookService books;

    @Override
    public Book getAsObject(FacesContext context, UIComponent component, String value) {
        if (value == null || value.isBlank()) {
            return null;
        }
        try {
            return books.find(Long.parseLong(value.trim())).orElseThrow(NumberFormatException::new);
        } catch (NumberFormatException e) {
            throw new ConverterException(new jakarta.faces.application.FacesMessage(
                    jakarta.faces.application.FacesMessage.SEVERITY_ERROR, "Unknown book", null), e);
        }
    }

    @Override
    public String getAsString(FacesContext context, UIComponent component, Book value) {
        return value == null ? "" : Long.toString(value.id());
    }
}

p:outputLabel Sets the Label

p:outputLabel takes the text of its value as the label of the input it is for, and the validation messages use it. In the scratch application this worked with p:inputText on both implementations, and it overrode a label attribute that the input also had: with p:outputLabel value="Outer label" and label="Attribute label" the message said Outer label: Validation Error: Value is required.. And a standard h:outputLabel does not do it: the label="Attribute c" of its h:inputText was used, and an input with neither shows its client id (f:d: Validation Error...).

The required asterisk of p:outputLabel follows indicateRequired. In the scratch form all seven labels of properties with such constraints showed the asterisk without a required attribute anywhere.

p:datePicker

p:datePicker replaced p:calendar. The 10.0 migration guide deprecated the calendar in favour of it, and the tag calendar is still in the tag library of PrimeFaces 16.0.0. What was measured in the scratch form (Mojarra and MyFaces gave the same results apart from the label prefix of Mojarra and MyFaces):

  • The browser posted the text of the field, finished_input=01/01/2020, and the server parsed it with the pattern.

  • A text that is not a date (not a date), and an ISO date (2020-01-01) for a dd/MM/yyyy pattern, gave Finished on: 'not a date' could not be understood as a date. and the same for the ISO string. Always post in the pattern of the field.

  • With maxdate set to today, widget.setDate(new Date(2999,0,1)) in the browser ended up at today’s date (the picker clamps). A forged post of 31/12/2999 was stopped by the Bean Validation message of @PastOrPresent: the only message was must be a date in the past or in the present. maxdate is a convenience for the visitor, not a guard on the server.

  • locale="es" alone changed nothing in the labels: the open panel still showed Jan Feb Mar ... and Today Clear. The labels come from PrimeFaces.locales, and only the English file was loaded. Load the locale script with <h:outputScript name="locales/locale-es.js" library="primefaces"/> (it exists: HTTP 200, 13,839 bytes, with accept:"Sí", addRule:"Agregar regla" and so on, and the Spanish validation messages for CSV) or rely on the context parameter primefaces.CLIENT_SIDE_LOCALISATION, whose default is true (see the context parameters): it adds locales/locale-<language>.js for the locale of the view automatically, so the manual script is needed only for a language the view locale does not select, or when the parameter is false.

p:autoComplete

p:autoComplete sends the typed text to a completeMethod that returns the suggestions. For strings that is all. For objects it needs var, itemLabel (what the list shows), itemValue (what is submitted) and a converter, as in the form above: the browser keeps the converter’s string in a hidden field (book_hinput=1) and shows the label in the visible one (book_input=Dune).

The request it sends is its own, not a command’s: source, execute and render are all the component itself, and the text travels as review:book_query=Du. Measured behaviour of the attributes used in the scratch application:

Attribute Observed

minQueryLength

minQueryLength="2": typing one character sent no request; the second character sent one.

queryDelay

Default 300 ms; the form uses 100.

maxResults, moreText

maxResults="3" showed three suggestions and a last line with the text of moreText; there is no default action for that line.

dropdown

Adds a button that starts a search, with an empty query or with the current text, as dropdownMode says.

forceSelection

Typing a text that matches no suggestion and leaving the field cleared it.

multiple, unique, selectLimit

The value is a List; each selected item becomes a token.

cache, cacheTimeout

Suggestions of an identical query are served from the browser (documented; not measured).

Consumes a REST endpoint instead of calling a bean method, for a method that does not need the Faces lifecycle (documented; not exercised).

escape

Default true: HTML in suggestions is escaped.

The completeMethod gets raw text from the browser. Use it as a parameter of a query, never as a part of a string that is run as JPQL or SQL, and limit the result (maxResults limits what is shown, not what is fetched). The method runs a full Faces request in the lifecycle of the component; keep it fast.

p:chips

p:chips collects free-form values as tokens. The value is a List (of strings, or of objects with a converter). Pressing Enter adds the typed text as a chip; max limits their number, unique rejects duplicates, separator splits text on paste with addOnPaste, and addOnBlur adds the pending text when the field loses focus. The client widget has addItem(value), removeItem(value) and toggleEditor(). p:inputMask

p:inputMask forces the text into a template. The mask attribute is required (since 7.0). The characters are 9 for a digit, a for a letter, A for an upper-case letter, * for a letter or digit and [ ] around an optional part; everything else is a literal. Other attributes: slotChar (the placeholder, _), autoClear (clear the field if the mask is not complete), showMaskOnFocus, showMaskOnHover and validateMask.

In the form, mask="AA-9999-9999" made typed ab12345678 appear as AB-1234-5678: the mask upper-cases, and the browser posts the value with its literals. Since PrimeFaces 8.0 the mask is also checked on the server (validateMask, default true), and the check does not produce a message. A forged ab-1234-5678, AB-12 or 12-ABCD-EFGH arrived in the bean as null. With @NotNull on the property the user got must not be null (Library card: must not be null on MyFaces), which is correct and unhelpful; without @NotNull the value is dropped without a word (Values That PrimeFaces Drops Without a Message). Set validateMask="false" only for masks that PrimeFaces cannot express, and then validate the pattern yourself. The widget methods are getValue() (with the mask), getValueUnmasked(), setValue(v), enable() and disable().

Client-Side Validation (CSV)

PrimeFaces Client Side Validation validates a form in the browser, with the same rules and the same messages as the server, before the request is sent. The documentation states its goals: compatibility with the server side (conversion and then validation, like the lifecycle), partial processing and update for Ajax, i18n, client-side renderers for the message components, custom client validators and converters, global or per-component switches, and Bean Validation integration. It works for PrimeFaces components only.

Switching It On

CSV is off by default. The global switch is a context parameter; the per-use switch is validateClient="true" on a p:commandButton, p:commandLink or p:remoteCommand. p:ajax has no such attribute (Validating While Typing: p:clientValidator is the way to validate on an event).

<context-param>
    <param-name>primefaces.CLIENT_SIDE_VALIDATION</param-name>
    <param-value>true</param-value>
</context-param>

The page rendered by PrimeFaces shows how it is wired. For validateClient="true" on an Ajax button and on a button with ajax="false", the generated onclick were (shortened):

<button id="f:ajax" ... onclick="if(PrimeFaces.vb({s:this,a:true,u:'f'})){PrimeFaces.ab({s:&quot;f:ajax&quot;,f:&quot;f&quot;,u:&quot;f&quot;});return false;}else{return false;}" type="submit">
<button id="f:nonajax" ... onclick="if(PrimeFaces.vb({s:this})){}else{return false;}" type="submit">

PrimeFaces.vb runs the validation of the processed inputs; if it fails, the handler returns false and nothing is sent. The global object PrimeFaces.settings in the page head carries the Faces settings that CSV mirrors (validateEmptyFields:true,considerEmptyStringNull:true in the scratch application, from the empty-value parameters).

Which inputs are validated depends on the request type:

  • Ajax (vb({a:true,u:'f'})): the inputs that the request processes (process), and the messages are rendered into the message components inside the update targets. Validation and update happen in the browser.

  • Non-Ajax: all visible, editable inputs of the form, and the message components have to be inside the form.

src/main/java/org/example/bookshelf/csv/Isbn13Validator.java
package org.example.bookshelf.csv;

import jakarta.faces.application.FacesMessage;
import jakarta.faces.component.UIComponent;
import jakarta.faces.context.FacesContext;
import jakarta.faces.validator.FacesValidator;
import jakarta.faces.validator.Validator;
import jakarta.faces.validator.ValidatorException;

import org.primefaces.validate.ClientValidator;

import java.util.Map;

@FacesValidator("bookshelf.isbn13")
public class Isbn13Validator implements Validator<String>, ClientValidator {

    public static boolean isValid(String isbn) {
        if (isbn == null || !isbn.matches("\\d{13}")) {
            return false;
        }
        int sum = 0;
        for (int i = 0; i < 13; i++) {
            sum += (isbn.charAt(i) - '0') * (i % 2 == 0 ? 1 : 3);
        }
        return sum % 10 == 0;
    }

    @Override
    public void validate(FacesContext context, UIComponent component, String value) {
        if (value == null || value.isBlank()) {
            return;
        }
        if (!isValid(value)) {
            throw new ValidatorException(new FacesMessage(FacesMessage.SEVERITY_ERROR,
                    "Invalid ISBN", "'" + value + "' is not a valid ISBN-13."));
        }
    }

    @Override
    public Map<String, Object> getMetadata() {
        return Map.of();
    }

    @Override
    public String getValidatorId() {
        return "bookshelf.isbn13";
    }
}

What CSV Does Not Do

  • It is not a security control. The validation runs in the browser, only when a command with validateClient="true" is used. The same form posted by a script, or with JavaScript off or edited, reaches the server, which validates again. The scratch application used this on purpose: the Save (server only) button posted invalid data and received the server’s messages; the raw posts of Values That PrimeFaces Drops Without a Message did the same. Keep every rule on the server, as the Bean Validation page does.

  • Only PrimeFaces components. A h:inputText, h:selectOneMenu and so on are posted unchecked (the Plain field above).

  • Components without metadata. p:selectCheckboxMenu rendered no data-p-val, so its @NotEmpty was enforced on the server only. Look at the markup of a component (the data-p-* attributes) when in doubt.

  • Hidden fields. The script of PrimeFaces.validation.validate filters out invisible inputs unless validateInvisibleElements is true, so a field in a hidden panel is not validated by a button click.

  • Messages need a target. No p:message, p:messages or p:growl in the form (for a full submit) or in update (Ajax) means that the click stops and nothing explains why; the validation function has a logUnrenderedMessages option for that case.

  • Locale. The client messages are in English unless the locale script of the language is on the page (p:datePicker).

p:defaultCommand

A form with several buttons has no standard "Enter submits this one". p:defaultCommand fixes it: nested in the form with a target that references a command (a p:commandButton or p:commandLink), it clicks that command when the user presses Enter in an input. An input must have the focus. scope names an ancestor of the inputs so that one form can have several default commands, each for its region.

The sign-up form above has <p:defaultCommand target="b1"/>. Pressing Enter in the confirmation field (no button focused) posted jakarta.faces.source=f:b1, f:b1=f:b1 and the form fields: the same request as clicking Register. The documentation example shows a target that does not match the id of the button in its own form; check that the id exists.

Source: PrimeFaces 16 documentation: DefaultCommand

p:focus

p:focus manages the focus: without attributes it focuses the first enabled, visible input of the page when the page loads, and after a failed validation it focuses the first invalid component. for focuses a specific component (useful in a dialog), context limits the search to a part of the page and minSeverity sets the lowest message severity that counts as invalid (default error). PrimeFaces.current().focus(expression) does the same from Java (PrimeFaces.current()).

Measured: the sign-up form (<p:focus/>) put the focus in the name field on load; after the failed password validation the focus was in the first password field. The review form with <p:focus context="review"/> focused the reviewer, the first invalid field, after the empty submit. An Ajax request moves the focus only if the p:focus is updated in the response (the documentation says so; the forms above update the whole form, which includes it).

Ajax Errors: p:ajaxExceptionHandler and the PrimeFaces ExceptionHandler

The general treatment of exceptions, error pages and the standard Ajax error element is on the exception handling page, which describes the PrimeFaces chain from the documentation (its section); this section reports what happened when it was run. The PrimeFaces documentation describes two levels. On the client, an error in an Ajax response (a server-reported error element, or a failed or timed-out connection) is handed to the onerror callbacks and global listeners, then to a matching p:ajaxExceptionHandler, then to a redirect to the matching error-page, and last to the console. On the server, PrimeFaces offers its own ExceptionHandler that redirects to the error page for Ajax requests as well, and exposes the exception through the EL name pfExceptionHandler (type, message, stackTrace, formattedStackTrace, timestamp, formattedTimestamp).

The PrimeFaces handler and its EL resolver are opt-in, in faces-config.xml:

<application>
    <el-resolver>org.primefaces.application.exceptionhandler.PrimeExceptionHandlerELResolver</el-resolver>
</application>
<factory>
    <exception-handler-factory>org.primefaces.application.exceptionhandler.PrimeExceptionHandlerFactory</exception-handler-factory>
</factory>

The action fail() throws an IllegalStateException whose message has a (fake) JDBC URL, to see what leaks. Without the PrimeFaces ExceptionHandler (Production stage):

The type matched on MyFaces too.

And treat pfExceptionHandler.message as sensitive: it printed the JDBC URL. Show a fixed text and a correlation id, as the exception handling page does. Rendering errors need jakarta.faces.FACELETS_BUFFER_SIZE big enough for the response not to be committed, or no handler can redirect.

Security Notes

  • The server decides. CSV, maxdate, min/max, masks, maxlength and partialSubmit are conveniences for the visitor. A forged post changes or omits anything the browser sent (Values That PrimeFaces Drops Without a Message), and a missing parameter skips validation of that field. Repeat each rule that matters in the action or the service (see the security page), and treat everything that arrives through p:remoteCommand parameters, completeMethod queries and callback names as untrusted input.

  • Escaping. Keep escape="true" (the default) on p:messages, p:message, p:growl and p:autoComplete; the scratch run showed script execution with escape="false" (p:messages, p:message and p:growl). Never write formattedStackTrace unescaped (Ajax Errors: p:ajaxExceptionHandler and the PrimeFaces ExceptionHandler).

  • Callback arguments are plain JSON in the response; do not put secrets or personal data into addCallbackParam.

  • View state and CSRF. Every PrimeFaces Ajax request in the scratch application carried jakarta.faces.ViewState, like a Faces postback, and the protections of the security page (protected views, SameSite, the same-origin checks) apply to them unchanged. A state-changing p:button or link with outcome is a GET and has the problems of any GET.

  • Content Security Policy. The handlers shown above are inline (onclick="PrimeFaces.ab(...)"). PrimeFaces has its own CSP support (primefaces.CSP, primefaces.CSP_POLICY); the security page reports what was run: a p:commandButton worked on both implementations with it, a h:commandButton with f:ajax failed on Mojarra only.

  • Passwords. Do not log them, do not return them in callback arguments, and hash them with a password hash. redisplay stays false.

  • Dependencies. The Ajax and CSV scripts are served from the application (the jakarta.faces.resource URLs), not from a CDN; keep PrimeFaces updated as a security dependency.

Mojarra and MyFaces

PrimeFaces gave the same results on Mojarra 4.1.17 and MyFaces 4.1.4 for the request format, the generated handlers, process and update resolution, partialSubmit, the callbacks and their arguments, PrimeFaces.current(), p:remoteCommand, p:autoUpdate, the input components, the silent drops, the message components, the whole of CSV, p:defaultCommand and p:focus. The differences found in the scratch application:

  • No-argument p:ajax listener. It worked on MyFaces, unlike the no-argument f:ajax listener that the Ajax page reports as failing there.

  • Form marker. Mojarra posts the form id as a parameter (f=f), MyFaces posts formId_SUBMIT=1. A raw post to a MyFaces page without that parameter is treated as if nothing was submitted and no validation runs, so scripts that replay requests need it.

  • Checkbox value. h:selectBooleanCheckbox posted on on Mojarra and true on MyFaces.

  • Phase id text. INVOKE_APPLICATION 5 against INVOKE_APPLICATION(5).

  • Generated ids. j_idt6 against j_id_a, and the view state element ids, as on the Ajax page.

  • A process that leaves out the command. Mojarra did not run the action of a button with process="a b"; MyFaces did (Partial Processing: A Dependent Menu).

  • Bean Validation messages on the server. MyFaces prefixes the label (Email: must be a well-formed email address), Mojarra does not. The client-side messages of CSV have the label on both.

  • Ajax error element. Mojarra reports the exception class and "See your server log for more information" in Production; MyFaces reports ContextAwareELException with the complete text, and p:ajaxExceptionHandler without the PrimeFaces ExceptionHandler does not match there (Ajax Errors: p:ajaxExceptionHandler and the PrimeFaces ExceptionHandler).

  • Cancel buttons. Without resetValues, the invalid field shows an empty text on Mojarra and the model value on MyFaces (resetValues and Cancel Buttons).

  • maxlength of the standard h:inputText. A post of ten characters for maxlength="3" was stored whole on Mojarra and ignored (the old value stayed, no message) on MyFaces; p:inputText cut it to three on both.

The versions of the books. RequestContext.getCurrentInstance(), p:calendar, javax.faces, the ThemeRoller themes and the first CSV.

Where the Books Are Outdated

Çalışkan and Varaksin (the PrimeFaces cookbook of 2015, PrimeFaces 5.1 and 5.2 on Faces 2.2) are the one book that is about this page; their chapters on Ajax and partial processing, on the inputs, on client-side validation and on the advanced topics map to the sections above. Burns and Schalk, and Leonard, write about f:ajax and the standard validators, on the Ajax and validators pages. Jonna’s book is about the PrimeFaces Extensions, which have their own page. What has changed:

  • RequestContext. The books use RequestContext.getCurrentInstance() to update components, add callback parameters and run scripts. Today it is PrimeFaces.current() with ajax().update(...), ajax().addCallbackParam(...) and executeScript(...) (PrimeFaces.current()).

  • p:calendar. It is deprecated (since 10.0); p:datePicker takes java.time values and works with LocalDate by default. The attribute names and the pattern syntax differ, as do the locale scripts.

  • Client-side validation. The framework of the book is the ancestor of the present one, with the same ideas (validateClient, p:clientValidator, ClientValidator, Bean Validation integration), but the context parameter, the packages (jakarta.*), the message handling and the JavaScript API changed (Client-Side Validation (CSV)); copy nothing from a PrimeFaces 5 CSV example without reading the present documentation.

  • Removed features. p:push, the autoUpdate attributes, p:watermark (use placeholder) and the mobile components are gone or replaced. Themes and icons are on the page about getting started with PrimeFaces.

  • Caching. The book’s caching chapter is about p:cache, which the performance page covers.

  • Namespaces. javax.faces becomes jakarta.faces and the http://primefaces.org/ui namespace is still accepted (the scratch pages use it; a page with xmlns:p="primefaces" rendered the same Ajax handler).

Common Mistakes

  • The command processes the whole view. A p:commandButton without process executes @all; one required field elsewhere blocks it. Set process="@this" or "@form".

  • The action does not run. process="@none", or (on Mojarra) a list that leaves out the command, skips the action. Add @this.

  • The error message never appears. The message component is not in update (or not auto-updated).

  • update with a typo fails the page. Identifiers are resolved at render time; prefer wrappers that are always rendered; use ignoreComponentNotFound only for optional parts.

  • A cancel button shows stale values. Add resetValues="true" or use p:resetInput.

  • onerror is not called for an exception. It is for transport failures; use p:ajaxExceptionHandler and register the PrimeFaces ExceptionHandler.

  • Callback arguments are empty. A Map or a record did not serialise; use a JavaBean.

  • The docs say addCallBackParam. The method is addCallbackParam.

  • A server rule that only the browser enforces. maxdate, min, max and maxlength drop values silently on the server; validate in the service. A missing parameter skips @NotNull.

  • must not be null for a card number. The mask check turned a mismatching value into null; show a message of your own, or validate the pattern with the mask check off.

  • Custom client validator never runs. The script was loaded before PrimeFaces (use target="body"), the id does not match getValidatorId(), or the component renders no CSV metadata.

  • h:inputText is not validated in the browser. CSV is for PrimeFaces components.

  • Doubled messages with CSV. Use the default showDetail on messages that CSV fills.

  • locale="es" shows English. Load the locale script by hand, or check that primefaces.CLIENT_SIDE_LOCALISATION was not set to false and that the view locale is the one you expect.

  • Password fields come back empty. That is redisplay="false"; keep it.

  • Passing a user id through p:remoteCommand. Check access to that id on the server.

  • escape="false" on messages, or formattedStackTrace unescaped. Script injection and information disclosure.

  • Enter submits the wrong button. Without p:defaultCommand the browser uses the first submit button of the form; add it and name the target.

  • A p:focus that does not move the focus after Ajax. It was not in update.
