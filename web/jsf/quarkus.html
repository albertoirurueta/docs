Jakarta Faces on Quarkus: myfaces-quarkus, quarkus-primefaces and quarkus-omnifaces

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Faces 4.1 as implemented by Apache MyFaces 4.1.4, packaged for Quarkus by the myfaces-quarkus extension 4.1.4, on the Quarkus platform 3.33.1 (the main runs) and 3.40.1 (the PrimeFaces run and the project generated by the Maven create goal), with Java 21 as the compiler release. The component-library extensions are quarkus-primefaces 4.16.0 (which bundles PrimeFaces 16.0.0; quarkus-primefaces-extensions 4.16.0 adds PrimeFaces Extensions 16.0.0) and quarkus-omnifaces 5.5.4 (OmniFaces 5.5.4; the current OmniFaces release is 5.5.5). Everything was built and run on 2026-10-08 on a Mac with JDK 26, compiling with --release 21. Quarkus 4.0.0.Beta1 is published; the MyFaces extension started on it and served a page, but nothing below describes Quarkus 4. Faces 5.0 is not covered: it is still a milestone.

Quarkus is not a servlet container into which you drop a WAR. It is a build tool that analyses your application, runs extensions at build time and produces a runnable jar. Faces runs on top of the Undertow servlet layer, with CDI provided by ArC, Quarkus' build-time CDI container. That changes where files live, what a backing bean may be, what survives a restart and what the build can and cannot do for you. Only the MyFaces-based extensions are covered here; the Mojarra and Tomcat routes are the subject of Jakarta EE Servers and Tomcat and Weld.

How Faces Fits Into Quarkus

The Faces extension has build steps that run while Quarkus builds your application and a small runtime. At build time it indexes your classes, registers the FacesServlet for *.xhtml when web.xml does not declare one, produces the context parameters that wire MyFaces to Quarkus (an injection provider and a Faces initializer), registers the Faces scopes as ArC contexts and records every class carrying a Faces or CDI annotation so MyFaces does not have to scan the classpath at startup. The result is a jar that starts in well under two seconds.

flowchart LR A["pom.xml with the Quarkus Maven plugin"] --> B["Build: Jandex index, ArC, extension build steps"] B --> C["Recorded: FacesServlet, init parameters, view and flow scoped contexts, annotated classes"] C --> D["target/quarkus-app (fast-jar) or one uber-jar"] D --> E["java -jar: Undertow, ArC and MyFaces start"] E --> F["Requests reach FacesServlet at the context path"]

Source: Apache MyFaces Core: Getting Started, Quarkus section and Quarkus: Contexts and Dependency Injection reference

The Faces lifecycle itself (see the lifecycle page) is unchanged: the same six phases, the same FacesContext. What differs is everything around it, and that is what the rest of this page covers. The general Quarkus topics (CDI, configuration, packaging, dev mode, tests) have their own pages in the Quarkus section of this site: CDI and the Programming Model, Configuration, Developer Experience, Packaging and JVM Modes, Native Executables and Testing Quarkus Applications. This page adds only the Faces-specific parts.

Project Setup

The Bookshelf project of this page is a plain Maven project: the Quarkus BOM, one extension dependency, and the Quarkus Maven plugin. There is no WAR packaging, no jakarta.jakartaee-web-api and no maven-war-plugin.

Where Files Go

A Quarkus application is packaged as a jar, so there is no src/main/webapp and no WEB-INF. The layout that was run:

The Bookshelf layout for Quarkus
bookshelf-quarkus/
  pom.xml
  src/main/java/org/example/bookshelf/
    model/Book.java
    service/BookService.java
    web/CatalogueBean.java
  src/main/resources/
    application.properties                      Quarkus configuration
    META-INF/web.xml                            replaces WEB-INF/web.xml
    META-INF/faces-config.xml                   replaces WEB-INF/faces-config.xml
    org/example/bookshelf/messages.properties   resource bundle, var msg
    org/example/bookshelf/messages_en.properties
    org/example/bookshelf/messages_es.properties
    META-INF/resources/                         the web root
      catalogue.xhtml                           views
      expired.xhtml
      resources/css/site.css                    Faces resource library "css"
      WEB-INF/templates/layout.xhtml            template, not reachable by URL
  src/test/java/org/example/bookshelf/web/CatalogueTest.java

Source: Apache MyFaces Core: Getting Started, "Differences to a normal servlet container while developing" and Jakarta EE Tutorial: Configuring Jakarta Faces Applications

Behaviour observed on this layout:

  • Views, resource libraries and static files under src/main/resources/META-INF/resources are the web root. A file placed in src/main/webapp is ignored: a view put there answered HTTP 404.

  • web.xml and faces-config.xml are read from META-INF of the classpath, the way a library jar supplies its own.

  • Templates and other include files can live in META-INF/resources/WEB-INF/templates/. A request for /WEB-INF/templates/layout.xhtml answers 404 (the directory is hidden), while template="/WEB-INF/templates/layout.xhtml" inside a view resolves. That keeps the section’s template path (/WEB-INF/templates/layout.xhtml) working unchanged. A template in META-INF/resources/templates/ also works but is a normally addressable view.

  • Everything else under META-INF/resources is public. A resource library file such as resources/css/site.css is served twice: through Faces at /jakarta.faces.resource/site.css.xhtml?ln=css and as a static file at /resources/css/site.css. Nothing under that tree should be secret.

  • Files outside META-INF/resources (for instance messages.properties and META-INF/web.xml) answered 404 when requested.

The Catalogue

The code is the usual Bookshelf: a Book record, an application-scoped BookService and a view-scoped CatalogueBean with a search field. Packages and the bundle variable msg follow the conventions of the section.

Book.java, BookService.java and CatalogueBean.java
package org.example.bookshelf.model;

import java.io.Serializable;

public record Book(long id, String title, String author, int year) implements Serializable {
}
package org.example.bookshelf.service;

import jakarta.enterprise.context.ApplicationScoped;
import java.util.List;
import org.example.bookshelf.model.Book;

@ApplicationScoped
public class BookService {

    private final List<Book> books = List.of(
            new Book(1, "Dune", "Frank Herbert", 1965),
            new Book(2, "Neuromancer", "William Gibson", 1984),
            new Book(3, "The Left Hand of Darkness", "Ursula K. Le Guin", 1969));

    public List<Book> findAll() {
        return books;
    }
}
package org.example.bookshelf.web;

import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;

@Named
@ViewScoped
public class CatalogueBean implements Serializable {

    @Inject
    BookService service;

    private String query = "";

    public List<Book> getBooks() {
        return service.findAll().stream()
                .filter(b -> b.title().toLowerCase().contains(query.toLowerCase()))
                .toList();
    }

    public String getQuery() {
        return query;
    }

    public void setQuery(String query) {
        this.query = query == null ? "" : query;
    }
}

Source: Jakarta EE Tutorial: Developing a Simple Facelets Application and Quarkus: Contexts and Dependency Injection reference

The injected field is package-private on purpose: the Quarkus guide recommends avoiding private injection members because native image needs reflection to reach them (a private field also works on the JVM, as shown later). The bean stays Serializable so that the same class also runs unchanged on the servers of the other pages; ArC does not require it (see ArC, Scopes and Injection).

The Ajax search was exercised with a raw partial request (execute set to the input, render set to the table): the response carried only the matching row. The @form keyword is resolved by the client script before the request is sent; a hand-built request that sends the literal @form as jakarta.faces.partial.execute did not apply the input in the runs, so a curl test has to send the form id. Source: Jakarta EE Tutorial: Configuring Jakarta Faces Applications

The messages_en.properties file is not decoration. With only messages.properties and messages_es.properties, a request with Accept-Language: en on a machine whose JVM default locale is Spanish rendered the Spanish title: the JDK’s ResourceBundle fallback tries the default locale’s bundle before the base bundle. The same happens on every Faces runtime, but on Quarkus the JVM default locale is that of the build or container host, which makes it easy to meet in a container. A bundle for every supported locale, English included, removes the dependency on the host. See Messages and Internationalisation.

The extension reads jakarta.faces.PROJECT_STAGE through MicroProfile Config while building and writes the result into the servlet initialisation parameters, so a web.xml entry for the stage has no effect, and a deployment cannot change it with an environment variable afterwards: it is fixed at build time, like the context path. Use the property (Quarkus profile prefixes such as %dev. are standard configuration syntax; they were not run for this property) and let the defaults do the rest. See the project stage section for what each stage changes.

The context root follows the same rule. quarkus.servlet.context-path=/bookshelf given when building made the application answer under /bookshelf/ and 404 at /, and every generated URL (resource links, form actions) carried the prefix. Setting QUARKUS_SERVLET_CONTEXT_PATH only when launching the jar changed nothing, because the value had already been baked in by the build.

ArC, Scopes and Injection

Quarkus' CDI container, ArC, implements CDI Lite plus selected extras (Decorators, parts of BeanManager, @SessionScoped with Undertow), not CDI Full. For Faces this means several things that Weld users take for granted need attention. Each statement below was run against myfaces-quarkus 4.1.4.

Table 3. Behaviour of ArC with Faces beans (production jar, Quarkus 3.33.1)
Pattern Result

A @ViewScoped bean that is not Serializable

works: a click counter incremented across postbacks with state kept in the view scope

A @Named bean with a private injected field, or a final class with constructor injection and no no-argument constructor

both work (ArC is more permissive than Weld here)

An @Inject field in a plain @FacesConverter("id") class

the field is null; the converter was created without CDI

The same converter with @FacesConverter(value = "id", managed = true)

the field is injected

CDI.current().select(Hidden.class) for an @ApplicationScoped bean nothing injects

not resolvable: the bean was removed as unused; resolvable once annotated @io.quarkus.arc.Unremovable

A @Named bean referenced only from Expression Language

kept: the @Named qualifier makes it unremovable

A @ConversationScoped bean

builds, then fails at render time with ContextNotActiveException
A converter that needs a service: managed, so that the injection happens
package org.example.bookshelf.web;

import jakarta.faces.component.UIComponent;
import jakarta.faces.context.FacesContext;
import jakarta.faces.convert.Converter;
import jakarta.faces.convert.FacesConverter;
import jakarta.inject.Inject;
import org.example.bookshelf.service.BookService;

@FacesConverter(value = "bookshelf.title", managed = true)
public class TitleConverter implements Converter<String> {

    @Inject
    BookService service;

    @Override
    public String getAsObject(FacesContext context, UIComponent component, String value) {
        return value == null ? null : value.trim();
    }

    @Override
    public String getAsString(FacesContext context, UIComponent component, String value) {
        return value;
    }
}

Source: Jakarta Faces 4.1 API: FacesConverter and Quarkus: Removing unused beans

A bean looked up programmatically has to be kept explicitly
package org.example.bookshelf.service;

import io.quarkus.arc.Unremovable;
import jakarta.enterprise.context.ApplicationScoped;

@Unremovable
@ApplicationScoped
public class AuditTrail {
    public String hello() {
        return "audit-ok";
    }
}

Source: Quarkus: Removing unused beans

What this means in practice:

  • The extension registers ArC contexts for @ViewScoped, @FlowScoped, @ClientWindowScoped and Faces' own scope annotation, so those scopes work the way they do on a server. It does not provide @ConversationScoped: the MyFaces extension documentation lists that scope as unsupported and the run above shows the failure mode. Replace conversations with @ViewScoped, a flow (see Faces Flows) or an explicit entity id in a view parameter. See the conversation section of the scopes page.

  • Because ArC removes unused beans at build time, anything that is looked up by name at run time (CDI.current(), Instance<T> with a qualifier, BeanManager) needs @Unremovable or a reference in the dependency tree. Beans reached through Expression Language need no annotation, because @Named marks them as in use.

  • Injection into Faces artefacts that are not CDI beans (a custom NavigationHandler, ViewHandler and the like) is not supported by the extension, according to its documentation. Use a managed converter or validator, a CDI bean, or CDI.current(). See Extending Faces for the artefacts involved and Backing Beans and CDI for the standard CDI rules.

  • @Inject FacesContext works in request-scoped beans; the bean that printed the project stage for the table above did exactly that.

State Saving, Sessions and Restarts

Quarkus keeps HTTP sessions in memory, in the single process. The MyFaces extension documentation states that Quarkus does not support session replication, passivation or clustering, and that Quarkus beans are not serialisable for that purpose anyway. On this page that has three consequences.

  • With the default server state saving, the view state lives in the session and a restart loses it. Every form open in a browser then fails with ViewExpiredException on the next postback: the error-page of the web.xml above renders expired.xhtml in Production, and in Development (dev mode) MyFaces writes its own development error page.

  • With client state saving the view state travels in the page, so a restart does not lose it, but only if the encryption key survives the restart. Without configured keys MyFaces generates random ones at startup, and the old state could not be decrypted afterwards: the postback answered HTTP 500 and the log showed ViewExpiredException.

  • A syntactically wrong jakarta.faces.ViewState value (not Base64) answered HTTP 500 with an IllegalArgumentException ("Last unit does not have enough valid bits") instead of an expired-view page. The page redirect from error-page is only applied for ViewExpiredException.

The keys belong in the environment, not in the source. Quarkus has no ${...} substitution inside web.xml, so a listener copies them from MicroProfile Config into the servlet context before MyFaces reads them:

web.xml (state saving method) and StateKeys.java (keys from configuration)
<context-param>
    <param-name>jakarta.faces.STATE_SAVING_METHOD</param-name>
    <param-value>client</param-value>
</context-param>
package org.example.bookshelf.web;

import jakarta.servlet.ServletContextEvent;
import jakarta.servlet.ServletContextListener;
import jakarta.servlet.annotation.WebListener;
import org.eclipse.microprofile.config.ConfigProvider;

/** Copies the client-state keys from runtime configuration (environment) into the servlet context. */
@WebListener
public class StateKeys implements ServletContextListener {

    @Override
    public void contextInitialized(ServletContextEvent event) {
        var config = ConfigProvider.getConfig();
        config.getOptionalValue("myfaces.secret", String.class)
                .ifPresent(v -> event.getServletContext().setInitParameter("org.apache.myfaces.SECRET", v));
        config.getOptionalValue("myfaces.mac-secret", String.class)
                .ifPresent(v -> event.getServletContext().setInitParameter("org.apache.myfaces.MAC_SECRET", v));
    }
}
# Generated once per environment and stored in a secret store, never in the repository.
export MYFACES_SECRET="$(openssl rand -base64 16)"        # AES key, 16 bytes
export MYFACES_MAC_SECRET="$(openssl rand -base64 32)"    # HMAC key, 32 bytes
java -jar target/quarkus-app/quarkus-run.jar

Source: Apache MyFaces 4.1 documentation and Quarkus: Configuration reference

Quarkus maps the environment variable MYFACES_SECRET to the property myfaces.secret. The sequence that was run: start with both variables, open the catalogue, stop the process, start it again with the same variables and post the old view state back (the click was applied, HTTP 200); then start it without variables and post the same state (HTTP 500, ViewExpiredException). The keys were 16 and 32 random bytes in Base64. All nodes of a deployment need the same two values, which is the multi-instance rule of the client-state keys section. For the cost and the audit of client state see the audit section. Client state also puts the encrypted view into every page, which matters for the size of the response; measure it with the state saving part of the performance page.

Tests

@QuarkusTest boots the application once and gives the test the real HTTP port. The Faces project stage in tests is SystemTest, which is why the log of a test run shows the system-test banner. The Arquillian approach of the testing page is not needed on Quarkus; a Quarkus test already runs against a started application.

CatalogueTest.java: a Quarkus test over HTTP/1.1
package org.example.bookshelf.web;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

import io.quarkus.test.common.http.TestHTTPResource;
import io.quarkus.test.junit.QuarkusTest;
import java.net.URI;
import java.net.URL;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import org.junit.jupiter.api.Test;

@QuarkusTest
class CatalogueTest {

    @TestHTTPResource("/catalogue.xhtml")
    URL catalogue;

    @Test
    void catalogueListsTheBooks() throws Exception {
        HttpRequest request = HttpRequest.newBuilder(URI.create(catalogue.toString()))
                .header("Accept-Language", "en")
                .build();
        HttpResponse<String> response = HttpClient.newBuilder()
                .version(HttpClient.Version.HTTP_1_1)
                .build()
                .send(request, HttpResponse.BodyHandlers.ofString());
        assertEquals(200, response.statusCode());
        assertTrue(response.body().contains("<td>Dune</td>"));
        assertTrue(response.body().contains("<h1>Catalogue</h1>"));
    }
}

Source: Quarkus: Testing your application

mvn test ran this test green. Two details cost time. First, the default HttpClient of the JDK asks for an HTTP/2 upgrade, and the test failed with Received RST_STREAM: Not an error while the log reported the request being handled after the shutdown; pinning HttpClient.Version.HTTP_1_1 fixed it. Second, the English assertion needed the Accept-Language header and the messages_en.properties file described earlier. For browser-level tests of Ajax and view state see the Faces testing page and End-to-End Testing in the Browser; the Quarkus side is in Testing Quarkus Applications.

Packaging: Fast-Jar, Uber-Jar and Containers

The default package type is the fast-jar: target/quarkus-app/quarkus-run.jar with its libraries beside it. The MyFaces extension documentation says that Quarkus uber-jars are not supported, referring to MYFACES-4427. That statement is out of date for the versions on this page: the issue is fixed in 4.0.3, 4.1.0-RC3 and 5.0.0, and the extension has a build step that merges the service files and faces-config.xml for uber-jars.

Building and running the two package types
# fast-jar (default): target/quarkus-app/quarkus-run.jar plus lib/
mvn package
java -jar target/quarkus-app/quarkus-run.jar

# one uber-jar: target/bookshelf-quarkus-1.0.0-SNAPSHOT-runner.jar
mvn package -Dquarkus.package.jar.type=uber-jar
java -jar target/bookshelf-quarkus-1.0.0-SNAPSHOT-runner.jar

Source: Quarkus: Creating a project with Maven, uber-jar and MYFACES-4427: Cannot open any pages in Quarkus with uber-jar

Both were built and served the catalogue: the MyFaces-only uber-jar was about 20 MB and the PrimeFaces uber-jar about 80 MB, and the PrimeFaces uber-jar rendered a page with its theme and stylesheet links and served the PrimeFaces jQuery resource. The fast-jar is the better default for containers because the libraries form a layer that changes less often than your classes; see Packaging and JVM Modes and Container Images. The Faces-specific deployment topics (the Production stage, state saving across several instances, the clustered picture) are on the deployment and clustering page: this page only adds that Quarkus has no session replication, so several instances need sticky sessions with server state or the shared keys of State Saving, Sessions and Restarts with client state.

Native Image

A native executable removes the JVM and starts in milliseconds, at the price of closed-world analysis. The MyFaces extension helps: its build steps register renderers, system events, StateHolder implementations and the factory classes for reflection, and the CDI side uses ArC, which is built for native. None of that was run here, because no GraalVM or Mandrel installation and no running container daemon were available on the test machine. This section therefore lists only what the extensions document:

  • The Quarkus CDI guide recommends avoiding private members in beans, since the build must register reflective access for them; use package-private fields, as CatalogueBean does.

  • PrimeFaces on native: FeedReader is not supported, and reflection-sensitive EL (size(), name()) may fail.

  • Any EL expression, converter or validator that reaches a class through reflection that the extension did not register needs a @RegisterForReflection annotation. The Quarkus native guide describes the mechanism and how to find the missing registration.

  • The generated native build command (from the project the Maven plugin created) is ./mvnw package -Dnative, or, without GraalVM installed, ./mvnw package -Dnative -Dquarkus.native.container-build=true.

Treat all of this as untested for Faces on 4.1.4 until you build it. See Native Executables for the general trade-offs.

What Changed

  • Faces 2.3 era. The MyFaces documentation says it has had a Quarkus extension "since 2.3-next", and the extension catalogue lists the first release of myfaces-quarkus on 2020-06-30. The Quarkiverse extensions for PrimeFaces and OmniFaces exist alongside it; their first release dates were not checked.

  • Quarkus 3 and Jakarta EE. The extensions moved to jakarta.* with Quarkus 3. The current MyFaces extension (4.1.4) requires Quarkus core 3.27 or later; quarkus-primefaces 4.16.0 requires 3.33 or later and declares Java 21 as its minimum.

  • Faces 4.0 and 4.1. Version 4.0.x of the extension provides Faces 4.0; 4.1.x provides Faces 4.1. The uber-jar problem MYFACES-4427 was fixed in 4.0.3 and 4.1.0-RC3. jakarta.faces.AUTOMATIC_EXTENSIONLESS_MAPPING is handled by the extension build step.

  • Quarkus 3.31. quarkus-junit5 became a relocation to quarkus-junit.

  • Faces 5.0 (upcoming) and Quarkus 4. Both exist as milestones or betas (Faces 5.0.0-M9, Quarkus 4.0.0.Beta1). Nothing here describes them.

Where the Books Are Outdated

All eight books in the bibliography predate Quarkus (first released in 2019) and the MyFaces extension (2020), so none describes this runtime. What they do describe differs from what you will do here in several ways.

  • The deployment chapters of the Faces 1.x and 2.x books assume a WAR copied to a servlet container or application server, with WEB-INF/web.xml mapping FacesServlet to *.jsf, /faces/* or *.faces. On Quarkus there is no WAR, the servlet is registered for *.xhtml by the extension, and the descriptors live in META-INF.

  • The books register beans in faces-config.xml (managed-bean), use #{...} managed properties and rely on @ManagedBean. These were removed in Faces 4.0; Quarkus has only CDI beans, resolved by ArC at build time.

  • The Spring, Seam and Hibernate recipes of the cookbook-style books assume a dynamic container that scans at run time. A build-time container removes unused beans and cannot run portable extensions, which is the reverse of those recipes.

  • The JSF 2.x books call for Development in web.xml and the stage switch as a deployment decision. On Quarkus it is a build-time property with launch-mode defaults.

  • The books' hot-deployment advice (redeploy, JRebel, exploded directory) is replaced by quarkus:dev live coding.

  • Nothing in the books covers native image or container-first packaging; their sizing and startup assumptions (seconds to minutes of start, a gigabyte of heap) do not apply to a Quarkus jar.

  • The PrimeFaces books target PrimeFaces 4 and 5 and a primefaces-themes setup by jar; the Quarkus extension bundles PrimeFaces 16 and its libraries, and themes other than the default one come from the separate themes jar (see the themes section).

Pitfalls

  • Putting views in src/main/webapp. They are ignored (HTTP 404). Put them under src/main/resources/META-INF/resources.

  • Setting jakarta.faces.PROJECT_STAGE in web.xml. It is overridden by the extension: the stage is Production whatever the file says. Use the property, in the build.

  • Expecting QUARKUS_SERVLET_CONTEXT_PATH or the stage to change at launch. Both are build-time values.

  • Extensionless mapping and the library folders. With jakarta.faces.AUTOMATIC_EXTENSIONLESS_MAPPING set to true, my reading of the extension’s build step (not documented) is that the mapping is built from the views found under META-INF/resources before the step meets a folder named WEB-INF or resources. Observed once, on one machine and file system (directory order of the build output), a project that had WEB-INF/templates and resources/css mapped only one of its three views extensionless (the others answered 404 without the extension), and a project with neither folder mapped all three. Test this parameter on your exact layout before relying on it, or keep the .xhtml suffix.

  • Plain converters and validators with @Inject. The field stays null; use managed = true.

  • Looking beans up with CDI.current() or Instance. Unused beans are removed; annotate with @Unremovable.

  • @ConversationScoped. It compiles and then fails at render time with ContextNotActiveException.

  • Server state in production. Every restart or deploy expires every open form. Use client state with keys from the environment, or accept the expiry and design the expired.xhtml page for it.

  • Client state without keys. Random keys per start: old pages fail after a restart and different instances cannot read each other’s state.

  • Hibernate Validator locales. Register the locales you serve with quarkus.locales; otherwise an unregistered Accept-Language produces HTTP 500 with HV000250.

  • A missing English bundle. On a non-English JVM default locale, the base bundle is skipped for an English request. Ship a bundle for every supported locale.

  • Using f:websocket without testing it. The socket was closed with 1011 on Quarkus in the runs; use o:socket.

  • The JDK HttpClient in tests. Pin HTTP/1.1.

  • Leaving the Dev UI and development stage in a production image. The dev UI is dev mode only; the stage in a normal build is Production unless you set it. Check the startup log for the MyFaces development warning.

  • Secrets in the repository. The client-state keys, database passwords and PrimeFaces or OmniFaces tokens belong in the environment or a secret store, as the listener on this page reads them.
