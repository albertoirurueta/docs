Security: Authentication, Authorization, CSRF, XSS and CSP

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Jakarta Faces 4.1 (API jakarta.faces-api 4.1.2, part of Jakarta EE 11), Eclipse Mojarra 4.1.17 and Apache MyFaces Core 4.1.4, Jakarta Security 4.0 (the Jakarta EE 11 release; 3.0 in Jakarta EE 10), Jakarta Servlet 6.1 and Java 17 or later (the examples were compiled with --release 21), with PrimeFaces 16.0.0 where it is named. Faces 4.0 behaves the same for almost everything below; the differences are collected in What Changed by Version. Every example that is not marked "compiled against the 4.0 API" was deployed in a scratch Bookshelf WAR on Apache Tomcat 11.0.26 with Weld 6.0.4.Final, once with Mojarra and once with MyFaces, and driven with scripted HTTP requests and a headless Chrome page; each status code, header, message and exploit result quoted below was observed in those runs on 2026-10-08. Tomcat does not ship Jakarta Security, so the runs used Eclipse Soteria 3.0.4, the reference implementation of Jakarta Security 3.0 (the newest release on Maven Central on that day); what is specific to Jakarta Security 4.0, and everything that needs an external system (an OpenID Connect provider, a database or LDAP server), comes from the specification and the API and was compiled, not run. Claims taken only from documentation are marked as such. Faces 5.0 is still a milestone release (5.0.0-M9, 2026-09-18) and is described as upcoming, never as current behaviour.

Security is correctness. Every credential, key and secret in this page is a placeholder read from the environment or from the server’s configuration; no listing contains a literal password, client secret or encryption key, and the scratch runs generated their own random values at start-up. Where a well-known bad habit is mentioned, the page says what it breaks and shows the correct form.

Faces does not authenticate anyone. It is a presentation framework that runs inside a servlet container, and the container (with Jakarta Security on top of it) decides who the caller is. What Faces adds is a set of protections that belong to a component framework: escaping on output, a view state that doubles as a request-forgery token (with conditions), protected views, an encrypted client state, and a few APIs for reading the caller and setting cookie attributes. Real security comes from using all the layers, each for what it is good at.

Where Security Lives

A request passes through several layers before a Faces bean runs. A control that sits in an earlier layer cannot be undone by a mistake in a later one, which is why URL access belongs to the container and not to the XHTML.

The lifecycle position of each Faces control is in the six phases. Two of them matter for security. Restore View is where the view state is looked up and where the view protection check runs, so a forged request is rejected before any of your code sees a value. Invoke Application is where the action method runs; a role check inside the method (or the service it calls) is the last line, and it still holds when every check in the view has been passed or forged.

Authentication Mechanisms in Jakarta Security

Jakarta Security (jakarta.security.enterprise, originally the Java EE Security API of Java EE 8) standardises three things that servers used to configure in proprietary ways: how a caller authenticates (an HttpAuthenticationMechanism), against what (an IdentityStore) and how the application asks (SecurityContext). Each built-in mechanism is switched on by an annotation on any CDI-managed class of the application; the container then registers an @ApplicationScoped bean for it. The specification lists four:

Table 2. Built-in authentication mechanisms (Jakarta Security 4.0 specification, 2.4)
Annotation Behaviour Since

@BasicAuthenticationMechanismDefinition

HTTP Basic: the browser asks for credentials and sends them on every request. Not a Faces login; useful for REST endpoints next to the views

1.0

@FormAuthenticationMechanismDefinition

Servlet FORM login: a login page with a plain HTML form that posts j_username and j_password to j_security_check

1.0

@CustomFormAuthenticationMechanismDefinition

The same login-to-continue flow, but the application collects the credentials itself (a Faces form with validation, messages, Ajax) and calls SecurityContext.authenticate()

1.0

@OpenIdAuthenticationMechanismDefinition

OpenID Connect Authorization Code flow with refresh tokens: the login page is the provider’s

3.0

Source: Jakarta Security 4.0 specification, 2.4 Annotations and Built-In HttpAuthenticationMechanism Beans and Jakarta Security 3.0 release page (OpenID Connect)

Three rules from the specification shape everything below.

  • The annotation replaces login-config. If the application has an HttpAuthenticationMechanism and also a login-config in web.xml, the container may fail the deployment and otherwise must use only the mechanism. Delete login-config once you move to the annotations.

  • The container resolves roles, not you. A caller who belongs to group foo has role foo by default (specification 1.2.1), so the groups an identity store returns are the role names that security-constraint, isUserInRole and SecurityContext.isCallerInRole see. Servers may override the mapping with proprietary configuration.

  • Jakarta Security 4.0 added qualifiers on the built-in beans and a basic API (HttpAuthenticationMechanismHandler) for applications that need more than one mechanism, and the in-memory identity store. Before 4.0 an application was limited to one mechanism.

Jakarta Security is part of Jakarta EE 11 (Web Profile and Platform), so GlassFish, WildFly, Payara, Open Liberty and TomEE provide an implementation; a bare servlet container such as Tomcat does not, and Eclipse Soteria (the reference implementation) can be added to the WAR. The next sections work with both flavours of form login because they are the ones a Faces developer meets first.

The FORM Mechanism With a Faces Login Page

The FORM mechanism is the Servlet form login: the container shows loginPage when an anonymous caller asks for a protected URL, the page posts j_username and j_password to j_security_check, and the container validates them (here against an identity store), sends the caller to the page that was originally requested or to errorPage. The login page is an ordinary Facelets view, but it must contain a plain HTML form: h:form renders a different action and prefixes the field names with the form id, so the container would never recognise them.

Use FORM when the login page is static and needs nothing from Faces: no validation messages, no Ajax, no bean. The page is then a plain template. As soon as the login form should behave like the rest of the application, use the custom form below.

The Custom FORM Mechanism: A Faces Login Form

@CustomFormAuthenticationMechanismDefinition keeps the login-to-continue behaviour (the container remembers the requested URL, sends the caller to loginPage, and brings them back after a successful login) but lets the application collect the credentials. The specification says it was designed to fit CDI, Jakarta Expression Language, Jakarta Validation "and specifically Jakarta Faces": the login page is a normal Faces form whose bean calls SecurityContext.authenticate() with the credentials. The result is a jakarta.security.enterprise.AuthenticationStatus:

Table 3. What authenticate() returns and what the bean does with it
Status Meaning In the action method

SEND_CONTINUE

The authentication succeeded and nothing was saved to continue to (the caller opened the login page directly)

LoginBean.java
package org.example.bookshelf.web;

import static jakarta.security.enterprise.authentication.mechanism.http.AuthenticationParameters.withParams;

import jakarta.enterprise.context.RequestScoped;
import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.ExternalContext;
import jakarta.faces.context.FacesContext;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import jakarta.security.enterprise.AuthenticationStatus;
import jakarta.security.enterprise.SecurityContext;
import jakarta.security.enterprise.credential.Password;
import jakarta.security.enterprise.credential.UsernamePasswordCredential;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

@Named
@RequestScoped
public class LoginBean {

    private String username;
    private String password;

    @Inject
    SecurityContext securityContext;

    @Inject
    FacesContext facesContext;

    public String login() {
        ExternalContext external = facesContext.getExternalContext();
        AuthenticationStatus status = securityContext.authenticate(
                (HttpServletRequest) external.getRequest(),
                (HttpServletResponse) external.getResponse(),
                withParams().credential(new UsernamePasswordCredential(username, new Password(password))));
        password = null;
        switch (status) {
            case SEND_CONTINUE -> {
                // the mechanism has already sent a redirect to the page the caller asked for first
                facesContext.responseComplete();
                return null;
            }
            case SEND_FAILURE -> {
                // one message for "unknown user" and "wrong password": do not reveal which accounts exist
                facesContext.addMessage(null, new FacesMessage(FacesMessage.SEVERITY_ERROR,
                        "Invalid user name or password", null));
                return null;
            }
            case SUCCESS -> {
                // logged in directly from the login page: go to a fixed landing page
                return "/index.xhtml?faces-redirect=true";
            }
            default -> {
                return null;
            }
        }
    }

    public String logout() throws ServletException {
        ExternalContext external = facesContext.getExternalContext();
        ((HttpServletRequest) external.getRequest()).logout();
        external.invalidateSession();
        return "/login.xhtml?faces-redirect=true";
    }

    public String getUsername() {
        return username;
    }

    public void setUsername(String username) {
        this.username = username;
    }

    public String getPassword() {
        return password;
    }

    public void setPassword(String password) {
        this.password = password;
    }
}

Source: Jakarta Security 4.0 specification, 2.4.9 Custom FORM Notes and Jakarta Security 4.0 API: SecurityContext

The page is small on purpose, because each line removes a mistake:

  • errorPage = "": failures are reported by the form itself (h:messages), so the user keeps the typed user name. The default errorPage is /login-error, and the specification redirects there only when the value is non-empty.

  • useForwardToLogin = false makes the mechanism redirect to the login page. With the default (true) the container forwards, so the address bar shows the protected URL while the login page is displayed.

  • h:inputSecret redisplay="false" (the default) never writes the password back into the HTML, and the bean sets password = null as soon as it has used it. The bean is @RequestScoped: a password in a @ViewScoped or @SessionScoped bean would live in the session or in the view state (and, with client state saving, in the page).

  • pt:autocomplete="current-password" and username tell the browser’s password manager what the fields are (HTML5 pass-through attributes, see HTML5-friendly markup); this makes strong, unique passwords practical for users.

  • One message for both failures. The scratch run answered a wrong password for an existing user and an unknown user with the identical page, on both implementations.

  • The SUCCESS branch returns a fixed outcome. Never redirect to a URL taken from a request parameter without checking it (see Redirects after login).

Observed on Tomcat with Soteria 3.0.4, Mojarra and MyFaces alike: an anonymous request for /members/shelf.xhtml answered 302 to /login.xhtml; the login post with the right password answered 302 to /members/shelf.xhtml and the session cookie changed (see Session Fixation and Logout); a login from the login page itself answered 302 to /index.xhtml (the SUCCESS branch); the wrong password re-rendered the form with the generic message.

sequenceDiagram autonumber participant B as Browser participant C as Container and mechanism participant F as FacesServlet and LoginBean participant S as IdentityStore B->>C: GET /members/shelf.xhtml (anonymous) C-->>B: 302 to /login.xhtml (the request is saved) B->>F: GET /login.xhtml F-->>B: login form with jakarta.faces.ViewState B->>F: POST /login.xhtml (user, password, view state) F->>C: securityContext.authenticate(request, response, credential) C->>S: validate(UsernamePasswordCredential) S-->>C: VALID with groups, or INVALID C-->>B: SEND_CONTINUE: 302 to /members/shelf.xhtml, new session id B->>C: GET /members/shelf.xhtml (new cookie)

Two limitations of the Tomcat scratch setup, neither a property of Faces. Soteria registers its authentication module when the application starts, and on embedded Tomcat that depended on the start-up order: the runs needed META-INF/context.xml to bind the BeanManager into JNDI (the standard Weld-on-Tomcat setup) and, in the MyFaces run, a small listener that registers the same module when Soteria’s own installer had not. On a Jakarta EE server none of this exists. And SecurityContext.getCallerPrincipal() and isCallerInRole() failed on Tomcat with IllegalArgumentException: unknown handler key (Soteria asks the Jakarta Authorization policy context for the caller’s Subject, and Tomcat has no such provider), so the scratch bean read the caller from ExternalContext, which the specification lists as equivalent (4.5).

Identity Stores and Password Hashes

An IdentityStore answers one question, "are these credentials valid, and which groups does the caller have?". The mechanism never touches the database; it hands the credential to the IdentityStoreHandler, which asks every enabled store in order of priority() (lower first) and combines the answers. A store implements validate(Credential) (usually through a method taking a concrete credential type, here UsernamePasswordCredential), getCallerGroups(...) for stores that only provide groups, priority() and validationTypes().

PasswordService.java — the one place that hashes
package org.example.bookshelf.security;

import jakarta.annotation.PostConstruct;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;
import jakarta.security.enterprise.identitystore.Pbkdf2PasswordHash;
import java.util.Map;

/** The one place that knows how passwords are hashed: PBKDF2 with HMAC-SHA-256 and the OWASP work factor, not the 2048 iterations of the default. */
@ApplicationScoped
public class PasswordService {

    @Inject
    Pbkdf2PasswordHash hasher;

    @PostConstruct
    void configure() {
        hasher.initialize(Map.of(
                "Pbkdf2PasswordHash.Algorithm", "PBKDF2WithHmacSHA256",
                "Pbkdf2PasswordHash.Iterations", "600000"));
    }

    /** Returns the encoded form: algorithm:iterations:base64(salt):base64(hash). */
    public String hash(char[] password) {
        return hasher.generate(password);
    }

    public boolean matches(char[] password, String storedHash) {
        return hasher.verify(password, storedHash);
    }
}
BookshelfIdentityStore.java
package org.example.bookshelf.security;

import jakarta.annotation.PostConstruct;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;
import jakarta.security.enterprise.credential.UsernamePasswordCredential;
import jakarta.security.enterprise.identitystore.CredentialValidationResult;
import jakarta.security.enterprise.identitystore.IdentityStore;
import java.util.UUID;

@ApplicationScoped
public class BookshelfIdentityStore implements IdentityStore {

    @Inject
    AccountRepository accounts;

    @Inject
    PasswordService passwords;

    /** Hash of a random password nobody knows. Verified when the user does not exist, so both paths cost the same. */
    private String decoyHash;

    @PostConstruct
    void init() {
        decoyHash = passwords.hash(UUID.randomUUID().toString().toCharArray());
    }

    /** Called by the IdentityStoreHandler for UsernamePasswordCredential. */
    public CredentialValidationResult validate(UsernamePasswordCredential credential) {
        var account = accounts.find(credential.getCaller());
        String hash = account.map(Account::passwordHash).orElse(decoyHash);
        boolean valid = passwords.matches(credential.getPassword().getValue(), hash);
        if (account.isPresent() && valid) {
            return new CredentialValidationResult(account.get().username(), account.get().groups());
        }
        return CredentialValidationResult.INVALID_RESULT;
    }
}

What the listings do, and why:

  • Passwords are hashed with a slow, salted function and never stored or logged. Pbkdf2PasswordHash is the implementation every server must provide. Its encoded form is <algorithm>:<iterations>:<base64 salt>:<base64 hash> (observed: four colon-separated parts, Base64 salt and hash of 44 characters each). The algorithm and the iteration count travel inside the string, so the API states that the configuration can change without invalidating stored hashes (observed: a hash generated with 600,000 iterations verified on an instance left at the defaults). Raise the work factor over time and rehash a password at the next successful login.

  • The default work factor is far too low. The API documents 2048 iterations and PBKDF2WithHmacSHA256 as the defaults, with a minimum of 1024. The OWASP Password Storage Cheat Sheet recommends 600,000 iterations for PBKDF2-HMAC-SHA256. The listing sets both explicitly through the documented parameters Pbkdf2PasswordHash.Algorithm, Pbkdf2PasswordHash.Iterations, Pbkdf2PasswordHash.SaltSizeBytes and Pbkdf2PasswordHash.KeySizeBytes. On the scratch machine (JDK 26) one hash at 600,000 iterations took about 120 ms; measure on production hardware and keep a login under a quarter of a second. (OWASP prefers Argon2id when a library for it is acceptable; the standard API offers PBKDF2 only, and you can implement PasswordHash yourself.)

  • The injected Pbkdf2PasswordHash is dependent-scoped, so every injection point is a separate instance that must be initialised; PasswordService holds the single configured instance.

  • char[], not String. Password.getValue() returns the characters, and Password.clear() and UsernamePasswordCredential.clearCredential() overwrite them, so a password does not have to linger as an immutable String.

  • Unknown users cost the same as wrong passwords. The store verifies against a throw-away hash when the account does not exist, so the response time does not reveal which names exist (eight runs each, including the two HTTP requests: median 81 ms for a wrong password, 76 ms for an unknown user).

  • The seeds come from the environment. AccountRepository is the stand-in for a JPA repository (see the persistence page); the demo accounts exist only when BOOKSHELF_SEED_ADMIN_PASSWORD and BOOKSHELF_SEED_MEMBER_PASSWORD are set. A real deployment creates accounts through a registration or administration use case that calls register, and never ships a default account.

OpenID Connect

@OpenIdAuthenticationMechanismDefinition (Jakarta Security 3.0 and later) turns the application into an OpenID Connect relying party that uses the Authorization Code flow: the mechanism redirects the caller to the provider, receives the code at the redirect URI, exchanges it for tokens at the provider’s token endpoint with the client secret, validates the ID token (issuer, audience, signature, expiry, and the nonce when useNonce is on) and takes the caller name and groups from claims. There is no login page and no password in the application.

Settings that matter, all from the specification and the API:

  • providerURI is the issuer; /.well-known/openid-configuration is appended to discover the endpoints. clientId and clientSecret are required. The API says of the secret that it is "strongly recommended to set this using an Expression so that the value is not hardcoded", which is what the listing does; the environment variable is read by a bean, so the secret never appears in the annotation, the WAR or the repository.

  • redirectURI defaults to ${baseURL}/Callback (baseURL is the application’s host and context path). The provider must have the exact URI registered; a wildcard registration at the provider is an open redirect (see exact redirect-URI matching).

  • scope defaults to openid, email and profile. Ask for the least that the application needs.

  • useNonce defaults to true; keep it. useSession defaults to true (state and nonce in the HTTP session); with false the specification requires a cookie that is HttpOnly and Secure.

  • claimsDefinition chooses which claims name the caller and give the groups; logout with notifyProvider = true calls the provider’s end-session endpoint so that signing out of the application also signs out of the provider.

  • tokenAutoRefresh refreshes expired tokens with the refresh token; redirectToOriginalResource restores the request that triggered the login, like the login-to-continue of the form mechanisms.

RolesRequiredInterceptor.java
package org.example.bookshelf.security;

import jakarta.annotation.Priority;
import jakarta.inject.Inject;
import jakarta.interceptor.AroundInvoke;
import jakarta.interceptor.Interceptor;
import jakarta.interceptor.InvocationContext;
import jakarta.servlet.http.HttpServletRequest;
import java.util.Arrays;

@RolesRequired({})
@Interceptor
@Priority(Interceptor.Priority.APPLICATION)
public class RolesRequiredInterceptor {

    @Inject
    HttpServletRequest request;

    @AroundInvoke
    public Object check(InvocationContext context) throws Exception {
        RolesRequired required = context.getMethod().getAnnotation(RolesRequired.class);
        if (required == null) {
            required = context.getMethod().getDeclaringClass().getAnnotation(RolesRequired.class);
        }
        boolean allowed = required != null && Arrays.stream(required.value()).anyMatch(request::isUserInRole);
        if (!allowed) {
            throw new SecurityException("Caller is not allowed to call " + context.getMethod().getName());
        }
        return context.proceed();
    }
}

Redirects after login

A redirect target that arrives in a request parameter (?next=...) is an open redirect: the login page becomes a trampoline to any site, and the user’s trust in your domain is used for phishing. The mechanisms that keep the original URL do it on the server (login-to-continue), which is why LoginBean above never reads a redirect parameter. When an application must accept one, accept only a path inside itself:

SafeRedirect.java
package org.example.bookshelf.web;

import java.net.URI;
import java.net.URISyntaxException;

/** Accepts only paths inside this application: no scheme, no host, no protocol-relative "//", no backslash tricks. */
public final class SafeRedirect {

    private SafeRedirect() {
    }

    public static String localPathOrDefault(String candidate, String contextPath, String fallback) {
        if (candidate == null || candidate.isBlank() || candidate.contains("\\") || candidate.chars().anyMatch(Character::isISOControl)) {
            return fallback;
        }
        try {
            URI uri = new URI(candidate).normalize();
            String path = uri.getRawPath() == null ? "" : uri.getRawPath();
            boolean local = uri.getScheme() == null && uri.getRawAuthority() == null
                    && path.startsWith("/") && !path.startsWith("//");
            boolean inApp = local && (path.equals(contextPath) || path.startsWith(contextPath + "/"));
            return inApp ? uri.toString() : fallback;
        } catch (URISyntaxException e) {
            return fallback;
        }
    }
}

Source: OWASP: Unvalidated Redirects and Forwards Cheat Sheet

Protecting What the View State Does Not Cover

Client state, stateless views and every non-Faces endpoint (a REST resource, a servlet, an upload endpoint, a WebSocket handshake) have no view state. Three measures cover them, in this order of importance.

1. SameSite cookies. A session cookie with SameSite=Lax is not sent by a browser on a cross-site POST, which blocks the classic forged form (Cookie Attributes and SameSite). It is defence in depth: browsers differ in age and policy, and Lax still sends the cookie on top-level GET navigations, which is why a GET must never change state.

2. A same-origin check in a filter. Browsers send Origin on cross-origin POSTs and, in current browsers, Sec-Fetch-Site on every request. A filter that refuses unsafe methods when the header says the request came from another site:

SameOriginFilter.java
package org.example.bookshelf.web;

import jakarta.servlet.Filter;
import jakarta.servlet.FilterChain;
import jakarta.servlet.FilterConfig;
import jakarta.servlet.ServletException;
import jakarta.servlet.ServletRequest;
import jakarta.servlet.ServletResponse;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;
import java.util.Set;

/** Defence in depth: refuse state-changing requests that the browser says come from another origin. */
public class SameOriginFilter implements Filter {

    private static final Set<String> SAFE = Set.of("GET", "HEAD", "OPTIONS");

    private String publicOrigin;

    @Override
    public void init(FilterConfig config) throws ServletException {
        // Configured, never taken from the request: for example https://books.example.org
        publicOrigin = System.getenv("BOOKSHELF_PUBLIC_ORIGIN");
        if (publicOrigin == null || publicOrigin.isBlank()) {
            throw new ServletException("BOOKSHELF_PUBLIC_ORIGIN is not set");
        }
    }

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) throws IOException, ServletException {
        HttpServletRequest request = (HttpServletRequest) req;
        if (!SAFE.contains(request.getMethod())) {
            String origin = request.getHeader("Origin");
            boolean crossSite = "cross-site".equals(request.getHeader("Sec-Fetch-Site"))
                    || (origin != null && !origin.equals(publicOrigin));
            if (crossSite) {
                ((HttpServletResponse) res).sendError(HttpServletResponse.SC_FORBIDDEN, "Cross-origin request refused");
                return;
            }
        }
        chain.doFilter(req, res);
    }
}

3. A token of your own. Cookie Attributes and SameSite

Three attributes decide how much damage a stolen or forged cookie can do: HttpOnly (scripts cannot read it, so an XSS cannot send the session id away), Secure (it travels only over HTTPS) and SameSite (Strict never sends it on a cross-site request, Lax sends it on top-level GET navigations only, None always, and requires Secure). MDN notes that some browsers use Lax when the attribute is missing, and that this default is a more permissive Lax: the cookie is still sent on a cross-site POST made within two minutes of the cookie being set. An explicit SameSite=Lax does not have that exception, so set the attribute instead of relying on the default.

The session cookie. Servlet 6.0 (Jakarta EE 10) added generic cookie attributes, so SameSite can be set in web.xml as an attribute element of cookie-config (and in code with SessionCookieConfig.setAttribute):

Session Fixation and Logout

In a session fixation attack the attacker obtains a valid session id (by visiting the site) and makes the victim use it (a crafted link with ;jsessionid=, a cookie set from a sibling domain); after the victim logs in, the attacker’s copy of the id belongs to an authenticated session. The remedy is the same everywhere: change the session id when the privilege level changes.

        HttpServletRequest request = (HttpServletRequest) facesContext.getExternalContext().getRequest();
        request.getSession().setAttribute("marker", "kept");
        String before = request.getSession().getId();
        String after = request.changeSessionId();
        facesContext.addMessage(null, new FacesMessage("rotated=" + !before.equals(after) + " marker=" + request.getSession().getAttribute("marker")));
        return null;
    }
}

Source: OWASP: Session Management Cheat Sheet

Observed: rotated=true marker=kept (the attribute set before the call survived), the cookie changed, and the caller stayed logged in.

Logout ends the authenticated state and the session: HttpServletRequest.logout() clears the container’s authentication data and ExternalContext.invalidateSession() destroys the session and everything in it, including view-scoped beans and client-window beans. The LoginBean.logout() above is bound to a commandButton (a POST with the view state), never a link: a logout link is a GET that any page can trigger, and the rule is that GET does not change state. After logging out through the button, the old cookie was answered with the redirect to the login page on both implementations. With OpenID Connect, also end the provider’s session (logout.notifyProvider, OpenID Connect), otherwise the next login is silent.

Idle and absolute session timeouts belong in web.xml (session-config/session-timeout, in minutes) and in the identity provider; keep them short for administrative areas.

Response Headers

Some protections do not belong in a component: framing, sniffing, the referrer and caching of private pages. A servlet filter sets them for every response the application produces:

SecurityHeadersFilter.java and its web.xml mapping
package org.example.bookshelf.web;

import jakarta.servlet.Filter;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.ServletRequest;
import jakarta.servlet.ServletResponse;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;

/** Adds the response headers that do not depend on the page: sniffing, referrer, framing and caching of private areas. */
public class SecurityHeadersFilter implements Filter {

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) throws IOException, ServletException {
        HttpServletRequest request = (HttpServletRequest) req;
        HttpServletResponse response = (HttpServletResponse) res;
        response.setHeader("X-Content-Type-Options", "nosniff");
        response.setHeader("Referrer-Policy", "strict-origin-when-cross-origin");
        response.setHeader("Content-Security-Policy", "frame-ancestors 'none'");
        String path = request.getServletPath();
        if (path.startsWith("/members/") || path.startsWith("/admin/")) {
            response.setHeader("Cache-Control", "no-store");
        }
        chain.doFilter(req, res);
    }
}

    <filter-name>securityHeaders</filter-name>
    <filter-class>org.example.bookshelf.web.SecurityHeadersFilter</filter-class>
</filter>
<filter>
    <filter-name>sameOrigin</filter-name>
    <filter-class>org.example.bookshelf.web.SameOriginFilter</filter-class>
</filter>
<filter-mapping>
    <filter-name>securityHeaders</filter-name>
    <url-pattern>/*</url-pattern>
</filter-mapping>

Source: MDN: Content Security Policy and OWASP: Content Security Policy Cheat Sheet

Observed on both implementations for a member’s request to /members/shelf.xhtml: Cache-Control: no-store, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin and Content-Security-Policy: frame-ancestors 'none' (which forbids framing, the modern replacement for X-Frame-Options, and stops clickjacking). Faces and Tomcat did not overwrite them. Notes:

  • The container answers first. The redirect to the login page and the 403 were produced before the filter ran and carried none of these headers (Cache-Control: private was Tomcat’s own). The login page itself, an ordinary Faces view, had all three. Put what must be on every response (HSTS, for one: Strict-Transport-Security, sent only over HTTPS and decided at the proxy or server) where the container’s responses also pass.

  • Authenticated pages get no-store. Without it a browser may show a cached private page from the back button after logout. Faces sets no caching header for views in these runs.

  • Do not mix the filter’s Content-Security-Policy with the nonce policy of Mojarra or PrimeFaces unless you want both enforced (a browser enforces every policy it receives): send the whole policy from one place.

  • Error pages. With no <error-page>, the 500 response of Tomcat 11 contained the exception class, the Faces stack trace (com.sun.faces.lifecycle...) and the server version (observed with Mojarra).   • Client state keys. Encrypted and authenticated client state needs a fixed key supplied by the server, not by the WAR: see client state keys.   • Push. f:websocket has its own checklist (protect /jakarta.faces.push/<channel>, never trust a user from a request parameter): WebSocket push security.

  • Window ids. The client window id comes from the browser: multi-window security notes.

  • Uploads and downloads. Validate the type and size, store outside the web root, and escape CSV cells: file upload and download.

  • Resources and contracts. Everything under resources/ can be requested as a file (resource handling); contract directories, the con parameter and contract names built from request input have their own warnings in resource library contracts.

  • Sensitive data in the view. A view-scoped bean or a component attribute lives in the view state, in the session or, with client state saving, in the browser. Keep tokens, passwords and personal data out of it.

Spring Security Through JoinFaces

Faces on Spring Boot normally uses Spring Security rather than Jakarta Security: the container is Spring Boot’s embedded server and the security layer is Spring’s. JoinFaces integrates the two. Its reference describes "Spring Security JSF Facelet Tag support": when Spring Security is on the classpath JoinFaces registers a tag library (namespace joinfaces.org/security) with the tags authorize, anonymous, authenticated and fullyAuthenticated, and a set of EL functions (areAllGranted, areAnyGranted, areNotGranted, isAllowed, and others) that stand in for rendered="#{request.isUserInRole(...)}" in the views. URL rules, login, CSRF protection and password encoding are then Spring Security’s: see Spring Security for the filter chain and server-side web UI frameworks for JoinFaces next to Thymeleaf and Vaadin. Two Faces-specific points still apply. Spring Security’s request-forgery protection and the Faces view state are separate mechanisms, so decide explicitly which one protects each state-changing request and test a forged post (this page did not run JoinFaces, but the Spring Boot with JoinFaces page did: a Faces post, plain or through f:ajax, that carried the _csrf hidden field was accepted and one without it got 403, so both the Spring token and the view state are sent; and a view reached through the /faces/* mapping alias bypassed a /admin/** rule until the mapping was restricted). And the escaping, CSP and cookie guidance above is unchanged, because it is about how Faces renders. The Spring Boot with JoinFaces page covers the starters and properties. What Changed by Version

  • JSF 2.2 (Java EE 7, 2013): protected views (<protected-views>, ViewHandler.addProtectedView, ProtectedViewException, ResponseStateManager.NON_POSTBACK_VIEW_TOKEN_PARAM), stateless views and ClientWindow; the specification’s change list names "Specify Cross Site Request Forgery protection" (issue 869).

  • Java EE 8 / JSF 2.3 (2017): the Java EE Security API 1.0 (JSR 375): HttpAuthenticationMechanism, IdentityStore, SecurityContext, the FORM and custom FORM annotations. f:websocket arrives with its own security considerations.

  • Jakarta EE 9 / Faces 3.0: javax.* becomes jakarta.*, Jakarta Security 2.0.

  • Jakarta EE 10 / Faces 4.0 (2022): ExternalContext.addResponseCookie accepts arbitrary cookie attributes such as SameSite (issue 1570); Servlet 6.0 adds generic cookie attributes (cookie-config/attribute); Jakarta Security 3.0 adds OpenID Connect; Mojarra 4.0.16 adds com.sun.faces.enableCspNonce.

  • Jakarta EE 11 / Faces 4.1: Jakarta Security 4.0: a handler for several authentication mechanisms, qualifiers on the built-in mechanisms, the in-memory identity store, Java 17, no references to the Java SecurityManager (Faces issue 1838 removes them too). Full state saving is deprecated (issue 1829; see the state saving page).

  • Mojarra 4.0.16 and later (including 4.1): the vendor parameters com.sun.faces.enableCspNonce and com.sun.faces.cspPolicy (both since 4.0.16 in the Mojarra context parameter reference); earlier 4.0 releases have no CSP support of their own.

  • Faces 5.0 (upcoming; latest milestone 5.0.0-M9 on 2026-09-18): jakarta.faces.ENABLE_CSP_NONCE, jakarta.faces.CSP_POLICY, ResourceHandler.getCurrentNonce (issue 1590). Do not rely on names until a final release.

Where the Books Are Outdated

  • Ed Burns and Chris Schalk’s JavaServer Faces 2.0: The Complete Reference (2010) covers container-managed authentication and role checks in views. The idea is still right: the container authenticates, and rendered and security-constraint decide. What changed is how: the realms and j_security_check forms of that era were configured per server (a user file, a JDBC realm, a vendor login module); Jakarta Security gives an IdentityStore, a mechanism annotation and SecurityContext that work on any Jakarta EE server, and its listings use the javax packages. It predates protected views (2.2), SameSite cookies and CSP.

  • Anghel Leonard’s JSF 2.0 Cookbook (2010) discusses several approaches to security; the libraries of that time (the JSF Security project, Acegi, Seam 2) have ended. Use Jakarta Security, or Spring Security through JoinFaces.

  • All of them predate the data they now have to protect: cookie attributes, Content Security Policy, Sec-Fetch-* headers, PBKDF2 or Argon2 password storage with a work factor, and OpenID Connect. Treat any listing in a book that stores a password in clear text, compares one with equals, or puts a user name and a password into web.xml as historical.

Common Mistakes

  • Checking roles only in the view. rendered hides a button; it does not protect the method. Check in the service (interceptor or SecurityContext) and in web.xml.

  • A URL constraint for one name. /admin/panel.xhtml leaves /admin/panel open with extensionless mapping. Constrain /admin/*.

  • An extra FacesServlet mapping. /faces/* served a view that the constraint on /admin/* did not cover. Constrain /* or each prefix.

  • Listing HTTP methods in a constraint and forgetting deny-uncovered-http-methods: POST and PUT were open.

  • f:viewAction as the only guard. It does not run on postbacks unless onPostback="true".

  • Client state saving or stateless views on a page that changes data without another forgery defence. The view state is not a CSRF token there.

  • A state change on a GET (h:link, a view action that writes). Use a command button (POST) and keep the confirmation page read-only.

  • Protected views taken for authorisation. The token says "came from this application", not "may open this".

  • Data in a script string or an event-handler attribute. HTML escaping does not stop it. Use data-* attributes and script files.

  • escape="false" on data. Sanitise first, or do not allow markup.

  • javascript: and data: URLs from user input. Accept http:, https: and relative paths only.

  • Passwords with a fast hash or the default work factor. PBKDF2 with 2048 iterations is the API default; set 600,000 with SHA-256, or use a stronger function.

  • Different responses for unknown user and wrong password, and different timing. One message, one cost.

  • @InMemoryIdentityStoreDefinition or seed accounts in production. They exist for demos.

  • A password, client secret or key in an annotation, web.xml, faces-config.xml or a bean. Read them from the environment or the server.

  • Redirecting to a next parameter. Validate the path or keep the target on the server.

  • Not rotating the session id when the application authenticates by itself. Call changeSessionId().

  • A logout link. Logout is a POST.

  • Missing HttpOnly, Secure or SameSite on the session cookie, and session ids in URLs (<tracking-mode>COOKIE</tracking-mode>).

  • Security headers set only in the filter. The container’s own redirects and 403s do not pass through it.

  • Default error pages. They disclosed class names, stack frames and the server version. Map them.

  • Assuming Faces 4.1 implements the 5.0 CSP parameter. It does not; use the implementation’s own.
