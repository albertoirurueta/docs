Preflight and Base Styles

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Preflight is Tailwind’s opinionated base layer — a cross-browser reset built on top of modern-normalize that removes the browser’s default styling so utilities have a predictable starting point. It is emitted into the base cascade layer, so any real CSS you write later overrides it easily. See Preflight.

What Preflight resets

Change Effect

Margins removed

h1--h6, p, blockquote, figure, dl, dd, lists — all default margins set to 0, so spacing only comes from utilities you add.

Headings unstyled

h1--h6 inherit font-size and font-weight from their parent; you opt back in with text-2xl font-bold etc. (keeps you on the type scale).

Lists unstyled

ul, ol, menu get list-style: none and no padding. Re-enable with list-disc list-inside or in @layer base.

Borders reset

Every element gets border: 0 solid so border / border-2 add a visible line without also having to set border-style. The default border colour is currentColor (v3 defaulted to gray-200).

Media block-level

img, svg, video, canvas, audio, iframe, embed, object are display: block and vertical-align: middle.

Media constrained

img and video get max-width: 100% and height: auto so they never overflow their container.

Form controls

button, input, select, textarea inherit font and colour; button keeps the browser’s cursor: default (v3 forced pointer; add cursor-pointer where you want it); placeholder text uses the current text colour at 50% opacity.

hidden wins

An element with the hidden attribute stays display: none even if you also put block / flex on it.

 
/* a representative slice of what Preflight emits into @layer base */
*, ::after, ::before, ::backdrop {
  box-sizing: border-box;
  border: 0 solid;
  margin: 0;
  padding: 0;
}
h1, h2, h3, h4, h5, h6 { font-size: inherit; font-weight: inherit; }
ol, ul, menu { list-style: none; }
img, svg, video, canvas, audio, iframe, embed, object { display: block; vertical-align: middle; }
img, video { max-width: 100%; height: auto; }

It ships automatically

Preflight is part of the single import — there is no separate include:

@import "tailwindcss";
/* expands to:
   @import "tailwindcss/theme.css"     layer(theme);
   @import "tailwindcss/preflight.css" layer(base);
   @import "tailwindcss/utilities.css" layer(utilities);   */

Extending Preflight

Add your own element-level defaults in @layer base. Because these land in the same layer as Preflight, later utilities still override them. Use theme variables for the values so the defaults track your design tokens.

@import "tailwindcss";

@layer base {
  h1 { font-size: var(--text-2xl); font-weight: var(--font-weight-bold); }
  h2 { font-size: var(--text-xl); }
  a  { color: var(--color-sky-600); text-decoration-line: underline; }

  /* restore readable defaults inside CMS / Markdown output */
  .prose-fallback :is(ul, ol) { list-style: revert; padding-left: revert; }
}

See Adding base styles.

Disabling or partially adopting Preflight

Import the layers individually and simply omit preflight.css:

/* theme variables + utilities, but no reset */
@import "tailwindcss/theme.css" layer(theme);
@import "tailwindcss/utilities.css" layer(utilities);

When you split the import like this, options that normally attach to @import "tailwindcss" move to the relevant sub-import: source(...) and important go on the utilities.css line, theme(static) / theme(inline) on the theme.css line, and prefix(...) on both. This is the usual approach when adding Tailwind to an existing codebase that already has its own reset, or when embedding a Tailwind-styled widget inside a host page you do not control.

Worked example: the Acme hero before and after

Take the Acme hero (see Building a Page with Utilities) and strip every class from it. Without a reset the browser’s own stylesheet decides how it looks; with Preflight it renders as plain, unopinionated text, and each visual decision then comes back as an explicit utility.

<section>
  <h1>Ship your site faster</h1>
  <p>Utility-first CSS, no context switching.</p>
  <ul>
    <li>Fast</li>
    <li>Small</li>
  </ul>
  <button>Get started</button>
</section>
Element Browser default With Preflight

h1

2em bold, 0.67em vertical margins

inherits the body size and weight, no margin

p

1em vertical margins

no margin

ul

bullets, 40px left padding, 1em margins

no bullets, no padding, no margin

button

grey native chrome, own font

transparent background, no border, inherits font and colour

A page that looks flat after the reset is the intended starting point, not a bug: the type scale, spacing and colours of the design come from utilities that draw on the theme, so two developers writing the same markup get the same result regardless of which browser’s defaults they are used to. Restoring the Acme hero is a matter of naming what you want:

<section class="mx-auto max-w-3xl px-6 py-16 text-center">
  <h1 class="text-4xl font-extrabold tracking-tight">Ship your site faster</h1>
  <p class="mt-4 text-gray-600">Utility-first CSS, no context switching.</p>
  <ul class="mt-8 list-disc list-inside text-left">
    <li>Fast</li>
    <li>Small</li>
  </ul>
  <button class="mt-8 cursor-pointer rounded-md bg-sky-600 px-5 py-2.5 font-semibold text-white">Get started</button>
</section>

Why Preflight lives in a layer

Preflight is emitted into the base cascade layer, below components and utilities. A rule in a lower layer loses to a rule in a higher layer regardless of specificity, so a bare utility such as font-bold always beats Preflight’s h1 { font-weight: inherit; } even though h1 is a type selector and the utility is a class. The same mechanism makes your own @layer base rules safe to write: they are in the same layer as Preflight, come after it in the file, and are still beaten by any utility.

flowchart LR T["theme layer: variables"] --> B["base layer: Preflight and your @layer base rules"] B --> C["components layer: plugin and your component CSS"] C --> U["utilities layer: every utility class"] U --> W["later layers win over earlier ones"]

A build of @import "tailwindcss"; followed by @layer base { h1 { font-weight: var(--font-weight-bold); } } confirms the ordering: the generated stylesheet contains two @layer base blocks, Preflight’s first and yours second, so your h1 rule wins over Preflight’s font-weight: inherit but loses to text-xl font-normal on the element.

Details worth knowing

  • html receives line-height: 1.5, a default sans-serif system font stack (override it with --default-font-family or --font-sans in @theme), tab-size: 4 and the text-size-adjust and tap-highlight resets. Every other element inherits from it, which is why a custom font-sans on body is rarely needed.

  • The border reset (border: 0 solid on every element and pseudo-element) is what makes the lone border class produce a visible 1px line: the width comes from the utility, while the style (solid) and colour (currentColor) are already in place. Set a colour (border-gray-200) or the line takes the text colour.

  • [hidden] is display: none !important unless its value is until-found, so the HTML hidden attribute is never overridden by flex or block.

  • ::placeholder uses the current text colour at 50% opacity, and form controls reset to font: inherit, which is why a styled input matches the surrounding paragraph text without extra classes.

  • Images, svg and other replaced elements are display: block with vertical-align: middle. Placing an icon inline with text then needs inline (or a flex row), and the old gap beneath a baseline-aligned image is gone.

@import "tailwindcss";

@layer base {
  /* a readable article body without adding classes to Markdown output */
  .article :is(h2, h3) { margin-top: 2rem; font-weight: var(--font-weight-semibold); }
  .article ul { list-style: revert; padding-inline-start: 1.5rem; }
  .article a { text-decoration-line: underline; }
}

When the generated markup comes from a CMS or a Markdown renderer you cannot add classes to, the typography plugin (prose) is usually a better answer than hand-written base rules.
