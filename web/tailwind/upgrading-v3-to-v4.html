Upgrading from v3 to v4

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Tailwind v4 (January 2025) rewrote the engine and moved configuration into CSS. Most utility names carry over, so v3 knowledge still applies — but the setup, several defaults, and a handful of class names changed. Both books in this section’s bibliography target v3.x; this page is the translation layer. The authoritative list is the Upgrade guide.

The automated tool

npx @tailwindcss/upgrade   # needs Node 20+; run on a clean git branch and review the diff

It migrates the config, the @tailwind directives, renamed classes, and most template changes. Complex projects still need a manual pass.

Configuration

v3 v4

tailwind.config.js (theme, content, plugins)

@theme { } in CSS; @source for content; @plugin for plugins — or keep the JS file via @config "../tailwind.config.js"

@tailwind base; @tailwind components; @tailwind utilities;

@import "tailwindcss";

PostCSS plugin: tailwindcss

@tailwindcss/postcss (or @tailwindcss/vite for Vite)

npx tailwindcss CLI

npx @tailwindcss/cli

 
/* v4 */
@import "tailwindcss";
@theme { --color-brand: #3f3cbb; }

Removed utilities and options

  • flex-shrink-* / flex-grow-* → shrink-* / grow-* (current v4 releases still compile the old names as deprecated aliases and the upgrade tool leaves them alone, so rename them yourself)

  • overflow-ellipsis → text-ellipsis

  • bg-opacity-*, text-opacity-*, border-opacity-*, divide-opacity-*, ring-opacity-*, placeholder-opacity-* → the / opacity modifier (bg-black/50)

  • Config keys corePlugins, safelist, separator are gone; content is replaced by @source

Not every renamed utility fails loudly, and this is the hazard worth knowing about. The old names fall into two groups:

  • Aliases that still produce the same CSS — bg-gradient-to-r, flex-shrink-0, overflow-ellipsis. Leaving them is harmless but deprecated.

  • Names that still compile but now mean something different — shadow-sm, rounded-sm, blur-sm, ring, and outline-none. They exist in v4, so a build succeeds and nothing warns you, yet the shadow is larger, the corner rounder, the ring 1px instead of 3px, and the outline suppressed differently. Only the migration tool or a visual review catches these.

Changed defaults and behaviour

<!-- border / divide colour is now currentColor, not gray-200 -->
<div class="border border-gray-200"></div>

<!-- ring is now 1px + currentColor (was 3px + blue-500) -->
<button class="ring-3 ring-blue-500"></button>

<!-- the important marker moved to the end -->
<div class="bg-red-500!"></div>          <!-- v3: !bg-red-500 -->

<!-- arbitrary CSS-variable shorthand -->
<div class="bg-(--brand)"></div>          <!-- v3: bg-[--brand] -->

<!-- variant stacking now reads left-to-right -->
<ul><li class="*:first:pt-0"></li></ul>   <!-- v3: first:*:pt-0 -->

Also: hover: only applies where the device actually supports hover; space-x-* / space-y-* and divide-* use a faster :not(:last-child) selector; Preflight changes the placeholder colour, gives button cursor: default, and resets <dialog> margins.

Deep dive: migrating the Acme page

The Acme page from Building a Page with Utilities makes a compact migration exercise. Imagine it was first built on Tailwind 3 with this configuration and stylesheet:

// tailwind.config.js (v3)
module.exports = {
  content: ["./src/**/*.html"],
  darkMode: "class",
  theme: {
    extend: {
      colors: { brand: "#3f3cbb" },
      fontFamily: { display: ["Satoshi", "ui-sans-serif", "sans-serif"] },
    },
  },
  plugins: [],
};
/* src/app.css (v3) */
@tailwind base;
@tailwind components;
@tailwind utilities;

@layer components {
  .btn { @apply rounded bg-brand px-4 py-2 font-semibold text-white shadow-sm hover:bg-brand/90; }
}

with markup that uses the v3 spellings:

<div class="flex-shrink-0 !bg-brand bg-[--brand] shadow-sm shadow rounded-sm rounded blur-sm outline-none ring border
            bg-gradient-to-r from-sky-500 to-brand first:*:pt-0 overflow-ellipsis">&#8230;</div>

Running npx @tailwindcss/upgrade on a clean branch migrates each part of the project in turn, and the result is what the rest of this page describes in the abstract:

/* src/app.css (after) */
@import 'tailwindcss';

@custom-variant dark (&:is(.dark *));

@theme {
  --color-brand: #3f3cbb;
  --font-display: Satoshi, ui-sans-serif, sans-serif;
}

/* ... a generated @layer base block that restores the v3 border colour (gray-200) ... */

@utility btn {
  @apply rounded-sm bg-brand px-4 py-2 font-semibold text-white shadow-xs hover:bg-brand/90;
}
<div class="flex-shrink-0 bg-brand! bg-(--brand) shadow-xs shadow-sm rounded-xs rounded-sm blur-xs outline-hidden ring-3 border
            bg-linear-to-r from-sky-500 to-brand *:first:pt-0 text-ellipsis">&#8230;</div>
What changed How

tailwind.config.js

deleted; colors and fontFamily moved into @theme; darkMode: "class" became a @custom-variant dark

@tailwind base/components/utilities

replaced by @import 'tailwindcss'

.btn in @layer components

became an @utility, so hover:btn and md:btn now work — and its @apply names were renamed (rounded to rounded-sm, shadow-sm to shadow-xs)

!bg-brand

bg-brand!

bg-[--brand]

bg-(--brand)

shadow-sm shadow, rounded-sm rounded, blur-sm

shifted down one step each

outline-none, ring

outline-hidden, ring-3 (the width that ring had in v3)

bg-gradient-to-r

bg-linear-to-r

first:*:pt-0

*:first:pt-0 (variant order reversed)

PostCSS config

tailwindcss plugin replaced by @tailwindcss/postcss

The tool also added a compatibility @layer base block so borders keep the v3 default colour. That block is a reminder rather than a fix: the v4 default is currentColor, and the clean solution is to give every bordered element an explicit colour utility (border-gray-200) and delete the block.

What the tool leaves for you

Two things are not rewritten, and one of them stops the run:

  • flex-shrink-0 stays as it is (it still compiles as an alias). Rename it to shrink-0.

  • bg-opacity-*, text-opacity-* and the other opacity utilities no longer exist at all. In markup they silently generate nothing, so bg-black bg-opacity-50 becomes a solid black background. Inside @apply, as in hover:bg-opacity-90 within the .btn rule, the tool aborts with Cannot apply unknown utility class after it has already migrated the configuration and the stylesheets. Replace them with the slash modifier (bg-black/50, hover:bg-brand/90) before you run the tool, or fix the named class and run it again.

Run the tool on a clean branch. It refuses to start when the working tree has uncommitted changes (unless you pass --force), and a clean tree is also what makes the final diff reviewable.

After the tool: a checklist

  1. Build, and open every page. Compare shadows, rounded corners and focus rings with the v3 version.

  2. Search for the leftovers: flex-shrink, flex-grow, bg-opacity, text-opacity, decoration-slice, and any theme( function call in custom CSS.

  3. Check any third-party plugin for a v4-compatible release; load a legacy JS config only as a stopgap with @config.

  4. Replace the compatibility border block with explicit border colours.

  5. Update CI and documentation: the CLI is @tailwindcss/cli, the PostCSS plugin is @tailwindcss/postcss, and Node 20 or newer is required.

Browser baseline

v4 requires Safari 16.4+, Chrome 111+, Firefox 128+ — it depends on @property and color-mix() and has no build-time fallback for older engines. A project that must support them should stay on Tailwind v3.4.
