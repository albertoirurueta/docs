Building a Page with Utilities

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page assembles utilities from the rest of the section into one small responsive layout, showing the usual order of work: structure first, then breakpoints, then states, then theme — the workflow described in Styling with utility classes. Paste any step into Tailwind Play to see it live.

1. Structure with layout utilities

<header class="flex items-center justify-between border-b border-gray-200 px-6 py-4">
  <a href="/" class="text-lg font-bold">Acme</a>
  <nav class="flex gap-6 text-sm font-medium">
    <a href="/features">Features</a>
    <a href="/pricing">Pricing</a>
    <a href="/docs">Docs</a>
  </nav>
</header>

<section class="mx-auto max-w-3xl px-6 py-16 text-center">
  <h1 class="text-4xl font-extrabold tracking-tight">Ship your site faster</h1>
  <p class="mt-4 text-gray-600">Utility-first CSS, no context switching.</p>
  <a href="/start" class="mt-8 inline-block rounded-md bg-sky-600 px-5 py-2.5 font-semibold text-white">
    Get started
  </a>
</section>

<div class="mx-auto grid max-w-5xl gap-6 px-6 pb-16">
  <article class="rounded-xl border border-gray-200 p-6">
    <h3 class="font-semibold">Fast</h3>
    <p class="mt-2 text-sm text-gray-600">Only the CSS you use is generated.</p>
  </article>
  <!-- two more <article> just like it -->
</div>

2. Add responsive variants

The nav collapses on small screens; the card grid goes from one column to two to three.

<header class="flex items-center justify-between border-b border-gray-200 px-6 py-4">

  <button class="sm:hidden" aria-label="Menu">&#9776;</button>
  <nav class="hidden gap-6 text-sm font-medium sm:flex">

4. Extract the repeated card

Once a class list repeats, move it into a component of whatever framework you use — not @apply.

function Feature({ title, children }) {
  return (
    <article className="rounded-xl border border-gray-200 p-6 hover:shadow-md
                        dark:border-slate-800 dark:bg-slate-800/50">
      <h3 className="font-semibold">{title}</h3>
      <p className="mt-2 text-sm text-gray-600 dark:text-slate-400">{children}</p>
    </article>
  );
}

5. One theme customization

Add a brand colour and display font once; every *-brand / font-display utility now exists.

@import "tailwindcss";

@theme {
  --color-brand: oklch(0.55 0.2 264);
  --font-display: "Satoshi", ui-sans-serif, sans-serif;
}
<h1 class="font-display text-4xl font-extrabold">Ship your site faster</h1>
<a href="/start" class="rounded-md bg-brand px-5 py-2.5 font-semibold text-white hover:bg-brand/90">
  Get started
</a>

6. A mobile menu that is state-driven

Step 2 hid the navigation on phones and showed a menu button, but the button did nothing. The state that matters — whether the menu is open — already has a standard home in the markup, the aria-expanded attribute, so the button carries the state and the stylesheet reacts to it. The button becomes a peer and the navigation, which follows it, uses peer-aria-expanded:.

<header class="flex flex-wrap items-center justify-between border-b border-gray-200 px-6 py-4">
  <a href="/" class="text-lg font-bold">Acme</a>

  <button class="peer rounded-md px-2 py-1 sm:hidden"
          aria-expanded="false" aria-controls="menu" aria-label="Menu">&#9776;</button>

  <nav id="menu"
       class="hidden w-full flex-col gap-2 pt-4 text-sm font-medium
              peer-aria-expanded:flex sm:flex sm:w-auto sm:flex-row sm:gap-6 sm:pt-0">
    <a href="/features">Features</a>
    <a href="/pricing">Pricing</a>
    <a href="/docs" aria-current="page" class="aria-[current=page]:text-brand">Docs</a>
  </nav>
</header>
const button = document.querySelector('button[aria-controls="menu"]');

button.addEventListener("click", () => {
  const open = button.getAttribute("aria-expanded") === "true";
  button.setAttribute("aria-expanded", String(!open));
});

Read the nav classes in layers. Unprefixed, it is a hidden full-width column. peer-aria-expanded:flex shows it while the button reports aria-expanded="true". From sm up, sm:flex sm:w-auto sm:flex-row makes it the inline row from step 2 regardless of the button, and the button itself is sm:hidden. The current page link is styled from aria-current, so the visual and the accessibility state cannot disagree.

stateDiagram-v2 [*] --> Closed Closed --> Open: click button, aria-expanded true Open --> Closed: click button, aria-expanded false Closed --> Inline: window reaches sm Open --> Inline: window reaches sm Inline --> Closed: window shrinks below sm

The script has one job — flip an attribute — and nothing in it knows about classes, so restyling the menu never touches JavaScript. A DOM test (for example with jsdom) can load the page, click the button twice and assert that the attribute alternates between "true" and "false".

7. Make the card ask its container

The card in step 1 is placed in a three-column grid on desktop, but the same component may later move into a sidebar or a wider layout. Wrap each card in a query container and let the card respond to the width it actually has:

<ul class="mx-auto grid max-w-5xl gap-6 px-6 pb-16 sm:grid-cols-2 lg:grid-cols-3">
  <li class="@container">
    <article class="group flex flex-col gap-2 rounded-xl border border-gray-200 p-6
                    @md:flex-row @md:items-center @md:gap-6
                    hover:shadow-md has-[a:focus-visible]:ring-2 has-[a:focus-visible]:ring-brand
                    dark:border-slate-800 dark:bg-slate-800/50">
      <h3 class="font-semibold group-hover:text-brand"><a href="/fast" class="outline-none">Fast</a></h3>
      <p class="text-sm text-gray-600 dark:text-slate-400">Only the CSS you use is generated.</p>
    </article>
  </li>
</ul>

Three changes from step 3, each from a different part of this section: the @container wrapper and @md: variants (Responsive Design); group-hover: plus has-[a:focus-visible]: so the whole card reacts to the pointer and to keyboard focus (Hover, Focus, and Other States); and the brand colour from the theme.

8. Put it together and build

The finished page needs only three files. The stylesheet below also wires the dark: variant to a data-theme attribute so a toggle can drive it (Dark Mode).

/* src/app.css */
@import "tailwindcss";
@source "./index.html";

@custom-variant dark (&:where([data-theme=dark], [data-theme=dark] *));

@theme {
  --color-brand: oklch(0.55 0.2 264);
  --font-display: "Satoshi", ui-sans-serif, sans-serif;
}
npm install tailwindcss @tailwindcss/cli
npx @tailwindcss/cli -i src/app.css -o app.css --minify

The result of building exactly the page assembled in steps 1 to 7 — header with the state-driven menu, hero, a container-aware feature card, hover, focus and dark variants, and the brand token — is a single stylesheet of about 13 kB (3.5 kB gzipped), of which roughly 12 kB is the fixed Preflight and theme scaffolding every Tailwind build includes. Adding the other two feature cards adds nothing, because they reuse the same classes: the stylesheet grows with the number of distinct utilities, not with the number of elements.

flowchart LR S1["1. Structure"] --> S2["2. Breakpoints"] S2 --> S3["3. States and dark"] S3 --> S4["4. Extract a component"] S4 --> S5["5. Theme token"] S5 --> S6["6. State-driven menu"] S6 --> S7["7. Container-aware card"] S7 --> B["8. Build: one stylesheet"]
The order matters. Structure and breakpoints decide the layout; states, dark mode and the theme only restyle it. Doing them in reverse makes every later change a layout change.
