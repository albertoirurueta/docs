State and Events

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Interactivity in React comes from two things: event handlers that respond to user input, and state that the component remembers between renders. Changing state re-renders the component.

Event handlers

Attach a handler by passing a function (not calling it) to a camelCased prop such as onClick, onChange, onSubmit.

function Toolbar() {
  function handleSave() {
    console.log('saved');
  }

  return (
    <>
      <button onClick={handleSave}>Save</button>          {/* pass the function */}
      <button onClick={() => handleSave()}>Save now</button>  {/* inline wrapper */}
      <button onClick={handleSave()}>Wrong</button>        {/* BUG: calls on render */}
    </>
  );
}

The handler receives a SyntheticEvent — a cross-browser wrapper over the native event with the same interface (e.target, e.currentTarget, e.key, e.preventDefault(), e.stopPropagation()). React attaches one listener at the root and dispatches from there.

function SearchForm({ onSearch }) {
  function handleSubmit(e) {
    e.preventDefault();                 // don't reload the page
    const q = new FormData(e.target).get('q');
    onSearch(q);
  }
  return (
    <form onSubmit={handleSubmit}>
      <input name="q" />
    </form>
  );
}

Events bubble through the React tree. Use onClickCapture for the capture phase, and e.stopPropagation() to stop a bubble. For the full capture/target/bubble model see Events. Reference: Responding to Events.

useState

useState gives a component a value that survives re-renders plus a setter that schedules a re-render.

import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);       // [current value, setter]
  const [name, setName] = useState('');        // as many as you need

  return (
    <button onClick={() => setCount(count + 1)}>
      {name || 'anon'}: {count}
    </button>
  );
}

State is per component instance: render <Counter /> twice and each has its own count. The initial value is used only on the first render. See State: A Component’s Memory.

Render and commit

Every screen update is three steps:

  1. Trigger — the first render (createRoot(...).render) or a state update from setState.

  2. Render — React calls your components and works out what the DOM should look like.

  3. Commit — React applies the minimal set of DOM changes, then the browser paints.

See Render and Commit.

State as a snapshot, batching, and updater functions

A component’s count is fixed for the duration of a render — a snapshot. Calling setCount(count + 1) three times in one handler still adds only 1, because all three read the same snapshot.

React automatically batches state updates — those in an event handler and, since React 18, those in promises, setTimeout, and native event handlers too — into a single re-render. To base an update on the latest pending value, pass an updater function:

setCount(count + 1);          // count is the render's snapshot
setCount((c) => c + 1);       // c is the latest queued value
setCount((c) => c + 1);
setCount((c) => c + 1);       // three updaters -> +3

References: State as a Snapshot, Queueing a Series of State Updates.

Updating objects and arrays

Treat state as immutable. Never mutate an object or array in state; create a new one and pass it to the setter, so React sees a new reference and re-renders.

// object
setUser({ ...user, name: 'Ada' });

// array
setItems([...items, newItem]);                 // add
setItems(items.filter((i) => i.id !== id));    // remove
setItems(items.map((i) => (i.id === id ? { ...i, done: true } : i)));  // update one

For deeply nested state, Immer (useImmer) lets you write mutating-looking code that produces an immutable update. References: Updating Objects in State, Updating Arrays in State.

Deep dive: one click, step by step

The cart quantity stepper in the storefront shows the whole cycle. The next diagram follows a single click from the browser event to the repainted screen:

sequenceDiagram participant U as User participant B as Browser participant R as React root listener participant C as Your component participant D as DOM U->>B: click "+" B->>R: native click event (bubbles to root) R->>C: run onClick with a SyntheticEvent C->>R: setQty(q => q + 1) queued Note over R: handler finished, queued updates are batched R->>C: re-render with the new snapshot C-->>R: new element tree R->>D: commit the minimal DOM change D-->>U: browser paints the new quantity

Two details are worth remembering. First, the handler itself never changes qty; it only asks React for a new render. Second, React runs the component again after the handler returns, so the handler always sees the value from the render it was created in.

Deep dive: snapshots and updater functions, measured

This component makes the difference between a snapshot read and an updater visible:

function Quantity() {
  const [qty, setQty] = useState(1);

  function addThreeWrong() { setQty(qty + 1); setQty(qty + 1); setQty(qty + 1); }
  function addThree() { setQty((q) => q + 1); setQty((q) => q + 1); setQty((q) => q + 1); }

  return (
    <div>
      <output>{qty}</output>
      <button onClick={addThreeWrong}>wrong</button>
      <button onClick={addThree}>right</button>
    </div>
  );
}

Rendering it with React Testing Library and clicking each button once gives:

2 (all three calls computed 1 + 1)

Both clicks cause exactly one render: three setQty calls are batched. Use the updater form whenever the next value depends on the previous one, and a plain value when it does not (setName(e.target.value)).

The initial value passed to useState is only used on the first render, but an expression there is still evaluated on every render. Pass a function (lazy initialization) when computing it is expensive:

const [filters, setFilters] = useState(() => readFiltersFromUrl());   // runs once
const [bad, setBad] = useState(readFiltersFromUrl());                 // runs on every render, result ignored

Deep dive: why mutation does not work

React decides whether to re-render by comparing the reference it is given with the one it has. Mutating the object in place and passing it back looks like "no change":

function Cart() {
  const [items, setItems] = useState([{ id: 'kb', name: 'Keyboard', qty: 1 }]);

  const bad = () => { items[0].qty += 1; setItems(items); };         // same array: React bails out
  const good = () => setItems(items.map((i) => (i.id === 'kb' ? { ...i, qty: i.qty + 1 } : i)));

  return (
    <div>
      <output>{items[0].qty}</output>
      <button onClick={bad}>bad</button>
      <button onClick={good}>good</button>
    </div>
  );
}

In a test, clicking bad leaves the output at 1 (the data was changed but the screen was not), and the next click on good suddenly shows 3, because the earlier mutation was already in the array. This is a classic source of "it updates on the second click" bugs. Immutability also lets memo, useMemo and the React Compiler use cheap reference checks.

Deep dive: events, propagation and a bit of history

  • e.stopPropagation() stops the event from reaching ancestors' handlers. With an outer <div onClick> and two buttons, clicking the button that stops propagation logs only its own handler, while the other button logs its own and then the outer one (stop,inner,outer in the test log).

  • React 17 and later attach listeners to the root container you pass to createRoot, not to document, so several React versions (or a React app and a non-React widget) can coexist on a page.

  • Before React 17, the synthetic event object was pooled and its fields were cleared after the handler returned, which forced e.persist() in asynchronous code. Pooling was removed: you can read the event in a setTimeout or a promise callback without special handling.

  • Handlers are plain functions. There is no need to call bind (a class-component habit); arrow functions and function declarations both work, and defining a handler inline is fine unless you pass it to a memoized child.

Deep dive: state belongs to a position in the tree

State is tied to where a component sits in the tree, not to which function it is. Two consequences you can use:

  • The same component at the same position keeps its state when its props change. A form for one product keeps its draft text if you simply render it with another product’s props.

  • Giving it a different key makes React treat it as a new instance and resets its state.

function Draft() {
  const [text, setText] = useState('');
  return <input aria-label="note" value={text} onChange={(e) => setText(e.target.value)} />;
}

function Page({ id }) {
  return <Draft key={id} />;     // without key={id} the draft survives a product change
}

Typing hello, then rendering the page for another product id: without the key the input still contains "hello"; with key={id} it is "". This is the recommended way to reset state when a prop changes, instead of an Effect that calls the setter (see Effects and Lifecycle).

References: Event propagation, React 17: changes to event delegation, Avoiding recreating the initial state, Preserving and Resetting State.
