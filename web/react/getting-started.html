Getting Started with React

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

React is a declarative, component-based JavaScript library for building user interfaces, maintained by Meta and a large open-source community. You describe what the UI should look like for a given state, and React updates the DOM to match when that state changes.

What React is

  • Declarative. You write components that return markup for the current state; you do not write the DOM mutations. Compare imperative code — document.createElement, el.append, el.remove — with a React component that just returns <ul>{items.map(...)}</ul> and lets React work out the minimal DOM change.

  • Component-based. The UI is a tree of functions (components) that each take inputs (props) and return a description of a piece of UI. Components compose like plain functions.

  • The virtual DOM and reconciliation. Rendering a component produces a lightweight tree of plain objects (React elements), not real DOM nodes. On each update React builds a new tree, diffs it against the previous one (reconciliation), and applies only the changed nodes to the real DOM. This is why you can re-render freely without hand-optimizing DOM writes.

function Greeting({ name }) {
  return <h1>Hello, {name}</h1>;
}

React Native reuses the same React core and component model to build native mobile apps, swapping the DOM renderer for native views. It is out of scope here — this section is about React on the web; see Getting Started with React Native for that platform, and the React "Learn" guide for the full introduction.

What’s new in React 19

React 19 is the current stable major line. The headline additions, each with its reference page:

  • Actions — pass an async function to <form action> and to transitions; pending, error, and optimistic state are handled for you. See useActionState, useFormStatus, and useOptimistic.

  • use — read a promise or a context during render, inside conditions and loops. See use.

  • ref as a prop — function components receive ref directly; forwardRef is no longer needed for new code. See the React 19 release post.

  • Document metadata — render <title>, <meta>, and <link> anywhere and React hoists them into <head>. See <title>.

  • Resource preloading APIs — preload, preinit, prefetchDNS, preconnect from react-dom. See preload.

  • Stable Server Components and Server Functions — see Server Components.

  • The React Compiler — an optional build-time optimizer that auto-memoizes components; version 1.0 is stable. See React Compiler and React Compiler v1.0.

  • React 19.2 and 19.3 — <Activity> and useEffectEvent (19.2), and stable <ViewTransition>, Fragment Refs and the browser API for opting a component out of server rendering (19.3). See React 19.2 and React 19.3.

Track releases at react.dev/versions and the React blog.

Creating an app

The framework route (recommended for products). A full-stack React framework gives you routing, data fetching, code splitting, and SSR out of the box:

  • Next.js (App Router) — see also Getting Started with Next.js in this reference

  • React Router (framework mode, formerly Remix)

  • Expo for React Native

See Creating a React App.

Build from scratch with Vite. When you do not want a framework, Vite is the standard toolchain:

npm create vite@latest my-app -- --template react
# or react-ts for TypeScript
cd my-app && npm install && npm run dev
Create React App was deprecated in February 2025 and is no longer recommended. Existing CRA projects should migrate to Vite or a framework. See Build a React App from Scratch.

Add React to an existing project. You can mount React into one part of a non-React page. See Add React to an existing project.

A quick experiment with no build step — an ES module from a CDN such as esm.sh:

<div id="root"></div>
<script type="module">
  import { createRoot } from 'https://esm.sh/react-dom@19/client';
  import { StrictMode, createElement } from 'https://esm.sh/react@19';
  createRoot(document.getElementById('root'))
    .render(createElement(StrictMode, null, createElement('h1', null, 'Hello')));
</script>

A normal project’s entry point looks like this:

// main.jsx
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>
);

See Installation.

  • Editor setup — an editor with JSX/TSX support and format-on-save. See Editor setup.

  • React Developer Tools — the browser extension adds a Components tab and a Profiler tab. See React Developer Tools.

  • StrictMode — wrap the tree so React double-invokes renders and Effects in development to surface impure code and missing cleanup. See <StrictMode>.

Deep dive: from JSX to pixels

The rest of this section builds one small storefront — a product catalog with a shopping cart — and grows it page by page. Before writing any code it helps to know what React does with the components you write.

Elements are plain objects

A component never touches the DOM. When React calls it, it returns React elements: small, immutable objects that describe what should be on screen. Printing one shows there is nothing magic in it.

import { createElement } from 'react';

const el = createElement('li', { className: 'product' }, 'Keyboard');
console.log(JSON.stringify({ type: el.type, props: el.props, key: el.key }));
// {"type":"li","props":{"className":"product","children":"Keyboard"},"key":null}

function Price({ amount }) { return <span>{amount.toFixed(2)}</span>; }
const el2 = <Price amount={9.5} />;
console.log(typeof el2.type, el2.props);
// function { amount: 9.5 }

For a DOM element type is a string ('li'); for a component it is the function itself. React stores the whole output of a render as a tree of these objects. Creating them is cheap, which is why re-rendering is not the same as touching the DOM.

The storefront example

This is the first version of the running example: a stateless catalog. Later pages add a cart, a reducer, Effects, Hooks and a form around it.

const PRODUCTS = [
  { id: 'kb', name: 'Keyboard', price: 49.9, stock: 3 },
  { id: 'ms', name: 'Mouse', price: 19.5, stock: 0 },
  { id: 'mn', name: 'Monitor', price: 189, stock: 12 },
];

function Price({ amount }) {
  return <span>{amount.toFixed(2)}</span>;
}

function ProductRow({ product }) {
  return (
    <li>
      {product.name} - <Price amount={product.price} />
      {product.stock === 0 && <em> sold out</em>}
    </li>
  );
}

export function Catalog({ products }) {
  return (
    <section>
      <h1>Catalog</h1>
      <ul>{products.map((p) => <ProductRow key={p.id} product={p} />)}</ul>
    </section>
  );
}

Rendering <Catalog products={PRODUCTS} /> with renderToString from react-dom/server produces the following HTML (the <!-- --> comments separate adjacent text nodes so hydration can match them):

<section><h1>Catalog</h1><ul><li>Keyboard<!-- --> - <span>49.90</span></li><li>Mouse<!-- --> - <span>19.50</span><em> sold out</em></li><li>Monitor<!-- --> - <span>189.00</span></li></ul></section>

Render, diff, commit

Each update runs the same pipeline: React calls the components to build a new element tree, compares it with the previous tree, and applies only the differences to the DOM.

flowchart LR S["State or props change"] --> C["Call components
(render phase)"] C --> T["New element tree"] T --> D{"Diff against
previous tree"} D -->|"same type and position"| U["Reuse node,
update changed props"] D -->|"different type"| R["Unmount old subtree,
mount new one"] U --> M["Commit: apply DOM changes"] R --> M M --> P["Browser paints"]

The diff uses two heuristics that make it linear in the size of the tree:

  • Elements of different types at the same position produce different trees: the old subtree is unmounted (its state is destroyed) and the new one is mounted from scratch.

  • Siblings in a list are matched by key (see JSX and Rendering).

You can observe the consequence with a component that owns state. Rendering <div><Counter /></div> again with a different prop keeps the counter’s state, while switching the parent from <div> to <section> resets it:

function Counter({ label }) {
  const [n, setN] = useState(0);
  return <button onClick={() => setN(n + 1)}>{label}:{n}</button>;
}

function Same({ label }) { return <div><Counter label={label} /></div>; }
function Toggle({ swap }) {
  return swap ? <div><Counter label="a" /></div> : <section><Counter label="a" /></section>;
}
// click the button once, then re-render:
//   <Same label="A" /> -> <Same label="B" />   shows "B:1"  (same type, state kept)
//   <Toggle swap={false} /> -> swap={true}      shows "a:0"  (different type, state lost)

State therefore belongs to a component’s position in the tree, not to the function. The same idea explains why the key prop can reset state on purpose.

What you do not have to do

Because the diff is automatic, the mental model is "the UI is a function of state": write what the screen should look like for the current data, and never write code that moves the screen from one state to the next. The sections that follow show how components receive data (props), remember it (state) and reach outside React (Effects).
