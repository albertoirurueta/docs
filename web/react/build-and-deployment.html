Build and Deployment

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A React app ships as static assets, a running server, or both. This page covers bundling with Vite and the three deployment shapes, with a worked static-SPA deploy.

Bundling

A bundler walks the module graph from your entry point, applies transforms (JSX → JS, TypeScript stripping), removes unused exports (tree-shaking), minifies, splits code into chunks, and writes content-hashed filenames (app.9f3a1c.js) so browsers can cache aggressively and still get updates.

Vite is the default toolchain: a dev server with hot module replacement and a production build. Vite 8 bundles with Rolldown; earlier versions used Rollup for the build and esbuild for development.

npm run build        # -> dist/  (index.html + hashed assets)
npm run preview      # serve dist/ locally to sanity-check

  • Dynamic import() becomes a separate chunk loaded on demand — the mechanism behind code splitting.

  • import.meta.env exposes build-time config; only variables prefixed VITE_ are sent to the client.

  • Source maps (build.sourcemap: true) map minified stack traces back to your source; upload them to your error tracker rather than serving them publicly.

References: Vite: Building for Production, Build a React App from Scratch.

A real build

The sample shop is a Vite app with a client router and a lazy reports page. npm run build prints the chunks it produced:

dist/index.html                             0.45 kB
dist/assets/rolldown-runtime-WkwZ5CU-.js    0.59 kB
dist/assets/Reports-Dbh9PXxC.js            12.16 kB │ map:   124.18 kB
dist/assets/index-gp5Zc0wQ.js              96.26 kB │ map:   547.85 kB
dist/assets/react-vendor-C7zjNxyP.js      218.70 kB │ map: 1,043.90 kB

Reading the output is the first performance review of the app. The hashed names change only when a file’s content changes, so the large react-vendor chunk (React and React DOM) stays cached in users' browsers across deployments while the small application chunk is refetched. Reports is separate because of the dynamic import(); it is downloaded the first time someone visits /reports.

The vendor chunk above comes from one setting. Recent Vite versions bundle with Rolldown, where chunk groups are declared under build.rolldownOptions.output.codeSplitting; Vite 7 and earlier used Rollup, where the same idea is build.rollupOptions.output.manualChunks:

// vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  build: {
    sourcemap: 'hidden',   // emit .map files but do not reference them from the bundles
    rolldownOptions: {
      output: {
        codeSplitting: {
          groups: [{ name: 'react-vendor', test: /node_modules[\\/](react|react-dom|scheduler)[\\/]/ }],
        },
      },
    },
  },
});

Do not create chunk groups by reflex: the defaults already split on dynamic imports, and an over-eager vendor group can force every page to download libraries only one route uses. sourcemap: 'hidden' writes the .map files without a sourceMappingURL comment in the bundles, so browsers do not fetch them, while you can upload them to an error tracker to de-minify stack traces.

Environment variables and modes

Vite loads .env, .env.[mode] and the .local variants for the current mode. The production build uses mode production; vite build --mode staging reads .env.staging. Only variables whose names start with VITE_ are exposed to client code through import.meta.env:

# .env.production
VITE_API_URL=https://api.example.com

# .env.staging
VITE_API_URL=https://staging-api.example.com

# .env.local  (never committed)
DB_PASSWORD=hunter2

Building in each mode and searching the output confirms what ends up in the bundle: the production build contains https://api.example.com, the staging build contains https://staging-api.example.com, and DB_PASSWORD appears in neither because it lacks the VITE_ prefix. The values that are exposed are inlined as string literals at build time, so they are visible to anyone who opens the downloaded JavaScript. Two consequences: never put a secret behind VITE_, and a build is bound to one environment, so promoting the same artifact from staging to production requires either a rebuild or a runtime configuration file (see below).

Previewing the build

vite preview serves dist/ with a static server that already falls back to index.html for unknown paths. Requesting /reports returns 200 text/html, and the hashed JavaScript is served with Cache-Control: no-cache, which is a development convenience; production caching is the host’s job (next sections). Always run the production build locally before deploying: some failures (a missing VITE_ variable, a dependency that only works unbundled) appear only there.

Three deployment models

  • (a) SPA / static build — upload dist/ to any static host or CDN (Netlify, Vercel, GitHub Pages, S3
    CloudFront). Configure a SPA fallback: rewrite unknown paths to /index.html so client-side routes work on refresh. No server. Best for dashboards, internal tools, auth-gated apps where SEO does not matter.

  • (b) SSR — a long-running Node or edge server calls renderToPipeableStream per request (or use a platform like Vercel/Netlify that runs your framework’s server for you). Best when pages are dynamic, per-user, and need fast first paint or SEO. See Server Rendering.

  • (c) SSG / prerender — render HTML per route at build time and serve the files statically, optionally revalidating (ISR). Best for content that changes rarely.

A Next.js app is deployed differently from a Vite SPA: as a Node.js server (next start), as a self-contained Docker image using output: 'standalone', as a static folder with output: 'export', or on a platform through an adapter. See Next.js Deployment and Self-Hosting.

Worked example B — a Vite React SPA on AWS S3 + CloudFront

A client-rendered SPA that calls a REST API with fetch/axios, built to static files and served from S3 behind CloudFront. No server-side rendering, so no server to run.

# 1. build
npm run build
#   dist/index.html
#   dist/assets/index-4e9b12.js
#   dist/assets/index-9a1f77.css

# 2. deploy: hashed assets get a long cache; index.html must not be cached
aws s3 sync dist/ s3://my-app-bucket --delete \
  --cache-control "public,max-age=31536000,immutable" \
  --exclude index.html
aws s3 cp dist/index.html s3://my-app-bucket/index.html \
  --cache-control "no-cache"

# 3. invalidate the CDN so index.html is refetched
aws cloudfront create-invalidation --distribution-id E123ABC --paths "/index.html"

CloudFront config: set the default root object to index.html, and add a custom error response mapping 403/404 to /index.html with a 200 status so deep links like /reports/42 load the SPA and let the client router take over. The API lives on its own origin, so it must send CORS headers for the SPA’s domain. For the private-bucket and Origin Access Control setup behind this pattern, see S3 Security and Static Hosting and CloudFront and CDN Delivery.

// the SPA just calls the API over the network
const res = await fetch(`${import.meta.env.VITE_API_URL}/products/42`);
const product = await res.json();

Caching strategy for a static deployment

The S3 commands above encode the one rule that makes SPA deployments both fast and safe to update: files whose names contain a content hash can be cached forever, and the one file whose name never changes must not be cached. index.html is the entry point that names the current hashed files, so a browser that keeps a stale copy would keep loading the previous version.

sequenceDiagram participant B as Browser participant C as CDN or host B->>C: GET /index.html C-->>B: 200, Cache-Control no-cache (always revalidated) Note over B: HTML names index-gp5Zc0wQ.js B->>C: GET /assets/index-gp5Zc0wQ.js C-->>B: 200, max-age=31536000 immutable Note over B: next visit after a deploy B->>C: GET /index.html C-->>B: new HTML naming index-NEW.js B->>C: GET /assets/index-NEW.js Note over B: unchanged vendor chunk comes from the cache

A deployment that removes old hashed files immediately (aws s3 sync --delete) can break tabs that were open before the deploy, because their lazy chunks no longer exist; keep the previous version’s assets for a while, or handle chunk-load errors by reloading the page (see Code Splitting and Suspense).

Serving the SPA from nginx in a container

When a static host is not available, the built files are served by any web server. The same two rules (fallback to index.html, long cache for hashed assets only) look like this in nginx, packaged as a multi-stage image that builds with Node and ships only the static output:

# nginx.conf
server {
  listen 80;
  root /usr/share/nginx/html;
  index index.html;

  location /assets/ {                       # hashed files: cache for a year
    add_header Cache-Control "public, max-age=31536000, immutable";
    try_files $uri =404;                    # a missing asset is a real 404, not the SPA shell
  }

  location / {
    add_header Cache-Control "no-cache";    # index.html and everything else
    try_files $uri /index.html;             # SPA fallback so deep links survive a refresh
  }
}
# Dockerfile
FROM node:24-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
ARG VITE_API_URL
ENV VITE_API_URL=$VITE_API_URL
RUN npm run build

FROM nginx:alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html

The build argument shows the build-time nature of VITE_ variables: the API URL is fixed when the image is built (docker build --build-arg VITE_API_URL=https://api.example.com .). The /assets/ location returns a real 404 for a missing file instead of the HTML shell, which prevents a stale tab from receiving index.html where it expected JavaScript.

Build once, configure at runtime

If the same artifact must run in several environments, keep environment-specific values out of the bundle and load them when the app starts, from a small file that the host serves and that is not cached:

// main.tsx
interface RuntimeConfig { apiUrl: string }

async function start() {
  const config: RuntimeConfig = await fetch('/config.json', { cache: 'no-store' }).then((r) => r.json());
  createRoot(document.getElementById('root')!).render(<App apiUrl={config.apiUrl} />);
}
start();

The deployment writes a different config.json per environment (a container entrypoint can generate it from environment variables). The file is public like everything else the browser downloads, so it can hold URLs and feature flags, never secrets.

A CI pipeline

A pipeline for the SPA runs the same checks locally and in CI, then publishes only if they pass. The steps map one to one onto the earlier sections: install exactly what the lockfile says, type-check, test, build for the target environment, and upload the hashed assets before index.html:

# .github/workflows/deploy.yml
name: deploy
on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    permissions:
      id-token: write      # OIDC: no long-lived AWS keys stored in GitHub
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: npm
      - run: npm ci
      - run: npx tsc --noEmit
      - run: npm test -- --run
      - run: npm run build
        env:
          VITE_API_URL: https://api.example.com
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/deploy-spa
          aws-region: eu-west-1
      - run: |
          aws s3 sync dist/ s3://my-app-bucket --delete --cache-control "public,max-age=31536000,immutable" --exclude index.html
          aws s3 cp dist/index.html s3://my-app-bucket/index.html --cache-control "no-cache"
          aws cloudfront create-invalidation --distribution-id E123ABC --paths "/index.html"

Uploading index.html last means a visitor can never receive a page that references assets that are not yet there. The role ARN, bucket and distribution id are placeholders for your own values.

CI/CD and environment variables

  • CI/CD — on push, install, run tests and type-check, npm run build, then publish: upload dist/ (SPA/ SSG) or deploy the server image (SSR). Keep the build reproducible (lockfile, pinned Node).

  • Build-time vs. run-time env — anything in import.meta.env.VITE_* is baked into the bundle at build and visible to users; never put secrets there. Runtime secrets belong on the server (SSR) or in the API, not the client bundle. Rebuild to change a build-time value. In Next.js the public prefix is NEXT_PUBLIC_ (read as process.env.NEXT_PUBLIC_*) instead of VITE_ (import.meta.env.VITE_*); it is also inlined at build, while unprefixed variables stay on the server and can be read at request time. See Next.js configuration and environment variables and Next.js Deployment and Self-Hosting.
