Components and Props

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A component is a JavaScript function that returns JSX. Components are the unit of reuse in React: you build a screen by composing small components into a tree.

Function components

  • A component name must start with a capital letter — Sidebar, not sidebar. JSX treats a lowercase tag as a DOM element and a capitalized tag as a component.

  • Return JSX, or null to render nothing.

  • One component per file is the common convention; the file’s default export is the component.

// Profile.jsx
export default function Profile() {
  return <img src="https://i.pravatar.cc/80" alt="" />;
}

// Gallery.jsx
import Profile from './Profile.jsx';

export function Gallery() {          // named export
  return (
    <section>
      <Profile />
      <Profile />
    </section>
  );
}

Use a default export for the one main component of a file and named exports for additional helpers. See Your First Component and Importing and Exporting Components.

Props

Props are the single argument object a component receives from its parent. Read them by destructuring in the parameter list; provide default values there too.

function Avatar({ user, size = 40, rounded = true }) {
  return (
    <img
      src={user.avatarUrl}
      alt={user.name}
      width={size}
      height={size}
      className={rounded ? 'rounded' : undefined}
    />
  );
}

// parent
<Avatar user={currentUser} size={64} />

  • children — whatever JSX a component wraps is passed as the children prop:

    function Panel({ title, children }) {
  return (
    <section className="panel">
      <h3>{title}</h3>
      {children}
    </section>
  );
}

<Panel title="Settings"><Form /></Panel>   // <Form /> is children

  • Spreading / forwarding props — pass a whole object through, usually to a wrapped DOM element:

    function TextInput({ label, ...rest }) {
  return (
    <label>
      {label}
      <input {...rest} />
    </label>
  );
}

  • Props are read-only. A component must never modify its props; to change what it sees, the parent re-renders it with new values. This is one-way data flow: data goes down as props, and a child influences an ancestor only by calling a function that ancestor passed down.

See Passing Props to a Component.

Composition over inheritance

React has no component inheritance. Reuse and customize by composing: pass elements as children or as props, and split UI into a container (owns state, fetches data) and presentational components (take props, render markup).

function Dialog({ header, children, footer }) {   // "slots" as props
  return (
    <div className="dialog">
      <header>{header}</header>
      <div className="body">{children}</div>
      <footer>{footer}</footer>
    </div>
  );
}

A render prop — a prop whose value is a function returning JSX — is an older sharing pattern. Today children and custom Hooks usually replace it.

Keeping components pure

A component must be pure: given the same props and state it returns the same JSX, and it does not change anything outside itself while rendering (no mutating variables created before it ran, no writing to the DOM, no network calls). Side effects belong in event handlers or in Effects.

let count = 0;

function Broken() {
  count += 1;             // impure: mutates an external variable during render
  return <p>{count}</p>;
}

function Ok({ items }) {
  const total = items.length;   // pure: derived from props during render
  return <p>{total}</p>;
}

<StrictMode> double-invokes components in development precisely to make impurity visible. Think of your UI as two trees: the render tree (which component rendered which) and the module dependency tree (which file imports which). See Keeping Components Pure and Understanding Your UI as a Tree.

Deep dive: from a monolithic component to a component tree

A frequent first draft puts the whole screen in one function: formatting, stock rules, layout and buttons are all mixed together. It works, but nothing can be reused and every change risks the rest. Refactoring is mostly about finding the seams — parts that have a name, take clear inputs and could appear elsewhere.

For the storefront, a product page naturally splits into five pieces:

flowchart TB PP["ProductPage
(owns the data)"] --> L["List
(generic, render prop)"] L --> PC["ProductCard"] PC --> C["Card
(layout slots)"] PC --> PR["Price"] PC --> SB["StockBadge"]
function Price({ amount, currency = 'EUR' }) {
  const text = new Intl.NumberFormat('en', { style: 'currency', currency }).format(amount);
  return <span className="price">{text}</span>;
}

function StockBadge({ stock }) {
  if (stock === 0) return <em>Sold out</em>;
  return <small>{stock} left</small>;
}

// Layout only: knows nothing about products. Slots are ordinary props.
function Card({ header, children, footer }) {
  return (
    <article className="card">
      <header>{header}</header>
      <div className="body">{children}</div>
      {footer && <footer>{footer}</footer>}
    </article>
  );
}

function ProductCard({ product, actions }) {
  return (
    <Card header={<h2>{product.name}</h2>} footer={actions}>
      <Price amount={product.price} />
      <StockBadge stock={product.stock} />
    </Card>
  );
}

Each component is pure and testable on its own: StockBadge is a function of one number. Card is reusable for orders, invoices or users because it only decides where things go, and the caller decides what goes there.

Deep dive: render props and when to still use them

A render prop is a prop whose value is a function that returns JSX. It lets a generic component own the algorithm (iterate, handle the empty case, assign keys) while the caller owns the markup of each item.

function List({ items, getKey, renderItem, empty = <p>Nothing here</p> }) {
  if (items.length === 0) return empty;
  return (
    <ul>
      {items.map((item) => <li key={getKey(item)}>{renderItem(item)}</li>)}
    </ul>
  );
}

function ProductPage({ products }) {
  return (
    <List
      items={products}
      getKey={(p) => p.id}
      renderItem={(p) => (
        <ProductCard product={p} actions={<button disabled={p.stock === 0}>Add to cart</button>} />
      )}
    />
  );
}

With two products, the server-rendered HTML is a <ul> of two <article class="card"> elements, the second with a disabled button because its stock is 0; with no products it is <p>Nothing here</p>.

Render props were the main way to share stateful logic before Hooks. Today, logic that has state goes into a custom Hook; render props remain a good fit when a component must call back into the caller’s markup per item (virtualized lists, tables with custom cells, headless UI libraries). Passing a function as children is the same pattern.

Forwarding the remaining props with ...rest keeps wrappers thin: <TextInput label="Qty" type="number" min={1} defaultValue={2} /> renders <label>Qty<input type="number" min="1" value="2"/></label>, with every attribute passed straight through to the input. Be aware that spreading hides what a component accepts and can pass unintended props to the DOM; prefer explicit props for components that are part of your public design system.

Deep dive: why purity is checkable

The impure Broken component above returns a different result each time it is rendered. Server rendering two <Broken /> elements in a row produces <p>1</p> and then <p>2</p>. The component is a function of hidden state, so React cannot safely skip, repeat, pause or reorder its renders, which is exactly what concurrent features do. <StrictMode> renders every component twice in development so that this kind of dependence on outside state shows up immediately. See The Rules of React for the full contract.
