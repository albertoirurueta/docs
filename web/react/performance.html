Performance and Concurrent Features

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

React re-renders a component when its state changes, when its parent re-renders, or when a context it consumes changes. Re-rendering is usually cheap. Optimize only after measuring a real problem.

The re-render model and measuring it

When a component re-renders, React also re-renders all of its descendants by default, then diffs the result and commits only real DOM changes. Slowness comes from doing expensive work in render or re-rendering large subtrees needlessly.

Measure with the React DevTools Profiler (record an interaction, read the flamegraph) and, in code, the <Profiler> component:

import { Profiler } from 'react';

<Profiler id="Sidebar" onRender={(id, phase, actualDuration) => log(id, phase, actualDuration)}>
  <Sidebar />
</Profiler>

See <Profiler>.

Render, commit and what triggers them

Every update goes through two phases. In the render phase React calls your components to compute the next UI as a tree of elements and diffs it against the previous one; this work is pure and may be interrupted. In the commit phase React applies only the real differences to the DOM, runs layout effects and then Effects. "Re-render" therefore does not mean "the DOM was rewritten": most re-renders end in a commit that changes nothing. A render is triggered by a state update in the component, by a re-render of its parent, or by a change of a context it reads.

Batching: several updates, one render

React batches state updates: all updates queued inside one event handler (and, since React 18, inside promises, timeouts and any other callback) are applied together, in a single re-render once the handler finishes. The component below sets two pieces of state after an await, which in React 17 would have caused two renders; now it renders once:

function Form() {
  const [a, setA] = useState(0);
  const [b, setB] = useState(0);
  return (
    <button
      onClick={async () => {
        await Promise.resolve();
        setA(a + 1);      // queued
        setB(b + 1);      // queued: one render for both
      }}
    >
      {a}-{b}
    </button>
  );
}

Counting renders confirms it: mount plus one update, not mount plus two. Two consequences follow. A state variable keeps its value for the whole render, so setCount(count + 1) three times in a row increments by one; use the updater form setCount((c) => c + 1) to chain updates (see State and Events). And when you must read the DOM right after an update, flushSync forces a synchronous render (see Refs and the DOM); it is an escape hatch, not a performance tool.

Reduce the work before caching it: state colocation

The cheapest optimization is to make less of the tree depend on state that changes often. The example below types into a colour field next to an expensive subtree. ExpensiveTree increments a counter each time it renders:

import { useState, type ReactNode } from 'react';

export function ExpensiveTree() { probe.expensive++; return <p>expensive subtree</p>; }

// Slow: typing re-renders the component that owns the state, and with it ExpensiveTree
export function Slow() {
  const [color, setColor] = useState('red');
  return (
    <div style={{ color }}>
      <input aria-label="Color" value={color} onChange={(e) => setColor(e.target.value)} />
      <ExpensiveTree />
    </div>
  );
}

// Fix 1: move the state down into the component that uses it
function ColorPicker() {
  const [color, setColor] = useState('red');
  return (
    <div style={{ color }}>
      <input aria-label="Color" value={color} onChange={(e) => setColor(e.target.value)} />
    </div>
  );
}
export function FastColocated() {
  return (<><ColorPicker /><ExpensiveTree /></>);
}

// Fix 2: keep the state where it is, but pass the expensive part as `children`
function Colored({ children }: { children: ReactNode }) {
  const [color, setColor] = useState('red');
  return (
    <div style={{ color }}>
      <input aria-label="Color" value={color} onChange={(e) => setColor(e.target.value)} />
      {children}              {/* same element object as last render: React skips it */}
    </div>
  );
}
export function FastChildren() {
  return <Colored><ExpensiveTree /></Colored>;
}

Typing five characters renders ExpensiveTree six times in Slow (mount plus five), but only once in each fix. In FastColocated the state moved below the expensive sibling, so nothing above it re-renders. In FastChildren the parent that creates <ExpensiveTree /> does not re-render when the state inside Colored changes, so React receives the identical element object and skips it. Both techniques cost nothing at run time, which is why they come before memo.

memo, useMemo, useCallback

These skip work when inputs are referentially unchanged (Object.is).

  • memo(Component) — skips re-rendering the component if its props are the same as last render.

  • useMemo(fn, deps) — caches the return value of fn between renders while deps are unchanged.

  • useCallback(fn, deps) — caches the function itself, so a memoized child does not re-render because it received a "new" callback.

const Row = memo(function Row({ item, onPick }) { /* ... */ });

function List({ items, onPick }) {
  const sorted = useMemo(() => [...items].sort(byName), [items]);   // expensive calc cached
  const handlePick = useCallback((id) => onPick(id), [onPick]);    // stable identity
  return sorted.map((it) => <Row key={it.id} item={it} onPick={handlePick} />);
}

They do not help — and add overhead — when the component is cheap, when props change every render anyway, or when the memoized value is trivial to recompute. References: memo, useMemo, useCallback.

Measuring memo, useMemo and useCallback

The three tools only help when used together, because each one protects the next. memo(Row) compares props with Object.is, so it is useless if the parent passes a new function each render; useCallback provides the stable function; and useMemo keeps an array or object (and an expensive computation) from being recreated. The test below counts renders of a memoized row and runs of a sort:

import { memo, useCallback, useMemo, useState } from 'react';

export interface Item { id: number; name: string }
export const counters = { row: 0, sort: 0 };

// A row that counts its renders so the effect of memo is visible in a test
export const Row = memo(function Row({ item, onPick }: { item: Item; onPick: (id: number) => void }) {
  counters.row++;
  return <li><button onClick={() => onPick(item.id)}>{item.name}</button></li>;
});

export function Catalog({ items }: { items: Item[] }) {
  const [picked, setPicked] = useState<number | null>(null);
  const [note, setNote] = useState('');

  const sorted = useMemo(() => {
    counters.sort++;
    return [...items].sort((a, b) => a.name.localeCompare(b.name));
  }, [items]);
  const pick = useCallback((id: number) => setPicked(id), []);   // stable identity for memo(Row)

  return (
    <>
      <input aria-label="Note" value={note} onChange={(e) => setNote(e.target.value)} />
      <p>Picked: {picked ?? 'none'}</p>
      <ul>{sorted.map((it) => <Row key={it.id} item={it} onPick={pick} />)}</ul>
    </>
  );
}

After the first render the counters are { row: 3, sort: 1 }. Typing five characters into the note field re-renders Catalog five times, yet the counters stay the same: sorted is cached because items did not change, and each Row receives the same item object and the same pick function, so memo skips it. Replace pick with an inline arrow function and row climbs by three on every keystroke, which is the failure the Profiler would show as rows that "rendered because the props changed". The callback setPicked needs no dependency because state setters are stable.

The React Compiler

The React Compiler is a build-time tool that automatically memoizes components and values, so hand-written memo / useMemo / useCallback become largely unnecessary. React Compiler 1.0, the first stable release (October 2025), is considered production-ready, works with Babel and bundlers such as Vite (SWC support is experimental), and can be adopted incrementally; new Vite and Next.js apps can start with it enabled. It relies on your components following the Rules of React. See React Compiler and React Compiler v1.0.

Enabling the React Compiler

With the Babel route in a Vite project (@vitejs/plugin-react with @rolldown/plugin-babel, @babel/core and babel-plugin-react-compiler installed as dev dependencies), the compiler is one extra plugin:

// vite.config.ts
import { defineConfig } from 'vite';
import babel from '@rolldown/plugin-babel';
import react, { reactCompilerPreset } from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react(), babel({ presets: [reactCompilerPreset()] })],
});

The compiled output of a component imports a cache from react/compiler-runtime and wraps each reactive value and JSX element in a guard that compares its inputs. The compiler works inside one component at a time: it caches the elements a component creates, so an unchanged element is skipped, but it does not remove the need to structure state sensibly. Keep existing memo, useMemo and useCallback calls when you adopt it (they remain valid, and removing them can change behavior), measure with the Profiler, and use the compiler’s 'use no memo' directive to opt a component out while debugging.

Concurrent features

  • useTransition — mark a state update as non-urgent so React can keep the UI responsive and interrupt the slow render if the user types again:

    const [isPending, startTransition] = useTransition();

function onChange(e) {
  setQuery(e.target.value);                        // urgent: the input
  startTransition(() => setResults(search(e.target.value)));  // non-urgent: the list
}

  • useDeferredValue — render a non-urgent part of the UI with a "lagging" copy of a value while a fast update goes through:

    const deferredQuery = useDeferredValue(query);
const list = useMemo(() => filter(items, deferredQuery), [items, deferredQuery]);

  • <Activity> (React 19.2) — hide part of the UI with mode="hidden" instead of unmounting it: React keeps its state, destroys its Effects while hidden, and still re-renders it at lower priority, so it can be pre-rendered or restored instantly. See <Activity>.

  • <ViewTransition> (stable in React 19.3) — animate elements as they enter, exit, move or resize when an update runs inside a Transition or a Suspense reveal, using the browser’s View Transition API. See <ViewTransition> and the React 19.3 post.

  • useSyncExternalStore — subscribe safely to an external store (see Custom Hooks).

  • List virtualization — for very long lists, render only the visible rows with a library such as react-window.

Prioritizing updates: a filterable list

A transition marks work as interruptible: React renders the urgent update first, then renders the non-urgent one in the background and abandons it if newer input arrives. The two APIs solve the same problem from two sides. useDeferredValue wraps a value you receive; useTransition wraps a state update you perform. The search box below filters 2,000 products, rendering the first 50 hits:

import { memo, useDeferredValue, useState, useTransition } from 'react';

const ITEMS = Array.from({ length: 2000 }, (_, i) => `Product ${i}`);

const Results = memo(function Results({ query }: { query: string }) {
  const hits = ITEMS.filter((n) => n.toLowerCase().includes(query.toLowerCase()));
  return <ul aria-label="results">{hits.slice(0, 50).map((n) => <li key={n}>{n}</li>)}</ul>;
});

// A: useDeferredValue -- the list renders with a lagging copy of the query
export function DeferredSearch() {
  const [query, setQuery] = useState('');
  const deferred = useDeferredValue(query);
  const stale = query !== deferred;
  return (
    <>
      <input aria-label="Search" value={query} onChange={(e) => setQuery(e.target.value)} />
      <div style={{ opacity: stale ? 0.5 : 1 }} data-stale={stale}><Results query={deferred} /></div>
    </>
  );
}

// B: useTransition -- split the update in an urgent half and a non-urgent half
export function TransitionSearch() {
  const [text, setText] = useState('');
  const [query, setQuery] = useState('');
  const [isPending, startTransition] = useTransition();
  return (
    <>
      <input
        aria-label="Search"
        value={text}
        onChange={(e) => {
          setText(e.target.value);                         // urgent: the input stays responsive
          startTransition(() => setQuery(e.target.value));  // non-urgent: the list may lag
        }}
      />
      {isPending && <p role="status">Updating…</p>}
      <Results query={query} />
    </>
  );
}

Results is wrapped in memo: with the deferred value this is what makes the technique work, because while the input updates urgently the deferred value is still the old one, the memoized list sees unchanged props and skips rendering, and the expensive render happens afterwards in a low-priority pass. The stale flag (the query differs from its deferred copy) drives a visual hint. After typing a query both versions end up showing the same list; the difference is only in how responsive the input stays on slow devices.

Asynchronous state updates

Since React 19 the function passed to startTransition may be async. isPending stays true for the whole awaited operation, and a state update made before the first await is part of the transition. This is the building block under the form Actions (see Forms and Actions):

export function AsyncTransition({ save }: { save: () => Promise<void> }) {
  const [isPending, startTransition] = useTransition();
  const [saved, setSaved] = useState(false);
  return (
    <>
      <button
        disabled={isPending}
        onClick={() =>
          startTransition(async () => {
            await save();
            setSaved(true);               // after an await: a normal update, not marked as a Transition
          })
        }
      >
        {isPending ? 'Saving…' : 'Save'}
      </button>
      {saved && <p>Saved</p>}
    </>
  );
}

While save() is pending the button shows "Saving…" and is disabled; when the promise resolves, "Saved" appears and the label returns to "Save". React cannot tell which updates after an await belong to the transition, so they are applied as ordinary urgent updates; if such an update is itself expensive, wrap it in a nested startTransition(() => ...).
