State Management

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

As an app grows, the question shifts from "how do I hold state" to "where should this state live and how does it get where it is needed". React’s built-in answers are lifting state up and Context; larger apps often add a library.

Lifting state up

When two components need the same state, move it to their closest common parent and pass it down as props plus a setter. That parent is the single source of truth.

function FilterableList({ items }) {
  const [query, setQuery] = useState('');            // lifted here
  return (
    <>
      <SearchBox query={query} onChange={setQuery} />
      <Results items={items.filter((i) => i.name.includes(query))} />
    </>
  );
}

An input is controlled when its value comes from state (value=\{query} + onChange), and uncontrolled when the DOM holds the value and you read it with a ref or FormData on submit. Prefer controlled inputs when you need to validate or react to every keystroke. See Sharing State Between Components.

Structuring state

  • Group values that change together; keep unrelated values separate.

  • Avoid redundant state — if you can compute it from props or other state during render, do not store it.

  • Avoid duplicated state — store an id, not a copy of the whole selected object.

  • React preserves state by a component’s position in the tree. Rendering a different component type, or the same type at a different position, resets its state. Force a reset by changing the key:

    <ProfileForm key={userId} user={user} />   {/* new userId -> fresh form state */}

References: Choosing the State Structure, Preserving and Resetting State.

Context

Context passes a value to every component below a provider without threading props through every level (prop drilling).

import { createContext, useContext, useState } from 'react';

const ThemeContext = createContext('light');

function App() {
  const [theme, setTheme] = useState('dark');
  return (
    <ThemeContext value={theme}>      {/* React 19: <Context> is the provider */}
      <Toolbar />
    </ThemeContext>
  );
}

function ThemedButton() {
  const theme = useContext(ThemeContext);   // reads nearest provider above
  return <button className={theme}>OK</button>;
}

Context is for global-ish data: theme, current user, locale, a router. Do not reach for it just to avoid passing a prop one or two levels — composition (passing JSX as children) is often enough. Every consumer re-renders when the context value changes (see below). References: Passing Data Deeply with Context, createContext, useContext.

The cost of Context: every consumer re-renders

A context value is compared with Object.is. When the provider re-renders with a new value, every component that calls useContext for that context re-renders, even if it only needs a part of the value, and memo does not prevent it. Two habits keep this under control:

  • Split contexts by how often and why they change. Put the stable parts (a dispatch function, which React guarantees is stable) in one context and the frequently changing data in another. Components that only trigger updates then never re-render when the data changes.

  • Memoize an object value (useMemo), or keep it in a single useState/useReducer, so the provider does not create a new object on each of its own renders.

The reducer + context pattern in the next section applies the first habit.

Reducer + context: a shopping cart

For app-wide state with non-trivial updates, combine a reducer with context: one context provides the state, another provides dispatch, and any component can read or update without prop drilling. The running example is the cart of the shop used throughout this section. The reducer is a plain function, so it is trivially testable and has no React in it:

// cartReducer.ts
import type { Product } from '../types';

export interface CartLine { product: Product; quantity: number }
export type CartState = Record<string, CartLine>;   // keyed by product id

export type CartAction =
  | { type: 'added'; product: Product }
  | { type: 'removed'; id: string }
  | { type: 'cleared' };

export function cartReducer(state: CartState, action: CartAction): CartState {
  switch (action.type) {
    case 'added': {
      const line = state[action.product.id];
      return {
        ...state,
        [action.product.id]: { product: action.product, quantity: (line?.quantity ?? 0) + 1 },
      };
    }
    case 'removed': {
      const { [action.id]: _removed, ...rest } = state;
      return rest;
    }
    case 'cleared':
      return {};
  }
}

export const totalOf = (state: CartState) =>
  Object.values(state).reduce((sum, l) => sum + l.product.price * l.quantity, 0);

The provider wires the reducer to two contexts, and two small hooks hide the contexts and fail loudly when a component is rendered outside the provider:

// CartContext.tsx
import { createContext, useContext, useReducer, type Dispatch, type ReactNode } from 'react';
import { cartReducer, type CartAction, type CartState } from './cartReducer';

const CartStateContext = createContext<CartState | null>(null);
const CartDispatchContext = createContext<Dispatch<CartAction> | null>(null);

export function CartProvider({ children }: { children: ReactNode }) {
  const [cart, dispatch] = useReducer(cartReducer, {});
  return (
    <CartStateContext value={cart}>
      <CartDispatchContext value={dispatch}>{children}</CartDispatchContext>
    </CartStateContext>
  );
}

export function useCart(): CartState {
  const cart = useContext(CartStateContext);
  if (!cart) throw new Error('useCart must be used inside <CartProvider>');
  return cart;
}

export function useCartDispatch(): Dispatch<CartAction> {
  const dispatch = useContext(CartDispatchContext);
  if (!dispatch) throw new Error('useCartDispatch must be used inside <CartProvider>');
  return dispatch;
}
// CartUi.tsx
export function AddButton({ product }: { product: Product }) {
  const dispatch = useCartDispatch();   // reads dispatch only: never re-renders when the cart changes
  return <button onClick={() => dispatch({ type: 'added', product })}>Add {product.name}</button>;
}

export function CartSummary() {
  const cart = useCart();
  const lines = Object.values(cart);
  return (
    <p aria-label="cart">
      {lines.reduce((n, l) => n + l.quantity, 0)} items, total {totalOf(cart).toFixed(2)}
    </p>
  );
}

Clicking AddButton twice for the widget updates CartSummary to "2 items, total 19.98", while a render counter placed in AddButton stays at one: it consumes only the stable dispatch context. See Scaling Up with Reducer and Context.

Climb the ladder one rung at a time. Most state belongs in the first two boxes; global stores are for state that many distant components read and write often, where Context’s "every consumer re-renders" behavior hurts.

External stores and useSyncExternalStore

Every global-state library is, underneath, a store that lives outside React plus a way for components to subscribe to it. React’s primitive for this is useSyncExternalStore(subscribe, getSnapshot): it re-renders the component when the snapshot changes, and it is safe under concurrent rendering because React reads the snapshot consistently during a render (no "tearing", where two parts of the UI show different values of the same store). The smallest useful store is a value, a setter and a subscribe function:

// externalStore.ts
import { useSyncExternalStore } from 'react';

export function createStore<T>(initial: T) {
  let state = initial;
  const listeners = new Set<() => void>();
  return {
    get: () => state,
    set(next: T) {
      if (Object.is(next, state)) return;   // no change, no notification
      state = next;
      listeners.forEach((l) => l());
    },
    subscribe(listener: () => void) {
      listeners.add(listener);
      return () => listeners.delete(listener);
    },
  };
}

export function useStore<T, S>(store: ReturnType<typeof createStore<T>>, select: (s: T) => S): S {
  return useSyncExternalStore(store.subscribe, () => select(store.get()));
}

Two rules keep it correct. getSnapshot must return the same value (by Object.is) while nothing changed, otherwise React loops, so a selector must not build a new object on every call. And state must be updated immutably, because "did it change" is a reference comparison. The libraries below add selectors, middleware, dev tools and persistence on top of exactly this mechanism. A test only needs to call store.set inside act() and assert on the DOM.

The same cart in three libraries

The library choice is mostly about how updates are written and how components subscribe. The three examples below keep the same cart and are exercised the same way in a test: dispatch an update inside act() and assert on what the component shows.

Zustand

Zustand is a tiny store created with create; a component subscribes by passing a selector, and re-renders only when the selected value changes. It needs no provider. Here it reuses the reducer from above:

import { create } from 'zustand';
import { cartReducer, type CartAction, type CartState } from './cartReducer';

interface CartStore {
  cart: CartState;
  dispatch: (action: CartAction) => void;
}

export const useCartStore = create<CartStore>()((set) => ({
  cart: {},
  dispatch: (action) => set((s) => ({ cart: cartReducer(s.cart, action) })),
}));

function Badge() {
  const kinds = useCartStore((s) => Object.keys(s.cart).length);   // re-renders only when this number changes
  return <span>kinds {kinds}</span>;
}

Adding a second unit of a product that is already in the cart does not change the number of kinds, so Badge does not re-render; adding a different product does. This selector-based subscription is what Context cannot offer.

Redux Toolkit

Redux Toolkit keeps all state in a single store, changed only by dispatching actions to reducers, with Immer letting a reducer "mutate" a draft while producing an immutable result. Its strengths are traceability (every change is a named action, visible in the Redux DevTools with time travel) and a large ecosystem of middleware.

// cartSlice.ts
import { configureStore, createSlice, type PayloadAction } from '@reduxjs/toolkit';
import type { Product } from '../types';

interface Line { product: Product; quantity: number }

const cartSlice = createSlice({
  name: 'cart',
  initialState: {} as Record<string, Line>,
  reducers: {
    added(state, action: PayloadAction<Product>) {
      const line = state[action.payload.id];          // Immer: "mutate" a draft
      if (line) line.quantity += 1;
      else state[action.payload.id] = { product: action.payload, quantity: 1 };
    },
    removed(state, action: PayloadAction<string>) {
      delete state[action.payload];
    },
  },
});

export const { added, removed } = cartSlice.actions;

export const makeStore = () => configureStore({ reducer: { cart: cartSlice.reducer } });
export type RootState = ReturnType<ReturnType<typeof makeStore>['getState']>;
export type AppDispatch = ReturnType<typeof makeStore>['dispatch'];

export const selectCount = (s: RootState) =>
  Object.values(s.cart).reduce((n, l) => n + l.quantity, 0);
import { Provider, useDispatch, useSelector } from 'react-redux';

function Badge() {
  const count = useSelector(selectCount);
  const dispatch = useDispatch<AppDispatch>();
  return <button onClick={() => dispatch(added(widget))}>count {count}</button>;
}

<Provider store={makeStore()}><Badge /></Provider>

The Provider makes the store available. It is how Redux avoids a module-level singleton, which matters for server rendering and tests: each test builds a fresh store with makeStore(). useSelector is the same idea as the Zustand selector. Writing state[id].quantity += 1 inside a reducer is only legal because of Immer; in a plain reducer such as cartReducer above it would be a bug.

MobX

MobX takes the opposite approach: state is ordinary mutable objects made observable, and components wrapped in observer re-render automatically when an observable they read during render changes. There are no selectors and no explicit subscriptions.

import { makeAutoObservable } from 'mobx';
import type { Product } from '../types';

export class CartStore {
  lines = new Map<string, { product: Product; quantity: number }>();
  constructor() {
    makeAutoObservable(this);
  }
  add(product: Product) {
    const line = this.lines.get(product.id);
    if (line) line.quantity += 1;
    else this.lines.set(product.id, { product, quantity: 1 });
  }
  get count() {                       // computed: cached until a line changes
    let n = 0;
    this.lines.forEach((l) => (n += l.quantity));
    return n;
  }
}
import { observer } from 'mobx-react-lite';

const store = new CartStore();
const Badge = observer(function Badge() {
  return <p>count {store.count}</p>;   // reading store.count subscribes this component to it
});

makeAutoObservable turns fields into observables, getters into cached computed values and methods into actions. The convenience has a cost: because mutation is allowed anywhere, a team needs conventions to keep updates in actions, and there is less built-in traceability than with Redux.

Domain models and form-heavy UIs

Whatever library you choose, do not copy server data into it. A list of products fetched from an API belongs in a query cache (see Data Fetching), which already handles loading states, deduplication and invalidation. Keep the global store for client-owned state such as the cart, the current filters or UI preferences.

Other libraries

  • Jotai — atomic state: many small independent atoms, so a component re-renders only for the atoms it reads. A good fit when state is naturally a graph of small derived values.

  • Server state — for data owned by a backend, a dedicated cache — TanStack Query, SWR, or RTK Query — is usually better than any store above; see Data Fetching.

See Managing State for the built-in story, and the Redux Toolkit quick start, the Zustand docs and MobX with React for the libraries.
