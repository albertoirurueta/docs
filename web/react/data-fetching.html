Data Fetching

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

React does not prescribe how you fetch data. The options range from a bare fetch in an Effect to a purpose-built caching library to framework-level loading. For a real app, use a library or a framework.

This page follows one running example, the product catalog of a small shop (GET /api/products and GET /api/products/:id), through every approach so the trade-offs are visible side by side. Every snippet was run against a mocked API with the setup described in Testing.

Where server data lives

Data from a backend is server state: it is owned elsewhere, it can change without your app knowing, and several components may want the same value. That makes it different from UI state such as "is the menu open". Each approach below answers the same four questions differently: when does the request start, who caches the result, what happens when the inputs change mid-flight, and how are loading and error states expressed.

fetch in an Effect: the baseline

function Product({ id }) {
  const [product, setProduct] = useState(null);
  const [error, setError] = useState(null);

  useEffect(() => {
    let ignore = false;
    fetch(`/api/products/${id}`)
      .then((r) => { if (!r.ok) throw new Error(r.status); return r.json(); })
      .then((data) => { if (!ignore) setProduct(data); })
      .catch((e) => { if (!ignore) setError(e); });
    return () => { ignore = true; };
  }, [id]);

  if (error) return <p role="alert">Failed to load.</p>;
  if (!product) return <Spinner />;
  return <ProductView product={product} />;
}

Its problems: request waterfalls (child fetches only start after the parent renders), race conditions (handled here with the ignore flag or an AbortController), no cache (every mount refetches), and no shared loading/error conventions. See Effects for the Effect mechanics, Networking for fetch itself, and — for cross-origin requests — What is CORS?.

Making the baseline correct: status, abort and a typed state

Three details separate a correct fetching Effect from a fragile one. First, fetch only rejects on a network failure: a 404 or 500 resolves normally, so the response must be checked. Second, the ignore flag stops a stale result from being stored, but the request still runs to completion; an AbortController cancels it. Third, three independent useState calls (product, error, loading) can disagree with each other, while a single discriminated union cannot.

// api.ts
const BASE = import.meta.env.VITE_API_URL ?? '';

export class HttpError extends Error {
  constructor(public status: number) {
    super(`HTTP ${status}`);
  }
}

export async function getJson<T>(path: string, signal?: AbortSignal): Promise<T> {
  const res = await fetch(`${BASE}${path}`, { signal });
  if (!res.ok) throw new HttpError(res.status);   // fetch only rejects on network errors
  return res.json() as Promise<T>;
}
// useProduct.ts
import { useEffect, useState } from 'react';
import { getJson } from './api';
import type { Product } from './types';

type State =
  | { status: 'loading' }
  | { status: 'error'; error: Error }
  | { status: 'success'; product: Product };

export function useProduct(id: string): State {
  const [state, setState] = useState<State>({ status: 'loading' });

  useEffect(() => {
    const controller = new AbortController();
    setState({ status: 'loading' });
    getJson<Product>(`/api/products/${id}`, controller.signal)
      .then((product) => setState({ status: 'success', product }))
      .catch((error) => {
        if (error.name !== 'AbortError') setState({ status: 'error', error });
      });
    return () => controller.abort();          // a newer id (or unmount) cancels this request
  }, [id]);

  return state;
}

When id changes from 1 to 2, React runs the cleanup of the first Effect (aborting request 1) before it runs the Effect for 2, so a slow response for 1 can never overwrite the result for 2. A component using the hook reads like the three cases of the union:

export function ProductCard({ id }: { id: string }) {
  const state = useProduct(id);
  if (state.status === 'loading') return <p>Loading…</p>;
  if (state.status === 'error') return <p role="alert">Failed to load.</p>;
  return <h2>{state.product.name} (${state.product.price})</h2>;
}

Under React’s <StrictMode> in development every Effect runs, is cleaned up and runs again, so you will see two requests for a mount; that is the check that your cleanup works, not a bug. A test that verifies the race is straightforward: render with id="1" while the mock delays that response, re-render with id="2", wait for the second product, and assert that the first never appears.

Request waterfalls

A waterfall is a chain of requests where each one can only start after the previous one finished. It is easy to build by accident with fetch-in-Effect, because a child component does not mount (and so does not fetch) until its parent has the data and renders it:

sequenceDiagram participant P as ProductPage participant R as Reviews child participant S as Server P->>S: GET /api/products/1 S-->>P: product Note over P: render, mount child R->>S: GET /api/products/1/reviews S-->>R: reviews Note over P,R: total time = sum of both requests

Two requests of 50 ms each take about 100 ms in sequence. The remedies all move the start of the second request earlier: start both requests in the same place (the parent, a route loader, or a server component) and pass the results or promises down; prefetch the data a child will need as soon as the parent knows the id (queryClient.prefetchQuery, or a router loader); or, with a server component, await the independent requests with Promise.all. Lifting the fetch into the parent is the simplest fix, and a query library makes it nearly free because the child’s useQuery finds the data already in the cache.

axios and server-state libraries

axios is a small HTTP client with interceptors, automatic JSON, and a terser API than fetch; it does not solve caching or races.

import axios from 'axios';
import type { Product } from './types';

export const http = axios.create({ baseURL: import.meta.env.VITE_API_URL, timeout: 5000 });

// interceptor: one place to attach credentials or translate errors
http.interceptors.response.use(
  (res) => res,
  (error) => {
    if (axios.isAxiosError(error) && error.response?.status === 401) {
      window.dispatchEvent(new Event('session-expired'));
    }
    return Promise.reject(error);
  },
);

export const fetchProduct = (id: string, signal?: AbortSignal) =>
  http.get<Product>(`/api/products/${id}`, { signal }).then((r) => r.data);   // JSON is parsed, non-2xx rejects

Compared with getJson above, axios already parses JSON, rejects on non-2xx statuses (the rejection carries error.response.status), supports a timeout, and accepts the same AbortSignal. Its interceptors are the natural place for cross-cutting concerns such as an Authorization header or redirecting to a login page on 401. Because it only wraps the request, you still need an Effect or a query library around it; a query function can call fetchProduct exactly as it would call getJson.

TanStack Query (and SWR, and RTK Query) treat server data as a cache: they deduplicate concurrent requests, cache by key, revalidate in the background (on focus, on reconnect, on interval), and expose mutations with cache invalidation.

import { useQuery } from '@tanstack/react-query';

function Product({ id }) {
  const { data, isPending, error } = useQuery({
    queryKey: ['product', id],
    queryFn: () => fetch(`/api/products/${id}`).then((r) => r.json()),
    staleTime: 60_000,
  });

  if (isPending) return <Spinner />;
  if (error) return <p role="alert">Failed to load.</p>;
  return <ProductView product={data} />;
}

How the query cache behaves

The queryKey is the identity of the data: two components that call useQuery with the same key share one cache entry and one in-flight request. A cache entry moves through a small lifecycle, driven by two timers:

  • staleTime (default 0) is how long fetched data counts as fresh. Fresh data is returned from the cache without a request. Stale data is still shown immediately, and a background refetch is triggered when a component mounts, the window regains focus, or the network reconnects.

  • gcTime (default five minutes) is how long an entry with no observers (no mounted component using it) is kept before it is garbage collected, which makes going back to a page instant.

stateDiagram-v2 [*] --> Fetching: first observer mounts Fetching --> Fresh: response arrives Fresh --> Stale: staleTime elapses Stale --> Fetching: mount, focus or reconnect Fresh --> Inactive: last observer unmounts Stale --> Inactive: last observer unmounts Inactive --> Fetching: observer mounts again and data is stale Inactive --> [*]: gcTime elapses

A request failure retries three times with exponential backoff by default, which is why tests construct the QueryClient with retry: false. Keep query keys structured and put every input the function depends on into the key, so the cache invalidates correctly; a small factory keeps keys consistent:

import { queryOptions } from '@tanstack/react-query';
import { getJson } from './api';
import type { Product } from './types';

export const productKeys = {
  all: ['products'] as const,
  detail: (id: string) => ['products', id] as const,
};

export const productsQuery = () =>
  queryOptions({ queryKey: productKeys.all, queryFn: ({ signal }) => getJson<Product[]>('/api/products', signal) });

export const productQuery = (id: string) =>
  queryOptions({
    queryKey: productKeys.detail(id),
    queryFn: ({ signal }) => getJson<Product>(`/api/products/${id}`, signal),
    staleTime: 60_000,
  });

queryOptions bundles key and function so the same definition works in useQuery, in queryClient.prefetchQuery (to remove a waterfall) and in queryClient.getQueryData, with the data type inferred. The signal passed to the query function is aborted when the query is cancelled, so a navigation away cancels the request for free.

Mutations, invalidation and optimistic updates

Writes use useMutation. After a successful write the cached data is out of date, so the mutation invalidates the affected keys and the library refetches whatever is currently displayed. An optimistic update goes one step further: it writes the expected result into the cache before the server answers, so the UI responds instantly, and rolls back if the request fails.

import { useMutation, useQueryClient } from '@tanstack/react-query';
import { sendJson } from './api';
import { productKeys } from './queries';
import type { Product } from './types';

export function useRename(id: string) {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (name: string) => sendJson<Product>('PATCH', `/api/products/${id}`, { name }),
    onMutate: async (name) => {
      await qc.cancelQueries({ queryKey: productKeys.detail(id) });   // stop in-flight refetches
      const previous = qc.getQueryData<Product>(productKeys.detail(id));
      qc.setQueryData<Product>(productKeys.detail(id), (old) => old && { ...old, name });
      return { previous };
    },
    onError: (_err, _name, ctx) => qc.setQueryData(productKeys.detail(id), ctx?.previous),
    onSettled: () => qc.invalidateQueries({ queryKey: productKeys.all }),   // refetch list and detail
  });
}

The three callbacks form a small protocol. onMutate runs first: it cancels refetches that could overwrite the optimistic value, snapshots the old value, writes the new one, and returns the snapshot as context. onError receives that context and restores the snapshot. onSettled runs on success and failure and re-synchronizes with the server, so the cache converges on the truth either way. Because productKeys.all is a prefix of productKeys.detail(id), one invalidateQueries call refreshes both the list and the detail view.

export function ProductPage({ id }: { id: string }) {
  const { data, isPending, error } = useQuery(productQuery(id));
  const rename = useRename(id);
  if (isPending) return <p>Loading…</p>;
  if (error) return <p role="alert">Failed to load.</p>;
  return (
    <>
      <h2>{data.name}</h2>
      <button onClick={() => rename.mutate('Widget Pro')}>Rename</button>
      {rename.isError && <p role="alert">Rename failed.</p>}
    </>
  );
}

In a test with a PATCH handler that fails after a short delay, the heading changes to Widget Pro immediately (the optimistic write) and returns to Widget once the failure is reported. For the React 19 Actions alternative to this pattern, useOptimistic, see Forms and Actions.

Suspense and the use API

A third style reads data during render and lets React’s <Suspense> show the fallback while the promise is pending (see Code Splitting and Suspense). The use API unwraps a promise; the one rule is that the promise must be stable across renders, so it comes from a cache keyed by the input rather than being created inline.

import { Suspense, use } from 'react';
import { getJson } from './api';
import type { Product } from './types';

const cache = new Map<string, Promise<Product>>();

export function loadProduct(id: string): Promise<Product> {
  let promise = cache.get(id);
  if (!promise) {
    promise = getJson<Product>(`/api/products/${id}`);
    cache.set(id, promise);                  // same promise on every render for the same id
  }
  return promise;
}

function ProductName({ promise }: { promise: Promise<Product> }) {
  const product = use(promise);              // suspends until the promise settles
  return <h2>{product.name}</h2>;
}

export function ProductSuspense({ id }: { id: string }) {
  return (
    <Suspense fallback={<p>Loading…</p>}>
      <ProductName promise={loadProduct(id)} />
    </Suspense>
  );
}

A hand-written module-level cache like this never expires and never revalidates, so it is only appropriate for data that is immutable for the page’s lifetime; in an application the promise normally comes from a router loader, a query library’s Suspense mode (useSuspenseQuery), or a Server Component that passes the promise to a Client Component as a prop. If the promise rejects, use throws the error to the nearest error boundary.

GraphQL and framework loading

For GraphQL APIs, a client such as Apollo Client, urql, or Relay provides the query cache and normalized store equivalent to the above. For a deeper reference on configuring these clients — Apollo Client, urql and Relay — see GraphQL Reference: configuring clients.

At the HTTP level GraphQL is a POST of a query document and its variables to a single endpoint, and the server answers with data and/or errors. Two points matter for the client code: a response with errors is usually still HTTP 200, so the status code alone does not tell you whether the call worked; and the variables object plays the role of the :id URL segment. You can call a GraphQL API with the same fetch-plus-TanStack-Query combination as a REST API, which is enough for simple apps:

import { useQuery } from '@tanstack/react-query';
import type { Product } from './types';

const PRODUCT_QUERY = /* GraphQL */ `
  query Product($id: ID!) {
    product(id: $id) { id name price }
  }
`;

// GraphQL over HTTP is a POST with { query, variables }. Errors arrive with status 200 in `errors`.
export async function gql<T>(query: string, variables: Record<string, unknown>, signal?: AbortSignal): Promise<T> {
  const res = await fetch(`${import.meta.env.VITE_API_URL}/graphql`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ query, variables }),
    signal,
  });
  const body = (await res.json()) as { data?: T; errors?: { message: string }[] };
  if (!res.ok || body.errors?.length) throw new Error(body.errors?.[0]?.message ?? `HTTP ${res.status}`);
  return body.data as T;
}

export const useGqlProduct = (id: string) =>
  useQuery({
    queryKey: ['gql-product', id],
    queryFn: ({ signal }) => gql<{ product: Product }>(PRODUCT_QUERY, { id }, signal).then((d) => d.product),
  });

What a dedicated GraphQL client adds on top is a normalized cache (an entity fetched by one query updates every other query that shows it), generated types from the schema, fragments colocated with components, and subscriptions. Reach for one when many screens share the same entities.

The modern answer for many apps is to fetch on the server: a framework route loader or a React Server Component fetches data before render, eliminating the client waterfall and shipping less JavaScript. In Next.js this is covered in Next.js Data Fetching.

Choosing an approach

Situation Prefer Why

A one-off request in a small component, or a tutorial

fetch in an Effect with an AbortController

No dependency; fine while there is one request and no sharing.

The same data is shown in several places, or must stay fresh

TanStack Query, SWR or RTK Query

Shared cache, deduplication, background refetch, mutations with invalidation.

An app that already uses a router with data APIs

Route loaders and actions

The request starts at navigation, before any component renders, so there is no waterfall.

Public, SEO-sensitive pages

Server Components or SSR

The HTML contains the data and no client round trip is needed.

A GraphQL backend with many related screens

Apollo Client, urql or Relay

A normalized cache keeps entities consistent across queries.
