Routing

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

React itself has no router. Client-side routing — mapping the URL to which components render, without a full page reload — is provided by a library. This page starts with an orientation to the options, then walks through a complete data-driven example; follow the links for the full reference.

The options

  • React Router — the most widely used; its data APIs add loaders, actions, and pending UI. Also runs as a full framework (formerly Remix).

  • TanStack Router — type-safe routes and search params, first-class data loading.

  • Framework routers — Next.js App Router (file-system routes, Server Components; see Next.js routing fundamentals), Expo Router for React Native (see Navigation for mobile navigation in depth). If you use a framework, use its router.

Library router vs framework router

A library router is a package you add to a client-rendered app, and you wire data loading, bundling and rendering yourself. A framework router is part of a framework that owns the build, the server and the route conventions. React Router spans both: its three modes are additive.

With React Router, the mode is chosen by the top-level API you use (BrowserRouter, createBrowserRouter, or the Vite plugin), and every example below imports from the react-router package. Since React Router 7 the former react-router-dom package is merged into react-router; react-router-dom is only a thin re-export of it (its latest release is still 7.x), and the current react-router major version is 8.

Minimal examples (React Router)

Declaring routes, including a nested route and a lazy one:

import { createBrowserRouter, RouterProvider } from 'react-router';

const router = createBrowserRouter([
  {
    path: '/',
    element: <Layout />,
    children: [
      { index: true, element: <Home /> },
      { path: 'products/:id', element: <Product /> },
      { path: 'reports', lazy: () => import('./routes/reports.jsx') },
    ],
  },
]);

<RouterProvider router={router} />;

Route params and query params:

import { useParams, useSearchParams } from 'react-router';

function Product() {
  const { id } = useParams();                 // "products/:id"
  const [searchParams] = useSearchParams();
  const tab = searchParams.get('tab') ?? 'overview';   // ?tab=specs
  return <h1>Product {id} — {tab}</h1>;
}

Links and programmatic navigation:

import { Link, NavLink, useNavigate } from 'react-router';

<Link to="/products/42">View</Link>
<NavLink to="/reports" className={({ isActive }) => (isActive ? 'on' : undefined)}>
  Reports
</NavLink>;

function SaveButton() {
  const navigate = useNavigate();
  return <button onClick={() => navigate('/products/42')}>Go</button>;
}

How a router works

Whatever the library, a client-side router does three jobs. It listens to the History API (pushState, and the popstate event for back and forward buttons) instead of letting the browser load a new document; it matches the current URL against a list of route patterns to pick a chain of routes; and it renders that chain, nesting each route’s component inside its parent’s <Outlet>. A link click calls pushState, the router re-matches, and only the components that differ are replaced.

flowchart LR U["URL
/products/2?tab=specs"] --> M["Match against route patterns"] M --> C["Chain of matches
Layout, products, :id"] C --> R["Render nested
Layout > Outlet > ProductDetail"] L["Link click or navigate()"] -->|"history.pushState"| U B["Back button"] -->|"popstate"| U

Matching is by specificity, not by order: a static segment such as products/new beats a dynamic segment such as products/:id, and the splat * matches only when nothing else does, which makes it the place for a "not found" page.

A complete data-driven example

The running example is the product catalog of a small shop: a list page with a search box, a detail page, an "add to cart" form, a lazy reports page and a not-found page. It uses React Router’s data mode (createBrowserRouter in the browser, createMemoryRouter in tests), where route objects can carry a loader (read data before rendering), an action (handle a form submission) and an ErrorBoundary.

import {
  Form, Link, NavLink, Outlet, createMemoryRouter, data, isRouteErrorResponse, redirect,
  useLoaderData, useNavigation, useParams, useRouteError, useSearchParams,
  type LoaderFunctionArgs, type ActionFunctionArgs,
} from 'react-router';
import { getJson, HttpError } from '../api';
import type { Product } from '../types';

function Layout() {
  const navigation = useNavigation();
  return (
    <>
      <nav>
        <NavLink to="/" end>Home</NavLink>{' '}
        <NavLink to="/products" className={({ isActive }) => (isActive ? 'on' : undefined)}>Products</NavLink>
      </nav>
      {navigation.state === 'loading' && <p role="status">Loading…</p>}
      <main><Outlet /></main>
    </>
  );
}

The layout route renders the navigation once and an <Outlet> where the matched child appears. NavLink receives an isActive flag (and the end prop stops / from being active on every page), and useNavigation().state is 'loading' between a click and the moment the next route’s loader finishes, which is the hook for a global pending indicator.

async function productsLoader({ request }: LoaderFunctionArgs) {
  const q = new URL(request.url).searchParams.get('q') ?? '';
  const all = await getJson<Product[]>('/api/products', request.signal);
  return { q, products: all.filter((p) => p.name.toLowerCase().includes(q.toLowerCase())) };
}

function Products() {
  const { q, products } = useLoaderData<typeof productsLoader>();
  const [, setParams] = useSearchParams();
  return (
    <>
      <input aria-label="Search" defaultValue={q} onChange={(e) => setParams({ q: e.target.value })} />
      <ul>
        {products.map((p) => (
          <li key={p.id}><Link to={p.id}>{p.name}</Link></li>
        ))}
      </ul>
    </>
  );
}

The search params are the state of the filter: typing updates the URL (/products?q=wid), the router re-runs the loader because the URL changed, and the page is shareable and survives a refresh. request.signal is aborted when a newer navigation supersedes this one, so passing it to fetch cancels the stale request. The relative <Link to={p.id}> resolves against the current route, giving /products/1.

async function productLoader({ params, request }: LoaderFunctionArgs) {
  try {
    return await getJson<Product>(`/api/products/${params.id}`, request.signal);
  } catch (e) {
    if (e instanceof HttpError && e.status === 404) throw data('No such product', { status: 404 });
    throw e;
  }
}

function ProductDetail() {
  const product = useLoaderData<typeof productLoader>();
  const { id } = useParams();
  return (
    <>
      <h1>{product.name}</h1>
      <p>id {id}</p>
      <Form method="post"><button>Add to cart</button></Form>
    </>
  );
}

async function addAction({ params }: ActionFunctionArgs) {
  // ...persist the change, for example POST to the API...
  return redirect('/cart');
}

function RouteError() {
  const error = useRouteError();
  if (isRouteErrorResponse(error)) return <p role="alert">{error.status}: {String(error.data)}</p>;
  return <p role="alert">Something went wrong.</p>;
}

A loader signals "this URL has no valid content" by throwing: data(body, { status }) produces a route error response, which renders the nearest ErrorBoundary instead of the component. <Form method="post"> submits without a page reload to the route’s action; after the action returns, React Router revalidates the loaders of the page, so data stays in sync with no manual refetch. redirect from an action (or a loader) is how you send the user on after success, or to a login page when they are not allowed to see a route.

export const routes = [
  {
    path: '/',
    Component: Layout,
    ErrorBoundary: RouteError,
    children: [
      { index: true, element: <h1>Welcome</h1> },
      {
        path: 'products',
        children: [
          { index: true, loader: productsLoader, Component: Products },
          { path: ':id', loader: productLoader, action: addAction, Component: ProductDetail },
        ],
      },
      { path: 'cart', element: <h1>Cart</h1> },
      { path: 'reports', lazy: async () => ({ Component: (await import('./Reports')).default }) },
      { path: '*', element: <h1>Not found</h1> },
    ],
  },
];

const router = createBrowserRouter(routes);   // in a test: createMemoryRouter(routes, { initialEntries: ['/products'] })

Because the route table is plain data, a test can build a router with createMemoryRouter and initialEntries, render <RouterProvider router={router} />, and drive it like a user: type into the search box, click a link, submit the form, then assert on the headings and on router.state.location. Requesting /products/999 renders the ErrorBoundary with 404: No such product, an unknown path renders the splat route, and /reports loads its chunk on demand through lazy. The lazy route property downloads the route module only when the route is matched, which is route-level code splitting without React.lazy.

Protecting routes

A route that needs a signed-in user can check in its loader and redirect before rendering anything, so the protected component never flashes. Parent loaders run for every child route, which makes a layout route the natural gatekeeper:

async function requireUser({ request }: LoaderFunctionArgs) {
  const user = await getCurrentUser();                       // your session lookup
  if (!user) {
    const from = new URL(request.url).pathname;
    throw redirect(`/login?from=${encodeURIComponent(from)}`);   // remember where to come back to
  }
  return user;
}

const routes = [
  { path: '/login', Component: Login },
  { path: '/account', loader: requireUser, Component: AccountLayout, children: [/* ... */] },
];

This is a user-experience guard, not a security boundary: the client bundle is public, so the API behind the route must enforce authorization itself.

Choosing a router

Use a framework router (Next.js, React Router framework mode) when you want server rendering, automatic code splitting and a prescribed project layout. Use React Router data mode or TanStack Router for a client rendered SPA that wants loaders and typed params without adopting a server framework. Use declarative mode only for small apps where <Routes> and <Route> are enough and data loading is handled by a query library.

Lazy routes pair with code splitting: each route’s component is its own chunk, downloaded on first visit. For everything else — data loading, nested layouts, error elements, scroll restoration — see reactrouter.com, tanstack.com/router, or the Next.js docs (and Next.js routing fundamentals in this reference).
