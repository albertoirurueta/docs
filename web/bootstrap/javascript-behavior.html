JavaScript Behavior

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Interactive Bootstrap components — modals, dropdowns, tooltips, offcanvas panels, collapses, carousels, toasts — need JavaScript to open, close, and animate, in addition to the CSS that styles them. Bootstrap 5 exposes two ways to drive that behavior: declarative data-bs-* attributes for the common case, and a full JavaScript API for programmatic control. This page covers both, the library’s dependency model, and the custom events every stateful component dispatches as it changes state.

Declarative behavior via data-bs-* attributes

For the majority of uses — a button that opens a modal, a link that toggles a collapse — no JavaScript needs to be written at all. Bootstrap’s own bundled script watches the document for clicks on elements carrying data-bs-toggle, and wires up the target component automatically:

<button type="button" class="btn btn-primary" data-bs-toggle="modal" data-bs-target="#exampleModal">
  Launch modal
</button>

<div class="modal" id="exampleModal" tabindex="-1">
  <div class="modal-dialog">
    <div class="modal-content">
      <div class="modal-header">
        <h5 class="modal-title">Modal title</h5>
        <button type="button" class="btn-close" data-bs-dismiss="modal" aria-label="Close"></button>
      </div>
      <div class="modal-body">Modal body content.</div>
    </div>
  </div>
</div>

data-bs-toggle="modal" identifies the component type, data-bs-target="#exampleModal" identifies which instance of it, and data-bs-dismiss="modal" on the close button closes it — three attributes, zero lines of custom script. The same pattern covers every other stateful component:

<!-- Dropdown -->
<button class="btn btn-secondary dropdown-toggle" data-bs-toggle="dropdown">Menu</button>

<!-- Collapse -->
<button class="btn" data-bs-toggle="collapse" data-bs-target="#details">Details</button>
<div class="collapse" id="details">Collapsible content.</div>

<!-- Tooltip -- requires explicit JS initialization, see below -->
<button data-bs-toggle="tooltip" data-bs-title="Helpful text">Hover me</button>

Tooltips and popovers are a deliberate exception: for performance, they are not auto-initialized on page load the way modals and collapses are (instantiating one per element would be wasteful on a page with many candidates), so they still need one explicit JavaScript call, shown below, even though they use the same data-bs-* attribute convention for their configuration.

Programmatic control via the JavaScript API

Every component that supports the data-bs-* pattern is backed by a JavaScript class of the same name — bootstrap.Modal, bootstrap.Dropdown, bootstrap.Collapse, bootstrap.Tooltip, and so on — constructible directly for cases the declarative attributes can’t express: opening a modal in response to a fetch completing, showing a toast from an error handler, or initializing every tooltip on a page in one pass.

import { Modal, Tooltip } from "bootstrap";

// Open a modal programmatically, e.g. after an async operation
const modalEl = document.getElementById("exampleModal");
const modal = new Modal(modalEl);
modal.show();

// Explicit tooltip initialization -- required, not automatic
const tooltipTriggers = document.querySelectorAll('[data-bs-toggle="tooltip"]');
tooltipTriggers.forEach((el) => new Tooltip(el));

getOrCreateInstance() is the safe way to retrieve a component instance that may already have been created (by the declarative attribute path or an earlier script), instead of risking a second, conflicting instance on the same element:

import { Modal } from "bootstrap";

const modalEl = document.getElementById("exampleModal");
const modal = Modal.getOrCreateInstance(modalEl);
modal.hide();

Every component exposes the same small, predictable method surface — typically show()/hide()/toggle() and dispose() to tear down the instance and detach its listeners — so switching from the declarative attributes to the JS API for one particular interaction doesn’t require learning a different vocabulary.

Dependencies: no jQuery, vanilla JS plus Popper.js

Bootstrap 4 and earlier required jQuery as a hard dependency for every interactive component. Bootstrap 5 dropped it entirely — every component is implemented in plain, framework-free JavaScript, which removes a sizeable dependency and its associated overhead for a project that doesn’t otherwise need jQuery.

The one dependency Bootstrap 5 still pulls in is Popper.js, used exclusively for positioning the floating elements that need to stay attached to a reference element while avoiding the viewport edge: dropdown menus, tooltips, and popovers. Popper is not needed for modals, collapses, offcanvas panels, toasts, or carousels, none of which have to dynamically reposition themselves relative to a trigger.

Two build outputs reflect this split:

File Contents

bootstrap.js / bootstrap.esm.js

Every Bootstrap component, without Popper bundled in — use this if Popper is already loaded separately (e.g. as its own dependency, or shared with another library on the page).

bootstrap.bundle.js / bootstrap.bundle.min.js

The same, with Popper bundled in — the simplest choice for a project with no other reason to manage Popper as a separate dependency.

 
<!-- Simplest path: one script tag, Popper included -->
<script src="https://cdn.jsdelivr.net/npm/bootstrap@5.3.3/dist/js/bootstrap.bundle.min.js"></script>

Component events

Every stateful component dispatches a pair of custom DOM events around each state transition — one just before the change starts, one just after it finishes (including its CSS transition, where applicable) — following the naming convention {event}.bs.{component}:

const modalEl = document.getElementById("exampleModal");

modalEl.addEventListener("show.bs.modal", (event) => {
  // fires immediately when show() is called, before the modal is visible
  console.log("Modal about to open", event.relatedTarget);
});

modalEl.addEventListener("shown.bs.modal", () => {
  // fires once the modal is fully visible and its CSS transition has completed
  document.getElementById("modal-input")?.focus();
});

modalEl.addEventListener("hidden.bs.modal", () => {
  // fires once the modal has fully closed -- safe point to reset form state
  modalEl.querySelector("form")?.reset();
});

The -ing/-ed-style pairing (show / shown, hide / hidden) is consistent across every component that has an open/close lifecycle — show.bs.collapse/shown.bs.collapse, show.bs.dropdown/shown.bs.dropdown, show.bs.offcanvas/shown.bs.offcanvas — which is what makes it practical to hook a single generic listener pattern (e.g. autofocusing the first input) across every dismissible component in a project rather than writing one-off logic per component type. The "before" event (show.bs.modal) is also cancelable via event.preventDefault(), letting application code veto the transition — for example, blocking a modal from opening until an unsaved-changes check passes.

The same flow applies whether the trigger was a data-bs-toggle click or a direct new Modal(el).show() call — the declarative attribute path is a thin layer that ends up calling the identical JavaScript API underneath, which is why both approaches dispatch the same show.bs.modal/shown.bs.modal events and can be mixed freely within one project.

Configuration and its precedence

A component’s options can come from three places, and Bootstrap merges them in a fixed order: the class’s built-in defaults (Modal.Default), then data-bs-* attributes on the element, then the options object passed to the constructor. The last one wins:

<div class="modal" id="exampleModal" data-bs-backdrop="static" data-bs-keyboard="false">...</div>
import { Modal } from "bootstrap";

const modal = new Modal(document.getElementById("exampleModal"), { keyboard: true });
// backdrop: "static"  (from the data attribute, no JS option given)
// keyboard: true      (the JS option overrides data-bs-keyboard="false")

Attribute names are the option name in kebab case prefixed with data-bs- (data-bs-custom-class, data-bs-auto-close). Options that are objects, such as a tooltip’s delay, are written as JSON in the attribute (data-bs-delay='{"show": 100, "hide": 0}'). In Bootstrap 5.3 a whole configuration can be given at once as a JSON object in data-bs-config, with the individual attributes still taking priority over it.

The component lifecycle

Every component with an open/close cycle moves through the same four states, and the events are emitted on the transitions between them. While a transition is running, further show() or hide() calls are ignored, so double-clicking a trigger does not produce overlapping animations or duplicate events:

stateDiagram-v2 [*] --> Hidden Hidden --> Showing: show() called and show event not canceled Showing --> Shown: transition ends Shown --> Hiding: hide() called and hide event not canceled Hiding --> Hidden: transition ends Hidden --> [*]: dispose()

Four events map onto this diagram: show fires on entering Showing and shown on leaving it, hide fires on entering Hiding and hidden on leaving it. Calling preventDefault() in the show or hide listener cancels the transition before it starts, so the component stays in its current state. toggle() simply calls show() or hide() depending on the current state, and returns before the transition finishes, so code that needs the final state must wait for shown/hidden rather than read the DOM immediately after the call.

Modals add one event to the set: hidePrevented.bs.modal, dispatched when a user tries to dismiss a modal that cannot be dismissed that way (a static backdrop clicked, or Escape pressed with keyboard: false). It is the hook for a "shake" animation or a "please finish the form first" message.

The event object is a normal DOM Event, with relatedTarget set to the element that triggered the change when there was one (the button whose data-bs-toggle opened a modal), and for carousels direction, from and to; for tabs relatedTarget is the tab being left or entered.

Deep dive: a delete-confirmation modal for the product catalog

The catalog page shows one "Delete" button per product, and a single shared modal asks for confirmation. The modal has no knowledge of any specific product: it is filled in when it opens, from the button that triggered it, using show.bs.modal and relatedTarget; it is closed from code when the request succeeds; and its state is cleared on hidden.bs.modal.

<button type="button" class="btn btn-outline-danger btn-sm"
        data-bs-toggle="modal" data-bs-target="#delete-modal"
        data-product-id="42" data-product-name="Mechanical Keyboard">Delete</button>

<div class="modal fade" id="delete-modal" tabindex="-1" aria-labelledby="delete-title" aria-hidden="true">
  <div class="modal-dialog">
    <div class="modal-content">
      <div class="modal-header">
        <h2 class="modal-title fs-5" id="delete-title">Delete product</h2>
        <button type="button" class="btn-close" data-bs-dismiss="modal" aria-label="Close"></button>
      </div>
      <div class="modal-body">Delete <strong id="delete-name"></strong>? This cannot be undone.</div>
      <div class="modal-footer">
        <button type="button" class="btn btn-secondary" data-bs-dismiss="modal">Cancel</button>
        <button type="button" class="btn btn-danger" id="delete-confirm">Delete</button>
      </div>
    </div>
  </div>
</div>
import { Modal } from "bootstrap";

const modalEl = document.getElementById("delete-modal");
let pending = null;

modalEl.addEventListener("show.bs.modal", (event) => {
  const trigger = event.relatedTarget;            // the Delete button that was clicked
  pending = { id: trigger.dataset.productId };
  document.getElementById("delete-name").textContent = trigger.dataset.productName;
});

document.getElementById("delete-confirm").addEventListener("click", async () => {
  const response = await fetch(`/api/products/${pending.id}`, { method: "DELETE" });
  if (response.ok) {
    Modal.getInstance(modalEl).hide();            // instance created by the data-bs-toggle attribute
  }
});

modalEl.addEventListener("hidden.bs.modal", () => {
  pending = null;                                 // safe point to reset state
});

Three details make this robust. event.relatedTarget is only set when the modal was opened by a trigger element; a modal opened with new Modal(el).show() has no relatedTarget, so code that reads it must handle undefined if the modal can also be opened programmatically. Modal.getInstance() returns the instance Bootstrap created when the trigger button was clicked, and returns null when none exists yet, whereas getOrCreateInstance() never returns null. And the same button can be activated repeatedly without duplicate listeners, because the three listeners are attached once to the modal, not once per click.

Dynamic content and cleanup

The data-API listens on document using event delegation, so triggers added to the page after load (rendered by a framework, or inserted by innerHTML) work without any call. The exceptions are the opt-in components, tooltips and popovers, which need an instance per element. For content that changes frequently, give the constructor a selector so one instance on a stable ancestor serves every matching descendant, present or future:

import { Tooltip } from "bootstrap";

new Tooltip(document.getElementById("product-table"), {
  selector: "[data-bs-toggle='tooltip']",
});

When an element that owns an instance is removed, call dispose() first (or on every instance when a single-page application unmounts a view). It removes the event listeners and the cached instance, so Modal.getInstance(el) afterwards returns null and the element can be garbage collected. In a component framework (React, Vue, Angular), create instances in a mount hook with getOrCreateInstance(ref) and dispose them in the unmount hook, and prefer the JavaScript API over data-bs-* attributes there, since the framework owns the DOM.

The optional jQuery layer

Bootstrap 5 does not need jQuery, but it still cooperates with it. When window.jQuery exists at the time Bootstrap loads (and <body> does not carry data-bs-no-jquery), every component also registers a jQuery plugin, so legacy code such as $("#exampleModal").modal("show") keeps working. The *.bs.* events are dispatched through jQuery as well, so $("#exampleModal").on("shown.bs.modal", handler) fires; with no jQuery on the page the same events are only reachable with addEventListener.

Module formats and Popper

Besides the two builds in the table above, the package ships an ESM build (bootstrap.esm.js) for bundlers. With import { Modal } from "bootstrap" a bundler can drop components that are never imported (tree-shaking), at the cost of declaring the Popper dependency yourself: bootstrap lists @popperjs/core as a peer dependency, so install it next to Bootstrap (npm install bootstrap @popperjs/core) if any of Dropdown, Tooltip or Popover is used. bootstrap.bundle.js is the opposite trade-off, a single script with every component and Popper included, and it exposes everything on window.bootstrap.
