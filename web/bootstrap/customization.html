Customization

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Bootstrap is not meant to be used as a fixed, unmodifiable stylesheet — it is a Sass source distribution, built specifically to be configured before compilation. This page covers the three main levers: overriding Sass variables and maps to retheme colors, spacing, and fonts; compiling a trimmed build that only includes what a project actually uses; and the layer of CSS custom properties Bootstrap 5 generates so some of that theming can also be adjusted live in the browser. It assumes the underlying Sass mechanics — $variable declarations, !default, and Sass maps — are already familiar; see Variables and Compilation for those fundamentals rather than repeating them here.

Every Bootstrap variable is a configuration knob

Bootstrap’s own source declares its hundreds of variables with !default, exactly the pattern documented in Variables: a value is assigned only if nothing has already defined that variable. Bootstrap’s own Sass files load each other with @import, not @use — so a project overriding Bootstrap must @import it too; @use "…" with (...) (the module-system override syntax covered in Variables) has no effect on it, since with(...) only configures the module being @use-d, not files that module itself later pulls in with @import. @import instead shares one global Sass scope, so a plain variable assignment placed before Bootstrap’s own @import "bootstrap/scss/variables"; configures its !default the same way any local variable would — no special syntax needed.

// _custom-bootstrap.scss

// 1. Functions first -- every Bootstrap partial that follows depends on it
@import "bootstrap/scss/functions";

// 2. Override individual variables -- these configure Bootstrap's own
//    !default values because @import shares one global scope
$primary:    #6f42c1;
$font-family-sans-serif: "Inter", system-ui, sans-serif;
$border-radius: 0.5rem;

// 3. Bootstrap's own variables -- skips every !default already set above
@import "bootstrap/scss/variables";
@import "bootstrap/scss/variables-dark";

// 4. Override a whole map -- $theme-colors now exists, so it can be extended
$theme-colors: map-merge(
  $theme-colors,
  (
    "brand":   #6f42c1,
    "accent":  #ff6b6b
  )
);

// 5. Everything else, including the rest of Bootstrap
@import "bootstrap/scss/maps";
@import "bootstrap/scss/mixins";
@import "bootstrap/scss/root";
@import "bootstrap/scss/bootstrap";

The ordering is not stylistic — it is required, and it runs in two passes for exactly the reason above: plain variable overrides must come before @import "bootstrap/scss/variables" (so they pre-empt its !default values), but a map override that reads an existing map like $theme-colors must come after that same import (so the map exists to read from in the first place).

Theming via maps: colors, spacing, fonts

Most of Bootstrap’s theming surface is not individual variables but maps — $theme-colors, $spacers, $font-sizes, $grid-breakpoints — for exactly the reason covered in Lists & Maps: a map is one source of truth that a loop consumes to generate many related outputs (utility classes, button variants, background/text color pairs) rather than each output being hand-maintained separately.

@use "sass:map";

// Excerpt: shown with the module syntax map.merge. In a file that also uses @import, call the global
// map-merge() instead (as in the full listing above), because @use must come before any other rule.

// Add a whole new theme color -- generates .btn-brand, .text-brand, .bg-brand,
// .border-brand, and more, automatically
$theme-colors: map.merge($theme-colors, ("brand": #6f42c1));

// Re-scale spacing from Bootstrap's default 0/0.25/0.5/1/1.5/3rem steps
$spacers: (
  0: 0,
  1: 0.25rem,
  2: 0.5rem,
  3: 1rem,
  4: 2rem,
  5: 4rem
);

// Swap the whole type scale
$font-family-base: "Source Sans Pro", sans-serif;
$font-size-base: 1rem;
$h1-font-size: $font-size-base * 2.5;

Adding one key to $theme-colors is enough to generate an entire family of component variants for that color — buttons, alerts, badges, text/background utilities — because every one of those components' Sass loops over $theme-colors rather than listing primary/secondary/success literally. This is the same mechanism, applied to component styles rather than utility classes, that The Utility API documents for $utilities specifically.

Compiling a trimmed custom build

Importing the single bootstrap/scss/bootstrap entry point pulls in every component’s styles, whether or not a project uses them. For a project that only needs a handful of components, importing individual partials instead produces a meaningfully smaller compiled stylesheet:

// 1. Required -- Bootstrap's own partials only support @import, not @use
@import "bootstrap/scss/functions";
@import "bootstrap/scss/variables";
@import "bootstrap/scss/variables-dark";
@import "bootstrap/scss/maps";
@import "bootstrap/scss/mixins";
@import "bootstrap/scss/root";

// 2. Optional -- include only what's actually used
@import "bootstrap/scss/reboot";
@import "bootstrap/scss/type";
@import "bootstrap/scss/containers";
@import "bootstrap/scss/grid";
@import "bootstrap/scss/buttons";
@import "bootstrap/scss/forms";

// 3. Utility API last, after any $utilities customization
@import "bootstrap/scss/utilities";
@import "bootstrap/scss/utilities/api";

Skipping @import "bootstrap/scss/card", .../modal, .../carousel, and every other unused component partial means their CSS — and, for components with a JS behavior, the incentive to load their JS bundle too — never ships. This is the Sass-level half of the story; the general compile pipeline (CLI vs. bundler, source maps, --style=compressed) that this build ultimately runs through is documented in full in Compilation.

Bootstrap’s use of CSS custom properties

Unlike a plain Sass variable, which is erased at compile time (see the comparison table in Variables), Bootstrap 5 also defines many of its values as CSS custom properties on :root, prefixed --bs-:

:root,
[data-bs-theme="light"] {
  --bs-primary: #0d6efd;
  --bs-body-font-family: system-ui, -apple-system, "Segoe UI", Roboto, sans-serif;
  --bs-border-radius: 0.375rem;
  --bs-gutter-x: 1.5rem;
}

This is why a color mode can be switched at runtime — no recompile — via a single data-bs-theme attribute: Bootstrap 5.3 ships a [data-bs-theme="dark"] block that redefines the same --bs-* custom properties with dark-mode values, and every component that reads var(--bs-body-bg) rather than a hard-coded color picks up the change instantly:

<html data-bs-theme="dark">
  <!-- every Bootstrap component on the page now uses the dark-mode custom property values -->
</html>

Components in turn declare their own --bs-* properties whose defaults are computed from Sass variables at build time and then read them with var(): the compiled .card rule contains --bs-card-border-radius: var(--bs-border-radius) and the card’s border radius is border-radius: var(--bs-card-border-radius). The Sass variable decides the value baked into the stylesheet, but because the rule reads a custom property, that value can still be overridden live afterward, without touching the Sass source at all:

.card {
  --bs-card-border-radius: 1rem;   /* override just this one component's radius, on this one card */
}

This two-layer model — a Sass variable decides the compiled default, a same-named CSS custom property lets that default be overridden per-element or per-theme at runtime — is exactly the pattern described generically in Variables's "Sass variables vs. CSS custom properties" section; Bootstrap 5 is simply the largest real-world example of applying it consistently across an entire component library.

Overriding components in custom SCSS

When a variable does not exist for what you need, override the component in your own SCSS by targeting the combination of classes. A chained selector such as .btn.btn-primary has a specificity of (0, 0, 2, 0), which beats Bootstrap’s own single-class .btn-primary rule, (0, 0, 1, 0), regardless of stylesheet order. Check the selector Bootstrap itself uses first, though: some components are already scoped, such as .nav-pills .nav-link.active (0, 0, 3, 0), and some already use the same compound, such as .form-control.is-invalid (0, 0, 2, 0). A shorter selector loses to them, and an equal one only wins when your stylesheet is imported after Bootstrap’s:

.btn.btn-primary            { letter-spacing: .04em; }   // (0,0,2,0) beats .btn-primary (0,0,1,0)
.nav-pills .nav-link.active { font-weight: 700; }        // (0,0,3,0) ties Bootstrap: import after it
.form-control.is-invalid    { border-width: 2px; }       // (0,0,2,0) ties Bootstrap: import after it

Keep overrides this narrow rather than reaching for !important. See Specificity of chained classes.

Partial order: what depends on what

The import order in the examples above is not arbitrary: each partial depends on the ones before it. The dependency chain below is what the "Undefined variable" or "Undefined mixin" errors are really telling you about:

flowchart TB FUNCTIONS["1. functions
tint-color, shade-color, color-contrast, map helpers"] VARIABLES["2. variables and variables-dark
all !default values"] MAPS["3. maps
theme-colors-rgb, utilities color maps"] MIXINS["4. mixins
media-breakpoint-up, button-variant, make-col"] ROOT["5. root
:root and data-bs-theme custom properties"] PARTIALS["6. component partials
reboot, grid, buttons, card, modal, ..."] UTILITIES["7. utilities, then utilities/api
the generated classes"] FUNCTIONS --> VARIABLES --> MAPS --> MIXINS --> ROOT --> PARTIALS --> UTILITIES OV1["Plain variable overrides
go before step 2"] -.-> VARIABLES OV2["Maps extended from variables
(theme-colors, grid-breakpoints) go after step 2"] -.-> MAPS OV3["Maps defined by step 3
(theme-colors-text, utilities-bg-subtle) go after step 3"] -.-> MIXINS OV4["utilities map
go between utilities and utilities/api"] -.-> UTILITIES

There are therefore four places an override can live, depending on where the thing being changed is defined:

  • Plain variables ($primary, $border-radius, $input-padding-y): before the variables partial.

  • Maps that the variables partial defines ($theme-colors, $grid-breakpoints, $spacers, $font-sizes): after variables, before maps.

  • Maps that the maps partial defines ($theme-colors-text, $theme-colors-bg-subtle, $utilities-bg-subtle): after maps, before mixins and root.

  • The $utilities map: after @import "bootstrap/scss/utilities", before @import "bootstrap/scss/utilities/api".

Feature flags

Many global behaviors are switched by $enable-* booleans, set before the variables partial like any other variable:

Variable Default Effect

$enable-rounded

true

When false, components stop emitting border-radius declarations (the --bs-border-radius custom properties still exist but nothing reads them).

$enable-shadows

false

Adds a box-shadow to buttons and form controls.

$enable-gradients

false

Adds a background-image gradient to components that support it.

$enable-transitions

true

Removes the CSS transitions when false.

$enable-reduced-motion

true

Wraps transitions in a prefers-reduced-motion guard.

$enable-dark-mode

true

Emits the [data-bs-theme="dark"] custom properties and the color-mode CSS.

$enable-negative-margins

false

Generates .mt-n1 style negative-margin utilities.

$enable-cssgrid

false

Adds the CSS Grid-based .grid and .g-col-* classes (see The Grid System).

$enable-validation-icons

true

The check and exclamation icons on validated fields.

$enable-important-utilities

true

Marks every utility declaration !important.

Using Bootstrap’s mixins and functions in your own Sass

Because Bootstrap’s mixins and functions are available once the functions, variables and mixins partials are imported, project components can use the same building blocks as the framework itself: media-breakpoint-up() for breakpoints that follow $grid-breakpoints, color-contrast() for readable text, $spacer multiples for spacing, tint-color() and shade-color() for derived shades, and @extend to give a semantic class name the styles of a Bootstrap class without adding that class in markup. The next section applies all of these.

Worked example: the Taskboard theme

This stylesheet is the complete theme for the Taskboard application: a green primary color, a purple brand color, no rounded corners, shadows enabled, a project font, a trimmed set of components, and two project components built from Bootstrap pieces. It was compiled with Bootstrap 5.3.3 and Dart Sass and the output was inspected.

// src/scss/theme.scss
@import "bootstrap/scss/functions";

// 1. Configuration: plain variables and flags, before the variables partial
$primary: #0b6e4f;
$enable-shadows: true;
$enable-rounded: false;
$font-family-sans-serif: "Inter", system-ui, sans-serif;

@import "bootstrap/scss/variables";
@import "bootstrap/scss/variables-dark";

// 2. Maps defined by the variables partial
$theme-colors: map-merge($theme-colors, ("brand": #6f42c1));

@import "bootstrap/scss/maps";
@import "bootstrap/scss/mixins";
@import "bootstrap/scss/root";

// 3. Only the Bootstrap parts the application uses
@import "bootstrap/scss/reboot";
@import "bootstrap/scss/containers";
@import "bootstrap/scss/grid";
@import "bootstrap/scss/buttons";
@import "bootstrap/scss/card";
@import "bootstrap/scss/utilities";
@import "bootstrap/scss/utilities/api";

// 4. Project components, built from Bootstrap's own variables and mixins
.task-card {
  @extend .card;
  border-left: 0.25rem solid var(--bs-primary);
  padding: $spacer * .5;

  @include media-breakpoint-up(md) {
    padding: $spacer;
  }
}

.task-card__action {
  @extend .btn;
  @extend .btn-outline-primary;
}

What the compiled output shows:

  • :root still contains the custom properties (--bs-primary is now #0b6e4f, and .btn-brand and .bg-brand exist from the extra $theme-colors entry), while no border-radius declaration is emitted by .btn, .card or the form controls, because $enable-rounded is false.

  • @extend .card rewrites the selector lists: the rules for .card become .card, .task-card, and .card > hr becomes .card > hr, .task-card > hr. .task-card therefore gets every card rule, including the descendant ones, with no extra class in the markup.

  • The extended selectors for .btn and .btn-outline-primary become .btn, .task-card__action and .btn-outline-primary, .task-card__action, so .task-card__action behaves like .btn.btn-outline-primary including its hover, active and disabled states.

  • The project’s own .task-card rule compiles to a left border and padding: 0.5rem, and to padding: 1rem inside @media (min-width: 768px), because media-breakpoint-up(md) resolves $grid-breakpoints at compile time.

@extend is the way to give semantic class names Bootstrap’s look. It also copies the selector list of every rule mentioning the extended class, which makes the output larger when many classes are extended; extending a few component classes (as here) is cheap, whereas extending a utility class generates a very long selector for each use, so apply utilities in markup instead.

Measuring a trimmed build

How much a trimmed build saves depends mostly on the utilities, which are the largest single part of Bootstrap’s CSS. These sizes come from compiling variations of the same project with Dart Sass in compressed mode and measuring the output (gzip at level 9):

Build Bytes Gzipped

Complete @import "bootstrap/scss/bootstrap" (with one overridden variable)

233,566

31,460

Reboot, type, containers, grid, buttons and forms, with all utilities

129,333

17,954

The same, with seven utility families removed through map-remove()

126,485

17,553

The same, keeping only 19 utility families through map-get-multiple()

87,075

12,984

The same, with no utilities at all

60,357

10,195

The pattern: leaving out components you do not use removes the bulk of the difference between the first two rows (the build kept a handful of component partials), and restricting the utilities removes a good part of what remains. Restricting is done with map-get-multiple() on the $utilities map, placed between the two utility imports:

@import "bootstrap/scss/utilities";

$utilities: map-get-multiple($utilities, (
  "display", "flex", "flex-direction", "justify-content", "align-items",
  "margin", "margin-x", "margin-y", "padding", "padding-x", "padding-y",
  "gap", "text-align", "font-weight", "text-color", "background-color",
  "border", "rounded", "visibility"
));

@import "bootstrap/scss/utilities/api";

In the compiled result .d-flex is present and .float-start is not, confirming that only the listed families were generated. The complementary technique, map-remove($utilities, "float", "opacity", ...), which drops chosen families and keeps the rest, saved only about 2% when it removed seven families (opacity, overflow, object-fit, z-index, float, user-select and pointer-events), because each removed family was small. Before pruning either way, search the markup for the class prefixes in use; a utility removed in Sass fails silently at run time.

The override-and-compile pipeline

flowchart LR subgraph config["Project Sass configuration"] VARS["Variable overrides
$primary, $font-family-base, ..."] MAPS["Map overrides
$theme-colors, $spacers via map.merge"] end IMPORT["@import 'bootstrap'
(full or trimmed partials)"] COMPILER["Dart Sass compiler"] CSS["Compiled CSS
component classes + :root custom properties"] RUNTIME["Browser
data-bs-theme switch, per-element --bs-* overrides"] VARS --> IMPORT MAPS --> IMPORT IMPORT --> COMPILER COMPILER --> CSS CSS --> RUNTIME classDef core fill:#3f51b5,stroke:#1a237e,color:#fff class COMPILER core

Everything left of the compiler is resolved once, at build time, exactly like the generic Sass pipeline in Compilation. Everything right of it — the data-bs-theme switch, an element-scoped --bs-card-border-radius override — happens live in the browser, with no rebuild, because it targets the CSS custom properties the compiled stylesheet already shipped.
