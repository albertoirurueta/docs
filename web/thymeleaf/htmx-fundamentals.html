htmx Fundamentals

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against htmx 2.0.11 (the latest tag on npm, published on 2026-09-22; htmx 4.0.0 exists only on the next tag, see htmx 4 status), Thymeleaf 3.1.5.RELEASE (2026-04-21), Spring Boot 4.1.1 (Spring Framework 7.0.9) and Java 21, checked on 2026-10-08. Every example was compiled and run in a scratch Bookshelf application (Maven wrapper, JDK 26 with --release 21, MockMvc tests, curl against the running jar, and a Chromium run driven by Playwright 1.62 for the browser behaviour); the HTML, headers, status codes and DOM results shown are the real output of those runs. htmx is a JavaScript library that runs in the browser, so everything about the attributes, the triggers, the swaps and the HX-* headers applies to Thymeleaf standalone, with Spring MVC and with Spring WebFlux alike: the template side is the Standard Dialect and the server side is whatever produces the HTML. The server code on this page is Spring MVC (with Spring Security, so the CSRF parts are Spring MVC specific); a WebFlux controller returns the same fragments, see Reactive Rendering with WebFlux. The library htmx-spring-boot (version 5.2.0) that wraps the headers in Java is the subject of htmx with Spring Boot; this page uses plain Spring MVC and Thymeleaf only, so you see what is on the wire. Recipes built from these pieces (active search, infinite scroll, bulk actions) are on htmx Patterns. The running scenario is the Bookshelf introduced on the Getting Started page.

Hypermedia-driven applications

A classic web page works like this: a link or a form makes the browser request a URL, the server answers with a complete HTML document, and the browser replaces the current page. htmx keeps that model and removes one restriction: any element can issue the request, on any event, with any HTTP method, and the response replaces any element instead of the whole window. The server still answers with HTML, so the application stays a hypermedia application: the markup it returns contains the next set of available actions (links, forms, buttons with hx-* attributes), which is the idea of Hypertext As The Engine Of Application State (HATEOAS). There is no JSON contract to keep in sync with a front-end model, and no client-side templating. This style is called HTML over the wire, and it fits Thymeleaf very well, because a Thymeleaf template can already render a fragment on its own (see Fragments and Fragment Rendering & AJAX).

The whole exchange of one htmx request, from the keystroke to the swapped DOM, looks like this (this is the active-search input of the demo application of this page):

sequenceDiagram participant U as User participant H as htmx in the browser participant S as Spring MVC and Thymeleaf U->>H: types in the search input H->>H: hx-trigger input changed delay 300ms, one request after the pause H->>S: GET /shelf?q=em with HX-Request true, HX-Target results, HX-Trigger-Name q S->>S: controller sees HX-Request and returns the results fragment S-->>H: 200 text/html, only the table H->>H: swap into the results div (innerHTML), add htmx-swapping then htmx-settling H->>U: new table is visible, URL pushed as /shelf?q=em H->>H: events htmx:afterSwap and htmx:afterSettle

Source: htmx — Requests & Responses

htmx has a design rule that matters for Thymeleaf applications: it is progressive enhancement friendly. The search input of the demo sits inside a normal GET form with a submit button, so a browser without JavaScript still searches (the whole page is reloaded). hx-boost goes further and turns ordinary links and forms into AJAX requests with no change to the markup, and falls back to normal navigation when JavaScript is off. Other patterns need more work to degrade gracefully, and some cannot degrade at all; that is a trade-off you make per feature. Two server-side consequences follow, and both appear again in the pitfalls table:

  • The same URL often has to answer a full page (a normal navigation, a copied link, the history restore) and a fragment (an htmx request). The controller decides on the HX-Request request header, and sends Vary: HX-Request so that caches key on it.

  • A response is HTML for the swap, not for the whole window: it is never a redirect page, and a state change is answered with the changed fragment instead of the Post/Redirect/Get dance.

Installing htmx

htmx has no dependencies and needs no build step. Four ways of getting htmx.min.js into a Thymeleaf application, from quickest to most controlled:

Way How

CDN (jsDelivr)

One script tag with a pinned version and a Subresource Integrity (SRI) hash. Quick, but the browser depends on a third party at run time; the htmx docs themselves say to consider not using a CDN in production.

Copy the file

Download htmx.min.js from jsDelivr (or the npm package) into src/main/resources/static/js/ and reference it with th:src="@{/js/htmx.min.js}".

Webjar

The Maven artifact org.webjars.npm:htmx.org wraps the npm package; Spring Boot serves it from /webjars/htmx.org/<version>/dist/htmx.min.js with no extra configuration. This is what the demo application uses.

npm / bundler

npm install htmx.org@2.0.11, then bundle node_modules/htmx.org/dist/htmx.js (or the .min.js) with your own scripts, or import 'htmx.org' in the entry point of a bundler. Use it when a front-end build is already present (for example for Tailwind CSS).

The verb attributes with th:hx-*

Five attributes issue a request, each with the URL as its value: hx-get, hx-post, hx-put, hx-patch and hx-delete. The element makes the request when its trigger fires (see Triggers) and, by default, puts the response inside itself.

Attribute Meaning

hx-get

GET the URL; the parameters of the element (and of its form) go in the query string

hx-post

POST; a form-encoded body

hx-put

PUT; a form-encoded body (Spring MVC reads it as request parameters through FormContentFilter, which Boot enables)

hx-patch

PATCH; same body encoding as PUT

hx-delete

DELETE; in htmx 2 the parameters go in the URL, not the body (htmx.config.methodsThatUseUrlParams defaults to ["get", "delete"])

Source: htmx — AJAX

In a Thymeleaf template the URL is a link expression, so the context path, the path variables and the URL encoding are handled by Thymeleaf. The attribute is written as th:hx-get, because the Standard Dialect sets any attribute with the th: prefix by evaluating its value as a Standard Expression (the default attribute processor); th:hx-get="@{/shelf}" renders as hx-get="/shelf". The same works for every hx-* attribute, and a conditional expression that yields null removes the attribute, which this page uses for hx-swap-oob and for the polling of a finished job. If you also write a static hx-get next to the th:hx-get, the static value is what a browser shows when it opens the template file without Thymeleaf, which keeps the template natural.

th:hx-delete with a link expression
<button type="button"
        th:hx-delete="@{/shelf/books/{id}(id=${b.id})}"
        hx-confirm="Remove this book from the shelf?"
        hx-target="closest tr" hx-swap="outerHTML swap:300ms">Remove</button>

Rendered (book 1):

Source: Using Thymeleaf — Setting the value of any attribute (default attribute processor)

The hx-* attribute values that are fixed (hx-target, hx-swap, hx-confirm above) need no th: prefix. Use th:hx-* only for values computed on the server: URLs, ids, flags. Never concatenate user-provided text into an attribute that htmx interprets as code or JSON, see Security. The dialect that adds shorter attributes (hx:get, with automatic CSRF) belongs to the library described on htmx with Spring Boot; everything here works without it.

htmx also accepts the data- prefix for every attribute (data-hx-post), for editors or validators that reject unknown attributes. Attribute names are case-insensitive in HTML, so hx-on handlers cannot use camel-case event names; see Events.

The controller answers the same URL with the full page or with the fragment. A boosted request also carries HX-Request: true, but it swaps the whole body, so it must get the full page; the controller therefore looks at HX-Boosted as well. The view names are constants chosen by the controller, never built from the request:

The same URL returns the page or the fragment (ShelfController)
    @GetMapping
    String index(@RequestParam(defaultValue = "") String q,
                 @RequestParam(defaultValue = "ALL") Filter filter,
                 @RequestHeader(name = "HX-Request", required = false) String hxRequest,
                 @RequestHeader(name = "HX-Boosted", required = false) String boosted,
                 Model model, HttpServletResponse response) {
        response.addHeader(HttpHeaders.VARY, "HX-Request");
        response.addHeader(HttpHeaders.VARY, "HX-Boosted");
        fill(model, q, filter, new NewBook());
        // a boosted request swaps the whole <body>, so it needs the full page
        boolean fragmentOnly = "true".equals(hxRequest) && boosted == null;
        return fragmentOnly ? "shelf/fragments :: results" : "shelf/index";
    }

    private void fill(Model model, String q, Filter filter, NewBook form) {
        model.addAttribute("q", q);
        model.addAttribute("filter", filter);
        model.addAttribute("books", shelf.search(q, filter));
        model.addAttribute("total", shelf.count());
        model.addAttribute("newBook", form);
    }

Triggers

A request starts when the element’s trigger fires. Without hx-trigger the natural event of the element is used: change for input, textarea and select, submit for a form, and click for everything else. hx-trigger takes a comma-separated list of triggers; each one has its own modifiers. It is not inherited.

Modifier Effect

once

The trigger fires only once

changed

Only fires when the element’s value has changed since the last request (change is the event, changed the modifier)

delay:<time>

Waits, and every new event resets the countdown (a debounce)

throttle:<time>

Ignores further events for the interval

from:<selector>

Listens on another element, for example from:body for hot keys or for events sent by an HX-Trigger response header. Accepts document, window, closest <selector>, find <selector>, next, previous. The selector is evaluated once, not when the page changes

target:<selector>

Only events whose target matches the selector; useful with from:body for elements that are added later

consume

The event does not trigger other htmx requests on ancestors

queue:<option>

What happens to events while a request is in flight: first, last (the default), all or none

A filter is a JavaScript expression in square brackets after the event name; the symbols are resolved against the event first (ctrlKey, key), then the global scope, and this is the element. Filters need eval, so they stop working when htmx.config.allowEval is false. Special events are load (fires once when the element is loaded), revealed (once, when the element scrolls into the viewport), and intersect (once, when it first intersects the viewport; options root:<selector> and threshold:<0.0 to 1.0>). Inside an element with overflow scrolling, use intersect once instead of revealed. Polling is written every <time>, with an optional filter after it (every 1s [!document.hidden] polls only while the tab is visible). A response with HTTP status 286 stops the polling; the response is still swapped. A custom event, for example one sent by the server, is just another trigger name.

Controlling the request

Besides the verb, the trigger, the target and the swap, a handful of attributes shape what is sent and what happens around it. Most are inherited, so one attribute on a container applies to every htmx element inside it; set a child to unset (or use hx-disinherit) to opt out, and htmx.config.disableInheritance plus hx-inherit turn the model around. hx-trigger and hx-swap-oob are not inherited.

Out-of-band swaps

A response can carry more than the main fragment. An element with hx-swap-oob is taken out of the response and swapped into the page by id, wherever it is, and everything else goes to the target in the normal way. The value is true (same as outerHTML), any hx-swap value, or a swap value, a colon and a selector (beforeend:#table tbody). With a strategy other than outerHTML the wrapping element is stripped, so give it the right tag for the context. An element that cannot stand alone in HTML (tr, td, thead, tbody, li and others) is put inside a template element; the template is removed afterwards. It is the way to update a counter, a toast or a navigation highlight in the same response as the main change.

The demo adds a book. The response is the new table row for the target (hx-target="#rows" with hx-swap="beforeend") plus the book counter in the page heading. Notes on out-of-band swaps:

  • By default any element with hx-swap-oob in the response is processed, even one nested inside the main fragment. That is a problem when the same fragment is also a normal part of a larger response (it is pulled out of its place). htmx.config.allowNestedOobSwaps set to false limits out-of-band swaps to elements adjacent to the main content.

  • An id that does not exist in the page raises htmx:oobErrorNoTarget; nothing is swapped.

  • The events htmx:oobBeforeSwap and htmx:oobAfterSwap surround each out-of-band swap.

  • hx-select-oob on the requesting element is the opposite approach: the page, not the response, says which parts of a full-page response to pick.

  • The htmx 2.0.11 documentation also describes hx-partial, a server-sent swap command where the response wraps content in hx-partial elements with an hx-target. It is in the 2.0.11 source and in the reference list, but this page does not use it; the hx-swap-oob form above is the long-standing and portable one.

Boost, history and the location bar

hx-boost="true" converts the anchors and forms inside an element into AJAX requests: a link becomes a GET whose response replaces the body (the innerHTML swap), the URL is pushed into the browser history, and a form is submitted with its own method and action. Only links to the same domain that are not local anchors are boosted. hx-boost="false" turns it off for a child, and with JavaScript disabled everything is a normal link. The request carries HX-Boosted: true; since it is an AJAX request, keep that in mind for redirects. The demo boosts its navigation:

Boosted navigation

In Chromium a click on "About" sent GET /shelf/about with HX-Request: true, HX-Boosted: true and HX-Current-URL; the page was not reloaded (a JavaScript marker survived), the URL changed to /shelf/about and document.title became "About - Bookshelf", because htmx takes the title of the response.

Source: htmx — hx-boost

History. hx-push-url="true" pushes the request URL (or the URL given as the attribute value) onto the browser history; hx-replace-url replaces the current entry; false disables a push that would come from an ancestor or from boost. Before the request, htmx saves a snapshot of the body (or of the element with hx-history-elt) in the browser’s web storage, and when the user goes back it swaps the snapshot in again. On a cache miss it requests the URL from the server with HX-History-Restore-Request: true and expects the full page; if htmx.config.refreshOnHistoryMiss is true it reloads the page instead. The documentation says the snapshots live in localStorage; the 2.0.11 source and the Chromium run use sessionStorage under the key htmx-history-cache, so clear that key when testing. hx-history="false" anywhere on a page keeps it out of the cache (for sensitive pages), and htmx.config.historyCacheSize set to 0 disables the cache.

Response headers are not processed on 3xx responses: the browser follows a redirect internally and htmx sees the headers of the final response. Server-triggered events

HX-Trigger takes an event name (pinned), a comma-separated list (event1, event2) or a JSON object ({"showMessage": "text"} puts the value in evt.detail.value; a nested object puts each property in evt.detail). Add a target property to fire the event on another element ({"showMessage": {"target": "#otherElement"}}). The event is fired on the triggering element and bubbles to the body, so an element that reacts to it needs from:body (hx-trigger="pinned from:body") or a listener on document.body. HX-Trigger fires as soon as the response is received, HX-Trigger-After-Swap after the swap and HX-Trigger-After-Settle after the settle step.

Responses, errors and status codes

htmx swaps responses according to their HTTP status. The defaults of htmx.config.responseHandling are: 204 is not swapped and is not an error, 2xx and 3xx are swapped, 4xx and 5xx are not swapped and are errors (htmx:responseError is fired), and anything else is not swapped. A network failure fires htmx:sendError. The array can be replaced; each entry has a code (a regular expression), swap, error, ignoreTitle, select, target and swapOverride. For inline validation, the usual change is to swap 422 responses; the demo does it in the htmx-config meta tag shown above.

CSRF

With Spring Security’s default CSRF protection, a POST, PUT, PATCH or DELETE without the token is rejected. A th:action form that is submitted by htmx gets the token as the hidden _csrf input Thymeleaf adds to it (the request body of the add form in the browser run was _csrf=<token>&title=Solaris&author=Stanislaw%20Lem). An element that is not inside such a form (the hx-delete and hx-put buttons) has no hidden input, and th:hx-post does not add a token automatically. Send it as a header for every htmx request:

  1. Put the token in meta tags, as the head fragment does (${_csrf.token} and ${_csrf.headerName}), and add it from an htmx:configRequest listener; the first lines of the script above are that listener. Every request in the Chromium run carried an X-CSRF-TOKEN header, and `GET`s, which do not need it, carry it too.

  2. Or put it in hx-headers on the body (inherited by every element). The demo’s About page does this (rendered and checked in a MockMvc test, but not exercised in the browser run); the rendered tag was <body hx-headers='{"X-CSRF-TOKEN": "<token>"}'> (the token is shortened here, and Thymeleaf wrote the quotes as " in the real output). A boosted navigation does not replace the body element itself, only what is inside it, so the meta approach is the more robust one.

The token in hx-headers on the body
<body th:hx-headers='|{"${_csrf.headerName}": "${_csrf.token}"}|'>

Do not send the token as a request parameter for hx-delete: htmx 2 puts the parameters of a DELETE in the URL, where the token would end up in access logs. The hx: Thymeleaf dialect of htmx-spring-boot-thymeleaf adds the header for you and is described on htmx with Spring Boot; the Spring Security side (CsrfToken, the SecurityFilterChain, an expired session) is on Spring Security Integration.

With the header removed on purpose (Playwright stripped X-CSRF-TOKEN from the pin request), the server rejected the request and htmx fired htmx:responseError with the status; in the scratch application it was 401 over HTTP Basic (the MockMvc test with a mock user saw 403), and with curl a POST without the token answered 401 too, while the same POST with -H "X-CSRF-TOKEN: $TOKEN" answered 200. If an ordinary form login is used the same failure is a 403.

Security

htmx makes HTML more expressive, which means HTML injected into a page can now start requests. The rules:

  • Escape everything. th:text and [[...]] escape user data; th:utext does not (see Template Security & XSS). Every fragment this page returns uses th:text. If you must inject third-party HTML, scrub attributes starting with hx- and data-hx as well as script tags, and wrap it in an element with hx-disable, which stops htmx processing the element and everything inside it; the attribute cannot be disabled by injecting further content.

  • No user data in code. hx-vals and hx-headers are JSON by default. Values given with the js: prefix are evaluated, so never splice request data into them, and do not build the JSON for hx-vals by concatenating strings from a user; use hidden inputs and hx-include. The demo’s hx-vals is a constant, and the HX-Trigger JSON contains only a generated number.

  • No view names or fragment selectors from the request. The controller maps a header or parameter to one of a fixed set of constants. The value of HX-Target is useful for logging and for choosing between constant views, never for composing a template name.

  • State changes use POST, PUT, PATCH and DELETE, never hx-get; keep CSRF on, and send the token as a header.

  • Configuration. selfRequestsOnly stays true (a request to another origin needs false or an htmx:validateUrl listener), allowEval can be false when a strict Content-Security-Policy forbids eval, allowScriptTags can be false, and hx-history="false" keeps sensitive pages out of the history snapshots. A CDN script needs SRI (see Installing) or a copy served from your own origin.

  • Responses are HTML for the swap. A login page swapped into a table is the typical symptom of an expired session; handle it with an entry point that answers htmx requests with HX-Redirect (described on Spring Security Integration).

Source: htmx — Security

htmx 2 compared with htmx 1.x

htmx 2.0 is deliberately close to 1.x. The migration guide lists these changes:

  • Extensions are not in the core file any more; each is a separate file and npm package (htmx-ext-sse and the others in the table above), the SSE extension must be the 2.x version, and the legacy hx-ws and hx-sse attributes are replaced by the extensions. The htmx-1-compat extension restores most of the 1.x behaviour.

  • Defaults changed: scrollBehavior is instant (it was smooth), methodsThatUseUrlParams includes delete (DELETE parameters go in the URL), and selfRequestsOnly is true (cross-domain requests need false).

  • hx-on is replaced by hx-on: attributes (the colon form, kebab-case event names): hx-on="htmx:beforeRequest: ..." becomes hx-on:htmx:before-request="...".

  • Module builds: ESM, AMD and CJS files in dist next to the browser-loadable htmx.js.

  • htmx.makeFragment() always returns a DocumentFragment, and the extension API method selectAndSwap is replaced by swap.

  • Internet Explorer is no longer supported; htmx 1.x continues to support it.

htmx 4 status

htmx 4.0.0 was published to npm on 2026-08-28 and is available only on the next tag; latest is still 2.0.11 (published 2026-09-22), and the htmx home page and this page’s examples pin 2.0.11. The documentation of htmx 4 is at https://four.htmx.org/docs/ and lists three major behaviour changes compared with htmx 2:

  • Attribute inheritance is explicit. An inherited attribute is written with the :inherited modifier (hx-confirm:inherited="Are you sure?", hx-headers:inherited=...); htmx.config.implicitInheritance set to true restores the htmx 2 behaviour.

  • Responses with 400 and 500 status codes are swapped by default, with an hx-status attribute to control per-code behaviour, and htmx.config.noSwap can restore the htmx 2 behaviour.

  • History uses a request to the server, instead of a local snapshot; the hx-history-cache extension restores local snapshots.

Event names were also standardised, htmx 4 uses fetch() instead of XMLHttpRequest, it ships an upgrade-check command-line tool (npx htmx.org@4.0.0 upgrade-check — ./path/to/project/root) and an htmx-2-compat extension. The Spring Boot library moves with it: htmx-spring-boot 6.0.0 targets htmx 4, is documented on the project’s main branch, and was not on Maven Central on 2026-10-08, so 5.2.0 is the version for htmx 2. A new application on Thymeleaf can start on htmx 2.0.11 today (everything on this page was run on it) and take on htmx 4 as a separate, deliberate upgrade once the library and the extensions you use are released for it. Re-check the dates above before relying on them: htmx 4 is the part of this page that is changing.

Pitfalls

A boosted link shows a bare table inside the existing page, or the whole page nested in itself

The controller returns a fragment for every request with HX-Request: true, but a boosted request swaps the whole body, and the history restore is also an htmx request unless it is turned off

Return the fragment only when HX-Request is true and HX-Boosted is absent; set historyRestoreAsHxRequest to false; send Vary: HX-Request

After the back button the page shows only a fragment, or a cached partial

The full URL was cached with the fragment body

Vary: HX-Request (and HX-Boosted), or getCacheBusterParam; never serve a fragment for a request without HX-Request

Validation errors do not appear after a 422

4xx responses are not swapped by default (they fire htmx:responseError)

Add {"code": "422", "swap": true} to responseHandling, or use response-targets

Delete returns 204 and the row stays

A 204 is never swapped

Return 200 with an empty body for outerHTML or use hx-swap="delete" with a 200

POST from a form works, POST from a button answers 401 or 403

th:hx-post adds no CSRF token; only th:action forms get the hidden input

Add the token as a header (htmx:configRequest or hx-headers)

The CSRF token ends up in the URL of a DELETE

htmx 2 sends the parameters of a DELETE in the query string

Send the token as a header, never as a parameter

A response header (HX-Trigger, HX-Retarget) has no effect

The response was a 3xx redirect: the headers of a redirect response are not processed

Answer 200 and use HX-Redirect or HX-Location

find or closest targets nothing; htmx:targetError in the console

Put the attribute on the container, or use next, previous or closest

hx-vals is ignored

The JSON is invalid (single quotes inside, unquoted keys)

An hx-swap-oob element nested in the main response vanishes from its place

Nested out-of-band elements are processed by default

allowNestedOobSwaps: false, or return the fragment without the attribute (the oob parameter used above)

Polling never stops

The extension does nothing

Missing hx-ext, wrong load order, or a 1.x extension

Where the books are outdated

The consulted edition of Modern frontends with htmx is v1.0.0 (2023, htmx 1.x). Its chapters 3 to 6 (starting with htmx, request and response headers, the TodoMVC project and out-of-band swaps) are still a good read for the concepts, but code written for htmx 1.x needs these corrections: extensions are separate files since htmx 2, the parameters of a DELETE go in the URL, and the old hx-on attribute became hx-on:. The book loads htmx from a version-less webjar path (/webjars/htmx.org/dist/htmx.min.js), while this page uses the versioned path that needs no extra dependency. The book’s htmx-spring-boot code uses the 3.x API; this section uses 5.2.0 (see htmx with Spring Boot). Taming Thymeleaf was written before htmx became part of the Thymeleaf story.
