htmx Patterns

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page is written against Thymeleaf 3.1.5.RELEASE (2026-04-21), Spring Boot 4.1.1 (Spring Framework 7.0.9), Java 21, htmx 2.0.11 (the npm latest on 2026-10-08) and htmx-spring-boot-thymeleaf 5.2.0 (2026-10-02), checked on 2026-10-08. The library is not managed by the Spring Boot BOM, so its version is explicit in the dependency. Every controller, template and test shown was compiled and run in a scratch Bookshelf application (Maven wrapper, JDK 26 with --release 21), the curl commands were run against the running application, and the behaviour that only exists in a browser (debouncing, history, the confirm dialog, the swap animation, polling, the download, the modal and the drag and drop) was checked in Chromium driven by Playwright. The rendered output shown is the real output of those runs. The browser requests for htmx and SortableJS were answered from local copies of the exact pinned files, so the Subresource Integrity (SRI) check in the page ran against the published bytes.

htmx runs in the browser, so the templates on this page work with Thymeleaf standalone, with Spring MVC and with Spring WebFlux alike: whatever produces the HTML fragment (for standalone, TemplateEngine.process with a fragment selector, see Fragment Rendering & AJAX) is a valid htmx server. The controllers use Spring MVC and htmx-spring-boot, whose request and response helpers target the servlet stack; the reactive view technology is on Reactive Rendering with WebFlux. The attribute vocabulary used here (triggers, targets, swaps, headers) is explained on htmx Fundamentals, and the library’s annotations, views and dialect on htmx with Spring Boot; this page is the cookbook that applies them to the running Bookshelf scenario from Getting Started.

Each pattern follows the same shape: the template, the controller, the Source: link to the matching official htmx example, and the request and response as they really came back. Two ideas run through all of them and are worth stating once.

  • The server returns HTML, not data. Every endpoint answers with a fragment (the results fragment of the patterns/search template, the row fragment of patterns/books, and so on) or, for the same URL without htmx, with the full page. @HxRequest on a second handler method with the same mapping is how the library tells the two apart; it matches only requests that carry HX-Request: true.

  • State changes use POST, PUT or DELETE with the CSRF token, never GET, and every piece of user data is rendered with th:text (see Template Security & XSS). Fragment names in the controllers are string constants; request input is only ever a lookup key.

Setting up the examples

The only dependency beyond the usual starters (spring-boot-starter-webmvc, -thymeleaf, -security, -validation) is the Thymeleaf flavour of the library, which brings htmx-spring-boot (the annotations and views) and the hx: dialect with it:

<dependency>
    <groupId>io.github.wimdeblauwe</groupId>
    <artifactId>htmx-spring-boot-thymeleaf</artifactId>
    <version>5.2.0</version>
</dependency>

Source: htmx-spring-boot 5.2.0 — README

Every page of the cookbook shares one <head>, kept in a fragment so that the htmx script, the CSRF metadata and the htmx configuration live in one place:

templates/patterns/head.html
<head th:fragment="head(title)">
  <meta charset="utf-8">
  <title th:text="|${title} - Bookshelf|">Bookshelf</title>
  <meta name="_csrf" th:content="${_csrf.token}">
  <meta name="_csrf_header" th:content="${_csrf.headerName}">
  <meta name="htmx-config" content='{"historyRestoreAsHxRequest": false}'>
  <link rel="stylesheet" th:href="@{/css/patterns.css}">
  <script src="https://cdn.jsdelivr.net/npm/htmx.org@2.0.11/dist/htmx.min.js"
          integrity="sha384-2OatzQy1H+Zd/IIrjr1TcuDGqLXeHhbooAyJY1KdQMKnr4LZ22k31GBLdYKHmVjg"
          crossorigin="anonymous"></script>
  <script th:src="@{/js/patterns.js}"></script>
</head>

Source: htmx — Installing and htmx — Configuring htmx

The SRI hash is the one published for htmx.org@2.0.11/dist/htmx.min.js on the htmx documentation page, and I recomputed it from the downloaded file (openssl dgst -sha384 -binary | openssl base64 -A) before using it. The htmx-config meta tag sets historyRestoreAsHxRequest to false, which the htmx documentation recommends whenever the server answers HX-Request requests with partials: a history cache miss then asks for the full page without claiming to be a partial request (see Pagination with history).

CSRF for every state-changing request

Spring Security’s CSRF protection stays on. Forms rendered with th:action get the hidden token automatically, but an htmx request that is not a form submission must send it as a header. The metadata above plus one small static script does that for all requests that are not GETs:

static/js/patterns.js
// Adds the Spring Security CSRF token to every state-changing htmx request.
document.addEventListener('htmx:configRequest', function (event) {
  var token = document.querySelector('meta[name="_csrf"]');
  var header = document.querySelector('meta[name="_csrf_header"]');
  if (token && header && event.detail.verb !== 'get') {
    event.detail.headers[header.content] = token.content;
  }
});

Source: htmx — Configuring htmx and Spring Security — CSRF, JavaScript Applications

htmx:configRequest fires after htmx has collected the parameters, and event.detail.headers and event.detail.verb are part of its detail. There are two alternatives:

  • hx-headers on <body> carries the token as JSON; the htmx documentation shows it, and warns that hx-boost does not update <body>, so the token must sit on an element that is replaced.

  • The hx: dialect of htmx-spring-boot-thymeleaf writes the header for you on any element that uses hx:post, hx:put, hx:patch or hx:delete, even outside a form. The delete button of the delete pattern uses it, and the page it appears on renders:

<button type="button" hx-delete="/patterns/books/1"
        hx-confirm="Remove this book from the shelf?"
        hx-target="closest tr" hx-swap="outerHTML swap:1s"
        hx-headers="{&quot;X-CSRF-TOKEN&quot;:&quot;TOKEN&quot;}">Delete</button>

Source: htmx-spring-boot — Automatic CSRF token injection

Do not put the token in the URL. The recipe of a hidden _csrf input pulled in with hx-include on a hx-delete worked with htmx 1.x, but htmx 2 sends the parameters of a DELETE in the query string, which leaks the token into logs and history.

Calling the endpoints from the shell

The Bookshelf’s form login stays in place (the demo user and password are the placeholders of the scratch application’s application.properties). The shell helper below logs in once, then reads the session’s CSRF token from the meta tag that every pattern page renders; the later curl commands reuse $JAR and $TOKEN:

BASE=http://localhost:8080
JAR=$(mktemp)
LOGIN=$(curl -s -c "$JAR" "$BASE/login" | sed -n 's/.*name="_csrf" type="hidden" value="\([^"]*\)".*/\1/p')
curl -s -b "$JAR" -c "$JAR" -o /dev/null -d username=reader -d password=change-me \
     --data-urlencode "_csrf=$LOGIN" "$BASE/login"
TOKEN=$(curl -s -b "$JAR" "$BASE/patterns/search" | sed -n 's/.*name="_csrf" content="\([^"]*\)".*/\1/p')

Source: Spring Security — CSRF, JavaScript Applications

Active search

Active search sends a request while the user types and replaces the result list, with no submit button. The input does everything with attributes: delay:500ms waits until typing pauses, changed skips the request when the value is the same as the last one, and an event filter adds Enter as an immediate trigger. hx-sync="this:replace" aborts a still-running request when a newer one starts, so a slow answer can never overwrite a newer one, and hx-indicator shows the "Searching" element for the duration.

templates/patterns/search.html
<h1>Search the shelf <span class="htmx-indicator" id="searching">Searching...</span></h1>
<input type="search" name="q" th:value="${q}" placeholder="Title or author"
       th:hx-get="@{/patterns/search}"
       hx-trigger="input changed delay:500ms, keyup[key=='Enter']"
       hx-target="#results" hx-indicator="#searching" hx-sync="this:replace">
<table>
  <thead><tr><th>Title</th><th>Author</th></tr></thead>
  <tbody id="results">
    <th:block th:fragment="results">
      <tr th:each="book : ${results}">
        <td th:text="${book.title}">Emma</td>
        <td th:text="${book.author}">Jane Austen</td>
      </tr>
      <tr th:if="${#lists.isEmpty(results)}"><td colspan="2">No books match.</td></tr>
    </th:block>
  </tbody>
</table>

Source: htmx — Active Search

The fragment results is a th:block inside the <tbody>, so the response contains only table rows and the default innerHTML swap into #results is correct. One URL serves both requests: the plain method returns the whole page for a browser, the @HxRequest method returns the fragment.

@GetMapping("/patterns/search")
String searchPage(@RequestParam(defaultValue = "") String q, Model model) {
    model.addAttribute("q", q);
    model.addAttribute("results", shelf.search(q));
    return "patterns/search";
}

@HxRequest
@GetMapping("/patterns/search")
String searchResults(@RequestParam(defaultValue = "") String q, Model model) {
    model.addAttribute("results", shelf.search(q));
    return "patterns/search :: results";
}

Source: htmx-spring-boot — Mapping Requests

curl -s -b "$JAR" "$BASE/patterns/search?q=bronte" | head -3
curl -s -b "$JAR" -H 'HX-Request: true' "$BASE/patterns/search?q=bronte" -D -

Without the header the response starts with <!DOCTYPE html>; with it, only the rows come back, and the response carries Vary: HX-Request, which the library adds so that browsers and proxies do not serve the fragment to a full navigation:

HTTP/1.1 200
Vary: HX-Request
Content-Type: text/html;charset=UTF-8

      <tr>
        <td>Villette</td>
        <td>Charlotte Bronte</td>
      </tr>
      <tr>
        <td>Jane Eyre</td>
        <td>Charlotte Bronte</td>
      </tr>
      ...

(The response headers are trimmed to the interesting ones.) In Chromium, typing eliot at 60 ms per key produced exactly one search request. A query such as <script> is rendered as text by th:text and simply finds no books.

Event filters such as keyup[key=='Enter'] are JavaScript expressions that htmx evaluates, so they need htmx.config.allowEval (the default) and are unavailable under a strict Content Security Policy that forbids eval.

Click to load

Click to load appends the next page when the user asks for it. The trick is the last row of every batch: it holds a button that replaces itself with the next batch, and that batch ends with a new button, until there is no next page.

templates/patterns/click-to-load.html
<tbody>
  <th:block th:fragment="rows">
    <tr th:each="book : ${volumes}">
      <td th:text="${book.title}">Emma</td>
      <td th:text="${book.author}">Jane Austen</td>
    </tr>
    <tr th:if="${hasNext}" id="more-row">
      <td colspan="2">
        <button type="button" th:hx-get="@{/patterns/click-to-load(page=${next})}"
                hx-target="#more-row" hx-swap="outerHTML" hx-disabled-elt="this">Load more books</button>
      </td>
    </tr>
  </th:block>
</tbody>

Source: htmx — Click to Load

hx-disabled-elt="this" disables the button for the duration of the request, which prevents a double click from loading a page twice. The controller computes the page and the model once, and the infinite scroll below reuses it:

@GetMapping("/patterns/click-to-load")
String clickToLoadPage(Model model) {
    page(1, model);
    return "patterns/click-to-load";
}

@HxRequest
@GetMapping("/patterns/click-to-load")
String clickToLoadRows(@RequestParam(defaultValue = "1") int page, Model model) {
    page(page, model);
    return "patterns/click-to-load :: rows";
}

private void page(int requested, Model model) {
    List<Shelf.Volume> all = shelf.all();
    int pages = Math.max(1, (all.size() + PAGE_SIZE - 1) / PAGE_SIZE);
    int page = Math.min(Math.max(requested, 1), pages);   // clamp: page=-3 or page=999 cannot fail
    int from = (page - 1) * PAGE_SIZE;
    model.addAttribute("volumes", all.subList(from, Math.min(from + PAGE_SIZE, all.size())));
    model.addAttribute("page", page);
    model.addAttribute("next", page + 1);
    model.addAttribute("hasNext", page < pages);
}

Source: htmx — Click to Load

curl -s -b "$JAR" -H 'HX-Request: true' "$BASE/patterns/click-to-load?page=2"
      <tr>
        <td>Silas Marner</td>
        <td>George Eliot</td>
      </tr>
      ... (four more rows)
      <tr id="more-row">
        <td colspan="2">
          <button type="button" hx-get="/patterns/click-to-load?page=3"
                  hx-target="#more-row" hx-swap="outerHTML" hx-disabled-elt="this">Load more books</button>
        </td>
      </tr>

In the browser, two clicks took the table from 5 to 10 to 15 rows plus the button. The same page with paging by page=6 returns the last rows and no more-row, so the button disappears. For real data use the paging support of Spring Data (Pageable) instead of subList; see Displaying Data, Pagination & Sorting.

Infinite scroll

Infinite scroll is click to load with the click replaced by a trigger: a sentinel row holds hx-trigger="revealed", which fires when the element is scrolled into the viewport, and it replaces itself with the next batch, whose last element is a new sentinel.

templates/patterns/infinite-scroll.html
<th:block th:fragment="rows">
  <tr th:each="book : ${volumes}">
    <td th:text="${book.title}">Emma</td>
    <td th:text="${book.author}">Jane Austen</td>
  </tr>
  <tr th:if="${hasNext}" th:hx-get="@{/patterns/infinite-scroll(page=${next})}"
      hx-trigger="revealed" hx-swap="outerHTML">
    <td colspan="2">Loading more books...</td>
  </tr>
</th:block>

Source: htmx — Infinite Scroll

The official example puts the trigger on the last data row with hx-swap="afterend"; the separate sentinel row above is the same pattern without having to decide in the loop which row is the last one. The controller has the same two methods as click to load, with the template patterns/infinite-scroll and the fragment selector rows.

curl -s -b "$JAR" -H 'HX-Request: true' "$BASE/patterns/infinite-scroll?page=2" | tail -5
      <tr hx-get="/patterns/infinite-scroll?page=3"
          hx-trigger="revealed" hx-swap="outerHTML">
        <td colspan="2">Loading more books...</td>
      </tr>

In Chromium (a 900 by 500 viewport), scrolling to the bottom repeatedly loaded all six pages, and the table ended with exactly 30 rows. Two limits of revealed are documented: it expects the window to scroll, so in a container with overflow such as overflow-y: scroll use intersect once instead; and if a batch is shorter than the viewport the new sentinel is revealed at once, so batches load back to back until the screen is full. Choose a page size larger than a screen.

Pagination with history

For pagination the URL is part of the application state, so the links push it into the browser history. The links stay ordinary href links (they work without JavaScript, and can be copied), and htmx enhances them: hx-get fetches the same URL, hx-target is the page region, and hx-push-url="true" pushes the fetched URL.

templates/patterns/pagination.html
<div id="page" th:fragment="page">
  <table> ... rows ... </table>
  <nav aria-label="Pages">
    <th:block th:each="n : ${#numbers.sequence(1, pages)}">
      <a th:text="${n}" th:href="@{/patterns/pagination(page=${n})}"
         th:hx-get="@{/patterns/pagination(page=${n})}"
         hx-target="#page" hx-swap="outerHTML" hx-push-url="true"
         th:aria-current="${n == page} ? 'page'">1</a>
    </th:block>
  </nav>
</div>

Source: htmx — hx-push-url

The htmx documentation insists on one rule: if you push a URL, that URL must return a full page when opened directly, because the user can paste it into a new tab, and because htmx asks for the whole page when the history cache has no snapshot (it sends HX-History-Restore-Request: true). The controller therefore returns the fragment only for a real partial request:

@GetMapping("/patterns/pagination")
String pagination(@RequestParam(defaultValue = "1") int page, HtmxRequest htmx, Model model) {
    page(page, model);
    int pages = (shelf.all().size() + PAGE_SIZE - 1) / PAGE_SIZE;
    model.addAttribute("pages", pages);
    boolean fragmentOnly = htmx.isHtmxRequest() && !htmx.isHistoryRestoreRequest();
    return fragmentOnly ? "patterns/pagination :: page" : "patterns/pagination";
}

Source: htmx — History Support

HtmxRequest is the library’s view of the request headers; isHtmxRequest() is HX-Request and isHistoryRestoreRequest() is HX-History-Restore-Request. The condition is a second line of defence: with historyRestoreAsHxRequest set to false in the page head the restore request has no HX-Request header at all, but the controller stays correct even when the configuration is missing.

curl -s -b "$JAR" "$BASE/patterns/pagination?page=3" | head -2
curl -s -b "$JAR" -H 'HX-Request: true' "$BASE/patterns/pagination?page=3" | head -2
curl -s -b "$JAR" -H 'HX-Request: true' -H 'HX-History-Restore-Request: true' "$BASE/patterns/pagination?page=3" | head -2

The first and third responses start with <!DOCTYPE html>; the second starts with <div id="page">. In Chromium, clicking page 3 and then page 5, pressing Back restored page 3 from htmx’s history snapshot without any request, and reloading the pushed URL returned the whole page with its <title>.

Inline editing

Inline editing swaps a read-only row for an editable one and back. The row fragment has an Edit button that requests the edit row (hx-get), and the edit row’s Save button sends the row’s inputs with hx-put and hx-include="closest tr". A <form> cannot sit inside a <tr>, which is exactly why hx-include exists.

templates/patterns/books.html
<tr th:fragment="row" th:id="|book-${volume.id}|">
  <td th:text="${volume.title}">Emma</td>
  <td th:text="${volume.author}">Jane Austen</td>
  <td>
    <button type="button" th:hx-get="@{/patterns/books/{id}/edit(id=${volume.id})}"
            hx-target="closest tr" hx-swap="outerHTML">Edit</button>
    ...
  </td>
</tr>

<tr th:fragment="edit-row" th:id="|book-${id}|" th:object="${form}">
  <td>
    <input name="title" th:value="*{title}" aria-label="Title" autofocus>
    <small class="error" th:if="${#fields.hasErrors('title')}" th:errors="*{title}">error</small>
  </td>
  <td>
    <input name="author" th:value="*{author}" aria-label="Author">
    <small class="error" th:if="${#fields.hasErrors('author')}" th:errors="*{author}">error</small>
  </td>
  <td>
    <button type="button" th:hx-put="@{/patterns/books/{id}(id=${id})}" hx-include="closest tr"
            hx-target="closest tr" hx-swap="outerHTML">Save</button>
    <button type="button" th:hx-get="@{/patterns/books/{id}(id=${id})}"
            hx-target="closest tr" hx-swap="outerHTML">Cancel</button>
  </td>
</tr>

Source: htmx — Click to Edit and htmx — Edit Row

The two fragments are kept at the bottom of the page template inside a wrapper with th:remove="all", so that the full page does not render them as stray rows (Thymeleaf selects a fragment from the unprocessed template, so the wrapper does not affect it). They could equally live in a template of their own. The page lists the rows by replacing a row with the fragment inside a loop, so the same row fragment serves the list and the single-row responses, with the model attribute volume:

<tbody>
  <th:block th:each="volume : ${volumes}">
    <tr th:replace="~{:: row}"></tr>
  </th:block>
</tbody>

Source: Using Thymeleaf — Difference between th:insert and th:replace

The controller binds the edit to a record, validates it with Bean Validation, and answers an invalid save with 200 and the edit row again, error messages included:

record BookForm(@NotBlank @Size(max = 80) String title, @NotBlank @Size(max = 80) String author) { }

@HxRequest
@GetMapping("/patterns/books/{id}/edit")
String editRow(@PathVariable long id, Model model) {
    Shelf.Volume v = find(id);
    model.addAttribute("id", id);
    model.addAttribute("form", new BookForm(v.title(), v.author()));
    return "patterns/books :: edit-row";
}

@HxRequest
@PutMapping("/patterns/books/{id}")
String save(@PathVariable long id, @Valid @ModelAttribute("form") BookForm form, BindingResult errors,
        Model model) {
    if (errors.hasErrors()) {
        model.addAttribute("id", id);
        return "patterns/books :: edit-row"; // 200 with the form and its messages: htmx swaps it in
    }
    model.addAttribute("volume", shelf.update(id, form.title(), form.author()));
    return "patterns/books :: row";
}

Source: htmx — Edit Row

The 200 matters: htmx 2 does not swap 4xx or 5xx responses (it raises htmx:responseError instead), so the common REST habit of answering a failed validation with 400 or 422 would leave the user looking at an unchanged row. Either return 200, as here, or change htmx.config.responseHandling deliberately.

curl -s -b "$JAR" -H 'HX-Request: true' "$BASE/patterns/books/1/edit"
curl -s -b "$JAR" -H 'HX-Request: true' -H "X-CSRF-TOKEN: $TOKEN" -X PUT \
     -d 'title=' -d 'author=Jane Austen' "$BASE/patterns/books/1"

The second command returns the edit row with the message next to the field (the language of the message follows the request locale; the output below is the English one):

Deleting from a detail page: use 303

When the delete button is on a detail page and the answer is a redirect to the list, the status code matters. Inline form validation

Inline validation checks a field when the user leaves it, using the same rules that the final submit applies. The form posts to the page as a whole, the ISBN input posts to a field endpoint, and both use the same record and the same Bean Validation annotations:

record NewBook(@NotBlank @Size(max = 80) String title,
        @NotBlank @Pattern(regexp = "\\d{13}", message = "must be 13 digits") String isbn) { }

@HxRequest
@PostMapping("/patterns/validation/isbn")
String checkIsbn(@Valid @ModelAttribute("newBook") NewBook newBook, BindingResult errors) {
    rejectDuplicate(newBook, errors);
    return "patterns/validation :: isbn-field"; // the title errors are in the result but never rendered here
}

@PostMapping("/patterns/validation")
String submit(@Valid @ModelAttribute("newBook") NewBook newBook, BindingResult errors) {
    rejectDuplicate(newBook, errors);
    if (errors.hasErrors()) {
        return "patterns/validation :: form";
    }
    shelf.add(newBook.title(), "Unknown", "Fiction", newBook.isbn());
    return "patterns/validation :: saved";
}

private void rejectDuplicate(NewBook newBook, BindingResult errors) {
    if (!errors.hasFieldErrors("isbn") && shelf.isbnTaken(newBook.isbn())) {
        errors.rejectValue("isbn", "duplicate", "is already on the shelf");
    }
}

Progress bar with polling, and a file download

A long-running job (here, a CSV export of the shelf with an artificial delay per row) must not hold the HTTP request open. The pattern has four steps: a POST starts the job and returns at once with 202 Accepted and a progress fragment; that fragment polls its own status URL with hx-trigger="every 600ms"; each answer replaces the fragment; and when the job finishes the answer is a done fragment with no trigger, which stops the polling and offers the download.

sequenceDiagram participant B as Browser (htmx) participant C as ExportController participant S as ExportService participant T as Task executor thread B->>C: POST /patterns/export (HX-Request and X-CSRF-TOKEN) C->>S: start(owner) S->>T: execute(job) C-->>B: 202 progress fragment (hx-trigger every 600ms) loop every 600 ms while the job runs B->>C: GET /patterns/export/ID/progress C->>S: find(ID, owner) S-->>C: percent C-->>B: progress fragment with the new width, replaces itself end T->>S: csv ready B->>C: GET /patterns/export/ID/progress C-->>B: done fragment (no trigger, polling ends) B->>C: GET /patterns/export/ID/download (plain link, hx-boost false) C-->>B: 200 text/csv with Content-Disposition attachment

The job runs on Spring Boot’s applicationTaskExecutor (a TaskExecutor), which the application can inject directly; @Async on a service method would work the same way once @EnableAsync is on. The service keeps the jobs in a map, and a job is visible only to the user who started it:

@Service
public class ExportService {

    private final Map<String, Job> jobs = new ConcurrentHashMap<>();
    private final Shelf shelf;
    private final TaskExecutor executor;
    private final Duration rowDelay;

    ExportService(Shelf shelf, TaskExecutor applicationTaskExecutor,
            @Value("${bookshelf.export.row-delay:100ms}") Duration rowDelay) {
        this.shelf = shelf;
        this.executor = applicationTaskExecutor;
        this.rowDelay = rowDelay;
    }

    public String start(String owner) {
        List<Shelf.Volume> snapshot = shelf.all();
        String id = UUID.randomUUID().toString();
        Job job = new Job(owner, snapshot.size());
        jobs.put(id, job);
        executor.execute(() -> run(job, snapshot));
        return id;
    }

    /** A job is visible only to the user who started it; anything else looks like "no such job". */
    public Optional<Job> find(String id, String owner) {
        return Optional.ofNullable(jobs.get(id)).filter(j -> j.owner.equals(owner));
    }

    private void run(Job job, List<Shelf.Volume> snapshot) {
        StringBuilder out = new StringBuilder("id,title,author,genre\r\n");
        for (Shelf.Volume v : snapshot) {
            out.append(v.id()).append(',').append(cell(v.title())).append(',').append(cell(v.author()))
                    .append(',').append(cell(v.genre())).append("\r\n");
            job.processed.incrementAndGet();
            try {
                Thread.sleep(rowDelay);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
        }
        job.csv = out.toString().getBytes(StandardCharsets.UTF_8);
    }

    /** Quotes the cell and defuses spreadsheet formulas ("CSV injection"). */
    static String cell(String value) {
        String safe = value;
        if (!safe.isEmpty() && "=+-@\t\r".indexOf(safe.charAt(0)) >= 0) {
            safe = "'" + safe;
        }
        return '"' + safe.replace("\"", "\"\"") + '"';
    }
}

Modals

A modal dialog is a fragment loaded on demand into an empty slot. The native <dialog> element does most of the work: showModal() makes it modal (focus trap, backdrop, Escape to close), and a form with method="dialog" closes it without JavaScript. The only script is one hx-on attribute on the slot that opens the dialog after htmx has swapped it in:

templates/patterns/modal.html
<button type="button" th:hx-get="@{/patterns/modal/{id}(id=${book.id})}" hx-target="#modal-slot">Details</button>
<div id="modal-slot" hx-on::after-swap="this.querySelector('dialog')?.showModal()"></div>

<dialog id="book-dialog" th:fragment="dialog" aria-labelledby="book-dialog-title">
  <h2 id="book-dialog-title" th:text="${volume.title}">Emma</h2>
  <p th:text="${volume.author}">Jane Austen</p>
  <form method="dialog"><button>Close</button></form>
</dialog>

Source: htmx — Custom Modal Dialogs and MDN — the dialog element

The official examples build the modal with CSS and Hyperscript, or with Bootstrap or UIKit components; the <dialog> version needs neither. The hx-on::after-swap shorthand (double colon) is hx-on:htmx:after-swap: it listens for htmx:afterSwap, which htmx fires on the swap target, here the slot. The server side is an ordinary fragment endpoint with a 404 for unknown ids:

With htmx the selected tab is part of the markup the server returns, in the spirit of "hypertext as the engine of application state". Each tab button requests its tab, and the response contains the whole tab list with the new selection marked and the new panel.

Errors, events and progressive enhancement

htmx does not swap 4xx and 5xx responses, so a failed request can be invisible. Two events let the page say so: htmx:responseError for an HTTP error response and htmx:sendError when the request could not be sent at all (a network failure); htmx:timeout covers a configured request timeout, and htmx:afterRequest fires after every request, successful or not (event.detail.successful and event.detail.failed tell them apart). The cookbook’s script reports the first two in the #toasts container, building the message as text so that nothing from the response is parsed as HTML:

static/js/patterns.js (continued)
function toast(message) {
  var box = document.getElementById('toasts');
  if (!box) { return; }
  var p = document.createElement('p');
  p.className = 'toast';
  p.setAttribute('role', 'alert');
  p.textContent = message;
  box.appendChild(p);
}
document.addEventListener('htmx:responseError', function (event) {
  toast('The server refused the request (' + event.detail.xhr.status + ').');
});
document.addEventListener('htmx:sendError', function () {
  toast('The server could not be reached.');
});

Source: htmx — Events

In Chromium, htmx.ajax('DELETE', '/patterns/books/9999', ...) (an unknown id, answered with 404) produced the toast The server refused the request (404)., and the same call with the network request aborted produced The server could not be reached.. htmx.ajax is the JavaScript API for issuing a request without an element.

Progressive enhancement is the other design question. Plain links (<a href>) and forms (th:action) work without JavaScript, and hx-boost or hx-get on top of them only improves the experience; the pagination links are built that way, and the search, click-to-load, infinite-scroll and pagination pages each have a full-page method next to the fragment method for browsers that do not use htmx. The Add book form is the counter-example: it posts with hx-post only, so without JavaScript it would not have a working fallback until it also gets a plain action and a full-page response. Patterns that cannot work without JavaScript (drag and drop, modals loaded on demand, polling) should be offered only where that is acceptable, or have a plain alternative such as a separate page. A boosted container also changes how redirects, downloads and scripts behave, as the download example showed.

Calling a remote service with an HTTP Interface client

A fragment endpoint often has to ask another service for data, and that service can be slow or down. Spring’s HTTP Interface client (an interface annotated with @HttpExchange, turned into a proxy by HttpServiceProxyFactory) keeps that call out of the controller’s body, and the controller turns a failure into a fragment the user can read. In Spring Boot 4 the RestClient.Builder bean comes from spring-boot-starter-restclient, which the project must declare next to the web starter. The interface and its configuration:

QuoteClient and QuoteConfig (the base URL is a placeholder property)
@HttpExchange
public interface QuoteClient {

    record Quote(String text, String author) { }

    @GetExchange("/quotes/{id}")
    Quote quote(@PathVariable long id);
}

@Configuration
public class QuoteConfig {

    @Bean
    QuoteClient quoteClient(RestClient.Builder builder, @Value("${quotes.base-url}") String baseUrl) {
        RestClient restClient = builder.baseUrl(baseUrl).build();
        return HttpServiceProxyFactory.builderFor(RestClientAdapter.create(restClient))
                .build()
                .createClient(QuoteClient.class);
    }
}

Source: Spring Framework — HTTP Service Client

The controller returns the quote fragment, or the unavailable fragment with status 503 when the remote call fails (RestClientException is the base of the client’s errors). Because htmx 2 does not swap a 4xx or 5xx response, the htmx:responseError handler of the previous section shows the toast, and the hx-indicator element tells the user that the request is in progress:

Pitfalls

Symptom Cause Fix

Every PUT, POST or DELETE does nothing on the page; the server logs 403

The CSRF token is not sent. htmx does not swap 4xx responses, so the failure is silent

Send the token in a header from the htmx:configRequest event, hx-headers, or the hx: dialect; keep CSRF protection on

A form that deletes returns HTTP 204 and the row stays

htmx ignores the body of 204 No Content responses by default

Answer a delete with 200 and an empty body

Validation messages never appear

The handler answers 400 or 422; htmx 2 does not swap 4xx and 5xx responses

Return 200 with the form and its errors, or deliberately change htmx.config.responseHandling or handle htmx:beforeSwap

Edit buttons ask for confirmation or wait one second

hx-confirm and hx-swap are inherited from a parent such as the <tbody>

Put the attributes on the element that needs them, or override them on the children

After Back or a reload, the page is a bare fragment

A URL pushed with hx-push-url returns the fragment for every request

Return the full page unless HX-Request is true and HX-History-Restore-Request is not; set historyRestoreAsHxRequest to false and send Vary: HX-Request (the library does)

Clicking a download link replaces the page with the file’s text

An ancestor has hx-boost="true", so the link is fetched with AJAX

Put hx-boost="false" on the link, or avoid boosting the container

The progress bar polls forever

The status endpoint keeps returning the fragment with hx-trigger="every ...", or it fails with a 4xx that is never swapped

Return a final fragment without the trigger, return HTTP 286, and give unknown jobs a fragment instead of an error status

Infinite scroll never fires, or loads everything at once

revealed is used in a scrolling container with overflow, or the batch is shorter than the viewport

Use intersect once inside scrolling containers; make the page size larger than a screen

Sorting works once and then stops, or the list sorts twice

The list is re-created by a swap and initialised twice, or the Sortable instance stays disabled

Initialise inside htmx.onLoad, and re-enable the instance on htmx:afterSwap as the official example does

The server redirects after a DELETE and the browser sends another DELETE

A 301 or 302 keeps the method of a DELETE request

Redirect with 303 See Other

The browser downloads a CSV and a spreadsheet runs a formula from a title

Cell values that start with =, +, - or @ are interpreted as formulas (CSV injection)

Quote every cell and prefix dangerous leading characters, as in the cell helper

A tab, modal or search term is used to build a template name such as "patterns/" + name

Fragment and view names are evaluated as expressions; request input must not reach them

Map the request value through a whitelist (an enum or a map) to a constant name

User data shows up unescaped in a toast, a row or a script

Markup built with string concatenation, th:utext, or values placed inside hx-on or <script>

Use th:text in fragments; pass data as data-* attributes or JSON, never concatenated into JavaScript

  • The consulted edition of Modern frontends with htmx (Wim Deblauwe, v1.0.0, 2023) targets htmx 1.9, Spring Boot 3.1 and htmx-spring-boot 3.x.
