Security

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Vaadin’s security model layers over Spring Security: one filter chain protects the framework’s endpoints, and per-view annotations decide who may open each route. This page follows the Security documentation. It replaces the Vaadin 7 pattern of checking permissions inside a Navigator ViewChangeListener.

Enabling security

Extend VaadinWebSecurity (or apply the security configurer to an HttpSecurity) and point it at a login view. The base class already permits Vaadin’s internal requests and adds the navigation access control filter:

@EnableWebSecurity
@Configuration
public class SecurityConfig extends VaadinWebSecurity {

    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth ->
                auth.requestMatchers("/images/**", "/api/public/**").permitAll());
        super.configure(http);
        setLoginView(http, LoginView.class);
    }

    @Bean
    UserDetailsService users() {
        return new InMemoryUserDetailsManager(
            User.withUsername("admin").password("{noop}admin").roles("ADMIN").build());
    }
}

See Enabling security.

Protecting routes

Access is denied by default once security is enabled. Open each view with one annotation; the navigation access control filter enforces it on every navigation, server-side:

Annotation Meaning

@AnonymousAllowed

anyone, logged in or not

@PermitAll

any authenticated user

@RolesAllowed("ADMIN")

users with the listed role(s)

@DenyAll

no one (the default for an unannotated view)

 
@Route("login")
@AnonymousAllowed
public class LoginView extends VerticalLayout { }

@Route(value = "admin", layout = MainLayout.class)
@RolesAllowed("ADMIN")
public class AdminView extends VerticalLayout { }

Put the annotation on a shared parent layout to cover a whole area at once. For finer control, @RouteScoped services can call AccessAnnotationChecker directly.

Login and logout

LoginForm embeds in a view; LoginOverlay is a full-screen modal. Either posts to Spring Security’s /login; AuthenticationContext handles programmatic login and logout:

@Route("login")
@AnonymousAllowed
public class LoginView extends VerticalLayout implements BeforeEnterObserver {

    private final LoginForm login = new LoginForm();

    public LoginView() {
        login.setAction("login");
        add(login);
    }

    @Override
    public void beforeEnter(BeforeEnterEvent event) {
        if (event.getLocation().getQueryParameters()
                .getParameters().containsKey("error")) {
            login.setError(true);
        }
    }
}

// elsewhere
authenticationContext.logout();

CSRF and CSP

Vaadin’s own client-server channel carries a per-session CSRF token automatically — no configuration needed. A @RestController you add is protected by Spring Security’s CSRF handling as normal. Set a Content Security Policy through the shell:

public class AppShell implements AppShellConfigurator {
    @Override
    public void configurePage(AppShellSettings settings) {
        settings.addMetaTag("Content-Security-Policy",
                "default-src 'self'; img-src 'self' data:");
    }
}

Hilla endpoints

The same annotations secure Hilla endpoints and their methods (Hilla and React Views); @BrowserCallable classes are @DenyAll until annotated. See Hilla security.

Beyond the basics

  • Sensitive data — server-side setVisible(false) genuinely removes a component from the DOM, so hiding an admin button is safe; but never send data to the browser you would not let that user read. What is CORS? covers cross-origin exposure.

  • SSO — the commercial SSO Kit adds OpenID Connect / SAML single sign-on and back-channel logout on top of this model (SSO Kit).

The security pipeline

Two independent layers protect a Vaadin application, and a request passes through both. The HTTP layer is Spring Security’s filter chain: it authenticates the user (session cookie or login form), applies URL rules and CSRF checks. The navigation layer is Vaadin’s access control: when the router resolves a view, it asks whether the current user may open that route class. The two answer different questions — "who is this?" and "may this person see this view?" — so neither replaces the other.

sequenceDiagram participant B as Browser participant F as Spring Security filter chain participant R as Vaadin router participant A as Navigation access control participant V as Target view B->>F: GET /admin F->>F: authenticate from the session F->>R: request passes the URL rules R->>A: may this user open AdminView? alt allowed by @RolesAllowed A->>V: proceed with navigation V-->>B: view rendered else not logged in A->>R: forward to the login view R-->>B: login page else logged in without the role A->>R: reroute to the access-denied error view R-->>B: not found or access denied end

The consequence is that a view annotation is a UI decision. Anything reachable by an HTTP URL that is not a Flow route — a REST controller, an actuator endpoint, a static file — is protected by the filter chain rules only, and every service method that mutates data should defend itself too (see the method-security section below).

The current configuration style

VaadinWebSecurity, shown above, is the original base class. From Vaadin 24.8 it is deprecated in favour of a plain SecurityFilterChain bean that applies VaadinSecurityConfigurer, and it is gone in Vaadin 25. The configurer does the same work — permits Vaadin’s internal requests, adds the navigation access control and the login redirect — but composes like any other Spring Security customiser, so new applications should use it:

@Configuration
@EnableWebSecurity
@EnableMethodSecurity
class SecurityConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth.requestMatchers("/api/public/**").permitAll());
        http.with(VaadinSecurityConfigurer.vaadin(), vaadin -> vaadin.loginView(SignInView.class));
        return http.build();
    }

    @Bean
    UserDetailsService users() {
        return new InMemoryUserDetailsManager(
                User.withUsername("admin").password("{noop}admin").roles("ADMIN").build(),
                User.withUsername("agent").password("{noop}agent").roles("AGENT").build());
    }
}

The {noop} password prefix and the in-memory users are for examples only; use a PasswordEncoder (bcrypt or Argon2) and a real UserDetailsService in production. The configurer exposes switches such as enableCsrfConfiguration(false) and enableLogoutConfiguration(false) for the rare case where the application supplies its own, and oauth2LoginPage(...) for an OpenID Connect login.

Worked example: role-aware screens

A secure application shows each user only what they can use, and refuses the rest on the server. Three tools combine in the customer application: a role-aware menu, the signed-in user’s name, and method security on the service that does the dangerous work.

Menu entries filtered by access. AccessAnnotationChecker evaluates the same @RolesAllowed / @PermitAll annotations that the router uses, so a menu built from it can never offer a link that would then be refused:

public class RoleAwareNav extends SideNav {

    public RoleAwareNav(AccessAnnotationChecker checker, AuthenticationContext auth) {
        record Entry(String label, String path, Class<? extends Component> view) { }

        List<Entry> entries = List.of(
                new Entry("Customers", "customers", CustomerListView.class),
                new Entry("Edit", "customers/1/edit", CustomerEditorView.class));

        entries.stream()
                .filter(e -> checker.hasAccess(e.view()))
                .forEach(e -> addItem(new SideNavItem(e.label(), e.path())));

        auth.getAuthenticatedUser(UserDetails.class)
                .ifPresent(u -> getElement().setAttribute("title", "Signed in as " + u.getUsername()));
    }
}

AuthenticationContext is the programmatic counterpart of the annotations: isAuthenticated(), getAuthenticatedUser(UserDetails.class), hasRole("ADMIN"), hasAnyRole(...) and logout(). Use it for conditions the annotations cannot express (show the Delete button only to administrators), but keep in mind that a hidden button is a courtesy, not a control.

Method security as the real control. The view-level annotation can be bypassed by a new entry point — another view, a REST endpoint, a scheduled task — that calls the same service. Putting the rule on the service means every caller is checked:

@Service
public class CustomerAdmin {

    @PreAuthorize("hasRole('ADMIN')")
    public void purge(Long id) {
        // irreversible: runs only for administrators, whoever calls it
    }
}

@EnableMethodSecurity on the configuration class (shown above) activates @PreAuthorize. The service call runs on the thread that holds the SecurityContext; when you move work to a background thread (see Server Push) the context is not propagated automatically, so pass the data you need, or wrap the executor with Spring Security’s DelegatingSecurityContextExecutor.

Test the rules. Because the rules are plain annotations, AccessAnnotationChecker can assert them in an ordinary unit test — no server, browser or Spring context. The checker takes the principal and a function that answers "does this user have role X?", so any combination can be simulated:

class AccessRulesTest {

    private final AccessAnnotationChecker checker = new AccessAnnotationChecker();

    @Test
    void editorIsAdminOnly() {
        Principal user = () -> "someone";
        assertTrue(checker.hasAccess(CustomerEditorView.class, user, role -> role.equals("ADMIN")));
        assertFalse(checker.hasAccess(CustomerEditorView.class, user, role -> role.equals("AGENT")));
        assertFalse(checker.hasAccess(CustomerEditorView.class, null, role -> false));   // anonymous
    }

    @Test
    void listIsForAnyAuthenticatedUser() {
        Principal user = () -> "someone";
        assertTrue(checker.hasAccess(CustomerListView.class, user, role -> false));
        assertFalse(checker.hasAccess(CustomerListView.class, null, role -> false));
    }
}

A browserless UI test with @WithMockUser (see Testing) then covers the wiring end to end; keep the checker test for the rule matrix, where it is far cheaper.

Hardening checklist

  • Deny by default. Keep the default of @DenyAll for unannotated views; annotate deliberately.

  • One chain for UI and API. Put the /api/** rules in the same SecurityFilterChain so there is a single place to review.

  • Store passwords hashed (DelegatingPasswordEncoder) and never log credentials or session ids.

  • Session fixation and expiry. Spring Security rotates the session id on login; set server.servlet.session.timeout to an intentional value.

  • Cookies. Set server.servlet.session.cookie.secure=true and same-site=lax (or strict) in production, and serve over HTTPS only.

  • Headers. Keep Spring Security’s default headers, and add a Content Security Policy as shown above, and tighten it step by step while testing against a production build.

  • Never trust the client. Re-validate every value on the server and keep authorisation in services, not in setVisible(false).
