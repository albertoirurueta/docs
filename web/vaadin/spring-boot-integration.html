Spring Boot Integration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Spring Boot is the default backend for a Vaadin application: the starter auto-configures the Vaadin servlet, makes views injectable, and adds Vaadin-aware bean scopes. This page follows the Spring integration guide. For SQL itself, see the SQL Reference.

The starter

vaadin-spring-boot-starter (pulled in by every generated project) registers the VaadinServlet, scans your packages for @Route views, and enables the scopes below:

<dependency>
  <groupId>com.vaadin</groupId>
  <artifactId>vaadin-spring-boot-starter</artifactId>
</dependency>

Limit the route scan for faster startup:

vaadin.allowed-packages=com.example.views,com.example.security

Beans and injection

Any @Component can be injected into a view through its constructor — Flow instantiates views through the Spring context. @SpringComponent is a thin alias that also plays nicely with the Vaadin scopes:

@Route("customers")
public class CustomerListView extends VerticalLayout {

    public CustomerListView(CustomerService service) {   // injected
        Grid<Customer> grid = new Grid<>(Customer.class);
        grid.setItems(service.findAll());
        add(grid);
    }
}

Vaadin bean scopes

Beyond singleton and prototype, the starter adds scopes tied to the Vaadin runtime:

Scope One instance per…

@VaadinSessionScope

user session (all that user’s tabs share it)

@UIScope

UI — i.e. per browser tab / window

@RouteScope + @RouteScopeOwner(View.class)

active route target; discarded on navigation away

 
@SpringComponent
@UIScope
public class ShoppingCart {          // one cart per tab
    private final List<LineItem> items = new ArrayList<>();
    // ...
}

A CRUD over Spring Data JPA

@Entity
public class Customer {
    @Id @GeneratedValue Long id;
    String name;
    String email;
    // getters / setters
}

public interface CustomerRepository extends JpaRepository<Customer, Long> { }

@Service
public class CustomerService {
    private final CustomerRepository repo;
    public CustomerService(CustomerRepository repo) { this.repo = repo; }

    public List<Customer> findAll() { return repo.findAll(); }
    @Transactional public Customer save(Customer c) { return repo.save(c); }
    @Transactional public void delete(Customer c) { repo.delete(c); }
}

@Route("customers")
public class CustomerCrudView extends VerticalLayout {

    private final Grid<Customer> grid = new Grid<>(Customer.class);
    private final Binder<Customer> binder = new Binder<>(Customer.class);
    private final TextField name = new TextField("Name");      // a field, so bindInstanceFields finds it
    private final CustomerService service;

    public CustomerCrudView(CustomerService service) {
        this.service = service;
        grid.setItems(service.findAll());
        grid.asSingleSelect().addValueChangeListener(e -> edit(e.getValue()));

        binder.bindInstanceFields(this);             // binds `name` to Customer.name
        Button save = new Button("Save", e -> {
            service.save(binder.getBean());
            grid.setItems(service.findAll());
        });
        add(grid, name, save);
        edit(null);                                  // start with an empty, bound bean
    }

    private void edit(Customer c) {
        binder.setBean(c != null ? c : new Customer());
    }
}

For lazy loading and the transaction boundary, see Data Persistence.

Spring events

Inject ApplicationEventPublisher to fire domain events; a @EventListener bean (or another view via a shared service) reacts. Combined with server push (Server Push) this notifies other users' open UIs.

Spring MVC and non-Boot Spring

Vaadin routes and Spring @RestController / @Controller mappings coexist under different URL paths in the same application — see REST and Services. In a plain Spring (non-Boot) WebApplication, add @EnableVaadin("com.example") to a @Configuration class instead of relying on the starter’s auto-configuration.

What Spring instantiates, and when

Flow asks the Spring context to create every @Route view, so views are beans, with two properties that surprise newcomers. A view is prototype-like: a new instance is created per navigation target and per UI, never shared between users. And a view is created on the request that navigates to it, so any scoped bean it injects must be resolvable at that moment. The Vaadin scopes tie a bean’s life to a runtime object:

flowchart TD ctx["Spring ApplicationContext
singleton beans: services, repositories"] --> sess["VaadinSession
@VaadinSessionScope"] sess --> ui["UI (one per browser tab)
@UIScope"] ui --> route["active route target
@RouteScope + @RouteScopeOwner"] ui --> view["view instances
created per navigation"] route --> view

  • Injecting a narrower scope into a wider one (a @UIScope bean into a singleton service) does not work: the singleton is created once, before any UI exists. Keep UI-scoped state in views and UI-scoped beans, and pass it to singletons as method arguments.

  • A @UIScope bean is discarded when its UI closes, which happens when the tab closes or the session times out; there is no explicit "tab closed" callback besides @PreDestroy and DetachEvent.

  • A bean in a session or UI scope is stored in the HttpSession, so it must be Serializable if sessions are persisted or replicated (see Production and Deployment).

Worked example: events from a transaction to every open screen

The CRUD view above refreshes its own grid, but a second user’s screen shows stale data. Spring events plus the push techniques from Server Push close the gap. The design has four parts: the service publishes a domain event; a singleton bridge listens for it after the transaction commits; each attached view registers a callback with the bridge; and the callback hops into the UI with ui.access(...).

public record CustomerSaved(Long customerId, String name) { }

@Service
public class CustomerCommands {
    private final CustomerRepository repo;
    private final ApplicationEventPublisher events;

    public CustomerCommands(CustomerRepository repo, ApplicationEventPublisher events) {
        this.repo = repo;
        this.events = events;
    }

    @Transactional
    public Customer save(Customer c) {
        Customer saved = repo.save(c);
        events.publishEvent(new CustomerSaved(saved.getId(), saved.getName()));
        return saved;
    }
}

/** Singleton bridge: Spring events in, per-UI callbacks out. */
@Component
public class CustomerChangeBroadcaster {
    private final Set<Consumer<CustomerSaved>> listeners = new CopyOnWriteArraySet<>();

    public Registration register(Consumer<CustomerSaved> listener) {
        listeners.add(listener);
        return () -> listeners.remove(listener);
    }

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    void on(CustomerSaved event) {
        listeners.forEach(l -> l.accept(event));
    }
}

@TransactionalEventListener(phase = AFTER_COMMIT) is the important detail: a plain @EventListener would run inside the publisher’s transaction, so a view could re-read the table before the new row is visible and show the old data. With AFTER_COMMIT the listeners run only for committed changes and are skipped on rollback.

The view registers on attach and unregisters on detach. It also injects a @UIScope bean, to show a per-tab state holder next to the singleton bridge:

@SpringComponent
@UIScope
public class ShoppingCart implements Serializable {          // one cart per browser tab
    private final List<String> lines = new ArrayList<>();
    void add(String sku) { lines.add(sku); }
    int size() { return lines.size(); }
}

@Route("customers-live")
@PermitAll
public class LiveCustomerListView extends VerticalLayout {

    private final CustomerService service;
    private final CustomerChangeBroadcaster broadcaster;
    private final Grid<Customer> grid = new Grid<>(Customer.class);
    private Registration registration;

    public LiveCustomerListView(CustomerService service, CustomerChangeBroadcaster broadcaster,
                                ShoppingCart cart) {
        this.service = service;
        this.broadcaster = broadcaster;
        add(grid, new Button("Add to cart", e -> {
            cart.add("sku-1");
            Notification.show("Items in this tab's cart: " + cart.size());
        }));
        grid.setItems(service.findAll());
    }

    @Override
    protected void onAttach(AttachEvent event) {
        UI ui = event.getUI();
        registration = broadcaster.register(saved -> ui.access(() -> grid.setItems(service.findAll())));
    }

    @Override
    protected void onDetach(DetachEvent event) {
        registration.remove();
    }
}

The listener is called on the thread that committed, which is typically a request thread of another user, so ui.access is not optional. The singleton never holds a Component, only a lambda that captures the UI, and the onDetach removal is what prevents a leak of closed UIs.

Spring Security and the UI thread

Spring stores the authenticated user in a thread-bound SecurityContext. Flow populates it for the request thread, so SecurityContextHolder and @PreAuthorize work inside a view’s listeners. Work that you hand to another thread — a @Async method, an executor task, a ui.access callback triggered from a broadcaster — does not inherit it. The pattern is to read what you need (the user name, a tenant id) on the request thread and pass it in explicitly, or to use Spring’s DelegatingSecurityContextExecutor when a service call needs the full context. See Security.
