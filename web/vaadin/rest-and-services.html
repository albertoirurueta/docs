REST and Services

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A Vaadin UI talks to the server through Vaadin’s own channel, so it needs no REST API for itself. REST still matters at the edges: exposing data to other clients, and consuming third-party APIs. This page follows the REST API guide and Business Logic.

A service layer

Put domain logic in @Service beans, not in views. A view is a thin adapter: gather input, call a service, render the result. The same service then backs a Flow view, a Hilla endpoint (Hilla and React Views), a REST controller, and a scheduled job — one implementation, many entry points.

@Service
public class InvoiceService {
    @Transactional
    public Invoice issue(IssueInvoiceCommand command) { /* ... */ }
    public List<Invoice> outstanding() { /* ... */ }
}

Exposing REST alongside Flow

A Spring @RestController and Flow routes live in the same application under different paths — Flow serves the UI, the controller serves /api/**:

@RestController
@RequestMapping("/api/invoices")
public class InvoiceController {

    private final InvoiceService service;
    public InvoiceController(InvoiceService service) { this.service = service; }

    @GetMapping
    public List<Invoice> outstanding() { return service.outstanding(); }

    @PostMapping
    public ResponseEntity<Invoice> issue(@RequestBody @Valid IssueInvoiceCommand cmd) {
        return ResponseEntity.status(HttpStatus.CREATED).body(service.issue(cmd));
    }
}

Secure /api/** in the same SecurityFilterChain as the Vaadin routes — see Security. If a browser client on another origin will call this API, configure CORS deliberately; What is CORS? explains the exchange.

Calling an external API from a view

Do the call on a background thread, then push the result with UI.access(...) so the UI thread is never blocked (Server Push):

private final RestClient rest = RestClient.create("https://api.example.com");

private void loadRates() {
    UI ui = UI.getCurrent();
    executor.execute(() -> {
        Rates rates = rest.get().uri("/rates").retrieve().body(Rates.class);
        ui.access(() -> {
            table.setItems(rates.entries());
            spinner.setVisible(false);
        });
    });
}

Use WebClient where you want reactive streaming, RestClient (or the older RestTemplate) for a plain blocking call. Keep the base URL and credentials in configuration, not in the view.

Endpoint or REST?

Use When

Hilla @BrowserCallable

The consumer is your own Hilla / React frontend — you get a generated, type-safe client and shared validation with no API contract to hand-maintain.

REST @RestController

The consumer is a third party, a mobile app, another service, or anything that needs a stable, documented HTTP contract (OpenAPI, versioned paths).

Where each kind of caller enters

All of the ways into the application should be thin adapters over the same service layer. The service owns transactions and business rules; the adapters own transport concerns (HTTP status codes, Flow components, JSON shapes):

flowchart LR flow["Flow view
(Java components)"] --> svc hilla["Hilla endpoint
@BrowserCallable"] --> svc rest["REST controller
/api/**"] --> svc job["scheduled job"] --> svc svc["Service layer
@Service + @Transactional"] --> repo["Repositories"] repo --> db[("Database")] svc --> ext["External API gateway
RestClient"]

The practical rule is that entities do not cross the boundary. A view may bind an entity to a Binder, but a REST or Hilla adapter should expose purpose-built records, so that renaming a column does not silently change a public contract.

Worked example: an invoice API

The example gives the invoice service a REST face with validation, a 201 Created response with a Location header, and errors rendered as RFC 9457 problem documents (ProblemDetail) instead of stack traces. The command and result types are plain records:

public record IssueInvoiceCommand(@NotBlank String customer, @DecimalMin("0.01") BigDecimal amount) { }

public record InvoiceDto(long id, String customer, BigDecimal amount) { }

@RestController
@RequestMapping("/api/invoices")
class InvoiceApi {
    private final InvoiceService service;
    InvoiceApi(InvoiceService service) { this.service = service; }

    @GetMapping
    List<InvoiceDto> outstanding() { return service.outstanding(); }

    @GetMapping("/{id}")
    InvoiceDto get(@PathVariable long id) { return service.get(id); }

    @PostMapping
    ResponseEntity<InvoiceDto> issue(@RequestBody @Valid IssueInvoiceCommand cmd) {
        InvoiceDto created = service.issue(cmd);
        return ResponseEntity.created(URI.create("/api/invoices/" + created.id())).body(created);
    }
}

@RestControllerAdvice(basePackageClasses = InvoiceApi.class)
class ApiErrors {
    @ExceptionHandler(NoSuchElementException.class)
    ProblemDetail notFound(NoSuchElementException e) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
        problem.setTitle("Not found");
        return problem;
    }
}

@RestControllerAdvice(basePackageClasses = ...) limits the handler to the API package, so it cannot change how exceptions from Flow views are reported. A request with a blank customer or a zero amount is rejected with 400 before the service is called, and an unknown id yields a 404 whose body carries title and detail.

The controller is easy to test without starting a server, using MockMvc in standalone mode:

@Test
void apiCreatesAndReportsNotFoundAsProblemDetail() throws Exception {
    LocalValidatorFactoryBean validator = new LocalValidatorFactoryBean();
    validator.afterPropertiesSet();
    MockMvc mvc = MockMvcBuilders.standaloneSetup(new InvoiceApi(new InvoiceService()))
            .setControllerAdvice(new ApiErrors()).setValidator(validator).build();

    mvc.perform(post("/api/invoices").contentType(MediaType.APPLICATION_JSON)
                    .content("{\"customer\":\"Ada\",\"amount\":12.50}"))
            .andExpect(status().isCreated())
            .andExpect(header().string("Location", "/api/invoices/1"));
    mvc.perform(post("/api/invoices").contentType(MediaType.APPLICATION_JSON)
                    .content("{\"customer\":\"\",\"amount\":0}"))
            .andExpect(status().isBadRequest());
    mvc.perform(get("/api/invoices/99"))
            .andExpect(status().isNotFound())
            .andExpect(jsonPath("$.title").value("Not found"));
}

Worked example: a resilient external API call

A call to a third-party service is the least reliable thing a view does, so three defences belong around it: timeouts (a hung API must not hold a thread for ever), an executor that is not the request thread, and an error path that reaches the user. The gateway wraps the client and puts the timeouts in one place:

@Configuration
class RatesClientConfig {
    @Bean
    RestClient ratesClient(RestClient.Builder builder) {
        HttpClient http = HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(2)).build();
        JdkClientHttpRequestFactory factory = new JdkClientHttpRequestFactory(http);
        factory.setReadTimeout(Duration.ofSeconds(5));
        return builder.baseUrl("https://api.example.com").requestFactory(factory).build();
    }
}

@Service
class RatesGateway {
    private final RestClient rest;
    RatesGateway(RestClient ratesClient) { this.rest = ratesClient; }

    Rates latest() {
        return rest.get().uri("/rates").retrieve().body(Rates.class);
    }
}

public record Rates(Map<String, BigDecimal> entries) { }

The view runs the gateway on Vaadin’s task executor and handles both outcomes inside one ui.access block, so the spinner always disappears:

@Route("rates")
@AnonymousAllowed
public class RatesView extends VerticalLayout {

    private final Grid<Map.Entry<String, BigDecimal>> table = new Grid<>();
    private final ProgressBar spinner = new ProgressBar();

    public RatesView(RatesGateway gateway, @VaadinTaskExecutor Executor executor) {
        spinner.setIndeterminate(true);
        table.addColumn(Map.Entry::getKey).setHeader("Currency");
        table.addColumn(Map.Entry::getValue).setHeader("Rate");
        add(spinner, table);

        UI ui = UI.getCurrent();                          // capture on the request thread
        CompletableFuture.supplyAsync(gateway::latest, executor)
                .whenComplete((rates, error) -> ui.access(() -> {
                    spinner.setVisible(false);
                    if (error != null) {
                        Notification.show("Rates unavailable")
                                .addThemeVariants(NotificationVariant.LUMO_ERROR);
                    } else {
                        table.setItems(rates.entries().entrySet());
                    }
                }));
    }
}

The gateway is tested in isolation by binding Spring’s MockRestServiceServer to the client builder, which replaces the network with a scripted response:

@Test
void gatewayParsesRates() {
    RestClient.Builder builder = RestClient.builder().baseUrl("https://api.example.com");
    MockRestServiceServer server = MockRestServiceServer.bindTo(builder).build();
    server.expect(requestTo("https://api.example.com/rates"))
            .andRespond(withSuccess("{\"entries\":{\"USD\":1.08}}", MediaType.APPLICATION_JSON));

    Rates rates = new RatesGateway(builder.build()).latest();

    assertEquals(1, rates.entries().size());
    server.verify();
}

Extend the sketch for production with a retry for idempotent GET requests and a circuit breaker (Resilience4j or Spring Retry), and cache the result when the data changes slowly, so that opening a view does not call the API every time.
