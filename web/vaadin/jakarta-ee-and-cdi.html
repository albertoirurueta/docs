Jakarta EE and CDI

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Vaadin Flow runs on any Servlet 6 (Jakarta EE 10) container. On a full Jakarta EE server the vaadin-cdi add-on gives views CDI injection and adds CDI-aware scopes, mirroring what the Spring starter does. This page follows the CDI integration guide. For the Spring equivalent, see Spring Boot Integration.

The add-on and packaging

<dependency>
  <groupId>com.vaadin</groupId>
  <artifactId>vaadin-cdi</artifactId>
</dependency>

<packaging>war</packaging>

A beans.xml under src/main/webapp/WEB-INF (or src/main/resources/META-INF) activates CDI. Build with mvn package and deploy the WAR to WildFly, Open Liberty, Payara, GlassFish or TomEE. No web.xml is needed — the add-on registers the Vaadin servlet.

Injection and events

@Route("customers")
public class CustomerListView extends VerticalLayout {

    @Inject
    public CustomerListView(CustomerService service, Event<CustomerSelected> selected) {
        Grid<Customer> grid = new Grid<>(Customer.class);
        grid.setItems(service.findAll());
        grid.asSingleSelect().addValueChangeListener(e ->
                selected.fire(new CustomerSelected(e.getValue())));
        add(grid);
    }
}

@ApplicationScoped
public class AuditListener {
    void onSelected(@Observes CustomerSelected event) { /* ... */ }
}

A JPA CRUD

With a container-managed EntityManager:

@Stateless
public class CustomerRepository {

    @PersistenceContext
    EntityManager em;

    public List<Customer> findAll() {
        return em.createQuery("select c from Customer c", Customer.class).getResultList();
    }

    public Customer save(Customer c) {
        return c.getId() == null ? persist(c) : em.merge(c);
    }

    private Customer persist(Customer c) { em.persist(c); return c; }
}

The view wires this to a Grid and a Binder exactly as in the Spring example; see Data Persistence for lazy loading and transactions, and the SQL Reference for the queries.

Legacy integrations

Vaadin 7’s portlet (Liferay / GateIn) and OSGi deployment models still exist as separate add-ons (vaadin-portlet, vaadin-osgi-integration) for maintaining older systems, but a new application should target a plain Servlet container or Spring Boot. They are not covered further here.

Scope lifetimes

Choosing a scope is choosing who shares the instance and when it dies. The Vaadin scopes nest inside each other, so a bean can safely depend on a bean of a wider scope but not the other way round:

flowchart TD svc["VaadinService
@VaadinServiceScoped
one per application"] --> ses["VaadinSession
@VaadinSessionScoped
one per logged-in user"] ses --> ui1["UI (browser tab 1)
@NormalUIScoped"] ses --> ui2["UI (browser tab 2)
@NormalUIScoped"] ui1 --> route1["active route target
@RouteScoped + @RouteScopeOwner"] ui2 --> route2["active route target
@RouteScoped + @RouteScopeOwner"]

  • A @VaadinSessionScoped bean such as user preferences is visible to every tab of that user, and is lost when the session ends.

  • A @NormalUIScoped bean is per tab: two tabs of the same user get different instances. It is the right home for the state of a workspace that must not leak between windows.

  • A @RouteScoped bean lives while its owner route target is on screen and is destroyed when the user navigates away, which makes it a natural container for wizard state.

  • Application-wide @ApplicationScoped beans are shared by all users, so they must be thread-safe and must not hold a UI or Component.

Scoped beans that are kept in the session must be Serializable, because the servlet container may passivate or replicate the session (see Production and Deployment). The pseudo-scoped @UIScoped variant is cheaper (no client proxy) but cannot be injected into a bean of a wider scope; prefer @NormalUIScoped unless you have measured a reason.

@VaadinSessionScoped
public class UserPreferences implements Serializable {
    String theme = "light";                       // shared by all tabs of one user
}

@NormalUIScoped
public class TabState implements Serializable {
    final List<String> openDocuments = new ArrayList<>();   // private to one tab
}

@RouteScoped
@RouteScopeOwner(CustomerListView.class)
public class ListFilter implements Serializable {
    String text = "";                             // discarded when the list view is left
}

Worked example: live updates through CDI events

CDI events are the Jakarta EE counterpart of the Spring event bridge in Spring Boot Integration. Two rules shape the design. First, a view is a poor event observer: its lifetime is tied to a UI, and an observer method on a short-lived bean can be called after the UI has gone. Second, fireAsync delivers on a container thread, so the callback must hop back into the UI with ui.access(...) (see Server Push). The solution is a small application-scoped bridge that the views register with while they are attached:

@ApplicationScoped
public class CustomerStore {
    @PersistenceContext EntityManager em;
    @Inject Event<CustomerSaved> saved;

    public List<Customer> findAll() {
        return em.createQuery("select c from Customer c", Customer.class).getResultList();
    }

    @Transactional
    public Customer save(Customer c) {
        Customer merged = em.merge(c);
        saved.fireAsync(new CustomerSaved(merged.getId(), merged.getName()));
        return merged;
    }
}

public record CustomerSaved(Long id, String name) { }

@ApplicationScoped
public class CustomerChanges {
    private final Set<Consumer<CustomerSaved>> listeners = new CopyOnWriteArraySet<>();

    public Registration register(Consumer<CustomerSaved> listener) {
        listeners.add(listener);
        return () -> listeners.remove(listener);
    }

    void onSaved(@ObservesAsync CustomerSaved event) {
        listeners.forEach(l -> l.accept(event));
    }
}

@Route("customers")
@PermitAll
public class CustomerListView extends VerticalLayout {

    @Inject CustomerStore store;
    @Inject CustomerChanges changes;
    private final Grid<Customer> grid = new Grid<>(Customer.class);
    private Registration registration;

    public CustomerListView() { add(grid); }

    @Override
    protected void onAttach(AttachEvent event) {
        grid.setItems(store.findAll());
        UI ui = event.getUI();
        registration = changes.register(e -> ui.access(() -> grid.setItems(store.findAll())));
    }

    @Override
    protected void onDetach(DetachEvent event) {
        registration.remove();                    // a closed tab stops receiving events
    }
}

Two points deserve a closer look. Injection into the view uses fields, because the router creates the view through the CDI container and the no-argument constructor keeps the example short; constructor injection with @Inject works equally well. And the event is fired from inside the @Transactional method, so an asynchronous observer may run before the transaction commits; if observers must see the committed row, fire from a @Observes(during = TransactionPhase.AFTER_SUCCESS) observer, or re-read inside the observer, as the view does here with store.findAll() after the ui.access hop.

Packaging checklist for a WAR

A WAR that starts but renders a blank page is almost always one of four mistakes:

  1. beans.xml missing or with bean-discovery-mode="none". Views are not discovered and routes are empty.

  2. Frontend bundle not built. The production profile must run build-frontend; see Production and Deployment.

  3. Duplicate Servlet API on the classpath. Mark jakarta.jakartaee-api as provided so the server’s own implementation is used.

  4. Context path assumptions. Deploying at /crm instead of / changes asset URLs; use relative paths and let UI.navigate resolve routes, rather than hard-coded absolute URLs.
