Hilla and React Views

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Hilla is the second programming model in Vaadin: the browser UI is written in React and TypeScript, and it calls type-safe endpoints generated from your Java services. The backend, build, theming and security are the same as Flow — one project, two ways to write views. This page follows the Hilla documentation and Add a React View. Hilla was previously called Fusion; the name changed in 2022, the model did not.

Figure 1. Flow and Hilla on one backend

Endpoints

Annotate a Spring service with @BrowserCallable (an alias of @Endpoint) and it becomes callable from the browser. Vaadin generates a TypeScript module with one typed function per public method:

@BrowserCallable
@AnonymousAllowed
public class PersonEndpoint {

    private final PersonRepository repository;

    public PersonEndpoint(PersonRepository repository) {
        this.repository = repository;
    }

    public List<Person> list() {
        return repository.findAll();
    }

    public Person save(@Valid Person person) {
        return repository.save(person);
    }
}
import { PersonEndpoint } from 'Frontend/generated/endpoints';

const people: Person[] = await PersonEndpoint.list();
await PersonEndpoint.save(edited);   // Person is a generated TS type

Bean Validation annotations on the parameters are enforced on the server and surfaced to the client. See Endpoints.

Views and routing

A .tsx file under src/main/frontend/views/ is a route; the path mirrors the folder structure (views/people/list.tsx → /people/list). An exported config object sets the title and menu placement; @vaadin/react-router handles navigation.

// src/main/frontend/views/people.tsx
import { ViewConfig } from '@vaadin/hilla-file-router/types.js';
import { Grid } from '@vaadin/react-components/Grid.js';
import { GridColumn } from '@vaadin/react-components/GridColumn.js';
import { useEffect, useState } from 'react';
import { PersonEndpoint } from 'Frontend/generated/endpoints';
import type Person from 'Frontend/generated/com/example/Person';

export const config: ViewConfig = { title: 'People', menu: { order: 1 } };

export default function PeopleView() {
  const [people, setPeople] = useState<Person[]>([]);
  useEffect(() => { PersonEndpoint.list().then(setPeople); }, []);
  return (
    <Grid items={people}>
      <GridColumn path="firstName" />
      <GridColumn path="lastName" />
    </Grid>
  );
}

See Routing and Routing.

Forms

useForm binds a generated model to fields, runs the same validators as the server, and exposes submit:

import { useForm } from '@vaadin/hilla-react-form';
import PersonModel from 'Frontend/generated/com/example/PersonModel';
import { TextField } from '@vaadin/react-components/TextField.js';
import { Button } from '@vaadin/react-components/Button.js';

function PersonForm() {
  const { model, field, submit, invalid } = useForm(PersonModel, {
    onSubmit: async (person) => { await PersonEndpoint.save(person); },
  });
  return (
    <>
      <TextField label="First name" {...field(model.firstName)} />
      <TextField label="Last name" {...field(model.lastName)} />
      <Button theme="primary" disabled={invalid} onClick={submit}>Save</Button>
    </>
  );
}

See Binding Data to Forms.

Security

Every endpoint is denied by default. Open it with a class- or method-level annotation, exactly as on the Flow side (Security):

@BrowserCallable
@RolesAllowed("ADMIN")
public class AdminEndpoint {
    @AnonymousAllowed
    public String publicPing() { return "ok"; }
}

On the client, useAuth() exposes the authenticated user, roles and login / logout, and route access is checked from each view’s config.rolesAllowed. See Security.

From a Java class to a typed React call

Hilla’s central trick is code generation: it reads your endpoint classes and the types they use and writes the TypeScript that calls them, so a rename or a changed signature in Java becomes a compile error in the React view instead of a runtime surprise.

flowchart LR java["Java: CustomerEndpoint and the Customer record"] -->|"build or dev server scans @BrowserCallable"| gen["Generated TypeScript: endpoints, Customer interface, CustomerModel"] gen --> view["React view imports the client function and the form model"] view -->|"typed call"| post["HTTP POST to the endpoint"] post --> java java -->|"Bean Validation and access rules run here"| post

What is generated, for the record below, is the Customer TypeScript interface (what you pass around), a CustomerModel class that carries the validation rules (what useForm binds to) and one function per public endpoint method.

Nullability

By default every generated field and return type is nullable (string | undefined), because Java gives no guarantee otherwise. Mark what is never null with @Nonnull — on a return type, on a type argument inside a collection, or on a record component — and the generated types become non-optional, which saves a null check on every use:

public record Customer(
        Long id,                                            // null until the first save
        @NotBlank @Size(max = 80) String name,
        @NotBlank @Email String email) { }

@BrowserCallable
@PermitAll
public class CustomerEndpoint {

    public @Nonnull List<@Nonnull Customer> search(String term) { /* ... */ }

    public @Nonnull Customer save(@Valid Customer customer) { /* ... */ }
}

With @Nonnull on both levels, search is generated as returning Customer[], so the view can map over it without ?. or !. A search for ada over two stored customers returns just Ada, an empty term returns both, and a customer with a blank name and a malformed e-mail fails the two constraints on name and email before save ever runs.

Worked example: customer search with a validated form

The view combines everything above — a typed search, a grid, and a form whose rules come from the Java record. The form is read from the selected row, saved through the endpoint and refreshed afterwards.

// src/main/frontend/views/customers.tsx
import { useEffect, useState } from 'react';
import { useForm } from '@vaadin/hilla-react-form';
import { Button } from '@vaadin/react-components/Button.js';
import { EmailField } from '@vaadin/react-components/EmailField.js';
import { Grid } from '@vaadin/react-components/Grid.js';
import { GridColumn } from '@vaadin/react-components/GridColumn.js';
import { TextField } from '@vaadin/react-components/TextField.js';
import { CustomerEndpoint } from 'Frontend/generated/endpoints';
import type Customer from 'Frontend/generated/com/example/Customer';
import CustomerModel from 'Frontend/generated/com/example/CustomerModel';

export default function CustomersView() {
  const [customers, setCustomers] = useState<Customer[]>([]);
  const [term, setTerm] = useState('');

  const { model, field, submit, read, clear, dirty, invalid } = useForm(CustomerModel, {
    onSubmit: async (customer) => {
      await CustomerEndpoint.save(customer);      // server-side @Valid failures land on the fields
      setCustomers(await CustomerEndpoint.search(term));
      clear();
    },
  });

  useEffect(() => {
    CustomerEndpoint.search(term).then(setCustomers);
  }, [term]);

  return (
    <div>
      <TextField label="Search" onValueChanged={(e) => setTerm(e.detail.value)} />
      <Grid items={customers} onActiveItemChanged={(e) => e.detail.value && read(e.detail.value)}>
        <GridColumn path="name" />
        <GridColumn path="email" />
      </Grid>
      <TextField label="Name" {...field(model.name)} />
      <EmailField label="Email" {...field(model.email)} />
      <Button theme="primary" disabled={!dirty || invalid} onClick={submit}>Save</Button>
    </div>
  );
}

The flow mirrors the Flow Binder pages: read(item) loads a bean (like readBean), dirty and invalid drive the Save button (like the status listener), and submit validates and calls onSubmit (like writeBeanIfValid followed by a service call). The difference is where the rules live: the @NotBlank, @Size and @Email annotations on the Java record are copied into CustomerModel, so the browser validates instantly and the server validates again on save — one definition, enforced on both sides. The endpoint is annotated @PermitAll, so only authenticated users can call it; see Security.

Reactive endpoints and signals

A method returning Flux<T> streams values to the client as an async iterable — for live prices, logs or progress:

public Flux<Integer> counter() {
    return Flux.interval(Duration.ofSeconds(1)).map(Long::intValue);
}
for await (const n of CounterEndpoint.counter()) { setCount(n); }

Full-stack signals go further: a NumberSignal / ValueSignal shared between the server and every connected client stays in sync automatically, giving collaborative state with no manual wiring. See Reactive Endpoints and Full-Stack Signals.

Mixing Flow and Hilla, and choosing

One application can serve Flow routes and Hilla routes side by side — a Flow admin area and a Hilla customer portal, for instance — sharing the security config, the theme and the domain layer.

Choose When

Flow

The team is Java-first; the UI is forms-and-tables heavy; you want data binding and Grid lazy loading with no REST layer to design.

Hilla

The team knows React; the UI is highly interactive or custom; you want the browser-side ecosystem (Styling and UI Libraries) with a type-safe Java backend instead of hand-written REST.
