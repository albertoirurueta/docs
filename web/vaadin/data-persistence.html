Data Persistence

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A Vaadin view holds no persistence code of its own — it calls a service, which uses whatever data-access stack the project already has. This page follows the Persistence guide and shows the two Vaadin-specific concerns: feeding a lazy Grid from the database, and the transaction boundary. For SQL and schema design, see the SQL Reference; for document stores, the MongoDB Reference.

Choosing a stack

Option Fits

Spring Data JPA

The default. Repositories, derived queries, Pageable — least code for CRUD.

jOOQ

Typed SQL DSL generated from the schema; full control over queries, no ORM surprises.

Flyway

Versioned schema migrations; runs on startup, independent of the query stack.

Flyway migrations live under src/main/resources/db/migration:

-- V1__create_customer.sql
CREATE TABLE customer (
    id      BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    version BIGINT       NOT NULL DEFAULT 0,      -- JPA @Version column, see optimistic locking
    name    VARCHAR(200) NOT NULL,
    email   VARCHAR(320) NOT NULL UNIQUE
);

Further migrations are new files, never edits of an applied one — V2__seed_customers.sql can insert sample rows, and Flyway runs them in version order at start-up. With spring.jpa.hibernate.ddl-auto=validate, Hibernate then only checks that the entity matches the migrated schema, so a drifting column fails fast at start-up instead of silently diverging.

A lazy Grid over a repository

Extend PagingAndSortingRepository (or JpaRepository), then translate the Grid’s Query into a Spring Pageable. VaadinSpringDataHelpers does the sort mapping:

@Entity
public class Customer {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Version
    private long version;
    private String name;
    private String email;
    // constructors, getters, setters
}

public interface CustomerRepository extends JpaRepository<Customer, Long> {

    Slice<Customer> findByNameContainingIgnoreCase(String name, Pageable pageable);

    long countByNameContainingIgnoreCase(String name);
}

@Service
public class CustomerService {

    private final CustomerRepository repo;

    public CustomerService(CustomerRepository repo) { this.repo = repo; }

    @Transactional(readOnly = true)
    public List<Customer> list(Pageable pageable, String filter) {
        return repo.findByNameContainingIgnoreCase(normalise(filter), pageable).getContent();
    }

    @Transactional(readOnly = true)
    public int count(String filter) {
        return (int) repo.countByNameContainingIgnoreCase(normalise(filter));
    }

    private static String normalise(String filter) { return filter == null ? "" : filter.trim(); }
}

// in the view
grid.setItems(
    query -> service.list(
            VaadinSpringDataHelpers.toSpringPageRequest(query),
            filterField.getValue()).stream(),
    query -> service.count(filterField.getValue()));

The repository returns a Slice for the page (which skips the extra count query a Page would run) and the grid’s count callback calls a dedicated count method, so a scroll costs one page query and the total is computed separately and only when the grid asks for it.

Now paging, sorting and filtering all execute in the database; the server never holds more than one page. See The Grid Component for the Grid side and Spring Data JPA.

From a grid Query to a Spring Pageable

The grid hands the fetch callback a Query — an offset, a limit and the sort orders of the clicked columns. VaadinSpringDataHelpers.toSpringPageRequest(query) converts it into the PageRequest Spring Data expects, and toSpringDataSort(query) produces just the Sort:

Query<Customer, String> query = new Query<>(2, 2,
        List.of(new QuerySortOrder("name", SortDirection.DESCENDING)), null, null);

PageRequest request = VaadinSpringDataHelpers.toSpringPageRequest(query);
// Page request [number: 1, size 2, sort: name: DESC]

Offset 2 with limit 2 is the second page of two rows, so Spring’s page number is 1. The sort property is whatever setSortProperty named on the column, which therefore has to be an entity property name (name, not a column header). When the offset is not a multiple of the limit the helper widens the page so that it still starts at the requested row: offset 3 with limit 2 becomes [number: 1, size 3]. The repository may then return more rows than query.getLimit(), so cap the stream in the callback with .limit(query.getLimit()) when your own code depends on the exact count.

Db-->>Repo: one page of rows Repo-->>Service: Slice of Customer Service-->>View: List of Customer View-->>Grid: Stream of Customer

Checked against an in-memory H2 database with six seeded customers: a page of two rows sorted by name descending, starting at offset 2, returns Grace Hopper and Barbara Liskov; counting with the filter a agrees with the size of the filtered list; and the filter LIN finds one customer, because the derived query is case-insensitive.

jOOQ

public List<Customer> search(String term, int offset, int limit) {
    return dsl.selectFrom(CUSTOMER)
              .where(CUSTOMER.NAME.likeIgnoreCase("%" + term + "%"))
              .orderBy(CUSTOMER.NAME)
              .offset(offset).limit(limit)
              .fetchInto(Customer.class);
}

The same fetch(offset, limit) / count() pair feeds grid.setItems(...).

The transaction boundary

A Flow view runs outside any transaction. Keep persistence work inside @Transactional service methods and return fully-initialised objects (or DTOs) — touching a lazy JPA association from the view thread throws LazyInitializationException:

@Transactional(readOnly = true)
public CustomerDetails load(Long id) {
    Customer c = repo.findById(id).orElseThrow();
    c.getOrders().size();                 // force-initialise inside the transaction
    return CustomerDetails.from(c);
}

Prefer projections / DTOs over spring.jpa.open-in-view=true, which keeps a session open for the whole request and hides the problem. A write goes through its own @Transactional method; concurrent edits are handled with a JPA @Version column (see Forms, CRUD and Master-Detail).

Projections for read-only views

A grid column rarely needs the whole entity, and a projection avoids loading (and lazily initialising) everything else. An interface projection lists the properties wanted and Spring Data selects only those columns:

public interface CustomerSummary {
    Long getId();
    String getName();
}

public interface CustomerRepository extends JpaRepository<Customer, Long> {

    Slice<CustomerSummary> findSummaryByNameContainingIgnoreCase(String name, Pageable pageable);
}

Projections are read-only snapshots: they cannot be saved, and they carry no version. Use them to fill grids and ComboBox lists, and load the full entity (inside a @Transactional service method) only when the user opens one row for editing.

Optimistic locking at the persistence layer

Two users edit the same customer. Both read it at version 0; the first save succeeds and stores version 1; the second still carries version 0 and is rejected with ObjectOptimisticLockingFailureException. Because the @Transactional service method is the transaction boundary, the exception surfaces from the save call itself, where the view can catch it. Note also that save on a detached entity returns a new instance carrying the incremented version while the original keeps the old one:

Customer first = service.list(PageRequest.of(0, 1), "ada").get(0);
Customer second = service.list(PageRequest.of(0, 1), "ada").get(0);   // same row, version 0

first.setName("Ada King");
Customer saved = service.save(first);        // saved.getVersion() == 1, first.getVersion() == 0

second.setName("Ada Byron");
service.save(second);                        // throws ObjectOptimisticLockingFailureException

The UI side of this — telling the user and reloading the record — is in Forms, CRUD and Master-Detail.

Connection settings

Everything the data layer needs lives in application.properties; Vaadin adds nothing here. A development configuration with an in-memory database that Flyway migrates on start looks like this:

spring.datasource.url=jdbc:h2:mem:demo;DB_CLOSE_DELAY=-1
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false

For a real database replace the URL and add spring.datasource.username / spring.datasource.password (from the environment, never from the file). DB_CLOSE_DELAY=-1 keeps the in-memory H2 database alive for the life of the JVM instead of dropping it when the last connection closes.

Refreshing after a write

The Grid does not know the database changed. After a save or delete, refresh the data view:

service.save(edited);
grid.getDataProvider().refreshAll();       // re-fetch visible rows
// or, for an in-place edit:
grid.getDataProvider().refreshItem(edited);
