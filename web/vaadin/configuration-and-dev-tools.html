Configuration and Dev Tools

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Vaadin needs very little configuration to run, and its development mode gives a tight edit-refresh loop. This page follows Configuration and Development mode.

Properties

On Spring Boot, Vaadin reads vaadin.* keys from application.properties:

vaadin.productionMode=false
vaadin.launch-browser=true
vaadin.frontend.hotdeploy=true
vaadin.allowed-packages=com.example.views
vaadin.pnpm.enable=true
vaadin.closeIdleSessions=true
vaadin.heartbeatInterval=300

Outside Spring Boot the same settings are servlet init parameters or -Dvaadin.<key> system properties. The full list is at Configuration properties.

Typed properties and deployment parameters

Two groups of settings exist, and the difference explains why some keys autocomplete in the IDE and others do not. The first group is bound by Spring Boot into typed properties, so the IDE knows their names and defaults:

Key Default Meaning

vaadin.url-mapping

/*

URL pattern the Vaadin servlet is mapped to.

vaadin.launch-browser

false

Open the default browser when the application starts in development mode.

vaadin.launch-browser-delay

30

Seconds to wait for the frontend before launching the browser.

vaadin.frontend.hotdeploy

false

Use the frontend dev server (true) instead of the dev bundle.

vaadin.pnpm.enable / vaadin.bun.enable

false

Install frontend packages with pnpm or bun instead of npm.

vaadin.react.enable

true

Enable the React-based router and shell used by Hilla file routing.

vaadin.allowed-packages / vaadin.blocked-packages

none

Limit which packages are scanned for routes and components; restricting the scan speeds up start-up.

vaadin.exclude-urls

none

Paths the servlet must not handle (for example a REST API).

vaadin.async-supported

true

Whether the servlet is registered with asynchronous support (needed by push).

vaadin.load-on-startup

true

Initialise the servlet at start-up rather than on the first request.

The second group are deployment configuration parameters — productionMode, heartbeatInterval, closeIdleSessions, pushMode, requestTiming, syncIdCheck, maxMessageSuspendTimeout, devmode.liveReload.enabled, devmode.devTools.enabled and others. They are not typed Spring properties, but the Spring integration passes every vaadin.* key from the environment through, so the same line in application.properties, an environment variable or a -D option works.

Profiles for development and production

Spring profiles keep the two configurations apart without code changes. Start the application with --spring.profiles.active=prod (or SPRING_PROFILES_ACTIVE=prod) and the matching file is layered over the defaults:

# application.properties -- shared
vaadin.allowed-packages=com.example

# application-dev.properties
vaadin.launch-browser=true
vaadin.frontend.hotdeploy=true

# application-prod.properties
vaadin.productionMode=true
vaadin.closeIdleSessions=true

Reading the effective configuration

When a setting does not seem to apply, ask the running service instead of guessing. The DeploymentConfiguration exposes the resolved values:

DeploymentConfiguration config = VaadinService.getCurrent().getDeploymentConfiguration();

boolean production = config.isProductionMode();
int heartbeatSeconds = config.getHeartbeatInterval();
boolean closeIdle = config.isCloseIdleSessions();
PushMode push = config.getPushMode();
boolean liveReload = config.isDevModeLiveReloadEnabled();

VaadinService.getCurrent() is only set on a request thread (or inside UI.access), so call it from a view or a listener, not from a static initialiser.

Development mode and the frontend toolchain

In development mode Vaadin serves the frontend either from a pre-compiled dev bundle (the default) or, with vaadin.frontend.hotdeploy=true, from a frontend dev server that compiles TypeScript / CSS on demand and hot-reloads it in the browser; the section below compares the two. Either way it needs Node.js; Vaadin downloads a project-local copy if none is on the PATH. The package manager defaults to npm; enable pnpm (vaadin.pnpm.enable=true) or bun (vaadin.bun.enable=true) for faster, disk-efficient installs.

The generated package.json and vite.config.ts are managed by Vaadin — edit them only through the annotations below, or Vaadin will overwrite your changes.

Dev bundle or dev server

Frontend code has to be compiled before a browser can run it. Development mode offers two ways to do that, chosen by vaadin.frontend.hotdeploy:

  • Dev bundle (false, the default). Vaadin ships a pre-compiled bundle of its own components and reuses it as long as your project’s frontend dependencies and theme are unchanged. Start-up is fast, and no frontend dev server runs. When you add an @NpmPackage or a @JsModule, or edit the theme, the bundle is rebuilt once.

  • Frontend dev server (true). A Vite server compiles each file on demand and pushes changes to the browser, so editing a .tsx or .css file is visible immediately. It costs more memory and a slower first start, and suits teams that write many Hilla views or custom Web Components.

Hot deployment and live reload

  • Frontend changes (anything under src/main/frontend) are pushed to the browser with no restart.

  • Java changes need the class reloaded. Options, fastest first:

    • JRebel or HotswapAgent — reload changed classes in place, no restart.

    • Spring Boot DevTools — restarts the context on a classpath change (add the dependency; Vaadin integrates its live-reload trigger).

    • Plain restart from the IDE.

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-devtools</artifactId>
  <optional>true</optional>
</dependency>

Feature flags

Preview features are gated behind flags in src/main/resources/vaadin-featureflags.properties (or the dev tools window’s Experimental Features tab):

com.vaadin.experimental.exampleFeatureFlag=true

The dev tools window and Copilot

Running in development mode, a small Vaadin logo in the corner opens the dev tools window: build and browser messages, the feature-flag list, and a live-reload indicator. Vaadin Copilot extends it into a visual, AI-assisted editor — select a component in the running app to inspect and edit it, adjust the theme, or scaffold a view — and writes the changes back to source. See Copilot.

Logging and troubleshooting

Most start-up problems show up in the console as one of two kinds. Frontend build failures (a missing package, a TypeScript error) are also shown in the browser by the dev tools window; fix the file and the page reloads. Configuration problems — a view not found, a route ignored — are usually a package outside vaadin.allowed-packages. Raise the logging to see what Vaadin is doing:

logging.level.com.vaadin=DEBUG
logging.level.com.vaadin.flow.server.frontend=INFO

If the frontend state itself seems corrupt, stop the application, delete node_modules and the generated dev bundle folder and start again; Vaadin regenerates both.

Adding frontend dependencies

Do not hand-edit package.json. Declare npm packages and modules with annotations on any component or the shell, and Vaadin adds them to the build:

@NpmPackage(value = "sortablejs", version = "1.15.2")
@JsModule("./drag-reorder.js")
public class ReorderableList extends Component { }

Maven and Gradle

Maven is the default (vaadin-maven-plugin, prepare-frontend + build-frontend goals). Gradle is fully supported through the com.vaadin plugin:

plugins {
    id 'org.springframework.boot' version '3.3.0'
    id 'com.vaadin' version '24.5.0'
}

vaadin {
    productionMode = false
}

The production build is ./gradlew -Pvaadin.productionMode=true bootJar — see Production and Deployment.
