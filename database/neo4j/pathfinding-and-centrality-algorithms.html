Pathfinding and centrality algorithms

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Once a graph is projected into memory (see Graph Data Science Fundamentals), two families of GDS algorithms answer most practical graph questions: pathfinding finds routes between specific nodes, and centrality ranks every node by some notion of importance. Both families share the same stream / write / mutate execution modes; the examples below use stream to return results without persisting them.

Pathfinding algorithms

Pathfinding algorithms need weighted relationships to be meaningful, so this section uses a small :Location / :ROAD road network rather than the :Person / :Movie domain — distances between places map naturally onto relationship weights, which acted-in credits do not. The graph has five Italian cities, five roads and, because A* will need them, a latitude and longitude on every city:

flowchart LR T["Turin"] ---|"140 km"| M["Milan"] T ---|"170 km"| G["Genoa"] M ---|"210 km"| B["Bologna"] G ---|"300 km"| B B ---|"100 km"| F["Florence"]
CREATE (a:Location {name: 'Turin',    latitude: 45.07, longitude: 7.69})
CREATE (b:Location {name: 'Milan',    latitude: 45.46, longitude: 9.19})
CREATE (c:Location {name: 'Genoa',    latitude: 44.41, longitude: 8.93})
CREATE (d:Location {name: 'Bologna',  latitude: 44.49, longitude: 11.34})
CREATE (e:Location {name: 'Florence', latitude: 43.77, longitude: 11.26})
CREATE (a)-[:ROAD {distance: 140}]->(b)
CREATE (a)-[:ROAD {distance: 170}]->(c)
CREATE (b)-[:ROAD {distance: 210}]->(d)
CREATE (c)-[:ROAD {distance: 300}]->(d)
CREATE (d)-[:ROAD {distance: 100}]->(e)

CALL gds.graph.project(
  'roads',
  'Location',
  {ROAD: {orientation: 'UNDIRECTED', properties: 'distance'}},
  {nodeProperties: ['latitude', 'longitude']}
)

Two details of that projection matter. orientation: 'UNDIRECTED' makes every road drivable both ways, which is what a road network means; and the latitude / longitude node properties are projected explicitly, because an algorithm can only read what is in the catalog — without them the A* example below fails.

Dijkstra: single-pair and single-source shortest path

Dijkstra’s algorithm finds the lowest-total-weight path from one source node, either to a single target or to every reachable node, and is the default choice whenever all relationship weights are non-negative (Dijkstra Source-Target).

MATCH (source:Location {name: 'Turin'}), (target:Location {name: 'Florence'})
CALL gds.shortestPath.dijkstra.stream('roads', {
  sourceNode: source,
  targetNode: target,
  relationshipWeightProperty: 'distance'
})
YIELD index, sourceNode, targetNode, totalCost, nodeIds, costs
RETURN
  gds.util.asNode(sourceNode).name AS from,
  gds.util.asNode(targetNode).name AS to,
  totalCost,
  [nodeId IN nodeIds | gds.util.asNode(nodeId).name] AS route
index, from, to, totalCost, route, costs
0, "Turin", "Florence", 450.0, ["Turin", "Milan", "Bologna", "Florence"], [0.0, 140.0, 350.0, 450.0]

costs is the running total at each node of the path, so the Milan leg costs 140, Bologna is reached at 350 and Florence at 450. The alternative through Genoa is 170 + 300 + 100 = 570, which is why it loses.

Dijkstra works by keeping a frontier of nodes ordered by the cheapest known distance from the source. It repeatedly settles the nearest unsettled node and relaxes its neighbors, which is correct only because no weight can be negative — a later edge can never make an already-settled node cheaper. With targetNode set it stops as soon as the target is settled; leaving it out computes the whole shortest-path tree with the single-source variant:

MATCH (source:Location {name: 'Turin'})
CALL gds.allShortestPaths.dijkstra.stream('roads', {
  sourceNode: source,
  relationshipWeightProperty: 'distance'
})
YIELD targetNode, totalCost
RETURN gds.util.asNode(targetNode).name AS to, totalCost
ORDER BY totalCost
to, totalCost
"Turin", 0.0
"Milan", 140.0
"Genoa", 170.0
"Bologna", 350.0
"Florence", 450.0

The stream mode returns paths as node-id lists. To keep a route in the database for later queries, the write mode materializes it as a relationship carrying the cost and the node ids:

MATCH (source:Location {name: 'Turin'}), (target:Location {name: 'Florence'})
CALL gds.shortestPath.dijkstra.write('roads', {
  sourceNode: source, targetNode: target,
  relationshipWeightProperty: 'distance',
  writeRelationshipType: 'ROUTE', writeNodeIds: true, writeCosts: true
})
YIELD relationshipsWritten
RETURN relationshipsWritten;
// 1  -> (:Turin)-[:ROUTE {totalCost: 450.0, nodeIds: [...], costs: [0.0, 140.0, 350.0, 450.0]}]->(:Florence)

A*: shortest path guided by a spatial heuristic

A* refines Dijkstra with a heuristic — typically great-circle distance between latitude/longitude point properties — that steers the search toward the target instead of expanding outward evenly, reaching the same optimal answer while visiting fewer nodes on geographically spread graphs (A* Shortest Path).

MATCH (source:Location {name: 'Turin'}), (target:Location {name: 'Florence'})
CALL gds.shortestPath.astar.stream('roads', {
  sourceNode: source,
  targetNode: target,
  relationshipWeightProperty: 'distance',
  latitudeProperty: 'latitude',
  longitudeProperty: 'longitude'
})
YIELD sourceNode, targetNode, totalCost
RETURN
  gds.util.asNode(sourceNode).name AS from,
  gds.util.asNode(targetNode).name AS to,
  totalCost
from, to, totalCost, route
"Turin", "Florence", 450.0, ["Turin", "Milan", "Bologna", "Florence"]

The answer equals Dijkstra’s, as it must: the heuristic only changes how many nodes are examined, never the result, provided it never overestimates the remaining cost. Great-circle distance is such a heuristic for a road network, because no road is shorter than the straight line. The saving is invisible on five nodes and large on a national road graph, where Dijkstra expands in every direction while A* leans toward the target. A* needs latitudeProperty and longitudeProperty on projected nodes, and a graph whose weights are not distances in the same unit as the heuristic can mislead it.

Yen’s algorithm: k-shortest paths

Yen’s algorithm returns not just the single best path but the k best loopless paths in increasing order of cost — useful whenever the true requirement is a ranked set of alternatives rather than one route, such as offering a traveler a primary route plus fallbacks (Yen’s Algorithm).

MATCH (source:Location {name: 'Turin'}), (target:Location {name: 'Florence'})
CALL gds.shortestPath.yens.stream('roads', {
  sourceNode: source,
  targetNode: target,
  relationshipWeightProperty: 'distance',
  k: 3
})
YIELD index, totalCost, nodeIds
RETURN index, totalCost,
  [nodeId IN nodeIds | gds.util.asNode(nodeId).name] AS route
ORDER BY index
index, totalCost, route
0, 450.0, ["Turin", "Milan", "Bologna", "Florence"]
1, 570.0, ["Turin", "Genoa", "Bologna", "Florence"]

Asking for k: 3 returned only two rows: Yen’s paths are loopless, and this network has exactly two loopless routes from Turin to Florence. The algorithm never pads the answer, so always read the row count rather than assuming k rows. Internally it finds the best path, then repeatedly forbids one edge of an earlier path and re-runs Dijkstra from the deviation point to collect candidate detours.

These three cover the common cases: Dijkstra for a plain weighted shortest path, A* when nodes carry real coordinates worth exploiting, and Yen’s when several ranked alternatives are needed instead of just the best one. All three, and the wider pathfinding family, are indexed at GDS Algorithms.

Centrality algorithms

Centrality algorithms score every node in a projected graph by some notion of "importance" — how connected it is, how much traffic flows through it, or how close it sits to everything else. They run over the whole graph rather than between two chosen nodes. The examples switch to the film graph of Graph Data Science Fundamentals and first turn it into a graph of people: actors who share a film become connected by a CO_STARRED relationship that carries the number of shared films.

MATCH (p1:Person)-[:ACTED_IN]->(:Movie)<-[:ACTED_IN]-(p2:Person)
WHERE id(p1) < id(p2)
WITH p1, p2, count(*) AS movies
MERGE (p1)-[r:CO_STARRED]->(p2)
SET r.movies = movies;

CALL gds.graph.project(
  'people',
  'Person',
  {CO_STARRED: {orientation: 'UNDIRECTED', properties: 'movies'}}
)
flowchart LR Ada ---|2| Bo Bo ---|1| Cy Bo ---|1| Flo Cy ---|1| Flo Cy ---|1| Di Cy ---|1| Ed Di ---|1| Ed

Projecting only the Person label would silently produce a graph without any relationships if the data kept actors and films apart, because every ACTED_IN ends on a Movie; materializing CO_STARRED (or building a Cypher projection, see Graph Data Science Fundamentals) avoids that trap. Ada and Bo share two films (Nine Lives and Red Horizon), so their edge has weight 2; every other pair shares one.

Algorithm What it measures Typical use

Degree

How many relationships a node has (in, out, or both).

Quick popularity/activity signal; a cheap first pass before running heavier measures.

PageRank

How much influence flows into a node, weighted by the influence of the nodes pointing at it.

Ranking overall importance in a directed graph, e.g. influential accounts or authoritative pages.

Betweenness

How often a node sits on the shortest path between other pairs of nodes.

Finding bridges/brokers whose removal would fragment the graph or lengthen many routes.

Closeness

How short a node’s paths are, on average, to every other node.

Finding nodes that can reach the rest of the graph fastest, e.g. a good broadcast or facility location.

Eigenvector

Like PageRank, but a node’s score depends purely on the score of its neighbors, with no damping/random-jump term.

Ranking importance in graphs without a natural directed "vote", e.g. undirected social or collaboration graphs.

Degree centrality

CALL gds.degree.stream('people')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).name AS person, score
ORDER BY score DESC, person
person, score
"Cy", 4.0
"Bo", 3.0
"Di", 2.0
"Ed", 2.0
"Flo", 2.0
"Ada", 1.0

Cy has four co-stars and tops the list. Adding relationshipWeightProperty: 'movies' sums the weights instead of counting edges, and the order changes: Bo and Cy tie at 4.0 because Bo’s edge to Ada counts twice. Degree is the cheapest centrality to compute and a useful sanity check on a projection, but it only sees immediate neighbors, which is what the remaining measures improve on.

PageRank and Personalized PageRank

Plain PageRank scores every node from the whole graph’s link structure (PageRank). It models a random surfer who follows a relationship with probability dampingFactor (0.85 by default) and otherwise jumps to a random node; a node’s score is the share of time the surfer spends on it. Scores are propagated for maxIterations rounds or until they change by less than tolerance.

CALL gds.pageRank.stream('people', {
  maxIterations: 20,
  dampingFactor: 0.85
})
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).name AS person, round(score * 1000) / 1000.0 AS score
ORDER BY score DESC, person
person, score
"Cy", 1.545
"Bo", 1.248
"Flo", 0.827
"Di", 0.823
"Ed", 0.823
"Ada", 0.501

Passing sourceNodes turns it into Personalized PageRank: the random walk always resets back to that source set instead of to any node in the graph, so the score answers "important relative to these specific starting nodes" rather than "important overall" — for example, ranking people by closeness to one actor’s neighborhood rather than globally.

MATCH (ada:Person {name: 'Ada'})
CALL gds.pageRank.stream('people', {
  sourceNodes: [ada],
  maxIterations: 20,
  dampingFactor: 0.85
})
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).name AS person, round(score * 1000) / 1000.0 AS score
ORDER BY score DESC, person
person, score
"Bo", 0.286
"Ada", 0.231
"Cy", 0.188
"Flo", 0.12
"Di", 0.068
"Ed", 0.068

The two rankings disagree on purpose. Globally Cy is the most important actor; seen from Ada, Bo — her only co-star — dominates, and Di and Ed, three hops away, fall to the bottom. That is the basis of "people you may know" style recommendations.

Betweenness centrality

Betweenness counts, for every node, the fraction of shortest paths between all other pairs that pass through it, so it ranks brokers: nodes whose removal lengthens or severs many routes.

CALL gds.betweenness.stream('people')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).name AS person, score
ORDER BY score DESC, person
person, score
"Cy", 6.0
"Bo", 4.0
"Ada", 0.0
"Di", 0.0
"Ed", 0.0
"Flo", 0.0

Ada is a leaf and Di, Ed and Flo sit in triangles, so none of them lies on a shortest path between two others, while Cy connects the Di/Ed group to the rest and Bo connects Ada. Exact betweenness needs a shortest-path search from every node, which is expensive on large graphs; the samplingSize and samplingSeed options approximate it from a random subset of sources and are the standard way to scale it.

Closeness centrality

Closeness is the inverse of a node’s average shortest-path distance to every other node it can reach, so a high score means information starting there spreads fast.

CALL gds.closeness.stream('people')
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).name AS person, round(score * 1000) / 1000.0 AS score
ORDER BY score DESC, person
person, score
"Cy", 0.833
"Bo", 0.714
"Flo", 0.625
"Di", 0.556
"Ed", 0.556
"Ada", 0.455

On a graph that is not connected, plain closeness misleads because it only averages over reachable nodes; the gds.closeness.harmonic variant sums the inverse distances instead and handles disconnected graphs gracefully (on this connected graph it returns 0.9 for Cy and 0.533 for Ada, the same ordering).

Eigenvector centrality

Eigenvector centrality gives a node a high score when it is connected to other high-scoring nodes, iterating a power method until the scores settle.

CALL gds.eigenvector.stream('people', {
  maxIterations: 20
})
YIELD nodeId, score
RETURN gds.util.asNode(nodeId).name AS person, round(score * 1000) / 1000.0 AS score
ORDER BY score DESC, person
person, score
"Cy", 0.596
"Bo", 0.44
"Flo", 0.394
"Di", 0.366
"Ed", 0.366
"Ada", 0.168

ArticleRank, a close relative of PageRank that dampens the influence of nodes with very few links, is also available as gds.articleRank.

Where these algorithms are applied

Both families depend on the projection and configuration groundwork covered in Graph Data Science Fundamentals. For worked, end-to-end scenarios that combine them with real business questions — routing and logistics optimization built on weighted shortest paths, and fraud-ring detection built on centrality and community structure — see Use Cases and Algorithms in Practice.
