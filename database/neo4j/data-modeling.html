Graph data modeling

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A property graph has no single "correct" schema derived from the data alone — the same facts can be shaped as nodes, relationships or properties in several valid ways. Modeling in Neo4j means starting from the questions the application must answer and shaping the graph so those questions become short, index-backed traversals. The examples build on the movie dataset; the results shown were produced on a Neo4j 2026.01 server, and each worked example cleans up after itself so that the next one starts from the same graph.

The modeling process

Modeling is iterative and driven by queries, not by an entity diagram drawn once. Each pass either confirms the model answers the questions with short traversals or reveals a property that should have been a node, a node that should have been a relationship, or a hub that needs breaking up.

Start from the questions, not a static schema

A relational schema is usually designed from the entities first (normalize the data, add foreign keys, worry about queries later). Graph modeling inverts that order: write down the concrete questions the application needs answered — "which products did this customer buy in the last 90 days", "what is the shortest approval chain between these two roles" — and let each question’s traversal shape drive which things become nodes, which become relationships, and which become properties (Modeling Tips).

The three-way decision for every real-world "thing" is:

  • Node — it has its own identity, is retrieved or matched on independently of anything else, or participates in more than one kind of connection. A Person, a Product, an Order are nodes because each is looked up, filtered and connected to different other things.

  • Relationship — it connects two things that already exist as nodes, and the connection itself is what a query traverses. Relationships are directed and typed, but their direction is often just a storage convenience — most queries can traverse either way, so pick the direction that reads naturally.

  • Property — it describes one node or relationship but is never itself queried as an independent entity, never shared across multiple parents, and never the target of its own traversal. A person’s birthDate is a property; if the application needed to query "everyone born in the same city" as a first-class entity with its own attributes, that city would earn a node instead.

// A first pass driven by a question: "which employees report, directly or
// transitively, into which department, and since when?"
CREATE (:Person {name: 'Ada', birthDate: date('1990-04-02')})
CREATE (:Person {name: 'Grace', birthDate: date('1985-11-30')})
CREATE (:Department {name: 'Engineering'})

MATCH (ada:Person {name: 'Ada'}), (grace:Person {name: 'Grace'})
MATCH (dept:Department {name: 'Engineering'})
CREATE (ada)-[:REPORTS_TO {since: date('2023-01-15')}]->(grace)
CREATE (ada)-[:WORKS_IN]->(dept)
CREATE (grace)-[:WORKS_IN]->(dept)

birthDate stays a property because no question asks for it independently; REPORTS_TO is a relationship because the traversal itself — who reports to whom, and transitively how far up the chain — is the point of the model, and it carries a since property because that single fact belongs to the connection, not to either person.

A property is promoted to a relationship (and its target to a node) as soon as a question needs to traverse it, filter on it independently, or attach further facts to it. A city string on Person stays a property until a question like "who else lives in this city" or "which cities does this company operate in" appears — at that point city becomes a City node and LIVES_IN a relationship, because now the value itself needs identity, indexing and its own connections (Modeling Designs).

Worked example: promoting a property to a node

Suppose the first version of the movie model stores a film’s genre as a string property, which answers "what genre is this film" and nothing more:

MATCH (m:Movie)
SET m.genre = CASE
  WHEN m.title STARTS WITH "The Matrix" OR m.title = "Cloud Atlas" THEN "Sci-Fi"
  WHEN m.title = "Speed" THEN "Action"
  ELSE "Romance" END
RETURN m.genre AS genre, count(*) AS films
ORDER BY genre;
+-------------------+
| genre     | films |
+-------------------+
| "Action"  | 1     |
| "Romance" | 2     |
| "Sci-Fi"  | 3     |
+-------------------+

A new question arrives: "which genres does each actor work in, and who are the sci-fi actors?" Both need the genre to be something you can traverse into and share between films, so it becomes a Genre node reached by an IN_GENRE relationship. The migration is a single statement that reads the old property, merges one node per distinct value and removes the property:

MATCH (m:Movie)
WHERE m.genre IS NOT NULL
MERGE (g:Genre {name: m.genre})
MERGE (m)-[:IN_GENRE]->(g)
REMOVE m.genre;

MATCH (p:Person)-[:ACTED_IN]->(:Movie)-[:IN_GENRE]->(g:Genre)
RETURN p.name AS actor, collect(DISTINCT g.name) AS genres
ORDER BY actor;
+----------------------------------------------+
| actor                | genres                |
+----------------------------------------------+
| "Carrie-Anne Moss"   | ["Sci-Fi"]            |
| "Hugo Weaving"       | ["Sci-Fi"]            |
| "Keanu Reeves"       | ["Sci-Fi", "Action"]  |
| "Laurence Fishburne" | ["Sci-Fi"]            |
| "Meg Ryan"           | ["Romance"]           |
| "Tom Hanks"          | ["Romance", "Sci-Fi"] |
+----------------------------------------------+

Now the second question is a plain traversal that starts at the shared node:

MATCH (g:Genre {name: "Sci-Fi"})<-[:IN_GENRE]-(m:Movie)<-[:ACTED_IN]-(p:Person)
RETURN g.name AS genre, count(DISTINCT p) AS actors, count(DISTINCT m) AS films;
+---------------------------+
| genre    | actors | films |
+---------------------------+
| "Sci-Fi" | 5      | 3     |
+---------------------------+

Moving the value into the graph is what made both questions cheap, but a node shared by many films is also the beginning of a hub; see supernodes below for when that stops being free.

Translating a relational join table

A many-to-many relational schema needs a join table only because SQL rows cannot point at two parents at once. A graph relationship already does that natively, so a join table almost always becomes a relationship, not a third node — unless the join row itself has its own identity that other rows point to.

flowchart LR subgraph REL["Relational"] S1["students
id, name"] --- E1["enrollments
student_id, course_id
grade, enrolled_at"] --- C1["courses
id, title"] end subgraph GR["Graph"] S2(("Student")) -- "ENROLLED_IN
grade, enrolledAt" --> C2(("Course")) end REL ==> GR
// Relational shape being replaced:
//   students(id, name)
//   courses(id, title)
//   enrollments(student_id, course_id, grade, enrolled_at)   -- the join table

CREATE (:Student {id: 'std-1', name: 'Ada'})
CREATE (:Course {id: 'c-1', title: 'Graph Theory'})

MATCH (s:Student {id: 'std-1'}), (c:Course {id: 'c-1'})
CREATE (s)-[:ENROLLED_IN {grade: 'A', enrolledAt: date('2026-02-01')}]->(c)

// The former join table's own columns (grade, enrolled_at) live directly on
// the relationship -- no separate "Enrollment" node is needed to hold them.
MATCH (s:Student)-[e:ENROLLED_IN]->(c:Course)
WHERE e.grade = 'A'
RETURN s.name, c.title, e.enrolledAt
+----------------------------------------+
| s.name | c.title        | e.enrolledAt |
+----------------------------------------+
| "Ada"  | "Graph Theory" | 2026-02-01   |
+----------------------------------------+

Keep the join table as its own node only when the join row is referenced by something other than its two endpoints — for example a Payment node pointing at a specific ENROLLED_IN fact, which relationships cannot be a traversal endpoint for. In that case, materialize an intermediate node (e.g. Enrollment) between Student and Course and hang both the grade and the payment link off it (Modeling Designs). The existing relationship can be reified in place, copying its properties onto the new node:

MATCH (s:Student {id: 'std-1'})-[e:ENROLLED_IN]->(c:Course {id: 'c-1'})
CREATE (en:Enrollment {grade: e.grade, enrolledAt: e.enrolledAt})
CREATE (s)-[:HAS_ENROLLMENT]->(en)-[:FOR_COURSE]->(c)
DELETE e;

MATCH (en:Enrollment)
CREATE (en)<-[:PAYS_FOR]-(:Payment {amount: 120.0, paidAt: date('2026-02-03')});

MATCH (s:Student)-[:HAS_ENROLLMENT]->(en)-[:FOR_COURSE]->(c:Course), (en)<-[:PAYS_FOR]-(pay:Payment)
RETURN s.name, c.title, en.grade, pay.amount;
+-------------------------------------------------+
| s.name | c.title        | en.grade | pay.amount |
+-------------------------------------------------+
| "Ada"  | "Graph Theory" | "A"      | 120.0      |
+-------------------------------------------------+

Anti-pattern: supernodes

A supernode is a single node with an extremely high relationship count — a "country" node connected to every citizen, a "status: active" node connected to every active order. Every traversal through it must scan all of its relationships even when only a handful matter to the query, and writes that touch it serialize against every other transaction touching the same node.

To see the cost, create 20,000 orders and connect each one to a shared Status node, 90 percent PENDING and the rest SHIPPED:

UNWIND range(1, 20000) AS i CREATE (:Order {id: i});

CREATE (pending:Status {name: 'PENDING'}), (shipped:Status {name: 'SHIPPED'})
WITH pending, shipped
UNWIND range(1, 20000) AS i
MATCH (o:Order {id: i})
FOREACH (_ IN CASE WHEN i % 10 <> 0 THEN [1] ELSE [] END | CREATE (o)-[:HAS_STATUS]->(pending))
FOREACH (_ IN CASE WHEN i % 10 = 0 THEN [1] ELSE [] END | CREATE (o)-[:HAS_STATUS]->(shipped));

MATCH (s:Status)
RETURN s.name AS status, COUNT { (s)<-[:HAS_STATUS]-() } AS orders
ORDER BY status;
+--------------------+
| status    | orders |
+--------------------+
| "PENDING" | 18000  |
| "SHIPPED" | 2000   |
+--------------------+

The PENDING node now has eighteen thousand incoming relationships. Asking how many orders are pending has to walk every one of them:

// Anti-pattern: every order connects straight to one shared "PENDING" node
PROFILE MATCH (o:Order)-[:HAS_STATUS]->(s:Status {name: 'PENDING'})
RETURN count(o);
// A frequently written status shared by millions of orders makes ":Status"
// a hot supernode: high fan-out to traverse, and a write hotspot to update.
+-------------------+----+------------------------+----------------+-------+---------+----------------+------------------------+
| Operator          | Id | Details                | Estimated Rows | Rows  | DB Hits | Memory (Bytes) | Page Cache Hits/Misses |
+-------------------+----+------------------------+----------------+-------+---------+----------------+------------------------+
| +ProduceResults   |  0 | `count(o)`             |              1 |     1 |       0 |              0 |                    0/0 |
| |                 +----+------------------------+----------------+-------+---------+----------------+------------------------+
| +EagerAggregation |  1 | count(o) AS `count(o)` |              1 |     1 |       0 |             24 |                    0/0 |
| |                 +----+------------------------+----------------+-------+---------+----------------+------------------------+
| +Filter           |  2 | o:Order                |           1000 | 18000 |   18000 |                |                    0/0 |
| |                 +----+------------------------+----------------+-------+---------+----------------+------------------------+
| +Expand(All)      |  3 | (s)<-[:HAS_STATUS]-(o) |           1000 | 18000 |   18002 |                |                    0/0 |
| |                 +----+------------------------+----------------+-------+---------+----------------+------------------------+
| +Filter           |  4 | s.name = $autostring_0 |              1 |     1 |       2 |                |                    0/0 |
| |                 +----+------------------------+----------------+-------+---------+----------------+------------------------+
| +NodeByLabelScan  |  5 | s:Status               |             10 |     2 |       3 |                |                    0/0 |
+-------------------+----+------------------------+----------------+-------+---------+----------------+------------------------+
Total database accesses: 36007, total allocated memory: 88

Mitigations:

  • Prefer a property over fan-out to a shared low-cardinality node. A status string property on Order, backed by an index, answers the same question without ever creating the supernode.

  • Break fan-out into intermediate nodes when the connection genuinely needs to stay a relationship (e.g. bucket a celebrity’s millions of followers by month or shard, rather than one FOLLOWS relationship per follower straight into the same node).

  • Push data onto the relationship itself instead of introducing a fan-out node purely to hold shared detail — a relationship property is cheaper to add than a new hop through a densely connected node.

// Mitigation: status becomes an indexed property, not a shared node
MATCH (o:Order)-[:HAS_STATUS]->(s:Status)
SET o.status = s.name;

CREATE INDEX order_status IF NOT EXISTS FOR (o:Order) ON (o.status);

PROFILE MATCH (o:Order)
WHERE o.status = 'PENDING'
RETURN count(o);
+-------------------+----+----------------------------------------------------------+----------------+-------+---------+----------------+------------------------+-----------------+
| Operator          | Id | Details                                                  | Estimated Rows | Rows  | DB Hits | Memory (Bytes) | Page Cache Hits/Misses | Indexes Used    |
+-------------------+----+----------------------------------------------------------+----------------+-------+---------+----------------+------------------------+-----------------+
| +ProduceResults   |  0 | `count(o)`                                               |              1 |     1 |       0 |              0 |                    0/0 |                 |
| |                 +----+----------------------------------------------------------+----------------+-------+---------+----------------+------------------------+-----------------+
| +EagerAggregation |  1 | count(o) AS `count(o)`                                   |              1 |     1 |       0 |             24 |                    0/0 |                 |
| |                 +----+----------------------------------------------------------+----------------+-------+---------+----------------+------------------------+-----------------+
| +NodeIndexSeek    |  2 | RANGE INDEX o:Order(status) WHERE status = $autostring_0 |          10000 | 18000 |   18001 |                |                    0/0 | order_status: 1 |
+-------------------+----+----------------------------------------------------------+----------------+-------+---------+----------------+------------------------+-----------------+
Total database accesses: 18001, total allocated memory: 88

The query planner now answers from the index (NodeIndexSeek): 18,001 db hits instead of 36,007 for the same answer. The gain here is only a constant factor, because 90 percent of the orders are pending and all of them have to be counted either way. What a query plan does not show is the write side: with the shared node, every transaction that connects an order to PENDING takes a write lock on that one node, so status changes serialize, while a property write locks only the order. Any traversal that starts at the hub also costs in proportion to its degree, however few of its neighbours the query finally wants. The index itself is explained in Indexes & constraints. See also Modeling Tips for further guidance on recognizing dense-node patterns before they reach production scale.

The trade-off is not absolute. A shared node is the right model when traversing into it is the question, as with the Genre node earlier, which connects few enough films that expanding it is cheap. The decision criterion is the size of the fan-out and how often it is written, not the pattern itself. A bucketing intermediate level looks like (:User)-[:FOLLOWED_IN]->(:FollowerBucket {month: "2026-03"})<-[:HAS_BUCKET]-(:User): each bucket stays small and can be traversed or dropped on its own.

Versioned and temporal modeling

Two common patterns capture how facts change over time without losing the earlier values.

Dated relationships — add validFrom/validTo properties to the relationship itself, and query the one whose range covers a given point in time (a null or absent validTo means "still current").

// A person's address history as successive, non-overlapping relationships
MATCH (p:Person {name: 'Ada Lovelace'})
CREATE (old:Address {city: 'Turin'}), (new:Address {city: 'Porto'})
CREATE (p)-[:LIVED_AT {validFrom: date('2020-01-01'), validTo: date('2025-06-01')}]->(old)
CREATE (p)-[:LIVED_AT {validFrom: date('2025-06-01'), validTo: null}]->(new)

// The address that was current on a given date
MATCH (p:Person {name: 'Ada Lovelace'})-[r:LIVED_AT]->(a:Address)
WHERE r.validFrom <= date('2024-01-01')
  AND (r.validTo IS NULL OR r.validTo > date('2024-01-01'))
RETURN a.city
+---------+
| a.city  |
+---------+
| "Turin" |
+---------+

(The second LIVED_AT has a null validTo, which Neo4j stores as no property at all, so r.validTo IS NULL is also how you find the current address.)

Snapshot nodes — when a whole entity’s state at a point in time matters (not just one relationship), version the node instead: create a new node per snapshot and chain them, keeping the identifying node stable.

// One stable Product node, with a new PriceSnapshot node per change
MATCH (prod:Product {sku: 'A-1'})
CREATE (snap:PriceSnapshot {price: 42.00, asOf: date('2026-03-01')})
CREATE (prod)-[:HAS_PRICE]->(snap)

// Later, a second snapshot
MATCH (prod:Product {sku: 'A-1'})
CREATE (snap:PriceSnapshot {price: 45.50, asOf: date('2026-06-01')})
CREATE (prod)-[:HAS_PRICE]->(snap)

// Most recent snapshot for a product
MATCH (p:Product {sku: 'A-1'})-[:HAS_PRICE]->(s:PriceSnapshot)
RETURN s.price, s.asOf
ORDER BY s.asOf DESC
LIMIT 1
+----------------------+
| s.price | s.asOf     |
+----------------------+
| 45.5    | 2026-06-01 |
+----------------------+

Dated relationships suit facts that attach to an existing edge (a role held over a period, an address lived at); snapshot nodes suit facts about the whole entity’s state, especially when several properties change together and must be read back as one consistent version.

Derived relationships and projections

Some questions are asked so often that it pays to store the answer as a relationship. A projection turns a two-kind (bipartite) graph — people and the films that connect them — into a one-kind graph of people who are connected directly, with a property recording how strongly. Many graph algorithms and recommendation queries want exactly that shape, and the Graph Data Science library builds such projections in memory; here the same idea is materialised in the database with plain Cypher:

MATCH (a:Person)-[:ACTED_IN]->(m:Movie)<-[:ACTED_IN]-(b:Person)
WHERE elementId(a) < elementId(b)
WITH a, b, count(m) AS films
MERGE (a)-[c:CO_ACTED_WITH]->(b)
SET c.films = films
RETURN count(c) AS pairs;
+-------+
| pairs |
+-------+
| 8     |
+-------+

The elementId(a) < elementId(b) filter keeps each unordered pair once, so the relationship’s direction carries no meaning and queries traverse it without an arrow. The derived relationship answers questions that previously needed a two-hop pattern and a count:

MATCH (a:Person {name: "Keanu Reeves"})-[c:CO_ACTED_WITH]-(b:Person)
RETURN b.name AS coActor, c.films AS sharedFilms
ORDER BY sharedFilms DESC, coActor;
+------------------------------------+
| coActor              | sharedFilms |
+------------------------------------+
| "Carrie-Anne Moss"   | 2           |
| "Hugo Weaving"       | 2           |
| "Laurence Fishburne" | 2           |
+------------------------------------+

The cost is that the derived data can go stale: when a film is added, the CO_ACTED_WITH relationships must be refreshed, so derived relationships belong in a batch job or are recomputed from the source relationships, never edited by hand. Delete them with MATCH ()-[c:CO_ACTED_WITH]->() DELETE c when they are no longer needed.

Refactoring and evolving a model

A graph has no migration scripts in the DDL sense, because labels, relationship types and properties come into existence when they are used, but a live model still changes, and every change must be made to the data too. The safe pattern is expand, migrate, contract: add the new shape next to the old one, copy the data across in batches, switch the application over, and remove the old shape. The genre example above is one such migration.

Change How

Add a property or a label

Nothing to declare; write it. Backfill existing nodes with a batched SET.

Rename a label

MATCH (n:Old) SET n:New REMOVE n:Old, in batches for a large graph, then recreate any index or constraint on the new label.

Rename a property

MATCH (n:Label) WHERE n.old IS NOT NULL SET n.new = n.old REMOVE n.old.

Rename a relationship type

Relationship types are immutable: create the new relationship, copy the properties, delete the old one (below).

Split a node, or promote a property to a node

MERGE the new node per distinct value, connect, then REMOVE the old property (genre example).

Change a property’s type

Convert with toInteger(), toFloat() or date() and write back; then add a property type constraint so it stays that way.

Because a relationship type cannot be changed in place, a rename is a copy of the relationship followed by a delete, preserving its properties with SET r2 = properties(r):

CREATE (:Person {name: "Rename Test"})-[:ACTED_IN {roles: ["X"]}]->(:Movie {title: "Rename Film"});

MATCH (a:Person)-[r:ACTED_IN]->(m:Movie)
WHERE a.name = "Rename Test"
CREATE (a)-[r2:STARRED_IN]->(m)
SET r2 = properties(r)
DELETE r
RETURN type(r2) AS newType, r2.roles AS roles;
+----------------------+
| newType      | roles |
+----------------------+
| "STARRED_IN" | ["X"] |
+----------------------+

On a large graph, run the copy with CALL { ... } IN TRANSACTIONS (see Importing data) so that millions of relationships are not rewritten in one transaction. To see what a database actually contains after several rounds of change, list the properties and their types per label and relationship type; a mandatory of false and several types for one property are the usual signs of an inconsistent model:

CALL db.schema.nodeTypeProperties() YIELD nodeLabels, propertyName, propertyTypes, mandatory
RETURN nodeLabels, propertyName, propertyTypes, mandatory
ORDER BY nodeLabels, propertyName;
+-------------------------------------------------------+
| nodeLabels | propertyName | propertyTypes | mandatory |
+-------------------------------------------------------+
| ["Movie"]  | "released"   | ["Long"]      | TRUE      |
| ["Movie"]  | "title"      | ["String"]    | TRUE      |
| ["Person"] | "born"       | ["Long"]      | TRUE      |
| ["Person"] | "name"       | ["String"]    | TRUE      |
+-------------------------------------------------------+

Common modeling mistakes

Mistake Better

One generic relationship type with the meaning in a property, such as -[:RELATED {kind: "ACTED_IN"}]->

A specific type per meaning (ACTED_IN, DIRECTED): the type is stored in the relationship record and is what a pattern filters on cheaply.

Properties modelled as nodes, such as a Born node holding a year for a single person

Keep the value as a property; promote it only when several nodes share it and a question traverses into it.

Lists of ids stored in a property (friendIds: [1, 2, 3]) used as foreign keys

Real relationships; a property holding ids brings the join back and defeats traversal.

A single "type" label for everything, such as :Node {kind: "Person"}

One label per kind: labels drive indexes, constraints and the query planner’s starting points.

Direction chosen per query, with the same fact stored both ways

Store each fact once, in the direction that reads naturally, and traverse it undirected where needed.

Unbounded fan-out into one node

Bucket it, or use an indexed property (see supernodes).
