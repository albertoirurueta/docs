APOC and the extension ecosystem

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

APOC ("Awesome Procedures On Cypher") is the standard extension library for Neo4j — hundreds of procedures and functions covering refactoring, data import/export, graph algorithms, and utilities that plain Cypher does not expose. This page covers installing and locking it down, its most commonly used procedure families, and a brief pointer to the wider extension ecosystem beyond APOC itself.

Installing and allowlisting APOC

APOC ships as a separate .jar dropped into the server’s plugins directory (or pulled in automatically on Aura, where a curated subset is pre-installed). Because many APOC procedures can read/write the filesystem, call out to JDBC, or run arbitrary Cypher, a server does not expose them all by default: two settings in neo4j.conf control what is actually callable.

Settings are split across two files. The apoc.* options that switch features on belong in a dedicated apoc.conf, next to neo4j.conf; the procedure security settings belong in neo4j.conf.

# conf/apoc.conf
# https://neo4j.com/docs/apoc/current/installation/

# Required for apoc.load.json / apoc.export.*.* to touch files on disk
# instead of only remote URLs or streams.
apoc.import.file.enabled=true
apoc.export.file.enabled=true
# Resolve file URLs against server.directories.import, as LOAD CSV does
apoc.import.file.use_neo4j_config=true
# conf/neo4j.conf
# Procedure/function allowlist: only names matching one of these globs are
# callable at all. Narrow this to the families a deployment actually needs
# rather than allowlisting the whole library.
dbms.security.procedures.allowlist=apoc.coll.*,apoc.load.*,apoc.refactor.*,apoc.periodic.*,apoc.export.*,apoc.path.*

# Procedures matching this pattern additionally run without Cypher's normal
# read/write permission checks -- keep this list at least as narrow as the
# allowlist above.
dbms.security.procedures.unrestricted=apoc.load.*,apoc.periodic.*

With Docker none of this needs a file edit. The image installs the plugin from NEO4J_PLUGINS and maps environment variables onto settings, with _ standing for . and __ for a literal underscore:

docker run -d --name neo4j-apoc -p 7474:7474 -p 7687:7687 \
  -e NEO4J_AUTH=neo4j/a-throwaway-password \
  -e NEO4J_PLUGINS='["apoc"]' \
  -e NEO4J_apoc_export_file_enabled=true \
  -e NEO4J_apoc_import_file_enabled=true \
  neo4j:2026.10.2

Without apoc.export.file.enabled=true an export to a file name fails with Export to files not enabled, and the message names the setting and the {stream: true} alternative. Checking what is installed is a Cypher statement away: the examples on this page ran on Neo4j 2026.10.2 (a newer build than the 2026.01 server most pages of this section use), and that build exposes 174 apoc.* procedures and 242 apoc.* functions (SHOW PROCEDURES YIELD name WHERE name STARTS WITH 'apoc.' RETURN count(*)).

The server must be restarted after editing neo4j.conf. See APOC Installation for the plugin drop-in steps per deployment type and the full list of security settings, and APOC Introduction for how the library is organized into procedure/function families. The library itself is catalogued at the APOC documentation; its project home and release notes live at APOC on Neo4j Labs.

Refactoring procedures

apoc.refactor.* reshapes an already-loaded graph: merging duplicate nodes, and renaming labels, relationship types, or properties without a full reload.

// Two Person nodes for the same person (e.g. found via a dedup query);
// merge them into one, combining scalar properties into arrays where they differ.
MATCH (p1:Person), (p2:Person)
WHERE p1.email = p2.email AND id(p1) < id(p2)
CALL apoc.refactor.mergeNodes([p1, p2], {properties: "combine", mergeRels: true})
YIELD node
RETURN node;

// Rename a label across the whole graph.
CALL apoc.refactor.rename.label("Person", "Customer") YIELD total RETURN total;

// Rename a relationship type.
CALL apoc.refactor.rename.type("ACTED_IN", "PERFORMED_IN") YIELD total RETURN total;

The id(p1) < id(p2) guard is not decoration: without it the pattern matches each duplicate pair twice (once in each order), so the same nodes would be offered for merging a second time. Renaming reports the number of entities it touched: renaming ACTED_IN on the film graph (six actors, four films, ten acting credits) returned 10.

Loading JSON and JDBC data

apoc.load.json streams a JSON document or NDJSON feed (local file or URL) as one row per top-level value; apoc.load.jdbc runs a SQL query against any JDBC-reachable database and streams back one row per result row, both driving a downstream MERGE to build the graph.

// Load a JSON array of people and upsert them as nodes.
CALL apoc.load.json("https://example.com/data/people.json")
YIELD value
MERGE (p:Person {id: value.id})
SET p.name = value.name, p.email = value.email;

// The same from a file in the server's import directory (needs apoc.import.file.enabled)
CALL apoc.load.json("file:///people.json")
YIELD value
MERGE (p:Employee {id: value.id})
SET p.name = value.name, p.email = value.email
RETURN p.id, p.name, p.email;
// 1, "Ada", "ada@x.io"
// 2, "Bo",  "bo@x.io"
flowchart LR SRC1["JSON file or URL"] -->|apoc.load.json| ROWS["One row per value"] SRC2["Relational database"] -->|apoc.load.jdbc| ROWS ROWS --> MERGE["MERGE + SET idempotent upsert"] MERGE --> G[("Graph")]

MERGE on the natural key makes the load idempotent: running the same import twice produces the same graph. Run against the file above, it created two Employee nodes. The JDBC form below needs a reachable relational database and the vendor’s driver jar on the server’s classpath.

// Pull rows from a relational source via JDBC (driver jar must also be on the
// server's plugins/classpath) and upsert them.
CALL apoc.load.jdbc(
  "jdbc:postgresql://localhost:5432/mydb?user=neo4j&password=change-me",
  "SELECT id, name, email FROM customers"
)
YIELD row
MERGE (c:Customer {id: row.id})
SET c.name = row.name, c.email = row.email;

Path utility functions

The apoc.path.* family expands or filters paths with more control than a plain Cypher pattern — bounding by relationship type/direction, label, or level without hand-writing a variable-length pattern for every case.

// All nodes reachable within 2 hops via ACTED_IN in either direction.
MATCH (start:Person {name: "Keanu Reeves"})
CALL apoc.path.subgraphNodes(start, {
  relationshipFilter: "ACTED_IN>|<ACTED_IN",
  maxLevel: 2
})
YIELD node
RETURN node;

On the film graph, starting from Ada (after the relationship type was renamed to PERFORMED_IN, hence the filter below), the same call reaches Ada, Bo and the two films they share, and nothing else within two hops:

MATCH (start:Person {name: 'Ada'})
CALL apoc.path.subgraphNodes(start, {relationshipFilter: 'PERFORMED_IN>|<PERFORMED_IN', maxLevel: 2})
YIELD node
RETURN labels(node)[0] AS label, coalesce(node.name, node.title) AS name
ORDER BY label, name;
label, name
"Movie", "Nine Lives"
"Movie", "Red Horizon"
"Person", "Ada"
"Person", "Bo"

subgraphNodes returns each reachable node once, ignoring how many paths lead to it. When the paths themselves matter, apoc.path.expandConfig returns them, and its labelFilter prunes the expansion: the string /Movie ends the path at a Movie node, so a depth-one expansion from Ada yields exactly her two films.

MATCH (start:Person {name: 'Ada'})
CALL apoc.path.expandConfig(start, {
  relationshipFilter: 'PERFORMED_IN', labelFilter: '/Movie', minLevel: 1, maxLevel: 1
})
YIELD path
RETURN length(path) AS hops, last(nodes(path)).title AS movie;
// 1, "Nine Lives"
// 1, "Red Horizon"

Periodic and batch processing

apoc.periodic.iterate splits a large update into batches, committing each one in its own transaction (optionally in parallel) so a bulk write on millions of rows does not hold one giant transaction open or blow the heap.

// Recompute a derived score for every unprocessed Person, 10k nodes per
// transaction, four batches running in parallel.
CALL apoc.periodic.iterate(
  "MATCH (p:Person) WHERE p.processed IS NULL RETURN p",
  "SET p.processed = true, p.score = COUNT { (p)-[:ACTED_IN]->() }",
  {batchSize: 10000, parallel: true, concurrency: 4}
)
YIELD batches, total, timeTaken, errorMessages
RETURN batches, total, timeTaken, errorMessages;
sequenceDiagram participant Q as Driving query participant A as apoc.periodic.iterate participant T as Batch transaction Q->>A: stream rows (outer statement) loop every batchSize rows A->>T: begin transaction, run inner statement per row T-->>A: commit or record error end A-->>Q: batches, total, errorMessages

Two details are easy to get wrong. First, the inner statement counts relationships with a COUNT { } subquery expression: an older size((p)-[:ACTED_IN]->()) pattern-size expression is rejected by the current Cypher version (the default language of the 2026.x line). Second, a failing batch does not fail the call. When the original version of this example used size(...), the procedure returned normally with batches = 3, total = 6 and an errorMessages map reporting three failed batches, while no node had been updated. Always inspect errorMessages (and failedBatches, failedOperations) rather than treating a returned row as success. The corrected example, run with batchSize: 2, parallel: true, concurrency: 2 on the six actors, returned 3 batches, 6 operations and an empty errorMessages, leaving each actor’s score equal to the number of films: Bo 3, Ada and Cy 2, the rest 1.

Use parallel: true only when the batches touch disjoint data; concurrent batches that update the same nodes can deadlock or lose retries. For plain one-statement batching in a query, CALL { ... } IN TRANSACTIONS is the native alternative described in Importing Data.

Exporting data

apoc.export.csv.* and apoc.export.json.* write the result of a query, a set of nodes/relationships, or the whole database to a file (subject to apoc.export.file.enabled above) or return it inline as a stream.

// Export a query's results to CSV on the server's import directory.
CALL apoc.export.csv.query(
  "MATCH (p:Person)-[:ACTED_IN]->(m:Movie) RETURN p.name AS actor, m.title AS movie",
  "actors.csv",
  {}
);

// Export the entire database as JSON, one line per node/relationship.
CALL apoc.export.json.all("full-export.json", {});

On the film graph the CSV export wrote the file actors.csv with ten rows (a "actor","movie" header and one line per acting credit, starting "Ada","Nine Lives"), and the JSON export reported 16 nodes and 12 relationships (the film graph plus the experiments above). The files land in the directory configured by server.directories.import. When file export is disabled, or the server has no writable disk (containers, Aura), pass null as the file name and {stream: true} to get the content back as a result column instead:

CALL apoc.export.csv.query("MATCH (p:Person) RETURN p.name AS name LIMIT 2", null, {stream: true})
YIELD data
RETURN data;
// "name"\n"Ada"\n"Bo"\n

Everyday utility functions

Beyond procedures, APOC adds functions that can be used inside any expression. A few of the most useful, all returning the value shown:

RETURN apoc.coll.toSet([1, 2, 2, 3]) AS set,                      // [1, 2, 3]
       apoc.map.fromPairs([['a', 1], ['b', 2]]) AS map,           // {a: 1, b: 2}
       apoc.date.format(0, 'ms', 'yyyy-MM-dd') AS epoch,          // "1970-01-01"
       apoc.text.levenshteinSimilarity('Alice Smith', 'Alise Smith') AS sim;   // 0.909...

// Add a label to an existing node, or upsert a node with dynamic labels
MATCH (m:Movie {title: 'Nine Lives'}) CALL apoc.create.addLabels(m, ['Archived']) YIELD node RETURN labels(node);
CALL apoc.merge.node(['Tag'], {name: 'x'}, {created: true}, {}) YIELD node RETURN node.name, node.created;

The first call prints the sets and map as commented; the last two return ["Movie", "Archived"] and "x", true. The apoc.create.* and apoc.merge.* families exist because plain Cypher cannot take a label or relationship type from a variable — which matters in generic loaders that read the schema from the input data.

The wider extension ecosystem

APOC is the general-purpose toolbox; a few other officially maintained projects extend Neo4j in more specific directions and are worth knowing about even though they are out of scope for this page:

  • The Neo4j GraphQL Library generates a GraphQL API (queries, mutations, and subscriptions) directly from a GraphQL type-definitions schema, translating each request into Cypher — Neo4j GraphQL Library.

  • The Kafka Connector streams data between Neo4j and Apache Kafka topics in both directions (source and sink), for event-driven pipelines that keep the graph in sync with the rest of a system — Neo4j Streams / Kafka Connector.

  • The Spark Connector reads and writes Neo4j nodes and relationships as Spark DataFrames, for bulk ETL and analytics jobs run from a Spark cluster — Neo4j Connector for Apache Spark.
