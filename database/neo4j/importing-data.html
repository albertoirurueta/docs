Importing data

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Neo4j offers two very different ways to get data in: a transactional LOAD CSV for ongoing or moderate-sized loads against a running, online database, and an offline bulk loader for populating a new database (or adding to one) as fast as possible from flat files. Which one applies depends on whether the database needs to stay up and queryable while the data lands.

flowchart TD S{"Where is the data
and how big is it?"} --> A["CSV file, up to a few million rows
database stays online"] S --> B["CSV files, tens of millions of rows
or more, new database"] S --> C["Another live system
REST API, JSON, JDBC"] S --> D["Small one-off load
on a desktop instance"] A --> A1["LOAD CSV with
CALL IN TRANSACTIONS"] B --> B1["neo4j-admin database import
offline"] C --> C1["APOC load procedures
batched the same way"] D --> D1["Data Importer tool"]

The examples were run on a Neo4j 2026.01 Community Edition server whose import directory is the folder that holds the CSV files; the bulk import was run with neo4j-admin from the same image against a fresh data volume.

LOAD CSV with CALL \{ …​ \} IN TRANSACTIONS

LOAD CSV streams rows from a CSV file (local or over HTTP/HTTPS/S3) one at a time into a Cypher query, with WITH HEADERS exposing each column as a map key. A file:/// URL is resolved relative to the server’s import directory (server.directories.import; /var/lib/neo4j/import in the Docker image), and a path that does not exist fails the query:

22N43: data exception - unable to load external resource. Could not load external resource from file:///missing.csv.

Start by reading a file without writing anything, which is the quickest way to see what the loader will hand to the write clauses. This credits.csv has a header and eight rows:

personName,movieTitle,releaseYear,role
Keanu Reeves,John Wick,2014,John Wick
Willem Dafoe,John Wick,2014,Marcus
Ian McShane,John Wick,2014,Winston
Keanu Reeves,John Wick: Chapter 2,2017,John Wick
Ian McShane,John Wick: Chapter 2,2017,Winston
Laurence Fishburne,John Wick: Chapter 2,2017,Bowery King
Keanu Reeves,Speed,1994,Jack Traven
Sandra Bullock,Speed,1994,
LOAD CSV WITH HEADERS FROM 'file:///credits.csv' AS row
RETURN row.personName AS person, row.movieTitle AS movie, row.role AS role LIMIT 8;
+---------------------------------------------------------------+
| person               | movie                  | role          |
+---------------------------------------------------------------+
| "Keanu Reeves"       | "John Wick"            | "John Wick"   |
| "Willem Dafoe"       | "John Wick"            | "Marcus"      |
| "Ian McShane"        | "John Wick"            | "Winston"     |
| "Keanu Reeves"       | "John Wick: Chapter 2" | "John Wick"   |
| "Ian McShane"        | "John Wick: Chapter 2" | "Winston"     |
| "Laurence Fishburne" | "John Wick: Chapter 2" | "Bowery King" |
| "Keanu Reeves"       | "Speed"                | "Jack Traven" |
| "Sandra Bullock"     | "Speed"                | NULL          |
+---------------------------------------------------------------+

Two things matter here. Every value arrives as a string, whatever it looks like, so numbers and dates must be converted explicitly (toInteger(row.releaseYear), date(row.day)); and an empty field arrives as null, not as an empty string, so Sandra Bullock has no role rather than a blank one:

LOAD CSV WITH HEADERS FROM 'file:///credits.csv' AS row
WITH row LIMIT 1
RETURN valueType(row.releaseYear) AS yearType, valueType(toInteger(row.releaseYear)) AS converted;
+----------------------------------------+
| yearType          | converted          |
+----------------------------------------+
| "STRING NOT NULL" | "INTEGER NOT NULL" |
+----------------------------------------+

Without WITH HEADERS each row is a list indexed from zero, and FIELDTERMINATOR changes the delimiter. This is the form to use for files with no header line:

LOAD CSV FROM 'file:///credits_noheader.csv' AS line FIELDTERMINATOR ';'
RETURN line[0] AS person, line[1] AS movie, toInteger(line[2]) AS year;
+-------------------------------------+
| person         | movie       | year |
+-------------------------------------+
| "Keanu Reeves" | "John Wick" | 2014 |
| "Ian McShane"  | "John Wick" | 2014 |
+-------------------------------------+

Older guidance wrapped a whole LOAD CSV in a single implicit transaction and used USING PERIODIC COMMIT to commit every N rows so the transaction state would not grow unbounded — that clause was removed in Neo4j 5. The modern replacement wraps the per-row work in CALL (row) { ... } IN TRANSACTIONS, which batches the inner unit of work into its own sub-transactions committed every rows rows. Before loading, MERGE on a label needs a matching constraint or index or every MERGE becomes a label scan; create it first:

CREATE CONSTRAINT person_name IF NOT EXISTS FOR (p:Person) REQUIRE p.name IS UNIQUE;
CREATE CONSTRAINT movie_title IF NOT EXISTS FOR (m:Movie) REQUIRE m.title IS UNIQUE;
// credits.csv: personName,movieTitle,releaseYear,role
LOAD CSV WITH HEADERS FROM 'file:///credits.csv' AS row
CALL (row) {
  MERGE (p:Person {name: row.personName})
  MERGE (m:Movie {title: row.movieTitle})
    ON CREATE SET m.released = toInteger(row.releaseYear)
  MERGE (p)-[a:ACTED_IN]->(m)
    ON CREATE SET a.roles = CASE WHEN row.role IS NULL THEN [] ELSE [row.role] END
} IN TRANSACTIONS OF 3 ROWS;
Created 5 nodes, created 7 relationships, set 14 properties, added 5 labels

The batch size is three rows here so that the eight rows commit as three transactions; in a real load use a few hundred to a few thousand (OF 500 ROWS). Re-running the identical statement changes nothing at all (it reports no update counters), because every write is a MERGE, which is what makes a load safe to repeat after a failure. The result is the original dataset plus five new nodes (three people, two films) and seven relationships:

MATCH (p:Person)-[a:ACTED_IN]->(m:Movie)
WHERE m.title STARTS WITH "John Wick" OR m.title = "Speed"
RETURN m.title AS movie, m.released AS year, collect(p.name + " as " + coalesce(head(a.roles), "?")) AS cast
ORDER BY year, movie;
+------------------------------------------------------------------------------------------------------------------------------+
| movie                  | year | cast                                                                                         |
+------------------------------------------------------------------------------------------------------------------------------+
| "Speed"                | 1994 | ["Sandra Bullock as ?", "Keanu Reeves as Jack Traven"]                                       |
| "John Wick"            | 2014 | ["Willem Dafoe as Marcus", "Keanu Reeves as John Wick", "Ian McShane as Winston"]            |
| "John Wick: Chapter 2" | 2017 | ["Ian McShane as Winston", "Laurence Fishburne as Bowery King", "Keanu Reeves as John Wick"] |
+------------------------------------------------------------------------------------------------------------------------------+

Each batch of rows commits independently, so a failure partway through leaves earlier batches durable rather than rolling back the whole file — the trade-off is that the load as a whole is no longer atomic. CALL { ... } IN TRANSACTIONS can only appear as a top-level clause (not nested inside another transactional construct), and every variable the inner block needs — row here — must be passed in explicitly, with the scope clause (row) or, in the older style, WITH row as the first line inside.

When a batch fails

By default the first failing batch aborts the statement, and batches that already committed stay. credits_bad.csv has a row whose divisor is zero; with the default behaviour the load stops at that row after committing the one before it:

LOAD CSV WITH HEADERS FROM 'file:///credits_bad.csv' AS row
CALL (row) {
  MERGE (p:Person {name: row.personName})
  SET p.score = 100 / toInteger(row.divisor)
} IN TRANSACTIONS OF 1 ROW;
22N28: data exception - overflow error. The result of the operation '/ by zero' has caused an overflow.

Rowan A, the row before the bad one, was committed and Rowan C, the row after it, never ran. Adding ON ERROR CONTINUE skips a batch that fails and carries on, and REPORT STATUS AS s adds a status map to every row so the caller can see what happened to each batch:

LOAD CSV WITH HEADERS FROM 'file:///credits_bad.csv' AS row
CALL (row) {
  MERGE (p:Person {name: row.personName})
  SET p.score = 100 / toInteger(row.divisor)
} IN TRANSACTIONS OF 1 ROW ON ERROR CONTINUE REPORT STATUS AS s
RETURN row.personName AS person, s.committed AS committed, s.errorMessage AS error;
+----------------------------------------------------------------------------------------------------+
| person    | committed | error                                                                      |
+----------------------------------------------------------------------------------------------------+
| "Rowan A" | TRUE      | NULL                                                                       |
| "Rowan B" | FALSE     | "/ by zero (Failure when processing file '///credits_bad.csv' on line 3.)" |
| "Rowan C" | TRUE      | NULL                                                                       |
+----------------------------------------------------------------------------------------------------+

The failed row is reported with the line of the file it came from, and the other two commit. The other options are ON ERROR BREAK, which stops at the first failed batch without raising an error to the client (with REPORT STATUS, Rowan C would come back as not committed, with no error of its own), and ON ERROR FAIL, the default. Use CONTINUE for loads where bad rows are expected and will be fixed up afterwards, and FAIL when a failure means the file is wrong and the load should be repeated from the start.

LOAD CSV is the right tool for incremental loads, upserts (MERGE), and files up to a few million rows against a database that other clients are still using concurrently. See LOAD CSV for the full clause reference, including headerless files, custom field terminators, and remote URLs.

Why the constraints come first

A three-thousand-row load of people and films, merged into a graph that already holds about three hundred nodes, took about a fifth of a second with the two uniqueness constraints in place and about a second without them (one run each on a shared test machine, so the figures are indicative only). Without a constraint or index each MERGE is a label scan, so the cost per row grows with the number of nodes already loaded and the whole load is quadratic. The same statement with the constraints is a seek per row.

Deleting in batches

The batching construct is just as useful for removing data. A single MATCH (n) DETACH DELETE n on a large graph is one huge transaction that must hold every deleted node in memory; run in batches it stays bounded:

MATCH (p:Person) WHERE p.name STARTS WITH "Bulk "
CALL (p) { DETACH DELETE p } IN TRANSACTIONS OF 1000 ROWS;

On the 3,300 bulk-loaded nodes used for the timing above this deleted the people and relationships in batches of a thousand rows and left the movie dataset untouched.

Bulk offline import and external sources

For an initial load of tens of millions of rows or more, LOAD CSV is far slower than writing the store files directly. neo4j-admin database import full builds a new database’s files from CSV, bypassing the transaction log and query engine entirely — the target database must not exist yet (or must be empty) and the DBMS must not be running that database while the import runs.

# Full import: builds a brand-new database from scratch (DBMS must be stopped, or the
# target database must not exist).
neo4j-admin database import full neo4j \
  --nodes=Person=people.csv \
  --nodes=Movie=movies.csv \
  --relationships=ACTED_IN=roles.csv \
  --array-delimiter=";"

The three files use Neo4j’s own header syntax, which is a different convention from the plain-column CSV that LOAD CSV reads. :ID(Person) declares the identifier column and its id space (so the same id can exist in two spaces), :START_ID(Person) and :END_ID(Movie) point a relationship at the id spaces of its two ends, born:int types a column, and string[] makes a column an array split on the array delimiter:

personId:ID(Person),name,born:int
p1,Keanu Reeves,1964
p3,Hugo Weaving,1960

movieId:ID(Movie),title,released:int
m1,The Matrix,1999
m2,Cloud Atlas,2012

:START_ID(Person),roles:string[],:END_ID(Movie)
p1,Neo,m1
p3,Agent Smith,m1
p3,Bill Smoke,m2

Run against four people, three films and six relationships, the importer reports its stages and a summary and exits in well under a second:

IMPORT DONE in 512ms.
Imported:
  7 nodes
  6 relationships
  27 properties
Peak memory usage: 514.0MiB

Starting a server on that data directory and querying it shows the multi-valued roles column as a real list, and born as an integer (int is normalized to long, which is what Cypher’s INTEGER is):

+---------------------------------------------------------------------------+
| person             | born | roles                         | movie         |
+---------------------------------------------------------------------------+
| "Hugo Weaving"     | 1960 | ["Bill Smoke"]                | "Cloud Atlas" |
| "Tom Hanks"        | 1956 | ["Zachry", "Dr. Henry Goose"] | "Cloud Atlas" |
| "Keanu Reeves"     | 1964 | ["Jack Traven"]               | "Speed"       |
| "Carrie-Anne Moss" | 1967 | ["Trinity"]                   | "The Matrix"  |
| "Hugo Weaving"     | 1960 | ["Agent Smith"]               | "The Matrix"  |
| "Keanu Reeves"     | 1964 | ["Neo"]                       | "The Matrix"  |
+---------------------------------------------------------------------------+

Community Edition has a single user database named neo4j, so that is the name to import into, and it has only the full command: asking it for incremental is refused as an unmatched argument and the usage text lists full as the only command. Incremental import, which adds nodes, relationships and properties from more CSV files into an existing database without a full reload, is an Enterprise Edition feature. It runs in stages and can resume a partially completed run with --stage=<name> if it is interrupted. The importer also does not create indexes or constraints; create the constraints after the import, as a CREATE CONSTRAINT over existing data verifies it as it builds the index.

For a GUI alternative on a single desktop instance, Neo4j Desktop's Data Importer tool maps CSV columns to node labels, relationship types and properties visually and drives the same import machinery underneath — useful for a one-off load without hand-writing the header syntax.

Neither tool reaches into another live system. To pull rows from a REST API, a JSON file, or a relational database directly inside Cypher, use the APOC procedures apoc.load.json (a URL or file path, walked as a stream of maps) and apoc.load.jdbc (a JDBC connection string and SQL query, streamed row by row) — both are typically driven through the same CALL { ... } IN TRANSACTIONS batching shown above rather than loaded as one giant transaction. See APOC and extensions for setup and more procedures.

Reference: Import (overview of both import paths), neo4j-admin import tutorial (worked walkthrough of the header syntax and multi-file imports), and CSV import (CSV shape and encoding requirements shared by both tools).

Choosing an approach

Tool Database state Best for

LOAD CSV with CALL { } IN TRANSACTIONS

Online, concurrently used

Incremental loads, upserts, small-to-moderate files

neo4j-admin database import full

Offline, database must not exist

Very large initial bulk loads

neo4j-admin database import incremental (Enterprise)

Offline, database already exists

Very large follow-up bulk loads

apoc.load.json / apoc.load.jdbc

Online

Pulling from an external API, file, or relational database

The same online-vs-offline split exists elsewhere: MongoDB separates ongoing writes from bulk tooling like mongoimport (see MongoDB schema design), and a relational engine separates row-by-row INSERT from bulk-loading utilities such as COPY or LOAD DATA (see SQL reference) — in every case, bypassing the normal write path trades transactional safety and concurrent access for raw load throughput.
