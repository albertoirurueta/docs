Concurrency, locking & durable writes

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Couchbase gives every item a CAS token that changes on each mutation, and a set of durable-write levels that hold a write until replicas confirm it. This page covers optimistic concurrency with CAS, pessimistic locking with getAndLock, how to choose between them, and the synchronous-replication durability that replaced the old client-side PersistTo / ReplicateTo approach.

Every example on this page runs against one running example: a bank-style account:42 item and an order:2026-0007 item in the app.sales.orders collection (bucket app, scope sales, collection orders, the keyspace introduced in Buckets, scopes & collections). The outputs shown were produced by running the code against a Couchbase Server 7.6.2 Enterprise node with the Python SDK 4.x and the Java SDK 3.7.

Why a single-key write still needs coordination

Every key-value mutation is atomic on one item: the Data service applies it to the active copy of the vBucket that owns the key, one mutation at a time. That does not make a read-modify-write sequence atomic. Two clients that each read account:42, subtract from the balance in application memory and write the result back will silently lose one of the updates — the classic lost update. Couchbase offers three tools to prevent it on a single item, and a fourth (distributed transactions) for several items:

Tool Where the coordination happens Cost when contended

Sub-document mutateIn (increment, array append, field set)

On the server, as one operation on the item

None — no read, no retry

CAS + retry loop (optimistic)

On the server (compares the CAS), retry logic in the client

Wasted reads and writes on every conflict

getAndLock (pessimistic)

On the server (the item is exclusively held)

Other writers wait or time out for the lock duration

Distributed transactions

A client-side library with server support

Several extra KV round trips per item; see SQL++ DML, functions & transactions

Optimistic locking with CAS

CAS (Compare-And-Swap) is an opaque 64-bit value in an item’s metadata. Every successful mutation assigns a new CAS. To update safely without holding a lock: read the item and its CAS, modify the value in the client, then replace while passing that CAS. If another writer changed the item in between, its CAS no longer matches and the server rejects the write with CasMismatchException — the client then re-reads and retries.

sequenceDiagram participant A as Client A participant B as Client B participant S as Data service A->>S: get account:42 S-->>A: balance 1000, cas C1 B->>S: get account:42 S-->>B: balance 1000, cas C1 A->>S: replace balance 975, cas C1 S-->>A: success, new cas C2 B->>S: replace balance 990, cas C1 S-->>B: CasMismatchException B->>S: get account:42 S-->>B: balance 975, cas C2 B->>S: replace balance 965, cas C2 S-->>B: success, new cas C3

Client B’s first write is rejected because C1 is no longer the item’s CAS. B re-reads the fresh value (975) and applies its change to that, so no update is lost. The same flow as a loop:

flowchart TD A[get id -> value, cas] --> B[modify value in client] B --> C[replace id, value, options.cas = cas] C --> D{result} D -->|success| E[done] D -->|CasMismatchException| F{attempts left?} F -->|yes| A F -->|no| G[fail: give up / surface conflict] D -->|DocumentNotFoundException| G

The first run below shows the conflict itself with the Python SDK: two readers see the same CAS, the first replace wins, the second is rejected.

a = col.get("account:42")          # reader A
b = col.get("account:42")          # reader B: same value, same CAS
print(a.cas == b.cas)

doc = a.content_as[dict]; doc["balance"] -= 25
col.replace("account:42", doc, ReplaceOptions(cas=a.cas))      # A wins, item gets a new CAS

doc = b.content_as[dict]; doc["balance"] -= 10
try:
    col.replace("account:42", doc, ReplaceOptions(cas=b.cas))  # B used a stale CAS
except CasMismatchException as e:
    print("B replace ->", type(e).__name__)

Output of that code:

cas read by A and B: True
A replace ok, new cas differs: True
B replace -> CasMismatchException

The retry loop in Java, written as a small reusable method. The loop re-reads inside every attempt, so it always applies the change to the freshest value:

static void debit(Collection accounts, String id, long amount) {
    for (int attempt = 0; attempt < 10; attempt++) {
        GetResult current = accounts.get(id);
        JsonObject acc = current.contentAsObject();
        acc.put("balance", acc.getLong("balance") - amount);
        try {
            accounts.replace(id, acc, ReplaceOptions.replaceOptions().cas(current.cas()));
            return;                              // committed
        } catch (CasMismatchException e) {
            // someone else mutated the item -- loop, re-read, re-apply
        }
    }
    throw new IllegalStateException(id + " too contended, gave up after 10 attempts");
}

To see the loop earn its keep, eight threads each debited account:42 by 1, five times, starting from a balance of 1000. Without CAS the final balance would almost certainly be above the correct 960 (lost updates); with the loop it is exact, and the loop really did have to retry:

== 2. retry loop, 8 threads x 5 debits of 1
final balance: 960 (expected 960) conflicts retried: True

The Java program (same eight threads, debit as above) prints balance = 960, CAS conflicts retried = true.

Use a bounded loop with a small retry budget, and apply the change to the freshly read value each time — never reuse the value from a previous attempt. Add a short randomized back-off (a few milliseconds) when many writers fight over one hot item, otherwise they keep colliding in lock-step. A single-path change (increment a number, append to an array) is usually better expressed as a sub-document mutateIn, which is atomic server-side and needs no retry loop at all (see Key-value & sub-document operations). See Concurrent Document Mutations for the full pattern.

What a CAS value is

Treat a CAS as an opaque token: compare it for equality and pass it back, nothing more. In practice the server derives it from a hybrid logical clock, so values increase with time and look like a nanosecond timestamp. META().cas exposes it to SQL++:

SELECT META().id, META().cas FROM app.sales.orders LIMIT 2;
{ "id": "order:1",   "cas": 1794319502132051968 }
{ "id": "order:101", "cas": 1794319443955154944 }

Do not parse the number, order items by it, or assume two items mutated "at the same time" have close values. The SDKs hand it back as a long (Java), an integer (Python) or an opaque string-like object depending on the language.

Pessimistic locking with getAndLock

When contention is high enough that retries would thrash, take an exclusive lock instead. getAndLock returns the value and locks the item for a lock TTL (default 15 seconds, 30 seconds maximum). While locked, every mutation of that item is refused with a locked status — including a mutation that carries a CAS, as long as it is not the lock’s CAS. Plain get calls still succeed, but the CAS they return is the sentinel 0xFFFFFFFFFFFFFFFF (-1 as a signed value), so it can never be used to write.

stateDiagram-v2 [*] --> Unlocked Unlocked --> Locked : getAndLock id, lockTime Locked --> Unlocked : replace or upsert with the lock CAS Locked --> Unlocked : unlock id, lockCas Locked --> Unlocked : lock TTL expires Locked --> Locked : other writers refused (locked) Locked --> Locked : plain get still allowed, returns CAS -1
GetResult locked = collection.getAndLock("account:42", Duration.ofSeconds(10));
long lockCas = locked.cas();
JsonObject acc = locked.contentAsObject();
acc.put("balance", acc.getLong("balance") - 25);

// A mutation that passes the lock CAS both writes and releases the lock
collection.replace("account:42", acc, ReplaceOptions.replaceOptions().cas(lockCas));

// If you decide not to write, release the lock explicitly with the same CAS
// collection.unlock("account:42", lockCas);

Every operation below was attempted against an item locked by another client (Python SDK, 15-second lock):

second getAndLock -> DocumentLockedException
replace without cas -> DocumentLockedException
upsert -> DocumentLockedException
remove -> DocumentLockedException
touch -> DocumentLockedException
mutate_in -> DocumentLockedException
plain get while locked: value ok = True cas == lock cas: False
replace with wrong cas -> DocumentLockedException
replace with lock cas ok; balance 975
after write the lock is released: replace without cas ok
explicit unlock -> replace ok
lock expired by itself after ~2.8s
unlock after expiry -> DocumentNotLockedException

Three details are easy to get wrong:

  • The lock blocks every kind of mutation, not just replace: upsert, remove, touch and sub-document mutateIn are all refused. A wrong CAS on a locked item is reported as locked, not as a CAS mismatch.

  • The SDK retries locked errors until the operation timeout, because the lock is expected to be short-lived. With the Python SDK the call finally surfaces as DocumentLockedException. The Java SDK surfaces the same situation as an AmbiguousTimeoutException whose retry reasons contain KV_LOCKED; this Java run shows it (a held lock plus a 2.5 second kvTimeout):

    replace on a locked item -> AmbiguousTimeoutException (retried: KV_LOCKED)
second getAndLock -> AmbiguousTimeoutException
replace with the lock CAS -> committed, balance 935

  • Unlocking an item that is no longer locked fails with DocumentNotLockedException: after the TTL expires, the old lock CAS is worthless, so always finish the critical section well inside the TTL.

The lock is released by a successful CAS mutation, by an explicit unlock, or automatically when the lock TTL expires — so a crashed client cannot wedge an item forever. Prefer pessimistic locking for short, guaranteed critical sections; prefer CAS retries when conflicts are rare. Never do slow work (network calls, user input) while holding a lock: every other writer of that key is stalled for its whole duration.

Choosing a strategy

flowchart TD Q{What changes?} -->|one field or counter| SD[Sub-document mutateIn: atomic on the server] Q -->|whole document, rare conflicts| CAS[CAS + bounded retry loop] Q -->|whole document, frequent conflicts, short work| LOCK[getAndLock, write with the lock CAS] Q -->|several documents must change together| TX[Distributed transaction] CAS --> HTTP{Over HTTP?} HTTP -->|yes| ETAG[CAS as ETag / If-Match]

CAS as an HTTP ETag

CAS maps directly onto HTTP conditional requests. Return the item’s CAS as the ETag of a GET response; require it back as If-Match on PUT / PATCH; translate a CasMismatchException into 412 Precondition Failed. Clients then get optimistic concurrency across the network for free.

sequenceDiagram participant C as HTTP client participant API as API service participant S as Couchbase C->>API: GET /accounts/42 API->>S: get account:42 S-->>API: value, cas API-->>C: 200, ETag = cas C->>API: PUT /accounts/42, If-Match = cas API->>S: replace account:42, cas alt CAS unchanged S-->>API: success API-->>C: 200, new ETag else CAS changed S-->>API: CasMismatchException API-->>C: 412 Precondition Failed end
@PutMapping("/accounts/{id}")
ResponseEntity<?> update(@PathVariable String id, @RequestHeader("If-Match") String ifMatch,
                         @RequestBody Account body) {
    long cas = Long.parseUnsignedLong(ifMatch.replace("\"", ""));
    try {
        MutationResult r = accounts.replace("account:" + id, body.toJson(),
            ReplaceOptions.replaceOptions().cas(cas));
        return ResponseEntity.ok().eTag("\"" + Long.toUnsignedString(r.cas()) + "\"").build();
    } catch (CasMismatchException e) {
        return ResponseEntity.status(HttpStatus.PRECONDITION_FAILED).build();
    } catch (DocumentNotFoundException e) {
        return ResponseEntity.notFound().build();
    }
}

Format the CAS the same way in both directions (an unsigned decimal or hexadecimal string) and quote it, as HTTP ETags are quoted strings.

Durable writes (synchronous replication)

By default a KV write is acknowledged as soon as the active copy has it in memory. A durable write asks the server to hold the acknowledgement until the mutation is also on replicas and/or on disk, using synchronous replication built into the server (6.5+). Pass a DurabilityLevel:

Level Acknowledged when

majority

A majority of configured replicas (including the active) hold the mutation in memory.

majorityAndPersistToActive

A majority hold it in memory and the active node has written it to disk.

persistToMajority

A majority of nodes have written the mutation to disk.

 
collection.upsert("order:2026-0007", order,
    UpsertOptions.upsertOptions().durability(DurabilityLevel.MAJORITY));

// Stronger: survive an active-node disk loss immediately after ack
collection.upsert("order:2026-0007", order,
    UpsertOptions.upsertOptions().durability(DurabilityLevel.PERSIST_TO_MAJORITY));
sequenceDiagram participant C as Client participant A as Active node participant R1 as Replica 1 participant R2 as Replica 2 C->>A: upsert(key, value), durability = majority A->>A: apply to active (in memory) A->>R1: replicate mutation A->>R2: replicate mutation R1-->>A: ack (in memory) Note over A,R1: majority reached (active + 1 replica) A-->>C: success R2-->>A: ack (later)

While the write is pending the item is in a prepared state: the mutation is not visible to readers until it commits, and a second write to the same key is refused with a DurableWriteInProgressException, which the SDK retries. That is the price of synchronous replication — two durable writes to one hot key serialize.

The numbers that matter are the bucket’s numReplicas and the number of nodes. Running the same upsert with all three levels against two different configurations of a single-node cluster shows how the server decides what is possible (the second bucket is configured for one replica, which a one-node cluster cannot hold):

Bucket with numReplicas 0:

MAJORITY -> success
MAJORITY_AND_PERSIST_TO_ACTIVE -> success
PERSIST_TO_MAJORITY -> success

Bucket with numReplicas 1 on a single data node:

plain upsert on 1-replica single-node bucket -> success
MAJORITY -> DurabilityImpossibleException after 0.00s
MAJORITY_AND_PERSIST_TO_ACTIVE -> DurabilityImpossibleException after 0.00s
PERSIST_TO_MAJORITY -> DurabilityImpossibleException after 0.00s

A bucket with no replicas has a majority of one (the active alone), so every level is satisfiable there — which also means the level then gives no protection against losing that node. A bucket configured for a replica the cluster cannot place fails immediately and deterministically with DurabilityImpossibleException, while a plain non-durable write to the same bucket still succeeds. The guarantee only becomes real once the topology exists: after changing numReplicas the new replicas appear only after a rebalance, and durable writes issued before that can fail with the same exception. Durable writes are supported for buckets with up to two replicas; with three, they are refused.

A durable write that is accepted but not confirmed before its timeout (default 10 seconds for durable operations in the SDKs) returns a DurabilityAmbiguousException: the write may still commit, so treat it like any ambiguous timeout — read the item back or retry only if the operation is idempotent.

A bucket can also set a minimum durability level (--durability-min-level on bucket-create), which the server applies to every write that asks for less; per-operation levels can only raise it.

Relation to the older PersistTo / ReplicateTo

Older SDK documentation performs client-side durability with PersistTo and ReplicateTo options: after the write is acknowledged, the SDK polls each node with observe calls until the required number report the mutation persisted or replicated. That approach still exists for compatibility with pre-6.5 servers, but it is client-driven, several round-trips, and not atomic with the write. If the requirement cannot be met, the client simply keeps polling until its deadline: on the one-node, one-replica bucket above, asking for ReplicateTo.ONE ended in an AmbiguousTimeoutException after the full timeout instead of failing at once the way DurabilityLevel does. On Couchbase Server 7.6 use DurabilityLevel instead — the guarantee is enforced by the server as part of the mutation, in one operation. Reach for PersistTo / ReplicateTo only when talking to a server too old for synchronous replication. The first edition of Couchbase Essentials covers only the observe-based style, which is the main outdated point to unlearn when reading it. See Durability for the comparison and KV durability options for the SDK surface.

from couchbase.durability import ServerDurability, Durability
from couchbase.options import UpsertOptions

col.upsert("order:2026-0007", {"total": 28.98},
           UpsertOptions(durability=ServerDurability(Durability.PERSIST_TO_MAJORITY)))

Durability also interacts with failover: with at least one replica, a durably acknowledged write survives the loss and failover of any single node, because the promoted replica already holds the mutation. Losing more nodes than the replica count tolerates can still lose data, so durability bounds how many failures are survived rather than promising the write forever; see Clusters, replication, failover & XDCR.

Contrast with MongoDB

Couchbase applies durability and concurrency per single-key operation: a DurabilityLevel is MongoDB’s write concern for one item, and a CAS-guarded replace is MongoDB’s single-document atomic update. MongoDB spells the majority guarantee w: "majority" and its on-disk variant with j: true; the concepts line up with majority and persistToMajority. See MongoDB single-document atomicity for the update-in-place guarantee and MongoDB write/read concern for the durability knobs. Multi-document ACID in Couchbase is a separate library, covered in SQL++ DML, functions & transactions.
