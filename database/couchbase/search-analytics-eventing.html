Full-Text & Vector Search, Analytics & Eventing

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The Data, Query and Index services cover key-value access and SQL++. Three further services handle work those cannot: the Search service for linguistic and vector similarity matching, the Analytics service for ad-hoc analytical queries that must not disturb the operational load, and the Eventing service for running code on every data change.

All three work from the same change feed, so they share one mental model: the Data service is the source of truth, and each of these services keeps its own derived copy, built from DCP, shaped for its own job.

flowchart LR DATA[(Data service: app.sales.*)] -->|DCP| FTS[Search: inverted + vector index] DATA -->|DCP| ANA[Analytics: columnar shadow datasets] DATA -->|DCP| EVT[Eventing: JavaScript functions] APP[Application] -->|KV| DATA APP -->|SQL++ SEARCH| QRY[Query service] QRY -->|search request| FTS QRY -->|fetch documents| DATA APP -->|analytical SQL++| ANA EVT -->|bucket binding write| DATA

The examples below use the running keyspace of this section: documents in app.sales.customers and app.sales.orders (bucket app, scope sales). Everything was run against a single Couchbase Server 7.6.2 Enterprise node with the Data, Query, Index, Search, Analytics and Eventing services, so the outputs are real. The sample data are four customers and four orders:

UPSERT INTO app.sales.customers (KEY k, VALUE v) SELECT k, v FROM [
 {"k":"customer:1","v":{"type":"customer","name":"Ada Lovelace","city":"London",
   "bio":"Quiet analytical engineer who loves mathematics and romantic poetry",
   "region":"EU","emb":[0.9,0.1,0.0,0.1]}},
 {"k":"customer:2","v":{"type":"customer","name":"Grace Hopper","city":"New York",
   "bio":"Compiler pioneer and naval officer, loud and funny","region":"US","emb":[0.1,0.9,0.1,0.0]}},
 {"k":"customer:3","v":{"type":"customer","name":"Alan Turing","city":"Manchester",
   "bio":"Quiet mathematician who ran long distances and loved puzzles","region":"EU","emb":[0.8,0.2,0.1,0.1]}},
 {"k":"customer:4","v":{"type":"customer","name":"Katherine Johnson","city":"Hampton",
   "bio":"Orbital mechanics calculations by hand for space flights","region":"US","emb":[0.0,0.2,0.9,0.1]}}
] AS x;

The Search service (FTS)

flowchart LR DOC[Document field text] --> CF[Character filters] CF --> TOK[Tokenizer] TOK --> TF[Token filters: lowercase, stop words, stemmer] TF --> IDX[(Inverted index: term to documents)] Q[Query text] --> QA[Same analyzer] QA --> LOOK[Term lookup and scoring] IDX --> LOOK LOOK --> HITS[Ranked hits with scores]

Search indexes and index definitions

A Search index is an inverted index maintained by the Search service, separate from GSI. Its index definition selects the collections and fields to index, the analyzer per field, and whether to store values for result highlighting. A dynamic mapping indexes every field it encounters; a static mapping indexes only the named fields and is far smaller and faster to build. The definition is a JSON document created through the REST API, the Web Console or an SDK. This one is scoped to app.sales, indexes the collection customers only, and uses a static mapping with a standard-analyzed name, an English-analyzed bio, a keyword-analyzed city and a four-dimensional vector field emb:

{
  "type": "fulltext-index",
  "name": "customers_idx",
  "sourceType": "gocbcore",
  "sourceName": "app",
  "planParams": { "maxPartitionsPerPIndex": 1024, "indexPartitions": 1, "numReplicas": 0 },
  "params": {
    "doc_config": { "mode": "scope.collection.type_field", "type_field": "type" },
    "mapping": {
      "default_analyzer": "standard",
      "default_mapping": { "enabled": false },
      "types": {
        "sales.customers": {
          "enabled": true,
          "dynamic": false,
          "properties": {
            "name": { "enabled": true, "fields": [ { "name": "name", "type": "text", "analyzer": "standard", "index": true, "store": true } ] },
            "bio":  { "enabled": true, "fields": [ { "name": "bio", "type": "text", "analyzer": "en", "index": true, "store": true, "include_term_vectors": true } ] },
            "city": { "enabled": true, "fields": [ { "name": "city", "type": "text", "analyzer": "keyword", "index": true, "store": true } ] },
            "emb":  { "enabled": true, "fields": [ { "name": "emb", "type": "vector", "dims": 4, "similarity": "l2_norm", "vector_index_optimized_for": "recall", "index": true } ] }
          }
        }
      }
    }
  }
}
curl -u Administrator:password -X PUT -H 'Content-Type: application/json' \
  http://localhost:8094/api/bucket/app/scope/sales/index/customers_idx -d @customers_idx.json
# {"status":"ok","name":"app.sales.customers_idx","uuid":"2740e532bedf0ab3"}

curl -u Administrator:password \
  http://localhost:8094/api/bucket/app/scope/sales/index/customers_idx/count
# {"status":"ok","count":4}

The count of 4 is the proof the index built from the four customers. Two key facts of the definition: the doc_config mode scope.collection.type_field tells the index to take the collection from the document’s keyspace, and the type-mapping key sales.customers is the scope.collection pair. See Full Text Search: Introduction.

Analyzers: tokenizers, token filters, languages

An analyzer = optional character filters, one tokenizer, and zero or more token filters:

"The Grand-Hotel, PARIS!"
  --unicode tokenizer-->  [The, Grand, Hotel, PARIS]
  --to_lower-->           [the, grand, hotel, paris]
  --stop (en)-->          [grand, hotel, paris]
  --stemmer (en)-->       [grand, hotel, pari]

Built-in language analyzers (en, fr, de, cjk, …​) bundle the right stop list and stemmer.

The analyzer used at index time must match the one used at query time, or the tokens will not line up and nothing matches. Language analyzers add stemming and stop-word removal; the keyword analyzer emits the whole field value as a single token, which is what you want for codes, enums and exact-match facets. That is why the index above analyzes city with keyword (the term is Manchester, case and all) and bio with en.

Stemming has one trap that the sample data expose. bio is analyzed with en, so "mathematics" is indexed as the stem mathemat. A wildcard acts on the indexed terms, not on the original words, so a wildcard prefix longer than the stem matches nothing:

SELECT c.name, SEARCH_SCORE() AS score
FROM app.sales.customers AS c
WHERE SEARCH(c, "bio:quiet +bio:mathematic*")
ORDER BY score DESC;
[{"name": "Alan Turing", "score": 0.8039964771002073}]

Only Alan Turing matched. The English analyzer stems "mathematics" (Ada Lovelace’s bio) to mathemat, which does not start with mathematic, while "mathematician" (Alan Turing’s bio) keeps a longer stem that does. The reverse also holds: bio:mathematics is analyzed the same way as the indexed text and matches Ada Lovelace only, because "mathematician" is a different stem. Query a stemmed field with whole words, and index a second, unstemmed copy of the field (for example with the standard analyzer) when you need prefix and wildcard searches over the original spelling.

Query types

-- SQL++ SEARCH() with a query-string query: a disjunction of two terms
SELECT c.name FROM app.sales.customers AS c WHERE SEARCH(c, "bio:quiet bio:funny");

-- Structured form: a full-text query object instead of a string
SELECT c.name FROM app.sales.customers AS c
WHERE SEARCH(c, {"query": {"match_phrase": "compiler pioneer", "field": "bio"}});
[{"name": "Alan Turing"}, {"name": "Ada Lovelace"}, {"name": "Grace Hopper"}]    -- query string
[{"name": "Grace Hopper"}]                                                    -- match_phrase
Query type Matches

match / match-phrase

analyzed text; a phrase keeps term order and adjacency

prefix / wildcard / regexp

a term by prefix, by ? / * glob, or by full regular expression

fuzzy

terms within an edit distance of the input (typo tolerance)

term

a single token with no analysis applied (exact)

numeric-range / date-range

a min / max bound over numeric or RFC-3339 date fields

geo distance / bounding-box / polygon

documents whose geo-point falls inside a region

bool / conjunction / disjunction

combine sub-queries with must, should, must_not

query-string

the mini-language above: + / -, field:, ~ fuzziness, *, phrases

Typo tolerance and a keyword field, both from the running data:

-- fuzzy: edit distance 1 on the keyword city field ("Londn" is one edit from "London")
SELECT c.name FROM app.sales.customers AS c
WHERE SEARCH(c.city, {"match": "Londn", "fuzziness": 1});

-- fuzzy on the analyzed name (distance 2)
SELECT c.name FROM app.sales.customers AS c
WHERE SEARCH(c, {"query": {"match": "Lovelase", "field": "name", "fuzziness": 2}});

-- exact match on the keyword field
SELECT c.name, c.city FROM app.sales.customers AS c WHERE SEARCH(c.city, "Manchester");
[{"name": "Ada Lovelace"}]
[{"name": "Ada Lovelace"}]
[{"name": "Alan Turing", "city": "Manchester"}]

See Types of Queries for the JSON shape of each.

Relevance scoring, index partitions and replicas

Hits are ranked by a TF-IDF / BM25-style relevance score — rarer query terms and denser matches score higher — exposed to SQL++ as SEARCH_SCORE(). Searching quiet in bio scored both matching customers 0.4867 (the term is equally rare in both short bios), while the two-term query above scored Alan Turing 0.804, because it matched more terms. Each Search index is divided into partitions spread across Search nodes so a query scans them in parallel, with optional replica partitions for availability and query throughput:

"planParams": { "indexPartitions": 6, "numReplicas": 1 }

SEARCH() and SEARCH_SCORE() from SQL++

SEARCH() is a predicate the Query service pushes down to the Search service; the surrounding SQL++ then joins, filters, groups and orders the hits like any other rows. SEARCH_SCORE() exposes the relevance score and SEARCH_META() the stored fields and highlights of each hit. See Search Functions.

sequenceDiagram participant App as Application participant Q as Query service participant F as Search service participant D as Data service App->>Q: SELECT ... WHERE SEARCH(c, ...) Q->>F: search request (index customers_idx) F-->>Q: ordered keys + scores + fragments Q->>D: fetch documents by key D-->>Q: documents Q->>Q: re-check predicate, join, order, project Q-->>App: rows

EXPLAIN confirms the shape: an IndexFtsSearch operator on app.sales.customers_idx, then a Fetch of the documents from the Data service, then a Filter re-applying the SEARCH predicate. A highlight from SEARCH_META(), with the query options naming the index explicitly:

SELECT c.name, SEARCH_META() AS m
FROM app.sales.customers AS c
WHERE SEARCH(c, {"query": {"match": "quiet", "field": "bio"}, "highlight": {}, "fields": ["name"]},
             {"index": "app.sales.customers_idx"});
{"name": "Ada Lovelace",
 "m": {"fields": {"name": "Ada Lovelace"},
       "fragments": {"bio": ["<mark>Quiet</mark> analytical engineer who loves mathematics and romantic poetry"]},
       "id": "customer:1", "score": 0.4866980679353247, ... }}

When naming the index, give it in its qualified form (app.sales.customers_idx). In the test run the bare name customers_idx returned no rows and no error, which is easy to mistake for "no match".

Vector Search and hybrid search (7.6)

Couchbase Server 7.6 adds Vector Search: an FTS index can carry a dense-vector field (cosine, dot-product or L2 similarity) and answer k-nearest-neighbour queries over embeddings. The index above declares emb as a vector field with dims 4 and similarity l2_norm; real embeddings have hundreds or thousands of dimensions (1536 for several common embedding models), and the declared dims must match the vectors you store and query with. A query carries a knn clause:

-- the four customers' nearest neighbours of a query vector, k = 2, no text clause
SELECT c.name, SEARCH_SCORE() AS score
FROM app.sales.customers AS c
WHERE SEARCH(c, {"query": {"match_none": {}},
                 "knn": [ {"field": "emb", "vector": [0.85, 0.15, 0.0, 0.1], "k": 2} ]})
ORDER BY score DESC;

-- hybrid: the same knn clause combined with a lexical match
SELECT c.name, SEARCH_SCORE() AS score
FROM app.sales.customers AS c
WHERE SEARCH(c, {"query": {"match": "quiet", "field": "bio"},
                 "knn": [ {"field": "emb", "vector": [0.85, 0.15, 0.0, 0.1], "k": 2} ]})
ORDER BY score DESC;
[{"name": "Ada Lovelace", "score": 200.0001721085599}, {"name": "Alan Turing", "score": 66.66665987836059}]
[{"name": "Ada Lovelace", "score": 200.48687017649522}, {"name": "Alan Turing", "score": 67.15335794629591}]

Ada Lovelace’s embedding is the closest to the query vector, Alan Turing’s second; Grace Hopper and Katherine Johnson are farther away and are not among the k of 2. In the hybrid query the lexical score (0.4867) is added to the vector score, which is how the two rankings combine; a boost on either clause shifts the balance. Because the vector index lives inside the same FTS index, one query can combine a knn clause with ordinary text and filter clauses — hybrid search — which is the retrieval step of a RAG pipeline: embed the user’s question, knn for the closest documents, pass them to the model as context. The similarity choice must match how the embedding model was trained (cosine or dot product for most text models, l2_norm for some image models). For the equivalent on the document-database side see MongoDB Text & Atlas Search. See Hybrid Search & Re-ranking for the vendor-neutral theory behind combining knn with lexical scoring this way.

The Analytics service

Analytics is an Enterprise-Edition service (and the engine behind Capella Columnar). It keeps its own column-oriented copy of chosen collections and answers long-running analytical SQL++ without adding load to the Data, Query or Index services.

flowchart TD subgraph OLTP[Operational side] KV[(Data service)] QS[Query service + GSI] end subgraph OLAP[Analytical side] LINK[Local link: DCP shadowing] DS[(Datasets: columnar, partitioned)] CC[Cluster controller: plans and coordinates] NC[Node controllers: run fragments in parallel] end KV -->|change feed| LINK LINK --> DS APP[Analytical SQL++] --> CC CC --> NC NC --> DS APP2[Operational SQL++] --> QS QS --> KV

Shadow datasets and links

-- Simple form: shadow one collection into an Analytics dataset.
ALTER COLLECTION app.sales.orders ENABLE ANALYTICS;
ALTER COLLECTION app.sales.customers ENABLE ANALYTICS;

-- Explicit form, with a filter:
CREATE DATASET paid ON app.sales.orders WHERE status = "PAID";

-- A secondary index inside the Analytics store:
CREATE ANALYTICS INDEX orders_status ON app.sales.orders(status: string);

-- A link names a data source; "Local" is this cluster. A remote link federates queries:
CREATE LINK s3link TYPE `s3` WITH { "region": "eu-west-1", "accessKeyId": "..." };

All three statements above up to the secondary index ran as written against the Analytics endpoint (POST /analytics/service, port 8095 plaintext or 18095 TLS). The metadata shows what was created. The simple form creates datasets named after the collection inside a dataverse called app/sales; the explicit CREATE DATASET without a dataverse lands in Default:

[{"DataverseName": "Default",   "DatasetName": "paid"},
 {"DataverseName": "app/sales", "DatasetName": "customers"},
 {"DataverseName": "app/sales", "DatasetName": "orders"}]

A dataset (analytical collection) is a shadow of a source collection, kept in sync from the change feed so it lags by seconds rather than being transactionally consistent. In the test run, a COUNT(*) issued moments after enabling shadowing on orders returned a partial count of 1, and the full count a few seconds later: always allow for this when reading right after a write or an ALTER COLLECTION. CREATE ANALYTICS INDEX builds a secondary index within the Analytics store; CREATE LINK attaches a remote Couchbase cluster or object store (S3, Azure Blob, GCS) so a single query can span operational data and archived data.

The Analytics SQL++ dialect vs. the Query service

Both speak SQL++, but Analytics is a separate implementation tuned for full scans and large joins: no USE KEYS, no index hints, no transactions; joins are hash or merge joins chosen by its own optimizer rather than nested-loop GSI lookups; a statement is expected to read most of a dataset. The Query service is the opposite — point lookups and selective range scans through GSI. A point lookup written the Query-service way is a syntax error in Analytics:

SELECT 1 AS x FROM app.sales.orders o USE KEYS "order:1";
[{"code": 24000, "msg": "Syntax error: In line 1 >>SELECT 1 AS x FROM app.sales.orders o USE KEYS \"order:1\";<< Encountered \"USE\" at column 39. "}]

The same keyspace path (app.sales.orders) works in both services, which makes it easy to move a query between them. See Analytics: Introduction.

The columnar engine and MPP execution

Datasets are stored column-major and compressed, so an aggregate over a few fields reads only those columns off disk. Execution is massively parallel (MPP): a coordinator splits the query into fragments run concurrently across all Analytics nodes and partitions, then merges the partial results. A revenue-by-region report joins orders to customers and groups the result, a shape that is a multi-collection scan and hash join rather than a point lookup:

SELECT c.region,
       COUNT(DISTINCT o.customerId) AS buyers,
       COUNT(*) AS orders,
       ROUND(SUM(o.total), 2) AS revenue
FROM app.sales.orders o
JOIN app.sales.customers c ON o.customerId = META(c).id
GROUP BY c.region
ORDER BY revenue DESC;
[{"buyers": 2, "orders": 3, "region": "EU", "revenue": 213.18},
 {"buyers": 1, "orders": 1, "region": "US", "revenue": 9.5}]

Over four orders this is trivial; the point is that the execution needs no index. A GROUP BY over millions of documents that would be a heavy blocking sort on the Query service returns quickly here. The Analytics EXPLAIN output is a tree of physical operators (DISTRIBUTE_RESULT, ONE_TO_ONE_EXCHANGE, STREAM_PROJECT, …​) rather than the Query service’s IndexScan / Fetch / Filter chain, which is the visible difference between the two engines.

When to reach for it

  • Ad-hoc reporting and dashboards over live operational data, with no ETL into a separate warehouse.

  • Large aggregations, GROUP BY and multi-collection joins that would slow the Query service or need too many purpose-built GSIs.

  • Federated queries across clusters or over object storage via CREATE LINK.

Keep OLTP reads and writes on the Data and Query services and send analytical scans here. For the aggregate and windowing SQL these queries build on, see SQL Aggregate & Window Functions. Enterprise Analytics and Capella Columnar are documented in depth at the Analytics introduction.

The Eventing service

Eventing runs user-supplied JavaScript Functions against the Data service’s change feed. Each function is deployed against one source collection and reacts to mutations in it. See Eventing: Overview.

flowchart LR W[Write to source collection] --> DCP[DCP change feed] DCP --> FN{Function} FN -->|insert or update| UPD[OnUpdate doc, meta] FN -->|delete or expiry| DEL[OnDelete meta, options] UPD --> B1[Bucket binding: write another collection] UPD --> B2[cURL binding: call an external API] UPD --> T[createTimer: run later] T --> TH[Timer handler] META[(Metadata keyspace: checkpoints and timers)] --- FN

The OnUpdate / OnDelete handlers

The function from the running example turns a paid order into a denormalised summary in another collection, and removes the summary when the order is deleted:

// Function body. `doc` is the changed document; `meta` carries its id and metadata.
function OnUpdate(doc, meta) {
  if (doc.type !== 'order' || doc.status !== 'PAID') return;
  // Write a denormalised summary into another collection via a bucket binding.
  summaries[meta.id] = { customer: doc.customerId, total: doc.total,
                         source: meta.keyspace };
  log('summarised', meta.id);
}
function OnDelete(meta, options) {
  delete summaries[meta.id];              // cascade delete
}

OnUpdate fires on insert and update; OnDelete on delete and on expiry. Handlers should be short and idempotent — they can be re-invoked after a rebalance or a restart. Note that meta.keyspace is an object (bucket_name, scope_name, collection_name), not a string; the stored summaries carried exactly that.

A function is defined by a JSON document pairing the code with its deployment configuration: source collection, a metadata keyspace for the checkpoints, and the bindings. It was created and deployed through the REST API on the Eventing port (8096):

{
  "appname": "paid_summary",
  "appcode": "function OnUpdate(doc, meta) { ... } function OnDelete(meta, options) { ... }",
  "depcfg": {
    "source_bucket": "app", "source_scope": "sales", "source_collection": "orders",
    "metadata_bucket": "evmeta", "metadata_scope": "_default", "metadata_collection": "_default",
    "buckets": [ { "alias": "summaries", "bucket_name": "app", "scope_name": "sales",
                   "collection_name": "order_summaries", "access": "rw" } ]
  },
  "settings": { "dcp_stream_boundary": "everything", "deployment_status": false,
                "processing_status": false, "log_level": "INFO", "worker_count": 1 },
  "function_scope": { "bucket": "*", "scope": "*" }
}
curl -u Administrator:password -X POST -H 'Content-Type: application/json' \
  http://localhost:8096/api/v1/functions/paid_summary -d @fn.json      # stored, not yet running
curl -u Administrator:password -X POST http://localhost:8096/api/v1/functions/paid_summary/deploy
curl -u Administrator:password http://localhost:8096/api/v1/status      # composite_status

The status went deploying for roughly half a minute (the function is compiled, workers start, the feed boundary is applied) and then deployed. Because the function was deployed from the beginning of the feed ("dcp_stream_boundary": "everything"), the two orders already PAID before deployment were summarised immediately, with no new write:

[{"id": "order:2", "customer": "customer:1", "total": 120}, {"id": "order:4", "customer": "customer:3", "total": 64.2}]

Then orders were changed with ordinary SQL++, and the function reacted each time:

UPDATE app.sales.orders SET status = "PAID" WHERE META().id = "order:1";
-- order_summaries now holds order:1, order:2 and order:4
DELETE FROM app.sales.orders WHERE META().id = "order:2";
-- order_summaries now holds order:1 and order:4  (OnDelete cascaded)
[{"id": "order:1", "customer": "customer:1", "total": 28.98}, {"id": "order:2", ...}, {"id": "order:4", ...}]
[{"id": "order:1"}, {"id": "order:4"}]

Observe the discipline this implies: the summary collection is a different keyspace from the source. A function that writes into its own source collection triggers itself, so Eventing refuses that binding.

Bindings: buckets, cURL, constants

  • Bucket binding — a keyspace mapped to a JavaScript variable (summaries above) in read-only or read-write mode. Access bypasses the SDK and is fast; a function must not write to its own source keyspace in a way that re-triggers itself.

  • cURL binding — a pre-registered, allow-listed external endpoint callable with curl() for notifications, webhooks, or enrichment from an API.

  • Constant binding — an injected configuration value available as a global.

Timers

// Schedule work for a future time from inside a handler.
function OnUpdate(doc, meta) {
  if (doc.type === 'reservation') {
    createTimer(sendReminder, new Date(doc.checkinDate), meta.id, { id: meta.id });
  }
}
function sendReminder(context) {
  curl('POST', notifyApi, { body: { reservation: context.id } });
}

Timers are durable and survive restarts, so Eventing handles scheduled and deferred work, not only immediate reactions. Their state is kept in the function’s metadata keyspace, which is why that keyspace must be separate from the source and must not be deleted while the function exists.

Feed boundary and deployment lifecycle

On deployment you choose a feed boundary: From now processes only mutations after deployment; From beginning (everything in the settings above) first replays every existing document through the handler, then tails new changes. The lifecycle is deploy → (pause / resume) → undeploy; pausing keeps the processing checkpoint, so resume does not re-process what was already seen.

stateDiagram-v2 [*] --> Undeployed Undeployed --> Deploying : deploy Deploying --> Deployed : workers started, feed running Deployed --> Paused : pause, checkpoint kept Paused --> Deployed : resume Deployed --> Undeployed : undeploy Paused --> Undeployed : undeploy

Typical uses, and DCP underneath

Common patterns are enrichment (fill a computed field), cascade delete, notifications, and maintaining a denormalised or aggregated view collection. All of these sit on the Database Change Protocol (DCP) — the ordered, per-vBucket stream of mutations with sequence numbers and rollback support that also feeds the Index service, Analytics shadowing, and XDCR. Eventing is the managed, in-cluster way to run code on that stream; an external consumer that needs the raw feed uses a DCP-based connector instead. For the same "act on every change" pattern in MongoDB, see MongoDB Change Streams.
