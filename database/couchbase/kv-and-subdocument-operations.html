Key-value & sub-document operations

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The key-value (KV) API is the fastest way in and out of Couchbase: it addresses one item by key and skips the query engine entirely. This page covers the connection path, the CRUD verbs, the atomic numeric and binary operations, and the sub-document API that reads or changes part of a document in a single round-trip.

Connecting: Cluster to Collection

Access always narrows through the same chain: a Cluster (a connection to the whole deployment) yields a Bucket, which yields a Scope, which yields a Collection. The default collection (_default scope, _default collection) exists in every bucket for backward compatibility.

Cluster cluster = Cluster.connect("couchbase://127.0.0.1", "appuser", "s3cr3t");
Bucket bucket = cluster.bucket("travel-sample");
bucket.waitUntilReady(Duration.ofSeconds(10));
Scope scope = bucket.scope("inventory");
Collection collection = scope.collection("airline");
# https://docs.couchbase.com/java-sdk/current/howtos/kv-operations.html

What the connect call does explains the speed of the KV path. The SDK opens a bootstrap connection, downloads the cluster map (which node owns which vBucket, and which services run where), opens one pooled connection per Data node, and from then on routes each operation directly to the right node:

sequenceDiagram participant App as Application participant SDK as SDK Cluster object participant N1 as Data node A participant N2 as Data node B App->>SDK: Cluster.connect(connection string) SDK->>N1: bootstrap, fetch cluster map N1-->>SDK: map of 1024 vBuckets to nodes App->>SDK: collection.get("customer::c-1") Note over SDK: CRC32(key) gives vBucket 244, owned by node B SDK->>N2: GET vBucket 244, collection ID, key N2-->>SDK: value, CAS, flags SDK-->>App: GetResult

A Cluster is expensive and thread-safe: create one per process and share it. After a rebalance or failover the server answers with a "not my vBucket" status carrying a newer map and the SDK retries transparently, so application code never handles topology.

The CRUD verbs

Operation Behavior

insert(id, value)

Create only. Fails with DocumentExistsException if the key already exists.

upsert(id, value)

Create or overwrite unconditionally.

replace(id, value)

Overwrite only. Fails with DocumentNotFoundException if the key is absent. Accepts a CAS for optimistic locking.

get(id)

Fetch the value and metadata. Fails with DocumentNotFoundException if absent.

remove(id)

Delete. Fails with DocumentNotFoundException if absent. Accepts a CAS.

exists(id)

Cheap existence check; returns a result whose exists() is a boolean, never throws for "not found".

getAndTouch(id, ttl)

Fetch the value and reset the expiry in one operation.

 
try {
    collection.insert("airline_1010", JsonObject.create().put("name", "40-Mile Air").put("iata", "Q5"));
} catch (DocumentExistsException e) {
    // key already present -- fall back to replace-with-CAS or upsert
}

GetResult r = collection.get("airline_1010");
JsonObject air = r.contentAsObject();
long cas = r.cas();

collection.replace("airline_1010", air.put("country", "United States"),
    ReplaceOptions.replaceOptions().cas(cas));   // fails with CasMismatchException if changed meanwhile

boolean present = collection.exists("airline_9999").exists();   // false, no exception
collection.remove("airline_1010");

Every operation takes an options object for timeout, durability, expiry, and CAS. Errors are typed: catch DocumentNotFoundException, DocumentExistsException, CasMismatchException, DurabilityImpossibleException, TimeoutException rather than inspecting status codes. See KV operations for the full result and error model, and Data Service fundamentals for how a KV request is routed.

A complete, runnable tour

The program below runs every verb above against the shop dataset. It needs the Java SDK on the class path (com.couchbase.client:java-client, version 3.7 was used) and a reachable node; the credentials are those of the development cluster built in What Couchbase Server is & how to run it. Its output follows, exactly as produced.

import com.couchbase.client.core.error.CasMismatchException;
import com.couchbase.client.core.error.DocumentExistsException;
import com.couchbase.client.core.error.DocumentNotFoundException;
import com.couchbase.client.core.error.subdoc.PathExistsException;
import com.couchbase.client.java.Bucket;
import com.couchbase.client.java.Cluster;
import com.couchbase.client.java.Collection;
import com.couchbase.client.java.json.JsonObject;
import com.couchbase.client.java.kv.GetResult;
import com.couchbase.client.java.kv.LookupInResult;
import com.couchbase.client.java.kv.LookupInSpec;
import com.couchbase.client.java.kv.MutateInSpec;
import com.couchbase.client.java.kv.ReplaceOptions;
import java.time.Duration;
import java.util.List;

public class Tour {
  public static void main(String[] args) {
    Cluster cluster = Cluster.connect("couchbase://127.0.0.1", "Administrator", "password");
    Bucket bucket = cluster.bucket("shop");
    bucket.waitUntilReady(Duration.ofSeconds(10));
    Collection customers = bucket.scope("sales").collection("customers");
    String key = "customer::c-100";

    // insert is create-only
    JsonObject doc = JsonObject.create().put("type", "customer").put("name", "Edsger Dijkstra").put("city", "Eindhoven");
    customers.insert(key, doc);
    try {
      customers.insert(key, doc);
    } catch (DocumentExistsException e) {
      System.out.println("second insert  -> DocumentExistsException");
    }

    // get, then replace guarded by the CAS that get returned
    GetResult r = customers.get(key);
    customers.replace(key, r.contentAsObject().put("city", "Nuenen"), ReplaceOptions.replaceOptions().cas(r.cas()));
    try {
      customers.replace(key, r.contentAsObject().put("city", "Waterloo"), ReplaceOptions.replaceOptions().cas(r.cas()));
    } catch (CasMismatchException e) {
      System.out.println("stale CAS      -> CasMismatchException");
    }

    // exists never throws; get does
    System.out.println("exists(nope)   -> " + customers.exists("customer::nope").exists());
    try {
      customers.get("customer::nope");
    } catch (DocumentNotFoundException e) {
      System.out.println("get(nope)      -> DocumentNotFoundException");
    }

    // sub-document: several paths mutated in one atomic call, one of them an extended attribute
    customers.mutateIn(key, List.of(
        MutateInSpec.upsert("loyalty.points", 10).createPath(),
        MutateInSpec.arrayAppend("tags", List.of("vip")).createPath(),
        MutateInSpec.arrayAddUnique("tags", "vip-2"),
        MutateInSpec.increment("loyalty.visits", 1).createPath(),
        MutateInSpec.upsert("audit.reviewedBy", "svc-audit").xattr().createPath()));
    try {
      customers.mutateIn(key, List.of(MutateInSpec.arrayAddUnique("tags", "vip")));
    } catch (PathExistsException e) {
      System.out.println("duplicate add  -> PathExistsException");
    }
    System.out.println("body           -> " + customers.get(key).contentAsObject());

    LookupInResult look = customers.lookupIn(key, List.of(
        LookupInSpec.get("name"),
        LookupInSpec.exists("email"),
        LookupInSpec.count("tags"),
        LookupInSpec.get("audit.reviewedBy").xattr()));
    System.out.println("lookupIn       -> name=" + look.contentAs(0, String.class)
        + " email.exists=" + look.exists(1)
        + " tags.count=" + look.contentAs(2, Integer.class)
        + " xattr=" + look.contentAs(3, String.class));

    customers.remove(key);
    cluster.disconnect();
  }
}
second insert  -> DocumentExistsException
stale CAS      -> CasMismatchException
exists(nope)   -> false
get(nope)      -> DocumentNotFoundException
duplicate add  -> PathExistsException
body           -> {"name":"Edsger Dijkstra","type":"customer","city":"Nuenen","loyalty":{"visits":1,"points":10},"tags":["vip","vip-2"]}
lookupIn       -> name=Edsger Dijkstra email.exists=false tags.count=2 xattr=svc-audit

Three details of that output are worth reading closely. The CasMismatchException is the optimistic-locking signal: the second replace used the CAS of a read that the first replace had already invalidated. The body shows that createPath() built the missing loyalty object, that a numeric increment on a missing path started from zero, and that the extended attribute written in the same mutateIn is not part of the body. And PathExistsException is the sub-document counterpart of DocumentExistsException: arrayAddUnique refuses to add a scalar that is already present, which is how a set is kept free of duplicates without reading it.

Atomic counters, binary append/prepend, range scan

increment / decrement atomically adjust an integer document held as an ASCII number. Both accept an initial value used only when the key does not yet exist, and a delta:

# Server-side atomic add; no read-modify-write race between clients
CounterResult c = collection.binary().increment("counter:visits",
    IncrementOptions.incrementOptions().initial(0).delta(1));
long current = c.content();

collection.binary().decrement("counter:seats-left",
    DecrementOptions.decrementOptions().initial(180).delta(2));
# https://docs.couchbase.com/java-sdk/current/howtos/kv-operations.html

Three successive increment calls with initial(100) and delta(1) returned 100, 101 and 102: the first call creates the counter at initial, later calls add delta.

append / prepend add bytes to the end or start of a non-JSON (binary/string) value. They must not be used on JSON documents — the result would not be valid JSON. For structured edits use the sub-document API below.

KV Range Scan (7.6) streams every key, or every key in a prefix, directly from the data service without an index. It is meant for background/export jobs, not low-latency request paths:

# Stream all keys beginning with "airline_" from the collection
ScanResult scan = collection.scan(ScanType.prefixScan("airline_"),
    ScanOptions.scanOptions().idsOnly(true));
scan.forEach(item -> process(item.id()));
# https://docs.couchbase.com/java-sdk/current/howtos/kv-operations.html

Against the shop data, a prefix scan on customer::c- returned the six matching keys (five customers plus the one inserted by the tour) without an index. This is the same mechanism that backs the sequential scan SQL++ falls back to when a keyspace has no index.

For throughput, the SDKs expose async (CompletableFuture) and reactive (Mono / Flux) variants of every KV call via collection.async() and collection.reactive(). A "bulk" operation is simply many async calls issued together and awaited as a batch — there is no separate multi-get wire command:

List<CompletableFuture<GetResult>> futures = keys.stream()
    .map(k -> collection.async().get(k))
    .collect(Collectors.toList());
CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();

The sub-document API

lookupIn (read) and mutateIn (write) operate on paths inside a JSON document, so the server sends or receives only the fragment involved instead of the whole value. This cuts bandwidth and, for mutateIn, removes the fetch-modify-store race: the change is applied server-side in one atomic step, optionally guarded by CAS.

Per-path operations:

Spec Effect

get / exists / count

Read a value at a path, test a path, or count an array/object at a path.

upsert / insert / replace / remove

Set, add-only, overwrite-only, or delete a field at a path.

arrayAppend / arrayPrepend / arrayInsert

Add elements at the end, start, or a given index of an array.

arrayAddUnique

Append a scalar only if it is not already present in the array.

increment / decrement

Atomically adjust a numeric field (sub-document counter).

 
# Read three fields (and one XATTR) without transferring the whole document
LookupInResult look = collection.lookupIn("airline_10", Arrays.asList(
    LookupInSpec.get("name"),
    LookupInSpec.get("country"),
    LookupInSpec.exists("icao"),
    LookupInSpec.get("$document.exptime").xattr()));   # virtual XATTR: server-computed expiry
String name = look.contentAs(0, String.class);
boolean hasIcao = look.exists(2);

# Mutate several paths in one atomic round-trip
collection.mutateIn("airline_10", Arrays.asList(
    MutateInSpec.upsert("updatedAt", Instant.now().toString()),
    MutateInSpec.arrayAddUnique("routes", "SFO-JFK"),
    MutateInSpec.increment("version", 1),
    MutateInSpec.upsert("audit.by", "svc-import").xattr().createPath()),
    MutateInOptions.mutateInOptions().cas(knownCas));
# https://docs.couchbase.com/java-sdk/current/howtos/subdocument-operations.html

createPath tells a mutation to create any missing intermediate objects along the path (so audit.by works even when audit did not exist). Adding .xattr() targets an Extended Attribute instead of the document body. A mutateIn can address at most 16 paths per call.

Why it matters: fetching a 200 KB document to change one timestamp and writing it back moves 400 KB over the wire and can lose a concurrent update. The equivalent mutateIn moves a few hundred bytes and cannot clobber fields it does not name. See Sub-Document operations for path syntax, macro values, and the per-path error model.

Why sub-document operations matter: a measured race

The claim that a sub-document mutateIn "cannot clobber fields it does not name" is easy to verify. Eight threads each add one to a views counter a hundred times, once with a read-modify-write of the whole document and once with a sub-document increment. The correct answer is 800 in both cases.

sequenceDiagram participant A as Thread A participant S as Server document participant B as Thread B A->>S: get, views = 7 B->>S: get, views = 7 A->>S: upsert views = 8 B->>S: upsert views = 8 Note over S: two increments, one counted A->>S: mutateIn increment views B->>S: mutateIn increment views Note over S: the server applies both, views = 10
JsonObject d = c.get("stats::naive").contentAsObject();                       // read
c.upsert("stats::naive", d.put("views", d.getInt("views") + 1));              // write back

c.mutateIn("stats::subdoc", List.of(MutateInSpec.increment("views", 1)));     // one atomic call
get + upsert   : 125 of 800
mutateIn incr  : 800 of 800

The first figure varies from run to run; the second does not. The get-then-upsert pattern loses updates whenever two clients interleave, and a CAS guard (the subject of Concurrency, locking & durable writes) would turn the silent loss into a retryable error. The sub-document call needs neither, because the server applies the increment to the current value.

Contrast with MongoDB

Couchbase’s mutateIn path operations play the role MongoDB’s update operators play: both change part of a document server-side without a client round-trip for the read. The main differences are that Couchbase addresses exactly one document by key (no query filter selects the target), a single mutateIn batches heterogeneous path ops with an optional CAS guard, and array de-duplication is an explicit arrayAddUnique rather than $addToSet. For the operator-update model and multi-document update semantics, see MongoDB Updating & Deleting.
