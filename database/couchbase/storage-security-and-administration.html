Storage internals, security & administration

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page covers the parts of Couchbase you tune and secure rather than write code against: how a mutation travels from RAM to disk, how access is authenticated and authorised, and the tools that build, back up, monitor, and automate a cluster.

The commands below were run against Couchbase Server 7.6.2 Enterprise in Docker, with the keyspace used throughout this section (bucket app, scope sales, collections orders and customers). Output blocks are the real results, trimmed to the relevant lines.

Storage internals

The Data service is memory-first. Every read and write goes through the managed cache, an in-process cache sized by the bucket’s RAM quota. Item metadata for every key is pinned in the cache at all times; values are held while there is room. The set of values currently in cache is the working set, and the share of items whose value is resident is the resident ratio. When the cache fills, the least-recently-used clean items are ejected (value dropped, metadata kept); a later read of an ejected key fetches its value from disk. A collapsing resident ratio is the primary signal that a bucket needs more RAM or a Magma backend.

sequenceDiagram participant C as Client participant MC as Managed cache (RAM) participant Q as Disk write queue participant FL as Flusher participant ST as Storage engine (disk) participant R as Replica and DCP consumers C->>MC: write (key, value) MC-->>C: acknowledged (non-durable write) MC->>Q: enqueue dirty item MC->>R: DCP mutation Q->>FL: batch of dirty items FL->>ST: append or write batch ST-->>FL: persisted FL->>MC: item now clean (can be ejected)

Writes are acknowledged from the cache and drained to disk asynchronously through the disk write queue. The queue absorbs bursts; a persistently long queue means disk cannot keep up with the write rate. Durable writes and cbbackupmgr care about what has drained — see Concurrency, locking & durable writes.

The health of this pipeline is readable from cbstats, which talks to the Data service port (11210) of a node. After loading a few hundred items into the 256 MB app bucket, the relevant counters were:

cbstats localhost:11210 -u Administrator -p password -b app all | grep -E \
  'vb_active_perc_mem_resident|ep_queue_size|ep_flusher_todo|ep_diskqueue_items|ep_max_size|ep_item_eviction_policy|ep_backend|curr_items:'
 curr_items:                       232
 ep_backend:                       couchdb
 ep_diskqueue_items:               0
 ep_flusher_todo:                  0
 ep_item_eviction_policy:          value_only
 ep_max_size:                      268435456
 ep_queue_size:                    0
 vb_active_perc_mem_resident:      100

Read them as the pipeline above: ep_queue_size and ep_flusher_todo are the items still waiting to be written (zero means the disk has caught up), ep_max_size is the bucket quota in bytes (256 MiB), vb_active_perc_mem_resident is the resident ratio of active vBuckets (100 percent: everything in RAM), and ep_item_eviction_policy is value_only, the Couchstore default that ejects values but keeps all metadata. The backend name couchdb is how the Couchstore engine identifies itself. The same figures are in the Web Console graphs and the /metrics endpoint described under Monitoring.

Two on-disk storage engines back a Couchbase bucket:

  • Couchstore — the default. One append-only B-tree file per vBucket; every mutation appends, so the file grows until compaction rewrites it without the stale blocks. Simple and fast when the data set is comfortably larger than RAM only by a small factor.

  • Magma — an LSM-style engine for large, dense data sets (a low target resident ratio, with much more data than RAM). It keeps far less metadata in RAM, writes more efficiently under heavy mutation, and compacts incrementally.

The engine is a per-bucket setting fixed at creation. The bucket information reports it, together with the vBucket count, the conflict-resolution type and the eviction policy:

# Choose the engine at bucket-create time (it cannot be changed later).
couchbase-cli bucket-create -c 10.0.0.1:8091 -u Administrator -p password \
  --bucket app --bucket-type couchbase --storage-backend magma \
  --bucket-ramsize 4096 --bucket-replica 1

curl -s -u Administrator:password http://10.0.0.1:8091/pools/default/buckets/app

Magma has a floor: asking for a Magma bucket with a 100 MiB quota is refused, and a 1024 MiB bucket is accepted.

ERROR: ramQuota - Ram quota for magma must be at least 1024 MiB

The same bucket-information call reported couchstore 1024 seqno valueOnly none (engine, vBuckets, conflict resolution, eviction policy, minimum durability) for the default bucket and magma 1024 for the Magma one (a 1024 MiB bucket, which needed the cluster memory quota raised first). That floor is the practical reason a small development bucket is Couchstore.

Ephemeral buckets skip the storage engine entirely — data lives only in the managed cache and its replicas, so a full-cluster restart loses it. They give predictable latency with no disk I/O and are suited to sessions, caches, and transient state; eviction is configured as noEviction (reject writes when full) or nruEviction (drop not-recently-used items).

couchbase-cli bucket-create -c 10.0.0.1:8091 -u Administrator -p password \
  --bucket sessions --bucket-type ephemeral --bucket-ramsize 100 \
  --bucket-eviction-policy nruEviction --bucket-replica 0

The bucket info for it reported ephemeral nruEviction and no storage backend, as expected.

Compaction reclaims the space that appended, superseded blocks leave behind. Auto-compaction triggers it per file once fragmentation crosses a threshold; it can also be scheduled for a quiet window.

# Cluster-wide auto-compaction at 30% database and 30% view fragmentation.
couchbase-cli setting-compaction -c 10.0.0.1:8091 -u Administrator -p password \
  --compaction-db-percentage 30 --compaction-view-percentage 30

The stored settings (GET /settings/autoCompaction) show the thresholds applied, and the separate magmaFragmentationPercentage (50 by default) that governs Magma:

{"autoCompactionSettings":{"parallelDBAndViewCompaction":false,"magmaFragmentationPercentage":50,
 "databaseFragmentationThreshold":{"percentage":30,"size":"undefined"},
 "viewFragmentationThreshold":{"percentage":30,"size":"undefined"}, ... }}

Deletes and expirations do not erase an item immediately; they write a tombstone (key + metadata, no value) so the removal can replicate to replicas and over XDCR. The metadata purge interval (per bucket, three days by default) is how long tombstones are retained before compaction sweeps them. Set it longer than the longest XDCR or replica outage you intend to survive, or a deletion can be purged before it replicates and the deleted item reappears at the destination.

couchbase-cli bucket-edit -c 10.0.0.1:8091 -u Administrator -p password \
  --bucket app --purge-interval 2

The bucket’s purgeInterval then read back as 2 (days).

DCP — the Database Change Protocol — is the single ordered mutation stream every downstream consumer reads: replicas, GSI, Search, Analytics, Eventing, XDCR, and the Kafka/Spark connectors. It replaced the older TAP protocol and adds restart-from-sequence-number so a consumer that disconnects resumes without a full resync.

After a restart a Data node performs warm-up: it loads all key metadata (and, depending on the engine and quota, values) back into the managed cache before the node reports healthy and starts serving. Warm-up time scales with item count, which is one reason Magma — with less resident metadata — restarts faster on large data sets. cbstats ... warmup reports its state and timings.

flowchart TD W[Write / mutation] --> MC[Managed cache in RAM] MC --> DWQ[Disk write queue] DWQ --> SE[(Storage engine: Couchstore or Magma)] MC --> DCP{{DCP stream}} SE --> DCP DCP --> RParts[Replica vBuckets] DCP --> GSI[Global secondary indexes] DCP --> FTS[Search service] DCP --> ANA[Analytics service] DCP --> XDCR[XDCR to remote cluster]
flowchart TD READ[Read a key] --> HIT{Value in managed cache?} HIT -->|yes| FAST[Return from RAM] HIT -->|no, ejected| FETCH[Background fetch from disk] FETCH --> LOAD[Load value into cache] LOAD --> FAST FULL[Cache above quota] --> EJ[Eject least-recently-used clean values] EJ --> META[Metadata stays resident] EJ --> MON[Resident ratio drops: add RAM or move to Magma]

The memory-first cache with an asynchronous drain and periodic compaction is the same shape as MongoDB’s WiredTiger cache plus checkpoints — see MongoDB WiredTiger — with Couchbase making the cache an explicit, quota-sized tier and exposing the resident ratio as a first-class health metric.

Security

Authorisation is role-based access control (RBAC). A user (or a group the user belongs to) is granted roles; each role is a privilege (read data, write data, run a query, manage a bucket, …​) optionally scoped to a bucket, scope, or collection. Couchbase ships a large set of built-in roles (51 on the 7.6.2 node used here, listed by GET /settings/rbac/roles) — data_reader, data_writer, query_select, bucket_admin, cluster_admin, security_admin_local, ro_admin, fts_searcher, eventing_admin, and many more — and custom roles cannot be defined, so least privilege is expressed by combining narrowly scoped built-in roles.

flowchart LR U[User: local or external] --> G[Group] U --> R1[Role: data_reader on app.sales.orders] G --> R2[Role: query_select on app.sales.orders] G --> R3[Role: query_insert on app.sales.orders] R1 --> P1[Privilege: read documents] R2 --> P2[Privilege: run SELECT] R3 --> P3[Privilege: run INSERT and UPSERT] P1 --> K[(Keyspace: bucket.scope.collection)] P2 --> K P3 --> K

The scoped-role syntax separates the bucket, scope and collection with colons: role[bucket:scope:collection] (a role scoped to a whole bucket is role[bucket], to a scope role[bucket:scope]). Writing the collection with a dot is rejected:

# A user that can read, write and query exactly one collection.
couchbase-cli user-manage -c 10.0.0.1:8091 -u Administrator -p password \
  --set --rbac-username appuser --rbac-password s3cretpw1 --auth-domain local \
  --roles 'data_reader[app:sales:orders],data_writer[app:sales:orders],query_select[app:sales:orders],query_insert[app:sales:orders]'
# SUCCESS: User appuser set

# Wrong separator -- refused:
#   --roles 'data_reader[app:sales.orders]'
# ERROR: roles - Cannot assign roles to user because the following roles are unknown,
#        malformed or role parameters are undefined: [data_reader[app:sales.orders]]

Note two details that surprise people. First, a key-value role and a query role are different privileges: data_reader and data_writer govern the KV API, while SQL++ needs query_select, query_insert, query_update, query_delete on the keyspace. Second, a grant is checked per statement. With only query_select on orders, the user was allowed to read its collection, and refused elsewhere with an error that names the missing role:

curl -u appuser:s3cretpw1 http://10.0.0.1:8093/query/service \
  --data-urlencode 'statement=SELECT COUNT(*) AS n FROM app.sales.orders'
# "results": [ { "n": 3 } ]

curl -u appuser:s3cretpw1 http://10.0.0.1:8093/query/service \
  --data-urlencode 'statement=SELECT COUNT(*) AS n FROM app.sales.customers'
# "errors":[{"code":13014,"msg":"User does not have credentials to run SELECT queries on
#   default:app.sales.customers. Add role query_select on default:app.sales.customers to allow
#   the statement to run.","reason":{"missing_role":"query_select","path":"default:app.sales.customers"}}]

# A SQL++ UPSERT with only data_writer + query_select:
# "errors":[{"code":13014,"msg":"User does not have credentials to run INSERT queries on
#   default:app.sales.orders. Add role query_insert on default:app.sales.orders to allow the
#   statement to run."...
-- The same grant, and its removal, from SQL++ (the keyspace needs no backticks unless a name has a hyphen).
GRANT query_select ON app.sales.customers TO appuser;
REVOKE query_select ON app.sales.customers FROM appuser;

After the GRANT, a read of the user’s roles (GET /settings/rbac/users/local/appuser) listed query_select on customers next to the existing ones, confirming the statement edits the same RBAC store as the CLI.

Authentication is either local (credentials stored in the cluster) or external:

  • LDAP — bind against a directory for password checks and map LDAP groups to Couchbase groups.

  • PAM — delegate to the host’s PAM stack (Linux users, etc.).

  • SAML SSO — browser single sign-on to the Web Console via an external IdP.

  • Client X.509 certificates — the client presents a certificate and Couchbase derives the username from a configured field (CN or a SAN), so no password crosses the wire.

couchbase-cli setting-ldap -c 10.0.0.1:8091 -u Administrator -p password \
  --authentication-enabled 1 --hosts ldap1.example.com --port 636 --encryption tls \
  --user-dn-query 'uid=%u,ou=people,dc=example,dc=com'

Transport security: enable TLS for client connections and, separately, node-to-node encryption so intra-cluster traffic (replication, rebalance, DCP) is also encrypted. --cluster-encryption-level strict refuses all non-TLS ports, and requires node-to-node encryption to be on first. Both commands refuse to run in the wrong order or with automatic failover enabled — real messages from the test cluster:

couchbase-cli node-to-node-encryption -c 10.0.0.1:8091 -u Administrator -p password --enable
# ERROR: Can't change network configuration when auto-failover is enabled.

couchbase-cli setting-security -c 10.0.0.1:8091 -u Administrator -p password \
  --set --cluster-encryption-level strict --tls-min-version tlsv1.2
# ERROR: clusterEncryptionLevel - Can't set cluster encryption level when cluster encryption is disabled.

So the working sequence is: switch automatic failover off, enable node-to-node encryption, raise the encryption level, then switch automatic failover back on:

couchbase-cli setting-autofailover -c 10.0.0.1:8091 -u Administrator -p password --enable-auto-failover 0
couchbase-cli node-to-node-encryption -c 10.0.0.1:8091 -u Administrator -p password --enable
couchbase-cli setting-security -c 10.0.0.1:8091 -u Administrator -p password \
  --set --cluster-encryption-level strict --tls-min-version tlsv1.2
couchbase-cli setting-autofailover -c 10.0.0.1:8091 -u Administrator -p password \
  --enable-auto-failover 1 --auto-failover-timeout 30 --max-failovers 1
# SUCCESS: Auto-failover settings modified / Switched node-to-node encryption on /
# SUCCESS: Security settings updated / SUCCESS: Auto-failover settings modified

Note that the minimum TLS version is spelt tlsv1.2 (not 1.2). Clients then connect with couchbases:// and the KV TLS port (11207), and the management API is on 18091; the strict level is what makes the plaintext ports refuse remote clients (node-local access over the loopback address remains allowed).

Encryption at rest (Enterprise Edition) protects the data files, typically layered with OS or volume encryption; it is linked from the disclaimer, not detailed here. Auditing records administrative and optionally data events to a rotating JSON log for review.

couchbase-cli setting-audit -c 10.0.0.1:8091 -u Administrator -p password \
  --set --audit-enabled 1 --audit-log-rotate-interval 86400
# SUCCESS: Audit settings modified

The _system scope is a reserved per-bucket scope Couchbase uses for internal collections (transactions, Eventing, mobile). Do not create application collections in it; RBAC on it is managed by the server.

Network hardening: bind admin ports to a management network, put client ports behind a firewall that allows only application subnets, and open only the ports a deployment actually uses (8091/18091 console, 11210/11207 KV, 8093/18093 Query, 8094 Search, plus the rest per service).

Security checklist:

  • Change the built-in Administrator password; create named admins with security_admin_local / cluster_admin instead of sharing it.

  • Give every application its own user with only the scoped data_reader / data_writer / query_* roles it needs; prefer groups over per-user grants.

  • Enable client TLS and node-to-node encryption; set cluster-encryption-level to strict once clients are migrated.

  • Use LDAP/PAM/SAML or X.509 for human and service identity; disable unused local accounts.

  • Turn on auditing and ship the audit log off-box.

  • Restrict admin and service ports at the network layer; keep encryption at rest on where required by policy.

  • Review roles after every schema or team change.

For the relational-database parallel, see MongoDB Security; the concepts (authentication sources, RBAC, TLS, auditing) line up, with Couchbase scoping roles down to the collection.

Administration & tooling

  • Web Console (:8091) — cluster setup, buckets, users, rebalance, XDCR, indexes, query workbench, and the built-in stats charts.

  • REST API — everything the console does is an HTTP endpoint under the same port; automation and the CLI are thin wrappers over it.

  • couchbase-cli — the administrative CLI used throughout this page (nodes, buckets, RBAC, XDCR, settings).

  • cbq — the interactive SQL++ shell for the Query service.

  • Couchbase Shell (cbsh) — a modern, scriptable shell that can drive multiple clusters and pipe results, covering both admin and data tasks; clusters are declared in its configuration file.

cbq -e couchbase://10.0.0.1 -u appuser -p s3cret
cbq -e http://localhost:8093 -u appuser -p s3cretpw1 -s 'SELECT META().id, META().cas FROM app.sales.orders LIMIT 2;'

The second line, run in the container, printed the connection banner, the statement, and a JSON result ("results": [ { "id": "order:1", "cas": ... }, ... ]); -s runs one statement and exits, which is the form to use in scripts.

Backup and restore is the Backup service (schedules and a repository, configurable in the console) with cbbackupmgr as its command-line form. cbbackupmgr does incremental, compressed, resumable backups and is the current tool; the earlier cbbackup, cbrestore, and cbtransfer utilities are removed from current releases and their use cases are covered by cbbackupmgr plus cbimport / cbexport.

flowchart LR CL[(Cluster)] -->|"cbbackupmgr backup (incremental)"| AR[(Archive / repo)] AR -->|"cbbackupmgr restore"| CL2[(Same or another cluster)] AR -->|"cbbackupmgr merge, remove"| AR SCHED[Backup service schedule] --> AR CL -->|"cbexport json"| FILE[JSON or CSV file] FILE -->|"cbimport json or csv"| CL2
cbbackupmgr config  --archive /backups --repo daily
cbbackupmgr backup  --archive /backups --repo daily \
  --cluster couchbase://10.0.0.1 --username Administrator --password password
cbbackupmgr restore --archive /backups --repo daily \
  --cluster couchbase://dr1.example.com --username Administrator --password password \
  --include-data app --force-updates

Run for real, config reported that the repository daily was created successfully, backup ended with Backup completed successfully, info listed one FULL backup that was Complete, and the restore reported the app bucket Succeeded with its mutations and deletions received (232 mutations, 12 deletions here, no errors). Note that the first backup of a repository is a full backup; later runs are incremental. Restore needs --force-updates when the destination already holds newer revisions of the same keys, because by default cbbackupmgr does not overwrite a document that has a higher revision.

Bulk import / export moves JSON and CSV between files and a collection. Both tools ran against the test node:

cbimport json --format lines -c couchbase://10.0.0.1 -u Administrator -p password \
  -b app --scope-collection-exp sales.orders -d file://orders.jsonl --generate-key %id%
# JSON `/tmp/orders.jsonl` imported to `couchbase://localhost` successfully
# Documents imported: 2 Documents failed: 0

cbexport json -c couchbase://10.0.0.1 -u Administrator -p password \
  -b app --scope-field _scope --collection-field _collection -f lines -o dump.jsonl
# JSON exported to `/tmp/dump.jsonl` successfully
# Documents exported: 232 Documents skipped: 0

cbexport with --scope-field / --collection-field adds those two fields to each exported line (for example {"_collection":"_default","_scope":"_default","name":"user 38"}) so that cbimport can route the documents back into the right collections. The %id% in --generate-key is a template: it builds the key from the id field of each JSON line, so the imported keys were order:101 and order:102.

Monitoring: GET /pools/default returns cluster and per-node health; the stats REST API and the per-service /metrics endpoint expose time series in Prometheus exposition format for scraping; cbstats reads low-level Data-service counters directly from a node; logs land under the install’s logs/ directory and named alerts (auto-failover fired, disk nearly full, metadata overhead high, IP changed) surface in the console and can be emailed.

curl -u Administrator:password http://10.0.0.1:8091/pools/default
curl -u Administrator:password http://10.0.0.1:8091/metrics
cbstats 10.0.0.1:11210 -u Administrator -p password -b app all

The /metrics lines for the test node, in the Prometheus text format (a metric name, a label set with the bucket, and a value):

kv_curr_items_tot{bucket="app"} 232
kv_curr_items_tot{bucket="sessions"} 0
kv_curr_items{bucket="app"} 232

/pools/default reports, for that node, status healthy, clusterMembership active and the service list ['cbas', 'eventing', 'fts', 'index', 'kv', 'n1ql']; the same endpoint is what Prometheus alert rules and load-balancer health checks usually poll.

The Autonomous Operator runs Couchbase on Kubernetes and OpenShift. A CouchbaseCluster custom resource declares size, per-node services, volumes, and backup schedules; the Operator reconciles the running cluster to it — performing adds, removes, rebalances, failovers, rolling upgrades, and scheduled backups without manual couchbase-cli steps.

kubectl get couchbaseclusters
kubectl describe couchbasecluster cb-example
