SQL++ data modification, functions & transactions

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page covers the write side of SQL++: the DML statements that change documents, the built-in and user-defined function library, and the distributed ACID transactions that let one unit of work span many documents and keyspaces.

Data modification: INSERT, UPSERT, UPDATE, DELETE, MERGE

Every SQL++ mutation identifies documents by key. INSERT and UPSERT take an explicit KEY / VALUE pair (or a SELECT that produces them); UPDATE, DELETE and MERGE locate documents by USE KEYS or by a WHERE predicate resolved through an index (DML statements).

-- INSERT fails if the key already exists
INSERT INTO main.sales.orders (KEY, VALUE)
VALUES ("order::o-100",
        { "type": "order", "userId": "u-1", "total": 42.00, "status": "OPEN" });

-- UPSERT writes or replaces, with no error on an existing key
UPSERT INTO main.sales.orders (KEY, VALUE)
VALUES ("order::o-100",
        { "type": "order", "userId": "u-1", "total": 42.00, "status": "OPEN" });

-- INSERT ... SELECT: derive the key and value from another keyspace
INSERT INTO main.sales.orderArchive (KEY k, VALUE o)
SELECT META(o).id AS k, o
FROM main.sales.orders AS o
WHERE o.status = "CLOSED";

SET and UNSET edit fields in place, including nested paths and array elements reached through a FOR clause; RETURNING echoes a projection of each mutated document:

UPDATE main.sales.orders AS o
USE KEYS "order::o-100"
SET o.status = "PAID",
    o.payment = { "method": "card", "at": NOW_STR() },
    o.lines[0].note = "gift wrap"
UNSET o.promoCode
RETURNING META(o).id, o.status;
-- predicate-driven UPDATE that rewrites array elements
UPDATE main.sales.orders AS o
SET l.price = l.price * 1.10 FOR l IN o.lines WHEN l.taxable = true END
WHERE o.status = "OPEN";
DELETE FROM main.sales.orders AS o
WHERE o.status = "ABANDONED" AND o.updatedAt < "2026-01-01"
RETURNING META(o).id;

MERGE applies updates, deletes and inserts to a target keyspace from a source in one statement:

MERGE INTO main.inventory.stock AS t
USING main.staging.delivery AS s
ON t.sku = s.sku
WHEN MATCHED THEN UPDATE SET t.qty = t.qty + s.qty
WHEN NOT MATCHED THEN INSERT (KEY s.sku,
  VALUE { "type": "stock", "sku": s.sku, "qty": s.qty });

For the relational treatment of the same operations, see SQL Data Modification.

Worked example: changing the shop

The statements below ran in sequence against the shop dataset; each result is the server’s answer. First, the difference between INSERT and UPSERT is the error:

INSERT INTO shop.sales.orders (KEY, VALUE) VALUES ("order::o-2000",
  {"type":"order","customerId":"customer::c-4","status":"OPEN","placedAt":"2026-04-01T10:00:00Z",
   "lines":[{"productId":"product::p-2","sku":"MS-200","qty":1,"price":24.50,"taxable":true}]});
-- success, mutationCount 1

INSERT INTO shop.sales.orders (KEY, VALUE) VALUES ("order::o-2000", {"x": 1});
-- error 12009: DML Error, possible causes include concurrent modification.
--   Failed to perform INSERT on key order::o-2000 - cause: Duplicate Key: order::o-2000

UPDATE with SET reaches nested paths, replaces a whole sub-object and drops a field with UNSET, and RETURNING shows the document as it was written:

UPDATE shop.sales.orders AS o USE KEYS "order::o-2000"
SET o.status = "PAID", o.payment = {"method":"card","at":"2026-04-01T10:05:00Z"}, o.lines[0].note = "gift wrap"
UNSET o.promoCode
RETURNING META(o).id, o.status, o.payment;
-- [{"id":"order::o-2000","status":"PAID","payment":{"at":"2026-04-01T10:05:00Z","method":"card"}}]

UNSET on a path that does not exist (promoCode here) is not an error. The FOR form of SET rewrites array elements that match a condition, here adding ten percent to the taxable lines of one customer’s paid orders:

UPDATE shop.sales.orders AS o
SET l.price = ROUND(l.price * 1.10, 2) FOR l IN o.lines WHEN l.taxable = true END
WHERE o.status = "PAID" AND o.customerId = "customer::c-4"
RETURNING o.lines;
-- [{"lines":[{"note":"gift wrap","price":26.95,"productId":"product::p-2","qty":1,"sku":"MS-200","taxable":true}]}]

INSERT ... SELECT copies documents between keyspaces, deriving the new key in the projection. This archives the cancelled order under a new key prefix; DELETE ... RETURNING then removes the rows it touched and says which:

INSERT INTO shop.sales.orders (KEY k, VALUE o)
SELECT "archive::" || META(o).id AS k, o FROM shop.sales.orders AS o WHERE o.status = "CANCELLED"
RETURNING META().id;
-- [{"id":"archive::order::o-1006"}]

DELETE FROM shop.sales.orders AS o WHERE META(o).id LIKE "archive::%" RETURNING META(o).id;
-- [{"id":"archive::order::o-1006"}]

MERGE is the right tool for a stock delivery: the source rows decide per product whether to update an existing stock count or insert a new product. A delivery of 10 keyboards (an existing SKU) and 5 of a new SKU:

MERGE INTO shop.sales.products AS t
USING shop.sales.deliveries AS s ON t.sku = s.sku
WHEN MATCHED THEN UPDATE SET t.stock = t.stock + s.qty
WHEN NOT MATCHED THEN INSERT (KEY "product::" || s.sku,
  VALUE {"type":"product","sku":s.sku,"name":"Unnamed " || s.sku,"price":0,"category":"new","tags":[],"stock":s.qty})
RETURNING META(t).id, t.stock;
-- [{"id":"product::WB-900","stock":5},{"id":"product::p-1","stock":50}]     (keyboards went from 40 to 50)

A MERGE action can also carry a condition and delete: WHEN MATCHED THEN DELETE WHERE t.category = "new" removed the new product again. The conditional goes in the trailing WHERE; there is no WHEN MATCHED AND ... form.

Functions

SQL++ ships a large built-in library (functions reference); the families that matter most for JSON:

  • Scalar — string (LOWER, SUBSTR, SPLIT, REGEXP_MATCHES), number (ROUND, TRUNC, ABS), date (NOW_STR, DATE_ADD_STR, DATE_DIFF_STR, MILLIS_TO_STR), type (TYPE, TONUMBER, TOSTRING, TOARRAY) and conditional (CASE, NVL, IFMISSING, IFMISSINGORNULL).

  • Array — ARRAY_LENGTH, ARRAY_APPEND, ARRAY_CONCAT, ARRAY_DISTINCT, ARRAY_FLATTEN, ARRAY_AGG, ARRAY_SUM, ARRAY_SORT.

  • Object — OBJECT_NAMES, OBJECT_VALUES, OBJECT_PAIRS, OBJECT_ADD, OBJECT_REMOVE, OBJECT_PUT.

  • Metadata and search — META() exposes id, cas, expiration and xattrs; SEARCH() and SEARCH_SCORE() push a predicate to a Full Text Search index from inside SQL++ — see Search, Analytics & Eventing.

SELECT META(h).id,
       META(h).cas,
       MILLIS_TO_STR(META(h).expiration * 1000) AS expires_at,
       ARRAY_LENGTH(h.public_likes) AS likes,
       OBJECT_NAMES(h.geo) AS geo_keys
FROM `travel-sample`.inventory.hotel AS h
LIMIT 3;
-- SEARCH() against an FTS index, scored and ordered
SELECT h.name, SEARCH_SCORE() AS score
FROM `travel-sample`.inventory.hotel AS h
WHERE SEARCH(h, "spa +country:France")
ORDER BY score DESC
LIMIT 10;

Run against the shop data, a mixed set of scalar, metadata and array functions gives:

SELECT SPLIT(c.email,"@")[1] AS domain, LOWER(c.email) AS e, SUBSTR(c.name,0,3) AS s3,
       NVL(c.tier,"n/a") AS tier, TOSTRING(c.schemaVersion) AS v
FROM shop.sales.customers c USE KEYS ["customer::c-3","customer::c-4"];
-- [{"domain":"Example.com","e":"grace@example.com","s3":"Gra","tier":"gold","v":"2"},
--  {"domain":"example.com","e":"linus@example.com","s3":"Lin","tier":"n/a","v":"1"}]

SELECT DATE_ADD_STR("2026-03-02T09:15:00Z", 7, "day") AS plus7,
       DATE_FORMAT_STR("2026-03-02T09:15:00Z","1111-11-11") AS d,
       DATE_DIFF_STR(NOW_STR(), "2026-03-02T09:15:00Z", "day") > 0 AS aged;
-- [{"plus7":"2026-03-09T09:15:00Z","d":"2026-03-02","aged":true}]

SELECT ARRAY_SORT(ARRAY_AGG(p.name)) AS names,
       ARRAY_SORT(ARRAY_DISTINCT(ARRAY_FLATTEN(ARRAY_AGG(p.tags), 1))) AS tags,
       MEDIAN(p.price) AS med
FROM shop.sales.products p;
-- [{"names":["27in Monitor","HDMI Cable","Mechanical Keyboard","Standing Desk","Wireless Mouse"],
--   "tags":["4k","adjustable","hdmi","mechanical","usb","wireless"],"med":89.9}]

ARRAY_AGG collects values into an array but takes no ORDER BY of its own in this release; sort the result with ARRAY_SORT. ARRAY_FLATTEN(..., 1) turns the array of tag arrays into one array and ARRAY_DISTINCT removes duplicates.

Aggregate and window functions. The aggregates (COUNT, SUM, AVG, MIN, MAX, ARRAY_AGG, MEDIAN, STDDEV) collapse a group; window functions compute a value per row over a moving frame without collapsing it (window functions). The OVER (PARTITION BY ... ORDER BY ...) clause, ROW_NUMBER, RANK, DENSE_RANK, NTILE, LAG, LEAD, FIRST_VALUE and running-aggregate frames all match SQL.

SELECT r.airline, r.sourceairport, r.distance,
       ROW_NUMBER() OVER (PARTITION BY r.airline ORDER BY r.distance DESC) AS rn,
       SUM(r.distance) OVER (PARTITION BY r.airline
                             ORDER BY r.distance DESC
                             ROWS UNBOUNDED PRECEDING) AS running_km
FROM `travel-sample`.inventory.route AS r
WHERE r.distance IS VALUED;

For the relational reference on both, see SQL Built-in Functions and SQL Aggregate & Window Functions.

User-defined functions extend the library (user-defined functions). An inline UDF wraps a SQL++ expression; an external UDF runs a JavaScript function stored in a library.

-- inline SQL++ UDF, scoped to a scope (bucket.scope.name)
CREATE OR REPLACE FUNCTION shop.sales.order_total(order_doc) {
  (SELECT RAW ROUND(SUM(l.price * l.qty), 2) FROM order_doc.lines AS l)[0]
};

SELECT shop.sales.order_total(o) AS total
FROM shop.sales.orders AS o
USE KEYS "order::o-1001";
-- [{"total":138.9}]

SELECT META(o).id AS id, shop.sales.order_total(o) AS total
FROM shop.sales.orders AS o ORDER BY id;
-- order::o-1001 138.9, order::o-1002 278.98, order::o-1003 420, order::o-1004 299.67, ...
-- external JavaScript UDF: the "discount" export of the "sales-lib" library
CREATE OR REPLACE FUNCTION shop.sales.discount(price, pct)
  LANGUAGE JAVASCRIPT AS "discount" AT "sales-lib";

The JavaScript library is uploaded through the Query service’s REST API, not through SQL++. A function that lives in a scope needs a library uploaded for that same scope; a library uploaded globally serves only global functions. The whole round trip, as run:

cat > lib.js <<'EOF'
function discount(price, pct) { return Math.round(price * (100 - pct)) / 100; }
EOF
curl -s -u Administrator:password -X POST \
  'http://localhost:8093/evaluator/v1/libraries/sales-lib/buckets/shop/scopes/sales' \
  --data-binary @lib.js -H 'Content-Type: text/plain'

CREATE OR REPLACE FUNCTION shop.sales.discount(price, pct) LANGUAGE JAVASCRIPT AS "discount" AT "sales-lib";
SELECT shop.sales.discount(p.price, 15) AS sale FROM shop.sales.products p USE KEYS "product::p-4";
-- [{"sale":357}]          (the standing desk, 420.00 less 15 percent)

system:functions lists the functions with their language (inline or javascript). An inline function is expanded into the calling statement and is optimised with it, so prefer it where an expression will do.

Distributed ACID transactions

Couchbase runs multi-document, multi-keyspace ACID transactions across the cluster (transactions). Two front ends drive the same engine.

SDK lambda API. transactions.run(ctx -> { ... }) takes a closure; the SDK retries the whole closure on a transient conflict and commits when it returns normally:

cluster.transactions().run(ctx -> {
    var from = ctx.get(accounts, "acct::a-1");
    var to   = ctx.get(accounts, "acct::a-2");
    var fromDoc = from.contentAsObject().put("balance",
                     from.contentAsObject().getInt("balance") - 100);
    var toDoc   = to.contentAsObject().put("balance",
                     to.contentAsObject().getInt("balance") + 100);
    ctx.replace(from, fromDoc);
    ctx.replace(to, toDoc);
    // no explicit commit: returning commits, throwing rolls back
});

SQL++ statements. BEGIN WORK (or SET TRANSACTION) opens one, SAVEPOINT and ROLLBACK TO SAVEPOINT mark partial undo points, COMMIT WORK / ROLLBACK WORK end it:

BEGIN WORK;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

UPDATE main.bank.account USE KEYS "acct::a-1" SET balance = balance - 100;
SAVEPOINT s1;
UPDATE main.bank.account USE KEYS "acct::a-2" SET balance = balance + 100;

COMMIT WORK;

Isolation. Transactions provide Read Committed isolation: a statement never sees another transaction’s uncommitted writes, and reads inside the transaction see its own earlier writes.

How it works. Each transaction owns an Active Transaction Record (ATR) — one of a fixed set of up to 1024 ATR documents per collection that tracks transaction state (PENDING, COMMITTED, ABORTED). Each mutated document is staged in its extended attributes (XATTRs), not its body, with a pointer to the owning ATR. The single atomic write that flips the ATR entry to COMMITTED is the commit point; asynchronous cleanup then copies staged content into document bodies and removes the staging. A reader that meets a still-staged document consults the ATR and either ignores the stage (not yet committed) or reads the staged value forward (committed, cleanup pending).

stateDiagram-v2 [*] --> Pending: create ATR entry Pending --> Staged: write docs into XATTRs, ATR = PENDING Staged --> Staged: further mutations staged Staged --> Committed: atomic ATR flip to COMMITTED (commit point) Staged --> Aborted: conflict / error / explicit ROLLBACK Committed --> Completed: async cleanup unstages into doc bodies Aborted --> RolledBack: async cleanup discards staged content Completed --> [*] RolledBack --> [*]

Durability. A transaction carries a durability level — MAJORITY (the default), MAJORITY_AND_PERSIST_TO_ACTIVE, or PERSIST_TO_MAJORITY — applied to both the staged writes and the commit, so an acknowledged commit survives node loss to the same degree as a durable KV write. See Concurrency, locking & durability.

Limits. A staged document must stay under 10 MB (below the 20 MB KV ceiling, because of staging overhead); cluster nodes must be NTP-synchronised for correct cleanup timing; the default transaction timeout is 15 seconds; and DDL is not transactional. Durability needs a cluster that can actually hold the replicas the bucket asks for — see the measurements in the worked example below.

Contrast with a hand-rolled two-phase commit. Before native transactions, spanning two documents meant the application emulating a two-phase commit by hand: a separate "transaction" document holding the participant keys and a state field, per-participant pending markers written and then cleared, and a recovery job that scanned for stuck transaction documents to roll them forward or back. It worked, but it pushed atomicity, isolation and crash recovery into application code, and forced every reader to understand the pending markers. The native engine keeps the same moving parts — a transaction record, staged mutations, a recovery sweep — inside the server, behind transactions.run(...). For the same feature elsewhere see SQL Transactions and MongoDB Transactions.

Worked example: moving money between two accounts

Two documents in the accounts collection of the shop bucket — account::a-1 with balance 500 and account::a-2 with balance 100 — are the classic case that needs a transaction: the two updates must both happen or neither must.

import com.couchbase.client.java.Bucket;
import com.couchbase.client.java.Cluster;
import com.couchbase.client.java.Collection;
import com.couchbase.client.java.json.JsonObject;
import com.couchbase.client.java.transactions.TransactionGetResult;
import com.couchbase.client.java.transactions.error.TransactionFailedException;
import java.time.Duration;

public class Transfer {
  public static void main(String[] args) {
    Cluster cluster = Cluster.connect("couchbase://127.0.0.1", "Administrator", "password");
    Bucket bucket = cluster.bucket("shop");
    bucket.waitUntilReady(Duration.ofSeconds(10));
    Collection accounts = bucket.scope("sales").collection("accounts");
    show(accounts, "before");

    // 1. the lambda commits when it returns normally
    cluster.transactions().run(ctx -> {
      TransactionGetResult from = ctx.get(accounts, "account::a-1");
      TransactionGetResult to = ctx.get(accounts, "account::a-2");
      JsonObject f = from.contentAsObject();
      JsonObject t = to.contentAsObject();
      ctx.replace(from, f.put("balance", f.getInt("balance") - 50));
      ctx.replace(to, t.put("balance", t.getInt("balance") + 50));
    });
    show(accounts, "after commit");

    // 2. an exception inside the lambda rolls every staged change back
    try {
      cluster.transactions().run(ctx -> {
        TransactionGetResult from = ctx.get(accounts, "account::a-1");
        ctx.replace(from, from.contentAsObject().put("balance", -999));
        throw new RuntimeException("insufficient funds");
      });
    } catch (TransactionFailedException e) {
      System.out.println("rolled back: " + e.getCause().getMessage());
    }
    show(accounts, "after rollback");
    cluster.disconnect();
  }

  static void show(Collection c, String label) {
    System.out.println(label + ": a-1=" + c.get("account::a-1").contentAsObject().getInt("balance")
        + " a-2=" + c.get("account::a-2").contentAsObject().getInt("balance"));
  }
}
before: a-1=500 a-2=100
after commit: a-1=450 a-2=150
rolled back: insufficient funds
after rollback: a-1=450 a-2=150

The same transfer through the Query service. SAVEPOINT marks a point inside the transaction, and ROLLBACK TO SAVEPOINT undoes only what came after it:

BEGIN WORK;
UPDATE shop.sales.accounts USE KEYS "account::a-1" SET balance = balance - 100;
SAVEPOINT s1;
UPDATE shop.sales.accounts USE KEYS "account::a-2" SET balance = balance + 100;
ROLLBACK TO SAVEPOINT s1;
SELECT META(c).id, c.balance FROM shop.sales.accounts c ORDER BY META(c).id;
-- account::a-1 400    account::a-2 100      (the second update is undone, the first remains)
ROLLBACK WORK;
SELECT META(c).id, c.balance FROM shop.sales.accounts c ORDER BY META(c).id;
-- account::a-1 500    account::a-2 100      (everything undone)

BEGIN WORK;
UPDATE shop.sales.accounts USE KEYS "account::a-1" SET balance = balance - 100;
UPDATE shop.sales.accounts USE KEYS "account::a-2" SET balance = balance + 100;
COMMIT WORK;
SELECT META(c).id, c.balance FROM shop.sales.accounts c ORDER BY META(c).id;
-- account::a-1 400    account::a-2 200

The statements ran through cbq, which keeps the transaction identifier (txid) between statements; over raw REST every statement after BEGIN WORK must send that txid. Each response inside a transaction also reports transactionElapsedTime and transactionRemainingTime (about 14.99 seconds at the start, from the default 15 second timeout).

sequenceDiagram participant App as Application participant A1 as Document a-1 participant ATR as ATR entry participant A2 as Document a-2 App->>ATR: create entry, state PENDING App->>A1: stage new balance in xattr txn App->>A2: stage new balance in xattr txn App->>ATR: set state COMMITTED Note over ATR: commit point, atomic App->>A1: unstage into the body App->>A2: unstage into the body App->>ATR: set state COMPLETED, remove entry

What durability a transaction needs from the cluster

The durability level of a transaction is applied to every staged write and to the commit. Whether it can be met depends on the replicas the bucket is configured with, and the difference was measured on a single-node cluster:

Bucket replicas Transaction durability Result

0

default (MAJORITY)

committed — the active copy is the whole majority

1 (no second node exists)

default (MAJORITY)

TransactionFailedException, cause DurabilityImpossibleException: "With the current cluster configuration, the requested durability guarantees are impossible"

1 (no second node exists)

NONE

committed

A plain durable KV write behaves the same way on the replicated bucket: durability(MAJORITY) fails with DurabilityImpossibleException, while a write with no durability requirement succeeds. The lesson is that a bucket configured for replicas on a cluster too small to host them cannot accept durable writes or transactions at the default level; fix the topology rather than weakening the level in production. In a development container, either create the bucket with --bucket-replica 0 or lower the transaction level at connection time:

Cluster lax = Cluster.connect("couchbase://127.0.0.1", ClusterOptions.clusterOptions("Administrator", "password")
    .environment(env -> env.transactionsConfig(TransactionsConfig.durabilityLevel(DurabilityLevel.NONE))));

Do you need a transaction at all?

flowchart TD a{"Does the change touch more than one document?"} -->|no| single["One KV or sub-document mutation: already atomic"] a -->|yes| b{"Can the data be embedded in one document?"} b -->|yes| embed["Embed it: single-document atomicity, no transaction"] b -->|no| c{"Must all documents change together or not at all?"} c -->|no| eventual["Independent writes, retry and reconcile"] c -->|yes| tx["Use a distributed transaction"]

Transactions cost latency (a transaction writes the staged documents, an ATR entry and then unstages), contend on the documents they stage and expire after the timeout, so they are the tool for the few operations that genuinely span documents — a transfer, an order that reserves stock — and not a default for every write.
