SDKs, connectors & Couchbase Mobile

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Applications reach Couchbase through a language SDK; data-integration pipelines use the connectors; and offline-capable apps use Couchbase Mobile. All three speak the same KV, query, and DCP protocols the server exposes.

flowchart LR subgraph APP[Application process] CODE[Your code] --> SDKAPI[SDK API: Cluster, Bucket, Scope, Collection] SDKAPI --> CORE[SDK core: cluster map, pools, retries, timeouts] end CORE -->|KV binary protocol 11210 / 11207| DATA[(Data nodes)] CORE -->|HTTP 8093 / 18093| QUERY[Query nodes] CORE -->|HTTP 8094| SEARCH[Search nodes] CORE -->|HTTP 8095| ANALYTICS[Analytics nodes] CORE -->|HTTP 8091 / 18091| MGMT[Management and config]

The examples run against the same Couchbase Server 7.6.2 node as the rest of this section (bucket app, scope sales, collection orders), through the Python SDK 4.x and the Java SDK 3.7, so the error names and outputs below are observed, not paraphrased.

The SDK family

Couchbase publishes SDKs for Java, .NET, Node.js, Python, Go, C, PHP, Ruby, Scala, and Kotlin. Since the 3.x generation they share one API shape — the names and object model are the same across languages, so a pattern learned in one transfers:

  • Cluster — the connection to the whole cluster and the entry point for cluster-level work (SQL++ queries, Search, Analytics, management APIs).

  • Bucket → Scope → Collection — the data hierarchy; Collection carries the KV and sub-document operations.

  • Options objects (GetOptions, QueryOptions, …​) carry per-operation settings; a cluster environment carries process-wide defaults.

The generation matters when reading older material: the first-generation books on the bibliography use the 2.x API (a Bucket opened straight from the cluster, CouchbaseCluster.create, JsonDocument objects, bucket.get("id") returning null for a missing key, view queries as the secondary-index mechanism). Current SDKs make Cluster.connect the entry point, address data as bucket.scope(...).collection(...), throw a typed exception for a missing key instead of returning null, and replace views with SQL++ and GSI (see Indexing with the Index service).

The connection string names seed nodes and the scheme: couchbase:// for plaintext, couchbases:// for TLS, optionally a DNS SRV hostname that expands to the seed list. Credentials and environment tuning go in ClusterOptions.

// Create the Cluster ONCE per process and share it. It is thread-safe, holds the
// connection pool, and refreshes the cluster map on topology changes.
Cluster cluster = Cluster.connect(
    "couchbases://db1.example.com,db2.example.com",
    ClusterOptions.clusterOptions("appuser", "s3cret").environment(env -> env
        .timeoutConfig(tc -> tc
            .kvTimeout(Duration.ofMillis(2500))
            .queryTimeout(Duration.ofSeconds(15)))
        .ioConfig(io -> io.numKvConnections(4))));

Bucket bucket = cluster.bucket("app");
bucket.waitUntilReady(Duration.ofSeconds(10));
Collection orders = bucket.scope("sales").collection("orders");

The same bootstrap in Python, where the timeouts live in ClusterTimeoutOptions:

from datetime import timedelta
from couchbase.cluster import Cluster
from couchbase.options import ClusterOptions, ClusterTimeoutOptions
from couchbase.auth import PasswordAuthenticator

opts = ClusterOptions(PasswordAuthenticator("appuser", "s3cret"),
    timeout_options=ClusterTimeoutOptions(kv_timeout=timedelta(milliseconds=2500),
                                          query_timeout=timedelta(seconds=15)))
cluster = Cluster("couchbase://db1.example.com", opts)
cluster.wait_until_ready(timedelta(seconds=10))     # waits for the cluster map and services
orders = cluster.bucket("app").scope("sales").collection("orders")
print(sorted(s.value for s in cluster.ping().endpoints))

The ping of the test cluster listed every service that answered: ['analytics', 'eventing', 'key_value', 'management', 'query', 'search', 'view'].

sequenceDiagram participant App as Application participant SDK as SDK core participant Seed as Seed node participant Data as Data node App->>SDK: Cluster.connect(connection string, credentials) SDK->>Seed: bootstrap (HTTP or KV), authenticate Seed-->>SDK: cluster map and service endpoints App->>SDK: cluster.bucket("app").waitUntilReady() SDK->>Data: open KV connection, select bucket Data-->>SDK: ready App->>SDK: collection.get(key) SDK->>Data: GET (vBucket from key hash) Data-->>App: value

Connection pooling is automatic: the SDK opens a small, fixed number of KV connections per node (numKvConnections, default 1) and multiplexes all operations over them, plus HTTP pools for Query/Search. Creating a Cluster per request instead of reusing one is the most common performance bug — each Cluster.connect re-runs discovery and rebuilds pools.

Timeouts are set per operation class (KV, query, view, management) with a default from the environment and an override on the options object. Every operation has a deadline; when it passes, the call fails with a TimeoutException.

The retry / error model

The retry / error model splits failures in two:

  • Deterministic errors (DocumentNotFoundException, DocumentExistsException, CasMismatchException, auth failures) are returned immediately — retrying cannot change the outcome.

  • Transient errors (temporary out-of-memory, "not-my-vBucket" during a rebalance, a locked item, connection blips) are retried automatically by the SDK’s best-effort retry strategy until the operation’s timeout.

flowchart TD OP[Operation sent] --> R{Result} R -->|success| OK[Return result] R -->|deterministic error| DET[Throw typed exception now] R -->|retryable error: locked, not-my-vbucket, tmpfail| RT{Deadline passed?} RT -->|no| BACK[Back off, refresh map if needed, resend] BACK --> OP RT -->|yes| TO{Operation idempotent or read?} TO -->|yes| UT[UnambiguousTimeoutException] TO -->|no, a write may have run| AT[AmbiguousTimeoutException]

Running a handful of failing calls against the live cluster with the Python SDK produced this table of what is thrown and when:

orders.get("order:nope")                                    # missing key
orders.insert("order:4", {})                                # key exists
orders.replace("order:nope", {})                            # replace of a missing key
orders.get("order:4", GetOptions(timeout=timedelta(microseconds=1)))
bucket.scope("sales").collection("nope").get("x")           # unknown collection
list(cluster.query("SELEC 1"))                              # malformed SQL++
Cluster(..., ClusterOptions(PasswordAuthenticator("Administrator", "wrong")))   # bad password
get missing                -> DocumentNotFoundException
insert existing            -> DocumentExistsException
replace missing            -> DocumentNotFoundException
read with 1 us deadline    -> UnAmbiguousTimeoutException
unknown collection         -> UnAmbiguousTimeoutException
query syntax error         -> ParsingFailedException
wrong password             -> AuthenticationException

Two behaviours are worth remembering. The first is the unknown collection: the SDK cannot tell a collection that does not exist yet from one whose id it has not learned, so it keeps retrying until the timeout and reports an unambiguous timeout, not a "collection not found" error. A typo in a collection name therefore looks like a slow, timing-out operation; check the name when you see a timeout on every call to one keyspace. The second is the locked item. In the Java SDK a mutation of an item held by getAndLock is retried until the timeout, then fails as an AmbiguousTimeoutException whose message lists the retry reason KV_LOCKED; the Python SDK surfaces the same case as DocumentLockedException (see Concurrency, locking & durable writes).

try {
    GetResult r = orders.get("order:1");
} catch (DocumentNotFoundException e) {
    // deterministic -- handle "missing", do not retry
} catch (UnambiguousTimeoutException e) {
    // the operation never ran: safe to retry any operation
} catch (AmbiguousTimeoutException e) {
    // a write may or may not have been applied: retry only if idempotent, or read back first
}

In Java the two timeout classes are subclasses of TimeoutException; the SDK throws the ambiguous one only when the operation was a non-idempotent mutation that might have reached the server. The Java version of the experiment produced DocumentNotFoundException, DocumentExistsException and UnambiguousTimeoutException (a one-nanosecond deadline on a read) for the three cases above that overlap. Full driver list and per-language guides: Couchbase SDKs.

For queries the scan consistency option decides whether a query statement waits for in-flight mutations to be indexed. The default (not_bounded) returns immediately from whatever the index has; request_plus waits until all mutations made before the request are indexed. See Querying with SQL++ for the trade-off; the SDK sets it through QueryOptions.

from couchbase.options import QueryOptions
from couchbase.n1ql import QueryScanConsistency

rows = cluster.query(
    "SELECT o.status, COUNT(*) AS n FROM app.sales.orders o GROUP BY o.status ORDER BY o.status",
    QueryOptions(timeout=timedelta(seconds=5), scan_consistency=QueryScanConsistency.REQUEST_PLUS))
print(list(rows.rows()))
[{'n': 2}, {'n': 2, 'status': 'NEW'}, {'n': 3, 'status': 'PAID'}]

The first row has no status: two documents in the collection carry none, and a GROUP BY keeps the missing-value group as its own row.

Big-data connectors

Purpose-built connectors move data between Couchbase and other systems using DCP, so they see every mutation in order:

  • Kafka connector — a Kafka Connect plugin. The source streams DCP mutations into Kafka topics; the sink writes Kafka records back into Couchbase. Kafka connector docs.

  • Spark connector — exposes buckets, collections, SQL++ queries, and DCP as Spark DataFrame/Dataset/DStream sources and sinks for batch and streaming jobs. Spark connector docs.

  • Elasticsearch connector — replicates documents from Couchbase into Elasticsearch indices via DCP, with checkpointing and restart. Elasticsearch connector docs.

flowchart LR CB[(Couchbase: app.sales.orders)] -->|DCP stream| KS[Kafka source connector] KS --> TOPIC[(Kafka topic cb.orders)] TOPIC --> CONS[Downstream consumers] TOPIC --> KSINK[Kafka sink connector] KSINK -->|upsert| CB2[(Couchbase: another cluster or collection)] CB -->|DCP stream| SP[Spark connector: batch and streaming jobs] CB -->|DCP stream| ES[Elasticsearch connector] ES --> ESI[(Elasticsearch index)]
# Kafka source connector: DCP mutations from one collection into a topic.
name=cb-orders-source
connector.class=com.couchbase.connect.kafka.CouchbaseSourceConnector
tasks.max=2
couchbase.seed.nodes=db1.example.com
couchbase.username=kafka
couchbase.password=s3cret
couchbase.bucket=app
couchbase.scope=sales
couchbase.collections=sales.orders
couchbase.topic=cb.orders
couchbase.stream.from=SAVED_OFFSET_OR_BEGINNING

The delivery semantics follow DCP: mutations of one document arrive in order (they share a vBucket, hence a Kafka partition key), and a restart resumes from the connector’s saved offsets, so processing is at least once. Consumers must tolerate a repeated record. Give the connector’s user only the data_dcp_reader and data_reader roles it needs.

Hand-rolling an Elasticsearch sync (polling for changes, pushing documents) is superseded on both ends: the Elasticsearch connector handles the streaming and checkpointing, and for search inside Couchbase the built-in Search service indexes the same documents with no second system to run — see Search, Analytics & Eventing. (Pro Couchbase Server and Pro Couchbase Development both spend chapters on the Elasticsearch plugin of the 2.x/3.x era; the current design is a standalone connector application, and the Search service has absorbed most of the use case.)

Couchbase Mobile

Couchbase Mobile extends the database to phones, desktops, and edge devices with an embedded database that syncs back to a cluster. On Apple platforms, the first-party alternatives are SwiftData and Core Data with CloudKit, which sync through the user’s iCloud account instead of a server you run.

flowchart LR subgraph DEVICE[Device] APPD[App] --> CBL[(Couchbase Lite database)] CBL --> REP[Replicator] end REP <-->|WebSocket, push and pull| SG[Sync Gateway or App Services] SG <-->|KV and DCP| CBS[(Couchbase Server bucket)] REP <-.->|peer-to-peer, no gateway| PEER[Another Couchbase Lite device] EDGE[Edge Server] <-->|replication| SG CLIENT[REST clients and other apps] --> CBS

Couchbase Lite

Couchbase Lite is a full database that runs in the application process (iOS, Android, Java, .NET, C, JavaScript/React Native). It stores JSON documents locally, works fully offline, and syncs when a connection is available. For how it compares with the other on-device storage options in a React Native app, see Storage and Offline.

// Couchbase Lite (Java) -- open a local database and do CRUD.
Database db = new Database("app");
Collection orders = db.createCollection("orders", "sales");

MutableDocument doc = new MutableDocument("order:1")
    .setString("status", "OPEN")
    .setDouble("total", 28.98);
orders.save(doc);

Document read = orders.getDocument("order:1");

The same collection and scope names as the server keyspace (sales.orders) are used on the device, so a document written on the phone lands in the server’s app.sales.orders when the replicator is pointed at the matching collection.

Queries use either SQL++ strings or the fluent QueryBuilder API; both run entirely on-device:

// SQL++ string form
Query q1 = db.createQuery(
    "SELECT META().id, total FROM sales.orders WHERE status = 'OPEN' ORDER BY total DESC");

// QueryBuilder form
Query q2 = QueryBuilder
    .select(SelectResult.expression(Meta.id), SelectResult.property("total"))
    .from(DataSource.collection(orders))
    .where(Expression.property("status").equalTo(Expression.string("OPEN")));

ResultSet rs = q1.execute();

Couchbase Lite also supports on-device full-text search (a MATCH index over document fields) and, in current releases, on-device vector search for similarity queries against locally stored embeddings — both run without a network round-trip.

The replicator moves changes between the local database and a Sync Gateway (or a peer). It is configured with an endpoint, a direction (push, pull, or both), continuous or one-shot mode, an authenticator, and the collections to sync:

ReplicatorConfiguration cfg = new ReplicatorConfiguration(
        new URLEndpoint(new URI("wss://sg.example.com:4984/app")))
    .addCollection(orders, null)
    .setType(ReplicatorType.PUSH_AND_PULL)
    .setContinuous(true)
    .setAuthenticator(new BasicAuthenticator("appuser", "s3cret".toCharArray()));

Replicator repl = new Replicator(cfg);
repl.addChangeListener(change -> { /* observe progress / errors */ });
repl.start();

When both sides changed the same document, the replicator resolves the conflict on the device: the default resolver keeps a deleted revision if one side deleted the document, otherwise the revision with the most changes (with a deterministic tie-break), and a custom ConflictResolver can merge fields instead. Nothing is lost silently, because both revisions are available to the resolver.

sequenceDiagram participant D1 as Device 1 participant SG as Sync Gateway participant D2 as Device 2 D1->>SG: push order:1 revision 2-a SG-->>D1: accepted D2->>SG: push order:1 revision 2-b (edited offline) SG-->>D2: conflict, server holds 2-a D2->>D2: conflict resolver merges 2-a and 2-b into 3-c D2->>SG: push order:1 revision 3-c SG-->>D1: pull order:1 revision 3-c

Sync Gateway

Sync Gateway is the server tier between Couchbase Lite clients and a Couchbase cluster. Its model:

  • Channels — every document is tagged with one or more channels; a client pulls only the channels it is granted. Channels are how a data set is partitioned per user or per tenant.

  • The sync function — a JavaScript function run on every incoming write. It validates the document, assigns it to channels, and grants users or roles access to channels.

  • Access control & authentication — users and roles live in Sync Gateway or an external provider (OIDC); the sync function’s requireUser / requireRole / access calls enforce per-document authorisation.

  • Replication & Delta Sync — clients replicate over WebSocket; Delta Sync sends only the changed fields of an updated document instead of the whole body, cutting bandwidth for large documents.

function (doc, oldDoc, meta) {
  if (!doc.region) { throw({forbidden: "missing region"}); }
  requireUser(doc.owner);
  channel("region-" + doc.region);
  access(doc.owner, "region-" + doc.region);
}

Read the sync function line by line: the first line rejects a write (the client sees a 403), the second requires the authenticated user to be the document’s owner, channel(...) routes the document into a channel that other users may pull, and access(...) grants the owner pull access to that channel. The function runs for every write, so keep it cheap and free of side effects: it cannot read other documents, only the incoming doc, the previous revision oldDoc and the metadata.

Sync Gateway keeps its own sync metadata in the bucket next to the document (and, with XDCR, replicates it); it needs a bucket user with the mobile_sync_gateway role, which exists among the built-in roles of a current server.

App Services, Edge Server & peer-to-peer

  • Capella App Services — the fully managed equivalent of Sync Gateway, run as part of Couchbase’s Capella cloud; same channel / sync-function / access model without operating the tier yourself.

  • Couchbase Edge Server — a lightweight single-node data + sync server for edge and on-premises sites (retail store, vehicle, factory floor). It serves a local REST API and replicates upstream to a cluster or App Services. Edge Server introduction.

  • Peer-to-peer sync — Couchbase Lite devices replicate directly to each other over a local network (one peer acts as listener, others connect) with no gateway, for collaboration that must keep working with no internet path.

For the API these mobile pieces sit under — SQL++, sub-document operations, the connection string — start from the Couchbase getting-started page, and compare the change-streaming model with MongoDB replica sets for the server-side side of sync.
