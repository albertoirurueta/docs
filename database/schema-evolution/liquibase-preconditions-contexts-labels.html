Liquibase: Preconditions, Contexts & Labels

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Three mechanisms decide whether a changeset runs on a given database: preconditions look at the state of the database, contexts and labels look at what the person running Liquibase asked for. They are evaluated in that combination for every pending changeset:

flowchart TD Start["Pending changeset"] --> Applied{"Already in DATABASECHANGELOG?"} Applied -->|yes| Skip["Skip: previously run"] Applied -->|no| Ctx{"Context expression matches --contexts?"} Ctx -->|no| Filtered["Filtered out: stays pending"] Ctx -->|yes| Lab{"Label expression matches the label filter?"} Lab -->|no| Filtered Lab -->|yes| Pre{"Preconditions pass?"} Pre -->|yes| Run["Run changes, record EXECUTED"] Pre -->|no| OnFail{"onFail setting"} OnFail -->|HALT| Halt["Abort the whole update"] OnFail -->|CONTINUE| Retry["Skip now, retry on next update"] OnFail -->|MARK_RAN| Mark["Record MARK_RAN, run nothing"] OnFail -->|WARN| Warn["Warn, then run anyway"]

Preconditions

A precondition is a state check that gates whether a changeset is allowed to run — What are Preconditions?. Common checks include tableExists, columnExists, indexExists, rowCount and sqlCheck (an arbitrary query whose result must match an expected value). Checks can be combined with and, or and not. A precondition failure is controlled by onFail:

onFail Behaviour

HALT (default)

Stop the entire update with an error.

CONTINUE

Skip this changeset now, but try it again on the next update.

MARK_RAN

Skip it and record it as run (exectype MARK_RAN), so it is never tried again.

WARN

Log a warning and run the changeset anyway.

A separate onError attribute controls what happens when evaluating the precondition itself throws, for example because a referenced table does not exist.

- changeSet:
    id: add-customer-email
    author: alberto
    preConditions:
      onFail: MARK_RAN
      not:
        - columnExists:
            tableName: customer
            columnName: email
    changes:
      - addColumn:
          tableName: customer
          columns:
            - column: { name: email, type: varchar(255) }

This makes the changeset a no-op (recorded as applied, nothing executed) if email already exists — useful when a column might have been added out-of-band, or when reconciling two changelogs that both add it. Running a second changeset with a different id but the same guarded addColumn against the bookshop database proves the point: it is recorded without touching the table.

 id                       | exectype
--------------------------+----------
 add-customer-email       | EXECUTED
 add-customer-email-again | MARK_RAN

A sqlCheck precondition is the escape hatch for anything the built-in checks cannot express, for example only running a destructive cleanup when no rows would be lost:

- changeSet:
    id: drop-legacy-column
    author: alberto
    preConditions:
      onFail: HALT
      onFailMessage: "legacy_status still has data"
      sqlCheck:
        expectedResult: 0
        sql: SELECT count(*) FROM customer WHERE legacy_status IS NOT NULL
    changes:
      - dropColumn:
          tableName: customer
          columnName: legacy_status

Preconditions can also be declared once at the changelog level, where they gate the whole file. Keep in mind that a precondition is evaluated each time Liquibase considers the changeset, not only the first time, which is why a MARK_RAN or a changeset-scoped check is the usual choice.

Contexts

A context is a logical expression attached to a changeset, evaluated at update time against a context expression the person running Liquibase supplies — What are Contexts?:

- changeSet:
    id: seed-demo-customers
    author: alberto
    context: "dev or test"
    changes:
      - insert:
          tableName: customer
          columns:
            - column: { name: full_name, value: "Ada Lovelace" }
            - column: { name: email, value: "ada@example.com" }
liquibase update --contexts=prod

The changeset only runs when the supplied --contexts value satisfies its expression. Contexts support boolean operators (and, or, not, with parentheses), so a changeset can be scoped to exactly the environments it belongs in. Two behaviours trip people up:

  • No --contexts at all means every context runs. A changeset tagged dev or test is still executed by a plain liquibase update, which is how demo data reaches production when someone forgets the flag. Production pipelines should always pass the context explicitly, or the application should set spring.liquibase.contexts.

  • A changeset with no context runs under every context, including prod. Only tagged changesets are filtered.

Labels

A label is a simpler tag, matched at run time the same way, but without contexts' boolean-expression semantics by default — What are Labels?:

- changeSet:
    id: index-customer-email
    author: alberto
    labels: reporting
    changes:
      - createIndex:
          tableName: customer
          indexName: idx_customer_email
          columns:
            - column: { name: email }
liquibase update --label-filter=reporting

The label filter is itself an expression, so --label-filter='!reporting' selects everything except the labelled changesets. Older documentation and releases spell the flag --labels; both work in 5.0.

Contexts vs. Labels: Who Decides

The practical difference is who controls the intent:

  • Contexts — the changeset author decides the logic when writing the changelog (dev or test). The person running update only supplies which contexts are currently active; they can’t change what the changeset’s own expression means.

  • Labels — the person running update decides which labelled changesets to include, by choosing which label filter to pass at invocation time. The changeset author just attaches a tag; the operational decision of when to apply it happens at deploy time.

Use contexts when the routing logic is a property of the change itself (test-only seed data, an environment this changeset must never touch); use labels when the same changelog needs to be run selectively depending on what a particular deployment run is for (e.g. "just the reporting-related changes this time").

A Filtered Changeset Stays Pending

A changeset that is filtered out is not recorded, so it remains pending and runs the first time a later update lets it through. That has a visible side effect on ordering. On the bookshop database, the first run applies everything except the seed data and the index:

$ liquibase update --contexts=prod --label-filter='!reporting'
UPDATE SUMMARY
Run:                          4
Previously run:               0
Filtered out:                 2
-------------------------------
Total change sets:            6
FILTERED CHANGE SETS SUMMARY
Context mismatch:             1
Label mismatch:               1

$ liquibase status --verbose --contexts=prod
1 changeset has not been applied to app@jdbc:postgresql://localhost:5432/bookshop
     changelog/releases/002-add-email.yaml::index-customer-email::alberto

Note that status for the prod context reports only the changeset it could run; the seed data is not considered pending there at all. Running update --contexts=dev --label-filter=reporting later applies the seed data and the index. They land at positions 5 and 6 in ORDEREXECUTED even though they sit in an earlier file than the backfill:

 id                          | orderexecuted | contexts      | labels
-----------------------------+---------------+---------------+-----------
 expand-customer-last-name   |             3 |               |
 backfill-customer-last-name |             4 |               |
 seed-demo-customers         |             5 | (dev or test) |
 index-customer-email        |             6 |               | reporting

Because the seed rows were inserted after the backfill ran, their last_name stays NULL. A changeset that is filtered out can therefore run later than the changesets that follow it in the file, and must not depend on them having been absent. If order matters, either do not filter the changesets in question or make the later changeset re-runnable.

Combining a Precondition with a Context

- changeSet:
    id: backfill-legacy-status
    author: alberto
    context: "migration"
    preConditions:
      onFail: MARK_RAN
      columnExists:
        tableName: customer
        columnName: legacy_status
    changes:
      - update:
          tableName: customer
          columns:
            - column: { name: legacy_status, value: "UNKNOWN" }
          where: "legacy_status IS NULL"

This changeset only even attempts to run under the migration context, and even then only if legacy_status still exists — so it becomes a safe no-op once that column is eventually dropped by a later changeset, instead of failing the whole changelog.
