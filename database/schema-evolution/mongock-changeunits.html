Mongock: ChangeUnits

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A change unit is a plain Java class. The annotations tell Mongock which method does what and in which phase; the class is instantiated by Mongock, so it may declare a constructor whose parameters Mongock injects too.

flowchart TD Start["Runner starts"] --> Lock["Acquire lock"] Lock --> Next{"Next unit by order"} Next --> Rec{"changeId already EXECUTED?"} Rec -->|yes| Next Rec -->|no| Before["@BeforeExecution, outside any transaction"] Before --> Tx["Open transaction if the unit is transactional"] Tx --> Exec["@Execution"] Exec --> Ok{"Throws?"} Ok -->|no| Commit["Commit and record EXECUTED"] Commit --> Next Ok -->|yes| Abort["Abort the transaction: its writes are undone"] Abort --> Stop["Stop the run with a MongockException, nothing recorded"] Next -->|none left| Release["Release lock"]

@ChangeUnit

Every Mongock migration is a class annotated @ChangeUnit. The annotation in Mongock 5.5.1 has seven attributes:

Attribute Meaning

id

Unique identifier — Mongock’s equivalent of a Liquibase changeset’s id (Core Concepts).

order

A string used to sort change units before execution — typically zero-padded ("001", "002") so lexicographic and numeric ordering agree.

author

Who wrote it, for the audit trail — purely informational, not part of identity the way Liquibase’s author is.

systemVersion

Optional — a version marker checked against the runner’s configured startSystemVersion/endSystemVersion window (startSystemVersion <= systemVersion < endSystemVersion), not an exact-match check. Lets a change unit’s activation be tied to a release window rather than requiring the running system to be on one specific version.

failFast

Whether a failure of this unit aborts the whole run (the default, true) or lets Mongock carry on with the next unit.

runAlways

Run the unit on every start instead of once. Only suitable for idempotent maintenance work.

transactional

Whether the unit runs inside a transaction when the runner is transactional (default true). Set it to false for a unit that must perform operations MongoDB refuses inside a transaction.

order is a plain string compared lexicographically, which is why "10" sorts before "2". Zero-pad it to a fixed width and never reuse or renumber an order once a unit has shipped; the file name carries no meaning for Mongock, so a naming convention such as V001_... is purely for humans.

@Execution — Mandatory

Every @ChangeUnit needs exactly one @Execution method: the code that actually performs the migration. It can accept any of Mongock’s supported dependency types as parameters (a MongoDatabase, a Spring Data MongoTemplate, or an application-defined @Inject-able bean), depending on the driver in use (Mongock: Getting Started):

@Execution
public void execution(MongoDatabase db) {
    db.getCollection("customer").updateMany(
        Filters.exists("status", false),
        Updates.set("status", "ACTIVE"));
}

A Worked Example: Splitting the Name

The second release of the bookshop splits fullName into firstName and lastName. Documents are rewritten in place, and the filter lastName does not exist makes the unit safe to run again (see the idempotency discussion in Core Concepts):

@ChangeUnit(id = "split-customer-name", order = "002", author = "alberto")
public class V002_SplitName {

    @Execution
    public void execution(MongoDatabase db) {
        MongoCollection<Document> customers = db.getCollection("customer");
        for (Document doc : customers.find(Filters.exists("lastName", false))) {
            String[] parts = doc.getString("fullName").split(" ", 2);
            customers.updateOne(
                Filters.eq("_id", doc.getObjectId("_id")),
                Updates.combine(
                    Updates.set("firstName", parts[0]),
                    Updates.set("lastName", parts.length > 1 ? parts[1] : "")));
        }
    }

    @RollbackExecution
    public void rollback(MongoDatabase db) {
        db.getCollection("customer").updateMany(
            new Document(), Updates.combine(Updates.unset("firstName"), Updates.unset("lastName")));
    }
}

After this unit runs, each document carries both shapes (fullName, firstName and lastName) — the expand phase of the pattern in Best Practices. Dropping fullName is a separate, later change unit.

@RollbackExecution — Highly Recommended

The inverse of @Execution, run if this migration needs to be undone. Unlike Liquibase, Mongock never generates this automatically — it is always hand-written code, and the official reference marks it as highly recommended rather than mandatory precisely because a change unit is materially riskier without one:

@RollbackExecution
public void rollback(MongoDatabase db) {
    db.getCollection("customer").updateMany(
        Filters.eq("status", "ACTIVE"),
        Updates.unset("status"));
}

A change unit with no @RollbackExecution can still run forward normally, but there is then no supported way to undo it if it turns out to be wrong — see Core Concepts' note on forward-only vs. reversible changes.

When a Change Unit Fails

A third unit tags every customer as a VIP and then throws, which simulates a failure partway through:

@ChangeUnit(id = "tag-vip-customers", order = "003", author = "alberto")
public class V003_FailsHalfway {

    @Execution
    public void execution(MongoDatabase db) {
        db.getCollection("customer").updateMany(new Document(), Updates.set("vip", true));
        if (Boolean.getBoolean("fail")) {
            throw new IllegalStateException("boom after updating every customer");
        }
    }

    @RollbackExecution
    public void rollback(MongoDatabase db) {
        db.getCollection("customer").updateMany(new Document(), Updates.unset("vip"));
    }
}

Run with -Dfail=true against a replica set. Units 001 and 002 complete, unit 003 aborts the run with a MongockException that carries the original message, and the collection afterwards has no vip field at all:

ERROR io.mongock.runner.core.executor.MongockRunnerImpl - Error in mongock process. ABORTED OPERATION
io.mongock.api.exception.MongockException: Error in method[V003_FailsHalfway.execution] : boom after updating every customer

> db.customer.find({}, {_id: 0, fullName: 1, vip: 1})
[ { fullName: 'Ada Lovelace' }, { fullName: 'Alan Turing' } ]

mongockChangeLog contains an EXECUTED entry for split-customer-name but none for tag-vip-customers, so the next run (this time without -Dfail) starts again from unit 003 and completes it. The writes of the failed unit were undone by the transaction. On a deployment without transaction support (a standalone mongod) nothing undoes them automatically, so the unit has to be safe to run again, and @RollbackExecution is what an operator has available for compensating; see Mongock: Transactions & Locking.

@BeforeExecution — Optional

An optional hook that runs before @Execution, outside of whatever transaction Mongock would otherwise wrap the execution in (Mongock: Transactions & Locking). It exists for operations MongoDB does not allow inside a multi-document transaction — most commonly DDL-like operations such as creating a collection or an index, which MongoDB requires to run outside any active transaction:

@BeforeExecution
public void beforeExecution(MongoDatabase db) {
    db.createCollection("audit_log");
}

@Execution
public void execution(MongoDatabase db) {
    db.getCollection("audit_log").insertOne(new Document("event", "initialized"));
}

A matching @RollbackBeforeExecution is available to undo whatever @BeforeExecution did, mirroring @RollbackExecution for the main method. As seen in the audit log of the previous page, Mongock records the before-phase as its own entry (<id>_before), so a unit whose before-phase succeeded but whose execution failed does not repeat the before-phase’s side effects blindly.

Code-First vs. Declarative: The Contrast With Liquibase

The defining difference from Liquibase is that a Mongock change unit is Java code, compiled and reviewed like any other class, rather than a declarative file in a separate format. This means:

  • Full language power — loops, conditionals, calling into application services — is available inside a migration, where a declarative changelog would need Liquibase’s more limited built-in change types or an embedded script.

  • There is no DBA-reviewable, non-Java artifact — reviewing a Mongock migration means reading Java.

  • There is no checksum: Mongock identifies a unit by id alone, so editing an applied unit changes nothing on databases where it already ran. The practical rule is the same as everywhere in this guide — append a new unit.

  • Ordering and the classpath-scanned "changelog" model follow the same rule as every code-based tool in this guide (Core Concepts' Changelog / Ordering section).

@BeforeExecution, @Execution and @RollbackExecution (with @RollbackBeforeExecution) can all live on the same class — see the individual snippets above; there’s no requirement to split them across separate classes.
