Flamingock: Changes & Target Systems

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Anatomy of a Change

A Flamingock change is a class (or, for template-based changes, a YAML file) with three pieces of identity and two methods. Compared with a Mongock @ChangeUnit (Mongock: ChangeUnits) the order attribute is gone and the target system has become its own annotation:

@TargetSystem(id = "bookshop-mongo")
@Change(id = "expand-customer-name", author = "alberto")
public class _0003__ExpandName {

    @Apply
    public void apply(MongoDatabase db, ClientSession session) { /* ... */ }

    @Rollback
    public void rollback(MongoDatabase db, ClientSession session) { /* ... */ }
}
Element Meaning

File name _0003__ExpandName

The text between the first underscore and the double underscore (0003) is the order, at least four characters and best zero-padded. The name after the double underscore is a descriptive PascalCase name. The order cannot change after the change has been deployed.

@Change(id, author)

id must be unique across the application and cannot change once deployed; author identifies who is responsible.

@Change(transactional = ...)

Optional, default true. Whether the change runs in a transaction; it has no effect on a non-transactional target system.

@TargetSystem(id = "...")

Names which configured target system the change applies to.

@Apply

Mandatory, the forward operation.

@Rollback

The inverse. Required in practice: Flamingock runs it automatically for non-transactional systems, and the operational undo tools depend on it.

@Recovery(strategy = ...)

Optional, see Recovery Strategies.

Parameters of @Apply and @Rollback are injected by type. A change resolves them first from its target system’s context (for MongoDB: MongoClient, MongoDatabase and ClientSession), then from dependencies added to the target system with addDependency(...), and finally from a global context.

The annotation processor writes down what it found for every change, which is why a typo in a file name fails at build time rather than at startup. A fragment of the generated META-INF/flamingock/metadata_*.json for the bookshop shows that the order came from the file name and that the default recovery strategy was applied:

{
  "id": "create-customer-email-index",
  "order": "0002",
  "author": "alberto",
  "source": "com.example.bookshop.changes.predeploy._0002__AddEmailIndex",
  "transactionalFlag": false,
  "targetSystem": { "id": "bookshop-mongo" },
  "recovery": { "strategy": "MANUAL_INTERVENTION", "alwaysRetry": false }
}

Transactions on MongoDB: Why ClientSession Matters

With the MongoDB Sync target system a change joins a transaction only if it declares a ClientSession parameter. Flamingock creates the session, starts the transaction before @Apply, commits on success and aborts on failure; operations written without the session still execute, but outside the transaction. A change that creates an index sets transactional = false and omits the session, because MongoDB does not allow that inside a transaction:

@TargetSystem(id = "bookshop-mongo")
@Change(id = "create-customer-email-index", author = "alberto", transactional = false)
public class _0002__AddEmailIndex {

    @Apply
    public void apply(MongoDatabase db) {
        db.getCollection("customer")
          .createIndex(Indexes.ascending("email"), new IndexOptions().unique(true));
    }

    @Rollback
    public void rollback(MongoDatabase db) {
        db.getCollection("customer").dropIndex(Indexes.ascending("email"));
    }
}

Why @Rollback Is Required for Non-Transactional Systems

An object store, a message queue, or a call to a third-party REST API has no transaction to roll back: once a message is published or a request is sent, the side effect has already happened outside Flamingock’s control. For target systems like these, @Rollback is the only mechanism that can undo a partially-applied change at all, and Flamingock invokes it automatically when @Apply fails.

The example below uses a NonTransactionalTargetSystem named order-events and a tiny stand-in for a message client, OrderEvents, registered as a dependency of the target system. The change publishes an event and then fails, to show what happens next:

@TargetSystem(id = "order-events")
@Change(id = "announce-new-shop", author = "alberto")
public class _0001__AnnounceNewShop {

    @Apply
    public void apply(OrderEvents events) {
        events.publish("shop.opened", "bookshop");
        if (Boolean.getBoolean("fail")) {
            throw new IllegalStateException("broker rejected the second message");
        }
    }

    @Rollback
    public void rollback(OrderEvents events) {
        events.publish("shop.opening-cancelled", "bookshop");
    }
}

The runner registers the dependency on the target system:

var queue = new NonTransactionalTargetSystem("order-events").addDependency(new OrderEvents());
Flamingock.builder()
    .setAuditStore(MongoDBSyncAuditStore.from(auditTarget))
    .addTargetSystems(auditTarget, queue)
    .build()
    .run();

Running it with -Dfail=true prints the event, the failure, and then the compensating event published by @Rollback, and the audit log records both outcomes:

PUBLISHED shop.opened bookshop
ERROR FK-ChangeExecution   - Change failed [change=announce-new-shop duration=20ms]: java.lang.IllegalStateException: broker rejected the second message
PUBLISHED shop.opening-cancelled bookshop

announce-new-shop     FAILED          order-events
announce-new-shop     ROLLED_BACK     order-events

@Rollback doesn’t literally "undo" the publish (the original message may already be consumed) — it publishes a compensating event instead, which is the general shape a rollback takes against a non-transactional system: not an inverse operation, but a compensating one. Design the receiving side so that applying the original and the compensation in sequence is harmless.

flowchart TD A["@Apply starts"] --> B{"Target system transactional?"} B -->|yes| C["Failure: abort the transaction"] B -->|no| D["Failure: Flamingock runs @Rollback"] C --> E["Audit: FAILED then ROLLED_BACK"] D --> E D -->|"@Rollback also fails"| F["Audit: ROLLBACK_FAILED, manual intervention"]

Recovery Strategies

What Flamingock does with a change that failed and could not be cleaned up is controlled per change with @Recovery:

Strategy Behaviour

MANUAL_INTERVENTION (default)

Execution stops, the problem is logged in the audit store, and an operator investigates and marks the change as applied or rolled back before the pipeline can continue.

ALWAYS_RETRY

The change is retried automatically on later executions until it succeeds. Only suitable for idempotent changes.

 
@Recovery(strategy = RecoveryStrategy.ALWAYS_RETRY)
@TargetSystem(id = "order-events")
@Change(id = "announce-new-shop", author = "alberto")
public class _0001__AnnounceNewShop { /* ... */ }

Target Systems

Flamingock’s target-system abstraction is what lets one pipeline coordinate changes across systems that would otherwise each need their own tool. Each is a class you instantiate with an id and a client, and pass to addTargetSystems:

Target system Class Notes

SQL (relational)

SqlTargetSystem(id, dataSource)

Transactional; similar guarantees to Liquibase’s target databases.

MongoDB (sync)

MongoDBSyncTargetSystem(id, mongoClient, database)

Transactional on a replica set/sharded cluster when the change takes a ClientSession, same as Mongock (Mongock: Transactions & Locking).

MongoDB (Spring Data)

MongoDBSpringDataTargetSystem

Same, using the application’s Spring Data configuration.

DynamoDB

DynamoDBTargetSystem

Non-relational, AWS-managed; transactional guarantees are narrower than a relational database’s.

Couchbase

CouchbaseTargetSystem

Document database; see the Couchbase Reference for the target system itself.

Non-transactional systems (message brokers, external APIs, cloud services)

NonTransactionalTargetSystem(id)

No native transaction to lean on — @Rollback is the undo path, as above.

See Target Systems — Introduction for the full, up-to-date list and configuration per target.

The Audit Store

Every @Apply/@Rollback execution, across every target system in a pipeline, is recorded in Flamingock’s audit store — a single, configurable place for the full execution history, decoupled from any one target system (unlike Liquibase’s DATABASECHANGELOG, which lives inside the database it’s tracking). The community edition provides stores for MongoDB (sync and Spring Data), SQL, DynamoDB and Couchbase. This is what makes "complete auditability" (Flamingock: Getting Started) possible even when a pipeline’s changes never touch a traditional database at all, as in the order-events example above, whose audit entries are written to MongoDB.

The MongoDB Sync store is created from a MongoDB target system and has optional settings with conservative defaults:

var auditStore = MongoDBSyncAuditStore.from(mongoTarget)
    .withWriteConcern(WriteConcern.W1)
    .withReadPreference(ReadPreference.secondary());

The defaults should ideally be left unchanged: weakening the write concern of the store that decides what has already run trades correctness for speed.

An audit entry carries the execution id, the stage, the change id and author, the state, the invoked class and method, the target system, the change order, the recovery strategy and whether the change was transactional, plus executionMillis, executionHostname and an errorTrace for failures. The states are STARTED, APPLIED, FAILED, ROLLED_BACK and ROLLBACK_FAILED.
