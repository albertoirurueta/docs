Liquibase: Changelogs & Changesets

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Changeset Identity

A changeset is uniquely identified by the triple id + author + the changelog file it is declared in, per What is a Changeset?. Liquibase tracks this triple in DATABASECHANGELOG (Liquibase: Tracking & Locking) — change any part of it and Liquibase treats the changeset as new and runs it again, even if the SQL inside is identical to one already applied. id does not need to be numeric or sequential; a descriptive string (add-customer-email) works just as well and is often clearer in review.

The file name is part of the identity, which has a practical consequence: renaming or moving a changelog file makes every changeset in it look new. Liquibase would try to run them all again against a database where they already ran. Two ways to avoid this are to never rename applied files, or to pin the recorded path with the logicalFilePath attribute on the databaseChangeLog element (a value that stays the same however the file is renamed or relocated on disk).

flowchart LR Master["db.changelog-master.yaml"] --> F1["001-create-customer.yaml"] Master --> Dir["includeAll: changelog/releases/"] Dir --> F2["002-add-email.yaml"] Dir --> F3["003-expand-contract-name.yaml"] F1 --> C1["changeset create-customer-table by alberto"] F2 --> C2["add-customer-email"] F2 --> C3["seed-demo-customers"] F2 --> C4["index-customer-email"] F3 --> C5["expand-customer-last-name"] F3 --> C6["backfill-customer-last-name"]

One Change Type per Changeset

Liquibase recommends keeping exactly one change type (createTable, addColumn, addForeignKeyConstraint, and so on) per changeset. This matters most for rollback: Liquibase’s auto-generated inverse (Liquibase: Rollback) is derived per change type, and a changeset mixing several change types either can’t be auto-rolled-back at all or rolls back in a way that’s harder to reason about. It also keeps the audit trail’s granularity meaningful — one row in DATABASECHANGELOG per logical change.

There is a second reason that matters on databases such as MySQL and Oracle, where DDL statements commit implicitly: a changeset is run in a transaction, but a DDL statement cannot be rolled back inside it. If a changeset with three DDL statements fails on the second, the first one is already committed, the changeset is not recorded in DATABASECHANGELOG, and the next update fails on the first statement because it has already run. PostgreSQL has transactional DDL, which hides the problem, but one change type per changeset keeps the changelog safe on every database.

Changeset Attributes Worth Knowing

Besides id and author, a changeset accepts attributes that change how and when it runs:

Attribute Effect

runOnChange: true

Re-run the changeset whenever its checksum changes, instead of failing validation. Suited to idempotent objects that are redefined as a whole — views, stored procedures, functions — written as CREATE OR REPLACE.

runAlways: true

Run on every update, whatever the checksum. Rarely appropriate for schema changes.

failOnError: false

Log a failure and carry on to the next changeset instead of aborting. Use sparingly: it makes the outcome of a run depend on the state of the database.

runInTransaction: false

Run the changeset outside a transaction. Needed for statements a database refuses to run inside one, such as PostgreSQL’s CREATE INDEX CONCURRENTLY.

context, labels, preConditions

Gate the changeset — see Liquibase: Preconditions, Contexts & Labels.

Splitting Large Changelogs: include and includeAll

A single master changelog can pull in others, so a large schema’s history doesn’t live in one file:

databaseChangeLog:
  - include:
      file: changelog/001-create-customer.yaml
  - includeAll:
      path: changelog/releases/

include names one file explicitly; includeAll pulls in every changelog file under a directory, in lexicographic filename order — the common convention is to prefix each file with a date or an incrementing number so that ordering is obvious from the filename alone. Splitting by feature, by release, or by team keeps merge conflicts down when several people add changesets concurrently. Prefer explicit zero-padded numbers (001, 002, …​ 010) over plain ones: lexicographic order puts 10- before 2-.

The Bookshop Changelog Over Three Releases

The running example starts with the customer table from Liquibase: Getting Started and gains one file per release. Release 2 (changelog/releases/002-add-email.yaml) adds a column, some demo rows and an index, as three separate changesets:

databaseChangeLog:
  - changeSet:
      id: add-customer-email
      author: alberto
      changes:
        - addColumn:
            tableName: customer
            columns:
              - column: { name: email, type: varchar(255) }
  - changeSet:
      id: seed-demo-customers
      author: alberto
      context: "dev or test"
      changes:
        - insert:
            tableName: customer
            columns:
              - column: { name: full_name, value: "Ada Lovelace" }
              - column: { name: email, value: "ada@example.com" }
  - changeSet:
      id: index-customer-email
      author: alberto
      labels: reporting
      changes:
        - createIndex:
            tableName: customer
            indexName: idx_customer_email
            columns:
              - column: { name: email }

Release 3 (003-expand-contract-name.yaml) starts splitting full_name into a first and last name using the expand/contract pattern from Best Practices: one changeset adds the nullable last_name column (expand), a second backfills it:

databaseChangeLog:
  - changeSet:
      id: expand-customer-last-name
      author: alberto
      changes:
        - addColumn:
            tableName: customer
            columns:
              - column: { name: last_name, type: varchar(255) }
  - changeSet:
      id: backfill-customer-last-name
      author: alberto
      changes:
        - sql:
            sql: >-
              UPDATE customer
              SET last_name = split_part(full_name, ' ', 2)
              WHERE last_name IS NULL
      rollback:
        - sql:
            sql: UPDATE customer SET last_name = NULL

On a fresh database, status --verbose lists all of them in file order, and on a database that already has release 1 only the later files are pending:

$ liquibase status --verbose
6 changesets have not been applied to app@jdbc:postgresql://localhost:5432/bookshop
     changelog/001-create-customer.yaml::create-customer-table::alberto
     changelog/releases/002-add-email.yaml::add-customer-email::alberto
     changelog/releases/002-add-email.yaml::seed-demo-customers::alberto
     changelog/releases/002-add-email.yaml::index-customer-email::alberto
     changelog/releases/003-expand-contract-name.yaml::expand-customer-last-name::alberto
     changelog/releases/003-expand-contract-name.yaml::backfill-customer-last-name::alberto

The backfill is written as a one-line UPDATE for a small table. On a large table it would hold locks and generate a long transaction; see Best Practices for batching.

Generating a Changelog from an Existing Database

For a database that predates Liquibase, generate-changelog inspects the live schema and writes out a changelog that would recreate it — a starting point for bringing an existing database under Liquibase management:

liquibase generate-changelog --changelog-file=baseline.yaml

Run against the bookshop database above, the start of the generated file looks like this (the numeric changeset ids are timestamps, and liquibase (generated) is the author):

databaseChangeLog:
- changeSet:
    id: 1794318123580-1
    author: liquibase (generated)
    changes:
    - createTable:
        columns:
        - column:
            autoIncrement: true
            constraints:
              nullable: false
              primaryKey: true
              primaryKeyName: customer_pkey
            name: id
            type: BIGINT
        - column:
            constraints:
              nullable: false
            name: full_name
            type: VARCHAR(255)
        # email, last_name ...
        tableName: customer

When a legacy database is first put under Liquibase management, the baseline changeset must be marked as already applied on the existing environments (otherwise Liquibase would try to create tables that exist): either run liquibase changelog-sync, which records every changeset as run without executing it, or guard the baseline with a tableExists precondition using onFail: MARK_RAN.

diff and diff-changelog instead compare two databases (or a database against a changelog) and produce only the changesets needed to reconcile the difference — useful for catching drift, or for generating the changesets for a change that was prototyped directly against a database. Here a reference database has one extra column (phone) that the target lacks:

liquibase diff-changelog --reference-url=jdbc:postgresql://localhost/bookshop_ref \
  --reference-username=app --reference-password=app --changelog-file=diff.yaml
databaseChangeLog:
- changeSet:
    id: 1794318134865-1
    author: liquibase (generated)
    changes:
    - addColumn:
        columns:
        - column:
            name: phone
            type: VARCHAR(30)
        tableName: customer

Both commands print a warning that the output must be inspected before it is deployed, and with good reason: generated changesets don’t include the semantic intent (why the schema looks the way it does) a hand-written one would, and objects such as stored logic or some vendor-specific features cannot always be represented. Treat them as a draft: review, rename the ids to something descriptive, and commit.
