Mongock: Getting Started

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Mongock migrates MongoDB from Java, using code-first classes instead of a declarative changelog file. This page covers the drivers and runners available and walks through a complete, runnable setup. The same bookshop used in the Liquibase pages is rebuilt here as a MongoDB customer collection: a first change unit creates the collection, seeds two customers and indexes the e-mail; later units evolve the document shape. Everything below was executed with Mongock 5.5.1 against MongoDB 8 running as a one-node replica set.

Mongock is in maintenance mode under the Flamingock organization, and new projects should use Flamingock. This page is for projects that already run Mongock or need to read and maintain its change units.

Drivers

The driver is which MongoDB Java client Mongock uses under the hood to execute a change unit’s operations:

Driver Notes

MongoDB Sync

The official synchronous MongoDB Java driver directly — the most common choice, no additional framework required. Artifact io.mongock:mongodb-sync-v4-driver.

Spring Data

Uses a project’s existing MongoTemplate/MongoRepository configuration, so change units can reuse Spring Data mappings and converters already defined for the application.

Reactive

The reactive MongoDB driver, for a project already built on Project Reactor/RxJava.

Pick the driver that matches how the rest of the application already talks to MongoDB, so change units can share connection configuration and, for Spring Data, object mapping.

Runners

The runner is how Mongock is invoked:

  • Standalone — Mongock runs as a plain Java library call, independent of any framework, useful for a migration-only job (a CLI tool, an init container) that isn’t itself a Spring Boot application.

  • Spring Boot — Mongock hooks into the Spring Boot application lifecycle and runs automatically at startup, the same auto-run-on-startup model as Liquibase’s Spring Boot integration, configured via application.yml:

mongock:
  migration-scan-package:
    - com.example.bookshop.migrations
flowchart LR CU["@ChangeUnit classes in migration-scan-package"] --> Runner subgraph Runner["Runner"] SA["Standalone: MongockStandalone.builder()"] SB["Spring Boot: starter + application.yml"] end Runner --> Driver subgraph Driver["Driver"] D1["MongoDB Sync v4"] D2["Spring Data"] D3["Reactive"] end Driver --> Mongo[("MongoDB")] Driver --> Audit[("mongockChangeLog and mongockLock")]

See Mongock Documentation for the exact starter dependency per driver/runner combination.

Dependencies

Mongock publishes a BOM so the artifacts stay on one version. A standalone project with the synchronous driver needs three dependencies. Mongock 5 is built against the 4.x MongoDB Java driver, so pin mongodb-driver-sync to a 4.x release, and use SLF4J 1.7 so that the logging binding matches the one Mongock compiles against (with SLF4J 2.x bindings Mongock’s log output is silently dropped):

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>io.mongock</groupId>
      <artifactId>mongock-bom</artifactId>
      <version>5.5.1</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
<dependencies>
  <dependency>
    <groupId>io.mongock</groupId>
    <artifactId>mongock-standalone</artifactId>
  </dependency>
  <dependency>
    <groupId>io.mongock</groupId>
    <artifactId>mongodb-sync-v4-driver</artifactId>
  </dependency>
  <dependency>
    <groupId>org.mongodb</groupId>
    <artifactId>mongodb-driver-sync</artifactId>
    <version>4.11.2</version>
  </dependency>
  <dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-simple</artifactId>
    <version>1.7.36</version>
  </dependency>
</dependencies>

A Complete Standalone Runner

The runner is a normal main method. It builds the driver from a MongoClient, tells Mongock which package to scan, and executes:

public class Main {

    public static void main(String[] args) {
        String uri = System.getProperty("mongo.uri",
            "mongodb://localhost:27017/?replicaSet=rs0&directConnection=true");
        try (MongoClient client = MongoClients.create(uri)) {
            MongockStandalone.builder()
                .setDriver(MongoSync4Driver.withDefaultLock(client, "bookshop"))
                .addMigrationScanPackage("com.example.bookshop.migrations")
                .setTransactional(true)
                .buildRunner()
                .execute();
        }
    }
}

withDefaultLock configures the default lock behaviour described in Mongock: Transactions & Locking, and setTransactional(true) asks Mongock to run each change unit in a transaction when the deployment supports it.

To try it locally, start MongoDB as a single-node replica set (transactions need one) and initiate it:

docker run -d --name mongo-lab -p 27017:27017 mongo:8 --replSet rs0 --bind_ip_all
docker exec mongo-lab mongosh --quiet --eval 'rs.initiate({_id:"rs0",members:[{_id:0,host:"localhost:27017"}]})'

A First @ChangeUnit

@ChangeUnit(id = "create-customer-email-index", order = "001", author = "alberto")
public class V001_CreateCustomerIndex {

    @BeforeExecution
    public void before(MongoDatabase db) {
        db.createCollection("customer");
    }

    @RollbackBeforeExecution
    public void rollbackBefore(MongoDatabase db) {
        db.getCollection("customer").drop();
    }

    @Execution
    public void execution(MongoDatabase db) {
        db.getCollection("customer")
          .createIndex(Indexes.ascending("email"), new IndexOptions().unique(true).sparse(true));
        db.getCollection("customer").insertMany(List.of(
            new Document("fullName", "Ada Lovelace").append("email", "ada@example.com"),
            new Document("fullName", "Alan Turing").append("email", "alan@example.com")));
    }

    @RollbackExecution
    public void rollback(MongoDatabase db) {
        db.getCollection("customer").dropIndex(Indexes.ascending("email"));
    }
}

Mongock discovers this class via classpath scanning (the migration-scan-package configured above), runs its @Execution method if create-customer-email-index hasn’t already been recorded as applied, and records it afterward. The collection is created in @BeforeExecution because MongoDB does not allow creating a collection inside a transaction (see Mongock: ChangeUnits).

After the first run, MongoDB contains the application collection plus Mongock’s two bookkeeping collections:

> db.getCollectionNames()
[ 'mongockLock', 'customer', 'mongockChangeLog' ]

> db.mongockChangeLog.find({}, {changeId: 1, state: 1, _id: 0})
[ { changeId: 'system-change-00001_before', state: 'EXECUTED' },
  { changeId: 'system-change-00001', state: 'EXECUTED' },
  { changeId: 'create-customer-email-index_before', state: 'EXECUTED' },
  { changeId: 'create-customer-email-index', state: 'EXECUTED' } ]

The two system-change entries are Mongock’s own housekeeping (creating its indexes); the _before entry is the @BeforeExecution method, recorded as a unit of its own. A second run of Main finds all of them recorded and does nothing. See Mongock: ChangeUnits for the full annotation reference, and the Migration / ChangeUnit reference for the official source.
