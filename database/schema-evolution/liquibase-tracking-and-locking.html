Liquibase: Tracking & Locking

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Liquibase keeps all of its state inside the database it manages, in two tables. Nothing about what has run is stored in the changelog files or on the machine that ran Liquibase, which is why any machine can take over a deployment, and why deleting these tables makes Liquibase believe the database is empty.

DATABASECHANGELOG

Liquibase records every applied changeset as a row in the DATABASECHANGELOG table, created automatically in the target database on first use. Each row carries the changeset’s id, author and source filename (its identity, per Liquibase: Changelogs & Changesets), the timestamp it ran, an execution order number, and a checksum of its content — per What is a Changelog?. This table is the audit trail: it’s what liquibase status reads to compute which changesets are still pending, and what Core Concepts' audit/tracking table concept maps onto for Liquibase specifically.

For the bookshop database of this section the table contains one row per changeset:

             id              |                     filename                     | orderexecuted | exectype |   contexts    |  labels   |               md5sum
-----------------------------+--------------------------------------------------+---------------+----------+---------------+-----------+------------------------------------
 create-customer-table       | changelog/001-create-customer.yaml               |             1 | EXECUTED |               |           | 9:0129796fdb343c9a0ea83f1098474ab9
 add-customer-email          | changelog/releases/002-add-email.yaml            |             2 | EXECUTED |               |           | 9:afcd05adcce52ab7b91e113127e33877
 expand-customer-last-name   | changelog/releases/003-expand-contract-name.yaml |             3 | EXECUTED |               |           | 9:80da9b0c25dfa6a8b67c13f7be8ec8ee
 backfill-customer-last-name | changelog/releases/003-expand-contract-name.yaml |             4 | EXECUTED |               |           | 9:7a7778b4ab1026e5d13955225c01aec3
 seed-demo-customers         | changelog/releases/002-add-email.yaml            |             5 | EXECUTED | (dev or test) |           | 9:44bdba9ccb1802b60c6e0f8cd7fed494
 index-customer-email        | changelog/releases/002-add-email.yaml            |             6 | EXECUTED |               | reporting | 9:24141e752f793d866b05c9c23438f422

The full column list is ID, AUTHOR, FILENAME, DATEEXECUTED, ORDEREXECUTED, EXECTYPE, MD5SUM, DESCRIPTION, COMMENTS, TAG, LIQUIBASE, CONTEXTS, LABELS and DEPLOYMENT_ID. A few are worth understanding:

  • EXECTYPE is EXECUTED for a changeset that ran, MARK_RAN for one recorded without running (a failed MARK_RAN precondition, or changelog-sync), and RERAN for a runOnChange or runAlways changeset that ran again.

  • MD5SUM starts with a number (9: above), the version of the checksum algorithm, followed by the hash. When Liquibase changes how it computes checksums, it recognizes the old version and does not report a false mismatch.

  • DEPLOYMENT_ID groups every changeset recorded by one update invocation, and liquibase history prints the table grouped by it.

  • TAG is filled by liquibase tag (see Liquibase: Rollback).

liquibase history renders the same information as an ASCII table, one block per deployment:

+---------------+-------------------+---------------------------------------+------------------+----------------------+-----+
| Deployment ID | Update Date       | Changelog Path                        | Changeset Author | Changeset ID         | Tag |
+---------------+-------------------+---------------------------------------+------------------+----------------------+-----+
| 4318041609    | 11/10/26, 1:40 PM | changelog/releases/002-add-email.yaml | alberto          | seed-demo-customers  |     |
+---------------+-------------------+---------------------------------------+------------------+----------------------+-----+

DATABASECHANGELOGLOCK

A second table, DATABASECHANGELOGLOCK, holds a single row used as a mutex: before update runs, Liquibase sets a LOCKED = true flag (with the locking host and timestamp) in this row, and clears it when the run finishes. This is what stops two instances of an application — or a developer and a CI job — from applying changesets to the same database concurrently and racing each other. The update-sql output of Liquibase: Getting Started shows the exact statements:

UPDATE public.databasechangeloglock SET LOCKED = TRUE, LOCKEDBY = '86b09a18767d (172.22.0.3)', LOCKGRANTED = NOW() WHERE ID = 1 AND LOCKED = FALSE;
-- ... changesets run here ...
UPDATE public.databasechangeloglock SET LOCKED = FALSE, LOCKEDBY = NULL, LOCKGRANTED = NULL WHERE ID = 1;

The WHERE ... AND LOCKED = FALSE clause is what makes it a lock: an UPDATE that touches zero rows means someone else holds it, and Liquibase waits and retries until a configurable timeout (a few minutes by default) before giving up with an error that it could not acquire the change log lock.

SET LOCKED = TRUE WHERE LOCKED = FALSE L-->>A: 1 row updated, lock acquired B->>L: UPDATE ... Checksum Mismatches

If a changeset already recorded in DATABASECHANGELOG is edited afterward — even a whitespace-only change to some formats — the checksum Liquibase recomputes on the next run no longer matches the one stored from the first run. By default this is a validation failure: Liquibase refuses to proceed, on the theory that it cannot know whether the edited version was ever actually applied to this database (see Core Concepts' idempotency and checksum sections). Changing varchar(255) to varchar(200) in the first changeset of the bookshop produces:

$ liquibase update
ERROR: Exception Primary Class:  ValidationFailedException
ERROR: Exception Primary Reason:  Validation Failed:
     1 changesets check sum
          changelog/001-create-customer.yaml::create-customer-table::alberto was: 9:0129796fdb343c9a0ea83f1098474ab9 but is now: 9:9cf0f7448a4425df99384d4bb972c383

Nothing runs, not even the changesets that come after the edited one. Two ways to resolve it:

  • Preferred: revert the edit, and add a new changeset for the additional change instead — never edit an applied changeset (Best Practices).

  • When the edit is confirmed harmless (e.g. a comment-only change, or the edit was already applied by hand and you are certain the two are equivalent): liquibase clear-checksums clears every stored checksum, and the next update recomputes and re-stores them from the current changelog content, accepting it as the new baseline. liquibase validate checks changelog integrity (including checksums) without applying anything, so it’s the safe way to confirm the mismatch before deciding:

    $ liquibase clear-checksums
Liquibase command 'clear-checksums' was executed successfully.
$ liquibase validate
No validation errors found.

Remember that clear-checksums accepts every edit made to every applied changeset, not only the one you meant. Inspect git diff of the changelog first.

Liquibase has two finer-grained tools for deliberate changes. runOnChange: true on a changeset re-runs it whenever its content changes (and records RERAN), which suits views and stored procedures written as CREATE OR REPLACE. A validCheckSum element inside a changeset lists a previous checksum that is also accepted, so one specific historical edit can be tolerated without disabling validation for everything else.

Baselining an Existing Database

changelog-sync records every changeset in the changelog as already run, without executing anything. It is used when a database already has the schema the changelog describes, for example after generate-changelog on a legacy database, so that the first real update has nothing to do (see Liquibase: Changelogs & Changesets). changelog-sync-sql previews the inserts, and mark-next-changeset-ran records just the next pending one.

Releasing a Stuck Lock

If a Liquibase run is interrupted (the process is killed, the container is stopped) while it holds the lock, DATABASECHANGELOGLOCK can be left with LOCKED = true even though nothing is actually running anymore. The next update then waits and finally fails with a lock-already-held error. liquibase list-locks shows who holds it, and liquibase release-locks forces the lock row back to unlocked. With a lock left behind by a pod that crashed:

$ liquibase list-locks
Database change log locks for app@jdbc:postgresql://localhost:5432/bookshop
 - crashed-pod (10.0.0.7) at Nov 10, 2026, 1:41:42 PM
$ liquibase release-locks
Successfully released all database change log locks for 'app@jdbc:postgresql://localhost:5432/bookshop'
$ liquibase list-locks
Database change log locks for app@jdbc:postgresql://localhost:5432/bookshop
 - No locks

Run this only once you’ve confirmed no other Liquibase process is genuinely still running against that database — forcing the lock while a real run is in progress reintroduces exactly the concurrent-write race the lock exists to prevent.

A subtle point is what a crash during a changeset leaves behind. On a database with transactional DDL such as PostgreSQL the changeset’s transaction is rolled back and the changeset is simply pending again. A changeset that adds a column and then inserts into a table that does not exist fails with relation "no_such_table" does not exist, and afterwards the column is absent and DATABASECHANGELOG still holds only the first changeset. On databases that commit DDL implicitly, the first statements may already have taken effect without being recorded, which is the other reason to keep one change type per changeset.
