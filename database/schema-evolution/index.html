Evolving the Database Model

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A database schema is never finished. Tables gain columns, MongoDB collections gain new document shapes, indexes get added and dropped, and every one of those changes has to land the same way in a developer’s laptop, a CI pipeline, staging and production — in the right order, exactly once, with a record of what ran and when. Making that change by hand — a DBA running a script, a developer clicking through a GUI — works for a while and then fails in the way manual processes always fail: one environment drifts from another, nobody remembers which scripts already ran where, and there is no way to undo a bad change short of restoring a backup.

Mongock is now maintained under the Flamingock GitHub organization (github.com/flamingock/mongock), and Flamingock is positioned as its successor — see Coming from Mongock. Readers starting a new project should default to Flamingock unless they have a specific reason to stay on Mongock.

Migrations as code solves this by treating every schema/model change as a versioned, ordered unit of work, committed to the same repository as the application code that depends on it. Each unit runs at most once per target, in a fixed order, and its execution is durably recorded — so any environment can be brought from "empty" to "current" (or from any past state to current) by replaying the same units, and the record of what ran becomes an audit trail for free. This gets you:

  • Repeatability — the same units, applied in the same order, produce the same schema everywhere.

  • Auditability — a durable record of what changed, when, and (via version control) who changed it and why.

  • Team coordination — schema changes go through the same review and merge process as any other code change, instead of living as tribal knowledge or a shared script folder.

  • Environment parity — development, CI, staging and production converge on the same state instead of drifting apart silently.

This guide covers three tools that implement this idea, each aimed at a different slice of the problem: Liquibase for relational/SQL databases with a declarative changelog, Mongock for MongoDB from Java/Spring using code-first change units, and Flamingock — Mongock’s successor — which generalizes the same Change-as-Code model to any target system, not just a database. Core Concepts introduces the vocabulary all three share before any tool-specific page uses it, and Choosing a Migration Tool helps you land on one.

Version baseline

The examples were executed against Liquibase 5.0.4 (CLI image liquibase/liquibase:5.0) on PostgreSQL 17, Mongock 5.5.1 and Flamingock 1.4.5 on MongoDB 8 running as a one-node replica set. All three share one running example, a small online bookshop whose customer data evolves from a single full_name field to separate first and last names.

This section documents schema/database evolution using version-controlled migration tools — Liquibase (relational/SQL), Mongock (MongoDB, Java-native) and Flamingock (Mongock’s successor, generalized to any external system) — as described by each tool’s own official documentation: liquibase.org and docs.liquibase.com for Liquibase, docs.mongock.io for Mongock, and docs.flamingock.io for Flamingock — which are the references these pages are written and verified against.

At a Glance

Tool Target system(s) Changelog format Tracking mechanism Best fit

Liquibase

Relational/SQL databases (any JDBC target)

Declarative SQL, XML, YAML or JSON changelog files

DATABASECHANGELOG / DATABASECHANGELOGLOCK tables in the target database

Relational schemas, polyglot stacks with no JVM requirement, DBA-reviewable changelogs

Mongock

MongoDB only

Code-first Java @ChangeUnit classes

An audit collection in the target MongoDB deployment, plus a distributed lock collection

Existing MongoDB + Java/Spring projects already invested in code-first change units

Flamingock

Any target system — SQL, MongoDB, DynamoDB, Couchbase, message brokers, APIs, cloud services

Code-first Java @Change classes, grouped into stages and pipelines

A configurable audit store, decoupled from any single target system

New projects, multi-target systems, or migrating an existing Mongock codebase forward

What’s covered

Core Concepts

  • Core Concepts — the vocabulary every tool shares: the life of a change unit, changelog/ordering, idempotency, checksums, the audit/tracking table and what each tool really writes, distributed locking, contexts and environments, forward-only vs. reversible changes, and dry runs.

Choosing a Migration Tool

  • Choosing a Migration Tool — a decision guide for Liquibase vs. Mongock vs. Flamingock, with the same change written three times, a comparison of how each tool behaves under failure, and a decision flowchart.

Liquibase

  • Liquibase: Getting Started — installing the CLI, running it from Docker, the Maven/Gradle plugin or Spring Boot auto-run, the four changelog formats, and a first changeset previewed with status and update-sql and applied with liquibase update.

  • Liquibase: Changelogs & Changesets — changeset identity (id/author/filename), the one-change-type-per-changeset recommendation, changeset attributes such as runOnChange, include/includeAll, the bookshop changelog over three releases, and generating a changelog from an existing database or a schema diff.

  • Liquibase: Preconditions, Contexts & Labels — gating a changeset on database state, tagging changesets per environment, and the author-vs-operator split between contexts and labels, and what a filtered changeset does on a later run.

  • Liquibase: Rollback — automatic inverse SQL, custom <rollback> blocks, previewing with rollback-sql, rolling back by tag, count or date, and testing rollbacks.

  • Liquibase: Tracking & Locking — the DATABASECHANGELOG/DATABASECHANGELOGLOCK tables column by column, checksum mismatches, baselining, and releasing a stuck lock.

Mongock

  • Mongock: Getting Started — the available drivers (MongoDB Sync, Spring Data, Reactive) and runners (Standalone vs. Spring Boot), Maven coordinates, a complete standalone runner and a first @ChangeUnit.

  • Mongock: ChangeUnits — @ChangeUnit, the mandatory @Execution method, @RollbackExecution, the @BeforeExecution hook, and code-first migrations as the contrast with Liquibase’s declarative changelogs, plus a worked name-split migration and what a failing unit leaves behind.

  • Mongock: Transactions & Locking — transactional execution on a replica set/sharded cluster (and why a standalone mongod fails), the distributed lock, and multi-tenant migrations.

Flamingock

  • Flamingock: Getting Started — the Change-as-Code philosophy, Maven setup with the annotation processor, a complete runnable example with its execution report, and the Mongock-to-Flamingock migration path.

  • Flamingock: Changes & Target Systems — the anatomy of a Change (file-name ordering, @TargetSystem, @Apply/@Rollback, @Recovery), a compensating rollback on a non-transactional system, and the supported target systems and audit store.

  • Flamingock: Stages & Pipelines — grouping Changes into ordered stages and multi-stage pipelines, and why stages are independent of each other.

  • Flamingock: Testing — the metadata change validator, unit testing a single Change, the BDD-style Given-When-Then API with passing and failing pipeline tests, and Spring Boot integration testing.

Best Practices

  • Best Practices — expand/contract with the bookshop name split release by release, one logical change per change unit, never editing an already-applied change, testing migrations in CI, coordinating rollout with the application deploy, zero-downtime strategies and a batched, resumable backfill.

Deliberately out of scope. This section is about three tools for evolving a schema or document model with version-controlled change units: Liquibase, Mongock and Flamingock. The following topics appear in most books on the subject but live elsewhere on this site, or are intentionally not covered:

  • Flyway — intentionally not covered as a tool of its own; it appears only in passing as the migration tool of a Vaadin application in Data Persistence, and the concepts in Core Concepts apply to it unchanged.

  • Moving data between systems with change data capture — see Database Migration for Debezium, and Handling Schema Changes During a Migration for how schema changes interact with a running pipeline.

  • ORM schema generation (hbm2ddl, ddl-auto) — generating DDL from entity mappings is a development convenience, not a migration strategy; see Schema Generation and Tooling.

  • Writing the DDL itself — the SQL that a Liquibase changeset or a hand-written migration runs is covered in Data Definition Language (DDL).

  • Entity Framework and other ORM-bundled migration tools — intentionally not covered; they are tied to one ORM rather than being a standalone tool.

  • Schema comparison GUIs and commercial editions — Liquibase Secure/Pro features such as targeted rollbacks and policy checks, and Flamingock Cloud, are intentionally not covered; this section sticks to the open-source CLI and libraries.
