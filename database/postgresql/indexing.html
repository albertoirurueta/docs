Indexing

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

An index is a separate data structure that lets the planner find rows without reading the whole table. PostgreSQL ships six index access methods (B-tree, hash, GIN, GiST, SP-GiST and BRIN), each suited to different operators, and an extension mechanism for more. Choosing the right one, and knowing what an index costs, is most of practical query tuning. This page shows each method on generated data with EXPLAIN evidence; reading the plans themselves is the subject of Query Planning & EXPLAIN, and the general method for a slow query is in Diagnosing Slow Queries.

Everything ran on PostgreSQL 18.6. The shop tables are too small for an index to matter, so the demos use a generated table, big_orders, of 500,000 rows with a seeded random() (setseed(0.42)). It lives in a scratch schema, lab; timings are from an arm64 laptop in a container and will differ on your hardware, but the plan shapes will not. Each EXPLAIN below uses ANALYZE so the plans show real row counts.

The test data

DROP TABLE IF EXISTS big_orders;
SELECT setseed(0.42);
CREATE TABLE big_orders (
  id          bigint PRIMARY KEY,
  customer_id int NOT NULL,
  status      text NOT NULL,
  amount      numeric(10,2) NOT NULL,
  created_at  timestamptz NOT NULL,
  email       text NOT NULL,
  tags        text[] NOT NULL,
  doc         jsonb NOT NULL,
  note        text NOT NULL
);
INSERT INTO big_orders
SELECT g,
       1 + (random() * 20000)::int,
       CASE WHEN random() < 0.02 THEN 'open' WHEN random() < 0.05 THEN 'cancelled' ELSE 'shipped' END,
       round((random() * 500)::numeric, 2),
       timestamptz '2025-01-01 00:00:00+00' + g * interval '1 minute',
       'User' || (1 + (random() * 20000)::int) || '@Example.com',
       ARRAY(SELECT (ARRAY['office','ergonomic','sale','led','usb','display','gift','new'])[1 + (random()*7)::int] FROM generate_series(1, 1 + (g % 3)::int) AS k WHERE g > 0),
       jsonb_build_object('channel', (ARRAY['web','mobile','store'])[1 + (random()*2)::int], 'items', 1 + (random()*5)::int, 'gift', random() < 0.1),
       (SELECT string_agg((ARRAY['fast','delivery','broken','chair','desk','lamp','refund','late','gift','monitor','cable','thanks'])[1 + (random()*11)::int], ' ') FROM generate_series(1, 6) AS w WHERE g > 0)
FROM generate_series(1, 500000) AS g;
ANALYZE big_orders;

The table is about 110 MB with only its primary-key index. created_at grows monotonically with id (physically ordered, which matters for BRIN), customer_id has 20,000 distinct values, status is skewed (about 2% open, 5% cancelled, the rest shipped), and tags, doc and note are an array, a jsonb document and a sentence of random words for the GIN and full-text demos.

How an index changes a plan

After a B-tree index on the filtered column the planner reads three index pages and about thirty table pages instead (a bitmap heap scan; with fewer matching rows it would choose a plain index scan):

Execution time dropped from several milliseconds (and some 14,000 buffers) to well under a millisecond. An index is not free: every INSERT, and every UPDATE that changes an indexed column or cannot be a HOT update, must maintain it, it takes disk space and memory, and it adds work to VACUUM. Index what queries actually filter, join and sort on.

B-tree

The default CREATE INDEX builds a B-tree, which supports <, <=, =, >=, > and BETWEEN, IN, IS NULL, sorting (ORDER BY without a sort step), and LIKE 'prefix%' under a suitable collation or text_pattern_ops. It is the right choice unless an operator needs something else.

Multicolumn indexes

An index on (customer_id, created_at DESC) serves equality on the leading column and a sort on the next, so "the three newest orders of a customer" becomes a few index entries with no sort and no extra table pages:

DROP INDEX big_orders_customer_idx;
CREATE INDEX big_orders_cust_date_idx ON big_orders (customer_id, created_at DESC);
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM big_orders WHERE customer_id = 4242 ORDER BY created_at DESC LIMIT 3;
                                                                    QUERY PLAN
---------------------------------------------------------------------------------------------------------------------------------------------------

   Buffers: shared hit=2 read=3

The rule of thumb is to put equality columns first and the range or sort column last; the index also serves queries on the leading column alone, so it replaced the single-column index above. A condition on a non-leading column alone used to be a poor fit. PostgreSQL 18 adds skip scan: when the leading column has few distinct values, the executor probes each value in turn. With status (three values) first:

CREATE INDEX big_orders_status_created_idx ON big_orders (status, created_at);
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF) SELECT id FROM big_orders WHERE created_at = '2025-03-01 00:00:00+00';
                                       QUERY PLAN
-----------------------------------------------------------------------------------------
 Index Scan using big_orders_status_created_idx on big_orders (actual rows=1.00 loops=1)
   Index Cond: (created_at = '2025-03-01 00:00:00+00'::timestamp with time zone)
   Index Searches: 7
 Planning Time: 0.118 ms
 Execution Time: 0.054 ms
(5 rows)

Index Searches: 7 shows the skip scan at work: the executor probed the index several times, jumping between the status values, instead of reading the whole index. With 20,000 distinct customers the same trick would not pay, so a condition on created_at alone needs an index of its own. Check Index Searches in EXPLAIN (ANALYZE) output.

Covering indexes, index-only scans and the visibility map

INCLUDE appends non-key columns to the leaf pages so that a query needing only those columns can be answered from the index alone (an index-only scan). Because MVCC visibility lives in the table (see Architecture), the scan must still check that each row is visible; it avoids visiting the table page only for pages marked all-visible in the visibility map, which VACUUM maintains.

DROP INDEX big_orders_cust_date_idx;
CREATE INDEX big_orders_cust_date_idx ON big_orders (customer_id, created_at DESC) INCLUDE (amount);
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF) SELECT customer_id, created_at, amount FROM big_orders WHERE customer_id = 4242;
VACUUM (ANALYZE) big_orders;
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF) SELECT customer_id, created_at, amount FROM big_orders WHERE customer_id = 4242;

A table that is updated constantly gets little benefit from index-only scans until autovacuum catches up. INCLUDE columns are not searchable and not part of uniqueness; use them for the few columns that a hot query selects.

Partial indexes

A partial index covers only the rows matching a WHERE predicate. It is much smaller and cheaper to maintain, and ideal for a small, frequently queried subset such as open orders or unprocessed jobs. The query’s own WHERE must imply the index predicate.

CREATE INDEX big_orders_open_idx ON big_orders (created_at) WHERE status = 'open';
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF) SELECT id, amount FROM big_orders WHERE status = 'open' AND created_at > '2025-12-01';
SELECT pg_size_pretty(pg_relation_size('big_orders_open_idx')) AS partial_index,
       pg_size_pretty(pg_relation_size('big_orders_status_created_idx')) AS full_index;

Expression indexes

An index can be built on an expression, which is the fix for a function call that makes a plain index unusable. The query must repeat the same expression:

EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF) SELECT id FROM big_orders WHERE lower(email) = 'user77@example.com';
CREATE INDEX big_orders_email_lower_idx ON big_orders (lower(email));

Hash indexes

A hash index supports only equality. Since PostgreSQL 10 it is crash-safe and WAL-logged, so it is a legitimate choice, but it cannot enforce uniqueness, cannot serve ranges or sorting, and is rarely smaller than a B-tree, because B-trees deduplicate repeated keys (since PostgreSQL 13). In this data set, with many rows per e-mail address:

CREATE INDEX big_orders_email_hash ON big_orders USING hash (email);
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF) SELECT id FROM big_orders WHERE email = 'User77@Example.com';
SELECT pg_size_pretty(pg_relation_size('big_orders_email_hash')) AS hash_size,
       pg_size_pretty(pg_relation_size('big_orders_email_lower_idx')) AS btree_size;
                                  QUERY PLAN
------------------------------------------------------------------------------
 Bitmap Heap Scan on big_orders (actual rows=24.00 loops=1)
   Recheck Cond: (email = 'User77@Example.com'::text)
   Heap Blocks: exact=24
   ->  Bitmap Index Scan on big_orders_email_hash (actual rows=24.00 loops=1)
         Index Cond: (email = 'User77@Example.com'::text)
         Index Searches: 1

 Execution Time: 0.144 ms

The hash index is about four times larger than the B-tree on the same column and no faster for this lookup, so a B-tree is the default recommendation even for equality, unless the keys are very long.

GIN: arrays, jsonb and full-text search

A Generalized Inverted Index maps each element (array member, jsonb key or value, lexeme) to the rows that contain it. It accelerates containment and overlap operators on composite values: @>, <@, && on arrays, @>, ? and @@ on jsonb, and @@ on tsvector. Reads are fast; writes are slower, which GIN softens with a pending list that is merged lazily.

EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF) SELECT count(*) FROM big_orders WHERE tags @> ARRAY['gift','new'];
CREATE INDEX big_orders_tags_gin ON big_orders USING gin (tags);
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF) SELECT count(*) FROM big_orders WHERE tags @> ARRAY['gift','new'];

Full-text search basics

Full-text search finds documents that match a query by meaning of words, not by substring: text is parsed into lexemes (normalized words with stop words removed and stemming applied for a configured language), compared with the @@ operator, and ranked. The two types are:

  • tsvector: a sorted list of lexemes with positions, produced by to_tsvector(config, text).

  • tsquery: a boolean query of lexemes with & (and), | (or), ! (not) and <-> (followed by), produced by to_tsquery, plainto_tsquery, phraseto_tsquery or, for user input, websearch_to_tsquery.

SELECT to_tsvector('english', 'The quick brown foxes jumped over the lazy dogs');
SELECT websearch_to_tsquery('english', '"fast delivery" refund -late');
SELECT to_tsvector('english', 'fast delivery of the refund') @@ websearch_to_tsquery('english', '"fast delivery" refund -late') AS matches;
                      to_tsvector
-------------------------------------------------------
 'brown':3 'dog':9 'fox':4 'jump':5 'lazi':8 'quick':2
(1 row)

--------------------------------------------
 'fast' <-> 'deliveri' & 'refund' & !'late'
(1 row)

 t
(1 row)

websearch_to_tsquery accepts the syntax users know from web search engines (quoted phrases, or, a leading -) and never raises a syntax error, so it is safe on raw input. Stop words (the, of) are dropped and foxes becomes fox. Computing to_tsvector for every row on every query is slow, as the unindexed query shows. The standard remedy is a stored tsvector column, kept in sync by a generated column, with a GIN index:

EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF) SELECT count(*) FROM big_orders WHERE to_tsvector('english', note) @@ websearch_to_tsquery('english', 'refund -late');
ALTER TABLE big_orders ADD COLUMN note_tsv tsvector GENERATED ALWAYS AS (to_tsvector('english', note)) STORED;
CREATE INDEX big_orders_note_fts ON big_orders USING gin (note_tsv);
EXPLAIN (ANALYZE, COSTS OFF, BUFFERS OFF, TIMING OFF) SELECT count(*) FROM big_orders WHERE note_tsv @@ websearch_to_tsquery('english', 'refund -late');

ts_rank (or ts_rank_cd, which accounts for proximity) scores matches for ordering, and ts_headline marks the matching words in the original text:

SELECT id, note, round(ts_rank(note_tsv, q)::numeric, 4) AS rank
FROM big_orders, websearch_to_tsquery('english', 'refund monitor') AS q
WHERE note_tsv @@ q ORDER BY rank DESC, id LIMIT 3;
SELECT ts_headline('english', note, websearch_to_tsquery('english', 'refund monitor'), 'StartSel=[, StopSel=]') AS snippet
FROM big_orders WHERE id = 3;

Ranking has to evaluate the rank for every matching row, which is why it is expensive when a query matches a large fraction of the table (here about 132,000 rows matched refund -late): limit the candidate set before ranking, or use more selective terms. Weights (setweight, labels A to D) let a title outweigh a body, unaccent and the pg_trgm extension add accent-insensitive and typo-tolerant matching (see Extensions), and a dedicated search engine (see Elasticsearch) takes over when you need facets, relevance tuning or very large corpora.

GiST, SP-GiST and exclusion constraints

A GiST (Generalized Search Tree) index is a framework for balanced trees over data that has no total order: ranges, geometric types, inet, trigram similarity, and PostGIS geometries. It answers overlap, containment, nearest-neighbour (ORDER BY a <-> b) and "does this region intersect" questions. An exclusion constraint generalizes a unique constraint: no two rows may satisfy the given operators against each other, enforced by a GiST (or SP-GiST) index. The classic use is "no overlapping bookings for the same room"; equality on a scalar column needs the btree_gist extension.

CREATE EXTENSION IF NOT EXISTS btree_gist;
CREATE TABLE room_reservations (
  room   text NOT NULL,
  during tstzrange NOT NULL,
  EXCLUDE USING gist (room WITH =, during WITH &&)
);
INSERT INTO room_reservations VALUES ('blue', '[2026-05-01 09:00+00, 2026-05-01 11:00+00)');
INSERT INTO room_reservations VALUES ('blue', '[2026-05-01 10:00+00, 2026-05-01 12:00+00)');
INSERT INTO room_reservations VALUES ('blue', '[2026-05-01 11:00+00, 2026-05-01 12:00+00)');
INSERT INTO room_reservations VALUES ('green', '[2026-05-01 10:00+00, 2026-05-01 12:00+00)');
SELECT room, during FROM room_reservations ORDER BY room, lower(during);

SP-GiST (space-partitioned GiST) supports non-balanced partitioning trees such as radix trees for text and IP prefixes, quad-trees and k-d trees for points. It is useful for data with natural clustering, like IP networks:

CREATE TABLE sensor_log AS
SELECT g AS id,
       ('10.' || (g % 256) || '.' || ((g / 256) % 256) || '.' || (g % 200))::inet AS addr,
       timestamptz '2025-01-01 00:00:00+00' + g * interval '1 second' AS ts,
       (random() * 100)::int AS v
FROM generate_series(1, 300000) AS g;

BRIN

A Block Range Index stores only the minimum and maximum of a column for each range of table pages (128 pages by default). It is tiny and nearly free to maintain, and it works when the column’s values correlate with physical row order, as an append-only created_at, an increasing id or a serial number does. pg_stats.correlation close to 1 or -1 is the signal.

CREATE INDEX sensor_log_ts_btree ON sensor_log (ts);
CREATE INDEX sensor_log_ts_brin ON sensor_log USING brin (ts) WITH (pages_per_range = 32);
SELECT pg_size_pretty(pg_relation_size('sensor_log')) AS table_size,
       pg_size_pretty(pg_relation_size('sensor_log_ts_btree')) AS btree,
       pg_size_pretty(pg_relation_size('sensor_log_ts_brin')) AS brin;
SELECT correlation FROM pg_stats WHERE tablename = 'sensor_log' AND attname = 'ts';
DROP INDEX sensor_log_ts_btree;

The BRIN index is a few hundred times smaller than the B-tree (24 kB against 6.6 MB) yet answers the range query from 64 candidate pages, with Rows Removed by Index Recheck showing the price of its coarseness: it returns whole page ranges and the executor filters them (a lossy bitmap). On randomly ordered data a BRIN index is useless.

The bloom extension offers a Bloom filter index for equality tests across many columns at once, when a multicolumn B-tree is impractical; it is lossy and only worth it for wide, ad-hoc WHERE combinations. It is mentioned here rather than demonstrated. Other extension-provided index types include pg_trgm GIN/GiST operator classes for LIKE '%text%' and similarity, and vector indexes (HNSW, IVFFlat), covered in Vector Databases & RAG and Extensions.

Unique constraints and exclusion constraints

A UNIQUE or PRIMARY KEY constraint is implemented by a unique B-tree index created for you; NULL values are distinct unless the constraint says NULLS NOT DISTINCT (PostgreSQL 15). A foreign key does not create an index on the referencing column: add one yourself when the child table is joined or when parent rows are deleted, otherwise each delete scans the child table. The shop’s orders(customer_id) is such a column.

Building and maintaining indexes

CREATE INDEX CONCURRENTLY

A plain CREATE INDEX blocks writes to the table for the whole build. CREATE INDEX CONCURRENTLY takes longer (two table scans) and cannot run inside a transaction block, but lets reads and writes continue, so it is the form to use on a live table. If it fails, for example on a unique violation, it leaves an invalid index behind that must be dropped:

CREATE UNIQUE INDEX CONCURRENTLY big_orders_email_uq ON big_orders (email);
SELECT indexrelid::regclass AS index, indisvalid, indisready FROM pg_index WHERE indrelid = 'big_orders'::regclass AND NOT indisvalid;
DROP INDEX CONCURRENTLY big_orders_email_uq;
CREATE INDEX CONCURRENTLY big_orders_amount_idx ON big_orders (amount);
SELECT indexrelid::regclass AS index, indisvalid FROM pg_index WHERE indexrelid = 'big_orders_amount_idx'::regclass;
ERROR:  could not create unique index "big_orders_email_uq"
DETAIL:  Key (email)=(User4349@Example.com) is duplicated.

Bloat and REINDEX

B-tree pages are reused after VACUUM, but the index file never shrinks by itself, and an index on a column that churns heavily can accumulate nearly empty pages (bloat). The pgstattuple extension measures it: pgstatindex reports the density of the leaf pages and pgstattuple the dead and free space of a table. Deleting half the rows, vacuuming, and then rebuilding the index shows the effect:

CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT pg_size_pretty(pg_relation_size('big_orders_amount_idx')) AS size, avg_leaf_density FROM pgstatindex('big_orders_amount_idx');
DELETE FROM big_orders WHERE amount < 250;
VACUUM big_orders;
SELECT pg_size_pretty(pg_relation_size('big_orders_amount_idx')) AS size_after_delete_and_vacuum, avg_leaf_density FROM pgstatindex('big_orders_amount_idx');
REINDEX INDEX CONCURRENTLY big_orders_amount_idx;
SELECT pg_size_pretty(pg_relation_size('big_orders_amount_idx')) AS size_after_reindex, avg_leaf_density FROM pgstatindex('big_orders_amount_idx');
SELECT dead_tuple_percent, free_percent FROM pgstattuple('big_orders');
