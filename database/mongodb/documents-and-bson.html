Documents, BSON & data types

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A MongoDB record is a document: an ordered set of field/value pairs, stored on disk and on the wire in a binary format called BSON. This page covers what a document may contain, the type system BSON provides, how _id and ObjectId work, how to reach into nested structure, and how values of different types compare.

The document and the BSON format

A document is an ordered list of fields; each field has a name (a string) and a value (one of the BSON types below). Field order is preserved as written and is significant for equality of embedded documents.

{
  "_id": 1,
  "title": "BSON basics",
  "tags": ["bson", "types"],
  "meta": { "views": 5, "draft": false }
}

BSON ("Binary JSON") is a length-prefixed binary encoding. It exists to add what plain JSON lacks for a database: distinct numeric types (32-bit vs 64-bit integers vs Decimal128), a native date type, a binary type, and an ObjectId type, plus fast traversal because every value is length-prefixed. It also drops JSON’s whitespace and repeats field names as raw bytes. See Documents in the manual for the model and Limits for the two hard constraints:

  • A single BSON document may be at most 16 MB. Larger blobs belong in GridFS or object storage.

  • The manual documents a nesting limit of 100 levels (embedded documents and arrays combined). Treat 100 as the contract: the 8.x server used to verify these pages accepted a document nested 180 levels deep and rejected one at 181 with BSONObj exceeds maximum nested object depth, but that internal ceiling is not a guarantee. In practice a document that deep is a modelling mistake long before it is a limit.

Anatomy of a BSON document

BSON is a length-prefixed format: every document starts with a 4-byte little-endian integer holding its total size, followed by a sequence of elements, followed by a single 0x00 terminator byte. Each element is one type byte, the field name as a NUL-terminated string, and then the value encoded in the way that type requires. An embedded document or array is just another length-prefixed document inside the element, which is why a reader can skip a sub-tree it does not need by jumping length bytes forward instead of parsing it.

flowchart LR subgraph DOC [BSON document] L[int32: total length] E1[element 1] E2[element 2] EN[element n] T[0x00 terminator] L --> E1 --> E2 --> EN --> T end subgraph EL [One element] TY[type byte] NM[field name as cstring] VL[value, encoded per type] TY --> NM --> VL end E2 -.-> TY VL -.->|embedded document or array| L

bsonsize() in mongosh reports the encoded size, which makes the cost of a shape visible. The sample document above, with its numeric _id, a short string, a two-element array and an embedded document, encodes to 103 bytes — much of it field names, because BSON repeats them in every document. Short field names on a billion-document collection are a real, if minor, saving.

shop> bsonsize({ _id: 1, title: "BSON basics", tags: ["bson", "types"], meta: { views: 5, draft: false } })
103
shop> db.hello().maxBsonObjectSize
16777216

The BSON type set

Each type has a canonical name and a numeric alias usable with the $type query operator.

Type Alias Notes

Double

"double"

64-bit IEEE 754 float; the default for a shell literal like 3.14.

String

"string"

UTF-8.

Object

"object"

An embedded document.

Array

"array"

An ordered list; stored as a document with numeric string keys.

Binary data

"binData"

Bytes plus a subtype (e.g. 4 for UUID).

ObjectId

"objectId"

12-byte identifier; see below.

Boolean

"bool"

true / false.

Date

"date"

Milliseconds since the Unix epoch, signed (dates before 1970 are negative).

Null

"null"

An explicit null value.

Regular expression

"regex"

A pattern plus option flags.

32-bit integer

"int"

Int32.

64-bit integer

"long"

Int64 / NumberLong.

Decimal128

"decimal"

128-bit IEEE 754-2008 decimal float; exact base-10, for money.

Timestamp

"timestamp"

Internal replication timestamp; not for application dates.

MinKey / MaxKey

"minKey" / "maxKey"

Sort below / above every other value.

The full list, including deprecated types, is at BSON Types. In mongosh the non-JSON types have constructors:

db.samples.insertOne({
  _id: 1,
  amount:   Decimal128("19.99"),      // exact decimal, not 19.99 as a Double
  count:    Long("9007199254790000"), // 64-bit integer beyond Double's safe range
  when:     ISODate("2026-01-15T00:00:00Z"),
  blob:     BinData(0, "SGVsbG8="),   // subtype 0, base64 payload
  pattern:  /^bson/i
})

Why Decimal128 for money: a binary Double cannot represent most decimal fractions exactly, so sums drift, whereas Decimal128 keeps base-10 digits. Run against the shop database:

shop> db.d.insertOne({ _id: 1, a: Decimal128("0.1"), b: 0.1 })
shop> db.d.aggregate([{ $project: { exact: { $add: ["$a", Decimal128("0.2")] }, binary: { $add: ["$b", 0.2] } } }])
[ { _id: 1, exact: Decimal128('0.3'), binary: 0.30000000000000004 } ]

The shop’s price fields are plain doubles to keep the examples short; a production catalogue would store Decimal128 (or integer cents) and keep the type consistent across every document.

Extended JSON

JSON has no syntax for a date or a Decimal128, so MongoDB tools exchange those types using Extended JSON: wrapper objects with $-prefixed keys. The "canonical" mode is type-preserving; "relaxed" mode emits plain JSON numbers and ISO date strings where it can.

{
  "_id": { "$oid": "64f0a1c3e13b1f00a8d9e4b2" },
  "amount": { "$numberDecimal": "19.99" },
  "count": { "$numberLong": "9007199254790000" },
  "when": { "$date": "2026-01-15T00:00:00Z" }
}

EJSON in mongosh converts in both directions, and the relaxed flag chooses between the two modes. The same values written in canonical and then relaxed form:

shop> EJSON.stringify({ when: ISODate("2026-01-15T00:00:00Z"), n: Int32(5), l: Long("5") }, { relaxed: false })
{"when":{"$date":{"$numberLong":"1768435200000"}},"n":{"$numberInt":"5"},"l":{"$numberLong":"5"}}
shop> EJSON.stringify({ when: ISODate("2026-01-15T00:00:00Z"), n: Int32(5), l: Long("5") }, { relaxed: true })
{"when":{"$date":"2026-01-15T00:00:00Z"},"n":5,"l":5}

Canonical mode keeps Int32 and Int64 distinct; relaxed mode collapses both to a bare JSON number, so a round trip through relaxed JSON can change a field’s BSON type. Use canonical mode when types must survive.

mongoexport, mongoimport, and EJSON in mongosh all speak this format; see MongoDB Extended JSON (v2). Tooling that reads and writes these files is covered in Backup & data tools.

_id and ObjectId

Every document has an _id field whose value is unique within its collection and immutable once written. It is always the first field on disk and is automatically backed by a unique index. If you do not supply _id on insert, the driver or server generates an ObjectId.

An ObjectId is 12 bytes:

  • a 4-byte value: seconds since the Unix epoch (the creation time, readable via ObjectId.prototype.getTimestamp());

  • a 5-byte per-process random value;

  • a 3-byte counter that increments per process, starting from a random value.

Because the leading bytes are a timestamp, ObjectId values generated over time are roughly monotonic — they sort close to insertion order, though not strictly so under concurrency or clock skew. See ObjectId() in the manual.

// Server-generated _id.
db.events.insertOne({ kind: "login" })
// { acknowledged: true, insertedId: ObjectId('64f0a1c3e13b1f00a8d9e4b2') }

// Supply your own _id -- any unique, non-array BSON value is allowed.
db.events.insertOne({ _id: "2026-01-15#login", kind: "login" })

// Recover the creation time embedded in an ObjectId.
ObjectId("64f0a1c3e13b1f00a8d9e4b2").getTimestamp()
// ISODate('2023-08-31T14:20:51.000Z')   <- the first 4 bytes, 0x64f0a1c3, are seconds since the epoch

The creation-time prefix is why an ObjectId is a convenient default key and a mild information leak: anyone who sees one knows when the document was created. A sequential or business key can be a better _id when the creation time must not leak, or when the key is also the natural lookup field (it saves a second unique index). Whichever you choose, avoid arrays and regular expressions as _id, and remember that _id cannot change after the insert — changing it means deleting and re-inserting the document.

Embedded documents, arrays, and dot notation

Values can be embedded documents, arrays of scalars, or arrays of documents, nested within the 100-level limit. Dot notation addresses a nested field as a single string: field names joined by ., with a non-negative integer segment selecting an array position.

db.people.insertOne({
  _id: 1,
  name: "Ada Lovelace",
  contact: { email: "ada@example.com", address: { city: "London", zip: "N1 9GU" } },
  items: [ { sku: "A-1", qty: 2 }, { sku: "B-7", qty: 1 } ]
})

// Reach into an embedded document.
db.people.find({ "contact.address.city": "London" })

// Match a specific array position, then any array element.
db.people.find({ "items.0.sku": "A-1" })   // first element only
db.people.find({ "items.sku": "B-7" })     // any element of items

The same paths work against the shop’s orders, whose items array holds subdocuments. A path through an array fans out over its elements, so one dotted name can reach many values:

shop> db.orders.find({ "items.0.sku": "A-1" }, { _id: 1 })    // only the FIRST line item is tested
[ { _id: 1001 } ]
shop> db.orders.find({ "items.sku": "A-1" }, { _id: 1 })      // ANY line item
[ { _id: 1001 }, { _id: 1004 } ]
shop> db.orders.find({ "items.qty": { $gte: 4 } }, { _id: 1 })
[ { _id: 1004 }, { _id: 1008 } ]

shop> db.orders.aggregate([ { $match: { _id: 1004 } },
...   { $project: { _id: 0, firstSku: { $arrayElemAt: ["$items.sku", 0] }, skus: "$items.sku", n: { $size: "$items" } } } ])
[ { firstSku: 'A-2', skus: [ 'A-2', 'A-1' ], n: 2 } ]

Quote any dotted key in the shell. Dot-notation matching semantics — especially how a query on items.sku matches across array elements, and how $elemMatch differs — are covered in Querying documents. See Dot notation in the manual.

Comparison and sort order across types

When queried values (or values in a sort) have different BSON types, MongoDB orders them by type first, using this fixed order (lowest to highest):

  1. MinKey

  2. Null

  3. Numbers (Int32, Int64, Double, Decimal128 — compared by numeric value, across the four types)

  4. String

  5. Object (embedded document)

  6. Array

  7. BinData

  8. ObjectId

  9. Boolean

  10. Date

  11. Timestamp

  12. Regular expression

  13. MaxKey

The authoritative table is at Comparison/Sort Order. Two consequences worth remembering:

  • Null versus missing. A query { field: null } matches both documents where field holds null and documents where field is absent. To match only an explicit null, combine with a type check: { field: { $type: "null" } }. To match only "present", use { field: { $exists: true } }.

  • Numeric-type conflation. The numeric types sort and compare by value, so 1, 1.0, and NumberLong(1) are equal for query matching and indexing. They are still stored as distinct BSON types, and $type distinguishes them — { n: { $type: "int" } } will not match a value stored as a Double. Choose one numeric type per field, and use Decimal128 for money to avoid binary-float rounding.

The null-versus-missing distinction is easy to check:

shop> db.nm.insertMany([ { _id: 1, f: null }, { _id: 2 }, { _id: 3, f: 0 } ])
shop> db.nm.find({ f: null })                 // explicit null AND missing
[ { _id: 1, f: null }, { _id: 2 } ]
shop> db.nm.find({ f: { $type: "null" } })    // explicit null only
[ { _id: 1, f: null } ]
shop> db.nm.find({ f: { $exists: false } })   // missing only
[ { _id: 2 } ]

In mongosh an unadorned number literal such as 1 or 1.0 is stored as a 32-bit integer when it fits; use Double(1) to store a genuine double and Long("1") for a 64-bit integer (pass a string, because a JavaScript number loses precision above 2^53). Running the experiment against the shop database:

shop> db.types.insertMany([ { n: 1 }, { n: Double(1) }, { n: Long("1") }, { n: "1" } ])
shop> db.types.aggregate([ { $project: { _id: 0, n: 1, t: { $type: "$n" } } } ])
[
  { n: 1, t: 'int' },
  { n: 1, t: 'double' },
  { n: Long('1'), t: 'long' },
  { n: '1', t: 'string' }
]

shop> db.types.countDocuments({ n: 1 })                    // int, double and long all equal 1
3
shop> db.types.countDocuments({ n: { $type: "int" } })     // only the value stored as Int32
1
shop> db.types.countDocuments({ n: { $type: "number" } })  // the "number" alias covers all four numeric types
3
shop> db.types.find({ n: { $lt: "2" } }, { _id: 0 })       // a string compares only with strings
[ { n: '1' } ]

The same type-bracketing applies to sorting. A sort across a deliberately mixed field returns the type order of the table above, from minKey up to maxKey:

shop> db.mix.aggregate([ { $sort: { v: 1 } }, { $project: { _id: 0, t: { $type: "$v" } } } ])
// minKey < null < int < string < object < binData < objectId < bool < date < timestamp < regex < maxKey

An array value does not sit at a fixed place in that order for a sort: ascending sort uses the array’s smallest element and descending sort uses its largest. With documents { v: [5, 1] }, { v: 3 } and { v: [2] }, an ascending sort returns them in the order [5, 1] (smallest element 1), [2], 3 — and the descending order is [5, 1] (largest element 5), 3, [2].
