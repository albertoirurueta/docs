Text, wildcard, geospatial & Atlas search

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Beyond ordinary single-field and compound indexes, MongoDB has index types built for specific access patterns: full-text matching, unpredictable field names, points and shapes on a sphere, and hash-distributed keys. This page covers each with a runnable example, then points to the Atlas-only search products. For the general index model and explain() see Indexing & query performance.

Which one to reach for depends on the question the query asks:

flowchart TD Q[What does the query look for?] --> W{Words inside long strings?} W -- yes --> T{Simple keyword match enough?} T -- yes --> TX[Text index and text query] T -- "no: relevance tuning, fuzzy, autocomplete, facets" --> AS[Atlas Search] W -- no --> G{Distance or containment on a map?} G -- yes --> GE[2dsphere index, 2d only for flat planes] G -- no --> N{Field names unknown in advance?} N -- yes --> WC[Wildcard index] N -- no --> H{Shard key on a monotonic value, equality lookups only?} H -- yes --> HA[Hashed index] H -- no --> OR[Ordinary single-field or compound index] Q --> V{Meaning of text, not exact words?} V -- yes --> VS[Atlas Vector Search]

Text indexes and $text

A text index tokenises string fields (and string elements of arrays) so $text can match by word rather than by exact string. Declare it with the special "text" direction; use "$**" as the field to index every string field. See Text indexes and Text search.

db.articles.createIndex({ title: "text", body: "text" })

db.articles.find({ $text: { $search: "mongodb index" } })   // matches "indexes", "indexing" via stemming

A collection may have only one text index, though that index can span many fields. Use $meta: "textScore" to project and sort by relevance. See $text and $meta.

db.articles.find(
  { $text: { $search: "mongodb index" } },
  { score: { $meta: "textScore" }, title: 1 }
).sort({ score: { $meta: "textScore" } })

On the shop’s products, a text index over name (weight 10) and tags (weight 1) turns the catalogue into a searchable store. Searching for desk finds both desks, and the per-word weights show up in the score:

shop> db.products.createIndex({ name: "text", tags: "text" }, { weights: { name: 10, tags: 1 }, name: "products_text" })
shop> db.products.find({ $text: { $search: "desk" } }, { name: 1, score: { $meta: "textScore" } }).sort({ score: { $meta: "textScore" } })
[ { _id: 'A-1', name: 'Standing Desk', score: 7.5 }, { _id: 'B-7', name: 'Desk Lamp', score: 7.5 } ]

shop> db.products.find({ $text: { $search: "office -lamp" } }, { name: 1 })      // a leading minus excludes a term
[ { _id: 'A-2', name: 'Office Chair' }, { _id: 'C-9', name: 'Monitor 27in' }, { _id: 'A-1', name: 'Standing Desk' } ]

shop> db.products.find({ $text: { $search: "ergonomics" } }, { name: 1 })        // stemming: ergonomics -> ergonom
[ { _id: 'A-2', name: 'Office Chair' }, { _id: 'A-1', name: 'Standing Desk' } ]

shop> db.products.find({ $text: { $search: "\"usb c\"" } }, { name: 1 })          // a quoted phrase matches the raw string
[]

Several lessons are in those results. A space-separated search is an OR of terms (office -lamp returns anything tagged office, minus the lamp), not an AND. The stemmer maps ergonomics and the stored tag ergonomic to the same root, which is why the plural query matches. The phrase "usb c" matches nothing even though the catalogue holds USB-C Hub: a phrase is checked against the original text, and the original contains USB-C, not usb c. And the two desks tie at 7.5, so add a tiebreaker to the sort when order matters. The same score is available inside the pipeline: { $match: { $text: { $search: "desk" } } } followed by { $set: { score: { $meta: "textScore" } } } and a $sort.

The index’s default_language sets the stemming and stop-word rules; a per-document language field can override it. weights scale each field’s contribution to the score, so a match in the title can outrank a match in the body.

db.articles.createIndex(
  { title: "text", body: "text" },
  { default_language: "english", weights: { title: 10, body: 1 } }
)

The built-in text index is adequate for simple keyword lookup. For real search workloads — relevance tuning, analyzers, autocomplete, faceting, fuzzy matching — Atlas Search and Atlas Vector Search supersedes it and is the recommended path on Atlas.

Wildcard indexes

A wildcard index uses the "$**" key to index fields whose names are not known in advance — an attribute bag such as attributes.color, attributes.ramGb, attributes.warrantyMonths that differs per document. wildcardProjection restricts it to (or excludes) a sub-tree. See Wildcard indexes.

db.products.createIndex({ "attributes.$**": 1 })

db.products.find({ "attributes.color": "blue" })          // uses the wildcard index
db.products.find({ "attributes.ramGb": { $gte: 16 } })    // and so does this

Against a small catalogue where every product carries its own attribute names (a laptop has ramGb, a phone has warrantyMonths, both have color), one wildcard index serves queries on any of them. Three products, and the plans for four queries, measured with explain("executionStats"):

shop> db.items.insertMany([
...   { _id: 1, name: "Laptop", attributes: { color: "silver", ramGb: 16 } },
...   { _id: 2, name: "Phone",  attributes: { color: "blue", warrantyMonths: 24 } },
...   { _id: 3, name: "Tablet", attributes: { color: "blue", ramGb: 8 } } ])
shop> db.items.createIndex({ "attributes.$**": 1 })
// find({ "attributes.color": "blue" })                  -> FETCH <- IXSCAN(attributes.$**_1)   keys 2, docs 2, returned 2
// find({ "attributes.ramGb": { $gte: 16 } })            -> FETCH <- IXSCAN(attributes.$**_1)   keys 1, docs 1, returned 1
// find({ "attributes.color": "blue", "attributes.ramGb": 8 })
//                                                        -> FETCH <- IXSCAN(attributes.$**_1)   keys 1, docs 1, returned 1
// find({ "attributes.color": "blue" }, { _id: 0, "attributes.color": 1 })
//                                                        -> PROJECTION_DEFAULT <- IXSCAN        keys 2, docs 0, returned 2

The two-field query shows the "one field at a time" rule in action: the index answers one predicate (ramGb: 8, one key) and the other is checked on the fetched document. The last query, which projects only the indexed field, examined no documents on this 8.x server; the manual’s older statement that a wildcard index cannot cover a query is therefore version-dependent, so confirm with explain on the release you run.

Trade-offs: a wildcard index can be large (one entry per indexed leaf field per document) and slows writes accordingly; it supports only one queried field at a time (it is not a substitute for a compound index); it cannot back a sort on an unspecified field; and it never covers a query. Reach for it only when the field names really are open-ended — otherwise name the fields in an ordinary index.

Geospatial indexes

A 2dsphere index indexes points and shapes stored as GeoJSON objects on an Earth-like sphere, so distances and containment are computed correctly across the globe. It supports $near / $nearSphere (nearest-first, optionally bounded by $maxDistance in metres), $geoWithin (inside a polygon), and $geoIntersects (shares any point with a geometry). See Geospatial queries and 2dsphere indexes.

db.places.insertOne({
  name: "Cafe",
  location: { type: "Point", coordinates: [ -3.7038, 40.4168 ] }   // [ longitude, latitude ]
})
db.places.createIndex({ location: "2dsphere" })

// Nearest places within 1 km
db.places.find({
  location: {
    $nearSphere: {
      $geometry: { type: "Point", coordinates: [ -3.7038, 40.4168 ] },
      $maxDistance: 1000
    }
  }
})

// Places inside a neighbourhood polygon
db.places.find({
  location: {
    $geoWithin: {
      $geometry: { type: "Polygon", coordinates: [ [ [ -3.71, 40.41 ], [ -3.69, 40.41 ], [ -3.69, 40.43 ], [ -3.71, 40.43 ], [ -3.71, 40.41 ] ] ] }
    }
  }
})

On three pickup locations around Madrid’s centre — a cafe at the query point, a bar 272 m away and a point some 12.8 km out — the 1 km query returns the first two, and the aggregation $geoNear stage, which reports the distance, shows why:

shop> db.places.aggregate([
...   { $geoNear: { near: { type: "Point", coordinates: [-3.7038, 40.4168] }, distanceField: "dist", spherical: true } },
...   { $project: { _id: 0, name: 1, dist: { $round: ["$dist", 0] } } } ])
[ { name: 'Cafe Sol', dist: 0 }, { name: 'Bar Luna', dist: 272 }, { name: 'Far Away', dist: 12770 } ]

shop> db.places.find({ location: { $nearSphere: { $geometry: { type: "Point", coordinates: [-3.7038, 40.4168] }, $maxDistance: 1000 } } }, { name: 1, _id: 0 })
[ { name: 'Cafe Sol' }, { name: 'Bar Luna' } ]
// plan: GEO_NEAR_2DSPHERE <- FETCH <- IXSCAN(location_2dsphere), keys 25, docs 2

Note the 25 keys examined for 2 results: a geo query expands outward through index cells, so it reads neighbouring cell entries, which is normal. GeoJSON order is [ longitude, latitude ], the reverse of what most map UIs display; swapping them is the most common geospatial bug and produces valid but wrong results. $geoNear must be the first stage of a pipeline and requires a geospatial index; $near returns nearest-first without a $sort.

See $near, $geoWithin, and $geoIntersects.

The legacy 2d index indexes coordinate pairs on a flat plane ([ x, y ] legacy pairs, not GeoJSON). Use it only for planar data such as a game map or floor plan, not for points on the Earth. See 2d indexes.

db.board.createIndex({ pos: "2d" })
db.board.find({ pos: { $geoWithin: { $box: [ [ 0, 0 ], [ 100, 100 ] ] } } })

Hashed indexes

A hashed index stores the hash of a single field’s value rather than the value itself. Its main use is a hashed shard key, which spreads monotonically increasing keys (such as ObjectId or a timestamp) evenly across shards instead of piling every new document onto one chunk. Hashed indexes support equality matches but not range queries or sorts on the field. See Hashed indexes, and for how a shard key is chosen see Sharding.

db.events.createIndex({ _id: "hashed" })
sh.shardCollection("app.events", { _id: "hashed" })

The equality-only restriction is visible in the plan. After db.ev.createIndex({ k: "hashed" }) on five documents, an equality uses it and a range cannot:

shop> db.ev.createIndex({ k: "hashed" })
k_hashed
// find({ k: 1 })            -> FETCH <- IXSCAN(k_hashed)   keys 1, docs 1, returned 1
// find({ k: { $gt: 0 } })   -> COLLSCAN                    keys 0, docs 5, returned 2
shop> convertShardKeyToHashed(1)
Long('5902408780260971510')

The helper convertShardKeyToHashed() shows what is actually stored: a 64-bit hash, which is why neighbouring values land far apart and why a range of the original values cannot be a range of the index. A hashed shard key buys even distribution of writes at the price of scatter-gather for range queries on that key.

Atlas Search and Atlas Vector Search

These are Atlas-only services — available on MongoDB Atlas, not in the self-managed server — so they are described here only in outline.

Atlas Search embeds an Apache Lucene index alongside the collection and exposes it through the $search aggregation stage. It provides analyzers, relevance scoring, fuzzy matching, autocomplete, highlighting, and facets — the capabilities the built-in text index lacks — and stays in sync with the collection automatically. Use it for user-facing full-text search. See Atlas Search.

Atlas Vector Search indexes dense vector embeddings and exposes approximate nearest-neighbour queries through the $vectorSearch stage, for semantic search, recommendations, and retrieval-augmented generation. You generate embeddings with an external model, store them as an array field, and query with a query vector through $vectorSearch. See Atlas Vector Search and the $vectorSearch stage reference for the full syntax. See The Vector Database Landscape for how Atlas Vector Search compares with dedicated vector databases and other engines' bolt-on vector search.
