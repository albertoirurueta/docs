Backups, import/export & GridFS

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

There are three ways to back a MongoDB deployment up, they trade off differently, and none of them is the right answer everywhere. This page compares them, then covers moving data as JSON/CSV and storing files larger than the 16 MB document limit with GridFS.

flowchart TD Q{How big is the data set?} -->|a few GB, or one database to copy| D[mongodump / mongorestore] Q -->|tens of GB and up, self-managed| FS[Filesystem or volume snapshots] Q -->|managed, point-in-time recovery needed| AT[Atlas or Ops Manager continuous backup] D --> T1[Logical: BSON files, indexes rebuilt on restore] FS --> T2[Physical: copy of the data files, restore is a mount] AT --> T3[Snapshots plus the oplog tail, restore to any second] SH{Sharded cluster?} -->|yes| CO[Coordinate: balancer stopped, or use a tool that coordinates] T1 --> SH T2 --> SH

The examples use the running example: a replica set holding shop.orders (20,000 orders with an items array, a Decimal128 total and a compound index on customerId and orderDate) plus a few other databases.

Backup methods and their trade-offs

mongodump / mongorestore

mongodump writes every document as BSON into a directory tree (one .bson file per collection plus .metadata.json for options and indexes); mongorestore reads it back. It is simple, portable, and needs no coordination with the filesystem, which makes it a fine fit for small deployments and for copying one database into another environment.

Its costs scale badly: it reads all data through the server (competing with live traffic and churning the WiredTiger cache), and a restore has to rebuild every index afterwards. On a large data set both take hours. Add --oplog on a replica-set member so the dump captures the oplog window it spans and restores to a consistent point in time.

# Consistent dump of a whole replica-set member, gzipped, with the oplog tail.
mongodump --uri "mongodb://user:pass@rs1.example.com:27017/?replicaSet=rs0" \
          --oplog --gzip --out /backups/2026-08-30

# Restore into a fresh deployment, replaying the captured oplog.
mongorestore --uri "mongodb://user:pass@new.example.com:27017" \
             --gzip --oplogReplay /backups/2026-08-30

# Single collection (--oplog is not allowed together with --db or --collection).
mongodump --db shop --collection orders --gzip --out /backups/orders

Two restrictions showed up when this was run. mongodump --db shop --oplog fails with "oplog mode only supported on full dumps", because the oplog window only makes sense for a dump of the whole instance. And on the restore side, mongorestore --oplogReplay --nsInclude "shop.*" fails with "cannot use --oplogReplay with includes specified" for the same reason. A point-in-time consistent restore is all-or-nothing; to move one database, take a plain dump of it.

A full dump of the example replica set, with the oplog, gzip-compressed:

mongodump --oplog --gzip --out /tmp/dump
writing `shop.orders` to `/tmp/dump/shop/orders.bson.gz`
writing `bank.accounts` to `/tmp/dump/bank/accounts.bson.gz`
done dumping `shop.orders` (20000 documents)
writing captured oplog to ``
	dumped 1 oplog entry
/tmp/dump
|-- admin/system.version.bson.gz, system.version.metadata.json.gz
|-- bank/accounts.bson.gz, accounts.metadata.json.gz
|-- shop/orders.bson.gz, orders.metadata.json.gz
|-- storlab/ev_none.bson.gz, ... (one pair of files per collection)
|-- oplog.bson
`-- prelude.json.gz

oplog.bson holds the operations that happened while the dump was running; replaying them after the restore brings every collection to the same instant even though each was read at a slightly different moment. The .metadata.json file of a collection keeps its options and index definitions, which is how mongorestore knows which indexes to rebuild.

Restoring that dump into a fresh standalone server, with the oplog replayed:

mongorestore --gzip --oplogReplay /tmp/dump
restoring indexes for collection `shop.orders` from metadata
260002 document(s) restored successfully. 0 document(s) failed to restore.

Afterwards the restored shop.orders has all 20,000 documents, both indexes (_id_ and customerId_1_orderDate_-1), and the Decimal128 total is still a Decimal128 (Decimal128('7.99') for order 7): the dump is BSON, so types survive. That is the property mongoexport does not have. Pass --noIndexRestore if you want to build the indexes yourself after the load, which is faster for very large collections.

sequenceDiagram participant D as mongodump participant P as Replica set member participant F as Dump directory participant R as mongorestore participant N as New deployment D->>P: note oplog position T0 D->>P: read every collection, one cursor each P-->>D: BSON documents D->>F: collection.bson.gz and metadata.json.gz D->>P: read oplog entries from T0 to now D->>F: oplog.bson R->>F: read collections and metadata R->>N: insert documents, then build indexes R->>N: replay oplog.bson up to the dump end

See mongodump and mongorestore.

Filesystem / volume snapshots

A block-level snapshot (LVM, or a cloud provider’s EBS/persistent-disk snapshot) captures the data volume almost instantly and independently of data size, which makes it the standard method above a few tens of GB. It gives a point-in-time image if the snapshot is atomic across the whole volume.

The condition that matters: the journal must be on the same volume as the data files, so the snapshot captures a recoverable state. If data and journal live on separate volumes, you need a coordinated snapshot of both, or you must stop writes (or fsync with lock) while the snapshot is taken. Encrypted-storage and --directoryperdb layouts have extra caveats in the manual.

# LVM example: data + journal on the same logical volume.
mongosh --eval 'db.fsyncLock()'                 # flush and block writes (optional if snapshot is atomic)
lvcreate --snapshot --size 20G --name mongo_snap /dev/vg0/mongo_data
mongosh --eval 'db.fsyncUnlock()'

# Restore = mount the snapshot as the new dbPath and start mongod against it.

What fsyncLock() does can be seen directly. It flushes everything to disk and then blocks all writes while still allowing reads:

db.fsyncLock().lockCount                                   // Long('1')
db.getSiblingDB("shop").orders.insertOne({ _id: 999999, x: 1 }, { maxTimeMS: 1500 })
//   -> MaxTimeMSExpired after 1504 ms   (the write waits behind the lock)
db.getSiblingDB("shop").orders.countDocuments({ _id: { $lt: 10 } })   // 9: reads still work
db.fsyncUnlock().lockCount                                 // Long('0')
db.getSiblingDB("shop").orders.insertOne({ _id: 999999, x: 1 })       // works again

Always pair the lock with an unlock in a finally block or a trap, since a forgotten lock stops all writes. On a replica set, snapshot a secondary so the primary keeps serving writes.

See Back Up with Filesystem Snapshots.

Atlas / Ops Manager continuous backup

Atlas Backup and Ops Manager (the on-prem product) tail the oplog continuously and keep base snapshots, which together give point-in-time recovery to any second within the retention window, plus scheduled snapshot policies and automated restores. This is managed infrastructure — there is no self-hosted equivalent to run — so this page links it rather than documenting it in depth: Atlas Cloud Backup and Ops Manager Backup.

Sharded clusters

A sharded cluster cannot be backed up shard-by-shard with independent, uncoordinated snapshots: chunk migrations in flight would leave the copies mutually inconsistent. Either stop the balancer first (sh.stopBalancer()) and snapshot every shard plus a config-server member while it is stopped, or use a tool that coordinates the cluster-wide snapshot for you (Atlas, Ops Manager, or mongodump against each component with the balancer off).

mongosh --eval 'sh.stopBalancer()'
# ... snapshot every shard + one config server member ...
mongosh --eval 'sh.startBalancer()'

See Back Up a Sharded Cluster with Filesystem Snapshots and Sharding for what the balancer does and why stopping it matters.

The overview of all methods, side by side, is at MongoDB Backup Methods.

Data movement: mongoexport / mongoimport

mongoexport writes a collection as JSON or CSV; mongoimport reads those formats back. They are for data interchange — feeding a spreadsheet, loading a CSV from another system — not for backups. JSON and CSV cannot represent every BSON type faithfully: an ObjectId, a Decimal128, a Date, a Long, or a binary field either becomes MongoDB Extended JSON ({"$oid": "..."}) or, in plain CSV, loses its type entirely. Use mongodump/mongorestore whenever type fidelity matters.

# Export selected fields as CSV.
mongoexport --uri "mongodb://localhost:27017/shop" --collection orders \
            --type csv --fields _id,customerId,total,orderDate \
            --query '{ "status": "OPEN" }' --out orders.csv

# Import a JSON-lines file, upserting on _id.
mongoimport --uri "mongodb://localhost:27017/shop" --collection orders \
            --file orders.json --mode upsert --upsertFields _id

The type loss is easy to see. Exporting four fields of three open orders as CSV, and importing the file into a new collection, gives numbers and strings but no dates or decimals:

_id,customerId,total,orderDate
4,4,4.99,2023-11-14T22:17:20.000Z
8,8,8.99,2023-11-14T22:21:20.000Z
12,12,12.99,2023-11-14T22:25:20.000Z
// after: mongoimport --collection orders_csv --type csv --headerline --file orders.csv
db.orders_csv.findOne()
// { _id: 4, customerId: 4, total: 4.99, orderDate: '2023-11-14T22:17:20.000Z' }
//                           ^ a double, not Decimal128     ^ a string, not a Date

mongoimport can restore the types if the header declares them, with --columnsHaveTypes:

printf "_id.int32(),total.decimal(),orderDate.date(2006-01-02T15:04:05Z)\n1,19.99,2023-11-14T22:13:20Z\n" > typed.csv
mongoimport --uri "mongodb://localhost:27017/shop" --collection orders_typed \
            --type csv --headerline --columnsHaveTypes --file typed.csv
db.orders_typed.findOne()
// { _id: 1, total: Decimal128('19.99'), orderDate: ISODate('2023-11-14T22:13:20.000Z') }

JSON export is richer, and the shape depends on the --jsonFormat option. The default is relaxed Extended JSON (readable, but a plain int and a long look the same); canonical keeps every type explicit:

relaxed:   {"_id":4,"customerId":4,"status":"OPEN","orderDate":{"$date":"2023-11-14T22:17:20Z"},"total":{"$numberDecimal":"4.99"},"items":[{"sku":"A-4","qty":2}]}
canonical: {"_id":{"$numberInt":"4"},"customerId":{"$numberInt":"4"},"status":"OPEN","orderDate":{"$date":{"$numberLong":"1700000240000"}},"total":{"$numberDecimal":"4.99"},"items":[{"sku":"A-4","qty":{"$numberInt":"2"}}]}

bsondump converts a raw .bson file (for example one produced by mongodump) to human-readable JSON for inspection, without a running server.

bsondump --pretty /backups/2026-08-30/shop/orders.bson | head

bsondump reads plain .bson, so a dump taken with --gzip has to be decompressed first (zcat orders.bson.gz > orders.bson). On the example dump the first two documents printed as canonical Extended JSON, for instance {"_id":{"$numberInt":"1"},"customerId":{"$numberInt":"1"},"status":"SHIPPED", ...}.

See mongoexport, mongoimport, bsondump, and Documents & BSON for why the JSON/CSV round trip is lossy and what Extended JSON preserves.

GridFS: files larger than 16 MB

A single BSON document is capped at 16 MB, so a large file cannot be stored as one field. GridFS is a convention — implemented by every driver — that splits a file into 255 KB chunks stored in a <bucket>.chunks collection, with one metadata document per file in <bucket>.files (filename, length, chunkSize, upload date, optional metadata). Reads stream chunk by chunk, and range reads fetch only the chunks they need.

// mongosh has no GridFS helper; drivers do. Node.js driver:
const bucket = new mongodb.GridFSBucket(db, { bucketName: "assets" });

fs.createReadStream("video.mp4")
  .pipe(bucket.openUploadStream("video.mp4", { metadata: { owner: 42 } }));

bucket.openDownloadStreamByName("video.mp4")
      .pipe(fs.createWriteStream("out.mp4"));

The same thing in Python, run against the example set. It uploads a 5 MB file into a bucket named assets, reads the metadata, does a range read through seek and verifies a full download:

import gridfs, os
from pymongo import MongoClient

db = MongoClient("mongodb://localhost:27017/?replicaSet=rs0").media
bucket = gridfs.GridFSBucket(db, bucket_name="assets")
data = os.urandom(5_000_000)

file_id = bucket.upload_from_stream("video.bin", data, metadata={"owner": 42, "contentType": "video/mp4"})
print(db.assets.files.find_one({"_id": file_id}, {"filename": 1, "length": 1, "chunkSize": 1, "metadata": 1}))
print("chunks:", db.assets.chunks.count_documents({"files_id": file_id}))

stream = bucket.open_download_stream(file_id)
stream.seek(2_000_000)                       # jump into the middle: only the covering chunks are read
print(stream.read(1000) == data[2_000_000:2_001_000])
bucket.delete(file_id)                       # removes the files document and every chunk
{'_id': ObjectId('...'), 'filename': 'video.bin', 'length': 5000000, 'chunkSize': 261120, 'metadata': {'owner': 42, 'contentType': 'video/mp4'}}
chunks: 20
True

The default chunkSize is 261,120 bytes (255 KiB). A 5,000,000-byte file needs ceil(5000000 / 261120) = 20 chunks, as reported. A 40 MB file uploaded with mongofiles produced 154 chunk documents, each of the form { _id, files_id, n, data }, plus one files document. Two indexes make the bucket work, and the driver creates them on first use: a unique index on files_id and n in chunks, and one on filename and uploadDate in files (the latter serves "latest version of this file name").

erDiagram FILES ||--o{ CHUNKS : "has chunks" FILES { ObjectId _id string filename long length int chunkSize date uploadDate document metadata } CHUNKS { ObjectId _id ObjectId files_id int n binary data }

mongofiles is the command-line client for the same buckets. It takes the database from --db, not from the database part of the connection string: with --uri "mongodb://localhost:27017/media" and no --db, the file was stored in the test database (the default) and the media database stayed empty.

mongofiles --uri "mongodb://localhost:27017" --db media put video.bin
mongofiles --uri "mongodb://localhost:27017" --db media list
mongofiles --uri "mongodb://localhost:27017" --db media --local video.out get video.bin

list printed the name and size (video.bin and 40000000), and the downloaded file was byte-identical (cmp reported no difference). The file name stored is the argument as typed, so put /tmp/video.bin stores the name /tmp/video.bin; change to the directory first if you want the bare name.

When not to use GridFS: if you mainly need blob storage with CDN delivery, a dedicated object store (S3, GCS, Azure Blob) is cheaper, serves HTTP directly, and does not put file bytes through the database’s cache and backups. GridFS earns its place when you want files transactionally and operationally alongside your documents — same replication, same backup, same access control — or need atomic-ish range access to portions of a file.

See GridFS and mongofiles.
