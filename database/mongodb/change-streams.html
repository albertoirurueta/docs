Reacting to data changes

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A change stream is an ordered feed of the data changes happening in a collection, a database, or a whole deployment. Instead of polling, an application opens the stream and receives a change-event document for every insert, update, replace, delete, and drop as it is applied. Change streams read from the replica-set oplog, so a replica set or sharded cluster is required (see Replication).

How a change stream works

A change stream is not a separate feature bolted onto the database: it is an aggregation pipeline whose first stage, $changeStream, tails the oplog of the replica set (or, on a sharded cluster, the oplogs of every shard, merged by mongos). The server turns each oplog entry into a change event, runs your extra pipeline stages over it, and sends the result down a tailable cursor.

flowchart LR W[Writes from applications] --> P[(Primary oplog)] P --> CS["$changeStream stage"] CS --> F[Your pipeline: match, project] F --> C[Cursor held open by the driver] C --> A[Application handler] A -->|saves resume token| T[(Token store)] T -.->|after a restart| C P -->|replicated| S[(Secondary oplogs)]

Three consequences follow from that design:

  • Only majority-committed changes are delivered. A change stream reads at the majority commit point, so it never reports a write that could still be rolled back. The price is a small delay compared with the primary’s own view of the data, and no events at all while the set cannot establish a majority.

  • Events arrive in the order of the oplog (a single, total order per shard; mongos merges shards by cluster time), and every event has a unique resume token.

  • History is bounded by the oplog. A token can only be resumed while the entry it points at is still in the oplog, so size the oplog for the longest outage a consumer must survive (see Replica sets & high availability).

Opening a stream with watch

db.collection.watch() opens a stream scoped to one collection. db.watch() widens it to every collection in a database, and Mongo.watch() (the deployment-level form) covers every database except the internal admin, local, and config. The returned cursor blocks until the next event is available.

// One collection
const stream = db.orders.watch();

while (stream.hasNext()) {
  const event = stream.next();
  print(`${event.operationType} on ${event.ns.coll} -> ${JSON.stringify(event.documentKey)}`);
}

See Change Streams in the manual, and db.collection.watch() for the method signature.

The change-event document

Every event is a document with a common shape. The most-used fields:

  • _id — the resume token for this event (see Resuming a stream).

  • operationType — insert, update, replace, delete, drop, rename, invalidate, and others.

  • clusterTime — the oplog timestamp at which the change was applied.

  • ns — the namespace, as { db, coll }.

  • documentKey — the _id (plus shard-key fields on a sharded collection) of the affected document.

  • fullDocument — for insert and replace, the whole new document; for update, present only when the stream was opened with fullDocument: "updateLookup".

  • updateDescription — for update only: { updatedFields, removedFields, truncatedArrays } describing exactly what changed.

A real update event produced against the running example, by changing one order in shop.orders ($set of status and shippedAt, $unset of total) while a plain watch() was open:

{
  "_id": { "_data": "826AF32B21000000042B..." },
  "operationType": "update",
  "clusterTime": { "$timestamp": { "t": 1794321185, "i": 4 } },
  "wallTime": { "$date": "2026-11-10T14:33:05.377Z" },
  "ns": { "db": "shop", "coll": "orders" },
  "documentKey": { "_id": 1001 },
  "updateDescription": {
    "updatedFields": { "status": "SHIPPED", "shippedAt": "2026-11-10" },
    "removedFields": [ "total" ],
    "truncatedArrays": []
  }
}

Note what is not there: without fullDocument options the event carries only the delta, not the order as it now looks. On a sharded collection the documentKey also contains the shard-key fields. Changing a few orders spread over the two shards of the cluster from Horizontal scaling with sharded clusters and watching through the mongos shows exactly that:

update {'region': 'EU', 'customerId': 1, '_id': ObjectId('6af3250d05bd2f0bbebba185')} {'points': 91}
update {'region': 'US', 'customerId': 0, '_id': ObjectId('6af3250d05bd2f0bbebba184')} {'points': 111}

See Change Events for every field of every operation type.

Resuming a stream

Each event carries a resume token in its _id. Persist the token as you process events, and after a disconnect reopen the stream from where you left off instead of from "now":

  • resumeAfter: <token> — resume starting with the event after the given token. The token’s event must still be in the oplog.

  • startAfter: <token> — like resumeAfter, but it also works to restart after an invalidate event (for example when the watched collection was dropped and recreated).

  • startAtOperationTime: <timestamp> — start from a cluster time rather than a token; useful for a first start at a known point.

let resumeToken = loadSavedToken();   // application-provided
const stream = db.orders.watch([], resumeToken ? { resumeAfter: resumeToken } : {});

while (stream.hasNext()) {
  const event = stream.next();
  handle(event);
  resumeToken = event._id;
  saveToken(resumeToken);
}

Change streams require readConcern: "majority" (the effective default): an event is only delivered once its change is majority-committed and therefore cannot be rolled back. See Resume a Change Stream.

Filtering with an aggregation pipeline

watch() accepts an aggregation pipeline as its first argument. The stages run on the server against each change event, so the application receives only the events it cares about and only the fields it needs. $match, $project, $addFields, $replaceRoot, and $redact are supported.

const stream = db.orders.watch([
  { $match: {
      operationType: { $in: ["insert", "update"] },
      "fullDocument.region": "EU"
  } },
  { $project: { "fullDocument.paymentDetails": 0 } }
], { fullDocument: "updateLookup" });

See Aggregation pipeline for the stage semantics and Modify Change Stream Output.

Seeing the whole document

By default an update event carries only the delta in updateDescription. Two options add the full document:

  • fullDocument: "updateLookup" — attach a current copy of the document (fetched at lookup time, so it may already reflect later changes) as fullDocument.

  • fullDocument: "whenAvailable" / "required" together with fullDocumentBeforeChange: "whenAvailable" / "required" — include the document image from before the change as fullDocumentBeforeChange. This requires changeStreamPreAndPostImages to be enabled on the collection with collMod.

db.runCommand({ collMod: "orders", changeStreamPreAndPostImages: { enabled: true } });

const stream = db.orders.watch([], {
  fullDocument: "required",
  fullDocumentBeforeChange: "required"
});

Pre-images are stored in a hidden collection, config.system.preimages, and are kept only for as long as they might be needed by a lagging stream. To bound that storage cluster-wide, set an expiry:

db.getSiblingDB("admin").runCommand({
  setClusterParameter: { changeStreamOptions: { preAndPostImages: { expireAfterSeconds: 3600 } } }
})

See Lookup Full Document for Update Operations.

A worked consumer with resume

The following PyMongo script is the whole life cycle of a consumer on shop.orders: it filters on the server, asks for the post-image and pre-image of updates, processes two events, stores the resume token, stops, lets more changes happen while it is "down", and resumes from the saved token.

from pymongo import MongoClient

client = MongoClient("mongodb://localhost:27017/?replicaSet=rs0")
db = client.shop
db.orders.drop()
db.create_collection("orders")
db.command("collMod", "orders", changeStreamPreAndPostImages={"enabled": True})

pipeline = [{"$match": {"operationType": {"$in": ["insert", "update", "delete"]}}}]
opts = dict(full_document="updateLookup", full_document_before_change="whenAvailable")

def show(ev):
    row = {"op": ev["operationType"], "key": ev["documentKey"]["_id"]}
    if "updateDescription" in ev: row["updated"] = ev["updateDescription"]["updatedFields"]
    if ev.get("fullDocument"): row["fullDocument"] = ev["fullDocument"]
    if ev.get("fullDocumentBeforeChange"): row["before"] = ev["fullDocumentBeforeChange"]
    print(row)

stream = db.orders.watch(pipeline, **opts)
db.orders.insert_one({"_id": 1001, "customerId": 42, "status": "OPEN", "total": 19.99})
db.orders.update_one({"_id": 1001}, {"$set": {"status": "SHIPPED"}})
for _ in range(2):
    show(next(stream))
token = stream.resume_token          # persist this somewhere durable
stream.close()
print("token saved:", token["_data"][:24] + "...")

# the consumer is offline; more changes happen
db.orders.delete_one({"_id": 1001})
db.orders.insert_one({"_id": 1002, "customerId": 7, "status": "OPEN", "total": 5})

# resume exactly after the last processed event
with db.orders.watch(pipeline, resume_after=token, **opts) as stream2:
    for _ in range(2):
        show(next(stream2))

Real output:

{'op': 'insert', 'key': 1001, 'fullDocument': {'_id': 1001, 'customerId': 42, 'status': 'OPEN', 'total': 19.99}}
{'op': 'update', 'key': 1001, 'updated': {'status': 'SHIPPED'}, 'fullDocument': {'_id': 1001, 'customerId': 42, 'status': 'SHIPPED', 'total': 19.99}, 'before': {'_id': 1001, 'customerId': 42, 'status': 'OPEN', 'total': 19.99}}
token saved: 826AF31F52000000052B042C...
{'op': 'delete', 'key': 1001, 'before': {'_id': 1001, 'customerId': 42, 'status': 'SHIPPED', 'total': 19.99}}
{'op': 'insert', 'key': 1002, 'fullDocument': {'_id': 1002, 'customerId': 7, 'status': 'OPEN', 'total': 5}}

Read it line by line:

  • The update event has the delta (updated), the current document (fullDocument, from updateLookup) and the document as it was before the change (before, from the pre-image). Pre- and post-images exist only because changeStreamPreAndPostImages was enabled with collMod.

  • After the token was saved the consumer closed its stream. The delete and the second insert happened while no stream was open, yet both are delivered, in order, when the stream is reopened with resume_after. Nothing was lost and nothing was delivered twice. A delete event has no fullDocument (there is no document any more), which is why the pre-image is the only way to see what was removed.

  • stream.resume_token is also advanced by empty batches (a stream on a quiet collection still moves its token), so an idle consumer does not fall off the end of the oplog window.

Drivers resume automatically from the last token they saw after a transient error such as a failover or a network blip, so most applications persist the token only to survive their own restarts.

Invalidation, drop and startAfter

Some changes end a stream. Dropping or renaming the watched collection produces a drop (or rename) event followed by an invalidate event, after which the cursor is closed. The token of the invalidate event cannot be used with resumeAfter, but startAfter accepts it:

insert
drop
invalidate | stream alive: False
resumeAfter(invalidate): 260 InvalidResumeToken
startAfter(invalidate) -> insert {'_id': 1}

The sequence above is: insert a document, drop the collection (events insert, drop, invalidate), try to reopen with resume_after the invalidate token (error code 260, InvalidResumeToken), then reopen with start_after and carry on after the collection was recreated. A stream opened on a whole database or the whole deployment is not invalidated by a collection drop, so prefer those scopes for long-running consumers that must survive schema changes.

Typical uses

  • Cache invalidation — evict or refresh a cached entry the moment its source document changes.

  • ETL and streaming — feed a downstream warehouse, search index, or message queue with a continuous, resumable stream of changes rather than periodic full scans.

  • Notifications — push in-app or email alerts when a watched document reaches a state (for example an order becoming SHIPPED).

Because the stream is resumable, a consumer that stores its last token can stop and restart without losing or double-counting events, as long as the token is still within the oplog window.
