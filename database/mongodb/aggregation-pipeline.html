The aggregation framework

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The aggregation pipeline transforms and combines documents through an ordered list of stages. Each stage reads the stream of documents produced by the previous stage and emits a new stream, so a pipeline reads like a series of data transformations rather than a single declarative query.

The pipeline model

db.collection.aggregate() takes an array of stage documents. Stage keys start with $; the same stage may appear more than once; the order is significant. The first stage reads from the collection, every later stage reads from its predecessor’s output.

// https://www.mongodb.com/docs/manual/core/aggregation-pipeline/
db.orders.aggregate([
  { $match: { status: "shipped" } },
  { $group: { _id: "$customerId", total: { $sum: "$amount" } } },
  { $sort:  { total: -1 } },
  { $limit: 3 }
])
{ "_id": "c-42", "total": 1806.50 }
{ "_id": "c-17", "total": 1499.99 }
{ "_id": "c-08", "total": 940.00 }

The stream of documents flows stage to stage, shrinking or reshaping as it goes:

flowchart LR IN[("orders
~50k docs")] --> M["$match
status = shipped
~12k docs"] M --> G["$group
by customerId
~3k docs"] G --> S["$sort
total desc"] S --> OUT[("$merge
into top_customers")]

Run against the shop, the first pipeline above (orders with $unwind added so each line item is summed separately) answers "who spent the most on shipped orders?":

shop> db.orders.aggregate([
...   { $match: { status: "shipped" } },
...   { $unwind: "$items" },
...   { $group: { _id: "$customerId", total: { $sum: { $multiply: ["$items.qty", "$items.price"] } }, orders: { $addToSet: "$_id" } } },
...   { $sort: { total: -1 } }, { $limit: 3 } ])
[
  { _id: 'c-3', total: 1456, orders: [ 1004 ] },
  { _id: 'c-1', total: 588.48, orders: [ 1007, 1001 ] },
  { _id: 'c-2', total: 117, orders: [ 1003 ] }
]

Each stage receives only what the previous one emitted. That is also the debugging method: run the pipeline with the last stages removed and read the intermediate documents, then add stages back one at a time. Unlike a find, a pipeline can create new document shapes — the orders array of ids in the result exists in no collection.

For single-collection reads that need no grouping or joins, the plain query API is simpler and easier to index — see Querying documents. The full list of stages is the aggregation stage reference.

Worked example: revenue per category

The shop’s headline report is revenue and units sold per product category, excluding cancelled orders. The data needed lives in two collections: the quantities and prices in orders.items, the category on products. The pipeline reshapes the data in five steps:

flowchart LR A[("orders
8 docs")] --> B["$match
status not cancelled
7 docs"] B --> C["$unwind items
one doc per line
10 docs"] C --> D["$lookup products
attach category
10 docs"] D --> E["$group by category
revenue, units
3 docs"] E --> F["$sort revenue desc"]
shop> db.orders.aggregate([
...   { $match: { status: { $ne: "cancelled" } } },
...   { $unwind: "$items" },
...   { $lookup: { from: "products", localField: "items.sku", foreignField: "_id", as: "p" } },
...   { $unwind: "$p" },
...   { $group: { _id: "$p.category",
...               revenue: { $sum: { $multiply: ["$items.qty", "$items.price"] } },
...               units:   { $sum: "$items.qty" } } },
...   { $sort: { revenue: -1 } } ])
[
  { _id: 'furniture',   revenue: 1994.5, units: 8 },
  { _id: 'electronics', revenue: 435,    units: 5 },
  { _id: 'lighting',    revenue: 199.92, units: 8 }
]

Checking the arithmetic by hand is part of using the pipeline: lighting is the Desk Lamp only, 2 + 1 + 5 = 8 units at 24.99 is 199.92, and the cancelled order 1005 (two Monitors) is correctly absent from electronics. The same pipeline with the $lookup done first would join all eight orders against products before filtering; putting $match at the front shrinks the stream before the expensive stage — the single most useful habit when writing pipelines. And if the category were copied onto each order line (an Extended Reference, see Schema Design for the Document Model), the $lookup and the second $unwind would disappear entirely.

Filtering and reshaping

$match filters the stream using ordinary query syntax. Place it as early as possible: a $match at the very front of the pipeline can use a collection index.

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/match/
{ $match: { status: "active", age: { $gte: 21 } } }

$project chooses, drops, renames, and computes fields. $addFields (and its identical alias $set) add or overwrite fields while keeping everything else; $unset removes fields and is the inverse of $set.

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/project/
{ $project: { _id: 0, name: 1, year: { $year: "$createdAt" } } }

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/set/
{ $set: { fullName: { $concat: ["$first", " ", "$last"] } } }

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/unset/
{ $unset: ["ssn", "internal.notes"] }

Grouping and accumulators

$group emits one document per distinct value of its _id expression; use _id: null to fold the whole stream into a single document. Accumulator operators compute a value across the group: $sum, $avg, $min, $max, $push (all values, as an array), $addToSet (distinct values), and $first / $last (which depend on a preceding $sort).

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/group/
{ $group: {
    _id:     "$category",
    count:   { $sum: 1 },
    revenue: { $sum: "$price" },
    avgPrice:{ $avg: "$price" },
    minPrice:{ $min: "$price" },
    maxPrice:{ $max: "$price" },
    skus:    { $push: "$sku" },
    brands:  { $addToSet: "$brand" },
    firstSku:{ $first: "$sku" },
    lastSku: { $last: "$sku" }
} }

On the shop, $sortByCount: "$status" and $bucket over product prices return:

shop> db.orders.aggregate([ { $sortByCount: "$status" } ])
[ { _id: 'shipped', count: 4 }, { _id: 'open', count: 3 }, { _id: 'cancelled', count: 1 } ]

$count is shorthand for a $group that counts followed by a $project, and $sortByCount is shorthand for grouping by an expression, counting, and sorting the counts descending.

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/count/
{ $count: "matching" }

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/sortByCount/
{ $sortByCount: "$category" }

Ordering, paging, and sampling

$sort, $skip, and $limit order and window the stream. A $sort directly followed by a $limit is optimized so the engine keeps only the top N documents in memory. $sample draws a pseudo-random subset.

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/sort/
{ $sort: { createdAt: -1 } }
{ $skip: 20 }
{ $limit: 10 }

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/sample/
{ $sample: { size: 100 } }

Working with arrays

$unwind expands an array field into one document per element. preserveNullAndEmptyArrays keeps documents whose array is missing or empty instead of dropping them.

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/unwind/
{ $unwind: { path: "$items", preserveNullAndEmptyArrays: true } }

Joining and combining collections

$lookup performs a left outer join to another collection in the same database — the pipeline analogue of a SQL JOIN (contrast Queries (SELECT)). The equality form matches a local field to a foreign field:

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/lookup/
{ $lookup: {
    from: "customers",
    localField: "customerId",
    foreignField: "_id",
    as: "customer"
} }

The pipeline / let form binds local values as variables ($$name) and runs an arbitrary sub-pipeline, so the join condition can be more than equality:

{ $lookup: {
    from: "prices",
    let: { sku: "$sku", qty: "$qty" },
    pipeline: [
      { $match: { $expr: { $and: [
        { $eq:  ["$sku", "$$sku"] },
        { $lte: ["$minQty", "$$qty"] }
      ] } } },
      { $sort: { minQty: -1 } },
      { $limit: 1 }
    ],
    as: "priceBreak"
} }

The equality form on the shop joins each shipped order to its customer. Order 1001 and 1007 both resolve to Ada Lovelace because they share customerId: "c-1":

shop> db.orders.aggregate([
...   { $match: { status: "shipped" } },
...   { $lookup: { from: "customers", localField: "customerId", foreignField: "_id", as: "customer" } },
...   { $unwind: "$customer" },
...   { $project: { who: "$customer.name", city: "$customer.city", lines: { $size: "$items" } } } ])
[
  { _id: 1001, who: 'Ada Lovelace',  city: 'London',   lines: 2 },
  { _id: 1003, who: 'Alan Turing',   city: 'Wilmslow', lines: 1 },
  { _id: 1004, who: 'Grace Hopper',  city: 'New York', lines: 2 },
  { _id: 1007, who: 'Ada Lovelace',  city: 'London',   lines: 1 }
]
sequenceDiagram participant S as $lookup stage participant L as orders stream participant F as customers collection L->>S: order 1001 with customerId c-1 S->>F: find where _id equals c-1 (index on _id) F-->>S: customer document Ada Lovelace S-->>L: order 1001 with customer array of one document L->>S: order 1003 with customerId c-2 S->>F: find where _id equals c-2 F-->>S: customer document Alan Turing S-->>L: order 1003 with customer array of one document

Each input document triggers a probe of the foreign collection, so the foreign field needs an index (here _id always has one); a $lookup against an unindexed foreignField repeats a collection scan per input document. Prefer fewer, filtered input documents over a faster join.

as is always an array; follow with $unwind when a single matched document is expected. $unionWith concatenates another collection (optionally piped) onto the current stream:

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/unionWith/
{ $unionWith: { coll: "archived_orders", pipeline: [ { $match: { year: 2023 } } ] } }

$unionWith stacks one collection’s documents under another’s: stacking all four customers' ids with the first two product ids yields six documents. $graphLookup follows a reference recursively to resolve hierarchies and graphs (org charts, category trees, bill-of-materials). See Data modeling for the tree/graph patterns it pairs with.

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/graphLookup/
{ $graphLookup: {
    from: "employees",
    startWith: "$managerId",
    connectFromField: "managerId",
    connectToField: "_id",
    as: "reportingChain",
    maxDepth: 5
} }

Run on the category tree tech > hw > monitors (each node stores its parent), asking for the ancestors of monitors with depthField to record the distance:

shop> db.cats.aggregate([
...   { $match: { _id: "monitors" } },
...   { $graphLookup: { from: "cats", startWith: "$parent", connectFromField: "parent", connectToField: "_id",
...                     as: "ancestors", depthField: "depth" } },
...   { $project: { ancestors: 1 } } ])
[ { _id: 'monitors', ancestors: [ { _id: 'tech', depth: Long('1') }, { _id: 'hw', parent: 'tech', depth: Long('0') } ] } ]

depth: 0 is the immediate parent. The ancestors array is not ordered by depth, so sort or use depthField when order matters.

Splitting and reshaping the stream

$facet runs several sub-pipelines over the same input in one pass, each producing its own array — handy for a results page that needs data plus summary counts.

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/facet/
{ $facet: {
    byStatus:   [ { $group: { _id: "$status", n: { $sum: 1 } } } ],
    priceStats: [ { $group: { _id: null, avg: { $avg: "$price" } } } ]
} }

On the shop’s orders, one pass computes both the count per status and the average quantity per line:

shop> db.orders.aggregate([ { $facet: {
...   byStatus:  [ { $sortByCount: "$status" } ],
...   itemStats: [ { $unwind: "$items" }, { $group: { _id: null, avgQty: { $avg: "$items.qty" }, lines: { $sum: 1 } } } ] } } ])
[ { byStatus:  [ { _id: 'shipped', count: 4 }, { _id: 'open', count: 3 }, { _id: 'cancelled', count: 1 } ],
    itemStats: [ { _id: null, avgQty: 2.090909090909091, lines: 11 } ] } ]

Each $facet sub-pipeline sees the same input but its output must fit in a single 16 MB document (the whole $facet result is one document), and sub-pipelines cannot use indexes: put the shared $match before the $facet. $bucket groups documents into explicit ranges; $bucketAuto picks a requested number of roughly equal buckets automatically.

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/bucket/
{ $bucket: {
    groupBy: "$price",
    boundaries: [0, 10, 50, 100],
    default: "100+",
    output: { n: { $sum: 1 }, avg: { $avg: "$price" } }
} }

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/bucketAuto/
{ $bucketAuto: { groupBy: "$price", buckets: 4 } }

On the shop’s five product prices, the explicit boundaries [0, 50, 200, 1000] produce three buckets, and $bucketAuto with two buckets chooses its own edges:

shop> db.products.aggregate([ { $bucket: { groupBy: "$price", boundaries: [0, 50, 200, 1000], default: "other",
...   output: { n: { $sum: 1 }, names: { $push: "$name" } } } } ])
[ { _id: 0,   n: 2, names: [ 'Desk Lamp', 'USB-C Hub' ] },
  { _id: 50,  n: 1, names: [ 'Office Chair' ] },
  { _id: 200, n: 2, names: [ 'Standing Desk', 'Monitor 27in' ] } ]
shop> db.products.aggregate([ { $bucketAuto: { groupBy: "$price", buckets: 2 } } ])
[ { _id: { min: 24.99, max: 279 }, count: 3 }, { _id: { min: 279, max: 349 }, count: 2 } ]

A bucket’s _id is its lower bound and each range is half-open, so a value equal to a boundary belongs to the upper bucket; values outside every range land in the default bucket.

$replaceRoot / $replaceWith promote an embedded document to the top level, discarding the wrapper.

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/replaceWith/
{ $replaceWith: "$customer" }

Window functions

$setWindowFields computes values over an ordered window of documents within a partition — running totals, moving averages, ranking — without collapsing the documents the way $group does. It is the pipeline counterpart of SQL window functions; see Aggregate & Window Functions.

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/setWindowFields/
{ $setWindowFields: {
    partitionBy: "$customerId",
    sortBy: { orderDate: 1 },
    output: {
      runningTotal: { $sum: "$amount", window: { documents: ["unbounded", "current"] } },
      movingAvg:    { $avg: "$amount", window: { documents: [-2, 0] } }
    }
} }

Applied to the shop, with each order’s value first derived from its embedded lines, a running total per customer and a two-order moving average show how spending evolves without losing any order document (customer c-1 has three non-cancelled orders):

shop> db.orders.aggregate([
...   { $match: { status: { $ne: "cancelled" } } },
...   { $set: { amount: { $sum: { $map: { input: "$items", as: "i", in: { $multiply: ["$$i.qty", "$$i.price"] } } } } } },
...   { $setWindowFields: { partitionBy: "$customerId", sortBy: { orderDate: 1 },
...       output: { runningTotal: { $sum: "$amount", window: { documents: ["unbounded", "current"] } },
...                 movingAvg:    { $avg: "$amount", window: { documents: [-1, 0] } } } } },
...   { $project: { customerId: 1, amount: { $round: ["$amount", 2] }, runningTotal: { $round: ["$runningTotal", 2] }, movingAvg: { $round: ["$movingAvg", 2] } } },
...   { $sort: { customerId: 1, _id: 1 } } ])
[ { _id: 1001, customerId: 'c-1', amount: 398.98, runningTotal: 398.98, movingAvg: 398.98 },
  { _id: 1002, customerId: 'c-1', amount: 279,    runningTotal: 677.98, movingAvg: 338.99 },
  { _id: 1007, customerId: 'c-1', amount: 189.5,  runningTotal: 867.48, movingAvg: 234.25 },
  { _id: 1003, customerId: 'c-2', amount: 117,    runningTotal: 117,    movingAvg: 117 },
  { _id: 1008, customerId: 'c-2', amount: 124.95, runningTotal: 241.95, movingAvg: 120.97 },
  { _id: 1004, customerId: 'c-3', amount: 1456,   runningTotal: 1456,   movingAvg: 1456 },
  { _id: 1006, customerId: 'c-4', amount: 63.99,  runningTotal: 63.99,  movingAvg: 63.99 } ]

The window restarts for every customer (partitionBy), the first row of each partition has nothing to average with, and the output is still seven documents, one per order — the difference from $group. Window frames can be counted in documents, as here, or in a value range (for example the previous seven days of orderDate).

Writing pipeline results

$out replaces an entire target collection with the pipeline output. $merge upserts into the target, can write to any database, and controls what happens per matched / unmatched document — the basis of on-demand materialized views.

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/out/
{ $out: "report_snapshot" }

// https://www.mongodb.com/docs/manual/reference/operator/aggregation/merge/
{ $merge: {
    into: "daily_rollup",
    on: "_id",
    whenMatched: "merge",
    whenNotMatched: "insert"
} }

A $merge into a shared target can accumulate results from different pipelines. Two runs on the shop, one counting shipped orders per customer and one counting open orders, both merged by _id with whenMatched: "merge", produce one row per customer that carries both counters:

shop> db.orders.aggregate([ { $match: { status: "shipped" } }, { $group: { _id: "$customerId", shipped: { $sum: 1 } } },
...   { $merge: { into: "customer_stats", on: "_id", whenMatched: "merge", whenNotMatched: "insert" } } ])
shop> db.orders.aggregate([ { $match: { status: "open" } }, { $group: { _id: "$customerId", open: { $sum: 1 } } },
...   { $merge: { into: "customer_stats", on: "_id", whenMatched: "merge", whenNotMatched: "insert" } } ])
shop> db.customer_stats.find().sort({ _id: 1 })
[ { _id: 'c-1', shipped: 2, open: 1 }, { _id: 'c-2', shipped: 1, open: 1 }, { _id: 'c-3', shipped: 1 }, { _id: 'c-4', open: 1 } ]

$out would have replaced the whole collection on the second run. $merge needs a unique index on the on fields (the default _id qualifies) and runs the whole pipeline before writing.

Expressions and system variables

Inside stages, a string beginning with $ is a field path ("$price", "$customer.city"); any other string is a literal. Expressions nest freely and are documented in the aggregation expression operator reference.

System variables are referenced with $$: $$ROOT is the whole input document, $$NOW is the current datetime, $$CURRENT is the current object being processed, and $$REMOVE evaluates to "omit this field".

{ $project: {
    original: "$$ROOT",
    ageDays:  { $dateDiff: { startDate: "$createdAt", endDate: "$$NOW", unit: "day" } },
    tier:     { $cond: [ { $gte: ["$spend", 1000] }, "gold", "$$REMOVE" ] }
} }

A single $project combining a $reduce over the embedded lines, a $switch on the status and a conditional that removes a field with $$REMOVE, run on the first four shop orders:

shop> db.orders.aggregate([ { $project: {
...   total: { $reduce: { input: "$items", initialValue: 0, in: { $add: ["$$value", { $multiply: ["$$this.qty", "$$this.price"] }] } } },
...   label: { $switch: { branches: [ { case: { $eq: ["$status", "open"] }, then: "pending" }, { case: { $eq: ["$status", "shipped"] }, then: "done" } ], default: "other" } },
...   big:   { $cond: [ { $gte: [{ $size: "$items" }, 2] }, "multi", "$$REMOVE" ] } } }, { $limit: 4 } ])
[ { _id: 1001, total: 398.98, label: 'done',    big: 'multi' },
  { _id: 1002, total: 279,    label: 'pending' },          // big is absent, not null: $$REMOVE dropped the field
  { _id: 1003, total: 117,    label: 'done' },
  { _id: 1004, total: 1456,   label: 'done',    big: 'multi' } ]

Operators fall into families: arithmetic ($add, $subtract, $multiply, $divide, $mod), string ($concat, $toLower, $split, $regexMatch), date ($year, $dateTrunc, $dateAdd, $dateToString), array ($map, $filter, $reduce, $size, $slice, $in, $arrayElemAt), and conditional ($cond, $switch, $ifNull).

{ $addFields: {
    label: { $switch: {
      branches: [
        { case: { $eq: ["$status", "A"] }, then: "active" },
        { case: { $eq: ["$status", "P"] }, then: "pending" }
      ],
      default: "unknown"
    } },
    nickname: { $ifNull: ["$nickname", "$name"] }
} }

Aggregation expressions inside find

$expr embeds an aggregation expression in a query predicate, so it works in find, in $match, in view definitions, and in $lookup conditions. Its main use is comparing two fields of the same document.

// https://www.mongodb.com/docs/manual/reference/operator/query/expr/
db.budgets.find({ $expr: { $gt: ["$spent", "$limit"] } })

Optimization and explain

The query planner rewrites a pipeline before running it. Notable transforms: a $match (and the field selection of a $project) is pushed ahead of $group and $sort when it is safe to do so; adjacent $match stages are coalesced; and a $sort immediately followed by a $limit is combined so only the top N documents are retained. A leading $match can be served by an index — once any document-transforming stage has run, later filters cannot use one.

// https://www.mongodb.com/docs/manual/core/aggregation-pipeline-optimization/
db.orders.explain("executionStats").aggregate([
  { $match: { status: "shipped" } },
  { $group: { _id: "$customerId", total: { $sum: "$amount" } } }
])

The explain output shows the rewritten stage list and whether an IXSCAN or a COLLSCAN feeds the first stage. Three rewrites observed on the shop with an index on status (the 8.x explain nests the cursor stage under $cursor and shows the executor under queryPlan):

flowchart LR subgraph WRITTEN [As written] direction LR W1["$project customerId, status"] --> W2["$group by customerId"] --> W3["$match n greater than 1"] --> W4["$match _id equals c-1"] end subgraph RUN [As executed] direction LR R1["cursor: filter customerId equals c-1
plus the group"] --> R2["$match n greater than 1"] end WRITTEN -.->|optimizer| RUN

  • A $match on the $group key, written after the $group, was moved in front of it and translated from _id: "c-1" to customerId: "c-1": the explain shows filter: { customerId: { $eq: "c-1" } } on the collection scan feeding the GROUP, and a $match on the computed count n stays after it, because it depends on the group output. The leading $project was absorbed as well.

  • { $sort: { orderDate: -1 } }, { $limit: 2 } became a single SORT with limitAmount: 2, a top-2 sort that never holds more than two documents in memory.

  • { $match: { status: "shipped" } }, { $group: ... } read the index: GROUP ← FETCH ← IXSCAN on status_1 with the bounds ["shipped", "shipped"], and executionStats reported 3 documents returned after examining 4 keys and 4 documents — the four shipped orders. The GROUP needs customerId, so the documents are still fetched; a pipeline whose fields are all in an index can be covered, like a query.

shop> const e = db.orders.explain("executionStats").aggregate([
...   { $match: { status: "shipped" } }, { $group: { _id: "$customerId", total: { $sum: 1 } } } ])
shop> e.stages[0].$cursor.queryPlanner.winningPlan.queryPlan       // abbreviated
{ stage: 'GROUP', inputStage: { stage: 'FETCH', inputStage: { stage: 'IXSCAN', indexName: 'status_1',
    indexBounds: { status: [ '["shipped", "shipped"]' ] } } } }

On a sharded cluster the explain also reports which stages run per shard and which run on the merging node; keep as much work as possible before the first stage that needs all documents in one place (see Horizontal Scaling with Sharded Clusters).

Map-reduce is superseded

Standalone mapReduce is deprecated. It still runs on the 8.x server used for the examples in this section, with a DeprecationWarning printed by the shell, so the legacy code below can be run to compare it with the pipeline that replaces it:

shop> db.orders.mapReduce(function () { emit(this.status, 1); }, function (k, v) { return Array.sum(v); }, { out: { inline: 1 } })
DeprecationWarning: Collection.mapReduce() is deprecated. Use an aggregation instead.
{ results: [ { _id: 'open', value: 3 }, { _id: 'shipped', value: 4 }, { _id: 'cancelled', value: 1 } ], ok: 1 }

shop> db.orders.aggregate([ { $sortByCount: "$status" } ])      // the same counts, in native code
[ { _id: 'shipped', count: 4 }, { _id: 'open', count: 3 }, { _id: 'cancelled', count: 1 } ]

Every grouping it expressed is covered by $group (with $accumulator / $function for the rare case that genuinely needs custom JavaScript), and the pipeline optimizes and parallelizes far better. See the aggregation pipeline overview for the recommended approach.

For the relational treatment of grouping, rollups, and windowing, see Aggregate & Window Functions and Queries (SELECT).
