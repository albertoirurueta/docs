Reading hits back

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A TopDocs gives back doc ids and scores, nothing else. To show results you fetch the stored copy of each document, and to sort, group or compute over them you read the columnar (doc-values) copy. Lucene 10 exposes both through small per-reader accessor objects obtained from the searcher.

Stored fields

searcher.storedFields() returns a StoredFields bound to the current reader. document(docId) materialises a Document from the stored fields written at index time. The old IndexSearcher.doc(int) and IndexReader.document(int) methods no longer exist in Lucene 10 (a reflection check for a method named doc on IndexSearcher found none) — use the accessor.

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/StoredFields.html
import org.apache.lucene.index.StoredFields;
import org.apache.lucene.document.Document;

StoredFields storedFields = searcher.storedFields();   // not thread-safe: one per thread
for (ScoreDoc sd : hits.scoreDocs) {
    Document doc = storedFields.document(sd.doc);
    String title = doc.get("title");
    String url   = doc.get("url");
}

Selective loading with StoredFieldVisitor

Loading only the fields a result page displays avoids building String and byte[] values you will throw away. The Set overload is the shortcut; a StoredFieldVisitor gives full control, including aborting once the wanted fields are in hand. What it does not avoid is decompression: stored fields are compressed in blocks that hold several documents, and reading any field of a document inflates the block it lives in.

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/StoredFieldVisitor.html
import java.util.Set;
import org.apache.lucene.index.FieldInfo;
import org.apache.lucene.index.StoredFieldVisitor;

Document slim = storedFields.document(docId, Set.of("title", "url"));

class TitleOnly extends StoredFieldVisitor {
    String title;
    @Override public Status needsField(FieldInfo fi) {
        if (fi.name.equals("title")) return Status.YES;
        return title != null ? Status.STOP : Status.NO;   // skip fields before title, stop right after it
    }
    @Override public void stringField(FieldInfo fi, String value) { title = value; }
}
TitleOnly v = new TitleOnly();
storedFields.document(docId, v);

Stored fields are visited in the order they were added, so a visitor that answers STOP for the first field it does not want would stop before it ever reached title in the catalog (where isbn precedes title). The correct shape is NO for fields that come before the wanted ones and STOP only once everything wanted has been seen. On the catalog the visitor above returned title=Lucene in Action after being asked about three fields (isbn answered NO, title answered YES, author answered STOP) instead of five.

StoredFieldVisitor has a typed callback per stored type (stringField, intField, longField, floatField, doubleField, binaryField); needsField returns YES, NO or STOP.

The cost is easy to measure. A 50,000-document index stored a small title and a 2.6 KB body per document in one segment, and the test fetched 5,000 hits eight times, once reading the whole document and once only title through the Set overload. The two variants were indistinguishable: 103 to 213 ms for whole documents and 128 to 184 ms for title-only, about 27 microseconds per hit either way. The time is the stored-field block decompression, which both variants pay. The practical consequences are that selective loading is worth doing for allocation and garbage reasons but will not rescue a result page that fetches hundreds of large documents; for that, keep large payloads out of the Lucene stored fields entirely (store them in a database or file keyed by the isbn), or load only the hits the page really displays, or move small hot fields to doc values, which are column-oriented and cheap to read.

Doc values for computed columns

Stored fields are the display copy; doc values are the per-segment columnar copy used for sorting, faceting and any custom per-hit computation. Read them by segment, mapping a global doc id to the segment-local id with leaf.docBase.

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/DocValues.html
import org.apache.lucene.index.DocValues;
import org.apache.lucene.index.LeafReaderContext;
import org.apache.lucene.index.NumericDocValues;

for (LeafReaderContext leaf : searcher.getIndexReader().leaves()) {
    NumericDocValues price = DocValues.getNumeric(leaf.reader(), "price");
    int local = globalDocId - leaf.docBase;
    if (local >= 0 && local < leaf.reader().maxDoc() && price.advanceExact(local)) {
        long value = price.longValue();
    }
}

Field types and how to index the doc-values variant are on Documents & fields.

Term vectors

If a field was indexed with term vectors, reader.termVectors().get(docId, field) (the accessor hangs off the IndexReader, not the searcher) returns a per-document Terms — the terms, frequencies and (optionally) positions/offsets for that one document. It is the input to the fast highlighters and to "more like this".

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/index/TermVectors.html
import org.apache.lucene.index.TermVectors;
import org.apache.lucene.index.Terms;
import org.apache.lucene.index.TermsEnum;
import org.apache.lucene.util.BytesRef;

TermVectors termVectors = reader.termVectors();
Terms tv = termVectors.get(docId, "body");   // null if the field has no term vectors
if (tv != null) {
    TermsEnum te = tv.iterator();
    BytesRef term;
    while ((term = te.next()) != null) {
        long freq = te.totalTermFreq();
    }
}

The catalog, end to end

The three accessors on the same three hits. The query is description:lucene, the description field was indexed with term vectors (positions and offsets), and each book also carries a price_cents doc value. A search returned three hits; selectively loading only title and year read two of the five stored fields of each:

doc 3 full fields=5 slim fields=2 -> Lucene in Action (2010)
doc 5 full fields=5 slim fields=2 -> Solr in Action (2014)
doc 4 full fields=5 slim fields=2 -> Elasticsearch: The Definitive Guide (2015)

doc values:  doc 3 price_cents=2050   doc 5 price_cents=2750   doc 4 price_cents=2400

term vector of doc 3 'description' (term@startOffset-endOffset):
  analysis@52-60 and@61-64 applications@16-28 building@0-8 indexing@42-50 lucene@34-40 search@9-15 searching@65-74 with@29-33

The doc-values loop does the one non-obvious step: a hit’s doc is a reader-wide id, so the code finds the leaf (ReaderUtil.subIndex(doc, leaves)) and subtracts its docBase before calling advanceExact on that leaf’s doc values. Skipping the subtraction reads the wrong document on every multi-segment index. The term vector lists terms in alphabetical order with the character offsets of the first occurrence, so lucene@34-40 locates the word in Building search applications with Lucene: indexing, ...; this is what a highlighter uses. A field without term vectors (the catalog’s title) returns null from termVectors().get, so the check in the sample is not optional.

flowchart LR H["ScoreDoc: global doc id 3"] --> L["ReaderUtil.subIndex: which leaf?"] L --> LC["LeafReaderContext: ord, docBase"] LC --> S["storedFields().document(3): display copy"] LC --> DV["DocValues.getNumeric(leaf.reader(), field).advanceExact(3 - docBase)"] H --> TV["reader.termVectors().get(3, field)"] S --> OUT["title, year, ..."] DV --> OUT2["price_cents"] TV --> OUT3["terms, offsets, positions"]

Paging with searchAfter

searchAfter(ScoreDoc after, Query, n) resumes ranking just past a hit from the previous page, avoiding the growing cost of search(query, pageStart + pageSize). With a sort, after must be the FieldDoc returned for the last hit so its sort values travel with it.

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/IndexSearcher.html#searchAfter(org.apache.lucene.search.ScoreDoc,org.apache.lucene.search.Query,int)
int PAGE = 20;

TopDocs page1 = searcher.search(query, PAGE);
ScoreDoc last = page1.scoreDocs[page1.scoreDocs.length - 1];
TopDocs page2 = searcher.searchAfter(last, query, PAGE);

// Sorted paging: cast the cursor to FieldDoc and pass the same Sort.
TopFieldDocs s1 = (TopFieldDocs) searcher.search(query, PAGE, sort);
FieldDoc sLast = (FieldDoc) s1.scoreDocs[s1.scoreDocs.length - 1];
TopFieldDocs s2 = (TopFieldDocs) searcher.searchAfter(sLast, query, PAGE, sort);

On the catalog, sorting by year descending and then by title_sort, in pages of three, produced three pages with no row repeated or skipped:

page 1 (total 8): 2018 Effective Java | 2015 Elasticsearch: The Definitive Guide | 2015 The Go Programming Language
page 2 (total 8): 2014 Solr in Action | 2010 Lucene in Action | 2008 Introduction to Information Retrieval
page 3 (total 8): 2006 Java Concurrency in Practice | 2005 Head First Java

Two things make this exact. The two 2015 books are separated by the second sort key (title_sort), a tie-breaker you should always provide, because two hits with equal sort values and no tie-breaker make searchAfter ambiguous. And the cursor is the FieldDoc of the last hit: its fields array holds the sort values ([2018, [65 66 66 ...]] for the first row: the year and the title bytes), and searchAfter resumes strictly after that tuple. For score paging (searchAfter with a ScoreDoc) on title:java with a page size of two, page one was Effective Java, Head First Java and page two Java Concurrency in Practice.

A stable searcher across pages

Every page of one result set must run against the same IndexSearcher. Doc ids are only stable within a reader generation: after a merge or a reopen they are renumbered, so a cursor captured against the old reader points at the wrong documents and counts drift. Hold the searcher for the pagination session — keep the IndexSearcher acquired from SearcherManager (see Near-real-time search) until the user stops paging, or cache it under a short-lived search token — and release it when done. Reopen the reader only when the user starts a fresh query, or deliberately to surface new documents, accepting that deep cursors are then invalidated. The equivalent trade-off in a distributed engine — search_after plus a point-in-time reader — is covered in Elasticsearch: Search API & pagination.
