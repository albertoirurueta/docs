Token-filter recipes

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Once the analysis pipeline and CustomAnalyzer are in place, most real work is choosing the right token filters and ordering them correctly. This page is a set of recipes — each a self-contained CustomAnalyzer or Analyzer — for the filters in the lucene-analysis-common module that come up again and again. Every class here has SPI-name and factory forms; see the analysis-common package summary for the full catalogue.

Folding: lower-casing and accent removal

LowerCaseFilter normalises case; ASCIIFoldingFilter maps accented Latin-1/Latin-Extended characters to their ASCII base (café → cafe), optionally keeping the original token with preserveOriginal=true so an exact accented match still scores. Fold with the same chain at index and query time.

// https://lucene.apache.org/core/10_0_0/analysis/common/org/apache/lucene/analysis/miscellaneous/ASCIIFoldingFilter.html
Analyzer folding = CustomAnalyzer.builder()
    .withTokenizer("standard")
    .addTokenFilter("lowercase")
    .addTokenFilter("asciiFolding", "preserveOriginal", "false")
    .build();

Run on Café Zürich Œuvre, the chain with preserveOriginal=false produces cafe, zurich, oeuvre — note that the ligature Œ expands to the two letters oe. With preserveOriginal=true the filter emits the folded form and then the original at the same position (cafe, café, zurich, zürich, oeuvre, œuvre); the original has a position increment of 0, so phrase queries are unaffected and both spellings match.

For non-Latin scripts reach for the ICU filters instead — see Pluggable language modules.

Stop words

StopFilter drops high-frequency, low-signal terms. Pass an explicit CharArraySet rather than relying on a language default when you can, and remember that removing stop words changes phrase positions — a slop-0 "to be or not to be" phrase cannot match an index that dropped every word in it.

// https://lucene.apache.org/core/10_0_0/analysis/common/org/apache/lucene/analysis/core/StopFilter.html
CharArraySet stop = new CharArraySet(Arrays.asList("a", "an", "the", "of", "and"), true);

Analyzer withStop = CustomAnalyzer.builder()
    .withTokenizer("standard")
    .addTokenFilter("lowercase")
    .addTokenFilter("stop", "words", "stopwords.txt", "ignoreCase", "true") // file on the resource path
    .build();
// or programmatically: new StopFilter(tokenStream, stop)

With no words parameter the stop factory uses the default English stop set, which contains to, be, or and not: the chain above turns To be or not to be into an empty token stream, and Lucene in Action through a StandardAnalyzer that carries that set becomes lucene, action. A field whose every token is a stop word indexes nothing and can never be found, which is the practical argument for keeping the stop set empty on titles and short fields and relying on BM25’s idf instead.

Synonyms: SynonymGraphFilter + FlattenGraphFilter

SynonymGraphFilter emits a token graph so multi-word synonyms (ny <→ new york) keep correct positions. A graph cannot be written to the index as-is, so the index analyzer must append FlattenGraphFilter as the last filter; the query analyzer uses SynonymGraphFilter alone (the query path consumes the graph directly).

flowchart LR subgraph index [Index analyzer] A[tokenizer] --> B[LowerCaseFilter] --> C[SynonymGraphFilter] --> D[FlattenGraphFilter] --> E[(postings)] end subgraph query [Query analyzer] F[tokenizer] --> G[LowerCaseFilter] --> H[SynonymGraphFilter] --> I[Query graph] end
// https://lucene.apache.org/core/10_0_0/analysis/common/org/apache/lucene/analysis/synonym/SynonymGraphFilter.html
// https://lucene.apache.org/core/10_0_0/analysis/common/org/apache/lucene/analysis/synonym/SynonymMap.Builder.html
SynonymMap.Builder b = new SynonymMap.Builder(true);
CharsRefBuilder reuse = new CharsRefBuilder();
// A multi-word side must be joined with SynonymMap.WORD_SEPARATOR, not written with a space.
b.add(new CharsRef("ny"), SynonymMap.Builder.join(new String[] {"new", "york"}, reuse), true);
b.add(new CharsRef("laptop"), new CharsRef("notebook"), true);
final SynonymMap synonyms = b.build();

Analyzer indexAnalyzer = new Analyzer() {
    @Override
    protected TokenStreamComponents createComponents(String field) {
        Tokenizer src = new StandardTokenizer();
        TokenStream tok = new LowerCaseFilter(src);
        tok = new SynonymGraphFilter(tok, synonyms, true);
        tok = new FlattenGraphFilter(tok);            // index-time only; org.apache.lucene.analysis.core
        return new TokenStreamComponents(src, tok);
    }
};
// Query analyzer: identical but WITHOUT FlattenGraphFilter.

The join call matters. Writing new CharsRef("new york") for the replacement looks natural but registers a single token that contains a space, so ny expands to the one term new york and neither new nor york is ever produced; the map must separate the words with the internal WORD_SEPARATOR character, which join inserts.

Run on NY laptop, the filter emits the original token and its synonyms on the same position, and the multi-word synonym is a graph path whose PositionLength spans two positions:

new       pos=0 inc=1 len=1 [0,2)
ny        pos=0 inc=0 len=2 [0,2)
york      pos=1 inc=1 len=1 [0,2)
notebook  pos=2 inc=1 len=1 [3,9)
laptop    pos=2 inc=0 len=1 [3,9)

ny covers positions 0 and 1 (len=2), exactly the span of new york. That is what lets a query analyzer turn a phrase into a correct graph. Against an index of three plain titles (New York travel guide, Notebook buying guide, Travel to Paris) indexed with no synonyms at all, a query parser that uses the synonym-aware analyzer finds what the plain one cannot:

Query Plain analyzer Synonym-aware query analyzer Hits (plain / synonym)

ny guide

title:ny title:guide

((+title:new +title:york) title:ny) title:guide

2 / 2

laptop

title:laptop

Synonym(title:laptop title:notebook)

0 / 1

"ny travel"

title:"ny travel"

title:"new york travel" title:"ny travel"

0 / 1

Both the new york travel phrase and the original ny travel phrase are tried: the graph was expanded into two alternative phrase queries. This is query-time expansion, which needs no reindex when the synonym list changes. Doing the expansion at index time instead (the analyzer above with FlattenGraphFilter) makes queries cheaper but ties every document to the synonym list that was current when it was indexed.

Stemming and lemmatization

Four interchangeable reducers, roughly from most aggressive to least:

Filter Notes

PorterStemFilter

Classic Porter algorithm, English only, no options; fast and aggressive (generously → gener).

KStemFilter

Less aggressive English stemmer that stays closer to real words (generously → generous); good default for English relevance.

SnowballFilter

Snowball (Porter2) with a language parameter — English, French, German, Spanish, Russian, …​ — the multi-language choice. Its CustomAnalyzer factory name is snowballPorter.

StemmerOverrideFilter

Not a stemmer: a dictionary that pins listed words to a fixed stem and marks them keyword so a later stemmer leaves them alone. Place it before the real stemmer.

 
// https://lucene.apache.org/core/10_0_0/analysis/common/org/apache/lucene/analysis/en/KStemFilter.html
// https://lucene.apache.org/core/10_0_0/analysis/common/org/apache/lucene/analysis/miscellaneous/StemmerOverrideFilter.html
StemmerOverrideFilter.Builder ob = new StemmerOverrideFilter.Builder();
ob.add("mice", "mouse");
ob.add("aging", "age");
final StemmerOverrideFilter.StemmerOverrideMap overrides = ob.build();

Analyzer english = new Analyzer() {
    @Override
    protected TokenStreamComponents createComponents(String field) {
        Tokenizer src = new StandardTokenizer();
        TokenStream tok = new LowerCaseFilter(src);
        tok = new StemmerOverrideFilter(tok, overrides);
        tok = new KStemFilter(tok);                   // swap for PorterStemFilter / SnowballFilter
        return new TokenStreamComponents(src, tok);
    }
};

The differences are easiest to see on one word list. Running generously mice aging running studies organization through each chain after lowercasing:

Chain Terms

PorterStemFilter

gener, mice, ag, run, studi, organ

KStemFilter

generous, mice, age, running, study, organization

SnowballFilter (English)

generous, mice, age, run, studi, organ

StemmerOverrideFilter (mice to mouse, aging to age) then KStemFilter

generous, mouse, age, running, study, organization

Porter turns organization into organ, which would conflate it with a different word — the over-stemming problem; KStem leaves it alone but also leaves running unstemmed, so run does not match running. Neither handles the irregular plural mice (override it explicitly). A stemmer is therefore a recall versus precision decision, and it only works when query and index use the same one.

Order matters

Filter order changes results, not just speed. Two cases from the catalog experiments:

  • Case splitting after lowercasing is impossible. WordDelimiterGraphFilter with SPLIT_ON_CASE_CHANGE turns PowerShot Wi-Fi into power, shot, wi, fi when it runs before LowerCaseFilter, but into powershot, wi, fi when lowercasing comes first, because the case boundary is gone by the time the filter looks for it.

  • Stop before stem. On this is being tested, removing stop words first yields be, test; stemming first yields thi, test, because this stems to thi, which is no longer in the stop list. Put StopFilter before stemmers, and lowercase before both.

Autocomplete and partial matching: n-grams

Two shapes:

  • EdgeNGramTokenFilter — prefix grams of each token (search → s, se, sea, sear, searc, search). Apply it in the index analyzer only; the query analyzer feeds the raw user prefix so sea matches the sea gram. This is the standard "search-as-you-type" recipe.

  • NGramTokenizer / NGramTokenFilter — interior grams too, for substring ("infix") matching.

Both multiply term volume: a 20-character field with minGramSize=1 produces up to ~20 terms per token, so the term dictionary and postings grow several-fold. Bound minGramSize (2 or 3, not 1) and maxGramSize, and prefer a dedicated field so the cost is not paid on every query.

// https://lucene.apache.org/core/10_0_0/analysis/common/org/apache/lucene/analysis/ngram/EdgeNGramTokenFilter.html
Analyzer autocompleteIndex = CustomAnalyzer.builder()
    .withTokenizer("standard")
    .addTokenFilter("lowercase")
    .addTokenFilter("asciiFolding")
    .addTokenFilter("edgeNGram", "minGramSize", "2", "maxGramSize", "20", "preserveOriginal", "true")
    .build();

Analyzer autocompleteQuery = CustomAnalyzer.builder()   // NO edgeNGram here
    .withTokenizer("standard")
    .addTokenFilter("lowercase")
    .addTokenFilter("asciiFolding")
    .build();

Indexing the titles of the catalog into a title_ac field with the index analyzer above (minimum gram 2, original preserved), and parsing what a user has typed with the query analyzer and the AND default operator, gives:

index 'Search Lucene': se sea sear searc search lu luc luce lucen lucene
query 'sear'          : sear
typed 'lu'       -> Lucene in Action
typed 'jav'      -> Effective Java; Head First Java; Java Concurrency in Practice
typed 'info ret' -> Introduction to Information Retrieval
typed 'sol'      -> Solr in Action

info ret works because each typed prefix is an AND-ed term and both exist as grams of Introduction to Information Retrieval. The price is index size: the same eight titles produced 121 distinct terms in title_ac against 21 with plain StandardAnalyzer analysis, a factor of almost six on a corpus of short titles. NGramTokenizer(3, 3) over lucene gives the interior grams luc, uce, cen, ene, which is what substring search indexes.

For a ranked suggester that is not a plain analyzer chain, see Highlighting, suggesters & more.

ShingleFilter: token n-grams for phrase-ish matching

ShingleFilter joins adjacent tokens into "shingles" (the quick fox → the quick, quick fox), which lets a plain TermQuery approximate a phrase match and feeds bigram-boost strategies. Keep outputUnigrams=true unless the field is used only for shingle matching.

// https://lucene.apache.org/core/10_0_0/analysis/common/org/apache/lucene/analysis/shingle/ShingleFilter.html
Analyzer shingles = CustomAnalyzer.builder()
    .withTokenizer("standard")
    .addTokenFilter("lowercase")
    .addTokenFilter("shingle",
        "minShingleSize", "2", "maxShingleSize", "2",
        "outputUnigrams", "true", "tokenSeparator", " ")
    .build();

On the quick brown fox the chain above (bigrams plus unigrams, space separator) emits the, the quick, quick, quick brown, brown, brown fox, fox. With maxShingleSize=3 and outputUnigrams=false the output is only the quick, the quick brown, quick brown, quick brown fox, brown fox. A TermQuery on quick brown now behaves like a phrase query without needing positions.

WordDelimiterGraphFilter: splitting mixed tokens

Splits Wi-Fi, PowerShot, SD500 and iPhone10 on case changes, letter/number boundaries and intra-word delimiters, and can re-concatenate the parts. Like the synonym filter it produces a graph, so the index analyzer ends with FlattenGraphFilter. Run it before LowerCaseFilter when splitOnCaseChange is on, or the case information is already gone.

// https://lucene.apache.org/core/10_0_0/analysis/common/org/apache/lucene/analysis/miscellaneous/WordDelimiterGraphFilter.html
Analyzer partNumbers = new Analyzer() {
    @Override
    protected TokenStreamComponents createComponents(String field) {
        Tokenizer src = new WhitespaceTokenizer();
        int flags = WordDelimiterGraphFilter.GENERATE_WORD_PARTS
                  | WordDelimiterGraphFilter.GENERATE_NUMBER_PARTS
                  | WordDelimiterGraphFilter.CATENATE_WORDS
                  | WordDelimiterGraphFilter.SPLIT_ON_CASE_CHANGE
                  | WordDelimiterGraphFilter.PRESERVE_ORIGINAL;
        TokenStream tok = new WordDelimiterGraphFilter(src, flags, null);
        tok = new LowerCaseFilter(tok);
        tok = new FlattenGraphFilter(tok);           // index-time only
        return new TokenStreamComponents(src, tok);
    }
};

On the whitespace-separated input Wi-Fi PowerShot SD500 the filter (with PRESERVE_ORIGINAL and CATENATE_WORDS) produced this graph:

wi-fi      pos=0 inc=1 len=2 [0,5)
wifi       pos=0 inc=0 len=2 [0,5)
wi         pos=0 inc=0 len=1 [0,5)
fi         pos=1 inc=1 len=1 [0,5)
powershot  pos=2 inc=1 len=2 [6,15)
powershot  pos=2 inc=0 len=2 [6,15)
power      pos=2 inc=0 len=1 [6,15)
shot       pos=3 inc=1 len=1 [6,15)
sd500      pos=4 inc=1 len=1 [16,21)

The original wi-fi, the concatenation wifi and the parts wi and fi all coexist, so a user searching wifi, wi-fi or wi fi finds the same product. Note that every part keeps the offsets of the whole original word ([0,5)); highlighters therefore mark the full word rather than a fragment.

DelimitedPayloadTokenFilter: per-term payloads

Reads a delimiter-suffixed weight off each token (fox|0.9) and stores it as a term payload — a few bytes attached to each posting, later read back by a payload-aware query or similarity for term-level weighting (importance tags, part-of-speech weights, per-occurrence scores).

// https://lucene.apache.org/core/10_0_0/analysis/common/org/apache/lucene/analysis/payloads/DelimitedPayloadTokenFilter.html
Analyzer payloads = new Analyzer() {
    @Override
    protected TokenStreamComponents createComponents(String field) {
        Tokenizer src = new WhitespaceTokenizer();       // input: "quick|0.2 fox|0.9"
        TokenStream tok = new LowerCaseFilter(src);
        tok = new DelimitedPayloadTokenFilter(tok, '|', new FloatEncoder());
        return new TokenStreamComponents(src, tok);
    }
};
// Read them back with PostingsEnum.getPayload(), or score with
// org.apache.lucene.queries.payloads.PayloadScoreQuery.

On the input quick|0.2 fox|0.9 jumps the filter produces quick with payload 0.2, fox with payload 0.9 and jumps with no payload (null): a token without the delimiter is simply left without one, so consumers must handle null.
