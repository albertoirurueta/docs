kNN / HNSW vector search

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Lucene stores a dense embedding in a vector field and searches it approximately with an HNSW graph: a layered proximity graph that a query walks greedily from a sparse top layer down to the full bottom layer. This is the engine under Elasticsearch’s dense_vector and Solr’s DenseVectorField; this page is the core-Lucene API.

Two data sets are used. A toy catalogue of the ten books, each with a hand-made four-number embedding (how much the book is about Java, about search, about storage and about theory; a real embedding model would produce hundreds of numbers), shows the query API. A synthetic benchmark of 20,000 vectors of 128 dimensions, in 50 clusters and unit length, shows what the graph parameters and quantised formats do to recall and index size. All outputs are real runs on Lucene 10.4.0, JDK 21.

Vector fields

KnnFloatVectorField holds a float[]; KnnByteVectorField holds a byte[] (one byte per dimension, roughly a quarter of the size, at some recall cost). Every value in a field must have the same dimension count, and every value is compared with the same VectorSimilarityFunction, fixed when the field is created. A document holds at most one vector per field name, and a field is not searchable by text: add a normal field next to it for the lexical side.

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/document/KnnFloatVectorField.html
import org.apache.lucene.document.KnnByteVectorField;
import org.apache.lucene.document.KnnFloatVectorField;
import org.apache.lucene.index.VectorSimilarityFunction;

float[] embedding = model.embed("wireless noise-cancelling headphones"); // length == dims
Document doc = new Document();
doc.add(new KnnFloatVectorField("vec", embedding, VectorSimilarityFunction.COSINE));

byte[] q8 = quantiseToBytes(embedding);
doc.add(new KnnByteVectorField("vec_b", q8, VectorSimilarityFunction.DOT_PRODUCT));

writer.addDocument(doc);
VectorSimilarityFunction Use when

EUCLIDEAN

Straight L2 distance; the default when no function is given, always safe

DOT_PRODUCT

Vectors are unit length — cheapest to compute

COSINE

Angle only; Lucene normalises internally, so magnitude is ignored

MAXIMUM_INNER_PRODUCT

Un-normalised vectors where magnitude carries meaning

Scores are always returned as a positive, higher-is-better number regardless of the function. Field reference: KnnFloatVectorField.

The HNSW graph and its codec formats

Graph parameters live in the KnnVectorsFormat on the codec, not on the field. Lucene99HnswVectorsFormat takes maxConn (M — edges kept per node, default 16) and beamWidth (candidate list size while inserting a node, default 100). Higher values raise recall and index size and slow the build; neither affects query latency directly. Because the graph is built per segment and rebuilt when segments merge, these two numbers are an indexing-time cost, paid again on every merge.

flowchart LR D["addDocument with a vector"] --> B["segment writer: buffer vectors, build graph at flush"] B --> S1["segment 1: .vec raw vectors, .vex graph"] B --> S2["segment 2"] S1 --> M["merge: vectors copied, graph rebuilt or extended"] S2 --> M M --> S3["segment 3: larger graph"]

The default codec already uses an HNSW format, so a plain new KnnFloatVectorField(...) works with no configuration. To change the graph, or to quantise, supply a codec that returns your format. The release-independent way is a FilterCodec that wraps the default codec and replaces only the vectors format through PerFieldKnnVectorsFormat:

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/codecs/lucene99/Lucene99HnswVectorsFormat.html
import org.apache.lucene.codecs.Codec;
import org.apache.lucene.codecs.FilterCodec;
import org.apache.lucene.codecs.KnnVectorsFormat;
import org.apache.lucene.codecs.lucene99.Lucene99HnswVectorsFormat;
import org.apache.lucene.codecs.lucene104.Lucene104HnswScalarQuantizedVectorsFormat;
import org.apache.lucene.codecs.lucene104.Lucene104ScalarQuantizedVectorsFormat.ScalarEncoding;
import org.apache.lucene.codecs.perfield.PerFieldKnnVectorsFormat;

KnnVectorsFormat plain     = new Lucene99HnswVectorsFormat(16, 100);      // full float32, M=16, beam=100
KnnVectorsFormat quantised = new Lucene104HnswScalarQuantizedVectorsFormat(ScalarEncoding.SEVEN_BIT, 16, 100);

Codec base = Codec.getDefault();
IndexWriterConfig iwc = new IndexWriterConfig(analyzer);
iwc.setCodec(new FilterCodec(base.getName(), base) {
    @Override public KnnVectorsFormat knnVectorsFormat() {
        return new PerFieldKnnVectorsFormat() {
            @Override public KnnVectorsFormat getKnnVectorsFormatForField(String field) {
                return field.equals("vec") ? quantised : base.knnVectorsFormat();
            }
        };
    }
});

The quantised format class is named after the codec generation that introduced it (Lucene104HnswScalarQuantizedVectorsFormat in 10.4; the older Lucene99HnswScalarQuantizedVectorsFormat moved to the lucene-backward-codecs module), so check the package of your release. ScalarEncoding chooses the number of bits per dimension: SEVEN_BIT and UNSIGNED_BYTE (8-bit), PACKED_NIBBLE (4-bit), and the asymmetric one-bit and two-bit encodings (SINGLE_BIT_QUERY_NIBBLE, DIBIT_QUERY_NIBBLE). Format list: codecs.lucene99 package.

What the parameters and formats cost

The benchmark indexed the 20,000 vectors with each format into one segment, then ran 100 queries for the 10 nearest neighbours and compared with an exact brute-force search. Recall@10 is the share of the true top 10 that the approximate search returned. The last numeric column asks for 50 candidates and re-ranks them exactly against the original vectors before keeping 10:

The raw data is 20,000 x 128 x 4 bytes = 10,000 KB. What the table shows:

  • The graph is small next to the vectors (306 to 972 KB against 10,000 KB) and a modest M and beam already give most of the recall. Dropping to M=4 and beam=10 costs two thirds of it. Doubling both to M=32 and beam=200 buys almost nothing here (0.854 to 0.858) and doubles the build time: more is not better past the knee.

  • Quantised formats do not shrink the files. They keep the full-precision .vec file (needed to rescore and to re-quantise on merge) and add a compact .veq copy that the graph search reads. What shrinks is the working set: searching touches .veq (2.8 MB, 1.6 MB, 0.6 MB) instead of 10 MB of floats, which decides whether the hot data fits in the page cache.

  • Seven-bit quantisation is nearly free (0.842 against 0.854), four-bit costs about twenty points of recall@10, and one-bit is unusable at 128 dimensions. Binary quantisation is designed for embeddings with several hundred dimensions, where the signal in each coordinate is smaller; do not extrapolate this small test to it.

  • Asking for more candidates and re-ranking recovers the loss. Fifty candidates plus an exact re-rank of the survivors bring even 4-bit to 0.992. In Lucene a k larger than you display is how you widen the search, since in core Lucene k is also the per-segment beam: engines on top of Lucene expose a separate num_candidates for exactly this reason.

Querying

KnnFloatVectorQuery (and KnnByteVectorQuery) does approximate search: it returns the k nearest vectors to a target. In core Lucene k is also the per-segment beam size — engines layered on top expose that second number separately as num_candidates / topK. A filter Query restricts which documents the graph walk may return, so k hits still come back even under a selective filter (pre-filtering, not post-filtering).

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/KnnFloatVectorQuery.html
import org.apache.lucene.search.KnnFloatVectorQuery;
import org.apache.lucene.search.TermQuery;
import org.apache.lucene.index.Term;

float[] qv = { 0.0f, 1.0f, 0.2f, 0.2f };      // "full text search engines" in the toy embedding

Query knn = new KnnFloatVectorQuery("vec", qv, 4);

Query filter = new TermQuery(new Term("category", "programming"));
Query filteredKnn = new KnnFloatVectorQuery("vec", qv, 3, filter);   // pre-filtered

TopDocs hits = searcher.search(filteredKnn, 3);

On the toy catalogue the unfiltered query returns the four search-themed books; scores under COSINE are the cosine mapped to the range 0 to 1 (a cosine of 1 scores 1.0, orthogonal vectors 0.5):

-- kNN k=4 (COSINE)
   0.9970 Lucene in Action
   0.9943 Solr in Action
   0.9811 Elasticsearch in Action
   0.8783 Introduction to Information Retrieval
-- kNN k=3 with filter category=programming
   0.5638 Java Concurrency in Practice
   0.5634 Head First Java
   0.5495 The Pragmatic Programmer

The filtered query asks for the nearest books among programming titles only and still gets three, although none of them is close to the target. A post-filter (search the top 3, drop the non-matching) would have returned nothing. Internally the filter is evaluated first; when it matches fewer documents than the graph search would visit, Lucene skips the graph and scores the matching documents exactly, which is also why a very selective filter makes the result exact.

sequenceDiagram participant App participant Q as KnnFloatVectorQuery participant G as Segment graph (each segment) participant S as IndexSearcher App->>S: search(query) S->>Q: rewrite: run per segment Q->>G: filter bits then greedy HNSW walk, keep k nearest Q->>G: or exact scan if the filter is selective G-->>Q: up to k candidates per segment Q-->>S: merged top k across segments S-->>App: TopDocs

A query returns up to k hits per segment and merges them, so a freshly flushed index with many small segments does more graph walks than a merged one; forceMerge(1) on a static index helps latency.

Similarity threshold (radius search)

FloatVectorSimilarityQuery(field, target, threshold) is the radius counterpart of kNN: it returns every document whose similarity score is at least the threshold, however many there are. On the toy catalogue a threshold of 0.9 against the search-themed target matches three books:

Query nearby = new FloatVectorSimilarityQuery("vec", qv, 0.9f);   // all docs with score >= 0.9
// totalHits: 3

Use it when the question is "everything similar enough" (deduplication, a relevance cut-off) rather than "the best k"; a threshold that is too low turns the query into a scan of the whole segment.

Exact kNN

When the candidate set is already small, skip the graph and score every match by brute force. The scoring source is FullPrecisionFloatVectorSimilarityValuesSource, a DoubleValuesSource that computes the similarity between the target and the stored vector of each matching document; wrap it in a FunctionScoreQuery over the candidate query:

// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/FullPrecisionFloatVectorSimilarityValuesSource.html
import org.apache.lucene.queries.function.FunctionScoreQuery;
import org.apache.lucene.search.*;

DoubleValuesSource exact = new FullPrecisionFloatVectorSimilarityValuesSource(qv, "vec", VectorSimilarityFunction.COSINE);

Query exactKnn = new FunctionScoreQuery(
        new TermQuery(new Term("category", "programming")), exact);   // exact over the filtered set
-- exact scoring over the filtered set
   0.5638 Java Concurrency in Practice
   0.5634 Head First Java
   0.5495 The Pragmatic Programmer

The scores are identical to the filtered approximate query above, which is the expected result for a set this small. Exact scoring costs one similarity computation per candidate and needs no graph, which is the right trade when a filter leaves a few thousand documents or fewer. DoubleValuesSource also has a static helper, similarityToQueryVector(leafContext, queryVector, field), that returns the per-document values of one segment, for code that implements its own DoubleValuesSource.

Hybrid lexical + vector search

Combine a text query and a vector query as SHOULD clauses of a BooleanQuery so both contribute to the score, or run the vector comparison only as a second pass with QueryRescorer.

import org.apache.lucene.search.*;

// (a) one ranking, both signals
Query hybrid = new BooleanQuery.Builder()
        .add(textQuery, BooleanClause.Occur.SHOULD)
        .add(new KnnFloatVectorQuery("vec", qv, 50), BooleanClause.Occur.SHOULD)
        .build();

// (b) lexical first pass, vector rescoring of the top N
// https://lucene.apache.org/core/10_0_0/core/org/apache/lucene/search/QueryRescorer.html
TopDocs firstPass = searcher.search(textQuery, 500);
Query vectorScore = new FunctionScoreQuery(new MatchAllDocsQuery(), exact);
Rescorer rescorer = new QueryRescorer(vectorScore) {
    @Override
    protected float combine(float first, boolean secondMatch, float second) {
        return 0.3f * first + 0.7f * second;
    }
};
TopDocs reranked = rescorer.rescore(searcher, firstPass, 10);

On the toy catalogue the hybrid query combines the text term java with a kNN query for a Java-flavoured vector, and the lexical-then-vector rescoring reorders the books matching search:

-- hybrid SHOULD(text java, knn k=3)
   1.7054 Head First Java
   1.6961 Effective Java
   1.6812 Java Concurrency in Practice
-- lexical 'search' then vector rescoring (0.3 x lexical + 0.7 x vector)
   0.8516 Solr in Action
   0.8401 Lucene in Action
   0.7705 Introduction to Information Retrieval

Because a BM25 score and a similarity score are not on one scale, an unweighted SHOULD blend favours whichever side produces larger numbers — weight the clauses or use the rescoring form when the lexical signal should decide the candidate set. Another common pattern is reciprocal rank fusion, which merges two ranked lists by rank rather than by score; Lucene does not ship it, but it is a few lines over two TopDocs.

Panama Vector API acceleration

Lucene 10 ships vectorised distance kernels that use the JDK’s incubating Vector API (jdk.incubator.vector). On a supported JDK the accelerated implementation is selected automatically from the multi-release lucene-core JAR once the module is added on the launch command:

java --add-modules jdk.incubator.vector -cp app.jar:lucene-core-10.4.0.jar com.example.App

Without the flag Lucene runs the scalar implementation and logs a warning at the first search or index. With the flag it says that it enabled the vector implementation. These are the real log lines from a JDK 21 run:

WARNING: Java vector incubator module is not readable. For optimal vector performance, pass '--add-modules jdk.incubator.vector' to enable Vector API.

WARNING: Using incubator modules: jdk.incubator.vector
INFO: Java vector incubator API enabled; uses preferredBitSize=128

The reported preferredBitSize is the hardware vector width the JVM chose (128 on this Apple silicon laptop, 256 or 512 on most x86 servers). The foreign-memory and Vector API internals are linked, not covered in depth, from the org.apache.lucene.search package overview, which also summarises the vector-search API.
