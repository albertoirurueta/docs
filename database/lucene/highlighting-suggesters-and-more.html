Highlighting, suggesters, spellcheck, MoreLikeThis & classification

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Once a query matches, several optional modules turn hits into user-facing features: snippet highlighting (lucene-highlighter), autocomplete and "did you mean" (lucene-suggest), find-similar (MoreLikeThis in lucene-queries), and text categorisation (lucene-classification). Each is a thin layer over the same index and IndexSearcher.

The examples use the book catalogue: titles and blurbs for suggestions, spelling, similarity and classification, and three short articles about sharding and merging for highlighting. Every output block was produced by running the code against Lucene 10.4.0.

flowchart LR IDX["index: stored fields, postings, term vectors"] --> H["UnifiedHighlighter: snippets"] IDX --> S["lucene-suggest: Lookup and SuggestField: completions"] IDX --> SP["spell checkers: corrections"] IDX --> M["MoreLikeThis: related documents"] IDX --> C["lucene-classification: labels"] H --> UI["result page"] S --> UI SP --> UI M --> UI C --> UI

Highlighting with the UnifiedHighlighter

UnifiedHighlighter is the current highlighter. The older Highlighter (query scorer), FastVectorHighlighter (term-vector based), and PostingsHighlighter are superseded — their capabilities are folded into this one class, which picks the cheapest offset source available per field. Build it from a searcher and analyzer, then highlight a TopDocs.

<dependency>
  <groupId>org.apache.lucene</groupId>
  <artifactId>lucene-highlighter</artifactId>
  <version>10.4.0</version>
</dependency>
// https://lucene.apache.org/core/10_0_0/highlighter/org/apache/lucene/search/uhighlight/UnifiedHighlighter.html
import org.apache.lucene.search.uhighlight.UnifiedHighlighter;
import java.text.BreakIterator;
import java.util.Locale;

Query query = new QueryParser("body", analyzer).parse("sharding strategy");
TopDocs top = searcher.search(query, 10);

UnifiedHighlighter highlighter = UnifiedHighlighter.builder(searcher, analyzer)
        .withBreakIterator(() -> BreakIterator.getSentenceInstance(Locale.ROOT))
        .build();

// one snippet string per hit (null when the field had no match), <b>..</b> by default
String[] snippets = highlighter.highlight("body", query, top, 3);   // up to 3 passages per hit

On three one-paragraph articles the query sharding strategy produces, for the first hit, the two best sentences joined, with every query term marked:

<b>Sharding</b> splits an index into shards. A <b>sharding</b> <b>strategy</b> decides which shard owns a document.
A <b>strategy</b> for query routing is separate from a <b>strategy</b> for <b>sharding</b>.

Only terms that the query matched are marked, and only inside the chosen passages. A phrase query marks the whole phrase as one span, because the highlighter reads match positions from the query’s own Matches:

phrase "sharding strategy": A <b>sharding strategy</b> decides which shard owns a document.
query merge               : The <b>merge</b> policy decides which segments <b>merge</b>.

Passages are scored with a BM25-like PassageScorer (term weight x passage-local frequency, with a pivot on passage length) so the returned fragments are the most query-relevant sentences, not merely the first ones. withFormatter, withScorer, and withMaxLength on the builder override the markup, the scoring, and the per-field character budget. A custom PassageFormatter can emit HTML escaped output or a structured result instead of <b> tags — do that for any text that is not already safe to embed in a page.

The offset-source requirement

The highlighter needs character offsets for the matched terms. Provide them one of three ways, in order of speed:

Source How to enable

Postings offsets

Index the field with IndexOptions.DOCS_AND_FREQS_AND_POSITIONS_AND_OFFSETS. Fastest; no re-analysis.

Term vectors with offsets

FieldType.setStoreTermVectorOffsets(true) (also positions + vectors). Bigger index, but useful if you already store vectors.

Analysis (default fallback)

Nothing indexed; the highlighter re-analyzes the stored field value at query time. Requires Field.Store.YES. Simplest, slowest.

 
// A TextField variant that carries offsets in its postings.
import org.apache.lucene.document.FieldType;
import org.apache.lucene.document.TextField;
import org.apache.lucene.index.IndexOptions;

FieldType bodyType = new FieldType(TextField.TYPE_STORED);
bodyType.setIndexOptions(IndexOptions.DOCS_AND_FREQS_AND_POSITIONS_AND_OFFSETS);
bodyType.freeze();

doc.add(new org.apache.lucene.document.Field("body", articleText, bodyType));

The same article was indexed three times, as a plain stored TextField, with postings offsets, and with term vectors including offsets. The snippets of the three fields are identical, as they must be: the offset source changes the cost, never the output. The table above is therefore the whole decision: store offsets in the postings when highlighting is a hot path, rely on re-analysis when documents are short and the index is small, and pick term vectors only when something else already needs them.

flowchart TD A["field to highlight"] --> B{"postings with offsets?"} B -->|yes| P["read offsets from postings: no analysis"] B -->|no| C{"term vectors with offsets?"} C -->|yes| T["read offsets from the document's term vector"] C -->|no| D{"stored value available?"} D -->|yes| R["re-analyze the stored text at query time"] D -->|no| X["nothing to highlight: no snippet"]

The lucene-highlighter module overview documents the uhighlight package. Solr’s highlighter component (Solr highlighting) and Elasticsearch’s highlight block (Elasticsearch search extras) both drive this class.

Autocomplete: the suggest module

lucene-suggest provides Lookup implementations backed by an FST (or, for the infix suggesters, an auxiliary Lucene index). Build one from a Dictionary, then call lookup.

<dependency>
  <groupId>org.apache.lucene</groupId>
  <artifactId>lucene-suggest</artifactId>
  <version>10.4.0</version>
</dependency>
Lookup Matches

AnalyzingSuggester

Prefix of the whole analyzed entry ("san fr" → "San Francisco"). Applies an analyzer at build and query time.

FuzzySuggester

Like AnalyzingSuggester but tolerates edits in the prefix (typos).

AnalyzingInfixSuggester

Any token prefix inside the entry ("fran" → "San Francisco"). Backed by its own index directory.

BlendedInfixSuggester

AnalyzingInfixSuggester plus a position-based score penalty so earlier matches rank higher.

FreeTextSuggester

Next-word prediction from an n-gram language model over the corpus — completes the sentence, not the term.

The usual source of entries is the index itself. A DocumentDictionary reads a stored text field and a numeric weight field from every document, so the suggestions track the catalogue:

// https://lucene.apache.org/core/10_0_0/suggest/org/apache/lucene/search/suggest/DocumentDictionary.html
import org.apache.lucene.search.suggest.DocumentDictionary;
import org.apache.lucene.search.suggest.Lookup.LookupResult;
import org.apache.lucene.search.suggest.analyzing.AnalyzingInfixSuggester;

// each catalogue document has a stored "entry" (the title) and a numeric doc value "weight" (popularity)
Dictionary titles = new DocumentDictionary(reader, "entry", "weight");

AnalyzingInfixSuggester suggester =
        new AnalyzingInfixSuggester(FSDirectory.open(Path.of("/var/data/suggest")), analyzer);
suggester.build(titles);

List<LookupResult> hits = suggester.lookup("act", false, 5);   // onlyMorePopular=false, 5 results
infix 'act' : Lucene in Action(400), Solr in Action(300), Elasticsearch in Action(250)
infix 'conc': Java Concurrency in Practice
infix 'in act' highlighted: Lucene <b>in</b> <b>Act</b>ion, Solr <b>in</b> <b>Act</b>ion, Elasticsearch <b>in</b> <b>Act</b>ion

The infix suggester found Action from the fragment act and Concurrency from conc, although neither is the start of a title; results come back by descending weight. The highlighted variant is lookup(key, contexts, num, allTermsRequired, doHighlight). The other suggesters differ in what the typed text must match:

analyzing prefix 'lucene i'  : Lucene in Action
analyzing prefix 'act'       : 0 results (not a prefix of a whole entry)
fuzzy 'lucenne'              : Lucene in Action
blended 'java'               : Effective Java(855), Java Concurrency in Practice(600)
free text 'sharding strategy ': strategy for, strategy decides

AnalyzingSuggester requires the typed text to be a prefix of the whole analyzed entry, so act finds nothing; FuzzySuggester forgives the doubled n. BlendedInfixSuggester scales the weight of a match by where it occurs: Effective Java carries weight 950 but the typed word is its second token, so it is scored 855, while Java Concurrency in Practice, where java is first, keeps its full 600. The order is unchanged here, but a modest-weight title that starts with the typed word can now overtake a popular one that contains it later. FreeTextSuggester is a different tool: built from sentences, it predicts the next word after a complete phrase (note the trailing space in the key). The infix suggesters keep their own index directory and must be build-t again, or refreshed with add / update and refresh, when the source changes. The Input and InputArrayIterator classes that appear in some examples online belong to Lucene’s own test code and are not in the published module; use a Dictionary such as DocumentDictionary, or implement InputIterator.

NRT completion: SuggestField and friends

The suggest.document package is a faster, near-real-time alternative: the completions live in the main index as a special postings format, so they update with your normal IndexWriter commits and respect deletes. Index a SuggestField (or ContextSuggestField to carry filter contexts), write with a CompletionAnalyzer and a codec that routes the suggest field through a CompletionPostingsFormat, and query through a SuggestIndexSearcher.

// https://lucene.apache.org/core/10_0_0/suggest/org/apache/lucene/search/suggest/document/SuggestField.html
import org.apache.lucene.codecs.Codec;
import org.apache.lucene.codecs.FilterCodec;
import org.apache.lucene.codecs.PostingsFormat;
import org.apache.lucene.codecs.perfield.PerFieldPostingsFormat;
import org.apache.lucene.search.suggest.document.*;

// --- indexing ---
CompletionAnalyzer completionAnalyzer = new CompletionAnalyzer(analyzer);
IndexWriterConfig iwc = new IndexWriterConfig(completionAnalyzer);
Codec base = Codec.getDefault();
PostingsFormat completion = new Completion104PostingsFormat();   // the format that ships with 10.4
iwc.setCodec(new FilterCodec(base.getName(), base) {
    @Override public PostingsFormat postingsFormat() {
        return new PerFieldPostingsFormat() {     // route only the suggest fields through completion postings
            @Override public PostingsFormat getPostingsFormatForField(String field) {
                return field.startsWith("title_suggest") ? completion : base.postingsFormat();
            }
        };
    }
});
try (IndexWriter w = new IndexWriter(dir, iwc)) {
    for (Book b : books) {
        Document d = new Document();
        d.add(new SuggestField("title_suggest", b.title(), b.popularity()));
        d.add(new ContextSuggestField("title_suggest_ctx", b.title(), b.popularity(), b.category()));
        d.add(new StoredField("title", b.title()));
        w.addDocument(d);
    }
}

// --- querying ---
try (DirectoryReader reader = DirectoryReader.open(dir)) {
    SuggestIndexSearcher searcher = new SuggestIndexSearcher(reader);
    CompletionQuery q = new PrefixCompletionQuery(completionAnalyzer, new Term("title_suggest", "java"));
    TopSuggestDocs suggestions = searcher.suggest(q, 5, false);
    // also: FuzzyCompletionQuery (typos), RegexCompletionQuery, ContextQuery (wrap + filter)
}
completion 'java'                 : Java Concurrency in Practice 600.0
fuzzy completion 'lucen in'       : Lucene in Action 2000.0
context 'databases' + prefix 'd'  : Designing Data-Intensive Applications 900.0
                                    Database Internals 350.0

The default codec class name changes with every release series, and so does the matching completion postings format class (Completion104PostingsFormat goes with the 10.4 codec), so the codec wrapper above delegates to Codec.getDefault() and only replaces the postings format. The context query shows the point of ContextSuggestField: with the context databases only the two database books are suggested for the prefix d, ordered by weight. Each hit carries a Lucene document id, so the stored fields (here the title) can be read back like any search result.

Spell checking

Three tools, none of which need a rebuild pipeline beyond an analyzer:

// https://lucene.apache.org/core/10_0_0/suggest/org/apache/lucene/search/spell/DirectSpellChecker.html
import org.apache.lucene.search.spell.*;

// 1. DirectSpellChecker -- runs against the LIVE index terms, no side index to maintain
DirectSpellChecker direct = new DirectSpellChecker();
SuggestWord[] fix = direct.suggestSimilar(new Term("body", "recieve"), 5, reader);

// 2. SpellChecker -- builds a separate n-gram index from a dictionary
SpellChecker spell = new SpellChecker(FSDirectory.open(Path.of("/var/data/spell")));
spell.indexDictionary(new LuceneDictionary(reader, "body"),
        new IndexWriterConfig(analyzer), false);            // or PlainTextDictionary(Path) for a word list
String[] byGram = spell.suggestSimilar("recieve", 5);

// 3. WordBreakSpellChecker -- split "newyork" -> "new york", or combine the reverse
WordBreakSpellChecker breaker = new WordBreakSpellChecker();
SuggestWord[][] splits = breaker.suggestWordBreaks(new Term("body", "javaconcurrency"), 3, reader,
        SuggestMode.SUGGEST_ALWAYS, WordBreakSpellChecker.BreakSuggestionSortMethod.NUM_CHANGES_THEN_MAX_FREQUENCY);
CombineSuggestion[] combined = breaker.suggestWordCombinations(
        new Term[] { new Term("body", "new"), new Term("body", "york") },
        5, reader, SuggestMode.SUGGEST_WHEN_NOT_IN_INDEX);

Against the catalogue’s body field (titles plus blurbs) the three behave as follows:

direct 'lucen'      : lucene(freq 2, score 0.80)
direct 'serch'      : search(freq 3, score 0.80)
direct 'concurency' : concurrency(freq 1, score 0.90)
direct 'databse'    : database(freq 1, score 0.86), databases(freq 1, score 0.71)
SpellChecker 'serch': search, searching
word break 'javaconcurrency': [java, concurrency]

DirectSpellChecker ranks by edit-distance similarity first and uses the document frequency to break ties; the score is that similarity, not a popularity. SpellChecker builds its own n-gram index of the dictionary terms, so it also proposes searching for serch. suggestWordBreaks splits a run-on query into two indexed words. suggestWordCombinations is the reverse and only proposes words that exist in the index, so combining data and intensive finds nothing on this catalogue (there is no word dataintensive); it is meant for corpora where the joined form is common, such as newyork or ecommerce. CombineSuggestion is a record, so its suggested word is combined[i].suggestion().string.

DirectSpellChecker is the low-maintenance default; SpellChecker + PlainTextDictionary / LuceneDictionary is the choice when the vocabulary is a curated list. This is a different technique from the index-time n-gram token filters in Token filters & recipes: those expand the terms in the main index so a wrong spelling still matches; the spell checkers keep a compact edit-distance structure on the side and suggest a correction instead. The lucene-suggest module overview covers the spell and suggest packages together. Compare Solr spell check & suggest, which exposes exactly these classes as search components.

MoreLikeThis

MoreLikeThis (in lucene-queries) reads the term vectors or re-analyzes a seed document, keeps the highest-tf-idf "interesting terms", and builds a BooleanQuery of SHOULD clauses from them — the "related articles" query.

// https://lucene.apache.org/core/10_0_0/queries/org/apache/lucene/queries/mlt/MoreLikeThis.html
import org.apache.lucene.queries.mlt.MoreLikeThis;

MoreLikeThis mlt = new MoreLikeThis(reader);
mlt.setAnalyzer(analyzer);
mlt.setFieldNames(new String[] { "body" });
mlt.setMinTermFreq(1);
mlt.setMinDocFreq(1);
mlt.setMaxQueryTerms(8);

Query similar = mlt.like(seedDocId);                       // from a doc already in the index
// or from arbitrary text:  mlt.like("body", new StringReader(pastedText));

// inspect what drove the query
String[] terms = mlt.retrieveInterestingTerms(seedDocId);

For the seed Lucene in Action (title plus blurb) the interesting terms and the generated query are:

MLT query: body:searching body:indexing body:library body:analysis body:full body:text body:behind body:lucene
interesting terms: [searching, indexing, library, analysis, full, text, behind, lucene]

The terms are the highest-scoring ones in the seed, because tf-idf rewards a word that is frequent in the document and rare in the index. Wrap similar in a BooleanQuery.Builder with a MUST_NOT on a unique field of the seed to exclude the document itself (here, a title term):

1.386 Elasticsearch in Action
0.671 Introduction to Information Retrieval

Both are search books, one sharing Lucene and searching with the seed and the other sharing indexing and search. MoreLikeThis needs the seed’s text: either term vectors on the field, or the stored field value, which it re-analyzes. Elasticsearch’s more_like_this query (Elasticsearch search extras) is this class over the DSL.

The lucene-classification module

lucene-classification treats an indexed, labelled corpus as training data: a Classifier assigns a class to new text using only index statistics — no external ML runtime.

Classifier Model

KNearestNeighborClassifier

Runs the input text as a MoreLikeThis query, takes the majority label among the top k hits.

KNearestFuzzyClassifier

kNN as above but with fuzzy term matching, for noisy / short input.

SimpleNaiveBayesClassifier

Multinomial naive Bayes from term frequencies per class.

BM25NBClassifier

Naive Bayes with BM25-weighted term contributions instead of raw counts.

 
// https://lucene.apache.org/core/10_0_0/classification/org/apache/lucene/classification/KNearestNeighborClassifier.html
import org.apache.lucene.classification.*;
import org.apache.lucene.util.BytesRef;

Classifier<BytesRef> knn = new KNearestNeighborClassifier(
        reader, null /* similarity */, analyzer, null /* query filter */,
        3 /* k */, 1 /* minDocFreq */, 1 /* minTermFreq */,
        "category" /* class field */, "body" /* text field(s) */);

ClassificationResult<BytesRef> result = knn.assignClass("threads and locks in java");
String label = result.getAssignedClass().utf8ToString();
double confidence = result.getScore();

Classifier<BytesRef> nb = new SimpleNaiveBayesClassifier(reader, analyzer, null, "category", "body");

The category field of each catalogue document is the label (programming, search, databases). With only ten training documents the classifiers still separate the three classes on short text:

kNN 'threads and locks in java'                  -> programming (0.640)
kNN 'indexing and searching text with a library' -> search      (0.466)
kNN 'replication and partitioning of storage'    -> databases   (0.444)
NB  'threads and locks in java'                  -> programming (0.851)
NB  'indexing and searching text with a library' -> search      (0.906)
NB  'replication and partitioning of storage'    -> databases   (0.946)

The two score columns are not comparable across classifiers (each model normalises its own way). Ten documents prove only that the API works: a real classifier needs hundreds of labelled documents per class, and the training data is simply the index, so retraining is re-indexing. ConfusionMatrixGenerator in the same module evaluates a classifier against a held-out slice of the index. See the lucene-classification module overview.
