Running Debezium on Kubernetes: Strimzi, the Debezium Operator and the Platform

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

The Bookshop migration runs for months. During that time the Debezium connectors are production software: they must be restarted when a node is drained, upgraded without losing their position in the Oracle redo stream, and configured without leaking the password of the LogMiner user into a Git repository or a REST response. Kubernetes gives you those properties if you let an operator manage the Kafka and Debezium components instead of writing Deployment manifests by hand. This page shows the three ways of doing that, and gives a complete, copyable set of manifests for the pipeline that the rest of the section runs with Docker Compose: the bookshop-oracle-source connector, reading the legacy BOOKSHOP schema and writing to topics under the legacy prefix.

The three options are:

  • Strimzi runs Kafka and Kafka Connect, and you describe each Debezium connector as a KafkaConnector resource. This is the Kubernetes version of the Kafka Connect deployment used everywhere else in this section, and it is the recommended default for a migration that also uses the JDBC sink.

  • The Debezium Operator runs Debezium Server instances described by DebeziumServer resources. Use it when the pipeline has no Kafka Connect sinks, or when the destination is not Kafka.

  • The Debezium Management Platform (incubating) adds a web UI and an API on top of the operator, in which sources, destinations, transforms and pipelines are managed as shared objects.

Kubernetes itself (pods, deployments, services, secrets, RBAC, Helm and operators) is covered in the Kubernetes section, and Kafka Connect concepts in Kafka Connect. This page explains only what is specific to running Debezium there. Monitoring the deployment is in Monitoring, Logging & Tracing, and offset handling in Offsets, Restarts & Exactly-Once.

Checked on 2026-11-09 against Debezium 3.7.1.Final, Strimzi 1.3.1 (released 2026-11-04, Kafka 4.2.x and 4.3.x, tested on Kubernetes 1.32 to 1.37), and version 3.7.1 of the debezium-operator and debezium-platform Helm charts. The manifests are derived from the official Debezium and Strimzi documentation and from the Strimzi 1.3.1 example files. They were not applied to a Kubernetes cluster here. What was checked on 2026-11-09: the plug-in checksums on Maven Central, the contents of the plug-in archives and of the quay.io/debezium/server:3.7.1.Final image (with Docker), the chart versions in both Helm repositories, and the Debezium Operator resource fields against the operator’s 3.7.1 source code.

Strimzi 1.x: the v1 API, KRaft and node pools

The Debezium page "Deploying Debezium on Kubernetes" still shows Strimzi resources with apiVersion: kafka.strimzi.io/v1beta2, the strimzi.io/kraft and strimzi.io/node-pools annotations, and Kafka 3.x versions. The current Strimzi release line no longer accepts that. Strimzi 1.0.0 made kafka.strimzi.io/v1 the only served and stored version and removed v1beta2 from the CRDs. Strimzi 1.3.1, the current release, supports Kafka 4.2.x and 4.3.x only, and therefore KRaft only: there is no ZooKeeper, every Kafka cluster is made of KafkaNodePool resources, and the annotations are no longer needed.

If you start from the Debezium example or an older internal manifest, change the following:

Older manifest (v1beta2) Strimzi 1.x (v1) Why it matters

apiVersion: kafka.strimzi.io/v1beta2

apiVersion: kafka.strimzi.io/v1

v1beta2 is not served any more, so kubectl apply rejects the resource.

strimzi.io/kraft: enabled and strimzi.io/node-pools: enabled annotations on Kafka

No annotations. KRaft and node pools are the only mode

The roles (controller, broker) and the storage are declared on each KafkaNodePool.

group.id, offset.storage.topic, config.storage.topic and status.storage.topic under KafkaConnect.spec.config

spec.groupId, spec.offsetStorageTopic, spec.configStorageTopic and spec.statusStorageTopic

Strimzi rejects these prefixes in spec.config, together with ssl., sasl., security., bootstrap.servers, plugin.path and rest. (with a few listed exceptions).

spec.replicas optional on KafkaConnect

Required in v1

tasks.max inside KafkaConnector.spec.config

spec.tasksMax only

name, connector.class, tasks.max and connector.plugin.version cannot be set in spec.config.

spec.version: 3.1.0 on KafkaConnect

spec.version: 4.3.2

The version selects the Strimzi Kafka image that the build starts from.

Two things in the Debezium page are still current: the use of the Strimzi build section to add the connector plug-in, and the use of the KubernetesSecretConfigProvider with a Role and a RoleBinding for the credentials. The manifests below use both, in the v1 form.

Installing the Strimzi Cluster Operator

Strimzi publishes its Helm chart as an OCI artifact. The following command installs the Cluster Operator into its own namespace and lets it manage the resources in bookshop-cdc. Create both namespaces first, because the chart creates role bindings in each watched namespace.

Installing Strimzi 1.3.1 with Helm and creating the Bookshop namespace
kubectl create namespace strimzi
kubectl create namespace bookshop-cdc

helm install strimzi-cluster-operator oci://quay.io/strimzi-helm/strimzi-kafka-operator \
  --version 1.3.1 \
  --namespace strimzi \
  --set 'watchNamespaces={bookshop-cdc}'

kubectl get pods -n strimzi --watch    # wait for strimzi-cluster-operator-... to be Running

Reference: Strimzi — Deploying Strimzi using Helm

Pin the chart version. Without --version Helm installs the newest chart, and a Strimzi upgrade also upgrades the CRDs and may drop the Kafka version that your manifests name. Helm itself is explained in Helm, and how operators reconcile custom resources in Custom Resources and Operators.

The Kafka cluster

The cluster below has three controllers and three brokers in two node pools with persistent storage. It disables broker-side topic creation, so that every Debezium topic is created either by a KafkaTopic resource or by Kafka Connect with the settings that the connector asks for. The plain listener on port 9092 is used inside the namespace. TLS and client authentication for Connect are covered in Security & Data Protection and Kafka Security.

bookshop-kafka.yaml — a KRaft Kafka 4.3 cluster with two node pools
apiVersion: kafka.strimzi.io/v1
kind: KafkaNodePool
metadata:
  name: controller
  namespace: bookshop-cdc
  labels:
    strimzi.io/cluster: bookshop-kafka
spec:
  replicas: 3
  roles:
    - controller
  storage:
    type: jbod
    volumes:
      - id: 0
        type: persistent-claim
        size: 20Gi
        kraftMetadata: shared
        deleteClaim: false
---
apiVersion: kafka.strimzi.io/v1
kind: KafkaNodePool
metadata:
  name: broker
  namespace: bookshop-cdc
  labels:
    strimzi.io/cluster: bookshop-kafka
spec:
  replicas: 3
  roles:
    - broker
  storage:
    type: jbod
    volumes:
      - id: 0
        type: persistent-claim
        size: 200Gi
        kraftMetadata: shared
        deleteClaim: false
---
apiVersion: kafka.strimzi.io/v1
kind: Kafka

Reference: Strimzi — Deploying a Kafka cluster in KRaft mode and Strimzi 1.3.1 example — kafka-ephemeral.yaml

Wait for kubectl wait kafka/bookshop-kafka --for=condition=Ready --timeout=600s -n bookshop-cdc. The bootstrap service is bookshop-kafka-kafka-bootstrap, so clients in the namespace use bookshop-kafka-kafka-bootstrap:9092. The 200 GiB per broker is a placeholder: size it from the change rate of the legacy database multiplied by the topic retention, plus the compacted mirror topics. Disk sizing for stateful workloads is discussed in Stateful Applications in Practice.

Topics that Debezium needs before it starts

Three Bookshop topics have requirements that automatic creation would not meet. The schema history topic must have a single partition, must never be compacted or expired, and is read in full at every connector start. The signal and notification topics are small, but you want to own their retention. Declaring them as KafkaTopic resources puts them under version control.

bookshop-topics.yaml — schema history, signal and notification topics
apiVersion: kafka.strimzi.io/v1
kind: KafkaTopic
metadata:
  name: legacy.schema-history
  namespace: bookshop-cdc
  labels:
    strimzi.io/cluster: bookshop-kafka
spec:
  partitions: 1
  replicas: 3
  config:
    cleanup.policy: delete
    retention.ms: -1
    retention.bytes: -1
---
apiVersion: kafka.strimzi.io/v1
kind: KafkaTopic
metadata:
  name: legacy.signals
  namespace: bookshop-cdc
  labels:
    strimzi.io/cluster: bookshop-kafka
spec:
  partitions: 1
  replicas: 3
  config:
    retention.ms: 604800000
---
apiVersion: kafka.strimzi.io/v1
kind: KafkaTopic
metadata:
  name: legacy.notifications
  namespace: bookshop-cdc
  labels:
    strimzi.io/cluster: bookshop-kafka
spec:
  partitions: 1
  replicas: 3
  config:
    retention.ms: 2592000000

Reference: Debezium — Oracle connector properties (schema.history.internal.kafka.topic) and Debezium — Internal schema history store

The data topics (legacy.BOOKSHOP.BOOK and the others) and the heartbeat topic are created by Kafka Connect when the connector first writes to them, with the topic.creation.default.* settings of the connector below. The Connect internal topics (configs, offsets, status) are created by the Connect workers themselves. Topic creation groups are explained in Offsets, Restarts & Exactly-Once.

Reaching the legacy Oracle database

The legacy Oracle database normally runs outside the cluster, on a server or a VM. An ExternalName service gives it a stable in-cluster name, so the connector configuration keeps database.hostname: oracle, exactly as in the Docker Compose labs, and only the service changes between environments.

oracle-service.yaml — an in-cluster name for the legacy database
apiVersion: v1
kind: Service
metadata:
  name: oracle
  namespace: bookshop-cdc
spec:
  type: ExternalName
  externalName: legacy-oracle.example.com
  ports:
    - name: sqlnet
      port: 1521

Reference: Kubernetes — Service type ExternalName

An ExternalName service is only a DNS CNAME. The Connect pods must still be able to reach port 1521 through the cluster’s egress rules and any firewall in front of Oracle. If you use network policies (see Network Policies), allow egress from the pods labelled strimzi.io/cluster: bookshop-connect to the Oracle host. A long LogMiner session holds the connection open, so the firewall’s idle timeout must also be longer than the connector’s longest mining step.

Credentials: a Secret and the KubernetesSecretConfigProvider

The Oracle user and password must not appear in the KafkaConnector resource. Anything in a connector configuration is returned in clear text by GET /connectors/bookshop-oracle-source/config, stored in the Connect config topic, and committed to Git with the manifest. Kafka’s configuration providers solve this: the configuration contains a placeholder such as ${secrets:bookshop-cdc/bookshop-oracle-credentials:ORACLE_PASSWORD}, and the worker resolves it when it starts the task. Strimzi ships io.strimzi.kafka.KubernetesSecretConfigProvider, which reads the value directly from a Kubernetes Secret through the Kubernetes API. It needs no volume mount, and a rotated password is picked up at the next connector restart without restarting the workers.

The provider calls the Kubernetes API as the service account of the Connect pods, which Strimzi names <KafkaConnect name>-connect, so bookshop-connect-connect here. That account needs get on exactly this secret.

bookshop-oracle-credentials.yaml — the Secret and the RBAC that lets Kafka Connect read it
apiVersion: v1
kind: Secret
metadata:
  name: bookshop-oracle-credentials
  namespace: bookshop-cdc
type: Opaque
stringData:
  ORACLE_USER: c##dbzuser
  ORACLE_PASSWORD: dbz
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: bookshop-oracle-credentials-reader
  namespace: bookshop-cdc
rules:
  - apiGroups: [""]
    resources: ["secrets"]
    resourceNames: ["bookshop-oracle-credentials"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: bookshop-oracle-credentials-reader
  namespace: bookshop-cdc
subjects:
  - kind: ServiceAccount
    name: bookshop-connect-connect
    namespace: bookshop-cdc
roleRef:
  kind: Role
  name: bookshop-oracle-credentials-reader
  apiGroup: rbac.authorization.k8s.io

Reference: Strimzi — Loading configuration values from secrets or config maps and Debezium — Creating secrets for the database

The values are the lab credentials used throughout this section. In a real cluster the secret is created from your secret store (an external secrets operator, sealed secrets or the CI system), never from a file in Git. The Secret object itself and the ways of populating it are covered in Secrets, and roles and bindings in Authentication, Authorization and RBAC. The keys use upper-case environment-variable style names on purpose: the Debezium Server resource later on this page imports the same secret as environment variables.

The Kafka Connect cluster with the Debezium plug-ins

The KafkaConnect resource below creates two Connect workers and builds their image. In the build section, Strimzi downloads each listed artifact, verifies its SHA-512 checksum, adds it under the plug-in path of the Strimzi Kafka base image, and pushes the result to the registry in build.output. A change to the plug-in list or the base image triggers a new build and a rolling restart of the workers. On Kubernetes Strimzi uses Buildah for the build (the UseConnectBuildWithBuildah feature gate became GA in Strimzi 1.3.0), and on OpenShift it uses an OpenShift build.

bookshop-connect.yaml — Kafka Connect with the Debezium Oracle and JDBC plug-ins

  name: bookshop-connect
  namespace: bookshop-cdc
  annotations:
    strimzi.io/use-connector-resources: "true"

  version: 4.3.2
  replicas: 2
  bootstrapServers: bookshop-kafka-kafka-bootstrap:9092
  groupId: bookshop-connect
  configStorageTopic: bookshop-connect-configs
  offsetStorageTopic: bookshop-connect-offsets
  statusStorageTopic: bookshop-connect-status
  config:
    config.storage.replication.factor: 3
    offset.storage.replication.factor: 3
    status.storage.replication.factor: 3
    config.providers: secrets
    config.providers.secrets.class: io.strimzi.kafka.KubernetesSecretConfigProvider
    key.converter: org.apache.kafka.connect.json.JsonConverter
    value.converter: org.apache.kafka.connect.json.JsonConverter
    key.converter.schemas.enable: true
    value.converter.schemas.enable: true
  resources:
    requests:
      cpu: "1"
      memory: 4Gi
    limits:
      memory: 4Gi
  jvmOptions:
    "-Xms": 2g
    "-Xmx": 3g
  logging:
    type: inline
    loggers:
      rootLogger.level: INFO
      logger.debezium.name: io.debezium
      logger.debezium.level: INFO
  build:
    output:
      type: docker
      image: registry.example.com/bookshop/bookshop-connect:3.7.1.Final
      pushSecret: bookshop-registry-credentials
    plugins:
      - name: debezium-connector-oracle
        artifacts:
          - type: tgz
            url: https://repo1.maven.org/maven2/io/debezium/debezium-connector-oracle/3.7.1.Final/debezium-connector-oracle-3.7.1.Final-plugin.tar.gz
            sha512sum: 5788ec1b3b32c87327c8d289e31056db43103d29b9f0c1eba5b04391dc01a977c68351be5979ef1e94d195e0faba3935058d80250bbe36f20e38ce10f3593a5c
      - name: debezium-connector-jdbc
        artifacts:
          - type: tgz
            url: https://repo1.maven.org/maven2/io/debezium/debezium-connector-jdbc/3.7.1.Final/debezium-connector-jdbc-3.7.1.Final-plugin.tar.gz

What each part does, and what to check:

  • strimzi.io/use-connector-resources: "true" makes the operator manage connectors from KafkaConnector resources. With it, the operator also reverts any connector created or changed with curl against the REST API, so pick one method per Connect cluster. The rest of this section shows curl commands for the Docker labs. On Kubernetes, put the same configuration in a KafkaConnector.

  • The internal topics get their names from groupId and the three ...StorageTopic fields. Every Connect cluster that shares the Kafka cluster needs its own group ID and its own three topics. The offsets topic holds the position of bookshop-oracle-source in the Oracle redo stream, so treat it like data, not like a cache.

  • The converters are set to JSON with schemas, which is the same default as the Debezium Connect image. For Avro with Apicurio Registry, add the converter artifacts as a third plug-in and change these properties as described in Serialization & Schema Registries.

  • Memory. The Oracle connector buffers every open transaction in the worker heap with the default log.mining.buffer.type=memory. Size the heap for the largest legacy batch job, keep the memory limit equal to the request so the pod is not evicted first under node pressure, and leave the gap between -Xmx and the limit for metaspace, threads and direct buffers. See Resource Management.

  • The Oracle JDBC driver. The Debezium Oracle documentation says that licensing prevents Debezium from including the Oracle JDBC driver in the connector archive, and asks you to add ojdbc11.jar yourself. The 3.7.1.Final plug-in archive on Maven Central does contain ojdbc11-23.26.1.0.0.jar and orai18n-23.26.1.0.0.jar in its debezium-connector-oracle/ directory (listed on 2026-11-09), and so does the JDBC sink archive. With these two artifacts the image therefore has the driver in each plug-in’s own class loader, and no third artifact is needed. Do not add a second ojdbc11 JAR to the same plug-in, because two driver versions in one class loader lead to ClassCastException or a driver chosen at random. If a later Debezium release drops the bundled driver, add com.oracle.database.jdbc:ojdbc11 as a type: maven artifact of the debezium-connector-oracle plug-in. The full discussion is in Installing Debezium.

  • Checksums. The sha512sum values are the ones Maven Central publishes next to each 3.7.1.Final archive (.tar.gz.sha512). Strimzi does not scan downloaded artifacts, so a checksum is your only guarantee that the image contains what you reviewed. Update the URL and the checksum together when you upgrade Debezium.

  • The registry. registry.example.com/bookshop/bookshop-connect and the bookshop-registry-credentials push secret (a kubernetes.io/dockerconfigjson secret) stand for your own registry. Strimzi pulls the built image by digest, so the tag can be reused safely.

Instead of the build section you can build the image yourself (FROM quay.io/strimzi/kafka:1.3.1-kafka-4.3.2, then copy the extracted plug-ins into /opt/kafka/plugins/) and set spec.image. On clusters with the Kubernetes image volume feature, Strimzi can also mount plug-ins packaged as OCI images through spec.plugins with type: image artifacts. Either way the rule about a single ojdbc11 per plug-in stays the same.

The bookshop-oracle-source connector as a KafkaConnector

The connector resource carries the same properties as bookshop-oracle-source.json in Oracle Connector, with three differences: the user and password are provider placeholders, name, connector.class and tasks.max move to the resource itself, and the bootstrap servers point at the Strimzi service.

bookshop-oracle-source.yaml — the legacy Oracle source connector
apiVersion: kafka.strimzi.io/v1

  name: bookshop-oracle-source

  state: running
  autoRestart:

    maxRestarts: 10
  config:

    database.port: "1521"
    database.user: ${secrets:bookshop-cdc/bookshop-oracle-credentials:ORACLE_USER}
    database.password: ${secrets:bookshop-cdc/bookshop-oracle-credentials:ORACLE_PASSWORD}

Notes on this resource:

  • Placeholders. The format is ${secrets:<namespace>/<secret>:<key>}, where secrets is the alias declared by config.providers in the KafkaConnect resource. The value is resolved inside the worker. GET .../config returns the placeholder, not the password. In a listing block YAML does not touch ${...}, so no quoting is needed.

  • The signal table name. signal.data.collection uses the PDB form FREEPDB1.BOOKSHOP.DEBEZIUM_SIGNAL. The official property description asks for the root database name instead, but Debezium 3.7.1 silently ignored that form in the worked example, and the PDB form worked. A log signal after the first deployment confirms the channel, as shown in The signal table name in a PDB.

  • Numbers and transactions. decimal.handling.mode: string delivers every Oracle NUMBER, keys included, as a JSON string ("BOOK_ID":"7"), which is why the mirror sink’s JDBC URL ends in ?stringtype=unspecified. provide.transaction.metadata publishes the legacy.transaction topic that the order projector reads. The schema history keeps the DDL of all tables (store.only.captured.tables.ddl: "false", the default), which the cut-over and a rollback rely on.

  • Topic creation. The topic.creation.default.* properties set the replication factor, partition count and retention of the data topics that Connect creates. One partition per table keeps the change events of a table in commit order. Fourteen days of retention gives the downstream consumers time to recover. Compacted mirror topics and per-table groups are explained in Topic auto-creation.

  • state. Setting spec.state: stopped (or paused) and applying the resource is the Kubernetes way to stop the connector, for example before a legacy maintenance window or before changing offsets. Since Strimzi 1.2.0 a connector that is created with stopped or paused starts directly in that state, which lets you deploy the resource first and start the capture at an agreed moment.

  • autoRestart. A Debezium task fails on errors it cannot retry, for example ORA-01291: missing logfile when the archive log for its offset is gone. Strimzi restarts failed connectors and tasks with an increasing back-off (0, 2, 6, 12, 20 and more minutes, capped at 60). maxRestarts: 10 stops the loop after about five hours, so that a permanent problem surfaces as a FAILED connector and an alert instead of an endless restart loop. A restart never fixes a missing archive log. See Troubleshooting & Failure Recovery.

Adding the JDBC sink

The bookshop-pg-mirror-sink that fills the PostgreSQL legacy_* mirror tables runs in the same Connect cluster as a second KafkaConnector. Its configuration is in JDBC Sink Connector. Translate it the same way: class: io.debezium.connector.jdbc.JdbcSinkConnector, tasksMax, and the bookshop_mirror PostgreSQL password in a second secret, read through the same provider (extend the Role with the new secret name). Because both connectors share the workers, a heavy sink can slow the source down. If the mirror sink needs many tasks, give it its own KafkaConnect resource with its own group ID and topics.

The Debezium Operator and DebeziumServer

The Debezium Operator manages Debezium Server, the standalone runtime that runs one source connector and writes to one sink without Kafka Connect (see Debezium Server). Each DebeziumServer resource becomes a deployment with one pod, a config map with the generated application.properties, and optionally a service for its API and a persistent volume for file-based offsets. The operator needs Java 21 based images, which the quay.io/debezium/server:3.7.1.Final image is.

Installing the operator

The operator is published in the Debezium Helm chart repository and, with the same versions, as an OCI chart on quay.io. Chart versions follow the Debezium version without the .Final suffix, so 3.7.1.Final is chart 3.7.1.

kubectl get pods -n bookshop-cdc --watch

How the operator turns this resource into Debezium Server configuration, as implemented in the 3.7.1 operator source:

  • spec.source.class becomes debezium.source.connector.class, and every key under spec.source.config becomes debezium.source.<key>. The official schema table names the field sourceClass, but the Java model serialises it as class (the name the examples use), so write class.

  • spec.source.offset.kafka configures the Kafka offset store (bootstrapServers, topic, partitions, replicationFactor, and props for extra Kafka client properties), and spec.source.schemaHistory.kafka configures the Kafka schema history in the same way. Each store is a nested object named after its type (file, memory, redis, kafka, jdbc, configMap or a custom store). The "complete example" on the official page writes type: kafka plus a config map instead, which does not match the schema tables, so follow the tables.

  • spec.sink.type becomes debezium.sink.type, and spec.sink.config keys become debezium.sink.<type>.<key>, hence producer.bootstrap.servers for the Kafka sink.

  • Keys under spec.quarkus.config are prefixed with quarkus., so write log.level, not quarkus.log.level. The complete example on the official page uses the full quarkus.log.level, which would end up as quarkus.quarkus.log.level.

  • runtime.environment.from is a list of standard Kubernetes EnvFromSource objects, so secretRef and configMapRef work as in a pod spec. Each key of the secret becomes an environment variable of the same name.

  • runtime.metrics.jmxExporter.enabled starts the Prometheus JMX exporter in the server pod, and configFrom can point to a config map key with your own rules (see Monitoring, Logging & Tracing).

The schema history topic is legacy.schema-history, the same topic as the Kafka Connect deployment, because this resource is an alternative to bookshop-oracle-source, not an addition. If you migrate an existing pipeline from Kafka Connect to Debezium Server, the offsets do not move automatically: the server keeps them in bookshop-oracle-server-offsets under its own key. Start the server with snapshot.mode set for the situation (a new snapshot, or no_data plus an incremental snapshot) after stopping the Connect connector, as explained in Offsets, Restarts & Exactly-Once.

The Debezium Management Platform

The Debezium Management Platform is labelled incubating in the official documentation, so its options may change between releases. It provides a data-centric view of Debezium: you define connections (how to reach a database or a sink), sources, destinations and transforms once, and combine them into pipelines. Each pipeline is deployed as a DebeziumServer resource through the Debezium Operator. Kubernetes is the only supported environment. The platform has two components: the conductor (the back end, with an API server and a watcher that talks to the operator) and the stage (the web UI).

flowchart LR U[Platform user] --> ST[Stage web UI] ST --> CO[Conductor API] CO --> DB[(Platform PostgreSQL)] CO --> W[Conductor watcher] W --> DOP[Debezium Operator] DOP --> DSP[DebeziumServer per pipeline] DSP --> SINK[Destination such as Kafka]

Installing the platform with Helm

The chart needs a domain name for its ingress and a PostgreSQL database for its own state. For a trial, database.enabled=true deploys a PostgreSQL pod with the chart. For a migration that runs for months, point it at a managed or operator-run database instead, with the credentials in an existing secret that has the keys username and password.

database:
  enabled: false
  name: debezium_platform
  host: platform-postgres.bookshop-cdc.svc
  auth:
    existingSecret: debezium-platform-db

offset:
  reusePlatformDatabase: true

schemaHistory:
  reusePlatformDatabase: true

debezium-operator:
  enabled: true

The chart installs the Debezium Operator as a dependency (debezium-operator.enabled=true by default). If you already installed the operator in the namespace as shown above, set it to false. With the default values, pipelines store their offsets and schema history in the platform database (offset.reusePlatformDatabase and schemaHistory.reusePlatformDatabase). Back that database up as carefully as the Kafka Connect offsets topic, because it holds the position of every pipeline in its source.

Using the platform for the Bookshop source

In the UI, create an Oracle connection to oracle:1521, then a source. The source editor has a Smart Editor that accepts the JSON you would POST to Kafka Connect: paste bookshop-oracle-source.json from the Oracle connector page and use Auto Format to convert it into the platform’s format, then remove the clear-text password and use the connection’s credentials. Create a Kafka destination for bookshop-kafka-kafka-bootstrap:9092, optional transforms, and a pipeline that joins them. Enable signaling on the source with the signal table name and the DDL that the dialog shows, and the Pipeline actions tab then sends signals such as an incremental snapshot without SQL access to Oracle. Pipeline logs and, when the OpenTelemetry monitoring stack is enabled, built-in dashboards (source lag, time since the last event, queue usage and snapshot progress) are available per pipeline.

Keep the limits in mind for a migration:

  • Editing a shared source, destination or transform restarts every pipeline that uses it.

  • Pipelines run on Debezium Server, so the Debezium JDBC sink and other Kafka Connect sinks are not available as destinations. The PostgreSQL mirror still needs a Kafka Connect cluster or an application consumer.

  • The platform is incubating. Pin the chart version, keep an export of each pipeline’s configuration outside the platform database, and test upgrades before applying them during the migration.

The Debezium CLI can manage platform objects from scripts (debezium source, destination, pipeline and so on). It is described in Installing Debezium.

OpenShift notes

The Debezium OpenShift page follows the same steps with OpenShift tools, and the differences are small:

  • Install Strimzi (or the Red Hat build of Apache Kafka, Streams for Apache Kafka) from OperatorHub with a Subscription, instead of Helm. The Debezium Operator is also listed in OperatorHub.

  • Create the namespace with oc new-project bookshop-cdc.

  • In the KafkaConnect build, output.type: imagestream pushes the image to an OpenShift ImageStream (image: bookshop-connect:3.7.1.Final), so no external registry and push secret are needed. Strimzi runs the build as an OpenShift build instead of Buildah.

  • The restricted security context constraints run containers with an arbitrary user ID. The Strimzi and Debezium images support this. If you build your own images, make the plug-in and lib directories readable by the root group.

  • Routes replace the ingress for the platform UI. Expose the Connect REST API only inside the cluster.

Operating the deployment during the migration

Task How on Kubernetes

Stop capture for a legacy maintenance window

spec.state: stopped on the KafkaConnector, apply, and set it back to running afterwards. The offsets stay in the Connect offsets topic. Make sure the archive logs from the stop SCN onwards are kept until the connector catches up.

Upgrade Debezium

Change the plug-in URLs and checksums in the KafkaConnect build. Strimzi rebuilds the image and rolls the workers one by one, and the connector resumes from its offset on another worker. Read the release notes for renamed properties first.

Upgrade Strimzi or Kafka

Upgrade the Cluster Operator with Helm, then change spec.kafka.version and metadataVersion as the Strimzi upgrade procedure describes. Connect needs no change unless you pin spec.version.

Drain a node

Two Connect replicas and a PodDisruptionBudget (Strimzi creates one for Connect by default) let the task move. The Oracle connector restarts its LogMiner session from the offset scn, which can take minutes after a long transaction.

Rotate the Oracle password

Update the secret, then restart the connector (strimzi.io/restart=true). The provider reads the new value at task start.

Inspect or change offsets

spec.listOffsets and spec.alterOffsets with the strimzi.io/connector-offsets annotation, or the REST endpoints through a port-forward. See Offsets, Restarts & Exactly-Once.

Decommission after the cut-over

Delete the KafkaConnector resources (the connector and its configuration are removed, the offsets stay in the topic), archive the topics, then delete the KafkaConnect and Kafka resources and their persistent volume claims.

What goes wrong

Symptom Cause and fix

no matches for kind "KafkaConnect" in version "kafka.strimzi.io/v1beta2"

The manifest was copied from the Debezium page or written for Strimzi 0.x. Change to kafka.strimzi.io/v1 and move group.id and the storage topic names to the spec fields.

The KafkaConnect resource reports that group.id (or bootstrap.servers) is forbidden

Strimzi manages these options. Use spec.groupId, spec.bootstrapServers and the ...StorageTopic fields.

The connector configuration shows ${secrets:...} in the error message and the task fails with an authentication error (ORA-01017)

The service account cannot read the secret (the RoleBinding names a different service account, or the Role names a different secret), or config.providers is missing from the KafkaConnect resource. Check with kubectl auth can-i get secret/bookshop-oracle-credentials --as=system:serviceaccount:bookshop-cdc:bookshop-connect-connect -n bookshop-cdc.

Changes made with curl to the connector disappear after a minute

strimzi.io/use-connector-resources is true, so the operator restores the configuration from the KafkaConnector. Change the resource instead.

The build pod fails with a checksum mismatch

The URL and the sha512sum belong to different versions. Download the .sha512 file next to the archive on Maven Central and copy its value.

No suitable driver found or ClassNotFoundException: oracle.jdbc.OracleDriver

A custom image or a later archive lacks the driver. List the plug-in directory in a worker pod (ls /opt/kafka/plugins/debezium-connector-oracle/*/) and add ojdbc11 to that plug-in only.

The connector fails to start with a schema history error after a namespace was recreated

The legacy.schema-history topic was deleted with the old cluster while the offsets survived, or the reverse. Offsets and schema history must always be kept or removed together. Recovery is described in Handling Schema Changes.

A DebeziumServer pod starts but ignores the log level, or a property set under quarkus.config

The key was written with the quarkus. prefix, which the operator adds itself.

The Oracle connection times out from the cluster but works from a laptop

Egress is blocked by a network policy or a firewall, or the ExternalName service points to a name that the cluster DNS cannot resolve. Test with a temporary pod: kubectl run -it --rm nettest --image=busybox — nc -zv oracle 1521.
