AWS (Amazon Web Services)

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Welcome to the AWS reference. It documents Amazon Web Services for practitioners who work from the AWS Management Console and the AWS CLI — provisioning resources, wiring them together, and operating what results — rather than from the perspective of a certification-style conceptual overview. It is written for developers and operators who already build software (the rest of this site covers the Java, web and database sides) and now need to run it on AWS. Examples across this section target AWS CLI v2 (the 2.37 line), AWS CDK v2 (aws-cdk-lib 2.272), AWS SAM CLI 1.166, eksctl 0.230 and Amazon EKS Kubernetes 1.36; this baseline was re-verified as current on 2026-10-01, and each page also names the service-specific versions it depends on, since AWS ships new capabilities to individual services on its own schedule. Prices are never quoted: each page describes the pricing model and cost drivers and links the dated official pricing page.

Also working on Google Cloud? See the Google Cloud section, which builds the same Bookshelf application there.

Reading path

Read this section foundations first — the cloud model, accounts, regions, organizations, identity and infrastructure as code — then compute, where Bookshelf’s services first get deployed. From there, storage and CDN put the static front end and its assets somewhere durable and fast to serve, and managed databases give catalog-api and orders-api somewhere to persist data. Security and runtime configuration then centralize the secrets and settings every earlier page referenced loosely, before networking, gateways and VPN lock the whole thing behind a private network and a proper API front door. Email and integration wire notifier up to the outside world, and operations, governance and beyond closes the loop: monitoring, cost, compliance, migration paths and the developer tooling that ties CI/CD back to everything above. A reader who only needs one topic can jump straight to its page; each page states which earlier pages it assumes.

Running example

Most pages in this section build up one running example, Bookshelf: a static web front end, a catalog-api (Spring Boot), an orders-api and a notifier worker that sends order-confirmation emails. It is the same application as in the Azure section, so the two clouds can be compared side by side. Bookshelf starts on ECS (the bookshelf cluster, covered in the Compute group below), where catalog-api is first deployed with ECS Express Mode and then as a full Fargate service, and later moves its services onto an EKS cluster (bookshelf-eks), covered in EKS Clusters and Deploying Microservices on EKS. The figure below shows Bookshelf’s end state, once every group’s pages have been applied: CloudFront in front of a private S3 bucket and an API Gateway HTTP API, the EKS-hosted services behind an Application Load Balancer, the databases, secrets and configuration reached from private subnets, event-driven Lambda functions and SES for email, an admin VPN path, and CloudWatch watching all of it. It is not the architecture a reader has running after just the Compute pages — see Choosing a Compute Service and ECS and Fargate for the earlier, ECS-only stage.
