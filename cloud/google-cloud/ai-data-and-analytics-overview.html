Choosing a service

Most data questions on Google Cloud begin with the same decision: do you want to write SQL against a managed warehouse, run your own pipeline code, or run an existing Hadoop or Spark job?

Service What it is Reach for it when

BigQuery

Serverless, columnar data warehouse with separated storage and compute, built-in streaming ingest, SQL machine learning and vector search

You can express the work as SQL, the data is large, or you want no cluster to operate

Dataflow

Managed runner for Apache Beam batch and streaming pipelines, with prebuilt templates

You need per-record transformation, windowing, joins on streams, or exactly-once streaming into a sink

Dataproc

Managed Hadoop and Spark clusters, and Serverless for Apache Spark batches and sessions

You have existing Spark, Hive or Hadoop code, or need the open-source ecosystem

Cloud Data Fusion

Visual, code-free pipeline builder based on the open-source CDAP, executing on Dataproc

Teams want drag-and-drop ETL with many ready connectors

Pub/Sub

Global messaging service; subscriptions can write directly to BigQuery and Cloud Storage

Events must flow into analytics continuously

Vertex AI

Platform for custom machine learning: notebooks, training, model registry, endpoints, batch prediction (now branded Gemini Enterprise Agent Platform)

You train and serve your own models, or build agents on Google models

Gemini

Google’s family of generative models, reachable from the platform, the Gemini API and the console

You need text, code, image or multimodal generation and embeddings

Looker and Looker Studio

Business intelligence: a governed semantic layer (Looker) and a free dashboard tool (Looker Studio)

Business users need dashboards over BigQuery

A rule of thumb: try BigQuery first; add Pub/Sub plus a BigQuery subscription for simple streaming; move to Dataflow when the transformation cannot be SQL; use Dataproc when you inherit Spark; and use Vertex AI when BigQuery ML does not offer the model you need.

BigQuery

BigQuery stores tables in a columnar format and runs SQL on a large pool of workers that you never see. Storage and compute are billed separately, and the same data can be queried from SQL, from the client libraries, from Spark, and from notebooks. Resources are organised as project, dataset and table (or view, routine, model); the dataset holds the access control and, importantly, its location (a region such as us-central1 or a multi-region such as US), which is fixed when the dataset is created. Queries cannot join tables across locations, so choose the dataset location to match your data and the services that write to it. For the Bookshelf the dataset is bookshelf in us-central1.

Editions, slots and pricing model

Compute is billed in one of two ways. On-demand pricing charges for the bytes a query processes, which is why scanning fewer bytes (by selecting only needed columns and by partitioning and clustering, below) directly lowers cost. Capacity pricing, sold as BigQuery editions (Standard, Enterprise and Enterprise Plus), charges for slots, units of compute that you reserve or let autoscale, regardless of bytes. Editions also gate features: for instance BigQuery vector indexes require the Enterprise or Enterprise Plus edition, and the more advanced governance and long-term-commitment options sit in the higher editions. Storage is billed per logical or physical byte, with a lower rate for tables or partitions not modified for 90 days; time travel and fail-safe storage (see below) can add to physical storage cost. Loading data from Cloud Storage with a standard load job is free of query charges, while streaming through the Storage Write API is billed per byte ingested. A monthly amount of query processing and storage is free of charge; check the dated pricing page before planning. Set a project-level or user-level maximum bytes billed and custom quotas on query usage per day to avoid a runaway query.

Console tour and first query

In the Google Cloud console

  1. Open the console, select the project in the project picker, and open BigQuery from the navigation menu (or press the search bar and type BigQuery). The API is enabled by default in new projects; otherwise enable it from APIs & Services.

  2. In the Explorer pane, click the three-dot menu on the project, choose Create dataset, enter bookshelf, pick the location us-central1, and click Create dataset. The location cannot be changed afterwards.

  3. Click the dataset, choose Create table, set Create table from to Upload or Google Cloud Storage, pick a CSV such as orders.csv, choose the file format, name the table orders_raw and tick Auto detect for the schema (or paste a schema as JSON). Click Create table.

  4. Open the SQL query editor tab. Before running, look at the validator message at the top right: it shows how many bytes the query will process, which is a dry run. Run the query and read the result and the Job information tab for bytes billed and slot time.

  5. Repeating an identical query within 24 hours is normally answered from the query cache at no charge. Open Query settings to disable the cache when you are benchmarking.

With the gcloud CLI

BigQuery is driven by the bq command-line tool, installed with the gcloud CLI; gcloud itself has only a few gcloud bigquery commands (for example for migration and reservations).

gcloud services enable bigquery.googleapis.com bigquerystorage.googleapis.com

REGION=us-central1

# Create a dataset in a fixed location
bq --location="$REGION" mk --dataset \
  --description "Bookshelf analytics" "$PROJECT_ID:bookshelf"

Partitioning and clustering

A partitioned table is divided into segments by a date or timestamp column, by an integer range, or by ingestion time. When a query filters on the partition column, BigQuery reads only the matching partitions (partition pruning) and bills only those bytes. Clustering sorts the data within each partition by up to four columns, so filters and aggregations on those columns read fewer blocks. Partitioning gives a predictable, up-front cost reduction and the ability to expire old partitions; clustering gives a best-effort reduction and works well with high-cardinality columns. Use both: the Bookshelf orders table is partitioned by order date and clustered by customer_id and status. Ingestion-time partitioning uses a pseudo column _PARTITIONTIME and is convenient when records have no usable event date. You can require a partition filter so that a forgotten WHERE clause cannot scan the whole table, and set a partition expiration to age data out automatically.

bq query --use_legacy_sql=false '
CREATE TABLE bookshelf.orders (
  order_id STRING NOT NULL,
  customer_id STRING,
  status STRING,
  total NUMERIC,
  order_ts TIMESTAMP
)
PARTITION BY DATE(order_ts)
CLUSTER BY customer_id, status
OPTIONS (
  require_partition_filter = TRUE,
  partition_expiration_days = 1095,
  description = "Bookshelf orders, partitioned by day"
)'

# Measure the effect: compare bytes for a filter on the partition column vs not
bq query --use_legacy_sql=false --dry_run \
  'SELECT SUM(total) FROM bookshelf.orders
   WHERE DATE(order_ts) BETWEEN "2026-09-01" AND "2026-09-07" AND status = "placed"'

Reference: Introduction to partitioned tables, Introduction to clustered tables and Create partitioned tables.

In the console the same options appear under Partition and cluster settings when you create a table. A dry run is the tool for judging a design: run the same query against the unpartitioned and the partitioned copy and compare the bytes reported.

Useful SQL patterns

GoogleSQL has a few constructs that appear constantly in warehouse work.

Pivoting turns rows into columns with PIVOT:

SELECT *
FROM (SELECT DATE_TRUNC(DATE(order_ts), MONTH) AS month, status, total
      FROM bookshelf.orders
      WHERE DATE(order_ts) >= "2026-01-01")
PIVOT (SUM(total) FOR status IN ("placed", "shipped", "returned"))
ORDER BY month;

Top one per group is cheapest with ARRAY_AGG and LIMIT 1, which avoids a self join:

SELECT customer_id,
       ARRAY_AGG(STRUCT(order_id, total, order_ts)
                 ORDER BY order_ts DESC LIMIT 1)[OFFSET(0)] AS latest
FROM bookshelf.orders
WHERE DATE(order_ts) >= "2026-01-01"
GROUP BY customer_id;

Deduplication matters because streaming and retried loads deliver at-least-once. Keep the newest row per key with QUALIFY and a window function, and fold new data into the warehouse table with an idempotent MERGE:

MERGE bookshelf.orders AS t
USING (
  SELECT * EXCEPT (rn) FROM (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY order_ts DESC) AS rn
    FROM bookshelf.orders_raw
  ) WHERE rn = 1
) AS s
ON t.order_id = s.order_id AND DATE(t.order_ts) = DATE(s.order_ts)
WHEN MATCHED THEN
  UPDATE SET status = s.status, total = s.total
WHEN NOT MATCHED THEN
  INSERT (order_id, customer_id, status, total, order_ts)
  VALUES (s.order_id, s.customer_id, s.status, s.total, s.order_ts);

References: PIVOT operator, MERGE statement and QUALIFY clause.

Putting the partition column in the MERGE join condition lets BigQuery prune partitions of the target table, which keeps the cost of a nightly merge proportional to the new data instead of to the whole table.

Time travel and recovery

BigQuery keeps the previous states of a table for a time travel window (7 days by default, configurable between 2 and 7 days per dataset). Within that window you can query a table as it was, restore a dropped or overwritten table, or undelete a deleted table. After the window closes, data stays for a further 7-day fail-safe period that only Google support can use. Deleted datasets can be restored for the same window too.

In the Google Cloud console

  1. In the editor, query the past state with FOR SYSTEM_TIME AS OF, for instance an hour ago.

  2. To recover a deleted table, run a table copy from a snapshot decorator in SQL, or use the bq cp command below. The console does not offer a one-click undelete for tables.

  3. To change the window, open the dataset, choose Edit details, expand Advanced options and set the Time travel window.

With the gcloud CLI

# Query the table as it was 1 hour ago
bq query --use_legacy_sql=false \
  'SELECT COUNT(*) FROM bookshelf.orders
   FOR SYSTEM_TIME AS OF TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR)'

# Restore a deleted table: copy it from a point in time (milliseconds since epoch) to a new name
NOW_MS=$(($(date +%s) * 1000))
bq cp "bookshelf.orders@$((NOW_MS - 600000))" bookshelf.orders_restored

# Lengthen or shorten the time travel window for the dataset (hours)
bq update --max_time_travel_hours=168 "$PROJECT_ID:bookshelf"

# Keep a long-lived, cheap copy of a table with a snapshot
bq cp --snapshot --no_clobber \
  bookshelf.orders bookshelf.orders_snapshot_20261001

References: Data retention with time travel and fail-safe, Introduction to table snapshots and Introduction to table clones.

Time travel is a safety net for mistakes, not a backup strategy. Table snapshots, scheduled exports to Cloud Storage and BigQuery’s cross-region dataset replication cover retention and disaster recovery.

BigQuery ML

BigQuery ML lets you create, evaluate and run models using only SQL, with the data staying in the warehouse. It supports linear and logistic regression, boosted trees, k-means clustering, matrix factorisation, time-series forecasting, deep neural networks and imported TensorFlow or ONNX models, and it can call remote models such as Gemini or models deployed on Vertex AI. The workflow is CREATE MODEL, ML.EVALUATE, ML.PREDICT.

CREATE OR REPLACE MODEL bookshelf.return_risk
OPTIONS (model_type = "LOGISTIC_REG", input_label_cols = ["returned"]) AS
SELECT total, EXTRACT(HOUR FROM order_ts) AS hour, customer_segment, returned
FROM bookshelf.orders_features
WHERE DATE(order_ts) < "2026-09-01";

SELECT * FROM ML.EVALUATE(MODEL bookshelf.return_risk, (
  SELECT total, EXTRACT(HOUR FROM order_ts) AS hour, customer_segment, returned
  FROM bookshelf.orders_features
  WHERE DATE(order_ts) >= "2026-09-01"));

SELECT order_id, predicted_returned_probs
FROM ML.PREDICT(MODEL bookshelf.return_risk, (
  SELECT order_id, total, EXTRACT(HOUR FROM order_ts) AS hour, customer_segment
  FROM bookshelf.orders_features
  WHERE DATE(order_ts) = CURRENT_DATE()));

Dataflow

Dataflow is Google’s fully managed runner for Apache Beam pipelines. You describe a pipeline as transforms over PCollections with the Beam SDK (Java, Python or Go), and Dataflow provisions workers, autoscales them, shuffles data and restarts failed work. The same code handles batch and streaming; streaming adds windows (fixed, sliding, session) and triggers that decide when partial results are emitted, driven by event time rather than by processing time. For Pub/Sub sources, Beam can read the event timestamp from a message attribute instead of the publish time, which keeps windows correct when messages arrive late (see the discussion in Messaging and integration).

Three styles of use cover most needs:

  • Provided templates are ready-made pipelines you start with parameters only, for example Pub/Sub to BigQuery, Pub/Sub to Cloud Storage, Cloud Storage text to BigQuery, and BigQuery to Bigtable. No code is required.

  • Flex Templates package your own Beam pipeline as a container image in Artifact Registry plus a JSON spec in Cloud Storage, so that others can launch it with parameters.

  • Your own pipeline launched directly from a development machine or CI.

A few Beam habits keep pipelines maintainable. Prefer Beam schemas (typed rows with named fields, from Java POJOs, Avro, Protocol Buffers or BigQuery) over hand-written coders; schemas let transforms such as Select, Join and GroupBy work by field name and map directly to BigQuery columns. Keep side effects idempotent, because retries can repeat work. Use a dead-letter output for records that fail parsing instead of failing the pipeline.

In the Google Cloud console

  1. Open Dataflow from the navigation menu, enable the Dataflow API if asked, and choose Jobs.

  2. Click Create job from template, enter a job name such as orders-to-bigquery, select the regional endpoint us-central1, and pick the template Pub/Sub Subscription to BigQuery.

  3. Enter the input subscription path, the output table my-project-id:bookshelf.orders_raw, and a temporary location in Cloud Storage. Under Optional parameters choose the worker service account (not the default Compute Engine one) and a maximum worker count.

  4. Click Run job. Open the job graph to watch throughput, system latency and data freshness, and use the Logs panel for errors.

A first Beam pipeline

A minimal batch pipeline in Python reads CSV lines from Cloud Storage, parses them and writes rows to BigQuery. Run it locally with DirectRunner while developing and on Dataflow with --runner=DataflowRunner. Install the SDK with pip install "apache-beam[gcp]".

import argparse
import apache_beam as beam
from apache_beam.options.pipeline_options import PipelineOptions

def parse(line):
    order_id, customer_id, status, total, order_ts = line.split(",")
    return {"order_id": order_id, "customer_id": customer_id, "status": status,
            "total": float(total), "order_ts": order_ts}

def run(argv=None):
    parser = argparse.ArgumentParser()
    parser.add_argument("--input", required=True)
    parser.add_argument("--table", required=True)
    known, beam_args = parser.parse_known_args(argv)
    with beam.Pipeline(options=PipelineOptions(beam_args, save_main_session=True)) as p:
        (p
         | "Read" >> beam.io.ReadFromText(known.input, skip_header_lines=1)
         | "Parse" >> beam.Map(parse)
         | "Write" >> beam.io.WriteToBigQuery(
               known.table,
               schema="order_id:STRING,customer_id:STRING,status:STRING,total:NUMERIC,order_ts:TIMESTAMP",
               write_disposition=beam.io.BigQueryDisposition.WRITE_APPEND,
               create_disposition=beam.io.BigQueryDisposition.CREATE_IF_NEEDED))

if __name__ == "__main__":
    run()
python orders_pipeline.py \
  --input="gs://$BUCKET/exports/orders.csv" --table="$PROJECT_ID:bookshelf.orders_raw" \
  --runner=DataflowRunner --project="$PROJECT_ID" --region="$REGION" \
  --temp_location="gs://$BUCKET/tmp" --service_account_email="$SA"

References: Create a Dataflow pipeline, Apache Beam programming guide and Set Dataflow pipeline options.

Pricing, quotas and security

Dataflow bills for the vCPU, memory and storage of workers (plus the Shuffle or Streaming Engine service) per second, so cost follows worker count and job duration. Streaming jobs run until stopped, which makes forgotten jobs a classic bill. Quotas include the number of concurrent jobs per region, Compute Engine CPUs and in-use IP addresses. Run workers without public IP addresses in a subnet with Private Google Access (see VPC networking), grant the worker service account only the roles above, and use customer-managed encryption keys when policy requires them.

Dataproc and Spark

Dataproc runs open-source data tools. Training, endpoints and batch prediction

Training a model in a notebook ties the work to one VM. Serverless custom training instead runs your code, as a Python package or a container, on resources that exist only for the duration of the job. The training service passes well-known locations to the code through environment variables; for instance AIP_MODEL_DIR is the Cloud Storage directory where the script must save the trained model. The saved model is registered in the Model Registry, then either deployed to an endpoint for low-latency online prediction or run against a dataset for batch prediction, reading from Cloud Storage or BigQuery and writing results back. Endpoints autoscale between a minimum and maximum replica count; dedicated public endpoints and private endpoints over Private Service Connect are the recommended types, and a model that stays deployed bills for its replicas even without traffic.

Gemini and generative AI

Gemini is Google’s family of multimodal generative models. They can be reached three ways: from the platform (Vertex AI API, with enterprise features such as IAM, VPC Service Controls, data residency and customer-managed keys), from the Gemini API in Google AI Studio (API-key based, aimed at prototyping), and as assistants inside Google products, such as Gemini Code Assist in the IDE and Gemini Cloud Assist in the console (Preview at the time of writing). For production work on Google Cloud use the platform path so that calls authenticate with a service account and Application Default Credentials, with no API key to manage. The platform also offers embeddings models, grounding with Google Search or your own data, context caching, function calling and an agent framework, and it hosts third-party and open models as well.

Calling Gemini from the console and the CLI

In the Google Cloud console

  1. Open the platform in the navigation menu and choose Studio (the prompt gallery and testing area).

  2. Choose a Gemini model, type a prompt such as "Summarise these order notes in one sentence", adjust the temperature and token limit, and click Submit.

  3. Use Get code to copy the same request as Python, Java or curl.

With the gcloud CLI

gcloud services enable aiplatform.googleapis.com
TOKEN=$(gcloud auth print-access-token)
MODEL=gemini-2.5-flash   # check the model list for current versions

curl -s -X POST \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  "https://$REGION-aiplatform.googleapis.com/v1/projects/$PROJECT_ID/locations/$REGION/publishers/google/models/$MODEL:generateContent" \
  -d '{"contents":[{"role":"user","parts":[{"text":"Summarise: customer asks to change the delivery address"}]}]}'

References: Google models, Generate content API reference and Quickstart.

Model identifiers are retired on published schedules, so read them from configuration (see Runtime configuration) instead of hard-coding them, and track the model-versions page for retirement dates.

From Java and Spring

Use the Google Gen AI SDK for Java (com.google.genai:google-genai), which targets the platform when configured with a project and location, so Application Default Credentials apply:

package com.example.bookshelf.ai;

import com.google.genai.Client;
import com.google.genai.types.GenerateContentResponse;

public class OrderNoteSummarizer {

    private final Client client = Client.builder()
            .vertexAI(true)
            .project(System.getenv("GOOGLE_CLOUD_PROJECT"))
            .location("us-central1")
            .build();

    public String summarize(String notes) {
        GenerateContentResponse response = client.models.generateContent(
                System.getenv().getOrDefault("GEMINI_MODEL", "gemini-2.5-flash"),
                "Summarise in one sentence: " + notes, null);
        return response.text();
    }
}

Reference: Generative AI SDKs and Application Default Credentials.

Spring applications can use Spring AI’s Google GenAI or Vertex AI integration instead of calling the SDK directly; see Integrating with Spring AI for chat clients, embeddings and vector stores, and Prompt augmentation and generation for the retrieval-augmented pattern. Give the Cloud Run service account roles/aiplatform.user to call models.

Retrieval, search and agents

For grounded answers over your own content, the platform provides Agent Search (formerly Vertex AI Search) for managed search and retrieval over websites, documents and structured data, Agent Retrieval (formerly Vector Search 2.0, in Preview) for vector retrieval at scale, and an agent framework with tool calling. You can also build retrieval-augmented generation yourself with embeddings stored in BigQuery, AlloyDB (ScaNN or pgvector), Cloud SQL (pgvector) or Firestore (see AlloyDB and PostgreSQL pgvector). Use managed search when you want results quickly; build your own when you need control of chunking, ranking and filters (see Document ingestion and chunking).

Pricing for generative models is per input and output token (or character, per modality), with different rates per model and discounts for batch use and context caching; there is no per-hour charge for on-demand Gemini, but provisioned throughput is a commitment. Every model has regional availability, per-minute quotas and a launch stage (Preview models carry no SLA). Prompts and responses are not used to train models for platform customers by default, and data residency and VPC Service Controls apply; verify the current data-governance page before processing personal data.

References: Generative AI pricing, Quotas and limits and Data governance.

Looker and Looker Studio

Looker Studio is a free, browser-based tool for building reports and dashboards, with connectors to BigQuery, Cloud SQL, Google Sheets and many other sources; it suits ad-hoc dashboards and sharing with colleagues who have Google accounts. Looker is the enterprise platform: its LookML modelling layer defines metrics once, so every dashboard and API consumer uses the same definitions, with governance, embedding and a developer workflow in Git. Both read BigQuery directly, so partitioned and clustered tables and BI Engine (an in-memory acceleration layer for BigQuery) keep dashboards fast and cheap. In the console, open Looker Studio from the Explore data menu of a BigQuery table, or go to the Looker Studio site and add a BigQuery data source. A viewer’s query is billed to the project of the data source’s credentials, so use a dedicated service account owner for shared dashboards.

References: Looker documentation, Looker Studio documentation and Introduction to BI Engine.

Cost, quotas and the shape of a bill

Data and AI services share a few cost traits worth planning for.

  • BigQuery on-demand cost follows bytes scanned; partitioning, clustering, selecting columns and dry runs control it. Capacity pricing follows slots and can be capped with a reservation’s maximum.

  • Streaming and storage costs accumulate silently: table storage, snapshots, long time travel windows and unexpired partitions all bill.

  • Dataflow streaming jobs, Dataproc clusters, Data Fusion instances, Workbench notebooks and deployed Vertex AI endpoints bill by the hour while they exist, whether or not they process data.

  • Gemini cost follows tokens; keep prompts short, cache context and use smaller models for simple tasks.

  • Egress between regions and out of Google Cloud is billed; keep datasets, buckets and jobs in one location.

  • Set budgets and alerts (see Cost management and billing), label resources by team, and export billing data to BigQuery.

References: BigQuery pricing, Dataflow pricing, Dataproc pricing and Vertex AI pricing. Pricing pages change; use the dated page and the pricing calculator.

What changed since older guides

  • The Google Cloud documentation host is docs.cloud.google.com; the older cloud.google.com/…​ URLs redirect.

  • Vertex AI was rebranded Gemini Enterprise Agent Platform on 2026-04-22; Vertex AI Search became Agent Search and Vector Search 2.0 became Agent Retrieval (Preview). APIs and IAM names keep the Vertex AI and Discovery Engine names.

  • Workbench’s managed and user-managed notebook types were replaced by Workbench instances.

  • Dataflow SQL and some legacy Dataflow templates have changed; prefer current templates, Beam SQL or BigQuery SQL.

  • The BigQuery Storage Write API supersedes the older insertAll streaming API for new work, and BigQuery editions (Standard, Enterprise, Enterprise Plus) replaced the older flat-rate commitments.

  • gsutil is superseded by gcloud storage for staging files; downloaded service-account keys are superseded by attached service accounts and Workload Identity Federation (see Identity and access).

  • Dataproc connectors are bundled in current image versions, so initialization actions for them are rarely needed.

Clean up

Delete billable resources first, in dependency order. Data services keep charging while idle.

# Streaming jobs and Spark
gcloud dataflow jobs drain JOB_ID --region="$REGION"
gcloud dataproc clusters delete bookshelf-spark --region="$REGION" --quiet
gcloud beta data-fusion instances delete bookshelf-fusion --location="$REGION" --quiet

# Vertex AI: undeploy before deleting the endpoint and model
gcloud ai endpoints undeploy-model ENDPOINT_ID --region="$REGION" --deployed-model-id=DEPLOYED_MODEL_ID
gcloud ai endpoints delete ENDPOINT_ID --region="$REGION" --quiet
gcloud ai models delete MODEL_ID --region="$REGION" --quiet
gcloud workbench instances delete bookshelf-notebook --location=us-central1-a --quiet

# Subscriptions created on this page
gcloud pubsub subscriptions delete orders-dataflow orders-archive --quiet

# BigQuery tables and the dataset (-r removes contained tables)
bq rm -r -f -d "$PROJECT_ID:bookshelf"

Deleted BigQuery tables can be restored for the time travel window, and storage still bills during it, so a deleted dataset is not instantly free. Delete the Dataflow worker service account (gcloud iam service-accounts delete) and the Cloud Storage objects under tmp and models, which otherwise keep accruing storage cost. If you created everything in a throwaway project, deleting the project removes all of it (see Resource hierarchy and projects).

References: gcloud dataflow jobs drain, gcloud dataproc clusters delete and Delete datasets.
