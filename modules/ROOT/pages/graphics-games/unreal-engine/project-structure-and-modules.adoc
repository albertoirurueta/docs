include::partial$ai-disclaimer.adoc[]

An Unreal project looks like a folder of assets and a folder of {cpp}, but behind that folder sits a build system with its own vocabulary: *modules* that compile separately, *targets* that decide what is built, three tools
that run in a fixed order (UnrealBuildTool, UnrealHeaderTool, UnrealAutomationTool) and a layered set of `.ini` files that configure everything at run time. Understanding this layout turns most baffling build errors, "why is my
setting ignored" questions and "which files do I commit" questions into one-line answers. It is also where {cpp} in Unreal differs most from a CMake project, for which see
xref:programming-languages/cpp/program-structure-and-compilation.adoc[Program Structure and Compilation] and xref:programming-languages/cpp/build-and-tooling.adoc[Build and Tooling].

The facts were checked in November 2026 against the Unreal Engine 5.8 documentation (release 5.8, hotfix 5.8.4). The layout and tools are the same on Windows, macOS and Linux; the command lines below use
Windows paths and PowerShell, and the engine ships `.sh` and `.command` equivalents of each `.bat` script. The running example is the *Bookshelf* project from
xref:graphics-games/unreal-engine/installing-and-building-from-source.adoc[Installing and Building from Source]: a Third Person template project with a {cpp} module named `Bookshelf`, an API macro `BOOKSHELF_API`, a log category `LogBookshelf` and later
an editor module. This page writes every file of that module.

== The project folder

.The Bookshelf project folder, annotated with what to commit
image::graphics-games-unreal-engine-project-structure-and-modules-folder-tree.svg["Tree of the Bookshelf project folder: Bookshelf.uproject, Config, Content, Source with two Target.cs files and the Bookshelf module folder containing Bookshelf.Build.cs and Public and Private, and Plugins are marked to commit; Binaries, Intermediate, Saved and DerivedDataCache are marked as generated",width=720]

A project folder is created by the Project Browser and holds a small, fixed set of folders. The first column names the folder, the second what Epic's directory documentation says it is for, and the third what to do with it in source control.

[cols="2,4,2"]
|===
|Folder or file |Purpose |Source control

|`Bookshelf.uproject`
|The project descriptor, a JSON file: which engine, which modules, which plugins and platforms. Opening it launches the editor.
|Commit

|`Config/`
|The `.ini` files that control engine behaviour. "Values set in the game project Config files override the values set in the `Engine\Config` directory."
|Commit

|`Content/`
|Asset packages (`.uasset`) and maps (`.umap`). A project's content is available only to that project; engine content is shared by every project using that engine.
|Commit; use Git LFS or Perforce for the large binary files

|`Source/`
|{cpp} code, one folder per module, and the `.Target.cs` files. Each module folder contains the `.Build.cs`, and conventionally `Public` and `Private` subfolders (the engine's own modules also have `Classes` and `Internal`).
|Commit

|`Plugins/`
|Project-local plugins. A plugin differs from a module in that it ships its own source, binaries, a `.uplugin` file and, optionally, content, so it can be redistributed.
|Commit (without its `Binaries` and `Intermediate`)

|`Binaries/`
|Executables and DLLs produced by compilation.
|Ignore

|`Intermediate/`
|Temporary files from builds, such as generated code and IDE project files; in a game directory the compiled shaders are stored here. Can be deleted and rebuilt.
|Ignore

|`Saved/`
|Autosaves, local `.ini` files and logs. Can be deleted and regenerated.
|Ignore

|`DerivedDataCache/`
|Derived data generated when referenced content loads, such as compiled shaders and cooked texture data. Missing cache files can greatly increase load times, but nothing is lost.
|Ignore
|===

The engine's own folder has the same ideas at a larger scale: `Engine/Source` is split into `Developer` (shared by editor and runtime), `Editor`, `Programs` (external tools) and `Runtime`; `Engine/Plugins` holds engine plugins available to all projects; `Engine/Config` holds the base `.ini` files; and `Engine/Content` holds engine assets. Projects can sit inside the engine root as *native* projects
or elsewhere on disk as *foreign* projects; every Launcher project is foreign, and source-built engines also support both. Native projects can be listed in a `.uprojectdirs` file such as `Default.uprojectdirs`.

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-directory-structure[Unreal Engine Directory Structure] and https://dev.epicgames.com/documentation/unreal-engine/managing-game-code-in-unreal-engine[Managing Game Code in Unreal Engine]

=== What to put under source control

Everything the table marks "Commit", and nothing marked "Ignore". The following files implement that rule; without Git LFS the repository grows by the size of every revision of every asset.

[source,bash]
----
# .gitignore for an Unreal project
Binaries/
DerivedDataCache/
Intermediate/
Saved/
.vs/
.idea/
*.sln
*.suo
*.xcworkspace
*.xcodeproj
Plugins/*/Binaries/
Plugins/*/Intermediate/
----

[source,bash]
----
# .gitattributes: store large binary assets in Git LFS
*.uasset filter=lfs diff=lfs merge=lfs -text
*.umap   filter=lfs diff=lfs merge=lfs -text
*.png    filter=lfs diff=lfs merge=lfs -text
*.wav    filter=lfs diff=lfs merge=lfs -text
*.glb    filter=lfs diff=lfs merge=lfs -text
----

The shared xref:attachment$bookshelf.glb[bookshelf.glb] is only the source asset; the imported `.uasset` files are what the project loads. Unreal assets are binary and cannot be merged, which is why teams use exclusive checkout (Perforce) or the *One File Per Actor* feature of World Partition (see
xref:graphics-games/unreal-engine/world-partition-and-pcg.adoc[World Partition and PCG]) to reduce conflicts.

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-directory-structure[Unreal Engine Directory Structure]

== The .uproject file

The descriptor lists the fields `FileVersion`, `EngineAssociation`, `Category`, `Description`, `Modules`, `Plugins` and `TargetPlatforms`. `EngineAssociation` holds either a Launcher version number such as `"5.8"` or the GUID of a source-built editor; right-click the file and choose *Switch Unreal Engine version* to change it, and *Generate Visual Studio project files* (or *Generate Xcode project files* on macOS) to
regenerate IDE files.

[source,json]
----
{
    "FileVersion": 3,
    "EngineAssociation": "5.8",
    "Category": "",
    "Description": "Bookshelf: a tiny game that grows from a book actor into a co-op library.",
    "Modules": [
        {
            "Name": "Bookshelf",
            "Type": "Runtime",
            "LoadingPhase": "Default"
        },
        {
            "Name": "BookshelfEditor",
            "Type": "Editor",
            "LoadingPhase": "Default"
        }
    ],
    "Plugins": [
        {
            "Name": "GameplayAbilities",
            "Enabled": true
        },
        {
            "Name": "CommonUI",
            "Enabled": true
        }
    ],
    "TargetPlatforms": [
        "Windows",
        "Android"
    ]
}
----

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-modules[Unreal Engine Modules] and https://dev.epicgames.com/documentation/unreal-engine/managing-game-code-in-unreal-engine[Managing Game Code in Unreal Engine]

* `Modules` controls which modules load and how. Regenerating project files adds entries for modules in the dependency chain. Optional filters restrict a module by platform, target, target configuration or program: `IncludelistPlatforms` and `ExcludelistPlatforms`, `IncludelistTargets` and `ExcludelistTargets`, `IncludelistTargetConfigurations` and `ExcludelistTargetConfigurations`, `IncludelistPrograms` and `ExcludelistPrograms`.
* `Plugins` enables or disables plugins by name for this project. Enabling a plugin in the Plugins window of the editor writes this entry; a module that uses a plugin's code also names the plugin's module in its `Build.cs`.
* `TargetPlatforms` limits the platforms the editor offers when packaging.
* The descriptor is plain JSON, so it can be edited by hand, but an editor that is open when you change it does not see the change until it restarts.

== Modules

A *module* is the basic building block of Unreal's architecture. It packages editor tools, runtime features or libraries as a standalone unit that compiles separately, so only the modules that changed are rebuilt. Every project and plugin has a primary module and can add more. A module is a folder with a `Build.cs` file; its name is the folder name, and
it is the unit of dependency: a module can only include headers from modules it depends on.

[cols="2,5"]
|===
|Module type (in `.uproject` or `.uplugin`) |Meaning

|`Runtime`
|Loaded in the game and the editor. This is where gameplay classes go.

|`RuntimeNoCommandlet`
|Like Runtime but not loaded when a commandlet runs.

|`Developer`
|Developer tools, loaded in editor and development builds, not in shipping.

|`Editor`
|Editor-only code: asset editors, details customisations, tool menus. Never shipped.

|`EditorNoCommandlet`
|Editor code that is not loaded for commandlets.

|`Program`
|For standalone programs built on the engine.
|===

`LoadingPhase` controls when the module loads: `Default` suits most gameplay modules, and `PreDefault` is for plugins that must load earlier, for example when the editor cannot find their {cpp} classes. Load order is not deterministic within one phase; use `LoadModule` or `LoadModuleChecked` in `StartupModule` to enforce an order.

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-modules[Unreal Engine Modules] and https://dev.epicgames.com/documentation/en-us/unreal-engine/plugins-in-unreal-engine[Plugins in Unreal Engine]

=== Build.cs and ModuleRules

.The Bookshelf's targets, modules and the engine modules they use
image::graphics-games-unreal-engine-project-structure-and-modules-module-graph.svg["Three Target.cs boxes for Game, Server and Editor at the top, pointing at the Bookshelf runtime module and the BookshelfEditor editor module in the middle, with dashed arrows down to the engine modules Core, CoreUObject, Engine, InputCore, EnhancedInput and UnrealEd",width=720]

Each module needs a `<ModuleName>.Build.cs` file in its root folder. It defines a class derived from `ModuleRules` that UnrealBuildTool finds and runs to learn the module's dependencies, extra libraries and include paths. The file is C# and the class name equals the module name; for the C# language itself,
xref:programming-languages/csharp/attributes-and-reflection.adoc[C# Attributes and Reflection] explains the reflection that has no equivalent in {cpp}, which is the reason Unreal builds its own (see
xref:graphics-games/unreal-engine/uobject-reflection-and-garbage-collection.adoc[UObject, Reflection and Garbage Collection]).

[source,csharp]
----
// Source/Bookshelf/Bookshelf.Build.cs
using UnrealBuildTool;

public class Bookshelf : ModuleRules
{
    public Bookshelf(ReadOnlyTargetRules Target) : base(Target)
    {
        PCHUsage = PCHUsageMode.UseExplicitOrSharedPCHs;

        // Needed in public headers: base classes, UPROPERTY types, input.
        PublicDependencyModuleNames.AddRange(new string[]
        {
            "Core",
            "CoreUObject",
            "Engine",
            "InputCore",
            "EnhancedInput"
        });

        // Needed only in .cpp files (settings now, gameplay tags in later pages).
        PrivateDependencyModuleNames.AddRange(new string[]
        {
            "DeveloperSettings",
            "GameplayTags"
        });
    }
}
----

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-modules[Unreal Engine Modules]

* *`PublicDependencyModuleNames`* is for modules whose classes appear in your *public* headers, so that modules depending on `Bookshelf` can include them too.
* *`PrivateDependencyModuleNames`* is for modules used only in `.cpp` files. Epic's guidance is that private dependencies are preferred wherever possible, because they reduce compile times.
* The name of a module in a dependency list is a string. A mistyped name does not fail in C#; the error appears later, as an unresolved include or link error.
* `PCHUsage` chooses precompiled header behaviour; the generated templates use `UseExplicitOrSharedPCHs`.
* `Public` and `Private` folders matter: headers under `Public` are visible to other modules, headers under `Private` are not. Module code includes other module headers by their `Public` relative path.
* Circular dependencies between modules are an error. Put shared types in a lower module.

=== The module's own header and source

The primary game module also declares the macro by which classes are exported and registers the module with the engine. `BOOKSHELF_API` is generated from the module name; it is `+__declspec(dllexport)+` when the module compiles and `+__declspec(dllimport)+` for modules that use it, and an empty macro in a monolithic build.
Put `BOOKSHELF_API` on classes and functions other modules call (for example, an editor module that includes `BookActor.h`).

[source,cpp]
----
// Source/Bookshelf/Bookshelf.h
#pragma once

#include "CoreMinimal.h"

// Log category used by every Bookshelf class: UE_LOG(LogBookshelf, Log, TEXT("..."));
DECLARE_LOG_CATEGORY_EXTERN(LogBookshelf, Log, All);
----

[source,cpp]
----
// Source/Bookshelf/Bookshelf.cpp
#include "Bookshelf.h"

#include "Modules/ModuleManager.h"

DEFINE_LOG_CATEGORY(LogBookshelf);

IMPLEMENT_PRIMARY_GAME_MODULE(FDefaultGameModuleImpl, Bookshelf, "Bookshelf");
----

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/logging-in-unreal-engine[Logging in Unreal Engine] and https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-modules[Unreal Engine Modules]

A secondary module uses `IMPLEMENT_MODULE(FDefaultModuleImpl, ModuleName);` instead of the primary-module macro. For the editor module of the Bookshelf the folder is `Source/BookshelfEditor` with its own `Build.cs` that depends on `Bookshelf` and on editor modules, and is
registered in the `.uproject` as `"Type": "Editor"` (see above).

[source,csharp]
----
// Source/BookshelfEditor/BookshelfEditor.Build.cs
using UnrealBuildTool;

public class BookshelfEditor : ModuleRules
{
    public BookshelfEditor(ReadOnlyTargetRules Target) : base(Target)
    {
        PCHUsage = PCHUsageMode.UseExplicitOrSharedPCHs;

        PublicDependencyModuleNames.AddRange(new string[] { "Core", "CoreUObject", "Engine" });

        PrivateDependencyModuleNames.AddRange(new string[]
        {
            "Bookshelf",
            "UnrealEd",
            "Slate",
            "SlateCore"
        });
    }
}
----

[source,cpp]
----
// Source/BookshelfEditor/Private/BookshelfEditorModule.cpp
#include "Modules/ModuleManager.h"

IMPLEMENT_MODULE(FDefaultModuleImpl, BookshelfEditor);
----

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/how-to-make-a-gameplay-module-in-unreal-engine[How To Make a Gameplay Module in Unreal Engine]

To add a module by hand, follow the same recipe: create the folder with `Private` and `Public`, write the `Build.cs`, add a `Private/<Name>Module.cpp` with `IMPLEMENT_MODULE`, add the module to the `Modules` list of the `.uproject`, add its name to another module's dependency list, and regenerate the project files.
Close the editor while you do this: Live Coding does not add modules.

== Targets

A *target* is a build recipe: it says what kind of executable or editor to produce and which project modules it contains. Targets are C# classes in files named `<Name>.Target.cs`, directly in `Source/`; the class name is the file name plus `Target`, and it derives from `TargetRules`. Epic's target reference lists five target types.

[cols="1,4"]
|===
|`TargetType` |Meaning

|`Game`
|A standalone game that requires cooked data to run.

|`Client`
|Like Game, but without server code.

|`Server`
|Like Game, but without client code, for dedicated servers.

|`Editor`
|Extends the Unreal Editor with your modules.

|`Program`
|A standalone utility built on the engine.
|===

[source,csharp]
----
// Source/Bookshelf.Target.cs
using UnrealBuildTool;
using System.Collections.Generic;

public class BookshelfTarget : TargetRules
{
    public BookshelfTarget(TargetInfo Target) : base(Target)
    {
        Type = TargetType.Game;
        DefaultBuildSettings = BuildSettingsVersion.Latest;
        IncludeOrderVersion = EngineIncludeOrderVersion.Latest;
        ExtraModuleNames.Add("Bookshelf");
    }
}
----

[source,csharp]
----
// Source/BookshelfEditor.Target.cs
using UnrealBuildTool;
using System.Collections.Generic;

public class BookshelfEditorTarget : TargetRules
{
    public BookshelfEditorTarget(TargetInfo Target) : base(Target)
    {
        Type = TargetType.Editor;
        DefaultBuildSettings = BuildSettingsVersion.Latest;
        IncludeOrderVersion = EngineIncludeOrderVersion.Latest;
        ExtraModuleNames.AddRange(new string[] { "Bookshelf", "BookshelfEditor" });
    }
}
----

[source,csharp]
----
// Source/BookshelfServer.Target.cs: a dedicated server for the co-op mode
using UnrealBuildTool;
using System.Collections.Generic;

public class BookshelfServerTarget : TargetRules
{
    public BookshelfServerTarget(TargetInfo Target) : base(Target)
    {
        Type = TargetType.Server;
        DefaultBuildSettings = BuildSettingsVersion.Latest;
        IncludeOrderVersion = EngineIncludeOrderVersion.Latest;
        ExtraModuleNames.Add("Bookshelf");
    }
}
----

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-build-tool-target-reference[Unreal Build Tool Target Reference]

Selected `TargetRules` properties from Epic's reference:

[cols="2,4"]
|===
|Property |Meaning

|`Type`
|The `TargetType` above.

|`DefaultBuildSettings` (`BuildSettingsVersion`)
|The engine version whose default build settings the target keeps, for backward compatibility. Specifying the latest value always uses the defaults of the current engine and can cause build errors when you upgrade; the template of your own project pins the value it was created with.

|`IncludeOrderVersion` (`EngineIncludeOrderVersion`)
|The include order version used to compile the target. `-ForceIncludeOrder` on the command line can override it, and `ModuleRules.IncludeOrderVersion` takes precedence over it.

|`ForcedIncludeOrder`
|Forces an include order version, overriding any target and module rules.

|`LinkType` (`TargetLinkType`)
|Monolithic or modular linking.

|`bUseUnityBuild`
|Whether source files are combined into unity files to compile faster.

|`bCompileAgainstEditor`, `bBuildDeveloperTools`
|Whether the target compiles against editor code or builds developer tools.

|`bIWYU`, `bIsEngineInstalled`, `HostPlatform`, `Architecture`
|Read-only: include-what-you-use mode, installed engine, host platform and CPU architecture.
|===

Because editor targets are modular, each module becomes a DLL (for example `UnrealEditor-Bookshelf.dll` in `Binaries/Win64`), and the editor loads them at start-up. Packaged game targets are linked monolithically by default, into one executable. A monolithic build is chosen in `BuildConfiguration.cs` or on the target, and it is why code
that works in the editor can fail to link or load in a packaged game when a module dependency is missing.

=== Build configurations

Each target is built in a *configuration*. Epic's build configuration page notes that the generated IDE projects include or omit configurations with `bIncludeDebugConfigs`, `bIncludeDevelopmentConfigs` and `bIncludeTestAndShippingConfigs` (and the matching `-NoDebugConfigs`, `-NoDevelopmentConfigs` and `-NoShippingConfigs` options), and that Shipping implies symbol stripping. In summary:

[cols="1,4"]
|===
|Configuration |Use

|`Debug`
|Unoptimised engine and game code, for debugging engine internals. Needs the Editor symbols and is very slow.

|`DebugGame`
|Engine code optimised, game modules unoptimised: the usual configuration for stepping through your own code.

|`Development`
|Optimised with developer features and asserts: the default for day-to-day work and for the editor.

|`Test`
|Like Shipping but with some profiling and console features kept, for performance testing.

|`Shipping`
|The final release: no console, stats or developer tools, symbols stripped.
|===

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/build-configuration-for-unreal-engine[Build Configuration for Unreal Engine]

== The build pipeline

[mermaid]
....
flowchart LR
    SRC[".uproject, Build.cs and Target.cs files"] --> UBT["UnrealBuildTool"]
    UBT --> UHT["UnrealHeaderTool: parses reflection macros, writes generated.h and gen.cpp files"]
    UHT --> CC["C++ compiler"]
    UBT --> CC
    CC --> LNK["Linker"]
    LNK --> OUT["Binaries: one DLL per module in the editor, one executable when monolithic"]
    UAT["UnrealAutomationTool: RunUAT BuildCookRun"] --> UBT
    UAT --> COOK["Cook, stage, pack and archive content"]
    OUT --> RUN["Editor or game"]
    COOK --> RUN
....

* *UnrealBuildTool (UBT)* is a custom tool that manages the process of building the source code across configurations. It reads each module's `Build.cs` and each target's `Target.cs`, decides what to compile, invokes UHT, and calls the compiler and linker. It runs independently of IDE project files (`.sln`, `.vcproj`): the IDE only calls UBT.
* *UnrealHeaderTool (UHT)* is a parsing and code-generation tool. Compilation has two phases: first UBT invokes UHT to parse the headers and generate the code that implements the `UObject` features (the `generated.h` and `gen.cpp` files), then UBT calls the compiler on the results. You rarely run UHT directly; its options matter for UHT plugin work, such as
`-FailIfGeneratedCodeChanges`, `-NoGoWide` for debugging, and logs at `Engine/Programs/UnrealHeaderTool/Saved/Logs/UnrealHeaderTool.log`. A known pitfall: a header that contains only `DECLARE_DYNAMIC_` delegates is not parsed, because UBT does not see it as needing parsing; put the `UDELEGATE` keyword above at least one delegate.
* *UnrealAutomationTool (UAT)* is a generic system that automates processes, including testing and building games. Its `BuildCookRun` command, run through `RunUAT.bat` (`RunUAT.sh` and `RunUAT.command` elsewhere), builds, cooks, stages and packages a project; *BuildGraph* is its scripting layer for custom builds. Packaging is covered in xref:graphics-games/unreal-engine/packaging-desktop.adoc[Packaging for Desktop].

The following PowerShell builds the Bookshelf editor with UBT and packages a Win64 build with UAT. Adjust the engine path to your install. It is a command-line equivalent of *Build* in the IDE and of *Platforms > Windows > Package Project* in the editor.

[source,powershell]
----
$Engine  = "C:\Program Files\Epic Games\UE_5.8"
$Project = "C:\Dev\Bookshelf\Bookshelf.uproject"

# Build the editor target (what the IDE's Development Editor | Win64 configuration does)
& "$Engine\Engine\Build\BatchFiles\Build.bat" BookshelfEditor Win64 Development "-Project=$Project" -WaitMutex

# Build, cook, stage and archive a packaged Win64 build
& "$Engine\Engine\Build\BatchFiles\RunUAT.bat" BuildCookRun `
    "-project=$Project" -noP4 -platform=Win64 -clientconfig=Development `
    -build -cook -stage -pak -archive "-archivedirectory=C:\Dev\Bookshelf\Packaged"
----

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-build-tool-in-unreal-engine[Unreal Build Tool], https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-header-tool-for-unreal-engine[Unreal Header Tool] and https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-automation-tool-for-unreal-engine[Unreal Automation Tool]

UBT also reads user-level settings from `BuildConfiguration.xml`. Project-specific settings go in `<ProjectDirectory>/Saved/UnrealBuildTool/BuildConfiguration.xml`; user-wide ones in `%APPDATA%\Unreal Engine\UnrealBuildTool\BuildConfiguration.xml` on Windows or
`~/.config/Unreal Engine/UnrealBuildTool/BuildConfiguration.xml` on macOS and Linux. Epic's page also lists engine-level and Documents-folder locations.

== Generating project files and opening the code

The IDE projects are generated, never edited. Right-click `Bookshelf.uproject` and choose *Generate Visual Studio project files* (*Generate Xcode project files* on macOS), or use *Tools > Refresh Visual Studio Project* in the editor. UBT writes the files, including IntelliSense data, to `Intermediate/ProjectFiles`; deleting `Intermediate` means you must regenerate them. Open the generated `Bookshelf.sln` in Visual Studio
(`UE5.sln` for a project inside a source engine root, `Bookshelf.xcodeproj` on macOS), or use *Tools > Open Visual Studio* or *File > Open in Xcode* from the editor. VS Code and Rider read the same project data; see xref:graphics-games/unreal-engine/installing-and-building-from-source.adoc[Installing and Building from Source] for the toolchains.

Regenerate whenever you add or remove source files, add a module, change a `Build.cs` or `Target.cs` or switch engine versions.

== Adding a class with the wizard

.Storyboard: create the BookActor class
image::graphics-games-unreal-engine-project-structure-and-modules-new-class-storyboard.svg["Five panels: open Tools then New C++ Class, choose Actor as the parent class, name the class BookActor and choose Public or Private, create the class so that the header and source are written, then compile with Live Coding so the class appears in Place Actors",width=720]

. In the editor choose *Tools > New {cpp} Class...* (a Blueprint-only project gets its {cpp} setup from this first class).
. The *Choose Parent Class* page shows common classes; select *Actor*, or choose *All Classes* to see the whole hierarchy, and click *Next*.
. Enter the name `BookActor` (alphanumeric characters only, no spaces) and choose where it goes: the module (here `Bookshelf`) and the `Public` or `Private` folder. Click *Create Class*.
. The wizard writes `BookActor.h` and `BookActor.cpp` into the module folders and, in a project that had no module, creates the `Source` folder, the `Build.cs`, the `Target.cs` files and the module files shown above. In a new module it also regenerates the IDE files.
. Compile: Live Coding is on by default, so press *Ctrl + Alt + F11* in the editor or the IDE. Otherwise build from the IDE with the editor closed.

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/using-the-cplusplus-class-wizard-in-unreal-engine[Using the {cpp} Class Wizard in Unreal Engine]

== Live Coding

*Live Coding* recompiles {cpp} while the editor or a Play In Editor session keeps running. It is on by default in new installs; press *Ctrl + Alt + F11* in the IDE or the editor to compile and patch. It also works with a packaged desktop build attached to the editor; it does not work on consoles or mobile. The Live Coding console starts with the IDE and stays hidden until a build starts.

[cols="2,4"]
|===
|Situation |What happens

|Body of a function changes
|Patched into the running process; the usual, safe case.

|A default value changes in a `.cpp` constructor
|Existing instances do not change. The same change in the `.h` file does take effect.

|New functions, new variables or larger refactors
|Can behave unpredictably unless *Enable Reinstancing* is on; without reinstancing these changes usually crash.

|Reflected types (`UCLASS`, `UFUNCTION`, `USTRUCT`, `UENUM`, `UDELEGATE`)
|Covered by Object Reinstancing. Code that holds pointers to reinstanced objects must use `ReloadReinstancingCompleteDelegate` and `ReloadCompleteDelegate` to refresh them or clear caches.

|With reinstancing, closing the editor
|May crash on shutdown because lingering objects conflict between old and new destructors.

|A new `Build.cs`, `Target.cs` or module
|Close the editor and build from the IDE.
|===

Settings are under *Editor Preferences > General > Live Coding*: *Enable Live Coding*, *Startup* (active or visible console), *Enable Reinstancing* (disabling is not recommended), *Automatically Compile Newly Added {cpp} Classes* and the list of modules to preload. Preloading more modules slows start-up; avoid preloading engine modules unless you change engine source.
*Hot Reload* remains available: if you disable *Enable Live Coding*, the editor falls back to it, but Epic describes Live Coding as faster and more flexible. When the editor misbehaves after a few patches, restart it: a restart costs less than chasing a ghost.

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/using-live-coding-to-recompile-unreal-engine-applications-at-runtime[Using Live Coding to Recompile Unreal Engine Applications at Runtime]

== Plugins

A *plugin* is a module container that can be enabled per project, redistributed and even carry content. Engine plugins live in `Engine/Plugins/<Name>/` and are available to every project; game plugins live in `<Project>/Plugins/<Name>/`. The engine scans the subfolders under `Plugins`, but does not scan inside a plugin it has already found.

* `Source/` holds one or more modules, each with its `.Build.cs`; code is optional (a plugin can be content only).
* `Binaries/` and `Intermediate/` are generated.
* `Content/` holds the plugin's assets and requires `CanContainContent` set to `true` in the descriptor.
* `Config/` holds settings: `Base<PluginName>.ini` for engine plugins and `Default<PluginName>.ini` for game plugins; these are not packaged automatically and must be copied into the project's `Config` folder by hand.
* `Resources/Icon128.png` is the 128 by 128 icon shown in the plugin browser.

The descriptor is a JSON file named `<PluginName>.uplugin` in the plugin root. `FileVersion` is the only required field (Epic recommends 3). Others include `FriendlyName`, `Version`, `VersionName`, `Category`, `EnabledByDefault`, `CanContainContent` and `Modules`; boolean fields drop the leading `b` of their variable names. Each module entry needs `Name` and `Type`
and may set `LoadingPhase`. A plugin can depend on other plugins at the same or higher level through its own `.uplugin`.

[source,json]
----
{
    "FileVersion": 3,
    "FriendlyName": "Bookshelf Extras",
    "Version": 1,
    "VersionName": "1.0",
    "Category": "Gameplay",
    "EnabledByDefault": true,
    "CanContainContent": true,
    "Modules": [
        {
            "Name": "BookshelfExtras",
            "Type": "Runtime",
            "LoadingPhase": "Default"
        }
    ]
}
----

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/plugins-in-unreal-engine[Plugins in Unreal Engine]

Enable or disable plugins in the Plugins window of the editor (*Edit > Plugins*), which writes the `.uproject` entry; the editor may need to restart. Features packaged as plugins include Enhanced Input, Gameplay Abilities and CommonUI, and the Game Features framework loads plugins at run time (see
xref:graphics-games/unreal-engine/data-driven-gameplay.adoc[Data-Driven Gameplay]).

== The config hierarchy

.Order of the Engine-category config files
image::graphics-games-unreal-engine-project-structure-and-modules-config-hierarchy.svg["Five stacked boxes from first to last loaded: engine base ini files, platform base files, the project DefaultEngine.ini highlighted as the file to edit, platform override files, and user override files; an arrow beside them reads that later files win",width=720]

Settings are stored in plain-text `.ini` files grouped by *category* (`Engine`, `Game`, `Input`, `Editor`, `Scalability` and others). For each category the engine loads a chain of files; if the same key appears in several, the later file wins. For the `Engine` category the order is:

[cols="1,5"]
|===
|# |File

|1
|`Engine/Config/Base.ini`

|2
|`Engine/Config/BaseEngine.ini`

|3
|`Engine/Config/<Platform>/Base<Platform>Engine.ini` and `Engine/Platforms/<Platform>/Config/Base<Platform>Engine.ini`

|4
|`<Project>/Config/DefaultEngine.ini`

|5
|`Engine/Config/<Platform>/<Platform>Engine.ini` and `Engine/Platforms/<Platform>/Config/<Platform>Engine.ini`

|6
|`<Project>/Config/<Platform>/<Platform>Engine.ini` and `<Project>/Platforms/<Platform>/Config/<Platform>Engine.ini`

|7
|`<LocalAppData>/Unreal Engine/Engine/Config/UserEngine.ini`, `<MyDocuments>/Unreal Engine/Engine/Config/UserEngine.ini` and `<Project>/Config/UserEngine.ini`
|===

File names follow `Base<Category>.ini` for engine defaults, `Default<Category>.ini` for project defaults, `<Platform><Category>.ini` for platform files and `User<Category>.ini` for per-user overrides. *Edit the `Default` files and commit them.* The editor writes changes made in Project Settings to `Default*.ini` for settings marked as default config, and other values go to `Saved/Config/<Platform>`,
which is regenerated and not committed.

=== Syntax

* A section is the class path: `[/Script/ModuleName.ClassName]` for module classes (the class name without its `U` or `A` prefix), `[/Script/PluginName.ClassName]` for plugin classes, `[/PathToUAsset/UAssetName.UAssetName_C]` for Blueprint assets, or any alphabetic name for a custom section that code must read by hand. Comments start with `;`.
* For arrays: `pass:c[+Key=Value]` appends if not present, `-Key=Value` removes an exact match, `.Key=Value` appends even if duplicated and `!Key=Ignored` clears the array (the value after `=` is ignored, so write a descriptive one).
* The console command `GetIni [Platform@]IniFile:Section Key` prints a loaded value; only loaded files are searched.

[source,ini]
----
; Config/DefaultEngine.ini: start the editor and the game on the library level
[/Script/EngineSettings.GameMapsSettings]
EditorStartupMap=/Game/Maps/L_Library.L_Library
GameDefaultMap=/Game/Maps/L_Library.L_Library

; Config/DefaultGame.ini: the project's own settings class (defined below)
[/Script/Bookshelf.BookshelfSettings]
MaxBooksPerShelf=16
ReturnSlotRadius=45.0
+ShelfLabels=Fiction
+ShelfLabels=Reference
----

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/configuration-files-in-unreal-engine[Configuration Files in Unreal Engine]

=== Reading config values from {cpp}

A class reads its own settings automatically when it is declared with a config category (`UCLASS(config=Game)`) and the property is `UPROPERTY(Config)`, using a section named after the class without its prefix. The best practice for project-wide settings is a `UDeveloperSettings` subclass, which also appears in *Project Settings* in the editor
and needs the `DeveloperSettings` module in `Bookshelf.Build.cs` (it is there above).

[source,cpp]
----
// Source/Bookshelf/Public/BookshelfSettings.h
#pragma once

#include "CoreMinimal.h"
#include "Engine/DeveloperSettings.h"
#include "BookshelfSettings.generated.h"

/** Project-wide Bookshelf settings, stored in Config/DefaultGame.ini. */
UCLASS(Config = Game, DefaultConfig, meta = (DisplayName = "Bookshelf"))
class BOOKSHELF_API UBookshelfSettings : public UDeveloperSettings
{
    GENERATED_BODY()

public:
    UBookshelfSettings();

    /** The settings object that holds the values loaded from the ini files. */
    static const UBookshelfSettings* Get();

    UPROPERTY(Config, EditAnywhere, Category = "Shelf", meta = (ClampMin = "1", ClampMax = "64"))
    int32 MaxBooksPerShelf = 12;

    UPROPERTY(Config, EditAnywhere, Category = "Shelf")
    float ReturnSlotRadius = 40.0f;

    UPROPERTY(Config, EditAnywhere, Category = "Shelf")
    TArray<FName> ShelfLabels;
};
----

[source,cpp]
----
// Source/Bookshelf/Private/BookshelfSettings.cpp
#include "BookshelfSettings.h"

#include "Bookshelf.h"

UBookshelfSettings::UBookshelfSettings()
{
    CategoryName = TEXT("Game");
}

const UBookshelfSettings* UBookshelfSettings::Get()
{
    return GetDefault<UBookshelfSettings>();
}

// Elsewhere in the module, for example in a game mode or a shelf actor:
//   const int32 Capacity = UBookshelfSettings::Get()->MaxBooksPerShelf;
//
// Reading a raw value without a settings class:
//   int32 Value = 0;
//   GConfig->GetInt(TEXT("/Script/Bookshelf.BookshelfSettings"),
//                   TEXT("MaxBooksPerShelf"), Value, GGameIni);
----

Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/configuration-files-in-unreal-engine[Configuration Files in Unreal Engine]

The manual functions of `GConfig` are `GetBool`, `GetInt`, `GetInt64`, `GetFloat`, `GetDouble`, `GetString`, `GetText` and `GetArray`; the category globals follow the pattern `G<Category>Ini`, such as `GEngineIni` and `GGameIni`. The editor equivalent of this class is the *Bookshelf* entry under *Project Settings > Game*.

== Common mistakes

* *Editing the `.sln` or the files in `Intermediate`.* They are regenerated. Edit `Build.cs`, `Target.cs` and source files, then regenerate.
* *Adding a header or source file by hand and not seeing it in the IDE.* Regenerate the project files.
* *Putting every dependency in `PublicDependencyModuleNames`.* It leaks the dependency to every module that uses yours and slows compiles; use the private list unless a public header needs it.
* *Forgetting `BOOKSHELF_API`* on a class that another module (an editor module, a plugin) uses: the build compiles and then fails to link with unresolved externals.
* *A runtime module that includes editor headers.* `UnrealEd` code in a `Runtime` module compiles in the editor and fails in the packaged game. Keep editor code in a module of type `Editor`.
* *Changing `Build.cs` or `Target.cs` while Live Coding is running.* Close the editor and rebuild from the IDE.
* *Editing `Saved/Config/*.ini` and expecting it to be project-wide.* It is a local override; edit `Config/Default*.ini`.
* *Wrong ini section.* The section is `[/Script/Module.Class]` with no `U` or `A` prefix on the class name; a mistake is silently ignored.
* *Committing `Binaries`, `Intermediate`, `Saved` or `DerivedDataCache`.* They are large, machine-specific and rebuilt.
* *Mismatched `EngineAssociation`.* A project from another minor version opens with a conversion prompt; back it up first.
* *Naming a module like an engine module.* A `Bookshelf` module is safe; a module called `Core` or `Engine` is not.

== Performance notes

* *Private dependencies and small public headers* shorten rebuilds: every module that depends on yours recompiles when a public header changes. Keep headers in `Public` minimal and forward-declare types (as `BookActor.h` forward-declares `UStaticMeshComponent`).
* *Include what you use.* `IncludeOrderVersion` and `bIWYU` make modules include the headers they need rather than relying on shared precompiled headers; a module that follows it compiles faster and breaks less across engine upgrades.
* *Unity builds* (`bUseUnityBuild`) combine source files to compile faster; a compile error that only appears with unity builds usually means a missing include.
* *Distributed compilation* with the Unreal Build Accelerator makes the first build of a large module tolerable; Epic cites 12 to 16 cores as a practical baseline for local compiles without distribution.
* *Many small modules* separate rebuild units and speed incremental builds, but each adds a DLL to load in the editor; split by dependency boundary (runtime, editor, tests), not by habit.
* *Live Coding preloads* the modules you list; more preloaded modules means slower editor start-up, so keep the list to your own modules.
* *Derived Data Cache.* Keep it on an SSD and share it in a team; deleting it forces shaders and derived assets to be rebuilt, which is slow. The 5.8 default cooked output store is Zenserver.
* *Config.* Reading a value through `GConfig` on every tick is slow; read once in `BeginPlay` or the constructor, or cache the settings pointer.

== Where the books are outdated

Two books explain project and {cpp} structure: Zhenyu George Li and E. Wyn Roberts' _Unreal Engine 5 Game Development with {cpp} Scripting_ (chapters 2 and 4; Unreal 5.0 and Visual Studio 2022) and Benjamin Carnall's _Unreal Engine 4.X By Example_ (chapter 4; Unreal 4.10 and 4.11). The structure they describe is still the right shape, but details have moved:

* *Compile loop.* Hot Reload and Visual Studio 2013 or 2015 (also assumed in Nitish Misra's _Learning Unreal Engine Android Game Development_, chapters 1 and 2) are replaced by Live Coding as the default and Visual Studio 2026 (2022 17.14 minimum).
* *Folder layout.* UE4-era projects use `Classes` and `Private` folders; today new modules use `Public` and `Private`, and the engine's own `Classes` folder is legacy.
* *`Build.cs` and `Target.cs`.* Older listings omit `DefaultBuildSettings` and `IncludeOrderVersion`, and use the pre-5.0 DLL names `UE4Editor-<Module>`.
* *The UE 5.0 book.* It predates the 5.8 toolchain, Enhanced Input as the default, Mass, StateTree, MegaLights and Iris, so its project template and plugin list differ from a new 5.8 project.
