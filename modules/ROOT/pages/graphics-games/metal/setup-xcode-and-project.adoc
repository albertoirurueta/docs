= Setup: Xcode and the Project
:description: How to prepare a Metal project in November 2026: Xcode 27 and its Apple-silicon requirement, the separately downloaded Metal Toolchain component, a multiplatform SwiftUI project with an MTKView, .metal files and the build that turns them into a metallib, a bridging header shared by Swift and MSL, build settings, scheme diagnostics, command-line compilation and what the Simulator can and cannot do.
:keywords: Xcode 27, Metal Toolchain, metallib, .metal, AIR, xcrun metal, MTL_LANGUAGE_REVISION, bridging header, ShaderTypes.h, makeDefaultLibrary, Simulator, multiplatform, visionOS target, Metal API validation

include::partial$graphics-games-metal-disclaimer.adoc[]

A Metal program is two programs. The Swift (or Objective-C or {cpp}) code runs on the CPU and sets everything up; the shaders, written
in the Metal Shading Language (MSL), run on the GPU and are compiled by a compiler that ships with Xcode. Getting both to build
from one project, for macOS, iOS, iPadOS and visionOS at once, is what this page does, and it ends with a small check program
that proves the toolchain works before any drawing starts.

The general concepts behind this page are in xref:graphics-games/graphics-apis-vs-game-engines.adoc[Graphics APIs vs Game Engines].

The facts were checked in November 2026. The versions documented are *Xcode 27* (Swift 6.4, the 27 SDKs), *Metal 4* on the 26 OSes
and *MSL 4.1* on the 27 OSes, as described in
xref:graphics-games/metal/whats-new-in-metal-4.adoc[What's New in Metal 4]. Xcode 27 needs an Apple-silicon Mac running macOS 26.6 or
later. The Metal Toolchain is a separate Xcode component that you download once, since Xcode 26. A device that
runs Metal 4 is an A14 or later, an M1 or later, or Apple Vision Pro; older devices still work with the Metal 3 path.

This page prepares the *Metal Bookshelf*, the running example of this section: one multiplatform SwiftUI app that hosts an
`MTKView` (see xref:graphics-games/metal/metalkit-mtkview-and-swiftui.adoc[MetalKit, MTKView and SwiftUI]) with a Metal 4 path and a Metal 3
fallback, plus a visionOS target (xref:graphics-games/metal/metal-on-visionos.adoc[Metal on visionOS]). The general Xcode project
mechanics (targets, schemes, signing) are in xref:apps/apple/xcode-projects-and-previews.adoc[Xcode Projects and Previews] and
xref:apps/apple/multiplatform-projects.adoc[Multiplatform Projects]; this page only covers what is specific to Metal.

== What you need

|===
|Item |Requirement in 2026 |Notes

|Mac

|Xcode
|27 (Swift 6.4, 27 SDKs)
|Older Xcode versions still build Metal 3 projects, but this section uses the 27 SDKs.

|Metal Toolchain

|Without it `.metal` files fail to compile with a message that the toolchain is missing.

|Account
|A free Apple account runs on your own devices

The first Metal by Tutorials chapters (MBT 4th edition) assume macOS 14, Xcode 15 and "every Mac since 2012". Both statements are
out of date: Xcode 27 needs Apple silicon, and managed storage, `MTLGPUFamily.mac2` and `.common3` are deprecated in the 27 OSes.

== Install the Metal Toolchain

Xcode 26 moved the Metal compiler and linker out of the main Xcode download, so a fresh Xcode can show the error that the
Metal Toolchain is not installed. Two equivalent ways fix it: open Xcode, choose Settings, then Components, and download the
Metal Toolchain; or run the download from a terminal.

[source,shell]
----
# Download and install the Metal Toolchain component
xcodebuild -downloadComponent MetalToolchain

# Check that the compiler is found for the macOS SDK
xcrun -sdk macosx metal --version
----

Source: https://developer.apple.com/documentation/xcode/metal-developer-workflows[Xcode documentation: Metal developer workflows]; https://developer.apple.com/documentation/xcode-release-notes/xcode-27-release-notes[Xcode 27 release notes]

On a CI machine the same command makes the component part of the image. Metal compilation is per SDK (`macosx`, `iphoneos`,
`iphonesimulator`, `xros` and so on), so a project that targets several platforms compiles each `.metal` file once per target SDK.

== The six steps

.The Bookshelf project in Xcode, as five panels
image::graphics-games-metal-setup-xcode-and-project-xcode-storyboard.svg["Storyboard of five panels: new multiplatform project, add Metal files and the shared header, bridging header, build settings, run with GPU capture and validation",width=720]

. *Create the project.* In Xcode choose File, New, Project, the Multiplatform tab, App. Pick SwiftUI for the interface and Swift as the language, and name it Bookshelf.
  The template targets iOS, iPadOS and macOS. Add a visionOS destination to the target later when the page on visionOS needs it.
. *Add the shader files.* Add a New File, Metal File (`Shaders.metal`) to the target. Xcode puts it in the Compile Sources phase, so it is compiled for every platform of the target.
. *Share types with a header.* Add `ShaderTypes.h`, a C header included by both languages, and (for Swift) a bridging header that imports it.
. *Set build settings* for the Metal compiler (below).
. *Edit the scheme* to turn on the debugging tools (below).
. *Build and run* on a device or the Mac, and check that the library loads (the program at the end of the page).

Source: https://developer.apple.com/documentation/xcode/configuring-a-multiplatform-app-target[Xcode documentation: Configuring a multiplatform app]

== From .metal to a library

.How Xcode turns shader source into something the app can load
image::graphics-games-metal-setup-xcode-and-project-shader-build.svg["Flow: Shaders.metal and Lighting.metal are compiled by metal -c into AIR files, linked by metallib into default.metallib in the app bundle, then at run time makeDefaultLibrary, makeFunction and a pipeline descriptor produce a pipeline state",width=720]

The shader pipeline has two compile stages, which is why a shader error shows up either at build time or when the app first
makes a pipeline:

. *Front end, at build time.* Each `.metal` file is compiled on its own into *AIR*, Apple's intermediate representation of the
  shader (older material names the files `.air`; Apple's current command-line article names them `.ir`). A syntax error, a missing
  `#include` or a type error appears here, in Xcode's issue list, with the file and line.
. *Library packaging, at build time.* The intermediate files are linked into one `.metallib` named `default.metallib` and placed in the app
  bundle (inside the Resources of the app, or the root of an iOS app).
. *Back end, at run time or earlier.* When you create a pipeline state, Metal's compiler turns AIR into machine code
  for the GPU in that particular device. This is the step that can cause a hitch on the first use. Binary archives and the
  Metal 4 compiler let you move it ahead of time (see
  xref:graphics-games/metal/shader-compilation-and-pipeline-caching.adoc[Shader Compilation and Pipeline Caching]).

The same pipeline can be run by hand. This is useful in CI and when something in Xcode looks wrong.

[source,shell]
----
# 1. Compile each source file to intermediate form (-c = compile only)
xcrun -sdk macosx metal -c Shaders.metal -o Shaders.ir
xcrun -sdk macosx metal -c Lighting.metal -o Lighting.ir

# 2. (Optional) bundle the intermediate files into an archive
xcrun -sdk macosx metal-ar -q Shaders.metalar Shaders.ir Lighting.ir

# 3. Build the library from intermediate files, archives, or both
xcrun -sdk macosx metal -o default.metallib Shaders.metalar
----

Source: https://developer.apple.com/documentation/metal/building-a-shader-library-by-precompiling-source-files[Building a shader library by precompiling source files]

`-sdk` selects the SDK (use `iphoneos` or `xros` for the other platforms), `-o` names the output and `-c` stops after the first
stage. Two details trip people up:

* A library built with the `macosx` SDK does not load on iOS. Xcode handles this by compiling per destination; a hand-made library must be built once per SDK.
* The Windows command-line tools take the same options as the macOS ones, which matters for the game-porting workflow in
  xref:graphics-games/metal/metal-cpp-and-game-porting.adoc[metal-cpp and Game Porting].

== Build settings

The Xcode target's Build Settings page has a Metal Compiler section (search for "Metal"). The settings that matter:

|===
|Setting |What it controls |Recommended

|`MTL_LANGUAGE_REVISION`
|The MSL version the files are compiled as
|The newest one the lowest deployment target allows. If you deploy to the 26 OSes use MSL 4.0, and use 4.1 only where every target is on the 27 OSes. The `.metal` file cannot use features newer than its revision.

|`MTL_ENABLE_DEBUG_INFO`
|Whether the shader debugger can show source lines and variables
|On for Debug, off for Release (or use symbol files).

|`MTL_FAST_MATH`
|Allows the compiler to reorder floating-point operations and ignore NaN and infinity
|On by default. Turn it off only to hunt a precision bug, and prefer the explicit functions in the `metal::precise` namespace for the few places where it matters.

|`MTL_HEADER_SEARCH_PATHS`
|Where `#include` finds shared headers
|Point it at the folder of `ShaderTypes.h` if you move it out of the target's own folder.

|`MTL_COMPILER_FLAGS`
|Extra command-line flags for the compiler
|Empty unless you have a reason.
|===

Source: https://developer.apple.com/documentation/xcode/building-your-project-with-embedded-shader-sources[Xcode documentation: Building your project with embedded shader sources]

== Shared types: one header for Swift and MSL

A vertex struct used by both sides must have the same layout, and the safest way to guarantee that is to write it once. The
header below is read by the Metal compiler and, through the bridging header, by Swift.

[source,c]
----
// ShaderTypes.h
#ifndef ShaderTypes_h
#define ShaderTypes_h

#include <simd/simd.h>

// Buffer indices shared by Swift and MSL
typedef enum {
    BufferIndexVertices = 0,
    BufferIndexUniforms = 1
} BufferIndex;

// One vertex of a book. vector_float3 occupies 16 bytes, so the stride is 32.
typedef struct {
    vector_float3 position;   // object space
    vector_float2 uv;         // texture coordinates
} BookVertex;

// Per-frame values
typedef struct {
    matrix_float4x4 modelViewProjection;
} Uniforms;

#endif
----

[source,swift]
----
// Bookshelf-Bridging-Header.h (set in the target's "Objective-C Bridging Header" build setting)
// #import "ShaderTypes.h"

// Swift can now use the same types
let stride = MemoryLayout<BookVertex>.stride   // 32 bytes
let uniformsSize = MemoryLayout<Uniforms>.stride
----

Source: https://developer.apple.com/documentation/xcode/configuring-a-multiplatform-app-target[Xcode documentation: Configuring a multiplatform app]

Two rules follow from the layout: a `vector_float3` takes the space of four floats, so a tightly packed three-float position
needs `packed_float3` (MSL) or `MTLVertexFormat.float3` described in a vertex descriptor, and the stride of the struct
is what `MemoryLayout.stride` returns, not the sum of the members. The details of vertex layouts are in
xref:graphics-games/metal/buffers-vertex-descriptors.adoc[Buffers and Vertex Descriptors] and the math types in
xref:graphics-games/metal/math-for-3d.adoc[Math for 3D].

== Scheme settings for debugging

Open Product, Scheme, Edit Scheme, then Run, then Diagnostics. The Metal-related options:

* *Metal API Validation* checks every API call against the rules (wrong sizes, missing resources, invalid states) and reports problems in the console. It is on by default for Debug runs from Xcode. It is cheap to leave on while learning and expensive to run in a benchmark.
* *Metal Shader Validation* checks what shaders do on the GPU: out-of-bounds buffer access, invalid texture use and similar bugs. It slows shaders a lot, so turn it on when a result is wrong.
* *GPU Frame Capture* sets whether the camera button in the debug bar appears and whether captures use Metal or the automatic choice.

The tools are described in xref:graphics-games/metal/debugging-and-profiling.adoc[Debugging and Profiling], and the general Xcode debugging
workflow is in xref:apps/apple/debugging-with-xcode-and-lldb.adoc[Debugging with Xcode and LLDB].

Source: https://developer.apple.com/documentation/xcode/validating-your-apps-metal-api-usage[Validating your app's Metal API usage]; https://developer.apple.com/documentation/xcode/validating-your-apps-metal-shader-usage[Validating your app's Metal shader usage]

== A program that proves the setup works

The code below creates the device, loads the default library, lists the functions it contains and prints what the GPU supports. Put
a trivial vertex function in `Shaders.metal` first.

[source,metal]
----
// Shaders.metal
#include <metal_stdlib>
using namespace metal;

struct VertexOut {
    float4 position [[position]];
};

vertex VertexOut hello_vertex(uint vertexID [[vertex_id]]) {
    float2 positions[3] = { float2(-0.5, -0.5), float2(0.5, -0.5), float2(0.0, 0.5) };
    VertexOut out;
    out.position = float4(positions[vertexID], 0.0, 1.0);
    return out;
}

fragment float4 hello_fragment() {
    return float4(0.9, 0.6, 0.2, 1.0);
}
----

[source,swift]
----
import Metal

func checkMetalSetup() {
    guard let device = MTLCreateSystemDefaultDevice() else {
        print("No Metal device: this machine or the Simulator cannot run Metal")
        return
    }
    print("GPU:", device.name)
    print("Unified memory:", device.hasUnifiedMemory)
    print("Apple9 family:", device.supportsFamily(.apple9))
    print("Metal 4 family:", device.supportsFamily(.metal4))

    guard let library = device.makeDefaultLibrary() else {
        print("default.metallib not found: is Shaders.metal in the target's Compile Sources?")
        return
    }
    print("Functions:", library.functionNames.sorted())
    for name in ["hello_vertex", "hello_fragment"] {
        print(name, library.makeFunction(name: name) != nil ? "found" : "missing")
    }
}

checkMetalSetup()
----

Source: https://developer.apple.com/documentation/metal/mtlcreatesystemdefaultdevice()[MTLCreateSystemDefaultDevice]; https://developer.apple.com/documentation/metal/mtldevice/makedefaultlibrary()[makeDefaultLibrary()]

If a library is not in the main bundle (a Swift package, a framework, a library built by a separate script), load it by URL:

[source,swift]
----
let url = Bundle.main.url(forResource: "default", withExtension: "metallib")!
let library = try device.makeLibrary(URL: url)
----

Source: https://developer.apple.com/documentation/metal/building-a-shader-library-by-precompiling-source-files[Building a shader library by precompiling source files]

For a Swift package, use `device.makeDefaultLibrary(bundle: Bundle.module)` so that the package's own compiled shaders are found
instead of the app's.

Common reasons `makeDefaultLibrary()` returns nil: the `.metal` file is in no target, the Metal Toolchain is missing, a
shader error stopped the build, or the code runs in a package or framework whose bundle is not the main bundle. The older book
code (CLA, Swift 4) calls `device.newDefaultLibrary()`, which is renamed `makeDefaultLibrary()`.

== The Simulator

The iOS, tvOS and visionOS Simulators give Metal apps hardware acceleration on the Mac: `MTLCreateSystemDefaultDevice()` returns a device
connected to the Simulator, and Metal calls are translated and sent to the host Mac's GPU. The Simulator does not emulate the GPU of the
simulated device (an A16 for an iPhone 15, say); the device it reports has capabilities similar to an Apple family 2 GPU
(`MTLGPUFamily.apple2`), so ask `supportsFamily` instead of assuming. The limits that matter for this section:

|===
|Area |Limit in the Simulator

|Textures
|No `renderTarget` usage on textures made from private-storage buffers; depth, stencil and multisample textures must use private storage; do not use a sample count of 2; use unified depth/stencil formats only; avoid a few packed and YUV formats; do not render to `rgb9e5Float` or write to sRGB textures.

|Constant buffers
|Keep them at or under 64 KB, align offsets to 256 bytes (devices generally need only 4) and use at most 14 per pipeline.

|Heaps
|Private storage only.

|Programmable blending
|Not available: fragment shaders cannot read the colour attachments, so tile-based techniques need extra passes (see xref:graphics-games/metal/deferred-and-tile-shading.adoc[Deferred and Tile Shading]).

|Tools
|Xcode cannot analyse memory footprint or measure performance in the Simulator.
|===

Apple's advice is to use the Simulator to prototype workflow and behaviour, not pixel-exact output, and to develop and profile the Apple-GPU
code paths on a device. For the Bookshelf, that means the unit tests and the layout work run on the Simulator, and every page that
measures time or uses tile memory is checked on hardware. Hardware ray tracing and the neural parts of MetalFX also need a real device with
the right chip.

Source: https://developer.apple.com/documentation/metal/developing-metal-apps-that-run-in-simulator[Developing Metal apps that run in Simulator]

== Common mistakes

* Building the project and seeing a black view because the `.metal` file is in the wrong target.
* Using a deployment target below the language revision (Xcode warns; the shader is rejected on older systems).
* Compiling shaders only in Release: errors then appear late.
* Debugging Release with fast math and optimisations without debug info, then wondering why variables are optimised out.
* Putting the shader's structs in two places and letting them drift apart. Use the shared header.
