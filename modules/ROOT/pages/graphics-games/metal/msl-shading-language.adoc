The Metal Shading Language is the language of every function that runs on an Apple GPU: vertex, fragment, kernel, mesh, object, intersection and
tile functions are all written in it. It is {cpp}17 with the parts a GPU cannot support removed (exceptions, virtual functions, most of the
standard library, new and delete before 4.1) and the parts a GPU needs added (vector and matrix types, address spaces, attributes that
bind a variable to a resource or to a hardware input, and a standard library of math, texture and synchronisation functions). Because the
language is close to {cpp}, most of the learning is in four places: the *address spaces*, the *attributes*, how data is *laid out in memory* so that Swift and
the shader agree, and *function constants* that let one function compile into many specialised pipelines. This page covers those four, plus the compiler options that change
how arithmetic behaves.

The facts were checked in November 2026. The version documented is MSL 4.1 (specification dated 4 June 2026, `-std=metal4.1`, `MTLLanguageVersion.version4_1`
on the 27 operating systems) and MSL 4.0 (`-std=metal4.0`, `MTLLanguageVersion.version4_0`, the 26 operating systems). Metal 4 and later is
based on {cpp}17; earlier language versions are based on {cpp}14. Shaders compile with Xcode 26 or later (the Metal Toolchain is a separate Xcode component, see
xref:graphics-games/metal/setup-xcode-and-project.adoc[Setting Up Xcode and a Metal Project]); targeting the 27 systems with MSL 4.1 needs Xcode 27 on an Apple-silicon Mac. Everything on this page
runs on iOS, iPadOS, macOS, tvOS and visionOS; the Metal 4 API types referenced here need an A14 or M1 and later.

In the Bookshelf running example this page defines the shared header that every later shader includes, extends the book's fragment function with function constants (an optional wear mask and a
variable number of lamps), and explains why the structs are declared once and shared. The pipeline that consumes the shaders is described in
xref:graphics-games/metal/render-pipeline.adoc[The Metal Render Pipeline]; how other languages compare is in xref:graphics-games/shading-languages-landscape.adoc[Shading Languages Landscape], and
the OpenGL equivalent is xref:graphics-games/opengl/glsl-language.adoc[The GLSL Language].

Xcode selects the version with the *Metal Language Revision* build setting; at run time the version of an online-compiled library comes from `MTLCompileOptions.languageVersion`. The same options
object exposes `mathMode`, `mathFloatingPointFunctions`, `fastMathEnabled`, `preprocessorMacros`, `enableLogging`, `preserveInvariance`,
`optimizationLevel`, `libraryType` and `maxTotalThreadsPerThreadgroup`. Useful predefined macros are `+__METAL_VERSION__+` (the language revision as an integer) and `+__METAL_MACOS__+`, `+__METAL_IOS__+` and
`+__METAL__+`, so a shader can adapt to the language level or platform it is compiled for. The offline compiler additionally accepts `-D` and `-I` for macros and header search paths.

What is not available, so you do not look for it: no standard {cpp} library (use the Metal standard library instead), no exceptions, no `dynamic_cast` or RTTI, no `goto`, no `thread_local`, no virtual functions or
derived classes, and `new` and `delete` only as placement `new` from 4.1. Function pointers exist from MSL 2.3, recursion only in compute functions from MSL 2.4, and lambdas from MSL 3.2.

== Types

=== Scalars, vectors and matrices

Scalars are `bool`, `char`, `short`, `int`, `long` (and unsigned forms), `half` (16-bit float), `bfloat` (16-bit brain float) and `float`. Vectors are `float2`, `float3`, `float4` and so on for
every scalar type. Components are accessed with `.xyzw` or `.rgba` and may be swizzled (`v.zyx`, `c.rrr`). Matrices are written *columns by rows*: `float4x4` has four columns of
four rows; `float3x2` has three columns of two rows. They are *column-major*: `m[1]` is the second *column*, and `+m * v+` multiplies a column vector. This matches the `simd` types in Swift (see
xref:graphics-games/metal/math-for-3d.adoc[Math for 3D with simd]).

The `+packed_+` types (`packed_float3`, `packed_half4`, `packed_uchar4`, ...) are storage formats for arrays of vertices and similar data: they have the alignment of their scalar, so a buffer of 12-byte positions is a

=== Textures, samplers and other resources

`texture2d<float, access::sample> tex` (the access defaults to `sample`), `texturecube<float>`, `texture2d_array<float>`, `depth2d<float>` and `texture3d<float>` are types you receive as arguments; the template
argument is the type that sampling returns, not the storage format. A `sampler` is either an argument bound at `+[[sampler(n)]]+` or a `constexpr sampler` declared in the shader, which needs no binding:

[source,metal]
----
constexpr sampler bookSampler(coord::normalized, address::clamp_to_edge,
                              filter::linear, mip_filter::linear);
float4 color = cover.sample(bookSampler, in.uv);
----

Source: https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf[Metal Shading Language Specification]

Other resource-like types: `atomic_int` and `atomic_uint` (and wider ones), `array<T, N>`, `+device T *+` pointers, `constant` references, `ray`, `intersector`, `acceleration_structure`, `+mesh<...>+`,
`visible_function_table` and, in Metal 4, `+tensor<...>+`. Textures and samplers are covered in xref:graphics-games/metal/textures-and-samplers.adoc[Textures and Samplers].

== Address spaces

.The address spaces and the memory they describe
image::graphics-games-metal-msl-shading-language-address-spaces.svg["Nested boxes: the GPU with device and constant memory, a threadgroup containing threadgroup memory and imageblock memory, and four threads with private memory; below, the specialised ray_data and object_data spaces and the rules",width=720]

An address space says which memory a pointer or reference points into and what you may do with it. Every pointer or reference declared as a parameter of a graphics or kernel function must name one, and a
declaration without one is a compile error.

|===
|Address space |Access |Lifetime and visibility |Typical use

|`device`
|read and write
|Buffer memory from the device's memory pool; visible to all threads
|Vertex arrays, output buffers, particle state, any large or writable data. Textures live here implicitly and need no qualifier.

|`constant`
|read only
|Buffer memory read uniformly by all threads, or program-scope constants initialised in the declaration (they must be core constant expressions)
|Uniforms and small tables. Buffers in this space have a minimum offset alignment per GPU (Feature Set Tables). Writing to it is a compile error.

|`thread`
|read and write
|Per-thread; the default for variables declared inside a function
|Local variables, arrays, and pointers to them.

|`threadgroup`
|read and write
|Shared by the threads of one threadgroup; exists for the threadgroup's lifetime (and across mid-render and fragment tile kernels over a tile)
|Compute reductions, tiles of data, mesh and object functions. Declared in the kernel body, or as a pointer argument sized from the API with `setThreadgroupMemoryLength`.

|`threadgroup_imageblock`
|read and write
|Tile (imageblock) memory of a render pass
|Tile shaders and programmable blending, see xref:graphics-games/metal/deferred-and-tile-shading.adoc[Deferred and Tile Shading].

|`ray_data`
|read and write
|Payload shared across ray tracing functions
|Intersection functions.

|`object_data`
|read and write
|Payload from an object function to its mesh function
|Mesh shading.
|===

For *graphics* functions a pointer or reference argument must be in `device` or `constant`. For *kernel* functions `device`, `threadgroup`, `threadgroup_imageblock` and `constant` are allowed. Marking
read-only buffers `constant` (or `device const`) lets the compiler and hardware use faster paths.

.Choosing the address space of a buffer parameter
[mermaid]
....
flowchart TD
    A{"Does the shader write to the buffer?"} -- yes --> B["device"]
    A -- no --> C{"Is the data small and read the same by all threads?"}
    C -- yes --> D["constant"]
    C -- no --> E["device const"]
    B --> F{"Is it shared only inside one threadgroup?"}
    F -- yes --> G["threadgroup, declared in the kernel or sized by the API"]
    F -- no --> H["stay with device"]
....

A kernel that touches every space in one place, a threadgroup sum reduction:

[source,metal]
----
#include <metal_stdlib>
using namespace metal;

kernel void sumReduce(device const float *input        [[buffer(0)]],   // read-only device data
                      device float *partialSums        [[buffer(1)]],   // writable device data
                      constant uint &count             [[buffer(2)]],   // uniform value
                      threadgroup float *scratch       [[threadgroup(0)]],
                      uint globalIndex                 [[thread_position_in_grid]],
                      uint localIndex                  [[thread_position_in_threadgroup]],
                      uint groupSize                   [[threads_per_threadgroup]],
                      uint groupIndex                  [[threadgroup_position_in_grid]])
{
    float value = globalIndex < count ? input[globalIndex] : 0.0f;   // a thread-space local
    scratch[localIndex] = value;
    threadgroup_barrier(mem_flags::mem_threadgroup);

    for (uint stride = groupSize / 2; stride > 0; stride >>= 1) {
        if (localIndex < stride) {
            scratch[localIndex] += scratch[localIndex + stride];
        }
        threadgroup_barrier(mem_flags::mem_threadgroup);
    }
    if (localIndex == 0) {
        partialSums[groupIndex] = scratch[0];
    }
}
----

Source: https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf[Metal Shading Language Specification, section 4: Address Spaces]

On the Swift side the `threadgroup` argument gets its size from `+encoder.setThreadgroupMemoryLength(threadsPerGroup * MemoryLayout<Float>.stride, index: 0)+`. The threadgroup size, dispatch rules and the
SIMD-group functions that replace most of this loop are in xref:graphics-games/metal/compute-kernels.adoc[Compute Kernels].

== Attributes: binding a variable to the outside world

Attributes are written in double square brackets after a declaration. They are how the shader says "this parameter is buffer 1", "this field is the clip-space position", or "this value is the thread's
index in the grid".

== Sharing structs with Swift

Every buffer the CPU fills and the GPU reads has a layout. Declaring that layout twice, once in Swift and once in MSL, is the most common source of garbage on screen. The robust approach is to declare it
*once*, in a C header that both compile.

.One header seen by the Swift compiler and by the Metal compiler
image::graphics-games-metal-msl-shading-language-shared-header.svg["Diagram: a shared ShaderTypes.h feeds a bridging header for Swift and an include for the Metal shader, producing the same struct layout on both sides, with a layout assertion",width=720]

[source,c]
----
// ShaderTypes.h: included by Swift (via the bridging header) and by MSL
#ifndef ShaderTypes_h
#define ShaderTypes_h

#ifdef __METAL_VERSION__
#define NS_ENUM(_type, _name) enum _name : _type _name; enum _name : _type
#define NSInteger metal::int32_t
#else
#import <Foundation/Foundation.h>
#endif

#include <simd/simd.h>

#if defined(__METAL_VERSION__) || defined(__cplusplus)
#define SHARED_ASSERT(cond, msg) static_assert(cond, msg)
#else
#define SHARED_ASSERT(cond, msg) _Static_assert(cond, msg)
#endif

typedef NS_ENUM(NSInteger, BookBufferIndex) {
    BookBufferIndexMeshVertices = 0,
    BookBufferIndexUniforms     = 1
};

typedef NS_ENUM(NSInteger, VertexAttribute) {
    VertexAttributePosition = 0,
    VertexAttributeNormal   = 1,
    VertexAttributeTexCoord = 2
};

typedef NS_ENUM(NSInteger, BookFunctionConstant) {
    BookFunctionConstantHasWear   = 0,
    BookFunctionConstantLampCount = 1
};

typedef struct {
    matrix_float4x4 viewProjection;   // offset 0,   64 bytes
    matrix_float4x4 model;            // offset 64,  64 bytes
    vector_float3   lightDirection;   // offset 128, 16 bytes (a float3 occupies a full slot)
} BookUniforms;

SHARED_ASSERT(sizeof(BookUniforms) == 144, "BookUniforms layout changed: update both sides");

#endif /* ShaderTypes_h */
----

Source: https://developer.apple.com/documentation/metal/drawing-a-triangle-with-metal-4[Apple: Drawing a triangle with Metal 4] (its `ShaderTypes.h` uses the same macro pattern)

.Adding the shared header to a project
image::graphics-games-metal-msl-shading-language-header-storyboard.svg["Storyboard of four steps: create ShaderTypes.h in every target, create a bridging header that imports it and set the Objective-C Bridging Header build setting, include it in the .metal file, and use the generated Swift types",width=720]

. *Create `ShaderTypes.h`.* In Xcode, File, New, File, choose Header File. In the File Inspector tick every app target (iOS, macOS and visionOS share one source).
. *Create the bridging header* (for example `Bookshelf-Bridging-Header.h`) containing `#import "ShaderTypes.h"`, and set the *Objective-C Bridging Header* build setting of each Swift target to its path. A Swift
  package target cannot use a bridging header: put the header in a C target (`include/ShaderTypes.h` plus a module map the package generates) and `import` that module from Swift.
. *Include the header in the `.metal` file* with `#include "ShaderTypes.h"` after `<metal_stdlib>`. A header in the same directory is found automatically; for others add a Metal header search path (the offline compiler's `-I`).
. *Use the types from Swift.* C structs import with memberwise initialisers, `matrix_float4x4` becomes `simd_float4x4`, `vector_float3` becomes `SIMD3<Float>`, and an `NS_ENUM` becomes a Swift enum with the common prefix
  removed, so `BookBufferIndexUniforms` is `BookBufferIndex.uniforms` and its `rawValue` is the `Int` you pass as a binding index.

Rules that keep the two sides identical:

* Use `simd` types in shared structs (`vector_float4`, `matrix_float4x4`, `vector_uint2`), which have the same size and alignment in C, in Swift and in MSL.
* Never put `NSInteger` or `int` of unknown width in a struct: the macro above makes `NSInteger` 32 bits in MSL but 64 in Swift. Use `int32_t`, `uint32_t` and `float` in shared structs; keep `NSInteger` for enum backing only.
* `vector_float3` takes 16 bytes. If you need the 12-byte form, declare `packed_float3` in MSL and three separate floats on the C side.
* Keep a `SHARED_ASSERT` of `sizeof` for each struct that crosses the boundary. The check runs in the Metal compiler and the C compiler, so a change to one side breaks the build.
* Resource handles such as textures are never in these structs; they go in argument buffers (see xref:graphics-games/metal/argument-buffers-and-bindless.adoc[Argument Buffers and Bindless Resources]).

== Function constants

A function constant is a value that is fixed when a *pipeline* is created, not when the shader is compiled to the library and not when it runs. The shader is compiled once to an intermediate form; when you
make the pipeline you supply the constant values, and the back-end compiler removes unused branches, can unroll loops whose bound is the constant, and drops unused parameters. The cost of a variant is
paid at load time instead of per pixel.

.One shader source specialised into pipeline variants when pipelines are created
image::graphics-games-metal-msl-shading-language-function-constants.svg["A shader with two function constants is compiled once; at pipeline creation constant values select four variants with and without the wear mask, with unused branches removed",width=720]

[source,metal]
----
// Shaders.metal: the textured book fragment function with two function constants
#include <metal_stdlib>
#include "ShaderTypes.h"
using namespace metal;

constant bool hasWear  [[function_constant(BookFunctionConstantHasWear)]];
constant uint lampCount [[function_constant(BookFunctionConstantLampCount)]];

struct BookVertexOut {
    float4 position [[position]];
    float3 worldNormal;
    float2 uv;
};

fragment float4 bookFragment(BookVertexOut in [[stage_in]],
                             constant BookUniforms &uniforms [[buffer(BookBufferIndexUniforms)]],
                             texture2d<float> cover [[texture(0)]],
                             texture2d<float> wear  [[texture(1), function_constant(hasWear)]])
{
    constexpr sampler s(coord::normalized, address::clamp_to_edge, filter::linear, mip_filter::linear);
    float3 albedo = cover.sample(s, in.uv).rgb;
    if (hasWear) {                                   // removed from the binary when hasWear is false
        albedo *= 1.0 - 0.5 * wear.sample(s, in.uv).r;
    }

    float3 n = normalize(in.worldNormal);
    float lighting = 0.2;
    for (uint i = 0; i < lampCount; ++i) {           // a constant trip count: the compiler unrolls it
        float3 toLamp = normalize(float3(0.3 * float(i + 1), 1.0, 0.4));
        lighting += saturate(dot(n, toLamp)) / float(lampCount);
    }
    return float4(albedo * lighting, 1.0);
}
----

Source: https://developer.apple.com/documentation/metal/using-function-specialization-to-build-pipeline-variants[Apple: Using function specialization to build pipeline variants]

On the Swift side the values go in an `MTLFunctionConstantValues`. Metal 3 asks the library for the specialised function; Metal 4 wraps the function descriptor and the values in a specialised function descriptor
so the compiler can do it as part of the pipeline build.

[source,swift]
----
import Metal

struct BookVariant: Hashable {
    var hasWear: Bool
    var lampCount: UInt32
}

func makeConstantValues(for variant: BookVariant) -> MTLFunctionConstantValues {
    let values = MTLFunctionConstantValues()
    var hasWear = variant.hasWear
    var lampCount = variant.lampCount
    values.setConstantValue(&hasWear, type: .bool, index: BookFunctionConstant.hasWear.rawValue)
    values.setConstantValue(&lampCount, type: .uint, index: BookFunctionConstant.lampCount.rawValue)
    return values
}

// Metal 3: the specialised MTLFunction goes straight into the pipeline descriptor.
func fragmentFunctionMetal3(library: MTLLibrary, variant: BookVariant) throws -> MTLFunction {
    try library.makeFunction(name: "bookFragment", constantValues: makeConstantValues(for: variant))
}

// Metal 4: a specialised function descriptor wraps the library function descriptor.
@available(iOS 26.0, macOS 26.0, tvOS 26.0, visionOS 26.0, *)
func fragmentDescriptorMetal4(library: MTLLibrary, variant: BookVariant) -> MTL4SpecializedFunctionDescriptor {
    let base = MTL4LibraryFunctionDescriptor()
    base.library = library
    base.name = "bookFragment"
    let specialized = MTL4SpecializedFunctionDescriptor()
    specialized.functionDescriptor = base
    specialized.constantValues = makeConstantValues(for: variant)
    return specialized     // assign to MTL4RenderPipelineDescriptor.fragmentFunctionDescriptor
}

/// A cache so each variant is compiled once.
@MainActor
final class BookPipelineCache {
    private var pipelines: [BookVariant: MTLRenderPipelineState] = [:]
    func pipeline(for variant: BookVariant, make: (BookVariant) throws -> MTLRenderPipelineState) rethrows -> MTLRenderPipelineState {
        if let existing = pipelines[variant] { return existing }
        let created = try make(variant)
        pipelines[variant] = created
        return created
    }
}
----

Source: https://developer.apple.com/documentation/metal/mtlfunctionconstantvalues[Apple: MTLFunctionConstantValues]

Details that matter:

* *Types and indices.* A function constant is a scalar or vector (a struct or an array is a compile error), and its index is between 0 and 65535. The `MTLDataType` passed to `setConstantValue` must match the
  declared type; a mismatch fails when the function is created.
* *What they can control.* Code paths that get compiled, optional arguments of graphics, kernel and helper functions, and optional members of a `+[[stage_in]]+` struct.
* *Index or name.* Constants are numbered with `+[[function_constant(n)]]+`. `+setConstantValue(_:type:index:)+` uses the number; `+setConstantValue(_:type:withName:)+` uses the variable's name. Numbers in a shared header keep both sides in sync.
* *Defined or not.* `is_function_constant_defined(name)` tells the shader whether the API supplied a value, which lets one source serve both "feature present" and "feature unknown" callers.
  The simplest rule is to define every constant the function uses.
* *Conditional parameters.* Adding `function_constant(name)` inside a parameter's attribute list removes that parameter from the signature when the constant is false or undefined, so the pipeline needs no binding for it.
* *Replace preprocessor variants.* The traditional alternative is `-D` macros, which means one library per variant or runtime source compilation. Function constants keep one library and specialise lazily.
* *Count.* Variants multiply: ten boolean constants allow 1,024 combinations. Create only the pipelines you use, cache them by key, and consider pre-compiling the likely ones with binary archives.
* *Relation to other mechanisms.* Branching on a *uniform* costs a branch for every thread each draw; function constants cost nothing at run time but need a pipeline per variant; `+[[visible]]+` and `+[[stitchable]]+` functions let you link pieces at run time instead.

== Math, precision and logging

* *Fast math by default.* The compiler's default `-fmetal-math-mode` is `fast` and `-fmetal-math-fp32-functions` is `fast`: the compiler may assume no NaNs or infinities, no signed zeros, allow reassociation and use
  fused multiply-add. A division by a value that can be zero is then undefined behaviour. `relaxed` keeps infinities and NaNs but still optimises aggressively, and `safe` disables unsafe transformations. In an
  `MTLCompileOptions` set `mathMode` and `mathFloatingPointFunctions`; the legacy `-ffast-math` and `-fno-fast-math` map to these settings. `#pragma METAL fp math_mode(safe)` scopes it to a block.
* *half versus float.* `half` halves register and bandwidth cost and is enough for colours; use `float` for positions, matrix products and accumulation. Mixed arithmetic promotes to `float`, and a stray `float` literal
  (`1.0`) in a `half` expression promotes the whole expression, so write `1.0h` where it matters.
* *Rounding.* From MSL 4.1 the default rounding mode of float-to-float conversions can be set to round toward zero.
* *Logging.* On Apple silicon, MSL 3.2 and later can log from a shader with `<metal_logging>` and an `os_log` object; compile with logging enabled (`-fmetal-enable-logging`, or `MTLCompileOptions.enableLogging`) and attach an
  `MTLLogState` to the command buffer (Metal 4: `MTL4CommandBufferOptions.logState`). See xref:graphics-games/metal/debugging-and-profiling.adoc[Debugging and Profiling Metal].

== Compiling shaders

Xcode compiles every `.metal` file of the target to AIR (Apple's intermediate representation) and links them into `default.metallib` in the app bundle; `device.makeDefaultLibrary()` loads it. The same steps on the
command line are `xcrun metal -c Shaders.metal -o Shaders.air` followed by `xcrun metallib Shaders.air -o default.metallib`, with `-std=metal4.0` (or `4.1`) selecting the language. Compiling source at run time
(`device.makeLibrary(source:options:)`) is useful for tools and experiments but is slower than a pre-built library and should not be on a shipping app's critical path. The build setup, including the Metal Toolchain
component, is in xref:graphics-games/metal/setup-xcode-and-project.adoc[Setting Up Xcode and a Metal Project], and pipeline caching is in
xref:graphics-games/metal/shader-compilation-and-pipeline-caching.adoc[Shader Compilation and Pipeline Caching].

Source: https://developer.apple.com/documentation/metal/shader-libraries[Apple: Shader libraries]

== Common mistakes

|===
|Symptom |Cause |Fix

|"missing address space qualifier" compile error
|A pointer or reference parameter has no `device`, `constant` or `threadgroup`
|Add the right address space; for read-only buffers prefer `constant` or `device const`.

|Colours or positions garbled, normals wrong
|`float3` in a struct read from tightly packed floats, or padding mismatch with Swift
|Share the struct through the header; use `packed_float3` for packed arrays; add `SHARED_ASSERT`.

|A uniform struct seems offset by a few bytes
|`NSInteger` or `int` widths differ, or a Swift `Float` array stands in for a struct
|Use `int32_t` or `uint32_t` in shared structs; declare the struct once.

|Rotation or projection looks transposed
|Matrix built row-major, or `+v * m+` instead of `+m * v+`
|MSL matrices are column-major; with simd matrices on the Swift side write `+m * v+`.

|NaN or infinity propagates into the image although the code guards for it
|Fast math assumes no NaNs or infinities, so the guard can be removed
|Set `mathMode` to `relaxed` or `safe` for the function or file, or restructure.

|Function constant error when the pipeline is created
|Wrong `MTLDataType`, an undefined constant used outside `is_function_constant_defined`, or a bad index
|Match types, define every used constant and keep indices in the shared header.

|Integer varying is garbage between stages
|Integer outputs are interpolated unless marked
|Mark integer members with `+[[flat]]+`.

|Shader works in Debug but not in Release
|Uninitialised `thread` variables, or races on `threadgroup` memory without barriers
|Initialise locals; add `threadgroup_barrier` between writes and reads; validate with Shader Validation.
|===

== Performance notes

* Use the smallest type that is accurate enough; `half` arithmetic is cheaper on every Apple GPU.
* Use `constant` for small, uniformly read data and `device const` for large read-only arrays; both beat writable `device` for the optimiser.
* Prefer function constants over runtime branches for per-draw decisions, and `select`, `mix`, `step` and `saturate` over data-dependent `if` for per-pixel ones.
* Keep per-thread state small: many live variables reduce the number of threads the GPU can keep in flight, which lowers latency hiding.
* Move invariant work out of the fragment function into the vertex function or the CPU.
* Barriers and atomics are expensive; prefer SIMD-group functions inside a SIMD group.
