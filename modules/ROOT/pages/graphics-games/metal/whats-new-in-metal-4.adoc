= What's New in Metal 4
:description: What Metal 4 changed and what came after it: the MTL4 core API (command queue, reusable command buffers, command allocators, argument tables, the compiler, unified compute encoder and the machine-learning encoder), MSL 4.0 and 4.1 language versions, the hardware that runs it, the WWDC26 additions, the deprecations of the 27 OSes and a step-by-step plan to adopt Metal 4 next to Metal 3 in the Bookshelf app.
:keywords: Metal 4, MTL4CommandQueue, MTL4CommandBuffer, MTL4CommandAllocator, MTL4ArgumentTable, MTL4Compiler, MTLTensor, MSL 4.1, supportsFamily, MTLGPUFamily.metal4, Xcode 27, MetalFX, incremental adoption

include::partial$ai-disclaimer.adoc[]

Metal is Apple's low-level graphics and compute API. Since 2014 it has grown in steps, and the biggest step since the first
release is *Metal 4*, announced at WWDC25 and shipped with the 26 operating systems. It keeps what made Metal pleasant
(one device, a few object types, a shading language that is {cpp}) and rebuilds the part that costs CPU time every frame:
how commands are recorded, how resources are made visible to the GPU, how shaders are compiled and how machine-learning
networks run next to graphics. This page is the map of what is new. The pages that follow use the new API in detail, and the
old one only where it is still the better answer.

The general concepts behind this page are in xref:graphics-games/history-of-real-time-graphics.adoc[History of Real-Time Graphics].

The facts were checked in November 2026. The versions documented are *Metal 4* (available from iOS, iPadOS, macOS, tvOS and
visionOS 26.0), *MSL 4.1* (the Metal Shading Language version available from the 27 OSes, `MTLLanguageVersion.version4_1`; 4.0
is available from the 26 OSes) and *Xcode 27* with the 27 SDKs. Metal 4 needs an A14 Bionic or later (iPhone, iPad, Apple TV), a Mac
with Apple silicon (M1 or later) or Apple Vision Pro. Xcode 27 itself needs an Apple-silicon Mac running macOS 26.6 or later,
which is why this section assumes one. Setting the toolchain up is the subject of
xref:graphics-games/metal/setup-xcode-and-project.adoc[Setup: Xcode and the Project].

In the running example, the *Metal Bookshelf*, this page is the starting point: the app is a multiplatform SwiftUI application
that hosts an `MTKView`, takes the Metal 4 path when the device supports it and falls back to Metal 3 otherwise, and has a
visionOS target. Every later page says which of the two paths it shows. The two paths are described below so that the choice is clear before
the first triangle (xref:graphics-games/metal/hello-triangle-metal4.adoc[Hello Triangle with Metal 4]).

== Why a new core API

The Metal 3 recording model was designed for the first iPhones. Every frame the app asks the queue for a new
`MTLCommandBuffer`, records one or more encoders, binds buffers and textures to each encoder one call at a time, and commits. Metal
tracked resource hazards and residency for you. That is convenient and it costs CPU: the per-call binding, the allocation of a fresh command
buffer and the automatic tracking all happen on the thread that is trying to feed the GPU. As scenes grew to hundreds of thousands
of draws, and as games moved to GPU-driven rendering (see
xref:graphics-games/metal/gpu-driven-rendering-icb.adoc[GPU-Driven Rendering and Indirect Command Buffers]), the CPU side became the bottleneck.

Metal 4 keeps the same device and the same resources, and changes six things.

. *Reusable command buffers and explicit allocators.* A `MTL4CommandBuffer` is created once from the device, not from a queue. Each
  frame you call `beginCommandBuffer(allocator:)` with an `MTL4CommandAllocator` and later `endCommandBuffer()`. The allocator provides
  the memory the commands are recorded into, and you call its `reset()` when the GPU has finished with that frame, which marks its memory
  for reuse. A command buffer does not hold strong references to resources.
. *Argument tables.* Metal 4 encoders have no methods that bind a single buffer, texture or heap. You fill an `MTL4ArgumentTable`
  (with `setAddress`, `setResource` and `setSamplerState`) and assign it to the stages of an encoder. A table is created from an
  `MTL4ArgumentTableDescriptor`, whose `maxBufferBindCount` and `maxTextureBindCount` fix its capacity.
. *Explicit residency.* Resources are treated as untracked. You add `MTLResidencySet` objects to the queue or the command buffer,
  and the drawable's layer has one of its own, so the GPU may touch exactly what you declared.
. *Explicit synchronisation.* Because nothing is tracked, you place barriers between passes yourself, for example from the dispatch stage of a compute pass
  to the fragment stage of a render pass that reads its output. Events (`MTLEvent`, `MTLSharedEvent`) still synchronise queues, the CPU
  and other devices. The details are in
  xref:graphics-games/metal/synchronization-and-barriers.adoc[Synchronization and Barriers].
. *A separate compiler object.* `MTL4Compiler` compiles libraries and pipeline states with explicit control of when and on which
  thread; see xref:graphics-games/metal/shader-compilation-and-pipeline-caching.adoc[Shader Compilation and Pipeline Caching].
. *Machine learning in the frame.* `MTLTensor` is a multidimensional resource, and `MTL4MachineLearningCommandEncoder` encodes the
  inference of a Core ML model into a command buffer on the GPU timeline. Inside shaders, tensor operations from the Metal
  Performance Primitives can be called inline. See
  xref:graphics-games/metal/machine-learning-in-metal-4.adoc[Machine Learning in Metal 4].

== The type map

.Metal 3 types and their Metal 4 counterparts
image::graphics-games-metal-whats-new-in-metal-4-type-map.svg["Two columns of types: Metal 3 command queue, command buffer, encoders and per-encoder binding on the left, with their MTL4 counterparts on the right",width=720]

The table repeats the figure with the member names that change, so it can be used as a lookup while porting.

|===
|Metal 3 |Metal 4 |What is different

|`MTLCommandQueue`
|`MTL4CommandQueue`
|Created with `device.makeMTL4CommandQueue()`. Work starts when you commit command buffers (`+commit(_:count:)+` takes an array). It also waits for and signals drawables (`+waitForDrawable(_:)+`, `+signalDrawable(_:)+`) and can signal events.

|`MTLCommandBuffer`
|`MTL4CommandBuffer`
|Created with `device.makeCommandBuffer()` and reused. Recording is bracketed by `beginCommandBuffer(allocator:)` and `endCommandBuffer()`.

|(memory managed by Metal)
|`MTL4CommandAllocator`
|Created with `device.makeCommandAllocator()`. Keep one per frame in flight and `reset()` it only after the GPU finished that frame.

|`MTLRenderCommandEncoder`
|`MTL4RenderCommandEncoder`
|No per-resource binding calls and no residency methods. Uses an argument table. Tessellation configuration is gone, and mesh shaders take its place. `MTLStoreActionOptions` is deprecated and does not apply to Apple silicon GPUs.

|`MTLComputeCommandEncoder`, `MTLBlitCommandEncoder`, `MTLAccelerationStructureCommandEncoder`
|`MTL4ComputeCommandEncoder`
|One encoder does dispatches, copies and acceleration-structure builds, so passes that mix them need fewer encoders and barriers.

|`setBuffer`, `setTexture`, `setSamplerState` on each encoder
|`MTL4ArgumentTable`
|Bind addresses with `+setAddress(_:index:)+`, resource IDs with `+setResource(_:bufferIndex:)+` and samplers with `+setSamplerState(_:index:)+`. Textures and samplers are referred to by `MTLResourceID`; `MTLTextureViewPool` makes lightweight texture views.

|`MTLDevice` library and pipeline calls
|`MTL4Compiler`
|Compilation is its own object, with its own queue of work.

|(none)
|`MTL4MachineLearningCommandEncoder`
|Runs a Core ML network on the GPU timeline, with `MTLTensor` as the data type.
|===

Source: https://developer.apple.com/documentation/metal/understanding-the-metal-4-core-api[Understanding the Metal 4 core API]

== The frame loop, old and new

.One frame in Metal 3 and in Metal 4
image::graphics-games-metal-whats-new-in-metal-4-frame-loop.svg["Two columns listing the steps of a frame: Metal 3 makes a command buffer from the queue every frame, Metal 4 resets an allocator, begins a reusable command buffer and commits through the queue",width=720]

The shape of the Metal 4 loop is the one used by Apple's triangle sample: there are a few frames in flight (the sample uses three), each with
its own allocator, and a shared event or semaphore tells the CPU when the GPU is done with a frame so its allocator can be reset.

[source,swift]
----
import Metal

let framesInFlight = 3

final class FrameResources {
    let device: MTLDevice
    let queue: MTL4CommandQueue
    let commandBuffer: MTL4CommandBuffer
    let allocators: [MTL4CommandAllocator]
    var frameNumber = 0

    init?(device: MTLDevice) {
        guard let queue = device.makeMTL4CommandQueue(),
              let commandBuffer = device.makeCommandBuffer() else { return nil }
        var made: [MTL4CommandAllocator] = []
        for _ in 0..<framesInFlight {
            guard let allocator = device.makeCommandAllocator() else { return nil }
            made.append(allocator)
        }
        self.device = device
        self.queue = queue
        self.commandBuffer = commandBuffer
        self.allocators = made
    }

    /// Call after the GPU has finished the frame that last used this slot.
    func beginFrame() -> MTL4CommandBuffer {
        let allocator = allocators[frameNumber % framesInFlight]
        allocator.reset()                                      // memory is reused
        commandBuffer.beginCommandBuffer(allocator: allocator)
        return commandBuffer
    }

    func endFrame() {
        commandBuffer.endCommandBuffer()
        // Commit with the queue's commit(_:count:), then signal an event so beginFrame()
        // knows when this allocator may be reset again.
        frameNumber += 1
    }
}
----

Source: https://developer.apple.com/documentation/metal/drawing-a-triangle-with-metal-4[Drawing a triangle with Metal 4]

Notes on the code:

* `makeMTL4CommandQueue()` is a factory method on `MTLDevice` (`newMTL4CommandQueue` in Objective-C). `makeCommandBuffer()` and
  `makeCommandAllocator()` are also methods of the device, which is why a Metal 4 command buffer is not tied to a queue when created.
* The allocator and the command buffer are cheap to keep. The cost that this design removes is the allocation of a new
  command buffer and its memory every frame.
* Do not call `reset()` while the GPU still reads from the allocator's memory. This is the new way to crash a frame loop: with
  Metal 3 the framework kept the memory alive for you.
* The complete render pass (descriptor, pipeline state, argument table, drawable handling) is the subject of
  xref:graphics-games/metal/hello-triangle-metal4.adoc[Hello Triangle with Metal 4].

== Incremental adoption

Metal 4 types can be adopted one at a time, next to the older ones. A `MTLDevice` creates both kinds of queue, resources
(`MTLBuffer`, `MTLTexture`, heaps) are the same objects in both worlds, and the two models can even share work through
events. Apple's guidance is to move piece by piece, and the order below is the one the Bookshelf follows.

.Steps to adopt Metal 4 next to Metal 3
[mermaid]
....
flowchart TD
    A["Existing Metal 3 renderer"] --> B{"device.supportsFamily(.metal4) and OS 26 or later?"}
    B -- "no" --> C["Stay on Metal 3 path (MTLCommandQueue)"]
    B -- "yes" --> D["Create MTL4CommandQueue and allocators"]
    D --> E["Move binding to argument tables and residency sets"]
    E --> F["Add barriers and events between passes"]
    F --> G["Move compilation to MTL4Compiler"]
    G --> H["Optional: tensors, ML encoder, MetalFX neural upscaling"]
....

The decision is made once, at start-up, and chooses an implementation of a small renderer protocol. The code below is the
selection logic used by the Bookshelf, including the language version for runtime-compiled shaders.

[source,swift]
----
import Metal

enum Backend { case metal4, metal3 }

func selectBackend(for device: MTLDevice) -> Backend {
    if #available(iOS 26.0, macOS 26.0, tvOS 26.0, visionOS 26.0, *),
       device.supportsFamily(.metal4) {
        return .metal4
    }
    return .metal3
}

/// Compile options for source-compiled shaders (rare; the default library is precompiled).
func makeCompileOptions() -> MTLCompileOptions {
    let options = MTLCompileOptions()
    if #available(iOS 27.0, macOS 27.0, tvOS 27.0, visionOS 27.0, *) {
        options.languageVersion = .version4_1
    } else if #available(iOS 26.0, macOS 26.0, tvOS 26.0, visionOS 26.0, *) {
        options.languageVersion = .version4_0
    } else {
        options.languageVersion = .version3_2
    }
    return options
}

guard let device = MTLCreateSystemDefaultDevice() else { fatalError("Metal is not available") }
print("Backend:", selectBackend(for: device))
----

Source: https://developer.apple.com/documentation/metal/mtlgpufamily[MTLGPUFamily]; https://developer.apple.com/documentation/metal/mtllanguageversion[MTLLanguageVersion]

Common mistakes when adopting:

* *Testing only the OS version.* An OS 26 device with an older GPU can fail `supportsFamily(.metal4)`; always ask the device.
* *Mixing the two models inside one pass.* An `MTL4RenderCommandEncoder` is recorded on an `MTL4CommandBuffer` and a
  `MTLRenderCommandEncoder` on an `MTLCommandBuffer`. Share resources and events between them, not encoders.
* *Forgetting residency.* A buffer that is not in a residency set attached to the queue or command buffer may not be resident when the
  GPU reads it. Add the long-lived set once and call `commit()` on it after changing its contents.
* *Resetting an allocator too early.* Tie `reset()` to a completion event of the frame that last used the allocator.

Performance note: the benefit of Metal 4 is mostly on the CPU side. A scene that is already limited by shading will not become
faster only by changing the API; use xref:graphics-games/metal/debugging-and-profiling.adoc[Debugging and Profiling] to see which side is the limit.

== Hardware

.Which Apple GPUs run Metal 4
image::graphics-games-metal-whats-new-in-metal-4-hardware.svg["Table of GPU families apple6 to apple9, apple10 and Vision Pro against Metal 4 support and hardware ray tracing",width=720]

`MTLGPUFamily` names the feature families, and `+supportsFamily(_:)+` is the way to query them (it replaced the old `MTLFeatureSet`
enumeration, which is deprecated since iOS 16 and macOS 13). The Apple families map to chips as follows.

|===
|Family |Chips

|`apple7`
|A14 and M1

|`apple8`
|A15, A16 and M2

|`apple9`
|A17, M3 and M4

|`apple10`, `apple11`
|Newer chips. Use `supportsFamily` rather than assuming a chip, and read the Feature Set Tables for what each family adds.

|`metal3`, `metal4`
|Capability families that are independent of the chip generation: they say which API generation the device supports.
|===

The older `common1` to `common3`, `mac1`, `mac2` and Mac Catalyst families are deprecated. Hardware ray tracing needs an A17 or M3
and later (see xref:graphics-games/metal/ray-tracing.adoc[Ray Tracing]), and the Neural Accelerators that WWDC26 added to the
machine-learning story are in the M5 Pro and M5 Max. The Feature Set Tables PDF (dated October 2026) lists limits such as the
maximum threadgroup size per family.

Source: https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf[Metal Feature Set Tables]

== What WWDC26 added

* *Quantised tensor formats and scale factors*, so quantised weights can be expressed directly, and native support in the Metal
  Performance Primitives for compressing model weights. The accompanying session is "Optimize custom ML operations with Metal tensors".
* *MetalFX*: a redesigned temporal upscaler that uses both the Neural Engine and the Neural Accelerators on the M5 Pro and M5 Max,
  reconstructing detail from lower render resolutions; subrectangle processing for dynamic resolution; motion vectors as direct input; and
  distortion fields for post-process effects. See
  xref:graphics-games/metal/metalfx-upscaling-and-frame-interpolation.adoc[MetalFX Upscaling and Frame Interpolation].
* *Game Porting Toolkit 4*, with a companion repository that provides skills and sample code for working with coding agents; see
  xref:graphics-games/metal/metal-cpp-and-game-porting.adoc[metal-cpp and Game Porting].
* *Command-line tools* `gpucapture`, `gpudebug` and `metalperftrace` for capture, inspection and tracing without opening Xcode.

Source: https://developer.apple.com/metal/whats-new/[What's new in Metal]; https://developer.apple.com/metal/tools/[Metal developer tools]

|Deprecated in the 27 OSes ("has no effect on Apple Silicon")

|Deprecated in the 27 OSes

With macOS 27 as a deployment target, `ARCHS_STANDARD` no longer includes x86_64, so new Mac builds are Apple-silicon only. Still current
and not deprecated: `MTKView`, `MTLArgumentEncoder`, `MTLResidencySet`, `CAMetalDisplayLink` (iOS 17 and macOS 14), mesh pipelines and
`MTLIOCommandQueue`.

== A first look at the Metal 4 pieces in the Bookshelf

Before the sequence of pages begins, here is what the finished renderer contains, as a checklist you can come back to.

. A `MTL4CommandQueue`, one reusable `MTL4CommandBuffer` and three allocators (this page).
. An `MTL4ArgumentTable` per stage that needs resources, and a residency set for the shelf, the books and the textures
  (xref:graphics-games/metal/argument-buffers-and-bindless.adoc[Argument Buffers and Bindless]).
. Pipeline states built through an `MTL4Compiler`, with a binary archive for fast launch.
. Barriers between the shadow pass, the main pass and the compute pass that animates the dust particles.
. On supported hardware, an upscaler between the main pass and the UI pass.
. The Metal 3 renderer implementing the same protocol for older devices, selected as shown above.
