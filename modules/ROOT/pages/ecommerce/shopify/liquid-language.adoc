This page describes Liquid as it is used in Shopify Online Store themes. Liquid is not versioned: the open-source engine
is the Ruby gem `liquid` (latest 5.14.0 on 2026-10-27, which needs Ruby 3.0 or newer), and Shopify extends it with its own
tags, filters and objects. At the Liquid reference revision used for this page the Shopify variant documents 33 tag
entries (31 distinct names), 155 filter entries (154 distinct names, because `date` is listed in two categories) in 19 categories and 142 objects. The facts below were checked on 2026-10-27
against the Liquid reference on shopify.dev, Shopify CLI 5.0.0 with Theme Check 3.31.0, the Ruby gem 5.3.0 (the last
release that runs on the macOS system Ruby 2.6 used for the tests) and LiquidJS 10.30.0.

Liquid is the layer where a theme turns store data into HTML on Shopify's servers, so it is the language of every file in
the `layout`, `templates`, `sections`, `blocks` and `snippets` folders described in
the theme architecture page. The running example is Pocket Coffee, the small specialty-coffee shop with the single-origin
beans product (18 variants, SKUs such as `+PC-ETH-WHL-250+`), the Coffee Club customer segment and free shipping to Spain
from 40 EUR. Every snippet in this page belongs to a small Pocket Coffee theme built from the Skeleton theme and
validated with Theme Check.

How the examples were verified is worth stating once. Plain Liquid constructs were run with the Ruby gem 5.3.0 and with
LiquidJS 10.30.0. Shopify-specific tags, filters and objects (`money`, `t`, `image_url`, `paginate`, `product`, `cart`) do
not exist in those engines, so the Pocket Coffee snippets were validated with Theme Check, the same engine that
`shopify theme check` embeds, and their logic was rendered with the Ruby gem plus a few stub filters that stand in for
`money` and `t`. Real theme rendering needs a store (`shopify theme dev` or `shopify theme console`), and no store or
account was used, so nothing on this page was rendered by Shopify itself. Where a result depends on Shopify's own engine,
the text says that it comes from the documentation.

== What Liquid is and where it runs

Liquid is a template language created by Shopify and released as an open-source project. A template mixes static text
(usually HTML) with Liquid code. When a storefront request arrives, Shopify's servers evaluate the Liquid, substituting
store data, and send plain HTML to the browser. Nothing of the Liquid reaches the browser, so Liquid cannot react to
clicks; behaviour after page load belongs to JavaScript, and the Ajax APIs or the Section Rendering API fetch fresh
HTML when a page must change without a reload.

Shopify documents four other variations of Liquid that use different tags, filters and objects: notification templates
(emails), Shopify Flow, order printer templates and packing slip templates. This page covers only the theme variation.

Liquid is evaluated in some theme files and deliberately not in others:

[cols="3,2,5",options=header]
|===
|File or construct
|Liquid evaluated
|Notes

|Layouts, templates (`.liquid`), sections, blocks, snippets
|Yes
|Every Liquid file; `layout/theme.liquid` must output `+{{ content_for_header }}+` and `+{{ content_for_layout }}+`.

|`+{% stylesheet %}+` and `+{% javascript %}+` bodies
|No
|The body is emitted as written; Liquid inside can cause syntax errors, and the Theme Check rule StaticStylesheetAndJavascriptTags reports it.

|`+{% style %}+` body
|Yes
|Rendered as a `<style data-shopify>` element, so `+{{ settings.colors_accent_1 }}+` works there.

|`+{% schema %}+` JSON
|No
|Settings values must be Liquid free (Theme Check rule LiquidFreeSettings).

|JSON templates, section groups, `+config/*.json+`
|No
|Data only; they name sections and blocks that are Liquid files.

|Locale files in `locales/`
|Placeholders only
|A `+{{ name }}+` placeholder is filled by arguments of the `t` filter; tags are not evaluated.
|===

Source: https://shopify.dev/docs/api/liquid[Shopify docs: Liquid reference]

== Syntax: output, tags and filters

Liquid has three kinds of markup. Output tags `+{{ ... }}+` print the value of an expression. Logic tags `+{% ... %}+`
control what is rendered and print nothing themselves. Filters, written after a pipe `|` inside either kind, transform a
value. Everything outside the delimiters is copied to the output unchanged.

[cols="2,5",options=header]
|===
|Markup
|Meaning

|`+{{ product.title }}+`
|Output the value of an object property. A missing value (`nil`) prints nothing.

|`+{{ product.title \| upcase \| truncate: 20 }}+`
|A chain of filters: each filter receives the result of the previous one. Arguments follow a colon and are separated by commas.

|`+{{ product.featured_image \| image_url: width: 400 }}+`
|Some filters take named arguments (`width: 400`); the first colon introduces the arguments, the second names one.

|`+{% assign label = 'Beans' %}+`
|A logic tag that stores a value in a variable. Tags that wrap content close with an `end` tag, for example `+{% if %}...{% endif %}+`.

|`+{% liquid ... %}+`
|A block of tags written one per line without delimiters; use `echo` to print inside it.

|`+{%- ... -%}+`, `+{{- ... -}}+`
|The hyphens strip whitespace on that side of the tag (see Whitespace control).

|`+{% comment %}...{% endcomment %}+`
|Content that is parsed but not executed or printed.

|`+{% # inline comment %}+`
|A single-line comment; inside a `liquid` tag a line that starts with `#` is a comment.

|`+{% raw %}...{% endraw %}+`
|Prints Liquid-looking text without evaluating it.

|`+{% doc %}...{% enddoc %}+`
|LiquidDoc documentation of a snippet or block (see LiquidDoc below).
|===

Literals are strings in single or double quotes, numbers (`7`, `7.5`), the booleans `true` and `false`, the nil value
`nil`, and ranges written `+(1..5)+` that exist only inside `for` loops and similar tags. You cannot write an array or an
object literal in Liquid; you obtain arrays from objects, from the `split` filter or from settings.

The tour below exercises comments, `raw`, the `liquid` tag and `echo`. It was run with Ruby Liquid 5.3.0, whose parser
predates inline comments, so the inline form is left out of the run; the Shopify documentation lists it as supported.

[source,liquid,subs=-attributes]
----
A{% comment %}hidden {{ 1 }}{% endcomment %}B{% raw %}{{ not parsed }}{% endraw %}C
{% liquid
  assign x = 'a'
  if x == 'a'
    echo 'is a'
  endif
  for i in (1..2)
    echo i
  endfor
%}
----

Observed output (Ruby Liquid 5.3.0 and LiquidJS 10.30.0 agree):

[source,text,subs=-attributes]
----
AB{{ not parsed }}C
is a12
----

Source: https://shopify.dev/docs/api/liquid/tags/liquid[Shopify docs: liquid tag]

== Types and truthiness

Liquid output is one of six data types. The Shopify reference lists them as string, number, boolean, nil, array and
`empty`, the last being the value returned for something that exists but has no content, such as a deleted page.

[cols="2,5",options=header]
|===
|Type
|Behaviour

|`string`
|Characters in single or double quotes. Concatenate with the `append` and `prepend` filters, or by writing values next to each other. `size` returns the length; a string cannot be indexed with brackets (`s[0]` prints nothing).

|`number`
|Integers and floats. The result type matters: `+{{ 10 \| divided_by: 4 }}+` prints `2` because the divisor is an integer, while `+{{ 10 \| divided_by: 4.0 }}+` prints `2.5`. Prices are integers in the currency's smallest unit (`+product.price+` of `890` is 8.90 EUR), which is why they go through the `money` filters.

|`boolean`
|`true` or `false`. Settings of type `checkbox` and many object properties (`available`) are booleans.

|`nil`
|The value of anything undefined, and of a property path that does not exist. It prints nothing and counts as false. The text `+'nil'+` is an ordinary non-empty string.

|`array`
|A list of any type, indexed from zero with `[0]`, `first`, `last` and `size`. Arrays are walked with `for` and `tablerow`. Negative indexes work: `+product.tags[-1]+` is the last tag.

|`empty`
|What Liquid returns for a defined object without content. Compare with the keyword `empty` to check that a resource exists before using it.
|===

Objects such as `product` or `cart` are not one of the six types: they are structured values whose properties you read
with dot notation (`product.title`) or bracket notation (`+product['title']+`, `+pages['about-us']+`). Square brackets accept
a quoted handle, a variable or an object reference, which is how you look up a property whose name is held in a variable.
Reading a property of `nil` is safe and gives `nil` again: `+nope.deeply.nested+` prints nothing and is false in an `if`.

=== Truthy and falsy

Only `nil` and `false` are falsy. This surprises developers coming from JavaScript or PHP, because the empty string, `0`
and the empty array are all truthy. The table was produced by evaluating `+{% if value %}+` in both engines, and the two
agree on every row.

[cols="3,2",options=header]
|===
|Value
|Result of `+{% if value %}+`

|`true`
|truthy

|`false`
|falsy

|`nil`, or an undefined variable
|falsy

|`+''+` (empty string)
|truthy

|`0`
|truthy

|`[]` (empty array)
|truthy

|any non-empty string, number, object
|truthy
|===

Because the empty string is truthy, test for content with `blank`: `+{% if product.vendor != blank %}+`. The keyword
`blank` is true for `nil`, `false`, empty strings and whitespace-only strings, and for empty arrays; `empty` is true for
empty strings, empty arrays and the empty object. The stock Ruby gem implements both keywords by calling `blank?` and
`empty?` on the value, and `blank?` comes from Rails, so the plain gem 5.3.0 answers `false` for `+'' == blank+` and
`nil == blank`, while LiquidJS and Shopify answer `true`. The practical rule is to rely on `blank` only inside a real
Shopify render, and to define `blank?` yourself when you test with the bare gem.

[source,ruby,subs=-attributes]
----
require "liquid"

d = { "zero" => 0, "empty_s" => "", "arr" => [], "product" => { "compare" => nil, "available" => true } }
%w[empty_s zero arr product.compare product.available nope].each do |k|
  out = Liquid::Template.parse("{% if #{k} %}truthy{% else %}falsy{% endif %}").render(d)
  puts "#{k.ljust(18)} => #{out}"
end
----

Source: https://shopify.dev/docs/api/liquid/basics#truthy-and-falsy[Shopify docs: Liquid basics, truthy and falsy]

=== Comparing and converting values

The comparison operators are `==`, `!=`, `>`, `<`, `>=`, `+<=+`, `and`, `or` and `contains`. Comparing values of different
types does not coerce them: `+{% if '10' == 10 %}+` is false in both engines, and `10 > 9` is true. Arithmetic filters
do coerce strings that look like numbers: `+{{ '10' | plus: 5 }}+` prints `15`, `+{{ '1.5' | plus: 1 }}+` prints
`2.5`, and a string with no number in it counts as `0` (`+{{ 'a' | plus: 'b' }}+` prints `0`). Passing a number to
`append` or `prepend` converts it to text (`+{{ 1 | append: 2 }}+` prints `12`).

`contains` checks for a substring in a string and for an exact string element in an array of strings. It cannot find an
object in an array of objects, and `+product.tags contains 'bea'+` is false because tags are compared whole.

=== Operators have a fixed order and no parentheses

When a tag mixes `and` and `or`, Liquid evaluates the operators from right to left and the order cannot be changed.
Parentheses are not valid inside Liquid conditions: a tag that contains them fails to parse. All three results below were
measured in both engines.

[source,liquid,subs=-attributes]
----
{% if true and false and false or true %}T{% else %}F{% endif %}
{% if true or false and false %}T{% else %}F{% endif %}
{% if false and false or true %}T{% else %}F{% endif %}
----

[source,text,subs=-attributes]
----
F
T
F
----

Source: https://shopify.dev/docs/api/liquid/basics#order-of-operations[Shopify docs: Liquid basics, order of operations]

The first line is read as `true and (false and (false or true))`, which is false. Write conditions that need grouping as
nested `if` tags or as separate `assign` steps. With parentheses the Ruby gem raises
`Expected dotdot but found comparison` (it tries to read `(1 == 1)` as a range) and LiquidJS raises
`invalid range syntax`; Theme Check reports `+Syntax error in 'if' tag+`.

== Objects

Objects carry the store data. Shopify groups them by where they are available, and using one outside its scope gives
`nil`, which is the source of many silent bugs.

* Global objects exist in every file. The reference flags 34, among them `shop`, `settings`, `routes`, `request`,
  `template`, `cart`, `customer`, `localization`, `linklists`, `pages`, `collections`, `all_products`, `blogs`,
  `articles`, `images`, `metaobjects`, `theme`, `scripts`, `canonical_url`, `current_page`, `page_title`,
  `page_description`, `page_image`, `handle`, `content_for_header` and `content_for_layout`.
* Template-bound objects exist when the template (or a section or snippet inside it) is rendered for that resource: for
  example `product` (and `remote_product`) on the product template, `collection` (and `current_tags`) on collections,
  `article` and `blog`, `page`, `search`, `order` on the customer order page, `gift_card` and `recipient` on the gift
  card template, `robots` in `robots.txt.liquid`, `checkout` and `metaobject` on their own pages.
* Scoped objects exist only inside the tag or file that creates them: `section` (in a section), `block` (in a theme
  block or a loop over `section.blocks`), `forloop` and `tablerowloop` (inside their loops), `paginate` (inside a
  `paginate` tag) and `form` (inside a `form` tag).

The objects the Pocket Coffee snippets use most, with the properties that matter:

[cols="2,6",options=header]
|===
|Object
|Properties used in this page and why

|`product`
|`title`, `handle`, `url`, `type` (the product type, for example `Beans`), `vendor`, `tags`, `price` (cents), `compare_at_price`, `available`, `variants`, `options_with_values`, `selected_or_first_available_variant`, `featured_image`, `images`, `metafields`. Its `variants` array can be paginated.

|`collection`
|`title`, `handle`, `products`, `products_count`, `all_tags`, `all_types`, `filters`, `sort_by`. `products` is an array that `paginate` can split.

|`cart`
|`items`, `item_count`, `total_price` (cents), `items_subtotal_price`, `original_total_price`, `currency`, `note`, `attributes`.

|`customer`
|`nil` for visitors who are not logged in; otherwise `email`, `first_name`, `tags` (this is where Coffee Club membership is read), `orders`, `default_address`.

|`shop`
|`name`, `url`, `currency`, `money_format`, `enabled_currencies`, `published_locales`, `customer_accounts_enabled`.

|`settings`

|`section` and `block`
|`section.id`, `section.settings`, `section.blocks`; `block.id`, `block.type`, `block.settings`, `block.shopify_attributes`. A block's `id` is generated by Shopify and can change, so never compare it with a literal.

|`root_url`, `cart_url`, `account_url`, `search_url`, `collections_url` and the other storefront paths. Use these instead of hard-coded paths such as `/cart`, which break for visitors in another market or language (Theme Check rule HardcodedRoutes).

|`request`
|`host`, `origin`, `path`, `page_type`, `locale`, `design_mode`. `design_mode` is true inside the theme editor, but customer-facing behaviour must not depend on it, because the editor preview has to match the live store.

|`content_for_header`, `content_for_layout`
|Required in `layout/theme.liquid`: the first carries Shopify's scripts inside `<head>` and must not be parsed or modified (Theme Check rule ContentForHeaderModification), the second is where the current template renders inside `<body>`.

Two limits are easy to miss. The `all_products` object accepts only 20 unique handles per page, so a longer list should
come from a collection. And fetching an array does not respect your `limit`: `+collection.products+` loads up to 50
products regardless of the loop's `limit`, which is why the pagination section below recommends `paginate`.

=== Metafields

Custom data reaches Liquid through metafields. Read a value with `+resource.metafields.<namespace>.<key>.value+`; the
shape of the value depends on the metafield type, and it is a string for text types, a number for number types, an object
for reference types (`product_reference` returns a `product`) and a date string for `date` and `date_time`, which you
format with the `date` filter. Metafields cannot be created from Liquid. When a key is named `size`, `first` or `last`,
use bracket notation (`+product.metafields.custom['size']+`) because dot notation can resolve to the filter of the same
name. The Pocket Coffee roast date is a metafield `custom.roast_date` of type `date`, rendered by the first snippet below.

Source: https://shopify.dev/docs/api/liquid/objects/metafield[Shopify docs: metafield object]

== Tags

Tags are the logic of Liquid. Shopify's reference lists 33 tag entries in these groups; `else` and `break` are each
documented twice (conditional and loop `else`; loop `break` and a theme-level `break` that stops the rest of a file from
rendering), which is why the entries number 33 for 31 distinct names. `elsif` and `when` are clauses of `if` and `case`,
and `schema` is documented with sections rather than in the Liquid reference.

[cols="2,5",options=header]
|===
|Group
|Tags

|Variables
|`assign`, `capture`, `increment`, `decrement`

|Conditionals
|`if`, `unless`, `case`, `else`, with `elsif` and `when`

|Iteration
|`for`, `break`, `continue`, `cycle`, `tablerow`, `paginate`

|Syntax helpers
|`comment`, `doc`, `echo`, `liquid`, `raw`

|Theme
|`content_for`, `layout`, `render`, `include` (deprecated), `section`, `sections`, `javascript`, `stylesheet`, `block`, `partial`

|HTML
|`form`, `style`
|===

=== Variable tags

`assign` creates a variable that lives for the rest of the file and in snippets rendered with `include`; it is not
scoped to the block where you write it, so a value assigned inside a `for` loop is still there after the loop (measured:
the variable holds the last item). `capture` stores rendered text, filters included, in a string variable. `increment`
and `decrement` keep their own counters: in the measured run two `+{% increment a %}+` tags printed `0` then `1`, and
two `+{% decrement b %}+` tags printed `-1` then `-2`.

[source,liquid,subs=-attributes]
----
{% assign tag_line = product.tags | join: ' | ' | upcase %}
{% capture heading %}{{ product.title | downcase }}-{{ product.variants.size }}{% endcapture %}
----

Source: https://shopify.dev/docs/api/liquid/tags/assign[Shopify docs: assign tag]

=== Conditionals

`if`, `elsif`, `else` and `unless` branch on the truthiness rules above; `case` compares one value with several `when`
values, and a `when` can list alternatives separated by commas or `or`. Logical operators work only in conditions: you
cannot write `+{% assign vip = a or b %}+` (the strict parser rejects it, see below), so compute the boolean with an `if`.

[source,liquid,subs=-attributes]
----
{% case product.tags.size %}
  {% when 0 %}no tags
  {% when 1, 2 %}few tags
  {% else %}many tags
{% endcase %}
----

Source: https://shopify.dev/docs/api/liquid/tags/case[Shopify docs: case tag]

=== Iteration

`for` repeats a block for each element of an array or range, accepts the parameters `limit`, `offset` and `reversed`,
and supports an `else` branch that runs when the array is empty. Inside the loop the `forloop` object gives the position:
for a three-tag array, `forloop.index` runs 1 to 3, `forloop.index0` 0 to 2, `forloop.rindex` 3 to 1 and
`forloop.rindex0` 2 to 0. `break` leaves the loop and `continue` skips to the next element. `cycle` rotates through a list
of strings inside a loop (odd and even row classes), and `tablerow` emits table rows and cells with `cols`, `limit` and
`offset` parameters and a `tablerowloop` object.

A `for` loop is limited to 50 iterations per page in themes. To go through more items, wrap the array in `paginate`,
which splits it into pages of 1 to 250 items and exposes the `paginate` object for the navigation links. Pagination
works only up to the 25,000th item of an array, so filter a larger collection before paginating it. The arrays that
can be paginated are `article.comments`, `blog.articles`, `collections`, `collection.products`, `customer.addresses`,
`customer.orders`, `metaobject_definition.values`, `pages`, `product.variants`, `search.results` and the
`article_list`, `collection_list` and `product_list` settings.

[source,liquid,subs=-attributes]
----
{% paginate collection.products by 12 %}
  <ul class="grid">
    {%- for product in collection.products -%}
      {% render 'product-card', product: product, index: forloop.index %}
    {%- endfor -%}
  </ul>
  {{ paginate | default_pagination }}
{% endpaginate %}
----

Source: https://shopify.dev/docs/api/liquid/tags/paginate[Shopify docs: paginate tag]

The `limit` parameter of `for` bounds the iterations but not the amount of data fetched. To fetch only what you show, put
a `paginate` with a matching page size around the loop and keep `limit` as well; the documentation measures this as
faster than a bare loop with `limit`.

[source,liquid,subs=-attributes]
----
{% paginate collection.products by 4 %}
  {% for product in collection.products limit: 4 -%}
    {{ product.title }}
  {%- endfor %}
{% endpaginate %}
----

Source: https://shopify.dev/docs/api/liquid/tags/for[Shopify docs: for tag]

=== Syntax helper tags

The `liquid` tag removes the delimiters from a block of statements, one statement per line, and `echo` prints an
expression inside it (equivalent to `+{{ }}+`, filters included). Long logic reads much better this way, and the lines
inside a `liquid` tag produce no whitespace of their own. A comment inside it must be on its own line and start with `#`.
The `doc` tag documents a snippet or block and is never rendered.

=== Theme tags

These tags assemble pages from other files; each has its own page of detail, so here is the summary.

[cols="2,5",options=header]
|===
|Tag
|Purpose

|`+{% layout 'name' %}+`, `+{% layout none %}+`
|Chooses the layout file (default `theme.liquid`) or renders the template with no layout.

|`+{% section 'header' %}+`
|Statically renders one section file.

|`+{% sections 'header-group' %}+`
|Renders a section group, used in layouts for the header and footer groups.

|`+{% render 'name' %}+`
|Renders a snippet or an app block in an isolated scope (see the next section).

|`+{% include 'name' %}+`
|Deprecated predecessor of `render`.

|`+{% content_for 'blocks' %}+`, `+{% content_for 'block', type: 'button', id: 'cta' %}+`
|Creates the area where a section renders the theme blocks configured in the editor, or renders one static theme block with extra arguments.

|`+{% block 'container' %}+`, `+{% partial %}+`
|Tags of the Liquid July '26 developer preview that compose a page from blocks directly in a Liquid template; the current Skeleton theme already uses `block`. They need a development store with the preview enabled, so they were validated only with Theme Check.

|`+{% form 'product', product %}+`
|Generates an HTML form of a given type with the hidden fields Shopify needs. The types are `activate_customer_password`, `cart`, `contact`, `create_customer`, `currency`, `customer`, `customer_address`, `customer_login`, `guest_login`, `localization`, `new_comment`, `product`, `recover_customer_password`, `reset_customer_password` and `storefront_password`.

|`+{% style %}...{% endstyle %}+`
|A `<style data-shopify>` element whose CSS can use Liquid; color settings used here update live in the theme editor.

|`+{% stylesheet %}+`, `+{% javascript %}+`
|CSS or JavaScript that belongs to one section, block or snippet. One of each per file, no Liquid inside, only in those three file types (Theme Check rules StylesheetOncePerFile, JavascriptOncePerFile and the TagInWrongFile checks).
|===

Source: https://shopify.dev/docs/api/liquid/tags/content_for[Shopify docs: content_for tag]

A Pocket Coffee product page combines several of these: a `form` for the add-to-cart button, a `render` for each piece of
reusable markup, and conditionals around the Coffee Club note. The next snippet reads the logged-in customer's tags.
`customer` is `nil` for guests, so the outer `if customer` protects the property access, and the result is stored in a
boolean before it is used.

[source,liquid,subs=-attributes]
----
{%- liquid
  assign is_member = false
  if customer
    if customer.tags contains 'Coffee Club'
      assign is_member = true
    endif
  endif
-%}

{%- if is_member and product.type == 'Beans' -%}
  <p>{{ 'products.product.club_discount' | t }}</p>
{%- endif -%}
----

Source: https://shopify.dev/docs/api/liquid/objects/customer[Shopify docs: customer object]

Rendered with stub filters, a Coffee Club member viewing a Beans product gets
`<p>Coffee Club members save 10% on beans.</p>` and a guest gets an empty string. Theme Check passes the file.

== Filters

A filter takes the value on its left as its first input and returns a new value. Filters chain left to right: each one
receives the result of the previous one, so `+{{ 'Hello, World' | split: ', ' | join: '-' }}+` prints `Hello-World`.
Arguments are positional (`truncate: 10`) or named (`+image_url: width: 400, crop: 'center'+`). Arguments themselves cannot
contain filters or operators, so compute a value with `assign` first. Applying a filter to `nil` usually gives `nil`,
`0` or an empty string rather than an error, and an unknown filter name is silently ignored by the plain Ruby gem
(`+{{ 1 | money }}+` prints `1`), but Theme Check reports it as the error UnknownFilter. Liquid does not escape output
automatically: `+{{ '<b>x</b>' }}+` prints the tag as written (confirmed with both engines), so text that comes from
customers or merchants should go through `escape`, as the Skeleton collection template does for product titles.

A few behaviours deserve attention. `default` replaces `nil`, `false` and the empty string, but not a whitespace-only
string and not `0`; pass `allow_false: true` to keep an explicit `false`. `divided_by` returns a result of the same type as
the divisor, so use a float divisor for percentages, as the free-shipping snippet below does. `date` accepts the strftime
directives, formats date strings from metafields, and prints nothing for `nil`. `json` serializes any value for use in
JavaScript and includes the quotes itself; applied to a `product` on a store created after 2017-12-05 it omits the variants' `inventory_quantity` and
`inventory_policy`, which you read from the variant objects. Newer filters such as `sum`, `find`, `find_index` and `has`
exist in Shopify and in LiquidJS 10.30.0 (`+{{ items | sum: 'q' }}+` printed `3`), but the Ruby gem 5.3.0 does not know
`sum` and echoes the array instead.

=== Shopify-specific filters

Shopify adds the filters that need store data: money formatting, CDN URLs, translations, URL helpers. None of them exist
in the plain engines, so they were checked with Theme Check and are described here from the reference.

|===
|Filter
|Behaviour

|`+{{ variant.price \| money }}+`
|Formats an amount in the currency's smallest unit using the store's HTML-without-currency format; variants include `money_with_currency` (adds the code), `money_without_currency` and `money_without_trailing_zeros`. The input is a number: never pass an already formatted string.

=== The rule that causes most filter bugs

Because each filter receives the previous filter's result, an expression such as `+{{ 'cart.free_shipping_missing' | t: amount: missing | money }}+`
applies `money` to the translated sentence, not to the number. The next figure shows both versions. In the
measured run with stub filters the wrong form printed `€0.00` instead of the sentence, because the text is not a number
(how Shopify's own `money` treats a non-numeric string was not tested). The fix is to format the number into a variable
and pass the variable to `t`.

=== Pocket Coffee price and free-shipping snippets

The first snippet prints a variant's price, with the struck-through compare-at price when the variant is on sale. It
documents its parameters with LiquidDoc, computes the sale flag in a `liquid` block and uses whitespace control so the
markup has no stray blank lines.

[source,liquid,subs=-attributes]
----
{% doc %}
  Renders the price of a variant, with the compare-at price when it is on sale.

  @param {variant} variant - The variant to price
  @param {boolean} [show_currency] - Show the ISO currency code after the amount

  @example
  {% render 'price', variant: product.selected_or_first_available_variant %}
{% enddoc %}

{%- liquid
  assign on_sale = false
  if variant.compare_at_price > variant.price
    assign on_sale = true
  endif
-%}

<p class="price">
  {%- if on_sale -%}
    <s>{{ variant.compare_at_price | money }}</s>
  {%- endif -%}
  {%- if show_currency -%}
    {{ variant.price | money_with_currency }}
  {%- else -%}
    {{ variant.price | money }}
  {%- endif -%}
</p>
----

Source: https://shopify.dev/docs/api/liquid/filters/money_with_currency[Shopify docs: money_with_currency filter]

Rendered with stub money filters (euro sign, two decimals), a variant priced 890 cents with a compare-at price of 1090
cents gives `<p class="price"><s>€10.90</s>€8.90</p>`, and a 2990 cent variant with `show_currency` gives
`<p class="price">€29.90 EUR</p>`. When `compare_at_price` is `nil` the comparison is false and no error is raised.

The second snippet implements the Zone 1 rule: free shipping to Spain from 40 EUR (4000 cents). It uses the math filters
and the float divisor, clamps the values with `at_least` and `at_most`, and applies the lesson of the previous figure.

[source,liquid,subs=-attributes]
----
{% doc %}
  Tells the customer how far the cart is from free shipping in Spain.

  @param {number} threshold - The free shipping threshold in cents, for example 4000
{% enddoc %}

{%- liquid
  assign missing = threshold | minus: cart.total_price | at_least: 0
  assign progress = cart.total_price | times: 100.0 | divided_by: threshold | at_most: 100 | round
  assign missing_formatted = missing | money
-%}

{%- if missing == 0 -%}
  <p>{{ 'cart.free_shipping_reached' | t }}</p>
{%- else -%}
  <p>{{ 'cart.free_shipping_missing' | t: amount: missing_formatted }}</p>
{%- endif -%}
<progress value="{{ progress }}" max="100"></progress>
----

The two translation keys live in the locale file, where `+{{ amount }}+` is the placeholder the `t` filter fills:

[source,json,subs=-attributes]
----
{
  "cart": {
    "free_shipping_reached": "Free shipping to Spain unlocked",
    "free_shipping_missing": "Add {{ amount }} more for free shipping to Spain"
  }
}
----

Source: https://shopify.dev/docs/api/liquid/filters/translate[Shopify docs: translate filter]

Measured with the stub filters: a cart of 31.90 EUR (3190 cents) renders
`<p>Add €8.10 more for free shipping to Spain</p><progress value="80" max="100"></progress>`, a cart of 45.00 EUR renders
`<p>Free shipping to Spain unlocked</p><progress value="100" max="100"></progress>`, and an empty cart renders the
40.00 EUR message with `value="0"`. The stub that supplied `money` and `t` is short:

[source,ruby,subs=-attributes]
----
require "liquid"
require "json"

LOCALE = JSON.parse(File.read("locales/en.default.json"))

module ShopStubs
  def money(cents) = format("€%.2f", cents.to_f / 100)

  def t(key, opts = {})
    text = key.split(".").reduce(LOCALE) { |h, k| h.is_a?(Hash) ? h[k] : nil }.to_s
    text.gsub(/\{\{\s*(\w+)\s*\}\}/) { opts[Regexp.last_match(1)].to_s }
  end
end
Liquid::Template.register_filter(ShopStubs)

# The doc tag is Shopify-specific: register it as a block that renders nothing.
class DocTag < Liquid::Block
  def render(_context) = ""
end
Liquid::Template.register_tag("doc", DocTag)

snippet = File.read("snippets/free-shipping-bar.liquid")
puts Liquid::Template.parse(snippet).render("threshold" => 4000, "cart" => { "total_price" => 3190 })
----

Source: https://github.com/Shopify/liquid[Shopify/liquid on GitHub: the open-source engine]

The stub does not reproduce Shopify's currency formatting, translation fallbacks or pluralization, so treat these runs as
checks of the Liquid logic only.

== Whitespace control

Every line of Liquid that prints nothing still leaves its newline and indentation in the output. Add a hyphen inside the
delimiter to strip whitespace, including newlines, on that side: `+{%- ... %}+` removes everything before the tag,
`+{% ... -%}+` removes everything after it, and both together do both. The same works for output tags with `+{{-+` and
`+-}}+`. Whitespace is only text, so the control also removes the spaces between two inline elements, which is the usual
way to glue words together by accident.

The table shows the exact string each template renders, measured with Ruby Liquid 5.3.0 and the origins list of the
Pocket Coffee beans (`Ethiopia`, `Colombia`, `Brazil`). The columns use `\n` for a newline. LiquidJS printed the same
strings for the cases it was given.

[cols="1,4,5",options=header]
|===
|Case
|Template
|Rendered text

|None
|`+<ul>\n{% for o in origins %}\n  <li>{{ o }}</li>\n{% endfor %}\n</ul>\n+`
|`<ul>\n\n  <li>Ethiopia</li>\n\n  <li>Colombia</li>\n\n  <li>Brazil</li>\n\n</ul>\n`

|Both sides of loop tags
|`+<ul>\n{%- for o in origins -%}\n  <li>{{ o }}</li>\n{%- endfor -%}\n</ul>\n+`
|`<ul><li>Ethiopia</li><li>Colombia</li><li>Brazil</li></ul>\n`

|Right side only
|`+<ul>\n{% for o in origins -%}\n  <li>{{ o }}</li>\n{% endfor -%}\n</ul>\n+`
|`<ul>\n<li>Ethiopia</li>\n<li>Colombia</li>\n<li>Brazil</li>\n</ul>\n`

|Left side of the inner lines
|`+<ul>\n  {%- for o in origins %}\n  <li>{{ o }}</li>\n  {%- endfor %}\n</ul>\n+`
|`<ul>\n  <li>Ethiopia</li>\n  <li>Colombia</li>\n  <li>Brazil</li>\n</ul>\n`

|Output tags, hyphens
|`+<p>\n  {{- 'Pocket' }} {{ 'Coffee' -}}\n</p>+`
|`<p>Pocket Coffee</p>`

|Output tags, none
|`+<p>\n  {{ 'Pocket' }} {{ 'Coffee' }}\n</p>+`
|`<p>\n  Pocket Coffee\n</p>`

|`if` and `else`, none
|`+A\n{% if club %}\nmember\n{% else %}\nguest\n{% endif %}\nB+`
|`A\n\nmember\n\nB`

|`if` and `else`, hyphens
|`+A\n{%- if club -%}\nmember\n{%- else -%}\nguest\n{%- endif -%}\nB+`
|`AmemberB`

|`liquid` tag
|`+A\n{% liquid\n  if club\n    echo 'member'\n  endif\n%}\nB+`
|`A\nmember\nB`

|`assign`, none
|`+A\n{% assign x = 1 %}\nB+`
|`A\n\nB`

|`assign`, left hyphen
|`+A\n{%- assign x = 1 %}\nB+`
|`A\nB`
|===

The hyphen on the right of `+{%- if club -%}+` in case 8 also removed the newline between `A` and the text, which is why
`A`, `member` and `B` ended up on one line. Remove only as much as you need: strip around block tags, keep the spaces
between inline elements, and remember that stripping inside `<pre>` or between words changes what the visitor sees.
The `strip`, `lstrip`, `rstrip` and `strip_newlines` filters act on string values, not on the template text around tags
(`+{{ '  padded  ' | strip }}+` gives `padded`).

== Snippets: render versus include

Both tags insert a file from the `snippets` folder, but they differ in scope, and that difference is why Shopify
deprecated `include`. The figure summarizes the measured behaviour, and the table adds the other differences.

image::ecommerce-shopify-liquid-render-scope.svg["Variable scope of the include tag compared with the render tag",width=900]

Figure: include shares the caller's variables and can overwrite them, render isolates the snippet and passes only named arguments.

[cols="2,3,3",options=header]
|===
|Aspect
|`render`
|`include` (deprecated)

|Scope
|The snippet cannot see variables created outside it and what it assigns stays inside.
|The snippet reads and changes the caller's variables.

|Passing data
|Named arguments `+{% render 'badge', label: text %}+`, a single object with `+with ... as+`, or each array item with `+for ... as+`.
|Needs no arguments, because everything is shared; accepts `key: value` pairs too.

|Global and template objects
|Documented as accessible (shop, settings, routes and the objects of the current template such as `product`).
|Accessible.

|Snippet name
|A quoted string literal only (`+{% assign n = 'price' %}{% render n %}+` is a syntax error).
|May be a variable.

|Nesting
|A rendered snippet cannot use `include` (the engine reports "include usage is not allowed in this context").
|A snippet included by `include` may call `render`.

|Status
|Current. Theme Check can validate its arguments against LiquidDoc.
|Deprecated: it hurts performance and readability. Theme Check reports it as the warning DeprecatedTag.
|===

The values behind the figure come from this harness, which was run with Ruby Liquid 5.3.0; LiquidJS 10.30.0 printed the
same results for the five scope cases it was given.

[source,ruby,subs=-attributes]
----
require "liquid"

class MemFS
  def initialize(files) = @files = files
  def read_template_file(name) = @files.fetch(name)
end

Liquid::Template.file_system = MemFS.new(
  "counter" => "{% assign count = count | plus: 1 %}[snippet count={{ count }}]",
  "badge"   => "<span class=\"badge\">{{ label | default: 'none' }}</span>"
)

def run(template) = Liquid::Template.parse(template).render({})

puts run("{% assign count = 1 %}{% include 'counter' %} outer count={{ count }}")
puts run("{% assign count = 1 %}{% render 'counter' %} outer count={{ count }}")
puts run("{% assign count = 1 %}{% render 'counter', count: count %} outer count={{ count }}")
puts run("{% assign label = 'Roasted today' %}{% include 'badge' %}")
puts run("{% assign label = 'Roasted today' %}{% render 'badge' %}")
puts run("{% assign x = 'Roasted today' %}{% render 'badge', label: x %}")
----

[source,text,subs=-attributes]
----
[snippet count=2] outer count=2
[snippet count=1] outer count=1
[snippet count=2] outer count=1
<span class="badge">Roasted today</span>
<span class="badge">none</span>
<span class="badge">Roasted today</span>
----

Source: https://shopify.dev/docs/api/liquid/tags/render[Shopify docs: render tag]

Two details of the run are worth knowing. In the second line the snippet received no `count`, so `nil | plus: 1` made it
`1` inside, and the outer variable stayed `1`; with the argument in the third line the snippet saw `1`, changed its own
copy to `2`, and the outer value was untouched. And the stock Ruby gem keeps even top-level render data out of a rendered
snippet (`+{% render 'seesproduct' %}+` printed an empty `product`), while Shopify documents that global objects and the
template's own objects remain reachable. That is a difference between the bare gem and Shopify, so test object access in a
store, not in the gem.

=== The forms of render

[source,liquid,subs=-attributes]
----
{% render 'price', variant: variant, show_currency: true %}
{% render 'badge' with product.title as label %}
{% render 'product-card' for collection.products as product %}
----

Source: https://shopify.dev/docs/api/liquid/tags/render[Shopify docs: render tag]

With `for`, the snippet also sees a `forloop` object for that implicit loop. With `with` and no `as`, the object is
available under the snippet's file name. A variable changed inside the snippet changes only the snippet's copy. The
parameters of `render` accept values, not expressions: Shopify's strict parser rejects filters, comparison operators
or a bare variable name among the arguments (see the strict parsing section for the exact rewrites).

=== Migrating from include

Replace each `include` with `render` in three steps. First list the variables the snippet reads from its caller; Theme
Check helps because a snippet documented with LiquidDoc reports the parameters it expects. Second, pass those variables
as named arguments. Third, if the snippet used to assign a variable for the caller, return the value another way: compute
it in the caller, move the assignment into the caller, or render the snippet into a variable with `capture`.

[source,liquid,subs=-attributes]
----
{% comment %} before {% endcomment %}
{% assign current_variant = product.selected_or_first_available_variant %}
{% include 'price' %}

{% comment %} after {% endcomment %}
{% assign current_variant = product.selected_or_first_available_variant %}
{% render 'price', variant: current_variant %}
----

Source: https://shopify.dev/docs/api/liquid/tags/include[Shopify docs: include tag]

== LiquidDoc: typed snippet interfaces

Without documentation, a misspelled argument passes silently: `+{% render 'loading-spinner', produt: product %}+`
renders without an error and without the data. LiquidDoc fixes this. Put a `doc` tag at the top of a snippet or block
file with a JSDoc-like syntax, and tools validate every `render` against it:

* `@description` explains the file (a leading paragraph with no tag works too).
* `+@param {type} name - description+` declares an input. The type is optional and one of `string`, `number`, `boolean`,
  `object` or a Liquid object such as `variant` or `product`. Square brackets around the name (`[show_currency]`) make
  the parameter optional.
* `@example` shows a usage and can span several lines.

Theme Check turns the declaration into checks. For documentation: UniqueDocParamNames, UnsupportedDocTag (the `doc` tag
belongs to snippet files), ValidDocParamTypes and UnusedDocParam (a declared parameter must be used). For usage:
MissingRenderSnippetArguments (a required parameter is missing), UnrecognizedRenderSnippetArguments (an unknown name),
DuplicateRenderSnippetArguments and the content_for equivalents for static blocks. The editor integration (hover, code
completion, type fallbacks of `+''+`, `0`, `false`) comes from the Liquid language server that `shopify theme language-server`
starts.

The Pocket Coffee roast-date badge uses all three tags. It reads a date metafield, formats it with `date`, and builds the
sentence with the `t` filter, formatting the date before the translation as the previous section requires.

[source,liquid,subs=-attributes]
----
{% doc %}
  Renders the roast date of a product as a badge.

  @param {product} product - The product that may carry a roast date metafield
  @param {string} [class] - Optional CSS class added to the badge

  @example
  {% render 'roast-date-badge', product: product %}
  {% render 'roast-date-badge', product: product, class: 'badge--small' %}
{% enddoc %}

{%- assign roast_date = product.metafields.custom.roast_date.value -%}

{%- if roast_date != blank -%}
  {%- assign roast_label = roast_date | date: '%-d %B %Y' -%}
  <span class="badge{% if class != blank %} {{ class }}{% endif %}">
    {{- 'products.product.roasted_on' | t: date: roast_label -}}
  </span>
{%- endif -%}
----

Source: https://shopify.dev/docs/storefronts/themes/tools/liquid-doc[Shopify docs: LiquidDoc]

With the locale entry `+"roasted_on": "Roasted on {{ date }}"+` and a roast date of `2026-10-20`, the stubbed render gives

  @param {product} product - The product to list
{% enddoc %}

<table>
  {%- for variant in product.variants limit: 50 -%}
    <tr class="{% cycle 'odd', 'even' %}">
      <td>{{ variant.sku }}</td>
      <td>{{ variant.title | escape }}</td>
      <td>{{ variant.price | money }}</td>
      <td>{% if variant.available %}{{ 'products.product.in_stock' | t }}{% else %}{{ 'products.product.sold_out' | t }}{% endif %}</td>
    </tr>
  {%- else -%}
    <tr><td colspan="4">{{ 'products.product.no_variants' | t }}</td></tr>
  {%- endfor -%}
</table>
----

Source: https://shopify.dev/docs/api/liquid/tags/for[Shopify docs: for tag]

== Strict parsing and where Liquid is heading

Until 2026 the Liquid parser accepted some code that looked valid but was evaluated wrongly. On 2026-01-13 Shopify began
enforcing stricter parsing for all themes and theme app extensions, and it automatically rewrites non-conforming files,
adding a comment that says what changed. New Theme Store and App Store submissions must already be strict-parsable.
The cases in the migration guide are listed below; all but the same-line comment were reproduced with Theme Check 3.31.0
in one-line snippets (the reported check was LiquidSyntaxError, UnsupportedFilterArguments or LiquidHTMLSyntaxError).

[cols="4,4,4",options=header]
|===
|Code that now fails
|Why
|Fix

|`+{% render 'price', variant: v, show: s \| default: true %}+`
|Filters are allowed only in output, `assign` and `echo`, not in `render` arguments (Theme Check: UnsupportedFilterArguments).
|`+{% assign show_flag = s \| default: true %}+` then pass `show: show_flag`.

|`+{% assign vip = customer.tags contains 'Coffee Club' or settings.x %}+`
|Logical operators work only in conditions.
|Compute the boolean in an `if` and assign inside the branches.

|`+{% render 'price' with variant: v %}+`
|`with` takes a single object, not a key-value pair.
|`+{% render 'price', variant: v %}+`, or `+{% assign variant = v %}{% render 'price' with variant %}+`.

|`+{% render 'price', v %}+`, `+{% render 'price', variant: %}+`
|Arguments must be `name: value` pairs with a value.
|`+{% render 'price', variant: v %}+`

|`+{% if a && b %}+`
|`&&` and `\|\|` are not Liquid operators.
|Use `and` and `or`.

|`+{% when => 'Beans' %}+`, and `when 1100 # note` inside a `liquid` tag
|Unexpected characters in `case`; a comment on the same line as a statement.
|Write `+{% when 'Beans' %}+` and put comments on their own line.

|`+{% assign p = [key] %}+`
|Bare bracket access is reserved for array literals.
|`+{% assign p = self[key] %}+`
|===

Source: https://shopify.dev/docs/storefronts/themes/tools/strict-liquid-migration[Shopify docs: migrate to Liquid's strictest parser]

The same changelog entry points to the direction of the language. The Liquid July '26 developer preview (2026-07-21) adds
the `block` and `partial` tags so that page structure can live in a Liquid template, and Theme Check 3.28.0 added rules
for such Liquid-first themes. The Skeleton theme cloned for these tests already contains `+{% block 'container' %}+` in
its templates. Existing sections, JSON templates and theme settings keep working, and the preview needs a development
store, so it is out of scope here beyond this note.

Source: https://shopify.dev/changelog/liquid-is-getting-faster-and-ready-to-evolve[Shopify changelog: stricter Liquid parsing]

== Common errors

Liquid reports two classes of problem. Syntax errors stop a file from parsing; in a store they appear as a message such
as `Liquid syntax error (line 3): Unexpected character =` and strict parsing now rejects more of them. Runtime errors happen while rendering a valid file and appear inline in the rendered text as `+Liquid error: ...+` with the
cause, for example `Liquid error: divided by 0`, `Liquid error: Could not find asset snippets/nope.liquid` or
`Liquid error: include usage is not allowed in this context` (all measured with Ruby Liquid 5.3.0, which prints no file or
line position; the Shopify messages quoted in the migration guide include `(line N)`). Often there is no error at all, only a wrong or empty output.

=== Wrong output without an error

[cols="3,4,4",options=header]
|===
|Symptom
|Cause
|Remedy

|Block printed for an empty setting or vendor
|The empty string is truthy.
|Test with `+!= blank+`, or give the value a fallback with `default`.

|`+{% if a and (b or c) %}+` fails, or a mixed condition gives a surprising result
|No parentheses; right-to-left evaluation.
|Nest `if` tags or assign intermediate booleans.

|A percentage shows `0` or a whole number
|`divided_by` with an integer divisor does integer division.
|Divide by a float (`+divided_by: 100.0+`) or multiply first.

|A price is 100 times too large
|Prices are integers in cents and were printed without `money`.
|Format with `money` or divide by 100.0 deliberately.

|The message shows `€0.00` or a bare number
|A formatting filter was chained after `t`.
|Format into a variable, then pass it as the argument.

|A variable keeps a value from a previous loop iteration
|`assign` is not block-scoped.
|Reassign at the top of the loop body, or use `capture` per iteration.

|A snippet shows defaults for everything
|`render` does not pass the caller's variables.
|Pass them as named arguments.

|`product` is empty inside a section on the home page
|The object only exists on its own template.
|Take the product from a setting of type `product`, or render the section on the product template.

|Only the first 50 items appear
|The 50-iteration limit of `for`.
|Wrap the array in `paginate`.

|`image_url` raises an error
|Neither `width` nor `height` was given.
|Pass at least one of them.

|A `+{% schema %}+` or `+{% stylesheet %}+` setting shows Liquid text
|Liquid is not evaluated there.
|Move the logic to the markup or a `style` tag.

|A block is matched by a literal `block.id`
|The ID is generated by Shopify and may change.
|Match on `block.type` or a setting.
|===

Source: https://shopify.dev/docs/api/liquid/basics[Shopify docs: Liquid basics]

If you test Liquid offline, know where the engines differ from Shopify. These differences were measured on 2026-10-27.

== Performance habits

Liquid runs on every uncached request, so the way you write it affects server response time. The measured and documented
points are:

* Fetch less. Put `paginate` with the page size you display around a loop and keep `limit`, instead of relying on `limit`
  alone, because `limit` does not reduce the data fetched.
* Keep loops small: 50 iterations per page is the cap, and a loop inside a loop multiplies the work. Theme Check reports
  high complexity (LiquidComplexity, maximum 120) and deep nesting (LiquidNestingDepth).
* Assign expensive lookups once to a variable and reuse it instead of repeating `product.metafields.custom.roast_date.value`.
* Prefer `render` to `include` so snippets stay isolated and cheap to reason about.
* Use `image_url` with explicit `width` and `height` so the layout does not shift
  (ImgWidthAndHeight); `asset_url` and `image_url` return CDN URLs.
* Do not parse or edit `content_for_header` (ContentForHeaderModification), and avoid remote assets (RemoteAsset) and
  manual preloads (AssetPreload) that duplicate what Shopify filters already do.

Source: https://shopify.dev/docs/storefronts/themes/best-practices/performance[Shopify docs: theme performance best practices]
