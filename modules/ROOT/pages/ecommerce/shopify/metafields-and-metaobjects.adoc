Shopify's data model is fixed: a product has a title, a vendor and up to three options, and nothing more. *Custom data*
is how a shop or an app adds the rest. A *metafield* is a typed value attached to an existing resource (a roast date on a
product, a membership date on a customer, a gift message on an order). A *metaobject* is a new record type that you
define yourself (a coffee origin with a name, a country, an altitude and a photo) and that products, pages or other
metaobjects can point to. This page was written against the Admin GraphQL API and Storefront API version *2026-10*,
Shopify CLI *5.0.0* (Node.js 22.12 or later) and Theme Check *3.31.0*, and every fact was checked on 2026-10-27. The
guides state no plan restriction for custom data; the only plan-dependent number is the count of merchant-owned
metaobject definitions, listed in <<limits,Limits>>.

The page covers ownership and namespaces, how to create, read, update and delete definitions and values, the
capabilities that switch on filtering, uniqueness and smart collections, the metaobject capabilities (draft and
published entries, translations, web pages), declarative definitions in `shopify.app.toml`, and every surface that reads
the data: Liquid, the Storefront API, Shopify Functions, checkout and customer account extensions, webhooks and
analytics. It builds on the xref:ecommerce/shopify/admin-graphql-api.adoc[Admin GraphQL API] page (versioning, cost,
pagination), the xref:ecommerce/shopify/apps-overview-and-scaffolding.adoc[Apps Overview and Scaffolding] page
(`shopify.app.toml`), the xref:ecommerce/shopify/authentication-and-access-scopes.adoc[Authentication and Access Scopes]
page (the scopes that custom data needs) and the xref:ecommerce/shopify/liquid-language.adoc[Liquid Language] page. The
running example is Pocket Coffee, a small specialty-coffee shop: a roast date, tasting notes and an origin on every
product, a Coffee Club tier that a Discount Function reads, a gift message that travels from the cart to the order, and
a member-since date on the customer.

Every GraphQL document on the page was validated against the public Admin and Storefront GraphQL schemas for 2026-10,
downloaded by introspection. The Liquid was checked with Theme Check, the Function was built and run with the Shopify
CLI, and the `shopify.app.toml` custom data was checked with a small offline script. Nothing was executed against a
Shopify store: that needs a store and an access token, and no account or credential was created. The section
<<what-was-run,What was run and what was not>> lists what each check covered.

== What custom data is

Metafields and metaobjects are both *custom data* stored in Shopify, queryable through the Admin API, renderable in themes, readable by Functions
and extensions, and editable by merchants in the Shopify admin when the definition allows it. They answer different
questions.

[cols="2,3,3",options="header"]
|===
| |Metafield |Metaobject

|What it is
|A typed key-value pair attached to an existing resource
|A record type that you define, with several typed fields, instantiated as many *entries*

|Use it when
|The data describes a product, variant, collection, customer, order, discount, shop or another Shopify resource
|The data does not belong to one resource, or is shared by many resources (an origin, a size chart, a store location)

|Identified by
|Namespace and key (`custom.roast_date`), plus the owner's ID
|Definition type (`origin`) and entry handle (`yirgacheffe`), plus the entry's ID

|Created from
|A *metafield definition* per owner type
|A *metaobject definition* with its field definitions

|Pocket Coffee example
|`custom.roast_date` on a product
|The `origin` definition with one entry per growing region
|===

Most data models use both: a metaobject defines the record and a *reference* metafield attaches it to the products it
applies to. The figure shows the model that the rest of the page builds.

image::ecommerce-shopify-custom-data-model.svg["Pocket Coffee custom data model: product, customer, order, discount and app installation metafields, the origin and club_tier metaobjects, and the surfaces that read them",width=760]

The model has two halves on purpose. The `custom` namespace and the `origin` metaobject are *merchant-owned*: store
staff and every installed app can edit them, and a theme can rely on them. The `$app` data (the Coffee Club tier, the
eligibility flag, the lot code, the gift message) is *app-owned*: only the Pocket Coffee app controls its structure.
Choosing which half a piece of data belongs to is the central design decision, and the next section explains the rules.

== Ownership and namespaces

A metafield's *namespace* groups related keys and prevents collisions. It also decides who owns the data. A metaobject
has no namespace; its definition *type* plays the same role. The prefix in the namespace or type is what encodes the
owner.

[cols="2,3,3,3",options="header"]
|===
|Owner |Namespace or type prefix |Who can change the definition |Who can change the values

|Merchant-owned
|Any name that does not start with `$app` and contains no `+--+`, such as `custom`, `specs` or `origin`
|The merchant and every installed app that has the scope
|The merchant and every installed app that has the scope

|App-owned
|`$app` or `$app:name` in the GraphQL API, `app` or a sub-namespace in `shopify.app.toml`; the stored form is `+app--<app id>+` or `+app--<app id>--name+`
|Only the owning app
|The owning app; merchants only if `access.admin` is `merchant_read_write`

|Shopify-reserved
|Namespaces and types that start with `+shopify--+`, and the standard definitions (`descriptors.subtitle`, `facts.isbn`, `product_review`)
|Shopify
|Usually merchant-owned values

|App-data (metafields only)
|Any namespace, on the `AppInstallation` resource
|The owning app
|The owning app; hidden from the Shopify admin and invisible to other apps
|===

Four rules follow from the table.

* *The `$app` shorthand is resolved for you in most places.* Shopify replaces `$app` with the stored `+app--<app id>+` in
Admin GraphQL input, in theme app extensions, in checkout and customer account extension configuration and in Function
input queries. Code that is not running as your app (the merchant's own theme, a headless storefront) uses the full
stored namespace, for example `+app--123456--club+`. Look the definition up with `metafieldDefinitions` to see the
namespace that Shopify stored.
* *`--` is reserved.* Since 2025-02-19 no new metafield namespace or metaobject type may contain two consecutive
hyphens, because the form is used for `+shopify--standard+` and `+app--<app id>+`. Existing definitions were left alone.
* *App-owned data stopped being public in 2025.* On 2025-05-19 Shopify converted every app-owned metafield and
metaobject that had `PUBLIC_READ` to `MERCHANT_READ` and `PUBLIC_READ_WRITE` to `MERCHANT_READ_WRITE`, in all API
versions. Data that another app must read has to move to a merchant-owned namespace such as `custom`.
* *App-owned does not mean secret.* Liquid reads any metafield regardless of its storefront access, and the merchant can
see app-owned metafields in the admin (read-only by default). Keep credentials in the app's own database or in
environment variables. Use an app-data metafield for per-installation configuration that the merchant must not see,
never for secrets.

=== Namespace and key syntax

The `MetafieldsSetInput` documentation of 2026-10 states that a namespace is 3 to 255 characters and a key is 2 to 64
characters, both made of letters, digits, hyphens and underscores. If `namespace` is omitted in `metafieldsSet`, the
app-reserved namespace is used. The Admin API and Liquid address a metafield as `namespace.key`; the search syntax
adds a prefix, `metafields.custom.roast_date`.

=== Standard definitions

Shopify publishes *standard metafield definitions* for common data (subtitle, ISBN, care instructions, ingredients) and
*standard metaobject definitions* (currently `product_review`, available to approved partners only). A standard
definition has a reserved namespace and key, a known type and preset access, does not count against the definition
limits, and is interoperable across themes and apps. List the templates with `standardMetafieldDefinitionTemplates`,
enable one with `standardMetafieldDefinitionEnable` (or `standardMetaobjectDefinitionEnable` with the type), or declare
it in `shopify.app.toml` with `standard_metafields = ["descriptors.subtitle", "facts.isbn"]` under
`[product.metafields]`. A standard metafield definition is also enabled automatically the first time a value is written
to its namespace and key. Once enabled, Shopify owns the schema while the values stay merchant-owned.

[source,graphql]
----
query ListStandardTemplates {
  standardMetafieldDefinitionTemplates(first: 25) {
    nodes {
      id
      namespace
      key
      name
      ownerTypes
      type {
        name
      }
    }
  }
}

mutation EnableSubtitle($id: ID!) {
  standardMetafieldDefinitionEnable(id: $id, ownerType: PRODUCT) {
    createdDefinition {
      id
      namespace
      key
    }
    userErrors {
      field
      message
      code
    }
  }
}
----

== Metafield definitions

A definition is the schema of a metafield: namespace, key, name, owner type, type, validations, access and capabilities.
Without one a metafield is an untyped string that merchants cannot edit with a typed editor, search or validate. Create
the definition before you write values.

=== The definition input

`metafieldDefinitionCreate` takes a `MetafieldDefinitionInput`. The fields of the 2026-10 schema are these.

[cols="2,1,4",options="header"]
|===
|Field |Required |Meaning

|`namespace`
|No
|Grouping and owner. Omitted: the app-reserved namespace. `$app` or `$app:sub` creates an app-owned definition.

|`key`
|Yes
|Identifier inside the namespace. Immutable.

|`name`
|Yes
|Label shown in the Shopify admin.

|`description`
|No
|Help text of the definition. The per-metafield `description` was removed from `MetafieldInput` in API 2025-07; read and write the description on the definition.

|`ownerType`
|Yes
|The resource, from the `MetafieldOwnerType` enum. Immutable.

|`type`
|Yes
|The data type name, for example `date` or `list.single_line_text_field`. Immutable through the API.

|`validations`
|No
|List of `{name, value}` rules; both are strings, see <<validations,Validations>>.

|`pin`
|No
|Pins the definition so that the admin shows its field first (50 pinned definitions per owner type).

|`access`
|No
|`admin`, `storefront` and `customerAccount`, see <<access,Access control>>.

|`constraints`
|No
|Applies the definition only to a subtype of the resource (a conditional definition): a `key` and the allowed `values`.

|`capabilities`
|No
|`adminFilterable`, `smartCollectionCondition`, `uniqueValues`, `analyticsQueryable`, `cartToOrderCopyable`, see <<capabilities,Capabilities>>.
|===

The `MetafieldOwnerType` enum of 2026-10 has 26 values: `API_PERMISSION`, `ARTICLE`, `BLOG`, `CARTTRANSFORM`,
`COLLECTION`, `COMPANY`, `COMPANY_LOCATION`, `CUSTOMER`, `DELIVERY_CUSTOMIZATION`, `DISCOUNT`, `DRAFTORDER`,
`FULFILLMENT_CONSTRAINT_RULE`, `GIFT_CARD_TRANSACTION`, `LOCATION`, `MARKET`, `MEDIA_IMAGE`, `ORDER`,
`ORDER_ROUTING_LOCATION_RULE`, `PAGE`, `PAYMENT_CUSTOMIZATION`, `PRODUCT`, `PRODUCTVARIANT`, `SELLING_PLAN`, `SHOP`,
`TRANSFER` (added for inventory transfers in 2026-07) and `VALIDATION`. There is no `CART` owner: cart metafields exist
on the Storefront API and in checkout, and are copied to order metafields when the order is created. App-data metafields
use the `AppInstallation` resource as owner and need no definition.

=== Create a merchant-owned definition

A definition in a namespace that is not reserved is merchant-owned. Pocket Coffee needs the roast date to be editable by
staff, readable by the theme and by a headless storefront, and filterable in the admin. The mutation takes the input as a
variable, which is how an app that lets merchants configure their own fields would call it.

[source,graphql]
----
mutation CreateRoastDateDefinition($definition: MetafieldDefinitionInput!) {
  metafieldDefinitionCreate(definition: $definition) {
    createdDefinition {
      id
      namespace
      key
      ownerType
      type {
        name
      }
      access {
        admin
        storefront
        customerAccount
      }
      capabilities {
        adminFilterable {
          enabled
        }
      }
    }
    userErrors {
      field
      message
      code
    }
  }
}
----

Variables:

[source,json]
----
{"definition":{"namespace":"custom","key":"roast_date","name":"Roast date","description":"Date the batch on sale was roasted","type":"date","ownerType":"PRODUCT","access":{"storefront":"PUBLIC_READ"},"capabilities":{"adminFilterable":{"enabled":true}}}}
----

Source: https://shopify.dev/docs/apps/build/metafields/definitions#graphql-admin-api-example[Manage metafield definitions, GraphQL Admin API example]

A merchant-owned definition cannot be declared in `shopify.app.toml`. The app needs the owner's scope: `write_products`
for product metafields, `write_customers` for customer metafields, `write_orders` for order metafields and so on.
Metaobject-reference types need the metaobject scopes too.

=== Create an app-owned definition with GraphQL

The same mutation with a `$app` namespace creates an app-owned definition. This one declares a lot code that must match
a pattern and be unique across products. Prefer `shopify.app.toml` for definitions that are the same in every shop (see
<<declarative,Declarative definitions>>); use GraphQL when the structure depends on what the merchant configures in your
app.

[source,graphql]
----
mutation CreateLotCodeDefinition {
  metafieldDefinitionCreate(
    definition: {
      namespace: "$app:roastery"
      key: "lot_code"
      name: "Lot code"
      description: "Internal lot identifier printed on the bag"
      type: "single_line_text_field"
      ownerType: PRODUCT
      access: { admin: MERCHANT_READ, storefront: NONE }
      validations: [{ name: "regex", value: "^LOT-[0-9]{6}$" }]
      capabilities: { uniqueValues: { enabled: true } }
    }
  ) {
    createdDefinition {
      id
      namespace
      key
    }
    userErrors {
      field
      message
      code
    }
  }
}
----

Source: https://shopify.dev/docs/apps/build/metafields/definitions#graphql-admin-api-example[Manage metafield definitions, GraphQL Admin API example]

=== Read definitions

`metafieldDefinitions` lists the definitions of one owner type, optionally filtered by namespace, key or a search
`query`. `metafieldDefinitionTypes` lists every type with the validations it supports and whether it supports definition
migrations. The `validationStatus` of a definition is `ALL_VALID`, `SOME_INVALID` or `IN_PROGRESS` after a validation
change, and `metafieldsCount` and `metafields(validationStatus:)` show how many values exist and how many break the rules.

[source,graphql]
----
query ListProductDefinitions {
  metafieldDefinitions(first: 50, ownerType: PRODUCT, namespace: "custom") {
    nodes {
      id
      namespace
      key
      name
      type {
        name
        category
      }
      access {
        admin
        storefront
      }
      validations {
        name
        value
      }
      metafieldsCount
    }
    pageInfo {
      hasNextPage
      endCursor
    }
  }
}

query FindOneDefinition {
  metafieldDefinitions(first: 1, ownerType: PRODUCT, namespace: "custom", key: "roast_date") {
    nodes {
      id
      validationStatus
      capabilities {
        adminFilterable {
          enabled
          eligible
        }
        smartCollectionCondition {
          enabled
        }
      }
    }
  }
}

query SupportedTypes {
  metafieldDefinitionTypes {
    name
    category
    supportedValidations {
      name
      type
    }
    supportsDefinitionMigrations
  }
}
----

Source: https://shopify.dev/docs/apps/build/metafields/definitions#reading-definitions[Manage metafield definitions, Reading definitions]

=== Update and delete

Only some parts of a definition can change after it is created.

[cols="2,1,3",options="header"]
|===
|Part |Can change |Notes

|Name and description |Yes |`name`, `description`
|Validations |Yes, with limits |Tightening a rule is accepted, but existing values that break it become invalid (see `validationStatus`)
|Access |Yes |`access` in `MetafieldDefinitionUpdateInput`; apps can also change access of merchant-owned definitions (since 2024-12-11)
|Capabilities |Yes |A capability that is switched on can often not be switched off again (`CAPABILITY_CANNOT_BE_DISABLED`)
|Namespace and key |No |Create a new definition, copy the values, switch the readers, delete the old one
|Owner type |No |Same migration
|Type |No through the API |`MetafieldDefinitionUpdateInput` has no `type`; the data types guide documents type migrations in the admin for the types whose `supportsDefinitionMigrations` is true, and a migration between incompatible types invalidates the values
|===

Update takes the owner type, namespace and key (there is no `id` argument in 2026-10), and delete takes the
definition's ID. `deleteAllAssociatedMetafields: true` deletes the values with the definition; `false` keeps them as
untyped metafields.

[source,graphql]
----
mutation WidenStorefrontAccess {
  metafieldDefinitionUpdate(
    definition: {
      namespace: "custom"
      key: "roast_date"
      ownerType: PRODUCT
      access: { storefront: PUBLIC_READ }
      capabilities: { adminFilterable: { enabled: true } }
    }
  ) {
    updatedDefinition {
      id
      access {
        storefront
      }
    }
    userErrors {
      field
      message
      code
    }
  }
}

mutation RemoveDefinition($id: ID!) {
  metafieldDefinitionDelete(id: $id, deleteAllAssociatedMetafields: false) {
    deletedDefinitionId
    userErrors {
      field
      message
      code
    }
  }
}
----

Source: https://shopify.dev/docs/apps/build/metafields/definitions#updating-definitions[Manage metafield definitions, Updating definitions]

A definition that is declared in `shopify.app.toml` is read-only through the API: the mutation returns an error with the
code `APP_CONFIG_MANAGED`. Change it in the file and deploy.

=== What happens on uninstall

When a merchant uninstalls the app, Shopify deletes its app-owned definitions, whether they came from TOML or from
GraphQL, and keeps the values without a definition for an unspecified time while cleanup runs asynchronously. If the app
is reinstalled before cleanup, the definitions are recreated and the values reattached. TOML definitions are deleted and
recreated with new GIDs; GraphQL definitions can outlive the uninstall until cleanup removes them. Shopify does not
guarantee the retention period, and a definition ID is not a stable identifier across an uninstall: look definitions up
by owner type, namespace and key. The same applies to a definition you remove from the TOML file and deploy: the values
are retained for a short period and are reattached, with a new GID, if you add the definition back before cleanup.

[[types]]
== Data types

Metafields and metaobject fields share the same type system. A value is always stored and exchanged as a *string*, even
for numbers and booleans; a structured value is a JSON string. The type decides how the value is validated, how the admin
edits it and what object Liquid returns.

[cols="2,4,2",options="header"]
|===
|Group |Types |Value format

|Text
|`single_line_text_field`, `multi_line_text_field`, `rich_text_field`, `url`, `link`, `language`, `color`, `id`
|A string; `rich_text_field` and `link` are JSON; `color` is `#fff123`; `id` is a unique string

|Numbers and booleans
|`number_integer` (absolute value up to 9,007,199,254,740,991), `number_decimal` (absolute value up to 9999999999999.999999999), `boolean`, `rating`
|`"42"`, `"4.25"`, `"true"`; `rating` is JSON with scale and value

|Dates
|`date`, `date_time`
|ISO 8601 without a presumed time zone (`2026-10-20`, `2024-01-01T12:30:00`)

|Money
|`money`
|JSON `{"amount": "5.99", "currency_code": "EUR"}`; market-localizable, not translatable

|Measurements
|`weight`, `volume`, `dimension`, `distance`, `area`, `duration`, `energy`, `power`, `temperature`, `speed`, `pressure`, `resolution`, `frequency`, `voltage`, `electric_current` and more
|JSON `{"value": 25.0, "unit": "centimeters"}`; each type has its own unit list

|JSON
|`json`
|Any JSON-serializable value, passed as a string

|References
|`product_reference`, `variant_reference`, `collection_reference`, `page_reference`, `article_reference`, `customer_reference`, `company_reference`, `order_reference`, `file_reference`, `metaobject_reference`, `mixed_reference`, `product_taxonomy_value_reference`
|A GID, for example `gid://shopify/Metaobject/2001`

|Lists
|`list.` followed by any basic or reference type, except `boolean`, `id`, `json`, `language`, `money`, `multi_line_text_field` and `rich_text_field`
|A JSON array in a string, for example `["jasmine","bergamot","honey"]`
|===

The guide lists 48 basic types in total, plus the reference and list types; `metafieldDefinitionTypes` returns the authoritative list for the API
version you call. A `file_reference` defaults to a generic file and can be restricted to images or videos with the
`file_type_options` validation. A `metaobject_reference` can be restricted to one definition, and a `mixed_reference` to
a set of definitions. Deleting a product or variant removes it from every list metafield that references it. `integer`,
`json_string` and `string` are older, deprecated types that Liquid still returns as plain values.

=== Size limits

Most types are limited to 64 KB (65,536 bytes). The exceptions are `id` and `url` (2 KB each) and `json` (128 KB). Since
API version 2026-04, writes of JSON values are limited to 128 KB; apps that already used JSON metafields before
2026-04-01 keep the previous 2 MB limit, and new apps that need more can ask for an exception. Large values already
stored stay readable in every version. A list holds at most 128 items (1,024 for metaobject references), and each item
obeys the size limit of its single type. Shopify Functions input queries do not return metafield values larger than
10,000 bytes: the value is stored and the Admin API returns it, but the Function receives `null`.

=== Validations

Validations constrain what a definition accepts. In GraphQL each is a `{name, value}` pair of strings; in TOML they are
keys under `validations`.

[cols="2,2,2,3",options="header"]
|===
|Validation |GraphQL name |Applies to |TOML

|Minimum and maximum length
|`min`, `max`
|`single_line_text_field`, `multi_line_text_field`
|`validations.min = 8`

|Regular expression (RE2)
|`regex`
|text types
|`+validations.regex = "^LOT-[0-9]{6}$"+`

|Allowed domains
|`allowed_domains`
|`url`
|`validations.allowed_domains = ["example.com"]`

|Choices (up to 128)
|`choices`
|`single_line_text_field`
|`validations.choices = ["Floral", "Sweet"]`

|File types
|`file_type_options`
|`file_reference`
|`validations.file_type_options = ["Image"]`

|Precision
|`max_precision`
|`number_decimal`
|`validations.max_precision = 2`

|Range of numbers
|`min`, `max`
|`number_integer`, `number_decimal`
|`validations.min = 0.5`

|Range of dates
|`min`, `max`
|`date`, `date_time`
|`validations.min = "2022-01-01"`

|Range of measurements
|`min`, `max`
|`weight`, `volume`, `dimension`
|`validations.min = { unit = "g", value = 10 }`

|Referenced definition
|`metaobject_definition_id`, `metaobject_definition_ids`, `metaobject_definition_type`
|`metaobject_reference`, `mixed_reference`
|Not needed: the type shorthand `metaobject_reference<$app:origin>` carries it

|JSON schema
|`schema`
|`json`
|`validations.schema = '{"type":"object"}'`

|List length
|`list.min`, `list.max`
|any list type
|`[product.metafields.app.tags.validations]` with `"list.max" = 6`
|===

[[access]]
=== Access control

The `access` block of a definition says who may read and write the values.

[cols="2,3,3,3",options="header"]
|===
|Surface |Setting (GraphQL / TOML) |Values and default |Effect

|Admin and Admin API
|`access.admin`: `MERCHANT_READ`, `MERCHANT_READ_WRITE` / `merchant_read`, `merchant_read_write`
|App-owned: `MERCHANT_READ`. Merchant-owned: always full access, no setting
|Whether merchants can edit the values in the admin. The owning app can always read and write.

|Storefront API
|`access.storefront`: `NONE`, `PUBLIC_READ` / `none`, `public_read`
|`NONE`
|Whether the Storefront API returns the value. It does not affect Liquid, which always reads the metafield.

|Customer Account API
|`access.customerAccount`: `NONE`, `READ`, `READ_WRITE` / `access.customer_account`: `none`, `read`, `read_write`
|`NONE`
|Whether customer account UI extensions and the Customer Account API can read or write the value
|===

Since 2026-06-16 a metafield on the app resource needs a definition with customer-account access to be returned by the
Customer Account API; metafields owned by customers and orders were not affected. The documentation adds that, for
merchant-owned metafields, the Customer Account API access can be changed only in the Shopify admin. The enum values
`PRIVATE`, `PUBLIC_READ` and `PUBLIC_READ_WRITE` of the admin access still exist in the schema for reading old data but
are never returned for metaobjects and cannot be set.

Source: https://shopify.dev/docs/apps/build/metafields#permissions[About metafields, Permissions]

[[capabilities]]
=== Capabilities

Capabilities switch on optional behaviour for a definition.

[cols="2,3,3,2",options="header"]
|===
|Capability |What it does |Limits and notes |In TOML

|`adminFilterable`
|Lets the admin and the Admin API filter products, orders, companies, company locations and metaobjects by the value
|Not for `json` and `rich_text_field`. 50 filterable definitions per owner type (5 for orders). Companies and locations do not support numeric and date filters.
|`capabilities.admin_filterable`

|`smartCollectionCondition`
|Lets an automated collection use the metafield as a rule. Supported for boolean, integer, decimal, rating, single-line text and metaobject reference (`equals`, and greater or less than for numbers).
|128 definitions per shop can power smart collections
|Not supported

|`uniqueValues`
|Rejects a value already used by another resource. Meant for ERP, PIM or CRM identifiers.
|`single_line_text_field`, `url`, `number_integer`. The `id` type is unique by design.
|`capabilities.unique_values`

|`cartToOrderCopyable`
|Copies a cart metafield to the order metafield with the same namespace and key when the order is created
|Order definitions only

`metafieldsSet` has a dynamic cost since 2026-09-15: `10 + sum(distinct owners of a type * weight of that type)`, with
weights of 10 for orders, 4 for products, 2 for variants and 1 for collections, customers and the shop. Setting two
metafields on one product, one on another product and one on a variant costs `10 + 2*4 + 1*2 = 20`. Cost is charged per
mutation invocation, so aliases do not share the base cost, and putting all metafields of a resource in one call is the
cheapest way to write them.

== Writing metafield values

A value is written either on the resource's own mutation, or on its own with `metafieldsSet`. Use `metafieldsSet` for
anything that is not part of creating or editing the resource.

=== metafieldsSet

`metafieldsSet` creates or updates up to 25 metafields in one atomic call: if one is invalid, none is saved. Each entry
has an `ownerId`, a `namespace` (default: the app-reserved one), a `key`, a `value` string and a `type`. The `type` is
optional when a definition exists and required otherwise. `compareDigest` turns the call into a compare-and-set: it is
applied only if the stored value still matches the digest you read earlier, and `null` means "only if it does not exist
yet".

[source,graphql]
----
mutation SetRoastMetafields($metafields: [MetafieldsSetInput!]!) {
  metafieldsSet(metafields: $metafields) {
    metafields {
      id
      namespace
      key
      type
      value
      compareDigest
    }
    userErrors {
      field
      message
      code
      elementIndex
    }
  }
}
----

Variables for a Pocket Coffee batch, including a reference to a metaobject entry, a list and an app-owned boolean:

{"metafields":[{"ownerId":"gid://shopify/Product/1234567890","namespace":"custom","key":"roast_date","type":"date","value":"2026-10-20"},{"ownerId":"gid://shopify/Product/1234567890","namespace":"custom","key":"origin","type":"metaobject_reference","value":"gid://shopify/Metaobject/2001"},{"ownerId":"gid://shopify/Product/1234567890","namespace":"custom","key":"tasting_notes","type":"list.single_line_text_field","value":"[\"jasmine\",\"bergamot\",\"honey\"]"},{"ownerId":"gid://shopify/Product/1234567890","namespace":"$app:club","key":"eligible","type":"boolean","value":"true"}]}

=== Read, delete and optimistic updates

Read a metafield through its owner: `metafield(namespace:, key:)` for one, `metafields(namespace:, first:)` for a
connection. `value` is always a string; `jsonValue` parses it for you, and `reference` and `references` resolve
reference types in the same request. `compareDigest` is what you pass back to `metafieldsSet`. `metafieldsDelete` removes
specific values and keeps the resource; deleting the resource deletes its metafields.

[source,graphql]
----
query ReadProductMetafields($id: ID!) {
  product(id: $id) {
    title
    roastDate: metafield(namespace: "custom", key: "roast_date") {
      value
      type
      jsonValue
      compareDigest
      definition {
        id
        name
      }
    }
    origin: metafield(namespace: "custom", key: "origin") {
      reference {
        ... on Metaobject {
          id
          handle
          displayName
          name: field(key: "name") {
            value
          }
        }
      }
    }
    notes: metafield(namespace: "custom", key: "tasting_notes") {
      jsonValue
    }
    tier: metafield(namespace: "$app:club", key: "tier") {
      reference {
        ... on Metaobject {
          label: field(key: "label") {
            value
          }
          discount: field(key: "discount_percent") {
            value
          }
        }
      }
    }
    custom: metafields(first: 20, namespace: "custom") {
      nodes {
        key
        type
        value
      }
    }
  }
}

== Querying by metafield value

Products, orders, companies, company locations and metaobjects can be filtered by a metafield value in the `query`
argument of their connection. The definition must have `adminFilterable` switched on; since API version 2026-10 a query
that filters by a metafield without a definition, without the capability, or with a comparison that the type does not
support returns an error. Earlier versions silently ignored the invalid predicate and returned unfiltered results.

The filter is `metafields.<namespace>.<key>:<value>` for resources and `fields.<key>:<value>` for metaobjects. The
syntax follows the general search syntax of the Admin API.

[cols="2,4,3",options="header"]
|===
|Pattern |Example |Notes

|Exact match
|`metafields.custom.color:"blue"`
|Case-sensitive for text; quote the value

|Prefix match
|`metafields.custom.lapel_style:notch*`
|Text types

|Exists, does not exist
|`metafields.custom.color:*`, `-metafields.custom.color:*`
|

|Negation
|`-metafields.custom.color:"blue"`, `NOT`
|

|Ranges
|`metafields.custom.roast_date:>=2026-10-01`
|Numbers, dates and measurements (`>=1kg`, `<2000g`; units are converted)

|Boolean
|`metafields.custom.eco_friendly:true`
|No quotes

|Reference
|`metafields.custom.origin:"gid://shopify/Metaobject/2001"`
|Full GID

|List value
|`metafields.custom.tasting_notes:"honey"`
|Matches if any item matches

|Combination
|`A AND B`, `A OR B`
|Also across different metafields

|App-owned
|`metafields.$app.weight_field:>=1kg`, `metafields.$app\:club.eligible:true`
|The `$app` shorthand works in queries since 2025-01-22; escape the colon of a sub-namespace with a backslash (`\\:` inside a GraphQL string)
|===

The query string is a GraphQL string, so quotes inside it are escaped. The variable keeps it readable.

[source,graphql]
----
query FreshBatches($query: String!) {
  products(first: 20, query: $query) {
    nodes {
      id
      title
      roastDate: metafield(namespace: "custom", key: "roast_date") {
        value
      }
    }
  }
}
----

Variables for "beans roasted in October 2026 from Colombia":

[source,json]
----
{
  "query": "metafields.custom.roast_date:>=2026-10-01 AND metafields.custom.origin_country:\"Colombia\""
}
----

Source: https://shopify.dev/docs/apps/build/metafields/query-using-metafields[Query using metafields]

== Metaobject definitions

A metaobject definition has a `type` (immutable, unique in its owner's scope), optional `name` and `description`, a list of
field definitions, an access block, a `displayNameKey` (the field whose value becomes the entry's display name and
handle), and capabilities. Field definitions have a `key`, a `type` from the same type system, a `name`, a
`description`, `required` and validations. Since 2026-04 `fieldDefinitions` is optional in `metaobjectDefinitionCreate`,
so a definition can start empty.

The admin access of a metaobject definition is `MERCHANT_READ` or `MERCHANT_READ_WRITE` (app-owned only; merchant-owned
types are always fully editable) and the storefront access is `NONE` or `PUBLIC_READ`. A merchant-owned `origin` type
needs the `read_metaobject_definitions` and `write_metaobject_definitions` scopes to create, and `read_metaobjects` and
`write_metaobjects` to manage entries. Since API version 2026-04 an app needs no scope at all for its own `$app:` types.

[source,graphql]
----
mutation CreateOriginDefinition {
  metaobjectDefinitionCreate(
    definition: {
      type: "origin"
      name: "Origin"
      description: "A growing region Pocket Coffee sources beans from"
      displayNameKey: "name"
      access: { storefront: PUBLIC_READ }
      capabilities: {
        publishable: { enabled: true }
        translatable: { enabled: true }
        renderable: { enabled: true, data: { metaTitleKey: "name", metaDescriptionKey: "country" } }
        onlineStore: { enabled: true, data: { urlHandle: "origins" } }
      }
      fieldDefinitions: [
        { key: "name", name: "Name", type: "single_line_text_field", required: true }
        {
          key: "country"
          name: "Country"
          type: "single_line_text_field"
          required: true
          validations: [{ name: "choices", value: "[\"Ethiopia\",\"Colombia\",\"Brazil\"]" }]
        }
        {
          key: "altitude_m"
          name: "Altitude (m)"
          type: "number_integer"
          validations: [{ name: "min", value: "0" }, { name: "max", value: "3000" }]
        }
        { key: "story", name: "Story", type: "rich_text_field" }
        {
          key: "photo"
          name: "Photo"
          type: "file_reference"
          validations: [{ name: "file_type_options", value: "[\"Image\"]" }]
        }
      ]
    }
  ) {
    metaobjectDefinition {
      id
      type
      displayNameKey
      fieldDefinitions {
        key
        required
        type {
          name
        }
      }
      capabilities {
        publishable {
          enabled
        }
        onlineStore {
          enabled
          data {
            urlHandle
          }
        }
      }

      field
      message
      code
    }

=== Metaobject capabilities

[cols="2,4,3",options="header"]
|===
|Capability |Effect |TOML

|`publishable`
|Entries have a status, `DRAFT` (the default for new entries) or `ACTIVE`. Liquid and the Storefront API return only active entries.
|`capabilities.publishable`

|`translatable`
|The fields can be translated with `translationsRegister` after reading `translatableResources(resourceType: METAOBJECT)` for the digests
|`capabilities.translatable`

|`renderable`
|Exposes SEO title and description, taken from the fields named in `metaTitleKey` and `metaDescriptionKey`, to Liquid and the Storefront API, and adds the entries to the sitemap
|`capabilities.renderable` (the CLI importer writes `renderable_meta_title_field` and `renderable_meta_description_field` next to it)

|`onlineStore`
|Gives the definition a URL handle and a theme template, so each entry becomes a page at `/pages/<urlHandle>/<entry handle>`
|Not supported

|`analyticsQueryable`
|Makes the fields available to analytics. Needs API version 2027-01 or later and at least one field of a compatible type, otherwise `CAPABILITY_NOT_ELIGIBLE`.
|`capabilities.analytics_queryable` (since 2026-10-20)
|===

== Metaobject entries

An entry has an `id`, a `handle` (generated from the display name, or chosen), a `displayName`, its field values and its
capability states. `metaobjectCreate` and `metaobjectUpdate` take `fields` (a list of key and string value, patch
semantics: unspecified fields are left as they are) or `values` (announced on 2026-06-11 and present in 2026-10), a JSON object keyed by field key, where
omitted fields are cleared. `metaobjectUpsert` creates or updates by handle. The type of an entry cannot change.

Creating thousands of entries one by one is slow. Use `bulkOperationRunMutation` with `metaobjectCreate`,
`metaobjectUpdate` or `metaobjectDelete` and a JSONL file of variables, as described on the
xref:ecommerce/shopify/bulk-operations.adoc[Bulk Operations] page; `metaobjectBulkDelete` deletes many entries in one
call. Deleting a definition deletes all its entries, and the metafield definitions that point to it, asynchronously.

=== Metaobject limits

Each definition can hold 1,000,000 entries (the plan-based limits of 64,000 and 128,000 were removed in 2025-10). A list
metafield can reference up to 1,024 entries. Liquid imposes its own, much lower, limits per page render, listed in
<<liquid-limits,Liquid limits>>.

=== Webhooks for metaobjects and definitions

The topics `metaobjects/create`, `metaobjects/update` and `metaobjects/delete` require a filter of the form `type:<type>`
(several types are joined with `OR`, wildcards are not supported). For an app-owned definition the filter must use the
stored form `+app--<app id>--<name>+`, not the `$app:` shorthand. Metafield definition changes have the topics
`metafield_definitions/create`, `metafield_definitions/update` and `metafield_definitions/delete`. Since 2026-07-21 Events
subscriptions can also trigger on changes to specific metafields of products, orders, customers, collections and
locations, for both `$app` and merchant-owned metafields.

[source,toml]
----
[webhooks]
api_version = "2026-10"

  [[webhooks.subscriptions]]
  topics = ["metaobjects/update"]
  uri = "/webhooks/metaobjects/update"
  filter = "type:app--123456--club_tier"
----

== Declarative definitions in shopify.app.toml

Definitions that are the same in every shop belong in the app's configuration file. The CLI sends them with
`shopify app deploy`, Shopify creates or updates them in every shop where the app is installed, and `shopify app dev`
tests them on the development store first. The definitions are version-controlled with the app, roll out atomically with
the app version and cannot be edited through the API.

=== Syntax

A metafield is declared as `[<owner>.metafields.<namespace>.<key>]` and a metaobject as
`[metaobjects.app.<name>]` with `[metaobjects.app.<name>.fields.<key>]` tables for its fields. The owner is the
snake-case form of the owner type: `product`, `product_variant`, `customer` and `order` in the guides; the other owner types follow the enum names in lower case. The namespace segment `app` means `$app`; any other segment creates a sub-namespace of the app, so
`[product.metafields.club.eligible]` declares `$app:club` and `eligible`, which is stored as `+app--<app id>--club+`.
Only app-owned definitions can be declared in TOML; the file cannot create `custom` or other merchant-owned ones.

[cols="2,5",options="header"]
|===
|Property |Meaning

|`name`, `description`
|Label and help text in the admin

|`type`
|A data type. For references to metaobjects use the shorthand that embeds the target: `metaobject_reference<$app:club_tier>`, `list.metaobject_reference<$app:club_tier>`, `mixed_reference<$app:author, $app:publisher>`

|`access.admin`, `access.storefront`, `access.customer_account`
|`merchant_read` or `merchant_read_write`; `none` or `public_read`; `none`, `read` or `read_write`

|`capabilities.*`
|`admin_filterable`, `unique_values`, `cart_to_order_copyable`, `analytics_queryable`; for metaobjects `publishable`, `translatable`, `renderable`

|`validations.*`
|The names of the validations table, as dotted keys (`validations.max = 40`) or a `validations` table for names with a dot (`"list.max" = 6`)

|`display_name_field` (metaobject)
|The field that supplies the display name and handle

|`required` (metaobject field)
|The field must have a value
|===

=== The Pocket Coffee definitions

This file declares the Coffee Club tier metaobject, the product, customer and order metafields that the Function, the
theme app extension and checkout use, and the unique lot code. It also needs the scopes of the owner types it touches.

display_name_field = "label"

type = "single_line_text_field"
required = true
validations.max = 40

[metaobjects.app.club_tier.fields.discount_percent]

[metaobjects.app.club_tier.fields.free_shipping_from]

Deploy with `shopify app deploy`. Remove a block and deploy again to delete the definition; the values are kept for a
short period and reattached if the block comes back.

=== Constraints

* Only app-owned definitions can be declared, so that Shopify can guarantee the same state in every shop.
* At most 25 definition changes (create, update or delete) per deploy. The guide does not say whether each field of a
metaobject counts as a change, so deploy large schemas in several versions.
* Declared definitions are read-only through the Admin API (`APP_CONFIG_MANAGED`).
* `smartCollectionCondition`, `pin` and the `onlineStore` metaobject capability cannot be declared in TOML.
* The definitions are distributed to all installations, including shops that never use the feature; keep the count low.

=== Migrating existing definitions

`shopify app import custom-data-definitions` (announced on 2026-01-22 as `import-custom-data-definitions` for CLI 3.89; CLI 5.0.0 lists it with a space) reads the
app-owned definitions of a development store, such as `$app` metafields and `$app:` metaobject types, and prints the
equivalent TOML without writing a file. Review it, copy it into `shopify.app.toml`, run `shopify app dev` to test and
`shopify app deploy` to distribute, then delete the code that created the definitions at runtime. Values keep working
unchanged. The command needs a development store and a login, so it was not run here; its `--help` was read.

=== An offline check before deploy

`shopify app build --no-input` validates the app configuration, but it does not look inside the custom data tables:
a misspelled access value, a reference to a metaobject that is not declared, a missing name, an unknown type and an
unknown owner are all accepted, and Shopify rejects them only at deploy. A short script catches the common mistakes earlier. It parses the TOML (`npm i smol-toml`),
resolves `$app:` references against the declared metaobjects, checks the access values, the owner of
`cart_to_order_copyable`, the display field, the counts of the limits table, and prints the namespace that each
declaration resolves to. It does not know the list of types or owner types, which Shopify validates on deploy.

[source,js]
----
// Offline pre-deploy lint for declarative custom data in shopify.app.toml.
// Usage: node check-custom-data.mjs shopify.app.toml
import {readFileSync} from 'node:fs';
import {parse} from 'smol-toml';

const toml = parse(readFileSync(process.argv[2], 'utf8'));
const errors = [];
const err = (where, msg) => errors.push(`${where}: ${msg}`);

const ADMIN = ['merchant_read', 'merchant_read_write'];
const STOREFRONT = ['none', 'public_read'];
const CUSTOMER = ['none', 'read', 'read_write'];
const oneOf = (where, key, value, allowed) =>
  value === undefined || allowed.includes(value) || err(where, `${key} = "${value}" is not one of ${allowed.join(', ')}`);

const defined = new Set(Object.keys(toml.metaobjects?.app ?? {}));
const refs = (type) => [...String(type).matchAll(/\$app:([a-z0-9_-]+)/gi)].map((m) => m[1]);
const checkType = (where, type) => {
  if (!type) return err(where, 'missing type');
  for (const ref of refs(type)) defined.has(ref) || err(where, `type references $app:${ref}, which is not declared under [metaobjects.app]`);
};

let changes = 0;
for (const [owner, section] of Object.entries(toml)) {
  if (!section || typeof section !== 'object' || !section.metafields) continue;
  const {standard_metafields: standard = [], ...namespaces} = section.metafields;
  const entries = Object.entries(namespaces).flatMap(([ns, keys]) => Object.entries(keys).map(([key, d]) => [ns, key, d]));
  entries.length + standard.length > 128 && err(`[${owner}.metafields]`, `${entries.length + standard.length} definitions, the limit is 128 per owner type`);
  for (const [ns, key, d] of entries) {
    const where = `[${owner}.metafields.${ns}.${key}]`;
    console.log(where + ' -> ' + (ns === 'app' ? '$app' : '$app:' + ns) + '.' + key);
    changes++;
    d.name || err(where, 'missing name');
    checkType(where, d.type);
    oneOf(where, 'access.admin', d.access?.admin, ADMIN);
    oneOf(where, 'access.storefront', d.access?.storefront, STOREFRONT);
    oneOf(where, 'access.customer_account', d.access?.customer_account, CUSTOMER);
    d.capabilities?.cart_to_order_copyable && owner !== 'order' && err(where, 'cart_to_order_copyable only applies to order definitions');
  }
}

const objects = Object.entries(toml.metaobjects?.app ?? {});
objects.length > 32 && err('[metaobjects.app]', `${objects.length} definitions, the TOML limit is 32`);
for (const [name, d] of objects) {
  const where = `[metaobjects.app.${name}]`;
  changes += 1;
  const fields = Object.entries(d.fields ?? {});
  fields.length > 64 && err(where, `${fields.length} fields, the TOML limit is 64`);
  oneOf(where, 'access.admin', d.access?.admin, ADMIN);
  oneOf(where, 'access.storefront', d.access?.storefront, STOREFRONT);
  d.display_name_field && !d.fields?.[d.display_name_field] && err(where, `display_name_field "${d.display_name_field}" is not a declared field`);
  for (const [key, f] of fields) checkType(`${where}.fields.${key}`, f.type);
}

changes > 25 && err('deploy', `${changes} definitions in one file; a deploy may change at most 25 (create, update, delete) definitions`);
errors.forEach((e) => console.log('ERROR', e));
console.log(errors.length ? `${errors.length} problem(s)` : `ok: ${changes} definition(s) checked`);
process.exit(errors.length ? 1 : 0);
----

Source: https://shopify.dev/docs/apps/build/metafields/definitions#toml-limitations[Manage metafield definitions, TOML limitations]

== Reading custom data in Liquid

Liquid is the one surface that reads every metafield and every published metaobject entry regardless of the storefront
access setting. A theme cannot create or change them: Liquid is read-only, and values are written by the admin or by an
app. The Liquid reference describes the objects; this section collects the rules that cause most bugs.

=== The metafield object

A resource's `metafields` property takes a namespace and then a key: `{{ product.metafields.custom.roast_date }}`. The
result is a *metafield object* with three properties, `value`, `type` and `list?`, and it is `nil` when no value is set,
so test it with `blank` and not with the value. Always read `.value` explicitly so that the code states what it expects.

[cols="3,4",options="header"]
|===
|Metafield type |`value` returns

|`single_line_text_field`, `multi_line_text_field`, `url`
|A string

|`rich_text_field`
|A rich text structure (render it with `metafield_tag`)

|`number_integer`, `number_decimal`
|A number

|`date`, `date_time`
|A date string; format it with the `date` filter

|`boolean`
|A boolean

|`json`
|A JSON object that you can read by property name or index, and loop over

|`color`
|A color object

|`weight`, `volume`, `dimension`
|A measurement object

|`rating`
|A rating object

|`money`
|A money object in the customer's presentment currency

|`product_reference`, `collection_reference`, `variant_reference`, `page_reference`
|The product, collection, variant or page object

|`file_reference`
|A media object (images and videos) or a generic file object

|`metaobject_reference`
|A metaobject object whose fields are read as `origin.name.value`

|Any `list.` type
|An array; reference lists loop over objects
|===

Source: https://shopify.dev/docs/api/liquid/objects/metafield[Liquid objects: metafield]

Three details cause most of the confusion.

* *Lists have two ways to count.* Reference lists expose `.count`; non-reference lists are plain arrays and use the `size`
filter. A loop over a reference list returns only the first 50 items; wrap the loop in `paginate` (up to 250 per page)
to reach more.
* *`size`, `first` and `last` are also filters.* With dot notation, `product.metafields.custom.size` returns the number of
metafields in the namespace when no metafield is called `size`. Use brackets, `product.metafields.custom["size"]`, which
always looks the key up.
* *Metafields without a type return `"string"`* since 2024-10-28 (`metafield.type == blank` no longer matches), and the
deprecated `integer`, `json_string` and `string` types return plain values without the `value` and `type` properties.

=== Filters that render a metafield

`metafield_tag` generates an element for the metafield: a `<time>` for dates, a `<span>` for numbers and text, an `<a>` for
URLs and references, a `<div>` for rich text, a `<script type="application/json">` for JSON, an `<img>` or `<video>` for
files, and so on, each with a class such as `metafield-date`. `metafield_text` returns plain text (the title of a
referenced product, the URL of a file, the number). Neither supports every list type: both handle
`list.single_line_text_field` and `list.metaobject_reference` only. Dates are localized to the visitor.

Source: https://shopify.dev/docs/api/liquid/filters/metafield_tag[metafield_tag]

=== Metaobjects in Liquid

The global `metaobjects` object gives access to published entries by type and handle:
`+{{ metaobjects.origin.yirgacheffe.name.value }}+` or, with brackets,
`+{{ metaobjects['origin']['yirgacheffe'].name.value }}+`. An entry is reached through the field keys of its definition,
and each field is a metafield object (so `.value`, `.type`). The `system` property groups the built-in properties so that
they do not collide with field keys: `system.handle`, `system.id`, `system.type`, `system.template_suffix` and
`system.url` (the relative URL, set only when the definition has the online store capability).
`metaobjects.origin.values` loops over every entry of a definition, and `values_count` returns their number.
`shop.metaobjects` was the older path; it still works and has been deprecated since 2025-01-28.

When the `publishable` capability is on, a `DRAFT` entry is invisible: a direct lookup returns `nil` and loops skip it.
A metaobject definition whose entries are web pages (`renderable` and `onlineStore`) adds a template
`templates/metaobject/<type>.json` or `.liquid`; inside it the `metaobject` object is the entry being rendered, and
`metaobject.system.template_suffix` returns the alternate template assigned to an entry, or `nil`.

[[liquid-limits]]
=== Liquid limits

These limits apply to each page render. They are separate from the storage limits (a definition can hold a million
entries, but one page can load only some of them). Exceeding a per-type limit renders a Liquid error instead of the
entries.

[cols="4,1",options="header"]
|===
|Limit |Value

|Entries returned by a loop over `metaobject_definition.values` or over a `list.metaobject_reference` or `list.mixed_reference` metafield without `paginate`
|50

|Entries per page with the `paginate` tag
|250

|Unique entries of one metaobject type loaded per page render
|1,000

|Unique handles of one type looked up with `metaobjects.TYPE[handle]` per page render, including handles that match no published entry
|20

|Metaobject definitions reachable through the `metaobjects` object per page render
|50
|===

The `size` of a reference list and of `values` reports the real total, except that `values.size` and `values_count` stop at
25,001 for definitions with more than 25,000 entries. The 20-handle limit and the impossibility of paginating a lookup by
handle are the reasons to prefer `values` with `paginate` when you do not know the handles in advance.

Source: https://shopify.dev/docs/apps/build/metaobjects/metaobject-limits#liquid-limits[Metaobject limits, Liquid limits]

=== App-owned data in themes and extensions

The code that runs inside your own theme app extension can use the shorthand: `$app:sub` for a namespace or a metaobject
type, resolved to your app's reserved name. The merchant's theme cannot; it addresses the same data with the stored name
`+app--<app id>--sub+`. Which spelling to use depends on who owns the Liquid file.

[cols="3,4,3",options="header"]
|===
|Where the Liquid runs |App-owned metafield |App-owned metaobject

|Theme app extension (app block or app embed)
|`{{ product.metafields["$app:club"].tier.value }}`
|`shop.metaobjects["$app:club_tier"]["gold"]` (the reserved-prefix documentation still shows `shop.metaobjects`)

|The merchant's theme
|`+{{ product.metafields["app--123456--club"].tier.value }}+`
|`+metaobjects["app--123456--club_tier"].gold+`

|Any theme app extension, app-data metafield
|`{{ app.metafields.club.enabled }}`
|Not applicable
|===

Source: https://shopify.dev/docs/apps/build/online-store/theme-app-extensions/configuration#reserved-prefixes-for-metafields-and-metaobjects[Configure theme app extensions, Reserved prefixes]

An app block can hide itself until the app has finished a setup step: `available_if` in the block's schema takes a
reference to a *boolean app-data metafield*, and the block is rendered and offered in the theme editor only when the
value is true. The Pocket Coffee block below uses `{{ app.metafields.club.enabled }}`, written by the `SetAppDataMetafield`
mutation shown earlier.

A rule of thumb for safe data: store every value that your extension renders as markup, CSS or JavaScript in an
app-owned or app-data metafield, with `MERCHANT_READ` access. A public namespace such as `custom` can be changed by other
installed apps, by staff and collaborators who can edit the resource, and by translations (a translation of a
translatable metafield replaces what Liquid renders for that locale). Output every value through `escape` unless it is
already safe, and never put secrets in a metafield: Liquid reads them whatever the storefront access says. The app
security checks of the App Store report shared-namespace metafield values that reach HTML, JavaScript or URL output.

Source: https://shopify.dev/docs/apps/build/security/storefront/store-settings-in-app-owned-metafields[Store storefront settings where only your app can write them]

=== Theme settings and dynamic sources

A section or block setting of type `metaobject` opens a picker for entries of one definition (`metaobject_type` is
required); the value is a metaobject object, or `blank` when nothing is chosen or the entry is gone. `metaobject_list` is the
multiple version (`limit` defaults to and cannot exceed 50) and its value can be paginated. Custom definitions are not
allowed in themes that are listed in the Theme Store, which must use standard definitions; apps can use the settings with
their own app-owned definitions.

*Dynamic sources* let a merchant connect a section or block setting to a metafield in the theme editor, so the setting
follows the product (or collection, or page) being rendered. They are available for section and block settings only, not
for general theme settings. Theme blocks reach the nearest resource of a type through `closest`, for example
`closest.product`. Metaobjects with storefront visibility are available as dynamic sources in any setting, and market-
specific values (metafields and metaobjects that are localized per market) follow the market.

Source: https://shopify.dev/docs/storefronts/themes/architecture/settings/dynamic-sources[Dynamic data sources]

=== The Pocket Coffee theme code

The following files were added to a copy of the Skeleton theme (`shopify theme init` default). The roast date badge
reads the merchant-owned `custom.roast_date` and shows how fresh the beans are. `date` formats the stored ISO date,
`'now' | date: '%s'` gives the current Unix time, and the `floor` filter keeps the day count an integer whatever
the Liquid engine. `doc` documents the snippet's parameter so Theme Check validates calls to it.

[source,liquid,subs=-attributes]
----
{% doc %}
  Shows when a product was roasted, read from the merchant-owned
  custom.roast_date metafield (type date).

  @param {product} product - The product whose roast date is shown

  @example
  {% render 'roast-badge', product: product %}
{% enddoc %}

{%- assign roast_date = product.metafields.custom.roast_date -%}

{%- if roast_date != blank -%}
  {%- assign roasted_label = roast_date.value | date: '%-d %b %Y' -%}
  {%- assign roasted_at = roast_date.value | date: '%s' -%}
  {%- assign now_at = 'now' | date: '%s' -%}
  {%- assign age_days = now_at | minus: roasted_at | divided_by: 86400 | floor -%}

  <p class="roast-badge" data-age-days="{{ age_days }}">
    {{ 'products.roast.roasted_on' | t: date: roasted_label }}
    ({{ 'products.roast.days_ago' | t: count: age_days }})
  </p>
{%- endif -%}
----

Source: https://shopify.dev/docs/api/liquid/objects/metafield[Liquid objects: metafield]

== Reading custom data with the Storefront API

The Storefront API is for headless storefronts, apps in the buyer's browser and custom storefronts. It is read-only for
metafields (apart from cart metafields) and reads only what the definition exposes.

=== Exposing and reading

A metafield or metaobject is returned only when its definition has `access.storefront = PUBLIC_READ`. The separate
`metafieldStorefrontVisibilityCreate` mutation was removed in API version 2025-01; a metafield that was exposed with it
must have its definition created or updated with the access setting. Reading metafields and metaobjects needs a
Storefront access token: the tokenless access of 2026 covers products, collections, selling plans, search, pages, blogs,
articles and the cart, but not metafields, metaobjects, product tags or menus. Use the public token from a
browser or the private token from a server (with the buyer IP), as described on the
xref:ecommerce/shopify/storefront-api-and-headless-hydrogen.adoc[Storefront API and Headless with Hydrogen] page.

Resources that implement the `HasMetafields` interface have `metafield(namespace:, key:)` and
`metafields(identifiers: [{namespace:, key:}])`. The list form returns one slot per identifier, `null` in the slot of an identifier that has no
readable value, so the order of the response matches the order of the request. These types
implement it in 2026-10: `Article`, `Blog`, `Cart`, `Collection`, `Company`, `CompanyLocation`, `Customer`, `Location`,
`Market`, `Order`, `Page`, `Product`, `ProductVariant`, `SellingPlan` and `Shop`. A `Metafield` returns `value`, `type`,
`list`, `reference` and `references` (for reference types) and `parentResource`. The `reference` union can be an
`Article`, `Collection`, `GenericFile`, `MediaImage`, `Metaobject`, `Model3d`, `Page`, `Product`, `ProductVariant` or
`Video`.

Metaobjects have two root fields: `metaobject(handle: {type:, handle:})` or `metaobject(id:)`, and
`+metaobjects(type:, sortKey:, first:, after:, ...)+`. The Storefront API has no field filter for metaobjects: filter in the
Admin API or on the client. A `Metaobject` has `handle`, `type`, `fields`, `field(key:)`, `id`, `updatedAt`, and, for
definitions with the renderable and online store capabilities, `seo` and `onlineStoreUrl`. The `seo` title and
description are fields themselves, so they need a selection of `value`. Only active entries are returned when the
definition is publishable. The Storefront API accepts `@inContext(country:, language:)` to return the translation or the
market-specific value of a field.

[source,graphql]
----
query ProductWithCustomData($handle: String!) {
  product(handle: $handle) {
    title
    roastDate: metafield(namespace: "custom", key: "roast_date") {
      value
      type

    custom: metafields(
      identifiers: [
        { namespace: "custom", key: "roast_date" }

      key
      type
      value
      reference {
        ... on Metaobject {
          handle
          type

            value
          }

                image {
                  url(transform: { maxWidth: 480 })

                }
              }
            }
          }
        }
      }
      references(first: 6) {
        nodes {
          ... on Metaobject {
            handle
          }
        }
      }
    }
  }
}

=== Cart metafields

The cart is the one place where the Storefront API writes metafields. `cartCreate` accepts `metafields` in its input and
`cartMetafieldsSet` and `cartMetafieldDelete` change them, up to 25 per request. The `key` of these inputs is the
namespace and the key together, `custom.gift_message`. If the shop has an order metafield definition with the same
namespace and key and the `cartToOrderCopyable` capability, the value is copied to the order when it is created (since
API 2026-04). Cart metafields set through the Storefront API do not trigger Shopify Functions: the Functions see them
when the buyer goes to checkout or changes the cart. Checkout UI extensions read and write cart metafields too; checkout
metafields were removed from checkout and customer account UI extensions in API 2026-04.

=== Customer Account API

The Customer Account API reads and writes the metafields of the logged-in customer and their orders when the definition's

== Using custom data in Functions and extensions

=== Shopify Functions

A Function's input query can read the metafields of its *function owner* (a discount, a payment customization), of the
cart, its lines' products and variants, the customer, the shop and the delivery options, and, since API 2026-04, app-owned
metaobject entries by handle or ID through the `shop` field. The metaobject type must use the `$app` prefix;
merchant-owned types are not available. The input query is limited to 3,000 bytes, to a calculated cost of 30
(a `metafield` costs 3, a `metaobject` root 1, a `field(key:)` 3, any other leaf 1) and to values of at most 10,000 bytes.
Using a single `json` metafield for a complex configuration keeps both the query and the merchant interface simple, and
changing the shape of a configuration is safest as an expand-and-contract migration: read the old and the new metafield,
write both, migrate, then drop the old one.

The Coffee Club Discount Function reads a JSON configuration from the discount (created by the app with `metafields` on
`discountAutomaticAppCreate`) and the `$app:club.eligible` flag of each product, and discounts only eligible lines.

The Function (JavaScript, `@shopify/shopify_function`; the type `RunInput` is generated by `shopify app function typegen`
from the query and the schema of the target):

[source,js]
----
// @ts-check

/**
 * @typedef {import("../generated/api").RunInput} RunInput
 * @typedef {import("../generated/api").CartLinesDiscountsGenerateRunResult} CartLinesDiscountsGenerateRunResult
 */

/**
 * Applies the percentage stored in the discount's app-owned JSON metafield to
 * the cart lines whose product has the $app:club.eligible metafield set to true.
 * @param {RunInput} input
 * @returns {CartLinesDiscountsGenerateRunResult}
 */
export function run(input) {
  const config = input.discount.club?.jsonValue;
  if (!config || typeof config.percentage !== 'number') {
    return {operations: []};
  }

  const targets = input.cart.lines
    .filter((line) => 'product' in line.merchandise && line.merchandise.product.clubEligible?.value === 'true')
    .map((line) => ({cartLine: {id: line.id}}));

  if (targets.length === 0) {
    return {operations: []};
  }

  return {
    operations: [
      {
        productDiscountsAdd: {
          candidates: [
            {
              message: config.message ?? 'Coffee Club',
              targets,
              value: {percentage: {value: config.percentage}},
            },
          ],
          selectionStrategy: 'FIRST',
        },
      },
    ],
  };
}
----

=== Checkout and customer account UI extensions

An extension declares the metafields it needs in `shopify.extension.toml`: `[[extensions.metafields]]` for the whole
extension or `[[extensions.targeting.metafields]]` for one target, each with `namespace`, `key` and, since 2026-10,
`owner_type` (`CART`, `COMPANY`, `COMPANY_LOCATION`, `CUSTOMER`, `PRODUCT`, `PRODUCTVARIANT` or `SHOP`). `owner_type` is
optional in 2026-10 and required in 2027-01, when a deployment that omits it is blocked. An app-owned metafield is
requested with `namespace = "$app"` or `"$app:sub"`; the fully qualified `+app--<app id>+` form is not supported there,
and an extension can read only the app-owned metafields of its own app. The values arrive through `shopify.appMetafields`.
Checkout and customer account extensions can use cart metafields (checkout) and order metafields (customer accounts)
in place of the removed checkout metafields.

=== Events, webhooks and analytics

* *Webhooks:* metaobject topics need a `type:` filter, and metafield definition topics exist, as shown earlier.
* *Events:* an Events subscription can name the metafields that trigger it, `product.metafield(namespace: 'custom', key:
'roast_date').value`, and query the resource that changed. Both `$app` and merchant-owned metafields are supported
and the app must have access to the metafield.
* *Flow and admin extensions:* merchant automations and admin UI built on the same definitions are covered on the
xref:ecommerce/shopify/flow-pos-and-admin-extensions.adoc[Flow, POS and Admin Extensions] page.
* *Analytics:* a definition with the `analyticsQueryable` capability can be grouped and filtered in analytics reports and
ShopifyQL.
* *Translations and markets:* text types, `rich_text_field`, `json`, `link`, `url` and `file_reference` are translatable with
`translationsRegister`, and `money` and reference types such as products and pages can be localized per market with
`marketLocalizationsRegister`; Liquid and the Storefront API then return the value of the visitor's market and language.

== Modeling Pocket Coffee

A relational mental model maps cleanly onto Shopify's. A built-in resource is a table; a metafield definition is a column
added to it; a metaobject definition is a new table; an entry is a row; the GID is the primary key; a reference type is a
foreign key; validations and `required` are constraints; `shopify.app.toml` is the migration file.

[cols="2,3,3",options="header"]
|===
|Need |Choice |Reason

|Roast date, lot code, eligibility flag
|Metafield on the product
|Describes one product and is edited with it

|Where the beans come from
|Metaobject `origin` plus a `metaobject_reference` metafield
|Shared by many products, with several fields and a page of its own

|Tasting notes
|`list.single_line_text_field` metafield
|Simple ordered strings with a list length validation

|Club tiers and their benefits
|App-owned metaobject `$app:club_tier`, referenced by a product metafield and read by the Function
|Structure is the app's, entries are edited by the merchant

|A relationship with data of its own (quantity per recipe)
|A third metaobject with two references and the extra fields
|Costly to query: nested reads can hit the Storefront API's nesting limits

|Configuration of a Function
|One `json` metafield on the discount
|One value, one validation, easy to migrate

|Per-shop switch for an app block
|App-data boolean metafield
|Hidden from the admin; used by `available_if`

|ERP identifier
|`unique_values` text metafield, or an `id` type
|Look-up and upsert by custom ID

|Secrets, personal data, high-volume records
|The app's own database
|Not a good fit for Shopify custom data (Liquid reads every metafield, definitions have size limits)
|===

Use references, never handles or IDs stored in text fields: a text field breaks the link, hides it from Liquid and the
Storefront API and prevents Shopify from resolving it. Use the GID for relationships and the handle for URLs and
cross-store migration. Choose the access settings explicitly: start with the narrowest and widen them, and enable
`storefront` only for headless use, since Liquid reads the data anyway.

== Pitfalls and documentation differences

[cols="3,4",options="header"]
|===
|Symptom |Cause and fix

|`Unknown argument "input" on field "Mutation.productUpdate"`
|API 2026-10 takes `product:` (a `ProductUpdateInput`). The guides for app-owned and merchant-owned metafields still show `+productUpdate(input: {...})+`. The same applies to `productCreate`.

|`Enum "MetafieldStorefrontAccessInput" cannot represent non-enum value: "PUBLIC_READ"`
|Enum values are written without quotes. The Storefront guide shows `access: { storefront: "PUBLIC_READ" }`.

|`Unknown argument "id" on field "Mutation.metafieldDefinitionUpdate"`
|The update identifies a definition by `ownerType`, `namespace` and `key` inside `definition`. The Storefront guide shows an `id` argument.

|`Field "type" of type "MetafieldDefinitionType!" must have a selection of subfields`
|`type` and `access` of a definition are objects, so select `type { name }` and `access { admin storefront }`. One guide example selects them bare.

|`Field "key" is not defined by type "MetaobjectFieldDefinitionOperationInput"`
|Fields of a definition are updated with `create`, `update` and `delete` operations. The guide's example passes the field directly.

|`Unknown type "MetaobjectDefinitionUpdate"`
|The input type is `MetaobjectDefinitionUpdateInput`. A capabilities example uses the shortened name.

|Filter by metafield returns every product (before 2026-10) or an error (from 2026-10)
|The definition has no `adminFilterable` capability, or the type or comparison is not supported. Enable the capability and use a documented comparison.

|`metafieldsSet` rejects a value
|The `type` is missing and there is no definition, the value does not match the type, a `compareDigest` is stale, or more than 25 metafields were sent.

|Liquid prints nothing for an app-owned metafield in the merchant's theme
|The theme must use `+app--<app id>--sub+`; the `$app:` shorthand works only inside the app's theme app extension.

|A loop over a reference list stops at 50 items
|Wrap the loop in `paginate` (250 per page).

|`product.metafields.custom.size` returns a number
|`size` is also a filter. Use `product.metafields.custom["size"]`.

|Draft metaobject missing on the storefront
|The `publishable` capability is on and the entry is `DRAFT`. Publish it with `metaobjectUpdate`.

|`shopify app deploy` is rejected for the 26th definition change
|At most 25 definition changes per deploy; deploy in several versions.

|Customer account extension gets `null` for an app metafield
|Since 2026-06-16 the metafield needs a definition with `access.customerAccount` set.

|The Function receives `null` for a metafield that exists
|The value is larger than 10,000 bytes, or the metaobject type is not app-owned.
|===
