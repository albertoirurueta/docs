This page was written against Online Store 2.0 themes as they work on 2026-10-27, the date it was checked: the reference themes
Skeleton (the default of `shopify theme init`), Dawn 16.0.0 and Horizon 4.3.0, Shopify CLI 5.0.0 with Theme Check 3.31.0,

has to produce the same results itself, and the xref:ecommerce/shopify/storefront-api-and-headless-hydrogen.adoc[Storefront

A theme is judged by four things that are easy to treat separately and are better treated together: whether a visitor
understands each page at a glance (information hierarchy), whether a search engine understands it (SEO), whether it
appears quickly and stays still while it loads (performance), and whether a keyboard or screen reader user can complete a
purchase (accessibility). The same markup decisions serve all four. One `h1` per page, content in reading order, images with
dimensions and alternative text, and a cart that works as a plain form before JavaScript enhances it are good for
visitors, crawlers, Lighthouse and assistive technology at the same time. The page ends with the Ajax Cart API, the
mechanism that lets a theme update the cart without a page load, built so that it keeps those four properties.

The running example is the Pocket Coffee shop: Spanish (default) and English storefronts, the product "Single-origin
beans" with 18 variants (origin by grind by size, SKUs such as `PC-COL-WHL-250` at 8.90 EUR), the "Starter kit", the Coffee
Club discount, free shipping above 40 EUR and a roast date metafield. This page builds a small Pocket Coffee theme on top of
Skeleton: a head with complete SEO tags, structured data, a `robots.txt.liquid`, a hero banner that handles the Largest
Contentful Paint image correctly, an accessible price and product page, and a cart drawer driven by the Ajax API.

== What the books taught and what changed

Two books cover this ground, and both were written for older themes. Gavin Ballard, _The Definitive Guide to Shopify
Themes_ (Apress, 2017), has the design chapters that this page borrows its method from: designing layout and navigation,
the product page and its information hierarchy, the home and collection pages, the cart, and then SEO and social sharing
and performance. Ivan Djordjevic, _Shopify Theme Customization with Liquid_ (Packt, 2021), has a chapter on the Ajax API.
The method is still sound: decide the job of each page, order the content by importance, make the first screen carry the
decision. The mechanics changed, and the table lists what to read as history.

[cols="2,3",options="header"]
|===
|In the books and in older themes
|Today

|Static sections and theme settings in `.liquid` templates
|JSON templates compose sections, section groups hold the header and footer, and the theme editor reorders everything. The information hierarchy is now the `order` array of a template.

|Microdata and hand-written JSON-LD in the theme
|The `structured_data` filter produces `Product`, `ProductGroup` and `Article` markup; the theme adds only what the filter does not cover.

|Page weight, request counts, asset concatenation and YSlow
|Shopify's CDN serves HTTP/3 with Brotli, minifies CSS and JavaScript, sends Early Hints and streams the HTML. The measures that matter are the Core Web Vitals (LCP, INP, CLS) and the Lighthouse scores that the Theme Store checks.

|Theme Kit, Slate, Grunt and jQuery
|Shopify CLI, Theme Check, native `fetch`, custom elements and ES modules with import maps.

|Currency and language hacks in JavaScript
|Shopify Markets: locale-aware URLs from `window.Shopify.routes.root`, contextual prices read from Liquid, `hreflang` tags added by the platform.

|The cart updated by `+$.post('/cart/add.js')+` and a hand-built HTML snippet
|The Ajax Cart API with bundled section rendering: the server returns the re-rendered cart section in the same response.

== Page information hierarchy

Information hierarchy is the order in which a page tells its story: what a visitor must understand first, what they must
do next and what can wait. It decides the order of the sections in the template, the heading levels, what is above the
fold and what a screen reader reads first. Because the DOM order is also the keyboard focus order and the order in which a screen
reader reads the page, designing the hierarchy once gives a consistent result for all three.

=== One job per page

Each template has one job, and the hierarchy follows from it. The four pages that carry a purchase are described in the
table with the Pocket Coffee choices; the search page, the 404 page, content pages and the blog follow the same rule with
a different job.

[cols="1,2,3,3",options="header"]
|===
|Template
|Job
|Above the fold
|Stays visible or is easy to reach

|`index`
|Say what the shop sells and send the visitor to a collection or a product.
|Header, one `h1` with one promise and one button, the hero image (usually the LCP element).
|Search, cart link, language and country selector, newsletter and policies in the footer.

|`collection`
|Let the visitor find the right product.
|Collection title (`h1`) and a short description, then filters and sorting, then the product grid.
|Filters and sort control (origin and grind for Pocket Coffee), pagination, a way back to all collections.

|`product`
|Make the buying decision and add to cart.
|Gallery with the first image loaded eagerly, product title (`h1`), price with the sale price marked, variant picker, add to cart.
|Stock and shipping hint (free shipping above 40 EUR), description, roast date, recommendations.

|`cart`
|Confirm what will be bought and move to checkout.
|Title and item count, line items with quantity and remove, subtotal, checkout button.
|Discount code field, shipping threshold progress, express payment buttons, order note.
|===

The figure shows the same four pages as wireframes with the reading order numbered. Blue blocks identify the shop, green
blocks carry content and amber blocks ask the visitor to decide or act.

image::ecommerce-shopify-page-hierarchy.svg["Wireframes of the home, collection, product and cart pages with numbered reading order",width=900]

Ballard's design chapters make the same cut. For the product page he orders imagery, then product details, then the add to
cart form, then recommended products; the sequence in the figure is the same with today's additions (variants as a picker,
sale price markup, the roast date metafield). What no longer applies is how the order is encoded.

=== Encoding the hierarchy in templates and section groups

In an Online Store 2.0 theme the hierarchy lives in the JSON template, and the theme editor can reorder it without code.
The `order` array is the DOM order. The header and footer are section groups (`header-group.json`, `footer-group.json`),
which Skeleton includes in the layout with `+{% sections 'header-group' %}+`. A template for the Pocket Coffee home page
needs one section, the hero:

[source,json,subs=-attributes]
----
{
  "sections": {
    "hero": {
      "type": "hero-banner",
      "settings": {
        "heading": "Freshly roasted, shipped in 24 hours",
        "button_label": "Shop beans"
      }
    }
  },
  "order": ["hero"]
}
----

Source: https://shopify.dev/docs/storefronts/themes/architecture/templates/json-templates[Shopify docs: JSON templates]

The product template keeps the Skeleton convention of a single `main` section, because everything on the product page
belongs together and is read in one order:

[source,json,subs=-attributes]
----
{
  "sections": {
    "main": {
      "type": "product",
      "settings": {}
    }
  },
  "order": ["main"]
}
----

Source: https://shopify.dev/docs/storefronts/themes/architecture/templates/product[Shopify docs: product template]

A few rules keep a hierarchy intact as the merchant edits the theme:

* Give every page exactly one `h1`, the title of the thing the page is about: the product title on a product page, the
  collection title on a collection page, the hero heading on the home page. Shopify's accessibility guidance requires the
  `h1` to identify the main topic and the other headings to follow in sequence, without skipping levels for visual
  effect.
* Make the first section of the template the one that carries the decision. The `section.index` property, which is the
  1-based position of a section in its location, lets a section behave differently when it is first (see the hero below).
* Put structure in sections, not in conditionals. A section can be hidden or reordered by the merchant, while an `if` in
  a layout cannot.
* Keep the product page's reading order equal to its DOM order. Do not move the add to cart button with CSS `order` or
  `position` so that it appears before the title; keyboard users follow the DOM.
* Use the `routes` object for every internal URL: `routes.root_url`, `routes.cart_url`, `routes.search_url`,
  `routes.collections_url`, `routes.all_products_collection_url`, `routes.cart_add_url`, `routes.cart_change_url`,
  `routes.cart_update_url`, `routes.cart_clear_url`, `routes.predictive_search_url` and
  `routes.product_recommendations_url`. A hard-coded `/cart` link on a localized storefront, where the cart is
  `/en/cart`, sends the visitor back to the default language or market, and Theme Check reports it with the
  `HardcodedRoutes` check.

Source: https://shopify.dev/docs/api/liquid/objects/routes[Shopify docs: routes object]

=== The product page in detail

The product page has the most structure, and Pocket Coffee's "Single-origin beans" is the hardest case: one product, three
options (origin, grind and size) and 18 variants. The section below renders the gallery, the title, the price, a variant
selector, the roast date badge, the add to cart form and the description in that order.

[source,liquid,subs=-attributes]
----
{% comment %}
  Pocket Coffee product page. Reading order: media, title, price, variant, add to cart, details.
{% endcomment %}

{%- liquid
  assign current_variant = product.selected_or_first_available_variant
-%}

<div class="product">
  <div class="product__media">
    {%- for media in product.media limit: 6 -%}
      {%- if media.media_type == 'image' -%}
        {%- assign alt = media.alt | default: product.title -%}
        {%- if forloop.first -%}
          {{ media | image_url: width: 1500 | image_tag: sizes: '(min-width: 750px) 50vw, 100vw', widths: '375, 750, 1100, 1500', loading: 'eager', fetchpriority: 'high', alt: alt }}
        {%- else -%}
          {{ media | image_url: width: 1500 | image_tag: sizes: '(min-width: 750px) 25vw, 50vw', widths: '375, 750, 1100', loading: 'lazy', alt: alt }}
        {%- endif -%}
      {%- endif -%}
    {%- endfor -%}
  </div>

  <div class="product__info">
    <h1>{{ product.title }}</h1>

    {% render 'price', product: product, variant: current_variant %}

    {%- assign roast_date = product.metafields.custom.roast_date.value | date: '%-d %B %Y' -%}
    {%- if roast_date != blank -%}
      <p class="roast-badge">
        {{ 'products.roast_date' | t: date: roast_date }}
      </p>
    {%- endif -%}

    {% form 'product', product, id: 'product-form' %}
      <label for="variant-id">{{ 'products.variant' | t }}</label>
      <select id="variant-id" name="id">
        {%- for variant in product.variants -%}
          <option
            value="{{ variant.id }}"
            {% if variant == current_variant %}selected{% endif %}
            {% unless variant.available %}disabled{% endunless %}
          >
            {{- variant.title }} - {{ variant.price | money -}}
          </option>
        {%- endfor -%}
      </select>

      <label for="quantity">{{ 'products.quantity' | t }}</label>
      <input
        type="number"
        id="quantity"
        name="quantity"
        value="1"
        min="1"
        inputmode="numeric"
        autocomplete="off"
      >

      <button
        type="submit"
        name="add"
        data-add-to-cart
        {% unless current_variant.available %}disabled{% endunless %}
      >
        {%- if current_variant.available -%}
          {{ 'products.add_to_cart' | t }}
        {%- else -%}
          {{ 'products.sold_out' | t }}
        {%- endif -%}
      </button>

      <p class="product__error" role="alert" data-product-error hidden></p>
    {% endform %}

    <div class="product__description">
      {{ product.description }}
    </div>
  </div>
</div>

{% stylesheet %}
  .product {
    display: grid;
    gap: 2rem;
    padding: 0 var(--page-margin);
  }
  @media (min-width: 750px) {
    .product {
      grid-template-columns: 1fr 1fr;
    }
  }
{% endstylesheet %}

{% schema %}
{
  "name": "Product",
  "settings": [],
  "disabled_on": { "groups": ["header", "footer"] }
}
{% endschema %}
----

Source: https://shopify.dev/docs/storefronts/themes/architecture/templates/product[Shopify docs: product template]

What the section does, in the order a visitor meets it:

* The gallery loops over `product.media` with `limit: 6`, so a product with many images does not render all of them. Only
  the first image is loaded eagerly and with `fetchpriority="high"`, because it is the Largest Contentful Paint element of
  the page. The others are lazy. The alternative text is the `alt` of the media or, when the merchant left it empty, the
  product title, computed once with `assign` because a `default` filter placed after `image_tag` arguments would apply to
  the whole `<img>` tag and not to the alt text.
* The `h1` is the product title. The price comes from the `price` snippet, shown below, so every template that prints a
  price marks a sale the same way.
* The roast date is a metafield (`custom.roast_date`, a date) read once, outside any loop, and formatted with the `date`
  filter. A metafield read inside a loop over variants is one of the most common causes of a slow server response; see
  the Liquid performance section.
* The variant picker is a `<select name="id">` inside the product form, as in Skeleton, so the form works without
  JavaScript. Unavailable variants are `disabled`. The Single-origin beans product has 18 variants, well below the limit
  of 250 variants that the Ajax API returns for a product.
* The form has labels with matching `for` attributes, a quantity input with `inputmode="numeric"` and an alert region for
  errors. The option text of the select carries each variant's price, so the price of a choice is visible without
  JavaScript; a theme that rewrites the price when the choice changes has to announce the change, as the accessibility
  part explains.

The price snippet marks regular and sale prices both visually and for screen readers, which Shopify's accessibility
guidance requires:

[source,liquid,subs=-attributes]
----
{% doc %}
  Renders a price so that sighted users and screen reader users get the same information.

  @param {product} product - The product whose price is rendered
  @param {variant} [variant] - The selected variant, defaults to the first available one
{% enddoc %}

{%- liquid
  assign target = variant | default: product.selected_or_first_available_variant
  assign on_sale = false
  if target.compare_at_price > target.price
    assign on_sale = true
  endif
-%}

<div class="price" data-price>
  {%- if on_sale -%}
    <p>
      <span class="visually-hidden">{{ 'products.price.regular' | t }}</span>
      <s>{{ target.compare_at_price | money }}</s>
      <span class="visually-hidden">{{ 'products.price.sale' | t }}</span>
      <strong>{{ target.price | money }}</strong>
    </p>
  {%- else -%}
    <p>
      <span class="visually-hidden">{{ 'products.price.regular' | t }}</span>
      <strong>{{ target.price | money }}</strong>
    </p>
  {%- endif -%}
  {%- if target.unit_price_measurement -%}
    <p class="price__unit">
      <span class="visually-hidden">{{ 'products.price.unit' | t }}</span>
      {{ target.unit_price | money }} / {{ target.unit_price_measurement.reference_value }}{{ target.unit_price_measurement.reference_unit }}
    </p>
  {%- endif -%}
</div>
----

Source: https://shopify.dev/docs/storefronts/themes/best-practices/accessibility[Shopify docs: Accessibility best practices for Shopify themes]

The snippet uses a LiquidDoc `doc` block to declare its parameters. The Coffee Club discount does not change the variant's
`price`: automatic discounts are applied in the cart and at checkout, which is why the cart drawer prints
`item.final_line_price`. The Theme Store requires that a theme shows discounts in the cart.

=== Navigation, search and the 404 page

Navigation is part of the hierarchy. Keep the main menu shallow, since each additional level doubles the work for a
keyboard user, and render one menu that adapts with CSS rather than two copies for mobile and desktop, which Shopify
lists as a performance recommendation because duplicated menus double the DOM size. Wrap navigation in a `nav` element,
mark the current page with `aria-current`, and do not use `role="menu"` for site navigation. The search page and the
404 page each need a clear next action: a search box and links back to the collections, not a dead end.

Ballard's guidance on categories, filtering, sorting and pagination for collection pages carries over unchanged. Two
platform details matter now: Shopify limits pagination of arrays of objects to 25,000 objects, and a count query stops at
25,001, which signals "more than 25,000". If a collection is that deep, the hierarchy needs more filters, not deeper
paging.

=== Pitfalls

* Several `h1` elements, or a logo marked as `h1` on every page, make the page topic ambiguous. Skeleton prints the shop
  name in an `h2` in its header for this reason.
* Skeleton's layout has no `main` element and no skip link, and Horizon's layout renders a `main`. Check the layout of the
  theme you start from; the accessibility part adds both.
* A hero image that is a CSS background cannot be discovered early by the browser and has no alternative text. Use an
  `img`.
* Content that exists only after JavaScript runs (a product description fetched by `fetch`) is later to paint and later
  to be understood by crawlers than server-rendered Liquid.

Source: https://shopify.dev/docs/storefronts/themes/best-practices/performance/render-essential-content-server-side[Shopify docs: Render essential content in Liquid and HTML, not JavaScript]

== SEO in the theme

Search engine optimization splits between what the theme controls and what the merchant controls in the admin. A theme
that outputs the right tags makes the merchant's work count: the page title and meta description a merchant types in the
admin do nothing unless the layout prints `page_title` and `page_description`.

[cols="2,3,3",options="header"]
|===
|Signal
|Who controls it
|Where

|Title tag and meta description
|The merchant writes them per product, collection, page and article in the admin. The theme prints them.
|`+{{ page_title }}+` and `+{{ page_description }}+` in the layout head.

|Canonical URL
|The platform computes it; the theme prints it.
|`+{{ canonical_url }}+` in `link rel="canonical"`.

|Open Graph and Twitter cards
|The theme.
|A snippet in the head, with `page_image` for the image.

|Structured data
|The theme, with the `structured_data` filter for products and articles.
|JSON-LD scripts in the head or in a section.

|`hreflang` alternates
|Shopify adds them automatically when the store uses Markets.
|They come from `+{{ content_for_header }}+`; do not add your own unless you turn the automatic ones off.

|`sitemap.xml`
|The platform. The theme has no template for it.
|`/sitemap.xml`, referenced from `robots.txt`.

|`robots.txt`
|The platform generates a default; a theme may replace it with `robots.txt.liquid`.
|`templates/robots.txt.liquid`, not allowed in Theme Store themes.

|Image alternative text, URL handles, redirects
|The merchant, in the admin.
|Read in the theme through `image.alt` and `product.url`.
|===

=== The head: title, description and canonical

Shopify's SEO metadata guide names three tags that every theme must print in the `<head>`: the title, the meta
description and the canonical link. The Theme Store requires this snippet in every theme. The code below is the guide's
own layout example.

[source,liquid,subs=-attributes]
----
<head>
  <title>
    {{ page_title -}}
    {%- if current_tags %} &ndash; tagged "{{ current_tags | join: ', ' }}"{% endif -%}
    {%- if current_page != 1 %} &ndash; Page {{ current_page }}{% endif -%}
    {%- unless page_title contains shop.name %} &ndash; {{ shop.name }}{% endunless -%}
  </title>

  {% if page_description %}
    <meta name="description" content="{{ page_description | escape }}" />
  {% endif %}

  <link rel="canonical" href="{{ canonical_url }}" />
</head>
----

Source: https://shopify.dev/docs/storefronts/themes/seo/metadata[Shopify docs: Add SEO metadata to your theme]

Line by line:

* `page_title` is a global object that holds the page title for search engine listings and social previews. The merchant
  edits it in the admin, in the search engine listing fields of a product, collection, page or article (the Help Center
  page that describes them blocks automated requests and could not be opened, so what Shopify uses when the field is empty
  is not stated here, and the theme should not assume it). The suffixes keep titles unique across pagination
  (`current_page`) and tag filtering (`current_tags`), and the last line appends the shop name unless the title already
  contains it.
* `page_description` is the matching global object for the description. It is printed only when present, and it goes
  through `escape` because it is merchant-typed text placed in an attribute.
* `canonical_url` is the URL that search engines should treat as the page's main address. Duplicate URLs are unavoidable in
  a shop: a product can be reached through a collection path or with a `?variant=` parameter, and a collection through
  sort and filter parameters. Print the object as it is, and do not build a canonical from `request.path` or
  `request.origin`: the platform knows the canonical rules and a hand-made value can contradict them. Google treats
  `rel="canonical"` as a strong signal but not a directive (redirects are stronger and sitemap inclusion is weaker), so it
  works best when the rest of the signals (internal links, the sitemap, the `hreflang` set) point to the same URL.

Source: https://shopify.dev/docs/api/liquid/objects/canonical_url[Shopify docs: canonical_url object]

Source: https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls[Google Search Central: Consolidate duplicate URLs]

Skeleton keeps these tags in a `meta-tags` snippet, and Dawn prints the title and canonical in `layout/theme.liquid` and the
social tags in its own `meta-tags` snippet. The Pocket Coffee theme uses one `seo-head` snippet that renders from the
layout (`+{% render 'seo-head' %}+`), so the SEO tags have a single owner. It is shown in full after the next two
subsections, because it also prints the social tags and the structured data.

=== Open Graph and Twitter cards

Social platforms read Open Graph (`og:`) and Twitter card (`twitter:`) tags to build link previews. The `page_image`
object holds the image Shopify picked for the page (the product's featured image, the collection image, the article
image), and it is an `image` object, so it needs a width or a height when passed to `image_url`: the filter returns an
error when neither is given, and it never enlarges an image beyond its original size. A width of 1200 is the usual
Open Graph size. `image_url` returns a protocol-relative URL (it starts with `//`), so the snippet prepends `https:`.
`og:type` follows `request.page_type`: `product` for product pages, `article` for articles and `website` otherwise.

=== Structured data

Structured data tells search engines what a page contains in a machine-readable vocabulary (schema.org). Shopify provides
a filter that does the hard part for products and articles.

[source,liquid,subs=-attributes]
----
<script type="application/ld+json">
  {{ product | structured_data }}
</script>
----

Source: https://shopify.dev/docs/api/liquid/filters/structured_data[Shopify docs: structured_data filter]

The `structured_data` filter works on the `product` and `article` objects. A product with no variants becomes a schema.org
`Product`; a product with variants becomes a `ProductGroup`. An article becomes an `Article`. The documented output for a
single-variant product contains `@context`, an `@id` such as `/products/crocodile-tears#product`, the `Brand`, the `name`,
`description`, `image` and an `offers` object with an `Offer`, its `availability` and `price`.

Rules that keep structured data valid:

* Output it once per page. Skeleton prints the product markup from its `meta-tags` snippet, while Dawn prints
  `+{{ product | structured_data }}+` inside its product sections (the main product, the featured product) and
  `+{{ article | structured_data }}+` in its article section. If a theme and an app both print product markup the page
  carries two `Product` entities that can disagree. The Pocket Coffee
  snippet prints it for `request.page_type` equal to `product` and the product section prints nothing.
* In a multi-currency store the offer's `priceCurrency` has to be the currency the visitor sees, `cart.currency`, and not
  the shop currency; Shopify's multi-currency guide says so for any structured data you output for products. Inspect the
  offers that the `structured_data` filter prints in a store with a second currency (Pocket Coffee sells in USD as well as
  EUR), and when you write product markup by hand set `priceCurrency` from `cart.currency.iso_code` and read prices
  through Liquid, because contextual prices differ per market and a base price converted by hand is wrong.
* The `json` filter is the way to put a Liquid value into a JSON-LD script: it adds the quotes and escapes characters.
  When applied to a `product` object it omits `inventory_quantity` and `inventory_policy` for stores created after
  2017-12-05, which keeps stock quantities away from bots and crawlers that have no access to the store.
* Google's product snippet and merchant listing documentation says which properties unlock rich results (price,
  availability, ratings and so on). The `structured_data` output covers the basics; ratings and reviews come from the app
  that holds them and must be added to the same entity, not to a second one.

Shopify's requirements page still tells theme authors to test with Google's Structured Data Testing Tool. That address now
redirects to Google's general structured data documentation, which recommends the Rich Results Test for validating
markup; the Schema Markup Validator at schema.org checks the vocabulary itself.

Source: https://developers.google.com/search/docs/appearance/structured-data/product[Google Search Central: Product structured data]

=== hreflang and Markets

Pocket Coffee has a Spanish storefront (the default) and an English one. Search engines use `hreflang` annotations to send
each visitor to the right language or region. When the store uses Shopify Markets, Shopify adds the tags automatically
through `+{{ content_for_header }}+`, which the layout prints in the `<head>`; the tags follow each market's languages and
regions (`fr-ca`, `en-us` for a country market, `fr` for a broader one), update when markets change and stay in sync with
the page's canonical URL.

A theme or an app that adds its own `hreflang` tags on top of the automatic ones creates duplicate or conflicting
annotations that can hurt rankings. If you must manage them yourself (an app already prints them, or you link versions
across separate stores), turn off Automatic `hreflang` tags in Online store > Preferences, in the Social sharing and SEO
section, and build the tags from the `localization` object rather than from hard-coded domains or handles, since a
resource's handle can differ in each language. Each localized URL must reference itself as its own canonical.

Source: https://shopify.dev/docs/storefronts/themes/seo/hreflang[Shopify docs: Use hreflang tags in your theme]

The markets and domains side is covered in xref:ecommerce/shopify/markets-and-internationalization.adoc[Markets and
Internationalization].

=== Sitemaps

Shopify generates the sitemap. It is served at `/sitemap.xml`, and the `sitemap` object that `robots.txt.liquid` prints
shows the directive as `Sitemap: https://your-store.myshopify.com/sitemap.xml`. None of the reference themes has a sitemap
template, so the theme's job is to keep the URLs that the sitemap lists correct: valid canonical URLs, no duplicate paths and pages that
return real content.

Google's rules for sitemaps are the ones to design around: a single sitemap may contain up to 50,000 URLs or 50 MB
uncompressed, and a larger site uses several sitemaps listed in a sitemap index file. Submit the sitemap URL in Google
Search Console; a domain is a separate property there, so a store with several domains submits the sitemap of each one.
The `Sitemap:` line in `robots.txt` lets crawlers find it without a
submission.

Shopify's Help Center pages on the structure of the generated sitemap (which child sitemaps it contains and how many URLs
each holds) and on hiding a resource from search engines could not be opened, because the site blocks automated
requests; they are therefore not summarized here, and the sitemap should be inspected in the
browser at `/sitemap.xml`. A headless storefront is served by its own code, so its sitemap is a route that code has to
provide.

Source: https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap[Google Search Central: Build and submit a sitemap]

=== robots.txt

`robots.txt` tells crawlers which URLs they may request. Shopify generates a default file that works for most shops. A
theme can replace it by adding `templates/robots.txt.liquid`, which cannot be a JSON template, and which Shopify does not
include in any theme by default. The Theme Store forbids the template in submitted themes, so it is a store-specific
customization, not something a distributed theme ships.

The template can use only six Liquid objects:

[cols="1,3",options="header"]
|===
|Object
|What it holds

|`robots`
|The default rule groups, in `robots.default_groups`.

|`group`
|One group: a `user_agent`, its `rules` and an optional `sitemap`.

|`rule`
|One directive (`Allow`, `Disallow`) and its `value`; printing the object prints the line.

|`user_agent`
|The crawler a group applies to, with a `value` such as `+*+`.

|`sitemap`
|The `Sitemap:` directive and its URL.

|`request`
|The current request, used for host-specific rules with `request.host`.
|===

Shopify strongly recommends using these objects instead of replacing the file with plain text, because adding the
template replaces the generated output and the output of the template does not always match the generated file exactly.
Before publishing, save a copy of the current `/robots.txt` and compare it with the rendered result.

Pocket Coffee wants crawlers to skip the sorted views of a collection (`?sort_by=` URLs duplicate the unsorted page), so it
adds one rule to the `+*+` group. Shopify's example also adds its literal rule inside the loop; the template here appends
an explicit line break to the literal rule, so it can never run into the line that follows, whatever the rule objects
print.

[source,liquid,subs=-attributes]
----
{%- capture newline %}
{% endcapture -%}

{%- for group in robots.default_groups -%}
  {{- group.user_agent }}

  {%- for rule in group.rules -%}
    {{ rule }}
  {%- endfor -%}

  {%- if group.user_agent.value == '*' -%}
    {{ 'Disallow: /*?sort_by=*' | append: newline }}
  {%- endif -%}

  {%- if group.sitemap != blank -%}
    {{ group.sitemap }}
  {%- endif -%}
{% endfor %}
----

Source: https://shopify.dev/docs/storefronts/themes/seo/robots-txt[Shopify docs: Customize robots.txt]

LiquidJS rendered this template against stand-in objects that mimic two default groups (the real ones come from Shopify,
and this is not evidence of Shopify's output), with the result:

[source,text,subs=-attributes]
----
--- robots.txt ---
User-agent: *
Disallow: /admin
Disallow: /cart
Disallow: /*?sort_by=*
Sitemap: https://pocket-coffee.example.com/sitemap.xml
User-agent: adsbot-google
Disallow: /checkout
----

The same page documents the other customizations, all variations of the loop above. To remove a default rule, skip it
inside the inner loop:

[source,liquid,subs=-attributes]
----
{% for group in robots.default_groups %}
  {{- group.user_agent }}

  {%- for rule in group.rules -%}
    {%- unless rule.directive == 'Disallow' and rule.value == '/policies/' -%}
      {{ rule }}
    {%- endunless -%}
  {%- endfor -%}

  {%- if group.sitemap != blank -%}
    {{ group.sitemap }}
  {%- endif -%}
{% endfor %}
----

Source: https://shopify.dev/docs/storefronts/themes/seo/robots-txt[Shopify docs: Customize robots.txt]

To give one market a different crawl policy, compare `request.host` inside the loop (for example
`+{%- if request.host == 'example.fr' -%}+` followed by a `Disallow: /en/` line). Do this only when the store has distinct
domains per market. Rules for crawlers that are not in the default set are plain text outside the loop:

[source,text,subs=-attributes]
----
User-agent: discobot
Disallow: /

Sitemap: [sitemap-url]
----

Source: https://shopify.dev/docs/storefronts/themes/seo/robots-txt[Shopify docs: Customize robots.txt]

`robots.txt` controls crawling, not indexing. Google states that the file is not a mechanism for keeping a page out of
Google: to keep a page out, block indexing with `noindex` or password-protect the page. Do not block a URL in
`robots.txt` and also rely on `noindex` on it, because a crawler that may not fetch the page cannot read the tag.

Source: https://developers.google.com/search/docs/crawling-indexing/robots/intro[Google Search Central: Introduction to robots.txt]

=== URLs, handles and duplicate content

Online Store URLs follow fixed patterns, as every example in the documentation shows (`/products/handle`,
`/collections/handle`, `/cart`, `/search`); what the merchant controls is the handle, the last path segment. Duplicate content comes from parameters that
change the view (`?sort_by=`, `?variant=`, filters and `page`), and the tools against it are the canonical URL, the
default `robots.txt` and, for sorted views, a rule such as the one above. Keep handles short, lowercase and stable, since
changing one changes the URL. The admin has a URL redirects feature for old addresses, but its Help Center page could not
be opened here, so it is not described. A theme should still never link to its own redirected URLs.

== Image and asset performance

Performance on a Shopify theme is two problems with two different owners. The platform owns the network: the CDN, the
compression, the server rendering and the early delivery of resources. The theme owns what the browser is asked to do with
what it receives: which image is the main one, how big it is, what blocks rendering, how much JavaScript runs. This part
covers the measures first and then the controls the theme has, in the order that moves the numbers most.

=== The metrics and the thresholds

The Core Web Vitals are the three metrics that Google uses as a ranking signal and that Shopify's guidance is organized
around. Google's thresholds, measured at the 75th percentile of page loads and segmented across mobile and desktop, are:

[cols="2,3,2,3",options="header"]
|===
|Metric
|What it measures
|Good
|Usual cause in a theme

|Largest Contentful Paint (LCP)
|When the largest element in the initial viewport finishes rendering, usually the hero or the product image.
|2.5 seconds or less
|A lazy-loaded or late-discovered hero, a huge image, render-blocking CSS or apps, slow Liquid.

|Interaction to Next Paint (INP)
|How long the page takes to respond visibly after a tap or click.
|200 milliseconds or less
|Main-thread JavaScript from the theme and from apps, many stylesheets, a huge DOM.

|Cumulative Layout Shift (CLS)
|How much visible content moves unexpectedly.
|0.1 or less
|Images without dimensions, fonts that swap late, app-injected content without reserved space.
|===

Source: https://web.dev/articles/vitals[web.dev: Web Vitals]

Shopify adds two supporting metrics that are not scored but locate the cause of a slow LCP: Time to First Byte (TTFB),
which on a Shopify storefront is mostly Liquid rendering, and First Contentful Paint (FCP), which render-blocking
stylesheets and scripts in the head delay. If the server response is slow, look at the Liquid; if it is fast, look at what
the browser does next.

The Theme Store applies two lab scores to a submitted theme: a minimum average Lighthouse performance score of 60 and a
minimum average accessibility score of 90, each averaged across the home, product and collection pages for both desktop and
mobile, with sections that contain real images and content. Those are lab scores on a benchmark store and entry
thresholds, not targets: the Core Web Vitals are measured separately, on real visitors.

Source: https://shopify.dev/docs/storefronts/themes/store/requirements[Shopify docs: Theme Store requirements]

=== What the platform already does

Before optimizing, know what not to redo. Shopify's performance documentation describes these platform features, all of
which work without changes to the theme:

[cols="2,5",options="header"]
|===
|Feature
|What it does and what it means for the theme

|CDN
|A Cloudflare-backed content delivery network. Files are minified and compressed with Brotli and gzip, requests use HTTP/3
and TLS 1.3, and storefront asset URLs are same-origin paths such as `/cdn/shop/files/hero.jpg`. Do not hard-code
`cdn.shopify.com`; reference assets through the `asset_url` and `image_url` filters.

|Versioned asset URLs
|The `asset_url` filter appends a version such as `?v=1384022871`, so a changed file is refetched. An image linked without
the filter can stay stale for a day or more. Only the `v` parameter is recognized for versioning; a raw timestamp or an
arbitrary parameter does not bust the cache. A CSS `+url(bg.gif)+` is static, so write
`+url({{ 'bg.gif' \| asset_url }})+` in a Liquid-processed stylesheet.

|Server-side rendering
|The Storefront Renderer serves storefront requests, which improves cache misses. TTFB is dominated by the theme's Liquid.

|Streamed HTML
|Eligible pages are sent in two parts: the layout up to `+{{ content_for_header }}+` first, the rest after the sections
render, so the browser works on the head while Shopify renders the sections. See below.

|Minification
|CSS and JavaScript with valid ES5 syntax are minified when requested. Shopify serves the original when the minified file
would be larger or when the file name ends in `.min.js` or `.min.css`; rename a file to `.min.js` to debug it.

|Early Hints
|Shopify sends HTTP 103 hints with `Link` preload and preconnect headers for the render-blocking scripts and stylesheets in
the head, on every storefront page. The hints that the theme adds through `preload_tag`, `stylesheet_tag: preload: true`
and `image_tag: preload: true` fill the remaining space of a limited header.

|Speculation rules
|Shopify injects speculation rules for prefetching and prerendering likely next pages in browsers that support them.
Themes can add rules; the default rules aim to avoid problems with data use, caching and analytics.

|Import map polyfill
|Shopify includes `es-module-shims` when needed, so `<script type="importmap">` and `type="module"` work without a
second copy of the polyfill.

|Pagination limit
|Arrays of objects paginate to at most 25,000 objects.
|===

Source: https://shopify.dev/docs/storefronts/themes/best-practices/performance/platform[Shopify docs: The Shopify platform]

=== Images: image_url and image_tag

Images are usually the LCP element, so their loading strategy is the largest single decision. Shopify's `image_url` and
`image_tag` filters do the difficult parts: they produce a `srcset`, add `width` and `height` to avoid layout shift and
serve from the CDN. Using them consistently is the baseline, and everything else builds on it.

`image_url` returns the CDN URL of an image from an `article`, `collection`, `image`, `line_item`, `product`, `variant` or
`country` object (or their `src`). Its parameters are:

[cols="1,4",options="header"]
|===
|Parameter
|Behaviour

|`width`, `height`
|Output size in pixels, up to 5760. At least one is required: with neither the filter returns an error. With one, the
other is computed from the aspect ratio. An image is never enlarged beyond its original dimensions.

|`crop`
|Which part to keep when the requested ratio differs from the original: `top`, `center` (default), `bottom`, `left`,
`right` or `region`. With `region`, `crop_left`, `crop_top`, `crop_width` and `crop_height` define the area, and `width` and
`height` can resize it. A country flag is an SVG and can only be cropped when `format` is also given.

|`format`
|`pjpg` (progressive JPEG) or `jpg`. Only some conversions are possible: `png` to `jpg` or `pjpg`, and `jpg` to `pjpg`.
Shopify detects the formats a browser supports (WebP, AVIF and others) and picks the best one automatically, taking the
features of a requested format into account.

|`pad_color`
|A hex color (`hex3` or `hex6`) used to pad the image when the dimensions give a different aspect ratio.

|`quality`
|An integer from 10 to 90; lower values reduce size and visual quality. Omitting it lets Shopify choose by format, which is
not the same as 100, and the output is not guaranteed to be byte-identical even when the size matches the source.
|===

`image_tag` turns an `image_url` into an `<img>` element:

[cols="1,4",options="header"]
|===
|Parameter
|Behaviour

|`width`, `height`
|Added from the image URL's dimensions and aspect ratio by default. Passing a value overrides it; passing `nil` omits the
attribute. If only one is given, only that attribute is added.

|`widths`
|A comma-separated list for the `srcset` widths instead of Shopify's default set, up to the width in the URL.

|`sizes`
|The HTML `sizes` attribute, which tells the browser how wide the image is displayed so it can choose a `srcset` entry.

|`srcset`
|Overrides the generated `srcset`; use it only to remove the attribute with `nil`.

|`preload`
|When true, sends a `Link` header with `rel=preload` and the matching `imagesrcset` and `imagesizes`. It does not change the
tag. Use it sparingly, for one above-the-fold image at most.

|`alt`
|Overrides the default, which is the media alt text, or the resource title for article, collection, line item, product and
variant images.

|Any HTML attribute
|A parameter named like an attribute (`class`, `loading`, `fetchpriority`, `id`) is added to the tag.
|===

When the image has a focal point set in the admin, `image_tag` also adds an `object-position` style. Without `preload`,
`loading` is set to `lazy` automatically for images in sections further down the page, and the documentation warns not to
lazy-load images above the fold; where the default does not fit, write your own logic with `section.index` and
`section.location`.

Source: https://shopify.dev/docs/api/liquid/filters/image_tag[Shopify docs: image_tag filter]

Source: https://shopify.dev/docs/api/liquid/filters/image_url[Shopify docs: image_url filter]

Shopify's example of the default output, for `+{{ product | image_url: width: 200 | image_tag }}+`, is an `<img>` with the
CDN `src`, the `alt`, a one-entry `srcset`, and `width` and `height`:

[source,html,subs=-attributes]
----
<img src="//polinas-potent-potions.myshopify.com/cdn/shop/files/science-beakers-blue-light-new.jpg?v=1683744744&amp;width=200" alt="Health potion" srcset="//polinas-potent-potions.myshopify.com/cdn/shop/files/science-beakers-blue-light-new.jpg?v=1683744744&amp;width=200 200w" width="200" height="133">
----

=== The LCP image

For most pages the LCP element is one image: the hero on the home page, the first gallery image on a product page, the
collection banner. Shopify lists these as its highest-impact recommendations, in this order of importance:

* Never lazy-load the LCP image. `loading="lazy"` delays an image until layout completes. Load every image that is visible
  in the initial viewport eagerly.
* Mark the LCP image with `fetchpriority="high"`, which tells the browser to fetch it before other resources.
* Do not hide it behind a fade-in or reveal animation: the LCP event waits for the animation even after the download ends.
* Use an `<img>`, not a CSS `background-image`, for hero content, so that the browser's preload scanner discovers it early.
* Render essential content in Liquid and HTML, not in JavaScript.
* Use `<picture>` when the mobile and desktop heroes are different images, instead of two images toggled with CSS, so the
  browser downloads only the one that matches.
* Preload sparingly: one or two resources that the browser finds late, because every hint competes for the same limited
  header.

Section Rendering API, so the test is written to fail safe: in those contexts the image gets the default behaviour of `image_tag`
rather than high priority by accident. The section also supports an optional separate mobile image

=== Layout order: first-paint resources before content_for_header

Streaming makes the order of the layout part of performance. Everything above `+{{ content_for_header }}+` reaches the
browser while the sections are still rendering, so stylesheets, font preloads, the import map and CSS variables that the
first paint needs belong above it, and the browser can download them in that time. A page streams when it renders from a
JSON template, when `content_for_header` is a plain output tag (no filter, not inside another tag or snippet, not assigned
to a variable first) and when it sits inside `<head>` before the closing tag. A wrapped, filtered or relocated tag turns
streaming off for every page that uses the layout. Preview themes, the preview bar and the theme editor are not streamed,
so measure on the live theme.

image::ecommerce-shopify-streamed-layout.svg["Layout split into a streamed first chunk above content_for_header and a second chunk with the sections, with a timeline of the browser fetching resources",width=900]

The Pocket Coffee layout follows the figure. The import map, CSS variables, the critical stylesheet (preloaded through
`stylesheet_tag: preload: true`, which also puts it in the Early Hints header) and the SEO head are above
`content_for_header`; the header group, the main content, the footer group, the cart drawer and the module script follow.

[source,liquid,subs=-attributes]
----
<!doctype html>
<html lang="{{ request.locale.iso_code }}">
  <head>
    {% # Import map for the cart modules, above content_for_header so it is part of the first streamed chunk %}
    <script type="importmap">
      { "imports": { "cart-api": {{ 'cart-api.js' | asset_url | json }} } }
    </script>

    {% # Inlined CSS variables and fonts %}
    {% render 'css-variables' %}

    {% # Critical CSS, loaded synchronously and preloaded through the Link header %}
    {{ 'critical.css' | asset_url | stylesheet_tag: preload: true }}

    {% # Title, description, canonical, social tags and structured data %}
    {% render 'seo-head' %}

    {{ content_for_header }}
  </head>

  <body>
    <a class="skip-link" href="#MainContent">{{ 'accessibility.skip_to_content' | t }}</a>

    {% sections 'header-group' %}

    <main id="MainContent" tabindex="-1">
      {{ content_for_layout }}
    </main>

    {% sections 'footer-group' %}

    {% section 'cart-drawer' %}

    <script src="{{ 'pocket-cart.js' | asset_url }}" type="module"></script>
  </body>
</html>
----

Source: https://shopify.dev/docs/storefronts/themes/best-practices/performance/load-critical-resources-before-content-for-header[Shopify docs: Load first-paint resources before content_for_header]

Two cautions go with this layout. The TTFB that a tool reports on a streamed page marks when the first part arrives, not
when rendering finishes, so judge server work by the total duration of the document request. And everything above the tag
must be cheap Liquid, because Shopify renders it before it can send the first part.

=== Stylesheets, fonts and scripts

* Stylesheets. Keep the number of `<link rel="stylesheet">` tags low, because each extra stylesheet triggers a style
  recalculation that hurts INP. Load the critical CSS synchronously. `stylesheet_tag: preload: true` adds the preload hint.
  Shopify subsets the CSS of `+{% stylesheet %}+` tags so each page loads only the styles of the sections it renders, so a
  class must be used only within the file that defines it or files it renders directly.
* Fonts. The `font_face` filter outputs the `@font-face` rule; Skeleton's `css-variables` snippet calls it with
  `+font_display: 'swap'+` for each font variant. A web font blocks text rendering until it loads or times out; system
  fonts avoid the download, and web fonts uploaded to the Shopify CDN avoid the DNS and connection cost of Google Fonts.
  Use `size-adjust` and the other override descriptors on the fallback font to reduce layout shift when the web font
  swaps in. Theme Check reports a redundant `preconnect` to Shopify's CDN (`CdnPreconnect`) and manual preloads that a
  Shopify filter would do better (`AssetPreload`).
* Scripts. Use `defer` for non-critical scripts, `async` only for independent third-party scripts whose order does not
  matter, and `type="module"` (deferred by default) for the theme's own modules. Load code on interaction with dynamic
  `import()` inside event listeners. Prefer an import map with bare specifiers over a bundler: the Pocket Coffee layout maps
  `cart-api` to its versioned asset URL, so `pocket-cart.js` can `+import { addToCart } from 'cart-api'+` and still gets
  cache busting. Do not load another copy of `es-module-shims`.
* Apps. Third-party scripts are the largest source of INP and LCP problems on many stores. Audit every script, remove
  render-blocking apps and A/B-test anti-flicker snippets that run when no test is active, and reserve space with
  `min-height` for app content so that it does not shift the layout. App blocks and app embed blocks of theme app
  extensions are the supported way for an app to appear in a theme; the older script tags are being retired
  (`scriptTagCreate` and `scriptTagUpdate` return an error from 2026-10-01 and Shopify stops injecting script tags into
  online store pages on 2027-03-01). The xref:ecommerce/shopify/theme-app-extensions-and-web-pixels.adoc[Theme App
  Extensions and Web Pixels] page covers the replacement.

Source: https://shopify.dev/docs/storefronts/themes/best-practices/performance[Shopify docs: Performance best practices for Shopify themes]

=== Liquid performance

The server time of a page is the time its Liquid takes, and Shopify's recommendations for it are about how cost grows with
the size of the catalog. A theme that is fast with 10 products can be slow with 100.

[cols="2,4",options="header"]
|===
|Recommendation
|Why and how

|Avoid deeply nested loops
|Loops nested across products, variants and options grow quadratically. It is the most common cause of a high TTFB.

|Move metafield access out of loops
|A metafield read inside a loop costs a lookup per iteration; read it once before the loop, and prefer theme settings for
static data. The Pocket Coffee product reads `custom.roast_date` once.

|Do not over-fetch variants
|Iterating `product.variants` forces database queries. Use `product.options_with_values` for option UI, and load only the
variant data that the first render needs.

|Limit what a loop fetches
|A `for` loop's `limit` reduces the fetch for `collection.products` and `collections`; other arrays need `paginate`. The
pagination ceiling is 25,000 objects.

|Flatten `render` nesting
|Each nested snippet adds overhead, especially inside a loop. Prefer one level of snippets.

|Move repeated work out of loops
|Assign filter results before the loop, assign `block.settings` to a variable, and use `echo` or output tags instead of
`append` and `prepend` chains.

|Defer dialog content
|Guard expensive Liquid in dialogs and drawers so it runs only when the component opens. The cart drawer is a static
section that re-renders after each change, so it is cheap by construction.

|Use `section.index` and `section.location`
|Apply different loading strategies above and below the fold.

|Use the Section Rendering API for updates
|Re-render a section through Ajax instead of reloading the page. The Ajax part below does this.
|===

To see which Liquid line costs time, use the Shopify Theme Inspector for Chrome, and compare the document request's total
duration with its TTFB in DevTools.

Source: https://shopify.dev/docs/storefronts/themes/tools/theme-inspector[Shopify docs: Shopify Theme Inspector for Chrome]

=== Performance pitfalls

* A score from the theme editor preview or a preview theme is not representative, because those are not streamed, and the
  first visit to a page right after publishing a change can arrive without Early Hints.
* Apps that cheat Lighthouse (they inject transparent elements or serve different pages to crawlers) improve the lab score
  and hurt visitors; Shopify tells developers to avoid them.
* Lazy-loading everything, including the hero, is the most common self-inflicted LCP regression. `image_tag` already makes
  the right choice for sections far down the page; override it only for the hero.
* A hero built as a CSS background, an animated reveal or a carousel that loads every slide are the other three.
* A `preload` on every image makes the Early Hints header fill up and pushes out the hints that matter.

== Accessibility

An accessible theme can be used by everyone, including people who rely on a keyboard, a screen reader or a switch device.
In a shop it also protects revenue: a visitor who cannot reach the add to cart button cannot buy. Shopify's best practices
were written with the Web Content Accessibility Guidelines (WCAG) in mind and are organized by the four principles of
WCAG: perceivable, operable, understandable and robust. The general standard, the conformance levels, the legal
background and the validation tools are explained in the repository's xref:web/accessibility.adoc[Web Accessibility] page;
this part covers what is specific to a Shopify theme.

Following the best practices does not by itself make a theme accessible, and Shopify says so. Treat the lists as the
minimum, test with a keyboard and a screen reader, and use automated tools to catch regressions.

=== What the Theme Store requires

The Theme Store accessibility requirements are the part that is checked on submission, and they are a good minimum for any
theme:

* Every part of a page is keyboard accessible, including dropdown navigation, and focusable elements show a visible focus
  state. Keyboard focus order matches the DOM order, top to bottom and left to right.
* Every image has an `alt` attribute. Product images use `image.alt` or `image_tag` with an `alt` argument.
* Form inputs have unique IDs, and labels have `for` attributes that match the input ID.
* The HTML is valid.
* Text contrast is at least 4.5:1 for main body content, and 3:1 for text larger than 18 pt and for non-text elements such as
  borders and icons.
* Pointer targets are at least 24 by 24 CSS pixels, except inline body text and elements that meet another exception of
  WCAG 2.2 target size (minimum). Shopify's separate best practices page recommends 44 by 44 pixels for primary controls.
* Headings `h1` to `h6` are visually different from each other.
* The minimum average Lighthouse accessibility score is 90 on the home, product and collection pages, desktop and mobile.

Source: https://shopify.dev/docs/storefronts/themes/store/requirements[Shopify docs: Theme Store requirements]

Source: https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html[W3C: Understanding Target Size (Minimum)]

|===
|Best practice
|Why
|In the Pocket Coffee theme

|`lang` on `html`, zoom enabled

|Headings in sequence, one `h1`
|Headings convey the outline of the page, not its styling.

|Sale and regular prices marked for screen readers

|Links for navigation, buttons for actions
|Native elements bring keyboard support and semantics.

|Forms: labels, `required`, `autocomplete`, errors in `aria-describedby`

|`critical.css` gives buttons, selects and inputs a minimum block size of 44 pixels and buttons a minimum inline size of 44 pixels.

=== The accessible cart drawer

The drawer in the Ajax part is built from the elements that give it accessibility for free. A native `<dialog>` opened
with `showModal()` is modal: the rest of the page becomes inert, focus moves into the dialog, Escape closes it and focus
returns to the element that opened it. It is labelled by its heading with `aria-labelledby`. The status paragraph is
present in the page before any message is written to it, which matters because a live region only announces changes made
after it exists. After a quantity change, focus is placed back on the same input, or on the drawer heading when the line
disappeared, so a keyboard user is not dropped at the top of the page. The DOM tests described in the Ajax part check the
status text and the focus handling after a change; modality, Escape and focus restoration are native browser behaviour of
`dialog` and were not tested here.

== The Ajax Cart API

The Ajax API is a set of lightweight REST-style endpoints that a Shopify-hosted theme calls from JavaScript, to add
products to the cart and update the cart counter, to suggest related products and to suggest products and collections while
a visitor types in a search box, all without a page reload. The Cart API is the part used most: it reads and changes the
cart of the current session.

The rules that define it:

* It is only for themes hosted by Shopify. It cannot be used from a custom storefront; a Hydrogen or other headless
  storefront uses the cart of the Storefront API instead.
* It is unauthenticated. It needs no access token or client ID, and it works on the cart of the visitor's current session,
  so never send an Admin or Storefront token to it.
* Requests are `GET` to read the cart and some product data, and `POST` to change the cart of the current session. Responses
  are JSON.
* There are no hard rate limits, but it is subject to Shopify's standard abuse prevention. Repeated failed attempts to add
  items to the same cart are throttled and return HTTP 429.
* It cannot read customer or order data or change store data; for that, use the GraphQL Admin API.
* A product JSON response lists at most 250 variants.
* It is unversioned, like Liquid: Shopify can change it at any time, so keep the code that calls it in one module (the
  `cart-api.js` below) and test it.

Source: https://shopify.dev/docs/api/ajax[Shopify docs: About the Shopify Ajax API]

=== Locale-aware URLs

A store that sells in several languages or countries has localized URLs (`/en/cart/add.js`), and the Ajax API must be called
on the URL of the language and country the visitor chose, or the visitor is forced back to the default. The global
`window.Shopify.routes.root` is the base for every Ajax URL. It always ends in `/`, so plain string concatenation is safe:

[source,javascript,subs=-attributes]
----
var cartContents = fetch(window.Shopify.routes.root + 'cart.js')
  .then(response => response.json())
  .then(data => { return data });
----

Source: https://shopify.dev/docs/api/ajax[Shopify docs: About the Shopify Ajax API]

In Liquid the same information is in `routes.cart_add_url`, `routes.cart_change_url`, `routes.cart_update_url` and
`routes.cart_clear_url`. In the endpoint names below `+{locale}+` stands for that root. For Pocket Coffee, whose Spanish
storefront is the default and whose English storefront has a prefix, the add endpoint is `/cart/add.js` in Spanish and
`/en/cart/add.js` in English.

=== Line items: how lines merge and split

The Ajax Cart API behaves according to how Shopify models lines, and several of its surprises come from that.

* Lines are identified by a `key` of the form `variantId:hash`. If the same variant is added again with identical price,
  properties and selling plan, the lines merge and the quantity grows. If the price differs (for instance because an
  automatic discount applies), or the properties or the selling plan differ, the items split into separate lines with the
  same `variant_id`.
* Because of that, `variant_id` is not unique. To change a line when the cart may hold duplicates, address it by the
  line item `key`, or by `line`, the 1-based index. The documentation shows `change.js` with a numeric variant ID, a string
  key and a `line`; with a key the `id` value must be a string. The Pocket Coffee drawer uses `line`.
* Line item properties are free-form key/value pairs on a line (an engraving text, a gift message). A request that
  includes `properties` overwrites the whole object, and once set it cannot be changed to an empty object; to clear them
  remove the line. A property whose name starts with an underscore (`+_foo+`) is private: hidden at checkout but visible in
  the admin order details. The storefront does not hide it in the theme, so filter keys that start with `+_+` out of
  `line_item.properties` in Liquid. Cart attributes starting with a double underscore (`+__+`) are private too, and those do
  not appear in `cart.attributes` or in the Ajax response, so they need no theme change.
* A selling plan is added with `selling_plan` and the ID of the plan; `change.js` sets one with an ID, or removes it with
  `null` or an empty string, and for that operation the line must be addressed with `line` and `quantity` should be given.
  `parent_id` in `add.js` attaches the new line to a parent line, and the response then carries a `parent_relationship` with
  the parent's key.
* The quantity of a variant that is added is capped by stock: adding 20 when 10 are available adds 10 and returns an error
  describing the limit. The line quantity set by `update.js` for a variant already in the cart is not validated against
  inventory, so a theme can add more than is available; checkout still validates it.
* Discount codes are applied with the `discount` field of `update.js`, comma-separated for several, and removed with an
  empty string. Automatic discounts, such as Pocket Coffee's Coffee Club rule, need no call: they appear in the line's
  `discounts` and in `final_price` and `final_line_price`. Prices in the JSON are integers in the smallest currency unit:
  the documentation's `items_subtotal_price: 100100` corresponds to the "$1,001.00 CAD" in the live-region text of the same
  example. Format money in Liquid, not in
  JavaScript, since the store's money format may differ from `Intl.NumberFormat`; bundled section rendering exists for this.

Source: https://shopify.dev/docs/api/ajax/reference/cart[Shopify docs: Cart API reference]

=== Errors

An error response has an HTTP error status and a JSON body with `status`, `message` and `description`. The cases in the
documentation are:

[cols="2,2,4",options="header"]
|===
|Endpoint and situation
|HTTP status
|Body

|`add.js`, quantity above stock
|422
|`message: "Cart Error"`, a description such as "You can't add more item name to the cart." The maximum available quantity is added.

|`add.js`, product sold out
|422
|"The product 'item name' is already sold out."

|`add.js`, all stock already in the cart
|422
|"You can't add more item name to the cart."

|`add.js`, variant does not exist or is not in the Online Store channel
|422
|`message: "Cart Error"`, `description: "Cannot find variant"`. A variant created, updated or published through the Admin API takes a few seconds to reach the cart; retry after a short delay that grows, and stop after a few attempts.

|`update.js`, variant does not exist or is not in the Online Store channel
|404
|The same `Cannot find variant` description with status 404.

|`change.js`, the item is not in the cart
|400
|`status: "bad_request"`, `message: "no valid id or line parameter"`. `change.js` never adds an item.

|`add.js`, repeated failures on the same cart
|429
|Throttled. Handle a response body that is not JSON.
|===

=== The Section Rendering API and bundled section rendering

A cart change normally has to refresh the cart drawer, the counter in the header and sometimes more. Without help the theme
would fetch `cart.js` and rebuild HTML in JavaScript, duplicating the Liquid that already renders the cart. The Section
Rendering API lets the theme ask Shopify for the HTML of sections instead:

* Append `?sections=id1,id2` (or `sections[]=id1&sections[]=id2`) to any page URL to get a JSON object that maps each section
  ID to its rendered HTML. Up to five sections can be requested. The section renders in the context of the page URL, so
  `+/products/{handle}?sections=...+` renders it with that product and parameters such as `q` or `page` are respected.
* `?section_id=id` returns the HTML of one section directly, and answers 404 when the section does not exist.
* A section that fails to render comes back as `null`, possibly inside an HTTP 200 response, so code must handle `null`.
* Settings cannot be passed: an existing section uses its saved settings, and otherwise defaults are used.
* A section ID is the file name for a static section (`social.liquid` has the ID `social`; the Pocket Coffee drawer is
  `cart-drawer`). For sections in JSON templates or section groups the ID is generated (`+template--5678__image_banner+`,
  `+sections--1234__header+`), which is why the markup of a section is wrapped in an element with the ID
  `shopify-section-<id>` that scripts can read.
* `section.index` is `nil` when sections are rendered through this API.

Bundled section rendering folds that second request into the first. The Cart API endpoints `add`, `change`, `clear` and
`update` accept a `sections` parameter (a comma-separated list or an array of up to five IDs) and an optional
`sections_url`. The response is the usual JSON plus a `sections` key that maps each ID to HTML rendered after the cart
change, so the page can update in one round trip:

[source,javascript,subs=-attributes]
----
items: [
  { id: 36110175633573, quantity: 2 }
],
sections: "cart-items,cart-icon-bubble,cart-live-region-text,cart-footer",
sections_url: "/cart?some_param=foo"
----

Source: https://shopify.dev/docs/api/ajax/reference/cart[Shopify docs: Cart API reference, Bundled section rendering]

By default the sections render in the context of the current page, taken from the HTTP Referer header; `sections_url`
chooses another page, must begin with `/` and may carry query parameters. Rendering happens after the data change, so a
rendering failure does not change the HTTP status of the cart call: the section is `null` and the cart is already updated.
A `sections` or `sections_url` value that is invalid (a `sections_url` that does not begin with `/`) makes the whole request
return 400 Bad Request, although the rest of the request may have succeeded.

Source: https://shopify.dev/docs/api/ajax/section-rendering[Shopify docs: Section Rendering API]

Dawn does exactly this. Its `product-form.js` builds a `FormData` from the add to cart form, appends the IDs of the sections
its cart drawer needs as `sections` and the current path as `sections_url`, posts it to `routes.cart_add_url` and passes the
response to `cart.renderContents`.

The code has three parts. `cart-api.js` is a wrapper with no DOM access: it builds locale-aware URLs from
`Shopify.routes.root`, always sends the `sections` parameter when asked, turns every error response (an HTTP error status or a
`Cart Error` body, JSON or not) into one `CartError`, and can retry the "Cannot find variant" error with a growing delay. It
matches that error by its description, because the documentation gives status 422 for `add.js` and 404 for `update.js`. It
is loaded through the import map as `cart-api`.

[source,javascript,subs=-attributes]
----
/**
 * Thin wrapper around the Shopify Ajax Cart API (add.js, change.js, update.js, clear.js, cart.js).
 * No DOM access, so it can be unit-tested outside a browser.
 */

export class CartError extends Error {
  constructor({ status, message, description }) {
    super(description || message || 'Cart Error');
    this.name = 'CartError';
    this.status = status;
    this.description = description || message;
  }
}

/** Always build URLs from the locale-aware root, never from a hard-coded "/cart". */
const root = () => globalThis.Shopify?.routes?.root ?? '/';

/** POST endpoints live under cart/ (cart/add.js); the read endpoint is cart.js at the root. */
const endpoint = (name) => `${root()}cart/${name}.js`;

const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

async function request(url, init = {}) {
  const response = await fetch(url, {
    ...init,
    headers: { Accept: 'application/json', ...(init.headers || {}) },
  });

  let data = null;
  try {
    data = await response.json();
  } catch {
    // A throttled (429) or proxied response is not always JSON.
  }

  // Cart errors carry an HTTP error status and a body with status/message/description.
  if (!response.ok || (data && data.status && data.message === 'Cart Error')) {
    throw new CartError({
      status: data?.status ?? response.status,
      message: data?.message ?? 'Cart Error',
      description: data?.description ?? response.statusText,
    });
  }
  return data;
}

function post(name, payload, { sections = [], sectionsUrl, signal } = {}) {
  const body = { ...payload };
  if (sections.length > 0) {
    // Bundled section rendering: up to five sections, rendered after the cart change.
    body.sections = sections.join(',');
    body.sections_url = sectionsUrl ?? globalThis.location?.pathname ?? '/';
  }
  return request(endpoint(name), {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(body),
    signal,
  });
}

/**
 * Adds one or more variants. Each item: { id, quantity, properties?, selling_plan? }.
 * With retryUnknownVariant, a "Cannot find variant" error is retried with a growing delay
 * (products created or published through the Admin API take a few seconds to reach the cart).
 */
export async function addToCart(items, options = {}) {
  const { retryUnknownVariant = false, attempts = 3, baseDelayMs = 500 } = options;
  for (let attempt = 1; ; attempt += 1) {
    try {
      return await post('add', { items }, options);
    } catch (error) {
      // add.js reports an unknown variant as 422, update.js as 404: match the description, not the status.
      const unknownVariant = error instanceof CartError && /cannot find variant/i.test(error.description ?? '');
      if (!retryUnknownVariant || !unknownVariant || attempt >= attempts) throw error;
      await sleep(baseDelayMs * 2 ** (attempt - 1));
    }
  }
}

/** Changes one existing line by its 1-based position (the safe way to address duplicated variants). */
export function changeLine({ line, quantity, properties, selling_plan }, options = {}) {
  const payload = { line, quantity };
  if (properties !== undefined) payload.properties = properties;
  if (selling_plan !== undefined) payload.selling_plan = selling_plan;
  return post('change', payload, options);
}

/** Bulk update: { updates, note, attributes, discount }. update.js does not validate stock for lines already in the cart. */
export function updateCart(payload, options = {}) {
  return post('update', payload, options);
}

export function clearCart(options = {}) {
  return post('clear', {}, options);
}

export function getCart({ signal } = {}) {
  return request(`${root()}cart.js`, { signal });
}
----

Source: https://shopify.dev/docs/api/ajax/reference/cart[Shopify docs: Cart API reference]

`pocket-cart.js` is the DOM layer. It listens on `document`, so it works for forms and drawers that appear later; it
intercepts the add to cart form (`+form[action*="/cart/add"]+`), the quantity inputs and remove links of the drawer, and the
header's cart link (which still works as a plain link without JavaScript). It sets `aria-disabled` on the button while a
request is running, and not `disabled`, so the focus is not lost. It replaces only the cart body of the drawer with the
bundled section HTML, updates every `data-cart-count` element, and writes the section's `data-announce` text into the live
region that already exists in the page. If the section came back `null` after an add, it falls back to the cart page.

[source,javascript,subs=-attributes]
----
import { addToCart, changeLine, CartError } from 'cart-api';

// Static section rendered by layout/theme.liquid with {% section 'cart-drawer' %}: its id is the file name.
const SECTIONS = ['cart-drawer'];

const drawer = () => document.querySelector('[data-cart-dialog]');
const live = () => document.querySelector('[data-cart-live]');

/** Replaces the cart body with the HTML Shopify rendered in the same response. Null means the section failed to render. */
function applySections(sections) {
  const html = sections?.['cart-drawer'];
  if (!html) return false;

  const incoming = new DOMParser().parseFromString(html, 'text/html');
  const body = incoming.querySelector('[data-cart-body]');
  const current = document.querySelector('[data-cart-body]');
  if (!body || !current) return false;
  current.replaceWith(body);

  const count = body.dataset.itemCount ?? '0';
  document.querySelectorAll('[data-cart-count]').forEach((el) => {
    el.textContent = count;
  });
  if (live()) live().textContent = body.dataset.announce ?? '';
  return true;
}

function openDrawer() {
  const dialog = drawer();
  if (dialog && !dialog.open) dialog.showModal();
}

async function onAddToCart(form) {
  const button = form.querySelector('[data-add-to-cart]');
  const errorBox = form.querySelector('[data-product-error]');
  const data = new FormData(form);
  const item = { id: Number(data.get('id')), quantity: Number(data.get('quantity')) || 1 };

  button.setAttribute('aria-disabled', 'true');
  errorBox.hidden = true;
  try {
    const result = await addToCart([item], { sections: SECTIONS });
    if (applySections(result.sections)) {
      openDrawer();
    } else {
      // Section failed to render: fall back to the cart page, the cart itself is already updated.
      window.location.assign(`${window.Shopify.routes.root}cart`);
    }
  } catch (error) {
    errorBox.textContent = error instanceof CartError ? error.description : 'Network error';
    errorBox.hidden = false;
  } finally {
    button.removeAttribute('aria-disabled');
  }
}

async function onChangeLine(line, quantity) {
  try {
    const cart = await changeLine({ line, quantity }, { sections: SECTIONS });
    applySections(cart.sections);
    // Keep keyboard users in place: back to the same line, or to the heading when it was removed.
    const next = document.querySelector(`[data-line-qty][data-line="${line}"]`) ?? document.querySelector('[data-cart-heading]');
    next?.focus();
  } catch (error) {
    if (live()) live().textContent = error instanceof CartError ? error.description : 'Network error';
  }
}

document.addEventListener('submit', (event) => {
  const form = event.target;
  if (!(form instanceof HTMLFormElement) || !form.matches('form[action*="/cart/add"]')) return;
  event.preventDefault();
  if (form.querySelector('[data-add-to-cart]').getAttribute('aria-disabled') === 'true') return;
  onAddToCart(form);
});

document.addEventListener('change', (event) => {
  const input = event.target.closest?.('[data-line-qty]');
  if (input) onChangeLine(Number(input.dataset.line), Number(input.value));
});

document.addEventListener('click', (event) => {
  const remove = event.target.closest?.('[data-line-remove]');
  if (remove) {
    event.preventDefault();
    onChangeLine(Number(remove.dataset.line), 0);
    return;
  }
  const cartLink = event.target.closest?.(`a[href="${window.Shopify.routes.root}cart"]`);
  if (cartLink && drawer()) {
    event.preventDefault();
    openDrawer();
  }
  if (event.target.closest?.('[data-cart-close]')) drawer()?.close();
});

=== Other cart calls: note, attributes, discounts and shipping rates

`update.js` carries everything that is not a quantity change on a single line. For Pocket Coffee the cart note holds a gift
message, an attribute records the grind choice for a starter kit, and a Coffee Club member can enter a code:

[source,javascript,subs=-attributes]
----
import { updateCart } from 'cart-api';

await updateCart({
  note: 'Gift for Ada, please include a card.',
  attributes: { 'Gift wrap': 'Yes' },
  discount: 'COFFEECLUB',
});
----

Source: https://shopify.dev/docs/api/ajax/reference/cart[Shopify docs: Cart API reference]

A shipping estimate for the Spain zone uses the prepare and async endpoints with the same `shipping_address` parameters.
The destination is given as `shipping_address[zip]`, `shipping_address[country]` and `shipping_address[province]`, URL
encoded:

[source,text,subs=-attributes]
----
POST /cart/prepare_shipping_rates.json?shipping_address%5Bzip%5D=28001&shipping_address%5Bcountry%5D=Spain
GET  /cart/async_shipping_rates.json?shipping_address%5Bzip%5D=28001&shipping_address%5Bcountry%5D=Spain
----

Source: https://shopify.dev/docs/api/ajax/reference/cart[Shopify docs: Cart API reference]

The second call answers `null` until the rates are ready, so poll with a short, growing delay; a ready response lists
`shipping_rates` with `name`, `price`, `code` and the delivery fields. These two requests were not run.

=== Pitfalls

* Use the variant ID, not the product ID, for `id`. The `select name="id"` of the product form already holds the variant ID.
* Set `Content-Type: application/json` only when the body is JSON, as in the documentation's first example. With a
  `FormData` body leave the header out, so the browser adds the multipart boundary itself.
* A hard-coded `/cart/add.js` URL sends the request to the default language's cart. Use `Shopify.routes.root`.
* Do not rebuild the cart HTML in JavaScript, and do not format money in JavaScript. Ask for the section.
* Handle `null` sections and non-JSON error responses (HTTP 429) as well as the documented JSON errors.
* `section.index` is `nil` in the Section Rendering API, so code that depends on it for loading hints must tolerate that.
* A cart drawer opened by JavaScript has to remain reachable without it: keep the cart page and the add to cart form working
  as plain HTML.
* The Ajax API is not a place to keep secrets or to read customers and orders. Anything that needs them belongs to an app and
  the Admin API.
