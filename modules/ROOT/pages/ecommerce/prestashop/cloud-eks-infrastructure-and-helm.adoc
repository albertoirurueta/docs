== What the configuration builds

image::ecommerce-prestashop-cloud-opentofu-layout.svg["OpenTofu layout: one root module with an S3 state backend and two workspaces; a VPC with public, private, database and ElastiCache subnets; and ECR, Secrets Manager, KMS, ACM and WAF outside the VPC",width=760]

One root module in `infra/` creates one environment; the workspace (`staging` or `production`) chooses which. The files are split by service:

[cols="1,3",options=header]
|===
| File | Contents
| `versions.tf`, `variables.tf`, `locals.tf` | Constraints, the S3 backend, the provider, the inputs and the per-workspace settings (sizes, CIDR, host name) in one map
| `vpc.tf`, `kms.tf` | VPC with public, private, database and ElastiCache subnets in three zones; one customer-managed key
| `eks.tf` | EKS Auto Mode cluster, the EFS add-on, Pod Identity roles for the EFS driver and External Secrets Operator
| `rds.tf` | RDS for MySQL 8.4, Multi-AZ in production, with a managed master password
| `efs.tf` | EFS with one mount target per zone and one access point, `/shared`, owned by UID and GID 33
| `elasticache.tf` | Valkey replication group for PHP sessions and a Memcached cluster for the SQL cache
| `ecr.tf`, `secrets.tf` | The image repository and the GitHub OIDC push role; the Secrets Manager containers
| `acm.tf`, `waf.tf` | The regional certificate with DNS validation; a web ACL that restricts the back office
| `outputs.tf` | The values the chart needs
|===

== Decisions that differ from the WordPress platform

* *MySQL 8.4, not MariaDB.* RDS for MySQL 8.4 is the engine the PrestaShop pages of this section use (standard support until 2029-07-31;
  8.0 left standard support on 2026-07-31). Aurora and MariaDB are alternatives on
  xref:ecommerce/prestashop/cloud-managed-database.adoc[Cloud: Managed Database (RDS and Aurora)].
* *Two cache services, because the shop has two cache needs.* PHP sessions go to Valkey (a replicated, TLS-protected store). The shop's SQL
  cache has no Valkey or Redis backend: the 9.2.0 source has `CacheApc`, `CacheMemcache`, `CacheMemcached` and `CacheXcache` in `classes/cache/`
  and nothing for Redis, so the shared option is ElastiCache for Memcached. The reasons and the settings are on
  xref:ecommerce/prestashop/cloud-cache-sessions-and-back-office.adoc[Cloud: Cache, Sessions and the Back Office in a Cluster].
* *No media bucket in this configuration.* PrestaShop 9.2.0 has no S3 media option, so product images live on EFS and are served by nginx.
  A CloudFront distribution in front of the media host is optional and described on
  xref:ecommerce/prestashop/cloud-shared-media-and-files.adoc[Cloud: Shared Media and Writable Paths]; leaving it out also leaves out the
  `us-east-1` provider alias that the WordPress module needs.
* *One extra WAF rule.* The back office lives in the renamed folder `admin-pocketcoffee`; the web ACL blocks that path for every address
  outside an allow-list, which is cheaper than any in-application restriction and cannot be bypassed by a module.
* *Secrets are containers.* OpenTofu creates the Secrets Manager secrets; a script writes the values (below). The shop has more secret
  material than WordPress: the database credentials of two users, `secret`, `cookie_key`, `cookie_iv`, `new_cookie_key` and, since 9.0, the key pair of
  the Admin API.

== State backend and workspaces

The backend is the S3 bucket and the `use_lockfile` locking of the WordPress page, with another key, so that both platforms can share one
bucket. Create the bucket as shown in
xref:cms/wordpress/eks-infrastructure-with-opentofu.adoc#_the_state_backend[the state backend section] (use your own bucket name), then pass it
with `-backend-config`. The workspace map in `locals.tf` refuses `default`, as there, so a plan in the wrong workspace fails instead of creating
a third environment. The honest limits of workspaces (one credential for both environments) are on the same page; separate AWS accounts with
the same code are the stricter choice.

The providers are the AWS and random providers; there is no second AWS provider block because nothing in this configuration lives in

Identical in structure to the WordPress platform: three `/20` private subnets (pods take their addresses from them), three public `/24`

Source: https://github.com/terraform-aws-modules/terraform-aws-eks[terraform-aws-modules/terraform-aws-eks]

EKS Auto Mode runs node provisioning and patching, the block storage driver and the pod networking; the EFS CSI driver is an add-on with its own Pod
Identity role, and the External Secrets Operator reads only `+pocketcoffee/<env>/*+`. The WordPress page explains each of these points,
including why `enable_cluster_creator_admin_permissions` should be replaced by access entries for people and for the deployment role. Two
differences: there is no role for the shop pods, because without an S3 offload the pods call no AWS API, so a pod needs no cloud
identity at all and the chart's service account has token mounting turned off; and Auto Mode does not include a Gateway API controller, so
the platform team installs the AWS Load Balancer Controller for the `Gateway` that the chart's `HTTPRoute` attaches to (see
xref:cloud/aws/eks-microservices.adoc[Deploying Microservices on EKS]). Node replacement under Auto Mode happens at least every 21 days, so the
chart's PodDisruptionBudget must allow a drain.

Source: https://github.com/terraform-aws-modules/terraform-aws-rds[terraform-aws-modules/terraform-aws-rds]

`manage_master_user_password` lets RDS create and rotate the master password in Secrets Manager, so it never passes through OpenTofu. The
application connects as `ps_app` and the Jobs as `ps_migrate`, two users created after the first apply with the grants described on
xref:ecommerce/prestashop/cloud-managed-database.adoc[Cloud: Managed Database (RDS and Aurora)] (without `REQUIRE SSL` while the image has no TLS support), which is also where the connection arithmetic
(`pods x pm.max_children` against `max_connections`) and RDS Proxy are covered. Parameter notes:

* `utf8mb4` and `utf8mb4_general_ci` are the character set and one of the two collations that the 9.2.0 installer accepts (its
  `Install.php` allows `utf8mb4_general_ci` and `utf8mb4_unicode_ci`).
* There is no `sql_mode` entry on purpose: `DbPDO` and `DbMySQLi` in 9.2.0 run `+SET SESSION sql_mode = ''+` on each connection, so the shop does
  not depend on the server default.
* `max_allowed_packet` is raised to 64 MiB for large imports and module upgrades.
* TLS is not enforced, and the PrestaShop core cannot ask for it. The 9.2.0 `DbPDO::getPDO()` passes no SSL attribute to PDO and `parameters.php` has no
  key for one, so a server that requires TLS (`require_secure_transport=ON`) refuses the connection with error 3159 and the shop stops. The baseline of this
  page therefore leaves the parameter off and compensates with the private subnets and the security group. Encrypting the connection needs a
  class override and a patch of the Doctrine options baked into the image; they are on the database page, and the parameter is set only after the image carries them.

  encrypted   = true
  kms_key_arn = module.kms.key_arn

      security_groups = [aws_security_group.efs.id]
    }
  }

  # img/, upload/ and download/ live below /shared; every client is UID/GID 33 (www-data).
  access_points = {
    shared = {
      name = "shared"
      posix_user = {
        uid = 33
        gid = 33
      }
      root_directory = {
        path = "/shared"
        creation_info = {
          owner_uid   = 33
          owner_gid   = 33
          permissions = "0755"
        }
      }
    }
  }

  enable_backup_policy = true
}
----

Source: https://github.com/terraform-aws-modules/terraform-aws-efs[terraform-aws-modules/terraform-aws-efs]

One file system, one access point. The access point makes every client UID and GID 33 (`www-data`) and creates `/shared`, so the pods need no
root and no ownership changes. The six folders that the shop writes (`img`, `upload`, `download`, the import folder, the combined theme assets
and the theme settings) are `subPath` directories of that one volume; which folders those are, and why code never goes on EFS, is the subject of
xref:ecommerce/prestashop/cloud-shared-media-and-files.adoc[Cloud: Shared Media and Writable Paths].

Valkey is a replication group with cluster mode disabled, TLS, an AUTH token and Multi-AZ failover, as on the WordPress page, with one change:

protection) and nothing that cannot be rebuilt from the database. The Memcached servers are not configured in `parameters.php`; they are rows of the table `ps_memcached_servers`
(`ip`, `port`, `weight`), which the back office writes on the performance page. A shop that is created by a Job has to insert that row itself;
see the cache page. The engine versions are strings, `9.0` for Valkey and `1.6.22` for Memcached here: check the ElastiCache user guide for
the versions offered when you apply.

== Secrets for the shop

PrestaShop wants more secret material than WordPress, and every value has the same rule: *identical on every pod, and never regenerated
by a pod*. The shop has two database users, `ps_app` (web pods and cron) and `ps_migrate` (the install and migrate Jobs), and each has its own
secret in the shape of a database credential: `pocketcoffee/prod/prestashop-db-app` and `pocketcoffee/prod/prestashop-db-migrate`, each with the JSON
keys `username`, `password`, `engine`, `host`, `port` and `dbname`. That is the structure that the Secrets Manager rotation functions and RDS Proxy
expect, and a secret that also held cookie keys could not be handed to a rotation function. The ExternalSecret of the chart maps the `password` of each into
the Kubernetes Secret keys `DB_PASSWORD_APP` and `DB_PASSWORD_MIGRATE`, and the chart helper `pc.dbEnv` puts the right one into the container variable
`DB_PASSWD` (the name the official image and the installer use) next to `DB_USER`. All the other values live in `pocketcoffee/prod/prestashop`, and the
Valkey endpoint and AUTH token in `pocketcoffee/prod/valkey`. The keys of the shop secret become environment variables of the pods under their own names:

[cols="2,3",options=header]
|===
| Key | Used for
| `PS_SECRET` | The Symfony `secret` parameter (`framework.secret` in `app/config/config.yml`)
| `PS_COOKIE_KEY`, `PS_COOKIE_IV` | `+_COOKIE_KEY_+` and `+_COOKIE_IV_+`, defined by `config/bootstrap.php`: the legacy cookie, tokens such as the abandoned-cart link, and the salt for passwords hashed by very old versions
| `PS_NEW_COOKIE_KEY` | `+_NEW_COOKIE_KEY_+`, the key of the encrypted `Cookie` class (front and back office login state), also passed to the Admin API's OAuth2 server as its encryption key
| `PS_API_PRIVATE_KEY`, `PS_API_PUBLIC_KEY` | The OAuth2 key pair of the Admin API (`oauth.yml` passes them to `League\OAuth2\Server\CryptKey`); the 9.2.0 installer writes them to `parameters.php`
|===

The `new_cookie_key` is not random text: it is a checksummed key in the format of the `defuse/php-encryption` library (the installer calls
`PhpEncryption::createNewRandomKey()`), so the seeding script asks the shop image to generate it. The script refuses to overwrite an existing
value, because new cookie keys log every customer and employee out and invalidate links in e-mails already sent. It was checked with
`shellcheck` and `bash -n`; it was not run, because that needs a shop image and an AWS account.

[source,bash]
----
#!/usr/bin/env bash
# Writes the shop secrets into pocketcoffee/<env>/prestashop, the two database credentials
# into pocketcoffee/<env>/prestashop-db-app and -db-migrate, and the first administrator
# password into pocketcoffee/<env>/prestashop-install. Run once per environment by a
# person with secretsmanager:PutSecretValue; nothing is printed or stored in a file.
set -euo pipefail

env="${1:?usage: seed-secrets.sh <staging|prod> <image> <db-endpoint>}"
image="${2:?usage: seed-secrets.sh <staging|prod> <image> <db-endpoint>}"
db_host="${3:?usage: seed-secrets.sh <staging|prod> <image> <db-endpoint>}"
secret_id="pocketcoffee/${env}/prestashop"
db_app_id="pocketcoffee/${env}/prestashop-db-app"
db_migrate_id="pocketcoffee/${env}/prestashop-db-migrate"
install_id="pocketcoffee/${env}/prestashop-install"

gen() { openssl rand -base64 96 | tr -d '+/=\n' | cut -c1-"${1:-48}"; }

# Refuse to overwrite: new cookie keys log everyone out and break stored tokens.
if aws secretsmanager get-secret-value --secret-id "$secret_id" \
  --query SecretString --output text >/dev/null 2>&1; then
  echo "${secret_id} already has a value; rotate it deliberately." >&2
  exit 1
fi

# new_cookie_key is a checksummed key in the format of defuse/php-encryption,
# so it is generated by the library that ships in the shop image.
new_cookie_key="$(docker run --rm --entrypoint php "$image" -r \
  'require "/var/www/html/vendor/autoload.php"; echo Defuse\Crypto\Key::createNewRandomKey()->saveToAsciiSafeString();')"

# Key pair of the Admin API (OAuth2 signing keys), PEM text.
private_key="$(openssl genrsa 2048 2>/dev/null)"
public_key="$(printf '%s\n' "$private_key" | openssl rsa -pubout 2>/dev/null)"

payload="$(
  jq -n \
    --arg secret "$(gen 64)" --arg cookie_key "$(gen 64)" --arg cookie_iv "$(gen 32)" \
    --arg new_cookie_key "$new_cookie_key" \
    --arg api_private "$private_key" --arg api_public "$public_key" \
    '{PS_SECRET: $secret, PS_COOKIE_KEY: $cookie_key, PS_COOKIE_IV: $cookie_iv,
      PS_NEW_COOKIE_KEY: $new_cookie_key,
      PS_API_PRIVATE_KEY: $api_private, PS_API_PUBLIC_KEY: $api_public}'
)"

# The shape of a database credential, as the rotation functions and RDS Proxy read it.
db_credential() {
  jq -n --arg user "$1" --arg password "$(gen 40)" --arg host "$db_host" \
    '{username: $user, password: $password, engine: "mysql", host: $host, port: 3306, dbname: "pocketcoffee"}'
}

aws secretsmanager put-secret-value --secret-id "$secret_id" --secret-string "$payload" >/dev/null
aws secretsmanager put-secret-value --secret-id "$db_app_id" --secret-string "$(db_credential ps_app)" >/dev/null
aws secretsmanager put-secret-value --secret-id "$db_migrate_id" --secret-string "$(db_credential ps_migrate)" >/dev/null
aws secretsmanager put-secret-value --secret-id "$install_id" \
  --secret-string "$(jq -n --arg p "$(gen 24)" '{ADMIN_PASSWORD: $p}')" >/dev/null
echo "Seeded ${secret_id}, ${db_app_id}, ${db_migrate_id} and ${install_id}"
----

Source: https://docs.aws.amazon.com/cli/latest/reference/secretsmanager/put-secret-value.html[AWS CLI Reference: secretsmanager put-secret-value]

Run it as `./scripts/seed-secrets.sh prod 123456789012.dkr.ecr.eu-west-1.amazonaws.com/pocketcoffee/prestashop:<git-sha> <db_endpoint>` (the
image is the `<git-sha>` tag of the release, and `db_endpoint` is the output of the same name of the OpenTofu configuration), then create the two
database users with the passwords it generated (read them from the two database secrets in the console or with `aws secretsmanager get-secret-value`
inside a trusted shell; the SQL is on the database page). The passwords therefore exist in Secrets Manager and in the database, nowhere else.
Keep the characters of generated values to letters and digits: a `%` in a value is read by Symfony as the start of a parameter reference, which
is why `parameters.php` below escapes it.

== parameters.php from the environment

The installer writes `app/config/parameters.php` once, for one server. In a cluster the file is part of the image and reads the
environment, so every pod builds the same configuration from the same sources, and no pod ever writes it. This is the one way the whole section
deploys the file: the image of xref:ecommerce/prestashop/cloud-container-image.adoc[Cloud: Production Container Image] carries it, read-only, because a file that only calls `getenv()`
contains nothing secret, can be linted at build time and needs no rendering step. Mounting the file from a Kubernetes Secret would work too, but the
secrets would then be in a second place and the file would not be identical across images, so no page of the section does it.

[source,php]
----
<?php
/**
 * app/config/parameters.php for Kubernetes: the installer's file, rebuilt from the
 * environment. Plain settings come from a ConfigMap, secrets from a Secret that
 * External Secrets Operator creates from Secrets Manager.
 */

/** Read a variable; without a default, a missing value stops the process. */
$pc_env = static function (string $name, ?string $default = null): string {
    $value = getenv($name);
    if (false !== $value && '' !== $value) {
        return $value;
    }
    if (null !== $default) {
        return $default;
    }
    error_log("parameters.php: missing environment variable $name");
    throw new RuntimeException('Configuration error');
};

// Symfony reads % in a parameter as the start of a reference, so the installer writes
// every % as %%. config/bootstrap.php undoes it for the legacy constants.
$pc_escape = static fn (string $value): string => str_replace('%', '%%', $value);

return [
    'parameters' => [
        'database_host' => $pc_env('DB_SERVER'),

The file was checked with `php -l` and executed with test values in a `php:8.4-fpm` container (it returned the expected array, escaped the
`%` of a test password as `%%`, and a missing variable stopped it with an error in the log). Points that matter:

* *The keys are those the installer writes.* `Install.php` in 9.2.0 writes `database_host`, `database_port`, `database_user`,
  `database_password`, `database_name`, `database_prefix`, `database_engine`, `cookie_key`, `cookie_iv`, `new_cookie_key`, `api_public_key`,
  `api_private_key`, `ps_creation_date`, `secret` and `locale`, merged over `parameters.yml.dist` (which adds the `+mailer_*+` keys and
  `ps_caching`). Outbound mail is configured in the back office and stored in the database, so the `+mailer_*+` entries stay at their defaults.
* *`ps_cache_enable` is a real boolean.* `app/config/set_parameters.php` enables the Symfony cache pool backed by Memcached only when the value
  is `true` (strict comparison), so an environment string such as `"1"` would silently do nothing. `filter_var` converts it. `ps_caching`
  names the legacy class, `CacheMemcached`; the legacy constant `+_PS_CACHE_ENABLED_+` is defined from the same value by `config/bootstrap.php`.
* *Percent signs.* The installer writes `%` as `%%` (the Symfony escape) and `config/bootstrap.php` turns `%%` back into `%` for the legacy
  constants. The file does the same escape on every secret, so a password containing `%` works on both sides.
* *`ps_creation_date` is required.* `bootstrap.php` reads it unconditionally. For a new shop it is the day of the install, in the chart
  value `shop.creationDate`; for an imported shop it is the value of the old file.
* *A missing secret stops the process* with a log line, so a pod without its secrets fails instead of serving a shop that cannot log anyone in.
* *The cache stores the result.* `config/bootstrap.php` copies the parameters into `var/cache/<env>/appParameters.php` and refreshes that copy
  only when `parameters.php` is newer. The Symfony container is compiled from the same values. A cache built while the image is built, without
  the real environment, would therefore carry empty values into every pod. This is why the chart builds the cache in an init container of each
  pod, with the real environment, into an `emptyDir` (see the Deployment below). The reference page speaks of a cache built at image build time;
  that works only if the build runs with the same parameters, which a cluster image cannot know.

== Cluster prerequisites

Once per cluster, outside the chart: the namespace with the `restricted` Pod Security level (the pods below run as non-root with all
capabilities dropped, a read-only root file system and the default seccomp profile, which satisfies it), the External Secrets Operator
with its `ClusterSecretStore` named `aws-secretsmanager`, and the platform `Gateway` that routes attach to. The first two are the manifests of
the WordPress page (replace `lumenpress` by `pocketcoffee`); the Operator is installed with its Helm chart into the namespace
`external-secrets`, where the Pod Identity association of `eks.tf` already expects its service account. The `Gateway` with its
`LoadBalancerConfiguration` (the HTTPS listener with the ACM certificate from the output `site_certificate_arn`, and the web ACL from
`waf_acl_arn`) and the `TargetGroupConfiguration` are listed with their fields on
xref:cloud/aws/eks-microservices.adoc[Deploying Microservices on EKS], because they belong to the platform, not to one application; this page
does not repeat them, since the field names of those controller resources change between controller versions. The chart's route names the Gateway
by `httpRoute.parentRef`. A cluster that still uses an Ingress instead (ingress-nginx was retired in March 2026; the AWS controller's
`Ingress` is the alternative) uses the Ingress shown on the WordPress page with the same Service.

Source: https://devdocs.prestashop-project.org/9/basics/installation/advanced/nginx/[PrestaShop devdocs: Configure Nginx]

The nginx configuration is the one tested on the
xref:ecommerce/prestashop/installation-and-local-environments.adoc#nginx[installation page] with the changes of a pod: PHP-FPM is on
`127.0.0.1:9000`, the admin folder name and the trusted proxy range come from the values (the file is rendered with Helm's `tpl`), and two
locations are new. `/healthz` is answered by nginx itself. `/readyz` sends a FastCGI request whose `SCRIPT_NAME` is `/fpm-ping`, which PHP-FPM
answers by itself (`ping.path` in the pool file) without starting PHP code; the location sets only three parameters, because `fastcgi_params`
would add a second `SCRIPT_NAME`. A raw FastCGI request with exactly these parameters, sent to a `php:8.4-fpm` container with the pool file's
`ping.path`, returned `pong`, and one with another script name returned `File not found`. Neither location touches the database.

What the Deployment does and why:

* *Two containers, one pod.* nginx serves static files and passes `.php` to PHP-FPM on `127.0.0.1:9000`. The pods are spread over zones with a
  hard constraint (`DoNotSchedule`) and over nodes with a soft one, so losing a zone loses at most half of the capacity. `maxUnavailable: 0`
  makes a rollout add a pod before it removes one.
* *The `warmup` init container.* It runs `bin/console cache:warmup --env=prod` once for each application kernel, `admin` and `front`: in 9.2.0
  each kernel has its own cache directory, `var/cache/<env>/<app-id>`. It uses the pod's real environment and writes into the `emptyDir` that the
  two containers then mount, for the reason given in the `parameters.php` section. The first pod of a rollout starts in tens of seconds, not
  milliseconds; `maxSurge` hides that. Whether `cache:warmup` needs the database to be reachable was not tested: if it does, a database outage
  also stops new pods from starting, which is the safer failure.
* *Probes that do not use the database.* The liveness probes are a TCP check of PHP-FPM and nginx's own `/healthz`; readiness is `/readyz`,
  which only asks PHP-FPM whether it can accept a connection. A PrestaShop page always queries the database, so a probe on a shop URL would turn a
  database failover into "all pods unready", which removes every pod from the load balancer at the moment a retry would have worked. Application
  errors are seen by the load balancer's 5xx metric and by the alarms on the operations page, not by the kubelet.
* *`preStop` sleep and `terminationGracePeriodSeconds`.* Ten seconds of sleep let the load balancer deregister the pod before nginx stops, and
  the grace period covers it plus the longest request.
* *Writable paths.* The root file system is read-only. `/tmp`, `var/cache`, `var/logs` and the back-office export folder are per-pod
  `emptyDir` volumes, and the six shared folders are `subPath` mounts of the EFS claim. nginx mounts only the two it serves (`img` and the
  combined theme assets), read-only. `fsGroup: 33` makes the `emptyDir` volumes writable for the PHP user; EFS ownership comes from the access point.
  A module that writes elsewhere fails with "read-only file system" at the first write, which is how you find it before production does.
* *Logs.* PHP and nginx errors go to stderr. The production Monolog handler of the shop is a `rotating_file` handler (`app/config/config_prod.yml`)
  that takes its path from `PS_LOG_OUTPUT`, and a rotating handler appends a date to the path, so pointing it at a stream does not work; this
  was not tested. The chart gives the shop's own log an `emptyDir` and leaves shipping it to the operations page.
* *The configuration checksum.* A changed ConfigMap changes the pod template, so the pods roll.

The install Job runs the command-line installer of the xref:ecommerce/prestashop/installation-and-local-environments.adoc#_the_command_line_installer[installation page] once, in an empty
database. It deliberately differs from the web pods:

* *It runs from a separate image tag.* The runtime image has no `install/` folder and a read-only tree; the installer needs the folder and a place to
  write `app/config/parameters.php`. The `-install` tag is the same code with `install/` kept and a tree owned by UID 33. What the installer writes to
  that tree (its own `parameters.php`, with newly generated keys; the removal of `install/`; the renaming of the admin folder) disappears with
  the Job's container, and that is intended: the keys that count are the ones in Secrets Manager. A fresh install has nothing encrypted with
  the installer's temporary keys: employee and customer passwords are hashed with bcrypt, which does not use `cookie_key` (`Hashing::hash` calls
  `password_hash`).
* *It writes the database and the shared folders.* The shop is created in the database with the installer's arguments: `--domain` and `--ssl=1`
  become the row of `ps_shop_url` and the configuration `PS_SSL_ENABLED` (next section), and the installer copies default images into `img/`
  (which is why the Job mounts the shared volume; run the seeding Job of the shared-files page first so that the `subPath` directories exist
  with the right owner).
* *It is not a hook.* A `post-install` hook would run after the web pods are ready, and the pods would serve a half-installed shop. So the chart
  deploys the Job as an ordinary object and, while `install.enabled` is true, scales the web Deployment to zero. The deployment script runs the
  chart twice: the Job first, the pods second.
* *The administrator password is a Secrets Manager value, passed in a variable and then on the command line*, where it shows in the process list of
  the Job pod. Treat it as a first-login password: change it with `bin/console prestashop:employee:change-password` (new in 9.2) and delete the
  secret.
* *`--db_clear=1` is the installer's default*, so running it twice against the same database erases the shop. The Job has `backoffLimit: 0`
  and is only rendered by a deliberate flag, and the migration Job must never run in the same release.

== Shop domain and SSL

PrestaShop does not keep its address in `parameters.php`. It is in the database, in three places, and the installer writes all of them
from `--domain` and `--ssl`:

* the table `ps_shop_url`: `domain`, `domain_ssl` and `physical_uri` of each shop (the 9.2.0 installer sets both domains to the host it was started
  with and `main` and `active` to 1);
* the configuration keys `PS_SHOP_DOMAIN` and `PS_SHOP_DOMAIN_SSL` (the same host, no scheme);
* the configuration key `PS_SSL_ENABLED` (`1` when the installer ran with `--ssl=1`).

`Link` and `Tools` build every URL from `ps_shop_url` and `PS_SSL_ENABLED`, so a shop installed under another host name produces links to that
host. `Tools::usingSecureMode()` honours `X-Forwarded-Proto: https` by itself (it is the last test of that method), so the legacy front office
recognises HTTPS behind the load balancer without configuration; the Symfony back office needs `PS_TRUSTED_PROXIES`. If `PS_SSL_ENABLED` is
on and the proxy range is missing, a back-office request arriving over plain HTTP with an HTTPS referer raises "Infinite redirection detected,
please fill in the 'PS_TRUSTED_PROXIES' environment variable" (`SSLMiddlewareListener`); the front office redirects to itself when the scheme
it detects does not match. The configuration key `PS_SSL_ENABLED_EVERYWHERE` of older versions is no longer read: a search of the 9.2.0 source
finds it only in the changelog, which lists its removal. Set it nowhere.

To change the stored domain of a running shop (a migrated shop that still has the old host, or a staging copy) use the statements of the
xref:ecommerce/prestashop/installation-and-local-environments.adoc#_moving_a_shop_to_another_server_or_changing_its_domain[installation page] against RDS from a one-off pod with
the migrate credentials, not from a web pod:

[source,sql]
----
UPDATE ps_shop_url
   SET domain = 'www.pocketcoffee.example', domain_ssl = 'www.pocketcoffee.example'
 WHERE id_shop_url = 1;
UPDATE ps_configuration
   SET value = 'www.pocketcoffee.example'
 WHERE name IN ('PS_SHOP_DOMAIN', 'PS_SHOP_DOMAIN_SSL');
----

Source: https://devdocs.prestashop-project.org/9/basics/installation/advanced/install-from-cli/[PrestaShop devdocs: Installing PrestaShop from CLI]

and switch SSL on from the console, which sets the key through the configuration service of the shop:

[source,bash]
----
kubectl -n pocketcoffee exec deploy/pocketcoffee-web -c php-fpm -- \
  php bin/console prestashop:config set PS_SSL_ENABLED --value=1 --env=prod
----

Source: https://devdocs.prestashop-project.org/9/development/components/console/[PrestaShop devdocs: The Console component]

The `prestashop:config` command exists in 9.2.0 (`ConfigCommand` with `--value`, `--lang`, `--shopId` and `--shopGroupId`); that its `set`
action takes the key and `--value` as shown was read from the source, not run against the cluster. One caution: the host in `ps_shop_url`
must equal the `Host` header that reaches the pod, which is why the route forwards `www.pocketcoffee.example` unchanged and nginx passes it on. A multistore has one `ps_shop_url` row per shop and domain, and each needs its own route and
certificate name.

| When | A new shop, or a staging environment created from scratch | A shop that runs on a single server today
| Database | Empty database `pocketcoffee`, users `ps_app` and `ps_migrate` created | A dump imported into RDS, the same users created
| Secrets | Generated by the seeding script | The old `cookie_key`, `cookie_iv`, `new_cookie_key`, `secret` (and the Admin API keys, if the old shop has them) copied into the secret
| Files | Written by the installer into the shared volume | The old `img/`, `upload/` and `download/` copied into the volume
| `install.enabled` | `true` for the first release only | Never
| `shop.creationDate` | The day of the install | The old `ps_creation_date`
| Domain | Set by `--domain` | Updated in `ps_shop_url` and the configuration, as in the previous section
|===

An import is a different procedure with its own risks (the old cookie keys must be kept or every customer is logged out, and old
hashed passwords depend on `cookie_key`); it is on
xref:ecommerce/prestashop/cloud-migrating-from-a-single-server.adoc[Cloud: Migrating from a Single Server]. The deployment script below is the
first install; for an import, skip the first `helm upgrade` and run the second.

[source,bash]
----
#!/usr/bin/env bash
# First deployment of the chart to pocketcoffee-prod: install Job first, then the web pods.
set -euo pipefail

sha="${1:?usage: deploy.sh <git-sha>}"
region="eu-west-1"
db_host="$(tofu -chdir=infra output -raw db_endpoint)"
fs_id="$(tofu -chdir=infra output -raw efs_file_system_id)"
ap_id="$(tofu -chdir=infra output -raw efs_access_point_id)"

aws eks update-kubeconfig --name pocketcoffee-prod --region "$region"

common=(
  --namespace pocketcoffee
  --set image.tag="$sha"
  --set database.host="$db_host"
  --set shared.efs.fileSystemId="$fs_id"
  --set shared.efs.accessPointId="$ap_id"
)

# 1. Install: web pods at zero replicas, the install Job creates the shop in the empty database.
helm upgrade --install pocketcoffee ./pocketcoffee-prestashop "${common[@]}" \
  --set install.enabled=true --set migrate.enabled=false --wait --wait-for-jobs --timeout 25m

# 2. Serve: the Job is removed, the web pods start with the finished database.
helm upgrade pocketcoffee ./pocketcoffee-prestashop "${common[@]}" \
  --set migrate.enabled=false --wait --timeout 10m

kubectl -n pocketcoffee get pods,hpa,pdb,cronjob
----

Source: https://helm.sh/docs/helm/helm_upgrade/[Helm Docs: helm upgrade]

The script passed `shellcheck` and `bash -n`. `--wait-for-jobs` makes Helm wait until the install Job completes; the second command removes the
Job, creates the HPA and starts the pods. `migrate.enabled=false` is set on both runs because the installer already created the current
schema and modules; later releases run with the default (migrate on). Run `tofu -chdir=infra output` first, as the script does, so the chart receives the
endpoint and the EFS identifiers.

=== Verifying the deployment

[source,bash]
----
kubectl -n pocketcoffee get pods -o wide
kubectl -n pocketcoffee get httproute
curl -fsS -o /dev/null -w '%{http_code}\n' https://www.pocketcoffee.example/
curl -fsSI https://www.pocketcoffee.example/admin-pocketcoffee/ | head -n 1   # 403 from outside the allow-list
kubectl -n pocketcoffee exec deploy/pocketcoffee-web -c php-fpm -- php bin/console prestashop:config get PS_SSL_ENABLED --env=prod
kubectl -n pocketcoffee exec deploy/pocketcoffee-web -c php-fpm -- ls /var/www/html/var/cache/prod
----

Source: https://kubernetes.io/docs/reference/kubectl/quick-reference/[Kubernetes Documentation: kubectl quick reference]

Check that every pod shows `2/2` containers ready and runs in more than one zone; that the shop answers with the `www` host and its links are
HTTPS; that the back office answers 403 from an address outside `admin_cidrs` and its login page from inside; that `var/cache/prod` holds the
`admin` and `front` caches built by the init container; and that a file written to `img/` in one pod is visible from the others (the script on the
shared-files page).

== Common problems

* *`required: set image.tag to the git SHA` or `set database.host`.* The chart refuses to render without them: pass the values from the
  script.
* *Every pod fails with `Configuration error` and a line `missing environment variable` in the log.* The ExternalSecret has not produced the
  Secret (check `kubectl describe externalsecret` and the Pod Identity association) or a key is missing from the secret JSON.
* *A back-office redirect loop, or "Infinite redirection detected".* `PS_TRUSTED_PROXIES` does not contain the address the pod sees the load
  balancer from, or the shop is reached over HTTP behind a proxy that does not send `X-Forwarded-Proto`.
* *Links in the shop point at another host.* `ps_shop_url` or `PS_SHOP_DOMAIN` hold the host the installer saw; fix them as shown above.
* *The shop shows empty values, or connects to the wrong database, after a release.* A cache built without the pod's environment (for example
  copied from the image) is in use; delete the `emptyDir` by restarting the pod, and keep the `warmup` init container.
* *A cache clear in the back office changes nothing on other pods.* It clears one pod's `emptyDir`; releases replace the cache, see the cache page.
* *The install Job fails on the first write.* The `-install` tree is not writable by UID 33, or the `subPath` directories do not exist on the volume.
* *Pods cannot mount EFS.* Check the mount target security group, that a mount target exists in the pod's zone and that the PV names the file
  system and the access point of the outputs.
* *The web pods are unready after a database failover.* They should not be: if they are, a probe has been pointed at a shop URL.
