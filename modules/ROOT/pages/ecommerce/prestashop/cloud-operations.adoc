== What there is to operate

[cols="2,3,3",options="header"]
|===
| Concern | Where the signal or the data is | What PrestaShop adds
| Load | CPU of the `php-fpm` container, busy PHP-FPM workers, the listen queue | A request holds a database connection for its whole life, so more pods means more connections
| Errors | The Monolog file, the `ps_log` table, the PHP-FPM error log, the nginx access log | Three different places, only one of them on stdout by default
| Database | RDS metrics, the slow query log, Database Insights | A shop that writes visit statistics on every page view (`ps_connections`) has a different profile from a blog
| Data to recover | The RDS instance, the EFS volume with `img/`, `upload/` and `download/`, the secret | Rows and files refer to each other by id, so they have to be restored to the same moment
| Access | The back office folder, the login pages, the Admin API, the payment callbacks | The admin folder name is a build-time choice, and the callbacks are ordinary front controllers that must stay reachable
| Keys | `cookie_key`, `cookie_iv`, `new_cookie_key`, `secret` and the database passwords | Changing the cookie keys signs everyone out, and one of them also decides which old passwords still work
|===

== Autoscaling the web tier

A PrestaShop pod is a fixed pool of PHP-FPM workers. When every worker is busy, requests wait in the listen queue of the FastCGI socket and then time out at nginx, often before the CPU of the pod is saturated, because the workers wait for the database, for a payment module or for an HTTP call to a carrier. CPU is therefore a good first signal for pages that are mostly rendered from caches and a poor one for a shop whose requests wait. The signal that describes saturation directly is the number of busy workers.

=== Pods, workers and database connections

The number that ties scaling to the database is `pods x pm.max_children`. The legacy database class of PrestaShop does not use persistent connections (there is no `PDO::ATTR_PERSISTENT` in `classes/db/`), so a request opens a connection when it first needs the database and closes it when it ends; the number of open connections is the number of requests in flight, never more than `pods x pm.max_children`, plus the cron Job and the `pocketcoffee-migrate` Job. With 12 workers per pod and a ceiling of 12 pods that is 144 connections from the web tier, which has to fit under `max_connections` of the instance with room for the Jobs and for the monitoring user. The arithmetic and RDS Proxy are in xref:ecommerce/prestashop/cloud-managed-database.adoc[Cloud: Managed Database (RDS and Aurora)]; the HPA `maxReplicas` below is chosen from it, not from the budget of the cluster.

=== The HorizontalPodAutoscaler

The HorizontalPodAutoscaler computes CPU utilisation as a percentage of the CPU *request* of the containers of the pod, and reports `unknown` if there is no request, so the `php-fpm` container needs one that reflects real use. The sidecars count in the average too (the exporter and the log shipper below have small requests, which lowers the average a little). The listing scales on two metrics: the CPU of the pod and the number of busy workers per pod (`phpfpm_active_processes`, next section). With two metrics the controller computes a desired number of replicas for each and takes the larger.

[source,yaml]
.hpa.yaml
----
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: pocketcoffee-web
  namespace: pocketcoffee
  labels:
    app.kubernetes.io/name: pocketcoffee-prestashop
    app.kubernetes.io/component: web
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: pocketcoffee-web
  minReplicas: 3
  maxReplicas: 12
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 65
    - type: Pods
      pods:
        metric:
          name: phpfpm_active_processes
        target:
          type: AverageValue
          averageValue: "7"
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Percent
          value: 100
          periodSeconds: 60
        - type: Pods
          value: 4
          periodSeconds: 60
      selectPolicy: Max
    scaleDown:
      stabilizationWindowSeconds: 600
      policies:
        - type: Pods
          value: 1
          periodSeconds: 120
----

Source: https://kubernetes.io/docs/tasks/run-application/horizontal-pod-autoscale/[Kubernetes documentation: Horizontal Pod Autoscaling]

The numbers follow from the pool of the next section: with `pm.max_children = 12`, a target of 7 busy workers keeps about 40 percent of the workers free for a burst while new pods start. Three is the minimum so that the loss of one availability zone leaves two pods, and a PodDisruptionBudget (`maxUnavailable: 1`) has room to drain nodes. Scale up fast, because a campaign e-mail brings the traffic within a minute; scale down slowly (one pod every two minutes after ten minutes of lower load), because a new pod starts with a cold OPcache and an empty `var/cache`, which is the slowest the shop will ever be. The cache warm-up that shortens it is in xref:ecommerce/prestashop/cloud-releases-and-upgrades.adoc[Cloud: Releases and Upgrades].

The `Pods` metric needs an adapter that exposes it through the `custom.metrics.k8s.io` API: the Kubernetes SIGs `prometheus-adapter` with a rule over `phpfpm_active_processes`, or KEDA, which replaces the HPA by a `ScaledObject`. The rule, the `PodMonitor` and the trade-off are the same as for WordPress and are in xref:cms/wordpress/releases-upgrades-and-autoscaling-on-kubernetes.adoc#_php_fpm_metrics_as_a_custom_metric[Releases, Upgrades and Autoscaling on Kubernetes]. Until the adapter exists, delete the `Pods` entry and keep the CPU metric; an HPA that lists a metric it cannot read stops scaling with `FailedGetPodsMetric`.

=== Nodes

The HPA adds pods; it does not add nodes. Pods that do not fit stay `Pending` until the node layer reacts: Karpenter, or EKS Auto Mode which runs it for you, creates a node for them, and removes empty nodes later. Both are described in xref:cloud/aws/eks-clusters.adoc[EKS clusters]. Two consequences for this shop. First, set the CPU and memory *requests* of both containers honestly, because the node scheduler packs pods by requests. Second, an Auto Mode node is replaced at most every 21 days and Karpenter consolidates nodes, so pods are evicted regularly: keep the PodDisruptionBudget, a `preStop` pause so that nginx stops receiving traffic before the container ends, and `terminationGracePeriodSeconds` longer than the slowest checkout request. A pod that is killed in the middle of a payment callback is the one place where graceful termination has a cost you can measure in orders.

=== What scaling does not fix

* *The database.* Another pod does not make a slow query faster; it makes the next one run in parallel. If `phpfpm_listen_queue` grows while CPU of the pods is low, look at the database (slow queries, below) before raising `maxReplicas`.
* *The back office.* A catalogue import or a stock export is one long request with a large memory use. Give the pool `request_terminate_timeout` and size the memory limit for it, or route the back office to its own small Deployment.
* *The cron Job.* `pocketcoffee-cron` is a CronJob, not part of the HPA; if its runs overlap, set `concurrencyPolicy: Forbid`.

== PHP-FPM metrics

PHP-FPM publishes the state of its pool on a status page when `pm.status_path` is set. The page is served by FPM itself over FastCGI, not by nginx, so it is reachable only by a client that speaks FastCGI to port 9000 inside the pod, which is what the exporter does; nginx has no location that passes `/status` on, so it is not exposed to the internet. The official image already sends the FPM error log and the access log to stderr (`docker.conf` sets `error_log = /proc/self/fd/2` and `access.log = /proc/self/fd/2`), listens on port 9000, sets `catch_workers_output = yes` and `clear_env = no`; the last one matters for the secrets below, because with the default `clear_env = yes` PHP code cannot read the environment variables of the container.

[source,ini]
.zz-pocketcoffee.conf (copied to /usr/local/etc/php-fpm.d/ in the image)
----
[www]
pm = dynamic
pm.max_children = 12
pm.start_servers = 4
pm.min_spare_servers = 2
pm.max_spare_servers = 6
pm.max_requests = 500
pm.status_path = /status
ping.path = /ping
ping.response = pong
request_terminate_timeout = 60s
----

Source: https://www.php.net/manual/en/install.fpm.configuration.php[PHP Manual: FastCGI Process Manager (FPM) configuration]

The file is read after `docker.conf` because of its name (`zz-`), so it overrides the defaults of the image. It was checked with `php-fpm -t` in `php:8.4-fpm`; the pool keys are the PHP ones, not PrestaShop's. `pm.max_children = 12` assumes a memory limit of about 1 GiB for the container: measure the resident memory of a worker under your own traffic (the test shop used 10.7 MB for the home page, the back office needs far more, see xref:ecommerce/prestashop/performance-and-caching.adoc[Performance and Caching]) and divide. `pm.max_requests` recycles workers, which bounds the growth of a leaky module.

The exporter is a sidecar of the `pocketcoffee-web` pod. The community project `hipages/php-fpm_exporter` (not an official PHP or PrestaShop project) turns the status page into Prometheus metrics on port 9253. Version 2.2.0 was run against a real FPM with the pool file above and exposed, among others, these series, which are the ones that matter:

[cols="2,4",options="header"]
|===
| Metric | Meaning
| `phpfpm_active_processes` | Workers serving a request now. The value the HPA scales on.
| `phpfpm_idle_processes` | Workers waiting for a request.
| `phpfpm_listen_queue` | Requests waiting for a free worker. Anything above zero for more than a few seconds is saturation.
| `phpfpm_max_children_reached` | How many times the pool hit `pm.max_children`. Alert on its increase, not on its value.
| `phpfpm_max_active_processes` | The highest number of busy workers since the pool started. Tells whether `pm.max_children` is too high or too low.
| `phpfpm_slow_requests` | Requests slower than `request_slowlog_timeout`, when that is set.
|===

Check the names on the `/metrics` endpoint of the version you deploy before building a dashboard or an HPA on them; they are the contract between the pieces. The pod listing in the next section contains the sidecar; the alerts that earn a page are an increase of `phpfpm_max_children_reached` over five minutes, a `phpfpm_listen_queue` above zero for two minutes, and a 5xx rate at the load balancer. The PHP slow log (`request_slowlog_timeout`, `slowlog`) works through `ptrace`, which a hardened pod without the `SYS_PTRACE` capability does not have; use it in staging and rely on the database slow log and an APM agent in production.

== Logs

PrestaShop writes in three places, and the first thing to settle is which of them is on stdout, because that is the only one Kubernetes and CloudWatch collect without help.

[cols="2,3,3",options="header"]
|===
| Source | Where it goes | In a pod
| The Symfony logger (Monolog) used by the back office, the console and the Symfony part of the front office | `+var/logs/<environment>.log+`, rotated daily (`rotating_file` handler) with 30 files kept | On the container filesystem, lost with the pod, not on stdout
| The legacy logger `PrestaShopLogger` (the Monolog handler `prestashop.handler.log` for level `warning` on the `app` channel, and calls made by modules) | The `ps_log` table, shown in *Advanced Parameters > Logs* | In the shared database, and growing; purge it as in xref:ecommerce/prestashop/performance-and-caching.adoc[Performance and Caching]
| PHP errors and the FPM access log | stderr of PHP-FPM | On the container output, collected
| nginx access and error log | `/dev/stdout` and `/dev/stderr` of the nginx container | On the container output, collected
|===

In `app/config/config.yml` of 9.2.0 the main Monolog handler is `rotating_file` with `+path: '%env(PS_LOG_OUTPUT)%'+` and `+max_files: '%env(int:PS_LOG_MAX_FILES)%'+`, and the defaults are `+%kernel.logs_dir%/%kernel.environment%.log+` and `30`. `config_prod.yml` wraps it in a `fingers_crossed` handler with `action_level: error`, so in production the log stays quiet until a request produces an error and then contains every record of that request, down to debug level. That is the behaviour you want from a log you read after an incident, and it keeps the volume small.

The obvious way to get the log onto stdout is to set `PS_LOG_OUTPUT=php://stderr`. *It does not work with the shipped handler.* The `rotating_file` handler of Monolog builds a dated file name from the path (`name-YYYY-MM-DD.ext`) and opens that; with `php://stderr` it creates a directory `php:` and a file `stderr-2026-10-29` in the working directory and writes there. This was reproduced with Monolog 2.10.0, the version locked by PrestaShop 9.2.0; a plain `StreamHandler` on `php://stderr` does work, but PrestaShop does not use one. There are two honest options:

. *Keep the file and ship it.* Point `PS_LOG_OUTPUT` at a directory that is an `emptyDir` shared with a log-shipper sidecar, and let the sidecar read the files and write them to its own stdout. Nothing in the core is changed, upgrades do not touch it, and this is what the listing below does.
. *Change the handler at build time*, for example with a `sed` in the Dockerfile that replaces `type: rotating_file` by `type: stream` in `app/config/config_prod.yml`. This puts the log on the container output with no sidecar, but it edits a core file that every core upgrade overwrites; it was not tested here, and the monolog-bundle options of the `stream` handler should be read before relying on it.

The listing shows the pod as the chart renders it, with the four containers of the web pod (nginx, PHP-FPM, the exporter and the log shipper) and the `emptyDir` volumes. The image tag `<git-sha>` and the secret names are those of the chart; the Helm template that produces this is in xref:ecommerce/prestashop/cloud-eks-infrastructure-and-helm.adoc[Cloud: EKS Infrastructure and Helm Deployment].

`fsGroup: 33` makes the `emptyDir` writable by `www-data`, the user of the PHP workers. `PS_LOG_MAX_FILES=2` keeps two daily files on the volume, which is plenty because the sidecar has already read them, and the `sizeLimit` evicts a pod whose log explodes instead of filling the node. The `preStop` pause gives the load balancer time to take the pod out of rotation before nginx stops accepting connections. The `ps-logs` volume is separate from the writable paths that must be shared between pods (`img/`, `upload/`, `download/` on EFS, see xref:ecommerce/prestashop/cloud-shared-media-and-files.adoc[Cloud: Shared Media and Writable Paths]); a log is per pod and is never shared. The excerpt was validated with `kubeconform -strict` against the Kubernetes 1.36 schemas; the real chart also mounts the shared volume, the probes and the secrets.

=== From the container output to CloudWatch Logs

Once everything is on the container output, collection is the same as for any pod. The Amazon CloudWatch Observability add-on of EKS installs the CloudWatch agent and Fluent Bit and sends the container output of every pod to log groups under `/aws/containerinsights/pocketcoffee-prod/` (the application logs in the group `application`). Whether the add-on is supported on an EKS Auto Mode cluster in your configuration, and the IAM role it needs (the managed policy `CloudWatchAgentServerPolicy`, through EKS Pod Identity or IAM roles for service accounts), are in the AWS documentation; verify both before choosing it over a log collector you run yourself.

[source,bash]
.Installing the add-on and setting the retention of the group
----
#!/usr/bin/env bash
set -euo pipefail

CLUSTER=pocketcoffee-prod
REGION=eu-west-1

# The role must carry CloudWatchAgentServerPolicy; the ARN comes from the OpenTofu stack.
aws eks create-addon \
  --region "$REGION" \
  --cluster-name "$CLUSTER" \
  --addon-name amazon-cloudwatch-observability \
  --pod-identity-associations "serviceAccount=cloudwatch-agent,roleArn=arn:aws:iam::123456789012:role/pocketcoffee-prod-cloudwatch-agent"

# Log groups are created without an expiry: set one explicitly.
aws logs put-retention-policy \
  --region "$REGION" \
  --log-group-name "/aws/containerinsights/${CLUSTER}/application" \
  --retention-in-days 30
----

Source: https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Container-Insights-setup-EKS-addon.html[Amazon CloudWatch User Guide: Quick Start with the Amazon CloudWatch Observability EKS add-on]

A Logs Insights query over the group finds the requests that failed. The field names of the Kubernetes metadata depend on the collector version, so look at one event before saving the query:

[source,text]
.CloudWatch Logs Insights
----
fields @timestamp, kubernetes.pod_name, log
| filter log like /app\.(ERROR|CRITICAL)/
| sort @timestamp desc
| limit 50
----

Source: https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/CWL_QuerySyntax.html[Amazon CloudWatch Logs User Guide: CloudWatch Logs Insights query syntax]

The Monolog line is plain text (`pass:c[[2026-10-29T17:52:51.316648+00:00\] app.ERROR: message [\] [\]]`), not JSON, which is why the query matches on text. Alerting on it is a metric filter on the log group with an alarm; the pattern is in xref:cloud/aws/monitoring-and-observability.adoc[Monitoring and observability on AWS]. If you prefer a collector that you run, a Fluent Bit sidecar with the `cloudwatch_logs` output does the same without the add-on.

== Slow queries

The database is where a PrestaShop shop usually spends its time, and RDS keeps a log of the statements that took too long. It is off by default: turn it on in the parameter group and export it to CloudWatch Logs, so that it can be searched from the same place as the application logs. The listing is the part of the OpenTofu stack that concerns logging and the retention of the group that RDS creates; the instance itself is in xref:ecommerce/prestashop/cloud-managed-database.adoc[Cloud: Managed Database (RDS and Aurora)].

[source,hcl]
.slow-query-log.tf
----
terraform {
  required_version = ">= 1.8"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = "eu-west-1"
}

resource "aws_db_parameter_group" "prestashop" {
  name   = "pocketcoffee-prod-mysql84"
  family = "mysql8.4"

  parameter {
    name  = "slow_query_log"
    value = "1"
  }

  parameter {
    name  = "long_query_time"
    value = "1"
  }

  parameter {
    name  = "log_output"
    value = "FILE"
  }
}

# On the aws_db_instance "pocketcoffee-prod" of the database page:
#   parameter_group_name            = aws_db_parameter_group.prestashop.name
#   enabled_cloudwatch_logs_exports = ["error", "slowquery"]

resource "aws_cloudwatch_log_group" "slowquery" {
  name              = "/aws/rds/instance/pocketcoffee-prod/slowquery"
  retention_in_days = 30
}
----

Source: https://registry.terraform.io/providers/hashicorp/aws/latest/docs/resources/db_parameter_group[Terraform Registry: aws_db_parameter_group (AWS provider)]

The registry page documents the AWS provider that OpenTofu uses unchanged. The log group is created by RDS the first time a log is exported; declaring it first, with the exact name, gives it a retention instead of keeping everything for ever. On Aurora MySQL the same parameters live in the *cluster* parameter group. A `long_query_time` of 1 second is a starting point: lower it to 0.5 for a week during a performance investigation, then back, because the log itself costs I/O and storage.

What to expect in the log is a function of the shop. The tables that grow with traffic and with the age of the shop (`ps_connections`, `ps_guest`, `ps_log`, `ps_cart` and its products) are the usual suspects, and the purge that keeps them small is in xref:ecommerce/prestashop/performance-and-caching.adoc[Performance and Caching]; the SQL cache (`CacheMemcached` on ElastiCache for Memcached, see xref:ecommerce/prestashop/cloud-cache-sessions-and-back-office.adoc[Cloud: Cache, Sessions and the Back Office in a Cluster]) hides repeated reads from the log, so a query that is slow and cached shows up rarely. A first aggregate over the slow log:

[source,text]
.CloudWatch Logs Insights on /aws/rds/instance/pocketcoffee-prod/slowquery
----
parse @message /Query_time: (?<qt>[0-9.]+)/
| filter ispresent(qt)
| stats count(*) as slow, max(qt) as worst, avg(qt) as mean by bin(1h)
| sort @timestamp desc
----

Source: https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_LogAccess.Concepts.MySQL.html[Amazon RDS User Guide: MySQL database log files]

Statement-level analysis is the job of CloudWatch Database Insights. It replaced the Performance Insights console experience, shows the load of the instance by wait event, SQL statement and user (so the `ps_app` application, the `ps_migrate` Job and the back office show up as separate sources only if they use separate users, which is one reason for having them), and in its Advanced mode also execution plans and on-demand analysis. The modes, the retention and their cost drivers are in xref:cloud/aws/rds.adoc[Amazon RDS]; choose the mode per instance, and check the current wording on the AWS page before relying on the old Performance Insights flags in automation.

== Backups and disaster recovery

A single-server PrestaShop is backed up by a dump of the database and an archive of the shop directory. On EKS the same information is in separate stores with separate recovery points, and the question to answer is whether they can be brought back to the *same moment*.

[cols="2,3,3",options="header"]
|===
| Component | Backup | Recovery
| RDS `pocketcoffee-prod` | Automated backups with point-in-time recovery (retention set on the instance), a manual snapshot before each release, an AWS Backup copy to a second region | `restore-db-instance-to-point-in-time` or `restore-db-instance-from-db-snapshot` create a *new* instance; the shop is repointed to it
| EFS `pocketcoffee-shared` (`img/`, `upload/`, `download/`) | AWS Backup, with a cross-region copy | A restore job creates a *new* file system; the PersistentVolume is repointed to it
| Secret `pocketcoffee/prod/prestashop` | Versions in Secrets Manager, a replica secret in the DR region | Promote the replica. Losing the cookie keys signs everyone out and breaks some old passwords, see the last section
| ECR `pocketcoffee/prestashop` | Replication to the DR region; the image is rebuildable from Git | Pull in the DR cluster
| Chart, `infra/` OpenTofu, Dockerfile, state | Git and a versioned state bucket | `tofu apply` in the DR region
| Valkey, Memcached, `var/cache`, Smarty cache | None, on purpose | Start empty; expect a slow first minutes
|===

Source: https://docs.aws.amazon.com/aws-backup/latest/devguide/cross-region-backup.html[AWS Backup Developer Guide: Creating backup copies across AWS Regions]

=== Before a release and the restore drill

A snapshot before every release is the rollback of the database part of a release; it takes the place of the dump that a single server would make. The restore drill is the part that proves the rest, and it belongs in the calendar (quarterly is a reasonable cadence), not in the incident.

[source,bash]
.Snapshot before a release, and a point-in-time restore into a drill instance
----
#!/usr/bin/env bash
set -euo pipefail

REGION=eu-west-1
SNAPSHOT="pocketcoffee-prod-pre-$(date -u +%Y%m%d%H%M)"

# 1. Before the release: a manual snapshot that no retention rule deletes.
aws rds create-db-snapshot \
  --region "$REGION" \
  --db-instance-identifier pocketcoffee-prod \
  --db-snapshot-identifier "$SNAPSHOT"
aws rds wait db-snapshot-available \
  --region "$REGION" \
  --db-snapshot-identifier "$SNAPSHOT"

# 2. The drill: restore the last restorable moment, or a chosen time, into a NEW instance.
aws rds restore-db-instance-to-point-in-time \
  --region "$REGION" \
  --source-db-instance-identifier pocketcoffee-prod \
  --target-db-instance-identifier pocketcoffee-restore-drill \
  --use-latest-restorable-time \
  --db-subnet-group-name pocketcoffee-db \
  --no-publicly-accessible
aws rds wait db-instance-available \
  --region "$REGION" \
  --db-instance-identifier pocketcoffee-restore-drill

aws rds describe-db-instances \
  --region "$REGION" \
  --db-instance-identifier pocketcoffee-restore-drill \
  --query 'DBInstances[0].Endpoint.Address' \
  --output text
----

Source: https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html[Amazon RDS User Guide: Restoring a DB instance to a specified time]

The restored instance has the data and the engine settings, and not the security groups, the parameter group or the users' network paths unless you pass them; give it the same subnet group, security group and parameter group as production, and attach the same monitoring. Point a staging release at it (`database.host` of the chart) and check the shop: the home page, a product, a checkout in test mode, a back office login, and the numbers of `ps_orders` and `ps_customer` against what you expect. A drill that ends at "the instance is available" has not shown that the shop works.

The file system is restored from a recovery point of the vault. The metadata of the restore is read from the recovery point and changed to ask for a new file system; the file system id of the production volume stays untouched:

[source,bash]
.Restoring the EFS file system into a new one
----
#!/usr/bin/env bash
set -euo pipefail

REGION=eu-west-1
VAULT=pocketcoffee-primary
RESOURCE_ARN="$1"   # the ARN of the EFS file system pocketcoffee-shared
ROLE_ARN=arn:aws:iam::123456789012:role/pocketcoffee-backup

RECOVERY_POINT_ARN=$(aws backup list-recovery-points-by-backup-vault \
  --region "$REGION" \
  --backup-vault-name "$VAULT" \
  --by-resource-arn "$RESOURCE_ARN" \
  --query 'sort_by(RecoveryPoints, &CreationDate)[-1].RecoveryPointArn' \
  --output text)

# The restore metadata of an EFS recovery point has to be changed to ask for a new file system.
METADATA=$(aws backup get-recovery-point-restore-metadata \
  --region "$REGION" \
  --backup-vault-name "$VAULT" \
  --recovery-point-arn "$RECOVERY_POINT_ARN" \
  --query 'RestoreMetadata' \
  --output json | jq -c '. + {newFileSystem: "true", CreationToken: ("pocketcoffee-drill-" + (now | floor | tostring))}')

aws backup start-restore-job \
  --region "$REGION" \
  --recovery-point-arn "$RECOVERY_POINT_ARN" \
  --iam-role-arn "$ROLE_ARN" \
  --metadata "$METADATA" \
  --resource-type EFS
----

Source: https://docs.aws.amazon.com/aws-backup/latest/devguide/restoring-efs.html[AWS Backup Developer Guide: Restore an Amazon EFS file system]

The scripts were checked with `shellcheck`; the `jq` expression was run on a sample metadata object, and the exact keys of the restore metadata for your recovery point must be read from the output of `get-recovery-point-restore-metadata` as above, not typed. When the job finishes, create a mount target and an access point (uid and gid 33) on the new file system, point a drill PersistentVolume at it, and check that `img/p/` and `upload/` have the files you expect.

=== The two stores must agree

The database stores the ids of products, images and attachments, and the file system stores the files under paths made from them (`img/p/1/2/3/123.jpg`), so a database from Monday with the images of Wednesday is not a disaster, but a database of Wednesday with the images of Monday shows broken product pictures for everything uploaded in between. The rules that follow:

* Restore both to the same moment when you can. A daily plan at 02:00 gives a database and a file system within minutes of each other.
* If the files are older than the database, the thumbnails are regenerated from the originals with `bin/console prestashop:thumbnails:regenerate`, but an original that was not in the backup is gone; the product page has to be edited again.
* If the database is older than the files, the extra files are unreferenced and harmless.
* A point-in-time restore loses the orders placed between the chosen time and the failure. The payment provider still holds the payments: reconcile its list of transactions against `ps_orders` before reopening, and decide for each missing order whether to recreate it or to refund. This is the largest cost of a database recovery for a shop, and the reason to keep the RPO of the database in minutes.

=== Disaster recovery in a second region

The RPO and the RTO of a regional loss are different from the single-instance backup. The database is as old as the last copy in the vault of `eu-central-1` (daily with this plan, so up to a day; shorten the schedule or add a cross-region read replica if that is too long), the files are as old as their copy, the secret and the image are replicated, and the code is in Git. The RTO is dominated by the steps that are not automatic: applying the OpenTofu stack in the DR region, restoring the database and the file system, and changing the DNS record of `www.pocketcoffee.example` (a health-checked failover record in Route 53 does the last step when the primary is down). Write the order down, rehearse it once a year in a scratch account or region, and keep the runbook outside the platform that it recovers.

== AWS WAF in front of the shop

A web ACL in front of the load balancer (or of CloudFront) removes a class of traffic before PHP sees it: known bad inputs, SQL injection patterns, bots with a bad reputation, and the brute force against the login forms. It does not replace a patched PrestaShop and modules, the secure coding rules, or the hardening of xref:ecommerce/prestashop/security.adoc[Security]; it buys time between an advisory and the rollout of the fix. The pieces that are specific to PrestaShop are three paths:

[cols="2,4",options="header"]
|===
| Path | Treatment
| `/admin-pocketcoffee/` (the renamed back office folder) | Allowed only from the office and VPN addresses, and a rate limit on the `POST` requests of the login. The folder name is changed at build time; the name alone is not a defence, the address list is.
| `/login` (the default URL of the customer authentication page, from the install data of `meta.xml`), and `/admin-api/` if the Admin API is in use | A rate limit per client address on `POST`; the Admin API additionally by the access token it requires.
| `+/module/pocketcoffee_pay/+` (the front controllers of the payment module, URLs of the form `+module/{module}/{controller}+`, from the `module` route of `classes/Dispatcher.php`) | Must be reachable from the payment provider. Excluded from the managed rule groups, whose body inspection rejects some webhook payloads, and protected instead by the signature that the module verifies, a generous rate limit, and the provider's published source addresses when it has them.
|===

== Rotating secrets

Not every secret rotates in the same way, and in PrestaShop the difference is large. The table lists what the shop reads, from `parameters.php`, and what happens when it changes.

[cols="2,2,4",options="header"]
|===
| Secret | Where | What a change does
| Database passwords (`ps_app`, `ps_migrate`) | Secrets Manager, read as `database_password` | Nothing, if the new password is valid in the database before the pods read it. Pods that keep the old one fail to connect, so rotate with two users that alternate, or restart the pods in the same step.
| `secret` | `framework.secret` in `config.yml` | The Symfony secret from which tokens and signatures are derived. Forms of the back office that were opened before the change fail their CSRF check and have to be reloaded. Nothing else is stored under it.
| `cookie_iv` | `+_COOKIE_IV_+` | The salt of the checksum inside the cookie, also used by `Tools::hashIV`. A change invalidates every cookie, like the next row.
| `new_cookie_key` | `+_NEW_COOKIE_KEY_+` | The key that encrypts the cookie. A change signs everyone out. See the last section.
| `cookie_key` | `+_COOKIE_KEY_+` | The static salt of the legacy password hash, of `Tools::hash` and of the cart recovery token in e-mails. A change locks out some accounts. See the last section.
|===

=== How the pods get a new value

The values reach the pod as environment variables built from a Kubernetes Secret that the External Secrets Operator keeps in step with Secrets Manager. A change in Secrets Manager updates the Secret within `refreshInterval`, but *a running container never sees a changed environment variable*, and there is a second reason that a restart is needed in PrestaShop: `config/bootstrap.php` evaluates `app/config/parameters.php`, writes the resulting array with `var_export` to `var/cache/<environment>/appParameters.php`, and reuses that file for as long as it is newer than `parameters.php`; the Symfony container compiled in `var/cache` also contains the parameters. Values read with `getenv()` in `parameters.php` are therefore *frozen into the cache* at the first request of the pod. Two rules follow: the rotated value takes effect when a pod starts with an empty `var/cache`, which is why the cache directory is a per-pod `emptyDir` (never a cache baked into the image with placeholder values, or the placeholders win because the cache file is newer than `parameters.php`), and every rotation ends with a rolling restart of the Deployment.

  region = "eu-west-1"
}

variable "rotation_lambda_arn" {
  type        = string
  description = "ARN of the Secrets Manager rotation function for MySQL with the alternating-users strategy"
}

resource "aws_secretsmanager_secret" "db_app" {
  name = "pocketcoffee/prod/prestashop-db-app"
}

resource "aws_secretsmanager_secret_rotation" "db_app" {
  secret_id           = aws_secretsmanager_secret.db_app.id
  rotation_lambda_arn = var.rotation_lambda_arn

  rotation_rules {
    automatically_after_days = 30
  }
}
----

Source: https://docs.aws.amazon.com/secretsmanager/latest/userguide/rotating-secrets-mysql.html[AWS Secrets Manager User Guide: Rotate Amazon RDS for MySQL database credentials]

The *alternating users* strategy keeps two database users (`ps_app` and `ps_app_clone`) and rotates the password of the one that is not in use, then switches the secret to it; the old password stays valid for one more rotation period. That window is what lets the rolling restart of the pods happen after the secret changed, without a moment in which the pods have a password that the database has already dropped. With the *single-user* strategy the password changes in the database and in the secret at the same instant, and every pod that has not restarted fails until it does. The function itself is created from the AWS templates for RDS MySQL (it runs in the VPC and needs a network path to Secrets Manager and to the database); the page does not reproduce it. The secret of the user that creates the schema and runs the upgrades (`ps_migrate`) is read by the Jobs only, so a rotation of it does not touch the web pods. The chart of the Helm page takes `DB_USER` from the value `database.appUser` and only the password from the secret, which fits the single-user strategy; with alternating users the user name changes with every rotation, so add `- secretKey: DB_USER_APP` with `property: username` to the `data` list of the ExternalSecret above and read `DB_USER` from that key in the helper `pc.dbEnv`. The listing of `rotation.tf` shows only the rotation of the secret that the OpenTofu configuration of the Helm page already declares as `aws_secretsmanager_secret.db_app`; in that configuration add the `aws_secretsmanager_secret_rotation` resource and not a second secret.

[source,bash]
.Rotating and rolling out
----
#!/usr/bin/env bash
set -euo pipefail

REGION=eu-west-1

# 1. Rotate now (outside the schedule) and wait for the new version to become current.
aws secretsmanager rotate-secret \
  --region "$REGION" \
  --secret-id pocketcoffee/prod/prestashop-db-app

# 2. Force the External Secrets Operator to read it now instead of waiting for refreshInterval.
kubectl --namespace pocketcoffee annotate externalsecret pocketcoffee-secrets \
  "force-sync=$(date +%s)" --overwrite

# 3. Restart the pods: each new pod starts with an empty var/cache and reads the new environment.
kubectl --namespace pocketcoffee rollout restart deployment/pocketcoffee-web
kubectl --namespace pocketcoffee rollout status deployment/pocketcoffee-web --timeout=10m

# 4. Check that the shop answers and that the pods connect.
kubectl --namespace pocketcoffee get pods -l app.kubernetes.io/component=web
curl --fail --silent --show-error --output /dev/null https://www.pocketcoffee.example/
----

Source: https://external-secrets.io/latest/introduction/faq/[External Secrets Operator: FAQ]

The annotation trick is the one of the Operator's documentation for forcing a reconciliation. A controller such as Reloader (`stakater/Reloader`) can restart the Deployment automatically when the Secret changes; it replaces step 3 and nothing else, and it should be tested on staging, because an unexpected restart in the middle of a campaign is also a rotation.

== The cookie keys

Three values in `parameters.php` look alike and do different things. They are read in `config/bootstrap.php` and defined as constants, and the table is what the 9.2.0 source does with each.

[cols="2,5",options="header"]
|===
| Parameter | What the code does with it
| `new_cookie_key` (`+_NEW_COOKIE_KEY_+`) | The key of the encryption of the front-office and back-office cookie: `+new Cookie(...)+` creates `+new PhpEncryption(_NEW_COOKIE_KEY_)+`, a `defuse/php-encryption` key in its ASCII form (136 characters, it is not a free-form string). Everything that identifies a visitor or an employee to the shop (customer id, cart id, language, employee id, the session token) is inside the encrypted cookie.
| `cookie_iv` (`+_COOKIE_IV_+`) | The salt of the checksum that is stored inside the cookie (a SHA-256 over the salt and the content, in `Cookie::update()`), and of `Tools::hashIV`. It is not an initialisation vector of the encryption, in spite of the name.
| `cookie_key` (`+_COOKIE_KEY_+`) | The *static salt* of the legacy password hashing (`Hashing::hash` and `checkHash`, where the old `md5(salt . password)` format is still accepted), of `Tools::hash`, and of the cart recovery token (`+md5(_COOKIE_KEY_ . 'recover_cart_' . id)+`) that the shop writes into abandoned cart e-mails and the back office writes into the links it sends to customers.
|===

Source: https://github.com/PrestaShop/PrestaShop/blob/9.2.0/config/bootstrap.php[PrestaShop 9.2.0: config/bootstrap.php]

=== What goes wrong, and what does not

*A pod without the keys invents its own.* In `config/bootstrap.php`, if `cookie_key`, `cookie_iv` or `new_cookie_key` is missing from the parameters, the constant is defined anyway "to prevent failure in the composer post-install script", from `Tools::passwdGen` or `PhpEncryption::createNewRandomKey()`, *at every start of PHP*. In a deployment where the environment variable is empty or misspelled, nothing fails: the shop answers, but every request has a different key, nobody can stay logged in, and the cart seems to empty itself. All pods must have the same three values, and an empty one must fail the deployment, not start the shop. The entrypoint of the container should therefore refuse to start when one of the three values is empty.

*A cookie that cannot be decrypted is a logout, not an error.* `PhpEncryptionEngine::decrypt` returns `false` for a wrong key, `Cookie::update()` then finds no checksum and calls `logout()`, which deletes the session record and empties the cookie. Visitors see no error page; customers are logged out, a guest loses the link to the cart (the cart row stays in the database, a logged-in customer finds it again), and employees have to sign in again. The behaviour was checked in the source, and the key behaviour with `defuse/php-encryption` (a different key raises `WrongKeyOrModifiedCiphertextException`, which PrestaShop turns into `false`).

*There is no old-key fallback.* Nothing in 9.2.0 accepts two cookie keys at once, so a rotation is a cut. During a rolling restart, a visitor can hit an old pod and a new pod in turn, and is logged out each time the pod changes; the shorter the rollout, the shorter that period. Rotate in a quiet hour, announce it for the back office (employees lose their unsaved forms), and use a rollout with a high `maxUnavailable`, or accept a short maintenance page (see xref:ecommerce/prestashop/cloud-releases-and-upgrades.adoc[Cloud: Releases and Upgrades]).

*`cookie_key` is the dangerous one.* Passwords are hashed with bcrypt first; `Customer::getByEmail` and `Employee::getByEmail` re-hash a password to bcrypt at the first successful login of an account whose hash is still the old `md5` form (the `isFirstHash` check in `classes/Customer.php` and `classes/Employee.php`). A bcrypt hash does not depend on the static salt. An account that has not logged in since it was created by an old version still has the `md5` hash, which is verified with `+_COOKIE_KEY_+`: after a change of `cookie_key` it cannot log in until the password is reset. The recovery links in e-mails already sent stop working as well. For a shop that began on PrestaShop 1.6 or 1.7 there can be many such accounts. So: never change `cookie_key` as routine; change it only if it was disclosed, accept the resets, and expect support tickets.

*The keys are not rotated by a schedule.* There is no reason to rotate `new_cookie_key` and `cookie_iv` every month; the lifetime of the cookie is a setting of the shop (`PS_COOKIE_LIFETIME_FO` and `PS_COOKIE_LIFETIME_BO`, 480 hours by default in the install data) and the cookie is worthless without the key. Rotate on a suspicion of exposure (a leaked secret, a departed administrator with access to Secrets Manager) and as part of the incident response of xref:ecommerce/prestashop/security.adoc[Security].

=== Generating and changing them

`cookie_key` and `cookie_iv` are random strings (the installer of PrestaShop makes them with `Tools::passwdGen`, 64 and 32 characters of letters and digits). `new_cookie_key` has to be a valid Defuse key, which the installer makes with `PhpEncryption::createNewRandomKey()`, that is `+Key::createNewRandomKey()->saveToAsciiSafeString()+` of the `defuse/php-encryption` library that ships in the `vendor/` directory of the shop. The script generates a fresh `new_cookie_key` and `cookie_iv` from inside a running pod (so that the library and PHP of the production image are used), writes them to a new version of the secret and starts the rollout of the previous section. It leaves `cookie_key` alone. The values are never printed.

[source,bash]
.Rotating new_cookie_key and cookie_iv
----
#!/usr/bin/env bash
set -euo pipefail

REGION=eu-west-1
NAMESPACE=pocketcoffee
SECRET_ID=pocketcoffee/prod/prestashop

POD=$(kubectl --namespace "$NAMESPACE" get pods -l app.kubernetes.io/component=web \
  -o jsonpath='{.items[0].metadata.name}')

# A valid Defuse key, made by the library of the shop itself.
NEW_KEY=$(kubectl --namespace "$NAMESPACE" exec "$POD" -c php-fpm -- php -r \
  'require "/var/www/html/vendor/autoload.php"; echo Defuse\Crypto\Key::createNewRandomKey()->saveToAsciiSafeString();')
NEW_IV=$(openssl rand -hex 16)

# Keep every other key of the secret, replace two.
UPDATED=$(aws secretsmanager get-secret-value \
  --region "$REGION" \
  --secret-id "$SECRET_ID" \
  --query SecretString \
  --output text | jq -c --arg key "$NEW_KEY" --arg iv "$NEW_IV" \
    '. + {PS_NEW_COOKIE_KEY: $key, PS_COOKIE_IV: $iv}')

aws secretsmanager put-secret-value \
  --region "$REGION" \
  --secret-id "$SECRET_ID" \
  --secret-string "$UPDATED" > /dev/null

# Same steps 2 and 3 as above: sync the Secret, then restart so that var/cache is empty.
kubectl --namespace "$NAMESPACE" annotate externalsecret pocketcoffee-secrets \
  "force-sync=$(date +%s)" --overwrite
kubectl --namespace "$NAMESPACE" rollout restart deployment/pocketcoffee-web
kubectl --namespace "$NAMESPACE" rollout status deployment/pocketcoffee-web --timeout=10m
----

Source: https://docs.aws.amazon.com/cli/latest/reference/secretsmanager/put-secret-value.html[AWS CLI Command Reference: put-secret-value]

The `php -r` line was run with `defuse/php-encryption` 2.x and produced a 136-character key; the whole script was checked with `shellcheck`, but never run against a cluster. The key is in the `vendor/` of the image, so no extra tool is needed in the container. Two cautions: the key is passed through shell variables and never printed, so keep shell tracing (`set -x`) off; and put a version of the secret with the *previous* values at hand (`aws secretsmanager get-secret-value --version-stage AWSPREVIOUS`), because a rotation that is rolled back needs them.
