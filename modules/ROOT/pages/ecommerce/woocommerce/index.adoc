*WooCommerce 11.2.1* (published 2026-10-09) running on *WordPress 7.1.3* (2026-10-06), with PHP 8.3.36 and MariaDB 11.8.9,

This page explains what WooCommerce is and how it is organised, the resources around it, the WordPress concepts that the

== What WooCommerce is

WooCommerce is a *plugin*. It is not a standalone shop application: it is a folder of PHP, JavaScript and templates that
WordPress loads like any other plugin, and it adds products, carts, checkout, orders, taxes, shipping, payment gateways,
emails, reports and APIs to a WordPress site. The plugin is developed by Automattic and a community of contributors in the
public repository https://github.com/woocommerce/woocommerce[github.com/woocommerce/woocommerce], it is licensed under the
GPL (the `readme.txt` of 11.2.1 declares `GPLv3`), and its official distribution channel is the WordPress.org plugin
directory, where it is installed with one click from `wp-admin` or with `wp plugin install woocommerce`.

image::ecommerce-woocommerce-overview-stack.svg["The layers of a WooCommerce site: clients, extensions and themes, the WooCommerce plugin, WordPress core, and PHP with the database",width=760]

The figure shows the consequence that shapes the whole subsection: everything below the WooCommerce layer is WordPress.
A request is served by PHP and a web server, WordPress loads its core and then every active plugin, and WooCommerce
registers its post types, tables, routes, blocks and hooks while loading. Extensions, themes and payment plugins then
change WooCommerce by attaching to the same hooks. The database is shared: WordPress tables such as `wp_posts`,
`wp_options` and `wp_users` sit next to WooCommerce tables such as `wp_woocommerce_sessions`, and since the High-Performance
Order Storage (HPOS) feature orders live in `wp_wc_orders` and its sibling tables instead of in `wp_posts`.

That architecture has consequences that shape this subsection.

* *You extend it with hooks, not by editing it.* WordPress calls it the plugin API: actions and filters that any plugin
  or theme can attach callbacks to. WooCommerce fires hundreds of them, and a customisation is almost always a small
  plugin of your own. The xref:ecommerce/woocommerce/hooks-actions-and-filters.adoc[Hooks: Actions and Filters] and
  xref:ecommerce/woocommerce/extension-development.adoc[Extension Development] pages are the centre of the developer path.
* *WordPress releases and WooCommerce releases are separate.* WooCommerce ships a minor release about every five weeks,
  WordPress a few times a year, and a version of WooCommerce supports a window of WordPress versions. Compatibility is a
  first-class concern: plugin headers, the L-1 support policy and compatibility declarations appear on several pages.
* *Operations are your job on a self-hosted store.* Hosting, PHP and database versions, backups, caching, cron and
  security updates belong to the merchant or the agency unless a managed host takes them over. The
  xref:ecommerce/woocommerce/performance-and-security.adoc[Performance and Security] page covers the production side.
* *The checkout moved from PHP templates to blocks.* New stores get the Cart and Checkout blocks by default, and the PHP
  hooks and filters that books from the classic era use for the checkout page do not change the block. Pages that touch
  the checkout say which of the two they describe and give the block replacement.
* *The platform moves, and so do the books.* The WooCommerce books of 2015 and 2018 describe orders stored as `shop_order`
  posts with post meta, shortcode-based cart and checkout pages, the Storefront theme with `storefront_*` hooks, WooThemes
  addresses and PHP 5. This subsection flags those approaches as legacy wherever a reader still meets them in an older
  store and gives the current replacement.

For market context, W3Techs reports WooCommerce on 7.8% of all websites and 47.4% of the sites whose e-commerce system it
can detect (checked 2026-10-27), and Store Leads counted 4,321,090 live WooCommerce stores against a peak of 4,776,386 in
the second quarter of 2024. The WordPress.org plugin page shows more than 7,000,000 active installations (the directory
reports a rounded band) and 470,682,885 downloads, and the repository had 10,569 stars and 2,148 contributors. The
xref:ecommerce/comparison.adoc[Comparison] page carries the dated figures and their sources.

== WordPress concepts used in this subsection

The table gives the minimum that the WooCommerce pages assume and points to the official WordPress developer handbook;
the xref:cms/wordpress/index.adoc[WordPress] section of this site covers each concept in depth. A reader who builds
WordPress sites can skip it.

[cols="2,5,3",options=header]
|===
|Concept |What it means for WooCommerce |Official reference

|Plugin and `Plugin Name` header
|A plugin is a PHP file whose comment header (`Plugin Name`, `Version`, `Requires at least`, `Requires PHP`, `Requires Plugins`, `WC requires at least`, `WC tested up to`) tells WordPress and WooCommerce how to treat it. WordPress refuses to activate a plugin whose `Requires at least` or `Requires PHP` is not met. WooCommerce itself is one.
|https://developer.wordpress.org/plugins/[Plugin handbook]

|Hooks: actions and filters
|An action runs code at a moment; a filter receives a value and returns a changed one. Both take a priority. Almost every WooCommerce customisation is a callback on a `woocommerce_*` hook.
|https://developer.wordpress.org/plugins/hooks/[Hooks]

|Options and post meta
|`get_option()` and `update_option()` store settings as rows of `wp_options`; WooCommerce keeps its settings there (`woocommerce_currency`, `woocommerce_default_country`). Custom fields attach to posts as post meta, which is what products still use.
|https://developer.wordpress.org/apis/options/[Options API]

|Post types and taxonomies
|Products are posts of type `product`, product variations are `product_variation`, categories and tags are taxonomies (`product_cat`, `product_tag`). Orders used to be `shop_order` posts; with HPOS they are rows of dedicated tables.
|https://developer.wordpress.org/plugins/post-types/[Post types]

|Users, roles and capabilities
|Customers are WordPress users with the `customer` role; shop managers have `shop_manager`. Code checks capabilities such as `manage_woocommerce`, never role names.
|https://developer.wordpress.org/plugins/users/roles-and-capabilities/[Roles and capabilities]

|Nonces
|Short-lived tokens that tie a request to a user and an action. The Store API requires one (or a `Cart-Token`) on writes from the browser.
|https://developer.wordpress.org/apis/security/nonces/[Nonces]

|WP-Cron
|Pseudo-cron that runs when the site receives a visit. WooCommerce schedules its background work on Action Scheduler, which uses it as one of its runners.
|https://developer.wordpress.org/plugins/cron/[Cron]

|The REST API and Application Passwords
|WordPress serves JSON under `/wp-json/`. WooCommerce adds the `wc/v3` namespace for administrators and the `wc/store/v1` namespace for shoppers. Application Passwords give a script a revocable credential for a real user.
|https://developer.wordpress.org/rest-api/[REST API handbook]

|Blocks, the block editor and the Site Editor
|Pages are made of blocks stored as HTML comments in post content. WooCommerce ships product, cart, checkout and mini-cart blocks. Block themes can be edited in the Site Editor, and what is saved there is stored in the database and overrides the theme files.
|https://developer.wordpress.org/themes/block-themes/[Block themes]

|`theme.json`
|The settings and styles file of a block theme: palette, typography, spacing, layout. It generates CSS custom properties such as `+--wp--preset--color--coffee+`.
|https://developer.wordpress.org/themes/global-settings-and-styles/[Global settings and styles]

|WP-CLI
|The `wp` command. WooCommerce adds a `wp wc` command group (products, orders, HPOS, tools) that runs through the REST API and needs `--user`.
|https://developer.wordpress.org/cli/commands/[WP-CLI commands]

|Abilities API
|The registry of machine-readable abilities (`wp_register_ability()`) that AI agents and tools can discover. The WooCommerce AI and MCP page builds on it.
|https://developer.wordpress.org/apis/abilities/[Abilities API]
|===

Source: https://developer.wordpress.org/plugins/plugin-basics/header-requirements/[WordPress plugin handbook: Header requirements]

A few WordPress terms recur: *mu-plugins* are plugins loaded automatically from `wp-content/mu-plugins`, *multisite* is a
network of sites on one installation, and a *child theme* inherits a parent theme's templates. The pages that need them
explain them where they first appear.

== A first look at the running store

The commands below were run against the local test site (WordPress 7.1.3, WooCommerce 11.2.1, a block theme that is a child
of Twenty Twenty-Five, HPOS enabled) with WP-CLI 2.12.0. They only read data.

=== The command line

[source,bash]
----
wp core version
wp plugin get woocommerce --fields=name,version,status
wp wc hpos status
wp eval 'echo wp_is_block_theme() ? "block theme" : "classic theme";'
----

Source: https://developer.woocommerce.com/docs/wc-cli/cli-overview/[WooCommerce docs: WC-CLI overview]

The outputs were `7.1.3`, a table with `name` `woocommerce`, `version` `11.2.1` and `status` `active`, the HPOS report
(`HPOS enabled?: yes`, `Compatibility mode enabled?: no`, `Unsynced orders: 0`) and `block theme`. HPOS was not on by default
in a scripted install: on a fresh site installed with WP-CLI, `wp wc hpos status` first reported `no`, and
`wp wc hpos enable` created the tables. The HPOS page shows how to check the setting and enable it.

=== The REST namespaces

WordPress lists every namespace its REST API serves at the root of `/wp-json/`. WooCommerce adds several, which is the quickest
way to see which of its APIs a site exposes.

[source,bash,subs=-attributes]
----
curl -s http://localhost:8081/wp-json/ | python3 -c "import json,sys; print([n for n in json.load(sys.stdin)['namespaces'] if 'wc' in n])"
----

Source: https://developer.wordpress.org/rest-api/[WordPress REST API handbook]

The list on the test site was `wc/v3`, `wc/v1`, `wc-admin`, `wc-analytics`, `wc/store`, `wc/store/v1`, `wc/private`, `wc/v2`,
`wc-admin-email`, `wc-push-notifications`, `wc-telemetry` and `wccom-site/v3`, including `wc/pos/v1/catalog`. `wc/v3` is the administrator API authenticated with consumer keys, and `wc/store/v1` is the shopper API
(see the xref:ecommerce/woocommerce/rest-api-and-webhooks.adoc[REST API and Webhooks] and
xref:ecommerce/woocommerce/store-api.adoc[Store API] pages). The `wc/v1` and `wc/v2` namespaces are older versions of the administrator API, and the Legacy REST API was removed from
core in 9.0.

=== A plugin of your own

A customisation is a plugin. This small one, `pocket-coffee-overview`, is the smallest useful shape: a header that declares
what it needs, and a WP-CLI command that prints the versions in play. The Versions page explains each header line.

[source,php]
----
<?php
/**
 * Plugin Name:       Pocket Coffee Overview
 * Description:       Prints the platform versions Pocket Coffee runs on.
 * Version:           0.1.0
 * Requires at least: 7.0
 * Requires PHP:      7.4
 * Requires Plugins:  woocommerce
 * License:           GPL-2.0-or-later
 * Text Domain:       pocket-coffee-overview
 */

defined( 'ABSPATH' ) || exit;

if ( defined( 'WP_CLI' ) && WP_CLI ) {
	WP_CLI::add_command(
		'pocket-coffee overview',
		function () {
			global $wp_version;
			WP_CLI::line( 'wordpress   ' . $wp_version );
			WP_CLI::line( 'woocommerce ' . ( defined( 'WC_VERSION' ) ? WC_VERSION : 'not loaded' ) );
			WP_CLI::line( 'php         ' . PHP_VERSION );
		}
	);
}
----

Source: https://developer.woocommerce.com/docs/extensions/core-concepts/example-header-plugin-comment/[WooCommerce docs: Example plugin header comment]

After copying the folder into `wp-content/plugins` and running `wp plugin activate pocket-coffee-overview`, the command
`wp pocket-coffee overview` printed `7.1.3`, `11.2.1` and `8.3.36` on three lines. The `Requires Plugins: woocommerce` line
is the WordPress plugin dependency header, added in WordPress 6.5, which makes WordPress ask for the required plugin
before this one can be activated.
