:description: How High-Performance Order Storage works in WooCommerce 11.2.1: the four order tables, authoritative and backup storage, synchronisation, the compatibility declaration, the recipe book for extensions, the wp wc hpos commands, and how to migrate book-era code that reads orders from postmeta.

include::partial$ecommerce-disclaimer.adoc[]

For fifteen years a WooCommerce order was a WordPress post of type `shop_order`, and everything the order knew (the billing
address, the total, the payment method) was a row in `wp_postmeta`. That design shared the posts and postmeta tables with every blog
post, page, product and plugin entity on the site, and it made order queries slow on stores with many orders.
*High-Performance Order Storage* (HPOS, formerly "custom order tables") gives orders their own tables and indexes.
It has been stable since WooCommerce 8.2 (released 2023-10-13) and is the storage for new stores; stores that
started earlier switch deliberately and with a safety net, which is what most of this page is about.

This page was written against WordPress 7.1.3 and WooCommerce 11.2.1 and checked on 2026-10-27. It covers the tables and the
roles of the old and new storage, how synchronisation works and how to run it, how to declare that a plugin supports HPOS, the
recipe book that tells extension authors what to change, the `wp wc hpos` commands, and a migration guide for code written when
orders were posts. The running example is the "gift note" of Pocket Coffee: a note a customer types for a gift order (for Grace, who
gets the beans) stored on the order, shown in a meta box and a list column, and written so that it works on both storages. Orders
are the CRUD objects described on xref:ecommerce/woocommerce/crud-objects-and-data-stores.adoc[CRUD Objects and Data Stores]; the
architecture around them is on xref:ecommerce/woocommerce/architecture.adoc[Architecture]; the plugin skeleton and headers of the
example are explained in xref:ecommerce/woocommerce/extension-development.adoc[Extension Development]. The `wp wc` command family as a
whole is on xref:ecommerce/woocommerce/wc-cli.adoc[WC-CLI].

Everything below ran in the local test shop (WordPress 7.1.3, WooCommerce 11.2.1, PHP 8.3.36, MariaDB 11.8.9) with HPOS authoritative
and compatibility mode off, the state of a fresh HPOS store. The shop was not switched between storages: switching modes, enabling synchronisation
and the `cleanup` command would change data that other examples in the same shop use, so they are described from the source and the
documentation and marked as not run. The test orders use the billing address `ada-hpos@example.test`, which no other order of the shop uses.

== What HPOS is, and its version history

HPOS replaces the posts-based storage with four tables that were designed for orders. The order keeps its ID, status, totals and customer in
`wc_orders`, its two addresses in `wc_order_addresses`, its internal fields in `wc_order_operational_data` and its custom fields in
`wc_orders_meta`. Order items stay in `woocommerce_order_items`. The goals stated by WooCommerce are scalability (dedicated tables and
indexes mean fewer reads and writes and fewer busy tables), reliability (targeted backups, and the possibility of read and write locks that
prevent race conditions) and simplicity (a schema you can browse and extend without wading through `wp_posts`).

=== Is HPOS on? A fresh scripted install says no

"Enabled by default for new installs" is true of the setup that a merchant goes through in the browser. In the test shop, a store created with
WP-CLI (`wp core install`, then `wp plugin install woocommerce --activate`) did *not* have HPOS: the option
`woocommerce_custom_orders_table_enabled` was `no` and the tables did not exist until `wp wc hpos enable` created them. The code that turns
HPOS on for new shops (`+WC_Install::maybe_enable_hpos()+`, run on `woocommerce_newly_installed` at priority 20) returns early unless all of
these hold:

* `woocommerce_init` has already fired when the check runs;
* the shop has no orders yet;
* no active plugin is incompatible with HPOS, *and* no active plugin is "uncertain", that is has made no declaration;
* the filter `woocommerce_enable_hpos_by_default_for_new_shops` returns `true` (its default).

The cause of the scripted install was not isolated; the first condition, a check that runs before the activation finished, is the likely
one. The practical rule is the same either way: after a scripted install or a deployment, check the state and enable HPOS explicitly.
The first script asks the questions that matter:

== The tables

The next figure shows the layout; the table afterwards lists every column of 11.2.1, taken from `SHOW CREATE TABLE` on the test shop (prefix `wp_`).
`+OrdersTableDataStore::get_all_table_names()+` returns the names, and `+OrderUtil::get_table_for_orders()+` and `get_table_for_order_meta()` return the ones in use.

image::ecommerce-woocommerce-hpos-tables.svg["The table wp_wc_orders with its columns, linked by order_id to wp_wc_order_addresses, wp_wc_order_operational_data and wp_wc_orders_meta, with a placeholder row in wp_posts and the unchanged order items tables",width=900]

[cols="2,3,4",options="header"]
|===
| Table | Columns | Notes

| `wc_orders`
| `id` (primary key, the order ID), `status`, `currency`, `type`, `tax_amount`, `total_amount`, `customer_id`, `billing_email`, `date_created_gmt`, `date_updated_gmt`, `parent_order_id`, `payment_method`, `payment_method_title`, `transaction_id`, `ip_address`, `user_agent`, `customer_note`
| One row per order, refund (`type` = `shop_order_refund`, `parent_order_id` = the order) or other order type. Statuses keep the `wc-` prefix. Amounts are `decimal(26,8)`. Dates are UTC. Indexes: `status`, `date_created_gmt`, `customer_id` with `billing_email`, `customer_id` with `status`, `billing_email`, `transaction_id`, `type` with `status` and `date_created_gmt`, `parent_order_id`, `date_updated_gmt`.

| `wc_order_addresses`
| `id`, `order_id`, `address_type` (`billing` or `shipping`), `first_name`, `last_name`, `company`, `address_1`, `address_2`, `city`, `state`, `postcode`, `country`, `email`, `phone`
| Two rows per order; the pair `address_type` and `order_id` is unique. Indexed on `order_id`, `email` and `phone`.

| `wc_order_operational_data`
| `id`, `order_id` (unique), `created_via`, `woocommerce_version`, `prices_include_tax`, `coupon_usages_are_counted`, `download_permission_granted`, `cart_hash`, `new_order_email_sent`, `order_key`, `order_stock_reduced`, `date_paid_gmt`, `date_completed_gmt`, `shipping_tax_amount`, `shipping_total_amount`, `discount_tax_amount`, `discount_total_amount`, `recorded_sales`
| Flags and amounts that the order uses internally. One row per order. `order_key` is indexed, which makes the order-received and pay-for-order links cheap.

| `wc_orders_meta`
| `id`, `order_id`, `meta_key`, `meta_value`
| The custom fields: everything that is not a prop of the order. Indexed on `meta_key` and `meta_value`, and on `order_id`, `meta_key` and `meta_value`. Also holds the bookkeeping rows `_billing_address_index` and `_shipping_address_index` that order search uses.
|===

Source: https://developer.woocommerce.com/2022/09/15/high-performance-order-storage-database-schema/[WooCommerce developer blog: HPOS database schema]

A few consequences follow from the schema. `billing_email` and `customer_id` are columns of the main table, so "orders of this customer" is an indexed read.
The address fields are not in the main table, so a query on `billing_first_name` joins `wc_order_addresses`. Totals are `decimal` columns: sorting and range queries on
`total` work without casting, unlike string-valued postmeta. The order *items* and their meta (`woocommerce_order_items`, `woocommerce_order_itemmeta`)
and the analytics lookup tables (`wc_order_stats`, `wc_order_product_lookup`, ...) are not part of HPOS and did not move.

Order 438 exists once in `wc_orders`, twice in `wc_order_addresses`, once in `wc_order_operational_data` and three times in `wc_orders_meta`: the two address index rows and the gift note. Its two line items sit in the unchanged `woocommerce_order_items` table. In `wp_posts` there is a row with the same ID, but its type is `shop_order_placehold` and it has
no total and no gift note. Two things in the last lines need attention. `get_post_type()` answers `shop_order_placehold` while `+OrderUtil::get_order_type()+` answers
`shop_order`, so only the second can be used to ask what an ID is. And the placeholder carries 16 postmeta rows, the billing and shipping address fields, which were written when the order was created (the code path that does it was not traced); the legacy section below shows why those rows are a trap, not a feature.

== Authoritative and backup storage

While HPOS exists on a store, the two sets of tables have roles. The *authoritative* tables are the working tables: orders are read from them and written to them. The
*backup* tables receive a copy of the authoritative data whenever synchronisation happens. The option `woocommerce_custom_orders_table_enabled` decides who is
authoritative: `yes` means the HPOS tables (the posts tables are the backup), `no` means the posts tables. In 11.2.1 the setting is the radio button "Order data storage" in
WooCommerce > Settings > Advanced > Features, with the labels "WordPress posts storage (legacy)" and "High-performance order storage (recommended)".

image::ecommerce-woocommerce-hpos-authoritative-roles.svg["Three set-ups side by side: legacy posts storage with unused HPOS tables, a transition with compatibility mode where either store is authoritative and the other is a backup copied on write, and HPOS only with the posts table holding placeholders and no copy",width=900]

The mechanism that makes the choice effective is small. `CustomOrdersTableController` hooks the filter `woocommerce_order_data_store` (and `woocommerce_order-refund_data_store`)
at priority 999, so `+WC_Data_Store::load( 'order' )+` returns `OrdersTableDataStore` when the option is `yes` and `WC_Order_Data_Store_CPT` otherwise. Everything that uses
`wc_get_order()`, `wc_get_orders()` or `WC_Order` goes through that store, which is the whole reason HPOS did not break the extensions that used the objects (see
xref:ecommerce/woocommerce/crud-objects-and-data-stores.adoc[CRUD Objects and Data Stores]).

Two safeguards protect the data. WooCommerce does not let you change the authoritative storage while orders are waiting to be synchronised: the radio buttons are disabled and the screen
offers "Sync orders now". The filter `wc_allow_changing_orders_storage_while_sync_is_pending` (since 8.3.0) overrides the rule, and its documentation says it exists for development
environments only and that using it in production can corrupt or lose order data. And the radio button for HPOS is disabled while a plugin that declared itself *incompatible* is active.

Source: https://developer.woocommerce.com/docs/features/orders/high-performance-order-storage/[WooCommerce docs: Authoritative tables]

== Synchronisation

*Synchronisation* applies the pending changes of the authoritative tables to the backup tables. An order is *pending synchronisation* when it was created, changed or deleted in the
authoritative store and the backup store has not seen it yet. The setting that keeps the stores equal is "Enable compatibility mode (Synchronize orders between High-performance order
storage and WordPress posts storage)", stored in the option `woocommerce_custom_orders_table_data_sync_enabled` (`yes` or `no`). The same function has had other names: "compatibility mode" in the settings,
"data sync" in the code and option, "sync" on the command line.

[mermaid]
....
flowchart TD
    A["Your code: order save"] --> B{"Option woocommerce_custom_orders_table_enabled"}
    B -->|yes| C["OrdersTableDataStore"]

The ways an order reaches the backup store, and what each costs:

[cols="2,5",options="header"]
|===
| Mechanism | Behaviour

| Immediate synchronisation
| With compatibility mode on, every write of an order to the authoritative store is copied to the backup store in the same request (when the posts are the backup this is called backfilling). Writes become more expensive, which is why large stores turn it off once HPOS is proven.

| Manual synchronisation
| `wp wc hpos sync` (older name `wp wc cot sync`) walks the pending orders in batches. It can be used with compatibility mode off, and is the fast way to migrate a large store. The same can be done in PHP: `+DataSynchronizer::get_next_batch_to_process( $size )+` returns the pending IDs and `process_batch( $ids )` syncs them.

| Scheduled synchronisation
| When compatibility mode is switched on while orders are pending, WooCommerce enqueues the `DataSynchronizer` as a batch processor. The watchdog action `wc_schedule_pending_batch_processes` finds pending work and schedules `wc_run_batch_process`, which processes one batch per run through xref:ecommerce/woocommerce/action-scheduler.adoc[Action Scheduler]. The batch size is 250 orders when the posts are authoritative and 26 when HPOS is (back-filling is slower than migrating, so the code divides by ten and adds one); the filter `woocommerce_orders_cot_and_posts_sync_step_size` changes it. The documentation of older versions speaks of 25 orders per action.

| Background synchronisation
| 11.2.1 reads the option `woocommerce_custom_orders_table_background_sync_mode` with the values `off`, `interval` and `continuous`; the default is `interval` when compatibility mode is on and `off` otherwise. In interval mode a recurring action `woocommerce_custom_orders_table_background_sync` checks for pending orders every `woocommerce_custom_orders_table_background_sync_interval` seconds (default 3600). The options have no settings screen in 11.2.1 and were read from the source, not changed.

| Synchronisation on read
| With compatibility mode on, reading an order can refresh it from the posts table when the post is newer. It is off by default since 10.7.0 because it can let stale posts data override correct HPOS data. The filter `woocommerce_hpos_enable_sync_on_read` turns it on or off explicitly.

| Deletion synchronisation
| Missing rows are ambiguous: an order absent from the backup may be new, or may have been deleted from the authoritative store. WooCommerce therefore records deletions as `_deleted_from` rows (value `orders_table` or `posts_table`) when the sync is not immediate and processes them at the next sync, so a bug cannot silently delete good orders. Placeholder posts are deleted immediately.
|===

=== Placeholder posts

Order IDs must be the same in both stores or synchronisation could not match rows. While the posts are authoritative this is trivial. While HPOS is authoritative a
non-order post could take an ID that an HPOS order would need later. WooCommerce prevents it by creating a placeholder row of type `shop_order_placehold` in `wp_posts` for every new order (when
compatibility mode is off), which reserves the ID. When a sync happens the placeholder is filled in and becomes a `shop_order`. The test order above shows one, with status `draft`. In 11.2.1 creating
an order also fires `save_post` once for the placeholder (type `shop_order_placehold`) but never `save_post_shop_order`:

[source,php,subs=-attributes]
----
<?php
$log = array();
$push = static function ( $label ) use ( &$log ) {
	return static function () use ( &$log, $label ) {
		$log[] = $label;
	};
};
add_action( 'save_post', static function ( $id, $post ) use ( &$log ) { $log[] = 'save_post (' . $post->post_type . ')'; }, 10, 2 );
add_action( 'save_post_shop_order', $push( 'save_post_shop_order' ) );
add_action( 'woocommerce_new_order', $push( 'woocommerce_new_order' ) );
add_action( 'woocommerce_update_order', $push( 'woocommerce_update_order' ) );
add_action( 'woocommerce_order_status_changed', $push( 'woocommerce_order_status_changed' ) );

$order = wc_create_order( array( 'status' => 'pending' ) );
$order->set_billing_email( 'ada-hpos-hooks@example.test' );
$order->save();

echo implode( "\n", $log ), "\n";

----

[source,text,subs=-attributes]
----

woocommerce_new_order
woocommerce_update_order
woocommerce_update_order
woocommerce_order_status_changed
----

The order of the lines is the order of the events. Updates fire only the WooCommerce hooks. Code that hooked `save_post_shop_order` or `wp_insert_post` for orders in the posts era will not run

== Enabling, switching and disabling

=== On a new store

Check first, then enable explicitly when a scripted install did not do it. The command creates the tables when they do not exist and refuses to enable when an incompatible plugin is active (override with `--ignore-plugin-compatibility`):

[source,bash,subs=-attributes]
----
wp wc hpos status
wp wc hpos enable --for-new-shop
----

The second command was not run on the test shop, where HPOS was already on.

Source: https://developer.woocommerce.com/docs/features/orders/high-performance-order-storage/cli-tools/[WooCommerce docs: HPOS CLI tools]

=== On an existing store

An existing store keeps the posts storage until someone switches it, and the switch needs both stores to be equal first. For a store of any size the safe order, described by the
"large store" guide of the WooCommerce documentation, has five phases. The figure puts it on one page; the text after it adds the reasoning.

image::ecommerce-woocommerce-hpos-migration-phases.svg["Five phases from posts storage to HPOS: mirror with compatibility mode and a sync, flip the authoritative storage, turn synchronisation on read off, turn synchronisation off, and clean up; switching back is immediate in the first three phases",width=900]

. *Test on a copy.* Run the store on a local or staging copy with every plugin and the custom code, try checkout with each payment method, refunds, and subscriptions if you use them, with
compatibility mode both on and off.
. *Mirror.* On production switch compatibility mode on while "WordPress posts storage" stays authoritative. New and changed orders now appear in the HPOS tables. Migrate the past with
`wp wc hpos sync` instead of waiting for the background batches; time it on staging first (the guide reports about a week for a store with nine million orders). Interrupting the command or switching the mode off is safe and the
work resumes later. Verify with `wp wc hpos verify_data`.
. *Flip.* Choose "High-performance order storage" with compatibility mode still on. If anything fails, switching back is immediate and loses nothing, because the posts tables have been kept current.
Test the critical flows and watch the support channels. Plan to be online for a while, and prefer a quiet period; both directions are hot switches without downtime.
. *Sync off on read, then off on write.* Disable synchronisation on read (since 10.7.0 this is already the default; before it, `+add_filter( 'woocommerce_hpos_enable_sync_on_read', '__return_false' )+`), wait, and
when the shop behaves, switch compatibility mode off. The guide's own store did the second step a week after the first and kept a manual `wp wc hpos sync` on a schedule to retain the option to fall back.
. *Clean up (optional).* `wp wc hpos cleanup` removes order data from the legacy tables; it is the one step that cannot be undone, and it keeps the placeholders.

Third-party systems matter as much as plugins: a data warehouse, an accounting export or a shipping-label tool that reads `wp_posts` and `wp_postmeta` directly will stop seeing new orders, and that
failure shows up in the code audit of no plugin. Inventory them before phase 3.

Source: https://developer.woocommerce.com/docs/features/orders/high-performance-order-storage/guide-large-store/[WooCommerce docs: A large store's guide to enable HPOS]

Source: https://developer.woocommerce.com/docs/features/orders/high-performance-order-storage/enable-hpos/[WooCommerce docs: How to enable High Performance Order Storage]

=== Disabling

Disabling is the same trip in reverse: make sure the stores are in sync (turn compatibility mode on, let the sync finish), then choose "WordPress posts storage". `wp wc hpos disable` refuses while orders are pending
sync, and `--with-sync` also turns compatibility mode off. Re-enabling later follows the steps above. Disabling, enabling, `sync` in either direction and `cleanup` were not run on the test shop, which is shared by other examples; their behaviour is
taken from `wp wc hpos <command> --help`, the 11.2.1 source and the documentation.

== Declaring compatibility

WooCommerce cannot know that a plugin reads orders correctly, so each plugin says so. The declaration goes in the main plugin file, runs on `before_woocommerce_init` and names a *feature*
(`custom_order_tables` for HPOS, `cart_checkout_blocks` for the Cart and Checkout blocks) and a boolean:

[source,php,subs=-attributes]
----
use Automattic\WooCommerce\Utilities\FeaturesUtil;

add_action(
	'before_woocommerce_init',
	static function () {
		if ( class_exists( FeaturesUtil::class ) ) {
			FeaturesUtil::declare_compatibility( 'custom_order_tables', __FILE__, true );   // false = incompatible
			FeaturesUtil::declare_compatibility( 'cart_checkout_blocks', __FILE__, true );
		}
	}
);
----

Source: https://developer.woocommerce.com/docs/features/orders/high-performance-order-storage/recipe-book/[WooCommerce docs: HPOS extension recipe book, declaring extension (in)compatibility]

The rules, from the source of `FeaturesUtil` and `FeaturesController`:

* `declare_compatibility( $feature_id, $plugin_file, $positive_compatibility = true )` returns `true` on success and `false` when the feature does not exist or the call is not made inside `before_woocommerce_init`.
* Pass `+__FILE__+`, or `+'my-plugin/my-plugin.php'+` when the declaration lives outside the main file.
* Declaring `false` states that the plugin does *not* support the feature. WooCommerce then warns on the Plugins screen and, while the plugin is active, disables the HPOS radio button.
* No declaration means "uncertain". Uncertain plugins are listed separately, and (see above) they stop HPOS from being enabled by default on a new shop.
* The warnings on the Plugins screen appear only for plugins that declare `WC tested up to` in their header, because many WordPress plugins have nothing to do with WooCommerce.
* `+class_exists( FeaturesUtil::class )+` protects against WooCommerce being inactive or too old to have the class; the `Requires Plugins: woocommerce` header makes WordPress enforce the dependency from 6.5 on.
* The Plugins screen can be filtered to the incompatible ones with `wp-admin/plugins.php?plugin_status=incompatible_with_feature&feature_id=custom_order_tables`.

The read side of the API tells what a store has declared:

[source,php,subs=-attributes]
----

$for_hpos = FeaturesUtil::get_compatible_plugins_for_feature( 'custom_order_tables' );
foreach ( $for_hpos as $state => $plugins ) {
	printf( "%-12s %d plugins\n", $state, count( $plugins ) );

echo 'registered features: ', count( FeaturesUtil::get_features( true ) ), "\n";

== The recipe book: making an extension HPOS-compatible

The official recipe book for extension authors is short, and its rules are the content of this section. The principle is stated once: use WooCommerce APIs, not WordPress APIs, to access order data.

=== Detecting the storage

CRUD code needs no detection. Only code that must choose between two behaviours does, for example an SQL query written for speed or a hook that exists on one screen only:

[source,php,subs=-attributes]
----
use Automattic\WooCommerce\Utilities\OrderUtil;

if ( OrderUtil::custom_orders_table_usage_is_enabled() ) {
	// HPOS is authoritative.
} else {
	// Posts storage.
}
----

Source: https://developer.woocommerce.com/docs/features/orders/high-performance-order-storage/recipe-book/[WooCommerce docs: Detecting whether HPOS tables are being used]

`OrderUtil` is the public helper for this and for several neighbours, all of them verified on the test shop:

[cols="3,4",options="header"]
|===
| Method | Use

| `custom_orders_table_usage_is_enabled()`
| HPOS is the authoritative storage.

| `custom_orders_table_data_sync_is_enabled()`
| Compatibility mode is on (since 11.0.0). Cheap.

| `is_custom_order_tables_in_sync()`
| Compatibility mode is on and no order is pending. Runs a query; avoid it in hot paths.

| `custom_orders_table_datastore_cache_enabled()`, `orders_cache_usage_is_enabled()`
| The datastore cache or the order object cache is in use.

| `get_table_for_orders()`, `get_table_for_order_meta()`
| The table in use for orders and for their meta; for raw SQL only.

| `get_order_type( $id )`, `is_order( $id, $types )`
| What an ID is; replaces `get_post_type()`.

| `get_order_admin_screen()`
| Screen ID of the order edit screen, for `add_meta_box()`; throws outside the admin.

| `get_order_admin_edit_url( $id )`, `get_order_admin_new_url()`
| The URLs of the edit and new-order screens.

| `is_order_list_table_screen()`, `is_order_edit_screen()`, `is_new_order_screen()`
| Screen checks for admin code.

| `init_theorder_object( $post_or_order )`, `get_post_or_order_id( $post_or_order )`, `get_post_or_object_meta( $post, $data, $key, $single )`
| Accept either a `WP_Post` or a `WC_Order`, which is what hooks give you on the two screens.

| `get_count_for_type( $type )`
| Counts of orders of a type (since 8.7.0).
|===

=== Auditing a code base

Start with a search. The recipe book gives a regular expression for the functions that must not touch orders and another for the post-list and post-edit hooks of the order screens. The first is meant for the
whole code base, with many false positives:

[source,text,subs=-attributes]
----
wpdb|get_post|get_post_field|get_post_status|get_post_type|get_post_type_object|get_posts|metadata_exists|get_post_meta|get_metadata|get_metadata_raw|get_metadata_default|get_metadata_by_mid|wp_insert_post|add_metadata|add_post_meta|wp_update_post|update_post_meta|update_metadata|update_metadata_by_mid|delete_metadata|delete_post_meta|delete_metadata_by_mid|delete_post_meta_by_key|wp_delete_post|wp_trash_post|wp_untrash_post|wp_transition_post_status|clean_post_cache|update_post_caches|update_postmeta_cache|post_exists|wp_count_post|shop_order
----

[source,text,subs=-attributes]
----
post_updated_messages|do_meta_boxes|enter_title_here|edit_form_before_permalink|edit_form_after_title|edit_form_after_editor|submitpage_box|submitpost_box|edit_form_advanced|dbx_post_sidebar|manage_shop_order_posts_columns|manage_shop_order_posts_custom_column
----

Source: https://developer.woocommerce.com/docs/features/orders/high-performance-order-storage/recipe-book/[WooCommerce docs: Auditing the code base]

Go through each match and decide whether it concerns an order. Most do not. Those that do are rewritten with the objects. The replacements:

[cols="3,3",options="header"]
|===
| Posts-era code | HPOS-ready code

| `+$post = get_post( $post_id );+`
| `+$order = wc_get_order( $post_id );+`

| `+get_post_meta( $id, $key, true )+`
| `+$order->get_meta( $key )+`

| `+update_post_meta( $id, $key, $value )+`, `+add_post_meta()+`, `+delete_post_meta()+`
| `+$order->update_meta_data( $key, $value )+`, `+add_meta_data()+`, `+delete_meta_data()+`, then `+$order->save()+`

| `+'shop_order' === get_post_type( $id )+`
| `+'shop_order' === OrderUtil::get_order_type( $id )+` or `+OrderUtil::is_order( $id, wc_get_order_types() )+`

| `+get_posts()+` and `+WP_Query+` for `shop_order`
| `+wc_get_orders()+` with `meta_query`, `field_query` and `date_query`

| `+wp_update_post()+` for the status
| `+$order->update_status( ... )+`

| `+$wpdb->postmeta+` joins
| CRUD; or, for SQL you cannot avoid, `+OrderUtil::get_table_for_orders()+` and the HPOS columns

| `+add_meta_box( ..., 'shop_order', ... )+`
| the same call with `+OrderUtil::get_order_admin_screen()+` as the screen; the callback receives a `WC_Order` on the HPOS screen and a `WP_Post` on the legacy one

| `+manage_edit-shop_order_columns+`, `+manage_shop_order_posts_custom_column+`
| `+woocommerce_shop_order_list_table_columns+`, `+woocommerce_shop_order_list_table_custom_column+` (since 7.3.0) for HPOS; keep the old pair while posts storage is supported
|===

Calling `save()` is relatively expensive; set everything first and save once.

=== Not reading the post table directly

The recipe book also warns that, with HPOS authoritative, reading the posts table "may mean reading an outdated order" and writing to it "may mean updating an order that will not be read". Code that
bypasses the objects can therefore *appear* to work. The next sections show what that looks like.

== A complete HPOS-ready extension: the gift note

The plugin below is the whole example: the compatibility declaration, a helper that writes the note with CRUD calls, the "order placed" log line of the Pocket Coffee thread (on `woocommerce_order_status_processing`, which every storage fires with
the complete order), a meta box on the order edit screen, the save handler, a list column, and the one function that needs SQL and therefore branches on the storage. It passes PHP_CodeSniffer with the `WooCommerce-Core` and `WordPress-Docs` standards without findings.

[source,php,subs=-attributes]
----
<?php
/**
 * Plugin Name:          Pocket Coffee HPOS
 * Description:          Gift note on orders, written for High-Performance Order Storage and legacy posts storage alike.
 * Version:              0.1.0
 * Requires at least:    7.0
 * Requires PHP:         7.4
 * Requires Plugins:     woocommerce
 * WC requires at least: 10.0
 * WC tested up to:      11.2
 * Text Domain:          pocket-coffee-hpos
 * License:              GPL-2.0-or-later
 *
 * @package PocketCoffee\Hpos
 */

defined( 'ABSPATH' ) || exit;

use Automattic\WooCommerce\Utilities\FeaturesUtil;
use Automattic\WooCommerce\Utilities\OrderUtil;

const POCKET_COFFEE_HPOS_GIFT_NOTE = '_pc_gift_note';

// 1. Tell WooCommerce this plugin works with HPOS (and with the Cart and Checkout blocks).
add_action(
	'before_woocommerce_init',
	static function () {
		if ( class_exists( FeaturesUtil::class ) ) {
			FeaturesUtil::declare_compatibility( 'custom_order_tables', __FILE__, true );
			FeaturesUtil::declare_compatibility( 'cart_checkout_blocks', __FILE__, true );
		}
	}
);

/**
 * Stores the gift note on the order. update_meta_data() + save() works on both storages.
 *
 * @param WC_Order $order Order.
 * @param string   $note  Note typed by the customer.
 */
function pocket_coffee_hpos_set_gift_note( WC_Order $order, $note ) {
	$note = sanitize_textarea_field( $note );
	if ( '' === $note ) {
		$order->delete_meta_data( POCKET_COFFEE_HPOS_GIFT_NOTE );
	} else {
		$order->update_meta_data( POCKET_COFFEE_HPOS_GIFT_NOTE, $note );
	}
	$order->save();
}

// 2. Log "order placed" with the order number and total once the order is paid or accepted.
add_action(
	'woocommerce_order_status_processing',
	static function ( $order_id, $order ) {
		wc_get_logger()->info(
			sprintf( 'Order %s placed: %s %s', $order->get_order_number(), $order->get_total(), $order->get_currency() ),
			array( 'source' => 'pocket-coffee-hpos' )
		);
	},
	10,
	2
);

// 3. Meta box on the order edit screen: the screen id differs between storages.
add_action(
	'add_meta_boxes',
	static function () {
		add_meta_box(
			'pocket-coffee-gift-note',
			__( 'Gift note', 'pocket-coffee-hpos' ),
			'pocket_coffee_hpos_render_gift_note_box',
			OrderUtil::get_order_admin_screen(), // woocommerce_page_wc-orders with HPOS, shop_order without.
			'side',
			'default'
		);
	}
);

/**
 * Renders the meta box. The argument is a WP_Post on the legacy screen and a WC_Order on the HPOS screen.
 *
 * @param WP_Post|WC_Order $post_or_order_object The object WordPress or WooCommerce passes.
 */
function pocket_coffee_hpos_render_gift_note_box( $post_or_order_object ) {
	$order = OrderUtil::init_theorder_object( $post_or_order_object );
	if ( ! $order ) {
		return;
	}

	wp_nonce_field( 'pocket_coffee_gift_note', 'pocket_coffee_gift_note_nonce' );
	printf(
		'<textarea name="pocket_coffee_gift_note" rows="3" style="width:100%%">%s</textarea>',
		esc_textarea( (string) $order->get_meta( POCKET_COFFEE_HPOS_GIFT_NOTE ) )
	);
}

// 4. Save it. Both order edit screens fire this action with the order ID; the second argument
// is a WP_Post on the legacy screen and a WC_Order on the HPOS screen, so load the order by ID.
add_action(
	'woocommerce_process_shop_order_meta',
	static function ( $order_id ) {
		$nonce = isset( $_POST['pocket_coffee_gift_note_nonce'] ) ? sanitize_text_field( wp_unslash( $_POST['pocket_coffee_gift_note_nonce'] ) ) : '';
		$order = wc_get_order( $order_id );
		if ( ! $order || ! wp_verify_nonce( $nonce, 'pocket_coffee_gift_note' ) || ! isset( $_POST['pocket_coffee_gift_note'] ) ) {
			return;
		}
		pocket_coffee_hpos_set_gift_note( $order, wp_unslash( $_POST['pocket_coffee_gift_note'] ) ); // phpcs:ignore WordPress.Security.ValidatedSanitizedInput.InputNotSanitized -- sanitized in the function.
	}
);

// 5. A "Gift" column in the order list: one pair of hooks per list screen.
add_filter(
	'woocommerce_shop_order_list_table_columns', // HPOS list table.
	'pocket_coffee_hpos_add_gift_column'
);
add_filter(
	'manage_edit-shop_order_columns', // Legacy posts list table.
	'pocket_coffee_hpos_add_gift_column'
);

/**
 * Adds the Gift column after the status column.
 *
 * @param array $columns Columns.
 * @return array
 */
function pocket_coffee_hpos_add_gift_column( $columns ) {
	$result = array();
	foreach ( $columns as $key => $label ) {
		$result[ $key ] = $label;
		if ( 'order_status' === $key ) {
			$result['pocket_coffee_gift'] = __( 'Gift', 'pocket-coffee-hpos' );
		}
	}
	return $result;
}

/**
 * Prints the cell for one order.
 *
 * @param string       $column Column id.
 * @param WC_Order|int $order  Order object (HPOS) or post ID (legacy).
 */
function pocket_coffee_hpos_render_gift_cell( $column, $order = null ) {
	if ( 'pocket_coffee_gift' !== $column ) {
		return;
	}
	$order = $order instanceof WC_Order ? $order : wc_get_order( $order ? $order : get_the_ID() );
	echo $order && $order->get_meta( POCKET_COFFEE_HPOS_GIFT_NOTE ) ? esc_html__( 'Yes', 'pocket-coffee-hpos' ) : '&ndash;';
}
add_action( 'woocommerce_shop_order_list_table_custom_column', 'pocket_coffee_hpos_render_gift_cell', 10, 2 );
add_action( 'manage_shop_order_posts_custom_column', 'pocket_coffee_hpos_render_gift_cell', 10, 2 );

/**
 * Counts orders per status with SQL, the one case where the storage matters.
 *
 * @return array<string,int> Status (with the wc- prefix) => count.
 */
function pocket_coffee_hpos_count_orders_by_status() {
	global $wpdb;

	if ( OrderUtil::custom_orders_table_usage_is_enabled() ) {
		$table = OrderUtil::get_table_for_orders(); // For example wp_wc_orders.
		$rows  = $wpdb->get_results( "SELECT status, COUNT(*) AS total FROM {$table} WHERE type = 'shop_order' GROUP BY status", ARRAY_A ); // phpcs:ignore WordPress.DB.PreparedSQL.InterpolatedNotPrepared -- Table name comes from WooCommerce.
	} else {
		$rows = $wpdb->get_results( "SELECT post_status AS status, COUNT(*) AS total FROM {$wpdb->posts} WHERE post_type = 'shop_order' GROUP BY post_status", ARRAY_A );
	}

	return array_map( 'intval', wp_list_pluck( $rows, 'total', 'status' ) );
}
----

Source: https://developer.woocommerce.com/docs/features/orders/high-performance-order-storage/recipe-book/[WooCommerce docs: HPOS extension recipe book]

How the pieces follow the rules of the recipe book:

* The meta box registers for `+OrderUtil::get_order_admin_screen()+`, which is `woocommerce_page_wc-orders` on HPOS and `shop_order` on posts. The callback receives a `WP_Post` on one screen and a `WC_Order` on the other, and
  `+OrderUtil::init_theorder_object()+` turns either into an order. The helper throws outside the admin, so it is called inside `add_meta_boxes`, never at load time.
* Saving uses `woocommerce_process_shop_order_meta`, which both edit screens fire with the order ID. The second argument is a `WP_Post` on the legacy screen and a `WC_Order` on the HPOS screen, so the handler ignores it and loads the order with `wc_get_order()`. Nonce and sanitisation are in the handler, and the helper only writes.
* The list column has one pair of hooks per list table. The two `add_filter` and `add_action` pairs are the price of supporting both storages and can be dropped when only HPOS stores matter.
* The log line goes on a status hook, not on `woocommerce_new_order`, because at creation the order may still be empty.
* `pocket_coffee_hpos_count_orders_by_status()` is the only code that mentions a table, and it asks WooCommerce which one, with the right column names for each storage.

The orders are placed with the function below (one CRUD object, no post function), which the examples call:

[source,php,subs=-attributes]
----
<?php
/**
 * Places a Pocket Coffee order with CRUD objects only: no post or postmeta function is involved.
 *
 * @package PocketCoffee\Hpos
 */

/**
 * Creates a processing order.
 *
 * @param array<int,int> $lines     Product or variation ID => quantity.
 * @param string         $email     Billing and shipping e-mail.
 * @param string         $gift_note Optional gift note.
 * @return int Order ID.
 */
function pocket_coffee_hpos_place_order( array $lines, $email, $gift_note = '' ) {
	$order = wc_create_order( array( 'status' => 'pending' ) );

	foreach ( $lines as $product_id => $quantity ) {
		$order->add_product( wc_get_product( $product_id ), $quantity );
	}

	$address = array(
		'first_name' => 'Ada',
		'last_name'  => 'Lovelace',
		'email'      => $email,
		'address_1'  => 'Calle de Alcala 1',
		'city'       => 'Madrid',
		'state'      => 'M',
		'postcode'   => '28014',
		'country'    => 'ES',
	);
	$order->set_address( $address, 'billing' );
	$order->set_address( $address, 'shipping' );
	$order->set_payment_method( 'bacs' );
	$order->calculate_totals();
	$order->save();

== Querying orders on HPOS

`wc_get_orders()` and `WC_Order_Query` are the same functions as on the posts storage and take the arguments described in
xref:ecommerce/woocommerce/crud-objects-and-data-stores.adoc[CRUD Objects and Data Stores]. HPOS adds three query types, all arguments of the same call and all inspired by `WP_Query`:

[cols="2,5",options="header"]
|===
| Argument | Meaning

| `meta_query`
| Conditions on custom fields. Each clause has `key`, optional `value`, optional `compare` (`=`, `!=`, `LIKE`, `EXISTS`, `BETWEEN`, `IN` and others) and optional `type` (a SQL cast). Clauses combine with `relation` `AND` or `OR`.

| `field_query`
| The same syntax for order *fields* (`total`, `shipping_total`, `billing_first_name`, `order_key` and the other props): use `field` where `meta_query` uses `key`. It exists for conditions the plain arguments cannot express: comparison operators, `OR` and nesting.

| `date_query`
| The `WP_Query` date syntax over the order dates `date_created`, `date_modified`, `date_completed` and `date_paid` (with the suffix `_gmt` for the UTC column).
|===

[source,php,subs=-attributes]
----
<?php
$ids = static fn( array $args ) => wp_json_encode( wc_get_orders( array_merge( $args, array( 'return' => 'ids', 'limit' => -1 ) ) ) );
$ada = array( 'billing_email' => 'ada-hpos@example.test' );

echo "--- the arguments every storage understands\n";
echo 'by email:           ', $ids( $ada ), "\n";
echo 'processing + email: ', $ids( array_merge( $ada, array( 'status' => 'processing' ) ) ), "\n";

echo "--- query types that need HPOS\n";
echo 'meta_query EXISTS:  ', $ids( array( 'meta_query' => array( array( 'key' => '_pc_gift_note', 'compare' => 'EXISTS' ) ), 'billing_email' => 'ada-hpos@example.test' ) ), "\n";
echo 'meta_query LIKE:    ', $ids( array( 'meta_query' => array( array( 'key' => '_pc_gift_note', 'value' => 'birthday', 'compare' => 'LIKE' ) ) ) ), "\n";
echo 'field_query OR:     ', $ids(
	array_merge(
		$ada,
		array(
			'field_query' => array(
				'relation' => 'OR',
				array( 'field' => 'total', 'value' => '30', 'compare' => '>=', 'type' => 'NUMERIC' ),
				array( 'field' => 'shipping_total', 'value' => '5', 'compare' => '<', 'type' => 'NUMERIC' ),
			),
		)
	)
), "\n";
echo 'date_query (paid):  ', $ids( array_merge( $ada, array( 'date_query' => array( array( 'column' => 'date_paid_gmt', 'after' => '1 hour ago' ) ) ) ) ), "\n";

echo "--- a custom argument\n";
add_filter(
	'woocommerce_order_query_args',
	static function ( $query_args ) {
		if ( ! empty( $query_args['has_gift_note'] ) ) {
			$query_args['meta_query'][] = array(
				'key'     => '_pc_gift_note',
				'compare' => 'EXISTS',
			);
		}
		unset( $query_args['has_gift_note'] );
		return $query_args;
	}
);
echo 'has_gift_note:      ', $ids( array_merge( $ada, array( 'has_gift_note' => true ) ) ), "\n";

echo "--- pagination\n";
$page = wc_get_orders( array_merge( $ada, array( 'limit' => 1, 'paginate' => true, 'return' => 'ids' ) ) );
printf( "total=%d pages=%d orders=%s\n", $page->total, $page->max_num_pages, wp_json_encode( $page->orders ) );

Notes on the filters, from the source of `OrdersTableQuery` and `OrdersTableDataStore`:

* `woocommerce_order_query_args` runs for every storage and is the place to translate a custom argument into a supported one (as `has_gift_note` is above). Remove the custom key afterwards, as the example does.
* `woocommerce_orders_table_datastore_get_orders_query` (since 10.4.0) filters the arguments just before the HPOS query is built.
* `woocommerce_orders_table_query_clauses` receives the SQL pieces (`fields`, `join`, `where`, `groupby`, `orderby`, `limits`) for last-minute edits; `woocommerce_orders_table_query_sql` and `woocommerce_orders_table_query_count_sql` receive the finished SQL.
* `woocommerce_hpos_pre_query` (since 8.2.0) can return a ready result (`orders`, `found_orders`, `max_num_pages`) and skip the query, which is how an external search index can answer order queries.
* `woocommerce_orders_table_datastore_extra_db_rows_for_order` lets an extension write its own rows when an order is saved; each entry names the table, the row and its format.

Read the output as three failure modes:

* *Silent emptiness.* `+get_post_meta( $id, '_order_total' )+` returns `+''+`, `get_posts()` and `WP_Query` find no `shop_order` for the order (the first line of the output asks for that e-mail address and gets zero), and the SQL sum over `wp_postmeta` is `NULL`. A report built on them shows zero.
* *Silent divergence.* `+get_post_meta( $id, '_billing_email', true )+` returned a real address. The address fields of the order were copied to the placeholder once, when the order was created, and were not updated by later
  saves: after the order moved to Barcelona the postmeta still said Madrid. Code that reads those rows works in the demo and fails in production. Writes are lost the same way: `update_post_meta()` stored a note, and the order never saw it.
* *Hooks that do not fire.* `save_post_shop_order` and `wp_insert_post` for orders do not run, as the hook experiment above shows.

The mapping from the recipe book is the cure, and the same questions in the second half of the output show it: `get_total()`, `get_billing_email()`, `get_status()`, `wc_get_orders()` and `update_meta_data()` plus `save()`.
The magic properties of the era (`+$order->billing_email+`, `+$order->id+`) still answer through the legacy class, with a `wc_doing_it_wrong()` notice since 3.0, so old code does not crash but should still be converted.

A typical posts-era "gift note" plugin, written the way such a recipe would do it, has the following shape. It is not executable code from a book; it condenses the patterns above to show what a migration touches.

	echo '<textarea name="gift_note">' . esc_textarea( get_post_meta( $post->ID, '_pc_gift_note', true ) ) . '</textarea>';
}
add_action( 'save_post_shop_order', function ( $post_id ) {
	update_post_meta( $post_id, '_pc_gift_note', sanitize_text_field( $_POST['gift_note'] ) );
} );
add_filter( 'manage_edit-shop_order_columns', 'pc_gift_column' );
add_action( 'manage_shop_order_posts_custom_column', function ( $column, $post_id = 0 ) {
	if ( 'gift' === $column ) {
		echo get_post_meta( $post_id, '_pc_gift_note', true ) ? 'Yes' : '-';
	}
}, 10, 2 );
$gifts = get_posts( array( 'post_type' => 'shop_order', 'post_status' => 'wc-processing', 'meta_key' => '_pc_gift_note', 'numberposts' => -1 ) );

  sync

[cols="3,4",options="header"]
|===
| Command | Purpose and options (from `--help` of 11.2.1)

| `wp wc hpos status`
| A summary: HPOS enabled, compatibility mode enabled, unsynced orders, orders subject to cleanup.

| `wp wc hpos enable [--for-new-shop] [--with-sync] [--ignore-plugin-compatibility]`
| Makes HPOS authoritative when the stores are in sync, or when `--for-new-shop` says the shop is new (the tables are created). `--with-sync` also enables compatibility mode. Refuses when incompatible plugins are active.

| `wp wc hpos disable [--with-sync]`
| Makes the posts authoritative again; refuses while orders are pending sync.

| `wp wc hpos count_unmigrated`
| The number of orders pending synchronisation.

| `wp wc hpos sync [--batch-size=<n>]`
| Synchronises from the authoritative store to the other, in batches (default 500).

| `wp wc hpos verify_data [--batch-size=<n>] [--start-from=<id>] [--end-at=<id>] [--verbose] [--order-types=<types>] [--re-migrate]`
| Compares the two stores. `--re-migrate` overwrites orders that differ; use it only before HPOS has ever been authoritative, or after reviewing the differences, because stale data can replace newer data.

| `wp wc hpos diff <order-id> [--format=table\|csv\|json\|yaml]`
| Shows the differences of one order between the two stores. It does not change anything.

| `wp wc hpos backfill <order-id> --from=<hpos\|posts> --to=<hpos\|posts> [--meta_keys=<keys>] [--props=<props>]`
| Copies a whole order, or only chosen props and meta keys, from one store to the other, whatever the current setting is. The tool for reconciling single orders.

| `+wp wc hpos cleanup <all\|id\|range>... [--batch-size=<n>] [--force]+`
| Removes order data from the legacy tables once HPOS is authoritative and compatibility mode is off. Stops on an order whose post looks newer than the HPOS order unless `--force`. Does not remove placeholders.

| `wp wc hpos compatibility-info [--include-inactive] [--display-filenames]`
| Plugins by compatibility state.

| `wp wc hpos compatibility-mode enable\|disable`
| Switches synchronisation without changing the authoritative store.
|===

== Performance features, and what HPOS does not solve

* *Datastore caching* (`hpos_datastore_caching`, option `woocommerce_hpos_datastore_caching_enabled`, off in the test shop) caches raw order data in the datastore instead of storing whole objects in the persistent cache; the feature text recommends it for stores that use object caching.
* *Full-text search indexes* (`hpos_fts_indexes`, option `woocommerce_hpos_fts_index_enabled`, off in the test shop, flagged experimental in the feature registry) create full-text indexes for order search on HPOS only.
* *Order list queries*: 11.0.0 rewrote multi-status order list queries as one `UNION` per status, a change listed in the changelog as a speed-up of the admin list on large stores.
* The lookup and analytics tables are separate, and importing historical orders into them is a background job (see xref:ecommerce/woocommerce/analytics.adoc[Analytics]).
* HPOS does not fix a slow plugin that loads all orders in a loop. Use the query arguments (`limit`, `return` of `ids`, `paginate`) and the fact that `wc_get_orders()` primes caches before building objects.

None of these was benchmarked here; the figures in the HPOS announcements concern stores with millions of orders, and the test shop has dozens.

== Pitfalls

[cols="2,3",options="header"]
|===
| Symptom | Cause and remedy

| HPOS is off after a scripted install
| The default is applied only when its preconditions hold. Run `wp wc hpos status` and enable explicitly.

| The HPOS radio button is greyed out
| An incompatible plugin is active, or orders are pending sync. `wp wc hpos compatibility-info` and `wp wc hpos count_unmigrated` say which.

| A plugin shows "incompatible" although it works
| It declared `false`, or declared nothing. Ask its author to add the declaration; as a last resort `wp wc hpos enable --ignore-plugin-compatibility` skips the check on your own responsibility.

| Reports, exports or integrations show no new orders
| They read `wp_posts` or `wp_postmeta`. Move them to the objects, the REST API or the HPOS tables.

| `get_post_meta()` returns old or empty values for orders
| See the legacy section: the posts side is a placeholder, plus stale copies of some fields.

| `get_order_admin_screen()` throws "This function should only be called in admin."
| Call it from admin hooks such as `add_meta_boxes`, not at load time or on the front end.

| The order list or a report disagrees with the database after a manual SQL edit
| Orders edited in the database bypass the CRUD layer and every cache and hook. Use the objects, and `wp wc hpos diff` to find the damage.

| Orders are missing after a switch of the storage
| The safeguard against switching with orders pending sync was bypassed (the development-only filter above). Switch back, run `wp wc hpos sync`, then switch again.

| `wp wc hpos verify_cot_data` is not found
| The name belongs to the `wp wc cot` alias; use `wp wc hpos verify_data`.

| A deleted order leaves a post behind
| Observed on 11.2.1: an order that had been backfilled to posts and was then deleted, with compatibility mode off, left its `shop_order` post in `wp_posts` (the HPOS rows were gone). Run a sync or remove the post by hand; deletions are only propagated by synchronisation.

| `--re-migrate` overwrote a good order
| It copies the older store over a newer one when it believes they differ. Review `diff` first.

| The setting `woocommerce_auto_flip_authoritative_table_roles` has no effect
| The HPOS documentation still describes it; the 11.2.1 source no longer contains the option, so the storage is switched by hand or by `wp wc hpos enable`.

| A plugin calls `new WC_Order( $post_id )` with an ID taken from `get_posts()`
| `get_posts()` returns nothing on HPOS. Use `+wc_get_orders( array( 'return' => 'ids' ) )+`.

| Day filters of `wc_get_orders()` return one more day after 11.2.0
| Day-precision dates now use the store's local midnight and a `+start...end+` range includes the last day.
|===

== What was and was not run

Run: every script and command whose output appears above, on the test shop with HPOS authoritative and compatibility mode off. That includes order creation through CRUD, the table and placeholder inspection, the legacy-code
reproduction, the HPOS-only query types and the custom query argument, the hook experiment, the plugin callbacks (meta box, save handler, list column), the compatibility API and `wp wc hpos` `status`, `count_unmigrated`, `diff`, `backfill` (one order of this page),
`verify_data` (one ID), `compatibility-info` and `--help` of every subcommand. PHP_CodeSniffer reported no findings for the plugin.

Not run: switching the authoritative storage in either direction, enabling and disabling compatibility mode and the scheduled and background synchronisation they start, `wp wc hpos enable`, `disable`, `sync` and `cleanup`
(each would change data of the shared shop; their behaviour comes from `--help`, the 11.2.1 source and the documentation), a plugin that declares `false` (it would have affected every other example in the shop), the order edit
and list screens in a browser, datastore caching and the full-text indexes, and any large-store timing.
