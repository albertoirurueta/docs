== What changes in a cluster

On a single server one system crontab starts `bin/magento cron:run` every minute; the job `consumers_runner` of the cron group `consumers` starts a background PHP process
for every queue consumer; the indexers are in whichever mode somebody chose once. Everything runs on the machine that also serves the
shop, which is why none of it ever needed a decision. In a cluster each of these duties needs one:

[cols="2,3,4",options="header"]
|===
| Duty | On one server | In the cluster

| Scheduling
| A crontab entry of the file system owner
| One CronJob, `pocketcoffee-cron`. The web pods and the consumers never run `cron:run`.

| Starting consumers
| The cron job `consumers_runner` forks one process per consumer
| One Deployment per consumer, `pocketcoffee-consumer-<slug>`, supervised by Kubernetes. `cron_consumers_runner` is switched off.

| Scaling consumers
| `multiple_processes` in `env.php`, a fixed number
| A KEDA `ScaledObject` per Deployment that follows the queue depth of the Amazon MQ broker.

| Indexing
| Update on Save or Update by Schedule, set by hand
| Update by Schedule everywhere, set once in the database; the cron group `index` applies the changelogs; full reindexes run as a Job.

| Logs
| `var/log/cron.log` on the disk
| `var/` is an `emptyDir` of the pod: the files disappear with it, so the logs go to the log pipeline of
xref:ecommerce/magento/cloud-operations.adoc[Cloud: Autoscaling, Observability, Backups and Security].
|===

The three pieces share the database and the broker, which is what makes them safe to move: the schedule is the table `cron_schedule` in RDS, the work of the consumers is in
the queues of Amazon MQ, and the state of the indexers is in the tables `indexer_state` and `mview_state`. None of it is in a file on a pod.

== One cron scheduler

=== What `cron:run` does

`bin/magento cron:run` is not a daemon and not a single job: it is one pass of a scheduler. For each cron group it takes a lock on the group, removes the old rows of the
table `cron_schedule`, writes the rows for the jobs that will be due in the next minutes, and then runs the rows that are due and whose status is `pending`. The
rows are the whole state: a job that is running is a row with the status `running`, a job that ran is a row with `success` or `error`, and a job whose window passed before it
started is a row with `missed`. The behaviour below was read from the 2.4.9 source (`Magento\Cron\Observer\ProcessCronQueueObserver` and
`Magento\Cron\Console\Command\CronCommand`; the files of the tag `2.4.9` and of the branch `2.4-develop` that were read are identical) and agrees with the description on
xref:ecommerce/magento/cli-cron-and-message-queues.adoc[CLI, Cron and Message Queues]:

* *Group lock.* Generating and cleaning the rows of a group happens under the lock `CRON_<group>` with a timeout of 60 seconds. A second `cron:run` that cannot get
the lock logs "Could not acquire lock for cron group" and skips the group in that pass.
* *Job lock.* Before a job runs, the scheduler takes a lock named after the group and the job code with a timeout of zero, and then changes the status of the row from `pending` to
`running` with an atomic update. A second scheduler that reaches the same row finds it taken and moves on. Rows of the same job that are still `running` when the next
one starts are turned into `error`, which is how a job killed together with its pod becomes visible.
* *Where the locks live.* The lock provider is the key `lock/provider` of `env.php` and defaults to `db`: the lock is a MySQL named lock taken with `GET_LOCK`, prefixed with
the database name, so it is shared by every pod that uses the same database. The provider `file` would be per pod, and in a cluster it would give no protection at all; the
providers `cache` and `zookeeper` also exist.
* *Options.* `--group=<id>` runs one group, `--exclude-group=<id>` (repeatable) runs all but those, and `--bootstrap=<param>` adds a bootstrap parameter.
The command does nothing, and says "Cron is disabled", when the key `cron/enabled` of `env.php` is `0`, which is the switch to use while a data migration runs.

Source: https://github.com/magento/magento2/blob/2.4.9/app/code/Magento/Cron/Observer/ProcessCronQueueObserver.php[Magento 2 source: ProcessCronQueueObserver]

=== Why one scheduler, and how many is too many

Because the locks and the atomic status change exist, two schedulers would not run the same row twice, and that is sometimes quoted as a reason to run the cron in every web pod. It
is not a good reason. Each pass of each scheduler still bootstraps Magento, reads and writes the same table, and competes for the group lock; with ten pods the table is written by ten
processes every minute for no extra throughput; a pod that is scaled in or evicted kills whatever job it was running; and a web pod that runs a long
`indexer_update_all_views` takes a PHP-FPM worker's memory away from customers. The rule of the other shops of this section applies here as well: the web pods never
schedule anything, and exactly one CronJob does. That is also what Adobe's documentation says for multi-node installations, where the crontab must run on one node only
(xref:ecommerce/magento/cli-cron-and-message-queues.adoc[CLI, Cron and Message Queues]).

The Kubernetes side of "exactly one" is `concurrencyPolicy: Forbid` on the CronJob: if the Job of the previous minute is still running when the next one is due, the controller skips the
new one instead of starting a second pod. The Magento side is the pair of locks above, which are the second line of defence when a Job is started by hand while the CronJob
is running, or when an old pod outlives a Job that the control plane has already given up on.

=== The pattern

The diagram shows one minute of the scheduler. The decision on the left is Kubernetes', the two locks on the right are Magento's; the web pods and the consumers are not part of it.

    BUSY -- "yes, concurrencyPolicy Forbid" --> SKIP["Kubernetes skips this tick"]

=== The pitfall: groups that run in a separate process

The cron group `index` and the group `consumers` have `use_separate_process` set to 1 in their `cron_groups.xml`; the group `default` has 0. For a group with 1 the
scheduler does not run the jobs itself: it starts `php bin/magento cron:run --group=<id> --bootstrap=standaloneProcessStarted=1` through a shell command renderer that sends the process to the background (the virtual
type `shellBackgroundCron` in the `di.xml` of `Magento_Cron`) and goes on to the next group. That is a good design on a server, where the parent returns after a second and the crontab entry is
free to start the next pass. In a container it is a trap: when the main process of the container ends, the pod ends, and the background children are killed with it. A CronJob that runs
the plain `cron:run` therefore succeeds in a few seconds, shows a green Job every minute, and the group `index` never gets a chance to run; the indexers fall behind and nothing reports an error.

The same source shows the way out. A process that is started with `--bootstrap=standaloneProcessStarted=1` does not fork again: it runs the group in the foreground. So the container starts one
`cron:run --group=<id> --bootstrap=standaloneProcessStarted=1` per group and waits for all of them, which is what the template below does. The parameter is not listed in the
Adobe documentation of `cron:run`; it is an internal parameter that the scheduler passes to itself, so it is one more reason to test the chart with the version you run and to read the
`cron_schedule` table after an upgrade (the commands are in <<_verifying>>).

=== Which groups to run

The groups differ per installation: every module can add jobs to the groups it chooses or declare a new one. The groups that matter on a Magento Open Source shop are `default` (most
core jobs: e-mail queue, cleaning, sitemap, currency rates) and `index` (the three jobs `indexer_reindex_all_invalid`, `indexer_update_all_views` and `indexer_clean_all_changelogs`).
Adobe Commerce and several extensions add groups. The list of groups of your image is in the XML of its modules:

[source,bash]
----
# Run in the build stage or in a shell of the image, from the Magento root
grep -rhoE '<group id="[a-z0-9_]+"' vendor/*/*/etc/crontab.xml vendor/*/*/*/etc/crontab.xml app/code/*/*/etc/crontab.xml 2>/dev/null \
  | sort -u
----

Source: https://developer.adobe.com/commerce/php/development/components/crons/[Adobe Commerce developer docs: Configure a custom cron job and cron group]

The chart takes the list from `cron.groups` (default `default` and `index`) and the groups of the extensions of the shop are added to it. The group `consumers` is never in the list, because
its only job, `consumers_runner`, is what the next part replaces. A group that is not listed does not run at all, which is the failure to look for when a feature of an extension
"does nothing" in the cluster only: look at the rows of `cron_schedule` for the job code, and at the groups of that extension's `crontab.xml`.

Two nodes of `env.php` belong to this page. The first switches off the consumer runner (the whole file is a template of the ConfigMap `pocketcoffee-env-php`, as in

    'cron_run' => false,        // the boolean false, not an environment variable: getenv() returns strings
],
'queue' => [
    // default_connection and the amqp node are shown on the page about the managed services
    'consumers_wait_for_messages' => 1,   // the integer 1: the code compares with ===

    'provider' => 'db',                   // the default; never 'file' in a cluster
],
----

Source: https://experienceleague.adobe.com/en/docs/commerce-operations/configuration-guide/files/config-reference-envphp[Adobe Commerce docs: env.php reference]

Both values have a trap that was found in the source. `ConsumersRunner::run()` reads `cron_consumers_runner/cron_run` and returns when it is falsy, so a `getenv()` string such as
`"false"` (which is truthy in PHP) would leave the runner active: write the literal. And the consumer loop treats `queue/consumers_wait_for_messages` as "wait for messages" only when
the value is the integer `1` (the comparison is strict), so `true` or `"1"` makes the consumer end as soon as the queue is empty.

The values and the template. The pod runs the same image as the web pods, with the same environment (`pc.envFrom`), the same `env.php` mounted read-only and the same writable

The decisions in the template:

* *`concurrencyPolicy: Forbid` and `startingDeadlineSeconds: 60`.* A run that overlaps the previous one is skipped, and a run that could not start within a minute of its time (a control-plane
pause, a node being replaced) is not started late on top of the next one. Magento tolerates the gaps: the rows of the group `default` have a `schedule_lifetime` of 15 minutes and those of
`index` of 2 minutes, after which an unstarted row becomes `missed` and the next pass writes new ones.
* *`backoffLimit: 0` and `restartPolicy: Never`.* A failed pass is not retried by Kubernetes; the next minute is the retry, and the jobs themselves have their status in `cron_schedule`. A retry loop of
pods would pile up against `Forbid` and hide the failure.
* *`activeDeadlineSeconds: 900`.* A pass that has not ended after 15 minutes is killed. It is a safety net against a hung database call, not a way to give jobs more time: one slow job in one group
delays the start of the whole next pass, because the container waits for every group. The jobs that can take an hour (a full `indexer_reindex_all_invalid` of a big catalogue, exports) belong in a
Job, as shown at the end of this page, not in the minute-by-minute pass. If one group must not wait for another, give it its own CronJob with its own name, `pocketcoffee-cron-<group>`, and list it
in a separate value; the template above stays the same.
* *`wait` on every child and `exit 1` when one fails.* The Job is marked failed when a group ends with a non-zero code, and `failedJobsHistoryLimit: 3` keeps the pods for `kubectl logs`.
* *The memory limit.* The PHP CLI of the official images has no `php.ini` and a `memory_limit` of 128M, far under the 756M that Magento asks for. The `php.ini` of the image (the ConfigMap `pocketcoffee-php`
is mounted by the web pods and can be added to this pod the same way) sets `memory_limit` for the CLI. The scheduler starts its children with a plain `php`, so an option on the command line of the
first process would not reach them.
* *Time zones.* The CronJob's `schedule` only has to tick every minute, so its time zone does not matter. The expressions of the Magento jobs (a nightly job at 03:00) are a different matter: `Magento\Cron\Model\Schedule` reads the
schedules of `crontab.xml` and of the database as times in the time zone of the store configuration (the code comment says "admin store timezone") and stores `scheduled_at` in UTC. A pod's own time zone is not involved, so nothing has to be set on the container.

== Queue consumers as Deployments

=== What `consumers_runner` does, and why it goes

On one server `consumers_runner` is the supervisor. `Magento\MessageQueue\Model\Cron\ConsumersRunner::run()` is called by the cron group `consumers` every minute. When
`cron_consumers_runner/cron_run` is true it takes the consumers of the installation (or the list `cron_consumers_runner/consumers`), and for each one that is not already running it starts a background process of
`php bin/magento queue:consumers:start <name> --single-thread --max-messages=<n>` (default 10000, `cron_consumers_runner/max_messages`), or one process per entry of `multiple_processes`.
"Already running" is decided with a named lock: the consumer takes `md5(<name>)` with `--single-thread`, the runner asks whether that lock is taken. The design assumes one machine, and breaks in three ways in a cluster:

* *The consumers would live in the cron pod.* The runner's children are background processes of the pass that forked them, the same trap as the groups above: they die when the CronJob pod ends,
and a CronJob pod that waited for them would never end and would block `Forbid`.
* *There is no supervision.* A consumer that is killed by the kernel for memory is started again at the next minute at best. Kubernetes restarts a container at once, reports the restarts, and
keeps the pod's resource requests and limits for the consumer alone.
* *There is no scaling.* The number of processes of a consumer is a number in `env.php`. The queue depth that decides how many are needed is only visible to the broker.

So `cron_consumers_runner/cron_run` is `false` (see above) and each consumer that the shop needs is a Deployment whose one container runs one `queue:consumers:start` in the foreground. The
consumers that exist are listed by `bin/magento queue:consumers:list` (24 on the Mage-OS 3.6.0 test shop of the other pages); a shop runs only those whose modules it uses. Pocket Coffee runs three:
`async.operations.all` (the individual operations of bulk and asynchronous API calls and mass actions), `product_action_attribute.update` (the mass attribute updates of the Admin) and
`media.storage.catalog.image.resize` (catalogue image resizing, see xref:ecommerce/magento/cloud-media-and-remote-storage.adoc[Cloud: Media and Remote Storage]).
In the XML of the three modules the name of the consumer and the name of its queue are the same, which is also the name of the queue on the broker.

Source: https://github.com/magento/magento2/blob/2.4.9/app/code/Magento/MessageQueue/Model/Cron/ConsumersRunner.php[Magento 2 source: ConsumersRunner]

=== The command

The command is the one of the single-server page; the options that matter in a container were read from `StartConsumerCommand` and the loop in `CallbackInvoker`:

[cols="2,5",options="header"]
|===
| Option or behaviour | In a Deployment

| `--max-messages=N`
| The process handles N messages and exits with code 0. Without it the consumer subscribes and never returns. A finite value is what releases memory that PHP does not give back and what makes the consumer pick up a new
configuration, so every Deployment sets it (1000 here; the runner's own default is 10000).

| `--single-thread`
| Takes the named lock of the consumer with timeout 0 and exits with "Consumer with the same name is running" when it is taken. Do not pass it: with two replicas the second one would fail and
restart in a loop. It exists for the one-per-machine model of the runner.

| `--multi-process=N`
| The same lock, one per process number. Not needed either: the number of processes is the number of replicas.

| `--area-code`, `--batch-size`
| Left alone. The area defaults to `global`, as in the runner.

| `queue/consumers_wait_for_messages`
| Must be the integer `1`. With `0` an empty queue ends the process; with `--max-messages` far above the traffic the container would exit and be restarted over and over.
|===

Source: https://experienceleague.adobe.com/en/docs/commerce-operations/configuration-guide/message-queues/manage-message-queues[Adobe Commerce docs: Manage message queues]

With the AMQP connection an idle consumer polls the broker (`dequeue()` with a one-second sleep by default), so every idle replica is one request per second to RabbitMQ. That is nothing for
a few replicas and one more reason to let KEDA take idle consumers to zero.

Notes on the template:

* *No `replicas` when KEDA is on.* The `ScaledObject` owns the replica count (the next part). With `keda.enabled: false` the Deployment uses `minReplicas`.
* *No probes.* A consumer serves no port. A liveness probe that runs a command in the pod would start a PHP process inside a pod that is already using its memory limit, and the only failure that
matters, a consumer that is alive but does not consume, shows up as a growing queue, which is the signal KEDA and the alerts of
xref:ecommerce/magento/cloud-operations.adoc[Cloud: Autoscaling, Observability, Backups and Security] already watch.
* *`maxUnavailable: 0`.* During a release a new consumer starts before an old one stops, so the queue is never without a consumer. Both versions of the code run side by side for a moment: handlers must accept
the messages of the previous release, a rule that comes back on xref:ecommerce/magento/cloud-releases-and-zero-downtime-deployments.adoc[Cloud: Releases and Zero-Downtime Deployments].
* *The same image tag as the web pods.* A consumer that runs old code against a new schema is the typical post-release error; because the consumers are in the same chart and the same
`image.tag`, one `helm upgrade` replaces them together with the web pods, after the migration Job.

=== Restarts and `queue:consumers:restart`

A consumer that reaches `--max-messages` ends with code 0 and, because a Deployment's pods have `restartPolicy: Always`, the kubelet starts the container again. Kubernetes applies a back-off to restarts of a
container that ends quickly (10 seconds, doubling, capped at five minutes, reset after the container has run for ten minutes), whatever the exit code, so a busy queue with a small `--max-messages` shows
restarts with a delay and counts in the `RESTARTS` column. That is expected, not a failure; choose `--max-messages` so that a consumer lives for minutes under load (1000 messages of the resize consumer
are minutes of work) and the restart count stays low. Check the behaviour of your Kubernetes version in the pod lifecycle documentation: the decay of the back-off has been under change in recent releases.

On a server the command `bin/magento queue:consumers:restart` tells the running consumers to restart after a deployment. It writes a new version to the table `queue_poison_pill`; each consumer compares the version
it saw when it started with the current one after each message it receives, and if they differ it rejects that message (the broker gets it back) and exits with code 0. In a cluster it is not part of a release, because the rolling update
replaces the pods. It is still useful in one case: to make every consumer drop its in-memory state (for example after a change of configuration that is read at start) without a new image, and
a consumer with an empty queue notices the pill only when its next message arrives.

=== Graceful shutdown

A consumer is stopped by SIGTERM, whenever a pod is evicted, a node is drained, KEDA scales in or a rollout replaces it. In the consumer classes that were read (`Consumer`, `CallbackInvoker`, `StartConsumerCommand`) no signal handler
is registered, so PHP's default applies and the process ends at once, in the middle of the handler if it is running. With RabbitMQ that is survivable by design: the message was delivered but not acknowledged, and a message that is
not acknowledged when the connection closes goes back to the queue and is delivered again. What the shop has to guarantee is the other half of that contract, which is also what the single-server page already says: *a handler must be idempotent*, because
"delivered twice" is a normal event in a cluster.

So a long `terminationGracePeriodSeconds` would not help here (there is nothing that finishes the current message), and the value is 30 seconds only to give the container time to close its connection. Two precautions follow:
keep the work of one message short (the resize consumer handles one image per message), and spread the replicas over nodes with `topologySpreadConstraints` as for the web pods so that one node drain does not stop a whole consumer
(xref:backend/kubernetes/scheduling-and-disruptions.adoc[Scheduling and Disruptions]). Whether the 2.4.9 consumers register signal handlers anywhere that was not read is not documented by Adobe; test a `kubectl delete pod` of a consumer
that is in the middle of a slow handler and look at whether the message is redelivered once.

Source: https://www.rabbitmq.com/docs/confirms[RabbitMQ Documentation: Consumer Acknowledgements and Publisher Confirms]

=== Several replicas of one consumer

With the AMQP connection all the replicas of a consumer read the same queue and the broker gives each message to one of them (competing consumers), which is what makes scaling work. Three things have to be true for a
consumer to be scaled beyond one replica:

* the handler is idempotent (above);
* the order of the messages does not matter, or is not guaranteed anyway: two replicas process messages in parallel and a retry changes the order;
* the handler takes its own locks when it touches shared state. The consumers of the core modules were written to be run `multiple_processes` on one server, which is the same situation, but a consumer of an extension may not have been.
Keep an unknown consumer at `maxReplicas: 1` until its vendor says otherwise.

Consumers that use the database queue (`connection="db"`, the table `queue_message`) are not covered by this page: the broker is not involved, and the queue depth is a `COUNT` on `queue_message_status` that a KEDA scaler for MySQL can follow, as for the Action Scheduler on
xref:ecommerce/woocommerce/cloud-action-scheduler-workers.adoc[Cloud: Action Scheduler Workers on Kubernetes]. On a production shop the connection is `amqp` for everything that is queue-driven; the managed service exists for that.

== Scaling the consumers with KEDA

=== What KEDA does, and the Amazon MQ endpoint

KEDA is an operator that turns an external number (here the number of messages waiting in a queue) into a replica count. A `ScaledObject` names a Deployment and one or more triggers; KEDA creates and owns a HorizontalPodAutoscaler for it
and adds what a plain HPA lacks, scaling from zero and back to zero. The general mechanics are on xref:backend/kubernetes/autoscaling.adoc[Autoscaling]; KEDA is installed once per cluster (the Helm chart or the EKS add-on of the cluster page,
xref:cloud/aws/eks-clusters.adoc[EKS Clusters]) and is not part of the Magento chart.

The RabbitMQ scaler can read the queue length over AMQP or over the management HTTP API. The HTTP API is the right one here, for a reason that is in the scaler's documentation: only the HTTP API counts the unacknowledged messages, so a
queue whose messages are all in the hands of busy consumers still reads as non-empty. On Amazon MQ the management API is served on the same listener ports as the web console, 443 and 15671 (the documentation says they can be used
interchangeably), under the broker's endpoint, with the broker's users. The endpoint of Pocket Coffee's broker is the placeholder `b-example.mq.eu-west-1.on.aws`; the AMQP port of the consumers is 5671 and the management port used
by KEDA is 443. Both are reachable only inside the VPC, so the security group of the broker must allow 443 from the nodes that run the KEDA operator (not from the application pods): the scaler runs inside the operator, which is in the namespace
`keda` and in the same VPC.

Source: https://docs.aws.amazon.com/amazon-mq/latest/developer-guide/rabbitmq-basic-elements-broker.html[Amazon MQ Developer Guide: Broker (RabbitMQ)]

=== A user for KEDA

The chart on the xref:ecommerce/magento/cloud-eks-infrastructure-and-helm.adoc[Cloud: EKS Infrastructure and Helm Deployment] page keeps the setup minimal: its `ScaledObject` reads the broker user of `env.php` from the consumer's environment. This section is the stricter variant, with a monitoring-only user and a `TriggerAuthentication`; the `keda.*` values below extend the chart's `keda` block and replace its trigger metadata.

The consumers connect as the broker user `magento`. KEDA gets a user of its own, `keda`, that can only look: Amazon MQ supports the tags `administrator`, `management` and `monitoring` on RabbitMQ users, and a user is created, and its tags
and permissions set, through the management API or the web console with an administrator (the first user, created with the broker). The commands below use placeholders; the administrator password is read from the environment and never typed
into the shell history, and the password of `keda` goes into the secret `pocketcoffee/prod/magento` under the key already used for the AMQP user, or under a key of its own (the template further down reads the key from `keda.remoteKey`).

[source,bash]

# From a host inside the VPC (a bastion or a debug pod). Placeholders only.

The fields, as documented for KEDA 2.21 and checked against the scaler's source (`pkg/scalers/rabbitmq_scaler.go`):

* *`protocol: http`.* The management API. The default `auto` infers it from the scheme of `host`; it is written explicitly so that a change of the URL cannot switch to AMQP unnoticed.
* *`host`.* The URL of the management API without credentials. The `username` and `password` of the `TriggerAuthentication` are used when both are set (setting only one is an error). The URL has no path:
the scaler takes the last path segment of `host` as the vhost, and an empty one means the root vhost `/`, which it requests as `%2F`. Pocket Coffee's vhost is `/`, so `vhostName: "/"` says the same thing
explicitly; a shop with another vhost sets `vhostName` and the scaler escapes it.
* *`mode: QueueLength` and `value`.* The target number of messages per replica. KEDA, through the HPA, asks for `ceil(messages / value)` replicas: with `value: "100"` and 450 messages in `async.operations.all`, five replicas,
capped by `maxReplicaCount`. Rate-based modes (`MessageRate` and others) exist and need `protocol: http`; the queue length is the signal that matches a backlog.
* *Which messages count.* With the HTTP protocol the length is the total (ready plus unacknowledged) unless `excludeUnacknowledged: "true"` is set. The default is right for consumers: a message that is being processed is load.
* *`activationValue`.* The threshold above which the scaler counts as active; with the default of `0`, one message wakes a Deployment that is at zero replicas, which is what `minReplicaCount: 0` of the resize consumer relies on.
* *`pollingInterval` and `cooldownPeriod`.* The scaler asks the broker every 30 seconds; after the last active reading KEDA waits 300 seconds before it scales to zero. Scaling between 1 and `maxReplicaCount` is done by the HPA's own algorithm and
its default stabilisation.

Validation: `helm lint` and `helm template | kubeconform -strict -ignore-missing-schemas` pass; the `ExternalSecret`, the `TriggerAuthentication` and the three `ScaledObject` objects are custom resources that `kubeconform` skips
(five skipped resources in the run of this page), so they are validated on a cluster with `kubectl apply --dry-run=server` once KEDA and External Secrets are installed.

=== Pitfalls

* *The `ScaledObject` owns the replica count.* The Deployment omits `replicas`; never add an HPA of your own for the same Deployment, and never scale the consumers by hand with `kubectl scale` (KEDA puts the number back).
* *Scale to zero means a cold start.* The first message into an empty queue waits for the next poll (up to 30 seconds), the pod scheduling (a new node under Auto Mode or Karpenter can add a minute) and the image pull. That is fine for image
resizing and wrong for a consumer that a shopper waits for, so `minReplicas` is 1 for the other two.
* *Scale-in kills consumers.* The HPA removes pods with SIGTERM, and the consumers do not finish their message (above). The cooldown and the HPA's stabilisation window make it rare; the idempotent handlers make it harmless.
* *The scaler runs in the operator.* If KEDA cannot reach the broker (the security group, a wrong URL, a wrong tag), the `ScaledObject` goes to `Unknown` or `Failed` and the replica count stays where it was. Add `fallback` (a number of replicas to use after N failed
reads) so that a broken scaler does not freeze the consumers at zero, and alert on KEDA's `keda_scaler_errors_total`.
* *A TLS certificate that is not trusted.* The Amazon MQ endpoint presents a certificate of a public authority, so the default trust of the operator image works; `unsafeSsl` must not be needed, and setting it is a sign that the URL is wrong.
* *One trigger per queue.* A Deployment that reads two queues (it does not here) would need two triggers; keep one consumer, one queue and one `ScaledObject`.

== Indexers in Update by Schedule

=== Why schedule

An indexer in *Update on Save* rebuilds the affected rows inside the request that changed the data (the Admin save, the import, the API call), so the web pods, the one thing that must stay quick, pay for the indexing, and several of them can try the same
tables at once. In *Update by Schedule* the change is only recorded: MySQL triggers on the source tables write the id of the changed row to a changelog table (`+_cl+` appended to the name of the view), and the cron job `indexer_update_all_views` of the group
`index`, once a minute, reads the new ids and reindexes those entities in portions. This is the *mview* mechanism of
xref:ecommerce/magento/caching-indexing-and-performance.adoc[Caching, Indexing and Performance], and it is what Adobe recommends for production. In a cluster it has an additional merit: the work moves to the one pod that is allowed to do background work, the CronJob.

The mode is state of the database, not of the code. The triggers and the changelog tables live in RDS, the mode in the tables `mview_state` and `indexer_state`; `config.php` of the image and the ConfigMap of `env.php` hold nothing about it. Two consequences:

* it is set once, after the installation and again after any restore of a database that was taken from a place where the mode was different (the migration page,
xref:ecommerce/magento/cloud-migrating-from-a-single-server.adoc[Cloud: Migrating from a Single Server], does this after the import);
* it cannot be forgotten by a rollout and it cannot be rolled back with the image.

=== Setting and checking the mode

[source,bash]
----
# In any pod of the image that has the environment, e.g. through kubectl exec into a web pod
kubectl -n pocketcoffee exec deploy/pocketcoffee-web -c php-fpm -- php bin/magento indexer:show-mode
kubectl -n pocketcoffee exec deploy/pocketcoffee-web -c php-fpm -- php bin/magento indexer:set-mode schedule
kubectl -n pocketcoffee exec deploy/pocketcoffee-web -c php-fpm -- php bin/magento indexer:status
----

Source: https://experienceleague.adobe.com/en/docs/commerce-operations/configuration-guide/cli/manage-indexers[Adobe Commerce docs: Manage the indexers]

`indexer:set-mode schedule` creates the triggers on the watched tables; without ids it does it for every indexer. Adobe's advice is to run it in maintenance mode with cron stopped, to avoid database locks, and in a cluster that is simple: run it before the
first traffic of a new environment (in the installation Job's last step or by hand right after it) and, on a running shop, scale the CronJob out of the way by setting `cron.enabled` to false in the same release, or use `cron/enabled` as the switch described above.
The customer grid indexer changed in 2.4.8 and supports both modes; read the output of `indexer:status` rather than assuming.

The status of an indexer has two parts, the state of the index (`Ready`, `Reindex required`, `Processing`) and the backlog of the schedule (`idle (3 in backlog)`), and the second one is the cheapest health check of the whole background machinery. A backlog that grows is one of three things: the CronJob does not
run the group `index`, it runs it but every pass fails or is killed, or the indexer is too slow for the rate of changes. The commands to tell them apart are in <<_verifying>>.

=== The `index` group in the CronJob

The group `index` has three jobs: `indexer_reindex_all_invalid` and `indexer_update_all_views` every minute, `indexer_clean_all_changelogs` every five. Its `cron_groups.xml` has `schedule_lifetime` of 2 minutes and `schedule_ahead_for` of 4, so a missed row is
quickly replaced, and `use_separate_process` of 1, which is the reason for the `standaloneProcessStarted` parameter of the template. Three effects to know:

* `indexer_reindex_all_invalid` reindexes any indexer whose state is invalid, in the CronJob pod. After an upgrade that invalidates an indexer, a big catalogue can keep a pass busy for hours, `activeDeadlineSeconds` ends it, and
the next pass starts it again from the beginning. Do not rely on this job for the big ones: run them in the reindex Job below, and keep the job for the small indexers that it handles well.
* While an indexer is `Processing`, a second `indexer:reindex` of the same indexer is refused: `IndexerReindexCommand` checks the status and prints "index is locked by another reindex process. Skipping." The check is on the status column, not on a lock, so a pod that was killed in the middle of a reindex
leaves the status `working` behind and blocks the next run until somebody resets it (`indexer:reset <id>` marks it invalid again, after which `indexer:reindex <id>` rebuilds it). Look for a status that does not change before
you look for a bug in the indexer.
* `indexer_update_all_views` runs the mviews in the order of the configuration, and a very large changelog (an import of the whole catalogue, a bulk price change) is processed in portions across passes; the backlog goes down over several minutes, not in one.

== Reindex Jobs

A full reindex is not part of the rhythm of the shop; it is an event, and Kubernetes has a primitive for events, the Job. `pocketcoffee-reindex` runs `bin/magento indexer:reindex` (all indexers, or the ids in `reindex.indexers`) to the end in a pod of its own, with the memory it needs, the same
image and environment as every other workload, and a status that `kubectl` and the CI can read. The cases for it are:

* after a release whose `setup:upgrade` changed what an indexer produces (the release notes and the module's `UpgradeData` say so, and `indexer:status` shows `Reindex required`);
* after the import of the database in a migration, or after a restore (xref:ecommerce/magento/cloud-migrating-from-a-single-server.adoc[Cloud: Migrating from a Single Server]);
* after a change of the search engine, the domain or the index prefix: every OpenSearch index is built again;
* after a long outage of the CronJob, when the backlog is larger than a minute-by-minute pass can clear.

The Job is a template in the chart, off by default. It is not a Helm hook, because a hook would run it at every upgrade; it is rendered on demand with `--show-only` and applied with `kubectl`, with a `run` value that is part of the Job's name (a finished Job with the same
name cannot be created again, and `ttlSecondsAfterFinished` removes it a day after the end). `MAGE_INDEXER_THREADS_COUNT` is the documented environment variable for the number of processes the reindex of the indexers that support it
uses; the default of 1 is the safe value on a shared database.

  resources:

    limits: { memory: 4Gi }

The load on RDS and on OpenSearch is real: run it in a quiet hour and watch the
dashboards of xref:ecommerce/magento/cloud-operations.adoc[Cloud: Autoscaling, Observability, Backups and Security].
* *Connections.* The Job connects as `mg_migrate`, like the cron pod and the consumers, because the indexers need DDL privileges (see the managed database page); the web pods use `mg_app`. The named locks of the previous parts are session state of MySQL; Amazon RDS Proxy lists the conditions that pin a client connection to one database connection (prepared statements and statements over 16 KB among them) and
`GET_LOCK` is not in that list, but the behaviour of long-lived named locks through the proxy was not tested here. If you use the proxy, test the cron and the consumers through it, or point those pods at the database endpoint directly; the managed-database page,
xref:ecommerce/magento/cloud-managed-database.adoc[Cloud: Managed Database (RDS and Aurora)], covers the proxy and the connection arithmetic.
* *`--set` on `helm template` is not a release.* The Job is applied outside the release; Helm does not own it and a later `helm upgrade` does not delete it. That is the purpose; the TTL cleans it.
* *Do not run two for the same indexers.* The second one skips the indexers that are `working` and exits successfully, which looks like a run that did nothing.
* *After it.* `indexer:status` in the logs shows `Ready` with a backlog of 0 for the rebuilt indexers; the mode of an indexer is not changed by a reindex.

== Releases and these workloads

A release changes the image tag, and every workload of this page takes it: the CronJob uses it for the next minute's Job; the consumers and the web pods roll with it. The order matters and is the one of
xref:ecommerce/magento/cloud-releases-and-zero-downtime-deployments.adoc[Cloud: Releases and Zero-Downtime Deployments]: the migration Job (`pocketcoffee-migrate`, `setup:upgrade --keep-generated`) runs first as a pre-upgrade hook, then the Deployments roll. Between the end of the migration and the end of the
rollout, old consumers and old web pods use the new schema, which is the reason for the rule of declarative schema migrations of
xref:ecommerce/magento/declarative-schema-and-patches.adoc[Declarative Schema and Patches] to add before removing. The cron pass that runs during a release starts from the new image tag if its Job
was created after the upgrade, and from the old one if it was created before; that overlap lasts one pass and is harmless for the jobs of the core.

Two things are worth a line in the release checklist: the output of `indexer:status` after the migration (an indexer that says `Reindex required` is the reason to start the reindex Job), and `bin/magento queue:config:status` (are the queues of the new code on the broker; the queue topology is created by
`setup:upgrade`, and a consumer for a queue that does not exist fails to start).

== Verifying

The commands to answer "is the machinery running" from the outside, with `kubectl` and the database:

[source,bash]
----
# The scheduler: last Jobs, their pods and their logs
kubectl -n pocketcoffee get cronjob pocketcoffee-cron
kubectl -n pocketcoffee get jobs -l app.kubernetes.io/component=cron --sort-by=.metadata.creationTimestamp | tail -5
kubectl -n pocketcoffee logs job/$(kubectl -n pocketcoffee get jobs -l app.kubernetes.io/component=cron -o jsonpath='{.items[-1:].metadata.name}')

# The consumers, KEDA and the replicas it chose
kubectl -n pocketcoffee get deploy -l app.kubernetes.io/component=consumer
kubectl -n pocketcoffee get scaledobject
kubectl -n pocketcoffee describe scaledobject pocketcoffee-consumer-async-operations-all | sed -n '/Conditions/,$p'

# The indexers and the consumers known to the code
kubectl -n pocketcoffee exec deploy/pocketcoffee-web -c php-fpm -- php bin/magento indexer:status
kubectl -n pocketcoffee exec deploy/pocketcoffee-web -c php-fpm -- php bin/magento queue:consumers:list
kubectl -n pocketcoffee exec deploy/pocketcoffee-web -c php-fpm -- php bin/magento queue:config:status
----

Source: https://kubernetes.io/docs/reference/kubectl/quick-reference/[Kubernetes Documentation: kubectl quick reference]

On the database (a read-only session on the replica or the primary, from a debug pod; the user `mg_app` can read the table):

[source,sql]
----
-- Did the scheduler run the groups in the last five minutes, and with which result?
SELECT status, COUNT(*) AS rows_, MAX(executed_at) AS last_executed
  FROM cron_schedule
 WHERE scheduled_at > NOW() - INTERVAL 5 MINUTE
 GROUP BY status;

-- Jobs in error or missed, with the reason
SELECT job_code, status, scheduled_at, LEFT(messages, 120) AS message
  FROM cron_schedule
 WHERE status IN ('error', 'missed') ORDER BY scheduled_at DESC LIMIT 20;

-- State of the views; the backlog is the changelog rows newer than version_id, which indexer:status prints
SELECT view_id, mode, status, version_id FROM mview_state;
----

Source: https://experienceleague.adobe.com/en/docs/commerce-operations/configuration-guide/cli/configure-cron-jobs[Adobe Commerce docs: Configure and run cron]

Reading the output: a table with `pending` rows only and none that are `success` means that nothing is executing them (the CronJob is suspended, or only the groups other than the ones of the rows run); rows of the group `index` missing altogether means that `cron.groups` has no `index`; `running`
rows that are older than a few minutes mean a pass that was killed, and `error` rows with the message "Cron Job has an error" lead to the log of the pod of that pass.

== Common problems

[cols="3,5",options="header"]
|===
| Symptom | Cause and fix

| The CronJob shows green Jobs, but `cron_schedule` has `pending` and `missed` rows of the group `index` and the backlog grows.
| The plain `cron:run` was used: the separate-process groups were forked into the background and killed with the pod. Run each group with `--bootstrap=standaloneProcessStarted=1`, as the template does.

| Consumers do not run, and a PHP process of `queue:consumers:start` exists inside the cron pod.
| `cron_consumers_runner/cron_run` is still true (a string from `getenv()` is truthy) or the group `consumers` is in `cron.groups`. Set the literal `false`, remove the group.

| A consumer Deployment is in `CrashLoopBackOff` with "Consumer with the same name is running".
| `--single-thread` or `--multi-process` was added; remove it, the replicas are meant to run together.

| A consumer exits within seconds and restarts again and again.
| `queue/consumers_wait_for_messages` is not the integer `1`, or the queue does not exist on the broker (`queue:config:status`, then `setup:upgrade`).

| `ScaledObject` is `Failed` with a 401 or a 403 in the KEDA operator log.
| The user `keda` has no tag or no permission on the vhost; the `curl` of the section on the user is the test.

| The replica count of a consumer does not move.
| An HPA or a manual `kubectl scale` fights the `ScaledObject`; or the Deployment has `replicas` in the manifest while `keda.enabled` is true.

| The message count is 0 but consumers are busy.
| `excludeUnacknowledged` is on, or the protocol is `amqp` and the queue is counted by `QueueDeclarePassive` ready messages only; use `http` and leave the default.

| `indexer:reindex` says "index is locked by another reindex process. Skipping."
| Another reindex runs, or one was killed and left the status `working`. Look at `indexer:status`; if nothing runs, `indexer:reset <id>` and run it again.

| After an import the storefront shows old products and `indexer:status` shows `Ready`.
| The mode is Update on Save and the rows were written by SQL, not by Magento; or the triggers are missing (the mode says schedule, the triggers were dropped by a restore). Set `realtime` and then `schedule` again, which recreates the triggers, then reindex.

| A job of an extension never runs only in the cluster.
| Its cron group is not in `cron.groups`. Find it in the extension's `crontab.xml` and add it.
|===
