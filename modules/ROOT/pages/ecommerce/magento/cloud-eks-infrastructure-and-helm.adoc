== What the configuration builds

image::ecommerce-magento-cloud-opentofu-layout.svg["OpenTofu layout: one root module with an S3 state backend and two workspaces; a VPC with public, private, database and ElastiCache subnets holding EKS, OpenSearch, Amazon MQ, RDS and two Valkey groups; and S3, EFS, ECR, Secrets Manager, KMS, ACM and WAF outside the VPC",width=760]

One root module in `infra/` creates one environment; the workspace (`staging` or `production`) chooses which. The files are split by service:

[cols="1,3",options=header]
|===
| File | Contents
| `versions.tf`, `variables.tf`, `locals.tf` | Constraints, the S3 backend, two provider blocks (the second is `us-east-1`, for the CloudFront certificate), the inputs and the per-workspace settings (sizes, CIDR, host names) in one map
| `vpc.tf`, `kms.tf` | VPC with public, private, database and ElastiCache subnets in three zones; one customer-managed key
| `eks.tf` | EKS Auto Mode cluster, the EFS add-on, the access entry of the deployment role, Pod Identity roles for the EFS driver and External Secrets Operator
| `rds.tf` | RDS for MySQL 8.4 with the parameter group `pocketcoffee-magento-mysql84`, Multi-AZ in production, with a managed master password
| `opensearch.tf` | Amazon OpenSearch Service domain, VPC access, fine-grained access control with an internal master user
| `elasticache.tf` | Two Valkey replication groups, `pocketcoffee-prod-cache` and `pocketcoffee-prod-session`, with different eviction policies
| `mq.tf` | Amazon MQ for RabbitMQ 4.3 broker, a cluster in production
| `media.tf`, `efs.tf` | The S3 media bucket, the IAM role of the Magento pods bound to the service account with Pod Identity; the EFS alternative
| `ecr.tf`, `secrets.tf` | Two image repositories and the GitHub OIDC deployment role; the Secrets Manager containers
| `acm.tf`, `waf.tf` | The regional site certificate and the `us-east-1` media certificate, both with DNS validation; a web ACL that restricts the Admin
| `outputs.tf` | The values the chart and the seeding script need
|===

== Decisions that differ from the other platforms

* *MySQL 8.4, not MariaDB.* RDS for MySQL 8.4 is the engine of this section (standard support until 2029-07-31; 8.0 left standard support on 2026-07-31) and
  Adobe's 2.4.9 requirements list MySQL 8.4 and MariaDB 12.3. Aurora MySQL 3 is the one Aurora version that Adobe's table names (`8.0.mysql_aurora.3.12 or latest
  available`); Aurora, RDS Proxy and MariaDB are on
  xref:ecommerce/magento/cloud-managed-database.adoc[Cloud: Managed Database (RDS and Aurora)]. The split database (separate sales and quote databases) is deprecated
  since 2.4.2 and nothing here uses it.
* *Five managed services behind one application.* Magento needs a search engine (OpenSearch 3), a cache and a session store (Valkey 9), a message broker
  (RabbitMQ 4.3) and a full page cache (Varnish, which runs in the cluster, because the page cache is not a managed service on AWS). Adobe's 2.4.9 table has a
  row per AWS service that is more conservative than the versions of the engines: `OpenSearch 3.1 or latest available`, `AWS MQ 3.13 or latest available` and
  ElastiCache `Valkey 8 is available`. This page uses what the application tests (OpenSearch 3.5, RabbitMQ 4.3, Valkey 9.0) and makes each version a one-line change; check
  those rows when you apply.
* *Two Valkey replication groups, not one.* Adobe recommends one instance per purpose. The cache group is rebuildable and uses `volatile-lru`; the session
  group never evicts (`noeviction`), keeps a daily snapshot and has replicas in other zones. The eviction choice and what `allkeys-lru` would do to the tag
  index of the cache backend are on the OpenSearch, Valkey and RabbitMQ page. There is no Valkey database for the full page cache: Varnish holds it, and
  `env.php` has no `page_cache` frontend.
* *Amazon MQ needs the Graviton family for 4.x.* RabbitMQ 4.3 and 4.2 run only on the `mq.m7g` instance types in Amazon's documentation, so the single
  instance of staging uses `mq.m7g.large` as well.
* *The media bucket always exists, EFS only when asked.* The default is remote storage on S3 behind CloudFront, so the pods need an IAM role and no shared
  volume; `media_mode = "efs"` creates the file system and its access point instead (see
  xref:ecommerce/magento/cloud-media-and-remote-storage.adoc[Cloud: Media and Remote Storage] for the choice).
* *Two extra WAF rules.* The Admin lives under the path of `admin_front_name` and the REST route that turns an administrator's password into a token bypasses it,
  so both are blocked for every address outside an allow-list; the managed rule groups run with one override that the Admin's large forms require.
* *Secrets are containers.* OpenTofu creates the Secrets Manager secrets; a script writes the values (below). The one value that must never pass through the
  configuration or the state is the encryption key, `crypt/key`.

== State backend and workspaces

The backend is the S3 bucket and the `use_lockfile` locking of the WordPress page, with the state key `magento/pocketcoffee.tfstate`, so that all platforms can share one
bucket. Create the bucket as shown in
xref:cms/wordpress/eks-infrastructure-with-opentofu.adoc#_the_state_backend[the state backend section] (use your own bucket name), then pass it with
`-backend-config`. The workspace map in `locals.tf` refuses `default`, as there, so a plan in the wrong workspace fails instead of creating a third environment.
The honest limits of workspaces (one credential for both environments) are on the same page; separate AWS accounts with the same code are the stricter choice.

The providers are AWS (twice, the second with the alias `us_east_1`, because a certificate for CloudFront must be requested there) and random. `admin_cidrs` is used
for the Kubernetes API endpoint and for both Admin rules of the web ACL, and holds a documentation address range here; replace it with the office and VPN ranges.
`admin_front_name` repeats the value of the chart's `shop.adminFrontName` and the environment variable `MAGENTO_BACKEND_FRONTNAME`, and the three must match. The
staging workspace is a smaller independent copy: its own cluster, database and data tier, one NAT gateway, no Multi-AZ, no dedicated OpenSearch master nodes and a
single-instance broker. `media_mode` and `github_oidc_provider_arn` are the two switches that change which resources exist.

Source: https://github.com/terraform-aws-modules/terraform-aws-eks[terraform-aws-modules/terraform-aws-eks]

EKS Auto Mode runs node provisioning and patching, the block storage driver and the pod networking; the EFS CSI driver is an add-on with its own Pod Identity role
(installed in both modes, because the driver costs nothing and the switch to EFS then needs no cluster change), and the External Secrets Operator reads only
`+pocketcoffee/<env>/*+`. The WordPress page explains each of these points, including why `enable_cluster_creator_admin_permissions` should be replaced by access entries for
people. One addition for Magento: `access_entries` gives the GitHub deployment role (`ecr.tf`) the cluster access policy `AmazonEKSAdminPolicy` scoped to the namespace
`pocketcoffee`, so the pipeline can run `helm upgrade` without any cluster-wide right. The role of the shop's own pods is in `media.tf`.
Auto Mode does not include a Gateway API controller, so the platform team installs the AWS Load Balancer Controller for the `Gateway` that the chart's `HTTPRoute`
objects attach to (see xref:cloud/aws/eks-microservices.adoc[Deploying Microservices on EKS]). Node replacement under Auto Mode happens at least every 21 days,
so the chart's PodDisruptionBudgets must allow a drain.

* `utf8mb4` and `utf8mb4_general_ci` are the character set and collation Magento uses; in 2.4.9 the adapter chooses its own `SET NAMES` statement when `env.php` has no

* There is no `sql_mode` entry on purpose: the page on the database says what Magento sets per connection; change nothing here without testing `setup:upgrade`.

cart in progress), so that group uses `noeviction`, has one snapshot a day and fails writes loudly when full. The cache is rebuildable but not evictable at will:
the cache backend of Magento stores each entry with an expiry but keeps its tag index (the sets that make "clean by tag" work) without one, so a policy that evicts any key could
delete part of an index and leave entries that can no longer be invalidated; `volatile-lru` evicts only keys that carry an expiry. Adobe's pages on Valkey (read for this page)
do not name a policy, so treat `volatile-lru` as a reasoned choice, watch the memory alarms of the operations page, and size the group so that it does not fill. The auth tokens
are 48 letters and digits (ElastiCache accepts 16 to 128 printable characters and forbids a few, among them `@`, `"` and `/`) and exist in the encrypted state, as on the WordPress page;
`outputs.tf` exposes them as sensitive outputs for the seeding script. Valkey 9.0 is an engine version that ElastiCache lists; Adobe's 2.4.9 table for AWS names Valkey 8 as available, so
`engine_version` and the parameter group family (`valkey9`) are the two lines to change if you stay on 8.

== Secrets for the shop

Magento keeps one value that cannot be recreated: the encryption key. Everything it encrypts in the database (payment tokens that modules store, API credentials in the configuration, the
two-factor secrets of administrators, saved integration tokens) is unreadable without it, and a different key on one pod means that pod fails to decrypt, or encrypts what the others
cannot read. The rule for all of the secrets is the same: *identical on every pod, and never generated by a pod*. The application secret holds seven keys, and the ExternalSecret of the chart maps each
to the Kubernetes Secret key of the same row:

[cols="2,3,3",options=header]
|===
| Key in `pocketcoffee/prod/magento` | Kubernetes Secret key and environment variable | Used by
| `db_app_password` | `MAGENTO_DB_PASSWORD` | Web and Admin pods, as `mg_app`
| `db_migrate_password` | `MAGENTO_MIGRATE_DB_PASSWORD` | Cron, consumers and the install, migrate and reindex workloads, as `mg_migrate` (the chart passes it to them as `MAGENTO_DB_PASSWORD`)
| `crypt_key` | `MAGENTO_CRYPT_KEY` | `crypt/key` of `env.php`; the install Job's `--key`
| `opensearch_password` | `MAGENTO_OPENSEARCH_PASSWORD` | The `system` node of `env.php` (search settings)
| `valkey_cache_auth_token` | `MAGENTO_VALKEY_CACHE_AUTH_TOKEN` | The cache backend
| `valkey_session_auth_token` | `MAGENTO_VALKEY_SESSION_AUTH_TOKEN` | The session handler
| `amqp_password` | `MAGENTO_AMQP_PASSWORD` | The `queue` node of `env.php`; KEDA reads the management API with it
|===

The encryption key is handled differently from the rest, and nothing on this page shows a value for it:

* *An existing shop* takes the key from the `crypt/key` entry of its current `app/etc/env.php`, written to a file that only you can read, and gives that file to the seeding script (see
  xref:ecommerce/magento/cloud-migrating-from-a-single-server.adoc[Cloud: Migrating from a Single Server]).
* *A new shop* needs a key before the install Job can run, because the Job passes it with `--key`. The installer generates one when the option is missing: `CryptKeyGenerator` in `Magento\Setup\Model` returns
  the prefix `base64` followed by the base64 text of 32 random bytes (the length of a libsodium key), and `ConfigGenerator` uses it only when no key is given and none is configured. Generate the
  key once, outside the cluster, with that class or with the installer on a disposable installation, write it to a file readable only by you and give the file to the script. Do not generate it in a pod.
* *The format allows several keys.* `Magento\Framework\Encryption\Encryptor` splits the setting on whitespace, treats the last entry as the newest and decrypts older values with the earlier ones, which is how
  `bin/magento encryption:key:change` rotates the key. That command writes the new key to `env.php`, which is read-only here, so a rotation is a deliberate procedure: run the command in a throwaway pod with a writable
  copy of `app/etc` (the pattern of the install Job below), copy the resulting `crypt/key` value into the secret, then restart the workloads. The command re-encrypts the database
  and may take long on a large one; take a database snapshot first. This procedure was read from the source and not run.

The script below creates the two secrets. It refuses to overwrite an existing secret, takes the generated infrastructure passwords from the OpenTofu outputs, generates the two database passwords
(letters and digits only), reads the crypt key from the file and passes the payload on standard input, so that no secret appears in the process list or in a file.
It was checked with `shellcheck` and `bash -n`; it was not run, because that needs an AWS account and a state.

[source,bash]
----
#!/usr/bin/env bash
# Writes the application secret pocketcoffee/<env>/magento (the seven JSON keys the chart maps) and the
# first administrator's password pocketcoffee/<env>/magento-install. Run once per environment by a person
# with secretsmanager:PutSecretValue and read access to the OpenTofu state; nothing is printed or stored
# in a file. The crypt key is not generated here: it comes from a file you control.
set -euo pipefail

env="${1:?usage: seed-secrets.sh <staging|prod> <crypt-key-file>}"
crypt_key_file="${2:?usage: seed-secrets.sh <staging|prod> <crypt-key-file>}"
secret_id="pocketcoffee/${env}/magento"
install_id="pocketcoffee/${env}/magento-install"

# Letters and digits only: the OpenSearch and RabbitMQ passwords travel inside URLs.
gen() { openssl rand -base64 96 | tr -d '+/=\n' | cut -c1-"${1:-40}"; }

# Refuse to overwrite: a new crypt key makes every encrypted value in the database unreadable.
if aws secretsmanager get-secret-value --secret-id "$secret_id" \
  --query SecretString --output text >/dev/null 2>&1; then
  echo "${secret_id} already has a value; rotate it deliberately." >&2
  exit 1
fi
[ -s "$crypt_key_file" ] || { echo "empty or missing crypt key file" >&2; exit 1; }

tf() { tofu -chdir=infra output "$@"; }

payload="$(
  jq -n \
    --rawfile crypt "$crypt_key_file" \
    --arg db_app "$(gen 40)" --arg db_migrate "$(gen 40)" \
    --arg search "$(tf -raw opensearch_master_password)" \
    --arg vcache "$(tf -json valkey_auth_tokens | jq -r .cache)" \
    --arg vsession "$(tf -json valkey_auth_tokens | jq -r .session)" \
    --arg amqp "$(tf -raw amqp_password)" \
    '{db_app_password: $db_app, db_migrate_password: $db_migrate,
      crypt_key: ($crypt | rtrimstr("\n")),
      opensearch_password: $search,
      valkey_cache_auth_token: $vcache, valkey_session_auth_token: $vsession,
      amqp_password: $amqp}'
)"

# The value goes in on standard input, so it never appears in the process list.
printf '%s' "$payload" | aws secretsmanager put-secret-value \
  --secret-id "$secret_id" --secret-string file:///dev/stdin >/dev/null
jq -n --arg p "$(gen 24)" '{ADMIN_PASSWORD: $p}' | aws secretsmanager put-secret-value \
  --secret-id "$install_id" --secret-string file:///dev/stdin >/dev/null
echo "Seeded ${secret_id} and ${install_id}"
----

Source: https://docs.aws.amazon.com/cli/latest/reference/secretsmanager/put-secret-value.html[AWS CLI Reference: secretsmanager put-secret-value]

Run it as `./scripts/seed-secrets.sh prod ~/crypt-key.txt` from the repository root, then create the two database users with the passwords it generated (read them from the secret inside a
trusted shell; the SQL is on the database page) and delete the key file. The passwords therefore exist in Secrets Manager and in the database, and the crypt key in Secrets Manager and wherever
you keep your own record of it: keep that record, because the secret has a recovery window of 30 days after deletion and the database cannot be read without the key.

== env.php from the environment

`app/etc/env.php` is the deployment configuration that the installer writes once, for one server. In a cluster the file is rebuilt from the environment, so every pod builds the same
configuration from the same sources and no pod ever writes it. Magento also supports environment variables natively: any node of `env.php` can be given as `MAGENTO_DC_` followed by the path with
`+__+` between the keys, and `MAGENTO_DC__OVERRIDE` takes a JSON document that replaces whole sections (see Adobe's `env.php` reference); `env.php` has priority over the variables. This page does
not use that mechanism, because it needs one variable per leaf and the file below is easier to read, to lint and to compare with the installation page. The file is mounted read-only from a ConfigMap
at `app/etc/env.php` with `subPath`; `app/etc/config.php` stays in the image.

The file was checked with `php -l` and executed in a PHP 8.5.12 container with test values: it returned the expected nodes (the database connection with the CA option when
`MAGENTO_DB_SSL_CA` is set, the `tls://` server names, the Varnish hosts split into host and port, the OpenSearch host with its scheme, the S3 driver and the media URL), and a missing variable
stopped it with a line in the log. Points that matter:

* *The nodes are those the installer writes, with the Kubernetes changes.* `crypt`, `db`, `resource`, `backend`, `cache`, `cache_types`, `session`, `queue`, `lock`, `x-frame-options`, `MAGE_MODE`,
  `install` and `downloadable_domains` are the nodes of a normal installation; `directories/document_root_is_pub` makes `pub` the document root.
* *The GraphQL salt must be fixed.* `Magento\GraphQlCache\Model\CacheId\CacheIdCalculator` reads `cache/graphql/id_salt` and, when it is missing, generates a salt and saves it to `env.php`: on a read-only
  file that is a failure, and on a writable one every pod would invent its own. The value is a cache-key salt, not a credential, so it comes from the values (`shop.graphqlIdSalt`).
* *`cache_types` is a list of what is enabled, and a missing entry means disabled.* `Magento\Framework\App\Cache\State` reads the node and treats an unknown type as off, and `cache:enable` and the
  installer persist the node by writing `env.php`, which no pod can do. The list in the file is the usual set; produce yours with `bin/magento cache:status` on a finished installation and add the types
  of your modules (Pocket Coffee's `PocketCoffee_RoastAdmin` adds one), because a type missing here is a cache that is silently off.
* *The search settings live in the `system` node.* Values in that node win over the database and lock the field in the Admin. The OpenSearch host needs its scheme, because the client builds the URL from it
  and defaults to `http` when there is none (the file adds `https://`); the port is 443; the user and password make Magento embed `user:password@` in the URL.
* *Both Valkey groups use TLS through the `tls://` prefix.* The cache backend and the session handler use the Credis client, which takes the scheme from the host name (`tls://host`), so the setting needs
  no extra option. The cache uses the backend identifier `valkey` and the session handler is `redis` with a Valkey server, the combination that
  xref:ecommerce/magento/installation.adoc#valkey-config[the installation page] found to work on Mage-OS 3.6.0 (the `valkey` session option set was ignored by that installer); test the session handler of your
  edition by logging in and looking for `sess_` keys in the session group. `max_concurrency` of 12 is a little over 10 percent of the 24 PHP-FPM children of one pod, the rule of thumb Adobe gives for the session lock.
* *`http_cache_hosts` lists every Varnish pod by name.* Magento sends a `PURGE` request to each, and the names come from the headless Service of the StatefulSet (the chart builds the list). The
  full page cache application is Varnish (`caching_application` is 2).
* *Queues.* `default_connection` is `amqp`, `ssl` is on with certificate and host name verification (the AMQP factory of 2.4.9 reads `ssl` and `ssl_options` such as `cafile` and `verify_peer`), and
  `cron_consumers_runner/cron_run` is off, because the consumers are Deployments and not processes that cron spawns.
* *Media.* With `MAGENTO_S3_BUCKET` set, the `remote_storage` node selects the S3 driver with a bucket and a region and no credentials; without it, media stays on the file system (mode `efs`). The Admin setting
  `system/media_storage_configuration/media_database` is locked to 0 as Adobe's remote storage page requires. `MAGENTO_MEDIA_BASE_URL` points the media base URLs at the CloudFront host.
* *`install/date` is a fixed value.* Magento treats the application as installed when the node exists; nothing reads the date for behaviour, but nothing may rewrite the file either.
* *A missing variable stops the process* with a log line, so a pod without its secrets fails instead of serving a store that cannot decrypt anything.

=== Configuration, secrets and the writable paths

[source,nginx]
----
# nginx container of the pod; PHP-FPM listens on 127.0.0.1:9000 in the same pod.
upstream fastcgi_backend {
    server 127.0.0.1:9000;
}

set_real_ip_from {{ .Values.shop.trustedProxies }};
real_ip_header X-Forwarded-For;
real_ip_recursive on;

server {
    listen 8080 default_server;
    server_name _;
    server_tokens off;
    client_max_body_size 32M;

    set $MAGE_ROOT /var/www/html;
    set $MAGE_DEBUG_SHOW_ARGS 0;

    # Liveness: answered by nginx itself, no PHP, no database.
    location = /healthz { access_log off; default_type text/plain; return 200 "ok\n"; }
    # Readiness uses /health_check.php of Magento, which the included file already routes to PHP-FPM.

    # The web installer and updater are never reachable in a cluster; ^~ wins over the regexes of the sample.
    location ^~ /setup { return 404; }
    location ^~ /update { return 404; }

    include /var/www/html/nginx.conf.sample;
}
----

Source: https://experienceleague.adobe.com/en/docs/commerce-operations/installation-guide/prerequisites/web-server/nginx[Adobe Commerce docs: Configure Nginx]

The nginx file keeps Magento's own routing: it includes `nginx.conf.sample` from the image (the file of the 2.4.9 code base, which routes `index.php`, `get.php`, `static.php`, the error pages and
`health_check.php` to PHP-FPM and denies the sensitive paths) and adds what a pod needs. PHP-FPM is the upstream `fastcgi_backend` on `127.0.0.1:9000`, the trusted proxy range comes from the values (the file is
rendered with Helm's `tpl`) so that the client address is the one in `X-Forwarded-For`, `/healthz` is answered by nginx itself, and the web setup (`/setup`) and updater (`/update`) are answered with 404:
the prefix location with `^~` wins over the regular-expression locations of the sample, so the installer's browser interface is never reachable in a cluster. The rendered file and the real `nginx.conf.sample` of the 2.4.9 tag passed `nginx -t` in an
`nginx:1.29-alpine` container, and a started container answered 200 on `/healthz` and 404 on `/setup/index.php`, `/setup/` and `/update/index.php`. Two consequences: the `-nginx` image must contain the `pub/*.php` entry points
(`index.php`, `get.php`, `static.php`, `health_check.php`), because the PHP location of the sample starts with `try_files $uri =404` and answers 404 for a file that nginx cannot see, even though PHP-FPM has it; and the
`pub/media` mount of the nginx container is read-only, so nginx serves media that PHP wrote and Magento's `get.php` fallback does the rest.

`pocketcoffee-web` and, with `admin.enabled=true`, `pocketcoffee-admin` come from one template, so the Admin pods are the same image and configuration with their own replica count, resources and Service. What the template does and why:

* *Two containers, one pod.* nginx serves the static files baked into the `-nginx` image and passes `.php` to PHP-FPM on `127.0.0.1:9000`. The pods are spread over zones with a hard constraint and over nodes with a soft one,
  so losing a zone loses at most half of the capacity. `maxUnavailable: 0` makes a rollout add a pod before it removes one.
* *Probes: `health_check.php` for readiness, a static file for liveness.* Magento's `pub/health_check.php` (read in the 2.4.9 source) boots the application, opens a connection for every entry of `db/connection` and
  creates and tests every cache frontend of `env.php`, answering 500 on any failure. That is exactly the readiness question ("can this pod serve a page?"), and the startup probe gives a cold pod three minutes. It is also
  the reason it is *not* the liveness probe: a database failover would make every pod fail liveness together and restart the whole tier at the moment a retry would have worked, so liveness is nginx's own `/healthz` and a TCP check of
  PHP-FPM. The cost of this readiness probe is that a failover of the database or of the cache group makes all pods unready for its duration (the load balancer then has no target, and the error page is the load balancer's);
  if that is the wrong trade for you, point readiness at `/healthz` and alarm on the 5xx rate instead. Each probe boots Magento, so the period is ten seconds.
* *Writable paths.* The root file system is read-only. `/tmp`, `var` and `pub/media` (mode `s3`) are per-pod `emptyDir` volumes; `generated/` (the compiled dependency injection) and `pub/static` (the deployed static
  content) are baked into the image and never written in production mode, and `app/etc` is not writable at all: `env.php` is a read-only file mount and `config.php` is in the image. A module that writes elsewhere fails
  with "read-only file system" at the first write, which is how you find it before production does. `fsGroup: 33` makes the `emptyDir` volumes writable for `www-data`.
* *`preStop` sleep and `terminationGracePeriodSeconds`.* Ten seconds of sleep let the load balancer deregister the pod before nginx stops, and the grace period covers it plus the longest request.
* *No warm-up init container.* The configuration and the caches are not per pod: the cache is in Valkey, and the compiled code is in the image. The first request on a cold pod pays for the opcache and the
  Valkey connection, which the startup probe absorbs.
* *The configuration checksum.* A changed ConfigMap changes the pod template, so the pods roll.

and the container below was run read-only, without capabilities, as UID 1000 with a writable and executable `/var/lib/varnish` (a `noexec` volume is refused by `varnishd`) before the manifest was written. Customer

queue through the broker's management API (`protocol: http`), `messagesPerReplica` messages per replica, between `minReplicas` and `maxReplicas`; a minimum of 0 is allowed for a queue that is usually empty (the image resize consumer). KEDA

One CronJob `pocketcoffee-cron` runs every minute with `concurrencyPolicy: Forbid`, so there is exactly one scheduler however many web pods run; the web pods never run cron. The command is `bin/magento cron:run --group=<group> --bootstrap=standaloneProcessStarted=1` once per entry of `cron.groups`
(`default` and `index` by default), one after the other, in the foreground. The flag matters. In 2.4.9 `ProcessCronQueueObserver` starts every group whose `use_separate_process` is 1 (the `index` and `consumers` groups; `default` is 0) as a child
process through a shell whose command renderer (`Magento\Cron\Shell\CommandRendererBackground`) appends `>> var/log/magento.cron.<group>.log 2>&1 &`, and then returns. In a container that ends the pod while the group still runs, and the log goes to a file in an `emptyDir`
that disappears with it. The child is started with exactly this `--bootstrap` flag, which makes the process run the group itself; the CronJob uses the flag directly, so the work finishes before the pod does and its output is in `kubectl logs`. The group `consumers` is left out on purpose, and its job
`consumers_runner` is disabled in `env.php`. Setting `cron.groups` to an empty list runs one plain `cron:run`, which is only right for a store whose groups are all inline; which groups a shop needs, the lock behaviour and the schedule table are on
xref:ecommerce/magento/cloud-cron-consumers-and-indexers.adoc[Cloud: Cron, Queue Consumers and Indexers].

The migrate Job is a `pre-upgrade` hook: it runs with the new image before the new pods roll out, as `mg_migrate`. It asks `bin/magento setup:db:status` first, and `setup:db:status` ends with 0 when schema and data are current, with 2 when
an upgrade is required and with 1 on a failure (`EXIT_CODE_UPGRADE_REQUIRED` in `DbStatusCommand`); only on 2 does it run `bin/magento setup:upgrade --keep-generated`, so an unchanged release costs a few seconds and a database that cannot be read
fails the release. `--keep-generated` keeps the compiled code that the image carries (without it `setup:upgrade` deletes `generated/code`). The upgrade wants a writable `app/etc` and `var`: its pre-flight check
(`getMissingWritableDirectoriesForDbUpgrade` in the framework's `FilePermissions`) fails when `app/etc` is not writable, so the Job copies the image's `app/etc` into an `emptyDir` with an init container, mounts it at `app/etc` and mounts the
read-only `env.php` over it. `setup:upgrade` then reads `env.php` and writes nothing to it (the cleanup of old init statements writes only when it changes something) and may rewrite the throwaway `config.php`, which is discarded.
A failing Job fails the upgrade and leaves the old pods running. A caveat of Helm hooks: a `pre-upgrade` hook runs before the other objects of the release are applied, so a change to a ConfigMap or to the Secret made in the same release is not yet
seen by the Job. The sequence around it (maintenance mode, the compatibility of old pods with the new schema, rollback) is on
xref:ecommerce/magento/cloud-releases-and-zero-downtime-deployments.adoc[Cloud: Releases and Zero-Downtime Deployments], and the declarative schema it applies on
xref:ecommerce/magento/declarative-schema-and-patches.adoc[Declarative Schema and Data and Schema Patches].

The install Job runs `bin/magento setup:install` once, in an empty database. It deliberately differs from the web pods:

* *It writes `app/etc/env.php` into a throwaway directory.* The installer's pre-flight check requires `app/etc`, `var` and `pub/media` to be writable (and `generated` and `pub/static` only outside production mode, which the
  image's mode makes unnecessary). The init container copies the image's `app/etc`, with its `config.php`, into an `emptyDir`; the installer writes its own `env.php` there with its own defaults (file cache and file sessions, which is
  why the Job needs neither Valkey nor the broker), and the directory disappears with the pod. That is intended: the `env.php` that counts is the one built from the environment.
* *It uses the key from the secret.* `--key` takes the value of `MAGENTO_CRYPT_KEY`; the installer writes it to its throwaway file and everything it encrypts during the install uses it, which is what makes the shop readable by the pods that start
  afterwards. The key appears in the command line of the Job's process, which anyone with exec access to the pod can read; treat the namespace accordingly.
* *It refuses to run over an existing shop.* A PDO query checks for the table `core_config_data` before anything else and ends with exit code 3 if it exists. The installer's `--cleanup-database` option is deliberately not used, because it drops tables.
* *It creates the shop's first administrator from the install secret.* The password is a Secrets Manager value, passed in a variable and then on the command line, where it shows in the process list of the Job pod: treat it as a first-login password, change it
  from the Admin and delete the secret. The Admin path is set explicitly with `--backend-frontname` to the value the WAF rule and the route use, instead of the random one the installer would choose.
* *It reaches OpenSearch and creates the first index.* The installer validates the search connection, stores the settings, and reindexes at the end; on an empty catalogue that is short. The settings it stores in the database are overridden by the locked `system` node
  of `env.php` afterwards.
* *It is not a hook.* A `post-install` hook would run after the pods are ready, and they would serve a half-installed shop. So the chart deploys the Job as an ordinary object and, while `install.enabled` is true, scales the web, the Admin and the consumer
  Deployments and the Varnish StatefulSet to zero and suspends the cron. The deployment script runs the chart twice: the Job first, the pods second.
* *`--base-url` and the language options are deprecated in 2.4.9.* The installer's help marks them so; they still work, and the locked `system` node of `env.php` supersedes the stored base URL.

Source: https://experienceleague.adobe.com/en/docs/commerce-operations/configuration-guide/cli/manage-indexers[Adobe Commerce docs: Manage the indexers]

`pocketcoffee-reindex` (with `-<run>` appended when `reindex.run` is set, so that a second run does not collide with a finished Job) is rendered only with `reindex.enabled=true` and runs `bin/magento indexer:reindex` (all indexers, or the ones in `reindex.indexers`) as `mg_migrate`, because a full reindex creates and swaps index tables. It is for a
one-off full reindex after an import or a migration; the steady-state indexing is "Update by Schedule" through cron, described on the cron page, not a Job.

== First install, or an existing database

There are two ways to create the database content, and the chart supports both with the same values:

[cols="1,2,2",options=header]
|===
| | First install with the Job | Import of an existing shop
| When | A new shop, or a staging environment created from scratch | A shop that runs on a single server today
| Database | Empty database `pocketcoffee`, users `mg_app` and `mg_migrate` created | A dump imported into RDS, the same users created
| Secrets | The key generated once outside the cluster, the rest by the seeding script | The old `crypt/key` copied into the secret; the other values generated
| Files | Written to the bucket by the shop afterwards | The old `pub/media` uploaded with `remote-storage:sync`, or copied to the volume
| `install.enabled` | `true` for the first release only | Never
| Base URLs | From `env.php`, locked | From `env.php`, locked; remove the old values from `core_config_data` if they conflict
|===

An import is a different procedure with its own risks (the old key must be kept or encrypted values are lost); it is on
xref:ecommerce/magento/cloud-migrating-from-a-single-server.adoc[Cloud: Migrating from a Single Server]. The deployment script below is the first install; for an import, skip the first `helm upgrade` and run the second.

[source,bash]
----
#!/usr/bin/env bash
# First deployment of the chart to pocketcoffee-prod: install Job first, then the web pods.
set -euo pipefail

sha="${1:?usage: deploy.sh <git-sha>}"
region="eu-west-1"
tf() { tofu -chdir=infra output -raw "$1"; }

aws eks update-kubeconfig --name pocketcoffee-prod --region "$region"

common=(
  --namespace pocketcoffee
  --set image.tag="$sha"
  --set database.host="$(tf db_endpoint)"
  --set opensearch.host="$(tf opensearch_endpoint)"
  --set valkey.cacheHost="$(tf valkey_cache_endpoint)"
  --set valkey.sessionHost="$(tf valkey_session_endpoint)"
  --set amqp.host="$(tf amqp_host)"
  --set media.bucket="$(tf media_bucket)"
)

# 1. Install: the web pods and consumers stay at zero replicas while the install Job creates the shop.
helm upgrade --install pocketcoffee ./pocketcoffee-magento "${common[@]}" \
  --set install.enabled=true --set migrate.enabled=false \
  --wait --wait-for-jobs --timeout 40m

# 2. Serve: the Job is removed, the pods start against the finished database.
helm upgrade pocketcoffee ./pocketcoffee-magento "${common[@]}" \
  --set migrate.enabled=false --wait --timeout 15m

kubectl -n pocketcoffee get pods,hpa,pdb,cronjob,scaledobject
----

Source: https://helm.sh/docs/helm/helm_upgrade/[Helm Docs: helm upgrade]

The script passed `shellcheck` and `bash -n`. `--wait-for-jobs` makes Helm wait until the install Job completes (the timeout covers the schema creation, the indexing and a slow OpenSearch domain); the second command removes the Job, creates the
HPA, scales the Deployments up and starts the pods. `migrate.enabled=false` is set on both runs because the installer already created the current schema and modules; later releases run with the default (migrate on). Run `tofu -chdir=infra output`
first, as the script does, so the chart receives the endpoints. After the first release, delete the install secret from Secrets Manager.

kubectl -n pocketcoffee get pods -o wide

kubectl -n pocketcoffee exec deploy/pocketcoffee-web -c php-fpm -- bin/magento config:show web/secure/base_url
kubectl -n pocketcoffee exec deploy/pocketcoffee-web -c php-fpm -- bin/magento cache:status

----

Source: https://kubernetes.io/docs/reference/kubectl/quick-reference/[Kubernetes Documentation: kubectl quick reference]

Check that every web pod shows `2/2` containers ready and that they run in more than one zone; that the shop answers with the `www` host and its links are HTTPS; that the Admin answers 403 from an address outside `admin_cidrs` and its login page from inside;
that `config:show` returns the locked base URL; that `cache:status` shows every type enabled (a missing type is the sign of a short `cache_types` list); and that a second request to a product page carries the Varnish headers of the page cache page. The state of a consumer
appears in the logs of its pods and in the queue length of the broker's console.

== Common problems

* *`required: set image.tag to the git SHA`, `set database.host` and similar.* The chart refuses to render without them: pass the values from the script.
* *Every pod fails with `Configuration error` and a line `missing environment variable` in the log.* The ExternalSecret has not produced the Secret (check `kubectl describe externalsecret` and the Pod Identity association of the operator) or a key is
  missing from the secret JSON.
* *Pods are unready and `health_check.php` answers 500.* The check failed on the database or on a cache frontend of `env.php`: read the log of the PHP container (`MySQL connection failed` and `Cache storage is not accessible` are the two messages the script logs),
  and check the security groups and the AUTH tokens.
* *Every request is a redirect loop or links point at `http`.* The load balancer does not send `X-Forwarded-Proto` or the `offloader_header` setting is missing from the `system` node; the value is `X-Forwarded-Proto`.
* *The Admin shows the store configuration fields greyed out.* That is the locked `system` node working as intended; to change a value, change the chart.
* *"Cache storage is not accessible" on the session group only.* The AUTH token of the session group was put into the cache setting or the other way round: the two secret keys are different.
* *Search returns nothing after the first release.* The installer indexed an empty catalogue; run the reindex Job after importing products, and check that `opensearch_server_hostname` carries `https://`.
* *The migrate Job fails with "Path app/etc is not writable".* The init container did not run or the `etc-work` volume is missing from a customised copy of the template.
* *`setup:upgrade` rewrote `config.php` in the image.* It did not, it rewrote the throwaway copy; if the module list differs from the baked file, rebuild the image with `app:config:dump` and commit the file.
* *A consumer does not start or its queue only grows.* Look at the Deployment's log first; then at the broker user's rights, at `consumers_wait_for_messages` and at the ScaledObject (`kubectl describe scaledobject`).
* *The install Job fails at the first write.* `app/etc`, `var` or `pub/media` is not writable by UID 33: the pod's `fsGroup` and the `emptyDir` volumes decide.
* *Pods cannot mount EFS.* Check the mount target security group, that a mount target exists in the pod's zone and that the PV names the file system and the access point of the outputs.
