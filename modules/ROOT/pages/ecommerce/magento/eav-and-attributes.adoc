This page was written against Magento Open Source and Adobe Commerce 2.4.9 (general availability 2026-05-12) and checked on
2026-10-27. Every example was run on Mage-OS 3.6.0, the Open Source distribution based on Magento 2.4.9, so the table

ship PHP. Adobe Commerce as a Cloud Service (ACCS) has a locked core and an out-of-process extensibility model, so a PHP
data patch such as the ones below cannot be deployed there; attributes on that edition are created in the Admin or
through the APIs, and the logic around them runs in App Builder (see
xref:ecommerce/magento/out-of-process-extensibility.adoc[Out-of-Process Extensibility]).

Entity-Attribute-Value (EAV) is the storage model behind most of the catalog and customer data of Magento: products,
categories, customers and customer addresses keep their descriptive fields as attribute definitions plus values in typed
tables, instead of one fixed column per field. It is the reason why a merchant can add a "Roast date" field in the Admin
without a schema change, and also the reason why reading a product is more expensive than reading a row. This page
explains the model, builds the attributes that the Pocket Coffee shop needs (an origin drop-down, a roast level, a roast
date, a favourite-grind customer attribute and a category "roast story") with data patches, reads them back through
repositories, REST and GraphQL, and explains how extension attributes differ from custom attributes. It sits after
xref:ecommerce/magento/declarative-schema-and-patches.adoc[Declarative Schema and Patches], whose data-patch mechanism it
uses, and before xref:ecommerce/magento/routing-controllers-blocks-layouts-and-templates.adoc[Routing, Controllers,
Blocks, Layouts and Templates], where the same attributes are displayed on the storefront.

== The model in one picture

image::ecommerce-magento-eav-tables.svg["How one attribute value is stored, from the entity row through eav_attribute to the typed value table",width=900]

An EAV entity is stored in three layers:

. *The entity table* holds the identity and the fixed columns, for example `catalog_product_entity` with `entity_id`,
  `attribute_set_id`, `type_id`, `sku`, `created_at` and `updated_at`.
. *The attribute metadata* describes every field: its code, its type, its input widget, its models and, for catalog
  entities, its storefront behaviour. It lives in `eav_attribute` plus one extension table per domain
  (`catalog_eav_attribute`, `customer_eav_attribute`).
. *The value tables* hold one row per entity, attribute and store view, in a table chosen by the attribute's backend
  type: `catalog_product_entity_int`, `_varchar`, `_text`, `_decimal`, `_datetime` (and `_gallery` for the legacy
  gallery). Categories use the same suffixes in `+catalog_category_entity_*+` and customers in `+customer_entity_*+`.

The value tables are keyed by `entity_id`, `attribute_id` and `store_id`; the unique key
`CATALOG_PRODUCT_ENTITY_INT_ENTITY_ID_ATTRIBUTE_ID_STORE_ID` on `(entity_id, attribute_id, store_id)` is what makes one
store view able to override the value of the default scope. In Magento Open Source the entity key column is
`entity_id`, as shown in the `SHOW CREATE TABLE catalog_product_entity_int` output of the test installation. Adobe
Commerce adds content staging, which uses a `row_id` key and sequence tables; that part of the model is Adobe
Commerce only and was not run for this page, so code that must work on both editions should go through the repositories
and the `EntityManager` rather than SQL.

Source: https://developer.adobe.com/commerce/php/development/components/attributes[Adobe Commerce developer docs: EAV and extension attributes]

== The metadata tables

The metadata is plain data that you can read with SQL, which is the quickest way to understand an attribute that
behaves strangely. These are the tables you will meet most often.

[cols="2,5",options="header"]
|===
| Table | What it holds

| `eav_entity_type`
| One row per EAV entity: `entity_type_code`, the resource `entity_model`, the `attribute_model` class, the main
  `entity_table`, the `increment_model` and the `default_attribute_set_id`.

| `eav_attribute`
| One row per attribute and entity type: `attribute_code`, `backend_type` (`static`, `int`, `varchar`, `text`,
  `decimal`, `datetime`), `frontend_input` (`text`, `select`, `date` and so on), `frontend_label`, `is_required`,
  `is_user_defined`, `is_unique`, `default_value`, `note`, and the class names `backend_model`, `frontend_model`,
  `source_model` and `backend_table`.

| `catalog_eav_attribute`
| Catalog-only extension of `eav_attribute`: `is_global` (scope), `is_searchable`, `is_filterable`,
  `is_filterable_in_search`, `is_comparable`, `is_visible_on_front`, `is_html_allowed_on_front`,
  `used_in_product_listing`, `used_for_sort_by`, `is_used_for_promo_rules`, `apply_to` (product types),
  `is_visible_in_advanced_search`, `is_wysiwyg_enabled`, `is_used_in_grid`, `is_visible_in_grid`,
  `is_filterable_in_grid` and `search_weight`.

| `customer_eav_attribute`
| Customer-domain extension: `is_visible`, `input_filter`, `multiline_count`, `validate_rules`, `is_system`,
  `sort_order`, `data_model` and the grid flags.

| `customer_form_attribute`
| Which forms render a customer attribute (`form_code` such as `adminhtml_customer`, `customer_account_create`,
  `customer_account_edit`).

| `eav_attribute_set`
| The attribute sets of an entity type. The `Default` product set has id 4 in the test installation.

| `eav_attribute_group`
| The groups (tabs or sections of the product form) inside an attribute set, with a stable `attribute_group_code` such
  as `product-details`.

| `eav_entity_attribute`
| The assignment of an attribute to a set and a group, with a `sort_order`. An attribute that is in no set is invisible
  in the Admin form.

| `eav_attribute_option`, `eav_attribute_option_value`
| The options of a drop-down or multiple-select attribute, and their labels per store.

| `eav_attribute_label`
| The storefront label of an attribute per store view.
|===

The entity types of the test installation, read from `eav_entity_type`, show which parts of the system are EAV:

[cols="1,2,2,1",options="header"]
|===
| id | `entity_type_code` | Main table | Default attribute set

| 1 | `customer` | `customer_entity` | 1
| 2 | `customer_address` | `customer_address_entity` | 2
| 3 | `catalog_category` | `catalog_category_entity` | 3
| 4 | `catalog_product` | `catalog_product_entity` | 4
| 5-8 | `order`, `invoice`, `creditmemo`, `shipment` | `sales_order`, `sales_invoice`, ... | 5-8

== Scope: global, website and store view

For catalog attributes, `catalog_eav_attribute.is_global` decides how many values an entity can have:

[cols="1,2,3",options="header"]
|===
| `is_global` | Constant (`ScopedAttributeInterface`) | Behaviour

| 1 | `SCOPE_GLOBAL` | One value for the whole installation, always stored with `store_id = 0`.
| 2 | `SCOPE_WEBSITE` | One value per website, stored for every store view of that website.
| 0 | `SCOPE_STORE` | One value per store view, falling back to the default value in `store_id = 0`.
|===

The numbers are not in the intuitive order and were confirmed on the test installation: the origin attribute (global)
has `is_global = 1`, the roast level (website) has 2 and the roast date (store view) has 0. Pick the narrowest scope
that matches the business rule, because every wider scope adds rows and a per-store fallback join. Origin does not
change per language, so it is global; a roast date can differ per website if each website sources its own batches, so a
real shop might choose website scope.

The Adobe documentation states that the scope of a customer custom attribute is global only, while the other entities
support the global, website and store-view scopes.

== The Pocket Coffee product attributes

The patch below creates three product attributes. A data patch runs once, records its class name in the `patch_list`
table, and is applied by `bin/magento setup:upgrade`. It implements `DataPatchInterface` for the forward step and
`PatchRevertableInterface` so that `module:uninstall` with data removal can undo it. The patch receives the
`EavSetupFactory`, not the `EavSetup` itself: injecting `EavSetup` directly is a documented cause of failing
`setup:upgrade` runs, because the object needs the module data setup passed to the factory.

[source,php]
----
<?php

declare(strict_types=1);

namespace PocketCoffee\Eav\Setup\Patch\Data;

use Magento\Catalog\Model\Product;
use Magento\Eav\Model\Entity\Attribute\ScopedAttributeInterface;
use Magento\Eav\Setup\EavSetup;
use Magento\Eav\Setup\EavSetupFactory;
use Magento\Framework\Setup\ModuleDataSetupInterface;
use Magento\Framework\Setup\Patch\DataPatchInterface;
use Magento\Framework\Setup\Patch\PatchRevertableInterface;

/**
 * Adds the origin, roast level and roast date product attributes of Pocket Coffee.
 */
class AddProductAttributes implements DataPatchInterface, PatchRevertableInterface
{
    public const ORIGIN = 'pc_origin';
    public const ROAST_LEVEL = 'pc_roast_level';
    public const ROAST_DATE = 'pc_roast_date';

    public function __construct(
        private readonly ModuleDataSetupInterface $moduleDataSetup,
        private readonly EavSetupFactory $eavSetupFactory
    ) {
    }

    public function apply(): self
    {
        $this->moduleDataSetup->getConnection()->startSetup();
        /** @var EavSetup $eavSetup */
        $eavSetup = $this->eavSetupFactory->create(['setup' => $this->moduleDataSetup]);

        // Drop-down with admin-managed options: stored as an int in catalog_product_entity_int.
        $eavSetup->addAttribute(Product::ENTITY, self::ORIGIN, [
            'type' => 'int',
            'label' => 'Origin',
            'input' => 'select',
            'source' => \Magento\Eav\Model\Entity\Attribute\Source\Table::class,
            'required' => false,
            'global' => ScopedAttributeInterface::SCOPE_GLOBAL,
            'user_defined' => true,
            'visible' => true,
            'visible_on_front' => true,
            'used_in_product_listing' => true,
            'searchable' => true,
            'filterable' => 1,
            'filterable_in_search' => true,
            'comparable' => true,
            'is_used_in_grid' => true,
            'is_visible_in_grid' => true,
            'is_filterable_in_grid' => true,
            'group' => 'General',
            'sort_order' => 60,
            'option' => ['values' => ['Ethiopia Yirgacheffe', 'Colombia Huila', 'Brazil Cerrado']],
        ]);

        // A second drop-down; per-website scope, not used in layered navigation.
        $eavSetup->addAttribute(Product::ENTITY, self::ROAST_LEVEL, [
            'type' => 'int',
            'label' => 'Roast level',
            'input' => 'select',
            'source' => \Magento\Eav\Model\Entity\Attribute\Source\Table::class,
            'required' => false,
            'global' => ScopedAttributeInterface::SCOPE_WEBSITE,
            'user_defined' => true,
            'visible' => true,
            'visible_on_front' => true,
            'group' => 'General',
            'sort_order' => 70,
            'option' => ['values' => ['Light', 'Medium', 'Dark']],
        ]);

        // A date: stored as a datetime in catalog_product_entity_datetime, editable per store view.
        $eavSetup->addAttribute(Product::ENTITY, self::ROAST_DATE, [
            'type' => 'datetime',
            'label' => 'Roast date',
            'input' => 'date',
            'backend' => \Magento\Eav\Model\Entity\Attribute\Backend\Datetime::class,
            'required' => false,
            'global' => ScopedAttributeInterface::SCOPE_STORE,
            'user_defined' => true,
            'visible' => true,
            'visible_on_front' => true,
            'used_in_product_listing' => true,
            'group' => 'General',
            'sort_order' => 80,
        ]);

        $this->moduleDataSetup->getConnection()->endSetup();

        return $this;
    }

    public function revert(): void
    {
        $this->moduleDataSetup->getConnection()->startSetup();
        /** @var EavSetup $eavSetup */
        $eavSetup = $this->eavSetupFactory->create(['setup' => $this->moduleDataSetup]);
        foreach ([self::ORIGIN, self::ROAST_LEVEL, self::ROAST_DATE] as $code) {
            $eavSetup->removeAttribute(Product::ENTITY, $code);
        }
        $this->moduleDataSetup->getConnection()->endSetup();
    }

    public static function getDependencies(): array
    {
        return [];
    }

    public function getAliases(): array
    {
        return [];
    }
}
----

=== Every key of addAttribute

`+EavSetup::addAttribute($entityType, $code, $options)+` accepts the keys below. The first column group is stored in
`eav_attribute`, the second in `catalog_eav_attribute` (only for catalog entities such as products and categories).
Defaults are those of the Adobe reference; an omitted key falls back to them, which is why an attribute created with
only `type` and `label` is a required, system, global varchar text field.

[cols="2,4,1",options="header"]
|===
| Key | Meaning | Default

| `type` | `backend_type`: `static`, `int`, `varchar`, `text`, `decimal` or `datetime`. Chooses the value table. | `varchar`
| `label` | `frontend_label`, the admin label. | none
| `input` | `frontend_input`, the widget: `text`, `textarea`, `date`, `boolean`, `select`, `multiselect`, `price`, `media_image`, `weee`, `swatch_visual`, `swatch_text`. | `text`
| `required` | `is_required`; the form refuses to save without a value. | 1
| `user_defined` | Marks the attribute as created by a merchant or extension. Required for it to be editable and deletable in the Admin. | 0
| `default` | `default_value`. | none
| `unique` | `is_unique`; checked on save. | 0
| `note` | A hint shown under the field. | none
| `backend` | `backend_model`: validates and transforms the value on save and load (for example the `Datetime` backend normalises dates). | none
| `frontend` | `frontend_model`: formats the value for the storefront. | none
| `source` | `source_model`: supplies the option list. `Magento\Eav\Model\Entity\Attribute\Source\Table` reads `eav_attribute_option`; `Boolean` gives Yes and No; your own class extends `AbstractSource`. | none
| `table` | `backend_table`: a custom value table instead of the default one. | none
| `option` | Initial options, for example `+['values' => ['A', 'B']]+`. Only with `Table`. | none
| `system` | Declares a system attribute that the Admin cannot delete. | 1
| `global` | `is_global`: scope (see above). | 1
| `group` | Attribute group name or id inside the set. | none
| `attribute_set` | Name of the attribute set to assign to. Combines with `group`. | all sets, when `user_defined` is false
| `sort_order` | Position in the group (`eav_entity_attribute.sort_order`). | none
| `visible` | `is_visible`. | 1
| `visible_on_front` | `is_visible_on_front`: shown in the "More Information" tab of the product page. | 0
| `searchable`, `filterable`, `filterable_in_search`, `comparable` | Search and layered navigation flags. `filterable` is 1 for "Filterable (with results)" and 2 for "Filterable (no results)". | 0
| `used_in_product_listing` | Loaded with the products of category listings and search results; leave it at 0 for attributes that a list card does not show. | 0
| `used_for_sort_by` | Offered as a sort option. | 0
| `is_html_allowed_on_front` | Whether the value is output without escaping on the storefront. | 0
| `is_used_in_grid`, `is_visible_in_grid`, `is_filterable_in_grid` | Availability as a column and filter of the Admin product grid. | 0
| `apply_to` | Product types that can have the attribute. | all types
| `position`, `input_renderer`, `attribute_model` | Layered navigation position, renderer class and the attribute model class. | none
|===

Only the keys of the examples were exercised; the others follow the Adobe reference.

=== Source, backend and frontend models

The three model classes are the extension points of an attribute and are stored as class names in `eav_attribute`.

* A *source model* turns an attribute into a list of options. `Source\Table` is the default for admin-managed
  drop-downs: the options live in `eav_attribute_option` and `eav_attribute_option_value`, so the merchant can edit them
  in the Admin (Stores > Attributes > Product). A custom source model is the right choice when the list comes from code
  or from another system, as the customer grind attribute below shows.
* A *backend model* runs when the value is saved or loaded: it can validate, convert (an array to a comma-separated
  string, a date to the database format) or reject the value. The `Datetime` backend normalises the roast date.
  Multiple-select attributes use an array backend that stores the selected ids as a comma-separated string.
* A *frontend model* renders the value for the storefront. Most attributes need none.

Option ids are surrogate keys. The options of `pc_origin` were stored as `option_id` 4, 5 and 6 (ids 1 to 3 belong to
the options of the core `gender` attribute), which is why code must look an option up by its label through the attribute metadata and never
hard-code the id, as the command below does.

Source: https://developer.adobe.com/commerce/php/development/components/add-attributes[Adobe Commerce developer docs: Add attributes]

=== Attribute sets and groups

An attribute only appears on a product if it is assigned to the product's attribute set and to a group of it. The
`group` key above placed the three attributes in the group named `General` of the `Default` set, which has the code
`product-details` and id 7 on the test installation. The assignment is the row in `eav_entity_attribute`:

[source,text]
----
entity_attribute_id  entity_type_id  attribute_set_id  attribute_group_id  attribute_id  sort_order
146                  4               4                 7                   147           60
147                  4               4                 7                   148           70
148                  4               4                 7                   149           80
----

Products of other sets (for example a "Coffee Beans" set created by a merchant) do not show the attributes unless the set
is edited. In code, `EavSetup` offers `addAttributeGroup()`, `addAttributeToSet()` and `addAttributeToGroup()`; over
REST the same is done with three calls, all of which were run against the test installation with an admin token:

[source,bash]
----
# 1. Create the set as a copy of the Default set (skeletonId 4); the response carries the new id (9 here)
curl -s -X POST localhost:8082/rest/V1/products/attribute-sets \
  -H "Authorization: Bearer <admin-token>" -H "Content-Type: application/json" \
  -d '{"attributeSet":{"attribute_set_name":"Coffee Beans","sort_order":10,"entity_type_id":4},"skeletonId":4}'

# 2. Add a group to the set; the response carries the group id (32 here)
curl -s -X POST localhost:8082/rest/V1/products/attribute-sets/groups \
  -H "Authorization: Bearer <admin-token>" -H "Content-Type: application/json" \
  -d '{"group":{"attribute_group_name":"Roast","attribute_set_id":9}}'

# 3. Assign an existing attribute to the set and group; the response is the entity-attribute id
curl -s -X POST localhost:8082/rest/V1/products/attribute-sets/attributes \
  -H "Authorization: Bearer <admin-token>" -H "Content-Type: application/json" \
  -d '{"attributeSetId":9,"attributeGroupId":32,"attributeCode":"pc_decaf","sortOrder":10}'
----

An attribute group id of 0 is rejected with "The group with the ID doesn't exist", which is the usual first mistake
when the group has not been created. The attribute used in step 3 had been created beforehand with
`POST /rest/V1/products/attributes` (a boolean `pc_decaf`); the set and the attribute were deleted afterwards with
`DELETE /rest/V1/products/attribute-sets/9` and `DELETE /rest/V1/products/attributes/pc_decaf`.

Source: https://developer.adobe.com/commerce/webapi/rest/[Adobe Commerce developer docs: REST API]

=== Attribute code rules

The attribute code must be unique per entity type, start with a letter, use only letters, digits and underscores,
and be at most 60 characters in the 2.4.9-based sources (`+Attribute::ATTRIBUTE_CODE_MAX_LENGTH+`); the validator message says "letters (a-z or A-Z), numbers (0-9) or underscore (_), and the first character should be a letter", and the prefix `container_` is reserved by the system. Reserved codes are
rejected by `ReservedAttributeList`. Prefix custom codes with a vendor token (`pc_` here) so that they cannot collide with
a future core attribute or another extension, and because the code becomes a property name in the REST payload, the
GraphQL filter input and the layered navigation URL parameter.

== Reading and writing values with the data interfaces

Values are accessed through the data interfaces and repositories, never by SQL. The command below is a complete,
runnable example: it resolves the option id of the origin label from the attribute metadata, creates (or updates) the
product `PC-ETH-WHL-250`, reads the values back, searches by the attribute and prints the SQL that a collection would
run. It is registered as a console command in `etc/di.xml`.

[source,xml]
----
<?xml version="1.0"?>
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xsi:noNamespaceSchemaLocation="urn:magento:framework:ObjectManager/etc/config.xsd">
    <type name="Magento\Framework\Console\CommandListInterface">
        <arguments>
            <argument name="commands" xsi:type="array">
                <item name="pocketcoffee_eav_demo" xsi:type="object">PocketCoffee\Eav\Console\Command\DemoCommand</item>
            </argument>
        </arguments>
    </type>
    <type name="Magento\Catalog\Api\ProductRepositoryInterface">
        <plugin name="pocketcoffee_eav_days_since_roast" type="PocketCoffee\Eav\Plugin\AddDaysSinceRoast"/>
    </type>
</config>
----

Source: https://developer.adobe.com/commerce/php/development/components/attributes[Adobe Commerce developer docs: EAV and extension attributes]

[source,php]
----
<?php

declare(strict_types=1);

namespace PocketCoffee\Eav\Console\Command;

use Magento\Catalog\Api\Data\ProductInterfaceFactory;
use Magento\Catalog\Api\ProductAttributeRepositoryInterface;
use Magento\Catalog\Api\ProductRepositoryInterface;
use Magento\Catalog\Model\ResourceModel\Product\CollectionFactory;
use Magento\Framework\Api\SearchCriteriaBuilder;
use Magento\Framework\App\Area;
use Magento\Framework\App\State;
use Magento\Framework\Exception\LocalizedException;
use Magento\Framework\Exception\NoSuchEntityException;
use PocketCoffee\Eav\Setup\Patch\Data\AddProductAttributes;
use Symfony\Component\Console\Command\Command;
use Symfony\Component\Console\Input\InputInterface;
use Symfony\Component\Console\Output\OutputInterface;

class DemoCommand extends Command
{
    public function __construct(
        private readonly State $appState,
        private readonly ProductAttributeRepositoryInterface $attributeRepository,
        private readonly ProductRepositoryInterface $productRepository,
        private readonly ProductInterfaceFactory $productFactory,
        private readonly SearchCriteriaBuilder $searchCriteriaBuilder,
        private readonly CollectionFactory $collectionFactory,
        ?string $name = null
    ) {
        parent::__construct($name);
    }

    protected function configure(): void
    {
        $this->setName('pocketcoffee:eav:demo')
            ->setDescription('Save a product with custom attributes and search by them');
    }

    protected function execute(InputInterface $input, OutputInterface $output): int
    {
        try {
            $this->appState->setAreaCode(Area::AREA_ADMINHTML);
        } catch (LocalizedException) {
            // The area code is already set when the command runs inside a web request or a test.
        }

        // 1. Resolve the option id of the label "Ethiopia Yirgacheffe" from the attribute metadata.
        $origin = $this->attributeRepository->get(AddProductAttributes::ORIGIN);
        $originId = null;
        foreach ($origin->getOptions() as $option) {
            $output->writeln(sprintf('option %s => %s', $option->getValue() ?: '(empty)', $option->getLabel()));
            if ($option->getLabel() === 'Ethiopia Yirgacheffe') {
                $originId = $option->getValue();
            }
        }

        // 2. Save a product with custom attribute values.
        try {
            $product = $this->productRepository->get('PC-ETH-WHL-250', true);

        $criteria = $this->searchCriteriaBuilder
            ->addFilter(AddProductAttributes::ORIGIN, $originId)
            ->create();

            $output->writeln('found: ' . $item->getSku());

        $collection = $this->collectionFactory->create()
            ->addAttributeToSelect(['name', AddProductAttributes::ORIGIN, AddProductAttributes::ROAST_DATE])
            ->addAttributeToFilter(AddProductAttributes::ORIGIN, $originId);
        $output->writeln((string) $collection->getSelect());

        return Command::SUCCESS;

== Customer attributes

Customer attributes are created with `CustomerSetup`, which wraps `EavSetup` and also knows the customer-specific
tables. Two things differ from products. First, the attribute must be marked `+system => false+` for
`getCustomAttributes()` to include it, otherwise the REST and GraphQL representation of the customer omits it (the
Adobe documentation states this for programmatically created customer attributes). Second, a customer attribute needs
to be attached to an attribute set, a group and one or more forms with `used_in_forms`, because the customer forms are
built from `customer_form_attribute`. Without it the attribute exists but is never rendered or saved by the account
pages and the Admin customer form.

The option list of the favourite grind is fixed, so it is a code-based source model instead of rows in
`eav_attribute_option`:

[source,php]
----
<?php

{

    public const ESPRESSO = 'espresso';
    public const FILTER = 'filter';

    public function getAllOptions(): array

        if ($this->_options === null) {

                ['value' => self::ESPRESSO, 'label' => __('Espresso')],

== Custom attributes and extension attributes

The two kinds of attribute are different in storage and in purpose.

[cols="2,3,3",options="header"]
|===
| | Custom (EAV) attribute | Extension attribute

| Defined by | A row in `eav_attribute` (a merchant in the Admin, or a data patch) | `etc/extension_attributes.xml` of a module
| Stored in | The typed EAV value tables | Anywhere you decide: your own table, a join, or computed
| Visible in the Admin | Yes, in the attribute set form | No
| Data types | Scalars and option ids | Scalars, interfaces and arrays of interfaces
| In the API | Under `custom_attributes` | Under `extension_attributes`
| Typical use | Product descriptors and customer profile fields | Attaching extra structured data to an API object without changing its interface
|===

Third-party code cannot add methods to a core data interface, but most of them carry `getExtensionAttributes()` and
`setExtensionAttributes()`. Declare the attribute in XML, then populate it with a plugin on the repository, because the
framework only generates the container class and does not know where the value comes from. The generated
`ProductExtensionInterface` gains `getDaysSinceRoast()` and `setDaysSinceRoast()` from the declaration:

[source,xml]
----
<?xml version="1.0"?>
<config xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xsi:noNamespaceSchemaLocation="urn:magento:framework:Api/etc/extension_attributes.xsd">
    <extension_attributes for="Magento\Catalog\Api\Data\ProductInterface">
        <attribute code="days_since_roast" type="int"/>
    </extension_attributes>
</config>
----

Source: https://developer.adobe.com/commerce/php/development/components/add-attributes[Adobe Commerce developer docs: Add extension attributes to entities]

[source,php]
----
<?php

declare(strict_types=1);

namespace PocketCoffee\Eav\Plugin;

use Magento\Catalog\Api\Data\ProductInterface;
use Magento\Catalog\Api\Data\ProductSearchResultsInterface;
use Magento\Catalog\Api\ProductRepositoryInterface;
use PocketCoffee\Eav\Setup\Patch\Data\AddProductAttributes;

/**
 * Fills the days_since_roast extension attribute on products returned by the repository.
 */
class AddDaysSinceRoast
{
    public function afterGet(ProductRepositoryInterface $subject, ProductInterface $product): ProductInterface
    {
        return $this->addDays($product);
    }

    public function afterGetList(
        ProductRepositoryInterface $subject,
        ProductSearchResultsInterface $searchResults
    ): ProductSearchResultsInterface {
        foreach ($searchResults->getItems() as $product) {
            $this->addDays($product);
        }

        return $searchResults;
    }

    private function addDays(ProductInterface $product): ProductInterface
    {
        $attribute = $product->getCustomAttribute(AddProductAttributes::ROAST_DATE);
        if ($attribute === null || !$attribute->getValue()) {
            return $product;
        }
        $roasted = new \DateTimeImmutable((string) $attribute->getValue());
        $days = (int) $roasted->diff(new \DateTimeImmutable('today'))->format('%r%a');

        $extension = $product->getExtensionAttributes();
        $extension->setDaysSinceRoast($days);
        $product->setExtensionAttributes($extension);

        return $product;
    }
}
----

Source: https://developer.adobe.com/commerce/php/development/components/add-attributes[Adobe Commerce developer docs: Add extension attributes to entities]

The plugin is wired in the `di.xml` shown earlier (a plugin on the interface applies to its preference, the product
repository). `GET /rest/V1/products/PC-ETH-WHL-250` on the test installation returned
`+"extension_attributes": {"days_since_roast": 7}+` for a roast date of 2026-10-20 checked on 2026-10-27.
The plugin reads the existing extension attributes and writes back the same container, the pattern that avoids clobbering
the extension attributes of other modules. See xref:ecommerce/magento/plugins-events-and-observers.adoc[Plugins, Events
and Observers] for the interception rules and
xref:ecommerce/magento/service-contracts-and-repositories.adoc[Service Contracts and Repositories] for the
data-interface background.

Three behaviours of extension attributes to remember:

* The `+<join>+` child of an `+<attribute>+` makes a value filterable in `SearchCriteria`, by joining a reference table;
  with a join on the same table as the main entity the REST query becomes ambiguous and the filter field must be written
  as `+main_table.<column>+`.
* A `+<resources><resource ref="Vendor_Module::resource"/></resources>+` child restricts the attribute to API callers whose role holds the
  given ACL resource. There is no equivalent for `custom_attributes`, which cannot be permission-restricted.
* `ProductExtensionInterface` is generated code. It is empty in a vanilla installation and acquires methods from the
  merged declarations of all modules, so the class is regenerated when the XML changes (clear `generated/code` in
  developer mode).

== Caching and performance

* *Metadata caching.* `Magento\Eav\Model\Config` loads attribute metadata lazily and keeps it in the `eav` cache type.
  Since 2.3.4 the system EAV attributes are preloaded, and each module declares them in its `di.xml` as the
  `attributesForPreload` argument of `Magento\Eav\Model\Config`; a heavily used custom attribute can be added the same
  way. After a patch that creates or changes an attribute, run `bin/magento cache:flush`, otherwise the old metadata
  keeps being served.
* *Indexes carry the load on the storefront.* The `catalog_product_attribute` indexer (shown as "Product EAV" in the CLI)
  copies filterable attribute values into `catalog_product_index_eav`. On the test installation it held
  `(entity_id 2, attribute_id 147, store_id 1, value 4)` for the origin of the product, which is the row that layered
  navigation joins. The search-driven pages use the OpenSearch index built by `catalogsearch_fulltext`.
* *Select only what you need.* `+addAttributeToSelect('*')+` is the most common cause of slow custom listings: it joins every
  value table that has data. List the attributes, and set `used_in_product_listing` only on the attributes that a category
  card really shows.
* *Scope costs rows.* A store-view-scoped attribute on 18 variants and 2 store views can produce 36 value rows; a global
  attribute produces 18. Use the widest scope that the business rule allows.
* *Do not hand-write SQL for writes.* A direct insert into a value table skips the backend models, the validation, the
  index invalidation and the cache cleaning. Use the repository or `+Product::save+` through the repository.

== Pitfalls

* The `group` key accepts a name, and the name is looked up in each target set: a typo creates the attribute but leaves it
  unassigned, which looks like a missing field in the Admin. Verify with a query on `eav_entity_attribute`.
* Option ids differ between environments; compare attributes by option label in code and fixtures.
* `+required => true+` (the default is 1) on an attribute added to existing products makes every later product save fail
  until the field is filled. Create new attributes as optional and tighten them in a later patch.
* A data patch that is edited after it ran is not run again. Create a new patch class for each change and declare
  `getDependencies()` when one must follow another.
* `+user_defined => false+` makes the attribute a system attribute that the Admin cannot edit or delete.
* A `select` attribute with `+source => Table+` and no options created in the patch is valid but empty; add the options in
  the same patch or through `AddOptionToAttribute`.
* A custom source model that returns translated labels with `+__()+` must not be cached in a static variable across
  locales; the `AbstractSource` cache in `$_options` is per instance and per request.
* Removing a module directory without reverting its patches leaves attributes whose `source_model` points at a missing
  class, which breaks the Admin product form with a class-not-found error. Use `module:uninstall` with data removal, or
  write a patch that removes the attribute, before deleting the module. For the test module the uninstall command was not
  run because it switches the shared installation to maintenance mode; the module was left in place.
* Code that must run on Adobe Commerce with content staging cannot use the `entity_id` column in SQL; stay with the
  repositories.

== What was and was not run

The following ran on Mage-OS 3.6.0 (based on Magento 2.4.9): `php -l` and `phpcs --standard=Magento2` on the module (no
errors; warnings for the long XML schema line and an empty catch block), XML validation of `module.xml`, `di.xml`,
`extension_attributes.xml` and `category_form.xml` against the framework XSDs, `module:enable`, `setup:upgrade`,
`cache:flush`, the demo command, the REST calls (attribute read and create, attribute set, group and assignment,
product read, customer create with a custom attribute, category update in both store scopes), reindexing of the search
and attribute indexers, the GraphQL queries above and the SQL inspections quoted in the text. Not run: Adobe Commerce
content staging (`row_id`), the Admin attribute screens and category form in a browser (HTTP checks only),
`module:uninstall` with data removal, address attributes, swatch attributes, the flat catalog tables and ACCS.
