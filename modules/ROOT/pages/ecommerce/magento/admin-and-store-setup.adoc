This page walks through everything you set up in the Admin of a new Magento store before it sells: where things are, how
configuration scopes work, the store structure, general settings and currencies, the catalogue (attributes, attribute
sets, categories, products and inventory), customer groups, taxes, shipping and payment methods, promotions, content, search
engine optimisation, emails and the checks to run before launch. It is written for *Magento Open Source 2.4.9*, *Adobe
Commerce 2.4.9* and *Mage-OS 3.6.0*, checked on 2026-10-27. Every screen name, field label and menu path below was read
from the Admin of a real Mage-OS 3.6.0 install (the one built on
xref:ecommerce/magento/local-development-environments.adoc[Local Development Environments]), and every setting was
applied there with `bin/magento config:set` or the REST API and then checked from the storefront, the REST API or the Admin
itself. Adobe Commerce adds screens and features that Open Source and Mage-OS do not have; where the Adobe documentation
page carries an edition badge, trust the badge. The install itself is on
xref:ecommerce/magento/installation.adoc[Installation]; the data model behind attributes is on
xref:ecommerce/magento/eav-and-attributes.adoc[EAV and Attributes]; multi-store and B2B depth are on
xref:ecommerce/magento/catalog-multistore-and-b2b.adoc[Catalog, Multistore and B2B].

The running example is *Pocket Coffee*: a Madrid shop with a Spanish store view (the default) and an English one, euro
prices that include VAT, a configurable product "Single-origin beans" (origin by bag size), a simple "Starter kit", a
"Coffee Club" customer group with 10 percent off the beans, Spanish shipping at 4.90 EUR (free from 40 EUR) and a flat
9.90 EUR rate to six other countries.

image::ecommerce-magento-admin-setup-order.svg["Nine steps to set up a store from the Admin: general settings, stores and views, attributes, catalog, customers, taxes, shipping and payment, CMS and SEO, and the pre-launch checks",width=1000]

The order matters in a few places. Create the store views and the general settings first, because language, currency and URL
settings affect everything you create after them. Create attributes before products, tax classes before products that use them,
and set the URL suffixes before you create categories and products, because the URL rewrites are generated when a record
is saved. Run the Pocket Coffee examples from the command line in this order and each step finds what it needs.

== Administrators, roles and sign-in

Create the first administrator with the installer (see the installation page) and further ones from the command line or
under *System > Permissions > All Users*. Restrict what each person can do with *System > Permissions > User Roles*,
which ties a role to a set of resources (the same ACL resources that `acl.xml` files define in modules).

[source,bash]
----
bin/magento admin:user:create --admin-user=grace --admin-password='<admin-password>' \
  --admin-email=grace@example.test --admin-firstname=Grace --admin-lastname=Hopper
bin/magento admin:user:unlock grace        # after too many failed logins
bin/magento security:tfa:providers         # list the two-factor providers (only while Magento_TwoFactorAuth is enabled)
bin/magento security:tfa:reset <user> <provider>   # reset the second factor of one user
----

Source: https://experienceleague.adobe.com/en/docs/commerce-admin/systems/security/tfa/security-two-factor-authentication[Adobe: Two-factor authentication]

`admin:user:create` printed "Created Magento administrator user named grace" in the test; the other commands appear in
`bin/magento list`. *Stores > Configuration > Advanced > Admin > Security* holds the policies you should read before
launch: *Admin Session Lifetime (seconds)*, *Maximum Login Failures to Lockout Account*, *Lockout Time (minutes)*,
*Minimum Admin Password Length*, *Password Lifetime (days)*, *Password Change*, *Admin Account Sharing*,
*Login is Case Sensitive*, *Add Secret Key to URLs* and the password-reset limits. Two-factor authentication is on by
default (module `Magento_TwoFactorAuth`) and applies to the Admin and to admin API tokens: on the test install
`POST /rest/V1/integration/admin/token` answered "Please ask an administrator with sufficient access to configure 2FA
first." until the module was disabled on a laptop. Do not disable it anywhere real. When Adobe IMS sign-in is enabled
instead (Adobe Commerce), the native two-factor screens are disabled because Adobe IMS handles the sign-in.

== Configuration scopes and how to change a setting

Almost every setting under *Stores > Configuration* can be set for the whole installation (*Default Config*), for a
*website*, or for a *store view*. Magento reads a value from the most specific scope that has one and falls back
outward, and finally to the module's `config.xml` default. Values written to `app/etc/env.php` or `app/etc/config.php`
override the database and make the field read-only in the Admin.

image::ecommerce-magento-scope-hierarchy.svg["Configuration scopes: the global scope, the websites pocketcoffee_eu and pocketcoffee_us, one store under each and the store views pc_es, pc_en and pc_us, with the order in which a value is resolved (store view, then website, then default scope)",width=1000]

The same setting is available in three equivalent ways, which is what makes a store reproducible:

[source,bash]
----
bin/magento config:set general/store_information/name "Pocket Coffee"                      # default scope
bin/magento config:set --scope=websites --scope-code=base general/store_information/name "Pocket Coffee B2C"
bin/magento config:set --scope=stores --scope-code=en general/locale/code en_US           # store view en
bin/magento config:show --scope=websites --scope-code=base general/store_information/name   # Pocket Coffee B2C
bin/magento config:set --lock-env web/cookie/cookie_lifetime 7200    # Value was saved in app/etc/env.php and locked.
----

Source: https://experienceleague.adobe.com/en/docs/commerce-operations/configuration-guide/cli/configuration-management/set-configuration-values[Adobe: Set configuration values]

Facts observed with these commands: the path must exist in a module's `system.xml` (an unknown path prints `+The "x" path doesn't exist. Verify and try again.+`); `config:show` prints only the values stored at the scope you ask for, so a
store view that inherits prints an empty line; a locked value cannot be changed again without `--lock-env`
(`The value you set has already been locked. To change the value, use the --lock-env option.`); `--lock-config` writes to
the shared `config.php` instead. Values stored with `--lock-env` end up under a `system` key of `env.php`, for example
`{"default":{"web":{"cookie":{"cookie_lifetime":"7200"}}}}`. A change made with the CLI shows in the Admin at once; the
Tax page of the test install showed the values set below as *Including Tax*, *After Discount* and *Total*.

== Websites, stores and store views

A *website* holds shared customers, a base currency and often payment and shipping methods; a *store* (a store group) is
a catalogue with a root category and a default store view; a *store view* is one language and presentation of a store. A
single-language shop still has one website, one store and one store view; Pocket Coffee adds a second store view for
English. The four entities are managed under *Stores > Settings > All Stores* and can be listed from the command line.

[source,bash]
----
bin/magento store:list
bin/magento store:website:list
----

----
+----+------------+----------+---------+---------+------------+-----------+
| ID | Website ID | Group ID | Name    | Code    | Sort Order | Is Active |
+----+------------+----------+---------+---------+------------+-----------+
| 0  | 0          | 0        | Admin   | admin   | 0          | 1         |
| 1  | 1          | 1        | Español | default | 0          | 1         |
| 2  | 1          | 1        | English | en      | 20         | 1         |
+----+------------+----------+---------+---------+------------+-----------+
----

Source: https://experienceleague.adobe.com/en/docs/commerce-admin/stores-sales/site-store/stores[Adobe: Stores and store views]

There is no CLI command and no REST endpoint to create a store view in 2.4.9; use *Stores > All Stores > Create Store View*, or
a short PHP script that bootstraps the framework and uses the store resource model of `Magento_Store` (this is what
produced the table above, and it is idempotent):

[source,php]
----
<?php
use Magento\Framework\App\Bootstrap;
use Magento\Store\Model\ResourceModel\Store as StoreResource;
use Magento\Store\Model\StoreFactory;
use Magento\Store\Model\StoreManagerInterface;

require __DIR__ . '/app/bootstrap.php';
$om = Bootstrap::create(BP, $_SERVER)->getObjectManager();
$om->get(\Magento\Framework\App\State::class)->setAreaCode('adminhtml');

$group = $om->get(StoreManagerInterface::class)->getGroup(1);
$store = $om->get(StoreFactory::class)->create()->load('en', 'code');
if (!$store->getId()) {
    $store->setCode('en')->setName('English')
        ->setWebsiteId($group->getWebsiteId())->setGroupId($group->getId())
        ->setSortOrder(20)->setIsActive(1);
    $om->get(StoreResource::class)->save($store);
}
----

Source: https://experienceleague.adobe.com/en/docs/commerce-admin/stores-sales/site-store/stores[Adobe: Stores and store views]

Run it as the file system owner from the project root (`php create-store-view.php`), then set the locale of the new
view, which needs the language to exist (`bin/magento info:language:list` printed 94 locales, including `es_ES`, `en_US`,
`ca_ES` and `de_DE`; further language packs install with Composer):

[source,bash]
----
bin/magento config:set --scope=stores --scope-code=en general/locale/code en_US
curl -s -o /dev/null -w "%{http_code}\n" "http://localhost:8093/single-origin-beans.html?___store=en"    # 200
----

Source: https://experienceleague.adobe.com/en/docs/commerce-admin/stores-sales/site-store/stores[Adobe: Stores and store views]

By default a store view is chosen by a cookie or the `+___store+` query parameter; to give each language its own URL set
*Add Store Code to Urls* (`web/url/use_store`) under *General > Web > Url Options* or give each store view its own base
URL under *Base URLs*. The Pocket Coffee names for the website, the store and the first store view (the installer names the website *Main
Website* and the view *Default Store View*) were set with the same kind of script.

== Currencies

*Stores > Configuration > General > Currency Setup > Currency Options* has three fields: *Base Currency* (`currency/options/base`,
the currency the catalogue is priced in and the one orders are charged in), *Default Display Currency*
(`currency/options/default`) and *Allowed Currencies* (`currency/options/allow`). Pocket Coffee's base and display
currency is EUR, set by the installer; adding USD makes it selectable:

[source,bash]
----
bin/magento config:set currency/options/allow EUR,USD
curl -s http://localhost:8093/rest/V1/directory/currency            # as an administrator
----

Source: https://experienceleague.adobe.com/en/docs/commerce-admin/stores-sales/site-store/currency/currency-configuration[Adobe: Configure currency]

The *Catalog Price Scope* (`catalog/price/scope`, *Stores > Configuration > Catalog > Catalog > Price*) is global by
default; set it to *Website* to price the same product differently per website, which also lets each website have its
own base currency.

The exchange rates are managed under *Stores > Currency > Currency Rates* (the page lists the rates between the allowed
currencies and an *Import Service* selector) and stored in `directory_currency_rate`. A new install already holds a rate
of 1.415 USD for 1 EUR, which is a placeholder: a store that shows a second currency must replace it with a real rate
or schedule an import. The import services in the 3.6.0 code are *Fixer.io (legacy)*, *Fixer Api (APILayer)* and
*Currency Converter API*, each with an *API Key* and *Connection Timeout in Seconds*, plus *Scheduled Import Settings*
(*Enabled*, *Service*, *Start Time*, *Frequency* and the error-email fields). Adobe states that Fixer.io was deprecated
and replaced by Fixer API (APILayer) from 2.4.6. Scheduled imports run in cron.

Checked from the storefront side: with USD allowed and the placeholder rate, the GraphQL request below returned the
starter kit at 33.96 USD (24.00 EUR x 1.415):

[source,bash]
----
curl -s -X POST http://localhost:8093/graphql -H 'Content-Type: application/json' \
  -H 'Content-Currency: USD' -H 'Store: en' \
  -d '{"query":"{ products(filter:{sku:{eq:\"PC-KIT\"}}) { items { sku name price_range { minimum_price { final_price { value currency } } } } } }"}'
----

Source: https://experienceleague.adobe.com/en/docs/commerce-admin/stores-sales/site-store/currency/currency-configuration[Adobe: Configure currency]

The header is `Content-Currency`; a request that sends `Currency: USD` was ignored and returned EUR. Customers *see* the
display currency, and the amounts are converted at the stored rate, but the payment method receives the order in the
base currency unless it supports the display currency, so confirm with your payment provider before you promise
"charge in USD". Currency symbols are customised under *Stores > Currency > Currency Symbols*.

== Catalog

=== Attributes and attribute sets

An *attribute* is a property of a product; an *attribute set* is the list of attributes (arranged in groups) a product
offers in the Admin form. Every product belongs to one set, and the set decides which fields you see. The Default set
(id 4) has 64 attributes; a custom set starts as a copy of it. The model behind this is described on
xref:ecommerce/magento/eav-and-attributes.adoc[EAV and Attributes]. For Pocket Coffee, one set "Coffee" with the
attributes *Origin*, *Grind*, *Bag size* and *Roast date* was created through the REST API (the Admin equivalent is
*Stores > Attributes > Attribute Set* and *Stores > Attributes > Product*). Set `BASE` and `TOKEN` first:

[source,bash]
----
BASE=http://localhost:8093
TOKEN=$(curl -s -X POST $BASE/rest/V1/integration/admin/token -H 'Content-Type: application/json' \
  -d "{\"username\":\"admin\",\"password\":\"${MAGENTO_ADMIN_PASSWORD}\"}" | tr -d '"')
api() { curl -s -g -X "$1" "$BASE/rest$2" -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' ${3:+-d "$3"}; }

# an attribute set cloned from Default (skeletonId 4)
api POST /V1/products/attribute-sets \
  '{"attributeSet":{"attribute_set_name":"Coffee","sort_order":1,"entity_type_id":4},"skeletonId":4}'
# {"attribute_set_id":9,"attribute_set_name":"Coffee","sort_order":1,"entity_type_id":4}

# a dropdown attribute used in layered navigation, with a label per store view
api POST /V1/products/attributes '{"attribute":{"attribute_code":"origin","frontend_input":"select",
  "entity_type_id":"4","is_user_defined":true,"default_frontend_label":"Origin",
  "frontend_labels":[{"store_id":1,"label":"Origen"},{"store_id":2,"label":"Origin"}],
  "is_filterable":true,"is_filterable_in_search":true,"is_searchable":true,"is_visible_on_front":true,"scope":"global",
  "options":[{"label":"Ethiopia Yirgacheffe","value":"ETH"},{"label":"Colombia Huila","value":"COL"},{"label":"Brazil Cerrado","value":"BRA"}]}}'

# put the attribute into the Product Details group of the Coffee set
api POST /V1/products/attribute-sets/attributes \
  '{"attributeSetId":9,"attributeGroupId":31,"attributeCode":"origin","sortOrder":10}'
----

Source: https://developer.adobe.com/commerce/webapi/rest/tutorials/configurable-product/[Adobe developer docs: Create a configurable product]

These calls returned, in order, the new set (id 9), the attribute id (145 for `origin`, 146 for `grind`, 148 for
`bag_size`, 149 for `roast_date`) and `"207"`, `"208"`, `"209"`, `"210"` for the four set assignments (the id of the
entity-attribute row). The attribute group id 31 is *Product Details* of the new set; list the groups of a set with
`GET /V1/products/attribute-sets/groups/list?searchCriteria[filter_groups][0][filters][0][field]=attribute_set_id&searchCriteria[filter_groups][0][filters][0][value]=9`.
Three traps appeared:

* *Option values that are numbers are read as option ids.* Creating `bag_size` with the options `250` and `1000` failed with
  `+SQLSTATE[23000]: Integrity constraint violation: 1452 Cannot add or update a child row: a foreign key constraint fails+`
  (on the `eav_attribute_option_value` table). Give options labels and non-numeric `value` strings, then read the generated option ids back
  from `GET /V1/products/attributes/<code>` (for `origin`: 4 Ethiopia, 5 Colombia, 6 Brazil).
* *Do not send a blank first option.* The REST response always lists an empty first option itself; sending your own
  produced a second blank entry in the dropdown.
* *A failed create still consumes an attribute id* (id 147 was lost to the failed `bag_size`).

An attribute used to build variants must have `scope` `global` and be a dropdown or swatch input. The attribute
screen (*Stores > Attributes > Product > Add New Attribute*) has the tabs *Properties*, *Manage Labels* and *Storefront
Properties*. *Properties* holds *Default Label*, *Catalog Input Type for Store Owner* (Text Field, Text Area, Text Editor,
Page Builder, Date, Date and Time, Yes/No, Multiple Select, Dropdown, Price, Media Image, Visual Swatch, Text Swatch,
Fixed Product Tax), *Values Required*, *Attribute Code*, *Scope*, *Default Value*, *Unique Value* and *Input Validation for
Store Owner*. *Storefront Properties* holds *Use in Search*, *Search Weight*, *Visible in Advanced Search*, *Comparable on
Storefront*, *Use in Layered Navigation*, *Use in Search Results Layered Navigation*, *Position*, *Use for Promo Rule
Conditions*, *Allow HTML Tags on Storefront*, *Visible on Catalog Pages on Storefront*, *Used in Product Listing* and *Used
for Sorting in Product Listing*; the API fields `is_searchable`, `is_filterable`, `is_filterable_in_search`,
`is_comparable`, `is_visible_on_front`, `used_in_product_listing` and `used_for_sort_by` map to them.

=== Categories

Categories live in a tree below the store's *root category* (*Default Category*, id 2, set per store under *Stores > All
Stores*). Pocket Coffee has two: Beans (id 3) and Equipment (id 4), created with:

[source,bash]
----
api POST /V1/categories '{"category":{"parent_id":2,"name":"Beans","is_active":true,"include_in_menu":true,
  "custom_attributes":[{"attribute_code":"url_key","value":"beans"}]}}'
----

Source: https://developer.adobe.com/commerce/webapi/rest/[Adobe developer docs: REST API]

=== Products

*Catalog > Inventory > Products* lists and edits products. The *Add Product* menu of the
test install offered Simple, Virtual, Downloadable, Configurable (variants chosen by attribute values), Grouped and Bundle
products; Adobe Commerce adds more, such as the gift card. Pocket Coffee has a configurable parent `PC-BEANS` whose variants are simple products with the SKU
pattern `PC-<ORIGIN3>-<GRIND3>-<SIZE>` (four of the 18 are shown) and a simple `PC-KIT`.

[source,bash]
----
# one variant: Ethiopia, whole bean, 250 g (option ids: origin 4, grind 7, bag size 10; tax class 4 = Food)
api POST /V1/products '{"product":{"sku":"PC-ETH-WHL-250",

* *Visibility*: variants are `1` (Not Visible Individually), the parent `4` (Catalog, Search).
* *Websites*: a product that is not assigned to a website is invisible. The Admin product form has a *Product in
  Websites* section; the API takes `extension_attributes.website_ids`.
* *Tax class*: the product's *Tax Class* attribute (here `tax_class_id` 4, "Food (reduced VAT)") selects the tax rule row;
  see <<taxes,Taxes>>.
* *Inventory*: the 2.4.9 install runs Multi-Source Inventory. *Stores > Inventory > Sources* and *Stocks* define where
  stock lives and which sales channel it feeds (the REST API listed the source `default`, "Default Source", and the stock
  with id 1, "Default Stock"), *Reservations* holds the salable-quantity ledger, and `stock_item.qty` on a product wrote to
  the default source (`inventory_source_item` held quantity 50 for `PC-KIT`). After the Spanish test order below, two
  rows in `inventory_reservation` existed, `get-product-salable-quantity` for `PC-KIT` answered 49 and the source
  quantity was still 50: an order reserves stock, and the source quantity drops when the shipment is created.
* *URL key*: each product and category has a `url_key`; the URL is `<key>` plus the product suffix `.html`.
* *Indexing*: all 11 indexers run in *Update by Schedule* mode, so a product saved through the API reaches search and
  category pages only after cron runs the indexer. `bin/magento indexer:status` showed `idle (1 in backlog)` for the
  Product Price, Product EAV and Catalog Search indexers after a product change; `bin/magento indexer:reindex` clears it
  immediately.

The starter kit is a plain simple product (`PC-KIT`, 24.00, weight 1.1, category Equipment, attribute set Default). The
storefront then served `/single-origin-beans.html` and `/starter-kit.html` with HTTP 200.

== Taxes [[taxes]]

Magento's tax model has four parts: *tax classes* (labels for products, customers and shipping), *tax rates* (a rate for a
country, region and postcode pattern), *tax rules* (which class combinations use which rates) and the *calculation
settings* that decide how the maths is done. Pocket Coffee sells a food product with a reduced VAT rate and equipment at
the standard rate, prices include VAT, and the customer pays the tax of the shipping address. The rates 10 and 21 percent
below are illustrative values for the walkthrough, not tax advice; take the rates, thresholds and rules for each
country from your tax adviser.

[source,bash]
----
api POST /V1/taxClasses '{"taxClass":{"class_name":"Food (reduced VAT)","class_type":"PRODUCT"}}'      # "4"
api POST /V1/taxRates '{"taxRate":{"tax_country_id":"ES","tax_region_id":0,"tax_postcode":"*","code":"ES-VAT-10","rate":10}}'
api POST /V1/taxRates '{"taxRate":{"tax_country_id":"ES","tax_region_id":0,"tax_postcode":"*","code":"ES-VAT-21","rate":21}}'
api POST /V1/taxRules '{"rule":{"code":"Spain - food 10%","priority":0,"position":1,
  "customer_tax_class_ids":[3],"product_tax_class_ids":[4],"tax_rate_ids":[3],"calculate_subtotal":false}}'
api POST /V1/taxRules '{"rule":{"code":"Spain - standard 21%","priority":0,"position":2,
  "customer_tax_class_ids":[3],"product_tax_class_ids":[2],"tax_rate_ids":[4],"calculate_subtotal":false}}'
----

Source: https://experienceleague.adobe.com/en/docs/commerce-admin/stores-sales/site-store/taxes/tax-rules[Adobe: Tax rules]

The Admin screens are *Stores > Taxes > Tax Rules* and *Tax Zones and Rates* (with *System > Data Transfer > Import/Export
Tax Rates* for bulk loads). A tax rate with postcode `+*+` matches every postcode in the country. Product tax class 2,
*Taxable Goods*, exists after the install and is the default for products; class 3, *Retail Customer*, is the default
customer class.

== Shipping

*Stores > Configuration > Sales > Shipping Settings* holds the *Origin* address (set above) and the optional *Shipping
Policy Parameters*; *Delivery Methods* configures the carriers. The Mage-OS install lists these carriers: *Flat Rate*, *Free
Shipping*, *Table Rates*, *In-Store Delivery* (in-store pickup), and the live carriers *UPS*, *FedEx*, *DHL* and *USPS*
(the last four need accounts with the carrier). Each carrier has *Enabled*, *Title*, *Method Name*, *Ship to Applicable
Countries* / *Ship to Specific Countries*, *Show Method if Not Applicable*, *Displayed Error Message* and *Sort Order*,
and the offline carriers add *Calculate Handling Fee* and *Handling Fee*.

Pocket Coffee has two zones (Spain; six other countries) and a free-shipping threshold:

[source,bash]
----
# Zone 1, Spain: flat rate per order, only for ES
bin/magento config:set carriers/flatrate/active 1
bin/magento config:set carriers/flatrate/type O                 # O = Per Order (I = Per Item)
bin/magento config:set carriers/flatrate/price 4.90
bin/magento config:set carriers/flatrate/sallowspecific 1
bin/magento config:set carriers/flatrate/specificcountry ES
bin/magento config:set carriers/flatrate/title "Pocket Coffee shipping"
bin/magento config:set carriers/flatrate/name "Spain, 1 to 3 days"
# free shipping from 40 EUR, only for ES
bin/magento config:set carriers/freeshipping/active 1
bin/magento config:set carriers/freeshipping/free_shipping_subtotal 40
bin/magento config:set carriers/freeshipping/sallowspecific 1
bin/magento config:set carriers/freeshipping/specificcountry ES
# Zone 2: table rates for six countries, condition = weight
bin/magento config:set carriers/tablerate/active 1
bin/magento config:set carriers/tablerate/condition_name package_weight
bin/magento config:set carriers/tablerate/sallowspecific 1
bin/magento config:set carriers/tablerate/specificcountry DE,FR,IT,PT,NL,BE
bin/magento config:set carriers/tablerate/title "Pocket Coffee Europe"
bin/magento config:set carriers/tablerate/name "European Union, 3 to 6 days"
----

Source: https://experienceleague.adobe.com/en/docs/commerce-admin/config/sales/shipping-settings[Adobe: Shipping settings]

The *Table Rates* carrier needs rows. They are imported from a CSV file in the Admin, at *website scope* (switch the scope
selector to the website, then use *Import* next to *Table Rates* in *Delivery Methods*, which is not shown at the default
scope). The CSV has five columns in this order: `Country`, `Region/State`, `Zip/Postal Code`, `Weight (and above)` (the
header changes with the chosen *Condition*: *Weight vs. Destination*, *Price vs. Destination* or *# of Items vs.
Destination*) and `Shipping Price`. The importer accepts ISO 3-letter country codes and stored the two-letter code:

----
Country,Region/State,Zip/Postal Code,Weight (and above),Shipping Price
DEU,*,*,0,9.90
FRA,*,*,0,9.90
ITA,*,*,0,9.90
PRT,*,*,0,9.90
NLD,*,*,0,9.90
BEL,*,*,0,9.90
----

The import was performed with the Admin's own form (a multipart POST of the CSV together with the *Condition* to the
configuration save URL at website scope). It answered "You saved the configuration." and `shipping_tablerate` held six
rows (`website_id` 1, `dest_country_id` DE and so on, `condition_name` `package_weight`, `condition_value` 0, `price` 9.90).
Two errors are worth knowing. Posting the file without the *Condition* field failed with "Something went wrong while
importing table rates." (an `Array to string conversion` in the CSV column resolver in the log). And rows inserted with
`website_id` 0 (the "all websites" id) were *not* used: the rate lookup matches the website of the request, so rows must
belong to website 1 when the store runs on website 1.

Checked with the shipping estimate API for a postcode of the destination:

[cols="3,3",options=header]
|===
|Cart and destination |Methods returned (amount)

|Guest, kit and one 250 g bag (33.90 incl. VAT), Spain
|Flat rate 4.90 only

|Guest, kit and two bags (43.80), Spain
|Free shipping 0.00 and flat rate 4.90

|Guest, 1 kg bag, Germany
|Table rate 9.90 ("European Union, 3 to 6 days")

|Any cart, United States
|No method: the country is not allowed
|===

Both rates stay available when free shipping qualifies: Magento offers every applicable method, so the free method is
listed next to the 4.90 flat rate and the customer picks. To remove the paid method when the threshold is met, Adobe's documentation describes a *Cart Price Rule* with a
free-shipping action (not run here), or sort and label the methods so the cheapest is obvious. About the threshold, the *Include Tax to Amount* switch (`carriers/freeshipping/tax_including`) was *No*, yet
the amount compared was the VAT-inclusive subtotal after discounts: with the member cart (37.83 excluding VAT, 41.82
including VAT after the 1.98 discount) thresholds of 38 and 40 offered free shipping and 42 did not, with the switch at
either value. That is the behaviour when catalogue prices include tax; re-test it if you switch to prices excluding tax.

Also note that the offline carriers do not enforce a parcel weight limit. A cart of six 1 kg bags (6 kg) still received the 9.90
table rate to Germany. A 5 kg limit per parcel must be modelled with table-rate tiers, a live carrier's *Maximum Package
Weight*, or a validation module.

== Promotions

Two kinds of rule give discounts. *Catalog Price Rules* change the displayed price of products matching conditions (the
indexer `catalogrule_rule` applies them); *Cart Price Rules* apply in the cart and can use coupons. The Coffee Club rule
is a cart price rule restricted to the Coffee Club group and to category Beans:

[source,bash]
----
api POST /V1/salesRules '{"rule":{"name":"Coffee Club 10% on beans","website_ids":[1],"customer_group_ids":[4],
  "uses_per_customer":0,"is_active":true,"stop_rules_processing":false,"is_advanced":true,"sort_order":0,
  "simple_action":"by_percent","discount_amount":10,"discount_qty":0,"discount_step":0,"apply_to_shipping":false,
  "coupon_type":"NO_COUPON",
  "condition":{"condition_type":"Magento\\SalesRule\\Model\\Rule\\Condition\\Combine","aggregator_type":"all","value":"1"},
  "action_condition":{"condition_type":"Magento\\SalesRule\\Model\\Rule\\Condition\\Product\\Combine",
    "aggregator_type":"all","value":"1","conditions":[
    {"condition_type":"Magento\\SalesRule\\Model\\Rule\\Condition\\Product","operator":"==",
     "attribute_name":"category_ids","value":"3"}]}}}'
----

Source: https://experienceleague.adobe.com/en/docs/commerce-admin/marketing/promotions/cart-rules/price-rules-cart[Adobe: Cart price rules]

In the Admin this is *Marketing > Promotions > Cart Price Rules*, with the customer group in *Customer Groups* and the
category in the *Actions* tab. The condition field in the API is `attribute_name`; sending `attribute` fails with
`"%fieldName" is not supported`. The rule discounted only the two bean lines (1.98 EUR) and left the kit alone; it applied
once the customer was signed in as a Coffee Club member. Guests, who are in group 0, saw no discount.

== Search engine optimisation settings

Magento sets sensible technical defaults; your work is URLs, meta data, the sitemap and robots.txt.

*URLs*. *Stores > Configuration > General > Web > Search Engine Optimization > Use Web Server Rewrites* (`web/seo/use_rewrites`)
removes `index.php` from URLs. *Catalog > Catalog > Search Engine Optimization* offers *Product URL Suffix*, *Category URL
Suffix*, *Use Categories Path for Product URLs*, *Create Permanent Redirect for URLs if URL Key Changed*, *Generate
"category/product" URL Rewrites*, *Apply transliteration for product URL*, *Product URL Rewrite Scope*, *Page Title
Separator* and *Use Canonical Link Meta Tag* for categories and products. Pocket Coffee uses `.html` for products and an empty
suffix for categories (set before the categories were created):

[source,bash]
----
bin/magento config:set catalog/seo/product_url_suffix .html
bin/magento config:set catalog/seo/category_url_suffix ""
bin/magento config:set catalog/seo/save_rewrites_history 1
bin/magento config:set catalog/seo/product_use_categories 0
bin/magento config:set catalog/seo/product_canonical_tag 1
bin/magento config:set catalog/seo/category_canonical_tag 1
----

Source: https://experienceleague.adobe.com/en/docs/commerce-admin/marketing/seo/seo-overview[Adobe: SEO overview]

The result: `/beans`, `/equipment`, `/single-origin-beans.html` and `/starter-kit.html`. A rewrite is stored as a row of
`url_rewrite` (`request_path`, `target_path`, `redirect_type`, `store_id`); *Marketing > SEO & Search > URL Rewrites* manages them.
With *Create Permanent Redirect for URLs if URL Key Changed* on, changing the starter kit's URL key to
`starter-kit-grinder` made the old URL answer `301` to the new one (`starter-kit.html` redirected to
`http://localhost:8093/starter-kit-grinder.html`) and added the row `+starter-kit.html -> starter-kit-grinder.html+` with
redirect type 301. Settle the suffixes before you create the categories and products, because the rewrites are written when a record is saved.

*Meta data*. Each product, category and CMS page has a meta title, description and keywords. On the configurable
product page the rendered head contained `<meta name="description" content="Ethiopia, Colombia and Brazil beans roasted in
Madrid, in 250 g and 1 kg bags."/>`, `<meta name="robots" content="INDEX,FOLLOW"/>`, `<title>Single-origin specialty coffee
beans</title>`, `<link rel="canonical" href="http://localhost:8093/single-origin-beans.html" />`, Open Graph tags
(`og:title`, `og:url`, `og:image`, `og:description`) and the product wrapped in `schema.org/Product` microdata.
No `hreflang` link and no JSON-LD block was present: add `hreflang` for the two store views and JSON-LD with a theme
change or an extension if you need them.

*Sitemap*. *Marketing > SEO & Search > Site Map* defines one or more sitemap files; *Stores > Configuration > Catalog > XML
Sitemap* has *Categories Options*, *Products Options* and *CMS Pages Options* (frequency and priority), *Generation
Settings* (a cron schedule), *Sitemap File Limits* and *Search Engine Submission Settings* (add the sitemap to robots.txt).
The sitemap grid entry and generation were created with a script that uses the sitemap model, and the resulting
`pub/sitemap.xml` listed the home page, both categories, the privacy page, the shipping page and both products with
`lastmod`, `changefreq` and `priority`; the cron job `sitemap_generate` (class `Magento\Sitemap\Model\Observer`) regenerates the files on the schedule you set.

*robots.txt*. Magento serves `/robots.txt` from configuration, so no file is deployed: set the content in the
`design/search_engine_robots/custom_instructions` value (*Content > Design > Configuration > Search Engine Robots*) and
the default meta robots in `design/search_engine_robots/default_robots`:

[source,bash]
----
bin/magento config:set design/search_engine_robots/custom_instructions $'User-agent: *\nDisallow: /checkout/\nSitemap: http://localhost:8093/sitemap.xml'
bin/magento config:set design/search_engine_robots/default_robots INDEX,FOLLOW
curl -s http://localhost:8093/robots.txt
----

----
User-agent: *
Disallow: /checkout/
Sitemap: http://localhost:8093/sitemap.xml
----

Source: https://experienceleague.adobe.com/en/docs/commerce-admin/marketing/seo/sitemap-xml[Adobe: Sitemap]

The value you edit is `custom_instructions`; `default_custom_instructions` holds the factory text that the reset button
restores, and `design/head/default_robots` is not a valid path (`config:set` rejects it). Keep the staging and development hosts at
`NOINDEX,NOFOLLOW`.

*Speed and links*. Magento's *Full Page Cache*, JavaScript and CSS minification and bundling, image formats and the
*Back/Forward Cache* and *Speculative Loading* settings under *Advanced > System* are performance topics covered on
xref:ecommerce/magento/caching-indexing-and-performance.adoc[Caching, Indexing and Performance]. The books and Adobe
recommend fast pages, clean URLs, one canonical URL per page and a sitemap as the base; product and category copy is the
rest of the work.

== Email

Transactional emails use templates under *Marketing > Communications > Email Templates* and the sender identities in
*Store Email Addresses*. *Stores > Configuration > Sales > Sales Emails* enables each order, invoice, shipment and credit memo email with a
template and optional copy recipients, *Contacts* configures the contact form, and *Newsletter* the subscription
emails. Email delivery needs a transport (see *Mail Sending Settings* above); on a laptop use a mail catcher. Brand the
templates and *Stores > Configuration > Sales > Sales > Invoice and Packing Slip Design* before launch: Adobe's pre-launch checklist asks for
both.

== Pre-launch checklist

image::ecommerce-magento-launch-checklist.svg["Launch checklist grouped into configuration, sales and tax, content and SEO, security and operations, with the commands to verify them",width=1000]

Adobe's prelaunch checklist (updated 2026-10-08) groups the checks as *General settings* (store URLs, a signed and
trusted certificate for the base URL domain, all store email addresses), *Marketing settings* (email templates, sales
communications such as invoices and packing slips, Google tools), *Sales settings* (cart options, checkout options with
terms and guest checkout, taxes, delivery methods, payment methods with test transactions in sandbox mode) and *System
settings* (cron jobs running at the right interval). The table adds the verification command for each item and the
Pocket Coffee value.

[cols="2,3,3",options=header]
|===
|Check |How to verify |Pocket Coffee

|Store URLs and HTTPS
|`bin/magento config:show web/secure/base_url`, a certificate from a certificate authority, `curl -I` the home page and the Admin URI
|`https://shop.example.com/`, HSTS on after HTTPS is stable

|Mode and cache
|`bin/magento deploy:mode:show`, `bin/magento cache:status`
|`production`, all cache types enabled

|Cron and indexers
|`crontab -l`, `+SELECT status, COUNT(*) FROM cron_schedule GROUP BY status+`, `bin/magento indexer:status`
|every minute; indexers `Ready`, backlog 0

|Emails
|Order a test product and read the confirmation; check `+trans_email/*+` and the transport
|real mailboxes, branded templates

|Taxes
|Add each product class to a cart for each country you sell to and read the totals
|10 percent beans, 21 percent equipment and shipping, tax shown inclusive

|Shipping
|`POST /V1/guest-carts/:cartId/estimate-shipping-methods` for every zone, including a country you do not serve
|Spain 4.90 and free from 40, six countries 9.90, US none

|Payment
|One real order in live mode with a small amount, then refund it
|offline methods for the test, a provider for production

|Catalogue and SEO
|View-source of a product page, `/robots.txt`, `/sitemap.xml`, 301 after a URL key change
|canonical, meta description, sitemap and robots as above

|Security
|2FA on for every administrator, random Admin URI, `bin/magento config:show admin/security/session_lifetime`, latest security patch
|Security bulletins read and applied, see xref:ecommerce/magento/security.adoc[Security]

|Backups and rollback
|A restored copy of the database and `pub/media` opens in a scratch environment
|dump script, tested restore
|===

Source: https://experienceleague.adobe.com/en/docs/commerce-admin/start/setup/prelaunch-checklist[Adobe: Prelaunch checklist]

A launch is a deployment as well as a configuration exercise: the configuration above is exported with `bin/magento
app:config:dump` into `app/etc/config.php` so every environment gets the same values, secrets stay in `env.php` or in
environment variables, and the deployment itself follows the build and release steps of
xref:ecommerce/magento/upgrades.adoc[Upgrades].
